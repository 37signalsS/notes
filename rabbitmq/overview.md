# Обзор RabbitMQ

RabbitMQ — это брокер сообщений с открытым исходным кодом, который поддерживает несколько протоколов обмена данными (AMQP 0-9-1, AMQP 1.0, MQTT, STOMP). В отличие от классической Kafka, работающей по Pull-модели, RabbitMQ традиционно использует **Push-модель**, но с версии 3.9 также поддерживает **Streams** (модель распределенного лога).

## Основные концепции

### Архитектура (AMQP 0-9-1)
Взаимодействие в классическом RabbitMQ строится вокруг следующих сущностей:
1. **Producer (Продюсер)** — отправляет сообщения в брокер, указывая название Exchange и Routing Key.
2. **Exchange (Обменник)** — **Роутер**. Принимает сообщения и на основе правил маршрутизации (биндингов) перенаправляет их в очереди. Exchange не хранит сообщения; если нет подходящей очереди, сообщение будет уничтожено (если не настроен DLX или альтернативный обменник).
3. **Queue (Очередь)** — **Хранилище**. Сообщения сохраняются здесь до тех пор, пока не будут прочитаны и подтверждены консьюмером. 
4. **Consumer (Консьюмер)** — подписывается на очередь и получает сообщения.
5. **Binding (Биндинг)** — связь между обменником и очередью, определяющая правила прохождения сообщений.

### Типы обменников (Exchanges)
| Тип | Логика маршрутизации |
|:---|:---|
| **Direct** | Прямое совпадение `routing_key` сообщения и ключа привязки очереди. |
| **Fanout** | Широковещательная рассылка: сообщение копируется во все привязанные очереди. |
| **Topic** | Маршрутизация по шаблону (маска с использованием `*` — одно слово, `#` — ноль или более слов). |
| **Headers** | Маршрутизация на основе атрибутов заголовка сообщения (headers) вместо ключа. |

## Типы очередей и Streams

RabbitMQ предлагает три основных типа структур данных для разных задач:

1. **Кворумные очереди (Quorum Queues):**
   - **Назначение:** Высокая доступность и сохранность данных (Data Safety).
   - **Механизм:** На базе алгоритма консенсуса **Raft**. Требуют кворума (большинства) для подтверждения записи.
   - **Особенности:** Начиная с **RabbitMQ 4.0**, являются основным HA-механизмом. Классические зеркалированные очереди (Mirrored Queues) удалены.

2. **Классические очереди (Classic Queues):**
   - **Назначение:** Простые задачи, где не критична потеря данных при сбое ноды.
   - **Особенности:** Поддерживают только одну ноду для хранения (после удаления зеркалирования). Быстрее кворумных, но менее надежны.

3. **RabbitMQ Streams:**
   - **Назначение:** Высокая пропускная способность, долгосрочное хранение, повторное чтение (Time-traveling).
   - **Модель:** Append-only log (аналог Kafka). Работают по **Pull-модели**.
   - **Производительность:** Поддерживают миллионы сообщений в секунду за счет оптимизированного бинарного протокола.

## Кластеризация и высокая доступность (HA)

### Кворумные очереди и Raft
В современном RabbitMQ (4.0+) для обеспечения отказоустойчивости используются исключительно Quorum Queues.
- **Лидер и последователи:** Одна нода — лидер (принимает чтение/запись), остальные — последователи (реплики).
- **Выбор лидера:** При падении лидера Raft автоматически выбирает нового среди наиболее актуальных реплик.
- **Репликация:** Данные всегда записываются на диск перед подтверждением (fsync).

### Ноды в памяти (RAM) и на диске (Disk)
- **Disk Node:** Основной тип узла, хранит состояние и данные на диске. Обязателен для кворумных очередей.
- **RAM Node:** Хранит только метаданные в памяти. Полезны в очень больших кластерах для ускорения операций управления (создание очередей/биндингов), но требуют наличия хотя бы одной Disk-ноды в кластере.

## Надежность и гарантии доставки

### Семантики доставки
- **At-most-once:** Сообщение может потеряться (например, при `auto_ack=true` на консьюмере).
- **At-least-once:** Гарантированная доставка через механизмы подтверждений (**Publisher Confirms** у продюсера и **Manual Ack** у консьюмера).
- **Exactly-once:** Нативно не поддерживается. Реализуется через идемпотентность на стороне приложения (дедупликация по бизнес-ID).

### Практический пример: Надежная публикация и потребление (Python/Pika)

```python
import pika

# Настройка соединения
connection = pika.BlockingConnection(pika.ConnectionParameters('localhost'))
channel = connection.channel()

# 1. Создание кворумной очереди
channel.queue_declare(
    queue='critical_tasks', 
    durable=True, 
    arguments={'x-queue-type': 'quorum'}
)

# 2. Включение Publisher Confirms
channel.confirm_delivery()

try:
    # 3. Публикация с подтверждением
    channel.basic_publish(
        exchange='',
        routing_key='critical_tasks',
        body='Important Data',
        properties=pika.BasicProperties(delivery_mode=2) # Персистентность
    )
    print("Сообщение успешно принято брокером")
except pika.exceptions.UnroutableError:
    print("Ошибка маршрутизации")

# 4. Консьюмер с ручным подтверждением (Manual Ack)
def callback(ch, method, properties, body):
    try:
        process_data(body)
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except Exception:
        # Возвращаем в очередь для повторной попытки
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)

channel.basic_consume(queue='critical_tasks', on_message_callback=callback)
```

## Эксплуатация в Kubernetes

Современный стандарт развертывания — **RabbitMQ Cluster Kubernetes Operator**.
- **Преимущества:** Автоматизирует создание кластера, управление сертификатами, обновление версий и масштабирование.
- **Автоскейлинг:** Эффективно работает с **KEDA** (Kubernetes Event-driven Autoscaling), позволяя масштабировать поды воркеров на основе длины очереди (даже до 0).

## Производительность и мониторинг

### Оптимизация
- **Prefetch Count (QoS):** Ограничение количества неподтвержденных сообщений на консьюмере. Рекомендуется начинать с **10–50** и подбирать под latency обработки.
- **Lazy Queues:** Классические очереди, которые агрессивно сбрасывают данные на диск. В кворумных очередях это поведение встроено.
- **Memory High Watermark:** Порог остановки приема сообщений (Flow Control). По умолчанию 40% RAM.

### Мониторинг
- **Prometheus Plugin:** Начиная с версии 3.8, RabbitMQ имеет встроенный плагин `rabbitmq_prometheus`, который отдает метрики в формате Prometheus на порту **15692**.
- **Ключевые метрики:**
  - `rabbitmq_queue_messages_ready` — длина очереди.
  - `rabbitmq_process_open_fds` — количество открытых файловых дескрипторов.
  - `rabbitmq_resident_memory_limit_bytes` — лимит памяти.

### Ограничения RabbitMQ
- **Не для Big Data:** RabbitMQ лучше всего работает, когда очереди пустые. Для долгосрочного хранения терабайт данных лучше использовать Streams или Kafka.
- **Порядок сообщений:** Гарантируется только внутри одной очереди при одном консьюмере. Шардирование или `requeue` могут нарушить порядок.
