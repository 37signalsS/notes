# Rancher Pipelines — конвейеры доставки (Legacy)

## Определения

**Rancher Pipelines** — устаревший и ныне удаленный механизм CI/CD (Continuous Integration / Continuous Delivery — непрерывная интеграция и непрерывная доставка), который был интегрирован непосредственно в платформу Rancher. Система была построена на базе Jenkins и предназначалась для автоматизации процессов сборки, тестирования и развёртывания приложений в кластерах Kubernetes через веб-интерфейс Rancher.

> **Критическое предупреждение:** данный инструмент полностью **удален** из платформы Rancher начиная с версии **v2.7.0**. В версиях v2.5.x и v2.6.x он имел статус устаревшего (deprecated). Для всех актуальных инсталляций (v2.8, v2.9+) использование Rancher Pipelines невозможно. Данный документ сохранен для исторической справки и поддержки legacy-окружений.

## Базовые концепции

### Архитектура решения (архивные данные)

Механизм Rancher Pipelines функционировал на базе Jenkins. При инициации конвейера платформа динамически разворачивала Jenkins Agent (вспомогательный под) внутри управляемого кластера. По завершении выполнения шагов агент автоматически удалялся.

### Структура конвейера (Pipeline)

- **Stage (Этап)** — логическое разделение процесса (например, "Сборка", "Тестирование", "Деплой").
- **Step (Шаг)** — атомарная операция внутри этапа: клонирование кода, сборка Docker-образа, выполнение shell-скрипта или применение YAML-манифестов.
- **Trigger (Триггер)** — событие автоматического запуска: Webhook от Git-провайдера (на `push` или `pull request`) или ручной запуск.

### Поддерживаемые провайдеры Git

Система поддерживала интеграцию через OAuth (Open Authorization) со следующими сервисами:
- GitHub / GitHub Enterprise
- GitLab
- Bitbucket

## Практические сценарии и миграция

### Современный подход к CI/CD в Rancher

Поскольку встроенные пайплайны удалены, экосистема Rancher перешла на разделение ответственности:

1.  **CI (Continuous Integration)**: Сборка и тестирование перенесены во внешние специализированные системы.
    - **GitHub Actions**: стандарт для open-source и облачных проектов.
    - **GitLab CI**: предпочтительный выбор для On-premise инсталляций.
    - **Jenkins**: классическое решение, которое теперь рекомендуется разворачивать как отдельный workload, не полагаясь на встроенные в Rancher механизмы.
2.  **CD (Continuous Delivery)**: Доставка манифестов осуществляется через GitOps-инструменты.
    - **Fleet**: встроенный в Rancher инструмент для GitOps в масштабе тысяч кластеров. Оптимален для управления инфраструктурой и доставки приложений.
    - **Argo CD / Flux**: популярные внешние контроллеры, легко интегрируемые через Rancher Apps & Marketplace.

### Архивный пример конфигурации `.rancher-pipeline.yml`

Для справки: так выглядело описание пайплайна, хранившееся в корне репозитория.

```yaml
stages:
  - name: Build
    steps:
      - publishImageConfig:
          dockerfilePath: ./Dockerfile
          imageName: myuser/myapp:v1.0.0
          pushRemote: true
          registry: index.docker.io
  - name: Deploy
    steps:
      - applyYamlConfig:
          path: ./deployment.yaml
```

### Рекомендации по сборке (Dockerfile)

Принципы эффективной сборки остаются неизменными вне зависимости от CI-системы. Рекомендуется использовать многоэтапную сборку (multi-stage build). Детальные принципы описаны в разделе [Оптимизация сборки Docker](../../Docker/Dockerfile/Docker_best_practices/build_optimization.md).

**Пример Dockerfile:**

```dockerfile
FROM golang:1.21-alpine AS builder
WORKDIR /build
COPY . .
RUN go build -o app ./cmd/main

FROM alpine:latest
WORKDIR /app
COPY --from=builder /build/app .
EXPOSE 9000
CMD ["./app"]
```

## Дополнительная информация

### Статус и стратегии замены

| Инструмент | Текущий статус | Рекомендуемое действие |
| :--- | :--- | :--- |
| **Rancher Pipelines** | **Удалено (v2.7+)** | Немедленная миграция на Fleet или внешние CI/CD |
| **Fleet** | Актуально | Использовать для CD (доставки) в стиле GitOps |
| **GitLab CI / GH Actions** | Актуально | Использовать для CI (сборки образов и тестов) |

### Рекомендации по эксплуатации в современных версиях

- **Безопасность**: Для доступа к приватным реестрам в новых версиях используйте секреты типа `kubernetes.io/dockerconfigjson`. Подробнее: [Секреты реестра](../../Kubernetes/Base/secrets/creating_secrets.md#docker-registry-secret).
- **GitOps**: Переход на Fleet позволяет декларативно описывать состояние кластеров, что исключает необходимость в императивных пайплайнах.
- **Версионирование**: Никогда не используйте тег `latest`. В Fleet или внешних CI пайплайнах фиксируйте хеш или версию образа.
