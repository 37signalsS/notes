# Rancher: Платформа управления Kubernetes

## Определения

**Rancher** — это платформа управления Kubernetes-кластерами, которая предоставляет единый интерфейс для развертывания, настройки, мониторинга и управления несколькими кластерами Kubernetes, развернутыми в различных средах (облако, локальная инфраструктура).

## Базовые концепции

### Зачем нужен Rancher?

1. **Управление несколькими кластерами**: Позволяет централизованно управлять Kubernetes-кластерами в различных облаках (AWS, GCP, Azure) и на локальной инфраструктуре.
2. **Упрощенная установка и настройка**: Предоставляет инструменты для быстрого развертывания Kubernetes-кластеров (например, с использованием RKE, RKE2) с минимальными усилиями.
3. **Безопасность и контроль доступа**: Поддерживает различные методы аутентификации, включая [LDAP (Lightweight Directory Access Protocol)](../../Linux/SystemAdministration/users_management.md#LDAP-Lightweight-Directory-Access-Protocol), Active Directory, GitHub и другие.
4. **Мониторинг и логирование**: Встроенная поддержка для таких инструментов, как Prometheus, Grafana и Fluentd.
5. **Развертывание приложений**: Упрощает развертывание приложений с поддержкой Helm-чартов и стандартных манифестов Kubernetes.

### Как работает Rancher?

*   **Rancher Server**: Центральный компонент, который управляет кластерами, предоставляет веб-интерфейс (UI) и API для взаимодействия.
*   **Kubernetes-кластеры**: Могут быть развернуты с помощью Rancher (используя RKE, RKE2) или импортированы (например, существующие EKS, AKS, GKE).
*   **Rancher Agents**: Агенты, устанавливаемые в каждом управляемом Kubernetes-кластере, обеспечивающие связь и взаимодействие с Rancher Server.

### Развертывание кластера Kubernetes с помощью RKE

**RKE (Rancher Kubernetes Engine)** — это дистрибутив Kubernetes от Rancher Labs, позволяющий легко развертывать кластеры Kubernetes на любой инфраструктуре (Bare Metal, облачные провайдеры) с помощью Rancher.

#### 1. Основные концепции

*   **Гибкость развертывания**: RKE поддерживает развертывание кластеров с различными конфигурациями узлов (etcd, Control Plane, Worker) и сетевыми плагинами.
*   **Управление через Rancher UI**: Весь процесс создания и управления кластером RKE интегрирован в веб-интерфейс Rancher.
*   **Модульность**: Позволяет выборочно развертывать компоненты (например, отдельный узел для etcd).

#### 2. Практический сценарий: Создание кластера RKE через Rancher UI

##### 2.1. Предварительные требования

*   **Подготовленные узлы**: Несколько серверов (физических или виртуальных) с установленным Docker.
*   **DNS-сервер**: Настроенный DNS-сервер для разрешения имен узлов (опционально, но рекомендуется).
*   **Rancher Server**: Запущенный и доступный Rancher Server (установленный, например, в Docker).

##### 2.2. Пошаговая установка

1.  **Начало создания кластера**: В Rancher UI перейдите в раздел `Global` -> `Clusters` -> `Add Cluster`. Выберите опцию `From existing nodes (Custom)` или `Create a new Kubernetes cluster using Rancher Kubernetes Engine`.
2.  **Настройка кластера**:
    *   **Имя кластера**: Задайте уникальное имя (например, `Rtest`).
    *   **Описание**: Добавьте описание кластера.
    *   **Версия Kubernetes и тип дистрибутива**: Выберите желаемую версию Kubernetes и тип дистрибутива (RKE2 или K3S).
        *   **RKE2**: Более современный и безопасный дистрибутив, подходит для большинства production-сценариев. Однако в некоторых тестовых или специфических окружениях может быть менее стабилен.
        *   **K3S**: Легковесный дистрибутив, часто более стабилен для быстрых развертываний и тестовых сред.
    *   **Network Provider**: Выберите сетевой плагин.
        *   `Flannel`: Простой и легкий оверлейный сетевой плагин.
        *   `Calico`: Мощный сетевой плагин, рекомендованный для production-сред, с поддержкой `NetworkPolicy`.
        *   `Cilium`: Высокопроизводительный CNI с расширенными функциями безопасности (NetworkPolicy) и обсервабилити, особенно эффективен для кластеров с высоким сетевым трафиком и требованиями к фильтрации.
    *   **Cloud Provider**: Укажите `None`, если развертывание происходит на Bare Metal или виртуальных машинах без интеграции с облачным провайдером.
    *   **Private Registry**: Пропустите, если нет собственного Docker Registry.
    *   **Advanced Options**: Оставьте по умолчанию для базовой установки.
    *   **Authentication**: Оставьте по умолчанию, если не настроены внешние провайдеры аутентификации.
3.  **Добавление узлов**: Rancher сгенерирует команду `docker run` для `rancher-agent`. Эту команду необходимо запустить на каждом подготовленном узле. Для каждого узла выберите его роль(и):
    *   **etcd**: Узлы, на которых будет размещено распределенное хранилище `etcd`. Рекомендуется 3 или 5 узлов для обеспечения кворума и отказоустойчивости.
    *   **Control Plane**: Узлы, на которых будут запущены `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`. Рекомендуется 2 или 3 узла для отказоустойчивости.
    *   **Worker**: Рабочие узлы, на которых будут запускаться поды приложений.
    *   **Insecure Selection (для самоподписанных сертификатов)**: Если ваш Rancher Server использует самоподписанный SSL-сертификат, необходимо поставить галочку "Insecure Selection" для агента, чтобы он мог успешно подключиться.
    *   **Процесс**: Запустите `rancher-agent` с выбранными ролями на соответствующих узлах. Rancher автоматически установит и сконфигурирует компоненты Kubernetes на этих узлах.
    *   **Cattle Cluster Agent**: Важно понимать, что не Rancher Server "лезет" в ваш кластер, а `Cattle Cluster Agent`, запущенный на узлах кластера, сам подключается к Rancher Server и передает ему информацию о состоянии кластера. Это агент-шпион, который сообщает о своем кластере Rancher.
4.  **Ожидание активации кластера**: Дождитесь, пока кластер перейдет в статус `Active` в Rancher UI.

#### 3. Особенности узлов RKE-кластера

*   **Taints на системных узлах**: По умолчанию узлы с ролями `etcd` и `Control Plane` будут иметь `taints` (например, `node-role.kubernetes.io/control-plane:NoSchedule`), которые предотвращают размещение на них обычных подов приложений. Это гарантирует стабильность и доступность системных компонентов.
*   **Встроенный Ingress Controller**: RKE-кластеры обычно поставляются с предустановленным Ingress-контроллером (например, Nginx Ingress Controller), который запускается как `DaemonSet` на Worker-узлах.
*   **Автоматическое обновление сертификатов**: Rancher предоставляет функционал `Rotate Certificates` для удобного обновления TLS-сертификатов кластера через UI, что критически важно для поддержания работоспособности кластера.

#### 4. Установка и настройка `kubectl` для RKE-кластера

Для управления RKE-кластером из командной строки с любой машины, имеющей доступ к Rancher Server:

1.  **Скачайте `kubectl`**: Загрузите соответствующую вашему окружению версию утилиты `kubectl` с официального сайта Kubernetes.
2.  **Сделайте исполняемым и переместите**: Предоставьте права на исполнение (`chmod +x`) и переместите бинарный файл в директорию, доступную в `$PATH` (например, `/usr/local/bin`).
3.  **Получите `kubeconfig`**: В Rancher UI перейдите в `Cluster Dashboard` для вашего RKE-кластера. Нажмите кнопку `Kubeconfig File` и скопируйте содержимое.
4.  **Сохраните `kubeconfig`**: Создайте директорию `~/.kube` и сохраните скопированное содержимое в файл `~/.kube/config`.
5.  **Проверьте доступ**: Используйте `kubectl get nodes` или `kubectl version` для проверки подключения к кластеру.

#### 5. Развертывание приложения через Rancher UI

Rancher упрощает развертывание приложений без необходимости вручную писать YAML-манифесты.

1.  **Выбор проекта/неймспейса**: В Rancher UI перейдите в желаемый `Project` и `Namespace`.
2.  **Создание Deployment**:
    *   Выберите `Workloads` -> `Deployments` -> `Create`.
    *   Задайте имя `Deployment`.
    *   Укажите образ контейнера (например, `openresty/openresty:latest`).
    *   **Port Mapping**: Добавьте порты контейнера и укажите, как их публиковать (например, `NodePort` для внешнего доступа).
3.  **Создание Ingress**:
    *   Выберите `Load Balancing` -> `Ingresses` -> `Create`.
    *   Задайте имя `Ingress`.
    *   Укажите `Namespace`.
    *   **Hostname**: Определите доменное имя (например, `www.r.truecof.local`).
    *   **Path**: Укажите путь (например, `/`).
    *   **Target Service**: Выберите `Service`, который был автоматически создан для вашего `Deployment`, и его целевой порт.
    *   **Сохранение**: Примените настройки. Rancher автоматически создаст необходимый `Ingress`-ресурс.
4.  **Проверка доступа**: Проверьте доступ к приложению через настроенный Ingress.

### Настройка мониторинга в Rancher

Rancher значительно упрощает развертывание и управление стеком мониторинга на базе Prometheus и Grafana в кластерах Kubernetes. Инструмент использует [Prometheus Operator](../../Concepts/kubernetes_operators.md#kubernetes-операторы-автоматизация-управления-приложениями) для автоматического конфигурирования Prometheus, позволяя ему обнаруживать поды с динамическими IP-адресами и портами.

#### 1. Основные концепции

*   **Основа мониторинга**: Мониторинг в Rancher базируется на проекте `kube-prometheus-stack` (ранее `Kube Prometheus`), который в свою очередь основан на `Prometheus Operator`. Он включает в себя:
    *   **Prometheus Operator**: Управляет развертыванием Prometheus и Alertmanager.
    *   **Prometheus**: Система сбора и хранения метрик.
    *   **Alertmanager**: Для обработки и маршрутизации оповещений.
    *   **Node Exporter**: Собирает метрики с узлов Kubernetes.
    *   **kube-state-metrics**: Экспортирует метрики о состоянии объектов Kubernetes API.
    *   **Prometheus Adapter for Metric Kubernetes**: (упоминается в источнике как "ерунда, не знаю, но наверное нужная штука").
    *   **Grafana**: Для визуализации метрик и создания дашбордов.
    *   **Автоматическая настройка**: `kube-prometheus-stack` предоставляет преднастроенные дашборды, правила алертов и цели сбора метрик из коробки, существенно упрощая начальную настройку кластера.
    *   **Критическое замечание о Rancher и мониторинге**: Изначально Rancher позиционировался как инструмент, облегчающий работу с Kubernetes для специалистов, не имеющих глубоких знаний в этой области, позволяя управлять сложными системами "тыканьем мышкой". В контексте мониторинга это означало бы легкую настройку Prometheus, Grafana и Alertmanager. Однако на практике, для тонкой настройки или устранения проблем (например, сбора метрик с ETCD или решения проблем с PersistentVolume), пользователю все равно требуется глубокое понимание `kube-prometheus-stack`, Helm-чартов и Kubernetes в целом. Это создает разрыв между обещаниями простоты и реальной необходимостью "копаться в навозе", как выразился автор видео.
    *   **Сложность конфигурации**: Несмотря на простоту установки, глубокая настройка `kube-prometheus-stack` может быть сложной из-за использования `jsonnet` для шаблонизации конфигураций, что добавляет еще один уровень абстракции помимо Go-шаблонов и Jinja.
*   **Node Exporter**: Агент, запускаемый на каждом узле кластера, собирающий метрики операционной системы и аппаратного обеспечения. Rancher предлагает включение Node Exporter одной кнопкой.
*   **Grafana**: В дополнение к Prometheus, Rancher автоматически разворачивает Grafana с заранее сконфигурированными дашбордами для мониторинга кластера. Это избавляет от необходимости ручной настройки визуализации.
*   **Типы мониторинга**:
    *   **Мониторинг кластера**: Собирает метрики со всех системных компонентов и узлов.
    *   **Мониторинг проектов/приложений**: Ранее Rancher позволял развертывать отдельный экземпляр Prometheus для сбора метрик с конкретных приложений в рамках выбранного проекта. **Однако, в Rancher версии 2.7.x эта функциональность была удалена, что существенно усложняет мониторинг бизнес-метрик приложений на уровне проектов.**
        *   **Критика текущего подхода**: В актуальных версиях Rancher все метрики пользовательских приложений, собираемые через `ServiceMonitor`, попадают в *общий* Prometheus, используемый для мониторинга самого кластера. Это приводит к нескольким проблемам:
            *   **Смешивание метрик**: Метрики приложений и системные метрики хранятся в одном хранилище, что усложняет управление ресурсами и может привести к переполнению общего Prometheus.
            *   **Ресурсные квоты**: У пользователя нет контроля над выделенным дисковым пространством для его метрик, что может быть критично для долгосрочного хранения.
            *   **Безопасность и избыточные права**: Для бесперебойной работы с UI мониторинга пользователю приходится выдавать относительно широкие права (например, `Manage Services`), что может быть избыточным и создавать потенциальные риски безопасности, так как пользователь получает доступ к "внутренней кухне" системы мониторинга.
        *   **Настоятельная рекомендация**: В связи с вышеизложенным, для мониторинга бизнес-метрик ваших приложений **настоятельно рекомендуется** разворачивать отдельные стеки мониторинга (например, Prometheus, VictoriaMetrics, Alert Manager) вручную в своих проектах или использовать специализированные внешние SaaS-решения, не используя встроенные возможности Rancher для мониторинга пользовательских приложений. Это обеспечит лучшую изоляцию, контроль ресурсов и безопасность.
*   **Service Monitor**: Custom Resource, используемый Prometheus Operator для указания Prometheus, откуда собирать метрики. Связывает приложение (через Service) с Prometheus. Используется для добавления кастомных целей сбора метрик.

#### 2. Практический сценарий: Включение мониторинга через Web UI

Для настройки мониторинга в Rancher используется интуитивно понятный веб-интерфейс.

##### 2.1. Включение мониторинга для кластера

1.  **Создайте отдельный Rancher Project для мониторинга:** Рекомендуется создать отдельный Rancher `Project` (например, "Monitoring") для размещения глобального стека мониторинга, а не использовать `System` Project. Это обеспечивает изоляцию и контроль доступа.
2.  Перейдите в **Cluster Dashboard** -> **Tools** -> **Monitoring**.
3.  Настройте параметры:
    *   **Project**: Выберите созданный вами `Project` (например, "Monitoring").
    *   **Version**: Выберите желаемую версию стека мониторинга.
    *   **Customize Helm Options for install**: Всегда рекомендуется включать эту опцию, так как она позволяет редактировать `values.yaml` Helm-чарта, лежащего в основе установки. Это критически важно для тонкой настройки.
    *   **General**:
        *   `Cluster Type`: Укажите тип кластера (например, `Other` для vanilla Kubernetes, установленного вручную).
    *   **Prometheus**:
        *   **Scrape Interval**: Интервал сбора метрик (например, `15s` вместо `1m` для более оперативных данных, что полезно для мониторинга пользовательских приложений).
        *   **Retention Time**: Срок хранения данных (например, `1d` или `5GB` для экспериментальных кластеров).
    *   **Enable Nodes Exporter**: Рекомендуется включить для сбора метрик с узлов.
    *   **Persistent Storage for Prometheus**:
        *   `false` (по умолчанию): Данные Prometheus будут временными и теряются при пересоздании пода. Подходит для тестовых сред.
        *   `true`: Требует предварительно настроенного [PersistentVolume](../../Storage/pv_and_pvc.md), иначе все данные будут утеряны. Обеспечивает сохранение данных Prometheus при его перезапусках. **Укажите желаемый размер хранилища (например, `5Gi`) и **StorageClass** (если StorageClass по умолчанию не настроен в вашем кластере).**
    *   **Persistent Storage for Grafana**: Опционально. **Как правило, не требуется включать Persistent Volume для Grafana**, если дашборды добавляются через ConfigMap, так как они не хранят изменяемые данные. Если же планируется создавать и сохранять дашборды непосредственно через UI Grafana, тогда рекомендуется включить.
    *   **Grafana Sidecar для обнаружения дашбордов**: Для автоматического обнаружения кастомных дашбордов, определенных в `ConfigMap` в других `namespaces`, необходимо включить и настроить `sidecar` контейнер Grafana. Этот `sidecar` будет искать ConfigMap с дашбордами за пределами стандартного `namespace` (`cattle-monitoring-system`). По умолчанию Grafana ищет дашборды только в предопределенной директории (`Graphana Cattle Dashboards`), и давать пользователям доступ к системным директориям не рекомендуется.
    *   **Важное замечание: Проблемы с NFS Provisioner**: При использовании устаревших NFS Provisioner, Prometheus может не стартовать из-за проблем с `volumeClaimTemplate`, в частности, из-за наличия параметра `selector` в PersistentVolumeClaim, на который некоторые старые Provisioner могут реагировать некорректно. В таких случаях может потребоваться ручное редактирование `values.yaml` Helm-чарта (доступно через "Customize Helm Options for install") для удаления секции `selector`, чтобы Prometheus мог получить PersistentVolume.

4.  Нажмите **Install** (или **Upgrade**). Rancher развернет Prometheus, Grafana и сопутствующие компоненты (например, Alertmanager) в `namespace` `cattle-monitoring-system` (если вы не указали другой Project/Namespace).

После активации в Rancher UI появятся новые разделы с метриками кластера и прямые ссылки на Grafana-дашборды.

##### 2.2. Настройка мониторинга для проекта/приложения (устарело)

*   **Примечание:** В Rancher версии 2.7.x и выше функциональность развертывания отдельного экземпляра мониторинга для конкретного проекта или приложения была **удалена**. Если вам требуется мониторинг бизнес-метрик ваших приложений, рассмотрите развертывание отдельного стека Prometheus/Grafana вручную в вашем проекте, либо используйте другие инструменты, такие как [VictoriaMetrics](../../VictoriaMetrics/victoriametrics_overview.md) или [Mimir](../../Mimir/mimir_overview.md) для масштабируемого мониторинга.

##### 2.3. Сбор метрик с приложений (Service Monitor)

Для того чтобы Prometheus собирал метрики с вашего приложения, необходимо:

1.  **Развернуть приложение**: Создайте Deployment или StatefulSet для вашего приложения.
2.  **Создать Service**: Определите [Service](../../Networking/Service/service_overview.md) для вашего приложения, чтобы обеспечить сетевую доступность.
3.  **Создать Service Monitor**: Это Custom Resource, который инструктирует Prometheus Operator о том, как собирать метрики. Он указывает:
    *   Имя Service приложения.
    *   Порт, на котором приложение предоставляет метрики (обычно `/metrics`).
    
    Пример Service Monitor:
    ```yaml
    apiVersion: monitoring.coreos.com/v1
    kind: ServiceMonitor
    metadata:
      name: example-app-monitor
      labels:
        # Эти метки должны совпадать с 'selector' Prometheus
        release: rancher-monitoring
    spec:
      selector:
        matchLabels:
          app: example-app # Метки Service вашего приложения
      endpoints:
      - port: http-metrics # Имя порта, определенного в Service
        path: /metrics
        interval: 30s
    ```
    Метки `release: rancher-monitoring` гарантируют, что Service Monitor будет подобран экземпляром Prometheus, управляемым Rancher.

#### 3. Мониторинг ETCD в Rancher

Мониторинг состояния кластера ETCD является критически важным для стабильности Kubernetes. В Rancher, при установке мониторинга кластера через `kube-prometheus-stack`, метрики ETCD по умолчанию могут не собираться, особенно если кластер Kubernetes был установлен вручную (не через Rancher).

Для полноценного мониторинга ETCD требуется ручная конфигурация:

1.  **Понимание архитектуры ETCD**: Необходимо знать, как ETCD запущен (например, как Pods, управляемые kubelet) и где находятся его сертификаты. ETCD использует SSL для внутренней коммуникации, и Prometheus должен быть настроен для использования этих сертификатов для доступа к метрикам.
2.  **Создание Kubernetes Secret**: Сертификаты ETCD (`CA certificate`, `client certificate`, `client key`) должны быть помещены в Kubernetes Secret, доступный для Prometheus.
3.  **Создание Kubernetes Service и Endpoint**: Для того чтобы Prometheus мог обнаруживать ETCD-серверы и собирать с них метрики, необходимо создать Service и соответствующий Endpoint, который будет указывать на IP-адреса и порт ETCD-инстансов.
4.  **Создание ServiceMonitor**: Используя Custom Resource `ServiceMonitor` из Prometheus Operator, Prometheus конфигурируется для сбора метрик с ETCD Service, указывая интервал сбора, путь к метрикам (обычно `/metrics` на порту `2379`) и Secret с сертификатами для TLS-аутентификации.

**Детальная настройка и YAML-примеры для мониторинга ETCD в контексте `kube-prometheus-stack` будут рассмотрены в файле [prometheus_config.md](../../Prometheus/Kubernetes/Kube_Prometheus_Stack_Helm/prometheus_config.md). Концептуальная информация об ETCD и его мониторинге также доступна в [architecture_and_concepts.md](../../etcd/architecture_and_concepts.md).**



### Настройка логирования в Rancher

Rancher предлагает встроенное решение для централизованного сбора, хранения и анализа логов, основанное на Fluentd.

#### 1. Основные концепции логирования

*   **12 Factor App: Логи как поток событий**: Современные приложения (особенно микросервисы) должны выводить логи на стандартные потоки (`stdout`/`stderr`). Обработка и хранение логов делегируется инфраструктуре. Это упрощает сбор логов и их дальнейшую обработку.
*   **Хранение логов на узлах**: В Kubernetes логи контейнеров физически сохраняются на узлах в директории `/var/log/containers/`. Для каждого пода создается файл с логами.
*   **Эфемерность логов**: Логи, хранящиеся на узлах, эфемерны: при удалении пода его логи также удаляются. Для длительного хранения и анализа необходима централизованная система логирования.
*   **Fluentd**: Rancher использует Fluentd как агент сбора логов. Fluentd (или его легковесная версия [Fluent Bit](../../MonitoringLogging/EFK/fluentbit/fluent_comparison.md)) запускается на каждом узле, собирает логи, обогащает их метаданными Kubernetes и пересылает в центральное хранилище.

#### 2. Практический сценарий: Включение логирования через Web UI

Для настройки логирования в Rancher используется веб-интерфейс.

##### 2.1. Включение логирования для кластера или проекта

1.  Перейдите в **Cluster Dashboard** -> **Tools** -> **Logging** (для логирования всего кластера) или **Project** -> **Tools** -> **Logging** (для логирования конкретного проекта).
2.  Выберите **Destination** (цель отправки логов). Rancher поддерживает несколько типов:
    *   **Elasticsearch**: Популярная система для индексации и поиска логов. Требует указания URL, порта, учетных данных (логин/пароль).
    *   **Splunk**: Коммерческая платформа для сбора и анализа данных.
    *   **Kafka**: Надежный буфер для потоковой передачи логов.
    *   **Syslog**: Классический протокол для отправки системных сообщений.
    *   **Fluentd**: Возможность отправить логи на другой экземпляр Fluentd (например, для построения иерархической системы сбора).

##### 2.2. Конфигурация для Elasticsearch (пример)

При выборе Elasticsearch доступны следующие параметры:

*   **Endpoint**: Полный URL Elasticsearch (например, `http://<elasticsearch-ip>:9200`). Важно использовать `http` или `https` в зависимости от конфигурации Elasticsearch.
*   **Authentication**: Учетные данные пользователя Elasticsearch, имеющего права на запись логов. Пользователь должен иметь как минимум `create_index`, `manage` и `write` привилегии на целевые индексы.
*   **Index Pattern**: Формат имени индекса в Elasticsearch, который будет использоваться для хранения логов. Рекомендуется использовать ежедневные индексы (например, `mycluster-YYYY.MM.DD`) для упрощения управления и архивирования.
    *   `mycluster-YYYY.MM.DD` (ежедневно)
    *   `mycluster-YYYY.MM` (ежемесячно)
    *   `mycluster-YYYY` (ежегодно)
    *   **Рекомендация**: Всегда используйте ежедневные индексы, так как они упрощают управление данными и минимизируют риски при работе с большими объемами логов.
*   **Include System Log**: Включение/отключение сбора логов всех системных компонентов Kubernetes. Для больших кластеров это может привести к огромному объему данных, требующему значительных ресурсов Elasticsearch. Следует внимательно оценить необходимость сбора всех системных логов.
*   **Enable JSON Parsing**: Попытка парсить логи в формате JSON. Если приложение выводит логи в JSON, Rancher (через Fluentd) будет пытаться разобрать их на отдельные поля.
    *   **Ограничение**: Встроенный парсер Rancher может не всегда корректно обрабатывать вложенные JSON-структуры или смешанные форматы логов, что может привести к тому, что логи останутся в виде одной текстовой "колбасы" в Elasticsearch. Для сложных случаев может потребоваться ручная донастройка Fluentd.

##### 2.3. Расширенная конфигурация Fluentd

Rancher предоставляет возможность тонкой настройки конфигурации Fluentd через опцию **"Edit As File"**. Это позволяет администраторам вручную редактировать `.conf` файл Fluentd, добавляя кастомные парсеры, фильтры и правила маршрутизации, которые не доступны через стандартный веб-интерфейс.

После настройки логирования в Kibana можно создавать [индекс-паттерны](../../MonitoringLogging/EFK/kibana_guide.md#1-создание-индекс-паттерна-для-логов-kubernetes) (например, `mycluster-*`) для поиска и анализа логов.

# CI/CD Pipelines в Rancher

## Определения

**Rancher Pipeline** — это встроенный инструмент Rancher для автоматизации процессов непрерывной интеграции и непрерывной доставки (CI/CD) приложений в Kubernetes-кластеры, управляемые Rancher. Он позволяет определять этапы сборки, тестирования и развертывания непосредственно из интерфейса Rancher или через YAML-файл, хранящийся в репозитории проекта.

## Базовые концепции

### Зачем использовать Rancher Pipelines?

*   **Ограниченные ресурсы**: Идеально подходит для сред с ограниченными ресурсами, где развертывание отдельных CI/CD систем (например, GitLab, Jenkins) нецелесообразно. Rancher использует внутренний экземпляр Jenkins для выполнения задач, но абстрагирует его от пользователя.
*   **Внутренняя доступность кластера**: Эффективен для кластеров, которые не доступны извне (например, локальные, development-кластеры), так как pipeline запускается внутри самого кластера Rancher.
*   **Интеграция с Git**: Поддерживает интеграцию с репозиториями Git (GitHub, GitLab, Bitbucket), позволяя триггерить пайплайны при изменениях в коде.
*   **Управление через UI/YAML**: Пайплайны могут быть настроены через интуитивно понятный веб-интерфейс Rancher или определены декларативно в файле `.rancher-pipeline.yml` в корне репозитория проекта.

### Как работают Rancher Pipelines?

1.  **Интеграция с Git-репозиторием**: Rancher подключается к выбранному Git-репозиторию (например, GitHub) с использованием OAuth.
2.  **Файл `.rancher-pipeline.yml`**: Определение пайплайна хранится в этом файле в корне репозитория. Он описывает стадии (stages) и шаги (steps) выполнения.
3.  **Внутренний Jenkins**: Rancher динамически разворачивает временный *Jenkins slave pod* внутри управляемого кластера для выполнения каждого запуска пайплайна. Этот подход позволяет использовать Jenkins без необходимости его ручной настройки и управления.
4.  **Секреты и учетные данные**: Rancher позволяет безопасно хранить учетные данные (например, для Docker Hub) в виде секретов, которые затем могут быть использованы в пайплайнах.
5.  **Автоматические и ручные триггеры**: Пайплайны могут запускаться автоматически при push-событиях в Git-репозитории (через вебхуки) или вручную из Rancher UI.

## Практический сценарий: Настройка CI/CD Pipeline для Go-приложения в Rancher

Рассмотрим процесс настройки CI/CD для простого Go-приложения, которое собирается в Docker-образ и деплоится в Kubernetes.

### 1. Подготовка проекта

Проект должен включать:

*   **Исходный код приложения**: Например, Go-приложение на фреймворке REVEL, настроенное для прослушивания всех сетевых интерфейсов (например, `0.0.0.0:9000`).
*   **Dockerfile**: Для сборки Docker-образа приложения. Рекомендуется использовать многостадийную сборку (multi-stage build) для уменьшения размера финального образа (например, с использованием Alpine Linux как базового образа для рантайма).
    *   **Пример структуры Dockerfile:**
        ```dockerfile
        # Build Stage
        FROM golang:1.X-alpine AS builder
        WORKDIR /app
        COPY . .
        RUN go mod tidy && go build -o main . # Пример для Go-приложения

        # Runtime Stage
        FROM alpine:latest
        WORKDIR /app
        COPY --from=builder /app/main .
        EXPOSE 9000
        CMD ["./main"]
        ```
*   **Kubernetes Manifests (YAML-файлы)**: Для развертывания приложения в кластере Kubernetes.
    *   **Service (например, `01-service.yaml`)**: Определяет сетевой доступ к приложению. В примере используется `NodePort` для внешнего доступа, прослушивающий порт `31313`.
    *   **Deployment (например, `02-deployment.yaml`)**: Определяет развертывание пода(ов) приложения.
        *   Жесткая привязка к конкретному `namespace` (например, `kubetest`).
        *   Рекомендуется использовать явные версии образов (например, `myuser/myapp:001`), избегая тега `latest` в разработке.
        *   Использование `imagePullPolicy: IfNotPresent` косвенно вынуждает разработчиков увеличивать версию образа при каждом изменении, иначе новые изменения не будут скачаны.
        *   Приложение должно прослушивать определенный порт (например, `9000`), который должен быть указан в манифесте Deployment и Service.

### 2. Настройка CI/CD в Rancher UI

#### 2.1. Создание Project и Namespace в Rancher

1.  В Rancher UI перейдите в **Global** -> **Clusters** -> (ваш кластер) -> **Projects/Namespaces**.
2.  Нажмите **Add Project** и создайте новый проект (например, `kubetest`).
3.  В созданном проекте перейдите в **Namespaces** и нажмите **Create Namespace**. Укажите имя (например, `kubetest`).
    *   **Примечание**: Рекомендуется вручную создавать `namespace` с осмысленным именем, так как Rancher может генерировать неудобные имена, если `namespace` не указан явно в манифестах приложения.

#### 2.2. Добавление Registry Credentials (Docker Hub)

1.  В Rancher UI перейдите в **Project** (например, `kubetest`) -> **Resources** -> **Secrets** -> **Registry Credentials**.
2.  Нажмите **Add Registry**.
3.  Укажите **Name** (например, `Docker Hub`).
4.  Выберите **Registry Type** (например, `Docker Hub`).
5.  Введите **Username** и **Password** вашей учетной записи Docker Hub.
6.  Выберите **Available to All Namespaces** или конкретный `namespace` (например, `kubetest`).

#### 2.3. Интеграция с GitHub

1.  В Rancher UI перейдите в **Project** (например, `kubetest`) -> **Tools** -> **Pipelines**.
2.  Нажмите **Configure Repositories**.
3.  Выберите **GitHub** (или другую систему контроля версий).
4.  Вам потребуется настроить GitHub OAuth App и указать `Client ID` и `Client Secret` в Rancher.
5.  После аутентификации выберите репозиторий проекта (например, `kubetest`) и нажмите **Enable** для активации пайплайнов для этого репозитория.

#### 2.4. Конфигурация Pipeline

1.  В разделе **Pipelines** вашего проекта выберите активированный репозиторий и нажмите **Edit Config**.
2.  **Настройка ветки**: Укажите ветку, по которой будет работать пайплайн (например, `edit` или `main`).
3.  **Визуальный конфигуратор**: Rancher предоставляет визуальный интерфейс для создания пайплайна.
4.  **Определение стадий (Stages)**:
    *   **Stage: Clone**: (Обычно создается автоматически) Клонирует исходный код из Git-репозитория.
    *   **Stage: Build** (Создайте новый):
        *   Добавьте **Step: Build and Publish Image**.
        *   **Dockerfile Path**: Укажите путь к Dockerfile (например, `Dockerfile`).
        *   **Image Name**: Укажите полное имя образа (например, `your_docker_hub_user/kubetest:001`).
        *   **Registry Credential**: Выберите созданный ранее секрет (например, `Docker Hub`).
        *   Этот шаг соберет Docker-образ и запушит его в Docker Hub.
    *   **Stage: Deploy** (Создайте новый):
        *   Добавьте **Step: Deploy YAML File**.
        *   **YAML File Path**: Укажите путь к манифесту сервиса (например, `01-service.yaml`).
        *   Добавьте еще один **Step: Deploy YAML File**.
        *   **YAML File Path**: Укажите путь к манифесту деплоймента (например, `02-deployment.yaml`).
5.  **Сохранение конфигурации**: Rancher предложит сохранить конфигурацию пайплайна в файл `.rancher-pipeline.yml` в вашем репозитории.

### 3. Запуск и мониторинг Pipeline

1.  **Ручной запуск**: В Rancher UI в разделе **Pipelines** выберите ваш пайплайн и нажмите **Run**. Выберите ветку, если необходимо.
2.  **Автоматический запуск**: Пайплайн может быть настроен на автоматический запуск при каждом `git push` (через вебхуки), но это требует внешней доступности Rancher Server для GitHub.
3.  **Мониторинг**: В Rancher UI отображается статус выполнения пайплайна, включая логи для каждого шага. Вы можете видеть, как Rancher разворачивает временный Jenkins slave pod, клонирует репозиторий, собирает образ, пушит его в Docker Hub и применяет Kubernetes-манифесты.
4.  **Проверка изменений**: После успешного выполнения пайплайна проверьте статус `Workloads` и `Services` в вашем проекте/namespace.

### 4. Особенности и рекомендации

*   **Версионирование образов**: Всегда используйте явные теги версий для Docker-образов (например, `001`, `1.0.0`), а не `latest`, особенно в production-средах, для обеспечения воспроизводимости и стабильности.
*   **`imagePullPolicy: IfNotPresent`**: Эта политика полезна в разработке, но будьте внимательны: если вы изменили код, но не обновили тег образа, Kubernetes не будет скачивать новый образ, если образ с таким тегом уже присутствует локально. Это может привести к тому, что старая версия приложения будет запущена.
*   **Rancher как обертка Jenkins**: Помните, что Rancher Pipelines используют Jenkins "под капотом". При этом Rancher берет на себя всю сложность управления Jenkins, предоставляя упрощенный интерфейс.
*   **Недостатки**: В некоторых случаях Rancher Pipeline может не позволять выборочно запускать стадии (например, только `deploy` без `build`), что может привести к более длительному времени выполнения при незначительных изменениях (например, только в манифестах Kubernetes).

### Дополнительная информация

*   Официальная документация Rancher по Pipeline: [Rancher Documentation](https://rancher.com/docs/rancher/v2.x/en/pipelines/)

## Методы установки Rancher Server

### 1. Установка Rancher Server в существующий кластер Kubernetes (Helm)

Наиболее рекомендуемый и отказоустойчивый способ установки Rancher Server — развертывание его в существующем кластере Kubernetes с использованием Helm.

#### 1.1. Предварительные требования

Для стабильной работы Rancher Server в кластере Kubernetes необходимо наличие следующих компонентов:

*   **Ingress Controller**: Для маршрутизации внешнего трафика к Rancher UI и API. Например, Nginx Ingress Controller.
*   **Cert Manager**: Для автоматического управления TLS-сертификатами (выдача и обновление Let's Encrypt или самоподписанных сертификатов).
*   **Load Balancer (Балансировщик нагрузки)**: Для обеспечения внешнего доступа к Ingress Controller и распределения трафика между его подами. На Bare Metal кластерах часто используется [MetalLB](../../Networking/LoadBalancing/metallb_overview.md).

#### 1.2. Процесс установки

1.  **Добавление Helm репозитория Rancher:**
    ```bash
    helm repo add rancher-stable https://releases.rancher.com/server-charts/stable
    helm repo update
    ```
2.  **Создание Namespace для Rancher:**
    ```bash
    kubectl create namespace cattle-system
    ```
3.  **Установка Rancher Server с помощью Helm:**
    ```bash
    helm upgrade --install rancher rancher-stable/rancher \
      --namespace cattle-system \
      --set hostname=rancher.yourdomain.com \
      --set bootstrapPassword=your_initial_admin_password \
      --set ingress.ingressClassName=nginx \
      --set ingress.tls.source=rancher \
      --set replicaCount=3 # Рекомендуется для High Availability
    ```
    *   `hostname`: Доменное имя, по которому будет доступен Rancher UI.
    *   `bootstrapPassword`: Начальный пароль администратора, который будет изменен при первом входе.
    *   `ingress.ingressClassName`: Указывает класс Ingress Controller, если в кластере их несколько (например, `nginx`).
    *   `ingress.tls.source=rancher`: Rancher автоматически сгенерирует и будет управлять самоподписанными TLS-сертификатами. Для использования собственных сертификатов или Let's Encrypt потребуется дополнительная настройка (см. документацию Rancher).
    *   `replicaCount`: Количество реплик пода Rancher Server. Для отказоустойчивости рекомендуется `3`. В однонодовых кластерах или для тестирования можно установить `1`.

#### 1.3. Особенности развертывания

*   **Создание дополнительных Namespace:** Rancher Server при запуске создает множество служебных `namespaces` (например, `cattle-fleet`, `cattle-fleet-local-system`, `cattle-system`), которые используются для своих внутренних компонентов и управления.
*   **Совместимость с Kubernetes:** Как было упомянуто ранее, критически важно проверять совместимость версии Rancher с версией целевого кластера Kubernetes. Проблемы с `PodSecurityPolicy` (PSP) в Kubernetes 1.25+ являются ярким примером, когда старые версии Rancher могут не функционировать.

### 2. Установка в Docker (для тестирования/ознакомления)

Для быстрого развертывания Rancher Server в тестовых целях или для ознакомления можно использовать Docker-контейнер:

```bash
docker run -d --name=rancher --restart=unless-stopped \
  -p 80:80 -p 443:443 \
  rancher/rancher:latest
```

**Особенности и ограничения:**
*   **Внутренняя структура:** Rancher в Docker-контейнере запускается в многослойной архитектуре: внутри контейнера разворачивается легковесный дистрибутив Kubernetes (например, K3S), а уже в нём запускается сам Rancher.
*   **Нестабильность:** Такой метод установки часто сталкивается с проблемами стабильности и производительности. Он не рекомендуется для производственных сред из-за его хрупкости и ограниченных возможностей масштабирования.
*   **Альтернатива для Single-Node:** Если требуется одноузловая установка для разработки или тестирования, более стабильным и рекомендуемым подходом является прямая установка Rancher на существующий кластер [K3S](../../Kubernetes/k3s/k3s_overview.md).
*   **Важное замечание по совместимости:** Rancher, особенно до версии 2.7.x, имеет строгие требования к версии Kubernetes, в котором он разворачивается. На момент написания, Rancher часто требовал Kubernetes версии **ниже 1.25** из-за изменений, связанных с деприкацией `PodSecurityPolicy` (PSP) в Kubernetes 1.25. Перед установкой всегда проверяйте официальную документацию Rancher на предмет совместимости версий Kubernetes.

### 3. Удаление компонентов Rancher/K3S

После экспериментов или в случае необходимости полного удаления Rancher Server или K3S, можно использовать следующие команды:

*   **Удаление K3S (полная очистка кластера):**
    На узле, где установлен K3S (например, в Docker-контейнере Rancher, или при самостоятельной установке K3S), выполните:
    ```bash
    /usr/local/bin/k3s-uninstall.sh
    ```
*   **Удаление агента K3S (Worker Node):**
    На узлах, которые были добавлены как worker-ноды в кластер K3S, выполните:
    ```bash
    /usr/local/bin/k3s-agent-uninstall.sh
    ```
*   **Удаление агента Rancher (на узлах, добавленных в RKE-кластер):**
    На узлах, которые были добавлены в RKE-кластер через Rancher UI (запускался `docker run rancher-agent ...`), можно удалить агент, если он установлен как служба:
    ```bash
    # Эта команда может быть сгенерирована Rancher UI для конкретного случая
    # Например, если агент был запущен через docker run, то удаляется контейнер:
    docker rm -f <container_id_или_имя_rancher_agent>
    # Или, если установлен как сервис:
    /usr/local/bin/rancher-system-agent-uninstall.sh
    ```
    *   **Примечание:** Точная команда удаления может зависеть от метода установки агента. Чаще всего, если `rancher-agent` запускался через `docker run`, достаточно остановить и удалить соответствующий Docker-контейнер.

Эти команды помогают полностью очистить узлы от компонентов Rancher и K3S, возвращая их в исходное состояние.

## Управление пользователями и RBAC в Rancher

### Определения

*   **Пользователь Rancher**: Учетная запись, созданная в Rancher (локально или через внешние провайдеры), позволяющая получить доступ к UI и управляемым кластерам. Отличается от пользователей на уровне Kubernetes.
*   **Global Role (Глобальная роль)**: Определяет права доступа пользователя к функционалу самого Rancher (например, создание кластеров, управление пользователями). Применяется ко всем управляемым кластерам.
*   **Cluster Role (Роль уровня кластера)**: Определяет права доступа пользователя в рамках конкретного кластера Kubernetes, управляемого Rancher. Соответствует концепции `ClusterRole` в Kubernetes.
*   **Project (Проект)**: Уровень абстракции в Rancher, группирующий один или несколько `namespaces` в пределах кластера. Используется для более детального делегирования прав и управления ресурсами.
*   **Project/Namespace Role (Роль уровня проекта/неймспейса)**: Определяет права доступа пользователя в рамках конкретного проекта или `namespace`.
*   **Аутентификационный провайдер (Auth Provider)**: Внешняя система, используемая Rancher для аутентификации пользователей (например, Active Directory, OpenLDAP, GitHub, Keycloak).

### Базовые концепции

1.  **Концепция пользователя в Rancher vs. Kubernetes**:
    *   В отличие от "ванильного" Kubernetes, где отсутствует явное понятие "пользователя" с паролем и UID (как в Unix/Linux), Rancher вводит полноценную сущность пользователя. Это упрощает управление доступом для людей.
    *   Rancher управляет пользователями, а затем транслирует их права в нативные механизмы [Kubernetes RBAC](../../Security/RBAC/rbac_overview.md) для работы с кластерами.
2.  **Rancher Project vs. Kubernetes Namespace**:
    *   **Rancher Project** — это логическая группировка одного или нескольких **Kubernetes Namespaces**. При создании `Project` в Rancher, вы определяете границы для RBAC и ресурсных квот, которые будут применяться к `namespaces`, входящим в этот `Project`.
    *   При этом, если пользователь, имеющий права только на `Project` в Rancher, попытается создать `Namespace` напрямую через `kubectl` (например, `kubectl create namespace my-new-ns`), этот `namespace` не будет автоматически связан с его `Project` в Rancher и не будет виден в Rancher UI в контексте этого `Project`. Соответственно, пользователь не сможет управлять таким `namespace` через веб-интерфейс Rancher и к нему не будут применены RBAC-политики, определенные на уровне Rancher `Project`. Для корректной работы `namespaces` должны быть созданы *внутри* Rancher `Project` через UI Rancher или с соответствующими метками, указывающими на принадлежность к `Project`.
3.  **Иерархия доступа**:
        *   **Global**: Определяет, что пользователь может делать с самим Rancher (создавать кластеры, управлять пользователями, настраивать провайдеров).
        *   **Cluster**: Определяет, что пользователь может делать в конкретном кластере (владелец, член).
        *   **Project**: В рамках кластера, `Project` группирует `namespaces` и позволяет детализировать разрешения и ресурсные квоты.
        *   **Namespace**: Самый гранулярный уровень, где разворачиваются приложения.3.  **Типы пользователей**:
    *   **Локальные пользователи**: Создаются и управляются непосредственно в Rancher.
    *   **Внешние пользователи**: Аутентифицируются через внешние провайдеры (LDAP, Active Directory, FreeIPA, Keycloak и т.д.), что позволяет централизовать управление учетными записями. Rancher взаимодействует с ними по протоколу LDAP.
4.  **Преимущества RBAC в Rancher**:
    *   **Удобство**: Упрощенное управление правами доступа через UI.
    *   **Делегирование**: Возможность делегировать управление частями кластера или проектами другим командам/пользователям.
    *   **Ограничение ресурсов**: Интегрированные механизмы квот на уровне проектов.

### Практические сценарии

#### 1. Создание локального пользователя и назначение глобальных прав

1.  В Rancher UI перейдите в **Global Settings** -> **User & Authentication** -> **Users**.
2.  Нажмите **Add User**.
3.  Укажите `Username`, `Display Name`, `Description` и `Password`.
4.  В разделе **Global Permissions** выберите подходящую глобальную роль:
    *   **Standard User**: Может создавать новые кластеры, управлять своими кластерами и проектами.
    *   **User-Base**: Может только логиниться в Rancher UI и видеть доступные ему кластеры/проекты, но не может создавать новые. Идеально для "рабочих" пользователей (DevOps), которым нужно только развертывать приложения в выделенных для них проектах.
5.  Нажмите **Create**.

#### 2. Создание проекта с ресурсными квотами и добавление пользователя

Проект в Rancher является логической группировкой `namespaces` и позволяет применять ресурсные ограничения.

1.  В Rancher UI перейдите в **Global** -> **Clusters** -> (ваш кластер) -> **Projects/Namespaces**.
2.  Нажмите **Create Project**.
3.  Укажите `Project Name` (например, `testapp`), `Description`.
4.  В разделе **Project Members** добавьте созданного ранее пользователя и назначьте ему роль уровня проекта:
    *   **Project Owner**: Полные права на управление проектом, включая изменение его параметров и ресурсных квот.
    *   **Project Member**: Может создавать и управлять ресурсами (Deployment, Service и т.д.) внутри проекта и его `namespaces`, но не может изменять параметры самого проекта. Рекомендуется для большинства DevOps-команд.
    *   **Read-only**: Только просмотр всех ресурсов проекта, кроме секретов.
    *   Также можно определить `Custom` роли, выбирая конкретные разрешения.
5.  **Настройка Resource Quotas (Ресурсные квоты)**:
    *   **Project Limits**: Определите лимиты ресурсов для всего проекта. Эти лимиты будут распределяться между `namespaces` внутри проекта.
        *   Например: `CPU Limit` (в mCPU), `Memory Limit` (в MB/GB).
    *   **Namespace Default Limits**: Укажите значения по умолчанию для лимитов и запросов CPU/Memory, которые будут автоматически применяться к новым `namespaces`, создаваемым в этом проекте, если они не указаны явно.
        *   Это гарантирует, что каждый новый `namespace` будет иметь предопределенные квоты, не превышающие общие лимиты проекта.
6.  Нажмите **Create**.

#### 3. Работа пользователя в проекте: создание Namespace и развертывание приложения

1.  **Логин как обычный пользователь**: Пользователь входит в Rancher UI. Он видит только кластеры и проекты, к которым ему предоставлен доступ.
2.  **Скачивание Kubeconfig**: Для работы с `kubectl` или другими CLI-инструментами пользователь может скачать файл `kubeconfig` из Rancher UI (раздел **Cluster Explorer** -> **Kubeconfig File**). Этот файл содержит необходимые учетные данные и контекст для доступа к кластеру с ограниченными правами.
3.  **Создание Namespace (через Rancher UI)**:
    *   В разделе **Projects/Namespaces** -> (ваш проект) -> **Namespaces** нажмите **Create Namespace`.
    *   Укажите `Namespace Name`.
    *   **Настройка Resource Limits**: В UI пользователь может легко распределить доступные ему квоты (унаследованные от проекта) на конкретный `namespace` (например, выделить 2 ядра CPU и 1024MB RAM из общих 4 ядер и 2048MB RAM проекта). Это преимущество UI перед ручным созданием YAML.
    *   **Container Default Resource Limits**: **Рекомендуется не устанавливать.** Это приучает разработчиков явно указывать `requests` и `limits` для своих подов. Если они не будут указаны, развертывание пода завершится ошибкой, что способствует лучшей практике.
4.  **Развертывание приложения (через Rancher UI или kubectl)**:
    *   Пользователь может создать `Deployment`, `Service` и другие ресурсы через Rancher UI (раздел **Workloads**). При этом UI позволяет удобно настроить:
            *   `Image` контейнера.
            *   `Port Mapping`.
            *   Автоматическое создание `Service`.
            *   **Resource Requests/Limits**: При развертывании приложения пользователь **обязан** указать `requests` и `limits` для CPU и памяти каждого контейнера в поде. Эти значения должны соответствовать квотам, установленным для `namespace` и проекта. Если они не указаны или превышают квоты, под не будет запущен.
        *   Или использовать `kubectl apply -f your-app.yaml`, убедившись, что манифесты соответствуют назначенным правам и квотам.
5.  **Настройка RBAC для просмотра мониторинга приложений**:
        *   Для того чтобы пользователь мог видеть метрики своих приложений в общей Grafana Rancher (или Prometheus), ему необходимо предоставить соответствующие права на `Project`, в котором установлен стек мониторинга (например, `Project Monitoring`).
        *   **Минимальные роли**:
            *   `View Monitoring`: Эта роль позволяет просматривать Grafana, Prometheus и Alertmanager.
            *   `Manage Services`: **Крайне важно** добавить эту роль *вместе* с `View Monitoring`. Без `Manage Services` пользователь будет постоянно сталкиваться с ошибками в UI Rancher, связанными с отсутствием прав на создание прокси-сервисов. Эта необходимость не задокументирована и выявлена опытным путем.
        *   **Процесс:**
            1.  В Rancher UI (как администратор) перейдите в `Project/Namespaces` -> (ваш Project мониторинга, например, `Monitoring`).
            2.  В разделе `Members` добавьте пользователя и назначьте ему обе роли: `View Monitoring` и `Manage Services`.

#### 4. Создание и привязка кастомных ролей

Rancher позволяет создавать собственные `ClusterRole` и `Role` для более тонкой настройки разрешений, аналогично нативному Kubernetes RBAC.

1.  В Rancher UI (как администратор) перейдите в **Global Settings** -> **Role Based Access Control** -> **Cluster Roles** (или **Project/Namespace Roles**).
2.  Нажмите **Create Cluster Role**.
3.  Укажите `Name` (например, `view-ns` для просмотра `namespaces`), `Description`.
4.  В разделе **Rules** укажите `Verbs` (например, `get`, `list`, `watch`) и `Resources` (например, `namespaces`).
5.  После создания роли, ее можно привязать к пользователю в разделе **Cluster Members** (или **Project Members**) для конкретного кластера/проекта.
    *   **Примечание:** Назначение нескольких кастомных ролей одному пользователю может быть нетривиальным и иногда требовать добавления пользователя несколько раз с разными ролями в UI.

### Дополнительная информация

*   **Rancher как "точка входа" для RBAC**: Rancher предоставляет централизованное и удобное средство для управления сложным механизмом Kubernetes RBAC, что является его ключевым преимуществом.
*   **Гибкость настройки**: Возможность использования как встроенных, так и кастомных ролей, а также интеграция с внешними аутентификационными провайдерами, делает Rancher очень гибким инструментом для управления доступом.
*   **Альтернативы**: Несмотря на мощь RBAC в Rancher, некоторые организации предпочитают использовать другие инструменты (например, [ArgoCD](../../GitOps/argo_cd_overview.md)) для управления правами доступа к развертыванию, если их экосистема уже построена вокруг GitOps-принципов и не требует всего функционала Rancher.
