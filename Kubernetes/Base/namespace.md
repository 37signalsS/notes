# Пространства имен (Namespace)

## Определения

**Namespace (Пространство имен)** — это объект **API (Application Programming Interface)** в Kubernetes, предназначенный для логического разделения одного физического кластера на несколько виртуальных кластеров. Он обеспечивает изолированную рабочую область для группы ресурсов, что позволяет разным командам, проектам или окружениям сосуществовать в одном кластере, соблюдая принцип **Separation of Concerns** (разделение ответственности).

Имена ресурсов (например, подов или сервисов) должны быть уникальными только в пределах одного `Namespace`. Это позволяет избежать конфликтов при развертывании идентичных стеков приложений в разных логических сегментах.

## Основные концепции

### Назначение и функции

1.  **Организация ресурсов:** Группировка объектов по проектам, командам или средам исполнения: **dev (development)**, **staging**, **prod (production)**.
2.  **Предотвращение конфликтов имен:** Позволяет запускать несколько экземпляров одного приложения (например, с именем `web-app`) в разных пространствах имен без риска пересечения имен в API.
3.  **Управление доступом (RBAC):** `Namespace` является основной единицей для применения политик **RBAC (Role-Based Access Control)**. Это позволяет гибко ограничивать права пользователей (например, полный доступ в `dev` и права только на чтение в `prod`).
4.  **Квотирование ресурсов (Resource Quotas):** Механизм ограничения суммарного потребления вычислительных ресурсов — **CPU (Central Processing Unit)** и оперативной памяти, а также лимитирование количества объектов (подов, сервисов, секретов) для конкретной группы пользователей.
5.  **Изоляция сетевых политик (Network Policies):** Позволяет контролировать сетевое взаимодействие между подами как внутри одного `Namespace`, так и между разными пространствами имен.

### Типы ресурсов по области действия

В Kubernetes ресурсы делятся на те, что привязаны к пространству имен, и общекластерные (Cluster-wide).

*   **Namespaced-ресурсы (внутри Namespace):**
    *   **Рабочие нагрузки:** [Pod](./Pod/pod_overview.md), [Deployment](./Deployment/index.md), [StatefulSet](./StatefulSet/statefulset_overview.md), [DaemonSet](./daemonset.md), [Job](./job.md), [CronJob](./job.md).
    *   **Конфигурация и сервисы:** [Service](../Networking/Service/service_overview.md), [Ingress](../Networking/Ingress/overview.md), [ConfigMap](./configmap.md), [Secret](./secrets/secrets_basics.md), `PersistentVolumeClaim`.
    *   **Политики и ограничения:** `NetworkPolicy`, `ResourceQuota`, `LimitRange`.
*   **Общекластерные ресурсы (Cluster-wide):**
    *   **Инфраструктура:** `Node` (узлы), `PersistentVolume` (физические тома).
    *   **Безопасность:** `ClusterRole`, `ClusterRoleBinding`.
    *   **Системные метаданные:** `Namespace`, `StorageClass`, `PriorityClass`.

### Автоматические метки (v1.21+)

Начиная с версии 1.21, Kubernetes автоматически добавляет метку `kubernetes.io/metadata.name` к каждому объекту Namespace. Значение этой метки всегда совпадает с именем пространства имен. Это упрощает написание `NetworkPolicy` и `PodAffinity`, так как позволяет выбирать целевые пространства имен без необходимости их предварительной ручной разметки администратором.

### DNS-адресация и FQDN

Kubernetes предоставляет встроенный DNS-сервис (CoreDNS), который формирует записи для сервисов. Полное доменное имя (**FQDN**) для Service имеет формат:
`<имя-сервиса>.<имя-namespace>.svc.cluster.local`

**Нюансы адресации:**
*   **Внутри одного Namespace:** Достаточно использовать только имя сервиса (например, `db-service`).
*   **Между разными Namespace:** Необходимо указывать как минимум имя и пространство имен (например, `db-service.database`).
*   **Полный путь:** Рекомендуется использовать для конфигураций, которые могут быть перенесены между кластерами или при использовании Service Mesh (Istio).

## Практические сценарии

### Создание и базовое управление

```bash
# Создание через императивную команду
kubectl create namespace my-project

# Декларативное создание с метаданными (рекомендуется для GitOps)
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Namespace
metadata:
  name: billing-prod
  labels:
    environment: production
    team: billing
    security-level: high
EOF

# Список всех пространств имен с их статусом
kubectl get namespaces
```

### Настройка контекста и окружения

Чтобы избежать постоянного указания флага `-n <namespace>`, следует настроить текущий контекст:

```bash
# Установить пространство имен по умолчанию для текущего контекста
kubectl config set-context --current --namespace=my-project

# Просмотр текущей конфигурации для проверки
kubectl config view --minify | grep namespace
```

### Проверка области действия ресурса

Если вы не уверены, является ли ресурс (например, `CustomResourceDefinition` или `Certificate`) общекластерным или относится к Namespace:

```bash
# Ресурсы, требующие указания Namespace
kubectl api-resources --namespaced=true

# Общекластерные ресурсы
kubectl api-resources --namespaced=false
```

### Сценарии на собеседованиях: «Весь интернет в одном Namespace»

Этот вопрос часто задается для проверки понимания ограничений масштабируемости Kubernetes и умения анализировать сложные системы.

**Неправильный ответ:** «Это невозможно» или «Интернет слишком большой». Это демонстрирует ограниченное понимание архитектуры.

**Правильный подход:**
1.  **Уточнение контекста:** Спросите, идет ли речь о данных, сервисах или всей инфраструктуре. Это показывает методичный подход.
2.  **Технические ограничения Namespace:**
    *   **Ресурсы:** Общая память и CPU кластера ограничивают возможности любого пространства имен.
    *   **Объекты:** Большое количество подов, сервисов и секретов в одном Namespace создает нагрузку на API-сервер и etcd.
    *   **Изоляция:** Хотя пространства имен обеспечивают логическую изоляцию, Kubernetes сам по себе накладывает жесткие ограничения на масштабирование объектов внутри одной единицы управления.
3.  **Ограничения масштабирования кластера:**
    *   Kubernetes сам по себе имеет пределы (например, рекомендуемый лимит в 5000 узлов и 150 000 подов на кластер).
    *   **Масштабируемость:** На практике интернет-службы распределяются по **нескольким пространствам имен** для лучшего управления ресурсами, разграничения прав доступа и минимизации радиуса поражения (blast radius) при сбоях.
    *   Для масштаба всего Интернета потребуется архитектура с множеством кластеров, распределенных систем и микросервисов. Даже Kubernetes работает в рамках физических пределов инфраструктуры.
4.  **Резюме:** Хотя Namespace логически изолирует ресурсы, физические ограничения инфраструктуры и лимиты самого Kubernetes требуют продуманного разделения огромных нагрузок на несколько пространств имен или даже кластеры. Ни одно пространство имен не может вместить рабочую нагрузку «размером с интернет» без глубокого архитектурного разделения.

### Диагностика «зависших» пространств имен (Terminating)

При удалении Namespace (`kubectl delete ns <name>`) он переходит в состояние `Terminating`. В этот момент контроллер начинает каскадное удаление всех вложенных ресурсов. Если Namespace «завис» в этом состоянии:

1.  **Проверьте наличие ресурсов:** Возможно, в Namespace остались объекты (например, кастомные ресурсы), которые не могут быть удалены из-за своих финализаторов.
2.  **Анализ финализаторов (Finalizers):** Финализаторы блокируют удаление, пока не будет выполнена определенная логика очистки.
    ```bash
    kubectl get ns <name> -o jsonpath='{.spec.finalizers}'
    ```
    Если в списке есть `kubernetes`, это означает, что Namespace ждет удаления всех вложенных ресурсов. Если там присутствуют другие значения — проблема в стороннем контроллере или операторе.
3.  **Подробности в статусе:**
    ```bash
    kubectl get ns <name> -o json | jq '.status.conditions'
    ```

Подробнее о механизмах решения проблем с финализаторами см. в разделе **[Проблемы с финализаторами (Finalizers)](../Troubleshooting/Common_Errors/PodTerminating/finalizer_issues.md)**.

## Дополнительная информация

### Стандартные пространства имен

*   **`default`**: Используется по умолчанию для всех команд `kubectl`, если Namespace не указан явно. Рекомендуется использовать только для временных экспериментов, но не для продуктивных нагрузок.
*   **`kube-system`**: Резервируется для системных компонентов Kubernetes (API Server, Scheduler, Controller Manager, CoreDNS, CNI-плагины). Обычным пользователям не рекомендуется размещать здесь свои приложения.
*   **`kube-public`**: Автоматически создаваемое пространство имен, доступное для чтения всем пользователям (включая неаутентифицированных). Обычно используется для хранения общекластерной информации (например, `cluster-info`).
*   **`kube-node-lease`**: Используется для хранения объектов **Lease**, которые представляют собой сигналы работоспособности (heartbeats) каждого узла. Это позволяет кластеру быстрее обнаруживать отказы узлов без избыточной нагрузки на etcd.

### Ресурсные квоты и лимиты

*   **ResourceQuota:** Позволяет администратору ограничить суммарное потребление ресурсов (CPU, RAM, количество Pod/Service/PVC) в рамках одного Namespace.
*   **LimitRange:** Позволяет задать значения запросов (requests) и лимитов (limits) по умолчанию для контейнеров, если разработчик не указал их в манифесте, а также ограничить минимальные и максимальные значения.

### Ограничения изоляции

Namespace обеспечивает **логическую**, но не **физическую** изоляцию по умолчанию:
1.  **Сетевая доступность:** По умолчанию поды из разных Namespace могут свободно взаимодействовать по сети. Для запрета трафика необходимо использовать [Network Policies](../Networking/Network/network_policy.md).
2.  **Общие узлы:** Поды из разных Namespace могут запускаться на одном и том же физическом узле (Node), разделяя его ядро, диск и сеть.
3.  **Каскадное удаление:** Удаление Namespace приводит к немедленному и безвозвратному удалению всех ресурсов внутри него. **Будьте крайне осторожны с этой операцией в Production.**
