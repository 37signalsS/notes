# StatefulSet: Лучшие практики

## Определения

**StatefulSet: Лучшие практики** — набор экспертных рекомендаций по настройке и эксплуатации контроллера StatefulSet для обеспечения максимальной надежности, сохранности данных и предсказуемости поведения приложений с состоянием в кластере Kubernetes.

## Основные концепции

### Обеспечение высокой доступности

Для предотвращения потери доступности кластерных приложений (базы данных, брокеры сообщений) при плановых работах или сбоях необходимо использовать следующие механизмы:

1.  **Pod Disruption Budget (PDB):** Устанавливает лимит на количество одновременно недоступных подов при добровольном выселении (например, при обслуживании узла).
    *   Рекомендация: Для кластеров из 3 узлов устанавливайте `maxUnavailable: 1` или `minAvailable: 2`.
    *   Подробнее: **[Pod Disruption Budget](../../Autoscaling/pod_disruption_budget.md)**.
2.  **Pod Anti-Affinity:** Гарантирует, что поды одного StatefulSet будут запущены на разных физических узлах или в разных зонах доступности (**Availability Zones**).
    *   Рекомендация: Используйте `requiredDuringSchedulingIgnoredDuringExecution` для жесткого разделения подов по узлам.
    *   Подробнее: **[Affinity и Anti-Affinity](../../Scheduling/affinity.md)**.

### Стратегия управления хранилищем

Правильная настройка **[PersistentVolume (PV)](../../Storage/pv_and_pvc.md)** и **[PersistentVolumeClaim (PVC)](../../Storage/pv_and_pvc.md)** критична для сохранности данных:

*   **Режим привязки томов:** В **StorageClass** всегда используйте `volumeBindingMode: WaitForFirstConsumer`. Это гарантирует, что том будет создан в той же зоне доступности, где планировщик решил запустить под.
*   **Политика восстановления:** Используйте `reclaimPolicy: Retain` для критических данных. Это предотвратит автоматическое удаление физического диска при удалении PVC, давая возможность восстановить данные вручную.
*   **Производительность:** Выбирайте типы дисков с соответствующим уровнем **IOPS (Input/Output Operations Per Second)**. Для баз данных предпочтительны локальные SSD (Solid State Drive) или быстрые сетевые SSD.

### Проверки состояния (Probes)

Корректно настроенные пробы предотвращают каскадные сбои:

*   **Readiness Probe:** Определяет готовность приложения принимать трафик. В StatefulSet это критично для обновлений: следующий под не начнет обновляться, пока текущий не пройдет Readiness-проверку.
*   **Liveness Probe:** Должна быть максимально простой (проверка порта или базовый HTTP-запрос). Слишком сложные проверки могут вызвать бесконечные перезапуски при временных перегрузках.
*   **Startup Probe:** Используйте для приложений с длительным временем инициализации (например, восстановление БД после сбоя), чтобы Liveness-проба не убила процесс до его завершения.

Подробнее: **[Пробы (Probes)](../probes.md)**.

### Управление жизненным циклом и очистка

*   **Политика удержания PVC:** Настраивайте `persistentVolumeClaimRetentionPolicy` (доступно с Kubernetes 1.27) в зависимости от среды. В Dev-средах полезно автоматическое удаление (`Delete`), в Production — строгое удержание (`Retain`).
*   **Принудительное удаление:** Избегайте использования `kubectl delete pod --force --grace-period=0` для подов StatefulSet. Это может привести к нарушению целостности данных или ситуации "split-brain", так как старый процесс может еще работать и держать блокировку на диске.

## Практические сценарии

### Обновление приложений через Helm

**Проблема:** При использовании **Helm** для обновления базы данных часто возникают ошибки совместимости старых данных на PVC с новой версией образа.

**Решение:**
1.  **Бэкап:** Всегда создавайте Snapshot (снимок) тома через **CSI (Container Storage Interface)** перед обновлением.
2.  **Миграция:** Используйте `initContainers` для автоматического выполнения скриптов миграции схемы данных перед запуском основного контейнера.
3.  **Поэтапное обновление:** Используйте параметр `partition` в `updateStrategy` для обновления только одной реплики ("канарейки"), проверки её работоспособности и последующего завершения раскатки.

### Безопасное масштабирование вниз

Перед уменьшением количества реплик (`replicas`) в кластерных системах (Kafka, Elasticsearch):
1.  Убедитесь, что данные синхронизированы и на оставшихся узлах достаточно места для перераспределения нагрузки.
2.  Проверьте текущий статус **PDB**, чтобы не нарушить квоту доступности при параллельном выселении подов.
3.  Выполните команду масштабирования: `kubectl scale statefulset <name> --replicas=<N>`.

### Диагностика при застревании обновлений

Если обновление StatefulSet остановилось:
1.  Проверьте статус Readiness-пробы текущего обновляемого пода: `kubectl describe pod <pod-name>`.
2.  Изучите события StatefulSet: `kubectl describe statefulset <name>`.
3.  Проверьте наличие свободных дисков в зоне доступности: часто причиной является достижение лимитов облачного провайдера на количество подключенных томов.

## Дополнительная информация

### Ограничения и особенности

*   StatefulSet не выполняет автоматическое перераспределение подов при падении узла (защита данных).
*   Удаление контроллера по умолчанию не ведет к удалению дисков.
