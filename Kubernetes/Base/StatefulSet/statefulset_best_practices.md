# StatefulSet: Лучшие практики

## Определения

**StatefulSet: Лучшие практики** — набор экспертных рекомендаций по настройке и эксплуатации контроллера StatefulSet для обеспечения максимальной надежности, сохранности данных и предсказуемости поведения приложений с состоянием (stateful) в кластере Kubernetes.

## Основные концепции

### Обеспечение высокой доступности и стабильности

Для предотвращения простоя кластерных приложений (базы данных, брокеры сообщений) при плановых работах или сбоях:

1.  **Pod Disruption Budget (PDB):** Устанавливает лимит на количество одновременно недоступных подов при добровольном выселении (например, `kubectl drain`).
    *   Рекомендация: Для кластера из 3 узлов устанавливайте `minAvailable: 2`.
    *   Подробнее: **[Pod Disruption Budget](../../Autoscaling/pod_disruption_budget.md)**.
2.  **Pod Anti-Affinity:** Гарантирует распределение подов по разным узлам или зонам доступности (AZ).
    *   Рекомендация: Используйте `requiredDuringSchedulingIgnoredDuringExecution`, чтобы избежать запуска двух реплик БД на одном узле.
    *   Подробнее: **[Affinity и Anti-Affinity](../../Scheduling/affinity.md)**.
3.  **Стабильность при запуске (`minReadySeconds`):** Укажите время (например, 30–60 секунд), в течение которого под должен проработать без ошибок, прежде чем Kubernetes сочтет его готовым. Это предотвращает каскадное обновление на заведомо неисправную версию, если она падает не сразу.

### Стратегия управления хранилищем

Правильная настройка **[PersistentVolume (PV)](../../Storage/pv_and_pvc.md)** и **[PersistentVolumeClaim (PVC)](../../Storage/pv_and_pvc.md)** критична для сохранности данных:

*   **Режим привязки томов:** В **StorageClass** всегда используйте `volumeBindingMode: WaitForFirstConsumer`. Это гарантирует создание тома в той же AZ, где запланирован под.
*   **Расширение томов:** Убедитесь, что в StorageClass установлено `allowVolumeExpansion: true`. Это позволяет увеличивать объем дисков без пересоздания StatefulSet.
*   **Политика удержания PVC:** Используйте поле `persistentVolumeClaimRetentionPolicy` (GA в v1.32).
    *   `whenDeleted: Retain` — сохранить данные при удалении StatefulSet (рекомендуется для Production).
    *   `whenScaled: Delete` — удалять диск при уменьшении количества реплик (полезно для временных данных или Dev-сред).
*   **Снимки (Snapshots):** Настройте регулярное создание CSI-снимков томов перед обновлениями или миграциями для быстрого отката.

### Проверки состояния (Probes)

Корректно настроенные пробы предотвращают каскадные сбои:

*   **Readiness Probe:** Определяет готовность принимать трафик. В StatefulSet это критично: следующий под не начнет обновляться, пока текущий не пройдет Readiness-проверку.
*   **Liveness Probe:** Должна быть максимально простой (проверка порта или базовый HTTP-запрос). Сложные проверки могут вызвать бесконечные перезапуски при временных перегрузках.
*   **Startup Probe:** Используйте для приложений с длительной инициализацией (например, восстановление БД), чтобы Liveness-проба не убила процесс до его завершения.
*   Подробнее: **[Пробы (Probes)](../probes.md)**.

### Управление обновлениями и индексами

Современные версии Kubernetes (v1.31+) предоставляют расширенный контроль:

*   **Ускорение обновлений (`maxUnavailable`):** По умолчанию StatefulSet обновляет поды строго по одному. Для больших кластеров можно разрешить параллельное обновление (GA в v1.31), если приложение поддерживает временное снижение кворума.
*   **Управление индексами (`ordinals`):** Используйте `spec.ordinals.start` (GA в v1.31) для запуска подов с произвольного индекса. Это упрощает миграцию данных между кластерами: можно запустить поды 3-5 в новом кластере, пока 0-2 работают в старом.
*   **Поэтапное обновление (`partition`):** Позволяет обновить только часть подов (например, одну реплику как «канарейку»), проверить её работу и только затем продолжить раскатку.

### Сетевая идентификация и эксплуатация

*   **Headless Service:** Всегда используйте Headless Service (`clusterIP: None`) для обеспечения стабильных DNS-имен вида `pod-0.service.ns.svc.cluster.local`. Это необходимо для формирования кворума в распределенных системах.
*   **Корректное завершение (`terminationGracePeriodSeconds`):** Базам данных часто требуется больше стандартных 30 секунд для сброса кэша на диск и передачи роли лидера. Устанавливайте значение осознанно (например, 120–300 секунд).
*   **Нативные Sidecar-контейнеры:** Используйте `restartPolicy: Always` в `initContainers` (GA в v1.29) для вспомогательных прокси-контейнеров. Это гарантирует их запуск до основного приложения и работу пров готовности.
*   **Ресурсы и OOM:** Всегда задавайте `requests` и `limits`. Для БД лимит памяти должен быть жестким, чтобы планировщик не вытеснял критические процессы и не срабатывал OOM Killer.

## Практические сценарии

### Бесшовная миграция между кластерами

**Задача:** Перенести stateful-приложение из кластера A в кластер B без конфликта имен и индексов.

**Решение:**
1. Синхронизировать данные томов.
2. В кластере B создать StatefulSet с `spec.ordinals.start: 3` (если в кластере A работают поды 0-2).
3. Переключить трафик на новый кластер.
4. Поэтапно остановить поды в кластере A и обнулить `start` в кластере B для возврата к стандартной нумерации.

### Диагностика при застревании обновлений

Если обновление StatefulSet остановилось:
1. Проверьте статус Readiness-пробы текущего пода: `kubectl describe pod <pod-name>`.
2. Проверьте события: `kubectl describe statefulset <name>`.
3. Убедитесь, что `minReadySeconds` не слишком велико и под успевает пройти проверку.
4. Проверьте наличие свободных дисков в AZ: часто причиной является лимит облачного провайдера на количество томов.

## Дополнительная информация

### Ограничения и особенности

* StatefulSet не выполняет автоматическое перераспределение подов при падении узла (защита от повреждения данных при одновременном доступе с двух узлов).
* Удаление контроллера по умолчанию не ведет к удалению PVC и PV.
