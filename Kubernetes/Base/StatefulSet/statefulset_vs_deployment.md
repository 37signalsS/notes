# Сравнение Deployment и StatefulSet

## Определения

**Deployment** — основной контроллер Kubernetes для управления приложениями без сохранения состояния (stateless), такими как веб-серверы и **API (Application Programming Interface)**. Поды в Deployment рассматриваются как взаимозаменяемые экземпляры.

**StatefulSet** — контроллер для управления приложениями с состоянием (stateful), такими как базы данных и брокеры сообщений. Обеспечивает стабильные сетевые идентификаторы и привязку к постоянному хранилищу.

Базовые принципы работы каждого контроллера описаны в разделах **[Kubernetes Deployment](../Deployment/index.md)** и **[Ключевые концепции StatefulSet](./statefulset_core_concepts.md)**.

## Основные концепции

### Сравнительная характеристика

| Характеристика | Deployment | StatefulSet |
| :--- | :--- | :--- |
| **Тип нагрузки** | Stateless (веб-интерфейсы, API) | Stateful (базы данных, очереди) |
| **Идентификация** | Эфемерные имена и **IP (Internet Protocol)** | Стабильные имена и **DNS (Domain Name System)** |
| **Хранилище** | Общее (временное или сетевое) | Индивидуальное для каждого пода |
| **Порядок в жизненном цикле** | Случайный или параллельный | Строго последовательный (0..N-1) |
| **Обновление** | Агрессивное, параллельное | Последовательное (по одному поду) |

### Ключевое отличие: Стратегия обновления

**Deployment** нацелен на скорость. При обновлении он может запускать новые поды до того, как старые будут полностью удалены, что эффективно для stateless-сервисов.

**StatefulSet** придерживается консервативной стратегии. Он обновляет поды строго по одному, дожидаясь перехода предыдущего пода в состояние `Ready`, прежде чем остановить следующий. Это критично для кластерных систем, чувствительных к порядку узлов.

### Поведение подов и сетевой доступ

В **Deployment** доступ к группе подов обычно осуществляется через один виртуальный IP сервиса. В **StatefulSet** каждый под имеет собственную DNS-запись, что позволяет обращаться напрямую к конкретной реплике (например, только к мастеру базы данных).

## Практические сценарии

### Выбор контроллера по типу хранилища

Выбор между Deployment и StatefulSet часто диктуется режимом доступа к данным (**Access Mode**).

#### Сценарий 1: Общее хранилище ReadWriteMany (RWX)
Для **CMS (Content Management System)** или файловых хранилищ, использующих **NFS (Network File System)**, оптимален **Deployment**:
*   Все поды подключаются к одному **PVC (PersistentVolumeClaim)**.
*   Блокировки файлов обрабатываются на уровне файловой системы.

#### Сценарий 2: Блочное хранилище ReadWriteOnce (RWO)
Если используются облачные диски с режимом **RWO (ReadWriteOnce)** (доступ только с одного узла), использование **StatefulSet** обязательно:
*   Deployment может вызвать конфликт при обновлении (старый узел не отпустил диск, а новый уже пытается его примонтировать).
*   StatefulSet гарантирует, что диск будет освобожден перед запуском нового пода.

### Алгоритм миграции с Deployment на StatefulSet

Если приложению потребовалась стабильная идентичность, выполните следующие шаги:

1.  **Создание Headless Service:** Обеспечивает DNS-имена для будущих подов StatefulSet.
2.  **Описание StatefulSet:** Создание нового манифеста с использованием `volumeClaimTemplates`.
3.  **Перенос данных:** Копирование данных со старых томов на новые индивидуальные PVC.
4.  **Переключение трафика:** Удаление старого Deployment и масштабирование StatefulSet.

Пример команды для проверки порядка запуска при миграции:
```bash
kubectl get pods -l app=my-app -w
# Наблюдайте, как поды появляются строго по очереди: app-0, затем app-1.
```

## Дополнительная информация

### Критерии выбора

| Приложение требует... | Используйте |
| :--- | :--- |
| Масштабирование без зависимостей | Deployment |
| Стабильное имя хоста для каждого узла | StatefulSet |
| Автоматическое восстановление на любом узле | Deployment |
| Привязку диска к конкретному индексу пода | StatefulSet |
