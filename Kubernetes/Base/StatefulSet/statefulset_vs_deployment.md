# Сравнение Deployment, StatefulSet и DaemonSet

## Определения

*   **Deployment** — основной контроллер для приложений без состояния (stateless). Поды рассматриваются как эфемерные, полностью взаимозаменяемые и не имеющие индивидуальной «личности». Оптимален для веб-серверов, API и микросервисов.
*   **StatefulSet** — специализированный контроллер для приложений с состоянием (stateful). Гарантирует уникальность, строгий порядок операций и стабильную идентичность (имя, сеть, диск) для каждой реплики. Необходим для баз данных и распределенных систем.
*   **DaemonSet** — контроллер, гарантирующий запуск ровно одной копии пода на каждом узле (или на выбранном подмножестве узлов). Предназначен для системных инфраструктурных сервисов.

Теоретические основы типов нагрузок см. в разделе **[Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md)**.

## Предварительные требования

Документ сравнивает поведение контроллеров и помогает выбрать нужный, поэтому предполагается:

1.  **Базовое владение kubectl** и понимание объектов [Pod](../Pod/pod_overview.md), Service, [PersistentVolumeClaim (PVC)](../../Storage/pv_and_pvc.md).
2.  **Понимание предметных областей трех контроллеров** перед сравнением свойств: [Deployment](../Deployment/index.md), [StatefulSet](./statefulset_overview.md), [DaemonSet](../daemonset.md).
3.  **Рекомендуемые версии кластера — v1.35–v1.37:** часть описываемых ниже возможностей (`persistentVolumeClaimRetentionPolicy`, `maxUnavailable`, стратегия `Recreate`) доступна только в современных релизах. Для проверки конкретной версии используется команда `kubectl version --short`.

## Основные концепции

### Сравнительная таблица характеристик (актуальные версии v1.35–v1.37)

| Характеристика | Deployment | StatefulSet | DaemonSet |
| :--- | :--- | :--- | :--- |
| **Именование подов** | Случайные суффиксы (`web-6c7d9b5d6-abc12`) | Стабильные индексы (`db-0`, `db-1`) | Случайный суффикс (`agent-4x2k9`), одна копия на узел |
| **Сетевой доступ** | Через Service (ClusterIP/LB) | Прямой (Headless Service) | hostNetwork/hostPort или IP узла |
| **DNS-идентификация** | Общая запись сервиса (endpoints) | Индивидуальная FQDN для каждого пода | Через имя узла (`spec.nodeName`/`status.hostIP`) |
| **Тип хранилища** | Общее (RWX) или эфемерное | Индивидуальное для каждой реплики (RWO) | Локальное (`hostPath`), системные тома |
| **Управление PVC** | Ручное создание/удаление | Автоматизация (`volumeClaimTemplates` + `retentionPolicy`) | Обычно не используются PVC |
| **Порядок операций** | Параллельный и случайный | Строго последовательный (0..N-1) | Независимый на каждом узле |
| **Обновление** | Агрессивное (`maxSurge`), есть `maxUnavailable` | Консервативное (по одному, `partition`) | Поузловое (`RollingUpdate`, `maxSurge` с v1.25) |
| **Масштабирование** | Мгновенное (параллельное), HPA | Постепенное (ожидание готовности), HPA | Автоматическое (по числу узлов), HPA нет |
| **Пересоздание при отказе узла** | Автоматически на другом узле | Не автоматически (защита от Split-brain) | На том же узле после его возврата |
| **Хранение истории ревизий** | Объекты ReplicaSet (N старых RS) | Объекты ControllerRevision | Объекты ControllerRevision |
| **Пауза/возобновление rollout** | Да (`kubectl rollout pause/resume`) | Нет | Нет |
| **PDB (добровольные прерывания)** | Применяется | Применяется (кворумные системы) | Не имеет смысла (один под на узел) |

### Глубокие различия в сетевой идентичности

**Deployment** использует абстракцию Service для балансировки трафика. Клиенту не важен конкретный экземпляр пода. Если под пересоздается, он получает новый IP и имя, но Service продолжает маршрутизацию прозрачно. Между подом и Service нет постоянной привязки «имя → личность».

**StatefulSet** предоставляет каждому поду «личность». Благодаря Headless Service каждый экземпляр получает постоянный FQDN:
`$(pod-name).$(service-name).$(namespace).svc.cluster.local`

**Технические преимущества StatefulSet:**
*   **Стабильная метка индекса (GA v1.32):** Метка `apps.kubernetes.io/pod-index` позволяет направлять трафик или собирать метрики с конкретной реплики (например, только с мастера базы данных).
*   **Внутрикластерная связь:** Узлы распределенных систем (Kafka, MongoDB) могут хранить в конфигурации имена соседей, которые не изменятся при перезагрузке.

**DaemonSet** не полагается на Service: адрес пода фактически совпадает с адресом узла (`hostNetwork: true`) или публикуется через `hostPort`/`NodePort`. Клиент обращается к агенту напрямую по IP узла. При необходимости использовать Service применяется `InternalTrafficPolicy: Local`, чтобы трафик с узла попадал именно в локальную копию пода.

### Стратегии обновления и откат

#### 1. Deployment

*   Стратегии: **`RollingUpdate`** (по умолчанию) и **`Recreate`** (GA с первых версий; сначала удаляются все старые поды — полный даунтайм).
*   `maxSurge` (по умолчанию `25%`): временно создает «лишние» поды сверх `replicas`, что ускоряет обновление без потери мощности. **Требует свободных ресурсов в кластере**.
*   `maxUnavailable` (по умолчанию `25%`): допустимая потеря мощности. Может быть `0` — тогда старые поды не удаляются, пока новые не стали `Ready` (Zero-Downtime при наличии ресурсов).
*   **Уникально для Deployment:** `kubectl rollout pause/resume`, поддержка `progressDeadlineSeconds`, принцип «Rollover» — при втором обновлении во время первого контроллер немедленно сворачивает промежуточную ревизию и переходит к новейшей (горячие фиксы не ждут).
*   **Пропорциональное масштабирование:** если в момент rollout подключается HPA, новые реплики распределяются между активными ReplicaSet пропорционально их размеру, соблюдая ограничения `maxSurge`/`maxUnavailable`.
*   Откат выполняется как **новая ревизия** через `rollout undo` (история не «отматывается», номера ревизий только растут); старые шаблоны хранятся как ReplicaSet в пределах `revisionHistoryLimit` (по умолчанию 10).

#### 2. StatefulSet

*   Стратегии: **`RollingUpdate`** (по умолчанию), **`OnDelete`**, **`Recreate`** (Alpha v1.37, feature gate `StatefulSetRecreateStrategy`).
*   Обновление идет строго от старшего индекса к младшему (N-1 → 0), ожидая `Ready` каждой реплики (плюс `minReadySeconds`).
*   **`partition`:** позволяет «заморозить» часть подов на старой версии (Canary-деплой) — поды с индексом меньше `partition` остаются на старой ревизии и пересоздаются на ней же.
*   **`maxUnavailable` (Beta v1.35, гейт `MaxUnavailableStatefulSet`):** В отличие от Deployment, здесь **нет** `maxSurge` — лишние экземпляры создавать нельзя из-за привязки к дискам. `maxUnavailable` не может быть `0`, значение задается числом или процентом.
    *   **Оговорка о свежести (важно для эксплуатации):** в v1.35.0–v1.35.3 гейт был включен по умолчанию, но из-за регрессии [kubernetes/kubernetes#137409](https://github.com/kubernetes/kubernetes/issues/137409) (rollout-deadlock при `podManagementPolicy: Parallel`, когда недоступные поды на устаревшей ревизии «съедали» бюджет) гейт **отключен по умолчанию** в v1.35.4+ и v1.36. В v1.37 фикс (PR [#137666](https://github.com/kubernetes/kubernetes/pull/137666), [#139466](https://github.com/kubernetes/kubernetes/pull/139466)) и гейт снова включен по умолчанию. Всегда проверяйте фактическое состояние гейта в вашем кластере, не полагаясь только на версию API.
    *   `maxUnavailable > 1` нарушает строгую упорядоченность готовности реплик. Для кворумных систем (3 реплики) безопасное значение — `1` (выигрыша нет), эффект появляется только при большом числе реплик.
*   Отсутствует `rollout pause/resume`; откат — через `rollout undo` (история — ControllerRevision, `revisionHistoryLimit` по умолчанию 10).

#### 3. DaemonSet

*   Стратегии: **`RollingUpdate`** (по умолчанию) и **`OnDelete`** (рекомендуется для критичных CNI-плагинов — обновление вручную).
*   `maxUnavailable` (по умолчанию `1`): сколько узлов могут потерять агента одновременно.
*   `maxSurge` (GA v1.25): позволяет запускать новый под на узле *рядом* со старым — минимизирует «слепые пятна» в мониторинге на время обновления (на узле временно работают две копии).
*   Откат — через `rollout undo` (история — ControllerRevision); `rollout pause/resume` недоступен.

**Командная сводка по контроллерам:**

| Операция | Deployment | StatefulSet | DaemonSet |
| :--- | :--- | :--- | :--- |
| `kubectl rollout restart` | Да | Да | Да |
| `kubectl rollout undo [--to-revision]` | Да | Да | Да |
| `kubectl rollout history` | Да (по RS) | Да (по ControllerRevision) | Да (по ControllerRevision) |
| `kubectl rollout pause / resume` | Да | Нет | Нет |
| `kubectl scale --replicas=N` | Да (HPA-совместим) | Да (HPA-совместим) | Нет (нет поля `replicas`) |
| `kubectl autoscale` (HPA) | Да | Да | Нет |

### Поведение при сбоях узлов и плановом обслуживании (SRE)

| Событие | Deployment | StatefulSet | DaemonSet |
| :--- | :--- | :--- | :--- |
| **Узел стал `NotReady`** | Pod удаляется контроллером (по умолчанию ~5 минут) и пересоздается на другом узле | Pod тоже выселяется, но пересоздание **заблокировано**: RWO-том не отмонтирован от недоступного узла | Под исчезает вместе с узлом; пересоздается автоматически, когда узел вернется |
| **Узел не вернется** | Ручных действий не требуется | Требуется **Non-Graceful Node Shutdown**: taint `node.kubernetes.io/out-of-service=nodeshutdown:NoExecute` (v1.28+), который принудительно отмонтирует тома и позволит пересоздать под | Ничего делать не нужно — контроллер сам дождется замены узла |
| **Плановый `kubectl drain`** | Поды выселяются с уважением к PDB и пересоздаются на других узлах | То же самое, PDB критичен для кворума (см. [PodDisruptionBudget](../../Autoscaling/pod_disruption_budget.md)) | Поды **не выселяются**; для завершения drain нужен флаг `--ignore-daemonsets` |

**Ключевая разница в самоизлечении:** Deployment при отказе узла поднимает замену автоматически, потому что поды взаимозаменяемы и не требуют конкретного тома. StatefulSet сознательно **не делает этого**, чтобы исключить Split-brain (два пода, пишущих в один диск). DaemonSet не «переезжает» вовсе — на новых узлах он появляется автоматически по мере их добавления.

### Хранение и версионирование: ReplicaSet vs ControllerRevision

*   **Deployment** хранит историю как **ReplicaSet**: каждая ревизия — отдельный объект RS (возможно, нулевого размера). Это позволяет видеть «ход» rollout, накапливать старые шаблоны и выполнять откат. Минус — нагрузка на etcd при очень частых деплоях (настройте `revisionHistoryLimit: 3–5`).
*   **StatefulSet и DaemonSet** используют **ControllerRevision** — один компактный объект-снапшот шаблона на каждое изменение. Нагрузка ниже, но в `rollout history` отсутствует промежуточная детализация RS.

## Практические сценарии

### Выбор на основе режима доступа к хранилищу

#### Сценарий 1: Сетевая ФС (ReadWriteMany — RWX)
Приложение (например, CMS WordPress или файловое хранилище) требует одновременного доступа всех реплик к одной директории:
*   **Выбор:** **Deployment**.
*   **Причина:** Все поды подключаются к одному PVC. Имена подов не важны для доступа к данным.

#### Сценарий 2: Блочные диски (ReadWriteOnce — RWO)
Для СУБД, где каждому узлу нужен эксклюзивный диск с высокой производительностью:
*   **Выбор:** **StatefulSet**.
*   **Причина:** Исключает конфликт **Multi-Attach**. В Deployment при обновлении новый под не сможет смонтировать диск, пока старый не удалится полностью. В StatefulSet под `db-0` гарантированно получит диск `data-db-0` после завершения старого процесса.
*   **Исключение:** если реплика всего одна и без порядка (например, очередь, которую читает один воркер, или биллинг-сервис), допустим **Deployment + стратегия `Recreate`** — тогда при обновлении старый под удаляется полностью, и Multi-Attach не возникает. Это дешевле StatefulSet, но даунтайм-окно гарантировано.

#### Сценарий 3: Локальные ресурсы узла (hostPath / device)
Системный агент работает с локальными файлами узла (`/var/log/pods`, сокеты CSI, сетевые интерфейсы):
*   **Выбор:** **DaemonSet**.
*   **Причина:** один экземпляр на каждый подходящий узел, прямой доступ к хостовым ресурсам и автоматическое покрытие вновь добавленных узлов.

### Как использовать DaemonSet вместо Deployment

DaemonSet критичен для сервисов, которые должны работать «под» приложением:
*   **Сборщики логов и метрик:** Fluentd, Logstash, Node Exporter.
*   **Сетевые плагины и прокси:** Calico, Cilium, kube-proxy.
*   **Инфраструктурные задачи:** Очистка кэша узла, локальные прокси для секретов.
*   **Автомасштабирование:** DaemonSet реагирует на появление нового узла в кластере мгновенно, без участия HPA.

**Когда Deployment с anti-affinity предпочтительнее DaemonSet:** если нужно «по одному на узел», но количество копий фиксировано (например, 3, а не «на всех узлах»), используется Deployment с `podAntiAffinity` по `topologyKey: kubernetes.io/hostname`. Подробнее в [DaemonSet — Альтернатива](../daemonset.md).

### Алгоритм выбора контроллера (чек-лист)

Последовательно отвечайте на вопросы — первое подходящее правило определяет контроллер:

1.  **Одна копия на каждом узле / работа с локальным ресурсом узла?** → **DaemonSet**.
2.  **Нужна стабильная идентичность (имя, DNS, диск) каждому поду?** → **StatefulSet**.
3.  **Нужен эксклюзивный RWO-диск на под или строгий порядок старта/останова (кворум)?** → **StatefulSet**.
4.  **Нужно быстрое параллельное масштабирование + HPA и нет требований к имени/диску?** → **Deployment**.
5.  **Общий RWX-том и/или нужен `maxSurge` для zero-downtime?** → **Deployment**.
6.  **Гибридный случай?** Разбейте на части: stateless-слой (веб) — Deployment, stateful-слой (БД) — StatefulSet, сборщики телеметрии — DaemonSet. Контроллеры спокойно сосуществуют в одном Namespace.

### Миграция Deployment → StatefulSet (SRE-сценарий)

Типичная задача: перевести сервис с общего `emptyDir`/общего PV на per-подовые диски без потери данных.

```bash
# 1. Подготовка: Headless Service с теми же labels, что у подов Deployment
vi web-headless.yaml   # kind: Service, clusterIP: None, selector: app=web

# 2. Создать новый StatefulSet рядом со старым Deployment (тот же selector.app!)
kubectl apply -f web-statefulset.yaml   # имя StatefulSet — web-sts
kubectl rollout status statefulset/web-sts
```

```yaml
# web-statefulset.yaml (ключевой фрагмент)
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web-sts
spec:
  serviceName: "web-headless"
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: nginx:1.27
        volumeMounts:
        - name: data
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: data
    spec:
      accessModes: ["ReadWriteOnce"]
      resources:
        requests:
          storage: 1Gi
```

```bash
# 3. Перенос данных: временный Job/cron одним контейнером копирует данные
#    из старого общего тома в новые per-подовые тома (rsync по FQDN: data-web-sts-0, ...)

# 4. Переключение трафика: переключить Service selector с Deployment на StatefulSet.
#    Обычно оба контроллера используют одинаковые labels (app=web), поэтому достаточно
kubectl scale deployment web --replicas=0   # отключить старые поды после проверки

# 5. Зачистка после стабилизации (данные уже в новых PVC)
kubectl delete deployment web
kubectl delete pvc <имя-старого-общего-pvc>
```

**Важные нюансы миграции:**

*   Никогда не переименовывайте активный контроллер «in-place»: новые PVC создаются только через `volumeClaimTemplates`, которых нет у Deployment.
*   Для уже существующих данных используйте `data-sts-0`-стиль имён и динамический провижининг (`storageClassName`), либо предварительно создайте PV/PVC с совпадающими именами — иначе per-подовые диски будут пустыми.
*   Храните оба манифеста (Deployment и StatefulSet) в Git. Откат плана: вернуть Service selector на Deployment и `kubectl scale deployment web --replicas=3`, не удаляя StatefulSet.
*   HPA (если есть) перенаправьте с Deployment на новый StatefulSet; в манифесте не задавайте `replicas` вручную, иначе `kubectl apply` перезапишет масштабирование.
*   Для тяжелых БД применяйте поэтапный перенос через `spec.ordinals.start` (GA v1.31) — см. [Ключевые концепции](./statefulset_core_concepts.md).

### Быстрая проверка «какой контроллер управляет подом»

```bash
# Владелец пода: видно ReplicaSet у Deployment, нет владельца-ReplicaSet у STS/DS
kubectl get pod web-0 -o jsonpath='{.metadata.ownerReferences[0].name}{"\n"}'

# Deployment: история = старые ReplicaSet
kubectl get rs -l app=web

# StatefulSet / DaemonSet: история = ControllerRevision
kubectl get controllerrevisions -l app=web

# DaemonSet: число подов равно числу подходящих узлов (масштабирование по узлам)
kubectl get ds -A
```

## Совет по собеседованию

> **Вопрос:** В чем фундаментальная разница между `RollingUpdate` в Deployment и StatefulSet?
>
> **Ответ:** Главное отличие в гарантиях идентичности и работе с хранилищем. `Deployment` может использовать `maxSurge`, создавая новые поды *до* удаления старых, что ускоряет процесс. `StatefulSet` не поддерживает `maxSurge`, так как каждый под привязан к уникальному диску (PVC). Чтобы под `db-0` обновился, старый `db-0` должен полностью завершиться и отмонтировать диск, и только потом создастся новый под с тем же именем, который «подхватит» этот же диск.

> **Вопрос:** Как ускорить rollout StatefulSet и всегда ли это безопасно?
>
> **Ответ:** «Из коробки» — установить `maxUnavailable` больше `1` (Beta, feature gate `MaxUnavailableStatefulSet`, с v1.37 включен по умолчанию), либо переключить `podManagementPolicy: Parallel` для параллельных запуска/останова (без упорядоченности, подходит не для всех кворумных приложений). Быстрый rollout **безопасен не всегда**: `maxUnavailable > 1` нарушает последовательную готовность реплик, а для кворумных систем (3 реплики) безопасный максимум недоступных равен `ceil(N/2)-1 = 1`, т.е. ускорения нет вовсе. Альтернатива без ускорения, но с контролем риска — канареечная выкатка через `partition`. Подробнее в [Ключевых концепциях](./statefulset_core_concepts.md).

## Дополнительная информация

### Матрица принятия решений

| Требование приложения | Рекомендуемый контроллер |
| :--- | :--- |
| Максимальная скорость деплоя и scale-out | **Deployment** |
| Zero-Downtime при обновлении (нужен `maxSurge`) | **Deployment** |
| Уникальные сетевые имена и DNS для каждой реплики | **StatefulSet** |
| Пер-подовые персистентные диски (RWO) со стабильной привязкой | **StatefulSet** |
| Строгий порядок старта/останова, кворум реплик | **StatefulSet** |
| Saving данных на диске между перезапусками пода | **StatefulSet** |
| Фоновая обработка очередей (Stateless) | **Deployment** |
| Один агент на каждом узле (логи/метрики/CNI/CSI) | **DaemonSet** |
| Работа со специфическими локальными ресурсами узла | **DaemonSet** |
| Автоматическое покрытие вновь добавленных узлов | **DaemonSet** |

### Ограничения и риски

*   **StatefulSet:** Критически зависит от Headless Service. Ошибка в `serviceName` сделает невозможным формирование DNS-записей. При отказе узла **не пересоздает** под автоматически (защита от Split-brain) — нужно вмешательство SRE (taint `out-of-service`). Развертывание медленное на больших количествах реплик (последовательное ожидание).
*   **Deployment:** Не гарантирует порядок запуска и стабильные имена. Если сервис А зависит от сервиса Б, это нужно обрабатывать на уровне приложения (init-контейнеры), а не контроллера. При `maxSurge` требует свободных ресурсов и может упереться в `ResourceQuota`; при слишком агрессивном `maxUnavailable` возможна потеря мощности.
*   **DaemonSet:** Неправильные `resources.requests` в DaemonSet могут привести к тому, что на узлах не останется места для пользовательских приложений. Всегда ограничивайте DaemonSet через `nodeSelector` или `affinity`. Конфликты портов при `hostPort`; для Control Plane требуется явная `toleration`. HPA и `replicas` для него недоступны.

### Рекомендации по выбору контроллера

#### Когда StatefulSet обязателен, а когда достаточно Deployment с Recreate

| Ситуация | Рекомендуемый контроллер | Обоснование |
| :--- | :--- | :--- |
| **База данных (PostgreSQL, MySQL, MongoDB) с RWO дисками** | **StatefulSet** | Стабильная идентичность (db-0, db-1), порядок старта/останова, исключение Multi-Attach, Headless Service для DNS |
| **Однорепличная очередь (RabbitMQ, Kafka single broker) без кворума** | **Deployment + Recreate** | Даунтайм при обновлении, но нет сложности StatefulSet. `Recreate` гарантирует: старый под удаляется → диск освобождается → новый под монтирует тот же PVC |
| **Распределенная СУБД с кворумом (etcd, Consul, Cassandra)** | **StatefulSet** | Строгий порядок, стабильные DNS-имена для конфигурации кластера, защита от Split-brain при отказе узла |
| **Stateless микросервисы (API, веб-серверы, воркеры)** | **Deployment** | `maxSurge` для zero-downtime, параллельное масштабирование, HPA, rollout pause/resume |
| **Stateful сервис на RWX (NFS, CephFS, GlusterFS)** | **Deployment** | Все поды читают/пишут в одно общее хранилище, личности не нужны |

#### StatefulSet: защита от Split-brain при отказе узла
Это **фундаментальное архитектурное решение**. Когда узел с подом `db-0` становится `NotReady`:
1. **Deployment** — контроллер видит пропавший под, создает замену на другом узле **мгновенно** (после таймаутов).
2. **StatefulSet** — **блокирует** создание нового `db-0`, потому что RWO-диск (PVC) всё ещё смонтирован на недоступном узле. Два пода с одним диском = **Split-brain / data corruption**.

**SRE-действие при невернувшемся узле (v1.28+):**
```bash
# Принудительный taint для Non-Graceful Node Shutdown
kubectl taint node <node-name> node.kubernetes.io/out-of-service=nodeshutdown:NoExecute --overwrite
```
Это заставляет kubelet на Control Plane отмонтировать тома и разрешить пересозождение пода. Без этого кластер «ждёт» узел вечно.

#### Headless Service — требование для StatefulSet
```yaml
apiVersion: v1
kind: Service
metadata:
  name: db-headless
spec:
  clusterIP: None          # Headless!
  selector:
    app: postgres
  ports:
  - port: 5432
```
Без `clusterIP: None` не работают:
- Индивидуальные DNS записи (`db-0.db-headless.default.svc.cluster.local`)
- Стабильная сетевая идентичность при пересоздании пода
- Внутрикластерное обнаружение соседних реплик

#### StatefulSet Recreate стратегия (Alpha v1.37)
Feature gate `StatefulSetRecreateStrategy`:
- Аналог `Recreate` в Deployment: удаляет все поды → создает новые с 0 до N-1
- Для малых реплик (1-2) может быть быстрее RollingUpdate
- **Риск:** полный даунтайм приложения во время обновления
