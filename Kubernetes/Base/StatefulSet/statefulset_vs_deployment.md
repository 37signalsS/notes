# Сравнение Deployment, StatefulSet и DaemonSet

## Определения

*   **Deployment** — основной контроллер для приложений без состояния (stateless). Поды рассматриваются как эфемерные и полностью взаимозаменяемые ресурсы. Идеален для веб-серверов, API и микросервисов.
*   **StatefulSet** — контроллер для приложений с состоянием (stateful). Гарантирует уникальность, порядок и стабильную идентичность (имя, сеть, диск) для каждой реплики. Используется для баз данных и распределенных систем.
*   **DaemonSet** — контроллер, обеспечивающий запуск ровно одной копии пода на каждом узле кластера (или на выбранных узлах). Применяется для системных агентов, сборщиков логов и мониторинга.

Базовые принципы описаны в разделах **[Kubernetes Deployment](../Deployment/index.md)**, **[Ключевые концепции StatefulSet](./statefulset_core_concepts.md)** и **[DaemonSet](../daemonset.md)**.

## Основные концепции

### Сравнительная таблица характеристик

| Характеристика | Deployment | StatefulSet | DaemonSet |
| :--- | :--- | :--- | :--- |
| **Идентификация** | Случайные суффиксы (`web-abcd-123`) | Стабильные индексы (`db-0`, `db-1`) | Привязана к имени узла |
| **Сетевой доступ** | Общий виртуальный IP (Service) | Прямой (Headless Service) | HostPort или прямой IP узла |
| **Хранилище** | Общее или временное (emptyDir) | Индивидуальное (VolumeClaimTemplates) | Локальное (`hostPath`) |
| **Порядок запуска** | Параллельный (случайный) | Строго последовательный (Ordered) | Независимый на каждом узле |
| **Обновление** | Агрессивное (`maxSurge`) | Консервативное (по одному или группами) | Поузловое (`RollingUpdate`) |
| **Управление PVC** | Ручное удаление/управление | Автоматизация (`retentionPolicy`) | Обычно не используются PVC |
| **Масштабирование** | Мгновенное (параллельное) | Постепенное (0..N) | Автоматическое (по числу узлов) |

### Различия в сетевой идентичности и DNS

**Deployment** скрывает поды за абстракцией сервиса. Клиенту не важно, какой именно под обработает запрос. Если под упал, новый получит другой IP и имя, но Service перенаправит трафик прозрачно.

**StatefulSet** предоставляет каждому поду «личность». Благодаря Headless Service каждый экземпляр получает DNS-имя (например, `db-0.postgres.svc.cluster.local`). Это позволяет:
*   Явно обращаться к Primary-узлу для записи.
*   Настраивать кворум и репликацию (узлы знают адреса друг друга).
*   Использовать метку `apps.kubernetes.io/pod-index` для точечного мониторинга.

### Стратегии обновления и доступность

1.  **Deployment (`RollingUpdate`):**
    *   Использует `maxSurge` (сколько новых подов создать сверх нормы) и `maxUnavailable` (сколько старых можно убить).
    *   Приоритет — скорость и непрерывность трафика.
2.  **StatefulSet (`RollingUpdate`):**
    *   По умолчанию обновляет поды от старшего индекса к младшему (N-1 → 0).
    *   **Max Unavailable:** Позволяет обновлять несколько подов одновременно (для ускорения больших кластеров), если приложение поддерживает временную потерю нескольких узлов.
    *   **Partition:** Позволяет обновить только часть подов (Canary), оставив остальные на старой версии.
3.  **DaemonSet:**
    *   Обновляет поды на узлах по очереди. Можно ограничить количество одновременно обновляемых узлов через `maxUnavailable`.

## Практические сценарии

### Выбор на основе режима доступа к хранилищу (Access Modes)

Выбор контроллера часто зависит от того, как приложение работает с дисками.

#### Сценарий 1: Общее хранилище (ReadWriteMany — RWX)
Если приложению (например, WordPress или Shared Storage) нужно, чтобы все реплики читали и писали в одну общую папку по NFS:
*   **Выбор:** **Deployment**.
*   **Причина:** Все поды подключаются к одному и тому же PVC. Уникальность подов не требуется.

#### Сценарий 2: Блочное хранилище (ReadWriteOnce — RWO)
Для баз данных, где каждому узлу нужен свой собственный эксклюзивный диск (EBS, Azure Disk, local-path):
*   **Выбор:** **StatefulSet**.
*   **Причина:** Гарантирует, что под `db-0` всегда получит диск `data-db-0`, даже если переедет на другой узел. Исключает конфликт Multi-Attach (когда два пода пытаются захватить один RWO диск при обновлении).

### Когда использовать DaemonSet вместо Deployment

Хотя Deployment можно запустить на всех узлах через Anti-Affinity, **DaemonSet** предпочтительнее для:
*   **Infrastructure-агентов:** Fluentbit, Prom-node-exporter. Они должны запускаться раньше пользовательских подов.
*   **Storage-прокси:** Если приложению нужен доступ к локальным ресурсам конкретного узла.
*   **Особенности:** DaemonSet автоматически масштабируется при добавлении новых узлов в кластер без изменения манифеста.

## Дополнительная информация

### Матрица принятия решений

| Если приложению нужно... | Рекомендуемый контроллер |
| :--- | :--- |
| Максимальная скорость масштабирования | **Deployment** |
| Стабильное DNS-имя для каждого экземпляра | **StatefulSet** |
| Гарантированный запуск на каждом сервере | **DaemonSet** |
| Упорядоченное завершение транзакций перед выключением | **StatefulSet** |
| Запуск фоновых задач или обработчиков очередей | **Deployment** |

### Ограничения

*   **StatefulSet:** Требует обязательной настройки Headless Service. Неправильная настройка приведет к неработоспособности DNS-имен.
*   **Deployment:** Не подходит для приложений, хранящих локальные данные, которые должны сохраняться между перезапусками (кроме случаев использования RWX сетевых ФС).
*   **DaemonSet:** Может потреблять значительные ресурсы кластера, так как запускается на *каждом* узле. Используйте `nodeSelector` или `affinity` для ограничения области распространения.
