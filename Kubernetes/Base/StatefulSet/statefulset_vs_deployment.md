# Сравнение Deployment, StatefulSet и DaemonSet

## Определения

*   **Deployment** — основной контроллер для приложений без состояния (stateless). Поды рассматриваются как эфемерные, полностью взаимозаменяемые и не имеющие индивидуальной «личности». Оптимален для веб-серверов, API и микросервисов.
*   **StatefulSet** — специализированный контроллер для приложений с состоянием (stateful). Гарантирует уникальность, строгий порядок операций и стабильную идентичность (имя, сеть, диск) для каждой реплики. Необходим для баз данных и распределенных систем.
*   **DaemonSet** — контроллер, гарантирующий запуск ровно одной копии пода на каждом узле (или на выбранном подмножестве узлов). Предназначен для системных инфраструктурных сервисов.

Теоретические основы типов нагрузок см. в разделе **[Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md)**.

## Основные концепции

### Сравнительная таблица характеристик (v1.32+)

| Характеристика | Deployment | StatefulSet | DaemonSet |
| :--- | :--- | :--- | :--- |
| **Именование подов** | Случайные суффиксы (`web-abcd-123`) | Стабильные индексы (`db-0`, `db-1`) | Привязано к имени узла |
| **Сетевой доступ** | Через Service (ClusterIP/LB) | Прямой (Headless Service) | HostPort или IP узла |
| **DNS-идентификация** | Общая запись сервиса | Индивидуальная запись для каждого пода | Зависит от конфигурации сети |
| **Тип хранилища** | Общее (RWX) или эфемерное | Индивидуальное для каждой реплики (RWO) | Локальное (`hostPath`) |
| **Управление PVC** | Ручное создание/удаление | Автоматизация (`retentionPolicy`) | Обычно не используются PVC |
| **Порядок операций** | Параллельный и случайный | Строго последовательный (0..N-1) | Независимый на каждом узле |
| **Обновление** | Агрессивное (`maxSurge`) | Консервативное (по одному или группами) | Поузловое (`RollingUpdate`) |
| **Масштабирование** | Мгновенное (параллельное) | Постепенное (ожидание готовности) | Автоматическое (по числу узлов) |

### Глубокие различия в сетевой идентичности

**Deployment** использует абстракцию Service для балансировки трафика. Клиенту не важен конкретный экземпляр пода. Если под пересоздается, он получает новый IP и имя, но Service продолжает маршрутизацию прозрачно.

**StatefulSet** предоставляет каждому поду «личность». Благодаря Headless Service каждый экземпляр получает постоянный FQDN:
`$(pod-name).$(service-name).$(namespace).svc.cluster.local`

**Технические преимущества StatefulSet:**
*   **Стабильная метка индекса (GA v1.32):** Метка `apps.kubernetes.io/pod-index` позволяет направлять трафик или собирать метрики с конкретной реплики (например, только с мастера базы данных).
*   **Внутрикластерная связь:** Узлы распределенных систем (Kafka, MongoDB) могут хранить в конфигурации имена соседей, которые не изменятся при перезагрузке.

### Стратегии обновления и доступность

1.  **Deployment (`RollingUpdate`):**
    *   `maxSurge`: Позволяет временно создать больше подов, чем указано в репликах, для ускорения обновления.
    *   `maxUnavailable`: Определяет допустимый процент недоступных подов во время процесса.
2.  **StatefulSet (`RollingUpdate`):**
    *   Обновление идет строго от старшего индекса к младшему (N-1 → 0).
    *   **maxUnavailable (GA v1.31):** В отличие от Deployment, здесь **нет** `maxSurge`. Можно разрешить параллельное обновление нескольких подов, но нельзя создавать «лишние» экземпляры из-за привязки к дискам.
    *   **Partition:** Позволяет «заморозить» часть подов на старой версии (Canary-деплой).
3.  **DaemonSet:**
    *   Обновляет поды по очереди на каждом узле. Можно ограничить количество одновременно обновляемых узлов через `maxUnavailable`.

## Практические сценарии

### Выбор на основе режима доступа к хранилищу

#### Сценарий 1: Сетевая ФС (ReadWriteMany — RWX)
Приложение (например, CMS WordPress или файловое хранилище) требует одновременного доступа всех реплик к одной директории:
*   **Выбор:** **Deployment**.
*   **Причина:** Все поды подключаются к одному PVC. Имена подов не важны для доступа к данным.

#### Сценарий 2: Блочные диски (ReadWriteOnce — RWO)
Для СУБД, где каждому узлу нужен эксклюзивный диск с высокой производительностью:
*   **Выбор:** **StatefulSet**.
*   **Причина:** Исключает конфликт **Multi-Attach**. В Deployment при обновлении новый под не сможет смонтировать диск, пока старый не удалится полностью. В StatefulSet под `db-0` гарантированно получит диск `data-db-0` после завершения старого процесса.

### Когда использовать DaemonSet вместо Deployment

DaemonSet критичен для сервисов, которые должны работать «под» приложением:
*   **Сборщики логов и метрик:** Fluentd, Logstash, Node Exporter.
*   **Сетевые плагины и прокси:** Calico, Cilium, kube-proxy.
*   **Инфраструктурные задачи:** Очистка кэша узла, локальные прокси для секретов.
*   **Автомасштабирование:** DaemonSet реагирует на появление нового узла в кластере мгновенно, без участия HPA.

## Совет по собеседованию

> **Вопрос:** В чем фундаментальная разница между `RollingUpdate` в Deployment и StatefulSet?
>
> **Ответ:** Главное отличие в гарантиях идентичности и работе с хранилищем. `Deployment` может использовать `maxSurge`, создавая новые поды *до* удаления старых, что ускоряет процесс. `StatefulSet` не поддерживает `maxSurge`, так как каждый под привязан к уникальному диску (PVC). Чтобы под `db-0` обновился, старый `db-0` должен полностью завершиться и отмонтировать диск, и только потом создастся новый под с тем же именем, который «подхватит» этот же диск.

## Дополнительная информация

### Матрица принятия решений

| Требование приложения | Рекомендуемый контроллер |
| :--- | :--- |
| Максимальная скорость деплоя и scale-out | **Deployment** |
| Уникальные сетевые имена и DNS для каждой реплики | **StatefulSet** |
| Работа со специфическими локальными ресурсами узла | **DaemonSet** |
| Сохранение данных на диске между перезапусками пода | **StatefulSet** |
| Фоновая обработка очередей (Stateless) | **Deployment** |

### Ограничения и риски

*   **StatefulSet:** Критически зависит от Headless Service. Ошибка в `serviceName` сделает невозможным формирование DNS-записей.
*   **Deployment:** Не гарантирует порядок запуска. Если сервис А зависит от сервиса Б, это нужно обрабатывать на уровне приложения (init-контейнеры), а не контроллера.
*   **DaemonSet:** Неправильные `resources.requests` в DaemonSet могут привести к тому, что на узлах не останется места для пользовательских приложений. Всегда ограничивайте DaemonSet через `nodeSelector` или `affinity`.
