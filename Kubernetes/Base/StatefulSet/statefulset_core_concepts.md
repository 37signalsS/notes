# StatefulSet: Ключевые концепции

## Определения

**StatefulSet** — специализированный контроллер Kubernetes для управления приложениями с состоянием (stateful), которым требуются стабильные идентификаторы, сохранение данных между перезапусками и строгий порядок выполнения операций. В отличие от **[Deployment](../Deployment/index.md)**, где поды (Pods) являются взаимозаменяемыми и эфемерными, StatefulSet гарантирует уникальность и "личность" каждого экземпляра.

Базовые концепции stateful/stateless архитектур описаны в разделе **[Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md)**.

## Основные концепции

### Почему Deployment не подходит для stateful-приложений

Стандартный **[Deployment](../Deployment/index.md)** оптимизирован для масштабируемых веб-служб и API, но создает критические проблемы для баз данных и распределенных систем:
1.  **Потеря идентичности:** При каждом перезапуске под получает новое имя (случайный суффикс) и новый IP-адрес (Internet Protocol), что ломает внутренние механизмы репликации кластерных приложений.
2.  **Проблемы с хранилищем:** Несколько реплик Deployment, использующих один **PersistentVolumeClaim (PVC)** (запрос на выделение диска), могут одновременно писать в одни и те же файлы, что ведет к повреждению данных.
3.  **Блокировки томов:** Блочные хранилища с режимом доступа **ReadWriteOnce (RWO)** (чтение/запись одним узлом) не позволяют запустить новую версию пода, пока старая не удалена, что вызывает простой при обновлениях.

Подробное сравнение см. в **[StatefulSet vs Deployment](./statefulset_vs_deployment.md)**.

### Архитектурный стек для приложений с состоянием

Для полноценной работы StatefulSet использует комбинацию четырех компонентов:

| Компонент | Назначение |
| :--- | :--- |
| **StatefulSet** | Главный оркестратор: управляет жизненным циклом подов и привязкой к дискам. |
| **PersistentVolumeClaim (PVC)** | Индивидуальный запрос на диск; StatefulSet создает уникальный PVC для каждого индекса пода. |
| **PersistentVolume (PV)** | Физическое хранилище (облачный диск, NFS, локальный раздел), удовлетворяющее запрос PVC. |
| **Headless Service** | Сервис без ClusterIP (Internet Protocol), обеспечивающий прямой DNS-доступ к каждому поду. |

Подробнее: **[Headless Service](../../Networking/Service/service_type_headless.md)**, **[PV и PVC](../../Storage/pv_and_pvc.md)**.

### Стабильные сетевые идентификаторы

Каждый под получает предсказуемое имя: `<имя-StatefulSet>-<индекс>` (например, `db-0`, `db-1`).

**Ключевые особенности:**
*   **Сохранение имен:** Имя пода остается неизменным при переезде на другой узел кластера или после перезапуска.
*   **Domain Name System (DNS):** Через **Headless Service** каждый под получает персональную DNS-запись формата: `pod-name.service-name.namespace.svc.cluster.local`.
*   **Автоматические метки:** Kubernetes добавляет метку `statefulset.kubernetes.io/pod-name`, что позволяет направлять трафик на конкретный экземпляр (например, только на Primary-узел базы данных).

### Управление персистентным хранилищем

StatefulSet автоматически генерирует PVC для каждой реплики на основе шаблона `volumeClaimTemplates`.

**Принципы работы:**
*   **Уникальность:** Имя PVC формируется как `<имя-шаблона>-<имя-пода>` (например, `data-db-0`).
*   **Связанность:** Под всегда подключается к своему конкретному тому, независимо от того, на каком узле он запущен.
*   **Защита данных:** По умолчанию при удалении StatefulSet связанные с ним PVC **не удаляются**, чтобы предотвратить случайную потерю данных.

**Политики удаления (Kubernetes 1.27+):** Параметр `persistentVolumeClaimRetentionPolicy` позволяет настроить автоматическое удаление PVC при уменьшении масштаба (`whenScaled`) или при удалении всего контроллера (`whenDeleted`).

### Упорядоченное развертывание и масштабирование

StatefulSet обеспечивает предсказуемый жизненный цикл подов:
*   **Создание:** Поды запускаются строго последовательно от 0 до N-1. Следующий под (например, `web-1`) не начнет создаваться, пока предыдущий (`web-0`) не перейдет в состояние `Ready`.
*   **Удаление:** Поды завершаются в обратном порядке от N-1 до 0.
*   **Управление порядком:** Поле `podManagementPolicy` позволяет изменить это поведение на `Parallel` для ускорения запуска, если приложение не имеет жестких зависимостей между узлами.

### Стратегии обновлений и партиционирование

*   **RollingUpdate:** Поочередное обновление подов (от старшего индекса к младшему).
*   **Partition (Разделение):** Позволяет обновить только часть подов. Если задан `partition: 3`, то обновятся только поды с индексами 3 и выше. Это удобно для канареечных (Canary) развертываний баз данных.
*   **OnDelete:** Новая спецификация применяется к поду только после его ручного удаления.

## Практические сценарии

### Наблюдение за порядком запуска

```bash
# Применение манифеста
kubectl apply -f statefulset.yaml

# Наблюдение за созданием (запуск по одному)
kubectl get pods -w
# web-0   0/1   Pending
# web-0   1/1   Running
# web-1   0/1   Pending   # Начало создания только после готовности web-0
```

### Проверка сохранения данных при перезапуске

```bash
# Создание файла внутри пода
kubectl exec web-0 -- sh -c 'echo "cluster-data" > /usr/share/nginx/html/index.html'

# Удаление пода
kubectl delete pod web-0

# Проверка после автоматического пересоздания
kubectl exec web-0 -- cat /usr/share/nginx/html/index.html
# Результат: cluster-data (данные сохранились на PersistentVolume)
```

### Доступ к конкретной реплике

Для прямой работы с конкретным узлом кластера (например, для выполнения бэкапа на Slave-узле) используйте DNS-имя:

```bash
# Проверка доступности через DNS внутри кластера
kubectl exec -it client-pod -- nslookup web-0.web-headless.default.svc.cluster.local
```

### Диагностика проблем с дисками

Если под завис в состоянии `Pending` при обновлении в облаке, проверьте события:
```bash
kubectl describe pod <pod-name>
# Частое сообщение: "Multi-Attach error" — старый узел еще не отпустил диск.
# StatefulSet гарантирует, что диск не будет подключен к двум подам одновременно.
```

## Дополнительная информация

### Особое поведение при сбоях

*   **Недоступность узла:** Если узел переходит в статус `NotReady`, Kubernetes **не переносит** поды StatefulSet автоматически. Это защита от повреждения данных (Split-brain). Для переноса требуется ручное подтверждение удаления пода или использование специализированных операторов.
*   **Завершение работы:** StatefulSet корректно обрабатывает сигнал `SIGTERM`, давая приложению время закрыть транзакции и корректно выйти из состава кластера.

### Ограничения

*   Требуется **Headless Service** для корректной работы сетевой идентификации.
*   Масштабирование происходит медленнее, чем в Deployment, из-за последовательного запуска.
*   Использование **ReadWriteOnce (RWO)** томов ограничивает возможность запуска реплик в разных зонах доступности (Availability Zones) одного региона, если хранилище не распределенное.
