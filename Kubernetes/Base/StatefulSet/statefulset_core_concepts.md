# StatefulSet: Ключевые концепции

## Определения

**StatefulSet** — специализированный контроллер Kubernetes для управления приложениями с состоянием (stateful), которым требуются стабильные идентификаторы, сохранение данных между перезапусками и строгий порядок выполнения операций. В отличие от **[Deployment](../Deployment/index.md)**, где поды (Pods) являются взаимозаменяемыми и эфемерными, StatefulSet гарантирует уникальность и «личность» каждого экземпляра.

Данный контроллер является стандартом для развертывания распределенных систем, таких как базы данных (PostgreSQL, MongoDB), очереди сообщений (Kafka, RabbitMQ) и кластерные хранилища.

Базовые концепции архитектур описаны в разделе **[Stateful vs Stateless](../../../Concepts/stateful_vs_stateless.md)**.

## Основные концепции

### Почему Deployment не подходит для stateful-приложений

Стандартный **[Deployment](../Deployment/index.md)** оптимизирован для масштабируемых веб-служб и API, но создает критические проблемы для приложений с состоянием:

1.  **Потеря идентичности:** При каждом перезапуске под получает новое имя (случайный суффикс) и новый IP-адрес. Это ломает механизмы репликации, которые часто полагаются на статические имена узлов или конфигурационные файлы, привязанные к имени хоста.
2.  **Проблемы с хранилищем:** Несколько реплик Deployment используют общие шаблоны, что может привести к попытке одновременной записи нескольких подов в один и тот же объем (Volume), вызывая повреждение файловой системы.
3.  **Блокировки томов (Multi-Attach):** Блочные хранилища в режиме **ReadWriteOnce (RWO)** не позволяют запустить новую версию пода, пока старая не завершена и не отпустила диск. В Deployment это часто приводит к «зависанию» обновлений.

Подробное сравнение см. в **[StatefulSet vs Deployment](./statefulset_vs_deployment.md)**.

### Архитектурный стек для приложений с состоянием

Для полноценной работы StatefulSet использует комбинацию четырех компонентов:

| Компонент | Назначение |
| :--- | :--- |
| **StatefulSet** | Главный оркестратор: управляет жизненным циклом подов, порядком их запуска и привязкой к дискам. |
| **PersistentVolumeClaim (PVC)** | Индивидуальный запрос на диск; StatefulSet создает уникальный PVC для каждого индекса пода на основе шаблона. |
| **PersistentVolume (PV)** | Физическое хранилище (облачный диск, NFS, локальный раздел), удовлетворяющее запрос PVC. |
| **Headless Service** | Сервис без ClusterIP, обеспечивающий прямой DNS-доступ к каждому конкретному поду в наборе. |

Подробнее: **[Headless Service](../../Networking/Service/service_type_headless.md)**, **[PV и PVC](../../Storage/pv_and_pvc.md)**.

### Стабильные сетевые идентификаторы

Каждый под в StatefulSet получает предсказуемое имя и сетевой адрес.

**Ключевые особенности:**

*   **Формат имени:** `<имя-StatefulSet>-<индекс>` (например, `db-0`, `db-1`).
*   **Произвольный старт индексов (`.spec.ordinals.start`):** Начиная с версии 1.31 (GA), можно задать начальный номер индекса. Это критично для миграции между кластерами: например, поды 0-2 работают в старом кластере, а 3-5 запускаются в новом без конфликтов имен.
*   **Автоматические метки:** Каждый под получает метку `apps.kubernetes.io/pod-index` (GA в 1.31) и `statefulset.kubernetes.io/pod-name`. Это позволяет направлять трафик на конкретный экземпляр (например, только на Primary-узел) через обычный Service.
*   **DNS-имена:** Через Headless Service каждый под получает запись формата: `pod-name.service-name.namespace.svc.cluster.local`. Эта запись сохраняется даже при переносе пода на другой узел кластера.

### Управление персистентным хранилищем

StatefulSet автоматически генерирует PVC для каждой реплики на основе шаблона `volumeClaimTemplates`.

**Принципы работы:**

*   **Уникальность:** Имя PVC формируется как `<имя-шаблона>-<имя-пода>` (например, `data-db-0`).
*   **Связанность:** Под всегда подключается к своему конкретному тому. Если `db-0` упал и поднялся на другом узле, он получит тот же самый диск `data-db-0`.
*   **Политики удержания (GA в 1.32):** Поле `persistentVolumeClaimRetentionPolicy` позволяет автоматизировать очистку данных:
    *   `whenDeleted`: Удалять ли PVC при удалении всего StatefulSet.
    *   `whenScaled`: Удалять ли PVC при уменьшении количества реплик (Scale down).
    *   *По умолчанию (Retain):* PVC остаются в кластере для защиты от случайной потери данных.

### Упорядоченное развертывание и масштабирование

StatefulSet обеспечивает предсказуемый жизненный цикл подов через параметр `podManagementPolicy`:

1.  **OrderedReady (по умолчанию):**
    *   **Создание:** Поды запускаются последовательно от 0 до N-1. Следующий под не начнет создаваться, пока предыдущий не станет `Ready`.
    *   **Удаление:** Происходит в обратном порядке от N-1 до 0.
2.  **Parallel:** Поды запускаются и удаляются одновременно. Полезно для приложений, которые сами управляют своей кластеризацией и не требуют строгого порядка (например, некоторые NoSQL базы).

### Стратегии обновлений

*   **RollingUpdate:** Поочередное обновление подов (от старшего индекса к младшему).
    *   **`maxUnavailable` (GA в 1.31):** Позволяет обновлять несколько подов одновременно, что ускоряет процесс для больших кластеров.
*   **Partition (Разделение):** Обновляются только поды с индексом, равным или большим, чем указанный в `partition`. Позволяет реализовать Canary-деплой: обновить только один узел (`db-2`), протестировать его и затем обновить остальные.

## Практические сценарии

### Наблюдение за порядком запуска

```bash
# Применение манифеста
kubectl apply -f database.yaml

# Наблюдение за созданием (запуск по одному)
kubectl get pods -w
# db-0   0/1   Pending
# db-0   1/1   Running
# db-1   0/1   Pending   # Начало создания только после готовности db-0
```

### Проверка сохранения данных при перезапуске

```bash
# Создание файла внутри пода
kubectl exec db-0 -- sh -c 'echo "important-data" > /data/index.html'

# Удаление пода
kubectl delete pod db-0

# Проверка после автоматического пересоздания
kubectl exec db-0 -- cat /data/index.html
# Результат: important-data (данные сохранились на PersistentVolume)
```

### Доступ к конкретной реплике через метки

```bash
# Использование метки индекса для фильтрации логов
kubectl logs -l apps.kubernetes.io/pod-index=0

# Создание сервиса для обращения только к первому поду
# (например, для записи в Master базу)
apiVersion: v1
kind: Service
metadata:
  name: db-master
spec:
  selector:
    statefulset.kubernetes.io/pod-name: db-0
  ports:
    - port: 5432
```

## Дополнительная информация

### Особое поведение при сбоях

*   **Недоступность узла:** Если узел переходит в статус `NotReady`, Kubernetes по умолчанию не переносит поды StatefulSet. Это предотвращает ситуацию, когда два пода одновременно пишут на один диск (защита от Corruption).
*   **Non-Graceful Node Shutdown (v1.28+):** Если узел физически выключен и не вернется, администратор может использовать механизм `Node Out of Service` для безопасного принудительного переноса подов без риска повреждения данных.
*   **Завершение работы:** StatefulSet всегда отправляет `SIGTERM`. Приложение должно корректно обрабатывать этот сигнал, чтобы завершить транзакции и выйти из кворума.

### Ограничения

*   Требуется корректная настройка **Headless Service** для сетевой идентификации.
*   Масштабирование в режиме `OrderedReady` может быть медленным на больших кластерах.
*   Использование **ReadWriteOnce (RWO)** дисков привязывает под к конкретной зоне доступности (Availability Zone), если только не используется распределенное хранилище.
