# Deployment

**Deployment** — это один из самых важных объектов Kubernetes, который декларативно управляет жизненным циклом подов. Его основная задача — поддерживать заданное количество работающих экземпляров приложения (`replicas`) и обеспечивать их предсказуемое, контролируемое обновление.

Схема управления выглядит так: Deployment → [ReplicaSet](#replicaset-двигатель-для-deployment) → [Pod](./pod.md).

Когда вы создаете или обновляете `Deployment`, он создает новый `ReplicaSet`. Этот `ReplicaSet`, в свою очередь, запускает поды в соответствии с указанным шаблоном (`template`). Старый `ReplicaSet` сохраняется для возможности отката.

---

## ReplicaSet: Двигатель для Deployment

Хотя вы почти всегда будете работать с объектом `Deployment`, важно понимать его внутренний механизм. `Deployment` достигает своей цели — поддержания заданного числа подов — с помощью дочернего объекта, который называется **`ReplicaSet`**.

**ReplicaSet** — это объект Kubernetes, основная задача которого — гарантировать, что указанное количество идентичных подов (реплик) всегда будет запущено.

Когда вы создаете `Deployment`, он создает `ReplicaSet`. Когда вы обновляете `Deployment` (например, меняете версию образа), он создает **новый** `ReplicaSet` для новой версии и постепенно масштабирует старый `ReplicaSet` до нуля, а новый — до нужного количества реплик.

### Как работает ReplicaSet?

`ReplicaSet` постоянно отслеживает количество подов, соответствующих его селектору (`selector`):

-   Если подов меньше, чем `replicas`, он создает новые из шаблона (`template`).
-   Если подов больше, он удаляет лишние.
-   Если под, управляемый `ReplicaSet`, выходит из строя, контроллер автоматически создает замену.

Поскольку `Deployment` управляет этими `ReplicaSet`-ами, вы получаете все преимущества `ReplicaSet` (самовосстановление) плюс возможность декларативных обновлений и отката. По этой причине `ReplicaSet` редко используется напрямую.

## Анатомия манифеста Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-webapp
  labels:
    app: my-webapp
spec:
  # 1. Желаемое количество работающих подов
  replicas: 3

  # 2. Сколько старых ReplicaSet'ов хранить для истории и отката.
  # Предотвращает «захламление» кластера старыми версиями.
  revisionHistoryLimit: 5

  # 3. Таймаут для развертывания. Если за это время (в секундах)
  # новый ReplicaSet не станет доступным, его статус будет Progressing=False
  # с причиной ProgressDeadlineExceeded.
  progressDeadlineSeconds: 600

  # 4. Селектор для связи с подами, которыми управляет Deployment
  selector:
    matchLabels:
      app: my-webapp

  # 5. Стратегия обновления
  strategy:
    type: RollingUpdate
    rollingUpdate:
      # На сколько подов можно превысить `replicas` во время обновления.
      # Может быть числом (1) или процентом ("25%").
      maxSurge: 1

      # Сколько подов может быть недоступно во время обновления.
      # Может быть числом (1) или процентом ("25%").
      maxUnavailable: 1

  # 6. Шаблон для создания подов
  template:
    metadata:
      labels:
        app: my-webapp # Метки должны совпадать с селектором
    spec:
      containers:
      - name: web-server
        image: nginx:1.28.0 # Используйте конкретную версию, а не :latest
        ports:
        - containerPort: 80
        # Важно! Добавьте [readinessProbe](./probes.md) для реальных приложений
        readinessProbe:
          httpGet:
            path: /
            port: 80
          initialDelaySeconds: 5
          periodSeconds: 10
```

### Разбор спецификации (`spec`)

- **`apiVersion: apps/v1`**: Версия API Kubernetes, используемая для данного объекта. Сейчас стандартной для Deployment является `apps/v1`.

- **`kind: Deployment`**: Тип объекта Kubernetes, который мы создаём.

- **`name: my-webapp`**: Имя, которое будет использоваться для идентификации этого объекта Deployment.

- **`replicas`**: Указывает желаемое количество реплик (подов), которое Deployment должен постоянно поддерживать. В данном примере — 3 экземпляра.

- **`selector`**: Определяет, как Deployment находит поды, которыми он должен управлять. 
  **Важно:** Метки (labels) в `spec.selector.matchLabels` должны в точности совпадать с метками в `spec.template.metadata.labels`. Значение `app: my-webapp` говорит Deployment-у, что он управляет всеми подами с этой меткой.

- **`template`**: Это шаблон (blueprint), по которому будут создаваться поды. Он содержит свою `metadata` и `spec`.
  - **`metadata.labels`**: Метки, которые будут назначены каждому созданному поду. Они должны совпадать с `selector` самого Deployment.
  - **`spec.containers`**: Описывает один или несколько контейнеров, которые будут запущены внутри каждого пода. В данном случае это один контейнер `web-server` с образом `nginx:1.28.0`.

- **`strategy`**: Задаёт стратегию обновления для подов.
  - **`type: RollingUpdate`**: Указывает, что обновление будет происходить постепенно, под за подом. Это стратегия по умолчанию, обеспечивающая непрерывную работу приложения.
  - **`rollingUpdate`**: Настройки для стратегии `RollingUpdate`.
    - **`maxUnavailable: 1`**: Допустимое количество подов, которые могут быть недоступны во время обновления.
    - **`maxSurge: 1`**: Максимальное количество подов, которое может быть создано сверх желаемого числа реплик (`replicas`) во время обновления. Это позволяет Kubernetes сначала поднять новый под, а затем остановить старый.

  Альтернативная стратегия — **`Recreate`**, при которой Deployment сначала останавливает все старые поды и только потом запускает новые. Это приводит к простою приложения на время обновления.

## Как работает Rolling Update

**Rolling Update** — это стратегия обновления по умолчанию, которая позволяет обновлять приложение без простоя. Она постепенно заменяет поды старой версии на поды новой, контролируя количество одновременно доступных и создаваемых экземпляров с помощью `maxSurge` и `maxUnavailable`.

**Сценарий:** У нас есть `replicas: 3`, `maxSurge: 1`, `maxUnavailable: 1`. Мы обновляем образ с `nginx:1.28.0` на `nginx:1.28.0`.

1.  **Начало:** В кластере работают 3 пода со старой версией (v1).
2.  **Шаг 1 (Surge):** Deployment создает 1 новый под (v2), так как `maxSurge: 1` позволяет иметь `3 + 1 = 4` пода одновременно.
3.  **Ожидание:** Deployment ждет, пока новый под (v2) полностью запустится и пройдет проверку `readinessProbe`.
4.  **Шаг 2 (Unavailable):** Как только новый под готов, Deployment удаляет 1 старый под (v1). В этот момент у нас 2 пода v1 и 1 под v2. Общее количество доступных подов не падает ниже `3 - 1 = 2`, как определено в `maxUnavailable`.
5.  **Повторение:** Процесс повторяется (создается новый под v2, затем удаляется старый v1), пока все реплики не будут обновлены до новой версии.

**Результат:** Обновление прошло плавно, и сервис всегда был доступен.
    
    **Примечание:** Для максимально плавного `Rolling Update` рекомендуется иметь как минимум две реплики сервиса. Это гарантирует, что даже при `maxUnavailable: 1` всегда будет доступен хотя бы один под старой версии, пока новый под запускается.

### Альтернативная стратегия: `Recreate`

При этой стратегии Deployment сначала останавливает **все** старые поды и только потом запускает новые. В кластере никогда не сосуществуют две разные версии одновременно.

**Это приводит к простою (downtime)!**

Стратегия `Recreate` может использоваться, если:

- Приложение не поддерживает работу двух версий параллельно (например, схема базы данных несовместима между версиями).
- Потребление ресурсов не позволяет запускать новый под до остановки старого.

## Управление развертываниями через `kubectl`

*   **Просмотр статуса и мониторинг:**

    ```bash
    # Показывает, как проходит процесс обновления в реальном времени
    kubectl rollout status deployment/my-webapp
    
    # При проблемах — для просмотра событий и причин
    kubectl describe deployment/my-webapp
    ```

*   **Пауза и возобновление развертывания:**

    ```bash
    # Приостановить развертывание
    kubectl rollout pause deployment/my-webapp
    
    # После внесения всех изменений, возобновить
    kubectl rollout resume deployment/my-webapp
    ```

    Это полезно, чтобы применить несколько изменений в спецификации Deployment одним батчем, а не запускать обновление после каждого изменения.

*   **Просмотр истории ревизий:**

    ```bash
    kubectl rollout history deployment/my-webapp
    ```

*   **Откат изменений:**

    ```bash
    # Откат к предыдущей успешной версии
    kubectl rollout undo deployment/my-webapp

    # Откат к конкретной ревизии
    kubectl rollout undo deployment/my-webapp --to-revision=2
    ```

*   **Принудительный перезапуск (рестарт):**

    ```bash
    # Элегантный способ перезапустить все поды в деплойменте
    kubectl rollout restart deployment/my-webapp
    ```

    Эта команда инициирует стандартный `Rolling Update`, не изменяя сам манифест. Это идеальный способ заставить поды подхватить изменения из [ConfigMap](./configmap.md) или [Secret](./secret.md), которые примонтированы как тома. Команда также работает для [daemonset](./daemonset.md) и [statefulset](./statefulset.md).

*   **Быстрое обновление образа:**

    ```bash
    # Императивный способ обновить образ контейнера
    kubectl set image deployment/my-webapp web-server=nginx:1.26.0
    ```

### Практический пример: Обновление и откат

Этот простой пример иллюстрирует процесс обновления и отката на практике.

Представим, что у нас есть `Deployment`, использующий образ `app:v1`. Этот образ представляет собой простое приложение, которое выводит в лог сообщение "Version 1" каждую секунду.

**Задача:** Обновить приложение до версии `app:v2`, которая выводит "Version 2", а затем выполнить откат.

**Шаг 1: Обновление образа**

Императивная команда `kubectl set image` — это самый быстрый способ обновить образ в `Deployment`.

```bash
# kubectl set image deployment/<имя-деплоймента> <имя-контейнера>=<новый-образ>
kubectl set image deployment/my-webapp web-server=app:v2
```

Сразу после выполнения этой команды Kubernetes запускает процесс `Rolling Update`:

1.  Создается новый `ReplicaSet` для версии `v2`.
2.  Начинают подниматься поды с новым образом `app:v2`.
3.  Параллельно начинают останавливаться старые поды с образом `app:v1`.

Вы можете наблюдать за этим процессом:

```bash
# Посмотреть статус выкатки
kubectl rollout status deployment/my-webapp

# Посмотреть на создаваемые и удаляемые поды
kubectl get pods -l app=my-webapp -w
```
После завершения все поды будут работать на `app:v2` и выводить в лог "Version 2".

**Шаг 2: Проверка истории и откат**

Kubernetes хранит историю всех развертываний (ревизий).

```bash
# Посмотреть историю
kubectl rollout history deployment/my-webapp
# REVISION  CHANGE-CAUSE
# 1         <none>
# 2         <none>
```

Теперь выполним откат к предыдущей версии (ревизия 1).

```bash
kubectl rollout undo deployment/my-webapp
# deployment.apps/my-webapp rolled back
```

Kubernetes снова запустит `Rolling Update`, но на этот раз в обратную сторону: будут создаваться поды с `app:v1`, а поды с `app:v2` — удаляться. После завершения отката приложение вернется в исходное состояние.

Этот механизм делает обновления и откаты в Kubernetes предсказуемыми и безопасными.

## Лучшие практики

*   **Всегда используйте `readinessProbe`:** Без него Kubernetes не знает, готов ли ваш под принимать трафик. Rolling Update может направить трафик на еще не готовый под, что приведет к ошибкам у пользователей. ([Probes](./probes.md))
*   **Используйте иммутабельные теги для образов:** Никогда не используйте тег `:latest` в продакшене. Он непредсказуем. Всегда указывайте конкретную версию (например, `nginx:1.26.0`).
*   **Настройте `maxSurge` и `maxUnavailable`:**
    *   `maxUnavailable: 0` — более безопасный вариант, гарантирующий отсутствие потери мощности, но требующий больше ресурсов (`maxSurge` должен быть > 0).
    *   `maxSurge: 0` — экономит ресурсы, но может снизить производительность во время обновления.
*   **Настройте авто-масштабирование:** Для динамического управления количеством реплик в зависимости от нагрузки используйте [Horizontal Pod Autoscaler](./horizontal_pod_autoscaler.md).

### Правильно настраивайте imagePullPolicy

`imagePullPolicy` влияет на предсказуемость обновлений и нагрузку на registry.

**Если не делать:** С `Always` можно случайно перегрузить registry/получить rate limit, с `IfNotPresent` - не обновиться.

```yaml
spec:
  containers:
  - name: app
    image: myregistry/app:v1.0.0
    imagePullPolicy: IfNotPresent  # или Always
```
