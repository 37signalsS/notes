# Пробы в Kubernetes (Probes)

## Определения

**Пробы (Probes)** (в профессиональной среде часто называемые **зонды**) — это механизмы, которые агент `kubelet` использует для периодической проверки состояния контейнера. Они позволяют оркестратору понимать, работает ли приложение корректно, готово ли оно принимать сетевой трафик или успешно ли завершился процесс его запуска.

В Kubernetes существует три основных типа проб (зондов):

1. **`livenessProbe` (зонды жизнеспособности):** проверяет, работает ли контейнер. Если проба завершается неудачно, `kubelet` завершает работу контейнера, и он перезапускается согласно `restartPolicy`. Предназначена для исправления зависаний и дедлоков.
2. **`readinessProbe` (зонды готовности):** проверяет, готово ли приложение обслуживать запросы. Если проба проходит успешно, под добавляется в `Endpoints` и `EndpointSlice` соответствующих сервисов. Если проба не проходит `failureThreshold` раз, под исключается из балансировки. Контейнер **не перезапускается**. Используется для временной неготовности (прогрев кэша, загрузка данных).
3. **`startupProbe` (зонды запуска):** проверяет, успешно ли запустилось приложение. Пока эта проба не прошла, остальные проверки (`liveness` и `readiness`) отключены (откладываются). Защищает медленно стартующие приложения от преждевременного перезапуска по `livenessProbe`.

## Основные концепции

### Механизмы проверок

Kubernetes поддерживает четыре способа выполнения проверок здоровья:

1. **`httpGet`**: Выполняет HTTP GET-запрос к указанному порту и пути.
    * **Успех:** Код состояния от `200` до `399`.
    * **Поддержка:** Можно передавать `httpHeaders` (например, `User-Agent` или `Authorization`).
2. **`tcpSocket`**: Проверка открытия TCP-порта.
    * **Успех:** Порт принимает соединения.
3. **`exec`**: Выполняет команду внутри контейнера.
    * **Успех:** Код выхода `0`.
    * **Внимание:** Создает новый процесс (fork). Избегайте тяжелых команд в высокочастотных пробах.
4. **`grpc`**: (GA в v1.27) Выполняет gRPC-вызов к сервису проверки здоровья.
    * **Успех:** Статус ответа `SERVING`.
    * **Поле `service`**: Позволяет указать имя проверяемого gRPC-сервиса.

### Параметры конфигурации

* **`initialDelaySeconds`**: Пауза перед первой проверкой после старта контейнера.
* **`periodSeconds`**: Интервал между проверками (по умолчанию 10с).
* **`timeoutSeconds`**: Таймаут ожидания ответа (по умолчанию 1с).
* **`failureThreshold`**: Кол-во неудач до признания пробы проваленной (по умолчанию 3).
* **`successThreshold`**: Кол-во успехов для возврата в здоровое состояние (для `liveness` всегда 1).
* **`terminationGracePeriodSeconds`**: (v1.28+) Позволяет задать специфическое время изящного завершения только для случая, когда контейнер убивается по неудачной `livenessProbe`. Это время может отличаться от общего `terminationGracePeriodSeconds` пода.

## Практические сценарии

### Настройка для Java/Spring Boot приложения

Приложения на Java часто стартуют долго, поэтому использование `startupProbe` является обязательным.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: spring-app
spec:
  template:
    spec:
      containers:
      - name: java-app
        image: spring-boot-app:3.2
        ports:
        - name: http
          containerPort: 8080
        
        # Даем 120 секунд на старт (12 * 10)
        startupProbe:
          httpGet:
            path: /actuator/health/liveness
            port: http
          failureThreshold: 12
          periodSeconds: 10

        livenessProbe:
          httpGet:
            path: /actuator/health/liveness
            port: http
          periodSeconds: 20
          # Если проба упала, даем 60с на дамп памяти и очистку
          terminationGracePeriodSeconds: 60

        readinessProbe:
          httpGet:
            path: /actuator/health/readiness
            port: http
          periodSeconds: 10
```

### Проверка gRPC сервиса

Для современных микросервисов на gRPC не требуется поднимать отдельный HTTP-сервер для проверок.

```yaml
livenessProbe:
  grpc:
    port: 9000
    service: my-service-name
  initialDelaySeconds: 5
```

## Диагностика и устранение неисправностей

Некорректная настройка проб может привести к созданию «черных дыр» в трафике или цикличным перезапускам здоровых приложений.

### Симптомы сбоев

| Тип пробы | Симптом | Поведение системы |
| :--- | :--- | :--- |
| **Liveness** | Цикличные перезапуски (`Restarts > 0`) | Контейнер убивается и перезапускается `kubelet`. Приложение может не успевать записать логи ошибок. |
| **Readiness** | Под в статусе `Running`, но `READY 0/1` | IP пода удаляется из `Endpoints` сервиса. Трафик не поступает на под. Перезапуск не происходит. |

> **Совет для собеседования:**
> Должен ли под находиться в состоянии `Running`, чтобы попасть в список эндпоинтов сервиса?
> **Ответ:** Нет, одного `Running` недостаточно. Под должен находиться в состоянии **Ready**. Его IP-адрес добавляется в объект `Endpoints` только после успешного прохождения проверки готовности (`readinessProbe`), если она определена. Это важнейший механизм Kubernetes, предотвращающий отправку трафика на поды, которые еще инициализируются, прогревают кэш или временно перегружены.

### Алгоритм диагностики

Если под не проходит проверки работоспособности, следуйте шагам:

1.  **Проверка событий (Events):**
    ```bash
    kubectl describe pod <pod-name>
    ```
    Ищите в разделе `Events` сообщения вида:
    * `Liveness probe failed: HTTP probe failed with statuscode: 503`
    * `Readiness probe failed: Get "http://10.244.1.5:8080/health": connection refused`
    Это подтверждает, что проблема именно в зонде, а не в расписании или ресурсах.

2.  **Ручная проверка конечной точки:**
    Проверьте, отвечает ли приложение внутри самого контейнера (чтобы исключить проблемы сетевой политики или Service):
    ```bash
    kubectl exec <pod-name> -- curl -v http://localhost:8080/health
    ```
    *   **Ошибка:** Проблема в приложении (неправильный порт, путь, зависание).
    *   **Успех:** Проблема в конфигурации пробы (неверный порт/путь в манифесте) или сетевых ограничениях узла.

3.  **Анализ временных параметров (Timing):**
    Зонды чувствительны к времени отклика, особенно под нагрузкой:
    *   **`initialDelaySeconds`**: Должен быть больше времени холодного старта приложения. Если Readiness проба падает сразу после старта, увеличьте этот параметр.
    *   **`timeoutSeconds`**: Если приложение отвечает медленно из-за нагрузки, таймаут по умолчанию (1с) может быть недостаточен.
    *   **`failureThreshold`**: Увеличение порога помогает сгладить кратковременные сетевые всплески или задержки в приложении.

4.  **Диагностика через cAdvisor:**
    При отладке сложных аварий контейнера (Container Crash Diagnostics) используйте данные **cAdvisor** (встроен в Kubelet). Он предоставляет низкоуровневые метрики ресурсов в момент падения, что помогает отличить проблемы приложения от нехватки ресурсов узла или троттлинга.

## Дополнительная информация

### Взаимодействие с Native Sidecars (v1.29+)

Если контейнер помечен как sidecar (через `restartPolicy: Always` в блоке `initContainers`), его `startupProbe` влияет на запуск основных контейнеров. Основные контейнеры не начнут запуск, пока все нативные sidecar-контейнеры не пройдут свою пробу готовности (`startupProbe` или станут `ready`).

### Лучшие практики

1. **Разделение логики:** `readiness` может зависеть от внешних систем (БД, кэш), `liveness` — **никогда**. Если база упала, приложение должно стать `Not Ready`, но не уходить в бесконечный цикл перезапусков.
2. **Таймауты и нагрузка:** Убедитесь, что `timeoutSeconds` меньше `periodSeconds`. Не используйте `exec` для частого выполнения тяжелых скриптов.
3. **Интеграция с приложением:** Для полной реализации самовосстановления Kubernetes приложение должно предоставлять специализированные эндпоинты (например, `/healthz`, `/readyz`). Логика внутри приложения должна проверять критические зависимости (БД, брокеры сообщений) для корректного ответа на `readinessProbe`.
4. **Graceful Shutdown:** Перед завершением по сигналу SIGTERM приложение должно начать возвращать ошибку на `readinessProbe`, если не используется `preStop` хук с задержкой, чтобы исключить под из балансировки.
5. **Коды выхода:**
    * **137:** Контейнер убит по `livenessProbe` или OOM (проверьте `Reason` в `kubectl describe pod`).
    * **143:** Контейнер завершился по сигналу SIGTERM (изящное завершение).
