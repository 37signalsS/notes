# Определения

Пробы — это механизм, который `kubelet` использует для проверки состояния контейнера. Они помогают Kubernetes понять, работает ли приложение корректно, готово ли оно принимать трафик или успешно ли запустилось.

1. **`livenessProbe` (Проба жизнеспособности):** Проверяет, работает ли контейнер. Если проба завершается неудачно (например, приложение зависло и не отвечает), `kubelet` убивает контейнер, и он будет перезапущен в соответствии со своей `restartPolicy`. Это как "дружеское похлопывание по плечу" — Kubernetes спрашивает: "Ты в порядке?". Если нет, он перезапускает под, чтобы восстановить работоспособность.
    * **Цель:** Обнаружение и устранение ситуаций, когда приложение живо, но неработоспособно (например, deadlock).
    * **Реакция на сбой:** Перезапуск контейнера.

2. **`readinessProbe` (Проба готовности):** Проверяет, готов ли контейнер принимать трафик. Если проба не проходит, эндпоинт пода удаляется из объектов `Service`, и трафик на него больше не направляется. Как только проба снова становится успешной, эндпоинт возвращается. Это "зеленый свет" для трафика — контейнер полностью готов к выполнению своих задач.
    * **Цель:** Предотвращение направления трафика на еще не готовые или временно неработоспособные поды (например, во время запуска, прогрева кэша, или временной потери связи с базой данных).
    * **Реакция на сбой:** Под помечается как `Not Ready` и исключается из балансировки нагрузки `Service`. Контейнер при этом не перезапускается.

3. **`startupProbe` (Проба запуска):** Проверяет, запустилось ли приложение в контейнере. Все остальные пробы (liveness и readiness) отключаются до тех пор, пока `startupProbe` не завершится успешно. Это особенно полезно для медленно стартующих приложений (например, больших Java-приложений, .NET-приложений, которым требуется время на "прогрев", инициализацию конфигураций, подключение к базам данных и т.д.).
    * **Цель:** Предоставить приложению достаточно времени для полного запуска и инициализации, не допуская преждевременных перезапусков от `livenessProbe`.
    * **Реакция на сбой:** Если `startupProbe` не завершается успешно в течение заданного `failureThreshold`, контейнер перезапускается. После успешного завершения `startupProbe` начинают работать `livenessProbe` и `readinessProbe`.

## Основные концепции

### Механизмы проверок

1. **`httpGet`**: Выполняет HTTP GET-запрос к указанному порту и пути. Если ответ имеет код состояния в диапазоне от `200` до `399`, проверка считается успешной. Можно также настроить `host`, `scheme` (HTTP/HTTPS), `headers` и `port`.
2. **`tcpSocket`**: Пытается установить TCP-соединение с указанным портом. Если соединение успешно установлено (порт открыт), проверка считается успешной. Это простой "телефонный звонок", чтобы убедиться, что что-то слушает на порту.
3. **`exec`**: Выполняет указанную команду внутри контейнера. Если команда завершается с кодом выхода `0`, проверка считается успешной. Любой другой код выхода указывает на сбой. Это позволяет реализовать кастомные проверки, например, наличие файла или состояние внутреннего процесса. Команда выполняется внутри контейнера.
4. **`grpc`**: Выполняет gRPC-вызов к методу проверки здоровья (`grpc.health.v1.Health/Check`). Целевой контейнер должен реализовывать gRPC Health Checking Protocol. Проверка считается успешной, если ответ содержит статус `SERVING` или `NOT_SERVING`. Статус `SERVICE_UNKNOWN` или ошибка соединения считаются провалом.
    * **Стабильность:** Доступна в stable-версии начиная с Kubernetes 1.27.
    * **Ограничения:**
      * Порт нельзя указать по имени — только числовым значением.
      * Не поддерживает параметры аутентификации (TLS-сертификаты, mTLS).
      * Probe выполняется на IP пода (pod IP), поэтому gRPC-сервис должен слушать именно этот адрес.
      * `timeoutSeconds` игнорируется — gRPC-пробы не считаются проваленными по таймауту; все ошибки соединения считаются immediate failure.
    * **Именование сервисов:** Для разделения liveness и readiness через gRPC Kubernetes рекомендует использовать формат с дефисом: `grpc.health.v1.Health/Check` для liveness и отдельный endpoint для readiness.

> **Предупреждение — overhead `exec`-пробы:** В отличие от `httpGet`, `tcpSocket` и `grpc`, `exec`-проба реализована через создание и форк нескольких процессов каждый раз при выполнении. В кластерах с большим количеством подов и низким `periodSeconds` это может создать значительный CPU overhead на ноде. В таких сценариях рекомендуется рассмотреть `httpGet` или `tcpSocket` как альтернативу.

### Параметры конфигурации

* **`initialDelaySeconds`**: Количество секунд после запуска контейнера до начала выполнения первой пробы.
* **`periodSeconds`**: Как часто (в секундах) выполнять пробу.
* **`timeoutSeconds`**: Количество секунд, после которого проба считается неуспешной из-за таймаута.
* **`failureThreshold`**: Количество последовательных неудачных попыток, после которого проба считается проваленной.
  * **Значение по умолчанию:** 3.
  * **Обнуление счётчика:** Одна успешная проба обнуляет счётчик последовательных failures. Если было 2 неудачных попытки, затем 1 успешная — счётчик сбрасывается, и снова нужно 3 последовательных провала для срабатывания.
* **`successThreshold`**: Количество последовательных успешных попыток, необходимое для того, чтобы считать пробу успешной после того, как она была провалена.
  * **Значение по умолчанию:** 1 для liveness и startup; для readiness зависит от контекста.
  * **Важно:** Для liveness всегда равно 1 — достаточно одной успешной пробы для обнуления счётчика ошибок.

## Практические сценарии

### Пример конфигурации

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-probes-pod
  labels:
    app: my-app
spec:
  containers:
  - name: my-app-container
    image: my-app:1.0

    # Liveness Probe: проверка жизнеспособности
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 15 # Первая проверка через 15 секунд после старта
      periodSeconds: 20     # Проверять каждые 20 секунд
      timeoutSeconds: 1       # Таймаут для ответа
      failureThreshold: 3   # Считать сбоем после 3 неудачных попыток
      successThreshold: 1   # Считать успехом после 1 удачной попытки

    # Readiness Probe: проверка готовности
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 10
      failureThreshold: 3

    # Startup Probe: проверка запуска
    startupProbe:
      httpGet:
        path: /startup
        port: 8080
      # Даем приложению 5 минут на запуск (30 проверок * 10 секунд)
      failureThreshold: 30
      periodSeconds: 10
```

### Сценарий: Прогрев кэша при старте

**Проблема:** Приложение запущено, но ему нужно 1-2 минуты, чтобы загрузить в память большой кэш. Если в это время направить на него трафик, пользователи получат ошибки, так как данные еще не готовы.

**Решение:** Настроить `readinessProbe` так, чтобы она блокировала трафик до полной загрузки кэша.

Предположим, наше приложение после загрузки кэша создает файл `/tmp/cache_loaded`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: cache-app-pod
spec:
  containers:
  - name: cache-app
    image: my-cache-app:1.0
    # Liveness probe просто проверяет, что процесс приложения жив
    livenessProbe:
      httpGet:
        path: /healthz
        port: 8080
      initialDelaySeconds: 15
      periodSeconds: 20

    # Readiness probe проверяет, готов ли кэш
    readinessProbe:
      exec:
        # Проверяем наличие файла-флага, который создается после загрузки кэша
        command:
        - cat
        - /tmp/cache_loaded
      initialDelaySeconds: 10 # Начинаем проверять через 10 секунд
      periodSeconds: 5      # Проверяем каждые 5 секунд
      failureThreshold: 12    # Даем 60 секунд на прогрев (12 * 5)
```

**Как это работает:**

1. Контейнер `cache-app` стартует.
2. `readinessProbe` начинает выполняться через 10 секунд.
3. Она пытается выполнить команду `cat /tmp/cache_loaded`. Пока кэш грузится, этого файла нет, и команда завершается с ошибкой (код `1`).
4. Пока проба завершается с ошибкой, эндпоинт этого пода **не добавляется** в `Service`, и трафик на него не идет.
5. Как только приложение заканчивает загрузку кэша и создает файл `/tmp/cache_loaded`, команда `cat` выполняется успешно (код `0`).
6. `readinessProbe` становится успешной, и Kubernetes немедленно добавляет под в ротацию для приема трафика.

### Сценарий: Проверка внешних зависимостей

Этот сценарий демонстрирует, как использовать пробы для управления подами, которые зависят от внешних сервисов, например, базы данных или другого API.

**Проблема:** Приложение запущено (`liveness` в порядке), но не может подключиться к своей базе данных (например, из-за проблем с сетью или перегрузки БД). Если направить на него трафик, все запросы будут завершаться ошибкой. Приложение "живо", но не "готово" к работе.

**Решение:** Разделить проверки: `livenessProbe` проверяет только сам процесс, а `readinessProbe` проверяет связь с зависимостями.

Предположим, у нас есть приложение, которое для работы обращается к `etcd`.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: adder-pod
spec:
  containers:
  - name: adder
    image: my-adder-app:1.0

    # Liveness probe: очень простая проверка, что порт приложения открыт.
    # Если процесс умер и порт закрылся, Kubernetes перезапустит под.
    livenessProbe:
      tcpSocket:
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 20

    # Readiness probe: более сложная проверка.
    # Приложение должно предоставить эндпоинт /ready, который внутри себя
    # проверяет соединение с etcd.
    readinessProbe:
      httpGet:
        path: /ready # Этот эндпоинт возвращает 200 OK только если связь с etcd есть
        port: 8080
      initialDelaySeconds: 5
      periodSeconds: 15
```

**Как это работает:**

1. Контейнер `adder` стартует. `livenessProbe` быстро становится успешной, так как `tcpSocket` просто проверяет, что порт `8080` открыт. Kubernetes знает, что процесс жив.
2. `readinessProbe` начинает проверять эндпоинт `/ready`.
3. Если приложение не может подключиться к `etcd`, обработчик `/ready` возвращает код ошибки (например, `503 Service Unavailable`).
4. Пока `readinessProbe` не успешна, под находится в состоянии `Not Ready`, и трафик на него не направляется. Это защищает пользователей от ошибок.
5. Как только соединение с `etcd` восстанавливается, эндпоинт `/ready` начинает возвращать `200 OK`.
6. `readinessProbe` становится успешной, и Kubernetes добавляет под в балансировщик нагрузки.

Этот паттерн является ключевым для построения отказоустойчивых распределенных систем. Он позволяет изолировать сбои и предотвращать их каскадное распространение, так как неработоспособные (но живые) экземпляры сервисов временно выводятся из эксплуатации без лишних перезапусков.

## Дополнительная информация

### Лучшие практики использования проб

#### Выбирайте правильный механизм пробы

* **`httpGet`**: Идеально для веб-сервисов. Позволяет проверить не только доступность порта, но и работоспособность самого приложения (например, что оно отвечает кодом `200 OK` на `/healthz`).
  * **Рекомендация:** `httpGet` является предпочтительным механизмом для liveness и readiness проб. Он легковеснее `exec` и предоставляет больше информации о состоянии приложения, чем `tcpSocket`.
  * **HTTP Proxy:** Начиная с Kubernetes 1.13, локальные HTTP Proxy environment variables (`HTTP_PROXY`, `HTTPS_PROXY`) **не влияют** на HTTP liveness probe. Пробы выполняются напрямую, минуя прокси.
* **`tcpSocket`**: Более легковесный способ, чем `httpGet`. Он просто проверяет, открыт ли TCP-порт. Этого может быть достаточно для многих приложений, не являющихся HTTP-сервисами.
  * **Пример:** Для веб-сервера вроде Nginx использование `tcpSocket` для `livenessProbe` может быть предпочтительнее, чем `httpGet`. Частые `httpGet`-запросы могут "засорять" access-логи, в то время как `tcpSocket` проверяет доступность порта без создания HTTP-трафика.
* **`exec`**: Самый гибкий механизм. Используйте его, когда для проверки состояния требуется выполнить команду внутри контейнера (например, проверить наличие PID-файла, выполнить запрос к базе данных с помощью утилиты командной строки и т.д.).
  * **Предупреждение:** `exec`-проба создаёт overhead на форк процессов. В кластерах с большим количеством подов рекомендуется использовать `httpGet` или `tcpSocket`.

#### Разделяйте Liveness и Readiness Endpoint'ы

Старайтесь использовать разные пути (endpoint'ы) для `livenessProbe` и `readinessProbe`. Это позволяет более гибко настраивать логику проверок:

* `livenessProbe` может проверять только базовую работоспособность процесса.
* `readinessProbe` может включать более сложную логику, такую как проверка доступности внешних зависимостей (базы данных, других сервисов).

#### Обработчики должны быть независимыми функциями

Для каждого типа пробы (liveness, readiness) желательно реализовать отдельные, независимые функции-обработчики в приложении. Эти обработчики должны иметь более высокий приоритет, чем обычные клиентские запросы, чтобы Kubernetes мог получить быстрый и точный ответ о состоянии пода.

#### Не отделяйте логику проб от приложения

Логика проб должна быть тесно связана с внутренним состоянием приложения. `livenessProbe` должна возвращать `200 OK`, если основной поток приложения запущен и жив, и `500 Internal Server Error` (или другой код сбоя), если приложение действительно мертво или зависло. `readinessProbe` должна учитывать все внутренние и внешние зависимости, необходимые для обработки трафика (например, подключение к базе данных, прогрев кэша).

#### Liveness Probe: простота и надежность

`livenessProbe` должна быть максимально простой и надежной. Ее основная задача — определить, находится ли приложение в состоянии, когда оно не может восстановиться самостоятельно и требует перезапуска. Избегайте сложной логики, которая может привести к ложным срабатываниям и ненужным перезапускам.

> **Предупреждение — каскадные рестарты:** Неправильно настроенная `livenessProbe` может вызвать каскадные ошибки. Если проба слишком агрессивна (низкий `failureThreshold`, частый `periodSeconds`), контейнер будет постоянно перезапускаться. Под нагрузкой это приводит к:
>
> * Повышенной нагрузке на оставшиеся поды (трафик перенаправляется на них)
> * Снижению общей масштабируемости сервиса
> * Каскадным сбоям, когда перегруженные поды тоже начинают проваливать пробы
>
> **Exit Code 137:** При перезапуске контейнера из-за failed liveness probe exit code может быть `137` (128 + 9 = SIGKILL). Это **не обязательно** означает OOM Kill — kubelet принудительно завершает процесс контейнера при провале пробы. Для диагностики всегда используйте `kubectl describe pod` и смотрите секцию `Last State` и события пода.

#### Readiness Probe: полнота и точность

`readinessProbe` должна предоставлять максимально полные и точные ответы о готовности приложения к приему трафика. Она должна проверять доступность всех критически важных зависимостей (например, соединение с базой данных, внешними API, наличие необходимых ресурсов). Если приложение не готово, `readinessProbe` должна возвращать код сбоя, чтобы под был исключен из балансировки нагрузки.

#### Избегайте логики восстановления состояния в Readiness Probe

Не пытайтесь реализовать логику восстановления состояния внутри обработчика `readinessProbe`. Ее задача — *сообщать* о текущем состоянии готовности, а не *изменять* его. Наличие такой логики может привести к непредсказуемому поведению и проблемам в распределенной системе.

#### Реализуйте дренаж соединений

Современная лучшая практика — использовать `readinessProbe` как единственный механизм дренажа трафика, а `preStop` — только для инициирования процесса внутри приложения.

Принцип прост: когда приложение получает `SIGTERM`, оно должно само изменить своё состояние готовности (например, начать возвращать 503 на запросы к `/ready`), и K8s автоматически исключит его из [`Service`](../Networking/Service/service_overview.md).

**Если не делать:** Во время rollout пользователи увидят 5xx/timeout, даже если «всё обновилось успешно».

Вот как это выглядит на практике:

```yaml
# deployment.yaml
spec:
  terminationGracePeriodSeconds: 90 # Даем достаточно времени на дренаж
  template:
    spec:
      containers:
      - name: app
        # Ключевой элемент: readinessProbe с коротким интервалом
        readinessProbe:
          httpGet:
            path: /ready       # Эндпоинт, который начинает возвращать 503 при получении SIGTERM
            port: 8080
          initialDelaySeconds: 5
          periodSeconds: 2     # Частая проверка для быстрого исключения из балансировки
          failureThreshold: 1  # Достаточно одного провала
          successThreshold: 1
        # preStop используется ТОЛЬКО для триггера, а не для дренажа
        lifecycle:
          preStop:
            exec:
              command:
              - /bin/sh
              - -c
              - |
                # Просто отправляем SIGUSR1 или делаем легкий HTTP-вызов,
                # чтобы приложение УЗНАЛО о начале shutdown.
                # Это НЕ должен быть эндпоинт, который меняет readiness.
                curl -s -X POST http://localhost:8080/internal-prestop || true
                # Краткая пауза, чтобы сигнал дошел
                sleep 1
```

Этот подход тесно связан с [жизненным циклом пода](./Pod/pod_lifecycle_and_state.md) и корректным [завершением работы (Graceful Shutdown)](./Pod/pod_lifecycle_and_state.md#graceful-shutdown). Мониторинг перезапусков контейнеров и OOM Killed событий настраивается через [алертинг в Grafana](../../Grafana/alerting/concepts.md).
