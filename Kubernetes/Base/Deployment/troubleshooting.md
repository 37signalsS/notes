# Устранение неполадок Deployment и RollingUpdate

Руководство по диагностике и решению проблем, возникающих при развертывании и обновлении stateless-приложений в Kubernetes.

## 1. Определения

**Зависшее обновление (Stuck Rollout)** — состояние объекта Deployment, при котором процесс перехода на новую версию (RollingUpdate) останавливается и не завершается в течение времени, заданного в `progressDeadlineSeconds`.

**ProgressDeadlineExceeded** — условие (`Condition`) в статусе Deployment, указывающее на то, что контроллер не смог завершить обновление в отведенный срок.

**ReplicaFailure** — состояние, сигнализирующее о невозможности контроллера создать поды (например, из-за нехватки прав или нарушения квот).

## 2. Основные концепции

Зависшее обновление в Kubernetes — это **механизм защиты**, а не просто сбой. Контроллер Deployment намеренно приостанавливает процесс, если новые поды не проходят проверку готовности. Это предотвращает «выжигание» рабочей нагрузки: старые (здоровые) поды не удаляются, пока новые не подтвердят работоспособность.

### Параметры, влияющие на процесс обновления

| Параметр | Роль при сбое | Критическая ситуация |
| :--- | :--- | :--- |
| **`maxUnavailable`** | Определяет допустимую потерю мощности | При `0` контроллер не удалит ни одного старого пода, пока новый не станет `Ready`. Если ресурсы кластера на пределе, обновление застрянет. |
| **`maxSurge`** | Определяет временный всплеск ресурсов | Высокое значение ускоряет выкатку, но может вызвать срабатывание `ResourceQuota` или нехватку CPU/RAM на узлах. |
| **`minReadySeconds`** | Задержка признания пода «здоровым» | Позволяет выявить ошибки, возникающие не сразу после старта (например, утечки при инициализации). |
| **`progressDeadlineSeconds`** | Таймер ожидания успеха | По истечении этого времени (по умолчанию 600с) Kubernetes перестает пытаться продвинуть обновление и выставляет статус ошибки. |

## 3. Практические сценарии

### Алгоритм диагностики при зависании (Rollout Stuck)

Если команда `kubectl rollout status deployment <name>` не показывает прогресса, следуйте системному алгоритму:

#### Шаг 1: Инспекция объекта Deployment
Проверьте условия в статусе:
```bash
kubectl describe deployment <name>
```
Ищите в секции `Conditions`:
- **Type=Progressing, Status=False, Reason=ProgressDeadlineExceeded**: Обновление официально признано проваленным.
- **Type=Available, Status=False**: Приложение недоступно для пользователей.

#### Шаг 2: Анализ ReplicaSets
Deployment создает новый `ReplicaSet` (RS) для каждой ревизии. Проверьте количество реплик в новом RS:
```bash
kubectl get rs -l app=<your-app-label>
```
Если в новом RS `DESIRED > CURRENT` или `CURRENT > READY`, значит проблема на уровне создания или готовности подов.

#### Шаг 3: Глубокая диагностика подов
Изучите поды, принадлежащие новому (проблемному) ReplicaSet:
```bash
kubectl get pods --selector=app=<label>
kubectl describe pod <new-pod-name>
```

**Типичные ошибки и причины:**

| Статус / Ошибка | Причина | Действие |
| :--- | :--- | :--- |
| **`Pending`** | Недостаточно ресурсов, Taints, Affinity | Проверить `Events` в `describe pod`. Увеличить ресурсы узлов или уменьшить `requests`. |
| **`ImagePullBackOff`** | Ошибка авторизации, опечатка в имени, отсутствие тега | Проверить `imagePullSecrets`. См. **[Ошибки загрузки образов](../../Troubleshooting/Common_Errors/PodImagePullErrors/definitions.md)**. |
| **`CrashLoopBackOff`** | Ошибка приложения, мисконфигурация | Читать логи: `kubectl logs <pod> --previous`. См. **[Диагностика CrashLoopBackOff](../../Troubleshooting/Common_Errors/pod_crash_loop_back_off/diagnostics.md)**. |
| **`Running (Ready 0/1)`** | Не проходит `readinessProbe` | Проверить логи и эндпоинты приложения. Возможно, неверно указан порт или путь пробы. |
| **`OOMKilled`** | Превышение лимита памяти | Увеличить `limits.memory`. См. **[Анализ OOMKilled](../../Troubleshooting/Common_Errors/oomkilled_pods.md)**. |

### Специфические проблемы контроллера

#### Ошибка селектора (Selector Mismatch)
Если вы изменили метки в `template`, но не обновили `spec.selector` (или наоборот), контроллер может начать создавать поды бесконечно или не видеть существующие.
- **Важно:** Поле `spec.selector` является **неизменяемым** после создания Deployment. Для изменения селектора требуется пересоздание всего объекта (`kubectl delete` -> `kubectl apply`).

#### Превышение квот (ResourceQuota)
В мультиарендных средах `maxSurge` может временно поднять потребление ресурсов выше разрешенного лимита неймспейса.
```bash
kubectl describe quota -n <namespace>
```
**Решение:** Уменьшить `maxSurge` или запросить увеличение квоты.

### Реальный пример: Ошибка миграции БД

**Ситуация:** Обновление застряло на 1 новой реплике. Старые поды работают, но новые не становятся `Ready`.
**Диагностика:**
1. `kubectl rollout status` висит.
2. `kubectl get pods` показывает новый под в `Running`, но `Ready 0/1`.
3. `kubectl logs <pod>` выдает: `FATAL: database "users_db" does not have table "sessions"`.
**Причина:** Новая версия кода требует новую таблицу, но миграция БД в CI/CD не выполнилась или `Job` миграции упал.
**Решение:** Выполнить миграцию вручную или исправить пайплайн, затем сделать `kubectl rollout restart`.

## 4. Дополнительная информация

### Полезные команды для траблшутинга

```bash
# Просмотр истории с указанием причин (если заполнены)
kubectl rollout history deployment/<name>

# Отмена зависшего обновления и возврат к стабильной версии
kubectl rollout undo deployment/<name>

# Мониторинг процесса с таймаутом (полезно для скриптов)
kubectl rollout status deployment/<name> --timeout=5m

# Просмотр событий уровня кластера для конкретного объекта
kubectl get events --field-selector involvedObject.name=<deployment-name>
```
