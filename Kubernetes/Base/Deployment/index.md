# Deployment в Kubernetes

Декларативное управление жизненным циклом stateless-приложений и подов.

## 1. Определения

**Deployment** — высокоуровневый объект Kubernetes, предназначенный для декларативного описания желаемого состояния приложения. Он обеспечивает автоматическое развертывание, масштабирование и обновление групп идентичных подов (stateless).

**Схема управления:** `Deployment` → [`ReplicaSet`](../replicaset.md) → [`Pod`](../Pod/pod_overview.md)

Deployment не управляет подами напрямую. Он создает и обновляет `ReplicaSet`, который, в свою очередь, гарантирует запуск и работу заданного количества реплик. Это разделение ответственности позволяет реализовать механизмы плавного обновления (rolling updates) и легкого отката к предыдущим версиям.

### Владелец ресурса (Owner References)

Механизм `ownerReferences` в метаданных ресурсов обеспечивает каскадное управление:
- `Pod` содержит ссылку на `ReplicaSet`.
- `ReplicaSet` содержит ссылку на `Deployment`.

При удалении Deployment сборщик мусора (Garbage Collector) Kubernetes автоматически удаляет все связанные ReplicaSets и Pods, если не указано иное (`propagationPolicy`).

## 2. Базовые концепции

### Анатомия манифеста

Ключевые параметры спецификации (`spec`):

- **`replicas`**: Целевое количество экземпляров приложения. Минимум 2 рекомендуется для обеспечения высокой доступности.
- **`selector`**: Определяет, какими подами управляет данный Deployment. Поле `spec.selector.matchLabels` должно строго соответствовать `spec.template.metadata.labels`. Поле является **неизменяемым** (immutable).
- **`template`**: Описание пода, который будет создан. Любое изменение в этом блоке инициирует создание новой ревизии и запуск процесса обновления (rollout).
- **`minReadySeconds`**: Время (в секундах), которое под должен проработать без сбоев, прежде чем он будет считаться «готовым» (available). По умолчанию: 0.
- **`revisionHistoryLimit`**: Количество старых ReplicaSet, сохраняемых для возможности отката. По умолчанию: 10.
- **`progressDeadlineSeconds`**: Время ожидания прогресса развертывания. Если в течение этого срока новый ReplicaSet не продвигается в развертывании, статус Deployment устанавливается в `False` с причиной `ProgressDeadlineExceeded`.

### Стратегии обновления

| Стратегия | Описание | Параметры |
| :--- | :--- | :--- |
| **`RollingUpdate`** (по умолчанию) | Поэтапная замена старых подов на новые. Обеспечивает непрерывную доступность. | `maxSurge`, `maxUnavailable` |
| **`Recreate`** | Полная остановка всех старых подов перед запуском новых. | Нет |

> **Примечание:** Стратегия **Blue-Green** не является встроенным типом `spec.strategy.type`, но является распространенным архитектурным паттерном. Она реализуется путем создания двух независимых Deployment и переключения трафика на уровне Service (см. [детальное описание](../../../CI-CD/Deployment_Strategies/blue_green_deployment.md)).

#### Особенности стратегии Recreate

Стратегия `Recreate` является самой простой, но и самой рискованной с точки зрения доступности.
- **Процесс:** Когда готова новая версия, старая версия полностью останавливается и удаляется, после чего развертывается новая.
- **Недостатки (Downtime):** Основная проблема — гарантированный простой приложения. Во время развертывания приложение недоступно для пользователей.
- **Откат:** В случае неудачного обновления процедуру удаления и пересоздания необходимо повторить для старой версии, что приводит к дополнительному времени простоя.
- **Когда использовать:** Подходит для некритических сред (dev/test), где допустимы окна обслуживания, или для приложений, которые категорически не поддерживают одновременную работу двух версий (например, из-за блокировок в БД).

#### Настройка RollingUpdate

Для тонкой настройки процесса миграции используются параметры:
- **`maxSurge`**: Максимальное количество подов, которые могут быть созданы сверх `replicas`. Может быть числом (2) или процентом (25%). Позволяет ускорить обновление за счет временного потребления большего объема ресурсов.
    - *Пример:* При `replicas: 4` и `maxSurge: 1` Kubernetes может создать 1 дополнительный под (всего в пике будет 5) перед удалением старых.
- **`maxUnavailable`**: Максимальное количество подов, которые могут быть недоступны в процессе обновления. Установка в `0` гарантирует, что количество работающих подов никогда не упадет ниже `replicas`.
    - *Пример:* При `replicas: 4` и `maxUnavailable: 1` в любой момент времени минимум 3 пода будут доступны для обработки трафика.

### Условия состояния (Conditions)

Deployment сообщает о своем состоянии через `status.conditions`. Основные типы:
- **Available**: `True`, если минимальное количество реплик (согласно `maxUnavailable`) доступно и работает.
- **Progressing**: `True`, пока идет процесс обновления, или если новые поды успешно создаются. Переходит в `False` (с ошибкой), если нарушен `progressDeadlineSeconds`.
- **ReplicaFailure**: Указывает на проблемы при создании подов (например, превышение квот или ошибки прав доступа).

### Перекрывающиеся обновления (Rollover)

Если Deployment обновляется в момент, когда предыдущий процесс развертывания еще не завершен (например, быстрое исправление бага), контроллер не ждет завершения текущего цикла. Он немедленно масштабирует промежуточный (уже не актуальный) ReplicaSet вниз и начинает создание подов для самой последней версии.

## 3. Практические сценарии

### Быстрый старт и базовое управление

```bash
# Применение манифеста
kubectl apply -f deployment.yaml

# Обновление образа (запуск rollout)
kubectl set image deployment/my-app nginx=nginx:1.29.0

# Просмотр истории ревизий
kubectl rollout history deployment/my-app

# Откат к предыдущей версии
kubectl rollout undo deployment/my-app

# Принудительный перезапуск подов (без изменения манифеста)
kubectl rollout restart deployment/my-app
```

### Анализ состояния

Команда `kubectl get deploy` предоставляет краткую сводку:
- **READY**: Соотношение доступных подов к желаемому количеству (`readyReplicas` / `replicas`).
- **UP-TO-DATE**: Количество подов, соответствующих последней версии шаблона.
- **AVAILABLE**: Общее количество подов, готовых к приему трафика (прошли `readinessProbe` и `minReadySeconds`).
