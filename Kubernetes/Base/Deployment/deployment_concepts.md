# Kubernetes Deployment: Концепции

## 1. Определения

**Deployment** — объект Kubernetes для декларативного управления жизненным циклом подов. Основная задача — поддержание заданного количества работающих экземпляров приложения (`replicas`) и обеспечение предсказуемого, контролируемого обновления.

**Схема управления:** `Deployment` → [`ReplicaSet`](../replicaset.md) → [`Pod`](../Pod/pod_overview.md)

При создании или обновлении `Deployment` создает новый `ReplicaSet`, который запускает поды согласно шаблону (`template`). Старый `ReplicaSet` сохраняется для возможности отката.

## 2. Базовые концепции

### 2.1. Анатомия манифеста

**`replicas`** — желаемое количество реплик (подов), которое `Deployment` должен поддерживать.

**`selector`** — определяет, как `Deployment` находит управляемые поды.

> **Важно:** Метки в `spec.selector.matchLabels` должны точно совпадать с метками в `spec.template.metadata.labels`.

**`template`** — шаблон для создания подов. Содержит `metadata` и `spec` с описанием контейнеров.

**`strategy`** — стратегия обновления подов:

| Стратегия | Описание | Когда использовать |
| :--- | :--- | :--- |
| **`RollingUpdate`** (по умолчанию) | Постепенное обновление под за подом без простоя | Веб-сервисы, stateless-приложения |
| **`Recreate`** | Остановка всех старых подов → запуск новых | Несовместимые версии, миграции БД, монолиты |

Детальное описание стратегий — в [Rolling Update](../../../CI-CD/Deployment_Strategies/rolling_update.md) и [Deployment Strategies](../../../CI-CD/Core_Concepts/deployment_strategies.md).

**`revisionHistoryLimit`** — количество старых `ReplicaSet` для истории и отката. Предотвращает «захламление» кластера. **По умолчанию: 10**.

**`progressDeadlineSeconds`** — таймаут развертывания. Если новый `ReplicaSet` не станет доступным за это время (например, из-за `CrashLoopBackOff` или ошибок `readinessProbe`), `Deployment` перейдет в состояние `Progressing=False` с причиной `ProgressDeadlineExceeded`.

> **Совет:** Используйте YAML-anchors (`&` и `*`) для повторяющихся меток в манифесте, чтобы избежать дублирования.

### 2.2. Owner References

Каждый ресурс содержит поле `ownerReferences` в `metadata`, определяющее связь «родитель-потомок»:

- `Pod` → принадлежит `ReplicaSet`
- `ReplicaSet` → принадлежит `Deployment`

Это используется для каскадного удаления: при удалении `Deployment` автоматически удаляются связанные `ReplicaSet` и `Pod`.

## 3. Практические сценарии

### 3.1. Rolling Update (по умолчанию)

Стратегия по умолчанию для `Deployment`. Детальное описание параметров и процесса — в [Rolling Update](../../../CI-CD/Deployment_Strategies/rolling_update.md).

**Параметры управления:**

- **`maxUnavailable`** — допустимое количество недоступных подов во время обновления. **По умолчанию: 25%** — гарантируется, что минимум 75% подов остаются запущенными.
- **`maxSurge`** — максимальное количество подов сверх желаемого числа `replicas`. **По умолчанию: 25%** — может быть поднято до 125% подов от желаемого количества.

**Сценарий:** `replicas: 3`, `maxSurge: 1`, `maxUnavailable: 1`, обновление с `nginx:1.28.0` на `nginx:1.29.0`:

1. Создание 1 нового пода (v2) → 4 пода.
2. Ожидание `readinessProbe`.
3. Удаление 1 старого пода (v1) → 3 пода.
4. Повторение до полного обновления.

**Поведение terminating подов:** Kubernetes не считает поды в состоянии Terminating как доступные реплики при вычислении операций масштабирования во время деплоя. В результате временно может быть больше подов, чем ожидалось (terminating поды + новые поды), пока не завершится процесс termination. Для приложений с длительным grace period это может привести к временному превышению потребления ресурсов.

> **Примечание:** Для плавного обновления рекомендуется минимум 2 реплики — при `maxUnavailable: 1` всегда останется доступен хотя бы один под.

### 3.2. Recreate

Сначала останавливаются **все** старые поды, потом запускаются новые.

**Приводит к простою (downtime)!**

Используется когда:

- Приложение не поддерживает работу двух версий параллельно.
- Потребление ресурсов не позволяет запускать новый под до остановки старого.

### 3.3. Сравнение стратегий

| Стратегия | Плюсы | Минусы | Когда выбирают |
| :--- | :--- | :--- | :--- |
| **`RollingUpdate`** | Минимальный или нулевой простой. | Требует совместимости версий. | Веб-сервисы, stateless-приложения, где важна непрерывность. |
| **`Recreate`** | Полностью атомарное обновление. | Приводит к простою приложения. | Несовместимые версии, миграции схем БД, монолиты. |

Полное сравнение стратегий развертывания — в [Comparison of Deployment Strategies](../../../CI-CD/Deployment_Strategies/comparison.md).

### 3.4. Rollover — несколько обновлений подряд

Если обновление запускается **во время уже идущего обновления** (rollover), Deployment не ждёт завершения предыдущей операции. Поведение:

1. Deployment контроллер обнаруживает изменение в `spec.template` и создаёт новый `ReplicaSet`.
2. Предыдущий (незавершённый) `ReplicaSet` немедленно масштабируется вниз до нуля.
3. Поды от всех старых `ReplicaSet` начинают удаляться, новые поды создаются по **последнему** шаблону.

**Пример:** Deployment с 5 репликами `nginx:1.14`. В процессе обновления до `nginx:1.16` (уже поднято 3 из 5 реплик) выпускается ещё одно обновление — до `nginx:1.16`. Deployment немедленно останавливает создание подов `nginx:1.14` и начинает создавать поды `nginx:1.16`. Kubernetes не дожидается завершения предыдущего обновления — ориентируется только на актуальный `spec.template`.

Это поведение означает, что при частых изменениях шаблона в кластере может накопиться несколько «бесхозных» `ReplicaSet` с нулём реплик. Они удаляются автоматически при превышении `revisionHistoryLimit`.

### 3.5. Обновление Label Selector

Изменение `spec.selector` после создания Deployment — **не рекомендуемая операция**. Селекторы следует планировать заранее. Однако в некоторых версиях Kubernetes такие изменения допускаются с определёнными последствиями.

> **Важно:** В актуальных версиях Kubernetes `spec.selector` является **immutable** (неизменяемым) полем. Приведённое ниже относится к старым API-версиям (`apps/v1beta1`, `apps/v1beta2`).

| Тип изменения | Поведение | Последствия |
| :--- | :--- | :--- |
| **Добавление нового ключа** в селектор | Создаётся новый `ReplicaSet` | Старые `ReplicaSet` и поды **не выбираются** новым селектором — остаются «бесхозными». Требуется ручное удаление. |
| **Изменение значения** существующего ключа | Создаётся новый `ReplicaSet` | Аналогично добавлению — старые поды остаются без управления. |
| **Удаление ключа** из селектора | Новый `ReplicaSet` **НЕ создаётся** | Старые `ReplicaSet` остаются под наблюдением Deployment, но удалённый лейбл сохраняется на ранее созданных подах. |

При добавлении или изменении селектора необходимо также обновить лейблы в `spec.template.metadata.labels`, иначе манифест не пройдёт валидацию.

**Рекомендация:** Используйте расширяемые селекторы с самого начала — добавляйте дополнительные пары `ключ: значение` в лейблы, чтобы в будущем иметь возможность расширить селектор без коллизий.

## 4. Дополнительная информация

### 4.1. Вывод kubectl get deploy

Команда `kubectl get deploy` отображает ключевые поля состояния Deployment:

| Поле | Описание |
| :--- | :--- |
| **READY** | Количество подов, прошедших readinessProbe и готовых принимать трафик (например, `3/3`) |
| **UP-TO-DATE** | Количество реплик, обновлённых до последней версии, указанной в манифесте |
| **AVAILABLE** | Общее количество работающих подов (прошли проверки готовности) |
| **AGE** | Время жизни объекта Deployment |

**Пример вывода:**

```bash
kubectl get deploy nginx-deployment
# NAME               READY   UP-TO-DATE   AVAILABLE   AGE
# nginx-deployment   3/3     3            3           25s
```

- `READY: 3/3` — все 3 пода готовы к получению трафика.
- `UP-TO-DATE: 3` — все 3 реплики используют актуальную версию образа.
- `AVAILABLE: 3` — 3 пода работают и доступны пользователям.
