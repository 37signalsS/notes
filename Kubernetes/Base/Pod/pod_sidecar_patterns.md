# Паттерны Sidecar в Kubernetes

## Определения

**Sidecar Pattern (паттерн сайдкар)** — архитектурный паттерн многоконтейнерного Pod (пода), при котором вспомогательный container (контейнер) запускается рядом с основным приложением для расширения его функциональности (логирование, мониторинг, безопасность), не изменяя код самого приложения.

**Adapter Pattern (паттерн адаптер)** — специализированный вид сайдкара, который приводит вывод основного приложения (например, метрики или логи) к единому формату, понятному внешним системам мониторинга.

**Ambassador Pattern (паттерн амбассадор)** — вид сайдкара, который выступает в роли прокси-сервера для управления внешними сетевыми соединениями основного приложения (например, для реализации логики ретраев, балансировки или защиты соединений).

**Native Sidecar (нативный сайдкар)** — механизм Kubernetes версии 1.29+ (стабилен в 1.33+), позволяющий определять вспомогательные контейнеры как init-контейнеры с политикой перезапуска `Always`. Это гарантирует их запуск до основного приложения и работу на протяжении всего жизненного цикла Pod. Подробности описаны в [KEP (Kubernetes Enhancement Proposal) 3839](https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/3839-sidecar-containers.md).

## Базовые концепции

### Виды паттернов и их применение

| Паттерн | Назначение | Пример реализации |
| :--- | :--- | :--- |
| **Sidecar** | Дополняет и расширяет возможности приложения | Fluentd для сбора логов, Istio для управления трафиком |
| **Adapter** | Унифицирует интерфейс взаимодействия с внешним миром | Конвертер кастомных метрик в формат Prometheus |
| **Ambassador** | Упрощает сетевое взаимодействие для приложения | Проксирование запросов к БД (базе данных) или внешним API |

**Типовые задачи сайдкар-контейнеров:**

* **Наблюдаемость:** сбор и отправка логов (Fluentbit, Filebeat) и экспорт метрик (metrics exporter) без внедрения агентов в код приложения.
* **Сетевое взаимодействие:** реализация Service Mesh (сервисной сетки), mTLS (Mutual Transport Layer Security) и управления трафиком (Envoy в Istio, Linkerd proxy).
* **Конфигурация:** динамическая подгрузка настроек и ротация секретов из внешних источников (Vault Agent Injector — запись в shared volume).
* **Безопасность:** автоматическое управление TLS (Transport Layer Security) сертификатами и аутентификацией.

### Native Sidecar (Kubernetes 1.29+)

До появления нативных сайдкаров порядок запуска и завершения контейнеров в Pod не был гарантирован: обычный sidecar мог завершиться раньше основного приложения, нарушив работу (например, Envoy умирает до того, как приложение закончило отправку запросов). Новый механизм решает эту проблему, позволяя использовать `initContainers` для долгоживущих процессов.

**Ключевые особенности:**

* **Гарантированный порядок:** нативные сайдкары запускаются первыми. Основные контейнеры не стартуют, пока сайдкар не перейдет в состояние `Ready` (после успешного прохождения `startupProbe`).
* **Жизненный цикл:** в отличие от обычных init-контейнеров, нативные сайдкары не завершаются перед стартом приложения, а продолжают работать параллельно.
* **Завершение Pod:** основные контейнеры завершаются первыми, после чего останавливаются сайдкары (последними). Это гарантирует, что вспомогательный сервис (прокси, логирование) жив, пока приложение завершает работу.

## Практические сценарии

### Сценарий 1: Сайдкар для сбора логов

Классический пример использования Fluentd для чтения логов из общего тома и их отправки в хранилище:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-logging
spec:
  volumes:
  - name: log-storage
    emptyDir: {}
  containers:
  - name: main-app
    image: my-app:1.2.0
    volumeMounts:
    - name: log-storage
      mountPath: /var/log/app
  - name: log-shipper
    image: fluent/fluentd:v1.16
    volumeMounts:
    - name: log-storage
      mountPath: /var/log/app
      readOnly: true
```

### Сценарий 2: Native Sidecar с гарантированной готовностью

Использование прокси-сервера Envoy, который должен быть полностью готов до того, как приложение начнет отправлять запросы:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-envoy
spec:
  initContainers:
  - name: envoy-proxy
    image: envoyproxy/envoy:v1.28
    restartPolicy: Always  # Делает контейнер нативным сайдкаром
    startupProbe:
      httpGet:
        path: /ready
        port: 9901
      initialDelaySeconds: 5
      periodSeconds: 2
      failureThreshold: 10
  containers:
  - name: app
    image: my-app:1.2.0
```

### Сценарий 3: Ambassador для legacy-приложений

Проксирование трафика для приложения, которое умеет работать только с `localhost`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: legacy-app-proxy
spec:
  containers:
  - name: legacy-app
    image: old-service:1.0 # Слушает только 127.0.0.1:8080
  - name: ambassador-proxy
    image: nginx:alpine
    volumeMounts:
    - name: config
      mountPath: /etc/nginx/conf.d
  volumes:
  - name: config
    configMap:
      name: proxy-config
```

## Дополнительная информация

### Особенности эксплуатации

* **Ресурсы:** ресурсы (CPU, RAM), потребляемые сайдкарами, суммируются с ресурсами основного приложения при расчете общего лимита Pod. Всегда устанавливайте `requests` и `limits` для сайдкаров.
* **Обновление:** изменение образа нативного сайдкара в спецификации требует пересоздания Pod.
* **Общие ресурсы:** контейнеры в одном Pod разделяют сетевой namespace (могут слушать на localhost) и volumes (через volumeMounts). **PID-namespace** объединяется опционально через `shareProcessNamespace: true` (требуется для отправки сигналов между контейнерами). Подробнее в разделе [Общие ресурсы контейнеров в поде](./pod_overview.md#общие-ресурсы-контейнеров-в-поде).
