# Паттерны Sidecar в Kubernetes

## Определения

**Sidecar Pattern (Сайдкар)** — архитектурный паттерн многоконтейнерного Pod, при котором вспомогательный контейнер запускается рядом с основным приложением для расширения его функциональности (логирование, мониторинг, безопасность), не изменяя код самого приложения.

**Adapter Pattern (Адаптер)** — специализированный вид сайдкара, который унифицирует вывод основного приложения (например, преобразует кастомные логи или метрики в стандартный формат) для внешних систем мониторинга.

**Ambassador Pattern (Амбассадор)** — вид сайдкара, выступающий в роли прокси-сервера для управления **исходящими** сетевыми соединениями приложения (например, для реализации логики ретраев, балансировки или защиты соединений с БД).

**Native Sidecar (Нативный сайдкар)** — механизм Kubernetes (стабилен с v1.30), позволяющий определять вспомогательные контейнеры как `initContainers` с параметром `restartPolicy: Always`. Это гарантирует их запуск до основного приложения и работу на протяжении всего жизненного цикла Pod. Подробности описаны в KEP-3839.

## Базовые концепции

### Виды паттернов и их применение

| Паттерн | Назначение | Пример реализации |
| :--- | :--- | :--- |
| **Sidecar** | Расширение возможностей приложения | Fluentd для сбора логов, синхронизация конфигов git-sync. |
| **Adapter** | Унификация интерфейса взаимодействия | Конвертер кастомных метрик в формат Prometheus. |
| **Ambassador** | Упрощение сетевого взаимодействия | Проксирование запросов к БД или внешним API (Envoy). |

**Типовые задачи sidecar-контейнеров:**

*   **Наблюдаемость:** сбор и отправка логов (Fluentbit, Filebeat) и экспорт метрик (metrics exporter) без внедрения агентов в код приложения.
*   **Сетевое взаимодействие:** реализация Service Mesh, mTLS и управления трафиком (Envoy в Istio, Linkerd proxy).
*   **Конфигурация:** динамическая подгрузка настроек и ротация секретов из внешних источников (Vault Agent Injector — запись в shared Volume).
*   **Безопасность:** автоматическое управление TLS сертификатами и аутентификацией.

### Native Sidecar (Kubernetes 1.29+)

До появления нативных сайдкаров порядок запуска и завершения контейнеров в Pod не был гарантирован: обычный сайдкар мог завершиться раньше основного приложения, нарушив работу (например, Envoy умирает до того, как приложение закончило отправку запросов).

**Ключевые особенности:**

*   **Гарантированный порядок:** нативные сайдкары запускаются первыми. Основные контейнеры не стартуют, пока сайдкар не перейдет в состояние `Ready` (после успешного прохождения `startupProbe`).
*   **Жизненный цикл:** в отличие от обычных Init-контейнеров, нативные сайдкары не завершаются перед стартом приложения, а продолжают работать параллельно.
*   **Завершение Pod:** основные контейнеры завершаются первыми, после чего останавливаются сайдкары (последними). Это гарантирует, что вспомогательный сервис (прокси, логирование) жив, пока приложение завершает работу. Решает проблему «зависших» Job.

## Практические сценарии

### Сценарий 1: Sidecar для сбора логов (Классический)

Использование Fluentd для чтения логов из общего Volume и их отправки в хранилище:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-logging
spec:
  volumes:
  - name: log-storage
    emptyDir: {}
  containers:
  - name: main-app
    image: my-app:1.2.0
    volumeMounts:
    - name: log-storage
      mountPath: /var/log/app
  - name: log-shipper
    image: fluent/fluentd:v1.16
    volumeMounts:
    - name: log-storage
      mountPath: /var/log/app
      readOnly: true
```

### Сценарий 2: Native Sidecar с гарантированной готовностью

Использование прокси-сервера Envoy, который должен быть полностью готов до того, как приложение начнет отправлять запросы:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-envoy
spec:
  initContainers:
  - name: envoy-proxy
    image: envoyproxy/envoy:v1.30.0
    restartPolicy: Always  # Делает контейнер нативным сайдкаром
    startupProbe:
      httpGet:
        path: /ready
        port: 9901
      initialDelaySeconds: 5
      periodSeconds: 2
      failureThreshold: 10
  containers:
  - name: app
    image: my-app:1.2.0
```

### Сценарий 3: Ambassador для legacy-приложений

Проксирование трафика для приложения, которое умеет работать только с `localhost`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: legacy-app-proxy
spec:
  containers:
  - name: legacy-app
    image: old-service:1.0 # Слушает только 127.0.0.1:8080
  - name: ambassador-proxy
    image: nginx:alpine
    volumeMounts:
    - name: config
      mountPath: /etc/nginx/conf.d
  volumes:
  - name: config
    configMap:
      name: proxy-config
```

## Дополнительная информация

### Особенности эксплуатации

*   **Ресурсы:** ресурсы (CPU, RAM), потребляемые сайдкаром, суммируются с ресурсами основного приложения при расчете общего лимита Pod. Всегда устанавливайте `requests` и `limits` для sidecar-контейнеров.
*   **Обновление:** изменение образа нативного сайдкара в спецификации требует пересоздания Pod.
*   **Общие ресурсы:** контейнеры в одном Pod разделяют сетевой Namespace (могут слушать на localhost) и Volume (через volumeMounts). **PID-namespace** объединяется опционально через `shareProcessNamespace: true` (требуется для отправки сигналов между контейнерами). Подробнее в разделе [Общие ресурсы контейнеров в Pod](./pod_overview.md).
