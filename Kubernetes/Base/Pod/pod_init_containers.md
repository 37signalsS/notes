# Init Containers в Kubernetes

## Определения

**Init Container (инициализирующий контейнер)** — специализированный container, который запускается и успешно завершается до начала работы основных container внутри Pod (пода). Init-контейнеры выполняются последовательно в порядке их объявления в спецификации. Они используются для предварительной настройки среды, ожидания зависимостей или выполнения задач, результаты которых необходимы приложению.

**Native Sidecar (нативный сайдкар)** — механизм Kubernetes 1.29+ (стабилен в 1.33+), позволяющий определять sidecar-контейнеры как init-контейнеры с параметром `restartPolicy: Always`. Такие контейнеры работают на протяжении всего жизненного цикла Pod, обеспечивая вспомогательные функции (логирование, проксирование). Подробности описаны в [KEP-3839 (Kubernetes Enhancement Proposal)](https://github.com/kubernetes/enhancements/blob/master/keps/sig-node/3839-sidecar-containers.md).

## Базовые концепции

### Назначение и сценарии использования

Использование init-контейнеров позволяет отделить логику инициализации от основного кода приложения:

| Сценарий | Описание |
| :--- | :--- |
| **Ожидание зависимостей** | Блокировка старта приложения до доступности внешних сервисов: БД (баз данных), API (Application Programming Interface). |
| **Подготовка конфигурации** | Генерация конфигурационных файлов из шаблонов с подстановкой сетевых параметров Pod (IP, hostname). |
| **Управление правами** | Изменение владельца или прав доступа к файлам в общих томах для непривилегированного пользователя. |
| **Миграции баз данных** | Выполнение скриптов обновления схемы БД перед запуском приложения. |
| **Безопасность** | Init-контейнер может содержать утилиты (curl, git, sed), которые не требуются в финальном образе приложения, что снижает поверхность атаки. |

### Порядок выполнения и жизненный цикл

1.  **Сеть и хранилище:** Kubelet ожидает готовности сетевого интерфейса и монтирования всех томов.
2.  **Последовательный запуск:** Контейнеры из списка `spec.initContainers` запускаются один за другим.
3.  **Успешное завершение:** Каждый init-контейнер должен завершиться с кодом `0`. Только после этого запускается следующий.
4.  **Сбой и перезапуск:** Если init-контейнер завершается с ошибкой, Kubelet перезапускает его в соответствии с `restartPolicy` всего Pod.
5.  **Запуск приложения:** После успешного выполнения всех init-контейнеров основные container запускаются параллельно.

### Сравнение с обычными контейнерами

| Характеристика | Init Container | Основной container |
| :--- | :--- | :--- |
| **Порядок запуска** | Строго последовательный | Параллельный (после всех init) |
| **Время работы** | Кратковременный (до кода 0) | Долгоживущий (до остановки) |
| **Probes** | Не поддерживаются | liveness, readiness, startup |
| **Lifecycle hooks** | Не поддерживаются | postStart, preStop |
| **Порты и Service** | Не участвуют в Endpoints | Доступны через Service |
| **Статус Pod** | Под не готов (Ready: false) | Зависит от readiness probe |

### Расчет ресурсов (Requests и Limits)

При планировании Pod ресурсы рассчитываются по формуле, учитывающей последовательный характер работы init-контейнеров:

*   **Эффективный request** = `max(init-контейнеры)` + `sum(основные контейнеры)`
*   **Эффективный limit** = `max(init-контейнеры)` + `sum(основные контейнеры)`

Здесь `max(init-контейнеры)` — это максимальное значение среди всех init-контейнеров для конкретного ресурса (CPU — Central Processing Unit или память). Это гарантирует, что Pod будет выделено достаточно ресурсов для самого "тяжелого" этапа инициализации.

## Практические сценарии

### Сценарий 1: Ожидание доступности базы данных

Использование `busybox` для проверки сетевой доступности порта БД перед стартом приложения:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-with-wait
spec:
  containers:
  - name: my-app
    image: my-registry/app:v1.2.0
  initContainers:
  - name: wait-db
    image: busybox:1.36
    command: ['sh', '-c', 'until nc -z db-service 5432; do echo "Waiting for DB..."; sleep 2; done']
```

### Сценарий 2: Подготовка данных в общем томе

Init-контейнер скачивает статический контент, который затем раздает `nginx`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-static
spec:
  volumes:
  - name: html-dir
    emptyDir: {}
  containers:
  - name: nginx
    image: nginx:1.27
    volumeMounts:
    - name: html-dir
      mountPath: /usr/share/nginx/html
  initContainers:
  - name: fetch-content
    image: alpine:3.18
    command: ['sh', '-c', 'wget -O /data/index.html https://info.cern.ch/']
    volumeMounts:
    - name: html-dir
      mountPath: /data
```

### Сценарий 3: Последовательное ожидание нескольких сервисов

```yaml
initContainers:
- name: wait-service-a
  image: busybox
  command: ['sh', '-c', 'until nslookup service-a; do sleep 1; done']
- name: wait-service-b
  image: busybox
  command: ['sh', '-c', 'until nslookup service-b; do sleep 1; done']
```
Под перейдет в состояние `Running` только после того, как оба сервиса станут доступны через DNS (Domain Name System).

## Дополнительная информация

### Диагностика статусов в kubectl

При использовании `kubectl get pods` состояние инициализации отображается в колонке `STATUS`:

| Статус | Значение |
| :--- | :--- |
| **Init:0/2** | Ни один из 2 init-контейнеров еще не завершился. |
| **Init:1/2** | Первый успешно завершен, второй находится в процессе выполнения. |
| **PodInitializing** | Все init-контейнеры завершены, запускаются основные container. |
| **Init:Error** | Один из init-контейнеров завершился с ненулевым кодом выхода. |
| **Init:CrashLoopBackOff** | Init-контейнер постоянно падает и перезапускается. |

### Особенности поведения

*   **activeDeadlineSeconds:** Ограничивает общее время жизни Pod, включая этап выполнения всех init-контейнеров. Если время истечет, Pod будет принудительно завершен.
*   **Идемпотентность:** Init-контейнеры могут перезапускаться (например, при сбое Node). Их логика должна быть идемпотентной: повторное выполнение не должно приводить к ошибкам или повреждению данных в `shared volumes`.
*   **Изменение образа:** Изменение `image` у init-контейнера в уже запущенном Pod невозможно без пересоздания объекта.
