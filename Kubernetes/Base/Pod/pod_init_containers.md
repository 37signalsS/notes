# Init-container в Kubernetes

## Определения

**Init-container (Инициализирующий контейнер)** — специализированный контейнер, который запускается и должен успешно завершиться до начала работы основных контейнеров в Pod. Они предназначены для подготовки среды, ожидания зависимостей или выполнения задач, результаты которых необходимы приложению.

**Native Sidecar (Нативный сайдкар)** — механизм Kubernetes 1.29+ (стабилен в 1.33+), позволяющий определять sidecar-контейнеры как Init-контейнеры с параметром `restartPolicy: Always`. Такие контейнеры работают на протяжении всего жизненного цикла Pod, обеспечивая вспомогательные функции (логирование, проксирование). Подробности описаны в KEP-3839.

---

## Базовые концепции

### Назначение и сценарии использования

Init-контейнеры позволяют вынести вспомогательную логику из основного образа приложения, уменьшая его размер и поверхность атаки.

| Сценарий | Описание |
| :--- | :--- |
| **Ожидание зависимостей** | Блокировка старта приложения до доступности внешних сервисов (БД, API): `nc -z db 5432`. |
| **Подготовка данных** | Скачивание артефактов, клонирование Git-репозитория или генерация конфигов в общий `emptyDir` том. |
| **Управление правами** | Изменение владельца (`chown`) или прав доступа (`chmod`) на монтируемых томах для работы от имени не-root пользователя. |
| **Миграции баз данных** | Выполнение скриптов обновления схемы БД перед запуском приложения. |
| **Безопасность** | Утилиты (curl, git, sed) используются только на этапе инициализации и не включаются в финальный образ приложения, что снижает поверхность атаки. |

### Порядок выполнения и жизненный цикл

1.  **Последовательность:** Init-контейнеры выполняются строго по одному в порядке их объявления в массиве `spec.initContainers`.
2.  **Условие перехода:** Следующий контейнер запускается только после успешного завершения текущего (Exit Code 0).
3.  **Сбой и перезапуск:** Если Init-контейнер завершается с ошибкой, Kubelet перезапускает его согласно `restartPolicy` Пода.
4.  **Запуск приложения:** Основные контейнеры (`spec.containers`) запускаются параллельно только после успешного завершения всех обычных Init-контейнеров.

**Особенности жизненного цикла:**
*   **Идемпотентность:** Init-контейнеры могут перезапускаться (например, при сбое узла). Их логика должна быть идемпотентной: повторное выполнение не должно приводить к ошибкам или повреждению данных в общем томе.
*   **activeDeadlineSeconds:** Ограничивает общее время жизни Pod, включая этап выполнения всех Init-контейнеров. Если время истечет, Pod будет принудительно завершен.
*   **Изменение образа:** Изменение `image` у Init-контейнера в уже запущенном Pod невозможно без пересоздания объекта.

### Взаимодействие с Native Sidecars (v1.29+)

Если контейнер помечен как нативный сайдкар (`restartPolicy: Always` в блоке `initContainers`):
*   **Блокировка:** Он запускается в порядке очереди, но следующий контейнер начнет запуск только после того, как сайдкар перейдет в состояние `Ready`.
*   **StartupProbe:** Если настроена `startupProbe`, основные контейнеры не начнут запуск, пока все нативные сайдкар-контейнеры не пройдут эту проверку.
*   **Параллелизм:** Работает на протяжении всего жизненного цикла Pod параллельно с основными контейнерами.

### Сравнение с обычными контейнерами

| Характеристика | Init-container | Основной container |
| :--- | :--- | :--- |
| **Порядок запуска** | Строго последовательный | Параллельный (после всех init) |
| **Время работы** | Кратковременный (до кода 0) | Долгоживущий (до остановки) |
| **Probes** | Поддерживаются **только** для Native Sidecar | Поддерживаются всегда |
| **Lifecycle hooks** | Не поддерживаются | postStart, preStop |
| **Статус Pod** | Pod не готов (Ready: false) | Зависит от readiness probe |

### Расчет ресурсов (Requests и Limits)

При планировании Pod ресурсы рассчитываются с учетом последовательного характера работы:
*   **Эффективный request/limit** = `max(max(обычные init), sum(основные) + sum(нативные сайдкары))`

## Практические сценарии

### Сценарий 1: Ожидание базы данных и миграция

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-db-init
spec:
  initContainers:
  - name: wait-db
    image: busybox
    command: ['sh', '-c', 'until nc -z db-service 5432; do sleep 2; done']
  - name: db-migration
    image: my-app-migrations:latest
  containers:
  - name: main-app
    image: my-app:v1
```

### Сценарий 2: Подготовка данных в общем томе

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-static-fetch
spec:
  volumes:
  - name: html-dir
    emptyDir: {}
  initContainers:
  - name: fetch-content
    image: alpine:3.18
    command: ['sh', '-c', 'wget -O /data/index.html https://info.cern.ch/']
    volumeMounts:
    - name: html-dir
      mountPath: /data
  containers:
  - name: nginx
    image: nginx:1.27
    volumeMounts:
    - name: html-dir
      mountPath: /usr/share/nginx/html
```

### Сценарий 3: Диагностика статусов в kubectl

| Статус | Значение |
| :--- | :--- |
| **Init:0/2** | Ни один из 2 Init-контейнеров еще не завершился. |
| **Init:Error** | Контейнер завершился с кодом != 0. Логи: `kubectl logs <pod> -c <name>`. |
| **Init:CrashLoopBackOff** | Контейнер циклично падает (ошибки в команде, правах или зависимостях). |
| **PodInitializing** | Все Init-контейнеры завершены, запускаются основные контейнеры. |
