# Рекомендации по написанию манифестов Pod

Создание "хорошего" манифеста для пода — это не просто перечисление обязательных полей. Правильно определенный манифест повышает надежность, предсказуемость и управляемость приложения. Ниже собраны ключевые рекомендации, которым стоит следовать.

## 1. Структура манифеста

Любой манифест Kubernetes, включая Pod, состоит из четырех основных полей верхнего уровня:

- `apiVersion`: Версия Kubernetes API, которая используется для создания объекта. Для подов это, как правило, `v1`.
- `kind`: Тип создаваемого объекта. В данном случае — `Pod`.
- `metadata`: Метаданные, идентифицирующие объект. Включает `name`, `namespace`, `labels` и `annotations`.
- `spec`: Спецификация желаемого состояния объекта. Здесь описываются все его характеристики, включая контейнеры, тома, сетевые настройки и т.д.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-first-pod
  namespace: work
  labels:
    app: my-app
    version: "1.27.5"
spec:
  # ... Спецификация пода ...
```

## 2. Используйте декларативные манифесты, а не императивные команды

Хотя `kubectl` позволяет создавать поды императивно (`kubectl run`), **всегда используйте декларативные YAML-файлы**.

- **Воспроизводимость:** Манифесты можно хранить в системе контроля версий (Git), что позволяет отслеживать изменения и легко откатываться к предыдущим версиям.
- **Наглядность:** Сложную конфигурацию пода гораздо проще описать и прочитать в YAML-файле, чем в длинной командной строке.
- **Стабильность:** API Kubernetes меняется реже и более предсказуемо, чем флаги командной строки `kubectl`.

## 3. Явно указывайте тег образа (избегайте `:latest`)

**Никогда не используйте тег `:latest` для контейнеров в production.** Это одна из самых распространенных ошибок.

- **Проблема:** Тег `:latest` является "плавающим". Если образ в репозитории обновится, при следующем перезапуске пода Kubernetes может скачать новую версию, несовместимую с вашими конфигурациями (переменными окружения, командами и т.д.). Это приводит к непредсказуемым сбоям.
- **Решение:** Всегда указывайте конкретный, неизменяемый тег версии, например `nginx:1.27.5` или `my-app:v1.2.3-commit-af85a7`.

```yaml
# ПЛОХО
image: nginx

# ПЛОХО
image: nginx:latest

# ХОРОШО
image: nginx:1.27.5
```

## 4. Определяйте ресурсы: `requests` и `limits`

Всегда указывайте запросы (`requests`) и лимиты (`limits`) по CPU и памяти для каждого контейнера.

- `requests`: Гарантированное количество ресурсов, которое будет зарезервировано для контейнера. Это значение используется планировщиком Kubernetes для выбора подходящего узла.
- `limits`: Максимальное количество ресурсов, которое контейнер может потреблять.

**Почему это критически важно:**

1.  **Стабильность узла:** Без лимитов "прожорливый" или "утекший" по памяти контейнер может занять все ресурсы узла, вызвав сбои в работе других подов и самого `kubelet`.
2.  **Предсказуемое планирование:** `requests` позволяют планировщику эффективно распределять поды по кластеру.
3.  **Quality of Service (QoS):** На основе `requests` и `limits` Kubernetes присваивает подам классы QoS (`Guaranteed`, `Burstable`, `BestEffort`), которые влияют на то, какой под будет "убит" первым при нехватке ресурсов на узле.

```yaml
resources:
  requests:
    memory: "64Mi"
    cpu: "250m" # 250 millicores (0.25 ядра)
  limits:
    memory: "128Mi"
    cpu: "500m" # 0.5 ядра
```

- **При превышении `limits.memory`:** Контейнер будет немедленно завершен OOM-киллером (Out of Memory).
- **При превышении `limits.cpu`:** Потребление CPU контейнером будет принудительно ограничено (throttled).

> **Правило:** `limits` должны быть всегда указаны. `requests` также крайне желательны для производственной среды.

## 5. Настраивайте пробы (Probes)

Пробы — это жизненно важный механизм для автоматического контроля состояния вашего приложения.

- **[livenessProbe](../probes.md):** Проверяет, "живо" ли приложение. Если проба проваливается, Kubernetes перезапустит контейнер.
- **[readinessProbe](../probes.md):** Проверяет, готово ли приложение принимать трафик. Если нет, под будет временно исключен из `Service`.
- **[startupProbe](../probes.md):** Используется для медленно стартующих приложений, отключая другие пробы на время запуска.

Использование проб позволяет Kubernetes автоматически восстанавливать сбойные приложения и безопасно управлять трафиком во время выкатки.

## 6. Используйте осмысленные метки (Labels)

Метки (`labels`) — это основной способ организации и выборки объектов в Kubernetes.

- Используйте согласованную схему меток для всех ваших ресурсов.
- **Рекомендуемый минимум:**
  - `app` или `app.kubernetes.io/name`: Название приложения (например, `frontend`, `api-gateway`).
  - `version` или `app.kubernetes.io/version`: Версия приложения, работающего в поде (например, `v1.2.3`).

```yaml
metadata:
  labels:
    app: web-server
    version: "1.27.5"
```

## 7. Помните о неизменяемости (Immutability)

Многие поля в спецификации пода являются неизменяемыми после его создания. Например, нельзя изменить `image` контейнера в уже запущенном поде через `kubectl apply`.

- **Правильный подход:** Если вам нужно изменить неизменяемое поле (например, обновить версию приложения), вы не "патчите" существующий под. Вы **удаляете старый под и создаете новый** с обновленным манифестом.
- На практике этим управляют контроллеры (например, `Deployment`), которые автоматически реализуют стратегии обновления (например, `RollingUpdate`).

## 8. Определяйте `securityContext`

Хотя эта тема требует более глубокого изучения, хорошей практикой является определение `securityContext`, чтобы ограничить привилегии вашего контейнера, например, запретив запуск от имени `root`.

```yaml
spec:
  containers:
  - name: my-container
    image: ...
    securityContext:
      allowPrivilegeEscalation: false
      runAsNonRoot: true
      runAsUser: 1001
```
