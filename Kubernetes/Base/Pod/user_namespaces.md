# User Namespaces в Pod

## Определения

**User Namespace (пользовательское пространство имён)** — механизм ядра Linux, позволяющий сопоставлять идентификаторы пользователей (UID, User Identifier) и групп (GID, Group Identifier) внутри container (контейнера) с другими идентификаторами на хост-системе. Процесс, запущенный от имени `root` (UID 0) внутри container, фактически работает под полномочиями непривилегированного пользователя на Node (узле).

**Host User Namespace** — пространство имён пользователей хоста. По умолчанию Pod (поды) используют именно его, что означает совпадение идентификаторов внутри и снаружи container.

**ID Map Mount (монтирование с сопоставлением идентификаторов)** — механизм файловой системы Linux, позволяющий динамически изменять владельцев файлов при монтировании. Это критическая технология для работы User Namespaces в Kubernetes, позволяющая нескольким Pod использовать одни и те же образы с разными маппингами пользователей.

## Базовые концепции

### Назначение и преимущества

User Namespaces изолируют пользователя внутри container от пользователей на Node. Процесс может обладать полными правами (capabilities) внутри своего пространства имён, но при этом оставаться полностью непривилегированным для операций с ресурсами хоста.

**Ключевые цели внедрения:**

| Цель | Описание |
| :--- | :--- |
| **Изоляция при компрометации** | Даже если злоумышленник получит права `root` внутри Pod, он не сможет управлять ресурсами Node или другими Pod, так как на уровне ядра его UID будет соответствовать обычному пользователю. |
| **Защита от уязвимостей (CVE)** | Нейтрализация критических уязвимостей (Common Vulnerabilities and Exposures), позволявших через ошибки в рантаймах изменять файлы хоста или эскалировать привилегии. |
| **Безопасный запуск от root** | Позволяет приложениям, требующим прав `root` для внутренней работы (например, для установки пакетов или изменения системных параметров внутри container), работать без риска для всей инфраструктуры. |

### Механизм сопоставления (Mapping)

При активации User Namespaces Kubernetes автоматически выполняет следующие действия:

1. Выделяет уникальный диапазон UID/GID на Node для каждого Pod.
2. Сопоставляет внутренний диапазон container (обычно 0–65535) с выделенным диапазоном хоста.
3. Обеспечивает непересекаемость диапазонов для разных Pod на одной Node.

```text
Внутри container: UID 0 (root) -> На Node: UID 500000 (непривилегированный)
Внутри container: UID 1000     -> На Node: UID 501000
```

**Важно:** Параметры `runAsUser`, `runAsGroup` и `fsGroup` в спецификации Pod всегда относятся к идентификаторам **внутри container**.

### Требования и совместимость

Для использования User Namespaces инфраструктура должна соответствовать ряду требований.

#### Статус в Kubernetes

| Версия | Статус | Feature Gate | Примечание |
| :--- | :--- | :--- | :--- |
| **1.30** | Beta | `UserNamespacesSupport=true` | Поддержка томов и StatefulSet. |
| **1.33+** | **GA** | Включено по умолчанию | Полная стабилизация механизма. |

#### Системные требования

| Компонент | Требование | Примечание |
| :--- | :--- | :--- |
| **Ядро Linux** | 6.3 или выше | Необходима поддержка `idmap mounts`. |
| **Container Runtime** | `containerd` 2.0+ или `CRI-O` 1.25+ | Поддержка взаимодействия через CRI (Container Runtime Interface). |
| **Файловая система** | ext4, XFS, Btrfs, tmpfs | ФС должна поддерживать сопоставление идентификаторов. |

**Особенности tmpfs:** Поддержка в `tmpfs` (Temporary File System) критична, так как Kubernetes использует её для монтирования Secret, ConfigMap и токенов ServiceAccount.

### Активация и использование

Функция активируется в спецификации Pod через поле `hostUsers`:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-app
spec:
  hostUsers: false  # Активирует выделенное User Namespace для Pod
  containers:
  - name: web-server
    image: nginx:latest
    securityContext:
      runAsUser: 0  # root внутри -> непривилегированный снаружи
```

| Значение `hostUsers` | Результат |
| :--- | :--- |
| `false` | Pod изолирован в собственном пользовательском пространстве имён. |
| `true` (по умолчанию) | Pod использует пространство имён хоста (изоляция UID/GID отсутствует). |

## Практические сценарии

### Сценарий 1: Изолированный Pod с веб-сервером

Запуск приложения, которому требуются права `root` для прослушивания стандартных портов (например, 80), в безопасном режиме:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: isolated-web
spec:
  hostUsers: false  # Изоляция включена
  containers:
  - name: nginx
    image: nginx:1.25
    ports:
    - containerPort: 80
```

### Сценарий 2: Проверка готовности узла

Перед внедрением необходимо убедиться, что Node поддерживает необходимые технологии:

```bash
# Проверка версии ядра (требуется 6.3+)
uname -r

# Проверка поддержки idmap mounts для файловой системы kubelet
# Обычно kubelet использует /var/lib/kubelet
findmnt -n -o FSTYPE /var/lib/kubelet
# Результат должен быть ext4, xfs или btrfs с поддержкой idmap
```

### Сценарий 3: Диагностика Overflow UID

Если процесс пытается взаимодействовать с файлом, UID которого находится вне выделенного диапазона, ядро отображает его как **Overflow UID** (обычно 65534, `nobody`).

```bash
# Проверка значения overflowuid в системе
sysctl kernel.overflowuid

# Внутри container такие файлы будут видны как:
# -rw-r--r-- 1 nobody nobody ...
```

Модификация файлов, отображаемых как `nobody` из-за ограничений диапазона, обычно запрещена на уровне ядра для предотвращения утечек прав.
