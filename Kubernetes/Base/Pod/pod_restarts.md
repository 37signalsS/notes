# Перезапуск Pod в Kubernetes

## Определения

**Перезапуск container** — процесс, при котором container внутри Pod завершается и создаётся заново, при этом сам объект Pod в Kubernetes API остаётся неизменным. UID и IP адрес Pod не меняются, а счётчик перезапусков (`restart count`) в статусе увеличивается.

**Пересоздание Pod** — процесс удаления существующего объекта Pod и создания нового. Новый Pod получает новый UID и новый IP адрес. Счётчик перезапусков для нового объекта сбрасывается в ноль.

**[Rolling update](../../../CI-CD/Deployment_Strategies/rolling_update.md)** — стратегия обновления (например, в Deployment), при которой старые Pod постепенно заменяются новыми. Это всегда приводит к пересозданию Pod.

**In-place resize** — возможность изменения лимитов CPU и памяти работающего Pod без его пересоздания.

## Базовые концепции

### Перезапуск против пересоздания: тест на UID

Главный способ отличить перезапуск процесса в container от пересоздания самого Pod — проверка его UID.

* **UID изменился:** произошло пересоздание Pod (объект был удалён из etcd и создан заново).
* **UID не изменился:** объект Pod остался тем же, перезапустился только процесс или container внутри (например, из-за срабатывания liveness probe или аварийного завершения приложения).

### Поведение Kubelet

Компонент `kubelet` отслеживает изменения только в **спецификации Pod** (`spec`). Он напрямую не следит за внешними объектами, такими как ConfigMap, Secret или CRD. Если эти объекты обновлены, но `spec` Pod остался прежним, `kubelet` не инициирует перезапуск.

### Hot-reload против Rollout

* **Hot-reload:** приложение само отслеживает изменения файлов (ConfigMap или Secret, смонтированные как volume) и перечитывает их. Это обеспечивает высокую скорость, но может скрыть ошибки конфигурации, которые проявятся только при следующем полноценном старте.
* **Rollout:** более надёжный метод управления конфигурацией. Если новый конфиг содержит критическую ошибку, новый Pod не пройдёт readiness probe, и контроллер Deployment остановит обновление, сохранив работоспособность старой версии.

## Практические сценарии

### Что вызывает перезапуск или пересоздание?

| Сценарий | Результат | Комментарий |
| :--- | :--- | :--- |
| **ConfigMap/Secret через ENV** | Ничего | Переменные окружения задаются при системном вызове `execve` в момент старта. Для обновления нужен `rollout restart`. |
| **ConfigMap/Secret как Volume** | Hot-reload | `kubelet` обновляет символические ссылки на файлы. Приложение должно отслеживать события файловой системы. |
| **Смена образа (Image)** | Пересоздание | Инициируется контроллером (например, Deployment) через создание нового ReplicaSet. |
| **In-place Resize** | Resize без перезапуска | UID и IP сохраняются. Container перезапустится только если в `resizePolicy` явно указано `RestartContainer`. |
| **Istio VirtualService** | Ничего | Управляющий слой `istiod` передаёт конфигурацию напрямую в память Envoy proxy через xDS по протоколу gRPC. |
| **NetworkPolicy** | Ничего | Агент CNI обновляет правила фильтрации трафика (eBPF или iptables) на Node. |

## Дополнительная информация

### Команды для диагностики

**Проверка UID, IP адреса и счётчика перезапусков:**

```bash
kubectl get pod <pod-name> -n <namespace> -o custom-columns="NAME:.metadata.name,UID:.metadata.uid,IP:.status.podIP,RESTARTS:.status.containerStatuses[0].restartCount"
```

**Просмотр событий Pod (Events):**

```bash
kubectl describe pod <pod-name> -n <namespace> | grep -A 20 "Events:"
```

### Анализ инцидентов

При расследовании проблем важно различать уровни сбоя:

1. **Изменился UID:** Pod был пересоздан контроллером (возможные причины: вытеснение, сбой Node, обновление Deployment).
2. **Вырос restart count:** упал процесс внутри container (возможные причины: OOMKiller, ошибки в коде, неудачная проба livenessProbe).
