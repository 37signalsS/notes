# Перезапуск подов в Kubernetes

## Определения

**Перезапуск контейнера** — процесс, при котором контейнер внутри пода завершается и создается заново, но сам объект Pod в API Kubernetes остается неизменным. UID и IP пода не меняются, а счетчик перезапусков (`restart count`) в статусе контейнера увеличивается на 1.

**Пересоздание пода** — процесс удаления существующего объекта Pod и создания нового. Новый под получает новый UID и (обычно) новый IP-адрес. Счетчик перезапусков для нового пода сбрасывается в 0.

**Rolling update** — стратегия обновления (например, в Deployment), при которой старые поды постепенно заменяются новыми. Это всегда приводит к пересозданию подов.

**In-place resize** — возможность изменения ресурсов (CPU/Memory) работающего пода без его пересоздания (стабилизировано в Kubernetes 1.35).

## Базовые концепции

### Перезапуск vs Пересоздание: тест на UID

Главный способ отличить перезапуск контейнера от пересоздания самого пода — проверка его уникального идентификатора (UID).
*   **UID изменился:** это пересоздание пода (объект был удален и создан заново).
*   **UID не изменился:** объект пода тот же, перезапустился только процесс/контейнер внутри (например, из-за liveness probe или падения процесса).

### Поведение Kubelet

`kubelet` отслеживает изменения в **спецификации пода** (`spec`). Он напрямую не следит за внешними объектами, такими как ConfigMap, Secret или CRD (например, Istio). Если эти объекты обновлены, но `spec` пода остался прежним, `kubelet` не инициирует никаких действий. Это часто является причиной того, что изменения конфигурации не применяются к приложению.

### Hot-reload vs Rollout

*   **Hot-reload:** Приложение само отслеживает изменения файлов (ConfigMap/Secret как volume) и перечитывает их. Это удобно и быстро, но может скрыть ошибки (приложение может принять некорректный конфиг в память, что проявится только при следующем полноценном перезапуске).
*   **Rollout (пересоздание):** Более надежный метод. Если новый конфиг содержит критическую ошибку, под не пройдет проверку готовности (readiness probe), и старая версия останется работать (в случае Deployment).

## Практические сценарии

### Что вызывает перезапуск или пересоздание?

| Сценарий | Результат | Комментарий |
| :--- | :--- | :--- |
| **ConfigMap/Secret через ENV** | Ничего | Переменные окружения задаются при запуске процесса (`execve`). Для обновления нужен `rollout restart`. |
| **ConfigMap/Secret как Volume** | Hot-reload | `kubelet` обновляет симлинк. Приложение должно отслеживать событие `IN_CREATE` на директории `..data`. |
| **Смена образа (Image)** | Пересоздание | Через Rolling Update (новый ReplicaSet). Новый UID, новый IP. |
| **CPU/Memory Resize (1.35+)** | Резайз (без перезапуска) | UID и IP сохраняются. Контейнер перезапустится только если в `resizePolicy` указано `RestartContainer`. |
| **Istio VS / DestinationRule** | Ничего | `istiod` пушит конфиг через xDS gRPC в память Envoy. |
| **NetworkPolicy** | Ничего | CNI-агент обновляет правила фильтрации (eBPF/iptables) на ноде. |

## Дополнительная информация

### Команды для проверки

**Проверка UID, IP и счетчика перезапусков:**

```bash
kubectl get pod <pod-name> -n <namespace> -o custom-columns="NAME:.metadata.name,UID:.metadata.uid,IP:.status.podIP,RESTARTS:.status.containerStatuses[0].restartCount"
```

**Просмотр событий пода (Events):**

```bash
kubectl describe pod <pod-name> -n <namespace> | grep -A 20 "Events:"
```

### Резюме для инцидентов

При расследовании инцидентов фраза «под перезапустился» слишком общая. Всегда начинайте с анализа:
1.  Изменился ли UID?
2.  Вырос ли `restart count`?

Это сразу даст ответ: упал ли процесс внутри (перезапуск контейнера) или контроллер решил заменить весь под целиком (пересоздание).
