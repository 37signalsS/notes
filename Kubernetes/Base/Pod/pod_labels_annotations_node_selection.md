# Метки, аннотации и выбор узлов для Pod

## Определения

**Labels (метки)** — пары «ключ-значение», прикрепляемые к объектам Kubernetes (например, Pod). Предназначены для идентификации, группировки и выборки объектов. Подробное описание концепции и стандартов именования см. в [Метаданные, метки и аннотации](../../Concepts/metadata_and_labels.md).

**Annotations (аннотации)** — неидентифицирующие метаданные, используемые для хранения произвольной вспомогательной информации (например, версии сборки, контактов ответственных или параметров внешних инструментов).

**Node Selection (выбор узла)** — процесс управления размещением Pod (пода) в кластере через явное указание требований к Node (узлу), на котором он должен быть запущен.

**nodeSelector** — простейший механизм фильтрации узлов на основе меток. Pod будет запланирован только на ту Node, которая обладает всеми метками, указанными в селекторе.

**nodeName** — способ прямой привязки Pod к конкретной Node по её имени. Игнорирует механизмы планировщика (scheduler) и ограничения Taints (тейнов).

## Базовые концепции

### Механизмы управления размещением

Для определения того, на какой Node будет работать Pod, Kubernetes предоставляет несколько уровней гибкости:

| Механизм | Описание | Уровень сложности | Рекомендация |
| :--- | :--- | :--- | :--- |
| `nodeSelector` | Привязка по точному совпадению меток | Низкий | Для простых сценариев |
| [Node Affinity](../../Scheduling/affinity.md) | Расширенные правила с логическими операторами | Средний | Основной метод для сложных топологий |
| [Taints / Tolerations](../../Scheduling/taints_and_tolerations.md) | Запрет или разрешение размещения на узлах | Средний | Для изоляции ресурсов |
| `nodeName` | Прямая запись имени узла в спецификацию | Критический | **Не рекомендуется** для постоянных нагрузок |

### Особенности nodeSelector

Использование `nodeSelector` является наиболее быстрым способом ограничить круг узлов для приложения. Если планировщик не находит ни одного узла, удовлетворяющего всем условиям (логическое «И»), Pod переходит в фазу `Pending`.

**Рекомендации:**

- Не привязывайтесь к системной метке `kubernetes.io/hostname`, так как узлы могут пересоздаваться с новыми именами (например, в облаках).
- Используйте логические метки ролей или характеристик (например, `disktype: ssd`, `gpu: "true"`).

### Опасности использования nodeName

Поле `nodeName` в спецификации Pod (`spec.nodeName`) заставляет систему обойти процесс планирования.

**Последствия:**

1. **Отсутствие отказоустойчивости:** если указанный узел выйдет из строя, Pod не будет перезапущен на другом узле автоматически.
2. **Игнорирование ограничений:** Pod может быть запущен на узле, где недостаточно ресурсов (CPU, память) или установлены запрещающие Taints.
3. **Конфликты:** если узел не существует или недоступен, Pod останется в состоянии ожидания вечно.

## Практические сценарии

### Сценарий 1: Использование nodeSelector для специализированного оборудования

Ограничение запуска задач машинного обучения только на узлах с GPU (Graphics Processing Unit).

**Шаг 1: Маркировка узла**

```bash
kubectl label nodes worker-gpu-01 hardware-type=gpu
```

**Шаг 2: Настройка манифеста Pod**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ml-task
spec:
  nodeSelector:
    hardware-type: gpu
  containers:
  - name: training-app
    image: my-ml-app:latest
```

### Сценарий 2: Привязка DaemonSet к группе узлов

Запуск агентов мониторинга только на узлах, предназначенных для обработки внешнего трафика.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: traffic-monitor
spec:
  selector:
    matchLabels:
      name: monitor
  template:
    metadata:
      labels:
        name: monitor
    spec:
      nodeSelector:
        node-role.kubernetes.io/ingress: "true"
      containers:
      - name: agent
        image: monitor-agent:1.2.0
```

### Сценарий 3: Использование nodeName для отладки

Прямой запуск диагностического Pod на конкретной Node, которая сообщает об ошибках файловой системы.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: debug-node-x
spec:
  nodeName: worker-node-broken-disk  # Прямое указание проблемного узла
  containers:
  - name: debugger
    image: busybox
    command: ["sleep", "3600"]
```
