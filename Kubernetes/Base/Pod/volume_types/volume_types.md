# Тома в Kubernetes

## Определения

**Volume (том)** — абстракция хранилища данных, которая предоставляет Pod (подам) доступ к файловой системе вне жизненного цикла отдельных container (контейнеров). В отличие от Docker, где тома могут быть менее структурированы, в Kubernetes тома имеют четко определенный жизненный цикл, привязанный к Pod.

**CSI (Container Storage Interface)** — современный стандарт интерфейса между Kubernetes и внешними системами хранения. Большинство старых встроенных (in-tree) плагинов (например, `awsElasticBlockStore`, `gcePersistentDisk`) объявлены устаревшими (deprecated) в пользу соответствующих CSI-драйверов. Подробнее: [Обзор CSI](../../../Storage/CSI/csi_overview.md).

**Эфемерное хранилище (Ephemeral Storage)** — тома, жизненный цикл которых совпадает с жизненным циклом Pod. При удалении Pod данные уничтожаются. Основные типы: `emptyDir`, `hostPath`, `configMap`, `secret`.

**Персистентное хранилище (Persistent Storage)** — тома, данные в которых сохраняются независимо от состояния Pod. Реализуется через механизмы `PersistentVolume` (PV) и `PersistentVolumeClaim` (PVC).

## Базовые концепции

### Назначение томов

| Проблема | Решение через Volume |
| :--- | :--- |
| **Эфемерность ФС** | Сохранение состояния при аварийном перезапуске контейнера внутри того же Pod. |
| **Совместное использование** | Доступ к одним и тем же файлам для нескольких контейнеров внутри одного Pod. |
| **Изоляция технологий** | Единый интерфейс доступа независимо от типа СХД (NFS, облачные диски, локальные диски). |
| **Инъекция данных** | Динамическая подстановка конфигураций (`ConfigMap`) и секретов (`Secret`) в ФС контейнера. |

### Механизм подключения

Работа с хранилищем в манифесте Pod описывается двумя секциями:

1. **Определение тома (`spec.volumes`)**: задается на уровне Pod. Описывает источник данных (Backend) и присваивает ему имя.
2. **Монтирование тома (`spec.containers[*].volumeMounts`)**: задается внутри конкретного контейнера. Указывает путь (`mountPath`), по которому том будет доступен, и дополнительные параметры (например, `readOnly`).

### Классификация типов томов

| Тип | Категория | Основное назначение | Персистентность |
| :--- | :--- | :--- | :--- |
| `emptyDir` | Эфемерное | Временные данные, кэш, обмен между контейнерами | Нет |
| `hostPath` | Эфемерное | Доступ к файлам Node (для системных утилит, мониторинга) | Нет (привязка к Node) |
| `configMap` / `secret` | Эфемерное | Инъекция конфигураций и чувствительных данных | Нет |
| `projected` | Эфемерное | Агрегация нескольких источников (Secret, ConfigMap) в один путь | Нет |
| `ephemeral` | Эфемерное | Generic Ephemeral Volumes (PVC-подобный функционал для временных данных) | Нет |
| `persistentVolumeClaim` | Персистентное | Постоянное хранение данных (БД, медиа, логи) | Да |

## Основные типы томов

### emptyDir

**Описание:** пустой каталог, создаваемый на Node в момент запуска Pod.
**Особенности:**
- **medium: Memory**: создание тома в RAM (tmpfs). Обеспечивает максимальную скорость, но данные потребляют лимиты памяти (Memory Limits) контейнера.
- **sizeLimit**: ограничение объема. При превышении лимита Pod будет выселен (evicted) с узла.
- **Использование:** идеален для `scratch space` (временных файлов), кэширования или передачи данных между контейнерами (например, `initContainer` и основным приложением).

### hostPath

**Описание:** монтирование файла или директории напрямую с файловой системы Node в Pod.
**Типы монтирования (`type`):**
- `DirectoryOrCreate`: если по указанному пути ничего нет, будет создана пустая директория (права 0755).
- `FileOrCreate`: если файл отсутствует, будет создан пустой файл.
- `Directory` / `File`: монтирование существующего объекта (вызовет ошибку, если путь не существует).
- `Socket` / `CharDevice` / `BlockDevice`: специфические типы для системных нужд.
**Ограничения:**
- **Безопасность:** требует `Privileged` прав или специальных политик (Pod Security Standards), так как дает доступ к хосту.
- **Отсутствие мобильности:** Pod становится "привязанным" к конкретной ноде.

> **Совет по собеседованию: Сравнение `emptyDir` и `hostPath`**
> На собеседованиях часто просят сравнить эти два типа эфемерных томов:
> * **Область действия (Scope):** `emptyDir` привязан к одному конкретному Pod и существует только в течение его жизненного цикла. `hostPath` привязан к узлу (Node) и монтирует директорию из файловой системы хоста.
> * **Постоянство (Persistence):** `emptyDir` полностью **временный**. Данные теряются при удалении или миграции Pod. `hostPath` сохраняет данные на хосте даже после удаления Pod (до ручного удаления директории или вывода узла из эксплуатации).
> * **Доступность (Accessibility):** `emptyDir` доступен только контейнерам внутри одного и того же Pod. `hostPath` может совместно использоваться несколькими разными Pod, если они запущены на одном узле.

### Сетевые и локальные тома (через PV/PVC)

Хотя раньше сетевые тома (например, NFS, iSCSI) можно было монтировать напрямую в Pod (In-Tree плагины), современным стандартом является использование механизма `PersistentVolume` (PV) и `PersistentVolumeClaim` (PVC) через CSI-драйверы:
- **Local Volume:** локально подключенное хранилище на узле. В отличие от `hostPath`, Local Volumes интегрированы в планировщик Kubernetes, что гарантирует запуск Pod на правильном узле с нужным диском.
- **NFS (Network File System):** сетевая файловая система, позволяющая Pod получать доступ к общим файлам на удаленных серверах (ReadWriteMany).
- **iSCSI:** протокол доступа к блочному сетевому хранилищу, позволяющий Pod монтировать LUN-ы напрямую.

### ConfigMap и Secret

Позволяют монтировать данные из одноименных объектов Kubernetes как файлы.
- [Использование ConfigMap в Pod](../../ConfigMap/pod_usage.md)
- [Использование Secret в Pod](../../secrets/using_secrets.md)

### Projected Volume (тип projected)

Объединяет несколько источников (Secret, ConfigMap, Downward API, ServiceAccountToken) в одну точку монтирования.
Подробнее: [Projected Volumes — агрегация источников](./projected_volumes.md).

### Generic Ephemeral Volumes (тип ephemeral)

Появились в K8s 1.23. Позволяют использовать параметры PVC (динамический провижининг, StorageClass) для создания временных томов, которые удаляются вместе с Pod. Это дает возможность использовать быстрые локальные SSD или сетевые диски как временное хранилище с управлением через лимиты.

### subPath и subPathExpr

Позволяют монтировать не весь том целиком, а только его поддиректорию или конкретный файл.
- `subPath`: статическое имя директории в томе.
- `subPathExpr`: позволяет использовать переменные окружения для формирования имени пути (полезно для шардирования данных).

### Права доступа и fsGroup

Для управления правами доступа к томам на уровне всей группы контейнеров в Pod используется `securityContext.fsGroup`. Kubernetes автоматически изменит владельца (owner) всех файлов в томе на указанный GID при монтировании.

## Практические сценарии

### Сценарий 1: Обмен данными через emptyDir (sidecar)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sidecar-storage-demo
spec:
  volumes:
  - name: shared-data
    emptyDir: {}
  containers:
  - name: app
    image: nginx:1.25
    volumeMounts:
    - name: shared-data
      mountPath: /usr/share/nginx/html
  initContainers:
  - name: fetcher
    image: busybox
    command: ["sh", "-c", "echo 'Hello from Init' > /data/index.html"]
    volumeMounts:
    - name: shared-data
      mountPath: /data
```

### Сценарий 2: Использование subPath для ConfigMap

Позволяет добавить один файл в существующую директорию, не перетирая её содержимое.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: config-subpath-demo
spec:
  containers:
  - name: nginx
    image: nginx
    volumeMounts:
    - name: config-volume
      mountPath: /etc/nginx/conf.d/custom.conf # Монтируем как конкретный файл
      subPath: nginx.conf # Ключ внутри ConfigMap
  volumes:
  - name: config-volume
    configMap:
      name: my-nginx-config
```

### Сценарий 3: hostPath для мониторинга (node-exporter)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: node-exporter
spec:
  containers:
  - name: exporter
    image: prom/node-exporter
    volumeMounts:
    - name: proc
      mountPath: /host/proc
      readOnly: true
  volumes:
  - name: proc
    hostPath:
      path: /proc
      type: Directory
```

## Дополнительная информация

### Mount Propagation

Позволяет разделять монтирования, выполненные контейнером, с другими контейнерами в том же Pod или даже с хостом.
- `None`: изоляция (по умолчанию).
- `HostToContainer`: контейнер видит новые монтирования на хосте в этом пути.
- `Bidirectional`: хост видит монтирования, сделанные контейнером (требует `privileged: true`).

### Сравнение с Docker Volumes

| Характеристика | Kubernetes Volume | Docker Volume |
| :--- | :--- | :--- |
| **Управление** | Декларативное (YAML) | Императивное (CLI) |
| **Масштабируемость** | В рамках всего кластера | Ограничено одним хостом |
| **Драйверы** | CSI (облачные диски, NFS, Ceph) | Volume Drivers |
| **Жизненный цикл** | Привязан к Pod (кроме PVC) | Независим от контейнера |
