# Эфемерные контейнеры в Kubernetes (Ephemeral Containers)

## Определения

**Ephemeral Container (эфемерный контейнер)** — временный container, запускаемый в существующем работающем Pod (поде) для выполнения административных действий, таких как отладка, инспектирование состояния или траблшутинг. В отличие от обычных container, они не предназначены для выполнения бизнес-логики приложения.

**Distroless-образ** — минималистичный образ container, не содержащий оболочки (shell), пакетных менеджеров и стандартных утилит (содержит только приложение и его зависимости времени выполнения). Использование таких образов повышает безопасность, но делает невозможным стандартное подключение через `kubectl exec`, требуя применения Ephemeral Containers.

**Process Namespace Sharing (совместное использование пространства имён процессов)** — механизм, позволяющий разным container внутри одного Pod видеть процессы друг друга (общий PID-namespace, от Process Identifier).

---

## Базовые концепции

### Общие сведения

- **Стабильность:** механизм является стабильным (stable) начиная с Kubernetes версии 1.25.
- **Управление:** создаются через специализированный обработчик Ephemeral Containers в API (Application Programming Interface), а не через прямую модификацию спецификации Pod.
- **Неизменяемость:** невозможно добавить эфемерный контейнер через `kubectl edit` или простое обновление YAML-манифеста.
- **Жизненный цикл:** они автоматически не перезапускаются при завершении и удаляются вместе с Pod.
- **Ограничения:** не поддерживаются для Static Pods (статических подов, управляемых напрямую `kubelet`).

### Ограничения спецификации

Хотя эфемерные контейнеры используют структуру `Container`, многие поля для них запрещены на уровне API:

| Запрещённое поле | Причина |
|:---|:---|
| `ports` | Не могут открывать сетевые порты для внешнего доступа. |
| `resources` (requests/limits) | Ресурсы Pod (Central Processing Unit, память) фиксируются при создании и не могут быть изменены. |
| `livenessProbe`, `readinessProbe`, `startupProbe` | Не являются частью жизненного цикла приложения. |
| `lifecycle` (hooks) | Обработчики `postStart` и `preStop` не поддерживаются. |
| `restartPolicy` | Политика перезапуска всегда подразумевает отсутствие перезапуска. |

### Влияние на ресурсы

- Эфемерные контейнеры потребляют ресурсы (память, CPU) из общих лимитов, выделенных Pod при создании.
- Если действия в эфемерном контейнере (например, интенсивный анализ трафика или дампы памяти) приведут к превышению лимитов, `kubelet` может инициировать процесс вытеснения (eviction) всего Pod.

## Практические сценарии

### Сценарий 1: Отладка Pod без оболочки (Distroless)

Если в основном образе отсутствует `/bin/sh` или `/bin/bash`, используйте `kubectl debug` для добавления отладочного образа.

```bash
# Добавление интерактивного контейнера на базе busybox
kubectl debug -it <pod_name> --image=busybox:1.36 --target=<container_name>
```

**Параметры:**

- `--image`: образ с необходимым набором утилит.
- `--target`: позволяет эфемерному контейнеру использовать PID/network Namespace целевого контейнера (требуется для инспектирования запущенных процессов, снятия дампов трафика).
- `nicolaka/netshoot` — рекомендуемый образ для сетевой отладки: содержит `tcpdump`, `curl`, `dig`, `strace` (требует privileged).

### Сценарий 2: Анализ процессов через общие Namespace

Для того чтобы видеть процессы основного приложения из отладочного контейнера, необходимо активировать совместное использование PID-namespace.

```bash
kubectl debug -it <pod_name> \
  --image=alpine:latest \
  --target=<container_name> \
  --share-processes
```

### Сценарий 3: Создание отладочной копии Pod (Copy-to)

Если Pod находится в состоянии `CrashLoopBackOff` или его нельзя изменять в текущем виде, можно создать его копию с изменёнными параметрами.

```bash
kubectl debug <pod_name> \
  --image=ubuntu:24.04 \
  --copy-to=<new_pod_name> \
  --set-image=*=ubuntu:24.04
```

**Особенности:**

- `--copy-to`: создаёт новый объект Pod с указанным именем.
- `--set-image`: позволяет заменить образы существующих контейнеров в новой копии.

### Сценарий 4: Отладка на уровне Node (узла)

Если проблема связана с конфигурацией самой Node (например, проблемы с сетью или хранилищем), можно запустить отладочный Pod в пространстве имён хоста.

```bash
# Запуск отладочного контейнера на ноде
kubectl debug node/<node_name> -it --image=ubuntu:24.04
```

*Примечание:* файловая система узла будет смонтирована в директорию `/host` внутри отладочного контейнера.

## Дополнительная информация

### Сравнение методов отладки

| Метод | Использование | Создание нового Pod | Изменение команды запуска |
|:---|:---|:---|:---|
| `kubectl debug <pod>` | Добавление контейнера "на лету" | Нет | Нет |
| `kubectl debug --copy-to` | Глубокая отладка упавших подов | Да | Да |
| `kubectl debug node/` | Инспектирование узла | Да (специальный) | N/A |
