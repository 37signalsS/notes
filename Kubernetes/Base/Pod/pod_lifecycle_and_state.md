# Жизненный цикл и состояния Pod в Kubernetes

## Определения

**Фаза пода (Pod Phase)** — высокоуровневое состояние пода в кластере. Определяется полем `status.phase` в объекте `PodStatus`.

**Условия пода (Pod Conditions)** — массив в `status.conditions`, предоставляющий детальную информацию о состоянии пода.

**Состояния контейнеров (Container States)** — текущее состояние каждого контейнера внутри пода: `Waiting`, `Running` или `Terminated`.

**Graceful Shutdown** — процесс корректного завершения работы пода с отправкой сигнала `SIGTERM` и ожиданием завершения приложений.

**terminationGracePeriodSeconds** — время (по умолчанию 30 секунд), отводимое контейнерам на корректное завершение работы после получения `SIGTERM` до принудительной остановки через `SIGKILL`.

## Базовые концепции

### Фазы пода

| Фаза | Описание | Типичные причины |
| :--- | :--- | :--- |
| `Pending` | Под принят кластером, контейнеры не запущены | Планировщик не назначил узел, скачивание образов, нехватка ресурсов, работа init-контейнеров |
| `Running` | Под привязан к узлу, контейнеры созданы | Хотя бы один контейнер работает, запускается или перезапускается. **Не означает готовность приложения** |
| `Succeeded` | Все контейнеры завершились с кодом 0 | Типично для `Job`. Контейнеры не будут перезапущены |
| `Failed` | Все контейнеры завершены, хотя бы один с ошибкой | Ненулевой код выхода, ошибка выполнения |
| `Unknown` | Состояние не определено | Проблемы связи с узлом, `kubelet` не отвечает |

### Условия пода

Условия пода (Pod Conditions) — массив в `status.conditions`, предоставляющий детальную информацию о состоянии пода. Каждое условие содержит поля:

| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `type` | string | Имя условия (например, `Ready`, `PodScheduled`) |
| `status` | string | `True`, `False` или `Unknown` |
| `lastProbeTime` | timestamp | Когда условие последний раз проверялось |
| `lastTransitionTime` | timestamp | Когда под последний раз переходил между состояниями |
| `reason` | string | Машиночитаемая причина перехода (UpperCamelCase) |
| `message` | string | Человеко-читаемое описание деталей перехода |

| Условие | Описание |
| :--- | :--- |
| `PodScheduled` | Поду назначен узел |
| `Initialized` | Все init-контейнеры завершены успешно. Для Pod без init-контейнеров устанавливается в `True` до создания sandbox и сетевых параметров |
| `ContainersReady` | Все контейнеры готовы принимать трафик |
| `Ready` | Под готов принимать трафик (комбинация `ContainersReady` и других проверок). Используется для балансировки нагрузки через Service |
| `PodReadyToStartContainers` | **Kubernetes 1.29+ (beta, включено по умолчанию):** Sandbox и сеть пода настроены, kubelet готов запускать контейнеры. `False` означает, что sandbox ещё не создан или разрушен (перезапуск ноды, проблемы с container runtime, использующим VM-изоляцию) |

> **Практическая проверка:** Колонка `READY` в выводе `kubectl get pods` показывает соотношение готовых контейнеров к общему числу (например, `1/1`, `2/2`, `1/2`). Для детальной диагностики конкретного контейнера используйте `kubectl describe pod <pod-name>`.

### Состояния контейнеров

Каждый контейнер в поде может находиться в одном из трёх состояний. Информация доступна через `kubectl describe pod <pod-name>` в разделе `Container Statuses`.

| Состояние | Описание | Типичные причины |
| :--- | :--- | :--- |
| `Waiting` | Контейнер не запущен, kubelet ожидает выполнения условий | Скачивание образа (`ImagePullBackOff`, `ErrImagePull`), ожидание Secret/ConfigMap (если объект отсутствует — контейнер будет в `Waiting` до его создания), ошибки конфигурации |
| `Running` | Контейнер исполняется без ошибок | Нормальная работа. Если определён `postStart` hook, он уже выполнен |
| `Terminated` | Контейнер завершил работу (успешно или с ошибкой) | Успешное завершение (код 0) или ошибка (ненулевой код). Доступен `Exit Code`, `Signal`, `Reason`, `Message` |

**Связь с жизненным циклом Pod:** При обновлении образа (например, через Deployment) старые Pod переходят в `Terminated`, а новые создаются с состояниями контейнеров `Waiting` → `Running`.

### Политика перезапуска контейнеров (Restart Policy)

Подробный разбор типов перезапусков, отличий между перезапуском контейнера и пересозданием пода, а также триггеров обновления см. в статье **[Перезапуск подов в Kubernetes](./pod_restarts.md)**.

Политика перезапуска применяется ко **всем** контейнерам в поде (основным, init и sidecar). Указывается в `spec.restartPolicy` и принимает одно из трёх значений:

| Значение | Поведение | Когда использовать |
| :--- | :--- | :--- |
| `Always` (по умолчанию) | Kubelet перезапускает контейнер при **любом** завершении (код 0 или ненулевой) | Долгоживущие сервисы (веб-серверы, микросервисы) |
| `OnFailure` | Перезапуск только при **ненулевом** коде выхода (ошибка) | Одноразовые задачи с логическим завершением (скрипты, batch-обработка) |
| `Never` | Контейнер **не** перезапускается ни при каких условиях | Отладка, одноразовые тесты |

> **Важно:** Restart Policy не применима к Sidecar-контейнерам, определённым как init-контейнеры — у них всегда `restartPolicy: Always`.

**Механизм перезапуска:**

- Kubelet **не** перемещает Pod на другую ноду — контейнер заменяется внутри того же Pod на той же ноде
- При частых падениях применяется **exponential backoff**: kubelet увеличивает задержку перед перезапуском
  - 1-й перезапуск: сразу
  - 2-й: через 10 секунд
  - 3-й: через 20 секунд
  - Далее: экспоненциально (×2), максимум — **5 минут** между перезапусками
- **Сброс счётчика:** Если контейнер работает стабильно **более 10 минут**, kubelet обнуляет счётчик backoff

> **CrashLoopBackOff:** При циклических падениях (контейнер завершается с ошибкой сразу после запуска) Pod переходит в статус `CrashLoopBackOff` — kubelet применяет максимальную задержку (5 минут) между перезапусками. Диагностика: `kubectl describe pod <pod-name>` → раздел `Events`.

**Типичная ошибка с `Always`:** Если контейнер выполняет одноразовую задачу (скачать файл, обработать данные) и завершается с кодом 0 — kubelet при политике `Always` будет бесконечно перезапускать его. Решение: используйте `OnFailure` или `Never`.

### Readiness Gates (Кастомные условия готовности)

**Readiness Gates** — механизм (стабилизирован в Kubernetes 1.14), позволяющий приложениям или операторам инжектить кастомные условия в статус пода для оценки его готовности.

**Зачем использовать:**
Когда стандартных проверок (`ContainersReady`, `Ready`) недостаточно — например, требуется внешняя зависимость (очередь сообщений, внешняя БД, лицензионный сервер), состояние которой Kubernetes не может проверить напрямую.

**Как работает:**

1. В `spec.readinessGates` пода добавляется список кастомных условий:

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: readiness-gates-demo
spec:
  readinessGates:
  - conditionType: "example.com/external-service-ready"
  containers:
  - name: app
    image: my-app:1.0
```

1. Kubernetes добавляет указанные `conditionType` в `status.conditions` пода
2. Если условие отсутствует в `status.conditions` — его статус по умолчанию `False`
3. Приложение/оператор должно обновить статус условия через `PATCH` (команда `kubectl patch` не поддерживает прямое изменение `status` — требуется использовать Kubernetes client library или прямой API call)
4. Pod переходит в `Ready` только когда **все** conditions (встроенные + кастомные) имеют `status: True`

> **Альтернатива:** В большинстве случаев достаточно стандартных readiness probes (HTTP/TCP проверки). Readiness Gates применяются для специфичных сценариев, где внешняя зависимость не проверяется через HTTP/TCP на уровне контейнера.

### Graceful Shutdown

Подробное описание процесса graceful shutdown, порядка терминации, настройки `preStop` hook и `terminationGracePeriodSeconds` см. в **[Graceful Shutdown](../../Troubleshooting/Common_Errors/PodTerminating/graceful_shutdown.md)**.

Краткая справка:

1. **Пользователь вызывает `kubectl delete pod`:** API-сервер проверяет аутентификацию и авторизацию, затем помечает Pod на удаление в `etcd`.
2. **Отправка SIGTERM:** Kubernetes отправляет сигнал `SIGTERM` всем контейнерам пода.
3. **Исключение из балансировки:** Контроллер EndpointSlice удаляет IP подa из соответствующего EndpointSlice. kube-proxy (через IPTables/IPVS) обновляет правила маршрутизации, прекращая отправку нового трафика на этот Pod.
4. **Выполнение preStop hook:** Если определён `preStop`, он выполняется параллельно с SIGTERM.
5. **Grace period:** Контейнеры получают время на корректное завершение (`terminationGracePeriodSeconds`, по умолчанию 30с).
6. **Отправка SIGKILL:** Если контейнеры не завершаются, им посылается `SIGKILL` для принудительной остановки.

> **Важно:** Приложение должно корректно обрабатывать `SIGTERM` для сохранения данных и завершения активных соединений. Для надёжного исключения из Service рекомендуется использовать `preStop` с задержкой — это даёт kube-proxy время на обновление правил маршрутизации.

Подробное описание особенностей отправки сигналов, терминации sidecar-контейнеров и очистки pause container см. в **[Graceful Shutdown](../../Troubleshooting/Common_Errors/PodTerminating/graceful_shutdown.md)**.

### Lifecycle Hooks (postStart / preStop)

**Lifecycle Hooks** — механизмы Kubernetes, позволяющие выполнять произвольные команды в контейнере при определённых событиях жизненного цикла. Контейнер может определять **один обработчик на одно событие** — то есть одна команда на `postStart` и одна на `preStop`. Несколько команд можно выполнить, если уложить их в одну shell-команду (например, через `&&` или `;`).

| Хук | Когда вызывается | Блокировка |
| :--- | :--- | :--- |
| `postStart` | Немедленно после запуска контейнера | Контейнер **не переходит** в статус `Running`, пока hook не завершится |
| `preStop` | При начале терминации контейнера (после `kubectl delete` или масштабирования) | Kubernetes **ждёт** завершения hook до отправки SIGKILL (в пределах `terminationGracePeriodSeconds`) |

#### postStart Hook

- Запускается **асинхронно** относительно entrypoint контейнера — оба процесса могут стартовать одновременно
- **Нет гарантии**, что `postStart` выполнится **до** начала работы основного процесса контейнера
- Несмотря на асинхронность, Kubernetes **блокирует** перевод контейнера в статус `Running` до завершения hook
- Если `postStart` завершается с ошибкой (ненулевой код выхода) — Kubernetes переводит контейнер в статус `Terminated` с причиной `Error`
- Типичные сценарии: создание начальных файлов конфигурации, регистрация сервиса, проверка зависимостей

#### preStop Hook

- Вызывается **немедленно** при получении сигнала на терминацию контейнера
- Выполняется **синхронно** — Kubernetes ждёт завершения hook перед отправкой SIGKILL
- Работает **параллельно** с отправкой SIGTERM (оба запускаются одновременно)
- Если основной процесс контейнера завершился **раньше** preStop — hook **продолжит** выполнение до своего завершения или до истечения `terminationGracePeriodSeconds`
- Типичные сценарии: закрытие сессий БД, завершение обработки запросов, уведомление сервиса о скором отключении

> **Важно:** preStop hook **НЕ вызывается** для Pod в статусе `Completed` — только для Pod, которые находятся в процессе терминации.

#### Практический пример: postStart + preStop

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: lifecycle-demo
spec:
  containers:
  - name: nginx
    image: nginx
    lifecycle:
      postStart:
        exec:
          command: ["/bin/sh", "-c", "echo 'Post-start executed' > /usr/share/nginx/html/message"]
      preStop:
        exec:
          command: ["/bin/sh", "-c", "sleep 15; nginx -s quit"]
```

**Что происходит:**

1. **postStart:** После запуска контейнера создаётся файл `/usr/share/nginx/html/message` с сообщением
2. **preStop:** При терминации — 15-секундная задержка (ожидание завершения запросов) и плавная остановка nginx (`nginx -s quit`)

**Проверка postStart:**

```bash
kubectl apply -f lifecycle-demo.yaml
kubectl exec -it lifecycle-demo -- bash
cat /usr/share/nginx/html/message  # → Post-start executed
```

#### Важные ограничения и предупреждения

| Сценарий | Поведение |
| :--- | :--- |
| `kubectl delete pod --force --grace-period=0` | Pod удаляется **мгновенно**, preStop hook **НЕ вызывается** |
| Pod в статусе `Completed` | preStop hook **НЕ вызывается** — под уже завершён корректно |
| Hook завершился с ошибкой | `postStart` → контейнер `Terminated`; `preStop` → Kubernetes всё равно отправит SIGKILL по таймауту |
| Превышение `terminationGracePeriodSeconds` | Hook принудительно завершается (SIGKILL), независимо от его состояния |

> **Рекомендация:** Не добавляйте **критическую** бизнес-логику в preStop hook — её можно обойти через `kubectl delete --force --grace-period=0`. Используйте preStop для оптимизации graceful shutdown, но не для гарантии сохранения данных.

### Жизненный цикл пода на worker-узле

| Этап | Описание |
| :--- | :--- |
| 1. Получение спецификации | `kubelet` получает спецификацию Pod и проверяет возможность размещения (ресурсы, taints) |
| 2. Создание sandbox | Container Runtime (`containerd`) создаёт изолированное окружение, включая сетевое пространство |
| 3. Загрузка образов | Runtime загружает необходимые образы контейнеров |
| 4. Подключение к сети | CNI-плагин подключает Pod к сети: выделяет IP, настраивает `veth`-пары и маршруты |
| 5. Запуск контейнеров | `kubelet` запускает init-контейнеры (если есть), затем основные контейнеры |
| 6. Пробы (Probes) | `kubelet` выполняет `startup`, `readiness` и `liveness` пробы |
| 7. Сбор телеметрии | Логи стримятся через CRI, метрики собираются через `cAdvisor` |
| 8. Завершение | При удалении: `SIGTERM` → `preStop` хуки → `terminationGracePeriodSeconds` → `SIGKILL` → освобождение ресурсов CNI/CSI → очистка pause container |
| 9. Terminal phase | Kubelet переводит под в фазу `Succeeded` или `Failed` в зависимости от exit code контейнеров (гарантировано с Kubernetes 1.27) |
| 10. Удаление из API | API-сервер удаляет объект Pod из etcd — под больше не виден в `kubectl get pods` |

## Практические сценарии

### Пример 1: Диагностика состояний пода

Для определения причины нахождения пода в состоянии `Pending`:

```bash
# Подробная информация о поде с событиями
kubectl describe pod <pod-name>

# Проверка условий пода
kubectl get pod <pod-name> -o jsonpath='{.status.conditions}'

# Проверка состояния контейнеров
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[*].state}'
```

Ключевой инструмент диагностики — раздел `Events` в выводе `kubectl describe`, показывающий ошибки скачивания образов, нехватку ресурсов и другие проблемы.

Подробные команды диагностики см. в [Практические сценарии и команды](./pod_practical_scenarios_commands.md).

## Дополнительная информация

### Pod Garbage Collector

**Pod Garbage Collector (Pod GC)** — контроллер в `kube-controller-manager`, который автоматически удаляет завершённые поды при превышении порога.

**Когда Pod GC удаляет поды:**

- Число подов в терминальных фазах (`Succeeded`, `Failed`) превышает `terminated-pod-gc-threshold` (настраивается в kube-controller-manager)
- Под был привязан к узлу, который больше не существует
- Под не был запланирован, но находится в статусе `Terminating`
- Под привязан к узлу с состоянием `NodeVolumeOut` (CSI driver не может отмонтировать volume — узел помечен как проблемный)

> **Важно:** Pod GC работает только с завершёнными подами. Активные поды не удаляются этим контроллером.
