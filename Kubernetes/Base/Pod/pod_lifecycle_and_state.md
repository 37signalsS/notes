# Жизненный цикл и состояния Pod в Kubernetes

## Определения

**Фаза пода (Pod Phase)** — высокоуровневое состояние пода в кластере. Определяется полем `status.phase` в объекте `PodStatus`.

**Условия пода (Pod Conditions)** — массив в `status.conditions`, предоставляющий детальную информацию о состоянии пода.

**Состояния контейнеров (Container States)** — текущее состояние каждого контейнера внутри пода: `Waiting`, `Running` или `Terminated`.

**Graceful Shutdown** — процесс корректного завершения работы пода с отправкой сигнала `SIGTERM` и ожиданием завершения приложений.

**terminationGracePeriodSeconds** — время (по умолчанию 30 секунд), отводимое контейнерам на корректное завершение работы после получения `SIGTERM` до принудительной остановки через `SIGKILL`.

## Базовые концепции

### Фазы пода

| Фаза | Описание | Типичные причины |
| :--- | :--- | :--- |
| `Pending` | Под принят кластером, контейнеры не запущены | Планировщик не назначил узел, скачивание образов, нехватка ресурсов, работа init-контейнеров |
| `Running` | Под привязан к узлу, контейнеры созданы | Хотя бы один контейнер работает, запускается или перезапускается. **Не означает готовность приложения** |
| `Succeeded` | Все контейнеры завершились с кодом 0 | Типично для `Job`. Контейнеры не будут перезапущены |
| `Failed` | Все контейнеры завершены, хотя бы один с ошибкой | Ненулевой код выхода, ошибка выполнения |
| `Unknown` | Состояние не определено | Проблемы связи с узлом, `kubelet` не отвечает |

### Условия пода

| Условие | Описание |
| :--- | :--- |
| `PodScheduled` | Поду назначен узел |
| `Initialized` | Все init-контейнеры завершены успешно |
| `ContainersReady` | Все контейнеры готовы принимать трафик |
| `Ready` | Под готов принимать трафик (комбинация `ContainersReady` и других проверок) |

### Состояния контейнеров

| Состояние | Описание | Типичные причины |
| :--- | :--- | :--- |
| `Waiting` | Контейнер не запущен | Скачивание образа, ожидание init-контейнеров, ошибки конфигурации |
| `Running` | Контейнер исполняется без ошибок | Нормальная работа |
| `Terminated` | Контейнер завершил работу | Успешное завершение (код 0) или ошибка (ненулевой код). Доступен код выхода |

### Graceful Shutdown

Процесс завершения работы пода:

1. **Отправка SIGTERM:** Kubernetes отправляет сигнал `SIGTERM` всем контейнерам пода
2. **Grace period:** Контейнеры получают время на корректное завершение (`terminationGracePeriodSeconds`, по умолчанию 30с)
3. **Отправка SIGKILL:** Если контейнеры не завершаются, им посылается `SIGKILL` для принудительной остановки

> **Важно:** Приложение должно корректно обрабатывать `SIGTERM` для сохранения данных и завершения активных соединений.

### Жизненный цикл пода на worker-узле

| Этап | Описание |
| :--- | :--- |
| 1. Получение спецификации | `kubelet` получает спецификацию Pod и проверяет возможность размещения (ресурсы, taints) |
| 2. Создание sandbox | Container Runtime (`containerd`) создаёт изолированное окружение, включая сетевое пространство |
| 3. Загрузка образов | Runtime загружает необходимые образы контейнеров |
| 4. Подключение к сети | CNI-плагин подключает Pod к сети: выделяет IP, настраивает `veth`-пары и маршруты |
| 5. Запуск контейнеров | `kubelet` запускает init-контейнеры (если есть), затем основные контейнеры |
| 6. Пробы (Probes) | `kubelet` выполняет `startup`, `readiness` и `liveness` пробы |
| 7. Сбор телеметрии | Логи стримятся через CRI, метрики собираются через `cAdvisor` |
| 8. Завершение | При удалении: `SIGTERM` → `preStop` хуки → `terminationGracePeriodSeconds` → `SIGKILL` → освобождение ресурсов CNI/CSI |

## Практические сценарии

### Пример 1: Корректная обработка SIGTERM

При получении `SIGTERM` приложение должно:

- Прекратить принимать новые соединения/запросы
- Завершить обработку текущих запросов
- Закрыть соединения с БД, очередями, внешними сервисами
- Освободить ресурсы и завершить работу

**Последствия некорректной обработки:** Потеря данных, обрыв запросов, неконсистентное состояние.

### Пример 2: Настройка graceful shutdown с preStop hook

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: graceful-shutdown-demo
spec:
  terminationGracePeriodSeconds: 60
  containers:
  - name: app
    image: my-app:1.0
    lifecycle:
      preStop:
        exec:
          command: ["/bin/sh", "-c", "curl -X POST http://localhost:8080/shutdown"]
    readinessProbe:
      httpGet:
        path: /ready
        port: 8080
      periodSeconds: 2
      failureThreshold: 1
```

**Порядок завершения:**
1. Kubernetes отправляет `SIGTERM`
2. Выполняется `preStop` hook (уведомление приложения)
3. Приложение меняет статус на `/ready` → `503` (исключение из Service)
4. Завершаются активные соединения
5. По истечении `terminationGracePeriodSeconds` процесс завершается

### Пример 3: Диагностика состояний пода

Для определения причины нахождения пода в состоянии `Pending`:

```bash
# Подробная информация о поде с событиями
kubectl describe pod <pod-name>

# Проверка условий пода
kubectl get pod <pod-name> -o jsonpath='{.status.conditions}'

# Проверка состояния контейнеров
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[*].state}'
```

Ключевой инструмент диагностики — раздел `Events` в выводе `kubectl describe`, показывающий ошибки скачивания образов, нехватку ресурсов и другие проблемы.

Подробные команды диагностики см. в [Практические сценарии и команды](./pod_practical_scenarios_commands.md).
