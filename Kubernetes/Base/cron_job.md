# CronJob

Если вам нужно выполнять [Job](./job.md) не один раз, а по расписанию (например, каждую ночь для создания бэкапа), используйте **CronJob**. Он работает как системный `cron` в Linux, но для Kubernetes.

`CronJob` создаёт объекты `Job` в соответствии с заданным расписанием в формате `cron`.

### Пример `CronJob`

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup-cronjob
spec:
  # Запускать каждый день в 2 часа ночи
  schedule: "0 2 * * *"
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup-container
            image: backup-tool
            command: ["/bin/sh", "-c", "run-backup.sh"]
          restartPolicy: OnFailure
```

## Важные параметры (spec)

Помимо расписания (`schedule`), `CronJob` имеет несколько ключевых параметров, которые управляют его поведением.

- **`startingDeadlineSeconds`**

  - **Что это:** Максимальное время в секундах, в течение которого `CronJob` может запустить `Job`, если он пропустил запланированное время (например, из-за того, что кластер был недоступен).
  - **Как работает:** Если с момента запланированного запуска прошло больше секунд, чем указано в `startingDeadlineSeconds`, `Job` не будет запущен, а событие будет засчитано как "пропущенное".
  - **Пример:** `startingDeadlineSeconds: 100` — если `Job` не удалось запустить в течение 100 секунд после планового времени, он будет пропущен.

- **`concurrencyPolicy` (Политика параллелизма)**

  - **Что это:** Определяет, как `CronJob` должен поступать с новыми `Job`, если предыдущие еще не завершились.
  - **Возможные значения:**
    - **`Allow` (по умолчанию):** Позволяет запускать несколько `Job` одновременно. Если пришло время для нового `Job`, а старый еще работает, новый `Job` все равно будет запущен.
    - **`Forbid`:** Запрещает параллельный запуск. Если предыдущий `Job` еще не завершен, новый `Job` будет пропущен.
    - **`Replace`:** Заменяет текущий активный `Job` новым. Если старый `Job` еще работает, `CronJob` остановит его и запустит новый.

- **`successfulJobsHistoryLimit`**

  - **Что это:** Количество успешно завершенных `Job`, которые нужно хранить.
  - **По умолчанию:** `3`.
  - **Зачем нужно:** Позволяет контролировать количество старых `Job` и `Pod`'ов в кластере, чтобы не засорять его. Установите в `0`, если не хотите хранить историю успешных запусков.

- **`failedJobsHistoryLimit`**

  - **Что это:** Количество неудачно завершенных `Job`, которые нужно хранить.
  - **По умолчанию:** `1`.
  - **Зачем нужно:** Полезно для отладки. Хранение логов и состояния упавших `Job` помогает понять, что пошло не так.
