## Основной принцип: Декларативное состояние

Вы не даете Kubernetes прямых указаний, как реагировать на сбой. Вместо этого вы объявляете **желаемое состояние** системы (например, «всегда должно быть запущено 3 экземпляра этого приложения»).

Контроллеры Kubernetes постоянно сравнивают текущее состояние кластера с желаемым и автоматически предпринимают действия для устранения расхождений. Этот процесс называется **циклом сверки (Reconciliation Loop)**.

## Ключевые компоненты для бесшовной работы

Для обеспечения высокой доступности и бесшовного переключения для пользователей используются следующие объекты:

### Deployment / ReplicaSet

*   **Задача**: Поддерживать заданное количество идентичных Подов (реплик).
*   **При сбое**: Если нода выходит из строя, `ReplicaSet` обнаруживает, что количество работающих реплик стало меньше желаемого. Он немедленно создает недостающие Поды, которые `Scheduler` размещает на здоровых нодах.

### Service

*   **Задача**: Предоставить единую, стабильную точку доступа (IP-адрес и DNS-имя) для группы Подов.
*   **При сбое**: `Service` отслеживает состояние своих эндпоинтов (Подов). Если Под становится недоступным, `Service` немедленно исключает его из списка и перестает направлять на него трафик. Как только новый Под запускается и становится готов, `Service` автоматически добавляет его в балансировщик. Именно `Service` обеспечивает "невидимость" сбоя для конечного пользователя.

### Probes (Пробы жизнеспособности и готовности)

*   **Readiness Probe (Проба готовности)**: Сообщает, готов ли Под принимать новый трафик. Если проба не проходит, `Service` временно убирает Под из ротации.
*   **Liveness Probe (Проба жизнеспособности)**: Проверяет, работает ли приложение внутри Пода. Если проба фейлится, `Kubelet` перезапускает контейнер.

Более подробно о настройке проб можно прочитать в документе [Пробы (Probes)](./probes.md).

## Сценарии работы

### Сценарий: Аварийный сбой рабочей ноды (Unplanned Failure)

Это классический пример самовосстановления:

1.  **Сбой**: Рабочая нода внезапно отключается.
2.  **Обнаружение**: `Control Plane` перестает получать сигналы работоспособности (heartbeats) от `Kubelet` на отказавшей ноде.
3.  **Реакция**: `Node Controller` помечает ноду как `NotReady`.
4.  **Выселение**: По истечении таймаута (`pod-eviction-timeout`, по умолчанию 5 минут), все Поды на этой ноде получают статус `Terminating`.
5.  **Восстановление**: `ReplicaSet` создает новые Поды для замены "потерянных".
6.  **Перенаправление трафика**: `Service` уже исключил Поды на отказавшей ноде и направляет трафик на новые, как только они проходят `Readiness Probe`.

### Сценарий: Плановое обслуживание ноды (Planned Maintenance)

Для обслуживания ноды без простоя для приложений используются следующие команды:

*   `kubectl cordon <node-name>`: Помечает ноду как недоступную для планирования новых Подов (unschedulable). Существующие Поды продолжают работать. Это подготовительный шаг.

*   `kubectl uncordon <node-name>`: Снимает пометку `unschedulable`, позволяя планировщику снова размещать новые Поды на этой ноде.

*   `kubectl drain <node-name>`: Выполняет `cordon` и безопасно "выселяет" все управляемые Поды с ноды. Это гарантирует, что работа сервиса не будет нарушена, так как контроллеры создадут замену на других нодах.

    **Важные флаги:**
    *   `--ignore-daemonsets`: `drain` по умолчанию остановится, если найдет Поды, управляемые `DaemonSet`. Этот флаг заставляет игнорировать их (поскольку `DaemonSet` должен работать на всех нодах, его поды не переносятся).
    *   `--delete-emptydir-data`: Необходимо использовать, если на ноде есть Поды с томами `emptyDir`. Этот флаг подтверждает, что временные данные в этих томах можно безопасно удалить.
    *   `--force`: Принудительно продолжить `drain`, даже если на ноде есть "голые" Поды (не управляемые `Deployment`, `StatefulSet` и т.д.). **Использовать с осторожностью.**

    **Пример:**
    ```bash
    # Безопасно очистить ноду, игнорируя системные поды DaemonSet
    kubectl drain <имя_ноды> --ignore-daemonsets
    ```

## Приоритеты и вытеснение (Pod Priority and Preemption)

В условиях ограниченных ресурсов планировщик может столкнуться с ситуацией, когда для нового, более важного пода нет места. Механизм **Priority and Preemption** решает эту проблему.

*   **`PriorityClass`**: Это объект уровня кластера, который определяет числовой приоритет. Чем выше значение, тем выше приоритет.
*   **`Pod Priority`**: Подам назначается `PriorityClass`.
*   **`Preemption` (Вытеснение)**: Если планировщик не может найти место для пода с высоким приоритетом, он может **вытеснить** (удалить) один или несколько подов с более низким приоритетом с подходящей ноды, чтобы освободить ресурсы.

Это позволяет гарантировать, что критически важные компоненты (например, `coredns`, `ingress-controller` или ключевые бизнес-приложения) будут запущены, даже если кластер "забит" менее важными задачами (например, тестовыми или batch-заданиями).

1.  **Создание `PriorityClass`**:
    ```yaml
    apiVersion: scheduling.k8s.io/v1
    kind: PriorityClass
    metadata:
      name: high-priority
    value: 1000000
    globalDefault: false
    description: "Этот PriorityClass используется для критически важных сервисов."
    ```

2.  **Назначение подам**:
    ```yaml
    apiVersion: v1
    kind: Pod
    metadata:
      name: my-critical-app
    spec:
      containers:
        - name: main
          image: nginx
      priorityClassName: high-priority # <-- Назначаем приоритет
    ```
    
Теперь, если для `my-critical-app` не хватит ресурсов, планировщик попытается удалить поды с приоритетом ниже `1000000`, чтобы запустить его.

## Управление размещением подов (Affinity)

Еще одним важным инструментом для обеспечения высокой доступности является управление размещением подов. С помощью правил **Affinity и Anti-Affinity** можно гарантировать, что реплики вашего приложения будут распределены по разным узлам или зонам доступности, предотвращая единую точку отказа.

Подробнее об этом можно прочитать в документе [Affinity и Anti-Affinity](./affinity.md).

## Fencing (Изоляция узла)

**Fencing** (от англ. "ограждение") — это фундаментальная техника в отказоустойчивых кластерах, которая гарантирует, что сбойный узел будет принудительно изолирован от общих ресурсов (таких как общее хранилище или база данных).

Самый известный метод — **STONITH (Shoot The Other Node In The Head)**, что дословно переводится как "выстрелить другому узлу в голову".

### Зачем это нужно: проблема Split-Brain

Представьте кластер из двух узлов, которые потеряли связь друг с другом, но оба продолжают работать. Каждый узел может решить, что он — единственный "живой" мастер, и попытаться захватить общие ресурсы. Этот сценарий называется **Split-Brain** ("расщепление мозга") и является катастрофой для целостности данных, так как оба узла могут начать одновременно писать в один и тот же файл или базу данных, вызывая их необратимое повреждение.

### Как работает Fencing

Fencing решает эту проблему, гарантируя, что прежде чем другой узел возьмет на себя роль мастера, старый мастер будет 100% отключен.

**Виды Fencing:**
-   **Power Fencing:** Самый надежный способ. Кластер обращается к внешнему устройству (например, управляемому блоку питания (PDU) или контроллеру управления основной платой, такому как IPMI/iDRAC/iLO), чтобы физически отключить питание сбойного узла.
-   **Resource Fencing:** Менее надежный способ, при котором доступ к общему ресурсу (например, общему диску) для сбойного узла блокируется на уровне самого ресурса (например, через SCSI-резервации).

Хотя Kubernetes сам по себе не выполняет STONITH, этот механизм является критически важной частью построения по-настоящему высокодоступной инфраструктуры, на которой работает Kubernetes, особенно для stateful-приложений с общими данными.
