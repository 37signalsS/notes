# ReplicaSet

## Определения

**ReplicaSet** — это объект API Kubernetes, основной задачей которого является поддержание стабильного набора идентичных подов (**Pod**, реплик) в любой момент времени. Он гарантирует, что в кластере запущено ровно то количество подов, которое указано в его конфигурации.

**Ключевые функции:**
- **Самовосстановление:** Если под удаляется или выходит из строя, `ReplicaSet` немедленно создает новый.
- **Масштабирование:** Позволяет легко изменять количество запущенных экземпляров приложения.
- **Управление жизненным циклом:** Служит фундаментом для более высокоуровневого контроллера — [Deployment](./Deployment/index.md).

**Исторический контекст:** `ReplicaSet` является преемником `ReplicationController`. Основное отличие заключается в поддержке более гибких селекторов (Set-based selectors).

## Основные концепции

### Анатомия и спецификация

В отличие от простых подов, `ReplicaSet` описывает не только желаемое состояние контейнеров, но и механизмы управления ими.

*   **`replicas`**: Желаемое количество экземпляров. По умолчанию `1`.
*   **`selector`**: Определяет, какими подами управляет данный `ReplicaSet`. Поддерживает два типа:
    *   `matchLabels` (Equality-based): Совпадение ключа и значения.
    *   `matchExpressions` (Set-based): Позволяет использовать операторы `In`, `NotIn`, `Exists`, `DoesNotExist`.
*   **`template`**: Шаблон пода, который будет использоваться для создания новых реплик.
*   **`minReadySeconds`**: Минимальное время (в секундах), в течение которого новый под должен проработать без сбоев и быть в состоянии `Ready`, чтобы считаться доступным. Это помогает избежать каскадных падений при запуске неисправных версий.

### Алгоритм выбора подов на удаление

Если количество подов превышает `replicas` (например, при масштабировании вниз или изменении меток), `ReplicaSet` удаляет "лишние" поды в следующем приоритете:
1.  Поды в состоянии `Terminating`.
2.  Поды с наименьшим количеством готовых контейнеров.
3.  Поды, не прошедшие проверки (Probes).
4.  Поды, запущенные на узлах с наибольшим количеством реплик данного `ReplicaSet`.
5.  Самые "молодые" поды (по времени создания).

### Метка pod-template-hash

При использовании в составе `Deployment`, контроллер автоматически добавляет к `ReplicaSet` и его подам метку `pod-template-hash`. Она необходима для:
- Разделения разных версий (ревизий) одного приложения.
- Гарантии того, что `Deployment` не "захватит" поды от другого репозитория или старой конфигурации.

## Практические сценарии

### Пример манифеста

Пример создания набора из 3 реплик веб-сервера с использованием гибкого селектора.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: web-frontend
  labels:
    app: guestbook
    tier: frontend
spec:
  replicas: 3
  selector:
    matchExpressions:
      - {key: tier, operator: In, values: [frontend]}
  template:
    metadata:
      labels:
        tier: frontend
    spec:
      containers:
      - name: php-redis
        image: gcr.io/google_samples/gb-frontend:v3
        resources:
          requests:
            cpu: 100m
            memory: 100Mi
```

### Масштабирование

Изменение количества реплик может выполняться как декларативно (через правку YAML), так и императивно:

```bash
# Императивное масштабирование до 5 реплик
kubectl scale rs web-frontend --replicas=5

# Проверка текущего состояния
kubectl get rs web-frontend
# NAME           DESIRED   CURRENT   READY   AGE
# web-frontend   5         5         5       2m
```

### Изоляция пода (Orphaning)

Если у работающего пода изменить метки так, чтобы они перестали соответствовать селектору `ReplicaSet`, под станет "сиротой" (orphaned). `ReplicaSet` немедленно создаст новый под взамен "потерянного", но старый под продолжит работать самостоятельно. Это полезно для отладки конкретного экземпляра без остановки всего сервиса.

## Дополнительная информация

### Почему лучше использовать Deployment?

Хотя `ReplicaSet` полностью функционален, в реальных проектах его **крайне редко** используют напрямую. `Deployment` предоставляет критически важные функции поверх `ReplicaSet`:
- **Rolling Update:** Плавная замена старых версий новыми без простоя.
- **Rollback:** Возможность быстро откатиться к предыдущему `ReplicaSet` при обнаружении проблем.
- **История ревизий:** Хранение информации о предыдущих конфигурациях.
