# ConfigMap

## Определения

**ConfigMap** — это объект API, который позволяет хранить неконфиденциальные конфигурационные данные в виде пар "ключ-значение". Его главная задача — **отделить конфигурацию от кода приложения** (separation of concerns), что делает приложения переносимыми и легко настраиваемыми для разных окружений (dev, staging, prod) без пересборки Docker-образа.

**Ключевое правило:** Используйте ConfigMap для настроек, которые могут меняться, а [Secret](./secrets/secrets_basics.md) — для конфиденциальных данных (пароли, токены, ключи API).

## Базовые концепции

### Проблема встраивания конфигурации в образ

Традиционный подход с копированием конфигурации в Docker-образ на этапе сборки (`COPY config.conf /etc/app/`) имеет серьёзные недостатки:

* **Необходимость пересборки образа** при любом изменении конфигурации
* **Невозможность использования одного образа** в разных окружениях (dev/staging/prod)
* **Усложнение поддержки** в больших проектах с множеством микросервисов

### Преимущества ConfigMap

* **Обновление конфигурации без пересборки образа** — изменения применяются при следующем запуске пода
* **Единый образ для всех окружений** — конфигурация варьируется через ConfigMap
* **Централизованное управление** — все настройки хранятся в одном месте Kubernetes
* **Возможность обновления на лету** — при использовании через volume файлы обновляются автоматически
* **Разделение ответственности** — разработчики управляют кодом, операторы — конфигурацией

### Ограничения ConfigMap

* Максимальный размер: **1 MiB**
* Типы данных: строки (UTF-8) в поле `data`, бинарные данные (base64) в поле `binaryData`
* Количество ключей: не ограничено (в пределах 1 MiB)
* **Не предоставляет шифрования или безопасности** — данные хранятся в открытом виде. Для конфиденциальных данных используйте [Secret](./secrets/secrets_basics.md)

### Структура объекта

В отличие от большинства объектов Kubernetes, у ConfigMap **нет поля `spec`**. Вместо него используются поля `data` и `binaryData`:

* **`data`** — строковые пары ключ-значение (UTF-8). Поле опционально — можно создать пустой ConfigMap, хотя практического смысла в этом мало
* **`binaryData`** — бинарные данные, закодированные в Base64. Также опционально
* Можно использовать оба поля одновременно или только одно из них

**Пример структуры:**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: game-config
data:
  # Простая переменная
  player_initial_lives: "3"
  # Файл конфигурации как значение
  game.properties: |
    enemy=dragon
    level=10
  ui.properties: |
    color.good=purple
    color.bad=yellow
binaryData:
  logo.png: "iVBORw0KGgoAAAANSUhEUg..."
```

### Способы использования

| Способ | Обновление | Когда использовать |
| :--- | :--- | :--- |
| **Переменные окружения** (`env`, `envFrom`) | Нет | Простые флаги, параметры |
| **Тома** (`volume`) | Да, автоматически | Конфигурационные файлы |
| **subPath** | Нет | Один файл в директории |
| **Projected** | Да, автоматически | Комбинация источников |

## Практические сценарии

### Быстрый старт

1. **Создание ConfigMap:**

   ```bash
   kubectl create configmap app-config --from-literal=LOG_LEVEL=info
   ```

2. **Использование в поде (переменные окружения):**

   ```yaml
   env:
     - name: LOG_LEVEL_VAR          # Имя переменной в поде (может отличаться от ключа)
       valueFrom:
         configMapKeyRef:
           name: app-config
           key: LOG_LEVEL            # Ключ в ConfigMap
   # Или все ключи сразу:
   envFrom:
     - configMapRef:
         name: app-config
   ```

   > **Важно:** Имя переменной окружения в поде (`name`) **не обязано совпадать** с ключом в ConfigMap (`key`). Это позволяет выбирать понятные имена переменных независимо от структуры ConfigMap.

3. **Использование в поде (том):**

   ```yaml
   volumes:
     - name: config
       configMap:
         name: app-config
   volumeMounts:
     - name: config
       mountPath: /etc/app/config
   ```

4. **Обновление с перезапуском:**

   ```bash
   kubectl rollout restart deployment/my-app
   ```
