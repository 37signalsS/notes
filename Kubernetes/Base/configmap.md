# ConfigMap в Kubernetes

## Определения

**ConfigMap** — это объект API Kubernetes, предназначенный для хранения неконфиденциальных данных в формате пар «ключ-значение». Он позволяет отделить конфигурацию приложения от его программного кода (**Separation of Concerns**), обеспечивая переносимость (Portability) образов контейнеров между различными окружениями (dev, staging, production) без их пересборки.

**Ключевое правило:** ConfigMap не предназначен для хранения секретов (паролей, токенов, ключей доступа). Для таких данных следует использовать [Secret](./secrets/secrets_basics.md).

## Основные концепции

### Преимущества внешнего управления конфигурацией

*   **Неизменяемость образов:** Один и тот же артефакт (Docker-образ) используется во всех средах, что гарантирует идентичность кодовой базы.
*   **Динамическое управление:** Настройки можно обновлять независимо от жизненного цикла приложения.
*   **GitOps и Config-as-Code:** Все параметры инфраструктуры версионируются в Git, обеспечивая прозрачность изменений.
*   **Гибкость доставки:** Данные предоставляются приложению как переменные окружения, аргументы командной строки или файлы.

### Ограничения и лимиты

*   **Размер:** Максимальный размер одного объекта ConfigMap ограничен **1 MiB** (жесткий лимит etcd). Для хранения больших объемов данных рекомендуется использовать `PersistentVolume`.
*   **Типы данных:** 
    *   `data`: Текстовые данные в кодировке UTF-8.
    *   `binaryData`: Бинарные файлы, закодированные в **Base64** (автоматически обрабатываются `kubectl`).
*   **Область видимости:** Ресурс уровня **Namespace**. Поды могут использовать только ConfigMap из своего пространства имен.
*   **Порядок создания:** ConfigMap **должен существовать до старта пода**, который ссылается на него (иначе `kubelet` откатит под). Исключение — флаг `optional: true`, позволяющий контейнеру запуститься без наличия указанного ключа.
*   **Passive-объект (нет контроллера):** ConfigMap не имеет собственного контроллера и «валяется» в кластере как глупое хранилище. Изменение данных в ConfigMap **не приводит к автоматическому перезапуску** зависимых подов — за это отвечает оркестратор версий (Kustomize с хешем, Helm-checksum) или ручной `rollout restart`.

### Структура объекта

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-settings
data:
  LOG_LEVEL: "DEBUG"
  config.yaml: |
    database:
      host: "db.local"
binaryData:
  favicon.ico: "iVBORw0KGgoAAAANSUh..."
```

## Практические сценарии

### Быстрый старт: сквозной пример

Ниже — минимальный целостный пример: один ConfigMap, значения которого потребляются приложением **двумя способами одновременно** — как переменные окружения и как смонтированный файл.

**1. Манифест ConfigMap:**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-settings
  namespace: backend
data:
  LOG_LEVEL: "info"          # ключ-значение, доступное как переменная окружения
  APP_MODE: "production"
  config.yaml: |             # многострочное значение, доступное как файл
    database:
      host: "db.internal"
      port: 5432
```

**2. Deployment, потребляющий этот ConfigMap:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-server
  namespace: backend
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api-server
  template:
    metadata:
      labels:
        app: api-server
    spec:
      containers:
      - name: app
        image: registry/example/api:1.0
        # Способ 1: отдельные ключи как переменные окружения
        env:
        - name: LOG_LEVEL
          valueFrom:
            configMapKeyRef:
              name: app-settings
              key: LOG_LEVEL
              optional: false
        # Способ 2: все ключи сразу (имена ключей = имена переменных)
        envFrom:
        - configMapRef:
            name: app-settings
        # Способ 3: монтирование значения как файла
        volumeMounts:
        - name: app-config
          mountPath: /app/config
          readOnly: true
      volumes:
      - name: app-config
        configMap:
          name: app-settings
          defaultMode: 0444   # файлы доступны только на чтение
```

**Применение и проверка (Validation):**

```bash
kubectl apply -f configmap.yaml -f deployment.yaml

# Проверка: под стал Ready, переменные и файл на месте
kubectl get pods -n backend          # → READY 1/1
kubectl exec deploy/api-server -n backend -- env | grep -E "LOG_LEVEL|APP_MODE"
# → LOG_LEVEL=info
# → APP_MODE=production
kubectl exec deploy/api-server -n backend -- cat /app/config/config.yaml
# → database:
#   host: "db.internal"
#   port: 5432
```

Развёрнутые варианты (генерация через Kustomize, Helm, бинарные данные) — в разделе детальных руководств ниже и в [Создание ConfigMap](./ConfigMap/creation.md).

### Способы подключения и обновления

| Метод | Особенности | Обновление «на лету» (Hot Reload) |
| :--- | :--- | :--- |
| **Переменные окружения** | Через `env` или `envFrom`. Просты в использовании. | **Нет** (требуется рестарт пода) |
| **Смонтированные тома** | ConfigMap монтируется как директория с файлами. | **Да** (через ~60–90 секунд) |
| **subPath монтирование** | Позволяет монтировать файл в существующую папку. | **Нет** (файл не обновится без рестарта) |

### Механизм атомарного обновления (Atomic Symlink Swap)

При монтировании как тома `kubelet` использует систему символических ссылок:
1. Создается новая директория с данными.
2. Ссылка `..data` атомарно переключается на новую директорию.
Это гарантирует, что приложение не прочитает файл в промежуточном состоянии.

**Внимание к `subPath`:** если вы смонтировали одиночный файл через `subPath`, **атомарный симлинк-обмен не срабатывает** — файл монтируется по конкретному пути как связка, и после обновления ConfigMap содержимое **не обновится** без пересоздания пода. Это самый частый источник путаницы: «изменил ConfigMap, файл в контейнере старый». Для горячего обновления монтируйте **директорию целиком**, а не файл через `subPath`.

### Что происходит при изменении ConfigMap

Поведение зависит от способа потребления данных:

| Способ | Сразу после изменения объекта | Требуется ли перезапуск |
| :--- | :--- | :--- |
| **Переменные окружения** (`env`/`envFrom`) | Внутри пода остаются **старые** значения. Переменные фиксируются при старте контейнера. | **Да** — `kubectl rollout restart` |
| **Смонтированные тома** | Файлы обновляются kubelet **асинхронно** (обычно ~60–90 секунд) без остановки пода. | **Нет**, но приложение должно уметь перечитать файл конфигурации |
| **subPath** | Файл **не** обновляется. | **Да** — пересоздание пода |

Практическое правило: ConfigMap с данными для окружения (env) в большинстве случаев семантически **иммутабелен** после деплоя — обновление требует нового rollout. Для часто меняющихся приложений используйте том+периодическое перечитывание файла либо внешний конфиг-сервис. Подробнее стратегии — в [Обновление и перезапуск](./ConfigMap/update_and_rollout.md).

### Флаг необязательности (Optional)

Параметр `optional: true` позволяет поду успешно запуститься, даже если ConfigMap или указанный ключ отсутствуют. По умолчанию этот флаг равен `false`, и отсутствие ресурса приведет к ошибке `CreateContainerConfigError`.

### Взаимодействие с Native Sidecars (v1.29+)

Нативные sidecar-контейнеры (init-контейнеры с `restartPolicy: Always`) могут использовать ConfigMap для настройки прокси или агентов. Они запускаются первыми, поэтому ConfigMap должен существовать до старта пода.

## Безопасность и производительность

### Контроллер NodeRestriction

 Admission-контроллер **NodeRestriction** ограничивает доступ `kubelet` только к тем ConfigMap и Secret, которые используются подами, запущенными на конкретном узле, снижая радиус поражения при компрометации узла.

### Неизменяемые (Immutable) ConfigMap

Начиная с Kubernetes v1.21, поддерживается поле `immutable: true`. 
**Преимущества:**
1.  **Производительность:** `kubelet` отключает `watch` для этого ресурса, что существенно снижает нагрузку на API-сервер и etcd в больших кластерах.
2.  **Защита:** Предотвращает случайные изменения конфигурации вручную. Обновление происходит через создание нового объекта (паттерн хеширования имен в Helm/Kustomize).

Подробнее см. в разделе **[Неизменяемые ConfigMap](./ConfigMap/immutable.md)**.

### Диагностика типовых проблем

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `CreateContainerConfigError` | Ссылка на несуществующий ключ/ConfigMap при `optional: false` | Проверить существование объекта и имя ключа: `kubectl get configmap`, `kubectl get configmap <name> -o yaml`. Если ключ действительно необязателен — поставить `optional: true`. |
| `FailedMount` | Том не смонтирован, ConfigMap не создан или удалён | Проверить события пода и наличие ConfigMap в том же Namespace. |
| Смонтированный файл не обновился | Монтирование через `subPath` (симлинк-обмен не работает) | Монтировать директорию целиком либо перезапустить под. |
| Переменные окружения не изменились | env фиксируются при старте контейнера, ConfigMap не перезапускает поды | Выполнить `kubectl rollout restart deployment/<name>` (или применить хеш-механику из GitOps). |
| Низкая производительность в большом кластере | Много изменяемых ConfigMap удерживают Watch на каждом узле | Использовать `immutable: true` / реже менять объекты, см. [Best Practices](./ConfigMap/best_practices.md). |

### Выбор механизма передачи параметров

При проектировании пода полезно сверяться с этой сводкой, чтобы выбрать подходящий механизм, а не «всё в ConfigMap»:

| Механизм | Что передаёт | Кто хранит | Обновление без рестарта | Когда использовать |
| :--- | :--- | :--- | :--- | :--- |
| **ConfigMap** | Неконфиденциальные параметры (строки/файлы) | Объект K8s в Namespace | Для томов — да; для env — нет | Конфигурация приложения, версии, отдельные параметры |
| **Secret** | Конфиденциальные данные (пароли, токены, ключи) | Объект K8s в Namespace | Для томов — да; для env — нет | Учётные данные, сертификаты |
| **Downward API** | Метаданные пода/контейнера (имя, namespace, IP, labels/annotations) | Генерируется из пода | Нет | Приложениям нужны собственные метаданные |
| **Arguments/Env в манифесте** | Жёстко заданные параметры пода | В манифесте | Нет | Редко меняющиеся значения конкретного пода |
