# ConfigMap

## Определения

**ConfigMap** — это объект **API (Application Programming Interface)** в Kubernetes, который позволяет хранить неконфиденциальные конфигурационные данные в виде пар «ключ-значение». Его главная задача — отделить конфигурацию от кода приложения (**Separation of Concerns**), что делает приложения переносимыми и легко настраиваемыми для разных окружений: **dev (development)**, **staging**, **prod (production)** без необходимости пересборки Docker-образа.

**Ключевое правило:** используйте ConfigMap только для открытых настроек. Для конфиденциальных данных (пароли, токены, ключи доступа) необходимо использовать [Secret](./secrets/secrets_basics.md).

## Основные концепции

### Проблема встраивания конфигурации в образ

Традиционный подход с копированием конфигурации в Docker-образ на этапе сборки (`COPY config.conf /etc/app/`) имеет критические недостатки:

* **Необходимость пересборки образа** при любом изменении конфигурации.
* **Невозможность использования одного образа** в разных окружениях.
* **Усложнение поддержки** в архитектурах с множеством микросервисов.

### Преимущества ConfigMap

* **Обновление конфигурации без пересборки образа** — изменения применяются при следующем запуске пода или обновлении тома.
* **Единый образ для всех окружений** — конфигурация варьируется через внешние объекты ConfigMap.
* **Централизованное управление** — все настройки хранятся в стандартных ресурсах Kubernetes.
* **Обновление на лету** — при использовании через тома (**volumes**) файлы в контейнере обновляются автоматически.
* **Разделение ответственности** — разработчики управляют кодом, системные инженеры — параметрами среды.

### Ограничения ConfigMap

* **Максимальный размер:** 1 **MiB (Mebibyte)**.
* **Типы данных:** строки в кодировке UTF-8 (поле `data`) или бинарные данные (поле `binaryData`).
* **Безопасность:** данные хранятся в открытом виде (в etcd они могут быть зашифрованы, но API возвращает их в открытом виде).
* **Назначение:** не предназначен для хранения секретов.

### Структура объекта

В отличие от большинства объектов Kubernetes, у ConfigMap отсутствует поле `spec`. Вместо него используются поля `data` и `binaryData`:

* **`data`** — текстовые пары ключ-значение.
* **`binaryData`** — бинарные данные, закодированные в **Base64**.
* Поля могут использоваться одновременно в одном объекте.

**Пример структуры:**

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: game-config
data:
  # Простая переменная
  player_initial_lives: "3"
  # Файл конфигурации как значение
  game.properties: |
    enemy=dragon
    level=10
  ui.properties: |
    color.good=purple
    color.bad=yellow
binaryData:
  logo.png: "iVBORw0KGgoAAAANSUhEUg..."
```

### Способы использования в подах

| Способ | Возможность обновления | Рекомендация к использованию |
| :--- | :--- | :--- |
| **Переменные окружения** (`env`, `envFrom`) | Требуется перезапуск пода | Простые флаги, параметры запуска |
| **Тома** (`volume`) | Автоматически (с задержкой) | Конфигурационные файлы |
| **subPath** | Требуется перезапуск пода | Монтирование одного файла в существующую директорию |
| **Projected volume** | Автоматически | Комбинация нескольких источников данных |

## Практические сценарии

### Основные операции управления

1. **Создание ресурса:** рекомендуется использовать декларативный подход через YAML-манифесты.
   ```bash
   kubectl apply -f configmap.yaml
   ```
   Подробности в разделе: [Создание ConfigMap](./ConfigMap/creation.md)

2. **Подключение к поду:** монтирование данных как файлов или передача через переменные окружения.
   ```yaml
   # Пример монтирования тома
   volumes:
     - name: config-volume
       configMap:
         name: app-config
   ```
   Подробности в разделе: [Использование ConfigMap в подах](./ConfigMap/pod_usage.md)

3. **Обновление данных:** при изменении содержимого ConfigMap изменения в смонтированных томах синхронизируются автоматически (кроме использования `subPath`).
   Подробности в разделе: [Обновление и перезапуск](./ConfigMap/update_and_rollout.md)
