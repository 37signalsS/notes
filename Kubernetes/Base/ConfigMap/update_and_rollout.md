# Обновление и плавный перезапуск (Rollout) ConfigMap

## Определения

**Обновление ConfigMap** — процесс внесения изменений в данные объекта ConfigMap через Kubernetes API. Эффект от обновления зависит от способа потребления данных (тома или переменные окружения) и архитектуры приложения.

**Плавный перезапуск (Rollout Restart)** — управляемый процесс последовательного пересоздания подов (Pods) контроллером (Deployment, StatefulSet, DaemonSet), используемый для принудительного применения новой конфигурации.

**Задержка распространения (Propagation Delay)** — временной интервал между обновлением ресурса в API и фактическим обновлением файлов на файловой системе пода (обычно до 60–90 секунд).

**Горячая перезагрузка (Hot Reload)** — способность приложения перечитывать конфигурационные файлы без перезапуска основного процесса, часто реализуемая через отслеживание событий файловой системы (`inotify`) или получение внешнего сигнала (SIGHUP, HTTP-запрос).

## Основные концепции

### Механизм синхронизации Kubelet

Синхронизация данных ConfigMap на узлах выполняется процессом `kubelet`. По умолчанию используется стратегия **Watch**, которая обеспечивает быструю доставку изменений от API-сервера к узлу. Однако фактическое обновление файлов на диске происходит во время периодического цикла синхронизации подов (по умолчанию каждые 60 секунд).

**Зависимость обновления от способа подключения:**

| Способ подключения | Автоматическое обновление файла/переменной | Требуемое действие для применения |
| :--- | :--- | :--- |
| **Тома (Volumes)** | **Да** (через симлинки) | Hot Reload приложения ИЛИ перезапуск. |
| **Переменные окружения** | **Нет** | Полный перезапуск пода. |
| **subPath монтирование** | **Нет** | Полный перезапуск пода. |

> **Примечание:** Эти же механизмы и ограничения применимы к объектам **Secret**.

### Атомарность обновления через символические ссылки

Kubernetes гарантирует атомарность обновления данных в томах. При изменении ConfigMap `kubelet` не перезаписывает файлы напрямую, а использует механизм символических ссылок:
1. Создается новая директория с актуальными данными (например, `..2024_08_05_12_00_00.123456789`).
2. Символическая ссылка `..data` атомарно переключается на новую директорию.
3. Это гарантирует, что приложение не прочитает файл в промежуточном или поврежденном состоянии.

## Практические сценарии

### Паттерн нативного Sidecar-перезагрузчика (K8s 1.29+)

С введением нативных Sidecar-контейнеров (стабильны в v1.33) реализация автоматической перезагрузки стала более надежной. Sidecar запускается как `initContainer` с `restartPolicy: Always`.

```yaml
spec:
  shareProcessNamespace: true # Позволяет sidecar-у посылать сигналы приложению (SIGHUP)
  initContainers:
  - name: config-reloader
    image: jimmidyson/configmap-reload:v0.11.1
    restartPolicy: Always
    args:
    - "--volume-dir=/config"
    - "--webhook-url=http://localhost:8080/-/reload" # Вызов эндпоинта приложения
    # - "--signal=SIGHUP" # Альтернатива: отправка сигнала процессу
    volumeMounts:
    - name: app-config
      mountPath: /config
  containers:
  - name: main-app
    image: my-app:2.0.0
```

### Автоматический перезапуск через хеширование (GitOps)

В подходах GitOps (ArgoCD, Flux) или при использовании Helm стандартной практикой является внедрение контрольной суммы (checksum) конфигурации в аннотации шаблона пода. Изменение аннотации инициирует стандартный **Rolling Update**.

**Пример для Helm:**
```yaml
kind: Deployment
spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
```

**При использовании Kustomize:**
Использование `configMapGenerator` автоматически добавляет хеш к имени ConfigMap (например, `app-config-f7h8z9`). Изменение данных создает новый ресурс, что обновляет спецификацию пода и гарантирует автоматический перезапуск.

### Ручное управление жизненным циклом (kubectl rollout)

Для управления процессом обновления и отката конфигураций используются императивные команды:

```bash
# Плавный перезапуск без простоя (Deployment, StatefulSet, DaemonSet)
kubectl rollout restart deployment/my-service

# Просмотр истории изменений
kubectl rollout history deployment/my-service

# Откат к предыдущей версии (если используется версионирование имен или ReplicaSet)
kubectl rollout undo deployment/my-service
```

## Дополнительная информация

### Выбор стратегии обновления конфигурации

*   **Hot Reload:** Рекомендуется для высоконагруженных систем (Prometheus, Nginx, Envoy), где недопустим кратковременный перезапуск. Требует поддержки `inotify` или HTTP-эндпоинта `/reload` в приложении.
*   **Rolling Update (Restart):** Самый надежный способ для приложений, использующих переменные окружения или не умеющих перечитывать конфиги. Гарантирует проверку `Readiness Probe` перед удалением старой версии.
*   **API Informer (Advanced):** Для критических приложений с жестким требованием к задержке (<1с) рекомендуется использовать `client-go` и механизм `Watch` напрямую из кода приложения, минуя файловую систему и задержки `kubelet`.

### Ограничения и риски при обновлении

*   **Задержка Kubelet:** Помните о стандартной задержке в 60–90 секунд при использовании томов. Не полагайтесь на мгновенное обновление.
*   **Невалидная конфигурация:** При Hot Reload некорректный конфиг может привести к тому, что приложение продолжит работать со старыми данными, но выдаст ошибку в логах. Рекомендуется использовать валидацию (например, `config-validator`) на этапе CI.
*   **Ресурсный пик:** При Rolling Update кратковременно запускается больше подов, чем обычно (согласно `maxSurge`). Убедитесь в наличии свободных ресурсов и квот.
*   **Immutable ConfigMap:** Если ConfigMap помечен как `immutable: true`, его обновление невозможно. Для изменения конфигурации необходимо создать новый ресурс с новым именем.
