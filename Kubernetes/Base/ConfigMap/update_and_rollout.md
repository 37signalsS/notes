# Обновление и Rollout ConfigMap

## Определения

**Обновление ConfigMap** — процесс внесения изменений в данные объекта ConfigMap через Kubernetes API. Эффект от обновления зависит от способа потребления данных (тома или переменные окружения) и архитектуры приложения.

**Rollout Restart** — управляемый процесс последовательного перезапуска подов (Pods) контроллером (Deployment, StatefulSet), используемый для принудительного применения новой конфигурации.

**Propagation Delay (Задержка распространения)** — временной интервал между обновлением ресурса в API и фактическим обновлением файлов на файловой системе пода.

## Основные концепции

### Механизм синхронизации Kubelet

Синхронизация данных ConfigMap на узлах выполняется процессом `kubelet`. По умолчанию используется стратегия **Watch**, которая обеспечивает быструю доставку изменений, однако фактическое обновление файлов на диске происходит во время периодического цикла синхронизации подов (по умолчанию каждые 60 секунд).

**Зависимость обновления от способа подключения:**

| Способ подключения | Автоматическое обновление файла/переменной | Требуемое действие для применения |
| :--- | :--- | :--- |
| **Тома (Volumes)** | **Да** (через симлинки) | Hot Reload приложения ИЛИ перезапуск. |
| **Переменные окружения** | **Нет** | Полный перезапуск пода. |
| **subPath монтирование** | **Нет** | Полный перезапуск пода. |

### Атомарность обновления через симлинки

Kubernetes гарантирует атомарность обновления данных в томах. При изменении ConfigMap `kubelet` не перезаписывает файлы напрямую, а использует механизм символических ссылок:
1. Создается новая директория с актуальными данными.
2. Символическая ссылка `..data` переключается на новую директорию.
3. Это гарантирует, что приложение не прочитает файл в промежуточном (битом) состоянии.

## Практические сценарии

### Паттерн Native Sidecar Reloader (K8s 1.29+)

С введением нативных Sidecar-контейнеров (стабильны в v1.33) реализация автоматической перезагрузки стала более надежной. Sidecar запускается как `initContainer` с `restartPolicy: Always`.

```yaml
spec:
  shareProcessNamespace: true # Позволяет sidecar-у посылать сигналы приложению
  initContainers:
  - name: config-reloader
    image: jimmidyson/configmap-reload:v0.11.1
    restartPolicy: Always
    args:
    - "--volume-dir=/config"
    - "--webhook-url=http://localhost:8080/-/reload" # Или сигнализация через PID
    volumeMounts:
    - name: app-config
      mountPath: /config
  containers:
  - name: main-app
    image: my-app:2.0.0
```

### Автоматический Rollout через хеширование (GitOps)

В подходах GitOps (ArgoCD, Flux) или при использовании Helm стандартной практикой является внедрение контрольной суммы (checksum) конфигурации в аннотации пода. Изменение аннотации инициирует **Rolling Update**.

**Пример для Helm:**
```yaml
kind: Deployment
spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
```

**При использовании Kustomize:**
Использование `configMapGenerator` автоматически добавляет хеш к имени ConfigMap (например, `app-config-f7h8z9`). Это меняет спецификацию пода при каждом обновлении данных, гарантируя автоматический перезапуск.

### Ручное управление (kubectl rollout)

Если автоматизация не настроена, используется императивная команда для безопасного перезапуска:

```bash
# Плавный перезапуск без простоя
kubectl rollout restart deployment/my-service

# Откат к предыдущей версии конфигурации (если используется версионирование имен)
kubectl rollout undo deployment/my-service
```

## Дополнительная информация

### Выбор стратегии обновления

*   **Hot Reload:** рекомендуется для высоконагруженных систем (Prometheus, Nginx, Envoy), где недопустим даже кратковременный перезапуск. Требует поддержки `inotify` или HTTP-эндпоинта `/reload` в приложении.
*   **Rolling Update (Restart):** самый надежный способ для приложений, использующих переменные окружения или не умеющих перечитывать конфиги. Гарантирует проверку `Readiness Probe` перед удалением старой версии.
*   **API Informer (Advanced):** для критических приложений с требованием задержки обновления <1с рекомендуется использовать `client-go` и механизм `Watch` напрямую из кода приложения, минуя файловую систему Kubelet.

### Ограничения и риски

*   **Задержка Kubelet:** помните о стандартной задержке в 60-90 секунд при использовании томов.
*   **Невалидный конфиг:** при Hot Reload невалидный конфиг может привести к тому, что приложение продолжит работать со старыми данными, но выдаст ошибку в логах. Всегда используйте валидацию (например, `config-validator` в CI).
*   **Ресурсный пик:** при Rolling Update кратковременно запускается больше подов, чем обычно. Убедитесь в наличии свободных ресурсов (Quota/Capacity).
