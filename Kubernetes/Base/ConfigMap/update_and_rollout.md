# Обновление и Rollout ConfigMap

## Определения

**Обновление ConfigMap** — процесс внесения изменений в данные объекта ConfigMap. Влияние этих изменений на работающее приложение зависит от способа подключения (Volume или ENV) и способности приложения к динамическому перечитыванию настроек.

**Rollout restart (перезапуск развёртывания)** — механизм Kubernetes для принудительного и постепенного перезапуска всех подов (Pods) в рамках объекта `Deployment` или `StatefulSet`.

**Hot reload (горячая перезагрузка)** — способность приложения обнаруживать изменения в конфигурационных файлах «на лету» и применять их без завершения основного процесса.

## Основные концепции

### Влияние обновлений на Pod

| Способ подключения | Обновление данных в Pod | Требуемое действие для применения |
| :--- | :--- | :--- |
| **Переменные окружения (`env`, `envFrom`)** | **Никогда** не обновляются автоматически. | Пересоздание Pod (например, через `rollout restart`). |
| **Монтирование томом (`volume`)** | **Автоматически** обновляется через механизм симлинков (задержка до 1 минуты). | Hot reload приложения ИЛИ перезапуск Pod. |
| **Том с `subPath`** | **Никогда** не обновляется автоматически. | Пересоздание Pod (например, через `rollout restart`). |

### Механизм обновления томов (Симлинки)

При использовании ConfigMap в качестве тома, Kubernetes использует механизм символических ссылок для обеспечения атомарности обновления:

1. `kubelet` создаёт в директории тома новую поддиректорию с временной меткой (например, `..2024_01_15_10_30_45`).
2. В эту директорию записываются актуальные файлы из ConfigMap.
3. Специальная симлинка `..data` переключается на новую директорию.
4. Файлы, доступные приложению, являются симлинками на файлы внутри `..data`.

Благодаря этому приложение всегда видит согласованный набор файлов, а не частично записанные данные в процессе обновления.

> **Важно:** при использовании `subPath` файл монтируется напрямую из `..data`, и последующие обновления симлинки `..data` не отслеживаются контейнером.

## Практические сценарии

### Ручной перезапуск (Rollout Restart)

Если приложение не поддерживает Hot reload или используется подключение через переменные окружения, необходимо инициировать перезапуск для применения новых настроек.

```bash
# Перезапуск всех подов Deployment
kubectl rollout restart deployment/my-app
# → deployment.apps/my-app restarted

# Проверка статуса обновления
kubectl rollout status deployment/my-app
# → Waiting for deployment "my-app" rollout to finish...
```

### Автоматический перезапуск через хеш-сумму (Checksum)

Для автоматизации перезапуска при изменении ConfigMap (особенно в подходах GitOps) используется паттерн с аннотацией в шаблоне пода. Изменение аннотации в `spec.template.metadata.annotations` заставляет Kubernetes считать спецификацию пода изменённой, что инициирует Rolling Update (плавное обновление).

**Пример манифеста Deployment:**

```yaml
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    metadata:
      annotations:
        # Хеш-сумма конфигурации. При изменении ConfigMap 
        # хеш изменится, что вызовет автоматический rollout.
        checksum/config: "sha256:5f4dcc3b5aa765d61d..." 
    spec:
      containers:
        - name: app
          image: my-app:1.0.0
          envFrom:
            - configMapRef:
                name: my-config
```

В CI/CD (Continuous Integration / Continuous Deployment) или при использовании Helm (пакетный менеджер Kubernetes) это автоматизируется функцией `sha256sum`.

### Динамическое обновление (Hot Reload)

Если приложение умеет отслеживать события файловой системы (например, через `inotify` в Linux), оно может перечитать конфигурацию без перезапуска.

**Пример на Python с использованием библиотеки watchdog:**

```python
from watchdog.observers import Observer
from watchdog.events import FileSystemEventHandler

class ConfigHandler(FileSystemEventHandler):
    def on_modified(self, event):
        if event.src_path == "/config/settings.yaml":
            print("Config updated! Reloading...")
            reload_settings()
```

## Дополнительная информация

### Сравнение стратегий обновления

| Стратегия | Плюсы | Минусы |
| :--- | :--- | :--- |
| **Hot reload** | Нулевой простой, мгновенное применение изменений. | Сложность реализации логики в коде приложения. |
| **Checksum Rollout** | Высокая надёжность, автоматическая проверка Readiness Probe новой версии. | Временное потребление дополнительных ресурсов при обновлении. |
| **Ручной перезапуск** | Простота реализации, полный контроль со стороны оператора. | Риск задержки реакции, вероятность человеческой ошибки. |
