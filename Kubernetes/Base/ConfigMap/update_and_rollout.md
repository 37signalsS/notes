# Обновление и плавный перезапуск (Rollout) ConfigMap

## Определения

**Обновление ConfigMap** — процесс внесения изменений в данные объекта ConfigMap через Kubernetes API. Эффект от обновления зависит от способа потребления данных (тома или переменные окружения) и архитектуры приложения.

**Плавный перезапуск (Rollout Restart)** — управляемый процесс последовательного пересоздания подов (Pods) контроллером (Deployment, StatefulSet, DaemonSet), используемый для принудительного применения новой конфигурации.

**Задержка распространения (Propagation Delay)** — временной интервал между обновлением ресурса в API и фактическим обновлением файлов на файловой системе пода (обычно до 60–90 секунд).

**Горячая перезагрузка (Hot Reload)** — способность приложения перечитывать конфигурационные файлы без перезапуска основного процесса, часто реализуемая через отслеживание событий файловой системы (`inotify`) или получение внешнего сигнала (SIGHUP, HTTP-запрос).

**Ревизия (Revision)** — неизменяемый снимок шаблона пода (`spec.template`) контроллера, создаваемый при **любом** его изменении, включая только смену аннотаций (например, хеша конфигурации или `kubectl.kubernetes.io/restartedAt`). Для Deployment каждой ревизии соответствует отдельный объект ReplicaSet, количество сохраняемых ревизий ограничено `revisionHistoryLimit` (по умолчанию 10).

**Окно расхождения конфигураций (Config Skew Window)** — временной интервал, в течение которого поды одного приложения работают с разными версиями конфигурации. Возникает потому, что узлы синхронизируют тома независимо (в собственном цикле синхронизации), а пересоздаваемые поды новой ревизии готовностью отличаются от ещё работающих старых.

## Основные концепции

### Механизм синхронизации Kubelet

Синхронизация данных ConfigMap на узлах выполняется процессом `kubelet`. По умолчанию используется стратегия **Watch**, которая обеспечивает быструю доставку изменений от API-сервера к узлу. Однако фактическое обновление файлов на диске происходит во время периодического цикла синхронизации подов (по умолчанию каждые 60 секунд).

Детали стратегий обнаружения изменений (`Watch`/`Get`/`Cache`), параметров `syncFrequency` и случайного «джиттера» (коэффициент 0.5), дающих суммарную задержку 60–90 секунд, разобраны в разделе «Детали механизма синхронизации Kubelet» файла [Способы использования ConfigMap в подах](./pod_usage.md). Здесь важен вывод для планирования: **нагрузка на задержку 60–90 секунд — это нижняя граница, а не точная величина**, реальное время зависит от узла, стратегии и «джиттера».

**Зависимость обновления от способа подключения:**

| Способ подключения | Автоматическое обновление файла/переменной | Требуемое действие для применения |
| :--- | :--- | :--- |
| **Тома (Volumes)** | **Да** (через симлинки) | Hot Reload приложения ИЛИ перезапуск. |
| **Переменные окружения** | **Нет** | Полный перезапуск пода. |
| **Аргументы командной строки (`$(VAR)`)** | **Нет** | Полный перезапуск пода. |
| **subPath монтирование** | **Нет** | Полный перезапуск пода. |

> **Примечание:** Эти же механизмы и ограничения применимы к объектам **Secret**.

### Почему изменение ConfigMap не запускает Rollout автоматически

Kubernetes инициирует новый rollout контроллера (Deployment, StatefulSet, DaemonSet) только при изменении `spec.template` пода. Содержимое ConfigMap в шаблонах **не** дублируется — под ссылается на объект по имени (`volume.configMap.name`, `configMapKeyRef`). Поэтому правка данных в уже существующем объекте не затрагивает шаблон пода: **новая ревизия не создаётся**, поды продолжают работать со старой конфигурацией до тех пор, пока не произойдёт одно из осознанных действий:

*   том + приложение с Hot Reload — обновятся файлы на диске (через симлинки);
*   `kubectl rollout restart` или смена аннотаций/имён (checksum, Kustomize-хеш, Reloader) — поды пересоздаются;
*   пересоздание по иной причине (выкат образа, выселение, краш-цикл) — поды стартуют с актуальными данными.

Именно отсутствие встроенного «рестарта при изменении конфигурации» является первопричиной всех паттернов, описанных в «Практических сценариях».

### Полная задержка применения конфигурации

Детали механизма атомарного обновления через символические ссылки (..data) и их влияние на Hot Reload разобраны в [Способы использования ConfigMap в подах](./pod_usage.md). Здесь важен вывод для планирования: **нагрузка на задержку 60–90 секунд — это нижняя граница, а не точная величина**, реальное время зависит от узла, стратегии и «джиттера».

Практическая метрика «сколько времени пройдёт до вступления конфигурации в силу» для томов складывается из независимых источников задержки:

1.  Запись данных в API-сервер (мгновенно после `kubectl apply`).
2.  Цикл синхронизации `kubelet` на конкретном узле (60–90 с: `syncFrequency` 60 с + «джиттер»).
3.  При стратегии обнаружения `Cache` — дополнительный `cacheTTL` (по умолчанию 1 минута).
4.  Обнаружение изменения приложением: событие `inotify` или интервал опроса файла (polling). Для последнего добавьте интервал опроса к суммарной задержке.
5.  Время перечитывания/инициализации конфигурации в приложении.
6.  При пересоздании подов (env, rollout) — дополнительно время готовности новой волны (Readiness Probe) и `terminationGracePeriodSeconds` старой волны.

Для **переменных окружения** задержка доступа определяется целиком моментом создания пода: если поды пересозданы, значения новы; если не пересозданы — их обновления ещё не произошло («запекание» в шаблон).

### Синхронность обновления и окно расхождения

Поскольку узлы и поды обновляются независимо, кластер в переходный период работает в состоянии **Config Skew Window**: часть подов применяет новую конфигурацию, часть ещё использует старую. Это штатное поведение, но оно предъявляет требования к самим конфигурациям:

*   **Совместимость формата:** новый формат файла или новые значения должны корректно читаться старыми подами (пока они существуют), иначе часть трафика получит ошибки.
*   **Взаимозависимые параметры:** пары «ключ-значение», которые применяются атомарно в одном ConfigMap, на уровне подов могут «расходиться» во времени между соседними подами.
*   **Наблюдение:** при канареечной раскатке алерты и проверки должны строиться на результатах, а не на факте единовременного применения.

## Практические сценарии

### Паттерн нативного Sidecar-перезагрузчика (K8s 1.29+)

С введением нативных Sidecar-контейнеров (стабильны в v1.33) реализация автоматической перезагрузки стала более надежной. Sidecar запускается как `initContainer` с `restartPolicy: Always`.

```yaml
spec:
  shareProcessNamespace: true # Позволяет sidecar-у посылать сигналы приложению (SIGHUP)
  initContainers:
  - name: config-reloader
    image: jimmidyson/configmap-reload:v0.11.1
    restartPolicy: Always
    args:
    - "--volume-dir=/config"
    - "--webhook-url=http://localhost:8080/-/reload" # Вызов эндпоинта приложения
    # - "--signal=SIGHUP" # Альтернатива: отправка сигнала процессу
    volumeMounts:
    - name: app-config
      mountPath: /config
  containers:
  - name: main-app
    image: my-app:2.0.0
```

Настройка утилиты `configmap-reload`:

*   `--reload-strategy` — `watch` (события файловой системы) или `debounce` (анти-дребезг при волне изменений нескольких файлов);
*   `--watch-interval` (по умолчанию 1 c) — частота опроса, значимая при `--reload-strategy=watch`;
*   `--webhook-url`/`--signal`/`--command` — способ уведомления приложения; `--webhook-url` можно указывать несколько раз.
*   Происхождение образа: версия `v0.11.1` — последняя из оригинальной линии сопровождения (jimmidyson); начиная с `v1.0.0` проект продолжает развиваться как `stakater/configmap-reload`.

**Плюсы паттерна:** не требуется контроллер в кластере; перезагрузка точечная (только при изменении конфигурации); доставка атомарна за счёт симлинков.
**Ограничения:** sidecar и утилита должны быть включены в образ/чарт каждого приложения; передача сигнала требует `shareProcessNamespace` и обработки сигнала приложением.

### Автоматический перезапуск через хеширование (GitOps)

В подходах GitOps (ArgoCD, Flux) или при использовании Helm стандартной практикой является внедрение контрольной суммы (checksum) конфигурации в аннотации шаблона пода. Изменение аннотации инициирует стандартный **Rolling Update**.

**Пример для Helm:**
```yaml
kind: Deployment
spec:
  template:
    metadata:
      annotations:
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
```

**При использовании Kustomize:**
Использование `configMapGenerator` автоматически добавляет хеш к имени ConfigMap (например, `app-config-f7h8z9`). Изменение данных создает новый ресурс, что обновляет спецификацию пода и гарантирует автоматический перезапуск.

**Полный арсенал приёмов** (хеширование каталогов через `Files.Glob`, обработка динамических шаблонов `tpl`, проверка изменений `helm diff`, чувствительность к пробелам, поведение `helm rollback`) — в [Автоматический перезапуск подов (Restart on Change)](../../ToolsUtilities/Helm/templating/scenarios/restart_on_change.md).

**Важный предел статического паттерна:** хеш вычисляется только в момент рендеринга (Helm) или сборки (Kustomize). Правки, внесённые напрямую в кластер (`kubectl edit configmap`), не попадают в Git, а значит не изменят хеш и не вызовут перезапуск — такой дрейф выявляется только diff-инструментами GitOps (см. [Рекомендации](./best_practices.md)).

### Ручное управление жизненным циклом (kubectl rollout)

Для управления процессом обновления и отката конфигураций используются императивные команды:

```bash
# Плавный перезапуск без простоя (Deployment, StatefulSet, DaemonSet)
kubectl rollout restart deployment/my-service
# → deployment.apps/my-service restarted
# В шаблон пода добавляется аннотация kubectl.kubernetes.io/restartedAt=<время>,
# что создает новую ревизию (новый ReplicaSet) и запускает Rolling Update без смены образа.

# Ожидание завершения обновления (обязательно с таймаутом в CI/CD-пайплайне)
kubectl rollout status deployment/my-service --timeout=5m
# → deployment "my-service" successfully rolled out

# Просмотр истории изменений
kubectl rollout history deployment/my-service
# → REVISION  CHANGE-CAUSE (для 2-й ревизии отражается reason обновления, если задан)

# Откат к предыдущей версии (ReplicaSet предыдущего шаблона)
kubectl rollout undo deployment/my-service
kubectl rollout undo deployment/my-service --to-revision=2
```

Ключевые следствия:

*   `rollout restart` применим только к **controllers с шаблоном пода**: Deployment, StatefulSet, DaemonSet. Для `Job`/`CronJob` и отдельного `Pod` механизма rollout нет — пересоздание выполняется `kubectl delete pod <name>` (контроллер воссоздаст под заново, но для Pod без владельца под будет удалён окончательно).
*   **Откат конфигурации:** развёрнутая тема — в [Версионирование, откаты и канареечные выкаты](./best_practices.md).
*   **Приостановка и ступенчатость:** `kubectl rollout pause` / `kubectl rollout resume` и параметры `maxSurge`/`maxUnavailable`, влияние Readiness Probe на завершение волны — механика уровня Deployment, подробно в [Deployment](../../Base/Deployment/index.md), [lifecycle_management](../../Base/Deployment/lifecycle_management.md) и [диагностика зависших rollout](../../Base/Deployment/troubleshooting.md).

### Поэтапная (канареечная) раскатка конфигурации

Мгновенное полное распространение (обычный `apply` + `rollout restart`) применимо к большинству конфигов, но не даёт проверить здоровье до полного переключения. Для критичных настроек применяют поэтапные приёмы:

*   **Партии через лимиты RollingUpdate:** `maxSurge: 1`, `maxUnavailable: 0` уже обеспечивают поочерёдное пересоздание подов с подтверждением Readiness Probe каждой волны (механика — в [Deployment](../../Base/Deployment/index.md)).
*   **Приложения с Hot Reload — «мягкое» распространение:** обновите только объект ConfigMap: тома обновятся на всех подах в пределах окна 60–90 секунд, работающие процессы перечитают их без перезапуска. Поэтапность здесь задаётся самим приложением, поэтому перед полной раскаткой валидируйте конфиг и наблюдайте за пробами.
*   **Канареечный ConfigMap:** отдельный объект (например, `app-config-canary`), на который направляется часть подов; доля увеличивается по мере подтверждения, затем канареечный объект заменяется основным. Управление долями и автоматический анализ метрик (Argo Rollouts, Flagger) описаны в [Прогрессивная доставка в GitOps](../../../GitOps/Concepts/progressive_delivery_gitops.md).
*   **partition у StatefulSet:** `RollingUpdate.partition: N` обновляет только поды с ordinal ≥ N — способ раскатать конфигурацию на одном тестовом узле (см. [StatefulSet](../../Base/StatefulSet/statefulset_overview.md)).
*   **Автоматизация контроллером:** [Reloader](../../ToolsUtilities/reloader/reloader_overview.md) самостоятельно инициирует rollout при изменении ConfigMap/Secret с выбором стратегии, в том числе совместимой с GitOps.

### Применение конфигурации в CI/CD

Типовой пайплайн доставки конфигурации и проверки результата:

```bash
# 1. Применение манифеста и ожидание завершения rollout (ненелевый код выхода при таймауте)
kubectl apply -f configs/ && kubectl rollout status deployment/app --timeout=5m

# 2. Контроль состояния подов (нет CreateContainerConfigError / CrashLoopBackOff)
kubectl get pods -l app=my-app
kubectl get events --sort-by=.lastTimestamp | grep -iE "config|rollout"
# → … Warning FailedMount  …  ConfigMap "config" not found

# 3. Для томов — проверка доставленной версии через симлинк ..data
kubectl exec deploy/app -- cat /etc/config/..data/app.config | head

# 4. Для env — проверка фактических значений в работающем поде
kubectl exec deploy/app -- env | grep ^LOG_LEVEL=
# → LOG_LEVEL=info
```

### Диагностика типовых проблем обновления

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Файлы в томе обновились, но приложение отдаёт старое поведение | Нет Hot Reload, либо файл открыт (старый inode) | Проверить `..data` (см. `pod_usage.md`); дать сигнал/перезапустить под |
| `env`-переменные не обновились после `kubectl edit configmap` | Переменные запекаются при старте контейнера | `kubectl rollout restart deployment/<name>` |
| Поды перезапущены (restartCount растёт), но конфиг старый | Перезапускался контейнер `kubelet`-ом, под в том же окружении | Добиться **пересоздания** пода: `rollout restart`; проверить аннотацию `restartedAt` и возраст ReplicaSet |
| Rollout не завершается, «завис» | Readiness Probe не проходит, `paused: true`, `progressDeadlineSeconds` истёк | Диагностика: [Deployment: устранение неполадок](../../Base/Deployment/troubleshooting.md) |
| `CreateContainerConfigError` | ConfigMap отсутствует или найден с задержкой | Проверить имя/namespace: [configmap_issues](../../Troubleshooting/Common_Errors/CreateContainerConfigError/configmap_issues.md) |
| После удаления ConfigMap под продолжает работать со старыми данными | Локальный кэш на узле; новые поды уже не запустятся | Восстановить объект; поды пересоздаются |
| Новый `immutable: true` объект не обновляется in-place | Неизменяемые объекты не редактируются | Создать новый объект с новым именем и переключить ссылки: [Неизменяемые ConfigMap](./immutable.md) |
| `subPath`-файл не обновляется | subPath отключает симлинк-механизм kubelet | Полный перезапуск пода либо смена способа доставки (см. `pod_usage.md`) |

## Дополнительная информация

### Выбор стратегии обновления конфигурации

*   **Hot Reload:** Рекомендуется для высоконагруженных систем (Prometheus, Nginx, Envoy), где недопустим кратковременный перезапуск. Требует поддержки `inotify` или HTTP-эндпоинта `/reload` в приложении.
*   **Rolling Update (Restart):** Самый надежный способ для приложений, использующих переменные окружения или не умеющих перечитывать конфиги. Гарантирует проверку `Readiness Probe` перед удалением старой версии.
*   **API Informer (Advanced):** Для критических приложений с жестким требованием к задержке (<1с) рекомендуется использовать `client-go` и механизм `Watch` напрямую из кода приложения, минуя файловую систему и задержки `kubelet`.
*   **Checksum / Name Hashing (GitOps):** автоматизация без ручных команд — изменение конфигурации через Git создаёт новую ревизию (Helm `checksum/config`, Kustomize `configMapGenerator`); статичный вариант, применяется только при фактическом рендеринге/применении.
*   **Reloader (контроллер):** автоматическое инициирование rollout при любом изменении ConfigMap/Secret, включая правки прямо в кластере; рекомендации по стратегии `annotations` (совместимость с GitOps) — в [Обзор Reloader](../../ToolsUtilities/reloader/reloader_overview.md) и [Сценарии Reloader](../../ToolsUtilities/reloader/reloader_usage_scenarios.md).

Сводное сравнение инструментов автоматизации перезапуска (Reloader vs Helm Checksum vs Kustomize Hash) приведено в [Обзоре Reloader](../../ToolsUtilities/reloader/reloader_overview.md), построчный обзор влияния изменения конфигурации на перезапуски/пересоздания подов — в [Перезапуск Pod](../../Base/Pod/pod_restarts.md).

### Взаимодействие с PodDisruptionBudget (PDB)

PodDisruptionBudget (PDB) защищает поды от **вынужденного** удаления (eviction) при плановых работах (node drain, обновление кластера). PDB **не блокирует Rolling Update напрямую** — контроллер Deployment при rollout не проверяет PDB.

**Когда PDB становится релевантным:**

| Сценарий | PDB блокирует? | Пояснение |
|---|---|---|
| Обычный `kubectl rollout restart` | **Нет** | Контроллер Deployment создаёт новые поды и удаляет старые без учёта PDB |
| `kubectl drain` + rollout одновременно | **Да** | Drain использует Eviction API, который проверяет PDB |
| Cluster Autoscaler сокращает узлы | **Да** | CA использует Eviction API |
| VPA Updater перезапускает поды | **Да** | VPA использует Eviction API |

**Типичная проблема:** Rollout «зависает» при `kubectl drain`, потому что PDB с `minAvailable: 3` не даёт выселить поды ниже этого лимита.

**Диагностика:**

```bash
# Проверка PDB перед rollout
kubectl get pdb -n production
# → NAME              MIN AVAILABLE   MAX UNAVAILABLE   ALLOWED DISRUPTIONS
# → app-pdb           2               —                 1

# Проверка конкретного PDB
kubectl describe pdb app-pdb -n production
# → Events:
# →   Type    Reason     Age   From               Message
# →   ----    ------     ----  ----               -------
# →   Normal  Allowed    12m   poddisruptionbudget  1 pods are allowed to be disrupted
```

**Рекомендации:**

1. **Согласуйте `maxUnavailable` в Deployment и `minAvailable` в PDB.** Если PDB требует `minAvailable: 3` из 5 подов, `maxUnavailable` не должен превышать 1.
2. **При плановых работах** координируйте rollout и drain: сначала завершите rollout, затем выполняйте drain.
3. **Используйте `unhealthyPodEvictionPolicy: AlwaysAllow`** (K8s 1.30+), чтобы «битые» поды не блокировали drain.
4. **В CI/CD добавьте проверку PDB** перед rollout: `kubectl get pdb -o jsonpath='{.items[*].status.disruptionsAllowed}'` — если 0, rollout может зависнуть.

### Ограничения и риски при обновлении

*   **Задержка Kubelet:** Помните о стандартной задержке в 60–90 секунд при использовании томов. Не полагайтесь на мгновенное обновление.
*   **Невалидная конфигурация:** При Hot Reload некорректный конфиг может привести к тому, что приложение продолжит работать со старыми данными, но выдаст ошибку в логах. Рекомендуется использовать валидацию (например, `config-validator`) на этапе CI.
*   **Ресурсный пик:** При Rolling Update кратковременно запускается больше подов, чем обычно (согласно `maxSurge`). Убедитесь в наличии свободных ресурсов и квот.
*   **Immutable ConfigMap:** Если ConfigMap помечен как `immutable: true`, его обновление невозможно. Для изменения конфигурации необходимо создать новый ресурс с новым именем.
*   **Неодновременность распространения:** Окно расхождения конфигураций (см. «Основные концепции») — новый формат конфигурации должен корректно читаться ещё работающими старыми подами.
*   **Открытые файловые дескрипторы:** Процесс, держащий файл открытым, читает прежний inode до повторного открытия — Hot Reload «не сработает», пока приложение не переоткроет файл.
*   **Лимит аннотаций:** хеш-аннотации корректны и компактны, но общий размер аннотаций ограничен 256 KiB — в аннотацию следует помещать только хеш, а не само содержимое конфигурации.
*   **Статичность checksum-подхода:** изменения, внесённые мимо Git (прямые правки в кластере), не отразятся на хеше и не вызовут перезапуск — требуются diff-контроль GitOps или контроллер на основе событий (Reloader).
