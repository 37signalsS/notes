# Обновление ConfigMap и его влияние на поды

## Определения

**ConfigMap update** — процесс изменения данных в ConfigMap. Поведение при обновлении зависит от способа использования ConfigMap в поде.

**Rolling Update** — механизм постепенного обновления подов в Deployment без простоя приложения.

## Базовые концепции

### Поведение при обновлении ConfigMap

Когда под стартует, он монтирует ConfigMap как volume. Kubernetes обновляет содержимое этого volume автоматически (хоть и с задержкой), однако:

* **Большинство приложений не отслеживают изменения файлов** в смонтированных томах.
* **Переменные окружения** читаются один раз при старте контейнера и никогда не обновляются.
* Даже при обновлении файлов в volume, приложению нужно явно сообщить об изменениях или перезапустить под.

Для гарантированного применения изменений рекомендуется **перезапуск пода**.

### Влияние изменений на работающий Pod

При обновлении данных в ConfigMap (например, замена `LOG_LEVEL: "info"` на `LOG_LEVEL: "debug"`) поведение работающего контейнера без перезагрузки зависит от метода подключения:

*   **Переменные окружения (`env`, `envFrom`)**: Приложение продолжит использовать старое значение (**`info`**). Переменные окружения считываются только в момент старта контейнера и остаются неизменными до его перезапуска.
*   **Монтирование томом (`volume`)**: Файл в файловой системе контейнера **обновится автоматически** (с задержкой до 1 минуты). 
    *   Если приложение поддерживает *Hot Reload* (динамическое перечитывание конфига), оно применит **`debug`** без перезапуска. 
    *   Если приложение читает конфиг только один раз при старте, значение в памяти останется **`info`**, хотя файл на диске уже будет содержать новое значение.
*   **Использование `subPath`**: Файл в контейнере **не обновится**. Kubernetes не поддерживает механизм автоматического обновления (симлинков) для файлов, смонтированных через `subPath`. Приложение всегда будет видеть **`info`**.

### Сравнение способов использования

| Способ использования | Поведение при обновлении ConfigMap | Что нужно делать? |
| :--- | :--- | :--- |
| **Том (`volume`)** | Файлы в смонтированной директории **обновляются автоматически** (с задержкой до минуты). | Приложение должно уметь само перечитывать файлы конфигурации. В противном случае — **перезапуск пода**. |
| **Том с `subPath`** | Файл **НЕ обновляется** автоматически. | Требуется **перезапуск пода**. |
| **Переменные окружения** | Переменные окружения **НЕ обновляются** никогда. | Требуется **перезапуск пода**. |

### Стратегии обновления

| Стратегия | Когда использовать | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **Ручной restart** | Редкие изменения, dev-окружения | Простота | Требует вмешательства |
| **Аннотация с хешем** | Production, GitOps | Автоматизация, надёжность | Требует настройки CI/CD |
| **Пересоздание пода** | Stateful-приложения | Полный контроль | Простой приложения |

## Практические сценарии

### Ручной перезапуск подов

Для принудительного перезапуска подов используйте команду:

```bash
kubectl rollout restart deployment/<deployment-name>
# → deployment.apps/<deployment-name> restarted
```

Подробнее см. в документе [Deployment](../Deployment/index.md).

### Механизм обновления томов (симлинки)

При обновлении ConfigMap Kubernetes создает **новую директорию** с актуальными файлами (содержит временную метку в пути, например `/var/lib/kubelet/pods/.../volumes/kubernetes.io~configmap/.../2025-01-15_10-30-45/`), а затем обновляет символическую ссылку `..data` на эту директорию. Сам Pod при этом продолжает работать, а приложение должно уметь перечитывать изменения (или требуется перезапуск пода).

### Автоматический перезапуск подов при изменении ConfigMap

По умолчанию, при изменении данных в `ConfigMap`, поды, использующие его через переменные окружения или `subPath`, **не обновляются автоматически**. Это требует ручного перезапуска, например, с помощью команды `kubectl rollout restart deployment/my-deployment`.

Чтобы автоматизировать этот процесс, можно использовать "трюк" с аннотацией в шаблоне пода.

#### Принцип работы

Идея состоит в том, чтобы добавить в аннотации шаблона пода (`spec.template.metadata.annotations`) хеш-сумму от данных `ConfigMap`.

1. Вычисляется хеш от содержимого `ConfigMap` (например, `sha256sum`).
2. Этот хеш добавляется как значение аннотации в `Deployment`.
3. При любом изменении в `ConfigMap` его хеш также меняется.
4. Изменение аннотации в шаблоне пода расценивается Kubernetes как изменение спецификации `Deployment`.
5. Kubernetes автоматически запускает `Rolling Update`, создавая новые поды, которые подхватывают обновленный `ConfigMap`.

Этот подход полностью автоматизирует процесс обновления конфигурации и является лучшей практикой при работе с [GitOps](../../../GitOps/GitOps_overview.md) и CI/CD (Continuous Integration / Continuous Deployment).

#### Пример реализации (с Helm)

Подробное описание работы с Helm см. в [Rolling Update on ConfigMap Change](../../ToolsUtilities/Helm/templating/scenarios/restart_on_change.md).

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    metadata:
      annotations:
        # При каждом изменении ConfigMap 'my-config' будет меняться хеш,
        # что вызовет автоматический rollout для Deployment'а.
        checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }}
    spec:
      containers:
      - name: app
        image: myimage:latest
        envFrom:
        - configMapRef:
            name: my-config
```

В данном примере Helm вычисляет `sha256sum` от отрендеренного шаблона `configmap.yaml` и вставляет его в аннотацию.

#### Пример с volumeMounts и sha256sum

Этот более общий пример подходит для любого Deployment, где ConfigMap монтируется как том.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    metadata:
      annotations:
        config-hash: "{{ sha256sum .Values.myConfig }}"
    spec:
      containers:
      - name: app
        image: myimage:latest
        volumeMounts:
        - name: cfg
          mountPath: /app/config
      volumes:
      - name: cfg
        configMap:
          name: my-config
```
