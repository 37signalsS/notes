# Неизменяемые (Immutable) ConfigMap

## Определения

**Immutable ConfigMap** (неизменяемый ConfigMap) — это объект API Kubernetes, в спецификации которого установлен флаг `immutable: true`. После создания такого объекта его данные (`data` и `binaryData`) защищены от изменений на уровне API-сервера.

## Основные концепции

### Технические преимущества (Performance & Scale)

Основная ценность неизменяемых ресурсов заключается в оптимизации работы **Control Plane** и **Kubelet**:

*   **Снятие нагрузки с API-сервера (Watch Reduction):** Для обычных (Mutable) ConfigMap каждый `kubelet` на каждом узле, где запущен под с этим конфигом, поддерживает открытое соединение (Watch) с API-сервером для отслеживания изменений. В кластерах с тысячами подов это создает колоссальную нагрузку.
*   **Закрытие Watch-соединений:** При установке `immutable: true` `kubelet` скачивает конфигурацию один раз и немедленно закрывает соединение. Он "знает", что данные не изменятся, что снижает потребление памяти и CPU на узлах и мастерах.
*   **Защита от дрейфа конфигурации (Configuration Drift):** Исключается возможность внесения изменений "в обход" Git (через `kubectl edit`), что гарантирует соответствие состояния кластера описанию в репозитории.

### Взаимосвязь с GitOps

В современных рабочих процессах (ArgoCD, Flux) неизменяемость неразрывно связана с **хешированием имен** (Name Hashing). Поскольку объект нельзя изменить, каждое обновление конфига — это создание нового объекта (например, `app-config-f7h8z9`). Это автоматически инициирует Rolling Update в Deployment, обеспечивая предсказуемость развертывания.

## Практические сценарии

### Создание неизменяемого ConfigMap

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config-v1
  namespace: production
immutable: true # Флаг неизменяемости
data:
  DB_HOST: "db.example.com"
  LOG_LEVEL: "error"
```

### Использование в Kustomize (Рекомендуемый подход)

Kustomize позволяет автоматизировать процесс создания неизменяемых ресурсов и обновления ссылок на них.

```yaml
# kustomization.yaml
generatorOptions:
  immutable: true # Применяется ко всем генерируемым ресурсам

configMapGenerator:
- name: app-config
  files:
    - configs/app.properties
```

При запуске `kubectl apply -k .` Kustomize создаст ConfigMap с хешем в имени и обновит Deployment, чтобы он указывал на актуальную версию.

### Попытка несанкционированного изменения

При попытке обновить поле `data` или `binaryData` API-сервер вернет ошибку:

```bash
kubectl patch configmap app-config-v1 -p '{"data":{"LOG_LEVEL":"debug"}}'
# → Error from server (BadRequest): error when patching "app-config-v1":
#   cannot modify fields other than 'metadata' for immutable configmap
```

*Примечание: Вы по-прежнему можете изменять `metadata` (labels, annotations).*

## Дополнительная информация

### Сравнение типов ConfigMap

| Характеристика | Изменяемый (Mutable) | Неизменяемый (Immutable) |
| :--- | :--- | :--- |
| **Обновление в поде** | Автоматически (~1 мин для томов) | Требует перезапуска пода |
| **Нагрузка на API** | Высокая (постоянные Watch) | Минимальная (разовое чтение) |
| **Целостность** | Риск рассинхронизации подов | Гарантированная идентичность |
| **Применение** | Разработка, Feature Flags | Production, критическая инфраструктура |

### Стратегии очистки (Garbage Collection)

При использовании хешированных имен в кластере могут накапливаться старые версии ConfigMap.
*   **В ArgoCD/Flux:** Используйте функцию **Pruning**. Она автоматически удаляет ресурсы, которые больше не описаны в Git или на которые нет ссылок.
*   **Ручная очистка:** Требуется осторожность, чтобы не удалить конфиг, используемый подами, которые еще не успели перезапуститься.

### Рекомендации по использованию

*   **Default to Immutable:** Считайте неизменяемость стандартом для всех конфигураций.
*   **Версионирование:** Всегда используйте суффиксы (хеши) в именах, чтобы избежать блокировок при обновлении через GitOps.
*   **Sidecars:** С появлением Sidecar Containers (K8s 1.29+) убедитесь, что их конфигурации также неизменяемы для предотвращения рассинхрона между основным и вспомогательным контейнерами.
*   **Secrets:** Применяйте этот же подход к [Secret](../secrets/secrets_basics.md) для аналогичного прироста производительности.
