# Рекомендации и лучшие практики для ConfigMap

## Определения

**ConfigMap** — объект Kubernetes для хранения неконфиденциальных конфигурационных данных в виде пар «ключ-значение».

## Основные концепции

### Принципы работы с ConfigMap

* **Предпочитайте монтирование через том:** Это позволяет обновлять конфигурацию на лету (если приложение это поддерживает). Это самый гибкий способ, который подробно описан в разделе об [использовании ConfigMap в подах](./pod_usage.md).
* **Удаляйте конфиги из Dockerfile:** При использовании ConfigMap **удалите команду копирования конфигурации** (например, `COPY nginx.conf /etc/nginx/`) из Dockerfile. Конфигурация теперь доставляется через том, а не встраивается в образ. Это ключевое преимущество подхода с ConfigMap — один и тот же образ может использоваться во всех окружениях с различной конфигурацией.
* **Именуйте и версионируйте ConfigMap:** Давайте осмысленные имена (например, `nginx-config-v2`) для предсказуемости развертываний. Это помогает при отладке и в CI/CD пайплайнах.
* **Проверяйте перед применением:** Используйте `kubectl diff -f my-manifest.yaml` для просмотра изменений до их применения в кластере. Это убережет от неожиданных ошибок.
* **Ограничение размера:** Размер одного ConfigMap не должен превышать 1 MiB. Для больших данных рассмотрите использование `PersistentVolume` или хранение данных в артефакт-репозитории.
* **Права доступа:** Управляйте правами на смонтированные файлы через `defaultMode` в `volume` и `securityContext.fsGroup` в поде для повышения безопасности.
* **Бинарные данные:** Для нетекстовых данных используйте поле `binaryData`. Это предотвращает ошибки при обработке данных, которые не являются валидными UTF-8 строками.
* **Используйте неизменяемые (Immutable) ConfigMap:** Для конфигураций, которые не должны меняться в течение жизни приложения, устанавливайте флаг `immutable: true`. Это повышает производительность и предсказуемость системы. См. [Неизменяемые ConfigMap](./immutable.md).
* **Автоматизируйте перезапуск подов:** Чтобы изменения в ConfigMap применялись гарантированно, настройте [автоматический rollout](./update_and_rollout.md) ваших `Deployment` или `StatefulSet`.

## Практические сценарии

### Рекомендации по выбору способа использования

| Сценарий | Рекомендуемый способ | Обоснование |
| :--- | :--- | :--- |
| Конфигурационные файлы | `volume` | Автоматическое обновление, гибкость монтирования |
| Переменные окружения | `env`/`envFrom` | Простота, но требует перезапуска пода |
| Один файл в существующей директории | `subPath` | Не скрывает другие файлы, но не обновляется автоматически |
| Конфигурация из нескольких источников | `projected` | Объединение ConfigMap + Secret + других источников |

Подробное сравнение способов — в документе [использование ConfigMap в подах](./pod_usage.md#сравнение-способов-использования).

### Безопасность и права доступа

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-app
spec:
  securityContext:
    fsGroup: 1000  # Группа для смонтированных файлов
  containers:
    - name: app
      volumeMounts:
        - name: config-volume
          mountPath: /etc/app/config
  volumes:
    - name: config-volume
      configMap:
        name: app-config
        defaultMode: 0640  # Права 640 для всех файлов
```
