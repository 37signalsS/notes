# Рекомендации и лучшие практики для ConfigMap

## Определения

**ConfigMap** — объект API Kubernetes для хранения неконфиденциальных конфигурационных данных. Основная цель — отделение конфигурации от кода приложения (**Separation of Concerns**), что обеспечивает переносимость артефактов и гибкость управления инфраструктурой.

## Основные концепции

### Принципы управления конфигурацией

* **Приоритет неизменяемости (Immutability):** используйте флаг `immutable: true` в сочетании с генераторами имен (например, Kustomize `configMapGenerator`). Это гарантирует предсказуемость состояния системы, упрощает откаты и снижает нагрузку на **API Server**. Подробнее см. [Неизменяемые ConfigMap](./immutable.md).
* **Предпочитайте монтирование через тома (Volumes):** в отличие от переменных окружения (`env`), данные в томах обновляются динамически без перезапуска подов. Это позволяет реализовать стратегии **Hot Reload** для приложений, умеющих перечитывать файлы. Подробнее см. [Использование в подах](./pod_usage.md).
* **Исключение конфигурации из образов:** Docker-образы должны быть неизменяемыми (**Stateless Images**). Все настройки окружения (Dev/Stage/Prod) должны доставляться исключительно через ConfigMap или Secret.
* **Соблюдение лимитов etcd:** размер одного объекта ConfigMap жестко ограничен **1 MiB**. При хранении больших объемов данных (например, сложных ML-моделей или статики) используйте `PersistentVolume` или внешние хранилища.
* **Использование бинарных данных:** для нетекстовых ресурсов (сертификаты, изображения) всегда используйте поле `binaryData`. Это предотвращает порчу данных при обработке UTF-8. Подробнее см. [Создание ConfigMap](./creation.md).

## Практические сценарии

### Жизненный цикл в GitOps

В современных CI/CD процессах (ArgoCD, Flux) рекомендуется использовать паттерн **Rendered Manifests**.

1. **Версионирование через хеширование:** использование уникальных имен (например, `app-config-f7h8z9`) при каждом изменении содержимого.
2. **Автоматизация Rollout:** если приложение использует переменные окружения, внедряйте аннотации с хешем содержимого ConfigMap в шаблон пода (`spec.template.metadata.annotations`). Это заставит Kubernetes выполнить Rolling Update при изменении настроек. Подробнее см. [Обновление и Rollout](./update_and_rollout.md).

### Настройка безопасности и изоляции

ConfigMap не является безопасным хранилищем. Данные в etcd хранятся в открытом виде (если не настроено шифрование ресурсов) и доступны любому пользователю с правами на чтение в пространстве имен.

* **Запрет на хранение секретов:** пароли, токены и ключи должны храниться только в [Secret](../secrets/secrets_basics.md).
* **Принцип наименьших привилегий:** используйте `readOnly: true` при монтировании томов. Устанавливайте строгие права доступа через `defaultMode` (например, `0440`).
* **Изоляция пространств имен:** ConfigMap — это ресурс уровня **Namespace**. Никогда не пытайтесь ссылаться на ConfigMap из другого пространства имен; вместо этого используйте репликацию или общие хранилища.

### Паттерн Sidecar-Reloader

Для приложений, не поддерживающих `inotify`, но требующих обновления без полного рестарта пода (например, Nginx или Prometheus), используйте Sidecar-контейнеры (Native Sidecars, K8s 1.29+).

* **Механизм:** Sidecar отслеживает изменения в томе ConfigMap и посылает сигнал (например, `SIGHUP`) основному процессу.
* **Преимущество:** обновление конфигурации за миллисекунды без прерывания обслуживания трафика.

## Дополнительная информация

### Выбор метода доставки

| Метод | Плюсы | Минусы | Резюме |
| :--- | :--- | :--- | :--- |
| **Volume** | Hot reload, атомарность | Задержка синхронизации (~1 мин) | Стандарт для конфигов |
| **Env** | Простота, мгновенно при старте | Требует рестарта пода | Для флагов и лимитов |
| **subPath** | Монтирование в папку с файлами | Блокирует обновления | Избегать в Prod |
