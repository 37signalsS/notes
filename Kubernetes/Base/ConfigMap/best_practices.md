# Рекомендации и лучшие практики для ConfigMap

## Определения

**ConfigMap** — объект API (Application Programming Interface) Kubernetes для хранения неконфиденциальных конфигурационных данных в виде пар «ключ-значение». Он позволяет отделить конфигурацию от кода приложения, обеспечивая переносимость и гибкость управления настройками.

## Основные концепции

### Принципы работы с ConfigMap

Для эффективного и безопасного управления конфигурациями в Kubernetes рекомендуется придерживаться следующих принципов:

* **Предпочитайте монтирование через тома (Volumes):** это самый гибкий способ, который поддерживает автоматическое обновление файлов в контейнере без перезапуска пода (при условии, что приложение умеет перечитывать конфиги). Подробнее см. [способы использования в подах](./pod_usage.md).
* **Исключайте конфигурацию из образов (Docker-образов):** при использовании ConfigMap **удалите инструкции копирования файлов настроек** (например, `COPY nginx.conf /etc/nginx/`) из Dockerfile. Это позволяет использовать один и тот же неизменяемый образ во всех окружениях (Dev, Staging, Production), меняя только ConfigMap.
* **Именуйте и версионируйте ресурсы:** давайте ConfigMap осмысленные имена (например, `nginx-config-v2`). Это упрощает отслеживание версий конфигурации и обеспечивает надежные откаты.
* **Соблюдайте ограничения размера:** размер одного ConfigMap в хранилище etcd ограничен **1 MiB** (Мегабайт). Для хранения файлов большего размера используйте `PersistentVolume` или артефакт-репозитории.
* **Используйте бинарные данные корректно:** для нетекстовых файлов (логотипы, бинарные конфигурации) используйте поле `binaryData`. Это гарантирует корректную передачу данных, которые могут содержать символы, недопустимые в UTF-8.
* **Применяйте неизменяемые (Immutable) ресурсы:** для стабильных конфигураций устанавливайте флаг `immutable: true`. Это снижает нагрузку на API-сервер (исключается необходимость watch-запросов) и защищает от случайных правок. Подробнее см. [Неизменяемые ConfigMap](./immutable.md).

## Практические сценарии

### Выбор метода доставки конфигурации

При проектировании развертывания важно выбрать правильный метод передачи данных из ConfigMap в приложение.

| Сценарий | Рекомендация | Обоснование |
| :--- | :--- | :--- |
| **Файлы конфигурации** | `volume` | Поддержка автообновления, атомарность изменений. |
| **Параметры запуска / Флаги** | `env` / `envFrom` | Простота реализации, но требует перезапуска пода для применения. |
| **Подмена одного файла** | `subPath` | Не скрывает остальные файлы в директории, но блокирует автообновление. |
| **Объединение источников** | `projected` | Позволяет собрать ConfigMap + Secret + данные API в одну папку. |

Подробное сравнение приведено в документе **[Использование ConfigMap в подах](./pod_usage.md#сравнение-способов-подключения)**.

### Настройка прав доступа и безопасности

Для ограничения доступа процесса внутри контейнера к файлам конфигурации рекомендуется использовать `readOnly` монтирование и специфические права доступа.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: secure-app
spec:
  securityContext:
    # Установка GID для доступа к смонтированным томам
    fsGroup: 1000  
  containers:
    - name: app
      image: my-app:1.2.3
      volumeMounts:
        - name: config-volume
          mountPath: /etc/app/config
          # Защита от записи внутри контейнера
          readOnly: true 
  volumes:
    - name: config-volume
      configMap:
        name: app-config-v2
        # Права 640: владелец (чтение/запись), группа (чтение)
        defaultMode: 0640  
```

## Дополнительная информация

### Проверка перед применением

Перед внесением изменений в Production-среду всегда проверяйте манифесты с помощью команды `kubectl diff`:

```bash
kubectl diff -f configmap-v2.yaml
# → Показывает разницу между текущим объектом в кластере и новым манифестом
```
