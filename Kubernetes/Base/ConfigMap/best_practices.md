# Рекомендации и лучшие практики для ConfigMap

## Определения

**ConfigMap** — объект API Kubernetes для хранения неконфиденциальных конфигурационных данных. Основная цель использования ConfigMap — реализация принципа **Separation of Concerns** (разделение ответственности) путем отделения настроек приложения от его исполняемого кода, что обеспечивает переносимость артефактов между окружениями.

**Best Practices для ConfigMap** — совокупность проверенных в производственной эксплуатации правил проектирования, организации, доставки, защиты и наблюдения за конфигурацией. Их цель — сделать конфигурацию воспроизводимой, версионируемой, предсказуемой и безопасной в масштабе команды, кластера и множества сервисов.

**Границы применимости ConfigMap:**

*   **Конфиденциальные данные** — пароли, токены, ключи, приватные сертификаты. Только [Secret](../secrets/security.md).
*   **Большие и бинарные объемы** — объект ограничен **1 MiB**; крупные конфигурации и артефакты — в `PersistentVolume`, внешнем хранилище или реестре образов.
*   **Данные, изменяемые самим приложением** — запись в смонтированный том не сохраняется в объект; используйте `PersistentVolume`, `emptyDir` или внешние сервисы.

## Основные концепции

### Архитектурные принципы

*   **Приоритет неизменяемости (Immutability):** Рекомендуется использовать флаг `immutable: true` для всех стабильных конфигураций. Это снижает нагрузку на API-сервер (Kubelet перестает отслеживать изменения) и защищает от случайных правок. Подробнее см. [Неизменяемые ConfigMap](./immutable.md).
*   **Исключение настроек из образов:** Docker-образы должны быть **Stateless**. Все параметры, зависящие от окружения (URL БД, уровни логирования), должны доставляться только через внешние ресурсы (ConfigMap/Secret).
*   **Выбор метода доставки:**
    *   **Тома (Volumes):** Стандарт для файлов конфигурации. Поддерживают **Hot Reload** (атомарное обновление через симлинки).
    *   **Переменные окружения (`env`):** Для простых флагов и лимитов. Требуют перезапуска пода при обновлении.
*   **Лимиты etcd:** Помните об ограничении в **1 MiB**. Для хранения больших конфигураций или бинарных файлов используйте специализированные хранилища или `PersistentVolume`.
*   **Один объект — одна ответственность:** Дробите конфигурацию по логическим сущностям (приложение, компонент, слой). Не смешивайте в одном ConfigMap несвязанные настройки разных команд: это усложняет согласование изменений, раздувает Watch-нагрузку и создает риск каскадного влияния на множество потребителей.
*   **Config-as-Code:** Единственный источник истины для конфигурации — Git-репозиторий. Применяйте только декларативные манифесты (Helm, Kustomize, Argo CD, Flux); императивные `kubectl create configmap` используйте лишь для отладки и разовых операций — иначе теряются версионирование, аудит и воспроизводимость.
*   **Fail Fast (провал по умолчанию):** Оставляйте `optional: false` (значение по умолчанию) для конфигураций, необходимых приложению. Отсутствие ConfigMap или ключа должно приводить к ошибке запуска `CreateContainerConfigError`, а не к старту с неполной конфигурацией. `optional: true` — осознанный выбор для действительно необязательных ключей.

### Стандарты именования и маркировки

*   **Использование меток (Labels):** Всегда добавляйте стандартные метки (например, `app.kubernetes.io/name`, `app.kubernetes.io/managed-by`). Это критично для аудита и работы инструментов автоматизации (например, `kor` или `argocd`). Для единообразия применяйте рекомендованный набор меток `app.kubernetes.io/*` (`name`, `instance`, `version`, `component`, `part-of`, `managed-by`): по ним легко выбирать конфигурации (`kubectl get configmap -l app.kubernetes.io/part-of=payment`), управлять ими через GitOps-инструменты и чистить неиспользуемые.
*   **Версионирование (Name Hashing):** При использовании Kustomize или Helm применяйте хеширование имен (например, `app-config-f7h8z9`). Это гарантирует, что изменение конфига приведет к созданию нового объекта и корректному Rolling Update зависимых подов. Механика: Kustomize `configMapGenerator` добавляет суффикс-хеш и автоматически обновляет ссылки в манифестах; Helm — через аннотацию `checksum/config` в шаблоне пода ([Helm: перезапуск при изменении конфига](../../ToolsUtilities/Helm/templating/scenarios/restart_on_change.md)).
*   **Структура имени:** Имя ConfigMap — это DNS-поддомен (RFC 1123), до 253 символов, строчными буквами. Рекомендуемый шаблон — `<приложение>-<компонент>-<роль>` (например, `payment-api-tls-config`). Окружения (dev/stage/prod) разделяйте **Namespaces**, а не суффиксом имени (`app-config-prod` / `app-config-dev` — анти-паттерн): один и тот же манифест применяется в разных Namespaces, а различия вносятся оверлеями GitOps.
*   **Соглашения о ключах:** Используйте осмысленные имена ключей в едином стиле (`nginx.conf`, `LOG_LEVEL`), а не `conf1`/`conf2`. Ключи, передаваемые через `envFrom`, обязаны быть валидными именами переменных окружения — иначе `kubelet` молча пропустит их при запуске пода (детали и защита — в [Использование ConfigMap в поде](./pod_usage.md)).

### Когда не следует использовать ConfigMap

*   **Секреты и приватные данные.** Пароли, токены, API-ключи, приватные сертификаты — только [Secret](../secrets/security.md). ConfigMap доступен всем субъектам с правом чтения Namespace и не шифруется по умолчанию (шифрование хранилища зависит от настроек кластера).
*   **Данные более 1 MiB или требующие записи приложением.** Монтирование выполняется `kubelet` заново на каждый цикл синхронизации, и запись из контейнера в смонтированный том не сохраняется. Используйте `PersistentVolume`, `emptyDir` или базу данных.
*   **Конфигурация с высокой частотой обновлений.** Каждое изменение ConfigMap обновляет файлы во **всех** подах, монтирующих его как том, а при хеш-подходе провоцирует перезапуски. Для динамических настроек (несколько изменений в час и чаще) применяйте внешние конфиг-сервисы или системы feature flag, а не ConfigMap.
*   **Разовые и локальные настройки.** Если конфигурация актуальна только для одного узла или разового запуска — рассмотрите `hostPath`, `emptyDir` и передачу параметров через command/args напрямую.

## Практические сценарии

### Сценарий 1: Управление жизненным циклом через GitOps

В современных CI/CD процессах (ArgoCD, Flux) конфигурация является частью кода.

1.  **Декларативное описание:** Храните ConfigMap в том же репозитории, что и манифесты приложения.
2.  **Автоматизация Rollout:** Для приложений, использующих `env`, внедряйте аннотацию с хешем содержимого ConfigMap в шаблон пода:
    ```yaml
    kind: Deployment
    spec:
      template:
        metadata:
          annotations:
            config-checksum: "${CONFIG_HASH}"
    ```
    Это заставит Kubernetes перезапустить поды сразу после применения нового конфига.
3.  **Валидация в CI перед применением:** Проверяйте манифесты конфигурации в конвейере: структурно (`kubeconform`), по политикам безопасности (`polaris`, `conftest`/OPA), статически (`kubeconform`). Дополнительно прогоняйте `kubectl apply --dry-run=client` и `--dry-run=server`, чтобы выявить ошибки схемы и недостающие права до момента записи объекта.
4.  **Обнаружение дрейфа (Drift):** В Argo CD/Flux используйте diff против репозитория (`argocd app diff`, `flux diff kustomization`), чтобы ручные правки в кластере (например, `kubectl edit configmap`) были обнаружены и приведены к состоянию Git. Для конфигурационных ресурсов можно отключить автосинк и применять изменения вручную после проверки — это добавляет контроль, но требует дисциплины.
5.  **Откат через Git:** При проблеме откатывайте через Git: `git revert` внесенного изменения, затем синхронизация/пересоздание объекта. Для env-конфигураций это сопровождается перезапуском подов; для томов — см. раздел «Версионирование, откаты и канареечные выкаты» ниже.

### Сценарий 2: Многослойная конфигурация

Комбинируйте ConfigMap с другими источниками для повышения гибкости.

*   **Базовые настройки:** Общий ConfigMap для всего кластера/пространства имен.
*   **Специфичные настройки:** ConfigMap конкретного приложения.
*   **Динамические данные:** Использование **Downward API** ([Downward API: метаданные пода](../Pod/downward_api.md)) для передачи метаданных пода (например, имя узла или IP) вместе с конфигами.
*   **Приоритетность:** Секция `env` переопределяет значения из `envFrom`.
*   **Базовый слой и оверлеи (Base + Overlay):** В Kustomize формируйте конфигурацию из базовой директории (общие настройки) и оверлеев окружений (`overlays/dev`, `overlays/prod`), которые точечно изменяют только отличающиеся части. Это устраняет дублирование манифестов между окружениями и гарантирует, что изменение базы автоматически попадает во все среды.
*   **Продвижение между окружениями (Promotion):** Прогоняйте одинаковые манифесты через dev → stage → prod, заменяя только значения параметров. Структура и ключи одного и того же ConfigMap в разных Namespaces идентичны — отличаются лишь значения, что проверяется тестами на согласованность схемы.

### Сценарий 3: Валидация и безопасность

ConfigMap не шифруется по умолчанию и доступен всем в рамках Namespace.

1.  **Запрет на секреты:** Никогда не храните пароли или ключи в ConfigMap. Используйте [Secret](../secrets/security.md).
2.  **Валидация манифестов:** Используйте `kubeconform` или `polaris` в CI-пайплайнах для проверки структуры и соблюдения политик (например, запрет на монтирование без `readOnly: true`).
3.  **Принцип наименьших привилегий:** Монтируйте тома с `readOnly: true` и устанавливайте `defaultMode: 0440`, чтобы предотвратить изменение конфига процессом внутри контейнера. Учитывайте поведение `fsGroup` в Pod Security Context: при его задании владелец файлов тома меняется на указанную группу — проверяйте фактические права внутри контейнера (`kubectl exec <pod> -- ls -la /etc/config`).
4.  **RBAC-сегментация:** ConfigMap — ресурс уровня Namespace. Приложениям достаточно прав `get`/`list`/`watch` на свою конфигурацию; `create`/`update`/`patch`/`delete` предоставляйте только агентам доставки (сервис-аккаунт CI или deploy-инструмента). Чтение ограничивайте списком конкретных имен (`resourceNames`). Образец Role — в [Использование ConfigMap в поде](./pod_usage.md).
5.  **Защита узлов (NodeRestriction):** Admission-контроллер **NodeRestriction** ограничивает доступ `kubelet` только теми ConfigMap/Secret, которые реально используются подами конкретного узла, снижая радиус поражения при компрометации узла.
6.  **Шифрование на уровне хранилища:** Данные ConfigMap размещаются в **etcd**. Если в кластере не включено шифрование хранилища (Encryption at Rest), содержимое читаемо из бэкапов etcd и при компрометации etcd. Для данных, чувствительных на уровне хранения, включайте шифрование хранилища (encryption-provider-config/KMS) или используйте Secret.
7.  **Admission-политики (Policy as Code):** ValidatingAdmissionPolicy или OPA/Gatekeeper позволяют централизованно запретить в Prod-Namespaces: создание не-immutable ConfigMap, монтирование без `readOnly`, отсутствие обязательных меток, наличие ключей с признаками секретов. Так «лучшие практики» внедряются как код и не зависят от дисциплины отдельных команд.

### Сценарий 4: Версионирование, откаты и канареечные выкаты

*   **Связь конфигурации с версией пода:** Хеш-аннотация в шаблоне пода привязывает содержимое ConfigMap к ReplicaSet: новый конфиг = новый ReplicaSet, откат = `kubectl rollout undo`. Для Helm механика описана в [restart_on_change](../../ToolsUtilities/Helm/templating/scenarios/restart_on_change.md).
*   **Откат env-конфигураций:** Значения переменных окружения «запекаются» в шаблон пода в момент его создания. Старые ReplicaSet сохраняют прежнее окружение, поэтому `kubectl rollout undo deployment/<app>` полностью восстанавливает предыдущую конфигурацию (вместе с прежним образом).
*   **Откат volume-конфигураций:** Тома читаются из актуального объекта ConfigMap на каждом цикле синхронизации. Простой `rollout undo` без возврата ConfigMap во Git/кластере **не** восстановит старые файлы: сначала откатите объект, затем выполните `kubectl rollout restart`. Именно поэтому связка «хеш-аннотация» или «immutable + новое имя» дает точечный и предсказуемый откат.
*   **Immutable как версионность:** Для `immutable: true` каждое изменение требует нового объекта с новым именем и обновления ссылок — Kustomize-хеш и Helm-checksum делают это автоматически. Результат: строгая версионная история, мгновенное переключение/откат и защита от случайных правок. Процедура безопасной миграции — в [Неизменяемые ConfigMap](./immutable.md).
*   **Канареечные выкаты (Canary):** Для постепенного раскатывания новой конфигурации создавайте отдельный ConfigMap канарейки (например, `app-config-canary`), направляйте на него часть подов, увеличивая долю по мере подтверждения, либо используйте продвинутую доставку (Argo Rollouts) с автоматическим анализом метрик до полного переключения.
*   **Проверка перед выкатом:** Перед целевым rollout убедитесь, что объект применяется (`kubectl apply --dry-run=server`), после применения не возникает `CreateContainerConfigError`/`FailedMount`, и наблюдайте за пробами (readiness/liveness) в течение окна синхронизации 60–90 секунд.

### Сценарий 5: Производительность и масштабирование

*   **Immutable как бюджет нагрузки:** `immutable: true` переводит `kubelet` в режим одноразового чтения (GET) вместо постоянного Watch, пропорционально снижая нагрузку на API-сервер и etcd в крупных кластерах. Все стабильные конфигурации должны быть неизменяемыми.
*   **Контроль числа мутабельных объектов:** Каждый изменяемый ConfigMap, используемый подами, удерживается в Watch на каждом узле, где расположены эти поды. Накопление сотен мелких изменяемых объектов заметно грузит API-сервер и etcd. Редко меняющиеся настройки группируйте в меньшее число объектов; часто меняющиеся — выносите за пределы ConfigMap (см. «Границы применимости»).
*   **Стратегии получения данных Kubelet:** При нестабильной сети или очень большом кластере можете перевести поды на стратегии `Get`/`Cache` вместо Watch по умолчанию: в обмен на увеличение задержки обновления вы снижаете нагрузку и количество ошибок синхронизации. Детали и параметры — в [Использование ConfigMap в поде](./pod_usage.md).
*   **Мониторинг конфигурации:** Настройте алерты на удаление критических ConfigMap (через `kube_configmap_created`), контролируйте успешность перезагрузок (метрики sidecar-reloader, например `configmap_reload_success_total`) и дифф конфигурации в GitOps-конвейере. Примеры выражений, включая причину непригодности `kube_configmap_info` для `changes()`, — в [Использование ConfigMap в поде](./pod_usage.md).
*   **Очистка неиспользуемых ConfigMap:** Включайте периодическую чистку: `kor` (сканирует неиспользуемые ресурсы Kubernetes) и CronJob для удаления устаревших immutable-версий с хеш-суффиксами. Рабочий пример такого Job — в [Неизменяемые ConfigMap](./immutable.md).

## Дополнительная информация

### Анти-паттерны ConfigMap

| Анти-паттерн | Почему это плохо | Рекомендация |
| :--- | :--- | :--- |
| **Секреты в ConfigMap** | данные читаемы всем с доступом к Namespace, не шифруются по умолчанию | [Secret](../secrets/security.md) |
| **Один ConfigMap «на всё»** | каскадные изменения, конфликты владельцев, раздувание Watch | дробить по сущностям |
| **Императивное создание в Prod** (`kubectl create configmap`) | нет версионирования, аудита, воспроизводимости | Config-as-Code + GitOps |
| **`subPath` для обновляемых данных** | файл перестает обновляться без перезапуска пода | том без `subPath` |
| **Полагаться на env для Hot Reload** | переменные окружения не перечитываются | тома + Hot Reload или перезапуск |
| **Ручные хеши/даты в имени** (`config-20240101`) | расходы на поддержку, дублирование объектов | Kustomize `configMapGenerator` / Helm checksum |
| **`immutable` для часто меняющихся конфигов** | каждое изменение = новый объект и пересоздание подов | внешний конфиг-сервис или feature flag |
| **`envFrom` из большого агрегата** | шум в окружении, молча пропускаемые невалидные ключи | явный `env` для критичных переменных |
| **Отсутствие меток** | невозможно выбрать, автоматизировать, чистить | стандартные `app.kubernetes.io/*` |
| **Ручное редактирование в кластере** | дрейф от Git, потерянный откат | GitOps + Diff/Drift-контроль |
| **Монтирование без `readOnly`** | процессы могут изменять файлы конфигурации, маскируя расхождения | `readOnly: true` + `defaultMode: 0440` |
| **Хранение больших бинарников** | превышение 1 MiB, нагрузка на etcd | `PersistentVolume`, реестр артефактов |

### Чек-лист внедрения ConfigMap (Production)

*   **Именование и метаданные:** имя — валидный DNS-поддомен; метки `app.kubernetes.io/*` и `managed-by` проставлены; аннотация/описание объясняет назначение.
*   **Содержимое:** только неконфиденциальные данные; ключи документированы и валидны для `envFrom`; размер менее 1 MiB.
*   **Доставка:** файлы — тома (`readOnly: true`, `defaultMode`), флаги — `env`; `optional` проставлен осознанно; критичные переменные — явный `env`, а не `envFrom`-агрегат.
*   **Жизненный цикл:** Config-as-Code в Git; CI-валидация (`kubeconform`, `polaris`, `conftest`); аннотация-хеш (Helm/Kustomize); `immutable: true` для стабильных.
*   **Безопасность:** RBAC: приложения — только чтение, деплой-агент — запись; NodeRestriction включен; шифрование хранилища (Encryption at Rest) там, где это важно; admission-политики в Prod.
*   **Наблюдаемость:** алерт на удаление ConfigMap (`kube_configmap_created`); GitOps-Diff (дрейф); метрики reloader при Hot Reload; очистка неиспользуемых (`kor`/CronJob).
*   **Откат:** определена стратегия отката (rollout undo / git revert + restart); процедура миграции immutable описана в команде.

### Выбор метода доставки конфигурации

| Метод | Плюсы | Минусы | Рекомендация |
| :--- | :--- | :--- | :--- |
| **Volume** | Hot reload, атомарность | Задержка синхронизации (~1 мин) | Основной метод для файлов |
| **Env** | Простота, мгновенный старт | Требует рестарта пода | Для флагов, лимитов, JVM-опций |
| **subPath** | Монтаж в непустую папку | **Блокирует обновления** | Избегать в Production |

Механика каждого метода (атомарная смена симлинков, правила `envFrom`/`prefix`, `optional`, подстановка `$(VAR)`, диагностика типовых ошибок) подробно разобрана в [Использование ConfigMap в поде](./pod_usage.md), стратегии обновления и перезапуска — в [Обновление и Rollout](./update_and_rollout.md).

### Resource Quotas и ConfigMap

ResourceQuota в Namespace ограничивает количество и размер объектов. ConfigMap — объект уровня Namespace, поэтому подпадает под квоты.

**Типы квот, влияющих на ConfigMap:**

| Тип квоты | Пример | Описание |
|---|---|---|
| `count/configmaps` | `count/configmaps: "50"` | Общее количество ConfigMap в Namespace |
| `count/configmaps.<quota-name>` | `count/configmaps.production: "20"` | Количество ConfigMap в scope с label |
| `requests.storage` | `requests.storage: "10Gi"` | Не влияет на ConfigMap напрямую |

**Пример ResourceQuota:**

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: configmap-quota
  namespace: production
spec:
  hard:
    count/configmaps: "50"
```

**Диагностика:**

```bash
# Проверка текущего использования квоты
kubectl get resourcequota -n production
# → NAME                AGE   REQUEST   LIMIT
# → configmap-quota     5d    12/50     —

# Проверка, какая квота блокирует создание
kubectl describe resourcequota configmap-quota -n production
# → Type        Used  Hard
# → ------      ----  ----
# → ConfigMaps  50    50  ← лимит исчерпан

# Поиск ConfigMap в scope квоты
kubectl get configmap -n production -l environment=production
```

**Решение при исчерпании квоты:**
1. Увеличьте лимит: `kubectl patch resourcequota configmap-quota -n production -p '{"spec":{"hard":{"count/configmaps":"100"}}}'`
2. Удалите неиспользуемые ConfigMap: `kor --namespace production` или вручную.
3. Используйте immutable ConfigMap с хеш-суффиксами — они считаются в квоту, но старые версии нужно чистить.

> Подробнее: [multi-tenancy.md](../../Concepts/multi-tenancy.md:139), [immutable.md](./immutable.md:64)

### Backup и восстановление ConfigMap

ConfigMap хранится в etcd как объект Kubernetes API. При бэкапе etcd все ConfigMap сохраняются автоматически.

**Уровни бэкапа:**

| Уровень | Инструмент | Что сохраняется | RPO |
|---|---|---|---|
| **etcd snapshot** | `etcdctl snapshot save` | Все объекты (ConfigMap, Secret, Deployment и др.) | 1–5 мин |
| **Velero** | `velero backup create` | API-ресурсы + PV | 1 мин–24 ч |
| **GitOps** | Git + ArgoCD/Flux | Манифесты ConfigMap в Git | Момент коммита |

**Восстановление ConfigMap из etcd:**

```bash
# 1. Создание снапшота
etcdctl snapshot save /backup/etcd.db --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# 2. Проверка снапшота
etcdctl snapshot status /backup/etcd.db --write-out=table

# 3. Восстановление (только offline, на остановленном etcd)
etcdutl snapshot restore /backup/etcd.db --data-dir=/var/lib/etcd-restored
```

**Восстановление одного ConfigMap из etcd-бэкапа (без полного restore):**

```bash
# Извлечение конкретного объекта из снапшота (упрощённо)
# 1. Восстановите кластер из снапшота на временной ноде
# 2. Экспортируйте нужный ConfigMap
kubectl get configmap app-config -n production -o yaml > restored-cm.yaml
# 3. Примените в целевом кластере
kubectl apply -f restored-cm.yaml -n production
```

**Velero (рекомендуемый подход для production):**

```bash
# Бэкап конкретного namespace
velero backup create prod-configs-backup \
  --include-namespaces production \
  --selector app.kubernetes.io/part-of=myapp

# Восстановление
velero restore create prod-configs-restore \
  --from-backup prod-configs-backup
```

> Подробнее: [etcd backup strategies](../../../../etcd/backup_strategies.md), [Kubernetes backup strategies](../../Operations/backup-strategies.md), [Velero overview](../../ToolsUtilities/velero-overview.md)

### Аудит и compliance для ConfigMap

Kubernetes Audit Policy позволяет логировать все обращения к ConfigMap через API-сервер.

**Пример Audit Policy для ConfigMap:**

```yaml
apiVersion: audit.k8s.io/v1
kind: Policy
rules:
  # Логировать все изменения ConfigMap (create, update, patch, delete)
  - level: RequestResponse
    resources:
      - group: ""
        resources: ["configmaps"]
    verbs: ["create", "update", "patch", "delete"]

  # Логировать чтение ConfigMap на уровне Metadata (без данных)
  - level: Metadata
    resources:
      - group: ""
        resources: ["configmaps"]
    verbs: ["get", "list", "watch"]
```

**Важно:** Уровень `RequestResponse` для чтения **не рекомендуется** — он логирует содержимое всех ConfigMap, что может привести к утечке данных в аудит-логи (если в ConfigMap случайно попали секреты).

**Анализ аудит-логов:**

```bash
# Найти все изменения конкретного ConfigMap
cat /var/log/kubernetes/audit.log | jq 'select(
  .verb == "update" and
  .objectRef.resource == "configmaps" and
  .objectRef.name == "app-config"
)'

# Найти, кто удалил ConfigMap
cat /var/log/kubernetes/audit.log | jq 'select(
  .verb == "delete" and
  .objectRef.resource == "configmaps" and
  .objectRef.name == "app-config"
) | {user: .user.username, time: .requestReceivedTimestamp}'
```

> Подробнее: [Kubernetes Audit](../../Security/audit.md), [GitOps Audit Logs](../../../../GitOps/Concepts/audit_logs.md)

### Namespace lifecycle и ConfigMap

ConfigMap является ресурсом уровня Namespace. При удалении Namespace все ConfigMap удаляются каскадно.

**Что происходит при удалении Namespace:**

1. Namespace переходит в состояние `Terminating`.
2. Контроллер запускает каскадное удаление всех вложенных ресурсов (Pods, Services, ConfigMaps, Secrets и др.).
3. Если хотя бы один ресурс не удаляется (например, из-за finalizer), Namespace остаётся в `Terminating`.

**Диагностика зависшего Namespace:**

```bash
# Проверка finalizers
kubectl get ns production -o jsonpath='{.spec.finalizers}'
# → ["kubernetes"]

# Проверка условий
kubectl get ns production -o json | jq '.status.conditions[]'
# → {"type":"Terminating","status":"True","reason":"NamespaceDeletionDiscoveryFailure",...}

# Проверка ресурсов, блокирующих удаление
kubectl api-resources --namespaced=true -o name | while read resource; do
  kubectl get $resource -n production --no-headers 2>/dev/null | head -1
done
```

**Влияние на приложения:**
*   Pods с `terminationGracePeriodSeconds` продолжают работать до завершения таймаута.
*   ConfigMap остаётся доступен работающим Pod (кэш на узле) до их завершения.
*   Новые Pod не смогут запуститься (ConfigMap удалён).

**Предотвращение случайного удаления:**
*   Admission Policy (OPA/Kyverno): запрет удаления Namespace с лейблом `critical: true`.
*   RBAC: ограничение `delete` на уровне Namespace.

> Подробнее: [namespace.md](../namespace.md:200), [finalizer_issues.md](../../Troubleshooting/Common_Errors/PodTerminating/finalizer_issues.md)

### ConfigMap vs Secret: сравнение

| Критерий | ConfigMap | Secret |
|---|---|---|
| **Назначение** | Неконфиденциальные данные (URL, порты, логи) | Конфиденциальные данные (пароли, токены, ключи) |
| **Шифрование в etcd** | Нет (открытый текст) | По умолчанию Base64; опционально Encryption at Rest |
| **RBAC** | Стандартный (get/list/watch) | Строже (рекомендуется ограничить create/delete) |
| **Размер** | 1 MiB | 1 MiB |
| **Типы данных** | `data` (UTF-8), `binaryData` (Base64) | `data` (Base64), `stringData` (plain text) |
| **Автообновление томов** | Да (~60–90 сек) | Да (~60–90 сек) |
| **Обновление env** | Требует рестарт | Требует рестарт |
| **Immutable** | K8s 1.21+ | K8s 1.21+ |

> Подробнее: [secrets_basics.md](../../Base/secrets/secrets_basics.md:52), [secret_issues.md](../../Troubleshooting/Common_Errors/CreateContainerConfigError/secret_issues.md:504)

### Что защищает от потери конфигурации

| Механизм | Защита от | Не защищает от |
|---|---|---|
| `immutable: true` | Случайных правок (`kubectl edit`) | Удаления объекта |
| GitOps (ArgoCD/Flux) | Дрейфа от Git | Ручного удаления из Git |
| RBAC (`resourceNames`) | Несанкционированного доступа | Действий с правами cluster-admin |
| Audit Policy | Аудита всех изменений | Предотвращения изменений |
| Backup (etcd/Velero) | Потери данных | Мгновенной утраты актуальности |
| Admission Policy | Нарушения политик | Ошибок в самих политиках |
