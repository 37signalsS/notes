# Основы Kubernetes Secret

## Определения

**Secret** — это объект Kubernetes, предназначенный для хранения и управления конфиденциальной информацией, такой как пароли, OAuth-токены, SSH-ключи и API-ключи. Секреты обеспечивают безопасный способ передачи чувствительных данных в Pod, гарантируя, что они зашифрованы в etcd и не раскрываются в текстовом формате в спецификациях (manifests) или системных журналах (logs).

**Кодирование vs Шифрование:** По умолчанию данные в Secret хранятся в etcd в кодировке **Base64**. Это не является шифрованием. Любой пользователь с доступом к API или etcd может легко декодировать эти данные. Для реальной защиты необходимо использовать шифрование на уровне хранилища.

Подробнее см. [Хранение в etcd](etcd_storage.md).

## Основные концепции

### Разделение конфигурации и секретов

Следование принципу **Separation of Concerns** (разделение ответственности) требует отделения конфигурации от кода:
- **ConfigMap:** для нечувствительных данных (имена хостов, порты, флаги).
- **Secret:** для конфиденциальных данных.

Это позволяет изменять настройки без пересборки образов и использовать разные учетные данные для сред разработки (Dev), тестирования (Staging) и эксплуатации (Prod).

### Отличие Secret от ConfigMap

| Признак | Secret | ConfigMap |
| :--- | :--- | :--- |
| **Назначение** | Конфиденциальные данные | Обычные настройки |
| **Доступ** | Ограничен через RBAC (get/list запрещены по умолчанию) | Более свободный доступ |
| **Хранение** | Поддерживается шифрование (Encryption at Rest) | Хранится в открытом виде |
| **Формат данных** | `data` (Base64), `stringData` (Plain text) | `data` (Plain text), `binaryData` |
| **Типы** | Специализированные типы (TLS, Docker Config) | Универсальный формат |
| **Типичные сценарии** | Пароли, токены, ключи SSH, TLS-сертификаты | Переменные окружения, флаги, конфиг-файлы |

### Поля данных: data и stringData

В манифесте Secret используются два ключевых поля:
- **data:** принимает значения, уже закодированные в Base64. Используется при автоматизации и экспорте существующих секретов.
- **stringData:** принимает значения в открытом виде (Plain text). Это поле удобно для ручного создания манифестов. При сохранении Kubernetes автоматически переносит эти данные в поле `data`, кодируя их в Base64. Поле `stringData` является "только для записи" и не отображается при чтении объекта через `kubectl get`.

### Типы Secret

Kubernetes предоставляет несколько встроенных типов для различных сценариев:

- **Opaque:** тип по умолчанию для произвольных данных (пароли, ключи).
- **kubernetes.io/tls:** для хранения сертификатов и приватных ключей TLS (требует ключи `tls.crt` и `tls.key`).
- **kubernetes.io/dockerconfigjson:** для учетных данных доступа к приватным Docker Registry.
- **kubernetes.io/service-account-token:** (Legacy) использовался для хранения токенов ServiceAccount. В современных версиях (1.22+) рекомендуется использовать Bound Service Account Tokens.
- **kubernetes.io/basic-auth:** для базовой аутентификации (логин/пароль).
- **kubernetes.io/ssh-auth:** для SSH-ключей.
- **bootstrap.kubernetes.io/token:** для токенов, используемых при присоединении новых узлов к кластеру.

## Практические сценарии

### Создание и управление

Секреты можно создавать как декларативно (через YAML), так и императивно (через `kubectl create secret`). При создании важно помнить, что данные в YAML-файлах на диске должны быть зашифрованы (например, через SOPS).

Подробнее: [Создание Secret](creating_secrets.md).

### Использование в приложениях

Существует три основных способа доставки секрета в Pod:
1. **Переменные окружения:** быстро, но менее безопасно.
2. **Монтирование тома (Volume):** наиболее безопасный метод, поддерживающий атомарное обновление данных.
3. **Projected Volumes:** для агрегации данных из нескольких источников.

Подробнее: [Использование Secret](using_secrets.md).

### Безопасность и риски

Основные риски включают компрометацию etcd, избыточные права RBAC и утечку секретов в логи приложения. Для минимизации рисков следует использовать:
- Шифрование в etcd.
- Внешние менеджеры секретов (HashiCorp Vault).
- Принцип минимальных привилегий в RBAC.

Подробнее: [Безопасность Secret](security.md).

## Дополнительная информация

### Ограничения

- **Размер:** Лимит одного объекта Secret составляет **1 МиБ** (ограничение etcd). Сюда входят метаданные, аннотации и сами данные.
- **Аннотации:** Максимальный размер аннотаций ограничен 256 КБ.
- **Производительность:** Большое количество секретов в одном пространстве имен может замедлить работу API-сервера и потребление памяти `kubelet`.
