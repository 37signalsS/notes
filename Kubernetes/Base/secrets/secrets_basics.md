# Kubernetes Secrets: Основы

## Определения

**Secret** — это объект Kubernetes для хранения небольших объёмов чувствительных данных (пароли, токены, ключи API).

> **Ловушка:** Secret не является шифрованием. По умолчанию данные в Secret хранятся в etcd в кодировке **Base64**, а не в зашифрованном виде. Base64 — не шифрование (это кодирование), данные легко раскодировать. Подробнее см. [Хранение в etcd](etcd_storage.md).

## Основные концепции

### Мотивация: разделение конфигурации и кода

Хранение конфигурационных параметров (например, `dbHost`, `dbName`, `dbUser`) прямо в коде приложения — плохая практика. Такие параметры должны быть отделены и храниться в [ConfigMap](../configmap.md), что позволяет:

- Запускать одно и то же приложение в разных окружениях (dev, staging, prod) без пересборки
- Изменять конфигурацию без изменения кода
- Следовать принципу **separation of concerns**

Для конфиденциальных данных (пароли, токены, ключи) используется [Secret](#kubernetes-secrets-основы) — аналог ConfigMap, но с дополнительными мерами защиты.

### Отличие Secret от ConfigMap

| Признак | Secret | ConfigMap |
| :--- | :--- | :--- |
| **Назначение** | Конфиденциальные данные | Некритичные конфигурационные данные |
| **Доступ** | Строгие политики RBAC | Более открытый доступ |
| **Хранение** | Требуется шифрование в etcd | Хранится в открытом виде |
| **Представление** | `data` (Base64), `stringData` | `data`, `binaryData` |
| **Типы** | Типизированные форматы (`tls`, `dockerconfigjson`) | Нет специальных типов |

### Риски безопасности

Secret в Kubernetes **не является абсолютно защищённым хранилищем**. Основные риски:

- **По умолчанию данные в etcd хранятся в Base64**, а не в зашифрованном виде. Любой с доступом к etcd может прочитать секреты. Решение: [шифрование в etcd](etcd_storage.md#шифрование-at-rest-encryption-at-rest).
- **Любой пользователь с правом создания Pod в namespace может прочитать любой Secret этого namespace.** Для этого не нужен прямой доступ к Secret — достаточно смонтировать его в Pod как volume или переменную окружения и прочитать содержимое.
- **Пользователь с доступом к exec в контейнере** может прочитать смонтированные секреты или переменные окружения.

**Меры защиты:**

1. Включить **Encryption at Rest** для etcd
2. Настроить **RBAC** с минимальными привилегиями — ограничить права на `create pod`, `exec`, `logs`
3. Ограничить монтирование Secret к **конкретным контейнерам**; при монтировании Secret как volume используется `tmpfs` (in-memory)
4. Использовать **внешние системы** управления секретами (HashiCorp Vault, External Secrets Operator)

> Подробнее: [Безопасность Secret](security.md), [Хранение в etcd](etcd_storage.md).

### Типы Secret

- **Opaque**: тип по умолчанию, произвольные пары ключ-значение
- **kubernetes.io/service-account-token**: аутентификация с API-сервером, содержит токен, namespace и CA-сертификат
- **kubernetes.io/dockerconfigjson**: учётные данные Docker Registry для pull образов из приватных репозиториев
- **kubernetes.io/basic-auth**: логины и пароли для базовой аутентификации
- **kubernetes.io/ssh-auth**: приватные SSH-ключи
- **kubernetes.io/tls**: TLS-сертификаты и приватные ключи
- **bootstrap.kubernetes.io/token**: токены для автоматической регистрации нод в кластере (bootstrap-процесс)

## Дополнительная информация

### Ограничения

- Размер одного Secret: **до 1 MiB** (ограничение etcd)
- Максимальный размер annotations: **256 KB**
- Для больших данных используйте внешние хранилища или [ConfigMap](../configmap.md) с `binaryData`

> **Нюанс:** Ограничение 1 MiB применяется к сериализованным данным (включая metadata, annotations). При превышении 256 KB в annotations Secret не будет создан.
