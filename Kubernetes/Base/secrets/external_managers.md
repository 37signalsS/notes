# Внешние системы управления секретами

## Определения

**External Secret Managers** — внешние системы для управления секретами, интегрированные с Kubernetes. Это стандарт для промышленных (production) окружений, обеспечивающий централизацию и повышенную безопасность.

**External Secrets Operator (ESO)** — оператор, который синхронизирует секреты из внешних API (HashiCorp Vault, AWS Secrets Manager, Google Secret Manager и др.) в нативные объекты `Secret` Kubernetes.

**Secrets Store CSI Driver** — драйвер, позволяющий монтировать секреты из внешних хранилищ напрямую в файловую систему подов как тома, без создания объектов `Secret` в кластере.

## Основные концепции

### Зачем нужны внешние менеджеры

1. **Безопасность хранения** — секреты не хранятся в etcd (CSI Driver) или хранятся там только в виде синхронизированных копий (ESO). Подробнее о проблемах etcd см. [Хранение в etcd](etcd_storage.md).
2. **Централизация** — единое хранилище секретов для нескольких кластеров и облачных провайдеров.
3. **Жизненный цикл** — автоматическая ротация, аудит доступа и централизованный отзыв (revocation) ключей.

### Сравнение подходов

| Подход | Хранение в Git | Внешнее ПО | Secret в etcd | Ротация |
| :--- | :--- | :--- | :--- | :--- |
| **Sealed Secrets** | Да (зашифровано) | Контроллер | Да | Ручная |
| **ESO** | Нет | Оператор + KMS | Да | Автоматическая |
| **CSI Driver** | Нет | Драйвер + KMS | Нет | Автоматическая |
| **SOPS** | Да (зашифровано) | Ключи (KMS/age) | Да | Ручная |

## Практические сценарии

### External Secrets Operator (ESO)

ESO позволяет приложениям использовать нативные Kubernetes Secrets, в то время как источником истины остается внешнее хранилище.

1. **Установка**: Оператор устанавливается в кластер (обычно через Helm).
2. **Конфигурация**: Создается ресурс `SecretStore` (для одного namespace) или `ClusterSecretStore` (на весь кластер) с параметрами подключения к KMS.
3. **Синхронизация**: Ресурс `ExternalSecret` описывает, какие данные из внешнего хранилища нужно извлечь.
4. **Результат**: Оператор создает и обновляет нативный `Secret`, который приложение использует стандартным способом (переменные окружения или тома).

**Провайдеры:** HashiCorp Vault, AWS Secrets Manager, Google Secret Manager, Azure Key Vault, Doppler.

### Secrets Store CSI Driver

Этот подход считается наиболее безопасным, так как секреты монтируются в `tmpfs` пода и никогда не записываются на диск ноды или в etcd.

1. **Монтирование**: Секреты подключаются как том типа `csi`.
2. **SecretProviderClass**: Описывает, какие объекты из внешнего KMS нужно смонтировать.
3. **Обновление**: Поддерживает автоматическое обновление секретов (rotation) в файловой системе без перезапуска пода.
4. **Ограничение**: Секреты доступны только в виде файлов. Для использования их как переменные окружения требуется дополнительная конфигурация (синхронизация в нативные `Secret`), что снижает уровень безопасности.

Подробная интеграция с Vault: [Интеграция Vault через CSI Driver](../../../Vault/guides/vault_kubernetes_integration.md).

### Sealed Secrets и SOPS (GitOps-подход)

Эти инструменты решают задачу безопасного хранения секретов в Git-репозиториях.

* **Sealed Secrets**: Асимметричное шифрование специально для конкретного кластера. Расшифровать может только контроллер внутри кластера. Подробнее см. **[Sealed Secrets](../../Security/sealed_secrets_overview.md)**.
* **SOPS (Secrets Operations)**: Шифрование значений в YAML/JSON/ENV файлах с использованием AWS KMS, GCP KMS, Azure Key Vault, HashiCorp Vault, PGP или age. Подробнее см. **[SOPS overview](../../../Security/Tools/sops_overview.md)**.

## Дополнительная информация

### Выбор инструмента

- **Для GitOps (хранение в Git)**: Sealed Secrets (проще) или SOPS (гибче).
- **Для максимальной безопасности**: Secrets Store CSI Driver (секреты не попадают в etcd).
- **Для совместимости с приложениями**: External Secrets Operator (приложения работают с нативными Secrets).
