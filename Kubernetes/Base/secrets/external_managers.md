# Внешние системы управления секретами

## External Secret Managers

Это "золотой стандарт" для управления секретами. Вместо хранения секретов в `etcd`, Kubernetes получает их "на лету" из внешнего хранилища.

*   **Примеры:** `HashiCorp Vault`, `AWS Secrets Manager`, `Google Cloud Secret Manager`, `Azure Key Vault`
*   **Как работает:**
    1. В кластере устанавливается оператор (например, `External Secrets Operator`)
    2. Создается ресурс `ExternalSecret`, описывающий, какой секрет и откуда получить
    3. Оператор аутентифицируется во внешнем хранилище и создает нативный Kubernetes `Secret`
    4. Приложение использует этот `Secret` как обычно

## GitOps: Sealed Secrets

Этот подход решает проблему "Как безопасно хранить секреты в Git-репозитории?"

*   **Как работает:**
    1. В кластере устанавливается контроллер `Sealed Secrets` с парой ключей
    2. Используется утилита `kubeseal` и **публичный ключ** для шифрования `Secret`
    3. Полученный `SealedSecret` **можно безопасно коммитить в Git**
    4. Контроллер расшифровывает его и создает нативный `Secret`

## Secrets Store CSI Driver

Этот драйвер позволяет подам Kubernetes монтировать внешние секреты как тома, не сохраняя их в `etcd`.

*   **Как работает:**
    1. Устанавливается Secrets Store CSI Driver и провайдер (например, для AWS)
    2. Создается `SecretProviderClass` ресурс
    3. В манифесте пода монтируется том типа `secrets-store.csi.k8s.io`
    4. CSI Driver извлекает данные из внешнего хранилища и монтирует их в под как файлы

*   **Преимущества:**
    *   **Улучшенная безопасность:** Секреты никогда не хранятся в `etcd`
    *   **Централизованное управление:** Единое управление секретами
    *   **Автоматическая ротация:** Внешние хранилища часто предлагают автоматическую ротацию
