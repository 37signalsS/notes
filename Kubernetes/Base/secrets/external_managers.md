# Внешние системы управления секретами

## Определения

**Внешние менеджеры секретов (External Secret Managers)** — сторонние специализированные системы (KMS), интегрированные с Kubernetes для централизованного хранения, аудита и ротации конфиденциальных данных. Использование внешних менеджеров является отраслевым стандартом для промышленных (production) сред.

**External Secrets Operator (ESO)** — Kubernetes-оператор, который считывает данные из внешних источников (HashiCorp Vault, AWS Secrets Manager, Google Secret Manager и др.) и автоматически создает на их основе нативные объекты `Secret` в кластере.

**Secrets Store CSI Driver** — интерфейс, позволяющий монтировать секреты из внешних хранилищ напрямую в файловую систему Pod в виде томов (Volumes). В отличие от ESO, этот метод позволяет полностью избежать создания объектов `Secret` в Kubernetes API.

## Основные концепции

### Преимущества внешних систем

1.  **Безопасность etcd:** Секреты либо вовсе не попадают в etcd (CSI Driver), либо хранятся там только временно в виде синхронизированных копий. Подробнее о рисках etcd см. [Хранение в etcd](etcd_storage.md).
2.  **Централизация и аудит:** Единое хранилище для нескольких кластеров, облачных регионов и On-premise серверов. Полная история того, кто и когда запрашивал секрет.
3.  **Динамическая ротация:** Возможность автоматической смены паролей баз данных или API-ключей без ручного вмешательства.
4.  **Разделение ответственности:** Системные администраторы управляют инфраструктурой Kubernetes, а специалисты по безопасности — политиками доступа к секретам во внешнем хранилище.

### Сравнение подходов к управлению

| Подход | Источник истины | Хранение в etcd | Ротация | Сложность |
| :--- | :--- | :--- | :--- | :--- |
| **Sealed Secrets** | Git (зашифровано) | Да | Ручная | Низкая |
| **SOPS** | Git (зашифровано) | Да | Ручная | Средняя |
| **External Secrets (ESO)** | Внешний KMS | Да (синхронизация) | Авто | Средняя |
| **Secrets Store CSI** | Внешний KMS | Нет | Авто | Высокая |

## Практические сценарии

### Использование External Secrets Operator (ESO)

Это наиболее сбалансированный подход, так как он сохраняет совместимость с приложениями, которые умеют читать только нативные секреты K8s.

**Архитектура:**
1.  **SecretStore / ClusterSecretStore:** Ресурс, содержащий параметры подключения к провайдеру (например, адрес Vault и метод аутентификации).
2.  **ExternalSecret:** Ресурс, описывающий, какие именно ключи из внешнего хранилища нужно забрать и в какой нативный `Secret` их поместить.

**Провайдеры:** HashiCorp Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault, GitLab Variables, Doppler, 1Password.

### Использование Secrets Store CSI Driver

Наиболее безопасный метод для приложений, поддерживающих чтение конфигурации из файлов.

**Особенности:**
- Секреты монтируются в `tmpfs` (память) Pod.
- **SecretProviderClass:** Ресурс, специфичный для каждого провайдера (например, AWS Secrets Manager или Azure Key Vault), который сопоставляет внешние объекты с путями в файловой системе Pod.
- **Синхронизация:** Драйвер может опционально создавать нативный `Secret` (для передачи в ENV), но это требует монтирования тома, что делает схему более сложной.

### Подход GitOps (Sealed Secrets и SOPS)

Если внешнее хранилище (KMS) недоступно или нецелесообразно, используется шифрование секретов непосредственно в Git-репозитории.

- **[Sealed Secrets](../../Security/sealed_secrets_overview.md):** Оптимально для простых кластеров. Расшифровать данные может только контроллер, запущенный в конкретном кластере.
- **[SOPS (Secrets Operations)](../../../Security/Tools/sops_overview.md):** Универсальный инструмент. Позволяет шифровать YAML-файлы, используя KMS (AWS/GCP/Azure) или PGP-ключи. Удобен для командной работы и CI/CD.

## Дополнительная информация

### Выбор решения

1.  **Начинающим:** Sealed Secrets или SOPS.
2.  **Мультикластерные среды:** External Secrets Operator (ESO).
3.  **Высокие требования безопасности (PCI DSS, HIPAA):** Secrets Store CSI Driver + Vault.
