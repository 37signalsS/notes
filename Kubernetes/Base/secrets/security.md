# Определения

## Безопасность Secret в Kubernetes

**Secret** — это объект Kubernetes, предназначенный для хранения конфиденциальных данных (пароли, токены, ключи API). В отличие от [ConfigMap](../configmap.md), который хранит неконфиденциальные данные, Secret обеспечивает дополнительный уровень защиты и может быть использован для монтирования чувствительных данных в поды.

> **Примечание:** Для общей информации о создании и использовании Secret см. [Secret](../secret.md). Данный документ фокусируется на аспектах безопасности.

## Основные концепции

### Шифрование в etcd (Encryption at Rest)

Это базовый уровень защиты, который шифрует данные `Secret` непосредственно в хранилище `etcd`.

*   **Как работает:** API-сервер Kubernetes шифрует секреты перед сохранением в `etcd` и расшифровывает их при чтении
*   **Настройка:** Требует изменения конфигурации API-сервера (`--encryption-provider-config`)

### Неизменяемые Secrets (Immutable Secrets)

Kubernetes позволяет сделать Secrets неизменяемыми (`immutable: true`).

*   **Преимущества:**
    *   **Безопасность:** Защита от случайных или вредоносных правок
    *   **Производительность:** Снижает нагрузку на `kube-apiserver` и `kubelet`
    *   **Предсказуемость:** Обновление секрета требует создания нового объекта

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-immutable-secret
immutable: true # Делает Secret неизменяемым
data:
  API_KEY: dmFsdWU=
```

> **Примечание:** Тот же подход применим к [ConfigMap](../configmap.md). См. раздел "Неизменяемые ConfigMaps" в документе ConfigMap.

# Практические сценарии

## Рекомендации по безопасности

### RBAC (Role-Based Access Control)

Всегда ограничивайте доступ к `Secret` с помощью ролей и ролевых привязок:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: secret-reader
  namespace: default
rules:
- apiGroups: [""]
  resources: ["secrets"]
  verbs: ["get", "list"]
```

### Монтирование vs Переменные окружения

**Предпочитайте монтирование секретов как `volume`:**

- При монтировании как volume секреты хранятся в tmpfs (RAM), а не на диске
- Переменные окружения могут быть видны в `/proc/<pid>/environ` и логах
- При монтировании можно ограничить доступ к конкретным ключам

```yaml
# Рекомендуемый способ - volume
spec:
  containers:
  - name: app
    volumeMounts:
    - name: secret-volume
      mountPath: "/etc/secrets"
      readOnly: true
  volumes:
  - name: secret-volume
    secret:
      secretName: my-secret
```

### Защита etcd

- **Всегда включайте Encryption at Rest** для секретов
- Ограничьте доступ к etcd только API-серверу
- Регулярно выполняйте ротацию ключей шифрования
- Используйте отдельные диски с шифрованием для хранения данных etcd

### Безопасность в CI/CD

- **Никогда не храните манифесты Secret с открытыми данными в Git**
- Используйте внешние хранилища секретов (Vault, Sealed Secrets, External Secrets Operator)
- Применяйте git-crypt или sops для шифрования секретов в репозитории

### Ограничение размера

Размер одного секрета не должен превышать 1 MiB (ограничение etcd). Для больших данных используйте:
- [ConfigMap](../configmap.md) с `binaryData` для неконфиденциальных бинарных данных
- Внешние хранилища с монтированием через CSI-драйверы

# Дополнительная информация

## Лучшие практики

*   **Используйте неизменяемые Secrets** для критичных конфигураций
*   **Применяйте принцип минимальных привилегий** при настройке RBAC
*   **Регулярно ротируйте секреты** — автоматизируйте процесс обновления
*   **Мониторьте доступ к Secrets** — используйте аудит-логи Kubernetes
*   **Используйте внешние менеджеры секретов** для production-окружений
