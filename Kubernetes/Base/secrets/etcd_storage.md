# Хранение Secret в etcd

## Определения

**etcd** — это высоконадежное распределенное хранилище данных типа «ключ-значение», использующее алгоритм консенсуса Raft. В Kubernetes etcd служит централизованным хранилищем для всех объектов кластера, включая секреты, конфигурации и состояние узлов.

**Хранение секретов в etcd** — процесс сериализации объектов `Secret` (обычно в формат Protobuf) и их записи в базу данных bbolt, используемую etcd. По умолчанию данные в etcd записываются в незашифрованном виде, где конфиденциальные значения в поле `data` лишь закодированы в Base64.

> **Критическая уязвимость:** Кодирование Base64 не является шифрованием. Любое лицо с доступом к файлам базы данных etcd (например, через бэкапы) или к API etcd может мгновенно получить доступ ко всем паролям и токенам кластера. Для защиты данных на диске необходимо использовать механизм **Encryption at Rest**.

## Основные концепции

### Структура данных в etcd

Секреты хранятся по пути:
`/registry/secrets/<namespace>/<name>`

*   **Формат хранения:** Protobuf (начиная с K8s 1.6+). Это более компактный и быстрый формат по сравнению с JSON.
*   **Лимиты:** Максимальный размер одного объекта в etcd составляет **1 МиБ**. Попытка создания секрета большего размера приведет к ошибке `RequestEntityTooLarge`.
*   **Ревизии:** Любое изменение секрета создает новую ревизию в etcd. Старые ревизии удаляются в процессе автоматической компакции (compaction).

### Шифрование при хранении (Encryption at Rest)

Шифрование выполняется на стороне `kube-apiserver` ПЕРЕД отправкой данных в etcd. При чтении API-сервер прозрачно расшифровывает данные.

**Провайдеры шифрования:**

| Провайдер | Алгоритм | Оценка безопасности | Особенности |
| :--- | :--- | :--- | :--- |
| **identity** | Нет | 0 | Значение по умолчанию. Данные хранятся как есть. |
| **aescbc** | AES-CBC (256-bit) | 8 | Рекомендуется для большинства сред. Использует PKCS7 padding. |
| **aesgcm** | AES-GCM (256-bit) | 9 | Быстрее на современном CPU (AES-NI). Обеспечивает проверку целостности. |
| **secretbox** | XSalsa20 + Poly1305 | 9 | Альтернатива AES, устойчивая к атакам по сторонним каналам. |
| **kms (v1)** | Внешний KMS | 10 | Ключи хранятся в облаке (AWS, GCP) или Vault. API-сервер делает gRPC-запрос на каждый объект. |
| **kms (v2)** | Внешний KMS | 10+ | **GA в 1.29+**. Кэширует ключи, поддерживает автоматическую ротацию без перезапуска API-сервера. |

## Практические сценарии

### Настройка EncryptionConfiguration

Для включения шифрования необходимо создать файл конфигурации и передать его через флаг `--encryption-provider-config` в манифест `kube-apiserver`.

```yaml
# /etc/kubernetes/encryption-config.yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
      - secrets
      - configmaps # Рекомендуется шифровать, если там есть токены
    providers:
      - aesgcm:
          keys:
            - name: key1
              secret: <base64-encoded-32-byte-key> # generate with: head -c 32 /dev/urandom | base64
      - identity: {} # Fallback для чтения старых данных
```

### Настройка KMS v2 (Рекомендуемый метод для Production)

KMS v2 значительно производительнее первой версии за счет локального кэширования ключей шифрования данных (DEK).

```yaml
providers:
  - kms:
      apiVersion: v2
      name: my-kms-provider
      endpoint: unix:///var/run/kms-provider.sock
      timeout: 3s
```

### Ротация ключей и перешифрование

При смене ключа (например, с `key1` на `key2`) процедура выглядит так:

1.  Добавьте новый ключ первым в список провайдеров в файле конфигурации.
2.  Перезапустите `kube-apiserver`.
3.  Инициируйте перешифрование всех существующих секретов:

```bash
kubectl get secrets --all-namespaces -o json | kubectl replace -f -
# → result: все секреты будут прочитаны старым ключом и записаны новым
```

4.  Убедитесь, что данные зашифрованы новым ключом (проверьте префикс в etcd).
5.  Удалите старый ключ из списка провайдеров.

### Проверка шифрования через etcdctl

Чтобы убедиться, что шифрование работает, проверьте сырые данные в etcd. Зашифрованные данные начинаются с префикса провайдера (например, `k8s:enc:aesgcm:v1:key1:`).

```bash
# Пример команды для чтения секрета напрямую из etcd
ETCDCTL_API=3 etcdctl --endpoints=$ENDPOINT \
  --cacert=$CA --cert=$CERT --key=$KEY \
  get /registry/secrets/default/my-app-secret
```

## Дополнительная информация

### Риски и нюансы

*   **Потеря ключей:** Если файл `EncryptionConfiguration` или ключи в KMS будут утеряны, данные в etcd расшифровать невозможно. Бэкап etcd бесполезен без бэкапа ключей.
*   **Производительность KMS:** KMS v1 может создавать значительную задержку (latency) на критических путях записи. Всегда используйте KMS v2 в современных кластерах.
*   **Безопасность мастера:** Сам файл `EncryptionConfiguration` содержит секреты (для `aes*` провайдеров). Доступ к нему должен быть только у `root` и `kube-apiserver`.
