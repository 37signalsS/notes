# Определения

**Secret** — это объект Kubernetes, предназначенный для хранения небольших объемов чувствительных данных, таких как пароли, токены или ключи. Использование `Secret` позволяет отделить конфигурацию от секретных данных, что повышает безопасность и гибкость.

> **Важно:** По умолчанию данные в `Secret` хранятся в `etcd` в кодировке **Base64**, а не в зашифрованном виде. Base64 — это не шифрование, и данные могут быть легко раскодированы. Для защиты секретов необходимо настраивать шифрование неактивных данных (Encryption at Rest).

## Что отличает Secret от ConfigMap

| Признак | Secret | ConfigMap |
| :--- | :--- | :--- |
| **Назначение** | Конфиденциальные данные (пароли, токены, ключи). | Некритичные конфигурационные данные. |
| **Доступ** | Подчиняется строгим политикам RBAC, не виден в логах. | Более открытый доступ. |
| **Хранение** | Рекомендуется шифрование в etcd (at-rest). | Хранится в открытом виде. |
| **Представление** | `data` (Base64), `stringData` (открытый текст). | `data`, `binaryData`. |
| **Типы** | Типизированные форматы (`tls`, `dockerconfigjson`). | Нет специальных типов. |

# Основные концепции

## Типы секретов

*   **Opaque**: Тип по умолчанию, используется для хранения произвольных пар ключ–значение.
*   **kubernetes.io/service-account-token**: Автоматически создаются для аутентификации с API-сервером.
*   **kubernetes.io/dockerconfigjson**: Применяются для хранения учётных данных Docker Registry для `imagePullSecrets`.
*   **kubernetes.io/basic-auth**: Содержат логины и пароли для базовой аутентификации.
    > **Подробнее:** [Настройка BasicAuth в Traefik с Kubernetes](../Security/traefik_kubernetes_basic_auth.md)
*   **kubernetes.io/ssh-auth**: Хранят приватные SSH-ключи для безопасного доступа.
*   **kubernetes.io/tls**: Включают TLS-сертификаты и приватные ключи для HTTPS-соединений.
*   **bootstrap.kubernetes.io/token**: Используются при подключении новых нод к кластеру.

## Создание и использование Secret в Pod'ах

### Способы создания

#### Декларативно (из манифеста) с `stringData` (рекомендуемый)

Это наиболее удобный способ, так как Kubernetes автоматически кодирует значения в Base64.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-cred
type: Opaque
stringData:
  # Kubernetes сам преобразует это значение в Base64
  username: "app"
  password: "my-super-secret-password"
```

#### Декларативно (из манифеста) с `data`

Значения должны быть предварительно закодированы в Base64.

```bash
# Кодирование пароля в Base64
 echo -n 'my-super-secret-password' | base64
# Вывод: bXktc3VwZXItc2VjcmV0LXBhc3N3b3Jk
```

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-database-secret
type: Opaque
data:
  # ключ: значение (в base64)
  password: bXktc3VwZXItc2VjcmV0LXBhc3N3b3Jk
```

#### Императивно (из команды)

`kubectl` автоматически кодирует значения в Base64.

```bash
kubectl create secret generic db-cred \
  --from-literal=username=app \
  --from-literal=password='S3cUr3!'
```

### Способы использования

#### Как переменные окружения (`env`, `envFrom`)

Удобно для простых значений, но менее безопасно, так как переменные окружения могут попасть в логи или отладочные выводы.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
spec:
  containers:
    - name: my-app
      image: my-app-image
      env:
        - name: DATABASE_PASSWORD
          valueFrom:
            secretKeyRef:
              name: db-cred # Имя секрета
              key: password     # Ключ в секрете
              optional: false # Под должен упасть, если секрета или ключа нет
      envFrom:
        - secretRef:
            name: db-cred
            optional: true # Под не упадет, если секрета нет
  automountServiceAccountToken: false
```
**Важно:** Переменные окружения **не обновляются автоматически** после старта пода. Для применения изменений требуется перезапуск.

#### Как файлы в томе (`volume`)

Это более безопасный и гибкий способ. Секреты монтируются как файлы в read-only `tmpfs` том (в памяти).

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
spec:
  containers:
    - name: my-app
      image: my-app-image
      volumeMounts:
        - name: secret-volume
          mountPath: "/etc/secrets"
          readOnly: true
  volumes:
    - name: secret-volume
      secret:
        secretName: db-cred
        defaultMode: 0400 # Права на файлы (только чтение для владельца)
        items:
          - key: username
            path: db_user.txt # ключ 'username' будет в файле 'db_user.txt'
```
*   **Обновление:** Файлы в томе **обновляются автоматически** (с задержкой до минуты), если Secret изменяется.
*   **Безопасность:** Чтение из файла предпочтительнее, чем из переменных окружения, так как снижает риск утечки.

#### Как `projected` том

Позволяет объединить несколько источников (Secrets, ConfigMaps, DownwardAPI) в одну директорию.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: app-projected
spec:
  containers:
  - name: app
    image: nginx
    volumeMounts:
    - name: all-in-one
      mountPath: /etc/app
      readOnly: true
  volumes:
  - name: all-in-one
    projected:
      sources:
      - secret:
          name: db-cred
          items:
            - key: username
              path: credentials/user
      - configMap:
          name: app-config
          items:
            - key: config.yaml
              path: settings/app.conf
```
При конфликте имен файлов приоритет имеет последний источник в списке `sources`.

## Шифрование в etcd (Encryption at Rest)

Это базовый уровень защиты, который шифрует данные `Secret` непосредственно в хранилище `etcd`. Если злоумышленник получит доступ к резервной копии `etcd`, он не сможет прочитать секреты без ключа шифрования.

*   **Как работает:** API-сервер Kubernetes шифрует секреты перед сохранением в `etcd` и расшифровывает их при чтении.
*   **Настройка:** Требует изменения конфигурации API-сервера (`--encryption-provider-config`). Необходимо определить провайдера шифрования (например, `aescbc`, `aesgcm` или `kms` для интеграции с облачными провайдерами).
*   **Вывод:** Обязательный шаг для любой production-среды.

## Неизменяемые Secrets (Immutable Secrets)

Kubernetes позволяет сделать Secrets неизменяемыми (`immutable: true`), что предотвращает случайные или нежелательные изменения после их создания. Это полезно для повышения стабильности и безопасности кластера.

*   **Преимущества:**
    *   **Безопасность:** Защита от случайных или вредоносных правок.
    *   **Производительность:** Снижает нагрузку на `kube-apiserver` и `kubelet`, так как им больше не нужно отслеживать изменения.
    *   **Предсказуемость:** Обновление секрета требует создания нового объекта и `rollout` деплоймента.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: my-immutable-secret
immutable: true # Делает Secret неизменяемым
data:
  API_KEY: dmFsdWU=
```

# Практические сценарии

## Внешние системы управления секретами (External Secret Managers)

Это "золотой стандарт" для управления секретами. Вместо хранения секретов в `etcd`, Kubernetes получает их "на лету" из внешнего, специально предназначенного для этого хранилища.

*   **Примеры:** `HashiCorp Vault`, `AWS Secrets Manager`, `Google Cloud Secret Manager`, `Azure Key Vault`.
*   **Как работает:**
    1. В кластере устанавливается оператор (например, `External Secrets Operator` или `Vault Secrets Operator`).
    2. Вы создаете специальный ресурс (например, `ExternalSecret`), который описывает, какой секрет и откуда нужно получить.
    3. Оператор аутентифицируется во внешнем хранилище, забирает оттуда секрет и **создает на его основе нативный Kubernetes `Secret`**.
    4. Приложение использует этот `Secret` как обычно.
*   **Преимущества:**
    *   Централизованное хранение, аудит и строгие политики доступа.
    *   Поддержка динамических секретов и ротации ключей.

> **Подробнее:** [HashiCorp Vault](../../Vault/overview.md)

## GitOps: Sealed Secrets

Этот подход решает проблему "Как безопасно хранить секреты в Git-репозитории?"

*   **Как работает:**
    1.  В кластере устанавливается контроллер `Sealed Secrets`. У него есть пара ключей: публичный и приватный. Приватный ключ хранится только в кластере.
    2.  Вы используете утилиту `kubeseal` и **публичный ключ** для шифрования вашего `Secret`. На выходе получается новый объект — `SealedSecret`.
    3.  Этот `SealedSecret` **можно безопасно коммитить в Git**, так как он зашифрован и бесполезен без приватного ключа.
    4.  Контроллер в кластере обнаруживает `SealedSecret`, расшифровывает его своим приватным ключом и создает нативный `Secret`.
*   **Преимущества:**
    *   Идеально для GitOps-подхода.
    *   Секреты хранятся вместе с кодом приложения, но в безопасном виде.

> **Подробнее:** [Sealed Secrets](../../Kubernetes/Security/sealed_secrets_overview.md)

## Secrets Store CSI Driver

Этот драйвер позволяет подам Kubernetes монтировать внешние секреты как тома, не сохраняя их в `etcd`.

*   **Как работает:**
    1.  Вы устанавливаете Secrets Store CSI Driver и соответствующий провайдер (например, для AWS).
    2.  Создаете `SecretProviderClass` ресурс, который определяет, какой внешний секрет нужно получить и из какого хранилища.
    3.  В манифесте пода вы ссылаетесь на этот `SecretProviderClass` и монтируете том типа `secrets-store.csi.k8s.io`.
    4.  CSI Driver взаимодействует с внешним хранилищем секретов, извлекает нужные данные и монтирует их в под как файлы, доступные только для чтения.
*   **ПреимущеMства:**
    *   **Улучшенная безопасность:** Секреты никогда не хранятся в `etcd` и доступны только в памяти пода во время его выполнения.
    *   **Централизованное управление:** Единое управление секретами во внешних хранилищах.
    *   **Автоматическая ротация:** Внешние хранилища часто предлагают автоматическую ротацию ключей.

# Дополнительная информация

## Рекомендации и лучшие практики

*   **RBAC:** Всегда ограничивайте доступ к `Secret` с помощью ролей и ролевых привязок. Предоставляйте подам доступ только к тем секретам, которые им необходимы (принцип наименьших привилегий).
*   **Монтирование > Переменные окружения:** Предпочитайте монтирование секретов как `volume` вместо `env`. Это безопаснее и позволяет автоматически обновлять данные.
*   **Не храните в Git:** Никогда не храните манифесты `Secret` с открытыми данными в Git. Используйте `Sealed Secrets`, `Helm secrets` или интеграцию с внешними хранилищами.
*   **Ограничение размера:** Размер одного секрета не должен превышать 1 MiB. Для больших данных используйте внешние хранилища.
*   **Операционная безопасность:**
    *   Не выводите значения секретов через `kubectl describe` или в логах.
    *   Отключайте автоматическое монтирование токена `ServiceAccount`, если он не нужен: `automountServiceAccountToken: false`.
