# Определения

**StatefulSet** — это объект Kubernetes, предназначенный для управления приложениями, которые требуют сохранения состояния и/или стабильных сетевых идентификаторов. В отличие от [Deployment](./deployment.md), он обеспечивает гарантии порядка и уникальности для своих подов.

Ключевая задача `StatefulSet` — обеспечить каждому поду:

1. **Стабильное, уникальное сетевое имя.**
2. **Стабильное, постоянное хранилище.**

## Проблема: Почему Deployment не подходит для Stateful-приложений?

Стандартный объект [Deployment](./deployment.md) обращается с подами как со взаимозаменяемыми и не имеющими состояния "копиями". При перезапуске или переносе пода он может получить новый IP-адрес, новое имя и, что самое важное, **потерять связь со своим хранилищем**. Для веб-сервера это нормально, но для базы данных — катастрофа, равносильная потере всех данных.

## Основные концепции

## Ключевые компоненты

Для правильного развертывания приложений с состоянием используется комбинация из четырех ключевых компонентов:

1. **`StatefulSet`**: Главный оркестратор. В отличие от `Deployment`, он предоставляет подам стабильные имена и привязывает их к конкретным дискам.
2. **`PersistentVolumeClaim` (PVC)**: "Запрос" пода на выделение диска. `StatefulSet` автоматически создает уникальный PVC для каждого своего пода.
3. **`PersistentVolume` (PV)**: Физический "кусок" хранилища в кластере (NFS, Ceph, диск облачного провайдера), который удовлетворяет запрос PVC.
4. **`Headless Service`**: Специальный тип [сервиса](../Networking/service.md), который обеспечивает каждому поду стабильное и уникальное DNS-имя внутри кластера.

## Ключевые особенности StatefulSet

1. **Стабильные, уникальные сетевые идентификаторы:**
    * Каждый [под](./pod.md) в StatefulSet получает предсказуемое имя в формате `<имя-StatefulSet>-<порядковый-номер>` (например, `web-0`, `web-1`).
    * Эти имена сохраняются при перезапуске и переносе подов, что критически важно для кластерных приложений.
    * Требует наличия **Headless Service** (сервис с `clusterIP: None`) для обеспечения уникальных DNS-имен для каждого пода.

2. **Стабильные, постоянные хранилища:**
    * Для каждого пода создается свой собственный [PersistentVolumeClaim](./pv_and_pvc.md) (PVC) на основе шаблона (`volumeClaimTemplates`).
    * Этот PVC привязан к конкретному поду и сохраняется даже после его удаления и пересоздания. `StatefulSet` гарантирует, что при воссоздании пода он будет использовать тот же самый том.
    * **Важно:** При удалении `StatefulSet` связанные с ним PVC **не удаляются** автоматически. Это сделано для защиты данных. Их необходимо удалять вручную.

3. **Упорядоченное развертывание и масштабирование:**
    * **Создание:** Поды создаются последовательно, один за другим (сначала `web-0`, потом `web-1`). Следующий под не начнет создаваться, пока предыдущий не станет `Ready`.
    * **Удаление:** Поды удаляются в обратном порядке (сначала `web-n`, потом `web-n-1`).
    * Это обеспечивает предсказуемое поведение для кластерных приложений.

4. **Особое поведение при сбоях:**
    * **Недоступность узла:** Если нода становится `NotReady`, Kubernetes **не будет** автоматически переносить под `StatefulSet` на другую ноду. Это сделано для защиты данных и предотвращения сценариев split-brain, особенно для баз данных. Перенос пода с `ReadWriteOnce` томом требует ручного вмешательства или использования операторов.
    * **Обработка `SIGTERM`:** `StatefulSet` может ожидать более длительное время при получении сигнала `SIGTERM`, что позволяет приложениям с состоянием корректно завершить работу, сохранить данные и отсоединиться от кластера.

## Практические сценарии

## Сценарий использования: Stateful-приложения (Kafka, базы данных)

`StatefulSet` является единственным правильным выбором для запуска приложений, которые требуют стабильного хранения данных и сетевой идентификации. Классический пример — **Apache Kafka**.

**Проблема:** Если развернуть Kafka с помощью `Deployment`, при любом рестарте пода (из-за сбоя ноды, обновления или масштабирования) он потеряет связь со своим диском (`PersistentVolume`). `Deployment` создает новый под как "чистый лист", без привязки к состоянию предыдущего. Это неминуемо приведет к **потере данных** в брокере Kafka.

**Решение с `StatefulSet`:**

`StatefulSet` решает эту проблему, предоставляя каждому поду:

1. **Стабильное имя**: `kafka-0`, `kafka-1`, и т.д.
2. **Стабильный PVC**: Для `kafka-0` будет автоматически создан и привязан PVC `data-kafka-0`, для `kafka-1` — `data-kafka-1`.

При рестарте пода `kafka-0` (даже на другой ноде) `StatefulSet` гарантирует, что он будет снова подключен к своему уникальному PVC `data-kafka-0`, сохраняя все данные.

## Пример: Развертывание Nginx с StatefulSet

Развернем простое stateful-приложение на базе Nginx, где каждый экземпляр будет иметь свой собственный, постоянный `index.html`.

### Шаг 1: Создание Headless Service

Это необходимо для того, чтобы `StatefulSet` мог присвоить подам уникальные DNS-имена в формате `<pod-name>.<service-name>.<namespace>.svc.cluster.local`.

```yaml
# service-headless.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-headless
spec:
  clusterIP: None # <-- Ключевой параметр, делающий сервис "безголовым"
  selector:
    app: my-stateful-app # Должен соответствовать меткам подов
  ports:
  - port: 80
    name: web
```

### Шаг 2: Создание StatefulSet

Это основной манифест, который связывает все воедино.

```yaml
# statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: my-app
spec:
  # serviceName должен соответствовать имени Headless Service
  serviceName: "my-app-headless"
  replicas: 2
  selector:
    matchLabels:
      app: my-stateful-app # Должен соответствовать меткам в шаблоне
  template: # Шаблон для создания подов
    metadata:
      labels:
        app: my-stateful-app
    spec:
      containers:
      - name: nginx
        image: nginx:1.25.5
        ports:
        - containerPort: 80
          name: web
        volumeMounts:
        - name: data-volume # Имя, которое будет связано с PVC
          mountPath: /usr/share/nginx/html # Путь монтирования внутри контейнера
        env: # Добавление переменных окружения
        - name: POD_IP # Название переменной окружения
          valueFrom:
            fieldRef:
              fieldPath: status.podIP # берет из описания пода IP и прокидывает его в кнтейнер как env

  # Шаблон для автоматического создания PVC для каждого пода
  volumeClaimTemplates:
  - metadata:
      name: data-volume # Имя PVC
    spec:
      accessModes: [ "ReadWriteOnce" ]
      # storageClassName: "your-storage-class" # Укажите ваш StorageClass
      resources:
        requests:
          storage: 1Gi # Размер диска для каждого пода
```

### Шаг 3: Проверка развертывания и состояния

1. **Применить манифесты:**

    ```bash
    kubectl apply -f service-headless.yaml
    kubectl apply -f statefulset.yaml
    ```

2. **Проверить поды и PVC:**
    Поды (`my-app-0`, `my-app-1`) и PVC (`data-volume-my-app-0`, `data-volume-my-app-1`) будут созданы последовательно.

    ```bash
    kubectl get pods,pvc -l app=my-stateful-app
    ```

3. **Записать уникальные данные в каждый под:**

    ```bash
    kubectl exec my-app-0 -- /bin/sh -c 'echo "Hello from Pod 0" > /usr/share/nginx/html/index.html'
    kubectl exec my-app-1 -- /bin/sh -c 'echo "Hello from Pod 1" > /usr/share/nginx/html/index.html'
    ```

4. **Проверить восстановление состояния:**
    Удалим один из подов, чтобы увидеть, как `StatefulSet` его восстановит с тем же состоянием.

    ```bash
    kubectl delete pod my-app-1
    # ...подождите немного...
    kubectl get pods # Убедитесь, что my-app-1 снова запущен
    kubectl exec my-app-1 -- cat /usr/share/nginx/html/index.html
    # Вывод должен быть: Hello from Pod 1
    ```

5. **Проверка DNS:**
    Запустим временный под и проверим DNS-записи.

    ```bash
    kubectl run -it --rm --image=busybox dns-test -- /bin/sh
    
    # Внутри dns-test пода:
    # Запрос к сервису вернет IP обоих подов
    nslookup my-app-headless

    # Запрос к конкретному поду вернет его собственный IP
    nslookup my-app-0.my-app-headless
    ```
