# StatefulSet

## Определения

**StatefulSet** — это объект Kubernetes, предназначенный для управления приложениями, которые требуют сохранения состояния и/или стабильных сетевых идентификаторов. В отличие от [Deployment](./deployment.md), который обращается с подами как со взаимозаменяемыми "копиями", StatefulSet обеспечивает гарантии порядка и уникальности для своих подов.

Ключевая задача `StatefulSet` — обеспечить каждому поду:

1. **Стабильное, уникальное сетевое имя** в формате `<имя-StatefulSet>-<порядковый-номер>` (например, `web-0`, `web-1`).
2. **Стабильное, постоянное хранилище** через [PersistentVolumeClaim](./pv_and_pvc.md), привязанное к конкретному поду.

> **Проблема:** Стандартный [Deployment](./deployment.md) при перезапуске или переносе пода может присвоить новый IP-адрес и имя, а также **потерять связь со своим хранилищем**. Для баз данных и других stateful-приложений это равносильно потере данных.

## Основные концепции

### Ключевые отличия от Deployment

| Характеристика          | [Deployment](./deployment.md)                                            | StatefulSet                                                                            |
| ----------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------------------------------------- |
| **Предназначение**      | **Stateless**-приложения (веб-серверы, API)                              | **Stateful**-приложения (базы данных, брокеры сообщений)                                 |
| **Сетевая идентификация** | Поды взаимозаменяемы, получают **случайные** имена и IP-адреса           | Поды получают **стабильные, уникальные** имена (`<имя>-0, <имя>-1`) и DNS-записи |
| **Хранилище (Storage)**   | Обычно используют общее хранилище (`ReadOnlyMany`) или временное         | Каждый под получает свое **постоянное** хранилище ([PersistentVolumeClaim](./pv_and_pvc.md))     |
| **Стратегия обновления**  | **`RollingUpdate`**: гибкое, параллельное обновление для быстрой выкатки | **`RollingUpdate` (упорядоченный)**: последовательное обновление (сначала N-1, потом N-2) |
| **Масштабирование/Удаление** | Поды создаются и удаляются **в случайном порядке**                       | Поды создаются **по порядку** (0, 1, 2) и удаляются **в обратном порядке** (n, n-1, n-2)   |

Именно стратегия обновления является ключевым отличием, `Deployment` стремится как можно быстрее обновить поды, часто запуская новые параллельно со старыми. `StatefulSet` же обновляет поды **строго по одному**, дожидаясь, пока обновленный под станет `Ready`, прежде чем переходить к следующему. Это гарантирует целостность кластерных систем, где важен порядок.

### Ключевые компоненты

Для правильного развертывания приложений с состоянием используется комбинация из четырех ключевых компонентов:

1. **`StatefulSet`**: Главный оркестратор. Предоставляет подам стабильные имена и привязывает их к конкретным дискам.
2. **`PersistentVolumeClaim` (PVC)**: "Запрос" пода на выделение диска. `StatefulSet` автоматически создает уникальный PVC для каждого своего пода.
3. **`PersistentVolume` (PV)**: Физический "кусок" хранилища в кластере (NFS, Ceph, диск облачного провайдера), который удовлетворяет запрос PVC.
4. **`Headless Service`**: Специальный тип [сервиса](../Networking/Service/service_overview.md) с `clusterIP: None`, который обеспечивает каждому поду стабильное и уникальное DNS-имя внутри кластера.

### Стабильные, уникальные сетевые идентификаторы

* Каждый [под](./Pod/pod_overview.md) в StatefulSet получает предсказуемое имя в формате `<имя-StatefulSet>-<порядковый-номер>` (например, `web-0`, `web-1`).
* Эти имена сохраняются при перезапуске и переносе подов, что критически важно для кластерных приложений.
* Требует наличия **Headless Service** (сервис с `clusterIP: None`) для обеспечения уникальных DNS-имен для каждого пода.
* Формат DNS-записи: `pod-ordinal.service.namespace.svc.cluster.local` (например, `web-0.my-svc.default.svc.cluster.local`)

### Стабильные, постоянные хранилища

* Для каждого пода создается свой собственный [PersistentVolumeClaim](./pv_and_pvc.md) (PVC) на основе шаблона (`volumeClaimTemplates`).
* Имя PVC строится как `<имя-claim>-<имя-pod>`, например `data-web-0`.
* Этот PVC привязан к конкретному поду и сохраняется даже после его удаления и пересоздания. `StatefulSet` гарантирует, что при воссоздании пода он будет использовать тот же самый том.
* **Важно:** При удалении `StatefulSet` связанные с ним PVC **не удаляются** автоматически. Это сделано для защиты данных. Их необходимо удалять вручную.

### Упорядоченное развертывание и масштабирование

* **Создание:** Поды создаются последовательно, один за другим (сначала `web-0`, потом `web-1`). Следующий под не начнет создаваться, пока предыдущий не станет `Ready`.
* **Удаление:** Поды удаляются в обратном порядке (сначала `web-n`, потом `web-n-1`).
* **Параметр `podManagementPolicy`:**
  - `OrderedReady` (по умолчанию): обеспечивает строгий порядок и ожидание готовности.
  - `Parallel`: создаёт/удаляет Pod'ы параллельно, если порядок не критичен.
* **`updateStrategy`:**
  - `RollingUpdate` с `partition` позволяет обновлять только Pod'ы с индексом ≥ `partition`, сохраняя нижние индексы нетронутыми.
  - `OnDelete` применяет новую спецификацию только к Pod'ам, которые вы удалите вручную.

### Особое поведение при сбоях

* **Недоступность узла:** Если нода становится `NotReady`, Kubernetes **не будет** автоматически переносить под `StatefulSet` на другую ноду. Это сделано для защиты данных и предотвращения сценариев split-brain, особенно для баз данных. Перенос пода с `ReadWriteOnce` томом требует ручного вмешательства или использования операторов.
* **Обработка `SIGTERM`:** `StatefulSet` может ожидать более длительное время при получении сигнала `SIGTERM`, что позволяет приложениям с состоянием корректно завершить работу, сохранить данные и отсоединиться от кластера.

# Практические сценарии

## Сценарий использования: Stateful-приложения (Kafka, базы данных)

`StatefulSet` является единственным правильным выбором для запуска приложений, которые требуют стабильного хранения данных и сетевой идентификации. Классический пример — **Apache Kafka**.

**Проблема:** Если развернуть Kafka с помощью `Deployment`, при любом рестарте пода (из-за сбоя ноды, обновления или масштабирования) он потеряет связь со своим диском (`PersistentVolume`). `Deployment` создает новый под как "чистый лист", без привязки к состоянию предыдущего. Это неминуемо приведет к **потере данных** в брокере Kafka.

**Решение с `StatefulSet`:**

`StatefulSet` решает эту проблему, предоставляя каждому поду:

1. **Стабильное имя**: `kafka-0`, `kafka-1`, и т.д.
2. **Стабильный PVC**: Для `kafka-0` будет автоматически создан и привязан PVC `data-kafka-0`, для `kafka-1` — `data-kafka-1`.

При рестарте пода `kafka-0` (даже на другой ноде) `StatefulSet` гарантирует, что он будет снова подключен к своему уникальному PVC `data-kafka-0`, сохраняя все данные.

## Пример: Развертывание Nginx с StatefulSet

Развернем простое stateful-приложение на базе Nginx, где каждый экземпляр будет иметь свой собственный, постоянный `index.html`.

### Шаг 1: Создание Headless Service

Необходимо для присвоения подам уникальных DNS-имен в формате `<pod-name>.<service-name>.<namespace>.svc.cluster.local`.

```yaml
# service-headless.yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-headless
spec:
  clusterIP: None # <-- Ключевой параметр, делающий сервис "безголовым"
  selector:
    app: my-stateful-app # Должен соответствовать меткам подов
  ports:
  - port: 80
    name: web
```

### Шаг 2: Создание StatefulSet

```yaml
# statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: my-app
spec:
  # serviceName должен соответствовать имени Headless Service
  serviceName: "my-app-headless"
  replicas: 2
  selector:
    matchLabels:
      app: my-stateful-app # Должен соответствовать меткам в шаблоне
  template: # Шаблон для создания подов
    metadata:
      labels:
        app: my-stateful-app
    spec:
      containers:
      - name: nginx
        image: nginx:1.25.5
        ports:
        - containerPort: 80
          name: web
        volumeMounts:
        - name: data-volume # Имя, которое будет связано с PVC
          mountPath: /usr/share/nginx/html # Путь монтирования внутри контейнера
        env: # Добавление переменных окружения
        - name: POD_IP # Название переменной окружения
          valueFrom:
            fieldRef:
              fieldPath: status.podIP # берет из описания пода IP и прокидывает его в контейнер как env

  # Шаблон для автоматического создания PVC для каждого пода
  volumeClaimTemplates:
  - metadata:
      name: data-volume # Имя PVC
    spec:
      accessModes: [ "ReadWriteOnce" ]
      # storageClassName: "your-storage-class" # Укажите ваш StorageClass
      resources:
        requests:
          storage: 1Gi # Размер диска для каждого пода
```

### Шаг 3: Проверка развертывания и состояния

**Применить манифесты:**

```bash
kubectl apply -f service-headless.yaml
kubectl apply -f statefulset.yaml
```

**Проверить поды и PVC:**

Поды (`my-app-0`, `my-app-1`) и PVC (`data-volume-my-app-0`, `data-volume-my-app-1`) будут созданы последовательно.

```bash
kubectl get pods,pvc -l app=my-stateful-app
```

**Записать уникальные данные в каждый под:**

```bash
kubectl exec my-app-0 -- /bin/sh -c 'echo "Hello from Pod 0" > /usr/share/nginx/html/index.html'
kubectl exec my-app-1 -- /bin/sh -c 'echo "Hello from Pod 1" > /usr/share/nginx/html/index.html'
```

**Проверить восстановление состояния:**

Удалим один из подов, чтобы увидеть, как `StatefulSet` его восстановит с тем же состоянием.

```bash
kubectl delete pod my-app-1
# ...подождите немного...
kubectl get pods # Убедитесь, что my-app-1 снова запущен
kubectl exec my-app-1 -- cat /usr/share/nginx/html/index.html
# Вывод должен быть: Hello from Pod 1
```

**Проверка DNS:**

```bash
kubectl run -it --rm --image=busybox dns-test -- /bin/sh

# Внутри dns-test пода:
# Запрос к сервису вернет IP обоих подов
nslookup my-app-headless

# Запрос к конкретному поду вернет его собственный IP
nslookup my-app-0.my-app-headless
```

# Дополнительная информация

## Лучшие практики

*   **Используйте PodDisruptionBudget** для защиты от плановых выселений при обслуживании нод. См. [Высокая доступность](./high_availability.md).
*   **Настройте readinessProbe** для корректного определения готовности пода к приему трафика.
*   **Используйте `volumeBindingMode: WaitForFirstConsumer`** в StorageClass для корректного размещения томов.
*   **Регулярно делайте бэкапы** PVC, даже несмотря на их постоянство.
*   **Применяйте podAntiAffinity** для распределения подов по разным зонам доступности.

## Сравнение поведения Pod'ов

| Аспект      | StatefulSet Pod                                | [Deployment](./deployment.md) Pod                         |
| :---------- | :--------------------------------------------- | :-------------------------------------------------------- |
| Имя и индекс | Стабильные, с порядком (0..N-1)                  | Эфемерные имена без порядка                               |
| DNS         | Предсказуемые записи per-Pod                     | Сервисный адрес без гарантии на Pod-идентичность          |
| Хранилище   | Отдельный PVC на Pod, сохраняется                | Общие шаблоны Volumes, без индивидуального PVC            |
| Порядок     | Управляемый (Ordered/Parallel)                   | Нет гарантий порядка                                      |
