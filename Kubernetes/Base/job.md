# Job и CronJob

## Определения

**Job** в Kubernetes — это объект, который создаёт один или несколько подов и гарантирует, что определённое количество из них успешно завершит свою работу (**exit code 0**).

В отличие от [Deployment](../Deployment/index.md), который ориентирован на приложения, работающие постоянно (контроллер следит, чтобы под был "жив"), `Job` следит за тем, чтобы задача была **выполнена до конца**. Если под упал — Job перезапустит его, пока задача не выполнится или не исчерпается лимит попыток.

**CronJob** — это контроллер, который по расписанию (классический cron-синтаксис) создаёт объекты `Job`. Сам он ничего не выполняет — только штампует Job'ы в нужный момент.

### Ключевые сценарии использования

* **Миграции базы данных:** Применение схемы или перенос данных.
* **Резервное копирование:** Создание бэкапов данных из томов (`PersistentVolume`).
* **Обработка данных:** Запуск скриптов для анализа, очистки или **ETL (Extract, Transform, Load)** процессов.
* **Запуск тестов:** Выполнение тестов в изолированном окружении.
* **Регулярные отчеты** или отправка email-сообщений.

## Основные концепции

### Концепции Job

* **`template`**: Обязательное поле, описывающее шаблон пода для запуска.
* **`restartPolicy`**: Определяет политику перезапуска контейнеров в поде. Для `Job` допустимы только:
  * `OnFailure`: Перезапускать контейнер, если он завершился с ошибкой.
  * `Never`: Никогда не перезапускать контейнер. `Job` сам управляет созданием новых подов в случае неудачи.

  **Важно:** В отличие от Deployment, где kubelet перезапускает поды, в Job решение о перезапуске принимает контроллер Job, а не kubelet.
* **`completions`**: Количество подов, которые должны успешно завершиться. Так реализуется параллельная обработка очереди. По умолчанию `1`.
* **`parallelism`**: Сколько подов могут работать одновременно. По умолчанию `1`.
* **`backoffLimit`**: Количество повторных попыток перед тем, как `Job` будет помечен как неудавшийся (`failed`). По умолчанию `6`. При каждой неудачной попытке интервал между запусками увеличивается (**exponential backoff**).
* **`activeDeadlineSeconds`**: Жёсткий таймаут на всю задачу (в секундах). Если время истекло, Job и все его поды будут завершены и помечены как failed.
* **`ttlSecondsAfterFinished`**: Автоочистка завершённых Job. Kubernetes автоматически удалит объект `Job` (и его поды) через указанное время после завершения. Без этого параметра завершённые поды и объекты Job копятся в кластере бесконечно.
* **`suspend`**: Позволяет приостановить выполнение `Job`. Если `true`, новые поды не создаются, а существующие могут быть завершены (в зависимости от настроек).
* **`managedBy`**: (Стабильно с v1.35) Позволяет явно указать, какой контроллер отвечает за управление `Job`. [Подробнее](#делегированное-управление-job-с-specmanagedby).
* **Изменение ресурсов (v1.36+)**: Возможность изменять ресурсы (CPU, память, GPU) в шаблоне пода приостановленного `Job` без его пересоздания. [Подробнее](#изменение-ресурсов-в-приостановленных-job-v136).

### Концепции CronJob

`CronJob` создаёт объекты `Job` на основе `jobTemplate` по расписанию.

* **`schedule`**: Расписание в формате `cron` (например, `"0 2 * * *"` — каждый день в 2 часа ночи).
* **`timeZone`**: Позволяет указать временную зону для расписания (например, `Europe/Moscow`). Если не указано, используется время сервера API.
* **`jobTemplate`**: Шаблон для создания `Job`.
* **`startingDeadlineSeconds`**: Если запуск был пропущен (например, control plane был недоступен), в течение этого окна CronJob ещё попытается его выполнить.
* **`concurrencyPolicy`**: Что делать, если предыдущий запуск ещё не завершился:
  * `Allow` (по умолчанию): Запускать Job параллельно. Для долгих задач это частый источник проблем.
  * `Forbid`: Пропустить новый запуск, пока работает старый.
  * `Replace`: Убить старый Job и запустить новый.
* **`successfulJobsHistoryLimit`**: Количество успешно завершенных `Job` для хранения (по умолчанию `3`).
* **`failedJobsHistoryLimit`**: Количество неудачно завершенных `Job` для хранения (по умолчанию `1`).

## Практические сценарии

### Пример манифеста Job

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: db-migration
spec:
  backoffLimit: 3               # максимум 3 повторные попытки
  activeDeadlineSeconds: 600    # убить задачу, если не уложилась в 10 минут
  ttlSecondsAfterFinished: 3600 # автоочистка Job через час после завершения
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: migrate
        image: myapp:1.07
        command: ["python", "manage.py", "migrate"]
```

### Пример манифеста Job с делегированным управлением

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: managed-externally
spec:
  managedBy: argo-workflows-controller  # Указываем внешний контроллер
  template:
    spec:
      containers:
      - name: data-processor
        image: data-processor:v1.2.0  # Избегайте :latest в production
        command: ["process", "--dataset", "daily"]
      restartPolicy: OnFailure
```

### Пример манифеста CronJob

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: report-generator
spec:
  schedule: "0 3 * * *"          # каждый день в 03:00
  timeZone: "Europe/Moscow"      # явное указание часового пояса
  concurrencyPolicy: Forbid       # не запускать новый, пока работает старый
  startingDeadlineSeconds: 300
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 5
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: Never
          containers:
          - name: report
            image: reports:2.1
```

### Управление через kubectl

1. **Создать:**

    ```bash
    kubectl apply -f my-job.yaml
    kubectl apply -f my-cronjob.yaml
    ```

2. **Проверить статус:**

    ```bash
    # Посмотреть список
    kubectl get jobs
    kubectl get cronjobs

    # Получить детальную информацию
    kubectl describe job my-job
    kubectl describe cronjob backup-cronjob
    ```

3. **Посмотреть логи:**
    Сначала найдите имя пода, созданного `Job`:

    ```bash
    kubectl get pods --selector=job-name=my-job
    ```

    Затем посмотрите его логи:

    ```bash
    kubectl logs <имя-пода>
    ```

4. **Удалить:**
    При удалении `Job` также удаляются все созданные им поды. При удалении `CronJob` удаляются все `Job`, которые он создал.

    ```bash
    kubectl delete job my-job
    kubectl delete cronjob backup-cronjob
    ```

## Дополнительная информация

### Делегированное управление Job (с .spec.managedBy)

В Kubernetes 1.35 стало стабильным поле `.spec.managedBy` для ресурсов Job. Оно позволяет явно указать, какой внешний контроллер отвечает за управление задачей.

**Зачем делегировать управление Job:**

* **Сложная логика выполнения:** Внешние контроллеры могут реализовывать продвинутые сценарии.
* **Интеграция с экосистемой:** Системы оркестрации рабочих процессов (например, Argo Workflows, JobSet, Kubeflow Trainer, KubeRay, Tekton Pipelines) получают нативный способ управления созданными через них заданиями.
* **Чёткое разделение ответственности:** Исключаются конфликты между встроенным контроллером Kubernetes и внешними системами.
* **Упрощение отладки:** По значению поля `managedBy` сразу понятно, какая система управляет задачей.

**Как работает .spec.managedBy:**

* Встроенный контроллер Kubernetes видит поле `managedBy` и игнорирует управление этим `Job`.
* Внешний контроллер (например, Argo Workflows) отслеживает `Job` с такой меткой и берёт на себя весь жизненный цикл (перезапуски, обработка завершения).

**Ограничения:**

* Поле `.spec.managedBy` **неизменяемое** (immutable) — передача запущенного Job другому контроллеру запрещена.
* Значение `unset` или `kubernetes.io/job-controller` — стандартный встроенный контроллер.
* Любое другое значение — встроенный контроллер пропускает reconcile, управление передается внешнему контроллеру.

Подробнее: [Kubernetes v1.35: Job .spec.managedBy for Jobs Goes GA](https://kubernetes.io/blog/2025/12/18/kubernetes-v1-35-job-managedby-for-jobs-goes-ga/).

### Изменение ресурсов в приостановленных Job (v1.36+)

Начиная с Kubernetes v1.36 (бета, включено по умолчанию), можно изменять ресурсы (CPU, память, GPU) в шаблоне пода (`podTemplate`) у приостановленного Job без необходимости его пересоздания. Это избавляет от необходимости удаления и повторного создания объекта, что сохраняет историю выполнения и метаданных.

**Условия для изменения ресурсов:**

1. `spec.suspend` должно быть установлено в `true`.
2. У Job не должно быть активных подов (`status.active == 0`).

**Технические детали:**

* **`podReplacementPolicy: Failed`**: Рекомендуется использовать эту политику, если Job уже запускался. Это гарантирует, что старые поды полностью завершатся перед созданием новых с обновлёнными ресурсами.
* **Ограничения:**
  * API-сервер отклонит изменения, если `status.active > 0`.
  * **DRA (Dynamic Resource Allocation)**: Поля `resourceClaimTemplates` остаются неизменяемыми.
  * Нельзя уменьшать лимиты ниже реквестов; расширенные ресурсы (extended resources) должны быть целыми числами.

**Включение функции:**

* **v1.36+**: Включено по умолчанию.
* **v1.35**: Требуется feature gate `--feature-gates=MutablePodResourcesForSuspendedJobs=true`.

Это особенно полезно для систем очередей (например, Kueue), которые могут динамически подбирать ресурсы под текущую загрузку кластера перед запуском задачи.

### Поведение подов после завершения Job

После завершения Job (успешно или с ошибкой), поды **не удаляются автоматически**. Они остаются в кластере как записи в etcd. Это позволяет:

* Просматривать логи завершённых подов
* Использовать `kubectl describe` для отладки

Для автоматической очистки подов после завершения используется `ttlSecondsAfterFinished`.

### Отладка через Events

Для диагностики проблем с Job полезно использовать:

```bash
kubectl events --namespace <namespace>
```

События покажут историю создания, планирования и завершения подов.
