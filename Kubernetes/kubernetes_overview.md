# Kubernetes: Обзор и ключевые концепции

## Определение

**Kubernetes** (K8s) — открытая платформа для автоматизации развёртывания, масштабирования и управления контейнеризированными приложениями. Она оркестрирует контейнеры на кластере хостов, абстрагируя приложения от нижележащей инфраструктуры и обеспечивая декларативное управление жизненным циклом ПО.

### Исторический контекст

Использование контейнеров опирается на механизмы изоляции ядра Linux: **cgroups** (контрольные группы) и **namespaces** (пространства имён).

- **2002–2009:** Формирование технологий изоляции в ядре Linux.
- **2014:** Выпуск Kubernetes компанией Google (на основе внутреннего опыта с системой Borg).
- **2015–н.в.:** Передача проекта в Cloud Native Computing Foundation (CNCF) и становление стандартом де-факто для облачной оркестрации.

### Основные решаемые задачи

Главная цель Kubernetes — автоматизация эксплуатации распределённых систем.

| Задача | Описание |
| :--- | :--- |
| **Масштабирование** | Горизонтальное (HPA) и вертикальное (VPA) масштабирование ресурсов и реплик |
| **Балансировка нагрузки** | Распределение трафика между подами через Service или Gateway API |
| **Service Discovery** | Автоматическое обнаружение сервисов через внутренний DNS кластера |
| **Self-healing** | Автоматический перезапуск упавших контейнеров и перенос нагрузки при сбое узлов |
| **Управление конфигурацией** | Разделение кода приложения и его настроек (ConfigMap, Secret) |
| **Оркестрация ресурсов** | Выделение CPU, памяти и специализированных ресурсов (GPU через DRA) |

## Основные концепции

### Декларативный подход и цикл согласования

Kubernetes работает по принципу **цикла согласования** (reconciliation loop):

1. **Желаемое состояние:** Пользователь описывает объект в YAML-манифесте.
2. **Текущее состояние:** Контроллеры Kubernetes постоянно отслеживают реальное положение дел.
3. **Согласование:** Если состояния различаются, контроллер предпринимает действия для их выравнивания (например, запускает новый под вместо удаленного).

### Архитектура кластера

Кластер состоит из двух логических уровней:

#### Панель управления (Control Plane)

«Мозг» кластера, координирующий все процессы. Основные компоненты:

- **`kube-apiserver`** — центральный шлюз, через который проходят все запросы. Единственный компонент, взаимодействующий с хранилищем. Подробнее: [Архитектура Control Plane](./Concepts/control_plane_architecture.md).
- **`etcd`** — высокодоступное распределённое хранилище всех данных кластера. Подробнее: [Обзор etcd](./Concepts/etcd_overview.md).
- **`kube-scheduler`** — выбирает оптимальный узел для запуска пода на основе ресурсов и политик. Подробнее: [kube-scheduler](./Concepts/kube_scheduler.md).
- **`kube-controller-manager`** — объединяет набор контроллеров (Node, Deployment, Namespace), следящих за состоянием ресурсов.

#### Рабочие узлы (Worker Nodes)

Узлы, непосредственно выполняющие полезную нагрузку:

- **`kubelet`** — агент, обеспечивающий запуск контейнеров и проверку их состояния. Подробнее: [Kubelet](./Concepts/kubelet.md).
- **`kube-proxy`** — сетевой агент, управляющий правилами трафика. В современных версиях (v1.31+) поддерживает режим **nftables**. Подробнее: [CNI и kube-proxy](./Networking/Network/cni_kube_proxy_roles.md).
- **Container Runtime (CRI)** — среда выполнения (`containerd`, `CRI-O`). Традиционный Docker деприкейтирован в пользу CRI-совместимых решений.
- **CNI** (Container Network Interface) — сетевые плагины (Cilium, Calico), обеспечивающие связность подов. Подробнее: [Сетевая модель](./Networking/Network/network_overview.md).

### Ключевые абстракции

| Абстракция | Назначение |
| :--- | :--- |
| **Pod** | Минимальная единица развёртывания. Поддерживает **нативные Sidecar-контейнеры** (с версии 1.29). Подробнее: [Pod overview](./Base/Pod/pod_overview.md) |
| **Deployment** | Декларативное управление репликами и стратегиями обновления (RollingUpdate). Подробнее: [Deployment overview](./Base/Deployment/index.md) |
| **Service** | Стабильный IP и DNS-имя для группы подов. Подробнее: [Service overview](./Networking/Service/service_overview.md) |
| **Gateway API** | Современный стандарт управления трафиком, заменяющий Ingress. Подробнее: [Gateway API](./Networking/gateway_api/definitions.md) |
| **Volume / PVC** | Абстракция хранилища данных. Подробнее: [CSI overview](./Storage/CSI/csi_overview.md) |
| **Namespace** | Логическая изоляция ресурсов внутри одного кластера. Подробнее: [Namespace](./Base/namespace.md) |

### Безопасность и стандарты

- **PSA (Pod Security Admission):** Современный механизм контроля безопасности подов (заменяет PSP). Предлагает три уровня профилей: Privileged, Baseline, Restricted.
- **User Namespaces:** Изоляция пользователей внутри контейнера для предотвращения выхода на хост (Container Breakout).
- **CEL (Common Expression Language):** Используется для декларативного описания политик валидации (ValidatingAdmissionPolicy), заменяя сложные вебхуки.

## Практические сценарии

### Когда использовать Kubernetes

- **Микросервисы:** когда количество сервисов растет и ручное управление становится невозможным.
- **Высокая нагрузка:** требуется динамическое масштабирование и эффективное использование ресурсов.
- **Гибридные облака:** переносимость приложений между разными провайдерами (AWS, GCP, Yandex Cloud, Bare Metal).
- **AI/ML задачи:** использование **Dynamic Resource Allocation (DRA)** для гибкого распределения GPU.

### Когда Kubernetes может быть избыточен

- **Простые монолиты:** достаточно одного сервера или Docker Compose.
- **Малые команды:** сложность эксплуатации может превысить выгоды от автоматизации.
- **Статичные нагрузки:** когда инфраструктура не меняется месяцами.
