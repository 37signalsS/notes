# Kubernetes: Обзор и решаемые проблемы

## Что такое Kubernetes?

**Kubernetes** (часто сокращается как K8s) — это открытая система для автоматизации развёртывания, масштабирования и управления контейнеризированными приложениями. По сути, это мощная платформа для управления кластерами контейнеров Linux, позволяющая запускать и управлять ими на большом количестве хостов, а также обеспечивать их размещение и репликацию.

## Какую проблему решает Kubernetes?

Kubernetes был создан для решения сложностей, связанных с управлением микросервисными и контейнеризированными приложениями в масштабе. Он предоставляет высокоуровневый API для группировки, размещения и балансировки контейнеров.

### Основные решаемые задачи:

1.  **Масштабирование и запуск контейнеров:** Управление развёртыванием и масштабированием контейнеров на большом количестве хостов.
2.  **Балансировка нагрузки:** Автоматическое распределение трафика между контейнерами для обеспечения высокой доступности и производительности.
3.  **Автоматизация инфраструктуры:**
    *   Развертывание приложений и их обновление (rolling updates).
    *   Откат к предыдущим версиям (rollbacks) в случае проблем.
4.  **Self-healing (Самовосстановление):** Kubernetes постоянно мониторит состояние кластера и сравнивает его с желаемым состоянием. Если контейнер падает или узел выходит из строя, Kubernetes автоматически перезапускает контейнеры или переносит их на здоровые узлы.
5.  **Service Discovery:** Позволяет сервисам автоматически находить друг друга в кластере без жесткого кодирования IP-адресов.
6.  **Управление ресурсами:** Эффективное распределение ресурсов (CPU, память) между приложениями.
7.  **Управление конфигурацией и секретами:** Безопасное хранение и предоставление конфигурационных данных и чувствительной информации (пароли, ключи) приложениям.
8.  **Мониторинг и логирование:** Предоставляет механизмы и точки интеграции для сбора метрик и логов из приложений и компонентов кластера.
9.  **CI/CD интеграция:** Упрощает автоматизацию процессов непрерывной интеграции и доставки.
10. **Уменьшение Vendor Lock-in:** Абстрагирует приложения от нижележащей инфраструктуры, делая их менее зависимыми от конкретного оборудования или облачного провайдера. Вы взаимодействуете с API Kubernetes, а он, как "черный ящик", берет на себя выполнение задач в любой совместимой среде.

### Пример проблемы и ее решение с Kubernetes

**Проблема:** У вас есть три машины (узла), на которых запущены контейнеры с вашими приложениями. Внезапно одна из машин выходит из строя или требует перезагрузки для обслуживания. Вам необходимо перенести запущенные на ней контейнеры.

**Без Kubernetes это приводит к следующим сложностям:**

*   **Ручной перенос и связанность:** Контейнеры могут быть тесно связаны между собой (например, используют общие данные или активно взаимодействуют). При ручном переносе нужно обеспечить, чтобы эти связанные контейнеры были перемещены вместе на другую ноду, сохранив их взаимосвязь.
*   **Ограничения ресурсов:** Контейнеры могут не "поместиться" на одном оставшемся узле из-за нехватки ресурсов (CPU, памяти). Приходится вручную определять, куда и как распределить контейнеры, чтобы избежать перегрузки.
*   **Возврат в строй:** Когда отказавшая нода возвращается в рабочее состояние, требуется повторный перенос контейнеров обратно для оптимального распределения нагрузки, что снова влечет за собой ручные манипуляции.

**Как Kubernetes решает эту проблему:**

В Kubernetes вы декларативно описываете желаемое состояние ваших приложений (например, "всегда должно быть запущено 3 экземпляра этого приложения" или "эти контейнеры всегда должны работать вместе на одной ноде").

1.  **Автоматическое обнаружение сбоев:** Kubernetes непрерывно мониторит состояние всех узлов и подов. Как только один из узлов выходит из строя, `kube-controller-manager` это обнаруживает.
2.  **Автоматическое перепланирование:** `kube-scheduler` автоматически определяет новые подходящие узлы для контейнеров, которые работали на отказавшем узле. Он учитывает требования к ресурсам (CPU, память), аффинность/анти-аффинность подов (для сохранения связанности или распределения) и другие политики размещения.
3.  **Запуск на новых узлах:** `kubelet` на новых узлах получает инструкции и запускает необходимые контейнеры, восстанавливая работоспособность приложений.
4.  **Восстановление баланса:** При возвращении отказавшего узла в строй Kubernetes может автоматически (или по вашим правилам) перераспределить поды для оптимальной утилизации ресурсов кластера.

## Версионирование API (API Versioning)

В манифестах Kubernetes поле `apiVersion` указывает версию API, которая используется для создания объекта. Версия API определяет структуру и схему объекта.

**Примеры:** `v1`, `apps/v1`, `batch/v1`, `rbac.authorization.k8s.io/v1`.

Версии API делятся на три уровня стабильности:

*   **Alpha-версии** (`v1alpha1`, `v2alpha1`, ...):
    *   Отключены по умолчанию.
    *   Могут содержать баги.
    *   Поддержка может быть прекращена в любое время без предупреждения.
    *   Совместимость с будущими версиями не гарантируется.
    *   **Не рекомендуется использовать в production.**

*   **Beta-версии** (`v1beta1`, `v2beta1`, ...):
    *   Включены по умолчанию.
    *   Хорошо протестированы.
    *   Поддержка не будет прекращена, но семантика и детали объектов могут измениться в будущих beta- или стабильных релизах.
    *   При изменениях предоставляется инструкция по миграции.
    *   **Не рекомендуется использовать в production**, но можно использовать в dev/staging для тестирования новых функций.

*   **Стабильные (Stable) версии** (`v1`, `v2`, ...):
    *   Готовы для использования в production.
    *   Схемы объектов будут совместимы с будущими версиями в рамках одной мажорной версии (например, `v1`).

## Архитектура кластера Kubernetes

*   **Control Plane (Мастер-узлы):**

    *   **Количество:** Минимум 3 узла для кворума `etcd` и отказоустойчивости управляющего слоя.
    *   **Назначение:** Исключительно для компонентов Control Plane (`etcd`, `api-server`, `scheduler`, `controller-manager`). Не должны запускать пользовательские рабочие нагрузки.

*   **Ingress-узлы:**

    *   **Количество:** Минимум 2 узла.
    *   **Назначение:** Выделенные узлы для запуска Ingress-контроллеров (например, Nginx, Traefik).
    *   **Сеть:** Должны иметь публичные ("белые") IP-адреса для приема трафика извне. Это изолирует входящий трафик и его обработку от основных приложений.

*   **Worker-узлы (Воркеры):**

    *   **Назначение:** Для запуска основных приложений и сервисов.

## Требования к узлам

### Конфигурация операционной системы

*   **Отключение Swap:** Swap-раздел должен быть отключен. `kubelet` не предназначен для работы со swap-памятью, так как это вносит непредсказуемость в управление ресурсами пода. Kubernetes ожидает, что поды будут использовать только выделенную им RAM, и при нехватке памяти должен убивать процессы (OOMKilled), а не замедлять их через swap.

*   **Файрвол:** Файрвол (например, `ufw`, `firewalld`) должен быть включен на всех узлах. Kubernetes сам управляет необходимыми правилами `iptables` для сетевого взаимодействия, но базовый файрвол обеспечивает дополнительный уровень защиты для ОС.

*   **Версия ядра Linux > 5.x:**

    *   **Причина:** Современные версии ядра Linux предоставляют критически важные функции для производительности, безопасности и функциональности Kubernetes.
    *   **Ключевые преимущества:**
        *   **cgroups v2:** Обеспечивает более унифицированный и эффективный механизм управления ресурсами (CPU, память), чем cgroups v1.
        *   **eBPF (extended Berkeley Packet Filter):** Является основой для современных сетевых решений (например, Cilium) и инструментов безопасности, которые работают с высокой производительностью прямо на уровне ядра.
        *   **Улучшенная безопасность:** Новые ядра включают более совершенные механизмы изоляции и защиты, такие как улучшенная поддержка пространств имен пользователей (user namespaces) и шифрования памяти.

### Аппаратные ресурсы

Ниже приведены минимальные рекомендации для производственной среды.

*   **Мастер-узел:**

    *   **CPU:** > 2 ядер
    *   **RAM:** > 4 ГБ

*   **Ingress-узел:**

    *   **CPU:** > 1 ядра
    *   **RAM:** > 2 ГБ

*   **Worker-узел:**

    *   **CPU:** > 2 ядер
    *   **RAM:** > 4 ГБ

## Стратегия для Worker-узлов

### "Много маленьких" вместо "мало больших"

Предпочтительной является стратегия использования большого количества воркеров с относительно небольшими ресурсами вместо малого числа очень мощных серверов.

*   **Преимущество:** Уменьшается "радиус взрыва" (blast radius). Потеря одного из 20 "маленьких" воркеров менее ощутима для общей производительности кластера, чем отказ одного из 3 "больших" воркеров, на котором может быть сконцентрирована треть всей нагрузки.
*   **Гибкость:** Такая архитектура упрощает масштабирование и обслуживание, так как вывод одного узла из эксплуатации затрагивает меньшую долю приложений.

## Компоненты Control Plane (master-ноды)

### `etcd`

*   **Роль:** **Память и единственный источник правды кластера.** Распределенное хранилище типа "ключ-значение".
*   **Описание:** Это отказоустойчивое, строго согласованное и распределённое хранилище типа "ключ-значение", где Kubernetes хранит всю конфигурацию и состояние кластера. База данных о состоянии кластера по-сути. Любое изменение в кластере начинается с записи в `etcd`. Хотя `etcd` является неотъемлемой частью архитектуры Kubernetes, это независимый проект с открытым исходным кодом, который разрабатывался отдельно и также состоит в CNCF.
*   **Ключевые механизмы:**
    *   **Raft:** Алгоритм консенсуса, который обеспечивает отказоустойчивость и согласованность данных между несколькими узлами `etcd`.
    *   **Watch:** Механизм подписки на изменения. Другие компоненты (например, `kube-scheduler`) "следят" за изменениями в `etcd`, чтобы реагировать на них в реальном времени.
    *   **Snapshotting:** Периодическое создание снимков данных для восстановления кластера после сбоев.

### `kube-apiserver` (API-сервер)

*   **Роль:** Центральный компонент и "фронтенд" управляющей плоскости. С ним взаимодействуют все компоненты. Он является центральным узлом.
*   **Ключевые функции:**
    *   Принимает и обрабатывает запросы по REST API (JSON и YAML).
    *   Предоставляет HTTP/HTTPS API, через которое взаимодействуют все остальные компоненты, пользователи (`kubectl`) и внешние системы.
    *   Является **единственным компонентом**, который напрямую взаимодействует с `etcd`.
    *   Обрабатывает все REST-запросы на изменение состояния объектов (создание пода, обновление сервиса и т.д.).

*   **Процесс обработки запроса (например, при создании Pod'а):**
    1.  **Валидация манифеста:** API-сервер проверяет синтаксис и корректность манифеста, удостоверяясь, что все необходимые поля заполнены и соответствуют спецификациям Kubernetes.
    2.  **Аутентификация и авторизация:** Удостоверяется в подлинности пользователя и проверяет его права на выполнение данной операции.
    3.  **Обработка запроса:** После успешной валидации и проверки прав, API-сервер обрабатывает запрос на создание нового объекта Pod.
    4.  **Сохранение состояния в `etcd`:** API-сервер сохраняет информацию о новом Pod'е в распределённом хранилище данных `etcd`.

### `kube-scheduler` (Планировщик)

*   **Роль:** **Диспетчер или логист.** Планирует, на каком узле запустить то или иное приложение.
*   **Описание:** Его задача — назначать новосозданные поды на подходящие рабочие узлы. Он отслеживает поды без назначенного узла и выбирает для них оптимальное место для запуска. Распределение выполняется на основании настроек и текущего использования ресурсов. Процесс планирования состоит из нескольких этапов:

    1.  **Фильтрация (Filtering):** Планировщик исключает узлы, которые не соответствуют требованиям Pod'а. Например, по количеству CPU или памяти, узлы с недостаточными ресурсами будут отфильтрованы. Учитываются такие параметры, как `nodeSelectors`, `taints` и `tolerations`, а также совместимость с архитектурой процессора.

    2.  **Оценка (Scoring):** После фильтрации оставшиеся узлы оцениваются по различным критериям, чтобы определить наиболее подходящий. Планировщик присваивает каждому узлу оценку на основе таких факторов, как близость к необходимым данным (локальность образов), количество уже запущенных Pod'ов и другие пользовательские метрики. Узел с наивысшей оценкой выбирается для размещения Pod'а.

    3.  **Привязка к узлу (Binding):** После выбора подходящего узла планировщик обновляет информацию в API-сервере, связывая Pod с выбранным узлом (записывая `spec.nodeName`). После этого компонент `kubelet` на этом узле "видит" новый Pod и начинает процесс его запуска.

### `kube-controller-manager` (Менеджер контроллеров)

*   **Роль:** **Команда менеджеров-контроллеров.**
*   **Описание:** Это один процесс, который для эффективности объединяет в себе множество контроллеров. Каждый контроллер — это фоновый цикл, который следит за определенным аспектом кластера, следит за состоянием кластера и вносит изменения для приведения *фактического* состояния кластера к *желаемому* (записанному в `etcd`). Мы говорим Kubernetes, что мы хотим видеть в конечном статусе.
    *   **Node Controller:** Реагирует на отказы узлов.
    *   **Deployment/ReplicaSet Controller:** Поддерживает заданное количество реплик пода.
    *   **Endpoints Controller:** Обновляет объект `Endpoints`, связывая `Service` с IP-адресами подов.

## Компоненты Worker Node 

### `kubelet`

*   **Роль:** Главный агент Kubernetes на каждом рабочем узле.
*   **Ключевые функции:**
    *   Служба, которая опрашивает API-сервер на предмет того, какие поды предназначены узлу (на котором служба находится).
    *   Запускает и удаляет поды через Container Runtime Engine (например, Docker, containerd, CRI-O).
    *   Регистрирует узел в кластере и следит за инструкциями от `API-сервера`.
    *   Гарантирует, что контейнеры, описанные в спецификациях подов, запущены и работают корректно.
    *   Взаимодействует со средой выполнения контейнеров (например, `containerd`) для управления жизненным циклом контейнеров.
    *   Выполняет пробы (`liveness`, `readiness`, `startup`).
    *   Информирует API-сервер о статусе работающих подов на узле.
    *   Передаёт `API-серверу` отчеты о состоянии узла и подов.

*   **Процесс инициализации Pod'а:**

    После того как `kube-scheduler` назначает Pod на узел, `kubelet` на этом узле выполняет следующие шаги:
    1.  **Получение спецификации Pod'а:** Kubelet получает описание Pod'а от API-сервера.
    2.  **Проверка и подготовка среды:** Проверяет доступность необходимых ресурсов на узле, настраивает сетевые интерфейсы и создает тома для хранения данных.
    3.  **Запуск init-контейнеров:** Если в спецификации указаны init-контейнеры, `kubelet` последовательно запускает их. Они выполняют подготовительные задачи перед запуском основных контейнеров.
    4.  **Запуск основных контейнеров:** Запускает основные контейнеры Pod'а с помощью среды выполнения контейнеров.
    5.  **Мониторинг состояния:** Непрерывно отслеживает состояние запущенных контейнеров.
    6.  **Обновление статуса Pod'а:** Постоянно обновляет статус Pod'а в API-сервере, отражая текущее состояние контейнеров.

### `kube-proxy`

*   **Роль:** Сетевой прокси, отвечающий за реализацию сетевой модели Kubernetes на каждом узле.
*   **Ключевые функции:**
    *   Компонент, управляющий сетевыми настройками узла.
    *   Поддерживает сетевые правила на узле, которые обеспечивают маршрутизацию трафика для объектов `Service`.
    *   Отслеживает изменения сервисов и их эндпоинтов (IP-адреса подов) через API Kubernetes и настраивает правила маршрутизации на уровне узла с помощью `iptables` или `IPVS` (использует ядро для более высокопроизводительной балансировки).
    *   **Endpoint** в контексте Kubernetes сервисов — это IP-адрес и нужный порт пода.
    *   **kube-proxy** занимается только подменой адреса назначения и балансировкой, а не маршрутизацией между узлами — этим занимается CNI.
    *   Перенаправляет трафик с виртуального IP-адреса сервиса на правильные IP-адреса подов.
    *   Работает в одном из режимов: `iptables` (наиболее распространенный), `ipvs` или `kernelspace`.

    **В режиме `iptables` (по умолчанию) `kube-proxy`:**
    -   Перехватывает трафик, направленный, например, на `ClusterIP` и порт сервиса.
    -   Выполняет DNAT (Destination NAT): подменяет адрес назначения с `ClusterIP` на IP-адрес одного из подов (эндпоинтов) сервиса.
    -   Балансирует трафик между подами, входящими в сервис.

    > **Примечание:** Можно зайти на любой узел и сбросить все правила командой `iptables -F`. Kubernetes по умолчанию понадобится 30 секунд, чтобы понять, что правил нет, и восстановить их. Либо 10 секунд по умолчанию, чтобы обновить правила маршрутизации при изменении эндпоинтов или сервисов.

### `cAdvisor`

*   **Роль:** Сборщик метрик контейнеров.
*   **Описание:** **cAdvisor (Container Advisor)** — это встроенный в `kubelet` компонент, который автоматически обнаруживает все контейнеры на узле и собирает информацию об их производительности и потреблении ресурсов (CPU, память, файловая система, сеть).
*   **Ключевые функции:**
    *   Предоставляет `kubelet` данные о состоянии контейнеров, которые могут использоваться `kube-scheduler` для принятия решений о планировании.
    *   Отдает метрики в формате Prometheus через эндпоинт `/metrics/cadvisor` на `kubelet`, что делает его фундаментальным источником данных для систем мониторинга.

### Container Runtime (Среда выполнения контейнеров) / CRI

*   **Роль:** **Движок для контейнеров.**
*   **Описание:** Программное обеспечение, которое непосредственно запускает контейнеры и управляет их жизненным циклом. Kubernetes совместим с любой средой, поддерживающей стандарт **CRI (Container Runtime Interface)**.
    *   **Container Runtime Interface (CRI):** Это API Kubernetes, который определяет, как `kubelet` (агент Kubernetes на каждой ноде) взаимодействует с выбранной средой выполнения контейнеров (например, Docker, containerd, CRI-O). Он стандартизирован в спецификации, что позволяет выбирать, какую реализацию CRI использовать, или даже создавать собственную.
    *   **Основные задачи CRI:**
        - Запуск и остановка контейнеров.
        - Управление жизненным циклом подов (создание, удаление).
        - Управление образами контейнеров (pull, remove).
    *   **Примеры реализаций CRI:**
        *   **`containerd`**: Изначально был частью Docker, но теперь является самостоятельным проектом. Он стал CRI-совместимым благодаря своему `cri plugin`.
        *   **`CRI-O`**: Был разработан как легковесная альтернатива, специально для Kubernetes, от Red Hat/IBM и других.
    *   Все эти среды выполнения в конечном итоге используют низкоуровневые инструменты, такие как `runc`, для взаимодействия с ядром Linux и запуска изолированных процессов в соответствии со спецификацией **Open Container Initiative (OCI) spec**.

### Поды (Pods)

*   **Роль:** Базовая единица развертывания в Kubernetes.
*   **Описание:** Поды представляют собой группу из одного или нескольких контейнеров, которые совместно используют сетевое пространство, хранилище и запускаются на одном узле. Подробнее см. в [Pod](./pod.md).

### Сетевые плагины (CNI - Container Network Interface)

*   **Роль:** Обеспечение сетевой связности между подами и узлами.
*   **Описание:** Kubernetes использует плагины **Container Network Interface (CNI)** для настройки сети. CNI — это интерфейс, который позволяет тюнить сетевые взаимодействия как между контейнерами (создает сетевые окружения для пода + занимается маршрутизацией трафика между подами и нодами). Они отвечают за выделение IP-адресов подам и обеспечение связи между ними, а также с внешним миром.
    *   **Основные задачи CNI:**
        - Выделение IP-адресов подам.
        - Настройка сетевых интерфейсов для каждого пода.
        - Обеспечение маршрутизации трафика между подами на одном узле и между узлами.
        - Реализация сетевых политик (в продвинутых CNI-плагинах).
    *   **Примеры реализаций CNI:** Flannel, Calico, Cilium, Weave Net. Подробнее см. в [Сетевая модель в Kubernetes](../Networking/network.md).

### CSI (Container Storage Interface)

*   **Роль:** Стандартизация подключения хранилищ к контейнерам.
*   **Описание:** **CSI** — это интерфейс, который позволяет стандартизировать подключение систем хранения данных к контейнерам. Он позволяет разработчикам интегрировать разные решения для управления данными в контейнерах, предоставляя универсальный API для взаимодействия систем оркестрации контейнеров (таких как Kubernetes) с системами хранения данных (СХД).
    *   **Основные задачи CSI:**
        - Динамическое выделение и девыделение томов хранения.
        - Монтирование и отмонтирование томов к подам.
        - Создание снапшотов и клонирование томов.
    *   **Примеры реализаций CSI:** OpenEBS, Rook, Portworx, Ceph CSI. Подробнее см. в [Container Storage Interface (CSI)](../Storage/CSI/csi_overview.md).

## Kubernetes и экосистема CNCF (Cloud Native Computing Foundation)

Kubernetes является флагманским проектом **Cloud Native Computing Foundation (CNCF)** — некоммерческой организации, созданной под эгидой The Linux Foundation. В CNCF входят сотни компаний (включая Google, Red Hat, AWS, Microsoft), которые совместно развивают облачно-ориентированные технологии.

Статус проекта в CNCF гарантирует **долгосрочную поддержку и открытое управление**, защищая его от резких изменений политики одной компанией.

Помимо Kubernetes, в CNCF входит множество других проектов, которые расширяют и дополняют его возможности, например:
- **`etcd`**: хранилище, используемое в Kubernetes (упомянуто выше).
- **`Prometheus`**: система мониторинга.
- **`Helm`**: пакетный менеджер.
- **`containerd`**: среда выполнения контейнеров.

### Полезные ресурсы CNCF

*   **[CNCF Landscape](https://landscape.cncf.io/):** Интерактивная карта, которая позволяет найти программное обеспечение по нужной категории в экосистеме Cloud Native.
*   **[CNCF Radar](https://radar.cncf.io/):** Предоставляет информацию о том, какие технологии из CNCF Landscape и насколько зрело используются в индустрии, основываясь на данных от конечных пользователей.

## Жизненный цикл создания `Pod`: Пошаговый сценарий

Этот раздел объединяет информацию о работе различных компонентов в единый процесс, который происходит при создании нового пода.

1.  **Пользователь и `kubectl`**:
    *   Процесс начинается, когда пользователь выполняет команду `kubectl apply -f pod.yaml`. `kubectl` преобразует YAML-манифест в API-запрос и отправляет его в `kube-apiserver`.

2.  **`kube-apiserver`**:
    *   **Аутентификация и валидация:** API-сервер проверяет, кто отправил запрос и имеет ли он необходимые права. Затем он валидирует манифест на корректность.
    *   **Запись в `etcd`:** После успешной проверки API-сервер записывает спецификацию пода в `etcd`. На этом этапе под "существует" только как запись в базе данных. `etcd` подтверждает успешную запись.

3.  **`kube-scheduler`**:
    *   **Обнаружение:** Планировщик постоянно следит за API-сервером и обнаруживает новый под, у которого не назначено поле `spec.nodeName` (т.е. он "бездомный").
    *   **Выбор узла:** Планировщик выбирает наиболее подходящий рабочий узел для пода, основываясь на доступных ресурсах (CPU, RAM), ограничениях и правилах `affinity/anti-affinity`.
    *   **Обновление `etcd`:** После выбора узла, планировщик сообщает об этом `kube-apiserver`, который обновляет запись о поде в `etcd`, добавляя имя выбранного узла в поле `spec.nodeName`.

4.  **`kubelet`**:
    *   **Обнаружение:** `kubelet` на каждом рабочем узле также следит за API-сервером. `kubelet` на *выбранном* узле видит, что ему назначен новый под.
    *   **Создание контейнеров:** `kubelet` обращается к **Container Runtime Interface (CRI)** (например, `containerd`), чтобы тот скачал необходимые образы и создал контейнеры внутри пода в соответствии со спецификацией.
    *   **Обновление статуса:** `kubelet` постоянно сообщает о состоянии пода и его контейнеров обратно в `kube-apiserver`, который, в свою очередь, обновляет статус в `etcd`.

5.  **`kube-proxy`**:
    *   Параллельно `kube-proxy` на всех узлах замечает новый под и, если он является частью какого-либо `Service`, обновляет правила `iptables` (или `ipvs`), чтобы обеспечить сетевую доступность пода.
