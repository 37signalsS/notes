# Шеринг GPU в Kubernetes: time-slicing, MPS, MIG, vGPU и HAMi

**Актуально для:** Kubernetes 1.31+; HAMi — CNCF Incubating (v2.x); MIG — Ampere+, MPS — Volta+

## Определения

* **Time-slicing (GPU)** — разделение GPU по времени: каждому процессу выделяется квант времени, аналогично многопоточности на одном ядре CPU. Никак не изолирует видеопамять.
* **MPS (Multi-Process Service)** — программный слой NVIDIA: несколько процессов (контейнеров) одновременно используют один GPU через общий CUDA-контекст. Золотая середина между time-slicing и MIG.
* **MIG (Multi-Instance GPU)** — аппаратное разделение GPU на изолированные партиции (инстансы) с выделенными SM, видеопамятью, кэшем и bandwidth. Доступен на архитектуре Ampere и новее.
* **vGPU** — виртуализация GPU от NVIDIA (аппаратная, защищена лицензией).
* **HAMi** — open source middleware GPU-виртуализации для Kubernetes (CNCF Incubating), реализует vGPU-подобный шеринг бесплатно.
* **Dynamic MIG** — создание и перераспределение MIG-партиций по запросу, без ручной переконфигурации ноды.

## Основные концепции

### Почему нативный шеринг невозможен

`nvidia.com/gpu` — целочисленный расширенный ресурс: указав `nvidia.com/gpu: 1`, под резервирует целую видеокарту, даже если модель занимает 600 МБ из 40 ГБ видеопамяти. Нативным способом несколько ворклоадов на одной карте не запустить — для этого технологии разделения: time-slicing, MPS, MIG (и vGPU/HAMi поверх).

### Сравнение технологий

| Критерий | Time-slicing | MPS | MIG |
|:---|:---|:---|:---|
| Уровень разделения | Время (кванты) | Программный (общий контекст) | Аппаратный (SM, память, кэш) |
| Архитектура | Любая | Volta+ (48 контекстов; pre-Volta — 16) | Ampere+ |
| Изоляция видеопамяти | Нет (лимит задаётся на уровне приложения) | Частичная (MPS-сервер убивает процесс, превысивший лимит) | Полная (аппаратная) |
| Макс. число партиций | Не ограничено (но деградация) | до 48 контекстов | до 7 (зависит от GPU) |
| Поведение производительности | Линейное падение с ростом числа ворклоадов | Между time-slicing и MIG | Константная (каждая партиция — отдельная «карта») |

### Time-slicing

Самый простой способ деления видеокарты: работает по принципу многопоточности на процессоре с одним ядром — каждому процессу выделяется квант времени. Чем больше ворклоадов, тем меньше производительность каждого. Главная особенность: никак не изолирует по видеопамяти — на уровне приложения нужно указывать, сколько видеопамяти должен потреблять ворклоад, и не больше.

### MPS (Multi-Process Service)

Доступен на архитектуре Volta и новее; MPS-сервер поддерживает до 48 клиентских CUDA-контекстов на устройство (pre-Volta — 16). На GPU деплоится сервер, отвечающий за распределение потоков: в каждом сервисе указывается, сколько видеопамяти он потребляет, и этот сервер убивает процесс, превысивший значение. Золотая середина: больше изоляции, чем time-slicing, меньше жёсткости, чем MIG.

### MIG (Multi-Instance GPU)

Делит GPU на уровне железа: из одной карты (например, A100-40GB) получаются несколько независимых инстансов. Максимальное число партиций — около семи. Важная деталь: A100-40GB делится на 8 слайсов по 5 ГБ, но один слайс (5 ГБ) остаётся незанятым — он отведён под управление и изоляцию партиций. Профили A100-40GB: `1g.5gb` (×7), `2g.10gb` (×3), `3g.20gb` (×2), `4g.20gb` (×1), `7g.40gb` (×1). Каждая партиция — отдельная «видеокарта» с гарантированным числом SM и объёмом памяти; производительность не зависит от соседних партиций.

Экономика (из доклада): 1/7 часть A100 стоит примерно как Tesla T4, а по производительности даже чуть быстрее (бенчмарк NVIDIA: один MIG-слайс 1g.5gb даёт ~1.07x throughput T4). Поэтому компании покупают несколько больших карт и нарезают их на части, вместо хранения множества мелких карт (сложнее обслуживать: нужен слот на сервере в каждом ДЦ).

В Kubernetes MIG запрашивается как `nvidia.com/mig-1g.5gb` (см. [Device Manager](./device_manager.md) и [MIG через CDI](../../Docker/Dockerfile/dockerfile-gpu-ml.md)).

### vGPU и лицензирование

vGPU от NVIDIA работает только по лицензии. HAMi — open source реализация похожей технологии (см. ниже).

### HAMi Project

**HAMi** (Heterogeneous AI Computing Virtualization Middleware, ранее `k8s-vGPU-scheduler`) — китайский open source проект (Apache 2.0), CNCF Incubating (sandbox — август 2024, incubating — июль 2026). Позволяет реализовать vGPU-подобный шеринг бесплатно — «азиатский Танос», уничтожающий платную лицензию vGPU.

Как работает: `nvidia-smi` показывает ровно столько видеопамяти, сколько указано в манифесте пода, но по процессингу HAMi-core работает на таймслайсинге — то есть это time-slicing + изоляция по видеопамяти. Если запускать на HAMi очень много ворклоадов, производительность будет падать (хуже, чем у MIG). Ресурсы пода:

| Ресурс | Значение |
|:---|:---|
| `nvidia.com/gpu` | Число vGPU |
| `nvidia.com/gpumem` | Видеопамять на vGPU, MiB |
| `nvidia.com/gpumem-percentage` | Доля видеопамяти в % (альтернатива `gpumem`, взаимоисключающие) |
| `nvidia.com/gpucores` | Доля вычислительных ядер (SM), % |

HAMi-core (в контейнере, `libvgpu.so`) принудительно ограничивает память (`CUDA_DEVICE_MEMORY_LIMIT_0`) и вычисления (`CUDA_DEVICE_SM_LIMIT`); политика `GPU_CORE_UTILIZATION_POLICY=force` запрещает burst выше квоты (по умолчанию — burst разрешён, пока GPU свободен).

Установка: `helm install hami hami-charts/hami -n kube-system`.

**Когда выбирать:** небольшие кластеры, где нет ручной настройки MIG; универсальный инструмент — поддерживает и таймслайсинг с изоляцией памяти, и MIG. Паттерн миграции: поставить HAMi, пользоваться, пока не придёте к ручной установке MIG.

### Производительность (график из доклада)

Бенчмарк, приведённый в докладе (компания Nebula; автор повторил эксперимент в своей статье и получил тот же результат): при time-slicing latency инференсов растёт линейно с числом ворклоадов (они борются за одну карту); MIG показывает всегда одно и то же значение (партиции независимы); MPS — между ними.

## Динамическое перераспределение MIG

### Проблема статических партиций

При статическом MIG перераспределение партиций требует вытеснения всех существующих ворклоадов (даунтайм) либо ручного хождения на каждую ноду / лейбления нод нужной конфигурации через GPU Operator. Динамический MIG должен решать это: при запросе, скажем, 20 ГБ видеопамяти поверх существующего ворклоада на 1g.5gb, партиции перераспределяются и второй сервис деплоится без даунтайма первого.

### InstaSlice

Open source оператор (репозитории `openshift/instaslice-operator` — Dynamic Accelerator Slicer, и `project-codeflare/instaslice`): динамически создаёт MIG-слайсы по запросу через GPU Operator, интегрируется с Kueue, квотами Kubernetes, vLLM/KServe. Хорошо работает на OpenShift; в докладе отмечена низкая активность разработки с ~2023 года (для `project-codeflare/instaslice`; статус проверяйте перед внедрением).

### HAMi и dynamic MIG

HAMi поддерживает dynamic MIG. Механика (из доклада): при деплое ворклоада с GPU HAMi определяет ноду, где можно использовать MIG, и текущие партиции; если требования не удовлетворены — перераспределяет партиции и деплоит. **Ограничение (на момент доклада):** перераспределение выполняется только один раз и только при отсутствии текущих ворклоадов — если на карте уже есть ворклоад, HAMi выпадает в ошибку; динамический MIG «поверх существующих ворклоадов» в проработке. Проверяйте актуальный статус в [документации HAMi](https://project-hami.io/) — проект активно развивается.

### DRA (Dynamic Resource Allocation)

DRA — механизм Kubernetes (beta с 1.32, feature gate `DynamicResourceAllocation`, по умолчанию выключен; см. [Cluster Autoscaler](../Autoscaling/cluster_autoscaler_detailed.md)): вместо `nvidia.com/gpu` указываются конкретные claims — как PVC/PV: описывается сам ресурс (видеокарта, драйвер, партиция MIG), а Kubernetes сам решает, куда что подключить. NVIDIA продвигает DRA как естественный способ аллокации GPU; есть официальный DRA-драйвер NVIDIA (DeviceClass `gpu.nvidia.com`, `mig.nvidia.com`, `vfio.gpu.nvidia.com`; dynamic MIG через feature gate `DynamicMIG`, alpha). Оценка из доклада: работает только с 32-й версией Kubernetes и то в бета — тащить в продакшн не лучшая идея; через пару лет, вероятно, к этому придём, потому что текущий механизм скедулинга ворклоадов на GPU оставляет желать лучшего.

## Практические сценарии

### Сценарий 1: MIG-инстанс для пода

```yaml
# Запрос 1/7 части A100-40GB (профиль 1g.5gb)
apiVersion: v1
kind: Pod
metadata:
  name: mig-inference
spec:
  containers:
  - name: triton
    image: nvcr.io/nvidia/tritonserver:24.01-py3
    resources:
      requests:
        nvidia.com/mig-1g.5gb: 1
      limits:
        nvidia.com/mig-1g.5gb: 1
```

Валидация:

```bash
kubectl get nodes -o json | jq '.items[].status.capacity | select(."nvidia.com/mig-1g.5gb")'
# → "nvidia.com/mig-1g.5gb": "7"   (A100-40GB, все 7 партиций свободны)
```

Предварительно: MIG настроен на хосте (статическая геометрия), CDI-спецификация сгенерирована — см. [Device Manager](./device_manager.md) и [MIG через CDI](../../Docker/Dockerfile/dockerfile-gpu-ml.md).

### Сценарий 2: HAMi — доля GPU по памяти и ядрам

```yaml
# Иллюстративный манифест: 1 vGPU с лимитом 3 ГБ видеопамяти и 30% ядер (HAMi)
apiVersion: v1
kind: Pod
metadata:
  name: gpu-pod
spec:
  containers:
  - name: ubuntu-container
    image: ubuntu:22.04
    command: ["bash", "-c", "sleep 86400"]
    env:
    - name: GPU_CORE_UTILIZATION_POLICY
      value: "force"   # строгий кап по gpucores (default — burst разрешён)
    resources:
      limits:
        nvidia.com/gpu: 1        # 1 vGPU
        nvidia.com/gpumem: 3000  # 3000 MiB видеопамяти на vGPU
        nvidia.com/gpucores: 30  # 30% вычислительных ядер
```

Валидация:

```bash
kubectl exec gpu-pod -- nvidia-smi
# → Memory-Usage: 0MiB / 3000MiB   (HAMi показывает лимит из манифеста)
```

## Troubleshooting

### HAMi dynamic MIG: ошибка при существующих ворклоадах

**Симптом:** деплой ворклоада с требованием MIG падает в ошибку, если на целой карте уже запущены другие ворклоады.
**Причина:** ограничение dynamic MIG в HAMi (на момент доклада): перераспределение партиций возможно только при пустой карте.
**Решение:** предварительно настроить статическую геометрию MIG под ожидаемые профили либо отслеживать статус функции в документации HAMi.

### Переконфигурация MIG вытесняет ворклоады

**Симптом:** при изменении геометрии партиций (вручную или через GPU Operator) все ворклоады на карте теряют доступ к GPU.
**Причина:** статический MIG требует вытеснения всех ворклоадов при перераспределении.
**Решение:** планировать геометрию заранее (профили `1g.5gb`/`2g.10gb`/...); для динамики — InstaSlice / HAMi dynamic MIG / DRA (см. выше).

## Best Practices

### Какой метод выбрать

| Ситуация | Метод |
|:---|:---|
| Некритичные dev-задачи, мелкие модели | Time-slicing (дешевле всего, но без изоляции памяти) |
| Много мелких инференсов, нужна плотность | MPS (Volta+, до 48 контекстов) |
| Критичные нагрузки, гарантированная производительность | MIG (Ampere+, аппаратная изоляция) |
| Нужна изоляция памяти без настройки MIG, малый кластер | HAMi (time-slicing + изоляция памяти/ядер) |
| Геометрия MIG меняется часто | Dynamic MIG: InstaSlice / HAMi / DRA (beta/alpha) |

### Автоскейлинг с шерингом

Автоскейлинг с шерингом GPU работает так же, как обычный: HPA деплоит новую реплику, но она падает не на карту с лейблом `nvidia.com/gpu`, а на конкретную партицию MIG (или vGPU от HAMi). Полный конвейер — в [GPU-инференс: автоскейлинг](../Autoscaling/gpu_inference_autoscaling.md).
