# Управление ресурсами в Kubernetes: Requests, Limits, Quotas и QoS

## Definitions

* **`requests` (Запросы):** Минимальное количество ресурсов (CPU и памяти), которое Kubernetes **гарантирует** выделить контейнеру. Используется планировщиком (`kube-scheduler`) для выбора узла.
  * **`requests.cpu`:** Минимальная гарантированная вычислительная мощность.
  * **`requests.memory`:** Минимальный гарантированный объём памяти.

* **`limits` (Лимиты):** Максимальное количество ресурсов, которое контейнеру **разрешено** использовать.
  * **`limits.cpu`:** Жёсткий потолок использования CPU. При превышении ресурс будет искусственно ограничиваться (**throttling**).
  * **`limits.memory`:** Жёсткий потолок использования памяти. При превышении контейнер будет принудительно завершён с ошибкой **OOMKilled** (Out of Memory Killed).

* **QoS (Quality of Service — Качество Обслуживания):** Класс, присваиваемый поду на основе установленных `requests` и `limits`. Определяет **приоритет пода** и влияет на его вытеснение (`eviction`) при нехватке ресурсов на узле.

> **Связанные механизмы:** Вытеснение подов также осуществляется через [Taints and Tolerations](./taints_and_tolerations.md) (эффект `NoExecute`) при проблемах с узлами.

### Единицы измерения

* **CPU:** Измеряется в **"milliCPU"** (тысячных долях ядра) или полных ядрах. `1000m` = `1` vCPU/Core. `500m` — это половина ядра.
* **Память:** Измеряется в байтах. Можно использовать суффиксы: `Ki` (кибибайт), `Mi` (мебибайт), `Gi` (гибибайт).

## Basic Concepts

### Классы качества обслуживания (QoS)

Kubernetes присваивает подам один из трёх классов QoS, исходя из их `requests` и `limits`:

* **`Guaranteed` (Гарантированный)**
  * **Условия:** Каждый контейнер в поде должен иметь `requests` и `limits` для CPU и памяти, причём **`requests` должны быть равны `limits`**.
  * **Приоритет:** **Высший**. Эти поды будут вытеснены в последнюю очередь.

* **`Burstable` (Эластичный)**
  * **Условия:** Под не соответствует критериям `Guaranteed`, но хотя бы у одного контейнера указан `requests` (CPU или памяти). `limits` могут быть установлены выше `requests` или отсутствовать.
  * **Приоритет:** **Средний**. Поды могут использовать больше ресурсов, чем запрошено (`requests`), вплоть до `limits`, если ресурсы на узле доступны. Будут вытеснены после `BestEffort` при нехватке памяти.
  * **Поведение при overcommit:** Если `limit` больше `request`, а на узле недостаточно ресурсов, под всё равно может быть запущен по его `request`. Однако, если под начнёт потреблять ресурсы сверх `request` и приблизится к своему `limit` на перегруженном узле, он может быть принудительно завершён (OOMKilled) для освобождения ресурсов.

* **`BestEffort` (Максимальное усилие)**
  * **Условия:** Ни у одного контейнера в поде не указаны ни `requests`, ни `limits`.
  * **Приоритет:** **Низший**. Эти поды получают ресурсы по остаточному принципу и будут **вытеснены первыми** при любой нехватке ресурсов.

#### Сводка по классам QoS

| QoS Класс      | Условие                                     | Приоритет при вытеснении | Сценарий использования                               |
|----------------|---------------------------------------------|--------------------------|------------------------------------------------------|
| **`Guaranteed`** | `requests` == `limits` для всех контейнеров | **Высший** (не вытесняется) | Критичные сервисы: базы данных, очереди сообщений     |
| **`Burstable`**  | `requests` < `limits` (или `limits` нет)    | **Средний**              | Стандартные приложения: веб-серверы, микросервисы    |
| **`BestEffort`** | `requests` и `limits` не заданы             | **Низший** (первый на вылет) | Разработка, тесты, некритичные фоновые задачи      |

### Eviction Manager и QoS

При нехватке ресурсов на узле (например, `MemoryPressure` или `DiskPressure`), компонент `kubelet` активирует **Eviction Manager**, который начинает принудительно «выселять» (удалять) поды для освобождения ресурсов. Решение о том, какие поды выселять первыми, принимается на основе их QoS-класса:

1. **`BestEffort`**: Выселяются в первую очередь.
2. **`Burstable`**: Выселяются после `BestEffort`.
3. **`Guaranteed`**: Выселяются в последнюю очередь, только если узел всё ещё находится под давлением после удаления всех подов других классов.

Таким образом, QoS напрямую влияет на стабильность и предсказуемость работы пода в условиях ограниченных ресурсов. Для повышения отказоустойчивости рекомендуется использовать совместно с [Affinity и Anti-Affinity](./affinity.md) для распределения подов по разным узлам и зонам.

### Автоматизация и ограничения ресурсов

* **`LimitRange`**: Используется на уровне `Namespace` для установки значений по умолчанию и ограничений для ресурсов подов/контейнеров.
  * **Назначение:** Помогает ввести безопасные значения по умолчанию и стандартизировать потребление ресурсов, предотвращая присвоение подам хаотичных QoS-классов (`BestEffort`) без явных `requests`/`limits`.
  * **Возможности:** Позволяет установить `defaultRequest`, `default` (для `limits`), `max` и `min` для CPU и памяти.

* **`ResourceQuota`**: Ограничивает **суммарное** потребление ресурсов в рамках одного `Namespace`.
  * **Назначение:** Критически важный инструмент для многопользовательских кластеров, предотвращающий монополизацию ресурсов одной командой. Задаёт жёсткие границы.
  * **Что может ограничивать:**
        1. **Вычислительные ресурсы:** Суммарные `requests.cpu`, `limits.cpu`, `requests.memory`, `limits.memory`.
        2. **Ресурсы хранения:** Суммарное количество `PersistentVolumeClaim` и запрошенного места.
        3. **Количество объектов:** Максимальное число подов, сервисов, секретов, `ConfigMap` и т.д.

## Practical Scenarios

### Пример: `Guaranteed` Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-pod
spec:
  containers:
    - name: main
      image: nginx
      resources:
        requests:
          memory: "128Mi"
          cpu: "250m"
        limits:
          memory: "128Mi"
          cpu: "250m"
```

### Пример: `Burstable` Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: burstable-pod
spec:
  containers:
    - name: main
      image: nginx
      resources:
        requests:
          memory: "128Mi"
          cpu: "250m"
        limits:
          memory: "256Mi"
          cpu: "500m"
```

### Пример: `BestEffort` Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: besteffort-pod
spec:
  containers:
    - name: main
      image: nginx
      # requests и limits не указаны
```

### Пример: `LimitRange`

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-resource-limits
  namespace: my-namespace
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"
      default:
        cpu: "500m"
        memory: "512Mi"
      max:
        cpu: "1"
        memory: "1Gi"
```

### Пример: `ResourceQuota`

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "10"       # Суммарно все поды не могут запросить более 10 CPU
    limits.cpu: "20"         # Суммарные лимиты не могут превышать 20 CPU
    requests.memory: "50Gi"  # Суммарно не более 50 GiB гарантированной памяти
    limits.memory: "100Gi"   # Суммарные лимиты не более 100 GiB
    pods: "50"               # Не более 50 подов в неймспейсе
    services: "20"           # Не более 20 сервисов
```

## Additional Information

### Стратегии и лучшие практики

* **Основная стратегия: `Burstable` для большинства нагрузок**
  * Для большинства приложений рекомендуется использовать класс QoS **`Burstable`**.
  * **`requests` (запросы) следует устанавливать на минимально необходимом** для старта и стабильной работы приложения уровне. Это позволяет Kubernetes более эффективно «упаковывать» поды на узлы.
  * **`limits` (лимиты) следует устанавливать на разумном максимальном уровне.** Это защитит узел от «шумных соседей» — подов, которые могут монополизировать ресурсы.
  * **Важный нюанс:** `HorizontalPodAutoscaler` (HPA) рассчитывает целевые значения (например, `targetAverageUtilization`) на основе `requests`, а не `limits`. Неправильно заниженные `requests` могут привести к некорректной работе автомасштабирования.

* **`Guaranteed` для критически важных сервисов**
  * Класс `Guaranteed` (`requests` == `limits`) следует использовать только для самых критически важных компонентов системы, где предсказуемость производительности важнее эффективного использования ресурсов (например, базы данных, очереди сообщений).
  * Использование `Guaranteed` для всех подряд приведёт к быстрому исчерпанию ресурсов кластера и неэффективным затратам.

* **`BestEffort` — только для некритичных задач**
  * Класс `BestEffort` (без указания `requests` и `limits`) следует использовать с большой осторожностью. Такие поды будут первыми кандидатами на вытеснение.
  * Подходит для задач разработки, тестирования, пакетных заданий. **Категорически не рекомендуется для production-окружений.**

* **Анти-паттерн: Отсутствие лимитов на CPU**
  * **Риск:** Один «шумный» под может монополизировать все ядра CPU на узле, вызывая «зависание» и троттлинг всех остальных подов, включая системные компоненты `kubelet`. Это может привести к полной деградации производительности узла.
  * **Решение:** Лучше установить разумный лимит на CPU и, если приложение в него упирается, разбираться с причиной (оптимизировать код, увеличить количество реплик через HPA).

* **Постоянный пересмотр ресурсов**
  * Настройка `requests` и `limits` — это не разовая задача. Их необходимо регулярно пересматривать.
  * **Мониторинг:** Используйте системы мониторинга (Prometheus, Grafana) для анализа реального потребления ресурсов.
  * **Анализ:** Сравнивайте `requests` и `limits` с реальным потреблением.
  * **Корректировка:** Уменьшайте `requests` и `limits` для более эффективного использования ресурсов или увеличивайте их, если приложение часто упирается в лимиты, после оптимизации кода.

* **In-Place Pod Resize**
  * Начиная с Kubernetes 1.27 (alpha), доступна функция [In-Place Pod Resize](../Autoscaling/in_place_pod_resize.md), позволяющая изменять `requests` и `limits` у запущенных подов без их пересоздания. В Kubernetes 1.33+ функция находится в статусе beta. Это позволяет корректировать ресурсы без простоя приложения.
