# Управление ресурсами в Kubernetes: Requests, Limits, Quotas и QoS

## Определения

### Механизмы: `requests` и `limits`

Эти параметры задаются в спецификации контейнера Pod (`spec.containers.resources`).

*   **`requests` (Запросы):** Минимальное количество ресурсов, которое Kubernetes **гарантирует** выделить контейнеру. Используется планировщиком (`kube-scheduler`) для выбора узла.
    *   **`requests.cpu`:** Минимальная гарантированная вычислительная мощность.
    *   **`requests.memory`:** Минимальный гарантированный объем памяти.

*   **`limits` (Лимиты):** Максимальное количество ресурсов, которое контейнеру **разрешено** использовать.
    *   **`limits.cpu`:** Жесткий потолок использования CPU. При превышении ресурс будет искусственно ограничиваться (**throttling**).
    *   **`limits.memory`:** Жесткий потолок использования памяти. При превышении контейнер будет принудительно завершен с ошибкой **OOMKilled** (Out of Memory).
    > **Примечание:** Начиная с Kubernetes 1.35, `requests` и `limits` могут быть изменены у уже запущенных подов без их перезапуска благодаря функции [In-Place Pod Resize](../../Autoscaling/autoscaling_overview.md#in-place-pod-resize-kubernetes-135).

#### Единицы измерения

*   **CPU:** Измеряется в **"milliCPU"** (тысячных долях ядра) или полных ядрах. `1000m` = `1` vCPU/Core. `500m` — это половина ядра.
*   **Память:** Измеряется в байтах. Можно использовать суффиксы: `Ki` (кибибайт), `Mi` (мебибайт), `Gi` (гибибайт).

### Классы качества обслуживания (QoS)

На основе установленных `requests` и `limits` Kubernetes присваивает подам один из трех классов QoS. Этот класс определяет **приоритет пода** и влияет на то, какие поды будут вытеснены (`evicted`) первыми в случае нехватки ресурсов на узле.

## Основные концепции

### Классы QoS

*   **`Guaranteed` (Гарантированный)**
    *   **Условия:** Каждый контейнер в поде должен иметь `requests` и `limits` для CPU и памяти, причем **`requests` должны быть равны `limits`**.
    *   **Приоритет:** **Высший**. Эти поды будут вытеснены в последнюю очередь.

*   **`Burstable` (Эластичный)**
    *   **Условия:** Под не соответствует критериям `Guaranteed`, но хотя бы у одного контейнера указан `requests` (CPU или памяти). `limits` могут быть установлены выше `requests`.
    *   **Приоритет:** **Средний**. Поды могут использовать больше ресурсов, чем запрошено (`requests`), вплоть до `limits`, если ресурсы на узле доступны. Будут вытеснены после `BestEffort` при нехватке памяти.
    *   **Поведение при overcommit:** Если `limit` больше `request`, а на узле недостаточно ресурсов, под все равно может быть запущен по его `request`. Однако, если под начнет потреблять ресурсы сверх `request` и приблизится к своему `limit` на перегруженном узле, он будет принудительно завершен (OOMKilled) для освобождения ресурсов.

*   **`BestEffort` (Максимальное усилие)**
    *   **Условия:** Ни у одного контейнера в поде не указаны ни `requests`, ни `limits`.
    *   **Приоритет:** **Низший**. Эти поды получают ресурсы по остаточному принципу и будут **вытеснены первыми** при любой нехватке ресурсов.

### Сводка по классам QoS

| QoS Класс      | Условие                                     | Приоритет при вытеснении | Сценарий использования                               |
|----------------|---------------------------------------------|--------------------------|------------------------------------------------------|
| **`Guaranteed`** | `requests` == `limits` для всех контейнеров | **Высший** (не вытесняется) | Критичные сервисы: базы данных, очереди сообщений     |
| **`Burstable`**  | `requests` < `limits` (или `limits` нет)    | **Средний**              | Стандартные приложения: веб-серверы, микросервисы    |
| **`BestEffort`** | `requests` и `limits` не заданы             | **Низший** (первый на вылет) | Разработка, тесты, некритичные фоновые задачи      |

### Автоматизация с `LimitRange`

`LimitRange` используется на уровне `Namespace` для установки значений по умолчанию и ограничений для ресурсов.
*   **Зачем это нужно:** Помогает ввести безопасные значения по умолчанию и стандартизировать потребление ресурсов, предотвращая хаотичное присвоение QoS-классов (`BestEffort`) подам без явных `requests`/`limits`.
*   Позволяет установить: `defaultRequest`, `default`, `max`, `min` для CPU и памяти.

### Ограничение суммарного потребления с `ResourceQuota`

`ResourceQuota` ограничивает **суммарное** потребление ресурсов в рамках одного `Namespace`.
*   **Зачем это нужно:** Критически важный инструмент для многопользовательских кластеров, предотвращающий монополизацию ресурсов одной командой. Задаёт жёсткие границы.
*   Может ограничивать:
    1.  **Вычислительные ресурсы:** Суммарные `requests.cpu`, `limits.cpu`, `requests.memory`, `limits.memory`.
    2.  **Ресурсы хранения:** Суммарное количество `PersistentVolumeClaim` и запрошенного места.
    3.  **Количество объектов:** Максимальное число подов, сервисов, секретов, `ConfigMap` и т.д.

## Практические сценарии

### Пример: `Guaranteed` Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: guaranteed-pod
spec:
  containers:
    - name: main
      image: nginx
      resources:
        requests:
          memory: "128Mi"
          cpu: "250m"
        limits:
          memory: "128Mi"
          cpu: "250m"
```

### Пример: `Burstable` Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: burstable-pod
spec:
  containers:
    - name: main
      image: nginx
      resources:
        requests:
          memory: "128Mi"  # Минимальный объем памяти, который требуется контейнеру
          cpu: "250m"      # Минимальный объем процессорного времени(милицпу, в кубере проц это 100 милицпу)
        limits:
          memory: "256Mi"
          cpu: "500m"
```

### Пример: `BestEffort` Pod

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: besteffort-pod
spec:
  containers:
    - name: main
      image: nginx
      # requests и limits не указаны
```

## Автоматизация с `LimitRange`

Чтобы не задавать `requests` и `limits` вручную для каждого пода и обеспечить соблюдение стандартов, можно использовать объект `LimitRange` на уровне `Namespace`.

> **Зачем это нужно:** `LimitRange` помогает ввести безопасные значения по умолчанию и стандартизировать потребление ресурсов. Если его не использовать, часть подов может оказаться без `requests` и `limits`, что приведет к присвоению им хаотичных QoS-классов (`BestEffort`) и затруднит разбор инцидентов, связанных с нехваткой ресурсов.

`LimitRange` позволяет установить:

*   `defaultRequest`: значения `requests` по умолчанию для контейнеров, где они не указаны.
*   `default`: значения `limits` по умолчанию.
*   `max` / `min`: максимальные и минимальные значения `limits` / `requests`.

```yaml
apiVersion: v1
kind: LimitRange
metadata:
  name: default-resource-limits
  namespace: my-namespace
spec:
  limits:
    - type: Container
      defaultRequest:
        cpu: "100m"
        memory: "128Mi"
      default:
        cpu: "500m"
        memory: "512Mi"
      max:
        cpu: "1"
        memory: "1Gi"
```

### Пример: `ResourceQuota`

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-a-quota
  namespace: team-a
spec:
  hard:
    requests.cpu: "10"       # Суммарно все поды не могут запросить более 10 CPU
    limits.cpu: "20"         # Суммарные лимиты не могут превышать 20 CPU
    requests.memory: "50Gi"  # Суммарно не более 50 GiB гарантированной памяти
    limits.memory: "100Gi"   # Суммарные лимиты не более 100 GiB
    pods: "50"               # Не более 50 подов в неймспейсе
    services: "20"           # Не более 20 сервисов
```

## Дополнительная информация

### Стратегии и лучшие практики

*   **Основная стратегия: `Burstable` для большинства нагрузок**

Для большинства приложений рекомендуется использовать класс QoS **`Burstable`**.

*   **`requests` (запросы) следует устанавливать на минимально необходимом для старта и стабильной работы приложения уровне.** Это позволяет Kubernetes более эффективно "упаковывать" поды на узлы, размещая на одной ноде больше рабочих нагрузок.
*   **`limits` (лимиты) следует устанавливать на разумном максимальном уровне.** Это защитит узел от "шумных соседей" — подов, которые из-за бага или пиковой нагрузки могут начать потреблять все доступные ресурсы, вызывая проблемы у других приложений.

**Важный нюанс:** `HorizontalPodAutoscaler` (HPA) рассчитывает целевые значения (например, `targetAverageUtilization`) на основе `requests`, а не `limits`. Неправильно заниженные `requests` могут привести к некорректной работе автомасштабирования.

*   **`Guaranteed` для критически важных сервисов**
    *   Класс `Guaranteed` (`requests` == `limits`) следует использовать только для самых критически важных компонентов системы, где предсказуемость производительности важнее эффективного использования ресурсов (например, базы данных, очереди сообщений).
    *   Использование `Guaranteed` для всех подряд приведет к быстрому исчерпанию ресурсов кластера и неэффективным затратам.

*   **`BestEffort` — только для некритичных задач**
    *   Класс `BestEffort` (без указания `requests` и `limits`) следует использовать с большой осторожностью. Такие поды будут первыми кандидатами на вытеснение.
    *   Подходит для задач разработки, тестирования, пакетных заданий.
    *   **Категорически не рекомендуется для production-окружений.**

*   **Анти-паттерн: Отсутствие лимитов на CPU**
    *   **Риск:** Один "шумный" под может монополизировать все ядра CPU на узле, вызывая "зависание" и троттлинг всех остальных подов, включая системные компоненты `kubelet`. Это может привести к полной деградации производительности узла.
    *   **Решение:** Лучше установить разумный лимит на CPU и, если приложение в него упирается, разбираться с причиной (оптимизировать код, увеличить количество реплик через HPA).

*   **Постоянный пересмотр ресурсов**
    *   Настройка `requests` и `limits` — это не разовая задача. Их необходимо регулярно пересматривать.
    *   **Мониторинг:** Используйте системы мониторинга (Prometheus, Grafana) для анализа реального потребления ресурсов.
    *   **Анализ:** Сравнивайте `requests` и `limits` с реальным потреблением.
    *   **Корректировка:** Уменьшайте `requests` и `limits` для более эффективного использования ресурсов или увеличивайте их, если приложение часто упирается в лимиты, после оптимизации кода.
