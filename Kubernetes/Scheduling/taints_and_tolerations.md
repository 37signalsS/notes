# Taints and Tolerations (Отравления и Терпимость)

**Taints** (отравления) и **Tolerations** (терпимость) — это механизм в Kubernetes, который позволяет ограничивать размещение подов на определенных нодах. Нода, имеющая `taint`, "отталкивает" поды, у которых нет соответствующего `toleration`.

Это ключевой инструмент для реализации таких сценариев, как:

*   Выделение нод для выполнения специфических задач (например, ноды с GPU).
*   Выделение нод для определенных групп пользователей.
*   Обеспечение вытеснения подов с нод в случае их неисправности.

---

## Taints (Отравления)

`Taint` — это метка, которая применяется к ноде. Она состоит из трех частей: ключ (`key`), значение (`value`) и эффект (`effect`).

```bash
# синтаксис
kubectl taint nodes <node-name> <key>=<value>:<effect>
```

### Эффекты Taint

Существует три основных эффекта:

1.  **`NoSchedule`**: Kubernetes не будет размещать на ноде новые поды, у которых нет соответствующего `toleration`. **Существующие поды на ноде продолжат работать.**

2.  **`PreferNoSchedule`**: Kubernetes будет *стараться* не размещать на ноде новые поды без `toleration`. Это "мягкая" версия `NoSchedule`. Если в кластере нет других доступных нод для пода, он все равно может быть размещен на ноде с таким `taint`.

3.  **`NoExecute`**: Это самый строгий эффект.
    *   Новые поды без `toleration` не будут размещены на ноде.
    *   **Существующие поды**, которые уже работают на ноде и не имеют соответствующего `toleration`, **будут вытеснены** (evicted) с ноды.

---

## Tolerations (Терпимость)

`Toleration` — это свойство, которое добавляется в спецификацию пода (`pod.spec`). Оно позволяет поду "терпеть" `taint` на ноде и, следовательно, быть размещенным на ней.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-pod
spec:
  # ... другие поля ...
  tolerations:
  - key: "key1"
    operator: "Equal"
    value: "value1"
    effect: "NoSchedule"
  - key: "key2"
    operator: "Exists"
    effect: "NoExecute"
```

*   `operator: "Equal"`: `toleration` "срабатывает", если `key`, `value` и `effect` точно совпадают с `taint`.
*   `operator: "Exists"`: `toleration` "срабатывает" для любого `taint` с указанным `key` и `effect`, независимо от `value`.

### Особый случай: `tolerationSeconds` для `NoExecute`

Для `toleration` с эффектом `NoExecute` можно указать поле `tolerationSeconds`. Оно определяет, как долго под будет продолжать работать на ноде после добавления `taint`, прежде чем будет вытеснен.

```yaml
tolerations:
- key: "node.kubernetes.io/unreachable"
  operator: "Exists"
  effect: "NoExecute"
  tolerationSeconds: 300
```

Если `tolerationSeconds` не указано, под с соответствующим `toleration` останется на ноде навсегда. Если `toleration` нет, под будет вытеснен немедленно.

## Сводка поведения

| Taint Effect     | Поведение для **новых** подов (без toleration) | Поведение для **существующих** подов (без toleration) |
|------------------|------------------------------------------------|-------------------------------------------------------|
| `NoSchedule`     | Не размещаются                                 | **Продолжают работать**                               |
| `PreferNoSchedule` | Kubernetes старается не размещать             | Продолжают работать                                   |
| `NoExecute`      | Не размещаются                                 | **Вытесняются (evicted)**                             |

## Практический сценарий: Отложенный запуск подов до готовности DaemonSet

Часто возникает задача — убедиться, что на узле сначала запущен системный компонент (например, сетевой плагин или агент мониторинга), развернутый через [DaemonSet](../Base/daemonset.md), и только потом на этот узел начинают планироваться обычные поды приложений. Этот сценарий идеально решается с помощью `Taints` и `Tolerations`.

### Шаг 1: Применение "отравления" (Taint) к узлам

Сразу после добавления в кластер, на узел применяется `taint` с эффектом `NoSchedule`. Это запретит планировщику размещать на нем любые поды.

```bash
# Добавляем taint к узлу my-node
kubectl taint nodes my-node my-daemonset.startup/not-ready:NoSchedule
```
*   `my-daemonset.startup/not-ready`: Это произвольный ключ, который мы используем для идентификации нашего условия.

### Шаг 2: Добавление "терпимости" (Toleration) в DaemonSet

Чтобы под `DaemonSet` мог запуститься на "отравленном" узле, в его манифест добавляется соответствующий `toleration`.

```yaml
# daemonset.yaml
apiVersion: apps/v1
kind: DaemonSet
# ...
spec:
  template:
    spec:
      tolerations:
      # Этот блок позволяет DaemonSet запуститься на "отравленном" узле
      - key: "my-daemonset.startup/not-ready"
        operator: "Exists"
        effect: "NoSchedule"
      containers:
      # ...
```

### Шаг 3: Автоматическое удаление "отравления"

После выполнения шагов 1 и 2, под `DaemonSet` успешно запустится на узле, в то время как все остальные поды будут ожидать. Однако Kubernetes **не удалит `taint` автоматически**. Для этого требуется внешний контроллер, который:

1.  Следит за узлами с `taint` `my-daemonset.startup/not-ready`.
2.  Проверяет статус пода `DaemonSet` на этих узлах.
3.  Как только под `DaemonSet` на узле переходит в состояние `Ready`, контроллер автоматически удаляет с этого узла `taint`.

Многие системные `DaemonSet` (например, сетевые плагины CNI) уже содержат такой контроллер "из коробки". Для собственных `DaemonSet` может потребоваться разработка такого оператора.
