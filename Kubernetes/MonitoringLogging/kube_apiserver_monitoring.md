# Мониторинг kube-apiserver

## Определения

- **Мониторинг `kube-apiserver`** — процесс наблюдения за ключевыми показателями производительности и состояния API (Application Programming Interface) сервера Kubernetes для обеспечения стабильности и надежности кластера.
- **SLI (Service Level Indicator), SLO (Service Level Objective) и SLA (Service Level Agreement)** — ключевые концепции для измерения и целеполагания в области надежности. Подробное определение и примеры приведены в разделе **[Концепции SRE (Site Reliability Engineering): SLA, SLO, SLI и метрики надежности](../../Concepts/sre_concepts_main.md)**. Нарушение SLO обычно является триггером для оповещений (алертов).
- **Control Plane** — плоскость управления Kubernetes, включающая `kube-apiserver`, `etcd`, `kube-controller-manager`, `kube-scheduler`. Архитектура описана в **[Control Plane Architecture](../Concepts/control_plane_architecture.md)**.

## Основные концепции

Ключевыми индикаторами состояния `kube-apiserver` являются:

1. **Задержка выполнения запросов (Request Latency)**: Время, которое требуется API-серверу для обработки входящих запросов.
    - **Метрика**: `apiserver_request_duration_seconds_bucket`.
    - **Описание**: [Гистограмма](../../Concepts/Observability_and_Monitoring/observability_definitions.md) времени выполнения запросов. При расчете перцентилей следует исключать долгоживущие запросы (`WATCH`, `CONNECT`), чтобы избежать искажения результатов.

2. **Частота ошибок (Error Rate)**: Доля запросов, завершившихся с ошибкой.
    - **Метрика**: `apiserver_requests_total`.
    - **Описание**: Счетчик всех запросов к API-серверу с разделением по коду ответа (HTTP Status Code). Для мониторинга ошибок отбираются клиентские (`4xx`) и серверные (`5xx`) статусы.

## Практические сценарии

### Мониторинг задержки (Latency)

- **SLI**: 99-й перцентиль (`p99` — значение, ниже которого находится 99% наблюдений) времени ответа на запросы.
- **SLO**: `p99` < 100 мс.

**Пример расчета SLI в PromQL (Prometheus Query Language):**

```promql
histogram_quantile(0.99, sum(rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|CONNECT"}[5m])) by (le))
# → {le="0.1"} 0.045
```

**Правило для алерта:** `p99 > 0.1`

- **Действие:** Если `kube-apiserver` отвечает медленнее 100 мс, требуется немедленное расследование. Возможные причины: проблемы с производительностью `etcd`, сетевые задержки или критическая нагрузка на Control Plane.

### Мониторинг частоты ошибок

- **SLI**: Количество запросов с кодом `4xx` или `5xx`.
- **SLO**: Менее 5 ошибок в минуту.

**Пример расчета SLI в PromQL:**

```promql
sum(rate(apiserver_requests_total{code=~"4..|5.."}[5m]))
# → {} 0.12
```

**Правило для алерта:** Количество ошибок превышает 5 за последние 5 минут.

- **Действие:** Появление значительного количества серверных или клиентских ошибок требует вмешательства дежурного инженера для выявления некорректно работающих клиентов или деградации компонентов системы.

## Дополнительная информация

### Дополнительные метрики для дашбордов

Помимо метрик для алертинга, для диагностики и глубокого анализа полезны следующие показатели:

- **Количество запросов по методам (`verb`) и ресурсам (`resource`):**
  - Помогает выявить аномальную активность, например, когда один из операторов (Controller) создает избыточную нагрузку на API-сервер, отправляя тысячи запросов к одному типу объектов.

- **Задержка (latency) по каждому типу объектов:**
  - Позволяет обнаружить проблемы с производительностью для конкретных ресурсов. Например, резкий рост времени ответа для `configmaps` может указывать на их чрезмерный объем или количество в конкретном пространстве имен (Namespace).
