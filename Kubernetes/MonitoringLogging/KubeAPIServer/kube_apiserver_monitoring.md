# Мониторинг kube-apiserver

### SLI: 99-й перцентиль времени ответа

В качестве индикатора используется 99-й перцентиль (`p99`) времени выполнения запросов. Это означает, что 99% запросов должны выполняться быстрее определенного значения.

*   **Метрика Prometheus:** `apiserver_request_duration_seconds_bucket`
*   **Важно:** При расчете этой метрики следует исключать долгоживущие запросы, такие как `watch` и `connect`, поскольку они могут исказить общую картину.

**Пример расчета `p99`:**

```promql
histogram_quantile(0.99, sum(rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|CONNECT"}[5m])) by (le))
```

### SLO: < 100 мс

В качестве цели можно установить, что 99% запросов должны обрабатываться быстрее, чем за 100 миллисекунд.

*   **Правило для алерта:** `p99 > 0.1`
*   **Действие:** Если `kube-apiserver` начинает отвечать медленнее, это требует немедленного расследования. Возможные причины могут включать проблемы с `etcd`, сетью или высокую нагрузку на сам API-сервер.

## Мониторинг частоты ошибок (Error Rate)

### SLI: Количество ошибок 4xx и 5xx

Индикатором служит количество запросов, которые `kube-apiserver` завершает со статусом `4xx` (ошибки клиента) или `5xx` (ошибки сервера).

*   **Метрика Prometheus:** `apiserver_requests_total` с фильтрацией по коду ответа.

**Пример подсчета ошибок:**

```promql
sum(rate(apiserver_requests_total{code=~"4..|5.."}[5m]))
```

### SLO: < 5 ошибок в минуту

В нормальном состоянии `kube-apiserver` должен работать практически без ошибок.

*   **Правило для алерта:** Количество ошибок превышает N за определенный промежуток времени (например, 5 ошибок за 5 минут).
*   **Действие:** Появление значительного количества ошибок требует вмешательства дежурного инженера.

## Дополнительные диагностические метрики

Помимо метрик для алертинга (SLO), существует ряд других полезных метрик, которые помогают в диагностике проблем и анализе состояния кластера. Их полезно регулярно просматривать на дашбордах.

*   **Количество запросов по методам (`verb`) и ресурсам (`resource`):**
    *   Помогает выявить аномальную активность, например, когда один из операторов начинает "спамить" API-сервер тысячами запросов к одному и тому же объекту.

*   **Задержка (latency) по каждому типу объектов:**
    *   Позволяет обнаружить проблемы с производительностью для конкретных ресурсов. Например, если время ответа на запросы `configmaps` резко возрастает, это может указывать на их чрезмерное количество в кластере (как это было в старых версиях Helm).
