# Мониторинг kube-apiserver

## Определения

- **Мониторинг `kube-apiserver`** — процесс наблюдения за ключевыми показателями производительности и состояния API-сервера Kubernetes для обеспечения стабильности и надежности кластера.
- **SLI (Service Level Indicator) и SLO (Service Level Objective)** — ключевые концепции для измерения и целеполагания в области надежности. Их подробное определение и примеры приведены в основной заметке: **[Концепции SRE: SLA, SLO, SLI и метрики надежности](../../../Concepts/SRE/sre_concepts_main.md)**. Нарушение SLO обычно является триггером для оповещений (алертов).

## Основные концепции

Ключевыми индикаторами состояния `kube-apiserver` являются:

1.  **Задержка выполнения запросов (Request Latency)**: Время, которое требуется API-серверу для обработки входящих запросов.
    -   **Метрика**: `apiserver_request_duration_seconds_bucket`.
    -   **Описание**: Гистограмма времени выполнения запросов, которая позволяет рассчитывать перцентили (например, p99). При расчете следует исключать долгоживущие запросы (`watch`, `connect`), чтобы избежать искажения результатов.

2.  **Частота ошибок (Error Rate)**: Доля запросов, завершившихся с ошибкой.
    -   **Метрика**: `apiserver_requests_total`.
    -   **Описание**: Счетчик всех запросов к API-серверу с разделением по коду ответа. Для мониторинга ошибок отбираются клиентские (`4xx`) и серверные (`5xx`) статусы.

## Практические сценарии

### Мониторинг задержки (Latency)

- **SLI**: 99-й перцентиль (`p99`) времени ответа на запросы.
- **SLO**: `p99` < 100 мс.

**Пример расчета SLI в PromQL:**
```promql
histogram_quantile(0.99, sum(rate(apiserver_request_duration_seconds_bucket{verb!~"WATCH|CONNECT"}[5m])) by (le))
```

**Правило для алерта:** `p99 > 0.1`
- **Действие:** Если `kube-apiserver` отвечает медленнее, требуется немедленное расследование. Возможные причины: проблемы с `etcd`, сетью или высокая нагрузка на сам API-сервер.

### Мониторинг частоты ошибок

- **SLI**: Количество запросов с кодом `4xx` или `5xx`.
- **SLO**: < 5 ошибок в минуту.

**Пример расчета SLI в PromQL:**
```promql
sum(rate(apiserver_requests_total{code=~"4..|5.."}[5m]))
```

**Правило для алерта:** Количество ошибок превышает 5 за последние 5 минут.
- **Действие:** Появление значительного количества ошибок требует вмешательства дежурного инженера.

## Дополнительная информация

Помимо метрик для алертинга, для диагностики и анализа полезны следующие метрики, которые рекомендуется выводить на дашборды:

- **Количество запросов по методам (`verb`) и ресурсам (`resource`):**
  - Помогает выявить аномальную активность, например, когда один из операторов "спамит" API-сервер тысячами запросов к одному объекту.

- **Задержка (latency) по каждому типу объектов:**
  - Позволяет обнаружить проблемы с производительностью для конкретных ресурсов. Например, если время ответа на запросы `configmaps` резко возрастает, это может указывать на их чрезмерное количество в кластере.
