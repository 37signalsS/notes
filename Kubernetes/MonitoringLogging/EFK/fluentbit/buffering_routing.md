## Определения

**Буферизация (Buffering)** — механизм временного хранения записей логов перед их отправкой в место назначения. Это ключевой элемент для обеспечения надежности доставки при сбоях сети или недоступности конечного хранилища.

**Слой хранения (Storage Layer)** — подсистема Fluent Bit, отвечающая за управление буферами (на диске или в памяти).

**Тег (Tag)** — строковый идентификатор, присваиваемый каждой записи при сборе. Используется как ключ для определения маршрута движения данных.

**Маршрутизация (Routing)** — процесс сопоставления тега записи с правилами `Match` в плагинах вывода (`[OUTPUT]`).

## Основные концепции

### Модели буферизации

Fluent Bit использует систему чанков (chunks) для хранения данных. Поддерживаются две основные модели:

1. **Memory (в памяти)**
    * Данные хранятся только в оперативной памяти.
    * Высокая скорость обработки.
    * **Риск:** при перезагрузке процесса или нехватке памяти (OOM — Out of Memory) накопленные данные будут утеряны.

2. **Filesystem (на диске)**
    * Данные сохраняются на диск с использованием механизма Memory-mapped files.
    * Обеспечивает персистентность (сохранность) данных между перезапусками.
    * Работает по принципу **FIFO (First In, First Out)** — "первым пришёл, первым ушёл".

### Управление нагрузкой (Backpressure)

Когда система назначения работает медленнее, чем поступают новые логи, возникает ситуация "обратного давления". Для ее решения используются параметры:

* **Mem_Buf_Limit**: Лимит памяти для входного плагина. Если предел достигнут, Fluent Bit приостанавливает чтение новых данных (pause) до тех пор, пока буфер не освободится.
* **Retry_Limit**: Ограничение количества попыток отправки чанка.

### Механизм маршрутизации

Маршрутизация основана на сопоставлении тегов:

* **Match**: Принимает простые шаблоны с подстановочными знаками (`*` — один уровень, `**` — любой путь).
* **Match_Regex**: Позволяет использовать регулярные выражения для гибкой фильтрации.

Порядок фильтров и выходов в конфигурации имеет значение: логи проходят через них последовательно.

## Практические сценарии

### Сценарий 1: Надежная доставка с дисковым буфером

Использование диска позволяет минимизировать риск потери данных при нестабильном соединении с Elasticsearch.

```ini
[SERVICE]
    Flush        1
    Log_Level    info
    storage.path /var/lib/fluent-bit/storage/
    storage.sync normal

[INPUT]
    Name          tail
    Tag           kube.*
    Path          /var/log/containers/*.log
    Parser        cri
    storage.type  filesystem
    Mem_Buf_Limit 10MB

[OUTPUT]
    Name        es
    Match       kube.*
    Host        elasticsearch.logging.svc
    Port        9200
    Retry_Limit False
```

*   `storage.type filesystem`: Принудительно сохраняет чанки на диск.
*   `Retry_Limit False`: Отключает лимит попыток, заставляя Fluent Bit повторять отправку бесконечно (актуально для критически важных логов).

### Сценарий 2: Группировка логов по окружению (Namespace)

Разделение потоков данных на основе метаданных Kubernetes.

```ini
# Фильтр добавляет метаданные (namespace, pod_name)
[FILTER]
    Name                kubernetes
    Match               kube.*
    Merge_Log           On

# Отправка логов production в отдельный индекс
[OUTPUT]
    Name            es
    Match_Regex     ^kube.*\.prod\..*$
    Host            es-prod.logging.svc
    Logstash_Prefix prod-logs

# Все остальные логи в общий индекс
[OUTPUT]
    Name            es
    Match           kube.*
    Host            es-dev.logging.svc
    Logstash_Prefix other-logs
```

### Сценарий 3: Использование Kafka как буферного слоя

В высоконагруженных системах Fluent Bit отправляет данные в Kafka, которая выступает в роли "амортизатора" (Buffer Layer).

```ini
[OUTPUT]
    Name        kafka
    Match       kube.*
    Brokers     kafka-broker.kafka.svc:9092
    Topics      kube-logs
```

Это позволяет изолировать сбор логов от их обработки и гарантирует сохранность данных даже при полной остановке систем анализа (Elasticsearch/ClickHouse).
