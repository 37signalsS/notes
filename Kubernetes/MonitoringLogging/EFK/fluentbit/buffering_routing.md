# Буферизация и маршрутизация в Fluent Bit

## Определения

**Буферизация (Buffering)** — механизм временного хранения записей логов перед их отправкой в место назначения. Необходим для предотвращения потери данных при сбоях сети или недоступности хранилища.

**Слой хранения (Storage Layer)** — подсистема Fluent Bit, управляющая жизненным циклом чанков (chunks) данных в памяти или на диске.

**Чанк (Chunk)** — логический блок данных, содержащий группу записей логов. Минимальная единица обработки для системы хранения.

**Тег (Tag)** — строковый идентификатор, присваиваемый каждой записи при сборе. Основной ключ для определения маршрута движения данных.

**Маршрутизация (Routing)** — процесс сопоставления тега записи с правилами `Match` или `Match_Regex` в плагинах вывода.

**Обратное давление (Backpressure)** — состояние, при котором скорость поступления данных превышает скорость их обработки или отправки, что требует механизмов регулирования нагрузки.

## Основные концепции

### Модели хранения данных

Fluent Bit поддерживает гибридную систему хранения, где данные могут находиться в двух состояниях:

1.  **Memory (только в памяти)**:
    *   Данные хранятся в RAM (Random Access Memory).
    *   Максимальная производительность.
    *   **Риск**: При сбое процесса или перезагрузке узла данные будут безвозвратно утеряны.
2.  **Filesystem (дисковый буфер)**:
    *   Использует механизм Memory-mapped files (mmap) для записи на диск.
    *   **Персистентность**: Данные сохраняются между перезапусками агента.
    *   **Управление очередью**: Работает по принципу FIFO (First In, First Out).

### Глобальные настройки слоя хранения (`service:`)

В версиях 3.x доступны расширенные параметры для тонкой настройки (в формате YAML):

| Параметр | Описание | Значение по умолчанию |
|:---|:---|:---|
| `storage.path` | Путь к директории на диске для хранения чанков. | Не задано |
| `storage.sync` | Режим синхронизации с диском (`normal`, `full`). | `normal` |
| `storage.metrics` | Включение эндпоинта `/api/v1/storage` для мониторинга буферов. | `off` |
| `storage.max_chunks_up` | Лимит чанков, которые могут одновременно находиться в памяти. | `128` |
| `storage.backlog.mem_limit` | Лимит памяти для подгрузки старых данных (бэклога) после перезапуска. | `5M` |

### Механизм управления нагрузкой (Backpressure)

Для предотвращения падения агента по OOM (Out of Memory) используются три уровня защиты:

1.  **Лимит плагина ввода (`mem_buf_limit`)**: Ограничивает объем данных, который плагин может держать в памяти. При достижении лимита плагин переходит в состояние `pause`.
2.  **Лимит активных чанков (`storage.max_chunks_up`)**: Если активных чанков в RAM больше лимита, новые чанки записываются **только на диск** (состояние `down`), минуя память.
3.  **Принудительная пауза (`storage.pause_on_chunks_overlimit`)**: Если включено, входной плагин полностью останавливает прием данных, пока количество активных чанков не снизится.

### Логика маршрутизации

Маршрутизация происходит на этапе вывода и основывается на правилах сопоставления тегов:

*   **Match**: Использует маски (`*` — один сегмент, `**` — любой путь). Пример: `kube.*` соответствует `kube.prod` и `kube.dev`.
*   **Match_Regex**: Использует регулярные выражения для более сложных правил (например, исключение определенных пространств имен).

## Практические сценарии

### Сценарий 1: Конфигурация для высоконагруженных Production-сред

Настройка с максимальной надежностью и защитой от переполнения памяти (рекомендуемый формат YAML для Fluent Bit 3.x+).

```yaml
service:
  flush: 1
  http_server: on
  http_port: 2020
  storage.path: /var/lib/fluent-bit/storage/
  storage.sync: normal
  storage.metrics: on
  storage.max_chunks_up: 256
  storage.backlog.mem_limit: 15M

pipeline:
  inputs:
    - name: tail
      tag: kube.*
      path: /var/log/containers/*.log
      parser: cri
      # Использовать диск как основной буфер
      storage.type: filesystem
      # Ограничение памяти на входе
      mem_buf_limit: 20MB

  outputs:
    - name: es
      match: kube.*
      host: elasticsearch.logging.svc
      # Бесконечные попытки при сбоях
      retry_limit: false
```

### Сценарий 2: Маршрутизация на основе пространств имен (Namespaces)

Разделение потоков данных для разных команд.

```yaml
pipeline:
  filters:
    # Фильтр добавляет метаданные Kubernetes
    - name: kubernetes
      match: kube.*
      merge_log: on

  outputs:
    # Логи безопасности (namespace: security) отправляются в защищенный индекс
    - name: es
      match_regex: ^kube\.var\.log\.containers\..*_security_.*$
      host: es-security.internal
      index: security-logs
      logstash_format: on

    # Все остальные логи в общий Elasticsearch
    - name: es
      match: kube.*
      host: es-general.internal
      index: general-logs
      logstash_format: on
```

### Сценарий 3: Динамическая маршрутизация через Rewrite_Tag

Используется для изменения тега записи на основе ее содержимого (например, уровня логирования).

```yaml
pipeline:
  filters:
    - name: rewrite_tag
      match: kube.*
      # Если в поле 'level' значение 'ERROR', меняем тег на 'alert.error'
      rule: $level ^(ERROR)$ alert.error false
      # Если 'WARN', меняем тег на 'alert.warn'
      rule: $level ^(WARN)$ alert.warn false

  outputs:
    - name: slack
      match: alert.error
      webhook: https://hooks.slack.com/services/...
```
