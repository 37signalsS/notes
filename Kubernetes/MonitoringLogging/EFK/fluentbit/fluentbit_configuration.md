# Конфигурация Fluent Bit

## Определения

**Секция `[SERVICE]` (или `service:`)** — блок глобальных настроек движка Fluent Bit, определяющий интервалы сброса данных, уровни логирования, параметры буферизации и механизмы перезагрузки.

**Секция `[INPUT]` (или `inputs:`)** — блок конфигурации источников данных (плагинов ввода). Каждому входу присваивается тег (Tag) для дальнейшей маршрутизации.

**Секция `[FILTER]` (или `filters:`)** — правила модификации, обогащения или фильтрации записей. Применяются ко всем записям, теги которых соответствуют параметру `Match`.

**Секция `Processors` (версия 3.0+)** — новый механизм обработки данных, доступный только в YAML-конфигурации. Процессоры привязываются напрямую к конкретному плагину ввода или вывода и работают в его потоке.

**Секция `[OUTPUT]` (или `outputs:`)** — блок конфигурации назначений (плагинов вывода) для отправки данных в системы хранения или анализа.

**Hot Reload** — механизм применения изменений в конфигурации без полной остановки и перезапуска процесса Fluent Bit.

## Основные концепции

### Форматы конфигурации

Fluent Bit поддерживает два основных формата конфигурации:
1.  **Classic (INI-подобный)**: Использует расширение `.conf`. Традиционный формат, простой, но не поддерживает новые функции, такие как процессоры.
2.  **YAML (YAML Ain't Markup Language)**: Использует расширение `.yaml`. Рекомендуемый формат для современных развертываний (v3.x+), так как он поддерживает типизацию сигналов (логи, метрики, трассировки) и процессоры.

### Жизненный цикл записи

Каждая запись проходит через строго определенную последовательность этапов в конвейере (pipeline):

```
[INPUT] → [PROCESSORS] → [FILTER] → [PROCESSORS] → [OUTPUT]
   ↓          ↓             ↓             ↓            ↓
  Сбор    →  Разбор      → Обработка   → Финализация → Отправка
```

### Секция `service`: Глобальные настройки (YAML)

```yaml
service:
    flush:           1
    daemon:          off
    log_level:       info
    # Путь к файлу с определениями парсеров (в v3.x поддерживается YAML формат)
    parsers_file:    parsers.yaml
    # Включение горячей перезагрузки (SIGHUP или HTTP API)
    hot_reload:      on
    
    # HTTP-сервер для мониторинга и API
    http_server:     on
    http_listen:     0.0.0.0
    http_port:       2020
    
    # Глобальные настройки хранения (Storage Layer)
    storage.path:              /var/lib/fluent-bit/storage/
    storage.sync:              normal
    storage.backlog.mem_limit: 128M
```

> **Примечание:** Несмотря на переход на YAML, Fluent Bit сохраняет обратную совместимость, поэтому директива `parsers_file: parsers.conf` (Classic формат) по-прежнему широко встречается и корректно обрабатывается движком.

### Секция `pipeline`: Сбор и обработка

#### Ввод данных (Inputs) и Процессоры

В версии 3.x процессоры позволяют выполнять тяжелые операции (например, SQL-фильтрацию или разбор JSON) непосредственно в потоке плагина ввода, не нагружая основной цикл событий.

```yaml
pipeline:
    inputs:
        - name: tail
          tag:  kube.*
          path: /var/log/containers/*.log
          # Использование процессоров (только в YAML)
          processors:
              logs:
                  - name: content_modifier
                    action: insert
                    key: cluster_name
                    value: production-01
```

**Примечание:** Подробности разбора строк и использования регулярных выражений приведены в [parsing.md](./parsing.md).

#### Фильтрация и обогащение (Filters)

Классический способ обработки, основанный на тегах. Плагин `kubernetes` является стандартом для обогащения логов метаданными из Kubernetes API.

```yaml
    filters:
        - name: kubernetes
          match: kube.*
          merge_log: on
          keep_log: off
          # Использовать аннотации подов для выбора парсера
          k8s-logging.parser: on
```

#### Доставка данных (Outputs)

```yaml
    outputs:
        - name:  es
          match: kube.*
          host:  elasticsearch-master.logging.svc
          port:  9200
          logstash_format: on
          logstash_prefix: k8s-logs
          # Бесконечные попытки отправки при сбоях
          retry_limit:     false
          # Количество потоков для параллельной отправки
          workers:         2
```

Детали механизмов надежности и дисковой буферизации описаны в [buffering_routing.md](./buffering_routing.md).

## Практические сценарии

### Сценарий 1: Конфигурация с Hot Reload и HTTP API

Использование современных механизмов управления конфигурацией в Kubernetes через ConfigMap.

```yaml
service:
    hot_reload: on
    http_server: on
    http_port: 2020

pipeline:
    inputs:
        - name: tail
          path: /var/log/containers/*.log
          tag: logs.*

    outputs:
        - name: stdout
          match: "*"
```

**Применение изменений без перезагрузки пода:**
1. Обновить ConfigMap в Kubernetes.
2. Выполнить запрос к API Fluent Bit:
   ```bash
   curl -X POST http://fluent-bit-service:2020/api/v2/reload
   ```

### Сценарий 2: Использование SQL-процессоров для фильтрации

Сценарий, в котором необходимо отфильтровать только критические логи на этапе сбора, чтобы снизить нагрузку на сеть и хранилище.

```yaml
pipeline:
    inputs:
        - name: tail
          path: /var/log/app.log
          tag:  app.logs
          processors:
              logs:
                  - name: sql
                    # Выбираем только записи с уровнем ERROR или CRITICAL
                    query: "SELECT * WHERE level IN ('ERROR', 'CRITICAL')"

    outputs:
        - name: es
          match: app.logs
          host:  es.internal
```
