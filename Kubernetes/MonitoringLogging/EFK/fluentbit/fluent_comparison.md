# Fluentd vs Fluent Bit: Сравнительный анализ и критерии выбора

## Определения

**Fluentd** — полнофункциональный агрегатор логов, написанный на Ruby/C. Предназначен для центральной точки маршрутизации, сложной обработки и веерной отправки логов в различные хранилища.

**Fluent Bit** — легковесный агент сбора логов (log shipper), написанный на C. Оптимизирован для высокой производительности и низкого потребления ресурсов на edge-устройствах и узлах Kubernetes.

**Агент сбора логов** (shipper) — компонент, развернутый на каждом узле для чтения, парсинга и первичной отправки логов.

**Центральный агрегатор** (aggregator) — компонент, принимающий логи от агентов, выполняющий сложную маршрутизацию и отправку в хранилища.

## Основные концепции

### Архитектурные различия

**Fluent Bit** спроектирован как легковесный **агент-сборщик** (agent/shipper). Его основная задача — эффективно собирать логи с минимальным потреблением CPU и RAM, что делает его идеальным для развертывания в виде `DaemonSet` на каждом узле Kubernetes.

**Fluentd**, в свою очередь, является более мощным и гибким **агрегатором** (aggregator/router). Он потребляет больше ресурсов, но предоставляет значительно более широкие возможности по буферизации, сложной маршрутизации и обработке логов.

Эта разница в философии определяет их роли в гибридной архитектуре: Fluent Bit на узлах собирает логи и пересылает их на центральный слой агрегации, построенный на базе Fluentd.

| Критерий | Fluent Bit | Fluentd |
|----------|------------|---------|
| **Основная роль** | Агент на узле, edge-устройства | Центральный агрегатор и роутер |
| **Потребление RAM** | ~1-50 МБ | >100 МБ (зависит от плагинов) |
| **Нагрузка на CPU** | Очень низкая | Средняя-высокая |
| **Язык** | C (фокус на производительности) | Ruby/C (гибкость и экосистема) |
| **Плагины** | ~100+ (встроенные) | ~1000+ (устанавливаемые как Gems) |
| **Конфигурация** | Простой INI-формат | Гибкий формат со сложными правилами |
| **Зависимости** | Нет | Ruby interpreter, Gems |

### Сходства

- Архитектура конвейера: `input → filter → output`
- Маршрутизация на основе тегов
- Поддержка форматов: JSON, регулярные выражения, стандартные логи
- Обеспечение надежности: TLS, переотправка с экспоненциальной задержкой, буферизация
- Парсинг многострочных логов (например, stack traces)

### Буферизация и надежность

| Аспект | Fluentd | Fluent Bit |
|--------|---------|------------|
| **Буфер по умолчанию** | `file` (для большинства плагинов) | `memory` (глобально) |
| **Типы буферов** | `memory` (в памяти), `file` (на диске) | `memory`, `filesystem` (дисковый) |
| **Управление перегрузкой** | `overflow_action`, backpressure | `Mem_Buf_Limit`, `storage.backlog.mem_limit` |
| **Гибкость маршрутизации** | `@label`, `copy`, сложные графы | Простые правила `Match`/`Match_Regex` |
| **Надежность доставки** | Очень высокая с `file`-буфером и `retry_forever` | Высокая с `storage.type=filesystem` и `Retry_Limit=False` |

## Матрица принятия решений

| Сценарий | Рекомендация | Причина |
|----------|-------------|---------|
| Сбор логов на узлах Kubernetes | **Fluent Bit** | Низкое потребление ресурсов, нативность. |
| Ограниченные ресурсы (IoT, Edge) | **Fluent Bit** | Минимальный footprint, отсутствие зависимостей. |
| Центральная агрегация логов | **Fluentd** | Мощная маршрутизация, отказоустойчивость. |
| Сложная маршрутизация и трансформация | **Fluentd** | Плагины для дедупликации, `copy`, `@label`. |
| Отправка в экзотические хранилища | **Fluentd** | Огромное количество output-плагинов. |
| **Production-кластер Kubernetes** | **Fluent Bit → Fluentd** | **(Рекомендуемый гибридный подход)**. |

## Практические сценарии

### Сценарий 1: Малый кластер или ограниченные ресурсы

**Задача:** Собирать логи со всех подов и отправлять напрямую в Elasticsearch.
**Выбор:** **Fluent Bit** как единственный инструмент.

**Обоснование:**
- Простота развертывания и настройки.
- Низкое потребление ресурсов на каждом узле.
- Отсутствие необходимости в промежуточной агрегации.

```yaml
# Пример конфигурации Fluent Bit
config:
  outputs: |
    [OUTPUT]
        Name            es
        Match           kube.*
        Host            elasticsearch-master.logging.svc.cluster.local
        Port            9200
        Logstash_Format On
        Retry_Limit     False # Бесконечные попытки отправки
```

### Сценарий 2: Production-кластер (>50 узлов) или требования Compliance

**Задача:** Гарантированная доставка логов, архивирование в S3, отправка в Elasticsearch для анализа.
**Выбор:** Гибридная топология **Fluent Bit → Fluentd**.

**Обоснование:**
- **Надежность:** Fluentd выступает как центральный буфер, защищая от потери логов при недоступности Elasticsearch или S3.
- **Гибкость:** Fluentd централизованно управляет сложной логикой (дублирование потока в S3 и ES), не усложняя конфигурацию агентов на узлах.
- **Масштабируемость:** Легко добавлять новые хранилища, изменяя только конфигурацию Fluentd.

**Архитектура:**
```
            KUBERNETES CLUSTER
┌─────────────────────────────────────────────┐
│  [Node 1]      [Node 2]      [Node N]       │
│  Fluent Bit →  Fluent Bit →  Fluent Bit ──┐ │
└───────│───────────│───────────│───────────┘ │
        └───────────┼───────────┘             │
                    │ (Forward protocol)      │
            ┌───────▼───────┐                 │
            │    Fluentd    │ (StatefulSet)   │
            │  (Aggregator) │                 │
            └───────┬───────┘                 │
      ┌─────────────┼─────────────┐           │
      │             │             │           │
┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐   │
│ Elasticsearch │ │    S3     │ │   Kafka   │   │
└─────────────┘ └─────────────┘ └─────────────┘
```

**Пример конфигурации Fluentd для дублирования потока:**
```xml
<source>
  @type forward
  port 24224
</source>

<match kube.**>
  @type copy
  
  <store>
    @type elasticsearch
    host es.logging.svc
    port 9200
    <buffer tag,time>
      @type file
      path /var/lib/fluentd/buffer/es
      chunk_limit_size 5m
      flush_interval 5s
      retry_forever true
    </buffer>
  </store>
  
  <store>
    @type s3
    s3_bucket my-logs-archive-bucket
    path logs/
    <buffer tag>
      @type file
      path /var/lib/fluentd/buffer/s3
      chunk_limit_size 10m
      flush_interval 60s
      retry_forever true
    </buffer>
  </store>
</match>
```
