# Fluentd vs Fluent Bit: Сравнительный анализ

## Определения

**Fluentd** — полнофункциональный агрегатор логов, написанный на Ruby/C. Предназначен для центральной точки маршрутизации и обработки логов.

**Fluent Bit** — легковесный агент сбора логов, написанный на C. Оптимизирован для edge-сценариев: узлы Kubernetes, IoT, системы с ограниченными ресурсами.

## Основные концепции

### Архитектурные различия

**Fluent Bit** спроектирован как легковесный **агент-сборщик** (agent/shipper). Его основная задача — эффективно собирать логи с минимальным потреблением CPU и RAM, что делает его идеальным для развертывания в виде `DaemonSet` на каждом узле Kubernetes.

**Fluentd**, в свою очередь, является более мощным и гибким **агрегатором** (aggregator/router). Он потребляет больше ресурсов, но предоставляет значительно более широкие возможности по буферизации, сложной маршрутизации и обработке логов.

Эта разница в философии определяет их роли в гибридной архитектуре: Fluent Bit на узлах собирает логи и пересылает их на центральный слой агрегации, построенный на базе Fluentd.

| Критерий | Fluent Bit | Fluentd |
|----------|------------|---------|
| **Назначение** | Агент на узле, edge-устройства | Центральный агрегатор и роутер |
| **Потребление RAM** | ~5–50 МБ | ~200–500 МБ |
| **Нагрузка на CPU** | Низкая | Средняя-высокая |
| **Язык реализации** | C (фокус на производительности) | Ruby/C (широкая экосистема) |
| **Количество плагинов** | ~100+ | ~1000+ |

### Сходства

- Модель конвейера: `inputs → filters → outputs`
- Маршрутизация по тегам
- Поддержка форматов: JSON, лог-файлы, структурированные события
- TLS, сжатие, повторные попытки с экспоненциальной задержкой
- Парсинг мультистрочных логов

### Буферизация и надежность

| Аспект | Fluentd | Fluent Bit |
|--------|---------|------------|
| **Буфер по умолчанию** | `file`/`memory` на каждый output | `memory` + опциональный `filesystem` |
| **Управление перегрузкой** | `overflow_action`, backpressure | `Mem_Buf_Limit`, `storage.backlog.mem_limit` |
| **Гибкость маршрутизации** | `@label`, `copy`, сложные графы | Простые правила `Match`/`Match_Regex` |
| **Надежность доставки** | Высокая с `file`-буфером | Высокая с `storage.type=filesystem` |

## Практические сценарии

### Сценарий 1: Fluent Bit как единственный сборщик

Применение: небольшие кластеры Kubernetes, ограниченные ресурсы.

```yaml
config:
  outputs: |
    [OUTPUT]
        Name            es
        Match           kube.*
        Host            elasticsearch-master.logging.svc.cluster.local
        Port            9200
        Logstash_Format On
        Retry_Limit     False
```

### Сценарий 2: Гибридная топология (рекомендуемая)

Fluent Bit на каждом узле → Fluentd (агрегатор) → Хранилища

```
┌─────────────────────────────────────────────────────────────┐
│                    KUBERNETES CLUSTER                       │
│                                                             │
│  ┌─────────────┐    ┌─────────────┐    ┌─────────────┐     │
│  │  Fluent Bit │    │  Fluent Bit │    │  Fluent Bit │     │
│  │  (Node 1)   │    │  (Node 2)   │    │  (Node N)   │     │
│  └──────┬──────┘    └──────┬──────┘    └──────┬──────┘     │
│         │                  │                  │            │
│         └──────────────────┼──────────────────┘            │
│                            │ Forward protocol             │
│                   ┌────────▼────────┐                     │
│                   │     Fluentd     │                     │
│                   │  (Aggregator)   │                     │
│                   └────────┬────────┘                     │
│                            │                              │
│         ┌──────────────────┼──────────────────┐           │
│         │                  │                  │           │
│    ┌────▼────┐       ┌────▼────┐       ┌────▼────┐       │
│    │    ES   │       │   S3    │       │  Kafka  │       │
│    └─────────┘       └─────────┘       └─────────┘       │
└─────────────────────────────────────────────────────────────┘
```

### Сценарий 3: Продвинутая маршрутизация во Fluentd

```xml
<source>
  @type forward
  port 24224
</source>

<match app.**>
  @type copy
  
  <store>
    @type elasticsearch
    host es
    port 9200
    <buffer tag,time>
      @type file
      path /var/lib/fluentd/buffer/es
      chunk_limit_size 5m
      flush_interval 5s
      retry_forever true
    </buffer>
  </store>
  
  <store>
    @type s3
    s3_bucket logs-archive
    <buffer tag>
      @type file
      path /var/lib/fluentd/buffer/s3
      chunk_limit_size 10m
      flush_interval 60s
    </buffer>
  </store>
</match>
```
