## Определения

**Fluentd** — полнофункциональный агрегатор логов с открытым исходным кодом, написанный на Ruby и C. Предназначен для создания центральных узлов маршрутизации, сложной обработки и веерной отправки данных в различные хранилища.

**Fluent Bit** — легковесный и высокопроизводительный агент сбора и обработки логов, написанный на языке C. Оптимизирован для сред с ограниченными ресурсами: контейнеров, edge-устройств и узлов Kubernetes.

**Агент сбора логов (Log Shipper)** — компонент, развернутый непосредственно в источнике данных (например, на каждом узле кластера) для первичного чтения, парсинга и пересылки логов.

**Центральный агрегатор (Aggregator)** — промежуточный слой, который принимает потоки данных от множества агентов, выполняет их объединение, сложную фильтрацию и доставку в системы хранения.

## Основные концепции

### Архитектурные различия

Основное различие заключается в фокусе инструментов: Fluent Bit спроектирован для максимальной производительности при минимальном потреблении ресурсов, в то время как Fluentd ориентирован на гибкость и расширяемость за счет богатой экосистемы плагинов.

| Критерий | Fluent Bit | Fluentd |
|:---|:---|:---|
| **Основная роль** | Агент на узле (Edge), Shipper | Центральный агрегатор, Router |
| **Потребление RAM (Random Access Memory)** | ~1–50 МБ | >100 МБ (зависит от количества Ruby-плагинов) |
| **Нагрузка на CPU (Central Processing Unit)** | Минимальная | Средняя или высокая при сложной обработке |
| **Язык разработки** | C | Ruby и C |
| **Экосистема плагинов** | ~100+ (встроены в бинарный файл) | ~1000+ (устанавливаются как Gems) |
| **Зависимости** | Отсутствуют (статическая сборка) | Требуется интерпретатор Ruby |

### Сходства инструментов

Оба инструмента разработаны в рамках проекта Fluent и разделяют общие принципы:

- **Конвейерная обработка:** данные проходят этапы `input → filter → output`.
- **Маршрутизация по тегам:** использование меток для определения пути следования логов.
- **Надежность:** поддержка TLS (Transport Layer Security), механизмы повторных попыток (retries) и буферизация.
- **Гибкость:** разбор структурированных (JSON) и неструктурированных данных.

Детали парсинга данных описаны в [parsing.md](./parsing.md).

### Сравнение механизмов буферизации

| Характеристика | Fluent Bit | Fluentd |
|:---|:---|:---|
| **Буфер по умолчанию** | В памяти (`memory`) | На диске (`file`) для большинства плагинов |
| **Типы буферизации** | `memory`, `filesystem` (дисковая) | `memory`, `file` |
| **Защита от перегрузки** | `Mem_Buf_Limit`, Backpressure | `overflow_action`, блокировка очереди |
| **Надежность доставки** | Высокая при настройке `storage.type=filesystem` | Очень высокая благодаря зрелым механизмам `retry_forever` |

Подробности настройки буферов Fluent Bit приведены в [buffering_routing.md](./buffering_routing.md).

## Практические сценарии

### Сценарий 1: Сбор логов в малом кластере Kubernetes

**Задача:** Сбор стандартных логов контейнеров и отправка в Elasticsearch.
**Выбор:** **Fluent Bit**.
**Обоснование:**

- Минимальный "отпечаток" ресурсов на узлах.
- Встроенный плагин `kubernetes` эффективно обогащает логи метаданными.
- Прямая отправка в Elasticsearch не требует промежуточных звеньев при малых объемах.

### Сценарий 2: Гибридная архитектура для Enterprise (рекомендуемая)

**Задача:** Гарантированная доставка логов из множества кластеров, дублирование потоков в S3 (Simple Storage Service) для архива и в Elasticsearch для анализа.
**Выбор:** **Fluent Bit (агенты) → Fluentd (агрегаторы)**.

**Архитектурная схема:**

```
            KUBERNETES CLUSTER
┌─────────────────────────────────────────────┐
│  [Node 1]      [Node 2]      [Node N]       │
│  Fluent Bit →  Fluent Bit →  Fluent Bit ──┐ │
└───────│───────────│───────────│───────────┘ │
        └───────────┼───────────┘             │
                    │ (Протокол Forward)      │
            ┌───────▼───────┐                 │
            │    Fluentd    │ (Слой агрегации)│
            │  (Aggregator) │                 │
            └───────┬───────┘                 │
      ┌─────────────┼─────────────┐           │
      │             │             │           │
┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐   │
│ Elasticsearch │ │    S3     │ │   Kafka   │   │
└─────────────┘ └─────────────┘ └─────────────┘
```

**Преимущества подхода:**

1. **Снижение нагрузки на хранилище:** Fluentd может объединять (batch) мелкие чанки от множества агентов перед отправкой.
2. **Отказоустойчивость:** Если Elasticsearch недоступен, Fluentd накапливает логи в дисковом буфере, не нагружая узлы кластера.
3. **Сложная логика:** Использование плагина `copy` во Fluentd для параллельной отправки данных в разные системы.
