# Парсинг логов в Fluent Bit

## Определения

**Парсинг (Parsing)** — процесс преобразования неструктурированной строки лога в структурированную запись (набор пар ключ-значение).

**Парсер (Parser)** — именованный набор правил в конфигурации (`[PARSER]`), определяющий логику разбора конкретного формата лога.

**Декодер (Decoder)** — механизм внутри парсера для обработки специально закодированных полей (например, вложенный JSON или экранированные строки).

**Многострочный парсинг (Multiline)** — механизм объединения нескольких строк (например, стектрейсов) в одно логическое событие.

## Основные концепции

### Типы парсеров

| Формат | Тип парсера | Особенности и применение |
|:---|:---|:---|
| **CRI** | `cri` или `regex` | Стандарт для Kubernetes. Разбор логов `containerd` и `CRI-O`. |
| **JSON** | `json` | Самый производительный формат для уже структурированных логов. |
| **Logfmt** | `logfmt` | Популярный формат `key=value`. Встроенная поддержка с версии 1.8+. |
| **Regex** | `regex` | Универсальный разбор через регулярные выражения с использованием именованных групп `(?<name>...)`. Самый ресурсозатратный. |
| **Syslog** | `syslog` | Поддержка стандартов RFC3164 и RFC5424. |
| **LTSV** | `ltsv` | Разбор Labeled Tab-separated Values. |

### Параметры времени (Time Resolution)

Парсеры отвечают не только за извлечение полей, но и за определение временной метки события (timestamp). По умолчанию Fluent Bit присваивает время прочтения файла, но парсер может извлечь оригинальное время генерации лога:

*   `Time_Key`: Имя поля в разобранном логе, содержащего временную метку (например, `time` или `@timestamp`).
*   `Time_Format`: Формат времени (используются спецификаторы `strftime`, например `%Y-%m-%dT%H:%M:%S.%L%z`).
*   `Time_Keep`: Сохранить поле со временем в итоговом JSON (`On`/`Off`). По умолчанию поле удаляется после установки внутренней метки события.
*   `Time_Offset`: Добавить смещение временной зоны (например, `+0300`), если в логах время локальное и без указания зоны.

### Места применения парсинга

1.  **Уровень Input (`[INPUT]`)**: Параметр `Parser`. Эффективно для однострочных логов. Парсинг происходит сразу при чтении.
2.  **Уровень Filter (`[FILTER]`)**: Плагин `parser`. Позволяет разбирать конкретное текстовое поле (например, поле `log`) после первичного сбора.
3.  **Processors (версия 3.0+)**: Процессоры в секции `inputs` или `outputs` позволяют выполнять парсинг и модификацию данных до попадания в основной конвейер, снижая нагрузку.
4.  **Аннотации Kubernetes**: Фильтр `kubernetes` может применять парсеры динамически на основе аннотаций пода (например, `fluentbit.io/parser: "nginx"`).

### Декодеры (Decoders)

Используются, когда лог упакован внутри другого формата (например, JSON внутри текстового поля).

*   **Типы**: `json`, `escaped`, `escaped_utf8`, `hex`.
*   **Синтаксис**: `Decode_Field_As <тип> <имя_поля>`.

### Современный многострочный парсинг

В новых версиях (3.x) рекомендуется использовать `multiline.parser` в плагине `tail`. Это позволяет склеивать строки максимально близко к источнику, используя конечные автоматы (state engine).

*   **Встроенные парсеры**: `java`, `python`, `go`, `ruby`, `cri`, `docker`.
*   **Кастомные парсеры**: Определяются в секции `[MULTILINE_PARSER]`. Каждое правило (Rule) описывает состояние (state), регулярное выражение и следующее состояние.

## Практические сценарии

### Сценарий 1: Разбор CRI-логов (Kubernetes)

Стандартный разбор для современных кластеров, использующих `containerd` или `CRI-O`.

```ini
# parsers.conf
[PARSER]
    Name        cri
    Format      regex
    Regex       ^(?<time>[^ ]+) (?<stream>stdout|stderr) (?<logtag>[^ ]*) (?<log>.*)$
    Time_Key    time
    Time_Format %Y-%m-%dT%H:%M:%S.%L%z
    Time_Keep   Off
```

### Сценарий 2: Обработка вложенного JSON (Decoders)

Если приложение пишет JSON, но среда исполнения (Docker/CRI) упаковывает его в текстовое поле `log`.

```ini
# parsers.conf
[PARSER]
    Name        docker_json_decoder
    Format      json
    Time_Key    time
    Time_Format %d/%b/%Y:%H:%M:%S %z
    # Декодируем текстовое поле 'log' как JSON-объект
    Decode_Field_As json log
```

### Сценарий 3: Парсинг формата Logfmt

Пример для логов, использующих ключи и значения (популярно в приложениях на Go).

```ini
# parsers.conf
[PARSER]
    Name        service_logfmt
    Format      logfmt
    # Опционально: игнорировать ключи без значений
    Logfmt_No_Bare_Keys true

# Использование в Input
[INPUT]
    Name        tail
    Path        /var/log/service.log
    Parser      service_logfmt
```

### Сценарий 4: Многострочные логи Java (Spring Boot)

Использование встроенного парсера для обработки стектрейсов напрямую в плагине `tail`.

```ini
# fluent-bit.conf
[INPUT]
    Name             tail
    Path             /var/log/containers/app-*.log
    Tag              app.*
    # Использование встроенного многострочного парсера (сначала java, затем cri как фоллбэк)
    multiline.parser java, cri
```

### Сценарий 5: Кастомный многострочный парсер (Custom Multiline)

Если стандартные парсеры не подходят, можно определить свой конечный автомат. Пример склейки логов, которые всегда начинаются с даты:

```ini
# parsers_multiline.conf
[MULTILINE_PARSER]
    Name          custom_date_multiline
    Type          regex
    Flush_timeout 1000
    # Правила:   Имя стейта   Regex шаблон                                 Следующий стейт
    Rule         "start_state" "/^[0-9]{4}-[0-9]{2}-[0-9]{2}.*/"           "cont"
    Rule         "cont"        "/^[^0-9].*/"                               "cont"
```

### Сценарий 6: Парсинг через Processors (Fluent Bit 3.x, YAML)

Современный подход использования процессоров на этапе `inputs`, что снижает накладные расходы на маршрутизацию.

```yaml
# fluent-bit.yaml
pipeline:
  inputs:
    - name: tail
      path: /var/log/app/*.json
      processors:
        logs:
          - name: parser
            parser: json
```

### Сценарий 7: Динамическое применение через Kubernetes Аннотации

Фильтр `kubernetes` может автоматически применять парсеры к логам конкретных подов, если они содержат аннотацию `fluentbit.io/parser`.

**Манифест пода (Deployment):**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  template:
    metadata:
      annotations:
        # Указываем Fluent Bit использовать встроенный парсер 'nginx'
        fluentbit.io/parser: nginx
```

**Конфигурация Fluent Bit:**
```ini
[FILTER]
    Name                kubernetes
    Match               kube.*
    Kube_URL            https://kubernetes.default.svc:443
    # Включаем чтение аннотаций для парсинга
    K8S-Logging.Parser  On
```

### Сценарий 8: Фильтр parser и сохранение данных (`Reserve_Data`)

При применении фильтра `parser` важно не потерять метаданные (например, теги Kubernetes), которые уже были добавлены к записи.

```ini
[FILTER]
    Name         parser
    Match        app.*
    Key_Name     log           # Имя поля, которое нужно распарсить
    Parser       custom_json
    Reserve_Data On            # Сохранить остальные поля (важно для K8s метаданных!)
    Preserve_Key Off           # Удалить оригинальное поле 'log' после успешного парсинга
```
