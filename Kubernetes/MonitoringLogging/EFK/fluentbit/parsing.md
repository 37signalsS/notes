# Парсинг логов в Fluent Bit

## Определения

**Парсинг (Parsing)** — процесс преобразования неструктурированной строки лога в структурированную запись (набор пар ключ-значение). Парсинг происходит на этапе [INPUT] (при чтении) или [FILTER] (при обработке), до попадания записи в основной конвейер.

**Парсер (Parser)** — именованный набор правил в конфигурации (`[PARSER]` в Classic или `parsers:` в YAML), определяющий логику разбора конкретного формата лога. Каждый входной плагин может иметь только один активный парсер.

**Декодер (Decoder)** — механизм внутри парсера для обработки специально закодированных полей (например, вложенный JSON, экранированные строки или Unicode-последовательности). Поддерживается цепочка декодеров с опциональными действиями при неудаче.

**Многострочный парсинг (Multiline Parsing)** — механизм объединения нескольких строк (например, стектрейсов Java/Python/Go или многострочных сообщений syslog) в одно логическое событие. Работает через конечный автомат (state engine) с правилами переходов между состояниями.

**Фильтр парсинга (Parser Filter)** — плагин фильтрации, применяющий именованный парсер к конкретному полю записи (`key_name`). Позволяет разбирать вложенные данные после первичного сбора.

**Процессор парсинга (Parser Processor)** — версия 3.0+, механизм обработки данных в YAML-конфигурации, привязанный напрямую к плагину ввода. Работает в потоке плагина, снижая нагрузку на основной цикл событий.

## Основные концепции

### Типы парсеров

| Формат | Тип парсера | Особенности и применение |
|:---|:---|:---|
| **CRI** | `cri` или `regex` | Стандарт для Kubernetes. Разбор логов `containerd` и `CRI-O`. |
| **JSON** | `json` | Самый производительный формат для уже структурированных логов. |
| **Logfmt** | `logfmt` | Популярный формат `key=value`. Встроенная поддержка с версии 1.8+. |
| **Regex** | `regex` | Универсальный разбор через регулярные выражения с использованием именованных групп `(?<name>...)`. Самый ресурсозатратный. |
| **Syslog** | `syslog` | Поддержка стандартов RFC3164 и RFC5424. |
| **LTSV** | `ltsv` | Разбор Labeled Tab-separated Values. |

### Параметры времени (Time Resolution)

Парсеры отвечают не только за извлечение полей, но и за определение временной метки события (timestamp). По умолчанию Fluent Bit присваивает время прочтения файла, но парсер может извлечь оригинальное время генерации лога:

*   `Time_Key`: Имя поля в разобранном логе, содержащего временную метку (например, `time` или `@timestamp`).
*   `Time_Format`: Формат времени (используются спецификаторы `strftime`, например `%Y-%m-%dT%H:%M:%S.%L%z`). Поле `%L` поддерживает дробные секунды и допустимо только после `%S` или `%s`.
*   `Time_Keep`: Сохранить поле со временем в итоговом JSON (`On`/`Off`). По умолчанию поле удаляется после установки внутренней метки события.
*   `Time_Offset`: Добавить смещение временной зоны (например, `+0300`), если в логах время локальное и без указания зоны.
*   `Time_Zone`: Имя часовой зоны IANA (например, `Europe/Moscow`, `America/New_York`). Приоритетнее `Time_Offset`, если оба заданы.
*   `Time_Strict`: Строгий режим разбора времени (`true` по умолчанию). При `false` парсер будет более терпим к отсутствию дробной части времени.
*   `Time_System_Timezone`: При `true` и отсутствии `%z` в формате времени используется системная временная зона из переменной `TZ`.

### Места применения парсинга

1.  **Уровень Input (`[INPUT]`)**: Параметр `Parser` (Classic) или `parser:` (YAML). Эффективно для однострочных логов. Парсинг происходит сразу при чтении, до фильтров и процессоров.
2.  **Уровень Filter (`[FILTER]`)**: Плагин `parser`. Позволяет разбирать конкретное текстовое поле (например, поле `log`) после первичного сбора. Поддерживает несколько парсеров (по одному на строку).
3.  **Processors (версия 3.0+)**: Процессоры в секции `inputs` или `outputs` позволяют выполнять парсинг и модификацию данных до попадания в основной конвейер, снижая нагрузку.
4.  **Аннотации Kubernetes**: Фильтр `kubernetes` может применять парсеры динамически на основе аннотаций пода (например, `fluentbit.io/parser: "nginx"`).

**Когда какой механизм использовать:**

| Механизм | Когда применять | Приоритет |
|:---|:---|:---|
| **Input Parser** | Лог уже структурирован (JSON, logfmt) или есть точный regex-формат | Самый высокий (минимальная задержка) |
| **Parser Filter** | Нужно распарсить поле внутри записи после обогащения Kubernetes-метаданными | Средний |
| **Processor** | Нужна обработка на этапе ввода с минимальными накладными расходами (только YAML, v3.x+) | Высокий (только v3.x+) |
| **Аннотации K8s** | Разные поды используют разные форматы логов | Динамический |

### Параметры конфигурации парсера

Полный список параметров, доступных для настройки кастомных парсеров:

| Параметр | Описание | По умолчанию |
|:---|:---|:---|
| `Name` | Уникальное имя парсера | *обязательный* |
| `Format` | Формат: `json`, `regex`, `logfmt`, `ltsv` | *обязательный* |
| `Regex` | Регулярное выражение (для формата `regex`) | *только regex* |
| `Time_Key` | Имя поля с временной меткой | *нет* |
| `Time_Format` | Формат времени (strftime) | *нет* |
| `Time_Keep` | Сохранять исходное поле времени | `Off` |
| `Time_Offset` | Смещение часовой зоны (например, `+0300`) | *нет* |
| `Time_Zone` | IANA-имя часовой зоны | *нет* |
| `Time_Strict` | Строгий разбор времени | `true` |
| `Time_System_Timezone` | Использовать системную TZ при отсутствии `%z` | `false` |
| `Skip_Empty_Values` | Пропускать пустые значения при разборе | `true` |
| `Types` | Приведение типов полей: `types field1:integer field2:float` | *нет* |
| `Logfmt_No_Bare_Keys` | Отклонять ключи без значений (logfmt) | `false` |
| `Decode_Field_As` | Декодирование поля с заменой содержимого | *нет* |
| `Decode_Field` | Декодирование поля с добавлением ключей | *нет* |

### Декодеры (Decoders)

Используются, когда лог упакован внутри другого формата (например, JSON внутри текстового поля). Fluent Bit поддерживает два варианта применения декодеров:

*   **`Decode_Field_As`**: Декодированное содержимое заменяет исходное поле. Дополнительные ключи не добавляются.
*   **`Decode_Field`**: Декодированное содержимое добавляется к исходной записи как новые ключи и значения.

**Типы декодеров:**

| Тип | Описание |
|:---|:---|
| `json` | Обработка содержимого как JSON-карты. Если декодер находит JSON, заменяет содержимое на структурированную карту. |
| `escaped` | Декодирование экранированной строки (например, Docker-логи с `\n`, `\t`). |
| `escaped_utf8` | Декодирование UTF-8 экранированных строк (например, `\u0009` -> табуляция). |
| `mysql_quoted` | Декодирование строк в формате MySQL-цитирования. |

**Опциональные действия при неудаче декодера:**

| Действие | Описание |
|:---|:---|
| `do_next` | Применить следующий декодер к тому же полю независимо от результата текущего. |
| `try_next` | Применить следующий декодер только если текущий завершился неудачей. |

**Ограничения:**
*   `decode_field_as`: При успешном декодировании другой декодер того же типа к тому же полю может быть применен только если данные продолжают быть неструктурированным текстом.
*   `decode_field`: Может быть применен только один раз к одному полю (предназначен для декодирования структурированных данных).

### Многострочный парсинг (Multiline)

Многострочный парсер объединяет несколько строк в одно событие через конечный автомат. Каждое правило (Rule) описывает:

1.  **Имя состояния (state)**: Текущее состояние автомата. Первое правило должно иметь имя `start_state`.
2.  **Регулярное выражение (regex)**: Паттерн для определения строк, принадлежащих данному состоянию.
3.  **Следующее состояние (next_state)**: Куда перейти после совпадения.

**Встроенные парсеры:**

| Парсер | Описание |
|:---|:---|
| `cri` | Логи CRI-O/containerd. Использует поле `_p` для определения завершенности строки (`F` = полная, `P` = частичная). |
| `docker` | Логи Docker JSON. Строки без `\n` считаются частичными и склеиваются. |
| `go` | Go-паника. Обнаруживает `panic:` и захватывает полный goroutine-стек. |
| `java` | Java-исключения. Обнаруживает `Exception`, `Error`, `Throwable` и их стек-трейсы. |
| `python` | Python-трейсы. Обнаруживает `Traceback (most recent call last):` и захватывает полный стек. |
| `ruby` | Ruby-исключения. Обнаруживает паттерны `file.rb:line:in 'method'` и продолжения `from`. |

**Параметры многострочного парсера:**

| Параметр | Описание | По умолчанию |
|:---|:---|:---|
| `Flush_Timeout` | Тайм-аут (мс) сброса незавершенного буфера | `4000` |
| `Key_Content` | Ключ со структурированным сообщением для обработки regex | *нет* |
| `Key_Group` | Ключ-идентификатор группировки (например, `stream` для stdout/stderr) | *нет* |
| `Key_Pattern` | Альтернативный ключ для применения regex (отдельно от `Key_Content`) | *нет` |
| `Match_String` | Строка для совпадения (для типов `endswith` и `equal`) | *нет* |
| `Negate` | Инвертировать результат regex (`true` = несовпадение считается совпадением) | `false` |
| `Parser` | Имя предопределенного парсера для предварительной обработки входных данных | *нет* |
| `Type` | Тип многострочного режима: `regex`, `endswith`, `equal` (или `eq`) | *обязательный* |
| `Multiline_Buffer_limit` | Максимальный размер буфера склейки (единицы: `KB`, `MB`, `GB`, `KiB`, `MiB`, `GiB`). При превышении — запись обрезается с флагом `multiline_truncated: true`. `0` = без ограничений. | `2MB` |

**Ограничения многострочного парсинга:**
*   Многострочный парсер не подчиняется параметру `buffer_max_size` входного плагина — составленная запись может превышать этот размер.
*   Опция `skip_long_lines` не применяется к многострочным сообщениям.
*   Невозможно извлечь временной ключ из тела многострочного сообщения напрямую. Для этого используйте фильтр.

## Практические сценарии

### Сценарий 1: Разбор CRI-логов (Kubernetes)

Стандартный разбор для современных кластеров, использующих `containerd` или `CRI-O`.

**Classic формат (`parsers.conf`):**
```ini
[PARSER]
    Name        cri
    Format      regex
    Regex       ^(?<time>[^ ]+) (?<stream>stdout|stderr) (?<logtag>[^ ]*) (?<log>.*)$
    Time_Key    time
    Time_Format %Y-%m-%dT%H:%M:%S.%L%z
    Time_Keep   Off
```

**YAML формат (`parsers.yaml`):**
```yaml
parsers:
  - name: cri
    format: regex
    regex: '^(?<time>[^ ]+) (?<stream>stdout|stderr) (?<logtag>[^ ]*) (?<log>.*)$'
    time_key: time
    time_format: '%Y-%m-%dT%H:%M:%S.%L%z'
    time_keep: off
```

**Использование во входном плагине:**
```yaml
pipeline:
  inputs:
    - name: tail
      path: /var/log/containers/*.log
      tag: kube.*
      parser: cri
```

### Сценарий 2: Обработка вложенного JSON (Decoders)

Если приложение пишет JSON, но среда исполнения (Docker/CRI) упаковывает его в текстовое поле `log`.

```ini
[PARSER]
    Name        docker_json_decoder
    Format      json
    Time_Key    time
    Time_Format %d/%b/%Y:%H:%M:%S %z
    # Декодируем текстовое поле 'log' как JSON-объект
    Decode_Field_As json log
```

### Сценарий 3: Парсинг формата Logfmt

Пример для логов, использующих ключи и значения (популярно в приложениях на Go).

```ini
[PARSER]
    Name        service_logfmt
    Format      logfmt
    # Опционально: игнорировать ключи без значений
    Logfmt_No_Bare_Keys true

# Использование в Input
[INPUT]
    Name        tail
    Path        /var/log/service.log
    Parser      service_logfmt
```

### Сценарий 4: Многострочные логи Java (Spring Boot)

Использование встроенного парсера для обработки стектрейсов напрямую в плагине `tail`.

```ini
[INPUT]
    Name             tail
    Path             /var/log/containers/app-*.log
    Tag              app.*
    multiline.parser java, cri
```

**YAML-эквивалент:**
```yaml
pipeline:
  inputs:
    - name: tail
      path: /var/log/containers/app-*.log
      tag: app.*
      multiline.parser: java, cri
```

### Сценарий 5: Кастомный многострочный парсер (Custom Multiline)

Если стандартные парсеры не подходят, можно определить свой конечный автомат. Пример склейки логов, которые всегда начинаются с даты:

```ini
[MULTILINE_PARSER]
    Name          custom_date_multiline
    Type          regex
    Flush_Timeout 1000
    Rule         "start_state" "/^[0-9]{4}-[0-9]{2}-[0-9]{2}.*/"           "cont"
    Rule         "cont"        "/^[^0-9].*/"                               "cont"
```

**YAML-эквивалент:**
```yaml
multiline_parsers:
  - name: custom_date_multiline
    type: regex
    flush_timeout: 1000
    rules:
      - state: start_state
        regex: '/^[0-9]{4}-[0-9]{2}-[0-9]{2}.*/'
        next_state: cont
      - state: cont
        regex: '/^[^0-9].*/'
        next_state: cont
```

**Использование:**
```yaml
pipeline:
  inputs:
    - name: tail
      path: /var/log/app/*.log
      tag: app.*
      multiline.parser: custom_date_multiline
```

### Сценарий 6: Парсинг через Processors (Fluent Bit 3.x, YAML)

Современный подход использования процессоров на этапе `inputs`, что снижает накладные расходы на маршрутизацию.

```yaml
pipeline:
  inputs:
    - name: tail
      path: /var/log/app/*.json
      processors:
        logs:
          - name: parser
            parser: json
```

### Сценарий 7: Динамическое применение через Kubernetes Аннотации

Фильтр `kubernetes` может автоматически применять парсеры к логам конкретных подов, если они содержат аннотацию `fluentbit.io/parser`.

**Манифест пода (Deployment):**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx
spec:
  template:
    metadata:
      annotations:
        # Указываем Fluent Bit использовать встроенный парсер 'nginx'
        fluentbit.io/parser: nginx
```

**Конфигурация Fluent Bit:**
```ini
[FILTER]
    Name                kubernetes
    Match               kube.*
    Kube_URL            https://kubernetes.default.svc:443
    # Включаем чтение аннотаций для парсинга
    K8S-Logging.Parser  On
```

### Сценарий 8: Фильтр parser и сохранение данных (`Reserve_Data`)

При применении фильтра `parser` важно не потерять метаданные (например, теги Kubernetes), которые уже были добавлены к записи.

```ini
[FILTER]
    Name         parser
    Match        app.*
    Key_Name     log           # Имя поля, которое нужно распарсить
    Parser       custom_json
    Reserve_Data On            # Сохранить остальные поля (важно для K8s метаданных!)
    Preserve_Key Off           # Удалить оригинальное поле 'log' после успешного парсинга
```

**YAML-эквивалент:**
```yaml
filters:
  - name: parser
    match: app.*
    key_name: log
    parser: custom_json
    reserve_data: on
    preserve_key: off
```

### Сценарий 9: Парсинг Syslog (RFC3164/RFC5424)

Разбор логов от сетевых устройств, syslog-агентов или стандартного syslog-демона Linux.

```ini
[PARSER]
    Name        syslog_rfc5424
    Format      syslog
    Time_Key    timestamp
    Time_Format %Y-%m-%dT%H:%M:%S%z
```

**Использование с UDP-входом:**
```yaml
pipeline:
  inputs:
    - name: syslog
      tag: syslog.*
      listen: 0.0.0.0
      port: 514
      protocol: udp
      parser: syslog_rfc5424

  outputs:
    - name: es
      match: syslog.*
      host: elasticsearch-master.logging.svc
      port: 9200
      logstash_format: on
      logstash_prefix: syslog
```

### Сценарий 10: Парсинг NGINX-логов

Разбор стандартного combined-формата логов NGINX с извлечением IP, метода, пути, кода ответа и User-Agent.

```ini
[PARSER]
    Name        nginx_combined
    Format      regex
    Regex       ^(?<remote>[^ ]*) (?<host>[^ ]*) (?<user>[^ ]*) \[(?<time>[^\]]*)\] "(?<method>\S+)(?: +(?<path>[^\"]*?)(?: +\S*)?)?" (?<code>[^ ]*) (?<size>[^ ]*)(?: "(?<referer>[^\"]*)" "(?<agent>[^\"]*)")?$
    Time_Key    time
    Time_Format %d/%b/%Y:%H:%M:%S %z
    Time_Keep   On
    Types       code:integer size:integer
```

**С декодированием JSON из поля `request_body` (если NGINX логирует тело запроса):**
```ini
[PARSER]
    Name        nginx_json_body
    Format      regex
    Regex       ^\[(?<time>[^\]]*)\] (?<remote>[^ ]*) (?<method>\S+) (?<path>\S+) (?<code>\d+) (?<size>\d+) (?<body>.+)$
    Time_Key    time
    Time_Format %d/%b/%Y:%H:%M:%S %z
    Decode_Field_As json body
    Types       code:integer size:integer
```

### Сценарий 11: Кастомный Regex с приведением типов

Извлечение полей из формата `APPLICATION: [LEVEL] message details` с приведением полей к нужным типам.

```ini
[PARSER]
    Name        app_log_regex
    Format      regex
    Regex       ^\[(?<timestamp>[^\]]+)\] (?<level>\w+) \[(?<component>[^\]]+)\] (?<pid>\d+) - (?<message>.+)$
    Time_Key    timestamp
    Time_Format %Y-%m-%d %H:%M:%S,%L
    Types       pid:integer
    Time_Keep   Off
```

**Использование с фильтром parser:**
```ini
[FILTER]
    Name         parser
    Match        app.*
    Key_Name     log
    Parser       app_log_regex
    Reserve_Data On
    Preserve_Key Off
```

### Сценарий 12: Многострочный парсер Python с группировкой по потоку

Склейка Python-трейсов с разделением по `stream` (stdout/stderr через `key_group`).

```yaml
multiline_parsers:
  - name: python_grouped
    type: regex
    flush_timeout: 2000
    key_content: log
    key_group: stream
    rules:
      - state: start_state
        regex: '/^Traceback \(most recent call last\):/'
        next_state: cont
      - state: cont
        regex: '/^\s+File|.*/'
        next_state: cont
      - state: cont
        regex: '/^\w+Error: |^\w+Exception: /'
        next_state: cont
```

### Сценарий 13: Декодирование escaped_utf8 (Unicode-символы в логах)

Обработка логов, содержащих Unicode-экранированные последовательности (например, табуляция `\u0009`).

```ini
[PARSER]
    Name        docker_utf8_decoder
    Format      json
    Time_Key    time
    Time_Format %Y-%m-%dT%H:%M:%S.%L
    Decode_Field_As escaped_utf8 log
```

### Сценарий 14: Цепочка декодеров (do_next / try_next)

Применение нескольких декодеров последовательно к одному полю. Например, сначала декодировать escaped-строку, затем попробовать распарсить как JSON.

```ini
[PARSER]
    Name        chained_decoder
    Format      json
    Time_Key    time
    Time_Format %Y-%m-%dT%H:%M:%S.%L
    # Сначала декодируем escaped-строку, затем пытаемся декодировать как JSON
    Decode_Field_As escaped log do_next
    Decode_Field_As json log
```

### Сценарий 15: Парсинг Kubernetes Audit Log

Разбор аудит-логов Kubernetes API-сервера для анализа безопасности.

```ini
[PARSER]
    Name   k8s-audit
    Format json
    Time_Key stageTimestamp
    Time_Format %Y-%m-%dT%H:%M:%S%.NZ

[INPUT]
    Name   tail
    Path   /var/log/kubernetes/audit.log
    Parser k8s-audit
    Tag    k8s.audit
    Read_From_Head true

[OUTPUT]
    Name   loki
    Match  k8s.audit
    Host   loki.internal.example.com
    Port   3100
    Labels job=k8s-audit,cluster=prod-eu-central
```

## Типовые ошибки и их решение

### Ошибка 1: Regex не совпадает с форматом лога

**Симптом:** Все записи попадают в `log` без разбора полей.

**Причина:** Несоответствие regex реальному формату строки.

**Диагностика и решение:**
1.  Вывести сырой лог через `fluent-bit -c config.yaml -o stdout` и визуально сравнить с regex.
2.  Использовать онлайн-тестеры regex (например, [Rubular](https://rubular.com/) для Ruby-синтаксиса, который использует Fluent Bit).
3.  Проверить экранирование спецсимволов в regex: `.`, `(`, `)`, `[`, `]`, `\` должны быть экранированы.

### Ошибка 2: `Reserve_Data On` не работает / теряются Kubernetes-метаданные

**Симптом:** После фильтра `parser` пропадают поля `kubernetes.*`.

**Причина:** По умолчанию фильтр `parser` удаляет все поля, кроме распарсенных.

**Решение:** Добавить `Reserve_Data On` (Classic) или `reserve_data: on` (YAML).

### Ошибка 3: Время в логах не распознается (Time_Format mismatch)

**Симптом:** Временная метка события = время чтения Fluent Bit, а не время из лога.

**Диагностика:**
1.  Проверить формат времени в логе: `2024-01-15T10:30:45.123Z` или `15/Jan/2024:10:30:45 +0000`.
2.  Убедиться, что `Time_Format` точно соответствует формату, включая пробелы, разделители и суффикс зоны.
3.  Проверить поддержку `%L` для дробных секунд (допустимо только после `%S` или `%s`).

**Пример несоответствия:**
```ini
# Лог: 2024-01-15T10:30:45.123Z
# Неправильно:
Time_Format %Y-%m-%dT%H:%M:%S%z
# Правильно:
Time_Format %Y-%m-%dT%H:%M:%S.%L%z
```

### Ошибка 4: Многострочное сообщение обрезается

**Симптом:** Стектрейс обрезан, символ `multiline_truncated: true` в записи.

**Причина:** Превышен лимит `multiline_buffer_limit` (по умолчанию 2MB).

**Решение:**
```yaml
service:
  multiline_buffer_limit: 4MB  # Увеличить лимит
```
Или уменьшить `Flush_Timeout` в определении многострочного парсера, чтобы запись сбрасывалась раньше.

### Ошибка 5: `Decode_Field_As` не декодирует поле

**Симптом:** Поле `log` остаётся как строка, JSON внутри не распарсен.

**Причины и решения:**
1.  Поле содержит невалидный JSON → проверить содержимое через `cat | jq`.
2.  Имя поля указано неверно → убедиться, что имя совпадает с ключом в записи.
3.  Поле уже было декодировано другим декодером → проверить порядок `Decode_Field_As` строк.

### Ошибка 6: Пропуск пустых значений (`Skip_Empty_Values`)

**Симптом:** Парсер пропускает ключи с пустыми значениями.

**Причина:** По умолчанию `Skip_Empty_Values` = `true`.

**Решение:** Добавить `Skip_Empty_Values false` в определение парсера, если нужно сохранять пустые ключи.

### Ошибка 7: High Cardinality из-за парсинга динамических полей

**Симптом:** Медленный поиск в хранилище логов, ошибки "Limit exceeded".

**Причина:** Динамические данные (UUID, IP, timestamp) попадают в метки (labels).

**Решение:** Использовать фильтр `modify` или процессор `content_modifier` для удаления/хеширования динамических полей перед отправкой в output.

## Best Practices и особенности

### Производительность

1.  **JSON предпочтительнее Regex:** Если приложение может логировать в JSON — используйте `Format json`. Это самый производительный вариант, так как не требует регулярных выражений.
2.  **Regex — последний выбор:** Regex-парсинг потребляет больше CPU и памяти. Используйте только когда нет альтернативы.
3.  **Input Parser > Filter Parser:** Парсинг на этапе входа эффективнее, чем через фильтр, так как данные проходят меньше этапов обработки.
4.  **Processors для v3.x+:** В YAML-конфигурации Processors работают в потоке плагина ввода, снижая нагрузку на основной цикл событий.

### Типы полей (Types)

Параметр `Types` позволяет приводить извлечённые поля к нужным типам сразу при парсинге, что критично для корректной фильтрации и агрегации:

```ini
[PARSER]
    Name    numeric_fields
    Format  regex
    Regex   ^(?<level>\w+) (?<pid>\d+) (?<cpu>\d+\.\d+) (?<message>.+)$
    Types   pid:integer cpu:float
```

Поддерживаемые типы: `string` (по умолчанию), `integer`, `bool`, `float`, `hex`.

### Парсинг в контейнерах Kubernetes

*   Используйте `multiline.parser` в плагине `tail` для склейки стектрейсов максимально близко к источнику.
*   Для динамического выбора парсера через аннотации подов убедитесь, что включены `K8S-Logging.Parser On` в фильтре `kubernetes`.
*   Фильтр `kubernetes` применяется **после** фильтра `parser`. Если нужно использовать метаданные Kubernetes при парсинге, разместите фильтр `parser` после `kubernetes`.

### Работа с форматами времени

*   `%L` (миллисекунды) допустим **только** после `%S` или `%s`.
*   Если в логах время локальное без указания часовой зоны, используйте `Time_Zone` (IANA-имя) или `Time_Offset` (+0300).
*   Для автоматического определения системной TZ: `Time_System_Timezone On` (работает из переменной `TZ`).

### Edge Cases и ограничения

*   **Многострочный парсер не подчиняется `buffer_max_size`:** Составленная запись может быть больше лимита входного буфера. Контролируйте через `multiline_buffer_limit`.
*   **`skip_long_lines` не работает с multiline:** Если нужен контроль длины — настраивайте `multiline_buffer_limit`.
*   **Время из multiline-тела:** Невозможно извлечь время из тела склеенного сообщения напрямую. Используйте фильтр `parser` с `Time_Key` после склейки.
*   **`decode_field` — одноразовое использование:** Декодер `decode_field` может быть применен только один раз к одному полю (в отличие от `decode_field_as`).
*   **Версионная совместимость:** Процессоры (Processors) доступны только с Fluent Bit 3.0+ в YAML-конфигурации. В Classic-формате они не поддерживаются.
