# Стек EFK в Kubernetes

## Определения

**Стек EFK** — это комплексное решение для сбора, хранения и визуализации логов в среде Kubernetes, состоящее из трех ключевых компонентов:

- **Elasticsearch**: поисковый и аналитический движок.
- **Fluent Bit**: сборщик и обработчик логов.
- **Kibana**: веб-интерфейс для визуализации и анализа данных.

> **Примечание:** Исторически аббревиатура EFK означала Elasticsearch, **Fluentd**, Kibana. В современных системах легковесный агент **Fluent Bit** часто заменяет Fluentd на уровне сбора логов, но стек по-прежнему называют EFK по традиции. Для сложных сценариев может использоваться [гибридная архитектура Fluent Bit → Fluentd](./fluentbit/fluent_comparison.md#сценарий-2-production-кластер-50-узлов-или-требования-compliance).

## Базовые концепции

- **[Elasticsearch](../../../ELK_Stack/Elasticsearch/elasticsearch_overview.md)**: Используется как централизованное хранилище для логов. Он индексирует поступающие данные, обеспечивая их быстрый поиск и анализ.
- **Fluent Bit**: Работает как легковесный агент, который развертывается на каждом узле кластера Kubernetes (обычно с помощью `DaemonSet`). Его задача — собирать логи из всех подов на узле, обогащать их метаданными (например, именами подов и неймспейсов) и отправлять в Elasticsearch. Подробнее о его архитектуре и конфигурации см. в разделе **[документации Fluent Bit](./fluentbit/fluent_comparison.md)**.
- **Kibana**: Предоставляет графический интерфейс для взаимодействия с данными в Elasticsearch. С помощью Kibana инженеры могут выполнять полнотекстовый поиск по логам, создавать дашборды для мониторинга состояния системы и анализировать события.

## Практический сценарий: Настройка стека EFK

### 1. Подготовка

Создадим отдельное пространство имен `logging` для всех компонентов стека.

```bash
kubectl create ns logging
```

Добавим необходимые Helm-репозитории.

```bash
helm repo add elastic https://helm.elastic.co
helm repo add fluent https://fluent.github.io/helm-charts
helm repo update
```

### 2. Установка Elasticsearch

Установим Elasticsearch с помощью Helm. Ключевые параметры:

- **`replicas`**: Количество реплик Elasticsearch. Для отказоустойчивости рекомендуется 3.
- **`esJavaOpts`**: Настройки JVM. Рекомендуется устанавливать `Xms` и `Xmx` в половину от лимита памяти пода.
- **`resources`**: Лимиты и запросы для подов. Elasticsearch требователен к памяти.
- **`volumeClaimTemplate.resources.requests.storage`**: Размер диска для хранения данных.

Установим Elasticsearch с помощью Helm, применив необходимые параметры:

```bash
helm upgrade --install elasticsearch elastic/elasticsearch \
  --namespace logging \
  --set replicas=3 \
  --set esJavaOpts="-Xmx1g -Xms1g" \
  --set resources.requests.cpu="100m" \
  --set resources.requests.memory="2Gi" \
  --set resources.limits.cpu="1000m" \
  --set resources.limits.memory="2Gi" \
  --set volumeClaimTemplate.resources.requests.storage="5Gi"
```

После установки проверьте статус подов:

```bash
kubectl get pods -n logging
```

### 3. Установка Fluent Bit

Установим Fluent Bit. Важно добавить `tolerations`, чтобы агент собирал логи со всех узлов, включая `master`-ноды.

```bash
helm upgrade --install fluent-bit fluent/fluent-bit \
  --namespace logging \
  --set tolerations[0].operator="Exists" \
  --set tolerations[0].effect="NoSchedule"
```

Проверьте, что поды Fluent Bit запустились на всех узлах кластера:

```bash
kubectl get pods -n logging -o wide
```

### 4. Установка Kibana

Установим Kibana и включим `Ingress` для доступа к веб-интерфейсу.

```bash
helm upgrade --install kibana elastic/kibana \
  --namespace logging \
  --set ingress.enabled=true \
  --set ingress.hosts[0].host="kibana.example.com" \
  --set ingress.hosts[0].paths[0].path="/"
```

> **Важно:** Замените `kibana.example.com` на ваш реальный домен.

### 5. Доступ и использование

После успешного запуска пода Kibana вы сможете получить доступ к веб-интерфейсу по адресу, указанному в `Ingress`.

### 6. Ключевые концепции отправки логов в Elasticsearch

При настройке **Fluent Bit** для отправки логов в Elasticsearch важно учитывать следующие аспекты, которые влияют на производительность, хранение и анализ логов.

#### 6.1. Аутентификация и права доступа

- Elasticsearch может быть настроен с аутентификацией. Fluent Bit должен использовать учетные данные пользователя, имеющего права на запись в целевые индексы.
- Минимальные привилегии для пользователя Fluent Bit в Elasticsearch: `create_index`, `manage` (для управления индексами) и `write` (для записи документов) на целевые индексы.

#### 6.2. Шаблоны индексов Elasticsearch

- **Индексы**: В Elasticsearch логи хранятся в индексах. Рекомендуется использовать ротацию индексов, чтобы избежать слишком больших индексов, которые трудно управлять. Fluent Bit можно настроить для записи в ежедневные индексы с помощью параметра `Logstash_Format On` в секции `[OUTPUT]`.
- **Рекомендации по ротации**:
  - **Ежедневные индексы (например, `my-cluster-YYYY.MM.DD`)**: Наиболее предпочтительный вариант. Каждый день создается новый индекс. Упрощает управление жизненным циклом данных (ILM), архивирование и удаление старых логов.
  - Ежемесячные (`my-cluster-YYYY.MM`) или ежегодные (`my-cluster-YYYY`) индексы могут стать слишком большими, что негативно скажется на производительности Elasticsearch и усложнит операции по реиндексации или восстановлению.
- **Kibana Index Pattern**: После создания индексов необходимо настроить [шаблон индексов в Kibana](./kibana_guide.md#1-создание-индекс-паттерна-для-логов-kubernetes) (например, `my-cluster-*`), чтобы Kibana могла агрегировать данные из всех подходящих индексов.

#### 6.3. Включение системных логов Kubernetes

- **Объем данных**: Сбор системных логов Kubernetes (`kubelet`, `container-runtime` и т.д.) может привести к большому объему данных.
- **Целесообразность**: Оцените, действительно ли вам нужны все системные логи в Elasticsearch. Для сбора логов системных служб можно использовать плагин `systemd` в `[INPUT]` секции Fluent Bit, настроив его на конкретные `unit`-ы. Это позволяет существенно снизить нагрузку на систему логирования.

#### 6.4. Парсинг JSON-логов

- **Автоматическое обогащение**: Если приложение выводит логи в формате JSON, фильтр `kubernetes` в Fluent Bit с опцией `Merge_Log On` может автоматически "поднять" поля из JSON-строки на верхний уровень. Это значительно облегчает фильтрацию и анализ логов в Kibana.
- **Ограничения**: Встроенные парсеры могут испытывать трудности с обработкой сложных или вложенных JSON-структур.
- **Решение**: Для сложных сценариев может потребоваться настройка кастомных парсеров. Подробнее см. в руководстве **[Fluent Bit: Парсинг логов](./fluentbit/parsing.md)**. Поды также могут динамически указывать нужный парсер через аннотации.

#### 6.5. Оптимизация Elasticsearch

- **Выделение ресурсов**: Elasticsearch крайне требователен к оперативной памяти. Рекомендуется выделять минимум 3-4 ГБ RAM на каждый экземпляр Elasticsearch.
- **Настройка JVM**: Параметры `Xms` и `Xmx` JVM должны быть установлены примерно в половину от выделенной памяти пода, чтобы избежать OutOfMemory ошибок.

## Дополнительная информация

- В production-средах рекомендуется выносить Elasticsearch за пределы кластера Kubernetes на выделенные серверы для обеспечения производительности и надежности. Для буферизации большого потока логов перед Elasticsearch можно использовать, например, Kafka.
- В данном руководстве параметры передаются через флаг `--set` для простоты. В реальных проектах рекомендуется использовать файлы `values.yaml` для управления конфигурацией.
- Для более детального разбора параметров `values.yaml` Fluent Bit обратитесь к документу **[Глубокое погружение в конфигурацию Fluent Bit](./fluentbit/fluentbit_configuration.md)**.
- Подробности о работе с логами в Kibana описаны в **[практическом руководстве](./kibana_guide.md)**.
- Для устранения неполадок обратитесь к руководству **[Устранение неполадок стека EFK](./efk_stack_troubleshooting.md)**.
