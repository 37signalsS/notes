# Стек EFK в Kubernetes

## Определения

**Стек EFK** — это комплексное решение для сбора, хранения и визуализации логов в среде Kubernetes, состоящее из трех ключевых компонентов:

- **Elasticsearch**: поисковый и аналитический движок.
- **Fluent Bit**: сборщик и обработчик логов.
- **Kibana**: веб-интерфейс для визуализации и анализа данных.

## Базовые концепции

- **[Elasticsearch](../../../ELK_Stack/Elasticsearch/elasticsearch_overview.md)**: Используется как централизованное хранилище для логов. Он индексирует поступающие данные, обеспечивая их быстрый поиск и анализ.
- **Fluent Bit**: Работает как легковесный агент, который развертывается на каждом узле кластера Kubernetes (обычно с помощью `DaemonSet`). Его задача — собирать логи из всех подов на узле, обогащать их метаданными (например, именами подов и неймспейсов) и отправлять в Elasticsearch.
- **Kibana**: Предоставляет графический интерфейс для взаимодействия с данными в Elasticsearch. С помощью Kibana инженеры могут выполнять полнотекстовый поиск по логам, создавать дашборды для мониторинга состояния системы и анализировать события.

## Практический сценарий: Настройка стека EFK

### 1. Подготовка

Создадим отдельное пространство имен `logging` для всех компонентов стека.

```bash
kubectl create ns logging
```

Добавим необходимые Helm-репозитории.

```bash
helm repo add elastic https://helm.elastic.co
helm repo add fluent https://fluent.github.io/helm-charts
helm repo update
```

### 2. Установка Elasticsearch

Установим Elasticsearch с помощью Helm. Ключевые параметры:

- **`replicas`**: Количество реплик Elasticsearch. Для отказоустойчивости рекомендуется 3.
- **`esJavaOpts`**: Настройки JVM. Рекомендуется устанавливать `Xms` и `Xmx` в половину от лимита памяти пода.
- **`resources`**: Лимиты и запросы для подов. Elasticsearch требователен к памяти.
- **`volumeClaimTemplate.resources.requests.storage`**: Размер диска для хранения данных.

Установим Elasticsearch с помощью Helm, применив необходимые параметры:

```bash
helm upgrade --install elasticsearch elastic/elasticsearch \
  --namespace logging \
  --set replicas=3 \
  --set esJavaOpts="-Xmx1g -Xms1g" \
  --set resources.requests.cpu="100m" \
  --set resources.requests.memory="2Gi" \
  --set resources.limits.cpu="1000m" \
  --set resources.limits.memory="2Gi" \
  --set volumeClaimTemplate.resources.requests.storage="5Gi"
```

После установки проверьте статус подов:

```bash
kubectl get pods -n logging
```

### 3. Установка Fluent Bit

Установим Fluent Bit. Важно добавить `tolerations`, чтобы агент собирал логи со всех узлов, включая `master`-ноды.

```bash
helm upgrade --install fluent-bit fluent/fluent-bit \
  --namespace logging \
  --set tolerations[0].operator="Exists" \
  --set tolerations[0].effect="NoSchedule"
```

Проверьте, что поды Fluent Bit запустились на всех узлах кластера:

```bash
kubectl get pods -n logging -o wide
```

### 4. Установка Kibana

Установим Kibana и включим `Ingress` для доступа к веб-интерфейсу.

```bash
helm upgrade --install kibana elastic/kibana \
  --namespace logging \
  --set ingress.enabled=true \
  --set ingress.hosts[0].host="kibana.example.com" \
  --set ingress.hosts[0].paths[0].path="/"
```

> **Важно:** Замените `kibana.example.com` на ваш реальный домен.

### 5. Доступ и использование

После успешного запуска пода Kibana вы сможете получить доступ к веб-интерфейсу по адресу, указанному в `Ingress`.

### 5. Доступ и использование

После успешного запуска пода Kibana вы сможете получить доступ к веб-интерфейсу по адресу, указанному в `Ingress`.

### 6. Расширенная конфигурация логирования в Elasticsearch (концепции)

При настройке Fluentd (через Rancher UI или вручную) для отправки логов в Elasticsearch важно учитывать следующие аспекты, которые влияют на производительность, хранение и анализ логов.

#### 6.1. Аутентификация и права доступа

*   Elasticsearch может быть настроен с аутентификацией. Fluentd должен использовать учетные данные пользователя, имеющего права на запись в целевые индексы.
*   Минимальные привилегии для пользователя Fluentd в Elasticsearch: `create_index`, `manage` (для управления индексами) и `write` (для записи документов) на целевые индексы.

#### 6.2. Шаблоны индексов Elasticsearch

*   **Индексы**: В Elasticsearch логи хранятся в индексах. Рекомендуется использовать ротацию индексов, чтобы избежать слишком больших индексов, которые трудно управлять.
*   **Рекомендации по ротации**:
    *   **Ежедневные индексы (например, `mycluster-YYYY.MM.DD`)**: Наиболее предпочтительный вариант. Каждый день создается новый индекс. Упрощает управление жизненным циклом данных (ILM), архивирование и удаление старых логов.
    *   Ежемесячные (`mycluster-YYYY.MM`) или ежегодные (`mycluster-YYYY`) индексы могут стать слишком большими, что негативно скажется на производительности Elasticsearch и усложнит операции по реиндексации или восстановлению.
*   **Kibana Index Pattern**: После создания индексов необходимо настроить [шаблон индексов в Kibana](../../MonitoringLogging/EFK/kibana_guide.md#1-создание-индекс-паттерна-для-логов-kubernetes) (например, `mycluster-*`), чтобы Kibana могла агрегировать данные из всех подходящих индексов.

#### 6.3. Включение системных логов Kubernetes (`Include System Log`)

*   **Объем данных**: Включение всех системных логов Kubernetes может привести к очень большому объему данных, особенно в крупных кластерах. Это требует значительных ресурсов для Elasticsearch (CPU, RAM, диск).
*   **Целесообразность**: Оцените, действительно ли вам нужны все системные логи в Elasticsearch для постоянного анализа. Возможно, некоторые логи (например, CNI-плагинов или DNS-серверов) требуются только для оперативной диагностики и не нужны в долгосрочной перспективе. Отключение этой опции позволяет существенно снизить нагрузку на систему логирования.

#### 6.4. Парсинг JSON-логов (`Enable JSON Parsing`)

*   **Автоматическое обогащение**: Если приложение выводит логи в формате JSON, включение этой опции позволяет Fluentd (или Fluent Bit) разобрать JSON-строку на отдельные поля. Это значительно облегчает фильтрацию и анализ логов в Kibana.
*   **Ограничения**: Встроенные парсеры могут испытывать трудности с обработкой сложных, вложенных или смешанных JSON-структур. В таких случаях логи могут остаться в виде одной неразобранной строки.
*   **Решение**: Для сложных сценариев может потребоваться ручная донастройка конфигурации Fluentd/Fluent Bit с использованием кастомных парсеров ([Fluent Bit: Парсинг логов](./fluentbit/parsing.md)), фильтров и регулярных выражений. В Rancher для этого можно использовать опцию "Edit As File" для прямого редактирования конфигурации Fluentd.

#### 6.5. Оптимизация Elasticsearch

*   **Выделение ресурсов**: Elasticsearch крайне требователен к оперативной памяти. Рекомендуется выделять минимум 3-4 ГБ RAM на каждый экземпляр Elasticsearch. Недостаток памяти часто приводит к нестабильной работе и ошибкам.
*   **Настройка JVM**: Параметры `Xms` и `Xmx` JVM должны быть установлены примерно в половину от выделенной памяти пода, чтобы избежать OutOfMemory ошибок.

## Дополнительная информация

- В production-средах рекомендуется выносить Elasticsearch за пределы кластера Kubernetes на выделенные серверы для обеспечения производительности и надежности. Для буферизации большого потока логов перед Elasticsearch можно использовать, например, Kafka.
- В данном руководстве параметры передаются через флаг `--set` для простоты. В реальных проектах рекомендуется использовать файлы `values.yaml` для управления конфигурацией.
- Для более детального разбора параметров `values.yaml` Fluent Bit обратитесь к документу **[Глубокое погружение в конфигурацию Fluent Bit](./fluentbit/fluentbit_configuration.md)**.
- Подробности о работе с логами в Kibana описаны в **[практическом руководстве](./kibana_guide.md)**.
