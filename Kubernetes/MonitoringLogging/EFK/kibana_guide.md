# Kibana: Практическое руководство в Kubernetes

> **Примечание:** Данный файл описывает практическое использование Kibana в среде Kubernetes. Общий обзор инструмента и его базовых концепций приведен в документе [Kibana: Обзор](../../../ELK_Stack/Kibana/kibana_overview.md).

## Определения

**Discover (Обнаружение)** — основной инструмент Kibana для интерактивного исследования, поиска и фильтрации необработанных записей (логов). В версиях 8.x включает режим **Document Explorer** с поддержкой мгновенной статистики по полям.

**Data View (ранее Index Pattern)** — логический шаблон, определяющий набор индексов Elasticsearch для поиска. В Kubernetes обычно охватывает индексы агентов (например, `logs-kubernetes-*`).

**KQL (Kibana Query Language)** — основной язык запросов для простой фильтрации прямо в строке поиска.

**ES|QL (Elasticsearch Query Language)** — (новое в 8.x) мощный язык запросов с поддержкой конвейеров (pipes), позволяющий фильтровать, преобразовывать и агрегировать логи Kubernetes в одном окне.

**Runtime Fields (Поля времени выполнения)** — вычисляемые поля («схема при чтении»), которые позволяют извлекать данные из логов (например, парсить регулярными выражениями) без их повторной индексации.

## Основные концепции

В среде Kubernetes Kibana служит «окном» в состояние кластера через анализ метаданных. Ключевые поля, добавляемые агентами (Fluent Bit, Elastic Agent):
* `kubernetes.namespace_name` — пространство имен.
* `kubernetes.pod_name` — имя пода.
* `kubernetes.container_name` — имя контейнера.
* `kubernetes.node.name` — узел (node), на котором запущен под.

В Kibana 8.x акцент смещен в сторону **схемы при чтении (Schema-on-read)**: если формат лога изменился или поле не было распарсено агентом, вы можете адаптировать поиск с помощью Runtime Fields, не меняя конфигурацию Fluent Bit или Ingest-конвейеров.

## Практические сценарии

### Создание Data View для логов Kubernetes

Для визуализации данных, поступающих из кластера:

1. Перейдите в **Stack Management** → **Data Views**.
2. Нажмите **Create data view**.
3. Введите шаблон. Для стандартного EFK это часто `kube-logs-*` или `fluentbit-*`.
4. Выберите `@timestamp` в качестве основного поля времени.
5. (Опционально) В разделе **Runtime fields** можно сразу добавить логику парсинга для извлечения кастомных полей из текста сообщения.

### Поиск и фильтрация логов Kubernetes

#### Использование KQL
Стандартный поиск для быстрой диагностики:
* **Логи конкретного приложения:** `kubernetes.labels.app: "my-service"`
* **Поиск ошибок в Namespace:** `kubernetes.namespace_name: "prod" and log.level: "error"`
* **Исключение «шума» (например, health-checks):** `not url.path: "/healthz"`

#### Использование ES|QL (Kibana 8.x+)
Позволяет выполнять сложные цепочки действий прямо в интерфейсе **Discover**:
```esql
FROM logs-kubernetes-*
| WHERE kubernetes.namespace_name == "production"
| WHERE log.level == "ERROR"
| STATS count(*) BY kubernetes.pod_name
| SORT count(*) DESC
```
*Этот запрос покажет поды с наибольшим количеством ошибок в production.*

### Работа с Runtime Fields (извлечение данных на лету)

Если приложение пишет логи в текстовом формате, а вам нужно отфильтровать их по `request_id`, который не был распарсен:

1. В настройках **Data View** нажмите **Add field**.
2. Выберите тип (например, `keyword`).
3. Введите скрипт (Painless) для извлечения данных:
   ```painless
   def m = /request_id=([^\s,]+)/.matcher(doc['message'].value);
   if (m.find()) {
     emit(m.group(1));
   }
   ```
4. Теперь поле `request_id` доступно в **Discover** для фильтрации, группировки и создания дашбордов.

### Визуальный анализ и статистика (Discover 2.0)

В современных версиях Kibana можно быстро оценить распределение ошибок:
1. В **Discover** выберите поле `log.level` (или созданное Runtime-поле).
2. Нажмите на имя поля в боковой панели → откроется панель статистики.
3. Вы увидите круговую диаграмму или гистограмму распределения значений прямо в интерфейсе поиска, что позволяет мгновенно заметить аномалии.

### Настройка табличного вида

Для удобства мониторинга потока логов:
1. В боковой панели выберите поля: `kubernetes.namespace_name`, `kubernetes.pod_name`, `message`.
2. Используйте кнопку **Field statistics** для быстрой проверки, нет ли всплесков логов в конкретном поде или контейнере.

## Решение проблем: неразобранные JSON-логи

**Симптом:** Поле `message` (или `log`) содержит JSON-строку, но ее поля не вынесены в отдельные атрибуты (невозможен поиск по полям).

**Решения:**
1. **На уровне агента:** Проверьте конфигурацию Fluent Bit (`Merge_Log On`) или наличие аннотаций у пода (`fluentbit.io/parser: json`). См. [Парсинг логов во Fluent Bit](./fluentbit/parsing.md).
2. **На уровне Kibana (Quick Fix):** Создайте Runtime Field, которое будет парсить JSON на лету для нужного подмножества логов.
3. **На уровне Elasticsearch:** Используйте Ingest Pipeline с процессором `json`. Это предпочтительный метод для высоконагруженных систем.
