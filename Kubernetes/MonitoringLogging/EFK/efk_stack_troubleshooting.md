> **Примечание:** Данный файл является специализированным руководством по диагностике в среде Kubernetes. Общие концепции и базовое решение проблем поиска описаны в документе [Elasticsearch: Обзор](../../../ELK_Stack/Elasticsearch/elasticsearch_overview.md).

## Определения

**`CrashLoopBackOff`** — статус пода в Kubernetes, означающий циклическую перезагрузку контейнера из-за ошибок конфигурации, нехватки ресурсов или сбоев приложения.

**`mapper_parsing_exception`** — ошибка в Elasticsearch, возникающая при несоответствии типа данных поля в новом документе ранее определенному маппингу индекса.

**Статусы здоровья кластера (Cluster Health)**:

* **Green**: все шарды (основные и реплики) распределены и доступны.
* **Yellow**: все основные шарды доступны, но некоторые реплики не распределены (кластер уязвим к сбоям узлов).
* **Red**: часть основных шардов недоступна (потеря данных или частичная неработоспособность).

**ILM (Index Lifecycle Management)** — автоматизированная система управления жизненным циклом индексов (ротация, перемещение между типами хранилищ, удаление).

## Основные концепции диагностики

Процесс поиска неисправностей в Kubernetes должен быть последовательным:

1. **Инспекция ресурсов**: проверка статуса подов.

    ```bash
    kubectl get pods -n logging
    # → Ожидаемый статус: Running
    ```

2. **Анализ логов**: изучение вывода конкретного компонента.

    ```bash
    kubectl logs <pod-name> -n logging
    # Проверка предыдущего запуска при перезагрузках:
    kubectl logs <pod-name> -n logging --previous
    ```

3. **События кластера**: поиск проблем на уровне планировщика или инфраструктуры.

    ```bash
    kubectl describe pod <pod-name> -n logging
    ```

4. **Сетевая связность**: проверка доступности API (Application Programming Interface).

    ```bash
    kubectl exec <pod-name> -n logging -- curl -v http://elasticsearch-master:9200
    ```

## Практические сценарии

### Сценарий 1: Проблемы сбора логов (Fluent Bit)

**Симптом: данные не отображаются в Kibana.**

* **Проверка путей**: Убедитесь, что `Path` в секции `[INPUT]` указывает на `/var/log/containers/*.log`.
* **Права доступа**: Проверьте, что ServiceAccount агента имеет права на чтение файлов хоста.
* **Backpressure**: Если в логах Fluent Bit видны сообщения о задержках, увеличьте `Mem_Buf_Limit`.
* **Конфликты маппинга**: Если Elasticsearch возвращает `400 Bad Request`, проверьте наличие точек в именах полей. Решение: `Replace_Dots On` в секции `[OUTPUT]`.

### Сценарий 2: Деградация кластера Elasticsearch

**Симптом: медленный поиск, статус кластера Red/Yellow.**

* **Нехватка памяти**: Проверьте логи на наличие `java.lang.OutOfMemoryError`.
  * *Решение:* Увеличьте лимиты RAM (Random Access Memory) и параметры JVM (Java Virtual Machine) `Xmx`/`Xms`.
* **Проблемы с диском**: При заполнении диска более чем на 90% Elasticsearch переходит в режим `read-only`.
  * *Решение:* Расширьте тома (PVC — Persistent Volume Claim) или настройте политику ILM для удаления старых данных.
* **Шарды не распределены**:

    ```bash
    curl "http://elasticsearch:9200/_cluster/allocation/explain?pretty"
    ```

### Сценарий 3: Проблемы визуализации (Kibana)

**Симптом: ошибка "Kibana server is not ready yet".**

* **Ожидание Elasticsearch**: Kibana может долго запускаться, пока проверяет статус индексов. Проверьте статус подключения в логах.
* **Index Pattern**: Убедитесь, что созданный Data View соответствует реальным индексам (например, `logstash-*`).
* **Версионность**: Проверьте совместимость версий. Kibana не должна быть старше версии Elasticsearch в кластере.
