# Устранение неполадок стека EFK в Kubernetes

> **Примечание:** Данный файл является частью документации по [стеку EFK в Kubernetes](./efk_stack_setup_guide.md). Общие концепции Elasticsearch описаны в [Elasticsearch: Обзор](../../../ELK_Stack/Elasticsearch/elasticsearch_overview.md).

## Определения

- **`CrashLoopBackOff`**: Статус пода в Kubernetes, означающий, что контейнер постоянно запускается и сразу же падает. Причина обычно кроется в ошибках приложения, нехватке ресурсов или неверной конфигурации.
- **`mapper_parsing_exception`**: Ошибка в Elasticsearch, возникающая, когда тип данных поля в новом документе не соответствует ранее определенному типу в маппинге индекса (например, отправка `string` в поле, которое уже определено как `integer`).
- **`red` / `yellow` статус кластера**: Состояния здоровья Elasticsearch. `yellow` означает, что все основные данные доступны, но некоторые реплики шардов не распределены. `red` означает, что данные некоторых основных шардов недоступны, и кластер не полностью функционален.
- **ILM (Index Lifecycle Management)**: Механизм Elasticsearch для автоматизации управления индексами на протяжении их жизненного цикла (например, ротация, перевод в "холодное" хранилище, удаление).

## Базовые концепции диагностики

1. **Проверка статуса подов**
    Убедитесь, что все поды (Elasticsearch, Fluent Bit, Kibana) находятся в состоянии `Running`.

    ```bash
    kubectl get pods -n logging
    ```

    Ошибки `CrashLoopBackOff` или `ImagePullBackOff` указывают на критические проблемы конфигурации или доступа к образу.

2. **Анализ логов подов**
    Логи — основной источник информации о проблемах.

    ```bash
    kubectl logs <pod-name> -n logging
    kubectl logs <pod-name> -n logging --previous # Для упавших подов
    ```

    Ищите сообщения об ошибках (`error`), предупреждения (`warning`) и проблемы с подключением.

3. **Изучение событий пода**
    События показывают проблемы на уровне Kubernetes, такие как сбои при монтировании томов или планировании.

    ```bash
    kubectl describe pod <pod-name> -n logging
    ```

    Анализируйте секцию `Events` в выводе команды.

4. **Проверка сетевой связности**
    Убедитесь, что компоненты могут общаться друг с другом по сети (Fluent Bit → Elasticsearch, Kibana → Elasticsearch).

    ```bash
    # Пример проверки из пода Fluent Bit
    kubectl exec <fluent-bit-pod-name> -n logging -- curl -v http://elasticsearch-master.logging.svc.cluster.local:9200
    ```

## Практические сценарии: решение проблем

### 1. Проблемы с Fluent Bit

**Симптом: Логи не поступают в Kibana.**

- **Fluent Bit не собирает логи:**
  - **Пути к логам**: Проверьте `Path` в конфигурации `[INPUT]`, он должен указывать на `/var/log/containers/*.log`.
  - **Права доступа**: Убедитесь, что у `DaemonSet` Fluent Bit есть доступ к директориям логов на узле.
  - **Длинные строки**: Если логи обрезаются, увеличьте `Mem_Buf_Limit` или включите `Skip_Long_Lines On`.

- **Fluent Bit не отправляет логи в Elasticsearch:**
  - **Сетевая связность**: Используйте `curl` из пода Fluent Bit, чтобы проверить доступность Elasticsearch.
  - **Конфигурация `[OUTPUT]`**: Проверьте `Host`, `Port` и `Match` в секции `[OUTPUT]`. `Match` должен соответствовать тегу `[INPUT]` (например, `kube.*`).
  - **Аутентификация**: Если Elasticsearch требует аутентификации, убедитесь, что Fluent Bit использует корректные учетные данные.

- **Проблемы с парсингом:**
  - **JSON-логи**: Если ваше приложение пишет логи в JSON, используйте `Merge_Log On` и `Keep_Log Off` в фильтре `kubernetes`, чтобы избежать вложенности.
  - **Ошибки маппинга**: Если в логах Elasticsearch появляются ошибки `mapper_parsing_exception` из-за точек в именах полей, включите `Replace_Dots On` в секции `[OUTPUT]` Fluent Bit.

### 2. Проблемы с Elasticsearch

**Симптом: Elasticsearch недоступен, кластер в "красном" или "желтом" статусе.**

- **Состояние кластера**:
  - Проверьте статус подов Elasticsearch.
  - Изучите логи подов на наличие `OutOfMemoryError` или проблем с диском.
  - Выполните запрос к API для проверки здоровья кластера:

      ```bash
      curl "http://elasticsearch-master.logging.svc.cluster.local:9200/_cluster/health?pretty"
      ```

      Статус `red` или `yellow` указывает на проблемы с шардами и репликами.

- **Проблемы с индексацией**:
  - **Конфликты маппинга**: Часто возникают, когда одно и то же поле отправляется с разными типами данных. Проверяйте логи Elasticsearch на `mapper_parsing_exception`.
  - **Производительность**: Если Elasticsearch не справляется с потоком логов, увеличьте ресурсы (CPU/память) или оптимизируйте конфигурацию Fluent Bit (например, увеличьте `Flush` интервал).

### 3. Проблемы с Kibana

**Симптом: Kibana не загружается или не отображает логи.**

- **Kibana не может подключиться к Elasticsearch**:
  - Проверьте логи пода Kibana на ошибки подключения.
  - Убедитесь, что переменная окружения `ELASTICSEARCH_HOSTS` указывает на правильный сервис Elasticsearch.
  - Проверьте совместимость версий Kibana и Elasticsearch.

- **Kibana не отображает данные**:
  - **Индекс-паттерны**: Убедитесь, что в Kibana создан корректный индекс-паттерн (например, `kube-*`) и что он соответствует индексам в Elasticsearch.
  - **Временной диапазон**: Проверьте, что в Kibana выбран правильный диапазон времени для отображения логов.
  - **Фильтры**: Убедитесь, что нет активных фильтров (KQL), которые скрывают данные.

## Дополнительная информация

- **Ресурсы**: Регулярно отслеживайте потребление CPU и памяти всеми компонентами стека EFK, чтобы вовремя выявлять узкие места.
- **Масштабирование Elasticsearch**: Для больших объемов данных масштабируйте кластер Elasticsearch, добавляя узлы данных.
- **Оптимизация Fluent Bit**: Настройте `Flush` интервал и `Mem_Buf_Limit` для баланса между задержкой доставки логов и потреблением ресурсов — [Конфигурация Fluent Bit](./fluentbit/fluentbit_configuration.md).
- **Управление жизненным циклом индексов (ILM)**: Настройте политики ILM в Elasticsearch для автоматического управления индексами (перемещение в "теплое"/"холодное" хранилище, удаление), чтобы контролировать использование диска.
- **Чистота данных**: Используйте `Logstash_Prefix` и `Replace_Dots On` в Fluent Bit для предотвращения конфликтов маппинга и упрощения управления индексами.
- **Надежность доставки**: Механизмы буферизации описаны в [Буферизация и маршрутизация Fluent Bit](./fluentbit/buffering_routing.md).
- **Настройка стека EFK**: Перед устранением неполадок убедитесь, что конфигурация соответствует рекомендациям из [руководства по установке](./efk_stack_setup_guide.md).
