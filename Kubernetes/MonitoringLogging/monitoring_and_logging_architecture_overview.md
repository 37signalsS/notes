# Мониторинг и Логирование в Kubernetes: Обзор Архитектуры

## Определения

> **Основная статья: [Observability (Наблюдаемость)](../../../Concepts/Observability_and_Monitoring/observability_overview.md)**

**Мониторинг** — это процесс сбора, обработки и анализа данных (метрик) для получения представления о производительности и состоянии системы. В контексте Kubernetes это относится ко всему, от бизнес-показателей до утилизации CPU на отдельных нодах.

**Типы метрик:**
1.  **Бизнес-метрики (Business-level):** Ключевые показатели, отражающие ценность для бизнеса (например, количество заказов в час). Являются наиболее приоритетными.
2.  **Метрики приложений (Application-level):** Показатели производительности сервисов (например, количество запросов, утилизация памяти, размер кэша).
3.  **Метрики доступности (Availability):** Данные, показывающие доступность приложений (например, результаты health-check'ов).
4.  **Системные метрики (System-level):** Низкоуровневые показатели производительности серверов или виртуальных машин (CPU, память, I/O).

**Логирование** — это процесс записи событий, происходящих в системе. В отличие от метрик (которые являются числовыми), логи представляют собой текстовую информацию о конкретных событиях.

**Структурированное логирование** — это практика записи логов в формате с четкой структурой (например, JSON), а не в виде простого текста. Это критически важно для эффективного парсинга, поиска и анализа логов в централизованных системах.

**Пример структурированного лога:**
```json
{
  "timestamp": "2025-05-20T10:30:45Z",
  "level": "error",
  "service": "api-server",
  "trace_id": "abc123",
  "message": "Failed to connect to database"
}
```

## Основные концепции

#### Слои мониторинга в Kubernetes

Комплексный мониторинг охватывает несколько уровней, каждый из которых важен для разных команд (бизнес, разработчики, DevOps/SRE).
-   **Бизнес-уровень:** Поведение пользователей и ключевые бизнес-показатели.
-   **Уровень приложений:** Состояние и производительность сервисов.
-   **Уровень кластера:** Состояние компонентов самого Kubernetes (etcd, API-сервер, CoreDNS и т.д.).
-   **Уровень нод:** Состояние "железа" или виртуальных машин (CPU, память, диски, сеть).

#### Методы анализа метрик

-   **Метод USE (Utilization, Saturation, Errors):** Идеально подходит для мониторинга инфраструктурных ресурсов.
    -   **Utilization (Утилизация):** Насколько ресурс занят (например, % использования памяти).
    -   **Saturation (Насыщение):** Насколько ресурс перегружен, наличие очереди (например, **Load Average** для CPU, см. [планировщик и LA](../../Linux/Core/processes/scheduling.md#load-average-la)).
    -   **Errors (Ошибки):** Количество ошибок, связанных с ресурсом.
-   **Метод RED (Rate, Errors, Duration):** Лучше подходит для мониторинга сервисов и приложений.
    -   **Rate (Частота):** Количество запросов в секунду.
    -   **Errors (Ошибки):** Количество запросов, завершившихся ошибкой.
    -   **Duration (Длительность):** Время обработки запроса.

#### Четыре золотых сигнала Google SRE

Это четыре ключевых метрики, на которые рекомендуется обращать внимание в первую очередь при мониторинге сервисов:
1.  **Latency (Задержка):** Время ответа на запрос.
2.  **Traffic (Трафик):** Нагрузка на сервис, измеряемая в запросах в секунду.
3.  **Errors (Ошибки):** Частота ошибок.
4.  **Saturation (Насыщение):** Насколько сервис "загружен", как близок он к пределу производительности.

#### Подсистема алертинга

Алертинг — это процесс уведомления инженеров о проблемах, требующих их внимания. Без эффективного алертинга мониторинг становится пассивным и малополезным.

#### Механизм логирования в Kubernetes

Стандартный и рекомендуемый подход заключается в том, что приложения пишут свои логи в стандартные потоки вывода `stdout` и `stderr`. Далее среда выполнения контейнеров (например, Docker) перехватывает эти потоки, сохраняет их в файлы на диске хоста и управляет их ротацией.

#### Расположение логов на хосте

-   **Docker:** `/var/lib/docker/containers/<container_id>/<container_id>-json.log`
-   **Kubernetes (симлинки):** Для удобства Kubernetes создает символические ссылки в `/var/log/pods/` и `/var/log/containers/`, что позволяет легко находить логи по имени пода и неймспейса.

#### Логирование системных компонентов

-   **Компоненты в подах** (`kube-apiserver`, `etcd`, `CoreDNS`) логируются как обычные приложения.
-   **Компоненты на хосте** (`kubelet`, `containerd`/`docker`) пишут логи в системный журнал, доступный через `journalctl` (`journalctl -u kubelet`).

#### Ограничения стандартного подхода

Централизованная система логирования необходима по нескольким причинам:
1.  **Недолговечность логов:** При удалении пода его логи теряются.
2.  **Распределенность:** Логи одного приложения распределены по разным машинам.
3.  **Отсутствие метаданных:** Стандартные логи не содержат информации о том, из какого пода или неймспейса они пришли.
4.  **Сложность анализа:** Простой текст сложно фильтровать и агрегировать.

## Практические сценарии

#### Инструменты для каждого слоя мониторинга
-   **Бизнес-метрики:**
    -   **Postgres-экспортер:** Для выполнения SQL-запросов к репликам баз данных.
    -   **Скрипт-экспортер:** Для выполнения кастомных скриптов и проверки сквозных сценариев.
-   **Метрики приложений:**
    -   **Клиентские библиотеки Prometheus:** Для инструментирования кода приложений.
-   **Метрики кластера и нод:**
    -   **Prometheus, Node Exporter, kube-state-metrics:** Стандартный де-факто стек для сбора этих метрик.

#### Ключевые компоненты кластера для мониторинга
-   **etcd:** Доступность кластера, частота смены лидера.
-   **Control Plane:** [kube-apiserver](./KubeAPIServer/kube_apiserver_monitoring.md), `kube-controller-manager`, `kube-scheduler`, `kubelet`, `kube-proxy`.
-   **Среда выполнения контейнеров:** Работоспособность Docker/containerd демонов.
-   **DNS (CoreDNS):** Количество запросов, ошибок, кэш-промахов.
-   **Ingress Controller:** Доступность подов, потребление ресурсов, внутренние метрики.
-   **kube-state-metrics:** Состояние объектов Kubernetes (деплойменты, поды).

#### Правила эффективного алертинга
1.  **Действенность:** Уведомлять только о том, что требует немедленного вмешательства.
2.  **Результативность:** Каждый алерт должен приводить к действию (исправление, тюнинг, изменение порога).
3.  **Совместная работа:** Настраивать мониторинг и алертинг совместно с разработчиками.
4.  **Анализ:** Формировать периодические отчеты для выявления трендов и предотвращения будущих алертов.

#### Анти-паттерны мониторинга
1.  **Ручная настройка:** Вместо этого следует использовать автоматическое обнаружение сервисов (service discovery).
2.  **Алертинг только по ресурсам (CPU/RAM):** Приводит к ложным срабатываниям. Алерты должны быть привязаны к симптомам (задержки, ошибки), а не только к причинам.
3.  **Изолированный специалист по мониторингу:** Настройка требует глубокого знания и инфраструктуры, и приложений.
4.  **Один инструмент для всего:** Не пытайтесь использовать систему мониторинга для логирования или трейсинга.

#### Архитектура централизованной системы логирования

Общепринятая архитектура, рекомендованная в документации Kubernetes, основана на использовании **логирующего агента (logging agent)**, запущенного как `DaemonSet` на каждой ноде. Этот агент:
1.  Читает лог-файлы контейнеров из `/var/log/pods/` или `/var/log/containers/`.
2.  Собирает логи системных компонентов из `journald`.
3.  Обращается к Kubernetes API для обогащения логов метаданными (имя пода, неймспейс, лейблы).
4.  Отправляет обработанные и обогащенные логи в центральное хранилище.

#### Обзор систем централизованного логирования

-   **EFK Stack (Elasticsearch, Fluent Bit, Kibana):**
    -   **Fluent Bit** выступает в роли легковесного и производительного логирующего агента. Он пришел на смену более тяжеловесному Fluentd в большинстве Kubernetes-инсталляций.
    -   **Elasticsearch** — мощное хранилище для поиска и анализа.
    -   **Kibana** — UI для визуализации.
    -   Это надежный, но ресурсоемкий и сложный в поддержке стек. Детали установки см. в [руководстве по настройке стека EFK](./EFK/efk_stack_setup_guide.md).

-   **Loki Stack (Promtail, Loki, Grafana):**
    -   **Promtail** — агент, специально созданный для Loki.
    -   **Loki** — система хранения логов от Grafana. В отличие от Elasticsearch, Loki индексирует только метаданные (лейблы), а не весь текст лога, что делает его значительно более легковесным и дешевым в эксплуатации.
    -   **Grafana** используется для визуализации, что позволяет объединить просмотр метрик и логов в одном инструменте.
    -   Loki отлично подходит для небольших и средних инсталляций, но может уступать Elasticsearch в производительности на очень больших объемах данных. Детали установки см. в [руководстве по настройке стека Loki](../../Loki/loki_stack_setup_guide.md).
