# Kubecost: Управление затратами и FinOps в Kubernetes

## Определения

**Kubecost** — инструмент для мониторинга и оптимизации затрат в Kubernetes, обеспечивающий гранулярную видимость расходов в реальном времени на уровне пространств имен, деплойментов, подов и меток (labels).

**OpenCost** — проект с открытым исходным кодом (CNCF sandbox), являющийся ядром (engine) для Kubecost. Он стандартизирует модель аллокации затрат в Kubernetes.

**FinOps (Cloud Financial Management)** — операционная модель и культурная практика, которая позволяет организациям получать максимальную выгоду от облака за счет объединения технологических, финансовых и бизнес-команд.

**Cost Allocation (Аллокация затрат)** — процесс распределения общих расходов кластера (узлы, диски, балансировщики) между конкретными потребителями (командами, проектами, приложениями).

**Right-sizing (Оптимизация размеров)** — процесс подбора оптимальных `requests` и `limits` ресурсов или типов узлов под реальное потребление для снижения финансовых потерь без деградации производительности.

## Основные концепции

### Архитектура и интеграция

Kubecost (и OpenCost) работает как набор сервисов внутри кластера и интегрируется с ключевыми компонентами инфраструктуры:
- **Cost Model Engine**: Основной движок, собирающий данные о ресурсах и сопоставляющий их с ценами.
- **Prometheus**: Используется как основное хранилище метрик потребления ресурсов (cAdvisor, kube-state-metrics). Долгосрочное хранение (Long-term retention) реализуется через интеграцию с Thanos или Mimir.
- **Cloud Billing APIs (AWS, Azure, GCP)**: Интеграция с биллингом облачных провайдеров (CUR, Cost and Usage Reports) для получения актуальных цен, учитывая корпоративные скидки, Reserved Instances (RI) и Savings Plans.
- **Интеграция с Spot-инстансами**: Kubecost автоматически распознает использование Spot-узлов (прерываемых инстансов) и применяет к ним соответствующие сниженные тарифы, что позволяет точно оценивать экономию.

### Зачем нужен Kubecost в 2026 году?

В современных гибридных средах, при борьбе с **cluster sprawl** (разрастанием кластеров) и использовании ресурсоемких GenAI-нагрузок (GPU), стандартных счетов облачных провайдеров недостаточно. Kubecost решает следующие задачи:
1. **Видимость в реальном времени**: Данные о расходах с точностью до минуты внутри кластера (счета провайдера не детализируют расходы по подам).
2. **Эффективность GPU**: Отслеживает использование дорогостоящих ускорителей, помогая выявить недоутилизированные GPU-инстансы или простой во время обучения/инференса.
3. **Showback и Chargeback**: Механизмы финансовой прозрачности. *Showback* — демонстрация расходов командам. *Chargeback* — фактическое распределение внутренних счетов между подразделениями.
4. **Governance и бюджетирование**: Установка лимитов на расходы (Budgets) для Namespace/команд с автоматическим алертингом.
5. **Обоснование консолидации**: Сравнение стоимости владения множеством мелких кластеров с одним крупным мультитенантным кластером для оптимизации TCO (Total Cost of Ownership).

## Роль в мультитенантных средах

Kubecost — основной инструмент для реализации финансовой изоляции и прозрачности в общих кластерах.

### 1. Атрибуция затрат по меткам (Labels)
Биллинг в Kubernetes строится на основе иерархии меток. Kubecost позволяет группировать расходы по:
*   `namespace`: Базовая единица аллокации.
*   `label:team`: Атрибуция конкретной инженерной команде.
*   `label:cost-centre`: Привязка расходов к конкретному бюджетному центру или проекту.
*   `label:environment`: Разделение затрат на Prod, Staging и Dev.

### 2. Детекция «шумных соседей» по стоимости
Помогает выявить тенантов, чьи рабочие нагрузки приводят к непропорциональному росту общих расходов (например, из-за отсутствия лимитов или утечек ресурсов, вызывающих агрессивное масштабирование узлов).

## Практические сценарии

### 1. Мониторинг затрат на GenAI (GPU) и AI-нагрузки
Поскольку GPU-инстансы являются самыми дорогими в кластере, их мониторинг критичен.
- **Детекция простоя (Idle GPU)**: Kubecost подсвечивает узлы, где GPU зарезервированы, но не используются для вычислений (нет активных процессов CUDA).
- **Сравнение цен и инстансов**: Помогает выбрать наиболее выгодные регионы или типы инстансов для обучения LLM (например, миграция с устаревших P3 на G5 или использование Spot-узлов для stateless задач обучения). Это частый кейс на собеседованиях: использование Kubecost позволяет соотнести стоимость инференса одной модели с её бизнес-доходом.

### 2. Оптимизация ресурсов (Right-sizing)
Kubecost анализирует исторические данные метрик Prometheus и выдает конкретные рекомендации:
- **Abandoned Workloads (Заброшенные нагрузки)**: Обнаружение подов, которые работают и потребляют ресурсы, но не принимают сетевой трафик.
- **Over-provisioned Requests (Избыточные запросы)**: Рекомендации по уменьшению `requests`, если поды исторически используют менее 20% от запрошенного CPU/RAM.

### 3. Настройка цен для Bare-Metal (On-Premise)
Если кластер находится в собственном ЦОД, интеграции с Cloud API нет. В этом случае настраиваются статические цены через файл конфигурации (Custom Pricing).
```yaml
# values-custom-pricing.yaml
kubecostProductConfigs:
  customPricesEnabled: true
  CPU: "0.031" # Цена за 1 vCPU в час
  RAM: "0.004" # Цена за 1 GB RAM в час
  storage: "0.0001" # Цена за 1 GB хранилища
```

### 4. Установка через Helm с настройкой Retention
Рекомендуется устанавливать Kubecost, отключая встроенный Prometheus, если в кластере уже есть Kube-Prometheus-Stack, чтобы избежать дублирования метрик.

```bash
helm repo add kubecost https://kubecost.github.io/cost-analyzer/
helm repo update

# Установка с интеграцией существующего Prometheus
helm install kubecost kubecost/cost-analyzer \
  --namespace kubecost --create-namespace \
  --set global.prometheus.fqdn="http://prometheus-operated.monitoring.svc:9090" \
  --set global.prometheus.enabled=false \
  --set prometheusRule.enabled=true \
  --set kubecostToken="YOUR_TOKEN"
```

### 5. Интеграция с Karpenter
В связке с **[Karpenter](../Autoscaling/Karpenter/overview.md)**, Kubecost помогает измерить экономический эффект от перехода на «group-less» автомасштабирование. Karpenter динамически заказывает оптимальные узлы (включая Spot), а Kubecost валидирует, насколько упала стоимость 1 часа работы кластера (`cluster run rate`) после внедрения.
