# Хранение данных: PV, PVC и StorageClass

## Определения

* **`PersistentVolume` (PV) — Ресурс хранилища**
  * **PersistentVolume (PV)** — это такой же ресурс кластера, как и узел, но предоставляющий не вычислительные ресурсы, а дисковые тома (например, NFS, RBD, CephFS). В рамках PV впоследствии можно выделять подам место для хранения данных.
  * Это "кусок" хранилища в кластере, который был предоставлен администратором или динамически создан. PV имеет свой жизненный цикл, независимый от любого пода, который его использует.
  * PV содержит детали реализации хранилища: тип, размер, путь, ID тома и т.д.

* **`PersistentVolumeClaim` (PVC) — Запрос на хранилище**
  * **PersistenceVolumeClaim (PVC)** — это запрос к PV на выделение места под хранение данных. По аналогии с подами, которые запрашивают ресурсы узла (CPU, память), PVC запрашивает у PV определенный объем хранилища и тип доступа.
  * Когда PVC связывается с PV, этот PV становится "занятым" (`Bound`) и не может быть использован другим PVC.

* **`StorageClass` (SC) — "Фабрика" хранилищ**
  * **StorageClass** — это механизм, который описывает "классы" хранилищ (например, "быстрый-ssd", "медленный-hdd", "резервные-копии"). Ключевой компонент `StorageClass` — это **`provisioner`**.
  * **Provisioner** — это плагин (драйвер), который умеет взаимодействовать с конкретной системой хранения (например, AWS EBS, GCE PD, Ceph, NFS) для **автоматического создания томов**. Современный стандарт для реализации таких плагинов — это **[Container Storage Interface (CSI)](./CSI/csi_overview.md)**, который позволяет сторонним разработчикам легко интегрировать свои системы хранения с Kubernetes.
  * Таким образом, `StorageClass` выступает в роли "фабрики", которая создает PV по запросу.

## Базовые концепции

#### Проблема: Прямое управление томами

Объекты PV, PVC и SC были созданы для решения проблем, возникающих при прямом монтировании томов в манифестах подов. Изначально в Kubernetes можно было определять тома непосредственно в манифесте пода (например, `awsElasticBlockStore`, `gcePersistentDisk`). Этот подход имеет серьезные недостатки:

1. **Ручное создание томов:** Администратору приходилось вручную создавать диски в системе хранения данных перед тем, как их можно было использовать в кластере.
2. **Жесткая связь с инфраструктурой:** Параметры доступа к тому (например, `volumeID`) жестко прописывались в манифесте приложения. Это делало приложение непереносимым между разными облаками или СХД.
3. **Сложность миграции:** При переезде из одного облака в другое (например, с AWS на GCP) требовалось найти и изменить манифесты всех приложений, использующих хранилище.

#### Решение: Абстрагирование хранилища через PV, PVC и SC

Для решения этих проблем была введена трехуровневая система абстракций, которая разделяет зоны ответственности между администратором кластера и разработчиком.

* **Разработчик (пользователь):** Описывает **требования** своего приложения к хранилищу. "Мне нужно 10 ГБ быстрого хранилища с эксклюзивным доступом".
* **Администратор кластера:** Настраивает **способы удовлетворения** этих требований. "Быстрое хранилище — это SSD-диски в нашем облаке, медленное — HDD в локальном ЦОД".

#### Процесс выделения хранилища

##### Динамическое выделение (Dynamic Provisioning) — Рекомендуемый способ

Это полностью автоматический подход, который является стандартом для большинства кластеров. Здесь плагин сам формирует PV при наличии запроса на него. Администратор создает `StorageClass`, где описывается хранилище, подключенное к кластеру, и с помощью плагина в ответ на запрос PVC Kubernetes создаст PV нужного размера и предоставит его для пода.

1. **Администратор** создает один или несколько `StorageClass`, указывая в них `provisioner` (например, `ebs.csi.aws.com`).
2. **Разработчик** создает `PersistentVolumeClaim` (PVC), в котором запрашивает нужный объем и указывает `storageClassName`.
3. **Kubernetes** видит PVC и обращается к `provisioner`-у, указанному в `StorageClass`.
4. **Provisioner** подключается к API системы хранения (например, AWS), создает там физический диск нужного размера, получает его ID.
5. После создания диска `provisioner` создает в кластере Kubernetes объект `PersistentVolume` (PV) с информацией о новом диске.
6. Kubernetes **связывает (binds)** этот новый PV с PVC разработчика.
7. Теперь под может использовать этот PVC для монтирования тома.

**Результат:** Разработчику не нужно ничего знать о нижележащей инфраструктуре хранения. При переезде в другое облако администратору достаточно создать новый `StorageClass` с другим `provisioner`-ом, а разработчику — поменять одну строку (`storageClassName`) в своем PVC.

##### Статическое выделение (Static Provisioning)

Этот "ручной" способ используется реже, в основном для интеграции с уже существующими системами хранения. Администратор заранее создает набор `PersistentVolume`. Например, если есть диск на 500 ГБ, администратор "нарезает" его с помощью PV на блоки по 10, 20, 50 ГБ. Когда поду нужно место, PVC делает заявку, и Kubernetes подбирает подходящий PV.

1. **Администратор** заранее подготавливает хранилище (NFS, iSCSI, облачный диск).
2. **Администратор** вручную создает YAML-манифест объекта `PersistentVolume`, описывая это хранилище.
3. **Разработчик** создает PVC, который по своим параметрам (размер, access modes) подходит под созданный PV.
4. Kubernetes связывает PVC с подходящим PV.

> **В чём разница, если коротко:**
>
> * **Статически:** вы создаете PV на 10 ГБ. PVC запрашивает 1 ГБ. Kubernetes ищет подходящие PV, видит PV на 10 ГБ и присоединяет его. В итоге 9 ГБ диска теряется для других запросов.
> * **Динамически:** вы создаете `StorageClass`. PVC запрашивает 1 ГБ. С помощью плагина для этого PVC автоматически создается PV нужного размера (1 ГБ).

#### Логика связывания PV и PVC (Binding Logic)

Когда создается PVC, Kubernetes ищет для него подходящий PV (при статическом выделении). Процесс выбора выглядит так:

1. **Фильтрация по `StorageClassName`**: Рассматриваются только те PV, у которых `storageClassName` совпадает с запрошенным в PVC. Если в PVC класс не указан, используются PV без класса.
2. **Фильтрация по `accessModes`**: Отбрасываются PV, которые не поддерживают режим доступа из PVC (например, PVC хочет `RWX`, а PV предоставляет только `RWO`).
3. **Фильтрация по размеру**: Отбрасываются все PV, емкость которых **меньше**, чем запрошено в PVC.
4. **Выбор наилучшего кандидата (Best Fit)**: Из оставшихся PV Kubernetes выбирает **наименьший подходящий том**. Например, если PVC запрашивает 20 ГБ, а доступны PV на 30 ГБ и 40 ГБ, будет выбран PV на 30 ГБ для экономии ресурсов.

#### Политика возврата (`reclaimPolicy`)

Политика `reclaimPolicy` указывается в `PersistentVolume` и определяет, что произойдет с нижележащим томом (диском в облаке) после того, как `PersistentVolume` будет освобожден (т.е. удален PVC, который его использовал).

* **`Retain` (Сохранить) — Рекомендуется для важных данных.**
  * **Что происходит:** После удаления PVC объект PV переходит в статус `Released`, но сам PV и физический том на СХД **сохраняются**.
  * **Действия администратора:** Данные остаются нетронутыми. Администратор должен вручную очистить том и либо удалить его, либо сделать доступным для другого PVC (удалив и пересоздав объект PV).
* **`Delete` (Удалить) — По умолчанию для динамических provisioner'ов.**
  * **Что происходит:** После удаления PVC **удаляются и объект PV, и физический том** в системе хранения.
  * **Использование:** Удобно для временных данных или в средах разработки/тестирования, где не страшно потерять данные. **Опасно для production!**
* **`Recycle` (Переиспользовать) — Устарело (Deprecated).**
  * **Что происходит:** Выполнялась базовая очистка (`rm -rf /thevolume/*`) тома. Этот метод больше не рекомендуется из-за проблем с безопасностью и неэффективности.

#### Режимы доступа (`accessModes`)

Основные типы доступа:

* `ReadWriteOnce` (RWO): Том может быть смонтирован для чтения и записи **одним узлом**.
* `ReadOnlyMany` (ROX): Том может быть смонтирован только для чтения **многими узлами**.
* `ReadWriteMany` (RWX): Том может быть смонтирован для чтения и записи **многими узлами**.
* `ReadWriteOncePod` (RWOP): Том может быть смонтирован для чтения и записи **одним подом** (эксклюзивный доступ для пода).

## Практические сценарии

#### Пример: Динамическое выделение хранилища

В этом примере под запрашивает хранилище через PVC, а `StorageClass` с `provisioner`'ом от облачного провайдера автоматически создает необходимый диск.

```yaml
# 1. StorageClass (обычно уже предоставлен облачным провайдером)
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: standard-ssd
provisioner: ebs.csi.aws.com # Пример для AWS (CSI-драйвер)
parameters:
  type: gp2
reclaimPolicy: Retain
volumeBindingMode: WaitForFirstConsumer

---
# 2. PersistentVolumeClaim (PVC)
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: my-app-pvc
spec:
  accessModes:
    - ReadWriteOnce # Эксклюзивный доступ на чтение/запись
  storageClassName: standard-ssd # Запрос к конкретному классу хранилища
  resources:
    requests:
      storage: 10Gi # Запрос на 10 ГиБ

---
# 3. Pod, использующий PVC
apiVersion: v1
kind: Pod
metadata:
  name: my-app-pod
spec:
  containers:
    - name: my-app
      image: nginx
      ports:
        - containerPort: 80
      volumeMounts:
        # Монтируем том, предоставленный PVC, в контейнер
        - name: my-storage
          mountPath: /usr/share/nginx/html
  volumes:
    - name: my-storage
      # Указываем, что источником тома является наш PVC
      persistentVolumeClaim:
        claimName: my-app-pvc
```
