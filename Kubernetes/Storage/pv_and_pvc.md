# Persistent Volumes и Persistent Volume Claims

## Определения

**`PersistentVolume` (PV)** — ресурс кластера, представляющий собой абстракцию над физическим или сетевым хранилищем (NFS, iSCSI, облачные диски AWS EBS/GCP PD, Ceph RBD/FS). Имеет жизненный цикл, независимый от жизненного цикла подов, использующих этот объем. Содержит технические параметры реализации: тип СХД, объем, пути монтирования и ID томов.

**`PersistentVolumeClaim` (PVC)** — запрос пользователя или приложения на выделение дискового пространства. Если под потребляет ресурсы узла (CPU/RAM), то PVC потребляет ресурсы PV. PVC определяет необходимый размер, режим доступа (один или несколько узлов) и класс хранилища. После успешного связывания с PV, PVC переходит в статус `Bound`.

**`StorageClass` (SC)** — механизм, позволяющий администраторам описывать "профили" предлагаемого хранения. SC определяет, какой провижинер (плагин) будет использоваться для автоматического создания томов и с какими параметрами (например, тип диска, тип файловой системы).

**`Container Storage Interface` (CSI)** — стандарт, позволяющий разработчикам СХД писать плагины один раз и использовать их в различных системах оркестрации (Kubernetes, Mesos и др.). Большинство современных функций (снимки, расширение) реализуются через CSI-драйверы.

Подробнее о StorageClass: [StorageClass](./storageclass.md). Расширенные возможности CSI (снимки, клонирование, топология): [CSI Advanced](./CSI/csi_advanced.md).

## Основные концепции

### Режим тома (volumeMode)

Параметр `volumeMode` определяет, как том будет представлен внутри пода:

| Режим | Описание | Применение |
| :--- | :--- | :--- |
| **`Filesystem`** | (По умолчанию). Том монтируется как файловая система в указанный путь. | Стандартные приложения, хранение файлов. |
| **`Block`** | Том предоставляется как необработанное блочное устройство (raw block device). | Базы данных, высокопроизводительные системы, требующие прямого доступа к диску. |

### Роли и ответственность

Система PV/PVC обеспечивает разделение обязанностей между администратором инфраструктуры и разработчиком приложений.

| Роль | Задача | Объекты |
|---|---|---|
| **Администратор** | Настройка физических СХД, установка CSI-драйверов, создание пулов и StorageClass. | PV, StorageClass |
| **Разработчик** | Определение потребностей приложения (объем, режим доступа) без привязки к реализации СХД. | PVC, Pod |

**Принцип абстракции:** Разработчику не нужно знать, используется ли в фоне NetApp, Dell EMC или локальные диски узла. Он оперирует только параметрами PVC.

### Режимы выделения хранилища

#### Статическое выделение (Static Provisioning)

Администратор вручную создает набор PV в кластере, ссылаясь на заранее созданные тома в СХД.

**Процесс:**

```
┌─────────────────┐
│ Администратор   │
│                 │
│ 1. Создаёт PV   │──────┐
│    (манифест)   │      │
└─────────────────┘      │
                         ▼
                  ┌─────────────────┐
                  │  Kubernetes     │
                  │  Control Plane  │
                  │                 │
                  │ 2. PV доступен  │
                  │    в кластере   │
                  └─────────────────┘
                         │
                         │ (ожидает PVC)
                         ▼
                  ┌─────────────────┐
┌─────────────────┐│  Контроллер   │
│ Разработчик     ││  Persistent   │
│                 ││  Volume       │
│ 3. Создаёт PVC  │─────► Bind     │
│    (манифест)   ││               │
└─────────────────┘│ 4. Связывание │
                   │    PV + PVC   │
                   └─────────────────┘
                            │
                            │ (Bound)
                            ▼
                   ┌─────────────────┐
                   │  Pod ссылается  │
                   │  на PVC         │
                   │                 │
                   │ 5. Том          │
                   │    монтируется  │
                   └─────────────────┘
```

**Недостатки статического метода:**
1. Необходимость ручного управления дисками на стороне СХД.
2. Неэффективное использование ресурсов (PV может быть 100 ГБ, а PVC запросит 10 ГБ — остаток пропадет).
3. Плохая масштабируемость при большом количестве заявок.

#### Динамическое выделение (Dynamic Provisioning) — рекомендуемый метод

Автоматическое создание физических томов и объектов PV при появлении PVC.

**Процесс:**

```
┌─────────────────────────┐
│ Администратор           │
│                         │
│ 1. Создаёт StorageClass │──────┐
│    (provisioner +       │      │
│     параметры)          │      │
└─────────────────────────┘      │
                                 │
                                 │ (StorageClass готов)
                                 ▼
                        ┌─────────────────┐
                        │  Kubernetes     │
                        │  Control Plane  │
                        └─────────────────┘
                                 │
                                 │ (ожидает PVC)
                                 ▼
                        ┌─────────────────┐
┌───────────────────────┤  Контроллер     │
│ Разработчик           │  StorageClass   │
│                       │                 │
│ 2. Создаёт PVC        │ 3. Обнаруживает │
│    storageClassName:  │    PVC          │
│    "gold-ssd"         │                 │
└───────────────────────┤ 4. Вызывает     │
                        │    provisioner  │
                        │                 │
                        │ 5. Создаёт      │
                        │    физический   │
                        │    том (СХД API)│
                        │                 │
                        │ 6. Создаёт PV   │
                        │    (манифест)   │
                        └─────────────────┘
                                 │
                                 │ (PV создан)
                                 ▼
                        ┌─────────────────┐
                        │  Автоматическое │
                        │  связывание     │
                        │  PV + PVC       │
                        │  (Bound)        │
                        └─────────────────┘
```

**Преимущества:**
- Полная автоматизация жизненного цикла хранения.
- Выделение точно запрошенного объема.
- Скрытие специфичных параметров СХД (WWN, IQN, Path) от разработчика.

### Запуск баз данных в Kubernetes (StatefulSet)

Запуск нагруженных БД в контейнерах имеет свои особенности:

- **Производительность:** Любая сетевая СХД (Ceph, GlusterFS) добавляет задержки (latency) из-за сетевого стека. Для высоконагруженных систем (OLTP) рекомендуется использовать локальные диски через `Local Persistent Volumes` или NVMe-over-Fabric.
- **Отказоустойчивость:** Kubernetes не управляет репликацией данных внутри БД. Рекомендуется использовать **Операторы** (CloudNativePG для Postgres, VictoriaMetrics Operator), которые автоматизируют бэкапы и переключение (failover) при падении ноды. Подробнее о комплексном подходе к бэкапам см. в **[Стратегиях резервного копирования Kubernetes](../Operations/backup-strategies.md)**.
- **Рекомендация:** Для критически важных Production БД часто выгоднее оставить базу вне K8s (Bare-metal/Managed DB), подключая приложения из кластера по сети.

### Роль контроллеров в подсистеме хранения

1. **PV Controller:** Занимается связыванием (binding) PVC с подходящими PV и следит за их жизненным циклом.
2. **CSI Sidecars (External Provisioner, Attacher):** Вспомогательные контейнеры, которые слушают события API Kubernetes и вызывают соответствующие методы CSI-драйвера (CreateVolume, ControllerPublishVolume).
3. **Kubelet (Volume Manager):** Выполняет фактическое монтирование устройства (`mount`) и создание файловой системы внутри узла, где запущен под.

### Режимы доступа (accessModes)

| Режим | Описание | Типичные СХД |
|---|---|---|
| **`ReadWriteOnce` (RWO)** | Том доступен на чтение/запись только одному узлу одновременно. | AWS EBS, vSphere Volume, iSCSI |
| **`ReadOnlyMany` (ROX)** | Том доступен только на чтение одновременно многим узлам. | NFS, CephFS |
| **`ReadWriteMany` (RWX)** | Том доступен на чтение/запись одновременно многим узлам. | NFS, CephFS, Longhorn |
| **`ReadWriteOncePod` (RWOP)** | Эксклюзивный доступ только одному поду (K8s 1.22+, GA 1.29). Предотвращает коррупцию данных при переезде пода, гарантируя, что старый инстанс полностью освободил том перед подключением нового. | CSI-драйверы с поддержкой |

> **Внимание:** Режим доступа определяется возможностями СХД, а не Kubernetes. Попытка использовать RWO том на двух узлах приведет к `Multi-Attach error`.

### Жизненный цикл и состояния PV

| Состояние | Описание |
|---|---|
| **`Available`** | Свободен, ждет привязки к PVC. |
| **`Bound`** | Успешно закреплен за конкретным PVC. |
| **`Released`** | PVC удален, но данные еще на месте. Требуется вмешательство. |
| **`Failed`** | Произошла ошибка при попытке автоматической очистки или удаления. |

**Важный нюанс состояния `Released`:**
Если `reclaimPolicy` установлен в `Retain`, после удаления PVC том переходит в `Released`. Даже если вы создадите новый PVC с такими же параметрами, он **не подцепит** этот том автоматически. Администратор должен вручную отредактировать PV, удалив поле `claimRef` из спецификации, чтобы вернуть его в `Available`.

### Политика возврата (reclaimPolicy)

| Политика | Действие после удаления PVC | Сфера применения |
|---|---|---|
| **`Retain`** | PV остается в статусе `Released`. Данные на СХД сохраняются. | Production, критичные данные. |
| **`Delete`** | Объект PV удаляется из K8s, вызывается команда на удаление тома в СХД. | Динамическое выделение, Dev/Test. |
| **`Recycle`** | **Устарело**. Выполнял `rm -rf /vol/*` и возвращал в `Available`. | Не использовать в современных кластерах. |

**Предупреждение по безопасности:** При использовании `Delete` на некоторых СХД данные могут быть не затерты физически, а просто помечены как свободные. Для полного уничтожения данных используйте механизмы шифрования или специфичные настройки СХД.

## Практические сценарии

### Динамическое расширение тома (Volume Expansion)

Большинство современных CSI-драйверов поддерживают расширение "на лету" (Online Expansion).
1. Убедитесь, что в `StorageClass` установлено `allowVolumeExpansion: true`.
2. Отредактируйте PVC, увеличив размер:
   ```bash
   kubectl patch pvc <pvc-name> -p '{"spec":{"resources":{"requests":{"storage":"20Gi"}}}}'
   ```
3. Kubernetes расширит том в СХД, а затем файловую систему (если под запущен).

### Работа с Volume Snapshots

CSI позволяет делать снимки данных через Kubernetes API.
1. Создается объект `VolumeSnapshotClass`.
2. Создается `VolumeSnapshot`, ссылающийся на PVC.
3. Новый PVC может быть создан из этого снимка (источник `dataSource`).
