# Container Storage Interface (CSI)

### Определения

**Container Storage Interface (CSI)** — это открытый стандарт, который определяет универсальный API для взаимодействия систем оркестрации контейнеров (таких как Kubernetes) с системами хранения данных (СХД).

Основная цель CSI — стандартизировать подключение систем хранения к контейнерам, что позволяет разработчикам легко интегрировать различные решения для управления данными.

**Ключевые задачи, решаемые CSI:**

- Динамическое выделение и девыделение томов хранения.
- Монтирование и отмонтирование томов к подам.
- Создание снапшотов и клонирование томов.
- Расширение томов.

### Основные концепции

#### Проблемы до-CSI (In-Tree плагины)

До появления CSI вся логика для работы с различными СХД (например, AWS EBS, GCE PD, Ceph) была встроена непосредственно в код Kubernetes. Это создавало ряд проблем:

- **Медленное развитие:** Добавление поддержки новой СХД требовало внесения изменений в основную кодовую базу Kubernetes и было привязано к его циклам релиза.
- **Раздувание кодовой базы:** Код Kubernetes содержал большое количество специфичных драйверов для разных вендоров.
- **Сложность поддержки:** Исправление ошибок или добавление функционала в одном драйвере требовало обновления всего кластера.

CSI решил эти проблемы, полностью отделив логику работы с хранилищами от Kubernetes, перейдя к модели **Out-of-Tree** плагинов.

#### Архитектура CSI-драйвера

CSI-драйвер для конкретной СХД обычно состоит из двух основных компонентов, которые развертываются в кластере как отдельные поды:

1. **Controller Plugin**
    - **Описание:** Централизованный компонент, который обычно работает как `Deployment` или `StatefulSet` с одной репликой. Он не зависит от конкретных узлов кластера и отвечает за высокоуровневые операции по управлению томами.
    - **Функции:**
        - Создание и удаление томов (`CreateVolume`, `DeleteVolume`).
        - Подключение и отключение томов к узлам (`ControllerPublishVolume`, `ControllerUnpublishVolume`).
        - Создание снапшотов и восстановление из них.
        - Изменение размера томов.
    - **Взаимодействие:** Напрямую с API системы хранения данных.

2. **Node Plugin**
    - **Описание:** Этот компонент работает на **каждом узле** кластера, обычно в виде `DaemonSet`. Он отвечает за низкоуровневые операции, специфичные для конкретного узла.
    - **Функции:**
        - Монтирование (`NodeStageVolume`, `NodePublishVolume`) и размонтирование (`NodeUnstageVolume`, `NodeUnpublishVolume`) тома в файловую систему пода.
        - Форматирование файловой системы (при необходимости).
    - **Взаимодействие:** `kubelet` на каждом узле взаимодействует с Node Plugin через локальный сокет для выполнения этих операций.

#### Преимущества использования CSI

Переход на CSI-драйверы предоставляет значительно более широкие возможности по сравнению со старыми встроенными плагинами:

- **Динамическое создание томов:** Автоматическое создание PV по запросу через `StorageClass`.
- **Создание снапшотов (Snapshots):** Возможность создавать "снимки" состояния `PersistentVolume` для резервного копирования или клонирования.
- **Клонирование томов:** Создание новых томов, которые являются точной копией существующих.
- **Изменение размера томов (Resize):** Увеличение размера `PersistentVolume` "на лету", без остановки приложения (если СХД это поддерживает).
- **Сбор метрик:** Предоставление метрик для мониторинга производительности и использования хранилища.
- **Поддержка топологии (Topology Aware):** Позволяет планировщику Kubernetes принимать решения о размещении подов с учетом физического расположения данных (например, разместить под в той же зоне доступности, где находится его диск, для минимизации задержек).
- **Поддержка различных режимов доступа:** Включая блочные устройства (`Block Storage`) и файловые системы (`File Storage`), а также режимы `RWO`, `ROX`, `RWX`.

### Практические сценарии

#### Пример: Ceph CSI

В качестве примера можно рассмотреть распределенную систему хранения данных [Ceph](https://ceph.io/en/). Драйвер **Ceph CSI** предоставляет доступ к двум типам хранилищ, закрывая разные потребности:

1. **RBD (RADOS Block Device)**
    - **Тип:** Блочное устройство.
    - **Режим доступа:** `ReadWriteOnce` (RWO).
    - **Аналогия:** Виртуальный жесткий диск, который монопольно используется одним подом.
    - **Применение:** Базы данных, Stateful-приложения.
    - **См. также:** [Установка и настройка драйвера Ceph CSI для RBD](../Ceph/ceph_csi_rbd_driver_setup.md).

2. **CephFS (Ceph File System)**
    - **Тип:** Распределенная файловая система, совместимая с POSIX.
    - **Режим доступа:** `ReadWriteMany` (RWX).
    - **Аналогия:** Общая сетевая папка, доступная для чтения и записи нескольким подам одновременно.
    - **Применение:** Общие данные для веб-серверов, CMS, аналитические задачи. Отличная альтернатива NFS.
    - **См. также:** [Установка и настройка драйвера CSI для CephFS](../Ceph/ceph_csi_cephfs_driver_setup.md).

#### Пример: Secrets Store CSI Driver

Этот драйвер используется не для хранения данных, а для безопасного управления секретами.

- **Задача:** Монтировать секреты из внешних хранилищ (например, HashiCorp Vault, AWS Secrets Manager, Azure Key Vault) напрямую в файловую систему пода, вместо того чтобы хранить их в `etcd` как объекты `Secret`.
- **Преимущества:**
  - **Централизованное управление:** Секреты хранятся в одном надежном месте.
  - **Автоматическая ротация:** Драйвер может автоматически обновлять смонтированные секреты.
  - **Повышенная безопасность:** Секреты не хранятся в `etcd` в base64.
- **См. также:** [Secrets Store CSI Driver в Kubernetes](../../Base/secret.md#secrets-store-csi-driver).
