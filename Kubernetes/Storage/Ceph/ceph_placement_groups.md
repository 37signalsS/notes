# Расчет количества Placement Group (PG) в Ceph

## Определения

**Placement Group (PG)** — логический контейнер для объектов Ceph, распределяемый по OSD. PG обеспечивают равномерное распределение данных и упрощают ребалансировку.

**OSD** (Object Storage Daemon) — демон хранения, управляющий физическим диском.

## Основные концепции

### Зачем нужны PG

PG решают задачу масштабирования:

- Без PG: каждый объект требует отслеживания местоположения
- С PG: отслеживается местоположение PG, объекты внутри PG распределяются хэшем

### Баланс между количеством PG и производительностью

| Мало PG | Много PG |
|---------|----------|
| ❌ Неравномерное распределение | ❌ Высокое потребление RAM |
| ❌ Медленная ребалансировка | ❌ Больше метаданных |
| ✅ Меньше метаданных | ✅ Равномерное распределение |
| ✅ Меньше RAM | ✅ Быстрая ребалансировка |

### Целевое количество PG на OSD

| Сценарий | PG на OSD | Примечание |
|----------|-----------|------------|
| Минимум | 50 | Допустимо для маленьких кластеров |
| **Рекомендуется** | **100-300** | Оптимальный баланс |
| Максимум | 500 | Требует много RAM |

**Эмпирическое правило**: 1 ГБ RAM на 1 ТБ дискового пространства на OSD.

## Практические сценарии

### Формула расчета общего количества PG

```
Total PGs = (OSD_count × Target_PG_per_OSD) / replication_factor
```

Где:

- `OSD_count` — общее количество OSD в кластере
- `Target_PG_per_OSD` — целевое значение (рекомендуется 100)
- `replication_factor` — фактор репликации (`size`, обычно 3)

### Пример расчета

**Дано:**

- 3 узла × 3 OSD = 9 OSD
- Репликация: `size=3`
- Целевое значение: 100 PG на OSD

**Расчет:**

```
Total PGs = (9 × 100) / 3 = 300 PG
```

### Распределение PG по пулам

#### Проблема равномерного распределения

При 3 пулах и 300 общих PG:

- Каждый пул получает 100 PG
- Но если пулы содержат разный объем данных, PG будут разного размера
- Большие PG медленнее ребалансируются

#### Рекомендуемое пропорциональное распределение

Распределяйте PG пропорционально **ожидаемому объему данных**:

| Пул | Ожидаемый объем | Доля | PG |
|-----|-----------------|------|-----|
| `rbd` | 500 ГБ | 50% | 150 |
| `cephfs_data` | 400 ГБ | 40% | 120 |
| `cephfs_metadata` | 100 ГБ | 10% | 30 |
| **Итого** | **1 ТБ** | **100%** | **300** |

### Использование степеней двойки

Ceph оптимизирован для работы с PG, количество которых — степень двойки:

| Значение | Степень | Рекомендация |
|----------|---------|--------------|
| 32 | 2⁵ | Маленькие пулы (< 100 ГБ) |
| 64 | 2⁶ | Средние пулы (100 ГБ - 1 ТБ) |
| 128 | 2⁷ | Большие пулы (1-10 ТБ) |
| 256 | 2⁸ | Очень большие пулы (> 10 ТБ) |
| 512 | 2⁹ | Огромные пулы (> 100 ТБ) |

**Пример настройки:**

```bash
# Создание пула с оптимальным количеством PG
ceph osd pool create mypool 128 128

# Изменение количества PG
ceph osd pool set mypool pg_num 256
ceph osd pool set mypool pgp_num 256
```

> **Важно**: `pgp_num` всегда должен быть равен `pg_num`.

### Динамическое изменение PG

#### Увеличение PG

```bash
# Увеличение с 64 до 128
ceph osd pool set mypool pg_num 128
ceph osd pool set mypool pgp_num 128
```

Процесс:

1. Ceph делит каждую PG пополам
2. Половина данных остается, половина перемещается
3. Запускается ребалансировка

> **Предупреждение**: Операция вызывает нагрузку на кластер. Выполняйте в maintenance window.

#### Уменьшение PG

Поддерживается в новых версиях Ceph (Reef 18.x+):

```bash
ceph osd pool set mypool pg_num 64
```

> **Осторожно**: Уменьшение возможно только если данные помещаются в меньшее количество PG.

### Мониторинг PG

```bash
# Статус PG
ceph pg stat

# Детализация по пулу
ceph pg dump --pools <pool_name>

# PG в неоптимальном состоянии
ceph pg dump_stale
ceph pg dump_undersized
ceph pg dump_incomplete

# Детали по конкретной PG
ceph pg <pg_id> query
```

#### Интерпретация статусов PG

| Статус | Описание | Действие |
|--------|----------|----------|
| `active+clean` | Норма | — |
| `active+recovering` | Идет восстановление | Мониторить |
| `active+degraded` | Не все реплики доступны | Проверить OSD |
| `active+undersized` | Меньше реплик чем нужно | Проверить OSD |
| `active+backfilling` | Заполнение новых OSD | Норма при расширении |
| `down` | Критическая ошибка | Немедленное вмешательство |

### Влияние на RAM

Примерная формула:

```
RAM_per_OSD (MB) = PG_per_OSD × 1 MB
```

Для 100 PG на OSD требуется ~100 МБ RAM только на метаданные PG.
