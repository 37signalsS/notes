# Расчет количества Placement Group (PG) в Ceph

Документ охватывает теорию, расчет и управление Placement Groups — критически важным компонентом архитектуры Ceph, определяющим равномерность распределения данных, производительность и отказоустойчивость. Является первичным источником по PG-тематике для DevOps/SRE/sysadmin.

---

## Определения

### Базовые компоненты

**Placement Group (PG)** — логический контейнер для объектов Ceph, распределяемый по OSD через алгоритм CRUSH. PG обеспечивают уровень абстракции между объектами и физическими дисками, гарантируя равномерное распределение данных, упрощая ребалансировку и минимизируя объем метаданных, отслеживаемых мониторами (MON). Каждый объект принадлежит ровно одной PG; PG может содержать миллионы объектов.

**OSD (Object Storage Daemon)** — демон хранения, управляющий физическим блочным устройством, отвечающий за репликацию/восстановление данных, scrubs (проверку целостности) и взаимодействие с клиентами для операций ввода-вывода. Каждый OSD хранит одну или несколько PG.

**Placement (Размещение)** — функция CRUSH, определяющая, на каких OSD будет храниться PG. Клиент вычисляет местоположение детерминированно: `object_name → PG → набор OSD`. Это исключает необходимость централизованного справочника.

### Параметры PG

**pg_num** — количество PG в пуле. Определяет, на сколько частей делится пул для распределения данных. Степень двойки обеспечивает максимально равномерное распределение.

**pgp_num (Placement Groups for Placement)** — количество PG, используемых для размещения (placement). В современных версиях (v18+) `pgp_num` синхронизируется с `pg_num` автоматически. Ручная настройка `pgp_num` отдельно от `pg_num` больше не требуется.

**mon_target_pg_per_osd** — целевое количество PG на один OSD. Параметр глобальной конфигурации, используемый `pg_autoscaler` для автоматического расчета. По умолчанию: 100. Для кластеров >50 OSD рекомендуется 200.

### Компоненты инфраструктуры PG

**CRUSH Rule (Правило CRUSH)** — набор правил, определяющих, как PG размещаются по failure domains (host, rack, datacenter). Определяет, будут ли реплики разнесены по разным хостам или стойкам. Для пулов CephFS автоматически создаются правила `cephfs_metadata` и `cephfs_data`.

**Scrub (Скрабинг)** — фоновый процесс проверки целостности данных в PG. Сравнивает checksum'ы объектов между репликами. Deep scrub additionally проверяет содержимое объектов (byte-level). Во время scrub возможен рост задержки для клиентов из-за нагрузки на диск.

**PG Autoscaling** — модуль Ceph Manager (`ceph-mgr`), который автоматически подбирает количество PG на основе фактической утилизации пула или заданных целевых параметров. В 2026 году (версии **Squid**, **Tentacle**, **Umbrella**) является основным и рекомендуемым методом управления.

## Основные концепции

### Зачем нужны PG

PG решают задачу масштабирования и эффективного распределения данных:

- **Абстракция**: Без PG кластеру пришлось бы отслеживать миллиарды объектов. Вместо этого он отслеживает несколько тысяч PG, что критично для производительности CPU и RAM мониторов.
- **Детерминизм (CRUSH)**: Алгоритм CRUSH вычисляет, в какую PG попадает объект (через хэширование имени объекта), а затем — на каких OSD эта PG должна храниться. Это исключает необходимость в централизованном справочнике объектов.
- **Математика CRUSH**: Использование степеней двойки (`pg_num`) обеспечивает максимально равномерное распределение объектов по PG. При значениях, отличных от степени двойки, "остаток" от деления хэш-диапазона приводит к тому, что некоторые PG получают в 2 раза больше данных, чем другие.
- **Ребалансировка**: При добавлении/удалении OSD или изменении `pg_num` данные перемещаются на уровне PG (не отдельных объектов), что эффективнее и проще для отслеживания.

### Процесс согласования (Peering)

**Peering** — это процесс согласования состояния PG между всеми OSD, которые хранят её реплики.

- **Цель**: Убедиться, что все реплики согласны с историей операций и текущими версиями объектов.
- **Триггеры**: Перезагрузка OSD, изменение карты кластера (OSD down/up), изменение `pg_num`, добавление/удаление OSD.
- **Статус**: Во время пиринга PG находится в статусе `peering` и временно недоступна для ввода-вывода (если нет других активных реплик).
- **Длительность**: Зависит от количества PG на OSD и скорости диска. При thousands PG на OSD peering может занимать минуты.
- **Оптимизация**: Увеличение `pg_num` снижает количество PG на OSD и ускоряет peering, но увеличивает overhead метаданных.

### Баланс между количеством PG и производительностью

| Мало PG | Много PG |
|---------|----------|
| Неравномерное распределение данных | Высокое потребление RAM на OSD/MON |
| Медленная ребалансировка (мало потоков) | Увеличение времени Peering при сбоях |
| Меньше метаданных | Равномерное распределение данных |
| Меньше нагрузки на CPU мониторов | Быстрая параллельная ребалансировка |
| Риск переполнения отдельных OSD | Более мелкие единицы восстановления |

### Целевое количество PG на OSD

| Сценарий | PG на OSD | Примечание |
|----------|-----------|------------|
| Минимум | 50 | Допустимо для тестовых сред |
| **Рекомендуется** | **100-250** | Оптимальный баланс для BlueStore/Crimson |
| Максимум | 500 | Вызывает избыточный peering и расход ресурсов |

Параметр `mon_target_pg_per_osd` по умолчанию равен 100. Для современных кластеров (>50 OSD) рекомендуется значение 200.

### Влияние на оперативную память (RAM)

Каждая PG требует ресурсов для хранения метаданных:
- **BlueStore**: ~1 МБ RAM на PG на каждом OSD.
- **Crimson (v20/v21)**: Оптимизированная lockless-архитектура снижает накладные расходы на PG, но требует значительного объема RAM для NVMe-кэширования (рекомендуется от 4 ГБ на OSD).
- **Эмпирическое правило**: 1 ГБ RAM на 1 ТБ дискового пространства OSD.
- **Практический расчет**: Кластер с 20 OSD × 256 PG на OSD = 5120 PG × ~1 МБ = ~5 ГБ RAM только для PG-метаданных на OSD.

### Полные статусы PG

PG проходят через различные состояния во время жизненного цикла. Понимание статусов критично для диагностики проблем:

| Статус | Описание | Действие |
|--------|----------|----------|
| `active+clean` | Нормальное состояние. Все реплики согласованы, данные актуальны. | Не требуется. |
| `active+clean+scrubbing` | Идет проверка целостности (scrub). | Наблюдение. Задержка нормальна. |
| `active+clean+deep` | Идет глубокая проверка (byte-level). | Наблюдение. Повышенная нагрузка на диск. |
| `active+recovering` | Идет восстановление реплик после сбоя OSD. | Мониторить прогресс (`ceph pg <pg_id> query`). |
| `active+degraded` | Не хватает реплик (например, при сбое OSD). Работоспособна, но уязвима. | Проверить состояние дисков, дождаться восстановления. |
| `active+undersized` | Количество реплик меньше `min_size`. Запись заблокирована. | Срочно восстановить OSD. |
| `active+backfilling` | Перенос данных на новый/восстановленный OSD. | Дождаться завершения. Нагрузка на сеть. |
| `active+backfill-toofull` | Backfill остановлен из-за заполненности целевого OSD (> `backfillfull_ratio`). | Освободить место на OSD или поднять порог (`ceph osd set-backfillfull-ratio`). |
| `active+remapped` | PG перемещается на другие OSD после изменения карты кластера. | Наблюдение. Данные доступны через старые OSD до завершения. |
| `peering` | Согласование состояния PG между репликами. | Наблюдение. Если застревает >10 мин — проверять OSD. |
| `stale` | PG не отвечает. Все OSD, хранящие PG, возможно, недоступны. | Проверить статус OSD (`ceph osd tree`). |
| `incomplete` | Не удалось завершить peering. Возможна потеря данных. | Критическая ошибка. Восстановление из бэкапа или возврат оборудования. |
| `down` | Данные недоступны. | Критическая ошибка. Проверить OSD и сеть. |
| `unclean` | Объекты не согласованы. Возможна потеря данных. | Проверить OSD, возможно потребуется `ceph pg repair`. |

## Практические сценарии

### Формула расчета общего количества PG

```
Total PGs = (OSD_count × Target_PG_per_osd) / replication_factor
```

Где:
- `OSD_count` — общее количество OSD в кластере.
- `Target_PG_per_osd` — целевое значение (рекомендуется 100-200).
- `replication_factor` — фактор репликации (`size`, обычно 3).

Для Erasure Coding:
```
Total PGs = (OSD_count × Target_PG_per_osd) / k
```
Где `k` — количество данныхых фрагментов (например, 4 в конфигурации 4+2).

### Пример расчета

**Дано:**
- 3 узла × 3 OSD = 9 OSD.
- Репликация: `size=3`.
- Целевое значение: 100 PG на OSD.

**Расчет:**
```
Total PGs = (9 × 100) / 3 = 300 PG
```
Округляем до ближайшей степени двойки: **256** или **512**.

**Для EC (4+2):**
```
Total PGs = (9 × 100) / 4 = 225 PG → 256
```

### Правило степени двойки

Значение `pg_num` каждого пула должно быть степенью двойки для обеспечения равномерного распределения. Это правило применяется **для каждого пула в отдельности**.

| Значение | Степень | Рекомендация |
|----------|---------|--------------|
| 32 | 2⁵ | Маленькие пулы (< 100 ГБ) |
| 64 | 2⁶ | Средние пулы (100 ГБ - 1 ТБ) |
| 128 | 2⁷ | Большие пулы (1-10 ТБ) |
| 256 | 2⁸ | Очень большие пулы (> 10 ТБ) |
| 512 | 2⁹ | Огромные пулы (> 100 ТБ) |
| 1024 | 2¹⁰ | Экстремальные пулы (> 1 ПБ) |

### Распределение PG по пулам

Распределяйте PG пропорционально **ожидаемому объему данных**:

| Пул | Тип | Ожидаемый объем | PG |
|-----|-----|-----------------|-----|
| `cephfs_metadata` | Метаданные (NVMe) | 100 ГБ | 64 |
| `cephfs_data` | Данные | 400 ГБ | 128 |
| `rbd` | Данные | 500 ГБ | 128 |
| **Итого** | | **1 ТБ** | **320** (~256-512) |

> **Примечание**: Каждый пул округляется до своей степени двойки независимо. Метаданные пулы CephFS всегда используют репликацию (size=3), данные — могут использовать EC.

### Ручная настройка PG

```bash
# Создание пула с ручным указанием PG
ceph osd pool create mypool 128 128

# Изменение количества PG
ceph osd pool set mypool pg_num 256

# Проверка текущего значения
ceph osd pool get mypool pg_num

# Проверка pgp_num (автоматически синхронизируется с pg_num)
ceph osd pool get mypool pgp_num
```

### Динамическое изменение PG

#### Увеличение (Splitting)

Ceph делит существующие PG, перенося часть объектов в новые PG. Процесс запускается при увеличении `pg_num` и выполняется фоново.

```bash
# Увеличение pg_num
ceph osd pool set mypool pg_num 256

# Мониторинг прогресса splitting
ceph pg dump | grep splitting
ceph -w  # → watching for "pg_num changed" events
```

- **Нагрузка**: Вызывает I/O нагрузку (чтение + запись объектов). Для больших пулов (>10 ТБ) splitting может занять часы.
- **Доступность**: PG остаются доступны для записи во время splitting.
- **Рекомендация**: Увеличивать pg_num постепенно (не более чем в 2 раза за раз) для снижения нагрузки.

#### Уменьшение (Merging)

Поддерживается в версиях v18+. Позволяет сжимать пулы, в которых слишком много PG.

```bash
# Уменьшение pg_num (требуется, чтобы pg_num был степенью двойки)
ceph osd pool set mypool pg_num 128

# Мониторинг прогресса merging
ceph pg dump | grep merging
```

- **Ограничение**: `pg_num` после уменьшения должен оставаться степенью двойки.
- **Нагрузка**: Аналогична splitting, но в обратном направлении.
- **Доступность**: PG остаются доступны для записи во время merging.

### PG Autoscaling (современный подход)

В версиях **Squid (19.x)**, **Tentacle (20.x)** и **Umbrella (21.x)** автоскейлинг является стандартом.

#### Включение автоскейлинга

```bash
# Включение для конкретного пула
ceph osd pool set <pool-name> pg_autoscale_mode on

# Проверка статуса всех пулов
ceph osd pool autoscale-status

# Детальный вывод по конкретному пулу
ceph osd pool autoscale-status <pool-name>
```

#### Режимы автоскейлинга

| Режим | Описание |
|-------|----------|
| `off` | Автоскейлинг отключен, управление только вручную. |
| `warn` | Ceph выдает предупреждения в `ceph health`, если `pg_num` не оптимален. Рекомендуется как переходный режим. |
| `on` | Автоматическое применение изменений (разделение или слияние PG). |

#### Управление в 2026 (v19/v20/v21)

```bash
# Включение автоскейлинга
ceph osd pool set <pool-name> pg_autoscale_mode on

# Отключение при обновлениях (рекомендуется)
ceph osd pool set <pool-name> pg_autoscale_mode off

# Флаг bulk: для новых больших пулов — сразу выделить целевое количество PG
ceph osd pool set <pool-name> bulk true

# Target Size: помогает автоскейлеру планировать заранее
ceph osd pool set <pool-name> target_size_bytes 100T
# Или по доле в кластере:
ceph osd pool set <pool-name> target_size_ratio 0.5

# Ограничения: минимальное и максимальное количество PG
ceph osd pool set <pool-name> pg_num_min 64
ceph osd pool set <pool-name> pg_num_max 1024
```

#### Автоскейлинг для Erasure Coding пулов

EC пулы требуют особого внимания, так как `pg_num` должен быть кратен `k` (количество данныхых фрагментов):

```bash
# Для EC пула с k=4
ceph osd pool set ec-pool pg_num_min 128  # кратно 4
```

### Scrubbing: влияние на PG

Scrubbing проверяет целостность данных, но создает нагрузку на диск и сеть.

```bash
# Статус scrubbing
ceph pg dump | grep scrubbing

# Включение/отключение scrubbing
ceph osd set noscrub    # → запретить scrub
ceph osd unset noscrub  # → разрешить scrub

# Глубокий scrub (byte-level проверка)
ceph osd set nodeep-scrub    # → запретить deep scrub
ceph osd unset nodeep-scrub

# Просмотр последнего времени scrub для PG
ceph pg <pg_id> query | grep -i scrub
```

**Влияние на производительность:**
- **Shallow scrub**: Сравнивает checksum'ы объектов. Нагрузка на диск умеренная.
- **Deep scrub**: Читает каждое хранилище объекта и проверяет на level-1. Нагрузка на диск высокая, возможен рост latency для клиентов.
- **Рекомендация**: Планировать deep scrub в периоды минимальной нагрузки (ночные окна). Использовать `noscrub`/`nodeep-scrub` флаги во время критических операций.

### Диагностика проблем с PG

#### Типичные сценарии сбоев

| Сценарий | Симптомы | Причины | Решение |
|----------|----------|---------|---------|
| `PG incomplete` | Данные недоступны для чтения/записи | Все OSD с репликами PG вышли из строя | Восстановление из бэкапа или возврат оборудования |
| `PG stale` | PG не отвечает, возможно зависание I/O | OSD down, сетевые проблемы, зависание MDS | Проверить `ceph osd tree`, перезапустить OSD |
| `PG degraded` | Запись работает, но PG уязвима к потере данных | OSD down, 아직 не завершено восстановление | Дождаться восстановления, проверить диски |
| `PG undersized` | Запись заблокирована (min_size не достигнут) | Количество реплик < min_size | Срочно восстановить OSD или увеличить min_size |
| `PG recovering` (долго) | Восстановление длится >30 мин | Мало PG, большой объем данных, медленные диски | Увеличить pg_num, добавить OSD, проверить сеть |
| `PG backfill-toofull` | Backfill остановлен | Целевой OSD заполнен > backfillfull_ratio | Освободить место или увеличить порог |
| `PG peering` (долго) | PG недоступна >10 мин | Много PG на OSD, медленные диски | Дождаться, проверить OSD logs |
| `PG unclean` | Объекты не согласованы | Конфликт версий, ошибки чтения | `ceph pg repair <pg_id>` (ОСТОРОЖНО) |

#### Команды диагностики

```bash
# Общий статус PG
ceph pg stat

# Список PG, требующих внимания (не active+clean)
ceph pg dump_not_clean

# Поиск зависших (stale) PG
ceph pg dump_stale

# Поиск неполных (incomplete) PG
ceph pg dump_incomplete

# Детали по конкретной PG (расширенный вывод)
ceph pg <pg_id> query

# Просмотр всех PG с их статусами
ceph pg dump --format json-pretty | python3 -c "
import json, sys
data = json.load(sys.stdin)
for pg in data.get('pg_stats', []):
    state = pg.get('state', 'unknown')
    if 'clean' not in state or 'active' not in state:
        print(f\"{pg.get('pgid', '?'):20s} {state}\")
"

# Поиск PG на конкретном OSD
ceph pg dump | grep "^<osd_id>"

# Статистика по OSD: сколько PG на каждом
ceph osd df tree

# Проверка здоровья кластера
ceph health detail

# Поиск PG с ошибками
ceph pg dump --format json-pretty | python3 -c "
import json, sys
data = json.load(sys.stdin)
for pg in data.get('pg_stats', []):
    state = pg.get('state', '')
    if any(x in state for x in ['down', 'incomplete', 'stale', 'unclean']):
        print(f\"{pg.get('pgid', '?'):20s} {state}\")
"
```

### Мониторинг PG

#### Полезные команды для регулярного использования

```bash
# Просмотр всех PG с их статусами и размерами
ceph pg dump --format json-pretty | python3 -c "
import json, sys
data = json.load(sys.stdin)
for pg in data.get('pg_stats', []):
    state = pg.get('state', 'unknown')
    size = pg.get('stat_sum', {}).get('num_bytes', 0)
    print(f\"{pg.get('pgid', '?'):20s} {state:30s} {size/1024/1024:.1f} MB\")
"

# Статистика по состояниям PG (агрегация)
ceph pg dump --format json-pretty | python3 -c "
import json, sys
from collections import Counter
data = json.load(sys.stdin)
states = Counter(pg.get('state', 'unknown') for pg in data.get('pg_stats', []))
for state, count in states.most_common():
    print(f\"{state:40s} {count}\")
"

# Мониторинг процесса восстановления
ceph -w | grep -i "recovery\|backfill"

# Просмотр операций в реальном времени (IO по PG)
ceph daemon osd.<id> dump_ops_in_flight 2>/dev/null | head -50
```

#### Настройка алертинга (Prometheus)

```yaml
# Алерт на PG в нештатном состоянии
groups:
  - name: ceph_pg_alerts
    rules:
      - alert: CephPGNotActiveClean
        expr: ceph_pg_state{state!~"active\\+clean"} > 0
        for: 5m
        labels:
          severity: warning
        annotations:
          summary: "PG {{ $labels.pgid }} в состоянии {{ $labels.state }}"

      - alert: CephPGIncomplete
        expr: ceph_pg_state{state=~".*incomplete.*"} > 0
        for: 1m
        labels:
          severity: critical
        annotations:
          summary: "PG {{ $labels.pgid }} incomplete - данные недоступны"

      - alert: CephPGRecovering
        expr: ceph_pg_state{state=~".*recovering.*"} > 0
        for: 30m
        labels:
          severity: warning
        annotations:
          summary: "PG {{ $labels.pgid }} восстанавливается >30 мин"
```

### CephFS: особенности PG для метаданных и данных

CephFS автоматически создает два пула с разными требованиями к PG:

#### Метаданный пул (`cephfs_metadata`)

- **Тип хранения**: Всегда репликация (size=3).
- **Характер доступа**: Мелкие random I/O (4 КБ - 64 КБ).
- **PG**: Обычно 64 (достаточно для метаданных).
- **Диски**: NVMe рекомендуется.
- **Особенность**: PG metadata пула определяют количество MDS рангов. Слишком много PG замедлит peering метаданных.

#### Пул данных (`cephfs_data`)

- **Тип хранения**: Репликация или Erasure Coding.
- **Характер доступа**: Крупные sequential I/O ( stripe unit × stripe count).
- **PG**: Зависит от объема данных. Рекомендация: 128-256 для пулов <10 ТБ.
- **Диски**: HDD/SSD для данных.
- **Особенность**: Для EC пулов `pg_num` должен быть кратен `k`.

```bash
# Проверка пулов CephFS
ceph osd pool ls detail | grep cephfs
# → pool 1 'cephfs_metadata' ... application cephfs
# → pool 2 'cephfs_data' ... application cephfs

# Настройка PG для метаданных пула
ceph osd pool set cephfs_metadata pg_num 64

# Настройка PG для пула данных
ceph osd pool set cephfs_data pg_num 256
```

### Erasure Coding: особенности PG

EC пулы требуют особого внимания при расчете PG:

```bash
# Создание EC пула с правильным количеством PG
ceph osd pool create ec-pool 256 256 replicated  # сначала replicated
ceph osd pool set ec-pool allow_ec_overwrites true
ceph osd pool create ec-pool 256 erasure default  # затем переключить на EC

# Проверка PG для EC пула
ceph osd pool get ec-pool pg_num
ceph osd pool get ec-pool erasure_code_profile
```

**Особенности:**
- `pg_num` должен быть кратен `k` (количество данныхых фрагментов).
- EC пулы не поддерживают `cephfs_metadata` (метаданные всегда реплицируются).
- При EC 4+2 (k=4): `pg_num` должен быть кратен 4 (64, 128, 256, ...).

### Переключение PG при обновлении кластера

```bash
# Перед обновлением: отключить автоскейлер
ceph osd pool set <pool-name> pg_autoscale_mode off

# Установить флаги для безопасного обновления
ceph osd set noout
ceph osd set nobackfill
ceph osd set norecover

# После обновления: снять флаги и включить автоскейлер
ceph osd unset noout
ceph osd unset nobackfill
ceph osd unset norecover
ceph osd pool set <pool-name> pg_autoscale_mode on
```

### Рекомендации для разных сценариев

| Сценарий | OSD | Репликация | PG на пул | Автоскейлер |
|----------|-----|------------|-----------|-------------|
| Лабораторный (Test) | 3 | 3 | 32-64 | off |
| Малый Production | 9-20 | 3 | 128 | warn |
| Средний Production | 20-100 | 3 | 256-512 | on |
| Крупный Production | 100+ | 3 | 1024+ | on (bulk) |
| EC (4+2) Production | 20+ | - | 128-256 (кратно k) | on |

### Известные проблемы и ограничения

- **Splitting/merging во время нагрузки**: Изменение `pg_num` вызывает фоновую активность. Планируйте изменения в окна обслуживания.
- **Scrub и latency**: Deep scrub может увеличить latency чтения. Используйте `noscrub`/`nodeep-scrub` флаги.
- **PG autoscaler и обновления**: Перед обновлением кластера временно отключите автоскейлер (`ceph osd pool set noautoscale`).
- **PG incomplete**: Это потеря данных. Восстановление возможно только из бэкапа или возвратом оборудования.
- **Много PG на маленьком кластере**: На 3 OSD с 256 PG = 85 PG на OSD. Peering будет медленным. Снизьте pg_num.
