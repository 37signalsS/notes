# Расчет количества Placement Group (PG) в Ceph

## Определения

**Placement Group (PG)** — логический контейнер для объектов Ceph, распределяемый по OSD. PG обеспечивают равномерное распределение данных и упрощают ребалансировку.

**OSD** (Object Storage Daemon) — демон хранения, управляющий физическим диском.

**PG Autoscaling** — механизм автоматического подбора количества PG на основе фактической утилизации пула.

## Основные концепции

### Зачем нужны PG

PG решают задачу масштабирования:

- Без PG: каждый объект требует отслеживания местоположения
- С PG: отслеживается местоположение PG, объекты внутри PG распределяются хэшем

### Баланс между количеством PG и производительностью

| Мало PG | Много PG |
|---------|----------|
| ❌ Неравномерное распределение | ❌ Высокое потребление RAM |
| ❌ Медленная ребалансировка | ❌ Больше метаданных |
| ✅ Меньше метаданных | ✅ Равномерное распределение |
| ✅ Меньше RAM | ✅ Быстрая ребалансировка |

### Целевое количество PG на OSD

| Сценарий | PG на OSD | Примечание |
|----------|-----------|------------|
| Минимум | 50 | Допустимо для маленьких кластеров |
| **Рекомендуется** | **100-250** | Оптимальный баланс |
| Максимум | 500 | Вызывает избыточный peering и расход RAM |

Параметр `mon_target_pg_per_osd` по умолчанию 100, рекомендуется 200 для кластеров >50 OSD.

### Влияние на RAM

Примерная формула:

```
RAM_per_OSD (MB) = PG_per_OSD × 1 MB
```

Для 100 PG на OSD требуется ~100 МБ RAM только на метаданные PG. Эмпирическое правило: 1 ГБ RAM на 1 ТБ дискового пространства на OSD.

## Практические сценарии

### Формула расчета общего количества PG

```
Total PGs = (OSD_count × Target_PG_per_OSD) / replication_factor
```

Где:

- `OSD_count` — общее количество OSD в кластере
- `Target_PG_per_OSD` — целевое значение (рекомендуется 100-200)
- `replication_factor` — фактор репликации (`size`, обычно 3)

### Пример расчета

**Дано:**

- 3 узла × 3 OSD = 9 OSD
- Репликация: `size=3`
- Целевое значение: 100 PG на OSD

**Расчет:**

```
Total PGs = (9 × 100) / 3 = 300 PG
```

Округляем до ближайшей степени двойки: **256** или **512**.

### Правило степени двойки

Значение `pg_num` каждого пула должно быть степенью двойки для обеспечения равномерного распределения данных. Это правило применяется **per-pool**, а не к сумме PG всех пулов.

| Значение | Степень | Рекомендация |
|----------|---------|--------------|
| 32 | 2⁵ | Маленькие пулы (< 100 ГБ) |
| 64 | 2⁶ | Средние пулы (100 ГБ - 1 ТБ) |
| 128 | 2⁷ | Большие пулы (1-10 ТБ) |
| 256 | 2⁸ | Очень большие пулы (> 10 ТБ) |
| 512 | 2⁹ | Огромные пулы (> 100 ТБ) |

Пример расчета: 200 OSD, 3 реплики → `(200 × 100) / 3 = 6667` → округляем до **8192**.

### Распределение PG по пулам

Распределяйте PG пропорционально **ожидаемому объему данных**:

| Пул | Ожидаемый объем | Доля | PG |
|-----|-----------------|------|-----|
| `rbd` | 500 ГБ | 50% | 128 |
| `cephfs_data` | 400 ГБ | 40% | 128 |
| `cephfs_metadata` | 100 ГБ | 10% | 64 |
| **Итого** | **1 ТБ** | **100%** | **320** (~256-512) |

> **Примечание**: Каждый пул округляется до своей степени двойки независимо.

### Ручная настройка PG

```bash
# Создание пула с оптимальным количеством PG
ceph osd pool create mypool 128 128

# Изменение количества PG
ceph osd pool set mypool pg_num 256
ceph osd pool set mypool pgp_num 256
```

> **Важно**: `pgp_num` всегда должен быть равен `pg_num`. Начиная с Nautilus, `pgp_num` синхронизируется автоматически при изменении `pg_num`.

### Динамическое изменение PG

#### Увеличение PG

```bash
# Увеличение с 64 до 128
ceph osd pool set mypool pg_num 128
ceph osd pool set mypool pgp_num 128
```

Процесс:

1. Ceph делит каждую PG пополам
2. Половина данных остается, половина перемещается
3. Запускается ребалансировка

> **Предупреждение**: Операция вызывает нагрузку на кластер. Выполняйте в maintenance window. Изменение `pg_num` целесообразно только при переходе на следующую степень двойки.

#### Уменьшение PG

Поддерживается в новых версиях Ceph (Reef 18.x+):

```bash
ceph osd pool set mypool pg_num 64
```

> **Осторожно**: Уменьшение возможно только если данные помещаются в меньшее количество PG.

### PG Autoscaling (современный подход)

Начиная с Nautilus, Ceph поддерживает автоматическое масштабирование PG.

#### Включение автоскейлинга

```bash
# Включение для конкретного пула
ceph osd pool set <pool-name> pg_autoscale_mode on

# Проверка статуса всех пулов
ceph osd pool autoscale-status

# Глобальная настройка по умолчанию
ceph config set global osd_pool_default_pg_autoscale_mode on
```

#### Режимы автоскейлинга

| Режим | Описание |
|-------|----------|
| `off` | Автоскейлинг отключен |
| `warn` | Показывает рекомендации без изменений |
| `on` | Автоматическое применение изменений |

#### Ограничения диапазона

```bash
# Установка минимального/максимального количества PG
ceph osd pool set <pool-name> pg_num_min 64
ceph osd pool set <pool-name> pg_num_max 512

# Установка ожидаемого размера пула для точного старта
ceph osd pool set <pool-name> target_size_bytes 100T
```

#### Особенности работы

- Корректировки применяются при отклонении текущего `pg_num` от рекомендованного более чем в 3 раза
- Пулы, охватывающие несколько CRUSH-корней (spanning pools), игнорируются до приведения к одному device class/правилу CRUSH
- Флаг `bulk` задает стартовый полный набор PG с последующим масштабированием вниз при неравномерной утилизации
- При активном балансировщике ожидается ~50-70 реплик PG на OSD

> **Рекомендация**: Используйте режим `warn` inicialmente для оценки рекомендаций перед переходом на `on`.

### Мониторинг PG

```bash
# Статус PG
ceph pg stat

# Детализация по пулу
ceph pg dump --pools <pool_name>

# PG в неоптимальном состоянии
ceph pg dump_stale
ceph pg dump_undersized
ceph pg dump_incomplete

# Детали по конкретной PG
ceph pg <pg_id> query
```

#### Интерпретация статусов PG

| Статус | Описание | Действие |
|--------|----------|----------|
| `active+clean` | Норма | — |
| `active+recovering` | Идет восстановление | Мониторить |
| `active+degraded` | Не все реплики доступны | Проверить OSD |
| `active+undersized` | Меньше реплик чем нужно | Проверить OSD |
| `active+backfilling` | Заполнение новых OSD | Норма при расширении |
| `down` | Критическая ошибка | Немедленное вмешательство |
