# CephFS: Продвинутые темы

## Определения

**Subtree Pinning (Привязка поддеревьев)** — механизм статического или динамического распределения нагрузки между несколькими активными MDS путем закрепления определенных директорий за конкретными рангами (Rank). Используется, когда администратору известна структура нагрузки и необходимо исключить накладные расходы на автоматическую миграцию метаданных.

**Ephemeral Pinning (Эфемерная привязка)** — автоматический механизм (v13+), при котором CephFS распределяет поддиректории внутри крупного каталога по разным MDS для устранения узких мест при обработке метаданных. Поддерживает два режима: `distributed` (равномерное распределение) и `random` (случайное распределение).

**MDS Rank (Ранг)** — логический экземпляр MDS в кластере. Нумерация начинается с 0. Количество рангов (`max_mds`) определяет степень параллелизма обработки метаданных. Каждый ранг управляет непрерывным поддеревом каталогов (subtree) и имеет собственный журнал.

**Scrubbing (Фоновая очистка)** — процесс проверки целостности файловой системы, при котором MDS сверяет метаданные в оперативной памяти с объектами в RADOS, проверяет соответствие индексов и восстанавливает поврежденные связи. Различают `scrub` (проверка метаданных) и `deep-scrub` (проверка данных с чтением объектов).

**LazyIO** — расширение POSIX, позволяющее приложениям (HPC, базы данных) осознанно обходить строгие гарантии когерентности кэша для повышения производительности при одновременном доступе к одному файлу с множества узлов. Требует поддержки на уровне приложения через `libcephfs`.

**Caps (Capabilities) Recall** — процесс отзыва прав на кэширование у клиентов. MDS инициирует recall, когда достигает лимита памяти или когда другой клиент запрашивает доступ, требующий изменения состояния кэша. Реколл является блокирующей операцией для клиента до завершения.

**MDLog (Metadata Journal)** — журнал операций с метаданными, обеспечивающий_durability. Каждый MDS записывает изменения в MDLog перед применением к индексам. Используется для восстановления после сбоев и репликации данных между активным и standby MDS.

## Основные концепции

### Многопользовательская балансировка MDS (Multi-active MDS)

В кластерах с `max_mds > 1` CephFS может распределять нагрузку по нескольким активным MDS.

*   **Динамическая балансировка**: Балансировщик MDS постоянно анализирует нагрузку (количество открытых файлов, запросов в секунду) и мигрирует части дерева метаданных между рангами. Балансировка основана на эвристике, учитывающей структуру каталогов и частоту обращений.
*   **Статическая привязка (Static Pinning)**: Применяется, когда администратор точно знает структуру нагрузки (например, разные проекты в разных корнях). Исключает накладные расходы на миграцию ("flickering"). Рекомендуется для директорий с предсказуемым паттерном доступа.
*   **Эфемерная привязка (Ephemeral Pinning)**: Идеально для директорий типа `/home` или `/users`, где тысячи независимых подкаталогов могут обрабатываться разными MDS параллельно без ручного вмешательства. Режим `distributed` обеспечивает равномерное распределение, `random` — случайное.

**Ограничения Multi-active MDS:**
- Увеличение `max_mds` выше 4-8 редко дает линейный прирост производительности из-за накладных расходов на координацию между MDS.
- Директории, связанные частыми перемещениями (`rename`) между поддеревьями, могут вызывать конфликты и снижение производительности.
- Не рекомендуется использовать `max_mds > 1` для workload с интенсивным `rename` между директориями.

### Управление кэшем и лимитами памяти

Кэш метаданных критичен для производительности CephFS. В версиях **Tentacle (20.x)** и **Umbrella (21.x)** алгоритмы вытеснения кэша оптимизированы для работы с NVMe-хранилищами метаданных.

*   **MDS Cache**: Хранит Inodes и Dentries. Размер регулируется `mds_cache_memory_limit`. При достижении лимита MDS начинает recall Caps у клиентов для высвобождения памяти.
*   **Client Cache**: Клиенты (Kernel/FUSE) удерживают Caps на файлы. Если клиент не возвращает Caps вовремя, MDS может пометить его как "stale" и принудительно разорвать сессию.
*   **Рекомендации по размеру кэша**: Для MDS выделяйте не менее 1 ГБ RAM на 1 million inodes в кэше. На SSD/NVMe для метаданных размещение journal и индексов снижает latency.

**Взаимодействие кэша MDS и клиента:**
1. Клиент открывает файл → получает Caps от MDS.
2. Клиент кэширует данные (read/write) локально.
3. При обращении другого клиента к тому же файлу → MDS инициирует recall Caps.
4. Первый клиент сбрасывает грязные данные (flush) и возвращает Caps.
5. MDS выдает новые Caps второму клиенту.

### Безопасность Messenger v2.1

Messenger v2.1 (стандарт с v16+) поддерживает современные режимы шифрования и аутентификации:
- **`crc`**: Проверка целостности (защита от ошибок передачи). Режим по умолчанию, минимальные накладные расходы.
- **`secure`**: Шифрование AES-GCM (защита от перехвата). В 2026 году аппаратное ускорение AES-NI на современных CPU практически нивелирует накладные расходы, делая этот режим стандартом для untrusted-сетей.

**Выбор режима:**
- `crc` — для доверенных сетей (например, внутри одного дата-центра). Обеспечивает целостность данных без шифрования.
- `secure` — для сетей между дата-центрами или при требованиях к конфиденциальности. Рекомендуется для production-сред.

**Порт по умолчанию:**
- v1: 6789 (устаревший, не рекомендуется)
- v2.1: 3300 (современный стандарт)

### Планировщик MDS (MDS balancer)

Балансировщик MDS работает в фоновом режиме и выполняет следующие задачы:
1. Мониторинг нагрузки на каждый ранг (количество inodes, rate операций).
2. Выявление "горячих" поддеревьев с интенсивным доступом.
3. Миграция поддеревьев между рангами для выравнивания нагрузки.
4. Разбиение крупных поддеревьев на более мелкие для эфемерной привязки.

## Практические сценарии

### Предварительные требования

Для выполнения команд в данном разделе необходимо:
- Кластер Ceph в версии **v16 (Quincy)** или выше (рекомендуется **v20+**).
- Доступ к узлу с установленным клиентом `ceph-common` и правами `admin` или `cephfs-admin`.
- Монтированная CephFS (для команд `setfattr`).
- Права на выполнение `ceph tell` и `ceph daemon` (обычно доступны из-под `ceph` user или через `sudo`).

### 1. Тюнинг и оптимизация MDS

#### Настройка лимитов памяти

```bash
# Установка лимита кэша (например, 16 ГБ)
# Значение указывается в байтах
ceph config set mds.<id> mds_cache_memory_limit 17179869184

# Настройка агрессивности отзыва Caps (пороговые значения)
# mds_recall_max_caps — максимальное количество Caps для отзыва за один цикл
ceph config set mds mds_recall_max_caps 5000

# Проверка текущего значения
ceph config get mds mds_cache_memory_limit
# → 17179869184
```

**Параметры для тюнинга:**

| Параметр | Описание | Рекомендуемое значение |
|----------|----------|----------------------|
| `mds_cache_memory_limit` | Лимит памяти кэша MDS (в байтах) | 50-70% от доступной RAM на MDS |
| `mds_recall_max_caps` | Макс. Caps для отзыва за цикл | 5000-10000 |
| `mds_decay_halflife` | Время полураспада метрик нагрузки | 60 (секунды) |
| `mds_bal_split_ceiling` | Макс. глубина разбиения поддерева | 30 |

#### Настройка эфемерной привязки (Ephemeral Pinning)

Рекомендуется для каталогов с огромным количеством поддиректорий (например, `/home` с тысячами пользователей).

```bash
# Включение распределения поддиректорий по MDS рангам (distributed)
setfattr -n ceph.dir.pin.distributed -v 1 /mnt/cephfs/users_data

# Или привязка всех вложенных объектов к одному случайному рангу (random)
setfattr -n ceph.dir.pin.random -v 1 /mnt/cephfs/project_archive

# Проверка установленного атрибута
getfattr -n ceph.dir.pin.distributed /mnt/cephfs/users_data
# → ceph.dir.pin.distributed="1"

# Отключение эфемерной привязки
setfattr -n ceph.dir.pin.distributed -v 0 /mnt/cephfs/users_data
```

**Сравнение режимов:**

| Режим | Поведение | Когда использовать |
|-------|----------|-------------------|
| `distributed` | Поддиректории распределяются равномерно по всем рангам | Равномерная нагрузка, много независимых подкаталогов |
| `random` | Поддиректории привязываются к случайному рангу | Когда нужна простая привязка без балансировки |

### 2. Обслуживание и Scrubbing

Проверка целостности должна быть регулярной в крупных инсталляциях. Рекомендуемая частота: `scrub` — еженедельно, `deep-scrub` — ежемесячно.

```bash
# Запуск глубокой проверки с автоматическим исправлением ошибок
# Рекурсивный scrub с repair и force (для принудительного запуска)
ceph tell mds.0 scrub start /projects recursive,repair,force

# Запуск обычного scrub (только метаданные)
ceph tell mds.0 scrub start /projects recursive

# Просмотр статистики текущего scrubbing
ceph tell mds.0 scrub status
# → scrub status: active scrubbing

# Просмотр результатов последнего scrub
ceph tell mds.0 scrub status --format json-pretty

# Принудительное завершение сессии зависшего клиента (eviction)
# Применяется, если клиент блокирует Recall и вешает MDS
# Сначала найдите ID клиента
ceph tell mds.0 session ls --format json-pretty | jq '.[].id'
# Затем выполните eviction
ceph tell mds.0 session evict id=<client_id>
```

**Планирование scrubbing:**

```bash
# Настройка интервала scrub (в часах, по умолчанию 168 = 7 дней)
ceph config set mds mds_scrub_begin_hour 0
ceph config set mds mds_scrub_duration 3600

# Исключение определенных директорий из scrub
# Установка атрибута на директории
setfattr -n ceph.dir.pin.distributed -v 0 /mnt/cephfs/readonly_archive
```

**Понимание результатов scrub:**

| Статус | Описание |
|--------|----------|
| `ok` | Ошибок не обнаружено |
| `fixed` | Обнаруженные ошибки исправлены |
| `errors` | Обнаружены ошибки (требуется ручное вмешательство) |
| `aborted` | Scrub прерван (например, из-за падения MDS) |

### 3. Настройка параметров клиента (Kernel)

Оптимизация на стороне Linux-узлов.

```bash
# Увеличение максимального количества открытых файлов (inodes) в кэше клиента
# Актуально для компиляции кода или работы с мелкими файлами на CephFS
echo 65536 | sudo tee /sys/module/ceph/parameters/mds_max_caps_per_client
# → 65536

# Отключение кэширования атрибутов для повышения консистентности
# actimeo=0 отключает кэширование атрибутов (цена - производительность)
mount -t ceph ... -o actimeo=0

# Просмотр текущих параметров монтирования
mount | grep ceph
# → 192.168.1.10:3300:/ on /mnt/cephfs type ceph (...)

# Проверка статистики клиента
cat /sys/kernel/debug/ceph/*/client/*/caps
```

**Параметры клиента для оптимизации:**

| Параметр | Описание | Значение по умолчанию |
|----------|----------|----------------------|
| `mds_max_caps_per_client` | Макс. Caps на клиента | 100000 |
| `actimeo` | Время кэширования атрибутов (сек) | 1 |
| `max_readdir` | Макс. записей при readdir | 1024 |
| `max_readahead` | Макс. readahead (байты) | 131072 |

### 4. Квоты на уровне директорий

CephFS поддерживает квоты, которые проверяются клиентами (cooperative quotas). Квоты не являются строгими лимитами — клиент может временно превысить квоту до следующей проверки с MDS.

```bash
# Ограничение по объему (1 ТБ)
setfattr -n ceph.quota.max_bytes -v 1099511627776 /mnt/cephfs/project_a

# Ограничение по количеству файлов (1 млн)
setfattr -n ceph.quota.max_files -v 1000000 /mnt/cephfs/project_a

# Проверка установленных квот
getfattr -n ceph.quota.max_bytes /mnt/cephfs/project_a
# → ceph.quota.max_bytes="1099511627776"

getfattr -n ceph.quota.max_files /mnt/cephfs/project_a
# → ceph.quota.max_files="1000000"

# Удаление квоты
setfattr -n ceph.quota.max_bytes -v 0 /mnt/cephfs/project_a
```

**Особенности cooperative quotas:**
- Клиент проверяет квоту локально перед записью.
- Задержка обновления может достигать 30 секунд (зависит от `cap_revoke_grace_period`).
- Квоты могут быть "пробиты" на несколько секунд/минут при высокой нагрузке.
- Для строгих лимитов используйте application-level проверки.

### 5. Принудительное шифрование (Messenger v2)

```bash
# Требовать шифрование для всех клиентских подключений к ФС
ceph fs set myfs ms_mode secure

# Проверка текущего режима
ceph fs get myfs | grep ms_mode
# → ms_mode: secure

# Пример монтирования с явным указанием режима
mount -t ceph 192.168.1.10:3300:/ /mnt/secure_fs \
  -o name=admin,secretfile=/etc/ceph/admin.secret,ms_mode=secure

# Монтирование с crc (по умолчанию, для доверенных сетей)
mount -t ceph 192.168.1.10:3300:/ /mnt/crc_fs \
  -o name=admin,secretfile=/etc/ceph/admin.secret,ms_mode=crc
```

**Включение шифрования для конкретного клиента:**

```bash
# В /etc/fstab
192.168.1.10:3300:/ /mnt/secure ceph name=admin,secretfile=/etc/ceph/admin.secret,ms_mode=secure,_netdev,noatime 0 0
```

### 6. Диагностика производительности MDS

```bash
# Просмотр текущей нагрузки на MDS
ceph daemon mds.<id> perf dump
# → Метрики: op_per_avg, commit_latency, journal_full

# Мониторинг inodes в кэше
ceph daemon mds.<id> cache status
# → CPU time: ..., Mem: ...

# Просмотр операций в реальном времени
ceph tell mds.<id> ops
# → Список текущих операций с временем выполнения

# Просмотр сессий и Caps клиентов
ceph daemon mds.<id> dump_sessions
# → Сессии с указанием количества Caps на каждого клиента
```

**Ключевые метрики для мониторинга:**

| Метрика | Описание | Пороговые значения |
|---------|----------|-------------------|
| `mds_cache_memory` | Использование памяти кэша | Не более 70% от `mds_cache_memory_limit` |
| `mds_inodes` | Количество inodes в кэше | Зависит от размера ФС |
| `mds_caps` | Количество выданных Caps | Не более 80% от `mds_cache_memory_limit` |
| `mds_request_latency` | Задержка обработки запросов | < 10ms (p99) |

## Диагностика и устранение неполадок

### Инструменты глубокой диагностики

| Команда | Назначение |
|---------|------------|
| `ceph daemon mds.<id> cache status` | Статистика по типам объектов в кэше (inodes, dentries). |
| `ceph tell mds.<id> ops` | Текущие "зависшие" или выполняемые операции. |
| `ceph daemon mds.<id> dump_sessions` | Детальная информация о каждом подключенном клиенте и его Caps. |
| `ceph daemon mds.<id> perf dump` | Низкоуровневые счетчики (задержки, попадания в кэш). |
| `ceph tell mds.<id> session ls` | Список активных сессий клиентов. |
| `ceph tell mds.<id> perf reset <counter>` | Сброс счетчика производительности. |

### Типичные проблемы и их решение

| Проблема | Симптомы | Причина | Решение |
|----------|----------|---------|---------|
| **MDS Laggy** | `ceph health detail` показывает `MDS_LAGGY`, высокие задержки | Медленный пул метаданных, переполненный кэш, или зависший клиент | Переместите пул метаданных на NVMe/SSD. Увеличьте `mds_cache_memory_limit`. Проверьте сессии через `ceph tell mds.<id> session ls`. |
| **Caps Recall stuck** | Клиент не может выполнить I/O, `dmesg` показывает `ceph: capsplit` | Клиент не возвращает Caps (зависание или сеть) | Выполните `ceph tell mds.<id> session evict id=<client_id>` для принудительного отключения клиента. |
| **Scrub errors** | В логах MDS ошибки целостности | Повреждение метаданных в RADOS | Запустите `scrub start /path recursive,repair`. При неудаче — восстановление из снапшота. |
| **Performance degradation** | Рост задержки, снижение throughput | Малый размер кэша, неоптимальные Caps, или network congestion | Проверьте `ceph daemon mds.<id> perf dump`. Увеличьте `mds_cache_memory_limit`. Проверьте сеть между клиентами и MDS. |
| **Quota exceeded** | Клиент получает `EDQUOT` при записи | Cooperative quota превышена | Проверьте текущее использование через `getfattr`. Увеличьте лимит или очистите данные. |

## Дополнительная информация

### Особенности производительности

- **Шифрование (AES-GCM)**: На 2026 год использование режима `secure` создает дополнительную нагрузку на CPU (~5-15% на ядрах без AES-NI), но обеспечивает защиту данных в транзите. На современных Intel/AMD CPU с AES-NI нагрузка составляет < 5%.
- **LazyIO**: Требует поддержки на уровне приложения (использование `libcephfs`). Не работает автоматически для стандартных утилит типа `cp` или `tar`. Используйте LazyIO для HPC-сценариев с параллельным доступом к одним файлам.
- **MDS Ranks**: Увеличение `max_mds` выше 4-8 редко дает линейный прирост производительности из-за накладных расходов на координацию между MDS, если дерево метаданных сильно связано (огромное количество ссылок между каталогами).
- **NVMe для метаданных**: Размещение пула метаданных и journal на NVMe снижает latency MDS на 30-50% по сравнению с SSD.
- **Кэш клиента**: Для workload с множеством мелких файлов увеличение `mds_max_caps_per_client` до 100000+ значительно снижает количество запросов к MDS.

### Мониторинг и алертинг

Для Prometheus рекомендуется отслеживать следующие метрики:

| Метрика | Описание | Алерт |
|---------|----------|-------|
| `ceph_mds_requests` | Количество запросов в секунду | Резкий рост может указывать на проблему |
| `ceph_mds_latency` | Задержка обработки запросов | > 10ms (p99) |
| `ceph_mds_cache_memory` | Использование памяти кэша | > 70% от лимита |
| `ceph_mds_caps` | Количество выданных Caps | Приближение к лимиту |
| `ceph_mds_sessions` | Количество активных сессий | Аномальные изменения |

### Best Practices

1. **Регулярный scrubbing**: Настройте автоматический `scrub` (еженедельно) и `deep-scrub` (ежемесячно).
2. **Мониторинг кэша**: Отслеживайте `mds_cache_memory` и `mds_caps` для предотвращения переполнения.
3. **Использование NVMe**: Размещайте пул метаданных и journal на NVMe для минимальных задержек.
4. **Эфемерная привязка**: Используйте для директорий с большим количеством независимых подкаталогов.
5. **Шифрование**: Включайте `ms_mode=secure` для сетей между дата-центрами.
6. **Квоты**: Используйте cooperative quotas для контроля использования, но не полагайтесь на них как на строгие лимиты.
7. **Логирование**: Настройте сбор логов MDS в централизованную систему (ELK, Loki).

### Ограничения и известные проблемы

- **Cooperative quotas**: Квоты могут быть временно превышены из-за задержки обновления (до 30 секунд).
- **Multi-active MDS**: Не эффективен для workload с интенсивным `rename` между директориями.
- **LazyIO**: Требует поддержки на уровне приложения. Стандартные утилиты (`cp`, `tar`) не поддерживают LazyIO.
- **Scrubbing**: Во время активного scrub возможен рост задержки для клиентов. Планируйте scrub в периоды низкой нагрузки.
