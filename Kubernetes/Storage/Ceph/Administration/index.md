# Администрирование Ceph: Обзор и навигация

Документ является входной точкой и общим навигационным ядром раздела администрирования Ceph. Он структурирует административные задачи (управление, мониторинг, обслуживание), объясняет ключевые концепции и направляет к специализированным руководствам, актуальным для версий **Squid (19.x)**, **Tentacle (20.x)** и **Umbrella (21.x)**.

## Определения

**Администрирование Ceph** — декларативный и операционный процесс обеспечения доступности, целостности и производительности данных в распределенном кластере RADOS. Включает управление жизненным циклом демонов, оптимизацию размещения данных (CRUSH), управление ресурсами (пулы, квоты) и мониторинг состояния компонентов.

**Декларативное управление (cephadm/orch)** — подход, ставший стандартом в 2026 году. Администратор описывает желаемое состояние (Service Specification в формате YAML), а оркестратор обеспечивает развертывание контейнеров, настройку системных служб и мониторинг их состояния.

**Операционное управление (RADOS CLI)** — низкоуровневое взаимодействие с логикой хранения через команды `ceph`, используемое для настройки пулов, управления ключами доступа (`cephx`) и глубокой диагностики.

## Базовые концепции

### Иерархия управления: Infrastructure vs RADOS

В современных инсталляциях обязанности администратора разделены на два уровня:

1.  **Уровень инфраструктуры (Orchestrator):** Команды `ceph orch ...`.
    *   **Задачи:** Установка узлов, добавление дисков (OSD), запуск демонов (MON, MGR, MDS, RGW), управление Ingress-контроллерами.
    *   **Метод:** Декларативные спецификации (`ceph orch apply -i spec.yaml`).
2.  **Уровень логики хранения (RADOS):** Команды `ceph osd ...`, `ceph pool ...`, `ceph auth ...`.
    *   **Задачи:** Создание пулов, настройка уровней репликации, управление правами доступа приложений, ручная коррекция карты CRUSH.
    *   **Метод:** Императивные команды CLI.

### Модульная архитектура MGR (Manager)

Демон **ceph-mgr** является центром автоматизации и единственной точкой доступа к административным API. Он работает в паре active/standby: активный экземпляр выполняет операции, резервный автоматически подхватывает его роль при сбое без ручного вмешательства. Активный и резервный модули однотипны, поэтому отказоустойчивость MGR не требует настройки — достаточно развернуть минимум два экземпляра (рекомендованная конфигурация — по одному на каждый узел MON).

В 2026 году критически важными модулями являются:
*   **dashboard:** Полнофункциональный GUI для мониторинга и базовых операций, включает встроенные Grafana-панели и управление оповещениями.
*   **prometheus:** Основной источник метрик для Grafana (порт `9283`, более 1500 метрик), подключается через `/etc/prometheus` или `ceph prometheus` напрямую.
*   **pg_autoscaler:** Автоматическое управление количеством PG (Placement Groups). Для самомасштабирования пула используйте `ceph osd pool autoscale-status`.
*   **balancer:** Балансировка нагрузки между OSD через `upmap`. Режимы: `crush-compat` (глобальная) и `upmap` (погонная, точечная). Проверка: `ceph balancer status`.
*   **nfs / smb:** Управление экспортами файловых протоколов напрямую через Ceph (развертывание NFS-Ganesha или Samba как сервисов `cephadm`).
*   **ingress:** Создание высокодоступных точек входа (Keepalived + HAProxy) для RGW и NFS с виртуальным IP (VIP).
*   **diskprediction:** Предсказание отказов дисков на основе локального анализа или облачной телеметрии; результат смотрится командой `ceph device predict-life-expectancy <osd-id>`.
*   **telemetry:** Периодическая отправка анонимных метрик и отчётов в Ceph Foundation; управляется `ceph telemetry status`. Применяется для глобальных моделей diskprediction и рекомендаций по безопасности.

Список активных и отключенных модулей проверяется командой `ceph mgr module ls`, а включение модуля выполняется через `ceph mgr module enable <module>`.

### Состояния здоровья кластера (Health Status)

| Статус | Описание | Приоритет действий | Как подтвердить |
| :--- | :--- | :--- | :--- |
| **`HEALTH_OK`** | Кластер в норме. | Регулярный сбор метрик. | `ceph status` → `health: HEALTH_OK`. |
| **`HEALTH_WARN`** | Есть некритичные проблемы (деградированные реплики, Nearfull OSD). | Плановое обслуживание (замена дисков, расширение). | `ceph health detail` показывает конкретные коды (например, `OSD_DOWN`, `PG_DEGRADED`, `OSD_NEARFULL`). Подробный разбор — в руководстве [Мониторинга](./monitoring.md). |
| **`HEALTH_ERR`** | Данные недоступны, потерян кворум или диски переполнены (Full OSD). | Аварийное восстановление (Incident Response). | `ceph health detail` + `ceph mon stat` (кворум) + `ceph df` (заполнение). Действия по Full OSD — в [Операциях](./operations.md#8-аварийные-операции-emergency). |

> **Быстрая триада при любом инциденте:** (1) `ceph status` — общая картина; (2) `ceph health detail` — конкретные коды причин; (3) `ceph df` и `ceph osd df tree` — оценка заполнения и равномерности распределения. Только после этого переходите в соответствующее руководство: `operations.md` (жизненный цикл) или `monitoring.md` (наблюдаемость).

## Быстрый старт администратора

Точка входа для инженера, получающего доступ к уже развернутому кластеру `cephadm`. Сначала оценивается *среда и доступ*, затем *состояние*, и только потом принимаются решения об изменениях.

```bash
# 1. Проверка корректности установки клиента и соединения с кластером
ceph --version                    # → ceph version 21.x (Umbrella) и т.п.
ceph status                       # → общее состояние, версия, health

# 2. Инвентаризация хостов, демонов и их распределения по узлам
ceph orch host ls                 # → список управляемых оркестратором хостов
ceph orch ps                      # → статус всех демонов (MON, MGR, OSD, MDS, RGW)
ceph osd tree                     # → иерархия OSD и их состояние (in/out, up/down)

# 3. Оценка ёмкости и равномерности распределения данных
ceph df                           # → общее и использованное пространство по пулам
ceph osd df tree                  # → заполнение каждого диска (для проверки дисбаланса)

# 4. Список пулов и ключевых параметров репликации
ceph osd pool ls detail           # → пулы с параметрами (size, min_size, pg_num)
ceph osd pool autoscale-status    # → что решил pg_autoscaler по количеству PG
```

**Интерпретация результатов:**
*   `health: HEALTH_OK` — кластер исправен, можно работать.
*   Появление `HEALTH_WARN`/`HEALTH_ERR` — см. таблицу выше и разбор в `monitoring.md`/`operations.md`.
*   Если какой-либо узел `host` отсутствует в `ceph orch host ls`, оркестратор теряет над ним контроль — проверьте сеть, SSH-ключи и агента `cephadm`.

> Данные команды — только *первичная* диагностика. Глубокие сценарии: изменение состава кластера — в [Операциях](./operations.md), наблюдаемость и регламентные работы — в [Мониторинге](./monitoring.md).

## Практические сценарии

Административные задачи разделены на две функциональные области:

### 1. Жизненный цикл и операции (Lifecycle)
Сценарии, связанные с активным изменением состава или конфигурации кластера.
*   **Развертывание и расширение:** Добавление новых узлов и дисков через `cephadm`.
*   **Декларативные сервисы:** Управление MDS для CephFS, RGW для S3 и шлюзами NFS/SMB.
*   **Управление пулами:** Настройка факторов репликации и правил CRUSH.
*   **Обновление кластера:** Бесшовный апгрейд версий (например, с Tentacle на Umbrella) через `ceph orch upgrade`.

> **Подробные руководства:** [Операции Ceph: управление компонентами](./operations.md)

### 2. Мониторинг, безопасность и обслуживание
Задачи по поддержанию стабильности и безопасности.
*   **Наблюдаемость (Observability):** Настройка Prometheus, анализ Slow Ops и задержек (Latency).
*   **Целостность данных:** Контроль и планирование Scrubbing / Deep Scrubbing.
*   **Безопасность:** Управление ключами `cephx`, ротация сертификатов и аудит доступа.
*   **Оптимизация емкости:** Управление квотами и очистка "сиротских" данных (orphaned objects).

> **Подробные руководства:** [Мониторинг и обслуживание Ceph](./monitoring.md)
