# Операции Ceph: Жизненный цикл и управление компонентами

Руководство по практическому управлению компонентами кластера RADOS. Документ является основным (авторитетным) справочником для операционных процедур в продуктовых средах Ceph, актуальных для версий **Squid (19.x)**, **Tentacle (20.x)** и **Umbrella (21.x)**.

> **Границы документа:** наблюдаемость, алертинг, скрабинг, задержки и пороги заполнения описаны в [Мониторинге](./monitoring.md); расчёт и автоскейлинг Placement Groups — в [Расчёте PG](../ceph_placement_groups.md); клиентские интерфейсы RBD и CephFS — в разделах `ceph_rbd_usage/` и `cephfs_setup_and_usage/`. Здесь рассматривается управление *самим кластером*: хосты, демоны, конфигурация, ключи, апгрейд и аварийное восстановление.

## Определения

**Операции Ceph** — набор действий по изменению физического или логического состава кластера для обеспечения его масштабируемости, отказоустойчивости и соответствия целевой архитектуре.

**Жизненный цикл компонента** — последовательность состояний демона (OSD, MON, MDS, MGR, RGW) от его регистрации и ввода в эксплуатацию до вывода из работы и очистки ресурсов.

**OSD Out vs Down:**
*   **Out:** Диск исключен из распределения данных (карта CRUSH обновлена), начинается перенос Placement Groups (PG) на другие OSD. Данные физически остаются на диске, но не используются.
*   **Down:** Демон перестал отвечать (сбой процесса, сети или диска), но все еще считается частью кластера. Перенос данных начнется только по истечении `mon_osd_down_out_interval` (по умолчанию 600 секунд).

**Сервисная спецификация (Service Specification)** — YAML-описание желаемого состояния службы: размещение (placement), число экземпляров, параметры. Основной объект декларативного управления в `cephadm`; применяется командой `ceph orch apply`.

**Дренирование (Drain)** — пошаговый вывод компонента из активной работы с предварительной эвакуацией данных. Для OSD — перенос всех PG на другие OSD; для хоста — последовательный вывод всех размещенных на нем демонов.

## Базовые концепции

### Декларативное и императивное управление

В 2026 году основным подходом является декларативный, однако императивный CLI остается необходимым для тонкой настройки и аварийных операций.

1.  **Декларативное (Orchestrator):** Описание желаемого состояния через YAML-спецификации. Оркестратор `cephadm` берет на себя развертывание контейнеров и конфигурацию. Команды: `ceph orch ...`.
2.  **Императивное (Direct CLI):** Прямые команды для немедленного изменения параметров RADOS. Команды: `ceph osd ...`, `ceph mds ...`, `ceph pool ...`.

Пример декларативной спецификации (Drive Group для OSD-сервиса):

```yaml
service_type: osd
service_id: all_nvme
placement:
  label: osd_nvme          # размещать на хостах с этим лейблом
data_devices:
  rotational: false        # только невращающиеся диски (SSD/NVMe)
```

```bash
# Применение спецификации и проверка фактического состояния
ceph orch apply -i spec.yaml
ceph orch ls                              # → список задекларированных служб
ceph orch ps                              # → фактический статус демонов
```

> `cephadm` — единственный поддерживаемый способ развертывания, управления и обновления кластера. Легаси-инструменты `ceph-ansible`/`ceph-deploy` актуальны только для обслуживания старых инсталляций (см. [Установка через ceph-ansible](../ceph_ansible_installation.md)).

### Централизованное управление конфигурацией

При `cephadm` вся конфигурация кластера хранится в **конфигурационной базе данных (config db)** на мониторах. Демоны получают параметры из этой базы при старте и применяют изменения на лету, поэтому правка `/etc/ceph/ceph.conf` на отдельных хостах при `cephadm` — анти-паттерн (файл используется только для загрузки/резервирования и управляется оркестратором).

Ключевое понятие — **скоп (who)**, область действия параметра:

| Скоп | Область |
| :--- | :--- |
| `global` | Все демоны кластера. |
| `mon`, `mgr`, `osd`, `mds`, `client`, `rgw` | Все демоны данного типа. |
| `osd.123`, `mon.host1`, `client.rbd` | Конкретный демон или клиент. |

Приоритет разрешения: конкретный скоп → тип демона → `global` → локальный `ceph.conf`. Это позволяет задать общекластерное значение, а затем точечно переопределить его для одного OSD.

Основные команды:

```bash
ceph config dump                          # → вся конфигурация кластера
ceph config get osd osd_max_backfills     # → действующее значение параметра
ceph config set osd osd_max_backfills 1   # → применить всем OSD (на лету)
ceph config rm osd osd_max_backfills      # → сбросить к значению по умолчанию
ceph config log                           # → журнал изменений конфигурации
ceph config assimilate-conf -i ceph.conf  # → импорт легаси-конфига в config db
```

Большинство параметров применяются динамически, без рестарта. Критичные (например, сетевые адреса, пулы хранения кластера) требуют перезапуска демона. Практические сценарии — в разделе [10. Централизованное управление конфигурацией](#10-централизованное-управление-конфигурацией).

### Флаги обслуживания (Maintenance Flags)

Перед проведением работ на узлах (перезагрузка, замена оборудования) необходимо установить флаги, чтобы предотвратить нежелательный массовый перенос данных (rebalancing):

| Флаг | Назначение |
| :--- | :--- |
| **noout** | Предотвращает автоматический вывод OSD из состояния `in` при потере связи. |
| **noscrub** | Отключает фоновую проверку целостности (Scrubbing). |
| **nodeep-scrub** | Отключает глубокую проверку контрольных сумм. |
| **norecover** | Приостанавливает текущее восстановление деградированных данных. |
| **nobackfill** | Приостанавливает копирование данных на новые или пустые OSD. |
| **noin** | Предотвращает автоматический возврат OSD в состояние `in` после `up` (ручное управление составом). |
| **nodown** | Запрещает MON помечать OSD как `down` (применять с крайней осторожностью). |
| **noup** | Запрещает MON помечать OSD как `up` (применять с крайней осторожностью). |
| **pause** | Останавливает все операции чтения/записи кластера (для консистентных offline-процедур). |

Флаги можно выставлять глобально (`ceph osd set <flag>`) или для группы OSD (`ceph osd set-group <flag> <osd ids>`), что полезно, когда окружение затрагивает только часть хостов, а не весь кластер. Проверка активных флагов:

```bash
ceph osd dump | grep -E '^flags|osd\.flag'
# → flags noout,noscrub,nodeep-scrub   (пример частично установленных флагов)
```

> **Критично:** флаги **не снимаются сами**. Их забвение приводит к тому, что после аварийной потери диска данные не перераспределяются, а кластер работает с пониженной избыточностью. Флаг снимается той же командой `ceph osd unset <flag>`.

### Жизненный цикл OSD: состояния и префлайт-проверки

OSD описывается двумя парами состояний:

*   `in` / `out` — участвует ли OSD в распределении данных (запись в карту CRUSH).
*   `up` / `down` — отвечает ли демон (процесс запущен, сеть доступна).

Дополнительно существует состояние `destroyed` (OSD помечен уничтоженным с сохранением ID для переиспользования при замене) и `stopped` (остановлен оркестратором).

Перед операциями, влияющими на доступность реплик, `cephadm` требует явного подтверждения безопасности. Две ключевые префлайт-команды:

```bash
# Можно ли остановить/перезапустить OSD без нарушения доступности PG (min_size)?
ceph osd ok-to-stop <osd_id>

# Можно ли уничтожить OSD *без* предварительной миграции данных?
ceph osd safe-to-destroy <osd_id>
```

Они анализируют карту распределения и предупреждают, если операция приведет к деградации ниже `min_size`. Игнорирование этих проверок («человеческий фактор») — главная причина аварий при выводе оборудования.

### Аутентификация CephX: модель доступа

Кластер по умолчанию защищён аутентификацией **CephX** (не путать с шифрованием: ключи аутентифицируют соединения, данные на диске не шифруются CephX).

*   Учетная запись клиента имеет вид `client.<имя>` (например, `client.admin`, `client.rbd`).
*   Права задаются **capabilities (caps)** отдельно для каждого типа сервиса: `mon`, `osd`, `mgr`, `mds`. В caps указываются права (например, `allow rw`) и, при необходимости, ограничения по пулам (`pool=volumes`).
*   Существуют готовые профили: `profile rbd`, `profile cephfs`, `profile osd`, `profile mds` — они упрощают выдачу типовых прав.
*   Ключи хранятся централизованно в config db мониторов и раздаются клиентам файлом keyring (`/etc/ceph/ceph.client.<name>.keyring`).

Практическое управление ключами с точки зрения администратора кластера — в разделе [9. Управление ключами доступа (CephX)](#9-управление-ключами-доступа-cephx); настройка клиентской стороны RBD и CephFS описана в соответствующих руководствах.

### Ограничение влияния операций на производительность

Любая массовая операция (перебалансировка, backfill, восстановление после потери OSD) конкурирует за дисковой ввод-вывод и сеть с клиентским трафиком. В высоконагруженных кластерах её влияние ограничивают лимитами восстановления:

```bash
# Притормозить recovery/backfill (например, перед отправкой в prod-трафик)
ceph config set osd osd_max_backfills 1
ceph config set osd osd_recovery_max_active 2
ceph config set osd osd_recovery_sleep 0.1

# Вернуть значения по умолчанию
ceph config rm osd osd_max_backfills
ceph config rm osd osd_recovery_max_active
ceph config rm osd osd_recovery_sleep
```

В версиях v17+ планировщик **mclock** (Quality-of-Service-планировщик) автоматически приоритизирует recovery-процессы относительно клиентских операций через профили (`osd_mclock_profile`, например `balanced`, `high_recovery_ops`). В «старых» кластерах или при тонкой настройке ручные лимиты остаются основным инструментом влияния на параллельность переноса данных.

## Практические сценарии

### Предварительные требования

*   Доступ к admin-хосту с рабочим ключом `client.admin` (`/etc/ceph/ceph.client.admin.keyring`) и командой `ceph` (пакет `ceph-common`).
*   Кластер развернут через `cephadm` и оркестратор работает (проверка: `ceph orch status`).
*   Все узлы, с которыми работает оркестратор, доступны по SSH (root или `sudo`) с admin-хоста.
*   Перед любой изменяющей операцией: `ceph -s` в состоянии `HEALTH_OK`, без критичных кодов в `ceph health detail`.

### 1. Жизненный цикл хоста: добавление, обслуживание, вывод

#### 1.1 Режим обслуживания узла

```bash
# Установка флагов (глобально)
ceph osd set noout
ceph osd set noscrub
ceph osd set nodeep-scrub

# Перевод хоста в режим обслуживания через оркестратор
# Это автоматически остановит демоны корректно
ceph orch host maintenance enter <hostname>

# --- Выполнение работ (например, обновление ядра или замена RAM) ---

# Выход из режима обслуживания
ceph orch host maintenance exit <hostname>

# Снятие флагов
ceph osd unset noout
ceph osd unset noscrub
ceph osd unset nodeep-scrub
```

**Как это работает:** команда `ceph orch host maintenance enter` останавливает на хосте все Ceph-демоны через управляемый `systemd`-target и применяет `noout` к OSD-поддереву хоста. Для хостов без OSD флаги можно не выставлять. Вход в режим блокируется, если операция небезопасна (например, приведет к потере кворума MON) — в этом случае используется ручная процедура через дренирование (раздел 1.3) или флаг принуждения `ceph orch host maintenance enter <hostname> --force` (с полным пониманием рисков).

**Валидация после работ** (обязательна):

```bash
ceph orch host ls --host-status maintenance   # → статус maintenance/'' 
ceph orch ps --hostname <hostname>            # → все демоны up/active
ceph status                                   # → health: HEALTH_OK
ceph pg stat                                  # → PGs: ... active+clean
```

Для хостов с OSD убедитесь, что после выхода из maintenance OSD вернулись в `up` и `in` (`ceph osd tree`), а кластер завершил backfill.

#### 1.2 Добавление нового хоста

```bash
# 1. Распространение SSH-ключа оркестратора на новый узел
ssh-copy-id -i /etc/ceph/ceph.pub root@<new-host-fqdn>

# 2. Регистрация хоста (адрес и лейблы задаются сразу)
ceph orch host add <new-host-fqdn> --labels=osd_nvme

# 3. Проверка регистрации
ceph orch host ls                          # → новый хост появляется в списке
ceph orch ps --hostname <new-host-fqdn>    # → демонов пока нет (вновь добавлен)

# 4. Развертывание служб — как правило, OSD:
ceph orch apply osd --all-available-devices --dry-run   # предпросмотр дисков
ceph orch apply osd --all-available-devices             # фактическое создание

# 5. Контроль появления OSD в кластере и начала ребалансировки
ceph osd tree                             # → новые OSD up/in
ceph -s                                   # → PG активны, идёт rebalancing
```

**Требования к новому хосту:** fully-qualified hostname, резолвится со всех узлов; на хосте установлен и доступен `sudo`/root и пакет `cephadm` (или принудительно копируется оркестратором); для OSD — свободные диски без данных.

Лейблы используются в placement-спецификациях (см. раздел «Базовые концепции»). Управление лейблами существующего хоста:

```bash
ceph orch host label add <hostname> <label>
ceph orch host label rm <hostname> <label>
ceph orch host ls --label <label>
```

#### 1.3 Вывод хоста из эксплуатации (drain и удаление)

```bash
# Дренирование: вывести все демоны и эвакуировать все OSD хоста
ceph orch host drain <hostname>

# Контроль прогресса эвакуации OSD
ceph orch osd rm status

# После завершения: на хосте не должно остаться демонов
ceph orch ps --hostname <hostname>

# Удаление хоста из-под управления оркестратора
# (--rm-crush-entry дополнительно удаляет bucket хоста из карты CRUSH)
ceph orch host rm <hostname> [--rm-crush-entry]
```

**Нюансы и edge cases:**

*   `ceph orch host drain` помечает хост лейблом `_no_schedule` (новые демоны не размещаются) и планирует удаление всех OSD. Удаление Ceph-конфигурации и keyring с хоста выполняется по умолчанию; для их сохранения добавьте флаг `--keep-conf-keyring`.
*   Остановившиеся на хосте демоны MON/MGR после drain либо переносятся (`ceph orch daemon move`), либо удаляются; при потере кворума MON вывод такого хоста блокируется до добавления монитора на другой узел.
*   Если хост физически недоступен (упал безвозвратно), удаление выполняется принудительно: `ceph orch host rm <hostname> --offline --force` (предварительно `ceph orch host drain` выполнить нельзя — данные эвакуируются по мере оживления OSD на других путях или остаются до восстановления оборудования).

> При плановом выводе целого кластера (переезд в другой ЦОД, полный аудит) используйте процедуру плановой остановки из пункта 1.4, а не поочерёдный drain.

#### 1.4 Плановая остановка и запуск всего кластера

Для плановых длительных остановок (переезд, отключение питания ЦОД) `cephadm` предоставляет штатную пару команд:

```bash
# Остановка (выполняется с admin-хоста)
cephadm cluster-stop --fsid <cluster-fsid>

# Запуск (аналогично, с admin-хоста)
cephadm cluster-start --fsid <cluster-fsid>
```

`cluster-stop` последовательно: проверяет health, приостанавливает оркестратор, выставляет `noout`, «выбивает» CephFS (fail) во избежание клиентского I/O, корректно останавливает демоны и хосты. `cluster-start` запускает кластер в обратном порядке и ожидает, пока все PG не вернутся в `active+clean`, после чего снимает `noout`.

> Это **единственный правильный** способ полной остановки: ручная остановка отдельных демонов или массовое `ceph orch stop` не гарантирует консистентного порядка и восстановления. FSID смотрится командой `ceph status` (`cluster id:`) или в `/etc/ceph/ceph.conf`.

### 2. Управление OSD (Классические и Crimson)

#### 2.1 Добавление OSD

```bash
# Развертывание OSD на всех свободных дисках кластера
ceph orch apply osd --all-available-devices

# Предпросмотр того, что будет создано, без изменений
ceph orch apply osd --all-available-devices --dry-run

# Точечное создание OSD на конкретном устройстве
ceph orch daemon add osd <hostname>:<device_path>

# Проверка
ceph osd tree                         # → новые OSD в статусе up/in
ceph orch ps --daemon-type osd
```

При использовании Drive Group / OSDSpec `cephadm` сам обнаруживает новые диски и разворачивает на них OSD. Если управление дисками должно быть полностью ручным, спецификация помечается `unmanaged: true`.

#### 2.2 Замена диска (BlueStore)

```bash
# 1. Пометить OSD на удаление (запуск эвакуации данных)
ceph orch osd rm <osd_id> --replace

# 2. Мониторинг статуса (безопасно вынимать диск только после завершения)
ceph orch osd rm status

# 3. Физическая замена. Если используется Drive Group, Ceph сам увидит новый диск.
# Иначе - добавить вручную:
ceph orch daemon add osd <hostname>:<device_path>
```

**Как работает `--replace`:** OSD не удаляется из карты CRUSH, а помечается флагом `destroyed` (ID резервируется). Когда на тот же хост устанавливается новый диск, совпадающий с OSDSpec, оркестратор автоматически пересоздаёт OSD со **прежним ID** — это сохраняет неизменной карту CRUSH и права пулов.

В актуальных версиях (Tentacle+/Umbrella) присутствует полностью автоматическая команда замены устройства:

```bash
# Автоматическая замена диска под osd.3 (только LVM-развернутые OSD)
ceph orch device replace osd.3 <device>

# Если устройство общее (DB/WAL сразу для нескольких OSD), оркестратор
# предупредит о сопутствующих OSD. Принудительный снос общего устройства:
ceph orch device replace osd.3 <device> --yes-i-really-mean-it
```

Оркестратор сам выполняет `ceph-volume zap` всех связанных устройств, помечает диск как «being replaced» (не разворачивает OSD повторно до вставки нового) и пересоздаёт OSD после установки нового диска. Очистка ошибочно установленного заголовка замены: `ceph orch device replace <hostname> <device> --clear`.

#### 2.3 Удаление OSD без замены

```bash
# Префлайт: безопасно ли уничтожать без миграции данных
ceph osd safe-to-destroy <osd_id>

# Удаление через оркестратор (эвакуация PG → удаление → затирание диска)
ceph orch osd rm <osd_id> [--zap]
ceph orch osd rm status                     # → прогресс эвакуации
```

*   `--zap` — стирает LVM и информацию о разделах устройства (blank slate для переиспользования).
*   `--force` — пропускает проверку безопасности (используйте, когда знаете, что PG на OSD нет).

Классический ручной путь (когда оркестратор недоступен или требуется точный контроль):

```bash
# 1. Исключить OSD из распределения данных
ceph osd out <osd_id>

# 2. Дождаться полного переноса всех PG на другие OSD
ceph pg dump_stale | grep "active+clean"    # и осмотреть ceph -w
ceph osd safe-to-destroy <osd_id>           # подтверждает завершение

# 3. Уничтожить и удалить из карт
ceph osd destroy <osd_id> --yes-i-really-mean-it
ceph osd purge <osd_id> --yes-i-really-mean-it
```

> Работа с группой OSD одного хоста выполняется перечислением ID: `ceph orch osd rm 2 5 7 --zap`. Операции необратимы — после удаления данные диска невосстановимы (если не был выполнен `--replace` и диск не извлечён физически).

#### 2.4 Специфика Crimson OSD (v20+)

Crimson разворачивается с флагом `--crimson`. Он не поддерживает FileStore и работает только с BlueStore или напрямую через SeaStar.

```bash
# Декларативное развертывание Crimson на всех свободных NVMe
ceph orch apply osd --all-available-devices --crimson
```

Crimson предназначен для NVMe-хранилищ с минимальной задержкой; его мониторинг (утилизация реакторов SeaStar, специальные метрики) описан в разделе [Мониторинга](./monitoring.md#1-мониторинг-crimson-osd-и-nvme). Перед внедрением Crimson в продуктивной среде проверьте перечень поддерживаемых функций версии — часть возможностей (например, не для всех режимов записи) ещё догоняет классический BlueStore.

### 3. Управление MON и MGR

Контрольная плоскость кластера: **MON** поддерживают карты кластера и кворум через Paxos, **MGR** — модули автоматизации (dashboard, balancer, pg_autoscaler) и работает в паре active/standby (кворума у MGR нет).

```bash
# Состав мониторов и состояние кворума
ceph mon stat
ceph quorum_status --format json-pretty

# Декларативное задание размещения мониторов (рекомендуемый способ в cephadm)
ceph orch apply mon --placement="3 host-a host-b host-c"

# Императивное изменение monmap (обычно не требуется, если задан placement)
ceph mon add <name> [v2addr] [v1addr]
ceph mon remove <name>
```

**Правила отказоустойчивости:**

*   Число MON — всегда нечетное; для production минимум 3, для крупных кластеров — 5. Падение до 2 из 3 переводит кластер в режим «только чтение» (нет кворума).
*   MON размещаются в разных фейл-доменах (разные стойки/хосты) — объединение всех MON в одном физическом месте сводит на нет смысл кворума.
*   Никогда не удаляйте MON, если это может сократить кворум ниже 50% (процедура аварийного восстановления — в разделе [8.2](#82-потеря-кворума-mon)).

```bash
# MGR: минимум 2 экземпляра (active + standby)
ceph orch apply mgr --placement=2
ceph mgr stat
ceph orch ps --daemon-type mgr
```

**Фейловер MGR** автоматический: при отказе active-мгр роль переходит к standby без вмешательства администратора. Единственный MGR в кластере — вырожденная конфигурация без отказоустойчивости (допустима только в тестовых средах).

После изменения состава MON или MGR проверяйте `ceph status` (секция `mon: 3/3 daemons up`) и `ceph mgr stat`.

### 4. Управление MDS для CephFS

```bash
# Просмотр текущего состояния файловых систем и рангов MDS
ceph fs status
ceph mds stat

# Увеличение количества активных MDS для масштабирования производительности
ceph fs set <fs_name> max_mds 2

# Создание MDS через спецификацию (Placement)
ceph orch apply mds <fs_name> --placement="3 node1,node2,node3"

# Гарантировать наличие резервных MDS (горячий standby для мгновенного failover)
ceph fs set <fs_name> standby_count_wanted 1
```

**Пояснение:** ранги MDS — независимые «потоки» метаданных; `max_mds` задаёт максимальное число активных рангов, `standby_count_wanted` — число резервных экземпляров. Режим `standby-replay` позволяет резервному MDS держать журнал реплицированным для мгновенного переключения. Создание самой файловой системы (пулы метаданных/данных, `ceph fs new`) и работа с субтомами описаны в [Практических сценариях CephFS](../cephfs_setup_and_usage/practical_scenarios.md); детальная настройка кэшей и балансировки — в [Продвинутых темах CephFS](../cephfs_setup_and_usage/advanced_topics.md).

### 5. Управление сетевыми шлюзами (RGW, NFS, Ingress)

В 2026 году шлюзы разворачиваются как сервисы `cephadm` и объединяются точками входа (Ingress-модуль).

```bash
# Развертывание S3 шлюза (RGW) с балансировщиком нагрузки
# Это создаст виртуальный IP (VIP) через Keepalived + HAProxy
ceph orch apply ingress rgw.<service_id> --virtual-ip <ip_address> --frontend-port 80
```

Декларативная спецификация сервиса RGW:

```yaml
service_type: rgw
service_id: rgw.s3
placement:
  hosts: [node1, node2, node3]
spec:
  frontend_port: 80
```

```bash
# Применение спецификации и управление сервисом
ceph orch apply -i rgw.yaml
ceph orch ls --service_type rgw            # → статус всех RGW-сервисов
ceph orch apply rgw rgw.s3 --placement="3 node1,node2,node3"   # масштабирование
ceph orch rm rgw.s3                        # удаление сервиса
```

**Ingress-слой:** модуль объединяет несколько экземпляров RGW или NFS за одним виртуальным IP (Keepalived + HAProxy). Выход из строя одного шлюза не прерывает клиентский доступ. Для протоколов SMB и NFS существуют соответствующие модули `cephadm` (`smb`, `nfs`) с аналогичным объявлением. Мониторинг шлюзов — в [Мониторинге](./monitoring.md#6-наблюдаемость-сетевых-шлюзов-rgw-nfs-smb).

### 6. Манипуляции с топологией CRUSH и балансировка

```bash
# Просмотр физической иерархии (Buckets)
ceph osd tree

# Перемещение хоста в другую логическую корзину (например, из стойки в стойку)
ceph osd crush move <hostname> rack=<rack_name>

# Ручное изменение веса (только если отключен balancer)
ceph osd crush reweight osd.<id> <weight>
```

**Классы устройств:** OSD можно группировать по классам (`hdd`, `ssd`, `nvme`), создавая «тир» хранения и целенаправленно размещая пулы на определенном типе дисков:

```bash
# Список классов и привязка OSD к классу
ceph osd crush class ls
ceph osd crush set-device-class nvme osd.10

# Правило размещения с фейл-доменом «host» в классе nvme
ceph osd crush rule create-replicated nvme_hosts default host nvme

# Применение правила к пулу
ceph osd pool set <pool_name> crush_rule nvme_hosts
```

**Балансировка (`balancer`, модуль MGR):** автоматическое перераспределение данных через `upmap` предпочтительнее ручных реweight-манипуляций:

```bash
ceph balancer status          # → текущий дисбаланс и режим
ceph balancer mode upmap      # → поосевой режим точечной балансировки
ceph balancer execute         # → применить следующее рассчитанное перераспределение
ceph balancer eval            # → оценка равномерности распределения
```

Разовый пересчёт весов по фактической утилизации (ручной, не работает одновременно с balancer):

```bash
ceph osd reweight-by-utilization
```

### 7. Управление пулами и их безопасностью

```bash
# Создание пула (рекомендуется доверять pg_autoscaler)
ceph osd pool create <pool_name> replicated

# Включение защиты от случайного удаления (обязательно для production)
ceph osd pool set <pool_name> nodelete true

# Установка квоты на объем данных в пуле
ceph osd pool set-quota <pool_name> max_bytes 10T
```

Расширенное управление пулами:

```bash
# Полная информация по всем пулам (size, min_size, pg_num, crush_rule, application)
ceph osd pool ls detail

# Параметры репликации
ceph osd pool set <pool_name> size 3
ceph osd pool set <pool_name> min_size 2

# Привязка пула к приложению (снимает HEALTH_WARN POOL_APP_NOT_ENABLED)
ceph osd pool application enable <pool_name> rbd

# Переименование пула
ceph osd pool rename <old_name> <new_name>
```

**Удаление пула — необратимая операция:**

```bash
# Требуется двойное указание имени и подтверждение
ceph osd pool delete <pool_name> <pool_name> --yes-i-really-really-mean-it
```

Перед удалением: убедитесь в отсутствии клиентов и снапшотов, для пулов CephFS — предварительно удалите файловую систему (`ceph fs rm <fs> --yes-i-really-mean-it` со снятием зависимостей), для пулов RBD — сначала удалите образы (`rbd rm`). Подробности расчёта и автоскейлинга PG — в [Расчёте PG](../ceph_placement_groups.md).

### 8. Аварийные операции (Emergency)

#### 8.1 Обработка Full OSD (95%)

Если запись заблокирована, необходимо временно поднять пороги, чтобы удалить лишние данные.

```bash
# Просмотр текущих лимитов
ceph osd dump | grep ratio

# Временное поднятие лимита (КРАЙНЕ ОСТОРОЖНО!)
ceph osd set-full-ratio 0.97

# После удаления данных или расширения кластера - ВЕРНУТЬ НАЗАД
ceph osd set-full-ratio 0.95
```

> **Важно:** достижение `full_ratio` (по умолчанию 0.95) блокирует **все** записи кластера, включая внутренний recovery. План действий: приоритетно освободить место (очистить устаревшие снапшоты, удалить ненужные образы/объекты), при необходимости временно поднять порог, и **обязательно** вернуть его прежнее значение. Порог `nearfull` (0.85) — нормальный триггер планового масштабирования, а не критического реагирования.

#### 8.2 Потеря кворума MON

Кворум MON теряется, когда доступно менее половины мониторов. Симптом — `ceph status` сообщает об отсутствии кворума, команды кластера «зависают».

**Диагностика:**

```bash
ceph -s                                   # → нет quorum, "no mon quorum"
ceph mon stat                             # → список MON и их доступность
ceph quorum_status --format json-pretty   # → состав кворума
ceph daemon mon.<hostname> mon_status     # → состояние конкретного MON (probing/electing/leader/peon)
journalctl -u ceph-mon@* 2>/dev/null | tail   # → логи MON на хосте
```

**Путь А — сохранился хотя бы один здоровый MON.** Восстановите остальные MON из кворума штатными средствами: пересоздайте MON на прежнем или новом хосте (`ceph orch apply mon --placement=...`), здоровые MON синхронизируют store. Если проблемы наблюдаются в monmap-е одного MON, его monmap можно актуализировать из живого кворума:

```bash
ceph mon getmap -o /tmp/monmap.bin
ceph-mon -i <id> --inject-monmap /tmp/monmap.bin   # выполняется на остановленном MON
```

**Путь Б — кворум потерян полностью, без бэкапа store.** Основной официальный метод — восстановление store-а из данных OSD (см. руководство по восстановлению MON). Обобщенная последовательность для `cephadm`:

```bash
# 1. Остановить ВСЕ демоны кластера (иначе OSD будут мешать сбору карт)
# 2. С каждого OSD-хоста собрать osdmap через cephadm shell:
#    cephadm shell -- ceph-objectstore-tool --data-path /var/lib/ceph/<fsid>/osd.<id> \
#      --type bluestore --op get-osdmap --out /tmp/mon-store/...
# 3. Собрать все карты в единый /tmp/mon-store и пересобрать store монитора:
cephadm shell -- ceph-monstore-tool /tmp/mon-store rebuild \
  -- --keyring /etc/ceph/ceph.client.admin.keyring --mon-ids mon.a mon.b mon.c
# 4. Развернуть полученный store на первом MON, запустить его, затем скопировать
#    store.db на остальные MON и запустить их.
```

**Критично знать после восстановления:** в пересобранном store повреждаются/теряются config db, записи auth (ключи), сервисные спецификации, image config и данные telemetry — их нужно пересоздать из резервной копии (раздел [12. Резервное копирование состояния кластера](#12-резервное-копирование-состояния-кластера-и-откат)), а после этого заново развернуть MDS/RGW и остальные сервисы. Поэтому бэкап состояния — обязательная практика, а **восстановление из данных OSD — это минимум две пары рук и чек-лист** (см. официальное [Troubleshooting Monitors](https://docs.ceph.com/en/latest/rados/troubleshooting/troubleshooting-mon/)).

**Путь В — есть недавний пер-мониторный бэкап store** (см. раздел 12). Восстановление: остановить мониторы, восстановить каждый MON из *своего* бэкапа (`ceph-mon -i <id> --restore-backup <path> --yes-i-really-mean-it`), запустить большинство; урезать monmap до выживших через `monmaptool`, если часть MON безвозвратно потеряна.

#### 8.3 PG в состоянии `incomplete` и «застрявшее» восстановление

*   `PG incomplete` означает, что все OSD, хранившие PG, вышли из строя и данных недоступны — это потеря данных определённого объёма. Диагностика и статусы PG описаны в [Расчёте PG](../ceph_placement_groups.md); восстанавливается только возвратом оборудования или из резервной копии.
*   «Застрявшее» восстановление (PG долго не переходят `active+clean`) обычно вызывается оставленными флагами `norecover`/`nobackfill`, превышением `backfillfull_ratio` на целевых OSD или нехваткой ресурсов. Снимать флаги — `ceph osd unset norecover`, регулировать параллельность — см. раздел «Ограничение влияния операций на производительность».

### 9. Управление ключами доступа (CephX)

Управление учетными записями клиентов с точки зрения кластерного администратора:

```bash
# Список всех учетных записей и их прав
ceph auth ls

# Создание/получение ключа (пример — клиент RBD для пула volumes)
ceph auth get-or-create client.rbd \
  mon 'profile rbd' \
  osd 'profile rbd pool=volumes' \
  mgr 'profile rbd pool=volumes'

# Экспорт ключа в файл keyring (для передачи на клиент или в секреты)
ceph auth get client.rbd -o client.rbd.keyring
ceph auth print-key client.rbd            # → печать только секретного ключа

# Изменение caps (без смены ключа)
ceph auth caps client.rbd \
  mon 'profile rbd' \
  osd 'allow rw pool=volumes, allow rw pool=vms'

# Ротация: пересоздать ключ с теми же caps (старый ключ перестает действовать)
ceph auth get-or-create client.rbd -o client.rbd.new.keyring \
  mon 'profile rbd' \
  osd 'profile rbd pool=volumes'

# Полная отзыв доступа
ceph auth rm client.rbd
```

**Синтаксис caps:** базовые права `allow r` / `allow rw` / `allow rwx` и готовые профили (`profile rbd`, `profile cephfs`, `profile osd`, `profile mds`). Ограничение по пулу — `pool=<имя> или список через запятую`; для монтирования с разграничением по директориям CephFS используются `path=` (см. [Практические сценарии CephFS](../cephfs_setup_and_usage/practical_scenarios.md)).

> Ротация ключей влияет на *новые* подключения; существующие клиентские сессии продолжают работать до переподключения. Обновление keyring на клиентах включает замену файла `/etc/ceph/ceph.client.<name>.keyring` и перемонтирование/пересоздание подключений (для RBD — unmap/map). Никогда не храните ключи в документации/скриптах открыто; в Kubernetes используйте Secrets (Rook/CSI — раздел [PV/PVC Scenarios](../../pv_and_pvc_scenarios.md)).

### 10. Централизованное управление конфигурацией

Практическое применение концепций из одноименного раздела выше:

```bash
# Полный дамп действующей конфигурации
ceph config dump

# Действующее значение параметра для конкретного скопа
ceph config get osd.12 osd_max_backfills

# Применение: глобально, по типу демона, точечно
ceph config set global mon_allow_pool_delete false
ceph config set osd osd_max_backfills 1
ceph config set osd.7 osd_memory_target 8G

# Откат параметра к значению по умолчанию
ceph config rm osd.7 osd_memory_target

# Импорт legacy-конфигурации в config db (извлекает неуправляемые настройки)
ceph config assimilate-conf -i /tmp/legacy.conf

# Историческая справка об изменениях
ceph config log | tail
```

**Аудит и поддержка:** перед изменением параметров фиксируйте исходное значение (`ceph config get`), после внесения изменений контролируйте влияние через `ceph -w`/`ceph status`. Большинство параметров применяются на лету; для параметров, требующих рестарта, логи сообщают «setting ... , restart required», после чего демон рестартуется оркестратором (`ceph orch daemon restart <daemon>`).

### 11. Обновление версий кластера (cephadm upgrade)

**Принцип:** обновление через `cephadm` — rolling-процесс (демон за демоном) в строгом порядке `mgr → mon → crash → osd → mds → rgw → ...`. Каждый демон перезапускается только после подтверждения, что кластер не потеряет доступность. `cephadm` автоматически выставляет флаг `noout` на время обновления и приостанавливает активность pg_autoscaler'а (если иное не задано). Во время апгрейда допустимо появление `HEALTH_WARN`.

```bash
# 1. Предварительная проверка
ceph -s                                     # → HEALTH_OK
ceph versions                               # → текущие версии по типам демонов
ceph orch upgrade status                    # → должен быть пустым (нет активного апгрейда)
ceph orch upgrade ls                        # → доступные целевые версии

# 2. Запуск (одна мажорная версия за раз!)
ceph orch upgrade start --ceph-version 21.2.1

# 3. Наблюдение
ceph orch upgrade status
ceph -w                                     # → поток событий

# 4. Управление процессом
ceph orch upgrade pause                     # приостановить (хост недоступен, health упал)
ceph orch upgrade resume
ceph orch upgrade stop                      # отменить

# 5. Откат (downgrade) на предыдущую версию — отдельной командой
ceph orch upgrade start --ceph-version 20.2.x

# 6. Контроль результата
ceph versions                               # → все демоны на целевой версии
ceph orch ps                                # → контейнеры обновлены, сервисы активны
```

**Ограничение охвата** (staggered upgrade, доступно в новых версиях): можно обновить только часть демонов параметрами `--daemon-types`, `--services`, `--hosts`, `--limit` (например, `ceph orch upgrade start --image <image> --daemon-types mgr,mon --hosts node1,node2`).

**Лучшие практики апгрейда:**

*   Обновляйте **за одну мажорную версию**, минимум в запланированном окне, с резервной копией состояния (раздел 12) и планом отката.
*   До старта все хосты online, кластер `HEALTH_OK`; недоступный хост автоматически приостанавливает апгрейд.
*   Не запускайте параллельно собственные операции (замена OSD, изменение CRUSH) — только одна «волна» изменений.
*   После завершения снимите `noout` (если оркестратор не сделал это сам) и проверьте `ceph health detail`.

Подробности и ограничения — в официальном [руководстве по обновлению Cephadm](https://docs.ceph.com/en/latest/cephadm/upgrade/).

### 12. Резервное копирование состояния кластера и откат

Карты, конфигурация и ключи не восстанавливаются из самих OSD автоматически. Регулярный бэкап состояния позволяет быстро восстановить мониторинг-инфраструктуру, сервисы и контроль после аварии, не изобретая её заново.

```bash
# Снимок состояния кластера в файлы (выполнять регулярно, например перед апгрейдом)
DATE=$(date +%F)
ceph config dump -f json-pretty        > ceph-config-${DATE}.json
ceph auth export -o ceph-auth-${DATE}.export
ceph -s -f json-pretty                 > ceph-status-${DATE}.json
ceph mon dump -f json-pretty           > ceph-monmap-${DATE}.json
ceph osd getcrushmap -o ceph-crushmap-${DATE}.bin
ceph orch ls --export -o ceph-specs-${DATE}.yaml   # полный экспорт сервисных спецификаций
```

**Бэкап store монитора** (пер-мониторный, необязателен при полноценных OSD-восстановлениях, но даёт быстрый seed): бэкап выполняется на остановленном MON:

```bash
ceph orch daemon stop mon.<hostname>            # остановить MON (cephadm)
rsync -aHP /var/lib/ceph/<fsid>/mon.<hostname>/store.db /backup/ceph/mon-<hostname>/
ceph orch daemon start mon.<hostname>           # вернуть MON в работу
```

**Откат/восстановление:** восстановление отдельных MON из бэкапа — см. раздел [8.2](#82-потеря-кворума-mon) (путь В); восстановление config/auth/spec-ов после полной потери store — команды из этого раздела выполняются в обратном направлении (`ceph config assimilate-conf`, импорт auth-экспорта, применение `ceph orch apply -i`). Храните бэкапы состояния офлайн от кластера (отдельный хост/хранилище).

> Официальная рекомендация: при полной потере store **противопоказано** восстанавливать старый store поверх текущего состояния — предпочтителен пересбор из текущего состояния OSD (раздел 8.2, путь Б) либо свежий бэкап. Бэкап состояния — это страховка от потери *конфигурации и контроля*, а не способ откатить «старые данные».

## Troubleshooting (типичные проблемы операций)

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `ceph orch osd rm` «завис», PG не мигрируют | Оставлены флаги `norecover`/`nobackfill`; низкая параллельность; целевые OSD в `backfillfull` | `ceph orch osd rm status`, `ceph osd dump`, `ceph pg dump_stale` | Снять флаги (`ceph osd unset norecover`), повысить `osd_max_backfills`/`osd_recovery_max_active`, расширить/освободить ёмкость |
| Апгрейд остановлен на «waiting for healthy daemons» | Хост offline или health не `HEALTH_OK` | `ceph orch upgrade status`, `ceph health detail`, `ceph orch host ls --host-status` | Вернуть хост/устранить health, `ceph orch upgrade resume`. При затянувшемся сбое — `ceph orch upgrade stop` |
| `ceph orch host maintenance enter` отклонён | На хосте критичные демоны (MON/OSD с данными) | `ceph orch log watch`, `ceph orch ps`, `ceph osd tree` | Дренировать OSD (`ceph orch host drain`) или `--force`/`--yes-i-really-mean-it` с пониманием риска |
| MON в состоянии `probing`, вне кворума | Повреждение store, устаревший/повреждённый monmap, `CLOCK_SKEW` | `ceph daemon mon.<id> mon_status`, логи MON, `chronyc tracking` | см. раздел [8.2](#82-потеря-кворума-mon) |
| `ceph config set` не применяется | Неверный скоп (`who`) или конфликт приоритетов | `ceph config dump`, `ceph config get <who> <key>` | Уточнить скоп (`osd.<id>`, `client.<name>`, `global`) |
| `POOL_APP_NOT_ENABLED` после создания пула | Пул не привязан к приложению | `ceph osd pool ls detail` | `ceph osd pool application enable <pool> rbd\|cephfs\|rgw` |
| `ceph auth` не видит/не может менять ключи | Нет прав на чтение ключей (`caps` на `mon`) | `ceph auth ls`, проверка caps `client.admin` | Выдать корректные caps; восстановить admin-ключ из бэкапа (раздел 12) |
| PG в `backfill_toofull`, клиентские записи блокируются | Целевые OSD достигли `backfillfull_ratio` (0.9) | `ceph osd df tree`, `ceph health detail` | Освободить ёмкость/расширить кластер; временно `ceph osd set nobackfill` — только после анализа |

## Лучшие практики (Best Practices)

*   **Префлайт перед любыми изменениями:** `ceph -s` → `HEALTH_OK`, `ceph health detail` без критичных кодов. При `HEALTH_ERR` сначала диагностика (см. [Индекс администрирования](./index.md#состояния-здоровья-кластера-health-status)), затем изменения.
*   **Работайте с бэкапом состояния.** Перед деструктивными операциями и апгрейдом — снимок конфигурации/ключей/спецификаций (раздел 12). Восстановление «на голом месте» в боевом кластере — это часы простоя.
*   **Флаги — только на время работ, и снимайте сразу.** Контролируйте снятие через `ceph osd dump`. Забытый `noout` тихо лишает кластер самовосстановления при следующем отказе диска.
*   **Кворум MON неприкосновенен.** Минимум 3 (для крупных кластеров — 5) MON в разных фейл-доменах; не выводите MON в maintenance-окно, рискуя кворумом; перед удалением MON проверяйте `ceph osd ok-to-stop`-аналоги для MON.
*   **Конфигурация — только через config db и service specs**, никогда через ручную правку `ceph.conf` на хостах `cephadm`.
*   **Контролируйте влияние recovery на prod** лимитами параллельности и планировщиком mclock (см. раздел «Ограничение влияния операций»).
*   **Одна волна изменений.** Не совмещайте апгрейд, замену OSD и изменение CRUSH в один момент — при инциденте невозможно определить источник.
*   **Тренируйте аварийное восстановление** (game day) на резервной копии кластера: процедура восстановления кворума из OSD не должна исполняться впервые во время реального инцидента.
*   **Взаимодействие с Kubernetes:** перед плановым обслуживанием нод, на которых работают Rook/CSI-хранилища, согласуйте maintenance-окна Ceph с процедурой [maintenance узла Kubernetes](../../../Operations/node_maintenance.md) (порядок drain подов → обслуживание ноды → возврат).
