# Обзор Ceph

## 1. Определения и назначение

Ceph — это программно-определяемое, распределенное и отказоустойчивое объектное хранилище. Ключевая особенность — работа на стандартном оборудовании (commodity hardware). Внутренне Ceph хранит данные как объекты, но предоставляет к ним доступ через несколько интерфейсов:

*   **Rados Block Device (RBD)**: Блочное устройство с поддержкой тонкого выделения ресурсов (thin provisioning) и снапшотов. Для операционной системы выглядит как обычный виртуальный диск. Детальное руководство по использованию доступно в заметке [Подключение и работа с RBD-образами](ceph_rbd_usage.md).
*   **Ceph File System (CephFS)**: Распределенная POSIX-совместимая файловая система для одновременного доступа с множества клиентов. Воспринимается как общая сетевая папка. Практические шаги по настройке описаны в заметке [Настройка и использование CephFS](cephfs_setup_and_usage.md).
*   **Rados Gateway (RGW)**: RESTful API, совместимый с Amazon S3 и OpenStack Swift, для нативного объектного доступа.

## 2. Базовые концепции

Кластер Ceph состоит из нескольких типов фоновых процессов (демонов), работающих на серверах.

### 2.1. Демоны Ceph (Роли)

*   **MON (Monitor)**: Демон мониторинга, модуль управления, точка подключения клиентов. Отвечает за поддержание состояния кластера и его конфигурации. Для отказоустойчивости требуется кворум из нескольких мониторов (обычно 3 или 5).
*   **OSD (Object Storage Daemon)**: Демон хранения, занимается непосредственно хранением данных на отдельных блочных устройствах (дисках). В простейшем случае каждый OSD хранит данные на одном диске.
*   **MDS (Metadata Server)**: Сервер метаданных. Необходим при использовании файловой системы CephFS для управления и хранения метаданных файлов. Один MDS активен, остальные находятся в режиме ожидания.
*   **MGR (Manager)**: Демон менеджера, который используется для мониторинга ресурсов кластера, сбора метрик и предоставления различных плагинов для управления и отчетности.

### 2.2. Организация хранения данных

*   **Пулы (Pools)**: Логические разделы для хранения объектов. Определяют базовые правила хранения, такие как уровень репликации (`size`) или отказоустойчивости (erasure coding) и количество Placement Groups.
*   **Placement Groups (PG)**: Внутренняя абстракция для распределения данных по OSD. Пул делится на PG, а каждая PG распределяется по разным OSD в соответствии с правилами CRUSH. Корректный [Расчет количества Placement Group (PG) в Ceph](ceph_placement_groups.md) критически важен для производительности.

Минимальный отказоустойчивый кластер состоит из трех серверов, на каждом из которых запущены MON, MGR и OSD.

## 3. Практические сценарии

### 3.1. Развертывание и администрирование

Наиболее распространенный способ развертывания — с помощью Ansible. Подробное руководство находится в заметке [Установка кластера Ceph с использованием Ansible](ceph_ansible_installation.md).

После установки основные задачи по управлению и мониторингу состояния кластера выполняются через утилиты командной строки, как описано в заметке [Администрирование Ceph](ceph_administration.md).

### 3.2. Интеграция с Kubernetes

Ceph является популярным решением для организации постоянного хранения (persistent storage) в Kubernetes. Интеграция выполняется с помощью CSI-драйверов:
*   Для блочных устройств (RWO, RWM с `block` mode): [Установка и настройка драйвера Ceph CSI для RBD](ceph_csi_rbd_driver_setup.md).
*   Для файловой системы (RWX): [Установка и настройка драйвера Ceph CSI для CephFS](ceph_csi_cephfs_driver_setup.md).

## 4. Продвинутые детали

### 4.1. CRUSH (Controlled Replication Under Scalable Hashing)

CRUSH — это алгоритм, позволяющий клиентам Ceph самостоятельно рассчитывать, на каком именно OSD хранить данные, и общаться с этим OSD напрямую. Такой подход позволяет Ceph избежать единой точки отказа и проблем с производительностью отдельных серверов.

*   **Карта CRUSH**: Изначально содержит распределение OSD по отдельным серверам. Вы можете расширить карту, добавив информацию о стойках, дата-центрах и лучах электропитания.
*   **Правила CRUSH**: Позволяют настроить алгоритм таким образом, чтобы, например, отключение одной стойки с серверами не приводило к потере всех копий данных. Также карты CRUSH могут использоваться для создания пулов, в которых данные будут размещаться только на быстрых или только на медленных серверах (tiering).
*   **Рекомендации**: В случае больших и сложных кластеров авторы Ceph категорически советуют создавать собственные правила и карту CRUSH, так как дефолтные настройки хорошо работают только в самых простых случаях.
