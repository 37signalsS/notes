# Обзор Ceph

## Определения

**Ceph** — программно-определяемое (SDS), распределенное, отказоустойчивое объектное хранилище данных. Работает на стандартном оборудовании (commodity hardware), обеспечивает высокую доступность и масштабируемость.

### Ключевые характеристики

| Характеристика | Описание |
|----------------|----------|
| **Масштабируемость** | Горизонтальная, до тысяч узлов |
| **Отказоустойчивость** | Репликация или коды Эраша (Erasure Coding) |
| **Доступность** | 99.999% (при правильной настройке) |
| **Интерфейсы** | RBD (блочное), CephFS (файловое), RGW (объектное S3/Swift) |

## Основные концепции

### Интерфейсы доступа

Ceph хранит данные как объекты, но предоставляет несколько интерфейсов доступа:

| Интерфейс | Тип | Протокол | Сценарий |
|-----------|-----|----------|----------|
| **RBD** (RADOS Block Device) | Блочное | Kernel module / librbd | ВМ, базы данных, stateful-приложения |
| **CephFS** | Файловое | Kernel module / FUSE | Общие файловые ресурсы, CI/CD, домашние каталоги |
| **RGW** (RADOS Gateway) | Объектное | REST API (S3/Swift) | Архивы, бэкапы, статический контент |

Подробные руководства:

- [Работа с RBD](./ceph_rbd_usage/practical_scenarios.md)
- [Настройка CephFS](./cephfs_setup_and_usage/definitions_and_concepts.md)

### Компоненты кластера (Демоны)

| Демон | Назначение | Требования к HA |
|-------|------------|-----------------|
| **MON** (Monitor) | Поддержание карты кластера, кворум | Минимум 3 (нечетное число) |
| **MGR** (Manager) | Метрики, мониторинг, API | 1 active + N standby |
| **OSD** (Object Storage Daemon) | Хранение данных на дисках | 1 OSD на диск |
| **MDS** (Metadata Server) | Метаданные для CephFS | 1 active + N standby |

#### Минимальная конфигурация для HA

```
3 узла × (MON + MGR + OSD)
```

### Организация хранения данных

#### Пулы (Pools)

Логические разделы для хранения объектов с настройками:

| Параметр | Описание | Значение по умолчанию |
|----------|----------|----------------------|
| `size` | Фактор репликации | 3 |
| `min_size` | Мин. реплик для записи | 2 |
| `pg_num` | Количество Placement Groups | Настраивается |
| `pgp_num` | PG для размещения (должен = pg_num) | Настраивается |
| `crush_rule` | Правило размещения | replica_rule |

#### Placement Groups (PG)

Внутренняя абстракция для распределения данных:

- Пул делится на PG
- PG равномерно распределяются по OSD
- Клиенты вычисляют местоположение через CRUSH

> **Важно**: Правильный расчет PG критичен для производительности. См. [Расчет PG](ceph_placement_groups.md).

### Алгоритм CRUSH

**CRUSH** (Controlled Replication Under Scalable Hashing) — алгоритм распределения данных:

1. Клиент вычисляет PG для объекта (хэш от имени объекта)
2. CRUSH определяет OSD для PG на основе карты топологии
3. Клиент записывает данные напрямую в OSD (без прокси)

#### Карта CRUSH

Описывает физическую топологию:

```
root
└── datacenter
    └── rack
        └── host
            └── osd.{0,1,2}
```

#### Правила CRUSH

Определяют размещение реплик:

- **replica_rule**: Репликация (по умолчанию)
- **erasure_rule**: Коды Эраша (экономия места)

Пример правила с учетом стоек:

```bash
ceph osd crush rule create-replicated ssd-rule host type=ssd
```

### Репликация vs Erasure Coding

| Параметр | Репликация | Erasure Coding |
|----------|------------|----------------|
| **Надежность** | Высокая | Высокая |
| **Использование места** | 3× для size=3 | ~1.5× для k=3,m=2 |
| **Производительность** | Высокая | Ниже на запись |
| **Сценарий** | Hot/Warm данные | Cold/Archive данные |

### Администрирование

Основные команды:

```bash
# Статус кластера
ceph status
ceph health detail

# Список OSD
ceph osd tree

# Пулы
ceph osd pool ls
ceph osd pool get <pool> pg_num

# Мониторы
ceph mon dump

# Менеджеры
ceph mgr dump
```

Подробнее: [Администрирование Ceph](./Administration/index.md)

### Расчет PG

Формула для расчета:

```
Total PGs = (OSD_count × 100) / replication_factor
```

Распределение по пулам — пропорционально ожидаемому объему данных.

Подробно: [ceph_placement_groups.md](ceph_placement_groups.md)

### Кастомизация CRUSH

Для сложных кластеров рекомендуется:

- Создавать собственные правила CRUSH
- Учитывать физическую топологию (стойки, дата-центры)
- Настраивать tiering (SSD/HDD)

- **Ceph Dashboard**: Встроенный веб-интерфейс
- **Alertmanager**: Алерты по здоровью кластера
