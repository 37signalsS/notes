# Обзор Ceph

## Определения

**Ceph** — программно-определяемая (SDS), распределенная, отказоустойчивая платформа хранения данных с открытым исходным кодом. Она объединяет блочное, файловое и объектное хранилище в едином кластере, работающем на стандартном серверном оборудовании (commodity hardware).

В основе Ceph лежит **RADOS** (Reliable Autonomic Distributed Object Store) — интеллектуальная распределенная сеть объектов, которая берет на себя задачи репликации, обнаружения ошибок и самовосстановления. RADOS обеспечивает:
- **Консистентность данных**: Гарантируется строгая консистентность на уровне объектов.
- **Отказоустойчивость**: Автоматическое перестроение данных при выходе узлов из строя.
- **Интеллектуальные узлы**: OSD сами участвуют в репликации и восстановлении, разгружая центральные компоненты.

### Основные характеристики

| Характеристика | Описание |
|----------------|----------|
| **Масштабируемость** | Горизонтальная, до тысяч узлов |
| **Отказоустойчивость** | Репликация или коды стирания (Erasure Coding) |
| **Доступность** | 99.999% (при правильной настройке) |
| **Интерфейсы** | RBD (блочное), CephFS (файловое), RGW (объектное S3/Swift), NVMeoF (высокопроизводительное блочное) |

## Основные концепции

### Интерфейсы доступа

Ceph хранит данные как объекты, но предоставляет несколько интерфейсов доступа:

| Интерфейс | Тип | Протокол | Сценарий |
|-----------|-----|----------|----------|
| **RBD** (RADOS Block Device) | Блочное | Kernel module / librbd | ВМ, базы данных, stateful-приложения |
| **CephFS** | Файловое | Kernel module / FUSE | Общие файловые ресурсы, CI/CD, домашние каталоги |
| **RGW** (RADOS Gateway) | Объектное | REST API (S3/Swift) | Архивы, бэкапы, статический контент |
| **NVMeoF Gateway** | Блочное | NVMe-over-Fabrics | Низкая задержка, высокопроизводительные вычисления (HPC) |

Подробные руководства:

- [Настройка CephFS](./cephfs_setup_and_usage/definitions_and_concepts.md)

### Компоненты кластера (Демоны)

| Демон | Назначение | Требования к отказоустойчивости (HA) |
|-------|------------|-----------------|
| **MON** (Monitor) | Поддержание "карт" кластера (maps), управление кворумом | Минимум 3 (нечетное число) |
| **MGR** (Manager) | Сбор метрик, Dashboard, API, PG autoscaler | Минимум 2 (active/standby) |
| **OSD** (Object Storage Daemon) | Хранение данных, репликация, восстановление | 1 OSD на физический диск |
| **MDS** (Metadata Server) | Метаданные только для CephFS (POSIX-иерархия) | 1 active + N standby |

#### Мониторы (MON) и алгоритм Paxos

Мониторы (MON) являются "мозгом" кластера. Они хранят Single Source of Truth о состоянии системы в виде набора карт (monmap, osdmap, pgmap, crushmap).
- **Кворум**: Для работы кластера должно быть доступно более половины мониторов (N/2 + 1).
- **Paxos**: Протокол распределенного консенсуса, используемый MON для синхронизации карт и обеспечения их идентичности на всех узлах. Это гарантирует, что кластер всегда находится в согласованном состоянии.

#### Технологии OSD (Backend)

- **BlueStore**: Стандартный backend для OSD. Пишет данные напрямую на блочное устройство, минуя файловую систему ОС. Использует RocksDB для метаданных и WAL (Write Ahead Log) для обеспечения целостности.
- **Crimson**: Высокопроизводительный OSD следующего поколения (v2), построенный на фреймворке **SeaStar**. В версии **Tentacle (20.x)** и выше Crimson считается готовым к промышленной эксплуатации для NVMe-хранилищ.
    - **Shared-nothing**: Каждый поток CPU управляет своим набором ресурсов без блокировок (lockless architecture).
    - **NVMe-оптимизация**: Минимизирует задержки на современных быстрых дисках за счет исключения переключений контекста.
- **Zoned Storage (ZNS)**: Поддержка дисков с зональной записью, что позволяет увеличить плотность хранения и ресурс SSD.

#### Минимальная конфигурация для высокой доступности (HA)

```
3 узла × (MON + MGR + OSD)
```

### Организация хранения данных

#### Пулы (Pools)

Логические разделы для хранения объектов с настройками:

| Параметр | Описание | Значение по умолчанию |
|----------|----------|----------------------|
| `size` | Фактор репликации | 3 |
| `min_size` | Мин. реплик для записи | 2 |
| `pg_num` | Количество Placement Groups | Настраивается (через autoscaler) |
| `pgp_num` | PG для размещения (должен = pg_num) | Настраивается |
| `crush_rule` | Правило размещения | replica_rule |

#### Placement Groups (PG)

Внутренняя абстракция для распределения данных:

- Пул делится на PG.
- PG равномерно распределяются по OSD.
- Клиенты вычисляют местоположение через алгоритм CRUSH.

> **Важно**: Правильный расчет PG критичен для производительности. См. [Расчет PG](ceph_placement_groups.md).

### Алгоритм CRUSH

**CRUSH** (Controlled Replication Under Scalable Hashing) — уникальный алгоритм распределения данных, который позволяет клиентам напрямую общаться с OSD, не обращаясь к центральному серверу метаданных (за исключением MDS для CephFS).

**Преимущества CRUSH:**
- **Отсутствие узких мест**: Нет централизованного справочника объектов.
- **Масштабируемость**: Карта кластера весит килобайты даже для петабайтных систем.
- **Детерминизм**: Одно и то же имя объекта всегда вычисляется в один и тот же набор OSD.
- **Осведомленность о топологии**: Позволяет задавать правила (например, "хранить реплики в разных стойках").

#### Карта и иерархия CRUSH

Карта CRUSH описывает физическую топологию кластера. Она состоит из **бакетов** (buckets), которые могут быть вложены друг в друга, формируя дерево.

**Стандартные типы бакетов (от меньшего к большему):**
1.  **osd**: Физический диск (листья дерева).
2.  **host**: Сервер, содержащий один или несколько OSD.
3.  **chassis**: Шасси для группы серверов.
4.  **rack**: Стойка.
5.  **row**: Ряд стоек.
6.  **pdu**: Блок распределения питания.
7.  **pod**: Группа стоек (Point of Delivery).
8.  **room**: Машинный зал.
9.  **datacenter**: Дата-центр.
10. **region**: Географический регион.
11. **root**: Корень иерархии (логический вход).

#### Целостность данных: Scrubbing

Ceph постоянно проверяет целостность данных в фоновом режиме:
- **Scrubbing (Light Scrub)**: Ежедневная проверка. Сравнивает метаданные объектов (размер, атрибуты) во всех репликах PG. Выявляет ошибки в файловой системе или базе данных OSD.
- **Deep Scrubbing**: Еженедельная (по умолчанию) проверка. Читает все данные объектов и сравнивает их контрольные суммы. Это единственный способ обнаружить "тихую" порчу данных (bit rot) на уровне физических секторов диска.

> **Важно**: Scrubbing создает нагрузку на I/O. В высоконагруженных кластерах его часто планируют на часы минимальной активности.

### Интеграция с Kubernetes

Ceph является основным решением для сетевого хранилища в Kubernetes. Начиная с версии Kubernetes 1.31, встроенные (in-tree) плагины для Ceph полностью удалены. Использование **CSI (Container Storage Interface)** является обязательным.

| Драйвер | Тип | Режим доступа | Примеры использования |
|---------|-----|---------------|-------------|
| **Ceph CSI RBD** | Блочное | RWO, ROX | [PV/PVC Scenarios (RBD)](../pv_and_pvc_scenarios.md#динамическое-выделение-ceph-rbd) |
| **Ceph CSI CephFS** | Файловое | RWX, ROX | [Сравнение CSI-драйверов](../CSI/csi_drivers_comparison.md) |

### Администрирование и мониторинг

Основные команды:

```bash
# Статус кластера
ceph status
# Список OSD и их состояние в иерархии
ceph osd tree
# Список пулов
ceph osd pool ls
# Просмотр параметров пула
ceph osd pool get <pool> pg_num
# Информация о мониторах и кворуме
ceph mon dump
```

## Состояние кластера и решение проблем (Troubleshooting)

Ceph предоставляет детальный статус здоровья через команду `ceph status` или `ceph health detail`.

### Типичные состояния здоровья (Health States)

| Состояние | Значение | Причины и действия |
|-----------|----------|-------------------|
| **HEALTH_OK** | Кластер в норме | Данные полностью реплицированы, кворум в порядке, все демоны активны. |
| **HEALTH_WARN** | Предупреждение | `OSD_DOWN`: один из дисков недоступен. `PG_DEGRADED`: не хватает реплик. `POOL_APP_NOT_ENABLED`: пул создан, но не привязан к приложению (rbd/cephfs). |
| **HEALTH_ERR** | Критическая ошибка | `MON_DOWN`: потеря кворума (менее 50% живых MON). `PG_INCOMPLETE`: данные недоступны. `OSD_FULL`: диск заполнен более чем на 95%, запись заблокирована. |

### Базовая диагностика

1.  **Проверка логов**:
    *   Для кластеров `cephadm`: `ceph orch log watch` (логи оркестратора) или `ceph log last 100`.
    *   Уровне системных демонов: `journalctl -u ceph-* -f`.
2.  **Анализ задержек (Latency)**:
    *   Команда `ceph osd perf` показывает задержки commit (запись в WAL) и apply (запись на диск).
    *   Значения > 50-100 мс обычно указывают на деградацию производительности дисковой подсистемы или сетевые проблемы.
3.  **Зависшие операции (Slow Ops)**:
    *   `ceph ops` или `ceph health detail` покажут запросы, которые выполняются дольше 30 секунд.
    *   Частые причины: высокая нагрузка на диск, проблемы с контроллером, перестроение данных (recovery).
4.  **Проверка заполнения и балансировки**:
    *   `ceph df` — общее использование пространства.
    *   `ceph osd df tree` — проверка равномерности заполнения дисков. Если разрыв между самым пустым и самым полным диском > 20%, требуется балансировка.

### Полезные команды отладки

```bash
# Детальный отчет о проблемах
ceph health detail

# Просмотр "медленных" запросов и заблокированных PG
ceph pg dump_stale

# Статус конкретной группы размещения (PG)
ceph pg <pg_id> query

# Проверка использования дисков и классов устройств (ssd/hdd)
ceph osd df tree

# Информация о менеджерах и активных модулях
ceph mgr dump

# Логи в реальном времени
ceph -w
```

### Выбор интерфейса: RBD vs CephFS vs RGW

| Критерий | RBD | CephFS | RGW |
|----------|-----|--------|-----|
| **IOPS** | Высокие (NVMe) | Средние | Средние |
| **Throughput** | Высокий | Высокий | Высокий |
| **Latency** | Низкая (<1мс) | Средняя | Средняя |
| **POSIX** | Нет | Да | Нет |
| **Доступность** | Single-pod (RWO) | Multi-pod (RWX) | Multi-tenant |
| **Стоимость** | 3x (replica) | 3x или EC | 3x или EC |
| **Сценарий** | СУБД, ВМ, QoS | Файлы, CI/CD, кеш | Архивы, S3 API |

#### Decision tree

```
Нужен POSIX-доступ?
├── Да → CephFS
└── Нет →
    Нужен блочный доступ (Volume)?
    ├── Да →
    │   Нужна низкая latency?
    │   ├── Да → RBD (NVMe)
    │   └── Нет → RBD (HDD/SSD) + EC
    └── Нет →
        Нужен S3/Swift API?
        ├── Да → RGW
        └── Нет → CephFS (POSIX fallback)
```
