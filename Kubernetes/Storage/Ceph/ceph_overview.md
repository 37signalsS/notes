# Обзор Ceph

## Определения

*   **Ceph**: Программно-определяемое, распределенное и отказоустойчивое объектное хранилище, предназначенное для работы на стандартном оборудовании (commodity hardware).

### Интерфейсы доступа

Ceph хранит данные как объекты, но предоставляет к ним доступ через несколько интерфейсов:

*   **Rados Block Device (RBD)**: Блочное устройство с поддержкой тонкого выделения ресурсов (thin provisioning) и снапшотов. Для операционной системы выглядит как обычный виртуальный диск. Детальное руководство по использованию доступно в заметке [Подключение и работа с RBD-образами](ceph_rbd_usage.md).
*   **Ceph File System (CephFS)**: Распределенная POSIX-совместимая файловая система для одновременного доступа с множества клиентов. Воспринимается как общая сетевая папка. Практические шаги по настройке описаны в заметке [Настройка и использование CephFS](cephfs_setup_and_usage.md).
*   **Rados Gateway (RGW)**: RESTful API, совместимый с Amazon S3 и OpenStack Swift, для нативного объектного доступа.

### Компоненты кластера (Демоны)

Кластер Ceph состоит из нескольких типов фоновых процессов:

*   **MON (Monitor)**: Демон мониторинга, модуль управления, точка подключения клиентов. Отвечает за поддержание состояния кластера и его конфигурации. Для отказоустойчивости требуется кворум из нескольких мониторов (обычно 3 или 5).
*   **OSD (Object Storage Daemon)**: Демон хранения, занимается непосредственно хранением данных на отдельных блочных устройствах (дисках). В простейшем случае каждый OSD хранит данные на одном диске.
*   **MDS (Metadata Server)**: Сервер метаданных. Необходим при использовании файловой системы CephFS для управления и хранения метаданных файлов. Один MDS активен, остальные находятся в режиме ожидания.
*   **MGR (Manager)**: Демон менеджера, который используется для мониторинга ресурсов кластера, сбора метрик и предоставления различных плагинов для управления и отчетности.

## Основные концепции

### Организация хранения данных

*   **Пулы (Pools)**: Логические разделы для хранения объектов. В пулах определяются правила хранения, такие как уровень репликации (`size`) или отказоустойчивости (erasure coding).
*   **Placement Groups (PG)**: Внутренняя абстракция для распределения данных. Пул делится на PG, которые равномерно распределяются по разным OSD в соответствии с правилами CRUSH.

### Алгоритм размещения данных CRUSH

**CRUSH (Controlled Replication Under Scalable Hashing)** — это алгоритм, позволяющий клиентам Ceph самостоятельно вычислять местоположение данных. Клиенты напрямую обращаются к нужному OSD, что устраняет единую точку отказа и повышает производительность.

*   **Карта CRUSH**: Описывает физическую топологию кластера: OSD, хосты, стойки, дата-центры.
*   **Правила CRUSH**: Определяют, как размещать реплики данных с учетом топологии для обеспечения отказоустойчивости (например, чтобы реплики не оказались в одной стойке).

Минимальный отказоустойчивый кластер состоит из трех серверов, на каждом из которых запущены MON, MGR и OSD.

### Интеграция с Kubernetes

Ceph является популярным решением для организации постоянного хранения (persistent storage) в Kubernetes. Интеграция выполняется с помощью CSI-драйверов:

*   **Для блочных устройств (RWO)**: [Установка и настройка драйвера Ceph CSI для RBD](ceph_csi_rbd_driver_setup.md).
*   **Для файловой системы (RWX)**: [Установка и настройка драйвера Ceph CSI для CephFS](ceph_csi_cephfs_driver_setup.md).

## Дополнительная информация

*   **Расчет PG**: Корректный [Расчет количества Placement Group (PG) в Ceph](ceph_placement_groups.md) критически важен для производительности и стабильности кластера.
*   **Кастомизация CRUSH**: В больших и сложных кластерах рекомендуется создавать собственные правила и карту CRUSH, так как настройки по умолчанию эффективны только для простых инсталляций. Это позволяет, например, настроить tiering (размещение данных на быстрых/медленных дисках) или повысить отказоустойчивость с учетом физического расположения оборудования.
