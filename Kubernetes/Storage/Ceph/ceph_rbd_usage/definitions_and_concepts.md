# RBD: Определения и фундаментальные концепции

Документ является основным источником (SSoT) для понимания архитектуры, механизмов работы и ключевых терминов блочного хранилища Ceph (RBD). Содержит определения всех уровней стека — от RADOS до RBD — и базовые концепции, необходимые для работы с блочным хранилищем Ceph в контексте DevOps/SRE/sysadmin.

## Определения

### Уровень RADOS (объектное хранилище)

**RADOS (Reliable Autonomic Distributed Object Store)** — ядро системы хранения Ceph. Распределённое объектное хранилище, автоматически обеспечивающее отказоустойчивость, самовосстановление и балансировку данных. Все данные в Ceph хранятся как объекты RADOS фиксированного размера (по умолчанию 4 МиБ).

**OSD (Object Storage Daemon)** — демон, управляющий одним физическим диском. Хранит данные RADOS, обрабатывает I/O-операции, выполняет балансировку данных, SELF-REPAIR при сбоях и репликацию/шифрование данных. Один сервер typically запускает по одному OSD на каждый диск.

**MON (Monitor)** — демон, поддерживающий кластеровую карту (cluster map) — граф состояния кластера (какие OSD существуют, какие PG分布在何处, топология CRUSH). Не хранит пользовательские данные. Кластер требует минимум 3 MON для кворума (majority quorum).

**MGR (Manager)** — демон, предоставляющий расширенную статистику, интеграцию с инструментами мониторинга (Prometheus, Grafana), а также Dashboard UI. Отвечает за балансировку нагрузки между OSD.

**CRUSH (Controlled Replication Under Scalable Hashing)** — алгоритм распределения данных в кластере Ceph. Вычисляет размещение объектов и PG на OSD без централизованного каталога, обеспечивая равномерную загрузку дисков и отказоустойчивость. Управляет топологией (дата-центры → стойки → серверы → диски) через CRUSH-карту.

**Placement Group (PG)** — логическая единица распределения данных. Объекты группируются в PG, которые распределяются по OSD согласно CRUSH-алгоритму. Количество PG влияет на балансировку нагрузки и производительность (оптимально: 100-200 PG на OSD).

**Pool (Пул)** — логический контейнер для образов RBD. Определяет параметры отказоустойчивости (количество реплик или профиль Erasure Coding) и правила размещения данных (CRUSH-правила). Внутри пула создаются PG, в которых хранятся объекты.

### Уровень RBD (блоковое хранилище)

**RADOS Block Device (RBD)** — программный интерфейс для предоставления распределённого блочного хранилища поверх RADOS. Позволяет использовать объекты RADOS как виртуальные диски для операционных систем и приложений. Маскирует объектную природу RADOS, предоставляя привычный блочный интерфейс.

**Image (Образ)** — абстракция виртуального диска. С точки зрения Ceph, образ — это метаданные (размер, функции, зависимости) и набор фрагментированных данных, распределённых по множеству объектов RADOS. Образ привязан к пулу и опционально к пространству имён.

**Namespace (Пространство имен)** — механизм логической изоляции образов внутри одного пула. Используется для разделения доступа между разными приложениями или клиентами (например, разными кластерами Kubernetes). Не обеспечивает сетевую изоляцию — изоляция реализуется через CephX caps.

### Механизмы работы RBD

**Thin Provisioning (Тонкое выделение)** — механизм, при котором RBD-образ резервирует место в RADOS только при записи данных, а не сразу при создании. Позволяет создавать образы большого размера без физического выделения всего пространства. Фактическое использование диска определяется командой `rbd du`. Для освобождения неиспользуемого пространства необходима TRIM/Discard (см. [Маппинг и монтирование](./mapping_and_mounting.md#trimdiscard-операции)).

**Snapshot (Снимок)** — мгновенный снимок состояния образа в определённый момент времени. Использует механизм **Redirect-on-Write (RoW)**: при записи в основной образ старые блоки перенаправляются в снимок, а новые записываются в основной образ. Создание снимка мгновенно и не потребляет место до тех пор, пока данные в основном образе не изменятся. Подробности: [Управление образами](./image_management.md#4-работа-со-снапшотами-и-клонами).

**Clone (Клон)** — записываемый образ, созданный на основе снапшота. Использует **Copy-on-Write (CoW)**: чтение происходит из родительского снапшота, запись новых данных — в новый объект клона. Клон зависит от снапшота до операции flatten. Подробности: [Управление образами](./image_management.md#создание-клона).

**Flatten** — процесс разрыва связи между клоном и родительским снапшотом путём копирования всех данных родителя в клон. После flatten клон становится полностью независимым. **Deep-flatten** — позволяет удалять снапшоты без потери данных в дочерних клонах (требует ядро 5.11+). Подробности: [Управление образами](./image_management.md#6-flatten-и-deep-flatten).

**Exclusive Lock (Эксклюзивная блокировка)** — механизм, гарантирующий, что только один клиент может записывать данные в образ одновременно. Обязателен для работы Ceph CSI и многописательных сценариев. При потере блокировки клиент автоматически откатывается. Подробности: [Продвинутая настройка](./advanced_topics.md#exclusive-lock-и-мульти-райтер-сценарии).

**Object Map** — карта занятых объектов образа, хранящая метаданные о том, какие объекты RADOS реально существуют. Ускоряет операции `rbd du`, `rbd info`, `rbd resize` — вместо полного сканирования RADOS используется карта.

**Fast Diff** — алгоритм быстрого вычисления разницы между снапшотами без чтения всех данных. Использует метаданные Object Map для определения изменённых блоков. Ускоряет операции сравнения и репликации.

**Journaling** — механизм журналирования изменений образа. Необходим для работы `rbd-mirror` (асинхронная репликация между кластерами). При включении journaling каждая запись логируется, что позволяет воспроизвести изменения на удалённом кластере.

## Базовые концепции

### Архитектура и уровни взаимодействия

Блочное хранилище Ceph работает на трёх основных уровнях:

```
┌─────────────────────────────────────────────────────┐
│                   Приложение (KVM, Pod)              │
├─────────────────────────────────────────────────────┤
│  librbd / krbd / rbd-nbd   (интерфейс клиента)     │
├─────────────────────────────────────────────────────┤
│              RBD Image Layer                        │
│  (образы, снапшоты, клоны, thin provisioning)      │
├─────────────────────────────────────────────────────┤
│              RADOS Object Store                     │
│  (объекты, PG, CRUSH, репликация/EC)              │
├─────────────────────────────────────────────────────┤
│              OSD Демоны                             │
│  (физические диски, блок-устройства)               │
└─────────────────────────────────────────────────────┘
```

1.  **RADOS Layer**: Нижний уровень хранения, где данные представлены в виде объектов фиксированного размера. Каждый OSD хранит множество объектов. Репликация/шифрование/Erasure Coding происходят на этом уровне.
2.  **RBD Image Layer**: Логика блочного устройства. Управляет образом как целым, предоставляя операции чтения/записи блоков. Реализует thin provisioning, снапшоты, клоны, exclusive-lock.
3.  **Клиентский интерфейс**: Три основных способа доступа к RBD (см. раздел "Сравнение клиентов" ниже).

### Путь ввода-вывода (I/O Path)

Упрощённый путь операции чтения/записи RBD:

```
Клиент → rbd map → /dev/rbdX → ФС → Блок-запрос
    ↓
librbd/krbd преобразует блок-запрос в RADOS-объект
    ↓
CRUSH вычисляет целевой PG и OSD
    ↓
RADOS отправляет запрос на OSD
    ↓
OSD выполняет операцию с физическим диском
    ↓
Ответ возвращается клиенту
```

При **записи**: данные сначала попадают в journal (если включён) или直接 в основной объект. При чтении снапшота: данные берутся из родительского объекта (CoW).

### Тонкое выделение (Thin Provisioning)

RBD-образы по умолчанию создаются с thin provisioning:
*   **Образ 100 ГБ** физически занимает место только для записанных данных (например, 5 ГБ).
*   Место выделяется при первой записи в каждый блок ( allocating on first write ).
*   **TRIM/Discard** позволяет файловой системе сообщить RBD, какие блоки больше не используются, чтобы освободить место в RADOS.
*   **Мониторинг**: `rbd du <pool/image>` показывает фактическое использование.

Пример:
```bash
# Создание образа с thin provisioning (по умолчанию)
rbd create --size 100G mypool/myimage

# Проверка фактического использования
rbd du mypool/myimage
# → NAME         PROVISIONED  USED
# → mypool/myimage    100GiB   5.2GiB

# TRIM (освобождение неиспользуемых блоков)
sudo fstrim -v /mnt/rbd-mount
# → /mnt/rbd-mount: 5.0 GiB trimmed
```

### Репликация vs Erasure Coding (кодирование с исправлением ошибок)

Ceph поддерживает два метода обеспечения отказоустойчивости данных:

| Параметр | Репликация | Erasure Coding |
| :--- | :--- | :--- |
| **Механизм** | Копирование данных на N OSD | Кодирование данных в K+M блоков |
| **Накладные расходы** | Высокие (×N объём данных) | Низкие (×(K+M)/K) |
| **Производительность чтения** | Высокая (чтение с любой реплики) | Средняя (декодирование) |
| **Производительность записи** | Высокая (параллельная запись) | Средняя (кодирование) |
| **Восстановление** | Быстрое (копирование целого объекта) | Медленное (вычисление недостающих блоков) |
| **Использование** | По умолчанию, высокопроизводительные | Холодные данные, архивы |

**Примеры конфигурации:**
```bash
# Репликация (3 копии)
ceph osd pool create mypool 128 128 replicated
ceph osd pool set mypool size 3

# Erasure Coding (K=4, M=2 — общие потери 2 дисков)
ceph osd pool create ecpool 128 128 erasure myprofile
```

### Сравнение клиентов: krbd vs librbd vs rbd-nbd

| Параметр | krbd | librbd | rbd-nbd |
| :--- | :--- | :--- | :--- |
| **Уровень** | Ядро Linux | Пользовательское пространство | Пользовательское пространство |
| **Устройство** | `/dev/rbdX` | QEMU/CSI device | `/dev/nbdX` |
| **Кэширование** | Базовое | Продвинутое (PWL) | Нет |
| **Шифрование** | Нет | LUKS (клиент) | Нет |
| **QoS** | Нет | Да | Нет |
| **Производительность** | Высокая (йерна обработка) | Высокая (с кэшированием) | Средняя |
| **Сценарий** | mounts в Linux | QEMU/KVM, Kubernetes CSI | Niche (нужно userspace device) |

**Рекомендация:** Используйте `krbd` для маппинга в Linux, `librbd` для виртуализации и CSI. `rbd-nbd` — только для специфичных случаев (недоступность ядра).

### Механизм распределения данных (Striping)

Для обеспечения высокой производительности и параллелизма Ceph разбивает образ на части:
*   **Object Size (order)**: По умолчанию 4 МиБ (2²² байт). Каждый блок данных образа становится отдельным объектом в RADOS.
*   **Stripe Unit**: Минимальный квант данных, записываемый в один объект перед переходом к следующему.
*   **Stripe Count**: Количество объектов, по которым распределяются данные в рамках одного страйпа.

Этот механизм позволяет выполнять операции ввода-вывода (I/O) параллельно на сотни OSD-демонов.

### Снапшоты и клонирование (Copy-on-Write)

Ceph RBD реализует эффективные механизмы копирования при записи:
*   **Snapshots**: Используют механизм **Redirect-on-Write (RoW)**. Создание снимка происходит мгновенно и не потребляет место до тех пор, пока данные в основном образе не изменятся.
*   **Clones**: Полноценные записываемые образы, созданные на основе снапшота. Используют **Copy-on-Write (CoW)**: чтение происходит из родительского снапшота, а запись новых данных — в новый объект клона.
*   **Flattening**: Процесс разрыва связи между клоном и родителем путём копирования всех данных родителя в клон.

### Функции образов (Image Features)

Современные возможности RBD определяются набором флагов. Несоответствие флагов версии ядра клиента может привести к ошибкам монтирования.

| Функция | Описание | Поддержка | Минимальное ядро |
| :--- | :--- | :--- | :--- |
| **layering** | Позволяет создавать клоны на основе снапшотов. | Базовая | 2.6.32 |
| **exclusive-lock** | Гарантирует, что только один клиент может писать в образ. | Обязательно для CSI | 3.14 |
| **object-map** | Хранит карту занятых объектов, ускоряя операции `ls`, `du`, `resize`. | Рекомендуется | 3.14 |
| **fast-diff** | Позволяет мгновенно вычислять разницу между снапшотами. | Рекомендуется | 3.14 |
| **deep-flatten** | Позволяет удалять снапшоты без потери данных в дочерних клонах. | Рекомендуется | 5.11 |
| **journaling** | Необходима для работы `rbd-mirror` (асинхронная репликация). | Для DR | 5.14 |
| **data-pool** | Пул для Erasure Coding ( overridden pool-level setting). | Опционально | 5.14 |

### Именование устройств

При маппинге образа создаётся блочное устройство с несколькими вариантами именования:

```bash
# После rbd map mypool/myimage:
lsblk
# → NAME    MAJ:MIN RM  SIZE RO TYPE MOUNTPOINT
# → rbd0    252:0    0  100G  0 disk

# Варианты путей:
/dev/rbd0                         # Простой (нестабильный — порядок может измениться)
/dev/rbd/poolname/imagename       # Стабильный (имя пула и образа)
/dev/disk/by-id/rbd-<pool>-<image>  # Самый стабильный (рекомендуется)
```

**Важно:** Используйте `/dev/disk/by-id/` или `/dev/rbd/pool/image` для production — они не зависят от порядка маппинга.

### Быстрая справка команд RBD

| Команда | Описание | Пример |
| :--- | :--- | :--- |
| `rbd ls <pool>` | Список образов в пуле | `rbd ls kube` |
| `rbd create --size <size> <pool>/<img>` | Создание образа | `rbd create --size 10G kube/vol1` |
| `rbd info <pool>/<img>` | Информация об образе | `rbd info kube/vol1` |
| `rbd du <pool>/<img>` | Фактическое использование | `rbd du kube/vol1` |
| `rbd resize --size <size> <pool>/<img>` | Изменение размера | `rbd resize --size 20G kube/vol1` |
| `rbd map <pool>/<img>` | Маппинг образа в `/dev/rbdX` | `rbd map kube/vol1` |
| `rbd unmap /dev/rbdX` | Отвязка устройства | `rbd unmap /dev/rbd0` |
| `rbd snap create <pool>/<img>@<snap>` | Создание снапшота | `rbd snap create kube/vol1@snap1` |
| `rbd snap ls <pool>/<img>` | Список снапшотов | `rbd snap ls kube/vol1` |
| `rbd snap protect <pool>/<img>@<snap>` | Защита снапшота | `rbd snap protect kube/vol1@snap1` |
| `rbd snap unprotect <pool>/<img>@<snap>` | Снятие защиты | `rbd snap unprotect kube/vol1@snap1` |
| `rbd snap rm <pool>/<img>@<snap>` | Удаление снапшота | `rbd snap rm kube/vol1@snap1` |
| `rbd clone <pool>/<img>@<snap> <pool>/<clone>` | Создание клона | `rbd clone kube/vol1@snap1 kube/vol1-clone` |
| `rbd flatten <pool>/<img>` | Разрыв связи с родителем | `rbd flatten kube/vol1-clone` |
| `rbd feature disable <pool>/<img> <feat>` | Отключение функции | `rbd feature disable kube/vol1 exclusive-lock` |
| `ceph -s` | Статус кластера | `ceph -s` |
| `ceph osd pool ls` | Список пулов | `ceph osd pool ls` |

### Частые ошибки и решения

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `rbd: map failed: (22) Invalid argument` | Образ использует функции, не поддерживаемые ядром | `rbd feature disable <pool>/<img> <unsupported-feature>` или обновите ядро |
| `rbd: snapshot protection is enabled` | Снапшот защищён от удаления (есть клон) | `rbd snap unprotect <pool>/<img>@<snap>` перед удалением |
| `rbd: clone is protected` | Клон привязан к защищённому снапшоту | Сначала `rbd snap unprotect` родительского снапшота |
| `rados: OSD error: no exists` | OSD недоступен или диск повреждён | `ceph health detail` — проверьте статус OSD |
| `rados: auth error` | Невалидный ключ или несоответствие caps | `ceph auth get <user>` — проверьте ключ и caps |
| `rados: mon timeout` | Мониторы недоступны или network partition | Проверьте сеть и порты 3300/6789: `nc -zv <mon-ip> 3300` |
| `ioctl RBD ioctl_set_events failed` | Конфликт exclusive-lock | `rbd lock list <pool>/<img>` — проверьте блокировки |
| `kernel: [rbdX] lost exclusive lock` | Клиент потерял блокировку | Проверьте сеть, обновите ядро или отключите exclusive-lock |
| `No such file or directory: /dev/rbdX` | Образ не замаплен | `rbd map <pool>/<img>` — заново выполните маппинг |
| `fstrim: /mnt/rbd: Operation not supported` | Файловая система не поддерживает TRIM | Проверьте `discard` в опциях mount и `rbd_discard` в пуле |
