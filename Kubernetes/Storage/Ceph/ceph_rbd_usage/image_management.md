# RBD: Управление образами

Документ является основным руководством по управлению жизненным циклом блочных устройств (RBD) в кластере Ceph. Охватывает создание, изменение размера, управление снапшотами и клонами (включая защиту зависимостей, flatten и deep-flatten), безопасное удаление через корзину, переименование, импорт/экспорт, пакетные операции и метаданные. Предполагается знакомство с архитектурными основами RBD (см. «[Определения и фундаментальные концепции](./definitions_and_concepts.md)») и подготовкой клиентской среды (см. «[Установка и настройка клиента](./installation_and_setup.md)»).

## Определения

**Образ (Image)** — виртуальный блочный диск, данные которого распределены в виде набора объектов RADOS внутри пула или пространства имен.

**Снапшот (Snapshot)** — неизменяемая копия образа в режиме "только для чтения" на определенный момент времени. Снапшоты в Ceph используют механизм **Redirect-on-Write (RoW)**, поэтому создание снимка происходит мгновенно и не потребляет место до начала изменений в основном образе.

**Клон (Clone)** — полноценный записываемый образ RBD, созданный на основе конкретного снапшота. Использует механизм **Copy-on-Write (CoW)**, считывая данные из родительского снапшота до тех пор, пока они не будут изменены в клоне.

**Корзина (Trash)** — механизм отложенного удаления, позволяющий переместить образ в защищенное хранилище перед окончательным удалением для предотвращения случайной потери данных. Образ в корзине доступен для восстановления в течение заданного периода.

**Flatten (Выравнивание)** — операция копирования всех данных родительского снапшота в клон, после которой клон становится независимым образом. Различают два режима: обычный flatten (только прямые данные родителя) и **deep-flatten** (включая снапшоты в цепочке родителей).

**Deep-flatten** — расширенная операция flatten, которая, помимо прямых данных родительского снапшота, копирует также данные всех вложенных снапшотов в цепочке. Позволяет удалять родительские снапшоты даже при наличии дочерних клонов, которые в свою очередь имеют собственные снапшоты.

**Protected Snapshot (Защищенный снапшот)** — снапшот с установленным флагом защите от случайного удаления. Пока снапшот защищен, его нельзя удалить стандартной командой `rbd snap rm`. Защита обязательна для снапшотов, на основе которых существуют клоны.

**Image Lock (Блокировка образа)** — механизм управления доступом к образу на уровне клиента. Гарантирует, что в один момент времени только один клиент выполняет операции с записью. Реализуется через функцию `exclusive-lock`.

**Orphaned Clone (Осиротевший клон)** — клон, чей родительский снапшот был удален (или whose parent image больше не существует). Восстановление данных из родителя невозможно; клон продолжает работать, но теряет возможность чтения неизмененных блоков из родителя (все данные уже скопированы при flatten или при удалении родителя).

## Базовые концепции

### Пространства имен (Namespaces)
Пространства имен позволяют логически изолировать группы образов внутри одного пула. Это критично для мультиарендных (multi-tenant) сред, где разные команды или приложения (например, разные кластеры Kubernetes) используют один и тот же пул.

Пространства имен **не обеспечивают сетевую изоляцию** — это только логическое разделение. Доступ к образам в любом namespace по-прежнему определяется ключами CephX и правилами CRUSH. Для реальной изоляции создавайте отдельные пулы.

```bash
# Просмотр всех namespace в пуле
rbd namespace ls -p kube
```

### Механизм Redirect-on-Write (RoW) при создании снапшота
При вызове `rbd snap create` Ceph **не копирует данные**. Вместо этого:
1. Создается запись метаданных, указывающая на текущий набор объектов образа.
2. Все новые операции записи перенаправляются (redirect) на новые объекты — старые объекты остаются неизменными.
3. Это обеспечивает мгновенное создание снапшота и нулевое потребление места до первого изменения в основном образе.

### Механизм Copy-on-Write (CoW) при клонировании
При вызове `rbd clone` Ceph создает новый образ, который **не копирует данные**:
1. Клон ссылается на родительский снапшот для чтения.
2. При чтении блока, который не был изменен, данные берутся из родительского снапшота.
3. При записи нового блока создается собственный объект клона (Copy-on-Write).
4. Клон растет в размере по мере записи, но исходные данные родителя остаются неизменными.

### Цепочки зависимостей и выравнивание (Flattening)
Клоны жестко привязаны к своим родительским снапшотам. До тех пор, пока существует хотя бы один клон, родительский снапшот не может быть удален (он находится в статусе `protected`).

**Flatten** — процесс копирования всех родительских данных в клон. После завершения операции клон становится независимым образом («плоским»), а родительский снапшот можно будет удалить.

**Deep-flatten** — расширенный flatten, который также обрабатывает вложенные снапшоты в цепочке. Копирует не только прямые данные родителя, но и данные всех снапшотов, на которые ссылаются дочерние клоны. Это позволяет удалять родительские снапшоты даже при наличии сложных цепочек зависимостей.

Важно: flatten — ресурсоемкая операция (чтение всех данных родителя и запись в клон). Для больших образов используйте фоновый режим или планируйте в окно обслуживания.

### Метаданные и тегирование
RBD позволяет назначать пользовательские метаданные (ключ-значение) образам. Это полезно для автоматизации, инвентаризации или интеграции с внешними системами (например, указание владельца или ID проекта).

Метаданные хранятся в RADOS и доступны через `rbd image-meta`. Ключи и значения — строки. Ограничения:
- Максимальная длина ключа: 64 символа.
- Максимальная длина значения: не ограничена формально, но рекомендуется < 1 КиБ.
- Метаданные не влияют на производительность I/O.

### Управление блокировками (Image Locking)
Механизм блокировки RBD контролирует доступ к образу на уровне клиента:

- **Exclusive Lock**: Гарантирует, что только один клиент имеет право на запись. Используется по умолчанию в современных конфигурациях. Критически важно для целостности данных.
- **Shared Lock**: Позволяет нескольким клиентам одновременно читать образ. Используется для кластерных ФС (GFS2/OCFS2).
- ** advisory Lock**: Опциональная блокировка, не влияющая на доступ к данным.

Блокировки управляются через `rbd lock list`, `rbd lock remove`. При нормальной работе блокировки снимаются автоматически при отключении клиента. Принудительное снятие блокировки допустимо только при полной уверенности, что данные не пишутся.

## Практические сценарии

### 1. Создание и инвентаризация

```bash
# Создание образа 20 ГБ с рекомендуемым набором функций для CSI
rbd create --size 20480 --pool kube \
  --image-features layering,exclusive-lock,object-map,fast-diff,deep-flatten \
  my-production-disk

# Установка метаданных (тегирование)
rbd image-meta set kube/my-production-disk project "alpha-7"
rbd image-meta set kube/my-production-disk owner "devops-team"

# Список всех образов в пуле с выводом метаданных
rbd ls -p kube -l
```

### 2. Управление пространствами имен

```bash
# Создание namespace
rbd namespace create kube/production

# Создание образа внутри namespace
rbd create --size 5120 --pool kube --namespace production prod-db-01

# Список образов в конкретном namespace
rbd ls -p kube --namespace production
```

### 3. Изменение размера (Online Resize)

Ceph поддерживает изменение размера образа "на лету". Если образ используется через `librbd` (QEMU/KVM), клиент автоматически увидит новый размер. Для модуля ядра (`krbd`) может потребоваться запуск `blockdev --setrw` или аналогичных команд внутри ОС.

```bash
# Увеличение до 40 ГБ
rbd resize --size 40960 kube/my-production-disk

# Уменьшение размера (опасная операция, требует флага)
rbd resize --size 10240 kube/my-production-disk --allow-shrink
```

### 4. Работа со снапшотами и клонами

#### Создание снапшота и клона

```bash
# Создание снапшота
rbd snap create kube/my-production-disk@backup-v1

# Просмотр снапшотов образа
rbd snap ls kube/my-production-disk
# → NUM  NAME       SIZE    PROTECTED
#    0    backup-v1  20 GiB  no
```

#### Защита снапшота

Прежде чем создавать клон на основе снапшота, его необходимо защитить от случайного удаления:

```bash
# Защита снапшота (обязательно перед клонированием)
rbd snap protect kube/my-production-disk@backup-v1

# Проверка статуса защиты
rbd snap ls kube/my-production-disk
# → NUM  NAME       SIZE    PROTECTED
#    0    backup-v1  20 GiB  yes
```

Защищенный снапшот нельзя удалить командой `rbd snap rm`. Попытка завершится ошибкой:
```bash
# → rbd: deleting protected snap is not allowed, unprotect it first.
```

#### Создание клона

```bash
# Создание клона на основе защищенного снапшота
rbd clone kube/my-production-disk@backup-v1 test-pool/test-disk-01

# Просмотр дочерних объектов (clones) снапшота
rbd children kube/my-production-disk@backup-v1
# → test-pool/test-disk-01
```

#### Удаление снапшота (требует сначала unprotect, затем удаление)

```bash
# Снятие защиты снапшота (только если нет активных клонов)
rbd snap unprotect kube/my-production-disk@backup-v1

# Удаление снапшота
rbd snap rm kube/my-production-disk@backup-v1
```

Если снапшот имеет активных клонов, `unprotect` завершится ошибкой:
```bash
# → rbd: image has snapshots that depend on this image; delete them first.
```

#### Цепочки зависимостей

Структура зависимостей:
```
base-image@snap-A  (protected)
  ├── clone-1       (reading from snap-A)
  └── clone-2       (reading from snap-A)
       └── clone-2@snap-B  (protected)
            └── grandchild-clone  (reading from snap-B)
```

Правила:
- Нельзя удалить `snap-A`, пока существуют `clone-1` или `clone-2`.
- Нельзя удалить `snap-B`, пока существует `grandchild-clone`.
- Для удаления `snap-A` нужно либо удалить все дочерние клоны, либо выполнить flatten каждого клона.

```bash
# Поиск всех зависимостей (рекурсивно)
rbd children kube/my-production-disk@backup-v1 --rbd
# → test-pool/test-disk-01

# Для каждого клона — проверка, есть ли у него собственные снапшоты
rbd snap ls test-pool/test-disk-01
```

### 5. Безопасное удаление (Trash)

```bash
# Перемещение образа в корзину с задержкой удаления (например, 7 дней)
# Внимание: по умолчанию задержка 0, если не настроено в ceph.conf
rbd trash mv kube/my-production-disk

# Список образов в корзине с указанием даты истечения
rbd trash ls -p kube

# Восстановление образа по его ID
rbd trash restore kube/1546738290 --image restored-disk

# Очистка корзины (удаление всех образов, срок хранения которых истек)
rbd trash purge -p kube
```

### 6. Flatten и Deep-flatten

#### Обычный Flatten

Обычный flatten копирует данные **только прямого родительского снапшота** в клон. После завершения клон становится независимым и не ссылается на родителя.

```bash
# Выполнение flatten клона
rbd flatten test-pool/test-disk-01

# Проверка прогресса (для длительных операций)
rbd status test-pool/test-disk-01
```

**Когда использовать:**
- Нужно удалить родительский снапшот, но клон должен остаться.
- Нужно перенести клон в другой пул (clone export).
- Клон используется в production и важна независимость от родителя.

**Ограничения:**
- Обычный flatten не обрабатывает вложенные снапшоты в цепочке.
- Если у клона есть собственные снапшоты, обычный flatten не освободит родительский снапшот от зависимости.

#### Deep-flatten

Deep-flatten копирует данные **всей цепочки** родителей, включая вложенные снапшоты. Это позволяет удалять родительские снапшоты даже при наличии сложных цепочек зависимостей.

```bash
# Выполнение deep-flatten клона
rbd flatten --deep test-pool/test-disk-01

# Deep-flatten работает рекурсивно: обрабатывает все уровни вложенности
```

**Когда использовать:**
- Сложные цепочки: `parent@snap1` → `clone1@snap2` → `clone2`.
- Нужно удалить промежуточный снапшот (`snap1`), но `clone2` должен остаться.
- Очистка старых снапшотов в автоматизированных пайплайнах.

**Производительность:**
- Deep-flatten потребляет больше ресурсов, чем обычный flatten.
- Для больших образов (>100 GiB) выполнять в окно обслуживания.
- Прогресс проверяется через `rbd status`.

#### Сравнение Flatten и Deep-flatten

| Параметр | Flatten | Deep-flatten |
| :--- | :--- | :--- |
| Копирует данные родителя | Да | Да |
| Обрабатывает вложенные снапшоты | Нет | Да |
| Позволяет удалить родителя при наличии вложенных клонов | Нет | Да |
| Требуемая версия Ceph | Любая | Squid (19.x) или новее |
| Влияние на производительность | Среднее | Высокое |

### 7. Переименование и перемещение образов

#### Переименование образа

```bash
# Переименование образа (в пределах одного пула)
rbd mv kube/old-name kube/new-name

# Переименование с перемещением в другой namespace
rbd mv kube/my-image kube/production/my-image
```

Переименование — мгновенная операция, изменяющая только метаданные. Физические данные не перемещаются. Все существующие маппинги и ссылки обновляются автоматически.

**Ограничения:**
- Нельзя переименовать образ, который в данный момент замаплен (`rbd status` покажет активных Watchers).
- Нельзя переименовать образ в другой пул (для этого используйте `rbd migration prepare`).

#### Просмотр образов в различных контекстах

```bash
# Все образы в пуле
rbd ls -p kube

# Образы в конкретном namespace
rbd ls -p kube --namespace production

# Образы с детальной информацией (размер, функции, объекты)
rbd ls -p kube -l

# Образы с фильтрацией по префиксу
rbd ls -p kube | grep "^prod-"

# Информация об одном образе
rbd info kube/my-production-disk
# → rbd image 'my-production-disk':
#    size 20 GiB in 5120 objects
#    order 22 (4 MiB objects)
#    snapshot_count: 0
#    id: 1546738290
#    block_name_prefix: rbd_data.1546738290
#    format: 2
#    features: layering,exclusive-lock,object-map,fast-diff,deep-flatten
#    op_features:
#    flags:
#    create_timestamp: Mon Aug 25 10:30:00 2025
```

### 8. Импорт и экспорт образов

#### Экспорт образа

Экспорт создает файл дампа образа в формате RBD. Используется для резервного копирования, миграции между кластерами или создания «золотых образов».

```bash
# Экспорт образа в файл
rbd export kube/my-production-disk /srv/backup/my-production-disk.img

# Экспорт в другой формат (raw, qcow, qcow2)
rbd export --export-format raw kube/my-production-disk /srv/backup/my-production-disk.raw
```

**Форматы экспорта:**
- `raw` — несжатый бинарный образ (совместим с `qemu-img`, `dd`).
- `qcow` — формат QEMU Copy-On-Write (только для чтения).
- `qcow2` — расширенный формат QEMU с поддержкой снапшотов.
- По умолчанию — формат RBD (`rbd export-diff` для инкрементального экспорта).

#### Импорт образа

```bash
# Импорт из raw-файла
rbd import /srv/backup/my-production-disk.img kube/imported-disk

# Импорт с указанием размера и функций
rbd import --size 20480 --image-features layering,exclusive-lock \
  /srv/backup/my-production-disk.raw kube/imported-disk

# Импорт qcow2-файла (формат определяется автоматически)
rbd import /srv/backup/vm-disk.qcow2 kube/imported-vm-disk
```

#### Инкрементальный экспорт (rbd export-diff)

```bash
# Экспорт разницы между двумя снапшотами
rbd export-diff kube/my-production-disk@snap-v1@snap-v2 /srv/backup/diff-v1-v2.img

# Импорт инкрементального дампа (на основе существующего образа)
rbd import-diff /srv/backup/diff-v1-v2.img kube/my-production-disk
```

Инкрементальный экспорт полезен для:
- Межкластерной миграции (только измененные данные).
- Резервного копирования больших образов (только дельта от предыдущего бэкапа).
- Репликации без включения `rbd-mirror`.

### 9. Пакетные операции со снапшотами

#### Пакетное создание снапшотов

```bash
# Создание снапшотов для всех образов пула с префиксом
for img in $(rbd ls -p kube | grep "^prod-"); do
  rbd snap create "kube/$img@daily-$(date +%Y%m%d)"
  rbd snap protect "kube/$img@daily-$(date +%Y%m%d)"
done
```

#### Пакетное удаление старых снапшотов

```bash
# Удаление снапшотов старше 7 дней (по имени с датой)
for img in $(rbd ls -p kube); do
  for snap in $(rbd snap ls "kube/$img" --format json | \
    python3 -c "import sys,json; [print(s['name']) for s in json.load(sys.stdin) \
    if s['name'].startswith('daily-') and s['name'] < 'daily-$(date -d-7days +%Y%m%d)']"); do
    rbd snap unprotect "kube/$img@$snap" 2>/dev/null || true
    rbd snap rm "kube/$img@$snap"
  done
done
```

#### Пакетный просмотр использованного места

```bash
# Суммарное использование всех образов пула
for img in $(rbd ls -p kube); do
  echo -n "$img: "
  rbd du "kube/$img" | awk 'NR==2{print $3}'
done
```

#### Список всех снапшотов в пуле (включая protected)

```bash
# Все снапшоты всех образов с указанием статуса защиты
for img in $(rbd ls -p kube); do
  snaps=$(rbd snap ls "kube/$img" --format json 2>/dev/null)
  if [ -n "$snaps" ]; then
    echo "$img:"
    echo "$snaps" | python3 -c "import sys,json; [print(f'  {s[\"name\"]:30s} protected={s[\"protected\"]}') for s in json.load(sys.stdin)]"
  fi
done
```

### Производительность и лучшие практики

#### Flatten: стоимость операции

Flatten — ресурсоемкая операция, которая выполняется в фоновом режиме:
- **Время выполнения**: Пропорционально размеру данных родителя. Для образа 100 GiB: ~10–30 минут (зависит от скорости сети и OSD).
- **Нагрузка на сеть**: Все данные родителя передаются от RADOS к клиенту и записываются обратно в клон.
- **Влияние на I/O**: В времени выполнения flatten снижается пропускная способность для всех операций в пуле.

**Рекомендации:**
- Выполнять flatten в окно обслуживания.
- Для критичных production-нагрузок не выполнять flatten без необходимости.
- Проверять прогресс через `rbd status`.

#### Shallow Clone vs Deep Clone

| Параметр | Shallow Clone (по умолчанию) | Deep Clone (flatten) |
| :--- | :--- | :--- |
| Зависимость от родителя | Да | Нет |
| Время создания | Мгновенно | Пропорционально размеру |
| Скорость чтения неизмененных блоков | Нормальная (из родителя) | Нормальная (из собственных объектов) |
| Удаление родителя | Невозможно | Возможность удаления |
| Миграция в другой пул | Невозможна (только через flatten) | Возможна |

#### Именование и тегирование: лучшие практики

1. **Единый формат именования**: `<project>-<env>-<component>-<sequence>` (например, `alpha7-prod-db-01`).
2. **Обязательные теги**: `project`, `owner`, `env`, `backup-schedule`, `created-by`.
3. **Префикс для снапшотов**: `<purpose>-<date>` (например, `daily-20250825`, `pre-upgrade-v2`).
4. **Избегайте**: спецсимволов, пробелов, кириллицы в именах образов и снапшотов.

```bash
# Установка набора метаданных при создании
rbd create --size 20480 --pool kube \
  --image-features layering,exclusive-lock,object-map,fast-diff,deep-flatten \
  my-production-disk

rbd image-meta set kube/my-production-disk project "alpha-7"
rbd image-meta set kube/my-production-disk owner "devops-team"
rbd image-meta set kube/my-production-disk env "production"
rbd image-meta set kube/my-production-disk backup-schedule "daily"
rbd image-meta set kube/my-production-disk created-by "terraform"
```

## Поиск неисправностей

### Ошибка: "image has snapshots that depend on this image"

При попытке удалить снапшот, у которого есть активные клоны.

**Причина:** Снапшот защищен или имеет дочерние клоны.

**Решение:**
```bash
# 1. Проверить наличие дочерних клонов
rbd children kube/my-production-disk@backup-v1

# 2a. Удалить все дочерние клоны (если они не нужны)
rbd rm test-pool/test-disk-01

# 2b. Или выполнить flatten каждого клона (если клоны нужны)
rbd flatten test-pool/test-disk-01

# 3. Снять защиту
rbd snap unprotect kube/my-production-disk@backup-v1

# 4. Удалить снапшот
rbd snap rm kube/my-production-disk@backup-v1
```

### Ошибка: "rbd: image is protected"

При попытке удалить защищенный снапшот.

**Решение:** Сначала снять защиту (требует отсутствия активных клонов):
```bash
rbd snap unprotect kube/my-production-disk@backup-v1
```

### Ошибка: "image is in use by another client"

При попытке переименовать или удалить замапленный образ.

**Диагностика:**
```bash
rbd status kube/my-production-disk
# → Watchers: 10.0.0.5:0 client.4132 ...
```

**Решение:** Остановить все клиенты, использующие образ:
```bash
# На клиенте (10.0.0.5):
sudo rbd unmap /dev/rbd0
# Или для QEMU: stop VM, затем rbd unmap
```

### Ошибка: "flatten failed" — образ слишком большой или нехватка места

**Причина:** Недостаточно места в целевом пуле для записи скопированных данных.

**Диагностика:**
```bash
# Проверка использования пространства в пуле
ceph df detail | grep test-pool
# → test-pool   20480M  18000M   2480M   121%
```

**Решение:** Расширить пул или освободить место:
```bash
# Расширение пула (если есть свободные OSD)
ceph osd pool set test-pool size 3  # или другой параметр
```

### Ошибка: "deep-flatten not supported"

**Причина:** Версия Ceph не поддерживает deep-flatten (требуется Squid 19.x+).

**Решение:** Использовать обычный flatten или обновить кластер:
```bash
# Обычный flatten (без --deep)
rbd flatten test-pool/test-disk-01
```

### Образ не отображается в `rbd ls`

**Возможные причины:**
1. Образ в другом namespace: `rbd ls -p kube --namespace production`
2. Образ в корзине: `rbd trash ls -p kube`
3. Нет прав доступа: проверьте ключ CephX и caps
