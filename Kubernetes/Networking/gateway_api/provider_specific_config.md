# Провайдер-специфичная конфигурация Gateway API

## Определения

**Policy Attachment** — стандартный механизм Gateway API для расширения функциональности шлюза (например, ограничение частоты запросов, аутентификация, настройки WAF) через отдельные ресурсы политик, не изменяя основные ресурсы маршрутизации.

**Provider-Specific Configuration** — конфигурация, специфичная для конкретной реализации Gateway API (Envoy Gateway, Traefik, Kong, облачные контроллеры). Она необходима для управления функциями, которые ещё не включены в основной стандарт спецификации.

**TargetRef** — поле в спецификации политики, содержащее ссылку на целевой ресурс Gateway API (Gateway, HTTPRoute, Service или Namespace), к которому должна быть применена данная политика.

## Базовые концепции

### Проблема тонкой настройки
Стандартные ресурсы, такие как `HTTPRoute` и `Gateway`, описывают общие правила маршрутизации, но не покрывают специфические опции контроллеров:
- Глубокая настройка таймаутов и лимитов.
- Специфические алгоритмы балансировки трафика.
- Интеграция с внешними системами безопасности (WAF, Auth-провайдеры).
- Вендор-специфичные оптимизации протоколов.

### Механизм Policy Attachment
Policy Attachment позволяет добавлять расширенные функции через выделенные Custom Resources (CRD):

1. **Разделение ответственности (Separation of concerns):** Логика маршрутизации остается в `HTTPRoute`, а вспомогательные функции (например, JWT-валидация) выносятся в отдельные политики.
2. **Иерархия и приоритеты:** Политики могут применяться на разных уровнях с чёткими правилами перекрытия: `Route-level` > `Gateway-level` > `Namespace-level`.
3. **Расширяемость:** Разработчики контроллеров могут внедрять собственные типы политик (например, `BackendTrafficPolicy` в Envoy Gateway).

**Точки прикрепления (Attachment Points):**
- **Gateway:** Политика влияет на весь входящий трафик шлюза.
- **HTTPRoute:** Политика применяется только к конкретному маршруту.
- **Service:** Политика настраивает поведение при обращении к конкретному бэкенду.

### Статус реализации (на 2026 год)
Несмотря на наличие стандарта Policy Attachment в спецификации Gateway API, многие провайдеры продолжают использовать собственные CRD или аннотации. Это создаёт риск «завязки» на вендора (vendor lock-in), поэтому рекомендуется изолировать такие настройки.

## Практические сценарии

### Ограничение частоты запросов (Rate Limiting) в Envoy Gateway
Пример использования политики для ограничения трафика на уровне маршрута:

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: BackendTrafficPolicy
metadata:
  name: api-rate-limit
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: main-api-route
  rateLimit:
    type: Global
    global:
      rules:
      - limit:
          requests: 100
          unit: Minute
```

### Настройка аутентификации (JWT)
Пример политики безопасности для защиты маршрута с помощью JWT:

```yaml
apiVersion: gateway.envoyproxy.io/v1alpha1
kind: SecurityPolicy
metadata:
  name: jwt-auth-policy
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: secure-api-route
  jwt:
    providers:
    - name: oidc-provider
      issuer: https://auth.example.com/
```

### Проверка статуса применения политики
Всегда проверяйте, была ли политика принята контроллером и применена к целевому ресурсу:

```bash
kubectl get backendtrafficpolicy api-rate-limit -o yaml
```
В выводе ищите секцию `status.conditions`. Статус `Accepted: True` означает корректность манифеста, а `Enforced: True` — что политика активно управляет трафиком.

## Дополнительная информация

**Best Practices:**
- Используйте одну политику для решения одной конкретной задачи.
- Документируйте иерархию политик в проекте во избежание конфликтов приоритетов.
- Всегда указывайте точную версию API в манифестах политик, так как они часто находятся в статусе beta или experimental.
- Регулярно проверяйте статус ресурсов через `kubectl describe` для выявления ошибок в `targetRef`.
