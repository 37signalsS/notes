# Gateway API — Определения и концепции

## Определения

**Gateway API** — стандартная спецификация с открытым исходным кодом для управления внешним доступом к сервисам в Kubernetes. Это эволюционное развитие концепции Ingress, предлагающее более выразительный, расширяемый и ролевой подход к управлению трафиком.

**Gateway API Controller** — программная реализация спецификации (например, Envoy Gateway, Traefik, Istio), которая отслеживает ресурсы Gateway API в кластере и настраивает Data Plane (прокси-сервер) для фактической обработки трафика.

**Data Plane** — инфраструктурный слой (обычно Envoy, Nginx или HAProxy), который непосредственно выполняет маршрутизацию, балансировку нагрузки и терминацию TLS на основе конфигурации от контроллера.

## Базовые концепции

### Ролевая модель управления

Gateway API разделяет ответственность за сетевую конфигурацию между различными участниками процесса:

- **Администраторы инфраструктуры:** управляют классами шлюзов (`GatewayClass`).
- **Операторы кластера:** развертывают и настраивают конкретные шлюзы (`Gateway`).
- **Разработчики приложений:** описывают правила маршрутизации для своих сервисов (`HTTPRoute`, `GRPCRoute` и др.).

### Преимущества перед Ingress

Gateway API решает фундаментальные ограничения классического Ingress:

| Характеристика | Ingress | Gateway API |
| :--- | :--- | :--- |
| **Разделение ролей** | Слабое (один манифест) | Четкое (GatewayClass → Gateway → Route) |
| **Расширяемость** | Через несовместимые аннотации | Через типизированные CRD и фильтры |
| **Пространства имен** | Только в namespace приложения | Кросс-неймспейс маршрутизация |
| **TLS-сертификаты** | Только в том же namespace | Ссылки на секреты в любых namespace |
| **Протоколы** | Ограничено HTTP/HTTPS | HTTP, HTTPS, gRPC, TCP, UDP |
| **Direct Pod Targeting** | Через Service | Напрямую на endpoints (повышает скорость) |

### Статусы ресурсов (Status Conditions)

Gateway API предоставляет расширенную обратную связь через поле `status`, что упрощает диагностику без необходимости проверки логов контроллера:

- **Accepted:** конфигурация синтаксически корректна и принята контроллером.
- **Programmed (для Gateway):** конфигурация успешно применена к прокси-серверу, шлюз готов принимать трафик.
- **ResolvedRefs (для Route):** все ссылки на бэкенды и сертификаты успешно проверены и существуют.

## Практические сценарии

### Выбор реализации

Конфигурации Gateway API обладают высокой переносимостью. При выборе реализации (контроллера) следует ориентироваться на требуемый функционал и существующий стек:

- **Envoy Gateway:** стандартная реализация на базе Envoy, чистое следование спецификации.
- **Traefik:** зрелый контроллер с поддержкой Gateway API и удобным веб-интерфейсом.
- **Cilium:** высокопроизводительная реализация на базе eBPF, если Cilium уже используется как CNI.

Сравнение популярных решений: [Envoy Gateway](./envoy_gateway.md), [Traefik](./traefik.md), [KGateway](./kgateway.md).

### Диагностика

Рекомендуется начинать отладку любого ресурса Gateway API с команды осмотра статусов:

```bash
kubectl describe <kind> <name>
```

Если значение `status.conditions.status` равно `False`, в поле `message` будет указана причина ошибки (например, конфликт имен хостов или отсутствие сертификата).
