# Миграция на Gateway API: тестирование и перенос трафика

## Определения

**Валидация конфигурации** — проверка корректности созданных ресурсов Gateway API перед переносом трафика.

**Поэтапный перенос** — стратегия миграции с постепенным переключением трафика с Ingress NGINX на Gateway API, начиная с non-production окружений.

## Базовые концепции

### Этапы тестирования

1. **Проверка статусов (Status Conditions)** — ПЕРВЫЙ шаг перед любыми запросами.
2. **Валидация конфигурации** — проверка ресурсов Gateway API.
3. **Проверка маршрутизации** — тестирование HTTP/HTTPS-запросов.
4. **Проверка TLS** — верификация сертификатов.
5. **Мониторинг** — отслеживание метрик и логов.

## Практические сценарии

### Шаг 0: Проверка статусов

В Gateway API ресурсы сами сообщают о своем состоянии. Используйте `kubectl describe`, чтобы убедиться, что всё "зеленое":

```bash
# Проверка Gateway
kubectl describe gateway external-gateway -n infra
# Ищем: Accepted: True, Programmed: True

# Проверка Route
kubectl describe httproute my-app-route -n my-namespace
# Ищем: Accepted: True, ResolvedRefs: True
```

Если статусы `False`, трафик не пойдет. Проверьте:

- Наличие `GatewayClass`.
- Правильность `parentRefs` в Route.
- Существование Secret для TLS.
- Совпадение портов.

### Поэтапный перенос трафика (Canary Migration)

Миграция не должна быть мгновенной. Используйте параллельный запуск и постепенное переключение на внешнем уровне (Cloud LB, DNS, HAProxy):

1. **0% (Synthetic Testing):** Gateway поднят рядом с Ingress. Трафик идет через Ingress. Вы тестируете Gateway через `curl --resolve` или проброс портов.
2. **1-5% (Early Bird):** Направьте минимальный процент реального трафика на Gateway. Мониторьте 5xx ошибки и latency.
3. **10-25% (Scaling):** Если ошибок нет, увеличивайте долю.
4. **50-100% (Finalize):** Полный переход.
5. **Cleanup:** Удаляйте старые Ingress-ресурсы и контроллер только через несколько дней стабильной работы Gateway.

**Важно:** Само приложение не замечает переезда. Мы меняем только точку входа.

### Мониторинг

- Метрики Gateway API-контроллера (запросы, ошибки, латентность)
- Логи контроллера на предмет ошибок маршрутизации
- Доступность конечных точек (health checks)
