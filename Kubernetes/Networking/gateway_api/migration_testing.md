# Тестирование и перенос трафика при миграции на Gateway API

## Определения

**Валидация конфигурации** — процесс проверки корректности созданных ресурсов Gateway API на соответствие спецификации и готовность контроллера к их обработке.

**Поэтапный перенос (Canary Migration)** — стратегия переключения трафика с устаревшего Ingress-контроллера на новую инфраструктуру Gateway API малыми порциями для минимизации рисков.

**Status Conditions** — встроенный механизм обратной связи Gateway API, позволяющий отслеживать состояние ресурсов через стандартные поля статуса в манифестах Kubernetes.

## Базовые концепции

### Стратегия верификации
Миграция считается успешной только после прохождения пяти уровней проверки:
1. **Синтаксический уровень:** отсутствие ошибок в манифестах YAML.
2. **Логический уровень:** проверка статусов ресурсов (Status Conditions).
3. **Сетевой уровень:** проверка доступности шлюза и корректности маршрутизации.
4. **Уровень безопасности:** проверка терминации или проброса TLS-сертификатов.
5. **Операционный уровень:** наличие метрик и логов трафика в системах мониторинга.

### Роль Status Conditions
В отличие от Ingress, Gateway API является "самодокументированным" в плане ошибок. Поле `status` позволяет понять, почему трафик не доходит до бэкенда, не обращаясь к логам самого контроллера.

## Практические сценарии

### Шаг 1: Первичная диагностика через Status Conditions
Перед выполнением запросов необходимо убедиться, что контроллер принял конфигурацию.

```bash
# Проверка шлюза (Gateway)
kubectl describe gateway external-gateway -n infra

# Ожидаемые состояния в секции Conditions:
# Accepted: True   (Контроллер принял манифест)
# Programmed: True (Шлюз успешно развернут и имеет IP/DNS)

# Проверка маршрута (HTTPRoute)
kubectl describe httproute my-app-route -n my-namespace

# Ожидаемые состояния:
# Accepted: True     (Маршрут привязан к шлюзу)
# ResolvedRefs: True (Все ссылки на Service и Secret корректны)
```

Если любое из значений `False`, необходимо изучить поле `message` в выводе `describe` — там будет указана причина (например, отсутствие `GatewayClass` или конфликт имен хостов).

### Шаг 2: Синтетическое тестирование (0% трафика)
Тестирование нового шлюза без влияния на реальных пользователей.

1. **Проверка через curl с подменой хоста:**
   ```bash
   # Получите внешний IP нового шлюза
   export GATEWAY_IP=$(kubectl get gateway external-gateway -n infra -o jsonpath='{.status.addresses[0].value}')
   
   # Выполните запрос к домену приложения через этот IP
   curl -v -H "Host: app.example.com" http://$GATEWAY_IP/api/health
   ```
2. **Проверка TLS-сертификата:**
   ```bash
   openssl s_client -connect $GATEWAY_IP:443 -servername app.example.com
   ```

### Шаг 3: Поэтапный перенос трафика (Canary Migration)
Переключение выполняется на уровне внешнего DNS или глобального балансировщика нагрузки (Cloud LB, F5, HAProxy).

| Этап | Доля трафика | Задача |
| :--- | :--- | :--- |
| **Early Bird** | 1–5% | Мониторинг 5xx ошибок и задержек (Latency) на новом контроллере. |
| **Scaling** | 10–50% | Наблюдение за нагрузкой на Control Plane и Data Plane контроллера. |
| **Finalize** | 100% | Полное переключение. Старый Ingress NGINX остается в резерве на 24–48 часов. |

### Шаг 4: Мониторинг и валидация
После переключения необходимо убедиться в корректности сбора данных:
- Проверить поступление метрик в Prometheus (`envoy_http_downstream_rq_total` для Envoy-based решений).
- Проверить наличие логов доступа (Access Logs).
- Проверить работу Health Checks бэкенд-сервисов через шлюз.
