# Gateway API — Ресурсы (CRD)

## Определения

**Custom Resource Definition (CRD)** — фундаментальный механизм расширения API Kubernetes, позволяющий определять собственные типы ресурсов. Gateway API полностью реализован на базе CRD, что позволяет сетевому стандарту развиваться независимо от циклов выпуска ядра Kubernetes, обеспечивая быструю адаптацию к новым протоколам (HTTP/3, gRPC) и AI-нагрузкам.

**Gateway API Resources** — иерархическая объектная модель, предназначенная для управления входящим (North-South) и мессервисным (GAMMA) трафиком. Она заменяет монолитный ресурс Ingress на набор специализированных объектов, обеспечивая четкое разделение ответственности (Separation of Concerns).

## Базовые концепции

### Ролевая модель управления

Gateway API распределяет ответственность за сетевую инфраструктуру между тремя основными ролями:

| Ресурс | Роль | Область ответственности |
| :--- | :--- | :--- |
| **GatewayClass** | Infrastructure Provider | Выбор контроллера (Envoy, Traefik, Cilium) и глобальные настройки провайдера. |
| **Gateway / ListenerSet** | Cluster Operator | Инфраструктурные параметры: IP-адреса, порты, TLS-терминация и лимиты. |
| ***Route** | Application Developer | Бизнес-логика: хосты, пути, фильтры (CORS, Auth) и бэкенды. |

### Основные ресурсы (Standard Channel v1.5+)

Начиная с версии v1.5, спецификация считается стабильной (GA). Ресурсы в канале **Standard** обеспечивают полную переносимость между различными реализациями контроллеров.

#### 1. GatewayClass (Cluster-scoped)
Декларативное описание реализации шлюза. Поле `spec.controllerName` связывает ресурс с конкретным контроллером. Позволяет задавать глобальные параметры через `spec.parametersRef` (например, конфигурацию облачного балансировщика или специфичные настройки Envoy). Является современной заменой `IngressClass`.

#### 2. Gateway (Namespaced)
Описание физической или виртуальной точки входа трафика. Содержит слушателей (`listeners`), определяющих протоколы (HTTP, HTTPS, TLS, TCP, UDP) и порты. Управляет безопасностью через `certificateRefs` и ограничивает привязку маршрутов из других неймспейсов через `allowedRoutes`.

#### 3. ListenerSet (Namespaced, v1.5+)
Специализированный ресурс для масштабируемых и мультитенентных сред. Он позволяет командам приложений самостоятельно описывать слушателей (хосты, порты, сертификаты) и «подклеивать» их к общему `Gateway`.
- **Решение проблемы лимитов:** Преодолевает архитектурное ограничение в 64 слушателя на один объект `Gateway`.
- **Самообслуживание:** Разработчики могут изменять настройки своих доменов без прямого доступа к редактированию общего инфраструктурного шлюза.

#### 4. Ресурсы маршрутизации (*Route)
- **HTTPRoute:** Основной ресурс для L7-трафика. Поддерживает сложные фильтры (Rewrites, Redirects, Mirroring) и весовую балансировку.
- **GRPCRoute:** Нативная поддержка gRPC (маршрутизация по сервисам и методам).
- **TLSRoute:** Маршрутизация по SNI для сценариев TLS Passthrough (без дешифрования).
- **TCPRoute / UDPRoute:** Управление трафиком на транспортном уровне (L4).

#### 5. GAMMA: Service как ParentRef
Инициатива **GAMMA** интегрирует Gateway API в Service Mesh. В этой модели `HTTPRoute` может использовать `Service` в качестве `parentRef`. Это позволяет применять политики Gateway API (например, канареечное развертывание 90/10) к трафику внутри кластера (East-West), используя стандартные объекты без привязки к проприетарным CRD конкретных меш-решений.

#### 6. ReferenceGrant (Namespaced)
Механизм безопасности для кросс-неймспейс ссылок. Позволяет владельцу ресурса (например, Secret или Service) разрешить его использование объектам из другого пространства имен. **Не имеет секции status**, так как проверяется контроллером в момент попытки доступа.

#### 7. BackendTLSPolicy (Namespaced)
Политика для настройки безопасности соединения между шлюзом и бэкендом (re-encryption). Позволяет указать доверенные CA и ожидаемый SNI для проверки сертификата пода, обеспечивая сквозное шифрование.

### Механизмы прикрепления политик (Policy Attachment)

Gateway API предоставляет стандартизированный способ расширения функционала через политики:

1.  **Direct Policy Attachment:** Политика применяется к конкретному ресурсу (например, `BackendTLSPolicy` привязана к конкретному `Service`).
2.  **Inherited Policy Attachment:** Политика прикрепляется к верхнему уровню (например, к `GatewayClass` или `Gateway`) и наследуется всеми дочерними ресурсами.
    - **Defaults:** Значения по умолчанию, которые можно переопределить ниже.
    - **Overrides:** Принудительные настройки, обязательные для выполнения (например, требования безопасности).

## Практические сценарии

### Жизненный цикл и связность ресурсов

Связь между ресурсами осуществляется через `parentRefs` и `targetRefs`.

**Пример делегирования TLS через ListenerSet:**

```yaml
# 1. Инфраструктурный Gateway (Namespace: infra)
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shared-gateway
spec:
  gatewayClassName: envoy-gateway
  allowedListeners:
    namespaces:
      from: Selector
      selector:
        matchLabels:
          tenant: allowed
---
# 2. ListenerSet команды приложения (Namespace: app-team)
apiVersion: gateway.networking.k8s.io/v1alpha1 # v1 в конце 2026
kind: ListenerSet
metadata:
  name: app-listeners
spec:
  parentRef:
    name: shared-gateway
    namespace: infra
  listeners:
  - name: https
    hostname: "api.example.com"
    port: 443
    protocol: HTTPS
    tls:
      mode: Terminate
      certificateRefs:
      - name: api-tls-secret
```

## Дополнительная информация

### Статусы ресурсов (Conditions)

Gateway API предоставляет детальную диагностику через `status.conditions`:
- **Accepted:** Конфигурация признана валидной контроллером.
- **Programmed:** (Gateway) Шлюз успешно сконфигурирован в Data Plane (выделен IP, открыты порты).
- **ResolvedRefs:** (Route) Все зависимости (Service, Secret, ReferenceGrant) найдены и корректны.
- **Conflicted:** Обнаружено пересечение хостов или портов между разными объектами.
