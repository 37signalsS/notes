# Ingress

## Определения

**Ingress** — это объект API Kubernetes, который описывает правила маршрутизации внешнего HTTP и HTTPS трафика к сервисам внутри кластера. Он действует как "умный" маршрутизатор или точка входа, позволяя определять правила маршрутизации на основе имени хоста (например, `api.example.com`) или пути (например, `/v1/users`). Ingress работает на **7 уровне модели OSI (прикладной уровень)** и позволяет централизованно управлять доступом к множеству сервисов через единый IP-адрес.

**Ingress-контроллер** — это приложение (обычно `Deployment` или `DaemonSet`), которое фактически реализует правила, описанные в объекте `Ingress`. Он отслеживает изменения в API-сервере Kubernetes и настраивает нижележащий прокси-сервер (например, NGINX, HAProxy, Traefik). **Без Ingress-контроллера объект Ingress не будет работать.**

### Почему Ingress, а не Service?

Хотя для публикации приложений можно использовать `Service` типа `LoadBalancer` или `NodePort`, `Ingress` является предпочтительным решением для HTTP/HTTPS трафика по нескольким ключевым причинам:

1.  **Маршрутизация на L7:** В отличие от `Service`, который работает на L4 (TCP/UDP), `Ingress` "понимает" HTTP-запросы. Это позволяет создавать гибкие правила маршрутизации на основе **имени хоста** (например, `api.example.com` и `shop.example.com` могут вести на разные сервисы) и **пути** (`example.com/api` и `example.com/ui`).
2.  **Централизованная точка входа:** `Ingress` позволяет управлять доступом ко множеству сервисов через **один внешний IP-адрес** и один балансировщик нагрузки. Это значительно экономит затраты и IP-адреса по сравнению с подходом, где для каждого `Service` типа `LoadBalancer` требуется свой уникальный IP.
3.  **Терминация TLS:** `Ingress` предоставляет стандартный способ для централизованной настройки и терминирования SSL/TLS-трафика, снимая эту задачу с каждого отдельного приложения.
4.  **Гибкая конфигурация:** Функциональность `Ingress` легко расширяется с помощью аннотаций, специфичных для каждого контроллера, позволяя настраивать аутентификацию, ограничение скорости запросов (rate limiting), перезапись URL и многое другое.

## Реализации Ingress-контроллеров

Выбор Ingress-контроллера — важное архитектурное решение. У каждого из них есть свои сильные и слабые стороны, основанные на используемых технологиях (прокси) и философии дизайна.

> **Статус NGINX Ingress Controller:**
> Важно отметить, что `ingress-nginx`, долгое время бывший стандартом "де-факто" и поддерживаемый сообществом Kubernetes, официально перешел в режим минимальной поддержки и больше не принимает новые фичи. Сообщество постепенно отказывается от него в пользу более современных альтернатив. Примеры в данном документе используют синтаксис NGINX из-за его исторической популярности, но при выборе контроллера для новых проектов стоит рассматривать альтернативы.

Ниже представлен обзор популярных современных Ingress-контроллеров.

### Traefik

Современный, облачно-ориентированный ("cloud-native") прокси-сервер, разработанный специально для динамических сред и микросервисов.

-   **Основа:** Написан на Go.
-   **Философия:** Простота и автоматизация.

#### Особенности и преимущества
- **Автоматическое обнаружение сервисов (Service Discovery):** Traefik постоянно отслеживает API Kubernetes и автоматически обновляет маршруты при появлении новых `Ingress` или изменении сервисов. Конфигурация обновляется на лету, без перезагрузок.
- **Встроенная поддержка Let's Encrypt:** Автоматическое получение и обновление TLS-сертификатов.
- **Middleware:** Гибкая концепция "посредников" для настройки запросов: добавление заголовков, базовая аутентификация, ограничение по частоте запросов (rate limiting), перенаправления и т.д.
- **Удобный Web UI:** Встроенная панель управления для визуализации маршрутов, сервисов и состояния.
- **Простота настройки:** Считается одним из самых простых контроллеров для начала работы.

#### Недостатки
- **Производительность:** В сценариях с экстремально высокими нагрузками может уступать контроллерам на базе HAProxy или Envoy.
- **Ограничения бесплатной версии:** Некоторые продвинутые функции (например, сложная синхронизация конфигурации в HA-кластере) доступны только в платной версии Traefik Enterprise.

**Вывод:** Отличный выбор для небольших и средних кластеров, динамических сред, где важны скорость разработки и автоматизация, а не экстремальная производительность.

### Envoy-based (Contour, Emissary-ingress)

Envoy — это высокопроизводительный прокси, изначально созданный в Lyft, а теперь являющийся частью CNCF. Он служит основой для многих Ingress-контроллеров и Service Mesh (например, Istio).

-   **Основа:** Envoy (написан на C++).
-   **Философия:** Производительность, расширяемость и API-ориентированная конфигурация (xDS).

#### Особенности и преимущества
- **Высокая производительность:** Envoy известен своей эффективностью и низкими задержками.
- **Динамическая конфигурация:** Обновление конфигурации происходит на лету через API (xDS), без перезагрузок и потерь соединений.
- **Продвинутое управление трафиком:** Поддержка зеркалирования трафика, повторных попыток (retries), сложных алгоритмов балансировки нагрузки, канареечных развертываний.
- **Расширяемость:** Функциональность можно расширять с помощью фильтров WebAssembly (WASM).
- **Интеграция с Service Mesh:** Является нативным выбором, если вы планируете использовать Service Mesh, так как `sidecar`-прокси в подах также будут на базе Envoy.

#### Недостатки
- **Высокая сложность настройки:** Сконфигурировать Envoy "с нуля" для получения максимальной производительности — нетривиальная задача. Большое количество параметров требует глубокого понимания его работы.
- **Ресурсоемкость:** В сложных конфигурациях может потреблять больше CPU и памяти по сравнению с более простыми решениями.

**Вывод:** Подходит для сложных инфраструктур, высоконагруженных систем и при необходимости интеграции с Service Mesh. Требует более высокой квалификации для настройки и поддержки.

### Kong

Мощный Ingress-контроллер, построенный на базе популярного API Gateway — Kong Gateway.

-   **Основа:** NGINX с модулями на Lua (OpenResty).
-   **Философия:** Расширяемость через плагины, фокус на управлении API.

#### Особенности и преимущества
- **Архитектура плагинов:** Главное преимущество Kong. Огромное количество готовых плагинов для аутентификации (JWT, OAuth2), безопасности (Bot detection, IP restriction), управления трафиком (Rate Limiting), логирования и мониторинга.
- **API Gateway "из коробки":** Предоставляет функциональность шлюза API, а не только Ingress-контроллера.
- **Высокая производительность:** Основан на проверенном временем NGINX.
- **Гибкая маршрутизация:** Продвинутые правила маршрутизации.

#### Недостатки
- **Сложность:** Требует понимания не только концепций Kubernetes, но и архитектуры самого Kong (Services, Routes, Consumers, Plugins).
- **Ресурсоемкость:** Наличие множества плагинов и функциональности API Gateway может увеличивать потребление ресурсов.
- **Зависимость от БД (опционально):** В некоторых режимах для хранения конфигурации Kong может требоваться внешняя база данных (например, PostgreSQL или Cassandra), что усложняет архитектуру.

**Вывод:** Идеальный выбор, если вам нужна функциональность API Gateway в кластере, и вы активно используете плагины для управления API.

### HAProxy

Один из самых старых, проверенных временем и высокопроизводительных прокси-серверов и балансировщиков нагрузки.

-   **Основа:** HAProxy (написан на C).
-   **Философия:** Максимальная производительность и надежность.

#### Особенности и преимущества
- **Экстремальная производительность:** Считается одним из самых быстрых прокси, способным обрабатывать огромные объемы трафика при низком потреблении ресурсов.
- **Надежность и стабильность:** Используется в индустрии десятилетиями в самых высоконагруженных системах.
- **Низкоуровневая настройка:** Позволяет очень тонко настраивать параметры TCP, очередей, тайм-аутов и алгоритмов балансировки.
- **Продвинутые проверки состояния (Health Checks):** Очень гибкие и настраиваемые проверки работоспособности бэкендов.
- **Отличная наблюдаемость:** Предоставляет подробные метрики и логи.

#### Недостатки
- **Ограниченная экосистема:** Меньше готовых плагинов и интеграций по сравнению с Kong или Traefik.
- **Менее интуитивная конфигурация:** Конфигурационные файлы и аннотации могут показаться сложнее для тех, кто привык к NGINX или Traefik.
- **Фокус на L4/L7:** Отлично справляется с балансировкой, но может иметь меньше "коробочных" фич для управления API по сравнению с Kong.

**Вывод:** Лучший выбор для систем, где требуется максимальная производительность, минимальные задержки и надежность, и вы готовы потратить время на тонкую настройку.

## Основные концепции


### Внешний доступ к Ingress-контроллеру

Для того чтобы Ingress-контроллер мог обрабатывать внешний трафик, его необходимо **выставить наружу** кластера. Часто это делается одним из следующих способов:

* **Service типа `LoadBalancer`**: Облачный провайдер выделяет внешний IP-адрес и направляет трафик на поды Ingress-контроллера.
* **Service типа `NodePort`**: Ingress-контроллер становится доступен на определенном порту на каждом узле кластера.
* **`HostPort`**: Ingress-контроллер публикует свой порт непосредственно на сетевом интерфейсе узла.

### Правила маршрутизации (Routing Rules)

#### Маршрутизация по хосту (Host-based)

Можно направлять трафик с разных доменов на разные сервисы.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-host-ingress
spec:
  rules:
    - host: "foo.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: foo-service
                port:
                  number: 80
    - host: "bar.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: bar-service
                port:
                  number: 80
```

#### Маршрутизация по пути (Path-based)

Трафик одного домена можно направлять на разные сервисы в зависимости от пути.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
spec:
  rules:
    - host: "myapp.example.com"
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service # Имя сервиса, на который пойдет трафик
                port:
                  number: 80 # Порт этого сервиса
```

* `pathType: Prefix` — соответствует любому пути, который начинается с указанного значения (например, `/api/v1`, `/api/v2`).
* `pathType: Exact` — соответствует только точно указанному пути.

#### Хост по умолчанию (Default Backend)

Можно определить сервис, который будет обрабатывать весь трафик, не соответствующий ни одному из правил.

```yaml
spec:
  defaultBackend:
    service:
      name: default-service
      port:
        number: 80
  rules:
    # ... правила ...
```

## Практические сценарии

### Настройка TLS/SSL

Ingress упрощает терминирование TLS-трафика. Для подключения HTTPS к Ingress, когда у вас уже есть сертификат и ключ, необходимо выполнить следующие шаги:

1. **Создайте `Secret` типа `kubernetes.io/tls` с сертификатом и ключом:**
    Этот Secret будет хранить ваш TLS-сертификат (`tls.crt`) и приватный ключ (`tls.key`).

    ```bash
    kubectl create secret tls my-app-tls-secret \
      --cert=path/to/tls.crt \
      --key=path/to/tls.key
    ```

    Пример манифеста `Secret`:

    ```yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: secret-tls
      namespace: default
    type: kubernetes.io/tls
    data:
      tls.crt: <base64-encoded-cert>
      tls.key: <base64-encoded-key>
    ```

2. **Укажите этот `Secret` в манифесте Ingress:**
    В секции `spec.tls` Ingress-манифеста необходимо указать домен, для которого применяется TLS, и имя созданного `Secret`.

    ```yaml
    apiVersion: networking.k8s.io/v1
    kind: Ingress
    metadata:
      name: my-app-ingress
    spec:
      tls:
        - hosts:
            - myapp.example.com
          secretName: my-app-tls-secret # Имя секрета с сертификатом
      rules:
        - host: myapp.example.com
          http:
            paths:
              - path: /
                pathType: Prefix
                backend:
                  service:
                    name: my-app-service
                    port:
                      number: 80
    ```

    Ingress-контроллер автоматически обнаружит этот `Secret`, подключит сертификат и ключ, и трафик по `https://myapp.example.com` будет зашифрован.

### Тонкая настройка через аннотации (Annotations)

Аннотации — это основной способ передачи специфичных для контроллера настроек, которые выходят за рамки стандартного API Ingress. Их набор и синтаксис определяются конкретным Ingress-контроллером.

**Примеры для NGINX Ingress Controller:**

* `nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"` — указывает, что приложение, на которое направляется трафик, ожидает HTTPS-соединение, а не HTTP (по умолчанию). Это позволяет Ingress-контроллеру понять, как именно обрабатывать и отправлять трафик к бэкенду.
* `nginx.ingress.kubernetes.io/rewrite-target: /` — перенаправляет трафик с указанного `path` на корневой путь (`/`) сервиса.
* `nginx.ingress.kubernetes.io/ssl-redirect: "true"` — принудительно перенаправляет HTTP-трафик на HTTPS.
* `nginx.ingress.kubernetes.io/proxy-body-size: "8m"` — устанавливает максимальный размер тела запроса.
* `nginx.ingress.kubernetes.io/proxy-read-timeout: "60s"` — задает таймаут чтения ответа от бэкенда. Полезно для долгих синхронных операций.
* `kubernetes.io/ingress.class: "nginx"` — указывает, какой Ingress-контроллер должен обрабатывать этот объект (актуально, если в кластере их несколько).

### Будущее Ingress: Gateway API

Несмотря на свою популярность, `Ingress` имеет ряд фундаментальных ограничений, таких как смешение ролей и зависимость от нестандартных аннотаций. Для их решения сообщество Kubernetes разработало **Gateway API** — новое поколение API для управления трафиком.

Gateway API предлагает более гибкую, мощную и ролевую модель, разделяя ответственность между администраторами инфраструктуры и разработчиками приложений.

Подробное описание концепции и примеры использования вынесены в отдельный документ: **[→ Kubernetes Gateway API](./gateway_api.md)**.

Ожидается, что со временем Gateway API станет стандартным способом управления L4/L7-трафиком в Kubernetes.
