# Ingress

**Ingress** — это объект API Kubernetes (манифест), который описывает правила маршрутизации внешнего трафика к сервисам внутри кластера, как правило, по протоколам **HTTP** и **HTTPS**. Он действует как "умный" маршрутизатор или точка входа, позволяя определять правила маршрутизации трафика на основе имени хоста (например, `api.example.com`) или пути (например, `/v1/users`). Ingress работает на **7 уровне модели OSI (прикладной уровень)**.

Ingress является высокоуровневой абстракцией, которая позволяет централизованно управлять доступом к множеству сервисов через единый IP-адрес.

## Ingress и Ingress-контроллер

Важно четко различать Ingress и Ingress-контроллер:

*   **Ingress** — это **манифест** (объект API Kubernetes), который определяет правила маршрутизации внешнего трафика к сервисам внутри кластера. Это декларативное описание того, *как* внешний трафик должен быть направлен к сервисам (например, на основе имени хоста или пути).
*   **Ingress-контроллер** — это **приложение** (обычно `Deployment` или `DaemonSet`), которое фактически реализует эти правила. Оно отслеживает объекты `Ingress` в API-сервере Kubernetes и настраивает нижележащий прокси-сервер или балансировщик нагрузки (например, NGINX, HAProxy, Traefik) в соответствии с описанными правилами. Без Ingress-контроллера объект Ingress не будет работать.

Для того чтобы Ingress-контроллер мог обрабатывать внешний трафик, его необходимо **выставить наружу** кластера. Часто это делается с использованием директивы `HostPort` (когда Ingress-контроллер публикует свой порт непосредственно на сетевом интерфейсе узла, позволяя внешнему трафику напрямую достигать контроллера по IP-адресу узла) или путем создания `Service` типа `LoadBalancer` или `NodePort`.

## Схема работы: путь трафика в Kubernetes

Подробное описание пути трафика в Kubernetes, от внешнего запроса до пода, включая роль Ingress Controller, Service и kube-proxy, было перенесено в документ [Сетевая модель в Kubernetes](./network.md#путь-трафика-от-ingress-до-pod) для централизации информации.

## Правила маршрутизации (Routing Rules)

### Маршрутизация по хосту (Host-based)

Можно направлять трафик с разных доменов на разные сервисы.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-host-ingress
spec:
  rules:
    - host: "foo.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: foo-service
                port:
                  number: 80
    - host: "bar.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: bar-service
                port:
                  number: 80
```

### Маршрутизация по пути (Path-based)

Трафик одного домена можно направлять на разные сервисы в зависимости от пути.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
spec:
  rules:
    - host: "myapp.example.com"
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service # Имя сервиса, на который пойдет трафик
                port:
                  number: 80 # Порт этого сервиса
```
*   `pathType: Prefix` — соответствует любому пути, который начинается с указанного значения (например, `/api/v1`, `/api/v2`).
*   `pathType: Exact` — соответствует только точно указанному пути.

### Хост по умолчанию (Default Backend)

Можно определить сервис, который будет обрабатывать весь трафик, не соответствующий ни одному из правил.

```yaml
spec:
  defaultBackend:
    service:
      name: default-service
      port:
        number: 80
  rules:
    # ... правила ...
```

## Настройка TLS/SSL

Ingress упрощает терминирование TLS-трафика. Для подключения HTTPS к Ingress, когда у вас уже есть сертификат и ключ, необходимо выполнить следующие шаги:

1.  **Создайте `Secret` типа `kubernetes.io/tls` с сертификатом и ключом:**
    Этот Secret будет хранить ваш TLS-сертификат (`tls.crt`) и приватный ключ (`tls.key`).
    ```bash
    kubectl create secret tls my-app-tls-secret \
      --cert=path/to/tls.crt \
      --key=path/to/tls.key
    ```
    Пример манифеста `Secret`:
    ```yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: secret-tls
      namespace: default
    type: kubernetes.io/tls
    data:
      tls.crt: <base64-encoded-cert>
      tls.key: <base64-encoded-key>
    ```

2.  **Укажите этот `Secret` в манифесте Ingress:**
    В секции `spec.tls` Ingress-манифеста необходимо указать домен, для которого применяется TLS, и имя созданного `Secret`.

    ```yaml
    apiVersion: networking.k8s.io/v1
    kind: Ingress
    metadata:
      name: my-app-ingress
    spec:
      tls:
        - hosts:
            - myapp.example.com
          secretName: my-app-tls-secret # Имя секрета с сертификатом
      rules:
        - host: myapp.example.com
          http:
            paths:
              - path: /
                pathType: Prefix
                backend:
                  service:
                    name: my-app-service
                    port:
                      number: 80
    ```
    Ingress-контроллер автоматически обнаружит этот `Secret`, подключит сертификат и ключ, и трафик по `https://myapp.example.com` будет зашифрован.

## Аннотации (Annotations)

Аннотации — это основной способ тонкой настройки поведения Ingress-контроллера. Они позволяют передавать дополнительную информацию и специфические настройки контроллеру, которые выходят за рамки стандартного API Ingress. Стандартные манифесты Kubernetes имеют строго определенную структуру и не позволяют произвольно менять поля или добавлять новые, так как API-сервер выполняет их валидацию. Аннотации решают эту проблему, позволяя контроллерам (например, Ingress-контроллеру) получать специфические инструкции, не нарушая при этом стандартную схему объекта Ingress. Аннотации не являются произвольными; их набор и синтаксис определяются конкретным Ingress-контроллером и должны быть изучены в его документации.

**Примеры для NGINX Ingress Controller:**

*   `nginx.ingress.kubernetes.io/backend-protocol: "HTTPS"` — указывает, что приложение, на которое направляется трафик, ожидает HTTPS-соединение, а не HTTP (по умолчанию). Это позволяет Ingress-контроллеру понять, как именно обрабатывать и отправлять трафик к бэкенду.
*   `nginx.ingress.kubernetes.io/rewrite-target: /` — перенаправляет трафик с указанного `path` на корневой путь (`/`) сервиса.
*   `nginx.ingress.kubernetes.io/ssl-redirect: "true"` — принудительно перенаправляет HTTP-трафик на HTTPS.
*   `nginx.ingress.kubernetes.io/proxy-body-size: "8m"` — устанавливает максимальный размер тела запроса.
*   `nginx.ingress.kubernetes.io/proxy-read-timeout: "60s"` — задает таймаут чтения ответа от бэкенда. Полезно для долгих синхронных операций.
*   `kubernetes.io/ingress.class: "nginx"` — указывает, какой Ingress-контроллер должен обрабатывать этот объект (актуально, если в кластере их несколько).

## Будущее Ingress: Gateway API

Несмотря на свою популярность, стандартный ресурс `Ingress` имеет ряд фундаментальных ограничений:

*   **Ограниченная функциональность:** API не стандартизирует множество необходимых функций (например, `rewrite`, веса для канареечных релизов, настройка таймаутов), что привело к появлению сотен специфичных для каждого контроллера аннотаций.
*   **Конфликты конфигурации:** Несколько команд, управляя своими `Ingress`-ресурсами, могут случайно "сломать" конфигурацию друг друга, так как все правила сливаются в один конфиг нижележащего прокси (например, Nginx).
*   **Смешение ролей:** Один и тот же объект `Ingress` используется и операторами кластера, и разработчиками, что усложняет разделение ответственности.

Для решения этих проблем сообщество Kubernetes разработало **Gateway API** — новое поколение API для управления трафиком.

### Ключевые преимущества Gateway API:

1.  **Ролевая модель:** Gateway API разделяет конфигурацию на три ресурса, соответствующих разным ролям:
    *   `GatewayClass`: Определяется администратором кластера (например, "это наш Nginx-контроллер").
    *   `Gateway`: Создается оператором для открытия точки входа (например, "открыть порт 443 на балансировщике для команды A").
    *   `HTTPRoute` (и другие `*Route`): Создается разработчиком для маршрутизации трафика к своему приложению.
2.  **Расширяемость и гибкость:** API изначально спроектирован как расширяемый, позволяя стандартизировать такие функции, как `Header`-модификации, взвешенная маршрутизация и т.д., без необходимости в аннотациях.
3.  **Портативность:** Конфигурации, созданные с помощью Gateway API, более переносимы между разными реализациями контроллеров.

Сообщество активно развивает Gateway API, и большинство современных Ingress-контроллеров уже поддерживают его. Ожидается, что со временем он станет стандартным способом управления L7-трафиком в Kubernetes, придя на смену `Ingress`.
