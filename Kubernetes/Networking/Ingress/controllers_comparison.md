# Ingress: Сравнение Контроллеров

Выбор Ingress-контроллера — важное архитектурное решение. У каждого из них есть свои сильные и слабые стороны, основанные на используемых технологиях (прокси) и философии дизайна.

> **Статус NGINX Ingress Controller:**
> Важно отметить, что `ingress-nginx`, долгое время бывший стандартом "де-факто" и поддерживаемый сообществом Kubernetes, в последние годы развивается менее активно. Хотя он остается стабильным и широко используемым решением, фокус сообщества смещается в сторону контроллеров, изначально спроектированных для более тесной интеграции с современными концепциями, такими как Gateway API и Service Mesh. При выборе контроллера для новых проектов рекомендуется оценивать и более современные альтернативы.

Ниже представлен обзор популярных Ingress-контроллеров.

### Traefik

Современный, облачно-ориентированный ("cloud-native") прокси-сервер, разработанный специально для динамических сред и микросервисов.

- **Основа:** Написан на Go.
- **Философия:** Простота и автоматизация.

#### Особенности и преимущества

- **Автоматическое обнаружение сервисов (Service Discovery):** Traefik постоянно отслеживает API Kubernetes и автоматически обновляет маршруты при появлении новых `Ingress` или изменении сервисов. Конфигурация обновляется на лету, без перезагрузок.
- **Встроенная поддержка Let's Encrypt:** Автоматическое получение и обновление TLS-сертификатов.
- **Middleware:** Гибкая концепция "посредников" для настройки запросов: добавление заголовков, аутентификация, ограничение частоты запросов (rate limiting), перенаправления и т.д.
- **Поддержка Gateway API:** Наряду с Ingress, активно поддерживает новую спецификацию Gateway API.
- **Удобный Web UI:** Встроенная панель управления для визуализации маршрутов, сервисов и состояния.

#### Недостатки

- **Производительность:** В сценариях с экстремально высокими нагрузками может уступать контроллерам на базе Envoy или HAProxy.
- **Ограничения бесплатной версии:** Некоторые продвинутые функции (например, сложная синхронизация конфигурации в HA-кластере) доступны только в платной версии Traefik Enterprise.

**Вывод:** Отличный выбор для сред, где важны скорость разработки и автоматизация. Идеален для стартапов и проектов, активно использующих Gateway API.

### Envoy-based (Contour, Emissary-ingress, Cilium)

Envoy — это высокопроизводительный прокси, изначально созданный в Lyft, а теперь являющийся частью CNCF. Он служит основой для многих Ingress-контроллеров и Service Mesh.

- **Основа:** Envoy (написан на C++).
- **Философия:** Производительность, расширяемость и API-ориентированная конфигурация (xDS).

#### Особенности и преимущества

- **Высокая производительность:** Envoy известен своей эффективностью и низкими задержками.
- **Продвинутое управление трафиком:** Поддержка зеркалирования трафика, повторных попыток (retries), сложных алгоритмов балансировки, канареечных развертываний.
- **Расширяемость:** Функциональность можно расширять с помощью фильтров WebAssembly (WASM).
- **Нативная поддержка Gateway API:** Большинство современных Envoy-based контроллеров (Contour, Cilium) активно используют Gateway API как основной способ конфигурации.
- **Интеграция с Service Mesh:** Является стандартным компонентом для Service Mesh, таких как Istio и Kuma.

#### Недостатки

- **Высокая сложность настройки:** Сконфигурировать Envoy "с нуля" — нетривиальная задача. Требуется глубокое понимание его работы.
- **Ресурсоемкость:** В сложных конфигурациях может потреблять больше CPU и памяти по сравнению с более простыми решениями.

**Вывод:** Подходит для сложных инфраструктур, высоконагруженных систем и при необходимости интеграции с Service Mesh. Требует более высокой квалификации для настройки и поддержки.

### Istio Ingress Gateway

Это не просто Ingress-контроллер, а стандартный компонент Service Mesh Istio, отвечающий за обработку входящего трафика.

- **Основа:** Envoy.
- **Философия:** Полная интеграция с Service Mesh.

#### Особенности и преимущества

- **Единая конфигурация:** Управление трафиком на входе в кластер (north-south) и внутри него (east-west) осуществляется через одни и те же CRD (`Gateway`, `VirtualService`, `DestinationRule`).
- **Продвинутая безопасность:** Автоматическая mTLS-аутентификация, JWT-валидация, политики авторизации на уровне всего меша.
- **Глубокая наблюдаемость:** Трассировка и метрики "из коробки", интегрированные с остальной частью сервисной сетки.

#### Недостатки

- **Избыточность без Service Mesh:** Устанавливать Istio только ради Ingress-контроллера нецелесообразно. Его сила — в экосистеме.
- **Высокий порог входа:** Требует изучения концепций и архитектуры Istio.

**Вывод:** Стандартный выбор, если вы уже используете или планируете внедрять Service Mesh Istio.

### Cilium Ingress Controller

Cilium использует технологию eBPF для обеспечения сети, наблюдаемости и безопасности. Его Ingress-контроллер является частью этой экосистемы.

- **Основа:** Envoy (для L7), eBPF (для L3/L4).
- **Философия:** Производительность и безопасность через eBPF.

#### Особенности и преимущества

- **Высокая производительность:** eBPF позволяет обрабатывать сетевые пакеты в ядре Linux, минуя часть сетевого стека, что снижает задержки.
- **Интеграция с eBPF:** Глубокая интеграция с сетевыми политиками Cilium (CiliumNetworkPolicy) и высокая производительность L4-балансировки.
- **Поддержка Gateway API:** Cilium является одной из эталонных реализаций Gateway API.
- **Встроенная замена `kube-proxy`**: Может полностью заменить `kube-proxy`, упрощая сетевой путь.

#### Недостатки

- **Требования к ядру Linux:** Для работы eBPF требуется достаточно свежая версия ядра Linux.
- **Молодость:** Как Ingress-контроллер, он новее, чем более устоявшиеся решения вроде NGINX или Traefik.

**Вывод:** Мощный выбор для современных инсталляций Kubernetes, особенно если производительность сети и безопасность являются ключевыми требованиями.

### Kong

Мощный Ingress-контроллер, построенный на базе популярного API Gateway — Kong Gateway.

- **Основа:** NGINX с модулями на Lua (OpenResty).
- **Философия:** Расширяемость через плагины, фокус на управлении API.

#### Особенности и преимущества

- **Архитектура плагинов:** Главное преимущество Kong. Огромное количество готовых плагинов для аутентификации (JWT, OAuth2), безопасности (Bot detection), управления трафиком (Rate Limiting) и др.
- **API Gateway "из коробки":** Предоставляет функциональность шлюза API, а не только Ingress-контроллера.
- **Поддержка Gateway API:** Kong активно развивает свою реализацию Gateway API.

#### Недостатки

- **Сложность:** Требует понимания не только концепций Kubernetes, но и архитектуры самого Kong.
- **Зависимость от БД (опционально):** В некоторых режимах для хранения конфигурации Kong может требоваться внешняя база данных (например, PostgreSQL).

**Вывод:** Идеальный выбор, если вам нужна функциональность API Gateway в кластере, и вы активно используете плагины для управления API.

### HAProxy

Один из самых старых, проверенных временем и высокопроизводительных прокси-серверов и балансировщиков нагрузки.

- **Основа:** HAProxy (написан на C).
- **Философия:** Максимальная производительность и надежность.

#### Особенности и преимущества

- **Экстремальная производительность:** Считается одним из самых быстрых прокси, способным обрабатывать огромные объемы трафика при низком потреблении ресурсов.
- **Надежность и стабильность:** Используется в индустрии десятилетиями в самых высоконагруженных системах.
- **Продвинутые проверки состояния (Health Checks):** Очень гибкие и настраиваемые проверки работоспособности бэкендов.

#### Недостатки

- **Ограниченная экосистема:** Меньше готовых плагинов и интеграций по сравнению с Kong или Traefik.
- **Менее динамичный:** Обновление конфигурации традиционно требовало перезагрузки, хотя современные версии улучшили этот аспект.

**Вывод:** Лучший выбор для систем, где требуется максимальная производительность, минимальные задержки и надежность.
