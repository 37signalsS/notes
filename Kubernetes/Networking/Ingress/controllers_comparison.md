# Ingress-контроллеры — сравнение и выбор

---
**Надёжность:** 10 (SSoT + Проектный контекст 2026)
**Свежесть:** Актуально на июль 2026
---

## Определения

**Ingress-контроллер** — это специализированное приложение (обычно `Deployment` или `DaemonSet`), которое реализует правила маршрутизации, описанные в объектах `Ingress` или `HTTPRoute`. Он отслеживает изменения в API Kubernetes и динамически настраивает нижележащий прокси-сервер (NGINX, Envoy, HAProxy, Traefik). Без Ingress-контроллера объект `Ingress` является лишь декларацией намерения и фактически не обрабатывает трафик.

**Критерии выбора контроллера:**

- **Производительность** — задержки (latency) и способность обрабатывать высокий RPS (Requests Per Second) с минимальным потреблением ресурсов.
- **Функциональность** — нативная поддержка TLS, аутентификации (OIDC, BasicAuth), Rate Limiting, WebSocket, gRPC, HTTP/3.
- **Простота эксплуатации** — качество документации, Helm-чартов, механизмы обновления без простоя и встроенные инструменты отладки (Dashboard).
- **Экосистема и стандарты** — поддержка Gateway API, интеграция с Service Mesh, Cert-manager и внешними системами безопасности (WAF).
- **Ресурсоемкость** — потребление CPU и памяти, особенно важно при большом количестве правил или в мульти-тентных кластерах.

## Контекст 2026 года: Статус проектов

### Закат Ingress-NGINX (kubernetes/ingress-nginx)

В марте 2026 года сообщество Kubernetes официально объявило о переходе проекта `kubernetes/ingress-nginx` в режим **End of Life (EOL)**. 
- **Причина:** Архитектурные ограничения NGINX при работе в высокодинамичных средах Kubernetes и фокус сообщества на Gateway API.
- **Последствия:** Контроллер больше не получает патчей безопасности. Использование в новых production-средах категорически не рекомендуется.
- **Рекомендация:** Миграция на **NGINX Gateway Fabric** (для любителей стека NGINX) или решения на базе **Envoy**.

### Gateway API — новый золотой стандарт

**Gateway API** стал основным способом управления трафиком. Большинство современных контроллеров либо полностью перешли на него, либо поддерживают его наравне с классическим Ingress. 

**Ключевые преимущества:**
- **Ролевая модель:** Четкое разделение ответственности (Инфраструктура vs Приложение).
- **Типизированная конфигурация:** Замена "войны аннотаций" на типизированные фильтры и CRD.
- **Кросс-неймспейс маршрутизация:** Возможность описывать правила для сервисов в разных пространствах имен в рамках одного шлюза.

## Классификация по архитектуре

| Тип | Примеры | Прокси | Характеристика |
| :--- | :--- | :--- | :--- |
| **Envoy-based** | Envoy Gateway, Contour, Cilium, Istio | Envoy (C++) | Максимальная производительность, нативная поддержка xDS API и Gateway API. |
| **eBPF-powered** | Cilium Ingress | Envoy + eBPF | Обработка L3/L4 в ядре Linux, экстремально низкий overhead. |
| **NGINX-based** | NGINX Gateway Fabric, Kong, Angie | NGINX | Проверенный временем движок, расширяемый через Lua или специализированные модули. |
| **Go-native** | Traefik | Собственный (Go) | Легкость в настройке, богатый встроенный функционал "из коробки". |

## Подробный обзор популярных контроллеров

### Traefik

Современный, облачно-ориентированный ("cloud-native") прокси-сервер, разработанный специально для динамических сред.

- **Основа:** Написан на Go.
- **Философия:** Максимальная автоматизация и "Zero Configuration".

**Особенности и преимущества:**
- **Автоматическое обнаружение (Service Discovery):** Traefik мгновенно реагирует на изменения в API Kubernetes, обновляя маршруты без перезагрузки (Zero Downtime).
- **Встроенная поддержка Let's Encrypt:** Полная автоматизация получения и обновления TLS-сертификатов (ACME) внутри контроллера.
- **Концепция Middleware:** Гибкая цепочка обработчиков (BasicAuth, ForwardAuth, RateLimit, Buffering, CircuitBreaker), которые можно применять к маршрутам через CRD.
- **Поддержка Gateway API:** Один из первых контроллеров, реализовавших полную поддержку Gateway API v1.x.
- **Веб-интерфейс (Dashboard):** Наглядная визуализация всех routers, services и middlewares, упрощающая поиск ошибок в конфигурации.

**Недостатки:**
- **Производительность:** В сценариях с экстремально высокими нагрузками (сотни тысяч RPS) Go-прокси может уступать Envoy или HAProxy.
- **Enterprise-функции:** Некоторые продвинутые возможности (например, распределенный Rate Limiting или поддержка FIPS) вынесены в платную версию Traefik Enterprise.

### Envoy Gateway

Официальное решение CNCF, призванное стать эталонной реализацией Gateway API.

- **Основа:** Envoy Proxy (C++).
- **Философия:** Стандартизация, масштабируемость и использование всей мощи Envoy без его сложности.

**Особенности и преимущества:**
- **Чистый Gateway API:** Не требует использования вендорских аннотаций; все функции (URL rewrite, redirects, header manipulation) настраиваются через стандартные фильтры Gateway API.
- **Производительность Envoy:** Минимальные задержки и эффективное использование ресурсов.
- **Расширяемость через WASM:** Возможность написания собственных фильтров обработки трафика на C++, Rust или Go (через WebAssembly).
- **Безопасность:** Встроенная поддержка OIDC, OAuth2 и интеграция с внешними Auth-сервисами.

**Недостатки:**
- **Относительная молодость:** Проект активно развивается, но может иметь меньше "community-рецептов" по сравнению с классическими решениями.

---

### Cilium Ingress / Gateway API

Часть экосистемы Cilium, использующая технологию eBPF для сетевой обработки.

- **Основа:** Envoy (для обработки L7), eBPF (для L3/L4).
- **Философия:** Производительность и безопасность через инновации в ядре Linux.

**Особенности и преимущества:**
- **Ускорение eBPF:** Пакеты обрабатываются максимально близко к сетевому интерфейсу, минуя многие слои сетевого стека ядра, что снижает задержки.
- **Замена kube-proxy:** Cilium может полностью заменить kube-proxy, обеспечивая более эффективную балансировку нагрузки.
- **Интеграция с политиками безопасности:** Глубокая связка с `CiliumNetworkPolicy`, позволяющая ограничивать трафик не только по IP, но и по DNS-именам или метаданным Gateway API.
- **Наблюдаемость (Hubble):** Полная прозрачность трафика: вы видите каждый запрос, его статус и задержки в интерфейсе Hubble.

**Недостатки:**
- **Требования к инфраструктуре:** Требуется свежая версия ядра Linux (5.10+) и установка Cilium как CNI.

---

### Istio Ingress Gateway

Стандартный компонент для тех, кто уже использует Service Mesh Istio.

- **Основа:** Envoy.
- **Философия:** Единая точка управления трафиком внутри и снаружи сервисной сетки.

**Особенности и преимущества:**
- **Единая конфигурация:** Использование объектов `Gateway` и `VirtualService` для управления всем трафиком.
- **Продвинутая безопасность:** Автоматическая mTLS-аутентификация между шлюзом и подами, интеграция с JWT.
- **Наблюдаемость:** Полная интеграция с Kiali, Jaeger и Prometheus "из коробки".

**Недостатки:**
- **Избыточность:** Устанавливать весь стек Istio только ради Ingress-контроллера — неоправданно дорого с точки зрения ресурсов.

---

### Contour

Высокопроизводительный Ingress-контроллер на базе **Envoy**, разработанный для современных динамических сред.

- **Основа:** Envoy Proxy.
- **Философия:** Устранение ограничений стандартного API Ingress через делегирование прав и расширенные возможности маршрутизации (через CRD `HTTPProxy`).

**Особенности и преимущества:**
- **Использование Envoy xDS API:** Contour динамически настраивает Envoy без перезагрузки, обеспечивая мгновенное применение изменений конфигурации.
- **Поддержка современных протоколов:** Нативная работа с HTTP/2, gRPC и WebSockets "из коробки".
- **CRD HTTPProxy:** Предлагает расширенную модель конфигурации, которая позволяет безопасно делегировать управление путями и доменами разным командам в кластере (Multi-tenancy).
- **Декларативность:** Четкое и понятное описание сложных правил маршрутизации без нагромождения аннотаций.
- **Масштабируемость:** Архитектура Contour (Control Plane отдельно от Data Plane) позволяет легко масштабировать прокси-слой независимо от контроллера.

**Недостатки:**
- **Зависимость от CRD:** Основная мощь раскрывается при использовании `HTTPProxy`, что требует изучения специфических для Contour ресурсов.

---

### Kong

Контроллер, выросший из мощного API Gateway.

- **Основа:** NGINX с модулями на Lua (OpenResty).
- **Философия:** Управление жизненным циклом API и расширяемость через плагины.

**Особенности и преимущества:**
- **Архитектура плагинов:** Сотни готовых плагинов для трансформации запросов, логирования, интеграции с внешними системами (Keycloak, Datadog).
- **API Gateway функции:** Идеален, если вам нужны продвинутые возможности: управление квотами, монетизация API, портал для разработчиков.
- **Гибридный режим:** Возможность разделения Data Plane и Control Plane для работы в распределенных средах.

**Недостатки:**
- **Сложность:** Архитектура Kong сложнее, чем у чистого Ingress-контроллера.
- **База данных:** В некоторых конфигурациях (DB-mode) требует PostgreSQL или Cassandra.

---

### HAProxy Ingress

Решение для тех, кому важна максимальная надежность и производительность балансировщика.

- **Основа:** HAProxy (написан на C).
- **Философия:** Стабильность, проверенная десятилетиями.

**Особенности и преимущества:**
- **Экстремальная производительность:** HAProxy часто показывает лучшие результаты в тестах на пропускную способность и стабильность задержек под высокой нагрузкой.
- **Гибкие Health Checks:** Очень детальные настройки проверки работоспособности бэкендов.
- **Поддержка сложных алгоритмов балансировки:** Кроме стандартного Round Robin, поддерживает `leastconn`, `source` (sticky sessions) и другие.

**Недостатки:**
- **Ограниченная экосистема:** Меньше готовых расширений по сравнению с Kong или Traefik.
- **Конфигурация:** Генерация конфига HAProxy из Ingress-ресурсов может быть менее гибкой, чем у Envoy-решений.

---

### NGINX Gateway Fabric

Официальный наследник от F5/NGINX, разработанный с нуля для соответствия Gateway API.

- **Основа:** NGINX.
- **Философия:** Преемственность производительности NGINX в мире Gateway API.

**Особенности и преимущества:**
- **Нативная поддержка Gateway API:** Разработан специально под новую спецификацию, избегая нагромождения аннотаций.
- **Производительность NGINX:** Использование всех преимуществ архитектуры NGINX для обработки HTTP/HTTPS трафика.

## Практические сценарии выбора

### Сценарий 1 — Малая команда или стартап
**Требования:** Минимум времени на настройку, автоматический SSL, наглядность.
**Рекомендация: Traefik**
- Быстрый старт через Helm.
- Автоматический Let's Encrypt через конфигурацию одной строкой.
- Встроенный Dashboard для быстрой диагностики.

### Сценарий 2 — Высоконагруженная микросервисная среда
**Требования:** Минимальные задержки, глубокая наблюдаемость, Gateway API.
**Рекомендация: Envoy Gateway или Cilium**
- Envoy Gateway для чистого следования стандартам.
- Cilium, если требуется максимальная скорость и интеграция с сетевым уровнем (eBPF).

### Сценарий 3 — Корпоративная платформа с управлением API
**Требования:** OAuth2/OIDC на входе, лимиты запросов на уровне пользователей, логирование в ELK.
**Рекомендация: Kong**
- Богатый выбор плагинов для решения бизнес-задач.
- Зрелое решение для управления публичными API.

### Сценарий 4 — Кластер с Service Mesh
**Требования:** mTLS, сквозная трассировка, единое управление политиками.
**Рекомендация: Istio Ingress Gateway**
- Нативная интеграция с остальными компонентами меша.
