## Определения

**Ingress** — это объект API Kubernetes, который описывает правила маршрутизации внешнего HTTP и HTTPS трафика к сервисам внутри кластера. Он действует как "умный" маршрутизатор или точка входа, позволяя определять правила маршрутизации на основе имени хоста (например, `api.example.com`) или пути (например, `/v1/users`). Ingress работает на **7 уровне модели OSI (прикладной уровень)** и позволяет централизованно управлять доступом к множеству сервисов через единый IP-адрес.

**Ingress-контроллер** — это приложение (обычно `Deployment` или `DaemonSet`), которое фактически реализует правила, описанные в объекте `Ingress`. Он отслеживает изменения в API-сервере Kubernetes и настраивает нижележащий прокси-сервер (например, NGINX, HAProxy, Traefik). **Без Ingress-контроллера объект Ingress не будет работать.**

**Зачем нужен Ingress-контроллер:**
- **Единая точка входа:** Действует как "входная дверь" для всего внешнего трафика, упрощая управление множеством маршрутов.
- **Маршрутизация L7:** Позволяет направлять запросы на разные сервисы на основе доменного имени или пути URL (path-based routing).
- **Терминация SSL/TLS:** Разгружает приложения от задач шифрования, выполняя расшифровку трафика на уровне контроллера.
- **Балансировка нагрузки:** Включает встроенные механизмы распределения трафика между подами.
- **Безопасность и Интеграция:** Поддержка внешних **WAF** (Web Application Firewall), систем **SSO** (Single Sign-On) и аутентификации. Для облачных контроллеров (например, AWS ALB) управление правами доступа реализуется через **IRSA (IAM Roles for Service Accounts)**.

**IngressClass** — ресурс, позволяющий разделить Ingress-контроллеры внутри одного кластера. Например, можно иметь один контроллер для внешнего трафика и другой для внутреннего, помечая ресурсы `Ingress` соответствующим `ingressClassName`.

**Ключевые компоненты:**

- **Ресурс Ingress** — манифест с правилами маршрутизации (объект API).
- **Ingress-контроллер** — приложение, реализующее эти правила.
- **Правила (Rules)** — условия маршрутизации (хост, путь).
- **Бэкенд-сервисы (Backend Services)** — целевые сервисы Kubernetes, обрабатывающие трафик.
- **Конфигурация TLS** — настройки для обеспечения безопасной связи (HTTPS).
- **Аннотации (Annotations)** — дополнительные параметры настройки поведения контроллера (таймауты, лимиты, rewrite-правила).
- **IngressClass** — селектор для выбора конкретного контроллера.

## Внутренний жизненный цикл: Как работает Ingress-контроллер

Хотя реализация зависит от конкретного контроллера (NGINX, Traefik, Envoy), общий алгоритм работы (Control Plane) выглядит следующим образом:

1.  **Создание ресурса:** Пользователь создает объект `Ingress` (манифест YAML), описывающий правила маршрутизации и настройки TLS.
2.  **API Watcher:** Контроллер постоянно наблюдает за API-сервером Kubernetes. При обнаружении нового, измененного или удаленного ресурса `Ingress`, контроллер считывает его спецификацию.
3.  **Конфигурация маршрутизации:** На основе полученных данных контроллер динамически генерирует конфигурацию для своего базового прокси-движка (например, обновляет `nginx.conf` или xDS-конфигурацию Envoy). Это включает настройку виртуальных хостов, путей и TLS-сертификатов.
4.  **Обработка трафика (Data Plane):** Контроллер перехватывает входящий трафик, предназначенный для внешнего IP или домена кластера. Он анализирует заголовки запроса (`Host`, `Path`), чтобы сопоставить его с правилом маршрутизации.
5.  **Балансировка и SSL:** Если указано в правилах, контроллер выполняет терминацию SSL и выбирает стратегию балансировки между целевыми подами.
6.  **Проксирование:** Определив целевой сервис, контроллер направляет запрос напрямую к подам приложения через внутреннюю сеть кластера.
7.  **Обработка ответа:** Контроллер получает ответ от пода и передает его клиенту, устанавливая необходимые заголовки и коды состояния.
8.  **Мониторинг:** Параллельно контроллер собирает метрики и логи трафика для анализа и отладки.

### Поток трафика: от клиента к приложению 

Для успешной работы приложения запрос от пользователя должен пройти следующие этапы (проверка этой цепочки — основа диагностики):

1.  **DNS-резолвинг:** Клиентский запрос (например, к `myapp.example.com`) разрешается DNS к IP-адресу внешнего балансировщика (LoadBalancer).
2.  **Перехват контроллером:** Балансировщик направляет запрос в Ingress-контроллер. Контроллер видит заголовок **Host** и сопоставляет его с правилом Ingress.
3.  **Маршрутизация к Service:** Контроллер находит целевой Service, указанный в правиле, и порт. 
    *   **Важно:** Ingress может маршрутизировать трафик к сервису типа `ClusterIP`, это стандартная и безопасная практика. Ошибкой является попытка прямого доступа к `ClusterIP` извне без Ingress/Gateway.
4.  **Отправка к Pod:** Через Service трафик направляется к соответствующему поду на его `targetPort` (обычно напрямую по IP из Endpoints).
5.  **Обработка в контейнере:** Контейнерное приложение прослушивает порт (например, 8080) и обрабатывает запрос.

### Как Ingress находит поды (Механизм Endpoints)

Вопреки распространенному мнению, Ingress-контроллер обычно направляет трафик **напрямую на IP-адреса подов**, минуя `ClusterIP` сервиса. Это делается для минимизации задержек и исключения лишнего шага NAT через `kube-proxy`.

**Цепочка обнаружения:**
1.  **Service:** В манифесте Ingress указывается имя целевого `Service`.
2.  **Endpoints:** При создании Service Kubernetes автоматически создает объект `Endpoints` (или `EndpointSlice`), содержащий актуальный список IP-адресов и портов всех подов, соответствующих селектору сервиса.
3.  **Разрешение (Resolution):** Ingress-контроллер запрашивает объект `Endpoints`, связанный с указанным сервисом, и получает "живой" список сетевых адресов.
4.  **Прямая маршрутизация:** Контроллер использует этот список для балансировки трафика непосредственно между подами. Kubernetes автоматически обновляет `Endpoints` при масштабировании, обновлении или сбоях подов, обеспечивая актуальность маршрутов в контроллере.

### Сравнение: Ingress и Service

Хотя для публикации приложений можно использовать `Service` типа `LoadBalancer` или `NodePort`, `Ingress` является предпочтительным решением для HTTP/HTTPS трафика по нескольким ключевым причинам:

| Критерий | Service (L4) | Ingress (L7) |
| :--- | :--- | :--- |
| **Уровень OSI** | Транспортный (TCP/UDP) | Прикладной (HTTP/HTTPS) |
| **Маршрутизация** | По порту | По хосту и пути |
| **Внешние IP** | Один IP на сервис | Один IP на все сервисы |
| **TLS** | Ручная настройка на сервисе | Централизованная терминация |
| **Гибкость** | Ограниченная | Расширяемая (аннотации) |

**Преимущества Ingress:**

1. **Маршрутизация на L7** — гибкие правила на основе имени хоста и пути
2. **Централизованная точка входа** — один внешний IP для множества сервисов
3. **Терминация TLS** — централизованное управление SSL-сертификатами
4. **Гибкая конфигурация** — аутентификация, ограничение частоты запросов (Rate Limiting), перезапись URL через аннотации

## Основные концепции

### Внешний доступ к Ingress-контроллеру

Для обработки внешнего трафика Ingress-контроллер должен быть выставлен наружу кластера. При этом критически важны два параметра:

1. **`externalTrafficPolicy`**:
   - `Cluster` (по умолчанию): трафик может перенаправляться между узлами. Скрывает реальный IP клиента (заменяется на IP узла).
   - `Local`: трафик остается на узле, принявшем запрос. Сохраняет реальный IP клиента, но требует наличия подов контроллера на всех принимающих узлах.

2. **PROXY Protocol**:
   - Если Ingress стоит за внешним L4 балансировщиком, для получения реального IP клиента необходимо включить поддержку PROXY-протокола как на балансировщике, так и в конфигурации контроллера (через `ConfigMap`).

| Способ | Описание | Применение |
| :--- | :--- | :--- |
| **LoadBalancer** | Service типа `LoadBalancer`, облачный провайдер выделяет внешний IP | Облачные среды (AWS, GCP, Azure), MetalLB |
| **NodePort** | Service типа `NodePort`, доступ на порту каждого узла | On-premise, тестовые среды |
| **Manual Proxy** | Внешний Nginx/HAProxy проксирует трафик на NodePort | Bare-metal при отсутствии MetalLB |
| **HostPort / HostNetwork** | Публикация порта непосредственно на сетевом интерфейсе узла | Максимальная производительность, риск конфликтов портов |

Подробное описание настройки Manual Proxy (NodePort + Nginx + dnsmasq) см. в [соответствующем руководстве](./bare_metal_manual_proxy.md).

### Правила маршрутизации

Ingress поддерживает два типа маршрутизации:

- **Host-based** — маршрутизация по имени хоста (`api.example.com` → один сервис, `shop.example.com` → другой)
- **Path-based** — маршрутизация по пути URL (`example.com/api` → API сервис, `example.com/` → фронтенд)

Подробные примеры манифестов для каждого типа доступны в разделе [Практические сценарии](#практические-сценарии).

### Режимы работы TLS

#### Режим 1 — TLS Termination (Терминация TLS)

Сертификат прикреплён к Ingress через Secret, контроллер расшифровывает трафик и передаёт бэкенду по HTTP.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-ingress
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls-secret
  rules:
  - host: api.example.com
    http:
      paths:
      - pathType: Prefix
        path: /
        backend:
          service:
            name: api-service
            port:
              number: 8080
```

**Характеристики:**

- Контроллер видит HTTP-заголовки
- Доступна маршрутизация по пути, заголовкам, cookies
- Бэкенд получает трафик по HTTP (или HTTPS при использовании re-encrypt)

#### Режим 2 — SSL Passthrough (Сквозное шифрование)

Контроллер проксирует зашифрованный поток напрямую к поду, не расшифровывая его. Включается аннотацией (зависит от контроллера):

```yaml
metadata:
  annotations:
    nginx.ingress.kubernetes.io/ssl-passthrough: "true"
```

**Характеристики:**

- Контроллер **не видит HTTP-заголовки**
- Маршрутизация возможна **только по SNI** (Server Name Indication — имени хоста в TLS Client Hello)
- Маршрутизация по пути или заголовкам **недоступна**
- Бэкенд сам терминирует SSL

> **Важно для миграции:** Если для одного хоста одновременно используются passthrough и HTTP-маршрутизация — архитектуру придётся пересматривать. Зафиксируйте для каждого хоста режим TLS до начала миграции на Gateway API.

### Архитектурные паттерны — связка LB, Ingress и ALB

Доступ к кластеру в production-средах обычно строится на комбинации внешних балансировщиков нагрузки (LB) и внутренних Ingress-контроллеров. Существует три основных паттерна организации этой связки:

#### 1. L4 Load Balancer + внутрикластерный Ingress-контроллер

Традиционный подход, используемый в большинстве кластеров (включая облачные среды по умолчанию и bare-metal с MetalLB).

**Путь трафика:** `Клиент → L4 NLB (TCP) → Ingress Controller Pod (Nginx/Traefik) → Service → Backend Pod`

- **Внешний LB (Network Load Balancer, NLB):** Работает на 4-м уровне OSI. Распределяет голый TCP-трафик между узлами Kubernetes (на порты сервиса типа `LoadBalancer`, за которым стоит Ingress).
- **Ingress Controller:** Работает внутри кластера. Принимает TCP-трафик, терминирует TLS-соединение и выполняет L7-маршрутизацию (HTTP/HTTPS) на основе доменного имени или пути.
- **Преимущества:** Независимость от облачного провайдера, единая точка конфигурации Ingress внутри кластера, богатый выбор контроллеров.
- **Недостатки:** Дополнительный "хоп" (переход) внутри кластера, Ingress Controller требует ресурсов (CPU/RAM).

#### 2. L7 Load Balancer (ALB) как Ingress

Подход, при котором внешний облачный балансировщик (например, AWS Application Load Balancer) берет на себя роль Ingress-контроллера.

**Путь трафика:** `Клиент → AWS ALB (L7 HTTP/HTTPS) → (через Target Group) → Backend Pod IP` (или NodePort)

- **Как это работает:** В кластере запускается специализированный контроллер (например, AWS Load Balancer Controller). При создании манифеста `Ingress`, этот контроллер обращается к API облака (AWS) и напрямую настраивает внешний ALB, создавая правила Listener и Target Groups.
- **Особенности ALB:** ALB сам терминирует TLS (часто используя сертификаты из AWS ACM) и маршрутизирует трафик сразу на поды приложения (если используется интеграция с VPC CNI) или на NodePort'ы.
- **Преимущества:** Снятие нагрузки с кластера (TLS-терминация и L7-роутинг происходят в облаке), нативная интеграция с облачными сервисами безопасности (WAF, Shield).
- **Недостатки:** Жесткая привязка (Vendor Lock-in) к конкретному облачному провайдеру, каждый `Ingress` ресурс может создавать отдельный платный ALB (если не использовать Ingress Grouping).

#### 3. Bare-Metal с MetalLB + Ingress-контроллер

Аналог стандартного подхода для локальных дата-центров (без облачных LoadBalancer-ов).

**Путь трафика:** `Клиент → Маршрутизатор дата-центра (BGP) → Узел Kubernetes → Ingress Controller Pod → Backend Pod`

- **MetalLB:** Анонсирует внешний IP-адрес сервиса `LoadBalancer` (за которым стоит Ingress-контроллер) внешнему маршрутизатору дата-центра по протоколу BGP или локально через L2 (ARP/NDP).
- **Внешний доступ:** Клиент подключается к публичному IP, пакеты доставляются на узел, выбранный MetalLB, где `kube-proxy` направляет их в Ingress Controller.

## Практические сценарии

### Сценарий 1 — маршрутизация по хосту

Направление трафика с разных доменов на разные сервисы:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-host-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: "foo.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: foo-service
                port:
                  number: 80
    - host: "bar.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: bar-service
                port:
                  number: 80
```

**Использование:** Разделение API (`api.example.com`) и веб-интерфейса (`app.example.com`).

### Сценарий 2 — маршрутизация по пути

Направление трафика одного домена на разные сервисы в зависимости от пути:

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
spec:
  ingressClassName: nginx
  rules:
    - host: "myapp.example.com"
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service
                port:
                  number: 80
```

**Типы путей:**

- `pathType: Prefix` — соответствует любому пути, начинающемуся с указанного (`/api/v1`, `/api/v2`)
- `pathType: Exact` — точное совпадение пути
- `pathType: ImplementationSpecific` — зависит от реализации контроллера

**Использование:** Микросервисная архитектура, где `/api` идёт на бэкенд, а `/` — на фронтенд.

### Сценарий 3 — Default Backend (Бэкенд по умолчанию)

Сервис для обработки трафика, не соответствующего правилам:

```yaml
spec:
  ingressClassName: nginx
  defaultBackend:
    service:
      name: default-service
      port:
        number: 80
  rules:
    # ... правила ...
```

**Использование:** Страница-заглушка или сервис ошибок для необработанных запросов.

### Сценарий 4 — TLS с несколькими сертификатами

```yaml
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls-secret
  - hosts:
    - shop.example.com
    secretName: shop-tls-secret
  rules:
  - host: api.example.com
    # ...
  - host: shop.example.com
    # ...
```

**Использование:** Разные SSL-сертификаты для разных доменов.

## Устранение неполадок Ingress (Troubleshooting)

Внешний доступ через Ingress — это сложная цепочка компонентов. Если пользователи получают ошибки **404 Not Found** или **502 Bad Gateway**, необходимо методично проверить каждое звено пути запроса.

### Путь входящего трафика (North-South)

Для успешной диагностики важно понимать полный путь запроса:
`Внешний DNS → Облачный балансировщик (LoadBalancer) → Ingress Controller → Service → Pod`

### Алгоритм диагностики внешнего доступа

Если внешнее приложение недоступно, следуйте от внешнего контура внутрь кластера:

1.  **Проверка внешнего пути (DNS и LoadBalancer):**
    *   **DNS:** Указывают ли DNS-записи для хоста (например, `myapp.example.com`) на IP-адрес балансировщика нагрузки, созданного контроллером?
    *   **LoadBalancer:** Узнайте внешний IP контроллера: `kubectl get svc -n <ingress-namespace>`. Если `EXTERNAL-IP` находится в статусе `<pending>`, проблема на стороне облачного провайдера или MetalLB.
    *   Проверьте доступность IP напрямую через `curl -k https://<EXTERNAL-IP>`.

2.  **Проверка Ingress-контроллера (Active Component):**
    Сам объект Ingress — это просто запись в базе данных; без контроллера (NGINX, Traefik, HAProxy) она не работает.
    *   **Статус контроллера:** Проверьте поды контроллера в `kube-system` или выделенном пространстве имен.
    *   **Логи контроллера:** Ищите сообщения о невозможности найти Backend-сервис или об ошибках перезагрузки конфигурации (Reload failed).

3.  **Проверка ресурса Ingress (Routing Map):**
    *   **Mapping:** Правильно ли указано **имя службы** и **порт службы**? Соответствует ли порт в Ingress порту, на котором сервис слушает трафик (L7 -> L4 mapping)?
    *   **Rules:** Соответствуют ли `host` и `path` вашему реальному запросу? Убедитесь, что заголовок `Host` в HTTP-запросе совпадает с полем `host` в манифесте.

4.  **Проверка Service и Pod (Last Mile):**
    *   **Тип сервиса:** Частая ошибка — попытка внешнего доступа к сервису типа `ClusterIP` напрямую. Для Ingress тип `ClusterIP` корректен, так как контроллер находится внутри кластера.
    *   **Селекторы (Labels):** Селектор Сервиса создает важнейшую связь между Сервисом и Подами. Если в метках или селекторе допущена опечатка, Служба не найдет ни одного модуля.
    *   **Быстрая проверка:** Самый быстрый способ проверить работу селектора — запустить `kubectl describe svc <имя-сервиса>` и проверить поле **Endpoints**. Если оно пусто или содержит `<none>`, это явный признак несоответствия селектора.
    *   **Порты:** Проверьте `targetPort` в сервисе. Прослушивает ли контейнер этот порт (например, 8080)?

5.  **Сетевые политики (NetworkPolicies):**
    *   NetworkPolicy может блокировать трафик от Ingress-контроллера к подам приложения. Убедитесь, что разрешен входящий трафик из пространства имен, где работает контроллер.

> **Совет для собеседования:**
> **Вопрос:** Вы развернули приложение, Ingress и Service, но оно недоступно извне. Какова роль селектора службы в этом сценарии и каков самый быстрый способ проверить его работу?
> **Ответ:** Селектор — это набор меток, которые Сервис использует для поиска подов серверной группы. Если есть опечатка, связь разорвется. Самый быстрый способ проверки — команда `kubectl describe svc <имя-сервиса>`. Если поле `Endpoints` пусто, значит селектор не нашел ни одного работающего пода. Далее я прослежу путь трафика: DNS -> LoadBalancer -> Ingress Rules -> Service -> Pod. Частая ошибка — несоответствие меток или использование порта в Ingress, который сервис не прослушивает. Также важно убедиться, что контроллер Ingress вообще запущен в кластере, так как сам объект Ingress не выполняет активных действий.

## Дополнительная информация

### Gateway API — эволюция Ingress

**Gateway API** — новое поколение API для управления трафиком в Kubernetes, разработанное для решения фундаментальных ограничений Ingress:

- **Стандартизация** — единая спецификация для всех вендоров (Envoy, Cilium, Istio, Traefik)
- **Ролевая модель** — разделение ответственности между инфраструктурой и разработчиками
- **Расширенные функции** — канареечные развертывания, gRPC, TCP/UDP маршрутизация из коробки

Подробное описание концепции и примеры использования доступны в документе [Kubernetes Gateway API](../gateway_api/definitions.md).

### Миграция с Ingress на Gateway API

Сообщество Kubernetes рекомендует переходить на Gateway API для новых проектов. Инструмент **ingress2gateway** автоматизирует преобразование манифестов Ingress в Gateway API.

Руководство по миграции: [Миграция с Ingress на Gateway API](../gateway_api/migration.md).
