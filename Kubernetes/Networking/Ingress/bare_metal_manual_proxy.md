# Внешний доступ в Bare-metal: NodePort + Nginx + dnsmasq

## Definitions

**NodePort** — тип сервиса Kubernetes, который открывает определенный порт на всех узлах кластера. Трафик, поступающий на этот порт, перенаправляется на соответствующие поды.

**dnsmasq** — легкий DNS-сервер, используемый для централизованного управления доменными именами в локальной сети или на этапе разработки (DEV-среды).

**Nginx Proxy** — внешний по отношению к кластеру прокси-сервер, который принимает HTTP/HTTPS трафик на стандартных портах (80/443) и перенаправляет его на `NodePort` узлов Kubernetes.

---

## Basic Concepts

В bare-metal средах часто возникают сложности с использованием `MetalLB` в режиме L2 (из-за блокировки ARP между сегментами сети) или BGP (из-за отсутствия поддержки на оборудовании). Комбинация внешнего прокси и централизованного DNS является надежным обходным решением для DEV-стендов и этапов миграции.

### Архитектура решения

1. **Клиент** запрашивает имя (например, `service-a.k8s`).
2. **DNS (dnsmasq)** возвращает IP-адрес внешнего прокси-сервера.
3. **Nginx** принимает запрос и перенаправляет его на `NodePort` одной из worker-нод.
4. **kube-proxy** на ноде доставляет трафик в целевой Pod.

**Преимущества:**

- Использование стандартных портов (80/443) для пользователей.
- Чистые и понятные URL вместо `IP:Port`.
- Централизованное управление именами через DNS.
- Отсутствие необходимости в сложных сетевых протоколах (ARP/BGP).

## Practical Scenarios

### Шаг 1: Настройка DNS (dnsmasq)

На выделенном сервере (обычно там же, где Nginx) добавляются записи для доменной зоны `.k8s`.

```bash
# Файл /etc/dnsmasq.d/k8s-local.conf
address=/service-a.k8s/192.168.1.100
address=/service-b.k8s/192.168.1.100
address=/service-c.k8s/192.168.1.100
```

*Где `192.168.1.100` — IP-адрес сервера с Nginx.*

```bash
sudo systemctl restart dnsmasq
```

### Шаг 2: Настройка Nginx Proxy

Конфигурация Nginx как reverse proxy для балансировки трафика между узлами кластера.

```nginx
# Файл /etc/nginx/conf.d/k8s-proxy.conf

# Группа worker-нод кластера
upstream k8s-backend {
    server 192.168.1.11:31895; # worker-нода 1
    server 192.168.1.12:31895; # worker-нода 2
}

# Определение виртуальных хостов
server {
    listen 80;
    server_name service-a.k8s;
    location / {
        proxy_pass http://k8s-backend/service-a/;
        proxy_set_header Host $host;
    }
}

server {
    listen 80;
    server_name service-b.k8s;
    location / {
        proxy_pass http://k8s-backend/service-b/;
        proxy_set_header Host $host;
    }
}
```

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### Шаг 3: Настройка клиентов

Все серверы и рабочие станции в сети должны использовать настроенный DNS-сервер в качестве основного в `/etc/resolv.conf`. Это избавляет от необходимости править `/etc/hosts` на каждой машине.

## Additional Information

### Рекомендации

- **Автоматизация:** При добавлении новых сервисов в Kubernetes необходимо обновлять конфигурацию Nginx и dnsmasq. Это можно автоматизировать с помощью скриптов или инструментов управления конфигурацией (Ansible).
- **Отказоустойчивость:** Для исключения Nginx как единой точки отказа можно использовать `Keepalived` для создания отказоустойчивой пары прокси-серверов.
- **Масштабируемость:** В секцию `upstream` следует включать все активные worker-ноды, на которых могут быть запущены поды (или те, на которых работает Ingress-контроллер в режиме NodePort).
