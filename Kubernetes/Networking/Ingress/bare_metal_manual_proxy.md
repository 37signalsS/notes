# Внешний доступ в Bare-metal — NodePort, Nginx и dnsmasq

## Определения

**NodePort** — тип сервиса Kubernetes, который открывает статический порт на всех узлах кластера. Трафик, поступающий на этот порт, перенаправляется на соответствующие поды через ClusterIP сервиса.

**dnsmasq** — легкий DNS-сервер, используемый для централизованного управления доменными именами в локальной сети или на этапе разработки (DEV-среды).

**Nginx-прокси (Nginx Proxy)** — внешний по отношению к кластеру прокси-сервер, который принимает HTTP/HTTPS трафик на стандартных портах (80/443) и перенаправляет его на `NodePort` узлов Kubernetes.

---

## Основные концепции

В bare-metal средах часто возникают сложности с использованием `MetalLB` в режиме L2 (из-за блокировки ARP между сегментами сети) или BGP (из-за отсутствия поддержки на сетевом оборудовании). Комбинация внешнего прокси и централизованного DNS является надежным обходным решением для DEV-стендов и этапов миграции.

### Архитектура решения

1. **Клиент** запрашивает доменное имя (например, `service-a.k8s`).
2. **DNS (dnsmasq)** возвращает IP-адрес внешнего прокси-сервера.
3. **Nginx** принимает запрос и балансирует его между `NodePort` рабочих узлов (worker nodes) кластера.
4. **kube-proxy** на узле доставляет трафик в целевой Pod.

**Преимущества:**

- Использование стандартных портов (80/443) для конечных пользователей.
- Понятные URL вместо комбинаций `IP:Port`.
- Централизованное управление именами через DNS.
- Отсутствие необходимости в поддержке ARP/BGP сетевым оборудованием.

## Практические сценарии

### Шаг 1 — настройка DNS (dnsmasq)

На выделенном сервере (обычно совмещенном с Nginx) добавляются записи для локальной доменной зоны.

```bash
# Файл /etc/dnsmasq.d/k8s-local.conf
address=/service-a.k8s/192.168.1.100
address=/service-b.k8s/192.168.1.100
address=/service-c.k8s/192.168.1.100
```

*Где `192.168.1.100` — IP-адрес сервера с Nginx.*

```bash
sudo systemctl restart dnsmasq
```

### Шаг 2 — настройка Nginx Proxy

Конфигурация Nginx как reverse proxy для балансировки трафика между узлами кластера.

```nginx
# Файл /etc/nginx/conf.d/k8s-proxy.conf

# Группа рабочих узлов (worker-нод) кластера
upstream k8s-backend {
    server 192.168.1.11:31895; # worker-нода 1
    server 192.168.1.12:31895; # worker-нода 2
}

# Определение виртуальных хостов
server {
    listen 80;
    server_name service-a.k8s;
    location / {
        proxy_pass http://k8s-backend/service-a/;
        proxy_set_header Host $host;
    }
}

server {
    listen 80;
    server_name service-b.k8s;
    location / {
        proxy_pass http://k8s-backend/service-b/;
        proxy_set_header Host $host;
    }
}
```

```bash
sudo nginx -t
sudo systemctl reload nginx
```

### Шаг 3 — настройка клиентов

Все серверы и рабочие станции в сети должны использовать настроенный DNS-сервер (dnsmasq) в качестве основного в `/etc/resolv.conf`. Это избавляет от необходимости править `/etc/hosts` на каждой локальной машине.

## Дополнительная информация

### Рекомендации

- **Автоматизация:** При добавлении новых сервисов в Kubernetes необходимо обновлять конфигурацию Nginx и dnsmasq. Для этого рекомендуется использовать Ansible или специализированные контроллеры (например, ExternalDNS для dnsmasq).
- **Отказоустойчивость:** Для исключения Nginx как единой точки отказа (SPOF) используйте `Keepalived` или `HAProxy` для создания отказоустойчивого кластера балансировки.
- **Масштабируемость:** В секцию `upstream` следует включать все активные worker-ноды, где запущен Ingress-контроллер в режиме NodePort.
