# Service

**Service** — это абстракция Kubernetes, которая определяет логическую группу `Pod`-ов и политику доступа к ним. Он предоставляет **стабильную сетевую точку входа** (IP-адрес и DNS-имя), которая не меняется, даже если `Pod`-ы, стоящие за ней, перезапускаются или перемещаются.

Основная задача `Service` — решить проблему непостоянства `Pod`-ов. `Pod`-ы могут быть уничтожены и созданы заново, получая новые IP-адреса. `Service` обеспечивает постоянный адрес, на который могут полагаться другие компоненты системы.

Связь между `Service` и `Pod`-ами устанавливается с помощью **меток и селекторов** (`labels` и `selectors`).

## Способы публикации приложений

В Kubernetes существует два основных подхода к публикации приложений и обеспечению внешнего доступа к ним. Приложение, запущенное в кластере, по умолчанию работает как в своеобразном "черном ящике", и для доступа к нему извне требуются дополнительные манипуляции с объектами Kubernetes.

1.  **Service**: Обеспечивает сетевое взаимодействие внутри кластера и может быть использован для ограниченного внешнего доступа. Работает на уровне L3/L4 (OSI), используя NAT и `kube-proxy` для маршрутизации трафика.
2.  **Ingress**: Предоставляет более гибкий и мощный механизм для внешнего доступа, особенно для HTTP/HTTPS трафика. Работает на уровне L7 (OSI), используя Ingress-контроллеры (например, Nginx, Envoy, Traefik, HAProxy). Подробнее об Ingress можно узнать в документе [Ingress](./ingress.md).

## Коммуникация между Подами (Pod-to-Pod)

Рассмотрим сценарий: вы находитесь в консоли одного пода (`Под А`) и хотите отправить запрос другому поду (`Под Б`).

### Способ 1: Напрямую по IP-адресу пода (Не рекомендуется)

Каждый под имеет свой уникальный IP-адрес в кластере. Технически, вы можете узнать IP пода `Б` и обратиться к нему:

```bash
# Находясь в консоли пода А
curl http://<IP-адрес-пода-Б>:<порт>
```

**Это плохая практика, так как:**

- **Поды эфемерны:** Они могут быть перезапущены или заменены в любой момент.
- **IP-адрес не стабилен:** При каждом пересоздании под получит новый IP-адрес, и связь нарушится.

### Способ 2: Через Service (Правильный и рекомендуемый способ)

Правильный способ — создать `Service` для пода `Б`. `Service` предоставляет стабильный DNS-адрес и IP-адрес.

```bash
# Если сервис находится в том же неймспейсе, что и Под А:
curl http://<имя-сервиса-Б>:<порт>

# Если сервис находится в другом неймспейсе:
curl http://<имя-сервиса-Б>.<имя-неймспейса-Б>.svc.cluster.local:<порт>
```

Kubernetes через внутренний DNS сам преобразует имя сервиса в его `ClusterIP`, а `kube-proxy` затем направит запрос на один из здоровых подов `Б`, стоящих за этим сервисом.

## Service Discovery и kube-proxy

### Используйте DNS для Service Discovery

DNS даёт гибкость и устойчивость к изменениям IP/эндпойнтов.

```
# Обращайтесь к сервисам через DNS
http://my-service.my-namespace.svc.cluster.local
http://my-service.my-namespace  # Сокращённая форма
http://my-service              # В пределах того же namespace
```

Kubernetes предлагает два основных способа обнаружения сервисов:

*   **DNS:** Внутренний DNS-сервер кластера (например, CoreDNS) создает A/AAAA-записи для каждого `Service`. Любой `Pod` в том же `namespace` может обратиться к сервису просто по его имени (например, `my-service`). `Pod` из другого `namespace` может использовать `my-service.namespace-name.svc.cluster.local`. **Это рекомендуемый способ.**
*   **Переменные окружения:** Когда `Pod` создается, `kubelet` добавляет в него переменные окружения для каждого активного `Service`. Этот метод имеет ограничения, например, `Pod` не получит переменные для `Service`, созданного после него.

За маршрутизацию трафика от `Service` к нужным `Pod`-ам отвечает компонент **`kube-proxy`**, который работает на каждом узле. Он использует один из режимов:

*   `iptables` (стандартный): настраивает правила `iptables` для перехвата и перенаправления трафика.
*   `ipvs`: использует IPVS (IP Virtual Server) для более производительной балансировки.
*   `userspace` (устарел).

## Типы сервисов

В Kubernetes доступны следующие типы сервисов:

*   **ClusterIP**
*   **NodePort**
*   **LoadBalancer**
*   **ExternalName**
*   **ExternalIPs**

### `ClusterIP`

*   **Описание:** Предоставляет внутренний IP-адрес, доступный **только внутри кластера**. Это тип **по умолчанию**.
*   **Использование:** Для внутренней коммуникации между компонентами приложения (например, бэкенд обращается к базе данных или кэшу).

**Два ключевых правила работы Service:**

1.  **Совпадение селектора с метками:** `Service` понимает, на какие поды отправлять трафик, только по механизму **селектора меток** (`selector`). Селектор сервиса должен точно совпадать с метками подов, на которые он должен направлять трафик.
2.  **Один и тот же Namespace:** Под и сервис должны работать в одном и том же `namespace`, иначе они не смогут найти друг друга.

**Пример манифеста `ClusterIP` Service:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app
  type: ClusterIP # Явно указываем тип ClusterIP, хотя это и значение по умолчанию
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 8080
```

**Публикация `ClusterIP` сервиса наружу (только для отладки/разработки):**
Чисто технически, `ClusterIP` сервис не предназначен для публикации наружу. Однако, для целей отладки или локальной разработки можно использовать следующие методы:

1.  **`kubectl proxy`**: Создает прокси-сервер, который позволяет обращаться к API Kubernetes и, через него, к сервисам.
    ```bash
    kubectl proxy --port=8080
    # Затем можно обратиться по адресу:
    # http://localhost:8080/api/v1/namespaces/default/services/my-service/proxy/
    ```
    Этот метод открывает доступ через API-сервер Kubernetes и **категорически не рекомендуется для использования в продакшене** из-за соображений безопасности и масштабируемости.

2.  **`kubectl port-forward`**: Пробрасывает порт с локальной машины на порт пода или сервиса в кластере.
    ```bash
    kubectl port-forward service/my-service 10000:80
    # Теперь трафик на localhost:10000 на вашей локальной машине будет перенаправлен на порт 80 сервиса my-service в кластере.
    ```
    Это удобный способ для локальной отладки и разработки, но **не предназначен для постоянной публикации приложения или использования в продакшн-средах**.


### `NodePort`

*   **Описание:** Открывает статический порт (`NodePort`) в диапазоне 30000-32767 на **каждом узле** кластера. Трафик, приходящий на `NodeIP:NodePort`, перенаправляется на `Service`. Это позволяет публиковать приложение "из коробки". При использовании `NodePort` на каждой ноде кластера открывается порт из этого диапазона (например, 31000), и обращаясь на внешний IP-адрес ноды и этот порт (например, `NodeIP:31000`), можно попасть в ваше приложение.
*   **Недостатки:**
    *   **Неудобство для пользователей:** Использование высоконумерованных портов (30000-32767) неудобно для конечных пользователей, так как требует явного указания порта в URL (например, `mysite.com:31000`).
    *   **Ограниченный диапазон портов:** Диапазон портов ограничен, что может стать проблемой при большом количестве сервисов.
    *   **Зависимость от IP-адреса ноды:** Если IP-адрес ноды изменится, доступ к приложению будет потерян.
*   **Использование:**
    *   Для предоставления внешнего доступа к сервису на время разработки, для демо или для приложений, не требующих сложной балансировки.
    *   В качестве бэкенда для внешнего балансировщика нагрузки, который перенаправляет трафик на `NodeIP:NodePort`.
    *   Для публикации не-HTTP приложений (например, TCP-сервисов, таких как RabbitMQ, базы данных).

### `LoadBalancer`

*   **Описание:** Создает внешний балансировщик нагрузки у облачного провайдера (AWS, GCP, Azure) и направляет трафик с него на `Service`. Является расширением `NodePort` и `ClusterIP` (трафик сначала попадает на `NodePort`, а затем на `ClusterIP`).
*   **Использование:** Стандартный способ публикации сервисов в интернет в облачных средах.

Сервис `LoadBalancer` отлично подходит для публикации вашего приложения, но с небольшой оговоркой: он работает только в облачных провайдерах (таких как Amazon, Google, Azure), которые предоставляют возможность работы с этим типом сервисов.

Механика работы этого сервиса следующая:
Снаружи кластера существует контроллер, который отслеживает API-сервер и контролирует создание новых сервисов типа `LoadBalancer`. Когда такой сервис создается, этот контроллер создает внешний балансировщик (например, Elastic Load Balancer в AWS), который, в свою очередь, отправляет трафик внутрь кластера на данный сервис вашего приложения. Если такого контроллера нет, `LoadBalancer` будет находиться в состоянии `Pending` и не будет работать корректно.

**Пример манифеста `LoadBalancer` Service:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-lb
spec:
  selector:
    app: my-app
  type: LoadBalancer
  ports:
    - name: http
      port: 80
      targetPort: 80
      protocol: TCP
```

**Использование статического IP-адреса:**
В `LoadBalancer` также есть возможность задавать статический IP-адрес в поле `loadBalancerIP`. Этот IP-адрес будет передан внешнему балансировщику, который будет отправлять трафик на этот IP-адрес в ваше приложение.

**Пример манифеста `LoadBalancer` Service со статическим IP:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-lb
  spec:
    selector:
      app: my-app
    type: LoadBalancer
    loadBalancerIP: "1.1.1.1" # Пример статического IP-адреса
    ports:
      - name: http
        port: 80
        targetPort: 80
        protocol: TCP
```

### `ExternalName`

Тип сервиса `ExternalName` отличается от других тем, что он не проксирует трафик на поды внутри кластера. Вместо этого он создает **CNAME-запись** во внутреннем DNS кластера, которая указывает на внешний ресурс. Это позволяет обращаться к внешним сервисам, используя внутреннее DNS-имя Kubernetes, что упрощает конфигурацию и скрывает реальный адрес внешнего ресурса.

**Принцип работы:**

При обращении к сервису типа `ExternalName` по его имени (например, `myService`), DNS-сервер кластера возвращает адрес, указанный в поле `externalName` манифеста сервиса. Таким образом, трафик направляется напрямую к внешнему ресурсу, минуя `kube-proxy` и балансировку нагрузки внутри кластера.

**Манифест `ExternalName` Service:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  type: ExternalName
  externalName: example.com
```

**Использование:**

*   **Доступ к внешним сервисам:** Основное назначение — предоставить внутренним приложениям в кластере доступ к внешним базам данных, API или другим сервисам, которые находятся за пределами кластера, используя при этом привычный механизм Service Discovery Kubernetes.
*   **Миграция или устаревшие системы (Legacy Systems):** В редких случаях может быть полезен для перенаправления трафика с внутреннего имени сервиса на внешний ресурс, если, например, внешний ресурс изменил свой адрес, а в коде приложений жестко прописано старое имя. Это позволяет избежать изменения кода приложений.

**Важные особенности:**

*   **Нет `ClusterIP`:** Сервисы `ExternalName` не имеют `ClusterIP`, так как они не балансируют нагрузку и не проксируют трафик.
*   **Нет селекторов:** Для `ExternalName` сервисов не используются селекторы подов, поскольку они не связаны с подами внутри кластера.
*   **Только DNS:** Работа `ExternalName` полностью основана на DNS.

### `ExternalIPs`

*   **Описание:** Сервис типа `ExternalIPs` позволяет привязать один или несколько внешних IP-адресов к сервису Kubernetes. Трафик, приходящий на эти IP-адреса, будет направлен на поды, обслуживаемые данным сервисом. Механика работы схожа с `NodePort`, но вместо открытия портов на нодах, `ExternalIPs` генерирует правила трансляции с указанного IP-адреса на ваше приложение.
    В отличие от `NodePort`, который открывает порты на узлах, `ExternalIPs` привязывается к конкретным IP-адресам.
*   **Принцип работы:** После создания такого сервиса на всех узлах кластера создаются правила трансляции (в `iptables` или `ipvs`), которые перенаправляют трафик, поступающий на указанные `externalIPs`, в соответствующие поды. Эти правила гарантируют, что трафик с указанного внешнего IP-адреса будет доставлен в ваше приложение, независимо от того, на каком узле кластера находится под.
*   **Реальные кейсы использования:**
    *   **Интеграция с VRRP/Keepalived:** Если у вас есть внешняя система, обеспечивающая отказоустойчивость IP-адресов (например, VRRP или Keepalived), вы можете привязать VIP-адрес к сервису типа `ExternalIPs`. Это гарантирует, что независимо от того, на какой ноде кластера в данный момент находится VIP-адрес, правила трансляции будут существовать на всех узлах, направляя трафик в ваше приложение.
    *   **Существующая инфраструктура:** Использование `ExternalIPs` может быть полезно, когда необходимо интегрировать Kubernetes-приложения с существующей сетевой инфраструктурой, которая уже использует определенные IP-адреса.

**Пример манифеста `ExternalIPs` Service:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: myservice
spec:
  selector:
    app: my-app
  ports:
    - name: http
      port: 80
      targetPort: 80
      protocol: TCP
  externalIPs:
    - 80.11.12.10
```

### `Headless Service`

**Headless Service** — это особый тип сервиса, который, в отличие от стандартных сервисов публикации, **не имеет `ClusterIP`**. Вместо предоставления единой виртуальной IP-точки входа для балансировки нагрузки, он напрямую предоставляет доступ к IP-адресам всех `Pod`-ов, которые соответствуют его селектору, через DNS-записи.

Чтобы сделать headless сервис, в его манифесте нужно явно указать `spec.clusterIP: None`.

**Пример манифеста `Headless Service`:**
```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  selector:
    app: my-app
  clusterIP: None # Отсутствие ClusterIP делает сервис "headless"
  ports:
    - name: http
      port: 80
      targetPort: 80
      protocol: TCP
```

#### Зачем и когда использовать Headless Service?

Основная цель — **обнаружение (`discovery`) отдельных `Pod`-ов**, а не проксирование трафика через единый IP.

Ключевые сценарии:

1.  **Stateful-приложения (`StatefulSet`):** Это основной и самый частый вариант использования. [StatefulSet](./statefulset.md) требует, чтобы каждый его `Pod` имел стабильное, уникальное сетевое имя. `Headless Service` обеспечивает это, создавая для каждого `Pod`-а предсказуемую DNS-запись.
    *   **Что будет, если не использовать Headless Service со StatefulSet?** 
    `StatefulSet` не получит стабильные DNS-имена для своих подов. Это сделает невозможным работу кластерных протоколов, требующих стабильных идентификаторов (например, для построения кворума в базах данных или брокерах сообщений), и приведет к нестабильности.

2.  **Прямой доступ к `Pod`-ам:** Когда клиенту или другому приложению нужно установить соединение с конкретным экземпляром `Pod`-а, а не со случайным (например, для репликации данных или выполнения административных задач).

3.  **Децентрализованные системы:** Для систем, где участники должны обнаруживать друг друга (peer-to-peer), например, кластеры баз данных (MongoDB, Cassandra) или брокеры сообщений.

4.  **Собственная логика балансировки:** Когда клиентское приложение само решает, к какому бэкенду подключиться, и ему нужен просто список всех доступных `Pod`-ов. Например, в базах данных можно направлять трафик на чтение на один под, а на запись — на другой.

#### Как это работает: DNS Discovery

Когда вы создаете `Headless Service`, внутренний DNS-сервер Kubernetes (CoreDNS) настраивает записи двух типов:

1.  **A-запись для самого сервиса:** `nslookup <service-name>` вернет **список IP-адресов всех `Pod`-ов**, подпадающих под селектор.
2.  **A-записи для каждого `Pod`-а:** Для каждого `Pod`-а создается уникальная запись в формате:
    ` <pod-name>.<service-name>.<namespace>.svc.cluster.local `

Это позволяет обращаться как ко всем `Pod`-ам сразу (получив их IP), так и к каждому `Pod`-у индивидуально по его стабильному DNS-имени.

> **Совет:** Для еще более тонкой настройки DNS-имен можно использовать поля `subdomain` и `hostname` в спецификации пода (`pod.spec`), чтобы создавать полностью кастомные FQDN.

## Пример: Headless Service для StatefulSet

Этот пример показывает, как `Headless Service` работает в паре со `StatefulSet` для создания `nginx`-подов со стабильными именами.

#### Шаг 1: Создание Headless Service

Манифест `nginx-headless-service.yaml`:
```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-headless
  labels:
    app: nginx
spec:
  # Установка clusterIP: None делает сервис "headless"
  clusterIP: None
  ports:
    - port: 80
      name: web
  # 2. Селектор должен соответствовать меткам подов StatefulSet.
  selector:
    app: nginx
```

#### Шаг 2: Создание StatefulSet

Манифест `nginx-statefulset.yaml`:
```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: web
spec:
  # 3. Имя сервиса должно совпадать с именем созданного Headless Service.
  serviceName: "nginx-headless"
  replicas: 2
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:1.28.0
          ports:
            - containerPort: 80
              name: web
```

В результате будут созданы поды `web-0` и `web-1`, каждый со своей уникальной DNS-записью.

## Проверка работы

После применения манифестов можно проверить DNS-записи из любого другого пода в кластере.

1.  **Запускаем временный под для отладки:**
    ```bash
    kubectl run -it --rm --image=busybox:1.36.1 dns-test -- /bin/sh
    ```

2.  **Внутри `dns-test` пода выполняем `nslookup`:**

    *   **Запрос к сервису (получаем все IP):**
        ```sh
        # nslookup nginx-headless
        Server:    10.96.0.10
        Address 1: 10.96.0.10 kube-dns.kube-system.svc.cluster.local

        Name:      nginx-headless.default.svc.cluster.local
        Address 1: 10.244.1.5
        Address 2: 10.244.2.4
        ```

    *   **Запрос к конкретному поду (получаем один IP):**
        ```sh
        # nslookup web-0.nginx-headless
        Server:    10.96.0.10
        Address 1: 10.96.0.10 kube-dns.kube-system.svc.cluster.local

        Name:      web-0.nginx-headless.default.svc.cluster.local
        Address 1: 10.244.1.5
        ```

## Сводка по типам сервисов

| Тип             | Доступность                  | IP-адрес                               | Основной сценарий                               |
|-----------------|------------------------------|----------------------------------------|-------------------------------------------------|
| **`ClusterIP`** | Только внутри кластера       | Стабильный внутренний IP               | Внутренние коммуникации (backend-to-db)         |
| **`NodePort`**  | Внутри и снаружи кластера    | Через `IP_узла:NodePort`               | Разработка, отладка, простые внешние сервисы    |
| **`LoadBalancer`**| Из интернета                 | Внешний IP от облачного провайдера     | Публикация приложений в облаке                  |
| **`ExternalName`**| - (только DNS)               | - (CNAME на внешний ресурс)            | Доступ к внешним сервисам по внутреннему имени  |
| **`ExternalIPs`** | Из интернета                 | Статический внешний IP                 | Интеграция с VRRP/Keepalived, существующая инфраструктура |
| **`Headless`**  | Прямой доступ к `Pod`-ам     | IP-адреса `Pod`-ов через DNS           | Stateful-приложения (например, с `StatefulSet`) |

## Пример: Service типа `NodePort`

Этот манифест создает `Service`, который находит все `Pod`-ы с меткой `app: my-app` и предоставляет к ним доступ.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-np
spec:
  # 1. Тип сервиса. Если не указан, по умолчанию используется ClusterIP.
  type: NodePort

  # 2. Селектор для выбора Pod'ов, на которые пойдет трафик.
  #    Должен соответствовать меткам в шаблоне Deployment, ReplicaSet и т.д.
  selector:
    app: my-app

  # 3. Описание портов.
  ports:
    - name: http
      protocol: TCP
      # port: Внутренний порт, на котором Service принимает трафик внутри кластера.
      port: 80
      # targetPort: Порт на Pod'ах, куда будет перенаправляться трафик.
      targetPort: 80
      # nodePort: Статический порт на узлах (только для типа NodePort).
      # Если не указать, будет выбран случайный из диапазона 30000-32767.
      # nodePort: 30080
```

**Как это работает:**

1.  Трафик, отправленный на `любой_узел_кластера:<NodePort>`, будет принят.
2.  `kube-proxy` перенаправит этот трафик на внутренний IP-адрес `Service` на порт `80`.
3.  `Service` выберет один из `Pod`-ов с меткой `app: my-app` и отправит трафик на его порт `80`.
