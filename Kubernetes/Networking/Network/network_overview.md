# Обзор сетевой модели Kubernetes

## Определения

**Сетевая модель Kubernetes** — это фундаментальная архитектурная абстракция, обеспечивающая унифицированное и предсказуемое взаимодействие между подами, узлами и внешними ресурсами. Она построена на принципе **IP-per-Pod**: каждому поду назначается уникальный IP-адрес, доступный из любой точки кластера без использования NAT (Network Address Translation) в пределах East-West трафика.

**Pod CIDR (podCIDR)** — диапазон IP-адресов, выделяемый кластеру (Cluster CIDR) и нарезаемый на сегменты для каждого узла. 
- **Multi-CIDR:** Современная возможность (стабильна в 2026), позволяющая динамически добавлять новые диапазоны IP, если основной пул исчерпан, без пересоздания кластера.

**Dual-stack (IPv4/IPv6)** — конфигурация, при которой каждый под получает два IP-адреса разных протоколов. Это стандарт для современных инсталляций, обеспечивающий масштабируемость за счет IPv6 и совместимость с legacy-системами через IPv4.

**CNI (Container Network Interface)** — стандарт (и набор библиотек), определяющий взаимодействие между средой выполнения контейнеров (CRI) и сетевыми плагинами. CNI делегирует настройку сетевых интерфейсов и маршрутов внешним решениям (Calico, Cilium, Flannel).

- **IPAM (IP Address Management):** Подсистема CNI, отвечающая за учет и выделение адресов (`host-local`, `dhcp`, или облачные реализации).

**kube-proxy** — сетевой агент, работающий на каждом узле. Его задача — программировать правила фильтрации и трансляции для реализации абстракции `Service`.

### Техническая реализация связности через CNI

При запуске нового пода Kubernetes вызывает CNI-плагин, который выполняет следующую последовательность действий:
1.  **Создание veth-пары:** Генерируется пара виртуальных интерфейсов. Один конец остается в пространстве имен хоста, второй — пробрасывается в Network Namespace пода.
2.  **Изоляция Namespace:** Интерфейс внутри пода переименовывается в `eth0` и получает уникальный IP-адрес из диапазона Pod CIDR.
3.  **Маршрутизация на хосте:** На узле создаются записи в таблице маршрутизации, указывающие, что трафик для данного IP должен направляться в соответствующий `veth` интерфейс.
4.  **Связность кластера:** Плагин (например, Calico через BGP или Flannel через VXLAN) анонсирует новый маршрут или инкапсулирует трафик для обеспечения L3-связности между узлами.

## Основные концепции
- **nftables (v1.31+):** Основной режим работы kube-proxy. Заменяет `iptables`, предлагая атомарные обновления правил и значительно меньшую нагрузку на CPU в кластерах с тысячами сервисов.

**EndpointSlice** — масштабируемая замена ресурса `Endpoints`. Группирует сетевые адреса подов в блоки по 100 единиц, что снижает нагрузку на API-сервер при обновлении состояния крупных сервисов.

**Service Discovery (Обнаружение сервисов)** — механизмы сопоставления стабильных имен с динамическими IP-адресами подов через DNS (CoreDNS) и актуальные списки эндпоинтов.

## Основные концепции

### Иерархия сетевых уровней кластера

Сетевое взаимодействие в Kubernetes разделено на три логических слоя:

1.  **Сеть узлов (Node Network):** Базовая инфраструктура (L2/L3), обеспечивающая связность между физическими или виртуальными машинами.
2.  **Сеть подов (Pod Network):** Виртуальная плоскость (Data Plane), создаваемая CNI. Позволяет подам общаться напрямую.
3.  **Сеть сервисов (Service Network):** Виртуальный слой ClusterIP. Трафик на этот IP перехватывается на узле и балансируется между подами-эндпоинтами.

### Фундаментальные принципы взаимодействия

*   **Отсутствие NAT между подами:** Пакет, отправленный подом А поду Б, должен дойти до него с неизменным Source IP.
*   **Связность "все-ко-всем":** Любой под может отправить UDP/TCP пакет любому другому поду без дополнительных настроек (если это не ограничено `NetworkPolicy`).
*   **Контейнеры в поде:** Разделяют один сетевой стек (`network namespace`), общаются через `localhost` и имеют общий IP-адрес.
*   **Эфемерность:** IP-адреса подов не гарантированы после перезапуска. Единственным надежным способом обращения является использование `Service`.
*   **Топологическая осведомленность (Topology Aware Routing):** Механизм, направляющий трафик на поды в той же зоне доступности (AZ) для минимизации задержек и экономии трафика в облаках.

## Техническая реализация связности

### 1. Взаимодействие внутри одного узла

Когда поды находятся на одном хосте, CNI создает виртуальные пары интерфейсов (**veth-pairs**):
- Один конец интерфейса (`eth0`) находится внутри пространства имен пода.
- Второй конец (`vethXXX`) находится в пространстве имен хоста.
- Связность обеспечивается либо через программный мост (linux bridge), либо через прямую маршрутизацию в стеке хоста.

### 2. Связность между разными узлами

Реализуется CNI-плагинами одним из трех методов:

#### 2.1. Оверлейные сети (Overlay: VXLAN, Geneve)
Инкапсуляция трафика пода в UDP-пакеты узла.
- **Плюсы:** Работает поверх любой L3-сети, не требует настройки физических коммутаторов.
- **Минусы:** Накладные расходы (около 50 байт на пакет), что снижает эффективный **MTU** до 1450. Требует включения MSS Clamping.

#### 2.2. Прямая маршрутизация (Direct Routing: BGP)
Узлы обмениваются маршрутами к своим Pod CIDR через протокол BGP (Calico).
- **Плюсы:** Максимальная производительность, отсутствие инкапсуляции (MTU 1500).
- **Минусы:** Требует поддержки BGP или статических маршрутов в физической сети.

#### 2.3. eBPF-native (Cilium)
Трафик перехватывается на уровне сокетов или драйвера сетевой карты.
- **Особенности:** Полный обход (bypass) стека Netfilter/iptables. Прямая доставка пакета в нужный интерфейс на основе Identity-based политик.

## Практические рекомендации и "белые пятна"

### Выбор режима kube-proxy
- **nftables:** Используйте как режим по умолчанию для k8s 1.31+. Он обеспечивает атомарную загрузку правил, что предотвращает кратковременные разрывы связи при обновлении сервисов.
- **eBPF (kube-proxy replacement):** В Cilium этот режим полностью удаляет kube-proxy, снижая задержки и нагрузку на CPU за счет отсутствия контекстных переключений между User Space и Kernel Space.

### Оптимизация MTU
В облачных средах (AWS, GCP) с VXLAN неправильный MTU приводит к обрывам сессий при передаче больших файлов. Всегда проверяйте, что MTU внутри пода на 50 байт меньше физического MTU узла.

### Проектирование CIDR
- Всегда выделяйте Pod CIDR с запасом. Если планируется 100 узлов по 110 подов, требуется сеть минимум `/16`.
- Используйте **Multi-CIDR**, если кластер растет быстрее, чем ожидалось.

### Совет для интервью: Глубокое понимание
**Вопрос:** "В чем разница между ClusterIP и Pod IP с точки зрения сети?"
**Ответ:** 
- **Pod IP** — это реальный IP-адрес на виртуальном интерфейсе, он маршрутизируется CNI-плагином.
- **ClusterIP** — это "виртуальный" IP (VIP), который не существует на интерфейсах. Пакет с `dst: ClusterIP` перехватывается kube-proxy на узле, где происходит **DNAT** (Destination NAT) на один из реальных Pod IP.
