# Обзор сетевой модели Kubernetes

## Определения

**Сетевая модель Kubernetes** — это фундаментальная архитектурная абстракция, обеспечивающая унифицированное и предсказуемое взаимодействие между подами, узлами и внешними ресурсами. Она построена на принципе **IP-per-Pod**: каждому поду назначается уникальный IP-адрес, доступный из любой точки кластера без использования NAT (Network Address Translation) в пределах East-West трафика.

**Pod CIDR (podCIDR)** — диапазон IP-адресов, выделяемый кластеру (Cluster CIDR) и нарезаемый на сегменты для каждого узла. Каждый узел получает свою подсеть (обычно /24 для IPv4), из которой CNI выделяет IP-адреса подам.
- **Multi-CIDR:** Современная возможность (стабильна в 2026), позволяющая динамически добавлять новые диапазоны IP, если основной пул исчерпан, без пересоздания кластера. Реализуется через параметр `clusterCIDR` в конфигурации CNI.

**Dual-stack (IPv4/IPv6)** — конфигурация, при которой каждый под получает два IP-адреса разных протоколов. Это стандарт для современных инсталляций, обеспечивающий масштабируемость за счет IPv6 и совместимость с legacy-системами через IPv4. Достигается включением флагов `--ipv4-stack` и `--ipv6-secondary` в конфигурации CNI.

**CNI (Container Network Interface)** — стандарт (и набор библиотек), определяющий взаимодействие между средой выполнения контейнеров (CRI) и сетевыми плагинами. CNI делегирует настройку сетевых интерфейсов и маршрутов внешним решениям (Calico, Cilium, Flannel). Спецификация определяет три основных действия: `ADD` (создание), `CHECK` (проверка), `DELETE` (удаление).

**IPAM (IP Address Management)** — подсистема CNI, отвечающая за учет и выделение адресов. Типичные реализации: `host-local` (статический пул на узле), `dhcp` (автоматическое через DHCP-сервер), `calico-ipam` (динамический с поддержкой跨用 между узлами).

**kube-proxy** — сетевой агент, работающий на каждом узле в виде DaemonSet. Его задача — программировать правила фильтрации и трансляции для реализации абстракции `Service`. Поддерживает режимы nftables (рекомендован с v1.31), IPVS (для высоких нагрузок) и iptables (устаревающий).

**Network Namespace (netns)** — механизм изоляции сетевого стека ядра Linux, лежащий в основе изоляции подов. Каждый под получает собственный netns с уникальным набором интерфейсов, таблиц маршрутизации и правил iptables/nftables.

**veth pair (Virtual Ethernet Pair)** — виртуальная пара интерфейсов, соединяющих netns пода с netns хоста. Работает как виртуальный патч-корд: пакет, вошедший в один конец, гарантированно выходит из другого.

## Основные концепции

### Иерархия сетевых уровней кластера

Сетевое взаимодействие в Kubernetes разделено на три логических слоя:

```
┌─────────────────────────────────────────────────────────────┐
│                    Сеть сервисов (Service Network)           │
│  Виртуальный IP (ClusterIP) → DNAT → Pod IP                 │
│  Реализация: kube-proxy (nftables/IPVS) или eBPF (Cilium)   │
├─────────────────────────────────────────────────────────────┤
│                    Сеть подов (Pod Network)                  │
│  IP-per-Pod, L3 связность через CNI                         │
│  Технологии: VXLAN, BGP, eBPF, direct routing              │
├─────────────────────────────────────────────────────────────┤
│                    Сеть узлов (Node Network)                 │
│  Базовая инфраструктура (L2/L3), физические или виртуальные │
│  Машины, подключенные к физической сети                     │
└─────────────────────────────────────────────────────────────┘
```

### Фундаментальные принципы взаимодействия

*   **Отсутствие NAT между подами:** Пакет, отправленный подом А поду Б, должен дойти до него с неизменным Source IP. Это критично для работы логирования, аудита и security-политик.
*   **Связность "все-ко-всем":** Любой под может отправить UDP/TCP пакет любому другому поду без дополнительных настроек (если это не ограничено `NetworkPolicy`).
*   **Контейнеры в поде:** Разделяют один сетевой стек (`network namespace`), общаются через `localhost` и имеют общий IP-адрес. Порт, прослушиваемый одним контейнером, доступен другим через `127.0.0.1`.
*   **Эфемерность:** IP-адреса подов не гарантированы после перезапуска. Единственным надежным способом обращения является использование `Service` или DNS-имени.
*   **Топологическая осведомленность (Topology Aware Routing):** Механизм, направляющий трафик на поды в той же зоне доступности (AZ) для минимизации задержек и экономии трафика.

## Техническая реализация связности

### 1. Жизненный цикл сетевой настройки пода

При запуске нового пода Kubernetes вызывает CNI-плагин, который выполняет следующую последовательность действий:

```
Pod Creation Request
        │
        ▼
┌───────────────────┐
│ 1. Создание       │   Kubelet вызывает CNI с командой ADD
│    Pod Sandbox     │   (-netns, -cidr, -config)
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│ 2. Создание       │   Генерируется пара виртуальных интерфейсов.
│    veth-pair       │   Один конец (eth0) в namespace пода,
│                   │   второй (vethXXX) — в namespace хоста.
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│ 3. Назначение IP  │   IPAM выделяет IP из podCIDR узла.
│    (IPAM)         │   Интерфейс eth0 получает этот адрес.
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│ 4. Маршрутизация  │   На узле создается маршрут:
│    на хосте       │   ip route add <pod-CIDR> via <gateway>
└────────┬──────────┘
         │
         ▼
┌───────────────────┐
│ 5. Связность      │   CNI анонсирует маршрут (BGP) или
│    кластера        │   инкапсулирует трафик (VXLAN/Geneve)
└───────────────────┘
```

### 2. Взаимодействие внутри одного узла

Когда поды находятся на одном хосте, CNI создает виртуальные пары интерфейсов (**veth-pairs**):

```
┌─────────────────────────────────────────────────────┐
│                    ХОСТ (Node)                        │
│                                                       │
│  ┌──────────────┐         ┌──────────────┐           │
│  │    eth0      │         │    eth0      │           │
│  │  (Pod A)     │         │  (Pod B)     │           │
│  │  10.244.1.5  │         │  10.244.1.6  │           │
│  └──────┬───────┘         └──────┬───────┘           │
│         │                        │                    │
│  ┌──────┴───────┐         ┌──────┴───────┐           │
│  │  vethXXX     │         │  vethYYY     │           │
│  └──────┬───────┘         └──────┬───────┘           │
│         │                        │                    │
│         └────────┬───────────────┘                    │
│                  │                                    │
│         ┌────────┴────────┐                           │
│         │   cbr0 / docker0│   Linux Bridge            │
│         │   (или direct   │   (или direct routing)    │
│         │    routing)     │                           │
│         └─────────────────┘                           │
└─────────────────────────────────────────────────────┘
```

- Один конец интерфейса (`eth0`) находится внутри пространства имен пода.
- Второй конец (`vethXXX`) находится в пространстве имен хоста.
- Связность обеспечивается либо через программный мост (linux bridge), либо через прямую маршрутизацию в стеке хоста.

**Команды диагностики на хосте:**

```bash
# Просмотр veth-интерфейсов на хосте
ip link show type veth

# Просмотр IP-адреса конкретного veth
ip addr show vethXXX

# Просмотр таблицы маршрутизации
ip route show

# Просмотр ARP-таблицы
ip neigh show
```

### 3. Связность между разными узлами

Реализуется CNI-плагинами одним из трех методов:

#### 3.1. Оверлейные сети (Overlay: VXLAN, Geneve)

Инкапсуляция трафика пода в UDP-пакеты узла.

```
Pod A (10.244.1.5) ──── Pod B (10.244.2.8)
        │                       │
        ▼                       ▼
┌───────────────┐       ┌───────────────┐
│  eth0 (pod)   │       │  eth0 (pod)   │
│  10.244.1.5   │       │  10.244.2.8   │
└───────┬───────┘       └───────┬───────┘
        │                       │
┌───────┴───────┐       ┌───────┴───────┐
│  vxlan0 (host)│       │  vxlan0 (host)│
│  UDP:8472     │       │  UDP:8472     │
└───────┬───────┘       └───────┬───────┘
        │                       │
        └───────────┬───────────┘
                    │
            ┌───────┴───────┐
            │  Физическая   │
            │  сеть (L3)    │
            └───────────────┘
```

- **Плюсы:** Работает поверх любой L3-сети, не требует настройки физических коммутаторов.
- **Минусы:** Накладные расходы (около 50 байт на пакет), что снижает эффективный **MTU** до 1450. Требует включения MSS Clamping.
- **Реализация:** Flannel (VXLAN), Calico (VXLAN/IPIP), Antrea (Geneve).

#### 3.2. Прямая маршрутизация (Direct Routing: BGP / Native Routing)

Узлы обмениваются маршрутами к своим Pod CIDR через протокол BGP (Calico, Cilium) или автоматические маршруты в L2-сегменте (Cilium `autoDirectNodeRoutes`).

- **Плюсы:** Максимальная производительность, отсутствие инкапсуляции (MTU 1500).
- **Минусы:** Требует поддержки BGP или статических маршрутов в физической сети; `autoDirectNodeRoutes` работает только в одном L2-сегменте.
- **См. также:** [Cilium: Настройка native routing и BGP](./CNI/cilium.md#настройка-native-routing-и-bgp-control-plane) — подробная конфигурация.

#### 3.3. eBPF-native (Cilium)

Трафик перехватывается на уровне сокетов или драйвера сетевой карты.

- **Особенности:** Полный обход (bypass) стека Netfilter/iptables. Прямая доставка пакета в нужный интерфейс на основе Identity-based политик.
- **Производительность:** Время поиска O(1) через хеш-таблицы, отсутствие контекстных переключений между User Space и Kernel Space.

### 4. Внутриподовая сеть (Loopback и Inter-Container)

Контейнеры внутри одного пода разделяют общий network namespace:

```
┌─────────────────────────────────────┐
│              POD (netns)             │
│                                      │
│  ┌──────────┐    ┌──────────┐       │
│  │App Ctr 1 │    │App Ctr 2 │       │
│  │ eth0     │    │ eth0     │       │
│  │10.244.1.5│    │10.244.1.5│       │
│  └────┬─────┘    └────┬─────┘       │
│       │               │              │
│       └───────┬───────┘              │
│               │                      │
│        ┌──────┴──────┐              │
│        │   lo (loopback)│            │
│        │  127.0.0.1   │             │
│        └─────────────┘              │
└─────────────────────────────────────┘
```

- **Loopback (lo):** Все контейнеры в поде видят общий интерфейс `lo` с адресом `127.0.0.1`. Трафик на `localhost` никогда не покидает под и не фильтруется NetworkPolicy.
- **Shared eth0:** Все контейнеры используют один `eth0` с одним IP-адресом. Порт, занятый одним контейнером, недоступен другим (необходимо использовать разные порты или координацию через init-контейнеры).
- **PID изоляция:** Несмотря на общий netns, контейнеры имеют изолированный PID namespace. Процессы одного контейнера не видны другому (но могут общаться через сокеты в общем netns).

## Практические рекомендации

### Выбор режима kube-proxy

| Режим | Когда использовать | Ключевые особенности |
| :--- | :--- | :--- |
| **nftables** | k8s 1.31+, рекомендован по умолчанию | Атомарные обновления правил, O(n) но с низким коэффициентом |
| **IPVS** | Кластеры с >1000 сервисов | O(1) через хеш-таблицы, алгоритмы: rr, lc, sh, sed |
| **eBPF** | Cilium, полный обход kube-proxy | Отсутствие контекстных переключений, Identity-based |

- **nftables:** Используйте как режим по умолчанию для k8s 1.31+. Он обеспечивает атомарную загрузку правил, что предотвращает кратковременные разрывы связи при обновлении сервисов.
- **eBPF (kube-proxy replacement):** В Cilium этот режим полностью удаляет kube-proxy, снижая задержки и нагрузку на CPU за счет отсутствия контекстных переключений между User Space и Kernel Space.

### Оптимизация MTU

MTU (Maximum Transmission Unit) — максимальный размер пакета в байтах, который может быть передан без фрагментации.

```
Физический MTU узла: 1500 (стандартный Ethernet)
        │
        ▼
Overlay overhead: -50 байт (VXLAN: 8 outer UDP + 20 outer IP + 8 VXLAN + 14 ethernet)
        │
        ▼
MTU внутри пода: 1450
```

**Расчет MTU:**

| Тип сети | Overhead | MTU пода | Примечание |
| :--- | :--- | :--- | :--- |
| VXLAN | 50 байт | 1450 | Стандарт для Flannel, Calico VXLAN |
| Geneve | 60 байт | 1440 | Antrea, Cilium |
| IPIP | 20 байт | 1480 | Calico direct routing |
| Direct (BGP) | 0 | 1500 | Calico BGP, Cilium native |

**Проверка MTU:**

```bash
# Изнутри пода
ping -M do -s 1422 <target-pod-ip>  # 1422 + 28 (ICMP header) = 1450

# С хоста
ip link show eth0 | grep mtu

# Проверка path MTU
tracepath <target-pod-ip>
```

**Проблемы с MTU:**
- TCP-сессии "залипают" при передаче больших файлов (SYN-пакеты проходят, данные — нет).
- MSS Clamping: CNI автоматически настраивает `iptables -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu`.
- Всегда проверяйте, что MTU внутри пода на N байт меньше физического MTU узла (N = overhead конкретного CNI).

### Проектирование CIDR

**Формула расчета:**

```
Pod CIDR = количество_узлов × максимальное_подов_на_узел × запас (20-30%)
```

**Примеры:**

| Сценарий | Узлы | Подов/узел | Запас | Рекомендация |
| :--- | :--- | :--- | :--- | :--- |
| Малый кластер | 10 | 110 | 30% | /16 (65534 адресов) |
| Средний кластер | 100 | 110 | 20% | /16 |
| Большой кластер | 500 | 110 | 20% | /14 или Multi-CIDR |
| Экстремальный | 2000+ | 250 | 20% | Multi-CIDR |

- Всегда выделяйте Pod CIDR с запасом. Если планируется 100 узлов по 110 подов, требуется сеть минимум `/16`.
- Используйте **Multi-CIDR**, если кластер растет быстрее, чем ожидалось.
- **Service CIDR** (отдельный от Pod CIDR): обычно /16 (65534 сервисов), задается флагом `--service-cluster-ip-range`.

### Совет для интервью: Глубокое понимание

**Вопрос:** "В чем разница между ClusterIP и Pod IP с точки зрения сети?"

**Ответ:**
- **Pod IP** — это реальный IP-адрес на виртуальном интерфейсе (`eth0`), он маршрутизируется CNI-плагином и существует в network namespace пода.
- **ClusterIP** — это "виртуальный" IP (VIP), который не существует ни на одном интерфейсе. Пакет с `dst: ClusterIP` перехватывается kube-proxy на узле, где происходит **DNAT** (Destination NAT) на один из реальных Pod IP. VIP является "анycast-like": он отвечает на ARP-запросы на каждом узле, но пакет никогда не покидает узел без обработки.

## Диагностика сетевых проблем

### Алгоритм диагностики

```bash
# 1. Проверка доступности пода ( readiness/readiness)
kubectl get pod <name> -o wide
kubectl describe pod <name> | grep -A 5 "Conditions"

# 2. Проверка IP-адреса пода
kubectl get pod <name> -o jsonpath='{.status.podIP}'
kubectl get pod <name> -o jsonpath='{.status.podIPs}'

# 3. Проверка DNS-резолвинга изнутри пода
kubectl exec -it <pod> -- nslookup <service>.<namespace>.svc.cluster.local
kubectl exec -it <pod> -- cat /etc/resolv.conf

# 4. Проверка сетевой связности
kubectl exec -it <pod> -- ping -c 3 <target-ip>
kubectl exec -it <pod> -- curl -v <service>:<port>

# 5. Просмотр сетевых интерфейсов в поде
kubectl exec -it <pod> -- ip addr show
kubectl exec -it <pod> -- ip route show

# 6. Проверка conntrack (на хосте)
conntrack -L | grep <pod-ip>
conntrack -S

# 7. Проверка правил nftables (на хосте)
nft list ruleset | grep <service-name>
```

### Таблица типичных проблем

| Симптом | Вероятная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Под не может резолвить DNS | CoreDNS недоступен или Egress блокирует порт 53 | `kubectl exec -it <pod> -- nslookup kubernetes.default` | Добавить Egress-правило для CoreDNS |
| Трафик между подами на разных узлах не проходит | CNI не настроил маршрутизацию между узлами | `ip route show` на обоих узлах | Проверить BGP-пиринг или VXLAN-туннель |
| Connection Timeout к Service | NetworkPolicy не разрешает трафик | `kubectl describe networkpolicy -n <ns>` | Добавить Ingress/Egress-правила |
| Высокий CPU на kube-proxy | Линейный перебор iptables при >1000 правил | `iptables -L -n -v \| wc -l` | Перейти на nftables или IPVS |
| Связность не восстанавливается после рестарта пода | conntrack кэширует старые решения | `conntrack -L \| grep <old-pod-ip>` | Очистить: `conntrack -D -s <old-pod-ip>` |
| Под не видит Service ClusterIP | kube-proxy не обновил правила | `nft list ruleset \| grep <cluster-ip>` | Перезапустить kube-proxy, проверить логи |
| Пакеты теряются при передаче больших файлов | MTU mismatch (фрагментация) | `ping -M do -s 1422 <target-ip>` | Настроить MTU в CNI и на физических интерфейсах |

```bash
# Проверка конфигурации CNI

kubectl get ippool -o wide  # для Calico
```

### Проверка состояния сети на узле

```bash
# Просмотр всех network namespaces
ip netns list

# Просмотр namespace конкретного пода (нужен PID пода)
PID=$(docker inspect --format '{{.State.Pid}}' <container-id>)
nsenter -t $PID -n ip addr show

# Просмотр таблицы маршрутизации в namespace пода
nsenter -t $PID -n ip route show

# Проверка ARP-таблицы
nsenter -t $PID -n ip neigh show

# Просмотр открытых портов в namespace пода
nsenter -t $PID -n ss -tlnp
```
