## Определения

**Сетевая модель Kubernetes** — фундаментальный набор правил и абстракций, обеспечивающий предсказуемое взаимодействие между всеми компонентами кластера. Основана на принципе **IP-per-Pod**: каждый под получает уникальный IP-адрес, доступный из любой точки кластера без использования трансляции адресов (NAT).

**Pod CIDR (podCIDR)** — диапазон IP-адресов, выделенный всему кластеру или конкретному узлу для назначения адресов подам. В современных кластерах поддерживается динамическое расширение диапазонов через Multi-CIDR.

**Dual-stack (IPv4/IPv6)** — режим работы сети, при котором подам и сервисам назначаются адреса обоих протоколов одновременно, обеспечивая плавную миграцию и совместимость с современными интернет-стандартами.

**CNI (Container Network Interface)** — открытая спецификация и набор библиотек, определяющих стандарт взаимодействия между средой выполнения контейнеров (CRI) и сетевыми плагинами. 

Основные характеристики CNI:
*   **Универсальность:** Позволяет любой среде выполнения (`containerd`, `CRI-O`) работать с любым сетевым плагином (Cilium, Calico, Flannel) через единый интерфейс.
*   **Жизненный цикл:** Среда выполнения вызывает CNI-плагин в момент создания пода для настройки сети и в момент удаления — для очистки ресурсов.
*   **Механика работы:** Плагины представляют собой исполняемые файлы. При вызове они создают сетевой интерфейс внутри пространства имен контейнера (Network Namespace), подключают его к сети хоста (часто через виртуальный мост или прямое подключение к хост-сети), назначают IP-адрес (через IPAM) и настраивают необходимые маршруты.

**Оверлейная сеть (Overlay Network)** — виртуальная сеть, создаваемая поверх физической инфраструктуры. Она позволяет подам на разных узлах взаимодействовать друг с другом через туннелирование (инкапсуляцию пакетов, например, VXLAN или GRE), обеспечивая абстракцию сети на уровне всего кластера независимо от физического расположения узлов.

**kube-proxy** — сетевой агент на каждом узле, реализующий абстракцию `Service`.
 Начиная с версии v1.31, основным и наиболее производительным режимом работы в ядре Linux является **nftables**, заменяющий устаревший iptables.

**NetworkPolicy** — ресурс для декларативного управления сетевой изоляцией (L3/L4) между подами. Реализуется силами CNI-плагина.

**Service Discovery** — механизмы (в основном DNS и EndpointSlice), позволяющие подам находить друг друга по именам сервисов вместо динамических IP-адресов.

## Основные концепции

### Три логических уровня сетей

Взаимодействие в Kubernetes строится на трех уровнях:

1.  **Сеть узлов (Node Network):** Физическая или виртуальная инфраструктура (L2/L3), по которой общаются серверы кластера.
2.  **Сеть подов (Pod Network):** Виртуальная сеть, создаваемая CNI-плагином. Обеспечивает прямую связность между всеми подами кластера без NAT.
3.  **Сеть сервисов (Service Network):** Абстрактная сеть виртуальных IP-адресов (ClusterIP), управляемая `kube-proxy` (или eBPF) для балансировки трафика.

### Фундаментальные принципы

*   **Уникальность:** Каждый под имеет собственный IP, разделяемый всеми контейнерами внутри этого пода.
*   **Прямая связность (No-NAT):** Любой под может отправить пакет любому другому поду без трансляции адресов. Исходный IP отправителя сохраняется (за исключением случаев прохождения через Service с `externalTrafficPolicy: Cluster`).
*   **Отсутствие NAT для агентов:** Kubelet и другие системные компоненты на узле могут обращаться к подам напрямую.
*   **Эфемерность:** IP-адреса подов динамичны; для стабильного доступа используются `Service`.
*   **Топологическая осведомленность:** Современная сеть Kubernetes (через Topology Aware Routing) стремится направлять трафик в пределах одной зоны/региона для снижения задержек.

## Практические сценарии

### Совет для интервью: Как отвечать на вопрос «Как взаимодействуют поды?»

Начинайте ответ с разделения на сценарии, так как механизмы реализации различаются:
1.  **Внутри одного пода:** через `localhost` (общее сетевое пространство имен).
2.  **Между подами на одном узле:** напрямую через IP пода и виртуальный мост/маршрутизацию узла.
3.  **Между подами на разных узлах:** через сеть кластера (маршрутизация или оверлей).

### 1. Взаимодействие внутри пода

Контейнеры внутри одного пода разделяют общее сетевое пространство имен (`network namespace`). Они взаимодействуют через `localhost`, разделяя общую таблицу портов и IP-адрес пода. Это общение происходит мгновенно и не выходит за пределы сетевого стека пода.

### 2. Связь между подами на одном узле

Каждому поду назначается уникальный IP-адрес. Когда поды находятся на одном узле:
- Они общаются напрямую, используя IP-адрес целевого пода.
- Трафик проходит через виртуальные интерфейсы (veth-пары) внутри сетевого стека узла.
- CNI-плагин настраивает либо сетевой мост (bridge), либо прямую маршрутизацию между veth-интерфейсами в основном пространстве имен узла.
- **Изоляция:** В отличие от взаимодействия через `localhost`, поды на одном узле изолированы друг от друга и используют сетевой стек хоста для связи.

### 3. Связь между подами на разных узлах

Когда поды распределены по нескольким узлам, связь становится межузловой. Kubernetes обеспечивает её через сеть кластера:
- Поды сохраняют свои уникальные IP-адреса, видимые всему кластеру.
- `kube-proxy` и CNI-плагины гарантируют, что запросы будут правильно маршрутизированы между физическими/виртуальными интерфейсами узлов.

Реализуется тремя основными способами:

#### 3.1. Прямая маршрутизация (BGP)
Используется в Calico или Cilium. Узлы кластера обмениваются маршрутами через BGP.
*   **Преимущество:** Максимальная производительность, исходный размер MTU (1500).
*   **Применение:** Дата-центры с контролем над сетевым оборудованием.

#### 3.2. Оверлейная сеть (Overlay: VXLAN/Geneve)
Инкапсуляция пакета пода в UDP-пакет узла.
*   **Механика:** Пакет пода оборачивается в заголовок VXLAN и передается по сети узлов.
*   **Недостаток:** Накладные расходы на инкапсуляцию (MTУ -50 байт), нагрузка на CPU.
*   **Применение:** Облака и среды, где L2/L3 связность между узлами ограничена.

#### 3.3. eBPF-native (Cilium)
Трафик перехватывается на уровне XDP или сетевого драйвера и направляется напрямую в целевой под, часто минуя стандартный стек Netfilter/iptables.

## Рекомендации по проектированию

1.  **Использование Gateway API:** Для новых проектов Gateway API является стандартом (заменяет Ingress), обеспечивая лучшую ролевую модель и расширенные функции L7.
2.  **Переход на nftables/eBPF:** При возможности откажитесь от режима `iptables` в `kube-proxy` в пользу `nftables` (v1.31+) или eBPF-решений (Cilium) для повышения производительности балансировки.
3.  **Безопасность по умолчанию:** Используйте `NetworkPolicy` для реализации принципа наименьших привилегий. Помните, что по умолчанию в Kubernetes разрешен весь трафик (Allow-All).
4.  **Dual-stack IPv4/IPv6:** Настраивайте поддержку двух стеков на этапе развертывания кластера, так как последующая миграция требует значительных усилий.
5.  **EndpointSlice вместо Endpoints:** Для кластеров с количеством подов более 1000 убедитесь, что ваши контроллеры используют EndpointSlice для снижения нагрузки на API-сервер.
