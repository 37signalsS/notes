# Обзор сетевой модели Kubernetes

Сетевая модель Kubernetes — фундаментальный набор правил, обеспечивающий предсказуемое и расширяемое взаимодействие между рабочими нагрузками. Основана на принципе **IP-per-Pod**: каждый под получает уникальный IP-адрес в кластере, все поды могут общаться напрямую без NAT.

---

## Определения

**Сетевая модель Kubernetes** — модель сетевой связности, основанная на принципе IP-per-Pod, где каждый под получает уникальный IP-адрес в рамках всего кластера, независимо от узла размещения.

**Pod CIDR (podCIDR)** — диапазон IP-адресов, выделенный для подов в кластере. Делится на подсети для каждого узла.

**Node CIDR (nodeCIDR)** — диапазон IP-адресов, выделенный конкретному узлу для распределения между подами.

**CNI (Container Network Interface)** — стандартный интерфейс для подключения контейнеров к сети. Отвечает за выделение IP-адресов подам и маршрутизацию трафика между узлами (L2/L3).

* *Подробные определения и разделение ролей с kube-proxy: [CNI и kube-proxy: определения](./CNI/definitions.md)*

**kube-proxy** — сетевой прокси на каждом узле. Реализует абстракцию `Service` через управление правилами в ядре Linux (iptables/IPVS), обеспечивая балансировку нагрузки на уровне L4.

* *Подробные определения: [CNI и kube-proxy: определения](./CNI/definitions.md)*

**NetworkPolicy** — ресурс Kubernetes для декларативного управления правилами доступа к сети (L3/L4) между подами. Работает только при поддержке CNI-плагином (Calico, Cilium, Weave Net).

* *Подробная информация: [NetworkPolicy: навигатор](./network_policy.md) и [NetworkPolicy: определения](./NetworkPolicy/definitions.md)*

**Service Discovery** — механизм автоматического обнаружения сервисов по стабильным DNS-именам вместо IP-адресов.

* *Введение: [Service Discovery](./dns_service_discovery.md), SSoT: [DNS в Kubernetes](../dns_deep_dive.md)*

**Ingress** — API-объект, управляющий внешним доступом к сервисам кластера, обычно для HTTP/HTTPS трафика.

* *Подробная информация: [Обзор Ingress](../Ingress/overview.md)*

## Основные концепции

### Принципы сетевой модели

1. **Уникальный IP на под в рамках всего кластера:**
   * Все контейнеры внутри одного пода разделяют одно сетевое пространство имен и общий IP-адрес
   * Контейнеры в одном поде общаются через `localhost`
   * Не может быть двух подов с одинаковыми IP-адресами в кластере, независимо от неймспейсов
   * Уникальность обеспечивает **CNI-плагин**, выделяющий IP из общего `podCIDR`

2. **Прямая связность без NAT:** Любой под может напрямую связаться с любым другим подом в кластере через его IP-адрес

3. **Агенты на узле могут общаться с подами:** Kubelet и другие агенты на узле имеют доступ к подам на этом узле

### Компоненты сети Kubernetes

| Компонент | Уровень | Описание | SSoT |
|-----------|---------|----------|------|
| **Pod-to-Pod** | L2/L3 | IP-связность между подами через CNI | Этот файл |

## Практические сценарии

### 1. Связь внутри пода (Container-to-Container)

Контейнеры внутри одного пода находятся в общем сетевом пространстве имен (network namespace). Взаимодействие:

* Через `localhost` и общие порты
* Разделяют один IP-адрес и сетевые ресурсы

### 2. Связь между подами на одном узле (Node-level)

Когда два пода находятся на одном узле, трафик проходит через виртуальные интерфейсы и мосты ОС:

**Архитектура:**

* **Корневое пространство (`root netns`)** — основное сетевое пространство узла с главным интерфейсом (`eth0`)
* **Пространство пода (`pod netns`)** — изолированное пространство для каждого пода с виртуальным интерфейсом (`eth0` из точки зрения пода)

**Процесс передачи пакета:**

1. Пакет от Пода 1 выходит из `eth0` и через `veth pair` попадает в `root netns` узла
2. В `root netns` работает сетевой мост (`cbr0` или `docker0`), действующий как виртуальный коммутатор
3. Мост получает пакет, определяет IP-адрес назначения (Под 2) и отправляет ARP-запрос
4. Интерфейс `veth` Пода 2 отвечает на ARP-запрос
5. Мост отправляет пакет на интерфейс `veth` Пода 2
6. Пакет через `veth pair` попадает в сетевое пространство Пода 2

### 3. Связь между подами на разных узлах (Cluster-level)

Взаимодействие между подами на разных узлах обеспечивается **CNI-плагином**. Существует два основных подхода:

#### 3.1. Прямая маршрутизация (BGP)

Используется CNI-плагинами **Calico** или **Cilium** в режиме BGP. Не использует инкапсуляцию — высокая производительность.

**Процесс:**

1. **BGP-демоны:** На каждом узле запускается BGP-демон (например, Bird), устанавливающий BGP-сессии с другими узлами
2. **Анонсирование маршрутов:** При появлении нового пода CNI-плагин сообщает локальному BGP-демону, что IP доступен через данный узел
3. **Обновление таблиц маршрутизации:** Все узлы получают обновление и добавляют запись в таблицу маршрутизации ядра Linux (например, `ip route add 10.48.1.5/32 via <IP-адрес Узла 1>`)
4. **Динамическое обновление:** При удалении или перемещении пода таблицы маршрутизации автоматически корректируются

**Преимущества:**

* Прямая маршрутизация без инкапсуляции
* Максимальная производительность
* Сетевая инфраструктура «знает» о подах

**Требования:**

* Поддержка BGP в сетевой инфраструктуре
* Или все узлы в одном L2-сегменте

* *Подробнее о BGP: [BGP (Border Gateway Protocol)](../../../../Networking/Protocols/bgp.md)*

#### 3.2. Оверлейная сеть (Overlay Network)

Используется CNI-плагинами **Flannel** (режим VXLAN) или **Calico** (режим IPIP). Пакеты инкапсулируются в пакеты узлов.

**Процесс:**

1. Пакет от Пода 1 доходит до сетевого моста (`cbr0`) как при связи в пределах узла
2. Мост не находит IP назначения в локальной ARP-таблице и передает пакет CNI-плагину
3. Демон CNI получает из `kube-apiserver` информацию о расположении всех подов
4. CNI-плагин инкапсулирует исходный пакет в новый (UDP для VXLAN, IP для IPIP) с IP-адресами узлов
5. «Обернутый» пакет отправляется через `eth0` Узла 1 на `eth0` Узла 2
6. На Узле 2 CNI-плагин декапсулирует пакет, извлекая исходный
7. Исходный пакет передается на локальный мост (`cbr0`) и доставляется до Пода 2

**Преимущества:**

* Проще в настройке
* Не требует конфигурации BGP
* Работает в любых сетях

**Недостатки:**

* Накладные расходы на инкапсуляцию
* Небольшое снижение производительности

#### 3.3. Анонсирование сервисных IP через BGP (Calico-specific)

Calico поддерживает **IP Advertisement** — анонсирование ClusterIP сервисов внешним BGP-роутерам. Позволяет направлять внешний трафик напрямую к сервисам без NodePort.

* *Подробнее: [IP Advertisement через BGP](./CNI/selection_and_external_access.md#ip-advertisement-через-bgp-calico-specific)*

## Дополнительные сведения

### Путь трафика от Ingress до Pod

Полное описание пути трафика через Ingress Controller, Service и kube-proxy до Pod см. в [Путь трафика: от Ingress до Pod](./traffic_path.md).

### Service и типы сервисов

Абстракция Service обеспечивает стабильную точку доступа к группе подов. Типы сервисов: ClusterIP, NodePort, LoadBalancer, ExternalName.

* *Подробнее: [Обзор Service](../Service/service_overview.md) и [Типы Service](../Service/service_types_summary.md)*

### Рекомендации по архитектуре

**Избегайте `hostPort` и `hostNetwork`:** Эти параметры привязывают под к сетевому стеку узла, ограничивая планирование и расширяя поверхность атаки. Исключения: DaemonSet'ы мониторинга, CNI-плагины, некоторые Ingress-контроллеры.

**Альтернативы:**

* `NodePort` Services для базового внешнего доступа
* `LoadBalancer` Services в облачных средах
* Ingress-контроллеры для HTTP-трафика
* `kubectl port-forward` для отладки

**Выделение Ingress-нод (DMZ-зона):** Для production-окружений рекомендуется архитектура с выделением отдельных нод под Ingress Controller:

```
Внешний трафик → Load Balancer → Ingress-ноды → Backend-ноды
                                      ↓
                              Service → Pods
```

Преимущества: изоляция внешних сервисов, безопасность, масштабируемость, специализация нод.

* *Подробнее: [Архитектура Load Balancer + Ingress Controller](./CNI/selection_and_external_access.md#архитектура-load-balancer--ingress-controller)*
