# Обзор сетевой модели Kubernetes

## Определения

**Сетевая модель Kubernetes** — фундаментальный набор правил и абстракций, обеспечивающий предсказуемое взаимодействие между всеми компонентами кластера. Основана на принципе **IP-per-Pod**: каждый под получает уникальный IP-адрес, доступный из любой точки кластера без использования NAT.

**Pod CIDR (podCIDR)** — диапазон IP-адресов, выделенный всему кластеру или конкретному узлу для назначения адресов подам. Подробнее: [IPAM в CNI](./CNI/ipam.md).

**CNI (Container Network Interface)** — стандарт интерфейса между средой выполнения контейнеров и сетевыми плагинами. Отвечает за выделение IP-адресов и настройку сетевой связности.

* Подробные роли компонентов: [CNI и kube-proxy: роли](./cni_kube_proxy_roles.md)

**kube-proxy** — сетевой агент на каждом узле, реализующий абстракцию `Service` через управление правилами маршрутизации в ядре Linux (iptables или IPVS).

**NetworkPolicy** — ресурс для декларативного управления сетевой изоляцией (L3/L4) между подами.

* Навигатор по политикам: [NetworkPolicy: навигатор](./network_policy.md)

**Service Discovery** — механизмы (в основном DNS), позволяющие подам находить друг друга по именам сервисов вместо динамических IP-адресов.

## Основные концепции

### Три уровня сетей кластера

Взаимодействие в Kubernetes строится на трех логических уровнях:

1. **Сеть узлов (Node Network):** Физическая или виртуальная инфраструктура (L2/L3), по которой общаются серверы кластера между собой и с внешним миром.
2. **Сеть подов (Pod Network):** Виртуальная сеть, создаваемая CNI-плагином. Обеспечивает прямую связность между всеми подами кластера по правилу No-NAT.
3. **Сеть сервисов (Service Network):** Абстрактная сеть виртуальных IP-адресов (ClusterIP), управляемая `kube-proxy` для балансировки трафика и обеспечения стабильных точек входа.

### Фундаментальные принципы

* **Уникальность:** Каждый под имеет собственный IP, разделяемый всеми контейнерами внутри этого пода.
* **Прямая связность:** Любой под может отправить пакет любому другому поду без трансляции адресов (NAT).
* **Отсутствие NAT для агентов:** Kubelet и другие системные компоненты на узле могут обращаться к подам напрямую.
* **Эфемерность:** IP-адреса подов динамичны и меняются при перезагрузке; для стабильного доступа используются `Service`.

## Практические сценарии

### 1. Взаимодействие внутри пода

Контейнеры внутри одного пода разделяют общее сетевое пространство имен (`network namespace`). Они взаимодействуют через `localhost`, разделяя общую таблицу портов и IP-адрес пода.

### 2. Связь между подами на одном узле

Трафик проходит через виртуальные интерфейсы и мост (bridge) внутри операционной системы узла:

1. Пакет из `eth0` пода попадает в пару `veth` в основном сетевом пространстве узла.
2. Сетевой мост (например, `cni0` или `docker0`) выступает в роли коммутатора, пересылая пакет на соответствующий `veth` целевого пода.

### 3. Связь между подами на разных узлах

Реализуется CNI-плагином одним из двух способов:

#### 3.1. Прямая маршрутизация (BGP)

Используется в Calico или Cilium. Узлы кластера обмениваются маршрутами через протокол BGP.

* **Преимущество:** Максимальная производительность, отсутствие накладных расходов на инкапсуляцию.
* **Требование:** Поддержка BGP сетевым оборудованием или размещение узлов в одном L2-сегменте.

#### 3.2. Оверлейная сеть (Overlay)

Используется в Flannel (VXLAN) или Calico (IPIP). Исходный пакет инкапсулируется ("оборачивается") в пакет сети узлов.

* **Преимущество:** Работает в любой инфраструктуре без настройки маршрутизаторов.
* **Недостаток:** Небольшие накладные расходы на инкапсуляцию и снижение MTU.

## Дополнительная информация

### Рекомендации по проектированию

* **Избегайте `hostNetwork` и `hostPort`:** Эти параметры привязывают под к порту узла, что мешает масштабированию и планированию. Используйте `Service` и `Ingress`.
* **Изоляция Ingress:** Рекомендуется запускать Ingress-контроллеры на выделенных узлах (DMZ) для отделения внешнего трафика от основных вычислительных ресурсов.
* **Размер сети:** При проектировании кластера закладывайте достаточный `podCIDR` с учетом будущего масштабирования, так как его изменение в работающем кластере затруднено.
