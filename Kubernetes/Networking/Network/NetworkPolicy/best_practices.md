# NetworkPolicy: Лучшие практики

## Определения

**Лучшие практики NetworkPolicy** — экспертные рекомендации по проектированию, внедрению и эксплуатации сетевой изоляции в Kubernetes, направленные на минимизацию рисков безопасности и оптимизацию производительности.

**Zero Trust Architecture (ZTA)** — стратегия безопасности «Никому не доверяй», предполагающая, что каждый сетевой запрос должен быть проверен и разрешен явно, независимо от его источника (внутри или вне периметра).

**SNAT и сохранение Source IP** — технический нюанс взаимодействия с внешним трафиком. По умолчанию (`externalTrafficPolicy: Cluster`) исходный IP клиента заменяется на IP узла (SNAT), что делает фильтрацию по `ipBlock` неэффективной. Режим `Local` позволяет сохранить исходный IP.

**Протоколы и расширенные порты:**
*   **SCTP (Stream Control Transmission Protocol):** Поддерживается в `v1` API, но требует явной поддержки со стороны CNI. Без поддержки правила SCTP будут молча проигнорированы.
*   **Диапазоны портов (endPort):** Позволяет указывать инклюзивный диапазон портов. Требует обязательного наличия поля `port`.

## Базовые Концепции

### Архитектурные принципы

Эффективное управление сетью основано на масштабируемости и наблюдаемости:

*   **Производительность Data Plane:** При большом количестве политик (>1000) стандартные `iptables` страдают от линейного поиска (O(N)), что увеличивает задержки. Рекомендуется использовать CNI на базе eBPF (Cilium, Calico eBPF), где поиск правил происходит за константное время (O(1)).
*   **Иерархия прав (3-Tier Model):** Использование `AdminNetworkPolicy` (ANP) и `BaselineAdminNetworkPolicy` (BANP) для разделения ответственности. Глобальные правила администратора (например, "запретить доступ к SSH узлов") всегда выполняются первыми.
*   **Декларативное именование:** Названия должны отражать логику: `<действие>-<направление>-<цель>-<назначение>`. Например, `allow-egress-to-rds-production`.

### Технические принципы

*   **Принцип минимальных привилегий:** Открывайте только те порты, которые необходимы приложению. Избегайте разрешений широких диапазонов без необходимости.
*   **Абстракция East-West:** Для трафика внутри кластера **никогда** не используйте `ipBlock`. Поды эфемерны, их IP меняются. Используйте только `podSelector` и `namespaceSelector`.

## Практические Сценарии

### 1. Реализация Zero Trust (Default Deny)

Начинайте настройку любого Namespace с политики «запретить всё». Это переводит сетевой стек в режим разрешительных списков.

**Критический нюанс:** При включении изоляции исходящего трафика (Egress) поды теряют доступ к DNS. Необходимо явно разрешить трафик к `kube-dns` (обычно в `kube-system`).

```yaml
# Разрешение DNS для всех подов в Namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-to-dns
spec:
  podSelector: {}
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

### 2. Фильтрация внешнего трафика (North-South)

Используйте `ipBlock` для ограничения доступа к внешним API или подсетям ЦОД.

**Проблема Source IP:** Чтобы `ipBlock` корректно фильтровал входящий трафик от клиентов, установите `externalTrafficPolicy: Local` в соответствующем Service. Это предотвратит SNAT и позволит политике увидеть реальный IP клиента.

### 3. Защита от SSRF и доступ к облачным метаданным

Блокируйте доступ к чувствительным эндпоинтам облачных провайдеров (AWS, GCP, Azure), чтобы предотвратить кражу IAM-токенов.

```yaml
# Блокировка доступа к Cloud Metadata API
egress:
- to:
  - ipBlock:
      cidr: 0.0.0.0/0
      except:
      - 169.254.169.254/32
```

### 4. Отладка и аудит

Стандартный Kubernetes не логирует заблокированные пакеты. Для диагностики используйте специализированные инструменты:

*   **Cilium Hubble:** `hubble observe --type drop` — показывает, какая именно политика и почему отбросила пакет.
*   **kubectl debug:** Запуск временного контейнера с инструментами (`curl`, `dig`, `nc`) внутри пода для проверки связности в контексте его сетевых прав.
*   **kubectl describe networkpolicy:** Позволяет увидеть, какие именно поды выбраны политикой (Target) и какие правила применены.

## Дополнительные Сведения

### Рекомендации по оптимизации
*   **Группировка правил:** Если несколько сервисов требуют одинаковых прав доступа, объедините их общими метками (Labels), чтобы уменьшить общее количество ресурсов NetworkPolicy.
*   **Использование GitOps:** Изменения в сетевых политиках должны проходить через Code Review. Используйте ArgoCD или Flux для автоматической синхронизации политик из Git.
