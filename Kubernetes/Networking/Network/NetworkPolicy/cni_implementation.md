# NetworkPolicy: Реализация CNI-плагинами

## Определения

**CNI (Container Network Interface) плагин с поддержкой NetworkPolicy** — сетевой компонент Kubernetes, ответственный не только за обеспечение связности между Pod (подами) на уровнях L2/L3, но и за принудительное исполнение (Enforcement) правил фильтрации трафика, описанных в ресурсах `NetworkPolicy`.

**Data Plane (Плоскость данных)** — уровень сетевого стека, на котором происходит фактическая обработка пакетов (маршрутизация, инкапсуляция, фильтрация). Реализация NetworkPolicy происходит именно здесь.

**Enforcement Point (Точка исполнения)** — место в сетевом пути, где CNI-плагин применяет разрешающие или запрещающие правила. Обычно это происходит на виртуальном интерфейсе пода (`veth-pair`) или внутри сетевого пространства имен пода.

**Важное замечание:** Ресурс NetworkPolicy в Kubernetes является лишь декларацией намерения. Если установленный CNI-плагин не поддерживает этот API (например, стандартный Flannel), политики будут успешно созданы в API-сервере, но **никакого эффекта на трафик не окажут**.

## Базовые Концепции

### Механизмы исполнения правил

Различные CNI используют разные технологии ядра Linux для реализации политик:

1.  **iptables / Netfilter:** Традиционный подход (Calico в стандартном режиме, Kube-router). Правила Kubernetes транслируются в цепочки iptables. При большом количестве подов и политик производительность может снижаться из-за линейного перебора правил и больших накладных расходов на атомарное обновление таблиц.
2.  **eBPF (Extended Berkeley Packet Filter):** Современный высокопроизводительный подход (Cilium, Calico eBPF mode). Программы фильтрации загружаются непосредственно в ядро и выполняются на сетевых событиях (например, `tc` ingress/egress). Обеспечивает практически константное время поиска правил (O(1)) через hash-карты (maps) и позволяет анализировать трафик на уровне L7 без переключения контекста.
3.  **Open vSwitch (OVS):** Используется в Antrea и OVN-Kubernetes. Позволяет строить сложные программируемые конвейеры обработки пакетов в пространстве пользователя или ядра через OpenFlow, обеспечивая высокую гибкость и поддержку гибридных сред.

### Сравнительный анализ CNI-плагинов

| CNI | Основной механизм | Поддержка SCTP | Особенности реализации |
| :--- | :--- | :--- | :--- |
| **Calico** | iptables / eBPF | Полная | BGP для маршрутизации, поддержка HostEndpoint, интеграция с внешними файрволами. |
| **Cilium** | eBPF | Полная | Полная замена kube-proxy, Identity-based безопасность, встроенный Hubble. |
| **Antrea** | Open vSwitch | Полная | Оптимизация для Windows, интеграция с VMware NSX, поддержка Tiers (приоритетов). |
| **Kube-router** | iptables / IPVS | Частично | Легковесность, объединение сетевого плагина и балансировщика. |
| **Flannel** | Отсутствует | — | Использует Calico (проект Canal) для реализации политик. |

## Практические Сценарии

### Архитектурный выбор CNI

При выборе решения следует руководствоваться следующими критериями:

1.  **Высокая нагрузка и Observability:** **Cilium**. eBPF позволяет эффективно обрабатывать десятки тысяч соединений в секунду, а Hubble предоставляет визуализацию отброшенных пакетов (Dropped Packets) с указанием конкретной политики.
2.  **Bare-metal и BGP-маршрутизация:** **Calico**. Позволяет интегрировать кластер в существующую сетевую инфраструктуру ЦОД, анонсируя IP-адреса подов напрямую маршрутизаторам.
3.  **Гибридные среды (Linux + Windows):** **Antrea**. Использование OVS обеспечивает консистентное поведение политик на обеих ОС и упрощает управление в гетерогенных кластерах.

### Методология миграции CNI (Flannel -> Cilium/Calico)

Миграция CNI является операцией с высоким риском и требует полной очистки сетевого состояния на узлах:

1.  **Подготовка:** Установка нового CNI-оператора. Настройка политик в режиме «мониторинга» (если поддерживается).
2.  **Остановка Flannel:** Удаление DaemonSet Flannel. На этом этапе связность между узлами может быть нарушена.
3.  **Очистка узлов:**
    *   Удаление виртуальных интерфейсов (`flannel.1`, `cni0`).
    *   Очистка `/etc/cni/net.d/`.
    *   Сброс iptables/ipvs правил (`iptables -F`, `ipvsadm -C`).
4.  **Запуск нового CNI:** Развертывание DaemonSet Calico или Cilium.
5.  **Ротация подов:** Все прикладные поды должны быть перезапущены для получения новых интерфейсов и IP-адресов. **Важно:** до перезапуска старые поды могут потерять сеть полностью.

## Дополнительные Сведения

### Архитектурные детали лидеров рынка

#### Calico: Гибкость и мощность
*   **HostEndpoint:** Позволяет применять NetworkPolicy к сетевым интерфейсам хоста (например, `eth0`). Это защищает сам узел от внешних атак, превращая каждый сервер в кластере в распределенный файрвол.
*   **GlobalNetworkPolicy:** Позволяет задавать правила на уровне кластера (Cluster-scoped). Идеально для разрешения трафика от систем мониторинга или безопасности ко всем подам без дублирования манифестов.
*   **Режимы инкапсуляции:** Поддерживает VXLAN, IP-in-IP или отсутствие инкапсуляции. Последний вариант наиболее производителен, так как исключает накладные расходы на заголовки пакетов.

#### Cilium: Сетевой интеллект на базе eBPF
*   **L7 Enforcement:** Cilium терминирует трафик (через прозрачный прокси Envoy) и может фильтровать запросы по HTTP путям, методам, заголовкам или топикам Kafka.
*   **FQDN-фильтрация:** Позволяет создавать правила вида «разрешить доступ к `*.google.com`». Cilium перехватывает DNS-ответы и динамически обновляет список разрешенных IP-адресов.
*   **Identity-based Security:** Вместо использования IP-адресов для правил, Cilium генерирует числовой идентификатор (Security Identity) на основе меток пода. Это исключает необходимость обновления правил при каждом перезапуске пода.
*   **Hubble UI:** Графический интерфейс для визуализации графа зависимостей и анализа сетевых аномалий в реальном времени.

#### Antrea: Enterprise возможности
*   **Policy Tiers:** Позволяет выстраивать иерархию (например, Tier `Emergency`, `SecurityAdmin`, `Application`). Правила в более высоких тирах проверяются первыми и не могут быть переопределены на нижних уровнях.
*   **Traceflow:** Инструмент для инъекции реальных пакетов в сеть для проверки прохождения всех этапов фильтрации (OVS flows).
