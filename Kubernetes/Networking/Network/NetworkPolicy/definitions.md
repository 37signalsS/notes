# NetworkPolicy: Определения и концепции

## Определения

**NetworkPolicy** — ресурс Kubernetes (API-группа `networking.k8s.io`), предназначенный для декларативного управления сетевым доступом на уровнях L3 (сетевой) и L4 (транспортный) модели OSI. Функционирует по принципу «белых списков» (Allow-lists). NetworkPolicy является лишь спецификацией в API; фактическое принудительное исполнение правил (Enforcement) выполняет сетевой плагин (CNI).

**policyTypes** — обязательное поле в секции `spec`, определяющее, в каких направлениях (Ingress, Egress) политика применяет правила. Без указания этого поля политика не оказывает никакого воздействия на трафик, даже если правила определены. Поддерживает значения `Ingress` и/или `Egress`.

**AdminNetworkPolicy (ANP)** — (начиная с K8s 1.30+ Beta) кластерный ресурс (API-группа `policy.networking.k8s.io`), позволяющий администраторам задавать глобальные правила безопасности, которые невозможно переопределить на уровне пространств имен. Поддерживает три действия: `Allow` (разрешает трафик), `Deny` (блокирует), `Pass` (передает на проверку в Tier 2).

**BaselineAdminNetworkPolicy (BANP)** — кластерный ресурс, определяющий сетевые правила «последнего шанса». Применяется только в том случае, если трафик не был разрешен или запрещен вышестоящими ANP или обычными NetworkPolicy.

**Сетевая изоляция (Network Isolation)** — состояние пода, при котором его сетевой стек переходит в режим «запрещено по умолчанию» (Default Deny). Активируется автоматически, как только под попадает под действие (`spec.podSelector`) хотя бы одной политики.

**CNI (Container Network Interface)** — интерфейс взаимодействия Kubernetes с сетевыми плагинами. Именно CNI-плагин (например, Cilium, Calico, Antrea) несет ответственность за техническую реализацию правил NetworkPolicy (через iptables, nftables, eBPF или OVS).

**Ingress / Egress** — направления трафика. Ingress — входящий трафик к поду; Egress — исходящий трафик от пода. Каждое направление определяется отдельной секцией правил и требует явного включения через `policyTypes`.

**matchExpressions** — расширенный механизм селекторов (set-based), позволяющий фильтровать объекты по вхождению меток в списки (`In`, `NotIn`) или их наличию (`Exists`, `DoesNotExist`). Поддерживает комбинирование нескольких выражений в одном селекторе.

**conntrack (Connection Tracking)** — механизм ядра Linux, отслеживающий состояния активных сетевых соединений. NetworkPolicy использует conntrack для автоматического разрешения ответного трафика (return traffic) независимо от наличия разрешающих правил в противоположном направлении.

**ipBlock** — секция правил, определяющая доступ по диапазонам IP-адресов (CIDR). Поддерживает поле `except` для исключения конкретных подсетей. Предназначен для внешнего трафика; не рекомендуется для East-West трафика внутри кластера из-за эфемерности IP подов.

**Named Ports** — механизм именования портов в Pod Spec, позволяющий ссылаться на порты по имени (например, `http`, `https`) вместо числового значения. NetworkPolicy поддерживает именованные порты, что повышает гибкость манифестов при изменении номеров портов.

## Базовые Концепции

### Принцип «Запрещено по умолчанию» (Zero Trust)

В стандартной конфигурации Kubernetes реализует модель **Default Allow**: любой под может отправить пакет любому другому поду. Как только создается NetworkPolicy, выбирающая под:
1.  Сетевой стек пода становится изолированным в направлениях, указанных в `policyTypes`.
2.  Любой пакет, не подходящий под разрешающие правила, отбрасывается (Drop).
3.  Если в политике есть секция `ingress`, но нет правил — весь входящий трафик блокируется. Аналогично для `egress`.

**Критический нюанс:** Если `policyTypes` не указан, но правила `ingress`/`egress` определены — политика **не применяется**. Kubernetes игнорирует правила, если направление не включено в `policyTypes`.

### Иерархическая модель (3-Tier Enforcement)

На 2026 год сетевая безопасность Kubernetes строится на строгой последовательности проверки правил:

*   **Tier 1: Admin Policies (ANP).** Глобальный уровень. Имеет три действия:
    *   `Allow`: Разрешает трафик, прекращая дальнейшие проверки.
    *   `Deny`: Блокирует трафик, прекращая дальнейшие проверки.
    *   `Pass`: Передает пакет на проверку в Tier 2.
*   **Tier 2: Developer Policies (NetworkPolicy).** Уровень Namespace. Работает аддитивная логика (логическое «ИЛИ» между всеми политиками). Если пакет разрешен хотя бы одной — он проходит. Если ни одна не разрешает — пакет уходит на Tier 3.
*   **Tier 3: Baseline Policies (BANP).** Глобальный уровень настроек по умолчанию. Если здесь нет разрешающего правила — пакет окончательно блокируется.

### Логические операторы И и ИЛИ

Эффективное управление доступом требует понимания того, как комбинируются условия:

1.  **Логическое «ИЛИ» (Массивы):**
    *   Элементы в списках `ingress` и `egress` являются независимыми правилами.
    *   Элементы в списках `from` (для Ingress) и `to` (для Egress) объединяются по «ИЛИ». Трафик разрешен, если он соответствует **хотя бы одному** из элементов списка.
2.  **Логическое «И» (Поля объекта):**
    *   Поля внутри одного элемента списка `from` или `to` (например, `podSelector` и `namespaceSelector`) объединяются по «И». Трафик разрешен только при **одновременном** выполнении всех условий.

**Важно:** Порядок элементов в массивах `ingress`/`egress` не имеет значения. Правила проверяются как единый набор, а не последовательно.

### Селекторы и их отсутствие

*   **`podSelector: {}`**: Выбирает **все** поды в пространстве имен, где создана политика.
*   **`podSelector: {}` в секции `from`**: Соответствует **всем** подам в текущем пространстве имен (без фильтрации по меткам).
*   **Отсутствие `podSelector` в секции `from`/`to`**: При наличии `namespaceSelector` означает «все поды в выбранном пространстве имен». Если `namespaceSelector` тоже отсутствует — означает «все поды во всех пространствах имен».
*   **Пустой `ingress: []` или `egress: []`**: Если направление указано в `policyTypes`, но список правил пуст, это означает «запретить всё» (Default Deny) для данного направления.
*   **Отсутствие `ingress`/`egress` (поле не указано)**: Если направление указано в `policyTypes`, но само поле отсутствует — это эквивалентно пустому списку и означает «запретить всё».

### Комбинирование namespaceSelector и podSelector

Комбинация `namespaceSelector` и `podSelector` в одном элементе списка `from`/`to` работает по логическому «И»:

*   **В одном объекте (И):** Трафик разрешен от подов, соответствующих **обоим** селекторам одновременно (под с нужными метками **в** нужном пространстве имен).
*   **В разных объектах массива (ИЛИ):** Трафик разрешен от **любого** пода в выбранном пространстве имен **ИЛИ** от подов с нужными метками в текущем пространстве имен.

### Семантика портов

Правила фильтрации по портам работают по принципу «белого списка»:

*   **Порты указаны:** Разрешен трафик **только** на указанные порты. Трафик на все остальные порты блокируется, даже если источник разрешен.
*   **Порты не указаны (секция `ports` отсутствует):** Разрешен трафик на **все** порты протоколов TCP, UDP и SCTP.
*   **Протоколы:** Поддерживаются `TCP`, `UDP` и `SCTP` (поддержка SCTP зависит от CNI). Если протокол не указан, правило применяется ко всем протоколам.
*   **Диапазоны (endPort):** Позволяют открывать массивы портов одной записью. Диапазон включает как `port`, так и `endPort` (включительно). Поддержка `endPort` появилась в Kubernetes 1.21+.

### Жизненный цикл соединения (Stateful)

NetworkPolicy являются **stateful** (с сохранением состояния). Если трафик разрешен в одном направлении, ответный трафик (Return traffic) разрешается автоматически на уровне ядра (Connection Tracking / conntrack), независимо от наличия разрешающих правил в противоположном направлении.

**Практическое следствие:** При настройке Egress-политики не нужно создавать отдельные Ingress-правила для ответного трафика. Однако это работает только для **ответов** на уже установленные соединения. Новые инициированные подом соединения подчиняются Egress-правилам, а новые входящие соединения — Ingress-правилам.

### Селекторы и CIDR

Политики используют три типа идентификации субъектов:
1.  **podSelector**: Выбор подов по меткам в текущем или другом (при наличии `namespaceSelector`) пространстве имен.
2.  **namespaceSelector**: Выбор всех подов в пространствах имен с определенными метками. Поддерживает автоматическую метку `kubernetes.io/metadata.name` (K8s 1.21+), позволяющую выбирать namespace по имени без предварительной ручной разметки.
3.  **ipBlock**: Определение внешних IP-диапазонов (CIDR).
    *   *Нюанс:* Не используйте `ipBlock` для трафика внутри кластера, так как IP подов эфемерны.

## Практические Сценарии

### Default Deny All

Изоляция всех подов в Namespace как отправная точка безопасности. После создания этой политики весь трафик блокируется, пока не будут добавлены разрешающие правила.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: production
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

### Namespace Segmentation

Разрешение трафика только между конкретными пространствами имен. Политика применяется к подам с меткой `role: api` и разрешает входящий трафик только от подов в namespace `frontend`.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend-only
  namespace: production
spec:
  podSelector:
    matchLabels:
      role: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: frontend
```

### Разрешение DNS при Egress-изоляции

Классическая ошибка — блокировка DNS-запросов при включении Egress. Без явного разрешения трафика к CoreDNS поды не смогут разрешать имена сервисов.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-egress-with-dns
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: api-server
  policyTypes:
  - Egress
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
      podSelector:
        matchLabels:
          k8s-app: kube-dns
    ports:
    - protocol: UDP
      port: 53
    - protocol: TCP
      port: 53
```

### Infrastructure Access через BANP

Глобальное разрешение доступа к CoreDNS для всех приложений на уровне Tier 3. Используется, если на Tier 2 (NetworkPolicy) не определены специфические правила для DNS.

```yaml
apiVersion: policy.networking.k8s.io/v1alpha1
kind: BaselineAdminNetworkPolicy
metadata:
  name: default-allow-dns
spec:
  selector:
    matchLabels: {}
  egress:
  - to:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: kube-system
    ports:
    - protocol: UDP
      port: 53
```

*Подробные манифесты и шаги настройки: [NetworkPolicy: Практические сценарии](./practical_scenarios.md)*

## Дополнительные Сведения

### Технические ограничения и нюансы

*   **Отсутствие L7:** Стандартные политики не понимают HTTP-пути, методы или заголовки Host. Для этого требуется Service Mesh или расширения CNI (CiliumNetworkPolicy).
*   **HostNetwork:** Поды с `hostNetwork: true` обычно не подчиняются NetworkPolicy, так как используют сетевое пространство имен хоста. Их трафик обрабатывается правилами iptables/nftables самого узла.
*   **IPv6:** Поддержка IPv6 в NetworkPolicy зависит от реализации CNI и конфигурации Dual-stack кластера. При использовании Dual-stack необходимо учитывать оба адресных пространства.
*   **Named Ports:** Использование имен портов вместо номеров поддерживается, но требует их предварительного определения в Pod Spec. CNI сопоставляет имя порта с числовым значением на этапе проверки правила.
*   **Трафик loopback:** NetworkPolicy не может заблокировать трафик внутри пода (между контейнерами через `127.0.0.1`), так как этот трафик не покидает сетевой стек пода и не проходит через CNI-плагин.
*   **FQDN Egress:** Начиная с 2025 года, многие CNI (Cilium, Calico) и расширения K8s API поддерживают фильтрацию Egress по доменным именам (FQDN), что позволяет разрешать доступ к внешним ресурсам без фиксации их IP-адресов.

### Взаимодействие с Services и DNAT

NetworkPolicy работают на уровне IP подов, а не IP сервисов (ClusterIP):

*   **Ingress:** Когда трафик идет через Service, CNI видит его уже после DNAT (замены IP сервиса на IP конкретного пода). Поэтому политика Ingress должна разрешать трафик от *источника* (например, Ingress-контроллера).
*   **Egress:** Если под обращается к ClusterIP, правила Egress должны разрешать доступ либо к IP сервиса, либо к IP подов назначения (зависит от момента выполнения DNAT в конкретном CNI). Безопаснее разрешать доступ по селекторам подов.

### Производительность

Алгоритмическая сложность проверки правил зависит от реализации CNI:

*   **iptables / nftables (Calico, Antrea):** Линейный перебор правил O(N). При количестве политик свыше 1000 и десятках тысяч подов наблюдается рост задержек и увеличение времени перезапуска подов.
*   **eBPF (Cilium):** Константное время поиска O(1) через хеш-таблицы. Критично для кластеров с динамичными рабочими нагрузками и большим количеством политик.

### Типичные ошибки

| Проблема | Вероятная причина | Решение |
|:---|:---|:---|
| Политика создана, но не работает | Отсутствует поле `policyTypes` | Добавить `policyTypes: [Ingress]` и/или `[Egress]` |
| Под не может разрешить DNS-имена | Egress-политика блокирует порт 53 | Добавить правило разрешения трафика к `kube-dns` |
| Трафик блокируется между подами в одном namespace | `podSelector: {}` с `ingress: []` блокирует весь входящий трафик | Добавить разрешающие правила для необходимых подов |
| Трафик от подов другого namespace не проходит | Используется только `podSelector` в `from` | Добавить `namespaceSelector` для выбора подов из другого namespace |
| Трафик к Service блокируется | NetworkPolicy работает с IP подов, а не ClusterIP | Разрешать трафик по селекторам подов назначения |

### Сравнение с альтернативами

*   **CiliumNetworkPolicy:** Добавляет поддержку DNS-имен (FQDN), L7-правила и интеграцию с TLS.
*   **Calico GlobalNetworkPolicy:** Позволяет применять политики к узлам (Nodes) и другим сущностям вне подов.
*   **Service Mesh (Istio/Linkerd):** Обеспечивает mTLS и авторизацию на прикладном уровне, дополняя L3/L4 защиту NetworkPolicy.

### Взаимодействие с ServiceAccount и RBAC

NetworkPolicy работает на сетевом уровне (L3/L4), а RBAC — на уровне API (авторизация). Эти слои работают независимо:

1. **RBAC разрешает доступ к API Server**, но NetworkPolicy может блокировать сетевой трафик к API Server (port 6443).
2. **NetworkPolicy разрешает трафик между подами**, но RBAC может запретить выполнение операции через API.
3. **ServiceAccount предоставляет токен** для аутентификации в API Server. Для работы токена NetworkPolicy должен разрешать Egress к API Server (6443).

**Критический нюанс:** Если под использует ServiceAccount для доступа к API Server, необходимо включить `automountServiceAccountToken: true` (по умолчанию) И разрешить Egress к API Server через NetworkPolicy.

### Взаимодействие с Admission Webhooks

Admission Webhooks (Kyverno, Gatekeeper, OPA) требуют сетевого доступа от API Server:

- **Порт webhook:**通常 8443 или 9443
- **Направление:** Ingress к webhook подам от API Server
- **Проблема:** Если NetworkPolicy блокирует порт webhook, API Server не может применить политику допуска

**Решение:** Явно разрешить Ingress к webhook подам от API Server (или от CIDR master-узлов).

### Взаимодействие с DNS

DNS критичен для работы почти всех приложений. При включении Egress Default Deny поды теряют доступ к CoreDNS:

- **Обязательно:** Разрешить UDP/TCP 53 к CoreDNS (`kube-system`) ПЕРЕД применением Default Deny Egress
- **NodeLocal DNSCache:** Если установлен, разрешить трафик к `169.254.20.10:53`
- **conntrack race:** При высокой нагрузке UDP-запросы к DNS могут сталкиваться с проблемами conntrack. Решение: NodeLocal DNSCache
