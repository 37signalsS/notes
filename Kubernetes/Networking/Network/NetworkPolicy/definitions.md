# NetworkPolicy: Определения и концепции

## Определения

**NetworkPolicy** — ресурс Kubernetes для декларативного управления правилами доступа к сети на уровнях L3 (Layer 3 — сетевой) и L4 (Layer 4 — транспортный) модели OSI (Open Systems Interconnection) между Pod (подами) и внешними сетевыми сущностями.

**Сетевая изоляция** — состояние, при котором сетевой трафик к Pod или от него ограничен правилами безопасности. В стандартной конфигурации Kubernetes Pod не изолированы.

**CNI (Container Network Interface)** — интерфейс сетевого плагина Kubernetes, ответственный за выделение IP-адресов (Internet Protocol) и обеспечение связности. Реализация правил NetworkPolicy зависит от возможностей конкретного CNI (например, Calico, Cilium, Weave Net).

*Подробнее о роли сетевых компонентов: [CNI и kube-proxy: навигатор](../cni_kube_proxy_roles.md) и [Общие определения CNI](../CNI/definitions.md).*

## Базовые Концепции

### Сетевая модель по умолчанию

В Kubernetes реализуется **«плоская» сетевая модель**, описанная в [Общем обзоре сетевой модели](../network_overview.md):

* Все Pod могут общаться со всеми Pod в кластере напрямую без NAT (Network Address Translation).
* Пространства имен (Namespaces) являются логическим разделением и не создают сетевых барьеров.

### Принцип Default Deny (Запрещено по умолчанию)

NetworkPolicy работает по принципу явного разрешения (Allow-list):

1. **Default Allow**: Если к Pod не применяется ни одна политика, весь входящий и исходящий трафик разрешен.
2. **Default Deny**: Как только к Pod применяется хотя бы одна NetworkPolicy, Pod переходит в режим изоляции. Весь трафик, который не разрешен явно текущей или другими политиками, блокируется.

### Структура ресурса

Основные поля в формате YAML (YAML Ain't Markup Language):

* **`spec.podSelector`**: Селектор целевых Pod, к которым применяется политика. Пустой селектор `{}` выбирает все Pod в текущем Namespace.
* **`spec.policyTypes`**: Определяет направления трафика: `Ingress` (входящий), `Egress` (исходящий) или оба.
* **`spec.ingress`**: Список разрешающих правил для входящего трафика.
* **`spec.egress`**: Список разрешающих правил для исходящего трафика.

#### Селекторы источников (from) и назначений (to)

1. **`podSelector`**: Выбор Pod по меткам.
2. **`namespaceSelector`**: Выбор всех Pod в Namespace по меткам этого Namespace.
3. **`ipBlock`**: Указание внешних диапазонов IP-адресов в формате CIDR (Classless Inter-Domain Routing).

### Терминология: Target, Source, Destination

При настройке политик используются следующие термины:

* **Target (Цель)**: Pod, к которым применяется политика (`spec.podSelector`).
* **Source (Источник)**: Откуда приходит трафик (`spec.ingress.from`).
* **Destination (Назначение)**: Куда направляется трафик (`spec.egress.to`).

### Нюансы реализации

* **Локальный трафик**: NetworkPolicy не ограничивает трафик между контейнерами внутри одного Pod через `localhost`.
* **Двусторонний трафик**: Для установления соединения между Pod А и Pod Б необходимо разрешить `Egress` на стороне А и `Ingress` на стороне Б.
* **Диапазоны портов**: Можно использовать `endPort` для указания диапазона портов TCP (Transmission Control Protocol) или UDP (User Datagram Protocol).

### Ограничения

* **Уровень фильтрации**: Стандартные политики работают только на L3/L4. Они не поддерживают протоколы L7 (Layer 7 — прикладной), такие как HTTP (HyperText Transfer Protocol) или gRPC (Google Remote Procedure Call).
* **FQDN**: Базовые ресурсы не поддерживают фильтрацию по полным доменным именам (Fully Qualified Domain Name).
* **Абстракции**: Политики применяются к Pod, а не к ресурсам Service.

## Практические Сценарии

Типовые примеры конфигураций включают:

* **Deny-all**: Полная изоляция входящего трафика.
* **Allow-all**: Разрешение всего трафика (используется для перекрытия ограничивающих политик).
* **Доступ к DNS**: Разрешение запросов к системе доменных имен (Domain Name System).

*Пошаговое руководство с примерами YAML: [NetworkPolicy: Практические сценарии](./practical_scenarios.md)*

## Дополнительные Сведения

### Альтернативы для L7 и FQDN

Для расширенного контроля трафика используются специализированные решения:

* **Cilium**: Поддержка DNS-политик и фильтрации FQDN на уровне eBPF.
* **Calico**: Расширенные политики (GlobalNetworkPolicy) и поддержка доменных имен.
* **Service Mesh (Istio, Linkerd)**: Обеспечение mTLS (mutual Transport Layer Security) и L7-авторизации.

### Проблемы NAT и Source IP

При использовании `NodePort` или `LoadBalancer` исходный IP клиента может подменяться на IP узла (Node). Для корректной работы `ipBlock` необходимо учитывать настройки `externalTrafficPolicy`.
