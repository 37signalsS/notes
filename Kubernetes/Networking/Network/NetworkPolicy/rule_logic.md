# NetworkPolicy: Логика правил

## Определения

**Логика правил NetworkPolicy** — совокупность принципов, по которым Kubernetes и сетевой плагин (CNI) интерпретируют селекторы, порты и диапазоны IP-адресов для принятия решения о разрешении или блокировке сетевого трафика.

**Аддитивность политик** — принцип, согласно которому итоговый набор разрешений для пода является объединением (логическое «ИЛИ») всех правил всех NetworkPolicy, которые выбирают данный под.

**Изоляция (Isolation)** — состояние пода, возникающее при его выборе хотя бы одной политикой. В этом состоянии весь трафик в выбранном направлении (Ingress/Egress) запрещен, если он не разрешен явно.

## Базовые Концепции

### Логические операторы И и ИЛИ

Эффективное управление доступом требует понимания того, как комбинируются условия в манифесте:

1.  **Логическое «ИЛИ» (Массивы):**
    *   Элементы в списках `ingress` и `egress` являются независимыми правилами.
    *   Элементы в списках `from` (для Ingress) и `to` (для Egress) объединяются по «ИЛИ». Трафик разрешен, если он соответствует **хотя бы одному** из элементов списка.
2.  **Логическое «И» (Поля объекта):**
    *   Поля внутри одного элемента списка `from` или `to` (например, `podSelector` и `namespaceSelector`) объединяются по «И». Трафик разрешен только при **одновременном** выполнении всех условий.

### Взаимодействие нескольких политик

Если к одному поду применяются несколько ресурсов NetworkPolicy:
*   Разрешения суммируются. Если политика А разрешает порт 80, а политика Б — порт 443, поду будет разрешен доступ по обоим портам.
*   Порядок создания политик не имеет значения.
*   Запрещающих правил (Deny rules) в стандартных NetworkPolicy не существует; изоляция работает как неявный запрет всего, что не разрешено.

### Селекторы и их отсутствие

*   **`podSelector: {}`**: Выбирает **все** поды в пространстве имен, где создана политика.
*   **Отсутствие `podSelector`**: В секции `spec` недопустимо (поле обязательно), но в правилах `from`/`to` отсутствие селектора при наличии `namespaceSelector` означает «все поды в выбранном пространстве имен».
*   **Пустой `ingress: []` или `egress: []`**: Если направление указано в `policyTypes`, но список правил пуст, это означает «запретить всё» (Default Deny) для данного направления.

## Практические Сценарии

### Пример 1: Комбинирование селекторов (Логическое «И»)

В данном примере трафик разрешен только от подов с меткой `app: frontend`, которые при этом находятся в Namespace с меткой `stage: prod`.

```yaml
ingress:
- from:
  - namespaceSelector:
      matchLabels:
        stage: prod
    podSelector:
      matchLabels:
        app: frontend
```

### Пример 2: Раздельные правила (Логическое «ИЛИ»)

Здесь разрешен трафик от любого пода в Namespace `monitoring` **ИЛИ** от подов с меткой `app: explorer` в текущем Namespace.

```yaml
ingress:
- from:
  - namespaceSelector:
      matchLabels:
        name: monitoring
  - podSelector:
      matchLabels:
        app: explorer
```

### Пример 3: Диапазоны IP-адресов и исключения (ipBlock)

`ipBlock` используется для фильтрации трафика от/к внешним сущностям. Поле `except` позволяет исключить подсети из разрешенного диапазона CIDR (Classless Inter-Domain Routing).

```yaml
egress:
- to:
  - ipBlock:
      cidr: 10.0.0.0/8
      except:
      - 10.1.0.0/16
```

**Нюанс:** Если `ipBlock` указан в одном элементе массива вместе с `podSelector`, это может привести к некорректной работе в зависимости от реализации CNI (обычно они используются раздельно).

### Пример 4: Диапазоны портов (endPort)

Начиная с Kubernetes 1.25 (Stable), можно указывать диапазоны портов.

```yaml
ingress:
- ports:
  - protocol: TCP
    port: 30000
    endPort: 32767
```

**Результат:** Разрешен входящий трафик на все порты в диапазоне от 30000 до 32767 включительно.

## Дополнительные Сведения

### Влияние policyTypes

Явное указание `policyTypes` является лучшей практикой:
*   Если `policyTypes` не указан, Kubernetes делает вывод на основе наличия секций `ingress` и `egress`.
*   Если в политике есть только `egress`, но `policyTypes` не содержит `Egress`, правила исходящего трафика будут проигнорированы.
*   Рекомендуется всегда указывать оба типа, если планируется управлять и входящим, и исходящим трафиком.

### Локальный трафик (Loopback)

NetworkPolicy не может заблокировать трафик внутри пода (между контейнерами через `127.0.0.1`), так как этот трафик не проходит через сетевой стек хоста или CNI, управляемый политиками.
