# Путь трафика в Kubernetes: от Ingress до Pod

- **Ingress Controller** — это главный ресепшен на входе в здание.
- **Service** — это внутренний номер отдела (например, "Отдел продаж, доб. 205").
- **Pod** — это конкретный сотрудник за своим столом в этом отделе.

Вот как запрос проходит через всю цепочку: `Внешний мир -> Ingress Controller -> Service -> Pod`.

## Этапы прохождения трафика

### 1. Внешний мир -> Балансировщик нагрузки

1.  **Пользователь** открывает в браузере сайт `https://my-app.com/path`.
2.  **DNS** преобразует домен `my-app.com` во внешний IP-адрес. Этот IP-адрес принадлежит внешнему балансировщику нагрузки (LoadBalancer), который облачный провайдер создал для службы Ingress Controller.
3.  Трафик попадает на этот внешний IP и перенаправляется на один из узлов (Node) вашего Kubernetes-кластера на определенный порт (`NodePort`).

### 2. Узел кластера -> Ingress Controller

1.  На узле кластера запрос принимает **под Ingress Controller'а** (например, Nginx, Traefik). Это обычный веб-сервер, запущенный в кластере и настроенный на прием внешнего трафика. Подробнее см. [Обзор Ingress](../Ingress/ingress_overview.md).
2.  Ingress Controller смотрит на запрос:
    -   **Хост:** `my-app.com`
    -   **Путь:** `/path`
3.  Он анализирует все **ресурсы `Ingress`** (YAML-файлы с правилами), которые вы создали в кластере. Он ищет правило, которое соответствует этому хосту и пути.
4.  Найдя подходящее правило, Ingress Controller видит, на какой **`Service`** нужно перенаправить этот запрос. Например, правило может гласить: "Все запросы для `my-app.com/path` отправляй на сервис `my-app-service` на порт `80`".

### 3. Ingress Controller -> Service

1.  Ingress Controller не отправляет трафик напрямую в под. Он отправляет его на внутренний, стабильный IP-адрес сервиса — **ClusterIP**. Этот IP-адрес доступен только внутри кластера.
2.  **`Service`** — это абстракция, которая предоставляет единую точку входа для группы подов. У него нет своего процесса, который принимает трафик. Его основная задача — постоянно отслеживать поды, у которых есть определенная метка (label), например, `app: my-app`. Подробнее см. [Обзор Service](../Service/service_overview.md).
3.  `Service` хранит список IP-адресов всех здоровых подов, соответствующих его селектору. Этот список называется **Endpoints**.

### 4. Service -> Pod (через kube-proxy)

Здесь в игру вступает `kube-proxy` — системный компонент, который работает на **каждом узле** кластера.

1.  `kube-proxy` видит, что Ingress Controller отправил пакет на виртуальный ClusterIP сервиса `my-app-service`.
2.  `kube-proxy` смотрит в список **Endpoints** для этого сервиса и выбирает IP-адрес одного из реальных, работающих подов.
3.  С помощью правил `iptables` (или `IPVS`) на уровне ядра операционной системы узла, `kube-proxy` "на лету" подменяет IP-адрес назначения (с ClusterIP сервиса на реальный IP пода) и перенаправляет пакет. Детали реализации см. в [Роли CNI и kube-proxy](./cni_kube_proxy_roles.md).

### 5. Доставка в Pod

1.  Сетевой пакет, пройдя все эти этапы, наконец-то достигает конкретного пода.
2.  Контейнер с вашим приложением, работающий внутри пода, получает запрос, обрабатывает его и отправляет ответ.
3.  Ответ проходит весь путь в обратном порядке и доставляется пользователю.

## Примерная схема трафика Pod-to-Pod (с Flannel)

1.  **Внутри узла:**

    -   Под `Pod A` на `Node 1` хочет отправить пакет поду `Pod B` на том же узле.
    -   Трафик идет от `Pod A` через его `veth` интерфейс на сетевой мост `cni0`.
    -   Мост `cni0` видит, что IP-адрес назначения принадлежит `Pod B` на этом же узле, и напрямую отправляет трафик на его `veth` интерфейс.

2.  **Между узлами:**

    -   `Pod A` на `Node 1` хочет отправить пакет поду `Pod C` на `Node 2`.
    -   Трафик снова попадает на мост `cni0`.
    -   Мост видит, что IP-адрес назначения находится в другой подсети, и, согласно таблице маршрутизации, отправляет трафик на виртуальный туннельный интерфейс, созданный Flannel (например, `flannel.1`).
    -   Flannel инкапсулирует исходный пакет в новый UDP-пакет (используя VXLAN) и отправляет его на IP-адрес `Node 2`.
    -   На `Node 2` Flannel распаковывает пакет и направляет его на мост `cni0`, который доставляет его до `Pod C`.

## Избегайте hostPort и hostNetwork

`hostNetwork` и `hostPort` привязывают под к сетевому стеку узла, что ограничивает планирование подов и расширяет поверхность атаки. Однако существуют легитимные сценарии их использования, например, для DaemonSet'ов мониторинга, CNI-плагинов или некоторых Ingress-контроллеров.

```yaml
# ИЗБЕГАЙТЕ, если это не является крайней необходимостью
spec:
  hostNetwork: true
  containers:
  - name: app
    ports:
    - containerPort: 80
      hostPort: 80  # Привязывает под к конкретному узлу
```

В качестве альтернативы рекомендуется использовать:

-   `NodePort` Services для базового внешнего доступа.
-   `LoadBalancer` Services в облачных средах.
-   Ingress-контроллеры для HTTP-трафика.
-   `kubectl port-forward` для отладки.
