# IPVS (IP Virtual Server) в Kubernetes

## Определения

**IPVS (IP Virtual Server)** — высокопроизводительный балансировщик нагрузки транспортного уровня (L4), реализованный в виде модуля ядра Linux. Является частью проекта LVS (Linux Virtual Server) и работает внутри сетевого стека ядра (Netfilter).

**kube-proxy в режиме IPVS** — режим работы сетевого прокси Kubernetes, при котором балансировка трафика между подами реализуется через хеш-таблицы IPVS вместо цепочек `iptables`.

**kube-ipvs0** — виртуальный (dummy) сетевой интерфейс, создаваемый `kube-proxy` на каждом узле. Он служит «якорем» для назначения виртуальных IP-адресов сервисов (`ClusterIP`), чтобы ядро Linux знало, что этот трафик нужно обрабатывать локально.

---

## Основные концепции

### Механизм работы

IPVS предназначен для распределения нагрузки между несколькими серверами. В Kubernetes он перехватывает трафик, направленный на VIP (Virtual IP) сервиса, и выполняет трансляцию адресов (DNAT) на конкретные IP-адреса подов.

В отличие от `iptables`, где правила проверяются последовательно (сложность $O(n)$), IPVS использует **хеш-таблицы** (сложность $O(1)$). Это делает его значительно более производительным в кластерах с тысячами сервисов.

### Алгоритмы балансировки (Schedulers)

IPVS предоставляет гибкость в выборе способа распределения трафика:

| Алгоритм | Код | Описание |
| :--- | :--- | :--- |
| **Round Robin** | `rr` | Простое циклическое распределение. |
| **Weighted Round Robin** | `wrr` | Учитывает веса (мощность) целевых узлов. |
| **Least Connection** | `lc` | Отправляет пакет туда, где меньше всего активных соединений. |
| **Source Hashing** | `sh` | Гарантирует попадание клиента на тот же под по IP-адресу (Sticky Sessions). |
| **Shortest Expected Delay** | `sed` | Минимизирует ожидаемую задержку ответа. |

### Сравнение технологий балансировки

| Критерий | iptables | IPVS | eBPF (Cilium) |
| :--- | :--- | :--- | :--- |
| **Масштабируемость** | Низкая (линейная) | Высокая | Очень высокая |
| **Скорость поиска** | $O(n)$ | $O(1)$ | $O(1)$ |
| **Алгоритмы** | Только случайный | Множество (rr, lc, sh) | Любая логика через код |
| **Зависимости** | Встроено в ядро | Требует модулей ядра | Ядро 5.10+ |

## Практические сценарии

### 1. Переключение kube-proxy на IPVS

Для активации режима необходимо выполнить два этапа: подготовить узлы и обновить конфигурацию.

#### Шаг 1: Подготовка узлов (Загрузка модулей)

Без этих модулей `kube-proxy` может автоматически «откатиться» в режим `iptables`.

```bash
cat <<EOF | sudo tee /etc/modules-load.d/ipvs.conf
ip_vs
ip_vs_rr
ip_vs_wrr
ip_vs_sh
nf_conntrack
EOF
sudo modprobe ip_vs ip_vs_rr ip_vs_wrr ip_vs_sh nf_conntrack
```

#### Шаг 2: Настройка KubeProxyConfiguration

В ConfigMap `kube-proxy` (обычно в namespace `kube-system`) измените режим:

```yaml
kind: KubeProxyConfiguration
mode: "ipvs"
ipvs:
  strictARP: true  # Обязательно для MetalLB
  scheduler: "rr"  # Выбор алгоритма
```

### 2. Использование с MetalLB (strictARP)

Параметр `strictARP: true` критически важен при использовании MetalLB в режиме Layer 2. Он заставляет узлы отвечать на ARP-запросы только для тех IP, которые настроены на их собственных интерфейсах, предотвращая «ARP-шторм» и конфликты виртуальных IP.

### 3. Особенности externalTrafficPolicy: Local

В режиме IPVS настройка `externalTrafficPolicy: Local` работает эффективнее, чем в `iptables`:
- Трафик направляется только на локальные поды узла.
- Если на узле нет подов данного сервиса, пакеты будут отброшены (что ожидаемо).
- Это сохраняет **Source IP** клиента без дополнительной инкапсуляции.

## Дополнительные сведения

### Диагностика и отладка

Для мониторинга IPVS используйте утилиту `ipvsadm` (требуется установка в ОС).

```bash
# Просмотр всех виртуальных сервисов и их бэкендов
sudo ipvsadm -Ln

# Просмотр активных соединений (траблшутинг сессий)
sudo ipvsadm -Lnc

# Статистика пакетов и байтов в реальном времени
sudo watch ipvsadm -Ln --stats
```

### Важные нюансы

1. **Интерфейс kube-ipvs0:** Если вы видите странные IP-адреса на интерфейсе `kube-ipvs0` через `ip addr`, не удаляйте их — это ClusterIP ваших сервисов.
2. **Conntrack:** Даже в режиме IPVS, системный `nf_conntrack` продолжает использоваться для отслеживания состояний соединений. При высоких нагрузках может потребоваться тюнинг `net.netfilter.nf_conntrack_max`.
