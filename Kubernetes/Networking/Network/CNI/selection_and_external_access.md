# Выбор CNI и внешние типы доступа в Kubernetes

## Определения

**IP Advertisement** — функция CNI-плагина Calico, позволяющая анонсировать IP-адреса сервисов (ClusterIP) внешним сетевым маршрутизаторам по протоколу BGP. Это делает сервисы доступными напрямую из физической сети без использования NodePort.

**Direct Service Return (DSR)** — технология оптимизации сетевого трафика, при которой ответ от пода направляется напрямую клиенту, минуя промежуточный узел-балансировщик. Реализуется через eBPF (в Calico/Cilium) или IPVS.

**externalTrafficPolicy: Local** — настройка сервиса в Kubernetes, заставляющая `kube-proxy` обрабатывать трафик только на тех узлах, где запущены целевые поды. Это сохраняет исходный IP-адрес клиента (Source IP) и исключает лишние переходы между узлами (cross-node hopping). Подробнее см. [externalTrafficPolicy в NodePort](../../Service/service_type_nodeport.md#externaltrafficpolicy-local).

## Основные концепции

### Выбор CNI-плагина

Выбор CNI определяет не только связность подов, но и возможности безопасности, масштабируемости и интеграции с внешним миром.

| Критерий | Flannel | Calico | Calico (eBPF) / Cilium |
| :--- | :--- | :--- | :--- |
| **Сложность** | Простая | Средняя | Средняя/Высокая |
| **NetworkPolicy** | Нет | Да | Да (на базе eBPF — эффективнее) |
| **Производительность** | Средняя (Overlay) | Высокая (BGP/Direct) | Очень высокая |
| **Замена kube-proxy** | Нет | Нет | Да (через eBPF) |
| **Режим работы** | Overlay (VXLAN) | Overlay/BGP/Direct | eBPF/Direct Routing |

### Внешние типы доступа в Kubernetes

Для доступа к сервисам извне кластера используются следующие механизмы:

| Метод | Уровень OSI | Описание | Применение |
| :--- | :--- | :--- | :--- |
| **NodePort** | L4 (TCP/UDP) | Открывает порт на каждом узле кластера | Тестирование, простые on-premise |
| **LoadBalancer** | L4 (TCP/UDP) | Использует внешний балансировщик (облако или MetalLB) | Production в облаке / bare-metal |
| **Ingress** | L7 (HTTP/S) | Маршрутизация на основе доменов и путей | Web-приложения, микросервисы |
| **IP Advertisement** | L3 (IP) | Анонсирование ClusterIP через BGP | Bare-metal, дата-центры |

## Практические сценарии

### IP Advertisement через BGP (Calico-specific)

В стандартном режиме `ClusterIP` (`10.2.0.0/16`) невидим за пределами кластера. Трафик должен проходить через NAT (NodePort или LoadBalancer).

**Преимущества IP Advertisement:**
- **Прямая доступность:** Обращение к сервисам напрямую по их IP без NodePort.
- **Масштабируемость:** Балансировка на уровне сетевого оборудования (ECMP).
- **Отсутствие NAT:** Упрощает диагностику и повышает производительность.

**Механизм работы:**
1. Calico устанавливает BGP-сессию с внешним маршрутизатором (Top-of-Rack или Core Router).
2. Маршрутизатор получает информацию о том, что подсеть `ClusterIP` доступна через узлы кластера.
3. Внешние пакеты направляются напрямую на узлы, где запущены поды сервиса.

### Оптимизация: externalTrafficPolicy: Local + IP Advertisement

Комбинация этих функций обеспечивает максимально эффективный путь трафика:

1. **Анонс только живых узлов:** Calico анонсирует сервисный IP только с тех узлов, где запущен хотя бы один под этого сервиса.
2. **Нулевой cross-node трафик:** Пакет приходит из физической сети на узел и сразу попадает в локальный под.
3. **Сохранение Source IP:** Клиентский IP сохраняется без использования прокси-протоколов.

### Direct Service Return (DSR) через eBPF

В классическом режиме трафик часто проходит через два узла:
`Клиент → Узел 1 (Балансировщик) → Узел 2 (Под) → Узел 1 (NAT) → Клиент`.

**Решение eBPF DSR:**
1. Пакет приходит на Узел 1.
2. eBPF-программа перенаправляет его на Узел 2, сохраняя информацию о VIP.
3. Под на Узле 2 формирует ответ и отправляет его **напрямую клиенту**, подменяя Source IP на IP сервиса (VIP).

**Результат:** Снижение задержек (Latency) и уменьшение нагрузки на сетевой стек промежуточных узлов.

## Дополнительная информация

### Архитектура Load Balancer + Ingress Controller

В production-средах внешние балансировщики (L4/L7) часто работают в связке с Ingress-контроллерами. Роль CNI в этих сценариях — обеспечить эффективную маршрутизацию между ingress-нодами и backend-нодами, а также реализовать политики безопасности.

Подробное описание архитектурных паттернов (AWS ALB, NLB, MetalLB + Ingress) см. в разделе **[Обзор Ingress: Архитектурные паттерны](../../Ingress/overview.md#архитектурные-паттерны--связка-lb-ingress-и-alb)**.
