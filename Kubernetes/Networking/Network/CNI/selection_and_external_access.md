## Внешние типы доступа в Kubernetes и роль Calico

### IP Advertisement через BGP (Calico-specific)

Calico предоставляет расширенную возможность **анонсирования сервисных IP-адресов** через BGP внешним маршрутизаторам.

**Стандартное поведение (без IP Advertisement):**

- ClusterIP (`10.2.0.0/16`) невидим для внешней сети
- Обращение к ClusterIP извне невозможно даже при наличии маршрута
- Пакеты будут отброшены, так как Ethernet-интерфейс не знает о внутренней сетке

**С IP Advertisement:**

- Calico анонсирует ClusterIP сервисов через BGP внешнему роутеру
- Внешний роутер направляет трафик напрямую на нужную ноду
- Трафик попадает на сервис без NodePort

**Преимущества:**

- Прямая маршрутизация к сервисам без NAT
- Возможность балансировки на уровне BGP (ECMP)
- Более эффективная доставка трафика

#### externalTrafficPolicy: Local + IP Advertisement

Комбинация этих функций даёт максимальную эффективность:

- Calico анонсирует сервис **только с тех нод, где есть соответствующие поды**
- BGP-роутер распределяет трафик (ECMP) только между активными нодами
- При падении пода/ноды анонс снимается, трафик перенаправляется
- **Отсутствие cross-node трафика:** пакет приходит на ноду и сразу на локальный под
- **Direct Service Return (DSR):** ответ от пода идёт напрямую клиенту через eBPF

**Риск неравномерной балансировки сохраняется:** При неравномерном распределении подов по нодам трафик распределяется между нодами, а не между подами.

### Direct Service Return (DSR) через eBPF

Calico в режиме eBPF реализует оптимизацию **Direct Service Return**.

**Проблема классического режима:**

1. Трафик приходит на ноду 1, перенаправляется на под на ноде 2
2. Ответ от пода идёт обратно через ноду 2 с NAT
3. Два хопа, дополнительная задержка

**Решение eBPF DSR:**

1. Трафик приходит на ноду 1, через eBPF перенаправляется на под на ноде 2
2. Под отвечает **напрямую клиенту**, подменяя source IP на ClusterIP сервиса через eBPF
3. Ответ идёт напрямую, минуя ноду-получатель

**Преимущества:**

- Снижение задержки (no extra hop)
- Уменьшение нагрузки на ноды
- Сохранение IP клиента без SNAT

**Требования:**

- Calico в режиме eBPF
- Поддержка eBPF ядром Linux (ядро 4.19+)

### Load Balancer + Ingress Controller

Для production-окружений рекомендуется архитектура с внешним балансировщиком:

```
Внешний трафик → Load Balancer → Ingress Controller → Service → Pods
```

**Преимущества перед NodePort:**

- **Интеллектуальная балансировка:** LB может учитывать нагрузку, живость нод
- **Гибкое распределение:** Можно направить больше трафика на более мощные ноды
- **Health checks:** LB проверяет доступность ingress-контроллеров
- **L7 маршрутизация:** Ingress распределяет трафик по доменам/путям

**Рекомендуемая архитектура:**

- Выделение отдельных нод под Ingress Controller (DMZ-зона)
- Ingress-ноды изолированы от рабочих нагрузок (backend pods)
- Внешний балансировщик распределяет трафик между ingress-нодами
- Ingress направляет трафик на сервисы, сервисы — на backend-поды

**Роль Calico:**

- Обеспечивает маршрутизацию между ingress-нодами и backend-нодами
- Реализует [NetworkPolicy](../NetworkPolicy/best_practices.md) для изоляции ingress от backend
- В режиме eBPF оптимизирует cross-node трафик
