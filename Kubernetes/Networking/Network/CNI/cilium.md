# Cilium: Высокопроизводительный CNI на базе eBPF

## Определения

**Cilium** — это современный плагин интерфейса сетевой связности контейнеров (CNI), спроектированный для обеспечения сетевой связности, безопасности и наблюдаемости между рабочими нагрузками. В отличие от традиционных CNI, Cilium использует технологию **eBPF** (Extended Berkeley Packet Filter) в ядре Linux для обработки пакетов.

**kube-proxy-replacement** — режим работы Cilium, при котором он полностью заменяет стандартный компонент `kube-proxy`, реализуя балансировку нагрузки сервисов (ClusterIP, NodePort, LoadBalancer) через eBPF-программы.

## Основные концепции

### Архитектура Cilium

Cilium состоит из нескольких ключевых компонентов:

- **Cilium Agent (DaemonSet):** Работает на каждой ноде кластера.
    - Взаимодействует с Kubernetes API (отслеживание подов, сервисов, политик).
    - Управляет сетевыми интерфейсами подов.
    - На лету формирует и загружает eBPF-программы в ядро Linux.
    - Выполняет функции IPAM и балансировки сервисов (замена kube-proxy).
- **Cilium Operator (Deployment):** Отвечает за общекластерные задачи. Обычно запускается в 2 экземплярах.
    - Управление пулом IP-адресов.
    - Сборка мусора (удаление устаревших `CiliumIdentity` и `CiliumEndpoints`).
    - Синхронизация ресурсов между нодами.
- **Cilium Envoy:** Прокси-сервер для обработки трафика L3-L7. Используется для реализации сетевых политик и Service Mesh функционала.

### Custom Resource Definitions (CRD)

Cilium расширяет Kubernetes API через собственные ресурсы:

- **CiliumEndpoint:** Сопоставление пода, его IP-адреса и Security Identity.
- **CiliumIdentity:** Список идентификаторов безопасности, вычисляемых на основе меток (Labels).
- **CiliumNode:** Информация о ноде с точки зрения Cilium (IPAM, маршрутизация).
- **CiliumNetworkPolicy:** Расширенные сетевые политики с поддержкой L7 (например, фильтрация по HTTP путям).

### Безопасность на основе Identity (Security Identity)

Традиционные сетевые политики полагаются на IP-адреса, что неэффективно в динамической среде Kubernetes.
- **Identity:** Cilium назначает каждому поду числовой идентификатор на основе его меток (**Labels**).
- **Стабильность:** Даже если под пересоздан с новым IP, его `Security Identity` остается прежним (если метки не изменились).
- **Производительность:** eBPF-программы проверяют идентификатор, а не IP, что значительно ускоряет фильтрацию и снижает нагрузку на CPU.

### Глубокая наблюдаемость (Hubble)

**Hubble** — это система наблюдения, интегрированная в Cilium.

**Компоненты Hubble:**
- **Hubble Server:** Встроен в Cilium Agent на каждой ноде. Получает данные напрямую из eBPF.
- **Hubble Relay:** Агрегатор данных со всех нод кластера.
- **Hubble UI:** Графический интерфейс для визуализации трафика и зависимостей.
- **Hubble CLI:** Утилита командной строки для запросов в реальном времени.

**Возможности:**
- Наблюдение за трафиком в реальном времени (`hubble observe`).
- Визуализация графа зависимостей между сервисами.
- Диагностика сетевых политик (поиск причин `dropped` пакетов).
- Фильтрация потоков по неймспейсам, подам и протоколам.

### Сравнение механизмов балансировки

| Механизм | Метод работы | Масштабируемость | Накладные расходы |
|----------|--------------|------------------|-------------------|
| **IP tables** | Линейный перебор правил | Низкая (O(n)) | Высокие (NAT/DNAT, Conntrack) |
| **IPVS** | Хэш-таблицы | Средняя | Средние (NAT/DNAT, Conntrack) |
| **eBPF (Cilium)** | Прямая передача (direct path) | Высокая (O(1)) | Минимальные (без NAT в ядре) |

## Преимущества и недостатки

### Преимущества

- **Высокая производительность:** Замена `iptables` на eBPF устраняет линейную деградацию производительности при росте количества сервисов.
- **Масштабируемость:** Производительность остается стабильной как при 5, так и при 50 000 сервисов.
- **Глубокая наблюдаемость:** Полная видимость сетевых потоков через Hubble.
- **Динамичность:** Возможность обновлять логику обработки трафика без пересборки ядра или перезагрузки узлов.

### Недостатки и ограничения

- **Сложность отладки:** Требует глубоких знаний ядра Linux и умения работать со специфичными инструментами.
- **Порог вхождения:** Для понимания внутренних процессов желательно знание языка C.
- **Потребление памяти:** BPF Maps хранятся в невытесняемой оперативной памяти ядра. Чем больше сервисов и соединений, тем выше потребление RAM.
- **Дефицит кадров:** Специалистов, способных глубоко отлаживать eBPF на уровне ядра, на рынке значительно меньше, чем администраторов классического сетевого стека.

## Практические сценарии

### Подготовка узлов (Prerequisites)

Перед установкой Cilium необходимо настроить узлы (например, на базе Rocky Linux/Ubuntu):

1. **Отключение Swap и Firewall:**

   ```bash
   sudo swapoff -a
   sudo systemctl stop firewalld && sudo systemctl disable firewalld
   ```

2. **Загрузка модулей ядра:**

   ```bash
   cat <<EOF | sudo tee /etc/modules-load.d/cilium.conf
   overlay
   br_netfilter
   EOF
   sudo modprobe overlay
   sudo modprobe br_netfilter
   ```

3. **Настройка параметров ядра:**

   ```bash
   cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
   net.bridge.bridge-nf-call-iptables  = 1
   net.bridge.bridge-nf-call-ip6tables = 1
   net.ipv4.ip_forward                 = 1
   EOF
   sudo sysctl --system
   ```

4. **Настройка Containerd:**
   Убедитесь, что в `/etc/containerd/config.toml` параметр `SystemdCgroup` установлен в `true`:

   ```toml
   [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
     SystemdCgroup = true
   ```

### Установка кластера без kube-proxy

При использовании `kubeadm` рекомендуется исключить `kube-proxy` на этапе инициализации:

```bash
# Пример команды инициализации
sudo kubeadm init --config=kubeadm-config.yaml --skip-phases=addon/kube-proxy
```

В `kubeadm-config.yaml` в секции `ClusterConfiguration` желательно сразу указать внешний адрес API-сервера (`controlPlaneEndpoint`), который Cilium будет использовать для подключения.

### Установка Cilium через Helm

После инициализации кластера (когда ноды находятся в состоянии `NotReady`), установите Cilium:

```bash
helm install cilium cilium/cilium \
  --namespace kube-system \
  --set kubeProxyReplacement=strict \
  --set k8sServiceHost=<API_SERVER_IP> \
  --set k8sServicePort=6443 \
  --set operator.replicas=2
```

- `kubeProxyReplacement=strict`: Включает полную замену `kube-proxy`.
- `k8sServiceHost`: IP-адрес API-сервера (или балансировщика перед мастерами).

### Интеграция с Node Local DNS

Для оптимальной работы DNS рекомендуется использовать `node-local-dns`. В конфигурации `kubelet` необходимо указать адрес локального DNS-сервера (например, `169.254.25.10`), чтобы трафик DNS не покидал узел.

## Дополнительная информация

### Проверка статуса

Для глубокой проверки состояния Cilium используются следующие команды:

```bash
# Базовый статус всех компонентов (Agent, Operator, Envoy, Hubble)
cilium status

# Детальный статус конкретного агента (внутри пода)
kubectl -n kube-system exec ds/cilium -- cilium status --verbose

# Просмотр выделенных IP-адресов на ноде (IPAM)
kubectl get ciliumnodes -o yaml

# Список всех endpoint и их Security Identity
kubectl get ciliumendpoints -A
```

На что обратить внимание в `cilium status --verbose`:
- `KubeProxyReplacement: True` — подтверждает полную замену kube-proxy.
- `IPAM: IPv4: 2/254 allocated` — количество используемых IP из выделенной ноде подсети.
- `Routing: VXLan` (или `Native`) — режим маршрутизации трафика между нодами.

### Наблюдение за трафиком (Практика)

Для тестирования Hubble можно использовать стандартные инструменты:

1. **Запуск тестовых подов:**
   ```bash
   kubectl create deployment nginx --image=nginx
   kubectl expose deployment nginx --port=80
   kubectl run net-tools --image=infoblox/dnstools -- sleep infinity
   ```

2. **Генерация трафика:**
   ```bash
   kubectl exec net-tools -- curl nginx
   ```

3. **Просмотр логов трафика через Hubble CLI:**
   ```bash
   # Наблюдение за трафиком в реальном времени в namespace default
   hubble observe --namespace default --follow

   # Просмотр только отброшенных пакетов
   hubble observe --type drop
   ```

### Итоги и выбор решения

Cilium является мощным инструментом, но его выбор должен быть обоснован:

- **Когда выбирать Cilium:**
    - Требуется экстремальная производительность при большом количестве сервисов (1000+).
    - Необходима глубокая наблюдаемость и аудит трафика (L7).
    - Нужны расширенные сетевые политики (FQDN-фильтрация, HTTP-пути).
- **Когда стоит подумать:**
    - **Сложность отладки:** В случае аварии стандартные `tcpdump` и `iptables -L` могут не показать полной картины, так как трафик обрабатывается в eBPF до попадания в стандартные цепочки.
    - **Стоимость владения:** Требуется высокая квалификация администраторов для глубокой настройки и траблшутинга.
    - **Альтернативы:** Для простых кластеров Calico (в режиме IPVS) может быть проще в эксплуатации при схожей производительности.
