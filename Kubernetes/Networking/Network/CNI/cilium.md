# Cilium: Высокопроизводительный CNI на базе eBPF

## Определения

**Cilium** — это современный плагин интерфейса сетевой связности контейнеров (CNI), спроектированный для обеспечения сетевой связности, безопасности и наблюдаемости между рабочими нагрузками. В отличие от традиционных CNI, Cilium использует технологию **eBPF** (Extended Berkeley Packet Filter) в ядре Linux для обработки пакетов.

**kube-proxy-replacement** — режим работы Cilium, при котором он полностью заменяет стандартный компонент `kube-proxy`, реализуя балансировку нагрузки сервисов (ClusterIP, NodePort, LoadBalancer) через eBPF-программы.

## Основные концепции

### Архитектура Cilium

Cilium состоит из нескольких ключевых компонентов:

- **Cilium Agent (DaemonSet):** Работает на каждом узле кластера. Управляет eBPF-программами, обрабатывает события от API-сервера и настраивает сетевые интерфейсы.
- **Cilium Operator (Deployment):** Отвечает за общекластерные задачи, такие как управление IP-адресами (IPAM) и сборку объектов Cilium. Обычно запускается в 2 экземплярах для отказоустойчивости.
- **Envoy:** Интегрированный прокси-сервер, используемый для обработки трафика на уровне L7 (HTTP, gRPC, сетевые политики уровня приложения).

### Безопасность на основе Identity (Security Identity)

Традиционные сетевые политики полагаются на IP-адреса, что неэффективно в динамической среде Kubernetes, где поды часто перезапускаются с новыми IP.
- **Identity:** Cilium назначает каждому поду числовой идентификатор на основе его меток (**Labels**).
- **Стабильность:** При перезапуске пода, если его метки не изменились, его `Security Identity` остается прежним.
- **Эффективность:** eBPF-программы проверяют идентификатор в заголовке пакета, что избавляет от необходимости постоянно обновлять тысячи правил IP tables при каждом изменении IP-адресов.

### Глубокая наблюдаемость (Hubble)

**Hubble** (назван в честь телескопа) — это распределенная система наблюдения, построенная поверх Cilium и eBPF.
- **Визуализация:** Предоставляет графический интерфейс (Hubble UI) для отображения сетевых связей между сервисами.
- **Аналитика:** Позволяет отслеживать не только факт прохождения пакета (L3/L4), но и детали протоколов прикладного уровня (L7), такие как HTTP-пути, заголовки, gRPC-методы и SQL-запросы.
- **Отладка:** Помогает быстро находить причины отброшенных пакетов (drops) и анализировать задержки в сети.

### Сравнение механизмов балансировки

| Механизм | Метод работы | Масштабируемость | Накладные расходы |
|----------|--------------|------------------|-------------------|
| **IP tables** | Линейный перебор правил | Низкая (O(n)) | Высокие (NAT/DNAT, Conntrack) |
| **IPVS** | Хэш-таблицы | Средняя | Средние (NAT/DNAT, Conntrack) |
| **eBPF (Cilium)** | Прямая передача (direct path) | Высокая (O(1)) | Минимальные (без NAT в ядре) |

## Преимущества и недостатки

### Преимущества

- **Высокая производительность:** Замена `iptables` на eBPF устраняет линейную деградацию производительности при росте количества сервисов.
- **Масштабируемость:** Производительность остается стабильной как при 5, так и при 50 000 сервисов.
- **Глубокая наблюдаемость:** Полная видимость сетевых потоков через Hubble.
- **Динамичность:** Возможность обновлять логику обработки трафика без пересборки ядра или перезагрузки узлов.

### Недостатки и ограничения

- **Сложность отладки:** Требует глубоких знаний ядра Linux и умения работать со специфичными инструментами.
- **Порог вхождения:** Для понимания внутренних процессов желательно знание языка C.
- **Потребление памяти:** BPF Maps хранятся в невытесняемой оперативной памяти ядра. Чем больше сервисов и соединений, тем выше потребление RAM.
- **Дефицит кадров:** Специалистов, способных глубоко отлаживать eBPF на уровне ядра, на рынке значительно меньше, чем администраторов классического сетевого стека.

## Практические сценарии

### Подготовка узлов (Prerequisites)

Перед установкой Cilium необходимо настроить узлы (например, на базе Rocky Linux/Ubuntu):

1. **Отключение Swap и Firewall:**

   ```bash
   sudo swapoff -a
   sudo systemctl stop firewalld && sudo systemctl disable firewalld
   ```

2. **Загрузка модулей ядра:**

   ```bash
   cat <<EOF | sudo tee /etc/modules-load.d/cilium.conf
   overlay
   br_netfilter
   EOF
   sudo modprobe overlay
   sudo modprobe br_netfilter
   ```

3. **Настройка параметров ядра:**

   ```bash
   cat <<EOF | sudo tee /etc/sysctl.d/k8s.conf
   net.bridge.bridge-nf-call-iptables  = 1
   net.bridge.bridge-nf-call-ip6tables = 1
   net.ipv4.ip_forward                 = 1
   EOF
   sudo sysctl --system
   ```

4. **Настройка Containerd:**
   Убедитесь, что в `/etc/containerd/config.toml` параметр `SystemdCgroup` установлен в `true`:

   ```toml
   [plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
     SystemdCgroup = true
   ```

### Установка кластера без kube-proxy

При использовании `kubeadm` рекомендуется исключить `kube-proxy` на этапе инициализации:

```bash
# Пример команды инициализации
sudo kubeadm init --config=kubeadm-config.yaml --skip-phases=addon/kube-proxy
```

В `kubeadm-config.yaml` в секции `ClusterConfiguration` желательно сразу указать внешний адрес API-сервера (`controlPlaneEndpoint`), который Cilium будет использовать для подключения.

### Установка Cilium через Helm

После инициализации кластера (когда ноды находятся в состоянии `NotReady`), установите Cilium:

```bash
helm install cilium cilium/cilium \
  --namespace kube-system \
  --set kubeProxyReplacement=strict \
  --set k8sServiceHost=<API_SERVER_IP> \
  --set k8sServicePort=6443 \
  --set operator.replicas=2
```

- `kubeProxyReplacement=strict`: Включает полную замену `kube-proxy`.
- `k8sServiceHost`: IP-адрес API-сервера (или балансировщика перед мастерами).

### Интеграция с Node Local DNS

Для оптимальной работы DNS рекомендуется использовать `node-local-dns`. В конфигурации `kubelet` необходимо указать адрес локального DNS-сервера (например, `169.254.25.10`), чтобы трафик DNS не покидал узел.

## Дополнительная информация

### Проверка статуса

```bash
# Проверка через CLI Cilium (требуется установка cilium-cli)
cilium status --wait

# Проверка подов в кластере
kubectl get pods -n kube-system -l k8s-app=cilium

# Проверка режима замены kube-proxy
kubectl -n kube-system exec ds/cilium -- cilium status | grep KubeProxyReplacement
```
