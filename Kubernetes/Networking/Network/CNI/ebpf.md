# eBPF в Kubernetes: Оптимизация сети, безопасности и наблюдаемости

## Определения

**eBPF (Extended Berkeley Packet Filter) в Kubernetes** — применение технологии eBPF для реализации высокопроизводительной сетевой связности, балансировки нагрузки, сетевых политик и глубокого мониторинга кластера на уровне ядра Linux.

**kube-proxy-replacement** — режим работы CNI-плагинов (Cilium, Calico), при котором стандартный компонент `kube-proxy` (на базе `iptables` или `IPVS`) полностью заменяется eBPF-программами для обработки трафика сервисов.

**Sidecar-less Service Mesh** — архитектура сервисной сетки, использующая eBPF для перехвата и обработки трафика на уровне узла или сокета, что исключает необходимость запуска прокси-контейнеров (sidecars) в каждом поде.

## Основные концепции

Подробное описание общей технологии eBPF (карты, верификатор, JIT) см. в [**eBPF в Linux**](../../../../Linux/Core/kernel/ebpf.md).

### Точки подключения (Hooks) в Kubernetes

Для работы в кластере eBPF использует специфичные точки входа:
- **XDP (eXpress Data Path):** Работает на уровне драйвера сетевой карты. Используется для сверхбыстрого сброса пакетов (DDoS защита) и балансировки входящего трафика.
- **TC (Traffic Control):** Основная точка для реализации NetworkPolicy и маршрутизации между подами.
- **Cgroup Hooks (connect/sendmsg):** Позволяют перехватывать сетевые вызовы на уровне сокета. Это дает возможность выполнять балансировку (DNAT) прямо в момент создания соединения, минуя сетевой стек узла.

### Ключевые механизмы оптимизации

1. **Socket Redirection (Перенаправление сокетов):** Если два пода на одном узле общаются друг с другом, eBPF перенаправляет пакеты напрямую из очереди одного сокета в другой, полностью минуя стек TCP/IP и виртуальные интерфейсы (veth-пары).
2. **Host Routing (Магистральная маршрутизация):** Трафик от пода к поду или во внешнюю сеть направляется по кратчайшему пути в ядре, сокращая количество переключений контекста и обработку в `iptables`.
3. **Bypass Conntrack:** Использование eBPF-карт вместо системного `netfilter conntrack` значительно снижает нагрузку на CPU и предотвращает проблемы с переполнением таблицы соединений при высоких нагрузках.

### Сравнение механизмов балансировки

| Характеристика | iptables | IPVS | eBPF |
| :--- | :--- | :--- | :--- |
| **Сложность поиска** | O(n) — линейная | O(1) — хэш-таблица | O(1) — хэш-таблица |
| **Обновление правил** | Полная перезагрузка | Частичное обновление | Мгновенно через Maps |
| **Производительность** | Падает с ростом сервисов | Стабильная | Максимальная |
| **Контекст пакета** | Ограничен | L4 | Полный доступ к метаданным |

## Практические сценарии

### Реализация замены kube-proxy через Cilium

Cilium является эталонным решением для работы с eBPF. Он реализует функции `ClusterIP`, `NodePort` и `ExternalIPs` напрямую в ядре.

Подробности установки и настройки см. в [**Cilium: Высокопроизводительный CNI на базе eBPF**](./cilium.md).

Основные преимущества в этом сценарии:
- **Maglev Hash:** Умная балансировка нагрузки, устойчивая к изменениям состава бэкендов.
- **Direct Server Return (DSR):** Ответ от пода идет клиенту напрямую, минуя балансировщик.

### Включение eBPF в Calico

Calico поддерживает режим eBPF как альтернативу `iptables`. Это актуально для кластеров с большим количеством NetworkPolicy.

**Настройка FelixConfiguration:**
```yaml
apiVersion: projectcalico.org/v3
kind: FelixConfiguration
metadata:
  name: default
spec:
  bpfEnabled: true
  bpfKubeProxyIptablesCleanupEnabled: true
  # Рекомендуется для ядер 5.10+
  bpfConnectTimeLoadBalancingEnabled: TCP
```

### Sidecar-less Service Mesh

Использование eBPF позволяет реализовать функции Service Mesh (mTLS, L7-трассировка, ретраи) без внедрения Envoy в каждый под.
- **Cilium Service Mesh:** Интегрирует Envoy на уровне узла, обрабатывая трафик через eBPF.
- **Istio Ambient Mesh:** Использует eBPF (ztunnel) для обеспечения безопасности транспортного уровня (mTLS) без sidecar.

### Наблюдаемость и безопасность среды выполнения

eBPF позволяет получать данные о системе без внесения изменений в приложение.
- **Hubble (Cilium):** Визуализация сетевых потоков, диагностика сетевых политик и мониторинг золотых метрик (latency, error rate).
- **Tetragon:** Инструмент безопасности, который не только мониторит системные вызовы, но и может блокировать опасные действия (например, запись в важные файлы) на уровне ядра.

## Дополнительные сведения

### Системные требования и Freshness

Для полноценной работы eBPF в Kubernetes рекомендуется использовать современные дистрибутивы Linux (Ubuntu 22.04+, RHEL 9+, Flatcar).

| Уровень поддержки | Версия ядра | Ключевые функции |
| :--- | :--- | :--- |
| **Базовый** | 4.19+ | XDP, TC, базовые карты |
| **Рекомендуемый** | 5.10+ | BTF (CO-RE), Ring Buffer, Socket Progs |
| **Оптимальный** | 5.15+ | Улучшенная производительность BPF Maps, новые хуки |

### Ограничения и риски

1. **Сложность диагностики:** Традиционные инструменты (tcpdump) могут не видеть трафик, обработанный внутри eBPF до попадания в стек. Требуется использование `bpftool`, `cilium-dbg` или `pwru`.
2. **Использование памяти:** BPF-карты занимают невытесняемую память ядра. При десятках тысяч сервисов это требует мониторинга ресурсов узла.
3. **Безопасность:** Загрузка eBPF-программ требует привилегий `CAP_BPF` или `CAP_SYS_ADMIN`, что требует осторожности при настройке прав доступа.
