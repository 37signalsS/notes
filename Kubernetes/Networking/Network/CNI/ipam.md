# IPAM (IP Address Management) в Kubernetes

## Определения

**IPAM (IP Address Management)** — функциональный блок CNI-плагина, отвечающий за полный жизненный цикл IP-адресов подов: выделение из пула, учёт привязки к интерфейсам и освобождение после удаления пода.

**podCIDR** — глобальный диапазон IP-адресов кластера (Pod Network), из которого выделяются адреса для всех подов.

**nodeCIDR** — поддиапазон (блок), закрепленный за конкретным узлом. Все поды на этом узле получают адреса из этого блока.

**Prefix Delegation (Делегирование префиксов)** — технология (преимущественно в AWS), позволяющая выделять узлу не отдельные IP, а целые подсети (/28), что значительно увеличивает лимит подов на одну сетевую карту (ENI).

**IP Pool** — логическая группировка диапазонов IP-адресов с определенными свойствами (например, пул для разных зон доступности или типов узлов).

---

## Основные концепции

### Иерархия распределения адресов

1. **Уровень кластера:** Определяется общий `clusterCIDR` (например, `10.244.0.0/16`).
2. **Уровень узла:** Каждой ноде выделяется `nodeCIDR` (например, `/24` — 254 адреса).
3. **Уровень пода:** CNI-агент на узле назначает конкретный IP из `nodeCIDR` интерфейсу пода.

### Режимы работы IPAM

#### 1. Host-local (Файловый)
Стандартный механизм, при котором `kube-controller-manager` назначает `podCIDR` узлу, а локальный CNI-плагин хранит состояние занятых адресов в файлах на диске узла.
- **Путь хранения:** `/var/lib/cni/networks/`
- **Особенности:** Простота, но отсутствие гибкости (сложно изменить размер подсети узла без пересоздания).

#### 2. Integrated (Интегрированный в CNI)
Плагины типа Calico или Cilium используют собственные базы данных (etcd или K8s CRD) для управления адресами, что позволяет динамически выделять блоки адресов узлам.

#### 3. Cloud-native (Облачный)
Использует API облачного провайдера (VPC) для назначения подам «настоящих» IP-адресов из подсетей облачной сети.
- **Примеры:** AWS ENI, Azure VNET, GKE Alias IP.
- **Преимущество:** Поды напрямую маршрутизируемы в VPC без Overlay (VXLAN/IPIP).

## Режимы IPAM в Cilium

Cilium предоставляет наиболее широкий выбор режимов управления адресами:

| Режим | Источник IP | Описание | Применение |
| :--- | :--- | :--- | :--- |
| **`cluster-pool`** | Cilium Operator | Оператор нарезает общую сеть кластера на куски для узлов | On-prem, универсальный режим |
| **`kubernetes`** | Node `spec.podCIDR` | Использует префиксы, назначенные стандартным контроллером K8s | Совместимость со стандартным K8s |
| **`aws-eni`** | AWS VPC Subnet | Назначает вторичные IP интерфейсам AWS ENI | AWS EKS / EC2 |
| **`azure`** | Azure VNET | Интеграция с Azure Virtual Network | Azure AKS |
| **`alibabacloud-eni`** | Alibaba VPC | Аналог ENI для Alibaba Cloud | Alibaba Cloud |

## Практические сценарии

### 1. Решение проблемы исчерпания IP-адресов

В облаках количество IP часто ограничено типом инстанса (количество ENI * количество IP на ENI).

**Решение в AWS (Cilium/AWS CNI):**
Включение **Prefix Delegation** позволяет назначать префиксы `/28` вместо одиночных IP, увеличивая плотность подов до 110+ на узел.

```bash
# Включение в Cilium
helm install cilium cilium/cilium \
  --set awsRuntimeDeviceDetection.enabled=true \
  --set eni.awsEnablePrefixDelegation=true
```

### 2. Изоляция трафика через разные пулы (Calico)

Можно создать разные `IPPool` для разных типов нагрузок (например, `frontend` и `backend`) и назначать их через `nodeSelector`.

```yaml
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: zone-a-pool
spec:
  cidr: 192.168.1.0/24
  nodeSelector: zone == "a"
```

### 3. Настройка Dual-Stack (IPv4/IPv6)

Для работы Dual-Stack необходимо:
1. Указать оба CIDR при инициализации кластера (`--pod-network-cidr=10.244.0.0/16,fd00:10:244::/48`).
2. Настроить CNI на использование обоих семейств. В Calico создаются два ресурса `IPPool`.

### 4. Мульти-сетевые конфигурации (Multus CNI)

Если поду требуется несколько сетевых интерфейсов с разными IPAM (например, один для управления, другой для данных), используется **Multus CNI**, который выступает мета-плагином и вызывает несколько CNI-конфигураций для одного пода.

## Диагностика и мониторинг

### Проверка в Calico
```bash
# Общая статистика по всем пулам
calicoctl ipam show --show-blocks

# Проверка конкретной ноды
calicoctl get node <node-name> -o yaml | grep podCIDR
```

### Проверка в Cilium
```bash
# Статус IPAM на узле (внутри пода cilium)
cilium status --verbose | grep IPAM

# Список выделенных IP на конкретном узле
kubectl get ciliumnode <node-name> -o jsonpath='{.spec.ipam}'
```

### Проверка Host-local
```bash
# На узле кластера
ls /var/lib/cni/networks/cni0/
# → 10.244.1.2, 10.244.1.3 ... (файлы-метки занятых адресов)
```

## Дополнительные сведения

### Проблемы перекрытия (Subnet Overlap)
При проектировании кластера критически важно, чтобы `podCIDR` не пересекался с:
- Сетью узлов (Node Network).
- Сетью сервисов (Service CIDR).
- Сетью офиса/VPN, из которой планируется доступ к подам.
