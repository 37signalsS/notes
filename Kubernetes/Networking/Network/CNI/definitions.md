# CNI и kube-proxy: Определения и Разделение Ролей

## Определения

**CNI (Container Network Interface)** — это интерфейс, который позволяет настраивать сетевые взаимодействия как между контейнерами (внутри пода), так и между подами и узлами кластера. Он стандартизирует способ, которым различные сетевые плагины (например, Calico, Flannel, Weave Net) конфигурируют сетевые интерфейсы контейнеров и управляют маршрутизацией трафика.

**kube-proxy** — сетевой прокси и балансировщик нагрузки, работающий на каждом узле кластера Kubernetes. Отвечает за реализацию сервисов (`Service`) и обеспечивает перенаправление трафика на поды путём управления правилами в ядре Linux (`iptables`, `IPVS`) или работы в пользовательском пространстве.

## Основные концепции

### Роль kube-proxy в Kubernetes

**Основные задачи:**

- Обеспечивает работу сервисов типов `ClusterIP`, `NodePort`, `LoadBalancer`
- Преобразует виртуальный IP сервиса в IP-адреса целевых подов (DNAT)
- Выполняет балансировку нагрузки на уровне L4 (TCP/UDP/SCTP)
- Отслеживает изменения сервисов и эндпоинтов через Kubernetes API
- Обновляет правила маршрутизации атомарно, без прерывания существующих соединений

**Ключевые особенности:**

- Работает независимо от container runtime (`containerd`, `CRI-O`)
- Запускается на каждой ноде как `DaemonSet` (или системный сервис)
- Взаимодействует только с сетевым стеком ноды, не влияет на сами поды
- Использует `EndpointSlice` для эффективного отслеживания бэкендов сервисов

### Роль CNI в Kubernetes

Kubernetes не реализует сетевую модель самостоятельно. Вместо этого он делегирует эту задачу **CNI-плагинам**.

**Основные задачи CNI:**

- Выделение IP-адресов подам.
- Настройка сетевых интерфейсов для каждого пода.
- Обеспечение маршрутизации трафика между подами на одном узле и между узлами.
- Реализация сетевых политик (в продвинутых CNI-плагинах).

После того как `kubelet` инициировал запуск Pod'а, он вызывает CNI-плагин для настройки сетевых ресурсов. Этот процесс включает следующие шаги:

1. **Назначение IP-адреса Pod'у:** Каждому Pod'у в Kubernetes присваивается уникальный IP-адрес из диапазона, выделенного для кластера.

2. **Создание сетевого пространства имен (Network Namespace):** Для каждого Pod'а создаётся свой собственный, изолированный `network namespace`. Это гарантирует, что у Pod'а будет свой собственный сетевой стек (таблица маршрутизации, сетевые устройства, порты).

3. **Настройка виртуальных Ethernet-устройств (veth-pair):** Создаётся пара виртуальных Ethernet-интерфейсов (`veth-pair`). Один конец этой пары помещается в сетевое пространство имен Pod'а (и становится его интерфейсом, например, `eth0`), а другой остаётся в корневом пространстве имен узла.

4. **Подключение к мосту узла:** Конец `veth-пары`, находящийся в пространстве имен узла, подключается к сетевому мосту (например, `cni0`). Это позволяет Pod'ам на одном узле обмениваться трафиком через этот мост.

5. **Настройка маршрутизации для межсетевого взаимодействия:** Для связи Pod'ов, расположенных на разных узлах, CNI-плагин настраивает маршруты. Часто это реализуется через оверлейные сети (например, с использованием VXLAN) или через прямое управление маршрутами (BGP). Детальное описание этих подходов см. в [обзоре сетевой модели](../network_overview.md).

## Жизненный цикл пода (CNI)

CNI-плагин выполняет функции «контракта» и должен уметь делать две вещи: настроить сеть для нового пода и удалить её для удаленного.

### 1. Создание пода (ADD)

Когда Kubelet получает задание запустить под, он вызывает CNI-плагин:

1. **Создание veth-пары:** Один конец в Network Namespace пода, другой в Bridge узла.
2. **Назначение IP:** Выделение адреса из пула `podCIDR` узла.
3. **Настройка маршрутов:** Прописывание маршрутов внутри пода и на узле.
4. **Правила файрвола:** Настройка Network Policies (если поддерживается).
5. **Запуск контейнера:** Только после настройки сети контейнер начинает работу.

### 2. Удаление пода (DELETE)

При удалении пода Kubelet снова вызывает CNI:

1. **Удаление veth-пары.**
2. **Освобождение IP:** Возврат адреса в пул для повторного использования.
3. **Очистка:** Удаление маршрутов и правил файрвола.

## Сравнение популярных CNI-плагинов

Выбор CNI — одно из критических решений при создании кластера. **Смена CNI на «живом» кластере крайне болезненна**, так как требует пересоздания всех подов и несет риск потери связности.

| Плагин | Подход | Плюсы | Минусы | Когда выбирать |
| :--- | :--- | :--- | :--- | :--- |
| **Flannel** | Overlay (VXLAN) | Простота, работает везде, не требует BGP. | Накладные расходы (Overlay), **нет поддержки NetworkPolicy**. | Обучение, простые тестовые среды. |
| **Calico** | Маршрутизация (BGP) | Высокая производительность, **полная поддержка NetworkPolicy**. | Требует поддержки BGP в сети (или Overlay-fallback). | Production, где важна безопасность. |
| **Cilium** | eBPF | Максимальная скорость, гибкость, обработка в ядре, visibility. | Требует свежих ядер Linux, высокая сложность. | Высоконагруженный Production, eBPF-экспертиза. |

## Разделение ролей: CNI (Flannel, Calico) и `kube-proxy`

### CNI-плагин (Flannel, Calico): Сеть для подов (L2/L3)

- **Задача:** Реализация спецификации CNI для обеспечения **IP-связности между всеми подами** кластера (связь Pod-to-Pod).
- **Функции:**
    1. **Выделение IP-адресов:** Назначает каждому поду уникальный IP из диапазона `podCIDR`.
    2. **Создание интерфейсов:** Создает и настраивает сетевые интерфейсы для подов (обычно `veth-pair`).
    3. **Маршрутизация между узлами:** Обеспечивает доставку пакетов между подами на разных узлах. Для этого используются два основных подхода:
        - **Overlay-сети (L2 поверх L3):** Используется в **Flannel (режим VXLAN)** и **Calico (режим IPIP)**. Трафик подов инкапсулируется (заворачивается) в пакеты узлов с помощью технологий вроде VXLAN или IP-in-IP. Это простой и универсальный способ, работающий в любой сети, но вносящий дополнительные накладные расходы на инкапсуляцию.
        - **Прямая маршрутизация (L3):** Основной режим работы **Calico**. Не использует инкапсуляцию. Каждый узел кластера выступает в роли BGP-маршрутизатора, анонсируя маршруты до подов, запущенных на нем, другим узлам. Ядро Linux напрямую маршрутизирует пакеты до нужного узла. Это обеспечивает максимальную производительность, но требует, чтобы сетевая инфраструктура поддерживала протокол [BGP (Border Gateway Protocol)](../../../../Networking/Protocols/bgp.md), или чтобы все узлы находились в одном L2-сегменте.
    4. **Сетевые политики** (Calico, Cilium): Реализует правила `NetworkPolicy` для фильтрации трафика. Flannel по умолчанию не поддерживает `NetworkPolicy`.

### kube-proxy: Абстракция Service (L4)

- **Задача:** Реализация виртуальной абстракции `Service`. Обеспечение **обнаружения (discovery) и балансировки нагрузки** для групп подов (связь Service-to-Pod).
- **Функции:**
    1. **Наблюдение:** Отслеживает изменения объектов `Service` и `Endpoints` (списки IP-адресов живых подов) через API-сервер.
    2. **Программирование правил:** На каждом узле кластера создает и обновляет правила в ядре Linux, используя один из режимов.
    3. **Трансляция адресов:** Эти правила перехватывают трафик, адресованный виртуальному `ClusterIP` сервиса, и выполняют **DNAT** (Destination Network Address Translation) — подменяют IP-адрес назначения на реальный IP-адрес одного из обслуживающих подов.

#### Режимы работы kube-proxy

**`iptables` (режим по умолчанию)**

- **Принцип работы:** Для каждого `Service` `kube-proxy` создаёт цепочку правил в `iptables`. Эти правила перехватывают трафик, направленный на `ClusterIP` и порт сервиса, и случайным образом перенаправляют его на IP-адрес одного из бэкенд-подов. Пакеты перенаправляются напрямую на поды без дополнительных переходов.
- **Плюсы:** Надёжный и универсальный режим, работает в любой Linux-среде; подходит для большинства кластеров среднего размера.
- **Минусы:** Может быть медленным при очень большом количестве сервисов (тысячи), так как `iptables` обрабатывает правила последовательно `O(n)`; балансировка реализована через случайный выбор правила без учёта загрузки бэкендов.

**`ipvs` (рекомендуется для крупных кластеров)**

- **Принцип работы:** Использует встроенный балансировщик ядра Linux `IPVS` (IP Virtual Server). `kube-proxy` программирует правила в хэш-таблицу IPVS, что обеспечивает практически константное время поиска `O(1)` независимо от количества правил.
- **Плюсы:** Значительно более производительный при большом количестве сервисов (>1000); выдерживает десятки тысяч сервисов без деградации; поддерживает различные алгоритмы балансировки (Round Robin, Least Connection, Source Hashing); обеспечивает session affinity (persistence) на уровне ядра.
- **Минусы:** Требует загрузки модулей ядра `ip_vs` и зависимостей; необходим параметр `strictARP: true` в конфигурации для корректной работы с некоторыми CNI.

**`userspace` (устаревший)**

- **Принцип работы:** `kube-proxy` запускает прокси-процесс в пользовательском пространстве, который принимает трафик и перенаправляет его подам. Каждое соединение проходит через процесс `kube-proxy`.
- **Статус:** Не используется в современных кластерах из-за низкой производительности и высоких накладных расходов; применяется только в legacy-кластерах.

**`kernelspace` (Windows)**

- Аналог `iptables`/`ipvs` для Windows-узлов.

### Техническое взаимодействие

1. `kube-proxy` **не занимается** маршрутизацией пакетов между узлами. Его работа — это трансляция адресов на уровне соединений (L4).
2. Когда `kube-proxy` с помощью `iptables` или `IPVS` подменяет `ClusterIP` на реальный IP пода, он передает пакет дальше в сетевой стек ядра.
3. Дальнейшая доставка этого пакета до целевого пода (особенно если тот на другом узле) — это уже **задача CNI-плагина**. Ядро ОС, используя таблицы маршрутизации, настроенные CNI-плагином, направляет пакет либо в VXLAN-туннель, либо напрямую на другой узел (в случае BGP).

**Итог:** CNI создает IP-связность на уровнях L2/L3. `kube-proxy` использует эту готовую связность для предоставления абстракции `Service` и балансировки на уровне L4. В традиционной модели оба компонента обязательны и не заменяют друг друга.

## Практические сценарии

### Выбор режима kube-proxy

| Сценарий | Рекомендуемый режим | Обоснование |
|----------|---------------------|-------------|
| Кластер до 1000 сервисов | `iptables` | Режим по умолчанию, прост в настройке, достаточная производительность |
| Крупный кластер (>1000 сервисов) | `ipvs` | Константное время поиска правил, поддержка алгоритмов балансировки |
| Требуется session affinity | `ipvs` | Встроенная поддержка на уровне ядра |
| Legacy-кластер или ограничения ядра | `userspace` | Только если `iptables`/`ipvs` недоступны |

### Диагностика kube-proxy

```bash
# Проверка запущенных подов kube-proxy
kubectl get pods -n kube-system -l k8s-app=kube-proxy

# Проверка режима работы
kubectl -n kube-system get configmap kube-proxy -o yaml | grep mode

# Для IPVS: проверка загруженных модулей
lsmod | grep ip_vs

# Для IPVS: просмотр правил балансировки
ipvsadm -Ln
```

## Дополнительные сведения

### Замена kube-proxy через eBPF

Современные CNI-плагины (**Cilium**, **Calico** в режиме eBPF) могут полностью заменять `kube-proxy`, обрабатывая балансировку нагрузки на уровне ядра через eBPF-программы. Это устраняет накладные расходы `iptables`/`IPVS` и упрощает сетевой путь.

- *Подробнее: [Решения на базе eBPF](./ebpf.md)*

### Влияние на производительность

- **iptables:** Последовательная обработка правил приводит к задержкам при >1000 сервисов
- **IPVS:** Хэш-таблицы обеспечивают константное время поиска независимо от количества сервисов
- **eBPF:** Обработка на уровне ядра без переключения контекста userspace/kernelspace
