# Путь трафика в Kubernetes

## Определения

**Путь трафика (Traffic Path)** — последовательность сетевых компонентов и узлов, через которые проходит запрос от источника (внешнего клиента или другого пода) до целевого контейнера в кластере Kubernetes.

**Ingress Controller** — специализированное приложение (прокси-сервер), которое управляет входящим трафиком на 7 уровне OSI (HTTP/HTTPS) на основе правил, описанных в ресурсах `Ingress`.

**Gateway API** — современный стандарт управления трафиком в Kubernetes, разделяющий ответственность за конфигурацию сети между разными ролями и предоставляющий более гибкие возможности маршрутизации по сравнению с Ingress.

**Endpoints** — объект API Kubernetes, содержащий список IP-адресов подов, готовых принимать трафик для конкретного сервиса. Используется сетевыми компонентами для фактической доставки пакетов.

## Основные концепции

### Общая схема внешнего трафика (North-South)

Внешний запрос проходит путь от ввода URL в браузере до конкретного контейнера:

1. **DNS-резолвинг:**
   - Клиент (браузер) ищет IP-адрес для `example.com`.
   - Проверка локального кэша и файла `/etc/hosts`.
   - Рекурсивный запрос к DNS-серверам (провайдера, публичным, корневым).
2. **Маршрутизация и NAT:** Запрос идет через серию хопов (коммутаторы, маршрутизаторы), где может применяться NAT (подмена IP-адреса клиента) при выходе в интернет.
3. **TCP и TLS Handshake:**
   - Установка TCP-соединения (3-way handshake).
   - Установка TLS-соединения (обмен сертификатами, аутентификация сервера, согласование симметричных ключей).
4. **LoadBalancer:** Внешний балансировщик (облачный или bare-metal) принимает запрос и перенаправляет его на узлы кластера.
5. **NodePort и kube-proxy:**
   - Трафик попадает на `NodePort` узла.
   - **kube-proxy** (используя `iptables`, `IPVS` или `eBPF`) перехватывает трафик и перенаправляет его на `Ingress Controller`.
6. **Ingress Controller:** Выполняет L7-маршрутизацию (на основе Host и Path) и передает запрос на соответствующий `Service`.
7. **Service (ClusterIP):** Виртуальный IP сервиса служит точкой входа для группы подов.
8. **Pod:** Конечная точка назначения. Трафик распределяется между подами (обычно случайным образом через `iptables` правила) и попадает в контейнер.

```text
Клиент → DNS → Маршрутизация/NAT → LB → NodePort → kube-proxy (iptables/IPVS) → Ingress → ClusterIP → Pod
```

### Взаимодействие внутри пода

Контейнеры внутри одного пода разделяют общее сетевое пространство имен (`network namespace`). Они взаимодействуют друг с другом через интерфейс `loopback` (`localhost`). Это позволяет использовать паттерн Sidecar для обработки трафика (например, логирование, кэширование или проксирование).

### Путь трафика Pod-to-Pod (East-West)

Взаимодействие между подами осуществляется напрямую по их IP-адресам без использования NAT (согласно сетевой модели Kubernetes).

- **Внутри одного узла:** Трафик проходит через виртуальный мост (bridge) или напрямую через виртуальные интерфейсы (veth pairs) под управлением CNI.
- **Между узлами:** Пакеты маршрутизируются CNI-плагином. В зависимости от реализации может использоваться инкапсуляция (VXLAN, Geneve) или прямая маршрутизация (BGP).

*Подробное описание механики L2/L3 связности: [Обзор сетевой модели Kubernetes](./network_overview.md)*

### Трафик в Service Mesh

При использовании Service Mesh (например, Istio) путь трафика усложняется за счет внедрения Sidecar-прокси (Envoy) в каждый под:

1. **Ingress Gateway:** Трафик входит в Mesh-сеть через специализированный шлюз.
2. **mTLS и Политики:** Трафик шифруется (Mutual TLS) и проверяется на соответствие политикам доступа (AuthorizationPolicy).
3. **Envoy-to-Envoy:** Запрос от пода-клиента перехватывается его локальным Sidecar-прокси и направляется на Sidecar-прокси пода-сервера.
4. **Observability:** Каждый прокси генерирует метрики и данные трассировки (Trace ID), позволяя визуализировать полный путь запроса.

*Подробнее об управлении трафиком в Mesh: [Istio Traffic Management](../../../Service_Mesh/traffic_management.md)*

## Практические сценарии

### Диагностика пути трафика

Для выявления узких мест или ошибок в маршрутизации используются следующие инструменты:

```bash
# Проверка актуальности списка Endpoints для сервиса
kubectl get endpoints <service-name>

# Проверка правил маршрутизации Service (ClusterIP) на узле
iptables-save | grep <service-name>
# или (если используется IPVS)
ipvsadm -Ln | grep <service-cluster-ip>

# Трассировка сетевого пути из тестового пода
kubectl run tracer --rm -it --image=busybox -- traceroute <service-name>

# Анализ логов Ingress-контроллера для поиска ошибок L7 (4xx, 5xx)
kubectl logs -n ingress-nginx -l app.kubernetes.io/component=controller --tail=100
```

### Типичные проблемы и решения

| Симптом | Вероятная причина | Метод проверки |
| :--- | :--- | :--- |
| **502 Bad Gateway** | Приложение в поде не слушает порт или упало | `kubectl get pods`, проверка логов приложения |
| **503 Service Unavailable** | Нет готовых (Ready) подов в сервисе | `kubectl describe service`, проверка Readiness Probe |
| **Connection Timeout** | NetworkPolicy блокирует входящий трафик | `kubectl get networkpolicy -A` |
| **404 Not Found** | Ошибка в правилах Ingress (хост или путь) | `kubectl describe ingress <name>` |

### Рекомендации по архитектуре

Для обеспечения стабильности и безопасности пути трафика рекомендуется:

1. **Использовать Gateway API** для новых проектов как более современную альтернативу Ingress.
2. **Изолировать Ingress-ноды** (DMZ) для отделения внешнего трафика от внутренних рабочих нагрузок.
3. **Настраивать Health Checks** (Liveness/Readiness probes) для исключения "битых" подов из пути трафика.
4. **Минимизировать использование hostNetwork**, чтобы не привязывать путь трафика к сетевому стеку конкретного узла.

*Полный список архитектурных рекомендаций: [Сеть Kubernetes: Принципы и рекомендации](./network_overview.md#рекомендации-по-архитектуре)*
