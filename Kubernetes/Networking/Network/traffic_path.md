# Путь трафика в Kubernetes

---
**Надёжность:** 10 (SSoT + Проектный контекст 2026)
**Свежесть:** Актуально на июль 2026
---

## Определения

**Путь трафика (Traffic Path)** — последовательность сетевых компонентов и узлов, через которые проходит запрос от источника (внешнего клиента или другого пода) до целевого контейнера в кластере Kubernetes.

**North-South трафик** — трафик, входящий в кластер извне или выходящий из него во внешние сети.

**East-West трафик** — трафик между подами или сервисами внутри одного кластера.

**Gateway API** — современный стандарт управления трафиком в Kubernetes (пришёл на смену Ingress в 2026 году), разделяющий ответственность за конфигурацию сети и предоставляющий расширенные возможности маршрутизации на L4 и L7.

**ExternalTrafficPolicy** — настройка сервиса (`Cluster` или `Local`), определяющая, может ли трафик перенаправляться между узлами кластера после попадания на `NodePort`.

**Topology Aware Routing** — механизм оптимизации пути трафика, направляющий запросы на эндпоинты в той же зоне (Zone) или регионе (Region) для снижения задержек и затрат на межзонный трафик.

## Основные концепции

### Внешний трафик (North-South: Ingress)

В 2026 году основным способом управления входящим трафиком является **Gateway API**. Классический путь запроса:

1.  **DNS-резолвинг:** Клиент получает IP внешнего балансировщика (LB).
2.  **Облачный/Bare-metal LB:** Принимает запрос и перенаправляет его на `NodePort` или напрямую на IP пода (в случае интеграции CNI с облаком, например, AWS VPC CNI).
3.  **Обработка на узле (kube-proxy vs eBPF):**
    -   **kube-proxy (iptables/nftables/IPVS):** Трафик попадает в цепочки правил ядра Linux, которые выполняют DNAT на IP пода или IP Gateway.
    -   **eBPF (Cilium/Calico VPP):** Трафик перехватывается на уровне сетевого драйвера, минуя стек `iptables`, что снижает задержки и нагрузку на CPU.
4.  **Gateway / Ingress Controller:** Выполняет L7-маршрутизацию, терминацию TLS и передает запрос на `Service` или напрямую на `Endpoint`.
5.  **Влияние `externalTrafficPolicy`:**
    -   `Cluster`: Трафик может прийти на узел А и быть перенаправлен на узел Б (лишний хоп, Source IP подменяется на IP узла А).
    -   `Local`: Трафик обрабатывается только на том узле, куда он пришел. Если там нет нужного пода — пакет дропается (Source IP сохраняется).

### Взаимодействие внутри пода

Контейнеры внутри одного пода разделяют общее сетевое пространство имен (`network namespace`). Они взаимодействуют через `localhost`. Трафик не выходит за пределы пода и не проходит через правила маршрутизации узла.

### Внутренний трафик (East-West: Pod-to-Pod)

1.  **Headless Service:** Если приложению нужен прямой доступ к IP подов (например, для баз данных), DNS возвращает список всех IP подов. Путь: `Pod A → DNS (IP Pod B) → CNI (Overlay/L3) → Pod B`.
2.  **ClusterIP Service:** Стандартный путь через виртуальный IP.
    -   Под-клиент отправляет пакет на VIP.
    -   Локальный `kube-proxy` (или eBPF-агент) на узле отправителя выполняет балансировку и заменяет VIP на IP одного из целевых подов.
    -   Пакет идет напрямую к поду-серверу через CNI.
3.  **Topology Aware Routing:** Если включено, `kube-proxy` отдает приоритет подам в той же зоне (topology.kubernetes.io/zone).

### Выходящий трафик (Egress)

Путь запроса из пода во внешний мир:

1.  **Прямой выход:** Под обращается к внешнему IP. Узел выполняет SNAT (Source NAT), заменяя IP пода на IP узла (за исключением случаев использования публичных IP напрямую в подах).
2.  **Egress Gateway:** В Service Mesh (Istio/Cilium) трафик можно принудительно направлять через выделенный шлюз для централизованного аудита, фильтрации или использования статического IP для внешних Firewall.
3.  **Egress NAT (Cilium):** Позволяет назначать конкретные внешние IP для групп подов (Namespace или Deployment), что критично для интеграции с legacy-системами.

## Практические сценарии

### Диагностика пути трафика

Современные методы отладки (2025-2026):

```bash
# Использование эфемерных контейнеров для трассировки (без установки утилит в образ приложения)
kubectl debug -it <pod-name> --image=nicolaka/netshoot -- tcpdump -i eth0

# Проверка путей eBPF в Cilium
cilium monitor --type drop
cilium connectivity test

# Анализ EndpointSlices (более масштабируемая замена Endpoints)
kubectl get endpointslices -l kubernetes.io/service-name=<service-name>

# Проверка Topology Hints
kubectl get endpointslices <service-name> -o jsonpath='{.items[*].endpoints[*].hints}'
```

### Типичные проблемы и решения

| Симптом | Вероятная причина | Метод проверки / Решение |
| :--- | :--- | :--- |
| **Высокая задержка (Latency)** | Межзонный трафик (Inter-zone hops) | Включить `topologyKeys` или Topology Aware Routing |
| **Connection Reset (Egress)** | MTU Mismatch в Overlay-сетях (VXLAN/Geneve) | Проверить MTU на узлах и в подах (`ip link`). Настроить MSS Clamping. |
| **504 Gateway Timeout** | Ingress не дождался ответа от пода | Проверить Liveness/Readiness probes и тайм-ауты в Gateway/Ingress. |
| **Source IP не виден** | Используется `externalTrafficPolicy: Cluster` | Изменить на `Local` или использовать PROXY Protocol (на LB и Gateway). |
| **Медленный DNS** | Перегрузка CoreDNS или conntrack race | Использовать NodeLocal DNSCache. |

### Рекомендации по архитектуре

1.  **Переход на Gateway API:** Использовать `HTTPRoute` и `Gateway` вместо устаревшего `Ingress` для лучшей управляемости.
2.  **eBPF вместо iptables:** При возможности выбирать CNI с поддержкой eBPF (Cilium) для исключения накладных расходов на обработку правил `iptables` (особенно при >1000 сервисов).
3.  **Оптимизация MTU:** В облачных средах с VXLAN убедиться, что MTU пода меньше MTU узла на 50 байт (или на размер заголовка инкапсуляции).
4.  **Зональная отказоустойчивость:** Использовать Topology Aware Routing только при достаточном количестве реплик в каждой зоне, чтобы избежать перекоса нагрузки.
