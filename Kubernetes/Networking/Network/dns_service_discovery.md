## Определения

**Service Discovery (Обнаружение сервисов)** — автоматизированный процесс поиска сетевых адресов динамических компонентов (подов) в кластере Kubernetes. Позволяет микросервисам взаимодействовать друг с другом, используя стабильные логические имена вместо эфемерных IP-адресов.

**DNS-резолвер кластера** — системный компонент (CoreDNS), обеспечивающий сопоставление доменных имен сервисов с их виртуальными IP (ClusterIP) или прямыми IP подов (для Headless-сервисов).

**EndpointSlice** — современный масштабируемый ресурс API Kubernetes, группирующий сетевые адреса подов. Является источником данных для `kube-proxy` и CoreDNS, поддерживая тысячи подов без деградации производительности API-сервера.

## Основные концепции

### DNS как основной механизм обнаружения

DNS является критической системной службой (обычно реализуемой через CoreDNS), которая интегрирована с Control Plane Kubernetes. Она обеспечивает надежное обнаружение служб и бесшовное взаимодействие между приложениями, абстрагируя эфемерные IP-адреса подов.

### Политики DNS (dnsPolicy)

Kubernetes позволяет настраивать способ разрешения DNS для каждого пода через поле `dnsPolicy`. Каждая политика может быть адаптирована к различным потребностям сети: от простых настроек до индивидуально настраиваемых конфигураций.

*   **`ClusterFirst` (По умолчанию):** Любой запрос DNS, который не соответствует суффиксу домена кластера, пересылается вышестоящему DNS-серверу, унаследованному от узла.
*   **`Default`:** Под наследует конфигурацию разрешения имен от узла, на котором он запущен.
*   **`None`:** Позволяет полностью игнорировать настройки DNS из среды Kubernetes. Все настройки DNS должны быть указаны вручную через поле `dnsConfig`.
*   **`ClusterFirstWithHostNet`:** Для подов, работающих в сети хоста (`hostNetwork: true`), необходимо явно указать эту политику, чтобы они могли использовать кластерный DNS.

**Ключевые функции DNS в Service Discovery:**
*   **Обнаружение служб:** Приложения используют стабильные DNS-имена для связи с другими компонентами, что исключает необходимость жесткой привязки к IP-адресам.
*   **Балансировка нагрузки:** DNS автоматически настраивает записи, которые помогают распределять трафик. В случае обычных сервисов запись указывает на виртуальный IP (ClusterIP), а для Headless-сервисов возвращает список IP-адресов всех готовых подов, позволяя клиенту самому выбирать цель.
*   **Интеграция с жизненным циклом:** При создании или удалении Service записи в DNS обновляются автоматически.
*   **Кастомная конфигурация:** Администраторы могут адаптировать DNS-имена и параметры разрешения под специфические нужды кластера (через Corefile).

| Тип записи | Когда создается | Что содержит |
| :--- | :--- | :--- |
| **A-запись** | Для любого сервиса с ClusterIP | Сопоставляет имя сервиса с виртуальным IP |
| **SRV-запись** | Для именованных портов в сервисе | Номер порта и имя хоста для протоколов (например, SIP, LDAP) |
| **CNAME** | Для сервисов типа `ExternalName` | Ссылка на внешний домен (например, `db.external.com`) |
| **PTR** | Обратная зона | Сопоставляет IP-адрес с именем (используется редко) |

### Обнаружение в Headless Services

При использовании `clusterIP: None` (Headless Service) DNS-сервер возвращает не один VIP, а список A-записей всех готовых (`Ready`) подов, соответствующих селектору.

- **StatefulSet Discovery:** Для каждого пода создается предсказуемое имя `<pod-name>.<service-name>.<namespace>.svc.cluster.local`. Это критично для баз данных и распределенных систем (Kafka, PostgreSQL), требующих прямого обращения к конкретным узлам.

### Роль EndpointSlices в масштабировании

В отличие от устаревшего ресурса `Endpoints`, `EndpointSlices` разбивают список IP-адресов на несколько объектов по 100 эндпоинтов. Это позволяет CoreDNS и сетевым агентам обновлять только измененные части данных, что критично для кластеров с количеством подов >1000.

### Топологическая осведомленность (Topology Hints)

Механизм **Topology Aware Routing** позволяет Service Discovery учитывать физическое расположение подов. Если включено, DNS/Endpoint-контроллер помечает эндпоинты "подсказками" (hints), направляя трафик на поды в той же зоне (Zone) или регионе, снижая задержек и затраты на межзонный трафик.

## Производительность и оптимизация

### Влияние параметра ndots

В файле `/etc/resolv.conf` подов по умолчанию установлено `ndots:5`. Это заставляет DNS-резолвер проверять все локальные суффиксы поиска (`default.svc.cluster.local`, `svc.cluster.local`, и т.д.) перед тем, как запросить внешнее имя (например, `google.com`).
**Оптимизация:** Использование FQDN с точкой на конце (`google.com.`) или внедрение **NodeLocal DNSCache**.

### NodeLocal DNSCache

Запускается как `DaemonSet` на каждом узле. Преимущества:
1. **Кеширование:** Уменьшает количество запросов к центральному CoreDNS.
2. **TCP-апгрейд:** Конвертирует UDP-запросы от подов в TCP для связи с CoreDNS, предотвращая проблемы с `conntrack` в iptables.
3. **Отказоустойчивость:** Снижает риск "DNS-шторма" при массовых перезапусках подов.

## Практические сценарии

### Навигация по пространствам имен (Namespace)

| Запрос | Результат | Применение |
| :--- | :--- | :--- |
| `my-svc` | Разрешается в текущем Namespace | Внутренняя связь модуля |
| `my-svc.prod` | Разрешается в Namespace `prod` | Связь между окружениями |
| `my-svc.prod.svc.cluster.local` | Полное имя (FQDN) | Самый надежный способ (исключает влияние ndots) |

## Устранение неполадок DNS (Troubleshooting)

DNS — критическая зависимость всего кластера. Сбой в этой системе делает невозможным обнаружение сервисов, даже если сами приложения и сетевые компоненты исправны. Ошибки обычно проявляются в логах как `Could not resolve host` или `Temporary failure in name resolution`.

### Путь DNS-запроса в кластере

Понимание пути запроса помогает систематически сужать область поиска неисправности:
1.  **Клиентский под:** Приложение отправляет UDP-запрос на IP из `/etc/resolv.conf`.
2.  **Служба `kube-dns`:** Трафик попадает на ClusterIP системного сервиса (обычно `10.96.0.10`).
3.  **CoreDNS:** `kube-proxy` (или eBPF) перенаправляет запрос на один из подов CoreDNS.
4.  **Ответ:** CoreDNS возвращает IP сервиса или пересылает запрос внешнему DNS (upstream).

### Алгоритм диагностики

Если под не может разрешить имя хоста, следуйте по пути запроса:

1.  **Проверка из клиентского пода:** Убедитесь, что проблема именно в DNS.
    ```bash
    kubectl run dns-test --image=registry.k8s.io/dnsutils:1.3 --rm -it -- nslookup <service-name>
    ```
    *   Если команда возвращает ошибку `server can't find...` или `connection timed out`, проблема подтверждена.

2.  **Состояние подов CoreDNS:** Проверьте здоровье системных подов в неймспейсе `kube-system`.
    ```bash
    kubectl get pods -n kube-system -l k8s-app=kube-dns
    ```
    *   Поды должны быть в статусе `Running`. Если они в `CrashLoopBackOff`, проверьте логи: `kubectl logs -n kube-system -l k8s-app=kube-dns`. Часто причиной сбоев является неверный Corefile (ConfigMap).

3.  **Проверка сервиса `kube-dns`:** Убедитесь, что системный сервис существует и имеет правильный ClusterIP.
    ```bash
    kubectl get svc -n kube-system kube-dns
    ```
    *   Каждый под в кластере настроен на отправку DNS-запросов именно на этот IP. Если IP сервиса изменился или сервис удален, DNS перестанет работать во всем кластере.

4.  **Проверка блокировок (NetworkPolicy):** Если CoreDNS исправен, но недоступен, проверьте сетевые политики. Ограничительная политика в неймспейсе приложения может блокировать исходящий трафик на порт **UDP 53** в сторону `kube-system`.

### Мини-кейс: Блокировка DNS сетевой политикой

После внедрения политики безопасности "Default Deny" несколько приложений потеряли связь с базами данных.
*   **Симптом:** Логи переполнены ошибками `nslookup: connection timed out; no servers could be reached`.
*   **Диагностика:** CoreDNS работает исправно, `nslookup` из системного неймспейса проходит. Однако в неймспейсе приложения обнаружена новая NetworkPolicy, которая разрешает трафик к БД, но забыла разрешить исходящий трафик к CoreDNS.
*   **Решение:** Обновление NetworkPolicy с добавлением правила Egress, разрешающего трафик в неймспейс `kube-system` на UDP-порт 53. Подробный пример см. в разделе **[NetworkPolicy: Сценарий восстановления DNS](./NetworkPolicy/practical_scenarios.md#шаг-4-разрешение-доступа-к-системному-dns-и-backend)**.

> **Совет для собеседования:**
> **Вопрос:** Под не может разрешить DNS-имя сервиса. Как вы будете это отлаживать?
> **Ответ:** Я пройду по пути DNS-запроса. Сначала подтвержу проблему с помощью `nslookup` из тестового пода. Затем проверю статус и логи подов CoreDNS в `kube-system`. Если они здоровы, проверю наличие эндпоинтов у сервиса `kube-dns`. Наконец, проверю, не блокирует ли трафик NetworkPolicy на UDP-порту 53, так как это частая причина «загадочных» сбоев после усиления безопасности.
