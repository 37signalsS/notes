## Определения

**Service Discovery (Обнаружение сервисов)** — автоматизированный процесс поиска сетевых адресов динамических компонентов (подов) в кластере Kubernetes. Позволяет микросервисам взаимодействовать друг с другом, используя стабильные логические имена вместо эфемерных IP-адресов.

**DNS-резолвер кластера** — системный компонент (CoreDNS), обеспечивающий сопоставление доменных имен сервисов с их виртуальными IP (ClusterIP) или прямыми IP подов (для Headless-сервисов).

**EndpointSlice** — современный масштабируемый ресурс API Kubernetes, группирующий сетевые адреса подов. Является источником данных для `kube-proxy` и CoreDNS, поддерживая тысячи подов без деградации производительности API-сервера.

## Основные концепции

### DNS как основной механизм обнаружения

DNS является критической системной службой (обычно реализуемой через CoreDNS), которая интегрирована с Control Plane Kubernetes. Она обеспечивает бесшовное взаимодействие между приложениями, абстрагируя эфемерные IP-адреса подов.

**Ключевые функции DNS в Service Discovery:**
*   **Обнаружение служб:** Приложения используют стабильные DNS-имена для связи с другими компонентами, что исключает необходимость жесткой привязки к IP-адресам.
*   **Балансировка нагрузки:** DNS автоматически настраивает записи, которые помогают распределять трафик. В случае обычных сервисов запись указывает на виртуальный IP (ClusterIP), а для Headless-сервисов возвращает список IP-адресов всех готовых подов, позволяя клиенту самому выбирать цель.
*   **Интеграция с жизненным циклом:** При создании или удалении Service записи в DNS обновляются автоматически.
*   **Кастомная конфигурация:** Администраторы могут адаптировать DNS-имена и параметры разрешения под специфические нужды кластера (через Corefile).

| Тип записи | Когда создается | Что содержит |
| :--- | :--- | :--- |
| **A-запись** | Для любого сервиса с ClusterIP | Сопоставляет имя сервиса с виртуальным IP |
| **SRV-запись** | Для именованных портов в сервисе | Номер порта и имя хоста для протоколов (например, SIP, LDAP) |
| **CNAME** | Для сервисов типа `ExternalName` | Ссылка на внешний домен (например, `db.external.com`) |
| **PTR** | Обратная зона | Сопоставляет IP-адрес с именем (используется редко) |

### Обнаружение в Headless Services

При использовании `clusterIP: None` (Headless Service) DNS-сервер возвращает не один VIP, а список A-записей всех готовых (`Ready`) подов, соответствующих селектору.

- **StatefulSet Discovery:** Для каждого пода создается предсказуемое имя `<pod-name>.<service-name>.<namespace>.svc.cluster.local`. Это критично для баз данных и распределенных систем (Kafka, PostgreSQL), требующих прямого обращения к конкретным узлам.

### Роль EndpointSlices в масштабировании

В отличие от устаревшего ресурса `Endpoints`, `EndpointSlices` разбивают список IP-адресов на несколько объектов по 100 эндпоинтов. Это позволяет CoreDNS и сетевым агентам обновлять только измененные части данных, что критично для кластеров с количеством подов >1000.

### Топологическая осведомленность (Topology Hints)

Механизм **Topology Aware Routing** позволяет Service Discovery учитывать физическое расположение подов. Если включено, DNS/Endpoint-контроллер помечает эндпоинты "подсказками" (hints), направляя трафик на поды в той же зоне (Zone) или регионе, снижая задержек и затраты на межзонный трафик.

## Производительность и оптимизация

### Влияние параметра ndots

В файле `/etc/resolv.conf` подов по умолчанию установлено `ndots:5`. Это заставляет DNS-резолвер проверять все локальные суффиксы поиска (`default.svc.cluster.local`, `svc.cluster.local`, и т.д.) перед тем, как запросить внешнее имя (например, `google.com`).
**Оптимизация:** Использование FQDN с точкой на конце (`google.com.`) или внедрение **NodeLocal DNSCache**.

### NodeLocal DNSCache

Запускается как `DaemonSet` на каждом узле. Преимущества:
1. **Кеширование:** Уменьшает количество запросов к центральному CoreDNS.
2. **TCP-апгрейд:** Конвертирует UDP-запросы от подов в TCP для связи с CoreDNS, предотвращая проблемы с `conntrack` в iptables.
3. **Отказоустойчивость:** Снижает риск "DNS-шторма" при массовых перезапусках подов.

## Практические сценарии

### Навигация по пространствам имен (Namespace)

| Запрос | Результат | Применение |
| :--- | :--- | :--- |
| `my-svc` | Разрешается в текущем Namespace | Внутренняя связь модуля |
| `my-svc.prod` | Разрешается в Namespace `prod` | Связь между окружениями |
| `my-svc.prod.svc.cluster.local` | Полное имя (FQDN) | Самый надежный способ (исключает влияние ndots) |

### Диагностика обнаружения

```bash
# Проверка разрешения через отладочный под
kubectl run tracer --rm -it --image=nicolaka/netshoot -- nslookup redis-master

# Проверка актуальности эндпоинтов для DNS
kubectl get endpointslices -l kubernetes.io/service-name=redis-master

# Просмотр конфигурации CoreDNS (Corefile)
kubectl -n kube-system get configmap coredns -o yaml
```

### Типичные проблемы

- **NXDOMAIN для внешних имен:** Проблема с `forward` в Corefile или блокировка UDP/53 на уровне Firewall узла.
- **Старые IP в кеше приложения:** Приложения на Java или Node.js могут кешировать DNS-ответы "навсегда" (TTL). Требуется настройка `networkaddress.cache.ttl` в JVM.
- **Readiness Probe:** Если под не проходит пробу готовности, он исключается из `EndpointSlice`, и его IP пропадает из DNS-ответов.
