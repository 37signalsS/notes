# Service Discovery в Kubernetes

Механизм Service Discovery позволяет компонентам системы находить друг друга в динамической среде Kubernetes. Основным инструментом реализации этого механизма является DNS-система кластера. Подробные технические детали реализации DNS описаны в файле [DNS в Kubernetes](../dns_deep_dive.md).

## Определения

**Service Discovery (Обнаружение сервисов)** — процесс автоматического поиска сетевых адресов сервисов в распределенной системе. В Kubernetes это позволяет подам обращаться к другим сервисам по стабильным именам вместо динамических IP-адресов.

**DNS-имя сервиса** — уникальный идентификатор сервиса в формате FQDN (Fully Qualified Domain Name), который автоматически создается и обновляется DNS-системой кластера при изменении состава подов.

**ClusterIP** — стабильный виртуальный IP-адрес сервиса, который служит точкой входа для Service Discovery и не меняется на протяжении всей жизни сервиса.

## Основные концепции

### Проблема динамической инфраструктуры

IP-адреса подов в Kubernetes эфемерны и могут изменяться в следующих случаях:

- Перезапуск или пересоздание пода после сбоя.
- Горизонтальное масштабирование (Scaling) набора подов.
- Обновление приложения (Rolling Update).
- Миграция подов между узлами кластера.

Для решения этой проблемы Kubernetes использует абстракцию `Service`, которая предоставляет стабильное имя и IP-адрес, скрывая за собой группу динамических подов.

### Формат DNS-имен

Служба DNS в кластере формирует имена согласно иерархической структуре:

| Тип имени | Формат | Пример | Применение |
| :--- | :--- | :--- | :--- |
| **Полное (FQDN)** | `<service>.<namespace>.svc.cluster.local` | `redis.production.svc.cluster.local` | Межпространственное взаимодействие |
| **Короткое** | `<service>` | `redis` | Внутри одного пространства имен |
| **С неймспейсом** | `<service>.<namespace>` | `redis.production` | Сокращенное межпространственное имя |

Домен кластера по умолчанию — `cluster.local`.

### Принцип работы Service Discovery

1. **Регистрация:** При создании `Service` контроллер регистрирует его имя в API-сервере.
2. **Обновление записей:** DNS-сервер кластера (CoreDNS) обнаруживает новый сервис и создает соответствующую A-запись, указывающую на его `ClusterIP`.
3. **Разрешение имен:** Когда клиентский под выполняет запрос по имени сервиса, локальный DNS-резолвер возвращает `ClusterIP`.
4. **Балансировка:** Трафик, отправленный на `ClusterIP`, перехватывается `kube-proxy` и перенаправляется на IP-адрес одного из здоровых подов, соответствующих селектору сервиса.

### Особенности сетевого стека контейнеров

Настройки DNS, заданные на уровне Docker (например, через `/etc/docker/daemon.json` или параметры `docker run`), полностью **игнорируются** для подов Kubernetes. Узел `Kubelet` самостоятельно управляет файлом `/etc/resolv.conf` внутри каждого контейнера, настраивая его на использование внутрикластерного DNS-сервера.

## Практические сценарии

### Взаимодействие внутри одного пространства имен

Для связи между компонентами внутри одного Namespace достаточно использовать имя сервиса:

```bash
# Обращение к базе данных в том же окружении
curl http://auth-db:5432
```

### Взаимодействие между пространствами имен

При обращении к сервису в другом Namespace рекомендуется использовать формат `<service>.<namespace>` или полное FQDN-имя для предотвращения неоднозначности:

```bash
# Обращение из namespace 'frontend' к сервису в 'backend'
curl http://api-gateway.backend.svc.cluster.local:8080
```

### Диагностика Service Discovery

Для проверки работы механизма обнаружения можно использовать утилиту `nslookup` из тестового пода:

```bash
# Запуск отладочного пода
kubectl run dns-utils --rm -it --image=busybox -- nslookup kubernetes.default

# Проверка статуса системных DNS-подов
kubectl get pods -n kube-system -l k8s-app=kube-dns

# Просмотр логов DNS-сервера для выявления ошибок разрешения
kubectl logs -n kube-system -l k8s-app=kube-dns
```

### Типичные проблемы и их причины

| Симптом | Вероятная причина | Метод устранения |
| :--- | :--- | :--- |
| Имя не разрешается (NXDOMAIN) | Ошибка в имени или сервис не создан | `kubectl get svc -A` |
| Таймаут разрешения запроса | Поды CoreDNS недоступны или перегружены | Проверка ресурсов и логов CoreDNS |
| Медленное разрешение внешних имен | Проблема с `ndots` или внешними рекурсорами | Настройка `NodeLocalDNS` |
| IP разрешается, но связи нет | Неверный селектор или порт в `Service` | `kubectl describe svc <name>` |
