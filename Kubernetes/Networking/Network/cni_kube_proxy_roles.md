# CNI и kube-proxy: роли и взаимодействие

---
**Надёжность:** 10 (SSoT + Проектный контекст 2026)
**Свежесть:** Актуально на июль 2026
---

## Определения

**CNI (Container Network Interface)** — стандартный интерфейс и набор библиотек для взаимодействия между средой исполнения контейнеров (Container Runtime, например, containerd или CRI-O) и сетевыми плагинами. Kubernetes делегирует настройку сети внешним плагинам: при создании пода Kubelet вызывает CNI-плагин с командой `ADD`, а при удалении — с командой `DELETE`. CNI отвечает за "канальный" и "сетевой" уровни (L2/L3), обеспечивая базовую связность Pod-to-Pod и Pod-to-Node.

**kube-proxy** — сетевой агент, работающий в виде DaemonSet на каждом узле кластера. Он является важнейшим компонентом сети Kubernetes, обеспечивающим эффективную маршрутизацию и балансировку нагрузки для служебного трафика. Его задача — перехватывать трафик, идущий на виртуальный IP сервиса, и перенаправлять его на реальный IP одного из подов-эндпоинтов. Поддерживая правила **iptables** или **IPVS**, kube-proxy гарантирует, что трафик внутри кластера последовательно направляется на правильные поды, динамически адаптируясь к изменениям в кластере (масштабирование, сбои, обновления).

## Основные концепции

### Роль CNI (L2/L3: Инфраструктурная связность)

**CNI (Container Network Interface)** — это стандартная подключаемая система, которая выступает в роли контракта между Kubernetes и сетевыми решениями. Kubernetes сам по себе не занимается настройкой сети; он делегирует эту задачу плагинам CNI. Выбор подходящего решения CNI зависит от конкретных потребностей сети, размера кластера и требований безопасности.

**Популярные плагины CNI и их сильные стороны:**
*   **Calico:** Лидер в области производительности и гибкости политик безопасности. Поддерживает как оверлейные сети (VXLAN), так и прямую маршрутизацию через BGP.
*   **Flannel:** Самое простое и легкое решение, идеально подходящее для небольших кластеров и сред, где требуется минимальная настройка (использует VXLAN).
*   **Cilium:** Современное решение на базе eBPF, обеспечивающее высокую производительность, продвинутую безопасность (L7-политики) и глубокую наблюдаемость (observability).

**Ключевые характеристики CNI:**
*   **Модульность и расширяемость:** Любое сетевое решение, реализующее интерфейс CNI, может быть легко интегрировано или заменено в кластере.
*   **Plug-and-play:** Плагины автоматически настраивают сеть при создании подов и очищают ресурсы при их удалении.
*   **Сетевая изоляция:** CNI обеспечивает сетевую изоляцию между контейнерами и подами, гарантируя безопасность границ при сохранении возможности взаимодействия.
*   **Общий интерфейс:** Стандартизированный набор функций для настройки интерфейсов, IPAM (назначение IP), маршрутизации и политик.

**Основные задачи и механизмы:**

- **IPAM (IP Address Management):** Управление пулом адресов. Плагин выделяет уникальный IP из выделенного узлу диапазона (`podCIDR`). В современных реализациях (Cilium, Calico) поддерживается Dual-stack (IPv4/IPv6) и динамическое расширение диапазонов.
- **Изоляция пространств имен:** Создание сетевого namespace для каждого пода, что изолирует его сетевой стек от хоста и других подов.
- **Настройка интерфейсов:** 
    - Создается пара виртуальных интерфейсов (`veth-pair`). 
    - Один конец (обычно `eth0`) помещается внутрь namespace пода. 
    - Второй конец остается в пространстве имен хоста (например, под именем `caliXXXX` в Calico или `vethXXXX`).
- **Маршрутизация и инкапсуляция:** 
    - Для межнодового взаимодействия CNI настраивает маршруты. 
    - В режиме **Overlay** используется инкапсуляция (VXLAN, Geneve, IPIP), где пакет пода оборачивается в UDP/IP пакет узла. 
    - В режиме **L3/Underlay** (например, BGP в Calico) пакеты передаются без изменений, но требуется поддержка маршрутизации внешней сетью.
- **NetworkPolicy:** Реализация правил фильтрации трафика. CNI-плагин (если поддерживает) транслирует объекты `NetworkPolicy` в правила `iptables`, `ipset` или программы `eBPF`.

**Жизненный цикл настройки сети (Интеграция с kubelet):**

1.  **Вызов плагина:** Kubelet на каждом узле взаимодействует с плагинами CNI. Когда под создается, Kubelet запускает бинарный файл плагина, передавая ему необходимые параметры конфигурации (команда `ADD`).
2.  **Конфигурация среды:** Плагин выполняет задачи настройки: назначение IP, создание veth-пары, настройка маршрутизации и установление политик.
3.  **Готовность контейнера:** Только после того, как CNI настроил сеть, контейнеры внутри пода могут начать взаимодействие.
4.  **Удаление ресурса:** При удалении пода Kubelet вызывает плагин с командой `DELETE`, чтобы освободить IP в IPAM и очистить интерфейсы.

### Роль kube-proxy (L4: Сервисная абстракция)

kube-proxy делает сеть Kubernetes "умной", позволяя обращаться к динамическим группам подов через единый стабильный IP.

**Основные задачи:**
- **Абстракция сервисов:** Реализует концепцию `Service`, позволяя предоставлять набор подов как единую сетевую службу со стабильным IP-адресом и DNS-именем.
- **Поддержка типов сервисов:** Работает с различными типами, включая `ClusterIP` (внутренний IP), `NodePort`, `LoadBalancer` и `ExternalName`.
- **Настройка ClusterIP:** При создании сервиса типа ClusterIP kube-proxy гарантирует, что ему назначен внутренний виртуальный IP, и настраивает правила маршрутизация трафика к этому IP.
- **Балансировка нагрузки:** Распределяет входящие запросы между подами-эндпоинтами. Поддерживает настройку **привязки сессий (Session Affinity / Sticky Sessions)**, гарантируя, что трафик от одного и того же клиента будет последовательно направляться в один и тот же под.
- **Обнаружение сервисов (Service Discovery):** Постоянно наблюдает (`watch`) за API-сервером Kubernetes на предмет изменений в объектах `Service` и `Endpoints` / `EndpointSlice`.
 При появлении нового сервиса или обновлении списка эндпоинтов, kube-proxy мгновенно обновляет правила маршрутизации на узле.
- **Проверка работоспособности (Health Checks):** kube-proxy отслеживает состояние подов-бэкендов. Трафик направляется только на исправные (`Healthy`) поды. Если под перестает проходить проверки (например, Readiness Probe), kube-proxy исключает его из правил маршрутизации до восстановления работоспособности.

**Режимы работы и технические нюансы:**

#### 1. Режим nftables (Рекомендован с v1.31)

Современная замена iptables, ставшая стабильной в версии 1.31.

- **Механика:** Использует таблицы и цепочки `nftables`. Трафик обрабатывается виртуальной машиной внутри ядра Linux.
- **Преимущества:** Атомарное обновление правил (нет риска "залипания" или частичного обновления), более высокая производительность при большом количестве сервисов, встроенная поддержка наборов (sets).

#### 2. Режим IPVS (High Performance)

Рекомендуется для высоконагруженных кластеров с тысячами сервисов.

- **Механика:** Создает виртуальный сервер в таблице IPVS ядра. Балансировка происходит через хеш-таблицы.
- **Сложность:** O(1) — время обработки пакета не зависит от общего количества правил.
- **Алгоритмы балансировки:** 
    - `rr` (Round Robin) — по очереди.
    - `lc` (Least Connection) — на под с наименьшим числом активных соединений.
    - `dh` (Destination Hashing), `sh` (Source Hashing).
    - `sed` (Shortest Expected Delay).

#### 3. Режим iptables (Традиционный)

Самый распространенный режим, работающий через Netfilter.

- **Цепочки правил:**
    - `KUBE-SERVICES`: Входная точка для всех пакетов, проверяющая обращение к ClusterIP.
    - `KUBE-SVC-*`: Цепочка конкретного сервиса, содержащая правила выбора эндпоинта.
    - `KUBE-SEP-*`: Цепочка конкретного эндпоинта (Service End Point), выполняющая финальный DNAT на IP пода.
- **Балансировка:** Реализуется через модуль `statistic` с параметром `--probability`. Например, для двух подов вероятность первого правила будет 0.5, второго (финального) — 1.0.

#### 4. Технология eBPF (Замена kube-proxy)

Реализуется в Cilium или Calico (VPP/eBPF dataplane). Программы eBPF перехватывают пакеты на уровне сетевого драйвера (TC/XDP). Это позволяет полностью исключить `kube-proxy` и `iptables`, достигая минимально возможных задержек (Latency) и снижая нагрузку на CPU.

### Разделение ответственности и взаимодействие

| Операция | Компонент | Уровень | Техническая суть |
| :--- | :--- | :--- | :--- |
| **Выбор пода** | kube-proxy | L4 | Замена VIP сервиса на IP выбранного пода (DNAT) |
| **Доставка до узла** | CNI-плагин | L3 | Маршрутизация или инкапсуляция в VXLAN/BGP |
| **Доставка в контейнер** | CNI-плагин | L2 | Проброс пакета в veth-интерфейс namespace пода |

**Техническое взаимодействие (пошагово):**

1.  Приложение в Поде А обращается к `10.96.0.10:80` (ClusterIP).
2.  Пакет попадает в сетевой стек узла. Правила **kube-proxy** (например, в `nftables`) срабатывают первыми, меняя целевой IP на `10.244.1.5:8080` (IP Пода Б).
3.  Сетевой стек узла видит новый целевой IP. Таблица маршрутизации, настроенная **CNI**, указывает, что этот IP находится на другом узле.
4.  CNI (если используется VXLAN) оборачивает пакет в UDP-заголовок с адресом целевого узла и отправляет его в физическую сеть.

## Практические сценарии

### Выбор CNI и режима проксирования

| Требование | CNI | kube-proxy mode |
| :--- | :--- | :--- |
| **Максимальная скорость** | Cilium | eBPF (kube-proxy free) |
| **Большой кластер (>2k сервисов)** | Calico | IPVS или nftables |
| **Стабильность и простота** | Calico / Flannel | nftables или iptables |
| **Сложные политики безопасности** | Calico / Cilium | Любой |

### Ограничения балансировки L4

Поскольку `kube-proxy` работает на уровне TCP/UDP, он не видит содержимое протоколов прикладного уровня (L7).
- **Проблема gRPC:** Из-за мультиплексирования HTTP/2 все запросы идут по одному TCP-соединению. kube-proxy выберет один под в начале сессии, и все последующие gRPC-вызовы уйдут на него, вызывая перекос нагрузки.
- **Решение:** Использовать **Gateway API**, **Ingress** или **Service Mesh** для балансировки на уровне L7.

```bash
# 1. Проверка текущего режима kube-proxy
kubectl -n kube-system get configmap kube-proxy -o yaml | grep mode
# → mode: "ipvs" (или "nftables", "iptables")

# 2. Просмотр активных эндпоинтов в IPVS
ipvsadm -Ln
# Prot LocalAddress:Port Scheduler Flags
#   -> RemoteAddress:Port           Forward Weight ActiveConn InActConn

# 3. Анализ правил nftables
nft list table ip kube-proxy | head -n 20

# 4. Проверка состояния CNI (на примере Cilium)
cilium status

# 5. Проверка veth-интерфейсов на узле
ip link show | grep veth
```

### Влияние на производительность (Performance Impact)

- **Контекстные переключения:** Режимы `iptables` и `IPVS` заставляют пакет проходить через весь стек Netfilter, что создает накладные расходы. eBPF минимизирует этот путь.
- **MTU и Fragmentation:** Инкапсуляция VXLAN добавляет 50 байт заголовка. Если MTU на физическом интерфейсе 1500, то внутри пода MTU должен быть **1450**. Неправильная настройка MTU приводит к фрагментации и резкому падению скорости (особенно в облаках).
- **CPU Load:** При частых обновлениях сервисов `iptables` может потреблять до 30-40% CPU одного ядра только на перезапись правил. `IPVS` и `nftables` решают эту проблему через инкрементальные обновления.
