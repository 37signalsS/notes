# CNI и kube-proxy: роли и взаимодействие

## Определения

**CNI (Container Network Interface)** — стандартный интерфейс для взаимодействия между средой исполнения контейнеров (Container Runtime) и сетевыми плагинами. Kubernetes не умеет настраивать сеть сам — при создании пода он вызывает CNI-плагин. Без CNI поды не получат IP и не смогут общаться. CNI отвечает за настройку сетевой связности между контейнерами внутри пода, а также между подами и узлами кластера на уровнях L2/L3.

**kube-proxy** — сетевой агент и балансировщик нагрузки, работающий на каждом узле кластера. Он отвечает за реализацию абстракции `Service` и обеспечивает перенаправление трафика на поды через правила сетевого стека узла на уровне L4.

## Основные концепции

### Роль CNI (L2/L3)

CNI-плагин обеспечивает базовую сетевую связность ("трубы") в кластере.

**Основные задачи:**

- Выделение уникальных IP-адресов подам (IPAM).
- Создание сетевого namespace для пода.
- Создание и настройка сетевых интерфейсов: veth-пара (один конец помещается в сетевой namespace пода, другой остаётся на хосте).
- Назначение IP из pod CIDR на интерфейс внутри namespace пода.
- Обеспечение маршрутизации трафика между подами как на одном узле, так и между узлами (overlay через VXLAN/IPIP или underlay через BGP).
- Реализация правил `NetworkPolicy` (в поддерживающих это плагинах).

**Жизненный цикл настройки сети (ADD/DELETE):**

1. **Создание пода:** Kubelet вызывает CNI-плагин. Создается сетевой namespace и veth-пара, поду назначается IP из pod CIDR, настраиваются маршруты. Контейнеры запускаются только после успешной настройки сети.
2. **Удаление пода:** Kubelet вызывает CNI-плагин для очистки интерфейсов, удаления сетевого namespace и возврата IP-адреса в пул.

### Роль kube-proxy (L4)

kube-proxy управляет виртуальными IP-адресами сервисов и балансировкой трафика.

**Основные задачи:**

- Реализация сервисов типов `ClusterIP`, `NodePort`, `LoadBalancer`.
- Трансляция адресов (DNAT) для перенаправления трафика с IP-адреса сервиса на реальные IP-адреса подов.
- Обеспечение балансировки нагрузки между подами одного сервиса.
- Отслеживание изменений объектов `Service` и `EndpointSlice` через API-сервер.

**Режимы работы:**

#### iptables (исторический дефолт)

kube-proxy в этом режиме — **агент конфигурации ядра**, а не прокси в userspace. Он не перенаправляет трафик через свой процесс, а программирует цепочки Netfilter:

- `KUBE-SERVICES` — корневая цепочка, перехватывающая весь трафик на ClusterIP.
- `KUBE-SVC-*` — отдельная цепочка на каждый Service.
- `KUBE-SEP-*` — цепочка на каждый endpoint (pod) сервиса.

Пакет, направленный на `ClusterIP:port`, проходит через `KUBE-SVC-*`, где с помощью `--probability` (модуль `statistic`) выполняется DNAT на случайный `pod IP:port`.

**Недостатки:**

- При 1000 сервисов и 10 подах каждый — тысячи правил.
- Каждое изменение (создание/удаление пода) вызывает полную перезапись всех правил.
- Сложность O(n) — с ростом числа сервисов время обработки пакета растёт линейно.

#### IPVS (рекомендован для больших кластеров)

kube-proxy создаёт **виртуальный сервер** в IPVS-таблице ядра и регистрирует под ним реальные серверы (pod IP). Балансировка происходит в ядре через хеш-таблицу за O(1).

**Поддерживаемые алгоритмы балансировки:**

- `rr` (round-robin) — по кругу.
- `lc` (least connections) — на pod с наименьшим числом соединений.
- `dh` (destination hash) — по хешу IP-адреса назначения.
- `sh` (source hash) — по хешу IP-адреса источника.

**Включение:** через ConfigMap `kube-proxy` (поле `mode: ipvs`) или флаг `--proxy-mode=ipvs`. Требует наличия `ipvsadm` и загруженных модулей ядра (`ip_vs`, `ip_vs_rr`, `ip_vs_wrr`, `ip_vs_sh`, `nf_conntrack`).

**Ограничение (оба режима):** kube-proxy работает только на L4 (IP+порт) и не знает о состоянии приложения. Именно поэтому **gRPC** плохо балансируется через kube-proxy: HTTP/2 мультиплексирует все вызовы в одном TCP-соединении, и kube-proxy выбирает pod один раз при установке соединения.

#### eBPF

Современная альтернатива (в Cilium/Calico), позволяющая полностью заменить kube-proxy программами на уровне ядра. Подробнее: [eBPF: Замена kube-proxy](./CNI/ebpf.md).

### Разделение ответственности и взаимодействие

| Компонент | Уровень OSI | Задача |
| :--- | :--- | :--- |
| **CNI-плагин** | L2/L3 | IP-связность Pod-to-Pod, маршрутизация между узлами |
| **kube-proxy** | L4 | Абстракция Service, балансировка Service-to-Pod |

**Техническое взаимодействие:**

1. `kube-proxy` подменяет виртуальный IP сервиса на реальный IP пода (DNAT).
2. После подмены пакет передается в сетевой стек ядра.
3. Дальнейшая доставка пакета до пода (через туннель VXLAN/IPIP или прямую маршрутизацию BGP) — задача CNI-плагина.

## Практические сценарии

### Выбор CNI-плагина

Выбор плагина определяет возможности безопасности и производительность сети.

| Плагин | Подход | NetworkPolicy | Применение |
| :--- | :--- | :--- | :--- |
| **Flannel** | Overlay (VXLAN) — только VXLAN, без NetworkPolicy | Нет | Простые кластеры, минимальные требования |
| **Calico** | L3 (BGP/Overlay) | Да | Production, высокая безопасность |
| **Cilium** | eBPF | Да | [Cilium](./CNI/cilium.md) — High-load, замена kube-proxy |

- Подробнее: [Выбор CNI и внешние типы доступа](./CNI/selection_and_external_access.md)

### Выбор режима работы kube-proxy

- **iptables:** Для кластеров среднего размера (до 500-1000 сервисов).
- **IPVS:** Для крупных кластеров с частым обновлением сервисов. Требует наличия `ipvsadm` на узлах.
- **eBPF (Cilium/Calico):** Для проектов, требующих максимальной производительности и отказа от накладных расходов Netfilter.

### Дополнительные сетевые функции

- **IPAM (IP Address Management):** Механизмы выделения IP-адресов (host-local, Calico IPAM). См. [IPAM в CNI](./CNI/ipam.md).
- **Внешний доступ:** Использование NodePort, LoadBalancer и Ingress. См. [Обзор Ingress](../Ingress/overview.md).
- **IP Advertisement:** Анонсирование ClusterIP внешним роутерам через BGP. См. [Внешние типы доступа](./CNI/selection_and_external_access.md).

## Дополнительная информация

### Диагностика сетевых компонентов

```bash
# Проверка режима работы kube-proxy
kubectl -n kube-system get configmap kube-proxy -o yaml | grep mode

# Проверка подов сетевого плагина (на примере Calico)
kubectl get pods -n kube-system -l k8s-app=calico-node

# Просмотр правил IPVS (если включен)
ipvsadm -Ln

# Проверка сетевой связности между подами
kubectl run tester --rm -it --image=busybox -- ping <target-pod-ip>
```

### Влияние на производительность

- **Инкапсуляция (VXLAN/IPIP):** Добавляет 50-100 байт накладных расходов на каждый пакет (MTU overhead) и нагружает CPU.
- **Прямая маршрутизация (BGP):** Работает на скорости физической сети, но требует поддержки BGP инфраструктурой.
- **eBPF-фильтрация:** Снижает задержки за счет обработки пакетов на ранних стадиях в ядре, минуя цепочки iptables.
