## CNI (Container Network Interface)

Kubernetes не реализует сетевую модель самостоятельно. Вместо этого он делегирует эту задачу **CNI-плагинам**. **CNI (Container Network Interface)** — это интерфейс, который позволяет настраивать сетевые взаимодействия как между контейнерами (внутри пода), так и между подами и узлами кластера. Он стандартизирует способ, которым различные сетевые плагины (например, Calico, Flannel, Weave Net) конфигурируют сетевые интерфейсы контейнеров и управляют маршрутизацией трафика.

**Основные задачи CNI:**
* Выделение IP-адресов подам.
* Настройка сетевых интерфейсов для каждого пода.
* Обеспечение маршрутизации трафика между подами на одном узле и между узлами.
* Реализация сетевых политик (в продвинутых CNI-плагинах).

После того как `kubelet` инициировал запуск Pod'а, он вызывает CNI-плагин для настройки сетевых ресурсов. Этот процесс включает следующие шаги:

1. **Назначение IP-адреса Pod'у:** Каждому Pod'у в Kubernetes присваивается уникальный IP-адрес из диапазона, выделенного для кластера.

2. **Создание сетевого пространства имен (Network Namespace):** Для каждого Pod'а создаётся свой собственный, изолированный `network namespace`. Это гарантирует, что у Pod'а будет свой собственный сетевой стек (таблица маршрутизации, сетевые устройства, порты).

3. **Настройка виртуальных Ethernet-устройств (veth-pair):** Создаётся пара виртуальных Ethernet-интерфейсов (`veth-pair`). Один конец этой пары помещается в сетевое пространство имен Pod'а (и становится его интерфейсом, например, `eth0`), а другой остаётся в корневом пространстве имен узла.

4. **Подключение к мосту узла:** Конец `veth-пары`, находящийся в пространстве имен узла, подключается к сетевому мосту (например, `cni0`). Это позволяет Pod'ам на одном узле обмениваться трафиком через этот мост.

5. **Настройка маршрутизации для межсетевого взаимодействия:** Для связи Pod'ов, расположенных на разных узлах, CNI-плагин настраивает маршруты. Часто это реализуется через оверлейные сети (например, с использованием VXLAN, как в **Flannel**) или через прямое управление маршрутами на узлах (как в **Calico**).

## Разделение ролей: CNI (Flannel, Calico) и `kube-proxy`

**CNI-плагин (Flannel, Calico): Сеть для подов (L2/L3)**

* **Задача:** Реализация спецификации CNI для обеспечения **IP-связности между всеми подами** кластера (связь Pod-to-Pod).
* **Функции:**
    1. **Выделение IP-адресов:** Назначает каждому поду уникальный IP из диапазона `podCIDR`.
    2. **Создание интерфейсов:** Создает и настраивает сетевые интерфейсы для подов (обычно `veth-pair`).
    3. **Маршрутизация между узлами:** Обеспечивает доставку пакетов между подами на разных узлах. Для этого используются два основных подхода:
        * **Overlay-сети** (Flannel, Calico в режиме IPIP): Трафик подов инкапсулируется (заворачивается) в трафик узлов с помощью технологий вроде VXLAN или IPIP.
        *   **Прямая маршрутизация** (Calico в режиме [../../Networking/Protocols/BGP_overview.md](BGP (Border Gateway Protocol): Обзор)): CNI-демон анонсирует маршруты до подов другим узлам по протоколу BGP, и ядро ОС напрямую маршрутизирует пакеты без инкапсуляции.
    4. **Сетевые политики** (Calico, Cilium): Реализует правила `NetworkPolicy` для фильтрации трафика.

**`kube-proxy`: Абстракция Service (L4)**

* **Задача:** Реализация виртуальной абстракции `Service`. Обеспечение **обнаружения (discovery) и балансировки нагрузки** для групп подов (связь Service-to-Pod).
* **Функции:**
    1. **Наблюдение:** Отслеживает изменения объектов `Service` и `Endpoints` (списки IP-адресов живых подов) через API-сервер.
    2. **Программирование правил:** На каждом узле кластера создает и обновляет правила в ядре Linux, используя один из режимов.
    3. **Трансляция адресов:** Эти правила перехватывают трафик, адресованный виртуальному `ClusterIP` сервиса, и выполняют **DNAT** (Destination Network Address Translation) — подменяют IP-адрес назначения на реальный IP-адрес одного из обслуживающих подов.

#### Режимы работы `kube-proxy`

- **`iptables` (по умолчанию):**
  - **Принцип работы:** Для каждого `Service` `kube-proxy` создает набор правил в `iptables`. Эти правила перехватывают трафик, направленный на `ClusterIP` и порт сервиса, и случайным образом перенаправляют его на IP-адрес одного из бэкенд-подов.
  - **Плюсы:** Надежный и универсальный режим, работает в любой Linux-среде.
  - **Минусы:** Может быть медленным при очень большом количестве сервисов (тысячи), так как `iptables` обрабатывает правила последовательно.

- **`ipvs` (IP Virtual Server):**
  - **Принцип работы:** Использует `IPVS` — встроенный в ядро Linux балансировщик нагрузки 4-го уровня. `IPVS` использует хэш-таблицы для хранения правил, что обеспечивает практически константное время поиска (`O(1)`) независимо от количества правил.
  - **Плюсы:** Значительно более производительный, чем `iptables`, при большом количестве сервисов. Поддерживает различные алгоритмы балансировки (например, Round Robin, Least Connection).
  - **Минусы:** Требует, чтобы на узле было загружено ядро `IPVS`.

### IPVS (IP Virtual Server) - подробный обзор

**IPVS** — это модуль ядра Linux, реализующий балансировку нагрузки на транспортном уровне (Layer 4) как часть подсистемы Linux Virtual Server (LVS). IPVS позволяет создавать высокопроизводительные отказоустойчивые сервисы путем распределения входящих запросов между несколькими backend-серверами.

#### Функционал IPVS

1. **Балансировка нагрузки L4:**
   - Работает на уровне TCP/UDP, анализируя IP-адреса и порты
   - Перехватывает входящие соединения и перенаправляет их на backend-серверы
   - Поддерживает Virtual IP (VIP) — виртуальные IP-адреса, на которые приходит трафик

2. **Алгоритмы балансировки:**
   - **Round Robin (rr):** Распределение запросов по кругу между всеми серверами
   - **Least Connection (lc):** Отправка запроса на сервер с наименьшим числом активных соединений
   - **Source Hashing (sh):** Привязка клиента к конкретному серверу на основе хеша IP-адреса источника (sticky sessions)
   - **Destination Hashing (dh):** Распределение на основе хеша IP-адреса назначения
   - **Weighted Round Robin (wrr):** Round Robin с учетом весов серверов
   - **Weighted Least Connection (wlc):** Least Connection с учетом весов

3. **Методы перенаправления (Forwarding Methods):**
   - **NAT (Network Address Translation):** IPVS модифицирует IP-адреса в пакетах
   - **DR (Direct Routing):** Пакеты отправляются напрямую клиенту backend-сервером, минуя IPVS (требует настройки loopback-интерфейса на backend)
   - **IP-IP Tunneling:** Инкапсуляция пакетов в IP-IP туннели для передачи backend-серверам в других сетях
   - **Full NAT:** Двусторонний NAT, позволяет backend-серверам быть в разных подсетях без специальной настройки

4. **Преимущества по сравнению с iptables:**
   - Время поиска правил O(1) благодаря хеш-таблицам (vs O(n) у iptables)
   - Поддержка различных алгоритмов балансировки
   - Более высокая производительность при большом количестве сервисов (>1000)
   - Встроенная поддержка health checking (в современных реализациях)

5. **Использование в Kubernetes:**
   - `kube-proxy` в режиме `ipvs` использует IPVS для реализации Service
   - Требует загруженного модуля ядра `ip_vs` и зависимостей
   - Проверка доступности: `lsmod | grep ip_vs`
   - Загрузка модуля: `modprobe ip_vs`

- **`userspace` (устарел):**
  - **Принцип работы:** `kube-proxy` запускал прокси-процесс в пользовательском пространстве, который принимал трафик и перенаправлял его подам.
  - **Статус:** Не используется в современных кластерах из-за низкой производительности и высоких накладных расходов.

- **`kernelspace` (Windows):** Аналог `iptables`/`ipvs` для Windows-узлов.

- **Решения на базе eBPF (например, Cilium):** Современные CNI-плагины, такие как Cilium, могут полностью или частично заменять функции `kube-proxy`, используя eBPF для реализации балансировки нагрузки L4 и сетевых политик прямо в ядре. Это позволяет достичь более высокой производительности и уменьшить количество правил `iptables`. Однако общая модель обнаружения сервисов через `EndpointSlices` сохраняется.

**Техническое взаимодействие:**

1. `kube-proxy` **не занимается** маршрутизацией пакетов между узлами. Его работа — это трансляция адресов на уровне соединений (L4).
2. Когда `kube-proxy` с помощью `iptables` или `IPVS` подменяет `ClusterIP` на реальный IP пода, он передает пакет дальше в сетевой стек ядра.
3. Дальнейшая доставка этого пакета до целевого пода (особенно если тот на другом узле) — это уже **задача CNI-плагина**. Ядро ОС, используя таблицы маршрутизации, настроенные CNI-плагином, направляет пакет либо в VXLAN-туннель, либо напрямую на другой узел (в случае BGP).

**Итог:** CNI создает IP-связность на уровнях L2/L3. `kube-proxy` использует эту готовую связность для предоставления абстракции `Service` и балансировки на уровне L4. Оба компонента обязательны и не заменяют друг друга.
