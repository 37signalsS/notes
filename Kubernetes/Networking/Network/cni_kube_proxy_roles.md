## Определения

**CNI (Container Network Interface)** — это интерфейс, который позволяет настраивать сетевые взаимодействия как между контейнерами (внутри пода), так и между подами и узлами кластера. Он стандартизирует способ, которым различные сетевые плагины (например, Calico, Flannel, Weave Net) конфигурируют сетевые интерфейсы контейнеров и управляют маршрутизацией трафика.

**kube-proxy** — сетевой прокси и балансировщик нагрузки, работающий на каждом узле. Реализует абстракцию `Service` путем управления правилами в `iptables` или `IPVS`.

## Основные концепции

### Роль CNI в Kubernetes

Kubernetes не реализует сетевую модель самостоятельно. Вместо этого он делегирует эту задачу **CNI-плагинам**.

**Основные задачи CNI:**

- Выделение IP-адресов подам.
- Настройка сетевых интерфейсов для каждого пода.
- Обеспечение маршрутизации трафика между подами на одном узле и между узлами.
- Реализация сетевых политик (в продвинутых CNI-плагинах).

После того как `kubelet` инициировал запуск Pod'а, он вызывает CNI-плагин для настройки сетевых ресурсов. Этот процесс включает следующие шаги:

1. **Назначение IP-адреса Pod'у:** Каждому Pod'у в Kubernetes присваивается уникальный IP-адрес из диапазона, выделенного для кластера.

2. **Создание сетевого пространства имен (Network Namespace):** Для каждого Pod'а создаётся свой собственный, изолированный `network namespace`. Это гарантирует, что у Pod'а будет свой собственный сетевой стек (таблица маршрутизации, сетевые устройства, порты).

3. **Настройка виртуальных Ethernet-устройств (veth-pair):** Создаётся пара виртуальных Ethernet-интерфейсов (`veth-pair`). Один конец этой пары помещается в сетевое пространство имен Pod'а (и становится его интерфейсом, например, `eth0`), а другой остаётся в корневом пространстве имен узла.

4. **Подключение к мосту узла:** Конец `veth-пары`, находящийся в пространстве имен узла, подключается к сетевому мосту (например, `cni0`). Это позволяет Pod'ам на одном узле обмениваться трафиком через этот мост.

5. **Настройка маршрутизации для межсетевого взаимодействия:** Для связи Pod'ов, расположенных на разных узлах, CNI-плагин настраивает маршруты. Часто это реализуется через оверлейные сети (например, с использованием VXLAN) или через прямое управление маршрутами (BGP). Детальное описание этих подходов см. в [обзоре сетевой модели](./network_overview.md#3-на-уровне-кластера-между-разными-узлами).

## Разделение ролей: CNI (Flannel, Calico) и `kube-proxy`

**CNI-плагин (Flannel, Calico): Сеть для подов (L2/L3)**

- **Задача:** Реализация спецификации CNI для обеспечения **IP-связности между всеми подами** кластера (связь Pod-to-Pod).
- **Функции:**
    1. **Выделение IP-адресов:** Назначает каждому поду уникальный IP из диапазона `podCIDR`.
    2. **Создание интерфейсов:** Создает и настраивает сетевые интерфейсы для подов (обычно `veth-pair`).
    3. **Маршрутизация между узлами:** Обеспечивает доставку пакетов между подами на разных узлах. Для этого используются два основных подхода:
        - **Overlay-сети (L2 поверх L3):** Используется в **Flannel (режим VXLAN)** и **Calico (режим IPIP)**. Трафик подов инкапсулируется (заворачивается) в пакеты узлов с помощью технологий вроде VXLAN или IP-in-IP. Это простой и универсальный способ, работающий в любой сети, но вносящий дополнительные накладные расходы на инкапсуляцию.
        - **Прямая маршрутизация (L3):** Основной режим работы **Calico**. Не использует инкапсуляцию. Каждый узел кластера выступает в роли BGP-маршрутизатора, анонсируя маршруты до подов, запущенных на нем, другим узлам. Ядро Linux напрямую маршрутизирует пакеты до нужного узла. Это обеспечивает максимальную производительность, но требует, чтобы сетевая инфраструктура поддерживала протокол [BGP (Border Gateway Protocol)](../../../Networking/Protocols/bgp.md), или чтобы все узлы находились в одном L2-сегменте.
    4. **Сетевые политики** (Calico, Cilium): Реализует правила `NetworkPolicy` для фильтрации трафика. Flannel по умолчанию не поддерживает `NetworkPolicy`.

**`kube-proxy`: Абстракция Service (L4)**

- **Задача:** Реализация виртуальной абстракции `Service`. Обеспечение **обнаружения (discovery) и балансировки нагрузки** для групп подов (связь Service-to-Pod).
- **Функции:**
    1. **Наблюдение:** Отслеживает изменения объектов `Service` и `Endpoints` (списки IP-адресов живых подов) через API-сервер.
    2. **Программирование правил:** На каждом узле кластера создает и обновляет правила в ядре Linux, используя один из режимов.
    3. **Трансляция адресов:** Эти правила перехватывают трафик, адресованный виртуальному `ClusterIP` сервиса, и выполняют **DNAT** (Destination Network Address Translation) — подменяют IP-адрес назначения на реальный IP-адрес одного из обслуживающих подов.

#### Режимы работы `kube-proxy`

- **`iptables` (по умолчанию):**
  - **Принцип работы:** Для каждого `Service` `kube-proxy` создает набор правил в `iptables`. Эти правила перехватывают трафик, направленный на `ClusterIP` и порт сервиса, и случайным образом перенаправляют его на IP-адрес одного из бэкенд-подов.
  - **Плюсы:** Надежный и универсальный режим, работает в любой Linux-среде.
  - **Минусы:** Может быть медленным при очень большом количестве сервисов (тысячи), так как `iptables` обрабатывает правила последовательно.

- **`ipvs` (IP Virtual Server):**
  - **Принцип работы:** Использует `IPVS` — встроенный в ядро Linux балансировщик нагрузки 4-го уровня. `IPVS` использует хэш-таблицы для хранения правил, что обеспечивает практически константное время поиска (`O(1)`) независимо от количества правил.
  - **Плюсы:** Значительно более производительный, чем `iptables`, при большом количестве сервисов. Поддерживает различные алгоритмы балансировки (например, Round Robin, Least Connection).
  - **Минусы:** Требует, чтобы на узле было загружено ядро `IPVS`.

### IPVS (IP Virtual Server) - подробный обзор

**IPVS** — это модуль ядра Linux, реализующий балансировку нагрузки на транспортном уровне (Layer 4) как часть подсистемы Linux Virtual Server (LVS). IPVS позволяет создавать высокопроизводительные отказоустойчивые сервисы путем распределения входящих запросов между несколькими backend-серверами.

#### Функционал IPVS

1. **Балансировка нагрузки L4:**
   - Работает на уровне TCP/UDP, анализируя IP-адреса и порты
   - Перехватывает входящие соединения и перенаправляет их на backend-серверы
   - Поддерживает Virtual IP (VIP) — виртуальные IP-адреса, на которые приходит трафик

2. **Алгоритмы балансировки:**
   - **Round Robin (rr):** Распределение запросов по кругу между всеми серверами
   - **Least Connection (lc):** Отправка запроса на сервер с наименьшим числом активных соединений
   - **Source Hashing (sh):** Привязка клиента к конкретному серверу на основе хеша IP-адреса источника (sticky sessions)
   - **Destination Hashing (dh):** Распределение на основе хеша IP-адреса назначения
   - **Weighted Round Robin (wrr):** Round Robin с учетом весов серверов
   - **Weighted Least Connection (wlc):** Least Connection с учетом весов

3. **Методы перенаправления (Forwarding Methods):**
   - **NAT (Network Address Translation):** IPVS модифицирует IP-адреса в пакетах
   - **DR (Direct Routing):** Пакеты отправляются напрямую клиенту backend-сервером, минуя IPVS (требует настройки loopback-интерфейса на backend)
   - **IP-IP Tunneling:** Инкапсуляция пакетов в IP-IP туннели для передачи backend-серверам в других сетях
   - **Full NAT:** Двусторонний NAT, позволяет backend-серверам быть в разных подсетях без специальной настройки

4. **Преимущества по сравнению с iptables:**
   - Время поиска правил O(1) благодаря хеш-таблицам (vs O(n) у iptables)
   - Поддержка различных алгоритмов балансировки
   - Более высокая производительность при большом количестве сервисов (>1000)
   - Встроенная поддержка health checking (в современных реализациях)

5. **Использование в Kubernetes:**
   - `kube-proxy` в режиме `ipvs` использует IPVS для реализации Service
   - Требует загруженного модуля ядра `ip_vs` и зависимостей
   - Проверка доступности: `lsmod | grep ip_vs`
   - Загрузка модуля: `modprobe ip_vs`

- **`userspace` (устарел):**
  - **Принцип работы:** `kube-proxy` запускал прокси-процесс в пользовательском пространстве, который принимал трафик и перенаправлял его подам.
  - **Статус:** Не используется в современных кластерах из-за низкой производительности и высоких накладных расходов.

- **`kernelspace` (Windows):** Аналог `iptables`/`ipvs` для Windows-узлов.

**Техническое взаимодействие:**

1. `kube-proxy` **не занимается** маршрутизацией пакетов между узлами. Его работа — это трансляция адресов на уровне соединений (L4).
2. Когда `kube-proxy` с помощью `iptables` или `IPVS` подменяет `ClusterIP` на реальный IP пода, он передает пакет дальше в сетевой стек ядра.
3. Дальнейшая доставка этого пакета до целевого пода (особенно если тот на другом узле) — это уже **задача CNI-плагина**. Ядро ОС, используя таблицы маршрутизации, настроенные CNI-плагином, направляет пакет либо в VXLAN-туннель, либо напрямую на другой узел (в случае BGP).

**Итог:** CNI создает IP-связность на уровнях L2/L3. `kube-proxy` использует эту готовую связность для предоставления абстракции `Service` и балансировки на уровне L4. В традиционной модели оба компонента обязательны и не заменяют друг друга.

### Решения на базе eBPF: Замена `kube-proxy`

Современные CNI-плагины, такие как **Calico** и **Cilium**, могут использовать технологию **eBPF (Extended Berkeley Packet Filter)** для полной замены `kube-proxy`. Это позволяет достичь более высокой производительности и упростить сетевой стек.

#### Что такое eBPF?

**eBPF** — это революционная технология в ядре Linux, которая позволяет запускать пользовательские программы в изолированной "песочнице" непосредственно в пространстве ядра (`kernel space`). Это устраняет необходимость в дорогостоящих переключениях контекста между ядром и пользовательским пространством (`user space`).

В контексте сети eBPF позволяет "прикреплять" эти программы к различным точкам (хукам) в сетевом стеке ядра, где они могут с высокой скоростью проверять, изменять или отбрасывать сетевые пакеты.

#### Преимущества eBPF в Calico

- **Высокая производительность:** Обработка пакетов происходит на уровне ядра, что значительно снижает задержки и нагрузку на CPU по сравнению с `iptables` или `ipvs`.
- **Замена `kube-proxy`:** Calico в режиме eBPF полностью берет на себя функции `kube-proxy`, включая трансляцию адресов (DNAT) для сервисов.
- **Эффективные сетевые политики:** Правила `NetworkPolicy` также реализуются через eBPF, что работает быстрее, чем `iptables`.

#### Недостатки eBPF

- **Сложность:** Отладка проблем с eBPF требует специальных знаний и инструментов.
- **Требования к ядру:** Требуется относительно свежая версия ядра Linux.
- **Золотое правило:** Если существующая сетевая подсистема справляется с нагрузкой, переход на eBPF может быть излишним усложнением.

### Управление IP-адресами (IPAM)

Помимо маршрутизации, CNI-плагин отвечает за управление IP-адресами (IP Address Management, IPAM). Существует два основных подхода:

- **Стандартный механизм Kubernetes (IPAM-плагин `host-local`):** `kube-controller-manager` выделяет каждому узлу префикс (обычно `/24`) из общего `podCIDR` кластера и записывает его в спецификацию объекта `Node`. CNI-плагин на узле затем использует стандартный IPAM-плагин `host-local`. Этот плагин считывает выделенный `podCIDR` для своей ноды и самостоятельно управляет выдачей IP-адресов из этого диапазона, сохраняя информацию о занятых IP в локальных файлах на диске узла (обычно в `/var/lib/cni/networks/`). Это простой и самый распространенный механизм.

- **IPAM, интегрированный в CNI (например, `calico-ipam`):** Является альтернативой `host-local`. Для его активации (в случае Calico) необходимо запустить `kube-controller-manager` с флагом `--allocate-node-cidrs=false`. В этом режиме Calico полностью берет на себя управление IP-адресами.

#### Ресурс `IPPool` в Calico

`calico-ipam` управляет адресами через кастомный ресурс `IPPool`.

```yaml
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: default-ipv4-ippool
spec:
  cidr: 192.168.0.0/16
  blockSize: 26
  natOutgoing: true
  disabled: false
```

- **`cidr`**: Общий пул адресов для подов, аналог `podCIDR`.
- **`blockSize`**: Размер блока адресов, который выделяется узлу. По умолчанию `26` (64 адреса). Это позволяет более гибко и экономно распределять адреса по сравнению с жестким `/24` в Kubernetes.
- **`natOutgoing`**: Если `true`, для трафика, идущего из подов этого пула во внешнюю сеть, будет применяться `MASQUERADE` (NAT). Это стандартное поведение для скрытия внутренних IP-адресов подов.
- **Диагностика**: Состояние выделенных блоков и адресов можно проверить с помощью утилиты `calicoctl`:

    ```bash
    calicoctl ipam show
    ```

#### Поддержка Dual-Stack (IPv4/IPv6)

Kubernetes и CNI-плагины, такие как Calico, поддерживают **dual-stack** режим, позволяя подам иметь одновременно IPv4 и IPv6 адреса.

- **Настройка Kubernetes:** При инициализации кластера необходимо указать два диапазона `pod-network-cidr` — один для IPv4, другой для IPv6 (например, `--pod-network-cidr=10.244.0.0/16,fd00:10:244::/48`). Также необходимо указать `service-cluster-ip-range` для обоих семейств.
- **Настройка CNI:**
  - **`host-local` IPAM:** Будет управлять двумя отдельными файлами состояний для каждого семейства адресов.
  - **`calico-ipam`:** Необходимо создать два ресурса `IPPool`, по одному для каждого семейства (IPv4 и IPv6). Calico автоматически назначит поду по одному адресу из каждого пула.

**Пример `IPPool` для IPv6:**

```yaml
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: default-ipv6-ippool
spec:
  cidr: fd00:10:244::/48
  blockSize: 122
  natOutgoing: false # NAT обычно не используется в IPv6
  disabled: false
```

Это позволит подам напрямую общаться по IPv6 без NAT.

## Практические сценарии

### Выбор CNI-плагина и режима работы

| Критерий | Flannel | Calico | Calico (eBPF) / Cilium |
| :--- | :--- | :--- | :--- |
| **Сложность настройки** | Простая | Средняя | Средняя/Высокая |
| **NetworkPolicy** | Нет | Да | Да (более эффективно) |
| **Производительность** | Средняя (overlay) | Высокая (BGP) | Очень высокая |
| **Замена kube-proxy** | Нет | Нет | Да |
| **Режим работы** | Overlay (VXLAN) | Overlay/BGP | eBPF/Direct Routing |

### Установка Calico с eBPF (для нового кластера)

> **Внимание:** Приведенные ниже команды и конфигурации являются примером. Всегда сверяйтесь с официальной документацией Calico для получения актуальной версии манифестов и инструкций, соответствующих вашей версии Kubernetes.

Миграция существующего кластера на eBPF является сложной и рискованной процедурой. Рекомендуемый подход — установка нового кластера сразу в режиме eBPF.

**Шаг 1: Инициализация кластера без `kube-proxy`**

При инициализации master-ноды с помощью `kubeadm`, необходимо пропустить установку `kube-proxy`.

```bash
sudo kubeadm init --skip-phases=addon/kube-proxy
```

**Шаг 2: Подготовка манифеста Calico**

1. Скачайте официальный манифест `calico.yaml` с сайта проекта Calico.
2. **Настройте `podCIDR`**: Убедитесь, что `CALICO_IPV4POOL_CIDR` в манифесте соответствует `pod-network-cidr`, указанному при инициализации кластера.
3. **Включите VXLAN**: Для максимальной совместимости и лучшей производительности с eBPF рекомендуется использовать режим VXLAN.

    ```yaml
    # В ConfigMap 'calico-config'
    - name: CALICO_IPV4POOL_IPIP
      value: "Never"
    - name: CALICO_IPV4POOL_VXLAN
      value: "Always"
    ```

**Шаг 3: Развертывание Calico**

Примените модифицированный манифест `calico.yaml`.

```bash
kubectl apply -f calico.yaml
```

**Шаг 4: Включение режима eBPF**

Создайте ресурс `FelixConfiguration`, чтобы активировать eBPF.

```yaml
# felix-config.yaml
apiVersion: projectcalico.org/v3
kind: FelixConfiguration
metadata:
  name: default
spec:
  bpfEnabled: true
```

Примените его с помощью утилиты `calicoctl` или `kubectl`.

```bash
# Убедитесь, что у вас настроен calicoctl
calicoctl apply -f felix-config.yaml
# или
kubectl apply -f felix-config.yaml
```

После этого Calico перезапустит свои компоненты (`calico-node`) и начнет работать в режиме eBPF.

### Диагностика и проверка

1. **Проверка отсутствия `kube-proxy`**: Убедитесь, что в `kube-system` нет подов `kube-proxy`.
2. **Проверка отсутствия `ipvs`**: На узлах кластера не должен быть виден интерфейс `kube-ipvs0`.
3. **Проверка файловой системы BPF**: Убедитесь, что на узлах смонтирована файловая система `bpf`.

    ```bash
    mount | grep bpf
    # Ожидаемый вывод: none on /sys/fs/bpf type bpf (rw,relatime)
    ```

4. **Просмотр NAT-таблицы eBPF**: Для отладки можно зайти в под `calico-node` и выполнить команду, чтобы увидеть, как eBPF обрабатывает трансляцию адресов.

    ```bash
    kubectl exec -it -n kube-system <calico-node-pod> -- calico-node bpf nat dump
    ```
