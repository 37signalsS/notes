### `LoadBalancer`

- **Описание:** Создает внешний балансировщик нагрузки у облачного провайдера (AWS, GCP, Azure), который получает публичный IP-адрес и направляет трафик с него на `Service`. Является расширением `NodePort` и `ClusterIP` (трафик сначала попадает на `NodePort`, а затем на `ClusterIP`). Облачный балансировщик также обеспечивает **health-check-и** на уровне провайдера.
- **Использование:** Стандартный способ публикации сервисов в интернет в облачных средах.

### `externalTrafficPolicy: Local`

Как и в случае с `NodePort`, `LoadBalancer` по умолчанию скрывает реальный IP-адрес клиента. Установка `spec.externalTrafficPolicy: Local` позволяет сохранить исходный IP, направляя трафик только на поды, расположенные на том же узле, на который балансировщик провайдера отправил запрос. Это стандартная практика для получения IP клиента в веб-приложениях, опубликованных через `LoadBalancer`.

Сервис `LoadBalancer` отлично подходит для публикации вашего приложения, но с небольшой оговоркой: "из коробки" он работает только в облачных провайдерах (таких как Amazon, Google, Azure), которые предоставляют возможность работы с этим типом сервисов.

**Для локальных (On-Premise) кластеров** эту функциональность можно получить с помощью **[MetalLB](../Addons/metallb.md)**, который эмулирует облачный балансировщик в вашей собственной сети.

Механика работы этого сервиса следующая:
Снаружи кластера существует контроллер, который отслеживает API-сервер и контролирует создание новых сервисов типа `LoadBalancer`. Когда такой сервис создается, этот контроллер создает внешний балансировщик (например, Elastic Load Balancer в AWS), который, в свою очередь, отправляет трафик внутрь кластера на данный сервис вашего приложения. Если такого контроллера нет (например, в bare-metal кластере без MetalLB), `LoadBalancer` будет находиться в состоянии `Pending` и не будет работать корректно.

#### Недостатки и ограничения

Несмотря на удобство, у `LoadBalancer` есть существенные ограничения:

- **Маршрутизация только на L4:** `LoadBalancer` работает на транспортном уровне и может перенаправлять только TCP/UDP трафик. Он не "понимает" HTTP-запросы и не может выполнять сложную маршрутизацию на основе хоста или пути.
- **Один IP-адрес на сервис:** Каждый `Service` типа `LoadBalancer` требует выделения отдельного, уникального IP-адреса. В крупных проектах с десятками микросервисов это приводит к быстрому исчерпанию доступных IP-адресов и дополнительным затратам.

Из-за этих ограничений для публикации HTTP/HTTPS-приложений в подавляющем большинстве случаев используется [Ingress](./ingress.md), который работает на уровне L7 и позволяет управлять доступом к множеству сервисов через один IP-адрес.

**Пример манифеста `LoadBalancer` Service:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-lb
spec:
  selector:
    app: my-app
  type: LoadBalancer
  ports:
    - name: http
      port: 80
      targetPort: 80
      protocol: TCP
```

**Использование статического IP-адреса:**
В `LoadBalancer` также есть возможность задавать статический IP-адрес в поле `loadBalancerIP`. Этот IP-адрес будет передан внешнему балансировщику, который будет отправлять трафик на этот IP-адрес в ваше приложение.

**Пример манифеста `LoadBalancer` Service со статическим IP:**

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-lb
spec:
  selector:
    app: my-app
  type: LoadBalancer
  loadBalancerIP: "1.1.1.1" # Пример статического IP-адреса
  ports:
    - name: http
      port: 80
      targetPort: 80
      protocol: TCP
```
