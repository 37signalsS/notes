# Тип Service — ClusterIP

## Определения

**ClusterIP** — базовый тип Service в Kubernetes, предоставляющий стабильный внутренний IP-адрес, доступный только внутри кластера. Это тип по умолчанию для любого создаваемого сервиса.

**Основная задача:** Обеспечение постоянной точки входа для взаимодействия компонентов приложения внутри кластера, скрывающей динамические IP-адреса отдельных подов.

## Основные концепции

### Принцип работы

Процесс реализации ClusterIP включает следующие этапы:

1. **Назначение VIP:** Kubernetes выделяет виртуальный IP (Virtual IP) из диапазона, определенного флагом API-сервера `--service-cluster-ip-range` (по умолчанию `10.96.0.0/12`).
2. **DNS-регистрация:** DNS-сервер кластера (CoreDNS) создает запись вида `<service>.<namespace>.svc.cluster.local`, указывающую на этот VIP.
3. **Маршрутизация:** Компонент `kube-proxy` на каждом узле настраивает правила (iptables или IPVS), которые перехватывают трафик, направленный на VIP, и выполняют **DNAT** (Destination NAT) на реальные IP-адреса подов.

### Ключевые правила взаимодействия

- **Селекторы:** Связь с подами устанавливается через селектор меток (`selector`), который должен точно соответствовать меткам (`labels`) целевых подов.
- **Область видимости:** Сервис доступен по короткому имени внутри своего пространства имен (Namespace). Для обращения из других пространств имен необходимо использовать полное доменное имя (FQDN).

### Особенности и Session Affinity

По умолчанию балансировка трафика осуществляется по алгоритму round-robin (в режиме iptables — случайный выбор с равным весом). Для обеспечения привязки клиента к конкретному поду используется механизм **Session Affinity**.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: sticky-service
spec:
  selector:
    app: my-app
  sessionAffinity: ClientIP  # Привязка сессии по IP-адресу клиента
  ports:
    - port: 80
      targetPort: 8080
```

Данная настройка полезна для stateful-приложений, систем кэширования сессий на уровне приложения или работы с WebSocket.

## Практические сценарии

### Пример манифеста

```yaml
apiVersion: v1
kind: Service
metadata:
  name: internal-app-service
spec:
  selector:
    app: internal-app
  # type: ClusterIP можно опустить, так как это значение по умолчанию
  ports:
    - name: http
      protocol: TCP
      port: 80         # Внутренний порт сервиса
      targetPort: 8080 # Порт приложения в контейнере
```

### Сценарии использования

- **Межсервисное взаимодействие:** Связь между фронтендом и бэкендом или бэкендом и базой данных.
- **Внутренние API:** Сервисы, предназначенные исключительно для служебного использования внутри инфраструктуры.
- **Обнаружение сервисов:** Использование стабильных имен DNS вместо динамических IP.

### Доступ для отладки

Для временного доступа к внутреннему сервису с локальной машины разработчика используется команда `port-forward`:

```bash
kubectl port-forward service/internal-app-service 8080:80
# → Forwarding from 127.0.0.1:8080 -> 80
```

После выполнения команды сервис будет доступен по адресу `http://localhost:8080`.

## Дополнительная информация

### Иерархия и ограничения

ClusterIP служит фундаментом для более сложных типов доступа:

- [NodePort](./service_type_nodeport.md) — расширяет ClusterIP, открывая порт на узлах.
- [LoadBalancer](./service_type_loadbalancer.md) — расширяет NodePort, интегрируясь с облачным балансировщиком.

**Основные ограничения:**

- **Отсутствие внешнего доступа:** Трафик извне кластера не может попасть напрямую на ClusterIP.
- **L4-балансировка:** Работает на транспортном уровне; для маршрутизации на основе HTTP-путей или хостов требуется [Ingress](../Ingress/overview.md).
