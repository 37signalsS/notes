# Тип Service — ClusterIP

## Определения

**ClusterIP** — это тип службы по умолчанию в Kubernetes. Он предоставляет сервису стабильный внутренний IP-адрес, доступный только внутри кластера. Это основной механизм для обеспечения связности между внутренними компонентами системы.

**Основная задача:** Обеспечение постоянной точки входа для взаимодействия компонентов приложения внутри кластера, скрывающей динамические IP-адреса отдельных подов. Благодаря динамическому назначению IP-адресов и автоматическому масштабированию, ClusterIP обеспечивает надежную конечную точку для общения.

## Основные концепции

### Механика и принцип работы

Реализация ClusterIP базируется на создании виртуального IP-адреса (VIP), который не привязан к конкретному сетевому интерфейсу, а управляется на уровне ядра узлов:

1. **EndpointSlice:** Kubernetes отслеживает готовность подов через селекторы и сохраняет их IP-адреса в объектах `EndpointSlice` (современная замена устаревшим `Endpoints`). Это обеспечивает масштабируемость для кластеров с тысячами подов.
2. **Kube-proxy:** На каждом узле компонент `kube-proxy` считывает данные из `EndpointSlice` и настраивает правила пересылки трафика.
3. **DNS-регистрация:** CoreDNS создает A/AAAA запись для сервиса: `<name>.<ns>.svc.cluster.local`, указывающую на VIP.

### Режимы работы kube-proxy

Алгоритм балансировки и производительность зависят от режима работы `kube-proxy`:

- **iptables:** Режим по умолчанию. Использует цепочки правил в ядре. Балансировка выполняется случайным образом (`statistic mode`), что может быть неэффективно при огромном количестве сервисов.
- **IPVS:** Использует транспортную балансировку на уровне ядра (Hash tables). Поддерживает различные алгоритмы (Round-robin, Least Connection) и работает значительно быстрее в крупных кластерах.
- **nftables:** Современный режим (доступен в новых версиях K8s), заменяющий `iptables` более эффективным механизмом обработки пакетов.

### Управление трафиком и топология

Для оптимизации задержек и стоимости трафика используются следующие механизмы:

- **internalTrafficPolicy:**
    - `Cluster` (по умолчанию): трафик может уйти на любой под в кластере.
    - `Local`: трафик направляется только на поды, находящиеся на том же узле, где инициирован запрос. Если подов на узле нет, запрос будет отброшен.
- **Topology Aware Hints:** Позволяет направлять трафик на поды, находящиеся в той же зоне доступности (Availability Zone), что и клиент, снижая межзональные задержки.

### Поддержка Dual-stack (IPv4/IPv6)

ClusterIP поддерживает работу в сетях с обоими протоколами. Настройка выполняется через поля:
- `ipFamilyPolicy`: `SingleStack`, `PreferDualStack` или `RequireDualStack`.
- `ipFamilies`: список семейств IP (например, `["IPv4", "IPv6"]`), определяющий порядок выделения адресов.

## Практические сценарии

### Пример манифеста

Стандартный манифест для внутреннего взаимодействия. Тип `ClusterIP` используется по умолчанию, поэтому его можно не указывать явно.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: internal-app-service
spec:
  selector:
    app: internal-app
  ports:
    - name: http
      protocol: TCP
      port: 80         # Внутренний порт сервиса
      targetPort: 8080 # Порт приложения в контейнере
```

### Настройка Session Affinity

Используется для привязки клиента к конкретному поду (например, для WebSocket или кэширования сессий).

```yaml
apiVersion: v1
kind: Service
metadata:
  name: session-aware-service
spec:
  selector:
    app: web
  sessionAffinity: ClientIP
  sessionAffinityConfig:
    clientIP:
      timeoutSeconds: 10800 # Время жизни привязки в секундах (по умолчанию 10800)
  ports:
    - port: 80
      targetPort: 8080
```

### Сценарии использования

- **Межсервисное взаимодействие:** Стабильная точка входа для связи фронтенда с бэкендом. Фронтенд может надежно подключаться к серверной службе, используя DNS-имя или ClusterIP, независимо от изменений IP-адресов отдельных подов или событий масштабирования.
- **Микросервисная архитектура:** Каждый микросервис представляется как ClusterIP, что обеспечивает их изоляцию внутри кластера. Отсутствие прямого доступа извне повышает общую безопасность системы и снижает риск атак.
- **Обнаружение сервисов (Service Discovery):** Позволяет компонентам динамически находить друг друга и взаимодействовать. Для поиска и подключения к другим службам через их ClusterIP используются Kubernetes DNS или переменные окружения.
- **Sidecar-коммуникации:** Использование `internalTrafficPolicy: Local` для взаимодействия основного контейнера с локальными агентами или прокси (например, Envoy), минимизируя сетевые задержки.
- **Высоконагруженные системы:** Использование режима `IPVS` для эффективной балансировки тысяч сервисов без деградации производительности `iptables`.

### Доступ для отладки

Для временного доступа к внутреннему сервису с локальной машины разработчика (например, при отладке API) используется команда `port-forward`:

```bash
kubectl port-forward service/internal-app-service 8080:80
# → Forwarding from 127.0.0.1:8080 -> 80
```

После выполнения команды сервис будет доступен по адресу `http://localhost:8080`.

## Дополнительная информация

### Иерархия и ограничения

ClusterIP служит фундаментом для более сложных типов доступа:

- [NodePort](./service_type_nodeport.md) — расширяет ClusterIP, открывая порт на узлах.
- [LoadBalancer](./service_type_loadbalancer.md) — расширяет NodePort, интегрируясь с облачным балансировщиком.

**Основные ограничения:**

- **Отсутствие внешнего доступа:** Трафик извне кластера не может попасть напрямую на ClusterIP.
- **L4-балансировка:** Работает на транспортном уровне; для маршрутизации на основе HTTP-путей или хостов требуется [Ingress](../Ingress/overview.md).
