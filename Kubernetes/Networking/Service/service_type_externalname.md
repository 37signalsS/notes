# Тип Service — ExternalName

## Определения

**ExternalName** — специальный тип Service в Kubernetes, который выполняет роль DNS-псевдонима. Вместо проксирования трафика через сетевой стек кластера (kube-proxy), он возвращает клиенту CNAME-запись, указывающую на внешнее доменное имя.

**Ключевое отличие:** Это единственный тип сервиса, который не имеет виртуального IP-адреса (ClusterIP), не использует селекторы подов и не создает эндпоинты (Endpoints/EndpointSlices).

## Основные концепции

### Механика работы

При обращении клиента к сервису типа ExternalName (например, по имени `my-service.prod.svc.cluster.local`), внутренний DNS-сервер (CoreDNS) не возвращает IP-адрес, а выдает ответ типа CNAME с адресом, указанным в поле `externalName`.

**Процесс разрешения:**
1. Приложение запрашивает DNS-имя сервиса.
2. CoreDNS находит запись типа `ExternalName` в своей конфигурации.
3. CoreDNS возвращает CNAME, указывающий на внешний ресурс (например, `db.external.com`).
4. Клиентское приложение (или его OS-резолвер) выполняет второй запрос для разрешения `db.external.com` в реальный IP-адрес.
5. Клиент устанавливает прямое соединение с полученным внешним IP.

### Характеристики и особенности

- **Минимальные накладные расходы:** Трафик идет напрямую от пода к внешнему ресурсу, не нагружая `kube-proxy` и не проходя через NAT.
- **Работа на уровне DNS:** Весь механизм реализован исключительно через конфигурацию CoreDNS.
- **Протокольная независимость:** Работает для TCP, UDP и любых L7-протоколов (HTTP, gRPC, базы данных).
- **Динамическое управление:** Позволяет менять внешний адрес зависимости (например, при переезде с одного облачного региона на другой) без перезапуска приложений.

## Практические сценарии

### Пример манифеста

```yaml
apiVersion: v1
kind: Service
metadata:
  name: cloud-db
  namespace: development
spec:
  type: ExternalName
  externalName: rds-instance-01.cxyz.eu-central-1.rds.amazonaws.com
```

### Тонкости работы с HTTP и SSL/TLS

Использование `ExternalName` для HTTP-сервисов (HTTPS API, внешние веб-сервисы) часто приводит к ошибкам из-за несоответствия имен:

1. **Заголовок Host:** При обращении к `http://cloud-db/` клиент отправляет заголовок `Host: cloud-db`. Внешний сервер (например, Nginx или Cloudflare) может отклонить запрос, так как ожидает `Host: rds-instance-01...`.
2. **SSL/TLS и SNI:** При установке защищенного соединения клиент отправляет имя сервиса (`cloud-db`) в поле SNI (Server Name Indication). Если внешний сервер использует сертификат только для своего реального имени, проверка SSL завершится ошибкой `Hostname mismatch`.

**Решение:** Для HTTP-зависимостей может потребоваться промежуточный прокси (например, Nginx Ingress или Sidecar), который будет подменять заголовок `Host` и переписывать SNI.

### Типовые сценарии использования

- **Managed-базы данных:** Обращение к RDS, Cloud SQL или Redis по коротким именам.
- **Внешние API:** Абстрагирование URL сторонних шлюзов (платежные системы, SMS-сервисы).
- **Миграция "Legacy -> K8s":** Постепенный перенос компонентов из старой инфраструктуры с сохранением имен.
- **Разделение сред:** `db-service` в namespace `dev` указывает на локальную БД, а в `prod` — на `ExternalName` в облаке.

## Дополнительная информация

### Сравнение подходов к внешним ресурсам

| Характеристика | ExternalName | Service без селектора + Endpoints |
| :--- | :--- | :--- |
| **Основа** | DNS (CNAME) | IP (DNAT) |
| **Цель** | Внешнее доменное имя | Внешний статический IP |
| **Проксирование** | Нет | Да (kube-proxy) |
| **Health Checks** | Нет | Опционально (через контроллеры) |

### Ограничения и риски

- **Кеширование DNS:** TTL ответов CoreDNS и настройки кеширования внутри приложений могут замедлить применение изменений при смене `externalName`.
- **Проблемы с виртуальными хостами:** Описанные выше сложности с SNI и `Host` заголовками.
- **Отсутствие прозрачности:** Трафик не виден в сетевых политиках (NetworkPolicies) кластера, так как идет напрямую на внешние IP.
- **IPv4/IPv6:** Некоторые клиенты могут испытывать трудности с разрешением CNAME, если внешний ресурс доступен только по протоколу, отличному от стека кластера.

### Диагностика

Для проверки работы сервиса используйте `dig` или `nslookup` изнутри пода:

```bash
nslookup cloud-db.development.svc.cluster.local
# → Server:    10.96.0.10
# → Address:   10.96.0.10#53
# →
# → cloud-db.development.svc.cluster.local canonical name = rds-instance-01.amazonaws.com.
```
