# ExternalName

## Определения

**ExternalName** — специальный тип `Service`, который не проксирует трафик, а возвращает CNAME-запись во внутреннем DNS кластера. Сопоставляет сервис с внешним DNS-именем, позволяя приложениям внутри кластера обращаться к внешнему ресурсу через внутреннее имя сервиса.

**Ключевое отличие:** Единственный тип сервиса, который не имеет `ClusterIP` и не управляет подами.

## Основные концепции

### Принцип работы

При обращении к сервису типа `ExternalName` по его имени (например, `my-external-db`), DNS-сервер кластера (CoreDNS) возвращает CNAME-запись с адресом, указанным в поле `externalName`. Трафик идёт напрямую к внешнему ресурсу, минуя `kube-proxy` и внутреннюю балансировку Kubernetes.

**Цель:** Скрыть реальный адрес внешнего ресурса и упростить конфигурацию приложений.

### Ключевые особенности

| Особенность | Описание |
| :--- | :--- |
| **Нет ClusterIP** | Не имеет внутреннего IP-адреса, не занимается проксированием |
| **Нет селекторов** | Не привязан к подам внутри кластера |
| **Только DNS** | Весь механизм основан исключительно на DNS-разрешении |
| **Нет балансировки** | Трафик идёт напрямую к внешнему ресурсу |

### Спецификация

| Поле | Описание | Пример |
| :--- | :--- | :--- |
| `type` | Тип сервиса | `ExternalName` |
| `externalName` | Внешний DNS-имя для маппинга | `my.database.example.com` |
| `selector` | Не применяется | — |
| `clusterIP` | Не применяется | — |

## Практические сценарии

### Пример манифеста

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-external-service
  namespace: default
spec:
  type: ExternalName
  externalName: my.database.example.com
```

Запросы к `my-external-service.default.svc.cluster.local` перенаправляются на `my.database.example.com`.

### Распространённые use-case

| Сценарий | Описание |
| :--- | :--- |
| **Управляемые БД** | Доступ к AWS RDS, Google Cloud SQL по внутреннему имени |
| **Внешние API** | Обращение к сторонним API как к внутренним сервисам |
| **Миграция** | Временное обращение к компонентам вне кластера во время миграции |
| **Абстракция** | Скрытие реальных адресов внешних зависимостей |

### Пример использования в приложении

```yaml
# Deployment обращается к сервису по внутреннему имени
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  template:
    spec:
      containers:
      - name: app
        image: my-app:latest
        env:
        - name: DATABASE_HOST
          value: "my-external-service.default.svc.cluster.local"
```

Приложение использует внутреннее DNS-имя, не зная реального адреса БД.

## Дополнительная информация

### Сравнение с другими типами

| Характеристика | ExternalName | ClusterIP | NodePort |
| :--- | :--- | :--- | :--- |
| **Проксирование** | Нет | Да | Да |
| **ClusterIP** | Нет | Да | Да |
| **Селекторы** | Нет | Да | Да |
| **Уровень** | DNS | L4 | L4 |
| **Внешний доступ** | К внешним ресурсам | Только внутри | Через узел |

### Ограничения

| Ограничение | Описание |
| :--- | :--- |
| **Только DNS** | Не работает без корректной DNS-инфраструктуры в кластере |
| **Нет балансировки** | Нельзя распределить трафик между несколькими внешними адресами |
| **Нет health checks** | Kubernetes не проверяет доступность внешнего ресурса |
| **Один externalName** | Один сервис = одно внешнее имя (нельзя указать несколько) |

### Альтернативы

- **Endpoints без селектора:** Для внешнего IP без DNS (ручное управление endpoints)
- **Service + CNI:** Для сложных сценариев маршрутизации внешнего трафика

> **Сводка:** Полное сравнение всех типов сервисов см. в [Сводке по типам сервисов](./service_types_summary.md).
