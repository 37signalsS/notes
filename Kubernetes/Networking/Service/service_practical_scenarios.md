# Практический сценарий: публикация приложения

В этом сценарии мы опубликуем `Deployment` с веб-сервером Nginx, используя два разных типа `Service`: сначала `ClusterIP` для внутренней доступности, а затем преобразуем его в `NodePort` для предоставления доступа извне кластера.

Предполагается, что у вас уже есть работающий `Deployment` с именем `nginx-deployment`, который управляет подами с меткой `app: nginx`.

## Шаг 1: Публикация через ClusterIP (внутренний доступ)

Сначала создадим сервис типа **[ClusterIP](./service_type_clusterip.md)**. Это позволит другим приложениям внутри кластера обращаться к нашему Nginx, но не будет открывать доступ наружу.

### Манифест Service

```yaml
# nginx-service.yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  # Селектор должен совпадать с метками подов нашего Deployment
  selector:
    app: nginx

  # type: ClusterIP можно не указывать, т.к. это значение по умолчанию
  type: ClusterIP

  ports:
    - name: http
      protocol: TCP
      # port: порт, на котором сервис будет доступен внутри кластера
      port: 8080
      # targetPort: порт на подах, куда будет перенаправляться трафик
      targetPort: 80
```

### Создание и проверка

1. **Применяем манифест:**

    ```bash
    kubectl apply -f nginx-service.yaml
    # service/nginx-service created
    ```

2. **Проверяем сервис:**

    ```bash
    kubectl get service nginx-service
    # NAME            TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)    AGE
    # nginx-service   ClusterIP   10.104.117.48   <none>        8080/TCP   30s
    ```

    Сервису был присвоен внутренний IP-адрес `10.104.117.48`.

3. **Проверка доступа (изнутри кластера):**
    Чтобы проверить доступ, можно зайти на одну из нод кластера или в любой под и выполнить `curl`.

    ```bash
    # Запрос на виртуальный IP сервиса и его порт
    curl 10.104.117.48:8080
    ```

    В ответ вы должны получить стандартную приветственную страницу Nginx. `kube-proxy` перехватит этот запрос и сбалансирует его на один из работающих подов `nginx-deployment`.

## Шаг 2: Преобразование в NodePort (внешний доступ)

Теперь изменим тип сервиса на **[NodePort](./service_type_nodeport.md)**, чтобы получить доступ к приложению извне.

### Изменение манифеста

Отредактируем файл `nginx-service.yaml`, указав тип `NodePort` и желаемый порт.

```yaml
# nginx-service.yaml (обновленная версия)
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx

  # 1. Меняем тип сервиса
  type: NodePort

  ports:
    - name: http
      protocol: TCP
      port: 8080
      targetPort: 80
      # 2. Указываем конкретный NodePort
      #    Если не указать, будет выбран случайный порт из диапазона 30000-32767
      nodePort: 30080
```

### Обновление и проверка

1. **Применяем измененный манифест:**

    ```bash
    kubectl apply -f nginx-service.yaml
    # service/nginx-service configured
    ```

2. **Проверяем сервис еще раз:**

    ```bash
    kubectl get service nginx-service
    # NAME            TYPE       CLUSTER-IP      EXTERNAL-IP   PORT(S)          AGE
    # nginx-service   NodePort   10.104.117.48   <none>        8080:30080/TCP   5m
    ```

    Обратите внимание:
    * Тип изменился на `NodePort`.
    * Внутренний `CLUSTER-IP` остался прежним.
    * В секции `PORT(S)` появилось сопоставление `8080:30080`, где `30080` — это порт, открытый на всех узлах кластера.

3. **Проверка доступа (снаружи кластера):**
    Теперь вы можете обратиться к приложению, используя IP-адрес **любой ноды** вашего кластера и порт `30080`.

    ```bash
    # Предположим, IP-адреса ваших нод: 192.168.1.10, 192.168.1.11, 192.168.1.12

    # Запрос на первую ноду
    curl http://192.168.1.10:30080

    # Запрос на вторую ноду
    curl http://192.168.1.11:30080

    # Запрос на третью ноду
    curl http://192.168.1.12:30080
    ```

    Каждый из этих запросов вернет страницу Nginx. Это демонстрирует главный принцип `NodePort`: он открывает один и тот же порт на всех узлах и перенаправляет трафик на нужные поды, независимо от того, на каком узле они запущены.
