# Тип Service — NodePort

## Определения

**NodePort** — тип Service в Kubernetes, который открывает статический порт на каждом узле кластера. Трафик, поступающий на любой узел по этому порту (`NodeIP:NodePort`), автоматически перенаправляется на соответствующие поды.

NodePort является надстройкой над [ClusterIP](./service_type_clusterip.md), добавляя возможность внешнего доступа к сервису через IP-адреса узлов.

## Основные концепции

### Принцип работы

При создании Service типа NodePort происходят следующие процессы:
1. Автоматически создается внутренний [ClusterIP](./service_type_clusterip.md).
2. На каждом узле кластера резервируется порт из диапазона **30000–32767**.
3. Компонент `kube-proxy` настраивает правила (iptables или IPVS) для перенаправления входящего трафика с `NodePort` на `ClusterIP` сервиса.
4. Далее трафик балансируется между подами согласно селектору.

### Диапазон портов

- **По умолчанию:** 30000–32767.
- **Настройка:** Диапазон можно изменить через флаг API-сервера `--service-node-port-range`.

### Политика внешнего трафика (externalTrafficPolicy)

Поле `externalTrafficPolicy` определяет, как обрабатывается трафик, приходящий на узел.

#### Режим Cluster (по умолчанию)
Трафик, пришедший на `NodePort` одного узла, может быть перенаправлен на под, находящийся на *другом* узле.
- **Минусы:** Выполняется SNAT (Source Network Address Translation), из-за чего внутри пода виден IP-адрес узла, а не реальный IP клиента. Возникает лишний сетевой прыжок (hop) между узлами.

#### Режим Local
Трафик направляется **только на те поды, которые находятся на том же узле**, куда пришел запрос.
- **Плюсы:** Сохраняется исходный IP-адрес клиента (отсутствует SNAT). Исключается лишний межсетевой трафик.
- **Минусы:** Если на узле нет локальных подов, трафик будет отброшен. Возможна неравномерная нагрузка, если количество подов на узлах различается.

### Проблема SNAT и возврат трафика

В стандартном режиме (`Cluster`) CNI-плагины (например, Calico или Flannel) используют SNAT для корректной маршрутизации обратных пакетов. Это скрывает реальный адрес источника, что критично для систем аудита, геолокации или ограничения доступа по IP. Для решения этих задач рекомендуется использовать `externalTrafficPolicy: Local`.

## Практические сценарии

### Пример манифеста

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-nodeport
spec:
  type: NodePort
  selector:
    app: my-app
  ports:
    - name: http
      protocol: TCP
      port: 80         # Внутренний порт сервиса
      targetPort: 8080 # Порт приложения в контейнере
      # nodePort: 30080  # Опционально: статический порт
```

### Сценарии использования

- **Разработка и тестирование:** Самый простой способ получить доступ к приложению извне без настройки Ingress.
- **On-premise кластеры:** Публикация сервисов в средах, где нет облачного LoadBalancer.
- **Не-HTTP приложения:** Публикация TCP/UDP сервисов (базы данных, брокеры сообщений).
- **Бэкенд для внешних балансировщиков:** Когда внешний аппаратный балансировщик направляет трафик на список `NodeIP:NodePort`.

## Дополнительная информация

### Ограничения

- **Нестандартные порты:** Пользователи вынуждены использовать порты из высокого диапазона (30000+).
- **Зависимость от IP узлов:** Если IP узла изменится или узел выйдет из строя, внешним клиентам потребуется обновить настройки подключения.
- **Безопасность:** Открытие портов на узлах увеличивает поверхность атаки и требует настройки firewall.

### Сравнение с другими типами

| Характеристика | NodePort | LoadBalancer | Ingress (L7) |
| :--- | :--- | :--- | :--- |
| **Уровень OSI** | L4 (TCP/UDP) | L4 (TCP/UDP) | L7 (HTTP/HTTPS) |
| **Порты** | 30000–32767 | Любые (80, 443) | Любые (80, 443) |
| **IP-адрес** | IP узлов | Выделенный внешний IP | IP Ingress Controller |
| **Облако** | Не требуется | Требуется провайдер | Требуется контроллер |
