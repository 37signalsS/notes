# NodePort

## Определения

**NodePort** — тип Service, который открывает статический порт в диапазоне **30000-32767** на **каждом узле** кластера. Трафик, приходящий на `NodeIP:NodePort`, перенаправляется на `Service`.

NodePort расширяет [ClusterIP](./service_type_clusterip.md), добавляя возможность внешнего доступа через IP-адрес любого узла кластера.

## Основные концепции

### Принцип работы

При создании Service типа NodePort:

1. Kubernetes создает внутренний ClusterIP (как у обычного сервиса)
2. На каждом узле открывается порт из диапазона 30000-32767
3. `kube-proxy` настраивает правила для перенаправления трафика с `NodePort` на `ClusterIP`
4. Трафик распределяется между Pod, соответствующими селектору

### Диапазон портов

- **По умолчанию:** 30000-32767
- **Настройка:** Можно изменить в конфигурации API-сервера флагами `--service-node-port-range`

### externalTrafficPolicy: Local (SSoT)

По умолчанию (`externalTrafficPolicy: Cluster`), трафик, пришедший на `NodePort` одного узла, может быть перенаправлен на под, работающий на *другом* узле.

**Недостатки режима Cluster (по умолчанию):**
1. **Теряется IP-адрес клиента:** Внутри пода виден IP-адрес узла, а не реальный IP клиента
2. **Лишний сетевой "хоп":** Трафик проходит дополнительный путь между узлами

**Режим Local:**

```yaml
spec:
  externalTrafficPolicy: Local
```

При установке `externalTrafficPolicy: Local`:
- `kube-proxy` отправляет трафик **только на поды, работающие на том же узле**, куда изначально пришел запрос
- **Сохраняется исходный IP-адрес клиента**
- Возможна неравномерная балансировка, если поды распределены по узлам неравномерно

**Применение:**
- Приложения, которым нужен реальный IP-адрес для логирования, аналитики или геолокации
- Публикация через [LoadBalancer](./service_type_loadbalancer.md) (см. ссылку на этот раздел)

## Практические сценарии

### Пример манифеста

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-np
spec:
  # 1. Тип сервиса. Если не указан, по умолчанию используется ClusterIP.
  type: NodePort

  # 2. Селектор для выбора Pod'ов, на которые пойдет трафик.
  #    Должен соответствовать меткам в шаблоне Deployment, ReplicaSet и т.д.
  selector:
    app: my-app

  # 3. Описание портов.
  ports:
    - name: http
      protocol: TCP
      # port: Внутренний порт, на котором Service принимает трафик внутри кластера.
      port: 80
      # targetPort: Порт на Pod'ах, куда будет перенаправляться трафик.
      targetPort: 80
      # nodePort: Статический порт на узлах (только для типа NodePort).
      # Если не указать, будет выбран случайный из диапазона 30000-32767.
      # nodePort: 30080
```

### Цепочка обработки трафика

```
Client → NodeIP:NodePort → kube-proxy → ClusterIP → Pod
```

### Распространенные use-case

- **Разработка и отладка:** Быстрый доступ к приложению без настройки Ingress
- **On-premise кластеры:** Альтернатива LoadBalancer в локальных средах
- **TCP/UDP сервисы:** Публикация не-HTTP приложений (RabbitMQ, базы данных)
- **Бэкенд для внешнего балансировщика:** Внешний LB перенаправляет трафик на `NodeIP:NodePort`

## Дополнительная информация

### Ограничения

| Ограничение | Описание |
|-------------|----------|
| **Диапазон портов** | Ограничен 30000-32767 (неудобные порты для пользователей) |
| **Зависимость от IP узла** | При изменении IP узла доступ теряется |
| **Безопасность** | Прямой доступ к узлам требует настройки firewall |

### Сравнение с LoadBalancer

| Критерий | NodePort | LoadBalancer |
|----------|----------|--------------|
| **Сложность** | Просто | Требует облачного провайдера или MetalLB |
| **Порт** | Высокий (30000+) | Стандартный (80, 443) |
| **IP-адрес** | IP узлов | Выделенный внешний IP |
| **Use-case** | Dev/test, on-prem | Production в облаке |

### Переход к другим типам

- Для production в облаке: используйте [LoadBalancer](./service_type_loadbalancer.md)
- Для HTTP/HTTPS приложений: используйте [Ingress](../Ingress/overview.md)
- Полная сводка типов: [service_types_summary.md](./service_types_summary.md)
