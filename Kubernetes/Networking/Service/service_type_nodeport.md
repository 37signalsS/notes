# NodePort

## Определения

**NodePort** — тип Service, открывающий статический порт в диапазоне **30000-32767** на **каждом узле** кластера. Трафик на `NodeIP:NodePort` перенаправляется на сервис.

NodePort расширяет [ClusterIP](./service_type_clusterip.md), добавляя внешний доступ через IP любого узла кластера.

## Основные концепции

### Принцип работы

При создании Service типа NodePort:

1. Kubernetes создаёт внутренний ClusterIP (как у обычного сервиса)
2. На каждом узле открывается порт из диапазона 30000-32767
3. `kube-proxy` настраивает правила для перенаправления трафика с `NodePort` на `ClusterIP`
4. Трафик распределяется между Pod по селектору

### Диапазон портов

| Параметр | Значение |
| :--- | :--- |
| **По умолчанию** | 30000-32767 |
| **Настройка** | Флаг API-сервера `--service-node-port-range` |

### externalTrafficPolicy

По умолчанию (`externalTrafficPolicy: Cluster`) трафик с `NodePort` одного узла может перенаправляться на под на *другом* узле.

#### Режим Cluster (по умолчанию)

**Недостатки:**

| Проблема | Описание |
| :--- | :--- |
| **Теряется IP клиента** | Внутри пода виден IP узла, а не реальный IP клиента |
| **Лишний хоп** | Трафик проходит дополнительный путь между узлами |

#### Режим Local

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service
spec:
  type: NodePort
  externalTrafficPolicy: Local  # Сохраняет IP клиента
  ports:
    - port: 80
      targetPort: 80
```

**Поведение:**

- `kube-proxy` отправляет трафик **только на поды на том же узле**, куда пришёл запрос
- **Сохраняется исходный IP-адрес клиента**
- Возможна неравномерная балансировка при неравномерном распределении подов

**Применение:** Приложения, требующие реальный IP для логирования, аналитики, геолокации; публикация через [LoadBalancer](./service_type_loadbalancer.md).

### Проблема возврата трафика и SNAT

**Проблема:**

1. Клиент обращается к `NodeIP:32xxx` (NodePort)
2. kube-proxy через iptables/IPVS выполняет DNAT, направляя трафик на под (`10.1.1.2:8080`)
3. Под отправляет ответ **со своего IP** (`10.1.1.2`)
4. Клиент отбрасывает пакет (ожидал ответ от `NodeIP`)

**Решение: Source NAT (SNAT/MASQUERADE)**

CNI-плагины (Calico, Flannel) применяют SNAT для трафика NodePort в режиме `Cluster`:

- Исходящий от пода пакет модифицируется: source IP меняется с `PodIP` на `NodeIP`
- Обратный пакет возвращается на ноду, выполняется обратная трансляция

**Недостаток SNAT:** Поды видят трафик от IP ноды, а не от оригинального IP клиента. Невозможно:

- Применение политик безопасности на основе IP клиента
- Гранулярный аудит и логирование источников
- Определение типа клиента (внешний/внутренний)

#### externalTrafficPolicy: Local — детали

| Аспект | Описание |
| :--- | :--- |
| **Преимущества** | Сохранение IP клиента, отсутствие cross-node трафика, эффективная маршрутизация |
| **Недостатки** | Неравномерная балансировка, требует равномерного распределения подов |
| **Риски** | При падении ноды трафик распределяется 50/50 между нодами, независимо от количества подов |
| **Ограничение** | Если на ноде нет локальных подов, трафик отбрасывается |

**Рекомендации:**

- Используйте `nodeSelector` или `affinity` для равномерного распределения подов по нодам
- Мониторьте балансировку трафика при использовании `Local`
- Для Calico рассмотрите **IP Advertisement** через BGP ([подробнее](../Network/CNI/selection_and_external_access.md#ip-advertisement-через-bgp-calico-specific))

## Практические сценарии

> **Полный пример:** Пошаговое создание ClusterIP и преобразование в NodePort см. в [Практическом сценарии](./service_practical_scenarios.md).

### Пример манифеста

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-service-np
spec:
  type: NodePort  # Если не указан, по умолчанию ClusterIP

  selector:
    app: my-app  # Должен соответствовать меткам Deployment/ReplicaSet

  ports:
    - name: http
      protocol: TCP
      port: 80         # Внутренний порт сервиса
      targetPort: 80   # Порт на Pod
      # nodePort: 30080  # Статический порт (опционально, иначе случайный из 30000-32767)
```

### Цепочка обработки трафика

```
Client → NodeIP:NodePort → kube-proxy → ClusterIP → Pod
```

### Распространённые use-case

| Сценарий | Описание |
| :--- | :--- |
| **Разработка и отладка** | Быстрый доступ без настройки Ingress |
| **On-premise кластеры** | Альтернатива LoadBalancer в локальных средах |
| **TCP/UDP сервисы** | Публикация не-HTTP приложений (RabbitMQ, БД) |
| **Бэкенд для внешнего LB** | Внешний балансировщик направляет трафик на `NodeIP:NodePort` |

## Дополнительная информация

### Ограничения

| Ограничение | Описание |
| :--- | :--- |
| **Диапазон портов** | 30000-32767 (неудобные порты для пользователей) |
| **Зависимость от IP узла** | При изменении IP узла доступ теряется |
| **Безопасность** | Прямой доступ к узлам требует настройки firewall |

### NodePort vs LoadBalancer

| Критерий | NodePort | LoadBalancer |
| :--- | :--- | :--- |
| **Сложность** | Просто | Требует облачного провайдера или MetalLB |
| **Порт** | Высокий (30000+) | Стандартный (80, 443) |
| **IP-адрес** | IP узлов | Выделенный внешний IP |
| **Use-case** | Dev/test, on-prem | Production в облаке |
