# Обзор Service

> **Reliability Score: 10** (SSoT + Web 2026). Базовый сетевой примитив Kubernetes. Обновлено с учетом функций v1.31-1.36.

## Определения

**Service (Сервис)** — абстракция в Kubernetes, определяющая логический набор подов и политику доступа к ним. Service предоставляет единую стабильную точку входа (Virtual IP и DNS-имя) для группы подов, выполняющих одну функцию, даже при изменении их внутренних IP-адресов. Они обеспечивают бесперебойную связь между компонентами приложения и гарантируют, что приложение остается доступным и функциональным, даже если модули (поды) добавляются, удаляются или заменяются.

**Основная задача:** Обеспечение сетевой связности, обнаружения (Service Discovery) и балансировки нагрузки. Service является стабильной точкой входа (Virtual IP), которая скрывает динамику и эфемерность сети подов, выступая в роли уровня абстракции для доступа к модулям. Это гарантирует, что приложение остается доступным, даже если поды добавляются, удаляются или заменяются.

## Основные концепции

### Проблема эфемерности IP-адресов подов

IP-адреса подов в Kubernetes являются **эфемерными (временными)**:
- IP привязан к поду только на время его жизни.
- При удалении пода (сбой, обновление Deployment, вытеснение) новый под получает другой IP.
- Поды не «перезапускаются» — старый объект удаляется, а контроллер создает новый с другими именем и сетевым адресом.

**Следствие:** Нельзя полагаться на прямые IP-адреса для взаимодействия между компонентами системы. В то время как CNI обеспечивает базовую связность (Connectivity), Service обеспечивает **обнаружение и стабильность** (Discovery & Stability). Клиенту не нужно знать список IP всех подов — он обращается к одному стабильному VIP сервиса. Способность сервиса динамически маршрутизировать и балансировать трафик играет жизненно важную роль в поддержании доступности и производительности услуг.

### Механизм работы через Labels и Selectors

Связь между Service и подами устанавливается через **метки (labels)** и **селекторы (selectors)**:

1.  **Labels (Метки):** Подам назначаются пары ключ-значение (например, `app.kubernetes.io/name: nginx`).
2.  **Selector (Селектор):** В спецификации Service указывается селектор, соответствующий этим меткам.

Kubernetes (в частности, `kube-controller-manager`) автоматически отслеживает поды с указанными метками и обновляет список эндпоинтов (Endpoints/EndpointSlices), направляя трафик только на работоспособные поды, прошедшие проверку `Readiness Probe`. Это обеспечивает динамическое масштабирование и реконфигурацию без нарушения доступности услуг.

### Спецификация Service: Ключевые поля

| Поле | Описание |
| :--- | :--- |
| `selector` | Группа меток для идентификации целевых подов. |
| `ports` | Массив определений портов (протокол, входящий порт, порт назначения). |
| `type` | Тип сервиса: `ClusterIP` (дефолт), `NodePort`, `LoadBalancer`, `ExternalName`. |
| `clusterIP` | Стабильный внутренний IP. При значении `None` создается **Headless Service**. |
| `trafficDistribution` | (v1.31+) Настройка стратегии распределения трафика (например, `PreferClose`). |

#### Спецификация портов: port vs targetPort

| Параметр | Описание |
| :--- | :--- |
| **`port`** | Порт, который «слушает» сам Service. Внутренние клиенты кластера обращаются на этот порт. |
| **`targetPort`** | Порт приложения внутри контейнера. Service перенаправляет входящий трафик на этот порт. |

**Важное правило:** `port` — это "входная дверь" сервиса в сети кластера, а `targetPort` — это порт, на котором приложение ожидает соединения внутри пода. Если `targetPort` не указан, он по умолчанию принимает значение `port`.

### Важность targetPort: Маршрутизация в многоконтейнерных подах

В подах с несколькими контейнерами (например, использующих [Sidecar-паттерн](../../Base/Pod/pod_sidecar_patterns.md)) критически важно точно указывать `targetPort`.

**Сценарий:** Под содержит два контейнера:
1.  **Main Application:** Слушает порт `8080`.
2.  **Nginx Sidecar:** Слушает порт `80` (выполняет роль прокси, раздает статику, терминирует TLS).

Если в Service указать `targetPort: 8080`, трафик пойдет напрямую к приложению, полностью игнорируя Nginx Sidecar. Это приведет к неработоспособности логики кэширования или авторизации, заложенной в sidecar. Для правильной работы необходимо указывать `targetPort: 80`, направляя трафик на прокси-контейнер.

## Практические сценарии

### Взаимодействие внутри кластера по DNS

Любой под внутри кластера может обратиться к сервису по его DNS-имени.
- **Полное имя (FQDN):** `<service-name>.<namespace>.svc.cluster.local`
- **Пример обращения:** `curl http://my-api.prod.svc.cluster.local:80`

Подробное описание работы DNS и CoreDNS см. в разделе [Service Discovery через DNS](../Network/dns_service_discovery.md).

### Публикация приложения и балансировка

Service автоматически выполняет балансировку нагрузки между подами (по умолчанию алгоритм round-robin на уровне `kube-proxy`). При масштабировании количества реплик (увеличении `replicas` в Deployment) новые поды автоматически добавляются в балансировку после успешного прохождения проверки готовности.

### Доступ снаружи для разработки

Для временного доступа к внутреннему сервису (тип `ClusterIP`) без настройки Ingress используется `kubectl port-forward`:
```bash
# Проброс порта 8080 локальной машины на порт 80 сервиса
kubectl port-forward svc/my-nginx 8080:80
```
Приложение станет доступно по адресу `http://localhost:8080`.

## Дополнительная информация

### Endpoints и EndpointSlices

Для каждого Service с селектором Kubernetes поддерживает объекты, содержащие актуальные сетевые адреса:
- **Endpoints:** Классический объект со списком IP. Имеет ограничения по производительности в крупных кластерах (>1000 подов).
- **EndpointSlices:** Современная масштабируемая альтернатива. Группирует эндпоинты в несколько объектов, что значительно снижает объем данных, передаваемых `kube-proxy` и API-сервером.

### Реализация через kube-proxy

Механизм Service реализуется компонентом `kube-proxy`, который работает на каждом узле кластера. Основные задачи `kube-proxy` — перехват трафика к ClusterIP и его пересылка соответствующим подам на основе правил фильтрации трафика.

#### Режимы работы
1.  **iptables (Default):** Самый распространенный режим. Использует цепочки iptables для NAT.
2.  **IPVS:** Предназначен для кластеров с огромным количеством сервисов. Работает быстрее iptables и поддерживает больше алгоритмов балансировки (lc, dh, sh).
3.  **nftables (Stable v1.31):** Современная замена iptables. Обеспечивает лучшую производительность и более простую отладку сетевых правил.

#### Алгоритмы балансировки нагрузки
Для распределения трафика между несколькими подами в рамках одного сервиса `kube-proxy` использует следующие стратегии:

- **Циклический (Round Robin):** Стандартная и наиболее распространенная стратегия. `kube-proxy` последовательно проходит по списку доступных эндпоинтов, отправляя каждое новое соединение следующему поду в списке. Хорошо подходит для большинства типичных рабочих нагрузок.
- **Случайный выбор (Random):** В зависимости от версии и конфигурации (особенно в режиме `iptables`), `kube-proxy` может выбирать конечную точку случайным образом. Это помогает избежать предсказуемых схем движения трафика.
- **Привязка сеанса (Session Affinity):** Настраивается через `sessionAffinity: ClientIP`. Гарантирует, что запросы с одного и того же IP-адреса клиента будут последовательно направляться на один и тот же под. Это критично для приложений, требующих сохранения состояния (sticky sessions).

### Современные возможности (2025-2026)

- **Multiple Service CIDRs (v1.31+):** Позволяет динамически добавлять новые диапазоны IP для сервисов, если основной диапазон исчерпан.
- **Gateway API:** Рекомендуемый стандарт для управления входящим (Ingress) и внутренним (Service Mesh) трафиком на уровнях L4-L7. Предоставляет гораздо больше возможностей, чем классический `Service` типа `LoadBalancer`.
