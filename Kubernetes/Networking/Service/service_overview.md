# Service

## Определения

**Service** — это абстракция в Kubernetes, которая определяет логический набор подов (Pods) и политику доступа к ним. Service предоставляет единую, стабильную точку входа (IP-адрес и DNS-имя) для доступа к группе подов, которые выполняют одну и ту же функцию, даже если их внутренние IP-адреса постоянно меняются.

Основная задача Service — обеспечить сетевую связность и простую балансировку нагрузки для приложений.

## Основная концепция

Связь между Service и подами устанавливается с помощью **меток (labels)** и **селекторов (selectors)**.

1. **Labels:** Подам, которые должны быть частью одного сервиса, назначаются одинаковые метки (например, `app.kubernetes.io/name: my-app`).
2. **Selector:** В спецификации Service указывается селектор, который соответствует этим меткам.

Kubernetes автоматически отслеживает все поды с указанными метками и обновляет маршрутизацию для Service, направляя трафик только на работоспособные поды.

## Спецификация (`spec`)

Ключевые поля в спецификации Service:

* `selector`: Определяет, на какие поды будет направляться трафик. Если под имеет все метки, указанные в селекторе, он становится частью сервиса.
* `ports`: Массив, описывающий маппинг портов.
  * `port`: Порт, который "слушает" сам Service. Клиенты обращаются именно на этот порт.
  * `targetPort`: Порт на подах, на который Service будет перенаправлять трафик.
  * `protocol`: Протокол порта. По умолчанию `TCP`.
  * `name`: Имя порта. Полезно для сценариев, где сервисы имеют несколько портов.
* `type`: Тип сервиса. Определяет, как сервис будет доступен.

### Пример манифеста

В одном YAML-файле можно определять несколько ресурсов, разделяя их `---`.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-first-nginx
  namespace: work
spec:
  replicas: 3
  selector:
    matchLabels:
      app.kubernetes.io/name: my-first-nginx
  template:
    metadata:
      labels:
        app.kubernetes.io/name: my-first-nginx # Метки пода
    spec:
      containers:
      - name: nginx
        image: nginx:latest
        ports:
        - containerPort: 80 # Порт контейнера
---
apiVersion: v1
kind: Service
metadata:
  name: my-first-nginx
  namespace: work
  labels:
    app.kubernetes.io/name: my-first-nginx
spec:
  selector:
    app.kubernetes.io/name: my-first-nginx # Селектор, соответствующий меткам пода
  ports:
    - name: http
      protocol: TCP
      port: 80         # Порт, который открывает сервис
      targetPort: 80   # Порт на подах, куда идет трафик
  type: ClusterIP      # Тип сервиса
```

## Типы сервисов (Service Types)

Kubernetes предлагает несколько типов сервисов, каждый из которых решает свою задачу по обеспечению доступа к приложениям. Выбор типа определяет, как сервис будет доступен и где.

* **[ClusterIP](./service_type_clusterip.md)**
  * **Тип по умолчанию**. Предоставляет стабильный внутренний IP-адрес, доступный **только внутри кластера**.
  * **Сценарий:** Внутренние коммуникации между компонентами приложения (например, бэкенд обращается к базе данных).

* **[NodePort](./service_type_nodeport.md)**
  * Открывает статический порт (в диапазоне 30000-32767) на IP-адресе **каждого узла** кластера.
  * **Сценарий:** Простой способ предоставить внешний доступ для разработки, отладки или в bare-metal средах, где нет облачного балансировщика.

* **[LoadBalancer](./service_type_loadbalancer.md)**
  * Расширяет `NodePort`. Автоматически запрашивает и настраивает внешний балансировщик нагрузки у облачного провайдера (AWS, GCP, Azure).
  * **Сценарий:** Стандартный способ публикации сервисов в интернет в облачных средах.

* **[ExternalName](./service_type_externalname.md)**
  * Особый тип без селекторов и IP-адреса. Создает CNAME-запись во внутреннем DNS, перенаправляя запросы на внешний сервис.
  * **Сценарий:** Предоставление доступа к внешним сервисам (например, к управляемой базе данных) по внутреннему имени.

* **[Headless Service](./service_type_headless.md)**
  * Сервис без `ClusterIP` (`clusterIP: None`). Вместо одного IP он возвращает IP-адреса всех подов, входящих в сервис.
  * **Сценарий:** Используется для `StatefulSet`-приложений, которым требуется стабильный сетевой идентификатор для каждого пода (например, кластеры баз данных).

Для более детального сравнения всех типов см. **[Сводку по типам сервисов](./service_types_summary.md)** и **[Сравнительную таблицу](./service_types_comparison.md)**.

## Как работает сервис: Endpoints и EndpointSlices

Когда создается Service, Kubernetes автоматически создает для него объект **EndpointSlice** (в старых версиях — **Endpoints**).

* `EndpointSlice` содержит список актуальных IP-адресов и портов всех подов, которые соответствуют `selector`'у сервиса.
* Контроллер `endpointslice-controller` постоянно следит за подами: если под удаляется, создается или становится неработоспособным, `EndpointSlice` немедленно обновляется.
* Когда к Service приходит запрос, `kube-proxy` (компонент на каждом узле) использует информацию из `EndpointSlice` для перенаправления трафика на один из здоровых подов, реализуя балансировку нагрузки.

`EndpointSlice` был введен для повышения производительности и масштабируемости по сравнению с устаревшим `Endpoints`.

## Доступ к сервису

### Внутри кластера

Любой под внутри кластера может обратиться к сервису по его имени (DNS) или по его `ClusterIP`. Например: `curl http://my-first-nginx.work:80`.

### Снаружи кластера (для разработки)

Сервисы типа `ClusterIP` недоступны извне. Для отладки и разработки можно воспользоваться командой `kubectl port-forward`.

```bash
kubectl port-forward -n <namespace> service/<service-name> <local-port>:<service-port>
```

Эта команда пробрасывает порт с вашей локальной машины на порт сервиса внутри кластера.

**Пример:**

```bash
kubectl port-forward -n work service/my-first-nginx 8080:80
```

После выполнения этой команды вы можете открыть браузер на своей машине по адресу `http://localhost:8080` и получить доступ к Nginx, работающему в кластере. Команда активна, пока вы не прервете ее (`Ctrl+C`).

Для публикации сервисов в production используются `Ingress` или `Gateway API`.
