# Service

## Определения

**Service** — это абстракция Kubernetes, которая определяет логическую группу `Pod`-ов и политику доступа к ним. Он предоставляет **стабильную сетевую точку входа** (IP-адрес и DNS-имя), которая не меняется, даже если `Pod`-ы, стоящие за ней, перезапускаются или перемещаются.

Сервис предоставляет стабильную точку доступа к динамически меняющемуся набору Pod и абстрагирует сетевой доступ на уровне L4. **Тип сервиса** определяет границы доступности и способ маршрутизации трафика.

## Основные концепции

### Связь Service и Pod

Связь между `Service` и `Pod`-ами устанавливается с помощью **меток и селекторов** (`labels` и `selectors`).

### Service Discovery и kube-proxy

За маршрутизацию трафика от `Service` к нужным `Pod`-ам отвечает компонент **`kube-proxy`**, который работает на каждом узле. Он отслеживает `Service` и `Endpoints` и преобразует виртуальный IP-адрес сервиса в реальный IP-адрес пода.

Подробнее о его роли, режимах работы (`iptables`, `ipvs`) и взаимодействии с CNI читайте в документе [Сетевая модель в Kubernetes](../Network/cni_kube_proxy_roles.md).

### Способы публикации приложений

В Kubernetes существует два основных подхода к публикации приложений:

1. **Service**: Обеспечивает сетевое взаимодействие внутри кластера и может быть использован для ограниченного внешнего доступа. Работает на уровне L3/L4 (OSI), используя NAT и `kube-proxy` для маршрутизации трафика.
2. **Ingress**: Предоставляет более гибкий механизм для внешнего доступа, особенно для HTTP/HTTPS трафика. Работает на уровне L7 (OSI), используя Ingress-контроллеры. Подробнее см. [Ingress](../Ingress/overview.md).

## Практические сценарии

### Коммуникация между Подами (Pod-to-Pod)

#### Напрямую по IP-адресу пода (Не рекомендуется)

Каждый под имеет свой уникальный IP-адрес в кластере. Технически можно обратиться напрямую:

```bash
curl http://<IP-адрес-пода-Б>:<порт>
```

**Недостатки:**

- **Поды эфемерны:** При пересоздании под получит новый IP-адрес
- **Нет балансировки:** Нет распределения нагрузки между репликами

#### Через Service (Рекомендуемый способ)

```bash
# В том же namespace:
curl http://<имя-сервиса>:<порт>

# В другом namespace:
curl http://<имя-сервиса>.<имя-неймспейса>.svc.cluster.local:<порт>
```

Kubernetes через внутренний DNS преобразует имя сервиса в его `ClusterIP`, а `kube-proxy` направит запрос на один из здоровых подов.

## Дополнительная информация

### Типы сервисов

Kubernetes поддерживает следующие типы сервисов:

- **[ClusterIP](./service_type_clusterip.md)** — внутренний доступ внутри кластера
- **[NodePort](./service_type_nodeport.md)** — публикация через порт узла
- **[LoadBalancer](./service_type_loadbalancer.md)** — облачный балансировщик
- **ExternalName** — DNS CNAME для внешних сервисов
- **Headless Service** — прямой доступ к Pod-ам

Подробное сравнение типов см. в [сводке по типам сервисов](./service_types_summary.md).
