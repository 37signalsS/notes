# Обзор Service

## Определения

**Service** — абстракция в Kubernetes, определяющая логический набор подов и политику доступа к ним. Предоставляет единую стабильную точку входа (IP-адрес и DNS-имя) для доступа к группе подов, выполняющих одну функцию, даже при изменении их внутренних IP-адресов.

**Основная задача:** Обеспечение сетевой связности и балансировки нагрузки для приложений. Service является стабильной точкой входа (Virtual IP), которая скрывает динамику и эфемерность сети подов.

## Основные концепции

### Проблема эфемерности IP-адресов подов

IP-адреса подов в Kubernetes **эфемерны (временны)**:

- IP привязан к поду только на время его жизни.
- При удалении пода (ошибка, обновление, перемещение) новый под получает другой IP.
- Поды не «перезапускаются» — старый удаляется, Deployment создаёт новый с другими именем и IP.

**Следствие:** Нельзя полагаться на прямые IP-адреса для взаимодействия. Пока CNI обеспечивает связность (Connectivity), Service обеспечивает **обнаружение и стабильность** (Discovery & Stability). Клиенту не нужно знать список IP всех подов — он обращается к одному стабильному IP сервиса.

### Механизм работы через Labels и Selectors

Связь между Service и подами устанавливается через **метки (labels)** и **селекторы (selectors)**:

1. **Labels:** Подам назначаются одинаковые метки (например, `app.kubernetes.io/name: my-app`).
2. **Selector:** В спецификации Service указывается селектор, соответствующий этим меткам.

Kubernetes автоматически отслеживает поды с указанными метками и обновляет список эндпоинтов, направляя трафик только на работоспособные поды.

### Спецификация Service

Ключевые поля в `spec`:

| Поле | Описание |
| :--- | :--- |
| `selector` | Определяет поды для маршрутизации (по соответствию меток) |
| `ports` | Массив маппинга портов |
| `type` | Тип сервиса: `ClusterIP`, `NodePort`, `LoadBalancer`, `ExternalName` |
| `clusterIP` | Внутренний IP сервиса (автоматически или вручную) |
| `clusterIP: None` | Headless Service — DNS возвращает IP подов напрямую |

#### Спецификация портов: port vs targetPort

| Порт | Описание |
| :--- | :--- |
| **`port`** | Порт, который «слушает» Service. Клиенты обращаются на этот порт внутри кластера |
| **`targetPort`** | Порт приложения внутри контейнера. Service перенаправляет трафик на этот порт |

**Правило:** `port` — входная дверь сервиса, `targetPort` — дверь приложения.

### Пример манифеста

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-first-nginx
  namespace: work
  labels:
    app.kubernetes.io/name: my-first-nginx
spec:
  selector:
    app.kubernetes.io/name: my-first-nginx
  ports:
    - name: http
      protocol: TCP
      port: 80
      targetPort: 80
  type: ClusterIP
```

### Важность targetPort: маршрутизация в многоконтейнерных подах

В подах с несколькими контейнерами (например, [Sidecar-паттерн](../../Base/Pod/pod_sidecar_patterns.md)) критически важно правильно указать `targetPort`.

**Сценарий:** Pod содержит два контейнера: основное приложение на порту `8080` и Nginx sidecar на порту `80` (раздача статики, проксирование). Если указать `targetPort: 8080`, трафик пойдет напрямую к приложению, минуя Nginx (кэширование, TLS-терминация не будут работать).

> **Подробно:** [Nginx Sidecar для раздачи статики](../../Base/Pod/pod_sidecar_patterns.md#nginx-sidecar-для-раздачи-статики)

## Практические сценарии

### Доступ к сервису внутри кластера

Любой под внутри кластера может обратиться к сервису по DNS-имени или `ClusterIP`.

**Внутрикластерный DNS:** Kubernetes автоматически преобразует имя сервиса в стабильный `ClusterIP`. Это основной способ сетевого взаимодействия.

**Рекомендация:** Используйте полное доменное имя (FQDN):
`<service-name>.<namespace>.svc.cluster.local`

#### Проверка через DNS

```bash
# Обращение к сервису по имени из соседнего пода
curl http://my-first-nginx.work:80
```

### Доступ снаружи кластера (для разработки)

Сервисы типа `ClusterIP` недоступны извне. Для отладки используйте `kubectl port-forward`:

```bash
kubectl port-forward -n work service/my-first-nginx 8080:80
```

Доступен по адресу `http://localhost:8080`.

> **Production:** Для публикации используются [Ingress](../Ingress/overview.md) или [Gateway API](../gateway_api/definitions.md).

### Балансировка нагрузки

Service автоматически распределяет трафик между подами (по умолчанию round-robin). При масштабировании (увеличении количества реплик) балансировка обновляется автоматически.

## Дополнительная информация

### Endpoints и EndpointSlices

Для каждого Service с селектором Kubernetes создаёт объекты **Endpoints** или **EndpointSlices**:

- **Endpoints controller** (внутри `kube-controller-manager`) следит за подами по селектору и поддерживает **EndpointSlice** с их IP и портами.
- **EndpointSlice** содержит список актуальных IP-адресов и портов здоровых подов.
- `kube-proxy` использует эти данные для настройки правил маршрутизации (iptables/IPVS) на узлах кластера.

### Типы сервисов

| Тип | Доступность | Основной сценарий |
| :--- | :--- | :--- |
| **[ClusterIP](./service_type_clusterip.md)** | Только внутри кластера | Внутренние коммуникации (по умолчанию) |
| **[NodePort](./service_type_nodeport.md)** | `IP_узла:NodePort` | Разработка, отладка, on-prem |
| **[LoadBalancer](./service_type_loadbalancer.md)** | Внешний IP (облако) | Production в облачных провайдерах |
| **[ExternalName](./service_type_externalname.md)** | DNS CNAME | Доступ к внешним ресурсам |
| **[Headless](./service_type_headless.md)** | Прямые IP подов | Stateful-приложения (StatefulSet) |

> **Сравнение:** Детальное сравнение и критерии выбора см. в [Сводке по типам сервисов](./service_types_summary.md).
