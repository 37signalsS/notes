# Container Runtime в Kubernetes

**Свежесть:** Актуально на июль 2026

## Определения

**Container Runtime (Среда выполнения контейнеров)** — это программный компонент, отвечающий за низкоуровневую задачу запуска и управления жизненным циклом контейнеров на узле. Он напрямую взаимодействует с ядром операционной системы хоста (через cgroups и namespaces) для создания изолированных окружений. Рантаймы не являются специфичными для Kubernetes и могут использоваться независимо.

**CRI (Container Runtime Interface)** — это стандартный программный интерфейс (API) и проект Kubernetes, который выступает в качестве стандартизированного моста между компонентами Kubernetes (преимущественно `kubelet`) и различными средами выполнения контейнеров. CRI определяет протокол связи (gRPC), что позволяет интегрировать новые рантаймы без изменения кода самого Kubernetes.

---

## Различия между Container Runtime и CRI

Хотя эти понятия тесно связаны, они служат разным целям:

| Характеристика | Container Runtime (Среда выполнения) | CRI (Интерфейс) |
| :--- | :--- | :--- |
| **Цель** | Непосредственное выполнение контейнеров и управление ими. | Стандартизация взаимодействия между K8s и рантаймом. |
| **Уровень** | Низкоуровневое ПО, работающее с ядром ОС. | Промежуточный слой (API/мост). |
| **Независимость** | Может работать автономно (вне Kubernetes). | Специфичен для экосистемы Kubernetes. |
| **Примеры** | containerd, CRI-O, Docker Engine, rkt. | Спецификация CRI, плагины CRI внутри containerd. |
| **Функции** | Создание, запуск, остановка, управление сетью и томами. | Определение методов API для управления подами и образами. |

## Основные концепции

### Роль Container Runtime в Kubernetes
Kubernetes не управляет контейнерами напрямую. Он делегирует эти задачи среде выполнения через CRI. Основные функции рантайма в контексте кластера:
- Загрузка образов контейнеров из реестров.
- Создание и запуск контейнеров.
- Управление ресурсами контейнеров (через cgroups).
- Изоляция процессов (через namespaces).
- Мониторинг состояния и сбор логов.

### Популярные среды выполнения

| Рантайм | Описание | Статус в K8s |
| :--- | :--- | :--- |
| **containerd** | Легковесный, промышленный стандартный рантайм. Проект CNCF. | Стандарт по умолчанию |
| **CRI-O** | Легковесная альтернатива, созданная специально для Kubernetes. | Популярный выбор (RedHat/OpenShift) |
| **Docker Engine** | Полнофункциональная платформа для контейнеризации. | Устарело (требует внешних адаптеров типа cri-dockerd) |
| **Kata Containers** | Рантайм на базе микро-VM для повышенной изоляции. | Специализированное использование |

### Преимущества перехода на containerd
Основные причины, по которым **containerd** стал стандартом вместо Docker Engine:

1.  **Соответствие стандартам (CNI/CRI/OCI)**: containerd является нативной реализацией стандартов CNCF.
2.  **Снижение сложности**: Цепочка вызовов сократилась. Раньше: `Kubelet → dockershim → Docker Daemon → containerd → runc`. Сейчас: `Kubelet → containerd → runc`.
3.  **Экономия ресурсов**: Отсутствие лишнего посредника (Docker Daemon) снижает потребление CPU и RAM.
4.  **Безопасность**: Меньше кода — меньше поверхность атаки.

## Сравнение Docker и containerd

На высоком уровне Docker Engine сам использует containerd для управления контейнерами. При использовании Docker в Kubernetes цепочка вызовов выглядела так:
`Kubelet → dockershim → Docker Daemon → containerd → runc`

При прямом использовании containerd цепочка сокращается:
`Kubelet → CRI-plugin (внутри containerd) → containerd → runc`

## Взаимодействие через CRI

CRI действует как мост между Kubernetes и рантаймом. Он определяет два сервиса gRPC:
1.  **RuntimeService**: Операции с подами и контейнерами (создание, запуск, остановка, удаление).
2.  **ImageService**: Операции с образами (загрузка, просмотр, удаление).

Это разделение позволяет `kubelet` быть независимым от конкретной реализации рантайма.

## Практические сценарии

### Проверка используемого рантайма

```bash
# Просмотр рантайма на узлах
kubectl get nodes -o wide
# → CONTAINER-RUNTIME: containerd://1.7.18

# Проверка через crictl (утилита для отладки CRI)
sudo crictl info
```

### Настройка containerd для Kubernetes

Для корректной работы containerd в кластере необходимо включить поддержку CRI в конфигурационном файле `/etc/containerd/config.toml`:

```toml
[plugins."io.containerd.grpc.v1.cri"]
  sandbox_image = "registry.k8s.io/pause:3.9"
[plugins."io.containerd.grpc.v1.cri".containerd.runtimes.runc.options]
  SystemdCgroup = true
```
