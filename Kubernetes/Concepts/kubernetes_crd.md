# CRD: Custom Resource Definition

## Определения

**Custom Resource Definition (CRD)** — это механизм расширения API Kubernetes, позволяющий добавлять собственные типы ресурсов без разработки отдельного API‑сервера. С помощью CRD формируется контракт: как называется ресурс, в каком API‑группе и версии он живет, какие поля допустимы, какие правила валидации применяются и какие подресурсы доступны. Дальше уже контроллер или оператор реализует логику согласования состояния, используя эти пользовательские ресурсы.

## Основные концепции

### Ключевые элементы CRD

- **Группа и версии (Group and Versions):**
  - `group`: Логическое пространство именования, например `example.io`.
  - `versions`: Список версий (`v1alpha1`, `v1beta1`, `v1`), для каждой указывается `served` (доступна ли через API) и `storage` (является ли версией для хранения в etcd).
- **Имена (Names):**
  - `names.kind`: Имя типа в CamelCase (например, `Backup`).
  - `names.plural`: Имя в нижнем регистре во множественном числе для URL (`/apis/group/version/plural`).
  - `names.singular`: Имя в единственном числе.
  - `shortNames`: Короткие псевдонимы для `kubectl` (например, `bk`).
  - `categories`: Включение ресурса в категории `kubectl` (например, `all`).
- **Область видимости (Scope):**
  - `scope`: `Namespaced` (ресурс живет в namespace) или `Cluster` (ресурс глобален для кластера).
- **Схема (Schema):**
  - `openAPIV3Schema` описывает допустимую структуру и типы полей на основе OpenAPI v3.
  - Поддерживаются `required`, `default`, `enum`, `format`, а также ограничения для чисел и строк.
- **Подресурсы (Subresources):**
  - `status`: Отделяет спецификацию (`spec`), которую задает пользователь, от статуса (`status`), которым управляет контроллер. Позволяет гранулировать права RBAC.
  - `scale`: Интегрирует ресурс с механизмами автомасштабирования Kubernetes (например, HPA).
- **Представление (Printing):**
  - `additionalPrinterColumns`: Позволяет настроить дополнительные колонки в выводе `kubectl get`.

### Валидация, значения по умолчанию и финализаторы

Схема CRD обеспечивает **серверную валидацию** и установку **значений по умолчанию** (`default`).

**Финализаторы (Finalizers)** используются для управляемого удаления. Когда у объекта есть финализатор, `kubectl delete` не удаляет его сразу, а устанавливает `metadata.deletionTimestamp`. Объект остается в системе, пока контроллер не выполнит необходимые действия по очистке (например, удаление внешних зависимостей) и не снимет финализатор с объекта.

## Жизненный цикл CRD и его экземпляров

1.  **Установка CRD:** Регистрация нового типа ресурса в API.
2.  **Создание экземпляра:** Пользователь создает объект. API-сервер применяет значения по умолчанию, валидирует объект по схеме и пропускает через admission-вебхуки.
3.  **Сохранение:** Объект сохраняется в etcd в `storage`-версии. Неизвестные поля (не описанные в схеме) удаляются (pruning).
4.  **Реконсиляция:** Оператор (контроллер) отслеживает создание/изменение объекта и приводит систему в желаемое состояние.
5.  **Обновления:** Изменение CRD (схемы, версий) и/или логики оператора.
6.  **Удаление:** Установка `deletionTimestamp`, запуск логики финализаторов, и только потом — физическое удаление объекта из etcd.

### Версионирование и Конвертация

CRD может публиковать несколько версий API одновременно (`v1alpha1`, `v1beta1`, `v1`).
- `served: true` - версия доступна клиентам.
- `storage: true` - единственная версия, в которой объекты хранятся в etcd.

При наличии нескольких версий возможна их конвертация:
- **`None`**: Прямое сопоставление полей. Работает, только если схемы идентичны.
- **`Webhook`**: API-сервер вызывает внешний вебхук для преобразования объекта между `served`-версией и `storage`-версией. Это позволяет эволюционировать схему без простоя. Вебхук должен уметь выполнять прямую и обратную конвертацию.

Переход на новую версию выполняется пошагово:
1.  Добавить новую версию как `served: true, storage: false`.
2.  Настроить и развернуть вебхук для конвертации.
3.  После валидации переключить `storage: true` на новую версию.
4.  Старую версию можно пометить как `served: false`, а затем удалить.

### Стратегии обновления схемы

- **Разрешено:**
  - Добавление нового необязательного поля.
  - Расширение `enum` новыми значениями.
  - Ослабление ограничений (увеличение `maxItems`, `maxLength`).
- **Рискованно:**
  - Изменение значения `default` без миграции существующих объектов.
  - Включение "обрезки" (`pruning`) полей при наличии неструктурированных данных.
- **Запрещено:**
  - Смена типа существующего поля.
  - Удаление или переименование поля без механизма конвертации.
  - Превращение опционального поля в обязательное (`required`).
  - Ужесточение ограничений, которое сделает существующие объекты невалидными.

## Практические сценарии

### Пример CRD

```yaml
apiVersion: apiextensions.k8s.io/v1
kind: CustomResourceDefinition
metadata:
  name: backups.example.io
spec:
  group: example.io
  names:
    kind: Backup
    plural: backups
    singular: backup
    shortNames: [bk]
    categories: [all]
  scope: Namespaced
  versions:
  - name: v1alpha1
    served: true
    storage: true
    schema:
      openAPIV3Schema:
        type: object
        required: ["spec"]
        properties:
          spec:
            type: object
            required: ["target","schedule"]
            properties:
              target:
                type: string
              schedule:
                type: string
              retentionDays:
                type: integer
                minimum: 1
                default: 7
          status:
            type: object
            properties:
              lastRun:
                type: string
                format: date-time
              phase:
                type: string
                enum: ["Pending","Running","Succeeded","Failed"]
    subresources:
      status: {}
    additionalPrinterColumns:
    - name: Schedule
      type: string
      jsonPath: .spec.schedule
    - name: Phase
      type: string
      jsonPath: .status.phase
    - name: Age
      type: date
      jsonPath: .metadata.creationTimestamp
```

### Экземпляр пользовательского ресурса

```yaml
apiVersion: example.io/v1alpha1
kind: Backup
metadata:
  name: db-nightly
spec:
  target: postgres-prod
  schedule: "0 3 * * *"
  retentionDays: 14
```

### Команды

```bash
kubectl apply -f crd-backup.yaml
kubectl apply -f backup.yaml
kubectl get backups
```

## Дополнительная информация

### CRD vs Aggregated API

| Критерий                  | CRD                                  | Aggregated API                             |
| ------------------------- | ------------------------------------ | ------------------------------------------ |
| Развертывание             | Обычный YAML манифест                | Отдельный API‑сервер и Kubernetes Service  |
| Валидация/Дефолты         | Схема OpenAPI, статически            | Полная произвольная логика в коде          |
| Гибкость/Производительность | Достаточно для большинства сценариев | Максимальная гибкость, тонкий контроль     |
