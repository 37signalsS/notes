# Kubernetes-операторы: Автоматизация управления приложениями

## Определения

**Kubernetes-оператор** — это доменно-специфический [контроллер](./control_plane_architecture.md), который расширяет API Kubernetes для создания, настройки и управления жизненным циклом сложных stateful-приложений от имени пользователя. Он инкапсулирует операционные знания и автоматизирует задачи, которые обычно требуют вмешательства человека.

**Custom Resource Definitions (CRD)** — это механизм Kubernetes для расширения API. Подробнее см. [CRD](./kubernetes_crd.md).

## Основные концепции

Операторы решают проблему управления сложными приложениями, которые требуют специфических операций (резервное копирование, восстановление, обновления, кластеризация), выходящих за рамки стандартных контроллеров вроде `Deployment`.

### Идея операторского паттерна

- **Декларативность:** Пользователь описывает *что* он хочет получить в CR (желаемое состояние), а не *как* это сделать.
- **Контур управления (Reconciliation Loop):** Оператор постоянно наблюдает за текущим состоянием ресурсов в кластере и шаг за шагом приводит его к желаемому состоянию, описанному в CR.
- **Идемпотентность:** Каждый цикл согласования (`reconcile`) безопасен при повторах и не вызывает нежелательных изменений, если система уже в нужном состоянии.
- **Реактивность:** Оператор реагирует на события от API-сервера (изменения в CR, зависимых ресурсах), а также на внутренние метрики или внешние зонды.
- **Прозрачность:** Оператор сообщает о своем состоянии через поле `.status` в CR, стандартные события Kubernetes (`Events`) и метрики Prometheus.

### Составные части оператора

- **Custom Resource Definition (CRD):** API, определяющий доменную модель ([см. заметку о CRD](./kubernetes_crd.md)).
- **Контроллер:** Процесс, реализующий `reconciliation loop` — см. [архитектура Control Plane](./control_plane_architecture.md).
- **RBAC:** Минимально необходимые права доступа для управления ресурсами.
- **Лидер-элекция:** Механизм, гарантирующий, что в каждый момент времени активна только одна реплика оператора (для отказоустойчивости).
- **Вебхуки (опционально):** Для валидации, мутации или конвертации версий CR.
- **Метрики, события и логи:** Для обеспечения наблюдаемости.

### Модель зрелости операторов

- **L1 (Basic Install):** Автоматизирует установку приложения.
- **L2 (Seamless Upgrades):** Управляет обновлениями приложения и его конфигурации, выполняя необходимые проверки.
- **L3 (Full Lifecycle):** Управляет резервным копированием, восстановлением и другими задачами жизненного цикла.
- **L4 (Deep Insights):** Предоставляет метрики, логи и аналитику о состоянии приложения.
- **L5 (Autopilot):** Автоматически настраивает производительность, выполняет автомасштабирование и самовосстановление на основе предиктивных действий.

## Внутреннее устройство: взаимодействие с контроллером

Взаимодействие оператора с кластером строится вокруг событийной модели, кэширования и идемпотентной функции `Reconcile`. Большинство операторов на Go используют библиотеку **`controller-runtime`**.

### Роль `controller-runtime` и `Manager`

- **Manager:** Инициализирует и запускает все компоненты оператора: клиент для общения с API, схему известных типов (GVK), кэш, вебхуки и сами контроллеры.
- **Контроллер:** Регистрирует источники событий (основной CR и зависимые ресурсы) и `Reconcile`-функцию.
- **Лидер-элекция:** Предотвращает одновременную активность нескольких реплик оператора.

### Поток событий и цикл согласования

1. **List & Watch:** Контроллер подписывается на события для интересующих его ресурсов. Сначала выполняется `list` для получения исходного снимка состояния всех ресурсов на определённый момент (определяется полем `resourceVersion`), а затем открывается `watch` для инкрементального получения событий.
2. **Informer / DeltaFIFO / Cache:** Информер получает события и пропускает их через структуру `DeltaFIFO`, которая отслеживает изменения с момента последнего известного `resourceVersion`. Затем изменения "мержатся" (merging) во внутреннее хранилище кэша. Это позволяет контроллеру всегда иметь актуальное состояние объектов в памяти без постоянных запросов к `kube-apiserver`, тем самым кардинально снижая нагрузку на API.
3. **Work Queue:** Информер генерирует события (создание/удаление/модификация), и ключ объекта (например, `namespace/name`) помещается в рабочую очередь. Очередь управляет повторными попытками при ошибках (с экспоненциальной задержкой) и дедуплицирует однотипные запросы (rate limiting).
4. **Reconcile:** Контроллер извлекает ключ из очереди и вызывает функцию `Reconcile`. Эта функция — ядро оператора.

### Сопоставление ролей

| Компонент        | Роль                                   | Где реализуется                 |
| ---------------- | -------------------------------------- | ------------------------------- |
| **Operator**     | Доменная логика, политика, схемы CRD   | Приложение с Manager и контроллерами |
| **Controller**   | Реакция на события, reconcile-цикл     | `controller-runtime`, `client-go`   |
| **Informer/Cache** | Эффективный доступ к состоянию кластера | `client-go`, `shared cache`       |
| **Work Queue**   | Управление обработкой и повторами      | `controller-runtime queue`      |
| **Status/Conditions** | Наблюдаемость и сигнализация о состоянии | Подресурс `status` в CR         |

### Контракт и паттерны функции `Reconcile`

Функция `Reconcile` получает запрос, находит по нему CR и выполняет основной цикл:

1. **Получение и проверка CR:** Загружает актуальное состояние CR из кэша или API.
2. **Обработка удаления:** Если у объекта установлен `deletionTimestamp`, запускает логику очистки (финализаторы).
3. **Сравнение состояния:** Сравнивает желаемое состояние (`spec`) с фактическим состоянием в кластере.
4. **Действие (Act):** Создает, обновляет или удаляет зависимые ресурсы (`Deployment`, `Service` и т.д.), чтобы привести фактическое состояние к желаемому.
5. **Обновление статуса:** Записывает наблюдаемое состояние в поле `.status` CR.
6. **Возврат результата:** Возвращает результат, указывая, нужно ли повторить обработку (`RequeueAfter`) или была ошибка.

```go
// Примерная структура Reconcile-функции
func (r *Reconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
  var cr MyApp
  if err := r.client.Get(ctx, req.NamespacedName, &cr); err != nil {
    return ctrl.Result{}, client.IgnoreNotFound(err)
  }

  // 1. Логика финализаторов для корректного удаления
  if !cr.ObjectMeta.DeletionTimestamp.IsZero() {
    // ... run finalizers ...
    return ctrl.Result{}, nil
  }

  // 2. Чтение фактического состояния зависимостей
  // 3. Применение diff: создание/обновление/удаление ресурсов
  // 4. Обновление Status/Conditions
  
  return ctrl.Result{RequeueAfter: time.Minute}, nil
}
```

### Важные паттерны реализации

- **Owner References:** Привязка зависимых объектов к основному CR. Это обеспечивает автоматическую сборку мусора: при удалении CR Kubernetes удалит все дочерние объекты.
- **Finalizers:** Механизм для упорядоченного удаления. Оператор добавляет финализатор к CR; при удалении CR Kubernetes ждет, пока оператор не завершит очистку и не удалит финализатор.
- **Status Subresource:** Использование подресурса `/status` для разделения прав на изменение `spec` (пользователь) и `status` (контроллер).
- **Predicates:** Фильтрация событий, чтобы не перегружать очередь обработки (например, игнорировать изменения только в `status`).
- **Map-функции:** Сопоставление событий по зависимым ресурсам обратно к владельцу (например, изменение `Deployment` инициирует `Reconcile` для владеющего им CR).

## Практические сценарии

### Сравнение подходов

| Критерий | Helm chart | Стандартные контроллеры (Deployment) | Operator |
| :--- | :--- | :--- | :--- |
| **Жизненный цикл** | Развернуть/обновить | Управление подами | Полный цикл: конфиг, миграции, бэкапы, failover |
| **Реакция на события**| Нет постоянного цикла | Ограничена уровнем объекта (поды) | Постоянный reconcile и доменная логика |
| **Состояние приложения**| Не учитывает | Низкоуровневое (поды) | Доменные статусы и проверки готовности |
| **Автовосстановление**| Базовое (перезапуск пода) | Базовое (перезапуск пода) | Сложные сценарии восстановления |

### Типовые сценарии использования

- Управление кластерами баз данных и брокеров: инициализация, репликация, failover, шифрование, обновления.
- Управление сертификатами и PKI: выпуск, ротация, продление.
- Резервное копирование и восстановление.
- Шардирование и масштабирование на уровне доменной логики.
- Канареечные обновления приложений со сложными проверками.

### Пример Custom Resource

Минимальный объект, описывающий кластер БД, которым управляет оператор:

```yaml
apiVersion: db.example.com/v1
kind: PostgresCluster
metadata:
  name: prod-db
spec:
  version: "15.3"
  instances: 3
  storage:
    size: 200Gi
    className: fast-ssd
  backup:
    enabled: true
    schedule: "0 */6 * * *"
status:
  phase: Creating
  readyInstances: 1
  lastBackup: "2024-12-01T12:00:00Z"
```

## Дополнительная информация

**Инструменты для разработки операторов:**

- **[Kubebuilder](https://book.kubebuilder.io/)** — фреймворк от Kubernetes SIGs для быстрого создания операторов на Go с использованием `controller-runtime`. Предоставляет готовую структуру проекта, генерацию кода и манифестов.
- **[Operator SDK](https://sdk.operatorframework.io/)** — инструмент от Red Hat, поддерживающий создание операторов на Go, Ansible и Helm. Включает CLI для генерации проекта, тестирования и упаковки.
- **[controller-runtime](https://github.com/kubernetes-sigs/controller-runtime)** — базовая библиотека, используемая обоими фреймворками. Предоставляет абстракции для контроллеров, кэширования, очередей и вебхуков.

**Популярные операторы:**

- **Prometheus Operator** — автоматизация развертывания и управления Prometheus, Alertmanager.
- **Cert Manager** — управление SSL/TLS сертификатами, интеграция с Let's Encrypt.
- **Strimzi** — управление Apache Kafka в Kubernetes.
- **Cloud Native PostgreSQL (CNPG)** — управление кластерами PostgreSQL с репликацией и бэкапами.
- **VictoriaMetrics Operator** — развертывание стека мониторинга VictoriaMetrics.

**Тестирование операторов:**

- **Unit-тесты** — тестирование логики `Reconcile` с моками клиента Kubernetes.
- **Integration-тесты** — запуск в test-кластере (envtest) с реальным API-сервером.
- **E2E-тесты** — развертывание оператора в реальном кластере и проверка полного жизненного цикла.
