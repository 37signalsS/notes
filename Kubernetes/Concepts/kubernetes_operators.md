# Kubernetes-операторы: автоматизация управления приложениями

## Определения

**Kubernetes-оператор** — это метод расширения API кластера, который использует [пользовательские ресурсы (CRD)](./kubernetes_crd.md) для управления сложными приложениями и их компонентами. Операторы позволяют инкапсулировать **эксплуатационные знания** (Operational Knowledge) администраторов и разработчиков в программный код, автоматизируя задачи, которые обычно выполняются вручную.

В отличие от стандартных контроллеров Kubernetes (таких как Deployment или StatefulSet), операторы обладают глубокими знаниями о предметной области приложения (Domain-specific knowledge). Это позволяет им выполнять сложные операции: миграции схем баз данных, настройку репликации, ротацию сертификатов и восстановление после специфических сбоев.

## Основные концепции

### Контур согласования (Reconciliation Loop)

Центральным механизмом оператора является цикл **Reconcile**. В отличие от простых скриптов, оператор работает по принципу **Level-triggered** (состояние), а не **Edge-triggered** (событие):
*   **Декларативность**: Пользователь описывает в CR желаемое состояние (Desired State).
*   **Наблюдение (Observe)**: Оператор постоянно отслеживает изменения через Watch API и запрашивает текущее состояние (Current State) ресурсов.
*   **Анализ (Analyze)**: Вычисляется разница (Diff) между желаемым и текущим состоянием.
*   **Действие (Act)**: Оператор выполняет операции для достижения цели.

Использование **Level-triggered** подхода гарантирует надежность: даже если оператор пропустил событие (например, из-за перезагрузки), в следующем цикле он увидит актуальное состояние и исправит расхождения.

### Финализаторы (Finalizers)

**Finalizers** — это ключи в метаданных объекта (`metadata.finalizers`), которые блокируют его окончательное удаление из etcd до тех пор, пока оператор не выполнит необходимые действия по очистке.
*   **Механизм**: Когда пользователь удаляет объект, Kubernetes устанавливает `deletionTimestamp`, но не удаляет запись, если список финализаторов не пуст.
*   **Действие оператора**: Контроллер видит флаг удаления, выполняет Cleanup-логику (например, удаляет внешние диски, облачные балансировщики или записи в DNS) и удаляет свой финализатор из списка.
*   **Завершение**: После удаления последнего финализатора объект окончательно удаляется системой.

### Условия статуса (Status Conditions)

Использование слайса `.status.conditions` является стандартом де-факто для обеспечения наблюдаемости (observability). Каждое условие должно содержать:
*   `Type`: Тип состояния (например, `Ready`, `Synced`, `Progressing`).
*   `Status`: Текущее значение (`True`, `False` или `Unknown`).
*   `Reason`: Краткая, машиночитаемая причина изменения (CamelCase, например `DatabaseReady`).
*   `Message`: Подробное, человекочитаемое сообщение о состоянии.

### Выбор лидера (Leader Election)

Для обеспечения высокой доступности (HA) несколько экземпляров одного оператора могут работать одновременно, но только один из них является **Лидером**.
*   Лидер берет на себя выполнение цикла согласования, в то время как остальные находятся в режиме ожидания (Standby).
*   Механизм реализуется через ресурс `Lease` в API Kubernetes. Если лидер падает, другой экземпляр захватывает блокировку и продолжает работу.

### Фильтрация событий (Predicates)

Для оптимизации производительности операторы используют **Predicates**. Они позволяют контроллеру игнорировать обновления, которые не требуют повторного согласования. Например, можно пропускать события, если изменились только метаданные (метки), но `spec` объекта остался прежним, что снижает нагрузку на API-сервер и Control Plane.

### Веб-перехватчики (Webhooks)

Веб-перехватчики — это HTTP-колбэки, которые API-сервер Kubernetes вызывает при обработке запросов. Они часто используются в связке с операторами и CRD для реализации пользовательской логики:

*   **Mutating Webhooks (Мутирующие)**: Позволяют изменять объект перед его сохранением в etcd (например, автоматическая вставка sidecar-контейнеров или установка меток).
*   **Validating Webhooks (Валидирующие)**: Принимают или отклоняют запросы на основе сложной бизнес-логики, которую нельзя описать через стандартные схемы OpenAPI или CEL.
*   **Conversion Webhooks (Конвертирующие)**: Обеспечивают плавный переход между разными версиями CRD (например, с `v1alpha1` на `v1`), трансформируя структуру объекта «на лету».
*   **Authentication Webhooks (Аутентифицирующие)**: Позволяют интегрировать внешние системы проверки подлинности для запросов к API.

Подробнее о механизмах расширения API: [CRD в Kubernetes](./kubernetes_crd.md).

### Современные стандарты реализации (2025/2026)

1.  **Server-Side Apply (SSA)**: Современный стандарт для внесения изменений. Вместо классического цикла "Read-Modify-Write" операторы отправляют только те поля, которыми они "владеют" (Field Ownership). Это предотвращает конфликты с другими контроллерами (например, HPA или sidecar-инжекторами) и позволяет API-серверу объединять изменения корректно.
2.  **CEL-валидация (K8s 1.30+)**: Использование **Common Expression Language** внутри CRD для проверки данных на уровне API-сервера. В современных инсталляциях это заменяет сложные Validating Webhooks, снижая задержки и упрощая архитектуру оператора.
3.  **Управление Sidecar-контейнерами (K8s 1.29+)**: Операторы должны использовать нативную поддержку Sidecar-контейнеров (init-контейнеры с `restartPolicy: Always`). Это гарантирует, что вспомогательные сервисы (прокси, логи) запускаются до основного приложения и завершаются только после него.

## Жизненный цикл и разработка

### Ключевые компоненты

1.  **Пользовательские ресурсы (CRD и CR)**: Определяют «желаемое состояние» приложения.
2.  **Контроллер (Controller)**: Основной мозг оператора. Содержит логику управления и реализует **цикл согласования (Reconciliation Loop)**.
3.  **Informers и Caches**: Механизмы `controller-runtime`, которые поддерживают локальную копию состояния кластера для быстрого доступа без постоянных запросов к API-серверу.
4.  **Workqueue**: Очередь задач, куда попадают события от Informers. Обеспечивает последовательную обработку и механизмы повторных попыток (back-off) при ошибках.
5.  **Operator Lifecycle Manager (OLM)**: Инструментарий для управления установкой, обновлением и жизненным циклом самих операторов в кластере.

### Наблюдаемость операторов (Observability)

Для DevOps/SRE критично обеспечить наблюдаемость не только управляемых приложений, но и самого оператора:

*   **Метрики `controller-runtime`**: Любой оператор, построенный на Kubebuilder/Operator SDK, автоматически экспонирует стандартные метрики:
    *   `controller_runtime_reconcile_total` — количество Reconcile-вызовов (по контроллеру и результату: `succeeded`, `failed`, `requeued`).
    *   `controller_runtime_reconcile_errors_total` — ошибки Reconcile (ключевая метрика для алертинга).
    *   `controller_runtime_reconcile_time_seconds` — латентность Reconcile.
    *   `workqueue_depth` — глубина очереди задач (индикатор перегрузки).
    *   `workqueue_queue_duration_seconds` — время ожидания в очереди.
*   **Логирование**: Операторы используют `logr` (структурированные логи). Уровень логирования настраивается через флаг `-v=<N>` (0 — ошибки, 1 — общая информация, 2 — отладочная информация, >3 — трассировка). В production рекомендуется уровень `1`.
*   **Health Endpoints**: Стандартные HTTP-эндпоинты `/healthz` (liveness) и `/readyz` (readiness) для kubelet. Агрессивные liveness-пробы могут убить healthy оператор при высокой нагрузке — настраивайте `initialDelaySeconds` и `timeoutSeconds` осторожно.
*   **Events**: Операторы должны генерировать Kubernetes Events при важных состояниях (успех/ошибка Reconcile, валидация CR). Events доступны через `kubectl describe` и API.

### Процесс разработки

1.  **Проектирование архитектуры**: Определение функциональных (управление ресурсами) и нефункциональных требований (производительность, HA).
2.  **Определение CRD**: Создание схем данных с использованием аннотаций в коде для генерации манифестов.
3.  **Настройка среды**: Использование фреймворков **Kubebuilder** или **Operator SDK**.
4.  **Реализация Reconcile**: Написание логики на Go, которая реагирует на изменения и приводит систему в желаемое состояние.
5.  **Тестирование**:
    *   **Unit-тесты**: Проверка отдельных функций (валидация, вычисления) без взаимодействия с кластером.
    *   **envtest**: Запуск тестов против реального Control Plane (API-сервер + etcd) без подов. Гарантирует корректность работы со схемами и RBAC. Используйте для тестирования интеграции с API, валидации CRD и коротких Reconcile-циклов.
    *   **E2E тесты**: Проверка в реальном кластере (Kind/Minikube). Запускают полный жизненный цикл оператора: установка CRD, создание CR, проверка reconciliation, удаление с финализаторами. Обязательны перед релизом.
    *   **Интеграционные тесты с的竞争**: Проверка корректной работы оператора при одновременном доступе к ресурсам (параллельные Reconcile, конфликты SSA). Используют`.

### Модель зрелости (Operator Capability Model)

*   **L1 (Basic Install)**: Автоматизированная установка и базовая настройка.
*   **L2 (Seamless Upgrades)**: Управление обновлениями версий, миграция схем данных.
*   **L3 (Full Lifecycle)**: Автоматизация резервного копирования, восстановления и очистки данных.
*   **L4 (Deep Insights)**: Предоставление специфичных метрик, алертов и анализа производительности.
*   **L5 (Autopilot)**: Автоматическое масштабирование и самовосстановление логики приложения.

## Практические сценарии

### Сравнение: Deployment vs Operator

| Характеристика | Стандартный Deployment | Kubernetes Operator |
| :--- | :--- | :--- |
| **Область знаний** | Только запуск контейнеров | Специфика приложения (логика БД, очереди) |
| **Обновление** | RollingUpdate (постепенно) | Сложные миграции, очистка кешей, паузы |
| **Масштабирование** | Только количество реплик | Реконфигурация шардов, балансировка данных |
| **Отказоустойчивость** | Перезапуск пода | Выбор нового мастера БД, переназначение ролей |

### Пример Custom Resource (PostgreSQL)

Декларативное описание кластера для оператора CloudNativePG:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: prod-db
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:16
  storage:
    size: 100Gi
  backup:
    barmanObjectStore:
      destinationPath: s3://backups/
      s3Credentials:
        name: s3-creds
```
