# Kubernetes-операторы: автоматизация управления приложениями

## Определения

**Kubernetes-оператор** — это специализированное приложение (контроллер), которое расширяет API кластера для автоматизации полного жизненного цикла сложных приложений. Операторы позволяют перенести **эксплуатационные знания** администраторов и разработчиков (Operational Knowledge) в программный код.

Операторы развивают концепцию CRD. В то время как CRD позволяют определять структуру пользовательских ресурсов, операторы автоматизируют управление ими:
*   **Автоматизация жизненного цикла**: развертывание, масштабирование, восстановление после сбоев и резервное копирование.
*   **Последовательность и эффективность**: гарантия того, что приложения обрабатываются единообразно, что снижает операционную нагрузку.
*   **Интеграция**: Операторы взаимодействуют напрямую с API-сервером, отслеживая изменения в кастомных ресурсах и выполняя необходимые действия.

### Веб-перехватчики (Webhooks)

Веб-перехватчики — это HTTP-колбэки, которые API-сервер Kubernetes вызывает при обработке запросов. Они часто используются в связке с операторами и CRD для реализации пользовательской логики:

*   **Mutating Webhooks (Мутирующие)**: Позволяют изменять объект перед его сохранением в etcd (например, автоматическая вставка sidecar-контейнеров или установка меток).
*   **Validating Webhooks (Валидирующие)**: Принимают или отклоняют запросы на основе сложной бизнес-логики, которую нельзя описать через стандартные схемы OpenAPI или CEL.
*   **Conversion Webhooks (Конвертирующие)**: Обеспечивают плавный переход между разными версиями CRD (например, с `v1alpha1` на `v1`), трансформируя структуру объекта «на лету».
*   **Authentication Webhooks (Аутентифицирующие)**: Позволяют интегрировать внешние системы проверки подлинности для запросов к API.

Подробнее о механизмах расширения API: [CRD в Kubernetes](./kubernetes_crd.md).

## Жизненный цикл и рабочий процесс

Концепция операторов была введена прежде всего для решения задачи управления **приложениями с состоянием (Stateful)**. Если приложения без состояния (например, веб-серверы) легко масштабируются стандартными средствами Kubernetes, то базы данных требуют сложной логики: резервное копирование, восстановление, синхронизация реплик.

### Ключевые компоненты оператора:

1.  **Пользовательские ресурсы (CRD и CR)**: Определяют «желаемое состояние» приложения.
2.  **Контроллер (Controller)**: Основной мозг оператора. Содержит логику управления и реализует **цикл согласования (Reconciliation Loop)**.
    *   **Наблюдение (Observe)**: Отслеживает изменения ресурсов через API.
    *   **Анализ (Analyze)**: Сравнивает желаемое состояние с фактическим.
    *   **Действие (Act)**: Выполняет операции для достижения цели (создание подов, настройка хранилищ).
3.  **Обработчики событий (Event Handlers)**: Механизмы внутри контроллера, реагирующие на события в кластере (создание, изменение, удаление объектов) и запускающие цикл согласования.
4.  **Клиентские библиотеки**: Используются контроллером для взаимодействия с API Kubernetes (например, `client-go` для Go или `kubernetes` для Python).
5.  **Operator Lifecycle Manager (OLM)**: Инструментарий для управления установкой, обновлением и жизненным циклом самих операторов в кластере.

## Основные концепции

### Принципы работы: Контур согласования (Reconciliation Loop)

Центральным механизмом оператора является цикл **Reconcile**. В отличие от простых скриптов, оператор работает по принципу **Level-triggered** (состояние), а не **Edge-triggered** (событие):
*   **Декларативность**: Пользователь описывает в CR желаемое состояние (Desired State).
*   **Наблюдение (Observe)**: Оператор запрашивает текущее состояние (Current State) управляемых ресурсов через API.
*   **Анализ (Analyze)**: Вычисляется разница (Diff) между желаемым и текущим состоянием.
*   **Действие (Act)**: Оператор выполняет действия для устранения разницы.

Использование **Level-triggered** подхода гарантирует, что даже если оператор пропустил событие (например, из-за перезагрузки), в следующем цикле он увидит текущее состояние и исправит его.

### Современные стандарты реализации (2025/2026)

1.  **Server-Side Apply (SSA)**: Современный стандарт для внесения изменений. Вместо классического цикла "Read-Modify-Write" операторы отправляют только те поля, которыми они владеют. Это предотвращает конфликты с другими контроллерами (например, HPA или sidecar-инжекторами).
2.  **CEL-валидация**: Использование **Common Expression Language** внутри CRD для проверки данных на уровне API-сервера. Это избавляет от необходимости разрабатывать и поддерживать сложные Validating Webhooks.
3.  **Управление Sidecar-контейнерами**: С версии K8s 1.29+ операторы должны использовать нативные Sidecar-контейнеры (init-контейнеры с `restartPolicy: Always`). Это решает проблемы с порядком запуска и завершения вспомогательных сервисов (логи, прокси).

## Жизненный цикл и рабочий процесс

Оператор постоянно отслеживает изменения в спецификации (`spec`) кастомного ресурса и управляет связанными объектами Kubernetes для поддержания желаемого состояния.

**Упрощенный жизненный цикл:**
1.  **Наблюдение**: Контроллер видит создание или изменение объекта CR через API-сервер.
2.  **Анализ**: Вычисляется разница между `spec` (желаемое) и текущим состоянием кластера.
3.  **Действие**: Оператор создает или обновляет вспомогательные ресурсы:
    *   **ServiceAccount (SA)** и роли для доступа.
    *   **ConfigMap (CM)** и **Secrets** для конфигурации.
    *   **Deployments** или **StatefulSets** для запуска приложения.
    *   **Services** для обеспечения доступа.
4.  **Обновление статуса**: После выполнения действий оператор обновляет поле `status` в CR, предоставляя информацию о готовности и метрики для мониторинга.

## Этапы разработки оператора

Процесс разработки современного оператора включает следующие шаги:

1.  **Проектирование архитектуры**: Определение функциональных (создание/обновление ресурсов) и нефункциональных требований (производительность, отказоустойчивость, обработка сбоев).
2.  **Определение кастомного ресурса**: Создание манифестов **CRD**, описывающих схему данных и правила валидации.
3.  **Настройка среды**: Выбор фреймворка (напр., **Operator SDK** или **Kubebuilder**) и установка зависимостей.
4.  **Инициализация проекта**: Создание скелета приложения (напр., `operator-sdk init`).
5.  **Реализация логики контроллера**: Написание кода (преимущественно на **Go**), реализующего цикл согласования (Reconciliation).
6.  **Реализация управления ресурсами**: Использование клиентских библиотек для взаимодействия с API Kubernetes (создание, патчинг, удаление дочерних объектов).
7.  **Сборка и распространение**: Упаковка оператора в Docker-образ и подготовка Helm-чарта для развертывания.

## Модель зрелости операторов (Operator Capability Model)

*   **L1 (Basic Install)**: Автоматизированная установка и базовая настройка через Helm или ресурсы.
*   **L2 (Seamless Upgrades)**: Управление обновлениями версий, миграция схем данных.
*   **L3 (Full Lifecycle)**: Автоматизация резервного копирования, восстановления и удаления старых данных.
*   **L4 (Deep Insights)**: Предоставление специфичных для приложения метрик, алертов и анализа производительности.
*   **L5 (Autopilot)**: Автоматическое горизонтальное и вертикальное масштабирование, самовосстановление при сбоях логики приложения.

## Проектирование и разработка

### Инструментарий
*   **controller-runtime**: Основная библиотека на Go, на которой строятся современные операторы. Предоставляет механизмы кэширования (Informers), лидер-элекции и управления очередями.
*   **Kubebuilder**: Фреймворк, генерирующий скелет проекта и манифесты.
*   **Operator SDK**: Расширенная надстройка над Kubebuilder, поддерживающая также Ansible и Helm-based операторы.

### Тестирование
Критически важным является использование **envtest**. Это позволяет запускать тесты против реального API-сервера и etcd (без полноценного узла), что гарантирует корректность работы со схемами CRD, RBAC и CEL-правилами.

## Практические сценарии

### Сравнение: Deployment vs Operator

| Характеристика | Стандартный Deployment | Kubernetes Operator |
| :--- | :--- | :--- |
| **Область знаний** | Только запуск контейнеров | Специфика приложения (логика БД, очереди) |
| **Обновление** | RollingUpdate (постепенно) | Сложные миграции, очистка кешей, паузы |
| **Масштабирование** | Только количество реплик | Реконфигурация шардов, балансировка данных |
| **Отказоустойчивость** | Перезапуск пода | Выбор нового мастера БД, переназначение ролей |

### Пример Custom Resource (PostgreSQL)

Декларативное описание кластера, которое обрабатывает оператор:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: main-db
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:16
  storage:
    size: 100Gi
  backup:
    barmanObjectStore:
      destinationPath: s3://backups/
      s3Credentials:
        name: s3-creds
```
