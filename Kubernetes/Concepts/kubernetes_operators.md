# Kubernetes-операторы: автоматизация управления приложениями

## Определения

**Kubernetes-оператор** — это специализированное приложение, разработанное специально для Kubernetes, которое расширяет API кластера для автоматизации полного жизненного цикла сложных приложений (преимущественно Stateful). Операторы взаимодействуют напрямую с API-сервером и могут изменять его состояние в ответ на определенные события, обеспечивая механизм динамического реагирования. Они инкапсулируют операционные знания администратора (deployment, scaling, backup, recovery) в программный код.

Операторы работают в связке с **Custom Resource Definitions (CRD)**, которые определяют новые типы объектов в API кластера. Подробнее: [CRD в Kubernetes](./kubernetes_crd.md).

## Основные концепции

### Принципы работы: Контур согласования (Reconciliation Loop)

Центральным механизмом оператора является цикл **Reconcile**. В отличие от простых скриптов, оператор работает по принципу **Level-triggered** (состояние), а не **Edge-triggered** (событие):
*   **Декларативность**: Пользователь описывает в CR желаемое состояние (Desired State).
*   **Наблюдение (Observe)**: Оператор запрашивает текущее состояние (Current State) управляемых ресурсов через API.
*   **Анализ (Analyze)**: Вычисляется разница (Diff) между желаемым и текущим состоянием.
*   **Действие (Act)**: Оператор выполняет действия для устранения разницы.

Использование **Level-triggered** подхода гарантирует, что даже если оператор пропустил событие (например, из-за перезагрузки), в следующем цикле он увидит текущее состояние и исправит его.

### Современные стандарты реализации (2025/2026)

1.  **Server-Side Apply (SSA)**: Современный стандарт для внесения изменений. Вместо классического цикла "Read-Modify-Write" операторы отправляют только те поля, которыми они владеют. Это предотвращает конфликты с другими контроллерами (например, HPA или sidecar-инжекторами).
2.  **CEL-валидация**: Использование **Common Expression Language** внутри CRD для проверки данных на уровне API-сервера. Это избавляет от необходимости разрабатывать и поддерживать сложные Validating Webhooks.
3.  **Управление Sidecar-контейнерами**: С версии K8s 1.29+ операторы должны использовать нативные Sidecar-контейнеры (init-контейнеры с `restartPolicy: Always`). Это решает проблемы с порядком запуска и завершения вспомогательных сервисов (логи, прокси).

### Модель зрелости операторов (Operator Capability Model)

*   **L1 (Basic Install)**: Автоматизированная установка и базовая настройка через Helm или ресурсы.
*   **L2 (Seamless Upgrades)**: Управление обновлениями версий, миграция схем данных.
*   **L3 (Full Lifecycle)**: Автоматизация резервного копирования, восстановления и удаления старых данных.
*   **L4 (Deep Insights)**: Предоставление специфичных для приложения метрик, алертов и анализа производительности.
*   **L5 (Autopilot)**: Автоматическое горизонтальное и вертикальное масштабирование, самовосстановление при сбоях логики приложения.

## Проектирование и разработка

### Инструментарий
*   **controller-runtime**: Основная библиотека на Go, на которой строятся современные операторы. Предоставляет механизмы кэширования (Informers), лидер-элекции и управления очередями.
*   **Kubebuilder**: Фреймворк, генерирующий скелет проекта и манифесты.
*   **Operator SDK**: Расширенная надстройка над Kubebuilder, поддерживающая также Ansible и Helm-based операторы.

### Тестирование
Критически важным является использование **envtest**. Это позволяет запускать тесты против реального API-сервера и etcd (без полноценного узла), что гарантирует корректность работы со схемами CRD, RBAC и CEL-правилами.

## Практические сценарии

### Сравнение: Deployment vs Operator

| Характеристика | Стандартный Deployment | Kubernetes Operator |
| :--- | :--- | :--- |
| **Область знаний** | Только запуск контейнеров | Специфика приложения (логика БД, очереди) |
| **Обновление** | RollingUpdate (постепенно) | Сложные миграции, очистка кешей, паузы |
| **Масштабирование** | Только количество реплик | Реконфигурация шардов, балансировка данных |
| **Отказоустойчивость** | Перезапуск пода | Выбор нового мастера БД, переназначение ролей |

### Пример Custom Resource (PostgreSQL)

Декларативное описание кластера, которое обрабатывает оператор:

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: main-db
spec:
  instances: 3
  imageName: ghcr.io/cloudnative-pg/postgresql:16
  storage:
    size: 100Gi
  backup:
    barmanObjectStore:
      destinationPath: s3://backups/
      s3Credentials:
        name: s3-creds
```
