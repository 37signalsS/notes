# Etcd: распределённое хранилище Kubernetes

## Определение

**etcd** — это высоконадежное распределённое хранилище данных в формате «ключ-значение», обеспечивающее согласованное хранение состояния кластера Kubernetes. Оно служит централизованным хранилищем (Single Source of Truth) для всех объектов: подов, сервисов, конфигураций и прав доступа.

**Ключевая роль:** В архитектуре Kubernetes etcd является «мозгом» кластера. Это единственный компонент, который сохраняет состояние (stateful). Если данные в etcd утеряны или повреждены, кластер перестаёт функционировать как управляемая система, даже если рабочие узлы продолжают исполнять контейнеры.

## Основные концепции

### Взаимодействие с Control Plane

`kube-apiserver` является **единственным** компонентом кластера, который напрямую взаимодействует с etcd. Все остальные части системы (планировщик, контроллеры, kubelet) получают информацию о состоянии только через запросы к API-серверу.

**Преимущества такой архитектуры:**
*   **Централизованная валидация:** API-сервер проверяет корректность данных (Admission Control) перед записью.
*   **Оптимистическая блокировка:** Использование `resourceVersion` предотвращает конфликты при одновременном редактировании.
*   **Абстракция:** Компоненты работают с высокоуровневыми объектами, не заботясь о деталях реализации хранилища.

### Внутренняя модель данных (MVCC)

etcd использует модель **MVCC** (Multi-Version Concurrency Control). В отличие от традиционных БД, etcd не перезаписывает данные, а создает новые ревизии.

*   **Revision (Ревизия):** Глобальный счетчик всего хранилища. Каждая операция записи инкрементирует это число.
*   **ModRevision:** Ревизия последнего изменения конкретного ключа. В Kubernetes это значение транслируется в поле `metadata.resourceVersion`.
*   **Generation:** Счетчик изменений спецификации объекта (увеличивается контроллерами, не etcd напрямую).

### Структура префиксов в Kubernetes

Все объекты организованы по иерархическим путям с префиксом `/registry`. Основные пути:

| Префикс | Описание |
| :--- | :--- |
| `/registry/pods/` | Спецификации и статусы подов. |
| `/registry/services/` | Определения сервисов и выделенные ClusterIP. |
| `/registry/secrets/` | Зашифрованные (или нет) объекты Secret. |
| `/registry/configmaps/` | Конфигурационные карты. |
| `/registry/events/` | Системные события (имеют короткий TTL, обычно 1 час). |
| `/registry/leases/` | Heartbeats узлов и блокировки лидеров (Leader Election). |
| `/registry/apiextensions.k8s.io/` | Определения CRD (Custom Resource Definitions). |

### Консенсус и отказоустойчивость (Raft)

etcd использует алгоритм **Raft**, требующий **кворума** для принятия любых изменений.

**Таблица отказоустойчивости:**

| Узлов | Кворум | Допустимые отказы | Рекомендация |
| :--- | :--- | :--- | :--- |
| 1 | 1 | 0 | Только для тестов / Edge (k3s). |
| 3 | 2 | 1 | Стандарт для малых и средних Production. |
| 5 | 3 | 2 | Высокая доступность для крупных кластеров. |
| 7 | 4 | 3 | Максимум (далее растет задержка репликации). |

*Подробнее о механике выбора лидера:* **[Алгоритм Raft](../../etcd/raft_consensus.md)**.

## Архитектура и топологии

### Stacked etcd (Совмещенный)

etcd запускается как статический под на тех же узлах, что и `kube-apiserver`.
*   **Плюсы:** Простота развертывания (стандарт для `kubeadm`), минимальная сетевая задержка до API-сервера.
*   **Минусы:** Конкуренция за ресурсы (CPU, RAM, Disk I/O) с другими компонентами Control Plane.

### External etcd (Выделенный)

etcd выносится на отдельные выделенные узлы.
*   **Плюсы:** Максимальная стабильность, изоляция нагрузки, возможность независимого масштабирования.
*   **Минусы:** Требуется больше серверов, сложнее настройка сертификатов и сетевой связности.

*Сравнение топологий:* **[Архитектура Control Plane](./control_plane_architecture.md#размещение-etcd-stacked-vs-external)**.

## Безопасность

1.  **mTLS (Mutual TLS):** Обязательное использование клиентских и серверных сертификатов для всех взаимодействий.
2.  **Encryption at Rest:** Шифрование данных «на лету» перед записью в etcd. API-сервер использует файл `EncryptionConfiguration`. Детально см. **[Хранение секретов в etcd](../Base/secrets/etcd_storage.md)**.
3.  **Authentication/Authorization:** etcd поддерживает собственные роли (RBAC), но в Kubernetes обычно полагаются на ограничение доступа к самому API-серверу.

## Практические сценарии

### Обслуживание: Компакция и дефрагментация

Из-за MVCC база etcd постоянно растет.
*   **Compaction (Компакция):** Удаление истории старых ревизий. API-сервер делает это автоматически (параметр `--etcd-compaction-interval`, обычно 5 мин).
*   **Defragmentation (Дефрагментация):** Физическое освобождение места на диске. Должна выполняться периодически (например, через CronJob), так как компакция лишь помечает место как свободное внутри БД.

### Работа с etcdctl

Для диагностики на мастере (Stacked):

```bash
export ETCDCTL_API=3
alias k-etcdctl="etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key"

# Проверка статуса и лидера
k-etcdctl endpoint status -w table
```

### Резервное копирование

```bash
k-etcdctl snapshot save /backup/etcd-$(date +%Y%m%d).db
```
*Важно:* Для восстановления также необходим файл `EncryptionConfiguration`. Подробнее: **[Кластеризация и восстановление etcd](../../etcd/clustering_and_recovery.md)**.

## Требования к производительности

etcd — самый требовательный к I/O компонент.
*   **Диск:** Только NVMe SSD. Задержка `fsync` (метрика `etcd_disk_wal_fdatasync_duration_seconds`) должна быть **< 10 мс**.
*   **Процессор:** Минимум 2 ядра. Высокая нагрузка на CPU при десериализации Protobuf в крупных кластерах.
*   **Сеть:** RTT между узлами etcd **< 10 мс**.

## Устранение неисправностей (Troubleshooting)

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `database space exceeded` | Достигнут лимит размера БД (по умолчанию 2GB). | Выполнить компакцию + дефрагментацию; увеличить `--quota-backend-bytes`. |
| `request entity too large` | Объект (напр., ConfigMap) > 1MB. | Разбить объект или хранить в PV; увеличить `--max-request-bytes`. |
| `etcdserver: leader changed` | Нестабильность сети или медленный диск. | Проверить задержки диска и RTT сети. |
| `mvcc: required revision has been compacted` | Watcher отстал от процесса компакции. | Увеличить интервал компакции или оптимизировать контроллеры. |
