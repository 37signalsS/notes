# Etcd: распределённое хранилище Kubernetes

## Определение

**etcd** — это высоконадежное распределённое хранилище данных в формате «ключ-значение», обеспечивающее согласованное хранение состояния кластера Kubernetes. Оно служит единственным источником истины (Single Source of Truth) для всех объектов: подов, сервисов, конфигураций и прав доступа.

**Ключевая роль:** В архитектуре Kubernetes etcd является «мозгом» кластера. Если данные в etcd утеряны или повреждены, кластер перестаёт функционировать как управляемая система, даже если рабочие узлы продолжают исполнять контейнеры.

## Основные концепции

### Взаимодействие с Control Plane

`kube-apiserver` является **единственным** компонентом кластера, который напрямую взаимодействует с etcd. Все остальные части системы (планировщик, контроллеры, kubelet) получают информацию о состоянии только через запросы к API-серверу.

**Преимущества такой архитектуры:**
*   **Централизованная валидация:** API-сервер проверяет корректность данных перед записью в etcd.
*   **Аудит и безопасность:** Все изменения проходят через единую точку контроля.
*   **Абстракция:** Остальные компоненты не зависят от внутренней структуры хранения etcd.

### Модель данных и префиксы

Kubernetes использует etcd в режиме **API v3**. Данные хранятся в бинарном формате (Protobuf). Все объекты организованы по иерархическим путям с префиксом `/registry`:

*   `/registry/pods/<namespace>/<name>` — данные о подах.
*   `/registry/services/endpoints/<namespace>/<name>` — данные о сервисах.
*   `/registry/secrets/<namespace>/<name>` — секреты.

Для наблюдения за изменениями используется механизм **Watch**, который позволяет контроллерам мгновенно реагировать на появление или изменение объектов без постоянного опроса (polling).

### Консенсус и отказоустойчивость

etcd использует алгоритм консенсуса **Raft**, который гарантирует строгую согласованность данных.
*   **Кворум:** Для подтверждения записи требуется согласие большинства узлов (например, 2 из 3 или 3 из 5).
*   **Рекомендация для Production:** Рекомендуется использовать нечетное количество узлов (3 или 5). Увеличение до 7 и более узлов повышает отказоустойчивость, но снижает производительность на запись из-за накладных расходов на репликацию.
*   **Подробнее:** [Алгоритм Raft](../../etcd/raft_consensus.md).

### Обслуживание: Компакция и дефрагментация

В отличие от традиционных БД, etcd хранит историю изменений (MVCC). Это приводит к постоянному росту базы данных.
*   **Компакция (Compaction):** Процесс удаления старых ревизий ключей. В Kubernetes API-сервер автоматически инициирует компакцию каждые 5 минут (настраивается).
*   **Дефрагментация (Defragmentation):** Компакция помечает место как свободное, но не возвращает его операционной системе. Дефрагментация необходима для физического освобождения места на диске и предотвращения ошибки `database space exceeded`.
*   **Подробнее:** [MVCC и компакция](../../etcd/mvcc_versioning_and_compaction.md).

## Безопасность

1.  **Транспортная безопасность (TLS/mTLS):** Все соединения между API-сервером и узлами etcd, а также между самими узлами etcd, должны быть защищены сертификатами. Использование mTLS (взаимная проверка) является обязательным стандартом.
2.  **Шифрование данных (Encryption at Rest):** Сами данные в файле базы данных etcd хранятся в открытом виде (секреты закодированы в base64). Для защиты от кражи носителей используется механизм `EncryptionConfiguration` на уровне API-сервера. Подробнее: [Хранение секретов в etcd](../Base/secrets/etcd_storage.md).
3.  **NodeRestriction:** Admission-контроллер, ограничивающий доступ узлов к данным, которые им не принадлежат.

## Практические сценарии

### Настройка интеграции с kube-apiserver

Параметры подключения задаются в манифесте API-сервера (`/etc/kubernetes/manifests/kube-apiserver.yaml`):

```bash
--etcd-servers=https://127.0.0.1:2379
--etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
--etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
--etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key
```

### Работа с etcdctl в Kubernetes

Для диагностики и управления etcd на мастере удобно настроить alias с путями к сертификатам:

```bash
export ETCDCTL_API=3
alias k-etcdctl="etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key"

# Проверка состояния кластера
k-etcdctl endpoint health
# Просмотр списка ключей ресурсов
k-etcdctl get /registry --prefix --keys-only
```

### Резервное копирование (Snapshot)

Снапшот — это полная копия состояния кластера в определенный момент времени.

```bash
k-etcdctl snapshot save /var/lib/kube-backups/etcd-snapshot-$(date +%F).db
```

При аварии восстановление производится с помощью `etcdutl` (или `etcdctl snapshot restore`) перед запуском сервиса etcd. Подробнее: [Кластеризация и восстановление etcd](../../etcd/clustering_and_recovery.md).

### Альтернативы etcd (Kine и k3s)

В малых кластерах (Edge, IoT, разработка) использование etcd может быть избыточным из-за потребления ресурсов. Проект **Kine** позволяет заменить etcd на реляционные БД (SQLite, PostgreSQL, MySQL), транслируя вызовы etcd API в SQL-запросы.
*   **k3s** — популярный дистрибутив, использующий Kine + SQLite по умолчанию.
*   **Подробнее:** [Альтернативы и безопасность](./etcd_alternatives_and_security.md).

## Дополнительная информация

### Требования к инфраструктуре

*   **Диск:** Только SSD/NVMe. etcd крайне чувствителен к задержкам записи (fsync).
*   **Сеть:** Задержка между узлами (RTT) должна быть менее 10 мс.
*   **CPU/RAM:** Минимум 2 ядра и 4 ГБ RAM для стабильной работы небольшого кластера.
