# Etcd: распределённое хранилище Kubernetes

## Определения

**Etcd** — распределённое согласованное хранилище ключ-значение, используемое в Kubernetes как единственный источник правды (Single Source of Truth) для всех объектов и состояний кластера. Является ключевым компонентом [Control Plane](./control_plane_architecture.md).

**Назначение в Kubernetes:** Хранение метаданных всех объектов кластера (Pods, Deployments, Services, Secrets, ConfigMaps и других).

## Основные концепции

### Роль в архитектуре Kubernetes

`kube-apiserver` является **единственным** компонентом, который напрямую взаимодействует с `etcd`. Все остальные компоненты (планировщик, контроллеры, `kubelet`) обращаются к состоянию кластера только через API-сервер. Такая архитектура обеспечивает централизованный контроль, валидацию и аудит всех изменений.

### Ключевые свойства

Etcd обладает характеристиками, критичными для работы Kubernetes:

* **Согласованность (CP по CAP)** — строгая согласованность через кворум. Подробнее: [CAP-теорема](../../Databases/Concepts/cap_theorem.md).
* **Raft** — алгоритм консенсуса с лидером, обеспечивающий репликацию данных. Подробнее: [Алгоритм Raft](../../etcd/raft_consensus.md).
* **Watch** — уведомления об изменениях в реальном времени, основа работы контроллеров.
* **MVCC** — версионирование через ревизии, позволяющее читать состояние на момент времени. Подробнее: [MVCC и версионирование](../../etcd/mvcc_versioning_and_compaction.md).

### Хранение данных Kubernetes

Все объекты Kubernetes хранятся с префиксом `/registry`:

```
/registry/<resource-type>/<namespace>/<resource-name>
```

Например: `/registry/pods/default/nginx`, `/registry/secrets/kube-system/coredns-token`.

Данные сериализуются в бинарный формат (Protobuf) перед записью, поэтому прямое чтение из etcd показывает нечитаемые данные.

## Практические сценарии

### Оперативное управление

Для взаимодействия с etcd используется утилита `etcdctl` (API v3). Базовые команды включают запись, чтение, создание снапшотов.

Полный список практических сценариев: [Практические сценарии etcd](./etcd_operations.md).

### Резервное копирование

Регулярное создание снапшотов etcd — обязательная практика для production-кластеров. Снапшоты должны храниться вне кластера.

Процедура восстановления из снапшота: [Кластеризация и восстановление](../../etcd/clustering_and_recovery.md).

### Мониторинг

Критические метрики для мониторинга включают размер базы данных, задержки `fsync`, состояние кворума, количество неудачных запросов.

Настройка алертинга: [Мониторинг etcd](../../etcd/etcd_monitoring.md).

## Дополнительная информация

### Альтернативы etcd

В некоторых сценариях (k3s, тестовые среды) etcd может быть заменён на SQL-базы через Kine. Подробнее: [Альтернативы и безопасность](./etcd_alternatives_and_security.md).

### Безопасность

Для защиты данных в etcd используется шифрование на уровне kube-apiserver (EncryptionConfiguration) и TLS для всего трафика.

### Требования к инфраструктуре

* **Диск:** Только SSD/NVMe. Быстрые накопители с низкой задержкой `fsync`:
  * Рекомендуется: **<10 мс**.
  * Для нагруженных кластеров: **<2 мс**.
* **Сеть:** Задержка между узлами <10 мс. Влияние сетевой задержки на запись является линейным — чем выше RTT, тем ниже пропускная способность.
* **CPU/RAM:** Выделенные ресурсы. Etcd чувствителен к переключению контекста и нехватке CPU для обработки heartbeats.

> **Миф о масштабировании:** Добавление большего количества узлов etcd (например, переход с 3 на 5 или 7) **не увеличивает** производительность записи, а наоборот, снижает её из-за необходимости репликации на большее число узлов. Увеличение числа узлов повышает только отказоустойчивость (доступность).

### Версии и совместимость

Etcd и Kubernetes имеют матрицу совместимости. Перед обновлением необходимо проверять поддерживаемые версии в официальной документации Kubernetes.
