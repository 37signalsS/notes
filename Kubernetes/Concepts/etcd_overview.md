# etcd: распределённое хранилище Kubernetes

**Актуально для:** Kubernetes 1.30+ / etcd 3.5.x, 3.6.x

## Определения

*   **etcd** — высоконадёжное распределённое транзакционное хранилище данных формата «ключ-значение» с открытым исходным кодом, использующее алгоритм консенсуса Raft и модель версионирования MVCC. Является единственным компонентом Kubernetes, сохраняющим состояние кластера (Single Source of Truth).
*   **Raft** — алгоритм распределённого консенсуса, гарантирующий согласованность данных между узлами кластера даже при частичных сетевых сбоях и отказах меньшинства участников.
*   **MVCC (Multi-Version Concurrency Control)** — механизм многоверсионного управления параллельным доступом. Любая модификация объекта не перезаписывает данные на диске, а порождает новую ревизию ключа.
*   **BoltDB (bbolt)** — встраиваемая транзакционная база данных на базе B+tree, используемая etcd в качестве постоянного низкоуровневого движка хранения (backend storage). Работает через механизм отображения файлов в память (`mmap`).
*   **treeIndex** — структура данных в оперативной памяти etcd (B-дерево), хранящая соответствие ключей их историческим MVCC-ревизиям и смещениям в BoltDB.
*   **Revision (Ревизия)** — 64-битный глобальный монотонно растущий счётчик etcd, инкрементируемый при каждой успешной транзакции записи (Put/Txn).
*   **ModRevision** — номер ревизии etcd, при которой ключ был создан или изменён в последний раз. В Kubernetes напрямую транслируется в строковое поле `metadata.resourceVersion`.
*   **Watch Cache** — встроенный кольцевой буфер в памяти `kube-apiserver`, кэширующий потоки событий от etcd для разгрузки хранилища от множественных клиентских `watch`-запросов контроллеров и kubelet.
*   **Кворум (Quorum)** — строгое большинство голосующих членов кластера ($Q = \lfloor N/2 \rfloor + 1$), необходимое для фиксации записей в логе Raft и выбора лидера.
*   **Learner Node** — вспомогательный член кластера etcd, который принимает репликацию лога и синхронизирует состояние, но не имеет права голоса и не учитывается при расчёте кворума до завершения синхронизации и промоушена.
*   **Stacked etcd (Совмещённый)** — топология развёртывания, при которой etcd запускается в виде статических подов на тех же Control Plane-узлах, что и `kube-apiserver`.
*   **External etcd (Выделенный)** — топология развёртывания, при которой etcd вынесен на отдельный независимый кластер серверов (bare-metal или виртуальные машины), изолированный от компонентов Control Plane.
*   **Compaction (Компакция)** — логическая очистка истории устаревших MVCC-ревизий до определённого порога, освобождающая место внутри файла BoltDB, но не возвращающая его файловой системе хоста.
*   **Defragmentation (Дефрагментация)** — физическое сжатие файла базы данных BoltDB на диске с возвратом неиспользуемых страниц операционной системе.
*   **Alarm `NOSPACE`** — состояние аварийной защиты etcd, активирующееся при превышении лимита размера базы данных (`--quota-backend-bytes`). Блокирует все операции записи, переводя кластер в режим read-only.

## Архитектура и основные концепции

### Место etcd в Control Plane Kubernetes

В архитектуре Kubernetes `kube-apiserver` выступает **единственным клиентом**, имеющим право прямого сетевого и криптографического доступа к etcd. Ни один другой компонент — будь то `kube-scheduler`, `kube-controller-manager`, сетевые CNI-агенты или узловой `kubelet` — не взаимодействует с etcd напрямую.

```text
[ kube-scheduler ]      [ kube-controller-manager ]      [ kubelet / pods ]
        │                            │                            │
        └────────────────────────────┼────────────────────────────┘
                                     │ HTTPS REST (443 / 6443)
                                     ▼
                          +────────────────────+
                          │   kube-apiserver   │ (AuthN, AuthZ, Admission Control,
                          +─────────┬──────────+  Schema Validation, Watch Cache)
                                    │
                                    │ gRPC + mTLS (порт 2379)
                                    ▼
                          +────────────────────+
                          │    etcd Cluster    │ (Raft Consensus, MVCC, BoltDB)
                          +────────────────────+
```

**Преимущества архитектурной изоляции:**
1.  **Централизованная валидация и бизнес-логика:** `kube-apiserver` осуществляет аутентификацию, авторизацию (RBAC), мутацию и валидацию (Admission Controllers) до формирования транзакции в etcd.
2.  **Оптимистическая блокировка (OCC):** предотвращение состояния гонки (race conditions) при параллельной модификации объектов через проверку поля `resourceVersion` (соответствующего `modRevision` в etcd). Если версия в запросе устарела, API-сервер возвращает статус `409 Conflict`.
3.  **Кэширование и мультиплексирование:** контроллеры создают сотни подписок на изменения ресурсов (`watch`). API-сервер объединяет эти запросы через внутренний Watch Cache, защищая etcd от перегрузки.

### Внутреннее устройство: MVCC, treeIndex и BoltDB

Архитектура etcd разделена на два фундаментальных слоя: оперативный индекс в памяти (`treeIndex`) и персистентное дисковое хранилище (`BoltDB` / `bbolt`), дополненное журналом опережающей записи (`WAL`).

```text
                               Клиентский запрос (gRPC)
                                          │
                                          ▼
                         +─────────────────────────────────+
                         │          Raft Consensus         │
                         +────────────────┬────────────────+
                                          │
                  ┌───────────────────────┴───────────────────────┐
                  ▼                                               ▼
     +────────────────────────+                     +──────────────────────────+
     │ Write-Ahead Log (WAL)  │                     │    MVCC Subsystem        │
     │ - Append-only          │                     │  +────────────────────+  │
     │ - fdatasync() на диск  │                     │  │ treeIndex (B-Tree) │  │
     +────────────────────────+                     │  │ (Keys -> Revisions)│  │
                                                    │  +─────────┬──────────+  │
                                                    │            │             │
                                                    │            ▼             │
                                                    │  +────────────────────+  │
                                                    │  │  BoltDB (B+ Tree)  │  │
                                                    │  │  (Revs -> Value)   │  │
                                                    │  │  mmap() на диск    │  │
                                                    │  +────────────────────+  │
                                                    +──────────────────────────+
```

1.  **Write-Ahead Log (WAL):** перед тем как изменение будет применено, операция сериализуется и записывается в журнал WAL. Запись сопровождается системным вызовом `fdatasync()` (или `fsync()`), гарантирующим физический сброс кэша контроллера диска на энергонезависимый носитель.
2.  **treeIndex (In-Memory B-Tree):** хранит имена ключей (например, `/registry/pods/default/nginx`), их поколения (generation) и список связанных ревизий (`created`, `modRevision`). Позволяет мгновенно находить ревизии ключа и диапазоны ревизий без обращения к диску.
3.  **BoltDB (bbolt на диске):** в качестве ключей в BoltDB используются 64-битные номера ревизий, а значениями являются сериализованные бинарные тела объектов Kubernetes. BoltDB отображает весь файл базы данных в адресное пространство процесса с помощью `mmap`. Это обеспечивает минимальную задержку произвольного чтения, однако требует достаточного объёма физической оперативной памяти хоста.

### Механизм консенсуса Raft и кворум

Кластер etcd использует протокол Raft, обеспечивающий строгую линеаризуемость (linearizable consistency) для операций записи и чтения.

*   **Роли узлов:**
    *   **Лидер (Leader):** обрабатывает все входящие запросы на запись, генерирует записи в Raft-логе, рассылает их последователям (`AppendEntries`) и отправляет периодические heartbeats.
    *   **Последователь (Follower):** принимает реплицируемый лог от лидера. При переадресации запроса на запись направляет его текущему лидеру.
    *   **Кандидат (Candidate):** инициирует выборы нового лидера при отсутствии heartbeats от текущего лидера в течение `election-timeout`.
    *   **Ученик (Learner):** неголосующий узел, используемый для безопасного расширения кластера без риска потери кворума.
*   **Формула кворума:**
    $$Q = \left\lfloor \frac{N}{2} \right\rfloor + 1$$
    где $N$ — общее число голосующих участников кластера.

**Матрица отказоустойчивости:**

| Число узлов ($N$) | Кворум ($Q$) | Допустимое число отказов ($F$) | Практическое применение в on-premise |
| :--- | :--- | :--- | :--- |
| **1** | 1 | 0 | Лабораторные стенды, edge-системы (k3s). Не обеспечивает отказоустойчивость. |
| **3** | 2 | 1 | Стандартный baseline для большинства production-кластеров. Выдерживает отказ 1 ноды. |
| **5** | 3 | 2 | Высоконагруженные критичные кластеры. Выдерживает одновременный отказ 2 нод (или плановые работы + 1 сбой). |
| **7** | 4 | 3 | Редко используется. Увеличивает сетевую задержку консенсуса при минимальном росте стабильности. |

> [!IMPORTANT]
> **Почему кластер всегда должен состоять из нечётного числа узлов:**
> Чётное число узлов не увеличивает отказоустойчивость, а лишь ухудшает её: кластер из 4 узлов требует кворума в 3 узла и переносит отказ ровно 1 узла (как и кластер из 3 узлов), но при разделении сети 2:2 ни одна половина не сможет набрать кворум, что приводит к полной остановке записи.
> Кроме того, увеличение числа узлов **не повышает пропускную способность записи**, так как запись требует подтверждения от большинства; больше узлов означает больше сетевых RTT и рост латентности.

### Путь чтения, Watch и Watch Cache

etcd предоставляет базовые примитивы API: `Range` (чтение по ключу или диапазону), `Put` (запись), `DeleteRange` (удаление), `Txn` (транзакции) и `Watch` (потоковое отслеживание изменений).

*   **Linearizable Read vs Serializable Read:**
    *   *Linearizable Read (по умолчанию в etcd):* чтение проходит подтверждение у текущего лидера через кворум (механизм `ReadIndex`), исключая чтение устаревших данных («split-brain» чтения).
    *   *Serializable Read:* чтение напрямую из локального состояния узла без согласования с лидером. Обладает минимальной латентностью, но может вернуть устаревшие данные, если узел отстаёт по репликации.
*   **Работа Watch:** контроллеры подписываются на изменения диапазона ключей. При коммите новой ревизии etcd отправляет событие подписчикам по gRPC-потоку.
*   **Watch Cache в `kube-apiserver`:** API-сервер поддерживает кольцевой буфер недавних событий в оперативной памяти. Когда клиент запрашивает `LIST` или `WATCH` с определённой `resourceVersion`, запрос обслуживается из Watch Cache без обращения к etcd.
*   **Ошибка `required revision has been compacted`:** возникает, когда отстающий контроллер или агент пытается продолжить чтение с ревизии, которая уже была удалена из etcd процедурой компакции и отсутствует в кольцевом буфере API-сервера. Клиент обязан выполнить полный сброс кэша и повторный полный `LIST` ресурсов с последующим `WATCH` с текущей ревизии.

### Иерархия префиксов `/registry` в Kubernetes

Все метаданные кластера сохраняются с префиксом `/registry` (настраивается параметром `--etcd-prefix` в `kube-apiserver`, по умолчанию `/registry`):

| Префикс в etcd | Назначение и состав объектов | Формат данных | Особенности жизненного цикла |
| :--- | :--- | :--- | :--- |
| `/registry/pods/<ns>/<name>` | Спецификации и статусы подов | Protobuf | Высокая частота обновлений статусов контейнеров. |
| `/registry/services/specs/<ns>/<name>` | Описания сервисов, ClusterIP, порты | Protobuf | Относительно статичные объекты. |
| `/registry/secrets/<ns>/<name>` | Секреты (токены, сертификаты) | Protobuf / Зашифрован | При включённом Encryption at Rest хранятся в шифрованном виде. |
| `/registry/configmaps/<ns>/<name>` | Конфигурационные файлы | Protobuf | Могут достигать предельных размеров при хранении больших конфигов. |
| `/registry/events/<ns>/<name>` | Системные события кластера | Protobuf | **Главный драйвер роста БД.** Короткий TTL (1 час). Сотни тысяч записей в нестабильном кластере. |
| `/registry/leases/<ns>/<name>` | Node Leases и Leader Election | Protobuf | Heartbeats узлов (`kube-node-lease`). Регулярные обновления каждые 10 секунд. |
| `/registry/apiextensions.k8s.io/...` | Описания CustomResourceDefinition (CRD) | Protobuf | Регистрация пользовательских API-схем. |
| `/registry/<group>/<resource>/...` | Пользовательские объекты CRD | **JSON** | По умолчанию сериализуются в JSON, занимая больший объём памяти и диска. |

#### Изоляция событий в отдельный кластер etcd

При масштабировании on-premise кластеров до сотен узлов и тысяч подов поток событий (`Event`) начинает создавать до 70–80% всех транзакций записи в etcd. Для предотвращения раздувания базы данных и блокировки критических ресурсов Kubernetes официально поддерживает разделение хранилищ на уровне `kube-apiserver`:

```bash
# Фрагмент /etc/kubernetes/manifests/kube-apiserver.yaml
--etcd-servers=https://10.0.0.11:2379,https://10.0.0.12:2379,https://10.0.0.13:2379
--etcd-servers-overrides=/events#https://10.0.0.21:2379,https://10.0.0.22:2379,https://10.0.0.23:2379
```

Это гарантирует, что шторм событий при сбое сетевой инфраструктуры или падении подов не исчерпает квоту основного хранилища etcd и не заблокирует работу Control Plane.

## Архитектура и топологии размещения

### Stacked etcd (Совмещённый кластер)

Стандартная схема развёртывания инструментами автоматизации (включая `kubeadm`). Процесс etcd запускается в виде статического пода на каждом узле Control Plane под контролем локального `kubelet` (манифест `/etc/kubernetes/manifests/etcd.yaml`).

```text
[ Master Node 1 ]              [ Master Node 2 ]              [ Master Node 3 ]
┌───────────────────────────┐  ┌───────────────────────────┐  ┌───────────────────────────┐
│ kube-apiserver            │  │ kube-apiserver            │  │ kube-apiserver            │
│       │ (localhost:2379)  │  │       │ (localhost:2379)  │  │       │ (localhost:2379)  │
│       ▼                   │  │       ▼                   │  │       ▼                   │
│ etcd (static pod)         │  │ etcd (static pod)         │  │ etcd (static pod)         │
│   ├── WAL (NVMe)          │  │   ├── WAL (NVMe)          │  │   ├── WAL (NVMe)          │
│   └── BoltDB (NVMe)       │  │   └── BoltDB (NVMe)       │  │   └── BoltDB (NVMe)       │
└─────────────┬─────────────┘  └─────────────┬─────────────┘  └─────────────┬─────────────┘
              │                              │                              │
              └──────── Raft Peer Traffic (порт 2380, mTLS) ────────────────┘
```

*   **Преимущества:**
    *   Минимальные аппаратные затраты (не требуются выделенные серверы под БД).
    *   Локальное сетевое взаимодействие: `kube-apiserver` обращается к etcd через петлевой интерфейс (`https://127.0.0.1:2379`), исключая накладные расходы внешних коммутаторов.
    *   Синхронный жизненный цикл узла Control Plane и члена etcd.
*   **Недостатки и риски:**
    *   **Конкуренция за дисковый ввод-вывод (I/O Contention):** при интенсивном логировании `kube-apiserver` или сборке образов контейнерным рантаймом задержка `fsync` может скачкообразно расти, вызывая потерю лидерства etcd.
    *   **Связанный радиус поражения (Coupled Blast Radius):** аппаратный сбой или kernel panic ноды одновременно выводит из строя узел Control Plane и один из голосов кворума etcd.

### External etcd (Выделенный кластер)

Кластер etcd разворачивается на независимой группе физических серверов или изолированных виртуальных машин, управляемых через systemd.

*   **Преимущества:**
    *   **Полная изоляция ресурсов:** процессор, оперативная память и дисковая подсистема выделены исключительно под потребности etcd.
    *   **Независимый жизненный цикл:** возможность раздельного обновления операционной системы, версий etcd и регламентного перезапуска серверов без риска нарушения работы Control Plane Kubernetes.
    *   **Гибкое масштабирование:** независимое масштабирование пула серверов API и узлов БД.
*   **Недостатки:**
    *   Требуется в два раза больше серверных мощностей (минимум 3 узла etcd + 2-3 узла Control Plane).
    *   Каждый запрос API-сервера к etcd проходит через физическую сеть, добавляя задержку коммутации (RTT).

### Сравнительный анализ топологий для SRE/Sysadmin

| Критерий | Stacked etcd | External etcd |
| :--- | :--- | :--- |
| **Минимальное число серверов** | 3 узла (совмещённые роли) | 6 узлов (3 Control Plane + 3 etcd) |
| **Изоляция дискового ввода-вывода** | Низкая (конкуренция с K8s, логами, рантаймом) | **Полная** (выделенный контроллер/диск) |
| **Сетевая задержка к API** | Нулевая (localhost / 127.0.0.1) | 0.5–2 мс (физический LAN) |
| **Сложность управления PKI** | Низкая (автоматизация kubeadm) | Средняя (ручной выпуск или Ansible/Vault) |
| **Устойчивость к сбоям нод** | Потеря ноды = потеря Master + etcd | Потеря Master не влияет на кворум etcd |
| **Рекомендованный профиль** | Кластеры до 200–300 узлов | Крупные и критичные on-premise кластеры (300+ узлов) |

## Безопасность и сетевая изоляция

### Модель PKI: разделение центров сертификации

В production-конфигурациях Kubernetes строго применяется взаимная аутентификация по TLS (mTLS). Для исключения атак с повышением привилегий используется разделение на **два независимых центра сертификации (CA)**:

```text
               +──────────────────────────────────+
               │          etcd-ca.crt             │
               │   (/etc/kubernetes/pki/etcd/)    │
               +────────────────┬────────────────-+
                                │
       ┌────────────────────────┼────────────────────────┐
       ▼                        ▼                        ▼
+──────────────+         +──────────────+         +──────────────+
│  server.crt  │         │   peer.crt   │         │healthcheck...│
│ (порт 2379)  │         │ (порт 2380)  │         │  client.crt  │
+──────────────+         +──────────────+         +──────────────+

               +──────────────────────────────────+
               │            ca.crt                │ (Kubernetes Root CA)
               │      (/etc/kubernetes/pki/)      │
               +────────────────┬────────────────-+
                                │
                                ▼
               +──────────────────────────────────+
               │   apiserver-etcd-client.crt      │
               │   (CN: kube-apiserver-etcd-client│
               │    O: system:masters)            │
               +──────────────────────────────────+
```

1.  **etcd-ca (`/etc/kubernetes/pki/etcd/ca.crt`):** удостоверяет внутренние серверные сертификаты etcd (`server.crt` для порта 2379), peer-сертификаты для межсерверного обмена Raft (`peer.crt` для порта 2380) и локальный проверочный сертификат `healthcheck-client.crt`.
2.  **kubernetes-ca (`/etc/kubernetes/pki/ca.crt`):** выпускает клиентский сертификат `apiserver-etcd-client.crt`, с помощью которого `kube-apiserver` авторизуется в etcd.
3.  **Критическая ошибка конфигурации:** попытка использовать клиентский сертификат Kubernetes для обращения к peer-порту (2380) или использование `ca.crt` вместо `etcd/ca.crt` при запуске `etcdctl` приводит к ошибкам `bad certificate` или `x509: certificate signed by unknown authority`.

### Сетевая изоляция портов

Узлы etcd прослушивают два стандартных порта:
*   **Порт 2379 (Client Traffic):** приём клиентских gRPC-запросов от `kube-apiserver` и утилит управления (`etcdctl`). Доступ должен быть открыт **исключительно** IP-адресам узлов Control Plane.
*   **Порт 2380 (Peer Traffic):** протокольный обмен Raft (репликация лога, выборы лидера, heartbeats). Доступ должен быть открыт **строго** между IP-адресами членов кластера etcd.

**Пример изоляции через `nftables` (Linux bare-metal хост etcd):**

```bash
# Разрешить трафик к порту 2379 только от узлов Control Plane
nft add rule inet filter input ip saddr { 10.0.0.11, 10.0.0.12, 10.0.0.13 } tcp dport 2379 accept

# Разрешить трафик к порту 2380 только между членами etcd
nft add rule inet filter input ip saddr { 10.0.0.11, 10.0.0.12, 10.0.0.13 } tcp dport 2380 accept

# Заблокировать неавторизованные обращения к портам etcd
nft add rule inet filter input tcp dport { 2379, 2380 } drop
```

### Шифрование данных на диске (Encryption at Rest)

Сам etcd не выполняет прикладного шифрования сохраняемых структур данных. Шифрование объектов (в первую очередь `Secret` и `ConfigMap`) выполняется на стороне `kube-apiserver` до момента передачи бинарной нагрузки в gRPC-канал etcd.

Архитектура конфигурации `EncryptionConfiguration` и интеграция с on-premise системами управления ключами (HashiCorp Vault через KMS v2) подробно документированы в **[etcd: альтернативы и безопасность](./etcd_alternatives_and_security.md)** и **[Хранение секретов в etcd](../Base/secrets/etcd_storage.md)**.

## Системные требования и тюнинг производительности (Sysadmin / SRE)

Стабильность etcd напрямую определяет работоспособность всего кластера Kubernetes. Поскольку каждая транзакция требует синхронного сброса на диск и подтверждения кворума по сети, etcd крайне чувствителен к задержкам дискового ввода-вывода (I/O latency) и сети (network RTT).

### Требования к дисковой подсистеме

*   **Физический носитель:** строго локальные **NVMe SSD** корпоративного класса (PCIe Gen4/Gen5) с защитой от потери питания (Power Loss Protection, PLP). Категорически не допускается использование шпиндельных дисков (HDD) и сетевых блочных хранилищ (NFS, iSCSI, Ceph RBD), так как джиттер задержки в них приводит к флаппингу лидера.
*   **Метрика `fsync`:** время системного вызова `fdatasync()` для WAL (метрика `etcd_disk_wal_fsync_duration_seconds`) должно находиться на уровне:
    *   *Норма (p99):* **< 10 мс** (в идеале на NVMe < 1–2 мс).
    *   *Критический порог:* превышение **10–20 мс** вызывает пропуск heartbeats лидером, запуск внеплановых выборов и временную недоступность кластера на запись.
*   **Изоляция WAL:** при развёртывании External etcd или выделении отдельных дисков на Control Plane настоятельно рекомендуется разносить директорию WAL (`--wal-dir`) и основное хранилище BoltDB (`--data-dir`) на разные физические дисковые устройства.
*   **Опции монтирования ФС:** использовать файловые системы `ext4` или `xfs` с обязательной опцией отключения обновления времени доступа:
    ```text
    /dev/nvme0n1p1 /var/lib/etcd ext4 defaults,noatime,nodiratime 0 0
    ```

### Тюнинг ядра Linux (Kernel Tuning)

Для предотвращения зависания дисковых операций и защиты процесса etcd от вытеснения на хостах настраиваются следующие параметры ядра (`/etc/sysctl.d/99-etcd.conf`):

```ini
# Агрессивный фоновый сброс «грязных» страниц памяти на диск для исключения всплесков I/O
vm.dirty_background_ratio = 5
vm.dirty_ratio = 10

# Отключение использования Swap (подкачки)
vm.swappiness = 0

# Увеличение очередей сокетов для высокоинтенсивного gRPC трафика
net.core.somaxconn = 32768
net.ipv4.tcp_max_syn_backlog = 16384
```

Применение параметров:
```bash
sysctl --system
# → * Applying /etc/sysctl.d/99-etcd.conf ...
```

### Приоритезация процессов и защита от OOM

1.  **Приоритет ввода-вывода (I/O Scheduling):** для процесса etcd на bare-metal назначается наивысший приоритет через `ionice`:
    ```bash
    ionice -c2 -n0 -p $(pgrep etcd)
    ```
2.  **Приоритет планировщика CPU:** для потоков консенсуса устанавливается политика реального времени:
    ```bash
    chrt -r -p 99 $(pgrep etcd)
    ```
3.  **Защита от OOM Killer:** в статических подах kubeadm для etcd автоматически устанавливается `oomScoreAdj: -999`, предотвращающий принудительное завершение демона при дефиците памяти на хосте. При запуске через systemd параметр задаётся в unit-файле:
    ```ini
    [Service]
    OOMScoreAdjust=-999
    ```

### Требования к сети

*   **Сетевая задержка (RTT):** время кругового обращения пакета (Round Trip Time) между узлами etcd должно составлять **< 10 мс** (оптимально внутри одного ЦОД: < 1–2 мс).
*   **Географически распределённые инсталляции (Metro-кластеры):** если узлы etcd разнесены между дата-центрами с RTT более 20–30 мс, необходимо скорректировать параметры тайм-аутов в конфигурации etcd:
    ```bash
    # Значения по умолчанию рассчитаны на локальную сеть:
    --heartbeat-interval=250    # дефолт 100 мс (рекомендуется 250-500 мс для cross-DC)
    --election-timeout=1250     # дефолт 1000 мс (рекомендуется 5 * heartbeat-interval)
    ```

## Эксплуатация и обслуживание

### Жизненный цикл данных: MVCC, Компакция и Дефрагментация

Вследствие архитектуры MVCC каждая модификация или удаление ресурса добавляет новую ревизию. Без регламентного обслуживания файл базы данных непрерывно увеличивается в размерах до исчерпания установленной квоты.

```text
           +─────────────────────────────────────────────────────────────+
           │                     Файл BoltDB (на диске)                  │
           +─────────────────────────────────────────────────────────────+
                                          │
       [Ревизии 1..1000]         [Ревизии 1001..5000]        [Ревизии 5001..]
          Устаревшие                  Устаревшие                 Актуальные
       (логически удалены)        (логически удалены)              данные
                                          │
                                          ▼
                         Операция Компакции (Compaction)
              - Удаляет старые ревизии из treeIndex и BoltDB
              - Помечает страницы внутри BoltDB как «свободные» (freelist)
              - РАЗМЕР ФАЙЛА НА ДИСКЕ НЕ УМЕНЬШАЕТСЯ!
                                          │
                                          ▼
                        Операция Дефрагментации (Defrag)
              - Перечитывает актуальные страницы BoltDB
              - Перезаписывает файл базы на диске без «дыр»
              - Возвращает свободное дисковое пространство ОС
```

1.  **Компакция (Compaction):**
    *   В кластере Kubernetes компакцию выполняет `kube-apiserver` на базе параметра `--etcd-compaction-interval=5m`.
    *   **Предостережение SRE:** категорически запрещено включать флаг `--auto-compaction-retention` на стороне самого демона etcd, если он уже управляется API-сервером. Параллельная работа двух независимых алгоритмов компакции вызывает рассинхронизацию ревизий и провоцирует аварии `mvcc: required revision has been compacted`.
2.  **Дефрагментация (Defragmentation):**
    *   Компакция оставляет внутри файла BoltDB пустые страницы (freelist). Для их физического высвобождения требуется регулярная дефрагментация.
    *   Выполняется утилитой `etcdctl defrag`. В production-кластере дефрагментация проводится **строго последовательно по одному узлу**, с контролем восстановления кворума между шагами. Запуск дефрагментации через флаг `--cluster` недопустим, так как временная блокировка нескольких узлов приводит к потере кворума.
3.  **Квота размера базы (`--quota-backend-bytes`):**
    *   Значение по умолчанию: **2 ГБ** (2147483648 байт).
    *   Максимальный рекомендованный предел: **8 ГБ** (8589934592 байт).
    *   Увеличение квоты свыше 8 ГБ не рекомендуется сообществом etcd: структуры BoltDB и механизмы дефрагментации на больших файлах вызывают длительные секундные паузы в обслуживании запросов.

### Ключевые метрики Prometheus для SRE-мониторинга

| Метрика | Тип | Норма SRE | Критический порог / Alert | Описание и влияние на систему |
| :--- | :--- | :--- | :--- | :--- |

### Базовые команды проверки здоровья (etcdctl)

Для взаимодействия с etcd на хосте Control Plane задаются переменные окружения и сертификаты администратора:

```bash
# Экспорт переменных окружения для etcdctl v3
export ETCDCTL_API=3
export ETCDCTL_CACERT="/etc/kubernetes/pki/etcd/ca.crt"
export ETCDCTL_CERT="/etc/kubernetes/pki/etcd/server.crt"
export ETCDCTL_KEY="/etc/kubernetes/pki/etcd/server.key"
export ETCDCTL_ENDPOINTS="https://127.0.0.1:2379"

# 1. Проверка доступности конечной точки
etcdctl endpoint health
# → https://127.0.0.1:2379 is healthy: successfully committed proposal: took = 2.15418ms

# 2. Проверка статуса, размера базы и текущего лидера
etcdctl endpoint status --write-out=table
# → +------------------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+
# → |        ENDPOINT        |        ID        | VERSION | DB SIZE |  IN USE   | IS LEADER  | IS LEARNER| RAFT TERM  | RAFT INDEX         | ERRORS |
# → +------------------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+
# → | https://127.0.0.1:2379 | 8e9e05c52164694d |  3.5.15 |   42 MB |     38 MB |       true |     false |          4 |               5421 |        |
# → +------------------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+

# 3. Проверка активных аварийных сигналов (Alarms)
etcdctl alarm list
# → (пустой вывод означает отсутствие активных алармов)
```

Пошаговые процедуры создания резервных копий (`snapshot save`), восстановления кластера (`etcdutl snapshot restore`) и вывода узлов из эксплуатации приведены в специализированном руководстве: **[etcd: практические сценарии и обслуживание в Kubernetes](./etcd_operations.md)**.

| :--- | :--- | :--- | :--- |

| **`mvcc: required revision has been compacted`** | Клиентский watcher отстал от прогресса базы, а запрошенная ревизия удалена компакцией. | Логи `kube-apiserver` вида `reflector.go: ... compacted`. | Нормальное поведение при длительном сетевом разрыве между узлом и API-сервером. ## Лучшие практики (Best Practices)

1.  **Выделенные аппаратные ресурсы:**
    *   Всегда размещайте файлы базы данных etcd (`--data-dir`) и журнал транзакций (`--wal-dir`) на **локальных NVMe-накопителях**. Категорически исключите сетевые блочные устройства (NFS, iSCSI, Ceph).
    *   Отключайте Swap на всех узлах, где запущен etcd (`vm.swappiness = 0`), чтобы предотвратить попадание страниц BoltDB в файл подкачки.
2.  **Архитектура и сайзинг кластера:**
    *   Используйте **3 узла** для стандартных production-систем и **5 узлов** для особо ответственных инсталляций. Не создавайте кластеры из 7 и более узлов — это не увеличивает надёжность, но снижает производительность записи.
    *   Для кластеров размером более 300–500 рабочих узлов разделяйте хранилища: выносите поток `/events` в отдельный независимый кластер etcd через `--etcd-servers-overrides`.
3.  **Управление емкостью и обслуживание:**
    *   Настройте автоматическую дефрагментацию по регламентному расписанию (CronJob / Ansible) с обязательной проверкой статуса каждого узла перед переходом к следующему.
    *   Установите лимит базы данных `--quota-backend-bytes` на уровне **4–8 ГБ**, предварительно убедившись, что хост обладает достаточным объёмом свободной RAM для `mmap`.
4.  **Безопасность и PKI:**
    *   Изолируйте порты 2379 и 2380 на сетевом уровне с помощью аппаратных фаерволов или правил `nftables`/`iptables`. Ни один рабочий узел (Worker Node) не должен иметь сетевого маршрута к портам etcd.
    *   Никогда не объединяйте `etcd-ca` и `kubernetes-ca` в единый центр сертификации.
    *   Настройте непрерывный мониторинг срока действия TLS-сертификатов (метрики `etcd_server_certificate_expiry_timestamp_seconds` или проверки через Node Problem Detector).
5.  **Резервное копирование и Disaster Recovery:**
    *   Создавайте автоматические снапшоты etcd минимум раз в час и сохраняйте их на независимый сервер хранения резервных копий.
    *   После каждого создания снапшота производите автоматическую верификацию его целостности с помощью утилиты `etcdutl snapshot status <backup_file>`. Регулярно проводите учения по восстановлению кластера из снапшота на тестовом стенде.
