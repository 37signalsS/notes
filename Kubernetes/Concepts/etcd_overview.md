# Etcd: Распределённое хранилище

## Определения

**Etcd** — это распределённое, согласованное (consistent) хранилище типа "ключ-значение", используемое в Kubernetes как единственный источник правды (Single Source of Truth) для всех объектов и состояний кластера. Etcd построен на основе алгоритма консенсуса **Raft**, что обеспечивает его отказоустойчивость. От доступности и низкой задержки etcd напрямую зависит производительность `kube-apiserver` и всего кластера.

## Основные концепции

### Ключевые свойства

*   **Согласованность (CP по CAP):** Запись считается успешной только после подтверждения большинством узлов (кворумом).
*   **Raft и лидерство:** Все операции записи проходят через узел-лидер. Отказ лидера инициирует процесс переизбрания.
*   **Ревизии (Revisions):** Каждое изменение объекта увеличивает номер его ревизии. Это позволяет отслеживать историю изменений и реализовывать оптимистичные блокировки.
*   **Транзакции (Compare-and-Swap):** Поддерживает атомарные операции, которые выполняются только при совпадении текущей версии объекта.
*   **Механизм `watch`:** Позволяет клиентам подписываться на изменения по определенному префиксу ключей, получая обновления в реальном времени. Это основа для работы контроллеров Kubernetes.
*   **Аренда (Leases) и TTL:** Позволяет привязывать ключи к "аренде" с определенным временем жизни (TTL), по истечении которого они автоматически удаляются.
*   **Компакция (Compaction):** Процесс очистки устаревших ревизий для контроля размера базы данных.
*   **Снапшоты (Snapshots):** Возможность создания полных снимков состояния для резервного копирования и восстановления.

### Роль в Kubernetes

`kube-apiserver` является **единственным** компонентом, который напрямую взаимодействует с `etcd`. Все остальные компоненты (планировщик, контроллеры, `kubelet`) обращаются к состоянию кластера только через API. Такая архитектура обеспечивает централизованный контроль, валидацию и аудит всех изменений.

## Практические сценарии

### Эксплуатационные рекомендации

| Аспект | Рекомендации |
| :--- | :--- |
| **Размер кластера** | 3–5 членов; избегать чётного числа; не масштабировать без необходимости. |
| **Диск** | Использовать быстрые SSD с низкой задержкой `fsync`; отключать swap. |
| **Сеть** | Защищать трафик с помощью TLS; задержка (RTT) между узлами <10 мс. |
| **Ресурсы** | Выделять отдельные CPU и ОЗУ; избегать конкуренции с другими рабочими нагрузками. |
| **Обслуживание** | Регулярно выполнять компакцию и дефрагментацию; настроить мониторинг и алертинг на размер БД. |
| **Совместимость** | Проверять совместимость версий `etcd` и Kubernetes перед обновлением. |
| **Бэкапы** | Настроить периодическое создание снапшотов и хранить их вне кластера; тестировать процедуру восстановления. |

### Типовые операции `etcdctl`

Для работы с `etcd` используется утилита `etcdctl`.

```bash
# Установить переменные для подключения
export ETCDCTL_API=3
EP="https://10.0.0.11:2379,https://10.0.0.12:2379,https://10.0.0.13:2379"
CA=/etc/etcd/ca.crt; CERT=/etc/etcd/client.crt; KEY=/etc/etcd/client.key

# Проверить статус кластера
etcdctl --endpoints=$EP --cacert=$CA --cert=$CERT --key=$KEY endpoint status -w=table

# Записать и прочитать значение
etcdctl --endpoints=$EP --cacert=$CA --cert=$CERT --key=$KEY put /k8s/demo "value"
etcdctl --endpoints=$EP --cacert=$CA --cert=$CERT --key=$KEY get /k8s/demo

# Создать снапшот
etcdctl --endpoints=$EP --cacert=$CA --cert=$CERT --key=$KEY snapshot save /backup/etcd.snap
```

### Интеграция с `kube-apiserver`

`kube-apiserver` настраивается для работы с `etcd` с помощью следующих флагов:

```bash
# Фрагмент аргументов kube-apiserver
--etcd-servers=https://10.0.0.11:2379,https://10.0.0.12:2379,https://10.0.0.13:2379
--etcd-cafile=/etc/kubernetes/pki/etcd/ca.crt
--etcd-certfile=/etc/kubernetes/pki/apiserver-etcd-client.crt
--etcd-keyfile=/etc/kubernetes/pki/apiserver-etcd-client.key
```

## Дополнительная информация

### Безопасность и отказоустойчивость

*   **TLS** является обязательным для защиты трафика как между клиентами и серверами, так и между самими узлами `etcd`.
*   **Ограничение доступа** по сети и использование сертификатов с правильными `CN/OU` для разделения ролей.
*   **Потеря кворума** требует восстановления кластера из последнего снапшота.
*   **Шифрование "на лету" (at-rest):** Для защиты секретов в `etcd`, `kube-apiserver` может быть настроен на их шифрование перед записью.

    ```yaml
    # encryption-provider-config.yaml
    apiVersion: apiserver.config.k8s.io/v1
    kind: EncryptionConfiguration
    resources:
      - resources:
        - secrets
        providers:
        - aescbc:
            keys:
            - name: key1
              secret: <BASE64_ENCODED_SECRET_KEY>
        - identity: {} # Оставляет возможность читать незашифрованные секреты
    ```
