# Etcd: распределённое хранилище Kubernetes

## Определение

**etcd** — это высоконадёжное распределённое хранилище данных в формате «ключ-значение», обеспечивающее согласованное хранение состояния кластера Kubernetes. Оно служит **централизованным источником достоверных данных** для всех объектов: подов, сервисов, конфигураций и прав доступа. Любой объект Kubernetes, который существует «живьём», в конечном счёте является записью в etcd.

**Ключевая роль:** В архитектуре Kubernetes etcd является «мозгом» кластера. Это единственный компонент, который сохраняет состояние (stateful). Если данные в etcd утеряны или повреждены, кластер перестаёт функционировать как управляемая система, даже если рабочие узлы продолжают исполнять контейнеры.

## Основные концепции

### Взаимодействие с Control Plane

`kube-apiserver` является **единственным** компонентом кластера, который напрямую взаимодействует с etcd. Все остальные части системы (планировщик, контроллеры, kubelet) получают информацию о состоянии только через запросы к API-серверу.

**Преимущества такой архитектуры:**
*   **Централизованная валидация:** API-сервер проверяет корректность данных (Admission Control) перед записью.
*   **Оптимистическая блокировка:** Использование `resourceVersion` предотвращает конфликты при одновременном редактировании.
*   **Абстракция:** Компоненты работают с высокоуровневыми объектами, не заботясь о деталях реализации хранилища.

**Как API-сервер подключается к etcd:** `kube-apiserver` адресует etcd через флаги `--etcd-servers`, `--etcd-cafile`, `--etcd-certfile`, `--etcd-keyfile` (обычно в манифесте `/etc/kubernetes/manifests/kube-apiserver.yaml`). Все подключения выполняются по **HTTPS с mTLS** — как на стороне сервера (etcd), так и на стороне клиента (API-сервер). Ручной разбор флагов и практического доступа через `etcdctl` см. в [Практических сценариях](./etcd_operations.md).

### Внутренняя модель данных (MVCC)

etcd использует модель **MVCC** (Multi-Version Concurrency Control). В отличие от традиционных БД, etcd не перезаписывает данные, а создаёт новые ревизии.

*   **Revision (Ревизия):** Глобальный счетчик всего хранилища. Каждая операция записи инкрементирует это число.
*   **ModRevision:** Ревизия последнего изменения конкретного ключа. В Kubernetes это значение транслируется в поле `metadata.resourceVersion`.
*   **Generation:** Счетчик изменений спецификации объекта (увеличивается контроллерами, не etcd напрямую).

#### Путь чтения и Watch

etcd предоставляет три ключевых API-операции, на которых строится вся работа Kubernetes: **Get** (чтение), **Put** (запись) и **Watch** (подписка на изменения).

*   **Watch:** основной «двигатель» контроллеров и `kubelet`. Компоненты подписываются через механизм `watch` внутри kube-apiserver, и etcd уведомляет их о каждом изменении ключа в реальном времени (по диапазону ключей, например `/registry/pods/<ns>/`). Это позволяет системе работать реактивно, а не через постоянный polling.
*   **Watch Cache:** сам `kube-apiserver` не отдаёт каждый watch-запрос напрямую в etcd. Вместо этого он ведёт собственный кэш (Watch Cache), благодаря чему большинство `list/watch`-запросов клиентов удовлетворяются из кэша API-сервера, снижая нагрузку на etcd.
*   **Чтение через ревизии:** благодаря MVCC клиент может читать состояние базы «на определённой ревизии». Именно на этом построены механики `resourceVersion` и консистентного наблюдения за изменениями без гонок (list + watch с фиксированной ревизии).

Глубокий разбор внутреннего устройства (WAL, BoltDB, treeIndex) см. в [Архитектуре и концепциях etcd](../../etcd/architecture-and-concepts.md).

### Структура префиксов в Kubernetes

Все объекты организованы по иерархическим путям с префиксом `/registry`. Основные пути:

| Префикс | Описание |
| :--- | :--- |
| `/registry/pods/` | Спецификации и статусы подов. |
| `/registry/services/` | Определения сервисов и выделенные ClusterIP. |
| `/registry/secrets/` | Зашифрованные (или нет) объекты Secret. |
| `/registry/configmaps/` | Конфигурационные карты. |
| `/registry/events/` | Системные события (имеют короткий TTL, обычно 1 час). Чаще всего именно они вызывают штормовой рост базы в нестабильном кластере. |
| `/registry/leases/` | Heartbeats узлов и блокировки лидеров (Leader Election). |
| `/registry/apiextensions.k8s.io/` | Определения CRD (Custom Resource Definitions). |

> **Почему события — главный «пожиратель» места.** Объекты `Event` создаются на каждое изменение состояния (появление/перезапуск пода, изменение статуса), и при нестабильной работе кластера их количество может исчисляться сотнями тысяч. По умолчанию TTL событий в API-сервере — 1 час (`--event-ttl`), и каждое новое событие оставляет MVCC-ревизию. Подробнее о статистике по типам объектов и о выделении событий в отдельный кластер etcd — в разделе [Требования к производительности](#требования-к-производительности) ниже.

### Консенсус и отказоустойчивость (Raft)

etcd использует алгоритм **Raft**, требующий **кворума** для принятия любых изменений.

**Таблица отказоустойчивости:**

| Узлов | Кворум | Допустимые отказы | Рекомендация |
| :--- | :--- | :--- | :--- |
| 1 | 1 | 0 | Только для тестов / Edge (k3s). |
| 3 | 2 | 1 | Стандарт для малых и средних Production. |
| 5 | 3 | 2 | Высокая доступность для крупных кластеров. |
| 7 | 4 | 3 | Максимум (далее растет задержка репликации). |

**Как выбрать число узлов:** для большинства production-кластеров достаточно **3 узлов** (один отказ) или **5** (два отказа). Важно понимать, что увеличение числа узлов НЕ повышает производительность на запись — наоборот, каждая запись требует подтверждения от кворума (большинства), поэтому больше узлов = больше сетевых RTT и выше латентность. Ключевой вопрос — «сколько узлов кластер может позволить себе потерять одновременно»; обычно 3–5 узлов и есть оптимум.

Выбор нечётного числа узлов принципиален: чётный кластер из N узлов даёт ту же отказоустойчивость, что и N−1, но требует больше ресурсов и рискует «расколоться» на две равные половины без гарантированного кворума.

*Подробнее о механике выбора лидера и реальности «split-brain»:* **[Алгоритм Raft](../../etcd/raft_consensus.md)**.

## Архитектура и топологии

### Stacked etcd (Совмещенный)

etcd запускается как **статический под** на тех же узлах, что и `kube-apiserver`. В kubeadm это стандартный вариант: манифест `/etc/kubernetes/manifests/etcd.yaml` автоматически создаётся при инициализации кластера.
*   **Плюсы:** Простота развертывания (стандарт для `kubeadm`), минимальная сетевая задержка до API-сервера, единый жизненный цикл с Control Plane.
*   **Минусы:** Конкуренция за ресурсы (CPU, RAM, Disk I/O) с другими компонентами Control Plane; при падении ноды падает и её etcd.

### External etcd (Выделенный)

etcd выносится на отдельные выделенные узлы (вне кластера Kubernetes или на узлы без Control Plane-компонентов).
*   **Плюсы:** Максимальная стабильность, изоляция нагрузки, возможность независимого масштабирования и отдельного мониторинга/бэкапа.
*   **Минусы:** Требуется больше серверов, сложнее настройка сертификатов и сетевой связности; добавляется сетевой RTT между API-сервером и etcd.

*Сравнение топологий:* **[Архитектура Control Plane](./control_plane_architecture.md#размещение-etcd-stacked-vs-external)**. Детальное развертывание внешнего HA-кластера — **[Кластеризация и восстановление etcd](../../etcd/clustering_and_recovery.md)**.

## Безопасность

1.  **mTLS (Mutual TLS):** Обязательное использование клиентских и серверных сертификатов для всех взаимодействий. В стандартной kubeadm-схеме используются **два отдельных центра сертификации (CA)**: один — для peer-соединений (между самими узлами etcd), второй — для server/client-соединений (между `kube-apiserver` и etcd, а также между `etcdctl` и etcd). Смешивание этих CA — частая причина ошибок аутентификации.
2.  **Encryption at Rest:** Шифрование данных «на лету» перед записью в etcd. API-сервер использует файл `EncryptionConfiguration`. **Важно:** шифрование выполняет сам API-сервер до записи, поэтому «сырой» бэкап etcd содержит уже зашифрованные данные, но без файла `EncryptionConfiguration` и ключей дешифровать их невозможно. Детально см. **[Хранение секретов в etcd](../Base/secrets/etcd_storage.md)**.
3.  **Authentication/Authorization:** etcd поддерживает собственные роли (RBAC), но в Kubernetes обычно полагаются на ограничение доступа к самому API-серверу. Порт 2379 должен быть доступен (через Firewall/NetworkPolicy) только Control Plane-узлам.

## Практические сценарии

### Обслуживание: Компакция и дефрагментация

Из-за MVCC база etcd постоянно растет — старые ревизии не удаляются автоматически.
*   **Compaction (Компакция):** Логическое удаление истории старых ревизий (оставляет только актуальное состояние). В Kubernetes API-сервер делает это автоматически через параметр `--etcd-compaction-interval` (обычно 5 минут). Компакция лишь помечает место в файле БД как свободное, но **не возвращает его файловой системе**.
*   **Defragmentation (Дефрагментация):** Физическое освобождение места на диске и снижение фрагментации. Должна выполняться периодически (например, по CronJob), так как без неё БД продолжает «расти» на диске даже после компакции. В HA-кластере дефрагментацию выполняют **строго поочерёдно на каждом узле**, а не через `--cluster`, чтобы не потерять кворум.

Полные команды, алгоритм восстановления при `NOSPACE`, а также процедуры создания/проверки снапшотов приведены в [Практических сценариях и обслуживании etcd](./etcd_operations.md).

### Работа с etcdctl и etcdutl

Для управления etcd используются **две** утилиты, которые важно не путать:
*   **`etcdctl`** — основной gRPC-клиент для работы с **запущенным** кластером (online): чтение данных, проверка здоровья, `snapshot save`/`restore`, дефрагментация, работа с членами.
*   **`etcdutl`** — служебная утилита (появилась в v3.6+) для **offline**-администрирования физических файлов БД: восстановление из снапшота, проверка целостности, прямое дефрагментирование файла. Для многих операций `snapshot` в новых версиях рекомендуется именно она.

Пример настройки доступа к etcd на master-узле (Stacked, kubeadm) и проверки статуса/лидера:

```bash
export ETCDCTL_API=3
alias k-etcdctl="etcdctl --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key"

# Проверка статуса и лидера
k-etcdctl endpoint status -w table
```

Полная шпаргалка команд `etcdctl`/`etcdutl` — в **[Шпаргалке по командам etcdctl](../../etcd/etcdctl_cheatsheet.md)**, а интеграционные примеры (включая доступ через `kubectl exec` в статический под etcd) — в [Практических сценариях](./etcd_operations.md).

### Резервное копирование

Снапшот etcd — единственный надёжный способ забекапить **весь кластер Kubernetes целиком** (все объекты, конфигурацию и состояние). Создание снапшота:

```bash
k-etcdctl snapshot save /backup/etcd-$(date +%Y%m%d).db
```

* **Проверка целостности:** способность прочитать снапшот нужно проверять сразу после создания (`etcdutl snapshot status/verify`), а не только факт появления файла — распространённая ошибка.
* **Что ещё нужно для восстановления:** без файла `EncryptionConfiguration` и (при использовании KMS) доступа к ключам восстановить расшифрованные данные невозможно. Снапшоты следует хранить в зашифрованном виде и в стороне от кластера.
* **Кто что делает:** `etcdctl snapshot save` — online-бэкап, restore — offline через `etcdutl`.

Подробности восстановления многоузлового кворума и DR-процедур см.: **[Кластеризация и восстановление etcd](../../etcd/clustering_and_recovery.md)** и [Практические сценарии](./etcd_operations.md).

## Требования к производительности

etcd — самый требовательный к I/O компонент. Его здоровье напрямую определяет стабильность всего Control Plane.
*   **Диск:** Только NVMe SSD. Задержка `fsync` (метрика `etcd_disk_wal_fdatasync_duration_seconds`) должна быть **< 10 мс**; при p99 > 100 мс лидер начинает пропускать heartbeat и происходят перевыборы. Желательно размещать данные и WAL на отдельных дисках от системного.
*   **Процессор:** Минимум 2 ядра. Высокая нагрузка на CPU при десериализации Protobuf в крупных кластерах.
*   **Сеть:** RTT между узлами etcd **< 10 мс** (для устойчивости выборов — до 50 мс, выше начинается нестабильность).
*   **Память:** BoltDB отображает файл БД в память целиком (memory-mapped), поэтому размер RAM должен заметно превышать размер БД. Рост БД напрямую увеличивает потребление памяти.

### Отдельный etcd для событий (Events)

Наибольший вклад в рост БД обычно вносят **объекты `Event`** (см. [Структуру префиксов](#структура-префиксов-в-kubernetes)). Для крупных или высоконагруженных кластеров Kubernetes официально рекомендует **выделять события в отдельный кластер etcd**, чтобы изолировать высокочастотный поток записи событий от критичных данных приложений.

```bash
# В манифесте kube-apiserver: основное хранилище + отдельное для /events
--etcd-servers=https://etcd-app-0:2379,https://etcd-app-1:2379,https://etcd-app-2:2379
--etcd-servers-overrides="/events#https://etcd-events-0:2379,https://etcd-events-1:2379,https://etcd-events-2:2379"
```

Это исключает ситуацию, когда «шторм событий» переполняет квоту и блокирует запись всех остальных объектов кластера.

### Приблизительный расчёт ёмкости

Практическое правило от производителей: одна пара «ключ-значение» в treeIndex занимает ~150–300 байт в памяти. Для первичного прогноза используйте наличие/отсутствие явных сигналов роста (ревизии, число объектов), а для точного мониторинга — метрики `etcd_mvcc_db_total_size_in_bytes` (выделено) и `etcd_mvcc_db_total_size_in_use_in_bytes` (занято). Запас физического диска после дефрагментации должен составлять >10–15%.

Подробные лимиты и формулы capacity planning — см. **[Лимиты и ограничения etcd](../../etcd/limits_and_constraints.md)**, а тесты производительности — **[Бенчмаркинг](../../etcd/benchmarking.md)**.

## Устранение неисправностей (Troubleshooting)

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `database space exceeded` / Alarm `NOSPACE` | Достигнут лимит размера БД (квота, по умолчанию **2 GB**, максимум **8 GB**). etcd переходит в режим только-чтения. | Выполнить компакцию + дефрагментацию; при легитимной потребности увеличить `--quota-backend-bytes` (учесть рост RAM). |
| `request entity too large` / `etcdserver: request is too large` | Объект (напр., ConfigMap или Secret) превышает `--max-request-bytes` (по умолчанию **1.5 MB**). | Разбить объект или хранить большое содержимое в PV; увеличить `--max-request-bytes`. |
| `etcdserver: leader changed` | Нестабильность сети или медленный диск (fsync). | Проверить задержки диска и RTT сети; убедиться, что диск NVMe. |
| `mvcc: required revision has been compacted` | Watcher (list/watch) отстал от процесса компакции — запрашивается уже удалённая ревизия. | Увеличить интервал компакции или оптимизировать контроллеры/клиентов; для `kubectl` — перезапросить с более свежей `resourceVersion`. |
| `auth: invalid auth token` / TLS-ошибки соединения | Несовпадение CA/cертификатов (например, peer CA вместо server/client). | Использовать правильную пару сертификатов и соответствующий `--cacert`. |

> Полные алгоритмы и playbook, включая ручную компакцию+дефрагментацию и снятие `NOSPACE`-аларма, — см. [Практические сценарии](./etcd_operations.md) и [Систематический troubleshooting](../../etcd/troubleshooting.md).
