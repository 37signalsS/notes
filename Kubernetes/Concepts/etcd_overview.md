# Etcd: распределённое хранилище Kubernetes

## Определения

**etcd** — распределённое согласованное хранилище типа «ключ-значение», используемое в Kubernetes для хранения всех объектов и состояний кластера. Является ключевым компонентом [Control Plane](./control_plane_architecture.md).

## Основные концепции

### Требования Kubernetes к хранилищу

API-сервер Kubernetes нуждается в базе данных со специфическими характеристиками. Традиционные SQL-базы данных (MySQL, PostgreSQL) оптимизированы для сложных запросов и больших объёмов данных, что избыточно для Kubernetes.

**Требуемые свойства:**

1. **Согласованность (Consistency)** — строгая согласованность критична для исключения конфликтов при одновременном изменении объектов. Etcd является **CP-системой** по [CAP-теореме](../../Databases/Concepts/cap_theorem.md) (Consistency, Availability, Partition Tolerance — Согласованность, Доступность, Устойчивость к разделению).
2. **Доступность (Availability)** — простой хранилища означает остановку всей плоскости управления (control plane), что недопустимо для продуктивных сред.
3. **Стабильная производительность** — API-сервер обрабатывает большое количество запросов на чтение и запись. Непредсказуемые задержки недопустимы.
4. **Уведомление об изменениях (Watch)** — возможность потоковой передачи изменений в реальном времени критична для работы контроллеров Kubernetes.

**Что НЕ требуется:**

* **Большие наборы данных** — API-сервер хранит только метаданные объектов. В типичном кластере объём данных составляет от сотен мегабайт до нескольких гигабайт.
* **Сложные запросы** — доступ к объектам происходит по типу, пространству имён и имени. Фильтрация по меткам выполняется на уровне API.

### Роль в архитектуре Kubernetes

`kube-apiserver` является **единственным** компонентом, который напрямую взаимодействует с `etcd`. Все остальные компоненты (планировщик, контроллеры, `kubelet`) обращаются к состоянию кластера только через API-сервер. Такая архитектура обеспечивает централизованный контроль, валидацию и аудит всех изменений.

Потеря `etcd` без актуального бэкапа приводит к потере управляемого состояния кластера. При этом рабочие узлы (Nodes) могут продолжать работу, но Kubernetes теряет возможность управлять объектами, изменять конфигурации и контролировать доступы.

### Ключевые свойства

Etcd обладает характеристиками, критичными для работы Kubernetes:

* **Согласованность (CP по CAP)** — строгая согласованность через кворум. Подробнее: [CAP-теорема](../../Databases/Concepts/cap_theorem.md).
* **Raft** — алгоритм консенсуса с лидером, обеспечивающий репликацию данных. Запись считается подтверждённой только после принятия большинством (кворумом) узлов. В production чаще используют **3 или 5 узлов**, что позволяет сохранять работоспособность при отказе одного или двух узлов соответственно. Подробнее: [Алгоритм Raft](../../etcd/raft_consensus.md).
* **Watch** — уведомления об изменениях в реальном времени, основа работы контроллеров.
* **MVCC (Multi-Version Concurrency Control)** — версионирование через ревизии, позволяющее читать состояние на момент времени. Подробнее: [MVCC и версионирование](../../etcd/mvcc_versioning_and_compaction.md).

### Требования к инфраструктуре и производительности

Для стабильной работы etcd критически важны низкие задержки дисковой подсистемы и сети:

* **Диск:** Только **SSD (Solid State Drive)** или **NVMe (Non-Volatile Memory Express)**. Быстрые накопители с задержкой `fsync` менее **10 мс** (в идеале <2 мс).
* **Сеть:** Минимальные задержки между узлами (<10 мс). Высокий **RTT (Round Trip Time — время кругового обхода)** напрямую снижает пропускную способность записи.

* **CPU/RAM:** Выделенные ресурсы для предотвращения троттлинга и задержек при обработке heartbeats.
* **Масштабирование:** Увеличение количества узлов (с 3 до 5 или 7) повышает отказоустойчивость, но **снижает** производительность записи из-за накладных расходов на репликацию.

### Безопасность

Защита данных в etcd обеспечивается на двух уровнях:

1. **Шифрование данных:** на уровне `kube-apiserver` с помощью `EncryptionConfiguration` (защита при краже физического носителя).
2. **Транспортная безопасность:** обязательное использование TLS/mTLS для всех соединений между узлами кластера и клиентами (API Server).

## Практические сценарии

### Хранение данных и Watch

Все объекты Kubernetes хранятся с префиксом `/registry`:
`/registry/<resource-type>/<namespace>/<resource-name>`

Данные сериализуются в бинарный формат (Protobuf). Контроллеры используют механизм **Watch** для подписки на изменения. Например, планировщик следит за новыми подами:

```bash
# Просмотр событий через etcdctl
etcdctl watch --prefix /registry/pods/
```

### Резервное копирование и восстановление

Регулярное создание снапшотов — критическая задача. Бэкапы должны храниться вне инфраструктуры кластера. Процедура восстановления должна регулярно тестироваться.

```bash
# Создание снапшота
etcdctl snapshot save snapshot.db
```
