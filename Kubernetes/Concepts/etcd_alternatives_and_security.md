# etcd: альтернативы и безопасность

## Определения

**Kine** (Kine Is Not etcd) — прослойка совместимости (shim), транслирующая вызовы API etcd v3 в SQL-запросы к реляционным базам данных. Это позволяет использовать стандартные СУБД в качестве хранилища состояния кластера.

**KMS v2** (Key Management Service) — современный стандарт Kubernetes (GA с версии 1.29) для интеграции с внешними провайдерами ключей (AWS KMS, GCP KMS, Vault). Используется для шифрования данных на диске (at-rest) с поддержкой ротации ключей без простоя.

**k3s** — дистрибутив Kubernetes, который по умолчанию заменяет etcd на связку Kine + SQLite для работы на Edge-устройствах и в малых кластерах.

## Основные концепции

### Альтернативы etcd: Kine и распределенные БД

Использование Kine оправдано в двух крайних случаях: экстремальная экономия ресурсов (Edge) или экстремальное масштабирование (Hyperscale).

| Бэкенд | Сценарий использования | Преимущества |
| :--- | :--- | :--- |
| **SQLite** | IoT, Edge, локальная разработка | Минимальный footprint, один файл БД. |
| **PostgreSQL / Aurora** | "Мега-кластеры", vCluster | Снятие лимита etcd в 8 ГБ, масштабируемость до ТБ данных. |
| **Dqlite** | MicroK8s, отказоустойчивый Edge | Распределенный SQLite, не требует отдельного сервера БД. |

#### Технические ограничения Kine:
*   **Производительность Watch**: механизм наблюдения за изменениями эмулируется через polling (опрос) таблицы БД, что создает дополнительную нагрузку при большом количестве подов.
*   **Консистентность**: гарантии зависят от настроек изоляции транзакций в целевой СУБД. Рекомендуется уровень `Serializable`.

### Безопасность etcd и хранилищ данных

Защита "мозга" кластера строится на двух уровнях: сетевом (In-Transit) и физическом (At-Rest).

#### 1. Транспортная безопасность (mTLS)
Все компоненты Control Plane общаются с etcd через **mTLS**.
*   **API Server**: предъявляет клиентский сертификат узлу etcd.
*   **Peer Communication**: узлы etcd проверяют друг друга при репликации лога Raft.
*   **Ограничение доступа**: порт 2379 должен быть закрыт для всех, кроме IP-адресов Control Plane узлов.

#### 2. Шифрование на диске (Encryption at Rest)
Секреты в etcd хранятся в формате Protobuf/Base64. Без шифрования любой, кто получит файл `member/wal/*`, получит доступ ко всем токенам кластера.

**KMS v2 (Рекомендуемый стандарт 2025/2026):**
*   **Кэширование ключей**: Значительно снижает задержки (latency) при чтении секретов за счет локального кэша DEK (Data Encryption Key).
*   **Ротация без перезагрузки**: Позволяет менять главный ключ (KEK) в облачном KMS без рестарта `kube-apiserver`.
*   **Иерархия ключей**: Возможность настройки разных ключей для разных Namespaces.

## Практические сценарии

### Анализ данных в Kine (SQL-запросы)
В Kine все объекты хранятся в одной таблице `kine`. Это позволяет использовать мощь SQL для аудита кластера, что невозможно в бинарном etcd без спецсредств.

```sql
-- Поиск всех объектов, созданных за последний час
SELECT name, created FROM kine 
WHERE deleted = 0 
AND created > (strftime('%s','now') - 3600);

-- Проверка размера ресурсов по типам
SELECT substr(name, 1, instr(substr(name, 11), '/') + 9) as type, 
       count(*) as count 
FROM kine WHERE deleted = 0 
GROUP BY type;
```

### Настройка KMS v2 для Production
Пример современной конфигурации `EncryptionConfiguration` для интеграции с внешним KMS:

```yaml
apiVersion: apiserver.config.k8s.io/v1
kind: EncryptionConfiguration
resources:
  - resources:
    - secrets
    providers:
    - kms:
        name: my-kms-provider
        endpoint: unix:///var/run/kms-plugin/socket.sock
        cachesize: 1000 # Кэш DEK для производительности
        timeout: 3s
    - identity: {} # Fallback для новых/незашифрованных данных
```
