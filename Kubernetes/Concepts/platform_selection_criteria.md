# Критерии выбора платформы: Docker, Kubernetes, Nomad и IDP

## Определения

Выбор технологического стека для запуска приложений в 2025–2026 годах сместился от подхода «Kubernetes по умолчанию» к прагматичной оценке **когнитивной нагрузки** и **типа нагрузки** (AI/ML, Edge, Legacy). Основная цель — выбор инструмента под конкретную задачу (**Right Tool for the Job**) с учетом масштаба команды, требований к SLA и бюджета на эксплуатацию (FinOps).

**Internal Developer Platform (IDP)** — уровень самообслуживания над инфраструктурой, скрывающий сложность оркестраторов (K8s/Nomad) за «Золотыми путями» (Golden Paths).

**Serverless Containers** (AWS Fargate, Google Cloud Run) — модель запуска контейнеров без управления узлами, где провайдер берет на себя всю операционную ответственность.

**WebAssembly (Wasm)** — портативный бинарный формат для исполнения кода с околонативной скоростью, становящийся альтернативой контейнерам для Edge и плагинов.

## Сравнение платформ

| Критерий | Docker / Compose | HashiCorp Nomad | Kubernetes (K8s) | Serverless (Fargate) |
| :--- | :--- | :--- | :--- | :--- |
| **Масштаб** | Малый (1–3 инженера) | Средний | Средний и крупный | Стартапы / MVP |
| **Тип нагрузки** | Контейнеры | Контейнеры, VM, Binaries | Контейнеры, Wasm, AI | Контейнеры |
| **GPU / AI поддержка** | Базовая (один хост) | Средняя | **Нативная (Kueue/DRA)** | Ограниченная |
| **Сложность** | Низкая | Средняя (Pragmatic) | Высокая («Налог на Ops») | Минимальная |
| **Скорость старта** | Секунды | Секунды | Секунды | Десятки секунд |
| **Экономика (FinOps)** | Дешево (CapEx) | Эффективно (Density) | Дорого (OpEx + Ops Tax) | Pay-as-you-go |

## Основные концепции

### 1. Docker и Docker Compose: Граница и локальная среда
Подходит для сценариев, где не требуется сложная оркестрация и динамическое масштабирование между десятками узлов.
*   **Плюсы:** Минимальные задержки, простота диагностики, идеален для локальной разработки.
*   **Минусы:** Отсутствие нативного self-healing между узлами, сложность управления сетью и секретами в распределенной среде.
*   **Когда использовать:** Локальная разработка, малые проекты (до 10 микросервисов), Edge-вычисления на одном узле, IoT-устройства.

### 2. HashiCorp Nomad: Прагматичный DevOps
Легковесная и гибкая альтернатива Kubernetes, ориентированная на эффективность использования ресурсов. Подробные определения и архитектура описаны в **[Nomad — определения и базовые концепции](../../Nomad/definitions_and_concepts.md)**.
*   **Плюсы:** Единый бинарный файл, поддержка гетерогенных нагрузок (Windows Binaries, Java, QEMU/VM). Нативная федерация регионов из коробки. Потребляет в 5–10 раз меньше RAM, чем K8s Control Plane.
*   **Минусы:** Меньшая экосистема (меньше готовых операторов и Helm-пакетов).
*   **Когда использовать:** Гибридные нагрузки (Legacy + Cloud Native), Edge Computing, высокопроизводительные вычисления (Batch jobs) с быстрой ротацией задач.


### 3. Kubernetes: Фундамент платформы
Индустриальный стандарт для масштабируемых систем с богатой экосистемой расширений. В 2025–2026 годах K8s стал «ОС для облака».
*   **Плюсы:** Огромная экосистема (ArgoCD, Cilium, Istio), мощные механизмы для AI/ML (GPU-шедулинг, Dynamic Resource Allocation). Стандарт де-факто для Enterprise.
*   **Минусы:** Высокая «стоимость владения». Требует постоянного обновления компонентов и высокой экспертизы команды.
*   **Когда использовать:** Микросервисная архитектура (20+ сервисов), запуск LLM и AI-инференса, необходимость в жесткой сегментации трафика и Zero Trust.

### 4. Внутренняя платформа разработчика (IDP)
Уровень абстракции, реализующий концепцию **Platform Engineering** для снижения когнитивной нагрузки.
*   **Плюсы:** Самообслуживание (Self-Service), порталы (Backstage), стандартизация через «Золотые пути» (Golden Paths). Позволяет разработчикам не знать YAML/K8s.
*   **Минусы:** Требует выделенной команды Platform-инженеров для создания и поддержки.
*   **Когда использовать:** Команды от 50+ разработчиков, где время выкатки (Time-to-Market) критичнее стоимости инфраструктуры.

### 5. WebAssembly (Wasm) и Edge
Новый слой исполнения, дополняющий или заменяющий контейнеры в специфических нишах.
*   **Плюсы:** Холодный старт в микросекундах, минимальный размер артефакта, изоляция на уровне Sandbox.
*   **Когда использовать:** Serverless-функции на краю (Edge), плагины для систем (Proxy, DB), запуск кода в браузере с околонативной скоростью.

## Операционная реальность: Облачные сервисы против собственного хостинга

### 1. Управляемые сервисы (Managed K8s: GKE, EKS, Managed K8s)
Провайдер берет на себя обслуживание Control Plane.
*   **Когда выбирать:** Приоритет на скорость доставки (TTM), малая команда эксплуатации, интеграция с облачной экосистемой (IAM, DB, Logging).
*   **Риски:** Зависимость от вендора (Vendor Lock-in), сложности с глубокой кастомизацией API-сервера.

### 2. Собственный хостинг (Bare Metal, Private Cloud)
Развертывание через `kubeadm`, `Kubespray` или `RKE2`.
*   **Когда выбирать:** Работа в изолированном контуре (Air-gapped), жесткие требования безопасности, необходимость специфического железа (FPGA, кастомные GPU), экономия на масштабе (100+ узлов).

## Технические триггеры для миграции

Переход с Docker Compose на Kubernetes оправдан при появлении следующих потребностей:
1.  **Zero Downtime Deployment:** Необходимость в Rolling Updates с проверками готовности (Readiness Probes).
2.  **Декларативное управление ресурсами:** Использование GitOps (ArgoCD/Flux).
3.  **Динамическое масштабирование:** Автозапуск узлов под нагрузку (Karpenter) или по событиям (KEDA).
4.  **Распределенное хранилище (CSI):** Когда данным нужна мобильность между узлами кластера.

## Практические сценарии

### Сценарий 1: Рост из Docker в Managed Kubernetes
Стартап вырос из одного сервера. Появились требования к SLA 99.9% и необходимость запуска GPU-нагрузок для AI-фич.
*   **Решение:** Переход в Managed K8s (EKS/GKE). Использование Karpenter для эффективного управления спот-инстансами с GPU.

### Сценарий 2: Гибридная среда на Nomad
Финтех-компания запускает контейнеры и старые Java-монолиты на Bare Metal.
*   **Решение:** Использование Nomad как единого оркестратора для всех типов задач. Интеграция с Vault для управления секретами и Consul для Service Discovery.
