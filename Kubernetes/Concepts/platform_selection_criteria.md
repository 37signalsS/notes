# Критерии выбора платформы: Docker, Kubernetes, Nomad и IDP

## Определения

Выбор технологического стека для запуска приложений в 2025–2026 годах сместился от подхода «Kubernetes по умолчанию» к прагматичной оценке **когнитивной нагрузки** и **типа нагрузки** (Legacy, Edge, Batch). Основная цель — выбор инструмента под конкретную задачу (**Right Tool for the Job**) с учетом масштаба команды, требований к SLA и бюджета на эксплуатацию (FinOps).

**Internal Developer Platform (IDP)** — уровень самообслуживания над инфраструктурой, скрывающий сложность оркестраторов (K8s/Nomad) за «Золотыми путями» (Golden Paths).

**WebAssembly (Wasm)** — портативный бинарный формат для исполнения кода с околонативной скоростью, становящийся альтернативой контейнерам для Edge и плагинов.

### Принцип выбора: сначала просто, потом умно

Стек подбирается под людей, а не наоборот. Если в команде нет опыта с Kubernetes, начинать с Kubernetes «для взрослости» — верный путь к ночным сменам с инцидентами. Фильтр принятия решений: «Смогу ли я через полгода спокойно обновить этот инструмент, не останавливая работу?» Если ответ неуверенный — откатитесь к более простому варианту.

Менеджер-сервисы кажутся дороже за юнит, но экономия на зарплатах Ops-инженеров и предсказуемость релизов часто перекрывают разницу. 1 час инженера дороже сотен минут вычислений.

## Предварительные требования (Prerequisites)

### Аппаратные минимальные требования

| Платформа | CPU | RAM | Диск | Сеть |
| :--- | :--- | :--- | :--- | :--- |
| **Docker Compose** | 1+ ядро | 512+ MiB | SSD 20+ GB | 1 NIC |
| **Nomad** (сервер) | 2+ ядра | 2+ GiB | SSD 20+ GB | 1 NIC |
| **Nomad** (клиент) | 2+ ядра | 2+ GiB | SSD 50+ GB | 1 NIC |
| **Kubernetes** (1 Control Plane) | 4+ ядра | 8+ GiB | NVMe 100+ GB | 1 NIC, 2 IP (VIP для HA) |
| **Kubernetes** (рабочий узел) | 2+ ядра | 4+ GiB | SSD 50+ GB | 1 NIC |

*Для Kubernetes рекомендуется минимум 3 Control Plane узла с NVMe-дисками для etcd.*

### Программные зависимости

*   **Docker Compose**: Docker Engine >= 24.0, Docker Compose >= 2.20 (или Compose Spec v5+)
*   **Nomad**: Единый бинарный файл >= 1.8 (LTS) или >= 2.0 (последняя версия)
*   **Kubernetes**: kubeadm + kubectl + kubelet одной версии (±1 минорная версия), containerd >= 1.6 или CRI-O >= 1.25
*   **ОС**: Ubuntu 22.04+, Debian 12+, CentOS/RHEL 9+ (или совместимые)
*   **Ядро Linux**: `overlay` (для containerd), `br_netfilter` (для сети K8s)

### Оценка зрелости команды

| Уровень | Ключевые навыки | Рекомендуемая платформа |
| :--- | :--- | :--- |
| Начинающий | Linux, SSH, базовые концепции контейнеров | Docker Compose |
| Средний | Networking, IaC (Ansible/Terraform), мониторинг | Nomad |
| Продвинутый | GitOps, RBAC, CRD, операторы, networking policies | Kubernetes |
| Платформенная команда | Platform Engineering, IDP, DevSecOps, FinOps | Kubernetes + IDP |

## Сравнение платформ

| Критерий | Docker / Compose | HashiCorp Nomad | Kubernetes (K8s) |
| :--- | :--- | :--- | :--- |
| **Масштаб** | Малый (1–3 инженера) | Средний | Средний и крупный |
| **Тип нагрузки** | Контейнеры | Контейнеры, VM, Binaries | Контейнеры, Wasm |
| **Сложность** | Низкая | Средняя (Pragmatic) | Высокая («Налог на Ops») |
| **Скорость старта** | Секунды | Секунды | Десятки минут |
| **Экономика (FinOps)** | Дешево (CapEx) | Эффективно (Density) | Дорого (OpEx + Ops Tax) |
| **Self-healing** | Нет (нужен Docker Swarm) | Да (кластерный режим) | Да (из коробки) |
| **Service Discovery** | DNS-имена сервисов | Consul / DNS | DNS + kube-dns + CoreDNS |
| **Rolling Update** | Нет нативно | Да (canary, blue-green) | Да (Rolling, Canary, Blue/Green) |
| **Secrets Management** | Docker Secrets / env-переменные | Vault (нативная интеграция) | Secrets + внешние бэкенды |
| **Network Policies** | Базовые (bridge/host) | Network namespace isolation | NetworkPolicy / CNI (Cilium, Calico) |
| **Storage (CSI)** | Bind mounts, volumes | Volume drivers (CSI, Host, AWS EBS) | CSI (100+ драйверов) |
| **RBAC** | Нет | ACL + Sentinel (Enterprise) | RBAC + ABAC + Webhook |
| **GitOps** | Команды / скрипты | Terraform, Nomad Pack | ArgoCD, Flux |

## Основные концепции

### 1. Docker и Docker Compose: Граница и локальная среда
Подходит для сценариев, где не требуется сложная оркестрация и динамическое масштабирование между десятками узлов.
*   **Плюсы:** Минимальные задержки, простота диагностики, идеален для локальной разработки. Быстрый старт (секунды от `docker compose up` до работающего стека).
*   **Минусы:** Отсутствие нативного self-healing между узлами, сложность управления сетью и секретами в распределенной среде. Нет нативного Rolling Update (нужен Docker Swarm или ручное управление).
*   **Когда использовать:** Локальная разработка, малые проекты (до 10 микросервисов), Edge-вычисления на одном узле, прототипирование, одиночные серверы.

### 2. HashiCorp Nomad: Прагматичный DevOps
Легковесная и гибкая альтернатива Kubernetes, ориентированная на эффективность использования ресурсов. Подробные определения и архитектура описаны в **[Nomad — определения и базовые концепции](../../Nomad/definitions_and_concepts.md)**. Продвинутые темы — в **[Nomad — продвинутые темы](../../Nomad/advanced_topics.md)**.
*   **Плюсы:** Единый бинарный файл, поддержка гетерогенных нагрузок (Windows Binaries, Java, QEMU/VM). Нативная федерация регионов из коробки. Потребляет в 5–10 раз меньше RAM, чем K8s Control Plane. Интеграция с Consul (Service Discovery) и Vault (секреты) «из коробки».
*   **Минусы:** Меньшая экосистема (меньше готовых операторов и Helm-пакетов). Ограниченная поддержка Network Policies (в отличие от CNI в K8s).
*   **Когда использовать:** Гибридные нагрузки (Legacy + Cloud Native), Edge Computing, высокопроизводительные вычисления (Batch jobs) с быстрой ротацией задач, команды 3–10 инженеров.

### 3. Kubernetes: Фундамент платформы
Индустриальный стандарт для масштабируемых систем с богатой экосистемой расширений.
*   **Плюсы:** Огромная экосистема (ArgoCD, Cilium, Istio), мощные механизмы масштабирования (Karpenter, KEDA), стандарт де-факто для Enterprise.
*   **Минусы:** Высокая «стоимость владения». Требует постоянного обновления компонентов и высокой экспертизы команды. Минимальный кластер — 3 Control Plane узла + N рабочих.
*   **Когда использовать:** Микросервисная архитектура (20+ сервисов), необходимость в жесткой сегментации трафика и Zero Trust, команды от 10+ инженеров.

### 4. Внутренняя платформа разработчика (IDP)
Уровень абстракции, реализующий концепцию **Platform Engineering** для снижения когнитивной нагрузки.
*   **Плюсы:** Самообслуживание (Self-Service), порталы (Backstage), стандартизация через «Золотые пути» (Golden Paths). Позволяет разработчикам не знать YAML/K8s.
*   **Минусы:** Требует выделенной команды Platform-инженеров для создания и поддержки.
*   **Когда использовать:** Команды от 50+ разработчиков, где время выкатки (Time-to-Market) критичнее стоимости инфраструктуры.

### 5. WebAssembly (Wasm) и Edge
Новый слой исполнения, дополняющий или заменяющий контейнеры в специфических нишах.
*   **Плюсы:** Холодный старт в микросекундах, минимальный размер артефакта, изоляция на уровне Sandbox.
*   **Когда использовать:** Serverless-функции на краю (Edge), плагины для систем (Proxy, DB), запуск кода в браузере с околонативной скоростью.

## Технические триггеры для миграции

### С Docker Compose → Kubernetes

Переход оправдан при появлении следующих потребностей:
1.  **Zero Downtime Deployment:** Необходимость в Rolling Updates с проверками готовности (Readiness Probes).
2.  **Декларативное управление ресурсами:** Использование GitOps (ArgoCD/Flux).
3.  **Динамическое масштабирование:** Автозапуск узлов под нагрузку (Karpenter) или по событиям (KEDA).
4.  **Распределенное хранилище (CSI):** Когда данным нужна мобильность между узлами кластера.
5.  **RBAC и безопасность:** Необходимость ролевого доступа к ресурсам кластера.
6.  **Мульти-тенантность:** Разделение кластера между командами (Namespace, ResourceQuota).

### С Docker Compose → Nomad

Переход оправдан при:
1.  **Гетерогенные нагрузки:** Запуск контейнеров + Java JAR + QEMU/VM на одном оркестраторе.
2.  **Малая команда:** 3–10 инженеров, нет времени на изучение K8s.
3.  **Edge Computing:** Федерация кластеров из коробки, низкий overhead.

### С Nomad → Kubernetes

Переход оправдан при:
1.  **Масштаб экосистемы:** Потребность в 100+ готовых операторах (Prometheus, PostgreSQL, Redis и т.д.).
2.  **Network Policies:** Необходимость микросегментации на уровне CNI (Cilium, Calico).
3.  **Enterprise-требования:** Клиент требует K8s как стандарт платформы.

## Операционная реальность: Self-hosted vs Managed

### Self-hosted (Bare Metal, Private Cloud)

Развертывание через `kubeadm`, `Kubespray` или `RKE2` (для K8s) или единый бинарный файл (для Nomad).
*   **Когда выбирать:** Работа в изолированном контуре (Air-gapped), жесткие требования безопасности, необходимость специфического железа (FPGA, кастомные GPU), экономия на масштабе (100+ узлов).
*   **Преимущества:** Полный контроль над инфраструктурой, нет Vendor Lock-in, предсказуемая стоимость.
*   **Недостатки:** Высокая эксплуатационная нагрузка, ручное обновление, ответственность за backup и HA.

### Управляемые сервисы (Managed K8s)

Провайдер берет на себя обслуживание Control Plane.
*   **Когда выбирать:** Приоритет на скорость доставки (TTM), малая команда эксплуатации, интеграция с облачной экосистемой (IAM, DB, Logging).
*   **Риски:** Зависимость от вендора (Vendor Lock-in), сложности с глубокой кастомизацией API-сервера.

## Практические сценарии

### Сценарий 1: Рост из Docker Compose в Bare Metal Kubernetes

**Контекст:** Стартап вырос из одного сервера (Docker Compose + PostgreSQL + Redis). Появилось 15 микросервисов, 3 разработчика, требования к SLA 99.9%.

**Решение:** Переход на Kubernetes через kubeadm на 3 Bare Metal серверах.

**Шаги миграции:**
1. Установка containerd и kubeadm на всех узлах
2. Инициализация Control Plane: `kubeadm init --pod-network-cidr=10.244.0.0/16`
3. Установка CNI (Flannel или Calico)
4. Конвертация Docker Compose → Kubernetes манифесты (Kompose или ручная миграция)
5. Настройка PersistentVolumes для PostgreSQL и Redis
6. Настройка Ingress (nginx-ingress) для маршрутизации трафика
7. Настройка мониторинга (Prometheus + Grafana)

**Результат:** Auto-healing, rolling updates, RBAC, масштабирование через HPA.

### Сценарий 2: Гибридная среда на Nomad

**Контекст:** Финтех-компания запускает контейнеры и старые Java-монолиты на Bare Metal. 5 инженеров, нет времени на изучение K8s.

**Решение:** Использование Nomad как единого оркестратора для всех типов задач. Интеграция с Vault для управления секретами и Consul для Service Discovery.

**Шаги внедрения:**
1. Установка Nomad (сервер + клиенты) через systemd
2. Настройка Consul для Service Discovery
3. Интеграция Vault для управления секретами
4. Создание Job-файлов (HCL) для контейнеров и Java-приложений
5. Настройка ACL и Namespaces для изоляции команд
6. Внедрение Nomad Pack для шаблонизации деплойментов

**Результат:** Единый оркестратор для всех типов нагрузки, низкий overhead, быстрый старт.

### Сценарий 3: Migration с Nomad на Kubernetes при росте команды

**Контекст:** Бывший стартап вырос до 30+ инженеров. Nomad покрывает базовые потребности, но экосистема не хватает (нет готовых операторов для PostgreSQL, Redis, Kafka).

**Решение:** Поэтапная миграция на Kubernetes.

**Шаги миграции:**
1. Развертывание K8s кластера параллельно с Nomad (blue-green)
2. Перенос Stateless-сервисов первыми (API-серверы, фронтенды)
3. Настройка CSI для StatefulSet (PostgreSQL, Redis)
4. Перенос Stateful-сервисов с использованием StatefulSet
5. Настройка Ingress и Network Policies
6. Отключение Nomad после завершения миграции

**Результат:** Доступ к экосистеме K8s (ArgoCD, Prometheus Operator, Cert-Manager), масштабирование через KEDA.

### Сценарий 4: Edge Computing с K3s

**Контекст:** Сеть из 50 магазинов, в каждом — локальный сервер для POS-системы и локальных данных. Нужна оркестрация без тяжелого Control Plane.

**Решение:** K3s (легковесный Kubernetes) на каждом узле, управление через центральный кластер.

**Шаги внедрения:**
1. Установка K3s на каждом Edge-узле: `curl -sfL https://get.k3s.io | sh -`
2. Регистрация узлов в центральном кластере через token
3. Настройка Node Affinity для маршрутизации подов на локальные узлы
4. Использование Local Path Provisioner для локального хранения
5. Настройка ServiceLB для локальных сервисов

**Результат:** Централизованное управление, локальная вычислительная мощность, низкий network latency.

## Диагностика и типовые ошибки

### Docker Compose

**Ошибка: Контейнер падает сразу после запуска**
```bash
# Проверка логов
docker compose logs <service>
# Проверка статуса
docker compose ps
# Проверка зависимостей
docker compose ps --format json | jq '.[] | select(.State == "exited")'
```
**Типичные причины:** Ошибка в Dockerfile, отсутствие переменных окружения, проблемы с сетью, неверный CMD/ENTRYPOINT.

### Nomad

**Ошибка: Задача не планируется на узел**
```bash
# Проверка статуса кластера
nomad status
# Проверка узлов
nomad node status
# Проверка логов задачи
nomad alloc logs <alloc-id>
# Проверка Doctor (диагностика)
nomad operator raft list-peers
```
**Типичные причины:** Драйвер задач недоступен (Docker не установлен), taints/constraints не совпадают, ресурсов на узле недостаточно.

### Kubernetes

**Ошибка: Под в статусе Pending**
```bash
# Проверка событий
kubectl describe pod <pod-name> | grep -A5 Events
# Проверка узлов
kubectl get nodes -o wide
# Проверка планировщика
kubectl logs -n kube-system kube-scheduler-<master>
```
**Типичные причины:** Все узлы с taints, недостаточно ресурсов, PVC не привязан, imagePullBackOff.

**Ошибка: Service не работает**
```bash
# Проверка Endpoints
kubectl get endpoints <service-name>
# Проверка selector
kubectl get svc <service-name> -o yaml | grep -A5 selector
# Проверка NetworkPolicy
kubectl get networkpolicy --all-namespaces
```
**Типичные причины:** Selector не совпадает с лейблами подов, NetworkPolicy блокирует трафик, Endpoints пусты.

## Best Practices

### Выбор платформы
*   **Начинайте с простого:** Docker Compose для прототипов, Nomad для средних команд, Kubernetes для крупных.
*   **Оценивайте команду:** Если нет опыта с K8s — берите Nomad или Managed K8s.
*   **Считайте TCO:** Учитывайте не только стоимость инфраструктуры, но и зарплаты инженеров.
*   **Планируйте рост:** Выбирайте платформу с запасом на 2–3 года.

### Миграция
*   **Поэтапность:** Мигрируйте сервисы по одному, начиная с stateless.
*   **Blue-Green:** Держите старую и новую среду параллельно до полного перехода.
*   **Тестирование:** Проверяйте каждый сервис в новой среде перед отключением старой.
*   **Rollback:** Имейте план отката на каждом этапе.

### Эксплуатация
*   **Мониторинг:** Собирайте метрики всех компонентов (Prometheus, Grafana).
*   **Логирование:** Централизуйте логи (Loki, ELK).
*   **Безопасность:** Включайте RBAC, Network Policies, Pod Security Standards.
*   **Резервное копирование:** Регулярно бекапьте etcd (K8s) или State (Nomad).
*   **Обновления:** Обновляйте по одной минорной версии, читайте changelogs.

### FinOps
*   **Kubecost/OpenCost:** Устанавливайте для мониторинга затрат в Kubernetes.
*   **Rightsizing:** Анализируйте потребление ресурсов и корректируйте requests/limits.
*   **Spot/Preemptible:** Используйте прерываемые инстансы для batch-задач.
*   **Тегирование:** Внедряйте единую систему тегов для атрибуции затрат.
