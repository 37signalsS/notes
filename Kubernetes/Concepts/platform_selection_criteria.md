# Критерии выбора платформы: Docker vs Kubernetes vs IDP

## Определение

Выбор технологического стека для запуска приложений зависит от масштаба компании, сложности архитектуры, требований к отказоустойчивости и зрелости процессов разработки.

## Сравнение платформ

| Критерий | Docker / Docker Compose | Kubernetes (K8s) | Internal Developer Platform (IDP) |
| :--- | :--- | :--- | :--- |
| **Масштаб компании** | Малый (стартапы, небольшие команды) | Средний и крупный | Крупный (десятки и сотни команд) |
| **Сложность системы** | Монолиты, 1-5 микросервисов | Десятки микросервисов | Сотни микросервисов |
| **Отказоустойчивость** | Базовая (restart policy) | Высокая (self-healing, репликация) | Высокая + стандартизация |
| **Уровень экспертизы** | Низкий (любой разработчик) | Высокий (нужны DevOps-инженеры) | Средний для разработчиков |
| **Скейлинг** | Ручной | Автоматический (HPA, VPA, CA) | Автоматический + квотирование |

## Основные концепции

### 1. Docker и Docker Compose

Подходит для сценариев, где не требуется колоссальная отказоустойчивость и сложные сетевые взаимодействия.

* **Плюсы:** Простота настройки, низкий порог вхождения, минимальные затраты на инфраструктуру.
* **Минусы:** Сложность управления взаимодействием более 10 сервисов, отсутствие нативного масштабирования между узлами (без Swarm), ручной траблшутинг.
* **Когда использовать:** Малые проекты, локальная разработка, внутренние утилиты с низким RPS.

### 2. Kubernetes

Индустриальный стандарт для высоконагруженных и масштабируемых систем.

* **Плюсы:** Мощные механизмы оркестрации, управление сотнями узлов, богатая экосистема (Helm, Argo CD, Prometheus).
* **Минусы:** Высокая сложность («overkill» для простых задач), требует выделенной команды эксплуатации.
* **Когда использовать:** Микросервисная архитектура, высокие требования к High Availability (HA), необходимость динамического масштабирования.

### 3. Internal Developer Platform (IDP)

Уровень абстракции над Kubernetes, предоставляющий разработчикам инструменты самообслуживания.

* **Плюсы:** Стандартизация окружений, высокая скорость выкатки (Time-to-Market), снижение нагрузки на DevOps через «золотые пути» (Golden Paths).
* **Минусы:** Самая высокая стоимость разработки и поддержки самой платформы.
* **Когда использовать:** Большая команда разработки (50+ человек), необходимость предоставления индивидуальных стендов (**Feature Stands**) на каждый коммит/фичу.

## Практические сценарии

### Сценарий 1: Рост из Docker в K8s

Компания начала с Docker Compose на одной виртуальной машине. При росте нагрузки и появлении требований к 99.9% аптайма принимается решение о миграции в Kubernetes.

* **Шаги:** Контейнеризация БД (или вынос в облако), написание Helm-чартов, настройка Ingress и мониторинга.

### Сценарий 2: Построение IDP для большой команды

В компании 50 разработчиков. Процесс выделения тестовых сред занимает слишком много времени и блокирует работу.

* **Решение:** Создание платформы на базе K8s, которая по запросу в GitLab CI создает отдельный Namespace, деплоит туда версию приложения и предоставляет DNS-имя.

## Дополнительная информация

**Ключевые выводы из практики:**

1. **Не усложняйте раньше времени:** Если 500 пользователей и один инстанс БД справляются — Kubernetes может быть избыточен.
2. **Отказоустойчивость стоит денег:** Переход в K8s требует инвестиций в железо (минимум 3 мастера для кворума) и людей.
3. **IDP — это продукт для внутренних пользователей:** Его цель — сделать работу разработчика комфортной и безопасной.
