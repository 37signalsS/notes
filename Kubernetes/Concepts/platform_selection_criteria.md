# Критерии выбора платформы: Docker vs Kubernetes vs Nomad vs IDP

## Определения

Выбор технологического стека для запуска приложений в 2025–2026 годах сместился от подхода «Kubernetes по умолчанию» к прагматичному выбору инструмента под конкретную задачу (**Right Tool for the Job**). Основными факторами выбора являются: масштаб команды, сложность архитектуры, требования к отказоустойчивости (SLA) и бюджет на эксплуатацию (FinOps).

## Сравнение платформ

| Критерий | Docker / Compose | HashiCorp Nomad | Kubernetes (K8s) | Platform (IDP) |
| :--- | :--- | :--- | :--- | :--- |
| **Масштаб** | Малый (1–3 инженера) | Средний | Средний и крупный | Крупный (50+ команд) |
| **Тип нагрузки** | Контейнеры | Контейнеры, VM, Binaries | Контейнеры (Wasm) | Абстракция над ресурсами |
| **Сложность** | Низкая (Single Binary) | Средняя (Pragmatic) | Высокая («Налог на Ops») | Низкая для Dev / Высокая для Ops |
| **Отказоустойчивость** | Базовая | Высокая (Federation) | Максимальная (Ecosystem) | Высокая + Стандартизация |
| **Скейлинг** | Ручной | Быстрый (High Density) | Автоматический (HPA/VPA/KEDA) | Автоматический + Квотирование |

## Основные концепции

### 1. Docker и Docker Compose (The Edge & Local)
Подходит для сценариев, где не требуется сложная оркестрация и динамическое масштабирование между десятками узлов.
*   **Плюсы:** Минимальные задержки при запуске, простота траблшутинга (один бинарник), низкий порог вхождения.
*   **Минусы:** Отсутствие нативного self-healing между узлами, сложность управления секретами и сетью в масштабе.
*   **Когда использовать:** Локальная разработка, малые проекты (до 10 микросервисов), Edge-вычисления, IoT-устройства.

### 2. HashiCorp Nomad (Pragmatic DevOps)
Легковесная альтернатива Kubernetes, ориентированная на простоту и гибкость.
*   **Плюсы:** Может оркестровать не только контейнеры, но и виртуальные машины (QEMU), а также обычные бинарные файлы (Java, Go). Один бинарный файл для сервера и агента.
*   **Минусы:** Меньшая экосистема по сравнению с K8s (меньше готовых Helm-подобных решений).
*   **Когда использовать:** Гибридные нагрузки (Legacy + Cloud Native), команды без выделенных K8s-специалистов, высокопроизводительные вычисления с быстрой ротацией задач.

### 3. Kubernetes (The Platform Foundation)
Индустриальный стандарт для масштабируемых систем с богатой экосистемой расширений.
*   **Плюсы:** Огромное количество готовых решений (Operator Pattern, Service Mesh, GitOps), мощные механизмы декларативного управления состоянием.
*   **Минусы:** Высокая «стоимость владения» (Ops Tax). Требует постоянного обновления компонентов (Control Plane, CNI, CSI).
*   **Когда использовать:** Микросервисная архитектура (20+ сервисов), необходимость в динамическом автомасштабировании (HPA, Karpenter), строгие требования к Zero Trust безопасности.

### 4. Internal Developer Platform (IDP)
Уровень самообслуживания над инфраструктурой (обычно поверх K8s), реализующий концепцию **Platform Engineering**.
*   **Плюсы:** Предоставление «Золотых путей» (Golden Paths) — готовых шаблонов инфраструктуры. Снижение когнитивной нагрузки на разработчиков через порталы (например, **Backstage**).
*   **Минусы:** Высокие затраты на создание и поддержку внутренней команды платформы.
*   **Когда использовать:** Огромные команды разработки, необходимость быстрой выкатки фич без ожидания действий от DevOps-инженеров.

## Операционная реальность: Managed vs Self-hosted

В 2026 году выбор «где запускать» важнее, чем «на чем».

1.  **Managed Services (GKE, EKS, Yandex Managed K8s):**
    *   **Правило 3 часов ночи:** Если ваша команда не готова чинить etcd или обновлять Control Plane в 3 часа ночи — выбирайте Managed.
    *   **Экономика:** Выше стоимость ресурсов, но значительно ниже стоимость ФОТ (фонда оплаты труда) инженеров.
2.  **Self-hosted (Bare Metal):**
    *   Оправдано только при огромном масштабе (тысячи узлов), жестких требованиях безопасности (Air-gapped) или специфическом железе (GPU, FPGA).

## Технические триггеры для миграции (Docker → K8s)

Когда пора уходить с Docker Compose на Kubernetes:
1.  **Потребность в Rolling Update без простоя:** Docker Compose не гарантирует Zero Downtime при обновлении одного сервиса без внешних балансировщиков.
2.  **Сложные сетевые политики:** Нужно ограничить доступ между базой данных и фронтендом на уровне сети.
3.  **Автомасштабирование по событиям:** Например, запуск новых воркеров при росте очереди в Kafka.
4.  **Распределенное хранилище:** Когда сервису нужны данные, доступные на любом узле кластера (CSI).

## Практические сценарии

### Сценарий 1: Рост из Docker в Managed Kubernetes
Стартап вырос из одной ВМ с Docker Compose. Появились требования к SLA 99.9% и необходимость сегментации трафика.
*   **Решение:** Переход в Managed K8s. Использование Helm для шаблонизации, Ingress-контроллера для терминирования TLS и Managed DB для исключения рисков потери данных.

### Сценарий 2: Построение IDP для Enterprise
В компании 100+ разработчиков, каждый из которых тратит 20% времени на «борьбу с YAML».
*   **Решение:** Внедрение IDP на базе Backstage. Разработчик через GUI выбирает «Создать проект», платформа автоматически создает репозиторий, Namespace в K8s, БД в облаке и настраивает CI/CD пайплайн.

## Дополнительная информация

**Ключевые выводы FinOps:**
*   Kubernetes — это не про экономию денег на серверах, а про экономию времени на масштабировании и унификации процессов.
*   Для экономии в K8s используйте **Karpenter** (для AWS) или **Spot-инстансы** для некритичных нагрузок.
