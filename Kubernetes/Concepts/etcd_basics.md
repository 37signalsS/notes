# Etcd: основы и архитектура

## Определения

**Etcd** — распределённое, согласованное (consistent) хранилище типа "ключ-значение", используемое в Kubernetes как единственный источник правды (Single Source of Truth) для всех объектов и состояний кластера. Является ключевым компонентом [Control Plane](./control_plane_architecture.md). Etcd построен на основе алгоритма консенсуса **Raft**, что обеспечивает его отказоустойчивость.

---

## Почему etcd? Требования к хранилищу Kubernetes

Сервер API Kubernetes нуждается в базе данных со специфическими характеристиками. Традиционные SQL-базы данных (MySQL, PostgreSQL) оптимизированы для сложных запросов и больших объёмов данных, что избыточно для Kubernetes.

### Требуемые свойства

1. **Согласованность (Consistency)**

   Так как API-сервер — центральный координационный пункт всего кластера, важна **строгая согласованность** (strong consistency). Будет катастрофой, если две ноды попытаются подключить один и тот же постоянный том по iSCSI, потому что сервер API сообщил им обеим, что он доступен.

   Из-за этого требования исключены NoSQL базы данных с конечной согласованностью (eventual consistency) и некоторые распределённые мультимастерные конфигурации SQL. Согласно [CAP-теореме](../../Databases/Concepts/cap_theorem.md), etcd является **CP-системой** (Consistency + Partition Tolerance).

2. **Доступность (Availability)**

   Простой API означает остановку всего Kubernetes control plane, что недопустимо для production-кластеров. Хотя 100%-ная доступность невозможна при строгой согласованности (CAP-теорема), минимизация простоев является важной целью.

3. **Стабильная производительность**

   API-сервер загруженного кластера обрабатывает значительное количество запросов на чтение и запись. Непредсказуемые замедления из-за конкуренции за ресурсы были бы огромной проблемой.

4. **Уведомление об изменениях (Watch)**

   Так как API-сервер выступает как централизованный координатор между разными клиентами, возможность потоковой передачи изменений в реальном времени является критической функцией. Это основа работы контроллеров Kubernetes.

### Что НЕ требуется от базы данных API

* **Большие наборы данных:** API-сервер хранит только метаданные о подах и других объектах. В большом кластере объём данных составляет от сотен мегабайт до нескольких гигабайт, но не терабайты.
* **Сложные запросы:** Доступ к объектам происходит предсказуемо — по типу, пространству имён и имени. Дополнительное фильтрование выполняется по меткам (labels) или аннотациям. Возможности SQL с соединениями (JOIN) и сложными аналитическими запросами избыточны.

## Сравнение с альтернативами

| Свойство | etcd | Традиционные SQL (MySQL/PostgreSQL) | NoSQL (Cassandra) |
| :--- | :--- | :--- | :--- |
| **Согласованность** | Строгая (CP) | Строгая (CA/CP) | Eventual (AP) |
| **Модель данных** | Ключ-значение | Реляционная | Документная/Колоночная |
| **Производительность** | Предсказуемая, низкая задержка | Зависит от сложности запросов | Высокая, но eventual consistency |
| **Watch/Уведомления** | Встроенные | Триггеры/polling | Limited |
| **Распределённость** | Из коробки | Требует настройки | Из коробки |
| **Сложность запросов** | Только по ключу/префиксу | Сложные (JOIN, подзапросы) | Ограниченные |

## Основные концепции

### Ключевые свойства

* **Согласованность (CP по CAP):** Запись считается успешной только после подтверждения большинством узлов (кворумом).
* **Raft и лидерство:** Все операции записи проходят через узел-лидер. Отказ лидера инициирует процесс переизбрания.
* **Ревизии (Revisions):** Каждое изменение объекта увеличивает номер его ревизии. Это позволяет отслеживать историю изменений и реализовывать оптимистичные блокировки.
* **Транзакции (Compare-and-Swap):** Поддерживает атомарные операции, которые выполняются только при совпадении текущей версии объекта.
* **Механизм `watch`:** Позволяет клиентам подписываться на изменения по определенному префиксу ключей, получая обновления в реальном времени.
* **Аренда (Leases) и TTL:** Позволяет привязывать ключи к "аренде" с определенным временем жизни (TTL), по истечении которого они автоматически удаляются.
* **Компакция (Compaction):** Процесс очистки устаревших ревизий для контроля размера базы данных.
* **Снапшоты (Snapshots):** Возможность создания полных снимков состояния для резервного копирования и восстановления.

### Роль в Kubernetes

`kube-apiserver` является **единственным** компонентом, который напрямую взаимодействует с `etcd`. Все остальные компоненты (планировщик, контроллеры, `kubelet`) обращаются к состоянию кластера только через API. Такая архитектура обеспечивает централизованный контроль, валидацию и аудит всех изменений.

## Как Kubernetes хранит данные в etcd

### Префикс `/registry`

Практически все данные Kubernetes имеют префикс `/registry`. Схема именования ключей:

```
/registry/<resource-type>/<namespace>/<resource-name>
```

**Примеры:**

* `/registry/pods/default/nginx` — под nginx в namespace default
* `/registry/deployments/kube-system/coredns` — Deployment coredns
* `/registry/secrets/default/my-secret` — Secret в namespace default

### Формат хранения

Kubernetes сериализует объекты в бинарный формат (Protobuf) перед записью в etcd. Поэтому прямое чтение из etcd показывает нечитаемые данные. Для просмотра в JSON/YAML необходимо обращаться через API (`kubectl get`).

### Watch в Kubernetes

Контроллеры Kubernetes используют механизм `watch` для подписки на изменения по префиксу. Например, `kube-scheduler` следит за подами без назначенного узла:

```bash
# Эквивалент того, что делает контроллер внутри
etcdctl watch --prefix /registry/pods/
```

Когда создаётся новый под, etcd отправляет событие контроллеру, который обрабатывает изменение.
