# Etcd: основы и архитектура для Kubernetes

## Определения

**Etcd** — распределённое согласованное хранилище типа «ключ-значение», используемое в Kubernetes как единственный источник правды (Single Source of Truth) для всех объектов и состояний кластера. Является ключевым компонентом [Control Plane](./control_plane_architecture.md). Построено на основе алгоритма консенсуса **Raft**.

## Основные концепции

### Требования Kubernetes к хранилищу

Сервер API Kubernetes нуждается в базе данных со специфическими характеристиками. Традиционные SQL-базы данных (MySQL, PostgreSQL) оптимизированы для сложных запросов и больших объёмов данных, что избыточно для Kubernetes.

**Требуемые свойства:**

1. **Согласованность (Consistency)** — строкая согласованность (strong consistency) критична. Etcd является **CP-системой** по [CAP-теореме](../../Databases/Concepts/cap_theorem.md) (Consistency + Partition Tolerance).

2. **Доступность (Availability)** — простой API означает остановку всего control plane, что недопустимо для production.

3. **Стабильная производительность** — API-сервер обрабатывает значительное количество запросов на чтение и запись. Непредсказуемые замедления недопустимы.

4. **Уведомление об изменениях (Watch)** — возможность потоковой передачи изменений в реальном времени критична для работы контроллеров Kubernetes.

**Что НЕ требуется:**

* **Большие наборы данных** — API-сервер хранит только метаданные объектов. В большом кластере объём данных составляет сотни мегабайт до нескольких гигабайт.
* **Сложные запросы** — доступ к объектам происходит по типу, пространству имён и имени. Фильтрование по меткам выполняется на уровне API.

### Роль etcd в Kubernetes

`kube-apiserver` является **единственным** компонентом, который напрямую взаимодействует с `etcd`. Все остальные компоненты (планировщик, контроллеры, `kubelet`) обращаются к состоянию кластера только через API. Такая архитектура обеспечивает централизованный контроль, валидацию и аудит всех изменений.

Подробнее об общих концепциях etcd (Lease, Watch, Revision, Transaction): [Архитектура и основные концепции etcd](../../etcd/architecture-and-concepts.md).

## Практические сценарии

### Хранение данных Kubernetes в etcd

**Префикс `/registry`:** Практически все данные Kubernetes имеют префикс `/registry`. Схема именования ключей:

```
/registry/<resource-type>/<namespace>/<resource-name>
```

**Примеры:**

* `/registry/pods/default/nginx` — под nginx в namespace default
* `/registry/deployments/kube-system/coredns` — Deployment coredns
* `/registry/secrets/default/my-secret` — Secret в namespace default

**Формат хранения:** Kubernetes сериализует объекты в бинарный формат (Protobuf) перед записью в etcd. Прямое чтение из etcd показывает нечитаемые данные. Для просмотра в JSON/YAML необходимо обращаться через API (`kubectl get`).

**Watch в Kubernetes:** Контроллеры используют механизм `watch` для подписки на изменения по префиксу. Например, `kube-scheduler` следит за подами без назначенного узла:

```bash
# Эквивалент того, что делает контроллер внутри
etcdctl watch --prefix /registry/pods/
```

Когда создаётся новый под, etcd отправляет событие контроллеру, который обрабатывает изменение.

## Дополнительная информация

**Ключевые свойства etcd** (подробнее в [architecture-and-concepts.md](../../etcd/architecture-and-concepts.md)):

* **Raft и лидерство** — все операции записи проходят через узел-лидер
* **Ревизии (Revisions)** — каждое изменение увеличивает номер ревизии
* **Транзакции (Compare-and-Swap)** — атомарные операции при совпадении версии
* **Компакция (Compaction)** — очистка устаревших ревизий
* **Снапшоты (Snapshots)** — снимки состояния для резервного копирования
