# Мульти-тенантность в Kubernetes

## Определения

**Тенант (tenant)** — это изолированная логическая единица потребления ресурсов кластера. Тенантом может быть отдельная проектная команда, департамент, приложение или внешний клиент в модели SaaS.

**Мульти-тенантность (multi-tenancy)** — это архитектурная модель, при которой один физический кластер Kubernetes разделяется между несколькими независимыми тенантами. Модель направлена на повышение эффективности утилизации ресурсов и централизацию управления при сохранении необходимого уровня изоляции.

---

## Модели мультитенантности

Выбор модели зависит от уровня доверия между тенантами и критичности обрабатываемых данных.

### Мягкая мультитенантность (Soft Multi-tenancy)
*   **Контекст:** Разные команды внутри одной организации (доверенные тенанты).
*   **Изоляция:** Преимущественно логическая через `Namespaces` и `RBAC`.
*   **Цель:** Предотвращение случайных ошибок, разграничение зон ответственности и квотирование.
*   **Риски:** Общее ядро ОС и общая плоскость управления (Control Plane). Злоумышленник, захвативший контейнер, может попытаться атаковать другие тенанты или саму платформу через уязвимости ядра.

### Жесткая мультитенантность (Hard Multi-tenancy)
*   **Контекст:** Разные клиенты SaaS-платформы или изолированные проекты (недоверенные тенанты).
*   **Изоляция:** Глубокая изоляция на уровнях API, сети и среды выполнения (Runtime).
*   **Цель:** Гарантированная безопасность и предотвращение атак типа "breakout" (побег из контейнера).
*   **Инструменты:** Виртуальные кластеры (**vcluster**), песочницы (**gVisor**, **Kata Containers**).

## Основные концепции и уровни изоляции

### 1. Логическая изоляция (Control Plane)
*   **Пространства имён ([`Namespaces`](../Base/namespace.md))**: Фундаментальный механизм разделения объектов и применения политик.
*   **Контроль доступа ([`RBAC`](../Security/rbac/rbac_overview.md))**:
    *   `Role` и `RoleBinding`: Строго локальные права в рамках Namespace.
    *   `ClusterRole`: В мультитенантных средах обычным пользователям выдается только для чтения общекластерных ресурсов (например, `Nodes`), если это необходимо.
*   **API Priority and Fairness (APF)**: Механизм защиты API-сервера. Позволяет ограничивать количество запросов от конкретных тенантов, предотвращая отказ API для всего кластера при аномальной нагрузке от одной команды.

### 2. Изоляция ресурсов (Data Plane)
*   **Квоты ([`ResourceQuota`](../Scheduling/qos_limit_and_requests.md))**: Ограничение суммарного потребления CPU, RAM и количества объектов (Pods, Services, Secrets) в Namespace. Защищает от проблемы "noisy neighbor" (шумный сосед).
*   **Диапазоны лимитов (`LimitRange`)**: Автоматическая установка `requests/limits` по умолчанию для контейнеров тенанта.
*   **Приоритеты ([PriorityClass](../Scheduling/qos_limit_and_requests.md))**: Гарантируют вытеснение менее важных задач (Dev) в пользу критических (Prod) при нехватке ресурсов.
*   **Изоляция узлов (Node Isolation)**: Использование `taints` и `tolerations` для выделения физических серверов под конкретных тенантов (например, для соблюдения требований комплаенса).

### 3. Сетевая изоляция
*   **Сетевые политики ([`NetworkPolicy`](../Networking/Network/network_overview.md))**: L3/L4 фильтрация трафика. Для мультитенантности обязателен подход **Default Deny** (запрет всего трафика, кроме явно разрешенного).
*   **Cilium (eBPF)**: Позволяет строить политики на основе Identity (меток), а не IP, и обеспечивает прозрачное шифрование трафика.
*   **Service Mesh (Istio/Linkerd)**: Обеспечивает строгий mTLS между сервисами тенантов, гарантируя аутентификацию отправителя.

### 4. Изоляция среды выполнения (Runtime)
*   **Политики безопасности ([`Pod Security Admission`](../Security/pod_security_context.md))**: Принудительное соблюдение стандартов (профили `baseline` или `restricted`).
*   **RuntimeClass**: Позволяет выбирать изолированные рантаймы для конкретных подов:
    *   **gVisor (runsc)**: Фильтрация системных вызовов через прослойку в user-space.
    *   **Kata Containers**: Запуск подов в легковесных микро-ВМ.

## Специализированные контроллеры

Стандартных `Namespaces` часто недостаточно для управления сложными структурами.

### Capsule (Operator)
Обеспечивает модель "Tenant-as-a-Service". Позволяет объединять несколько Namespaces в один логический "Tenant".
*   **Агрегированные квоты**: Лимиты ресурсов на весь набор Namespaces тенанта.
*   **Self-service**: Пользователи могут сами создавать Namespaces внутри своих квот без прав администратора кластера.

### Hierarchical Namespace Controller (HNC)
Позволяет создавать древовидную иерархию "родительский-дочерний" Namespace.
*   **Наследование**: Политики (RBAC, Quotas, Secrets) автоматически каскадируются от родителя к детям.
*   **Упрощение**: Идеально для крупных департаментов с множеством микросервисов.

### Virtual Clusters ([vcluster](../ToolsUtilities/vcluster/vcluster_overview.md))
Технология создания виртуальных кластеров внутри хостового.
*   **Изоляция API**: Тенант получает собственный API-сервер и `etcd`.
*   **Полномочия**: Тенант может иметь права `Cluster Admin` в своем vcluster, устанавливать свои `CRD` и операторы.

## Обсервабильность в мульти-тенантной среде

### Мониторинг (Prometheus/Mimir)
*   Использование меток `namespace` или `tenant_id` во всех метриках.
*   **Grafana Mimir**: Изоляция данных через HTTP-заголовок `X-Scope-OrgID`.

### Логирование (Loki)
*   Разделение прав доступа на уровне Grafana Datasource.
*   Ограничение объема записываемых логов (ingestion rate) для каждого тенанта.

## Практические сценарии

### Сценарий 1: Изоляция команд разработки
**Задача:** Разделить 5 команд разработки в одном кластере.
**Решение:**
1. Создать Namespace для каждой команды.
2. Настроить RBAC для доступа только к своему Namespace.
3. Установить `ResourceQuota` для предотвращения захвата всех ресурсов.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
    services: "10"
```

### Сценарий 2: Разделение сред (Dev/Staging/Prod)
**Задача:** Запустить среды разработки и продакшена в одном кластере.
**Решение:**
1. Разделение по Namespace (`myapp-dev`, `myapp-prod`).
2. Физическая изоляция Prod через `taints` и `tolerations` на выделенных `NodePool`.
3. Использование `PriorityClass` для обеспечения безусловного приоритета Prod-нагрузок.
4. Строгие политики `PodSecurity` (профиль `restricted`) для Prod.

### Сценарий 3: Мультитенантность для SaaS-платформы
**Задача:** Изоляция клиентов SaaS (Software as a Service) платформы.
**Решение:**
1. Namespace на каждого клиента.
2. Полная сетевая изоляция трафика через `NetworkPolicy` (изоляция на уровне L4).
3. Использование **vcluster** для предоставления клиентам возможности кастомизировать свои API (например, создавать свои Namespaces внутри SaaS-аккаунта).
4. Выделенные `StorageClass` для разграничения данных на уровне хранилища.

### Сценарий 4: Индивидуальные стенды разработчиков (Feature Stands)
**Задача:** Предоставить каждому разработчику изолированное окружение для тестирования микросервисов.
**Решение:**
1. **Изоляция:** Выделение отдельного **Namespace** для каждого стенда (например, `dev-user1`, `feature-auth-fix`).
2. **Автоматизация:** Использование **GitLab CI/CD** в связке с **Helm** для деплоя полного стека сервисов в целевой Namespace.
3. **Доступ:** Настройка **RBAC** (RoleBinding), позволяющая разработчику просматривать логи и состояние подов только в своём Namespace.
4. **Контроль ресурсов:** Обязательное использование **ResourceQuota**, чтобы экспериментальные стенды не исчерпали ресурсы кластера.
5. **Сетевой доступ:** Настройка Ingress-контроллера для генерации уникальных DNS-имен (например, `user1.dev.example.com`).

## Дополнительная информация

**Важные принципы:**
1.  **Принцип наименьших привилегий**: Тенанты не должны иметь доступа к API узлов, системным секретам и общекластерным настройкам.
2.  **FinOps и биллинг**: Рекомендуется использование **Kubecost** для детального анализа затрат в разрезе тенантов.
3.  **Лимиты API**: Ограничивайте количество объектов (Secrets, ConfigMaps) в Namespace, чтобы избежать деградации `etcd`.
