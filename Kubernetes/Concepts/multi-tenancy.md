# Мульти-тенантность в Kubernetes

**Тенант (tenant)** — это группа пользователей, команда, проект или приложение, которые используют общий кластер Kubernetes, но должны быть изолированы друг от друга.

**Мульти-тенантность (multi-tenancy)** — это модель работы, при которой один Kubernetes-кластер используется несколькими тенантами. Вместо создания отдельных физических или виртуальных кластеров для каждой команды, они разделяют ресурсы одного большого кластера.

Основная задача мульти-тенантности — обеспечить надежную **изоляцию** между тенантами на разных уровнях: ресурсы, сеть, безопасность и доступ к API.

## Уровни и инструменты изоляции

### 1. Изоляция на уровне API и объектов (Logical Isolation)

-   **Пространства имён (`Namespaces`)**: Являются основным механизмом для логического разделения ресурсов. Объекты (Pods, Services, Deployments) в одном namespace изолированы от объектов в другом по именам. Это базовый уровень изоляции, который является обязательным для мульти-тенантности.

-   **Права доступа (`RBAC - Role-Based Access Control`)**: Определяют, какие действия пользователи или группы пользователей могут выполнять с ресурсами.
    -   `Role` и `RoleBinding`: Предоставляют права в рамках одного Namespace. Идеально для изоляции тенантов, так как команда получает доступ только к своему пространству имён.
    -   `ClusterRole` и `ClusterRoleBinding`: Предоставляют права на уровне всего кластера. Используются с осторожностью.

### 2. Изоляция ресурсов (Resource Isolation)

-   **Квоты на ресурсы (`ResourceQuota`)**: Ограничивают потребление ресурсов в рамках одного Namespace. Это предотвращает ситуацию, когда один тенант монополизирует все ресурсы кластера. Квоты можно установить на:
    -   Вычислительные ресурсы: `limits.cpu`, `requests.cpu`, `limits.memory`, `requests.memory`.
    -   Количество объектов: `pods`, `services`, `deployments`, `persistentvolumeclaims`.

-   **Диапазоны лимитов (`LimitRange`)**: Задают значения по умолчанию, а также минимальные и максимальные лимиты на ресурсы для контейнеров в Namespace. Это гарантирует, что каждый под имеет разумные ограничения, даже если они не указаны явно.

### 3. Сетевая изоляция (Network Isolation)

-   **Сетевые политики (`NetworkPolicy`)**: Контролируют трафик между подами на уровне IP-адресов и портов (L3/L4). По умолчанию весь трафик разрешен, но можно настроить политики, которые запрещают подам из одного Namespace общаться с подами из другого, кроме случаев, когда это явно разрешено.
    -   **Важно:** Для работы `NetworkPolicy` необходим сетевой плагин (CNI), который их поддерживает (например, Calico, Cilium, Weave Net).

### 4. Изоляция на уровне выполнения и безопасности (Runtime & Security Isolation)

-   **Политики безопасности подов (`Pod Security Admission / Pod Security Policies`)**: Ограничивают возможности подов, запрещая, например, запуск привилегированных контейнеров, использование host network или монтирование томов с хоста. Это критически важно для предотвращения эскалации привилегий одним тенантом и атак на хост-систему или другие тенанты.

-   **Изоляция хранилища (`Storage Isolation`)**:
    -   `StorageClass`: Позволяет определять разные типы хранилищ. Можно создать отдельные StorageClasses для разных тенантов.
    -   `PersistentVolumeClaim (PVC)`: Запросы на хранилище привязаны к Namespace, что обеспечивает изоляцию данных.

## Преимущества мульти-тенантности

-   **Эффективность использования ресурсов:** Снижение издержек за счет консолидации рабочих нагрузок на меньшем количестве кластеров и более плотного "упаковывания" приложений.
-   **Централизованное управление:** Упрощение администрирования, мониторинга и обновлений, так как управлять нужно одним кластером, а не множеством.
-   **Гибкость и скорость:** Команды могут быстро получать готовые и настроенные окружения для своих приложений без необходимости разворачивать новый кластер.

## Заключение

Мульти-тенантность в Kubernetes — это мощный подход для совместного использования кластера несколькими командами или проектами. Он требует тщательной настройки изоляции на всех уровнях (namespaces, RBAC, квоты, сетевые политики и политики безопасности), но в результате позволяет значительно сократить затраты и упростить управление инфраструктурой.
