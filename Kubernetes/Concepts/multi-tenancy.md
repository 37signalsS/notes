# Мульти-тенантность в Kubernetes

## Определения

**Тенант (tenant)** — это группа пользователей, команда, проект или приложение, которые используют общий кластер Kubernetes, но должны быть изолированы друг от друга.

**Мульти-тенантность (multi-tenancy)** — это модель работы, при которой один Kubernetes-кластер используется несколькими тенантами. Вместо создания отдельных физических или виртуальных кластеров для каждой команды, они разделяют ресурсы одного большого кластера.

## Основные концепции

Основная задача мульти-тенантности — обеспечить надежную **изоляцию** между тенантами на разных уровнях: ресурсы, сеть, безопасность и доступ к API.

### Уровни и инструменты изоляции

1. **Изоляция на уровне API и объектов (Logical Isolation)**
    * **Пространства имён ([`Namespaces`](../Base/namespace.md))**: Являются основным механизмом для логического разделения ресурсов. Объекты (Pods, Services, Deployments) в одном namespace изолированы от объектов в другом по именам. Это базовый уровень изоляции, который является обязательным для мульти-тенантности.
    * **Права доступа ([`RBAC - Role-Based Access Control`](../Security/rbac/rbac_overview.md))**: Определяют, какие действия пользователи или группы пользователей могут выполнять с ресурсами.
        * `Role` и `RoleBinding`: Предоставляют права в рамках одного Namespace. Идеально для изоляции тенантов, так как команда получает доступ только к своему пространству имён.
        * `ClusterRole` и `ClusterRoleBinding`: Предоставляют права на уровне всего кластера. Используются с осторожностью.

2. **Изоляция ресурсов (Resource Isolation)**
    * **Квоты на ресурсы ([`ResourceQuota`](../../Scheduling/qos_limit_and_requests.md#ограничение-суммарного-потребления-с-resourcequota))**: Ограничивают потребление ресурсов в рамках одного Namespace. Это предотвращает ситуацию, когда один тенант монополизирует все ресурсы кластера. Квоты можно установить на вычислительные ресурсы (`limits.cpu`, `requests.cpu`, `limits.memory`, `requests.memory`) и количество объектов (`pods`, `services`, `deployments`, `persistentvolumeclaims`).
    * **Диапазоны лимитов (`LimitRange`)**: Задают значения по умолчанию, а также минимальные и максимальные лимиты на ресурсы для контейнеров в Namespace. Это гарантирует, что каждый под имеет разумные ограничения, даже если они не указаны явно.

3. **Сетевая изоляция ([Network Isolation](../../Networking/Network/network_overview.md#сетевая-изоляция-и-networkpolicy))**
    * **Сетевые политики ([`NetworkPolicy`](../../Networking/Network/network_overview.md#сетевая-изоляция-и-networkpolicy))**: Контролируют трафик между подами на уровне IP-адресов и портов (L3/L4). По умолчанию весь трафик разрешен, но можно настроить политики, которые запрещают подам из одного Namespace общаться с подами из другого, кроме случаев, когда это явно разрешено. Для работы `NetworkPolicy` необходим сетевой плагин (CNI), который их поддерживает (например, Calico, Cilium, Weave Net).

4. **Изоляция на уровне выполнения и безопасности (Runtime & Security Isolation)**
    * **Политики безопасности подов ([`Pod Security Admission / Pod Security Policies`](../../Security/pod_security_context.md#pod-security-standards-pss-и-pod-security-admission-psa))**: Ограничивают возможности подов, запрещая, например, запуск привилегированных контейнеров, использование host network или монтирование томов с хоста. Это критически важно для предотвращения эскалации привилегий одним тенантом и атак на хост-систему или другие тенанты.
    * **Изоляция хранилища (`Storage Isolation`)**:
        * `StorageClass`: Позволяет определять разные типы хранилищ. Можно создать отдельные `StorageClasses` для разных тенантов.
        * [`PersistentVolumeClaim (PVC)`](../Storage/pv_and_pvc.md): Запросы на хранилище привязаны к Namespace, что обеспечивает изоляцию данных.

## Практические сценарии

### Сценарий 1: Изоляция команд разработки

**Задача:** Разделить 5 команд разработки в одном кластере, обеспечив независимую работу и предотвращение взаимного влияния.

**Решение:**
1. Создать namespace для каждой команды: `team-alpha`, `team-beta`, и т.д.
2. Настроить RBAC: предоставить каждой команде доступ только к своему namespace через `Role` и `RoleBinding`.
3. Установить `ResourceQuota` для ограничения потребления ресурсов каждой командой.
4. Применить `NetworkPolicy` для запрета межкомандного трафика (если требуется).

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
    services: "10"
```

### Сценарий 2: Разделение сред (Dev/Staging/Prod)

**Задача:** Запустить среды разработки, тестирования и продакшена в одном кластере с различной степенью изоляции.

**Решение:**
1. Создать namespace с суффиксами: `myapp-dev`, `myapp-staging`, `myapp-prod`.
2. Для prod-среды использовать отдельные `NodePool` с `taints` и `tolerations` для физической изоляции.
3. Применить более строгие `PodSecurity` политики для prod.
4. Настроить различные `LimitRange` для каждой среды (prod получает больше ресурсов).

### Сценарий 3: Мультитенантность для SaaS-платформы

**Задача:** Обеспечить изоляцию клиентов (тенантов) SaaS-платформы в одном кластере Kubernetes.

**Решение:**
1. Использовать namespace на клиента: `customer-acme`, `customer-globex`.
2. Применить `NetworkPolicy` для полной изоляции трафика между клиентами.
3. Использовать отдельные `StorageClass` для данных каждого клиента.
4. Настроить `PodSecurity` на уровне namespace в зависимости от требований клиента.
5. Для критичных клиентов — выделенные узлы с `nodeAffinity`.

Мульти-тенантность в Kubernetes позволяет:

* **Эффективно использовать ресурсы**: Снижает издержек за счет консолидации рабочих нагрузок на меньшем количестве кластеров и более плотного "упаковывания" приложений.
* **Централизованно управлять**: Упрощает администрирование, мониторинг и обновления, так как управлять нужно одним кластером, а не множеством.
* **Обеспечить гибкость и скорость**: Команды могут быстро получать готовые и настроенные окружения для своих приложений без необходимости разворачивать новый кластер.
