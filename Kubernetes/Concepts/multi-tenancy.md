# Мульти-тенантность в Kubernetes

## Определения

**Тенант (tenant)** — это группа пользователей, команда, проект или приложение, которые используют общий кластер Kubernetes, но должны быть изолированы друг от друга.

**Мульти-тенантность (multi-tenancy)** — это модель работы, при которой один Kubernetes-кластер разделяется между несколькими тенантами. Вместо создания отдельных физических или виртуальных кластеров для каждой команды, они используют общие вычислительные ресурсы, что повышает эффективность их утилизации и упрощает администрирование.

## Модели мультитенантности

В зависимости от уровня доверия между тенантами и требований к безопасности выделяют две основные модели:

### Мягкая мультитенантность (Soft Multi-tenancy)
*   **Контекст:** Разные команды внутри одной организации (доверенные тенанты).
*   **Изоляция:** Преимущественно логическая (Namespaces, RBAC).
*   **Цель:** Предотвращение случайных ошибок, разграничение прав и квотирование ресурсов.
*   **Риски:** Взлом одного контейнера может потенциально привести к атаке на другие тенанты через ядро узла или API-сервер.

### Жесткая мультитенантность (Hard Multi-tenancy)
*   **Контекст:** Разные клиенты SaaS-платформы или изолированные проекты (недоверенные тенанты).
*   **Изоляция:** Глубокая изоляция на уровне API (Control Plane), сети и среды выполнения (Runtime).
*   **Цель:** Гарантированная безопасность и предотвращение атак типа "breakout" (выход за пределы контейнера).
*   **Риски:** Сложность настройки и дополнительные накладные расходы. Требует использования виртуальных кластеров (vcluster) или песочниц (gVisor/Kata).

## Основные концепции и уровни изоляции

Основная задача мульти-тенантности — обеспечить надежную изоляцию на разных уровнях: ресурсы, сеть, безопасность и доступ к API.

### 1. Изоляция на уровне API и объектов (Logical Isolation)
*   **Пространства имён ([`Namespaces`](../Base/namespace.md))**: Основной механизм для логического разделения ресурсов. Объекты (Pods, Services, Deployments) в одном namespace изолированы от объектов в другом по именам.
*   **Права доступа ([`RBAC - Role-Based Access Control`](../Security/rbac/rbac_overview.md))**: Определяют действия пользователей или групп.
    *   `Role` и `RoleBinding`: Права в рамках конкретного Namespace.
    *   `ClusterRole` и `ClusterRoleBinding`: Права на уровне всего кластера. В мульти-тенантных средах следует избегать выдачи `ClusterRoleBinding` обычным тенантам.

### 2. Изоляция ресурсов (Resource Isolation)
*   **Квоты на ресурсы ([`ResourceQuota`](../Scheduling/qos_limit_and_requests.md))**: Ограничивают потребление CPU, памяти и количество объектов в Namespace. Это предотвращает ситуацию "noisy neighbor" (шумный сосед), когда один тенант потребляет все ресурсы кластера.
*   **Диапазоны лимитов (`LimitRange`)**: Задают значения ресурсов по умолчанию (requests/limits) для контейнеров, если они не указаны разработчиком.
*   **Приоритеты ([PriorityClass](../Scheduling/qos_limit_and_requests.md))**: Позволяют гарантировать запуск критических сервисов (например, Production) путем вытеснения менее приоритетных подов (например, Dev/Test).

### 3. Сетевая изоляция (Network Isolation)
*   **Сетевые политики ([`NetworkPolicy`](../Networking/Network/network_overview.md))**: Контролируют трафик между подами на уровне IP и портов (L3/L4). По умолчанию в K8s разрешены все соединения ("any-to-any"), поэтому для мульти-тенантности обязателен подход "Default Deny".
*   **Cilium**: Современный CNI, использующий eBPF. Позволяет строить политики на основе identity (меток), а не IP, и обеспечивает прозрачное шифрование (mTLS).

### 4. Изоляция на уровне выполнения и безопасности (Runtime & Security Isolation)
*   **Политики безопасности подов ([`Pod Security Admission`](../Security/pod_security_context.md))**: Ограничивают привилегии контейнеров (запрет host network, privileged mode, запуск от root).
*   **Изоляция хранилища**: Использование разных `StorageClass` и изоляция через `PersistentVolumeClaim`.
*   **Sandboxed Runtimes**: Использование **gVisor** или **Kata Containers** для создания дополнительного барьера между ядром ОС и контейнером клиента.

## Admission Control и политики

**Admission Control** — механизм перехвата запросов к API перед сохранением объектов.

*   **Validating Webhook**: Валидация объектов (например, запрет использования `hostNetwork` или проверка наличия обязательных меток). Инструменты: [Kyverno](../Security/kyverno/policies/practical_scenarios.md), OPA Gatekeeper.
*   **Mutating Webhook**: Автоматическая модификация объектов (например, автоматическое добавление sidecar-контейнеров или установка `PriorityClass` в зависимости от Namespace).

## Управление ресурсами на уровне узла (Node-level)

Параметры kubelet для защиты узлов от исчерпания ресурсов одним тенантом:

*   `maxPods`: Ограничивает максимальное количество подов на одном физическом узле.
*   `podPidsLimit`: Защищает от PID exhaustion (исчерпания идентификаторов процессов), предотвращая атаку типа "fork bomb" внутри контейнера.

## Иерархическое управление и виртуализация

Для сложных организационных структур стандартных Namespaces может быть недостаточно:

*   **Hierarchical Namespace Controller (HNC)**: Позволяет создавать иерархию "родительский-дочерний" Namespace. Политики (RBAC, Quotas, Secrets) автоматически наследуются от родителя к детям, что упрощает управление крупными департаментами.
*   **Virtual Clusters ([`vcluster`](../ToolsUtilities/vcluster/vcluster_overview.md))**: Технология Hard Multi-tenancy, где каждый тенант получает свой собственный API-сервер, работающий внутри "хостового" кластера.
    *   Тенанты могут иметь права Cluster Admin в своем виртуальном кластере.
    *   Возможность устанавливать свои CRD и Operator-ы без влияния на других тенантов.

## Практические сценарии

### Сценарий 1: Изоляция команд разработки
**Задача:** Разделить 5 команд разработки в одном кластере.
**Решение:**
1. Создать Namespace для каждой команды.
2. Настроить RBAC для доступа только к своему Namespace.
3. Установить `ResourceQuota` для предотвращения захвата всех ресурсов.

```yaml
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-alpha-quota
  namespace: team-alpha
spec:
  hard:
    requests.cpu: "4"
    requests.memory: 8Gi
    limits.cpu: "8"
    limits.memory: 16Gi
    pods: "20"
    services: "10"
```

### Сценарий 2: Разделение сред (Dev/Staging/Prod)
**Задача:** Запустить среды разработки и продакшена в одном кластере.
**Решение:**
1. Разделение по Namespace (`myapp-dev`, `myapp-prod`).
2. Физическая изоляция Prod через `taints` и `tolerations` на выделенных `NodePool`.
3. Использование `PriorityClass` для обеспечения безусловного приоритета Prod-нагрузок.
4. Строгие политики `PodSecurity` (профиль `restricted`) для Prod.

### Сценарий 3: Мультитенантность для SaaS-платформы
**Задача:** Изоляция клиентов SaaS (Software as a Service) платформы.
**Решение:**
1. Namespace на каждого клиента.
2. Полная сетевая изоляция трафика через `NetworkPolicy` (изоляция на уровне L4).
3. Использование **vcluster** для предоставления клиентам возможности кастомизировать свои API (например, создавать свои Namespaces внутри SaaS-аккаунта).
4. Выделенные `StorageClass` для разграничения данных на уровне хранилища.

### Сценарий 4: Индивидуальные стенды разработчиков (Feature Stands)
**Задача:** Предоставить каждому разработчику изолированное окружение для тестирования микросервисов.
**Решение:**
1. **Изоляция:** Выделение отдельного **Namespace** для каждого стенда (например, `dev-user1`, `feature-auth-fix`).
2. **Автоматизация:** Использование **GitLab CI/CD** в связке с **Helm** для деплоя полного стека сервисов в целевой Namespace.
3. **Доступ:** Настройка **RBAC** (RoleBinding), позволяющая разработчику просматривать логи и состояние подов только в своём Namespace.
4. **Контроль ресурсов:** Обязательное использование **ResourceQuota**, чтобы экспериментальные стенды не исчерпали ресурсы кластера.
5. **Сетевой доступ:** Настройка Ingress-контроллера для генерации уникальных DNS-имен (например, `user1.dev.example.com`).

## Дополнительная информация

**Преимущества мульти-тенантности:**
*   **Эффективное использование ресурсов**: Консолидация нагрузок снижает издержки за счет разделения неиспользуемых мощностей.
*   **Централизованное управление**: Упрощение администрирования (обновление кластера, патчи безопасности) одного большого кластера вместо десяти маленьких.
*   **Скорость развертывания**: Быстрое получение изолированных окружений через API без ожидания выделения виртуальных машин.

**Важные принципы:**
1.  **Kubernetes не обеспечивает мульти-тенантность "из коробки"** — это конструктор, требующий настройки всех уровней изоляции.
2.  **CPU/RAM — не единственные ресурсы** — диск, сеть, PID, количество объектов API также требуют квотирования.
3.  **Принцип наименьших привилегий** — тенанты не должны иметь доступа к API узлов, системным секретам и настройкам кластера.
4.  **Мониторинг и FinOps** — необходимо отслеживать потребление ресурсов в разрезе тенантов для корректного биллинга и планирования емкости.
