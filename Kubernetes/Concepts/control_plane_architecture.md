# Архитектура Control Plane в Kubernetes

## Определения

**Control Plane (Плоскость управления)** — это "мозг" кластера Kubernetes, который управляет его состоянием. Он отвечает за принятие глобальных решений о кластере (например, планирование запуска контейнеров), а также за обнаружение и реагирование на события в кластере.

Компоненты Control Plane:

*   **`etcd`**: Распределенное хранилище типа "ключ-значение", которое служит единственным источником правды (`Single Source of Truth`) о конфигурации и состоянии всего кластера.
*   **`kube-apiserver` (API-сервер)**: Центральный компонент, который предоставляет HTTP/HTTPS API для взаимодействия с кластером. Это единственная точка входа для всех операций управления.
*   **`kube-scheduler` (Планировщик)**: Компонент, отвечающий за назначение подов (Pods) на доступные рабочие узлы (Nodes) на основе заданных ограничений и доступных ресурсов.
*   **`kube-controller-manager` (Менеджер контроллеров)**: Процесс, который запускает несколько циклов-контроллеров. Эти контроллеры отслеживают состояние кластера и работают над приведением фактического состояния к желаемому, записанному в `etcd`.
*   **`cloud-controller-manager` (Облачный менеджер контроллеров)**: Встраивает Kubernetes в API конкретного облачного провайдера. Выносит логику взаимодействия с облачной инфраструктурой (например, создание балансировщиков, дисков) из основного `kube-controller-manager`, позволяя ядру Kubernetes быть независимым от облака.

**Data Plane (Плоскость данных)** — это совокупность рабочих узлов (Nodes), на которых непосредственно запускаются и работают приложения пользователей в контейнерах.

*   **`kubelet`**: Агент, работающий на каждом узле. Он получает инструкции от `kube-apiserver` и отвечает за жизненный цикл подов на своем узле: запускает, останавливает и следит за состоянием контейнеров.
*   **`kube-proxy`**: Сетевой прокси, работающий на каждом узле. Он реализует сетевые правила и концепцию сервисов (`Services`) в Kubernetes, управляя сетевым трафиком между подами.
*   **Среда выполнения контейнеров (Container Runtime)**: Программное обеспечение, отвечающее за запуск контейнеров (например, `containerd`, `CRI-O`).

## Основные концепции

Control Plane работает как единая система, где компоненты непрерывно взаимодействуют друг с другом для управления кластером.

*   **Источник правды (`etcd`)**: Любое изменение в кластере инициируется через `kube-apiserver` и записывается в `etcd`. Это гарантирует, что в любой момент времени существует только одно авторитетное состояние кластера. `etcd` использует алгоритм консенсуса **Raft** для обеспечения отказоустойчивости и согласованности данных между несколькими узлами.

*   **Центральный API (`kube-apiserver`)**: Все компоненты, включая пользователей (через `kubectl`) и другие части системы, взаимодействуют только с `kube-apiserver`. Он валидирует, аутентифицирует, авторизует и обрабатывает запросы, прежде чем сохранить их в `etcd`. Это делает API-сервер центральным шлюзом и единственным компонентом, имеющим прямой доступ к `etcd`.

*   **Циклы согласования (`Reconciliation Loops`)**: `kube-controller-manager` реализует ключевой принцип Kubernetes. Контроллеры (например, `Deployment Controller`, `Node Controller`) "наблюдают" (`watch`) за изменениями в `etcd` через `kube-apiserver`. Когда контроллер обнаруживает расхождение между желаемым состоянием (записанным в `etcd`) и фактическим состоянием (в кластере), он предпринимает действия для устранения этого расхождения.
    *   **Примеры контроллеров:**
        *   **Node Controller:** Реагирует на отказы узлов, помечая их как неработоспособные.
        *   **ReplicaSet/Deployment Controller:** Поддерживает заданное количество реплик пода, создавая или удаляя их при необходимости.
        *   **Endpoints Controller:** Обновляет объект `Endpoints` (IP-адреса подов), связывая `Services` с их реальными бэкендами.

*   **Планирование (`kube-scheduler`)**: `kube-scheduler` также "наблюдает" за API-сервером. Как только появляется новый под без назначенного узла, планировщик выбирает для него наиболее подходящий узел и сообщает об этом решении API-серверу, который записывает эту информацию в `etcd`.

## Практические сценарии

### Жизненный цикл создания пода

1.  **Запрос**: Пользователь отправляет `kubectl` команду для создания нового пода. Манифест пода (в формате YAML или JSON) отправляется на `kube-apiserver`.
2.  **Валидация и сохранение**: `kube-apiserver` проверяет манифест, аутентифицирует и авторизует пользователя, а затем сохраняет информацию о новом поде в `etcd`. У пода пока нет назначенного узла.
3.  **Планирование**: `kube-scheduler` обнаруживает новый под без поля `spec.nodeName`. Он выполняет **фильтрацию** (отбрасывает неподходящие узлы) и **оценку** (ранжирует оставшиеся), выбирая лучший узел.
4.  **Привязка**: `kube-scheduler` сообщает о своем решении `kube-apiserver`, который обновляет объект пода в `etcd`, записывая в него имя выбранного узла (`spec.nodeName`).
5.  **Запуск**: `kubelet` на целевом узле обнаруживает, что ему назначен новый под. Он скачивает необходимые образы контейнеров и запускает их.
6.  **Обновление статуса**: `kubelet` регулярно сообщает о состоянии пода `kube-apiserver`, который обновляет эту информацию в `etcd`.

### Обеспечение отказоустойчивости (High Availability)

Для производственных сред критически важно иметь отказоустойчивый Control Plane. Это достигается запуском нескольких (обычно нечетного числа) мастер-узлов.

*   **Кворум `etcd`**: Кластер `etcd` требует наличия "кворума" — большинства работающих узлов (`(N/2) + 1`) — для выполнения операций записи. Кластер из **3 мастеров** может пережить отказ **1** мастера, а кластер из **5 мастеров** — отказ **2** мастеров. Четное число узлов не добавляет отказоустойчивости по сравнению с предыдущим нечетным числом, но требует больше ресурсов.

*   **Единая точка входа**: Рабочие узлы (`kubelet`) не знают IP-адреса всех мастеров. Вместо этого они подключаются к **балансировщику нагрузки (Load Balancer)**, который имеет стабильный виртуальный IP (VIP) или DNS-имя. Балансировщик распределяет запросы между всеми здоровыми `kube-apiserver` на мастер-узлах. Если один мастер выходит из строя, балансировщик автоматически перестает направлять на него трафик, обеспечивая бесперебойную работу для воркеров.

## Дополнительная информация

*   **Механизм `Watch`**: Компоненты Control Plane активно используют механизм подписки (`watch`) через `kube-apiserver` для отслеживания изменений в `etcd` в реальном времени, вместо постоянного опроса.
*   **Контроллеры в `kube-controller-manager`**:
    *   **Node Controller**: Реагирует на отказы узлов.
    *   **Deployment/ReplicaSet Controller**: Поддерживает заданное количество реплик пода.
    *   **Endpoints Controller**: Обновляет объект `Endpoints`, связывая сервисы с IP-адресами подов.
*   **Восстановление после сбоев**: `etcd` поддерживает создание **снимков (snapshots)**, которые позволяют восстанавливать состояние кластера.
