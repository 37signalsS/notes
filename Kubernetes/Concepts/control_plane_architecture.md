# Архитектура Control Plane в Kubernetes

## Определения

**Control Plane (Плоскость управления)** — центральный узел управления кластером Kubernetes, отвечающий за принятие глобальных решений (например, планирование запуска контейнеров), обнаружение и реагирование на события в кластере.

**Data Plane (Плоскость данных)** — совокупность рабочих узлов (**Nodes**), на которых непосредственно выполняются приложения пользователей в контейнерах.

### Концепция «6 бинарных файлов»

Архитектура Kubernetes базируется на шести ключевых исполняемых файлах:

1.  **`kube-apiserver`** (Control Plane)
2.  **`kube-scheduler`** (Control Plane)
3.  **`kube-controller-manager`** (Control Plane)
4.  **`cloud-controller-manager`** (Control Plane)
5.  **`kubelet`** (Рабочий узел)
6.  **`kube-proxy`** (Рабочий узел)

*Примечание: **etcd** и среда выполнения (**Container Runtime**, например, `containerd`) являются внешними по отношению к основному проекту Kubernetes.*

### Требования к узлам кластера

| Тип узла | Ресурсы (типичные) | Особенности |
| :--- | :--- | :--- |
| **Master (Control Plane)** | 2 **CPU**, 4 GB **RAM** | Запускают только управляющие компоненты. Для **HA (High Availability)** рекомендуется 3 или 5 узлов. |
| **Worker (Рабочие узлы)** | Зависят от нагрузки приложений | Требования определяются потребностями контейнеров. |

## Основные концепции

### Компоненты Control Plane

*   **`kube-apiserver` (API-сервер)**: Центральный компонент, «входная дверь» и коммуникационный концентратор кластера. Предоставляет **HTTP** API, обрабатывает и проверяет REST-запросы от пользователей, операторов и внутренних компонентов. Служит единственной точкой входа для всех административных задач и связывает все остальные части Control Plane. Подробнее о способах доступа см. в разделе **[Взаимодействие с API Kubernetes](./api_interaction.md)**. Масштабируется горизонтально.
*   **`etcd`**: Распределенное хранилище типа «ключ-значение» на основе алгоритма консенсуса **Raft**. Это **централизованное хранилище** кластера, обеспечивающее согласованность всей конфигурации и текущего состояния ресурсов. Требует **нечётного числа узлов** для формирования кворума. **Медленный диск** (fsync >10 мс) вызывает перевыборы лидера и дестабилизацию кластера. Подробнее: **[Обзор etcd](./etcd_overview.md)**.
*   **`kube-scheduler` (Планировщик)**: Отвечает за распределение работы по узлам. Он обнаруживает новые поды без назначенного узла, оценивает их требования к ресурсам (Pod requests), политики качества обслуживания (**QoS**), аффинити-правила и другие ограничения для принятия решения о размещении. Процесс включает фазы **Filtering** (отсев) и **Scoring** (ранжирование). Подробнее: **[Планировщик подов](./kube_scheduler.md)**.
*   **`kube-controller-manager`**: Единый процесс, объединяющий десятки контроллеров. Неустанно работает для поддержания желаемого состояния кластера (цикл согласования).
    **Основные встроенные контроллеры:**
    *   **Node controller** (Контроллер узлов): следит за состоянием (heartbeat) узлов, управляет их добавлением и удалением.
    *   **Replication controller** (Контроллер репликации): обеспечивает запуск и поддержание заданного количества реплик подов (для объектов ReplicaSet и Deployment).
    *   **Endpoints controller** (Контроллер конечных точек): автоматически заполняет объекты `Endpoints` и `EndpointSlice`, связывая сервисы с IP-адресами подов.
    *   **Service Account & Token controller**: управляет созданием учетных записей служб и токенов API для доступа внутри кластера.
    *   **Namespace controller**: отвечает за правильную инициализацию новых пространств имен и очистку ресурсов при их удалении.
    *   **Persistent Volume controller**: управляет жизненным циклом `PersistentVolumes` (PV) и `PersistentVolumeClaims` (PVC), взаимодействуя с хранилищами через интерфейс **CSI**.
    *   **Job controller**: обеспечивает успешное выполнение разовых и пакетных заданий (Jobs).
    *   **DaemonSet controller**: гарантирует запуск пода на каждом подходящем узле кластера.

*   **`cloud-controller-manager`**: «Облачный шепот» (Cloud Whisperer) — компонент, обеспечивающий интеграцию с API и сервисами конкретных облачных провайдеров (AWS, GCP, Azure и др.).
    **Ключевые функции:**
    *   **Интеграция с провайдером**: позволяет Kubernetes использовать нативные возможности облака (балансировщики, сети, хранилища).
    *   **Предоставление ресурсов**: автоматизирует создание облачных ресурсов (например, внешнего LB при создании сервиса типа `LoadBalancer`).
    *   **Очистка ресурсов**: гарантирует удаление соответствующих облачных ресурсов при удалении объектов в K8s, предотвращая лишние затраты.
    *   **Изоляция кода**: выносит специфичный для облака код за пределы основного ядра Kubernetes, сохраняя проект модульным и вендор-нейтральным.

## Структура API: Группы и Версии

API Kubernetes организован иерархически для обеспечения расширяемости, логической классификации и обратной совместимости.

### Разделение ресурсов (API Groups)
Ресурсы классифицируются по **группам API**, что позволяет управлять ими независимо:
*   **Основная группа (Core / Legacy Group)**: Находится по пути `/api/v1`. Включает базовые ресурсы: `Pods`, `Services`, `Nodes`, `ConfigMaps`. У этой группы нет имени в поле `apiVersion` (пишется просто `v1`).
*   **Именованные группы (Named Groups)**: Находятся по пути `/apis/$GROUP_NAME/$VERSION`. Примеры:
    *   `apps`: высокоуровневые ресурсы (`Deployments`, `StatefulSets`).
    *   `batch`: задачи (`Jobs`, `CronJobs`).
    *   `networking.k8s.io`: сетевые ресурсы (`Ingress`, `NetworkPolicy`).
    *   `apiextensions.k8s.io`: управление пользовательскими ресурсами (`CustomResourceDefinitions`).

### Версионирование (API Versions)
Версии позволяют развивать API, не нарушая работу существующих систем:
*   **Alpha (`v1alpha1`)**: Новые функции, могут содержать ошибки. Отключены по умолчанию. Нет гарантии обратной совместимости.
*   **Beta (`v1beta1`)**: Функции протестированы, включены по умолчанию. Могут быть внесены изменения, но с поддержкой миграции.
*   **Stable (`v1`)**: Готовы к промышленному использованию. Гарантия обратной совместимости в течение многих версий.

### Команды для исследования API
*   `kubectl api-resources`: список всех доступных типов ресурсов, их кратких имен и групп.
*   `kubectl api-versions`: список всех поддерживаемых версий API в кластере.
*   `kubectl api-resources --api-group=monitoring.coreos.com`: фильтрация ресурсов по конкретной группе (например, от Prometheus Operator).

## kube-apiserver — обработка запросов (Handler Pipeline)

> **Аутентификация** — процесс проверки личности пользователя или системы (гарантирует, что сущность является тем, за кого себя выдает).
> **Авторизация** — определение прав доступа аутентифицированного пользователя к конкретным действиям или ресурсам.

1.  **Аутентификация (Authentication)**: Проверка личности («кто вы?»). Используются сертификаты, токены, OIDC. С версии 1.30 рекомендуется **Structured Authentication Config** для поддержки нескольких провайдеров без перезагрузки.
2.  **Авторизация (Authorization)**: Проверка прав («что можно?»). Обычно через **RBAC**. С версии 1.30 доступна **Structured Authorization Config**.
3.  **Admission (Mutation → Validation)**:
    *   **Mutating**: Может изменить запрос (например, добавить sidecar или установить default-значения).
    *   **Validating**: Проверяет корректность. Современный стандарт — **ValidatingAdmissionPolicy** (на базе **CEL**), работающий внутри процесса API-сервера без задержек на внешние вебхуки.
4.  **Сохранение в etcd**: Запись объекта в базу данных.
5.  **Уведомление подписчиков**: Рассылка событий через механизм **Watch**.

> **Важно:** порядок authn → authz → admission критичен. Авторизация невозможна без установления личности. Admission выполняется после авторизации, так как политики могут зависеть от прав пользователя или изменять уже разрешенный запрос.

### kube-controller-manager — цикл согласования

Это бесконечный цикл, состоящий из трех шагов:
1.  **Наблюдение (Observe)**: Получение текущего состояния через API (Watch).
2.  **Сравнение (Diff)**: Сопоставление желаемого (`spec`) с фактическим (`status`).
3.  **Действие (Act)**: Устранение разницы (создание/удаление объектов).

**Основные контроллеры:**
*   **Deployment / ReplicaSet controller**: Поддерживает заданное число реплик.
*   **Node controller**: Следит за heartbeat узлов. Если узел не отвечает (Lease истек), помечает его `NotReady`.
*   **Job / CronJob controller**: Запуск задач по расписанию.
*   **EndpointSlice controller**: Обновляет списки IP-адресов подов для сервисов.
*   **Namespace controller**: Очистка ресурсов при удалении пространства имен.

### Выбор лидера (Leader Election) и Leases

Компоненты `kube-controller-manager` и `kube-scheduler` используют объекты **Lease** для выбора лидера. Только один экземпляр активен, остальные ждут. Также **Lease** используются как легковесный механизм Heartbeats для узлов (вместо тяжелых обновлений объекта Node), что критично для масштабируемости.

### Компоненты рабочего узла (Data Plane)

*   **`kubelet`**: Главный агент на узле, выступающий связующим звеном между Control Plane и рабочими узлами. Управляет полным жизненным циклом подов (создание, удаление, поддержание состояния) и контейнеров внутри них. Подробнее: **[Kubelet — основы работы](./kubelet.md)**.
*   **`kube-proxy`**: Сетевой прокси, управляющий сетевыми правилами для обеспечения связности подов с внешним миром и внутри кластера. Программирует **iptables** или **IPVS**. Подробнее: **[CNI и kube-proxy: роли](../Networking/Network/cni_kube_proxy_roles.md)**.
*   **CRI (Container Runtime Interface)**: Стандартный API, позволяющий Kubernetes использовать различные среды выполнения контейнеров без привязки к конкретной реализации.
*   **Container Runtime**: Среда запуска (CRI-совместимая), отвечающая за загрузку образов и управление жизненным циклом контейнеров (например, **containerd**, **CRI-O**). Считается стандартом после отказа от `dockershim`.

> **Почему Docker Engine был объявлен устаревшим (deprecated)?**
> Традиционный Docker Engine не имел встроенной поддержки протокола **CRI**, что требовало использования промежуточного слоя — **dockershim**. Kubernetes перешел на прямое использование **containerd** и **CRI-O** по следующим причинам:
> 1.  **Снижение накладных расходов**: Прямое взаимодействие с рантаймом через CRI эффективнее, так как исключается лишнее звено в цепочке вызовов (Docker Engine содержит много функций, не нужных Kubernetes).
> 2.  **Стабильность**: Отсутствие зависимости от специфических обновлений Docker Engine, которые могли нарушить работу кластера.
> 3.  **Соответствие стандартам OCI**: Фокус на стандартах Open Container Initiative обеспечивает лучшую переносимость и модульность архитектуры.

### Размещение etcd: Stacked vs External

1.  **Stacked etcd (Совмещенный)**: etcd работает на тех же узлах, что и Control Plane.
    *   *Плюсы:* Простота установки, быстрая локальная сеть.
    *   *Минусы:* Конкуренция за CPU/RAM/Disk. Сбой ноды выбивает и API, и член кворума.
2.  **External etcd (Выделенный)**: etcd на отдельных серверах.
    *   *Плюсы:* Максимальная изоляция, независимое масштабирование.
    *   *Минусы:* Дополнительные сетевые задержки, большее количество хостов для администрирования.

### Статические поды (Static Pods)

Механизм запуска компонентов Control Plane до готовности самого кластера. `kubelet` сканирует `/etc/kubernetes/manifests/` и запускает их автономно. API-сервер создает для них Mirror Pods для отображения.

## Практические сценарии

#### Жизненный цикл создания пода

Процесс при запуске `kubectl create deployment nginx`:
1.  **kubectl** сериализует запрос и отправляет его в API-сервер.
2.  **kube-apiserver** проходит этапы Authn → Authz → Admission и записывает начальное состояние пода (`Pending`) в **etcd**.
3.  **Deployment controller** видит новый объект через механизм Watch, создает **ReplicaSet**.
4.  **ReplicaSet controller** создает спецификации **Pod**-объектов.
5.  **kube-scheduler** обнаруживает новый под в etcd, проходит фазы **Filtering** и **Scoring**, выбирает подходящий узел и обновляет статус пода в **etcd** (связывает под с узлом через `nodeName`).
6.  **kubelet** на выбранном узле видит назначение через Watch, вызывает **CRI** (Container Runtime) запустить контейнер и **CNI** для настройки сети.
7.  **kubelet** сообщает окончательный статус (`Running`) обратно в API-сервер, который обновляет данные в **etcd**.

### Сценарии отказов

*   **Отказ единственного мастера**: `kubelet` продолжает работу запущенных подов, но управление кластером (scaling, apply) невозможно.
*   **Потеря кворума etcd** (например, 3 из 5 узлов упали): API-сервер переходит в **read-only**. Записи невозможны. Авто-восстановление подов прекращается.
*   **Падение планировщика**: Новые поды навсегда зависают в `Pending`.

### Масштабирование Deployment

При `kubectl scale --replicas=5` (или через API) запрос проходит следующий путь («путешествие масштабирования»):
1.  **Пользователь** отправляет запрос на сервер API.
2.  **kube-apiserver** проверяет и обрабатывает запрос, а затем взаимодействует с **etcd** для сохранения намерения пользователя (нового количества реплик).
3.  **etcd** выступает в качестве надежной системы хранения данных кластера.
4.  **Deployment controller** (часть Controller Manager) видит обновление в etcd через Watch и обновляет `replicas` в соответствующем ReplicaSet.
5.  **ReplicaSet controller** видит разницу (фактически 3, нужно 5) и создает 2 новых объекта Pod в API-сервере.
6.  **Scheduler** (Планировщик) обнаруживает новые поды в etcd, выбирает для них подходящие узлы и записывает это решение обратно в etcd.
7.  **Kubelet** на целевом узле получает инструкции от плоскости управления и запускает контейнеры.
