# Архитектура Control Plane в Kubernetes

## Определения

**Control Plane (Плоскость управления)** — это "мозг" кластера Kubernetes, который управляет его состоянием. Он отвечает за принятие глобальных решений о кластере (например, планирование запуска контейнеров), а также за обнаружение и реагирование на события в кластере.

Компоненты Control Plane:

* **`etcd`**: Распределенное хранилище типа "ключ-значение", которое служит единственным источником правды (`Single Source of Truth`) о конфигурации и состоянии всего кластера. Подробнее см. [Обзор etcd](./etcd_overview.md).
* **`kube-apiserver` (API-сервер)**: Центральный компонент, который предоставляет HTTP/HTTPS API для взаимодействия с кластером. Это единственная точка входа для всех операций управления.
* **`kube-scheduler` (Планировщик)**: Компонент, отвечающий за назначение подов (Pods) на доступные рабочие узлы (Nodes) на основе заданных ограничений и доступных ресурсов.
* **`kube-controller-manager` (Менеджер контроллеров)**: Единый бинарный файл, который объединяет и запускает все основные контроллеры Kubernetes в одном процессе. Каждый контроллер является независимым циклом управления (`reconciliation loop`), который отслеживает состояние определенного типа ресурсов (например, `Deployment`, `Node`) и стремится привести фактическое состояние кластера в соответствие с желаемым состоянием, записанным в `etcd`. Подробнее о паттерне reconciliation loop см. [Kubernetes-операторы](./kubernetes_operators.md).
* **`cloud-controller-manager` (Облачный менеджер контроллеров)**: Встраивает Kubernetes в API конкретного облачного провайдера. Выносит логику взаимодействия с облачной инфраструктурой (например, создание балансировщиков, дисков) из основного `kube-controller-manager`, позволяя ядру Kubernetes быть независимым от облака.

**Data Plane (Плоскость данных)** — это совокупность рабочих узлов (Nodes), на которых непосредственно запускаются и работают приложения пользователей в контейнерах.

* **`kubelet`**: Агент, работающий на каждом узле. Он получает инструкции от `kube-apiserver` и отвечает за жизненный цикл подов на своем узле: запускает, останавливает и следит за состоянием контейнеров.
* **`kube-proxy`**: Сетевой прокси, работающий на каждом узле. Он реализует сетевые правила и концепцию сервисов (`Services`) в Kubernetes, управляя сетевым трафиком между подами. Подробнее: [CNI и kube-proxy: определения](../Networking/Network/CNI/definitions.md).

* **Среда выполнения контейнеров (Container Runtime)**: Программное обеспечение, отвечающее за запуск контейнеров (например, `containerd`, `CRI-O`).

Подробнее о компонентах worker-ноды: [Kubelet](./kubelet.md), [CNI и kube-proxy](../Networking/Network/CNI/definitions.md).

## Основные концепции

### kube-apiserver: центральная нервная система кластера

**`kube-apiserver`** — это не просто REST API, а центральный компонент control plane, совмещающий роль шлюза, диспетчера, хранителя состояния и механизма оповещений. Все операции управления кластером проходят через него.

#### Ключевые функции

1. **Единая точка входа (Gateway)** — все компоненты (kubectl, kubelet, scheduler, контроллеры, внешние системы) общаются только с API-сервером, не друг с другом напрямую.

2. **Аутентификация и авторизация** — проверяет, кто делает запрос (сертификат, токен, OIDC, ServiceAccount) и имеет ли он права через RBAC.

3. **Валидация и мутация** — при создании/изменении ресурса проверяет корректность манифеста и может изменять его через admission webhooks (mutating и validating).

4. **Хранение состояния** — единственный компонент, который напрямую общается с etcd. Кэширует данные и обеспечивает согласованность состояния кластера.

5. **Механизм Watch** — клиенты подписываются на изменения ресурсов через long polling, что позволяет мгновенно реагировать на события без постоянных опросов (polling).

#### Жизненный цикл запроса API

1. **Аутентификация:** Проверка личности пользователя или сервиса (сертификат, токен, OIDC).
2. **Авторизация (RBAC):** Проверка прав на выполнение операции в указанном namespace.
3. **Mutating Webhooks:** Модификация полезной нагрузки запроса (например, добавление default-значений, применение политик).
4. **Валидация:** Проверка корректности данных (внутренняя схема + Validating Webhooks).
5. **Сохранение в etcd:** Сериализация объекта в Protobuf/JSON и запись в etcd.
6. **Уведомление подписчиков:** Отправка событий всем `watch`-клиентам (контроллерам, kubelet, scheduler).

**Важно:** Понимание работы kube-apiserver помогает диагностировать 80% проблем с кластером: от отказа в доступе (authentication/authorization failures) до зависших ресурсов (watch timeouts, etcd latency).

### etcd: источник правды

Любое изменение в кластере инициируется через `kube-apiserver` и записывается в `etcd`. Подробнее: [Обзор etcd](./etcd_overview.md).

**Архитектурная роль kube-apiserver:** API-сервер по сути является CRUD-приложением (Create, Read, Update, Delete). Большая часть его работы — хранение и предоставление данных, аналогично другим системам управления контентом.

* **Циклы согласования (`Reconciliation Loops`)**: `kube-controller-manager` реализует ключевой принцип Kubernetes. Контроллеры "наблюдают" (`watch`) за изменениями в `etcd` через `kube-apiserver`. Когда контроллер обнаруживает расхождение между желаемым состоянием (записанным в `etcd`) и фактическим состоянием (в кластере), он предпринимает действия для устранения этого расхождения. Подробнее о паттерне reconciliation loop см. [Kubernetes-операторы](./kubernetes_operators.md).

* **Планирование (`kube-scheduler`)**: `kube-scheduler` также "наблюдает" за API-сервером. Как только появляется новый под без назначенного узла, планировщик выбирает для него наиболее подходящий узел и сообщает об этом решении API-серверу, который записывает эту информацию в `etcd`. Подробно о процессе планирования: [Kube-scheduler](./kube_scheduler.md).

## Практические сценарии

### Коммуникация между компонентами

Коммуникация в Kubernetes строится вокруг `kube-apiserver` как центральной шины обмена. Все компоненты взаимодействуют с ним по HTTPS, используя событийную модель `watch` для получения обновлений.

* **Контроллеры и планировщик**: `kube-scheduler` и `kube-controller-manager` наблюдают за ресурсами (Pods, Nodes, ReplicaSets) и отправляют в API-сервер решения о планировании и согласовании состояния.
* **Kubelet**: Агент на узле регистрируется в API-сервере, получает задания на запуск подов, сообщает об их статусе. Для интерактивных команд (`exec`, `logs`, `port-forward`) `kube-apiserver` инициирует соединение к `kubelet`. В средах с ограниченной связностью для этого может использоваться `Konnectivity` прокси.
* **CoreDNS**: Отслеживает объекты `Service` и `EndpointSlice` для предоставления DNS-имен внутри кластера.
* **Пользователи и операторы**: Взаимодействуют с кластером через `kubectl`, дашборды или кастомные контроллеры, которые также обращаются к `kube-apiserver`.

#### Сетевая коммуникация и безопасность

* **Pod-to-Pod**: Связность обеспечивается CNI-плагином, который настраивает маршрутизацию в кластере.
* **Pod-to-Service**: `kube-proxy` на каждом узле отслеживает `EndpointSlices` и программирует правила `iptables` или `IPVS` для перенаправления трафика с виртуального `ClusterIP` на реальные IP-адреса подов.
* **Admission Webhooks**: Для валидации или мутации объектов `kube-apiserver` выполняет HTTPS-вызовы к вебхукам. Важно обеспечить сетевую доступность вебхуков (через `Service`) и корректно настроить `NetworkPolicy`, чтобы не блокировать этот трафик.
* **Безопасность**: Аутентификация компонентов выполняется через клиентские сертификаты и токены `ServiceAccount`. Авторизация регулируется через `RBAC`.

#### Порты и направления трафика

| Компонент/порт | Направление | Назначение |
| :--- | :--- | :--- |
| 6443 (apiserver) | клиенты → apiserver | Все запросы к API |
| 2379–2380 (etcd) | apiserver ↔ etcd | Хранилище и Raft-пиринг `etcd` |
| 10250 (kubelet) | apiserver → kubelet | `exec`/`logs`/`port-forward`, метрики/health |
| 10257 (controller-manager) | локально/ops | health/metrics компонента |
| 10259 (scheduler) | локально/ops | health/metrics компонента |
| 10249/10256 (kube-proxy) | локально | metrics/health |
| 30000–32767 (NodePort) | внешние клиенты → узлы | Доступ к `Service` извне |

### Жизненный цикл создания пода

#### Пример: kubectl create deployment

```bash
kubectl create deployment nginx --image=nginx
```

Пошаговый процесс:

1. **kubectl преобразует команду** в HTTP-запрос (JSON) и отправляет его на `kube-apiserver`.
2. **Аутентификация:** API-сервер проверяет пользователя (например, по сертификату из kubeconfig).
3. **Авторизация (RBAC):** Проверяет права на создание deployment в указанном namespace.
4. **Admission Controllers:** Запускается цепочка admission controllers — валидация (синтаксис) и мутация (политики по умолчанию).
5. **Запись в etcd:** API-сервер сериализует объект и записывает в etcd.
6. **Ответ клиенту:** Возвращает успешный ответ.
7. **Реакция контроллеров:** Событие о создании deployment через watch получает `kube-controller-manager`, который создаёт ReplicaSet, а тот — поды. Scheduler назначает поды на ноды, kubelet их запускает.

#### Пример: kubectl get pods с отладкой

```bash
kubectl get pods -v=8
```

В выводе видны HTTP-запросы к `/api/v1/namespaces/default/pods`. API-сервер:

* Аутентифицирует запрос
* Проверяет RBAC
* Загружает данные из etcd (или из cache)
* Сериализует в JSON и возвращает

Это полезно для диагностики проблем доступа и понимания того, какие именно запросы отправляет kubectl.

### Обеспечение отказоустойчивости

* **Кворум `etcd`**: Кластер `etcd` требует наличия "кворума" — большинства работающих узлов (`(N/2) + 1`) — для выполнения операций записи. Кластер из **3 мастеров** может пережить отказ **1** мастера, а кластер из **5 мастеров** — отказ **2** мастеров. Четное число узлов не добавляет отказоустойчивости по сравнению с предыдущим нечетным числом, но требует больше ресурсов.

* **Единая точка входа**: Рабочие узлы (`kubelet`) не знают IP-адреса всех мастеров. Вместо этого они подключаются к **балансировщику нагрузки (Load Balancer)**, который имеет стабильный виртуальный IP (VIP) или DNS-имя. Балансировщик распределяет запросы между всеми здоровыми `kube-apiserver` на мастер-узлах. Если один мастер выходит из строя, балансировщик автоматически перестает направлять на него трафик, обеспечивая бесперебойную работу для воркеров.

Подробнее о стратегиях обеспечения высокой доступности, включая PDB, Fencing и предотвращение Split-Brain, см. в документе [Высокая доступность в Kubernetes](../Base/high_availability.md).

## Дополнительная информация

* **Механизм `Watch`**: Компоненты Control Plane активно используют механизм подписки (`watch`) через `kube-apiserver` для отслеживания изменений в `etcd` в реальном времени, вместо постоянного опроса.
* **Восстановление после сбоев**: `etcd` поддерживает создание **снимков (snapshots)**, которые позволяют восстанавливать состояние кластера.
* **Контроллеры**: Подробное описание паттерна reconciliation loop и операторов см. в документе [Kubernetes-операторы](./kubernetes_operators.md).
