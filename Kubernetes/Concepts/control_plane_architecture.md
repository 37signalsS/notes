# Архитектура Control Plane в Kubernetes

## Определения

**Control Plane (Плоскость управления)** — центральный узел управления кластером Kubernetes, отвечающий за принятие глобальных решений (например, планирование запуска контейнеров), обнаружение и реагирование на события.

**Data Plane (Плоскость данных)** — совокупность рабочих узлов (**Nodes**), на которых непосредственно выполняются приложения пользователей в контейнерах.

### Концепция «5 бинарных файлов»

Архитектура Kubernetes базируется на пяти ключевых исполняемых файлах:

1. **`kube-apiserver`** (Control Plane)
2. **`kube-scheduler`** (Control Plane)
3. **`kube-controller-manager`** (Control Plane)
4. **`kubelet`** (Рабочий узел)
5. **`kube-proxy`** (Рабочий узел)

*Примечание: **etcd** и среда выполнения (**Container Runtime**, например, `containerd`) являются внешними по отношению к основному проекту Kubernetes.*

### Требования к узлам кластера

| Тип узла | Ресурсы (типичные) | Особенности |
| :--- | :--- | :--- |
| **Master (Control Plane)** | 2 **CPU**, 4 GB **RAM** | Запускают только управляющие компоненты. Для **HA (High Availability)** рекомендуется 3 или 5 узлов. |
| **Worker (Рабочие узлы)** | Зависят от нагрузки приложений | Требования определяются потребностями контейнеров. |

## Основные концепции

### Компоненты Control Plane

- **`kube-apiserver` (API-сервер)**: центральный компонент, предоставляющий **HTTP** API для взаимодействия с кластером. Единственная точка входа для всех операций управления.
- **`etcd`**: распределенное хранилище типа «ключ-значение» на основе алгоритма консенсуса **Raft**, служащее единым источником данных о состоянии кластера. Требует **нечётного числа узлов** для формирования кворума (floor(N/2)+1). **Медленный диск** (fsync >10 мс) вызывает перевыборы лидера (leader re-elections) и дестабилизацию кластера. Подробнее: [Обзор etcd](./etcd_overview.md).
- **`kube-scheduler` (Планировщик)**: отвечает за назначение подов (**Pods**) на доступные узлы на основе требований к ресурсам и ограничений. Процесс планирования включает две основные фазы: **Filtering** (отсев неподходящих узлов по taints, ресурсам и т.д.) и **Scoring** (ранжирование оставшихся). Планировщик учитывает только **requests** (гарантированные ресурсы), в то время как **limits** определяют максимально допустимое потребление в рантайме и на планирование не влияют. Можно обходить стандартный планировщик, используя **статические поды** или напрямую указывая `nodeName` в манифесте. Подробнее: [Планировщик подов](./kube_scheduler.md).
- **`kube-controller-manager` (Менеджер контроллеров)**: единый процесс, объединяющий десятки контроллеров. Каждый контроллер реализует цикл согласования (**reconciliation loop**), приводя фактическое состояние кластера к желаемому. Подробнее: [Цикл согласования](#kube-controller-manager--цикл-согласования).
- **`cloud-controller-manager`**: интегрирует кластер с API конкретного облачного провайдера (управление балансировщиками, дисками, маршрутами).

### kube-apiserver — обработка запросов

Все запросы к API-серверу проходят через конвейер обработки (**handler pipeline**). Порядок строгий — перестановка невозможна:

1. **Аутентификация (Authentication):** проверка личности клиента — кто делает запрос (сертификаты, токены, ServiceAccount JWT, **OIDC (OpenID Connect)**). Компоненты кластера общаются через **mTLS (mutual Transport Layer Security)**.
2. **Авторизация (Authorization):** проверка прав — что можно делать (через **RBAC (Role-Based Access Control)**).
3. **Admission (Mutation → Validation):** может изменить запрос (MutatingWebhookConfiguration) или запретить его (ValidatingWebhookConfiguration).
4. **Сохранение в etcd:** запись объекта в базу данных. Admission controllers выполняются строго до записи.
5. **Уведомление подписчиков:** рассылка событий через механизм **Watch** (позволяет компонентам эффективно отслеживать изменения ресурсов без постоянных опросов (polling), используя длинные соединения).

> **Ловушка:** порядок нельзя путать — authn → authz → admission. Авторизация не может быть до аутентификации: без установления личности (`кто`) нельзя проверить права (`что можно`). Admission выполняется **после** авторизации — политики могут изменить или запретить уже авторизованный запрос.

### kube-controller-manager — цикл согласования

**kube-controller-manager** — единый бинарник, внутри которого десятки логически независимых контроллеров выполняются в отдельных горутинах (goroutines). Они объединены в один процесс для экономии ресурсов и упрощения эксплуатации.

Каждый контроллер реализует бесконечный цикл согласования (**reconciliation loop**), сводящийся к трём шагам:

1. **Наблюдение (Watch):** через watch-механизм API-сервера контроллер получает события об изменении ресурсов.
2. **Сравнение:** сопоставляет желаемое состояние (`spec`) с текущим (`status`).
3. **Действие:** если есть расхождение — создаёт, удаляет или изменяет объекты для устранения разницы.

Цикл повторяется бесконечно. Удаление пода вручную приводит к обнаружению расхождения и созданию нового.

В состав kube-controller-manager входят:

- **Deployment / ReplicaSet controller** — поддерживает заданное число реплик. Разворачивает ReplicaSet из Deployment, тот создаёт поды.
- **Node controller** — следит за состоянием узлов. Если нода перестаёт отправлять heartbeat, помечает её `NotReady` и инициирует выселение подов.
- **Job / CronJob controller** — управляет жизненным циклом задач и их запуском по расписанию.
- **EndpointSlice controller** — связывает Service с подами, обновляя списки эндпоинтов.
- **ServiceAccount & Token controller** — создаёт сервис-аккаунты и связанные с ними секреты в новых namespace.
- **Namespace controller** — удаляет все ресурсы внутри namespace при его удалении.

### Выбор лидера (Leader Election)

`kube-controller-manager` и `kube-scheduler` участвуют в **leader election** через объекты `Leases` (хранятся в etcd, namespace `kube-system`). Активный экземпляр удерживает Lease — только он выполняет reconciliation/scheduling. Остальные стоят в режиме ожидания и перехватывают Lease при отказе активного.

### Компоненты рабочего узла

- **`kubelet`**: агент на каждом узле, управляющий жизненным циклом подов. Подробнее: [Kubelet](./kubelet.md).
- **`kube-proxy`**: сетевой прокси, программирующий **iptables** или **IPVS** для реализации абстракции сервисов и балансировки трафика. Подробнее: [CNI и kube-proxy: роли](../Networking/Network/cni_kube_proxy_roles.md).
- **Container Runtime**: среда запуска контейнеров (CRI-совместимая, например, `containerd`).

### Запуск ядра: статические поды (Static Pods)

Для решения проблемы запуска API-сервера до того, как API-сервер станет доступен, используются **статические поды**. `kubelet` сканирует директорию `/etc/kubernetes/manifests/` и автоматически запускает поды, описанные в найденных манифестах. Это позволяет развернуть компоненты Control Plane как контейнеры на этапе инициализации кластера.

### etcd — размещение и производительность

В зависимости от требований к кластеру, **etcd** может быть развернут:

1. **На тех же хостах, что и Control Plane (Stacked etcd):**
   - **Плюсы:** более быстрый сетевой доступ (общение через localhost или локальную сеть ноды), упрощенное управление (один набор нод).
   - **Минусы:** компоненты Control Plane и etcd делят одни и те же ресурсы (CPU, RAM, Disk I/O). При сбое ноды теряется и API-сервер, и член кворума etcd.
2. **На выделенных хостах (External etcd):**
   - **Плюсы:** максимальная отказоустойчивость, независимое масштабирование ресурсов, удобство резервного копирования.
   - **Минусы:** дополнительные задержки (latency) при общении API-сервера с etcd по сети, большее количество управляемых хостов.

## Практические сценарии

### Жизненный цикл создания пода

При выполнении команды `kubectl create deployment nginx --image=nginx`:

1. **kubectl** сериализует YAML в JSON и шлёт HTTP POST/PATCH на **kube-apiserver**.
2. **kube-apiserver** выполняет (строго последовательно):
   - **Аутентификацию** (cert/token/OIDC).
   - **Авторизацию** (RBAC).
   - **Admission controllers** — все выполняются до записи в etcd:
     - `MutatingWebhookConfiguration` — может изменить манифест (например, Vault Agent Injector добавляет sidecar). Выполняется первым.
     - `ValidatingWebhookConfiguration` — проверяет корректность. Выполняется после мутации.
     - `ResourceQuota` — проверяет лимиты namespace.
3. Прошедший все проверки объект **Deployment** записывается в **etcd** — единый источник истины.
4. **Deployment controller** (внутри `kube-controller-manager`) подписан на события через **informer** (watch); вычисляет diff (desired vs actual), создаёт **ReplicaSet**. **ReplicaSet controller** создаёт **Pod**-объекты с пустым полем `nodeName` (статус Pending).
5. **kube-scheduler** видит unscheduled pods, запускает фазы:
   - **Filtering** — отсеивает ноды по taints/`resources.requests` (не `limits`)/affinity.
   - **Scoring** — ранжирует оставшиеся.
   Планировщик учитывает только **requests** (зарезервировано для пода), а **limits** — это максимум для runtime (OOMKill / CPU throttle) и не влияют на планирование.
   Записывает выбранную ноду в `pod.spec.nodeName` через binding-запрос в API-сервер.
6. **kubelet** на выбранной ноде подписан на поды, назначенные именно ей (через Watch); вызывает **CRI** (`containerd` через gRPC) для pull образа и старта контейнера, настраивает volumes, затем вызывает **CNI-плагин** для сетевого пространства.
7. kubelet обновляет `pod.status` (фаза Running) обратно в API-сервер.

Важно: kubelet не обращается к etcd напрямую — только к API-серверу.

### Отказ единственного мастера (Single Master)

В кластере с одним мастер-узлом его отказ приводит к:

- **`kubelet` на воркерах автономен** — запущенные поды продолжают работать
- **`kube-apiserver` недоступен** — `kubectl` и все API-запросы не проходят
- **`kube-scheduler` недоступен** — новые поды не назначаются на узлы
- **`kube-controller-manager` недоступен** — ReplicaSet не создаёт новые поды при сбоях

В HA-конфигурации (3+ мастера) отказ одного узла компенсируется кворумом etcd и leader election — control plane продолжает работу. Подробнее: [Высокая доступность](../Base/high_availability.md).

### Восстановление после потери мастера

Если мастер утерян без возможности возврата (например, аппаратный сбой), процедура восстановления:

```bash
etcdctl snapshot restore backup.db --data-dir /var/lib/etcd-new
# → {"level":"info","ts":"...","logger":"etcd-server","msg":"added member","...":""} (Успешное восстановление снапшота)
```

1. **Новый мастер-хост** — подготовить сервер (ОС, containerd, kubeadm/kubectl/kubelet)
2. **kubeadm init / kubeadm join** — инициализировать или присоединить новый мастер к кластеру, указав `--control-plane-endpoint` (VIP балансировщика)
3. **Рестарт воркеров** — kubelet на воркерах переподключается к новому API-серверу через VIP (автоматически, если `kubelet.kubeconfig` указывает на балансировщик)

Для Kubespray-кластеров восстановление выполняется через повторный запуск `kubespray` с инвентари, содержащей новый мастер-узел.

### Потеря кворума etcd

Кворум etcd = `floor(N/2) + 1`. Для 5 узлов кворум = 3. Если падает 3 ноды из 5 (остаётся 2 < 3), наступает потеря кворума:

* **Запись:** лидер не избирается, write-запросы (POST/PUT/PATCH/DELETE) не коммитятся.
* **Чтение:** API-сервер перестаёт отвечать на read-запросы или отдаёт данные из кэша, если включён `stale-read`.
* **Поды:** продолжают работать — kubelet автономен, трафик между подами идёт, уже запущенные контейнеры не останавливаются.
* **Изменения:** невозможны — `kubectl apply`, `scale`, `rollout`, `exec`, `logs` не работают.

> **Ловушка:** «всё умерло». Нет — нагрузка (поды, трафик) живёт, отказывает только управление. Кластер переходит в read-only.

**Восстановление:** вернуть упавшие ноды в строй или выполнить `etcdctl snapshot restore` из резервной копии на новой ноде. Подробнее: [Кластеризация и восстановление etcd](../../etcd/clustering_and_recovery.md).

### Масштабирование Deployment

При выполнении `kubectl scale deployment nginx --replicas=5`:

1. **kubectl** отправляет запрос в API-сервер, тот записывает новое значение `replicas=5` в **etcd**.
2. Через watch-событие об изменении Deployment уведомление получает **kube-controller-manager**.
3. **Deployment controller** обновляет связанный **ReplicaSet**.
4. **ReplicaSet controller** видит: желаемо 5 подов, фактически 3. Создаёт 2 новых пода через API-сервер.
5. Новые поды попадают в очередь — их подхватывает **kube-scheduler** и назначает на ноды.
6. **kubelet** на этих нодах запускает контейнеры и докладывает о статусе обратно в API-сервер.

Controller-manager при этом не запускает контейнеры и не назначает поды — он лишь приводит число объектов к нужному, а непосредственную работу выполняют scheduler и kubelet.
