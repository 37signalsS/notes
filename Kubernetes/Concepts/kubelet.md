# Kubelet — агент Kubernetes на узле

## Определение

**Kubelet** — это основной агент Kubernetes («ножной» агент), работающий на каждом узле кластера. Он функционирует как системный сервис (обычно через systemd) и является единственной точкой управления, которая взаимодействует напрямую со средой выполнения контейнеров (Container Runtime).

**Ключевая роль:** Kubelet преобразует декларативные спецификации подов (PodSpec), полученные из API-сервера или локальных файлов, в фактические действия по запуску и управлению контейнерами. Он обеспечивает соответствие текущего состояния узла желаемому, гарантируя, что описанные контейнеры запущены и здоровы.


## Основные концепции

### Жизненный цикл управления подом (Sync Loop)

Kubelet работает в бесконечном цикле синхронизации (**sync loop**). Он опрашивает источники конфигурации и приводит состояние узла в соответствие с ними.

#### Механизм PLEG (Pod Lifecycle Event Generator)
Для эффективного отслеживания состояния контейнеров Kubelet использует механизм **PLEG**. 
*   **Зачем это нужно:** Вместо того чтобы постоянно опрашивать Container Runtime о статусе каждого контейнера (что создает высокую нагрузку), Kubelet полагается на события.
*   **Как это работает:** PLEG периодически запрашивает у рантайма список изменений состояний контейнеров, генерирует события (например, `ContainerStarted`, `ContainerDied`) и помещает их в очередь. 
*   **Влияние на диагностику:** Ошибка `PLEG is unhealthy` в логах часто означает, что среда выполнения контейнеров зависла или перегружена и не может вовремя ответить на запросы Kubelet.

#### Этапы синхронизации:

1.  **Получение конфигурации:** Kubelet получает список подов из трех источников:
    *   **API Server:** основной источник через механизм `watch`.
    *   **Статические файлы:** директория на диске (обычно `/etc/kubernetes/manifests`).
    *   **HTTP-endpoint:** внешний URL (редко используется).
2.  **Синхронизация с желаемым состоянием:** Kubelet взаимодействует с API-сервером, чтобы получить актуальные PodSpec и данные о связанных ресурсах (Secrets, ConfigMaps).
3.  **Синхронизация ресурсов:**
    *   **Извлечение образов:** Если указанный в спецификации образ отсутствует на узле, Kubelet обращается к Container Runtime для его загрузки из реестра.
    *   **Управление контейнерами:** Обращается к **CRI** (Container Runtime Interface) для создания и запуска контейнеров. Kubelet обеспечивает запуск и остановку всех контейнеров в поде одновременно.
    *   **Настройка сети:** Обращается к **CNI** (Container Network Interface) для настройки сетевого пространства имен, которое является общим для всех контейнеров в поде.
    *   **Монтирование хранилища:** Обращается к **CSI** (Container Storage Interface) для подготовки и монтирования томов.
4.  **Мониторинг и самовосстановление:** 
    *   Управляет полным жизненным циклом (создание, запуск, мониторинг).
    *   Предпринимает корректирующие действия (например, перезапуск), если фактическое состояние контейнеров не соответствует желаемому.
    *   Выполняет периодические проверки работоспособности (Liveness, Readiness, Startup пробы).
5.  **Отчетность:** Регулярно сообщает о состоянии узла и подконтрольных контейнеров в API-сервер для принятия решений о планировании и распределении ресурсов.

### Механизм Heartbeats (Lease API)

Для информирования кластера о своей работоспособности Kubelet использует объекты **Lease** в пространстве имен `kube-node-lease`.
*   **Старый метод (NodeStatus):** Kubelet отправлял полное состояние узла каждые 10 секунд, что создавало большую нагрузку на API-сервер и etcd.
*   **Современный метод (Lease):** Kubelet обновляет легковесный объект Lease каждые **10 секунд** (`nodeLeaseDurationSeconds` = 40 — срок, после которого узел считается недоступным). Полное состояние (NodeStatus) отправляется только при значительных изменениях или раз в **5 минут** (`nodeStatusReportFrequency`). Это существенно повышает масштабируемость кластера. Подробности см. в разделе [Механизм Lease](../Troubleshooting/Common_Errors/NodeUnavailability/definitions.md#heartbeats-и-lease-api).

### Управление ресурсами и Node Allocatable

Kubelet гарантирует, что системные процессы узла имеют достаточно ресурсов для стабильной работы кластера. Для этого используется концепция **Node Allocatable**.

**Формула расчета:**
`Allocatable = Node Capacity - [kube-reserved] - [system-reserved] - [eviction-threshold]`

*   **kube-reserved:** Ресурсы для компонентов Kubernetes (Kubelet, Container Runtime).
*   **system-reserved:** Ресурсы для системных демонов ОС (sshd, udev, systemd).
*   **eviction-threshold:** Запас ресурсов, при достижении которого начинается вытеснение подов.

### Вытеснение подов (Eviction)

Kubelet жестко контролирует использование ресурсов узла (CPU, память, диск) и гарантирует, что контейнеры не превышают установленные лимиты.
*   **Контроль лимитов:** Если контейнер потребляет слишком много ресурсов, Kubelet может принудительно завершить или выселить его.
*   **Hard Eviction:** Порог, при котором Kubelet немедленно удаляет поды без ожидания завершения (`grace period`).
*   **Soft Eviction:** Порог с настраиваемым временем ожидания перед удалением.
*   **QoS (Quality of Service):** При вытеснении Kubelet в первую очередь удаляет поды класса `BestEffort`, затем `Burstable`, и в последнюю очередь `Guaranteed`. Детально см. **[Классы QoS и работа Менеджера выселения](../Troubleshooting/Common_Errors/PodEvicted/qos_and_eviction.md)**.
*   **Профилактика:** Настройка порогов и резервирование ресурсов описаны в руководстве **[Профилактика выселения подов](../Troubleshooting/Common_Errors/PodEvicted/prevention.md)**.
*   **Очистка узла:** При удалении пода Kubelet освобождает все связанные с ним ресурсы и удаляет контейнеры.

### Сборка мусора (Garbage Collection)

Kubelet автоматически очищает ресурсы узла:
*   **Container GC:** Удаляет старые завершенные контейнеры и их логи.
*   **Image GC:** Удаляет неиспользуемые образы, когда использование диска превышает порог (параметр `ImageGCHighThresholdPercent`).

## Архитектура и компоненты

Место Kubelet в общей схеме кластера (взаимодействие с Control Plane и другими узлами) описано в [Архитектуре Control Plane](./control_plane_architecture.md).

### Взаимодействие через CRI

Kubelet взаимодействует со средой выполнения контейнеров (containerd, CRI-O) через gRPC по протоколу **CRI** (Container Runtime Interface). Этот стандартный API позволяет Kubernetes быть полностью независимым от конкретной реализации рантайма. Подробнее о рантаймах, их типах и инструментах см. [Container Runtime и CRI](./container_runtime.md).

**Ключевое преимущество:** Именно разделение через CRI позволило отказаться от жесткой привязки к Docker Engine (**dockershim**) и перейти на более легковесные и специализированные среды выполнения. Это гарантирует модульность: можно использовать любой OCI-совместимый рантайм без изменения кода самого Kubelet.
*   **Runtime Service:** управление контейнерами и подами.
*   **Image Service:** управление образами.

### Менеджеры ресурсов (Resource Managers)

Для обеспечения высокой производительности и изоляции нагрузок Kubelet включает специализированные менеджеры:

1.  **CPU Manager:** Позволяет назначать подам выделенные (exclusive) ядра CPU (при использовании класса `Guaranteed` с целыми значениями CPU).
2.  **Memory Manager:** Обеспечивает выделение памяти на конкретных NUMA-узлах для минимизации задержек доступа. Подробнее: [Memory Manager](../Scheduling/memory_manager.md).
3.  **Device Manager:** Управляет доступом к специализированному оборудованию (GPU, FPGA, RDMA) через механизм **Device Plugins**. Подробнее: [Device Manager](../Scheduling/device_manager.md).
4.  **Topology Manager:** Координирует работу других менеджеров, гарантируя, что CPU, память и устройства выделяются оптимально с точки зрения топологии оборудования (например, на одном NUMA-узле). Подробнее: [Topology Manager](../Scheduling/topology_manager.md).

### Интегрированный cAdvisor

В состав Kubelet встроен **cAdvisor** (Container Advisor). Он собирает метрики использования ресурсов (CPU, память, диск, сеть) по каждому контейнеру и предоставляет их через API (обычно `/metrics/cadvisor`). Эти данные используются Horizontal Pod Autoscaler (HPA) и системами мониторинга (Prometheus).

## Безопасность

### TLS Bootstrapping

Процесс автоматического подключения нового узла к кластеру:
1.  Kubelet запускается с временным токеном (bootstrap token).
2.  Генерирует запрос на подпись сертификата (CSR).
3.  API-сервер (или администратор) одобряет CSR.
4.  Kubelet получает клиентский сертификат для авторизованного общения с API.
5.  Автоматическая ротация сертификатов (`rotateCertificates: true`) обновляет их до истечения срока.

Детали жизненного цикла сертификатов, одобрения CSR и практической настройки ротации — в разделе [Управление сертификатами](../Operations/certificate_management.md).

### NodeRestriction

Специальный Admission-контроллер **NodeRestriction** ограничивает возможности Kubelet. Агент может изменять только "свои" объекты (свой узел и поды, запущенные на нем). Это минимизирует ущерб в случае компрометации отдельной ноды.

Подробнее о полной конфигурации безопасности Kubelet, включая аутентификацию, авторизацию, TLS и CIS Benchmark, см. в [Безопасность Kubelet](../Security/kubelet_security.md).

### Порты Kubelet

Kubelet слушает несколько портов, каждый из которых имеет своё назначение и уровень защиты:

| Порт | Назначение | Аутентификация |
| :--- | :--- | :--- |
| **10250** | Основной HTTPS-порт Kubelet API (список подов, метрики, `exec`, `logs`, `port-forward`). Используется API-сервером и всеми инструментами мониторинга. | Требуется (X.509 сертификат) |
| **10255** | Устаревший read-only порт (без аутентификации/авторизации). С версии 1.16 **отключён по умолчанию** (`readOnlyPort: 0`) и помечен как deprecated. Рекомендуется не включать — любой, кто имеет сетевой доступ к узлу, сможет читать метки/метрики нод и подов. | Нет (небезопасен) |
| **10248** | Endpoint `healthz` проверки работоспособности, слушается только на `127.0.0.1`. Позволяет локально проверять, жив ли Kubelet. Отключается значением `healthzPort: 0`. | Нет (только loopback) |

Проверка работоспособности Kubelet на узле:

```bash
curl -s http://127.0.0.1:10248/healthz
# → ok
```

Если служба вернула ошибку или соединение отклонено — Kubelet не готов принимать поды.

### Безопасность Kubelet API

Kubelet прослушивает порт 10250 и предоставляет API для управления и сбора метрик. Защита этого API критична: уязвимый Kubelet — это прямой путь к компрометации всего узла, так как через него можно выполнять команды внутри контейнеров (`exec`) и читать их логи и метаданные.
*   **Authentication (Аутентификация):** По умолчанию может быть включен анонимный доступ (не рекомендуется). Рекомендуется использовать X.509 клиентские сертификаты (см. подпись `clientCAFile` / TLS Bootstrapping) или аутентификацию через API-сервер (webhook). Запросы без валидных учётных данных при анонимном доступе рассматриваются от имени `system:anonymous`.
*   **Authorization (Авторизация):** Рекомендуется режим `Webhook`, при котором Kubelet делегирует проверку прав API-серверу (RBAC). По умолчанию может действовать `AlwaysAllow`, что недопустимо в production.
*   **Отключение read-only порта:** Требование безопасности по умолчанию — `readOnlyPort: 0` (это же значение по умолчанию с 1.16). Включение 10255 без необходимости признаётся нарушением в аудитах безопасности (например, kube-bench, CIS).
*   **TLS:** Порт 10250 обслуживает HTTPS. Сертификат задаётся через `tlsCertFile`/`tlsPrivateKeyFile` и генерируется автоматически (self-signed) в `--cert-dir`, если они не указаны.

## Практические сценарии

### Типовая конфигурация

Конфигурационный файл `/var/lib/kubelet/config.yaml`:

```yaml
apiVersion: kubelet.config.k8s.io/v1
kind: KubeletConfiguration
cgroupDriver: systemd
staticPodPath: /etc/kubernetes/manifests
evictionHard:
  memory.available: "200Mi"
  nodefs.available: "10%"
kubeReserved:
  cpu: "200m"
  memory: "512Mi"
systemReserved:
  cpu: "100m"
  memory: "256Mi"
rotateCertificates: true
serverTLSBootstrap: true
authentication:
  anonymous:
    enabled: false
  webhook:
    enabled: true
authorization:
  mode: Webhook
```

### Источники конфигурации: файл, флаги и drop-in

Современная схема получения параметров Kubelet — **иерархия приоритетов** (от высшего к низшему):

1.  **Командные флаги** (в `ExecStart` unit-файла systemd) — имеют наивысший приоритет.
2.  **Файлы drop-in** из каталога `--config-dir` (например, `/etc/kubernetes/kubelet.conf.d`) — переопределяют основной конфиг-файл и значения по умолчанию.
3.  **Конфигурационный файл**, заданный флагом `--config <путь>` (обычно `/var/lib/kubelet/config.yaml`), тип `KubeletConfiguration`.
4.  **Значения по умолчанию** для версии `KubeletConfiguration`.

Ключевые особенности:

*   **Флаги переопределяют файл:** если параметр задан и флагом, и в конфиг-файле, действует значение из командного флага. Это сделано для обратной совместимости с устаревшим CLI-подходом.
*   **Дефолты различаются:** значения по умолчанию для конфиг-файла отличаются от дефолтов отдельных CLI-флагов. Если указан `--config`, применяются дефолты соответствующей версии `KubeletConfiguration` (например, `kubelet.config.k8s.io/v1beta1` или `kubelet.config.k8s.io/v1`), а не дефолты флагов. Именно поэтому при переходе с флагов на файл стоит явно проверить такие параметры, как `readOnlyPort`, `evictionHard`, `cgroupDriver`.
*   **Относительные пути** в конфиг-файле разрешаются относительно расположения самого файла, а в командных флагах — относительно текущего рабочего каталога процесса.
*   **Drop-in каталог** (Beta с Kubernetes v1.30): файлы обязаны иметь суффикс `.conf` и обрабатываются в лексическом порядке. Для v1.28–v1.29 требовалась переменная окружения `KUBELET_CONFIG_DROPIN_DIR_ALPHA`. Допускается указывать `--config-dir` без основного `--config`.
*   При установке через **kubeadm** конфигурация Kubelet генерируется в `/var/lib/kubelet/config.yaml`, а стартовые флаги (включая `--config`) прописываются в `/etc/systemd/system/kubelet.service.d/10-kubeadm.conf`.

Типовой unit-файл службы kubelet (генерируется kubeadm в `/etc/systemd/system/kubelet.service.d/10-kubeadm.conf`):

```ini
[Service]
Environment="KUBELET_KUBECONFIG_ARGS=--bootstrap-kubeconfig=/etc/kubernetes/bootstrap-kubelet.conf \
--kubeconfig=/etc/kubernetes/kubelet.conf"
Environment="KUBELET_CONFIG_ARGS=--config=/var/lib/kubelet/config.yaml"
ExecStart=/usr/bin/kubelet $KUBELET_KUBECONFIG_ARGS $KUBELET_CONFIG_ARGS $KUBELET_EXTRA_ARGS
```

Изменение конфигурации требует перезагрузки systemd-даемона (после правки unit) и перезапуска службы:

```bash
sudo systemctl daemon-reload
sudo systemctl restart kubelet
```

### Управление Kubelet как службой systemd

Kubelet — это классическая системная служба, которой управляет `systemd`:

```bash
sudo systemctl status kubelet                # статус и последние ошибки
sudo systemctl restart kubelet               # перезапуск
sudo systemctl enable --now kubelet          # включить автозапуск и запустить
journalctl -u kubelet -f                     # логи в реальном времени
journalctl -u kubelet --since "1 hour ago"   # логи за последний час
```

Проверка конфигурации и связности с рантаймом:

```bash
kubelet --version                            # версия бинарника
sudo crictl info                             # состояние CRI-рантайма (связность)
curl -s http://127.0.0.1:10248/healthz       # healthz-эндпоинт
```

Распространённый симптом: `systemctl status kubelet` показывает активный (running) сервис, но узел в `NotReady` — тогда проблема не в запуске процесса, а в его взаимодействии с API-сервером или рантаймом (см. раздел «Диагностика»).

### Ключевые параметры KubeletConfiguration

Помимо параметров из примера выше, важно понимать и уметь настраивать:

*   **`maxPods`** (по умолчанию `110`) — максимальное количество подов на узле. Увеличивают для плотных кластеров, уменьшают для маленьких узлов. Значение отражается в `allocatable.pods` узла; при превышении планировщик отбрасывает поды с причиной `Too many pods`.
    *   **Почему именно 110:** Дефолтное значение связано с переключением контекста (context switch). Каждый под содержит минимум 2 контейнера (приложение + `pause`), поэтому 110 подов ≈ 220 процессов. При ~250 процессах на одной машине переключение контекста может занимать до 50% CPU-времени, что делает дальнейшее увеличение числа процессов экономически неэффективным.
*   **`podPidsLimit`** (по умолчанию `-1` = без лимита) — лимит процессов (PID) на под. Защищает узел от «размножившихся» процессов внутри пода (например, fork-бомб). Общий лимит PID узла задаётся на уровне ядра (`kernel.pid_max`) и контролируется условием `PIDPressure`.
*   **`kubeAPIQPS` / `kubeAPIBurst`** (по умолчанию `50` / `100`) — ограничение частоты и «всплеска» запросов Kubelet к API-серверу. Полезно снизить при риске флуда, повысить — при большом числе подов на узле.
*   **`nodeStatusUpdateFrequency`** (по умолчанию `10s`) — частота публикации статуса узла (когда Lease выключен). Влияет на скорость обнаружения `NotReady` контроллером узла.
*   **`nodeStatusReportFrequency`** (по умолчанию `5m`) — частота отчётности статуса узла при неизменном состоянии (совместно с Lease). Публикация немедленна при любом изменении.
*   **`nodeLeaseDurationSeconds`** (по умолчанию `40`) — срок действия Lease-объекта группы `kube-node-lease`; Lease продлевается каждые `10s`. По истечении срока узел считается недоступным.
*   **`evictionHard` / `evictionSoft`** — жёсткие/мягкие пороги вытеснения (см. раздел «Вытеснение подов»).
*   **`imageGCHighThresholdPercent` / `imageGCLowThresholdPercent`** (по умолчанию `85` / `80`) — пороги сборки мусора образов по заполнению файловой системы, выделенной под образы (`imagefs`).
*   **Ротация логов контейнеров:** `containerLogMaxSize` (по умолчанию `10Mi`) и `containerLogMaxFiles` (по умолчанию `5`) — размер и число ротируемых лог-файлов контейнера.
*   **`cgroupDriver`** — должен совпадать с драйвером cgroups у Container Runtime (обычно `systemd`). Несовпадение приводит к сбоям запуска подов и ошибкам в логах Kubelet.
*   **`failSwapOn`** (по умолчанию `true`) — Kubelet отказывается запускаться на узле с включённым swap. Поддержка swap у подов требует `failSwapOn: false`, активного feature gate `NodeSwap` (Alpha с 1.22, Beta с 1.28, GA с 1.34) и явного поведения `memorySwap.swapBehavior` (`NoSwap` по умолчанию либо `LimitedSwap` для выделения swap рабочим нагрузкам; опция `UnlimitedSwap` удалена). Swap для подов работает только на cgroup v2 и доступен лишь подам QoS-класса `Burstable` (не высокоприоритетным).

Любой параметр из KubeletConfiguration можно вывести для справки или отладить через стандартные средства:

```bash
kubelet --help | grep -A2 maxPods                  # описание параметра в бинарнике
cat /var/lib/kubelet/config.yaml                   # фактически применённый файл
```

### Статические поды (Static Pods)

**Статические поды** — это поды, которыми Kubelet управляет напрямую, без участия API-сервера. Они являются полностью **независимыми от плоскости управления (Control Plane)**, что делает их идеальными для начальной загрузки кластера и критического обслуживания.

**Основные характеристики:**
*   **Локальное управление:** Kubelet самостоятельно считывает файлы конфигурации из локальной файловой системы, создает поды и автоматически перезапускает их в случае сбоя.
*   **Местоположение конфигурации:** Путь определяется параметром `staticPodPath` (обычно `/etc/kubernetes/manifests`) в конфигурационном файле kubelet или через аргументы командной строки процесса.
*   **Именование:** Статические поды идентифицируются по суффиксу с именем узла (например, `kube-apiserver-my-node-name`). Это явный признак того, что под управляется напрямую kubelet на конкретном узле.
*   **Применение:** Используются для запуска критических компонентов Control Plane (API Server, Scheduler, etcd). Это гарантирует их работоспособность даже при возникновении проблем в плоскости управления кластера.
*   **Зеркальные поды (Mirror Pods):** Kubelet создает «зеркальную» копию пода в API-сервере для отображения статуса в `kubectl`.
*   **Процедура удаления:** Требует ручного вмешательства на уровне ОС. Чтобы удалить статический под, необходимо физически удалить его файл манифеста из директории статических подов на конкретном узле:
    ```bash
    rm /etc/kubernetes/manifests/<POD_DEFINITION_FILE>
    ```
    Kubelet обнаружит отсутствие файла и остановит контейнеры пода. Попытки удаления через `kubectl delete pod` будут проигнорированы — API-сервер удалит зеркальный под, но Kubelet немедленно его воссоздаст, пока файл манифеста существует.

**Ограничение:** Статические поды не могут использовать Secret или ConfigMap из API, так как работают автономно.

### Graceful Node Shutdown

Механизм корректного завершения работы узла (выключение, перезагрузка). Kubelet отслеживает сигналы от `systemd-logind` (ACPI-события, питание) и пытается завершить работу подов с соблюдением `terminationGracePeriodSeconds`.

*   **Настройка:** Требует настройки параметров `shutdownGracePeriod` (общее время на выключение) и `shutdownGracePeriodCriticalPods` (время для критических подов) в `KubeletConfiguration`.
*   **Приоритетность:** При выключении сначала завершаются обычные поды, затем — критические компоненты.
*   **Дифференциация по PriorityClass:** параметр `shutdownGracePeriodByPodPriority` позволяет задать разное время на завершение для подов с разным приоритетом (список пар `priority` / `shutdownGracePeriodSeconds`, обрабатывается по диапазонам значений priority). Это полезно, когда критическим DaemonSet-подам нужно меньше времени, чем обычным рабочим нагрузкам.
*   **Ограничения:** Механизм работает только при корректной настройке systemd (события `PrepareForShutdown`) и не заменяет `drain` при плановом обслуживании. Для плановых работ используйте `kubectl drain`, чтобы перераспределить поды заранее (см. [Обслуживание узлов: Cordon и Drain](../Operations/node_maintenance.md)).

### In-place Pod Resize

Начиная с Kubernetes 1.27 (Alpha/Beta), Kubelet поддерживает изменение ресурсов (CPU, RAM) контейнера без его перезапуска. Kubelet обновляет параметры `cgroups` на лету, если Container Runtime поддерживает эту операцию.

Подробный разбор механизма, ограничений, влияния на QoS-классы и практические сценарии см. в [отдельном руководстве](../Autoscaling/in_place_pod_resize.md).

### Отладка через Kubelet API

Многие команды `kubectl` выполняются через проксирование запросов к Kubelet API (порт 10250):
*   `kubectl logs` — чтение файлов логов контейнера на узле.
*   `kubectl exec` — открытие потока gRPC для выполнения команд внутри контейнера.
*   `kubectl top node` — получение метрик ресурсов.
*   `kubectl port-forward` — туннелирование трафика к поду через Kubelet.

Полный перечень эндпоинтов Kubelet API:

*   `/pods` — список подов, известных Kubelet на узле (включая статические и зеркальные).
*   `/metrics` и `/metrics/cadvisor` — метрики самого Kubelet и cAdvisor (используются Prometheus-сервисом discovery).
*   `/healthz` — проверка живости Kubelet.
*   `/stats/...` — статистика использования ресурсов по контейнерам (источник для `kubectl top pod`).
*   `/run` и `/exec` — выполнение команд в контейнерах.
*   `/logs/...` — доступ к логам узла и контейнеров через веб-интерфейс. Включается параметром `enableSystemLogHandler` (`/logs`), а query-режим выбора логов по фильтрам — `enableSystemLogQuery` (функция Node Log Query стала стабильной в v1.36). Оба параметра считаются security-sensitive: их оставляют отключёнными в production и включают только на время отладки.

Проверить доступность Kubelet API напрямую с узла (для отладки):

```bash
curl -ks --cacert /var/lib/kubelet/pki/kubelet-client-current.pem \
  https://127.0.0.1:10250/pods | jq '.items | length'
# → количество подов, известных Kubelet изнутри
```

Для отладки самого Kubelet можно повысить уровень логирования через флаг `--v=N` (например, `--v=4` для детального вывода Sync Loop). Уровень задаётся в unit-файле службы (например, добавив `--v=4` в `KUBELET_EXTRA_ARGS`), после чего требуется перезапуск службы.
