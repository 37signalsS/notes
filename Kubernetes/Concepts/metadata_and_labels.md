# Метаданные, метки и аннотации в Kubernetes

## Определение

В Kubernetes каждый объект (Pod, Service, ConfigMap) содержит поле **`metadata`**, которое используется для его идентификации, организации и управления жизненным циклом. Основными инструментами структурирования и обогащения данных являются метки и аннотации.

*   **Метаданные (Metadata)** — системные данные, описывающие объект (имя, UID, версия ресурса).
*   **Метки (Labels)** — пары «ключ-значение», используемые для **идентификации** и группировки объектов. Метки индексируются API-сервером и используются селекторами.
*   **Аннотации (Annotations)** — пары «ключ-значение» для хранения **дополнительных данных**, не предназначенных для идентификации. Они не индексируются и не используются для поиска.

---

## Поля метаданных (Metadata Fields)

Помимо пользовательских меток и аннотаций, поле `metadata` содержит критически важные системные поля (заполняются API-сервером):

*   **`name`**: Уникальное имя объекта в рамках одного **Namespace**.
*   **`namespace`**: Логическое пространство имен. Если не указано, используется `default`.
*   **`uid`**: Глобально уникальный идентификатор (UUID), генерируемый API-сервером при создании.
*   **`resourceVersion`**: Используется для оптимистичной блокировки при параллельных изменениях.
*   **`generation`**: Номер версии спецификации объекта (`spec`). Увеличивается при каждом изменении.
*   **`ownerReferences`**: Список объектов-владельцев (например, Deployment владеет ReplicaSet). Используется механизмом Garbage Collection для каскадного удаления.
*   **`finalizers`**: Список блокировок, препятствующих удалению объекта до выполнения внешних очисток (см. **[Механизм Finalizers](./kubernetes_crd.md#финализаторы-finalizers)**).
*   **`managedFields`**: Метаданные о том, какой компонент (например, `kubectl` или `helm`) управляет конкретными полями объекта (механизм Server-Side Apply).

## Метки (Labels) и Селекторы

Метки позволяют организовывать объекты в наборы (группировать), значимые для пользователей, без изменения структуры API.

### Синтаксис ключей и лимиты
*   **Префикс (опционально)**: DNS-поддомен (до 253 символов). Рекомендуется использовать для разделения ответственности (например, `company.com/env`).
*   **Имя**: Обязательно (до 63 символов). Должно начинаться и заканчиваться буквой или цифрой, может содержать `-`, `_`, `.`.
*   **Значение**: До 63 символов (может быть пустым).

**Пример:** `app.kubernetes.io/name: "nginx"`.

### Типы селекторов (Label Selectors)

Селекторы позволяют API-серверу быстро находить объекты по их меткам.

1.  **На основе равенства (Equality-based)**:
    Используется в основном в старых ресурсах (например, Service `spec.selector`).
    *   `env = production`
    *   `tier != frontend`

2.  **На основе множеств (Set-based)**:
    Современный подход, используется через поле `matchExpressions` в `Deployment`, `Job`, `DaemonSet`.
    *   `env in (prod, staging)`
    *   `tier notin (backup)`
    *   `partition` (выбор объектов, у которых просто *есть* такой ключ).
    *   `!partition` (ключ отсутствует).

## Рекомендованные метки (Well-known Labels)

Kubernetes стандартизирует набор меток для обеспечения совместимости между инструментами (Helm, ArgoCD, Kustomize).

| Ключ | Описание | Пример |
| :--- | :--- | :--- |
| `app.kubernetes.io/name` | Название приложения | `mysql` |
| `app.kubernetes.io/instance` | Уникальное имя экземпляра | `mysql-abcxzy` |
| `app.kubernetes.io/version` | Текущая версия (SemVer) | `v1.4.2` |
| `app.kubernetes.io/component` | Роль компонента | `database`, `frontend` |
| `app.kubernetes.io/part-of` | Родительская система | `wordpress` |
| `app.kubernetes.io/managed-by` | Инструмент деплоя | `helm`, `argocd` |

### Топологические метки
Эти метки автоматически проставляются компонентом Kubelet или Cloud Controller Manager:
*   `topology.kubernetes.io/zone`: Зона доступности (например, `eu-central-1a`).
*   `topology.kubernetes.io/region`: Регион.
*   `kubernetes.io/hostname`: Имя узла.
*   `kubernetes.io/os` / `kubernetes.io/arch`: ОС и архитектура (например, `linux`, `amd64`).

## Аннотации (Annotations)

Используются для данных, которые не подходят для селекторов, но важны для контроллеров, дашбордов или внешних инструментов интеграции.

**Типовые сценарии использования:**
*   **Конфигурация Ingress**: Управление поведением NGINX (`nginx.ingress.kubernetes.io/rewrite-target: /`).
*   **Секреты и Vault**: Управление внедрением секретов (`vault.hashicorp.com/agent-inject: "true"`).
*   **Service Mesh**: Автоматическое внедрение прокси (`sidecar.istio.io/inject: "true"`).
*   **Отслеживание изменений**: `kubernetes.io/change-cause`: "Update to v2" (сохраняется в истории ревизий Deployment).
*   **Мониторинг**: `prometheus.io/scrape: "true"` (для автообнаружения).

## Практические сценарии

### 1. Работа с метками через kubectl

```bash
# Показать поды с их метками
kubectl get pods --show-labels

# Поиск по селектору на основе множеств (Set-based)
kubectl get pods -l "env in (production, staging),tier=frontend"

# Добавить метку существующему узлу
kubectl label nodes worker-1 disktype=ssd

# Удалить метку (минус после ключа)
kubectl label nodes worker-1 disktype-

# Перезапись существующей метки
kubectl label pods my-pod env=prod --overwrite
```

### 2. Использование matchExpressions в Deployment

```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  selector:
    matchExpressions:
      - {key: tier, operator: In, values: [frontend, api]}
      - {key: env, operator: NotIn, values: [dev]}
```

### 3. Фиксация причины изменения (Change Cause)

Аннотации полезны для ведения аудита ручных изменений:

```bash
kubectl annotate deployment/my-app kubernetes.io/change-cause="Обновление образа до v1.2.3"
# Результат будет виден в `kubectl rollout history deployment/my-app`
```

## Дополнительная информация

### Рекомендации (Best Practices)
1.  **Избегайте «голых» ключей**: Не используйте `env: prod`, используйте `my-company.com/env: prod`. Это предотвращает конфликты с чартами сторонних поставщиков и системными контроллерами.
2.  **Валидация (Policy-as-Code)**: Используйте инструменты типа **Kyverno** или **OPA Gatekeeper** для обязательного требования меток (`owner`, `cost-center`) при создании ресурсов.
3.  **Лимиты размера**: Суммарный объем метаданных объекта (Labels + Annotations) ограничен **256KB** (лимит etcd). Не храните в аннотациях огромные конфигурационные файлы; используйте для этого `ConfigMap`.
4.  **Селекторы неизменны**: В ресурсах типа `Deployment` поле `spec.selector` является **неизменяемым** после создания. Изменение меток в `template.metadata.labels` без обновления селектора (что невозможно) приведет к ошибке или потере управления подами.
