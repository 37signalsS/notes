# Контроллеры допуска (Admission Controllers)

## Определения

**Контроллер допуска (Admission Controller)** — это специализированный компонент API-сервера Kubernetes, который перехватывает запросы к кластеру после успешной аутентификации и авторизации, но до того, как объект будет сохранен в `etcd`.

**Мутирующий контроллер (Mutating Admission Controller)** — изменяет объект запроса до его валидации (например, подставляет значения ресурсов по умолчанию или добавляет sidecar-контейнеры).

**Валидирующий контроллер (Validating Admission Controller)** — проверяет запрос на соответствие политикам и правилам безопасности. Может отклонить запрос (например, если образ не из доверенного реестра).

**Admission Webhook** — механизм расширения Kubernetes, позволяющий вызывать внешние HTTP-сервисы (Webhook) для выполнения логики мутации или валидации.

## Основные концепции

### Фазы выполнения

Процесс обработки запроса API-сервером состоит из двух фаз Admission Control:

1.  **Фаза мутации (Mutating phase):** Выполняются встроенные и внешние мутирующие контроллеры. Порядок выполнения важен, так как один контроллер может изменить поля, на которые опирается другой.
2.  **Фаза валидации (Validating phase):** Выполняются встроенные и внешние валидирующие контроллеры. Эти контроллеры запускаются параллельно и не могут изменять объект, только разрешить или отклонить его.

*Если любой из контроллеров в любой фазе отклоняет запрос, вся операция немедленно завершается ошибкой.*

### Зачем нужны Admission Controllers?

1.  **Безопасность:** Запрет запуска контейнеров от `root`, требование подписей образов, ограничение доступа к `hostPath`.
2.  **Стандартизация и управление (Governance):** Автоматическое добавление меток (labels), аннотаций или принудительное назначение `ResourceQuota`.
3.  **Автоматизация:** Внедрение Service Mesh sidecars (Istio/Linkerd) или внедрение секретов из внешних хранилищ (Vault).
4.  **Управление ресурсами:** Автоматическая коррекция лимитов через **[VPA Admission Controller](../Autoscaling/vpa_detailed.md)**.

## Популярные встроенные контроллеры

| Контроллер | Тип | Назначение |
| :--- | :--- | :--- |
| **`NamespaceLifecycle`** | Validating | Запрещает создание ресурсов в удаляемых неймспейсах. |
| **`LimitRanger`** | Mutating/Validating | Применяет ограничения ресурсов, заданные в `LimitRange`. |
| **`ServiceAccount`** | Mutating | Автоматически внедряет `ServiceAccount` в поды. |
| **`AlwaysPullImages`** | Mutating | Принудительно устанавливает `imagePullPolicy: Always`. |
| **`PodSecurity`** | Validating | Реализует стандарты безопасности подов (**PSA**). |
| **`NodeRestriction`** | Validating | Ограничивает права `kubelet` только своими собственными ресурсами. |

## Расширение через Webhooks

Kubernetes позволяет создавать собственные контроллеры через два типа ресурсов:
*   `MutatingWebhookConfiguration`
*   `ValidatingWebhookConfiguration`

Популярные движки политик, работающие через вебхуки:
*   **[Kyverno](../../Security/kyverno/concepts.md)** — написание политик на YAML.
*   **OPA Gatekeeper** — использование языка Rego.

## Практические сценарии

### 1. Включение контроллеров
В управляемых кластерах (EKS, GKE) список контроллеров управляется провайдером. В `kubeadm` список настраивается через флаг API-сервера:
```bash
--enable-admission-plugins=NodeRestriction,NamespaceLifecycle,LimitRanger,...
```

### 2. Отладка вебхуков
Если создание ресурсов "зависает" или возвращает ошибки таймаута, проблема часто в недоступности Admission Webhook.
```bash
# Поиск конфигураций вебхуков
kubectl get mutatingwebhookconfigurations
kubectl get validatingwebhookconfigurations

# Проверка логов контроллера (например, Kyverno)
kubectl logs -n kyverno -l app.kubernetes.io/name=kyverno
```

## Дополнительная информация

### Риски и ограничения
*   **Производительность:** Каждый запрос к API-серверу должен пройти через все контроллеры. Медленные вебхуки увеличивают Latency управления кластером.
*   **Блокировка кластера:** Если критический вебхук (например, валидирующий все поды) недоступен и настроен с `failurePolicy: Fail`, создание любых подов в кластере будет остановлено.
