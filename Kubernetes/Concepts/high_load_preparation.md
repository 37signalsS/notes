# Подготовка к высоким нагрузкам в Kubernetes

## Определения

**Высокая нагрузка (High Load)** в Kubernetes — состояние, при котором потребление ресурсов (CPU, RAM, Network, Disk IOPS) сервисами или платформой приближается к пределу их текущей инфраструктурной мощности.

Ключевым фактором является не только абсолютное число **RPS (Requests Per Second)**, но и скорость изменения нагрузки, готовность системы к резким пикам (**Spikes**) и время восстановления. Нагрузка может быть плановой (маркетинговые акции) или внезапной (**DDoS**).

## Признаки высокой нагрузки

1.  **Увеличение времени отклика (Latency)**: Сервисы медленнее отвечают на запросы, появляется троттлинг **CPU**, растет число таймаутов на стороне клиента.
2.  **Рост числа ошибок**: Приложения возвращают HTTP-ошибки серии `5xx`, возникают каскадные сбои в зависимых микросервисах из-за накопления очередей.
3.  **Ошибки нехватки памяти (OOMKilled)**: Поды завершаются с ошибкой **OOM (Out Of Memory)** из-за превышения лимитов или утечек памяти под нагрузкой.
4.  **Рост очередей**: В асинхронных системах (Kafka, RabbitMQ) сообщения накапливаются быстрее, чем обрабатываются потребителями (**Consumer Lag**).
5.  **Увеличение времени развертывания**: Обновление **Deployment** с большим количеством реплик замедляется, так как планировщику труднее найти свободные ресурсы в плотно упакованном кластере.

## Стратегии масштабирования

*   **Вертикальное масштабирование (Vertical Scaling)**: Увеличение ресурсов (CPU, память) для существующих подов. Реализуется вручную или через **VPA (Vertical Pod Autoscaler)**. Эффективно для приложений, плохо поддающихся горизонтальному дроблению.
*   **Горизонтальное масштабирование (Horizontal Scaling)**: Увеличение количества реплик подов. Реализуется через **HPA (Horizontal Pod Autoscaler)**. Требует строго **Stateless**-архитектуры приложений.
*   **Функциональное масштабирование**: Архитектурное разделение системы на независимо масштабируемые блоки (микросервисы, отдельные группы узлов для разных типов задач — например, выделенные узлы для ML или DB).
*   **Параметрическое масштабирование**: Оптимизация параметров конфигурации без изменения ресурсов (увеличение количества воркеров Nginx/PHP-FPM, настройка пулов соединений с базами данных, тюнинг **GC (Garbage Collector)**).

## Инфраструктурный тюнинг и оптимизация

Для High Load систем стандартные настройки Linux и Kubernetes часто становятся узким местом.

### Системный тюнинг (sysctl)
Использование `securityContext` в подах для снятия ограничений сетевого стека:
```yaml
spec:
  securityContext:
    sysctls:
    - name: net.core.somaxconn
      value: "8192" # Размер очереди прослушивания сокетов
    - name: net.ipv4.ip_local_port_range
      value: "1024 65535" # Расширение диапазона портов для исходящих соединений
    - name: net.ipv4.tcp_max_syn_backlog
      value: "4096" # Защита от SYN-флуда и переполнения очереди подключений
```

### Настройка узлов (Node Level)
*   **TCP BBR**: Включение алгоритма контроля перегрузки сети BBR на уровне ядра узлов для снижения задержек на "шумных" сетях.
*   **Ulimits**: Настройка `nofile` (максимальное количество открытых файлов) на уровне контейнерного рантайма (containerd/docker) до значений 1,000,000+.
*   **CPU Manager**: Использование политики `static` в kubelet для предоставления критическим подам эксклюзивных ядер CPU, что минимизирует задержки от переключения контекста.

## Управление соединениями и ресурсами

### Connection Pooling
Создание TCP/TLS соединений — дорогая операция.
*   **DB Pooling**: Используйте **PgBouncer** (для Postgres) или **ProxySQL** (для MySQL). Важно настраивать пулинг как можно ближе к базе или в виде выделенного сервиса, чтобы тысячи подов приложения не "убили" БД количеством открытых соединений.
*   **Keep-Alive**: Настройка агрессивных таймаутов Keep-Alive на Ingress и в приложениях для повторного использования соединений.

### Оптимизация размещения
*   **Pod Affinity**: Размещение часто общающихся сервисов на одних итых же узлах (`topologyKey: kubernetes.io/hostname`) или в одной зоне для минимизации сетевого "хопа".
*   **Taints и Tolerations**: Выделение отдельных групп узлов (**NodePool**) под критические нагрузки, чтобы избежать влияния "шумных соседей" (noisy neighbors).

## Паттерны отказоустойчивости (Resilience)

1.  **Circuit Breaker (Прерыватель)**: Если зависимый сервис начинает тормозить или выдавать ошибки, оператор (или Service Mesh) должен временно прекратить отправку запросов к нему, чтобы основной сервис не "захлебнулся" в ожидании. Реализуется через **Istio** (`DestinationRule`).
2.  **Load Shedding (Сброс нагрузки)**: При достижении критических порогов Latency Ingress-контроллер должен начать отдавать `503 Service Unavailable` или кэшированную заглушку для части трафика, сохраняя ресурсы для обработки остального.
3.  **Graceful Shutdown**: Настройка `terminationGracePeriodSeconds` и использование `preStop` хуков. Это критично, чтобы под успел дообработать текущие запросы после получения сигнала SIGTERM и выхода из балансировки.

## Практические сценарии

### Борьба с DDoS и аномальной нагрузкой
1.  **Rate Limiting**: Настройка лимитов на уровне Ingress (например, аннотации Nginx Ingress для лимитирования запросов по IP или Cookie).
2.  **WAF (Web Application Firewall)**: Использование внешних облачных решений (Cloudflare, Qrator) или встроенных модулей для фильтрации вредоносного трафика до того, как он попадет в кластер.
3.  **Масштабирование до пределов**: Установка высокого лимита `maxReplicas` в HPA, чтобы "прожевать" легитимный всплеск трафика.

### Диагностика под нагрузкой

**Проверка троттлинга CPU:**
```bash
# Просмотр текущего потребления и сравнение с requests/limits
kubectl top pods --sort-by=cpu

# Анализ метрики container_cpu_cfs_throttled_seconds_total в Prometheus
# Если значение растет — приложению не хватает CPU лимитов, даже если загрузка < 100%
```

**Проверка OOMKilled:**
```bash
# Поиск событий завершения из-за нехватки памяти
kubectl get pods -A | grep -i "OOMKilled"

# Проверка логов ядра узла на предмет работы OOM Killer
dmesg | grep -i "oom"
```

## Инструменты автоматизации

*   **HPA (Horizontal Pod Autoscaler)**: Масштабирование по CPU/RAM или кастомным метрикам.
*   **VPA (Vertical Pod Autoscaler)**: Автоматическая подстройка ресурсов для подов, которые сложно масштабировать горизонтально.
*   **KEDA**: Масштабирование на основе внешних событий (очереди Kafka, запросы в Prometheus). Поддерживает Scale-to-Zero.
*   **Karpenter / Cluster Autoscaler**: Добавление физических/виртуальных узлов в кластер при нехватке ресурсов.

## Наблюдаемость (Observability)

Для High Load систем мониторинг должен строиться по двум основным методам:

1.  **RED Метод (для Сервисов)**:
    *   **R**ate (количество запросов).
    *   **E**rrors (количество ошибок).
    *   **D**uration (длительность/latency, особенно P99).
2.  **USE Метод (для Ресурсов)**:
    *   **U**tilization (утилизация).
    *   **S**aturation (насыщение/очереди).
    *   **E**rrors (ошибки оборудования/ядра).

## Дополнительная информация

**Рекомендации:**
*   **Нагрузочное тестирование**: Проводите регулярные тесты (например, через k6 или JMeter) с нагрузкой, превышающей расчетную в 2-3 раза.
*   **Алертинг**: Настраивайте алерты на *скорость роста* очередей и *тенденцию* изменения Latency, а не только на статические пороги.
*   **PDB (Pod Disruption Budget)**: Обязательно ограничивайте количество одновременно выключаемых подов при работах в кластере.
