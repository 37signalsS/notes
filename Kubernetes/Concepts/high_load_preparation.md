# Подготовка к высоким нагрузкам в Kubernetes

## Определения

**High Load (Высокая нагрузка)** в Kubernetes — состояние, при котором нагрузка на сервисы или платформу приближается к пределу их текущей инфраструктурной или проектной мощности.

Ключевым фактором является не только абсолютное число запросов (RPS), но и скорость изменения нагрузки, готовность системы к резким пикам и восстановление после них. Нагрузка может быть плановой (часы пик, маркетинговые акции) или внезапной (DDoS-атака, вирусный эффект).

## Основные концепции

### Признаки высокой нагрузки

1. **Увеличение времени отклика (Latency):** Сервисы медленнее отвечают на запросы, появляется троттлинг CPU, растёт число таймаутов между микросервисами.

2. **Рост числа ошибок:** Приложения возвращают HTTP `5xx` (502, 503, 504), происходят обрывы соединений, возникает каскадный эффект сбоев в зависимых сервисах.

3. **Ошибки нехватки памяти (`OOMKilled`):** Поды падают с ошибкой `OOMKilled` из-за превышения `limits.memory`. Под нагрузкой могут проявляться скрытые утечки памяти.

4. **Рост очередей:** В асинхронных системах (Kafka, RabbitMQ) сообщения накапливаются быстрее, чем консьюмеры их обрабатывают.

5. **Увеличение времени развёртывания:** `Rolling Update` для `Deployment` с большим количеством реплик замедляется, время запуска приложений (прогрев кэша, инициализация) усугубляет проблему.

6. **Полный или частичный отказ системы:** При неверно настроенном автомасштабировании нагрузка упирается в лимиты (поды, коннекты к БД, воркеры).

### Стратегии масштабирования

**Вертикальное масштабирование (Vertical Scaling):** Увеличение ресурсов (`requests` и `limits` CPU/Memory) для существующих подов. Реализуется вручную или через [VPA](../Autoscaling/vpa_detailed.md). Ограничено пределами физического узла.

**Горизонтальное масштабирование (Horizontal Scaling):** Увеличение количества реплик подов. Реализуется вручную или через [HPA](../Autoscaling/HPA/index.md). Требует stateless-приложения и балансировщика нагрузки.

**Функциональное масштабирование (Functional Scaling):** Архитектурное разделение системы на независимо масштабируемые блоки: микросервисы, node pools для разных типов нагрузки, географическое распределение по зонам доступности, разделение узлов для чтения/записи (Elasticsearch).

**Параметрическое масштабирование (Parametric Scaling):** Увеличение пропускной способности через настройку параметров конфигурации без добавления ресурсов: увеличение worker'ов (Gunicorn, Nginx), настройка пула соединений с БД, включение `keep-alive`, тюнинг GC, оптимизация очередей и буферов.

## Практические сценарии

### Диагностика проблем высокой нагрузки

**Проверка троттлинга CPU:**

```bash
kubectl top pods --sort-by=cpu
kubectl describe pod <pod-name> | grep -A 5 "Limits"
```

Троттлинг возникает при превышении `limits.cpu`. Подробнее: [QoS, Requests и Limits](../Scheduling/qos_limit_and_requests.md).

**Проверка OOMKilled:**

```bash
kubectl get pods --field-selector=status.phase=Failed
kubectl describe pod <pod-name> | grep -i "oom"
```

Причины и устранение: [OOMKilled pods](../Troubleshooting/Common_Errors/oomkilled_pods.md).

**Проверка очередей:**

```bash
# Для RabbitMQ
kubectl exec -it rabbitmq-0 -- rabbitmqctl list_queues name messages consumers

# Для Kafka
kubectl exec -it kafka-cli -- kafka-consumer-groups --bootstrap-server kafka:9092 --describe
```

### Настройка автомасштабирования

Для автоматической реакции на высокую нагрузку используются:

* **HPA** — масштабирование по CPU, памяти, кастомным метрикам
* **VPA** — рекомендации или автоматическая настройка ресурсов
* **KEDA** — событийное масштабирование по очередям, расписаниям
* **Cluster Autoscaler / Karpenter** — добавление узлов при нехватке ресурсов

Обзор компонентов: [Автомасштабирование: обзор](../Autoscaling/overview_concepts.md).

### Обеспечение высокой доступности

При высоких нагрузках критична отказоустойчивость:

* **Pod Disruption Budget** — защита от массового выселения подов
* **Pod Anti-Affinity** — распределение реплик по узлам
* **Multi-zone deployment** — размещение в разных зонах доступности

Стратегии HA: [Высокая доступность в Kubernetes](../Base/high_availability.md).

## Дополнительная информация

**Рекомендации по подготовке:**

* **Нагрузочное тестирование:** Регулярно проводите тесты на staging с нагрузкой, превышающей production в 1.5-2 раза.
* **Capacity planning:** Рассчитывайте необходимую ёмкость на основе пиковых метрик с запасом 30-50%.
* **Runbook:** Документируйте процедуры реагирования на инциденты высокой нагрузки.
* **Алертинг:** Настройте уведомления по метрикам latency, error rate, saturation (USE-метод).

**Оптимизация перед масштабированием:**

* Профилирование приложения (pprof, async-profiler)
* Оптимизация запросов к БД (индексы, кэширование)
* Настройка connection pooling
* Включение compression для HTTP/gRPC
