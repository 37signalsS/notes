# Подготовка к высоким нагрузкам в Kubernetes

## Определения

**Высокая нагрузка (High Load)** в Kubernetes — состояние, при котором потребление ресурсов сервисами или платформой приближается к пределу их текущей инфраструктурной мощности.

Ключевым фактором является не только абсолютное число **RPS (Requests Per Second — запросов в секунду)**, но и скорость изменения нагрузки, готовность системы к резким пикам и время восстановления. Нагрузка может быть плановой (маркетинговые акции) или внезапной (**DDoS (Distributed Denial of Service — распределённая атака типа «отказ в обслуживании»)**).

## Основные концепции

### Признаки высокой нагрузки

1. **Увеличение времени отклика (Latency):** сервисы медленнее отвечают на запросы, появляется троттлинг **CPU (Central Processing Unit — центральный процессор)**, растёт число таймаутов.
2. **Рост числа ошибок:** приложения возвращают **HTTP (HyperText Transfer Protocol)** ошибки серии `5xx`, возникают каскадные сбои в зависимых сервисах.
3. **Ошибки нехватки памяти (OOMKilled):** поды завершаются с ошибкой **OOM (Out Of Memory)** из-за превышения лимитов.
4. **Рост очередей:** в асинхронных системах (Kafka, RabbitMQ) сообщения накапливаются быстрее, чем обрабатываются.
5. **Увеличение времени развёртывания:** обновление **Deployment** с большим количеством реплик замедляется.

### Стратегии масштабирования

* **Вертикальное масштабирование (Vertical Scaling):** увеличение ресурсов (CPU, память) для существующих подов. Реализуется вручную или через **VPA (Vertical Pod Autoscaler)**.
* **Горизонтальное масштабирование (Horizontal Scaling):** увеличение количества реплик подов. Реализуется через **HPA (Horizontal Pod Autoscaler)**. Требует stateless-архитектуры.
* **Функциональное масштабирование:** архитектурное разделение системы на независимо масштабируемые блоки (микросервисы, отдельные группы узлов).
* **Параметрическое масштабирование:** оптимизация параметров конфигурации (увеличение воркеров Nginx, настройка пулов соединений с базами данных, тюнинг **GC (Garbage Collector — сборщик мусора)**).

## Практические сценарии

### Диагностика проблем

**Проверка троттлинга CPU:**

```bash
# Просмотр текущего потребления
kubectl top pods --sort-by=cpu

# Анализ лимитов пода
kubectl describe pod <pod-name> | grep -A 5 "Limits"
```

Подробнее о диагностике: [QoS, Requests и Limits](../Scheduling/qos_limit_and_requests.md).

**Проверка OOMKilled:**

```bash
# Поиск упавших подов
kubectl get pods --field-selector=status.phase=Failed

# Проверка причины завершения
kubectl describe pod <pod-name> | grep -i "oom"
```

Методы устранения: [Ошибки OOMKilled](../Troubleshooting/Common_Errors/oomkilled_pods.md).

### Инструменты автоматизации

Для автоматической реакции на нагрузку используются:
* **HPA** — масштабирование по метрикам ресурсов.
* **VPA** — автоматическая настройка лимитов контейнеров.
* **KEDA (Kubernetes Event-driven Autoscaling)** — масштабирование на основе внешних событий (очереди, расписания).
* **Cluster Autoscaler** — добавление узлов в кластер при нехватке ресурсов.

Обзор инструментов: [Автомасштабирование в Kubernetes](../Autoscaling/overview_concepts.md).

## Дополнительная информация

**Рекомендации по подготовке:**
* **Нагрузочное тестирование:** проводите регулярные тесты с нагрузкой, превышающей продуктивную в 1.5–2 раза.
* **Алертинг:** настройте уведомления по метрикам задержек, ошибок и насыщения (**USE-метод: Utilization, Saturation, and Errors**).
* **Оптимизация:** перед масштабированием выполняйте профилирование приложений и оптимизацию запросов к базам данных.
