# Фоновое сканирование в Kyverno

## Определения

**Фоновое сканирование (Background Scan)** — процесс периодической или триггерной проверки ресурсов кластера на соответствие политикам безопасности. В отличие от Admission-контроля, работающего в синхронном режиме при создании ресурса, фоновое сканирование анализирует уже существующие объекты асинхронно.

**Update Request (UR)** — системный ресурс Kyverno, выступающий посредником для выполнения фоновых задач. Каждый раз, когда политика требует изменения или генерации существующего ресурса, создается UR, который отслеживает прогресс и результат операции.

## Основные концепции

### Архитектура и разделение обязанностей

В современной архитектуре Kyverno (v1.12+) функции фоновой обработки строго разделены между двумя контроллерами:

| Контроллер | Функциональная роль | Основные задачи |
| :--- | :--- | :--- |
| **Reports Controller** | Аудит и наблюдаемость | Сканирование ресурсов для формирования `PolicyReports`. Обрабатывает правила `validate` и `verifyImages`. |
| **Background Controller** | Активное управление | Выполнение правил `generate` и `mutateExisting`. Управляет жизненным циклом `UpdateRequests`. |

### Жизненный цикл фоновой операции (UR)

Процесс мутации существующего ресурса проходит следующие этапы:
1.  **Триггер**: Создание/обновление политики или плановое сканирование.
2.  **Создание UR**: `background-controller` создает объект `UpdateRequest` в пространстве имен `kyverno`.
3.  **Выполнение**: Контроллер считывает UR и применяет изменения к целевому ресурсу.
4.  **Очистка**: После успешного выполнения UR автоматически удаляется (начиная с v1.14+), чтобы не перегружать `etcd`.

### Ключевые параметры спецификации

*   **`spec.background`**: (по умолчанию `true`) — разрешает создание отчетов о соответствии (`PolicyReport`) для существующих ресурсов.
*   **`spec.mutateExisting`**: Современный механизм (пришедший на замену `mutateExistingOnPolicyUpdate`), позволяющий точечно выбирать целевые ресурсы для мутации через селекторы.

> **Важно**: Фоновое сканирование в режиме `Enforce` **не блокирует** существующие ресурсы. Оно лишь фиксирует нарушение в отчете. Реальное изменение объекта происходит только при использовании правил `mutateExisting`.

## Практические сценарии

### 1. Оптимизация интервала сканирования

Для больших кластеров (>5000 объектов) рекомендуется увеличивать интервал сканирования для предотвращения пиковых нагрузок на API-сервер.

**Настройка через Helm `values.yaml`**:
```yaml
backgroundController:
  envVars:
    - name: BACKGROUND_SCAN_INTERVAL
      value: "12h" # Полное сканирование раз в 12 часов
reportsController:
  envVars:
    - name: BACKGROUND_SCAN_INTERVAL
      value: "12h"
```

### 2. Мутация существующих ресурсов (mutate.targets)

Пример политики, которая асинхронно добавляет метку безопасности во все существующие Namespace, где она отсутствует.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: enforce-security-label
spec:
  mutateExistingOnPolicyUpdate: false # Рекомендуется false при использовании targets
  rules:
    - name: add-label-to-namespaces
      match:
        any:
          - resources:
              kinds: [Namespace]
      mutate:
        targets:
          - apiVersion: v1
            kind: Namespace
            selector:
              matchLabels:
                security-audit: null # Обрабатывать только те, где метки нет
        patchStrategicMerge:
          metadata:
            labels:
              security-audit: "enabled"
```

### 3. Исключение системных областей (Noise Reduction)

Для снижения нагрузки на `reports-controller` и уменьшения объема отчетов следует исключать инфраструктурные Namespace.

```yaml
spec:
  background: true
  rules:
    - name: validate-resource-limits
      match:
        resources:
          kinds: [Pod]
      exclude:
        resources:
          namespaces:
            - kube-system
            - kyverno
            - istio-system
```

## Дополнительная информация

### Производительность и параллелизм

Если обработка фоновых задач замедляется, необходимо увеличить количество рабочих потоков (workers) в аргументах контроллера:
- `--backgroundScanWorkers`: количество воркеров для формирования отчетов (по умолчанию 10).
- `--updateRequestWorkers`: количество воркеров для обработки мутаций/генераций (по умолчанию 10).

### Диагностика фоновых процессов

Основным инструментом диагностики является просмотр ресурсов `UpdateRequest`:

```bash
# Проверка наличия зависших задач
kubectl get updaterequests -n kyverno

# Получение детальной ошибки выполнения
kubectl describe updaterequest <ur-name> -n kyverno
```

Типовые причины сбоев фоновых операций:
1.  **RBAC**: У `background-controller` нет прав на `patch` целевого ресурса ([см. additional.md](./additional.md)).
2.  **Конфликты**: Ресурс одновременно изменяется другим контроллером (например, Argo CD).
