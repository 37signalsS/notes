# Сценарии безопасности Kyverno

## Определения

**Сценарии безопасности** — практические примеры использования Kyverno для автоматизации контроля безопасности, обеспечения соответствия отраслевым стандартам и внедрения лучших практик (Best Practices) в кластере Kubernetes.

Реализация сценариев базируется на механизмах **валидации** (проверки) и **мутации** (автоматического изменения) ресурсов ([подробнее о типах правил](../rules.md)).

---

## Основные концепции

### Категории сценариев безопасности

| Категория | Цель | Механизм Kyverno |
|-----------|------|------------------|
| **Предотвращение (Prevention)** | Блокировка небезопасных конфигураций на входе. | `validate` (валидация) с режимом `Enforce`. |
| **Исправление (Remediation)** | Автоматическое приведение ресурсов к безопасному состоянию. | `mutate` (мутация). |
| **Аудит (Audit)** | Выявление нарушений в уже запущенных ресурсах. | `validate` с режимом `Audit` + [Background Scans](../background.md). |
| **Обеспечение (Provisioning)** | Автоматическое создание ресурсов безопасности (например, сетевых политик). | `generate` (генерация). |

## Практические сценарии

### 1. Контроль безопасности в реальном времени (Admission Control)

**Проблема**: Необходимо гарантировать, что ни один контейнер не будет запущен с правами суперпользователя (root), так как это увеличивает поверхность атаки.

**Решение**: Использование контроллера допуска (Admission Controller) Kyverno для блокировки таких запросов.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-security-context
spec:
  # Режим Enforce блокирует создание ресурса при нарушении
  validationFailureAction: Enforce
  rules:
    - name: require-run-as-non-root
      match:
        resources:
          kinds:
            - Pod
      validate:
        message: "Контейнер должен запускаться от имени non-root пользователя"
        pattern:
          spec:
            securityContext:
              runAsNonRoot: true
```

> **Сравнение инструментов**: [kubesec](../../kubesec.md) выполняет статический анализ YAML-файлов до деплоя; Kyverno контролирует процесс деплоя в реальном времени; [Falco](../../../../Security/Tools/falco.md) отслеживает подозрительную активность во время выполнения (runtime).

### 3. Автоматическое внедрение лучших практик (Mutation)

**Проблема**: Команды разработки часто забывают настраивать параметры безопасности в манифестах, что приводит к уязвимостям или отклонению деплоя политиками валидации.

**Решение**: Мутация ресурсов для автоматической вставки корректных настроек безопасности "на лету".

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: add-security-context
spec:
  rules:
    - name: add-default-security-context
      match:
        resources:
          kinds:
            - Pod
      mutate:
        patchStrategicMerge:
          spec:
            # Автоматическое добавление настроек, если они отсутствуют
            securityContext:
              runAsNonRoot: true
              runAsUser: 1000
              fsGroup: 1000
```

*Полный пример манифеста мутации доступен в [Библиотеке политик](../policies/practical_scenarios.md#мутация-добавление-securitycontext).*

## Дополнительная информация

### Рекомендации по стратегии безопасности

1. **Режим обучения**: Всегда начинайте внедрение новых политик в режиме `validationFailureAction: Audit`. Это позволит собрать статистику нарушений в [Policy Reports](../reports.md), не прерывая работу приложений.
2. **Фоновая проверка**: Включайте параметр `background: true` для анализа уже запущенных ресурсов в кластере ([подробнее](./../background.md)).
3. **Исключения**: Настраивайте секцию `exclude` для системных пространств имен (`kube-system`, `kyverno`), чтобы избежать блокировки критических компонентов кластера.
4. **Визуализация**: Используйте [Policy Reporter](../reporter.md) для получения наглядных отчетов о состоянии безопасности (Compliance Dashboard).
