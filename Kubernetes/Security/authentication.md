# Аутентификация в Kubernetes

## Определения

**Аутентификация** в Kubernetes — это процесс проверки личности пользователя или компонента, который пытается выполнить действие в кластере. API-сервер должен идентифицировать источник каждого запроса, прежде чем передать его на стадию авторизации.

## Основные способы аутентификации

Kubernetes предлагает несколько встроенных и внешних методов аутентификации, каждый из которых подходит для определенных сценариев.

### 1. X.509 Сертификаты
- **Описание:** Основной и наиболее распространенный способ аутентификации для пользователей и системных компонентов (например, kubelet).
- **Принцип работы:** Клиент предоставляет сертификат, подписанный доверенным центром сертификации (CA) кластера. `Common Name` (CN) в сертификате используется как имя пользователя, а `Organization` (O) — для определения принадлежности к группам.
- **Практический сценарий:** Администратор создает для сотрудника ключ и CSR (Certificate Signing Request), подписывает его CA кластера и передает готовый `kubeconfig`.

### 2. Токены сервисных аккаунтов (Service Account Tokens)
- **Описание:** Метод, предназначенный для аутентификации внутрикластерных процессов (подов), которым требуется доступ к API-серверу.
- **Принцип работы:** Kubernetes автоматически создает JWT-токен для каждого `ServiceAccount` и монтирует его в поды по пути `/var/run/secrets/kubernetes.io/serviceaccount/`.
- **Практический сценарий:** Приложение в поде читает токен из файла и использует его в заголовке `Authorization: Bearer <token>` для запросов к API.

### 3. OpenID Connect (OIDC)
- **Описание:** Интеграция с внешними провайдерами идентификации (IdP), такими как Google, Okta, Azure AD, Keycloak.
- **Принцип работы:** Пользователь аутентифицируется через внешнего провайдера, получает OIDC токен (ID Token) и передает его API-серверу. API-сервер проверяет подлинность токена, обратившись к IdP.
- **Практический сценарий:** Настройка единого входа (SSO) для разработчиков в корпоративной среде. API-сервер конфигурируется с параметрами `--oidc-issuer-url` и `--oidc-client-id`.

### 4. Статический файл с токенами (Static Token File)
- **Описание:** Простой, но небезопасный метод, при котором токены хранятся в CSV-файле на API-сервере.
- **Принцип работы:** API-сервер при запуске читает файл, указанный в опции `--token-auth-file`. Файл содержит записи вида `token,user,uid,"group1,group2"`.
- **Предостережение:** **Не рекомендуется использовать в производственной среде** из-за сложностей с управлением и ротацией токенов. Подходит только для разработки и тестирования.

### 5. Bootstrap Tokens
- **Описание:** Специализированные временные токены для безопасного добавления новых узлов в кластер.
- **Принцип работы:** Токены создаются динамически и хранятся в виде `Secrets` в пространстве имен `kube-system`. Используются в процессе начальной загрузки (`bootstrap`) для аутентификации kubelet перед тем, как он получит свой постоянный X.509 сертификат.
- **Практический сценарий:** `kubeadm join` использует bootstrap-токен для присоединения рабочей ноды к кластеру.

### 6. Webhook Token Authentication
- **Описание:** Гибкий механизм для интеграции с кастомными или внешними системами аутентификации.
- **Принцип работы:** API-сервер отправляет токен из запроса на внешний веб-сервис (webhook). Этот сервис проверяет токен и возвращает информацию о пользователе в ответ.
- **Практический сценарий:** Реализация сложной логики аутентификации, которая не покрывается стандартными методами, например, интеграция с проприетарной системой управления пользователями.

## Рекомендации по безопасности
- **Отключайте анонимную аутентификацию:** Запускайте API-сервер с флагом `--anonymous-auth=false`, чтобы все запросы требовали проверки личности.
- **Не используйте `default` Service Account:** Создавайте выделенные сервисные аккаунты для каждого приложения с минимально необходимыми правами (RBAC).
- **Регулярно ротируйте учетные данные:** Настройте процессы для периодической ротации сертификатов X.509 и токенов, чтобы минимизировать риски в случае их компрометации.
- **Используйте OIDC для пользователей:** Для аутентификации людей (разработчиков, администраторов) предпочитайте интеграцию с централизованными IdP через OIDC. Это упрощает управление жизненным циклом пользователей (onboarding/offboarding).
