# Аутентификация в Kubernetes

## Определения

**Аутентификация** в Kubernetes — это процесс проверки личности пользователя или компонента, который пытается выполнить действие в кластере. API-сервер должен идентифицировать источник каждого запроса, прежде чем передать его на стадию [авторизации (RBAC)](./rbac/rbac_overview.md).

**Важно:** Аутентификация отвечает на вопрос «Кто вы?», авторизация — на вопрос «Что вам разрешено?». Подробнее о разграничении: [Authentication vs Authorization](../../Security/Concepts/authentication_vs_authorization.md).

## Основные концепции

### 1. X.509 Сертификаты

Принцип работы: Клиент предоставляет сертификат, подписанный доверенным центром сертификации (CA) кластера. `Common Name` (CN) в сертификате используется как имя пользователя, а `Organization` (O) — для определения принадлежности к группам.

Подробнее о PKI и сертификатах: [PKI Overview](../../Security/Concepts/pki_overview.md), [TLS и mTLS](./tls_and_mtls_in_kubernetes.md).

### 2. Токены сервисных аккаунтов (Service Account Tokens)

Принцип работы: Kubernetes автоматически создает JWT-токен для каждого `ServiceAccount` и монтирует его в поды по пути `/var/run/secrets/kubernetes.io/serviceaccount/`.

**Кастомизация токена:** Через [Projected Volume](../Base/Pod/volume_types/projected_volumes.md) можно создать токен с измененными параметрами:
- `expirationSeconds` — срок действия (по умолчанию 1 час, минимум 600 секунд)
- `audience` — аудитория токена (для доступа к внешним API)
- `path` — нестандартный путь монтирования

### 3. OpenID Connect (OIDC)

Принцип работы: Пользователь аутентифицируется через внешнего провайдера, получает OIDC токен (ID Token) и передает его API-серверу. API-сервер проверяет подлинность токена, обращаясь к IdP.

Подробнее: [OAuth2 Overview](../../Security/Concepts/oauth2_overview.md).

### 4. Статический файл с токенами (Static Token File)

Принцип работы: API-сервер при запуске читает файл, указанный в опции `--token-auth-file`. Файл содержит записи вида `token,user,uid,"group1,group2"`.
Предостережение: **Не рекомендуется использовать в производственной среде** из-за сложностей с управлением и ротацией токенов. Подходит только для разработки и тестирования.

### 5. Bootstrap Tokens

Принцип работы: Токены создаются динамически и хранятся в виде `Secrets` в пространстве имен `kube-system`. Используются в процессе начальной загрузки (`bootstrap`) для аутентификации kubelet перед тем, как он получит свой постоянный X.509 сертификат.

### 6. Webhook Token Authentication

Принцип работы: API-сервер отправляет токен из запроса на внешний веб-сервис (webhook). Этот сервис проверяет токен и возвращает информацию о пользователе в ответ.

## Практические сценарии

### 1. X.509 Сертификаты для администраторов

Администратор создает CSR (Certificate Signing Request), подписывает его CA кластера и формирует `kubeconfig` с сертификатом и ключом. Подходит для доступа к API серверу вне кластера.

### 2. Service Account Tokens для приложений

Приложение в поде использует автоматически смонтированный токен (`/var/run/secrets/kubernetes.io/serviceaccount/token`) в заголовке `Authorization: Bearer <token>` для запросов к Kubernetes API. Для кастомизации параметров токена (срок, аудитория) используется [Projected Volume](../Base/Pod/volume_types/projected_volumes.md).

### 3. OIDC для единого входа (SSO)

Разработчики аутентифицируются через корпоративный IdP (Keycloak, Dex, Google). API-сервер конфигурируется флагами `--oidc-issuer-url` и `--oidc-client-id`. Подробнее: [OAuth2 Overview](../../Security/Concepts/oauth2_overview.md).

### 4. Bootstrap Tokens для присоединения нод

`kubeadm join` использует bootstrap-токен (хранится как `Secret` в `kube-system`) для первоначальной аутентификации kubelet до получения им постоянного X.509 сертификата.

### 5. Webhook для кастомной аутентификации

API-сервер отправляет токен на внешний webhook-сервис для проверки. Применяется при интеграции с проприетарными системами управления пользователями.

### 6. Static Token File (только для разработки)

Файл с записями вида `token,user,uid,"group1,group2"`, передаваемый через `--token-auth-file`. Не рекомендуется для production из-за сложностей с ротацией.

## Дополнительная информация

### Рекомендации по безопасности

- **Отключайте анонимную аутентификацию:** Запускайте API-сервер с флагом `--anonymous-auth=false`, чтобы все запросы требовали проверки личности.
- **Не используйте `default` ServiceAccount:** Создавайте выделенные сервисные аккаунты для каждого приложения с минимально необходимыми правами ([RBAC](./rbac/rbac_overview.md)).
- **Регулярно ротируйте учетные данные:** Настройте процессы для периодической ротации сертификатов X.509 и токенов.
- **Используйте OIDC для пользователей:** Для аутентификации людей предпочитайте интеграцию с централизованными IdP через OIDC — это упрощает onboarding/offboarding.

### Сравнение методов аутентификации

| Метод | Use Case | Безопасность | Сложность |
|-------|----------|--------------|-----------|
| **X.509** | Компоненты кластера, администраторы | Высокая | Средняя |
| **Service Account** | Приложения внутри кластера | Средняя | Низкая |
| **OIDC** | Пользователи (SSO) | Высокая | Средняя |
| **Bootstrap** | Временная аутентификация kubelet | Средняя | Низкая |
| **Webhook** | Кастомные сценарии | Зависит от реализации | Высокая |
| **Static Token** | Разработка/тестирование | Низкая | Низкая |
