# Pod Security Context в Kubernetes

Pod Security Context (контекст безопасности пода) определяет привилегии и разрешения для пода и его контейнеров. Эти настройки применяются к контейнерам внутри пода и могут влиять на их взаимодействие с хостовой системой и другими процессами.

Настройки Security Context могут быть определены на двух уровнях:

1.  **`PodSecurityContext` (уровень пода):** Применяется ко всем контейнерам в поде.
2.  **`ContainerSecurityContext` (уровень контейнера):** Применяется к отдельному контейнеру и переопределяет настройки на уровне пода, если они конфликтуют.

## Основные поля `securityContext`

Ниже представлены ключевые поля, используемые в `securityContext` для управления привилегиями:

### `privileged`

*   `privileged: true` предоставляет контейнеру расширенные привилегии, эквивалентные правам root на хостовой системе. Контейнер получает доступ ко всем устройствам хоста, возможность изменять параметры ядра и выполнять системные вызовы, обычно зарезервированные для ядра.
*   **Использование:** Применяется в исключительных случаях, когда контейнеру необходимо взаимодействовать с низкоуровневыми функциями операционной системы хоста, например, для запуска Docker внутри Docker (DinD), изменения настроек сети или монтирования файловых систем.
*   **Риски:** Использование `privileged: true` представляет серьезный риск безопасности, так как скомпрометированный контейнер может получить полный контроль над хостом. Следует избегать его использования, если есть более гранулированные способы предоставления необходимых разрешений.

### `runAsUser` и `runAsGroup`

*   `runAsUser`: Указывает UID пользователя, под которым будет запущен процесс в контейнере.
*   `runAsGroup`: Указывает GID основной группы, под которой будет запущен процесс в контейнере.
*   **Использование:** Позволяет запускать процессы в контейнере от имени определенного пользователя/группы, отличного от `root`, что повышает безопасность, минимизируя область атаки.

### `fsGroup`

*   `fsGroup`: Указывает GID, который будет применяться ко всем томам, примонтированным к поду. Владение томами изменяется на этот GID, и любые файлы, созданные в этих томах, также будут принадлежать этому GID.
*   **Использование:** Особенно полезно при работе с постоянными томами (Persistent Volumes), где необходимо гарантировать, что процессы в контейнере имеют правильные разрешения для чтения/записи файлов на смонтированных томах.

### `capabilities`

*   `capabilities`: Позволяет добавлять или удалять определенные POSIX-возможности Linux для контейнера. Вместо предоставления полных привилегий (`privileged: true`), можно предоставить только те возможности, которые действительно необходимы.
*   **Примеры:**
    *   `CAP_NET_ADMIN`: Разрешает выполнять сетевые операции (например, настройка сетевых интерфейсов).
    *   `CAP_SYS_ADMIN`: Разрешает выполнять различные системные административные операции (используется для `sysctl`).
*   **Использование:** Предпочтительный способ предоставления повышенных прав, так как он более гранулирован и безопасен, чем `privileged: true`.

### `allowPrivilegeEscalation`

*   `allowPrivilegeEscalation`: Булево значение, указывающее, может ли процесс в контейнере получать больше привилегий, чем его родительский процесс. По умолчанию `true`. Установка в `false` предотвращает, например, использование `setuid` или `setgid` бинарников.
*   **Использование:** Для усиления безопасности, когда контейнеру не требуется возможность повышения привилегий.

## Пример использования `securityContext`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-context-demo
spec:
  securityContext:
    runAsUser: 1000
    runAsGroup: 3000
    fsGroup: 2000
  containers:
  - name: sec-ctx-container
    image: busybox
    command: [ "sh", "-c", "sleep 1h" ]
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        add: ["NET_ADMIN"]
        drop: ["ALL"]
      privileged: false # Явно устанавливаем в false, чтобы избежать нежелательных привилегий
  initContainers:
  - name: init-privileged-container
    image: busybox
    command: ["sh", "-c", "sysctl -w vm.max_map_count=262144"]
    securityContext:
      privileged: true # В данном случае, требуется для изменения системных параметров
```
