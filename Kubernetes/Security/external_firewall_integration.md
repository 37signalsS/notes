# Интеграция внешних файрволов с Kubernetes

## Определения

**Внешний файрвол (NGFW)** — аппаратное или виртуальное устройство сетевой безопасности, расположенное вне кластера Kubernetes, обеспечивающее инспекцию трафика на уровнях L3–L7, включая IPS, Application Control, URL Filtering.

**East-West трафик** — сетевой трафик между подами внутри кластера Kubernetes (в отличие от North-South — трафик между кластером и внешним миром).

**UDR (User Defined Routes)** — пользовательские правила маршрутизации, позволяющие перенаправлять трафик через шлюзы безопасности (например, NGFW).

**Identity Awareness** — механизм идентификации рабочих нагрузок (подов) по метаданным (метки, namespace), позволяющий применять политики безопасности на уровне логических объектов, а не IP-адресов.

## Основные концепции

### Архитектура интеграции

В корпоративных средах Kubernetes-кластеры часто развертываются в приватном режиме, без прямого доступа из интернета. Весь трафик (входящий, исходящий, внутренний) проходит через внешний файрвол для глубокой инспекции.

```
┌─────────────────────────────────────────────────────────────┐
│                     Приватный кластер                        │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐          │
│  │   NodePool1 │  │   NodePool2 │  │   NodePool3 │          │
│  │  (Frontend) │  │  (Backend)  │  │   (Secret)  │          │
│  │ 10.4.1.0/24 │  │ 10.4.2.0/24 │  │ 10.4.3.0/24 │          │
│  └──────┬──────┘  └──────┬──────┘  └──────┬──────┘          │
│         │                │                │                  │
│         └────────────────┼────────────────┘                  │
│                          │                                   │
│                   ┌──────▼──────┐                            │
│                   │   CNI (L2)  │                            │
│                   │  Прямая связь│                            │
│                   └──────┬──────┘                            │
└──────────────────────────┼───────────────────────────────────┘
                           │
                    ┌──────▼──────┐
                    │   UDR /     │
                    │ Маршрутизация│
                    └──────┬──────┘
                           │
         ┌─────────────────┼─────────────────┐
         │                 │                 │
   ┌─────▼─────┐   ┌──────▼──────┐   ┌─────▼─────┐
   │ Интернет  │   │  NGFW/IPS   │   │ Внутренняя│
   │           │   │  (L3–L7)    │   │   сеть    │
   └───────────┘   └─────────────┘   └───────────┘
```

### Уровни инспекции трафика

| Уровень | Описание | Когда использовать |
|---------|----------|-------------------|
| **Только интернет-трафик** | Через NGFW маршрутизируется только исходящий/входящий трафик из интернета | Базовая защита периметра |
| **Между зонами безопасности** | Трафик между разными NodePool (например, frontend ↔ backend) проходит через NGFW | Сегментация по уровням доверия |
| **Весь East-West трафик** | Весь внутренний трафик между подами инспектируется NGFW | Высокие требования к безопасности, конфиденциальные workload |

### Режимы работы CNI и видимость IP-адресов

Для корректной инспекции трафика на внешнем файрволе критически важно, чтобы пакеты приходили с **родных IP-адресов подов**, а не с IP-адресов нод.

#### Проблема NAT

По умолчанию многие CNI-плагины (включая Calico) используют NAT для исходящего трафика:

```yaml
# Calico IPPool по умолчанию
apiVersion: projectcalico.org/v3
kind: IPPool
metadata:
  name: default-ipv4-ippool
spec:
  cidr: 10.233.0.0/16
  natOutgoing: true  # ⚠️ Трафик маскирадится под IP ноды
```

**Результат:** На файрволе виден IP ноды, а не пода → невозможно применить политики на уровне подов.

#### Решение: Отключение NAT

**Calico:**

```bash
# Отключить NAT для конкретного IPPool
kubectl patch ippool default-ipv4-ippool \
  --type merge \
  --patch '{"spec":{"natOutgoing":false}}'
```

**Azure CNI Overlay:**

- Поды получают IP-адреса из той же подсети, что и ноды
- Маршрутизация осуществляется на уровне гипервизора
- NAT не требуется по умолчанию

**On-prem с Calico:**

- Требуется явная настройка `natOutgoing: false`
- Необходима правильная маршрутизация между узлами (BGP или IPIP)

### Identity Awareness и динамические политики

Современные NGFW (Check Point, Palo Alto) поддерживают интеграцию с Kubernetes API для получения метаданных о подах:

1. **Подключение к Kubernetes API:**
   - Указывается адрес API-сервера (например, `https://kubernetes.default.svc:6443`)
   - Предоставляется сервисный аккаунт с правами на чтение Pod, Namespace, Label

2. **Импорт объектов:**
   - Поды импортируются как динамические объекты
   - Метки (labels) и namespace становятся атрибутами объектов
   - При пересоздании пода с новым IP объект автоматически обновляется

3. **Применение политик:**

   ```
   Правило 1: namespace=external → любой → ICMP → Accept + Log
   Правило 2: role=ingress → любой → любой → Accept
   Правило 3: namespace=backend → namespace=database → TCP/5432 → Accept
   Правило 4: любой → любой → любой → Drop + Log
   ```

**Ограничения:**

- Identity Awareness работает с задержкой (не мгновенно)
- Не подходит для сред с экстремально частыми пересозданиями подов (<1 сек)
- Требует включения функции на файрволе (даже если не работаете с пользователями)

## Практические сценарии

### Сценарий 1: Инспекция только интернет-трафика

**Конфигурация UDR:**

```
Маршрут по умолчанию (0.0.0.0/0) → NGFW
Локальная маршрутизация (10.4.0.0/16) → напрямую
```

**Преимущества:**

- Минимальная задержка для внутреннего трафика
- Простая настройка

**Недостатки:**

- Внутренние атаки не детектируются

### Сценарий 2: Инспекция между зонами безопасности

**Конфигурация UDR:**

```
10.4.1.0/24 (Frontend) → 10.4.2.0/24 (Backend) → NGFW
10.4.1.0/24 (Frontend) → 10.4.1.0/24 (Frontend) → напрямую
```

**Использование:**

- Разделение NodePool по уровням доверия
- Frontend (публичный доступ) ↔ Backend (внутренние сервисы)
- Детекция lateral movement при компрометации публичного сервиса

### Сценарий 3: Полная инспекция East-West трафика

**Конфигурация UDR:**

```
Весь трафик 10.4.0.0/16 → NGFW
```

**Требования:**

- Высокая производительность NGFW (задержка <1 мс)
- Отключение NAT на CNI (`natOutgoing: false`)
- Identity Awareness для динамических политик

**Использование:**

- Конфиденциальные workload (финансы, персональные данные)
- Соответствие регуляторным требованиям (PCI DSS, GDPR)

## Дополнительная информация

### Требования к NGFW

| Функция | Описание |
|---------|----------|
| **Kubernetes API Integration** | Импорт Pod, Namespace, Label как объектов безопасности |
| **Identity Awareness** | Динамическое применение политик на основе метаданных |
| **L7 Inspection** | Глубокий анализ HTTP/HTTPS, DNS, SQL |
| **IPS** | Обнаружение и предотвращение вторжений |
| **Application Control** | Идентификация приложений независимо от порта |
| **Высокая производительность** | Задержка <1 мс для East-West трафика |

### Ограничения и рекомендации

1. **Задержка Identity Awareness:** Не используйте для подов с временем жизни <1 сек
2. **Производительность:** Полная инспекция East-West требует мощного NGFW
3. **NAT:** Всегда отключайте NAT для видимости IP подов на файрволе
4. **Маршрутизация:** Убедитесь, что UDR не создаёт циклов маршрутизации
5. **Тестирование:** Проверяйте политики на тестовом кластере перед production
