# Аудит безопасности кластера Kubernetes до развёртывания (Cluster API)

**Актуально для:** Cluster API v1.x / CIS Kubernetes Benchmark 2.x / Kyverno CLI 1.10+

## Определения

**Cluster API (CAPI)** — подпроект Kubernetes (SIG Cluster Lifecycle), предоставляющий декларативные API и инструменты для унификации создания, обновления и эксплуатации множества Kubernetes-кластеров. Инфраструктура (ВМ, сети, балансировщики, VPC) и конфигурация кластера описываются теми же декларативными YAML-ресурсами, что и обычные рабочие нагрузки.

**CIS Kubernetes Benchmark** — стандартизированный чеклист безопасности от Center for Internet Security: набор рекомендаций по настройке компонентов Kubernetes (API Server, etcd, kubelet, Control Plane, Policies). Рекомендации делятся на Level 1 (практичные, не ингибируют работу технологии) и Level 2 (для сред с повышенными требованиями к безопасности); каждая помечена как Automated или Manual.

**Policy Engine** — движок политик, проверяющий манифесты на соответствие правилам (Kyverno, OPA Gatekeeper). Может блокировать раскатку (Enforce), мутировать манифест или работать в режиме аудита (dry-run с алертом).

**Shift Down Security** — концепция переноса проверок безопасности на платформенные команды: продуктовые команды доставляют бизнес-ценность, security-команды следят за внутренними регламентами и запускают сканеры, а платформенные команды доставляют приложения — именно на этом этапе можно отрезать наибольшую долю рисков. Концепция упомянута в докладе как новая; устоявшегося отраслевого определения пока нет.

**Metadata propagation** — механизм Cluster API, связывающий ресурсы между собой через лейблы, поля и метаданные; образует дерево зависимостей ресурсов будущего кластера.

**Модель нарушителя (threat actor model)** — согласованный с заказчиком перечень гипотетических атакующих (внешний нарушитель, внутренний, скомпрометированный разработчик), определяющий чек-лист аудита.

## Основные концепции

### Зачем аудитировать кластер, которого ещё нет

Типичный проект пентеста/аудита начинается с работающего кластера. Но в крупных организациях кластеры создаются декларативно через Cluster API: заказчик приходит с набором CAPI-манифестов, а кластера в железе ещё нет. Проверка манифестов до раскатки позволяет:

- удешевить и ускорить исправление мисконфигов — не нужно ждать, пока кто-то насканит работающий кластер;
- сделать кластер безопасным «с рождения», а не патчить постфактум.

### Как устроен Cluster API

Проблема: большая компания, множество кластеров и команд, каждая готовит конфигурации по-своему, обновляет и масштабирует кластеры под свои нужды. Решение — фреймворк Cluster API: унифицирует процессы создания кластеров, автоматически развёртывает их, описывает всё декларативно в YAML-ресурсах, масштабируется и управляется из одной точки — management-кластера (control plane, который катит остальные кластеры).

Факты: проект начат рабочей группой SIG Cluster Lifecycle; репозиторий создан в марте 2018 года, первые релизы — 2018 год; на GitHub более 4 тысяч звёзд; поддерживает десятки провайдеров — публичные облака (AWS, Google, Azure, Yandex) и on-premise (OpenStack, vSphere, bare-metal через Metal3).

Основные ресурсы (на них стоит обращать внимание с точки зрения безопасности):

| Ресурс | Что описывает |
| :--- | :--- |
| **Cluster** | Общая конфигурация кластера: сетевые настройки, подсети подов и сервисов, ссылки на infrastructure provider и control plane. |
| **InfrastructureProvider** (например, AWS-специфичный ресурс) | Конфигурация чисто под провайдера: VPC, подсети, control plane endpoint и прочие облачные сущности. Может перезаписывать поведение, заданное в `Cluster`. |
| **KubeadmControlPlane** | Конфигурация будущего API-сервера: реплики, версии, admission-плагины, feature gates — всё декларативно. |
| **MachineDeployment** | Конфигурация будущих нод; наследует и переиспользует темплейты через ссылки на предыдущие ресурсы. |
| **Machine** | Регулирует настройку конкретной будущей ноды. |

Все манифесты связаны друг с другом по лейблам, полям и метаданным (metadata propagation) — это дерево зависимостей, которое и является объектом аудита.

### Модели нарушителя и типовой чек-лист аудита

Перед аудитом с заказчиком согласовывают модели нарушителя:

- **Внешний нарушитель** — видит сеть кластера, ноды, торчащие наружу сервисы.
- **Внутренний нарушитель** — пробрался внутрь скомпрометированного контейнера, действует изнутри.
- **Скомпрометированный разработчик** — имеет минимальные права: сборка и пуш образов, запуск pipeline, деплой.

Чек-лист аудита (согласуется с заказчиком, обычно привязан к стандартам безопасности):

1. Соответствие CIS Kubernetes Benchmark.
2. Policy Engine: есть ли, можно ли обойти, недостатки конфигурации.
3. Network Policy: есть ли, что защищают, что не защищают (часто их нет вовсе).
4. RBAC: избыточные права и что можно с ними сделать.
5. Секреты: хранятся в кластере или используются сторонние решения (Vault).
6. Эксплуатация уязвимостей в компонентах: CoreDNS, containerd, сторонние обвязки (например, NVIDIA GPU Operator), уязвимые версии — каждая компания собирает дистрибутив по-своему, где-то забывают патчить.

### Структура CIS Kubernetes Benchmark

Benchmark состоит из разделов (номера и состав меняются от версии к версии):

1. **Компоненты Control Plane** — конфигурационные файлы нод, флаги API-сервера, controller-manager, scheduler.
2. **etcd** — флаги, ключи, TLS.
3. **Конфигурация Control Plane** — аутентификация, авторизация, логирование, аудит.
4. **Worker-ноды** — конфигурация kubelet и прочее.
5. **Policies** — ролевая модель (RBAC), Pod Security Standards (в т.ч. через Policy Engine: Kyverno, Gatekeeper), Network Policy и CNI, хранение секретов (in-cluster vs Vault).

В докладе упоминается порядка 130 проверок; точное число рекомендаций меняется от версии Benchmark к версии. Часть проверок — Manual: автоматизированный инструмент их не проверяет, результат не даёт. Для полного покрытия нужны ручные проверки, особенно по разделу Policies.

### Чем проверять

- **kube-bench** (Aqua Security, open-source): запускается как DaemonSet/Job на нодах, монтирует директории (`/etc`, `/var`), сканирует параметры запуска процессов и права на конфигурационные файлы. Плюс: open-source, есть хоть что-то. Минус: покрывает далеко не все проверки — часть в manual-режиме.
- Скрипты, делающие то же самое.
- Своя реализация для полного покрытия, включая manual-проверки раздела Policies.
- **Policy Engine** (Kyverno, OPA Gatekeeper) — для проверки самих манифестов.

### Shift Down Security и связь с CAPI

Суть концепции: безопасность переносится на платформенные команды. Продуктовые команды доставляют бизнес-ценность; security-команды следят за внутренними регламентами, смотрят код, запускают сканеры; платформенные команды доставляют приложения — и на этом этапе можно многое отрезать с точки зрения безопасности.

Концепция ложится на подход доклада: любой ресурс в Kubernetes — YAML-манифест; CAPI-манифесты — тоже YAML-ресурсы. Policy Engine умеет проверять любые манифесты (не только YAML — JSON и другие форматы). Скармливаем CAPI-манифесты Policy Engine — получаем результат до того, как кластер существует.

### Что можно и чего нельзя проверить до развёртывания

**Можно:**

- флаги компонентов Control Plane и Data Plane — то, что требует CIS Kubernetes Benchmark;
- явно указанное и захардкоженное, где точно известны уязвимости: версия ядра, версия хостовой ОС, container runtime, CNI — быстро патчится, бампается версия.

**Нельзя:**

- содержимое YAML-манифестов приложений — Cluster API не предоставляет механизма контроля содержимого;
- security context в будущих манифестах (если катится что-то особенное);
- сетевые политики — какие они будут и как работают.

**Результат:** по итогам проекта, описанного в докладе, более 73% проверок CIS Kubernetes Benchmark можно выполнить на этапе, когда кластер ещё не существует; с учётом доработки manual-проверок руками процент выше.

## Практические сценарии

### 1. Проверка CAPI-манифеста через Kyverno CLI

Kyverno CLI (`kyverno apply`) применяет политики к локальным YAML-файлам без кластера — создан для валидации ресурсов до добавления в кластер и для CI/CD-пайплайнов.

```bash
# Проверить один CAPI-манифест одной политикой
kyverno apply /path/to/policy.yaml --resource /path/to/cluster.yaml

# Проверить папку CAPI-манифестов папкой политик
kyverno apply /path/to/policies/ --resource /path/to/capi-manifests/

# Вывод в JSON для интеграции в пайплайн
kyverno apply /path/to/policy.yaml --resource /path/to/cluster.yaml --output-format json
```

Пример политики (иллюстративный): проверка, что в манифесте задан файл аудит-политики и режим авторизации API-сервера:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-audit-and-authz
spec:
  validationFailureAction: Audit
  rules:
    - name: audit-policy-file-present
      match:
        any:
          - resources:
              kinds:
                - KubeadmControlPlane
      validate:
        message: "Файл аудит-политики должен быть задан"
        pattern:
          spec:
            kubeadmConfigSpec:
              files:
                - path: /etc/kubernetes/audit-policy.yaml
    - name: authorization-mode
      match:
        any:
          - resources:
              kinds:
                - KubeadmControlPlane
      validate:
        message: "authorization-mode должен включать RBAC"
        pattern:
          spec:
            kubeadmConfigSpec:
              apiServer:
                extraArgs:
                  authorization-mode: "*RBAC*"
```

> Пример политики иллюстративный: структура `KubeadmControlPlane` зависит от версии CAPI и bootstrap-провайдера. В API `v1beta1` `extraArgs` — map, в `v1beta2` — список объектов `{name, value}`; проверяйте формат в документации kubeadm bootstrap provider.

То же самое — для других настроек: admission-плагины, любые другие флаги API-сервера, конфигурация etcd (`spec.kubeadmConfigSpec.etcd.local.extraArgs`), kubelet (`spec.kubeadmConfigSpec.kubeletExtraArgs`).

Режимы работы Policy Engine: блокировка раскатки (Enforce), мутация манифеста, dry-run аудит с алертом. Для предварительного аудита CAPI-манифестов подходит режим Audit — нарушения фиксируются в отчёт без блокировки.

### 2. Проверка конфигурации Istio — Snowcat

Для Istio есть готовое решение: **Snowcat** (praetorian-inc/snowcat) — инструмент, который собирает и анализирует конфигурацию Istio-кластера и проверяет её на нарушения security best practices (например, валидация TLS-сертификатов в DestinationRules, политика JWT для control plane). Работает в двух режимах: unauthenticated (перечисление control plane) и static analysis. Дополняется встроенным анализатором Istio — `istioctl analyze` (проверяет все виды мисконфигураций, не только безопасность).

### 3. Проверка Docker-образов — Trivy compliance

Trivy поддерживает compliance-отчёты (фича помечена EXPERIMENTAL): встроенные отчёты для Docker (`trivy image --compliance docker-cis-...`) и Kubernetes (`trivy k8s cluster --compliance=k8s-cis-...`), а также NSA/CISA и Pod Security Standards. Это не аналоги kube-bench, а другой класс инструментов: сканирование образов и конфигурации, а не хостовых параметров нод.

### 4. Хостовая часть — CIS Linux Benchmark + OpenSCAP

Для хостов есть CIS Benchmark для Linux и инструмент OpenSCAP, для которого существуют Ansible-плейбуки (проект ansible-lockdown), позволяющие автоматизировать аудит и ремедиацию. Важно: CIS «из коробки» обычно не работает как готовое решение — всегда нужна дополнительная доработка под компанию: расстановка «заборчиков», осознанные отклонения. Пример из практики: best practices требуют отключить анонимную аутентификацию, но компания собирает метрики анонимно — отклонение осознанное, его нужно прикрыть compensating controls (мандатка, фильтрация системных вызовов) и задокументировать.

## Ограничения подхода

- Невозможно проверить содержимое будущих YAML-манифестов приложений, security context и сетевые политики — CAPI не контролирует содержимое.
- kube-bench и аналоги покрывают не все проверки CIS: часть — Manual, автоматизации не поддаётся.
- Open-source инструменты аудита безопасны, если их запускает осознанный оператор с пониманием прав: инструменты только подсвечивают уязвимости, не эксплуатируют их; более инвазивные инструменты (например, kube-hunter) могут действовать активно — предупреждение обязательно. При выборе смотрите популярность проекта (звёзды), как исправляются баги и есть ли maintainers: в популярных проектах за кодом следят компании, рандомный код не вливается; в заброшенных проектах уязвимости могут лежать годами.
- Отклонение от best practices — это осознанный выбор, а не дефект: если бизнес и ИБ готовы принять риск, параметр можно оставить. Best practices — ориентир «как сделать безопасно в лоб», а не единственное решение.

## Best Practices

1. **Не ставьте все контролы подряд.** «Старая школа безопасности» (антивирус в контейнер + политики + оператор на всё подряд) даёт перегруженную систему и тяжёлый флоу работы команд. Безопасность ради безопасности — слив бюджета. Нужна приоритизация.
2. **Приоритизация по бизнес-ценности.** Владелец денег лучше всего знает, чего он боится и не хочет потерять: у одной компании это данные заказов, у другой — PCI DSS и карты, у третьей — видеопоток. От этого строится стратегия защиты. Закрыть всё не хватит ни финансовых, ни человеческих ресурсов — security-команда всегда в дефиците.
3. **Модель угроз.** Модель угроз (STRIDE и т.п.) — классическая модель из науки безопасности, но перечень из 500 угроз, найденных пентест-инструментом, бизнесу не нужен; нужны реально проработанные, актуальные для конкретного бизнеса угрозы. Для приоритизации существует десяток методик.
4. **Секреты — не в контейнере.** Не храните секреты в виде файлов или переменных окружения в контейнере: прокидывайте их в момент runtime, когда приложение запускается, через инжектор (Vault, Secrets Store CSI driver). Выбор механизма зависит от модели нарушителя: защищаетесь от cluster-admin — Vault; от того, что попадёт в контейнер — CSI driver.
5. **Kyverno vs OPA Gatekeeper.** Эмпирическое правило из практики: если Admission Controller внедряет команда эксплуатации — OPA (Rego), если команда безопасности — Kyverno (нативный YAML, проще писать и читать). Rego мощнее, но порог входа выше: нужны люди, которые его знают; большие политики на Rego тяжело анализировать с точки зрения безопасности. Сейчас оба движка функционально на одной стадии (Kyverno добавил поддержку ValidatingAdmissionPolicy).
6. **Автоматизируйте проверку в пайплайне.** Kyverno CLI в CI/CD на CAPI-манифесты, Trivy compliance на образы, kube-bench/Trivy на кластер после раскатки — Policy Engine, который не пропустит или алертнет, лучше ручного сканирования.
