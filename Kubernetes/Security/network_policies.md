# NetworkPolicy: Сетевая безопасность и изоляция подов

**NetworkPolicy** является ключевым инструментом обеспечения безопасности в Kubernetes, реализующим принципы микросегментации и нулевого доверия (Zero Trust) на сетевом уровне.

> Полное руководство с навигацией по всем аспектам находится в **[NetworkPolicy: Навигатор](../Networking/Network/network_policy.md)**.

## Определения

**NetworkPolicy** — это ресурс Kubernetes (API-группа `networking.k8s.io/v1`), который позволяет управлять сетевым трафиком на уровнях L3 и L4 модели OSI. Он определяет правила разрешения трафика для групп подов, работая по принципу "белых списков" (allow-lists).

* **Подробные определения**: [NetworkPolicy: Определения и концепции](../Networking/Network/NetworkPolicy/definitions.md)

### Ключевые понятия безопасности

* **Default behavior (Поведение по умолчанию)**: Изначально в кластере разрешены все входящие и исходящие соединения.
* **Изоляция подов**: Как только `NetworkPolicy` выбирает под через `podSelector`, этот под становится **изолированным**. С этого момента разрешается только тот трафик, который явно указан в политике. Все остальные соединения блокируются.
* **Default Deny (Запрет по умолчанию)**: Режим, при котором любой трафик, не разрешенный явно, блокируется. Это фундамент безопасности в кластере.
* **CNI (Container Network Interface)**: Сетевой плагин, отвечающий за фактическую реализацию правил фильтрации. Без поддержки со стороны CNI (например, Calico или Cilium) ресурс NetworkPolicy будет проигнорирован.

*Подробный разбор логики: [NetworkPolicy: Логика правил](../Networking/Network/NetworkPolicy/rule_logic.md)*

## Основные концепции

### Цели сетевой безопасности в Kubernetes
Сетевая безопасность направлена на защиту трафика внутри кластера и между кластером и внешними объектами.

**Ключевые приоритеты:**
- **Эффективная изоляция:** предотвращение несанкционированного доступа между приложениями, командами или отделами.
- **Защита конфиденциальных данных:** предотвращение перехвата или подделки данных (PII).
- **Минимизация распространения атак (Blast Radius):** ограничение бокового перемещения злоумышленника.
- **Защита от внешних угроз:** снижение риска DDoS и атак перебора.
- **Обеспечение доступности:** предотвращение сбоев через сегментацию.
- **Поддержание доверия:** соблюдение стандартов безопасности.

### Реализация сетевых политик: детали
1.  **Создание политик:** Ресурсы `NetworkPolicy` определяют правила взаимодействия на основе меток и селекторов.
2.  **Маркировка (Labeling):** Помечайте поды конкретными идентификаторами. Метки определяют, на какие поды распространяются правила.
3.  **Правила Ingress/Egress:** Определите источники входящего трафика и пункты назначения исходящего.
4.  **Политика "Default Deny":** Настоятельно рекомендуется определить политику "запретить всё" по умолчанию. Это подход с нулевым доверием (Zero Trust).

### Совет по собеседованию: Ingress vs Egress
> **Вопрос:** В чем разница между правилами Ingress и Egress?
> **Ответ:** **Ingress** управляет входящим трафиком к подам (кто может обращаться к приложению), а **Egress** — исходящим трафиком от подов (куда приложение может отправлять запросы). Оба типа используют селекторы подов, пространств имен и блоки IP (CIDR).

### Принцип нулевого доверия (Zero Trust)

В стандартной модели Kubernetes сеть считается открытой ("flat network"): все поды могут свободно взаимодействовать. Безопасный подход требует внедрения модели **Default Deny**:

1. Изначально весь трафик разрешен.
2. Как только селектор `podSelector` в NetworkPolicy выбирает под, этот под становится изолированным.
3. Разрешается только тот трафик, который явно указан в разделах `ingress` или `egress`.

### Направления трафика и типы политик

Поле `policyTypes` определяет, какие направления трафика будут контролироваться:

* **Ingress**: Правила для входящего трафика к целевым подам.
* **Egress**: Правила для исходящего трафика от целевых подов.

Если `policyTypes` не указан, Kubernetes пытается определить его автоматически на основе наличия секций `ingress` и `egress`, однако явное указание считается лучшей практикой.

### Селекторы и правила

Правила могут основываться на трех типах селекторов:

* **podSelector**: Выбор подов в том же пространстве имен.
* **namespaceSelector**: Выбор всех подов в определенных пространствах имен.
* **ipBlock**: Определение внешних IP-диапазонов (CIDR). При использовании `ipBlock` следует учитывать нюансы работы NAT и `externalTrafficPolicy`.

### Порты и протоколы

NetworkPolicy поддерживает:
* **TCP**, **UDP** и **SCTP**.
* **Диапазоны портов**: Поле `endPort` (доступно в стабильных версиях) позволяет указывать диапазон портов вместо перечисления каждого по отдельности.

## Практические сценарии

Типовые сценарии для обеспечения безопасности:

* **Полная изоляция пространства имен**: Создание политики `default-deny`, которая блокирует весь входящий и исходящий трафик. Это рекомендуется делать для каждого нового namespace.
* **Изоляция базы данных**: Разрешение входящего трафика на порт БД только из доверенных сегментов (например, от подов с меткой `app: backend`).
* **Разрешение DNS-трафика**: При использовании Egress-изоляции необходимо явно разрешить доступ к DNS (обычно порт 53 UDP/TCP) для работы Service Discovery.
* **Ограничение внешнего доступа**: Использование `ipBlock` для запрета доступа к публичным сетям при сохранении доступа к внутренним сервисам.

*Все сценарии с готовыми YAML-примерами: [Практические сценарии NetworkPolicy](../Networking/Network/NetworkPolicy/practical_scenarios.md)*

## Дополнительная информация

### Ограничения и альтернативы

Стандартные NetworkPolicy имеют ряд ограничений:
* **Отсутствие поддержки L7**: Невозможно фильтровать трафик по HTTP-путям, заголовкам или методам.
* **Нет поддержки FQDN**: Правила работают только с IP-адресами и селекторами, но не с доменными именами.
* **Отсутствие логирования**: Нативный ресурс не предоставляет средств для аудита заблокированного трафика.

Для расширенного контроля рекомендуется использовать:
* **Расширенные CNI (Calico, Cilium)**: Поддержка GlobalNetworkPolicy, политик на уровне узлов и фильтрации по FQDN.
* **Service Mesh (Istio, Linkerd)**: Управление безопасностью на уровне L7, mTLS и детальное логирование.

### Рекомендуемые инструменты

* **Визуализация**: Инструменты типа Cilium Editor или аналогичные визуализаторы помогают проверить корректность правил перед применением.
* **Автоматизация**: [Генерация NetworkPolicy через Kyverno](./kyverno/policies/practical_scenarios.md) позволяет автоматически создавать базовые политики безопасности.
