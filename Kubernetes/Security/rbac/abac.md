# Управление доступом на основе атрибутов (ABAC)

> **Статус: устаревший (deprecated)**. Режим авторизации `ABAC` официально объявлен устаревшим начиная с Kubernetes v1.17 и **не рекомендуется** для новых установок. Механизм по-прежнему присутствует в бинарнике `kube-apiserver`, но всей функциональности не удаляется (вопреки первоначальному плану удаления в v1.20), а развитие сосредоточено на RBAC. Для атрибутных сценариев (условия, содержимое, контекст) современной альтернативой служат Admission Webhooks (OPA Gatekeeper, Kyverno) и `ValidatingAdmissionPolicy` (CEL). Данный документ описывает механизм для понимания legacy-кластеров и процесса миграции.

## Определения

**ABAC (Attribute-Based Access Control — управление доступом на основе атрибутов)** — метод авторизации в Kubernetes, который принимает решения на основе комбинации атрибутов субъекта, ресурса и действия. В отличие от RBAC, где права привязаны к ролям, ABAC позволяет определять политики напрямую для пользователей или групп в виде структурированного JSON-файла на диске мастер-узла.

**Атрибут (Attribute)** — характеристика запроса, используемая для сопоставления с политикой: имя пользователя (`user`), группа (`group`), пространство имён (`namespace`), тип ресурса (`resource`), API-группа (`apiGroup`), путь вне ресурсов (`nonResourcePath`) и режим доступа (`readonly`).

**Политика (Policy)** — отдельная строка JSON-файла, описывающая один набор разрешений. Правила действуют **аддитивно**: если хотя бы одна политика разрешает запрос, запрос авторизуется.

## Основные концепции

### Механизм работы

При использовании ABAC API-сервер Kubernetes проверяет каждый входящий запрос на соответствие списку политик, загруженных из локального файла. Запрос разрешается, если хотя бы одна политика в файле явно разрешает данное действие.

Алгоритм принятия решения:

1. Для каждого входящего запроса формируется набор атрибутов (субъект, ресурс, действие, путь). Неизвестные атрибуты принимают нулевое значение своего типа (пустая строка, `0`, `false`).
2. Каждый атрибут сопоставляется со свойствами всех политик в файле. Свойство `*` (wildcard) совпадает с любым значением соответствующего атрибута.
3. Если **хотя бы одна** политика полностью совпадает со всеми атрибутами запроса — запрос авторизуется (`Allow`).
4. Если ни одна политика не совпала — модуль возвращает `No Opinion` (в отличие от жёсткого `Deny`). Это важно: решение о конечном запрете принимает цепочка авторизаторов (см. ниже).

**Отсутствие Deny-правил:** как и RBAC, ABAC работает по принципу "закрытого мира" и не позволяет явно запрещать операции. Ограничение достигается только тем, что отсутствующая политика просто не даёт права на действие.

### Настройка API-сервера

Для включения ABAC необходимо передать API-серверу следующие флаги:

- `--authorization-mode=ABAC` — активирует модуль авторизации ABAC (может использоваться совместно с RBAC через запятую: `Node,RBAC,ABAC`).
- `--authorization-policy-file=/etc/kubernetes/policies/abac.json` — путь к JSON-файлу с политиками.

**Важно:** Изменения в файле политик не подхватываются автоматически. Для применения новых правил требуется перезагрузка процесса `kube-apiserver`. Это ключевое эксплуатационное отличие от RBAC, где изменения применяются мгновенно через API.

**Полный доступ без описания среды:** для доступа к специальным ресурсам (например, эндпоинтам, не относящимся к ресурсам) их необходимо явно открыть через свойство `nonResourcePath` в политике.

### Современная альтернатива флагам — `--authorization-config`

Начиная с Kubernetes v1.30 (GA в v1.31) конфигурация цепочки авторизаторов может задаваться файлом `AuthorizationConfiguration` (`apiserver.config.k8s.io/v1`) через флаг `--authorization-config` вместо `--authorization-mode`. Это позволяет гибко описывать несколько авторизаторов, включая `ABAC`, их порядок и параметры (например, Webhook). **Важно:** флаг `--authorization-config` **нельзя** комбинировать с `--authorization-mode` и `--authorization-webhook-*` — одновременное использование обоих способов приводит к ошибке на старте API-сервера.

### Структура политики

Каждая строка в файле политик представляет собой отдельный JSON-объект. Формат файла — **JSONL**: один объект на строку, без внешнего списка или карты. Пустые строки и строки-комментарии, начинающиеся с `#`, игнорируются.

Поля в секции `spec`:

- **Версионирование:**
  - `apiVersion`: строка, допустимое значение `abac.authorization.kubernetes.io/v1beta1`. Обеспечивает версионирование и конвертацию формата политик.
  - `kind`: строка, допустимое значение `Policy`.
- **Субъект (Subject):**
  - `user`: Имя пользователя (строка), полученное из `--token-auth-file` (см. [Аутентификация](../authentication.md)). Используйте `*` для обозначения всех пользователей.
  - `group`: Имя группы (строка). Используйте `system:authenticated` для всех аутентифицированных пользователей, `system:unauthenticated` — для всех неаутентифицированных. Если указана группа, она должна совпадать с одной из групп аутентифицированного пользователя.
- **Ресурс (Resource):**
  - `namespace`: Пространство имен.
  - `resource`: Тип ресурса (например, `pods`, `services`).
  - `apiGroup`: Группа API (например, `extensions`, `apps`).
- **Действие (Action):**
  - `readonly`: Булево значение (`true`/`false`). Если `true`, разрешены только `get`, `list`, `watch` для ресурсных политик и только `get` — для политик `nonResourcePath`.
  - `nonResourcePath`: Пути, не относящиеся к ресурсам (например, `/healthz`, `/metrics`). Используйте `*` как wildcard для всех путей или `/foo/*` для всех подпутей `/foo/`.

**Неперечисленное свойство** эквивалентно нулевому значению для своего типа (пустая строка, `0`, `false`). Например, если `readonly` не указан, оно считается `false`, и политика разрешает все действия (create, update, delete и т.д.) над указанным ресурсом. Для читаемости рекомендуется не указывать свойство, вместо того чтобы явно задавать нулевое значение.

### Сравнение ABAC и RBAC

| Характеристика | ABAC | RBAC |
| :--- | :--- | :--- |
| **Хранение** | Локальный файл на мастере | Объекты в etcd (API-ресурсы) |
| **Применение** | Требуется рестарт API-сервера | Мгновенно через API |
| **Управление** | Доступ к файловой системе мастера | Стандартные инструменты (`kubectl`) |
| **Гибкость** | Высокая (поддержка wildcard) | Ограничена структурой ролей |
| **Масштабируемость** | Низкая (сложно управлять в больших кластерах) | Высокая |
| **Аудит** | Нет встроенного инструментария | Нативная интеграция с `kubectl auth can-i` и аудитом |
| **Прямые изменения политик** | Только через SSH на мастер + рестарт | Через API / `kubectl` |

**Ключевой факт:** RBAC **строго выразительнее** ABAC — он может авторизовать и ресурсы, и non-resource пути так же, как ABAC, но при этом хранится в API и применяется динамически. Единственное принципиальное отличие ABAC — политика полностью находится под контролем настройщика `kube-apiserver` и не может быть изменена или дополнена через API (что уменьшает поверхность атаки при компрометации API).

### Место в цепочке авторизаторов

Запросы проверяются модулями авторизации последовательно. Если один из модулей разрешает запрос (`Allow`), проверка прекращается. Если модуль не может принять решение (`No Opinion`) — запрос переходит к следующему. Если все модули отказали — возвращается ошибка `403 Forbidden`.

ABAC при отсутствии совпадения возвращает `No Opinion`, поэтому его можно безопасно включать в цепочку **после** RBAC как "резервный" источник прав:

```text
Node -> RBAC -> ABAC
```

При миграции с ABAC на RBAC это позволяет держать оба авторизатора одновременно: любой запрос, разрешённый либо RBAC, либо ABAC, будет пропущен.

## Практические сценарии

### Пример 1: Полный доступ администратору

Разрешить пользователю `admin` любые действия над всеми ресурсами во всех пространствах имен.

```json
{
  "apiVersion": "abac.authorization.kubernetes.io/v1beta1",
  "kind": "Policy",
  "spec": {
    "user": "admin",
    "namespace": "*",
    "resource": "*",
    "apiGroup": "*"
  }
}
```

### Пример 2: Доступ на чтение для всех аутентифицированных пользователей

Разрешить всем пользователям просматривать поды в любом namespace.

```json
{
  "apiVersion": "abac.authorization.kubernetes.io/v1beta1",
  "kind": "Policy",
  "spec": {
    "group": "system:authenticated",
    "resource": "pods",
    "readonly": true
  }
}
```

### Пример 3: Доступ к служебным путям (non-resource)

Разрешить всем (включая неаутентифицированных) доступ к эндпоинту проверки здоровья.

```json
{
  "apiVersion": "abac.authorization.kubernetes.io/v1beta1",
  "kind": "Policy",
  "spec": {
    "user": "*",
    "nonResourcePath": "/healthz"
  }
}
```

### Пример 4: Полный доступ неаутентифицированным пользователям (запрещённый сценарий)

Разрешить любое чтение (get/list/watch) всем, включая неаутентифицированных. **Опасно** — используется только в отладочных/открытых средах.

```json
{
  "apiVersion": "abac.authorization.kubernetes.io/v1beta1",
  "kind": "Policy",
  "spec": {
    "group": "system:unauthenticated",
    "nonResourcePath": "*",
    "readonly": true
  }
}
```

### Пример 5: Чтение только в конкретном namespace (пример из официальной документации)

Разрешить пользователю `bob` читать поды только в неймспейсе `projectCaribou`.

```json
{
  "apiVersion": "abac.authorization.kubernetes.io/v1beta1",
  "kind": "Policy",
  "spec": {
    "user": "bob",
    "namespace": "projectCaribou",
    "resource": "pods",
    "readonly": true
  }
}
```

### Пример 6: Права kubelet на поды и события

Типовой legacy-сценарий для узла: kubelet получает права на чтение подов и полный доступ к событиям в любом namespace.

```json
{"apiVersion": "abac.authorization.kubernetes.io/v1beta1", "kind": "Policy", "spec": {"user": "kubelet", "namespace": "*", "resource": "pods", "readonly": true}}
{"apiVersion": "abac.authorization.kubernetes.io/v1beta1", "kind": "Policy", "spec": {"user": "kubelet", "namespace": "*", "resource": "events"}}
```

### Полноценный файл политик (JSONL)

Реальный файл содержит по одному объекту на строку (формат JSONL). Комментарии с `#` и пустые строки игнорируются:

```jsonl
# Полный доступ администратора
{"apiVersion": "abac.authorization.kubernetes.io/v1beta1", "kind": "Policy", "spec": {"user": "admin", "namespace": "*", "resource": "*", "apiGroup": "*"}}
# Чтение подов аутентифицированным пользователям
{"apiVersion": "abac.authorization.kubernetes.io/v1beta1", "kind": "Policy", "spec": {"group": "system:authenticated", "resource": "pods", "readonly": true}}
# Доступ к healthz всем (включая неаутентифицированных)
{"apiVersion": "abac.authorization.kubernetes.io/v1beta1", "kind": "Policy", "spec": {"user": "*", "nonResourcePath": "/healthz/"}}
```

### Проверка работоспособности

1. **Проверка запуска:** после рестарта `kube-apiserver` убедитесь, что в логах нет ошибок загрузки политик вида `failed to load policy file`. При ошибке формата API-сервер откажется стартовать.
2. **Функциональная проверка:** выполните запрос от имени субъекта, для которого настроена политика:
   ```bash
   # Ожидается успешный ответ (список подов)
   kubectl get pods --as=admin

   # Ожидается 403 Forbidden для пользователя без прав (или с ограниченными правами)
   kubectl delete pod some-pod --as=restricted-user
   ```
3. **Проверка через SubjectAccessReview:** можно отправить `SelfSubjectAccessReview`, чтобы увидеть, разрешает ли политика действие, без реального его выполнения.

### Миграция с ABAC на RBAC (рекомендованный процесс)

Пошаговый переход без сбоев рабочих нагрузок:

1. **Параллельный запуск авторизаторов:** включите в цепочку и RBAC, и ABAC, оставив файл с legacy-политиками:
   ```bash
   --authorization-mode=Node,RBAC,ABAC --authorization-policy-file=/etc/kubernetes/abac-policy.json
   ```
   Пока обе системы активны, любой запрос, разрешённый хотя бы одной из них, будет пропущен. Это гарантирует, что RBAC-миграция не «сломает» существующие сервисы.
2. **Выявление фактических прав:** включите подробное логирование решений RBAC (`--v=5` или `--vmodule=rbac*=5`). В логах `kube-apiserver` появятся записи об отказах RBAC (префикс `RBAC`). На основе этих записей определите, какие роли нужно выдать определённым пользователям, группам или ServiceAccount.
3. **Выдача ролей:** создайте нужные `Role`/`ClusterRole` и связывания через `kubectl` (см. [Роли и ClusterRole](./roles.md) и [Привязки ролей](./bindings.md)).
4. **Контроль:** убедитесь, что рабочие нагрузки работают без новых записей об отказах RBAC в логах.
5. **Удаление ABAC:** после стабилизации удалите `ABAC` из `--authorization-mode` и отключите `--authorization-policy-file`, затем перезапустите `kube-apiserver`.

**Внимание:** исторически многие legacy-кластеры использовали избыточно «широкие» ABAC-политики, в том числе с полным доступом для всех ServiceAccount. Такие права не следует слепо переносить в RBAC — вместо этого проведите ревизию и назначьте минимально необходимые права (принцип наименьших привилегий).

### Диагностика и устранение неполадок

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| API-сервер не стартует | Ошибка формата или пути `--authorization-policy-file` | Проверить корректность JSONL, права доступа к файлу, наличие строки-объекта |
| Запросы возвращают `403`, хотя политика есть | Частичное совпадение (например, неправильно указан `namespace` или отсутствует `readonly`), либо запрос не доходит до ABAC из-за предыдущего `Deny` в цепочке | Проверить соответствие всех атрибутов; порядок авторизаторов |
| Изменения политики не действуют | Файл читается только при старте процесса | Перезапустить `kube-apiserver` |
| `readonly: true` не ограничивает запись | Свойство применяется только при указании `readonly: true`; если на ресурс есть отдельная политика без `readonly` | Убедиться, что нет «широкой» политики без `readonly` для того же субъекта |

## Дополнительная информация

### Принцип наименьших привилегий

Независимо от выбранного метода, всегда следуйте принципу **минимальных привилегий (PoLP)**. ABAC в Kubernetes считается устаревшим (legacy) методом и не рекомендуется для использования в новых инсталляциях, уступая место более динамичному и удобному RBAC. Все возможности ABAC воспроизводимы в RBAC и Webhook-авторизаторах.

### Ограничения и особенности ABAC

- **Статичность:** политики нельзя менять динамически — только перезапуском API-сервера.
- **Без контекста:** ABAC (как и RBAC) не учитывает внешние атрибуты (время, IP, содержимое запроса). Для атрибутной логики в современных кластерах применяются Admission Webhooks (OPA Gatekeeper, Kyverno) и `ValidatingAdmissionPolicy` (CEL). См. [Ограничения RBAC и OPA/Kyverno](./limitations_opa.md).
- **Слепота к содержимому:** ABAC проверяет только глагол и ресурс, но не содержимое манифеста (например, `privileged: true`).
- **Отсутствие deny:** нельзя явно запретить действие — только не разрешить его.
- **Единственный статический источник:** недоступность редактирования через API может считаться преимуществом безопасности, так как компрометация API-уровня не даёт злоумышленнику изменить политики.
