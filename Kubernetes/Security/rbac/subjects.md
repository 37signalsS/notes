# Субъекты доступа (Subjects) в Kubernetes

## Определения

**Субъекты (Subjects)** — это сущности, которым предоставляются разрешения на выполнение действий в кластере Kubernetes. RBAC связывает роли с этими субъектами через объекты Binding.

Существует три основных типа субъектов:

1.  **Пользователи (Users):** Отдельные люди (администраторы, разработчики). Kubernetes не управляет объектами пользователей напрямую, а полагается на внешние системы аутентификации (сертификаты, токены, LDAP, OIDC).
2.  **Группы (Groups):** Коллекции пользователей. Позволяют назначать права сразу множеству людей (например, `system:authenticated`).
3.  **Учетные записи служб (Service Accounts):** Идентификаторы для приложений, процессов или подов, работающих внутри кластера.

---

## Основные концепции

### Учетные записи служб (Service Accounts)

В отличие от пользователей, **Service Accounts (SA)** являются внутренними ресурсами, которыми управляет сам Kubernetes через API. Это рекомендуемый способ предоставления подам возможности безопасного взаимодействия с Kubernetes API внутри кластера.

- **Назначение и идентификация:** Service Account обеспечивает уникальную идентификацию для процессов, работающих в кластере. Каждый под связан с SA (явно или через `default`), и при запросе к API-серверу под аутентифицируется с использованием учетных данных (токенов), связанных с его SA.
- **Взаимодействие с API:** SA позволяют подам обмениваться данными с API-сервером, выполнять действия с ресурсами и взаимодействовать с другими компонентами кластера.
- **Управление доступом (RBAC):** На Service Accounts в полной мере распространяются политики RBAC. Это позволяет администраторам определять детализированные разрешения (роли) и ограничивать действия модулей по принципу минимальных привилегий.
- **Автоматизация токенов:** Kubernetes автоматически генерирует и управляет токенами-носителями (bearer tokens) для Service Accounts, обеспечивая безопасную связь.
- **Лучшая практика (SSoT):** Хотя каждое пространство имен содержит `default` Service Account, **необходимо** создавать специальные учетные записи для конкретных приложений. Это позволяет реализовать принцип минимальных привилегий и изолировать доступы разных сервисов.
- **Изоляция:** Каждое пространство имен имеет стандартный `default` Service Account.


### Область действия разрешений

Разрешения, назначаемые субъектам, могут иметь разную область детализации:

- **Уровень пространства имен (Namespace):** Роли (`Role`) ограничивают доступ только к ресурсам внутри конкретного namespace (например, `dev` или `prod`). Это предпочтительный метод для изоляции команд.
- **Уровень кластера (Cluster):** Кластерные роли (`ClusterRole`) предоставляют доступ к ресурсам во всех пространствах имен одновременно или к ресурсам вне пространств имен (узлы, PV).

## Практические сценарии

### Создание Service Account

```bash
# Создание сервисного аккаунта в namespace dev
kubectl create serviceaccount my-app-sa -n dev
```

### Привязка субъекта к роли

После определения субъекта он должен быть привязан к [Роли](./roles.md) с помощью [RoleBinding](./bindings.md).

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: read-pods-binding
  namespace: dev
subjects:
- kind: ServiceAccount
  name: my-app-sa
  namespace: dev
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

## Дополнительная информация

### Советы для собеседования

> **Вопрос:** В чем разница между User и ServiceAccount?
> **Ответ:** Пользователи (Users) предназначены для людей и управляются внешними системами. Сервисные аккаунты (ServiceAccounts) — это внутренние объекты Kubernetes для идентификации приложений и подов.

> **Вопрос:** Могут ли роли быть ограничены только одним пространством имен?
> **Ответ:** Да, объект `Role` всегда ограничен пространством имен. Для доступа на уровне всего кластера необходимо использовать `ClusterRole`.
