# Обзор управления доступом на основе ролей (RBAC)

## Определения

**RBAC (Role-Based Access Control — управление доступом на основе ролей)** — основной механизм авторизации в Kubernetes, обеспечивающий гранулярное управление доступом субъектов (пользователей, групп, [сервисных аккаунтов](./subjects.md)) к ресурсам кластера через декларативные правила.

Ключевые сущности:

- **Субъект (Subject)** — "Кто" запрашивает доступ: `User`, `Group`, [ServiceAccount](./subjects.md).
- **Роль (Role)** — "Что" разрешено: набор правил и глаголов ([Role](./roles.md) или [ClusterRole](./roles.md)).
- **Привязка (Binding)** — "Связь": сопоставление субъекта с ролью ([RoleBinding](./bindings.md) или [ClusterRoleBinding](./bindings.md)).

## Основные концепции

### Место RBAC в архитектуре Kubernetes

Каждый запрос к API-серверу проходит через три основных этапа контроля:

1. **Аутентификация (Authentication):** Идентификация субъекта. Kubernetes не хранит объекты "пользователь", а доверяет внешним источникам (сертификаты, токены, OIDC). Подробнее см. в [Субъекты доступа](./subjects.md).
2. **Авторизация (Authorization):** Проверка прав. Модуль RBAC анализирует запрос на основе установленных правил.
3. **Контроль допуска (Admission Control):** Дополнительная логика (валидация, мутация), выполняемая после авторизации, но до записи в etcd.

**Цепочка авторизации (Authorization Modules):**
Запросы проверяются модулями последовательно (согласно параметру `--authorization-mode`). Типовой порядок:
`Node -> RBAC -> Webhook`

- **Node:** Проверяет права узлов (Kubelet).
- **RBAC:** Основной декларативный механизм.
- **Webhook:** Вызов внешней системы для принятия решения.
- **[ABAC](./abac.md):** Альтернативный/устаревший метод на основе атрибутов.

### Детальная настройка доступа к API Kubernetes

Детальная настройка включает реализацию точечных элементов управления для ограничения разрешений на основе конкретных ролей и требований к ресурсам.

**Алгоритм настройки:**
1. **Определение настраиваемых ролей:** Создание специфических ролей (`Role` или `ClusterRole`), инкапсулирующих минимально необходимые разрешения. Хотя K8s предоставляет встроенные роли, для безопасности рекомендуется определять кастомные.
2. **Выбор области действия:** Решите, должны ли права быть ограничены одним `Namespace` или действовать на уровне всего кластера.
3. **Создание привязок (Bindings):** Связывание ролей с конкретными субъектами (пользователями, группами или сервисными аккаунтами).

Подробные примеры манифестов и описания глаголов приведены в разделе **[Роли и ClusterRole](./roles.md)**.

### Модель разрешений

RBAC в Kubernetes является **аддитивным** (права суммируются) и работает по принципу **"закрытого мира"**: всё, что явно не разрешено — запрещено. Запрещающие правила (deny) отсутствуют.

Логика доступа строится на трёх уровнях:

- **Что?** — ресурсы (pods, secrets, nodes) и субресурсы (pods/log, pods/exec).
- **Действие?** — глаголы (get, list, watch, create, update, patch, delete).
- **Где?** — пространство имён (Namespace) или уровень всего кластера.

### Основные объекты RBAC

| Объект | Уровень | Назначение |
|--------|---------|------------|
| [Role](./roles.md) | Пространство имён | Права на ресурсы внутри одного namespace. |
| [ClusterRole](./roles.md) | Кластер | Права на кластерные ресурсы (nodes, PV) или все namespace одновременно. |
| [RoleBinding](./bindings.md) | Пространство имён | Привязка Role или ClusterRole к субъекту в конкретном namespace. |
| [ClusterRoleBinding](./bindings.md) | Кластер | Глобальная привязка ClusterRole к субъекту на весь кластер. |

#### Субресурсы (Subresources)

Для тонкого управления доступом к внутренним функциям ресурсов используются субресурсы:

- **`pods/log`** — чтение логов.
- **`pods/exec`** — выполнение команд в контейнере.
- **`pods/portforward`** — проброс портов.
- **`nodes/metrics`** — сбор метрик с узла.

В правилах RBAC они указываются через косую черту: `resources: ["pods/exec"]`.

## Практические сценарии

### Проверка прав доступа через CLI

Для быстрой проверки разрешений используется команда `kubectl auth can-i`.

```bash
# Могу ли я создавать деплойменты в текущем namespace?
kubectl auth can-i create deployments

# Есть ли у пользователя 'jane' права на чтение секретов в namespace 'dev'?
kubectl auth can-i list secrets --namespace dev --as jane

# Посмотреть список всех разрешений текущего контекста
kubectl auth can-i --list
```

### Изоляция ресурсов

Типовой сценарий — предоставление команде разработки доступа только к их проекту:
1. Создание **Namespace**.
2. Создание **Role** с нужными правами.
3. Создание **RoleBinding** для группы пользователей или ServiceAccount.

Примеры манифестов и подробный разбор привязок приведены в разделе **[Практические сценарии — Bindings](./bindings.md)**.

## Дополнительная информация

### Безопасность и Hardening

#### Эволюция токенов ServiceAccount
Для повышения безопасности в новых версиях Kubernetes механизмы токенов были пересмотрены:

- **Bound Service Account Tokens (v1.24+):** Токены теперь имеют ограниченный срок жизни (TTL), привязаны к конкретному поду и не хранятся в `Secret` в открытом виде.
- **Node-Bound Tokens (v1.31+):** Новая возможность привязки токена к ноде. При удалении или компрометации ноды все её токены аннулируются.

#### Переход от PSP к PSA (v1.25+)
С удалением **PodSecurityPolicy (PSP)** в версии 1.25, механизм авторизации безопасности подов изменился:
- Глагол `use` для политик больше не используется.
- Вместо этого применяется **Pod Security Admission (PSA)**, работающий на уровне меток (labels) пространства имён.
- Права на изменение меток namespace теперь являются критически важными с точки зрения безопасности.

### Критические риски (Attack Vectors)

| Риск | Описание |
|------|----------|
| **`system:masters`** | Группа суперпользователей, обходящая все проверки RBAC. Не используйте её для личных учетных записей. |
| **Escalation/Bind** | Глаголы `escalate` и `bind` позволяют пользователю изменять роли или создавать привязки, фактически повышая собственные права. |
| **Impersonation** | Глагол `impersonate` позволяет действовать от имени другого субъекта, что затрудняет аудит. |
| **Listing Secrets** | Право `list` на секреты в namespace эквивалентно праву чтения всех секретов. Используйте `get` с `resourceNames`. |

### Рекомендации (Best Practices)

1. **Принцип наименьших привилегий (PoLP):** Предоставляйте пользователям и приложениям только те разрешения, которые необходимы для выполнения их задач. Если приложению нужно только чтение, не давайте прав на изменение или удаление. Избегайте использования подстановочных знаков (`*`) в правилах.
2. **Изоляция:** Всегда предпочитайте `RoleBinding` вместо `ClusterRoleBinding` для ограничения области доступа.
3. **Автоматизация:** Используйте `automountServiceAccountToken: false` для подов, которым не нужен доступ к API.
4. **Аудит:** Включите **[Аудит событий API](../audit.md)** и регулярно проверяйте права доступа инструментами типа `rakkess` или `kubescape`.
