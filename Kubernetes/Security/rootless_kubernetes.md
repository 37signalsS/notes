# Rootless Kubernetes

**Актуально для:** Kubernetes 1.33+ (user namespaces включены по умолчанию), Podman 5.x / CRI-O 1.25+

## Определения

**Rootless Kubernetes** — режим развёртывания кластера, при котором все процессы узла (kubelet, CRI-рантайм, системные поды Control Plane) работают внутри пользовательского пространства имён (user namespace) и на хост-системе отображаются как процессы обычного непривилегированного пользователя. Даже получив `root` внутри контейнера, злоумышленник получает на хосте лишь права этого пользователя.

**Rootful Kubernetes** — обычный режим: все процессы узла работают от `root` хоста, UID 0 внутри контейнера совпадает с UID 0 хоста.

**User Namespace** — механизм ядра Linux, мапирующий UID/GID внутри пространства имён на другие UID/GID снаружи. Механика и требования: [User Namespaces в Pod](../Base/Pod/user_namespaces.md).

**«Двуликий Янус»** — метафора из доклада: в rootless-режиме процесс одновременно `root` внутри окружения (полный доступ к ядру внутри namespace) и обычный пользователь на хосте. В rootful-режиме Янус «одноликий»: root и там, и там.

**rootlesskit** — утилита проекта rootless-containers: создаёт user namespace и удерживает его живым для запуска множества команд; поддерживает copy-up файлов в окружение, сетевые драйверы и проброс портов. Удержание namespace после выхода запустившего процесса — та же задача, что и у pause-процесса Podman.

**unshare** — утилита util-linux для создания пространств имён; базовый примитив для ручного запуска окружения.

**slirp4netns** — сетевой стек в пространстве пользователя с NAT для rootless-контейнеров; исторический драйвер сети rootless-кластеров.

**policy.json** — файл политики доверия образов (`/etc/containers/policy.json`): определяет, какие образы и откуда разрешено загружать. Синтаксис: [containers-policy.json(5)](https://github.com/containers/image/blob/main/docs/containers-policy.json.5.md).

**lookaside (sigstore)** — хранилище подписей образов; адрес задаётся в `/etc/containers/registries.d/*.yaml`, оттуда рантайм загружает подписи для проверки. Синтаксис: [containers-registries.d(5)](https://github.com/containers/image/blob/main/docs/containers-registries.d.5.md).

**Trivy** — сканер уязвимостей образов, SBOM и конфигураций.

## Основные концепции

### Почему rootful Kubernetes опасен

В rootful-режиме все контейнеры запускаются от `root`, и UID 0 внутри контейнера совпадает с UID 0 хоста. Типичные вектора атак:

- **Запуск образа от root с монтированием хостовой ФС.** Контейнер с примонтированным `/` хоста: `rm -rf /` внутри контейнера уничтожает хост.
- **Повышение привилегий** (privilege escalation) через уязвимости ядра или рантайма.
- **Прямой доступ по SSH к узлам** — компрометация учётной записи даёт доступ ко всему узлу.
- **Ошибки настройки kubelet** и прочие недекларируемые возможности: чем больше фич, тем больше дыр.

Образ с обычным пользователем не решает проблему: нет гарантии, что UID 486 в образе не совпадёт с UID 486 на хосте — и тогда у злоумышленника снова полный доступ к файлам этого пользователя. Кроме того, UID в Dockerfile, превышающий разрядность, может привести к переполнению и превращению в 0 (root) — случай из практики докладчика: мониторинг показывал «образов от root нет», а такой образ запускался с правами root.

Ключевой тезис доклада: абсолютно защищённых программ не существует — в том числе программы, обеспечивающие работу Kubernetes. Единственный выход — перевести в rootless-режим и системные процессы узла: даже сломав kubelet, злоумышленник не должен получить возможность нарушить работу хост-системы.

### Rootless Kubernetes: весь узел в user namespace

Начиная с Kubernetes 1.33 user namespaces включены по умолчанию: даже контейнер, запущенный от `root`, может работать от другого пользователя на хосте. Внутри контейнера пользователь считает себя root — может запускать tcpdump, менять eBPF-программы, работать с ядром как root. В рамках всей системы он — обычный пользователь: удалить хостовые файлы у него не получится.

**Отличие от pod-level user namespaces.** Механизм `hostUsers: false` (см. [User Namespaces в Pod](../Base/Pod/user_namespaces.md)) изолирует отдельный Pod. Rootless Kubernetes идёт дальше: в user namespace помещается **весь узел** — kubelet, CRI-рантайм и все системные поды Kubernetes. В дереве процессов хоста все процессы Kubernetes находятся не в корне, а в окружении rootless-пользователя: внутри они считают себя root, а система видит их как обычного пользователя (в примере докладчика — UID 453).

### Механизм работы узла

Описанный в докладе подход (вендорно-нейтральный, реализуется своими силами):

1. **`unshare`** создаёт окружение пользователя: отдельное дерево процессов, группа пользователей, время, монтирования. Хост-система этого окружения не видит.
2. **`rootlesskit`** создаёт окружение для запуска множества команд: copy-up файлов (часть ФС пользователя передаётся в окружение, где с ней можно делать всё, что угодно, и никто, кроме владельца, этого не видит), сетевая поддержка, проброс портов.
3. **Обёртка над `kubeadm`.** Часть команд из user-namespace-окружения помещается в отдельный каталог, который добавляется в `PATH`. Обёртка принимает два параметра: `init` (мастер) и `join` (дополнительные узлы). Она запускает shell из своего каталога → rootlesskit-окружение → системный `kubeadm`.
4. **Переопределение `PATH`.** Внутри окружения `systemd`/`systemctl` запускаются из каталога обёрток, а не системные — за счёт этого все сервисы Kubernetes разворачиваются внутри rootless-окружения.
5. **Результат.** `kubeadm init` создаёт мастер в rootless-режиме и выдаёт стандартные строки подключения для control-plane и worker-узлов; `kubeadm join` разворачивает остальные узлы. Пользователь и администратор не подозревают, что системные команды Kubernetes работают в rootless-режиме.

Эволюция подхода, описанная в докладе: первое поколение (март 2023) разворачивалось через docker compose на одном узле (kind, minikube и ранние user-namespace-решения на тот момент были непригодны для продакшна — всё работало на одном узле); второе поколение (сентябрь 2023) поддерживает `kubeadm` и многонодовые кластеры. Точная реализация обёрток — инженерная задача; в докладе описан принцип, а не готовые скрипты.

### Движки и политики доверия образов

**Почему Podman и CRI-O.** На момент доклада (2023) только Podman и CRI-O поддерживали политики доступа к образам (`policy.json` из библиотеки containers/image); Docker не поддерживал. Дополнительный аргумент: Podman daemonless — в Docker демон поднимается от root и клиенты обращаются к нему по TCP (опасно), а Podman работает от обычного пользователя без центрального демона.

**Политика reject-by-default.** В каталоге `/etc/containers/` задаётся политика: все транспорты запрещены, разрешена загрузка только из локального регистратора и только подписанная определённым пользователем. Транспорты `docker-archive`, `oci-archive`, `dir` (то есть `docker save/load`, `podman save/load` и развёртывание из архива) запрещены — взять архив образа и развернуть его не получится.

**Раздача ключей.** В файле `default` каталога `/etc/containers/registries.d/` указан URL, откуда узлы скачивают открытые ключи (хранилище подписей), чтобы движок CRI-O мог проверить правильность подписи образа.

**Разделение политик по пользователям.** Для пользователя, имеющего право работать с образами (image-maker), создаётся собственный каталог политик, где разрешено всё: создавать образы, модифицировать, делать дочерние. Все остальные работают с системным `policy.json`, где всё это запрещено. Для обычных пользователей дополнительно закрыта возможность создать себе такой же файл политик, как у image-maker.

### Классы пользователей и мониторинг

Три класса пользователей, описанные в докладе:

| Класс | Права |
| :--- | :--- |
| **Создатели образов** | Создание, модификация, подписание образов, дочерние образы, заливка в локальный регистратор. Доступа в интернет нет. |
| **Пользователи образов** | Только загрузка подписанных образов из локального регистратора. |
| **Администраторы** | Создают пользователей, но сами работают как обычные пользователи: не могут создавать и модифицировать образы. |

Инфраструктура: локальный регистратор образов, веб-сервер для раздачи политик и ключей на узлы, сканер уязвимостей Trivy. Мониторинг безопасности покрывает:

- **Сборку образов** — проверка Trivy: при обнаружении уязвимостей образ не строится.
- **Работу контейнеров** — появление лишнего в контейнерах (например, файлов в `/bin`) немедленно сообщается администратору.
- **API Kubernetes** — аудит попыток взлома через API.
- **Неизменность политик** — контроль, что `policy.json` и ключи не менялись.

## Практические сценарии

### Сценарий 1: примитивы user namespace

```bash
# Проверка выделенных диапазонов UID/GID
grep $USER /etc/subuid
# → user:100000:65536

# Создание user namespace: текущий пользователь мапится на root внутри
unshare --user --map-root-user --mount --pid --fork --mount-proc bash
```

Внутри окружения:
```bash
id
# → uid=0(root) gid=0(root) groups=0(root)
```

На хосте тот же процесс виден как обычный пользователь. Удаление хостовых файлов изнутри окружения невозможно — ядро применяет права реального UID.

### Сценарий 2: политика доверия образов (reject-by-default)

```json
// /etc/containers/policy.json
{
  "default": [{"type": "reject"}],
  "transports": {
    "docker": {
      "registry.local": [
        {
          "type": "signedBy",
          "keyType": "GPGKeys",
          "keyPath": "/etc/pki/containers/registry-local-pubkey.gpg"
        }
      ]
    }
  }
}
```

Логика: `default: reject` — всё, что явно не разрешено, запрещено. Указан только `docker`-транспорт для `registry.local` (placeholder — адрес локального регистратора) с требованием подписи GPG-ключом. Транспорты `dir`, `oci`, `docker-archive` не указаны и потому запрещены.

```yaml
# /etc/containers/registries.d/default.yaml
default-docker:
  lookaside: http://registry.local:8000
```

Адрес хранилища подписей: cri-o/podman загружают оттуда подписи и проверяют их ключом из `policy.json`.

Управление политикой через CLI Podman:
```bash
# Просмотр действующей политики
podman image trust show --raw

# Установка политики reject-by-default (от root)
sudo podman image trust set --signature-policy /etc/containers/policy.json --type reject default
```

### Сценарий 3: развёртывание кластера через обёртку kubeadm

Последовательность (принцип из доклада; реализация обёрток — инженерная задача):

1. Установить пакеты: Podman/CRI-O, rootlesskit, slirp4netns, `uidmap` (утилиты `newuidmap`/`newgidmap`), Trivy.
2. Создать каталог обёрток (например, `/opt/rootless-k8s/bin`) и добавить его в `PATH` перед системным.
3. На мастере: `kubeadm init` (обёртка) — создаёт master в rootless-режиме, выдаёт строки `kubeadm join` для control-plane и worker-узлов.
4. На остальных узлах: скопировать политики через веб-сервер, затем `kubeadm join` (обёртка) — разворачивает узел в rootless-режиме.
5. Проверка: дерево процессов хоста показывает процессы Kubernetes от обычного пользователя, а не от root.

Параметризация (переменные/файл переменных): версия Kubernetes, регистратор образов (стандартный registry.k8s.io, локальный регистратор или произвольный набор образов). Без локального регистратора и классов пользователей развёртывание совпадает с обычным `kubeadm`-развёртыванием — отличие только в добавлении каталога обёрток в `PATH`.

Для offline-медиа: набор начальных образов Kubernetes (3–4 ГБ) удаётся сжать до ~200 МБ через squashfs-архив с сжатием (подход из доклада), что позволяет поместить образы на ISO.

### Сценарий 4: мониторинг безопасности

```bash
# Сканирование образа перед попаданием в регистратор
trivy image registry.local/app:1.0
# → при обнаружении уязвимостей образ не должен строиться/публиковаться
```

Дополнительно (по описанию в докладе): контроль целостности контейнеров (изменение содержимого, например в `/bin`), аудит API Kubernetes, контроль неизменности `policy.json` и ключей.

## Типичные проблемы и ограничения

### Сеть: slirp4netns и NAT

Для создания сети внутри rootless-кластера используется slirp4netns, который применяет трансляцию адресов (NAT). Последствие (по опыту докладчика): когда пакет переходит на другой узел, его IP-адрес меняется на локальный; BGP-протоколы (Cilium, Calico) должны знать, куда пошёл пакет, но считают, что он пришёл локально — и «замирают». Flannel работает устойчиво. Проблему планируется решать (на момент доклада — открытая задача).

### etcd

etcd целесообразно запускать тоже в rootless-режиме: иначе его могут взломать и нарушить работу системы. Вынос etcd на отдельные узлы возможен, но в описанном проекте не реализован из-за сжатых сроков.

### Гетерогенный кластер

Часть узлов может работать в rootful-режиме, часть — в rootless (по опыту докладчика).

### Cluster API

Из коробки Cluster API с rootless доступен в сертифицированных (платных) дистрибутивах; в открытых дистрибутивах реализуется самостоятельно (по опыту докладчика).

### Отладка

Rootless-узел сложнее отлаживать. SSH на узлах — вектор атаки, поэтому в докладе рекомендуют его отключение; при shell-less подходе (ОС без shell/SSH, управление через API) логи узла получаются через API-утилиту — см. [Talos Linux](../Installation/local_cluster_with_talosctl.md).

## Рекомендации

1. **Все системные процессы узла — в rootless-окружении.** Изоляция части подов (`hostUsers: false`) не заменяет rootless-узел: kubelet и CRI-рантайм остаются от root.
2. **Reject-by-default для образов.** Только подписанные образы из локального регистратора; транспорты архивов и локальных каталогов запрещены.
3. **Сканирование перед публикацией.** Trivy проверяет образ до попадания в регистратор.
4. **Разделение классов пользователей** (создатели/пользователи образов/администраторы) и запрет обычным пользователям создавать собственные файлы политик.
5. **Мониторинг целостности** контейнеров и неизменности политик; аудит API.
6. **Sizing диапазонов UID.** С Kubernetes 1.33 количество ID на Pod задаётся в `KubeletConfiguration` (кратно 65536, по умолчанию 65536) — планируйте `/etc/subuid`/`/etc/subgid` с запасом:
   ```yaml
   apiVersion: kubelet.config.k8s.io/v1beta1
   kind: KubeletConfiguration
   userNamespaces:
     idsPerPod: 1048576
   ```
7. **Минимальные привилегии, read-only rootfs, seccomp/AppArmor** — см. [Безопасность контейнерного рантайма](./container_runtime_security.md) и [Rootless режим в Podman](../../Podman/podman_rootless.md).
