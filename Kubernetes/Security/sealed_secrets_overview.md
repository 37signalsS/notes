# Sealed Secrets

## Определения

Sealed Secrets — это инструмент для Kubernetes от Bitnami, предназначенный для безопасного хранения секретов (паролей, токенов, ключей) в публичных Git-репозиториях. Он решает проблему хранения стандартных Secrets Kubernetes, которые по умолчанию закодированы в base64, но не зашифрованы. Основная идея заключается в том, что секреты шифруются с помощью асимметричного шифрования. Расшифровать их может только контроллер, работающий в целевом кластере Kubernetes.

## Основные концепции

Sealed Secrets использует асимметричное шифрование (public-key cryptography).

### Архитектура

Sealed Secrets состоит из двух основных компонентов:

1.  Контроллер (Controller):
    *   Работает в кластере Kubernetes.
    *   Владеет парой ключей (приватным и публичным). При первом запуске он генерирует пару ключей.
    *   Приватный ключ хранится только внутри кластера в etcd и недоступен извне.
    *   Публичный ключ используется для шифрования секретов и может быть безопасно выгружен.
    *   Следит за созданием новых ресурсов SealedSecret.
    *   Расшифровывает SealedSecret и создает стандартный ресурс Secret Kubernetes.

2.  Утилита командной строки (`kubeseal`):
    *   Используется разработчиками и CI/CD системами для шифрования.
    *   Получает открытый ключ у контроллера для шифрования.
    *   Преобразует стандартные Secret в кастомный ресурс SealedSecret.

### Процесс работы (Workflow)

1.  Создание и шифрование: Разработчик создает стандартный Secret (например, в YAML) и шифрует его с помощью утилиты kubeseal и публичного ключа.
2.  Коммит в Git: Зашифрованный SealedSecret безопасно коммитится в Git-репозиторий, так как он не содержит конфиденциальной информации в открытом виде.
3.  Развертывание: SealedSecret применяется в кластере через kubectl apply или инструменты GitOps (ArgoCD, Flux).
4.  Расшифровка: Контроллер в кластере обнаруживает новый SealedSecret, расшифровывает его своим закрытым ключом и создает на его основе обычный Secret.
5.  Использование: Поды используют созданный Secret как обычно (через переменные окружения или тома).

## Практические сценарии

### Установка контроллера

Контроллер Sealed Secrets обычно устанавливается в кластер с помощью Helm или манифестов YAML.

# Установка с помощью Helm 3
helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
helm install sealed-secrets/sealed-secrets --name-template sealed-secrets -n kube-system

### Шифрование секрета

Создание SealedSecret из стандартного секрета Kubernetes.

1.  Создать обычный секрет в YAML (my-secret.yaml):

        # my-secret.yaml
    apiVersion: v1
    kind: Secret
    metadata:
      name: mysecret
      namespace: default
    data:
      password: "SuperSecretPassword" # Перед шифрованием кодируется в base64
    

    Или создать "на лету":

        kubectl create secret generic my-secret --from-literal=password='supersecret' --dry-run=client -o yaml
    

2.  Зашифровать с помощью `kubeseal`:

    Утилита kubeseal "запечатывает" секрет, превращая его в SealedSecret.

        # Установить kubeseal (пример для macOS)
    brew install kubeseal

    # Зашифровать из файла, результат направить в stdout
    kubeseal < my-secret.yaml --format yaml

    # Зашифровать из файла и сохранить в новый файл
    kubeseal < my-secret.yaml --format yaml > my-sealed-secret.yaml

    # Зашифровать секрет, созданный "на лету", и сохранить в файл
    kubectl create secret generic my-secret --from-literal=password='supersecret' --dry-run=client -o yaml | kubeseal --controller-name <controller-name> --controller-namespace <namespace> > my-sealed-secret.yaml
    
    Полученный my-sealed-secret.yaml можно безопасно коммитить в Git.

### Варианты использования

*   GitOps: Хранение всей конфигурации Kubernetes, включая секреты, в Git.
*   CI/CD: Автоматизация процесса обновления секретов без необходимости предоставления прямого доступа к кластеру для их создания или изменения.
*   Безопасность: Снижение риска утечки учетных данных, так как в репозиториях хранятся только зашифрованные данные. ## Дополнительная информация

### Преимущества

*   Безопасное хранение в Git: Устраняет необходимость хранить secrets.yaml локально или в отдельных зашифрованных хранилищах.
*   Декларативность: Управление секретами становится частью декларативной конфигурации приложения.
*   Аудит и версионирование: Все изменения в секретах отслеживаются через систему контроля версий.
*   Простота использования: Прозрачно интегрируется с существующими рабочими процессами Kubernetes.

### Продвинутые детали

#### Ротация ключей

Приватный ключ контроллера по умолчанию не имеет срока действия. Однако его можно и нужно периодически ротировать для повышения безопасности. Новая пара ключей может быть сгенерирована контроллером, и в течение некоторого времени он будет способен расшифровывать секреты, зашифрованные как старым, так и новым публичным ключом.

#### Область действия (Scope)

По умолчанию SealedSecret может быть расшифрован только в том же namespace, в котором он был создан. Это предотвращает случайное или намеренное использование секрета в другом пространстве имен. Область действия можно изменить с помощью аннотаций:
- sealedsecrets.bitnami.com/namespace-wide: "true": Секрет будет доступен в любом namespace.
- sealedsecrets.bitnami.com/cluster-wide: "true": Секрет будет доступен во всем кластере.
