# Sealed Secrets

## Определения

Sealed Secrets — это инструмент для Kubernetes от Bitnami, предназначенный для безопасного хранения секретов (паролей, токенов, ключей) в публичных Git-репозиториях. Он решает проблему хранения стандартных Secrets Kubernetes, которые по умолчанию закодированы в base64, но не зашифрованы. Основная идея заключается в том, что секреты шифруются с помощью асимметричного шифрования. Расшифровать их может только контроллер, работающий в целевом кластере Kubernetes.

## Основные концепции

Sealed Secrets использует асимметричное шифрование (public-key cryptography).

### Архитектура и криптографическая схема

Sealed Secrets состоит из двух основных компонентов:

1.  **Контроллер (Controller):**
    *   Работает в кластере Kubernetes.
    *   При первом запуске он генерирует ключевую пару (приватный и публичный ключ). Приватный ключ хранится в виде стандартного секрета Kubernetes и доступен только контроллеру.
    *   Публичный ключ (в виде сертификата) используется для шифрования и может быть безопасно выгружен.
    *   Следит за созданием новых ресурсов `SealedSecret`.
    *   Обнаружив новый `SealedSecret`, он расшифровывает его своим приватным ключом и создает/обновляет стандартный ресурс `Secret`.

2.  **Утилита командной строки (`kubeseal`):**
    *   Используется разработчиками и CI/CD системами.
    *   Получает публичный ключ контроллера для шифрования.
    *   Преобразует стандартные `Secret` в кастомный ресурс `SealedSecret`.

**Криптографическая схема:** `kubeseal` использует гибридную схему шифрования для обеспечения конфиденциальности и целостности:
1.  Для каждого значения в секрете генерируется случайный симметричный ключ.
2.  Данные шифруются этим ключом с использованием алгоритма AES-GCM.
3.  Сам симметричный ключ шифруется с помощью асимметричного алгоритма RSA-OAEP, используя публичный ключ контроллера.
4.  В зашифрованный блок также включается контекст (имя и namespace секрета) для строгой привязки.

Эта схема гарантирует, что расшифровать данные может только контроллер, владеющий соответствующим приватным ключом.

### Процесс работы (Workflow)

1.  **Создание и шифрование:** Разработчик создает стандартный Secret (например, в YAML) и шифрует его с помощью утилиты `kubeseal` и публичного ключа контроллера.
2.  **Коммит в Git:** Зашифрованный `SealedSecret` безопасно коммитится в Git-репозиторий, так как он не содержит конфиденциальной информации в открытом виде.
3.  **Развертывание:** `SealedSecret` применяется в кластере через `kubectl apply` или инструменты GitOps (ArgoCD, Flux).
4.  **Расшифровка:** Контроллер в кластере обнаруживает новый `SealedSecret`, расшифровывает его своим закрытым ключом и создает на его основе обычный `Secret`.
5.  **Использование:** Поды используют созданный `Secret` как обычно (через переменные окружения или тома).

## Практические сценарии

### Установка контроллера

Контроллер Sealed Secrets обычно устанавливается в кластер с помощью Helm или манифестов YAML.

```
# Установка с помощью Helm 3
helm repo add sealed-secrets https://bitnami-labs.github.io/sealed-secrets
helm install sealed-secrets/sealed-secrets --name-template sealed-secrets -n kube-system
```

### Шифрование секрета

Создание `SealedSecret` из стандартного секрета Kubernetes.

1.  Создать обычный секрет "на лету" и передать его `kubeseal` для шифрования:

    ```bash
    # Получить публичный ключ контроллера (сертификат)
    kubeseal --controller-name=sealed-secrets --controller-namespace=kube-system --fetch-cert > pubcert.pem

    # Создать секрет и сразу зашифровать его
    kubectl create secret generic my-secret --from-literal=password='supersecret' --dry-run=client -o yaml | \
      kubeseal --cert pubcert.pem --format yaml > my-sealed-secret.yaml
    ```

2.  Полученный `my-sealed-secret.yaml` можно безопасно коммитить в Git.
    ```yaml
    apiVersion: bitnami.com/v1alpha1
    kind: SealedSecret
    metadata:
      name: my-secret
      namespace: default
    spec:
      encryptedData:
        password: Ag...
      template:
        metadata:
          name: my-secret
          namespace: default
    ```

### Управление доступом через RBAC

Для реализации принципа наименьших привилегий можно ограничить права CI/CD систем только созданием `SealedSecret` в определенном namespace, запретив им чтение обычных `Secret`.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: ci-sealed-writer
  namespace: app
rules:
- apiGroups: ["bitnami.com"]
  resources: ["sealedsecrets"]
  verbs: ["create"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: ci-sealed-writer
  namespace: app
subjects:
- kind: ServiceAccount
  name: ci-runner
  namespace: app
roleRef:
  kind: Role
  name: ci-sealed-writer
  apiGroup: rbac.authorization.k8s.io
```

### Варианты использования

*   **GitOps:** Хранение всей конфигурации Kubernetes, включая секреты, в Git.
*   **CI/CD:** Автоматизация процесса обновления секретов без необходимости предоставления прямого доступа к кластеру для их создания или изменения.
*   **Безопасность:** Снижение риска утечки учетных данных, так как в репозиториях хранятся только зашифрованные данные.

## Дополнительная информация

### Преимущества

*   **Безопасное хранение в Git:** Устраняет необходимость хранить `secrets.yaml` локально или в отдельных зашифрованных хранилищах.
*   **Декларативность:** Управление секретами становится частью декларативной конфигурации приложения.
*   **Аудит и версионирование:** Все изменения в секретах отслеживаются через систему контроля версий.
*   **Простота использования:** Прозрачно интегрируется с существующими рабочими процессами Kubernetes.

### Области шифрования (Scope)

По умолчанию `SealedSecret` привязан к имени и пространству имен. Это поведение можно изменить с помощью опции `--scope` у `kubeseal`.

| Режим | Привязка | Переносимость | Назначение |
| :--- | :--- | :--- | :--- |
| `strict` (по умолчанию) | имя + namespace | Нет | Максимальная изоляция, предотвращает "replay attack" в другой цели. |
| `namespace-wide` | Только namespace | Ограниченная | Упрощает переименование секрета внутри одного namespace. |
| `cluster-wide` | Нет | Высокая | Редко используемый. Позволяет создать секрет в любом namespace. |

### Ротация ключей

Контроллер может периодически ротировать ключи шифрования, сохраняя старые приватные ключи для обратной совместимости. Это позволяет расшифровывать секреты, созданные ранее. Для обновления секрета на новый публичный ключ используется команда:
```bash
kubeseal --re-encrypt < old.sealed.yaml > new.sealed.yaml
```

### Модель угроз и ограничения

*   **Компрометация приватного ключа контроллера:** Это самая серьезная угроза. Получив доступ к приватному ключу (хранящемуся в `Secret` в кластере), злоумышленник сможет расшифровать все `SealedSecret`, зашифрованные соответствующим публичным ключом. Защита доступа к etcd и RBAC-политики в кластере критически важны.
*   **Перенос между кластерами:** `SealedSecret`, созданный для одного кластера, не может быть расшифрован в другом, так как у них разные пары ключей. Для переноса требуется вручную экспортировать и импортировать ключевую пару, что не рекомендуется.
*   **Дополнительные меры:** Sealed Secrets не отменяют необходимость в RBAC и защите etcd at-rest. Это комплементарные уровни безопасности.
