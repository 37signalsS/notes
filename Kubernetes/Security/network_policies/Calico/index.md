# Calico: Глобальные политики, HostEndpoint и расширенная безопасность

**Calico** — это CNI-плагин и распределенный файрвол для Kubernetes, расширяющий стандартные сетевые политики за счёт управления трафиком на уровнях узлов (host protection), всего кластера (GlobalNetworkPolicy) и внешних сетей. Поддерживает высокопроизводительные механизмы обработки трафика (eBPF, nftables, VPP) и интеграцию с физической сетевой инфраструктурой через BGP.

Calico не является частью ядра Kubernetes — он реализует как стандартный API `networking.k8s.io/v1` (NetworkPolicy), так и собственный CRD API (`projectcalico.org/v3`) для расширенных возможностей: глобальных политик, защиты узлов, IPAM, шифрования и BGP-маршрутизации.

> Основная документация: [NetworkPolicy: Сетевая безопасность](../../network_policies.md)
> Установка Calico в HA кластере: [Установка CNI](../../../Installation/HA_Cluster_Bare_Metal/cni_installation.md)

## Определения

### Компоненты Calico

**Felix** — основной агент Calico (DaemonSet), работающий на каждом узле кластера. Он отвечает за программирование маршрутов, ACL (правил фильтрации) и управление сетевыми интерфейсами. Felix транслирует политики в правила конкретного data plane (iptables, eBPF, nftables или VPP). Экспортирует метрики Prometheus (по умолчанию порт 9091), включая `felix_active_local_endpoints`, `felix_execution_time_seconds` и другие.

**Typha** — промежуточный прокси-агент (fan-out proxy), который используется в крупных кластерах (обычно более 50 узлов). Felix подключается к Typha вместо прямого обращения к Kubernetes API, что значительно снижает нагрузку на Control Plane при обновлении политик или состоянии подов. Один экземпляр Typha способен обслуживать до 200 узлов.

**BIRD (BGP)** — встроенный демон маршрутизации, используемый Calico для распространения маршрутов между узлами по протоколу BGP. Позволяет кластеру работать без оверлейных сетей (например, VXLAN) при наличии поддержки BGP в физической инфраструктуре. BIRD конфигурируется через демон **Confd**, который мониторит изменения конфигурации Calico и обновляет файлы конфигурации BIRD.

**Confd** — служба, которая мониторит изменения в конфигурации Calico (через etcd или Kubernetes API) и динамически обновляет конфигурационные файлы BIRD при изменении маршрутизационных политик.

### Ресурсы Calico (CRD API: projectcalico.org/v3)

**HostEndpoint** — ресурс Calico, представляющий сетевой интерфейс физического или виртуального узла. Позволяет применять политики безопасности к трафику самого хоста, защищая его от внешних угроз и контролируя административный доступ (SSH, API). Каждый HostEndpoint привязывается к конкретному сетевому интерфейсу (`interfaceName`) и узлу (`node`).

**GlobalNetworkPolicy** — кластерная политика, область действия которой не ограничена одним Namespace. Она применяется ко всем подам и узлам кластера, подходящим под селектор. Поддерживает типы `Ingress`, `Egress` и комбинации, а также параметры `preDNAT`, `applyOnForward`, `order` и `types`.

**GlobalNetworkSet** — глобальный набор IP-адресов или CIDR-диапазонов, к которому можно обращаться из политик по меткам. Удобен для группировки внешних ресурсов (например, "доверенные офисные сети", "публичные облака"). Метки GlobalNetworkSet используются как `source` или `destination` в правилах политик.

**IPPool** — пул IP-адресов, из которого Calico выделяет адреса подам. Каждый пул определяет CIDR-диапазон, режим инкапсуляции (VXLAN, IPIP, None) и параметр `natOutgoing` для контроля исходящего NAT.

**FelixConfiguration** — ресурс для настройки параметров агента Felix на глобальном или именованном уровне. Включает настройки `prometheusMetricsEnabled`, `failsafeInboundHostPorts`, `failsafeOutboundHostPorts`, `wireguardEnabled` и другие.

**BGPConfiguration** — ресурс для настройки параметров BGP-сессий Calico: AS-номер кластера, интервалы объявления маршрутов, логирование.

### Протоколы и механизмы

**WireGuard** — современный протокол шифрования, интегрированный в Calico для обеспечения безопасной передачи трафика между подами и узлами с минимальными накладными расходами на производительность. В режиме eBPF поддерживается также шифрование трафика между самими хостами (Host-to-Host).

**BGP (Border Gateway Protocol)** — протокол маршрутизации, используемый Calico для распространения маршрутов к подам между узлами. Поддерживает eBGP-пиринг с физическими маршрутизаторами для интеграции кластера в существующую сеть (routed-модель).

## Архитектура и компоненты

Архитектура Calico построена на модульном принципе для обеспечения масштабируемости до тысяч узлов:

```
┌─────────────────────────────────────────────────────────────────┐
│                     Kubernetes API / etcd                        │
│            (хранилище состояний и конфигураций)                  │
└───────────────┬──────────────────────────┬──────────────────────┘
                │                          │
        ┌───────▼───────┐          ┌───────▼───────┐
        │   Typha       │          │  Confd        │
        │ (fan-out proxy│          │ (конфигурация │
        │  для 50+ узл.)│          │  BIRD)        │
        └───────┬───────┘          └───────┬───────┘
                │                          │
    ┌───────────▼───────────┐    ┌─────────▼─────────┐
    │   Felix (на каждом    │    │   BIRD (BGP        │
    │   узле кластера)      │    │   маршрутизатор)   │
    │                       │    │                    │
    │  - ACL / правила      │    │  - Обмен маршрутами│
    │  - Маршруты           │    │  - Пиринг с        │
    │  - Data plane         │    │    физ. сетью       │
    │    (iptables/eBPF/    │    │                    │
    │     nftables/VPP)     │    │                    │
    └───────────────────────┘    └────────────────────┘
```

1. **Хранилище данных (Datastore)**: Calico может использовать `etcd` напрямую или работать в режиме `Kubernetes API datastore` (рекомендуется для современных версий). Режим Kubernetes API позволяет использовать стандартные RBAC и не требует отдельного кластера etcd.
2. **Felix**: Инсталлирует правила фильтрации в ядро Linux. Работает как DaemonSet, обрабатывая трафик каждого узла.
3. **BIRD (BGP Client)**: Отвечает за обмен маршрутами между узлами. В режиме VXLAN/IPIP может быть отключен, так как инкапсуляция обеспечивает связность без BGP.
4. **Confd**: Служба, которая мониторит изменения в конфигурации Calico и обновляет конфигурационные файлы BIRD.
5. **Typha**: Опциональный компонент для горизонтального масштабирования доступа к API. Рекомендуется для кластеров с числом узлов более 50.

## Основные концепции

### Механизмы обработки трафика (Data Planes)

Calico поддерживает несколько режимов работы, выбираемых в зависимости от требований к производительности и версии ядра:

1. **iptables**: Классический режим, обеспечивающий максимальную совместимость. Использует стандартные цепочки Linux (PREROUTING, FORWARD, POSTROUTING) для фильтрации. При большом количестве политик (>1000) производительность снижается из-за линейного перебора правил (O(N)).
2. **eBPF**: Высокопроизводительный режим (Kernel 5.3+). Позволяет полностью заменить `kube-proxy`, снижает нагрузку на CPU, обеспечивает нативное сохранение Source IP и поддерживает DSR (Direct Server Return). Поиск правил через хэш-таблицы за O(1). Требует смонтированной BPF filesystem (`/sys/fs/bpf`).
3. **nftables**: Современная альтернатива iptables (введена в Calico 3.29, используется по умолчанию с v3.29+). Обеспечивает лучшую производительность и совместимость с современными дистрибутивами Linux (RHEL 9, Debian 12+).
4. **VPP (Vector Packet Processing)**: Режим для сверхвысоких нагрузок (телеком), обеспечивающий обработку пакетов в User Space. Пакеты обрабатываются группами (векторами) для максимальной пропускной способности.

> Сравнение data plane: [CNI: Сравнение реализаций NetworkPolicy](../../../Networking/Network/NetworkPolicy/cni_implementation.md)

### Сетевые режимы (Network Modes) и инкапсуляция

Calico определяет, как трафик между подами доставляется через физическую сеть. Выбор режима зависит от топологии сети и требований к производительности:

| Режим | Инкапсуляция | Описание | Производительность | Требования |
| :--- | :--- | :--- | :--- | :--- |
| **VXLAN** (по умолчанию) | VXLAN (50 байт overhead) | Универсальный overlay-режим. Работает в любой L2/L3 сети. | Средняя | Нет специальных требований |
| **VXLANCrossSubnet** | VXLAN только между подсетями | Оптимизация: внутри одной подсети трафик маршрутизируется напрямую, VXLAN используется только для межподсетевого трафика. | Высокая | Поддержка маршрутизации между подсетями |
| **IPIP** | IP-in-IP (20 байт overhead) | Чуть выше производительность, чем VXLAN, но может блокироваться некоторыми сетевыми экранами и файрволами. | Средне-Высокая | Поддержка IPIP на маршрутизаторах |
| **IPIPCrossSubnet** | IPIP только между подсетями | Аналог VXLANCrossSubnet, но с IPIP-инкапсуляцией. | Высокая | Поддержка IPIP |
| **None (BGP)** | Без инкапсуляции | Максимальная производительность. Поды получают маршрутизируемые IP в физической сети. Требует BGP-пиринга с коммутаторами (Top-of-Rack). | Максимальная | BGP на физических маршрутизаторах |
| **VXLAN mesh** | VXLAN между всеми узлами | Полный mesh без BGP. Подходит для сред без BGP-поддержки. | Средняя | Нет |

> Подробнее: [Режимы инкапсуляции в HA кластере](../../../Installation/HA_Cluster_Bare_Metal/cni_installation.md)

### IPAM (IP Address Management)

Calico реализует собственную систему управления IP-адресами, отличающуюся от стандартного host-local IPAM:

**Block-Based IPAM** — основной механизм Calico, при котором узлам выделяются не фиксированные подсети, а динамические блоки адресов (обычно `/26`, до 64 адресов в блоке). Это позволяет более эффективно использовать адресное пространство в разреженных кластерах — узлы получают ровно столько адресов, сколько им необходимо, а не целую подсеть.

**Основные компоненты IPAM:**
- **IPPool**: Определяет CIDR-диапазон, режим инкапсуляции и параметр `natOutgoing`. Управляет выделением адресов подам.
- **Block**: Динамический блок адресов (обычно `/26`), выделяемый конкретному узлу. Блоки перераспределяются при изменении нагрузки.
- **Affinity**: Привязка пула к конкретному узлу или namespace (опционально).

**Параметры IPPool:**
- `cidr`: Диапазон IP-адресов (например, `10.244.0.0/16`).
- `blockSize`: Размер блока по умолчанию `/26` (64 адреса).
- `encapsulation`: Режим инкапсуляции (`VXLAN`, `IPIPCrossSubnet`, `None`).
- `natOutgoing`: Включает NAT для исходящего трафика из пула (по умолчанию `Enabled`).

> Детали IPAM: [IPAM в Kubernetes](../../../Networking/Network/CNI/ipam.md)

### Приоритеты, иерархия и Tiers

В отличие от стандартных NetworkPolicy Kubernetes, Calico предоставляет продвинутые механизмы управления порядком правил:

*   **Order**: Поле, определяющее приоритет (целое число от 1 до 10000). Чем ниже значение, тем выше приоритет. Политики с одинаковым приоритетом применяются в произвольном порядке.
*   **Policy Tiers**: Группировка политик по уровням (например, `security`, `platform`, `application`). Политики в уровне `security` всегда оцениваются раньше, чем в `application`, что позволяет администраторам задавать глобальные "гарды" (guardrails), которые нельзя переопределить на уровне приложения.
*   **Admin Network Policy (ANP)**: Поддержка стандартного Kubernetes API (v1alpha1+) для управления кластерными политиками безопасности с четким разделением ролей. ANP имеет приоритет над стандартными NetworkPolicy.

### Расширенные селекторы

*   **ServiceAccount**: Выбор подов на основе связанного с ними ServiceAccount. Это обеспечивает identity-based безопасность, не зависящую от нестабильных IP-адресов или меток.
*   **Wildcards**: Поддержка подстановочных знаков (`*`) в метках для масштабного фильтрования.
*   **Host Selection**: Применение политик к узлам на основе меток (например, `kubernetes.io/hostname` или кастомных меток ролей).

### Фильтрация до NAT (preDNAT)

При использовании `HostEndpoint` Calico позволяет фильтровать трафик до того, как Kubernetes применит трансляцию адресов (DNAT) для NodePort или LoadBalancer. Это критически важно для защиты сервисов, открытых наружу, так как позволяет блокировать трафик на основе реальных внешних IP-адресов, а не внутренних адресов подов.

| Параметр | Описание | Когда использовать |
| :--- | :--- | :--- |
| `preDNAT: true` | Политика применяется в цепочке PREROUTING, до DNAT. | Защита NodePort и LoadBalancer сервисов |
| `applyOnForward: true` | Применяется к транзитному трафику, проходящему через узел (routing). | Защита узла как маршрутизатора |

### Безопасные порты (Failsafe Ports)

Для предотвращения случайной самоблокировки узла (lockout) Calico по умолчанию держит открытыми критические порты управления. Настройка осуществляется в ресурсе `FelixConfiguration`:

**Входящие (Inbound) — по умолчанию:**
*   SSH (22)
*   BGP (179)
*   Kubernetes API (6443)

**Исходящие (Outbound) — по умолчанию:**
*   DNS (53)
*   BGP (179)
*   etcd (2379-2380) — при использовании etcd datastore

> Изменение failsafe-портов требует осторожности: при неверной настройке узел может стать недоступным. Рекомендуется тестировать изменения в стейджинг-среде.

### Шифрование (WireGuard)

Calico позволяет включить прозрачное шифрование трафика между подами одной командой. В режиме eBPF поддерживается также шифрование трафика между самими хостами (Host-to-Host). Это обеспечивает соответствие требованиям безопасности (Zero Trust) без необходимости внедрения Service Mesh.

**Включение шифрования:**
```bash
# Включение WireGuard через calicoctl
calicoctl patch felixconfiguration default --patch '{"spec": {"wireguardEnabled": true}}'
```

**Проверка статуса:**
```bash
# Проверка наличия публичных ключей WireGuard у узлов
calicoctl get nodes -o wide
# → В выводе должен присутствовать столбец с публичным ключом WireGuard

# Метрики WireGuard в Prometheus
# wireguard_sent_bytes_total, wireguard_rcvd_bytes_total
```

> Шифрование и mTLS: [TLS и mTLS в Kubernetes](../../../Security/tls_and_mtls_in_kubernetes.md)

## Практические сценарии

Calico позволяет реализовать следующие стратегии безопасности:

*   **Защита периметра**: Блокировка несанкционированного доступа к узлам через `HostEndpoint` с фильтрацией до DNAT.
*   **Кластерный Default Deny**: Обеспечение изоляции всех пространств имен через `GlobalNetworkPolicy` с низким приоритетом.
*   **Микросегментация**: Тонкая настройка доступа между уровнями приложения через Tiered Policies и ServiceAccount-based селекторы.
*   **Аудит трафика**: Логирование заблокированных и разрешенных соединений через действие `Log` в политиках.

*Подробные примеры конфигураций: [Практические сценарии Calico](./scenarios.md)*

### Быстрый старт: Default Deny с разрешением DNS

При внедрении Zero-Trust необходимо сначала разрешить DNS-трафик, иначе поды потеряют способность разрешать имена сервисов:

```yaml
# 1. Разрешение DNS (высокий приоритет)
apiVersion: projectcalico.org/v3
kind: GlobalNetworkPolicy
metadata:
  name: allow-dns-global
spec:
  order: 50
  selector: "all()"
  types: [Egress]
  egress:
    - action: Allow
      protocol: UDP
      destination:
        selector: "k8s-app == 'kube-dns'"
        namespaceSelector: "kubernetes.io/metadata.name == 'kube-system'"
        ports: [53]
    - action: Allow
      protocol: TCP
      destination:
        selector: "k8s-app == 'kube-dns'"
        namespaceSelector: "kubernetes.io/metadata.name == 'kube-system'"
        ports: [53]
---
# 2. Default Deny (низкий приоритет)
apiVersion: projectcalico.org/v3
kind: GlobalNetworkPolicy
metadata:
  name: global-default-deny
spec:
  order: 2000
  selector: "all()"
  types: [Ingress, Egress]
  ingress:
    - action: Deny
  egress:
    - action: Deny
```

> Порядок применения критичен: сначала создаются разрешающие политики, затем запрещающие.

## Установка и первоначальная настройка

### Предварительные требования

- Kubernetes v1.24+ (рекомендуется v1.34.x — v1.35.x)
- Calico v3.28+ (рекомендуется v3.33.x — текущая стабильная ветка)
- Ядро Linux 4.15+ (для eBPF — 5.3+)
- Смонтированная BPF filesystem на всех узлах (для eBPF): `mount -t bpf bpf /sys/fs/bpf`
- Доступ к `kubectl` с правами администратора кластера

### Методы установки

| Метод | Плюсы | Минусы | Применение |
| :--- | :--- | :--- | :--- |
| **Tigera Operator** | Автоматическое обновление, управление через CRD, контроль жизненного цикла | Требует установки дополнительных CRD | Production, HA кластеры |
| **Manifest (Legacy)** | Простота (один файл), отсутствие лишних сущностей | Ручное управление обновлениями, сложность тонкой настройки | Test, Dev, малые кластеры |

### Установка через Tigera Operator (рекомендуется)

```bash
# 1. Установка оператора Tigera
kubectl create -f https://raw.githubusercontent.com/projectcalico/calico/v3.33.0/manifests/tigera-operator.yaml

# 2. Создание конфигурации установки
cat <<EOF > calico-config.yaml
apiVersion: operator.tigera.io/v1
kind: Installation
metadata:
  name: default
spec:
  calicoNetwork:
    ipPools:
    - blockSize: 26
      cidr: 100.64.0.0/16       # Замените на ваш Pod Network CIDR
      encapsulation: VXLANCrossSubnet
      natOutgoing: Enabled
      nodeSelector: all()
---
apiVersion: operator.tigera.io/v1
kind: APIServer
metadata:
  name: default
spec: {}
EOF

kubectl apply -f calico-config.yaml
```

> Полное руководство по установке: [Установка CNI в HA кластере](../../../Installation/HA_Cluster_Bare_Metal/cni_installation.md)

### Проверка работоспособности после установки

```bash
# Проверка статуса узлов (должны перейти в Ready)
kubectl get nodes

# Проверка подов Calico
kubectl get pods -n calico-system

# Проверка состояния IPAM
kubectl get ippools

# Тест связности между подами
kubectl run test-pod --image=busybox --restart=Never -- sleep 3600
kubectl exec test-pod -- ping -c 3 <pod-ip-of-another-pod>
```

## Диагностика и обслуживание

Для управления ресурсами Calico используется утилита **`calicoctl`**. Она позволяет просматривать состояние BGP-сессий, HostEndpoints и проверять корректность применения политик.

### Основные диагностические команды

```bash
# Установка calicoctl (как kubectl плагин)
curl -L https://github.com/projectcalico/calico/releases/download/v3.33.0/calicoctl-linux-amd64 -o /usr/local/bin/calicoctl
chmod +x /usr/local/bin/calicoctl

# Проверка BGP-сессий
calicoctl node status
# → Ожидаемый результат: Peer Status: Established для каждого узла

# Просмотр всех ресурсов Calico
calicoctl get globalnetworkpolicy -o wide
calicoctl get hostendpoint -o wide
calicoctl get ippool -o wide

# Просмотр логов Felix
kubectl logs -n calico-system ds/calico-node -c calico-node -f

# Проверка eBPF (если используется)
kubectl exec -it -n calico-system <calico-node-pod> -- calico-node -bpf counters dump
```

### Диагностика по режимам Data Plane

| Режим | Инструмент | Команда |
| :--- | :--- | :--- |
| **Standard (iptables)** | `iptables-save`, `calicoctl node status` | `iptables-save -c -t filter \| grep cali` |
| **eBPF** | `bpftool`, `calico-node -bpf` | `kubectl exec -n calico-system ds/calico-node -- calico-node -bpf policy dump <iface> ingress` |
| **nftables** | `nft` | `nft list ruleset \| grep cali` |

### Типичные ошибки и устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Узлы в NotReady** | Неверный `pod-network-cidr` или оператор не запущен | Проверьте логи: `kubectl logs -n tigera-operator -l k8s-app=tigera-operator` |
| **Потеря SSH-доступа** | HostEndpoint заблокировал порт 22 | Проверьте `FailsafePorts` в `FelixConfiguration` или создайте разрешающую политику |
| **Timeout в eBPF режиме** | Ядро Linux < 5.3 или не смонтирована BPF FS | Убедитесь что `/sys/fs/bpf` смонтирована, проверьте `uname -r` |
| **NodePort не работает** | Конфликт с kube-proxy или отсутствие `preDNAT` | В eBPF режиме Calico должен заменять kube-proxy. В Standard — добавьте `preDNAT: true` |
| **Ошибка BGP** | Закрыт порт 179/TCP | Разрешите 179/TCP между всеми IP узлов, проверьте `calicoctl node status` |
| **Несоответствие MTU** | Инкапсуляция (VXLAN/IPIP) | MTU в `FelixConfiguration` должен быть на 20-50 байт меньше физического интерфейса |
| **IPAM исчерпан** | Все адреса в пуле выделены | Расширите IPPool: `calicoctl apply -f <new-pool.yaml>` |
| **Потеря IP после перезапуска узла** | host-local IPAM без синхронизации | Используйте Integrated IPAM (etcd/CRD) для сохранения состояния |

*Подробное руководство по диагностике: [Операции Calico: Диагностика и обслуживание](./operations.md)*

## Лучшие практики

1. **Всегда начинайте с DNS**: При внедрении GlobalNetworkPolicy первым создавайте политику разрешения DNS, иначе поды потеряют разрешение имён сервисов.
2. **Тестируйте в стейджинге**: Перед применением политик в production проверяйте их влияние в изолированной среде. Неверная политика может заблокировать доступ к кластеру.
3. **Используйте Tigera Operator**: Для production-сред рекомендуется Operator вместо raw-манифестов — он обеспечивает автоматические обновления и контроль жизненного цикла.
4. **Мониторинг метрик**: Настройте сбор метрик Felix через Prometheus (`prometheusMetricsEnabled: true`) для своевременного обнаружения проблем.
5. **Регулярные бэкапы**: Экспортируйте конфигурацию Calico (IPPool, GlobalNetworkPolicy, HostEndpoint) через `calicoctl get <resource> -o yaml`.
6. **WireGuard для Zero Trust**: Включайте шифрование WireGuard для соответствия требованиям безопасности, особенно в средах с высоким уровнем доверия.
7. **eBPF для производительности**: При количестве политик более 1000 или требований к низкой латентности переходите на eBPF dataplane.
8. **Избегайте derived-политик**: Не создавайте больше 10000 политик в кластере — это влияет на время их применения Felix.
9. **BGP для bare-metal**: В физических дата-центрах используйте BGP-режим для интеграции с существующей маршрутизацией и максимальной производительности.
10. **Версионная совместимость**: Проверяйте матрицу совместимости перед обновлением Calico или Kubernetes: [Supported Releases](https://docs.tigera.io/calico/latest/about/supported-releases)
