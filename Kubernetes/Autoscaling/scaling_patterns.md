# Паттерны масштабирования

Помимо стандартных механизмов HPA и VPA, существуют архитектурные паттерны, которые используются для масштабирования специфичных типов нагрузок.

## Шардирование и разделение трафика

**Шардирование** — это техника, при которой рабочая нагрузка разделяется на несколько независимых, изолированных друг от друга групп (шардов). В Kubernetes это реализуется путем развертывания нескольких логических групп подов (например, нескольких `Deployment`) с разными селекторами.

Для каждой группы можно создать отдельный `Service`, что упрощает изоляцию, индивидуальные лимиты и канареечные выкатки.

**Когда применять:**
-   Когда данные или трафик можно легко разделить по ключу (например, по региону пользователя, ID клиента, типу подписки).
-   Для повышения отказоустойчивости: сбой в одном шарде не затрагивает другие.
-   Для обхода ограничений производительности отдельных компонентов.

**Пример:**
Развертываются два `Deployment`, `webapp-shard-a` и `webapp-shard-b`, с метками `shard: a` и `shard: b` соответственно. Затем создаются два сервиса, каждый из которых направляет трафик только на свой шард:
-   `service-a` с селектором `shard: a`
-   `service-b` с селектором `shard: b`

Маршрутизация на нужный шард выполняется на уровне клиента, Ingress-контроллера или API-шлюза.

**Плюсы:**
-   **Локальность данных:** Запросы обрабатываются ближе к данным.
-   **Изоляция отказов:** Проблемы в одном шарде не влияют на другие.

**Ограничения:**
-   **Сложность маршрутизации:** Требуется дополнительная логика для направления клиентов на правильный шард.
-   **Операционная сложность:** Управление несколькими развертываниями вместо одного.

## Паттерн "Workers + Очередь"

Этот паттерн идеально подходит для **масштабирования асинхронных и фоновых задач**.

**Как это работает:**
1.  **Очередь сообщений:** Вне Kubernetes разворачивается очередь сообщений (например, RabbitMQ, Kafka, SQS).
2.  **Producers:** Другие сервисы (продюсеры) отправляют задачи в эту очередь.
3.  **Consumers (Workers):** В Kubernetes разворачивается `Deployment` с подами-воркерами (консумерами), которые читают сообщения из очереди и обрабатывают их.

Масштабирование в этом паттерне привязывается к длине очереди.
-   Если очередь растет, **HPA с внешней метрикой** (например, `queue_messages_ready`) автоматически увеличивает количество подов-воркеров.
-   Если очередь пуста, HPA уменьшает количество воркеров до минимального значения (или до нуля, если используется KEDA).

**Когда применять:**
-   Обработка видео, генерация отчетов, отправка email-рассылок и другие долгие задачи.
-   Системы, где нужно сгладить пиковые нагрузки.

**Плюсы:**
-   **Линейная масштабируемость:** Производительность системы растет прямо пропорционально количеству воркеров.
-   **Отказоустойчивость:** Если воркер падает, сообщение остается в очереди и будет обработано другим воркером.

**Важные аспекты:**
-   **Идемпотентность:** Задачи должны быть идемпотентными, то есть повторное выполнение одной и той же задачи не должно приводить к ошибкам.
-   **Дедупликация:** Механизмы для предотвращения повторной обработки сообщений.
-   **Контроль параллелизма:** Ограничение количества сообщений, которые один воркер может обрабатывать одновременно.
