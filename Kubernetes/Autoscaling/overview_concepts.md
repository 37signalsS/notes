# Автоматическое масштабирование в Kubernetes: Обзор

## Определения

**Автоматическое масштабирование (Autoscaling)** — возможность Kubernetes динамически управлять ресурсами кластера и приложений в зависимости от нагрузки. Обеспечивает эластичность, высокую доступность и оптимизацию затрат.

**Масштабирование по горизонтали (Horizontal Scaling)** — увеличение количества экземпляров приложения (подов).

**Масштабирование по вертикали (Vertical Scaling)** — увеличение ресурсов (CPU, memory) отдельных экземпляров.

## Основные концепции

### Уровни масштабирования

| Уровень | Компонент | Что масштабирует | Направление |
|---------|-----------|------------------|-------------|
| **Поды** | [HPA](hpa_detailed.md) | Количество реплик | Горизонтально |
| **Контейнеры** | [VPA](vpa_detailed.md) | Resources (CPU/RAM) | Вертикально |
| **Узлы** | [Cluster Autoscaler](cluster_autoscaler_detailed.md) | Количество узлов | Горизонтально |
| **Узлы (оптимизировано)** | [Karpenter](karpenter_detailed.md) | Количество узлов | Горизонтально |
| **События** | [KEDA](keda_detailed.md) | Количество реплик по событиям | Горизонтально |
| **Ресурсы без перезапуска** | [In-Place Pod Resize](in_place_pod_resize.md) | Resources у запущенных подов | Вертикально |

### Краткое описание компонентов

#### Horizontal Pod Autoscaler (HPA)

Автоматически увеличивает или уменьшает количество реплик подов на основе метрик (CPU, memory, custom, external). Работает с Deployment, ReplicaSet, StatefulSet.

**Подробнее:** [HPA Detailed](hpa_detailed.md)

#### Vertical Pod Autoscaler (VPA)

Автоматически настраивает `requests` и `limits` CPU/memory для контейнеров. Работает в режимах рекомендаций (`Off`) или автоматического применения (`Initial`, `Recreate`, `Auto`).

**Подробнее:** [VPA Detailed](vpa_detailed.md)

#### Cluster Autoscaler (CA)

Автоматически добавляет или удаляет узлы кластера при нехватке ресурсов или избытке. Работает с Node Groups в облачных средах.

**Подробнее:** [Cluster Autoscaler Detailed](cluster_autoscaler_detailed.md)

#### Karpenter

Высокопроизводительная альтернатива CA. Создаёт узлы оптимального размера «точно в срок» под требования ожидающих подов. Быстрее и эффективнее CA.

**Подробнее:** [Karpenter Detailed](karpenter_detailed.md)

#### KEDA (Kubernetes Event-driven Autoscaling)

Расширяет возможности HPA, позволяя масштабировать поды на основе событий из 60+ источников (очереди, метрики, расписание). Поддерживает масштабирование до нуля.

**Подробнее:** [KEDA Detailed](keda_detailed.md)

#### In-Place Pod Resize

Функция Kubernetes 1.35+, позволяющая изменять ресурсы запущенных подов без пересоздания. Интегрируется с VPA для автоматического применения рекомендаций.

**Подробнее:** [In-Place Pod Resize Detailed](in_place_pod_resize.md)

### Синергия компонентов (Совместная работа)

```
┌─────────────────────────────────────────────────────────────────────┐
│                        Нагрузка возрастает                          │
└─────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  1. HPA/KEDA обнаруживает рост нагрузки (CPU, длина очереди)       │
│     → Решение: увеличить количество подов с 3 до 10                │
└─────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  2. Новые 7 подов переходят в состояние Pending                     │
│     (недостаточно ресурсов на существующих узлах)                  │
└─────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  3. Cluster Autoscaler / Karpenter видит Pending поды              │
│     → CA: запрашивает новый узел из Node Group                     │
│     → Karpenter: создаёт узел оптимального размера                 │
└─────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  4. Новые узлы готовы → Kubernetes размещает на них поды           │
└─────────────────────────────────────────────────────────────────────┘
                                   │
                                   ▼
┌─────────────────────────────────────────────────────────────────────┐
│  5. VPA (в режиме Off) параллельно анализирует работу приложения   │
│     → Рекомендует увеличить requests для CPU                       │
│     → С In-Place Pod Resize: применяет без перезапуска             │
└─────────────────────────────────────────────────────────────────────┘
```

## Практические сценарии

### Выбор компонента для масштабирования

| Сценарий | Рекомендуемое решение |
|----------|----------------------|
| Stateless-приложение с переменной нагрузкой | HPA по CPU/memory |
| Асинхронная обработка очередей | KEDA (RabbitMQ, Kafka scaler) |
| Пакетные задачи с расписанием | KEDA (Cron scaler) |
| Stateful-приложения с долгим запуском | VPA + In-Place Pod Resize |
| Динамичная облачная среда | Karpenter вместо CA |
| Мульти-облачная инфраструктура | Cluster Autoscaler |
| Оптимизация затрат (spot-инстансы) | Karpenter + Consolidation |
| Масштабирование до нуля | KEDA |

### Предварительные требования

1. **Metrics Server** — обязателен для HPA и VPA. [Подробнее](../MonitoringLogging/metrics-server.md).
2. **Requests/Limits** — должны быть заданы для всех контейнеров.
3. **Pod Disruption Budget** — рекомендуется для критических приложений. [Подробнее](pod_disruption_budget.md).
4. **Readiness Probes** — обязательны для корректного исключения подов из балансировки.

### Лучшие практики

* **Используйте PodDisruptionBudget** — всегда создавайте [PDB](pod_disruption_budget.md) для критически важных приложений.
* **Правильно настраивайте requests** — CA и HPA основывают решения на `requests`, а не на реальном потреблении.
* **Несколько Node Groups** — разделяйте узлы по типам нагрузки (GPU, memory-optimized).
* **Масштабирование до нуля** — установите `min-size: 0` для тестовых групп узлов.
* **Аннотации для контроля CA** — `cluster-autoscaler.kubernetes.io/scale-down-disabled: "true"`.
* **Behavior в HPA** — настройте `stabilizationWindowSeconds` для scale-down.
* **Правильная метрика для HPA** — для I/O-bound приложений используйте кастомные метрики (RPS).
* **Не используйте HPA и VPA вместе для одной метрики** — это вызывает конфликты и «гонку масштабирования».
* **KEDA для событий** — используйте для очередей, расписаний, внешних метрик.
* **Karpenter для облаков** — предпочтительнее CA в AWS, Azure, GCP.

## Дополнительная информация

### Что мешает удалению узла Cluster Autoscaler?

* Поды с жесткими правилами `podAntiAffinity`
* Поды, не управляемые контроллерами (Deployment, StatefulSet)
* Поды с локальным хранилищем (`hostPath`, `emptyDir`)
* Поды, для которых не соблюдается [PDB](pod_disruption_budget.md)
* Поды с аннотацией `cluster-autoscaler.kubernetes.io/safe-to-evict: "false"`

### Конфликты и ограничения

| Конфликт | Решение |
|----------|---------|
| HPA + VPA для CPU/memory | Использовать VPA в режиме `Off` для рекомендаций |
| CA + Karpenter одновременно | Выбрать один компонент (рекомендуется Karpenter) |
| KEDA + HPA на одном Deployment | KEDA управляет HPA, не создавать отдельно |
| PDB блокирует scale-down | Проверить конфигурацию PDB, увеличить `maxUnavailable` |

### Интеграции между компонентами

* **HPA ↔ PDB** — HPA учитывает [PDB](pod_disruption_budget.md) при масштабировании вниз.
* **HPA ↔ Pod Distribution** — созданные HPA поды распределяются согласно [правилам распределения](pod_distribution.md).
* **VPA ↔ In-Place Resize** — VPA использует In-Place Pod Resize для применения рекомендаций без перезапуска.
* **KEDA ↔ HPA** — KEDA создаёт и управляет нативным HPA.
* **CA/Karpenter ↔ HPA/KEDA** — CA/Karpenter реагируют на поды, созданные HPA/KEDA.
* **Все компоненты ↔ PDB** — все учитывают PDB при удалении подов/узлов.
