# Horizontal Pod Autoscaler (HPA)

## Определения

**Horizontal Pod Autoscaler (HPA)** — механизм Kubernetes для автоматического изменения количества реплик подов на основе метрик загрузки.

**Metrics Server** — компонент кластера, собирающий метрики ресурсов с узлов и предоставляющий их для HPA.

**Stabilization Window** — период времени, в течение которого HPA учитывает исторические данные перед принятием решения о масштабировании вниз.

## Основные концепции

### Алгоритм принятия решений

HPA работает по принципу термостата с периодичностью 15 секунд:

```
желаемыеРеплики = ceil(текущиеРеплики × (текущаяМетрика / желаваяМетрика))
```

**Пример расчета:**
- Текущие реплики: 3
- Целевая метрика (CPU): 50%
- Текущая нагрузка: 90%
- Результат: `ceil(3 × (90 / 50)) = 6 реплик`

### Типы метрик

| Тип | Описание | Источник |
|-----|----------|----------|
| Resource Metrics | CPU/RAM утилизация | Metrics Server |
| Custom Metrics | RPS, специфичные показатели | Prometheus Adapter |
| External Metrics | Длина очередей, бизнес-метрики | Внешние системы |

### Конфигурация поведения

Параметры `behavior` позволяют настроить:
- Скорость масштабирования вверх/вниз
- Задержки стабилизации
- Политики изменения реплик (процент или абсолютное значение)

## Практические сценарии

### Предварительные требования

1. **Установить Metrics Server:** Для работы с базовыми метриками (`cpu`, `memory`) в кластере должен быть развернут компонент **Metrics Server**. Он собирает данные о потреблении ресурсов с каждого узла и предоставляет их HPA.
2. **Задать запросы (requests) для контейнеров:** Чтобы HPA мог корректно рассчитывать утилизацию CPU в процентах, у контейнеров в вашем `Deployment` должны быть установлены запросы на ресурсы (`spec.containers.resources.requests`).

    ```yaml
    resources:
      requests:
        cpu: "200m" # 200 милли-ядер
        memory: "256Mi"
    ```

### Пример манифеста

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
  namespace: default
spec:
  # 1. Ссылка на масштабируемый ресурс (Deployment или StatefulSet)
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app # Измените на имя вашего Deployment

  # 2. Границы масштабирования
  minReplicas: 3
  maxReplicas: 20

  # 3. Метрики для принятия решений
  metrics:
    # Метрика по утилизации CPU (ресурсная метрика)
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization # Тип цели — средняя утилизация
          averageUtilization: 60 # Целевое значение 60% утилизации CPU
    # Внешняя метрика (например, из очереди сообщений)
    - type: External
      external:
        metric:
          name: queue_messages_ready # Название внешней метрики
        target:
          type: AverageValue
          averageValue: "200" # Целевое среднее значение 200 сообщений в очереди

  # 4. Поведение при масштабировании (опционально, для тонкой настройки)
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0 # Отсутствие задержки для быстрого масштабирования вверх
      policies:
      - type: Percent
        value: 100 # Увеличение на 100% от текущего числа подов
        periodSeconds: 15 # Каждые 15 секунд
    scaleDown:
      stabilizationWindowSeconds: 300 # 5-минутная задержка для масштабирования вниз
      policies:
      - type: Pods
        value: 2 # Уменьшение на 2 пода
        periodSeconds: 60 # Каждую минуту
```

### Рекомендации по настройке

-   **`readinessProbe`**: Настройка `readinessProbe` критически важна для исключения «холодных» (еще не готовых) подов из балансировки, предотвращая направление трафика на неинициализированные экземпляры.
-   **`minReadySeconds`**: Использование параметра `minReadySeconds` в спецификации Deployment/StatefulSet помогает уменьшить "флаппинг" (быстрое переключение состояний подов) и гарантирует, что новый под считается "готовым" только после прохождения `readinessProbe` и стабильной работы в течение этого времени.
-   **Корректные `requests`**: Указание адекватных запросов на ресурсы (CPU/RAM `requests`) позволяет планировщику заранее резервировать необходимые ресурсы на узлах, что способствует более стабильному и предсказуемому масштабированию.

## Дополнительная информация

### Ограничения

- HPA не масштабирует ниже `minReplicas` даже при нулевой нагрузке; для масштабирования до нуля используйте KEDA
- Метрики собираются с интервалом 15 секунд
- **Конфликт с VPA**: не используйте HPA по CPU/memory одновременно с [VPA](vpa_detailed.md) в активных режимах (`Initial`, `Recreate`, `Auto`) — используйте VPA в режиме `Off` для получения рекомендаций

### Интеграции

HPA при масштабировании учитывает [Pod Disruption Budget](pod_disruption_budget.md) для защиты от добровольных прерываний. Созданные HPA поды распределяются согласно правилам [распределения подов](pod_distribution.md). Для масштабирования workers по длине очереди используются [паттерны масштабирования](scaling_patterns.md) с внешними метриками.
