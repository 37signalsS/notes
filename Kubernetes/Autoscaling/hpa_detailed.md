# Horizontal Pod Autoscaler (HPA)

### Horizontal Pod Autoscaler (HPA)

#### Как HPA принимает решения?

HPA работает как термостат для вашего приложения. Он периодически (по умолчанию каждые 15 секунд) запрашивает метрики у **Metrics Server**, сравнивает их с целевыми значениями и рассчитывает необходимое количество реплик по формуле:

`желаемыеРеплики = ceil(текущиеРеплики * ( текущаяМетрика / желаемаяМетрика ))`

**Пример:**

* `текущиеРеплики`: 3
* `желаемаяМетрика` (цель по CPU): 50%
* `текущаяМетрика` (реальная нагрузка): 90%

`желаемыеРеплики = ceil(3 * (90 / 50)) = ceil(3 * 1.8) = ceil(5.4) = 6`

HPA увеличит количество реплик с 3 до 6.

#### Типы метрик для HPA

* **Метрики ресурсов (Resource Metrics):** Среднее потребление CPU (`Utilization`) или среднее значение RAM (`AverageValue`). Это базовые метрики, но они не всегда отражают реальную нагрузку на приложение.
* **Кастомные метрики (Custom Metrics):** Метрики, связанные с объектами Kubernetes, но не являющиеся стандартными (например, количество запросов в секунду (RPS) на под). Требуют установки адаптера, например, **Prometheus Adapter**, который "переводит" метрики из Prometheus в понятный для HPA формат.
* **Внешние метрики (External Metrics):** Метрики из внешних систем, не связанных напрямую с объектами Kubernetes. Это идеальный вариант для масштабирования на основе бизнес-показателей.
  * **Примеры:** Длина очереди в RabbitMQ или Kafka, количество активных пользователей в базе данных.
  * Также требуют настройки адаптера для соответствующей системы.

Использование кастомных и внешних метрик позволяет создавать более интеллектуальные и точные правила масштабирования, которые реагируют на реальную потребность бизнеса, а не только на утилизацию "железа".

## Практические сценарии

### Настройка HPA

#### Предварительные требования

1. **Установить Metrics Server:** Для работы с базовыми метриками (`cpu`, `memory`) в кластере должен быть развернут компонент **Metrics Server**. Он собирает данные о потреблении ресурсов с каждого узла и предоставляет их HPA.
2. **Задать запросы (requests) для контейнеров:** Чтобы HPA мог корректно рассчитывать утилизацию CPU в процентах, у контейнеров в вашем `Deployment` должны быть установлены запросы на ресурсы (`spec.containers.resources.requests`).

    ```yaml
    resources:
      requests:
        cpu: "200m" # 200 милли-ядер
        memory: "256Mi"
    ```

    Без этого HPA не знает, от какого базового значения считать процент.

#### Анатомия манифеста HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
  namespace: default
spec:
  # 1. Ссылка на масштабируемый ресурс (Deployment или StatefulSet)
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app # Измените на имя вашего Deployment

  # 2. Границы масштабирования
  minReplicas: 3
  maxReplicas: 20

  # 3. Метрики для принятия решений
  metrics:
    # Метрика по утилизации CPU (ресурсная метрика)
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization # Тип цели — средняя утилизация
          averageUtilization: 60 # Целевое значение 60% утилизации CPU
    # Внешняя метрика (например, из очереди сообщений)
    - type: External
      external:
        metric:
          name: queue_messages_ready # Название внешней метрики
        target:
          type: AverageValue
          averageValue: "200" # Целевое среднее значение 200 сообщений в очереди

  # 4. Поведение при масштабировании (опционально, для тонкой настройки)
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0 # Отсутствие задержки для быстрого масштабирования вверх
      policies:
      - type: Percent
        value: 100 # Увеличение на 100% от текущего числа подов
        periodSeconds: 15 # Каждые 15 секунд
    scaleDown:
      stabilizationWindowSeconds: 300 # 5-минутная задержка для масштабирования вниз
      policies:
      - type: Pods
        value: 2 # Уменьшение на 2 пода
        periodSeconds: 60 # Каждую минуту
```

1. **`scaleTargetRef`**: Указывает, каким `Deployment` или `StatefulSet` будет управлять HPA.
2. **`minReplicas` / `maxReplicas`**: Задает границы масштабирования.
3. **`metrics`**: Список метрик. HPA рассчитает необходимое количество реплик для *каждой* метрики и выберет **наибольшее** значение.
4. **`behavior`**: Позволяет тонко настроить скорость масштабирования, чтобы избежать "дребезжания" (быстрого увеличения и уменьшения реплик).

#### Практические рекомендации:

-   **`readinessProbe`**: Настройка `readinessProbe` критически важна для исключения «холодных» (еще не готовых) подов из балансировки, предотвращая направление трафика на неинициализированные экземпляры.
-   **`minReadySeconds`**: Использование параметра `minReadySeconds` в спецификации Deployment/StatefulSet помогает уменьшить "флаппинг" (быстрое переключение состояний подов) и гарантирует, что новый под считается "готовым" только после прохождения `readinessProbe` и стабильной работы в течение этого времени.
-   **Корректные `requests`**: Указание адекватных запросов на ресурсы (CPU/RAM `requests`) позволяет планировщику заранее резервировать необходимые ресурсы на узлах, что способствует более стабильному и предсказуемому масштабированию.
