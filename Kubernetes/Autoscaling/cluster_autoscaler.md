# Cluster Autoscaler (CA)

**Cluster Autoscaler (CA)** — это компонент Kubernetes, который автоматически регулирует размер кластера, добавляя или удаляя узлы (Nodes) в зависимости от текущей нагрузки. Его главная задача — обеспечить, чтобы в кластере всегда было достаточно ресурсов для запуска всех подов, и при этом экономить затраты, отключая простаивающие узлы.

CA работает на уровне инфраструктуры и взаимодействует напрямую с API облачного провайдера (AWS, GCP, Azure и др.) для заказа или удаления виртуальных машин.

---

## Как Cluster Autoscaler принимает решения?

Cluster Autoscaler периодически проверяет состояние кластера и принимает решения о масштабировании на основе двух ключевых сценариев.

### Масштабирование вверх (Scale-Up)

CA решает добавить новый узел, если обнаруживает в кластере поды в состоянии `Pending`, которые не могут быть размещены из-за нехватки ресурсов (CPU, RAM, GPU).

**Процесс принятия решения:**
1.  **Обнаружение `Pending` подов:** CA сканирует кластер на наличие подов, которые планировщик (`kube-scheduler`) не смог никуда разместить.
2.  **Симуляция размещения:** Для каждого такого пода CA симулирует, сможет ли он разместиться, если в кластер будет добавлен новый узел определенного типа (из группы автомасштабирования). При этом учитываются:
    *   Запросы ресурсов пода (`requests`).
    *   Правила `nodeSelector` и `nodeAffinity`.
    *   `Taints` и `Tolerations`.
3.  **Выбор группы узлов:** Если симуляция успешна, CA выбирает наиболее подходящую группу узлов (Node Group) для расширения.
4.  **Запрос к облачному провайдеру:** CA отправляет запрос в API облака на создание нового узла в выбранной группе.

### Масштабирование вниз (Scale-Down)

CA решает удалить узел, если он соответствует следующим критериям:

1.  **Низкая утилизация:** Узел в течение определенного времени (по умолчанию 10 минут) используется слабо. Утилизация рассчитывается как отношение суммы запросов (`requests`) запущенных на нем подов к общей емкости узла. Порог по умолчанию — 50%.
2.  **Возможность безопасного перемещения подов:** Все поды, работающие на этом узле, могут быть безопасно перемещены на другие доступные узлы кластера.

**Что мешает удалению узла?**

CA **не будет** удалять узел, если на нем есть поды, которые не могут быть перемещены. К ним относятся:
*   Поды с жесткими правилами `podAntiAffinity` по отношению к другим подам.
*   Поды, не управляемые контроллерами (`Deployment`, `StatefulSet`, `Job`).
*   Поды, у которых есть локальное хранилище (`local storage`).
*   Поды, для которых не соблюдается [PodDisruptionBudget (PDB)](../../Base/pod_disruption_budget.md) — правило, ограничивающее количество одновременно недоступных подов одного приложения.
*   Поды с аннотацией `"cluster-autoscaler.kubernetes.io/safe-to-evict": "false"`.

## Взаимодействие с облачными провайдерами

Cluster Autoscaler не создает машины сам. Он управляет **группами автомасштабирования** (Node Groups / Autoscaling Groups) в облаке.

*   **AWS:** Auto Scaling Groups (ASG)
*   **GCP:** Managed Instance Groups (MIG)
*   **Azure:** Virtual Machine Scale Sets (VMSS)

Вы заранее создаете и настраиваете эти группы (например, указываете тип инстанса, образ диска, сеть), а CA затем только изменяет желаемое количество машин в этих группах.

## Ключевые параметры конфигурации (флаги)

Поведение Cluster Autoscaler настраивается с помощью флагов при его запуске.

*   `--scan-interval`: Как часто (в секундах) CA сканирует кластер на наличие `Pending` подов. (По умолчанию: `10s`).
*   `--scale-down-utilization-threshold`: Порог утилизации узла (в долях от 0 до 1), ниже которого он становится кандидатом на удаление. (По умолчанию: `0.5`).
*   `--scale-down-unneeded-time`: Как долго узел должен быть слабо утилизирован, прежде чем CA попытается его удалить. (По умолчанию: `10m`).
*   `--skip-nodes-with-local-storage`: Запрещает CA удалять узлы с подами, использующими `hostPath` или `emptyDir`. (По умолчанию: `true`).
*   `--balance-similar-node-groups`: Если `true`, CA будет стараться сбалансировать количество узлов в похожих группах. (По умолчанию: `false`).

## Лучшие практики

*   **Используйте [PodDisruptionBudget (PDB)](../../Base/pod_disruption_budget.md):** Всегда создавайте PDB для критически важных приложений. Это гарантирует, что CA не удалит слишком много подов одного сервиса одновременно во время масштабирования вниз, предотвращая простой.
*   **Правильно настраивайте `requests`:** CA принимает решения на основе `requests`, а не реального потребления. Неправильно заданные (слишком низкие) `requests` могут привести к тому, что CA не добавит узел, хотя реальных ресурсов уже не хватает.
*   **Используйте несколько Node Groups:** Разделяйте узлы на группы по типам нагрузки (например, обычные, с GPU, с большим объемом памяти). Это позволяет CA более гранулярно управлять ресурсами.
*   **Аннотации для контроля:** Используйте аннотации для тонкого управления.
    *   `"cluster-autoscaler.kubernetes.io/safe-to-evict": "true"` на поде — разрешает CA выселять под, даже если он обычно этого не делает.
    *   `"cluster-autoscaler.kubernetes.io/scale-down-disabled": "true"` на узле — временно запрещает CA удалять этот узел. Полезно во время проведения работ по обслуживанию.
*   **Синергия с HPA и VPA:** Используйте все три автоскейлера вместе для максимальной эластичности. См. [Обзор автоматического масштабирования](./autoscaling_overview.md).
