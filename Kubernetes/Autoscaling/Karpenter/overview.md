# Karpenter: Обзор и концепции

> **Важно:** Karpenter предназначен для облачных провайдеров (AWS, Azure, GCP). Для локального аринта (on-premise, bare-metal) используйте **[Cluster Autoscaler](../cluster_autoscaler_detailed.md)** с node groups или **Volcano** для batch-нагрузок.

## Определения

**Karpenter** — оператор Kubernetes для автоматического масштабирования кластера, который динамически создаёт узлы оптимального размера под требования ожидающих подов. Разработан в AWS, передан в CNCF.

**Node Pool** (ранее **Provisioner**) — объект Karpenter, определяющий параметры создаваемых узлов (типы инстансов, зоны, метки, тэги).

**Consolidation** — механизм оптимизации затрат, который автоматически заменяет узлы на более дешёвые или объединяет несколько слабо утилизированных узлов в один.

**EC2NodeClass** (AWS) / **NodeClass** — шаблон конфигурации узла (AMI, диск, сеть, IAM-роль).

## Основные концепции

### Отличия от Cluster Autoscaler

| Характеристика | Cluster Autoscaler | Karpenter |
|----------------|-------------------|-----------|
| **Подход** | Работает с предопределёнными группами узлов (Node Groups) | Создаёт узлы «точно в срок», управляет каждым узлом индивидуально |
| **Скорость** | 1-3 минуты на масштабирование | 30-60 секунд (мгновенное создание) |
| **Эффективность** | Выбор из готовых шаблонов | Оптимальный подбор типа инстанса (amd64/arm64, GPU, специализированные) |
| **Гибкость** | Ограничена группами узлов | Динамический выбор из сотен типов инстансов, контроль limits по стоимости, выбор spot/on-demand |
| **Consolidation** | Базовый scale-down | Умная консолидация (замена + объединение) |
| **Сложность** | Средняя | Выше, требует настройки CRD (Provisioner, NodeTemplate) |

### Ключевые преимущества

**Скорость** — Karpenter не ждёт, пока освободятся ресурсы на существующих узлах — он сразу создаёт новый, идеально подходящий под требования пода. Это особенно важно для burst-нагрузок и пакетных задач.

**Гибкость** — Позволяет точно контролировать, какие типы узлов используются, задавать limits по стоимости, выбирать между spot и on-demand, а также учитывать `topologySpreadConstraints` для распределения по зонам.

**Отказ от групп узлов** — В отличие от Cluster Autoscaler, которому нужны предопределённые группы, Karpenter управляет каждым узлом индивидуально. Это упрощает конфигурацию и убирает ограничения на размер группы.

### Как работает Karpenter

1. **Мониторинг Pending Pods** — Karpenter отслеживает поды в состоянии `Pending`.
2. **Анализ требований** — анализирует `requests`, `affinity`, `tolerations`, `nodeSelector`, `topologySpreadConstraints`.
3. **Подбор инстанса** — выбирает оптимальный тип инстанса из доступных в облаке (архитектура amd64/arm64, зона доступности, GPU).
4. **Создание узла** — запускает новый узел через API облачного провайдера за секунды.
5. **Планирование** — после готовности узла Kubernetes размещает на нём поды.
6. **Консолидация** — автоматически удаляет неэффективные узлы и перепаковывает поды на другие, оптимизируя заполнение кластера.

### Компоненты архитектуры

* **Karpenter Controller** — оператор, работающий как Deployment в namespace `kube-system` или `karpenter`.
* **Node Pool** — определяет параметры создаваемых узлов (аналог Node Group).
* **EC2NodeClass** (AWS) / **NodeClass** — шаблон конфигурации узла (AMI, диск, сеть).
* **Consolidation Controller** — компонент для оптимизации затрат.

## Дополнительная информация

### Интеграции

* **[HPA](../HPA/index.md)** — Karpenter реагирует на поды, созданные HPA.
* **[VPA](../vpa_detailed.md)** — VPA помогает оптимизировать `requests` для лучшего подбора узлов.
* **[KEDA](../keda/practical_scenarios.md)** — KEDA создаёт HPA, который активирует Karpenter.
* **[Cluster Autoscaler](../cluster_autoscaler_detailed.md)** — альтернатива Karpenter, не рекомендуется использовать одновременно.
* **[Pod Disruption Budget](../pod_disruption_budget.md)** — Karpenter учитывает PDB при консолидации.

### Ограничения

* **Только облачные провайдеры** — AWS (полная поддержка), Azure, GCP (в разработке).
* **Не работает с bare-metal** — требует API облачного провайдера.
* **Сложность настройки** — требует глубокого понимания инфраструктуры.
* **Стоимость** — неправильная настройка может привести к неожиданным затратам.

## Практические сценарии

### Масштабирование по длине очереди Kafka

Karpenter идеально подходит для рабочих нагрузок, масштабируемых по внешним метрикам, таким как длина очереди сообщений. Этот сценарий показывает, как объединить KEDA, HPA и Karpenter для эффективного управления ресурсами.

**Архитектура решения:**

1. **Экспортёр метрик**: Специализированный экспортер (например, `kafka-exporter`) собирает метрику `kafka_consumergroup_lag` и предоставляет её для Prometheus.
2. **KEDA (`ScaledObject`)**: KEDA настраивается для отслеживания этой метрики в Prometheus.
3. **HPA (Горизонтальное автомасштабирование подов)**: KEDA автоматически создает и управляет объектом `HorizontalPodAutoscaler` (HPA) на основе `ScaledObject`. Когда длина очереди превышает пороговое значение, HPA увеличивает количество реплик (подов) приложения.
4. **Karpenter (Автомасштабирование узлов)**:
    * Karpenter обнаруживает новые поды в состоянии `Pending`, созданные HPA.
    * Он анализирует их ресурсные запросы (`requests`) и другие требования (affinity, tolerations).
    * Karpenter напрямую обращается к API облачного провайдера (например, AWS EC2) и создает новый узел оптимального размера, который может вместить все ожидающие поды.
    * Как только узел готов, `kube-scheduler` размещает на нем поды, и они начинают обрабатывать очередь.

**Преимущества этого подхода:**

* **Эффективность**: Ресурсы (узлы) создаются только тогда, когда есть реальная нагрузка (сообщения в очереди).
* **Скорость**: Karpenter значительно быстрее, чем Cluster Autoscaler, что критически важно для быстрого реагирования на всплески нагрузки.
* **Оптимизация затрат**: Karpenter подбирает наиболее дешевый тип инстанса, подходящий для подов, и может использовать spot-инстансы для дополнительной экономии.
