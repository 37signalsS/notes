# Обзор и основные концепции Karpenter

> **Важно:** Karpenter предназначен для облачных провайдеров (AWS (Amazon Web Services), Azure, Alibaba Cloud). Для GCP рекомендуется использовать нативный **Node Auto-Provisioning (NAP)**. Для локальных окружений (on-premise, bare-metal) используйте **[Cluster Autoscaler](../cluster_autoscaler_detailed.md)** с группами узлов или **Volcano** для пакетных (batch) нагрузок.

## Определения

**Karpenter** — высокопроизводительный open-source оператор Kubernetes для автоматического масштабирования кластера (Node Autoscaling), который динамически создаёт узлы оптимального размера в ответ на требования ожидающих (pending) подов. Проект передан в CNCF (Cloud Native Computing Foundation) и является стандартом де-факто для эффективного управления мощностями в облачных средах. Текущая стабильная ветка — v1.x (актуальная версия v1.14.x, 2026 год).

**Философия Just-in-time (JIT)** — в отличие от традиционных подходов, Karpenter предоставляет ресурсы «точно в срок», оптимизируя затраты и производительность за счет выбора идеального типа инстанса в реальном времени под конкретную нагрузку, вместо использования заранее определенных групп узлов.

**NodePool** — основной CRD (Custom Resource Definition) Karpenter, определяющий правила (intent) по созданию и управлению узлами. В версии v1.x NodePool является стабильным API. Он служит фильтром, через который Karpenter анализирует доступные типы инстансов, зоны и архитектуры, выбирая наиболее подходящий вариант для ожидающего пода, а также задает политики прерываний.

**NodeClass (EC2NodeClass в AWS / AKSNodeClass в Azure)** — ресурс, описывающий специфичные для облака инфраструктурные параметры узла: AMI (Amazon Machine Image) / ImageID, идентификаторы подсетей (subnets), группы безопасности (security groups), IAM-роли и настройки дисковой подсистемы.

**NodeClaim** — стабильный и неизменяемый (immutable) ресурс, представляющий запрос на конкретный экземпляр узла. Заменяет устаревшую концепцию `Machine`. Если конфигурация меняется, NodeClaim удаляется и создается заново (механизм Drift).

**Disruption** (Прерывание) — объединённый механизм оптимизации кластера, управляющий жизненным циклом узлов. Включает в себя консолидацию (consolidation), обработку дрейфа конфигурации (drift) и удаление пустых или недоутилизированных узлов.

**Drift** (Дрейф конфигурации) — состояние, при котором параметры запущенного узла перестают соответствовать текущим настройкам `NodePool` или `NodeClass` (например, обновился AMI, версия Kubernetes или изменились метки). Karpenter автоматически заменяет такие узлы.

## Основные концепции

### Отличия от Cluster Autoscaler

| Характеристика | Cluster Autoscaler (CA) | Karpenter (v1.x) |
|----------------|-------------------|-----------|
| **Модель управления** | Работает с абстракцией Cloud Provider Node Groups (ASG в AWS, VMSS в Azure) | Напрямую управляет API инстансов (Fleet API), минуя группы узлов |
| **Скорость реакции** | Реактивная (ожидает цикл сканирования и реакции ASG, 3-10 минут) | Проактивная (мгновенный анализ бинпакинга и вызов API, <60 сек) |
| **Принятие решений** | Ограничено заранее созданными шаблонами групп | Свободный выбор из сотен типов инстансов под конкретный запрос |
| **Оптимизация** | Базовое удаление пустых узлов | Агрессивная/Сбалансированная консолидация и перепаковка для минимизации затрат |
| **Контроль стоимости** | Требует настройки нескольких групп (spot/on-demand) | Динамический приоритет Spot с автоматическим откатом на On-demand |
| **Обновление узлов** | Требует внешних инструментов или ручного вмешательства | Встроенный механизм Drift для автоматической замены устаревших узлов |

### Ключевые преимущества и возможности

**Безопасность и аутентификация (IRSA/Pod Identity)** — Karpenter требует прав для управления инстансами облака. В AWS рекомендуется использовать **EKS Pod Identity** или **IRSA (IAM Roles for Service Accounts)** для предоставления контроллеру необходимых полномочий без использования статических ключей.

**Интеллектуальный бинпакинг (Bin-packing)** — Karpenter анализирует не только запросы ресурсов (`requests`), но и правила близости (`affinity`), допуски (`tolerations`) и ограничения распределения (`topologySpreadConstraints`). Это позволяет выбрать один инстанс большого размера вместо нескольких маленьких, что дешевле и эффективнее.

**Сбалансированная консолидация (Balanced Consolidation)** — улучшенная политика консолидации (появилась в поздних v1.x). Она находит компромисс между экономией средств и стабильностью (pod churn), предотвращая пересоздание узлов ради мизерной выгоды, если стоимость прерывания подов слишком высока.

**Поддержка CEL (Common Expression Language)** — возможность использовать выражения CEL для динамического расчета параметров узла (например, `maxPods`, `kubeReserved`, `systemReserved`) на основе характеристик выбранного инстанса, что делает конфигурацию более гибкой.

**Управление прерываниями и гранулярные бюджеты (Disruption Budgets)** — в версии v1.x+ реализовано гранулярное управление прерываниями через `NodePool`, позволяя задавать бюджеты отдельно для разных причин удаления (`Underutilized`, `Empty`, `Drifted`). Karpenter использует расчетливый подход к управлению сбоями, балансируя между скоростью оптимизации и стабильностью кластера.

#### Логика работы бюджетов прерываний

Скорость, с которой Karpenter сокращает количество узлов, контролируется настройкой `budgets` в `NodePool`. Это позволяет регулировать темпы сокращения, гарантируя, что рабочие нагрузки не пострадают.

1.  **Расчет процента**: Если бюджет основан на процентах, Karpenter округляет произведение общего количества узлов на процент. Из полученного числа вычитается количество узлов, которые уже удаляются или находятся в состоянии `NotReady`.
2.  **Фиксированные бюджеты**: Если указано число, расчет упрощается: из этого числа вычитаются узлы в процессе удаления и узлы `NotReady`.
3.  **Приоритет ограничений**: Если в `NodePool` задано несколько бюджетов, Karpenter применяет **наиболее ограничительное** (минимальное) значение из всех рассчитанных.

*Пример:* Если один бюджет разрешает прерывание 15% узлов, а другой запрещает любые сбои в определенные часы (бюджет 0), то во время действия второго правила удаление узлов будет полностью заблокировано.

**Автоматическое исправление дрейфа** — если администратор изменяет параметры в `NodePool` (например, добавляет новую метку), Karpenter помечает старые узлы как «дрейфующие» и плавно заменяет их новыми, соответствующими новой конфигурации.

**Отсутствие «проклятия Node Groups»** — Cluster Autoscaler часто страдает от того, что в группе узлов находятся разные типы инстансов, что путает планировщик. Karpenter создаёт узлы с чёткими метками и характеристиками, идеально подходящими под нагрузку.

**Интеграция с DRA (Dynamic Resource Allocation)** — поддержка механизма Kubernetes для работы со сложным оборудованием (GPU, сетевые ускорители).

### Принцип работы

1. **Мониторинг Pending подов** — контроллер отслеживает события планировщика о невозможности разместить под.
2. **Анализ ограничений** — вычисляется пересечение всех требований пода (nodeSelector, affinity, ресурсные лимиты).
3. **Генерация NodeClaim** — Karpenter формирует запрос на создание оптимального узла.
4. **Запуск инстанса** — через Cloud Provider API (например, AWS EC2 Fleet) запрашивается конкретный тип инстанса напрямую, минуя группы автоскейлинга.
5. **Подготовка узла** — узел регистрируется в кластере, Karpenter накладывает необходимые метки и taints.
6. **Размещение нагрузки** — `kube-scheduler` видит новый узел и назначает на него поды.
7. **Постоянная оптимизация** — контроллер Disruption непрерывно ищет возможности для консолидации или замены узлов из-за дрейфа, соблюдая при этом заданные бюджеты и **[Pod Disruption Budgets (PDB)](../pod_disruption_budget.md)** приложений.

### Архитектурные компоненты

**Karpenter Controller** — основной управляющий процесс (Deployment).

**Webhook Server** — валидирует и мутирует CRD-ресурсы Karpenter.

**Disruption Controller** — отвечает за логику удаления и замены узлов для оптимизации.

**Cloud Provider Plugin** — модуль взаимодействия с конкретным облаком (AWS, Azure, Alibaba).

## Практические сценарии

### Масштабирование по длине очереди Kafka

Сценарий демонстрирует совместную работу KEDA (Kubernetes Event-driven Autoscaling), HPA и Karpenter для обработки всплесков данных.

**Архитектура решения:**

1. **KEDA (`ScaledObject`)**: Мониторит `consumer lag` в Kafka через Prometheus или напрямую.
2. **HPA**: При увеличении лага KEDA масштабирует количество подов-воркеров.
3. **Pending State**: Если в кластере нет места, новые поды переходят в `Pending`.
4. **Karpenter**:
    * Видит `Pending` поды и их требования (например, `topologySpreadConstraints` по зонам).
    * Выбирает оптимальные инстансы (например, c6g.xlarge для CPU-интенсивных задач).
    * Поднимает узлы за <60 секунд.
5. **Scale Down**: Когда очередь пуста, HPA удаляет поды. Karpenter видит недоутилизированные узлы и консолидирует их, возвращая лишние инстансы облаку.

### Масштабирование ресурсоёмких вычислительных нагрузок

Сценарий ориентирован на динамическое управление ресурсами для вычислительно intensive приложений (например, пакетная обработка данных, высоконагруженные базы данных), где стоимость простоя оборудования значительна.

1.  **Just-in-Time Provisioning**: Karpenter создает узлы с специализированными характеристиками (например, локальное NVMe хранилище, высокочастотные CPU) только при наличии задач в очереди. Это критично для дорогостоящего оборудования, простой которого напрямую влияет на TCO.
2.  **Поддержка специализированного железа**: В NodePool настраиваются требования к локальным дискам (`local SSD`), сетевой производительности (`100 GbE`) или конкретным архитектурам. Karpenter учитывает эти требования при планировании, позволяя эффективно использовать фрагментированные ресурсы.
3.  **Оптимизация затрат с Kubecost**: Интеграция с **[Kubecost](../../MonitoringLogging/kubecost.md)** позволяет отслеживать расходы на специализированные узлы в реальном времени, соотнося их с конкретными командами или проектами. В v1.x Karpenter также предоставляет **Native Cost Metrics** прямо на уровне NodePool.
4.  **Spot для пакетных задач**: Использование Spot-инстансов для длительных задач обработки данных с сохранением чекпоинтов, что снижает затраты.

## Дополнительная информация

### Мониторинг и алертинг

Karpenter экспортирует метрики Prometheus на порту `:8080/metrics`. Для production-сред критично настроить следующие сигналы:

| Метрика | Назначение | Критичность |
|---------|-----------|-------------|
| `karpenter_nodeclaims_created_total` | Общее количество созданных запросов на узлы | Информативно |
| `karpenter_nodeclaims_terminated_total` | Количество удаленных/прерванных узлов | Высокая (churn rate) |
| `karpenter_nodeclaims_failed_total` | Ошибки создания (Insufficient Capacity, IAM, квоты) | КРИТИЧЕСКИ |
| `karpenter_provisioning_scheduling_duration_seconds` | Время от `Pending` пода до создания `NodeClaim` | Средняя |
| `karpenter_voluntary_disruption_decisions_total` | Решения о консолидации/удалении узлов | Высокая |
| `karpenter_interruption_actions_total` | Реакции на прерывания (Spot, drift) | Высокая |
| `karpenter_cloudprovider_errors_total` | Ошибки API облака (throttling, quota exhaustion) | КРИТИЧЕСКИ |
| `karpenter_scheduler_queue_depth` | Количество подов, ожидающих provisioning | Средняя |

**Рекомендуемые алерты:**
*   **Provisioning bottleneck:** `karpenter_provisioning_scheduling_duration_seconds` p95 > 60 секунд.
*   **Consolidation storm:** резкий рост `karpenter_voluntary_disruption_decisions_total`.
*   **Registration delta:** разница между `karpenter_nodeclaims_created_total` и `karpenter_nodes_created_total` за последние 15 минут > 0 (инстанс создан, но не зарегистрировался в кластере).
*   **Cloud provider errors:** рост `karpenter_cloudprovider_errors_total` с label `error="InsufficientInstanceCapacity"`.

### Диагностика и устранение неисправностей

**Проверка логики планирования**:
Если поды висят в `Pending`, проверьте логи контроллера (причина отказа подбора, например "no instance types found").
```bash
kubectl logs -n karpenter -l app.kubernetes.io/name=karpenter --tail=100 -f
```

**Работа с NodeClaims**:
Если инстанс не создается в облаке, `NodeClaim` покажет ошибку API (например, квоты или IAM).
```bash
kubectl get nodeclaims
kubectl describe nodeclaim <name>
```

**Защита от прерываний (Disruption)**:
Для временного запрета удаления узла (например, при миграции БД):
```bash
kubectl annotate node <node-name> karpenter.sh/do-not-disrupt=true
```

### Типичные проблемы и решения

| Симптом | Возможная причина | Решение |
|---------|-----------------|---------|
| Поды `Pending`, NodeClaim не создается | Требования пода не соответствуют ни одному NodePool | Проверьте `nodeSelector`, `tolerations`, `affinity` |
| NodeClaim создан, но узел не появляется | Ошибка kubelet, AMI, IAM, сеть | Проверьте `kubectl describe nodeclaim`, логи kubelet через SSM |
| Консолидация не запускается | PDB блокирует eviction, `do-not-disrupt` annotation | Проверьте `karpenter_voluntary_disruption_eligible_nodes` |
| Частые Spot-прерывания | Слишком узкий выбор типов инстансов | Расширьте `requirements` в NodePool |
| Двойной drain (Karpenter + NTH) | AWS Node Termination Handler запущен параллельно | Отключите NTH, Karpenter handles interruptions natively |

### Лучшие практики эксплуатации

1.  **Drift Mechanism**: Дрейф включен по умолчанию. Любое изменение в `NodeClass` (смена SG, VNet, AMI) приведет к планомерному пересозданию всех узлов.
2.  **Spot Diversity**: В `requirements` NodePool указывайте как можно больше типов инстансов. Ограничение пула одним типов приведет к отказу при его дефиците.
3.  **Over-provisioning**: Используйте `Pause Pods` (поды с низким приоритетом) для резервирования места. Karpenter вытеснит их и мгновенно разместит критичную нагрузку.
4.  **Limits**: Обязательно устанавливайте `spec.limits` в NodePool для защиты от бесконечного спавна узлов при ошибках конфигурации деплоймента.
5.  **NodePool Isolation**: Разделяйте NodePool по типам workloads (system, web, batch) с разными taints. Один универсальный NodePool для всех нагрузок — антипаттерн.
6.  **Controller Placement**: Запускайте контроллер Karpenter на системных узлах, которые он не управляет (не на Karpenter-пуле). Это предотвращает bootstrap-зависимость при пересоздании узлов.
7.  **Scheduled Disruption Budgets**: Замораживайте консолидацию во время пиковой нагрузки (например, `nodes: "0"` в рабочие часы).
8.  **Termination Grace Period**: Настраивайте `terminationGracePeriod` на уровне NodePool с запасом на graceful shutdown приложений.

### Ограничения

**Привязка к облачному API** — Karpenter не может работать без доступа к API управления инстансами облачного провайдера.

**Поддержка провайдеров** — AWS (полная/зрелая), Azure (GA с 2026), GCP (альфа/ограниченно, рекомендуется GKE NAP).

**Bare-metal и On-premise** — не поддерживаются напрямую без кастомных плагинов. Для таких случаев следует использовать Cluster Autoscaler.

**Сложность отладки** — из-за высокой динамичности кластера требуется качественный мониторинг (Grafana Dashboard) для отслеживания причин создания и удаления узлов.

**Нет pod-level rightsizing** — Karpenter оптимизирует узлы на основе `requests`, а не реального потребления. Для коррекции requests используйте VPA.

## Советы для собеседования

**Вопрос:** Что такое NodePool в Karpenter и какие два ключевых ограничения вы можете определить внутри него для контроля подготовки узлов?
**Ответ:** NodePool — это ресурс Karpenter (стабильный API в v1.x), который определяет правила управления незапланированными подами и характеристики создаваемых узлов. Два ключевых ограничения:
1.  **Типы экземпляров (Instance Types)**: можно указать список разрешенных семейств (например, `t3`, `m5`) для контроля стоимости и производительности.
2.  **Зоны (Zones)**: ограничение предоставления узлов определенными зонами доступности, что критично для приложений с Persistent Volumes или зональными зависимостями.

**Вопрос:** В чем разница между NodePool и NodeClass (например, EC2NodeClass)?
**Ответ:** NodePool определяет «что» нам нужно (требования к CPU, RAM, архитектуре, лимиты, политики прерываний). NodeClass определяет «как» это реализовать в конкретном облаке (какой AMI использовать, в каких подсетях запускать, какие роли назначать). Это разделение позволяет использовать один NodePool для разных облаков или разных конфигураций сети.

**Вопрос:** Как работает механизм Consolidation в Karpenter?
**Ответ:** Karpenter постоянно анализирует утилизацию узлов. Если узел пуст (`WhenEmpty`) или недоутилизирован (`WhenEmptyOrUnderutilized`), Karpenter симулирует выселение подов и проверяет, можно ли разместить их на меньшем числе узлов или более дешевых типах инстансов. При успешной симуляции старый узел удаляется. Скорость консолидации ограничена `consolidateAfter` и бюджетами прерываний.

**Вопрос:** В чем разница между Drift и Expiration в Karpenter?
**Ответ:** Drift — это реакция на изменение желаемого состояния (обновился AMI, метка или K8s версия). Узлы дрейфуют относительно `NodePool`/`NodeClass` и заменяются автоматически. Expiration — это плановое удаление узлов по таймауту (`expireAfter`), необходимое для периодической ротации и снижения рисков утечек памяти/фрагментации. Оба механизма являются частью Disruption Controller.

**Вопрос:** Почему Karpenter быстрее Cluster Autoscaler?
**Ответ:** Cluster Autoscaler работает через абстракцию Node Groups (ASG/VMSS), что добавляет задержку на валидацию шаблона и запуск новых экземпляров группой. Karpenter вызывает API облака напрямую (EC2 Fleet, Azure VM API), минуя группу, и использует собственную симуляцию планировщика вместо ожидания событий от kube-scheduler. Это сокращает время появления нового узла с 3-4 минут до 45-60 секунд.
