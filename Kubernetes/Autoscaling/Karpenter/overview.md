# Обзор и основные концепции Karpenter

> **Важно:** Karpenter предназначен для облачных провайдеров (AWS (Amazon Web Services), Azure, GCP (Google Cloud Platform)). Для локальных окружений (on-premise, bare-metal) используйте **[Cluster Autoscaler](../cluster_autoscaler_detailed.md)** с группами узлов или **Volcano** для пакетных (batch) нагрузок.

## Определения

**Karpenter** — высокопроизводительный оператор Kubernetes для автоматического масштабирования кластера (Node Autoscaling), который динамически создаёт узлы оптимального размера в ответ на требования ожидающих (pending) подов. Проект передан в CNCF (Cloud Native Computing Foundation) и является стандартом де-факто для эффективного управления мощностями в AWS. Текущая стабильная версия — v1.x.

**NodePool** — основной CRD (Custom Resource Definition) Karpenter, определяющий намерения (intent) по созданию узлов: допустимые типы инстансов, зоны доступности, ограничения по стоимости (spot/on-demand) и политики прерывания (disruption). Пришёл на замену устаревшему `Provisioner`.

**EC2NodeClass** (AWS) / **NodeClass** — ресурс, описывающий инфраструктурные параметры узла: AMI (Amazon Machine Image), идентификаторы подсетей (subnets), группы безопасности (security groups), IAM-роли и настройки дисковой подсистемы.

**NodeClaim** — эфемерный ресурс, представляющий запрос на конкретный экземпляр узла. Заменяет концепцию `Machine` и является неизменяемым (immutable) после создания.

**Disruption** (Прерывание) — объединённый механизм оптимизации кластера, включающий в себя консолидацию (consolidation), обработку дрейфа конфигурации (drift) и удаление пустых узлов.

**Drift** (Дрейф конфигурации) — состояние, при котором параметры запущенного узла перестают соответствовать текущим настройкам `NodePool` или `EC2NodeClass` (например, обновился AMI или изменились метки). Karpenter автоматически заменяет такие узлы.

## Основные концепции

### Отличия от Cluster Autoscaler

| Характеристика | Cluster Autoscaler (CA) | Karpenter |
|----------------|-------------------|-----------|
| **Модель управления** | Работает с абстракцией Cloud Provider Node Groups (ASG в AWS) | Напрямую управляет API инстансов (Fleet API), минуя группы узлов |
| **Скорость реакции** | Реактивная (ожидает цикл сканирования и реакции ASG) | Проактивная (мгновенный анализ бинпакинга и вызов API) |
| **Принятие решений** | Ограничено заранее созданными шаблонами групп | Свободный выбор из сотен типов инстансов под конкретный запрос |
| **Оптимизация** | Базовое удаление пустых узлов | Агрессивная консолидация и перепаковка для минимизации затрат |
| **Контроль стоимости** | Требует настройки нескольких групп (spot/on-demand) | Динамический приоритет Spot с автоматическим откатом на On-demand |
| **Обновление узлов** | Требует внешних инструментов или ручного вмешательства | Встроенный механизм Drift для автоматической замены устаревших узлов |

### Ключевые преимущества

**Интеллектуальный бинпакинг (Bin-packing)** — Karpenter анализирует не только запросы ресурсов (`requests`), но и правила близости (`affinity`), допуски (`tolerations`) и ограничения распределения (`topologySpreadConstraints`). Это позволяет выбрать один инстанс большого размера вместо нескольких маленьких, что дешевле и эффективнее.

**Управление жизненным циклом (Disruption Budgets)** — в версии v1.0+ введено гранулярное управление прерываниями. Можно задать разные бюджеты для различных причин удаления узлов (например, запретить консолидацию в пиковые часы, но разрешить удаление пустых узлов).

**Автоматическое исправление дрейфа** — если администратор изменяет параметры в `NodePool` (например, добавляет новую метку), Karpenter помечает старые узлы как «дрейфующие» и плавно заменяет их новыми, соответствующими новой конфигурации.

**Отсутствие «проклятия Node Groups»** — Cluster Autoscaler часто страдает от того, что в группе узлов находятся разные типы инстансов, что путает планировщик. Karpenter создаёт узлы с чёткими метками и характеристиками, идеально подходящими под нагрузку.

### Принцип работы

1. **Мониторинг Pending подов** — контроллер отслеживает события планировщика о невозможности разместить под.
2. **Анализ ограничений** — вычисляется пересечение всех требований пода (nodeSelector, affinity, ресурсные лимиты).
3. **Генерация NodeClaim** — Karpenter формирует запрос на создание оптимального узла.
4. **Запуск инстанса** — через Cloud Provider API (например, AWS EC2 Fleet) запрашивается конкретный тип инстанса.
5. **Подготовка узла** — узел регистрируется в кластере, Karpenter накладывает необходимые метки и taints.
6. **Размещение нагрузки** — `kube-scheduler` видит новый узел и назначает на него поды.
7. **Постоянная оптимизация** — контроллер Disruption непрерывно ищет возможности для консолидации или замены узлов из-за дрейфа.

### Архитектурные компоненты

**Karpenter Controller** — основной управляющий процесс (Deployment).

**Webhook Server** — валидирует и мутирует CRD-ресурсы Karpenter.

**Disruption Controller** — отвечает за логику удаления и замены узлов для оптимизации.

**Cloud Provider Plugin** — модуль взаимодействия с конкретным облаком (AWS, Azure).

## Практические сценарии

### Масштабирование по длине очереди Kafka

Сценарий демонстрирует совместную работу KEDA (Kubernetes Event-driven Autoscaling), HPA и Karpenter для обработки всплесков данных.

**Архитектура решения:**

1. **KEDA (`ScaledObject`)**: Мониторит `consumer lag` в Kafka через Prometheus или напрямую.
2. **HPA**: При увеличении лага KEDA масштабирует количество подов-воркеров.
3. **Pending State**: Если в кластере нет места, новые поды переходят в `Pending`.
4. **Karpenter**:
    * Видит `Pending` поды и их требования (например, `topologySpreadConstraints` по зонам).
    * Выбирает оптимальные инстансы (например, c6g.xlarge для CPU-интенсивных задач).
    * Поднимает узлы за <60 секунд.
5. **Scale Down**: Когда очередь пуста, HPA удаляет поды. Karpenter видит недоутилизированные узлы и консолидирует их, возвращая лишние инстансы облаку.

## Дополнительная информация

### Интеграции

**[HPA (Horizontal Pod Autoscaler)](../HPA/index.md)** — основной триггер для работы Karpenter.

**[VPA (Vertical Pod Autoscaler)](../vpa_detailed.md)** — уточняет запросы подов, что позволяет Karpenter точнее подбирать размер узлов.

**[KEDA (Kubernetes Event-driven Autoscaling)](../keda/keda_concepts.md)** — позволяет масштабировать узлы на основе внешних событий.

**[Pod Disruption Budget (PDB)](../pod_disruption_budget.md)** — Karpenter строго соблюдает PDB при проведении любых операций оптимизации (consolidation/drift).

### Ограничения

**Привязка к облачному API** — Karpenter не может работать без доступа к API управления инстансами облачного провайдера.

**Поддержка провайдеров** — AWS (полная/стабильная), Azure (стабильная), GCP (бета-версия).

**Bare-metal и On-premise** — не поддерживаются напрямую. Для таких случаев следует использовать Cluster Autoscaler.

**Сложность отладки** — из-за высокой динамичности кластера требуется качественный мониторинг (Grafana Dashboard) для отслеживания причин создания и удаления узлов.
