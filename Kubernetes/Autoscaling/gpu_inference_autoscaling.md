# GPU-инференс в Kubernetes: автоскейлинг, ускорение деплоя и шеринг

**Актуально для:** Kubernetes 1.31+ (DRA — beta с 1.32); замеры длительности этапов — авторские (кластер доклада)

## Определения

* **Inference (инференс)** — выполнение модели на входных данных в режиме веб-сервиса: HTTP/gRPC-запрос → модель → ответ. В отличие от обучения, инференс — долгоживущий сервис с требованием доступности 24/7.
* **Triton Inference Server** — open source сервер инференса от NVIDIA (C++ под капотом): динамический батчинг запросов, ансамбли моделей, поддержка TensorRT, PyTorch, TensorFlow, ONNX, OpenVINO. Модель кладётся в репозиторий, сервер отдаёт HTTP (8000), gRPC (8001) и metrics (8002). См. [GPU и ML-нагрузки в Dockerfile](../../Docker/Dockerfile/dockerfile-gpu-ml.md).
* **Dynamic batching** — объединение входящих запросов в батчи на лету для повышения утилизации GPU.
* **HPA (Horizontal Pod Autoscaler)** — масштабирование числа реплик подов. Для GPU-инференса — основной механизм (см. ниже, почему VPA не подходит).
* **Prometheus Adapter** — компонент Aggregation Layer, конвертирующий PromQL-запросы в Custom Metrics API для HPA. Механика — в [Prometheus Adapter: настройка](./HPA/prometheus_adapter_setup.md).
* **GPU Operator** — набор сервисов NVIDIA, готовящих ноду под GPU-нагрузки: устанавливает драйверы, Container Toolkit и Device Plugin, который определяет, сколько GPU-ресурсов стало доступно в Kubernetes.
* **Cluster Autoscaler** — масштабирование числа нод кластера (в облаке поднимает ВМ с GPU, on-premise — через Cluster API/Metal3).

## Основные концепции

### Inference как веб-сервис

Масштабирование инференса — та же задача, что масштабирование веб-сервиса, но с GPU как узким местом. Масштаб проблемы: OpenAI поддерживает около 3600 GPU-серверов для 400 млн активных пользователей в неделю, и даже при такой инфраструктуре статус-страница показывает периоды деградации (данные из доклада). Типичные вопросы платформы инференса: динамический батчинг запросов, управление моделями разных форматов, разные конфигурации железа, деплой модели на несколько видеокарт одновременно, inference-графы, трассировка. На эти вопросы отвечает Triton Inference Server — именно его выбирают как open source-решение для инференса. Его минус — автоскейлинг ресурсов, который и рассматривается в этом файле.

### Почему VPA не подходит для GPU-инференса

Vertical Pod Autoscaler не подходит: GPU — расширенные ресурсы (`nvidia.com/gpu`), выделяемые целыми числами и закрепляемые за подом. Изменить размер GPU «на лету» нельзя — нужна новая реплика с новым выделением устройства. Поэтому горизонтальное масштабирование (HPA) — единственный нативный путь для GPU-нагрузок.

### Конвейер автоскейлинга инференса

```
Трафик → Triton (в очереди скапливаются запросы) → Prometheus (метрики Triton, порт 8002)
   → Prometheus Adapter (Custom Metrics API) → HPA (таргет превышен)
   → новая реплика Triton (требуется ресурс nvidia.com/gpu)
   → [нет свободной ноды] Cluster Autoscaler (новая нода с GPU)
   → GPU Operator (драйверы, Container Toolkit, Device Plugin)
   → pull образа Triton → нода готова к аллокации → реплика готова
```

Scale-down: трафик пропадает → HPA уничтожает реплику → нода помечается кандидатом на удаление → через некоторое время скейлится в ноль.

### Четыре этапа и их длительность

Замеры из доклада (авторские, на его кластере; воспроизводите на своём железе):

| Этап | Длительность | Что происходит |
|:---|:---|:---|
| Создание реплики Triton через HPA | ~1 мин | HPA добавляет реплику, kube-scheduler ищет ноду со свободным `nvidia.com/gpu` |
| Сетап ноды Cluster Autoscaler-ом | до 5 мин | Подъём ВМ с GPU, зависит от выбранного флейвора |
| GPU Operator | до 3 мин | Установка драйверов, Container Toolkit, Device Plugin |
| Pull образа Triton | ~10 мин | Образ ~20 ГБ, слои до 6 ГБ |

Итого: деплой инференса «с нуля» занимает ~15 минут и больше. Узкие горлышки — не только сеть: экстракция слоёв на ноду происходит последовательно (см. [Troubleshooting](#образ-скачивается-быстро-но-под-долго-не-стартует)).

## Ускорение этапов

### Веса модели вовне

Не хранить веса в образе — иначе каждая реплика тянет их при старте. Варианты хранилища (из доклада):

* NFS-хранилище (в облаке — файловый storage на NFS-протоколе);
* Longhorn — для кэша (автор тестировал его ранее как read-write PVC, к которому обращаются несколько реплик; работает по протоколу NFS, поэтому при наличии NFS-хранилища можно обойтись им);
* CSI для S3-бакета — веса подтягиваются в каждую реплику по мере необходимости.

Альтернатива — снапшотить сами веса (PVC snapshot), а не ноду целиком.

> **Edge case (LLM):** веса больших моделей (например, DeepSeek на 600 млрд параметров) занимают ~1 ТБ; скачивать их на каждую реплику при автоскейлинге — плохая идея, вынос в общее хранилище обязателен (вопрос из зала, ответ автора).

### Кэширование образов ближе к нодам

Harbor позволяет кэшировать слои на нодах рядом с ворклоудами и скачивать образы оттуда, а не из удалённого реестра. Другой класс решений — P2P-распределение образов (Dragonfly, Kraken): слои живут на разных нодах, система работает как торрент-трекер (упомянуто в вопросах из зала; в базе не покрывается).

### Ленивая загрузка слоёв (lazy loading)

Суть: подгружать из реестра только те слои, которые реально используются в данный момент. Исследование, приведённое в докладе: 76% времени старта контейнера уходит на загрузку пакетов, но только 6,5% этих данных требуются для начала полезной работы контейнером. Для Kubernetes есть snapshotters: eStargz, Nydus, SOCI — у них опубликованы бенчмарки с многократным ускорением pull-а относительно нативного способа.

**Почему snapshotters не спасли Triton (опыт автора):** Triton запустился не за 6,5 мин, а за 1,5 мин, но слои Triton огромны (до 6 ГБ) — при запросе к Triton слой всё равно вытягивался из удалённого реестра, и до появления логов проходило ~6 минут. Вывод: проблема не в скачивании слоёв, а в их экстракции.

### Сжатие ZSTD вместо GZIP

Docker по умолчанию использует GZIP — достаточно старый формат сжатия. ZSTD создан для увеличения скорости компрессии/декомпрессии слоёв. BuildKit позволяет указать формат сжатия при сборке:

```bash
# Сборка и пуш образа со слоями в ZSTD (вместо GZIP по умолчанию)
docker buildx build \
  --output type=image,name=<registry>/<image>,push=true,compression=zstd .
# → образ в реестре со слоями application/vnd.oci.image.layer.v1.tar+zstd
```

Параметры (верифицировано по документации Docker): `compression` принимает `uncompressed`/`gzip`/`estargz`/`zstd`; `compression-level` — 0–22 для zstd (3–6 — default, 9–22 ≈ внутренний уровень 11); `force-compression=true` пережимает слои, унаследованные от базового образа.

Результат автора: время pull-а образа Triton сократилось с 6,5 до 2 минут — частично решило задачу.

### Почему чистка Dockerfile даёт только 5–10%

Стандартные методики (чистка кэшей, multi-stage, объединение слоёв) сокращают образ всего на 5–10%: Triton содержит ~20 ГБ библиотек, а конкурентный образ AMD (ROCm + PyTorch, аналог CUDA) весит ~60 ГБ в распакованном виде. Время аплоуда сокращается незначительно (из 7 минут — до 6,5). Поэтому для больших GPU-образов оптимизации Dockerfile не заменяют кэширование, ленивую загрузку и ZSTD.

### Снапшоты нод

Самый быстрый вариант: заснапшотить подготовленную ноду (с драйверами и образом Triton) и деплоить из снапшота. Минусы: не всегда возможен, складирование больших образов, отсутствие гибкости — снапшот всегда старой версии ноды.

## Практические сценарии

### Сценарий 1: HPA для Triton по кастомной метрике

Схема: метрики Triton (порт 8002) → Prometheus → Prometheus Adapter → HPA. Манифест иллюстративный (имя метрики и PromQL — под вашу установку; механика adapter — в [Prometheus Adapter](./HPA/prometheus_adapter_setup.md)):

```yaml
# Иллюстративный манифест: HPA Triton по кастомной метрике очереди
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: triton-inference
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: triton
  minReplicas: 1
  maxReplicas: 10
  metrics:
  - type: Pods
    pods:
      metric:
        name: <triton-custom-metric>  # PromQL-метрика Triton через adapter
      target:
        type: AverageValue
        averageValue: "100"
```

Валидация:

```bash
kubectl get --raw "/apis/custom.metrics.k8s.io/v1beta1" | jq .
# → список кастомных метрик, включая метрику Triton
kubectl describe hpa triton-inference
# → Metrics: <triton-custom-metric> ... текущие/таргет
```

### Сценарий 2: вынос весов модели на NFS

```yaml
# Иллюстративный манифест: веса модели на NFS, общие для всех реплик
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: model-weights
spec:
  accessModes: [ReadOnlyMany]
  storageClassName: nfs-client
  resources:
    requests:
      storage: 50Gi
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: triton
spec:
  template:
    spec:
      containers:
      - name: triton
        image: nvcr.io/nvidia/tritonserver:24.01-py3
        volumeMounts:
        - name: weights
          mountPath: /models
        command: ["tritonserver", "--model-repository=/models"]
      volumes:
      - name: weights
        persistentVolumeClaim:
          claimName: model-weights
          readOnly: true
```

## Troubleshooting

### Образ скачивается быстро, но под долго не стартует

**Симптом:** слои докачаны, но логи контейнера появляются только через ~6 минут.
**Причина:** узкое место — не download, а последовательная экстракция (разархивация) слоёв на ноду.
**Решение:** пересобрать образ со слоями в ZSTD (`compression=zstd`, см. выше); использовать snapshotter (eStargz/Nydus/SOCI) — но учитывайте опыт автора: для очень больших слоёв Triton эффект ограничен.

### Совместимость CUDA, драйвера и фреймворка (вопрос из зала)

Зачем CUDA в образе, если есть NVIDIA Container Toolkit? Разделение ответственности: на хосте — драйверы + Container Toolkit (позволяет контейнерам работать через драйверы), в образе — конкретная версия CUDA под фреймворк (разные версии PyTorch/TensorFlow требуют разных версий CUDA). Матрица совместимости (версия CUDA ↔ фреймворк ↔ драйвер ↔ ядро ОС) — в [CUDA Compatibility Guide](https://docs.nvidia.com/deploy/cuda-compatibility/) и в [GPU и ML-нагрузки в Dockerfile](../../Docker/Dockerfile/dockerfile-gpu-ml.md).

### Балансировка перед серверами инференса (вопрос из зала)

Автор использует Istio (service mesh). Triton в их деплое привязан к ноде 1:1: на ноде с одной видеокартой модель ограничена её видеопамятью. Для LLM-нагрузок альтернатива — специализированные серверы (vLLM и аналоги); выбор фреймворка — дискуссионная тема: Triton универсален (LLM, эмбеддинги, обычные ML-модели), балансировка либо внутри Triton, либо несколькими репликами Triton через HPA.

## Best Practices

### Выбор планировщика для GPU-кластера

Нативный `kube-scheduler` с `nvidia.com/gpu` годится для небольших кластеров, но при деплое нескольких инференсов одновременно возникает гонка за видеокартами: «кто первый съел, тот и прав» — второй под ждёт. Критерии выбора специализированного планировщика (из доклада): гарантия ресурсов (квоты на команду), прерывание (preemption приоритетных задач), gang scheduling (all-or-nothing для распределённого обучения), очереди с квотами, мониторинг. Финалисты доклада — Kueue и Koordinator; выбран **Kueue** как более зрелый (Koordinator на момент доклада вышел только этим летом). См. [Kueue](../Scheduling/kueue.md) и [обзор решений для планирования](../Scheduling/scheduling_solutions_overview.md).

### Ускорение деплоя — чек-лист

1. Веса модели — вовне (NFS / Longhorn / CSI-S3), снапшоты PVC.
2. Образы — кэш в Harbor рядом с нодами; P2P (Dragonfly/Kraken) для больших кластеров.
3. Сжатие слоёв — ZSTD через BuildKit.
4. Lazy loading (eStargz/Nydus/SOCI) — для образов с большим числом мелких слоёв; для Triton эффект ограничен размером слоёв.
5. Снапшоты нод — только когда гибкость не важна.
