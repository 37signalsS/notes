# Автоматическое масштабирование в Kubernetes

## Определения

**Автоматическое масштабирование** — одна из ключевых возможностей Kubernetes, позволяющая динамически управлять ресурсами кластера и приложений в зависимости от нагрузки. Это обеспечивает эластичность, высокую доступность и оптимизацию затрат.

Существует несколько ключевых механизмов, работающих на разных уровнях:

*   **Horizontal Pod Autoscaler (HPA):** Автоматически увеличивает или уменьшает количество подов (`Deployment`, `ReplicaSet`, `StatefulSet`) в ответ на изменение нагрузки. Работает на уровне **подов**.
*   **Vertical Pod Autoscaler (VPA):** Автоматически настраивает запросы (`requests`) и лимиты (`limits`) на CPU и RAM для контейнеров в подах. Работает на уровне **контейнеров**.
*   **Cluster Autoscaler (CA):** Автоматически добавляет или удаляет узлы (виртуальные машины) в кластере. Работает на уровне **инфраструктуры**.
*   **KEDA (Kubernetes Event-driven Autoscaling):** Легковесный компонент, который расширяет возможности стандартного HPA, позволяя масштабировать приложения на основе событий из десятков различных источников, включая возможность масштабирования до нуля.
*   **Karpenter:** Гибкий и высокопроизводительный инструмент для автомасштабирования кластеров, который создает новые узлы оптимального размера "точно в срок" под требования ожидающих подов.

---

## Основные концепции

### Horizontal Pod Autoscaler (HPA)

#### Как HPA принимает решения?

HPA работает как термостат для вашего приложения. Он периодически (по умолчанию каждые 15 секунд) запрашивает метрики у **Metrics Server**, сравнивает их с целевыми значениями и рассчитывает необходимое количество реплик по формуле:

`желаемыеРеплики = ceil(текущиеРеплики * ( текущаяМетрика / желаемаяМетрика ))`

**Пример:**
*   `текущиеРеплики`: 3
*   `желаемаяМетрика` (цель по CPU): 50%
*   `текущаяМетрика` (реальная нагрузка): 90%

`желаемыеРеплики = ceil(3 * (90 / 50)) = ceil(3 * 1.8) = ceil(5.4) = 6`

HPA увеличит количество реплик с 3 до 6.

#### Типы метрик для HPA

-   **Метрики ресурсов (Resource Metrics):** Среднее потребление CPU (`Utilization`) или среднее значение RAM (`AverageValue`). Это базовые метрики, но они не всегда отражают реальную нагрузку на приложение.
-   **Кастомные метрики (Custom Metrics):** Метрики, связанные с объектами Kubernetes, но не являющиеся стандартными (например, количество запросов в секунду (RPS) на под). Требуют установки адаптера, например, **Prometheus Adapter**, который "переводит" метрики из Prometheus в понятный для HPA формат.
-   **Внешние метрики (External Metrics):** Метрики из внешних систем, не связанных напрямую с объектами Kubernetes. Это идеальный вариант для масштабирования на основе бизнес-показателей.
    -   **Примеры:** Длина очереди в RabbitMQ или Kafka, количество активных пользователей в базе данных.
    -   Также требуют настройки адаптера для соответствующей системы.

Использование кастомных и внешних метрик позволяет создавать более интеллектуальные и точные правила масштабирования, которые реагируют на реальную потребность бизнеса, а не только на утилизацию "железа".

### KEDA: Масштабирование на основе событий

**Ключевая возможность:** KEDA может масштабировать количество реплик `Deployment` **от нуля до N** и обратно. Если событий нет, KEDA может уменьшить количество реплик до нуля, экономя ресурсы. Как только в источнике появляется событие (например, сообщение в очереди Kafka), KEDA активирует `Deployment`, создавая поды для обработки нагрузки.

**Как это работает:**
1.  **Оператор:** KEDA устанавливается в кластер как оператор.
2.  **`ScaledObject`:** Вы создаете кастомный ресурс `ScaledObject`, в котором описываете:
    *   На какой `Deployment` воздействовать.
    *   Источник событий (`scaler`), например, Prometheus, Kafka, RabbitMQ, Cron и др.
    *   Пороговые значения для масштабирования.
3.  **Управление HPA:** На основе этих данных KEDA сама создает и управляет нативным объектом HPA.

KEDA является идеальным решением для асинхронных и событийно-ориентированных архитектур, где нагрузка непредсказуема и может отсутствовать в течение долгого времени.

### Vertical Pod Autoscaler (VPA)

VPA решает две проблемы:

1.  **Перерасход ресурсов (Overprovisioning):** Когда для подов запрашивается значительно больше ресурсов, чем им реально нужно.
2.  **Нехватка ресурсов (Underprovisioning):** Когда запрошено слишком мало ресурсов, что приводит к снижению производительности или `OOMKilled`.

#### Компоненты VPA

1.  **VPA Recommender:** Следит за историей потребления ресурсов и предлагает новые, оптимальные значения `requests`.
2.  **VPA Updater:** Отвечает за применение рекомендаций, выселяя (`evicts`) поды для обновления их ресурсов.
3.  **VPA Admission Controller:** Вебхук, который перехватывает запросы на создание подов и подменяет в них `requests` на рекомендованные.

#### Режимы работы (`updateMode`)

-   **`Off` (Режим "только рекомендации"):** Самый безопасный режим для начала. VPA только анализирует потребление и записывает рекомендации, не применяя их.
-   **`Initial`:** VPA применяет рекомендации **только в момент создания пода**. Уже работающие поды не затрагиваются.
-   **`Recreate`:** VPA применяет рекомендации как при создании, так и для уже работающих подов, **перезапуская** их при необходимости. Может вызывать простои для приложений с одной репликой.
-   **`Auto`:** Работает так же, как `Recreate`, но в будущем позволит применять изменения без перезапуска пода.

### Cluster Autoscaler (CA)

#### Как Cluster Autoscaler принимает решения?

##### Масштабирование вверх (Scale-Up)

CA решает добавить новый узел, если обнаруживает в кластере поды в состоянии `Pending`, которые не могут быть размещены из-за нехватки ресурсов (CPU, RAM, GPU).

**Процесс:**
1.  Обнаруживаются `Pending` поды.
2.  CA проверяет заранее определенные **группы узлов (Node Groups)** и симулирует, поможет ли добавление нового узла из одной из этих групп разместить поды.
3.  Если да, CA отправляет запрос в API облака на создание нового узла в рамках выбранной группы.

##### Масштабирование вниз (Scale-Down)

CA решает удалить узел, если он одновременно:

1.  **Слабо утилизирован** в течение определенного времени (по умолчанию 10 минут, порог утилизации < 50%).
2.  Все его поды **могут быть безопасно перемещены** на другие узлы.

### Karpenter: Продвинутая альтернатива Cluster Autoscaler

В отличие от стандартного Cluster Autoscaler, который работает с предопределенными группами узлов, Karpenter подходит к задаче иначе.

**Как работает Karpenter:**
1.  Он напрямую отслеживает поды в состоянии `Pending`.
2.  Анализирует их требования (`requests`, `affinity`, `tolerations` и т.д.).
3.  **Мгновенно создает и конфигурирует новый узел оптимального размера**, который идеально подходит под требования ожидающих подов.

**Ключевые преимущества перед CA:**
*   **Скорость:** Реакция на нехватку ресурсов и запуск нового узла происходит значительно быстрее.
*   **Эффективность:** Вместо выбора из готовых "шаблонов" узлов, Karpenter создает узел "точно в срок" (`just-in-time`) с нужным количеством CPU, памяти и нужного типа (например, с GPU), что оптимизирует затраты.
*   **Гибкость:** Упрощает управление разнообразными типами нагрузок, так как не требует ручного создания и поддержки множества групп узлов.

Karpenter является предпочтительным выбором для динамичных сред с сильно меняющейся нагрузкой.

## Практические сценарии

### Настройка HPA

#### Предварительные требования

1.  **Установить Metrics Server:** Для работы с базовыми метриками (`cpu`, `memory`) в кластере должен быть развернут компонент **Metrics Server**. Он собирает данные о потреблении ресурсов с каждого узла и предоставляет их HPA.
2.  **Задать запросы (requests) для контейнеров:** Чтобы HPA мог корректно рассчитывать утилизацию CPU в процентах, у контейнеров в вашем `Deployment` должны быть установлены запросы на ресурсы (`spec.containers.resources.requests`).
    ```yaml
    resources:
      requests:
        cpu: "200m" # 200 милли-ядер
        memory: "256Mi"
    ```
    Без этого HPA не знает, от какого базового значения считать процент.

#### Анатомия манифеста HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
  namespace: default
spec:
  # 1. Ссылка на масштабируемый ресурс
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app

  # 2. Границы масштабирования
  minReplicas: 2
  maxReplicas: 10

  # 3. Метрики для принятия решений
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization # Тип цели — среднее использование
          averageUtilization: 50
    - type: Resource
      resource:
        name: memory
        target:
          type: AverageValue
          averageValue: 200Mi

  # 4. Поведение при масштабировании
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Pods
        value: 2
        periodSeconds: 60
```
1.  **`scaleTargetRef`**: Указывает, каким `Deployment` или `StatefulSet` будет управлять HPA.
2.  **`minReplicas` / `maxReplicas`**: Задает границы масштабирования.
3.  **`metrics`**: Список метрик. HPA рассчитает необходимое количество реплик для *каждой* метрики и выберет **наибольшее** значение.
4.  **`behavior`**: Позволяет тонко настроить скорость масштабирования, чтобы избежать "дребезжания" (быстрого увеличения и уменьшения реплик).

### Настройка VPA

#### Анатомия манифеста VPA
```yaml
apiVersion: "autoscaling.k8s.io/v1"
kind: VerticalPodAutoscaler
metadata:
  name: my-app-vpa
spec:
  # 1. Ссылка на целевой контроллер
  targetRef:
    apiVersion: "apps/v1"
    kind:       Deployment
    name:       my-app

  # 2. Политика обновления
  updatePolicy:
    updateMode: "Off"

  # 3. Ограничения на ресурсы
  resourcePolicy:
    containerPolicies:
      - containerName: '*'
        minAllowed:
          cpu: 100m
          memory: 50Mi
        maxAllowed:
          cpu: "1"
          memory: 500Mi
```

### Настройка Cluster Autoscaler

#### Ключевые параметры конфигурации (флаги)

*   `--scan-interval`: Как часто сканировать кластер (по умолчанию `10s`).
*   `--scale-down-utilization-threshold`: Порог утилизации узла, ниже которого он — кандидат на удаление (по умолчанию `0.5`).
*   `--scale-down-unneeded-time`: Как долго узел должен быть слабо утилизирован перед удалением (по умолчанию `10m`).
*   `--skip-nodes-with-local-storage`: Запрещает CA удалять узлы с подами, использующими `hostPath` или `emptyDir` (по умолчанию `true`).
*   `--balance-similar-node-groups`: Если `true`, CA будет стараться сбалансировать количество узлов в похожих группах (по умолчанию `false`).

### Совместная работа: Синергия

Эти механизмы создают полную цепочку автоматического масштабирования:

1.  **Резко возрастает трафик.**
2.  **HPA** (или **KEDA**) замечает рост нагрузки (потребление CPU, длина очереди) и решает увеличить количество подов с 3 до 10.
3.  Новые 7 подов переходят в состояние `Pending`, так как на существующих узлах кластера нет свободных ресурсов.
4.  **Cluster Autoscaler** (или **Karpenter**) видит "зависшие" поды и запрашивает у облака новые узлы.
5.  Когда новые узлы готовы, Kubernetes размещает на них ожидающие поды.
6.  **VPA** (в режиме `Off`) параллельно анализирует работу приложения и рекомендует увеличить `requests` для CPU, чтобы в будущем HPA реагировал еще точнее.

### Совместное использование VPA и HPA

**Внимание:** Не используйте VPA в режимах `Initial` или `Recreate` для управления CPU или памятью, если для этих же метрик настроен HPA. Это приведет к конфликту.

**Рекомендуемая стратегия совместного использования:**
1.  **VPA в режиме `Off`:** Используйте для получения точных рекомендаций по `requests`.
2.  **Ручная настройка `requests`:** На основе рекомендаций VPA установите адекватные `requests` в манифесте.
3.  **HPA для масштабирования:** Настройте HPA для масштабирования подов по утилизации ресурсов. Корректно заданные `requests` сделают работу HPA гораздо точнее.

## Дополнительная информация

### Лучшие практики

*   **Используйте [PodDisruptionBudget (PDB)](../../Base/high_availability.md#защита-от-плановых-выселений-poddisruptionbudget-pdb):** Всегда создавайте PDB для критически важных приложений, чтобы предотвратить простой во время scale-down.
*   **Правильно настраивайте `requests`:** Решения CA и HPA основаны на `requests`, а не на реальном потреблении.
*   **Используйте несколько Node Groups:** Разделяйте узлы на группы по типам нагрузки (с GPU, с большим объемом памяти), чтобы CA мог гранулярно управлять ресурсами.
*   **Масштабирование до нуля:** Для экономии ресурсов настройте `min-size` для некритичных групп узлов (например, для тестовых или пакетных задач) в `0`. Это позволит Cluster Autoscaler полностью удалять все узлы из группы, если на них нет нагрузки.
*   **Используйте аннотации для контроля CA:** Например, `"cluster-autoscaler.kubernetes.io/scale-down-disabled": "true"` на узле временно запретит его удаление.
*   **Настройте `behavior` в HPA:** Чтобы предотвратить слишком агрессивное масштабирование вниз при кратковременных провалах нагрузки, установите `stabilizationWindowSeconds` для `scaleDown`.
*   **Выбирайте правильную метрику для HPA:** Для I/O-bound приложений масштабирование по CPU может быть неэффективным. Рассмотрите кастомные метрики (например, RPS).
*   **Не используйте HPA и VPA вместе для одной метрики:** Это может привести к конфликтам и "гонке масштабирования", когда один контроллер пытается увеличить количество подов, а другой в это же время изменяет их запросы, вызывая постоянные перезапуски.

### Что мешает удалению узла Cluster Autoscaler?

*   Поды с жесткими правилами `podAntiAffinity`.
*   Поды, не управляемые контроллерами (`Deployment`, `StatefulSet` и др.).
*   Поды с локальным хранилищем (`local storage`).
*   Поды, для которых не соблюдается **[PodDisruptionBudget (PDB)](../../Base/high_availability.md#защита-от-плановых-выселений-poddisruptionbudget-pdb)**.
*   Поды с аннотацией `"cluster-autoscaler.kubernetes.io/safe-to-evict": "false"`.
