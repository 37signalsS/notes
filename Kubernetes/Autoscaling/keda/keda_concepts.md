# KEDA: Основные концепции

## Определения

**KEDA (Kubernetes Event-driven Autoscaling)** — легковесный оператор Kubernetes для автоматического масштабирования подов на основе событий из внешних источников (очереди сообщений, метрики, расписание). Работает в связке с HPA (Horizontal Pod Autoscaler), предоставляя External Metrics API для кастомных метрик. Поддерживает масштабирование до нуля и обратно.

**ScaledObject** — кастомный ресурс KEDA (CRD), определяющий правила масштабирования для Deployment или StatefulSet. Содержит ссылку на целевой ресурс, границы масштабирования (`minReplicaCount` / `maxReplicaCount`), период опроса (`pollingInterval`) и триггеры с пороговыми значениями. На один ресурс допускается только один ScaledObject.

**Scaler** — компонент KEDA, подключающийся к внешнему источнику событий и предоставляющий метрики для масштабирования. KEDA включает 60+ встроенных scaler'ов: Kafka, RabbitMQ, Prometheus, Cron, AWS SQS и другие. Scaler опрашивает источник каждые `pollingInterval` секунд и передаёт значение в KEDA Metrics Server.

**Trigger** — условие в ScaledObject, определяющее пороговое значение (`triggerThreshold`) для активации масштабирования. При превышении порога KEDA увеличивает количество реплик. Пример: `queueLength: "10"` — масштабирование при длине очереди более 10 сообщений.

**TriggerAuthentication** — ресурс KEDA для хранения учётных данных подключения к источникам событий (секреты, IAM-роли, токены). Позволяет разделять конфигурацию масштабирования и чувствительные данные. Поддерживает namespace-level и cluster-level аутентификацию.

**Fallback** — резервная конфигурация масштабирования при недоступности источника метрик. Определяет количество реплик и порог ошибок (`failureThreshold`) перед активацией fallback. Предотвращает полную остановку масштабирования при сбоях внешних систем.

**Cooldown Period** — период стабилизации после масштабирования вниз (по умолчанию 300 секунд). Предотвращает «флаппинг» — частые изменения количества реплик при колебаниях нагрузки около порогового значения.

**Polling Interval** — интервал опроса источника событий scaler'ом (по умолчанию 30 секунд, минимум 5 секунд). Меньшее значение повышает реактивность, но увеличивает нагрузку на источник метрик.

## Базовые принципы

### Ключевые возможности

* **Масштабирование до нуля** — KEDA может уменьшить количество реплик до 0 при отсутствии событий и восстановить их при появлении новых событий (cold start).
* **Событийное масштабирование** — реакция на события из 60+ источников через специализированные scaler'ы.
* **Управление HPA** — KEDA автоматически создаёт и управляет нативным объектом HPA на основе конфигурации ScaledObject.
* **Внешние метрики** — использование показателей, недоступных стандартному Metrics Server (длина очереди, бизнес-метрики).

### Архитектура KEDA

* **KEDA Operator** — основной контроллер, обрабатывающий ресурсы ScaledObject и TriggerAuthentication.
* **Metrics Server** — предоставляет внешние метрики через Kubernetes External Metrics API для использования в HPA.
* **Admission Webhook** — выполняет валидацию конфигураций ресурсов KEDA при их создании или обновлении.

### Принцип работы

KEDA работает как посредник между источником событий и стандартным HPA:

1. **Сбор метрик** — Scaler подключается к источнику и получает текущее значение (например, длину очереди).
2. **Обработка** — KEDA Operator вычисляет необходимое количество реплик.
3. **Передача в HPA** — Metrics Server предоставляет значение через External Metrics API. HPA опрашивает этот API (по умолчанию каждые 15 секунд).
4. **Масштабирование** — HPA изменяет количество реплик целевого ресурса.

```
┌─────────────┐    ┌──────────────┐    ┌─────────────┐    ┌──────────┐
│   Источник  │───▶│ KEDA Scaler  │───▶│   KEDA     │───▶│   HPA    │
│   событий   │    │ (сбор метрик)│    │  Operator  │    │          │
└─────────────┘    └──────────────┘    └─────────────┘    └────┬─────┘
                                                               │
                                                               ▼
                                                        ┌─────────────┐
                                                        │ Deployment  │
                                                        │   (scale)   │
                                                        └─────────────┘
```

### Типы scaler'ов

KEDA поддерживает широкий спектр источников, разделенных по категориям:

* **Очереди сообщений:** Kafka, RabbitMQ, AWS SQS, Azure Service Bus.
* **Мониторинг:** Prometheus, Datadog, Grafana Loki.
* **Базы данных:** MySQL, PostgreSQL, Redis, MongoDB.
* **Расписание:** Cron (масштабирование в рабочие часы или пики).

Полный список доступен на [официальном сайте](https://keda.sh/docs/latest/scalers/).

## Дополнительная информация

### Интеграции

* **HPA** — KEDA управляет HPA. **Запрещено** создавать ручной HPA для того же Deployment, это вызовет конфликт.
* **Cluster Autoscaler (CA)** — реагирует на поды, созданные KEDA. При нехватке ресурсов в кластере CA добавит новые узлы.
* **Karpenter** — эффективная альтернатива CA для быстрого добавления узлов при резких скачках событийной нагрузки.
* **Prometheus** — может выступать как источник метрик (через Prometheus scaler) и как инструмент мониторинга самой KEDA.

### Ограничения и особенности

* **Один ScaledObject на ресурс** — для комбинации нескольких условий используйте блок `triggers` внутри одного объекта (логика ИЛИ).
* **Типы ресурсов** — штатно работает с Deployment и StatefulSet. Для задач типа Job используйте KEDA Jobs.
* **Задержка (Latency)** — суммарная задержка складывается из `pollingInterval` KEDA, цикла опроса HPA и времени запуска пода.
* **Cold Start** — при масштабировании из 0 требуется время на запуск первого пода. В критических системах рекомендуется `minReplicaCount: 1`.

### Сравнение KEDA и нативного HPA

| Характеристика | HPA | KEDA |
| :--- | :--- | :--- |
| **Источники метрик** | CPU, Memory, Custom, External | 60+ scaler'ов (очереди, DB, расписание) |
| **Scale to Zero** | Нет (минимум 1) | Да |
| **Событийное управление** | Нет | Да |
| **Управление** | Прямое | Через HPA (KEDA управляет HPA) |
| **External Metrics API** | Требуется адаптер | Встроенный Metrics Server |
