# Cluster Autoscaler (CA)

Cluster Autoscaler (CA) — это системный компонент Kubernetes, предназначенный для автоматического изменения размера вычислительного кластера путём добавления или удаления узлов (Node). Решение принимается на основе анализа потребностей подов в ресурсах и их текущего распределения по узлам.

## Определения

*   **Cluster Autoscaler (CA)** — контроллер, который масштабирует инфраструктуру (виртуальные или физические машины), когда поды не могут быть запланированы из-за нехватки ресурсов или когда узлы простаивают.
*   **Группа узлов (Node Group / ASG / MIG)** — логическое объединение идентичных инстансов (одинаковый тип машины, диск, метки), которыми управляет облачный провайдер.
*   **Scale-Up (Масштабирование вверх)** — процесс добавления нового узла в кластер при обнаружении подов в состоянии `Pending`.
*   **Scale-Down (Масштабирование вниз)** — процесс удаления недоутилизированных узлов для оптимизации затрат.
*   **Expander (Расширитель)** — логический модуль CA, отвечающий за выбор конкретной группы узлов для расширения, если несколько групп подходят под требования подов.
*   **Over-provisioning (Избыточное резервирование)** — стратегия создания «буфера» свободных ресурсов в кластере для мгновенного запуска новых подов без ожидания подготовки узлов облаком.

## Основные концепции

### Принцип работы

#### Масштабирование вверх (Scale-Up)

Процесс инициируется планировщиком (`kube-scheduler`). Если планировщик не находит узла, удовлетворяющего требованиям пода (ресурсы, `nodeSelector`, `affinity`), под переходит в статус `Pending` с причиной `Unschedulable`.

1.  CA сканирует кластер (по умолчанию каждые 10 секунд).
2.  При обнаружении `Pending` подов CA симулирует их размещение в доступных группах узлов.
3.  Выбирается подходящая группа (на основе выбранного `Expander`).
4.  CA отправляет запрос в API облачного провайдера на увеличение `Desired Capacity` группы.

#### Масштабирование вниз (Scale-Down)

CA анализирует узлы на предмет низкой утилизации (суммарные `requests` подов < 50% от емкости узла). Узел считается кандидатом на удаление, если:
1.  Все поды на нем (кроме DaemonSet) могут быть перемещены на другие существующие узлы.
2.  На узле нет подов с аннотацией, запрещающей выселение.
3.  Узел находится в состоянии низкой утилизации дольше заданного времени (`--scale-down-unneeded-time`).

### Стратегии выбора групп узлов (Expanders)

| Стратегия | Описание |
| :--- | :--- |
| **`random`** | Выбор случайной подходящей группы (по умолчанию). |
| **`most-pods`** | Выбирает группу, которая позволит запланировать максимальное количество ожидающих подов. |
| **`least-waste`** | Выбирает группу, после добавления которой останется минимум неиспользованных ресурсов (CPU/RAM). |
| **`priority`** | Использует настраиваемые приоритеты из ConfigMap. Идеально для выбора Spot-инстансов перед On-demand. |
| **`price`** | Выбирает группу с минимальной стоимостью (доступно для GCP и AWS). |

### Ключевые параметры конфигурации (Flags)

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `--scan-interval` | `10s` | Частота проверки состояния кластера. |
| `--scale-down-utilization-threshold` | `0.5` | Порог утилизации (0.5 = 50%), ниже которого узел кандидат на удаление. |
| `--scale-down-unneeded-time` | `10m` | Как долго узел должен быть недогружен перед удалением. |
| `--max-nodes-total` | — | Максимальный размер всего кластера (защита от перерасхода). |
| `--expander` | `random` | Алгоритм выбора Node Group. |
| `--max-drain-parallelism` | `10` | (v1.32+) Максимальное количество узлов, выводимых из эксплуатации одновременно. |
| `--capacity-quotas-enabled` | `false` | (v1.30+) Поддержка лимитов ресурсов через CRD CapacityQuota. |

## Практические сценарии

### Настройка избыточного резервирования (Over-provisioning)

Для обхода задержки в 3–10 минут при создании новых виртуальных машин используется паттерн «Pause Pods».

1.  Создается **PriorityClass** с очень низким приоритетом (например, -10).
2.  Развертывается Deployment с образом `registry.k8s.io/pause` и этим приоритетом.
3.  Эти поды занимают место в кластере, заставляя CA держать лишние узлы.
4.  Когда появляется реальный под с нормальным приоритетом, он вытесняет (preempt) pause-под.
5.  Pause-под переходит в `Pending`, и CA начинает заранее готовить новый узел в фоновом режиме.

### Использование Priority Expander для экономии

Пример настройки `ConfigMap` для приоритетного выбора Spot-инстансов в AWS:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-autoscaler-priority-expander
  namespace: kube-system
data:
  priorities: |-
    100:
      - .*spot.*
    50:
      - .*on-demand.*
```
*Запуск CA должен быть с флагом `--expander=priority`.*

### Управление выселением через аннотации

Если под выполняет критическую задачу (например, тяжелая миграция БД), можно запретить CA удалять узел, на котором он запущен.

```yaml
metadata:
  annotations:
    # Запрещает удалять конкретный узел, даже если он пустой
    cluster-autoscaler.kubernetes.io/scale-down-disabled: "true"
    # На уровне пода: запрещает выселять этот под для scale-down узла
    cluster-autoscaler.kubernetes.io/safe-to-evict: "false"
```

### Развёртывание на Bare-metal

В локальных окружениях CA не может напрямую управлять «железом» через облачный API. Требуются промежуточные инструменты:
*   **Metal3**: Управляет жизненным циклом физических серверов через API Kubernetes (Bare Metal Operator).
*   **MAAS (Metal as a Service)**: Позволяет CA взаимодействовать с API MAAS для включения/выключения физических серверов.
*   **VMware vSphere**: CA поддерживает интеграцию с vCenter для создания/удаления ВМ в кластерах vSphere.

## Дополнительная информация

### Новое в версиях 1.30–1.32

*   **Structured Parameters (DRA)**: Улучшена симуляция для GPU и специфического оборудования. Теперь CA «понимает» сложные требования к ресурсам до фактического появления узла.
*   **ProvisioningRequest (Beta)**: Новый CRD, позволяющий запрашивать емкость кластера под пакетные задачи до создания самих подов.
*   **Удаление In-tree провайдеров**: Для Azure и других облаков теперь обязательно использование внешних Cloud Provider интерфейсов.

### Ограничения и особенности

1.  **DaemonSets**: CA не учитывает поды из DaemonSet при расчете утилизации узла (они считаются системным оверхедом).
2.  **Локальное хранилище**: По умолчанию CA не удаляет узлы, на которых запущены поды с `emptyDir` или `hostPath` (требуется флаг `--skip-nodes-with-local-storage=false`).
3.  **Задержка (Cooldown)**: После добавления узла CA делает паузу (`--scale-up-from-zero` и др.), чтобы избежать осцилляции (быстрого добавления/удаления).

### Сравнение с Karpenter

| Характеристика | Cluster Autoscaler | Karpenter |
| :--- | :--- | :--- |
| **Абстракция** | Node Groups (ASG/MIG) | Прямое управление инстансами (Fleet API) |
| **Скорость** | Медленная (3–10 мин) | Быстрая (<1 мин) |
| **Бинпакинг** | Ограничен шаблоном группы | Свободный выбор любого типа инстанса |
| **On-premises** | Поддерживается (vSphere, Metal3) | Не поддерживается |

Подробное сравнение: **[Karpenter против Cluster Autoscaler](./Karpenter/overview.md#отличия-от-cluster-autoscaler)**.
