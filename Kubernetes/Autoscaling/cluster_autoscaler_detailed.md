# Cluster Autoscaler (CA)

Cluster Autoscaler (CA) — это системный компонент Kubernetes, предназначенный для автоматического изменения размера вычислительного кластера путём добавления или удаления узлов (Node). Решение принимается на основе анализа потребностей подов в ресурсах и их текущего распределения по узлам.

## Определения

Kubernetes имеет двухуровневую структуру масштабирования инфраструктуры:
*   **Плоскость управления (Control Plane)** — в управляемых облачных сервисах (например, AWS EKS) провайдер обычно масштабирует её автоматически. Задача пользователя — следить за нагрузкой на API-сервер (частота создания подов и запросов).
*   **Рабочие узлы (Worker Nodes)** — среда выполнения ваших приложений, требующая динамического расширения емкости (виртуальных или физических машин).

**Cluster Autoscaler (CA)** — системный контроллер, который масштабирует количество рабочих узлов, когда поды не могут быть запланированы из-за нехватки ресурсов или когда узлы простаивают.

**Группа узлов (Node Group / ASG / MIG)** — логическое объединение идентичных инстансов (одинаковый тип машины, диск, метки), которыми управляет облачный провайдер.

**Триггер масштабирования** — в отличие от HPA, **CA не измеряет напрямую использование CPU или памяти**. Он реагирует исключительно на появление подов в состоянии `Pending` с причиной `Unschedulable`.

## Основные концепции

### Принцип работы

#### Масштабирование вверх (Scale-Up)

Процесс инициируется планировщиком (`kube-scheduler`). Если планировщик не находит узла, удовлетворяющего требованиям пода, под переходит в статус `Pending`.

1.  **Мониторинг:** CA постоянно сканирует кластер на наличие `Pending` подов (по умолчанию каждые 10 секунд).
2.  **Симуляция:** При обнаружении потребности CA проверяет, можно ли добавить узлы в рамках установленных лимитов (`max-nodes-total`).
3.  **Запрос:** CA инструктирует облачного провайдера увеличить количество машин в подходящей Node Group.
4.  **Включение:** Новые узлы запускаются, регистрируются в Control Plane и становятся доступными для планировщика, который размещает на них ранее ожидавшие поды.

#### Масштабирование вниз (Scale-Down)

CA анализирует узлы на предмет низкой утилизации (суммарные `requests` подов < 50% от емкости узла). Узел считается кандидатом на удаление, если:
1.  Все поды на нем (кроме DaemonSet) могут быть перемещены на другие существующие узлы.
2.  На узле нет подов с аннотацией, запрещающей выселение.
3.  Узел находится в состоянии низкой утилизации дольше заданного времени (`--scale-down-unneeded-time`).

### Стратегии выбора групп узлов (Expanders)

| Стратегия | Описание |
| :--- | :--- |
| **`random`** | Выбор случайной подходящей группы (по умолчанию). |
| **`most-pods`** | Выбирает группу, которая позволит запланировать максимальное количество ожидающих подов. |
| **`least-waste`** | Выбирает группу, после добавления которой останется минимум неиспользованных ресурсов (CPU/RAM). |
| **`priority`** | Использует настраиваемые приоритеты из ConfigMap. Идеально для выбора Spot-инстансов перед On-demand. |
| **`price`** | Выбирает группу с минимальной стоимостью (доступно для GCP и AWS). |

### Ключевые параметры конфигурации (Flags)

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `--scan-interval` | `10s` | Частота проверки состояния кластера. |
| `--scale-down-utilization-threshold` | `0.5` | Порог утилизации (0.5 = 50%), ниже которого узел кандидат на удаление. |
| `--scale-down-unneeded-time` | `10m` | Как долго узел должен быть недогружен перед удалением. |
| `--max-nodes-total` | — | Максимальный размер всего кластера (защита от перерасхода). |
| `--expander` | `random` | Алгоритм выбора Node Group. |
| `--max-drain-parallelism` | `10` | (v1.32+) Максимальное количество узлов, выводимых из эксплуатации одновременно. |
| `--capacity-quotas-enabled` | `false` | (v1.30+) Поддержка лимитов ресурсов через CRD CapacityQuota. |

## Практические сценарии

### Настройка избыточного резервирования (Over-provisioning)

Для обхода задержки в 3–10 минут при создании новых виртуальных машин используется паттерн «Pause Pods».

1.  Создается **PriorityClass** с очень низким приоритетом (например, -10).
2.  Развертывается Deployment с образом `registry.k8s.io/pause` и этим приоритетом.
3.  Эти поды занимают место в кластере, заставляя CA держать лишние узлы.
4.  Когда появляется реальный под с нормальным приоритетом, он вытесняет (preempt) pause-под.
5.  Pause-под переходит в `Pending`, и CA начинает заранее готовить новый узел в фоновом режиме.

### Использование Priority Expander для экономии

Пример настройки `ConfigMap` для приоритетного выбора Spot-инстансов в AWS:

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: cluster-autoscaler-priority-expander
  namespace: kube-system
data:
  priorities: |-
    100:
      - .*spot.*
    50:
      - .*on-demand.*
```
*Запуск CA должен быть с флагом `--expander=priority`.*

### Управление выселением через аннотации

Если под выполняет критическую задачу (например, тяжелая миграция БД), можно запретить CA удалять узел, на котором он запущен.

```yaml
metadata:
  annotations:
    # Запрещает удалять конкретный узел, даже если он пустой
    cluster-autoscaler.kubernetes.io/scale-down-disabled: "true"
    # На уровне пода: запрещает выселять этот под для scale-down узла
    cluster-autoscaler.kubernetes.io/safe-to-evict: "false"
```

### Развёртывание на Bare-metal и On-premise

В локальных окружениях (on-premise) CA сталкивается с фундаментальными сложностями из-за отсутствия стандартизированного API для динамического управления «железом». Это делает его использование менее эффективным:

*   **Отсутствие гибкого API**: В отличие от облаков с их Fleet API, локальные системы требуют сложной интеграции с инструментами вроде Metal3, MAAS или vSphere.
*   **Статичность ресурсов**: В облаке можно заказать любой тип инстанса. On-premise ограничен заранее закупленным оборудованием, что нивелирует преимущество "бесконечного" масштабирования.
*   **Сложность автоматизации**: Процессы PXE-загрузки, настройки BIOS и регистрации узла занимают значительно больше времени (часто 15-30 минут вместо 3-5).
*   **Инструменты интеграции**:
    *   **Metal3**: Управляет жизненным циклом физических серверов через API Kubernetes (Bare Metal Operator).
    *   **MAAS (Metal as a Service)**: Позволяет CA взаимодействовать с API MAAS для включения/выключения физических серверов.
    *   **VMware vSphere**: Поддерживает создание/удаление ВМ в кластерах vSphere для динамического расширения.

## Дополнительная информация

### Новое в версиях 1.30–1.32

*   **Structured Parameters (DRA)**: Улучшена симуляция для GPU и специфического оборудования. Теперь CA «понимает» сложные требования к ресурсам до фактического появления узла.
*   **ProvisioningRequest (Beta)**: Новый CRD, позволяющий запрашивать емкость кластера под пакетные задачи до создания самих подов.
*   **Удаление In-tree провайдеров**: Для Azure и других облаков теперь обязательно использование внешних Cloud Provider интерфейсов.

### Ограничения и особенности

1.  **Триггер — Pending поды**: CA не реагирует на загрузку CPU/RAM. Он начинает работу только тогда, когда планировщик не может разместить под.
2.  **Задержки масштабирования**: Изменение размера кластера не происходит мгновенно. Процесс (обнаружение -> запрос -> запуск ВМ -> регистрация) обычно занимает **3–10 минут**. Это может замедлить реакцию на внезапные всплески трафика.
3.  **Производительность в масштабе**: Эффективность CA может снижаться по мере роста кластера. При очень большом количестве узлов контроллер может сталкиваться с задержками при анализе бинпакинга и взаимодействии с Cloud API.
4.  **Масштабирование на основе ресурсов (Requests)**: CA ориентируется на зарезервированные ресурсы (`requests`), а не на фактическое потребление. Это может привести к избыточному выделению ресурсов (over-provisioning), если лимиты подов настроены неточно.
5.  **Допущение об отказоустойчивости**: CA предполагает, что поды можно безопасно перезапустить на новых узлах при уменьшении масштаба (scale-down). Для приложений, чувствительных к прерываниям, необходимо настраивать PDB.
6.  **Проблемы с ограничениями узлов**: Узлы со специфическими зависимостями, локальными дисками или конфигурациями, препятствующими их удалению, создают сложности для CA, даже если они недогружены.
7.  **Локальное хранилище**: По умолчанию CA не удаляет узлы, на которых запущены поды с `emptyDir` или `hostPath` (требуется флаг `--skip-nodes-with-local-storage=false`).
8.  **On-premises**: Хотя поддержка существует (vSphere, Metal3), она менее надежна и сложна в настройке по сравнению с нативными облачными решениями.
9.  **DaemonSets**: CA не учитывает поды из DaemonSet при расчете утилизации узла (они считаются системным оверхедом).

### Сравнение с Karpenter

| Характеристика | Cluster Autoscaler | Karpenter |
| :--- | :--- | :--- |
| **Абстракция** | Node Groups (ASG/MIG) | Прямое управление инстансами (Fleet API) |
| **Скорость** | Медленная (3–10 мин) | Быстрая (<1 мин) |
| **Бинпакинг** | Ограничен шаблоном группы | Свободный выбор любого типа инстанса |
| **On-premises** | Поддерживается (vSphere, Metal3) | Не поддерживается |

## Советы для собеседования

**Вопрос:** Почему Cluster Autoscaler считается менее надежным и эффективным для On-premise кластеров по сравнению с облачными?
**Ответ:** Основная причина — архитектурная зависимость CA от облачных абстракций (Node Groups). В On-premise отсутствуют динамические пулы ресурсов, которыми можно управлять через единый API. Автоматизация физических серверов (Bare metal) требует сложной обвязки (Metal3/MAAS), а время подготовки нового узла может быть слишком большим для оперативного реагирования на всплески нагрузки. Кроме того, CA нацелен на экономию денег за счет удаления машин, что в On-premise (где "железо" уже куплено) дает меньше экономического смысла.

**Вопрос:** Загрузка CPU в моем кластере составляет 95%, но Cluster Autoscaler не добавляет новые узлы. Это нормально?
**Ответ:** Да, это ожидаемое поведение. Триггером для Cluster Autoscaler является не высокая утилизация ресурсов (CPU/RAM), а наличие подов в состоянии `Pending`, которые планировщик не может разместить. Пока все существующие поды успешно работают, CA будет бездействовать, даже если ресурсы узлов практически исчерпаны. Масштабирование начнется только при попытке запустить новый под, для которого не найдется места.
