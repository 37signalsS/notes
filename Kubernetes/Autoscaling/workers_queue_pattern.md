# Архитектурный паттерн «Воркеры + Очередь» (Workers + Queue) в Kubernetes

## Определения

**Workers + Queue (Воркеры + Очередь)** — архитектурный паттерн для асинхронной обработки задач через очередь сообщений, где воркеры (обработчики) масштабируются в зависимости от глубины (длины) очереди.

**Producer (Производитель)** — сервис или компонент, генерирующий задачи и помещающий их в очередь.

**Consumer (Потребитель / Worker)** — под (Pod), извлекающий и обрабатывающий задачи из очереди.

**Идемпотентность** — свойство операции, при котором повторное выполнение одной и той же задачи не приводит к изменению состояния системы сверх того, что было достигнуто при первом выполнении (отсутствие побочных эффектов при повторах).

**Dead Letter Queue (DLQ — очередь недоставленных сообщений)** — вспомогательная очередь для задач, которые не удалось обработать после нескольких попыток, предназначенная для последующего анализа и ручного разбора.

## Основные концепции

Архитектура «Воркеры + Очередь» обеспечивает эластичность и устойчивость системы за счет развязки производителей и потребителей.

### Ключевые преимущества

* **Сглаживание пиковых нагрузок** — очередь выступает буфером, предотвращая перегрузку потребителей при резком росте числа задач.
* **Эластичное масштабирование** — количество воркеров динамически изменяется в зависимости от объема работы в очереди.
* **Гарантированная обработка** — использование механизмов подтверждения (acknowledgement) позволяет вернуть задачу в очередь при сбое воркера.

### Требования к задачам

| Требование | Описание | Реализация |
| :--- | :--- | :--- |
| **Идемпотентность** | Повторная обработка не создает дублей | Уникальные ID (Identifier) задач, проверка состояния в БД |
| **Дедупликация** | Предотвращение приема одинаковых задач | Фильтрация по ключу, использование TTL (Time To Live) |
| **Ограничение параллелизма** | Контроль нагрузки на внешние системы | Семафоры (Semaphore), квоты на уровне потребителей |
| **Timeout обработки** | Защита от «зависших» задач | Deadline (крайние сроки), механизмы heartbeat |
| **Dead Letter Queue** | Изоляция проблемных сообщений | Автоматическая пересылка в DLQ после N попыток |

### Паттерны обработки очередей

| Паттерн | Описание | Применение |
| :--- | :--- | :--- |
| **Competing Consumers** | Несколько воркеров читают из одной очереди | Параллельная обработка, балансировка |
| **Publisher-Subscriber** | Сообщение доставляется всем подписчикам | Рассылка уведомлений, синхронизация кэша |
| **Priority Queue** | Обработка в порядке приоритета задач | VIP-задачи, критические системные алерты |
| **Scheduled Messages** | Отложенная обработка (по расписанию) | Напоминания, периодические отчеты |

## Практические сценарии

### Сценарий 1: Масштабирование через HPA (внешние метрики)

Использование стандартного Horizontal Pod Autoscaler (HPA — горизонтальный авторовщик подов) с адаптером внешних метрик для мониторинга брокера сообщений.

```yaml
# Deployment Воркеров
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-workers
spec:
  replicas: 2
  selector:
    matchLabels:
      app: order-workers
  template:
    metadata:
      labels:
        app: order-workers
    spec:
      containers:
        - name: worker
          image: order-processor:latest
          env:
            - name: RABBITMQ_HOST
              value: "rabbitmq"
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
---
# HPA с внешней метрикой (длина очереди)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: workers-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-workers
  minReplicas: 1
  maxReplicas: 50
  metrics:
    - type: External
      external:
        metric:
          name: queue_messages_ready
        target:
          type: AverageValue
          averageValue: "100"  # 1 под на каждые 100 сообщений
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
        - type: Percent
          value: 100
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300
```

**Диагностика:**

```bash
# Проверка статуса масштабирования
kubectl get hpa workers-hpa
# → NAME          REFERENCE                  TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
# → workers-hpa   Deployment/order-workers   150/100 (avg)   1         50        3          5m
```

### Сценарий 2: Использование KEDA (рекомендуемый подход)

KEDA (Kubernetes Event-driven Autoscaling — событийное автоскейлинг Kubernetes) упрощает интеграцию с брокерами и поддерживает масштабирование до нуля.

```yaml
# ScaledObject KEDA для RabbitMQ
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: rabbitmq-workers-scaledobject
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-workers
  minReplicaCount: 0  # Масштабирование до нуля при пустой очереди
  maxReplicaCount: 50
  triggers:
    - type: rabbitmq
      metadata:
        queueName: orders
        host: amqp://rabbitmq:5672
        queueLength: "20"
```

**Преимущества KEDA:**

* **Scale to Zero:** полная остановка воркеров при отсутствии задач.
* **Широкая поддержка:** 60+ встроенных триггеров (Kafka, SQS, Redis).
* **Простота:** не требует настройки сложных адаптеров внешних метрик.

## Дополнительная информация

### Интеграция с компонентами Kubernetes

Реализация паттерна требует комплексного подхода к настройке кластера:

* **[KEDA](./keda/keda_concepts.md)** — основной инструмент для событийного масштабирования воркеров.
* **[HPA](../Autoscaling/HPA/index.md)** — базовый механизм, используемый KEDA под капотом.
* **[Cluster Autoscaler](../Autoscaling/cluster_autoscaler_detailed.md)** — обеспечивает добавление узлов (Nodes) при нехватке ресурсов для новых воркеров.
* **[Affinity/Anti-Affinity](../Scheduling/affinity.md)** — гарантирует отказоустойчивость за счет распределения воркеров по разным узлам или зонам.

### Выбор технологий и брокеров

Выбор брокера сообщений напрямую влияет на возможности масштабирования и гарантии доставки. Подробное сравнение принципов работы и технологий приведено в разделе **[Принципы работы очередей сообщений](../../Kafka/message_queues_principles.md)**.

Основные решения:

* **RabbitMQ:** классические очереди, отличная поддержка KEDA.
* **Apache Kafka:** высокая пропускная способность, работа через consumer groups.
* **Cloud Native (SQS, Pub/Sub):** управляемые очереди облачных провайдеров.

### Мониторинг и метрики

Для контроля здоровья системы воркеров необходимо отслеживать:

1. **Queue Length (Длина очереди):** основной показатель для автоскейлинга.
2. **Consumer Lag (Отставание потребителей):** время/количество сообщений между публикацией и обработкой.
3. **Processing Latency:** время выполнения одной задачи воркером.
4. **Error Rate / DLQ Size:** количество неудачных попыток обработки, требующих вмешательства.

### Сценарии применения

* **Тяжелые вычисления:** рендеринг видео, генерация PDF, анализ данных.
* **Интеграция с внешними API:** когда скорость внешнего сервиса ниже скорости поступления запросов.
* **Асинхронные бизнес-процессы:** отправка email, обработка платежей, фоновое обновление индексов.
