# Архитектурный паттерн «Воркеры + Очередь»

Паттерн «Воркеры + Очередь» (Workers + Queue) является фундаментальным решением для асинхронной обработки задач в распределенных системах. Он позволяет изолировать (decouple) процесс генерации задач от процесса их выполнения, обеспечивая эластичность и устойчивость системы к всплескам нагрузки.

## Определения

*   **Workers + Queue (Воркеры + Очередь)** — паттерн, в котором воркеры (обработчики) масштабируются в зависимости от глубины (длины) очереди сообщений.
*   **Producer (Производитель)** — сервис или компонент, генерирующий задачи и помещающий их в очередь.
*   **Consumer (Потребитель / Worker)** — под (Pod), извлекающий и обрабатывающий задачи из очереди.
*   **Идемпотентность** — свойство операции, при котором повторное выполнение одной и той же задачи не приводит к некорректному изменению состояния системы (отсутствие побочных эффектов при повторах).
*   **Dead Letter Queue (DLQ)** — вспомогательная очередь для задач, которые не удалось обработать после нескольких попыток, предназначенная для последующего анализа.
*   **Graceful Shutdown (Безопасное завершение)** — механизм корректной остановки воркера, позволяющий завершить текущую задачу перед выключением пода.

## Основные концепции

### Ключевые преимущества

*   **Сглаживание пиковых нагрузок**: Очередь выступает буфером, предотвращая перегрузку потребителей при резком росте числа задач.
*   **Эластичное масштабирование**: Количество воркеров динамически изменяется в зависимости от объема работы в очереди.
*   **Гарантированная обработка**: Использование механизмов подтверждения (acknowledgement) позволяет вернуть задачу в очередь при сбое воркера.

### Требования к задачам

| Требование | Описание | Реализация |
| :--- | :--- | :--- |
| **Идемпотентность** | Повторная обработка не создает дублей | Уникальные ID задач, проверка состояния в БД |
| **Дедупликация** | Предотвращение приема одинаковых задач | Фильтрация по ключу, использование TTL |
| **Ограничение параллелизма** | Контроль нагрузки на внешние системы | Семафоры, квоты на уровне потребителей |
| **Timeout обработки** | Защита от «зависших» задач | Deadline, механизмы heartbeat |
| **Dead Letter Queue** | Изоляция проблемных сообщений | Пересылка в DLQ после N попыток (Max Delivery) |

### Паттерны обработки очередей

| Паттерн | Описание | Применение |
| :--- | :--- | :--- |
| **Competing Consumers** | Несколько воркеров читают из одной очереди | Параллельная обработка, балансировка нагрузки |
| **Publisher-Subscriber** | Сообщение доставляется всем подписчикам | Рассылка уведомлений, синхронизация кэша |
| **Priority Queue** | Обработка в порядке приоритета задач | VIP-задачи, критические системные алерты |
| **Scheduled Messages** | Отложенная обработка (по расписанию) | Напоминания, периодические отчеты |

### Обеспечение отказоустойчивости воркеров

В Kubernetes воркеры должны настраиваться с учетом их асинхронной природы:

*   **Pod Disruption Budget (PDB)**: Предотвращает одновременное удаление слишком большого количества воркеров во время обслуживания узлов.
*   **Topology Spread Constraints**: Равномерно распределяет воркеры по зонам доступности для защиты от локальных сбоев.
*   **Priority Classes**: Назначение воркерам высокого приоритета гарантирует, что они не будут вытеснены менее важными подами при нехватке ресурсов.
*   **Graceful Shutdown**: Настройка `terminationGracePeriodSeconds` должна превышать максимальное время обработки одной задачи.

## Практические сценарии

### Сценарий 1: Масштабирование через HPA (внешние метрики)

Использование стандартного Horizontal Pod Autoscaler с адаптером внешних метрик для мониторинга брокера сообщений.

```yaml
# Deployment Воркеров с защитой от прерываний
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order-workers
spec:
  replicas: 2
  selector:
    matchLabels:
      app: order-workers
  template:
    metadata:
      labels:
        app: order-workers
    spec:
      terminationGracePeriodSeconds: 300 # 5 минут на завершение задачи
      containers:
        - name: worker
          image: order-processor:latest
          resources:
            requests:
              cpu: "250m"
              memory: "512Mi"
---
# HPA с внешней метрикой (длина очереди)
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: workers-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: order-workers
  minReplicas: 1
  maxReplicas: 50
  metrics:
    - type: External
      external:
        metric:
          name: queue_messages_ready
        target:
          type: AverageValue
          averageValue: "100"  # 1 под на каждые 100 сообщений
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 300 # Плавное сжатие
```

### Сценарий 2: Использование KEDA (рекомендуемый подход)

**[KEDA](./keda/keda_concepts.md)** упрощает интеграцию и поддерживает масштабирование до нуля.

```yaml
# ScaledObject KEDA для RabbitMQ
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: rabbitmq-workers-scaler
spec:
  scaleTargetRef:
    name: order-workers
  minReplicaCount: 0  # Масштабирование до нуля
  maxReplicaCount: 50
  triggers:
    - type: rabbitmq
      metadata:
        queueName: orders
        host: amqp://rabbitmq:5672
        queueLength: "20"
```

### Сценарий 3: Масштабирование тяжелых задач через Job (ScaledJob)

Для задач, требующих изоляции или очень долгого времени выполнения (часы), используются Job вместо Deployment.

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledJob
metadata:
  name: video-transcoder
spec:
  jobTargetRef:
    template:
      spec:
        containers:
        - name: transcoder
          image: ffmpeg-worker:latest
        restartPolicy: OnFailure
  triggers:
  - type: aws-sqs
    metadata:
      queueURL: https://sqs.us-east-1.amazonaws.com/tasks
      queueLength: "1" # Одна Job на одно сообщение
```

## Дополнительная информация

### Выбор брокера сообщений

Выбор технологии напрямую влияет на возможности масштабирования. Подробное сравнение приведено в разделе: **[Принципы работы очередей сообщений](../../Kafka/message_queues_principles.md)**.

*   **RabbitMQ**: Классические очереди, эффективен для Competing Consumers.
*   **Apache Kafka**: Потоковая обработка, масштабирование через партиции и consumer groups.
*   **Redis**: Легковесное решение для простых очередей.

### Мониторинг и метрики

Для контроля системы воркеров необходимо отслеживать:
1.  **Queue Length / Consumer Lag**: Основной показатель для масштабирования.
2.  **Processing Latency**: Время выполнения одной задачи (p95, p99).
3.  **Error Rate / DLQ Size**: Количество неудачных попыток обработки.
4.  **Scaling Latency**: Время от появления задачи в очереди до запуска нового воркера.
