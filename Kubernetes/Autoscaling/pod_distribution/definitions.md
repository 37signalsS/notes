# Распределение подов: Определения

## Определения

**Pod Anti-Affinity** — правило планирования, запрещающее или предпочитающее размещение определённых подов на одном узле или в одной зоне доступности. Используется для обеспечения высокой доступности путём распределения реплик приложения. Подробное описание всех типов Affinity см. в [Affinity и Anti-Affinity](../../Scheduling/affinity.md).

**Pod Affinity** — правило планирования, предпочитающее или требующее размещение подов рядом с другими подами (коликейшн). Применяется для совместного размещения связанных компонентов, например, приложения и кэша, что снижает сетевую задержку между ними.

**Topology Spread Constraints** — механизм равномерного распределения подов по доменам топологии (узлам, зонам, регионам) для повышения отказоустойчивости. В отличие от Pod Anti-Affinity, обеспечивает балансировку нагрузки, а не бинарное размещение.

**Topology Key** — метка узла, определяющая домен топологии:

- `kubernetes.io/hostname` — отдельный узел (распределение по физическим серверам)
- `topology.kubernetes.io/zone` — зона доступности (распределение по зонам отказов)
- `topology.kubernetes.io/region` — регион (распределение по географическим регионам)

**Failure Domain** — домен отказа (зона, регион, стойка), выход из строя которого не должен влиять на доступность приложения. Распределение подов по разным failure domain повышает отказоустойчивость и снижает риск одновременной недоступности всех реплик.

## Связанные темы

Механизмы распределения подов тесно интегрированы с другими компонентами Kubernetes: [Pod Disruption Budget](../pod_disruption_budget.md) защищает от массового выселения, [HPA](../HPA/index.md) создаёт поды с учётом правил распределения, [Cluster Autoscaler](../cluster_autoscaler_detailed.md) добавляет узлы для соблюдения правил планирования.

## Типы правил размещения

Правила Affinity и Topology Spread имеют два уровня строгости: `requiredDuringScheduling...` (жёсткое требование — под не будет запланирован при нарушении) и `preferredDuringScheduling...` (предпочтение — планировщик старается выполнить, но может нарушить). Поведение после запуска определяется суффиксом: `...IgnoredDuringExecution` (стандартное — правила применяются только при планировании) или `...RequiredDuringExecution` (правила продолжают действовать, при нарушении под может быть выселен).

## Рекомендации по выбору механизма

Для обеспечения высокой доступности рекомендуется использовать **Topology Spread Constraints** с `topologyKey: topology.kubernetes.io/zone` и `maxSkew: 1` — это обеспечивает равномерное распределение по зонам доступности. **Pod Anti-Affinity** подходит для жёстких требований к изоляции (например, не более одного пода базы данных на узел). Комбинирование обоих механизмов даёт максимальную отказоустойчивость.
