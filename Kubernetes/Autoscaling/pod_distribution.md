# Распределение подов

Механизмы распределения подов определяют, как реплики приложения размещаются в инфраструктуре кластера. В контексте автоматического масштабирования (Autoscaling) правильное распределение критично для обеспечения высокой доступности (HA) и эффективного использования ресурсов при изменении нагрузки.

## Определения

*   **Распределение подов (Pod Distribution)** — процесс размещения реплик приложения по разным узлам или зонам доступности для минимизации рисков при сбоях инфраструктуры.
*   **Домен топологии (Topology Domain)** — логическая или физическая область (сервер, стойка, зона доступности, регион), в границах которой контролируется размещение подов.
*   **Максимальный перекос (maxSkew)** — параметр `topologySpreadConstraints`, определяющий максимально допустимую разницу в количестве подов между разными доменами топологии.
*   **Дескедулер (Descheduler)** — вспомогательный компонент Kubernetes, который анализирует текущее распределение подов и инициирует их перенос (путем выселения), если они нарушают правила политики или если появились более подходящие узлы.
*   **Консолидация (Consolidation)** — процесс уплотнения подов на меньшем количестве узлов для экономии ресурсов, часто применяемый в Karpenter.

## Основные концепции

### Механизмы планирования

Для управления распределением Kubernetes предоставляет три основных инструмента:

1.  **Pod Affinity / Anti-Affinity**: Бинарные правила («быть рядом» или «быть врозь»).
2.  **Topology Spread Constraints (TSC)**: Гибкий механизм для обеспечения равномерности распределения с контролем перекоса.
3.  **Node Affinity**: Привязка подов к конкретным группам узлов (например, по типу дисков или зонам).

Детальное описание параметров и YAML-примеры настройки этих механизмов находятся в основном руководстве: **[Управление размещением подов: Affinity, Anti-Affinity и TSC](../Scheduling/affinity.md)**.

### Взаимодействие с автомасштабированием

Распределение подов тесно связано с работой масштабировщиков:

*   **Horizontal Pod Autoscaler (HPA)**: При увеличении количества реплик новые поды проходят через цикл планирования. Если настроены правила `Anti-Affinity` или `TSC`, планировщик будет стараться разнести их по разным зонам или узлам.
*   **Cluster Autoscaler (CA) / Karpenter**: Если новые поды не могут быть размещены из-за жестких правил распределения (`DoNotSchedule`), масштабировщик узлов добавит новые ноды в нужных зонах.
*   **Важность мягких правил**: Для систем с активным масштабированием рекомендуется использовать `whenUnsatisfiable: ScheduleAnyway` для TSC или `preferredDuringScheduling...` для Affinity. Это гарантирует, что приложение продолжит масштабироваться, даже если идеальное распределение временно невозможно.

### Динамическая балансировка (Descheduler)

Стандартный планировщик (`kube-scheduler`) принимает решение только в момент создания пода. Со временем распределение может стать субоптимальным (например, после восстановления упавшего узла все поды остались на старых нодах). 

**Descheduler решает следующие задачи:**
*   Выселение дубликатов подов с одного узла.
*   Перенос подов на недозагруженные узлы.
*   Исправление нарушений правил Affinity и TSC, возникших со временем.
*   Выселение подов с узлов, которые скоро будут удалены или обновлены.

## Практические сценарии

### Сценарий 1: Равномерное распределение по зонам (Multi-AZ HA)

При использовании HPA важно, чтобы новые реплики распределялись по зонам доступности поровну.

```yaml
# Фрагмент шаблона Deployment
topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: topology.kubernetes.io/zone
    whenUnsatisfiable: ScheduleAnyway # Позволяет масштабироваться при сбое зоны
    labelSelector:
      matchLabels:
        app: my-service
```

### Сценарий 2: Оптимизация при использовании Karpenter

Karpenter может автоматически заменять несколько мелких узлов на один крупный (консолидация). Чтобы при этом не пострадала отказоустойчивость, необходимо:
1.  Использовать `topologySpreadConstraints` по хосту (`kubernetes.io/hostname`).
2.  Настроить **[Pod Disruption Budget](./pod_disruption_budget.md)**, чтобы Karpenter не выселял слишком много подов одновременно.

### Сценарий 3: Перераспределение после расширения кластера

Если в кластер были добавлены новые узлы, Descheduler с политикой `LowNodeUtilization` поможет перенести часть нагрузки с переполненных старых узлов на новые, обеспечивая более ровный профиль потребления ресурсов.

## Дополнительная информация

### Рекомендации

*   **Используйте Topology Spread Constraints**: Это более современный и надежный способ обеспечения HA, чем Pod Anti-Affinity.
*   **Связь с PDB**: Всегда настраивайте `PodDisruptionBudget` совместно с правилами распределения. Это предотвратит ситуацию, когда плановые работы (например, обновление ядра на узлах) приведут к одновременной остановке всех реплик в одной зоне.
*   **Мониторинг планирования**: Отслеживайте метрики `leader_election_master_status` и события `FailedScheduling`, чтобы вовремя заметить, что правила распределения стали слишком жесткими для текущего размера кластера.
