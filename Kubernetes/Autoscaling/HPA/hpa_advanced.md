# HPA — продвинутые темы и тонкая настройка

> **Достоверность: 10** (Основные источники + Официальная документация Kubernetes v1.30)

## 1. Определения

Для получения базовой информации см. основной раздел **[HPA: Главная](./index.md)**.

**Flapping (дребезг)** — ситуация, при которой количество реплик постоянно колеблется (увеличивается и тут же уменьшается) из-за нестабильных метрик или слишком агрессивных настроек масштабирования.

**Поле `behavior`** — секция в спецификации HPA API `v2`, позволяющая тонко настраивать политики и скорость масштабирования вверх (`scaleUp`) и вниз (`scaleDown`), включая окна стабилизации.

**kube-state-metrics** — сервис, генерирующий метрики о состоянии объектов Kubernetes (включая статус HPA) из API-сервера для сбора системой Prometheus.

## 2. Диагностика и статус условий (Conditions)

HPA сообщает о своем состоянии через `status.conditions`. Это первый источник данных при отладке:

- **`AbleToScale`**: указывает, может ли HPA изменять количество реплик. `False` может означать отсутствие прав RBAC или проблемы с целевым объектом (например, Deployment удален).
- **`ScalingActive`**: показывает, активен ли сбор метрик. `False` сигнализирует о проблемах с Metrics API (Metrics Server недоступен) или отсутствии `requests` у контейнеров.
- **`ScalingLimited`**: сообщает, что масштабирование ограничено параметрами `minReplicas` или `maxReplicas`.

Проверка условий:
```bash
kubectl describe hpa <name>
```

## 3. Продвинутые возможности API v2

### 3.1. Настройка поведения (Behavior)

Поле `behavior` — ключевой инструмент для предотвращения "дребезга".

- **`stabilizationWindowSeconds`**: период, за который HPA анализирует рекомендации. Для `scaleDown` выбор идет по **наибольшему** (наиболее безопасному) количеству реплик за окно. По умолчанию: `scaleUp` = 0с, `scaleDown` = 300с.
- **`selectPolicy`**: определяет выбор при наличии нескольких политик.
  - `Max`: выбирает политику, дающую **наибольшее** количество реплик (консервативный `scaleDown`, агрессивный `scaleUp`). По умолчанию используется для обоих направлений.
  - `Min`: выбирает политику, дающую **наименьшее** количество реплик.
  - `Disabled`: полностью отключает масштабирование в данном направлении.

**Пример:** агрессивный рост и сверхмедленное уменьшение.

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 0
    policies:
      - type: Percent
        value: 100 # Удвоить количество реплик
        periodSeconds: 15
    selectPolicy: Max
  scaleDown:
    stabilizationWindowSeconds: 600 # Ждать 10 минут
    policies:
      - type: Pods
        value: 1 # Удалять только по 1 поду за раз
        periodSeconds: 60
    selectPolicy: Max
```

### 3.2. Масштабирование по отдельным контейнерам

Тип `ContainerResource` позволяет игнорировать потребление ресурсов sidecar-контейнерами (например, `istio-proxy` или `fluent-bit`), которые могут искажать общую картину утилизации пода.

```yaml
metrics:
  - type: ContainerResource
    containerResource:
      name: cpu
      container: main-app
      target:
        type: Utilization
        averageUtilization: 70
```

## 4. Особенности метрик памяти

Масштабирование по памяти (Memory) сложнее, чем по CPU, по ряду причин:

1. **Working Set vs RSS**: Kubernetes (и HPA) использует `working_set_bytes` (RSS + Page Cache). Если приложение активно читает файлы, кеш растет, и HPA может ошибочно считать, что память заканчивается.
2. **Отсутствие освобождения**: Многие среды исполнения (JVM, Go, Python) не возвращают память ОС мгновенно после завершения задач. Это приводит к тому, что HPA «застревает» на максимальном количестве реплик.
3. **Рекомендация**: Используйте память как **второстепенную** метрику или как ограничение (`ScalingLimited`), отдавая приоритет CPU или кастомным метрикам (RPS).

## 5. Конфликты с инструментами GitOps (ArgoCD)

Если в Git-репозитории в манифесте Deployment указано поле `replicas`, ArgoCD при включенном `SelfHeal` будет пытаться вернуть количество реплик к исходному значению, конфликтуя с HPA.

**Решение:** Настройте ArgoCD так, чтобы он игнорировал изменения в поле `replicas`:

```yaml
spec:
  ignoreDifferences:
    - group: apps
      kind: Deployment
      jsonPointers:
        - /spec/replicas
```
*Или просто удалите поле `replicas` из манифеста в Git — Kubernetes будет использовать значение по умолчанию (1), а HPA возьмет управление на себя.*

## 6. Алгоритм диагностики при сбоях

1. **`FailedGetResourceMetric`**: HPA не видит метрики.
   - Проверьте Metrics Server: `kubectl top pods`.
   - Проверьте наличие `resources.requests` у всех контейнеров пода.
2. **`FailedComputeMetricsReplicas`**: Ошибка в расчетах.
   - Проверьте лог `kube-controller-manager` на предмет ошибок аутентификации в Custom Metrics API.
3. **HPA не масштабирует вниз**:
   - Проверьте `stabilizationWindowSeconds` в `behavior`.
   - Проверьте `working_set_bytes` — возможно, память не освобождается.

## 7. Лучшие практики

- **PDB (Pod Disruption Budget)**: Обязательно используйте PDB вместе с HPA, чтобы агрессивный `scaleDown` не нарушил доступность сервиса (например, `minAvailable: 50%`).
- **Readiness Probes**: HPA учитывает только "готовые" поды. Без проб HPA может начать масштабирование на основе данных от еще не прогретых или некорректно запущенных подов.
- **CPU как база**: Для stateless-приложений CPU почти всегда является наиболее надежным показателем нагрузки.
- **Избегайте малых `maxReplicas`**: Слишком узкий диапазон (например, 1-2 реплики) лишает HPA смысла и делает его чувствительным к малейшим колебаниям.
