# HPA: Основные концепции

В данном документе рассматриваются логика работы, алгоритмы и архитектурные компоненты системы горизонтального масштабирования подов (Horizontal Pod Autoscaler).

Для получения вводной информации см. основной раздел **[HPA: Главная](./index.md)**. Готовые YAML-манифесты — в **[HPA: Практические сценарии](./hpa_scenarios.md)**. Продвинутая настройка и тонкая диагностика — в **[HPA: Продвинутые темы](./hpa_advanced.md)**.

## Определения

**Control Loop (Петля управления)** — бесконечный цикл, в котором контроллер HPA опрашивает API метрик, сравнивает результат с целевым значением и вносит корректировки. По умолчанию интервал опроса составляет 15 секунд (определяется флагом `--horizontal-pod-autoscaler-sync-period` в `kube-controller-manager`). Контроллер **никогда не останавливается** — даже если метрики стабильны, он продолжает опрашивать API и проверять, нет ли отклонений.

**ScaleTargetRef** — ссылка на объект, который управляет масштабированием (Deployment, ReplicaSet или StatefulSet). HPA не управляет подами напрямую — он изменяет поле `replicas` через `/scale` подресурс целевого объекта. При использовании Deployment необходимо ссылаться именно на Deployment, а не на ReplicaSet — иначе при Rollout HPA может масштабировать старый (неактивный) ReplicaSet.

**Stabilization Window (Окно стабилизации)** — временной интервал, используемый для фильтрации кратковременных колебаний метрик. Предотвращает «дребезг» (flapping) — частое переключение между увеличением и уменьшением количества реплик. По умолчанию: `scaleUp` = 0 секунд (мгновенная реакция), `scaleDown` = 300 секунд (5 минут ожидания стабильности). Максимальное значение — 3600 секунд.

**Target Utilization (Целевое использование)** — пороговое значение ресурса (например, 70% CPU), при котором система считается оптимально нагруженной. Рассчитывается как процент от `requests` контейнера. Например, при `requests.cpu: 200m` и `averageUtilization: 70%` HPA стремится к потреблению `140m` CPU на под.

**Requests и Limits** — фундаментальные поля ресурсов пода. `requests` — гарантированный объем ресурсов, зарезервированных для контейнера. HPA использует `requests` как базовую линию для расчета процента утилизации. `limits` — максимальный объем ресурсов, который контейнер может потребить. Без `requests` расчет утилизации невозможен, статус HPA будет `<unknown>`.

**Custom Metrics** — метрики, определяемые пользователем, доступные через API `custom.metrics.k8s.io`. Примеры: количество запросов в секунду (RPS), задержка ответа (latency), глубина очереди. Предоставляются адаптерами метрик (Prometheus Adapter) на основе данных из систем мониторинга.

**External Metrics** — метрики, находящиеся за пределами кластера, доступные через API `external.metrics.k8s.io`. Примеры: длина очереди RabbitMQ, количество сообщений в Kafka, метрики из внешних API. Обычно предоставляются KEDA или специализированными адаптерами.

## Предварительные требования

Для понимания концепций HPA необходимы следующие базовые знания:

1. **Pod и Container Resources:** понимание разницы между `requests` и `limits`, их влияние на планирование и потребление ресурсов.
2. **Deployment и ReplicaSet:** понимание иерархии объектов: Deployment → ReplicaSet → Pod, и того, как масштабирование работает через `/scale` подресурс.
3. **Metrics Server:** компонент кластера, собирающий метрики CPU/памяти из kubelet и предоставляющий их через Metrics API (`metrics.k8s.io`). Является обязательным для базового масштабирования.
4. **RBAC:** понимание ролей и привилегий Kubernetes. Контроллер HPA работает от имени сервис-аккаунта `system:hpa-controller` и должен иметь права на чтение и изменение подресурса `scale`.

Для практических предварительных требований (установка, проверка доступности, настройка) см. **[HPA: Главная — Предварительные требования](./index.md#предварительные-требования)**.

## Базовые концепции

### Алгоритм принятия решений

Количество необходимых реплик рассчитывается по формуле:

```
желаемые_реплики = ceil(текущие_реплики × (текущая_метрика / целевая_метрика))
```

**Особенности работы алгоритма:**

1.  **Толерантность (Tolerance):** Контроллер вносит изменения только в том случае, если отношение `текущая_метрика / целевая_метрика` выходит за пределы диапазона `[0.9, 1.1]`. Это значение настраивается через флаг `--horizontal-pod-autoscaler-tolerance` (по умолчанию 0.1, то есть 10%). Без толерантности HPA реагировал бы на каждое минимальное колебание метрики, что приводило бы к «дребезгу».
2.  **Округление:** Результат всегда округляется вверх (`ceil`), чтобы гарантировать достаточный запас ресурсов. Например, `ceil(3.1) = 4`, а не 3.
3.  **Обработка отсутствующих данных:** Если часть подов не отдает метрики (например, в процессе запуска), HPA делает «безопасное» предположение:
    *   При потенциальном **увеличении** количества реплик считается, что отсутствующие поды потребляют 0% ресурса (оптимистичный сценарий — чтобы не задерживать масштабирование).
    *   При потенциальном **уменьшении** количества реплик считается, что отсутствующие поды потребляют 100% ресурса (пессимистичный сценарий — чтобы не удалить «полезные» поды).
4.  **Несколько метрик:** Если в HPA задано несколько метрик, расчет производится для каждой отдельно. Контроллер выберет **наибольшее** из полученных значений желаемых реплик. Это гарантирует, что ни одна из метрик не будет проигнорирована.

#### Примеры расчета

**Простой случай — одна метрика:**
```
Текущее количество реплик: 2
Текущее потребление CPU: 90%
Целевое использование: 50%

Формула: ceil(2 × (90 / 50)) = ceil(2 × 1.8) = ceil(3.6) = 4 реплики
```

**С учетом толерантности:**
```
Текущее количество реплик: 2
Текущее потребление CPU: 54%
Целевое использование: 50%

Соотношение: 54 / 50 = 1.08
Допустимый диапазон толерантности: [0.9, 1.1]
1.08 попадает в диапазон → масштабирование НЕ происходит
```

**Нарушение толерантности (масштабирование вверх):**
```
Текущее количество реплик: 2
Текущее потребление CPU: 56%
Целевое использование: 50%

Соотношение: 56 / 50 = 1.12
1.12 > 1.1 (выходит за пределы толерантности) → масштабирование происходит
Формула: ceil(2 × (56 / 50)) = ceil(2 × 1.12) = ceil(2.24) = 3 реплики
```

**Две метрики (выбирается наибольшее):**
```
Метрика 1 (CPU): 2 реплики × (80% / 50%) = ceil(3.2) = 4 реплики
Метрика 2 (Memory): 2 реплики × (75% / 60%) = ceil(2.5) = 3 реплики

Результат: HPA выберет 4 реплики (наибольшее значение)
```

**Масштабирование вниз:**
```
Текущее количество реплик: 10
Текущее потребление CPU: 20%
Целевое использование: 50%

Формула: ceil(10 × (20 / 50)) = ceil(10 × 0.4) = ceil(4) = 4 реплики
```

### Типы метрик (API v2)

| Тип | Описание | Применение | Методы расчета |
| :--- | :--- | :--- | :--- |
| **Resource** | Стандартные ресурсы (CPU, Memory). | Масштабирование по утилизации ресурсов контейнеров. Наиболее предсказуемый тип для stateless-приложений. | `AverageUtilization` (процент от `requests`), `AverageValue` (абсолютное значение в среднем на под). |
| **ContainerResource** | Ресурсы конкретного контейнера в поде. | Позволяет игнорировать sidecar-контейнеры (Envoy, fluent-bit, telegraf), которые искажают общую картину утилизации. | `AverageUtilization`, `AverageValue`. |
| **Pods** | Метрики, относящиеся к каждому поду индивидуально (например, RPS на инстанс). | Масштабирование по нагрузке на каждый инстанс приложения. Используется, когда метрика привязана к конкретному поду. | `AverageValue` (среднее значение на под), `Value` (абсолютное значение). |
| **Object** | Метрики других объектов Kubernetes (например, Ingress, Job). | Масштабирование по общей нагрузке на балансировщик или очередь задач. Метрика является общей для всех подов. | `Value` (абсолютное значение для всего объекта), `AverageValue`. |
| **External** | Метрики вне кластера (очереди Kafka/RabbitMQ, метрики баз данных). | Использование KEDA или внешних адаптеров для масштабирования по бизнес-логике (очереди, RPI, размер БД). | `AverageValue` (среднее значение на под), `Value`. |

**Методы расчета:**
*   `AverageUtilization`: процент от `requests` (только для Resource и ContainerResource). Формула: `(текущее_потребление / requests) × 100%`.
*   `AverageValue`: абсолютное значение в среднем на под. HPA делит общее значение метрики на количество готовых подов.
*   `Value`: абсолютное значение для всего объекта (только для Object и External). HPA сравнивает общее значение метрики с целевым напрямую.

**Когда какой тип использовать:**
- **Resource (CPU):** Основной выбор для stateless-веб-приложений. Наиболее надежный и предсказуемый.
- **Resource (Memory):** Используйте как второстепенную метрику или ограничение безопасности. Многие среды (JVM, Go) не возвращают память ОС мгновенно после GC, что ведет к «застреванию» HPA на максимальных репликах.
- **ContainerResource:** Когда в поде есть sidecar, потребляющий значительную долю ресурсов (например, Envoy proxy — до 100m CPU).
- **Pods:** Когда метрика привязана к конкретному инстансу (RPS на под, размер локального кэша).
- **Object:** Когда метрика является общей для всех подов (общая нагрузка на Ingress, количество активных Job).
- **External:** Когда метрика находится за пределами кластера (очереди сообщений, данные из внешних API). Требует адаптера (KEDA, Prometheus Adapter).

### Архитектура и поток данных

Полный путь метрики от контейнера до решения о масштабировании:

```
Container (cgroups) → Kubelet (cAdvisor) → Metrics Server → Aggregated API (metrics.k8s.io) → HPA Controller → /scale subresource → Deployment/StatefulSet → Scheduler → Kubelet
```

1. **Сбор данных:** На каждом узле kubelet через cAdvisor (встроенный в kubelet) собирает метрики потребления CPU и памяти контейнерами из cgroups.
2. **Агрегация:** Metrics Server опрашивает kubelet на каждом узле и агрегирует данные в Resource Metrics API (`metrics.k8s.io`). Это компоненты Aggregation Layer Kubernetes.
3. **Запрос HPA:** HPA Controller обращается к Aggregated API для получения текущих значений метрик. Запросы выполняются каждые 15 секунд (по умолчанию).
4. **Расчет:** На основе формулы HPA вычисляет целевое количество реплик с учетом толерантности.
5. **Применение:** HPA изменяет значение `replicas` через `/scale` подресурс целевого объекта (Deployment, ReplicaSet, StatefulSet). Это позволяет масштабировать без изменения основной спецификации манифеста.
6. **Планирование:** Scheduler распределяет новые поды по узлам, Kubelet запускает контейнеры.

Для кастомных и внешних метрик конвейер расширяется:

```
Prometheus/KEDA → Custom/External Metrics Adapter → Custom Metrics API (custom.metrics.k8s.io) или External Metrics API (external.metrics.k8s.io) → HPA Controller
```

Prometheus Adapter или KEDA подключаются как дополнительные источники метрик через Aggregated API и предоставляют данные в формате, понятном HPA Controller.

### Компоненты архитектуры

1.  **HPA Controller:** Контроллер в составе `kube-controller-manager`. Он выполняет математические расчеты и применяет изменения через механизм изменения **`/scale` подресурса (subresource)** целевого объекта (Deployment, ReplicaSet, StatefulSet). Это позволяет HPA менять количество реплик, не затрагивая основную спецификацию манифеста. Контроллер не хранит состояние — все решения принимаются на основе текущих метрик и конфигурации HPA.
2.  **Aggregation Layer:** Механизм Kubernetes, позволяющий регистрировать дополнительные API (например, `metrics.k8s.io`, `custom.metrics.k8s.io`). Расширяет базовый API-сервер без модификации его кода.
3.  **Metrics Server:** Собирает базовые метрики (CPU/RAM) из kubelet и предоставляет их через Metrics API. Является обязательным для базового масштабирования по ресурсам. Не хранит историю — предоставляет только текущие значения.
4.  **Custom/External Metrics Adapters:** Сторонние компоненты (например, Prometheus Adapter, KEDA), которые забирают данные из систем мониторинга и отдают их в формате Kubernetes API. Подключаются через Aggregation Layer.

## Практические сценарии

### Валидация работы HPA

После создания HPA необходимо убедиться, что он работает корректно:

```bash
# Проверка текущего состояния HPA
kubectl get hpa my-app
# → NAME       REFERENCE          TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
# → my-app     Deployment/my-app  35%/70%   3         20        3          5m

# Детальная информация (включая условия и события)
kubectl describe hpa my-app

# Просмотр условий (Conditions) — первый источник диагностики
kubectl get hpa my-app -o jsonpath='{.status.conditions[*].type}'
# → AbleToScale ScalingActive ScalingLimited

# Проверка конкретного условия
kubectl get hpa my-app -o jsonpath='{.status.conditions[?(@.type=="ScalingActive")].status}'
# → True (метрики собираются) или False (проблема)

# Просмотр текущего потребления ресурсов
kubectl top pods -l app=my-app
```

**Ожидаемый результат:** В колонке `TARGETS` отображается процент утилизации (например, `35%/70%`), а не `<unknown>`. Если TARGETS = `<unknown>`, см. раздел «Типовые проблемы» ниже.

### Типовые проблемы при внедрении

| Проблема | Причина | Решение |
|:---|:---|:---|
| `TARGETS` показывает `<unknown>` | Отсутствуют `requests` у контейнеров или Metrics Server недоступен. | Добавить `resources.requests` всем контейнерам, установить Metrics Server. |
| HPA не масштабирует вниз | Метрики не падают ниже порога толерантности или достигнут `minReplicas`. | Проверить фактическое потребление: `kubectl top pods`. Уменьшить `minReplicas`. |
| HPA не масштабирует вверх | Метрики стабильны в пределах толерантности (±10% от целевого значения). | Проверить, что нагрузка действительно растет. Увеличить `maxReplicas`. |
| Дребезг (flapping) | Частое переключение между масштабированием вверх и вниз. | Настроить `behavior` с окном стабилизации для `scaleDown`. Увеличить `maxReplicas`. |
| Конфликт с ручным `kubectl scale` | HPA перезаписывает вручную заданные `replicas`. | Управлять масштабированием только через HPA. Не использовать `kubectl scale` для масштабируемых объектов. |
| `<unknown>` при работающем Metrics Server | У sidecar-контейнера отсутствуют `requests`. HPA требует `requests` для **всех** контейнеров. | Добавить `requests` sidecar или использовать тип метрики `ContainerResource`. |

Детальная диагностика: [Устранение неполадок HPA](../../Troubleshooting/Common_Errors/hpa_troubleshooting.md).

## Дополнительная информация

### Граничные случаи (Edge Cases)

1. **Масштабирование при обновлении Deployment:** При Rollout Deployment создается новый ReplicaSet. HPA начинает масштабировать новый ReplicaSet только после того, как поды из него становятся `Ready`. Старый ReplicaSet масштабируется вниз. Если `scaleTargetRef` указывает на ReplicaSet (а не на Deployment), HPA может масштабировать неактивный ReplicaSet.

2. **HPA иemonset:** HPA **не поддерживается** для DaemonSet, так как DaemonSet гарантирует ровно один под на каждом узле. Масштабирование регулируется количеством узлов в кластере.

3. **HPA и Job/CronJob:** HPA обычно **не применяется** к Job и CronJob, так как эти объекты имеют конечный жизненный цикл. Для масштабирования воркеров в очередях используйте **[KEDA ScaledJob](../keda/keda_concepts.md#scaledjob-dlya-batch-zadach)** — кастомный ресурс, создающий новую Kubernetes Job для каждого поступившего события. Сравнение ScaledObject vs ScaledJob см. в **[Workers + Queue Pattern](../workers_queue_pattern.md)**.

4. **Множественные HPA на один объект:** Kubernetes **не запрещает** создание нескольких HPA на один Deployment. Однако это приводит к непредсказуемому поведению — каждый HPA независимо рассчитывает целевое количество реплик и конфликтует за право записи в `/scale`. Рекомендация: **один HPA на объект**, несколько метрик в одном HPA.

5. **Отсутствие метрик при масштабировании вниз:** Если Metrics Server временно недоступен, HPA **не уменьшает** количество реплик — он сохраняет текущее состояние до восстановления доступа к метрикам. Это защитный механизм для предотвращения ошибочного удаления реплик.

6. **Очень маленький `maxReplicas`:** Диапазон `min=1, max=2` лишает HPA математического смысла — формула `ceil(1 × (метрика / цель))` практически всегда даст 1 или 2, и HPA будет постоянно «застревать» на лимитах. Рекомендуется `maxReplicas >= 5` для корректной работы алгоритма.

7. **Нулевое потребление метрик:** Если все поды потребляют 0% ресурсов (приложение простаивает), HPA рассчитает: `ceil(3 × (0 / 50)) = ceil(0) = 0`. Однако `minReplicas` не позволит опуститься ниже заданного минимума. Для масштабирования до нуля используйте KEDA.

### Лучшие практики

1. **Начинайте с CPU:** Для stateless-приложений CPU является наиболее надежным и предсказуемым показателем нагрузки.
2. **Настраивайте `behavior`:** Для продакшена всегда определяйте политики scaleUp/scaleDown. Агрессивный рост при пиках и медленное сжатие — типичный паттерн.
3. **Используйте PDB:** Обязательно создавайте **Pod Disruption Budget** вместе с HPA. Это гарантирует, что при масштабировании вниз или удалении узлов не будет нарушена доступность сервиса.
4. **Настраивайте Readiness Probes:** HPA учитывает только «готовые» поды. Без настроенных `readinessProbe` HPA может начать масштабирование на основе данных от еще не прогретых подов.
5. **Избегайте узких диапазонов `maxReplicas`:** Слишком маленький диапазон (например, 1-2 реплики) лишает HPA математического смысла и делает его излишне чувствительным к колебаниям.
6. **Не задавайте `replicas` в манифесте:** Если HPA управляет масштабированием — удалите поле `replicas` из Deployment-манителста. Иначе повторный `kubectl apply` перезапишет значение, выставленное HPA.
7. **Память как второстепенная метрика:** Многие среды (JVM, Go) не возвращают память ОС мгновенно после GC, что ведет к «застреванию» HPA на максимальных репликах. Используйте память как ограничение безопасности, а не основную метрику.

### Взаимодействие с другими компонентами

- **[Cluster Autoscaler (CA)](../cluster_autoscaler_detailed.md):** HPA создает потребность в новых подах, а CA реагирует на поды в статусе `Pending`, добавляя узлы в кластер. CA опирается на `requests` для принятия решений — завышенные requests ведут к over-provisioning, заниженные — к нехватке узлов.
- **[Vertical Pod Autoscaler (VPA)](../vpa_detailed.md):** Совместное использование на одних и тех же ресурсах (CPU/RAM) **строго запрещено**, так как это приводит к бесконечной гонке: HPA создает новые поды, а VPA изменяет их запросы, что ломает расчеты утилизации. Корректные связки: HPA по кастомной метрике + VPA по ресурсам, или HPA по ресурсам + VPA в режиме `Off`.
- **[Pod Disruption Budget (PDB)](../pod_disruption_budget.md):** HPA учитывает PDB при масштабировании вниз, предотвращая удаление подов ниже критического уровня доступности.
- **[KEDA](../keda/keda_concepts.md):** Событийное масштабирование и Scale-to-Zero. Рекомендуемый подход для воркеров и queue-based нагрузок. KEDA не заменяет HPA, а управляет им, динамически подставляя значения в HPA object.
