# Horizontal Pod Autoscaler (HPA): Основные концепции

В данном документе подробно рассматривается логика работы, алгоритмы и архитектурные компоненты системы горизонтального масштабирования подов.

## Определения

Для получения базовой информации см. основной раздел **[HPA (index.md)](./index.md)**.

**Control Loop (Петля управления)** — бесконечный цикл, в котором контроллер HPA опрашивает API (Application Programming Interface) метрик, сравнивает результат с целевым значением и вносит корректировки.

**Stabilization Window (Окно стабилизации)** — временной интервал, используемый для фильтрации кратковременных колебаний метрик. Предотвращает «дребезг» (частое переключение между увеличением и уменьшением количества реплик).

**Target Utilization (Целевое использование)** — пороговое значение ресурса (например, 70% CPU), при котором система считается оптимально нагруженной.

## Базовые концепции

### Алгоритм принятия решений

Контроллер HPA опрашивает метрики с интервалом 15 секунд (по умолчанию). Количество необходимых реплик рассчитывается по формуле:

```
желаемые_реплики = ceil(текущие_реплики × (текущая_метрика / целевая_метрика))
```

**Особенности расчета:**
- **Округление:** результат всегда округляется вверх (`ceil`).
- **Толерантность:** если разница между текущей и целевой метрикой менее 10% (по умолчанию), изменения не вносятся.
- **Отсутствие данных:** если часть подов не отдает метрики, HPA делает консервативное предположение для обеспечения стабильности.

### Типы метрик

| Тип | Описание | Источники данных |
| :--- | :--- | :--- |
| **Resource** | Стандартные ресурсы контейнера | Metrics Server (API `metrics.k8s.io`) |
| **Pods** | Метрики, относящиеся к подам (RPS) | Prometheus Adapter (API `custom.metrics.k8s.io`) |
| **Object** | Метрики других объектов K8s (Ingress) | Custom Metrics API |
| **External** | Внешние по отношению к кластеру метрики | KEDA (Kubernetes Event-driven Autoscaling) |

### Компоненты архитектуры

1. **HPA Controller:** компонент `kube-controller-manager`, отвечающий за логику масштабирования.
2. **Metrics Registry:** реестр API, через который контроллер находит нужные источники данных.
3. **Metrics Server:** агрегатор базовых ресурсных метрик (CPU, Memory).
4. **Адаптеры:** специализированные сервисы (Prometheus Adapter, Stackdriver Adapter), преобразующие внешние метрики в формат Kubernetes API.

### Конфигурация поведения (Behavior)

Настройка `behavior` позволяет раздельно управлять политиками `scaleUp` (расширение) и `scaleDown` (сжатие).

- **Stabilization Window:** для `scaleDown` рекомендуется 300 секунд (5 минут), для `scaleUp` — 0 секунд (мгновенная реакция).
- **Политики:** можно ограничить скорость изменения (например, «не более 4 подов в минуту» или «не более 100% от текущего числа за 15 секунд»).

## Практические сценарии

Выбор концептуального подхода зависит от типа нагрузки приложения:

- **Вычислительная нагрузка:** использование `Resource Metrics` по CPU (Central Processing Unit).
- **Сетевая нагрузка:** масштабирование по `Custom Metrics` на основе RPS (Requests Per Second) или активных соединений.
- **Асинхронная обработка:** использование `External Metrics` для контроля длины очередей в брокерах сообщений.

Более подробные примеры реализации представлены в разделе **[Практические сценарии (hpa_scenarios.md)](./hpa_scenarios.md)**.
