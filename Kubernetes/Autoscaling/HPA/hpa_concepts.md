# HPA: Основные концепции

В данном документе рассматривается логика работы, алгоритмы и архитектурные компоненты системы горизонтального масштабирования подов (Horizontal Pod Autoscaler).

## Определения

Для получения вводной информации см. основной раздел **[HPA: Главная](./index.md)**.

**Control Loop (Петля управления)** — бесконечный цикл, в котором контроллер HPA опрашивает API метрик, сравнивает результат с целевым значением и вносит корректировки. По умолчанию интервал опроса составляет 15 секунд.

**Stabilization Window (Окно стабилизации)** — временной интервал, используемый для фильтрации кратковременных колебаний метрик. Предотвращает «дребезг» (flapping) — частое переключение между увеличением и уменьшением количества реплик.

**Target Utilization (Целевое использование)** — пороговое значение ресурса (например, 70% CPU), при котором система считается оптимально нагруженной.

## Базовые концепции

### Алгоритм принятия решений

Количество необходимых реплик рассчитывается по формуле:

```
желаемые_реплики = ceil(текущие_реплики × (текущая_метрика / целевая_метрика))
```

**Особенности работы алгоритма:**

1.  **Толерантность (Tolerance):** Контроллер вносит изменения только в том случае, если отношение `текущая_метрика / целевая_метрика` выходит за пределы диапазона `[0.9, 1.1]`. Это значение настраивается через флаг `--horizontal-pod-autoscaler-tolerance`.
2.  **Округление:** Результат всегда округляется вверх (`ceil`), чтобы гарантировать достаточный запас ресурсов.
3.  **Обработка отсутствующих данных:** Если часть подов не отдает метрики (например, в процессе запуска), HPA делает «безопасное» предположение:
    *   При потенциальном **увеличении** количества реплик считается, что отсутствующие поды потребляют 0% ресурса.
    *   При потенциальном **уменьшении** количества реплик считается, что отсутствующие поды потребляют 100% ресурса.
4.  **Несколько метрик:** Если в HPA задано несколько метрик, расчет производится для каждой отдельно. Контроллер выберет **наибольшее** из полученных значений желаемых реплик.

### Типы метрик (API v2)

| Тип | Описание | Применение |
| :--- | :--- | :--- |
| **Resource** | Стандартные ресурсы (CPU, Memory). | Масштабирование по утилизации ресурсов контейнеров. |
| **ContainerResource** | Ресурсы конкретного контейнера в поде. | Позволяет игнорировать sidecar-контейнеры. |
| **Pods** | Метрики, относящиеся к подам (например, RPS). | Масштабирование по нагрузке на каждый инстанс. |
| **Object** | Метрики других объектов K8s (например, Ingress). | Масштабирование по общей нагрузке на балансировщик. |
| **External** | Метрики вне кластера (очереди, Cloud API). | Использование KEDA или внешних адаптеров. |

**Методы расчета:**
*   `AverageUtilization`: процент от `requests` (только для Resource).
*   `AverageValue`: абсолютное значение в среднем на под.
*   `Value`: абсолютное значение для всего объекта (только для Object/External).

### Компоненты архитектуры

1.  **HPA Controller:** Контроллер в составе `kube-controller-manager`. Он выполняет математические расчеты и применяет изменения через механизм изменения **`/scale` подресурса (subresource)** целевого объекта (Deployment, ReplicaSet, StatefulSet). Это позволяет HPA менять количество реплик, не затрагивая основную спецификацию манифеста.
2.  **Aggregation Layer:** Механизм Kubernetes, позволяющий регистрировать дополнительные API (например, `metrics.k8s.io`).
3.  **Metrics Server:** Собирает базовые метрики (CPU/RAM) из kubelet и предоставляет их через Metrics API.
4.  **Custom/External Metrics Adapters:** Сторонние компоненты (например, Prometheus Adapter), которые забирают данные из систем мониторинга и отдают их в формате Kubernetes API.

## Практические сценарии

### Концептуальный пример расчета при всплеске нагрузки

Предположим, у вас есть Deployment с `target utilization = 50%` CPU.
- Текущее количество реплик: `2`
- Внезапный скачок нагрузки приводит к тому, что поды начинают потреблять в среднем `90%` CPU.
- Формула: `ceil(2 × (90 / 50)) = ceil(2 × 1.8) = ceil(3.6) = 4` реплики.

Контроллер HPA обратится к API Kubernetes и обновит `/scale` подресурс Deployment, установив значение `replicas: 4`. Планировщик (Scheduler) и Kubelet распределят новые поды, и через некоторое время средняя нагрузка упадет ближе к целевым 50%.

## Дополнительная информация

### Взаимодействие с другими компонентами

*   **Cluster Autoscaler (CA):** HPA создает потребность в новых подах, а CA реагирует на поды в статусе `Pending`, добавляя узлы в кластер (инфраструктурное масштабирование).
*   **Vertical Pod Autoscaler (VPA):** Совместное использование на одних и тех же ресурсах (CPU/RAM) **строго запрещено**, так как это приводит к бесконечной гонке: HPA создает новые поды, а VPA изменяет их запросы, что ломает расчеты утилизации.
*   **Pod Disruption Budget (PDB):** HPA учитывает PDB при масштабировании вниз, предотвращая удаление подов ниже критического уровня доступности.
