# Horizontal Pod Autoscaler (HPA)

Horizontal Pod Autoscaler (HPA) — механизм автоматического масштабирования количества подов в Kubernetes на основе метрик потребления ресурсов или пользовательских показателей.

## Определения

**Horizontal Pod Autoscaler (HPA)** — контроллер в составе `kube-controller-manager`, который автоматически изменяет количество реплик в Deployment, ReplicaSet или StatefulSet. Он работает по принципу «петли управления» (control loop), по умолчанию сверяя метрики каждые 15 секунд (определяется флагом `--horizontal-pod-autoscaler-sync-period` в `kube-controller-manager`).

**Масштабирование по горизонтали** — процесс увеличения или уменьшения количества экземпляров приложения (подов) для обработки изменяющейся нагрузки.

**Metrics Server** — компонент кластера, агрегирующий метрики использования ресурсов (CPU, память) и предоставляющий их через Metrics API (`metrics.k8s.io`). Является обязательным для базовых сценариев автомасштабирования по ресурсам.

**Control Loop (Петля управления)** — бесконечный цикл, в котором контроллер HPA опрашивает API метрик, сравнивает результат с целевым значением и вносит корректировки в количество реплик. По умолчанию интервал опроса составляет 15 секунд.

## Базовые концепции

### Архитектура и конвейер метрик

Решение HPA о масштабировании проходит через цепочку компонентов:

```
kubelet (cAdvisor) → Metrics Server → Aggregated API (metrics.k8s.io) → HPA Controller → /scale subresource → Scheduler → Kubelet
```

1. **Сбор данных:** kubelet на каждом узле через cAdvisor собирает метрики потребления CPU и памяти контейнерами.
2. **Агрегация:** Metrics Server опрашивает kubelet и агрегирует данные в Resource Metrics API (`metrics.k8s.io`).
3. **Запрос HPA:** HPA Controller обращается к Aggregated API для получения текущих значений метрик.
4. **Расчет:** На основе формулы HPA вычисляет целевое количество реплик.
5. **Применение:** HPA изменяет значение `replicas` через `/scale` подресурс целевого объекта (Deployment, ReplicaSet, StatefulSet). Это позволяет масштабировать без изменения основной спецификации манифеста.
6. **Планирование:** Scheduler распределяет новые поды по узлам, Kubelet запускает контейнеры.

Для кастомных и внешних метрик конвейер расширяется: Prometheus Adapter или KEDA подключаются как дополнительные источники через Custom Metrics API (`custom.metrics.k8s.io`) или External Metrics API (`external.metrics.k8s.io`).

### Версии API

Существует две основные версии API для HPA:
-   **`autoscaling/v1`**: Первая стабильная версия, поддерживает масштабирование только на основе метрики CPU. Проста в использовании, но сильно ограничена.
-   **`autoscaling/v2`**: Стабильная (GA) версия, начиная с Kubernetes 1.23. Является стандартом и настоятельно рекомендуется к использованию. Расширяет возможности:
    -   Масштабирование по нескольким метрикам одновременно (CPU, память).
    -   Пользовательские метрики (`Custom Metrics`) и внешние метрики (`External Metrics`).
    -   Тонкая настройка поведения масштабирования через блок `behavior`.

### Алгоритм и толерантность

-   **Формула расчёта:** `желаемое количество = ceil[текущее количество * (текущее значение метрики / целевое значение метрики)]`.
-   **Толерантность (Tolerance):** По умолчанию HPA игнорирует изменения метрики, если соотношение текущего значения к целевому близко к 1.0. Стандартная толерантность составляет 0.1 (10%). Это означает, что масштабирование не произойдет, пока разница между текущей и целевой метрикой не превысит 10%. Это предотвращает «дребезг» (флаттеринг) при незначительных колебаниях нагрузки.
-   **Округление:** Результат всегда округляется вверх (`ceil`), чтобы гарантировать достаточный запас ресурсов.
-   **Обработка отсутствующих данных:** Если часть подов не отдает метрики (например, в процессе запуска), HPA делает «безопасное» предположение:
    -   При потенциальном **увеличении** количества реплик считается, что отсутствующие поды потребляют 0% ресурса.
    -   При потенциальном **уменьшении** количества реплик считается, что отсутствующие поды потребляют 100% ресурса.
-   **Несколько метрик:** Если в HPA задано несколько метрик, расчет производится для каждой отдельно. Контроллер выберет **наибольшее** из полученных значений желаемых реплик.

### Типы метрик (API v2)

| Тип | Описание | Применение |
|:---|:---|:---|
| **Resource** | Стандартные ресурсы (CPU, Memory). | Масштабирование по утилизации ресурсов контейнеров. |
| **ContainerResource** | Ресурсы конкретного контейнера в поде. | Позволяет игнорировать sidecar-контейнеры. |
| **Pods** | Метрики, относящиеся к подам (например, RPS). | Масштабирование по нагрузке на каждый инстанс. |
| **Object** | Метрики других объектов Kubernetes (например, Ingress). | Масштабирование по общей нагрузке на балансировщик. |
| **External** | Метрики вне кластера (очереди, Cloud API). | Использование KEDA или внешних адаптеров. |

**Методы расчета:**
-   `AverageUtilization`: процент от `requests` (только для Resource).
-   `AverageValue`: абсолютное значение в среднем на под.
-   `Value`: абсолютное значение для всего объекта (только для Object/External).

### Управление поведением (Behavior)

Начиная с `autoscaling/v2`, HPA поддерживает блок `behavior`, который позволяет гибко настраивать скорость масштабирования (scale-up и scale-down) и окна стабилизации (`stabilizationWindowSeconds`).
-   **Окно стабилизации** позволяет HPA «запоминать» исторические рекомендации и выбирать наибольшее/наименьшее значение из них за указанный период, предотвращая резкое удаление подов при кратковременном спаде нагрузки.
-   **`selectPolicy`**: определяет поведение при наличии нескольких политик: `Max` (наибольшее кол-во реплик, по умолчанию), `Min` (наименьшее) или `Disabled` (отключение масштабирования в данном направлении).

## Предварительные требования

Перед настройкой HPA необходимо убедиться в выполнении следующих условий:

1. **Metrics Server:** должен быть развернут в кластере для сбора данных о потреблении ресурсов (CPU/память). Проверка:
   ```bash
   kubectl get apiservice v1beta1.metrics.k8s.io
   # → v1beta1.metrics.k8s.io    kube-system/metrics-server   True    1m
   kubectl top pods
   ```
   Если Metrics Server не установлен, см. раздел [Metrics Server](../../MonitoringLogging/metrics-server.md).

2. **Resource Requests:** HPA использует запросы ресурсов (`requests`) в спецификации пода как базовую линию для расчета процента утилизации. Без них расчет в процентах невозможен, и статус HPA будет `<unknown>`:
   ```yaml
   resources:
     requests:
       cpu: "200m"
       memory: "256Mi"
   ```
   **Важно:** `requests` должны быть заданы у **всех** контейнеров пода (включая sidecar). Если хотя бы один контейнер не имеет `requests`, HPA не сможет рассчитать утилизацию.

3. **RBAC:** ServiceAccount, от имени которого работает HPA, должен иметь права на чтение и изменение подресурса `scale` целевого объекта. Для стандартного HPA эти права включены в ClusterRole `system:hpa-controller`.

4. **Корректный `scaleTargetRef`:** HPA должен указывать на Deployment, ReplicaSet или StatefulSet, а не на Pod напрямую. При использовании Deployment настраивайте HPA на **Deployment**, а не на ReplicaSet — иначе при Rollout HPA может масштабировать старый (неактивный) ReplicaSet.

## Практические сценарии

### Создание HPA

HPA можно создать двумя способами:

**Способ 1: Через kubectl (быстрый)**
```bash
# Масштабирование по CPU (70% утилизации, от 3 до 20 реплик)
kubectl autoscale deployment my-app --cpu-percent=70 --min=3 --max=20

# Просмотр в реальном времени
kubectl get hpa my-app -w
```

**Способ 2: Через YAML-манифест (рекомендуемый)**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app
  minReplicas: 3
  maxReplicas: 20
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

### Валидация работы HPA

```bash
# Текущее состояние и целевые метрики
kubectl get hpa my-app
# → NAME       REFERENCE          TARGETS   MINPODS   MAXPODS   REPLICAS   AGE
# → my-app     Deployment/my-app  35%/70%   3         20        3          5m

# Детальная информация и события
kubectl describe hpa my-app

# Имитация нагрузки для проверки масштабирования
kubectl run load-generator --rm -i --tty --image=busybox -- /bin/sh -c "while true; do wget -q -O- http://my-app:8080; done"
```

### Типовые сценарии

| Сценарий | Метрика | Пример использования |
|:---|:---|:---|
| Stateless веб-приложения | CPU | Nginx, Node.js, Go-сервисы |
| Мультиметрика | CPU + Memory | Приложения с кэшированием |
| Очереди сообщений | External (очередь) | Воркеры Kafka, RabbitMQ |
| HTTP-нагрузка | Custom (RPS) | API-сервисы за Ingress |

[Готовые YAML-манифесты для каждого сценария](./hpa_scenarios.md)

### Типовые проблемы при внедрении

-   **`<unknown>` в колонке TARGETS:** отсутствуют `requests` у контейнеров или Metrics Server недоступен. Решение: добавить `resources.requests` или установить Metrics Server.
-   **HPA не масштабирует вниз:** метрики не падают ниже порога толерантности или достигнут `minReplicas`. Проверьте фактическое потребление: `kubectl top pods`.
-   **Дребезг (flapping):** частое переключение между масштабированием вверх и вниз. Решение: настроить `behavior` с окном стабилизации.
-   **Конфликт с ручным `kubectl scale`:** HPA перезаписывает вручную заданные `replicas`. Управляйте масштабированием только через HPA.

Детальная диагностика: [Устранение неполадок HPA](../../Troubleshooting/Common_Errors/hpa_troubleshooting.md).

## Дополнительная информация

### Преимущества и ограничения

- **Оптимизация ресурсов:** поддержание баланса между производительностью и стоимостью. Вы платите только за те ресурсы, которые нужны.
- **Ограничение `minReplicas`:** HPA сам по себе не масштабирует ресурсы ниже `minReplicas` (не поддерживает scale-to-zero). Для масштабирования до нуля требуется **KEDA**.
- **Конфликт с VPA:** HPA по CPU/Memory конфликтует с Vertical Pod Autoscaler (VPA) в активных режимах. Их совместное использование допускается только при разнесении метрик (например, HPA по кастомной метрике, VPA по CPU/Mem).
- **Неподдерживаемые объекты:** HPA не используется для `DaemonSet` (по одному поду на узел) и обычно не применяется к `Job`/`CronJob`.

### Лучшие практики

1. **Начинайте с CPU:** Для stateless-приложений CPU является наиболее надежным и предсказуемым показателем нагрузки. Память используйте как второстепенную метрику — многие среды (JVM, Go) не возвращают память ОС мгновенно после GC, что ведет к «застреванию» HPA на максимальных репликах.
2. **Настраивайте `behavior`:** Для продакшена всегда определяйте политики scaleUp/scaleDown. Агрессивный рост при пиках и медленное сжатие — типичный паттерн.
3. **Используйте PDB:** Обязательно создавайте **Pod Disruption Budget** вместе с HPA. Это гарантирует, что при масштабировании вниз или удалении узлов не будет нарушена доступность сервиса.
4. **Настраивайте Readiness Probes:** HPA учитывает только «готовые» поды. Без настроенных `readinessProbe` HPA может начать масштабирование на основе данных от еще не прогретых подов.
5. **Избегайте узких диапазонов `maxReplicas`:** Слишком маленький диапазон (например, 1-2 реплики) лишает HPA математического смысла и делает его излишне чувствительным к колебаниям.
6. **Не задавайте `replicas` в манифесте:** Если HPA управляет масштабированием — удалите поле `replicas` из Deployment-манителста. Иначе повторный `kubectl apply` перезапишет значение, выставленное HPA.
7. **Тестируйте в staging:** Вводите масштабирование постепенно, начиная с наименее критичных сервисов. Обязательно тестируйте настройки `behavior` под имитируемой нагрузкой.

### Взаимодействие с другими компонентами

-   **[Metrics Server](../../MonitoringLogging/metrics-server.md)** — источник данных для базового масштабирования по ресурсам.
-   **[KEDA](../keda/keda_concepts.md)** — событийное масштабирование и Scale-to-Zero. Рекомендуемый подход для воркеров иueue-based нагрузок.
-   **[VPA](../vpa_detailed.md)** — вертикальное масштабирование. Никогда не используйте HPA и VPA по одним и тем же ресурсам (CPU/Memory) одновременно. Корректные связки: HPA по RPS + VPA по ресурсам, или HPA по ресурсам + VPA в режиме `Off` (для аналитики).
-   **[Cluster Autoscaler](../cluster_autoscaler_detailed.md)** — инфраструктурное масштабирование. HPA создает поды, которые триггерят работу CA при нехватке узлов. CA опирается на `requests` для принятия решений — завышенные requests ведут к over-provisioning, заниженные — к нехватке узлов.
-   **[Pod Disruption Budget](../pod_disruption_budget.md)** — защита кворума и доступности приложения при масштабировании вниз (scale-down).
-   **[Обзор автомасштабирования](../overview_concepts.md)** — место HPA в общей архитектуре Kubernetes.

### Диагностика

Для быстрой проверки состояния HPA:
- `kubectl get hpa` — текущие метрики и количество реплик. Если в колонке TARGETS указано `<unknown>`, это говорит об ошибке сбора метрик.
- `kubectl describe hpa <name>` — просмотр событий (Events) и причин последнего масштабирования.
- `kubectl get hpa <name> -o yaml` — полный вывод статуса, включая `status.conditions`.

### Советы для собеседования

**Вопрос:** Как работает HPA в Kubernetes?
**Ответ:** HPA реализует «петлю управления» (control loop). Каждые 15 секунд контроллер опрашивает API метрик (Metrics Server для CPU/Memory, Prometheus Adapter для кастомных), вычисляет целевое количество реплик по формуле `ceil[текущее * (текущая_метрика / целевая_метрика)]` с учетом толерантности 10%, и применяет результат через `/scale` подресурс Deployment/StatefulSet. Блок `behavior` позволяет управлять скоростью масштабирования и окнами стабилизации для предотвращения дребезга.

**Вопрос:** Почему HPA показывает `<unknown>` в колонке TARGETS?
**Ответ:** Три основные причины: (1) Metrics Server не установлен или недоступен — `kubectl get apiservice v1beta1.metrics.k8s.io` покажет `False`; (2) У контейнеров не заданы `resources.requests` — HPA не может рассчитать процент утилизации; (3) Некоторые поды в процессе запуска и не отдают метрики. Проверка: `kubectl top pods`, `kubectl describe hpa`.

**Вопрос:** Можно ли масштабировать поды на основе размера очереди (например, RabbitMQ)?
**Ответ:** Да. Это можно сделать двумя способами:
1. **Custom/External Metrics:** используя адаптер метрик (Prometheus Adapter), который экспортирует данные из системы очередей в Metrics API Kubernetes.
2. **KEDA (Kubernetes Event-driven Autoscaling):** это проект CNCF, устанавливающий оператор, который сам собирает метрики (более 50+ скалеров) и транслирует их в HPA. Это рекомендуемый современный подход, поддерживающий масштабирование в ноль.

**Вопрос:** В чем разница между HPA и VPA?
**Ответ:** HPA масштабирует **количество** реплик (горизонтально), VPA масштабирует **ресурсность** каждой реплики (вертикально, изменяя `requests` и `limits`). Их совместное использование по одним и тем же ресурсам (CPU/Memory) запрещено — возникает бесконечная гонка. Корректные связки: HPA по кастомной метрике + VPA по ресурсам, или HPA по ресурсам + VPA в режиме `Off`.

**Вопрос:** Как HPA взаимодействует с Cluster Autoscaler?
**Ответ:** HPA создает поды, которые при нехватке ресурсов кластера переходят в статус `Pending`. Cluster Autoscaler обнаруживает такие поды и добавляет новые узлы. CA опирается на `requests` подов для принятия решений — поэтому корректная настройка `requests` критична для обоих механизмов.

**Вопрос:** Как предотвратить дребезг (flapping) HPA?
**Ответ:** Использовать поле `behavior` в API v2: настроить `stabilizationWindowSeconds` для `scaleDown` (по умолчанию 300с) и задать консервативные политики (например, уменьшение на 10% за раз с периодом 60с). Также важно иметь достаточный диапазон `maxReplicas` и корректно настроенные readiness probes.
