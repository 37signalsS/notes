# Horizontal Pod Autoscaler (HPA)

Horizontal Pod Autoscaler (HPA) — механизм автоматического масштабирования количества подов в Kubernetes на основе метрик потребления ресурсов или пользовательских показателей.

## Определения

**Horizontal Pod Autoscaler (HPA)** — контроллер в составе `kube-controller-manager`, который автоматически изменяет количество реплик в Deployment, ReplicaSet или StatefulSet. Он работает по принципу «петли управления» (control loop), по умолчанию сверяя метрики каждые 15 секунд (определяется флагом `--horizontal-pod-autoscaler-sync-period` в `kube-controller-manager`).

**Масштабирование по горизонтали** — процесс увеличения или уменьшения количества экземпляров приложения (подов) для обработки изменяющейся нагрузки.

**Metrics Server** — компонент кластера, агрегирующий метрики использования ресурсов (CPU, память) и предоставляющий их через Metrics API (`metrics.k8s.io`). Является обязательным для базовых сценариев автомасштабирования по ресурсам.

## Базовые концепции

Логика HPA основана на расчёте необходимого количества реплик для достижения целевого значения метрики. 

### Версии API

Существует две основные версии API для HPA:
-   **`autoscaling/v1`**: Первая стабильная версия, поддерживает масштабирование только на основе метрики CPU. Проста в использовании, но сильно ограничена.
-   **`autoscaling/v2`**: Стабильная (GA) версия, начиная с Kubernetes 1.23. Является стандартом и настоятельно рекомендуется к использованию. Расширяет возможности:
    -   Масштабирование по нескольким метрикам одновременно (CPU, память).
    -   Пользовательские метрики (`Custom Metrics`) и внешние метрики (`External Metrics`).
    -   Тонкая настройка поведения масштабирования через блок `behavior`.

### Алгоритм и толерантность

-   **Формула расчета:** `желаемое количество = ceil[текущее количество * (текущее значение метрики / целевое значение метрики)]`.
-   **Толерантность (Tolerance):** По умолчанию HPA игнорирует изменения метрики, если соотношение текущего значения к целевому близко к 1.0. Стандартная толерантность составляет 0.1 (10%). Это означает, что масштабирование не произойдет, пока разница между текущей и целевой метрикой не превысит 10%. Это предотвращает «дребезг» (флаттеринг) при незначительных колебаниях нагрузки.

### Управление поведением (Behavior)

Начиная с `autoscaling/v2`, HPA поддерживает блок `behavior`, который позволяет гибко настраивать скорость масштабирования (scale-up и scale-down) и окна стабилизации (`stabilizationWindowSeconds`). 
- **Окно стабилизации** позволяет HPA "запоминать" исторические рекомендации и выбирать наибольшее/наименьшее значение из них за указанный период, предотвращая резкое удаление подов при кратковременном спаде нагрузки.

## Практические сценарии

HPA рекомендуется внедрять в следующих случаях:
- **Переменные нагрузки:** спрос колеблется в течение дня. HPA масштабирует вверх в пики и вниз в периоды затишья (снижение стоимости).
- **Непредсказуемый трафик:** адаптация к изменениям в реальном времени без ручного вмешательства.
- **Событийное масштабирование:** реакция на бизнес-метрики (например, глубина очереди в брокере сообщений).

Настройка HPA требует наличия установленных `resources.requests` у контейнеров в манифесте пода (для масштабирования по CPU/Memory) и корректно настроенного источника метрик. Если `requests` не заданы, HPA не сможет вычислить процент утилизации и поды не будут масштабироваться (статус `<unknown>`).

### Примеры использования

-   **По CPU/Memory:** базовый сценарий для веб-приложений (stateless).
-   **Внешние метрики:** автомасштабирование консьюмеров (воркеров) на основе длины очереди (Kafka, RabbitMQ) через адаптеры (например, KEDA).

## Дополнительная информация

### Преимущества и Ограничения

- **Оптимизация ресурсов:** поддержание баланса между производительностью и стоимостью. Вы платите только за те ресурсы, которые нужны.
- **Ограничение `minReplicas`:** HPA сам по себе не масштабирует ресурсы ниже `minReplicas` (не поддерживает scale-to-zero). Для масштабирования до нуля требуется **KEDA**.
- **Конфликт с VPA:** HPA по CPU/Memory конфликтует с Vertical Pod Autoscaler (VPA) в активных режимах. Их совместное использование допускается только при разнесении метрик (например, HPA по кастомной метрике, VPA по CPU/Mem).
- **Неподдерживаемые объекты:** HPA не используется для `DaemonSet` (по одному поду на узел) и обычно не применяется к `Job`/`CronJob`.

### Диагностика и мониторинг

Для проверки состояния HPA используйте:
- `kubectl get hpa` — быстрый просмотр текущих метрик и количества реплик. Если в колонке TARGETS указано `<unknown>`, это говорит об ошибке сбора метрик.
- `kubectl describe hpa <name>` — просмотр событий (Events) и причин последнего масштабирования.

### Советы для собеседования

**Вопрос:** Как работает HPA в Kubernetes?
**Ответ:** HPA — это контроллер (control loop), который отслеживает метрики (например, использование CPU или памяти) и автоматически увеличивает или уменьшает количество реплик Pod в Deployment, ReplicaSet или StatefulSet в соответствии с текущим спросом и заданными порогами (target utilization), используя расчет по формуле и учитывая окно стабилизации для избежания дребезга.

**Вопрос:** Можно ли масштабировать поды на основе размера очереди (например, RabbitMQ)?
**Ответ:** Да. Это можно сделать двумя способами:
1. **Custom/External Metrics:** используя адаптер метрик, который экспортирует данные из системы очередей в Metrics API Kubernetes.
2. **KEDA (Kubernetes Event-driven Autoscaling):** это проект CNCF, устанавливающий оператор, который сам собирает метрики (более 50+ скалеров) и транслирует их в HPA. Это рекомендуемый современный подход, поддерживающий масштабирование в ноль.
