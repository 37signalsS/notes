# Let's Encrypt: Углублённые концепции ACME

## Определения

**ACME (Automated Certificate Management Environment)** — протокол (RFC 8555), обеспечивающий полностью автоматизированное взаимодействие между клиентом (cert-manager) и центром сертификации (Let's Encrypt) для управления жизненным циклом TLS-сертификатов.

**JWS (JSON Web Signature)** — стандарт (RFC 7515), используемый в ACME для обеспечения аутентификации, целостности и защиты от повторов (anti-replay) всех сообщений между клиентом и сервером.

**Certificate Transparency (CT)** — открытый стандарт мониторинга цифровых сертификатов. С 2026 года публикация пре-сертификатов становится обязательным мандатом для признания доверия в современных браузерах.

**ARI (ACME Renewal Information)** — расширение протокола (RFC 9773), позволяющее CA динамически управлять окном продления сертификатов на стороне клиента.

## Основные концепции

### Механизмы безопасности ACME и JWS

ACME использует асимметричное шифрование и JWS для каждой операции. 

| Компонент | Техническая роль | Специфика ACME |
| :--- | :--- | :--- |
| **Account Key** | Идентификация клиента | ECDSA P-256 или RSA 3072+. Подписывает все API-запросы. |
| **Replay-Nonce** | Защита от повторных атак | Передается в HTTP-заголовке и встраивается в `protected` заголовок JWS. |
| **Account URL** | Уникальный ID аккаунта | Используется вместо передачи публичного ключа в каждом запросе после регистрации. |

**Важно:** ACME требует использования **JSON Serialization** для JWS (RFC 7515, Section 3.2), а не более привычной компактной записи (Base64-цепочка через точки).

### Иерархия и цепочки доверия (Preferred Chain)

В 2025–2026 годах Let's Encrypt использует иерархию **Generation X** (Intermediates R10-R14 для RSA и E5-E9 для ECDSA), подписанную **ISRG Root X1**.

В Kubernetes с помощью cert-manager можно управлять выбором цепочки через параметр `preferredChain`.

| Сценарий | Настройка | Цель |
| :--- | :--- | :--- |
| **Стандарт (ISRG X1)** | `preferredChain: "ISRG Root X1"` | Современная иерархия, по умолчанию. |
| **Старые Android (DST)** | `preferredChain: "DST Root CA X3"` | Использовалось для совместимости (срок истекает). |
| **Переход на Gen Y** | `preferredChain: "ISRG Root X2"` | Подготовка к использованию только ECDSA-цепочек. |

### Мандаты 2026: CT и EKU Split

Экосистема WebPKI в 2026 году претерпевает фундаментальные изменения:

1.  **Обязательный Pre-issuance CT**: С 15 июня 2026 года пре-сертификаты должны быть залогированы *до* выдачи финального сертификата. Без SCT (Signed Certificate Timestamp) браузеры Chrome/Safari заблокируют доступ без возможности обхода.
2.  **Разделение EKU (Extended Key Usage)**: Публичные сертификаты больше не могут быть одновременно `serverAuth` и `clientAuth`. Для mTLS необходимо использовать внутренние PKI (Vault, Step-CA).
3.  **Shorter Lifetimes**: Переход на 45-дневный цикл ротации становится стандартом. Let's Encrypt ARI является основным механизмом для реализации этой частоты без риска простоев.

## Практические сценарии

### Настройка Preferred Chain в Kubernetes

Если ваш стек требует специфический корень (например, для легаси-клиентов), укажите это в `Certificate`:

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: api-tls
spec:
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  commonName: api.example.com
  # Выбор конкретной цепочки доверия
  issuerOptions:
    preferredChain: "ISRG Root X1"
```

### Проверка Nonce и JWS-сообщений

Для глубокой отладки взаимодействия (например, ошибки `badNonce`) можно использовать `curl` для получения свежего nonce:

```bash
# Получение нового nonce от API Let's Encrypt
curl -I https://acme-v02.api.letsencrypt.org/new-nonce | grep -i "Replay-Nonce"
# → Replay-Nonce: 0102AbCd...
```

### Мониторинг CT-логов (2026)

Убедитесь, что ваши сертификаты содержат необходимые SCT:

```bash
# Проверка расширения SCT в сертификате
openssl x509 -in cert.pem -text -noout | grep -A 5 "CT Precertificate SCTs"
```

## Дополнительная информация

### Архитектура ISRG Root X2 и ECDSA

Let's Encrypt активно продвигает переход на ECDSA (E5/E6), так как эти сертификаты меньше по размеру и быстрее обрабатываются на мобильных устройствах. Однако они все еще кросс-подписаны RSA-корнем ISRG X1 для совместимости.
