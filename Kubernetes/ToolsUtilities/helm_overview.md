# Helm: пакетный менеджер для Kubernetes

### Предпосылки создания Helm: проблема 배포 и темплейтизации

Когда количество манифестов для одного приложения становится большим, управлять ими вручную становится проблематично. Возникает необходимость в **темплейтизации** — процессе, который позволяет использовать переменные и шаблоны для генерации конечных манифестов. Это решает проблему повторяющихся полей (например, `selector` и `labels`) и упрощает управление конфигурациями для разных окружений.

#### Альтернативные подходы и их недостатки

Существует несколько способов реализовать темплейтизацию:

1.  **Простые утилиты (`sed`, `envsubst`):** Позволяют заменять плейсхолдеры в файлах на значения переменных окружения. Это простой, но ограниченный метод, который не справляется со сложной логикой.

2.  **Системы управления конфигурациями (`Ansible`):** Предоставляют мощные шаблонизаторы (например, Jinja2) и встроенные модули для работы с Kubernetes. Это надежное решение, но оно, как и многие другие, является **`kubectl-based`**. Это означает, что инструмент генерирует YAML-файлы и последовательно применяет их через `kubectl`.

3.  **Специализированные инструменты (`kustomize`, `jsonnet`):** Предлагают более структурированные подходы к управлению конфигурациями.

Основной недостаток всех `kubectl-based` подходов — **проблема атомарного отката**. Стандартная команда `kubectl rollout undo` работает только для `Deployment`. Если в рамках одного релиза были изменены другие ресурсы (`Service`, `Ingress`, `ConfigMap`), их придется откатывать вручную, что сложно и чревато ошибками.

#### Путь к решению: версионирование релизов

Чтобы решить проблему отката, можно реализовать следующую стратегию:

1.  **Сохранять отрендеренные манифесты:** После генерации всех YAML-файлов для конкретной версии приложения, их можно сохранить как единый артефакт.
2.  **Версионировать артефакты:** Каждому такому набору присваивается версия (v1, v2, v3).
3.  **Хранить артефакты:** Их можно хранить во внешнем хранилище (например, Artifactory) или прямо в кластере Kubernetes.

При хранении в кластере можно использовать `ConfigMap`. Однако, `ConfigMap` имеет ограничение по размеру. Чтобы обойти его, можно сжать все манифесты в `zip-архив`, закодировать его в `base64` и сохранить полученную строку в `ConfigMap`.

**Именно эта концепция и легла в основу Helm.**

Helm автоматизирует весь этот процесс: он темплейтизирует манифесты, создает версионированные релизы и управляет их жизненным циклом. В качестве хранилища для информации о релизах Helm версии 3 использует `Secrets`, что является более безопасным решением, чем `ConfigMap`. Таким образом, Helm — это не просто шаблонизатор, а полноценная система управления релизами приложений в Kubernetes.

### Структура Helm-чарта

В контексте Helm, пакеты называются **чартами** (Charts). Чарт — это архив в формате `.tgz`, который содержит все необходимое для развертывания приложения в Kubernetes.

Структура чарта стандартизирована и включает в себя следующие обязательные элементы:

*   **`Chart.yaml`**: Файл с метаданными о чарте.
    *   `apiVersion`: Версия API чарта (обязательно).
    *   `name`: Имя чарта (обязательно).
    *   `version`: Версия самого чарта (обязательно, следует семантическому версионированию).
    *   `appVersion`: Версия приложения, которое разворачивается этим чартом.
    *   `description`: Краткое описание чарта.
    *   `maintainers`: Список ответственных за чарт.

*   **`values.yaml`**: Файл со значениями по умолчанию для переменных, используемых в шаблонах. Это позволяет легко настраивать чарт без изменения его шаблонов.

*   **`templates/`**: Директория, в которой хранятся все темплейтизированные манифесты Kubernetes (например, `deployment.yaml`, `service.yaml`, `ingress.yaml`).

*   **`charts/`**: Директория для зависимостей — других чартов, от которых зависит текущий чарт.

### Темплейтизация манифестов

Одной из ключевых возможностей Helm является использование шаблонов для генерации манифестов. Это позволяет избежать дублирования и упростить управление конфигурациями.

В качестве языка шаблонов Helm использует **Go template engine**.

Рассмотрим на примере простого `deployment.yaml`:

**До темплейтизации:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
  labels:
    app: nginx
spec:
  replicas: 3
  selector:
    matchLabels:
      app: nginx
  template:
    metadata:
      labels:
        app: nginx
    spec:
      containers:
      - name: nginx
        image: "nginx:1.14.2"
        ports:
        - containerPort: 80
```

В этом файле много жестко заданных значений, которые могут меняться: версия `image`, количество `replicas`, `labels`.

**После темплейтизации:**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: {{ .Release.Name }}-deployment
  labels:
    app: {{ .Chart.Name }}
spec:
  replicas: {{ .Values.replicaCount }}
  selector:
    matchLabels:
      app: {{ .Chart.Name }}
  template:
    metadata:
      labels:
        app: {{ .Chart.Name }}
    spec:
      containers:
      - name: {{ .Chart.Name }}
        image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"
        ports:
        - containerPort: {{ .Values.service.port }}
```

Теперь значения подставляются из разных источников:

*   `{{ .Values.replicaCount }}`: Из файла `values.yaml`.
*   `{{ .Release.Name }}`: Из данных о самом релизе (имя, которое вы даете при установке).
*   `{{ .Chart.Name }}`: Из метаданных чарта (`Chart.yaml`).

Соответствующий `values.yaml` может выглядеть так:

```yaml
replicaCount: 2

image:
  repository: nginx
  tag: stable

service:
  port: 80
```

При установке чарта Helm "рендерит" шаблоны, подставляя в них значения из `values.yaml` и встроенных объектов (`.Release`, `.Chart`), и генерирует итоговые манифесты, которые отправляются в Kubernetes API.

### Продвинутое шаблонизирование: функции и управление потоком

Хотя базовой подстановки значений (`{{ .Values.someValue }}`) достаточно для простых случаев, реальная мощь шаблонизатора Go раскрывается через использование функций, управляющих конструкций и встроенных объектов. Рассмотрим продвинутые приемы на примере создания чарта с нуля.

#### Пример: `values.yaml`

Создадим `values.yaml` с более сложной структурой, включающей вложенные объекты и списки:

```yaml
# values.yaml
replicas: 2

image:
  name: nginx
  tag: "1.12"

port: 80

# Блок для вставки "как есть"
resources:
  limits:
    cpu: 100m
    memory: 128Mi
  requests:
    cpu: 100m
    memory: 128Mi

# Список для итерации
env:
  - name: VAR1
    value: "value1"
  - name: VAR2
    value: "value2"

# Объект для условного включения
annotations:
  prometheus.io/scrape: "true"
  prometheus.io/port: "80"
```

#### Условное включение секций: `if`

Часто бывает необходимо включать определенные секции манифеста только при выполнении условия (например, если в `values.yaml` определен соответствующий блок). Для этого используется конструкция `if`.

**Задача:** Добавить блок `annotations` в метаданные пода, только если он определен в `values.yaml`.

```yaml
template:
  metadata:
    {{- if .Values.annotations }}
    annotations:
      {{- toYaml .Values.annotations | nindent 6 }}
    {{- end }}
```

*   `{{- if .Values.annotations }}`: Проверяет наличие объекта `annotations` в `values`.
*   `{{- toYaml .Values.annotations }}`: Функция `toYaml` сериализует объект `annotations` обратно в формат YAML. Это позволяет вставлять целые структуры, а не отдельные значения.
*   `| nindent 6`: Функция `nindent` (newline indent) добавляет перенос строки и ставит 6 пробелов перед каждой строкой, обеспечивая корректную вложенность YAML.
*   `{{- end }}`: Закрывает блок `if`.
*   Дефисы (`-`) по краям (`{{- ... -}}`) используются для **удаления пробельных символов** (включая переносы строк) до или после тега, что помогает форматировать итоговый YAML и избегать пустых строк.

#### Итерация по спискам: `range`

Для генерации повторяющихся блоков, таких как переменные окружения или монтирование томов, используется оператор `range`.

**Задача:** Сгенерировать переменные окружения для контейнера на основе списка `env` из `values.yaml`.

```yaml
spec:
  containers:
    - name: {{ .Chart.Name }}
      {{- if .Values.env }}
      env:
        {{- range .Values.env }}
        - name: {{ .name | quote }}
          value: {{ .value | quote }}
        {{- end }}
      {{- end }}
```

*   `{{- range .Values.env }}`: Запускает цикл, который итерируется по каждому элементу списка `.Values.env`. Внутри цикла контекст (`.`) меняется на текущий элемент списка (например, на `{"name": "VAR1", "value": "value1"}`).
*   `{{ .name | quote }}`: Обращается к полю `name` текущего элемента и заключает его значение в кавычки с помощью функции `quote`. Это предотвращает проблемы, если значение является числом или булевым типом, которые YAML может интерпретировать не как строку.

#### Локальная отладка: `helm template`

Перед установкой чарта крайне полезно проверить, как будут выглядеть итоговые манифесты. Команда `helm template` рендерит чарт локально и выводит результат в `stdout`, не отправляя ничего в кластер.

```bash
# helm template [RELEASE_NAME] [CHART_PATH]

# Рендерим чарт в текущей директории с именем релиза "my-app"
helm template my-app .
```

Эта команда — основной инструмент для отладки шаблонов. Рассмотрим типичные проблемы и их решения.

**Проблема 1: Неправильные отступы**

YAML чувствителен к отступам. Если при вставке блока через `toYaml` не указать правильный отступ, валидация манифеста провалится.

*   **Шаблон:**

    ```yaml
    spec:
      containers:
      - name: {{ .Chart.Name }}
        resources:
    {{ toYaml .Values.resources }}
    ```

*   **Результат рендеринга (неверный):**

    ```yaml
    spec:
      containers:
      - name: my-chart
        resources:
    limits:
      cpu: 100m
      memory: 128Mi
    requests:
      cpu: 100m
      memory: 128Mi
    ```

    Здесь блок `limits` находится на том же уровне, что и `spec`, что является ошибкой.

*   **Решение:** Использовать функцию `nindent` (или `indent`) для добавления нужного количества пробелов.

    ```yaml
    spec:
      containers:
      - name: {{ .Chart.Name }}
        resources:
    {{- toYaml .Values.resources | nindent 10 }}
    ```

*   **Результат рендеринга (верный):**

    ```yaml
    spec:
      containers:
      - name: my-chart
        resources:
          limits:
            cpu: 100m
            memory: 128Mi
          requests:
            cpu: 100m
            memory: 128Mi
    ```

**Проблема 2: Лишние пустые строки**

Управляющие конструкции Go (`if`, `range`) могут оставлять пустые строки в отрендеренном YAML, что делает его неопрятным.

*   **Шаблон:**

    ```yaml
      env:
        {{ if .Values.env }}
        {{ range .Values.env }}
        - name: {{ .name | quote }}
          value: {{ .value | quote }}
        {{ end }}
        {{ end }}
    ```

*   **Результат рендеринга (неопрятный):**

    ```yaml
      env:
        
        - name: "VAR1"
          value: "value1"
        
        - name: "VAR2"
          value: "value2"
    ```

*   **Решение:** Использовать дефисы `{-` и `-}` для удаления пробелов и переносов строк до и после тега.

    ```yaml
      env:
        {{- if .Values.env }}
        {{- range .Values.env }}
        - name: {{ .name | quote }}
          value: {{ .value | quote }}
        {{- end }}
        {{- end }}
    ```

*   **Результат рендеринга (чистый):**

    ```yaml
      env:
        - name: "VAR1"
          value: "value1"
        - name: "VAR2"
          value: "value2"
    ```

#### Стартовые чарты: `helm create`

Чтобы не создавать всю структуру чарта вручную, можно использовать команду `helm create`, которая генерирует стандартный шаблонный чарт со всеми необходимыми файлами и директориями.

```bash
helm create my-new-chart
```

Эта команда создаст директорию `my-new-chart` с готовым к работе чартом, включающим `Deployment`, `Service`, `Ingress`, `HPA`, тесты и хорошо структурированный `values.yaml`. Это отличная отправная точка для большинства приложений. Вы можете кастомизировать этот "стартер" под нужды вашей компании и распространять его среди разработчиков для унификации процесса развертывания.

### Основные команды и рабочий процесс: пошаговое руководство

Helm предоставляет набор команд для управления жизненным циклом приложений. Рассмотрим полный цикл на практическом примере установки утилиты `kube-ops-view`.

#### Шаг 1: Управление репозиториями
Репозиторий Helm — это HTTP-сервер, на котором хранятся упакованные чарты. Прежде чем что-то установить, нужно подключить репозиторий и обновить локальный кэш.

*   **Добавить репозиторий:**

    ```bash
    # helm repo add [NAME] [URL]
    # Добавим официальный репозиторий, который был популярен ранее (сейчас в статусе deprecated)
    helm repo add stable https://charts.helm.sh/stable
    ```

*   **Обновить информацию о чартах из всех репозиториев:**

    ```bash
    helm repo update
    ```

    Эту команду необходимо выполнять регулярно, чтобы получать последние версии чартов.

#### Шаг 2: Поиск чарта
Для поиска доступных пакетов (чартов) используется команда `helm search`.

*   **Найти чарт в Artifact Hub (глобальный поиск):**

    Artifact Hub — это централизованный реестр для поиска CNCF-пакетов. Это предпочтительный способ поиска.

    ```bash
    # helm search hub [KEYWORD]
    helm search hub kube-ops-view
    ```

*   **Найти чарт в подключенных репозиториях (локальный поиск):**

    ```bash
    # helm search repo [KEYWORD]
    helm search repo kube-ops-view
    ```

#### Шаг 3: Подготовка к установке

Перед установкой чарта необходимо изучить его настраиваемые параметры (`values`).

*   **Просмотреть значения по умолчанию:**

    Эта команда выведет стандартный `values.yaml` для чарта.

    ```bash
    # helm show values [CHART]
    helm show values stable/kube-ops-view
    ```

*   **Сохранить `values.yaml` для кастомизации:**

    Лучшей практикой является сохранение `values` в локальный файл для дальнейшего редактирования и версионирования.

    ```bash
    helm show values stable/kube-ops-view > values.yaml
    ```

    После этого откройте `values.yaml` и настройте его под свои нужды. Например, для `kube-ops-view` может потребоваться включить Ingress и RBAC:

    ```yaml
    # values.yaml
    ingress:
      enabled: true
      hostname: kube-ops-view.my-cluster.com
    
    rbac:
      create: true
    ```

#### Шаг 4: Установка и управление релизом

Процесс установки чарта называется созданием **релиза** (release). Релиз — это конкретный экземпляр чарта, развернутый в кластере.

*   **Установить чарт:**

    ```bash
    # helm install [RELEASE_NAME] [CHART] -n [NAMESPACE] -f [VALUES_FILE]
    helm install ops-view stable/kube-ops-view --namespace kube-system -f values.yaml
    ```

    *   `ops-view`: Имя релиза. Вы можете выбрать любое.
    *   `stable/kube-ops-view`: Имя чарта.
    *   `--namespace kube-system`: Целевое пространство имен.
    *   `-f values.yaml`: Файл с вашими кастомными значениями.

#### Идемпотентное развертывание: `upgrade --install`

На практике вместо `helm install` часто используется команда `helm upgrade --install`. Она является **идемпотентной**:

*   Если релиз с таким именем еще не существует, он будет установлен (аналогично `install`).
*   Если релиз уже существует, он будет обновлен (аналогично `upgrade`).

Это делает ее идеальной для использования в CI/CD пайплайнах, так как один и тот же шаг может использоваться и для первоначального развертывания, и для последующих обновлений.

```bash
helm upgrade --install ops-view stable/kube-ops-view -f values.yaml
```

#### Практический пример: `--atomic` и `--timeout` при сбое

Рассмотрим, как флаги `--atomic` и `--timeout` защищают от сбоев на реальном примере.

**Сценарий:** В `values.yaml` мы случайно указали несуществующий тег для образа приложения.

1.  **Запуск развертывания:**

    ```bash
    helm upgrade --install my-app ./my-chart \
      --atomic \
      --timeout 30s
    ```

2.  **Что происходит в кластере:**

    *   Helm создает новый `ReplicaSet`.
    *   Kubernetes пытается скачать образ с несуществующим тегом.
    *   Поды переходят в состояние `ImagePullBackOff` или `ErrImagePull`, так как образ не может быть загружен.
3.  **Действия Helm:**

    *   Helm ожидает 30 секунд (согласно `--timeout`), пока ресурсы не перейдут в состояние готовности.
    *   Поскольку поды не могут запуститься, таймаут истекает, и Helm фиксирует неудачное обновление.
    *   Благодаря флагу `--atomic`, Helm немедленно выполняет `helm rollback` к предыдущей успешной ревизии.
4.  **Результат:**

    *   Команда завершается с ошибкой, CI/CD пайплайн "краснеет".
    *   В кластере остается работать предыдущая стабильная версия приложения. Простоя не происходит.

*   **Посмотреть список установленных релизов:**

    ```bash
    # helm list -n [NAMESPACE]
    helm list -n kube-system
    ```

*   **Проверить статус релиза:**

    ```bash
    # helm status [RELEASE_NAME] -n [NAMESPACE]
    helm status ops-view -n kube-system
    ```

#### Шаг 5: Обновление и откат

*   **Обновить релиз:**

    Если вы изменили `values.yaml` или хотите обновить версию чарта, используйте `helm upgrade`.

    ```bash
    helm upgrade ops-view stable/kube-ops-view -f values.yaml
    ```

    Перед обновлением крайне рекомендуется использовать плагин `helm-diff` для просмотра изменений.

*   **Откатить релиз:**

    Если обновление прошло неудачно, можно откатиться к предыдущей стабильной версии.

    ```bash
    # helm rollback [RELEASE_NAME] [REVISION]
    helm rollback ops-view 1 
    ```

#### Шаг 6: Удаление релиза

*   **Удалить релиз и все связанные с ним ресурсы:**

    ```bash
    # helm delete [RELEASE_NAME] -n [NAMESPACE]
    helm delete ops-view -n kube-system
    ```

    Рекомендуется удалять приложения, установленные с помощью Helm, именно через `helm delete`, а не `kubectl delete`, чтобы гарантировать удаление всех ресурсов, включая те, что находятся вне пространства имен релиза (например, `ClusterRole`).

### Инспектирование локального чарта

Иногда полезно не устанавливать чарт, а просто скачать его и изучить структуру.

*   **Скачать и распаковать чарт:**

    Команда `helm pull` скачивает архив `.tgz` чарта из репозитория. Флаг `--untar` позволяет сразу же его распаковать.

    ```bash
    helm pull stable/kube-ops-view --untar
    ```

    После выполнения этой команды в текущей директории появится папка `kube-ops-view`, в которой можно найти `Chart.yaml`, `values.yaml` и директорию `templates` со всеми шаблонами. Это лучший способ понять, как устроен тот или иной чарт.

### Ключевые преимущества Helm

Помимо решения проблемы темплейтизации и управления релизами, Helm обладает рядом других преимуществ, которые делают его стандартом де-факто для развертывания приложений в Kubernetes.

1.  **Шаблонизация и переиспользуемость:** Helm использует движок шаблонов Go, позволяя создавать гибкие и переиспользуемые манифесты. Один и тот же чарт можно легко развертывать на разные окружения (dev, staging, prod), просто передавая разные файлы с переменными (`values.yaml`).

2.  **Версионирование и управляемые релизы:** Helm упаковывает сложные наборы YAML-файлов в единую сущность — **чарт**, который можно версионировать. Это обеспечивает более контролируемую работу с инфраструктурой и позволяет легко обновлять или откатываться к предыдущим стабильным версиям конфигураций.

3.  **Управление зависимостями:** Чарт может зависеть от других чартов (например, ваше приложение зависит от базы данных PostgreSQL). Helm позволяет объявить эти зависимости в файле `Chart.yaml` или `requirements.yaml` и автоматически управляет их установкой и обновлением с помощью команды `helm dependency update`.

*   **[Helm Best Practices](./helm_best_practices.md)**: Дополнительные рекомендации по использованию Helm, включая управление подичартами, образами и развертыванием в разных средах.

4.  **Надежные развертывания и атомарные откаты:** Helm предоставляет мощные механизмы для CI/CD:
    *   **`--wait`:** Флаг, который заставляет Helm дожидаться, пока все ресурсы релиза перейдут в состояние готовности.
    *   **`--atomic`:** Флаг, который гарантирует, что в случае неудачного развертывания релиз будет автоматически откачен к предыдущей успешной версии.

5.  **Архитектура без Tiller (Helm 3):** В ранних версиях Helm использовал серверный компонент `Tiller`, создававший риски для безопасности. Начиная с **Helm 3**, `Tiller` был полностью удален. Теперь Helm — это исключительно клиентский инструмент, который использует стандартный `kubeconfig` и настройки RBAC, что делает его гораздо более безопасным.

6.  **Хуки и тестирование:** Helm предоставляет "хуки" для выполнения действий на разных этапах жизненного цикла релиза (например, миграция БД перед обновлением) и встроенный механизм тестирования (`helm test`) для проверки корректности развертывания.

7.  **Проект CNCF:** Helm является выпускником (graduated) `Cloud Native Computing Foundation` (CNCF), той же организации, что и Kubernetes. Это гарантирует высокий уровень поддержки и развития.

8.  **Система плагинов:** Функциональность Helm можно расширять с помощью плагинов. Некоторые из наиболее полезных:
    *   **`helm-diff`:** Показывает изменения, которые будут применены к кластеру.
    *   **`helm 2to3`:** Помогает мигрировать релизы со второй версии Helm на третью.
    *   **`helm-monitor`:** Позволяет интегрировать кастомные проверки в процесс выкатки релиза.

### Атомарный откат при сбое: практический пример

Теоретическое описание флага `--atomic` не полностью передает его пользу. Рассмотрим реальный сценарий, демонстрирующий, как Helm обеспечивает отказоустойчивость развертывания.

**Сценарий:** Мы намеренно "ломаем" приложение, указывая неверный адрес базы данных, и запускаем обновление релиза с флагом `--atomic`.

**Шаг 1: Внесение неисправности**

В файле `values.yaml` изменяется параметр, отвечающий за хост подключения к базе данных, на заведомо несуществующий.

```yaml
# values.yaml
database:
  host: postgresql-host-v1fis1 # Несуществующий хост
```

**Шаг 2: Запуск обновления**

Выполняется команда `helm upgrade` с флагом `--atomic`.

```bash
helm upgrade my-app ./my-chart --atomic
```

**Шаг 3: Наблюдение в кластере**

1.  Kubernetes пытается развернуть новую версию приложения. Создается новый `ReplicaSet` и запускаются новые поды.
2.  При старте поды не могут подключиться к базе данных и начинают падать с ошибкой (например, `CrashLoopBackOff`). Это можно увидеть в логах пода: `kubectl logs <new-pod-name>`.
3.  Helm, благодаря флагу `--wait`, ожидает, пока все ресурсы нового релиза перейдут в состояние `Ready`. Поскольку новые поды не могут стабилизироваться, Helm не считает обновление успешным.

**Шаг 4: Автоматический откат**

1.  По истечении таймаута Helm фиксирует неудачное обновление.
2.  Благодаря флагу `--atomic`, Helm немедленно инициирует `helm rollback` к предыдущей, стабильной ревизии.
3.  Новые, неработоспособные поды и соответствующий `ReplicaSet` удаляются.
4.  Старые, рабочие поды, которые обслуживали трафик все это время, остаются нетронутыми.

**Итог:**

*   **Для пользователя:** Весь процесс проходит абсолютно прозрачно. Работоспособность приложения не нарушается ни на секунду, так как трафик не переключался на нерабочие экземпляры.
*   **Для CI/CD:** Пайплайн развертывания завершится с ошибкой (exit code 1), сигнализируя о проблеме. Однако в кластере останется развернутой последняя стабильная версия приложения.

Этот механизм превращает Helm из простого шаблонизатора в мощный инструмент для надежного управления жизненным циклом приложений, защищая производственные среды от сбоев во время обновлений.

### `helm-diff`: предпросмотр изменений

**`helm-diff`** — это незаменимый плагин, который показывает `diff` изменений перед выполнением `helm upgrade`. Он наглядно демонстрирует, что именно будет добавлено, изменено или удалено в ваших Kubernetes-ресурсах, предотвращая случайные или некорректные обновления.

**Ключевые возможности:**

*   **Предпросмотр обновлений:** Основная функция, показывает `diff` между текущим состоянием и тем, что будет после `helm upgrade`.
*   **Сравнение ревизий:** Позволяет сравнить две любые ревизии релиза.
*   **Анализ отката:** Показывает, что изменится при выполнении `helm rollback`.

Плагин устанавливается одной командой:

```bash
helm plugin install https://github.com/databus23/helm-diff
```

После установки плагина у вас появится новая подкоманда `helm diff`.

**Показать `diff` для `helm upgrade`:**

```bash
# Сравнить текущий релиз с изменениями из локального чарта
helm diff upgrade my-release ./my-chart

# Можно использовать те же флаги, что и для `helm upgrade`, например, для передачи values
helm diff upgrade my-release ./my-chart -f values.yaml
```

**Сравнить две ревизии релиза:**

```bash
# Показать разницу между 1-й и 2-й ревизией
helm diff revision my-release 1 2
```

**Показать `diff` для `helm rollback`:**
```bash
# Показать, что изменится, если откатиться к ревизии 1
helm diff rollback my-release 1
```

Интеграция `helm-diff` в CI/CD пайплайны является лучшей практикой, так как позволяет команде ревьюить изменения в инфраструктуре так же, как они ревьюят код.

### Тестирование релиза (helm test)

Helm предоставляет встроенный механизм для тестирования развернутого релиза. Это позволяет убедиться, что приложение не только установилось, но и функционирует корректно.

**Принцип работы:**

1.  **Создание тестовых манифестов:** В директории `templates/` вашего чарта создается поддиректория `tests/`.
2.  **Размещение тестов:** Внутрь `templates/tests/` помещаются манифесты Kubernetes, которые выполняют проверку. Как правило, это `Pod` или `Job`, которые запускают тестовый контейнер.
3.  **Аннотация для тестов:** Ключевым моментом является добавление аннотации `helm.sh/hook: test` в метаданные тестовых ресурсов. Эта аннотация сообщает Helm, что данный манифест является тестом и его не нужно включать в основной релиз.
4.  **Запуск тестов:** После установки или обновления релиза, тесты запускаются командой `helm test <release_name>`.

Helm будет следить за статусом тестовых подов. Если под завершается с кодом `0`, тест считается успешным. Если с ненулевым кодом — проваленным.

**Пример тестового манифеста (`templates/tests/test-connection.yaml`):**

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: "{{ .Release.Name }}-connection-test"
  annotations:
    "helm.sh/hook": test
spec:
  containers:
    - name: wget
      image: busybox
      command: ['wget']
      args: ['{{ .Release.Name }}-my-service:{{ .Values.service.port }}']
  restartPolicy: Never
```

Этот под пытается выполнить `wget` к сервису, созданному в рамках релиза. Если сервис доступен, команда завершится успешно.

### Хуки (Hooks)

Хуки — это механизм, позволяющий выполнять определенные действия на разных этапах жизненного цикла релиза. Это могут быть `Job` для миграции базы данных перед обновлением приложения, `Pod` для выполнения резервного копирования перед удалением релиза или любые другие манифесты Kubernetes.

Ресурс становится хуком, если в его метаданные добавлена аннотация `helm.sh/hook`.

**Доступные хуки:**

*   `pre-install`: Выполняется перед тем, как в кластер будут загружены какие-либо ресурсы релиза.
*   `post-install`: Выполняется после того, как все ресурсы релиза были установлены.
*   `pre-delete`: Выполняется перед удалением ресурсов релиза.
*   `post-delete`: Выполняется после того, как все ресурсы релиза были удалены.
*   `pre-upgrade`: Выполняется перед обновлением релиза.
*   `post-upgrade`: Выполняется после того, как релиз был обновлен.
*   `pre-rollback`: Выполняется перед откатом релиза.
*   `post-rollback`: Выполняется после отката релиза.

**Управление хуками:**

*   **Вес хука (`helm.sh/hook-weight`):** Если для одного и того же этапа (например, `pre-install`) определено несколько хуков, их можно упорядочить с помощью веса. Хуки выполняются в порядке возрастания их веса (отрицательные значения разрешены).
*   **Политика удаления (`helm.sh/hook-delete-policy`):** Хуки не являются частью самого релиза и не удаляются автоматически вместе с ним (если только они не попали под `helm delete`). Аннотация `helm.sh/hook-delete-policy` позволяет управлять их удалением.
    *   `before-hook-creation`: Удаляет предыдущий хук перед запуском нового (поведение по умолчанию).
    *   `hook-succeeded`: Удаляет хук после его успешного завершения.
    *   `hook-failed`: Удаляет хук, если он завершился с ошибкой.

**Пример хука для `post-install`:**

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: "{{ .Release.Name }}-post-install-job"
  annotations:
    "helm.sh/hook": post-install
    "helm.sh/hook-weight": "-5"
    "helm.sh/hook-delete-policy": hook-succeeded
spec:
  template:
    spec:
      containers:
        - name: post-install-container
          image: alpine:3.3
          command: ["/bin/sleep", "{{ default "10" .Values.sleepyTime }}"]
      restartPolicy: Never
  backoffLimit: 4
```

### Создание собственного репозитория Helm

Хотя чарты можно хранить в системе контроля версий (например, Git), для централизованного распространения и управления версиями используются репозитории Helm.

Репозиторий Helm — это простой HTTP-сервер, который может отдавать файлы.

**Требования к серверу:**

1.  Сервер должен быть способен обслуживать файлы YAML и архивы `.tgz`.
2.  Сервер должен отвечать на GET-запросы.
3.  На сервере должен присутствовать специальный файл `index.yaml`, который содержит метаданные обо всех чартах в репозитории.

**Структура репозитория:**

Типичная структура директорий на сервере выглядит следующим образом:

```
https://example.com/charts/
├── index.yaml
├── alpine-0.1.2.tgz
└── alpine-0.1.2.tgz.prov (опциональный файл для проверки целостности)
```

*   `index.yaml`: Главный файл, описывающий содержимое репозитория.
*   `*.tgz`: Упакованные архивы чартов.

**Файл `index.yaml`:**

Этот файл генерируется автоматически командой `helm package --destination <path>` и `helm repo index <path>`. Он содержит информацию о каждом чарте, включая его имя, версию, описание и контрольную сумму.

**Пример содержимого `index.yaml`:**

```yaml
apiVersion: v1
entries:
  alpine:
  - apiVersion: v2
    appVersion: 1.0.0
    created: "2025-11-07T18:00:00.000000000Z"
    description: A basic Alpine Linux pod
    digest: 99c76e403d752c84ead610644d4b1c2f2b453a74b921f422b9dcb8a7c8b559cd
    name: alpine
    type: application
    urls:
    - https://example.com/charts/alpine-0.1.2.tgz
    version: 0.1.2
```

**Рабочий процесс:**

1.  **Упаковка чарта:** `helm package ./my-chart` -> создает `my-chart-0.1.0.tgz`.
2.  **Создание/обновление индекса:** `helm repo index . --url https://my-repo.com/charts` -> создает/обновляет `index.yaml`.
3.  **Загрузка на сервер:** Загрузить `*.tgz` и `index.yaml` на ваш HTTP-сервер.

### Структура проекта с Helm и Kustomize

На практике для управления сложными приложениями в разных средах часто используется гибридный подход, сочетающий сильные стороны Helm для шаблонизации и Kustomize для управления конфигурациями под конкретное окружение.

-   **Helm** используется для пакетирования приложения и управления его зависимостями.
*   **[Kustomize](../../ToolsUtilities/kustomize_overview.md)** позволяет "на лету" накладывать патчи на базовые манифесты, сгенерированные Helm, для каждой среды (`dev`, `staging`, `prod`).

Такая структура может выглядеть следующим образом:

```
k8s-project/
├── base/                   # Базовые манифесты, сгенерированные `helm template`
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── configmap.yaml
│   ├── ingress.yaml
│   └── kustomization.yaml    # Указывает на все ресурсы в base
│
├── overlays/               # Специфичные для окружений "наслоения"
│   ├── dev/
│   │   ├── kustomization.yaml  # Указывает на ../../base и применяет патчи
│   │   ├── namespace.yaml
│   │   ├── configmap-patch.yaml # Патч для ConfigMap (например, меняет URL базы данных)
│   │   └── ingress-patch.yaml   # Патч для Ingress (например, меняет домен)
│   │
│   ├── staging/
│   │   └── ...
│   └── prod/
│       └── ...
│
└── helm/                     # Исходный Helm-чарт приложения
    ├── Chart.yaml
    ├── values.yaml
    └── templates/
        └── ...
```

**Рабочий процесс:**

1.  **Генерация базы:** С помощью `helm template ./helm > ./base` генерируются "чистые" Kubernetes манифесты.
2.  **Применение Kustomize:** Для развертывания в `dev`-окружение используется команда `kubectl apply -k overlays/dev`. Kustomize берет базовые манифесты и применяет к ним патчи из `overlays/dev`.

Этот подход позволяет держать логику приложения в Helm-чарте, а все конфигурационные отличия между средами — в декларативных патчах Kustomize.
