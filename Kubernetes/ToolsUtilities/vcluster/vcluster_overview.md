# vCluster — обзор и архитектура

> Концептуальная база и архитектурный разбор виртуальных Kubernetes-кластеров vCluster. Документ служит точкой входа в предмет: содержит определения, описывает компоненты и их взаимодействие, сравнивает режимы развёртывания и фиксирует практические сценарии для DevOps/SRE/sysadmin. Детальные инструкции по установке, сетевой связности и безопасности вынесены в профильные файлы.

## Определения

**vCluster (Virtual Cluster)** — инструмент для создания легковесных виртуальных Kubernetes-кластеров. В классическом режиме работает внутри отдельного пространства имен (namespace) хостового кластера, имея собственный Control Plane (API Server, Controller Manager, Scheduler, etcd) и обеспечивая полную изоляцию от других vCluster.

**Host Cluster (Хост-кластер)** — основной Kubernetes-кластер, на котором разворачиваются и функционируют виртуальные кластеры (в классическом режиме).

**vCluster Syncer (Синхронизатор)** — ключевой компонент, отвечающий за синхронизацию ресурсов (Pods, Services, PVC) между виртуальным и хостовым окружением. Он имитирует наличие узлов (nodes) внутри vCluster, перенося фактическую нагрузку на узлы хост-кластера.

**vCluster Standalone** — режим работы (v0.29+), позволяющий запускать виртуальный кластер как независимый бинарный файл на Linux-хосте (VM или Bare Metal) без необходимости наличия хостового Kubernetes-кластера.

**Private Nodes** — функция, позволяющая выделять виртуальному кластеру выделенные физические узлы (dedicated nodes) для обеспечения максимальной изоляции и производительности (например, для GPU-нагрузок).

**Auto Nodes** — механизм динамического масштабирования узлов (на базе Karpenter) непосредственно внутри виртуального кластера, работающий прозрачно для тенанта.

**vcluster.yaml** — единый формат конфигурации (введен в v0.20+), заменяющий разрозненные Helm-значения и управляющий всеми аспектами жизненного цикла кластера.

**vind (vCluster in Docker)** — Open Source инструмент для запуска vCluster локально в контейнерах Docker (аналог `kind` для виртуальных кластеров).

**Sleep Mode (Режим сна)** — функция автоматической или ручной остановки vCluster. В режиме сна поды нагрузки масштабируются до нуля, а Control Plane переходит в режим ожидания, автоматически пробуждаясь (Auto-Wakeup) при первом обращении к API.

**Tenancy Spectrum (Спектр мультитенантности)** — концептуальная модель выбора между уровнями изоляции и стоимости инфраструктуры: от общих узлов до полностью выделенного оборудования.

**Resource Patching (Патчинг ресурсов)** — механизм модификации полей объектов Kubernetes "на лету" при пересечении границы vCluster ↔ host, реализуемый Syncer.

**Backing Store (Хранилище состояния)** — компонент, в котором виртуальный Control Plane хранит своё состояние (etcd, SQLite, внешняя БД).

## Основные концепции

### Архитектура системы

```text
┌─────────────────────────────────────────────────────────────────┐
│                      Host Cluster                                │
│  ┌─────────────────┐  ┌─────────────────┐  ┌─────────────────┐ │
│  │   Namespace A   │  │   Namespace B   │  │   Namespace C   │ │
│  │  ┌───────────┐  │  │  ┌───────────┐  │  │  ┌───────────┐  │ │
│  │  │ vCluster  │  │  │  │ vCluster  │  │  │  │ vCluster  │  │ │
│  │  │ Control   │  │  │  │ Control   │  │  │  │ Control   │  │ │
│  │  │ Plane     │  │  │  │ Plane     │  │  │  │ Plane     │  │ │
│  │  │ (pods)    │  │  │  │ (pods)    │  │  │  │ (pods)    │  │ │
│  └──┼─────┬─────┼──┘  └──┼─────┬─────┼──┘  └──┼─────┬─────┼──┘ │
│     │     │     │        │     │     │        │     │     │     │
│  ┌──▼─────▼─────▼──┐  ┌──▼─────▼─────▼──┐  ┌──▼─────▼─────▼──┐ │
│  │ Synced Pods     │  │ Synced Pods     │  │ Synced Pods     │ │
│  │ (Worker Nodes)  │  │ (Worker Nodes)  │  │ (Worker Nodes)  │ │
│  └─────────────────┘  └─────────────────┘  └─────────────────┘ │
└─────────────────────────────────────────────────────────────────┘
```

В этой схеме каждый vCluster живёт в своём namespace хост-кластера. Control Plane — это набор подов с собственным API Server и хранилищем. Syncer реплицирует workload-объекты (Pods, Services, PVC) в namespace хоста, где они фактически исполняются на worker-узлах. Таким образом vCluster не имеет собственных worker-узлов — он "арендует" их у хоста через механизм виртуальных нод.

### Как работает Syncer: виртуальные узлы и планирование

Ключевая идея vCluster в том, что внутри виртуального кластера пользователь видит обычные объекты Kubernetes, включая Nodes. Однако реальные узлы принадлежат хост-кластеру. Syncer решает это противоречие следующим образом:

1. **Фиктивные (виртуальные) ноды:** При запуске Syncer регистрирует в API Server vCluster один или несколько объектов `Node` (с метками, указывающими на хост). Эти ноды отражают ресурсы, доступные тенанту (CPU, RAM, GPU), а не реальные worker-узлы.
2. **Scheduler внутри vCluster:** При создании Pod пользователем vCluster-scheduler выбирает виртуальную ноду, ориентируясь на её ресурсы.
3. **Трансляция в хост:** Syncer перехватывает Pod, выполняет патчи (Resource Patching — например, переименование ServiceAccount, корректировка tolerations, замена imagePullSecrets) и создаёт "теневой" Pod в namespace хост-кластера с привязкой (`nodeName`) к реальному worker.
4. **Обратная связь:** Изменения статуса Pod (Running, Failed, IP) зеркалируются обратно в виртуальный кластер через `watch`-механизм.
5. **Очистка:** При удалении объекта в одной плоскости Syncer удаляет его парный объект в другой.

Так достигается иллюзия собственного кластера при фактическом использовании ресурсов хост-кластера. С точки зрения тенанта `kubectl get nodes -o wide` показывает "его" ноды, а `kubectl describe pod` — IP, выданный kubelet'ом хоста.

### Компоненты виртуального кластера

| Компонент | Описание |
| :--- | :--- |
| **Control Plane** | API Server, Controller Manager и хранилище. Может работать в Pod (Host-mode) или как процесс (Standalone). |
| **Syncer** | Обеспечивает двустороннюю синхронизацию объектов. Поддерживает патчи ресурсов (Resource Patching) "на лету". |
| **Backing Store** | Хранилище состояния: встроенные SQLite (K3s), etcd (K8s) или внешние БД (PostgreSQL/MySQL/TiDB). |
| **vCluster VPN** | Встроенный оверлей (Tailscale-powered) для безопасного соединения между Control Plane и удаленными узлами. |
| **CoreDNS** | Изолированное разрешение имен внутри vCluster, независимое от настроек хост-кластера. |
| **Gateway API** | Полная поддержка (v0.35+) для современного управления трафиком и маршрутизации. |

#### Backing Store: выбор хранилища

Backing Store определяет, где хранится состояние API Server виртуального кластера. От выбора зависят надёжность, размер и поведение при сбоях:

| Хранилище | Когда выбирать | Особенности |
| :--- | :--- | :--- |
| **SQLite (K3s)** | Dev, CI, ephemeral-окружения | Минимальный оверхед; один файл на PVC; не подходит для HA внутри vCluster. |
| **Embedded etcd (K3s)** | То же, но с поддержкой `--backend` kine etcd | Совместим с большинством операторов. |
| **etcd (Vanilla K8s)** | Продакшн, multi-writer контроллеры | Полная совместимость с GA-фичами; требует больше CPU/RAM. |
| **External PostgreSQL/MySQL** | Крупные инсталляции, корпоративные политики хранения | Масштабируется до терабайт; используется драйвером Kine. |
| **TiDB** | Распределённые сценарии, требования к отказоустойчивости | Поддержка транзакций, репликации. |

Для Bare-Metal/Edge-сценариев обычно выбирают SQLite (минимум зависимостей) или embedded etcd. Для критичных нагрузок с операторами, требующими multi-writer — external etcd/PostgreSQL.

### Спектр мультитенантности (Tenancy Spectrum)

vCluster к 2026 году предлагает гибкий выбор между уровнями изоляции и стоимостью:

1.  **Shared Nodes (Общие узлы):** Нагрузки виртуальных кластеров работают на общих узлах хост-кластера. Самый дешевый вариант (Dev/Test, CI/CD).
2.  **Auto Nodes (Авто-узлы):** Динамическое выделение узлов под нужды конкретного vCluster через Karpenter. Баланс гибкости и изоляции.
3.  **Private Nodes (Приватные узлы):** Полное выделение физического оборудования под vCluster. Максимальная безопасность и предсказуемость (AI, High Performance).
4.  **Standalone (Независимый):** Запуск без хост-кластера. Идеально для Edge-вычислений и Bare Metal сред.

#### Сравнение моделей изоляции: где находится vCluster в общей картине

| Модель | Уровень изоляции | API-сервер | CRD | Требования к ресурсам |
| :--- | :--- | :--- | :--- | :--- |
| **Namespace (soft tenancy)** | Логический | Общий | Общие | Минимальные |
| **Capsule** | Namespace + политики тенанта | Общий | Общие | Минимальные |
| **HNC (Hierarchical Namespaces)** | Иерархия namespace | Общий | Общие | Минимальные |
| **vCluster (virtual cluster)** | API + Control Plane | Собственный | Собственные | Средние |
| **Cluster API (отдельные кластеры)** | Полный физический | Собственный | Собственные | Высокие |
| **Выделенный bare-metal кластер** | Физический | Собственный | Собственные | Очень высокие |

vCluster занимает промежуточную нишу: дешевле полноценного кластера, но даёт собственные CRD и ClusterRoles.

### Дистрибутивы Control Plane

| Дистрибутив | Особенности | Рекомендуемое использование |
| :--- | :--- | :--- |
| **K3s** | SQLite/etcd, минимальный оверхед. | Разработка, CI/CD, Edge. |
| **Kubernetes (Vanilla)** | Полноценный etcd, поддержка всех GA-фич. | Продакшн, сложные операторы. |
| **K0s** | Облегченный, без внешних зависимостей. | Изолированные окружения. |
| **Standalone Binary** | Встроенный etcd, запуск одной командой. | Bare Metal, локальная разработка. |

### Передовые возможности

- **Namespace 1:1 Syncing:** Синхронизация пространств имен без переименования (no rewriting). Необходима для работы legacy-инструментов мониторинга и безопасности.
- **Hybrid Scheduling:** Возможность запускать обычные поды в vCluster, а ресурсоемкие задачи (GPU jobs) делегировать на специализированные планировщики хоста (Volcano, Kueue).
- **CSI Snapshot Support:** Поддержка снапшотов для stateful-нагрузок внутри виртуального кластера.

#### Resource Patching: подробности

Resource Patching — одна из самых тонких частей vCluster. При синхронизации объекта между плоскостями Syncer может применять патчи, чтобы избежать конфликтов имён, добавить префиксы, или скорректировать поля, несовместимые с хостом. Поддерживаются три механизма:

1. **Встроенные патчи по умолчанию** — например, переименование ServiceAccount, добавление метки `vcluster.loft.sh/managed-by`.
2. **Пользовательские патчи в `vcluster.yaml`** — задаются в секции `sync.toHost.<resource>.patches` или `sync.fromHost.<resource>.patches`.
3. **CEL-патчи (v0.31+)** — Common Expression Language для сложных условных трансформаций (например, `spec.secretName` с префиксом имени vCluster для изоляции secret-имен между тенантами).

Патчинг особенно критичен для CRD: многие операторы (cert-manager, ArgoCD, ExternalSecrets) хранят состояние в связанных объектах, и без переименования возникают конфликты при использовании одного оператора в нескольких vCluster.

### Матрица совместимости версий (на 2026 год)

Для стабильной работы рекомендуется поддерживать актуальность минорных версий.

| Хост-кластер (Host) | Поддерживаемые версии vCluster |
| :--- | :--- |
| **1.33** | 1.32, 1.33, 1.34, 1.35 |
| **1.34** | 1.33, 1.34, 1.35, 1.36 |
| **1.35** | 1.34, 1.35, 1.36 |
| **Standalone** | Любая версия 1.30+ |

> Общее правило: версия Control Plane vCluster может быть на 1–3 минорных релиза выше или ниже версии хост-кластера. Большое расхождение (≥4 минорных релиза) не поддерживается и может приводить к несовместимости API-объектов.

### Сравнение: Namespace vs vCluster

| Характеристика | Namespace (Пространство имен) | vCluster (Виртуальный кластер) |
| :--- | :--- | :--- |
| **API Server** | Общий для всех | Собственный для каждого кластера |
| **Глобальные ресурсы (CRD)** | Общие (требуют прав администратора) | Изолированные (свой API-сервер) |
| **Изоляция RBAC** | Только внутри namespace | Полная (ClusterRoles, RoleBindings) |
| **Управление через kubectl** | Нужен контекст хоста | Свой kubeconfig (полный доступ) |
| **Конфигурация** | Helm values | `vcluster.yaml` (Unified Config) |
| **Ресурсы** | Минимальные | ~200-500Mi RAM (зависит от дистро) |
| **Масштабируемость** | До сотен namespaces | До тысяч vClusters в одном хосте |

### Жизненный цикл vCluster

Каждый vCluster проходит через несколько состояний, которыми можно управлять из CLI:

| Фаза | Что происходит | Когда применять |
| :--- | :--- | :--- |
| **Create** | Развёртывание Control Plane, инициализация Backing Store, регистрация виртуальных нод. | Первичная установка. |
| **Connect** | Установление port-forward или VPN-туннеля для проброса kubeconfig. | Локальная работа, отладка. |
| **Pause** | Остановка Syncer и Control Plane без удаления данных. | Кратковременная приостановка для обслуживания. |
| **Sleep** | Масштабирование workload-подов до нуля, перевод Control Plane в idle. | Неактивные среды (ночные, выходные) — экономия CPU/RAM. |
| **Wake** | Восстановление подов и активация Control Plane по запросу. | Возобновление работы. |
| **Upgrade** | Обновление версии Control Plane и/или Syncer в пределах поддерживаемой матрицы. | Минорные/патч-релизы. |
| **Migrate** | Перенос vCluster между namespace/хост-кластерами (через бэкап Backing Store). | Перепланирование инфраструктуры. |
| **Delete** | Полное удаление namespace, PVC, всех связанных ресурсов. | Завершение проекта, очистка CI-артефактов. |

#### Sleep Mode: внутренний механизм

Sleep Mode — один из самых полезных сценариев для CI/CD и dev-окружений. Работает в три этапа:

1. **Снятие нагрузки:** Syncer (или отдельный контроллер `sleepmode`) scaleDown всех Deployment/StatefulSet до `replicas: 0` внутри vCluster.
2. **Остановка Control Plane:** API Server и Scheduler уменьшают ресурсы (CPU request → near-zero), сохраняя состояние в Backing Store.
3. **Пробуждение (Auto-Wakeup):** При первом запросе к API (kubectl get pods, helm install и т.п.) — отдельный HTTP-эндпоинт видит активность, запускает Control Plane и восстанавливает поды.

Время пробуждения обычно 3–15 секунд, в зависимости от дистрибутива (K3s — быстрее) и наличия внешних Backing Store (требуется сетевой доступ при старте).

### Когда НЕ стоит использовать vCluster

vCluster не универсален. Есть сценарии, где он избыточен или вреден:

| Ситуация | Почему vCluster не подходит | Альтернатива |
| :--- | :--- | :--- |
| **1-2 команды, 5-10 сервисов** | Namespace даёт 95% преимуществ при нулевой дополнительной сложности. | Namespace + RBAC + NetworkPolicy. |
| **Жёсткие требования PCI DSS / ФСТЭК уровня изоляции** | vCluster разделяет ядро ОС worker-узлов с хостом; физическая изоляция отсутствует. | Выделенный bare-metal кластер. |
| **Высокочастотный HPA/Cluster Autoscaler** | Слой Syncer добавляет 100–300 мс задержки на реконсиляцию. | Прямое использование namespace + HPA. |
| **Multi-region актив-актив** | Один vCluster = один Backing Store; распределённые транзакции не поддерживаются. | Несколько кластеров + GitOps (ArgoCD multi-cluster). |
| **Критичные workload с гарантией latency SLO ≤10 мс** | Дополнительный сетевой hop через iptables-virtual-nodes может нарушить SLO. | Bare-metal с прямым CNI. |

### Минимальный пример vcluster.yaml (skeleton)

Полный разбор — в файле установки, здесь приводится только скелет для понимания структуры:

```yaml
# vcluster.yaml
controlPlane:
  distro: k8s              # k3s | k8s | k0s
  backingStore:
    etcd:
      embedded: true

sync:
  toHost:
    pods:
      enabled: true
    services:
      enabled: true
  fromHost:
    storageClasses:
      enabled: true
    nodes:
      enabled: true

policies:
  podSecurityStandard: restricted

sleepMode:
  enabled: true
  autoWakeup: true
```

## Практические сценарии

### Основные варианты использования

- **Разработка операторов и контроллеров:** Безопасное тестирование CRD и логики контроллеров с правами `ClusterAdmin` без риска для стабильности хоста.
- **Изолированный AI/ML (GPU):** Использование **Private Nodes** для запуска ресурсоемких ML-задач на выделенном оборудовании с сохранением централизованного управления.
- **Edge Computing (Standalone):** Развертывание легких кластеров на удаленных точках или IoT-устройствах без зависимости от центрального мастер-кластера.
- **Мультитенантность (Hard Multi-tenancy):** Создание "песочниц" для команд с полной изоляцией API и etcd.
- **Оптимизация затрат:** Масштабирование временных окружений до нуля через **Sleep Mode** и динамическое управление узлами через **Auto Nodes**.
- **CI/CD пайплайны:** Мгновенное создание и удаление чистых кластеров для автоматизированного тестирования.

### Расширенные сценарии для DevOps/SRE/sysadmin

- **Изоляция Blast Radius:** Каждый тенантский vCluster имеет свой Backing Store, поэтому падение/повреждение etcd одного тенанта не затрагивает остальных. Это особенно важно при инцидентах с operator-ами, которые могут повредить состояние кластера.
- **Платформа для внешних клиентов (SaaS-on-prem):** В B2B-сценариях каждому клиенту выдаётся собственный vCluster внутри shared-платформы провайдера. Клиент получает Cluster Admin, не имея доступа к хост-API.
- **Тестирование обновлений Kubernetes:** Поднять vCluster на версии 1.36 за минуты, прогнать регресс-набор, удалить — без риска для продакшна.
- **Compliance-driven изоляция (ФЗ-152, HIPAA-эквиваленты):** Обработка ПДн в отдельном vCluster с собственным аудит-логом, при этом инфраструктура одна.

### Требования к окружению

| Компонент | Требование | Примечание |
| :--- | :--- | :--- |
| **Kubernetes Host** | v1.28+ | Рекомендуется для использования всех возможностей v0.35+. |
| **vCluster CLI** | v0.29+ | Поддержка Standalone и унифицированной конфигурации. |
| **Helm** | v3.12+ | Для установки инфраструктурных компонентов. |
| **kubectl** | Совместим с версией host-кластера | Для управления хостом при создании vCluster. |
| **Container Runtime** | containerd ≥1.7 или CRI-O ≥1.25 | На worker-узлах хост-кластера (для workload-подов). |

### Ресурсы Control Plane (Kubernetes Vanilla)

Средние требования для одного виртуального кластера:

| Компонент | CPU Request | Memory Request | CPU Limit | Memory Limit |
| :--- | :--- | :--- | :--- | :--- |
| **API Server** | 150m | 200Mi | 400m | 512Mi |
| **etcd / DB** | 100m | 128Mi | 200m | 256Mi |
| **Syncer** | 50m | 100Mi | 150m | 200Mi |
| **Итого** | **~300m** | **~428Mi** | **~750m** | **~1Gi** |

*При использовании дистрибутива K3s потребление RAM снижается до 150-200Mi.*

Для планирования емкости хост-кластера на N vCluster используйте формулу:

```text
Host CPU headroom ≥ N × 300m + 20% (резерв на Auto Nodes / HPA workloads)
Host RAM headroom ≥ N × 500Mi + 30% (резерв на workload-пики)
```

При N > 50 рекомендуется переходить на Auto Nodes или внешний Backing Store для снижения давления на локальный scheduler.

### Наблюдаемость (Observability)

Для SRE мониторинга vCluster развёртывается три уровня метрик:

| Источник | Что показывает | Инструменты |
| :--- | :--- | :--- |
| **Хост API Server** | Синхронизированные поды, статус Syncer, состояние namespace. | Prometheus + kube-state-metrics на хосте. |
| **vCluster API Server** | Метрики самого виртуального кластера (control-plane latency, watch-errors). | Prometheus Operator внутри vCluster, scrape через serviceMonitor. |
| **Workload-метрики** | Метрики приложений тенанта. | Стандартный стек (Prometheus/Grafana), развёрнутый внутри vCluster. |

> Тонкий момент: метрики `kube_pod_*` хоста и vCluster различаются по лейблам (например, `pod` в хосте может называться `myapp-xxx-0-host`, а в vCluster — `myapp-xxx-0`). Это нормально, но требует аккуратного relabeling в Prometheus, чтобы не дублировать алерты.

#### Логирование

Syncer пишет структурированные логи в JSON (stdout) — собираются стандартным log-агентом (Vector, Loki Promtail, Fluent Bit). Ключевые события для алертинга:

- `failed to sync resource` — ошибка репликации конкретного объекта.
- `backing store unavailable` — потеря связи с etcd/БД.
- `watch timeout exceeded` — задержки Syncer >10s (деградация).
- `connection to host API lost` — критично, тенант теряет управление.

### Типичные ошибки и диагностика

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `vcluster connect` зависает на 30s | Syncer не может подключиться к API Server vCluster из-за сетевых политик. | Проверить NetworkPolicy в namespace хоста, разрешить egress от Syncer к API. |
| Поды внутри vCluster в статусе `Pending` | Не зарегистрированы виртуальные ноды или их ресурсы = 0. | Проверить `kubectl get nodes` внутри vCluster; убедиться, что `sync.fromHost.nodes.enabled: true`. |
| Ошибка `forbidden: cannot create resource "x"` | RBAC Syncer ограничен и не имеет прав на реплицируемый CRD. | Расширить ClusterRole Syncer или включить generic sync. |
| Медленная реакция HPA | Дополнительный hop Syncer задерживает реконсиляцию. | Включить `--sync-interval` <5s или отказаться от HPA внутри vCluster. |
| `etcd` OOMKilled в Backing Store | Превышен лимит RAM etcd при большом числе объектов. | Перейти на external etcd/PostgreSQL или поднять memory limit. |
| Sleep Mode не просыпается | Auto-wakeup endpoint не доступен извне. | Проверить service `vcluster-<name>` в namespace хоста, что порт wakeup открыт. |
| PVC в vCluster не привязывается | StorageClass хоста не синхронизирован во vCluster. | Включить `sync.fromHost.storageClasses.enabled: true`. |
| `helm install` внутри vCluster падает с timeout | Таймаут на фоне пробуждения Control Plane из Sleep. | Увеличить `--timeout` Helm до 5m, либо отключить Sleep для активного CI. |

### Best Practices

- **Версионирование конфигурации:** Храните `vcluster.yaml` в Git. Любое изменение синхронизации или политик — через PR с ревью.
- **Лимиты по умолчанию:** Всегда задавайте `LimitRange` в namespace хоста и внутри vCluster, чтобы один тенант не исчерпал ресурсы.
- **Именование:** Используйте префиксы тенантов в именах vCluster и namespace (`team-alpha-prod`), это упрощает автоматизацию.
- **Мониторинг Syncer:** Алерт на `vcluster_syncer_sync_errors_total > 0` в течение 5 минут.
- **Бэкап Backing Store:** Регулярные снапшоты etcd/SQLite; для PostgreSQL — `pg_dump` или WAL-архивирование.
- **Изоляция RBAC:** ServiceAccount Syncer должен иметь минимально необходимые права; избегайте wildcard verbs/resources.
- **Тестовые среды через Sleep Mode:** Для dev-окружений разработчиков включайте `sleepMode.autoWakeup: true` с scaleDown до 0 — экономия CPU/RAM ~70%.
- **Ротация сертификатов:** В v0.30+ API Server автоматически ротирует сертификаты, но убедитесь, что `kubelet`-клиент корректно перезапрашивает kubeconfig.

### Очистка

```bash
# Удаление vCluster (полная очистка namespace и PVC)
vcluster delete my-vc -n my-namespace

# Удаление без PVC (для последующего восстановления)
vcluster delete dev-vc -n team-alpha --keep-pvc

# Остановка всех workload-подов без удаления кластера (мягкая остановка)
vcluster pause my-vc -n my-namespace

# Возобновление
vcluster resume my-vc -n my-namespace
```

> Все операции идемпотентны: повторный `delete` не приводит к ошибкам, повторный `create` поверх существующего namespace вернёт осмысленную ошибку.

### Ограничения и известные проблемы (Edge cases)

| Сценарий | Поведение | Обходной путь |
| :--- | :--- | :--- |
| **ClusterRole `cluster-admin` внутри vCluster** | Не даёт доступа к хост-API (и не должна), но часто вводит в заблуждение. | Документировать для пользователей. |
| **Pod с `hostNetwork: true`** | Syncer патчит поле `hostNetwork: false`, потому что хост-сеть зарезервирована. | Использовать `hostAliases` или DaemonSet хоста. |
| **Service `type: LoadBalancer`** | Syncer не создаёт реальный LB на хосте, если `sync.toHost.services` отключён. | Включить sync + Ingress/Gateway API. |
| **Job с TTL > restartPolicy** | При удалении Job Syncer может пропустить финальный статус. | Включить `keepCompletedJobs: true` (планируется в v0.36+). |
| **CSI driver из хост-кластера** | Не пробрасывается во vCluster автоматически. | Явно через generic sync или `fromHost`. |
| **Webhook внутри vCluster** | Может конфликтовать с метриками/аудитом хоста из-за одинаковых имён. | Использовать префиксы или per-vCluster namespace. |
| **Поды с `priorityClassName: system-*`** | Зарезервированы за хост-кластером, Syncer переписывает на менее приоритетные классы. | Создать собственные PriorityClass внутри vCluster. |
| **Большое число CRD (>100)** | Заметная деградация startup API Server (до 30–60s). | Использовать Vanilla K8s вместо K3s; увеличить ресурсы Control Plane. |

### Миграция между дистрибутивами и версиями

| Переход | Сложность | Процедура |
| :--- | :--- | :--- |
| **K3s → Vanilla K8s** | Средняя | Бэкап SQLite/etcd → восстановление в новый vCluster с дистрибутивом k8s. |
| **v0.30 → v0.35** | Низкая | Helm upgrade или `vcluster upgrade` in-place. |
| **v0.20 → v0.30+** | Средняя | Конвертация Helm values → `vcluster.yaml` (есть авто-мигратор в CLI v0.30+). |
| **Host-кластер 1.30 → 1.33** | Низкая | vCluster обычно совместим с ±3 минорных релиза; обновить host, потом проверить матрицу совместимости. |
| **vCluster на namespace A → namespace B** | Средняя | Бэкап Backing Store + `vcluster create` в новом namespace + restore. |

### Проверка корректности установки (smoke-test)

После создания vCluster полезно прогнать минимальный набор проверок:

```bash
# 1. Подключение
vcluster connect my-vc -n my-namespace -- update-current

# 2. Проверка нод (должна быть минимум одна виртуальная)
kubectl get nodes -o wide
# → NAME           STATUS   ROLES                  AGE   VERSION
# → vcluster-node  Ready    control-plane,master   1m    v1.33.0

# 3. Проверка системных подов
kubectl get pods -n kube-system
# → coredns-xxx   1/1   Running
# → kube-proxy    1/1   Running

# 4. Создание тестового workload
kubectl run nginx --image=nginx --restart=Never
sleep 5
kubectl get pod nginx
# → nginx   0/1   ContainerCreating   0   <n>

# 5. Проверка синхронизации в хост-кластере
kubectl get pods -n my-namespace -l vcluster.loft.sh/managed-by
# → nginx-my-vc-xxx   1/1   Running
```

Если какой-то шаг падает — обратитесь к матрице диагностики выше.
