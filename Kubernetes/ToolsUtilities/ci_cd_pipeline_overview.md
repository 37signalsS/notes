# Обзор CI/CD Пайплайна для Kubernetes

Этот документ является практическим руководством. Для ознакомления с базовыми концепциями CI/CD обратитесь к [общему обзору](../../CI-CD/ci_cd_overview.md).

## Определения

**CI/CD (Continuous Integration/Continuous Delivery) для Kubernetes** — это практика автоматизации сборки, тестирования и развертывания приложений в кластере Kubernetes. Пайплайн представляет собой последовательность шагов: от коммита кода в репозиторий до работающего приложения в production-среде, что делает процесс выпуска новых версий быстрым и надежным.

## Основные концепции

Типичный CI/CD пайплайн для Kubernetes состоит из нескольких ключевых этапов.

### 1. Сборка (Build)

*   **Задача:** Сборка Docker-образа из `Dockerfile`, находящегося в репозитории приложения.
*   **Ключевая особенность:** Каждой сборке автоматически присваивается уникальный тег (например, на основе ID пайплайна). Это гарантирует, что каждая сборка является уникальной и отслеживаемой версией приложения.

### 2. Тестирование (Test)

*   **Задача:** Проверка работоспособности приложения.
*   **Окружение:** Для тестирования с помощью `docker-compose` разворачивается изолированное окружение, включающее в себя как само веб-приложение, так и его зависимости, например, тестовый экземпляр базы данных.

#### Детальная настройка тестового окружения с Docker Compose

Для создания изолированного тестового окружения используется `docker-compose`. Файл описывает два ключевых сервиса: базу данных и само приложение.

**Пример `docker-compose.yml` для тестов:**

```yaml
version: '2.1'

services:
  db:
    image: postgres:9.6
    healthcheck:
      # Команда для проверки готовности базы данных
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 5s
      retries: 5

  app:
    # Используется образ, собранный на предыдущем шаге пайплайна
    image: ${CI_REGISTRY_IMAGE}/${CI_PROJECT_NAME}:${CI_COMMIT_REF_SLUG}.${CI_PIPELINE_ID}
    environment:
      # Переменные для подключения к БД и указания тестового окружения
      - DATABASE_URL=postgres://postgres@db/test_db_name
      - RAILS_ENV=test
    depends_on:
      db:
        # Контейнер приложения запустится только после того, как БД будет готова
        condition: service_healthy
    # Команда для запуска миграций и тестов
    command: >
      sh -c "bundle exec rake db:migrate && 
             bundle exec rake test"
```

**Ключевые моменты конфигурации:**

*   **Версия `2.1`:** Используется для поддержки опции `condition: service_healthy` в `depends_on`, которая гарантирует запуск приложения только после полной готовности базы данных.
*   **Динамический образ:** Имя образа (`image`) формируется из переменных GitLab CI, что позволяет использовать образ, собранный на шаге `build`.
*   **`healthcheck`:** Проверка состояния сервиса `db` позволяет дождаться полной готовности PostgreSQL.

#### Интеграция этапа тестирования с `.gitlab-ci.yml`

Для запуска тестов и последующей очистки в `.gitlab-ci.yml` добавляются этапы `test` и `cleanup`.

**Пример добавления этапов в `.gitlab-ci.yml`:**
```yaml
stages:
  - build
  - test
  - cleanup

# ... этап build ...

test_step:
  stage: test
  script:
    - >
      docker-compose 
      -p ${CI_PIPELINE_ID} 
      up 
      --quiet-pull 
      --abort-on-container-exit 
      --exit-code-from app

cleanup_step:
  stage: cleanup
  script:
    - docker-compose -p ${CI_PIPELINE_ID} down
  when: always
```

**Описание шагов:**

*   **Этап `test`**:
    *   `-p ${CI_PIPELINE_ID}`: Задает уникальное имя проекта для `docker-compose`, чтобы избежать конфликтов на GitLab Runner.
    *   `--exit-code-from app`: `docker-compose` завершится с кодом выхода тестового контейнера, что позволяет GitLab CI корректно определить результат тестов.
*   **Этап `cleanup`**:
    *   `when: always`: Шаг выполняется всегда, даже если тесты провалились, чтобы гарантировать удаление временного окружения.

### 3. Очистка (Cleanup)

*   **Задача:** Удаление инфраструктуры, созданной для этапа тестирования.
*   **Условие выполнения:** Этот шаг выполняется **всегда**, независимо от того, успешно ли прошли тесты. Это обеспечивает чистоту сборочной среды.

### 4. Публикация (Push)

*   **Задача:** Публикация собранного и протестированного Docker-образа в Docker Registry.
*   **Важное замечание:** Образ публикуется только **после** успешного прохождения тестов. Нет смысла хранить в репозитории неработающие или непроверенные образы.

#### Настройка доступа Kubernetes к GitLab Registry

После того как Docker-образ опубликован в GitLab Registry, кластеру Kubernetes необходимы права для его скачивания (pull). Без этого шага поды не смогут запуститься с ошибкой `ImagePullBackOff`. Для предоставления доступа используется механизм `imagePullSecrets`.

Процесс состоит из двух этапов: создание Deploy Token в GitLab и создание секрета в Kubernetes.

##### Создание Deploy Token в GitLab

Deploy Token — это долгоживущий токен с ограниченными правами, предназначенный для доступа к репозиторию или registry без использования учетных данных пользователя.

1.  В вашем проекте GitLab перейдите в **Settings > Repository**.
2.  Найдите раздел **Deploy Tokens** и раскройте его.
3.  Введите имя для токена (например, `kubernetes-pull-token`).
4.  **Важно:** Установите галочку **`read_registry`**. Это предоставит токену права только на чтение из Docker Registry.
5.  Нажмите **Create deploy token**.

GitLab сгенерирует и покажет вам **имя пользователя (username)** и **пароль (password)**. **Сохраните их, так как пароль будет показан только один раз.**

##### Создание секрета в Kubernetes

Теперь, используя полученные учетные данные, необходимо создать секрет типа `docker-registry` в том namespace, куда будет развертываться приложение.

Выполните следующую команду, подставив ваши данные:

```bash
kubectl create secret docker-registry <имя-секрета> \
  --namespace <ваш-namespace> \
  --docker-server=<адрес-вашего-gitlab-registry> \
  --docker-username=<имя-пользователя-из-deploy-token> \
  --docker-password=<пароль-из-deploy-token> \
  --docker-email=<любой-email>
```

**Пример:**

```bash
kubectl create secret docker-registry gitlab-registry-secret \
  --namespace my-app-production \
  --docker-server=registry.gitlab.com \
  --docker-username=gitlab+deploy-token-12345 \
  --docker-password=xxxxxxxxxxxxxxxxxxxx \
  --docker-email=ci@example.com
```

*   `<имя-секрета>`: Имя, которое вы будете использовать в манифестах (например, `gitlab-registry-secret`).
*   `<адрес-вашего-gitlab-registry>`: Обычно это `registry.gitlab.com` или адрес вашего self-hosted экземпляра.
*   `docker-email`: Это поле является обязательным для команды, но не используется для аутентификации. Можно указать любое значение.

После создания этого секрета, его имя нужно будет указать в спецификации пода или в ServiceAccount, чтобы Kubernetes мог автоматически использовать его для скачивания образов из вашего GitLab Registry.

### 5. Развертывание (Deploy)

*   **Задача:** Развертывание приложения непосредственно в кластер Kubernetes.
*   **Инструмент:** Для управления процессом развертывания используется пакетный менеджер [Helm](./helm_overview.md). Команда `helm upgrade --install` позволяет атомарно обновить приложение до новой версии.
*   **Подготовка:** Перед первым развертыванием может потребоваться предварительная подготовка кластера (например, создание namespace, секретов и т.д.). 

## Практические сценарии

### Пример: CI/CD для Ruby-проекта "Xpaced"

В качестве практического примера рассмотрим процесс настройки CI/CD для реального Ruby-on-Rails проекта "Xpaced".

#### 1. Подготовка репозитория

Первым шагом является подготовка рабочего окружения и получение кода проекта.

1.  **Fork проекта:** В GitLab создается fork исходного репозитория проекта "Xpaced" в личное пространство имен пользователя.
2.  **Клонирование репозитория:** После создания fork, репозиторий клонируется на рабочий хост:
    ```bash
    git clone <URL_вашего_форка>
    cd xpaced
    ```

#### 2. Анализ Dockerfile

Ключевым компонентом для сборки является `Dockerfile`. Рассмотрим его структуру и основные шаги.

-   **Базовый образ:** Используется легковесный образ `ruby` на основе Alpine Linux.
-   **Зависимости:** Устанавливаются системные пакеты, необходимые для сборки и работы приложения.
-   **Конфигурация:** Копируются конфигурационные файлы для Nginx.
-   **Установка гемов:** Копируются `Gemfile` и `Gemfile.lock`, после чего `bundler` устанавливает все Ruby-зависимости.
-   **Копирование кода:** Исходный код приложения копируется в образ.
-   **Сборка статитики:** Выполняется команда для сборки статических ассетов (CSS, JS) прямо на этапе сборки образа.
-   **Точка входа (`entrypoint`):** Используется кастомный скрипт `docker-entrypoint.sh`, который выполняет следующие действия при старте контейнера:
    1.  Выполняет миграции базы данных (`db:migrate`).
    2.  Запускает application-сервер `Puma`.
    3.  Запускает веб-сервер `Nginx`.

Такой `Dockerfile` готовит полностью самодостаточный образ, который можно использовать для тестирования и развертывания.

#### 3. Создание файла `.gitlab-ci.yml`

Этот файл является ядром CI/CD в GitLab. Рассмотрим его создание по шагам.

##### 3.1. Определение этапов (Stages)

В первую очередь, определяются все этапы пайплайна.

```yaml
stages:
  - build
  - test
  - cleanup
  - push
  - deploy
```

##### 3.2. Этап `build` (Сборка)

Добавляется задание для сборки Docker-образа.
```yaml
build_step:
  stage: build
  script:
    - docker build -t $CI_REGISTRY_IMAGE/$CI_PROJECT_NAME:$CI_COMMIT_REF_SLUG.$CI_PIPELINE_ID .
```

**Разбор конфигурации:**

*   `stages`: Определяет последовательность этапов пайплайна.
*   `build_step`: Название конкретного задания (job).
*   `stage: build`: Привязывает задание к этапу `build`.
*   `script`: Содержит команды, которые будут выполнены. В данном случае — `docker build`.
*   **Тегирование образа:** Тег для Docker-образа формируется динамически с использованием встроенных переменных GitLab CI:
    *   `$CI_REGISTRY_IMAGE/$CI_PROJECT_NAME`: Формирует полное имя образа, включая адрес встроенного в GitLab registry. Например: `registry.example.com/username/project-name`.
    *   `$CI_COMMIT_REF_SLUG`: Название текущей ветки (например, `master` или `feature-branch`).
    *   `$CI_PIPELINE_ID`: Уникальный идентификатор пайплайна, который инкрементируется при каждом запуске.
    *   **Результат:** Такой подход (`master.12345`) гарантирует, что каждый коммит в каждой ветке порождает уникальный, отслеживаемый Docker-образ.

##### 3.3. Коммит и запуск пайплайна

После создания файла `.gitlab-ci.yml` необходимо закоммитить его в репозиторий и отправить на сервер GitLab.

```bash
# Добавление файла в индекс Git
git add .gitlab-ci.yml

# Создание коммита
git commit -m "Add build stage to CI pipeline"

# Отправка изменений на сервер
git push
```

##### 3.4. Проверка результата

После выполнения команды `git push` GitLab автоматически запустит новый пайплайн.

1.  Перейдите в ваш проект в GitLab.
2.  Откройте раздел **CI/CD -> Pipelines**.
3.  Вы увидите запущенный пайплайн с одним этапом `build`.
4.  Кликнув на задание, можно посмотреть логи выполнения, где будет видна команда `docker build` и то, как были раскрыты переменные в имени и теге образа. Успешное выполнение будет отмечено зеленой иконкой.

##### 3.5. Этап `push` (Публикация)

Добавляется задание для публикации образа в GitLab Registry.
```yaml
stages:
  - build
  - test
  - cleanup
  - push
  - deploy

# ... пропущены этапы build, test, cleanup ...

push_step:
  stage: push
  before_script:
    # Аутентификация в GitLab Registry с использованием предопределенных переменных
    - docker login -u $CI_REGISTRY_USER -p $CI_BUILD_TOKEN $CI_REGISTRY
  script:
    # Публикация образа, собранного на этапе build
    - docker push $CI_REGISTRY_IMAGE/$CI_PROJECT_NAME:$CI_COMMIT_REF_SLUG.$CI_PIPELINE_ID
  only:
    # Выполнять этот шаг только для master-ветки
    - master
```

**Разбор конфигурации:**

*   `stages`: Мы добавляем `push` и `deploy` в список этапов. Важно, чтобы они шли после `test` и `cleanup`, гарантируя, что публикуется и развертывается только протестированный код.
*   `push_step`: Новое задание для публикации образа.
*   `before_script`: Выполняет команду `docker login` для аутентификации в GitLab Registry. GitLab автоматически предоставляет временный `CI_BUILD_TOKEN` для этой цели, что является безопасной практикой.
*   `script`: Выполняет `docker push`, используя те же динамические переменные, что и при сборке. Это гарантирует, что публикуется именно тот образ, который был собран и протестирован в рамках текущего пайплайна.
*   `only: - master`: Этот ключ ограничивает выполнение шага только для `master` ветки. Это распространенная практика, чтобы в registry попадали только стабильные, готовые к развертыванию версии кода, в то время как для feature-веток выполняются только сборка и тесты.

##### 3.6. Настройка доступа Kubernetes к GitLab Registry

В этом шаге необходимо настроить кластер Kubernetes для доступа к GitLab Registry. Подробное описание этого процесса, включая создание Deploy Token и `imagePullSecrets`, находится в разделе "[Настройка доступа Kubernetes к GitLab Registry](#настройка-доступа-kubernetes-к-gitlab-registry)" в основных концепциях.

##### 3.7. Этап `deploy` (Развертывание)

Финальное задание для развертывания приложения в Kubernetes с помощью Helm.
```yaml
deploy_step:
  stage: deploy
  script:
    - >
      helm upgrade --install my-release-name ./path/to/chart \
        --namespace my-app-production \
        --set image.tag=$CI_COMMIT_REF_SLUG.$CI_PIPELINE_ID \
        --wait \
        --atomic \
        --timeout 5m0s
  only:
    - master
```

**Разбор конфигурации:**

*   `stage: deploy`: Привязывает задание к последнему этапу пайплайна.
*   `script`: Содержит основную команду для развертывания — `helm upgrade --install`.
    *   `my-release-name`: Имя релиза в Kubernetes. Использование `--install` гарантирует, что если релиз с таким именем не существует, он будет создан. Если существует — обновлен.
    *   `./path/to/chart`: Путь к директории с Helm-чартом вашего приложения.
    *   `--namespace`: Указывает, в какое пространство имен производить развертывание.
    *   `--set image.tag=...`: Динамически передает в чарт тег Docker-образа, который был собран и протестирован на предыдущих шагах. Это ключевой механизм, связывающий CI и CD: мы развертываем именно тот артефакт, который прошел все проверки.
    *   `--wait`: Заставляет Helm ожидать, пока все ресурсы, созданные в рамках релиза (например, поды), не перейдут в состояние готовности. Если этого не произойдет, обновление будет считаться неудачным.
    *   `--atomic`: Если обновление завершается неудачей (например, из-за таймаута флага `--wait`), этот флаг гарантирует, что Helm автоматически откатит релиз к предыдущей успешной версии. Это обеспечивает **атомарность операции** и является критически важным для стабильности production-окружения.
    *   `--timeout 5m0s`: Устанавливает максимальное время ожидания для команды. Если за это время ресурсы не стабилизировались, Helm прервет операцию.
*   `only: - master`: Ограничивает автоматическое развертывание только для `master`-ветки, что является стандартной практикой.

## Дополнительная информация

### Поведение развертывания при сбое

Рассмотрим сценарий, когда выкатывается "сломанная" версия приложения. 
1.  `helm upgrade --install --atomic` пытается развернуть новую версию. 
2.  Новые поды не могут запуститься и переходят в состояние `CrashLoopBackOff`. 
3.  Флаг `--wait` не дожидается их готовности в течение заданного `--timeout`. 
4.  Развертывание считается проваленным. 
5.  Благодаря флагу `--atomic`, Helm автоматически выполняет `helm rollback`. 
6.  В кластере Kubernetes остается работать предыдущая стабильная версия приложения. Для конечных пользователей сбой полностью прозрачен. 
7.  Команда `helm upgrade` завершается с ненулевым кодом выхода, и GitLab CI помечает **пайплайн как неуспешный (красный)**.

Это именно то поведение, которое требуется: **инфраструктура остается стабильной, а команда получает четкий сигнал о том, что в новой версии кода есть проблема.**
