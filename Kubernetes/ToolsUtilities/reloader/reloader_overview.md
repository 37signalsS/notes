# Обзор Reloader

## Определения

**Reloader** — контроллер Kubernetes (K8s) от компании Stakater, предназначенный для автоматизации процесса обновления рабочих нагрузок (workloads) при изменении связанных с ними конфигурационных данных.

**Основные задачи контроллера:**
- Отслеживание изменений в объектах `ConfigMap` и `Secret`.
- Автоматическое инициирование плавного обновления (Rolling Upgrade) для `Deployment`, `StatefulSet`, `DaemonSet`, `Argo Rollout` и `DeploymentConfig`.
- Решение проблемы "зависших" конфигураций, когда изменение `ConfigMap` не подхватывается приложением без перезапуска пода (Pod), особенно при использовании переменных окружения (Environment Variables) или `subPath`.

**Текущее состояние (август 2026):**
- **Версия приложения:** `v1.4.19` (Go `1.26.2`, образы на базе UBI 9).
- **Версия Helm-чарта:** `v2.2.14`.
- **Лицензирование:** Доступны версии Open Source Software (OSS) и Enterprise (с поддержкой подписанных образов и SBOM).
- **Надёжность:** Высокая, подтверждена E2E-тестами на базе фреймворка **Ginkgo**.

**Связанные файлы:** [Установка и настройка](./reloader_installation.md) · [Практические сценарии](./reloader_usage_scenarios.md) · [Мониторинг и лучшие практики](./reloader_monitoring_and_best_practices.md) · [Безопасность](./reloader_security.md) · [Runbooks](./reloader_runbooks.md)

## Предварительные требования

### Версии Kubernetes и зависимостей

| Компонент | Минимальная версия | Рекомендуемая версия | Примечание |
| :--- | :--- | :--- | :--- |
| **Kubernetes** | 1.26 | 1.28+ | Поддержка User Namespaces требует 1.25+ |
| **Helm** (для установки через чарт) | 3.10 | 3.12+ | Для управления версиями и HA |
| **Go** (для сборки из исходников) | 1.26.2 | 1.26.2 | Версия, использованная в официальном билде |

### Необходимые ресурсы кластера

- **RBAC:** Контроллер требует ServiceAccount с правами на чтение ConfigMap/Secret и запись к рабочим нагрузкам.
- **Хранилище:** Для работы CSI-интеграции необходим установленный Secrets Store CSI Driver.
- **Сеть:** Доступ к API Server Kubernetes для получения событий watch.

### Пререквизиты для продакшн-развёртывания

1. **High Availability (HA):** Для отказоустойчивости рекомендуется запускать минимум 2 реплики контроллера с включенным Leader Election.
2. **Ресурсы:** Минимальные ресурсы — 100m CPU / 128Mi Memory (request), 300m CPU / 512Mi Memory (limit). Для кластеров с >1000 рабочих нагрузок рекомендуется увеличить лимиты.
3. **Мониторинг:** Настройка Prometheus и Grafana для сбора метрик (`/metrics` эндпоинт на порту 9090).

## Основные концепции

### Архитектура и принцип работы

Reloader построен на базе **controller-runtime** — фреймворка для создания контроллеров Kubernetes, который предоставляет:
- **Manager:** Управление жизненным циклом контроллера, Leader Election, управление кешем.
- **Reconciler:** Паттерн согласования желаемого состояния с текущим.
- **Cache:** Локальный кеш объектов Kubernetes для снижения нагрузки на API Server.

```text
┌─────────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  ConfigMap /    │ ──> │    Reloader      │ ──> │  Rolling Upgrade│
│    Secret       │     │   (watch API)    │     │   подов (Pods)  │
│   (изменение)   │     │                  │     │                 │
└─────────────────┘     └──────────────────┘     └─────────────────┘
                                │
                                ▼
                    ┌──────────────────────┐
                    │   Leader Election    │
                    │   (для HA режима)    │
                    └──────────────────────┘
```

#### Этапы обработки события

1. **Отслеживание (Watch):** Reloader подписывается на события Kubernetes API Server для мониторинга изменений ресурсов. Используется机制 informer для эффективного кеширования и обработки событий.
2. **Анализ зависимостей:** При обнаружении изменения контроллер сканирует аннотации рабочих нагрузок и находит те, которые ссылаются на изменённый ресурс. Поиск осуществляется по индексу аннотаций для O(1) сложности.
3. **Обновление:** В зависимости от выбранной стратегии, Reloader модифицирует шаблон пода (`PodTemplateSpec`), что заставляет Kubernetes инициировать стандартный процесс Rolling Update.
4. **Кеширование:** Reloader поддерживает локальный кеш состояний для предотвращения повторной обработки уже обработанных событий (idempotency).

#### Leader Election (для HA)

В режиме High Availability несколько реплик контроллера работают одновременно, но только одна является "лидером" и обрабатывает события. При падении лидера происходит автоматический переход (failover) к другой реплике. Флаг `--sync-after-restart` позволяет новому лидеру провести полную сверку состояния кластера после перевыборов.

### Способы обнаружения ресурсов

- **Автоматический (`auto`):** Reloader сканирует спецификацию пода и автоматически находит все используемые `ConfigMap` и `Secret` (через `env`, `envFrom`, `volumes`). Рекомендуется для stateless-приложений.
- **Явный (Explicit):** В аннотациях рабочей нагрузки указывается конкретный список ресурсов для отслеживания. Рекомендуется для минимизации лишних перезапусков и для критических систем.
- **Поиск по совпадению (Match):** Синхронизация происходит только если аннотация в `ConfigMap`/`Secret` совпадает с аннотацией в рабочей нагрузке. Полезно для мультитенантных сред.

### Управляющие аннотации и флаги

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `reloader.stakater.com/auto` | `"true"` | Включает автоматическое отслеживание всех зависимостей. |
| `configmap.reloader.stakater.com/reload` | `"name1,name2"` | Отслеживать только указанные ConfigMap. |
| `secret.reloader.stakater.com/reload` | `"name1,name2"` | Отслеживать только указанные Secret. |
| `reloader.stakater.com/ignore` | `"true"` | Игнорировать данную рабочую нагрузку. |
| `deployment.reloader.stakater.com/pause-period` | `"1m"` | Задержка перед перезапуском (Debounce) для группировки изменений. |
| `--ignore-annotation` | флаг запуска | **Новое (v1.4.19):** Глобальный переопределитель, заставляющий Reloader игнорировать аннотацию `ignore`. |
| `--namespaces-to-select` | флаг запуска | Список namespace для отслеживания (белый список). |
| `--namespaces-to-ignore` | флаг запуска | Список namespace для исключения (черный список). |
| `--reload-strategy` | флаг запуска | Стратегия обновления: `env-vars` (по умолчанию), `annotations`, `restart`. |
| `--enable-csi-integration` | флаг запуска | Включение интеграции с Secrets Store CSI Driver. |
| `--log-level` | флаг запуска | Уровень логирования: `info` (по умолчанию), `debug`. |
| `--sync-after-restart` | флаг запуска | Полная сверка состояния после перевыборов лидера. |

### Стратегии обновления

| Стратегия | Механизм | Применение | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- | :--- |
| **`env-vars`** (Default) | Добавляет переменную `STAKATER_RELOADER_...` с хешем данных. | Универсальный метод, работает везде. | Простота, совместимость со всеми приложениями. | Может вызывать лишние рестарты при использовании `envFrom`. |
| **`annotations`** | Добавляет аннотацию `reloader.stakater.com/last-reloaded-from`. | **Рекомендовано для GitOps (ArgoCD)**, минимизирует diff манифестов. | Чистый diff в GitOps, минимум побочных эффектов. | Требует настройки ignoreDifferences в ArgoCD. |
| **`restart`** | Выполняет `rollout restart` через API. | Идеально для Argo Rollouts, предотвращает состояние OutOfSync. | Минимальное воздействие на манифесты. | Не модифицирует PodTemplate, зависит от поведения API. |

## Новые возможности и интеграции

### Интеграция с Secrets Store CSI Driver

Reloader полноценно поддерживает отслеживание объектов `SecretProviderClass`.
- При включении `--enable-csi-integration=true` контроллер следит за ротацией секретов во внешних хранилищах (HashiCorp Vault, AWS Secrets Manager, Azure Key Vault).
- Интеграция работает через отслеживание `SecretProviderClassPodStatus`: как только CSI-драйвер обновляет секрет, Reloader инициирует перезагрузку.
- **Важно:** CSI-интеграция требует установленного Secrets Store CSI Driver версии 1.0+.

### Уведомления и алертинг (Webhooks)

Нативная поддержка отправки уведомлений о событиях перезагрузки для мониторинга в реальном времени:
- **Поддерживаемые каналы:** Slack, Microsoft Teams, Google Chat.
- **Данные в алерте:** Имя ресурса, Namespace, время, стратегия и результат (Success/Failure).
- **Конфигурация:** Настройка через переменные окружения или Helm values.

### Безопасность и высокая доступность (HA)

- **User Namespaces:** Поддержка запуска контроллера в изолированных пространствах имён пользователей (Linux Kernel isolation) для предотвращения атак типа container breakout. Требует Kubernetes 1.25+ и поддержки в CRI (containerd/CRI-O).
- **Синхронизация (`--sync-after-restart`):** Позволяет новому лидеру провести полную сверку состояния кластера после перевыборов (Leader Election). Рекомендуется для кластеров с частыми обновлениями.
- **Hardened Images:** Использование UBI 9 и подпись образов через Cosign (Enterprise).
- **Non-root:** Запуск от UID 65534, minimal privileges.

## Практические сценарии

### Сценарий 1: Выбор инструмента для обновления конфигурации

| Характеристика | Reloader | Helm Checksum | Kustomize Hash |
| :--- | :--- | :--- | :--- |
| **Тип** | Динамический (Controller) | Статический (Template) | Статический (Build) |
| **Trigger** | Изменение ресурса в K8s API | `helm upgrade` | `kubectl apply` |
| **GitOps Friendly** | Да (с `annotations` strategy) | Да | Да |
| **Сложность** | Требует установки контроллера | Не требует дополнений | Не требует дополнений |
| **Hot Reload** | Да (watch API) | Нет | Нет |
| **Время отклика** | Мгновенно (событийный) | Только при deploy | Только при apply |
| **Побочные эффекты** | Дополнительный контроллер | Изменение хеша в манифесте | Изменение хеша в манифесте |

**Когда выбирать Reloader:**
- Приложения не поддерживают hot reload конфигурации.
- Необходимо реагирование на изменения в реальном времени (не только при deploy).
- Используется внешнее хранилище секретов (Vault, CSI Driver).
- Нужна интеграция с Argo Rollouts для Canary/Blue-Green.

### Сценарий 2: Оптимизация для больших кластеров

При наличии более 5000 секретов рекомендуется использовать фильтрацию для снижения нагрузки на API Server:

```bash
# Ограничение области видимости через namespaces
reloader --namespaces-to-select=prod,staging --namespaces-to-ignore=kube-system
# → result: Reloader будет обрабатывать только события из prod и staging
```

**Дополнительные рекомендации:**
- Используйте `--namespaces-to-ignore` для исключения системных namespace.
- Настройте debounce (`pause-period: "1m"`) для приложений с частыми обновлениями.
- Мониторьте глубину очереди задач (`workqueue_depth`) для выявления перегрузки.

### Сценарий 3: Миграция с Helm Checksum на Reloader

**Этапы миграции:**
1. Установите Reloader в кластер ([Установка и настройка](./reloader_installation.md)).
2. Добавьте аннотации `reloader.stakater.com/auto: "true"` к целевым Deployment.
3. Удалите checksum-аннотации из Helm-шаблонов.
4. Настройте `--reload-strategy=annotations` для GitOps-совместимости.
5. Добавьте `reloader.stakater.com/last-reloaded-from` в ignoreDifferences ArgoCD.
6. Протестируйте в staging-окружении перед продакшном.

## Устранение неполадок (Troubleshooting)

### Типичные ошибки и их решения

| Проблема | Вероятная причина | Решение |
| :--- | :--- | :--- |
| **Приложение не перезапускается** | Reloader не отслеживает данный namespace | Проверьте флаги `--namespaces-to-select` / `--namespaces-to-ignore` |
| **Приложение не перезапускается** | Отсутствуют необходимые аннотации | Добавьте `reloader.stakater.com/auto: "true"` или явные аннотации |
| **Приложение не перезапускается** | Проблемы с RBAC | Выполните `kubectl auth can-i patch deployments --as=system:serviceaccount:reloader-system:reloader` |
| **Массовые перезапуски** | Отсутствует debounce | Добавьте `deployment.reloader.stakater.com/pause-period: "1m"` |
| **OutOfSync в ArgoCD** | Используется `env-vars` стратегия | Переключитесь на `--reload-strategy=annotations` |
| **Секреты CSI не отслеживаются** | CSI-интеграция не включена | Добавьте `--enable-csi-integration=true` в аргументы контроллера |
| **Высокая нагрузка на API Server** | Слишком много отслеживаемых ресурсов | Ограничьте namespace через `--namespaces-to-select` |
| **Reloader не стартует** | Неверная конфигурация или нехватка ресурсов | Проверьте логи: `kubectl logs -n reloader-system -l app=reloader` |

### Диагностические команды

```bash
# Проверка состояния контроллера
kubectl get pods -n reloader-system -l app=reloader

# Просмотр логов для поиска событий перезагрузки
kubectl logs -n reloader-system -l app=reloader | grep -i "triggering"

# Проверка RBAC прав
kubectl auth can-i patch deployments --as=system:serviceaccount:reloader-system:reloader -n <namespace>

# Проверка аннотаций на целевом Deployment
kubectl get deployment <name> -n <namespace> -o jsonpath='{.metadata.annotations}' | jq .

# Проверка статусов CSI (если используется)
kubectl get secretproviderclasspodstatuses -n <namespace>
```

### Проверка работоспособности (Health Checks)

Reloader предоставляет HTTP-эндпоинты для проверки состояния:
- `/healthz` — Liveness Probe (проверка жизнеспособности процесса).
- `/readyz` — Readiness Probe (готовность к обработке событий API).
- `/metrics` — Prometheus Metrics (экспорт технических метрик).

## Ограничения и известные проблемы

### Ограничения

- **subPath**: При монтировании файлов через `subPath` изменения не синхронизируются внутри контейнера без перезапуска пода. Reloader — стандартное решение этой проблемы.
- **RBAC**: Требуются права `watch`, `list` для секретов/конфигмапов и `patch`/`update` для рабочих нагрузок. В больших кластерах рекомендуется использовать scoped Roles вместо ClusterRoles.
- **Именованные ConfigMap/Secret**: При использовании явного отслеживания имена ресурсов должны быть указаны точно (без wildcards).
- **Одновременные изменения**: При одновременном изменении нескольких ConfigMap/Secret Reloader выполняет один Rolling Update с обновлением всех зависимостей.

### Известные особенности поведения

- **Дебаунсинг**: Reloader группирует изменения в окне `pause-period` и выполняет один Rolling Update. Это предотвращает "шторм" перезапусков.
- **Идемпотентность**: Контроллер отслеживает состояние и не выполняет повторные обновления при отсутствии реальных изменений.
- **Приоритет аннотаций**: Аннотация `ignore` имеет приоритет над `auto`. Если установлен флаг `--ignore-annotation=true`, эта иерархия нарушается.

## Оценка ресурсов и масштабирование

### Рекомендуемые ресурсы

| Параметр | Малый кластер (<100 namespaces) | Средний кластер (100-500 namespaces) | Большой кластер (>5000 namespaces) |
| :--- | :--- | :--- | :--- |
| **CPU Request** | 100m | 200m | 500m |
| **CPU Limit** | 300m | 500m | 1000m |
| **Memory Request** | 128Mi | 256Mi | 512Mi |
| **Memory Limit** | 512Mi | 1Gi | 2Gi |
| **Реплики (HA)** | 1-2 | 2-3 | 3+ |

### Факторы, влияющие на потребление ресурсов

1. **Количество отслеживаемых объектов**: Каждый ConfigMap/Secret добавляется в кеш контроллера.
2. **Частота обновлений**: Высокая частота изменений увеличивает нагрузку на queue.
3. **Количество рабочих нагрузок**: Каждая аннотация增加了 overhead при сканировании.
4. **Использование CSI**: Интеграция с Secrets Store CSI增加了 дополнительный overhead.

### Оптимизация производительности

- Используйте `--namespaces-to-select` для ограничения области отслеживания.
- Настройте `pause-period` для группировки изменений.
- Мониторьте `workqueue_depth` и `reloader_resource_watch_total`.
- Для больших кластеров рассмотрите горизонтальное масштабирование реплик.

## Миграция между стратегиями

### Переключение с `env-vars` на `annotations`

1. Обновите конфигурацию контроллера: `--reload-strategy=annotations`.
2. Настройте ArgoCD/Flux на игнорирование аннотации `reloader.stakater.com/last-reloaded-from`.
3. Существующие переменные окружения `STAKATER_RELOADER_*` будут удалены при следующем обновлении.

### Переключение с `annotations` на `restart`

1. Обновите конфигурацию контроллера: `--reload-strategy=restart`.
2. Убедитесь, что приложения корректно обрабатывают SIGTERM.
3. Для Argo Rollouts используйте `--is-argo-rollouts=true`.

### Миграция с другого инструмента

1. Установите Reloader параллельно с существующим решением.
2. Постепенно переносите аннотации на Reloader.
3. Убедитесь в корректной работе в staging-окружении.
4. Отключите старое решение после полной миграции.

## Когда НЕ стоит использовать Reloader

Reloader не является универсальным решением. Существуют сценарии, где использование контроллера избыточно, рискованно или менее эффективно альтернатив.

### Сценарии, где Reloader не нужен

| Сценарий | Почему не нужен | Альтернатива |
| :--- | :--- | :--- |
| **Приложение поддерживает hot reload** | Приложение само перечитывает конфигурацию без перезапуска (Nginx с `reload`, Envoy, Prometheus) | Ничего — приложение само реагирует на изменения |
| **GitOps с Helm checksum** | `helm upgrade` уже триггерит перезапуск через checksum аннотацию | Helm checksum (`checksum/config`) |
| **Kustomize с configMapGenerator** | Kustomize хеширует имя ConfigMap, что заставляет Kubernetes выполнить Rolling Update | Kustomize `configMapGenerator` |
| **Используется ArgoCD с Resource Hooks** | ArgoCD может выполнить `PreSync`/`PostSync` хуки для restart | ArgoCD Resource Hooks |
| **Infrequent changes (раз в месяц/год)** | Контроллер — лишний overhead для редких изменений | Ручной `kubectl rollout restart` |
| **Стоимость контроля выше стоимости проблемы** | Для dev/staging сред, где перезапуск не критичен | Manual intervention |

### Сравнение с альтернативами

| Подход | Механизм | Hot Reload | GitOps | Сложность | Overhead |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Reloader** | Controller watch | Да | Да (annotations) | Средняя | Контроллер + ресурсы |
| **Helm Checksum** | Template hash | Нет | Да | Низкая | Нет |
| **Kustomize Hash** | Name suffix | Нет | Да | Низкая | Нет |
| **ArgoCD Hooks** | PreSync/PostSync | Нет | Да | Средняя | Нет |
| **Custom Controller** | Свой reconciler | Да | Да | Высокая | Свой контроллер |
| **ConfigMap/Secret immutable** | Новая версия объекта | Нет | Да | Низкая | Нет |

### Когда Reloader предпочтителен

1. **Приложения не поддерживают hot reload** — большинство legacy и stateless-приложений
2. **Изменения происходят вне deploy** — ротация секретов, обновление через внешние системы (Vault, CSI Driver)
3. **Нужна реакция в реальном времени** — не только при `helm upgrade` или `kubectl apply`
4. **Множество зависимостей** — приложение зависит от 5+ ConfigMap/Secret, ручное управление аннотациями громоздко
5. **Argo Rollouts** — интеграция с Canary/Blue-Green стратегиями
