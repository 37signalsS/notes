## Практические сценарии

### 1. Создание собственного репозитория

Helm-репозиторий — это HTTP-сервер, который отдает YAML-файл `index.yaml` и упакованные чарты (`.tgz`).

**Ключевые требования:**

1. HTTP-сервер, способный обслуживать файлы YAML и `.tgz` по GET-запросам.
2. Наличие файла `index.yaml`, который содержит метаданные обо всех чартах в репозитории.
3. Опционально: файлы `.prov` для верификации чартов.

**Рабочий процесс:**

1. **Упаковка чарта:** Создается `.tgz` архив из директории чарта.

    ```bash
    helm package ./my-chart
    ```

2. **Создание/обновление индекса:** Генерируется или обновляется `index.yaml` с информацией о чартах в текущей директории.

    ```bash
    helm repo index . --url https://my-repo.com/charts
    ```

3. **Публикация:** Архив `.tgz` и файл `index.yaml` загружаются на HTTP-сервер.

### 2. Гибридное использование с Kustomize

Для сложных проектов эффективен гибридный подход: **Helm** используется как шаблонизатор, а **[Kustomize](../kustomize_overview.md)** — для наложения патчей, специфичных для окружения.

**Структура проекта:**

```
k8s-project/
├── base/         # Базовые манифесты, сгенерированные `helm template`
├── overlays/     # Патчи для окружений (dev, prod)
└── helm/         # Исходный Helm-чарт
```

**Рабочий процесс:**

1. **Генерация базы:** `helm template` создает "сырые" Kubernetes-манифесты из чарта.

    ```bash
    helm template my-release ./helm > ./base/resources.yaml
    ```

2. **Применение патчей:** `kubectl apply -k` использует Kustomize для применения патчей к базовым манифестам перед отправкой в кластер.

    ```bash
    kubectl apply -k overlays/dev
    ```

Этот подход сочетает гибкость шаблонов Helm и декларативность патчей Kustomize, позволяя избежать сложной логики в чартах.

### 3. Создание адаптивных ("умных") шаблонов

Шаблоны Helm позволяют не просто вставлять значения, но и создавать логику, которая адаптирует манифесты под окружение, в частности, под версию Kubernetes. Это ключевой аспект создания по-настоящему переиспользуемых и надежных чартов.

#### Пример: Адаптивный Ingress-шаблон

Шаблон `ingress.yaml`, генерируемый командой `helm create`, является отличным примером "умного" шаблона. Он решает несколько проблем совместимости "из коробки".

**Адаптация `apiVersion`:**

API для Ingress менялся несколько раз (`extensions/v1beta1` → `networking.k8s.io/v1beta1` → `networking.k8s.io/v1`). Шаблон использует встроенный объект `.Capabilities` для выбора корректной версии API, поддерживаемой кластером.

```yaml
{{- $kubeVersion := .Capabilities.KubeVersion.Version -}}
{{- if semverCompare ">=1.19-0" $kubeVersion -}}
apiVersion: networking.k8s.io/v1
{{- else if semverCompare ">=1.14-0" $kubeVersion -}}
apiVersion: networking.k8s.io/v1beta1
{{- else -}}
apiVersion: extensions/v1beta1
{{- end }}
kind: Ingress
...
```
- `.Capabilities.KubeVersion.Version` получает семантическую версию Kubernetes.
- `semverCompare` сравнивает версии, позволяя выстроить логическую цепочку.

**Динамическое управление `ingressClassName`:**

До Kubernetes 1.18 класс ингресса указывался через аннотацию. Начиная с 1.18, появилось специальное поле `spec.ingressClassName`. Шаблон элегантно обрабатывает оба случая.

```yaml
...
metadata:
  annotations:
    {{- if and .Values.ingress.className (not (semverCompare ">=1.18-0" .Capabilities.KubeVersion.Version)) }}
    {{- if not (hasKey .Values.ingress.annotations "kubernetes.io/ingress.class") }}
    {{- $_ := set .Values.ingress.annotations "kubernetes.io/ingress.class" .Values.ingress.className}}
    {{- end }}
    {{- end }}
    {{- with .Values.ingress.annotations }}
    {{- toYaml . | nindent 4 }}
    {{- end }}
spec:
  {{- if and .Values.ingress.className (semverCompare ">=1.18-0" .Capabilities.KubeVersion.Version) }}
  ingressClassName: {{ .Values.ingress.className }}
  {{- end }}
...
```
- **Логика для старых версий (K8s < 1.18):**
    1. Проверяется, что `ingress.className` задан и версия кластера < 1.18.
    2. `hasKey` проверяет, не задал ли пользователь аннотацию `kubernetes.io/ingress.class` вручную.
    3. Если нет, `set` динамически **добавляет** эту аннотацию в словарь `.Values.ingress.annotations` перед его рендерингом через `toYaml`.
- **Логика для новых версий (K8s >= 1.18):**
    1. Проверяется, что `ingress.className` задан и версия кластера >= 1.18.
    2. Если да, рендерится поле `ingressClassName` в спецификации.

**Манипуляция строками с `printf`:**

Иногда имя ресурса, на который нужно сослаться, отличается от имени релиза. Например, сервис может называться `my-release-svc`. Функция `printf` позволяет конструировать такие строки на лету.

```yaml
...
{{- $fullName := include "mychart.fullname" . -}}
{{- $svcPort := .Values.service.port -}}
{{- $svcName := printf "%s-svc" $fullName -}}

...
backend:
  service:
    name: {{ $svcName }}
    port:
      number: {{ $svcPort }}
...
```
Здесь переменной `$svcName` присваивается результат форматирования строки — к полному имени релиза добавляется суффикс `-svc`.

Эти техники позволяют создавать универсальные чарты, которые работают в разных окружениях без необходимости ручной правки.

## Дополнительная информация

### Инструменты для оркестрации

Для декларативного управления множеством Helm-релизов (Infrastructure as Code) используются специализированные инструменты:

* **[Helmfile](./helmfile_overview.md)**: Популярный оркестратор, использующий `helmfile.yaml` для описания желаемого состояния релизов.
* **[Helmwave](./helmwave_overview.md)**: Более гибкая альтернатива, которая использует Go-шаблоны для всей конфигурации, обеспечивая максимальную динамичность.

### Плагины

Функциональность Helm расширяется с помощью плагинов. Один из самых востребованных — **[helm-diff](../helm_plugins.md#helm-diff)**, который позволяет просматривать изменения (`diff`) перед применением обновления.

## 4. Частые проблемы и паттерны их решения

При создании сложных чартов возникают неочевидные проблемы, требующие продуманных архитектурных решений.

### Проблема "Курицы и Яйца": Конфигурация, зависящая от состояния кластера

**Проблема:** Приложению внутри `ConfigMap` требуется параметр, значение которого генерируется Kubernetes уже **после** создания ресурсов. Классический пример — внешний URL приложения, который должен включать `NodePort` сервиса. Однако `NodePort` назначается кластером динамически и неизвестен на этапе `helm install`.

**Анти-паттерн:** Пытаться "угадать" или вычислить это значение с помощью сложных и хрупких конструкций в шаблонах.

**Решение: Явное конфигурирование.**

Надежный способ — переложить ответственность за предоставление этого значения на пользователя.

1.  **Сделайте параметр обязательным в `values.yaml`**. Вместо того чтобы пытаться вычислить URL, создайте в `values.yaml` явное поле, например, `app.baseUrl`.
2.  **Используйте `required` для валидации**. В шаблоне `ConfigMap` используйте функцию `required`, чтобы установка завершалась с ошибкой, если пользователь не предоставил это значение.

**values.yaml:**
```yaml
# Требуется указать полный базовый URL для доступа к приложению
app:
  baseUrl: "" 
```

**templates/configmap.yaml:**
```yaml
data:
  #...
  APP_BASE_URL: {{ required "Необходимо указать app.baseUrl в values.yaml" .Values.app.baseUrl | quote }}
  #...
```
**Преимущества:**
- **Надежность:** Чарт не зависит от непредсказуемого состояния кластера.
- **Гибкость:** Пользователь может указать любой URL, соответствующий его окружению (например, URL за прокси-сервером или `LoadBalancer`).
- **Прозрачность:** Конфигурация становится явной и понятной.

### Синхронизация конфигурации между ресурсами

**Проблема:** Один и тот же параметр конфигурации требуется в нескольких местах. Например, путь монтирования тома (`mountPath`) должен быть указан и в `spec.containers.volumeMounts` у `Deployment` или `StatefulSet`, и в `ConfigMap`, который передается приложению.

**Анти-паттерн:** Жестко кодировать значение в обоих местах. Это приводит к рассинхронизации при изменениях.

**Решение: Единый источник истины (SSoT) в `values.yaml`.**

1.  **Определите параметр в `values.yaml` один раз.**

    **values.yaml:**
    ```yaml
    volumes:
      data:
        # Этот путь будет использоваться и для volumeMounts, и для конфига приложения
        mountPath: /var/lib/data 
    ```

2.  **Ссылайтесь на это значение во всех необходимых шаблонах.**

    **templates/deployment.yaml:**
    ```yaml
    ...
    spec:
      containers:
      - volumeMounts:
        - name: data-volume
          mountPath: {{ .Values.volumes.data.mountPath }}
    ...
    ```

    **templates/configmap.yaml:**
    ```yaml
    ...
    data:
      APP_DATA_PATH: {{ .Values.volumes.data.mountPath | quote }}
    ...
    ```

**Преимущества:**
- **Консистентность:** Изменение параметра в `values.yaml` автоматически применяется ко всем зависимым ресурсам.
- **Упрощение рефакторинга:** Конфигурация находится в одном месте, что облегчает её изменение.
- **Снижение ошибок:** Исключается возможность опечаток или забытых изменений при ручном редактировании нескольких файлов.
