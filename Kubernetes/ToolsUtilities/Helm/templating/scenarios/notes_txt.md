# Инструкции NOTES.txt в Helm-чартах

---

## Определения

**NOTES.txt** — специализированный файл в директории `templates/` чарта, содержимое которого рендерится движком Go templates и выводится в стандартный поток вывода (stdout) после завершения операций `helm install`, `helm upgrade` или `helm rollback`.

**Пост-инсталляционные заметки (Post-installation notes)** — динамический интерфейс взаимодействия с пользователем, предназначенный для предоставления инструкций по быстрому старту, получению доступов и проверке статуса развёрнутых ресурсов.

**Метаданные заметок** — текст после рендеринга сохраняется как часть данных релиза в Secret (или ConfigMap, если релиз публичный) внутри кластера. Физически заметки хранятся в поле `data` объекта Secret в закодированном виде (base64).

**Субчартовые заметки** — `NOTES.txt` из зависимых чартов (subcharts), которые не выводятся по умолчанию и требуют флага `--render-subchart-notes`.

**Шаблон заметок** — Go template с доступом ко всем встроенным объектам Helm (`.Release`, `.Chart`, `.Values`, `.Files`, `.Capabilities`, `.Template`), но без доступа к `.Capabilities.KubeVersion` для некоторых операций в песочнице.

---

## Основные концепции

### Технические особенности

- **Произвольный формат:** В отличие от манифестов, `NOTES.txt` не обязан соответствовать структуре YAML. Это текстовый файл, поддерживающий полную мощь Go templates и функций Sprig.
- **Хранение в метаданных:** Текст заметок сохраняется как часть данных релиза в Secret (или ConfigMap) внутри кластера. Его можно просмотреть в любой момент командой `helm get notes <release>`.
- **Локальный рендеринг:** Ошибки синтаксиса в `NOTES.txt` являются блокирующими и прерывают процесс установки или обновления чарта.
- **Кодировка:** Файл должен быть сохранён в кодировке UTF-8.

### Жизненный цикл и интеграция с операциями Helm

NOTES.txt участвует в жизненном цикле релиза синхронно с рендерингом манифестов:

| Операция | Время рендеринга NOTES.txt | Особенности |
|----------|---------------------------|-------------|
| `helm install` | После успешного применения всех ресурсов (при использовании `--wait`) или сразу после отправки манифестов в API | Выводится после создания релиза |
| `helm upgrade` | После успешного применения новой ревизии | Заменяет предыдущие заметки |
| `helm rollback` | После восстановления предыдущей ревизии | Отображаются заметки из целевой ревизии |
| `helm template` | При локальном рендеринге без создания релиза | Выводится в stdout вместе с манифестами |

**Важно:** NOTES.txt не является хуком. Хуки (`pre-install`, `post-install` и т.д.) выполняются в рамках жизненного цикла релиза, но NOTES.txt рендерится и выводится после завершения основной операции. Если хук завершается с ошибкой, NOTES.txt не выводится, так как релиз переходит в статус `failed`.

### Порядок рендеринга и зависимость от .Files

- Файл загружается и парсится на этапе слияния шаблонов (template discovery).
- Рендеринг происходит после слияния всех `values.yaml` (родительского чарта и субчартов), но до валидации манифестов.
- `.Files.Get` в NOTES.txt работает с файлами из директории `files/` чарта, но **не** имеет доступа к файлам субчартов.
- При использовании `--dry-run` NOTES.txt рендерится локально, без обращения к API кластера (исключение: функция `lookup`).

### Управление выводом и область видимости

| Команда / Параметр | Функциональное назначение |
|--------------------|--------------------------|
| `helm status <name>` | Позволяет повторно отобразить заметки для активного релиза. |
| `--render-subchart-notes` | По умолчанию Helm выводит заметки только родительского чарта. Этот флаг активирует рендеринг `NOTES.txt` из всех зависимых чартов (subcharts). |
| `--debug` | При использовании с `helm install` или `template` позволяет увидеть процесс рендеринга заметок. |
| Пустой файл | Если файл отсутствует или не содержит текста после рендеринга, секция `NOTES` в выводе Helm не отображается. |

### Объект .Template и именованные шаблоны

В NOTES.txt доступен объект `.Template` с методами:
- `.Template.BasePath` — путь к директории шаблонов (обычно `templates`).
- `.Template.Name` — имя текущего шаблона (`NOTES.txt`).

Это позволяет использовать `include` для вызова именованных шаблонов из `_helpers.tpl`, что критично для DRY-подхода в больших чартах:

```text
{{- include "mychart.labels" . | nindent 4 }}
```

**Важно:** Именованные шаблоны, определённые в субчартах, доступны только если субчарт объявлен в `dependencies` и его `_helpers.tpl` загружен. Конфликты имён разрешаются в пользу родительского чарта.

### Хранение в Secret и лимиты

- Заметки хранятся в Secret вида `<release-name>.helm.sh/v1` в namespace релиза.
- Размер Secret ограничен 1 МБ (лимит etcd на объект).
- При превышении лимита `helm upgrade` завершается ошибкой: `Error: UPGRADE FAILED: cannot patch "<name>" with kind Secret`.
- Решение: вынести большие блоки текста в отдельные ConfigMap или использовать `.Files.Get` для вставки содержимого из `files/`.

### Взаимодействие с хуками жизненного цикла

| Хук | Влияние на NOTES.txt |
|-----|----------------------|
| `pre-install` | Выполняется до рендеринга манифестов. NOTES.txt ещё не выводится. |
| `post-install` | Выполняется после применения манифестов, но до вывода NOTES.txt (если не используется `--wait`). |
| `pre-upgrade` / `post-upgrade` | Аналогично install, но для операций обновления. |
| `pre-rollback` / `post-rollback` | Заметки выводится после завершения rollback. |

При использовании флага `--wait` Helm ожидает готовности всех ресурсов перед выводом NOTES.txt. Если ресурс не достигает готовности за `--timeout`, операция прерывается, и NOTES.txt не выводится.

## Практические сценарии

### Динамические инструкции по доступу

Использование условий для вывода команд в зависимости от типа сервиса или наличия Ingress.

```text
{{- $fullName := include "myapp.fullname" . -}}
Приложение {{ .Chart.Name }} успешно развёрнуто!

{{- if .Values.ingress.enabled }}
Доступ к веб-интерфейсу:
{{- range .Values.ingress.hosts }}
  http://{{ .host }}{{ (index .paths 0).path }}
{{- end }}
{{- else if eq .Values.service.type "NodePort" }}
Получение URL через NodePort:
  export NODE_PORT=$(kubectl get --namespace {{ .Release.Namespace }} -o jsonpath="{.spec.ports[0].nodePort}" services {{ $fullName }})
  export NODE_IP=$(kubectl get nodes --namespace {{ .Release.Namespace }} -o jsonpath="{.items[0].status.addresses[0].address}")
  echo http://$NODE_IP:$NODE_PORT
{{- else if eq .Values.service.type "LoadBalancer" }}
Ожидание внешнего IP (может занять 2-5 минут):
  kubectl get svc --namespace {{ .Release.Namespace }} {{ $fullName }} -w
{{- else }}
Локальный доступ (Port-Forwarding):
  kubectl --namespace {{ .Release.Namespace }} port-forward svc/{{ $fullName }} 8080:{{ .Values.service.port }}
  Затем откройте: http://127.0.0.1:8080
{{- end }}
```

### Безопасное извлечение секретов

Никогда не выводите пароли в открытом виде. Используйте команды для их безопасного получения из кластера.

```text
{{- $secretName := printf "%s-auth" (include "myapp.fullname" .) -}}
Данные для авторизации (Admin):

  Пользователь: {{ .Values.adminUser | default "admin" }}
  Пароль (выполните команду):
    kubectl get secret --namespace {{ .Release.Namespace }} {{ $secretName }} -o jsonpath="{.data.password}" | base64 -d; echo
```

### Валидация состояния ресурсов (kubectl wait)

Полезно предоставить пользователю команду, которая позволит дождаться готовности приложения.

```text
Проверка готовности подов:
  kubectl wait --namespace {{ .Release.Namespace }} \
    --for=condition=ready pod \
    --selector=app.kubernetes.io/instance={{ .Release.Name }} \
    --timeout=90s
```

### Нюансы использования lookup

Функция `lookup` работает только при наличии соединения с кластером и не возвращает данных при первом деплое (так как ресурсы ещё не созданы).

```text
{{- $svc := (lookup "v1" "Service" .Release.Namespace (include "myapp.fullname" .)) -}}
{{- if and $svc $svc.status.loadBalancer.ingress }}
  {{- $ingress := index $svc.status.loadBalancer.ingress 0 -}}
Публичный адрес: {{ default $ingress.ip $ingress.hostname }}
{{- else }}
Внешний адрес ещё не назначен или вы используете --dry-run.
{{- end }}
```

### Многоокружевая стратегия вывода

Для чартов, развёртываемых в dev/staging/production, контекстуализируйте вывод в зависимости от окружения:

```text
{{- if eq .Values.environment "production" }}
ПРОDUCTION-режим
Включены расширенные метрики и audit-log.
{{- else if eq .Values.environment "staging" }}
STAGING-режим
Данные регулярно очищаются.
{{- else }}
DEV-режим
Используйте port-forward для доступа.
{{- end }}
```

### Интеграция с CI/CD и парсинг вывода

Для автоматизации в пайплайнах используйте markers для детерминированного парсинга:

```text
{{- printf "# NOTES_BEGIN" }}
Release: {{ .Release.Name }}
Namespace: {{ .Release.Namespace }}
Chart: {{ .Chart.Name }}-{{ .Chart.Version }}
Revision: {{ .Release.Revision }}
{{- if .Values.ingress.enabled }}
URL: {{ index .Values.ingress.hosts 0 }}
{{- end }}
{{- printf "# NOTES_END" }}
```

В CI/CD скриптах:
```bash
# Извлечение URL из NOTES.txt
HELM_NOTES=$(helm get notes myapp -n production)
APP_URL=$(echo "$HELM_NOTES" | awk '/URL:/ {print $2}')

# Передача в следующий stage pipeline
echo "APP_URL=$APP_URL" >> deploy.env
```

### Вывод списка ресурсов и их статусов

Для оперативного аудита предоставьте команду получения всех ресурсов релиза:

```text
Все ресурсы релиза:
  kubectl get all,secret,configmap,serviceaccount,role,rolebinding \
    --namespace {{ .Release.Namespace }} \
    -l app.kubernetes.io/instance={{ .Release.Name }}
```

### Работа с ConfigMap и файлами конфигурации

Если чарт включает configuration файлы через `.Files.Get`, укажите команды для их просмотра:

```text
{{- $config := .Files.Get "conf/app.properties" -}}
{{- if $config }}
Конфигурация приложения сохранена в ConfigMap.
Просмотр:
  kubectl get configmap {{ $fullName }}-config \
    --namespace {{ .Release.Namespace }} \
    -o jsonpath="{.data.app\.properties}"
{{- end }}
```

### Валидация через helm test и smoke-проверки

Интегрируйте инструкции по запуску встроенных тестов Helm:

```text
Запуск smoke-тестов:
  helm test {{ .Release.Name }} --namespace {{ .Release.Namespace }}

Ожидание готовности (ручная проверка):
  kubectl wait --for=condition=ready pod \
    --selector=app.kubernetes.io/instance={{ .Release.Name }} \
    --namespace {{ .Release.Namespace }} \
    --timeout=120s
```

### Сценарии отката (rollback) и аудит

Укажите пользователю команды для просмотра истории и отката:

```text
История изменений:
  helm history {{ .Release.Name }} --namespace {{ .Release.Namespace }}

Откат к предыдущей версии:
  helm rollback {{ .Release.Name }} 1 --namespace {{ .Release.Namespace }}
```

### Безопасность: исключение чувствительных данных

Соблюдайте правила при выводе информации в NOTES.txt:

- **Запрещено:** Пароли, токены, ключи SSH/TLS в открытом виде.
- **Разрешено:** Команды безопасного извлечения через `kubectl get secret ... -o jsonpath`.
- **Рекомендуется:** Указывать имена Secret и ConfigMap, но не их содержимое.
- **Внимание:** Заметки хранятся в Secret без шифрования at-rest (зависит от конфигурации etcd). Не храните в NOTES.txt данные, которые нельзя показать любому пользователю с доступом `get secret` в namespace.

### Онлайн- и офлайн-среды

При деплое в air-gapped средах учитывайте:

- Функция `lookup` не работает без подключения к API-серверу.
- `helm get notes` требует доступа к кластеру.
- Для CI/CD в изолированных сетях сохраняйте NOTES.txt в артефакты пайплайна для последующего распространения.

## Дополнительная информация

### Лучшие практики

- **Минимизация объема:** `NOTES.txt` не является заменой `README.md`. Выводите только те данные, которые уникальны для конкретной инсталляции.
- **Проверка зависимостей:** Если вы используете субчарты, информируйте пользователя о необходимости флага `--render-subchart-notes`, если их заметки важны.
- **Табличное форматирование:** Для выравнивания списков используйте функцию `printf`. Например: `{{ printf "%-20s %s" "Namespace:" .Release.Namespace }}`.
- **DRY в заметках:** Если блок текста повторяется или слишком велик, выносите его в именованный шаблон в `_helpers.tpl` и вставляйте через `{{ include "..." . }}`.
- **Тестирование заметок:** Используйте `helm template` для локальной проверки вывода NOTES.txt без установки чарта:
  ```bash
  helm template myapp ./mychart | grep -A 20 "NOTES"
  ```
- **Валидация в CI/CD:** Добавьте `helm lint` и `helm template` в пайплайн для проверки синтаксиса NOTES.txt на этапе сборки.
- **Консистентность имен:** Используйте `include "mychart.fullname" .` вместо хардкода имён сервисов и Secret. Это обеспечивает согласованность между манифестами и заметками.
- **Обработка ошибок:** Указывайте пользователю диагностические команды при типичных проблемах (например, `kubectl describe pod`, `kubectl logs`).

### Устранение неисправностей

| Проблема | Вероятная причина | Решение |
|----------|-------------------|---------|
| Заметки не выводятся | Пустой результат рендеринга или ошибка в имени файла | Убедитесь, что файл называется именно `NOTES.txt` и находится в `templates/`. |
| Ошибка рендеринга при деплое | Синтаксическая ошибка в Go templates внутри заметок | Используйте `helm template --debug` для локальной проверки вывода. |
| `lookup` всегда возвращает `nil` | Использование флага `--dry-run` или отсутствие прав у ServiceAccount | `lookup` требует живого соединения с API-сервером. |
| Заметки субчартов не выводятся | Флаг `--render-subchart-notes` не указан | Добавьте флаг при установке/обновлении. |
| Рендеринг зависает на `include` | Циклическая зависимость в `_helpers.tpl` или очень большая структура `.Values` | Проверьте helpers на рекурсию. Ограничьте глубину `range` в NOTES.txt. |
| Заметки содержат мусор ({{ }}) | Не хватает дефисов для управления пробелами (`{{-` / `-}}`) | Добавьте дефисы для обрезки лишних переносов строк. |
| Размер Secret превышает 1 МБ | Слишком большие NOTES.txt или много ресурсов в чарте | Вынесите большой текст в ConfigMap или используйте `.Files.Get`. |
| Пароль выводится в открытом виде | Разработчик забыл заменить вывод на команду `kubectl get secret` | Проверьте чарт на предмет утечек секретов через NOTES.txt. |
