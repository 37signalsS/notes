# Обзор сценариев шаблонизации Helm

---

## Определения

**Сценарии шаблонизации** — это классифицированные архитектурные паттерны и практические методики применения движка Go templates в Helm для динамической генерации манифестов Kubernetes. Сценарии охватывают широкий спектр задач: от базовой параметризации до сложной логики адаптации под возможности кластера и управления жизненным циклом ресурсов.

**Паттерны проектирования чартов** — проверенные подходы к организации кода шаблонов, обеспечивающие соблюдение принципов DRY (Don't Repeat Yourself), идемпотентности и безопасности развёртывания.

**Движок рендеринга (Rendering Engine)** — двухпроходный механизм Helm. На первом этапе происходит парсинг всех файлов `templates/*.yaml` и `_helpers.tpl` в абстрактное синтаксическое дерево (AST). На втором этапе выполняется подстановка значений из объединённой карты `.Values`, интроспекция через встроенные объекты (`.Release`, `.Chart`, `.Capabilities`, `.Files`) и генерация итоговых YAML-манифестов.

**Область видимости (Scope)** — контекст данных, доступный текущему выражению в шаблоне. Helm различает глобальную область (`$`, корневой объект) и локальную область (`.`), которая изменяется внутри блоков `range`, `with` и `define`. Некорректное управление scope — одна из наиболее частых причин ошибок `nil pointer evaluating`.

**Именованный шаблон (Named Template)** — переиспользуемый фрагмент логики, объявленный через `define` (обычно в `_helpers.tpl`) и вызываемый через `include`. Обеспечивает инкапсуляцию, DRY и централизованное управление метками, селекторами и именами.

**Валидационная pipeline** — последовательность статических и динамических проверок чарта: `helm lint` (синтаксис и схема), `helm template` (рендеринг), `helm install --dry-run` (API-валидация), юнит-тесты (`helm-unittest`). Наличие pipeline снижает риск деплоя нерабочих конфигураций в production.

## Архитектура и основные концепции

### Двухпроходный рендеринг

Helm не выполняет простую подстановку переменных. Перед генерацией манифестов происходит:

1. **Парсинг:** Все шаблоны загружаются и проверяются на синтаксическую корректность.
2. **Слияние значений:** Из различных источников (`values.yaml`, `-f` файлы, `--set`, глобальные значения субчартов) формируется единая карта `.Values` по алгоритму глубокого слияния (deep merge) для словарей и полного замещения для списков.
3. **Выполнение:** Движок Go templates обходит AST, вычисляет выражения, вызывает функции Sprig и Helm, подставляет значения встроенных объектов.
4. **Валидация:** Результат сериализуется в YAML и проверяется на соответствие схеме `values.schema.json` (если присутствует).

### Порядок обнаружения и загрузки шаблонов

Helm загружает файлы из директории `templates/` в алфавитном порядке. Этот порядок имеет значение для:
- **Конфликтов имён:** Если два файла определяют шаблон с одинаковым именем через `define`, последний загруженный переопределяет предыдущий. В практике это означает, что `_helpers.tpl` (имеющий префикс `_` и загружаемый первым) может быть переопределён файлом с именем, идущим после него в алфавитном порядке.
- **Зависимости:** Шаблоны, вызываемые через `include`, должны быть определены до момента их первого вызова. Helm выполняет полный парсинг всех `define` перед рендерингом, поэтому взаимозависимости разрешаются корректно при условии уникальности имён.

**Правило для SRE:** Всегда проверяйте алфавитный порядок файлов в `templates/` при добавлении новых `define`. Используйте префикс `_` для файлов с хелперами, чтобы обеспечить детерминированный порядок загрузки.

### Объект .Template

Помимо `.Values`, `.Release`, `.Chart` и `.Capabilities`, Helm предоставляет объект `.Template`, содержащий метаданные о текущем процессе рендеринга:

- **`.Template.BasePath`**: Абсолютный путь к директории `templates/` текущего чарта. Используется для построения путей к файлам в пайплайнах с `include` (например, для checksum-аннотаций).
- **`.Template.Name`**: Полное имя текущего шаблона в формате `CHART_NAME/templates/FILE_NAME`. Полезно для отладки и создания уникальных имён ресурсов.

### Комментирование в шаблонах

Helm поддерживает однострочные и многострочные комментарии внутри `{{ }}`:

```yaml
{{- /* Этот комментарий не попадёт в итоговый YAML */ -}}
{{- /* 
   Многострочный комментарий
   для документации логики
*/ -}}
```

**Важно для DevOps:** Комментарии внутри `{{-` и `-}}` полностью удаляются на этапе парсинга и не влияют на размер итоговых манифестов. Однако строки комментариев, размещённые вне фигурных скобок (в чистом YAML), останутся в сгенерированных ресурсах и будут видны через `kubectl get ... -o yaml`.

### Область видимости (Scope)

В Helm существует два контекста доступа к данным:

- **Глобальный (`$`)** — неизменная ссылка на корневой объект. Используется внутри `range`, `with` и вложенных `include` для доступа к `.Release.Name`, `.Values.global` и другим корневым свойствам.
- **Локальный (`.`)** — изменяется в зависимости от текущего блока. Внутри `with .Values.resources` точка `.` указывает на `.Values.resources`, а не на корень.

**Правило для SRE:** При потере контекста (ошибка `nil pointer evaluating field Release`) всегда используйте `$.Release` вместо `.Release` внутри циклов и `with`.

### Интеграция с жизненным циклом релиза

Шаблонизация тесно связана с операциями Helm:

| Операция | Влияние на шаблоны |
|----------|-------------------|
| `helm install` | Рендерит все шаблоны, создаёт релиз в Secret. Срабатывают `pre-install` и `post-install` хуки. |
| `helm upgrade` | Перерендеривает шаблоны с новыми значениями, обновляет ресурсы через SSA. Срабатывают `pre-upgrade` и `post-upgrade` хуки. |
| `helm rollback` | Восстанавливает манифесты предыдущей ревизии, перерендеривает их. Срабатывают `pre-rollback` и `post-rollback` хуки. |
| `helm test` | Запускает ресурсы из `templates/tests/` с аннотацией `helm.sh/hook: test`. |
| `helm uninstall` | Удаляет все ресурсы релиза (кроме помеченных `helm.sh/resource-policy: keep`). Срабатывает `pre-delete` и `post-delete` хуки. |

### Ключевые принципы реализации

- **Типизация и валидация:** строгое использование типов данных в `values.yaml` и проверка обязательных параметров через `required` и `values.schema.json`.
- **Контекстная изоляция:** правильное управление областями видимости (Scope) при вызове функций и циклов. Использование глобального `$` для доступа к корневым объектам внутри локальных блоков.
- **Адаптивность:** использование интроспекции кластера через `.Capabilities` для обеспечения совместимости между разными версиями Kubernetes.
- **Автоматизация изменений:** внедрение механизмов отслеживания изменений в конфигурациях для автоматического обновления подов (checksum-аннотации, Reloader).
- **Детерминированность:** избегание недетерминированных функций (`now`, `randAlphaNum`, `randNumeric`) в хешируемых аннотациях и конфигурациях, чтобы предотвратить ложные срабатывания Rolling Update.
- **Сетевой контекст:** учёт политик сети (NetworkPolicy) при проектировании шаблонов для приложений, работающих в сегментированных окружениях.

## Интеграция с CI/CD и многокомпонентные стратегии

### Pipeline валидации чарта в CI/CD

Для SRE и DevOps-инженеров автоматизация проверок чарта — часть обязательного pipeline перед деплоем в production. Минимальный набор стадий:

```yaml
# .gitlab-ci.yml (аналогично для GitHub Actions, Jenkins)
stages:
  - lint
  - test
  - build
  - deploy

helm:lint:
  stage: lint
  image: alpine/helm:3.22.0
  script:
    - helm lint ./my-chart --strict
    - helm template my-release ./my-chart -f values.yaml | kubeconform --strict

helm:test:
  stage: test
  image: alpine/helm:3.22.0
  script:
    - helm unittest ./my-chart

helm:diff:
  stage: build
  image: alpine/helm:3.22.0
  script:
    - helm dependency build ./my-chart
    - helm diff upgrade my-release ./my-chart -f values.yaml --allow-unreleased
```

**Обоснование для SRE:**
- `helm lint` проверяет синтаксис и структуру без доступа к кластеру.
- `kubeconform` валидирует рендеренные YAML-манифесты по JSON-схемам Kubernetes API.
- `helm diff` показывает точные изменения перед применением, что критично для compliance и аудита.
- `helm unittest` обеспечивает покрытие логики шаблонов тестами.

### Многоокружная стратегия деплоя

Паттерн «один чарт — много окружений» требует аккуратной организации `values`:

```bash
# Базовый values.yaml (дефолты для dev)
helm upgrade --install app ./chart -f values.yaml

# Продакшен (наложение production.yaml поверх базового)
helm upgrade --install app ./chart \
  -f values.yaml \
  -f values-production.yaml \
  --namespace prod \
  --atomic \
  --timeout 5m
```

**Порядок слияния критичен:** файлы, переданные через `-f`, применяются в указанном порядке. Последний файл имеет наивысший приоритет при конфликтах ключей. Для переопределения отдельных ключей без дублирования всего объекта используйте патч-файлы.

### Канареечный и сине-зелёный деплой через Helm

Helm не предоставляет встроенных стратегий канареечного деплоя, но шаблоны могут быть адаптированы под Argo Rollouts или Flux:

```yaml
# values.yaml
rollout:
  enabled: false
  steps:
    - setWeight: 10
    - pause: {duration: 1m}

# templates/rollout.yaml (если rollout.enabled)
{{- if .Values.rollout.enabled }}
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: {{ include "myapp.fullname" . }}
spec:
  replicas: {{ .Values.replicaCount }}
  strategy:
    canary:
      steps: {{ toYaml .Values.rollout.steps | nindent 4 }}
{{- end }}
```

Для SRE важно: чарт должен оставаться применимым и без Argo Rollouts (условное включение ресурса через `if`), чтобы не нарушать стандартный деплой через `helm upgrade`.

### Интеграция с GitOps (ArgoCD / Flux)

При использовании GitOps-подхода обратите внимание на:
- **Helm-режим ArgoCD:** рендеринг происходит на стороне ArgoCD, а не Helm. Конфигурация передаётся через `values.yaml` в репозитории. Убедитесь, что чарт не вызывает внешних команд (`exec`) в hooks — это нарушает принцип GitOps.
- **Helm-режим Flux:** аналогично, используется `helm-template` для генерации манифестов. Проверяйте совместимость с `--api-versions` в автоматизации.
- **Helm Chart Refresh:** для ArgoCD настройте `Helm Repository` с polling, чтобы автоматически подхватывать новые версии чартов.

## Валидация и контроль качества

### Pipeline проверок чарта

Для production-grade развёртываний рекомендуется выполнять как минимум четыре уровня проверок:

```bash
# 1. Статический анализ: синтаксис, структура, значения по умолчанию
helm lint ./my-chart --strict

# 2. Локальный рендеринг: визуальный аудит итоговых YAML
helm template my-release ./my-chart -f values.yaml

# 3. Валидация манифестов: проверка по JSON-схемам Kubernetes API
helm template my-release ./my-chart -f values.yaml | kubeconform --strict

# 4. Сухой запуск: валидация через API сервера кластера (проверка версий API, RBAC)
helm install my-release ./my-chart -f values.yaml --dry-run --debug
```

**SRE-контекст:** Этап 3 (`kubeconform`) критичен для on-premise и air-gapped сред, где нет доступа к API-серверу. `kubeconform` работает оффлайн и проверяет типы ресурсов, обязательные поля и версии API. Интеграция в CI/CD:

```bash
# Полная pipeline валидации без кластера
helm dependency build ./my-chart
helm template my-release ./my-chart -f values.yaml | \
  kubeconform --kubernetes-version 1.30.0 --strict
```

### Сравнение изменений (helm-diff)

Плагин `helm-diff` показывает различия между текущим релизом и новым манифестом:

```bash
# Установка плагина
helm plugin install https://github.com/databus23/helm-diff

# Просмотр изменений перед upgrade
helm diff upgrade my-release ./my-chart -f values.yaml

# Показать изменения даже для первого деплоя
helm diff upgrade my-release ./my-chart -f values.yaml --allow-unreleased
```

**Для аудита:** Вывод `helm diff` можно перенаправить в файл и сохранить как артефакт CI/CD-сборки для соответствия требованиям compliance.

### Валидация через JSON Schema

Файл `values.schema.json` обеспечивает строгую типизацию перед рендерингом:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "required": ["image"],
  "properties": {
    "image": {
      "type": "object",
      "required": ["repository", "tag"],
      "properties": {
        "tag": { "type": "string" },
        "pullPolicy": { "enum": ["Always", "IfNotPresent", "Never"] }
      }
    },
    "replicaCount": {
      "type": "integer",
      "minimum": 1,
      "maximum": 20
    }
  }
}
```

### Юнит-тестирование шаблонов

Для автоматизированной проверки логики используйте `helm-unittest`:

```bash
# Запуск всех тестов в директории tests/
helm unittest ./my-chart
```

Тесты проверяют:
- Корректность рендеринга при различных комбинациях `values.yaml`.
- Наличие обязательных полей в сгенерированных манифестах.
- Содержимость аннотаций, меток и селекторов.

Пример тестового файла `tests/deployment_test.yaml`:

```yaml
suite: test deployment
templates:
  - deployment.yaml
release:
  name: my-release
  namespace: default
chart:
  version: 1.0.0
tests:
  - it: should render replicas from values
    set:
      replicaCount: 3
    asserts:
      - matchSnapshot: {}
      - equal:
          path: spec.replicas
          value: 3
  - it: should fail if replicaCount is 0
    set:
      replicaCount: 0
    asserts:
      - failedSnapshot: {}
```

### Проверка безопасности манифестов

Интеграция с `kube-score` для оценки безопасности сгенерированных манифестов:

```bash
helm template my-release ./my-chart -f values.yaml | \
  kube-score score -
```

`kube-score` проверяет:
- Наличие `readinessProbe` и `livenessProbe`.
- Отсутствие привилегированных контейнеров.
- Использование безопасных контекстов (non-root, read-only root filesystem).
- Корректность RBAC (ServiceAccount, ограничения).

## Устранение неисправностей

### Диагностическая методология SRE

При возникновении ошибок рендеринга или деплоя применяйте последовательный подход:

1. **Изоляция:** Выполните `helm template my-release ./my-chart > rendered.yaml` и проверьте выходной файл на синтаксические ошибки YAML.
2. **Контекст:** Определите, на каком шаге возникает ошибка — парсинг, слияние значений или валидация.
3. **Минимальный пример:** Упростите `values.yaml` до минимального набора параметров и постепенно добавляйте значения для локализации проблемы.
4. **Версия Helm:** Убедитесь, что используемая версия Helm поддерживает features, задействованные в чарте (например, `--set-json` появился в Helm 3.14.0).

### Типичные ошибки и решения

| Ошибка | Вероятная причина | Решение |
|--------|-------------------|---------|
| `nil pointer evaluating field X` | Потеря контекста внутри `range` или `with` | Используйте `$.X` вместо `.X` для доступа к глобальному scope |
| `can't evaluate field` | Попытка доступа к вложенному полю `nil`-объекта | Добавьте проверку `{{ if .Values.parent }}` или `with .Values.parent` |
| `wrong number of args for eq` | Отсутствие пробела между аргументами | Используйте `{{ if eq .a .b }}`, а не `{{ if eq .a.b }}` |
| Условие срабатывает на `0` | Helm трактует `0` как `false` | Используйте явное сравнение: `{{ if ne (int .Values.val) 0 }}` |
| `template: ...: invalid value` | Несоответствие типа данных в values | Проверьте типы в `values.yaml` и `values.schema.json` |
| `.Files.Get` возвращает пустоту | Файл в `templates/` или `.helmignore` | Переместите файл в корень чарта или проверьте `.helmignore` |
| `Has` возвращает `false` в `helm template` | Оффлайн-режим использует дефолты | Добавьте `--api-versions` и `--kube-version` |
| `lookup` возвращает `nil` | `--dry-run` или отсутствие прав SA | `lookup` требует живого соединения с API-сервером |
| `subchart values not applied` | Неверное имя секции или alias | Проверьте `Chart.yaml` и секцию в `values.yaml` |
| `release name exceeds 53 chars` | Длинное имя из комбинации env + chart | Используйте `nameOverride` или `fullnameOverride` |
| `Error: failed to render chart: missing label values` | Хелпер `include` возвращает пустую строку | Проверьте, что именованный шаблон определён в `_helpers.tpl` и не содержит опечаток в имени |
| `values do not meet the specifications` | Нарушение схемы `values.schema.json` | Проверьте типы, диапазоны и обязательные поля в values |
| `SSA conflict` при `helm upgrade` | Изменение полей, управляемых другим контроллером | Используйте `--force` или убедитесь, что поля не изменяются внешними системами |
| `rendered manifests contain a resource that already exists` | Конфликт имён при установке в Namespace с существующими ресурсами | Проверьте `fullnameOverride` или используйте уникальный `--name-template` |

## Лучшие практики

### Архитектура шаблонов

1. **Минимизация логики в YAML:** Сложные вычисления и преобразования данных рекомендуется выносить в именованные шаблоны (`_helpers.tpl`). Это упрощает отладку и повторное использование.
2. **Явное кавычирование:** Всегда используйте пайплайн `| quote` для строковых значений, чтобы избежать ошибок парсинга YAML (особенно для портов, версий и меток).
3. **Документирование values.yaml:** Каждый параметр должен сопровождаться комментарием, объясняющим его назначение, тип и формат.
4. **Принцип Immutable Release:** Шаблоны не должны содержать хардкода окружных значений. Все параметры (имена, неймспейсы, образы) должны приходить из `values.yaml` или встроенных объектов.
5. **Validation Pipeline:** Никогда не деплойте без прохождения `helm lint` → `helm template` → `helm install --dry-run`. Автоматизируйте pipeline в CI.
6. **Глобальный контекст в циклах:** Всегда используйте `$.Release`, `$.Chart`, `$.Values` внутри `range` и `with`, чтобы избежать потери scope.
7. **DRY через _helpers.tpl:** Выносите повторяющиеся конструкции (метки, селекторы, полные имена) в именованные шаблоны. Это снижает риск опечаток при изменении naming convention.
8. **Глобальные значения (global):** Используйте `.Values.global` для передачи данных между родительским и дочерними чартами (registry, домены, окружение).

### Многоокружная эксплуатация

9. **Слои values:** Используйте базовый `values.yaml` + окружные оверрайды (`-f values-prod.yaml`). Избегайте хранения секретов в `values.yaml` — используйте `helm-secrets` или внешние источники.
10. **Идемпотентность:** Чарт должен допускать многократный `helm upgrade` с одинаковыми значениями без побочных эффектов. Избегайте `randAlphaNum` в шаблонах.
11. **Обратная совместимость:** При изменении `Chart.yaml` (например, увеличении `apiVersion`) убедитесь, что старые релизы могут быть развёрнуты обратно через `helm rollback`.
12. **Изоляция окружений:** Разделяйте dev/staging/prod не только значениями, но и namespace. Используйте `--namespace` явно, а не полагайтесь на дефолт.

### Безопасность

13. **Безопасность хуков:** Job-хуки (`pre-upgrade`, `pre-install`) должны использовать отдельные ServiceAccount с минимальными правами. Никогда не выполняйте миграции от имени администратора кластера.
14. **Ограничение размера .Files:** Помните о лимите в 1 МБ для ConfigMap/Secret. Для файлов большего размера используйте PersistentVolume или выносите данные в Docker-образ.
15. **Защита от инъекций:** Ограничьте использование `tpl` внешними конфигурационными файлами. Никогда не передавайте пользовательский ввод напрямую в `tpl`.
16. **RBAC для Helm:** ServiceAccount, от имени которого работает Helm в CI/CD, должен иметь права только наnamespace релиза. Используйте `tiller`-подобную модель прав (минимальные privileges).

### Производительность и надёжность

17. **Размер значений:** Крупные `values.yaml` (>1 МБ) замедляют рендеринг. Разбейте конфигурацию на логические части или используйте `.Files.Get` для внешних данных.
18. **Кэширование зависимостей:** В CI/CD кэшируйте директорию `.helm/` между сборками, чтобы избежать повторной загрузки зависимостей.
19. **Атомарность:** Используйте `--atomic` в `helm upgrade` для автоматического отката при частичном деплое.
20. **Ограничение ревизий:** Настройте `--history-max` (по умолчанию 10) для предотвращения бесконечного роста Secret с историей релизов в namespace.

## Ограничения и особые случаи

### Оффлайн-рендеринг (`helm template`)

При локальном рендеринге Helm не подключается к кластеру и использует дефолтные значения `.Capabilities` (обычно последняя стабильная версия K8s). Это означает:
- `.Capabilities.APIVersions.Has` может возвращать `false` для ресурсов, доступных в целевом кластере.
- `.Capabilities.KubeVersion.Version` отражает дефолт, а не реальный кластер.

**Решение:** Используйте флаги `--kube-version` и `--api-versions` для эмуляции целевой среды.

**SRE-практика:** Сохраняйте конфигурацию целевых кластеров в виде файлов:

```bash
# prod-cluster.yaml
--api-versions networking.k8s.io/v1/Ingress
--api-versions batch/v1/CronJob
--kube-version 1.30.0
```

И вызывайте:
```bash
helm template my-release ./my-chart -f values.yaml $(cat prod-cluster.yaml)
```

### Функция `lookup`

`lookup` выполняет запрос к живому API-серверу Kubernetes. Особенности:
- При первом `helm install` ресурсы ещё не созданы — `lookup` возвращает `nil`.
- При `helm install --dry-run` соединения с API может не быть — результат также `nil`.
- Требует соответствующих RBAC-прав у ServiceAccount, от имени которого выполняется Helm.

**Правило:** Всегда реализуйте fallback-логику:

```yaml
{{- $secret := lookup "v1" "Secret" $.Release.Namespace "my-secret" }}
secretKey: {{ if $secret }}{{ $secret.data.key }}{{ else }}default-value{{ end }}
```

### Функция `tpl`

Динамический рендеринг строк из `values.yaml` через `tpl` создаёт риск инъекции шаблонов (Template Injection). Используйте `tpl` только для:
- Внешних конфигурационных файлов (`.Files.Get`).
- Динамических блоков в NOTES.txt.

Избегайте `tpl` для основной логики манифестов — это затрудняет статический анализ и линтинг.

**Безопасность:** Если чарт предназначен для публичного использования, добавьте `{{- /* comment */ -}}` с предупреждением о рисках `tpl` в заголовке шаблонов.

### Лимиты Kubernetes

- **Размер ConfigMap/Secret:** 1 МБ. При превышении разбейте данные на несколько объектов или используйте PersistentVolume.
- **Размер аннотаций:** 256 КБ. Хеширование больших структур через `sha256sum` безопасно (хеш короткий), но сам `include` может замедлить рендеринг.
- **Длина имени релиза:** 53 символа (DNS-1123). Длинные комбинации `namespace-chart-name` требуют `nameOverride` или `fullnameOverride`.
- **Размер манифеста:** etcd имеет лимит на размер объекта (по умолчанию 1.5 МБ). Следите за количеством элементов в `range`, генерирующих огромные списки.

### Производительность рендеринга

- **Большие values.yaml (>1 МБ):** Helm загружает все значения в память. Для конфигураций большой длины используйте `.Files.Get` с внешними файлами.
- **Вложенные range:** Глубоко вложенные циклы (`range` внутри `range` внутри `range`) экспоненциально увеличивают время рендеринга. Ограничьте вложенность двумя уровнями.
- **Функции с побочными эффектами:** Вызов `now`, `randAlphaNum` внутри шаблонов делает рендеринг недетерминированным. Используйте их только в hooks, а не в основных манифестах.
- **Количество шаблонов:** Чарт с сотней файлов рендерится медленнее, чем чарт с 10 файлами. Объединяйте логически связанные ресурсы в один файл, где это уместно.

### Специфика air-gapped сред

В изолированных сетях (on-premise, банк, госсектор) отсутствует доступ к внешним OCI-реестрам:
- Загружайте чарты через `helm pull oci://registry.example.com/chart --version 1.0.0`.
- Используйте `helm dependency build` с локальным репозиторием (`helm repo add local file:///path/to/charts`).
- Для секретов используйте `helm-secrets` с локальным SOPS backend (age, GPG) вместо облачных KMS.

### Поведение при откате (rollback)

`helm rollback` восстанавливает манифесты предыдущей ревизии, но:
- Значения `.Values` берутся из целевой ревизии, а не из текущей.
- Хуки не выполняются при rollback (за исключением `pre-rollback` и `post-rollback`).
- Аннотации checksum пересчитываются на основе ревизии, к которой происходит откат, что инициирует Rolling Update.
