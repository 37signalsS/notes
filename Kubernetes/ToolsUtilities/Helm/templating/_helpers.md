# Именованные шаблоны и хелперы

---

## Определения

**Именованные шаблоны (Named Templates)** — это фрагменты кода Go templates, которые определяются один раз и могут быть многократно использованы в различных частях Helm-чарта. Они позволяют соблюдать принцип DRY (Don't Repeat Yourself).

**Хелперы (Helpers)** — общепринятое название для именованных шаблонов, которые хранятся в файле `_helpers.tpl`. Как правило, они используются для генерации имен ресурсов, стандартных меток (labels) и других повторяющихся фрагментов YAML.

---

## Основные концепции

### Файлы с префиксом подчеркивания

Файлы, имена которых начинаются с нижнего подчеркивания (например, `_helpers.tpl`), обрабатываются Helm особым образом:
- Содержимое этих файлов не рендерится как манифесты Kubernetes.
- Они служат исключительно для хранения определений шаблонов.
- Эти файлы доступны для всех шаблонов внутри текущего чарта и его дочерних чартов.

### Передача контекста (Scope)

Именованные шаблоны не имеют автоматического доступа к глобальному контексту. При вызове шаблона необходимо явно передать данные в качестве аргумента.

| Конструкция | Описание |
|-------------|----------|
| `{{ define "name" }}` | Определяет новый шаблон с именем `name`. |
| `{{ include "name" . }}` | Вызывает шаблон, передавая текущий контекст (точка). |
| `{{ template "name" . }}` | Устаревший способ вызова; результат выводится напрямую, пайплайны не поддерживаются. |

### Управление пробелами в определениях

При определении шаблона через `define` важно использовать whitespace control (`{{-` и `-}}`), чтобы избежать появления лишних пустых строк в итоговом YAML после рендеринга.

```go
{{- define "mychart.name" -}}
{{- default .Chart.Name .Values.nameOverride | trunc 63 | trimSuffix "-" -}}
{{- end -}}
```

### Сравнение include и template

| Характеристика | include | template |
|----------------|---------|----------|
| **Возвращаемое значение** | Строка | Вывод в stdout рендеринга |
| **Поддержка пайплайнов** | Да (например, `| nindent 4`) | Нет |
| **Рекомендация** | Использовать всегда для YAML-блоков | Не рекомендуется для сложных структур |

## Практические сценарии

### Передача нескольких аргументов через dict

Если шаблону требуется доступ к нескольким независимым объектам (например, текущему контексту и специфичному значению), используется функция `dict`.

**Определение хелпера:**
```go
{{- define "mychart.config" -}}
{{- $top := index . "top" -}}
{{- $name := index . "name" -}}
app: {{ $name }}
release: {{ $top.Release.Name }}
{{- end -}}
```

**Вызов хелпера:**
```yaml
metadata:
  labels:
    {{- include "mychart.config" (dict "top" . "name" "my-app") | nindent 4 }}
```

### Генерация стандартных меток (labels)

Стандартный набор меток (`app.kubernetes.io/*`) обеспечивает совместимость с инструментами экосистемы Kubernetes.

```go
{{- define "mychart.labels" -}}
app.kubernetes.io/name: {{ include "mychart.name" . }}
app.kubernetes.io/instance: {{ .Release.Name }}
{{- if .Chart.AppVersion }}
app.kubernetes.io/version: {{ .Chart.AppVersion | quote }}
{{- end }}
app.kubernetes.io/managed-by: {{ .Release.Service }}
{{- end -}}
```

### Использование tpl для динамических значений

Функция `tpl` позволяет рендерить строки из `values.yaml` так, как если бы они были шаблонами. Это полезно для передачи формул или путей.

**values.yaml:**
```yaml
config:
  path: "/data/{{ .Release.Name }}"
```

**deployment.yaml:**
```yaml
env:
  - name: APP_PATH
    value: {{ tpl .Values.config.path . | quote }}
```

## Дополнительная информация

### Библиотечные чарты (Library Charts)

Если вы используете общую логику в нескольких проектах, вы можете вынести хелперы в **library chart** (тип `library` в `Chart.yaml`). Такие чарты не деплоят свои ресурсы, а только предоставляют свои `define` для родительских чартов.

### Лучшие практики

- **Уникальность имен:** Префиксируйте имена шаблонов именем чарта (`chartname.fullname`), чтобы избежать коллизий при использовании субчартов.
- **Неизменяемость селекторов:** Метки, используемые в `spec.selector`, должны быть вынесены в отдельный хелпер (например, `chart.selectorLabels`) и не содержать версию чарта или приложения, так как Kubernetes запрещает изменение селекторов.
- **nindent vs indent:** Всегда используйте `nindent` для вставки блоков в YAML, так как он гарантирует перенос строки перед отступом.
- **Документирование:** Используйте комментарии `{{/* ... */}}` внутри `_helpers.tpl` для описания ожидаемых аргументов.

### Устранение неисправностей

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `wrong type for value; expected map[string]interface{}` | В `include` передан неверный контекст (например, строка вместо объекта) | Проверьте аргумент после имени шаблона в `include` |
| `nil pointer evaluating...` | Шаблон пытается обратиться к `.Values`, но контекст не был передан | Убедитесь, что при вызове передана точка `.` или соответствующий `dict` |
| Лишние отступы в результирующем YAML | Смешивание ручных отступов и `indent` | Проверьте базу отступа перед `{{- include ... }}` и значение в `nindent` |
| Шаблон переписывает сам себя | Дублирование имен в `define` в разных файлах | Используйте уникальные префиксы для каждого чарта |
