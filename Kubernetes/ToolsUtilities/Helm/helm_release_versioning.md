# Управление версиями Helm

Helm управляет версиями на трёх уровнях: версия чарта, версия приложения и ревизия релиза в кластере. Система опирается на стандарт SemVer 2.0.0 для пакетов и последовательную нумерацию для развёртываний.

---

## Определения

| Сущность | Где определяется | Формат | Назначение |
|----------|------------------|--------|------------|
| **Версия чарта (`version`)** | `Chart.yaml: version` | SemVer 2.0.0 | Идентификация пакета; выбор версии при установке из репозитория или OCI |
| **Версия приложения (`appVersion`)** | `Chart.yaml: appVersion` | Свободный (обычно SemVer) | Маркер версии ПО внутри контейнера; чисто информационное поле |
| **Ревизия релиза (`revision`)** | Secret/ConfigMap в кластере | Целое число (1, 2, 3…) | Снимок состояния (манифесты + values) для конкретного развёртывания |

**Хранилище истории:**

- **Helm 3 (текущий):** Secrets с именем `sh.helm.release.v1.<release-name>.v<revision>` в том же namespace, где находится релиз.
- **Helm 2 (Legacy):** ConfigMaps в namespace `kube-system` (по умолчанию).

---

## Основные концепции

### Семантическое версионирование (SemVer)

Версии чартов **обязаны** следовать формату `MAJOR.MINOR.PATCH`:

- **MAJOR** — обратно несовместимые изменения (например, удаление параметров в `values.yaml` или миграция API-версий K8s).
- **MINOR** — новая функциональность (новые параметры, добавление ресурсов), обратно совместимая.
- **PATCH** — исправления ошибок в шаблонах или документации.

**Пре-релизы и метаданные:**
Helm поддерживает расширенный формат SemVer:
- `1.2.3-alpha.1` — пре-релиз (при поиске `helm search` такие версии скрыты без флага `--devel`).
- `1.2.3+build.001` — метаданные сборки (игнорируются при сравнении версий).

**Диапазоны версий в зависимостях (`Chart.yaml`):**

```yaml
dependencies:
  - name: redis
    version: "^17.1.0"    # >=17.1.0 и <18.0.0 (совместимые изменения)
  - name: postgresql
    version: "~12.1.0"    # >=12.1.0 и <12.2.0 (только патчи)
  - name: mysql
    version: ">=8.0.0"    # Любая версия от 8.0.0 и выше
```

### Взаимосвязь `version` и `appVersion`

Хотя `appVersion` информативна, лучшей практикой в CI/CD является строгая синхронизация и инкрементирование версий.

- **`appVersion`** должна соответствовать версии развертываемого приложения (например, тегу Docker-образа).
- **`version`** (версия чарта) должна инкрементироваться (обычно `PATCH`-часть) при **любом** изменении, включая:
  - Изменения в шаблонах (`templates/`).
  - Добавление новых параметров в `values.yaml`.
  - **Обновление `appVersion`**.

Этот подход гарантирует, что для каждой версии приложения существует уникальный, неизменяемый артефакт чарта. Это позволяет точно отслеживать, какая версия чарта развертывает какую версию приложения, и обеспечивает надежные откаты.

**Пример в CI/CD:**
При сборке новой версии приложения `v1.5.0`:

1. CI-пайплайн собирает Docker-образ `my-app:v1.5.0`.
2. Затем он обновляет `Chart.yaml`:
    - `appVersion` устанавливается в `"1.5.0"`.
    - `version` инкрементируется, например, с `1.1.2` до `1.1.3`.
3. Новая версия чарта публикуется в репозиторий.

### Версионирование в OCI-репозиториях

Helm 3 поддерживает хранение чартов в контейнерных реестрах (Registry) как OCI-артефактов:

- Тег образа в реестре **должен строго соответствовать** полю `version` в `Chart.yaml`.
- При публикации (`helm push`) Helm автоматически использует версию из манифеста как тег.

```bash
# Работа с OCI версиями
helm pull oci://registry.example.com/charts/my-app --version 1.2.3
```

### История и ревизии

Каждая модификация релиза (upgrade или rollback) создаёт новую ревизию. Ревизии неизменяемы (immutable snapshots). История хранит:
- Манифесты, отправленные в кластер.
- Значения параметров (values).
- Информацию о дате, статусе и описании (описание можно задать через `--description`).

**Статусы в истории (`helm history`):**
- `deployed` — текущая активная версия.
- `superseded` — предыдущая версия, замененная новой.
- `failed` — попытка обновления завершилась ошибкой.
- `uninstalled` — релиз удален, но история сохранена (флаг `--keep-history`).

### Зависимости и lock-файл

При использовании зависимостей Helm фиксирует точные версии в `Chart.lock`:

```yaml
# Chart.yaml
dependencies:
  - name: redis
    version: "^17.1.0"
    repository: https://charts.bitnami.com/bitnami
```

```bash
# Обновление зависимостей и создание Chart.lock
helm dependency update

# Сборка зависимостей по Chart.lock
helm dependency build
```

## Практические сценарии

### Просмотр и анализ истории

```bash
# Просмотр последних 10 ревизий
helm history my-release -n prod --max 10

# Детали конкретной ревизии
helm get values my-release -n prod --revision 7   # Пользовательские values
helm get manifest my-release -n prod --revision 7 # Итоговый YAML манифест

# Показать все значения текущей ревизии (включая дефолтные из чарта)
helm get values my-release -n prod --all

# Показать заметки (NOTES.txt) релиза
helm get notes my-release -n prod
```

### Безопасный откат (Rollback)

```bash
# Откат к конкретной ревизии
helm rollback my-release 7 -n prod

# Откат к предыдущей успешной версии (0 — автоматически выбирает последнюю рабочую)
helm rollback my-release 0 -n prod

# Откат с ожиданием готовности подов и таймаутом
helm rollback my-release 7 -n prod --wait --timeout 5m

# Восстановление после удаления с сохранением истории
helm uninstall my-release -n prod --keep-history
helm rollback my-release 0 -n prod
```

### Автоматизация откатов при обновлении

Для минимизации простоев используйте флаги контроля состояния:

```bash
# --atomic: если обновление не удалось, Helm САМ выполнит rollback к предыдущей ревизии
# --cleanup-on-fail: удаляет созданные ресурсы, если транзакция не удалась
helm upgrade --install my-app ./chart \
  --atomic \
  --cleanup-on-fail \
  --timeout 10m \
  -n prod
```

### Управление глубиной истории

По умолчанию Helm хранит 10 последних ревизий (в версиях 3.0+). Большое количество ревизий перегружает API-сервер Kubernetes и увеличивает размер etcd.

```bash
# Ограничение количества хранимых ревизий при конкретном обновлении
helm upgrade myapp bitnami/nginx --history-max 10 -n prod

# Глобальное ограничение через переменную окружения (в пайплайнах)
export HELM_HISTORY_MAX=20
```

### Продвижение через окружения (Promotion)

```bash
# Установка конкретной версии в Dev
helm upgrade --install app app-chart 
  -f values/dev.yaml 
  --version 2.3.1 
  -n dev

# Продвижение той же версии в Staging
helm upgrade --install app app-chart 
  -f values/staging.yaml 
  --version 2.3.1 
  -n stage

# Продвижение в Production с дополнительными проверками
helm upgrade --install app app-chart 
  -f values/prod.yaml 
  --version 2.3.1 
  --wait 
  --timeout 10m 
  --atomic 
  -n prod
```

### Проверка изменений перед обновлением

```bash
# Просмотр диффа перед обновлением (требуется плагин helm-diff)
helm diff upgrade myapp bitnami/nginx -n prod

# Сравнение двух ревизий вручную через манифесты
helm get manifest myapp -n prod --revision 5 > rev5.yaml
helm get manifest myapp -n prod --revision 6 > rev6.yaml
diff rev5.yaml rev6.yaml
```

## Дополнительная информация

### Рекомендации (Best Practices)

- **Пиннинг версий:** Всегда указывайте конкретные версии чартов в продакшене (`--version X.Y.Z`).
- **Атомарность:** Используйте флаг `--atomic` для автоматического восстановления после неудачных деплоев.
- **Контроль истории:** Ограничивайте `--history-max` для экономии ресурсов (рекомендуется 10-20).
- **Хранение values:** Держите `values` файлы под версионным контролем (Git) для воспроизводимости.
- **Тестирование:** Проверяйте обновления в staging окружении, максимально приближенном к production, перед финальным деплоем.
- **Chart.lock:** Всегда коммитьте `Chart.lock` в репозиторий, чтобы гарантировать, что все участники команды и CI используют одинаковые версии зависимостей.
- **Очистка failed ревизий:** Если ревизия застряла в статусе `failed`, проанализируйте причины (`helm status`) перед повторным запуском.
