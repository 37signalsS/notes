# Сравнение версий Helm (v2, v3, v4)

История развития Helm отражает эволюцию Kubernetes: от клиент-серверной архитектуры с избыточными правами (v2) к безопасной клиентской модели (v3) и современному подходу на базе Server-Side Apply и WebAssembly (v4).

> **⚠️ Статус поддержки:**
> *   **Helm v2:** EOL (End of Life) с 13 ноября 2020 года. Использование в новых проектах запрещено.
> *   **Helm v3:** Bug fixes до июля 2026, Security fixes до ноября 2026 (EOL). Рекомендуется планировать миграцию.
> *   **Helm v4:** Актуальная стабильная версия (с ноября 2025).

---

## Определения

| Термин | Описание |
|--------|----------|
| **Tiller** | Серверный компонент Helm 2, работавший в кластере с правами `cluster-admin`. |
| **Three-way merge** | (v3) Сравнение желаемого состояния, последней ревизии и текущего состояния кластера. |
| **Server-Side Apply (SSA)** | (v4) Механизм Kubernetes, при котором логика слияния манифестов выполняется на стороне API-сервера. |
| **WASM Plugin Runtime** | (v4) Изолированная среда выполнения плагинов, заменяющая прямые вызовы бинарных файлов. |
| **apiVersion** | Версия формата чарта: `v1` (v2), `v2` (v3/v4), `v3` (v4 экспериментальный). |

## Базовые концепции

### Архитектурная эволюция

| Аспект | Helm v2 | Helm v3 | Helm v4 |
| :--- | :--- | :--- | :--- |
| **Модель управления** | Client-Server (Tiller) | Client-only | Client-only (SDK v4) |
| **Стратегия деплоя** | Two-way merge | Three-way merge | **Server-Side Apply (SSA)** |
| **Безопасность** | RBAC для Tiller | RBAC пользователя | RBAC пользователя + WASM Sandbox |
| **Хранение релизов** | ConfigMaps в `kube-system` | Secrets в namespace релиза | Secrets (SSA-aware) |
| **Уникальность имён** | Глобальная (на кластер) | В пределах namespace | В пределах namespace |
| **Плагины** | Локальные бинарные файлы | Локальные бинарные файлы | **OCI-артефакты (WASM)** |

### Безопасность и RBAC

**Helm 2 (Проблема Tiller):**
Tiller часто устанавливался с правами `cluster-admin`, что позволяло любому пользователю с доступом к Tiller манипулировать любыми ресурсами в кластере, обходя персональные ограничения RBAC.

**Helm 3 (Интеграция с RBAC):**
Полный отказ от Tiller. Все операции выполняются напрямую через Kubernetes API, используя права текущего пользователя из `kubeconfig`. Это сделало Helm нативно совместимым с многопользовательскими кластерами.

**Helm v4 (Изоляция плагинов):**
Внедрение WASM для плагинов ограничивает их доступ к хост-системе. В отличие от v2/v3, где плагин мог выполнить любой скрипт от имени пользователя, WASM-плагины работают в песочнице с ограниченными возможностями (Sandboxed execution).

### Стратегии слияния манифестов

1.  **Two-way merge (v2):** Сравнивались только чарт и предыдущая ревизия Helm. Если кто-то изменил ресурс вручную через `kubectl edit`, Helm мог не заметить этого при следующем апгрейде.
2.  **Three-way merge (v3):** Сравниваются: новый чарт + сохранённая ревизия Helm + живое состояние в кластере. Это позволяет Helm корректно обновлять ресурсы, даже если в них были внесены внешние правки.
3.  **Server-Side Apply (v4):** Логика слияния делегируется API-серверу Kubernetes.
    *   **Владение полями (Field Ownership):** Kubernetes отслеживает, какой инструмент (Helm, ArgoCD, контроллер) установил каждое поле.
    *   **Разрешение конфликтов:** Если два инструмента пытаются управлять одним полем, API-сервер выдаёт ошибку или применяет политику слияния, что критично для GitOps.

## Практические сценарии

### Сравнение формата чартов (Chart API)

| Функция | apiVersion: v1 (v2) | apiVersion: v2 (v3/v4) |
| :--- | :--- | :--- |
| **Файл зависимостей** | `requirements.yaml` | Секция `dependencies` в `Chart.yaml` |
| **Типы чартов** | Только `application` | `application` и `library` |
| **Lock-файл** | Отсутствует | `Chart.lock` |
| **Директория CRD** | Обрабатывается как шаблоны | Директория `crds/` (приоритетная установка) |

#### Пример миграции зависимостей (v1 → v2)

**Helm 2 (`requirements.yaml`):**
```yaml
dependencies:
- name: redis
  version: "10.5.x"
  repository: "https://charts.bitnami.com/bitnami"
```

**Helm 3/4 (`Chart.yaml`):**
```yaml
apiVersion: v2
name: my-app
version: 1.0.0
dependencies:
- name: redis
  version: "17.x.x"
  repository: "https://charts.bitnami.com/bitnami"
  condition: redis.enabled
```

### Различия в синтаксисе команд

**Установка релиза:**
*   **v2:** `helm install stable/mysql --name my-db` (имя через флаг).
*   **v3/v4:** `helm install my-db bitnami/mysql` (имя — позиционный аргумент).
*   **v3/v4 (автогенерация):** `helm install --generate-name bitnami/mysql`.

**Репозитории:**
*   **v2/v3:** Добавление по полному URL.
*   **v4:** Работа с OCI-реестрами стала приоритетной. `helm registry login` в v4 требует только доменное имя (без `https://`).

### Работа с CRD (Custom Resource Definitions)

В **Helm 2** CRD обрабатывались как обычные шаблоны, что часто приводило к ошибкам "Resource not found", если ресурсы этого типа создавались в том же чарте.

В **Helm 3 и v4** введена директория `crds/`:
1.  Манифесты из `crds/` устанавливаются первыми, до рендеринга шаблонов.
2.  **Важно:** Helm не обновляет и не удаляет CRD из этой директории при обновлении/удалении релиза, чтобы предотвратить случайную потерю данных пользователей в кластере.

### Библиотечные чарты (Library Charts)

Введены в Helm 3. Позволяют создавать общие шаблоны (helpers), которые не разворачиваются как самостоятельные приложения, а подключаются как зависимости.

```yaml
# Chart.yaml библиотечного чарта
apiVersion: v2
name: common-lib
type: library  # Ключевое отличие
version: 1.0.0
```

## Дополнительная информация

### Миграция с Helm 2 на Helm 3/4

Для перехода с v2 на v3 использовался плагин `helm-2to3`, который конвертировал конфигурации Tiller в Secrets. На текущий момент (2026 год) прямая миграция с v2 актуальна только для восстановления данных из архивов. 

Миграция с v3 на v4 проходит бесшовно для большинства чартов (`apiVersion: v2` полностью поддерживается), но требует обновления бинарного файла и проверки скриптов автоматизации на предмет использования SSA.
