# Сравнение Helm v2 и v3

Helm прошел значимую эволюцию от версии v2 к v3. Изменения затронули архитектуру, безопасность, формат чартов и опыт работы с релизами. Ключевое отличие — отказ от серверной составляющей Tiller в пользу полностью клиентской модели, что привело к упрощению внедрения и снижению рисков.

## Архитектурные и операционные различия

-   **Tiller**: В Helm v2 присутствовал компонент Tiller — сервер в кластере, который принимал команды от клиента и применял манифесты. В v3 Tiller удален; клиент Helm напрямую взаимодействует с Kubernetes API от имени пользователя и его контекста kubeconfig.
-   **Безопасность**: Модель безопасности в v3 основана на нативном RBAC Kubernetes. В v2 требовались отдельные права для Tiller, что усложняло контроль доступа.
-   **Хранение релизов**: В v2 состояние релизов хранилось в ConfigMap'ах в неймспейсе Tiller (`kube-system`). В v3 релизы по умолчанию сохраняются как Secrets в целевом namespace релиза, что повышает конфиденциальность.

### Таблица различий

| Аспект | Helm v2 | Helm v3 |
| :--- | :--- | :--- |
| **Управляющий компонент** | Tiller (в кластере) | Только клиент |
| **Безопасность** | Разрешения для Tiller | RBAC пользователя |
| **Хранение релизов** | ConfigMaps в неймспейсе Tiller | Secrets в неймспейсе релиза |
| **Область имен релиза** | Часто кластерная при одном Tiller | Уникальность в пределах namespace |
| **Chart API** | `apiVersion: v1` | `apiVersion: v2` |
| **Типы чартов** | Нет | `application`, `library` |
| **Зависимости** | `requirements.yaml` | `dependencies` в `Chart.yaml` |
| **CRD** | Устанавливались как обычные шаблоны | Отдельный каталог `crds/` для установки до релиза |
| **Локальные каталоги** | `~/.helm` | XDG (`~/.config/helm`, `~/.cache/helm`, `~/.local/share/helm`) |
| **Команда install** | `helm install CHART --name RELEASE`| `helm install RELEASE CHART` (или `--generate-name`) |

## Синтаксис команд и управление релизами

Смена порядка аргументов в `install`:

**Helm v2**
```bash
helm install stable/mysql --name mydb --namespace prod
```

**Helm v3**
```bash
# Имя релиза - первый аргумент
helm install mydb bitnami/mysql --namespace prod

# или с автогенерацией имени
helm install --generate-name bitnami/mysql --namespace prod
```

В v3 одинаковые имена релизов допустимы в разных namespace. Helm v3 также использует трехстороннее стратегическое слияние при обновлениях, корректнее учитывая расхождения между желаемым состоянием, прошлой ревизией и "живым" состоянием в кластере.

## Формат чартов и зависимости

Переход к Chart API `v2` ввел явные типы чартов и перенес определение зависимостей в `Chart.yaml`, сделав `requirements.yaml` устаревшим.

**Пример для v2 (`requirements.yaml`):**
```yaml
dependencies:
- name: redis
  version: "~10.5"
  repository: "https://charts.example.com"
```

**Пример для v3 (`Chart.yaml`):**
```yaml
apiVersion: v2
name: myapp
type: application
version: 0.1.0
dependencies:
- name: redis
  version: "~17.0"
  repository: "https://charts.example.com"
```

В v3 также появился `Chart.lock` для фиксации версий зависимостей.

## CRD и порядок установки

В v2 CRD создавались как обычные шаблоны, что могло приводить к race conditions. В v3 появился специальный каталог `crds/`, содержимое которого применяется до рендеринга основных шаблонов. Это гарантирует, что кастомные типы ресурсов будут определены до создания их экземпляров.
