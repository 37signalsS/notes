# Продвинутые возможности Helm

## Определения

**Продвинутые возможности Helm** — это совокупность методов, инструментов и архитектурных паттернов, направленных на решение задач масштабируемости, безопасности, отказоустойчивости и переиспользования кода при управлении инфраструктурой Kubernetes в on-premise и гибридных средах. Использование продвинутого функционала позволяет перейти от простого деплоя одиночных приложений к созданию сложных систем управления жизненным циклом приложений (**Application Lifecycle Management**, ALM) и интеграции в **GitOps**-пайплайны без зависимости от облачных сервисов.

К продвинутым областям относятся:
- **Декларативная оркестрация**: управление десятками и сотнями релизов через внешние инструменты (Helmfile, Helmwave) в локальных и изолированных сетях.
- **Модульная архитектура**: использование библиотечных чартов, зонтичных чартов (Umbrella charts) и сложных зависимостей для переиспользования кода между командами и проектами.
- **Интеграция с OCI (Open Container Initiative)**: использование стандартных реестров артефактов (Harbor, CNCF Distribution) для хранения, подписи и распространения чартов в изолированных средах.
- **Безопасность и валидация**: обеспечение качества и соответствия политикам через JSON-схемы, Policy-as-Code (OPA/Gatekeeper, Kyverno) и юнит-тестирование шаблонов.
- **Расширяемость**: изолированное расширение функциональности CLI через WASM-плагины без рисков выполнения произвольного кода на хосте.

## Основные концепции

### 1. Современная дистрибуция через OCI
Традиционные HTTP-репозитории (`index.yaml`) уступают место OCI-реестрам (Harbor, CNCF Distribution). Это позволяет объединить хранение образов контейнеров и Helm-чартов в единой инфраструктуре, используя стандартные механизмы аутентификации, версионирования и безопасности. В отличие от облачных реестров, локальные OCI-реестры развертываются в изолированных сетях без доступа в интернет, что критично для отраслей с высокими требованиями к безопасности (финансы, госсектор, промышленность).

OCI-реестры поддерживают:
- Дигисты (sha256) для гарантии неизменности артефактов
- Ролевую модель доступа (RBAC) для команд
- Сканирование уязвимостей чартов и образов
- Репликацию между кластерами в разных географических локациях

### 2. Управление ресурсами через Server-Side Apply (SSA)
В Helm v4 логика слияния манифестов делегирована API-серверу Kubernetes. Это вводит понятие **Field Ownership** (владение полями), что позволяет Helm делить управление объектом с другими контроллерами (например, HPA, Kyverno, Istio-инъекторами) без возникновения конфликтов конфигурации.

Преимущества SSA для SRE:
- Исключение конфликтов «пинг-понга» между Helm и операторами, изменяющими поля ресурсов (например, HPA, изменяющий `replicas` в Deployment)
- Возможность принудительного захвата владения полями флагом `--force-conflicts` при миграции с Helm v3 на v4
- Автоматическое отслеживание управляемых Helm полей через `kubectl apply --field-manager=helm`

### 3. Расширяемость через WASM-плагины
Helm v4 заменяет традиционные скриптовые плагины на изолированные модули WebAssembly (WASM), исполняемые в среде Extism runtime. Это обеспечивает:
- Безопасность выполнения (Sandbox): плагины не имеют доступа к файловой системе хоста и API системы вне разрешенного контекста
- Кроссплатформенность: один скомпилированный плагин работает на Linux, Windows и macOS без пересборки
- Возможность распространения плагинов через те же OCI-реестры, что и чарты, с подписью через Cosign

Для sysadmin это упрощает поддержку Helm CLI в гетерогенных средах: не требуется установка интерпретаторов Python, Bash или Go на хосты, где выполняется Helm.

### 4. Модульность: Библиотечные чарты (Library Charts)
Библиотечные чарты не создают собственных Kubernetes-ресурсов, а служат контейнерами для общих функций и именованных шаблонов (helpers). Это позволяет централизованно управлять логикой (например, метками, селекторами, стратегиями деплоя, политиками безопасности) для сотен сервисов в enterprise среде.

Пример использования: библиотечный чарт `company-common` содержит шаблоны для формирования стандартных меток, аннотаций для мониторинга и политик Pod Security Standards, которые автоматически применяются во всех прикладных чартах компании через `include`.

### 5. Пост-рендеринг (Post-rendering)
Механизм `--post-renderer` позволяет Helm передавать сгенерированные манифесты внешней утилите (например, Kustomize, yq, кастомному скрипту) перед их отправкой в API-сервер. Это дает возможность вносить изменения, которые Helm не поддерживает "из коробки", не модифицируя сам чарт.

Типичные сценарии использования:
- Инъекция Sidecar-контейнеров безопасности (например, Falco, Aqua) в сторонние закрытые чарты
- Добавление стандартных аннотаций для мониторинга и логирования
- Мутация ресурсов в соответствии с внутренними политиками безопасности (например, добавление SecurityContext, ограничение привилегий)
- Приведение манифестов к стандартам компании перед деплоем

В Helm v4 пост-рендереры должны быть зарегистрированы как плагины типа `postrenderer/v1`, что повышает безопасность и предотвращает выполнение произвольных скриптов.

### 6. Валидация и качество (Quality Assurance)
- **JSON Schema**: Использование `values.schema.json` для строгой типизации входных параметров. Позволяет отловить ошибки конфигурации на этапе рендеринга, до попытки деплоя в кластер.
- **Юнит-тестирование**: Проверка логики шаблонов через `helm-unittest` без развертывания в кластере. Поддерживает BDD-стиль написания тестов, интеграцию в CI/CD пайплайны.
- **Policy-as-Code**: Интеграция с OPA/Gatekeeper или Kyverno для проверки соответствия сгенерированных манифестов внутренним политикам безопасности и стандартам.

## Типовые сценарии использования для SRE/sysadmin

### Управление конфигурацией в enterprise среде
Использование библиотечных чартов и зонтичных чартов для централизованного управления конфигурацией сотен микросервисов. Изменения в общих политиках (метки, SecurityContext, ресурсные лимиты) применяются единовременно через обновление библиотечного чарта, без необходимости изменять каждый прикладной чарт отдельно.

### Интеграция в CI/CD пайплайны без облачных сервисов
- Валидация чартов через `helm lint` и `helm unittest` на этапе сборки PR
- Подпись чартов через Cosign перед публикацией в локальный OCI-реестр
- Автоматический деплой через Helmfile/Helmwave после прохождения всех проверок
- Откат релизов через `helm rollback` с сохранением истории ревизий

### Обеспечение безопасности в изолированных сетях
- Развертывание локальных OCI-реестров (Harbor) с RBAC и сканированием уязвимостей
- Использование Sops для шифрования секретов в Git-репозиториях
- Применение Policy-as-Code через Kyverno/OPA для проверки манифестов перед деплоем
- Использование WASM-плагинов для аудита чартов без риска компрометации хоста

### Диагностика и устранение неисправностей
- Использование `helm get manifest`, `helm get values` и `helm history` для анализа состояния релиза
- Интеграция с Prometheus и Grafana для мониторинга метрик Helm-релизов (количество неудачных деплоев, время применения изменений)
- Использование `helm diff` плагина для визуализации изменений перед применением
- Логирование всех операций Helm в SIEM-системы для соответствия требованиям аудита

## Ограничения и известные проблемы

- **SSA и устаревшие API**: Некоторые старые версии Kubernetes (<1.18) не поддерживают полный функционал SSA и Field Ownership. При миграции на Helm v4 в кластерах с устаревшими API требуется предварительное обновление Kubernetes.
- **WASM-плагины**: На данный момент не все плагины v3 имеют портированные версии для WASM. Плагины, требующие длительных операций или интенсивного доступа к файловой системе, могут иметь ограничения производительности в песочнице Extism.
- **OCI в изолированных сетях**: При работе через корпоративные прокси и файрволы требуется предварительная настройка доверенных корневых сертификатов для OCI-реестров. Дигесты артефактов должны проверяться на этапе сборки, так как в изолированных сетях может отсутствовать возможность повторной проверки через удаленный реестр.
- **Пост-рендеринг**: Сложные мутации, требующие доступа к состоянию кластера, не могут быть реализованы через пост-рендерер, так как он работает только с статическими манифестами. Для динамических мутаций требуются операторы или admission webhooks.
- **Юнит-тестирование**: Тесты helm-unittest проверяют только логику рендеринга шаблонов, но не валидируют соответствие манифестов API сервера и политикам безопасности. Обязательным является дополнительный этап проверки через `kubeconform` или `kubectl apply --dry-run`.
