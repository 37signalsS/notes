# Паттерны и устранение неисправностей Helm

## Определения

**Паттерны Helm** — проверенные архитектурные и конфигурационные решения типичных проблем, возникающих при разработке сложных чартов (пакетов Helm).

**Устранение неисправностей (Troubleshooting) Helm** — процесс диагностики и исправления ошибок на этапах рендеринга шаблонов, линтинга, установки и обновления релизов в кластере Kubernetes.

---

## Основные концепции

### Принципы эффективной конфигурации

Для создания надежных и поддерживаемых чартов рекомендуется следовать трем принципам:

1. **Явная конфигурация**: все изменяемые параметры должны быть вынесены в `values.yaml` (YAML Ain't Markup Language), а не скрыты внутри логики шаблонов или получены динамически из состояния кластера.
2. **Единый источник истины**: каждый параметр определяется в одном месте (обычно в `values.yaml`) и используется во всех зависимых шаблонах через переменные.
3. **Ранняя валидация**: использование встроенных функций (например, `required`) позволяет обнаруживать отсутствие критичных данных на этапе рендеринга, предотвращая деплой некорректных манифестов.

### Инструменты диагностики

Основные инструменты для поиска и устранения проблем:

- **`helm template`** — локальный рендеринг шаблонов для проверки корректности YAML-вывода.
- **`helm lint`** — проверка чарта на синтаксические ошибки и соответствие стандартам.
- **`helm install --dry-run --debug`** — имитация установки с выводом отрендеренных манифестов и метаданных без внесения изменений в кластер.
- **`kubectl get events`** — анализ событий Kubernetes для понимания причин сбоев после успешного (с точки зрения Helm) деплоя.

Подробное описание инструментов отладки см. в разделе **[Команды и рабочий процесс Helm](../helm_commands_and_workflow.md)**.

## Практические сценарии

### 1. Проблема динамических зависимостей (Chicken-and-Egg)

**Проблема:** Приложению требуется параметр, который генерируется Kubernetes только **после** создания ресурса (например, `NodePort` сервиса или внешний IP (Internet Protocol) `LoadBalancer`). Попытка вычислить эти значения внутри шаблона Helm на этапе установки приведет к ошибке или непредсказуемому результату.

**Решение: Принудительная явная конфигурация.**

Переложите ответственность за предоставление значения на внешнюю систему или пользователя.

1. **Обязательный параметр**: создайте пустое поле в `values.yaml`.
2. **Строгая проверка**: используйте `required` для блокировки установки при отсутствии значения.

**Пример (values.yaml):**

```yaml
# Полный базовый URL для доступа к приложению (обязательно для ConfigMap)
app:
  baseUrl: ""
```

**Пример (templates/configmap.yaml):**

```yaml
data:
  APP_BASE_URL: {{ required "Необходимо указать app.baseUrl в values.yaml" .Values.app.baseUrl | quote }}
```

### 2. Синхронизация данных между ресурсами

**Проблема:** Использование одного и того же значения (например, пути монтирования тома `mountPath`) в разных файлах чарта. Жесткое кодирование (Hardcode) в нескольких местах ведет к рассинхронизации при обновлении.

**Решение: Использование централизованных переменных.**

**Пример (values.yaml):**

```yaml
volumes:
  data:
    mountPath: /var/lib/data
```

**Пример (templates/deployment.yaml):**

```yaml
spec:
  containers:
  - volumeMounts:
    - name: data-volume
      mountPath: {{ .Values.volumes.data.mountPath }}
```

**Пример (templates/configmap.yaml):**

```yaml
data:
  # Приложение узнает о пути монтирования из этого конфига
  STORAGE_PATH: {{ .Values.volumes.data.mountPath | quote }}
```
