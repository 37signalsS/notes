# Безопасность и лучшие практики Helm

## Определения

**Безопасность Helm** — это комплекс мер по защите конфигураций, проверке подлинности артефактов и ограничению области влияния (blast radius) при развертывании приложений в Kubernetes.

**Лучшие практики (Best Practices)** — набор устоявшихся архитектурных подходов, обеспечивающих воспроизводимость, минимизацию конфликтов и автоматизацию жизненного цикла (Lifecycle Management) инфраструктуры.

---

## Основные концепции

### 1. Безопасность в Helm v4 (SSA и WASM)
Современная архитектура Helm фокусируется на минимизации прав клиента и изоляции кода расширений:
- **Server-Side Apply (SSA)**: Передача логики слияния на сторону API-сервера позволяет точно отслеживать "владельцев" (field ownership) каждого поля. Это предотвращает случайное затирание настроек, внесенных другими контроллерами (например, HPA или Mesh-инъекторами).
- **WASM Sandbox**: Плагины Helm v4 работают в изолированной среде WebAssembly. В отличие от скриптовых плагинов v3, они не имеют прямого доступа к файловой системе хоста или переменным окружения, если это не разрешено явно.

### 2. Целостность и подпись артефактов
При использовании OCI-реестров критически важно гарантировать неизменность чарта.
- **Подпись через Cosign**: Использование Sigstore/Cosign для подписи образов чартов позволяет валидировать их происхождение в конвейерах CI/CD.
- **Установка по дигесту**: Использование `sha256` вместо тегов исключает атаку типа "подмена тега" (tag moving).

### 3. Управление секретами
Helm не шифрует значения в `values.yaml` по умолчанию.
- **GitOps-подход**: Шифрование файлов с секретами в Git с помощью **SOPS** (плагин `helm-secrets`).
- **Runtime-подход**: Использование **External Secrets Operator** или **Secrets Store CSI Driver** для инъекции данных напрямую из Vault/AWS KMS в поды, минуя хранение секретов в манифестах Helm.

## Практические сценарии

### 1. Многоуровневая валидация манифестов
Для предотвращения деплоя небезопасных конфигураций используйте цепочку проверок перед `helm upgrade`:

```bash
# 1. Проверка синтаксиса
helm lint ./my-chart

# 2. Валидация против API-схем Kubernetes (SSoT: kubeconform)
helm template my-release ./my-chart | kubeconform -strict -summary -

# 3. Статический анализ безопасности (Checkov / Terrascan)
# Позволяет найти запуск от root, отсутствие лимитов и др.
checkov -d . --framework helm
```

### 2. Применение принципа минимизации прав (Least Privilege)
- **Namespace isolation**: Всегда ограничивайте область действия релиза конкретным неймспейсом.
- **History limits**: Ограничивайте количество хранимых ревизий для защиты от раздувания базы секретов кластера:
  ```bash
  helm upgrade --install app ./chart --history-max 5
  ```
- **Atomic operations**: Используйте флаг `--atomic` для автоматического отката при неудачном деплое, что предотвращает состояние "битого" релиза.

### 3. Использование JSON-схем для валидации ввода
Создайте `values.schema.json`, чтобы разработчики не могли передать некорректные типы данных, которые могут привести к падению шаблонизатора или уязвимостям.
