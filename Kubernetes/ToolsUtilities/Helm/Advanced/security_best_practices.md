# Безопасность и лучшие практики Helm

## Определения

**Безопасность Helm** — совокупность методов и инструментов для защиты секретов, валидации чартов (пакетов Helm) и разграничения прав доступа в кластере Kubernetes.

**Лучшие практики (Best Practices)** — рекомендации по структуре чартов, управлению шаблонами и интеграции в процессы CI/CD (Continuous Integration/Continuous Deployment — непрерывная интеграция и непрерывное развёртывание) для обеспечения стабильности и воспроизводимости инфраструктуры.

---

## Основные концепции

### Области обеспечения безопасности

1. **Управление секретами**: исключение хранения чувствительных данных в открытом виде в файлах `values.yaml` (YAML Ain't Markup Language). Использование внешних хранилищ или шифрования.
2. **Валидация и статический анализ**: проверка манифестов на соответствие схемам API (Application Programming Interface) Kubernetes и корпоративным политикам безопасности перед деплоем.
3. **Минимизация привилегий**: использование механизмов RBAC (Role-Based Access Control — управление доступом на основе ролей) для ограничения прав Tiller (в Helm v2) или клиентских прав (в Helm v3).
4. **Целостность данных**: проверка подписей чартов и использование доверенных OCI (Open Container Initiative)-реестров.

### Ключевые инструменты валидации

- **[kubeconform](../../kubeconform/kubeconform_overview.md)** — высокопроизводительный валидатор манифестов против схем JSON Schema API Kubernetes. **(Основной инструмент)**.
- **[helm-diff](../helm_plugins.md#helm-diff-предпросмотр-изменений)** — плагин для визуализации изменений между текущим состоянием релиза и целевым.
- **conftest** — инструмент для проверки манифестов на соответствие политикам, написанным на языке Rego (OPA — Open Policy Agent).

## Практические сценарии

### 1. Работа с секретами

**Рекомендации:**

- **Никогда** не храните пароли и ключи в `values.yaml` в открытом виде.
- Используйте плагин **[helm-secrets](https://github.com/jkroepke/helm-secrets)** совместно с SOPS для шифрования данных в Git.
- Внедряйте **External Secrets Operator** для автоматической синхронизации секретов из внешних систем (Vault, AWS Secrets Manager).

### 2. Многоуровневая валидация чарта

Для обеспечения качества и безопасности используйте цепочку проверок в конвейере CI/CD:

```bash
# 1. Синтаксический анализ и проверка на соответствие стандартам Helm
helm lint ./my-chart

# 2. Валидация сгенерированных манифестов против API Kubernetes (SSoT: kubeconform)
# Подробное руководство: [Использование kubeconform](../../kubeconform/kubeconform_overview.md)
helm template my-release ./my-chart | kubeconform -strict -summary -

# 3. Проверка политик безопасности (Policy-as-Code)
helm template my-release ./my-chart | conftest test -
```

### 3. Ограничение прав и изоляция

- **Namespace-изоляция**: всегда используйте флаг `--namespace` для логического разделения приложений и ограничения области влияния ошибок.
- **Ограничение истории**: для предотвращения раздувания хранилища конфигураций (Secrets/ConfigMaps в `kube-system` или рабочих пространствах) ограничивайте количество хранимых ревизий:

  ```bash
  helm upgrade --install my-app ./my-chart --history-max 10
  ```

- **RBAC**: создавайте выделенные ServiceAccount для процессов деплоя с минимально необходимым набором прав (Least Privilege).

### 4. Стандартизация структуры (Best Practices)

- **Версионирование**: строго следуйте SemVer (Semantic Versioning — семантическое версионирование) для поля `version` в `Chart.yaml`.
- **Фиксация зависимостей**: используйте файл `Chart.lock` (генерируется при `helm dependency update`) для обеспечения идентичности состава чарта в разных окружениях.
- **Именованные шаблоны**: выносите повторяющуюся логику (метки, префиксы имен) в `_helpers.tpl`. Подробнее: **[Шаблонизация в Helm](../helm_templating.md)**.
- **Обязательные параметры**: используйте функцию `required` в шаблонах для критичных значений, без которых приложение не сможет работать.
