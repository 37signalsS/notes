# Helmfile: декларативный оркестратор для Helm

Helmfile — это инструмент для декларативного управления множеством Helm-релизов. Он позволяет описать желаемое состояние всей инфраструктуры приложений в одном или нескольких YAML-файлах, обеспечивая повторяемость, автоматизацию и управление сложными зависимостями между чартами.

---

## Определения

| Термин | Описание |
|--------|----------|
| **Helmfile** | Декларативный оркестратор, автоматизирующий выполнение команд Helm для группы чартов. |
| **State File (`helmfile.yaml`)** | Основной файл конфигурации, описывающий репозитории, релизы, параметры окружений и зависимости. |
| **Environment (Окружение)** | Именованный контекст (например, `production`, `staging`), позволяющий варьировать значения `values` для одних и тех же релизов. |
| **Selector (Селектор)** | Механизм фильтрации релизов по именам или меткам для выборочного применения изменений. |
| **Needs (Зависимости)** | Механизм, определяющий порядок развертывания релизов. Релиз будет установлен только после успешной готовности зависимых релизов. |
| **Templates (Шаблоны)** | Блоки конфигурации, которые можно переиспользовать в разных релизах для минимизации дублирования (DRY). |
| **Bases / Helmfiles** | Механизмы разделения больших конфигураций на логические части или вложенные файлы. |
| **Hooks (Хуки)** | Скрипты или команды, выполняемые на ключевых этапах жизненного цикла (presync, postsync, on-error). |
| **Installed (Флаг установки)** | Условие (шаблон), определяющее, должен ли релиз присутствовать в целевом состоянии. Позволяет условно включать/отключать релизы без удаления конфигурации. |
| **MissingFileHandler** | Стратегия обработки отсутствующих файлов значений: `Error` (по умолчанию), `Warn`, `Info`. |
| **Inherit (Наследование)** | Механизм, позволяющий релизу наследовать свойства шаблона (namespace, chart, values) с возможностью переопределения. |
| **Common Labels / Common Annotations** | Метки и аннотации, автоматически добавляемые ко всем ресурсам релиза для единообразия и фильтрации. |
| **SkipDeps** | Флаг, отключающий автоматическое обновление зависимостей чартов перед рендерингом. |
| **Reconciliation (Реконсиляция)** | Процесс вычисления разницы между текущим состоянием кластера и желаемым состоянием, описанным в helmfile.yaml. |

## Базовые концепции

### Архитектура и принцип работы

Helmfile — это исполняемый бинарный файл (оригинальная реализация на Python, также существует порт на Go), который выступает прослойкой между желаемым состоянием (YAML-конфигурация) и CLI Helm. В отличие от прямого выполнения Helm-команд, Helmfile хранит снимок состояния (`helmfile.yaml`) и выполняет идемпотентную реконсиляцию:

1. **Парсинг:** Загрузка `helmfile.yaml`, разрешение переменных окружения, расширение Go-шаблонов.
2. **Резолвинг:** Определение актуальных репозиториев, загрузка чартов, вычисление итоговых `values` (с учетом наследования, окружений и `bases`).
3. **Сравнение:** Определение списка релизов, которые необходимо установить, обновить или удалить для достижения целевого состояния.
4. **Применение:** Последовательное (или с учетом DAG-зависимостей) выполнение Helm-операций с учетом флагов `needs` и `installed`.

### Ключевые возможности

1.  **Декларативное управление:** Описание целевого состояния инфраструктуры. Helmfile сам вычисляет необходимые действия (install, upgrade, delete) для достижения этого состояния.
2.  **Многоуровневая шаблонизация:** Поддержка Go-шаблонов непосредственно в `helmfile.yaml`. Это позволяет использовать логику, функции (например, `readFile`, `env`, `exec`) и динамически формировать конфигурацию на основе переменных окружения.
3.  **Управление зависимостями (`needs`):** Позволяет выстраивать направленный ациклический граф (DAG) развертывания. Helmfile дождется готовности (readiness) ресурсов зависимого релиза, прежде чем приступать к следующему.
4.  **Модульность и переиспользование:**
    *   **`templates`**: Позволяют выносить общие настройки релизов в именованные блоки.
    *   **`bases` / `helmfiles`**: Механизмы разделения огромных конфигураций на логические части или вложенные файлы.
5.  **Интеграция с экосистемой:** Нативная поддержка плагинов `helm-diff` (для безопасного предпросмотра изменений) и `helm-secrets` (через SOPS/Vault).
6.  **Хуки (Hooks):** Возможность запуска команд на разных стадиях жизненного цикла (пре-деплой, пост-деплой, при ошибках).

### Механизм `needs` и порядок развертывания

Поле `needs` определяет явные зависимости между релизами. Helmfile строит DAG и гарантирует, что зависимый релиз начнет развертывание только после перехода всех родительских релизов в состояние Ready. Важные нюансы:

- **Readiness:** Helmfile проверяет готовность зависимых релизов через Kubernetes API (анализ условий готовности Deployment, StatefulSet, DaemonSet и CRD).
- **Циклические зависимости:** При обнаружении циклов Helmfile завершает работу с ошибкой.
- **Селекторы в `needs`:** Поддерживается синтаксис `namespace/name` для ссылки на релиз в другом пространстве имен.
- **Параллелизм:** Независимые релизы (без общих предков/потомков) могут развертываться параллельно, что ускоряет общий процесс деплоя.

### Флаги управления поведением

| Флаг | Описание | Где применяется |
|------|----------|-----------------|
| `missingFileHandler` | `Error` (по умолчанию), `Warn`, `Info` — реакция на отсутствие файла значений. | На уровне релиза |
| `installed` | Условное включение релиза. Позволяет отключать релизы без удаления их из конфигурации. | На уровне релиза |
| `skipDeps` | Отключает автоматический `helm dependency build` перед рендерингом. | На уровне релиза |
| `force` | Применение изменений без интерактивного подтверждения. | Глобально (`helmfile apply --force`) |
| `wait` | Ожидание готовности ресурсов после деплоя (аналог `helm upgrade --wait`). | Глобально |
| `timeout` | Максимальное время ожидания готовности (по умолчанию 5m). | Глобально |
| `diff.strategy` | Выбор стратегии сравнения: `helm` (через плагин helm-diff) или `server-side` (через Kubernetes API). | Глобально |
| `sync.force` | Принудительная переустановка релизов, даже если хеш совпадает. | Глобально (`helmfile sync --force`) |

### Управление значениями и окружениями

Helmfile поддерживает иерархическое наложение значений. Значения могут быть статическими файлами, шаблонами или результатом выполнения команд.

```yaml
environments:
  default:
    values:
      - domain: dev.example.com
  production:
    values:
      - domain: example.com
      - replicas: 5
```

Порядок применения значений (от низшего к высшему приоритету):
1. Значения из `values:` релиза (в порядке объявления).
2. Значения из `environments.<name>.values`.
3. Значения из шаблонов (`templates`), если релиз их наследует.
4. Значения, сгенерированные динамически через `{{ exec ... }}` или `{{ readFile ... }}`.

## Командный интерфейс

| Команда | Описание |
|---------|----------|
| `helmfile repos` | Синхронизация репозиториев, описанных в конфигурации. |
| `helmfile diff` | Визуализация разницы между текущим состоянием кластера и конфигурацией (требуется `helm-diff`). |
| `helmfile apply` | Основная команда: выполняет `diff` и применяет только необходимые изменения. |
| `helmfile sync` | Принудительная переустановка всех релизов, даже если изменений нет. |
| `helmfile destroy` | Полное удаление ресурсов, описанных в текущем контексте/селекторе. |
| `helmfile lint` | Валидация синтаксиса шаблонов и проверка чартов. |
| `helmfile list` | Список релизов, управляемых текущим helmfile.yaml. |
| `helmfile status` | Подробный статус каждого релиза (версия, ревизия, описание). |
| `helmfile test` | Запуск helm-тестов для выбранных релизов. |

### Флаги фильтрации и выборочного применения

| Флаг | Описание | Пример |
|------|----------|--------|
| `--selector` / `-l` | Фильтр по меткам релизов. | `helmfile -l tier=storage apply` |
| `--pattern` | Фильтр по glob-паттерну имени релиза. | `helmfile -p "redis-*" sync` |
| `--skip-deps` | Пропустить обновление зависимостей чартов. | `helmfile apply --skip-deps` |
| `--interactive` | Интерактивный режим подтверждения изменений. | `helmfile apply --interactive` |

## Практические сценарии

### Комплексный пример с зависимостями и шаблонами

Пример демонстрирует использование переиспользуемых шаблонов, управления порядком деплоя (`needs`) и секретов.

```yaml
# Использование шаблонов для DRY
templates:
  default-app:
    namespace: apps
    chart: ./charts/generic-app
    missingFileHandler: Warn
    values:
      - ./config/common.yaml
      - ./config/{{ .Environment.Name }}/values.yaml

environments:
  staging:
  production:

repositories:
  - name: prometheus-community
    url: https://prometheus-community.github.io/helm-charts

releases:
  # Инфраструктурный компонент
  - name: prometheus-operator
    namespace: monitoring
    chart: prometheus-community/kube-prometheus-stack
    version: 45.0.0

  # Приложение, зависящее от инфраструктуры
  - name: backend-api
    inherit:
      - template: default-app
    # Релиз начнется только после готовности prometheus-operator
    needs:
      - monitoring/prometheus-operator
    values:
      - image: my-registry/api:v1.2.3
    secrets:
      - secrets/{{ .Environment.Name }}/api-secrets.yaml

  # Условная установка (только для prod)
  - name: cleanup-job
    chart: ./charts/cleanup
    installed: {{ eq .Environment.Name "production" }}
```

### Работа с секретами (SOPS + helm-secrets)

Helmfile поддерживает встроенную интеграцию с `helm-secrets` через поле `secrets:`. Это позволяет хранить зашифрованные файлы значений в Git, а дешифровать их только на этапе деплоя.

```yaml
releases:
  - name: payment-service
    chart: ./charts/payment
    values:
      - values/payment/{{ .Environment.Name }}.yaml
    secrets:
      - secrets/payment/{{ .Environment.Name }}.yaml.enc
```

Команда деплоя остаётся неизменной — Helmfile автоматически вызывает `sops -d` для каждого файла из `secrets:` перед передачей в Helm.

### Управление зависимостями между пространствами имен

В крупных инфраструктурах инфраструктурные релизы (например, cert-manager, ingress-nginx) часто размещаются в отдельных namespace. Helmfile поддерживает ссылки на релизы в других namespace через синтаксис `<namespace>/<release-name>`:

```yaml
releases:
  - name: cert-manager
    namespace: cert-manager
    chart: jetstack/cert-manager
    version: v1.14.3

  - name: my-app
    namespace: apps
    chart: ./charts/my-app
    needs:
      - cert-manager/cert-manager # зависимость из другого namespace
```

### Использование хуков для автоматизации

Хуки позволяют интегрироваться с внешними системами (Slack, БД, CI).

```yaml
releases:
  - name: my-db
    chart: bitnami/postgresql
    hooks:
      - events: ["presync"]
        showlogs: true
        command: "./scripts/db-backup.sh"
      - events: ["postsync"]
        command: "curl"
        args: ["-X", "POST", "-H", "Content-Type: application/json", "--data", '{"text":"Database updated in {{ .Environment.Name }}"}', "https://hooks.slack.com/..."]
```

### Группировка и фильтрация (Selectors)

Селекторы позволяют управлять частями инфраструктуры, не затрагивая остальные.

```yaml
releases:
  - name: redis
    labels:
      tier: storage
      critical: "true"
  - name: web-ui
    labels:
      tier: frontend
```

Применение изменений только для критических хранилищ:
```bash
helmfile -l tier=storage -l critical=true apply
```

Выборочное обновление по имени:
```bash
helmfile -p "redis-*" sync
```

### Динамическая генерация значений и секретов

Helmfile позволяет генерировать `values` на лету, что полезно для интеграции с внешними системами мониторинга или CMDB:

```yaml
releases:
  - name: elasticsearch
    chart: elastic/elasticsearch
    values:
      - replicas: {{ exec "oc" "get" "nodes" "-o" "json" | jq '.items | length' }}
```

Для air-graded сред, где `exec` недоступен, используйте статические файлы с предварительно вычисленными значениями.

### Интеграция в CI/CD пайплайн

Типовой этап deployment в GitLab CI / Jenkins / TeamCity:

```yaml
# .gitlab-ci.yml
deploy:
  stage: deploy
  image: alpine/helm:3.14.0
  script:
    - apk add --no-cache helmfile yq
    - helmfile -e production sync --wait --timeout 600s
  only:
    - main
```

Для безопасного предпросмотра изменений перед мержем:
```bash
# В pipeline PR
helmfile -e staging diff --selector app=backend
```

## Интеграция с GitOps (Argo CD CMP)

В 2026 году стандартом является использование Helmfile внутри Argo CD через механизм **Config Management Plugins (CMP v2)**. Это позволяет Argo CD использовать логику Helmfile для генерации манифестов, сохраняя при этом преимущества контроля дрейфа конфигурации.

**Пример CMP конфигурации для Argo CD:**
```yaml
# sidecar контейнер в argocd-repo-server
- name: helmfile-cmp
  image: ghcr.io/helmfile/helmfile:v0.150.0
  command: [/var/run/argocd/argocd-cmp-server]
  env:
    - name: HELMFILE_TMP_DIR
      value: /tmp/helmfile
```

Важные нюансы интеграции:
- **RBAC:** Sidecar должен иметь права на чтение ресурсов в целевых namespace, так как Helmfile проверяет readiness через Kubernetes API.
- **Kubeconfig:** Убедитесь, что `KUBECONFIG` доступен в контексте sidecar-контейнера или используется `ServiceAccount` с соответствующими правами.
- **Версии:** Версия образа Helmfile в CMP должна совпадать с версией, используемой локально, чтобы избежать расхождений в поведении.

### Сравнение с Helmwave

| Особенность | Helmfile | Helmwave |
|-------------|----------|----------|
| **Архитектура** | Python (legacy) / Go | Нативно Go (высокая скорость) |
| **Шаблонизация** | Частичная (values) | **Полная** (весь конфиг) |
| **Зависимости** | Линейные / `needs` | Полноценный **DAG** |
| **Мониторинг** | Внешние плагины | Встроено (**kubedog**) |
| **Планы (State)** | Отсутствуют | **Неизменяемые планы** |

Helmfile предпочтительнее для:
- Сред с legacy-инфраструктурой (широкая поддержка Helm v3/v4).
- Команд, где важнее зрелость экосистемы и документации, чем скорость выполнения.
- Интеграций через Argo CD CMP, где Helmfile имеет более зрелые механизмы обработки секретов.

Helmwave предпочтительнее для:
- Высоконагруженных пайплайнов, где время применения критично.
- Сред, требующих полной аудируемости изменений (детерминированные планы).
- Сложных графов зависимостей с параллельным развертыванием.

## Дополнительная информация

### Типовые ошибки и устранение неисправностей

| Ошибка / Симптом | Причина | Решение |
|------------------|---------|---------|
| `release "X" in namespace "Y" is not ready` | Релиз не прошел проверку readiness (лимиты ресурсов, CrashLoopBackOff). | Проверьте `kubectl describe pod` и логи; увеличьте `timeout` в helmfile. |
| `circular dependency detected` | В `needs` задана циклическая ссылка. | Визуализируйте граф: `helmfile template --graph | dot -Tpng > graph.png`. |
| `missingFileHandler: values.yaml not found` | Файл значений отсутствует, а обработчик установлен в `Error`. | Измените на `Warn` или создайте файл с дефолтными значениями. |
| `helm-diff plugin not found` | Плагин не установлен в PATH или не доступен в контейнере CI. | Установите плагин или используйте `diff.strategy: server-side`. |
| `hook failed: exit status 1` | Команда в хуке вернула ненулевой код. | Добавьте `showlogs: true` для диагностики; проверьте права и сетевую доступность. |
| Дрейф конфигурации | Прямые изменения в кластере (`kubectl edit`). | Включите `helmfile apply` в cron-задачу или webhook для периодического восстановления состояния. |

### Ограничения

1. **Производительность:** При управлении сотнями релизов последовательная обработка может быть медленной. Используйте `--concurrency` (если поддерживается версией) или разделите конфигурацию на несколько helmfile.yaml.
2. **Сложная логика:** Встроенный шаблонизатор имеет ограничения по сравнению с полноценными языками программирования. Сложную логику выносите во внешние скрипты, вызываемые через `{{ exec }}`.
3. **Offline-режим:** Для работы в air-graded средах требуется предварительное кэширование чартов и репозиториев (через `helm pull` и локальный репозиторий).
4. **Readiness-проверки:** Helmfile опирается на стандартные условия готовности Kubernetes. Для кастомных CRD может потребоваться ручная настройка прож.
5. **Совместимость версий:** Убедитесь, что версия Helmfile совместима с версией Helm, установленной в среде выполнения (особенно при переходе на Helm v4).
6. **Секреты:** Helmfile не шифрует секреты самостоятельно — используйте `helm-secrets` (SOPS) или внешние операторы (External Secrets Operator) для управления чувствительными данными.
