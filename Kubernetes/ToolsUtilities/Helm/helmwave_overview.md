# Helmwave: декларативный оркестратор для Helm

Helmwave — это декларативный инструмент на языке Go для управления релизами Helm в рамках концепции "Инфраструктура как код" (IaC). Он предлагает более гибкую и мощную альтернативу Helmfile благодаря полной шаблонизации конфигурационных файлов и глубокой интеграции с инструментами мониторинга ресурсов Kubernetes.

---

## Определения

| Термин | Описание |
|--------|----------|
| **Helmwave** | Декларативный оркестратор Helm-релизов с поддержкой нативной Go-шаблонизации всей конфигурации |
| **Plan (План)** | Набор отрендеренных манифестов и метаданных, сформированный командой `build` и готовый к применению |
| **DAG (Directed Acyclic Graph)** | Направленный ациклический граф зависимостей, определяющий порядок развёртывания релизов |
| **kubedog** | Встроенная библиотека для потокового отслеживания состояния ресурсов (логов, событий) в процессе развёртывания |
| **Lifecycle Hooks** | Пользовательские скрипты или команды, выполняемые на определенных этапах жизненного цикла релиза |

## Базовые концепции

### Полная шаблонизация всей конфигурации

В отличие от большинства других оркестраторов, Helmwave позволяет шаблонизировать не только значения (values), но и сам файл `helmwave.yml`. Это дает возможность использовать условную логику для генерации списка релизов, динамического определения репозиториев и параметров на основе переменных окружения или внешних файлов.

### Управление зависимостями (DAG)

Helmwave автоматически выстраивает порядок развёртывания на основе поля `depends_on`. Релизы устанавливаются параллельно везде, где это позволяют зависимости, что существенно ускоряет процесс деплоя в больших инфраструктурах.

### Двухфазное развёртывание: Build и Up

Процесс разделен на два четких этапа:
1.  **Build (`helmwave build`)**: Рендеринг всех шаблонов, проверка синтаксиса и создание плана в директории `.helmwave/`. План является неизменяемым артефактом, который можно проверить перед применением.
2.  **Up (`helmwave up`)**: Применение ранее созданного плана к кластеру. Если план не был создан заранее, команда `up` выполнит `build` автоматически.

### Отслеживание ресурсов через kubedog

Интеграция с `kubedog` позволяет в реальном времени видеть в терминале логи контейнеров и события Kubernetes при деплое. Это обеспечивает прозрачность процесса и быструю диагностику ошибок (например, CrashLoopBackOff или ошибки liveness-проб) без использования `kubectl`.

## Практические сценарии

### Пример сложной конфигурации helmwave.yml

```yaml
version: 0.42.0
project: platform-services

# Использование шаблонов для выбора окружения
{{ $env := env "ENV" | default "dev" }}

repositories:
  - name: argo
    url: https://argoproj.github.io/argo-helm

releases:
  - name: redis
    namespace: infrastructure-{{ $env }}
    chart:
      name: bitnami/redis
    values:
      - values/redis/{{ $env }}.yaml

  - name: app-backend
    namespace: apps-{{ $env }}
    chart:
      name: my-repo/backend
    # Зависимость: backend не начнет деплой, пока redis не будет готов
    depends_on:
      - redis@infrastructure-{{ $env }}
    values:
      - values/backend/common.yaml
    # Жизненные циклы
    lifecycle:
      pre_build:
        - echo "Starting build for {{ $env }}"
      post_up:
        - ./scripts/notify-slack.sh "Backend deployed to {{ $env }}"

  - name: app-frontend
    namespace: apps-{{ $env }}
    chart:
      name: my-repo/frontend
    depends_on:
      - app-backend@apps-{{ $env }}
```

### Основные команды и флаги

- `helmwave build` — создать план.
- `helmwave up --build` — собрать и применить план одной командой.
- `helmwave ls` — список релизов в текущем проекте.
- `helmwave down` — удаление всех ресурсов проекта из кластера.
- `helmwave build --diff` — генерация плана с отображением разницы (diff) относительно текущего состояния в кластере.

### Фильтрация через селекторы (Tags)

Вы можете помечать релизы тегами и управлять ими выборочно:
```yaml
releases:
  - name: database
    tags: ["storage", "critical"]
  - name: cache
    tags: ["storage"]
```
Применение только релизов с тегом `storage`:
```bash
helmwave up --tags storage
```

## Дополнительная информация

### Особенности эксплуатации (Ограничения)

В процессе использования Helmwave в сложных Production-средах важно учитывать следующие нюансы:
- **Чувствительность к состоянию**: Инструмент сравнивает желаемую конфигурацию с фактическим состоянием в кластере. Любые ручные правки ресурсов могут привести к некорректному определению дельты или пропуску обновлений.
- **Требования к RBAC**: Для работы (особенно в режиме интеграции) требуются расширенные права ClusterRole, чтобы считывать текущее состояние ресурсов.
- **Идемпотентность**: При обновлении ресурсов Helmwave может завершиться с ошибкой, если в чартах отсутствуют обязательные метки или аннотации управления.

### Сравнение с альтернативами

- **[Helmfile](./helmfile_overview.md)**: Стабильное, проверенное временем решение. Менее гибкое в шаблонизации самого конфига, но обладающее огромным сообществом.
- **Argo CD**: Может интегрироваться с Helmwave через **[Config Management Plugins (CMP)](../../../GitOps/ArgoCD/argocd_custom_tooling.md#сценарий-4-интеграция-helmfile-и-helmwave-cmp-v2)**. Это позволяет объединить мощь DAG-зависимостей Helmwave с надежностью GitOps-контроллера ArgoCD.

### Сравнение с Helmfile

| Особенность | Helmfile | Helmwave |
|-------------|----------|----------|
| Язык реализации | Go | Go |
| Шаблонизация | Частичная (в основном values) | Полная (весь конфиг) |
| Зависимости | Линейные / Ограниченные | Полноценный DAG |
| Скорость | Последовательно / Ограниченно | Параллельно (нативно) |
| Анализ логов | Требует плагинов | Встроено (kubedog) |
