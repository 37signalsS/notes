# Helmwave: декларативный оркестратор для Helm

Helmwave — это современный декларативный инструмент на языке Go, предназначенный для управления множеством Helm-релизов в рамках концепции "Инфраструктура как код" (IaC). В отличие от классических решений, Helmwave предлагает полную шаблонизацию всей конфигурации, нативную поддержку параллельного развертывания через DAG и встроенные инструменты мониторинга состояния ресурсов в реальном времени.

---

## Определения

| Термин | Описание |
|--------|----------|
| **Helmwave** | Декларативный оркестратор Helm-релизов с полной поддержкой Go-шаблонизации конфигурационного файла. |
| **Plan (План)** | Детерминированный артефакт (директория `.helmwave/`), содержащий отрендеренные манифесты и метаданные, готовые к применению. |
| **DAG (Directed Acyclic Graph)** | Направленный ациклический граф, автоматически выстраиваемый на основе зависимостей между релизами. |
| **kubedog** | Встроенная библиотека для потокового отслеживания логов и событий Kubernetes в процессе развертывания. |
| **Lifecycle Hooks** | Скрипты или команды, выполняемые на ключевых этапах (pre-build, post-up, pre-down и др.). |
| **State Registry** | (v0.40+) Механизм хранения планов в удаленных хранилищах (S3, GCS, Azure Blob) для командной работы. |

## Базовые концепции

### Полная шаблонизация конфигурации

Helmwave позволяет использовать Go templates непосредственно внутри `helmwave.yml.tpl`. Это радикально расширяет возможности по сравнению с Helmfile:
*   Динамическая генерация списка релизов на основе внешних YAML/JSON файлов.
*   Использование логики `if/else` и `range` для выбора репозиториев и параметров в зависимости от окружения.
*   Доступ к функциям Sprig и переменным окружения на этапе формирования конфига.

### Управление зависимостями (DAG) и параллелизм

Поле `depends_on` позволяет указывать зависимости между релизами (включая зависимости между разными пространствами имен). Helmwave:
1.  Строит граф зависимостей.
2.  Запускает независимые релизы параллельно.
3.  Гарантирует, что зависимый релиз начнет развертывание только после того, как все его "родители" перейдут в состояние `Ready` (благодаря kubedog).

### Двухфазная модель развертывания

*   **Этап 1: Build (`helmwave build`)**: Рендеринг шаблонов и создание неизменяемого плана. План содержит `manifest.yaml` для каждого релиза, что позволяет провести аудит изменений перед их внесением в кластер.
*   **Этап 2: Up (`helmwave up`)**: Применение плана. В GitOps-пайплайнах рекомендуется разделять эти шаги: `build` на этапе проверки PR, `up` на этапе слияния.

### Нативная поддержка OCI (Helm v4+)

Helmwave полностью поддерживает установку чартов из OCI-реестров, что является стандартом безопасности в 2026 году. Поддерживается аутентификация через `helm registry login` и использование дигестов (shasum) для гарантии неизменности артефактов.

## Практические сценарии

### Комплексный пример helmwave.yml.tpl

```yaml
version: 0.42.0
project: core-infrastructure

# Динамическая загрузка конфигурации окружения
{{ $env := env "ENVIRONMENT" | default "development" }}
{{ $config := readFile (printf "configs/%s.yaml" $env) | fromYaml }}

repositories:
  - name: bitnami
    url: https://charts.bitnami.com/bitnami
  - name: my-oci-repo
    url: oci://registry.example.com/charts

releases:
  # Инфраструктурный слой (Redis)
  - name: redis
    namespace: infra
    chart:
      name: bitnami/redis
    values:
      - values/redis/common.yaml
      - values/redis/{{ $env }}.yaml

  # Слой приложений с зависимостью от Redis
  - name: api-server
    namespace: apps
    chart:
      name: my-oci-repo/api-server
      version: 1.2.3
    depends_on:
      - redis@infra # Синтаксис: <name>@<namespace>
    values:
      - replicas: {{ $config.api.replicas }}
    lifecycle:
      pre_up:
        - echo "Checking DB connectivity for {{ $env }}..."
      post_up:
        - ./scripts/register-service.sh {{ .Release.Name }}
```

### Командный интерфейс и селекторы

| Команда | Описание |
|---------|----------|
| `helmwave build --diff` | Сборка плана с отображением разницы (diff) относительно кластера. |
| `helmwave up --build` | Выполнение сборки и применения за один шаг. |
| `helmwave down` | Удаление всех ресурсов, описанных в проекте. |
| `helmwave build --tags app` | Сборка плана только для релизов с тегом `app`. |

### Использование State в S3 (Командная работа)

Для синхронизации планов между участниками команды или шагами CI/CD используется удаленное хранилище:
```yaml
# helmwave.yml
project: prod-cluster
plan_dir: s3://my-terraform-state-bucket/helmwave/plans/{{ env "CI_PIPELINE_ID" }}
```

## Дополнительная информация

### Интеграция с GitOps (Argo CD CMP v2)

Helmwave идеально подходит для использования в качестве генератора манифестов в Argo CD. Это позволяет обойти ограничения стандартного плагина Helm в Argo CD (например, отсутствие нативного DAG между релизами).

**Настройка Sidecar для Argo CD:**
```yaml
# sidecar в argocd-repo-server
- name: helmwave-cmp
  image: ghcr.io/helmwave/helmwave:0.42.0
  env:
    - name: HELMWAVE_LOG_LEVEL
      value: "debug"
```

### Сравнение с Helmfile

| Особенность | Helmfile | Helmwave |
|-------------|----------|----------|
| **Архитектура** | Python (legacy) / Go | Нативно Go (высокая скорость) |
| **Шаблонизация** | Частичная (values) | **Полная** (весь конфиг) |
| **Зависимости** | Линейные / `needs` | Полноценный **DAG** |
| **Мониторинг** | Внешние плагины | Встроено (**kubedog**) |
| **Планы (State)** | Отсутствуют | **Неизменяемые планы** |
