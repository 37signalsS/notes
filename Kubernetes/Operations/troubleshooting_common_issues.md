# Распространенные проблемы и их решения в Kubernetes

---

### 1. Pod в состоянии `Pending`

*   **Симптомы:** Под не переходит в состояние `Running` и "зависает" в `Pending`.
*   **Диагностика:**
    *   `kubectl describe pod <pod-name>`
*   **Причина:** Чаще всего, планировщику не удается найти узел, удовлетворяющий требованиям пода. В данном случае, это нехватка ресурсов CPU или памяти на всех узлах кластера. В выводе `describe` будет событие `FailedScheduling` с сообщением о нехватке ресурсов.
*   **Решение:**
    1.  Проверить доступные ресурсы на узлах: `kubectl top nodes` или `kubectl describe node <node-name>`.
    2.  **Снизить запросы (`requests`) ресурсов для пода.** Это временное решение. Долгосрочное - добавление новых узлов в кластер или оптимизация потребления ресурсов приложениями.
    3.  Поскольку `requests` пода нельзя изменить напрямую после создания (поды являются неизменяемыми объектами), необходимо обновить его манифест.
        *   **Для объектов, управляющих подами (Deployment, StatefulSet, DaemonSet):**
            *   Используйте `kubectl edit <resource-type>/<resource-name>` (например, `kubectl edit deployment my-app`). Отредактируйте значения в `spec.template.spec.containers.resources.requests` и сохраните изменения. Kubernetes автоматически выполнит rolling update, создав новые поды с обновленными ресурсами.
        *   **Для напрямую созданных подов (редко):**
            *   Получите YAML-манифест пода: `kubectl get pod <pod-name> -o yaml --export > pod.yaml` (флаг `--export` может быть устаревшим в новых версиях kubectl, но помогает удалить специфичные для кластера поля).
            *   Удалите под: `kubectl delete pod <pod-name>`.
            *   Отредактируйте файл `pod.yaml`, уменьшив значения в `spec.containers.resources.requests`.
            *   Создайте под заново: `kubectl apply -f pod.yaml`.

### 2. Pod не назначается на узел из-за `nodeSelector`

*   **Симптомы:** Под деплоймента остается в состоянии `Pending`.
*   **Диагностика:**
    *   `kubectl describe pod <pod-name>` показывает событие `FailedScheduling` с сообщением о том, что ни один узел не соответствует селекторам.
*   **Причина:** В спецификации пода указан `nodeSelector`, которому не соответствует ни один из узлов кластера (например, `architecture: arm` в то время как все узлы `amd64`).
    Также причиной могут быть Taints на узлах, которые запрещают планирование подов без соответствующих Tolerations.
*   **Решение:**
    1.  Проверить метки на узлах: `kubectl get nodes --show-labels`.
    2.  Исправить `nodeSelector` в манифесте деплоймента, чтобы он соответствовал меткам на узлах.
    3.  Применить изменения: `kubectl edit deployment <deployment-name>` или `kubectl apply -f deployment.yaml`. Kubernetes автоматически создаст новый под с правильным селектором.

### 3. Deployment не создает поды

*   **Симптомы:** Объект Deployment существует, `replicas` установлены в `1` или больше, но ни один под не создается.
*   **Диагностика:**
    *   `kubectl describe deployment <deployment-name>` покажет события, связанные с невозможностью создания подов.
    *   `kubectl describe pod <pod-name>` (если поды все-таки создаются, но не запускаются) для проверки поля `serviceAccountName` в спецификации пода.
*   **Причина:** В данном случае, в шаблоне пода (`spec.template.spec`) указано имя сервисного аккаунта (`serviceAccountName`), который не существует в данном неймспейсе.
*   **Решение:**
    1.  Отредактировать манифест Deployment.
    2.  Либо удалить поле `serviceAccountName`, чтобы использовался сервисный аккаунт `default`.
    3.  Либо создать необходимый сервисный аккаунт: `kubectl create serviceaccount <account-name>`.

### 4. Deployment не может создать реплики из-за квот

*   **Симптомы:** Deployment не может развернуть нужное количество реплик.
*   **Диагностика:**
    *   `kubectl describe deployment <deployment-name> -n <namespace>` показывает, что создание пода заблокировано из-за `resource quota`.
*   **Причина:** В неймспейсе установлена `ResourceQuota`, которая ограничивает суммарное количество ресурсов (CPU, memory). Запросы нового пода превышают доступную квоту.
*   **Решение:**
    1.  Проверить квоты: `kubectl get resourcequota -n <namespace>`.
    2.  Описать квоту для деталей: `kubectl describe resourcequota <quota-name> -n <namespace>`.
    3.  Либо увеличить лимиты в объекте `ResourceQuota`, либо уменьшить запросы в спецификации пода.

### 5. Pod в состоянии `ImagePullBackOff`

*   **Симптомы:** Под не может запуститься, его статус циклически меняется на `ImagePullBackOff` или `ErrImagePull`.
*   **Диагностика:**
    *   `kubectl describe pod <pod-name>` показывает ошибки при скачивании образа.
*   **Причина:** Неверно указано имя или тег образа в спецификации контейнера.
*   **Решение:**
    1.  Исправить имя и тег образа в манифесте (`spec.containers.image`).
    2.  Применить изменения.

---

### 6. Pod в состоянии `CrashLoopBackOff`

*   **Симптомы:** Контейнер в поде запускается, сразу же падает и переходит в состояние `CrashLoopBackOff`.
*   **Диагностика:**
    *   `kubectl logs <pod-name>` для просмотра логов приложения.
    *   `kubectl logs <pod-name> --previous` для просмотра логов предыдущего "упавшего" контейнера.
*   **Причина:**
    *   Ошибка в приложении, приводящая к его немедленному завершению.
    *   Некорректная конфигурация контейнера, например, ошибочные или отсутствующие `command` и/или `args` в спецификации контейнера.
*   **Решение:** Исправить ошибку в коде приложения или в параметрах запуска (`command`, `args`) в манифесте Kubernetes.

### 7. Init-контейнер не может запуститься

*   **Симптомы:** Под "зависает" в состоянии `Init:0/1` (или `Init:Error`).
*   **Диагностика:**
    *   `kubectl describe pod <pod-name>` показывает, что init-контейнер падает.
    *   `kubectl logs <pod-name> -c <init-container-name>` для просмотра логов именно init-контейнера.
*   **Причина:** Init-контейнер пытается выполнить операции, требующие повышенных привилегий или записи в файловую систему, которая по умолчанию доступна только для чтения (например, изменение параметров ядра через `sysctl` или запись в системные каталоги). Ошибка "Read-only file system" является частым признаком.
*   **Решение:**
    1.  Для операций, требующих доступа к хост-системе или модификации ядра, необходимо добавить `securityContext` для init-контейнера и установить `privileged: true`. Это дает контейнеру доступ ко всем устройствам хоста и возможность изменять параметры ядра.

    ```yaml
    spec:
      initContainers:
      - name: sysctl-init
        image: busybox
        command: ['sh', '-c', 'sysctl -w vm.max_map_count=262144']
        securityContext:
          privileged: true
    ```
    
    **Внимание:** Использование `privileged: true` предоставляет контейнеру расширенные права и должно применяться с осторожностью. Рассмотрите возможность использования более гранулированных `capabilities` (например, `CAP_SYS_ADMIN`) или других методов для достижения цели, если это возможно.
