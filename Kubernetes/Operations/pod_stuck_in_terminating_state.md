## Устранение проблемы: под завис в состоянии Terminating

Иногда после удаления объекта (например, Deployment или StatefulSet) некоторые его поды не исчезают, а надолго остаются в состоянии `Terminating`. Попытки принудительного удаления через `kubectl delete pod` также не дают эффекта.

### Причина: блокировка при завершении работы

Когда Kubernetes удаляет под, `kubelet` на узле выполняет последовательность действий по его корректному завершению:

1.  Отправляет процессу в контейнере сигнал `SIGTERM`.
2.  Ожидает `terminationGracePeriodSeconds` (по умолчанию 30 секунд).
3.  Если процесс не завершился, отправляет `SIGKILL`.
4.  Останавливает все контейнеры.
5.  **Размонтирует тома (`volumes`)** и отсоединяет сетевые пространства имен.
6.  Удаляет объект пода из API-сервера.

Проблема возникает на шаге 5. Если какой-либо ресурс, используемый подом (чаще всего — том), не может быть освобожден, `kubelet` не может завершить процедуру удаления. Типичная ошибка — `device or resource busy`.

Корень проблемы почти всегда в том, что какой-то процесс все еще использует смонтированный том, не давая его отмонтировать. Это может быть "утекший" процесс из самого контейнера или проблема на уровне хостовой системы.

### Диагностика

#### 1. Проверка финализаторов (Finalizers)

Первым делом нужно проверить, нет ли у пода финализаторов. Финализаторы — это специальные "крючки", которые не дают удалить объект, пока не будут выполнены определенные условия.

```bash
kubectl get pod <имя-пода> -o jsonpath='{.metadata.finalizers}'
```

Если команда выводит список финализаторов (например, `kubernetes.io/pv-protection`), не удаляйте их вручную. Обычно это финализаторы хранилища (PVC, CSI), которые блокируют удаление до тех пор, пока не будет завершена очистка связанных ресурсов. Вместо этого нужно разбираться с системой хранения.

#### 2. Поиск утечки монтирования на узле

Если финализаторов нет, проблема, скорее всего, на уровне узла.

1.  **Подключитесь к узлу**, где был запланирован под.

2.  **Найдите UID пода:**

    ```bash
    # Замените <имя-пода> и <неймспейс> на ваши
    POD=<имя-пода>
    NS=<неймспейс>
    UID=$(kubectl get pod $POD -n $NS -o jsonpath='{.metadata.uid}')
    echo "UID пода: $UID"
    ```

3.  **Найдите "зависшие" точки монтирования**, связанные с этим UID:

    ```bash
    # Ищем в /proc/mounts
    grep -F "$UID" /proc/mounts
    
    # Ищем с помощью findmnt
    findmnt | grep "$UID"
    ```

    Если вы видите в выводе пути вида `/var/lib/kubelet/pods/<UID>/volumes/...` — это и есть виновник проблемы.

4.  **Определите, какой процесс держит монтирование:**
    Используйте `lsof` для поиска открытых файлов в директории пода.

    ```bash
    lsof +D /var/lib/kubelet/pods/$UID 2>/dev/null
    ```

### Решение: ручная очистка

**Внимание:** следующие шаги являются инвазивными и могут повлиять на работу узла. Действуйте осторожно.

1.  **Остановите контейнер вручную (если он еще работает):**

    Найдите ID контейнера и остановите его.

    *   **Для containerd:**

        ```bash
        crictl ps | grep $POD
        crictl stopp <ID-контейнера>
        crictl rmp <ID-контейнера>
        ```

    *   **Для Docker:**

        ```bash
        docker ps --no-trunc | grep $POD
        docker stop <ID-контейнера>
        ```
    Если ничего не помогает, в крайнем случае можно перезапустить рантайм: `systemctl restart containerd` или `systemctl restart docker`.

2.  **Принудительно размонтируйте том:**

    Если контейнер уже остановлен, но точка монтирования осталась, используйте `umount` с флагом "ленивого" размонтирования (`-l`).

    ```bash
    # Пример пути, замените на ваш
    umount -l /var/lib/kubelet/pods/$UID/volumes/kubernetes.io~csi/pvc-xxxx/mount
    ```

3.  **Удалите под:**

    После того как блокировка снята, `kubelet` должен сам завершить удаление. Если этого не произошло, попробуйте удалить под еще раз:

    ```bash
    kubectl delete pod $POD -n $NS
    ```

### Последний довод: `--force`

Если ничего из вышеперечисленного не помогло, и вы уверены, что все ресурсы на узле освобождены, можно прибегнуть к принудительному удалению записи из API-сервера.

```bash
kubectl delete pod $POD -n $NS --grace-period=0 --force
```

**Что делает эта команда:**

*   `--grace-period=0`: Немедленно инициирует удаление, не дожидаясь `SIGTERM`.
*   `--force`: Принудительно удаляет объект из etcd, даже если `kubelet` не подтвердил его фактическое удаление.

**Предупреждение:** Это API-уровневый "молот". Он просто удаляет запись из базы данных Kubernetes. Он **не решает** исходную проблему на узле (зависший процесс или точка монтирования). Используйте его только как последнее средство для очистки "мертвой" записи. С особой осторожностью применяйте к подам из [StatefulSet](../Base/statefulset.md), так как это может нарушить гарантии уникальности.
