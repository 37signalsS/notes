# Обслуживание узлов кластера: Cordon и Drain

## Определения

**Обслуживание узлов кластера** — это процесс безопасного вывода узла из эксплуатации для проведения плановых работ (например, обновления ядра, перезагрузки, изменения оборудования) и последующего возврата в работу. Процедура основана на двух ключевых командах: `cordon` и `drain`.

* **`cordon`**: Команда, которая помечает узел как недоступный для планирования (`SchedulingDisabled`). Это гарантирует, что планировщик Kubernetes больше не будет размещать на нем новые поды.
* **`drain`**: Команда, которая инициирует процесс безопасного "выселения" (eviction) всех подов с указанного узла. Перед выселением команда неявно выполняет `cordon`.

### Команды `kubectl` для обслуживания узлов

* `kubectl cordon <node-name>`: Помечает ноду как недоступную для планирования новых Подов (unschedulable). Существующие Поды продолжают работать. Это подготовительный шаг.

* `kubectl uncordon <node-name>`: Снимает пометку `unschedulable`, позволяя планировщику снова размещать новые Поды на этой ноде.

* `kubectl drain <node-name>`: Выполняет `cordon` и безопасно "выселяет" все управляемые Поды с ноды. Это гарантирует, что работа сервиса не будет нарушена, так как контроллеры создадут замену на других нодах.

  **Важные флаги:**

  * `--ignore-daemonsets`: `drain` по умолчанию остановится, если найдет Поды, управляемые `DaemonSet`. Этот флаг заставляет игнорировать их (поскольку `DaemonSet` должен работать на всех нодах, его поды не переносятся).
  * `--delete-emptydir-data`: Необходимо использовать, если на ноде есть Поды с томами `emptyDir`. Этот флаг подтверждает, что временные данные в этих томах можно безопасно удалить.
  * `--force`: Принудительно продолжить `drain`, даже если на ноде есть "голые" Поды (не управляемые `Deployment`, `StatefulSet` и т.д.). **Использовать с осторожностью.**

    **Пример:**

    ```bash
    # Безопасно очистить ноду, игнорируя системные поды DaemonSet
    kubectl drain <имя_ноды> --ignore-daemonsets
    ```

## Основные концепции

### Процесс безопасного вывода узла

1. **`cordon`**: Изоляция узла от новых размещений.
2. **`drain`**: Безопасное выселение существующих подов.
3. **Проведение работ**: Обслуживание самого узла.
4. **`uncordon`**: Возврат узла в кластер для приема новых подов.

### Нюансы команды `drain`

`kubectl drain` — "умная" команда, разработанная для предотвращения простоя приложений и потери данных. По умолчанию она остановит выполнение, если столкнется с определенными условиями. Для корректной работы почти всегда требуются дополнительные флаги:

* **Поды, управляемые `DaemonSet`**: `drain` не удаляет такие поды (например, CNI-плагины, сборщики логов), так как они являются частью инфраструктуры узла. Флаг `--ignore-daemonsets` разрешает продолжить выселение, игнорируя их.
* **Поды с `emptyDir`**: Если под использует `emptyDir` для хранения временных данных, `drain` остановится, чтобы предотвратить их потерю. Флаг `--delete-emptydir-data` подтверждает, что эти данные можно безопасно удалить.
* **"Голые" поды (без контроллера)**: Если под не управляется `ReplicaSet`, `Deployment` или `StatefulSet`, он не будет пересоздан на другом узле. Флаг `--force` требуется для принудительного удаления таких подов.
* **PodDisruptionBudgets (PDB)**: Процесс `drain` уважает PDB, гарантируя, что выселение не нарушит заданный уровень доступности приложения.

## Практические сценарии

### 1. Стандартный безопасный вывод узла

Этот сценарий используется, когда выселяемые поды могут быть перенесены на любой доступный узел в кластере.

**Шаг 1: Запретить размещение новых подов (`cordon`)**

```bash
kubectl cordon <имя-вашей-ноды>
```

*Узел получит статус `SchedulingDisabled`. Существующие поды продолжат работать.*

**Шаг 2: Выселить существующие поды (`drain`)**
Итоговая команда для большинства случаев, которая игнорирует системные поды DaemonSet и разрешает удаление временных данных:

```bash
kubectl drain <имя-вашей-ноды> --ignore-daemonsets --delete-emptydir-data
```

**Шаг 3: Провести обслуживание**
Теперь, когда на узле не осталось рабочих подов, можно безопасно его перезагружать, обновлять ПО и выполнять другие работы.

**Шаг 4: Вернуть узел в работу (`uncordon`)**
После завершения обслуживания разрешите планировщику снова использовать узел:

```bash
kubectl uncordon <имя-вашей-ноды>
```

### 2. Перенос подов на конкретный узел

`kubectl drain` не позволяет напрямую указать целевой узел. Решение всегда принимает планировщик. Чтобы повлиять на его выбор, нужно использовать один из следующих подходов.

#### Способ 1: "Силовой" (не рекомендуется для production)

Этот метод заключается в искусственном ограничении выбора для планировщика.

1. **Запретить размещение на всех узлах**, кроме целевого, с помощью `kubectl cordon`.
2. **Выполнить `drain` исходного узла**. Так как у планировщика останется только один доступный узел, все поды будут перенесены туда.
3. **Вернуть все узлы в работу** с помощью `kubectl uncordon`.

#### Способ 2: Декларативный через `nodeAffinity` (рекомендуемый)

Это "правильный" и предсказуемый способ, подходящий для production и автоматизации.

1. **Добавить метку на целевой узел**:

    ```bash
    kubectl label node <целевая-нода> my-target-node=true
    ```

2. **Модифицировать манифест `Deployment` или `StatefulSet`**: Добавить правило `nodeAffinity`, которое требует размещения подов на узле с меткой `my-target-node=true`.

    ```yaml
    spec:
      template:
        spec:
          affinity:
            nodeAffinity:
              requiredDuringSchedulingIgnoredDuringExecution:
                nodeSelectorTerms:
                - matchExpressions:
                  - key: my-target-node
                    operator: In
                    values:
                    - "true"
    ```

3. **Применить изменения и выполнить `drain`**: После применения манифеста и перезапуска подов (`kubectl rollout restart ...`) `kubectl drain` заставит планировщик переместить поды на узел с нужной меткой в соответствии с правилом `nodeAffinity`.
