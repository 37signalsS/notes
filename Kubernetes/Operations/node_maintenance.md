# Обслуживание узлов кластера: Cordon и Drain

Процедура безопасного вывода узла из эксплуатации для проведения обслуживания (например, обновления ядра, перезагрузки) состоит из двух основных шагов: `cordon` и `drain`.

---

## 1. Стандартный безопасный вывод узла (перенос подов на любые узлы)

### Шаг 1: `cordon` — запрет на размещение новых подов

Сначала узел необходимо пометить как не доступный для планирования. Это гарантирует, что Kubernetes не будет размещать на нем новые поды, пока вы проводите обслуживание.

```bash
kubectl cordon <имя-вашей-ноды>
```
После этой команды узел получит статус `SchedulingDisabled`. Существующие поды продолжат на нем работать.

### Шаг 2: `drain` — безопасное выселение подов

Эта команда выполняет `cordon` неявно, а затем инициирует процесс безопасного "выселения" (eviction) всех подов с узла.

```bash
kubectl drain <имя-вашей-ноды>
```

**Важные нюансы и флаги:**

`kubectl drain` очень осторожен и остановится, если может потерять данные или нарушить работу системных сервисов. Поэтому почти всегда требуются дополнительные флаги:

*   `--ignore-daemonsets`: `drain` по умолчанию не удаляет поды, управляемые объектом `DaemonSet` (например, CNI-плагины или сборщики логов), так как они должны работать на каждом узле. Этот флаг разрешает продолжить выселение, игнорируя их. Сами поды `DaemonSet` не будут удалены.
*   `--delete-emptydir-data`: `drain` остановится, если на узле есть поды, использующие `emptyDir`. Это сделано для того, чтобы администратор подтвердил, что временные данные в этих директориях можно безопасно удалить.
*   `--force`: Требуется для выселения подов, у которых нет "владельца" (ReplicaSet, Deployment, StatefulSet). Такие поды не будут созданы заново, поэтому флаг требует явного подтверждения.

**Итоговая команда для большинства случаев:**

```bash
kubectl drain <имя-вашей-ноды> --ignore-daemonsets --delete-emptydir-data
```

Процесс `drain` будет уважать **PodDisruptionBudgets (PDB)**, гарантируя, что работа ваших приложений не будет нарушена.

### Шаг 3: Проведение работ на узле

Теперь, когда на узле не осталось рабочих подов (кроме системных от DaemonSet), вы можете безопасно его перезагружать, обновлять ПО и т.д.

### Шаг 4: `uncordon` — возврат узла в работу

После завершения обслуживания верните узел в кластер, разрешив планировщику снова размещать на нем поды.

```bash
kubectl uncordon <имя-вашей-ноды>
```

## 2. Перенос подов на КОНКРЕТНЫЙ узел

`kubectl drain` не имеет флага `--target-node`. Решение о размещении пода всегда принимает планировщик. Чтобы заставить его выбрать конкретный узел, нужно искусственно ограничить его выбор.

### Способ 1: "Силовой" (не рекомендуется для production)

Этот метод грубый, но быстрый для тестовых сред.

1.  **Запретить размещение на ВСЕХ узлах, кроме целевого:**
    ```bash
    # Сначала находим все узлы, которые не являются целевым или исходным
    kubectl get nodes
    # Для каждого "лишнего" узла выполняем cordon
    kubectl cordon <другая-нода-1>
    kubectl cordon <другая-нода-2>
    ...
    ```
2.  **Выполнить `drain` исходного узла:**
    ```bash
    kubectl drain <исходная-нода> --ignore-daemonsets --delete-emptydir-data
    ```
    Так как у планировщика остался только один доступный узел для размещения (`<целевая-нода>`), все поды будут перенесены туда.

3.  **Вернуть все узлы в работу:**
    Не забудьте после этого вернуть все "закрытые" узлы обратно командой `uncordon`.
    ```bash
    kubectl uncordon <другая-нода-1>
    kubectl uncordon <другая-нода-2>
    kubectl uncordon <исходная-нода>
    ```

### Способ 2: Декларативный, через `nodeAffinity` (рекомендуемый)

Это "правильный" способ в Kubernetes, основанный на декларативном подходе.

1.  **Добавить метку на целевой узел:**
    ```bash
    kubectl label node <целевая-нода> my-target-node=true
    ```

2.  **Модифицировать манифест вашего `Deployment` или `StatefulSet`:**
    Добавьте в спецификацию пода правило `nodeAffinity`, которое заставит планировщик предпочитать узел с вашей меткой.

    ```yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: my-app
    spec:
      replicas: 3
      template:
        spec:
          affinity:
            nodeAffinity:
              requiredDuringSchedulingIgnoredDuringExecution:
                nodeSelectorTerms:
                - matchExpressions:
                  - key: my-target-node
                    operator: In
                    values:
                    - "true"
          containers:
          ...
    ```

3.  **Применить изменения и выполнить `drain`:**
    *   Примените обновленный манифест (`kubectl apply -f ...`).
    *   Запустите `rollout restart` для вашего Deployment, чтобы поды начали пересоздаваться с учетом нового правила `affinity`.
    *   Затем выполните `kubectl drain <исходная-нода>`.

    При выселении подов планировщик увидит правило `nodeAffinity` и разместит их на узле с меткой `my-target-node=true`. Этот способ сложнее, но гораздо более предсказуем и лучше подходит для автоматизации и production-сред.
