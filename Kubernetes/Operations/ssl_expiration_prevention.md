# Предотвращение истечения SSL-сертификатов в Kubernetes

## Определения

**SSL/TLS Rotation (Ротация сертификатов)** — процесс планового обновления цифровых сертификатов до истечения их срока действия. В Kubernetes ротация должна быть автоматизирована для обеспечения непрерывности работы (High Availability) и исключения человеческого фактора.

**Kubelet Serving Certificate** — сертификат, используемый агентом `kubelet` для идентификации себя при входящих запросах от API-сервера (например, при командах `kubectl logs`, `exec`, `metrics-server`).

**CSR (Certificate Signing Request) Approver** — контроллер или процесс, ответственный за автоматическую проверку и одобрение запросов на подпись сертификатов. Без него автоматизация ротации на уровне узлов невозможна.

**ARI (ACME Renewal Information)** — расширение протокола ACME, позволяющее центру сертификации (например, Let's Encrypt) рекомендовать клиенту (cert-manager) оптимальное время для продления сертификата, основываясь на нагрузке или технических работах на стороне CA.

## Основные концепции

Стратегия защиты от истечения сертификатов в Kubernetes строится на трех независимых эшелонах:

### 1. Эшелон инфраструктуры (Control Plane и etcd)
Самый критический уровень. Истечение сертификата API-сервера или etcd приводит к полной потере управления кластером.
* **Метод:** Плановые обновления версии кластера или принудительное продление через `kubeadm`.
* **Доверие:** Корневые сертификаты (CA) имеют срок действия 10 лет, листовые — 1 год.

### 2. Эшелон узлов (Kubelet)
Обеспечивает связь между API и агентами на узлах.
* **Client Certs:** Используются для авторизации узла в API. Обновляются автоматически при обновлении кластера или через механизм `rotate-certificates`.
* **Server Certs:** Требуются для безопасного сбора метрик и логов. Требуют настройки `serverTLSBootstrap`.

### 3. Эшелон приложений
Сертификаты для Ingress, Gateway API и внутренних mTLS-соединений (Service Mesh).
* **Метод:** Полная автоматизация через ACME/Vault с использованием `cert-manager`.

## Практические сценарии

### 1. Автоматизация ротации Control Plane (kubeadm)

В кластерах под управлением `kubeadm` основным методом продления является регулярное обновление минорной версии (Upgrade).

* **Ручной контроль (Check-point):**
  ```bash
  sudo kubeadm certs check-expiration
  ```
* **Принудительное продление:**
  Если обновление кластера невозможно, сертификаты продлеваются командой:
  ```bash
  sudo kubeadm certs renew all
  ```
  *Примечание: После продления необходим перезапуск статических подов (API-сервер, Scheduler, Controller Manager).*

Подробная инструкция: **[Управление сертификатами через kubeadm](./certificate_management.md)**.

### 2. Настройка автоматической ротации для Kubelet

Для исключения ручного одобрения (approve) сертификатов узлов рекомендуется использовать автоматизацию.

**Шаг 1: Настройка Kubelet**
В файле конфигурации `kubelet-config.yaml` или через флаги запуска:
```yaml
serverTLSBootstrap: true
rotateCertificates: true
```

**Шаг 2: Автоматизация одобрения (CSR Approver)**
Kubernetes по умолчанию не одобряет серверные сертификаты Kubelet из соображений безопасности. Для автоматизации можно использовать:
*   **kube-controller-manager:** Настройка RBAC для автоматического одобрения запросов от `system:nodes`.
*   **Cert-manager:** Использование `csi-driver` или кастомных аппруверов.

### 3. Настройка cert-manager для приложений

Для предотвращения истечения сертификатов Let's Encrypt используйте параметр `renewBefore`.

```yaml
apiVersion: cert-manager.io/v1
kind: Certificate
metadata:
  name: api-tls
spec:
  secretName: api-tls-secret
  issuerRef:
    name: letsencrypt-prod
    kind: ClusterIssuer
  duration: 2160h # 90 дней
  renewBefore: 360h # Начать продление за 15 дней до конца срока
  dnsNames:
  - api.example.com
```

**Использование ARI (v1.15+):**
Современные версии `cert-manager` поддерживают ARI, что позволяет игнорировать жестко заданный `renewBefore` и следовать рекомендациям Let's Encrypt. Убедитесь, что ваш `ClusterIssuer` поддерживает этот функционал.

## Мониторинг и оповещения

Мониторинг — это последняя линия обороны.

### Метрики инфраструктуры (Prometheus)
Поскольку API-сервер не экспортирует сроки действия своих сертификатов в метрики напрямую, рекомендуется использовать:
1.  **Kube-state-metrics:** Для мониторинга объектов `Certificate` от cert-manager.
2.  **Custom Exporter:** Скрипт-экспортер, читающий `/etc/kubernetes/pki`.

### Метрики Cert-manager
```yaml
# Алерт: сертификат истекает менее чем через 21 день
- alert: KubernetesCertExpiringSoon
  expr: certmanager_certificate_expiration_timestamp_seconds - time() < (21 * 24 * 3600)
  for: 1h
  labels:
    severity: warning
  annotations:
    summary: "Сертификат {{ $labels.name }} истекает скоро"
```

### Внешний мониторинг (Blackbox Exporter)
Проверка сертификата "глазами пользователя" на внешнем эндпоинте.
```yaml
# Алерт: SSL на внешнем URL истекает через 14 дней
- alert: SSLCertificateExpiring
  expr: probe_ssl_earliest_cert_expiry - time() < 86400 * 14
  for: 10m
  labels:
    severity: critical
```
Подробности: **[Blackbox Exporter: Метрики и алертинг](../../Prometheus/Exporters/blackbox/blackbox_exporter_metrics_and_alerting.md)**.

## Дополнительная информация

### Лучшие практики

| Рекомендация | Техническое обоснование |
| :--- | :--- |
| **Короткие сроки (Short-lived)** | Используйте сертификаты на 24-48 часов (через Vault), чтобы минимизировать окно компрометации и сделать процесс ротации регулярным (проверяемым). |
| **Изоляция CA** | Не используйте Cluster CA для подписи пользовательских приложений. Используйте отдельные Issuer в cert-manager. |
| **Отказ от статичных Secret** | Не создавайте TLS-секреты вручную через `kubectl create secret tls`. Это ломает цепочку автоматизации. |
| **Интеграция с Vault** | Для Enterprise-сред используйте HashiCorp Vault как бэкенд для cert-manager. |
