# Диагностика и решение распространенных ошибок в Kubernetes

Эта заметка является структурированным справочником по наиболее частым ошибкам в Kubernetes, методам их диагностики и устранения.

## 1. Pod в состоянии `Pending` (Ожидание)

### Определение

Состояние `Pending` означает, что API-сервер принял спецификацию пода, но планировщик (`kube-scheduler`) еще не может разместить его на одном из узлов (Nodes). Под ожидает решения планировщика.

### Основные концепции

*   **Планировщик (`kube-scheduler`):** Компонент Control Plane, который отвечает за назначение подов на узлы. Он фильтрует узлы по ряду критериев.
*   **Ресурсы (`requests` и `limits`):** `requests` — это гарантированное количество ресурсов (CPU, memory) для контейнера. Планировщик использует это значение для выбора узла.
*   **Селекторы и Affinity (`nodeSelector`, `nodeAffinity`):** Правила, которые ограничивают выбор узлов на основе их меток (`labels`).
*   **Taints и Tolerations:** `Taints` (отравление) — это свойство узла, которое "отталкивает" поды. `Tolerations` (терпимость) — это свойство пода, которое позволяет ему размещаться на "отравленном" узле.
*   **Persistent Volumes (PV, PVC):** Механизм для работы с постоянными хранилищами. Под, запрашивающий том (`PVC`), не запустится, пока соответствующий том (`PV`) не будет найден или динамически создан.

### Практические сценарии

#### Диагностика

Основная команда для анализа — `kubectl describe pod <pod-name>`. В разделе `Events` будет указана причина, по которой планировщик не может найти узел.

```
Events:
  Type     Reason            Age        From               Message
  ----     ------            ----       ----               -------
  Warning  FailedScheduling  <unknown>  default-scheduler  0/3 nodes are available: 3 Insufficient cpu.
```

#### Распространенные случаи и их решения

1.  **Нехватка ресурсов (`Insufficient cpu/memory`)**
    *   **Причина:** Под запрашивает больше ресурсов, чем доступно на любом из узлов.
    *   **Решение:**
        *   Уменьшите `requests` в спецификации пода.
        *   Добавьте новые узлы в кластер.
        *   Проверьте, не занимают ли другие поды слишком много ресурсов.

2.  **Несоответствие селекторам (`nodeSelector`, `affinity`)**
    *   **Причина:** Ни один узел не удовлетворяет правилам `nodeSelector` или `affinity` пода.
    *   **Решение:**
        *   Проверьте метки на узлах: `kubectl get nodes --show-labels`.
        *   Скорректируйте `nodeSelector` или `affinity` в манифесте.

3.  **Узел имеет `Taints`, а у пода нет `Tolerations`**
    *   **Причина:** Узлы "отравлены" и не принимают поды без соответствующего `toleration`.
    *   **Решение:** Добавьте необходимый `toleration` в спецификацию пода.

4.  **`PersistentVolumeClaim` (PVC) не может быть удовлетворен**
    *   **Причина:** PVC пода находится в состоянии `Pending`, так как нет подходящего `PersistentVolume` (PV) или `StorageClass` не может его создать.
    *   **Решение:** Проверьте статус PVC (`kubectl describe pvc <pvc-name>`) и решайте проблему на уровне системы хранения.

## 2. Pod в состоянии `ImagePullBackOff` / `ErrImagePull`

### Определение

Состояние `ImagePullBackOff` означает, что `kubelet` на узле не может скачать образ контейнера из репозитория. `ErrImagePull` — это начальная ошибка, которая при повторных неудачах переходит в `ImagePullBackOff` с нарастающей задержкой между попытками.

### Основные концепции

*   **Kubelet:** Агент, работающий на каждом узле и отвечающий за жизненный цикл контейнеров, включая скачивание образов.
*   **Репозиторий образов:** Хранилище (например, Docker Hub, GCR, Harbor), откуда скачиваются образы.
*   **ImagePullSecrets:** Секрет Kubernetes, содержащий учетные данные для доступа к приватным репозиториям.

### Практические сценарии

#### Диагностика

`kubectl describe pod <pod-name>` покажет детальную ошибку в разделе `Events`.

```
Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Warning  Failed     2m (x4 over 3m)    kubelet            Failed to pull image "my-app:1.1": rpc error: code = Unknown desc = Error response from daemon: manifest for my-app:1.1 not found
```

#### Распространенные случаи и их решения

1.  **Неверное имя или тег образа**
    *   **Причина:** Опечатка в `spec.containers.image`.
    *   **Решение:** Проверьте и исправьте имя и тег образа в манифесте.

2.  **Проблемы с доступом к приватному репозиторию**
    *   **Причина:** Отсутствует или неверно настроен `imagePullSecrets`.
    *   **Решение:** Убедитесь, что `imagePullSecrets` создан корректно, содержит правильные credentials и указан в спецификации пода.

3.  **Образ не существует**
    *   **Причина:** Образ с указанным тегом никогда не был загружен в репозиторий.
    *   **Решение:** Проверьте наличие образа и тега в репозитории.

4.  **Сетевые проблемы**
    *   **Причина:** Узел не имеет сетевого доступа к репозиторию (проблемы с DNS, firewall, прокси).
    *   **Решение:** Проверьте доступность репозитория с узла (например, с помощью `curl` или `docker pull` непосредственно на узле).

## 3. Pod в состоянии `CrashLoopBackOff`

### Определение

Состояние `CrashLoopBackOff` означает, что контейнер в поде запускается, но немедленно завершается с ошибкой. `kubelet` пытается его перезапустить, но сбой повторяется в цикле, с каждым разом увеличивая интервал перед перезапуском.

### Основные концепции

*   **Код выхода (Exit Code):** Процесс в контейнере при завершении возвращает код. `0` означает успешное завершение, любой другой код — ошибку.
*   **Логи контейнера:** Стандартные потоки вывода (`stdout`) и ошибок (`stderr`) приложения, которые являются основным источником информации для диагностики.
*   **Probes (Liveness, Readiness):** Проверки жизнеспособности и готовности. Неудачная `livenessProbe` приведет к перезапуску контейнера, что также может вызвать `CrashLoopBackOff`.

### Практические сценарии

#### Диагностика

1.  **Просмотр логов предыдущего падения:** Это самая важная команда.
    ```bash
    kubectl logs <pod-name> --previous
    ```
2.  **Анализ статуса пода:** `kubectl describe pod <pod-name>` покажет `Last State` с причиной `Error` и кодом выхода (`Exit Code`), либо причину `OOMKilled`.
3.  **Просмотр текущих логов:** `kubectl logs <pod-name>`. Может быть пустым, если контейнер падает слишком быстро.

#### Распространенные случаи и их решения

1.  **Ошибка в приложении**
    *   **Причина:** Неперехваченное исключение, баг, который проявляется при старте.
    *   **Решение:** Анализируйте логи (`--previous`), исправляйте код приложения.

2.  **Неверная конфигурация**
    *   **Причина:** Отсутствуют переменные окружения, не смонтирован `ConfigMap`/`Secret`, неверные аргументы командной строки (`command`/`args`).
    *   **Решение:** Проверьте конфигурацию пода и убедитесь, что все зависимости (конфиги, секреты) доступны.

3.  **Проблемы с зависимостями**
    *   **Причина:** Приложение не может подключиться к базе данных или другому сервису при старте.
    *   **Решение:** Убедитесь, что внешние сервисы доступны из пода (проверьте DNS, сетевые политики).

4.  **Неудачная liveness-проба**
    *   **Причина:** `livenessProbe` завершается с ошибкой, и `kubelet` принудительно перезапускает контейнер.
    *   **Решение:** Проверьте корректность и таймауты `livenessProbe`. Возможно, приложению нужно больше времени для старта.

5.  **Недостаточно прав доступа (RBAC)**
    *   **Причина:** Приложение внутри контейнера при старте пытается обратиться к API Kubernetes, но у его `ServiceAccount` нет на это прав. В логах можно увидеть ошибки `Forbidden` или `permission denied`.
    *   **Пример из практики:** Контейнер-сборщик логов (log shipper) пытается получить логи с других подов в кластере. Для этого ему необходимо право `get` для ресурса `pods/log`. Если этого права нет, приложение-агент может аварийно завершиться.
    *   **Диагностика:**
        1.  Изучите логи контейнера (`kubectl logs <pod> --previous`). Если вы видите сообщения об ошибках доступа к API, это ваш случай.
        2.  Определите `ServiceAccount`, который использует под: `kubectl get pod <pod-name> -o yaml | grep serviceAccountName`. Если не указан, используется `default`.
        3.  Проверьте, есть ли у этого `ServiceAccount` нужные права с помощью `kubectl auth can-i`:
            ```bash
            # Замените на ваши namespace и serviceaccount
            kubectl auth can-i get pods/log \
              --namespace my-app-ns \
              --as=system:serviceaccount:my-app-ns:my-app-sa
            # Ответ "no" подтвердит проблему.
            ```
    *   **Решение:**
        1.  Найдите `Role` или `ClusterRole`, привязанную к вашему `ServiceAccount` через `RoleBinding` или `ClusterRoleBinding`.
        2.  Добавьте в `rules` этой роли необходимые права. Для примера с логами:
            ```yaml
            - apiGroups: [""]
              resources: ["pods/log"]
              verbs: ["get", "list", "watch"]
            ```
        3.  Примените изменения и перезапустите под.

#### Частный случай: `Init:CrashLoopBackOff`

Если в `CrashLoopBackOff` уходит `initContainer`, диагностика аналогична, но для просмотра логов нужно указать имя init-контейнера: `kubectl logs <pod-name> -c <init-container-name>`.

## 4. `CreateContainerConfigError`

### Определение

Эта ошибка возникает до запуска контейнера и означает, что `kubelet` не может создать его конфигурацию.

### Практические сценарии

#### Диагностика

`kubectl describe pod <pod-name>` даст точный ответ в разделе `Events`.

```
Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Warning  Failed     56s (x6 over 1m)   kubelet            Error: configmap "missing-config" not found
```

#### Распространенные случаи и их решения

1.  **Отсутствует `ConfigMap` или `Secret`**
    *   **Причина:** Под пытается смонтировать или использовать как переменные `ConfigMap` или `Secret`, который не существует в данном namespace.
    *   **Решение:** Создайте недостающий ресурс или исправьте ссылку на него в манифесте пода.

## 5. `OOMKilled`

### Определение

`OOMKilled` (Out of Memory Killed) — это не статус пода, а причина (`Reason`) завершения контейнера. Она означает, что процесс в контейнере был принудительно "убит" ядром операционной системы узла из-за превышения выделенного лимита памяти.

### Основные концепции

*   **`requests` и `limits`:** `memory.limits` — это жесткое ограничение памяти для контейнера. При его превышении контейнер будет завершен с кодом выхода `137`.
*   **QoS (Quality of Service):** Класс `Guaranteed` (где `requests` == `limits`) обеспечивает наибольшую защиту от `OOMKilled` со стороны узла, но не от превышения собственного лимита.

### Практические сценарии

#### Диагностика

1.  **Анализ статуса пода:** `kubectl describe pod <pod-name>` в `Last State` покажет `Reason: OOMKilled` и `Exit Code: 137`.
2.  **Мониторинг:** Используйте `kubectl top pod <pod-name>` для наблюдения за потреблением ресурсов.
3.  **Анализ логов:** Проверьте логи ядра на узле (`dmesg` или `journalctl -k`), чтобы найти сообщения об OOM killer.

#### Распространенные случаи и их решения

1.  **Превышение `limits.memory`**
    *   **Причина:** Приложение потребило больше памяти, чем ему разрешено.
    *   **Решение:** Увеличьте `limits.memory` в манифесте, предварительно проанализировав потребление.

2.  **Утечка памяти в приложении**
    *   **Причина:** Баг в коде, который приводит к постоянному росту потребления памяти.
    *   **Решение:** Используйте инструменты профилирования памяти для вашего языка программирования и оптимизируйте код.

## 6. `NodeNotReady` / `Node Unreachable`

### Определение

Это статус узла (`Node`), а не пода. `NotReady` означает, что `kubelet` на узле работает, но сообщает, что узел не готов принимать новые поды. `Unreachable` означает, что `kube-apiserver` не может связаться с `kubelet` на узле.

### Практические сценарии

#### Диагностика

1.  **Проверка статуса узлов:** `kubectl get nodes`.
2.  **Анализ состояния узла:** `kubectl describe node <node-name>`. Обратите внимание на секцию `Conditions`. Статусы `MemoryPressure`, `DiskPressure` или `PIDPressure` в состоянии `True` укажут на нехватку ресурсов. `Ready` будет `False` или `Unknown`.
3.  **Проверка `kubelet` на узле:** Подключитесь к проблемному узлу по SSH и выполните:
    *   `systemctl status kubelet`
    *   `journalctl -u kubelet -f`
    *   Проверьте системные ресурсы (`top`, `df -h`, `free -m`).

#### Распространенные случаи и их решения

1.  **Узел выключен или недоступен по сети:** Проверьте физическое состояние и сетевое подключение.
2.  **Сбой `kubelet`:** Процесс `kubelet` "упал" или не отвечает. Перезапустите его.
3.  **Перегрузка узла:** Нехватка CPU, памяти или диска мешает работе `kubelet`. Освободите ресурсы или увеличьте их.

## 7. `Forbidden` (403) / `Unauthorized` (401)

### Определение

Эти ошибки возникают при попытке доступа к ресурсам через `kubectl` или API Kubernetes.
*   **401 Unauthorized:** Kubernetes не смог вас аутентифицировать. Проблема в вашем токене, сертификате или другом методе аутентификации.
*   **403 Forbidden:** Kubernetes вас аутентифицировал, но у вас нет прав (RBAC) на выполнение запрошенной операции (например, `get pods` в определенном `namespace`).

### Основные концепции

*   **Authentication:** Процесс проверки личности пользователя (кто вы?).
*   **Authorization (RBAC):** Процесс проверки прав пользователя на выполнение действия (что вам можно делать?). Определяется через `Role`, `ClusterRole`, `RoleBinding` и `ClusterRoleBinding`.
*   **Kubeconfig:** Файл, содержащий информацию для подключения к кластеру, включая учетные данные.

### Практические сценарии

#### Диагностика

Главный инструмент для отладки RBAC — `kubectl auth can-i`:

```bash
# Могу ли я смотреть поды в неймспейсе 'default'?
kubectl auth can-i get pods -n default

# Может ли это делать сервисный аккаунт 'my-sa'?
kubectl auth can-i list secrets -n kube-system --as=system:serviceaccount:default:my-sa
```

#### Решение

*   **401:** Проверьте ваш `kubeconfig` (`kubectl config view`) или обновите токен/сертификат.
*   **403:** Создайте или исправьте `Role`/`ClusterRole` и `RoleBinding`/`ClusterRoleBinding`, чтобы предоставить необходимые права.

## 8. Pod завис в состоянии `Terminating`

### Определение

Под не может завершить свою работу и "зависает" в состоянии `Terminating`.

### Практические сценарии

#### Диагностика

Чаще всего это происходит, когда том (`volume`), используемый подом, не может быть размонтирован, потому что какой-то процесс все еще его использует. Ошибка на уровне узла — `device or resource busy`.

1.  Подключитесь к узлу, где был запущен под.
2.  Найдите UID пода: `kubectl get pod <pod-name> -o jsonpath='{.metadata.uid}'`
3.  Найдите "зависшие" точки монтирования: `findmnt | grep <UID>`
4.  Найдите процесс, который держит монтирование: `lsof +D /var/lib/kubelet/pods/<UID>`

#### Решение

1.  Попробуйте принудительно размонтировать том на узле: `umount -l <путь-к-точке-монтирования>`.
2.  Если это не помогает, как крайняя мера, используйте принудительное удаление. **Внимание: это может быть опасно для Stateful-приложений, так как может привести к потере данных!**
    ```bash
    kubectl delete pod <pod-name> --grace-period=0 --force
    ```
    Эта команда удаляет запись из `etcd`, но не решает исходную проблему на узле.

## 9. Pod в статусе `Evicted` (Выселен)

### Определение

Статус `Evicted` означает, что Kubernetes принудительно выселил под с узла. Это происходит, когда на узле заканчиваются ресурсы (чаще всего память или место на диске).

### Основные концепции

*   **Node Pressure:** Состояние узла, при котором ему не хватает ресурсов (`MemoryPressure`, `DiskPressure`). `kubelet` активно пытается освободить ресурсы, выселяя поды.
*   **QoS (Quality of Service):** Kubernetes выселяет поды на основе их класса качества. Первыми выселяются поды с QoS `BestEffort` (без `requests` и `limits`), затем `Burstable`. Поды с QoS `Guaranteed` (`requests` == `limits`) выселяются последними.

### Практические сценарии

#### Диагностика

*   `kubectl describe pod <pod-name>` покажет причину выселения.
*   `kubectl describe node <node-name>` покажет состояние `Pressure` на узле.

#### Решение

1.  **Удаление пода:** Выселенный под не удаляется автоматически. Его нужно удалить вручную: `kubectl delete pod <pod-name>`. `ReplicaSet` или `Deployment` создаст новый (если есть ресурсы в кластере).
2.  **Профилактика:**
    *   **Всегда указывайте `requests` и `limits` для ваших приложений**, чтобы присвоить им адекватный QoS и сделать планирование более предсказуемым.
    *   Настройте мониторинг ресурсов на узлах, чтобы заранее предсказывать и решать проблемы.
