# Поиск и устранение неисправностей в Kubernetes

## Определение

Поиск и устранение неисправностей в Kubernetes — это процесс диагностики, анализа и решения проблем, возникающих в кластере. Он включает применение специфических инструментов и методик для восстановления нормального функционирования систем.
Для получения информации о конкретных распространенных ошибках (таких как `CrashLoopBackOff`, `ImagePullBackOff`, `Pending` и др.) обратитесь к справочнику: [Распространенные ошибки в Kubernetes и их решения](./common_errors.md).

### Основные инструменты командной строки

#### `kubectl describe`: Детальная диагностика ресурсов

`kubectl describe` — основной инструмент для получения подробной информации о состоянии любого ресурса. В отличие от `kubectl get -o yaml`, `describe` предоставляет текущий статус, недавние события и диагностические данные.

**Ключевые поля вывода:**
*   **`State` / `Last State`:** Текущее и предыдущее состояние контейнера.
*   **`Reason`:** Причина последнего завершения (например, `OOMKilled`, `Error`, `Completed`).
*   **`Exit Code`:** Код выхода процесса. `137` указывает на `OOMKilled`, ненулевой код — на ошибку.
*   **`Restart Count`:** Количество перезапусков контейнера. Значение `> 0` прямо указывает на проблему.
*   **`Events`:** Хронологический список событий, связанных с ресурсом. **Приоритетный раздел для проверки.**

#### `kubectl logs`: Анализ логов контейнеров

`kubectl logs` позволяет просматривать стандартный вывод (`stdout`) и ошибки (`stderr`) процессов, запущенных в контейнерах.

**Ключевые флаги:**
*   `--previous` (`-p`): Показывает логи контейнера непосредственно перед его последним падением. Критически важен при `CrashLoopBackOff`.
*   `--follow` (`-f`): Стриминг логов в реальном времени.
*   `--tail=<N>`: Отображает последние N строк лога.
*   `--all-containers`: Показывает логи всех контейнеров в поде.
*   `-l <метка>`: Показывает логи всех подов с указанной меткой.
*   `--since=<время>`: Показывает логи за указанный период (например, `10m`, `1h`).

#### `kubectl exec`: Выполнение команд внутри контейнера

`kubectl exec` предоставляет интерактивный доступ к оболочке (`shell`) внутри запущенного контейнера для оперативной отладки.
**Синтаксис:** `kubectl exec -it <имя-пода> -- /bin/bash`
Флаг `-it` используется для интерактивных сессий. `--` отделяет команду `kubectl` от команды, выполняемой внутри контейнера. Для подов с несколькими контейнерами используйте `-c <имя-контейнера>`.

#### `kubectl port-forward`: Доступ к приложению

`kubectl port-forward` пробрасывает порт с локальной машины на порт пода, обеспечивая доступ к приложению, как если бы оно работало на `localhost`. Инструмент незаменим для отладки внутренних сервисов или подключения к базам данных.
**Синтаксис:** `kubectl port-forward pod/<имя-пода> 8080:80`

#### `kubectl debug`: Продвинутая отладка с эфемерными контейнерами

`kubectl debug` позволяет подключать к работающим подам эфемерные контейнеры с отладочными инструментами (`netshoot`, `busybox`) без перезапуска или изменения основного пода. Это безопасный метод диагностики в production-среде.
**Пример:**
```bash
# Подключить контейнер с сетевыми утилитами к поду my-pod
kubectl debug -it my-pod --image=nicolaka/netshoot --target=app-container
```
Данная команда позволяет запускать `tcpdump`, `ping`, `nslookup` и другие утилиты в сетевом пространстве имен проблемного пода.

## Практические Сценарии

### Изоляция пода для отладки с помощью меток

Манипуляция метками — безопасный и эффективный способ изолировать под от входящего трафика для "живой" отладки, не останавливая его. `Service` использует селектор для поиска подов. Временно удалив у пода целевую метку, вы исключаете его из списка конечных точек (`Endpoints`), и `Service` прекращает направлять на него трафик.

**Процесс:**

1.  **Изолировать под:** Удалите метку с пода. Знак `-` в конце ключа метки удаляет ее.
    ```bash
    # Предположим, сервис ищет поды с меткой app=myapp
    # Удаляем эту метку у конкретного пода
    kubectl label pod myapp-pod-xyz app-
    ```
    Под продолжает работать, но не получает новый трафик от сервиса.
2.  **Отладка пода:** Подключитесь к изолированному поду для диагностики.
    ```bash
    kubectl exec -it myapp-pod-xyz -- /bin/sh
    ```
3.  **Завершение:** После отладки рекомендуется удалить этот под. `Deployment` или `ReplicaSet` автоматически создаст новый, "чистый" экземпляр.
    ```bash
    kubectl delete pod myapp-pod-xyz
    ```

### Временная "заморозка" падающего пода с помощью `sleep`

При постоянных рестартах пода (`CrashLoopBackOff`), когда нет возможности провести отладку, можно временно изменить команду запуска контейнера на `sleep`. Это "заморозит" под в запущенном состоянии, позволяя диагностику.

**Команда для "заморозки" пода:**
```bash
kubectl patch deployment my-app \
  -p '{"spec":{"template":{"spec":{"containers":[{"name":"app","command":["sleep","3600"]}]}}}}'
```
Где `my-app` — имя деплоймента, `app` — имя контейнера для "заморозки".

**Преимущества:**
*   Под запускается и остается в состоянии `Running`.
*   Возможен доступ внутрь контейнера через `kubectl exec`.
*   Позволяет проверить переменные окружения, файлы, конфигурацию, состояние сети, логи.
*   Помогает выявить истинную причину сбоя (например, отсутствие файла конфигурации, неверная переменная окружения, проблемы с правами).
После отладки деплоймент откатывается к предыдущей версии или применяется оригинальный манифест.
Метод эффективен при `CrashLoopBackOff`, ошибках при старте контейнера, а также когда логи приложения неполны.

## Дополнительная информация

### Сбор и анализ Core Dumps

При аварийном завершении приложения (например, с ошибкой сегментации) Kubernetes можно настроить на сохранение **core dump** (снимка памяти процесса) для последующего анализа.

*   **Механизм:** `initContainer` с привилегиями (`privileged: true`) изменяет параметры ядра (`kernel.core_pattern`, `ulimit`) и сохраняет дампы в общий том (`PersistentVolume`).
*   **Анализ:** Дампы анализируются отладчиками, такими как `gdb` (для C/C++) или `delve` (для Go).

### Удаленная отладка с Delve (для Go)

Позволяет подключиться локальным отладчиком к процессу, запущенному внутри пода.

*   **Механизм:**
    1.  В `Dockerfile` приложения `Delve` (`dlv`) устанавливается и используется для запуска приложения в режиме сервера отладки.
    2.  `kubectl port-forward` пробрасывает порт отладчика на локальную машину.
    3.  IDE (GoLand, VS Code) подключается к `localhost:<port>` для пошаговой отладки и инспекции переменных.

### Отладка проблем с правами доступа с помощью `strace`

`strace` отслеживает системные вызовы приложения, помогая диагностировать ошибки прав доступа (`Permission Denied`), особенно в контейнерах с `readOnlyRootFilesystem`.

*   **Механизм:** `kubectl debug` подключает к поду отладочный контейнер (например, `alpine`) с повышенными привилегиями (`--profile=sysadmin`), откуда запускается `strace` для отслеживания основного процесса приложения.
    ```bash
    # Запуск отладочного контейнера
    kubectl debug -it -c debugger --target=app --image=alpine ${POD_NAME} --profile=sysadmin
    # Внутри отладчика: отслеживаем сбои системных вызовов
    strace -f -e status=failed -p 1
    ```
