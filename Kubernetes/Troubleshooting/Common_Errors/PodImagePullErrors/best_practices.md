# Ошибки загрузки образов (Image Pull Errors): Лучшие практики

## Определения

В данном разделе представлены стратегические рекомендации по проектированию инфраструктуры и CI/CD процессов для минимизации вероятности возникновения ошибок загрузки образов. Базовые понятия и терминология приведены в разделе [Определения](./definitions.md).

---

## Основные концепции

### Стратегии предотвращения сбоев

Эффективное управление образами базируется на трех столпах: неизменяемость, доступность и наблюдаемость.

| Категория | Рекомендация | Техническое обоснование |
| :--- | :--- | :--- |
| **Идентификация** | Использование SHA256 digest для критических компонентов | Исключает атаку типа "подмена образа" и гарантирует идентичность кода на всех узлах кластера. |
| **Локализация** | Развертывание Pull-through Cache или локальных зеркал (Harbor) | Снижает зависимость от внешних каналов связи и исключает влияние Rate Limits публичных реестров. |
| **Автоматизация** | Инъекция `imagePullSecrets` через мутирующие адмишн-контроллеры | Упрощает манифесты приложений и централизует управление учетными данными реестров. |
| **Оптимизация** | Регулярная очистка неиспользуемых образов (GC) | Предотвращает ошибки `No space left on device` на узлах. Настраивается в параметрах `kubelet` или рантайма. |

### Выбор политики imagePullPolicy

Правильный выбор политики напрямую влияет на стабильность и скорость масштабирования:

- **`IfNotPresent`**: Основной выбор для production. Позволяет избежать лишних сетевых запросов при перезапуске подов.
- **`Always`**: Обязательна для тегов, которые могут быть перезаписаны (например, `:latest`, `:stable`), чтобы гарантировать получение актуальной версии. Однако использование таких тегов само по себе является антипаттерном для production-сред.

## Практические сценарии

### Сценарий 1: Управление квотами и приоритетами загрузки

В условиях дефицита ресурсов или пропускной способности сети важно гарантировать загрузку критически важных образов (системные компоненты, базы данных).

**Использование PriorityClasses:**
Хотя `PriorityClass` в первую очередь влияет на планирование, он косвенно помогает избежать задержек загрузки, вытесняя менее важные поды и освобождая дисковое пространство (через Image GC).

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: critical-apps
value: 1000000
globalDefault: false
description: "Приоритет для критических приложений"
```

### Сценарий 2: Централизованное управление реестрами (ImagePolicyWebhook)

Для предотвращения загрузки образов из неавторизованных или публичных реестров (Docker Hub) используйте **ImagePolicyWebhook**. Это гарантирует, что кластер будет принимать только образы из внутреннего доверенного реестра (например, `harbor.mycompany.io`).

**Пример логики проверки:**
- Если `image` начинается на `myregistry.io/` — разрешить.
- Если нет — отклонить создание пода с ошибкой в `Admission Controller`.

### Сценарий 3: Расширенный мониторинг и алертинг

Мониторинг должен охватывать не только текущий статус `ImagePullBackOff`, но и предсказывать проблемы.

**PromQL для обнаружения массовых сбоев загрузки:**
```yaml
# Алерт сработает, если > 10% подов в namespace находятся в состоянии ошибки загрузки
- alert: HighImagePullFailureRate
  expr: |
    sum(kube_pod_container_status_waiting_reason{reason="ImagePullBackOff"}) by (namespace)
    /
    count(kube_pod_info) by (namespace)
    > 0.1
  for: 5m
  labels:
    severity: critical
  annotations:
    summary: "Массовая ошибка загрузки образов в namespace {{ $labels.namespace }}"
```

### Сценарий 4: Тюнинг Kubelet для управления образами

Для предотвращения ошибок `DiskPressure`, приводящих к сбоям Pull, настройте пороги очистки в конфигурации `kubelet` (через `KubeletConfiguration` или флаги):

```yaml
# Пример настройки в kubeadm
imageGCHighThresholdPercent: 85
imageGCLowThresholdPercent: 80
```
Это заставит `kubelet` начинать удаление неиспользуемых образов при заполнении диска на 85%, освобождая место для новых загрузок.
