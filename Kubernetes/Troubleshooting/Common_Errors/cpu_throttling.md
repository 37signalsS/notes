# Троттлинг процессора (CPU Throttling)

## Определения

**Троттлинг процессора (CPU Throttling)** — механизм планировщика Linux CFS (Completely Fair Scheduler), который искусственно ограничивает вычислительную мощность контейнера, если он превышает установленный `limits.cpu`. 

В отличие от памяти, это «мягкое» ограничение: процесс не убивается (как при OOMKilled), а приостанавливается («засыпает») до начала следующего периода планирования. Это приводит к деградации производительности, росту задержек (Latency) и таймаутам, что делает троттлинг «тихим убийцей» приложений.

## Основные концепции

### Жесткие vs Мягкие лимиты

| Ресурс | Тип лимита | Механизм | Последствие превышения | Видимость |
|:---|:---|:---|:---|:---|
| **Память** | Жесткий (Hard) | Resident Set Size (RSS) | **OOMKilled** (немедленная смерть) | Очевидна (Reason: OOMKilled) |
| **ЦП** | Мягкий (Soft) | CFS Quota | **Throttling** (замедление/паузы) | Скрыта (рост Latency) |

### Механизм работы CFS (Completely Fair Scheduler)

Kubernetes использует cgroups и CFS для управления CPU. Ключевые параметры:
*   **`cpu.cfs_period_us`** (cgroups v1) / **`cpu.max`** (cgroups v2): Период планирования (по умолчанию 100 000 мкс или 100 мс).
*   **`cpu.cfs_quota_us`** (cgroups v1) / **`cpu.max`** (cgroups v2): Квота времени CPU, которую контейнер может использовать за один период.

**Пример:**
Если вы задали `limits.cpu: 200m` (0.2 ядра), Kubernetes установит:
*   `period` = 100ms
*   `quota` = 20ms
Контейнер может использовать 20 мс процессорного времени каждые 100 мс. Если он потребит 20 мс за первые 5 мс периода (например, в 4 потока по 5 мс), он будет **приостановлен на оставшиеся 95 мс**.

### Различия между cgroups v1 и v2

Современные дистрибутивы (Ubuntu 22.04+, RHEL 9+) используют **cgroups v2** (унифицированная иерархия). Основные отличия:

| Параметр | Cgroups v1 | Cgroups v2 |
| :--- | :--- | :--- |
| **Файлы CPU** | `cpu.cfs_period_us`, `cpu.cfs_quota_us` | `cpu.max` (формат: `quota period`) |
| **Вес CPU** | `cpu.shares` | `cpu.weight` |
| **Статистика** | `cpu.stat` (ограниченная) | `cpu.stat` (расширенная: `usage_usec`, `nr_throttled`, `throttled_usec`) |
| **Burst** | Нет нативной поддержки | `cpu.max.burst` (накопление неиспользованной квоты) |

**Проверка версии cgroups:**
```bash
# Проверка типа файловой системы
stat -f /sys/fs/cgroup | grep "Type"
# → cgroup2fs (v2) или tmpfs (v1)

# Или через mount
mount | grep cgroup
# → cgroup2 on /sys/fs/cgroup/unified type cgroup2 (v2)
# → cgroup on /sys/fs/cgroup/cpu,cpuacct type cgroup (v1)
```

### Планировщик EEVDF (ядро 6.6+)

Начиная с ядер Linux 6.6 (2023), планировщик **EEVDF (Earliest Eligible Virtual Deadline First)** заменил классический CFS. Основные отличия:

- **Виртуальные дедлайны:** Вместо накопления `vruntime` (как в CFS), EEVDF рассчитывает время готовности и дедлайны для каждой задачи.
- **Более низкая латентность:** Интерактивные задачи получают CPU быстрее благодаря более точному соблюдению приоритетов.
- **Групповая справедливость:** Улучшено распределение времени между группами процессов (cgroups).

**Важно:** Механизм троттлинга CFS/EEVDF работает аналогично — при превышении квоты процесс приостанавливается. Основные файлы статистики (`cpu.stat`) и лимиты (`cpu.max`) остаются прежними.

### Влияние многопоточности

Многопоточные приложения (Java JVM, Go, Node.js с воркерами) особенно уязвимы к троттлингу. 
Если у приложения лимит 1 ядро, но оно запускает 10 потоков, каждый из которых активно работает, лимит в 100 мс (для периода 100 мс) будет исчерпан за **10 мс реального времени**. Оставшиеся 90 мс периода приложение будет полностью заблокировано.

### Исторический баг CFS (Phantom Throttling)

До ядер Linux **5.4+** (и обновленных LTS 4.19.84+) существовал критический баг в алгоритме CFS. Из-за некорректного учета остаточного времени в локальных очередях процессоров, контейнеры троттлились даже тогда, когда их общее потребление было **ниже 50% от лимита**. 
*   **Решение:** Обновить ядро ОС на узлах или использовать современные дистрибутивы (Ubuntu 22.04+, Amazon Linux 2023).

**Проверка версии ядра:**
```bash
uname -r
# → 5.15.0-78-generic (ippers)
# → 6.5.0-44-generic (актуальное)

# Проверка наличия патчей для LTS-ядер
cat /proc/version
# → Linux version 5.15.0-78-generic ... (Ubuntu 22.04.3 LTS)
```

## Практические сценарии

### Диагностика дросселирования

Основным признаком является аномально высокая задержка при низком или «ровном» графике CPU.

#### Алгоритм поиска основной причины:

1.  **Проверка метрик Prometheus:**
    - `container_cpu_cfs_throttled_periods_total`: общее количество интервалов, в которых сработал лимит. Рост этого счетчика — прямой индикатор проблемы.
    - `container_cpu_cfs_throttled_seconds_total`: суммарное время, на которое приложение было замедлено.
    - **Формула интенсивности:** `rate(container_cpu_cfs_throttled_seconds_total[5m])`.
    - **Процент троттлинга:** `rate(container_cpu_cfs_throttled_periods_total[5m]) / rate(container_cpu_cfs_periods_total[5m]) * 100`.

2.  **Анализ графиков в Grafana:**
    - Если график `CPU Usage` выглядит как **горизонтальная линия (плато)**, упирающаяся в значение `CPU Limit` — это классический троттлинг.
    - Если потребление кажется низким, но `throttled_periods` растет — проверьте на наличие микро-всплесков (micro-bursts) или старого ядра Linux.

3.  **Локальная проверка на узле:**
    ```bash
    # Просмотр статистики cgroup напрямую (для cgroup v1)
    cat /sys/fs/cgroup/cpu/kubepods/pod<pod_uid>/<container_id>/cpu.stat
    # nr_periods — сколько периодов прошло
    # nr_throttled — в скольких сработал троттлинг
    # throttled_time — время в наносекундах

    # Для cgroups v2 (современные дистрибутивы)
    cat /sys/fs/cgroup/system.slice/docker-<container_id>.scope/cpu.stat
    # usage_usec — общее время на CPU
    # nr_throttled — количество throttling-событий
    # throttled_usec — общее время в throttling
    ```

4.  **Проверка PSI (Pressure Stall Information):**
    ```bash
    # Проверка давления на CPU на узле
    cat /proc/pressure/cpu
    # some avg10=0.00 avg60=0.00 avg300=0.00 total=0
    # full avg10=0.00 avg60=0.00 avg300=0.00 total=0

    # Проверка давления на память (влияет на троттлинг)
    cat /proc/pressure/memory
    # some avg10=0.00 avg60=0.00 avg300=0.00 total=0
    # full avg10=0.00 avg60=0.00 avg300=0.00 total=0
    ```

5.  **Использование kubectl для диагностики:**
    ```bash
    # Просмотр потребления ресурсов подом
    kubectl top pod <pod-name> --containers

    # Просмотр лимитов пода
    kubectl get pod <pod-name> -o jsonpath='{.spec.containers[*].resources}'

    # Просмотр событий пода
    kubectl describe pod <pod-name> | grep -A 10 "Events:"

    # Просмотр логов пода (поиск признаков троттлинга)
    kubectl logs <pod-name> | grep -i "timeout\|slow\|latency"
    ```

### Регулирование CPU Burst (K8s 1.26+)

Для борьбы с троттлингом из-за коротких всплесков в Kubernetes 1.26+ (стабильно) доступна функция **CPU Burst**. Она позволяет контейнеру «накапливать» неиспользованную квоту из предыдущих периодов и тратить её на кратковременные всплески выше лимита.

*   **Как включить:** Требуется поддержка в `kubelet` (флаг `--feature-gates=CPUBurst=true`) и ядро Linux 5.14+.
*   **Результат:** Снижение P99 Latency для всплесковых нагрузок (например, десериализация больших JSON или старт приложения) без изменения лимитов.

**Реализация в cgroups v2 (`cpu.max.burst`):**

В cgroups v2 управление burst осуществляется через файл `cpu.max.burst`:

```bash
# Просмотр текущего burst (в наносекундах)
cat /sys/fs/cgroup/.../cpu.max.burst
# → 0 (по умолчанию)

# Установка burst на 20% (20000 нс при периоде 100000 нс)
echo "20000" | sudo tee /sys/fs/cgroup/.../cpu.max.burst
# → 20000
```

**Как это работает:**
1. Если контейнер не использует всю квоту в периоде, неиспользованное время накапливается в `cpu.max.burst`.
2. При всплеске нагрузки контейнер может использовать накопленное время сверх основной квоты.
3. Максимальный burst ограничивается значением `cpu.max.burst`.

**Пример сценария:**
- Контейнер имеет лимит 1 ядро (`cpu.max = "100000 100000"`)
- Burst установлен на 50% (`cpu.max.burst = 50000`)
- Контейнер может использовать до 1.5 ядра кратковременно (100% + 50% burst)

### Кейс: Троттлинг Java-приложения

* **Проблема:** Java API тормозит под нагрузкой, `kubectl top` показывает 80% от лимита.
* **Причина:** JVM при запуске видит количество ядер хоста (например, 32), а не лимит контейнера (например, 2 ядра). Параллельный Garbage Collector (GC) запускает 32 потока, которые мгновенно выедают квоту 100 мс периода, вызывая жесткий троттлинг.
* **Решение:** 
    1. Использовать флаг `-XX:ActiveProcessorCount=2`.
    2. Обновить Java до версии 11+, которая лучше понимает лимиты контейнеров.
    3. Увеличить `limits.cpu` или использовать `CPU Burst`.

## Рекомендации по настройке

1.  **Requests vs Limits:** Устанавливайте `requests.cpu` на уровне реального среднего потребления.
2.  **Отказ от лимитов CPU:** В некоторых высоконагруженных окружениях (например, в Google или Uber) практикуется установка `requests.cpu` без `limits.cpu`. Это позволяет избежать троттлинга ценой риска того, что один под «съест» весь узел (требует строгой изоляции и мониторинга).
3.  **Static CPU Manager Policy:** Для критичных к задержкам БД или кешей используйте эксклюзивные ядра. См. **[Static CPU Manager Policy](../../Scheduling/qos_limit_and_requests.md#static-cpu-manager-policy)**.
4.  **Размер периода:** В редких случаях (для специфических нагрузок) можно изменить `cpu.cfs_period_us` через параметры kubelet, но это влияет на весь узел.
5.  **Использование CPU Burst:** Включите `CPUBurst=true` в feature-gates kubelet для приложений с всплесковой нагрузкой.
6.  **Мониторинг троттлинга:** Настройте алерты в Prometheus на превышение процента троттлинга > 25%.

### Алгоритм устранения неисправностей

1. **Определите проблему:** Проверьте метрики `container_cpu_cfs_throttled_seconds_total` и `container_cpu_cfs_throttled_periods_total`.
2. **Проверьте версию ядра:** Убедитесь, что ядро >= 5.4 (для исправления Phantom Throttling).
3. **Проверьте тип cgroups:** Определите, используется ли cgroups v1 или v2.
4. **Анализируйте потребление:** Проверьте, является ли приложение CPU-bound или I/O-bound.
5. **Настройте лимиты:** Увеличьте `limits.cpu` или используйте CPU Burst.
6. **Оптимизируйте код:** Уменьшите потребление CPU или оптимизируйте алгоритмы.
7. **Настройте мониторинг:** Создайте алерты для早期 обнаружения троттлинга.

### Часто задаваемые вопросы

**В: Может ли троттлинг вызвать OOMKilled?**
Н: Нет, троттлинг и OOMKilled — это разные механизмы. Троттлинг замедляет процесс, а OOMKilled убивает его при нехватке памяти.

**В: Как влияет троттлинг на latency?**
Н: Троттлинг вызывает рост latency, так как процессы приостанавливаются до конца периода CFS. Это особенно критично для интерактивных приложений.

**В: Можно ли отключить троттлинг?**
Н: Нет, троттлинг — это механизм ядра Linux для управления ресурсами. Его можно только минимизировать через настройку лимитов и оптимизацию кода.

### Совет для собеседования
**Вопрос:** Почему приложение может троттлиться, если `kubectl top` показывает потребление ниже лимита?
**Ответ:** 
1. **Микро-всплески:** Приложение потребляет квоту очень быстро (например, в начале 100 мс окна), а `kubectl top` усредняет значения.
2. **Многопоточность:** Много потоков суммарно быстро выбирают квоту за малый промежуток времени.
3. **Старое ядро:** Наличие бага CFS "Phantom Throttling".
