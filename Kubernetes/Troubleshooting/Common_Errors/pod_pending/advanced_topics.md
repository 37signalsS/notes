# Pod в состоянии `Pending`: Продвинутые темы

## Определения

**Продвинутая диагностика Pending** — глубокий анализ взаимодействия механизмов планирования, мониторинг состояния очереди планировщика и исследование специфических ограничений, блокирующих запуск подов в сложных инфраструктурных условиях.

**Scheduling Gates (врата планирования)** — механизм (K8s 1.27+), позволяющий удерживать под в состоянии `Pending` до тех пор, пока внешняя система (например, контроллер безопасности или квот) не удалит соответствующие записи из `spec.schedulingGates`.

**Scheduler Profile** — набор настроек планировщика, определяющий поведение плагинов на различных стадиях (Filter, Score и др.) для разных групп подов через поле `spec.schedulerName`.

## Основные концепции

### 1. Порядок применения фильтров планировщика

Планировщик проверяет условия последовательно. Если под застрял в `Pending`, критически важно понимать, на каком этапе Scheduling Framework происходит отказ:

1.  **Scheduling Gates:** проверка поля `spec.schedulingGates`. Планирование не начнется, пока список не пуст.
2.  **NodeSelector / NodeAffinity:** базовые фильтры по меткам узлов.
3.  **Taints/Tolerations:** исключающий фильтр (эффект `NoSchedule`).
4.  **ResourceRequests:** наличие свободных ресурсов (CPU, Memory, Ports, Extended Resources).
5.  **PodAffinity/AntiAffinity:** правила взаимного расположения подов.
6.  **TopologySpreadConstraints:** проверка соблюдения равномерности распределения (`maxSkew`).
7.  **Volume Filters:** проверка доступности томов (особенно актуально для локальных дисков и зональных облачных дисков).

### 2. Взаимодействие с Cluster Autoscaler (CA)

Наличие `Pending` пода является триггером для CA. Однако расширение кластера может не произойти, если:

*   **PDB (Pod Disruption Budget):** при вытеснении других подов для освобождения места планировщик учитывает PDB. Если PDB запрещает удаление, новые поды могут остаться в `Pending`.
*   **Зональный дисбаланс (Zonal Mismatch):** под требует PVC, привязанный к конкретной зоне доступности, в которой исчерпаны лимиты масштабирования облачного провайдера.
*   **Немасштабируемые группы (Unexpandable Nodes):** CA помечает группы узлов как не подлежащие расширению (например, из-за достижения `maxNodes` или ошибок API провайдера).
*   **Специфические ресурсы:** под требует ресурсов (например, GPU конкретной серии), которые отсутствуют в описании групп узлов для автоскейлера.

### 3. Лимиты и квоты (ResourceQuota)

На продвинутом уровне состояние `Pending` может быть вызвано не физической нехваткой ресурсов, а логическими ограничениями:

*   **Namespace Quotas:** суммарные `requests` всех подов в Namespace достигли предела `ResourceQuota`. Поды будут отклонены API-сервером или останутся в `Pending`, если создаются через контроллеры (Deployment/StatefulSet).
*   **LimitRange:** под не соответствует минимальным или максимальным значениям ресурсов, установленным для Namespace, или в нем не указаны `requests/limits`, а значения по умолчанию не заданы.

### 4. Метрики и профилирование планировщика

Для анализа производительности планирования в больших кластерах используются следующие метрики:

*   `scheduler_pending_pods`: количество подов в различных очередях (active, backoff, unschedulable).
*   `scheduler_scheduling_attempt_duration_seconds`: время, затраченное на одну попытку планирования.
*   `scheduler_pod_scheduling_duration_seconds`: общее время от появления пода до его привязки к узлу.

## Практические сценарии

### Анализ Scheduling Gates

Если `kubectl describe pod` не показывает событий `FailedScheduling`, проверьте шлюзы:
```bash
kubectl get pod <pod-name> -o jsonpath='{.spec.schedulingGates}'
```
**Решение:** проверьте логи контроллера, который должен удалять эти шлюзы (например, Kyverno, Gatekeeper или кастомные операторы).

### Диагностика Topology Spread Constraints

При строгой политике `whenUnsatisfiable: DoNotSchedule` под застревает в `Pending`, если дисбаланс превышает `maxSkew`.
```bash
# Проверка распределения подов приложения по доменам топологии
kubectl get pods -o wide -l app=<label>
```
**Решение:** рассмотрите возможность перехода на `ScheduleAnyway` или добавьте узлы в недоиспользуемые домены топологии.

### Проверка статуса Cluster Autoscaler

Если под ожидает расширения кластера:
```bash
# Получение статуса автоскейлера из ConfigMap
kubectl get configmap cluster-autoscaler-status -n kube-system -o yaml
```
**Ищите сообщения:** `no.scale.up.node.group.unneeded`, `scale.up.error.api.call`.

## Дополнительная информация

### Рекомендуемые практики

| Ситуация | Рекомендация |
|:---|:---|
| **Критические нагрузки** | Всегда используйте `PriorityClass` с `preemptionPolicy: PreemptLowerPriority`. |
| **Фоновые задачи** | Используйте `preemptionPolicy: Never`, чтобы не провоцировать каскадное вытеснение. |
| **Локальные диски** | Настраивайте `volumeBindingMode: WaitForFirstConsumer` в StorageClass для синхронизации выбора узла и PVC. |
