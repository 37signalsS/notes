# Ошибки доступа к API: определения 401 и 403

## Определения

**401 Unauthorized** (неавторизован) — код состояния HTTP, означающий, что API-сервер Kubernetes не смог подтвердить личность (аутентифицировать) субъекта. Это первый барьер безопасности: если личность не установлена, запрос отклоняется немедленно, не доходя до проверки прав доступа.

**403 Forbidden** (запрещено) — код состояния HTTP, означающий, что API-сервер успешно идентифицировал субъекта, но отклонил запрос. Это происходит на одном из двух последующих этапов:
1.  **Авторизация (RBAC):** У субъекта нет разрешающих правил для выполнения действия.
2.  **Контроль допуска (Admission Control):** Запрос нарушает политики кластера (например, квоты или стандарты безопасности подов), даже если RBAC разрешает действие.

> Полный разбор методов аутентификации: [../../../Security/authentication.md](../../../Security/authentication.md)
> Полный обзор RBAC: [../../../Security/rbac/rbac_overview.md](../../../Security/rbac/rbac_overview.md)

## Основные концепции

### Различия между AuthN и AuthZ

| Код | Этап | Технический вопрос | Типичная причина | Ресурс |
|-----|------|--------------------|------------------|--------|
| **401** | Аутентификация (AuthN) | Вы тот, за кого себя выдаете? | Невалидный токен, истёкший сертификат | [authentication_methods.md](authentication_methods.md) |
| **403** | Авторизация (AuthZ) | Вам разрешено делать это? | Отсутствие RoleBinding для субъекта | [common.md](common.md) |
| **403** | Admission Control | Это безопасно для кластера? | Нарушение PSA, превышение ResourceQuota | [advanced.md](advanced.md) |

### Системные группы и анонимный доступ

Kubernetes автоматически назначает субъектов в системные группы на основе результата аутентификации:

*   **`system:authenticated`**: Включает всех успешно опознанных пользователей и ServiceAccounts.
*   **`system:unauthenticated`**: Группа для запросов, которые не предоставили учетных данных (при включенном анонимном доступе).
*   **`system:anonymous`**: Имя пользователя, назначаемое анонимным запросам.

**Важно:** Если `--anonymous-auth=false`, то анонимные запросы всегда получают **401 Unauthorized**. Если анонимный доступ разрешен, они получают **403 Forbidden** (так как у группы `system:unauthenticated` обычно нет прав).

### Роль аудита в диагностике

Логи аудита (Audit Logs) являются "черным ящиком" для разбора ошибок доступа. Каждый запрос помечается уникальным `audit ID`.

*   **Для 401:** В логах отсутствует поле `user.username` или оно содержит `system:anonymous`, а этап `decision` помечен как `Drop`.
*   **Для 403:** Логи содержат информацию о том, какой именно модуль авторизации (RBAC, NodeRestriction) или Admission Webhook отклонил запрос.

> Настройка и анализ логов: [../../../Security/audit.md](../../../Security/audit.md)

## Практические сценарии

### Жизненный цикл запроса к API

Понимание последовательности проверок критично для диагностики. Ошибка на раннем этапе делает невозможным прохождение к следующему.

```text
Запрос (Header, Payload)
    ↓
1. Аутентификация (Authentication) — Установка личности
    ├── Провал → 401 Unauthorized (EXIT)
    └── Успех  → Субъект помечен (User, Groups)
    ↓
2. Авторизация (Authorization) — Проверка RBAC/ABAC/Node
    ├── Провал → 403 Forbidden (EXIT)
    └── Успех  → Запрос разрешен авторизацией
    ↓
3. Admission Control — Финальная проверка политик
    ├── Mutating → Изменение объекта (sidecars, defaults)
    ├── Validating → Проверка (PSA, Quotas, Webhooks)
    │     └── Провал → 403 Forbidden (EXIT)
    └── Успех  → Объект готов к сохранению
    ↓
4. Фиксация в etcd / Исполнение
```
