# Ошибки доступа к API: определения 401 и 403

## Определения

**401 Unauthorized** (неавторизован) — состояние, при котором Kubernetes не смог аутентифицировать запрос. Личность субъекта не подтверждена. Проблема обычно связана с невалидным токеном, истёкшим сертификатом или отсутствием учётных данных в запросе.

**403 Forbidden** (запрещено) — Kubernetes успешно аутентифицировал запрос (личность известна), но отклонил его по одной из двух причин:
1.  **RBAC** — у субъекта недостаточно прав для выполнения запрошенной операции.
2.  **Admission Control** (Контроль допуска) — запрос нарушает политики безопасности или квоты кластера (например, требования безопасности подов или ограничения NodeRestriction).

> Полное описание RBAC: [../../../Security/rbac/rbac_overview.md](../../../Security/rbac/rbac_overview.md)

## Основные концепции

### Различия между 401 и 403

| Код | Уровень | Основной вопрос | Причина | Куда смотреть |
|-----|---------|-----------------|---------|---------------|
| **401** | Аутентификация | Кто вы? | Неверный токен, истёкший сертификат | [authentication_methods.md](authentication_methods.md) |
| **403** | Авторизация | Что можно делать? | Недостаточно прав RBAC | [common.md](common.md) |
| **403** | Admission Control | Можно ли ЭТО делать? | Нарушение политик (PSA, NodeRestriction) | [advanced.md](advanced.md) |

### Модель прохождения запроса

Проверка запроса в API-сервере выполняется строго последовательно. Нарушение на любом этапе прерывает цепочку.

```
Запрос к API
    ↓
1. Аутентификация (AuthN) — Кто вы?
    ├── Не удалось → 401 Unauthorized
    ↓
2. Авторизация (AuthZ) — Что вам разрешено?
    ├── Нет прав (RBAC) → 403 Forbidden
    ↓
3. Admission Control — Соответствует ли запрос политикам?
    ├── Отклонено политикой → 403 Forbidden
    ↓
4. Запись в etcd / Исполнение
    ↓
200 OK / 201 Created
```

### Ключевые субъекты (subjects)

Kubernetes идентифицирует запросы через три типа субъектов:

| Тип | Формат | Описание |
|-----|--------|----------|
| **User** | `username` | Внешний пользователь (OIDC, клиентский сертификат) |
| **Group** | `groupname` | Группа внешних пользователей |
| **ServiceAccount** | `system:serviceaccount:<namespace>:<name>` | Учётная запись приложения внутри кластера |

**Важно:** `User` и `Group` не являются объектами Kubernetes — они управляются внешними системами. `ServiceAccount` — полноценный объект K8s.

## Дополнительная информация

### Последовательность проверок

Если запрос не прошёл аутентификацию (401), API-сервер прекращает обработку. Права доступа (RBAC) и политики (Admission) проверяются только для успешно опознанных пользователей.

### Анонимные запросы

Если учётные данные не предоставлены, запрос может быть помечен как анонимный (`system:anonymous`). 
- Если анонимный доступ разрешен, но прав не хватает — вернётся **403 Forbidden**.
- Если анонимный доступ запрещен (`--anonymous-auth=false`) — вернётся **401 Unauthorized**.

### Admission Control (Контроль допуска)

Даже при наличии полных прав RBAC (например, у `cluster-admin`), запрос может быть отклонен с кодом 403 механизмами контроля допуска:
- **Pod Security Admission (PSA):** Запрет на создание привилегированных подов в защищенном неймспейсе.
- **NodeRestriction:** Ограничение прав `kubelet` на изменение объектов вне его узла.
- **Admission Webhooks:** Динамические проверки внешними инструментами (Kyverno, Gatekeeper, кастомные вебхуки).
