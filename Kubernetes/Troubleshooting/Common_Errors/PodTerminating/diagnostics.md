# Pod Terminating — диагностика и алгоритмы поиска неисправностей

## Определения

**Диагностический алгоритм Pod Terminating** — структурированная последовательность проверок для выявления причины, по которой объект Pod не удаляется из API-сервера. Основные направления поиска: подсистема хранения (CSI/Volumes), механизмы защиты (Finalizers), состояние инфраструктуры (Nodes) и политики доступности (PDB).

**UID (Unique Identifier)** — уникальный идентификатор Pod в кластере. В диагностике используется для сопоставления объекта API с физическими директориями на узле (например, `/var/lib/kubelet/pods/<UID>`) и анализа зависших точек монтирования.

**Зависший финализатор (Stuck Finalizer)** — состояние, при котором контроллер, ответственный за снятие финализатора, не может выполнить задачу (из-за ошибки или отсутствия связи), что блокирует окончательное удаление записи из `etcd`.

**Grace Period (Период ожидания)** — время, прошедшее с момента установки `deletionTimestamp`. Если этот интервал значительно превышает `terminationGracePeriodSeconds`, диагностика переходит от анализа жизненного цикла приложения к анализу системных компонентов кластера.

## Базовые концепции

### Логическая схема диагностики

Анализ строится по принципу «от внешнего к внутреннему»:

1.  **API-уровень**: Анализ метаданных объекта (`deletionTimestamp`, `finalizers`) и системных событий (`Events`).
2.  **Уровень управления (Control Plane)**: Проверка внешних контроллеров (CSI, PDB, Job), которые могут удерживать объект.
3.  **Уровень узла (Node Level)**: Проверка связи `kubelet` с API-сервером и физического состояния контейнеров, процессов и томов на конкретном хосте.
4.  **Уровень среды выполнения (Runtime)**: Проверка состояния процессов внутри контейнера (обработка сигналов, состояние I/O).

### Диагностическая матрица

| Инструмент | Сфера применения | Искомые данные |
| :--- | :--- | :--- |
| `kubectl describe pod` | Общий аудит | Ошибки монтирования, таймауты узла, события жизненного цикла. |
| `kubectl get pod -o json` | Полная спецификация | Точные значения `finalizers` и `deletionTimestamp`. |
| `journalctl -u kubelet` | Анализ на узле | Ошибки `UnmountVolume`, `Orphaned pod found`, тайм-ауты обращения к CRI. |
| `kubectl get volumeattachment` | Проверка CSI | Зависшие связи между томами и узлами в инфраструктуре. |
| `findmnt` / `lsof` | Локальная проверка | Процессы, блокирующие освобождение файловых дескрипторов томов. |

## Практические сценарии

### Пошаговый алгоритм устранения зависания

#### Этап 1: Первичный сбор данных

```bash
# 1. Проверка времени зависания и статуса фазы
kubectl get pod <pod-name> -o jsonpath='{.metadata.deletionTimestamp} {.status.phase}'

# 2. Список активных финализаторов (причина блокировки в etcd)
kubectl get pod <pod-name> -o jsonpath='{.metadata.finalizers}'

# 3. Анализ событий для выявления явных ошибок
kubectl describe pod <pod-name> | grep -A 20 Events
```

**Интерпретация:**
- В событиях виден `FailedUnmount` → **Перейти к диагностике томов (Этап 2)**.
- Список финализаторов содержит `external-attacher` → **Перейти к анализу CSI (Этап 3)**.
- Узел находится в статусе `NotReady` → **Перейти к диагностике узла (Этап 4)**.

#### Этап 2: Диагностика подсистемы хранения на узле

Если Pod не удаляется из-за ошибок размонтирования:

```bash
# Получение UID пода для поиска на ФС
POD_UID=$(kubectl get pod <pod-name> -o jsonpath='{.metadata.uid}')

# На узле: проверка наличия активных монтирований
findmnt | grep $POD_UID

# Поиск процессов, использующих директории пода
lsof +D /var/lib/kubelet/pods/$POD_UID
```

*Частая причина:* Процесс в состоянии `D` (uninterruptible sleep) завис на операции ввода-вывода с сетевым диском (NFS, iSCSI).

#### Этап 3: Анализ объектов CSI и VolumeAttachment

Если Pod завис с финализатором `external-attacher`:

```bash
# Проверка наличия объекта VolumeAttachment для данного тома
kubectl get volumeattachment | grep <volume-name>

# Проверка логов CSI-контроллера (например, для Ceph, EBS и т.д.)
kubectl logs -n kube-system -l app=csi-provisioner -c csi-provisioner
```

#### Этап 4: Действия при отказе узла

Если узел недоступен (`NotReady`), Kubelet не может подтвердить удаление.

1.  **Проверка возможности восстановления**: Попробовать перезапустить `kubelet` или узел.
2.  **Механизм Out-of-Service (K8s 1.24+)**:
    ```bash
    kubectl taint nodes <node-name> node.kubernetes.io/out-of-service=NoExecute:NoExecute
    ```
    Это позволит контроллерам безопасно отсоединить тома и удалить поды.

### Сценарий быстрой очистки (Последний рубеж)

Если все стандартные методы исчерпаны и риск повреждения данных (для StatefulSet) учтён:

```bash
# 1. Принудительное удаление из API (без ожидания Kubelet)
kubectl delete pod <pod-name> --force --grace-period=0

# 2. Очистка финализаторов вручную (если Pod всё ещё висит)
kubectl patch pod <pod-name> -p '{"metadata":{"finalizers":null}}' --type=merge
```

## Дополнительная информация

### Типовые признаки блокировки

*   **Конфликт PDB**: В событиях виден статус `Denied` от `PodDisruptionBudget`. Решение: временно увеличить количество реплик или изменить PDB.
*   **Зомби-процессы**: Контейнер завершён, но его `shim` (containerd-shim) не завершается, так как ждёт выхода дочернего процесса.
*   **Зависший NFS**: Проблема на уровне ядра ОС хоста, требующая вмешательства на уровне `mount` или перезагрузки узла.
