# Pod Terminating — диагностика и алгоритмы поиска неисправностей

## Определения

**Диагностический алгоритм Pod Terminating** — структурированная последовательность проверок для выявления причины, по которой объект Pod не удаляется из API-сервера. Основные направления поиска: подсистема хранения (CSI/Volumes), механизмы защиты (Finalizers), состояние инфраструктуры (Nodes), политики доступности (PDB) и жизненный цикл контейнеров (Runtime).

**UID (Unique Identifier)** — уникальный идентификатор Pod в кластере. Используется для сопоставления объекта API с физическими диреториями на узле (`/var/lib/kubelet/pods/<UID>`), поиском контейнеров в CRI (`crictl ps --pod <UID>`) и анализом зависших точек монтирования.

**Зависший финализатор (Stuck Finalizer)** — состояние, при котором контроллер, ответственный за снятие финализатора, не может выполнить задачу (из-за ошибки API облака, отсутствия связи или бага в логике), что блокирует удаление записи из `etcd`.

**Grace Period (Период ожидания)** — время, прошедшее с момента установки `deletionTimestamp`. Если этот интервал значительно превышает `terminationGracePeriodSeconds`, диагностика переходит от анализа жизненного цикла приложения к анализу системных компонентов кластера и CRI.

**Uninterruptible Sleep (D-state)** — состояние процесса, ожидающего завершения ввода-вывода (I/O). Такие процессы игнорируют сигналы `SIGTERM` и `SIGKILL`, блокируя завершение контейнера и размонтирование томов.

## Базовые концепции

### Логическая схема диагностики

Анализ строится по принципу «от внешнего к внутреннему»:

1.  **API-уровень**: Анализ метаданных (`finalizers`, `deletionTimestamp`) и системных событий (`Events`).
2.  **Уровень политик (PDB)**: Проверка, не блокирует ли `PodDisruptionBudget` удаление.
3.  **Уровень управления (Control Plane)**: Проверка внешних контроллеров (CSI, Job), удерживающих объект.
4.  **Уровень узла (Node Level)**: Проверка связи `kubelet` с API, состояния CRI и физических томов.
5.  **Уровень среды выполнения (Runtime)**: Анализ процессов (PID 1, зомби, D-state, порядок завершения Sidecars).

### Диагностическая матрица инструментов

| Инструмент | Сфера применения | Искомые данные |
| :--- | :--- | :--- |
| `kubectl describe pod` | Общий аудит | Ошибки монтирования, таймауты узла, события жизненного цикла. |
| `kubectl get pod -o json` | Полная спецификация | Точные значения `finalizers` и `deletionTimestamp`. |
| `kubectl get pdb` | Анализ доступности | Проверка `ALLOWED DISRUPTIONS`. Если 0 — удаление может быть заблокировано. |
| `crictl ps --pod <UID>` | CRI (на узле) | Статус контейнеров внутри пода на уровне runtime. |
| `journalctl -u kubelet` | Анализ Kubelet | Ошибки `UnmountVolume`, тайм-ауты обращения к CRI, `Orphaned pod found`. |
| `findmnt` / `lsof` | Файловая система | Процессы, блокирующие освобождение дескрипторов томов. |
| `nsenter -t <PID> -m` | Mount Namespace | Глубокая проверка точек монтирования внутри namespace процесса. |

## Практические сценарии

### Пошаговый алгоритм устранения зависания

#### Этап 1: Первичный сбор и анализ метаданных

```bash
# 1. Проверка времени зависания и финализаторов
kubectl get pod <pod-name> -o jsonpath='{.metadata.deletionTimestamp} {"\n"} {.metadata.finalizers}'

# 2. Проверка PDB (если удаление инициировано через Drain или Eviction)
kubectl get pdb --all-namespaces

# 3. Анализ событий (включая ошибки планировщика и CSI)
kubectl describe pod <pod-name> | grep -A 20 Events
```

**Интерпретация:**
- `finalizers: [kubernetes.io/pvc-protection]` → Проверьте, не используется ли связанный PVC другими подами.
- `Events: FailedUnmount` → **Перейти к Этапу 2 (Storage)**.
- `Events: Denied by PDB` → Увеличьте количество реплик или временно удалите PDB.

#### Этап 2: Диагностика Native Sidecars (K8s 1.29+)

Если под завис, проверьте статус контейнеров. В новой модели основные контейнеры должны завершиться **до** сайдкаров.
```bash
# Проверка статуса каждого контейнера (ContainerStatuses)
kubectl get pod <pod-name> -o jsonpath='{.status.containerStatuses[*].state}'
```
Если основное приложение завершилось (состояние `Terminated`), но сайдкар (например, `istio-proxy` или `cloud-sql-proxy`) все еще в `Running`, это может указывать на баг в логике завершения сайдкара или на то, что он не получил `SIGTERM`.

#### Этап 3: Диагностика подсистемы хранения (CSI/Volumes)

Если Pod не удаляется из-за ошибок размонтирования:

```bash
# 1. Получение UID и NodeName
kubectl get pod <pod-name> -o jsonpath='{.metadata.uid} {.spec.nodeName}'

# 2. На узле: Поиск процессов, удерживающих тома (включая скрытые монтирования)
POD_UID="<UID>"
lsof +D /var/lib/kubelet/pods/$POD_UID
# Проверка mountinfo для поиска "застрявших" bind-mounts
grep $POD_UID /proc/self/mountinfo

# 3. Поиск процессов в D-state (Uninterruptible Sleep)
ps -aux | awk '$8=="D" {print $0}'
```

#### Этап 4: Проверка CRI и контейнерного рантайма

Если Kubelet не может удалить контейнеры, проверьте их состояние напрямую через CRI (на узле):

```bash
# Список контейнеров для конкретного пода
crictl ps -a --pod $(crictl pods --uid <UID> -q)

# Просмотр логов конкретного контейнера на уровне рантайма (если kubectl logs недоступен)
crictl logs <container-id>
```

#### Этап 5: Диагностика Graceful Node Shutdown

Если поды зависают при выключении узла, проверьте события `systemd-logind` и логи `kubelet`:

```bash
# Проверка событий выключения
journalctl -u kubelet --grep "Shutdown manager"
# Проверка, получил ли kubelet сигнал от logind
journalctl -t systemd-logind
```

## Дополнительная информация

### Коды завершения (Exit Codes) при остановке

Анализ `status.containerStatuses[*].lastState.terminated.exitCode` помогает понять, как завершился процесс:

*   **Exit Code 0**: Успешное завершение.
*   **Exit Code 143 (128+15)**: Процесс корректно завершился по сигналу **SIGTERM**. Это признак правильной работы Graceful Shutdown.
*   **Exit Code 137 (128+9)**: Процесс был убит по сигналу **SIGKILL**.
    *   Если `reason: OOMKilled` — нехватка памяти.
    *   Если `reason: Terminated` без OOM — приложение не успело завершиться за `terminationGracePeriodSeconds` и было убито принудительно.

### Типовые признаки блокировки

*   **Зомби-процессы (Zombies)**: Если PID 1 не выполняет `wait()`, дочерние процессы остаются в состоянии `<defunct>`. Это может блокировать очистку контейнера в CRI.
*   **Зависший NFS/FUSE**: Если точка монтирования недоступна, любой вызов `ls` или `umount` в этой директории зависнет в `D-state`.
*   **Finalizer "external-attacher"**: Указывает на проблему в AD-контроллере (Attach/Detach) или CSI-драйвере. Проверьте `kubectl get volumeattachment`.
