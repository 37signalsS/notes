# Pod Terminating — проблемы размонтирования томов (Volume Unmount)

## Определения

**Размонтирование тома (Volume Unmount)** — финальный этап жизненного цикла тома на узле (Node), при котором Kubelet отключает файловую систему тома от дерева каталогов хоста. Выполняется после остановки всех контейнеров Pod.

**Устаревшее монтирование (Stale Mount)** — состояние, при котором точка монтирования остается активной в ядре ОС или в `mount namespace` Kubelet, хотя объект Pod уже помечен как удаленный. Это блокирует удаление PVC/PV и освобождение ресурсов хранилища.

**Kubelet Volume Manager** — подсистема Kubelet, работающая в отдельном цикле (reconciliation loop). Она сверяет желаемое состояние (Desired State) томов из API с текущим состоянием (Actual State) на узле и инициирует операции монтирования/размонтирования.

**Подпути (Volume Subpaths)** — механизм Kubernetes для монтирования части тома (или одного файла) в контейнер. Создает дополнительные точки монтирования в `/var/lib/kubelet/pods/<pod-uid>/volume-subpaths/`, которые часто становятся причиной блокировки основного тома.

**Распространение монтирования (Mount Propagation)** — режим взаимодействия между Mount Namespace хоста и контейнера (`None`, `HostToContainer`, `Bidirectional`). При `Bidirectional` контейнер может создавать монтирования, которые "утекают" на хост и блокируют очистку.

**Lazy Unmount (`umount -l`)** — "ленивое" размонтирование. Немедленно удаляет точку монтирования из иерархии ФС, делая её недоступной для новых процессов, но ядро фактически освобождает ресурсы только после закрытия всех существующих файловых дескрипторов.

## Базовые концепции

### Процесс очистки томов (Cleanup Workflow)

Когда Pod переходит в `Terminating`, Kubelet следует строгому алгоритму:

1.  **Graceful Shutdown контейнеров:** Ожидание завершения процессов.
2.  **Проверка использования (Refcount check):** Volume Manager проверяет, не используется ли том другими контейнерами того же Pod.
3.  **Размонтирование подпутей (Unmount Subpaths):** Сначала очищаются все `bind mounts` в директории `volume-subpaths`.
4.  **Размонтирование основного тома (NodeUnmount):** Выполняется системный вызов `umount` для пути в `/var/lib/kubelet/pods/<pod-uid>/volumes/`.
5.  **Очистка CSI (NodeUnpublishVolume):** Вызов метода `NodeUnpublish` у CSI-драйвера для финализации очистки на уровне узла.
6.  **Detach (ControllerUnpublish):** Внешний контроллер (AD Controller) инициирует `ControllerUnpublish` (отсоединение диска от ВМ).

### Механизмы блокировки размонтирования

| Фактор | Описание проблемы |
| :--- | :--- |
| **Открытые дескрипторы** | Процессы (включая зомби или sidecars) удерживают файлы. Часто это логи или сокеты. |
| **Зависшие Subpaths** | Баг или сбой Kubelet, при котором подпуть не размонтировался, блокируя родительский том. |
| **SELinux / AppArmor** | Политики безопасности могут запрещать Kubelet выполнять `umount`, если контекст процесса и монтирования конфликтуют. |
| **Сетевые сбои (NFS/iSCSI)** | При потере связи с хранилищем системный вызов `umount` уходит в состояние `D` (Uninterruptible Sleep). |
| **Shared Mounts** | Использование `mount --bind` сторонними сервисами (например, агентами мониторинга или бэкапа) на узле. |

## Практические сценарии

### Сценарий 1: Блокировка процессами (In-use)

**Симптом:**
В логах Kubelet: `UnmountVolume.tearDown failed for volume ... volume is in use by another process`.

**Диагностика:**
1. Найти UID пода: `kubectl get pod <name> -o jsonpath='{.metadata.uid}'`.
2. Найти все процессы, удерживающие файлы на томе (выполнять на узле):
   ```bash
   # Поиск процессов по пути
   lsof +D /var/lib/kubelet/pods/<UID>/volumes
   # Альтернатива через fuser (показывает PID и тип доступа)
   fuser -vm /var/lib/kubelet/pods/<UID>/volumes/*/*
   ```

**Решение:**
1. Если процесс — это "осиротевший" контейнер:
   ```bash
   crictl ps -a --pod <UID>
   crictl stop <container-id>
   ```
2. Если процесс сторонний (например, антивирус или агент мониторинга), необходимо настроить исключения для `/var/lib/kubelet`.
3. Принудительное завершение процессов (крайняя мера):
   ```bash
   fuser -ck /var/lib/kubelet/pods/<UID>/volumes/*/*
   ```

### Сценарий 2: Зависшие подпути (Volume Subpaths)

**Симптом:**
Основной том не размонтируется, хотя `lsof` ничего не находит в основной директории `volumes`.

**Диагностика:**
Проверьте наличие активных монтирований в директории подпутей:
```bash
findmnt | grep <UID> | grep "volume-subpaths"
```

**Решение:**
Размонтируйте подпути вручную в обратном порядке:
```bash
for subpath in $(findmnt -rn -o TARGET | grep "<UID>/volume-subpaths"); do
  umount -l "$subpath"
done
```

### Сценарий 3: "Призрачные" монтирования (Mountinfo)

**Симптом:**
Директория пода пуста, `df` ничего не показывает, но Kubelet продолжает сообщать об ошибке размонтирования.

**Диагностика:**
Проверка через `mountinfo` (ядро видит больше, чем утилита `mount`):
```bash
grep <UID> /proc/self/mountinfo
```
Если записи найдены, значит монтирование "застряло" в namespace.

**Решение:**
1. Попробуйте войти в mount namespace Kubelet (если он запущен в контейнере или имеет свой NS):
   ```bash
   nsenter -t $(pidof kubelet) -m umount -l <путь-из-mountinfo>
   ```
2. Перезапуск Kubelet часто помогает ядру провести очистку (garbage collection) осиротевших монтирований.

### Сценарий 4: Проблемы сетевых ФС (NFS/iSCSI)

**Симптом:**
Команда `df -h` зависает. Kubelet не может размонтировать том из-за тайм-аута RPC.

**Диагностика:**
Проверьте состояние NFS-монтирований:
```bash
nfsstat -m
# Проверка RPC-соединений
rpcinfo -p <nfs-server-ip>
```

**Решение:**
Используйте принудительное размонтирование для сетевых систем:
```bash
umount -f -l /var/lib/kubelet/pods/<UID>/volumes/kubernetes.io~nfs/<vol-name>
```

### Сценарий 5: Конфликты SELinux

**Симптом:**
В `audit.log` видны ошибки `denied { unmount }`.

**Диагностика:**
```bash
ausearch -m avc -ts recent | grep unmount
```

**Решение:**
Если используется RHEL/CentOS, убедитесь, что установлен пакет `container-selinux`. Временное решение для проверки: `setenforce 0`. Если это помогло — необходимо перемаркировать директории Kubelet или обновить политики.

## Дополнительная информация

### Проверка Mount Propagation

Если в Pod используется `mountPropagation: Bidirectional`, контейнер может монтировать ФС внутри себя, и они станут видимыми на хосте. Если контейнер завершится аварийно, эти монтирования на хосте могут остаться активными и блокировать размонтирование основного тома пода.

### Полезные команды для глубокой отладки

*   `lsblk` — проверка, не осталось ли примонтированных блочных устройств CSI.
*   `find /var/lib/kubelet/pods/<UID> -type d` — поиск пустых, но не удаленных директорий.
*   `journalctl -u kubelet --grep "VolumeManager.*unmount"` — фильтрация логов Volume Manager.
