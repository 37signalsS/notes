# Pod Terminating — основные определения и механизмы

## Определения

**`Terminating` (Состояние завершения)** — статус Pod, отображаемый в CLI, который указывает на то, что объект получил `deletionTimestamp`, но ещё не был полностью удалён из API-сервера. Технически Pod может оставаться в фазе `Running` или `Unknown`, пока процесс завершения не будет подтверждён `kubelet`.

**`deletionTimestamp`** — временная метка, устанавливаемая в метаданных объекта при получении команды на удаление. Её наличие переводит Pod в режим «корректного завершения» (graceful shutdown) и блокирует его выборку сервисами (Service) и контроллерами (EndpointSlice).

**`terminationGracePeriodSeconds`** — общее время (по умолчанию 30 секунд), выделяемое поду на самозавершение. **Важно:** этот интервал включает в себя как выполнение `PreStop Hook`, так и время на обработку сигнала `SIGTERM`. Если хук выполняется дольше этого времени, сигнал `SIGTERM` может не быть отправлен до `SIGKILL`.

**`PreStop Hook`** — команда или HTTP-запрос, выполняемый `kubelet` непосредственно перед отправкой сигнала `SIGTERM`. Используется для завершения транзакций или «паузы» для обновления сетевых таблиц в распределенных системах.

**`SIGTERM` (Signal Termination)** — стандартный сигнал POSIX (номер 15), отправляемый основному процессу (PID 1) в каждом контейнере для инициации корректной остановки.

**`SIGKILL` (Signal Kill)** — принудительный сигнал завершения (номер 9), отправляемый процессам, если они не завершились по истечении `terminationGracePeriodSeconds`. Не может быть перехвачен процессом.

**`Native Sidecar` (K8s 1.29+)** — Sidecar-контейнеры, определенные в `initContainers` с полем `restartPolicy: Always`. Имеют специфический порядок завершения (после основных контейнеров).

**Финализатор (Finalizer)** — строка в `metadata.finalizers`, которая сообщает Kubernetes, что объект нельзя удалять из базы данных `etcd` до тех пор, пока не будут выполнены специфические условия (например, отмонтирование диска CSI-драйвером).

**Терминальная фаза (Terminal Phase)** — состояние, при котором Pod достиг конечного статуса (`Succeeded` или `Failed`). Начиная с K8s 1.29, `kubelet` гарантированно переводит поды в терминальную фазу перед удалением, что важно для корректной работы Job и Sidecar-контейнеров.

**`Graceful Node Shutdown` (K8s 1.21+)** — механизм, позволяющий `kubelet` корректно завершать поды при выключении самого узла (через взаимодействие с `systemd-logind`).

**Принудительное удаление (Force Deletion)** — удаление объекта из API без ожидания подтверждения от `kubelet`. Выполняется командой `kubectl delete pod --force --grace-period=0`. Рискованно при использовании `StatefulSet`.

## Базовые концепции

### Процесс удаления Pod

Последовательность действий при штатном удалении:

```
Пользователь/Контроллер → kubectl delete pod
    ↓
API устанавливает metadata.deletionTimestamp
    ↓
---------------------------------------------------------
| Параллельное выполнение:                              |
| 1. Control Plane: Удаление из EndpointSlice/Service    |
| 2. Node (Kubelet): Начало процедуры остановки         |
---------------------------------------------------------
    ↓
Исполнение PreStop hook (если настроен)
    ↓
Отправка SIGTERM основным контейнерам (PID 1)
    ↓
[Ожидание завершения основных контейнеров]
    ↓
Отправка SIGTERM в Native Sidecar контейнеры (K8s 1.29+)
    ↓
[Ожидание завершения или истечение terminationGracePeriodSeconds]
    ↓
Отправка SIGKILL (если процессы всё ещё активны)
    ↓
Размонтирование томов (Volumes) и очистка сетевых ресурсов
    ↓
Kubelet сообщает API о переводе в фазу Succeeded/Failed
    ↓
Снятие системных финализаторов
    ↓
Удаление объекта из etcd
```

Подробное описание процесса: [Graceful Shutdown](./graceful_shutdown.md).

### Стандартные финализаторы (Finalizers)

| Финализатор | Назначение |
| :--- | :--- |
| `kubernetes.io/pod-protection` | Гарантирует, что Pod не будет удалён из API до подтверждения от Kubelet о завершении контейнеров. |
| `node.kubernetes.io/out-of-service` | (K8s 1.24+) Позволяет контроллерам принудительно снять финализаторы на выключенном узле после наложения taints. |
| `external-attacher/<csi-driver>` | Ожидает, пока CSI-контроллер подтвердит физическое отсоединение (detach) тома от узла. |
| `kubernetes.io/pvc-protection` | Предотвращает удаление PVC, если он используется активным подом. |

Проверка финализаторов: `kubectl get pod <name> -o jsonpath='{.metadata.finalizers}'`

### Основные причины зависания в состоянии Terminating

| Категория | Причина | Описание |
| :--- | :--- | :--- |
| **Инфраструктура** | **Проблемы CSI/Томов** | Том не может быть отмонтирован из-за блокировки на уровне ОС или ошибки API облачного провайдера. |
| **Узел** | **Node NotReady/Lost** | Kubelet не выходит на связь. API-сервер ждет подтверждения удаления, которое не может прийти. |
| **Приложение** | **Игнорирование SIGTERM** | Приложение (или PID 1) не обрабатывает сигнал. Часто из-за "shell form" в Dockerfile или отсутствия обработчика. |
| **Сеть** | **Zombies / D-state** | Процессы в состоянии `Uninterruptible Sleep (D)` или зомби-процессы блокируют завершение контейнера/shim. |
| **Политики** | **Блокировка через PDB** | PodDisruptionBudget запрещает удаление, если оно нарушает минимальный порог доступности реплик. |

## Практические сценарии

### Быстрая диагностика зависшего пода

```bash
# 1. Проверка наличия deletionTimestamp и фазы
kubectl get pod <pod-name> -o jsonpath='{.metadata.deletionTimestamp} {.status.phase}'

# 2. Поиск зависших финализаторов (CSI или защита пода)
kubectl get pod <pod-name> -o jsonpath='{.metadata.finalizers}'

# 3. Анализ событий (Events) для выявления ошибок CSI (Attach/Detach)
kubectl describe pod <pod-name> | grep -A 15 Events:

# 4. Проверка состояния узла, на котором запущен Pod
kubectl get node $(kubectl get pod <pod-name> -o jsonpath='{.spec.nodeName}')

# 5. Проверка наличия процессов в D-state на узле
# ps -aux | awk '{if ($8 == "D") print $0}'
```

### Принудительное завершение на выключенном узле (Non-graceful Shutdown)

Если узел окончательно вышел из строя (K8s 1.24+), используйте механизм `out-of-service`:

1.  **Пометить узел как окончательно недоступный:**
    ```bash
    kubectl taint nodes <node-name> node.kubernetes.io/out-of-service=NoExecute:NoExecute
    ```
2.  **Результат:** Системные контроллеры автоматически снимут финализаторы, позволяя подам (в т.ч. StatefulSet) переехать на другие узлы.

## Дополнительная информация

### Сборщик мусора подов (Pod Garbage Collector)

**Pod Garbage Collector (Pod GC)** — контроллер в `kube-controller-manager`, который очищает завершённые объекты.

**Типы очистки:**
1.  **По количеству:** Удаляет старые завершённые поды (фазы `Succeeded`/`Failed`), если их число превышает `--terminated-pod-gc-threshold` (по умолчанию 12500).
2.  **Бесхозные поды:** Удаляет поды, привязанные к удалённым узлам.
3.  **Зависшие поды:** Пытается очистить поды в состоянии `Terminating`, если узел был удалён из API.

**Важно:** Если Pod завис в `Terminating` из-за финализатора (например, CSI), Pod GC **не удалит** его принудительно, так как это нарушило бы гарантии безопасности (риск коррупции данных).

### Проблема PID 1 и проброса сигналов

Если приложение запускается через shell-оболочку (`CMD my-app.sh`), сигналы `SIGTERM` могут не доходить до процесса.
- **Решение:** Используйте "exec form" в Dockerfile (`ENTRYPOINT ["/app/binary"]`) или легковесные init-системы (`tini`, `dumb-init`).
