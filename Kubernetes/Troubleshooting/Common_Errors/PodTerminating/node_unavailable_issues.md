# Pod Terminating — узел недоступен (Node Unavailable)

## Определения

**Pod на недоступном узле в Terminating** — состояние, при котором объект Pod получил метку времени удаления (`deletionTimestamp`), но Kubelet на целевом узле не может подтвердить завершение процессов и очистку ресурсов из-за потери связи с Control Plane.

**Lease объект (Node Lease)** — механизм в пространстве имен `kube-node-lease`, через который Kubelet сообщает о своей жизнеспособности. Обновляется чаще и легче, чем `NodeStatus` (каждые 10 секунд по умолчанию).

**Состояние Unknown** — статус узла (`Ready=Unknown`), возникающий, когда Control Plane не получает обновлений `Lease` или `NodeStatus` в течение `node-monitor-grace-period` (по умолчанию 40с).

**Тайм-аут выселения (Pod Eviction Timeout)** — задержка перед тем, как контроллер начнет удалять поды с неисправного узла (по умолчанию 5 минут). Настраивается через `--pod-eviction-timeout` в `kube-controller-manager`.

Базовые причины потери связи с узлом описаны в разделе: [Определения недоступности узла](../NodeUnavailability/definitions.md).

## Базовые концепции

### Механизм автоматического выселения (Taint-based Eviction)

Когда узел переходит в статус `Unknown` или `NotReady`, запускается цепочка событий:

1.  **Tainting:** Node Controller накладывает на узел taints:
    *   `node.kubernetes.io/unreachable:NoExecute` (связь потеряна).
    *   `node.kubernetes.io/not-ready:NoExecute` (узел сообщил о неготовности).
2.  **Eviction:** Контроллер инициирует удаление подов, у которых нет подходящего `toleration` (или истекло `tolerationSeconds`). По умолчанию Kubernetes автоматически добавляет подам `toleration` для `unreachable` и `not-ready` на 300 секунд.
3.  **Блокировка (Stuck in Terminating):** Объект Pod переходит в `Terminating`, но Kubelet не может:
    *   Послать `SIGTERM`/`SIGKILL` процессам.
    *   Выполнить Unmount томов и Detach через CSI.
    *   Удалить системные финализаторы (например, `kubernetes.io/pod-protection`).

### Нюансы StatefulSet

Для StatefulSet состояние `Terminating` на недоступном узле является критическим механизмом защиты. В отличие от Deployment, StatefulSet гарантирует **уникальность индекса**. Если под `web-0` завис на упавшем узле, контроллер **не создаст** новый `web-0` на другом узле до тех пор, пока старый объект не будет полностью удален из API, чтобы избежать одновременной записи в один том (Split-brain).

### Роль Cloud Controller Manager (CCM)

В облачных средах (AWS, GCP, Azure), если виртуальная машина удалена через консоль облака, CCM обнаружит отсутствие инстанса и удалит объект Node из Kubernetes. Удаление объекта Node автоматически очищает все связанные с ним поды, обходя стандартные тайм-ауты выселения.

## Практические сценарии

### Сценарий 1: Кратковременный сбой (Self-healing)

**Ситуация:** Сетевой "морг" или перезагрузка ОС.

**Действие:** Если критичность приложения позволяет, лучше дождаться возвращения узла. Kubelet после старта синхронизирует состояние с API, завершит старые контейнеры и подтвердит удаление подов.

### Сценарий 2: Принудительное удаление (Force Delete)

**Ситуация:** Узел физически уничтожен, и вы уверены, что процессы на нем не запущены.

**Решение:**
1.  Удалите Pod принудительно:
    ```bash
    kubectl delete pod <pod-name> --force --grace-period=0
    ```
2.  **Проблема Multi-Attach:** Если том остался примонтирован к "мертвому" узлу в системе хранения, новый под на другом узле не сможет его подключить. Проверьте `VolumeAttachment`:
    ```bash
    kubectl get volumeattachment | grep <node-name>
    ```
    В крайнем случае удалите объект `VolumeAttachment` вручную, но это может потребовать ручного вмешательства в консоли СХД.

### Сценарий 3: Non-graceful Node Shutdown (K8s 1.28+ GA)

**Ситуация:** Узел выключен намеренно (например, через IPMI или гипервизор), но Kubelet не успел корректно завершить работу.

**Решение:**
Используйте механизм `out-of-service` taint. Это сигнализирует контроллерам (включая CSI), что можно безопасно отсоединить тома и пересоздать поды.

1.  Установите taint:
    ```bash
    kubectl taint nodes <node-name> node.kubernetes.io/out-of-service=NoExecute:NoExecute
    ```
2.  Дождитесь пересоздания подов.
3.  Удалите taint перед возвращением узла в строй:
    ```bash
    kubectl taint nodes <node-name> node.kubernetes.io/out-of-service-
    ```

### Сценарий 4: Очистка зависших финализаторов

**Ситуация:** Pod не исчезает даже после `--force` удаления и удаления узла.

**Решение:**
Ручное патчинг метаданных (последнее средство):
```bash
kubectl patch pod <pod-name> -p '{"metadata":{"finalizers":[]}}' --type=merge
```
**Внимание:** Это может привести к "осиротевшим" ресурсам в облаке или СХД (неотсоединенные диски).

## Дополнительная информация

### Взаимодействие с PDB

**Важно:** Pod Disruption Budget (PDB) **не блокирует** выселение подов, вызванное taints (`NoExecute`). PDB предназначен только для добровольных прерываний (voluntary disruptions), таких как `kubectl drain` или масштабирование. Непроизвольные прерывания (involuntary disruptions), к которым относится падение узла, игнорируют PDB.

### Диагностика

*   **Статус Lease:** Проверьте время последнего обновления:
    ```bash
    kubectl get lease -n kube-node-lease <node-name> -o yaml
    ```
*   **События узла:**
    ```bash
    kubectl describe node <node-name> | grep -A 10 Events
    ```
*   **Логи контроллера:** Ищите ошибки `Node Eviction` в `kube-controller-manager`.
