# Pod Terminating — узел недоступен (Node Unavailable)

## Определения

**Pod на недоступном узле в Terminating** — состояние, при котором объект Pod получил метку времени удаления (`deletionTimestamp`), но Kubelet на целевом узле не может подтвердить завершение процессов и очистку ресурсов, так как связь узла с Control Plane потеряна.

**Состояние Unknown** — статус узла (`Ready=Unknown`), возникающий, когда Kubelet перестает обновлять свой `Lease` объект или `NodeStatus` в течение времени, превышающего `node-monitor-grace-period` (по умолчанию 40 секунд).

**Тайм-аут выселения (Pod Eviction Timeout)** — задержка перед тем, как контроллер начнет удалять поды с неисправного узла (по умолчанию 5 минут). Управляется через `--pod-eviction-timeout` в `kube-controller-manager`.

Базовые причины потери связи с узлом описаны в разделе: [Определения недоступности узла](../NodeUnavailability/definitions.md).

---

## Базовые концепции

### Механизм автоматического выселения

Когда узел становится недоступным, кластер следует логике:

1.  **Детекция:** По истечении `node-monitor-grace-period` статус узла меняется на `Unknown`.
2.  **Tainting:** Node Controller накладывает на узел taints:
    *   `node.kubernetes.io/unreachable:NoExecute` (если связь потеряна).
    *   `node.kubernetes.io/not-ready:NoExecute` (если узел сообщил о проблеме).
3.  **Eviction:** Если у Pod нет `toleration` к этим taints (или истекло время `tolerationSeconds`), контроллер инициирует удаление объекта.
4.  **Блокировка:** Объект Pod переходит в `Terminating`. Однако, поскольку Kubelet на узле недоступен, он не может:
    *   Завершить процессы (`SIGTERM`/`SIGKILL`).
    *   Освободить тома (Unmount).
    *   Удалить финализаторы (например, `kubernetes.io/pvc-protection`).

### Риск одновременного запуска (Split-Brain)

Для подов с томами (`PersistentVolumes`) принудительное удаление с недоступного узла опасно. Если узел на самом деле жив, но изолирован сетью, принудительный запуск пода на другом узле приведет к тому, что два процесса будут одновременно писать в один и тот же том, что гарантированно повредит файловую систему (особенно для блочных устройств RWO).

## Практические сценарии

### Сценарий 1: Узел временно недоступен (Self-healing)

**Ситуация:** Кратковременный сетевой сбой или перезагрузка узла.

**Действие:** Ничего не предпринимать. Как только связь восстановится:
1.  Kubelet увидит, что Pod удален в API.
2.  Выполнит локальную очистку (stop containers, unmount volumes).
3.  Подтвердит удаление, и объект исчезнет из API.

### Сценарий 2: Принудительное удаление (Force Delete)

**Ситуация:** Узел физически уничтожен и никогда не вернется.

**Решение:**
1.  Удалите Pod принудительно:
    ```bash
    kubectl delete pod <pod-name> --force --grace-period=0
    ```
2.  **Важно:** Если Pod использовал PVC, контроллер хранилища может не отсоединить том от "мертвого" узла автоматически (ошибка Multi-Attach). Проверьте объекты `VolumeAttachment`:
    ```bash
    kubectl get volumeattachment | grep <node-name>
    ```

### Сценарий 3: Non-graceful Node Shutdown (K8s 1.24+)

**Ситуация:** Современный и безопасный способ обработки выключенных узлов, особенно для StatefulSet.

**Решение:**
Вместо небезопасного `force delete`, пометьте узел как "выведенный из строя". Это даст сигнал контроллерам, что поды можно безопасно перезапустить на других узлах, так как тома гарантированно не используются.

1.  Наложите специальный taint:
    ```bash
    kubectl taint nodes <node-name> node.kubernetes.io/out-of-service=NoExecute:NoExecute
    ```
2.  После того как все поды будут пересозданы на других узлах, и вы убедитесь в стабильности, удалите taint:
    ```bash
    kubectl taint nodes <node-name> node.kubernetes.io/out-of-service-
    ```

### Сценарий 4: Очистка зависших финализаторов

**Ситуация:** Pod застрял в `Terminating` даже после удаления узла и использования `--force`.

**Решение:**
Ручное снятие финализаторов (использовать только если вы уверены, что ресурсы томов очищены или узел физически отсутствует):
```bash
kubectl patch pod <pod-name> -p '{"metadata":{"finalizers":[]}}' --type=merge
```

## Дополнительная информация

*   Проверка времени последнего сердцебиения: `kubectl get node <name> -o yaml` (поле `lastHeartbeatTime`).
*   Логи контроллера: `journalctl -u kube-controller-manager` (поиск событий `Eviction`).
