# Pod Terminating — корректное завершение (Graceful Shutdown)

## Определения

**Корректное завершение (Graceful Shutdown)** — регламентированный процесс остановки Pod, при котором приложению предоставляется время на корректную обработку текущих запросов, закрытие сетевых соединений и сохранение состояния перед физическим уничтожением контейнеров.

**Обработчик preStop (preStop hook)** — команда или HTTP-запрос, который `kubelet` выполняет внутри контейнера непосредственно перед отправкой сигнала `SIGTERM`. Основное назначение — дать приложению время на исключение из балансировщиков (Service, Ingress) или выполнение финальных действий.

**Период корректного завершения (`terminationGracePeriodSeconds`)** — общее время (по умолчанию 30 секунд), выделяемое на весь процесс остановки пода. Этот интервал включает выполнение `preStop hook` и время на обработку `SIGTERM`.

**Сигнал SIGTERM (Signal Termination)** — стандартный сигнал завершения (номер 15), отправляемый основному процессу (PID 1) контейнера. Приложение должно уметь перехватывать этот сигнал для инициации внутренней процедуры остановки.

**Сигнал SIGKILL (Signal Kill)** — принудительный сигнал немедленной остановки (номер 9). Отправляется ядром ОС процессам, которые не завершились по истечении установленного `terminationGracePeriodSeconds`.

## Базовые концепции

### Последовательность событий при удалении Pod

Процесс остановки инициируется через API-сервер (команда `delete`, работа автоскейлера или контроллера реплик).

1.  **Маркировка в API**: Объект Pod получает временную метку `deletionTimestamp`. Его статус меняется на `Terminating`.
2.  **Исключение из трафика**: Одновременно с другими действиями контроллер `EndpointSlice` (или `Endpoints`) удаляет Pod из списка активных бэкендов для всех связанных сервисов. Балансировщики перестают направлять на него новые запросы.
3.  **Запуск preStop hook**: `Kubelet` на узле запускает настроенный хук. **Важно**: `kubelet` ждёт завершения выполнения `preStop hook` прежде чем переходить к следующему шагу.
4.  **Отправка SIGTERM**: Сразу после завершения `preStop hook` (или если он не настроен), `kubelet` отправляет сигнал `SIGTERM` всем основным процессам (PID 1) в каждом контейнере пода.
5.  **Ожидание и SIGKILL**: `Kubelet` отсчитывает оставшееся время от `terminationGracePeriodSeconds`. Если по истечении этого времени контейнеры всё еще запущены, `kubelet` отправляет сигнал `SIGKILL`, принудительно завершая все процессы.

### Порядок завершения Sidecar-контейнеров (K8s 1.29+)

Если в поде используются Sidecar-контейнеры (новое поле `restartPolicy: Always` в `initContainers`), порядок завершения строго определен:
1.  Сначала завершаются основные контейнеры (через `preStop` и `SIGTERM`).
2.  Только после полной остановки основных контейнеров `kubelet` инициирует завершение Sidecar-контейнеров. Это позволяет вспомогательным сервисам (логирование, прокси) работать до самого конца жизни приложения.

### Проблема PID 1 и проброса сигналов

Если приложение запускается через shell-оболочку (например, `ENTRYPOINT /app/start.sh`), оболочка становится процессом с PID 1.
- **Проблема**: Многие оболочки (sh, bash) не пробрасывают сигналы (`SIGTERM`) дочерним процессам.
- **Симптом**: Приложение игнорирует `SIGTERM` и всегда завершается принудительно через 30 секунд по `SIGKILL`.
- **Решение**: Использовать "exec form" в Dockerfile (`CMD ["/app/binary"]`) или команду `exec` в скрипте запуска (`exec /app/binary`).

## Практические сценарии

### Настройка корректного завершения

Пример для веб-приложения, которому требуется время на очистку соединений:

```yaml
spec:
  terminationGracePeriodSeconds: 60  # Увеличенное время для долгоживущих соединений
  containers:
  - name: web-app
    lifecycle:
      preStop:
        exec:
          # Пауза в 5-10 секунд позволяет Endpoints обновиться в распределенной сети
          command: ["/bin/sh", "-c", "sleep 10"]
```

### Диагностика причин некорректного завершения

Если Pod всегда завершается по таймауту (`SIGKILL`), проведите проверку по шагам:

**1. Проверка обработки сигналов процессом**
Зайдите в контейнер и проверьте дерево процессов:
```bash
kubectl exec <pod-name> -- ps -ef
```
Если ваш бинарный файл не имеет PID 1, скорее всего, он не получает сигналы.

**2. Анализ логов приложения**
В логах должны присутствовать записи о получении `SIGTERM` и начале Graceful Shutdown:
```text
[INFO] Received SIGTERM, shutting down...
[INFO] Waiting for active connections to close...
```
Если таких логов нет — приложение либо не получает сигнал, либо не умеет его обрабатывать.

**3. Проверка длительности preStop**
Если `preStop hook` выполняется слишком долго (например, `sleep 40` при `gracePeriod: 30`), `SIGTERM` может вообще не быть отправлен, так как под будет убит по `SIGKILL` прямо во время выполнения хука.

### Принудительное удаление (Force Delete)

Используйте только как крайнюю меру:
```bash
kubectl delete pod <pod-name> --force --grace-period=0
```
**Последствия**:
- Не выполняется `preStop` и `SIGTERM`.
- В `etcd` запись удаляется сразу, но процессы на узле могут зависнуть в состоянии Zombie.
- Для StatefulSet это может привести к невозможности запуска нового пода, если старый все еще удерживает диск.

## Дополнительная информация

### Рекомендации по настройке
- **Grace Period > preStop**: Всегда устанавливайте `terminationGracePeriodSeconds` больше, чем время выполнения самого долгого `preStop hook` + время на остановку приложения.
- **Использование dumb-init**: Для сложных контейнеров рекомендуется использовать легковесный менеджер процессов (например, `tini` или `dumb-init`), который корректно управляет PID 1 и сигналами.
