# Pod Terminating — корректное завершение (Graceful Shutdown)

## Определения

**Корректное завершение (Graceful Shutdown)** — регламентированный процесс остановки Pod, при котором приложению предоставляется время на корректную обработку текущих запросов, закрытие сетевых соединений и сохранение состояния перед физическим уничтожением контейнеров.

**Обработчик preStop (preStop hook)** — команда или HTTP-запрос, который `kubelet` выполняет внутри контейнера непосредственно перед отправкой сигнала `SIGTERM`. Основное назначение — искусственная задержка для синхронизации состояния сети или выполнение финализации (например, выход из кворума).

**Период корректного завершения (`terminationGracePeriodSeconds`)** — общее время (по умолчанию 30 секунд), выделяемое на весь процесс остановки пода. Этот интервал включает выполнение `preStop hook` и время на обработку `SIGTERM`.

**Контейнерный Grace Period (K8s 1.25+)** — возможность задать индивидуальный `terminationGracePeriodSeconds` на уровне конкретного контейнера. Это полезно, если сайдкару нужно меньше времени на остановку, чем основному приложению.

**Сигнал SIGTERM (Signal Termination)** — стандартный сигнал завершения (номер 15), отправляемый процессу с PID 1. Приложение должно уметь перехватывать этот сигнал для инициации внутренней процедуры остановки.

**Сигнал SIGKILL (Signal Kill)** — принудительный сигнал немедленной остановки (номер 9). Не может быть перехвачен процессом. Отправляется ядром ОС процессам, которые не завершились по истечении установленного лимита времени.

## Базовые концепции

### Последовательность событий и сетевая гонка (Race Condition)

Процесс остановки инициируется через API-сервер. Ключевая проблема — асинхронность уведомлений:

1.  **Маркировка в API**: Установка `deletionTimestamp`. Статус — `Terminating`.
2.  **Сетевой уровень (EndpointSlice)**: Контроллер удаляет Pod из списка эндпоинтов. Узлы кластера (kube-proxy, Ingress-контроллеры, CoreDNS) получают уведомление об обновлении.
3.  **Уровень узла (Kubelet)**: `kubelet` на узле получает уведомление об удалении и **параллельно** с обновлением сети запускает процесс остановки.

**Проблема задержки (Propagation Delay):** `kubelet` может начать останавливать контейнер раньше, чем Ingress или `kube-proxy` на других узлах успеют обновить свои таблицы маршрутизации. Это приводит к ошибкам 502/504, так как трафик продолжает идти на под, который уже начал закрывать соединения.
**Решение:** Использование `preStop` хука с командой `sleep`, чтобы под оставался «живым» и принимал трафик, пока сеть синхронизируется.

### Порядок завершения Native Sidecar (K8s 1.29+)

Для контейнеров в `initContainers` с `restartPolicy: Always`:
1.  Сначала завершаются основные контейнеры (`containers[]`).
2.  `kubelet` ожидает их полной остановки.
3.  Только после этого инициируется остановка сайдкаров. Это гарантирует, что сайдкар (например, прокси или сборщик логов) работает до тех пор, пока основное приложение не завершится.

### Проблема PID 1 и проброса сигналов

Если приложение запускается через shell (`ENTRYPOINT /app/start.sh` без `exec`), сигналы `SIGTERM` поглощаются shell-оболочкой.
- **Симптом**: Приложение всегда удаляется ровно через 30 секунд (по `SIGKILL`).
- **Решение**: Использовать `exec` в скриптах или массивную форму в Dockerfile (`CMD ["/app/binary"]`).

## Практические сценарии

### Идеальная настройка Graceful Shutdown

Пример манифеста, решающего проблему сетевой гонки и долгого закрытия соединений:

```yaml
spec:
  terminationGracePeriodSeconds: 60  # Сумма sleep + время работы приложения
  containers:
  - name: web-app
    lifecycle:
      preStop:
        exec:
          # Даем 10-15 секунд на то, чтобы EndpointSlice обновился во всем кластере
          command: ["/bin/sh", "-c", "sleep 15"]
```

### Обработка SIGTERM в различных рантаймах

Приложение должно явно слушать сигнал. Примеры логики:

- **Go**: `signal.Notify(c, syscall.SIGTERM)`
- **Node.js**: `process.on('SIGTERM', () => server.close())`
- **Python**: `signal.signal(signal.SIGTERM, handler)`

Если приложение использует `readinessProbe`, хорошим паттерном является перевод пробы в статус `Failed` в самом начале обработки `SIGTERM`, хотя `preStop sleep` является более надежным способом исключения из трафика.

### Диагностика процесса завершения на узле

Если вы сомневаетесь, получает ли контейнер сигналы, проверьте это через CRI (на узле):

```bash
# 1. Поиск контейнера и его PID на хосте
CONTAINER_ID=$(crictl ps --name web-app -q)
PID=$(crictl inspect $CONTAINER_ID | jq .info.pid)

# 2. Мониторинг системных вызовов в реальном времени (нужен strace)
strace -p $PID -e signal

# 3. Проверка дерева процессов
ps -fH -p $PID
```

### Типичные ошибки конфигурации

| Ошибка | Последствие | Решение |
| :--- | :--- | :--- |
| **preStop > GracePeriod** | Контейнер будет убит по `SIGKILL` до того, как завершится `preStop`. | Увеличьте `terminationGracePeriodSeconds`. |
| **Отсутствие PID 1** | Приложение не видит `SIGTERM`. | Используйте `tini` или `exec form`. |
| **Игнорирование SIGTERM** | Приложение резко обрывает транзакции. | Реализуйте обработчик сигнала в коде (Graceful Exit). |
| **Длительный PDB** | `drain` узла зависает из-за блокировки. | Проверьте [Блокировку PDB](./pdb_blocking.md). |

## Дополнительная информация

### Использование dumb-init и tini
Для приложений, которые не могут корректно работать как PID 1 (например, не умеют собирать "зомби-процессы"), рекомендуется использовать легковесные менеджеры:
```dockerfile
ENTRYPOINT ["/sbin/tini", "--"]
CMD ["/app/app.py"]
```

### Взаимодействие с облачными балансировщиками
При использовании AWS Load Balancer Controller или GCP Ingress, задержка обновления таргетов (Target Group) может достигать 30-120 секунд. В таких случаях `preStop sleep` должен быть соразмерен времени `Deregistration Delay` в настройках балансировщика.
