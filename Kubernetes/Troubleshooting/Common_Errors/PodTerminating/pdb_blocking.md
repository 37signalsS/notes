# Pod Terminating — блокировка через PDB

## Определения

**Блокировка удаления через PDB** — состояние, при котором объект Pod застревает в процессе удаления или выселения (eviction), так как его завершение нарушит заданный бюджет доступности (Pod Disruption Budget).

**Eviction API** — механизм, используемый командами обслуживания (например, `kubectl drain`) для безопасного удаления подов. В отличие от прямой команды `delete`, Eviction API всегда проверяет наличие и состояние PDB.

**Violation of Disruption Budget** — ошибка, возвращаемая API server, когда текущее количество здоровых реплик равно или меньше значения `minAvailable` (или равно пределу `maxUnavailable`), и удаление ещё одного пода недопустимо.

---

## Базовые концепции

### Почему PDB блокирует завершение

PDB защищает приложение от **добровольных прерываний** (voluntary disruptions), таких как:

- Выполнение `kubectl drain` администратором узла.
- Работа Cluster Autoscaler при уменьшении количества узлов.
- Обновление конфигурации узлов облачным провайдером.

Если под удаляется напрямую командой `kubectl delete pod`, PDB **игнорируется**. Блокировка в состоянии `Terminating` через PDB обычно возникает при автоматизированных процессах (drain), которые не могут завершить выселение пода.

### Симптомы проблемы

Основной признак — сообщение в событиях (Events) или выводе команды drain:

```text
Cannot evict pod as it would violate the pod's disruption budget.
```

В статусе PDB (`kubectl get pdb`) значение `ALLOWED DISRUPTIONS` при этом равно `0`.

## Практические сценарии

### Диагностика блокировки

#### Шаг 1: Поиск проблемного PDB

Найдите PDB, который защищает ваш Pod:

```bash
# Поиск PDB в текущем namespace
kubectl get pdb

# Проверка селектора
kubectl describe pdb <pdb-name>
```

#### Шаг 2: Анализ состояния бюджета

Проверьте значения в выводе:

```bash
kubectl get pdb <pdb-name>
# → NAME      MIN AVAILABLE   CURRENT   DESIRED   ALLOWED DISRUPTIONS
# → web-pdb   2               2         2         0
```

Если `ALLOWED DISRUPTIONS` равен `0`, выселение невозможно. Это может происходить, если:

1. Часть подов уже недоступна (статус не `Ready`).
2. Общее количество реплик равно `minAvailable`.
3. Установлено `maxUnavailable: 0` или `minAvailable: 100%`.

### Методы решения

#### Вариант 1: Увеличение количества реплик (рекомендуется)

Если приложение управляется Deployment или StatefulSet, добавьте временную реплику, чтобы удовлетворить бюджет:

```bash
kubectl scale deployment <deployment-name> --replicas=<current+1>
```

После того как новый Pod станет `Ready`, `ALLOWED DISRUPTIONS` увеличится, и заблокированный Pod будет удален.

#### Вариант 2: Корректировка бюджета (Patch)

Временно уменьшите требования PDB, чтобы разрешить удаление одного пода:

```bash
# Пример для minAvailable
kubectl patch pdb <pdb-name> -p '{"spec":{"minAvailable":1}}'

# Пример для maxUnavailable
kubectl patch pdb <pdb-name> -p '{"spec":{"maxUnavailable":1}}'
```

#### Вариант 3: Принудительное удаление (в обход PDB)

Если блокировка вызвана процессом `drain`, вы можете удалить Pod напрямую. Это проигнорирует PDB:

```bash
kubectl delete pod <pod-name> --grace-period=30
```

**Внимание:** это может привести к кратковременной недоступности приложения, если оставшихся подов недостаточно для обработки трафика.

#### Вариант 4: Очистка зависших подов

Если бюджет нарушен из-за того, что некоторые поды находятся в `CrashLoopBackOff` или `Pending`, они занимают место в расчетах, но не считаются «здоровыми» (`Ready`). Исправьте их состояние или удалите проблемные объекты.
