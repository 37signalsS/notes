# Недоступность узла: Плановое обслуживание

## Определения

**Зависание обслуживания** — состояние, при котором процесс вывода узла из эксплуатации (дренаж) не завершается в отведенное время или узел остается недоступным для планировщика после завершения работ.

**Забытый узел** — исправный узел, который остался в состоянии `SchedulingDisabled` из-за отсутствия команды `uncordon`.

**Eviction API (Интерфейс выселения)** — программный интерфейс Kubernetes, обеспечивающий безопасное удаление подов с соблюдением бюджетов доступности и параметров корректного завершения.

Основные определения процедур обслуживания (Cordon, Drain, Uncordon) приведены в разделе: [Обслуживание узлов Kubernetes: Cordon и Drain](../../../Operations/node_maintenance.md).

## Основные концепции

### Статусы узла при обслуживании

Для диагностики причин недоступности узла используются следующие индикаторы:

| Индикатор | Значение | Описание |
| :--- | :--- | :--- |
| `SchedulingDisabled` | В выводе `kubectl get nodes` | На узел наложен запрет планирования (`cordon`). |
| `Unschedulable` | `true` (в `describe node`) | Внутренний флаг спецификации (`.spec.unschedulable`). |
| События (Events) | `Cordon`, `Drain` | Фиксируют начало и результат процедур обслуживания. |

### Типичные причины сбоев

Диагностика проблем обслуживания обычно выявляет одну из трех категорий неисправностей:

1. **Программная блокировка:** Ошибки при выполнении `kubectl drain` (PDB, локальные данные, финализаторы).
2. **Административная ошибка:** Пропуск шага возврата узла в кластер (`uncordon`).
3. **Инфраструктурный сбой:** Ошибка запуска Kubelet или Container Runtime после перезагрузки.

## Практические сценарии

### Сценарий 1: Узел застрял в состоянии SchedulingDisabled

Если узел имеет статус `Ready`, но новые поды на него не назначаются:

1. Проверьте флаг `unschedulable`:

   ```bash
   kubectl get node <node-name> -o jsonpath='{.spec.unschedulable}'
   # → true
   ```

2. Если плановые работы завершены, верните узел в работу:

   ```bash
   kubectl uncordon <node-name>
   ```

### Сценарий 2: Ошибки выселения при выполнении kubectl drain

Если процесс дренажа блокируется, проверьте следующие факторы:

* **PDB (Pod Disruption Budget — бюджет прерывания подов):** Команда `drain` не удалит под, если это нарушит бюджет доступности.

  ```bash
  kubectl get pdb -A
  ```

* **Локальные данные (emptyDir):** Kubernetes защищает поды, использующие временные локальные хранилища.
  * *Решение:* Используйте флаг `--delete-emptydir-data`.
* **DaemonSet:** Эти поды не подлежат дренажу стандартным способом.
  * *Решение:* Используйте флаг `--ignore-daemonsets`.
* **Поды без контроллера (Bare Pods):** Поды, созданные напрямую без Deployment или ReplicaSet.
  * *Решение:* Используйте флаг `--force`.

### Сценарий 3: Поды застряли в состоянии Terminating

Если под не исчезает с узла после команды выселения, это часто связано с наличием `Finalizers` (финализаторов), ожидающих завершения внешних процессов.

1. Проверьте наличие финализаторов:

   ```bash
   kubectl get pod <pod-name> -o jsonpath='{.metadata.finalizers}'
   ```

2. Если внешние ресурсы (например, тома или записи в БД) уже очищены, удалите финализаторы вручную:

   ```bash
   kubectl patch pod <pod-name> -p '{"metadata":{"finalizers":null}}' --type=merge
   ```

### Сценарий 4: Узел NotReady после обслуживания

Если после проведения работ узел не переходит в статус `Ready`:

1. Проверьте состояние системных служб на узле:

   ```bash
   systemctl status kubelet
   systemctl status containerd
   ```

2. Проанализируйте логи Kubelet на наличие ошибок сети, сертификатов или аутентификации:

   ```bash
   journalctl -u kubelet -n 50 --no-pager
   ```
