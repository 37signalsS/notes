# Недоступность узла: Проблемы при обслуживании

## Основные определения

**Зависание обслуживания (Maintenance Hang)** — состояние, при котором процедура дренажа (`drain`) не завершается из-за блокирующих факторов (PDB, финализаторы) или узел остаётся в нерабочем состоянии после физической перезагрузки.

**Забытый узел (Stale SchedulingDisabled)** — исправный узел, который ошибочно остался в состоянии `SchedulingDisabled` после завершения работ, так как не была выполнена команда `uncordon`.

**Eviction API** — программный интерфейс, используемый для безопасного выселения подов. В отличие от прямого удаления, он запрашивает разрешение у контроллеров, что может привести к блокировке процесса обслуживания.

Базовые инструкции по проведению работ доступны в разделе: [Обслуживание узлов Kubernetes: Cordon и Drain](../../../Operations/node_maintenance.md).

## Основные концепции

### Механизмы блокировки обслуживания

Процесс вывода узла может быть остановлен на уровне API по следующим причинам:

1.  **Нарушение PodDisruptionBudget (PDB)**: Если выселение очередного пода приведет к тому, что количество доступных реплик упадет ниже `minAvailable` или превысит `maxUnavailable`.
2.  **Наличие финализаторов (`finalizers`)**: Поды или связанные с ними ресурсы (например, VolumeAttachment) имеют метаданные, блокирующие удаление до выполнения внешнего условия.
3.  **Локальное хранилище**: Поды с типом диска `emptyDir` защищены от случайного удаления данных, если не указан явный флаг подтверждения.

### Жизненный цикл Heartbeats при обслуживании

Во время планового обслуживания (особенно при обновлении ядра или прошивок) важно учитывать поведение **Node Lease**:
- Если узел выключен дольше, чем `node-monitor-grace-period` (обычно 40с), он перейдет в статус `Unknown`.
- Это инициирует автоматическое наложение taints и может запустить процесс выселения подов на уровне контроллера, даже если вы предварительно сделали `cordon`.

## Практические сценарии

### Сценарий 1: Узел «завис» в SchedulingDisabled

**Симптом**: Узел `Ready`, но планировщик его игнорирует.
**Причина**: Не выполнен возврат узла в работу.

**Диагностика**:
```bash
kubectl get nodes <node-name>
# В колонке STATUS будет Ready,SchedulingDisabled
```

**Решение**:
```bash
kubectl uncordon <node-name>
```

### Сценарий 2: Блокировка kubectl drain

**Симптом**: Команда `kubectl drain` выполняется бесконечно или завершается с ошибкой.

**Причины и решения**:
- **PDB**: Проверьте бюджеты `kubectl get pdb -A`. Если бюджет нарушен, увеличьте количество реплик или временно скорректируйте PDB.
- **DaemonSet**: Убедитесь, что используете `--ignore-daemonsets`.
- **Локальные данные**: Если под использует `emptyDir`, добавьте `--delete-emptydir-data`.
- **Тайм-ауты**: Для автоматизации всегда используйте `--timeout=5m`, чтобы дренаж не блокировал очередь обновлений.

### Сценарий 3: Поды застряли в статусе Terminating

**Симптом**: После успешного дренажа поды остаются на узле в статусе удаления.

**Диагностика**:
Проверьте финализаторы пода:
```bash
kubectl get pod <pod-name> -o jsonpath='{.metadata.finalizers}'
```

**Решение**:
Если вы уверены, что узел выключен и данные в безопасности, удалите финализаторы вручную:
```bash
kubectl patch pod <pod-name> -p '{"metadata":{"finalizers":null}}' --type=merge
```

### Сценарий 4: Узел NotReady после перезагрузки

**Симптом**: Узел загрузился, но статус `NotReady`.

**Алгоритм проверки**:
1.  **Статус сервисов**:
    ```bash
    systemctl status kubelet containerd
    ```
2.  **Логи рантайма**: Часто после обновления ОС не запускается `containerd` из-за несовместимости конфигурации или отсутствия модулей ядра (например, `overlay`, `br_netfilter`).
    ```bash
    journalctl -u containerd -n 50
    ```
3.  **Монтирование дисков**: Если `/var/lib/kubelet` или `/var/lib/containerd` вынесены на отдельные разделы, проверьте их успешное монтирование.

### Сценарий 5: Сбой Graceful Node Shutdown

**Симптом**: При выключении узла (через `shutdown` или кнопку) поды убиваются мгновенно (SIGKILL) вместо плавного завершения (SIGTERM).

**Решение**:
Убедитесь, что в конфигурации `kubelet` настроены параметры:
```yaml
shutdownGracePeriod: 30s
shutdownGracePeriodCriticalPods: 10s
```
И проверьте, что служба `systemd-logind` запущена и передает сигналы в `kubelet`.
