# Недоступность узла: Сетевые проблемы

## Основные определения

**`NetworkUnavailable`** — состояние узла (условие `NetworkUnavailable` равно `True`), указывающее на то, что CNI-плагин (Container Network Interface) не смог корректно настроить сетевой стек для подов. Это блокирует запуск новых подов, так как они не могут получить IP-адрес.

**Node Unreachable (Network)** — состояние, при котором узел полностью теряет связь с Control Plane. В отличие от проблем агента `kubelet`, здесь сбой происходит на уровне L2/L3 инфраструктуры (коммутаторы, маршрутизаторы, правила файрволов) или сетевого стека ядра ОС.

**Связь с Node Lease**: Сетевые задержки или потери пакетов напрямую влияют на обновление объектов **Lease**. Если `kubelet` не может отправить heartbeat из-за сети в течение `node-monitor-grace-period` (40с), узел переходит в статус `Unknown`.

## Основные концепции

### Компоненты сетевой связности

| Компонент | Роль в доступности узла |
| :--- | :--- |
| **CNI Plugin** | Настройка интерфейсов (`eth0` в поде), мостов (`cni0`) и маршрутов. |
| **kube-proxy** | Управление правилами трансляции адресов (iptables или IPVS). |
| **CoreDNS** | Разрешение имен внутри кластера (сбой DNS часто воспринимается как недоступность сети). |
| **Контроллер узлов** | Помечает узел `Unknown`, если сеть не пропускает трафик Lease. |

### Глубокие причины сетевых сбоев

1.  **Проблемы MTU (Maximum Transmission Unit)**: При использовании инкапсуляции (VXLAN в Calico/Flannel, IPIP) добавляется заголовок (обычно 50 байт). Если MTU на физическом интерфейсе равен 1500, то внутри туннеля он должен быть 1450. Несоответствие приводит к отбрасыванию больших пакетов.
2.  **Переполнение таблиц ядра**:
    *   **Conntrack**: Таблица отслеживания соединений. При превышении лимита новые соединения (включая DNS-запросы и heartbeats) отбрасываются.
    *   **ARP-таблица**: Лимит записей о соседях в сегменте L2 (актуально для больших кластеров).
3.  **Облачные лимиты**: Ограничения облачного провайдера на количество пакетов в секунду (PPS) или количество одновременных соединений на инстанс.

## Практические сценарии

### Сценарий 1: Состояние NetworkUnavailable=True

**Симптомы**: Узел `NotReady`, поды в `ContainerCreating`, в `describe node` видно `NetworkUnavailable=True`.

**Диагностика**:
```bash
# 1. Проверка наличия конфигурации CNI
ls -la /etc/cni/net.d/

# 2. Проверка подов CNI в пространстве имен kube-system
kubectl get pods -n kube-system -l k8s-app=calico-node # или cilium/flannel

# 3. Проверка логов CNI (через crictl, если kubectl на узле не работает)
crictl logs $(crictl ps --name calico-node -q)
```

**Решение**: Перезапуск DaemonSet сетевого плагина или исправление конфигурации в `/etc/cni/net.d/`.

### Сценарий 2: Проблемы MTU (пакеты теряются под нагрузкой)

**Симптомы**: Мелкие команды (ping) работают, но TCP-соединения (HTTP, скачивание образов) «зависают» или обрываются по таймауту.

**Диагностика**:
```bash
# Проверка Path MTU Discovery с запретом фрагментации
ping -M do -s 1472 <target-ip> 
# Если не проходит, пробуйте уменьшать размер (например, 1422 для VXLAN)
```

**Решение**: Уменьшить MTU в конфигурации CNI-плагина (например, в ConfigMap Calico или Flannel).

### Сценарий 3: Переполнение таблицы Conntrack

**Симптомы**: Случайные отказы в установке соединений, ошибки `connection refused` или `timeout` при наличии ресурсов.

**Диагностика**:
```bash
# 1. Проверка текущего заполнения и лимита
sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max

# 2. Проверка сообщений в dmesg
dmesg | grep -i "conntrack table full"
```

**Решение**: Увеличить лимит в `/etc/sysctl.conf` или оптимизировать таймауты соединений.

### Сценарий 4: Узел в статусе Unknown (полная изоляция)

**Симптомы**: `kubectl get nodes` показывает `Unknown`. SSH недоступен.

**Алгоритм**:
1.  Проверить статус ВМ/сервера в консоли облака или через IPMI.
2.  Проверить правила Security Groups / Firewall (порт 6443 и порты CNI).
3.  Проверить статус анонсов маршрутов (если используется BGP/Calico).
