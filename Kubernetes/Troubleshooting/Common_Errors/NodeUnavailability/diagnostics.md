# Диагностика недоступности узла: Алгоритм

## Основные определения

**Диагностика узла** — системный процесс выявления причин перехода узла в состояния `NotReady` или `Unknown`. Включает в себя последовательный анализ от уровня Kubernetes API до низкоуровневых проверок ядра ОС и аппаратного обеспечения.

**Целевое состояние** — точная локализация компонента сбоя (сеть, `kubelet`, дефицит ресурсов, CRI-рантайм или ядро ОС) для применения соответствующего сценария восстановления.

Основные статусы и условия описаны в разделе: [Недоступность узла: Определения](./definitions.md).

## Основные концепции

### Инструменты диагностики

| Инструмент | Уровень | Назначение |
| :--- | :--- | :--- |
| **`kubectl`** | Кластер | Внешний осмотр через API (основной инструмент). |
| **`kubectl debug node/`** | Узел | Современный метод отладки через эфемерные контейнеры без прямого SSH. |
| **`ssh`** | ОС | Прямой доступ к узлу для глубокого анализа. |
| **`systemctl` / `journalctl`** | Сервисы | Проверка статуса и логов `kubelet` и CRI (containerd). |
| **`dmesg`** | Ядро | Поиск аппаратных ошибок, проблем с дисками и срабатываний OOM-killer. |

### Ключевые индикаторы (Node Conditions)

При выполнении `kubectl describe node <node-name>` критически важными являются поля `Reason` и `Message`:

| Reason | Состояние | Интерпретация |
| :--- | :--- | :--- |
| **`KubeletReady`** | `True` | `kubelet` работает штатно. |
| **`KubeletNotReady`** | `False` | `kubelet` активен, но есть блокирующие проблемы (обычно CNI или Storage). |
| **`KubeletStopped`** | `False` | Служба `kubelet` на узле остановлена. |
| **`NodeStatusNeverUpdated`** | `Unknown` | API-сервер не получал heartbeats (Lease) с момента создания объекта. |
| **`NodeStatusUnknown`** | `Unknown` | Потеря связи с работающим ранее узлом (тайм-аут Lease). |

### Сетевые зависимости

Для корректной работы узла должны быть открыты порты:
- **`10250`** (TCP): Входящий для `kubelet` API (логи, метрики, `exec`).
- **`6443`** (TCP): Исходящий от `kubelet` к API-серверу (Control Plane).
- **Порты CNI**: Зависят от плагина (например, 4789/UDP для VXLAN).

## Практические сценарии

### Пошаговый алгоритм диагностики

#### Шаг 1: Анализ через Control Plane

Начните с проверки состояния объекта Node в API:

```bash
# 1. Проверка статуса и времени последнего обновления
kubectl get nodes -o wide

# 2. Поиск событий (Events), связанных с узлом
kubectl describe node <node-name> | grep -A 20 Events
```
*Если статус `Unknown` — проверьте объект Lease в пространстве имён `kube-node-lease`.*

#### Шаг 2: Удалённая отладка (если доступен API-сервер)

Используйте `kubectl debug` для запуска отладочного контейнера на узле:

```bash
kubectl debug node/<node-name> -it --image=ubuntu:24.04
# Внутри контейнера доступна ФС узла через /host
```

#### Шаг 3: Локальная диагностика (SSH)

Если `kubectl debug` недоступен, подключитесь напрямую:

```bash
# 1. Проверка жизненно важных служб
systemctl status kubelet containerd

# 2. Анализ логов kubelet на наличие ошибок подключения к API или CRI
journalctl -u kubelet -n 100 --no-pager

# 3. Проверка сообщений ядра (OOM-killer, Hardware errors)
dmesg -T | grep -iE "oom|killed|error|fail"
```

#### Шаг 4: Проверка ресурсов и рантайма

```bash
# Проверка дискового пространства и лимитов PID
df -h
df -i
cat /proc/sys/kernel/pid_max

# Проверка работоспособности CRI (например, containerd)
crictl info
crictl ps
```

### Сопоставление симптомов и причин

| Симптом | Вероятная причина | Ссылка на руководство |
| :--- | :--- | :--- |
| `Ready=False`, `DiskPressure=True` | Заполнение системного диска | [Давление ресурсов](./resource_pressure.md) |
| `Ready=Unknown` | Потеря связи между Node и API Server | [Проблемы с сетью](./network_issues.md) |
| `Ready=NotReady` (Flapping) | Сбой PLEG, нехватка PID или нестабильная сеть | См. раздел ниже |
| Узел падает под нагрузкой | OOM-killer (системный) | [Проблемы Kubelet](./kubelet_issues.md) |

## Сценарий: "Мигающий" узел (Ready/NotReady Flapping)

Ситуация, при которой узел неоднократно переключается между состояниями `Ready` и `NotReady`, является критической, так как вызывает каскадные выселения (eviction) подов и нестабильность кластера.

### 1. Проверка журналов Kubelet
Первоочередное действие — анализ логов на самом узле:
```bash
journalctl -u kubelet -f
```
Ищите сообщения о невозможности отправить heartbeat серверу API или ошибки взаимодействия с CRI.

### 2. Проверка работоспособности PLEG
**PLEG (Pod Lifecycle Event Generator)** — механизм в kubelet, который синхронизирует состояние подов со средой выполнения контейнеров (CRI). 
- **Признак сбоя:** Сообщения в логах `PLEG is unhealthy` или `skipping pod lifecycle event`.
- **Причина:** Если PLEG неисправен, kubelet не может вовремя сообщить статус подов и самого узла, что приводит к переходу в `NotReady`. Часто это указывает на зависание рантайма (Docker/containerd).

### 3. Углубленная проверка системных ресурсов
Нехватка ресурсов может приводить к "замиранию" kubelet:
- **Память:** Проверьте `free -m`. Активен ли OOM-killer?
  ```bash
  dmesg | grep -i "killed process"
  ```
- **CPU:** Неконтролируемые процессы могут вызывать "голодание" kubelet. Проверьте `top` / `htop`.
- **Диск:** Проверьте `df -h`. Заполнение `/var/lib/kubelet` или корневой ФС блокирует работу агента.
- **PID:** Исчерпание идентификаторов процессов.
  ```bash
  sysctl kernel.pid_max
  ps -eLf | wc -l
  ```

### 4. Сетевое подключение к API Server
Периодическая потеря пакетов или проблемы с брандмауэром между узлом и Master-нодами.
```bash
# Базовая проверка доступности API изнутри узла
curl -k https://<api-server-ip>:<port>/healthz
```

**Реальный пример (Кейс из практики):**
Узел переходил в `NotReady` каждые несколько часов. Логи kubelet показали `PLEG is unhealthy`. Дальнейшее расследование выявило известную ошибку в версии Docker, связанную с обработкой большого количества проверок работоспособности контейнеров. Рантайм переставал отвечать, PLEG выходил из строя, и kubelet переставал отправлять пульс. 
**Решение:** Вывод узла из эксплуатации (drain), обновление Docker до исправленной версии и возврат в кластер.

### 5. Архитектурное влияние "хлопающего" узла

Проблема Flapping Node на уровне архитектуры кластера выходит за рамки недоступности одного сервера:

1.  **Нагрузка на Control Plane:** Каждое изменение статуса `Ready/NotReady` вызывает серию событий в API-сервере и записи в `etcd`. При массовом флапинге это может привести к деградации производительности всего Control Plane.
2.  **Каскадное выселение (Churn):** Когда узел становится `NotReady`, контроллер узлов (`node-controller`) через определенный таймаут (`pod-eviction-timeout`) начинает помечать поды для удаления и пересоздания. Если узел быстро возвращается в `Ready`, а затем снова падает, планировщик пытается вернуть поды обратно, создавая "цикл пересоздания" (churn), что ведет к простою сервисов.
3.  **Неэффективность планирования:** `kube-scheduler` видит узел в `Ready`, планирует туда нагрузку, но из-за нестабильности поды не могут запуститься, оставаясь в состоянии `ContainerCreating` или `Pending`.
4.  **Фрагментация ресурсов:** Постоянная ротация подов из-за флапинга мешает механизмам консолидации (например, в **[Karpenter](../../Autoscaling/Karpenter/overview.md)**), что ведет к неоптимальному использованию ресурсов и росту затрат.
