# Недоступность узла: Taints и выселение

## Основные определения

**Taints (отравления)** — механизм Kubernetes, позволяющий узлам «отталкивать» поды. В контексте недоступности узла, система автоматически накладывает на узел специфические taints с эффектом `NoExecute`, что служит сигналом для выселения подов.

**Toleration (терпимость)** — свойство пода, позволяющее ему игнорировать определенные taints узла и продолжать работу на нем даже при возникновении сбоев (например, временной потери связи).

**TolerationSeconds** — критический параметр в спецификации пода, определяющий задержку (в секундах) перед выселением пода с узла, имеющего эффект `NoExecute`.

Общие принципы работы механизмов описаны в разделе: [Taints и Tolerations: Управление размещением подов](../../../Scheduling/taints_and_tolerations.md).

## Основные концепции

### Автоматические Taints при сбоях (Taint-based Eviction)

Когда узел переходит в нездоровое состояние, контроллер узлов (`node-controller`) автоматически накладывает следующие taints:

| Taint | Состояние (Condition) | Эффект | Описание |
| :--- | :--- | :--- | :--- |
| **`node.kubernetes.io/unreachable`** | `Ready=Unknown` | `NoExecute` | Узел перестал отвечать на heartbeats (тайм-аут Lease). |
| **`node.kubernetes.io/not-ready`** | `Ready=False` | `NoExecute` | `kubelet` доступен, но сообщает о неготовности узла. |

### Жизненный цикл выселения (Eviction Timeline)

Процесс выселения при потере связи с узлом следует строгому графику:

1.  **Обнаружение (40с)**: Контроллер ждет время `node-monitor-grace-period` (дефолт 40с). Если обновлений нет, узел помечается как `Unknown`.
2.  **Маркировка**: На узел накладывается taint `unreachable:NoExecute` (или `not-ready`).
3.  **Ожидание (300с)**: Для каждого пода запускается индивидуальный таймер. Если в поде не указан `tolerationSeconds`, Kubernetes использует значение по умолчанию — **300 секунд** (5 минут).
4.  **Выселение**: По истечении таймера API-сервер удаляет объект Pod. Планировщик видит дефицит реплик и пытается пересоздать поды на других (здоровых) узлах.

## Практические сценарии

### Сценарий 1: Диагностика массового выселения

**Симптом**: Поды массово переходят в статус `Terminating` или исчезают с узла.

**Алгоритм проверки**:
1. Проверьте текущие taints узла:
   ```bash
   kubectl describe node <node-name> | grep -A 5 "Taints:"
   # → Taints: node.kubernetes.io/unreachable:NoExecute
   ```
2. Проверьте события контроллера выселения:
   ```bash
   kubectl get events -A --field-selector reason=TaintManagerEviction
   ```

### Сценарий 2: Блокировка выселения через PodDisruptionBudget (PDB)

**Симптом**: Время ожидания выселения истекло, но поды остаются на узле и не пересоздаются.

**Причина**: PDB запрещает удаление подов, так как это нарушит минимально допустимое количество работающих реплик.

**Решение**:
Проверьте разрешенные прерывания:
```bash
kubectl get pdb -A
# → DISRUPTIONS ALLOWED: 0 (означает блокировку выселения)
```
Для возобновления выселения необходимо либо увеличить количество реплик в Deployment, либо временно удалить/ослабить PDB.

### Сценарий 3: Принудительное удаление (Force Delete)

**Риск**: Принудительное удаление (`--force`) пода с недоступного узла может привести к **Data Corruption** или **Split-brain** для приложений с состоянием (StatefulSet).

**Рекомендация**: Используйте принудительное удаление только если вы физически уверены, что старый узел выключен или изолирован и старый процесс точно не пишет в хранилище.

```bash
kubectl delete pod <pod-name> --force --grace-period=0
```

### Сценарий 4: Настройка устойчивости приложения к сбоям сети

Для высокодоступных приложений рекомендуется увеличивать время ожидания, чтобы избежать ненужных переездов при кратковременных морганиях сети:

```yaml
spec:
  tolerations:
  - key: "node.kubernetes.io/unreachable"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 600 # ждать 10 минут
  - key: "node.kubernetes.io/not-ready"
    operator: "Exists"
    effect: "NoExecute"
    tolerationSeconds: 600
```
