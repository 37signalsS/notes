# Недоступность узла: Taints и выселение

## Определения

**Taints (отравления)** — механизм Kubernetes, позволяющий узлам «отталкивать» поды. При недоступности узла (`Ready=Unknown` или `Ready=False`) система автоматически накладывает на него специфические taints, инициирующие процесс выселения подов.

**Toleration (терпимость)** — свойство пода, позволяющее ему игнорировать определенные taints узла и продолжать работу на нем даже при неблагоприятных условиях.

**TolerationSeconds** — параметр в спецификации пода, определяющий, сколько времени под может оставаться на узле с эффектом `NoExecute` (например, при потере связи) до момента принудительного удаления.

Основные концепции управления размещением подов приведены в разделе: [Taints и Tolerations: Управление размещением подов](../../../Scheduling/taints_and_tolerations.md).

## Основные концепции

### Автоматические Taints при сбоях

При обнаружении проблем со связностью контроллер узлов (`node-controller`) накладывает на узел следующие ограничения с эффектом `NoExecute`:

| Taint | Состояние узла (Condition) | Описание |
| :--- | :--- | :--- |
| `node.kubernetes.io/unreachable` | `Ready=Unknown` | Узел не отвечает на проверки здоровья (timeout). |
| `node.kubernetes.io/not-ready` | `Ready=False` | Kubelet активен, но сообщает о неготовности узла. |

### Жизненный цикл выселения (Eviction Timeline)

Процесс удаления подов с недоступного узла проходит через фиксированные этапы:

1. **Обнаружение**: Узел не отвечает в течение времени `node-monitor-grace-period` (по умолчанию 40с).
2. **Маркировка**: Узел получает статус `Unknown`, накладывается taint `unreachable:NoExecute`.
3. **Ожидание**: Запускается таймер для каждого пода. Если в поде не настроены специфические tolerations, используется значение по умолчанию (обычно 300с).
4. **Выселение**: По истечении таймера (`tolerationSeconds`) поды удаляются из API и планировщик пытается пересоздать их на других узлах.

## Практические сценарии

### Сценарий 1: Диагностика причин выселения

Если поды массово покидают узел, необходимо проверить наличие и время наложения taints.

1. Проверьте текущие taints узла:

   ```bash
   kubectl describe node <node-name> | grep -A 5 "Taints:"
   ```

2. Проанализируйте события выселения для подтверждения причины:

   ```bash
   kubectl get events --field-selector reason=TaintManagerEviction --sort-by='.lastTimestamp'
   ```

### Сценарий 2: Блокировка выселения через PodDisruptionBudget (PDB)

**Симптом**: Узел недоступен, тайм-аут выселения истек, но поды остаются на узле и не пересоздаются.

**Причина**: PDB запрещает удаление подов, так как это приведет к падению количества доступных реплик ниже критического уровня.

**Диагностика**:

```bash
# Проверка разрешенных прерываний (Disruptions Allowed)
kubectl get pdb -A
```

Если значение `DISRUPTIONS ALLOWED` равно 0, контроллер выселения не сможет удалить под.

**Решение**: Временно увеличить количество реплик в Deployment или скорректировать параметры PDB для разрешения вылета.

### Сценарий 3: Принудительное удаление подов с вышедшего из строя узла

Если узел окончательно недоступен (например, аппаратный сбой), поды могут застрять в статусе `Terminating`, так как Kubelet не может подтвердить их удаление.

**Решение (с осторожностью)**:

```bash
kubectl delete pod <pod-name> --force --grace-period=0
```

> **Важно**: Для `StatefulSet` принудительное удаление может привести к конфликту записи (split-brain), если старый под на самом деле продолжает работать. Перед использованием `--force` убедитесь, что физический узел выключен.

### Сценарий 4: Настройка времени ожидания перед выселением

Если приложение критично к переездам или сеть в дата-центре нестабильна, можно увеличить время ожидания в спецификации пода:

```yaml
tolerations:
- key: "node.kubernetes.io/unreachable"
  operator: "Exists"
  effect: "NoExecute"
  tolerationSeconds: 600 # ждать 10 минут вместо 5
```
