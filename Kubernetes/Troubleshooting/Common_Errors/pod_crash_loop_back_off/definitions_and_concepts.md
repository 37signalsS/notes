# Состояние `CrashLoopBackOff` в Kubernetes: Определения и концепции

## Определения

**CrashLoopBackOff** — состояние Pod в Kubernetes, указывающее на то, что контейнер многократно запускается, падает и перезапускается с экспоненциальной задержкой. Это не ошибка сама по себе, а индикатор того, что контейнер не может успешно запуститься или стабильно работать.

**BackOff** — механизм экспоненциальной задержки между перезапусками. Kubernetes ожидает некоторое время перед следующей попыткой запуска, чтобы предотвратить перегрузку системы (Node) бесполезными попытками. Интервалы обычно составляют: 10s, 20s, 40s, 80s, ..., максимум 300s (5 минут).

## Основные концепции

### Причины возникновения CrashLoopBackOff

Контейнер переходит в это состояние, когда процесс внутри него завершается с ненулевым кодом или внезапно прерывается. Основные группы причин:

1. **Ошибка приложения** — баг в коде, необработанное исключение или паника.
2. **Неверная конфигурация** — отсутствие необходимых ConfigMap, Secret или переменных окружения.
3. **Проблемы с зависимостями** — недоступность базы данных, кэша или внешних API (Application Programming Interface).
4. **Недостаточно прав RBAC (Role-Based Access Control)** — приложение пытается взаимодействовать с Kubernetes API без соответствующих прав.
5. **Неудачная Liveness/Startup Probe** — проверка здоровья не проходит из-за слишком долгого старта или внутренней ошибки. Если startup time приложения больше `initialDelaySeconds × failureThreshold`, probe убивает контейнер до завершения инициализации. Решение: настроить `startupProbe` с достаточным `failureThreshold`, чтобы покрыть время прогрева.
6. **OOMKilled (Out Of Memory Killed)** — процесс потребляет больше памяти, чем установлено в лимитах (limits), и завершается ядром ОС.

### Архитектура цикла перезапуска

Процесс управления перезапусками выглядит следующим образом:

```text
┌─────────────────┐
│  Запуск         │
│  контейнера     │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Падение        │
│  контейнера     │
│  (Exit Code ≠0) │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Увеличение     │
│  Restart Count  │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Задержка       │
│  (BackOff)      │
│  (10s → 300s)   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Повторная      │
│  попытка        │
└─────────────────┘
```

### Коды завершения (Exit Codes)

Анализ кода завершения позволяет быстро сузить круг поиска проблемы:

| Код | Значение | Вероятная причина |
|-----|----------|-------------------|
| **0** | Success | Контейнер завершился штатно. Для долгоживущих сервисов — ошибка: пустой entrypoint или неправильный CMD |
| **1** | Error | Общая ошибка приложения, баг или ошибка конфигурации (stacktrace в логах) |
| **2** | Misuse | Ошибка использования shell/builtin-команды (синтаксис в bash-скрипте) |
| **125** | Docker run error | Ошибка запуска контейнера со стороны рантайма |
| **127** | Command not found | Указанная команда в ENTRYPOINT или CMD не найдена в образе |
| **137** | OOMKilled | Процесс убит за превышение лимитов памяти (SIGKILL). Решение: увеличить `limits.memory` или починить утечку |
| **139** | Segmentation Fault | Ошибка обращения к памяти (бинарный файл поврежден или баг) |
| **143** | Graceful Shutdown | Процесс завершился по SIGTERM — приложение не завершилось за `terminationGracePeriodSeconds` |

## Практические сценарии

### Базовая диагностика

Для определения причин `CrashLoopBackOff` используется стандартный набор инструментов:

1. **Просмотр статуса и событий:**

   ```bash
   kubectl describe pod <pod-name>
   ```

   Ищите раздел `Events` в конце вывода — там часто указаны ошибки монтирования томов или проблемы с планировщиком.

2. **Анализ логов предыдущего запуска:**

   ```bash
   kubectl logs <pod-name> --previous
   ```

   Флаг `--previous` (или `-p`) критически важен, так как обычный `kubectl logs` покажет пустоту или начало нового (падающего) цикла.

3. **Проверка событий Namespace:**

   ```bash
   kubectl get events --sort-by='.lastTimestamp'
   ```
