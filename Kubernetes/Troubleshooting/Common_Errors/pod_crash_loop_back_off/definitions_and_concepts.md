# Состояние `CrashLoopBackOff` в Kubernetes: Определения и концепции

## Определения

**CrashLoopBackOff** — состояние Pod в Kubernetes, указывающее на то, что контейнер многократно запускается, падает и перезапускается с экспоненциальной задержкой. Это не ошибка сама по себе, а защитный механизм (индикатор), сигнализирующий о неспособности контейнера выйти в стабильный режим работы.

**BackOff** — механизм экспоненциальной задержки между перезапусками. Kubernetes увеличивает время ожидания перед каждой следующей попыткой, чтобы предотвратить бесполезную трату ресурсов узла (CPU/IO) на запуск заведомо неисправного приложения.
- **Интервалы:** Обычно начинаются с 10s и удваиваются (20s, 40s, 80s...) до достижения максимума.
- **Максимальная задержка:** 300 секунд (5 минут).
- **Сброс счетчика:** Если контейнер успешно проработал более 10 минут, счетчик задержки сбрасывается.

## Основные концепции

### Причины возникновения CrashLoopBackOff

Контейнер переходит в это состояние, когда основной процесс (PID 1) завершается. Основные группы причин:

1. **Ошибка приложения** — баг в коде, необработанное исключение или паника.
2. **Неверная конфигурация** — отсутствие необходимых ConfigMap, Secret или опечатки в переменных окружения.
3. **Проблемы с зависимостями** — недоступность базы данных, кэша или внешних API на этапе инициализации.
4. **Недостаточно прав RBAC (Role-Based Access Control)** — приложение пытается взаимодействовать с Kubernetes API без соответствующих разрешений ServiceAccount.
5. **Неудачные пробы (Liveness/Startup Probes)** — проверка здоровья убивает контейнер, если он не отвечает вовремя.
   - *Важно:* Ошибка **Readiness Probe** НЕ вызывает `CrashLoopBackOff`, она лишь исключает под из трафика сервисов.
6. **OOMKilled (Out Of Memory Killed)** — процесс превышает лимит памяти (`limits.memory`) и убивается ядром ОС (Exit Code 137).

### Политика перезапуска (RestartPolicy)

Поведение `CrashLoopBackOff` напрямую зависит от поля `spec.restartPolicy` в манифесте Pod:

| Политика | Описание | Поведение при падении |
|:---------|:---------|:----------------------|
| **Always** (дефолт) | Перезапускать всегда. | Входит в цикл `CrashLoopBackOff`. |
| **OnFailure** | Перезапускать только при Exit Code ≠ 0. | Входит в цикл только при ошибках. |
| **Never** | Никогда не перезапускать. | Остается в статусе `Error` или `Completed`, в `CrashLoopBackOff` не переходит. |

### Архитектура цикла перезапуска

```text
┌─────────────────┐
│  Запуск         │
│  контейнера     │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Падение        │
│  контейнера     │
│  (Exit Code ≠0) │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Увеличение     │
│  Restart Count  │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Задержка       │
│  (BackOff)      │
│  (10s → 300s)   │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  Повторная      │
│  попытка        │
└─────────────────┘
```

### Коды завершения (Exit Codes)

| Код | Значение | Вероятная причина |
|:----|:---------|:------------------|
| **0** | Success | Контейнер завершился штатно. Для сервисов — это ошибка: процесс завершился слишком рано. |
| **1** | Error | Общая ошибка приложения (stacktrace в логах). |
| **2** | Misuse | Ошибка синтаксиса shell-команд или встроенных утилит. |
| **125** | Runtime Error | Ошибка запуска контейнера со стороны CRI (Container Runtime Interface). |
| **127** | Command not found | Утилита, указанная в `ENTRYPOINT` или `command`, не найдена в образе. |
| **128** | Invalid Argument | Некорректные параметры запуска (например, неверный UID пользователя). |
| **137** | OOMKilled / SIGKILL | Процесс убит за превышение лимитов памяти или по `kill -9`. |
| **139** | Segmentation Fault | Ошибка сегментации (обращение к защищенной памяти, баг в бинарном файле). |
| **143** | SIGTERM | Процесс завершился корректно по сигналу остановки, но не успел за `terminationGracePeriod`. |

## Практические сценарии

### Быстрая диагностика через CLI

Для определения причин `CrashLoopBackOff` используется стандартный набор команд с анализом их вывода:

1. **Проверка статуса и событий Pod:**

   ```bash
   kubectl describe pod <pod-name>
   ```

   # → Ищите в выводе:
   # State: Waiting / Reason: CrashLoopBackOff
   # Last State: Terminated / Reason: Error / Exit Code: 1
   # Events: Warning BackOff (Back-off restarting failed container)

2. **Анализ логов предыдущего запуска (критично):**

   ```bash
   kubectl logs <pod-name> --previous
   ```

   # → Позволяет увидеть лог падения, даже если текущий контейнер пуст или только запустился.

3. **Проверка событий Namespace (сортировка по времени):**

   ```bash
   kubectl get events --sort-by='.lastTimestamp'
   ```

   # → Помогает увидеть системные проблемы (OOM, сбои узла), затрагивающие несколько подов.
