# Поиск и устранение неисправностей: Диагностика CrashLoopBackOff

## Определения

**Диагностика CrashLoopBackOff** — систематический процесс выявления причин циклического перезапуска контейнеров в Kubernetes. Основная цель — локализовать проблему на одном из уровней: инфраструктура, конфигурация среды или логика самого приложения.

**Эфемерный контейнер (Ephemeral Container)** — временный контейнер, который запускается в существующем Pod для отладки. Это основной инструмент диагностики для образов без встроенного shell (distroless) или в случаях, когда основной контейнер падает слишком быстро.

Общие понятия и архитектура цикла перезапуска описаны в файле:
> **[Определения и концепции CrashLoopBackOff](./definitions_and_concepts.md)**

## Основные концепции диагностики

Для эффективного поиска причин рекомендуется следовать иерархии уровней анализа:

1. **Инфраструктурный уровень (Events):** Проверка событий кластера (ошибки планирования, монтирования томов, лимиты узла).
2. **Уровень состояния (Pod Status):** Анализ кодов завершения (`Exit Codes`) и причин остановки (`Reason`).
3. **Уровень приложения (Logs):** Изучение стандартного вывода приложения, включая предыдущие неудачные запуски.
4. **Уровень интроспекции (Interactive Debug):** Прямое взаимодействие с файловой системой и сетевым окружением пода через отладочные контейнеры.

## Практические сценарии

### Пошаговый алгоритм диагностики

#### Шаг 1: Анализ состояния и событий Pod

Первичный осмотр статуса и истории событий через `describe`. Обратите внимание на поле `Last State` для ранее завершенного контейнера.

```bash
kubectl describe pod <pod-name>
```

# → Результат: В секции `Last State` виден `Exit Code`. Код **1** обычно указывает на ошибку приложения, а код **137** означает, что контейнер был убит системой (например, OOMKilled). В секции `Events` могут быть сообщения о неудачных пробах (`Liveness probe failed`).

#### Шаг 2: Проверка Init-контейнеров

Если Pod завис в состоянии `Init:CrashLoopBackOff`, проблема заключается в подготовительных шагах (например, ожидание БД или миграции).

```bash
# Проверка логов конкретного init-контейнера
kubectl logs <pod-name> -c <init-container-name>
```

# → Результат: Сообщения об ошибках при миграции БД, отсутствии прав на запись в тома или недоступности внешних ресурсов.

#### Шаг 3: Просмотр логов предыдущей итерации

Критически важно смотреть логи именно *упавшей* инстанции, так как текущая может еще не успеть ничего записать до следующего падения.

```bash
# Просмотр логов предыдущего запуска
kubectl logs <pod-name> --previous
```

# → Результат: Стек вызовов (stack trace) приложения, ошибки инициализации фреймворка или сообщения о ненайденных конфигурационных файлах.

#### Шаг 4: Интерактивная отладка через эфемерные контейнеры (Modern Way)

Если приложение использует distroless-образ (без `sh`, `ls`, `curl`) или вы не хотите менять манифест пода, используйте `kubectl debug`.

```bash
# Запуск отладочного контейнера в сети и пространстве процессов целевого пода
kubectl debug -it <pod-name> --image=nicolaka/netshoot --target=<container-name>
```

# → Результат: Интерактивный доступ к сетевым утилитам внутри пода для проверки связи с БД или другими микросервисами.

#### Шаг 5: Отладка при мгновенном падении (`--copy-to`)

Если контейнер падает быстрее, чем вы успеваете подключиться, или `kubectl logs --previous` ничего не показывает (приложение падает до вывода в stdout), создайте его копию с измененной точкой входа.

```bash
# Создание копии пода с заменой команды запуска на shell
kubectl debug <pod-name> -it --copy-to=debug-pod --container=<app-container> -- sh
```

**Действия внутри отладочного пода:**
- **Проверка файлов конфигурации:** `ls -la /etc/config/` (поиск опечаток в путях монтирования).
- **Валидация переменных окружения:** `env | grep APP_` (проверка наличия Secret/ConfigMap данных).
- **Ручной запуск:** Попробуйте запустить бинарный файл приложения напрямую: `./app-binary --config=/etc/config/config.yaml`. Это позволит увидеть ошибку (например, `FileNotFound` или `Segmentation Fault`) прямо в терминале.

**Очистка:** Отладочный под является полноценным ресурсом и не удаляется автоматически. После завершения расследования удалите его: `kubectl delete pod debug-pod`.

#### Шаг 6: Проверка лимитов и ресурсов

Если в статусе указано `OOMKilled` (Exit Code 137), проверьте соответствие лимитов реальному потреблению. Изучите раздел `Last State` в `describe pod` — там часто фиксируется причина сбоя.

```bash
# Проверка лимитов и текущего потребления (требуется metrics-server)
kubectl top pod <pod-name>
```

# → Результат: Вывод потребления CPU и памяти. Если память достигла `limits.memory`, произойдет OOMKill.

## Дополнительная информация

### Краткая справка по кодам завершения

Подробный разбор кодов доступен в [Определениях](./definitions_and_concepts.md).

- **0:** Успех (для сервисов это часто означает, что процесс завершился слишком рано).
- **1:** Общая ошибка (проверить логи приложения).
- **137:** OOMKilled (увеличить лимиты памяти).
- **139:** Segmentation Fault (ошибка в бинарном файле или библиотеках).
- **143:** SIGTERM (приложение не завершилось вовремя и было убито).
