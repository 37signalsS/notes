# Состояние CrashLoopBackOff: Распространенные случаи и решения

## Определения

**Сценарии CrashLoopBackOff** — классифицированный набор типовых неисправностей, приводящих к циклическому перезапуску контейнеров, сгруппированный по точкам отказа (конфигурация, сеть, права доступа, ресурсы).

**Решения (Solutions)** — проверенные методы устранения корневых причин сбоев, включающие исправление манифестов, настройку инфраструктуры или корректировку логики запуска приложения.

Базовые концепции и системный алгоритм диагностики представлены в разделах:
- **[Определения и концепции](./definitions_and_concepts.md)**
- **[Диагностика и пошаговый чек-лист](./diagnostics.md)**

## Основные концепции

Эффективное устранение `CrashLoopBackOff` строится на принципе сопоставления симптомов (логи, события, коды завершения) с архитектурными слоями Kubernetes. Большинство проблем решается без изменения кода приложения путем корректировки среды выполнения (Environment) или управления зависимостями.

### Принципы исправления
1. **Изоляция:** Прежде чем менять код, убедитесь, что все внешние ресурсы (ConfigMap, Secret, БД) доступны.
2. **Идемпотентность запуска:** Приложение должно корректно обрабатывать повторные попытки старта.
3. **Безопасность:** Решение проблем с правами доступа должно следовать принципу наименьших привилегий (Least Privilege).

## Практические сценарии

### Сценарий 1: Отсутствующие или некорректные конфигурации (ConfigMap/Secret)

**Симптомы:**
- Exit Code: 1.
- Логи: `file not found`, `required environment variable missing`, `failed to load config`.

**Решение:**
1. Проверьте наличие ресурсов, на которые ссылается `Deployment`.
2. Если используется `envFrom`, убедитесь, что ConfigMap/Secret существует в том же namespace.

**Мини-кейс: Отсутствующий файл конфигурации (FileNotFound)**
Микросервис входит в `CrashLoopBackOff`.
- **Симптом:** `kubectl logs --previous` показывает ошибку `FileNotFound: /etc/config/config.yaml`.
- **Диагностика:** `kubectl get pod -o yaml` выявил опечатку в пути `volumeMounts` (вместо `/etc/config` было указано `/etc/conf`).
- **Решение:** Исправление пути в манифесте `Deployment`. После редеплоя контейнер успешно находит файл.

```bash
# Проверка наличия ресурса
kubectl get configmap app-config -n my-namespace
```
# → Результат: список параметров или ошибка `NotFound`.

3. Если ресурс существует, проверьте наличие в нем нужных ключей.

### Сценарий 2: Проблемы сетевой связности и зависимостей

**Симптомы:**
- Логи: `connection refused`, `timeout`, `dial tcp: lookup db-service: no such host`.

**Решение:**
1. **Использование Init-контейнеров:** Добавьте проверку доступности зависимости до старта основного приложения.

```yaml
initContainers:
- name: wait-for-db
  image: busybox:1.36
  command: ['sh', '-c', 'until nc -z db-service 5432; do echo waiting for db; sleep 2; done']
```
# → Результат: Под не перейдет к запуску основного контейнера, пока порт БД не станет доступен.

2. **Startup Probe:** Для приложений с долгой инициализацией настройте `startupProbe`, чтобы `livenessProbe` не убивала процесс раньше времени.

### Сценарий 3: Ошибки прав доступа к файловой системе

**Симптомы:**
- Exit Code: 1 или 13.
- Логи: `permission denied`, `cannot create directory`, `open /var/run/secrets/...: permission denied`.

**Решение:**
1. Проверьте контекст безопасности (`securityContext`). Если используется `readOnlyRootFilesystem: true`, приложению могут потребоваться тома `emptyDir` для временных файлов. Подробнее см. **[Security Context в Kubernetes](../../../Security/pod_security_context.md)**.
2. Настройте `fsGroup` или `runAsUser` для соответствия прав на томах.

```yaml
securityContext:
  runAsUser: 1000
  fsGroup: 2000
```
# → Результат: Kubernetes автоматически изменит владельца примонтированных томов на GID 2000.

### Сценарий 4: Некорректные параметры запуска (Entrypoint/Command)

**Симптомы:**
- Exit Code: 127 (`Command not found`) или 128 (`Invalid argument`).
- `kubectl describe` показывает ошибку запуска контейнера.

**Решение:**
1. Убедитесь, что путь к исполняемому файлу в `command` является абсолютным или файл находится в `$PATH`.
2. Если вы переопределяете `command`, помните, что это заменяет `ENTRYPOINT` образа, а `args` заменяет `CMD`.

```yaml
containers:
- name: app
  image: my-app:latest
  command: ["/usr/local/bin/app"]
  args: ["--config", "/etc/config/settings.yaml"]
```

### Сценарий 5: Ошибки прав доступа API (RBAC)

**Симптомы:**
- Логи: `Forbidden`, `user system:serviceaccount:... cannot get resource`.

**Решение:**
1. Проверьте права через `auth can-i`.

```bash
kubectl auth can-i list pods --as=system:serviceaccount:default:my-sa
```
# → Результат: `yes` или `no`.

2. Создайте или обновите `Role` и `RoleBinding` для соответствующего ServiceAccount.

### Сценарий 6: Ошибки монтирования и квот хранилищ

**Симптомы:**
- Состояние: `ContainerCreating` долго висит, затем переходит в `CrashLoopBackOff` (если приложение требует файл на томе).
- `kubectl describe pod` события: `FailedMount`, `Volume node mismatch`.

**Решение:**
1. Проверьте статус `PersistentVolumeClaim` (PVC).
2. Убедитесь, что `accessModes` (ReadWriteOnce/ReadWriteMany) соответствует количеству узлов, на которых запущены поды.

### Сценарий 7: Завершение штатного процесса (Batch Jobs в Deployments)

**Симптомы:**
- Exit Code: 0.
- Состояние: `Completed` → `CrashLoopBackOff`.

**Решение:**
Если приложение — это скрипт или миграция, которые должны выполниться один раз, используйте ресурс `Job` или `CronJob` вместо `Deployment`. `Deployment` всегда стремится поддерживать процесс запущенным.

### Сценарий 8: Недостаточно памяти (OOMKilled)

**Симптомы:**
- Reason: `OOMKilled`.
- Exit Code: 137.

**Мини-кейс: Java-приложение и жесткие лимиты**
Java-сервис постоянно перезапускается под нагрузкой.
- **Симптом:** `kubectl describe pod` показывает `Last State: Terminated`, `Reason: OOMKilled`, `Exit Code: 137`.
- **Диагностика:** Лимит памяти в манифесте установлен в `256Mi`, что недостаточно для Heap и Non-Heap памяти данной JVM под нагрузкой.
- **Решение:** Увеличение лимита до `1Gi` и настройка `-XX:MaxRAMPercentage=75.0` в переменных окружения.

Подробнее см. раздел **[Поды, завершенные из-за нехватки памяти (OOMKilled)](../oomkilled_pods.md)**.

## Дополнительная информация

### Чек-лист быстрого исправления
1. **Проверить логи:** `kubectl logs --previous` (90% ответов здесь).
2. **Проверить события:** `kubectl get events --sort-by=.lastTimestamp`.
3. **Проверить ресурсы:** Хватает ли `limits.memory` (не OOMKilled ли это?).
4. **Проверить зависимости:** Доступны ли БД и API.
