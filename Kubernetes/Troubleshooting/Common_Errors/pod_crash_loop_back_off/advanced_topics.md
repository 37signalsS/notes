# Продвинутые темы и лучшие практики: CrashLoopBackOff

## Определения

**Продвинутая диагностика CrashLoopBackOff** — применение глубоких методов анализа системных вызовов, сетевых политик и жизненного цикла контейнеров для решения скрытых проблем, которые не выявляются стандартными логами.

**Нативный Sidecar (Native Sidecar)** — контейнер, определенный в `initContainers` с полем `restartPolicy: Always` (доступно с K8s 1.29). Он гарантированно запускается до основного приложения и завершается последним, предотвращая ошибки связи на этапе старта (Race Conditions).

Базовые сведения и пошаговый алгоритм поиска неисправностей представлены в разделах:

## Основные концепции

### Иерархия причин и маскировка ошибок

`CrashLoopBackOff` часто является симптомом более глубоких сбоев. Важно различать первичные причины и их последствия:

| Состояние | Взаимосвязь с CrashLoopBackOff | Продвинутая диагностика |
|:----------|:-------------------------------|:------------------------|
| **OOMKilled** | Прямая причина (Exit Code 137). | Проверить `dmesg` на узле для выявления Node-level OOM (если лимиты пода не превышены). |
| **Race Condition** | Приложение падает, так как Sidecar (например, Istio-proxy) еще не готов. | Использовать Native Sidecars (K8s 1.29+) или `startupProbe` для прокси-контейнера. |
| **Zombie Process** | Контейнер "живет", но основные потоки умерли. | Настроить `livenessProbe` для мониторинга внутренних потоков или порта, а не только наличия процесса. |
| **SIGSEGV** | Ошибка сегментации (Exit Code 139). | Использовать eBPF-инструменты (Inspektor Gadget, Parca) для трассировки стека вызовов. |

### Поведение Cgroup v2 (Modern Kubernetes)

В современных дистрибутивах (GKE, EKS, последние версии Ubuntu) используется Cgroup v2. В отличие от v1, при превышении лимита памяти ядро убивает **всю группу** (весь контейнер целиком), что делает диагностику более предсказуемой:
- Если убит один поток — падает весь контейнер.
- Переход в `CrashLoopBackOff` происходит мгновенно, без "зависаний" приложения в полурабочем состоянии (Zombie).

## Практические сценарии

### Сценарий 1: Устранение Race Condition через Native Sidecar (K8s 1.29+)

Если приложение падает, потому что пытается подключиться к БД через Sidecar-прокси, который еще не успел инициализироваться, используйте механизм нативных sidecars.

```yaml
spec:
  initContainers:
  - name: istio-proxy
    image: istio/proxyv2:1.20.0
    restartPolicy: Always # Делает init-контейнер нативным sidecar'ом
    startupProbe:
      httpGet:
        path: /healthz/ready
        port: 15021
      failureThreshold: 30
      periodSeconds: 2
  containers:
  - name: main-app
    image: my-app:v1
    # Этот контейнер запустится ТОЛЬКО после того, как istio-proxy пройдет свою startupProbe
```

# → Результат: Приложение `main-app` гарантированно находит готовый сетевой прокси при старте, исключая ошибки подключения.

### Сценарий 2: Диагностика "молчаливых" падений через eBPF

Когда логи приложения пусты (`kubectl logs` возвращает пустоту), используйте **Inspektor Gadget** для отслеживания системных вызовов.

```bash
# Трассировка выполнения всех процессов в реальном времени
kubectl gadget trace exec -n my-app-namespace
```

# → Результат: Список всех попыток запуска процессов. Это позволяет увидеть, если приложение упало из-за отсутствующей библиотеки или ошибки прав доступа (`Permission Denied`) до того, как успело инициализировать систему логирования.

### Сценарий 3: Автоматизированный сбор Post-Mortem данных

Скрипт для извлечения расширенной информации о последнем сбое, включая проверку логов узла.

```bash
#!/bin/bash
# Сбор расширенных данных о падении Pod

POD_NAME=$1
NS=${2:-default}

echo "=== 1. Анализ состояния всех контейнеров ==="
kubectl get pod $POD_NAME -n $NS -o jsonpath='{range .status.containerStatuses[*]}{.name}: LastState={.lastState.terminated.reason}, ExitCode={.lastState.terminated.exitCode}{"\n"}{end}'

echo -e "\n=== 2. Проверка событий уровня узла (OOM) ==="
NODE_NAME=$(kubectl get pod $POD_NAME -n $NS -o jsonpath='{.spec.nodeName}')
kubectl debug node/$NODE_NAME -it --image=busybox --quiet -- chroot /host dmesg | grep -i "oom" | tail -n 3
```

# → Результат: Вывод кодов завершения для всех контейнеров (включая sidecars) и логов ядра узла для поиска скрытых OOM-киллов на уровне ОС.

## Дополнительная информация

### Рекомендации по настройке (Best Practices)

1.  **Startup Boost (CPU Bursting):** Если приложение (например, на Java) требует много CPU только при старте, установите `requests.cpu` ниже `limits.cpu`. Это позволит приложению использовать свободные ресурсы узла для быстрой инициализации, избегая перехода в `CrashLoopBackOff` по таймауту проб.
2.  **Continuous Profiling:** Для отладки утечек памяти или CPU, приводящих к падению через длительное время, интегрируйте инструменты профилирования (например, Pyroscope) через eBPF, чтобы данные не терялись при перезапуске контейнера.
3.  **Fail-Fast с информативностью:** При возникновении критических ошибок (неверный конфиг, отсутствие секрета) приложение должно завершаться немедленно с осмысленным кодом ошибки и сообщением в `stderr`.
4.  **Graceful Shutdown:** Всегда обрабатывайте сигнал `SIGTERM`. Убедитесь, что `terminationGracePeriodSeconds` достаточно велик для завершения текущих транзакций и корректного закрытия соединений.
