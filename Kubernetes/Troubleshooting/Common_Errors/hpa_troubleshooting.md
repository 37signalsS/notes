# Устранение неполадок HPA (Horizontal Pod Autoscaler)

## Определения

**HPA Troubleshooting** — процесс выявления и устранения сбоев в работе горизонтального автомасштабировщика подов. HPA работает как «петля управления» (Control Loop), и сбой обычно происходит в конвейере передачи метрик от приложения к контроллеру.

## Алгоритм диагностики

Когда HPA не масштабируется так, как ожидается, следуйте по шагам в указанном порядке:

### Шаг 1: Проверка объекта HPA
Это ваша отправная точка для поиска симптомов.
```bash
kubectl describe hpa <hpa-name>
```
**Критический признак:** Появление `<unknown>` в разделе использования метрик:
`Metrics: ( current / target ) <unknown> / 70%`

Это означает, что HPA не получает данные. Также проверьте раздел **Events** на наличие ошибок доступа или отсутствия метрик.

### Шаг 2: Проверка конвейера метрик
HPA получает данные из Metrics API, который обычно обслуживается компонентом `metrics-server`.
1. **Проверьте работоспособность metrics-server:**
   ```bash
   kubectl top pods
   ```
   * Если команда возвращает ошибку или пустые данные — `metrics-server` неисправен или не установлен. Это **основная причина** проблем с HPA по CPU/Memory.
2. **Проверьте логи metrics-server:** Убедитесь, что у него есть доступ к метрикам узлов (проблемы с сертификатами или сетевой связностью).

### Шаг 3: Проверка спецификации Pod (Resources Requests)
Это самая распространенная ошибка конфигурации.
- HPA рассчитывает процент использования на основе **базовой линии**, которой является `resources.requests`.
- **Если у контейнера не задан `requests.cpu` (или memory), HPA не сможет рассчитать процент утилизации и не будет масштабироваться.**

### Шаг 4: Проверка логики и емкости кластера
Если конвейер метрик исправен, но масштаб не меняется или поды не запускаются:
1. **Соответствие порогу**: Действительно ли текущий показатель превышает целевой? (Например, текущая загрузка 50% при цели 70% не вызовет масштабирования).
2. **Предел `maxReplicas`**: Проверьте, не достиг ли HPA своего верхнего лимита.
3. **Емкость узлов**: Проверьте события ReplicaSet. Если HPA инициировал создание подов, но они зависли в состоянии `Pending` — в кластере закончились свободные узлы. Это проблема **Cluster Autoscaler**, а не HPA.

## Практические сценарии

### Сценарий 1: HPA показывает <unknown>
- **Причина 1:** Не установлен `metrics-server`.
- **Причина 2:** У подов не заданы `requests`.
- **Причина 3:** Сетевые политики (Network Policies) блокируют доступ `kube-controller-manager` к Metrics API.

### Сценарий 2: Мини-кейс — HPA не масштабируется из-за отсутствия запросов
**Ситуация:** На сайте электронной коммерции настроен HPA (цель 70% CPU). Во время распродажи существующие поды перегружены, но новые не добавляются.
- **Диагностика:** `kubectl describe hpa` показывает статус метрики `<unknown> / 70%`. При этом `kubectl top pods` работает, подтверждая исправность `metrics-server`.
- **Причина:** В манифесте Deployment были указаны `limits` ресурсов, но отсутствовали `requests`. HPA не имел базовой линии для расчета процента использования.
- **Решение:** Добавление `resources.requests.cpu` в спецификацию контейнера. HPA немедленно начал считывать данные и отмасштабировал сервис.

## Дополнительная информация

### Совет для собеседования
**Вопрос:** Почему HPA может не масштабировать развертывание, даже если поды очень загружены?
**Ответ:** Я проверю три уровня:
1. **Данные:** Если `describe hpa` показывает `<unknown>`, значит сломан конвейер метрик (нет `metrics-server` или у подов отсутствуют `requests`).
2. **Конфигурация:** Возможно, лимит `maxReplicas` уже достигнут или текущая нагрузка еще не превысила заданный порог.
3. **Инфраструктура:** Если HPA отдал команду на создание подов, но они в `Pending` — проблема в нехватке физических ресурсов узлов (нужен Cluster Autoscaler).

### Схема конвейера данных HPA
`Pod (cAdvisor) → Kubelet → Metrics Server → Kubernetes Metrics API → HPA Controller`
