# Выселение подов: Классы QoS и работа Менеджера выселения

## Определения

**Менеджер выселения (Eviction Manager)** — внутренний модуль kubelet, который непрерывно отслеживает использование системных ресурсов на узле и принимает решение о принудительном завершении подов при достижении критических порогов (eviction thresholds).

**Класс QoS (Quality of Service — качество обслуживания)** — категория приоритетности пода, определяющая его "выживаемость" при дефиците ресурсов. Класс присваивается автоматически на основе указанных запросов (`requests`) и лимитов (`limits`).
Подробное описание: **[Управление ресурсами: QoS](../../../Scheduling/qos_limit_and_requests.md)**.

**Рабочий набор памяти (Working set memory)** — объем памяти (RSS + кэш, который нельзя освободить), используемый Менеджером выселения для оценки реального потребления.
Подробнее: **[Выселение по памяти: Расчет доступной памяти](./memory_eviction.md#расчет-доступной-памяти-в-kubelet)**.

**oom_score_adj** — параметр ядра Linux (от -1000 до 1000), через который kubelet сообщает системе, какие процессы следует убивать первыми при возникновении критической нехватки памяти (OOM).

## Основные концепции

### Очередность выселения по классам QoS

При нехватке памяти (`MemoryPressure`) или диска (`DiskPressure`) Менеджер выселения удаляет поды в следующем порядке:

1. **`BestEffort`** — выселяются первыми.
2. **`Burstable`** — выселяются вторыми, если превышают свои запросы (`requests`).
3. **`Guaranteed`** — выселяются в последнюю очередь.

| Класс QoS | `oom_score_adj` | Описание ресурсов | Очередность выселения | Защита от OOMKilled |
|:---|:---|:---|:---|:---|
| **`BestEffort`** | `1000` | `requests` и `limits` отсутствуют | Первая | Нет (убиваются первыми) |
| **`Burstable`** | `2` – `999` | `requests` < `limits` | Вторая | До уровня `limits` |
| **`Guaranteed`** | `-997` | `requests` == `limits` | Последняя | Максимальная защита |

> **Технический нюанс:** Процессы `kubelet` и рантайма (containerd/docker) имеют `oom_score_adj = -999`, что делает их практически неуязвимыми для системного OOM Killer.

### Ранжирование подов внутри одного класса

Если на узле много подов одного класса, kubelet использует следующие критерии для выбора цели:

#### Класс BestEffort

Поды сортируются по объему потребляемого рабочего набора памяти (`working set memory`).
* **Кандидат на выселение:** Под с наибольшим фактическим потреблением памяти. Kubelet считает такие поды "безбилетниками", использующими свободные ресурсы узла без гарантий.

#### Класс Burstable

Поды ранжируются на основе того, насколько их текущее потребление превышает заявленные запросы (`requests`).
* **Метрика:** `(Usage - Requests) / Capacity`.
* **Кандидат на выселение:** Под с наибольшим относительным превышением `requests`. Поды, которые потребляют **меньше** своих запросов, защищены от выселения до тех пор, пока на узле остаются нарушители (даже если их класс выше).

#### Класс Guaranteed

Выселяются крайне редко, обычно когда системные процессы требуют освобождения ресурсов и других подов не осталось. Ранжирование происходит по объему потребления (аналогично `BestEffort`).

### Алгоритм работы Менеджера выселения

1. **Мониторинг:** Kubelet проверяет состояние ресурсов (память, диск, PID) каждые 10 секунд по умолчанию.
2. **Триггер:** Ресурсы падают ниже жесткого порога (`evictionHard`).
3. **Сортировка:** Создается список кандидатов на основе QoS и формул превышения.
4. **Сигналы завершения:**
   - **Hard Eviction:** Поду отправляется `SIGKILL`. `terminationGracePeriodSeconds` игнорируется.
   - **Soft Eviction:** Поду отправляется `SIGTERM`. Дается время `min(pod_grace, eviction_max_grace)`.
5. **Цикл:** Kubelet ожидает освобождения ресурсов и повторяет процесс, если давление сохраняется.

### Время на завершение при выселении

При выселении kubelet может ограничивать время на остановку:

| Параметр | Описание | Значение |
|:---|:---|:---|
| `evictionMaxPodGracePeriod` | Лимит времени на завершение при выселении | 0s (Hard), до 120s (Soft) |
| `terminationGracePeriodSeconds` | Период завершения из спецификации пода | Обычно 30s |

## Практические сценарии

### Анализ причин выселения и QoS

1. **Проверка QoS-класса выселенного пода:**
   ```bash
   kubectl get pod <pod-name> -o jsonpath='{.status.qosClass}'
   # → Burstable
   ```

2. **Проверка oom_score_adj процесса на узле (через SSH):**
   ```bash
   # Поиск PID процесса контейнера и его веса в OOM
   cat /proc/<PID>/oom_score_adj
   # → 1000 (BestEffort) или -997 (Guaranteed)
   ```

3. **Анализ текущего потребления и лимитов:**
   ```bash
   kubectl top pod -n <namespace>
   # → NAME  CPU(cores)  MEMORY(bytes)
   # → app   150m        1200Mi (Requests: 512Mi, Limits: 2Gi)
   ```

### Настройка мягкого выселения (Soft Eviction)

Мягкое выселение позволяет приложениям корректно завершить работу и сбросить кэши.

```yaml
# /var/lib/kubelet/config.yaml
evictionHard:
  memory.available: "200Mi"
evictionSoft:
  memory.available: "500Mi"      # Начало процесса выселения
evictionSoftGracePeriod:
  memory.available: 2m           # Время на удержание порога перед убийством
evictionMaxPodGracePeriod: 60    # Максимальное время на SIGTERM
```

## Дополнительная информация

### Сравнение механизмов защиты

| Угроза | BestEffort | Burstable | Guaranteed |
|:---|:---|:---|:---|
| **Node Pressure Eviction** | Выселяются первыми | Вторые (при превышении requests) | Последние |
| **OOMKilled** | `oom_score_adj: 1000` | `oom_score_adj: 2-999` | `oom_score_adj: -997` |
| **Смена узла (drain)** | Соблюдение PDB | Соблюдение PDB | Соблюдение PDB |

### Рекомендации по выживанию подов

* **Минимизация BestEffort:** В продуктивной среде всегда указывайте `requests`. Без них планировщик считает, что под не потребляет ресурсов, что ведет к переуплотнению (overcommit) узла.
* **Балансировка Burstable:** Устанавливайте `requests` на уровне среднего потребления (p50/p90), чтобы под оставался защищенным при нормальной нагрузке.
* **Использование LimitRange:** Настройте лимиты по умолчанию в пространстве имен, чтобы предотвратить появление "неразмеченных" (BestEffort) подов.
