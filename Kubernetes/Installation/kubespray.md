# Kubespray

Kubespray — это проект с открытым исходным кодом, который объединяет **Ansible** и **kubeadm** для автоматизации процесса установки и управления жизненным циклом кластеров Kubernetes.

## Основная идея

В то время как `kubeadm` является инструментом **для инициализации отдельных узлов кластера**, Kubespray автоматизирует выполнение команд `kubeadm` на всех хостах (мастер- и рабочих узлах) с помощью Ansible-плейбуков. Это позволяет декларативно описывать состояние кластера и применять его к целевым серверам.

## Ключевые возможности

*   **Автоматизация:** Полностью автоматизированное развертывание, масштабирование и обновление кластеров.
*   **Гибкость:** Поддерживает большое количество операционных систем (Ubuntu, CentOS, и др.).
*   **Настраиваемость:** Позволяет легко настраивать компоненты кластера, включая:
    *   Сетевые плагины (CNI), такие как Calico, Cilium, Flannel.
    *   DNS-провайдеры (например, CoreDNS).
    *   Различные среды выполнения контейнеров.
*   **Отказоустойчивость (HA):** Встроенная поддержка для создания высокодоступных Control Plane.

## Недостатки и рекомендации

*   **Медленная скорость изменений:** Так как Kubespray основан на Ansible (Python) и использует большое количество ролей, любые изменения в конфигурации кластера могут занимать много времени.
*   **Установка дополнений:** Установку дополнительных компонентов (например, DNS) рекомендуется выполнять отдельно, а не в рамках Kubespray. Это связано с медленной скоростью работы и потенциальными ошибками, которые усложняют процесс обновления и отката.
*   **Обновления и масштабирование:** Kubespray предоставляет отдельные Ansible-плейбуки для добавления новых узлов и для обновления кластера. Однако следует помнить, что эти процессы также могут быть медленными.
*   **Основной файл конфигурации:** Центральным файлом для описания кластера является `cluster.yml`.

## Практическое руководство по установке

### Установка зависимостей

После клонирования директории `kubespray` необходимо установить зависимости.

1.  Найдите файл `requirements.txt`.
2.  Обновите `pip`:
    ```bash
    pip install --upgrade pip
    ```
3.  Установите зависимости:
    ```bash
    pip install -r requirements.txt
    ```

### Конфигурация Inventory

1.  Скопируйте пример inventory из `inventory/sample` в новую директорию, например, `inventory/my-cluster`.
    ```bash
    cp -rfp inventory/sample inventory/my-cluster
    ```
2.  Отредактируйте файл `inventory/my-cluster/inventory.ini`.

#### Пример inventory.ini

Для ингресса была создана отдельная группа `[kube_ingress]`, так как ее изначально не было. Kubespray использует имя этой группы для установки соответствующего label на узел. В примере также показано, как можно указать пользователя для SSH-подключения (`ansible_ssh_user`) и имя для участника etcd-кластера (`etcd_member_name`) прямо в строке хоста.

```ini
[all]
master-1.s000006.slurm.io ansible_host=172.22.193.2 ip=172.22.193.2 ansible_ssh_user=root etcd_member_name=etcd1
master-2.s000006.slurm.io ansible_host=172.22.193.3 ip=172.22.193.3 ansible_ssh_user=root etcd_member_name=etcd2
master-3.s000006.slurm.io ansible_host=172.22.193.4 ip=172.22.193.4 ansible_ssh_user=root etcd_member_name=etcd3
ingress-1.s000006.slurm.io ansible_host=172.22.193.5 ip=172.22.193.5 ansible_ssh_user=root
node-1.s000006.slurm.io ansible_host=172.22.193.6 ip=172.22.193.6 ansible_ssh_user=root
node-2.s000006.slurm.io ansible_host=172.22.193.7 ip=172.22.193.7 ansible_ssh_user=root

[kube_control_plane]
master-1.s000006.slurm.io
master-2.s000006.slurm.io
master-3.s000006.slurm.io

[etcd]
master-1.s000006.slurm.io
master-2.s000006.slurm.io
master-3.s000006.slurm.io

[kube_node]
node-1.s000006.slurm.io
node-2.s000006.slurm.io
ingress-1.s000006.slurm.io

[kube_ingress]
ingress-1.s000006.slurm.io

[k8s-cluster:children]
kube_control_plane
kube_node
```

### Конфигурация переменных (group_vars)

В Ansible переменные для групп хостов можно определять в каталоге `group_vars`.

*   **Для всех хостов:** Переменные, применяемые ко всем хостам из inventory, можно указать в файле `group_vars/all/all.yml`. Если переменных много, их можно разложить на несколько файлов в директории `group_vars/all/`.
*   **Для конкретной группы:** Для группы `etcd` переменные будут находиться в `group_vars/etcd.yml` или в каталоге `group_vars/etcd/`.

#### `group_vars/all/all.yml`
```yaml
# Позволяет kubelet подгружать необходимые модули ядра
kubelet_load_modules: true

# Отключает использование kubeadm (используется классический способ установки)
kubeadm_enabled: false

# Включает read-only порт (10255) для сбора метрик без авторизации
kube_read_only_port: 10255
```

#### `group_vars/all/docker.yml`
```yaml
# Устанавливает `overlay2` как драйвер хранилища для Docker
docker_storage_options: -s overlay2
```

#### `group_vars/all/download.yml`
```yaml
# Оптимизация загрузки: файлы и образы скачиваются один раз на один узел,
# а затем копируются на остальные узлы кластера.
download_run_once: true
```

#### `group_vars/etcd.yml`
```yaml
# Уменьшает количество записей в журнале операций, хранимых в памяти,
# для снижения потребления памяти etcd.
etcd_snapshot_count: "5000"

# Устанавливает приоритет I/O для etcd
etcd_ionice: '-c2 -n0'

# Лимит памяти для etcd (0 - без ограничений)
etcd_memory_limit: 0
```

#### `group_vars/k8s-cluster/k8s-cluster.yml`
В этом файле настраиваются ключевые параметры самого кластера Kubernetes.

```yaml
# Версия Kubernetes для установки
kube_version: v1.18.3

# Отключаем все методы аутентификации, оставляя только по токену
kube_oidc_auth: false
kube_basic_auth: false

# Сетевой CNI-плагин
kube_network_plugin: flannel
# Сеть для сервисов типа ClusterIP
kube_service_addresses: 10.100.0.0/16
# Сеть для подов
kube_pods_subnet: 10.0.0.0/16

# Отключаем небезопасный порт API-сервера
kube_apiserver_insecure_port: 0
# Режим работы kube-proxy
kube_proxy_mode: iptables
cluster_name: s000000.1local

# Копирование kubeconfig на локальную машину для управления кластером
kubeconfig_localhost: true
kubectl_localhost: true

# Включаем аутентификацию и авторизацию kubelet через вебхуки по токену
kubelet_authentication_token_webhook: true
kubelet_authorization_mode_webhook: true
```

#### `group_vars/k8s-cluster/k8s-net-flannel.yml`
Здесь содержатся настройки для сетевого плагина Flannel.

```yaml
# Указываем бэкенд для Flannel. host-gw - самый быстрый и простой режим,
# так как он создает статические маршруты между узлами в одной L2-сети.
flannel_backend_type: "host-gw"

# Указываем Flannel, на каком сетевом интерфейсе работать.
# Он выберет тот интерфейс, IP-адрес которого совпадет с регулярным выражением.
flannel_interface_regexp: '172\.21\.0\.\d{1,3}'
```

### Запуск развертывания

После того как все файлы конфигурации (`inventory.ini` и переменные в `group_vars`) подготовлены, можно запустить главный плейбук `cluster.yml` из корневой директории Kubespray. Этот файл обычно является "точкой входа", которая импортирует основной плейбук `playbooks/cluster.yml`.

Реалистичная команда для запуска выглядит следующим образом:

```bash
ansible-playbook cluster.yml \
  -i inventory/my-cluster/inventory.ini \
  -u myuser -b \
  --private-key=~/.ssh/id_rsa
```

Разберем команду:
*   `ansible-playbook cluster.yml`: Запускает выполнение плейбука.
*   `-i inventory/my-cluster/inventory.ini`: Указывает путь к вашему файлу инвентаря.
*   `-u myuser` или `--user=myuser`: Задает имя пользователя для SSH-подключения к узлам.
*   `-b` или `--become`: Указывает Ansible повысить привилегии (например, через `sudo`) для выполнения задач, требующих прав `root`.
*   `--private-key=~/.ssh/id_rsa`: Указывает путь к вашему приватному SSH-ключу для аутентификации на узлах.

Эта команда запустит процесс установки или обновления кластера в соответствии с вашими декларативными настройками.

## Проверка кластера после установки

Если в вашей конфигурации (например, в `group_vars/k8s-cluster/k8s-cluster.yml`) был установлен параметр `kubeconfig_localhost: true`, то Kubespray скопирует файл `admin.conf` на вашу локальную машину. Этот файл содержит учетные данные для доступа к кластеру с правами администратора.

1.  **Найдите файл kubeconfig:** Он будет находиться в директории `inventory/имя_вашего_кластера/artifacts/admin.conf`.

2.  **Выполните команду для проверки статуса узлов:** Используйте `kubectl`, указав путь к вашему файлу конфигурации.
    ```bash
    kubectl --kubeconfig=inventory/my-cluster/artifacts/admin.conf get nodes
    ```

3.  **Проанализируйте результат:** В выводе вы должны увидеть все узлы вашего кластера со статусом `Ready`.

4.  **(Опционально) Установите переменную окружения:** Чтобы не указывать флаг `--kubeconfig` каждый раз, можно экспортировать переменную окружения `KUBECONFIG`.
    ```bash
    export KUBECONFIG=$(pwd)/inventory/my-cluster/artifacts/admin.conf
    ```

## Управление кластером: Масштабирование

Kubespray предоставляет отдельные плейбуки для масштабирования кластера.

### Добавление Worker Node

1.  **Обновите inventory:** Добавьте новые узлы в ваш inventory-файл (например, `inventory/my-cluster/inventory.ini`) в группу `[kube_node]`.
2.  **Запустите плейбук `scale.yml`:** Этот плейбук добавит новые рабочие узлы в существующий кластер.
    ```bash
    ansible-playbook -i inventory/my-cluster/inventory.ini scale.yml
    ```

### Добавление Master Node (Control Plane)

Процесс добавления нового master-узла более сложный и требует переконфигурации кластера.

1.  **Обновите inventory:** Добавьте новые master-узлы в inventory-файл в группы `[kube_control_plane]` и `[etcd]`.
2.  **Запустите плейбук `cluster.yml`:** В отличие от добавления worker-ов, для добавления master-узлов используется основной плейбук `cluster.yml`, который применяет новую конфигурацию ко всему кластеру.
    ```bash
    ansible-playbook -i inventory/my-cluster/inventory.ini cluster.yml
    ```

## Управление кластером: Обновление

### Проверка доступной версии для обновления

Перед обновлением необходимо выяснить, до какой максимальной версии Kubernetes может быть обновлен кластер с вашей текущей версией Kubespray. Эта информация содержится в файле с контрольными суммами компонентов.

1.  Перейдите в директорию роли `download`:
    ```bash
    cd roles/download/defaults
    ```
2.  Откройте файл `main.yml` и найдите переменную `kubelet_checksums`. В ней перечислены все доступные для скачивания версии.
    ```bash
    cat main.yml | grep kubelet_checksums
    ```

Обновление версии Kubernetes в кластере, развернутом с помощью Kubespray, выполняется с помощью плейбука `upgrade-cluster.yml`.

### Процесс обновления

1.  **Измените версию:** В конфигурационном файле (например, `group_vars/k8s-cluster/k8s-cluster.yml`) укажите новую целевую версию Kubernetes в переменной `kube_version`.
    ```yaml
    kube_version: v1.19.0
    ```
2.  **Запустите плейбук `upgrade-cluster.yml`:** Из корневой директории Kubespray выполните команду:
    ```bash
    ansible-playbook -i inventory/my-cluster/inventory.ini upgrade-cluster.yml
    ```
    > **Важное замечание:** В отличие от `cluster.yml`, плейбук `upgrade-cluster.yml` выполняет задачи последовательно на каждом узле, а не параллельно. Это обеспечивает более безопасный и контролируемый процесс обновления.

### Проверка после обновления

После завершения работы плейбука `upgrade-cluster.yml`, необходимо убедиться, что все компоненты кластера успешно обновились.

1.  **Проверка версии API Server:** Команда `kubectl version` покажет версию сервера, которая должна соответствовать целевой.
    ```bash
    kubectl version
    ```
2.  **Проверка версии `kubelet` на узлах:** `kubectl get nodes` покажет версии всех worker-нод.
    ```bash
    kubectl get nodes
    ```
3.  **Проверка версий компонентов Control Plane:** Образы и версии ключевых компонентов (`kube-apiserver`, `kube-scheduler` и т.д.) можно проверить через `describe` их подов в пространстве имен `kube-system`.
    ```bash
    kubectl describe pod <pod-name> -n kube-system
    ```
    В выводе команды нужно смотреть на версию используемого образа (`Image`).

### Возможные проблемы и важные моменты

При обновлении кластера могут возникнуть следующие сложности, которые требуют внимания:

*   **Правило одной минорной версии:** Обновлять кластер можно только последовательно, на одну минорную версию за раз (например, с `1.27` на `1.28`). Пропуск версий (например, с `1.27` сразу на `1.29`) не поддерживается и может привести к несовместимости API и потере данных.
*   **Устаревшие API и манифесты:** В новых версиях Kubernetes могут быть удалены или изменены API. Перед обновлением необходимо проверить манифесты ваших приложений на использование устаревших `apiVersion`.
*   **Изменение опций компонентов:** Параметры запуска компонентов Control Plane (например, `kube-apiserver`) или ключи запуска могут измениться. Kubespray обычно обрабатывает это, но кастомные конфигурации могут потребовать ручной корректировки.
*   **Обновление среды выполнения контейнеров:** Обновление Kubernetes может потребовать или повлечь за собой обновление среды выполнения (например, Docker, containerd), что может вызвать проблемы совместимости.
*   **Проверка `release notes`:** Перед любым обновлением критически важно изучить официальные `release notes` для новой версии Kubernetes, чтобы быть в курсе всех значительных изменений.

## Системные поды после установки

После успешной установки кластера с помощью Kubespray в пространстве имен `kube-system` будут развернуты следующие основные системные поды. Их состав может незначительно меняться в зависимости от выбранной конфигурации (например, от CNI-плагина).

Более подробно о стандартных пространствах имен и о том, как Kubespray их использует, можно прочитать в документе [о пространствах имен](./base/namespace.md#namespaces-и-kubespray).

На примере стандартной установки можно увидеть следующие компоненты:

*   **Control Plane компоненты (Static Pods):**
    *   `kube-apiserver-*`: API-сервер Kubernetes, главная точка входа для управления кластером.
    *   `kube-controller-manager-*`: Менеджер контроллеров, который следит за состоянием кластера (например, за репликами, узлами).
    *   `kube-scheduler-*`: Планировщик, который распределяет поды по узлам кластера.

*   **Сетевые компоненты:**
    *   `kube-flannel-*`: Поды сетевого плагина Flannel, который обеспечивает оверлейную сеть для коммуникации между подами.
    *   `kube-proxy-*`: Компонент, который управляет сетевыми правилами на каждом узле, обеспечивая маршрутизацию трафика к сервисам.

*   **DNS и сервисы:**
    *   `coredns-*`: Основной DNS-сервер кластера, отвечающий за разрешение имен сервисов.
    *   `dns-autoscaler`: Автоматически масштабирует количество подов CoreDNS в зависимости от нагрузки.
    *   `nodelocaldns-*`: Кэширующий DNS-агент на каждом узле для повышения производительности и надежности DNS-запросов.

*   **Дополнительные компоненты (Addons):**
    *   `kubernetes-dashboard-*`: Веб-интерфейс для управления кластером.
    *   `kubernetes-metrics-scraper-*`: Сборщик метрик для Kubernetes Dashboard.
    *   `nginx-proxy-ingress-*`: Ingress-контроллер на базе Nginx для управления внешним доступом к сервисам кластера.

## Выделенные ноды для Ingress в Kubespray

Это практический пример конфигурации из `group_vars` в Kubespray для создания выделенных нод под Ingress-контроллер. Этот подход использует связку меток, `taints` и `tolerations` для изоляции Ingress-подов.

Подробное теоретическое объяснение этого механизма можно найти в документе:
*   **[Taints and Tolerations](./base/taints_and_tolerations.md)**

### `group_vars/k8s-cluster/addons.yml`

В этом файле настраиваются параметры для дополнительных компонентов кластера, включая Nginx Ingress.

```yaml
# Параметры для дополнительного ПО
ingress_nginx_enabled: true
ingress_nginx_host_network: true # Прокидывает сетевой неймспейс узла внутрь контейнера
ingress_nginx_configmap: # Настройки ConfigMap для Ingress-контроллера
  server-tokens: "false" # Не показывать версию Nginx
  proxy-body-size: "2048m" # Максимальный размер тела запроса
  proxy-buffer-size: "16k" # Размер буфера для прокси
  worker-shutdown-timeout: "180s" # Таймаут для graceful shutdown воркеров
ingress_nginx_nodeselector:
  node-role.kubernetes.io/ingress: "" # Запускать поды только на нодах с этой меткой
ingress_nginx_tolerations: # Позволяет подам запускаться на "отравленных" нодах
- key: "node-role.kubernetes.io/ingress"
  operator: "Exists"
  effect: "NoSchedule"
```

### `group_vars/all/kube-ingress.yml`

Этот файл определяет, какие метки (`node_labels`) и `taints` (`node_taints`) будут применены к нодам, входящим в группу `kube_ingress` в `inventory`.

```yaml
# На ноды из группы 'kube_ingress' будет установлена соответствующая метка
node_labels:
  node-role.kubernetes.io/ingress: ""

# На эти же ноды будет добавлено "отравление" (taint)
node_taints:
  - "node-role.kubernetes.io/ingress:NoSchedule"
```

Этот пример демонстрирует, как `taint` `NoSchedule` в сочетании с `toleration` гарантирует, что только поды Ingress-контроллера будут размещены на выделенных для них нодах, в то время как другие поды не смогут на них попасть.

## Конфигурация MetalLB (Load Balancer)

**MetalLB** — это реализация балансировщика нагрузки для bare-metal кластеров Kubernetes. В облачных средах (AWS, GCP, Azure) сервисы типа `LoadBalancer` автоматически получают внешний IP-адрес от облачного провайдера. В локальных средах такой функциональности нет. MetalLB решает эту проблему, позволяя назначать внешние IP-адреса из заранее определенного пула.

### `group_vars/k8s-cluster/addons.yml`

Конфигурация MetalLB, как и других дополнений, обычно находится в файле `addons.yml`.

```yaml
# Включаем MetalLB
metallb_enabled: true
metallb_speaker_enabled: true

# Определяем пулы IP-адресов, которые MetalLB будет использовать
metallb_config:
  address_pools:
    primary:
      ip_range:
        - "5.75.169.149/32"
        - "91.99.78.20/32"
      # auto_assign: false # Можно отключить автоматическое назначение адресов для этого пула
```

*   `metallb_enabled: true`: Включает установку MetalLB.
*   `metallb_speaker_enabled: true`: Включает компонент `speaker`, который отвечает за анонсирование IP-адресов по протоколам L2 (ARP) или BGP.
*   `metallb_config`: Содержит конфигурацию пулов адресов. В данном примере определен один пул `primary` с двумя IP-адресами, которые могут быть назначены сервисам типа `LoadBalancer`.
