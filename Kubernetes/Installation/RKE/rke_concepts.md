# RKE: Основные концепции

> [!WARNING]
> **RKE1 достиг конца жизненного цикла (EOL) 31 июля 2025 года.** 
> Поддержка прекращена, основное внимание Rancher Labs полностью переключено на **RKE2**. Эксплуатация допускается только для существующих сред с обязательным планом миграции.

## Определения

**RKE (Rancher Kubernetes Engine)** — это Docker-ориентированный дистрибутив Kubernetes. Ключевая особенность заключается в том, что все компоненты управления (control plane) и рабочие компоненты (kubelet, proxy) запускаются как обычные Docker-контейнеры.

**rke-tools** — вспомогательный образ контейнера, используемый RKE для выполнения системных операций на узлах (подготовка конфигураций, ротация сертификатов, создание снимков etcd).

**cluster.rkestate** — файл состояния кластера в формате JSON. Содержит полную копию `cluster.yml`, сгенерированные сертификаты и ключи. Без этого файла обновление или модификация кластера через RKE CLI невозможны.

## Базовые концепции

### Архитектурные принципы

RKE работает по принципу "инфраструктура как код", где конечное состояние кластера описывается в YAML.
* **Зависимость от Docker:** RKE требует наличия установленного Docker Engine на всех узлах. Утилита взаимодействует с Docker через сокет `/var/run/docker.sock`.
* **Управление через SSH:** RKE CLI подключается к узлам по SSH, проверяет версию Docker и запускает необходимые контейнеры компонентов.
* **Статические сертификаты:** RKE самостоятельно генерирует все необходимые TLS-сертификаты для внутренних коммуникаций и сохраняет их в файле состояния.

### Сравнение RKE с другими дистрибутивами

| Аспект | RKE (RKE1) | RKE2 (Next Gen) | kubeadm |
| :--- | :--- | :--- | :--- |
| **Среда выполнения (Runtime)** | Docker | containerd | Любой CRI (containerd/CRI-O) |
| **Метод запуска** | Docker-контейнеры | Системные сервисы + статические поды | Статические поды (Static Pods) |
| **Конфигурация** | Один файл `cluster.yml` | Конфиг-файлы + CLI флаги | CLI флаги + ConfigMaps |
| **Управление узлами** | SSH доступ от имени RKE CLI | Локальный запуск на узле | Локальный запуск `kubeadm join` |
| **Безопасность** | Базовая | Высокая (CIS Hardened по умолчанию) | Зависит от пользователя |

### Роли узлов (Node Roles)

В RKE узел может совмещать несколько ролей:
1. **etcd:** Хранилище состояния. Требуется нечетное количество (1, 3, 5).
2. **controlplane:** Запуск API Server, Scheduler, Controller Manager.
3. **worker:** Запуск пользовательских нагрузок (Kubelet, Proxy).

### Сетевое взаимодействие (CNI)

RKE поддерживает несколько плагинов, которые разворачиваются как Kubernetes-ресурсы сразу после запуска Control Plane:
* **Canal:** Гибрид Flannel (для VXLAN сети) и Calico (для сетевых политик). Самый популярный выбор.
* **Flannel:** Простая L3-сеть, не поддерживает сетевые политики.
* **Calico:** Полноценная поддержка политик и BGP.
* **Weave:** Поддержка шифрования трафика "из коробки".

### Системные аддоны (Add-ons)

RKE автоматически управляет жизненным циклом критических компонентов внутри кластера:
* **Ingress:** По умолчанию устанавливается Nginx Ingress Controller в режиме HostNetwork.
* **DNS:** CoreDNS (в старых версиях KubeDNS).
* **Metrics Server:** Для работы HPA (Horizontal Pod Autoscaler).

## Практические сценарии

### Структура конфигурации (cluster.yml)

Основной файл содержит следующие ключевые блоки:
```yaml
nodes:
  - address: 192.168.1.10
    user: ubuntu
    role: [controlplane, etcd]
    ssh_key_path: ~/.ssh/id_rsa

services:
  etcd:
    snapshot: true
    creation: 6h
    retention: 24h

network:
  plugin: canal

authentication:
  strategy: x509
```

### Безопасность и управление доступом

* **X.509:** Основной метод аутентификации между компонентами.
* **RBAC:** Включен по умолчанию. Все права доступа внутри кластера управляются через RoleBinding и ClusterRoleBinding.
* **SSH-туннелирование:** RKE использует SSH-туннели для безопасного развертывания компонентов, что минимизирует количество открытых портов на узлах.

## Дополнительная информация

### Жизненный цикл и стратегия миграции

С 2025 года RKE1 считается устаревшим. В 2026 году эксплуатация допускается только в режиме "поддержки до миграции".
**Шаги миграции на RKE2:**
1. **Подготовка:** Создание нового кластера RKE2 параллельно существующему.
2. **Сетевая связность:** Настройка маршрутизации или использование общих балансировщиков.
3. **Перенос данных:** Использование Velero или Rancher Backup для миграции объектов и томов (PV).
4. **Очистка:** После успешного переключения трафика, старый кластер RKE1 удаляется командой `rke remove`.
