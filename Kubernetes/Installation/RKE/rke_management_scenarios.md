# RKE: Управление и поиск неисправностей

> [!WARNING]
> **RKE1 достиг конца жизненного цикла (EOL) 31 июля 2025 года.** 
> Поддержка прекращена, основное внимание Rancher Labs полностью переключено на **RKE2**. Используйте данный раздел исключительно для поддержки существующих Legacy-кластеров.

## Определения

**RKE CLI** — утилита командной строки, предназначенная для развертывания, обновления и обслуживания кластеров RKE1. Работает по принципу "запуск из любого места", так как не требует локальной установки Kubernetes на узлах.

**cluster.rkestate** — критически важный файл состояния кластера. Содержит полную копию конфигурации, данные сертификатов и текущее состояние ресурсов. При потере этого файла управление кластером через RKE CLI становится невозможным.

**Ротация сертификатов** — процедура обновления TLS-сертификатов всех системных компонентов Kubernetes. RKE управляет этим процессом централизованно через SSH.

**Снимок (Snapshot) etcd** — полная резервная копия базы данных etcd, включая все секреты, конфигурации и состояние объектов Kubernetes.

## Базовые концепции

### Инструментарий управления

*   **RKE CLI**: Основной инструмент для "Day 0" (установка) и "Day 2" (обслуживание вне Rancher). Все команды выполняются относительно файла конфигурации `cluster.yml`.
*   **Rancher UI**: Если кластер импортирован в Rancher, большинство операций (бэкапы, ротация) доступны через веб-интерфейс, который под капотом вызывает RKE CLI.
*   **SSH-доступ**: RKE требует беспарольный доступ по SSH к каждому узлу от имени пользователя с правами запуска Docker (обычно член группы `docker`).

### Жизненный цикл конфигурации

Любое действие в RKE следует циклу:
1.  Правка `cluster.yml`.
2.  Запуск `rke up`.
3.  Проверка `cluster.rkestate` (обновляется автоматически).
4.  Проверка доступности API через `kubectl`.

## Практические сценарии

### Установка RKE CLI

Для управления кластером необходимо использовать последнюю стабильную версию утилиты.

```bash
# Скачивание версии v1.8.14 (последняя стабильная версия для RKE1)
curl -L https://github.com/rancher/rke/releases/download/v1.8.14/rke_linux-amd64 -o rke

# Установка прав и перемещение в системный PATH
chmod +x rke
sudo mv rke /usr/local/bin/

# Проверка корректности установки
rke --version
# → rke version v1.8.14
```

### Масштабирование: Добавление и удаление узлов

RKE не поддерживает автоматическое масштабирование. Все операции выполняются вручную.

**Добавление узла:**
1. Подготовьте новый узел (установите Docker, настройте SSH).
2. Добавьте описание узла в секцию `nodes` файла `cluster.yml`.
3. Запустите обновление:
   ```bash
   rke up --config cluster.yml
   ```

**Удаление узла:**
1. Удалите описание узла из `cluster.yml`.
2. Запустите обновление:
   ```bash
   rke up --config cluster.yml
   # RKE остановит контейнеры на удаленном узле и перенастроит кластер.
   ```

### Обновление версии Kubernetes

Поскольку RKE1 находится в режиме EOL, новые версии выпускаются редко и только для закрытия критических уязвимостей.

```yaml
# В файле cluster.yml
kubernetes_version: "v1.28.10-rancher1-1"
```

При запуске `rke up` процесс обновления происходит последовательно:
1. Обновление компонентов на etcd-узлах.
2. Обновление controlplane-узлов.
3. Поочередное обновление worker-узлов (Rolling Update).

### Резервное копирование и восстановление etcd

**Создание снимка:**
Снимки сохраняются на всех узлах с ролью `etcd` в директории `/opt/rke/etcd-snapshots/`.

```bash
rke etcd snapshot-save --name backup-$(date +%F) --config cluster.yml
# → INFO[0000] Sending image [rancher/rke-tools:v0.1.99] to nodes
# → INFO[0015] Finished saving snapshot [backup-2026-08-07] on all etcd nodes
```

**Восстановление из снимка:**
Процесс требует перезапуска всех компонентов кластера.

```bash
rke etcd snapshot-restore --name backup-2026-08-07 --config cluster.yml
# → INFO[0000] Restoring snapshot [backup-2026-08-07]
# → INFO[0045] Finished restoring snapshot successfully
```

### Поиск и устранение неисправностей

**Проблема: x509: certificate has expired**
Если сертификаты истекли, кластер перестает принимать команды `kubectl`.

```bash
# Принудительная ротация всех сертификатов
rke cert rotate --config cluster.yml

# Ротация только для конкретного сервиса (например, kubelet)
rke cert rotate --service kubelet --config cluster.yml
```

**Диагностика через логи контейнеров:**
Если API-сервер недоступен, проверяйте логи напрямую на узлах через Docker.

```bash
# Проверка состояния компонентов
docker ps --filter name=kube-apiserver
docker ps --filter name=etcd

# Просмотр логов etcd при ошибках кворума
docker logs etcd 2>&1 | grep -i "error"

# Проверка логов kubelet на worker-узлах
docker logs kubelet
```

**Проблема: Расхождение состояния (State Mismatch)**
Если `rke up` завершается с ошибкой о несоответствии данных:
1. Проверьте, что в директории присутствует актуальный `cluster.rkestate`.
2. Если файл поврежден, но кластер работает, попробуйте `rke up` — RKE попытается восстановить состояние из работающих контейнеров (если это возможно).

## Дополнительная информация

### Состав файлов состояния

*   **cluster.yml**: Ваши намерения (желаемое состояние).
*   **cluster.rkestate**: Текущая реальность кластера (сертификаты, ключи, версии). **Никогда не удаляйте этот файл.**
*   **kube_config_cluster.yml**: Ваш пропуск в кластер. Содержит сертификат администратора.

### Важные ограничения RKE1
*   **Docker Only**: Не поддерживает containerd напрямую (только через Docker).
*   **SSH Latency**: При плохом соединении между машиной с RKE CLI и узлами возможны таймауты при развертывании.
