# RKE: Управление и поиск неисправностей

> [!WARNING]
> **RKE1 достигает конца жизненного цикла (EOL) 31 июля 2025 года.** 
> Основное внимание Rancher Labs переключено на **RKE2**. Рекомендуется использовать данный раздел для поддержки существующих кластеров и планирования миграции.

## Определения

**RKE CLI** — утилита командной строки для развертывания, обновления и управления жизненным циклом кластеров RKE1.

**cluster.rkestate** — файл состояния кластера, содержащий сертификаты и текущую конфигурацию. Необходим для выполнения любых операций обновления или восстановления.

**Ротация сертификатов** — процесс генерации новых TLS-сертификатов для внутренних компонентов Kubernetes (apiserver, etcd, kubelet) до истечения срока их действия.

**Снимок (Snapshot) etcd** — резервная копия базы данных etcd, содержащая все объекты и состояние кластера.

## Базовые концепции

### Инструментарий управления

*   **RKE CLI**: Основной инструмент для "Day 0" (установка) и "Day 2" (обслуживание вне Rancher).
*   **Rancher UI**: Рекомендуется для визуального управления, настройки автоматических бэкапов и ротации сертификатов через веб-интерфейс.
*   **kubectl**: Используется для управления ресурсами внутри кластера (нагрузки, сервисы) после завершения установки.

### Безопасность и сертификаты

По умолчанию RKE выпускает сертификаты сроком на 1 год. 
*   **Автоматизация**: Rancher UI может автоматически обновлять сертификаты до истечения срока.
*   **Ручное управление**: Если кластер развернут только через RKE CLI, ротацию необходимо запускать вручную.
*   **Риски**: Истечение сертификатов приводит к остановке API-сервера и невозможности управления кластером через `kubectl`.

## Практические сценарии

### Установка RKE CLI

Для управления кластером необходимо установить актуальную версию бинарного файла.

```bash
# Скачивание версии v1.8.14 (актуальная стабильная версия RKE1)
curl -L https://github.com/rancher/rke/releases/download/v1.8.14/rke_linux-amd64 -o rke

# Установка прав и перемещение в PATH
chmod +x rke
sudo mv rke /usr/local/bin/

# Проверка установки
rke --version
# → rke version v1.8.14
```

### Жизненный цикл кластера

**Развертывание и обновление:**
Любые изменения в `cluster.yml` (добавление узлов, смена версии Kubernetes, изменение CNI) применяются одной командой:

```bash
rke up --config cluster.yml
# → INFO[0000] Initiating Kubernetes cluster
# → ...
# → INFO[0120] Finished building Kubernetes cluster successfully
```

**Удаление кластера:**
Команда удаляет контейнеры компонентов и очищает конфигурацию с узлов.
```bash
rke remove --config cluster.yml
```

### Резервное копирование и восстановление etcd

**Создание снимка вручную:**
Снимки сохраняются на всех узлах с ролью `etcd` в директории `/opt/rke/etcd-snapshots/`.

```bash
rke etcd snapshot-save --name manual-backup-$(date +%F) --config cluster.yml
# → INFO[0000] Sending image [rancher/rke-tools:v0.1.99] to nodes
# → INFO[0015] Finished saving snapshot [manual-backup-2026-07-22] on all etcd nodes
```

**Восстановление из снимка:**
ВНИМАНИЕ: Восстановление etcd является деструктивной операцией и перезаписывает текущее состояние кластера.

```bash
rke etcd snapshot-restore --name manual-backup-2026-07-22 --config cluster.yml
# → INFO[0000] Restoring snapshot [manual-backup-2026-07-22]
# → INFO[0045] Finished restoring snapshot successfully
```

### Поиск и устранение неисправностей

**Проблема: Истечение сертификатов (x509: certificate has expired)**
Если `kubectl` перестал отвечать, выполните принудительную ротацию:

```bash
# Ротация всех сертификатов
rke cert rotate --config cluster.yml

# Ротация конкретного компонента (например, только API Server)
rke cert rotate --service kube-apiserver --config cluster.yml
```

**Проблема: API-сервер недоступен**
1. Проверьте доступность порта 6443:
   ```bash
   nc -zv <control-plane-ip> 6443
   # → Connection to 192.168.1.10 6443 port [tcp/https] succeeded!
   ```
2. Если порт закрыт, проверьте логи контейнера на узле Control Plane:
   ```bash
   docker ps -a | grep kube-apiserver
   docker logs kube-apiserver
   ```

**Проблема: Ошибки доступа в логах (Unauthorized / Forbidden)**
Часто связано с расхождением данных в `cluster.yml` и файлом состояния `cluster.rkestate`. Убедитесь, что оба файла актуальны и находятся в одной директории при запуске `rke up`.

## Дополнительная информация

**Важность файлов состояния:**
*   **cluster.rkestate**: Содержит приватные ключи сертификатов. Если этот файл потерян, вы не сможете обновить кластер через `rke up` без полной переустановки или сложного восстановления сертификатов из работающих контейнеров.
*   **kube_config_cluster.yml**: Содержит данные для доступа администратора. Рекомендуется хранить его в защищенном хранилище секретов.
