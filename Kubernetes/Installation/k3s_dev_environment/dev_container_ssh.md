# Создание Dev-контейнера с SSH

Руководство по созданию изолированного рабочего пространства внутри кластера K3s. Контейнер предоставляет доступ по протоколу SSH и персистентную домашнюю директорию, используется для удаленной разработки непосредственно в кластере.

Контекст: Часть серии по созданию dev-окружения в K3s. Развертывание через Helm описано в [Развертывание Dev-контейнера с помощью Helm](./dev_container_helm_deployment.md). Предварительно требуется [вспомогательный образ kubeutils](./kubeutils_image.md).

---

## Определения

| Термин | Описание |
|--------|----------|
| **Dev-контейнер** | Изолированное рабочее пространство в кластере Kubernetes с доступом по SSH и персистентной домашней директорией |
| **Init Script** | Скрипт инициализации (`ENTRYPOINT`), выполняемый при старте контейнера. Динамически создает пользователя, настраивает права и запускает SSH-демон |
| **SSO-аутентификация** | В данном контексте — аутентификация (Single Sign-On) по SSH-ключам без пароля. Подробнее см. [SSH Аутентификация](../../../Linux/Security/ssh/server/ssh_authentication.md) |

## Основные концепции

### Архитектура решения

Dev-контейнер представляет собой образ на базе актуальной LTS-версии Ubuntu (24.04) с SSH-сервером и набором базовых утилит.

Компоненты:

1. **Базовый образ:** `ubuntu:24.04` — стандарт де-факто для сред разработки, обеспечивающий максимальную совместимость с SDK.
2. **SSH-сервер:** `openssh-server` — настроен на доступ исключительно по ключам.
3. **Утилиты:** `sudo`, `git`, `curl` — минимальный набор; остальные инструменты разработчик устанавливает сам в свою персистентную директорию.
4. **Скрипт инициализации:** Связывает жизненный цикл пода с UID/GID хостовой системы для бесшовной работы с томами.

Принцип работы:

```text
┌─────────────────────────────────────────────────────────┐
│                    Pod: dev-container                   │
├─────────────────────────────────────────────────────────┤
│  ┌─────────────────┐      ┌──────────────────────────┐  │
│  │ init-container.sh ──→  │ sshd (foreground)        │  │
│  │ (создание юзера)│      │ рабочая среда bash       │  │
│  └─────────────────┘      └──────────────────────────┘  │
│                            │                            │
│                            ↓                            │
│                   ┌─────────────────┐                   │
│                   │ hostPath Volume │ ←── K3s Node      │
│                   │ /home/<user>    │     filesystem    │
│                   └─────────────────┘                   │
└─────────────────────────────────────────────────────────┘
                              │
                              ↓ SSH (NodePort / Ingress TCP)
                    ┌─────────────────┐
                    │  Developer IDE  │
                    │  (VS Code SSH)  │
                    └─────────────────┘
```

### Преимущества и риски

Размещение среды разработки прямо в кластере кардинально меняет рабочий процесс.

| Аспект | Традиционная ВМ | Dev-контейнер в K3s |
|--------|-----------------|---------------------|
| **Изоляция** | Общая среда на команду, риск конфликтов | Строгая контейнерная изоляция |
| **Воспроизводимость** | Зависит от Ansible/Chef | Гарантируется Docker-образом |
| **Масштабирование** | Ручное выделение ресурсов | Квоты CPU/RAM средствами K8s |
| **Безопасность среды**| Легко скомпрометировать весь хост | Компрометация ограничена namespace'ом |

Ограничения архитектуры:
- **Риски hostPath:** Монтирование локальных директорий узла требует строгого контроля UID/GID. Если злоумышленник получит root в контейнере, он может записать вредоносные файлы на узел.
- **Сетевой доступ:** Необходимость проброса SSH наружу (через NodePort, LoadBalancer или TCP-роутинг Ingress) увеличивает поверхность атаки.
- **Запуск от root:** Для работы демона `sshd` в стандартной конфигурации контейнер должен стартовать от пользователя `root`.

### Механика Init-скрипта

Скрипт решает критическую проблему монтирования томов в Kubernetes: несовпадение прав. Если `hostPath` на узле принадлежит UID 1000, а пользователь в образе имеет UID 1001, возникнет ошибка `Permission denied`.

Логика `init-container.sh`:
1. Чтение желаемых UID/GID из переменных среды (переданных через ConfigMap или Pod Spec).
2. Динамическое создание системной группы и пользователя с точным совпадением ID.
3. Выдача пользователю прав `sudo` без пароля (так как это dev-среда).
4. Импорт корпоративных корневых сертификатов (если применимо).
5. Запуск SSH-демона процессом с PID 1, чтобы под корректно обрабатывал сигналы завершения.

## Практические сценарии

### Dockerfile для Dev-контейнера

Файл оптимизирован для Ubuntu 24.04.

```dockerfile
FROM ubuntu:24.04

# Отключение интерактивных запросов apt
ENV DEBIAN_FRONTEND=noninteractive

# Установка SSH-сервера и базовых утилит
RUN apt-get update && apt-get install -y --no-install-recommends \
    openssh-server \
    sudo \
    git \
    curl \
    ca-certificates \
    && rm -rf /var/lib/apt/lists/*

# Директория, необходимая для запуска sshd в Ubuntu
RUN mkdir -p /run/sshd && chmod 0755 /run/sshd

# Копирование скрипта инициализации
COPY init-container.sh /usr/local/bin/init-container.sh
RUN chmod +x /usr/local/bin/init-container.sh

# Экспорт порта SSH
EXPOSE 22

# Скрипт инициализации выступает точкой входа
ENTRYPOINT ["/usr/local/bin/init-container.sh"]
```

Best practices:
- `DEBIAN_FRONTEND=noninteractive` предотвращает зависание сборки на запросах конфигурации (например, при настройке часовых поясов).
- Каталог `/run/sshd` критически важен: без него `sshd` в Ubuntu завершается с ошибкой `Missing privilege separation directory`.
- Скрипт помещен в `/usr/local/bin/` согласно иерархии FHS.

### Скрипт инициализации (`init-container.sh`)

Обратите внимание на использование команд `groupadd` и `useradd`, специфичных для систем на базе Debian/Ubuntu.

```bash
#!/bin/bash
set -e

# Переменные окружения с дефолтными значениями
USER_NAME=${DEV_USER_NAME:-developer}
GROUP_NAME=${DEV_GROUP_NAME:-developer}
USER_ID=${DEV_USER_ID:-1000}
GROUP_ID=${DEV_GROUP_ID:-1000}

# Создание группы (если она еще не существует)
if ! getent group "${GROUP_NAME}" > /dev/null 2>&1; then
    groupadd -g "${GROUP_ID}" "${GROUP_NAME}"
fi

# Создание пользователя
if ! id -u "${USER_NAME}" > /dev/null 2>&1; then
    useradd -u "${USER_ID}" -g "${GROUP_ID}" -s /bin/bash -m "${USER_NAME}"
    # Отключаем пароль для пользователя (разрешен только вход по ключу)
    passwd -d "${USER_NAME}"
fi

# Настройка sudo без пароля
echo "${USER_NAME} ALL=(ALL) NOPASSWD: ALL" > "/etc/sudoers.d/${USER_NAME}"
chmod 0440 "/etc/sudoers.d/${USER_NAME}"

# Импорт дополнительных CA-сертификатов (например, для Harbor)
CA_CERT_PATH="/etc/ssl/certs/custom-ca.crt"
if [ -f "$CA_CERT_PATH" ]; then
    cp "$CA_CERT_PATH" /usr/local/share/ca-certificates/
    update-ca-certificates > /dev/null 2>&1
fi

# Запуск SSH-демона в foreground-режиме
# Ключ -D: не отсоединяться от консоли
# Ключ -e: выводить логи в стандартный поток ошибок (stderr) для Docker/K8s логов
exec /usr/sbin/sshd -D -e
```

### Локальное тестирование образа

Перед деплоем в Kubernetes образ следует протестировать локально:

```bash
# 1. Сборка
docker build -t dev-container:local .

# 2. Подготовка локальной директории для hostPath
mkdir -p ~/dev-home
chmod 700 ~/dev-home

# 3. Запуск с эмуляцией переменных K8s
docker run -d \
  -p 2222:22 \
  -e DEV_USER_NAME=testuser \
  -e DEV_USER_ID=$(id -u) \
  -e DEV_GROUP_ID=$(id -g) \
  -v ~/dev-home:/home/testuser \
  --name dev-test \
  dev-container:local

# 4. Проверка логов (sshd должен стартовать без ошибок)
docker logs dev-test

# 5. Генерация ключа и копирование (если еще не сделано)
# ssh-copy-id -p 2222 testuser@localhost

# 6. Вход в контейнер
ssh -p 2222 testuser@localhost
```

### Предупреждения по безопасности

| Аспект | Риск | Решение |
|--------|------|---------|
| **SSH-демон от Root** | Запуск `sshd` требует прав root внутри контейнера | Используйте AppArmor/Seccomp профили для ограничения системных вызовов |
| **hostPath** | Побег из контейнера (Container Escape) | Не монтируйте системные директории (например, `/`, `/var/run`, `/etc`). Только директории данных проекта |
| **sudo без пароля** | Если ключ утек, злоумышленник получает root в контейнере | Настройте ротацию SSH-ключей. В идеале — используйте сертификаты SSH вместо ключей |

### Современные альтернативы

Хотя метод с SSH-контейнером эффективен, существуют более управляемые Cloud-Native альтернативы:

1. **DevSpace / Skaffold:** Утилиты CLI, которые синхронизируют локальный код с контейнером в Kubernetes "на лету" без необходимости поднимать SSH-сервер.
2. **Eclipse Che / Gitpod:** Полноценные платформы для оркестрации рабочих сред в Kubernetes (Workspace-as-a-Service).
3. **KubeVirt / vCluster:** Выделение изолированного виртуального кластера K8s каждому разработчику.
