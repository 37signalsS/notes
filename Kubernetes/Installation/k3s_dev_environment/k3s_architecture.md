# Архитектура Dev-окружения на K3s

Обзор архитектуры самодостаточной лаборатории для изучения практик DevOps на базе легковесного дистрибутива Kubernetes K3s. Все вспомогательные сервисы (CI/CD, реестр, GitOps) запускаются внутри кластера.

Контекст: Этот файл описывает общую архитектуру. Детали реализации см. в [Создание Dev-контейнера с SSH](./dev_container_ssh.md), [Развертывание через Helm](./dev_container_helm_deployment.md), [Интеграция GitLab с Harbor](./gitlab_harbor_integration.md).

## Определения

| Термин | Описание |
|--------|----------|
| **K3s Dev Environment** | Самодостаточная лаборатория для изучения DevOps-практик на базе одного сервера с K3s. Все сервисы (GitLab, Harbor, ArgoCD) запускаются внутри кластера |
| **Dev-контейнер** | Изолированное рабочее пространство в кластере с доступом по протоколу SSH и персистентной домашней директорией через `hostPath` |
| **Local Path Provisioner** | Встроенный в K3s провизионер для динамического выделения хранилища на локальных дисках узла. Поддерживает режим доступа RWO (ReadWriteOnce) |
| **Kine** | Абстрактный слой в K3s, позволяющий использовать SQLite, PostgreSQL или MySQL вместо etcd |
| **ServiceLB** | Встроенный в K3s балансировщик нагрузки (ранее Klipper LB), использующий порты хоста для экспонирования сервисов типа LoadBalancer |

## Основные концепции

### Архитектура решения

В основе — один сервер (физический или виртуальный) под управлением Linux с установленным **K3s**. Вся инфраструктура "Dev-as-Code" развернута внутри этого кластера.

Основные компоненты:

| Компонент | Назначение | Технология |
|-----------|------------|------------|
| **Оркестратор** | Легковесная реализация Kubernetes | K3s (v1.36.2+) |
| **Ingress Controller** | Маршрутизация внешнего трафика (HTTP/HTTPS) | NGINX (выбран для совместимости с prod-стандартами) |
| **Хранилище** | Динамическое выделение локальных томов | Local Path Provisioner |
| **CI/CD платформа** | Хранение кода и выполнение пайплайнов | GitLab (v19.2+) |
| **Реестр артефактов** | Хранение Docker-образов и Helm-чартов | Harbor (v2.15.2+) |
| **GitOps оператор** | Декларативное управление состоянием кластера | ArgoCD |
| **Объектное хранилище** | S3-совместимое хранилище для артефактов и бэкапов | Minio |
| **Базы данных** | Реляционная СУБД для внутренних нужд | PostgreSQL |

### Преимущества K3s для dev-окружения

K3s идеально подходит для локальных лабораторий и edge-сценариев благодаря следующим особенностям:

1. **Минимальное потребление ресурсов:** Весь Control Plane упакован в один бинарный файл, потребляющий от 512 МБ RAM.
2. **Встроенная база данных:** Использование SQLite через прослойку Kine избавляет от необходимости администрирования тяжелого кластера etcd на одном узле.
3. **Готовность "из коробки":** Включает в себя Flannel (CNI), CoreDNS, Metrics Server и Local Path Provisioner.
4. **Автоматизация манифестов:** Директория `/var/lib/rancher/k3s/server/manifests/` позволяет автоматически применять YAML-файлы при старте.

### Сравнение K3s и MicroK8s

Оба решения популярны, но имеют разную философию.

| Характеристика | K3s | MicroK8s |
|:---------------|:----|:---------|
| **Метод поставки** | Один бинарный файл | Snap-пакет |
| **Хранение состояния** | SQLite (по умолчанию), etcd, MySQL/Postgres | DQLite (распределенный SQLite) |
| **Потребление RAM (idle)** | ~512 МБ | 2–4 ГБ |
| **Сетевой плагин (CNI)** | Flannel (по умолчанию), поддержка Cilium/Calico | Calico (по умолчанию) |
| **Управление аддонами** | Через HelmChart CRD или автодеплой | Встроенная команда `microk8s enable` |
| **Архитектура** | Один процесс для Control Plane | Раздельные процессы systemd |

Вывод: K3s остается приоритетным выбором для систем с ограниченными ресурсами (Raspberry Pi, дешевые VPS) и сценариев, где важна простота установки одним скриптом.

### Концепция Dev-контейнера

Ключевая идея данной архитектуры — перенос рабочего окружения разработчика в кластер.

Процесс работы:
1. **Изоляция:** Разработчик подключается по SSH не к хосту, а в конкретный под (Pod) в Kubernetes.
2. **Инструментарий:** В образе под-контейнера уже предустановлены все необходимые SDK, линтеры и CLI-утилиты.
3. **Персистентность:** Домашняя директория разработчика монтируется через `hostPath` или `Local PV`, сохраняя настройки IDE и кэши инструментов между перезапусками.
4. **Тонкий клиент:** Локально используется только VS Code с расширением Remote-SSH.

Преимущества:
- Мгновенный онбординг (окружение готово за секунды через Helm).
- Отсутствие "мусора" на локальной машине.
- Идентичность среды разработки и среды исполнения (K8s).

## Практические сценарии

### Последовательность развертывания лаборатории

1. **Подготовка ОС:** Установка необходимых зависимостей (curl, iptables) на чистый сервер.
2. **Инсталляция K3s:** Запуск с отключенным Traefik (`--disable traefik`), если планируется использование NGINX.
3. **Настройка Ingress:** Установка NGINX Ingress Controller для управления внешними доменными именами.
4. **Развертывание инфраструктуры:** Установка Harbor, GitLab и ArgoCD через Helm-чарты.
5. **Интеграция компонентов:** Настройка доверенных сертификатов и связей между GitLab и Harbor.
6. **Запуск рабочего места:** Развертывание персонального `dev-container` для разработчика.

### Ограничения и риски локального хранилища

Использование **Local Path Provisioner** и **hostPath** в dev-окружении удобно, но накладывает ограничения:
- **Отсутствие репликации:** При выходе из строя диска или узла данные будут потеряны.
- **Привязка к узлу:** В многоузловом кластере под должен запускаться на том же узле, где созданы его данные (node affinity).
- **Безопасность hostPath:** Контейнер имеет доступ к части файловой системы хоста. Это допустимо для разработки, но категорически запрещено в Production без использования PSP (Pod Security Policies) или Admission Controllers.

### Масштабирование (High Availability)

Хотя данное руководство ориентировано на один узел, K3s поддерживает полноценный HA режим:
- **Embedded etcd:** Позволяет создать кластер из 3-х и более master-узлов без внешней БД.
- **External DB:** Подключение внешнего кластера PostgreSQL/MySQL через Kine для хранения состояния Control Plane.
- **DSR (Direct Server Return):** Оптимизация трафика через ServiceLB.

При переходе к HA рекомендуется заменить Local Path Provisioner на реплицируемое хранилище, такое как **Longhorn**.
