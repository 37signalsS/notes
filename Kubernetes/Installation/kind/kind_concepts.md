# kind — определения и концепции

## Определения

**kind (Kubernetes IN Docker)** — инструмент для запуска локальных кластеров Kubernetes, где каждый узел кластера запускается как Docker-контейнер. Предназначен для тестирования Kubernetes, локальной разработки и CI/CD (Continuous Integration / Continuous Deployment).

**kindest/node** — официальный Docker-образ узла kind. Представляет собой полноценную среду, содержащую `systemd`, `containerd`, `kubelet` и другие компоненты Kubernetes, необходимые для работы узла.

**Узел kind** — изолированный Docker-контейнер, выполняющий роль control-plane или worker-узла кластера Kubernetes.

**kindnet** — легковесный CNI (Container Network Interface) плагин по умолчанию, встроенный в kind. Обеспечивает базовую маршрутизацию Pod-to-Pod внутри кластера.

## Основные концепции

### Архитектура kind и внутреннее устройство узла

Вопреки популярному заблуждению, kind не использует Docker-in-Docker в чистом виде для запуска контейнеров (Pods) внутри узлов. Начиная с версии Kubernetes 1.24, встроенная поддержка Docker (DockerShim) была удалена, и kind использует `containerd`. 

Архитектура одного узла (контейнера `kindest/node`) выглядит следующим образом:
1.  **Init-система:** Внутри Docker-контейнера узла запускается `systemd` как процесс с PID 1.
2.  **Container Runtime:** `systemd` управляет демоном `containerd`, который отвечает за непосредственный запуск пользовательских контейнеров (Pods).
3.  **Kubelet:** Также управляется через `systemd` и взаимодействует с `containerd` через протокол CRI (Container Runtime Interface).
4.  **Изоляция сетей:** Каждый созданный кластер kind по умолчанию создает собственную bridge-сеть на уровне Docker хоста (сеть `kind`). Взаимодействие между узлами (контейнерами Docker) происходит внутри этой сети.
5.  **Хранилище (Storage):** kind поставляется со встроенным провижинером `local-path-provisioner` (создающим StorageClass `standard`), который динамически выделяет директории внутри узла для запрашиваемых PVC (PersistentVolumeClaim).

| Компонент | Описание |
| :--- | :--- |
| **Узел как контейнер** | Каждый узел (control-plane, worker) — изолированный Docker-контейнер с `systemd`, `containerd` и `kubelet`. |
| **Среда выполнения (Runtime)** | Хостовая система использует Docker или Podman для запуска узлов, а внутри узлов работает `containerd` для запуска Pod'ов. |
| **Изоляция сетей** | Каждый кластер создает собственную сеть на уровне хоста для изоляции трафика узлов. |

### Поддержка альтернативных Provider (Podman, Rootless)

kind поддерживает работу не только поверх классического Docker-демона, работающего от пользователя root, но и:
-   **Rootless Docker:** Запуск узлов в пространстве обычного пользователя для повышения безопасности.
-   **Podman:** Использование Podman вместо Docker (включается через переменную окружения `KIND_EXPERIMENTAL_PROVIDER=podman`). Это позволяет запускать локальные кластеры в окружениях без демона (daemonless) и с повышенным уровнем изоляции.

### Преимущества и ограничения

| Преимущества | Ограничения |
| :--- | :--- |
| **Скорость:** Быстрое создание и удаление кластеров (от десятков секунд до пары минут). | **Не для Production:** Инструмент предназначен исключительно для тестирования и разработки. |
| **Топология:** Поддержка сложных multi-node и HA (High Availability) кластеров локально. | **Производительность I/O:** Ограниченная производительность дисковой подсистемы из-за вложенности файловых систем. |
| **CI/CD:** Идеально подходит для интеграционных тестов в пайплайнах (на GitHub Actions, GitLab CI). | **Зависимости:** Требует установленного Docker или Podman на хост-машине. |
| **Декларативность:** Конфигурация топологии и параметров узлов осуществляется через YAML-файлы. | **Сетевые ограничения:** Прямой доступ к сервисам NodePort извне требует ручного проброса портов (Port Mapping) при создании кластера. |

### Сравнение с локальными аналогами

| Инструмент | Назначение | Отличие от kind |
| :--- | :--- | :--- |
| **[minikube](../minikube/minikube_concepts.md)** | Локальная разработка | Запускает полноценную VM (в зависимости от драйвера), имеет множество встроенных аддонов, по умолчанию создает однонодовый кластер. |
| **k3d** | Локальная разработка / IoT | Запускает k3s (сильно облегченный дистрибутив Kubernetes от Rancher) в контейнерах. Менее требователен к ресурсам, но отличается от "ванильного" K8s. |
| **[talosctl](../local_cluster_with_talosctl.md)** | Локальная разработка | Использует иммутабельную операционную систему Talos Linux, безопаснее, максимально приближен к production-практикам развертывания Talos, но сложнее в изучении и отладке. |

## Практические сценарии

### Поддерживаемые версии Kubernetes

kind следует политике поддержки N-2 (три последние минорные версии Kubernetes). Актуальные статусы на середину 2026 года:

| Версия Kubernetes | Статус | EOL (End of Life) |
| :--- | :--- | :--- |
| **1.36** | Активная поддержка | Апрель 2027 |
| **1.35** | Активная поддержка | Декабрь 2026 |
| **1.34** | Активная поддержка | Август 2026 |
| **1.33** | Достигла EOL | Апрель 2026 |

**Использование конкретной версии:**

Версия Kubernetes в кластере kind жестко определяется тегом используемого Docker-образа `kindest/node`.

```yaml
# Пример фиксации версии Kubernetes
nodes:
- role: control-plane
  image: kindest/node:v1.36.0
```

> **Примечание:** Актуальные теги образов для свежих релизов всегда публикуются на [странице релизов kind в GitHub](https://github.com/kubernetes-sigs/kind/releases). Использование устаревших образов совместно с новыми версиями `kind` CLI может привести к ошибкам запуска.

### Ключевые переменные окружения

| Переменная | Описание |
| :--- | :--- |
| `KIND_EXPERIMENTAL_PROVIDER` | Позволяет переопределить среду выполнения на хосте. Значение `podman` указывает kind использовать Podman вместо Docker. |
| `KIND_EXPERIMENTAL_DOCKER_NETWORK` | Задает пользовательское имя Docker-сети, к которой будут подключены узлы кластера (вместо сети по умолчанию). |
| `KIND_NODE_IMAGE` | Переопределяет образ узла `kindest/node` по умолчанию для всех создаваемых кластеров (имеет меньший приоритет, чем явное указание `image` в YAML-конфигурации). |

## Дополнительная информация

### Требования к системе

| Компонент | Версия / Требование | Примечание |
| :--- | :--- | :--- |
| **Docker** | 18.09+ | Рекомендуемая среда для запуска узлов. Требуется выделение достаточного объема оперативной памяти (минимум 4-8 GB для Docker Desktop). |
| **Podman** | 3.0+ | Альтернатива Docker для систем без демона (Linux/macOS). |
| **kubectl** | Любая совместимая | Необходима для управления созданным кластером. Версия должна отличаться не более чем на 1 минорную версию от версии K8s в кластере (+/- 1). |
| **ОС (Операционная Система)** | Linux / macOS / Windows | Windows поддерживается через WSL2 (Windows Subsystem for Linux) или Docker Desktop. |
