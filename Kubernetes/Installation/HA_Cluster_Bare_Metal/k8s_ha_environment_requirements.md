# HA кластер Kubernetes: Требования к среде

## Определения

**HA кластер (High Availability)** — отказоустойчивая конфигурация Kubernetes с избыточностью узлов Control Plane (обычно 3, 5 или более), обеспечивающая непрерывную доступность API-сервера и сохранность данных при выходе из строя отдельных серверов.

**Control Plane** — «мозг» кластера, включающий `kube-apiserver`, `etcd`, `kube-controller-manager` и `kube-scheduler`.

**Кворум etcd** — минимальное количество работоспособных узлов в кластере `etcd`, необходимое для принятия решений и записи данных. Рассчитывается как `(n/2) + 1`.

**VIP (Virtual IP)** — плавающий IP-адрес, обеспечивающий единую точку входа для API-сервера. Переключается между мастерами с помощью протоколов VRRP (Keepalived) или BGP (Kube-vip).

**cgroups v2** — современная версия контрольных групп Linux. Единая иерархия (в отличие от v1) обеспечивает предсказуемое потребление ресурсов контейнерами. Обязательна для Kubernetes 1.25+.

**SWAP (Раздел подкачки)** — область на диске, используемая ОС при нехватке оперативной памяти. Kubernetes требует полного отключения SWAP, так как `kubelet` не умеет учитывать подкачку при планировании ресурсов.

**Raft** — алгоритм консенсуса, используемый etcd для репликации данных и выбора лидера. Требует большинства узлов (кворума) для подтверждения записи.

## Основные концепции

### Аппаратные требования

#### Control Plane узлы (мастеры)

| Ресурс | Минимум | Рекомендация (Production) | Техническое обоснование |
| :--- | :--- | :--- | :--- |
| **CPU** | 2 ядра | 4–8 ядер | Обработка API-запросов и работа etcd. |
| **RAM** | 4 ГБ | 8–16 ГБ | Кэширование данных etcd и стабильность API. |
| **Disk** | 40 ГБ SSD | 100 ГБ+ NVMe SSD | **Критично:** etcd требует низкой задержки (fsync < 10ms). |
| **Network** | 1 Гбит/с | 10 Гбит/с | Минимизация джиттера и задержек репликации etcd. |

**Количество узлов**: Строго нечётное (3, 5) для обеспечения кворума.

#### Worker узлы

| Ресурс | Минимум | Рекомендация | Примечание |
| :--- | :--- | :--- | :--- |
| **CPU** | 2 ядра | 4+ ядра | Масштабируется в зависимости от нагрузки. |
| **RAM** | 4 ГБ | 16–64 ГБ | Зависит от требований запускаемых приложений. |
| **Disk** | 40 ГБ | 100 ГБ+ (SSD/NVMe) | Под хранение образов и эфемерных данных. |

#### Дисковая подсистема etcd (Критический фактор)

Для стабильности HA-кластера задержка `fdatasync` диска на мастер-узлах должна быть стабильно **менее 10 мс**.
- **Рекомендуется**: Локальные NVMe SSD.
- **Запрещено**: Сетевые диски (NFS, iSCSI, Ceph RBD) для раздела с данными etcd из-за высокого джиттера задержек.

**Почему это критично:** Алгоритм Raft, используемый etcd, блокируется на каждом шаге записи до завершения физического сброса данных на диск (fsync). Задержка более 10 мс приводит к потере лидера и нестабильности всего кластера.

Подробнее об архитектуре etcd и консенсусе Raft: **[Архитектура etcd](../../../etcd/architecture-and-concepts.md)**.

#### Матрица кворума и отказоустойчивости

| Узлов | Кворум | Допустимый отказ | Сценарий применения |
| :--- | :--- | :--- | :--- |
| 3 | 2 | 1 | Малые кластеры, ограниченный бюджет |
| 5 | 3 | 2 | Production (рекомендуется) |
| 7 | 4 | 3 | Крупные кластеры, высокая доступность |

**Правило:** Чётное количество узлов (например, 4) не повышает устойчивость к сбоям по сравнению с меньшим нечётным числом (3), но увеличивает накладные расходы на сеть.

## Практические сценарии

### Программные требования

#### Матрица совместимости ОС

| ОС | Версия | Статус |
| :--- | :--- | :--- |
| **Ubuntu** | 22.04 LTS, 24.04 LTS | Основная платформа (рекомендуется) |
| **Debian** | 11, 12 | Полная поддержка |
| **RHEL / Rocky / Alma** | 8.x, 9.x | Рекомендуется для Enterprise сред |

**Требования к ядру и среде**:
- Ядро Linux: 5.4+ (рекомендуется 6.x для лучшей поддержки eBPF/Cilium).
- Менеджер ресурсов: `systemd` (использование cgroups v2 обязательно для K8s 1.25+).
- Рантайм: `containerd` 1.6+ (совместим с K8s v1.35).

### Сетевое планирование

#### Порты Control Plane (Обязательно к открытию)

| Порт | Протокол | Назначение |
| :--- | :--- | :--- |
| 6443 | TCP | Kubernetes API Server (входящий для всех) |
| 2379-2380 | TCP | etcd client & peering (только между мастерами) |
| 10250 | TCP | Kubelet API (входящий от API-сервера) |
| 10257 | TCP | kube-controller-manager (healthz) |
| 10259 | TCP | kube-scheduler (healthz) |

#### Порты балансировщика (Keepalived/HAProxy)

| Порт | Протокол | Назначение |
| :--- | :--- | :--- |
| 6443 | TCP | Внешний порт VIP (проксирует на мастера) |
| 9000 | TCP | Статистика HAProxy (опционально) |
| VRRP | Protocol 112 | Сигнализация Keepalived (внутри L2 сегмента) |

#### Планирование CIDR (Подсети)

1.  **Node Network**: Физические IP серверов.
2.  **Pod Network**: Например, `10.244.0.0/16`. Не должна пересекаться с Node Network.
3.  **Service Network**: Например, `10.96.0.0/12`. Виртуальные IP внутри кластера.
4.  **MTU**: При использовании инкапсуляции (VXLAN) MTU интерфейсов подов должен быть на 50 байт меньше физического (например, 1450 при стандартном 1500).

**Почему MTU важен:** VXLAN добавляет 50 байт заголовка (8 байт VXLAN + 8 байт UDP + 20 байт IP + 14 байт Ethernet). Если MTU пода равен MTU физического интерфейса, пакеты фрагментируются, что снижает производительность и увеличивает задержки.

### Предварительная проверка готовности

#### Проверка задержки диска (etcd)

Перед развертыванием кластера убедитесь, что диск соответствует требованиям etcd:

```bash
# Установка fio (если не установлен)
sudo apt install -y fio  # Ubuntu/Debian
# sudo dnf install -y fio  # RHEL/Rocky

# Тест fdatasync latency (критично для etcd)
fio --rw=write --ioengine=sync --fdatasync=1 --directory=/var/lib/etcd \
    --size=22m --bs=2300 --name=etcd-sync-test
# → Ищите результат "clat" (completion latency) в микросекундах
# → p99 должен быть менее 10000 микросекунд (10 мс)
```

Подробнее о тестировании дисков: **[fio — тестирование производительности](../../../Linux/Diagnostics/Filesystem/fio.md)**.

#### Проверка синхронизации времени

```bash
# Установка и запуск Chrony
sudo apt install -y chrony  # Ubuntu/Debian
# sudo dnf install -y chrony  # RHEL/Rocky
sudo systemctl enable --now chrony

# Проверка статуса синхронизации
chronyc tracking
# → Leap status: Normal
# → System time: 0.000001234 seconds fast of NTP time

# Проверка доступных серверов
chronyc sources -v
# → Должны показать NTP-серверы с префиксами ^* или ^+

# Проверка разницы времени между узлами (на каждом узле)
date +%s%N
# → Сравните вывод на всех мастерах; разница должна быть < 100мс
```

**Важно:** В HA-кластерах все узлы должны синхронизироваться с одними и теми же NTP-серверами. Различные источники времени могут приводить к расхождениям.

#### Проверка сетевой связности

```bash
# Проверка портов между мастерами
nc -zv <master-ip> 2379  # etcd client
nc -zv <master-ip> 2380  # etcd peering
nc -zv <master-ip> 6443  # API Server

# Проверка задержки сети между узлами
ping -c 10 <master-ip>
# → Средняя задержка должна быть < 1мс в пределах одного дата-центра

# Проверка MTU
ping -M do -s 1472 <master-ip>
# → Если пакет проходит — MTU корректен (1472 + 28 байт заголовка = 1500)
```

#### Проверка отключения SWAP

```bash
# Проверка текущего состояния
swapon --show
# → Должен быть пустой вывод (swap отключен)

# Если swap активен — отключить
sudo swapoff -a
sudo sed -i '/ swap / s/^\(.*\)$/#\1/g' /etc/fstab

# Проверка в /etc/fstab
grep -i swap /etc/fstab
# → Все строки со swap должны быть закомментированы
```

Подробнее о подготовке ОС: **[Подготовка узлов HA кластера](./k8s_ha_node_preparation.md)**.

## Дополнительная информация

### Предварительная готовность инфраструктуры

- **Синхронизация времени**: `chrony` или `ntp` обязательны. Разница более 500мс между мастерами разрывает кворум etcd.
- **DNS**: Узлы должны резолвить имена друг друга. Рекомендуется прописать статические записи в `/etc/hosts` в качестве fallback.
- **SSH**: Доступ по ключам с правами `sudo` на все узлы для инструментов автоматизации (kubeadm, ansible).
- **NetworkManager**: Если на узлах установлен `NetworkManager`, убедитесь, что он не управляет интерфейсами, созданными Kubernetes/CNI. Рекомендуется добавить `unmanaged-devices` в конфигурацию NetworkManager.

Подробнее о настройке NetworkManager для Kubernetes: **[Подготовка узлов HA кластера](./k8s_ha_node_preparation.md)**.

### Freshness и актуальность (v1.35+)

- **Kubernetes**: v1.35 (актуально на 2026 год).
- **containerd**: v1.7.x / v2.0 (поддержка CDI и WASM).
- **Cilium**: v1.16+ (предпочтительный CNI для Bare Metal с BGP).

### Типичные ошибки при планировании

| Ошибка | Последствие | Решение |
| :--- | :--- | :--- |
| **Использование HDD для etcd** | Высокая задержка fsync, потеря лидера, нестабильность кластера | Заменить на NVMe SSD |
| **Чётное количество узлов etcd** | Нет выигрыша в отказоустойчивости, увеличение накладных расходов | Использовать 3, 5, 7 узлов |
| **Разные NTP-серверы на узлах** | Рассинхронизация времени, проблемы с сертификатами и кворумом | Настроить одинаковые NTP-серверы |
| **Пересечение CIDR** | Конфликты маршрутизации, недоступность подов/сервисов | Планировать непересекающиеся подсети |
| **Активный SWAP** | kubelet не запускается | `swapoff -a` и комментирование в `/etc/fstab` |
| **Игнорирование MTU** | Фрагментация пакетов, снижение производительности | Установить MTU на 50 байт меньше физического |

### Best Practices для production

1. **Изоляция etcd**: Размещайте данные etcd на отдельных физических дисках (или разделах) от системного диска.
2. **Резервирование сети**: Используйте несколько сетевых интерфейсов (bonding) для трафика etcd и API-сервера.
3. **Мониторинг диска**: Настройте алерты на `etcd_disk_wal_fsync_duration_seconds` (p99 > 20мс) и `etcd_disk_backend_commit_duration_seconds`.
4. **Документирование топологии**: Храните схему сети, IP-адреса и CIDR в системе контроля версий.
5. **Тестирование отказов**: Проводите регулярные GameDay-тесты (отключение мастера, сети, диска).
