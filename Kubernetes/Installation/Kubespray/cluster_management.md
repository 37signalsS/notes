# Kubespray: Управление кластером

## Определения

**Управление кластером** — комплекс операций по изменению жизненного цикла существующего кластера, включая вертикальное и горизонтальное масштабирование, обновление версий компонентов, ротацию сертификатов и вывод узлов из эксплуатации.

**Масштабирование (Scaling)** — процесс изменения количества узлов в кластере. В контексте Kubespray разделяется на добавление рабочих узлов (Workers) и узлов плоскости управления (Control Plane/etcd).

**Обновление (Upgrade)** — переход на более новую минорную или патч-версию Kubernetes. В Kubespray реализовано как автоматизированный процесс rolling update.

**Идемпотентный плейбук** — сценарий Ansible, который можно запускать многократно; он приводит систему к заданному состоянию, выполняя действия только там, где текущее состояние отличается от целевого.

## Основные концепции

### Плейбуки жизненного цикла

Для управления кластером после его первичного развертывания используются следующие основные сценарии:

| Плейбук | Назначение |
| :--- | :--- |
| **`scale.yml`** | Добавление новых рабочих узлов. Оптимизирован для быстрого расширения кластера. |
| **`cluster.yml`** | Полная перенастройка кластера или добавление узлов Control Plane / etcd. |
| **`upgrade-cluster.yml`** | Последовательное обновление всех компонентов (etcd, runtime, K8s) без простоя. |
| **`remove-node.yml`** | Удаление узла: исключение из API, очистка конфигурации и остановка сервисов. |
| **`reset.yml`** | Полная очистка узлов от компонентов Kubernetes. Возвращает ОС к состоянию до установки. |
| **`facts.yml`** | Сбор актуальных данных о состоянии узлов без внесения изменений. |

### Правила и ограничения обновлений

1.  **Шаг обновления:** поддерживается обновление только на одну минорную версию за раз (например, v1.31 → v1.32). Перескакивать через версию (например, v1.30 → v1.32) запрещено.
2.  **Длительность:** процесс обновления HA-кластера может занимать значительное время (от 20 минут до нескольких часов) в зависимости от количества узлов, так как задачи выполняются последовательно для сохранения кворума.
3.  **Состояние узлов:** перед запуском обновления все узлы должны находиться в статусе `Ready`. Обновление кластера с "битыми" узлами может привести к непредсказуемым последствиям.

## Практические сценарии

### Сценарий 1: Масштабирование (Добавление узлов)

#### Добавление рабочих узлов (Worker Nodes)

При добавлении воркеров рекомендуется использовать флаг `--limit`, чтобы Ansible не тратил время на опрос всего кластера.

1.  **Обновление инвентаря:** добавьте новый хост в `inventory/my-cluster/hosts.yaml` в группу `kube_node`.
2.  **Запуск:**
    ```bash
    # Использование --limit позволяет значительно ускорить процесс
    ansible-playbook -i inventory/my-cluster/hosts.yaml --become scale.yml --limit=new_node_name
    ```

#### Добавление узлов управления (Control Plane)

Добавление мастер-узлов требует пересчета кворума etcd и обновления сертификатов на всех существующих мастерах.

1.  **Обновление инвентаря:** добавьте хост в группы `kube_control_plane` и `etcd`.
2.  **Запуск:**
    ```bash
    # Для Control Plane использование --limit НЕ рекомендуется, так как требуется настройка связей
    ansible-playbook -i inventory/my-cluster/hosts.yaml --become cluster.yml
    ```

### Сценарий 2: Удаление узла

Плейбук `remove-node.yml` автоматически выполняет `kubectl drain`, удаляет узел из кластера и очищает его локальные данные.

```bash
ansible-playbook -i inventory/my-cluster/hosts.yaml --become remove-node.yml -e node=node_name_to_remove
```

### Сценарий 3: Обновление версии Kubernetes

#### Подготовка

1.  **Бэкап etcd:** обязательный шаг перед обновлением. См. [Обслуживание etcd](../../Concepts/etcd_overview.md).
2.  **Обновление кода Kubespray:** переключитесь на нужную ветку репозитория (например, `branch-2.29` для K8s v1.32).
3.  **Обновление зависимостей:** `pip install -r requirements.txt`.

#### Выполнение обновления

1.  **Настройка версии:** в файле `group_vars/k8s_cluster/k8s-cluster.yml` установите:
    ```yaml
    kube_version: v1.32.1
    ```
2.  **Запуск:**
    ```bash
    ansible-playbook -i inventory/my-cluster/hosts.yaml --become upgrade-cluster.yml
    ```

### Сценарий 4: Полный сброс (Reset)

Если установка завершилась критической ошибкой или узел нужно переиспользовать для других целей:

```bash
# Осторожно: удаляет ВСЕ данные кластера на указанных узлах
ansible-playbook -i inventory/my-cluster/hosts.yaml --become reset.yml
```

## Диагностика и обслуживание

### Типовые проблемы при управлении

| Проблема | Причина и решение |
| :--- | :--- |
| **Ошибка при Cordon/Drain** | Наличие подов с Local Storage или отсутствие PDB (Pod Disruption Budget). Используйте `-e force_drain=true`. |
| **Развал кворума etcd** | Возникает при одновременном обновлении или падении >50% мастеров. Требуется ручное восстановление. |
| **Несоответствие контрольных сумм** | Ошибка при загрузке бинарных файлов. Попробуйте запустить с `-e download_force_cache=true`. |

### Обслуживание узлов без Ansible

В экстренных случаях (например, при зависании Ansible) можно использовать стандартные средства Kubernetes:
- `kubectl cordon <node>` — запрет назначения новых подов.
- `kubectl drain <node> --ignore-daemonsets` — вытеснение текущих нагрузок.
- `kubectl uncordon <node>` — возврат узла в работу.
