# Kubespray: Offline установка — Определения

## Определения

**Offline-кластер (Air-gapped)** — кластер Kubernetes, развёртываемый в изолированной среде без прямого доступа к публичным сетям. Требует пре-стейджинга (pre-staging) всех зависимостей и их физического переноса (через USB, SCP или выделенные шлюзы) в закрытую сеть. Термин «air-gapped» буквально означает «воздушный зазор» — физическое отсутствие сетевого подключения к внешнему миру.

**Закрытый контур (Closed Loop)** — сегмент сети предприятия, защищенный межсетевыми экранами, где запрещен любой исходящий трафик в интернет. Для работы требуются локальные зеркала: Harbor (для образов и чартов) и репозитории пакетов ОС (APT/YUM). Все DNS-запросы и pull-образов перенаправляются на локальные сервисы.

**Открытый контур (Open Loop)** — доверенный сегмент сети с доступом к интернету, используемый как точка сбора (Gateway) для формирования установочного бандла. Узел `pc-inet` является представителем открытого контура и единственным узлом с прямым доступом к публичным реестрам.

**Локальный кэш Kubespray (Download Cache)** — структура директорий на узле `pc-inet`, где механизм `download` сохраняет бинарные файлы и tar-архивы образов. Позволяет избежать повторных загрузок и упрощает упаковку. Располагается в `/opt/kubespray-cache` (образы) и `/opt/kubespray-releases` (бинарные файлы, Helm-чарты).

**Артефакты (Artifacts)** — полный технологический стек, необходимый для развертывания:
- **Python Wheel пакеты:** зависимости для Ansible и плагинов.
- **System Binaries:** `kubeadm`, `kubectl`, `kubelet`, `etcd`, `helm`, `cni-plugins`.
- **Container Images:** системные компоненты (apiserver, scheduler, proxy), CNI (cilium, hubble), CSI (provisioners) и аддоны (coredns).
- **OCI Artifacts:** Helm-чарты, упакованные в формате контейнерных слоев.

**Пре-стейджинг (Pre-staging)** — процесс подготовки и переноса всех необходимых артефактов из открытого контура в закрытый до начала фактического развёртывания. Включает загрузку, упаковку, физическую передачу и импорт в локальный реестр. Пре-стейджинг является критическим этапом — ошибка на этом шаге мультиплицируется на все последующие.

**Установочный бандл (Offline Bundle)** — архивированная совокупность всех артефактов, упакованная для переноса в закрытый контур. Обычно представляет собой tar.gz-архив размером 2-4 ГБ, содержащий tar-архивы образов, бинарные файлы и Helm-чарты. Формируется на `pc-inet` и переносится через SCP или USB.

**Инвентарь Ansible (Inventory)** — файл `inventory.ini` в Kubespray, определяющий состав кластера, IP-адреса, SSH-параметры и группировку узлов по ролям (control plane, etcd, kube-node). В offline-режиме инвентарь содержит реальные IP-адреса узлов закрытого контура и указание на Harbor как единственный реестр.

**Тегирование образов (Image Tagging)** — механизм Kubespray по формирования тегов образов в формате `harbor.domain.local/k8s/<оригинальный_реестр>/<образ>:<тег>`. Гарантирует, что containerd на целевых узлах обращается только к Harbor, а не к публичным реестрам. Механизм управляется переменными `*_image_repo` в `group_vars/all/offline.yml`.

**Кворум (Quorum)** — минимальное число узлов etcd, необходимое для عملоспособности кластера ключ-значений. Для кластера из N узлов кворум составляет `(N/2) + 1`. Трёхузловой etcd требует доступности минимум 2 из 3 узлов — потеря большего числа делает кластер недоступным.

## Основные концепции

### Архитектура offline-развёртывания

Процесс строится на строгом разделении зон ответственности. Узел `pc-inet` выступает «чистой комнатой» для подготовки артефактов.

```text
┌─────────────────────────────────────────────────────────────┐
│                   Открытый контур (INET)                    │
│  ┌─────────────┐                                            │
│  │   pc-inet   │ ──┐ Загрузка артефактов (Download Tag):     │
│  │ 192.168.1.99│   │ - venv/ (Ansible 2.17+ / Python 3.12)  │
│  └─────────────┘   │ - /opt/kubespray-cache/ (Images/K8s)   │
│        │           │ - /opt/kubespray-releases/ (Helm/Bin)  │
│        ▼           │ - cilium-v1.19.6.tgz (Helm Chart)      │
└─────────────────────────────────────────────────────────────┘
                          │
                          │ Перенос архивов (Tarball)
                          ▼
┌─────────────────────────────────────────────────────────────┐
│                   Закрытый контур (NO INET)                 │
│  ┌─────────────┐     ┌─────────────────────────────────┐    │
│  │ Harbor      │     │  master-1-k8s (Ansible Control) │    │
│  │192.168.1.100│◄────┤  192.168.1.101                  │    │
│  │  - k8s/*    │     │  - Kubespray Inventory          │    │
│  │  - helm/*   │     │  - group_vars/all/offline.yml   │    │
│  └─────────────┘     └──────────┬──────────────────────┘    │
│                                 │                            │
│              ┌──────────────────┼──────────────────┐         │
│              ▼                  ▼                  ▼         │
│       master-2,3           node-1,2        MetalLB VIP       │
│      192.168.1.102-103   192.168.1.104-105   192.168.1.200   │
└─────────────────────────────────────────────────────────────┘
```

### Методы переноса артефактов

Выбор метода переноса зависит от политики безопасности предприятия и физической доступности узлов:

| Метод | Скорость | Безопасность | Применение |
| :--- | :--- | :--- | :--- |
| **SCP/SFTP** | Высокая (сеть) | Средняя (шифрование) | Закрытый контур с выделенным шлюзом |
| **USB-накопитель** | Средняя | Высокая (физический контроль) | Полностью изолированные среды (SIPR/NIPR) |
| **Оптический диск** | Низкая | Высокая | Архивное копирование, аудит |

При использовании SCP необходимо учитывать:
- Пропускную способность сети между контурами (обычно 100 Мбит/с — 1 Гбит/с)
- Необходимость верификации целостности архивов (checksum SHA-256)
- Политику хранения временных файлов на промежуточных узлах

При использовании USB:
- Форматирование в ext4/xfs (не NTFS — проблемы с правами Linux)
- Шифрование LUKS при политике безопасности enterprises
- Физическая цепочка custody (кто передавал, кто принимал)

### Модель безопасности offline-кластера

Offline-кластер имеет принципиально иную модель угроз по сравнению с облачными кластерами:

1. **Отсутствие обновлений:** Без доступа к интернету невозможно получение CVE-патчей. Необходимо планировать регулярные циклы обновления черезpc-inet.
2. **Доверие к артефактам:** Все образы и бинарные файлы загружаются из публичных реестров на `pc-inet`. Компрометация этого узла приводит к компрометации всего кластера.
3. **Физическая безопасность:** Закрытый контур должен быть физически защищен — unauthorized access к узлам кластера является критическим инцидентом.
4. **TLS-сертификаты:** Harbor использует самоподписанные сертификаты. CA-сертификат должен быть распространён на все узлы до начала развёртывания.
5. **Audit trail:** Все операции по переносу артефактов должны логироваться для соответствия требованиям аудита (SOC 2, PCI DSS).

### Зоны отказа (Failure Domains)

Offline-кластер имеет уникальные зоны отказа, отличающиеся от облачных:

| Зона отказа | Компонент | Последствия | Восстановление |
| :--- | :--- | :--- | :--- |
| **Сеть** | Связность между узлами | Потеря кворума etcd, сетевая изоляция подов | Проверка коммутаторов, кабелей |
| **Реестр** | Harbor | Невозможность запуска новых подов | Рестарт Harbor, проверка диска |
| **Диск** | SSD узлов Control Plane | Потеря данных etcd, нестабильность кластера | Восстановление из backup etcd |
| **Узел** | Control Plane / Worker | Потеря кворума / уменьшение ресурсов | Рестарт kubelet/containerd, перезапуск ВМ |
| **Время** | NTP/Chrony | Расхождение сертификатов, split-brain в etcd | Синхронизация времени, проверка Chrony |

### Версии компонентов (Матрица совместимости 2026)

Для обеспечения стабильности в рамках данного руководства используются следующие версии:

| Компонент | Версия | Примечание |
| :--- | :--- | :--- |
| **Kubespray** | v2.31.0 | Стабильная ветка для Ubuntu 24.04 |
| **Kubernetes** | v1.34.3 | Базовая версия API |
| **Cilium** | v1.19.6 | eBPF CNI с поддержкой Hubble |
| **MetalLB** | v0.16.1 | Работает через frr-k8s |
| **Harbor** | v2.11.x | Реестр с поддержкой OCI и Helm |
| **Containerd** | v1.7.20+ | Runtime с поддержкой hosts.toml |

> **Важно:** Версии Kubespray, Kubernetes и Cilium должны соответствовать матрице совместимости. Использование несовместимых версий приводит к ошибкам на этапе установки или нестабильности кластера. Актуальную матрицу совместимости Kubespray проверяйте в [официальной документации](https://github.com/kubernetes-sigs/kubespray).

## Практические сценарии

### Обзор процесса offline-установки

Offline-установка — это пять последовательных этапов, каждый из которых имеет строгие входные и выходные данные. Нарушение порядка (критический путь) делает невозможным выполнение последующих шагов.

```text
Этап 1: Подготовка VM ──────────────────────────────────────►
        (SSH, системные параметры, NTP)
        Вход: 7 чистых ВМ с Ubuntu 24.04
        Выход: SSH-доступ, настроенные узлы
                          │
                          ▼
Этап 2: Загрузка артефактов (pc-inet) ──────────────────────►
        (Kubespray download, Helm charts)
        Вход: Доступ в интернет на pc-inet
        Выход: tar.gz-архив ~2-4 ГБ
                          │
                          ▼
Этап 3: Настройка Harbor (закрытый контур) ──────────────────►
        (Развёртывание реестра, импорт образов)
        Вход: Архивы из Этапа 2
        Выход: Harbor с образами и чартами
                          │
                          ▼
Этап 4: Развёртывание кластера ──────────────────────────────►
        (ansible-playbook cluster.yml)
        Вход: Harbor работает, образы доступны
        Выход: Kubernetes кластер (5 узлов)
                          │
                          ▼
Этап 5: MetalLB + Ingress + Валидация ───────────────────────►
        (Внешний доступ, Hubble UI, E2E-тесты)
        Вход: Рабочий кластер
        Выход: Полностью функциональный offline-кластер
```

### Предварительные проверки (Pre-flight)

Перед каждым этапом необходимо выполнить блок проверок. Игнорирование pre-flight проверок приводит к ошибкам на последующих шагах, где стоимость исправления значительно выше.

#### Проверки перед Этапом 1 (Инфраструктура)

```bash
# Проверка доступности всех IP-адресов
for ip in 192.168.1.{99,100,101,102,103,104,105}; do
  ping -c 1 -W 1 $ip > /dev/null 2>&1 && echo "$ip: OK" || echo "$ip: FAILED"
done

# Проверка SSH-доступа с master-1
for ip in 192.168.1.{99,100,102,103,104,105}; do
  ssh -o BatchMode=yes -o ConnectTimeout=3 admin@$ip "hostname" 2>/dev/null \
    && echo "$ip: SSH OK" || echo "$ip: SSH FAILED"
done

# Проверка Ubuntu версии на целевых узлах
for ip in 192.168.1.{101,102,103,104,105}; do
  ssh admin@$ip "lsb_release -rs" 2>/dev/null
done
# → Ожидаемый результат: 24.04 на всех узлах
```

#### Проверки перед Этапом 2 (Загрузка)

```bash
# Проверка доступа в интернет на pc-inet
curl -s -o /dev/null -w "%{http_code}" https://registry.k8s.io/v2/
# → 401 (требуется авторизация, но соединение установлено)

# Проверка DNS-резолвинга
for registry in registry.k8s.io gcr.io docker.io quay.io helm.cilium.io; do
  nslookup $registry > /dev/null 2>&1 && echo "$registry: OK" || echo "$registry: FAILED"
done

# Проверка свободного места на pc-inet (минимум 25 ГБ)
df -h /opt | tail -1 | awk '{print "Free: " $4}'
```

#### Проверки перед Этапом 4 (Deploy)

```bash
# Проверка доступности Harbor
curl -sk https://harbor.domain.local/api/v2.0/health
# → {"status":"healthy"}

# Проверка наличия критических образов
for img in kube-apiserver kube-controller-manager kube-scheduler kube-proxy; do
  curl -sk "https://harbor.domain.local/v2/k8s/registry.k8s.io/${img}/tags/list" \
    | python3 -c "import sys,json; print('$img:', json.load(sys.stdin).get('tags',['EMPTY']))" 2>/dev/null
done

# Проверка SSH-доступа ко всем узлам кластера
for ip in 192.168.1.{101,102,103,104,105}; do
  ssh -o BatchMode=yes admin@$ip "sudo systemctl is-active containerd" 2>/dev/null
done
# → Ожидаемый результат: active на всех узлах
```

### Порядок действий при различных сценариях

| Сценарий | Этапы | Примечание |
| :--- | :--- | :--- |
| **Новое развертывание** | 1 -> 2 -> 3 -> 4 -> 5 | Строго последовательно |
| **Добавление Worker-узла** | 1 (VM) -> 4 (scale.yml) | Пропуск шагов 2-3 |
| **Обновление Kubernetes** | 2 (загрузка) -> 3 (Harbor) -> 4 (upgrade) | Обновление через upgrade-теги |
| **Миграция Harbor** | 3 (импорт) -> 4 (применение) | Только обновление образов |
| **Замена Master-узла** | 1 (VM) -> 4 (恢复) | Восстановление etcd из backup |

### Ключевые переменные для offline-режима

Все настройки вносятся в файл `inventory/offline_cluster/group_vars/all/offline.yml`:

```yaml
# === Глобальные настройки кэширования (pc-inet) ===
download_run_once: true           # Скачивать файл/образ только один раз
download_localhost: true          # Хранить кэш на управляющей машине
download_format: "tarball"        # Формат архивов для переноса
local_release_dir: "/opt/kubespray-releases"
download_cache_dir: "/opt/kubespray-cache"

# === Переопределение реестров (закрытый контур) ===
registry_host: "harbor.domain.local"
kube_image_repo: "{{ registry_host }}/k8s/registry.k8s.io"
gcr_image_repo: "{{ registry_host }}/k8s/gcr.io"
docker_image_repo: "{{ registry_host }}/k8s/docker.io"
quay_image_repo: "{{ registry_host }}/k8s/quay.io"

# === Cilium через OCI ===
cilium_version: "v1.19.6"
cilium_install_with_helm: true
cilium_install_extra_flags: "--repository oci://{{registry_host}}/helm/cilium"
cilium_deploy_with_digest: false  # Обязательно при миграции через docker save/load
```

### Типовые ошибки offline-установки

| Ошибка | Этап | Причина | Решение |
| :--- | :--- | :--- | :--- |
| `Permission denied (publickey)` | 1 | SSH-ключ не скопирован | `ssh-copy-id admin@<ip>` |
| `sudo: a password is required` | 1 | Не настроен NOPASSWD | `echo "admin ALL=(ALL) NOPASSWD:ALL" > /etc/sudoers.d/admin` |
| `python3-apt: No module named` | 2 | venv не видит системные пакеты | `python3 -m venv --system-site-packages venv` |
| `403 Forbidden` при загрузке | 2 | Реестр блокирует скачивание | Использовать зеркала или VPN на pc-inet |
| `x509: certificate signed by unknown authority` | 3-4 | CA Harbor не установлен | Добавить сертификат в `/usr/local/share/ca-certificates/` |
| `manifest unknown` | 3-4 | Образ отсутствует в Harbor | Проверить проект k8s в веб-интерфейсе Harbor |
| `ImagePullBackOff` (Cilium) | 4 | Digest не совпадает | Установить `cilium_deploy_with_digest: false` |
| etcd: `leader changed` | 4 | Медленные диски или сеть | Использовать SSD, проверить `ping` между мастерами |
| VIP застрял в `<pending>` | 5 | IP-пул вне L2-подсети | Проверить `addresses` в IPAddressPool |
| `connection refused` (Harbor) | 4 | Harbor недоступен | Проверить DNS, порт 443, статус сервиса |
