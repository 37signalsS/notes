# Kubespray: Развертывание HA-кластера — Основные концепции

## Определения

**HA-кластер (High Availability)** — конфигурация Kubernetes с несколькими узлами Control Plane (обычно 3, 5 или более), предназначенная для устранения единой точки отказа (SPoF) и обеспечения непрерывной работы API-сервера и etcd. В HA-кластере выход из строя одного или нескольких узлов не приводит к полной потере управляемости кластера.

**VIP (Virtual IP)** — плавающий IP-адрес, обеспечивающий единую точку входа для клиентов (kubectl, CI/CD). Не привязан к конкретному физическому интерфейсу и может динамически перемещаться между узлами. Управляется через механизмы VRRP (L2) или BGP (L3).

**VRRP (Virtual Router Redundancy Protocol)** — сетевой протокол уровня 3, используемый Keepalived для автоматического назначения VIP активному узлу и обнаружения сбоев. Узлы обмениваются VRRP-объявлениями (Advert packets) с настраиваемым интервалом (по умолчанию 1 секунда). При прекращении получения объявлений от текущего MASTER-узла, BACKUP-узел с наивысшим приоритетом инициирует выборы и берёт VIP на себя.

**nopreempt** — режим VRRP, при котором восстановившийся узел с более высоким приоритетом **не** отбирает VIP обратно у текущего MASTER. Рекомендуется для Kubernetes, чтобы избежать лишних переключений VIP и кратковременных разрывов соединений при восстановлении узла. В Kubernetes приоритет VIP менее критичен, чем стабильность соединений.

**Gratuitous ARP** — механизм, с помощью которого Keepalived уведомляет сетевое оборудование (коммутаторы, маршрутизаторы) о том, что VIP-адрес переместился на другой MAC-адрес. Gratuitous ARP — это broadcast-пакет с целевым MAC `ff:ff:ff:ff:ff:ff`, который обновляет ARP-таблицы всех узлов в L2-сегменте. Используется в режиме Multicast; в Unicast-режиме обновление ARP происходит через сам VRRP-протокол.

**Unicast VRRP** — режим работы Keepalived, при котором VRRP-пакеты отправляются на конкретные IP-адреса соседей, а не в Multicast-группу (224.0.0.18). Необходим в сетях, где Multicast заблокирован или недоступен (большинство enterprise-сред и public cloud).

**BFD (Bidirectional Forwarding Detection)** — протокол обнаружения отказов линков, работающий в паре с VRRP для ускорения обнаружения недоступности узла. Вместо ожидания нескольких интервалов `advert_int` (по умолчанию 1 секунда), BFD детектирует отказ за миллисекунды (до 50 мс). Конфигурируется через `keepalived.conf` с параметрами `min_rx`, `min_tx` и `multiplier`.

**BGP (Border Gateway Protocol)** — протокол маршрутизации уровня 3, используемый kube-vip для анонсирования VIP через маршрутизаторы. В отличие от ARP (L2), BGP работает в L3-средах и поддерживает ECMP (Equal-Cost Multi-Path) для распределения трафика между несколькими узлами. Каждый узел устанавливает BGP-сессию с настраиваемым AS-номером и анонсирует маршрут к VIP.

**Kube-vip** — cloud-native решение для организации VIP и балансировки нагрузки, работающее в виде Static Pod. Объединяет функции управления VIP и балансировки трафика. Запускается как Pod в `/etc/kubernetes/manifests/kube-vip.yaml` до инициализации кластера. Рекомендуемый метод для bare-metal инсталляций в Kubespray.

**Nginx-proxy (Local LB)** — «safety net» механизм Kubespray. Представляет собой локальный балансировщик на каждом узле кластера, который перенаправляет запросы к API-серверу на группу мастеров. Работает на уровне L4 (TCP) и обеспечивает внутреннюю связность кластера (`kubelet` -> `apiserver`) даже при недоступности внешнего VIP.

**HAProxy** — высокопроизводительный L4/L7-балансировщик, используемый для распределения трафика API-сервера между мастер-узлами. Выполняет глубокую проверку здоровья (Health Check) бэкендов через HTTP-запросы к `/healthz` на порту 6443 (или 6444 при разделении портов). Конфигурируется как система или Static Pod.

**Keepalived** — пользовательское пространство, реализующее VRRP и мониторинг здоровья (Health Check) через встроенные скрипты. Управляет назначением VIP на MASTER-узел и исключением нездоровых бэкендов из балансировки HAProxy. Работает как системный сервис (systemd) или Static Pod.

**Control Plane Endpoint** — стабильный адрес (DNS-имя или VIP:Port), который используется всеми компонентами кластера (`kubelet`, `kube-proxy`, `scheduler`) и администраторами (`kubectl`) для взаимодействия с API-сервером. Задаётся через флаг `--control-plane-endpoint` при `kubeadm init` или через переменную `apiserver_endpoint` в Kubespray.

**ip_nonlocal_bind** — параметр ядра Linux (`net.ipv4.ip_nonlocal_bind = 1`), позволяющий процессам (например, HAProxy) привязываться к IP-адресам, которые ещё не назначены интерфейсу. Критично для запуска HAProxy на BACKUP-узлах, которые не владеют VIP, но должны быть готовы принять трафик при переключении.

**Connection Draining** — механизм плавного завершения активных TCP-соединений при исключении бэкенда из балансировки. В HAProxy реализуется через параметры `timeout server` и `option redispatch`, позволяющие перенаправить незавершённые соединения на другой здоровый бэкенд. Предотвращает разрыв запросов при failover.

**Кворум** — минимальное количество узлов в распределенной системе (например, etcd), необходимое для принятия решений и поддержания консистентности данных. Для кластера etcd из N узлов кворум составляет `N/2 + 1`.

## Основные концепции

### Проблема единой точки отказа (SPOF)

В стандартной Kubernetes-установке с одним Control Plane узлом отказ этого узла приводит к:

1. **Полная недоступность API-сервера.** Все компоненты, взаимодействующие с API (kubelet, kube-proxy, scheduler, controller-manager, kube-dns, все пользовательские контроллеры), перестают функционировать.
2. **Невозможность управления жизненным циклом подов.** Deployment, StatefulSet, DaemonSet и другие контроллеры не могут реагировать на изменения (масштабирование, обновление, восстановление после сбоев).
3. **Работающие поды продолжают выполнение,** но контроллеры не смогут среагировать на их падение или изменение нагрузки.
4. **Через `node-monitor-grace-period`** (по умолчанию 40 секунд) узлы будут помечены как `NotReady`, и поды начнут выселяться на другие узлы (если есть куда).

> **Важно:** Worker-узлы с `kubelet` продолжают работать и выполнять контейнеры, но не могут получить обновления от Control Plane. Это критическое отличие от ситуации, когда выходит из строя один worker-узел — тогда затронуты только поды на этом узле.

**Каскадные эффекты при потере API-сервера:**
- kubelet не может обновлять статус подов и узлов.
- kube-proxy не может обновлять правила iptables/IPVS при изменении сервисов.
- Scheduler не может планировать новые поды.
- Controller-manager не может запускать replacement-поды при падении.
- etcd продолжает работать, но без API-сервера данные в нём «замораживаются».

**Решение:** Резервирование Control Plane через VIP и балансировщик.

### Архитектура Kube-vip (Рекомендуемый метод)

Kube-vip объединяет функции управления VIP и балансировки трафика. Он мониторит состояние локального `kube-apiserver` и участвует в выборах лидера для владения VIP.

#### Сетевой поток (Kube-vip L2)
```text
КЛИЕНТ (kubectl) -> VIP:6443 -> [Node с VIP] -> Kube-vip (L4) -> Локальный apiserver:6443
                                                      |
                                                      +-> apiserver на других мастерах (proxy)
```

#### Режимы работы

| Режим | Механизм | Область применения |
| :--- | :--- | :--- |
| **Layer 2 (ARP)** | Gratuitous ARP для обновления ARP-таблиц в L2-сегменте | Среды с L2-связностью между узлами (большинство bare-metal) |
| **Layer 3 (BGP)** | Анонсирование маршрута через BGP-сессию с маршрутизатором | Среды с L3-связностью, нужны ECMP или маршрутизация через роутеры |

#### Особенности
- **Control Plane HA:** Kube-vip запускается как Static Pod до инициализации кластера. Порт по умолчанию: 6443.
- **Service LB:** Может работать как контроллер для `type: LoadBalancer` (заменяя MetalLB в простых конфигурациях) через переменные `kube_vip_services_vip` и `kube_vip_lb_class`.
- **Health Check:** Kube-vip проверяет доступность API-сервера через HTTP GET на `/healthz`. При недоступности локального API-сервера лидерство VIP теряется и VIP мигрирует на другой узел.
- **Leader Election:** Kube-vip использует стандартный механизм Leader Election Kubernetes (через ConfigMap или Lease) для определения активного узла.

### Архитектура Keepalived + HAProxy (Классический метод)

Традиционный подход, использующий системные демоны ОС. Для предотвращения конфликта портов Kubespray использует схему с разделением портов:

*   **HAProxy:** слушает на порту `6443` (внешний порт API).
*   **Kube-apiserver:** слушает на порту `6444` (реальный порт).

#### Сетевой поток
```text
КЛИЕНТ -> VIP:6443 (Keepalived) -> HAProxy Node1:6443 -> HAProxy (L4 Balance) 
                                       |--> Master1:6444 (apiserver)
                                       |--> Master2:6444 (apiserver)
                                       |--> Master3:6444 (apiserver)
```

#### Особенности
- **Keepalived:** реализует VRRP, обеспечивая отказоустойчивость самого балансировщика. Управляет VIP и исключением нездоровых бэкендов.
- **HAProxy:** выполняет глубокую проверку здоровья (Health Check) API-серверов через HTTP GET на `https://<backend>:6444/healthz` с интервалом `option httpchk`.
- **ip_nonlocal_bind:** На BACKUP-узлах HAProxy привязывается к VIP (который назначен на MASTER). Требуется `net.ipv4.ip_nonlocal_bind = 1` (настраивается Kubespray через sysctl).
- **Connection Draining:** При переключении VIP активные соединения плавно завершаются через `timeout server` и `option redispatch`.

### Архитектура Nginx-proxy (Локальный балансировщик)

Этот механизм обеспечивает внутреннюю связность кластера (`kubelet` -> `apiserver`) и является резервным методом.

*   На каждом **worker-узле** и **мастер-узле** запускается контейнер `nginx-proxy`.
*   Все локальные компоненты настроены на обращение к `https://localhost:6443`.
*   Nginx балансирует эти запросы ко всем мастерам из списка в инвентаре.

#### Сетевой поток
```text
Worker: Kubelet -> localhost:6443 -> nginx-proxy -> [Master1:6443, Master2:6443, ...]
```
Это решение позволяет кластеру сохранять работоспособность, даже если внешний VIP недоступен. Однако оно **не** обеспечивает внешнюю доступность API-сервера для `kubectl` и CI/CD.

### VRRP: конечный автомат и состояния

Keepalived реализует конечный автомат VRRP с тремя состояниями:

```text
              ┌─────────────┐
              │   MASTER    │  Узел владеет VIP, обрабатывает трафик
              └──────┬──────┘
                     │ Отказ / Снижение приоритета
                     ▼
              ┌─────────────┐
              │   BACKUP    │  Узел в режиме ожидания, мониторит MASTER
              └──────┬──────┘
                     │ Все MASTER недоступны
                     ▼
              ┌─────────────┐
              │   FAULT     │  Узел некондиционен, не участвует в выборах
              └─────────────┘
```

| Состояние | Описание | Поведение |
| :--- | :--- | :--- |
| **MASTER** | Узел владеет VIP, принимает и обрабатывает трафик | Рассылает VRRP-объявления каждые `advert_int` (по умолчанию 1 сек). Проверяет здоровье локальных сервисов. |
| **BACKUP** | Узел ожидает, мониторит MASTER по VRRP-объявлениям | Не рассылает объявления. При превышении `dead_master_down` (3 × `advert_int` + Skew Time) инициирует выборы. |
| **FAULT** | Узел некондиционен (сбой Health Check, потеря сети) | Не участвует в выборах VIP. Вернётся в BACKUP после восстановления. |

**Приоритеты:** Каждому узлу назначается приоритет (1–254). Узел с наивысшим приоритетом становится MASTER при старте. При `nopreempt=true` восстановившийся узел с более высоким приоритетом НЕ отбирает VIP обратно — это рекомендуемый режим для Kubernetes.

**Skew Time:** Дополнительное время (по умолчанию 0 сек), добавляемое к времени ожидания перед выборами. Позволяет быстрее стартующим узелам не захватить VIP раньше стабильных.

### Health Checks в Kubespray

#### HAProxy Health Checks

HAProxy выполняет активные HTTP-проверки состояния каждого API-сервера:

```
# Схема проверки
HAProxy --[GET /healthz]--> Master1:6444
                          --[GET /healthz]--> Master2:6444
                          --[GET /healthz]--> Master3:6444
```

- **Интервал проверки:** по умолчанию 2 секунды (`inter 2000`).
- **Таймаут:** по умолчанию 1 секунда (`timeout check 1000`).
- **Порог:** после 3 последовательных неудачных проверок бэкенд помечается как DOWN (`fall 3`).
- **Восстановление:** после 2 последовательных успешных проверок бэкенд помечается как UP (`rise 2`).

**Фильтрация по HTTP-статусу:** HAProxy проверяет HTTP-код ответа. Допустимые коды: `200`, `204`. Любой другой код или отсутствие ответа = бэкенд DOWN.

#### Keepalived Health Checks

Keepalived может запускать собственные скрипты проверки здоровья:

```bash
# Пример скрипта проверки HAProxy
vrrp_script check_haproxy {
    script "/usr/bin/killall -0 haproxy"
    interval 2
    weight -20
    fall 3
    rise 2
}
```

- При падении проверки HAProxy, Keepalived снижает приоритет узла на `weight` (в данном случае на 20).
- Если приоритет падает ниже порогового, VIP мигрирует на BACKUP-узел.
- Скрипт также может проверять доступность API-сервера напрямую.

#### Kube-vip Health Checks

Kube-vip проверяет локальный API-сервер через HTTP GET на `/healthz`:

- **Интервал:** по умолчанию 2 секунды.
- **Порог:** после 3 неудачных проверок лидерство теряется.
- При недоступности локального API-сервера Kube-vip инициирует переключение VIP на другой узел через Leader Election.

### Сравнение методов балансировки

| Характеристика | Kube-vip | Keepalived + HAProxy | Nginx-proxy (local) |
| :--- | :--- | :--- | :--- |
| **Рекомендуемая среда** | Bare-metal / On-prem | Enterprise Bare-metal | Тесты / Edge |
| **Единый VIP** | Да | Да | Нет |
| **Тип балансировки** | L4 (TCP) | L4 (TCP) | L4 (TCP) |
| **Health Check** | HTTP /healthz | HTTP /healthz (HAProxy) + VRRP (Keepalived) | Passively (TCP connect) |
| **Connection Draining** | Да (при leader switch) | Да (option redispatch) | Нет |
| **Сложность настройки** | Низкая | Средняя | Минимальная |
| **Тип запуска** | Static Pod (K8s) | Системный сервис (Systemd) или Static Pod | Контейнер (Containerd) |
| **Зависимости** | Нет | Требует настройки ip_nonlocal_bind | Только Container Runtime |
| **Split-brain защита** | Leader Election (K8s) | VRRP Priorities + Health Checks | Отсутствует |
| **BFD поддержка** | Нет (через BGP) | Да (Keepalived) | Нет |
| **Unicast поддержка** | Да (BGP) | Да (keepalived_unicast_peers) | Нет |
| **Внешняя доступность** | Да | Да | Нет (только локально) |

## Кворум и etcd

Отказоустойчивость Kubernetes напрямую зависит от состояния базы данных etcd. Kubespray по умолчанию разворачивает etcd в режиме стекированной (stacked) топологии на всех мастер-узлах.

### Математика отказоустойчивости

| Кол-во узлов etcd | Кворум (n/2 + 1) | Допустимый отказ узлов | Примечание |
| :--- | :--- | :--- | :--- |
| **1** | 1 | 0 | Нет HA. Только для тестов / Edge (k3s). |
| **3** | 2 | 1 | Минимальный Production. Стандарт для большинства кластеров. |
| **5** | 3 | 2 | Высокая надежность для крупных кластеров. |
| **7** | 4 | 3 | Максимум. Далее растёт латентность записи (RTT между узлами). |

> **Важно:** Увеличение числа узлов НЕ повышает производительность на запись — наоборот, каждая запись требует подтверждения от кворума (большинства), поэтому больше узлов = больше сетевых RTT и выше латентность. Ключевой вопрос — «сколько узлов кластер может позволить себе потерять одновременно»; обычно 3–5 узлов и есть оптимум.

**Почему нечётное число:** Чётный кластер из N узлов даёт ту же отказоустойчивость, что и N−1 (потеря 2 узлов из 4 = потеря кворума), но требует больше ресурсов и рискует «расколоться» на две равные половины без гарантированного кворума.

### Механизм консенсуса (Raft)
1.  **Выборы лидера:** При потере лидера узлы инициируют новые выборы. Узел с наивысшим индексом последней записи становится кандидатом.
2.  **Репликация логов:** Лидер рассылает записи (log entries) остальным узлам. Запись считается подтвержденной только после записи на большинство (кворум) узлов.
3.  **Сплит-брейн:** Если сеть разделяется, только сегмент с кворумом (большинством) продолжает принимать записи. Сегмент в меньшинстве переходит в режим Read-Only или блокируется.

Детальные инструкции по восстановлению при потере кворума см. в [Восстановлении etcd](../../../../etcd/clustering_and_recovery.md).

### Топологии размещения etcd

| Топология | Описание | Рекомендация |
| :--- | :--- | :--- |
| **Stacked (Совмещённый)** | etcd запускается на тех же узлах, что и Control Plane. Стандарт для Kubespray. | Малые и средние кластеры. Простота развертывания. |
| **External (Выделенный)** | etcd вынесен на отдельные узлы. Максимальная изоляция и производительность. | Крупные кластеры с высокой нагрузкой на запись. |

## Практические сценарии

### Верификация архитектуры HA после развертывания

После развертывания кластера Kubespray выполните проверку всех слоёв HA:

#### 1. Проверка VIP

```bash
# Определение узла-владельца VIP
ip a show <interface> | grep <VIP_ADDRESS>
# → inet 192.168.1.100/32 scope global eth0

# Проверка доступности API через VIP
curl -sk https://<VIP>:6443/healthz
# → ok

# Проверка Kubernetes API
kubectl cluster-info
# → Kubernetes control plane is running at https://<VIP>:6443
```

#### 2. Проверка HAProxy (при Keepalived + HAProxy)

```bash
# Статус бэкендов
```

### Edge Cases и особенности

#### Split-brain (раскол мозга)

Split-brain — критическое состояние, при котором из-за сетевой изоляции два или более узла одновременно объявляют себя владельцами VIP.

**Причины:**
- Multicast-пакеты VRRP не доходят до части узлов.
- `virtual_router_id` различается на MASTER и BACKUP.
- Firewall блокирует протокол VRRP (IP-протокол 112).

**Защитные механизмы:**
- **VRRP Priorities:** Только узел с наивысшим приоритетом становится MASTER.
- **Health Checks:** Keepalived исключает нездоровые узлы из балансировки.
- **Leader Election (Kube-vip):** Стандартный механизм Kubernetes сетсямой гарантирует唯一 лидера.
- **Unicast:** Убирает зависимость от Multicast.

**Диагностика:**
```bash
# Проверка ARP-таблиц
arp -n | grep <VIP>
# → ? (192.168.1.100) at <MAC> on eth0  [ether] on eth0
# Если MAC-адреса различаются на разных узлах — split-brain

# Проверка VRRP-трафика
tcpdump -i any proto 112 -c 20
# → VRRP advertisement от master-1
# → VRRP advertisement от master-2  ← проблема
```

#### Конфликт портов API-сервера

При использовании Keepalived + HAProxy Kubespray разделяет порты:
- HAProxy: `6443` (внешний)
- kube-apiserver: `6444` (реальный)

При использовании Kube-vip:
- Kube-vip: `6443` (внешний)
- kube-apiserver: `6443` (тот же порт, Kube-vip проксирует)

**Риск:** Если одновременно активны Keepalived и Kube-vip на одном узле, возникает конфликт порта 6443. Kubespray автоматически предотвращает это через переменные `enable_keepalived` и `kube_vip_enabled` (только один метод активен).

#### Конфликт virtual_router_id

Если в одной L2-сегменте работают несколько групп Keepalived (например, для K8s API и для Ingress), `virtual_router_id` должны различаться. Иначе VRRP-объявления от одной группы будут «слышать» узлы другой, что приведёт к конфликтам.

**Решение:** Используйте разные `virtual_router_id` (например, 51 для API, 52 для Ingress).

#### Dual-stack (IPv4 + IPv6)

При использовании dual-stack кластера VIP должен быть назначен на стек, который используется для внутренней связи. Убедитесь, что `kube_vip_address` указан для нужного стека, и что VRRP/BGP работает для этого стека.
