# Kubespray: Развертывание HA-кластера — Основные концепции

## Определения

**HA-кластер (High Availability)** — архитектура Kubernetes с несколькими узлами Control Plane, обеспечивающая доступность API-сервера при выходе из строя одного или нескольких мастеров.

**VIP (Virtual IP)** — плавающий IP-адрес, обеспечивающий единую точку входа для клиентов (kubectl, CI/CD). Управляется через механизмы VRRP или ARP/BGP.

**Kube-vip** — современное cloud-native решение для организации VIP и балансировки нагрузки, работающее в виде Static Pod. Является рекомендуемым методом для bare-metal инсталляций в Kubespray.

**Nginx-proxy (Local LB)** — механизм Kubespray, разворачивающий локальный балансировщик на каждом worker-узле для связи с API-серверами мастеров.

---

## Основные концепции

### 1. Архитектура через Kube-vip (Рекомендуемый метод)

Kube-vip объединяет функции управления VIP и балансировки трафика. Он мониторит состояние локального `kube-apiserver` и участвует в выборах лидера для владения VIP.

```
                    ┌─────────────────┐
                    │      VIP        │
                    │  192.168.1.100  │
                    └────────┬────────┘
                             │
              ┌──────────────┼──────────────┐
              │              │              │
     ┌────────▼───────┐ ┌───▼────────┐ ┌───▼────────┐
     │   Master-1     │ │  Master-2  │ │  Master-3  │
     │  Kube-vip      │ │  Kube-vip  │ │  Kube-vip  │
     │  (LEADER)      │ │  (FOLLOWER)│ │  (FOLLOWER)│
     │ apiserver:6443 │ │apiserver:6443│ │apiserver:6443│
     └────────────────┘ └────────────┘ └────────────┘
```

#### Технические особенности
- **Режимы работы:** Layer 2 (ARP/ndp) для одной подсети или Layer 3 (BGP) для маршрутизируемых сетей.
- **Control Plane HA:** Автоматически настраивается Kubespray через Static Pods.
- **Service LB:** Kube-vip может также выступать в роли контроллера для сервисов типа `LoadBalancer`.

### 2. Архитектура через Keepalived + HAProxy (Классический метод)

Традиционный подход, использующий системные демоны ОС на каждом мастер-узле.

- **Keepalived:** реализует протокол VRRP для переключения VIP.
- **HAProxy:** принимает трафик на порту 6443 и балансирует его между API-серверами на порту 6444.

Этот метод считается более тяжеловесным в настройке, но проверен годами в Enterprise-средах.

### 3. Локальный балансировщик (nginx-proxy)

Используется по умолчанию в Kubespray для обеспечения внутренней связности кластера.

- На каждом **worker-узле** запускается контейнер `nginx-proxy`.
- Компоненты узла (kubelet, kube-proxy) обращаются к `localhost:6443`.
- Nginx балансирует эти запросы ко всем мастерам из списка.
- **Ограничение:** Не обеспечивает единый внешний IP для управления кластером извне.

---

### Сравнение методов балансировки

| Характеристика | Kube-vip | Keepalived + HAProxy | Nginx-proxy (local) |
| :--- | :--- | :--- | :--- |
| **Рекомендуемая среда** | Bare-metal / On-prem | Enterprise Bare-metal | Тесты / Edge |
| **Единый VIP** | Да | Да | Нет |
| **Сложность настройки** | Низкая | Средняя | Минимальная |
| **Тип запуска** | Static Pod (K8s) | Системный сервис (Systemd) | Контейнер (Containerd) |
| **Зависимости** | Нет | Требует настройки в ОС | Только Container Runtime |

### Кворум и etcd

Отказоустойчивость Control Plane неразрывно связана с состоянием etcd.
- Минимальное количество узлов для HA: **3**.
- Допустимый отказ: `(n-1)/2`. Для 3 узлов — отказ 1, для 5 — отказ 2.
- Детальные механизмы обеспечения консенсуса описаны в [Кластеризация и восстановление etcd](../../../etcd/clustering_and_recovery.md).
