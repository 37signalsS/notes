# Kubespray: Развертывание HA-кластера — Основные концепции

## Определения

**HA-кластер (High Availability)** — конфигурация Kubernetes с несколькими узлами Control Plane (обычно 3, 5 или более), предназначенная для устранения единой точки отказа (SPoF) и обеспечения непрерывной работы API-сервера и etcd.

**VIP (Virtual IP)** — плавающий IP-адрес, обеспечивающий единую точку входа для клиентов (kubectl, CI/CD). Управляется через механизмы VRRP (L2) или BGP (L3).

**Kube-vip** — cloud-native решение для организации VIP и балансировки нагрузки, работающее в виде Static Pod. Рекомендуемый современный метод для bare-metal инсталляций в Kubespray.

**Nginx-proxy (Local LB)** — "safety net" механизм Kubespray. Представляет собой локальный балансировщик на каждом узле кластера, который перенаправляет запросы к API-серверу на группу мастеров.

**Кворум** — минимальное количество узлов в распределенной системе (например, etcd), необходимое для принятия решений и поддержания консистентности данных.

## Основные концепции

Kubespray реализует "stacked" архитектуру HA, где компоненты Control Plane и etcd размещаются на одних и тех же узлах.

### 1. Архитектура через Kube-vip (Рекомендуемый метод)

Kube-vip объединяет функции управления VIP и балансировки трафика. Он мониторит состояние локального `kube-apiserver` и участвует в выборах лидера для владения VIP.

#### Сетевой поток (Kube-vip L2)
```text
КЛИЕНТ (kubectl) -> VIP:6443 -> [Node с VIP] -> Kube-vip (L4) -> Локальный apiserver:6443
```
*   **Layer 2 (ARP):** Лидер отправляет Gratuitous ARP пакеты, чтобы объявить себя владельцем VIP в подсети.
*   **Layer 3 (BGP):** Лидер анонсирует маршрут к VIP через BGP-сессию с сетевым оборудованием.

#### Технические особенности
- **Control Plane HA:** Kube-vip запускается как Static Pod до инициализации кластера.
- **Service LB:** Может работать как контроллер для `type: LoadBalancer` (заменяя MetalLB в простых конфигурациях).

### 2. Архитектура через Keepalived + HAProxy (Классический метод)

Традиционный подход, использующий системные демоны ОС. Для предотвращения конфликта портов Kubespray часто использует схему с разделением портов:

*   **HAProxy:** слушает на порту `6443` (внешний порт API).
*   **Kube-apiserver:** слушает на порту `6444` (реальный порт).

#### Сетевой поток
```text
КЛИЕНТ -> VIP:6443 (Keepalived) -> HAProxy Node1:6443 -> HAProxy (L4 Balance) 
                                       |--> Master1:6444 (apiserver)
                                       |--> Master2:6444 (apiserver)
                                       |--> Master3:6444 (apiserver)
```

#### Особенности
- **Keepalived:** реализует VRRP, обеспечивая отказоустойчивость самого балансировщика.
- **HAProxy:** выполняет глубокую проверку здоровья (Health Check) API-серверов.

### 3. Локальный балансировщик (nginx-proxy)

Этот механизм обеспечивает внутреннюю связность кластера (`kubelet` -> `apiserver`) и является резервным методом.

*   На каждом **worker-узле** и **мастер-узле** запускается контейнер `nginx-proxy`.
*   Все локальные компоненты настроены на обращение к `https://localhost:6443`.
*   Nginx балансирует эти запросы ко всем мастерам из списка в инвентаре.

#### Сетевой поток
```text
Worker: Kubelet -> localhost:6443 -> nginx-proxy -> [Master1:6443, Master2:6443, ...]
```
Это решение позволяет кластеру сохранять работоспособность, даже если внешний VIP недоступен.

---

### Сравнение методов балансировки

| Характеристика | Kube-vip | Keepalived + HAProxy | Nginx-proxy (local) |
| :--- | :--- | :--- | :--- |
| **Рекомендуемая среда** | Bare-metal / On-prem | Enterprise Bare-metal | Тесты / Edge |
| **Единый VIP** | Да | Да | Нет |
| **Сложность настройки** | Низкая | Средняя | Минимальная |
| **Тип запуска** | Static Pod (K8s) | Системный сервис (Systemd) | Контейнер (Containerd) |
| **Зависимости** | Нет | Требует настройки в ОС | Только Container Runtime |

## Кворум и etcd

Отказоустойчивость Kubernetes напрямую зависит от состояния базы данных etcd. Kubespray по умолчанию разворачивает etcd в режиме кластера на всех мастер-узлах.

### Математика отказоустойчивости

| Кол-во узлов etcd | Кворум (n/2 + 1) | Допустимый отказ узлов | Примечание |
| :--- | :--- | :--- | :--- |
| **1** | 1 | 0 | Нет HA |
| **3** | 2 | 1 | Минимальный Production |
| **5** | 3 | 2 | Высокая надежность |
| **7** | 4 | 3 | Редкость (растет latency на запись) |

### Механизм консенсуса (Raft)
1.  **Выборы лидера:** При потере лидера узлы инициируют новые выборы.
2.  **Репликация логов:** Лидер рассылает записи остальным узлам. Запись считается подтвержденной только после записи на большинство (кворум) узлов.
3.  **Сплит-брейн:** Если сеть разделяется, только сегмент с кворумом (большинством) продолжает принимать записи. Сегмент в меньшинстве переходит в режим Read-Only или блокируется.

Детальные инструкции по восстановлению при потере кворума см. в [Восстановление etcd](../../../../etcd/clustering_and_recovery.md).
