# Высокая доступность API-сервера с Keepalived и HAProxy

## Определения

**HA Control Plane (Отказоустойчивый узел управления)** — архитектура кластера с 3+ мастер-узлами, обеспечивающая непрерывную работу API-сервера при выходе из строя отдельных серверов.

**Virtual IP (VIP)** — виртуальный IP-адрес, который не привязан к конкретному физическому интерфейсу и может динамически перемещаться между узлами кластера.

**VRRP (Virtual Router Redundancy Protocol)** — сетевой протокол, используемый для автоматического назначения VIP активному узлу и обнаружения сбоев.

**Control Plane Endpoint** — стабильный адрес (DNS или VIP:Port), который используется всеми компонентами кластера (`kubelet`, `kube-proxy`, `scheduler`) и администраторами (`kubectl`) для взаимодействия с API.

**Stacked etcd** — топология, при которой распределенное хранилище `etcd` запускается на тех же узлах, что и компоненты Control Plane. Это стандартная схема для `kubeadm`.

**External etcd** — топология с выносом `etcd` на отдельную группу выделенных узлов для максимальной изоляции и производительности.

**ip_nonlocal_bind** — параметр ядра Linux, позволяющий процессам (например, HAProxy) привязываться к IP-адресам, которые еще не назначены интерфейсу (критично для запуска HAProxy на BACKUP-узлах).

## Основные концепции

### Проблема единой точки отказа (SPOF)

В стандартной установке с одним мастером отказ этого узла приводит к:
- Прекращению обработки всех API-запросов.
- Невозможности управления жизненным циклом подов и сервисов.
*   **Важно**: Работающие поды продолжат выполнение, но контроллеры (например, Deployment) не смогут среагировать на их падение или изменение нагрузки.

### Архитектура VIP + HAProxy

В bare-metal окружениях без внешнего облачного балансировщика используется связка Keepalived и HAProxy, развернутая непосредственно на мастер-узлах.

#### Путь трафика (Traffic Flow)
1.  **Клиент (kubectl/kubelet)** обращается к `https://<VIP>:7443`.
2.  **Keepalived** направляет пакет на узел, владеющий VIP в данный момент.
3.  **HAProxy** принимает TCP-соединение на порту 7443.
4.  **Балансировщик** проверяет состояние локального и удаленных `kube-apiserver` (порт 6443).
5.  **Трафик** пересылается на один из "здоровых" бэкендов.

### Топологии и Кворум

Для обеспечения отказоустойчивости необходимо нечетное количество узлов Control Plane (минимум 3). Это связано с алгоритмом консенсуса **Raft**, который использует `etcd`.

| Количество узлов | Допустимые отказы | Примечание |
| :--- | :--- | :--- |
| 1 | 0 | SPOF |
| 3 | 1 | Оптимально для большинства систем |
| 5 | 2 | Высокая надежность для крупных инсталляций |

#### Сравнение топологий etcd
- **Stacked (Совмещенная)**: Проще в развертывании и обслуживании. Требует меньше ресурсов (серверов).
- **External (Внешняя)**: Выше изоляция. Отказ всех мастеров не приводит к потере данных `etcd`. Рекомендуется для критических нагрузок.

## Практические сценарии

### 1. Настройка ядра для HA-режима

Для стабильной работы балансировщиков на всех узлах необходимо разрешить привязку к нелокальным адресам:

```bash
# Проверка текущего значения
sysctl net.ipv4.ip_nonlocal_bind

# Включение параметра
echo "net.ipv4.ip_nonlocal_bind = 1" >> /etc/sysctl.d/ha_k8s.conf
sysctl -p /etc/sysctl.d/ha_k8s.conf
```

### 2. Механизм Health Checks в HAProxy

HAProxy должен интеллектуально проверять статус API-сервера. Использование простого TCP-чека недостаточно, так как процесс может слушать порт, но быть в состоянии "зависания".
Рекомендуется использовать HTTP-проверку эндпоинта `/healthz` или `/readyz`:

```haproxy
backend k8s-api
    mode tcp
    option httpchk GET /healthz
    http-check expect status 200
    server master1 192.168.1.11:6443 check check-ssl verify none
    server master2 192.168.1.12:6443 check check-ssl verify none
    server master3 192.168.1.13:6443 check check-ssl verify none
```

### 3. Тестирование отказа (Failover)

Сценарий частичного отказа:
- **Ситуация**: `kube-apiserver` на MASTER-узле упал, но сам узел и Keepalived работают.
- **Ожидаемое поведение**: HAProxy должен обнаружить падение бэкенда через Health Check и перенаправить трафик на другой мастер, даже если VIP остался на текущем узле.

### 4. Альтернатива: kube-vip

В современных инсталляциях всё чаще используется **kube-vip** вместо связки Keepalived+HAProxy.
- **Плюсы**: Работает как статический под внутри Kubernetes, не требует настройки внешних сервисов на ОС, поддерживает BGP.
- **Минусы**: Сложнее в отладке при проблемах с сетью самого Kubernetes.

## Дополнительная информация

### Диагностика состояния HA

| Команда | Описание |
| :--- | :--- |
| `ip addr show | grep -E 'inet|vip'` | Проверка владельца VIP адреса |
| `ss -tulpn | grep -E '6443|7443'` | Проверка прослушивания портов API и балансировщика |
| `journalctl -u keepalived -n 50` | Просмотр последних событий VRRP (переходы Master/Backup) |
| `echo "show stat" | socat /var/run/haproxy.sock stdio` | Получение статистики HAProxy через сокет |

### Типичные ошибки конфигурации

1.  **Конфликт идентификаторов**: Использование одинакового `virtual_router_id` для разных кластеров в одной L2-сети.
2.  **MTU mismatch**: VRRP пакеты могут отбрасываться, если MTU на интерфейсах различается.
3.  **Firewall**: Блокировка протокола VRRP (IP protocol 112) или Multicast/Unicast трафика между узлами.
