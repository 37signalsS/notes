# High Availability API-сервера с Keepalived и HAProxy

## Определения

**HA Control Plane** — отказоустойчивая архитектура с несколькими мастер-узлами для устранения единой точки отказа (SPOF).

**Virtual IP (VIP)** — плавающий IP-адрес, перемещающийся между узлами кластера через протокол VRRP.

**Control Plane Endpoint** — стабильная точка входа для доступа к API-серверу (`<VIP>:<PORT>` или DNS-имя).

**L4 Load Balancer** — балансировщик транспортного уровня (TCP), который перенаправляет трафик без терминирования TLS-соединения.

**VRRP (Virtual Router Redundancy Protocol)** — сетевой протокол для автоматического переключения VIP между узлами в случае сбоя.

---

## Основные концепции

### Проблема единой точки отказа (SPOF)

В кластере с одним мастер-узлом при его выходе из строя:
- Управление кластером через API становится невозможным.
- `kubelet` на воркерах не может получать новые инструкции.
- Невозможно добавить новые узлы через `kubeadm join`.
- Автоматическое восстановление подов при сбоях воркеров прекращается.

### Решение: VIP + L4-балансировщик

Схема взаимодействия компонентов:

```text
                    ┌─────────────────────────────────────────┐
                    │           Virtual IP (VIP)              │
                    │         192.168.122.189:7443            │
                    └─────────────────────────────────────────┘
                                      │
                    ┌─────────────────┼─────────────────┐
                    │                 │                 │
              ┌─────▼─────┐   ┌──────▼──────┐   ┌──────▼──────┐
              │ Keepalived│   │ Keepalived  │   │ Keepalived  │
              │  MASTER   │   │   BACKUP    │   │   BACKUP    │
              │           │   │             │   │             │
              │  HAProxy  │   │   HAProxy   │   │   HAProxy   │
              │           │   │             │   │             │
              │ API:6443  │   │  API:6443   │   │  API:6443   │
              └───────────┘   └─────────────┘   └─────────────┘
```

**Принцип работы:**
1. **Keepalived** поддерживает доступность VIP. Узлы обмениваются сообщениями (heartbeat), и при падении MASTER-узла роль переходит к BACKUP с наивысшим приоритетом.
2. **HAProxy** принимает запросы на VIP:7443 и распределяет их между локальными инстансами `kube-apiserver` (порт 6443).
3. Приложение (kubectl или kubelet) видит только один стабильный адрес.

### Архитектурные требования

| Компонент | Требование | Примечание |
| :--- | :--- | :--- |
| **Количество мастеров** | 3, 5 или более | Нечётное число необходимо для обеспечения кворума etcd |
| **Режим балансировки** | TCP Mode (Layer 4) | API Server сам управляет TLS, балансировщик только пробрасывает пакеты |
| **Порты** | 6443 (API), 7443 (VIP) | Порт VIP должен отличаться, если балансировщик на тех же узлах |
| **Сетевая связность** | Unicast VRRP | Рекомендуется для production и облачных сред, где Multicast запрещен |

## Практические сценарии

### Проверка состояния отказоустойчивости

Для диагностики текущего состояния VIP и балансировщика используются следующие инструменты:

```bash
# Проверка наличия VIP на интерфейсе (выполнять на всех узлах)
ip addr show | grep <VIP>

# Просмотр логов переключения (failover)
journalctl -u keepalived -f

# Проверка конфигурации HAProxy перед перезапуском
haproxy -c -f /etc/haproxy/haproxy.cfg
```

### Тестирование переключения (Failover Test)

Критически важная процедура для проверки готовности кластера к авариям:
1. Запустите мониторинг API: `watch kubectl get nodes`.
2. Остановите Keepalived на мастере: `sudo systemctl stop keepalived`.
3. Убедитесь, что VIP появился на другом узле через 1-2 секунды.
4. Проверьте, что `kubectl` продолжает возвращать данные без ошибок (возможна задержка в пару секунд).

### Типичные проблемы и решения

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| VIP висит на двух узлах одновременно | Split-brain (проблемы с сетью) | Проверить прохождение VRRP трафика (порт 112) |
| HAProxy выдает 503 Service Unavailable | Все мастера в статусе Down | Проверить health checks и доступность порта 6443 |
| Медленное обнаружение сбоя | Высокий интервал heartbeat | Уменьшить `advert_int` в конфигурации Keepalived |

## Дополнительная информация

### Рекомендации по эксплуатации

- **Мониторинг**: Обязательно настройте алертинг на смену роли MASTER -> BACKUP.
- **Изоляция**: По возможности используйте выделенную сеть для heartbeat-трафика.
- **Обновления**: Обновляйте балансировщики по очереди, начиная с BACKUP-узлов.
