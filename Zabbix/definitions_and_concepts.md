# Zabbix — определения и основные концепции

> **Актуальность:** материал сверен по состоянию на август 2026 г. Основная долгосрочная ветка — **Zabbix 7.0 LTS** (обновления до 30 июня 2027, ограниченная поддержка до 30 июня 2029). Текущая стандартная ветка — **Zabbix 7.4** (выпущена 30 июня 2025). Ожидается выход **Zabbix 8.0 LTS** в Q3 2026 (сентябрь). Особенности конкретных версий отмечены по тексту.

## Определения

*   **Zabbix** — свободная, масштабируемая система мониторинга ИТ-инфраструктур с открытым исходным кодом (лицензия AGPL v3, бесплатна для коммерческого и некоммерческого использования). Предназначена для отслеживания состояния серверов, сетевого оборудования, приложений и веб-сервисов в режиме реального времени.
*   **Метрика (Metric)** — числовое значение, изменяющееся во времени (например, загрузка CPU, свободное место на диске, количество запросов в секунду).
*   **Элемент данных (Item / Айтем)** — конкретный настроенный сборщик определенной метрики (например, «загрузка CPU на сервере №5»).
*   **Триггер (Trigger)** — логическое выражение (условие), которое определяет, является ли собранное значение проблемой (например, «свободно менее 10% диска»).
*   **Событие (Event)** — атомарная запись об изменении состояния триггера (переход в Problem, возврат в OK/восстановление) либо о результатах корреляции событий. Именно на событиях строится вся дальнейшая обработка: оповещения и действия.
*   **Проблема (Problem)** — активное событие, созданное триггером при срабатывании Problem Expression. Проблема «открыта» до тех пор, пока не сработает Recovery Expression.
*   **Восстановление (Recovery)** — механизм перевода проблемы в состояние OK на основе отдельного Recovery Expression (опционально). Без восстановления события могут «висеть» в состоянии Problem бесконечно.
*   **Оповещение (Alert / Алёрт)** — уведомление человека о сработавшем триггере (Email, Telegram, звонок).
*   **Шаблон (Template)** — готовый набор элементов данных, триггеров, графиков, discovery-правил и макросов, который можно применить к множеству хостов одновременно, обеспечивая единообразие мониторинга.
*   **Хост (Host)** — мониторируемый объект (сервер, сетевое устройство, БД, приложение). Каждому хосту может быть назначен один или несколько шаблонов.
*   **Группа хостов (Host Group)** — логическая группировка хостов для управления правами доступа, оповещением и массовыми операциями.
*   **Интерфейс хоста (Host Interface)** — сетевые реквизиты хоста (IP/DNS-имя, порт, используемые типы: agent, SNMP, IPMI, JMX). Определяет, как именно Zabbix подключается к устройству.
*   **Макрос (Macro)** — параметризованное значение, позволяющие переопределять параметры без правки шаблона. Виды: пользовательские `{$MACRO}` (уровня шаблона/хоста), LLD-макросы `{#NAME}`, встроенные `{HOST.HOST}`, `{ITEM.VALUE}`; Expression-макросы `{?EXPR}`.
*   **Предобработка (Preprocessing)** — цепочка шагов трансформации данных после сбора и до записи: извлечение по JSONPath/регулярным выражениям, JS-обработка, расчет дельт, отбрасывание неизменных значений и др.
*   **Зависимость (Dependency)** — связь триггера: при срабатывании «родительского» триггера дочерние проблемы скрываются/оповещения подавляются для снижения шума (см. **[Лучшие практики настройки](./zabbix_best_practices.md)**).
*   **Тип носителя (Media Type)** — канал доставки оповещений: Email (SMTP), SMS-шлюзы, Webhook (Telegram, Slack, Jira и др.), скриптовые носители.
*   **Действие (Action)** — правило «условия → операции»: при срабатывании триггера отправляет оповещение через носитель (Media Type), назначает дежурного или уровень эскалации, выполняет Remote Command.
*   **История и тренды (History / Trends)** — двухуровневое хранение временных рядов: история — актуальные собранные значения (настраиваемое окно хранения), тренды — часовые агрегаты (min/avg/max) для долгосрочной аналитики и графиков за большой период.
*   **Zabbix Server** — центральное ядро («мозг») системы, отвечающее за сбор, обработку данных, вычисление триггеров и рассылку оповещений.
*   **Zabbix Proxy** — локальный сборщик данных, который опрашивает устройства от имени сервера. Используется для:
    *   Мониторинга удаленных локаций (филиалы, разные города).
    *   Снижения нагрузки на основной Zabbix Server.
    *   Обеспечения надежности сбора при нестабильной связи (прокси копит данные и отдает их серверу одним потоком при восстановлении связи).
    *   Изоляции сети мониторинга (proxy может быть расположен в периметре мониторинга без доступа к серверу в DMZ).
*   **Zabbix Agent** — программный демон, устанавливаемый на целевые хосты для сбора локальных метрик. Доступны две редакции: классический (на C) и **Agent 2** (на Go, стандарт по умолчанию).
*   **Zabbix Trapper** — механизм и тип элемента данных (Item), принимающий входящие данные на определенном TCP-порту (Push-модель).
*   **Безагентный мониторинг** — сбор данных без установки агента Zabbix (через SNMP, IPMI, JMX, HTTP, SSH/Telnet, TCP/UDP-порт). Всего доступно более 15 типов элементов данных и способов сбора.
*   **Синтетический мониторинг** — имитация действий пользователя (введено в Zabbix 7.0 через **Browser Items**).
*   **Низкоуровневое обнаружение (LLD)** — автоматическое обнаружение динамических сущностей (диски, интерфейсы) и создание элементов мониторинга для них по образцу. Подробно: **[Низкоуровневое обнаружение](./low_level_discovery.md)**.
*   **Плановое обслуживание (Maintenance)** — заранее заданный период, в течение которого оповещения для указанных хостов/групп подавляются, а события не порождают проблем, чтобы не создавать ненужных алертов при плановых работах.
*   **Инвентаризация (Inventory)** — хранилище метаданных о хосте (сертификат, ОС, контактные данные), заполняется вручную или автоматически из метрик.

## Основные концепции

### Модель данных и жизненный цикл данных

Данные в Zabbix проходят сквозь цепочку, определяющую устройство всей системы:

```text
Хост (Host) → Элемент данных (Item) → История (History) → Тренды (Trends)
                                 ↕ Processing (Preprocessing)
Триггер (Trigger) → Событие (Event) → Проблема (Problem) → Действие (Action) → Оповещение
```

- **История (History)** — «горячие» актуальные значения (период удержания задается в конфигурации элемента данных, например 7–31 день). Объем этой таблицы определяет требования к диску и вводу-выводу.
- **Тренды (Trends)** — почасовые агрегированные значения, хранящиеся годы (по умолчанию 365 дней). Используются для долгосрочной визуализации и функций `avg()`, `trendavg()` и т.п.
- **Очистка (Housekeeping)** — регулярное удаление устаревших данных. Для больших инсталляций рекомендуется **TimescaleDB**, обеспечивающая партиционирование и сжатие (компрессия) таблиц истории/трендов. Подробнее о процессах и хранилище — **[Внутреннее устройство и процессы](./additional_info.md)**.

### Цикл мониторинга

Весь мониторинг в Zabbix можно свести к цепочке:

1.  **Собрали число** (Item / Metric).
2.  **Решили, что оно плохое** (Trigger → Event → Problem).
3.  **Позвали человека** (Action → Media → Alert).

### Ключевые возможности

* **Асинхронный сбор метрик:** Начиная с версии 7.0, процессы сбора данных (HTTP, SNMP, Agent) используют асинхронную архитектуру, позволяя одному процессу обрабатывать до 1000 параллельных проверок.
* **Продвинутая визуализация:** Построение графиков, дашбордов, гео-карт и карт сети. В 7.4 улучшены графики и виджеты (динамический редактор виджетов, палитры цветов).
* **Автоматизация и Remediation:** Возможность не только отправлять алерты (Telegram, Jira), но и выполнять скрипты автоматического восстановления при сбоях (Remote commands).
* **Отказоустойчивость (High Availability):** Нативная кластеризация для Server (с версии 6.0) и балансировка нагрузки и HA для Proxy (с версии 7.0).
* **Корреляция и подавление проблем:** Event Correlation и Problem Suppression (7.0+) снижают шум алертинга. Подробнее — **[Лучшие практики настройки](./zabbix_best_practices.md)**.
* **Безопасность по умолчанию:** поддержка TLS/PSK/certificates для всех каналов (агент, прокси, сервер), а в **7.4** — принудительный TLS для trapper (`TLSListen=required`) и шифрование соединения Frontend ↔ Server.

### Архитектура и компоненты

Современная инфраструктура Zabbix состоит из следующих компонентов:

#### Серверный стек

* **Zabbix Server:** Ядро системы. Может работать в режиме кластера **High Availability (HA)**, где активна одна нода (Active), а остальные находятся в горячем резерве (Standby). Автоматическое переключение активной ноды при отказе основной.
* **СУБД:** Хранилище конфигурации и истории (PostgreSQL или MySQL). Рекомендуется использовать **PostgreSQL + TimescaleDB** для автоматического партиционирования и сжатия временных рядов.
* **Frontend:** Веб-интерфейс на PHP для конфигурации и анализа данных.
* **Zabbix Web Service:** отдельный сервис (по умолчанию порт 10053), используется для выполнения Browser Items (Selenium) и рендеринга отчетов.
* **Java Gateway:** посредник для мониторинга приложений через **JMX**. Выступает промежуточным звеном между Zabbix Server и Java-агентами, агрегируя запросы и обеспечивая высокую масштабируемость.

#### Распределенный мониторинг (Proxy)

* **Zabbix Proxy:** Устанавливается в удаленных ЦОД или филиалах.
* **Proxy Groups (с версии 7.0):** Позволяет объединять прокси в группы для обеспечения **High Availability и балансировки нагрузки**. Если один прокси выходит из строя, хосты автоматически переключаются на другие доступные прокси в группе.
* **Memory Proxy Buffer:** Прокси могут работать в режиме *in-memory* (без локальной SQLite/MySQL базы), что значительно повышает производительность и срок службы дисков.

#### Агенты (Pull и Push)

Доступно две редакции агентов:

* **Zabbix Agent (Classic):** Написан на языке C. Отличается минимальным потреблением ресурсов памяти и CPU. Идеален для IoT и legacy-систем.
* **Zabbix Agent 2:** Написан на Go. Является стандартом по умолчанию. Поддерживает многопоточность, постоянные соединения с БД (connection pooling), **именованные сессии (Named Sessions)** для безопасного хранения учетных данных и расширяемые плагины (для мониторинга PostgreSQL, MySQL, Docker, Redis и т.д.).

### Модели сбора данных

Zabbix поддерживает гибридный подход:

* **Pull-модель (Пассивный режим):** Server или Proxy инициирует TCP-соединение и запрашивает метрику (Пассивный агент, SNMP). Создает предсказуемую сетевую нагрузку, но требует открытия портов на стороне клиента.
* **Push-модель (Активный режим):** Агент или внешняя система (через Trapper) самостоятельно подключается к серверу и передает данные. **Настоятельно рекомендуется** для масштабных инсталляций, так как перекладывает нагрузку по расписанию проверок на сами хосты и работает из-за NAT.
    * Дополнительное применение Push: отправка событий из внешних систем (например, Wazuh через `zabbix_sender` или API-метод `history.push` в 7.0+).

**Типы элементов данных.** Способ сбора определяет тип Item: `Zabbix agent` (пассивный/активный), `SNMP`, `IPMI`, `JMX`, `HTTP agent`, `trapper`, database monitor, `SSH`/`Telnet` скрипты, `external check`, `Browser` (7.0+) и др. Выбор типа напрямую влияет на сетевые требования и нагрузку — см. **[Выбор метода мониторинга](#выбор-метода-мониторинга)**.

### События, проблемы и восстановление

* **Серьезность (Severity):** классификация проблем — Critical / High / Average / Warning / Information / Disaster.
* **Тэги (Tags):** произвольные пары «ключ:значение», позволяют коррелировать инциденты и гибко маршрутизировать алерты. Рекомендуется применять иерархическую систему тегов (например, `component`, `target`, `scope`). Подробнее — **[Лучшие практики](./zabbix_best_practices.md)**.
* **Recovery Expression:** синтаксис восстановления может требовать явного перехода в OK (соответствие логике сработки).
* **Эскалация и ручные действия:** для важных проблем настраиваются этапы эскалации (каскады операций через заданные интервалы) и подтверждение acknowledgement — при неакцептованной проблеме она продолжает привлекать внимание в UI/дашбордах.
* **Event Correlation:** связывание связанных событий (например, «сервер недоступен» и «сервис недоступен») позволяет закрывать старые проблемы, не рассылая дублирующие алерты, и сохранять полную историю инцидента.
* **Problem Suppression (7.0+):** временно подавить оповещения по проблеме на заданный период (например, при плановой остановке или известном сбое).
* **Maintenance (плановое обслуживание):** глобальное подавление проблем и алертов для выбранных хостов на период работ; сработавшие триггеры в этом окне не порождают новых оповещений и проблем.

**Оповещения и автообслуживание.** Запустить оповещения могут: сработавший триггер (событие), восстановление, обнаружение проблемы и т.д. Операции бывают: отправка сообщения по каналу, закрытие другой проблемы, выполнение Remote Command (для автоматизации восстановления).

## Практические сценарии

### Выбор метода мониторинга

| Целевой объект | Рекомендуемый метод | Обоснование |
| :--- | :--- | :--- |
| **ОС (Linux/Windows)** | Zabbix Agent 2 (Active) | Поддержка плагинов, минимальная задержка (Push), безопасность (работа за NAT). |
| **Сетевое оборудование** | SNMP v2c / v3 (Async) | Индустриальный стандарт. Асинхронные поллеры обеспечивают высокую скорость опроса MIB-деревьев. |
| **Сложные веб-приложения (SPA)** | Browser Items (Selenium) | Позволяет авторизоваться, кликать по кнопкам и сохранять скриншоты (тип данных `Binary`) при ошибках. |
| **Базы данных (PostgreSQL/MySQL)** | Zabbix Agent 2 Plugin | Нативная реализация метрик без устаревших UserParameter-скриптов. См. **[Мониторинг БД](./zabbix_database_monitoring.md)**. |
| **Микросервисы / Serverless** | Zabbix Trapper / HTTP Agent | Метрики отправляются приложением напрямую в момент выполнения задачи (push). |

### Безопасность соединений (TLS)

Все компоненты поддерживают шифрование:

* **PSK (Pre-Shared Key):** простой способ, легко распространяется (используйте уникальные ключи на каждый хост).
* **Сертификаты (X.509):** строгая аутентификация по публичным/приватным CA; повышенное соответствие для больших инсталляций.
* В **7.4** добавлена возможность принудительного TLS (`TLSListen=required`) для trapper и выбор режима приема соединений Frontend (`TLSFrontendAccept=cert` | `unencrypted`).

### Автоматизация масштабирования

* **Network Discovery:** Сканирование IP-сетей и автоматическое добавление найденных устройств в мониторинг (на базе ответов портов или агента).
* **Auto-registration:** Механизм, при котором новый активный агент сам обращается к серверу, и сервер автоматически применяет к нему нужный шаблон и группу (на основе метаданных агента `HostMetadata`).
* **Low-Level Discovery (LLD):** обнаружение динамических компонентов *внутри* хоста; в **7.4** появилось вложенное (Nested) LLD — обнаружение в нескольких уровнях (например, «БД → таблицы»). Подробнее: **[Низкоуровневое обнаружение](./low_level_discovery.md)**.

### Сравнение с Prometheus

Zabbix и Prometheus предназначены для разных типов инфраструктур:

| Характеристика | Zabbix | Prometheus |
| :--- | :--- | :--- |
| **Инфраструктура** | Классическая (Bare-metal, VM, сеть) | Динамические облака (Kubernetes, контейнеры) |
| **Жизненный цикл хостов** | Статичный (машины живут годами) | Динамичный (машины живут секундами) |
| **Модель сбора** | Pull и Push (гибридная) | Pull (преимущественно) |
| **Хранение** | Реляционная СУБД (SQL) + TimescaleDB | Собственная TSDB (временные ряды) |
| **Компоненты** | Все в одном (Сбор, Хранение, Визуализация, Алертинг) | Модульная структура |

*Примечание: в современных развивающихся инфраструктурах обе системы часто сосуществуют, дополняя друг друга.*
