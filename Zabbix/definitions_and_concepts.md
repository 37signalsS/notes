# Zabbix — определения и основные концепции

> **Актуальность:** материал сверен по состоянию на сентябрь 2026 г. Основная долгосрочная ветка — **Zabbix 7.0 LTS** (обновления до 30 июня 2027, ограниченная поддержка до 30 июня 2029). Текущая стандартная ветка — **Zabbix 7.4** (выпущена 30 июня 2025). Ожидается выход **Zabbix 8.0 LTS** в Q3 2026 (сентябрь 2026); как на сентябрь 2026 г., версия находится в стадии beta (последний релиз — 8.0.0beta2, июль 2026). Особенности конкретных версий отмечены по тексту.

## Определения

*   **Zabbix** — свободная, масштабируемая система мониторинга ИТ-инфраструктур с открытым исходным кодом (лицензия AGPL v3, бесплатна для коммерческого и некоммерческого использования). Предназначена для отслеживания состояния серверов, сетевого оборудования, приложений и веб-сервисов в режиме реального времени.
*   **Метрика (Metric)** — числовое значение, изменяющееся во времени (например, загрузка CPU, свободное место на диске, количество запросов в секунду).
*   **Элемент данных (Item / Айтем)** — конкретный настроенный сборщик определенной метрики (например, «загрузка CPU на сервере №5»).
*   **Триггер (Trigger)** — логическое выражение (условие), которое определяет, является ли собранное значение проблемой (например, «свободно менее 10% диска»).
*   **Событие (Event)** — атомарная запись об изменении состояния триггера (переход в Problem, возврат в OK/восстановление) либо о результатах корреляции событий. Именно на событиях строится вся дальнейшая обработка: оповещения и действия.
*   **Проблема (Problem)** — активное событие, созданное триггером при срабатывании Problem Expression. Проблема «открыта» до тех пор, пока не сработает Recovery Expression.
*   **Восстановление (Recovery)** — механизм перевода проблемы в состояние OK на основе отдельного Recovery Expression (опционально). Без восстановления события могут «висеть» в состоянии Problem бесконечно.
*   **Оповещение (Alert / Алёрт)** — уведомление человека о сработавшем триггере (Email, Telegram, звонок).
*   **Шаблон (Template)** — готовый набор элементов данных, триггеров, графиков, discovery-правил и макросов, который можно применить к множеству хостов одновременно, обеспечивая единообразие мониторинга.
*   **Хост (Host)** — мониторируемый объект (сервер, сетевое устройство, БД, приложение). Каждому хосту может быть назначен один или несколько шаблонов.
*   **Группа хостов (Host Group)** — логическая группировка хостов для управления правами доступа, оповещением и массовыми операциями.
*   **Интерфейс хоста (Host Interface)** — сетевые реквизиты хоста (IP/DNS-имя, порт, используемые типы: agent, SNMP, IPMI, JMX). Определяет, как именно Zabbix подключается к устройству.
*   **Макрос (Macro)** — параметризованное значение, позволяющие переопределять параметры без правки шаблона. Виды: пользовательские `{$MACRO}` (уровня шаблона/хоста), LLD-макросы `{#NAME}`, встроенные `{HOST.HOST}`, `{ITEM.VALUE}`; Expression-макросы `{?EXPR}`.
*   **Предобработка (Preprocessing)** — цепочка шагов трансформации данных после сбора и до записи: извлечение по JSONPath/регулярным выражениям, JS-обработка, расчет дельт, отбрасывание неизменных значений и др.
*   **Зависимость (Dependency)** — связь триггера: при срабатывании «родительского» триггера дочерние проблемы скрываются/оповещения подавляются для снижения шума (см. **[Лучшие практики настройки](./zabbix_best_practices.md)**).
*   **Тип носителя (Media Type)** — канал доставки оповещений: Email (SMTP), SMS-шлюзы, Webhook (Telegram, Slack, Jira и др.), скриптовые носители.
*   **Действие (Action)** — правило «условия → операции»: при срабатывании триггера отправляет оповещение через носитель (Media Type), назначает дежурного или уровень эскалации, выполняет Remote Command.
*   **История и тренды (History / Trends)** — двухуровневое хранение временных рядов: история — актуальные собранные значения (настраиваемое окно хранения), тренды — часовые агрегаты (min/avg/max) для долгосрочной аналитики и графиков за большой период.
*   **Zabbix Server** — центральное ядро («мозг») системы, отвечающее за сбор, обработку данных, вычисление триггеров и рассылку оповещений.
*   **Zabbix Proxy** — локальный сборщик данных, который опрашивает устройства от имени сервера. Используется для мониторинга удаленных локаций, снижения нагрузки на основной сервер, обеспечения надежности сбора при нестабильной связи и изоляции сети мониторинга.
*   **Zabbix Agent** — программный демон, устанавливаемый на целевые хосты для сбора локальных метрик. Доступны две редакции: классический (на C) и **Agent 2** (на Go, стандарт по умолчанию).
*   **Zabbix Trapper** — механизм и тип элемента данных (Item), принимающий входящие данные на определенном TCP-порту (Push-модель).
*   **Безагентный мониторинг** — сбор данных без установки агента Zabbix (через SNMP, IPMI, JMX, HTTP, SSH/Telnet, TCP/UDP-порт). Всего доступно более 15 типов элементов данных и способов сбора.
*   **Синтетический мониторинг** — имитация действий пользователя (введено в Zabbix 7.0 через **Browser Items**).
*   **Низкоуровневое обнаружение (LLD)** — автоматическое обнаружение динамических сущностей (диски, интерфейсы) и создание элементов мониторинга для них по образцу. Подробно: **[Низкоуровневое обнаружение](./low_level_discovery.md)**.
*   **Плановое обслуживание (Maintenance)** — заранее заданный период, в течение которого оповещения для указанных хостов/групп подавляются, а события не порождают проблем, чтобы не создавать ненужных алертов при плановых работах.
*   **Инвентаризация (Inventory)** — хранилище метаданных о хосте (сертификат, ОС, контактные данные), заполняется вручную или автоматически из метрик.
*   **NVPS (New Values Per Second)** — количество новых значений, записываемых системой в базу данных за секунду; ключевой метрический показатель производительности мониторинга с точки зрения SRE.
*   **Очередь (Zabbix Queue)** — список элементов данных, чей опрос запаздывает относительно запланированного интервала; индикатор нехватки процессов сбора.
*   **Self-monitoring** — встроенный механизм сбора внутренних статистических данных сервера (нагрузка поллеров, объем очередей, утилизация кэшей).

## Основные концепции

### Модель данных и жизненный цикл данных

Данные в Zabbix проходят сквозной цепочку:

```text
Хост (Host) → Элемент данных (Item) → Предобработка (Preprocessing) → История (History) → Тренды (Trends)
                                  ↕ Processing
Триггер (Trigger) → Событие (Event) → Проблема (Problem) → Действие (Action) → Оповещение
```

- **История (History)** — «горячие» актуальные значения (период удержания задается в конфигурации, например 7–31 день). Объем этой таблицы определяет требования к диску и вводу-выводу.
- **Тренды (Trends)** — почасовые агрегированные значения (min/avg/max), хранящиеся годами. Используются для долгосрочной визуализации и функций `avg()`, `trendavg()` и т.п.
- **Очистка (Housekeeping)** — регулярное удаление устаревших данных. Для больших инсталляций рекомендуется **TimescaleDB**, обеспечивающая партиционирование и сжатие таблиц истории/трендов. Подробнее о процессах и хранилище — **[Внутреннее устройство и процессы](./additional_info.md)**.

### Цикл мониторинга

Весь мониторинг в Zabbix сводится к цепочке:

1.  **Собрали число** (Item / Metric).
2.  **Решили, что оно плохое** (Trigger → Event → Problem).
3.  **Позвали человека** (Action → Media → Alert).

### DevOps/SRE/Sysadmin контекст

Zabbix встроена в процессы эксплуатации ИТ-инфраструктур:

- **Monitoring as Code:** конфигурация мониторинга (шаблоны, хосты, триггеры) хранится в Git и развертывается через Zabbix API. Изменения проходят code review и применяются автоматически. Это исключает «дрейф конфигурации» и позволяет восстанавливать мониторинг за минуты.
- **Incident Management:** оповещения Zabbix интегрируются с ITSM-системами (Jira, GLPI) и дежурными сервисами (PagerDuty, OpsGenie). При срабатывании триггера автоматически создается тикет с контекстом (теги, оперативные данные), что сокращает время реакции.
- **SLI/SLO/SLA:** Zabbix 7.0+ поддерживает расчет SLA на основе тегов триггеров (Services → SLA). SRE используют эти данные для определения целевых показателей доступности и производительности.
- **Runbook Automation:** действия (Actions) могут выполнять не только оповещения, но и скрипты автоматического восстановления (Remote Commands). При срабатывании триггера Zabbix может автоматически перезапустить сервис, очистить место на диске или вызвать API оркестратора.
- **Post-mortem Analysis:** события и проблемы сохраняются с полным контекстом (теги, оперативные данные, временные метки). Это позволяет проводить постмортем-анализ инцидентов и выявлять системные причины.
- **Change Management:** все изменения в конфигурации мониторинга (новые триггеры, пороги) проходят через процедуры управления изменениями. Версионный контроль шаблонов в Git обеспечивает аудит и откат.
- **Capacity Planning:** внутренние метрики Zabbix (NVPS, очереди, утилизация кэшей) позволяют SRE планировать масштабирование инфраструктуры мониторинга до наступления проблем.
- **On-call Integration:** эскалация действий (Actions) поддерживает каскадную отправку оповещений: сначала дежурный, затем тимлид, затем руководство. Время эскалации и каналы доставки настраиваются отдельно для каждой серьезности.

### Ключевые возможности

* **Асинхронный сбор метрик:** Начиная с версии 7.0, процессы сбора данных (HTTP, SNMP, Agent) используют асинхронную архитектуру, позволяя одному процессу обрабатывать до 1000 параллельных проверок.
* **Продвинутая визуализация:** Построение графиков, дашбордов, гео-карт и карт сети. В 7.4 улучшены графики и виджеты (динамический редактор виджетов, палитры цветов).
* **Автоматизация и Remediation:** Возможность не только отправлять алерты, но и выполнять скрипты автоматического восстановления при сбоях (Remote commands).
* **Отказоустойчивость (High Availability):** Нативная кластеризация для Server (с версии 6.0) и балансировка нагрузки и HA для Proxy (с версии 7.0).
* **Корреляция и подавление проблем:** Event Correlation и Problem Suppression (7.0+) снижают шум алертинга. Подробнее — **[Лучшие практики настройки](./zabbix_best_practices.md)**.
* **Безопасность по умолчанию:** поддержка TLS/PSK/certificates для всех каналов (агент, прокси, сервер), а в 7.4 — принудительный TLS для trapper и шифрование соединения Frontend ↔ Server.

### Архитектура и компоненты

Современная инфраструктура Zabbix состоит из следующих компонентов:

#### Серверный стек

* **Zabbix Server:** Ядро системы. Может работать в режиме кластера **High Availability (HA)**, где активна одна нода (Active), а остальные находятся в горячем резерве (Standby). Автоматическое переключение активной ноды при отказе основной.
* **СУБД:** Хранилище конфигурации и истории (PostgreSQL или MySQL). Рекомендуется использовать **PostgreSQL + TimescaleDB** для автоматического партиционирования и сжатия временных рядов.
* **Frontend:** Веб-интерфейс на PHP для конфигурации и анализа данных.
* **Zabbix Web Service:** отдельный сервис (по умолчанию порт 10053), используется для выполнения Browser Items (Selenium) и рендеринга отчетов.
* **Java Gateway:** посредник для мониторинга приложений через **JMX**. Выступает промежуточным звеном между Zabbix Server и Java-агентами, агрегируя запросы и обеспечивая высокую масштабируемость.

#### Распределенный мониторинг (Proxy)

* **Zabbix Proxy:** Устанавливается в удаленных ЦОД или филиалах.
* **Proxy Groups (с версии 7.0):** Позволяет объединять прокси в группы для обеспечения **High Availability и балансировки нагрузки**. Если один прокси выходит из строя, хосты автоматически переключаются на другие доступные прокси в группе.
* **Memory Proxy Buffer:** Прокси могут работать в режиме *in-memory* (без локальной SQLite/MySQL базы), что значительно повышает производительность и срок службы дисков.

#### Агенты (Pull и Push)

Доступно две редакции агентов:

* **Zabbix Agent (Classic):** Написан на языке C. Отличается минимальным потреблением ресурсов памяти и CPU. Идеален для IoT и legacy-систем.
* **Zabbix Agent 2:** Написан на Go. Является стандартом по умолчанию. Поддерживает многопоточность, постоянные соединения с БД (connection pooling), **именованные сессии (Named Sessions)** для безопасного хранения учетных данных и расширяемые плагины (для мониторинга PostgreSQL, MySQL, Docker, Redis и т.д.).

### Модели сбора данных

Zabbix поддерживает гибридный подход:

* **Pull-модель (Пассивный режим):** Server или Proxy инициирует TCP-соединение и запрашивает метрику (Пассивный агент, SNMP). Создает предсказуемую сетевую нагрузку, но требует открытия портов на стороне клиента.
* **Push-модель (Активный режим):** Агент или внешняя система (через Trapper) самостоятельно подключается к серверу и передают данные. **Настоятельно рекомендуется** для масштабных инсталляций, так как перекладывает нагрузку по расписанию проверок на сами хосты и работает из-за NAT.
    * Дополнительное применение Push: отправка событий из внешних систем (например, Wazuh через `zabbix_sender` или API-метод `history.push` в 7.0+).

**Типы элементов данных.** Способ сбора определяет тип Item: `Zabbix agent` (пассивный/активный), `SNMP`, `IPMI`, `JMX`, `HTTP agent`, `trapper`, database monitor, `SSH`/`Telnet` скрипты, `external check`, `Browser` (7.0+) и др. Выбор типа напрямую влияет на сетевые требования и нагрузку — см. **[Выбор метода мониторинга](#выбор-метода-мониторинга)**.

### События, проблемы и восстановление

* **Серьезность (Severity):** классификация проблем — Disaster / High / Average / Warning / Information / Not classified.
* **Теги (Tags):** произвольные пары «ключ:значение» для корреляции инцидентов и гибкой маршрутизации алертов. Рекомендуется применять иерархическую систему тегов (например, `class`, `target`, `scope`). Подробнее — **[Лучшие практики](./zabbix_best_practices.md)**.
* **Recovery Expression:** синтаксис восстановления может требовать явного перехода в OK (соответствие логике сработки).
* **Эскалация и ручные действия:** для важных проблем настраиваются этапы эскалации (каскады операций через заданные интервалы) и подтверждение acknowledgement — при неакцептованной проблеме она продолжает привлекать внимание в UI/дашбордах.
* **Event Correlation:** связывание связанных событий (например, «сервер недоступен» и «сервис недоступен») позволяет закрывать старые проблемы, не рассылая дублирующие алерты, и сохранять полную историю инцидента.
* **Problem Suppression (7.0+):** временно подавить оповещения по проблеме на заданный период (например, при плановой остановке или известном сбое).
* **Maintenance (плановое обслуживание):** глобальное подавление проблем и алертов для выбранных хостов на период работ; сработавшие триггеры в этом окне не порождают новых оповещений и проблем.

**Оповещения и автообслуживание.** Запустить оповещения могут: сработавший триггер (событие), восстановление, обнаружение проблемы и т.д. Операции бывают: отправка сообщения по каналу, закрытие другой проблемы, выполнение Remote Command (для автоматизации восстановления).

## Операции и команды

### Управление службами (systemd)

```bash
# Проверка статуса
systemctl status zabbix-server
# → active (running) / failed / inactive

# Перезапуск после изменения конфигурации
systemctl restart zabbix-server

# Перезагрузка конфигурации без прерывания сбора (где поддерживается)
systemctl reload zabbix-server

# Включение автозагрузки
systemctl enable zabbix-server
```

Для Zabbix Proxy: `zabbix-proxy` вместо `zabbix-server`.

### Валидация и диагностика

```bash
# Предварительная проверка синтаксиса конфигурации
zabbix_server -n
# → "Configuration file [/etc/zabbix/zabbix_server.conf] looks OK"

# Проверка версии
zabbix_server -V
# → Zabbix Server 7.4.x (revision ...)

# Проверка агента
zabbix_agent2 -t site.auth
# → site.auth [u]: 1

# Проверка пассивного агента
zabbix_get -s 127.0.0.1 -p 10050 -k agent.ping
# → 1
```

### Внутренние метрики для валидации

| Элемент данных | Назначение | Пример проверки |
| :--- | :--- | :--- |
| `zabbix[version]` | Версия сервера | `zabbix_get -s 127.0.0.1 -k "zabbix[version]"` |
| `zabbix[process,<тип>,avg,busy]` | Утилизация процесса | `zabbix_get -s 127.0.0.1 -k "zabbix[process,poller,avg,busy]"` |
| `zabbix[queue,5m]` | Очередь за 5 минут | `zabbix_get -s 127.0.0.1 -k "zabbix[queue,5m]"` |
| `zabbix[history]` | NVPS (записей/сек) | `zabbix_get -s 127.0.0.1 -k "zabbix[history]"` |
| `zabbix[wcache,history,...]` | Заполненность History Cache | `zabbix_get -s 127.0.0.1 -k "zabbix[wcache,history,pused]"` |
| `zabbix[wcache,values,all]` | Попадания в Value Cache | `zabbix_get -s 127.0.0.1 -k "zabbix[wcache,values,all]"` |
| `zabbix[queue,overall]` | Общая очередь | `zabbix_get -s 127.0.0.1 -k "zabbix[queue,overall]"` |

### Runtime Control

Администратор может отправлять команды работающему Zabbix Server без перезапуска:

```bash
# Принудительно обновить кэш конфигурации
zabbix_server -R config_cache_reload
# → "command sent successfully"

# Запустить Housekeeper вне расписания
zabbix_server -R housekeeper_execute

# Запустить Trigger Housekeeper
zabbix_server -R trigger_housekeeper_execute

# Перезагрузить секреты из Vault
zabbix_server -R secrets_reload

# Статус кластера HA
zabbix_server -R ha_status
# → список нод кластера HA

# Диагностика секции
zabbix_server -R diaginfo=historycache
# → диагностика History Cache в логе
zabbix_server -R diaginfo=preprocessing
# → диагностика предобработки
zabbix_server -R diaginfo=alerting
# → диагностика оповещений
```

Для Zabbix Proxy доступно то же подмножество команд (`zabbix_proxy -R <command>`), включая `config_cache_reload` и `log_level_increase`.

## Устраннение неисправностей

### Типичные симптомы

| **Симптом** | **Вероятная причина** |
| :--- | :--- |
| **Рост очереди** | Нехватка поллеров, высокие таймауты, недоступность устройств. |
| **Разрывы на графиках (Gaps)** | Переполнение History Cache, недоступность БД. |
| **Элементы в статусе Unsupported** | Битые ключи элементов, сетевые проблемы, ошибки прав доступа. |
| **Медленный веб-интерфейс** | Слабая конфигурация PHP-FPM/OPcache, медленные запросы к БД. |
| **Долгие вычисления триггеров** | Нехватка Value Cache → прямые SELECT в БД. |
| **Падение NVPS** | Дисковая подсистема СУБД не справляется с потоком записи. |

### Быстрая диагностика

1. **Подключите Template App Zabbix Server** к самому серверу. Отслеживайте:
   - очередь: `zabbix[queue,1m]`, `zabbix[queue,overall]`;
   - NVPS: `zabbix[history]`, `zabbix[trends]`;
   - утилизацию кэшей: `zabbix[wcache,values,all]`, `zabbix[wcache,history,...]`.
2. **Проверьте логи:**
   - Zabbix Server: `/var/log/zabbix/zabbix_server.log`
   - Zabbix Proxy: `/var/log/zabbix/zabbix_proxy.log`
3. **Временное повышение логирования:**
   ```bash
   zabbix_server -R log_level_increase='poller'
   # → Debug level 4 для всех pollers
   zabbix_server -R log_level_decrease='poller'
   # → возврат к стандартному уровню
   ```
4. **Диагностика через diaginfo:**
   ```bash
   zabbix_server -R diaginfo
   # → все доступные секции в логе
   zabbix_server -R diaginfo=valuecache
   # → попадания/промахи, утилизация
   ```

### Распространенные проблемы

| **Проблема** | **Причины** | **Решение** |
| :--- | :--- | :--- |
| **Queue растет** | Мало поллеров, высокие таймауты, недоступные устройства | Увеличить StartPollers, проверить сеть, увеличить таймауты. |
| **Gaps на графиках** | Переполнение History Cache, недоступность БД | Увеличить HistoryCacheSize, проверить IOPS. |
| **Unsupported items** | Битые ключи, недоступность хостов | Проверить ключи, сеть, права. |
| **NVPS падает** | Диск СУБД не справляется | Переход на TimescaleDB, увеличение IOPS. |

## Лучшие практики

### Monitoring as Code

- **Версионируйте конфигурацию:** шаблоны, хосты, триггеры экспортируются через Zabbix API (XML/JSON) и хранятся в Git.
- **Code Review:** любые изменения в порогах, триггерных выражениях или тегах проходят через pull request.
- **CI/CD pipeline:** автоматическое применение конфигурации мониторинга через API после merge в main. Откат — через Git revert.
- **Change Management:** все изменения проходят через процедуры управления изменениями с плановым окном.

### Incident Management

- **Один источник правды:** каждый триггер должен иметь теги `class`, `target`, `scope` для маршрутизации и корреляции.
- **Acknowledgment:** оператор обязан подтвердить проблему (acknowledge) с комментарием. Без подтверждения оповещения продолжают приходить.
- **Escalation:** для каждой серьезности определена цепочка эскалации (дежурный → тимлид → руководство) с интервалами.
- **Post-mortem:** после каждого значимого инцидента проводится разбор: root cause, timeline, remediation, lessons learned. Данные берутся из истории событий Zabbix.

### Дизайн триггеров

- **Устойчивость к пикам:** используйте `avg()`, `min()`, `max()` с временным окном вместо `last()`.
- **Пороги в макросах:** выносите пороги в user macros (`{$CPU.LOAD.MAX.WARN}`).
- **Гистерезис:** используйте отдельное Recovery Expression с более низким порогом.
- **Оперативные данные:** используйте Operational Data для вывода реальных значений в проблему.

## Практические сценарии

### Выбор метода мониторинга

| Целевой объект | Рекомендуемый метод | Обоснование |
| :--- | :--- | :--- |
| **ОС (Linux/Windows)** | Zabbix Agent 2 (Active) | Поддержка плагинов, минимальная задержка (Push), безопасность. |
| **Сетевое оборудование** | SNMP v2c / v3 (Async) | Индустриальный стандарт. Асинхронные поллеры обеспечивают высокую скорость опроса. |
| **Сложные веб-приложения (SPA)** | Browser Items (Selenium) | Позволяет авторизоваться, кликать по кнопкам и сохранять скриншоты при ошибках. |
| **Базы данных (PostgreSQL/MySQL)** | Zabbix Agent 2 Plugin | Нативная реализация метрик без устаревших UserParameter-скриптов. |
| **Микросервисы** | Zabbix Trapper / HTTP Agent | Метрики отправляются приложением напрямую в момент выполнения задачи (push). |

### Безопасность соединений (TLS)

Все компоненты поддерживают шифрование:

- **PSK (Pre-Shared Key):** простой способ, легко распространяется.
- **Сертификаты (X.509):** строгая аутентификация по публичным/приватным CA.
- В 7.4 добавлена возможность принудительного TLS для trapper.

### Автоматизация масштабирования

* **Network Discovery:** Сканирование IP-сетей и автоматическое добавление найденных устройств в мониторинг (на базе ответов портов или агента).
* **Auto-registration:** Механизм, при котором новый активный агент сам обращается к серверу, и сервер автоматически применяет к нему нужный шаблон и группу (на основе метаданных агента `HostMetadata`).
* **Low-Level Discovery (LLD):** обнаружение динамических компонентов *внутри* хоста. Подробнее: **[Низкоуровневое обнаружение](./low_level_discovery.md)**.

### Сравнение с Prometheus

Zabbix и Prometheus предназначены для разных типов инфраструктур:

| Характеристика | Zabbix | Prometheus |
| :--- | :--- | :--- |
| **Инфраструктура** | Классическая (Bare-metal, VM, сеть) | Динамические (Kubernetes, контейнеры) |
| **Жизненный цикл хостов** | Статичный (машины живут годами) | Динамичный (машины живут секундами) |
| **Модель сбора** | Pull и Push (гибридная) | Pull (преимущественно) |
| **Хранение** | Реляционная СУБД (SQL) + TimescaleDB | Собственная TSDB (временные ряды) |
| **Компоненты** | Все в одном (Сбор, Хранение, Визуализация, Алертинг) | Модульная структура |

*Примечание: в современных развивающихся инфраструктурах обе системы часто сосуществуют, дополняя друг друга.*
