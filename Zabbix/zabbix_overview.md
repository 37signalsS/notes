# Zabbix: Обзор системы мониторинга

## 1. Определения

*   **Zabbix** – это свободная, масштабируемая система мониторинга IT-инфраструктур с открытым исходным кодом. Она предназначена для отслеживания состояния серверов, сетевого оборудования и приложений в режиме реального времени.
*   **Безагентный мониторинг** — это совокупность методов сбора данных с хостов и устройств, не требующих установки программного обеспечения (агента) Zabbix. К таким случаям относится мониторинг сетевого оборудования (коммутаторы, маршрутизаторы), принтеров или специализированных аппаратных хранилищ.
*   **SNMP (Simple Network Management Protocol)** — это стандартный протокол для управления и мониторинга сетевых устройств. Он позволяет Zabbix запрашивать данные у оборудования без установки какого-либо дополнительного ПО. Ключевыми компонентами являются:
    - **Сетевой менеджер (Network Manager):** Система, которая опрашивает устройства (в нашем случае — Zabbix Server).
    - **Агент (Agent):** Программное обеспечение на управляемом устройстве, которое отвечает на запросы менеджера.
    - **MIB (Management Information Base):** Иерархическая база данных на устройстве, содержащая сведения о его параметрах. Каждое устройство имеет свою MIB-таблицу.
    - **OID (Object Identifier):** Уникальный числовой идентификатор, представляющий собой путь к конкретному объекту (метрике) в дереве MIB (например, `1.3.6.1.2.1.1.2`). OID позволяет однозначно идентифицировать данные, которые можно запросить у устройства.
*   **Zabbix Trapper** — это специальный элемент данных (`Item`), который не инициирует проверок, а только прослушивает входящие данные на определённом порту. Он используется для реализации **Push-модели** сбора данных, когда они активно отправляются на сервер из внешних источников. Для отправки данных используется утилита **`zabbix_sender`**.
*   **Обнаружение хостов (Network Discovery)** — это механизм, позволяющий Zabbix автоматически находить и добавлять в мониторинг хосты в вашей сети на основе заданного диапазона IP-адресов и результатов проверок.
*   **Низкоуровневое обнаружение (Low-Level Discovery, LLD)** — это технология, которая позволяет автоматически обнаруживать **элементы данных, триггеры и графики** на хосте. Это незаменимо для мониторинга сущностей, количество которых может меняться, например: сетевые интерфейсы, файловые системы или [базы данных](../../Zabbix/zabbix_postgresql_monitoring.md).

## 2. Основные концепции

### Ключевые возможности

-   **Сбор метрик:** Отслеживание параметров производительности (загрузка ЦПУ, использование диска, сетевая активность, доступность по ICMP и др.).
-   **Обнаружение проблем:** Автоматическое определение, когда параметры выходят за пределы нормы.
-   **Визуализация:** Построение графиков для анализа тенденций.
-   **Оповещения и автоматизация:** Отправка уведомлений о проблемах через различные каналы (Email, SMS, Telegram) и выполнение скриптов. Рекомендации по настройке рассмотрены в документе: **[Лучшие практики настройки Zabbix](./zabbix_best_practices.md)**.
-   **Автоматическое обнаружение:** Автоматическое нахождение и постановка на мониторинг новых устройств и ресурсов.

### Архитектура и компоненты

-   **Zabbix Server:** Ядро системы, которое собирает, хранит и анализирует данные. Взаимодействует с базой данных (поддерживаются MySQL, PostgreSQL). Подробнее о мониторинге баз данных: **[Мониторинг Баз Данных с помощью Zabbix](./zabbix_database_monitoring.md)**.
-   **Zabbix Proxy:** Опциональный компонент для сбора данных от имени сервера, что снижает нагрузку на ядро и позволяет мониторить изолированные сегменты сети.
-   **Zabbix Agent:** Программа, устанавливаемая на хосты для активного сбора данных.
-   **Веб-интерфейс:** Централизованная консоль для настройки, просмотра данных и управления системой.

### Модели и способы сбора данных

#### Модель Pull vs Push
Zabbix гибок и поддерживает обе модели сбора данных, хотя исторически тяготеет к Push-модели.
-   **Push-модель (проталкивание):** Zabbix-агент активно собирает метрики и отправляет их на Zabbix-сервер. Этот подход используется в **активных проверках (Active checks)**.
-   **Pull-модель (затягивание):** Zabbix-сервер сам запрашивает значение метрики у агента. Этот подход используется в **пассивных проверках (Passive checks)** и при мониторинге по SNMP.

Такой гибридный подход отличает Zabbix от систем, строго придерживающихся одной модели, как [Prometheus](../Prometheus/overview.md) (Pull). Подробное сравнение стратегий сбора метрик рассмотрено в заметке: **[Стратегии сбора метрик](../Concepts/Observability_and_Monitoring/observability_overview.md#стратегии-сбора-метрик)**.

#### Способы сбора данных

1.  **Zabbix Agent:** Основной способ. Агент, установленный на хост, может работать в двух режимах:
    *   **Активные проверки:** Агент периодически запрашивает у сервера список необходимых элементов данных и самостоятельно отправляет результаты. Это предпочтительный, лучше масштабируемый режим.
    *   **Пассивные проверки:** Сервер сам запрашивает у агента значение конкретной метрики.

2.  **Безагентный мониторинг:** Используется, когда установка агента невозможна или нецелесообразна.
    *   **SNMP:** Zabbix имеет множество встроенных шаблонов для мониторинга сетевого оборудования от различных производителей (Cisco, MikroTik, Huawei и др.) по SNMP. При настройке хоста указывается его IP-адрес, версия протокола и `community` (пароль), после чего Zabbix начинает опрашивать устройство для сбора метрик, определённых в шаблоне.
    *   **ICMP:** Для простых проверок доступности (ping).
    *   **SSH/Telnet:** Для выполнения команд на удаленных хостах.
    *   **HTTP/HTTPS:** Для проверки доступности и кодов ответа веб-сервисов.

3.  **Zabbix Trapper:** Этот метод основан на **Push-модели**: данные не запрашиваются сервером, а активно отправляются на него из внешних источников. Это мощный механизм для интеграции Zabbix с кастомными скриптами и [приложениями](../../ELK_Stack/Logstash/logstash_overview.md). Скрипт может собирать любые данные (бизнес-метрики, данные из CLI проприетарного оборудования) и отправлять их в Zabbix.

### Автоматическое обнаружение

#### Обнаружение хостов (Network Discovery)
Процесс состоит из двух частей:
1.  **Правило обнаружения (`Discovery rule`):** Задаётся диапазон IP-адресов для сканирования и проверки (например, доступность порта Zabbix-агента).
2.  **Действие (`Action`):** Настраивается реакция на успешное обнаружение хоста. Например, при обнаружении Linux-сервера его можно автоматически добавить в нужную группу и привязать к нему соответствующий шаблон мониторинга.

#### Низкоуровневое обнаружение (LLD)
Принцип работы LLD следующий:
1.  **Правило обнаружения (LLD Rule)** внутри шаблона выполняет проверку, которая возвращает **JSON-объект** со списком обнаруженных ресурсов.
2.  **Прототипы (`Prototypes`)** элементов данных, триггеров и графиков используют специальные макросы из полученного JSON.
3.  **Создание реальных объектов:** Zabbix автоматически создаёт настоящие элементы данных, триггеры и графики для каждого обнаруженного ресурса, подставляя значения из JSON в прототипы.

Если какой-то объект (например, файловая система) исчезает из JSON при следующей проверке, Zabbix автоматически удаляет связанные с ним метрики и триггеры.

## 3. Практические сценарии

### Установка Zabbix Server (на Ubuntu)

**1. Установка необходимых компонентов (Apache, MariaDB, PHP)**
```bash
sudo apt update && sudo apt upgrade -y
sudo apt install -y apache2 mariadb-server mariadb-client php php-cgi php-mbstring php-gd php-xml php-mysql php-bcmath php-ldap php-json
```

**2. Добавление репозитория Zabbix**
```bash
wget https://repo.zabbix.com/zabbix/6.0/ubuntu/pool/main/z/zabbix-release/zabbix-release_6.0-4+ubuntu22.04_all.deb
sudo dpkg -i zabbix-release_6.0-4+ubuntu22.04_all.deb
sudo apt update
```

**3. Установка компонентов Zabbix**
```bash
sudo apt install -y zabbix-server-mysql zabbix-frontend-php zabbix-apache-conf zabbix-sql-scripts zabbix-agent
```

**4. Создание и настройка базы данных**
```sql
-- Входим в консоль MariaDB: sudo mysql -uroot -p
CREATE DATABASE zabbix CHARACTER SET utf8mb4 COLLATE utf8mb4_bin;

# Создаем пользователя и задаем пароль (замените 'your_password' на надежный пароль)
CREATE USER 'zabbix'@'localhost' IDENTIFIED BY 'your_password';

# Выдаем привилегии
GRANT ALL PRIVILEGES ON zabbix.* TO 'zabbix'@'localhost';

# Выходим
FLUSH PRIVILEGES;
quit;
```

**5. Импорт начальной схемы данных**
```bash
# Импортируем схему в созданную БД. Система запросит пароль пользователя 'zabbix'.
zcat /usr/share/zabbix-sql-scripts/mysql/server.sql.gz | sudo mysql -uzabbix -p zabbix
```

**6. Конфигурация Zabbix Server и PHP**
-   В файле `/etc/zabbix/zabbix_server.conf` укажите пароль `DBPassword`.
-   В файле `/etc/php/8.1/apache2/php.ini` задайте свой часовой пояс `date.timezone`.

**7. Запуск служб**
```bash
sudo systemctl restart zabbix-server zabbix-agent apache2
sudo systemctl enable zabbix-server zabbix-agent apache2
```

**8. Завершение установки через веб-интерфейс**
-   Откройте `http://<IP-адрес_сервера>/zabbix`.
-   Следуйте шагам мастера установки, указав пароль от БД.
-   Стандартные учетные данные для входа: `Admin` / `zabbix`.

### Установка Zabbix Agent (на Ubuntu)

**1. Добавление репозитория Zabbix и установка**
```bash
# Репозиторий добавляется так же, как для сервера
sudo apt update
sudo apt install zabbix-agent
```

**2. Настройка агента**
Отредактируйте `/etc/zabbix/zabbix_agentd.conf`:
```ini
# IP-адрес вашего Zabbix-сервера
Server=192.168.1.100

# Для активных проверок
ServerActive=192.168.1.100

# Имя хоста (должно совпадать с именем в веб-интерфейсе Zabbix)
Hostname=MyUbuntuServer
```

**3. Запуск службы и настройка файрвола**
```bash
sudo systemctl restart zabbix-agent
sudo systemctl enable zabbix-agent
# Разрешите входящие подключения на порт 10050/tcp от Zabbix-сервера
sudo ufw allow from 192.168.1.100 to any port 10050 proto tcp
```
После этого не забудьте добавить хост в веб-интерфейсе Zabbix.

### Отправка данных с помощью zabbix_sender
```bash
zabbix_sender -z <zabbix_server_ip> -p 10051 -s <hostname> -k <item_key> -o <value>
```
- `-z`: IP-адрес Zabbix-сервера.
- `-s`: Имя хоста в Zabbix (должно точно совпадать).
- `-k`: Ключ `trapper`-элемента.
- `-o`: Отправляемое значение.

### Настройка SNMP-мониторинга
1. При создании хоста в Zabbix добавляется интерфейс типа **SNMP**.
2. Указывается IP-адрес или DNS-имя устройства.
3. Задаются параметры SNMP: - **SNMP version:** Чаще всего `2`. - **SNMP community:** Строка-пароль (например, `public`), которая должна совпадать с настроенной на устройстве.

### Пример автоматического добавления хоста
Настроив правило обнаружения для сети `192.168.1.0/24` и действие, которое реагирует на значение `Linux` от проверки `system.uname`, новые Linux-серверы с установленным агентом будут автоматически добавляться в Zabbix в группу `Linux servers` и ставиться на мониторинг с шаблоном `Linux by Zabbix agent`.

### Пример JSON для LLD файловых систем
```json
{ "data": [ { "{#FSNAME}": "/", "{#FSTYPE}": "ext4" }, { "{#FSNAME}": "/boot", "{#FSTYPE}": "ext4" }, { "{#FSNAME}": "/var/log", "{#FSTYPE}": "xfs" } ]
}
```
На основе этих данных Zabbix создаст проверки для каждой файловой системы, используя прототипы, например, `Free disk space on {#FSNAME}` с ключом `vfs.fs.size[{#FSNAME},pfree]`.

## 4. Дополнительная информация

### Процесс запуска Zabbix Server

При запуске Zabbix Server выполняет следующую последовательность действий:
1.  **Чтение конфигурации** (`zabbix_server.conf`).
2.  **Загрузка модулей** и создание кэшей в памяти.
3.  **Проверка версии схемы БД**.
4.  **Запуск HA менеджера** (в режиме высокой доступности).
5.  **Загрузка конфигурации мониторинга из БД** в кэш. В Zabbix 7.0+ это происходит инкрементально, что снижает нагрузку.
6.  **Запуск рабочих процессов** (`pollers`, `trappers`, `history syncers` и др.).

### Оптимизация и устранение неисправностей

Для обеспечения стабильной работы и высокой производительности Zabbix важно регулярно проводить оптимизацию и уметь диагностировать проблемы.
> Подробное руководство доступно в документе: **[Поиск и устранение неисправностей и тюнинг производительности Zabbix](./zabbix_troubleshooting_and_performance_tuning.md)**.

### Реализация LLD для кастомных метрик
Этот подход обеспечивает максимальную гибкость, позволяя мониторить практически любые динамические сущности.

1.  **Скрипт обнаружения:** На хосте создается скрипт, который формирует JSON для LLD. Пример `my_discovery_script.sh`: ```bash #!/bin/bash echo '{ "data": [ { "{#ITEMNAME}": "CPU_Usage", "{#ITEMDESCRIPTION}": "Загрузка процессора" }, { "{#ITEMNAME}": "Memory_Free", "{#ITEMDESCRIPTION}": "Свободная память" } ] }' ```

2.  **UserParameter для агента:** В конфигурации [Zabbix-агента](../../Zabbix/zabbix_overview.md) (`/etc/zabbix/zabbix_agentd.conf.d/`) создается `UserParameter` для вызова [скрипта](../../Databases/mysql.md): ``` UserParameter=otus.discovery,/usr/local/bin/my_discovery_script.sh ```
3.  **LLD-правило в Zabbix:** В шаблоне создается правило обнаружения с ключом `otus.discovery`, которое будет выполнять этот `UserParameter` для получения JSON.

4.  **Прототипы элементов:** Создаются прототипы элементов данных с типом **`Zabbix trapper`** и ключами, использующими макросы из JSON. - **Прототип:** `Custom metric {#ITEMDESCRIPTION}` с ключом `custom.metric[{#ITEMNAME}]`.

5.  **Отправка данных:** Для отправки значений обнаруженных метрик на Zabbix-сервер используется утилита `zabbix_sender` в отдельном скрипте, запускаемом по расписанию (cron). ```bash #!/bin/bash ZABBIX_SERVER="<zabbix_server_ip>" HOSTNAME="My Host" # Имя хоста, как оно определено в Zabbix # Получение значения загрузки процессора CPU_VALUE=$(awk '{print $1*100}' @/proc/loadavg | cut -d'.' -f1) # Пример # Отправка значения CPU_Usage zabbix_sender -z "$ZABBIX_SERVER" -s "$HOSTNAME" -k 'custom.metric[CPU_Usage]' -o "$CPU_VALUE" # Получение значения свободной памяти MEM_VALUE=$(free -m | awk 'NR==2{print $4}') # Пример # Отправка значения Memory_Free zabbix_sender -z "$ZABBIX_SERVER" -s "$HOSTNAME" -k 'custom.metric[Memory_Free]' -o "$MEM_VALUE" ```
