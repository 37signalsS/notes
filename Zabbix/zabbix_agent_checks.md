# Zabbix — режимы работы агентов и авторегистрация

**Актуально для:** Zabbix 7.0 LTS / 7.4

## Определения

* **Zabbix Agent** — классический агент (C-реализация), устанавливаемый на контролируемый хост. Поддерживает активные и пассивные проверки.
* **Zabbix Agent 2** — переписанный агент на Go с поддержкой плагинов (PostgreSQL, MySQL, Docker, systemd и др.). Совместим по ключам с классическим агентом, но добавляет собственные ключи и плагинную архитектуру.
* **Пассивная проверка (passive check)** — сервер или прокси инициирует соединение к агенту (порт 10050) и запрашивает значение по ключу.
* **Активная проверка (active check)** — агент сам устанавливает соединение к серверу/прокси (порт 10051), получает список ключей и отправляет значения.
* **Активный сервер (ServerActive)** — адрес сервера/прокси, к которому подключается агент для активных проверок.
* **Буфер агента (buffer)** — область, где агент накапливает неотправленные значения при недоступности сервера. Бывает оперативным (в памяти) и постоянным (на диске).
* **Авторегистрация (autoregistration)** — автоматическое создание хоста в Zabbix при появлении нового агента, без ручного добавления. Работает только для активных агентов.
* **Метаданные узла (HostMetadata)** — произвольная строка, передаваемая агентом при авторегистрации и используемая сервером для маршрутизации (например, назначения шаблонов).

## Основные концепции

### Активные и пассивные проверки

Выбор режима диктуется сетевое топологией и направлением, в котором можно инициировать соединение.

| Критерий | Пассивные (passive) | Активные (active) |
|---|---|---|
| Кто инициирует соединение | Server/Proxy → Agent | Agent → Server/Proxy |
| Порт на стороне агента | 10050 (входящий) | 10051 (исходящий на сервер) |
| Требования к firewall на хосте | Открыть входящий 10050 | Открыть исходящий на 10051 |
| Работа за NAT / динамический IP | Затруднена | Работает |
| Нагрузка на сервер | Выше: сервер опрашивает хост по каждому ключу | Ниже: агент сам отправляет данные |
| Где исполняется ключ | На агенте (по запросу сервера) | На агенте (по расписанию, полученному от сервера) |
| Логи, `log[]`, `logrt[]` | Недоступны | Только активные проверки |
| Чувствительность к задержкам сервера | Каждый опрос — отдельное соединение | Одно долгоживущее соединение на пакет ключей |

Ключевое следствие: **элементы данных типов `log`, `logrt`, `log.count`, `logrt.count` и Zabbix Agent 2 плагинные ключи при активном режиме проверяются только активным способом.** Пассивный агент их не отдаёт.

### Как агент получает список активных проверок

1. Агент подключается к `ServerActive` (или к серверу, отдавшему список при первом обращении) и вызывает `active checks`.
2. Сервер возвращает список ключей с интервалами и параметры (например, таймауты).
3. Агент сам определяет момент выполнения каждого ключа (`RefreshActiveChecks`, по умолчанию 120 секунд) и отправляет результаты пачками.
4. Если ключ на сервере отключён — агент прекращает его собирать; если снова включён — начинает после следующего обновления списка.

### Буферизация

При недоступности сервера/прокси агент не теряет значения мгновенно:

* **BufferSize** — количество значений, удерживаемых в памяти.
* **BufferSize** может персистить данные на диск (в Zabbix 7.0 — `PersistentBuffer`), чтобы пережить перезапуск агента. При заполнении буфера агент вытесняет самые старые значения.

### Авторегистрация

Различают два механизма:

* **Активная авторегистрация** — агент с активными проверками регистрируется на сервере сам. Администратор настраивает действие (Action) с условием по `HostMetadata`, которое назначает хост-группу и шаблоны. Обязательное условие: у агента задан `ServerActive` и включены активные проверки.
* **Пассивная авторегистрация** — сервер добавляет хост, когда к нему впервые обращается пассивный агент с незарегистрированным именем. Настраивается отдельно и требует, чтобы хост ещё не существовал.

Типовой сценарий массового развёртывания: агент передаёт `HostMetadata` вида `Linux;prod;web` или `MySQL`, а действия на сервере по значению метаданных назначают группу (`Linux servers`, `Databases`) и шаблоны (`Linux by Zabbix agent`, `MySQL by Zabbix agent 2`).

## Практические сценарии

### Предварительные требования

* Установленный Zabbix Agent или Agent 2 на контролируемом хосте.
* Открытые порты: 10050 (пассивно, на агент) и/или 10051 (активно, на сервер).
* Зарегистрированный хост в веб-интерфейсе при отключённой авторегистрации.

### Сценарий 1. Пассивный агент

`/etc/zabbix/zabbix_agentd.conf`:

```ini
Server=192.168.1.100          # адрес сервера/прокси, которым разрешён опрос
ListenPort=10050
ListenIP=0.0.0.0
StartAgents=3                 # число пассивных воркеров
```

Проверка с сервера:

```bash
zabbix_get -s 192.168.1.10 -p 10050 -k agent.ping
# → 1
```

Элементы данных на хосте создаются с типом `Zabbix agent` (пассивный режим).

### Сценарий 2. Активный агент с буфером

`/etc/zabbix/zabbix_agentd.conf`:

```ini
ServerActive=192.168.1.100:10051
Hostname=web01.example.com     # имя должно совпадать с хостом в Zabbix
HostMetadata=Linux;prod;web
RefreshActiveChecks=120
BufferSend=5                   # отправлять буфер каждые 5 секунд
BufferSize=100                 # до 100 значений в памяти
# PersistentBuffer=1           # 7.0: сохранять буфер на диск
```

Проверка, что агент видит активные проверки:

```bash
# На агенте: список полученных активных проверок
grep -i "active check" /var/log/zabbix/zabbix_agentd.log | tail
# → enabling active checks ...
# → active check "system.cpu.load[all,avg1]" is not supported ...

# На сервере: диагностика очереди (результат пишется в лог сервера)
zabbix_server -R diaginfo
grep -i "queue" /var/log/zabbix/zabbix_server.log | tail
```

Элементы данных должны быть типа `Zabbix agent (active)` (ключ с флагом активной проверки), иначе сервер вернёт «не поддерживается».

### Сценарий 3. Включение авторегистрации (активный агент)

На агенте — как в Сценарии 2 (`ServerActive`, `HostMetadata`). На сервере:

1. `Alerts → Actions → Autoregistration actions → Create action`.
2. Условие, например `Host metadata contains Linux`.
3. Операция `Add host` с указанием группы `Linux servers` и связывания шаблона `Linux by Zabbix agent`.
4. Опционально — `Add to host groups` и `Link to templates`.

После рестарта агента хост появляется в `Data collection → Hosts` автоматически.

```bash
systemctl restart zabbix-agent2
# → новая запись хоста появляется в списке хостов в течение интервала
#    RefreshActiveChecks (120 с)
```

### Сценарий 4. Отключение авторегистрации

Если развёртывание контролируемое, авторегистрацию выключают, чтобы посторонний узел не создал себе хост:

* Удалить `Actions → Autoregistration actions`.
* Оставить только предварительно созданные хосты.
* Для защиты самой регистрации использовать шифрование PSK/сертификаты (см. [zabbix_authentication_and_rbac.md](./zabbix_authentication_and_rbac.md)).

## Операции и команды

| Задача | Команда |
|---|---|
| Проверить пассивный агент с сервера | `zabbix_get -s <host> -p 10050 -k agent.ping` |
| Синтаксис конфигурации агента | `zabbix_agentd -t agent.ping` / `zabbix_agent2 -t agent.ping` |
| Список ключей Agent 2 | `zabbix_agent2 -p` (печатает поддерживаемые ключи) |
| Перечитать конфиг агента | `systemctl reload zabbix-agent2` |
| Лог агента | `/var/log/zabbix/zabbix_agentd.log` |
| Версия агента | `zabbix_agentd -V` / `zabbix_agent2 -V` |

```bash
# Тест конкретного ключа локально на агенте
zabbix_agent2 -t system.cpu.load[all,avg1]
# → system.cpu.load[all,avg1]                      [f|0.42]

# Проверка, что активный агент дозвонился до сервера
journalctl -u zabbix-agent2 | grep -i "active checks"
```

## Устранение неисправностей

### Хост добавлен, но данные не приходят (активный режим)

1. Проверить, что `Hostname` в конфиге агента **точно** совпадает с именем хоста (`Host name`) в Zabbix. Рассинхрон имени — самая частая причина.
2. Убедиться, что элементы данных имеют тип `Zabbix agent (active)`, а не пассивный.
3. Проверить, что `ServerActive` доступен по сети и порт 10051 открыт на сервере.
4. В логе агента искать `cannot connect`, `active checks`.

### «Get value from agent failed» (пассивный режим)

* Порт 10050 закрыт firewall на хосте или в `Server=` не указан адрес сервера.
* Превышен `Timeout` для тяжёлого ключа — увеличьте таймаут элемента данных (в Zabbix 7.0 глобальный `Timeout`, при необходимости `Timeout` per-item).
* Агент слушает `ListenIP`, отличный от адреса, к которому обращается сервер.

### Значения теряются при недоступности сервера

* Увеличить `BufferSize` и включить `PersistentBuffer`.
* Разнести нагрузку: при пике NVPS значения вытесняются быстрее, чем отправляются.

### Не работает авторегистрация

* Агент не в активном режиме (нет `ServerActive`).
* Действие авторегистрации отсутствует, отключено или условие по `HostMetadata` не совпадает (регистр и разделители имеют значение).
* Хост уже существует с тем же именем — авторегистрация не сработает повторно.

## Лучшие практики

* **Активные проверки — по умолчанию для больших инсталляций.** Снижают нагрузку на сервер и позволяют работать за NAT. Официальные шаблоны Zabbix 7.x ориентированы именно на активные проверки.
* **Задавайте `HostMetadata` осмысленно** — это основа маршрутизации авторегистрации. Единый формат (например, `OS;env;role`) упрощает массовый онбординг.
* **Не смешивайте роли одного хоста** в одном агенте без необходимости: разделение сборки метрик и логов по разным интерфейсам усложняет диагностику.
* **Защищайте регистрацию** шифрованием PSK и отключением авторегистрации там, где она не нужна.
* **Мониторьте сам агент** элементом `zabbix[process,...]` на сервере и `agent.ping` на хосте; используйте `zabbix_agent2 -p` при миграции на Agent 2 для сверки набора ключей.
* **При переходе agent → agent 2** проверяйте кастомные `UserParameter` и плагинные ключи: часть внешних скриптов может требовать адаптации.
