# Zabbix — аутентификация, права и безопасность доступа

**Актуально для:** Zabbix 7.0 LTS / 7.4

## Определения

* **Внутренняя аутентификация (Internal)** — учётные записи хранятся в базе Zabbix (логин/пароль). Метод по умолчанию.
* **LDAP-аутентификация** — проверка учётных данных во внешнем каталоге (OpenLDAP, Active Directory). Пароли пользователей хранятся не в Zabbix.
* **HTTP-аутентификация** — доверие имени пользователя, переданному веб-сервером (SSO на уровне reverse-proxy). Требует настройки frontend и веб-сервера.
* **SAML-аутентификация** — вход через SAML 2.0 IdP (например, Keycloak, Okta). Поддерживается с Zabbix 5.0.
* **MFA (Multi-Factor Authentication)** — второй фактор (TOTP) в дополнение к паролю. Появился в Zabbix **6.4**.
* **Роль пользователя (User role)** — набор прав на разделы UI и методы API. Введена в **5.2** и заменила жёсткие типы пользователей (User/Admin/Super admin действуют как предопределённые роли).
* **Группа пользователей (User group)** — задаёт права на **группы хостов** (`read-write`/`read`/`deny`) и может быть привязана к роли. Права на данные определяет группа, права на функциональность — роль.
* **API-токен** — постоянный секрет для доступа к API (с версии 5.4), привязан к пользователю и наследует его права либо ограничивается отдельной ролью.

Безопасность канала (TLS/PSK между server, proxy, agent, frontend) настраивается отдельно — см. [Установка и настройка](./installation.md), сценарий шифрования.

## Основные концепции

### Два контура доступа

1. **Аутентификация** — «кто ты»: пароль в базе, LDAP, SAML, HTTP, MFA-фактор.
2. **Авторизация** — «что тебе можно»: роль (функции и методы API) + группа пользователей (видимость и запись по группам хостов).

Эти контуры независимы: пользователь может аутентифицироваться через AD, но его права всё равно ограничиваются ролью и группами в Zabbix.

### Методы аутентификации

| Метод | Где настраивается | Особенность |
|---|---|---|
| Internal | `Administration → Authentication` | Полный контроль, пароли в БД Zabbix |
| LDAP | там же + параметры сервера | Нужны bind DN, base DN, search attribute, mapping групп |
| HTTP | там же + конфиг веб-сервера | Пользователь должен существовать в Zabbix; frontend доверяет заголовку |
| SAML | там же + IdP | Обмен метаданными SP/IdP, маппинг атрибутов |

Одновременно может быть активен только один основной механизм входа, но для отдельных пользователей можно оставить и внутренние пароли (зависит от конфигурации и версии).

### Роли и группы

* **Роль** определяет: доступ к UI-разделам, доступ к действиям (например, управление проблемами, экспорт данных), доступ к **методам API**. Роли создаются и назначаются группам пользователей.
* **Группа пользователей** сопоставляется с **группами хостов** и уровнем прав (`read-write`, `read`, `deny`). Это защищает данные: инженер БД не видит хосты других команд.
* Для сервисных учёток автоматизации заводится отдельная роль с минимальным набором методов.

### MFA

С версии 6.4 поддерживается TOTP. MFA включается администратором в `Administration → Authentication → MFA settings` (задать имя, алгоритм/hash, разрешённые методы), после чего пользователь привязывает приложение-аутентификатор. Политики (для каких групп обязателен MFA) задаются параметрами аутентификации.

## Практические сценарии

### Сценарий 1. Смена метода аутентификации на LDAP

`Administration → Authentication → LDAP settings`:

* Host — адрес LDAP-сервера (`ldap://` или `ldaps://` для TLS);
* Port — `389` / `636`;
* Base DN — `dc=example,dc=com`;
* Search attribute — `uid` (или `sAMAccountName` для AD);
* Bind DN + Bind password — сервисная учётка для поиска;
* Test authentication — проверочные логин/пароль.

Затем в `Administration → Authentication` выберите LDAP как метод по умолчанию.

### Сценарий 2. Роль для мониторинга (только чтение)

`Administration → User roles → Create role`:

* Запретить доступ на запись к разделам конфигурации;
* Разрешить доступ к `Monitoring` и к методам API чтения (`host.get`, `problem.get`);
* Назначить роль в группе пользователей, которой даны права `read` на нужные группы хостов.

### Сценарий 3. API-токен для автоматизации

1. Создать отдельного пользователя (например, `svc-monitoring`).
2. `Users → API tokens → Create API token`: задать срок действия, при необходимости — отдельную роль с минимумом методов.
3. Скопировать токен (показывается один раз) и хранить в секрет-менеджере.

```bash
# Использование токена в запросе API
curl -s -X POST http://zabbix.example.com/api_jsonrpc.php \
  -H 'Content-Type: application/json-rpc' \
  -H "Authorization: Bearer $ZABBIX_TOKEN" \
  -d '{"jsonrpc":"2.0","method":"apiinfo.version","params":{},"id":1}'
# → {"jsonrpc":"2.0","result":"7.4.0","id":1}
```

### Сценарий 4. Включение MFA для администраторов

1. `Administration → Authentication → MFA settings` — создать метод TOTP, задать hash и имя эмитента.
2. В параметрах аутентификации указать, для каких групп MFA обязателен.
3. Пользователь при первом входе привязывает TOTP-приложение по QR/секрету.

### Проверка доступа

```bash
# Что видит конкретный пользователь через API (его токен)
curl ... -d '{"jsonrpc":"2.0","method":"host.get",
  "params":{"output":["host"],"countOutput":true},"id":1}' \
  -H "Authorization: Bearer $USER_TOKEN"
# → число хостов, видимых в рамках его групп хостов
```

## Операции и команды

| Задача | Где / команда |
|---|---|
| Настройка аутентификации | `Administration → Authentication` |
| Создание роли | `Administration → User roles` |
| Создание группы | `Administration → User groups` |
| API-токены | `Users → API tokens` |
| Настройка MFA | `Administration → Authentication → MFA settings` |
| Проверка LDAP-логина | кнопка `Test authentication` в LDAP settings |
| Сброс пароля пользователя | `Users → <user> → Change password` (админ) |

```bash
# Список токенов пользователя через API (метод token.get, если права позволяют)
curl ... -d '{"jsonrpc":"2.0","method":"token.get",
  "params":{"output":"extend"},"id":1}' -H "Authorization: Bearer $ADMIN_TOKEN"
```

## Устранение неисправностей

### Пользователь AD/LDAP не может войти

* В Zabbix нет пользователя с тем же логином — при LDAP-аутентификации пользователь должен существовать (или автосоздаваться при включённой опции).
* Mapping групп не настроен — пользователь аутентифицируется, но без прав.
* TLS: самоподписанный сертификат LDAP не принят — импортировать CA.

### HTTP-аутентификация не работает

* Пользователь не создан в Zabbix.
* Веб-сервер не передаёт ожидаемый заголовок/переменную, либо `REMOTE_USER` не доходит до frontend.
* Конфликт с методом аутентификации по умолчанию.

### Токен не действует

* Истёк срок действия или токен отозван.
* Роль токена не включает нужный метод API.
* Заголовок `Authorization` отсутствует или искажён прокси.

### «Permission denied» при видимых доступах

* Пользователь состоит в группе без прав на нужные группы хостов (уровень `deny`/`read`).
* Роль запрещает соответствующий раздел/метод.

## Лучшие практики

* **SSO через LDAP/SAML** для людей; **API-токены** для сервисов — единый вход и централизованный отзыв доступа.
* **Принцип наименьших прав**: роль + группа хостов под конкретную команду; отдельная урезанная роль для автоматизации.
* **Ротация и срок жизни токенов**; хранение в Vault/секретах CI, не в Git.
* **MFA для привилегированных учёток** (Super admin, доступ к API управления).
* **Шифрование транспорта** (PSK или сертификаты) между всеми компонентами — обязательно в проде; см. [Установка и настройка](./installation.md).
* **Секреты в макросах — через Vault**, а не открытым текстом; перезагрузка секретов выполняется Runtime Control (`secrets_reload`), см. [внутреннее устройство](./additional_info.md).
* **Регулярный аудит**: перечень пользователей, ролей, токенов и их сроков; отзыв неиспользуемого.
* **Отключите авторегистрацию** там, где она не нужна, чтобы посторонний узел не появился в мониторинге (см. [Режимы работы агентов](./zabbix_agent_checks.md)).
