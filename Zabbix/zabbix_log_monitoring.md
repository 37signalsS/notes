# Zabbix — мониторинг логов

**Актуально для:** Zabbix 7.0 LTS / 7.4

## Определения

* **Log item (`log[key]`)** — элемент данных, который читает текстовый файл и передаёт строки, совпадающие с шаблоном (или факт совпадения). Работает только как активная проверка.
* **`logrt`** — вариант для **ротируемых** логов: имя файла задаётся регулярным выражением, агент отслеживает текущий файл (по имени и позиции), корректно переживая ротацию и `logrotate`.
* **`log.count` / `logrt.count`** — возвращают количество совпавших строк за интервал опроса, а не сами строки.
* **`log[]` с пустым regexp** — проверка появления любой новой строки (используется с триггером `nodata()`).
* **Output template** — шаблон извлечения подстрок из найденной строки (`\1`…`\9`), позволяющий вернуть только нужное поле.
* **Active check** — режим, при котором агент сам отправляет значения на сервер; для `log`/`logrt` он обязателен.

> Логи нельзя собирать пассивно. Причина: агент должен непрерывно знать позицию чтения в файле; сервер, опрашивающий пассивно, не хранит это состояние. Поэтому `log`/`logrt`-элементы всегда имеют тип `Zabbix agent (active)`. См. [Режимы работы агентов](./zabbix_agent_checks.md).

## Основные концепции

### Синтаксис ключей

```
log[<file>,<regexp>,<encoding>,<maxlines>,<mode>,<output>,<maxproclines>]
logrt[<file_regexp>,<regexp>,<encoding>,<maxlines>,<mode>,<output>,<maxproclines>]
log.count[<file>,<regexp>,<encoding>,<maxlines>,<mode>,<output>,<maxproclines>]
```

Параметры:

| Параметр | Значение |
|---|---|
| `file` (для `log`) | Абсолютный путь к файлу |
| `file_regexp` (для `logrt`) | Регулярное выражение, под которое подпадают имена файлов (без пути) |
| `regexp` | POSIX-регулярное выражение для отбора строк. При пустом значении передаются все новые строки |
| `encoding` | Кодировка файла (`UTF-8`, `cp1251`, …); по умолчанию UTF-8 |
| `maxlines` | Максимум новых строк в секунду, отправляемых агентом (защита от шторма) |
| `mode` | `all` (по умолчанию), `skip` (пропустить старые строки при старте), `front` (только с начала файла при ротации) |
| `output` | Шаблон формата строки, `\0` — вся строка, `\1`…`\9` — группы |
| `maxproclines` | Максимум строк в секунду для обработки (для тяжёлых regexp) |

### Поведение и производительность

* Агент отслеживает позицию файла и через агентский буфер отправляет новые строки.
* `logrt` определяет файл по имени; при ротации агент переключается на новый файл, но **продолжает читать старый до конца**.
* Регулярные выражения в `log[]` выполняются на агенте, поэтому сложные паттерны нагружают CPU хоста — следите за `maxproclines`.
* Число активных `log`-элементов и объём читаемых файлов влияют на `BufferSize` (часть значений может вытесняться при переполнении).

### Числовые метрики из логов

`log.count`/`logrt.count` возвращают число совпадений и удобны для построения графиков и триггеров по «порогу ошибок за минуту», в отличие от текстовых `log`, где триггер строится на факте совпадения.

## Практические сценарии

### Предварительные требования

* Активный агент: заданы `ServerActive` и `Hostname` (см. [Режимы работы агентов](./zabbix_agent_checks.md)).
* Пользователь `zabbix` имеет право чтения логов (часто требуется добавить в группу `adm`/`systemd-journal`).
* Хост создан в Zabbix, элементы данных — тип `Zabbix agent (active)`.

### Сценарий 1. Мониторинг появления ошибок

Элемент данных:

* **Type:** `Zabbix agent (active)`;
* **Key:** `log[/var/log/app/app.log,ERROR|FATAL,UTF-8,,skip,,]`;
* **Type of information:** `Log` (текстовая запись с меткой времени).

Триггер — на факт получения новой строки:

```
length(last(/web01/log[/var/log/app/app.log,ERROR|FATAL,UTF-8,,skip,,]))>0
```

Для дедупликации в `output` извлекается уникальный фрагмент (например, код ошибки), чтобы одинаковые строки не считались разными.

### Сценарий 2. Ротируемый лог приложения

```
logrt[/var/log/nginx/access.log.*,GET /health,UTF-8,,skip,,]
```

`file_regexp` покрывает `access.log`, `access.log.1`, `access.log-20261014`. При ротации агент дочитывает старый файл и переходит на новый.

### Сценарий 3. Счётчик ошибок за интервал

```
log.count[/var/log/app/app.log,ERROR,UTF-8]
```

Триггер «слишком много ошибок»:

```
sum(/web01/log.count[/var/log/app/app.log,ERROR,UTF-8],5m)>50
```

### Сценарий 4. Извлечение поля (output template)

Строка `2026-10-14 12:00:01 [pool-1-thread-3] ERROR com.example.Service - timeout after 30s`. Ключ:

```
log[/var/log/app/app.log,"ERROR (.*)",UTF-8,,all,\1]
```

Вернёт `com.example.Service - timeout after 30s` — удобно для группировки и текста события.

### Сценарий 5. Обнаружение «зависшего» лога

Элемент с пустым regexp и триггером `nodata()`:

```
log[/var/log/app/heartbeat.log,,UTF-8,,skip]
```

```
nodata(/web01/log[/var/log/app/heartbeat.log,,UTF-8,,skip],10m)=1
```

Если сервис перестал писать heartbeat — лог «молчит» 10 минут, срабатывает триггер.

### Проверка

```bash
# Доступность файла пользователю zabbix
sudo -u zabbix test -r /var/log/app/app.log && echo readable
# → readable

# Активные проверки включены у агента
grep -i "active check" /var/log/zabbix/zabbix_agentd.log | tail
# → enabling active checks on ...
```

## Операции и команды

| Задача | Команда |
|---|---|
| Проверить чтение файла под zabbix | `sudo -u zabbix head -1 /var/log/app/app.log` |
| Проверить ключ локально | `zabbix_agentd -t "log[/var/log/app/app.log,ERROR,UTF-8,,skip]"` |
| Новые значения в UI | `Monitoring → Latest data` по элементу |
| Лог агента | `/var/log/zabbix/zabbix_agentd.log` |

```bash
# Локальный запуск проверки (одноразово, вне активного режима)
zabbix_agentd -t "log[/var/log/syslog,error]"
# → log[...]  [s|<найденная строка>]
```

## Устранение неисправностей

### «Cannot open file» / элемент Unsupported

* У пользователя `zabbix` нет прав на файл или на каталог (нужен доступ на чтение каталога для слежения).
* Неверный путь или файл ещё не создан.
* Для SELinux — контекст, запрещающий агенту чтение.

### Элемент создан, но значения не приходят

* Элемент имеет тип **пассивный** (`Zabbix agent`) — `log`/`logrt` так не работают. Переключить на `Zabbix agent (active)`.
* У агента не задан `ServerActive`/`Hostname` или активные проверки отключены.
* Строки не совпадают с regexp (проверить regexp; POSIX, не PCRE).

### Пропуск строк / «задержка» логов

* Низкий `maxlines`/`maxproclines` — агент троттлит поток строк. Увеличить, если хост справляется.
* Переполнение `BufferSize` при недоступности сервера — увеличить буфер и/или `PersistentBuffer`.

### Проблемы при ротации

* Для `log` (не `logrt`) ротация приведёт к «залипанию» на старом файле по inode. Использовать `logrt` с корректным `file_regexp`.
* `mode=skip` пропускает старые строки при старте — это ожидаемо; для чтения с начала использовать `front`.

### Дублирование событий

* Regexp совпадает со старыми строками после перезапуска агента. Использовать `skip` и/или output-шаблон с уникальным полем.

## Лучшие практики

* **Только активные проверки** для `log`/`logrt` — это не ограничение, а требование архитектуры.
* **Один элемент на тип события**, а не «один на весь лог» — точечные regexp снижают шум и нагрузку.
* **`logrt` для всего, что ротируется**; никогда не вешайте `log[]` на файл под `logrotate`.
* **Троттлинг** (`maxlines`, `maxproclines`) защищает агент и сеть от шторма при всплеске логов.
* **`log.count` для количественных алертов** («>N ошибок за 5 мин»), `log` — для факта и текста события.
* **Следите за правами** и ростом объёма: чтение огромных логов нагружает агент; разумнее логировать только важные события.
* **Не собирайте логи через Zabbix там, где есть ELK/Loki** — тяжёлые полнотекстовые задачи эффективнее в специализированных системах; Zabbix оставьте для событийно-ориентированных алертов.
