# Zabbix — триггеры и выражения

**Актуально для:** Zabbix 7.0 LTS / 7.4

Документ описывает язык триггерных выражений, функции, режимы генерации OK-событий, зависимости и семантику неизвестных значений. Принципы проектирования триггеров (гистерезис, снижение ложных срабатываний, тегирование) — в **[Лучших практиках](./zabbix_best_practices.md)**.

---

## Определения

* **Триггер (Trigger)** — логическое выражение, которое оценивает данные элементов и определяет текущее состояние системы. Триггер меняет состояние и порождает событие.
* **Problem expression** — основное выражение, определяющее условие проблемы. Проблема создаётся, когда выражение вычисляется в TRUE.
* **Recovery expression** — дополнительное (необязательное) выражение, определяющее условие восстановления. Используется для гистерезиса.
* **OK event generation** — режим генерации OK-события: `Expression`, `Recovery expression`, `None`.
* **OK event closes** — какие проблемные события закрывает OK-событие: `All problems` или `All problems if tag values match` (trigger-level корреляция).
* **Hysteresis (гистерезис)** — разные пороги срабатывания и восстановления, устраняющие дребезг триггера.
* **Unknown** — состояние, когда значение выражения не может быть вычислено (неподдерживаемый элемент, ошибка функции).
* **Evaluation period (период оценки)** — интервал, по которому функция анализирует историю: время (`10m`) или количество значений (`#5`).

## Основные концепции

### Состояния и модель событий

Триггер имеет три состояния:

| Состояние | Описание |
|---|---|
| **OK** | Нормальное состояние. |
| **Problem** | Условие проблемы выполнено. |
| **Unknown** | Значение нельзя вычислить (неподдерживаемый элемент, ошибка функции). |

Каждое изменение состояния порождает событие. Типы событий от триггера — **Problem** и **OK**:

* **Problem** создаётся, когда problem expression вычисляется в TRUE и триггер в состоянии OK (или при каждом выполнении выражения, если включена генерация множественных проблемных событий).
* **OK** закрывает связанное проблемное событие и создаётся на основе настройки `OK event generation` (либо корреляцией событий, либо ручным закрытием через task manager).

### Пересчёт триггера

* Триггер пересчитывается **при каждом поступлении нового значения**, если выражение ссылается на этот элемент.
* При поступлении нового значения пересчитываются **все функции** выражения, а не только затронутая.
* Если в выражении используются функции времени (`date()`, `time()`) или `nodata()`, триггер дополнительно пересчитывается каждые **30 секунд**.
* Новый (или включённый) триггер вычисляется сразу после получения первого значения; для `nodata()`/времени — в течение 30 секунд.

### Период оценки (evaluation period)

Функции, работающие с историей, принимают период оценки:

* **Временной интервал:** `30s`, `10m`, `1h`, `1d` — все значения между «now − период» и «now».
* **Количество значений:** `#5` — пять последних значений.
* **Сдвиг во времени (time shift):** `1d` перед периодом, например `avg(/host/load,10m,1d)` — среднее за 10 минут сутки назад.

Отсчёт ведётся от времени последнего пересчёта триггера, а не от «серверного now». Если за указанный период данных нет, элемент/выражение становится **неподдерживаемым**.

### Основные функции выражений

| Функция | Назначение |
|---|---|
| `last()` | Последнее значение |
| `avg()`, `min()`, `max()`, `sum()` | Агрегаты за период |
| `count()` | Число значений, соответствующих условию (или всех) |
| `change()`, `abschange()` | Разница с предыдущим значением (со знаком / по модулю) |
| `delta()`, `prev()` | Абсолютное изменение `last-prev` / предыдущее значение |
| `nodata()` | Отсутствие поступления данных за период |
| `band()`, `percentile()` | Статистические метрики |
| `forecast()`, `timeleft()` | Линейное прогнозирование (значение через интервал / время до порога) |
| `date()`, `time()`, `now()` | Текущая дата/время/метка времени |
| `fuzzytime()` | Сравнение локального времени с временем агента (проверка рассинхрона) |

**Суффиксы значений:** `K`, `M`, `G`, `T` (кило/мега/гига/тера) и `s`, `m`, `h`, `d`, `w` (секунды/минуты/часы/дни/недели).

### Операторы и приоритет

Поддерживаются: `+ - * /`, `= <> < > <= >=`, `and`, `or`, `not`, скобки, а также `~` (регулярное выражение) и `band` (побитовое И). Приоритет: скобки → арифметика → сравнение → `and`/`or`/`not`. Явные скобки обязательны для читаемости сложных условий.

### OK event generation

| Режим | Условие OK-события |
|---|---|
| `Expression` (по умолчанию) | Problem expression стал FALSE |
| `Recovery expression` | Problem expression FALSE **и** recovery expression TRUE |
| `None` | OK-событие не генерируется никогда (триггер сам не вернётся в OK) |

### Гистерезис

Гистерезис нужен, когда простой порог даёт дребезг. Пример: проблема — температура выше 20 °C; восстановление — только когда она опустится ниже 15 °C.

```default
Problem expression:  last(/srv/temp)>20
Recovery expression: last(/srv/temp)<15
```

Порядок разрешения проблемы двухступенчатый: сначала problem expression должен стать FALSE, затем recovery expression — TRUE. Recovery expression не может разрешить проблему, пока problem expression всё ещё TRUE. Использовать `{TRIGGER.VALUE}` в recovery expression бессмысленно — на момент его вычисления триггер всегда в состоянии Problem (`{TRIGGER.VALUE}` = 1).

### Неизвестные операнды (Unknown)

Если в выражении встречается неподдерживаемый элемент или функция завершается ошибкой, выражение в общем случае вычисляется в **Unknown**. Важное следствие: выражение, ставшее Unknown, **не меняет состояние** триггера. Например, если проблема была открыта, а после сбоя данных выражение стало Unknown, триггер **останется** в состоянии Problem. Некоторые операторы (в частности, `and`/`or` при известном втором операнде) вычисляются до определённого результата, невзирая на Unknown.

### OK event closes и корреляция

* `All problems` — OK-событие закрывает все открытые проблемы этого триггера.
* `All problems if tag values match` — закрываются только проблемы с совпадающим значением тега (`Tag for matching`). Это trigger-level корреляция: позволяет различать проблемы по тегу (например, по `service`).
* **Ручное закрытие** разрешается настройкой `Allow manual close`: пользователь закрывает проблему, создаётся задача `close event`, task manager генерирует соответствующее OK-событие.

### Зависимости триггеров

Зависимость (Trigger dependency) подавляет проблемные события зависимого триггера, пока активна проблема родительского. Классический случай: недоступность хоста (`agent.ping` = 0) подавляет все триггеры по метрикам этого хоста, устраняя «шторм» событий. Зависимости создаются на уровне триггера в веб-интерфейсе.

## Практические сценарии

### Предварительные требования

* Настроенные элементы данных, на которые будут ссылаться триггеры (см. **[Элементы данных](./zabbix_items.md)**).
* Права на редактирование шаблона/хоста.
* Понимание ожидаемого поведения метрики (порог, частота поступления данных).

### Сценарий 1. Создание простого порогового триггера

Data collection → Hosts/Templates → Triggers → Create trigger:

* `Name`: `CPU load too high on {HOST.NAME}`.
* `Severity`: Warning.
* `Expression`: `avg(/host/system.cpu.load,5m)>4`.
* `OK event generation`: Expression.

Использование `avg(...,5m)` вместо `last()` снижает реакцию на кратковременные пики.

### Сценарий 2. Гистерезис для устранения дребезга

```default
Problem expression:  min(/app/disk.used.pct,5m)>90
Recovery expression: max(/app/disk.used.pct,5m)<85
```

OK event generation = `Recovery expression`. Проблема не закроется, пока использование не опустится ниже 85 % и не продержится так до выполнения условия.

### Сценарий 3. Проверка доступности и подавление шторма

Триггер доступности (родитель):

```default
Problem expression: nodata(/host/agent.ping,3m)=1
```

Дочерние триггеры (метрики CPU, диск, сервисы) помечаются зависимыми от него — при недоступности хоста их проблемы не генерируются.

### Сценарий 4. Предиктивный триггер (forecast)

```default
Problem expression: timeleft(/db/fs.used,1h,100G)<1h
```

Проблема, если при текущем тренде заполнения место на ФС исчерпается менее чем за час. Требует достаточной истории и линейного характера роста.

### Сценарий 5. Триггер рассинхрона времени (NTP)

```default
Problem expression: fuzzytime(/host/system.localtime,60s)=0
```

Проблема, если локальное время хоста отличается от времени Zabbix-сервера более чем на 60 секунд (см. настройку time sync в **[Установке](./installation.md)**).

### Валидация

* Кнопка **Test** в форме триггера: подставить тестовые значения и проверить срабатывание выражения.
* Проверить сам элемент: Monitoring → Latest data, либо через ключ агента.
* Убедиться, что состояние триггера меняется при изменении метрики (Monitoring → Problems).

## Операции и команды

```bash
# Список триггеров с состоянием через API
curl -s -X POST -H 'Content-Type: application/json-rpc' \
  -H 'Authorization: Bearer <TOKEN>' \
  -d '{"jsonrpc":"2.0","method":"trigger.get","params":{"output":["triggerid","description","value","priority"]},"id":1}' \
  http://zabbix.example.com/zabbix/api_jsonrpc.php
# → value: "0" (OK) / "1" (Problem), priority: 0..5 (Not classified..Disaster)
```

| Поле API | Значение |
|---|---|
| `value` | `0` — OK, `1` — Problem |
| `recovery_mode` | `0` — Expression, `1` — Recovery expression, `2` — None |
| `correlation_mode` | `0` — All problems, `1` — All problems if tag values match |
| `status` | `0` — enabled, `1` — disabled |
| `priority` | `0`–`5` — важность (Information…Disaster) |

## Устранение неисправностей

| Симптом | Причина | Решение |
|---|---|---|
| Триггер остаётся Problem после восстановления метрики | Включён `Recovery expression`, но условие восстановления не выполнено; или `OK event generation = None` | Проверить/упростить recovery expression; сменить режим |
| Триггер «дребезжит» OK↔Problem | Пороги срабатывания и восстановления совпадают | Ввести гистерезис (`avg`/`min` + recovery expression) |
| Триггер не переходит в OK при явном восстановлении | Выражение стало `Unknown` из-за сбоя данных | Восстановить элемент; Unknown не меняет состояние |
| Триггер не срабатывает | Неверный ключ/период оценки; нет данных за период | Проверить элемент (Latest data), увеличить период, проверить поддержку элемента |
| Массовые ложные проблемы при недоступности хоста | Нет зависимостей триггеров | Сделать метрические триггеры зависимыми от `agent.ping`/ICMP |
| `avg()/last()` возвращает пусто | Нет данных за evaluation period | Проверить интервал опроса и историю элемента |
| Проблема не разрешается вручную | `Allow manual close` выключен | Включить в настройках триггера |

## Лучшие практики

* **Использовать периоды вместо `last()`** там, где метрика шумная (`avg`/`min` за 5 минут).
* **Гистерезис вместо единого порога** для ресурсных метрик (диск, температура, память).
* **Зависимости — обязательны** для метрик хоста, чтобы не порождать события при его недоступности.
* **Теги на триггерах** (`service`, `scope`, `severity`) упрощают маршрутизацию, корреляцию и SLA-отчётность (см. **[Inventory и отчётность](./zabbix_inventory_and_reporting.md)**).
* **Разделять важность (severity):** `Warning`—`Average`—`High`—`Disaster` должны соответствовать реальной критичности, иначе возникает alert fatigue.
* **Не злоупотреблять режимом `None`** — он оставляет проблему «вечно открытой».
* **Тестировать выражения** кнопкой Test до включения триггера.
