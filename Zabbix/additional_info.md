# Zabbix — внутреннее устройство и архитектура процессов

Данный документ описывает внутренние механизмы, архитектуру демонов и рабочие процессы, обеспечивающие функционирование Zabbix Server и Zabbix Proxy. Сведения актуальны для **Zabbix 7.0 LTS** и **Zabbix 7.4** (текущая стандартная ветка). **Zabbix 8.0 LTS** на момент сверки не выпущен: доступен кандидат в релиз **8.0.0rc1 (1 октября 2026)**, выпуск GA запланирован на Q4 2026 (по roadmap — ноябрь 2026), поэтому особенности версии 8.0 отмечены по тексту и приведены по предрелизным данным. Архитектура асинхронных поллеров и общая модель демонов сохраняются и в 8.0. Для настройки производительности кэшей и решения проблем с очередями обращайтесь к разделу **[Тюнинг и устранение неисправностей](./zabbix_troubleshooting_and_performance_tuning.md)**.

## Определения

* **Процесс запуска Zabbix Server** — последовательность инициализации внутренних компонентов системы при старте службы, включающая загрузку параметров конфигурации, синхронизацию с базой данных и активацию рабочих процессов.
* **Воркер (Worker / Daemon)** — специализированный фоновый процесс Zabbix, выполняющий строго определенную задачу (например, сбор метрик, очистку базы данных или расчет триггеров). Количество экземпляров каждого типа задается параметрами `Start*` в конфигурационном файле.
* **NVPS (New Values Per Second)** — количество новых значений, записываемых в базу данных за секунду; ключевой метрический показатель производительности мониторинга с точки зрения SRE.
* **Инкрементальная загрузка конфигурации** — механизм обновления кэша конфигурации Zabbix Server (введен в Zabbix 7.0, сохранен в 8.0), при котором в память из базы данных загружаются только измененные объекты. Снижает нагрузку на СУБД и ускоряет применение настроек.
* **Кэш конфигурации (Configuration Cache)** — разделяемый сегмент памяти, хранящий данные о хостах, элементах данных, триггерах и интервалах опроса. Управляется процессом `configuration syncer`. Размер задается параметром `CacheSize` (по умолчанию 32M). Период обновления — `CacheUpdateFrequency` (по умолчанию 10 секунд).
* **Shared Memory** — блок разделяемой оперативной памяти, используемый Zabbix для кэшей (History, Value, Configuration). Размер задается параметром `MemSize` в `zabbix_server.conf`. При переполнении сервер пишет предупреждение в лог и начинает сбрасывать данные на диск, что ведет к разрывам на графиках (Gaps).
* **Self-monitoring** — встроенный механизм сбора внутренних статистических данных сервера (нагрузка поллеров, объем очередей, утилизация кэшей); на них строятся элементы данных шаблона `Zabbix server health`.

## Основные концепции

### Архитектура рабочих процессов (Daemons)

Производительность Zabbix зависит от слаженной работы пула специализированных демонов. Сервер запускает процессы по типам (`poller`, `trapper`, `history syncer` и т.д.); количество экземпляров каждого типа задается параметрами `Start*` в `zabbix_server.conf`. Ниже представлены ключевые внутренние процессы.

#### 1. Сбор данных (Data Gathering)

Начиная с версии 7.0, Zabbix перевел значительную часть проверок на асинхронную модель для повышения пропускной способности. В Zabbix 8.0 асинхронная модель остается стандартом.

* **Async Pollers (Асинхронные поллеры):** один процесс (`agent poller`, `http agent poller`, `snmp poller`) поддерживает до 1000 параллельных проверок (параметр `MaxConcurrentChecksPerPoller`, по умолчанию 1000), не блокируясь в ожидании ответа. Запуск: `StartAgentPollers`, `StartHTTPAgentPollers`, `StartSNMPPollers` (по умолчанию по 1).
* **Pollers (Синхронные поллеры):** классические процессы для остальных пассивных проверок и веб-мониторинга: `poller` (обычные пассивные проверки), `http poller` (веб-сценарии/веб-страницы), `internal poller` (внутренние проверки сервера), `odbc poller` (проверки ODBC), `java poller` (JMX через Java Gateway), `icmp pinger` (ICMP-пинги), `ipmi manager`/`ipmi poller` (IPMI). Запуск через `StartPollers`, `StartHTTPPollers`, `StartODBCPollers`, `StartJavaPollers`, `StartPingers`, `StartIPMIPollers`.
* **Browser Poller:** процесс `browser poller` для выполнения сложных веб-сценариев через управляемый браузер (например, Selenium). Запуск: `StartBrowserPollers` (по умолчанию 1). Использует отдельный `Zabbix web service` (порт 10053) для рендеринга.
* **Trappers:** прослушивают входящие TCP-соединения для приема данных по модели Push (от `zabbix_sender`, Zabbix Proxy или активных агентов). Запуск: `StartTrappers` (по умолчанию 5).
* **SNMP trapper:** принимает SNMP-ловушки (traps), записанные во временный файл trap-демоном (`SNMPTrapperFile`). Запуск: `StartSNMPTrapper` (по умолчанию 0 — выключен).
* **Proxy Poller:** опрашивает пассивные Zabbix Proxy. Также отвечает за отправку конфигурации и запрос данных. Запуск: `StartProxyPollers` (по умолчанию 1).
* **VMware Collector:** собирает данные через vCenter/ESXi (`StartVMwareCollectors`, по умолчанию 0). Один процесс на vCenter/ESXi.
* **Unreachable Poller:** обрабатывает периодические проверки недоступных хостов, чтобы разблокировать основные поллеры. Запуск: `StartPollersUnreachable` (по умолчанию 1).

#### 2. Обработка и сохранение данных

* **Preprocessing Manager / Workers:** процессы, отвечающие за предварительную трансформацию данных (парсинг JSON, извлечение по регулярным выражениям, расчет дельт) перед их записью. Менеджер координирует задачи, воркеры — исполняют (в 7.0+ воркеры выполняются как потоки). Запуск: `StartPreprocessors` (по умолчанию 16; не меньше числа ядер CPU, если предобработка CPU-интенсивная).
* **History Syncers:** критически важные процессы. Забирают обработанные данные из History Cache, производят вычисление триггеров на их основе и записывают (сбрасывают) значения в базу данных. Запуск: `StartDBSyncers` (по умолчанию 4; слишком много — лишние подключения к БД).
* **History Poller:** обрабатывает вычисляемые проверки (calculated checks) и элементы, требующие обращения к базе данных. Запуск: `StartHistoryPollers` (по умолчанию 5).
* **Configuration Syncer:** периодически (интервал `CacheUpdateFrequency`, по умолчанию 10 секунд) обновляет внутренний Configuration Cache данными из БД; в Zabbix 7.0+ применяет инкрементальную загрузку. Это **одиночный** процесс: отдельного параметра `Start*` для него не существует, масштабировать его количество нельзя. Чем больше `CacheSize` (то есть чем больше хостов, элементов и триггеров), тем дольше применяются изменения конфигурации — размер увеличивают только при стабильной утилизации выше 80%.
* **Configuration Syncer Worker (с 7.0):** вспомогательный процесс, разрешает и синхронизирует пользовательские макросы в именах элементов данных.
* **Task Manager:** выполняет административные задачи, приходящие от фронтенда: закрытие/подтверждение проблем, «проверить значение сейчас», выполнение удаленных команд.
* **Service Manager:** управляет сервисными ИТ-услугами (автоматические проблемы и root cases) на основе потока от `history syncer`, `task manager` и `alert manager`. Частота синхронизации — `ServiceManagerSyncFrequency` (по умолчанию 60 с).

#### 3. Обслуживание и автоматизация

* **Хранение данных (History vs Trends):**
    * **История (History):** сырые данные, сохраняемые точка за точкой. Обеспечивает максимальную детализацию графиков, но занимает большой объем в БД.
    * **Тренды (Trends):** почасовые агрегаты (минимум, среднее, максимум за час). Используются для долгосрочного хранения (годы) и быстрого построения графиков за большие периоды.
* **Housekeeper (Сборщик мусора):** фоновый процесс, запускающийся по расписанию (по умолчанию раз в час, `HousekeepingFrequency=1`) для удаления устаревших исторических данных и трендов. Без его корректной работы база данных бесконтрольно разрастается, что ведет к деградации производительности.
    * В Zabbix 8.0 процесс удаления через Housekeeper был изменен для работы с housekeeper table API (`ZBXNEXT-10076`).
    * При использовании PostgreSQL + TimescaleDB процесс Housekeeper работает максимально эффективно, так как удаляет данные целыми партициями (chunks).
* **Trigger Housekeeper:** отдельный демон, удаляющий проблемы и события, созданные для уже удаленных триггеров (периодичность — `ProblemHousekeepingFrequency`, по умолчанию 60 с).
* **Timer:** процесс, отвечающий за вычисление функций времени в триггерах (например, `nodata()`, `count()`, `time()`), а также периодами обслуживания (Maintenance) — период активного обслуживания обновляет только первый timer process.
* **Discovery Manager / Workers (с версии 7.0):** процессы для параллельного сетевого обнаружения (Network Discovery), значительно ускоряющие сканирование больших подсетей.
* **LLD Manager / Workers:** менеджер низкоуровневого обнаружения (Low-Level Discovery) и его воркеры; находят и создают элементы, триггеры, сценарии на основе шаблонов.
* **Escalator:** обрабатывает логику эскалации действий и рассылки оповещений (Alerts). Работает в паре с процессом `alerter`; эскалатор вычисляет шаги, а их фактическую доставку выполняет alerter.

#### 4. Оповещение (Alerts) и отчеты

* **Alert Manager:** хранит очередь для генерации собственно оповещений для дальнейшей обработки.
* **Alert Syncer:** отвечает за запись оповещений (alerts) в базу данных.
* **Alerter:** процесс, который фактически доставляет оповещения через соответствующие типы медиа (электронная почта, вебхуки, скрипты). Запуск: `StartAlerters` (по умолчанию 3).
* **Report Writer (и Report Manager):** генерация плановых отчетов (PDF, экспорт в Report). Включается параметром `StartReportWriters` (по умолчанию 0 — отключено; для работы также требуется отдельный процесс `zabbix-web-service` на порту 10053 и параметр `WebServiceURL`).

#### 5. Служебные и инфраструктурные процессы

* **HA Manager:** `ha manager` — управляет узлами кластера High Availability. Работает только при включенном `HANodeName`.
* **Availability Manager:** процесс, обновляющий состояние доступности хостов.
* **Self-monitoring:** процесс, который собирает внутренние статистические данные сервера (нагрузку поллеров/синхронизаторы, объем очередей) — на них строятся элементы данных `Zabbix server health`.
* **Connector Manager / Worker (с 7.0):** менеджер и воркеры для коннекторов — интеграций со сторонними платформами (например, экспорт в SIEM/BI).

### Последовательность запуска сервера

При старте службы `zabbix-server` система выполняет следующие этапы инициализации:

1. **Чтение конфигурации:** загрузка параметров из файла `zabbix_server.conf`.
2. **Аллокация памяти:** создание и инициализация разделяемых сегментов памяти (Shared Memory) для кэшей (History, Value, Configuration).
3. **Проверка схемы БД:** верификация соответствия версии базы данных текущему бинарному файлу сервера.
4. **Запуск HA-менеджера:** активация процессов обеспечения высокой доступности (High Availability cluster), если параметр `HANodeName` сконфигурирован.
5. **Первичная загрузка кэша:** наполнение оперативной памяти данными о хостах, элементах и триггерах из базы данных.
6. **Активация воркеров:** запуск основного пула процессов (`pollers`, `trappers`, `syncers`).

### Ограничения архитектуры и краевые случаи

Знание этих ограничений важно при планировании мощности и диагностике деградации:

* **Configuration Syncer не масштабируется** — это одиночный процесс. Рост числа хостов, элементов и триггеров увеличивает время применения изменений конфигурации; смягчается только уменьшением размера конфигурации, а не добавлением процессов.
* **History Syncers:** штатных 4 процессов достаточно примерно до 4000 NVPS. Увеличение количества повышает параллелизм записи, но не производительность БД (и иногда вредит ей), поэтому `StartDBSyncers` поднимают только после исчерпания других оптимизаций (партиционирование, TimescaleDB, разделение истории по партициям).
* **Асинхронные поллеры применимы не ко всем типам проверок:** они используются только для `agent`, `http agent` и `snmp`, и именно для них число одновременных проверок на процесс ограничено параметром `MaxConcurrentChecksPerPoller` (по умолчанию 1000). Синхронные поллеры (ICMP, JMX, ODBC, IPMI и др.) обрабатывают по одной проверке на процесс.
* **Буфер Proxy в режиме `memory`:** при переполнении данные теряются; при перезапуске прокси несохранённый буфер также теряется. Для устойчивости к сбоям используют `ProxyBufferMode=hybrid` (сохранение на диск) или `disk`.
* **Housekeeper:** без TimescaleDB удаление исторических данных выполняется построчно и создаёт высокую нагрузку на БД; с TimescaleDB данные удаляются сбросом целых чанков, что значительно дешевле.
* **Value Cache miss:** если запрошенное значение триггера отсутствует в Value Cache, сервер выполняет прямой `SELECT` из БД, что при частых промахах превращается в постоянную нагрузку на базу.
* **Trends и детализация графиков:** тренды — это почасовые агрегаты; на графике они появляются с задержкой до 2 часов. Для старых данных доступна только трендовая гранулярность, а не исходная история.
* **Scheduled reports и Browser items** требуют отдельного сервиса `zabbix-web-service` (по умолчанию порт 10053), без которого задачи встают в очередь и завершаются ошибкой.

### Изменения в Zabbix 8.0 LTS

* **Trend function cache monitoring:** добавлен внутренний элемент `zabbix[tcache,cache,paccessed]` (`ZBXNEXT-10480`), возвращающий процент записей кэша функций трендов, к которым было обращение за последние 24 часа.
* **Housekeeper table API:** изменен процесс отложенного удаления данных через housekeeper table API (`ZBXNEXT-10076`), что влияет на управление хранилищем в установках с большим объемом исторических данных.
* **ClickHouse backend:** поддержка ClickHouse в качестве дополнительного хранилища исторических данных (LOG/TEXT/CHAR → Elasticsearch, числовые → PostgreSQL, JSON → ClickHouse). Снижает нагрузку на основной SQL-бэкенд при больших объемах структурированных данных. Устаревшие параметры `HistoryStorageURL`, `HistoryStorageDateIndex` и `HistoryStorageTypes` заменены единым параметром `HistoryProvider`.
* **JSON data type:** нативный тип данных JSON для элементов данных, что упрощает работу с неструктурированными и полуструктурированными данными (`ZBXNEXT-10069`).
* **CEP Correlation Engine:** новый движок корреляции событий (Complex Event Processing) для связывания событий в контекстные группы и автоматического добавления контекста к проблемам. Существующие глобальные правила корреляции помечены как устаревшие (legacy), но сохраняются для обратной совместимости.
* **Scatter Plot widget:** новый виджет для визуализации корреляций между двумя метриками (оси X и Y), выявления кластеров и аномалий.
* **Elasticsearch improvements:** сервер теперь повторно использует существующие соединения с Elasticsearch вместо открытия нового для каждого запроса, что снижает накладные расходы.

## Практические сценарии

### Предварительные требования

* Zabbix Server (`zabbix-server`) 7.0 LTS / 7.4 установлен и запущен; для части проверок дополнительно нужна утилита `zabbix-get`.
* Доступ к конфигурационному файлу `/etc/zabbix/zabbix_server.conf` и лог-файлу `/var/log/zabbix/zabbix_server.log`.
* К самому серверу подключён шаблон `Template App Zabbix Server`, а к каждому прокси — `Template App Zabbix Proxy` (для self-monitoring).
* Права суперпользователя либо членство в группе `zabbix` для чтения конфигурации и запуска служебных команд.

### Анализ процесса запуска через логи

Для диагностики проблем при старте сервера рекомендуется использовать лог-файл (обычно `/var/log/zabbix/zabbix_server.log`).

Основные сообщения об успешном прохождении этапов:
* `Starting Zabbix Server. Zabbix 8.0.x (revision ...).` — начало запуска.
* `using configuration file: /etc/zabbix/zabbix_server.conf` — файл прочитан.
* `current database version (main/optional): 08000000/08000000` — версия БД корректна. Если процесс прерывается здесь, проверьте правильность импорта схемы SQL.
* `server #0 started [main process]` — сервер и основные воркеры успешно запущены.

Наблюдение за живыми процессами (вариант для Linux):
```bash
ps -eo pid,cmd | grep zabbix_server
# → пример вывода (описательное "процесс-тип #номер [task]")

# Утилизация процессов через внутренний элемент Zabbix:
zabbix_get -s 127.0.0.1 -k "zabbix[process,poller,avg,busy]"
```

### Управление внутренними процессами (Runtime Control)

Администратор может отправлять команды работающему Zabbix Server без его перезапуска через утилиту командной строки (`zabbix_server -R <command>`):

* `config_cache_reload` — принудительно обновить кэш конфигурации (полезно после массовых изменений в БД или веб-интерфейсе). Игнорируется, если кэш в данный момент уже загружается.
* `housekeeper_execute` — запустить процесс очистки мусора вне расписания (Housekeeper).
* `trigger_housekeeper_execute` — запустить Trigger Housekeeper для удаления устаревших проблем удаленных триггеров.
* `log_level_increase=<process_type>` / `log_level_decrease` — повысить/понизить уровень логирования для конкретного пула процессов (например, `poller` или `history syncer`) для глубокой отладки (Troubleshooting). Поддерживается цель: тип процесса, `тип,номер` (например `poller,2`) или PID.
* `snmp_cache_reload` — перезагрузить кэш SNMP (после смены учетных записей SNMPv3-интерфейсов или при аномалиях с engineBoots/engineID).
* `secrets_reload` — перезагрузить секреты, хранящиеся в Vault (не требует перезапуска сервера).
* `ha_status` — вывести статус нод в кластере High Availability.
* `ha_remove_node[=<имя/ID>]` — удалить ноду из кластера HA; `ha_set_failover_delay[=<задержка>]` — изменить задержку фейловера.
* `prof_enable=<process_type>` / `prof_disable` — включить/отключить профилирование (детальные метрики rwlocks/mutex) для выбранного процесса.
* `diaginfo[=<секция>]` — собрать диагностическую информацию по внутренним подсистемам (`historycache`, `preprocessing`, `alerting`, `lld`, `valuecache`) в лог-файл сервера.

Пример (выполнение команды из консоли, результат виден в логе сервера):
```bash
zabbix_server -R config_cache_reload
# → "command sent successfully"
zabbix_server -R ha_status
# → вывод списков нод кластера HA
```

Для Zabbix Proxy доступно то же подмножество команд (`zabbix_proxy -R <command>`), включая `config_cache_reload` и `log_level_increase`.

### Наблюдение за процессами через внутренние метрики Zabbix

Каждый тип процесса можно отслеживать внутренними элементами данных (internal items) из шаблона `Zabbix server health`:

| Тип процесса | Пример элемента данных | Примечание |
| :--- | :--- | :--- |
| Загрузка поллеров | `zabbix[process,<тип>,avg,busy]` | Средняя/максимальная занятость процесса типа `<тип>` (например, `poller`, `history syncer`) |
| Загрузка всех процессов | `zabbix[process,,avg,busy]` | Общая утилизация демонов сервера |
| Очередь на опрос | `zabbix[queue,<интервал>]` | Количество элементов, чей опрос запаздывает |
| Пропускная способность | `zabbix[requiredperformance]` | Требуемая производительность — новых значений в секунду (NVPS) |
| Утилизация кэша истории | `zabbix[wcache,history,...]` | Заполненность History Cache |
| Утилизация кэша значений | `zabbix[vcache,buffer,pused]` | Заполненность Value Cache (критично для производительности триггеров) |
| Утилизация кэша конфигурации | `zabbix[rcache,buffer,<mode>]` | Заполненность Configuration Cache (`pused` — процент) |

Практическое правило: начинайте со значений по умолчанию и увеличивайте количество процессов (`Start*`) только при стабильной загрузке более 75% (подробнее — в разделе **[Тюнинг производительности](./zabbix_troubleshooting_and_performance_tuning.md)**).

### Capacity Planning для SRE

При проектировании инфраструктуры мониторинга на основе Zabbix SRE должен учитывать следующие параметры:

* **NVPS как целевой показатель:** определяйте требуемую пропускную способность (количество новых значений в секунду) до закупки железа. Для оценки используйте формулу: `NVPS ≈ (количество_хостов × среднее_число_элементов_на_хост) / средний_интервал_опроса_в_секундах`.
* **Дисковая подсистема:** критичный фактор для NVPS > 5000. PostgreSQL + TimescaleDB на NVMe/SSD с достаточным IOPS — стандарт для высоконагруженных систем. Включите компрессию TimescaleDB для данных старше 7 дней.
* **Память:** не менее 4 ГБ RAM (8 ГБ для >5000 NVPS). Shared Memory (`MemSize`) должен покрывать пиковую нагрузку на кэши; при переполнении сервер пишет в лог `Zabbix server is busy` и начинает сбрасывать данные на диск.
* **Сеть:** для WAN-сценариев (филиалы, дата-центры) используйте Zabbix Proxy. Zabbix Proxy Groups (с 7.0) обеспечивают нативный HA и балансировку нагрузки для прокси (аналогично Server HA).
* **Горизонтальное масштабирование:** Zabbix Server 8.0 поддерживает нативный HA-режим (с 6.0) и Proxy Groups (с 7.0), что позволяет строить отказоустойчивые кластеры без внешних балансировщиков на уровне прокси.

### Мониторинг мониторинга (Self-Monitoring)

Встроенный механизм self-monitoring собирает внутренние метрики, критичные для SRE:

* **Очереди (`zabbix[queue,...]`):** отражают отставание опроса. Рост очереди при стабильном NVPS указывает на недостаток поллеров или недоступность устройств.
* **Утилизация кэшей (`zabbix[wcache,...]`, `zabbix[cache,...]`):** показывают, хватает ли оперативной памяти для текущей нагрузки.
* **Внутренние метрики сервера:** `zabbix[process,<тип>,avg,busy]` позволяют выявлять узкие места без внешних инструментов.

Для полного сбора этих метрик настройте на самом Zabbix Server шаблон `Template App Zabbix Server` (встроенный). Он автоматически создаст элементы данных для отслеживания очередей, NVPS, утилизации кэшей и загрузки воркеров.

### Логирование и диагностика

Для SRE важно настроить структурированное логирование Zabbix:

* **Основной лог сервера:** `/var/log/zabbix/zabbix_server.log` (управляется параметром `LogFile`).
* **Уровень логирования:** по умолчанию `information`. Для диагностики конкретных проблем временно повышайте уровень через Runtime Control: `zabbix_server -R log_level_increase='poller'` или `zabbix_server -R log_level_increase='history syncer'`. После завершения диагностики понижайте: `zabbix_server -R log_level_decrease`.
* **Диагностическая команда `diaginfo`:** собирает диагностику по внутренним подсистемам в лог:
  ```bash
  zabbix_server -R diaginfo=historycache
  # → диагностика History Cache в логе
  zabbix_server -R diaginfo=preprocessing
  # → диагностика предобработки
  zabbix_server -R diaginfo=alerting
  # → диагностика оповещений
  ```
* **Логи прокси:** `/var/log/zabbix/zabbix_proxy.log` — аналогичная структура, полезны при отладке распределенных инсталляций.

## Устранение неисправностей

### Типичные проблемы при запуске

* **Сервер не стартует, лог пустой:** проверьте права на файл лога (`LogFile`), SELinux/AppArmor, доступность СУБД и корректность строки подключения (`DBHost`, `DBName`, `DBUser`, `DBPassword`).
* **Ошибка версии БД:** `current database version ... does not match` — импортируйте или обновите схему Zabbix через `mysql`/`psql` (см. официальную документацию по миграции).
* **Ошибка прав доступа к БД:** проверьте, что пользователь БД имеет права `SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, INDEX, ALTER` на схему Zabbix.
* **Сервер стартовал, но элементы в статусе `Unsupported`:** проверьте сетевую доступность агентов, корректность ключей элементов, работу поллеров (`zabbix[process,poller,avg,busy]`).

### Проблемы с очередями и кэшами

* **Рост очереди (`zabbix[queue,...]`):**
  * Причина 1: нехватка поллеров — увеличьте `StartPollers`, `StartAgentPollers`, `StartSNMPPollers` (для асинхронных моделей).
  * Причина 2: недоступность устройств — проверьте сеть, фаерволы, работу агентов.
  * Причина 3: медленная предобработка — увеличьте `StartPreprocessors` или оптимизируйте шаги preprocessing.
* **Переполнение History Cache (`zabbix[wcache,history,pused]` близко к 100%):**
  * Увеличьте `HistoryCacheSize` (по умолчанию 16M; для высоких NVPS — 64–256M).
  * Проверьте IOPS СУБД: диск не справляется с потоком записи. Переход на TimescaleDB или увеличение IOPS решает проблему.
* **Высокая заполненность Value Cache (`zabbix[vcache,buffer,pused]` близко к 100%):**
  * Увеличьте `ValueCacheSize` (по умолчанию 8M; для больших инсталляций — 32–128M).
  * Прямые `SELECT` в БД при вычислении триггеров «убивают» производительность СУБД; настройка кэша решает проблему.

### Проблемы с Housekeeper

* **База данных бесконтрольно растет:** проверьте, что `HousekeepingFrequency` > 0 и `MaxHousekeeperDelete` не слишком мал (по умолчанию 5000). При использовании TimescaleDB Housekeeper работает эффективнее за счет партиционирования.
* **Высокая нагрузка на СУБД во время очистки:** выполните Housekeeper в часы низкой нагрузки (`zabbix_server -R housekeeper_execute`) или увеличьте `MaxHousekeeperDelete` для ускорения одного цикла.

### Диагностика через `diaginfo`

Команда `zabbix_server -R diaginfo=<секция>` собирает детальную диагностику в лог:

```bash
zabbix_server -R diaginfo=historycache
# → размер, заполненность, количество элементов

zabbix_server -R diaginfo=preprocessing
# → очередь, скорость обработки, ошибки

zabbix_server -R diaginfo=alerting
# → очередь оповещений, доставленные/недоставленные

zabbix_server -R diaginfo=valuecache
# → попадания/промахи, утилизация
```

Для получения полной диагностики по всем подсистемам:
```bash
zabbix_server -R diaginfo
# → все доступные секции в логе
```

## Лучшие практики

### Производительность и масштабирование

* **Начинайте с параметров по умолчанию.** Увеличивайте `Start*` только при стабильной загрузке соответствующего процесса выше 75%. Избыточное количество воркеров создает лишние соединения с СУБД и расходует память.
* **Мониторьте NVPS, а не количество хостов.** 100 хостов с 1000 элементов каждый (100 000 элементов) при интервале 60с дают ~1667 NVPS. Проектируйте инфраструктуру под целевой NVPS с запасом 30–50%.
* **Используйте TimescaleDB или ClickHouse** для высоконагруженных инсталляций (>5000 NVPS). TimescaleDB — стандарт для числовых метрик и трендов; ClickHouse — для JSON и текстовых данных.
* **Включайте компрессию TimescaleDB** для данных старше 7 дней. Это снижает IOPS в 3–10 раз и ускоряет запросы к долгосрочной истории.
* **Для WAN-сценариев используйте Zabbix Proxy.** Прокси изолирует основной сервер от сетевых задержек, кэширует данные при нестабильной связи и снижает нагрузку на канал.
* **Используйте Proxy Groups (Zabbix 7.0+)** для автоматического переключения при отказе прокси и балансировки нагрузки между несколькими прокси в одной группе.

### Безопасность и операции

* **Версионируйте конфигурацию:** храните `zabbix_server.conf`, `zabbix_proxy.conf` и шаблоны в Git. Любое изменение должно быть отслеживаемым.
* **Настройте логирование в centralized SIEM:** отправляйте логи Zabbix в централизованный syslog (Graylog, ELK, Loki) для корреляции с событиями инфраструктуры.
* **Используйте Runtime Control вместо рестарта:** `config_cache_reload`, `log_level_increase`, `housekeeper_execute` позволяют влиять на сервер без прерывания сбора данных.
* **Регулярно проверяйте внутренние метрики:** шаблон `Zabbix server health` должен быть подключен к самому серверу и прокси. Настройте алерты на рост очередей, переполнение кэшей и падение NVPS.
* **Планируйте Capacity Review** раз в квартал: анализируйте тренды NVPS, роста хостов, заполнения диска и корректируйте `Start*` и размеры кэшей.
* **Держите процедуру очистки под рукой:** порядок штатного снятия компонентов и удаления данных описан в разделе **[Удаление и очистка](./installation.md#удаление-и-очистка)**.

### Резервное копирование и Disaster Recovery

* **Бэкап базы данных:** регулярный дамп PostgreSQL/MySQL/MariaDB + WAL-архивация (для PITR). Для TimescaleDB используйте `pg_dump` с отключенными триггерами или continuous archiving.
* **Бэкап конфигурации:** экспортируйте шаблоны, хосты, макросы через Zabbix API (`configuration.export`) и храните в Git.
* **Тестируйте восстановление:** раз в полгода выполняйте drill восстановления на тестовом стенде. Проверяйте время восстановления (RTO) и целостность данных.
