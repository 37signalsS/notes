# Zabbix — Zabbix Proxy

**Актуально для:** Zabbix 7.0 LTS / 7.4

Документ описывает распределённый мониторинг через Zabbix Proxy: режимы работы, механизмы буферизации данных, отказоустойчивость через Proxy Groups. Базовая установка прокси приведена в **[Установке](./installation.md)**, архитектура процессов — в **[Внутреннем устройстве](./additional_info.md)**.

---

## Определения

* **Zabbix Proxy** — отдельный демон (`zabbix_proxy`), который от имени Zabbix Server собирает данные мониторинга, выполняет часть обработки (предобработку, расчёт триггеров для локальных данных, network discovery) и передаёт результаты на сервер. Не имеет собственного веб-интерфейса и не хранит конфигурацию как источник истины — конфигурация приходит с сервера.
* **Активный прокси (active)** — прокси сам инициирует соединение с сервером, забирает у него конфигурацию и отправляет собранные данные. Требует только исходящего соединения с прокси на сервер. Рекомендуемый режим, в том числе для DMZ.
* **Пассивный прокси (passive)** — сервер сам подключается к прокси по известному адресу для получения данных. Требует, чтобы прокси принимал входящие соединения от сервера (порт `10051`).
* **Proxy Buffer** — буфер собранных данных (history, discovery, autoregistration) между моментом сбора на прокси и моментом выгрузки на сервер.
* **Proxy Group (с 7.0)** — логическая группа прокси, обслуживающая один набор хостов. Внутри группы Zabbix автоматически балансирует хосты между прокси и перестраивает распределение при выходе прокси из строя (нативный HA на уровне прокси).
* **Data sender / Data sender worker** — процессы прокси, выгружающие буфер на сервер.

## Основные концепции

### Зачем нужен прокси

Zabbix Server — централизованный компонент. Прокси решает задачи, которые централизованный сервер решает плохо:

* **Изоляция сети и DMZ.** В защищённых сегментах нежелательно открывать входящий порт сервера. Активный прокси работает только исходящими соединениями.
* **Снижение нагрузки на сервер.** Прокси берёт на себя сбор, предобработку и расчёт триггеров; на сервер передаются уже агрегированные/обработанные данные. На сервере для таких хостов не создаются отдельные поллеры.
* **Экономия канала WAN.** Данные от филиала передаются в сжатом виде одним потоком, а не отдельными проверками.
* **Автономность при обрыве связи.** При потере связи с сервером прокси продолжает сбор и накапливает данные в буфере; после восстановления связи выгружает накопленное (в пределах `ProxyOfflineBuffer`).
* **Обход ограничений на количество хостов.** Один сервер обслуживает ограниченное число хостов; горизонтально масштабируются добавлением прокси.

### Режимы работы

| Свойство | Active | Passive |
|---|---|---|
| Кто инициирует соединение | Прокси → сервер | Сервер → прокси |
| Адрес прокси на сервере | Не требуется | Обязателен (`Address`, порт `10051`) |
| Требуемые входящие порты на прокси | Нет | `10051` от сервера |
| Пригодность для DMZ | Да (рекомендуется) | Требует публикации прокси |
| Параметр конфигурации | `ProxyMode=0` (по умолчанию) | `ProxyMode=1` |
| Интервал получения конфигурации | `ProxyConfigFrequency` (по умолчанию 10 с) | Обновляется при подключении сервера |

Режим прокси в веб-интерфейсе (Administration → Proxies) и параметр `ProxyMode` в `zabbix_proxy.conf` должны совпадать, иначе прокси не заработает.

### Механизмы буферизации (`ProxyBufferMode`)

Параметр `ProxyBufferMode` определяет, где хранятся собранные, но ещё не переданные серверу данные:

* **`disk`** (документированное значение по умолчанию) — данные пишутся в локальную базу прокси и выгружаются оттуда. Устойчиво к перезапуску и обрывам, но создаёт часть нагрузки на локальный диск. Для существующих установок это значение сохраняется.
* **`memory`** — данные хранятся в буфере в оперативной памяти (ring buffer). При переполнении буфера **старые данные отбрасываются**. При остановке прокси буфер не сохраняется. Неустойчив к перезапуску и потере данных, но максимально быстрый.
* **`hybrid`** — гибридный режим: по умолчанию работает как `memory`, но как только буфер переполняется или возраст самой старой записи превышает `ProxyMemoryBufferAge`, он сбрасывается на диск и работает как `disk` до полной выгрузки, после чего снова переключается в память. При остановке память сбрасывается на диск.

> Начиная с Zabbix 7.0 режим `hybrid` применяется ко всем новым установкам как рекомендуемый. Для установок, обновлённых с более старых версий, сохраняется `disk`.

Ключевые параметры памяти:

| Параметр | Назначение | По умолчанию | Диапазон |
|---|---|---|---|
| `ProxyBufferMode` | Механизм хранения данных | `disk` | `disk`; `memory`; `hybrid` |
| `ProxyMemoryBufferSize` | Размер shared-memory буфера | `0` (выключен) | `0`; `128K`–`2G` |
| `ProxyMemoryBufferAge` | Максимальный возраст данных в буфере, сек | `0` | `0`; `600`–`864000` |
| `ProxyLocalBuffer` | Держать данные локально ещё N часов после синхронизации | `0` | — |
| `ProxyOfflineBuffer` | Хранить данные N часов при отсутствии связи с сервером | `1` | `1`–`720` |
| `ProxyConfigFrequency` | Частота получения конфигурации активным прокси, сек | `10` | — |

Важные ограничения:

* `ProxyMemoryBufferSize` **нельзя использовать вместе** с `ProxyLocalBuffer` — параметры взаимоисключающие.
* `ProxyMemoryBufferAge` должен быть **меньше или равен** `ProxyOfflineBuffer`.
* Если `ProxyBufferMode` = `hybrid`/`memory`, а `ProxyMemoryBufferSize` = `0`, режим памяти фактически не включается.

### Выгрузка данных на сервер

Прокси собирает и обрабатывает данные независимо, а затем выгружает их на сервер пакетами через процессы data sender. Объём выгружаемого определяется внутренними настройками и не требует ручной подстройки при типовых нагрузках. При отсутствии связи данные накапливаются в буфере; по достижении лимита `ProxyOfflineBuffer` (для `disk`) или переполнения кэша (для `memory`) самые старые данные теряются.

### Proxy Groups и HA (с 7.0)

Proxy Group объединяет несколько прокси для обслуживания одного набора хостов. Внутри группы:

* Хосты автоматически распределяются между прокси формально по их доступности/нагрузке (алгоритм распределения прозрачен для администратора).
* При падении прокси его хосты перераспределяются на живые прокси группы — это заменяет ручную перенастройку, характерную для схем на отдельных прокси.
* Группа может содержать любое число прокси; сервер сам решает, какой прокси опрашивает конкретный хост.

Это встроенный механизм отказоустойчивости: отдельный прокси остаётся единой точкой отказа, Proxy Group — нет. Он аналогичен Server HA (с 6.0), но на уровне сбора данных.

### Шифрование между прокси и сервером

Соединение прокси↔сервер можно защитить TLS. Поддерживаются режимы взаимной аутентификации (pre-shared key, сертификаты). На прокси задаются `TLSConnect`, `TLSAccept`, `TLSPSKIdentity`, `TLSPSKFile`; аналогичные параметры — на сервере. При включении шифрования обязательно настроить обе стороны, иначе прокси будет отвергнут.

## Практические сценарии

### Предварительные требования

* Установленная и работающая база данных для прокси (только если используется локальное хранилище: SQLite по умолчанию для небольших прокси, либо PostgreSQL/MySQL для крупных).
* Совпадающие версии Zabbix Server и Proxy: прокси должен быть **не старше** сервера (сервер 7.0 требует прокси 7.0).
* Для активного прокси: исходящий доступ с прокси на сервер (`10051`). Для пассивного: входящий `10051` на прокси от сервера.
* DNS-имена или IP-адреса, разрешаемые в обе стороны.
* На сервере — права администратора для создания прокси в веб-интерфейсе.

### Сценарий 1. Активный прокси (рекомендуемый)

**Шаг 1. Создать прокси в веб-интерфейсе.** Administration → Proxies → Create proxy:

* `Proxy mode`: Active.
* `Proxy name`: имя, **точно совпадающее** с `Hostname` в `zabbix_proxy.conf` (чувствительно к регистру).
* Поле `Address` оставить пустым — активный прокси сам заявит о себе.

**Шаг 2. Настроить прокси.** Минимальный `zabbix_proxy.conf`:

```ini
Server=10.0.0.10
Hostname=proxy-branch-01
ProxyMode=0
ProxyConfigFrequency=10
ProxyBufferMode=hybrid
ProxyMemoryBufferSize=16M
ProxyOfflineBuffer=24
DBName=zabbix_proxy
LogFile=/var/log/zabbix/zabbix_proxy.log
```

`Server` для активного прокси — адрес Zabbix Server; `Hostname` — уникальное имя прокси.

**Шаг 3. Запустить и проверить.**

```bash
sudo systemctl start zabbix-proxy
sudo systemctl enable zabbix-proxy
# → служба активна
sudo grep -iE "cannot|failed|error" /var/log/zabbix/zabbix_proxy.log
# → при успешном старте строк об ошибках нет
```

В веб-интерфейсе Administration → Proxies прокси должен перейти в состояние **Active** (последний обмен данными — «сейчас»/недавнее время). Состояние **Unknown** означает, что прокси не выходит на связь.

### Сценарий 2. Пассивный прокси

В веб-интерфейсе: `Proxy mode` = Passive, `Address` = IP или DNS прокси (порт задаётся полем `Port`, по умолчанию `10051`). В `zabbix_proxy.conf` на прокси:

```ini
Server=10.0.0.10
Hostname=proxy-branch-02
ProxyMode=1
```

Здесь `Server` — адрес сервера, **с которого разрешены подключения** (если указать неверный адрес, сервер не сможет забрать данные). Убедитесь, что firewall прокси пропускает входящий `10051` от сервера.

### Сценарий 3. Прокси в DMZ / филиале

1. Используйте **активный** режим — это избавляет от необходимости открывать входящие порты в защищённый сегмент.
2. На стороне прокси разрешите исходящий `10051` к серверу.
3. Включите TLS между прокси и сервером (создание PSK и сертификатов — в разделе шифрования сервера и в документации Zabbix).
4. Настройте `ProxyOfflineBuffer` с запасом (например, `24` часа), чтобы переживать длительные обрывы канала без потери данных.

### Сценарий 4. Отказоустойчивость через Proxy Group

1. Создайте Proxy Group: Administration → Proxy groups → Create proxy group.
2. Добавьте в группу не менее двух прокси (лучше — в разных зонах доступности).
3. Назначьте хосты этой группе вместо отдельного прокси — тогда распределение и перераспределение выполняет сервер.
4. Проверка отказоустойчивости: остановите один прокси группы и убедитесь, что его хосты в течение некоторого времени стали обслуживаться другим активным прокси группы.

### Сценарий 5. Настройка буферизации

Для устойчивости к обрывам и перезапуску (продакшен):

```ini
ProxyBufferMode=hybrid
ProxyMemoryBufferSize=16M
ProxyMemoryBufferAge=600
ProxyOfflineBuffer=24
```

Для максимальной производительности в пределах потери данных при перезапуске (лаборатория, некритичные метрики):

```ini
ProxyBufferMode=memory
ProxyMemoryBufferSize=32M
```

Выбор обосновывается требованиями: `hybrid`/`disk` — когда недопустима потеря данных; `memory` — когда важна скорость, а потеря короткого интервала при сбое приемлема.

### Валидация

```bash
# Проверить активность процесса на прокси
pgrep -a zabbix_proxy
# → список процессов прокси

# Проверить, что прокси отдаёт данные на сервер (журнал сервера)
sudo grep -iE "proxy.*(active|inactive|last seen)" /var/log/zabbix/zabbix_server.log
# → записи об активности прокси

# Проверить состояние прокси через API (пример)
curl -s -X POST -H 'Content-Type: application/json-rpc' \
  -d '{"jsonrpc":"2.0","method":"proxy.get","params":{"output":"extend"},"id":1}' \
  http://zabbix.example.com/zabbix/api_jsonrpc.php
```

## Операции и команды

```bash
# Проверить конфигурацию прокси перед запуском
zabbix_proxy -T
# → "zabbix_proxy: configuration file is valid" или путь к ошибочному параметру

# Тестовая проверка элемента через прокси
zabbix_get -s 127.0.0.1 -p 10051 -k "agent.ping"
# → 1

# Перезапуск прокси
sudo systemctl restart zabbix-proxy
```

| Параметр | Назначение | По умолчанию |
|---|---|---|
| `ProxyMode` | Режим работы (0 — active, 1 — passive) | `0` |
| `Server` | Адрес/список адресов Zabbix Server | — |
| `Hostname` | Имя прокси, совпадает с настройкой на сервере | локальный hostname |
| `ProxyConfigFrequency` | Интервал получения конфигурации активным прокси, сек | `10` |
| `ProxyBufferMode` | Механизм буферизации (`disk`/`memory`/`hybrid`) | `disk` |
| `ProxyMemoryBufferSize` | Размер буфера в памяти | `0` |
| `ProxyMemoryBufferAge` | Максимальный возраст данных в памяти, сек | `0` |
| `ProxyLocalBuffer` | Локальное хранение после синхронизации, ч | `0` |
| `ProxyOfflineBuffer` | Хранение при отсутствии связи, ч | `1` |
| `DataSenderFrequency` | Интервал выгрузки данных на сервер, сек | `1` |

## Устранение неисправностей

| Симптом | Возможная причина | Диагностика и решение |
|---|---|---|
| Прокси в состоянии `Unknown`/`Inactive` | Несовпадение `Hostname` на прокси и в веб-интерфейсе | Сверить строки посимвольно (регистр важен); исправить и перезапустить |
| Активный прокси не появляется | Нет исходящего доступа на сервер `10051` | `nc -vz <server> 10051`; проверить firewall |
| Пассивный прокси не опрашивается | Неверный `Server` или `Address`, закрыт входящий порт | Проверить `Server` на прокси и `Address` на сервере, входящий `10051` |
| Разрывы на графиках | `ProxyOfflineBuffer` или `ProxyMemoryBufferSize` малы; при `memory` старые данные отбрасываются | Увеличить буфер; перейти на `disk`/`hybrid` |
| Данные теряются при перезапуске | `ProxyBufferMode=memory` — буфер не сохраняется | Перейти на `hybrid`/`disk` |
| «Прокси не может получить конфигурацию» | Нет активного прокси-объекта на сервере с таким именем | Создать/исправить прокси в Administration → Proxies |
| Ошибка «не удалось принять TLS-соединение» | Шифрование настроено только на одной стороне | Согласовать `TLSConnect`/`TLSAccept`/PSK на сервере и прокси |
| Прокси старше сервера | Несовместимые версии | Обновить прокси до версии сервера |

## Лучшие практики

* **Активный режим по умолчанию** для удалённых площадок и DMZ — меньше правил firewall и обратный трафик инициируется прокси.
* **`hostname` во внутренней сети:** имя прокси должно быть стабильным (DNS или неизменяемый hostname), иначе после переименования потребуется пересоздать объект на сервере.
* **`hybrid` для продакшена:** компромисс между скоростью памяти и сохранением данных при обрыве.
* **Proxy Groups вместо «зоопарка» отдельных прокси** там, где нужна отказоустойчивость сбора: сервер сам перераспределит хосты.
* **Запас по `ProxyOfflineBuffer`** под максимально ожидаемый обрыв канала (часто 24 часа).
* **Мониторить сам прокси:** к прокси подключите шаблон `Template App Zabbix Proxy` и настройте триггеры на «прокси не на связи» (см. **[Эскалацию и алертинг](./zabbix_alerting_and_escalation.md)**).
* **Шифровать трафик прокси↔сервер**, если он идёт через недоверенную сеть.
* **Не поднимать прокси того же хоста, что и сервер,** без необходимости — это не даёт выигрыша в архитектуре и лишь усложняет схему.
