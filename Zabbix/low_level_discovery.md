# Zabbix — низкоуровневое обнаружение (Low-Level Discovery)

## Определения

* **Низкоуровневое обнаружение (LLD)** — технология Zabbix для автоматического обнаружения динамических сущностей на хосте и создания элементов данных, триггеров, графиков и групп хостов для них. Применяется для мониторинга файловых систем, сетевых интерфейсов, баз данных и облачных ресурсов.
* **Правило обнаружения (LLD Rule)** — конфигурационный объект (на уровне хоста или шаблона), выполняющий периодическую проверку и возвращающий JSON-данные со списком ресурсов. История предыдущих результатов такого правила не хранится (запоминается только последний результат).
* **Прототип (Prototype)** — шаблон объекта мониторинга (элемента данных, триггера, графика, хоста). Использует макросы обнаружения (например, `{#FSNAME}`) для генерации реальных сущностей.
* **Макрос обнаружения (LLD Macro)** — специальная переменная формата `{#MACRO}`, извлекаемая из JSON-ответа и используемая в прототипах.
* **Переопределение (Override)** — механизм LLD, позволяющий изменять свойства генерируемых объектов (интервал опроса, статус, теги, важность триггера) в зависимости от значений макросов.
* **Потерянный ресурс (Lost Resource)** — ранее обнаруженная сущность, которая перестала появляться в JSON-ответе правила (или перестала проходить фильтр). Судьба ресурса определяется параметрами «Удалить потерянные ресурсы» / «Отключить потерянные ресурсы» (см. «Жизненный цикл объекта»).

## Основные концепции

### Преимущества LLD

Использование низкоуровневого обнаружения критически важно для масштабных инфраструктур (сотни и тысячи серверов):
*   **Автоматизация:** избавляет от необходимости вручную прописывать каждый диск, сетевой интерфейс или датчик температуры.
*   **Динамичность:** если на сервере появится новый диск, Zabbix обнаружит его при следующем сканировании и автоматически начнет мониторить.
*   **Снижение ошибок:** исключает человеческий фактор при настройке однотипных объектов мониторинга.
*   **Масштабируемость:** позволяет поддерживать огромную инфраструктуру небольшими силами администраторов.

### Принцип работы

1. **Сбор данных:** LLD-правило выполняет проверку (через Zabbix Agent, Agent 2, SNMP, HTTP-агент, JMX, ODBC, IPMI, скрипт, Prometheus и др.) и получает сырые данные (обычно JSON).
2. **Предобработка (Preprocessing):** сырые данные трансформируются в требуемый JSON-массив (через JSONPath, JavaScript, CSV to JSON, Prometheus to JSON и т.д.). На этом же этапе применяется фильтрация дубликатов (Throttling).
3. **Извлечение макросов:** Zabbix парсит JSON и присваивает значения макросам `{#MACRO}` для каждого найденного объекта.
4. **Фильтрация и переопределения:** применяются регулярные выражения для отсева ненужных сущностей (Filters) и правила модификации атрибутов (Overrides).
5. **Генерация:** на основе прототипов создаются реальные сущности (элементы данных, триггеры, графики, при необходимости — даже хосты).

Обработку результатов LLD в современных версиях выполняют специализированные процессы `LLD Manager` и `LLD Workers`, что обеспечивает параллельную обработку большого числа правил (подробнее — в **[документе о процессах Zabbix](./additional_info.md)**).

### Формат данных и JSONPath

Начиная с версии **Zabbix 4.2** строгий формат `{"data": [...]}` **больше не обязателен** — правило LLD принимает обычный JSON-массив в корне документа:

```json
[
  { "disk": "/", "type": "ext4" },
  { "disk": "/home", "type": "xfs" }
]
```

Для обратной совместимости сервер по-прежнему распознает старую оболочку `{"data": [...]}` и автоматически извлекает из нее содержимое по пути `$.data`, однако такой формат считается устаревшим.

Существует два способа описать макросы в LLD-правиле:

1. **Макрос в имени ключа JSON.** Если поле JSON-объекта оформлено как `"{#IFNAME}": "value"`, Zabbix автоматически распознает имя макроса и его значение:
   ```json
   [
     { "{#IFNAME}": "lo" },
     { "{#IFNAME}": "eth0" }
   ]
   ```
   Такой синтаксис используется встроенными ключами агентов (например, `net.if.discovery`).
2. **Пользовательские LLD-макросы с JSONPath.** Если в JSON нет готовых имен ключей, на вкладке **LLD macros** правила задается маппинг — каждому макросу сопоставляется JSONPath:
   * `{#FSNAME}` = `$.disk`
   * `{#FSTYPE}` = `$.type`

JSONPath поддерживает точечную (`$.foo`) и скобочную (`$['key with special chars']`) нотацию; скобочная обязательна при наличии специальных символов или Unicode в имени поля.

Основные выразительные возможности диалекта JSONPath в Zabbix:
* Рекурсивный обход — `$..key`.
* Индекс массива — `$[0]`; выбор элементов — `$.data[*].field`.
* Условия (фильтр-выражение) — `$[?(@.size > 10)]`; поддерживаются операторы сравнения, `=~` (совпадение с regex), логические `&&`, `||`, `!`.
* Суффикс `~` (например, `$.*~`) — применить путь не к значениям, а к **именам ключей** объекта; полезно для извлечения имен из сложных вложенных структур.
* Функции в конце пути: `sum()`, `min()`, `max()`, `avg()`, `length()`, `first()`.

### Фильтры и переопределения

* **Фильтр (Filter):** решает, *нужно ли* создавать объект (например, `{#FSTYPE} matches ext4|xfs`). Если фильтр не пройден — объект отбрасывается полностью. Фильтров может быть несколько (поддерживается с версии 2.4); для каждого макроса задается отдельное условие (`matches` / `not matches`). Если макрос, указанный в фильтре, отсутствует в JSON-данных текущего объекта, такой объект будет проигнорирован.
* **Переопределение (Override):** решает, *как именно* будет сконфигурирован созданный объект. Выполняется после фильтров правила. Позволяет, например, отключить элементы данных для конкретного диска (`{#FSNAME} matches /var/log/tmp`), не удаляя их, или повысить серьезность триггера для корневого раздела (`/`). Переопределения добавлены в Zabbix **4.2**.
  * Для каждого переопределения задаются **Filters** (к каким сущностям применяется) и логика цепочки: **Continue overrides** — продолжить обработку следующих переопределений; **Stop processing** — выполнить операции текущего (и предыдущих) и игнорировать последующие для совпавших строк.
  * Переопределения применяются в порядке их списка (можно перетаскивать); выполняются после фильтров самого правила.
  * Доступные действия: обнаруживать или не обнаруживать элемент/триггер/график, создавать во включенном/отключенном состоянии, изменить интервал обновления, применить теги, изменить важность триггера и т.д.

### Троттлинг (Throttling)

Для снижения нагрузки на базу данных Zabbix в шагах предобработки LLD-правила **обязательно** следует применять шаг **Discard unchanged with heartbeat** (например, `1h` или `1d`). Это предотвращает запись одних и тех же результатов обнаружения в базу при каждой проверке, если список объектов не изменился. Допускается только одна операция троттлинга на правило.

Примечание: изменение самих прототипов НЕ сбрасывает троттлинг — сброс происходит только при изменении preprocessing-шагов правила.

### Жизненный цикл объекта (Lost Resources)

Если объект исчезает из JSON-ответа (или перестает проходить фильтр), все созданные для него сущности (элементы данных, триггеры, графики, хосты) переходят в состояние «не обнаружен» (Not discovered). Их судьба управляется двумя параметрами правила (в Zabbix 6.x и новее; в более старых версиях существовал один параметр «Keep lost resources period»):

* **Отключить потерянные ресурсы (`Disable lost resources`):** никогда / сразу / через заданное время — автоматически **отключить** созданные сущности (прекратить сбор новых данных), не удаляя историю. Автоматически отключенные объекты будут **снова включены**, если сущность будет обнаружена повторно. Вручную отключенные администратором объекты повторно включаться НЕ будут.
* **Удалить потерянные ресурсы (`Delete lost resources`):** никогда / сразу / через заданное значение (по умолчанию 30 дней) — **удалить** сущности после указанного срока нахождения в состоянии «не обнаружен». Значение должно быть больше значения отключения.

Рекомендации:
* Использовать «Immediately» для удаления **не рекомендуется** — при ошибочной правке фильтра можно массово удалить элементы вместе с их историей.
* Пока сущность не удалена, в списке объектов на хосте отображается индикатор «осталось дней до удаления» (прогресс-точка у имени элемента).
* Если удаление было отложено (правило или хост были отключены), объект будет удален при следующем проходе обнаружения.
* Вложенные объекты (например, триггер на основе LLD-элемента данных) при наличии потомков, помеченных на удаление, не обновляются до полного удаления этих потомков.

### Вложенное обнаружение и прототипы хостов

Одного уровня иерархии LLD часто бывает недостаточно (например, обнаружить БД, а внутри — таблицы). Начиная с **Zabbix 7.4** поддерживается **вложенное низкоуровневое обнаружение (Nested LLD)**: внутри LLD-правила создается **прототип правила обнаружения (Discovery prototype)**, и результат проверки используется как источник данных для вложенного LLD-правила. Это снимает ограничение на двух- и более уровневые каскады.

Кроме того, через **прототипы хостов (Host prototypes)** LLD умеет автоматически добавлять в мониторинг целые хосты с интерфейсами и привязывать шаблоны (например, обнаружение ВМ на гипервизоре). Прототип хоста может быть использован и как элемент правила верхнего уровня во вложенном обнаружении. Для хостов также применимы правила управления потерянными ресурсами.

### Ограничения по размеру данных

* Нет верхнего предела размера JSON для LLD-правила, если данные приходят **непосредственно на сервер** (обрабатываются в памяти, в БД не сохраняются).
* Если проверка выполняется через **UserParameter** или внешний скрипт — действует ограничение на размер возвращаемого значения (по умолчанию 512 КБ для user parameter).
* При сборе через промежуточный **Zabbix proxy** JSON временно хранится в БД прокси, поэтому действует лимит размера значения, хранимого прокси (например, ~2 КБ для прокси с IBM DB2).

## Практические сценарии

### Использование встроенных правил

Zabbix предоставляет готовые правила для типовых задач (большинство реализуются агентскими ключами `*discovery`):

* **Файловые системы (`vfs.fs.discovery`):** обнаружение разделов и мониторинг их объема. Макросы: `{#FSNAME}`, `{#FS.NAME}`, `{#FS.TYPE}` и др.
* **Сетевые интерфейсы (`net.if.discovery`):** автоматические графики трафика для всех портов; макрос `{#IFNAME}`.
* **CPU и ядра (`system.cpu.discovery`):** автоматизация мониторинга CPU-ресурсов; макросы `{#CPU.NAME}`, `{#CPU.NUMBER}` и др.
* **СУБД и сервисы:** LLD для PostgreSQL, MySQL, Docker-контейнеров, systemd-сервисов (см. **[Мониторинг PostgreSQL](./zabbix_postgresql_monitoring.md)** и связанные шаблоны).
* **SNMP OIDs:** получение списка интерфейсов (`1.3.6.1.2.1.2.2`), дисков (`1.3.6.1.2.1.25.2.3`) и т.д.
* **JMX (через Java gateway):** обнаружение Java-объектов по MBeans.
* **IPMI sensors:** автоматический сбор датчиков по IPMI.
* **Windows:** службы (`service.discovery`), счетчики производительности (`perf_counter.discovery`), WMI-запросы.
* **WMI и ODBC:** обнаружение сущностей через WMI-запросы и SQL-запросы соответствующих ODBC-мониторов.
* **Prometheus:** данные из Prometheus-метрик (тип данных + preprocessing «Prometheus to JSON»).
* **Host interfaces:** интерфейсы хостов Zabbix (например, для построения топологии) — так называемое «discovery of host interfaces».
* **Block devices:** обнаружение блочных дисков (например, для мониторинга LVM/RAID) — `vfs.dev.discovery`/шаблоны.

### Синтаксис ключей discovery в агентах

Агент Zabbix (классика) и Agent 2 отличаются синтаксисом части discovery-ключей:
* Zabbix Agent (классика): `vfs.fs.discovery`, `net.if.discovery`, `system.cpu.discovery`.
* Zabbix Agent 2: предпочтительно использовать «модернизированные» ключи и плагины, например `vfs.fs.get`, `net.if` (в сочетании с preprocessing/JSONPath), `systemd.unit.discovery`, `docker.container.discovery`.

### Реализация кастомного обнаружения через скрипт

Алгоритм создания собственного LLD (например, для мониторинга пула запущенных Java-процессов):

#### 1. Подготовка скрипта
Скрипт на стороне агента должен возвращать список процессов в формате JSON:
```bash
#!/bin/bash
echo '[{"{#APP}": "tomcat-api"}, {"{#APP}": "kafka-worker"}]'
```

#### 2. Настройка UserParameter
В конфигурации Zabbix Agent (в `/etc/zabbix/zabbix_agent2.d/`) прописывается команда вызова:
```
UserParameter=custom.app.discovery,/opt/scripts/discover_apps.sh
```

Ограничение: предельный размер возврата через UserParameter — 512 КБ.

#### 3. Настройка LLD в веб-интерфейсе
1. Создайте LLD-правило с типом `Zabbix agent` и ключом `custom.app.discovery`. Установите интервал опроса (например, `15m` — `1h`).
2. Во вкладке **Preprocessing** добавьте шаг `Discard unchanged with heartbeat` (`1h` или `1d`).
3. Сразу после настройки правила используйте кнопку **Check now** («Выполнить сейчас») для принудительного запуска обнаружения; кнопка **Test** позволяет проверить правило без внесения изменений.
4. Создайте **Item prototypes** для метрик. Для прототипов, получающих значения push-методом от скриптов, используйте тип `Zabbix trapper`.

#### 4. Отправка данных для прототипов (Trapper)
Данные для созданных прототипов отправляются утилитой `zabbix_sender`:
```bash
zabbix_sender -z <zabbix_server> -s <hostname> -k "app.memory[tomcat-api]" -o 1024
```
Подробности: **[Отправка данных через zabbix_sender](./installation.md#отправка-данных-через-zabbix_sender)**.

#### 5. Ожидаемый результат
Вот что должен увидеть администратор после первого прохода обнаружения:
```bash
zabbix_get -s 127.0.0.1 -k custom.app.discovery
# → "[{"{#APP}":"tomcat-api"},{"{#APP}":"kafka-worker"}]"
```
В **Configuration → Hosts → Discovery rules → Item prototypes** должны появиться созданные элементы данных с подставленным вместо `{#APP}` именем приложения.

## Дополнительная информация

### Развитие функциональности

| Версия | Изменения |
| :--- | :--- |
| **Zabbix 4.2** | Отказ от обязательной оболочки `{"data": [...]}` — допускается обычный JSON-массив; появились пользовательские LLD-макросы с JSONPath; Overrides впервые введены в этой версии. |
| Zabbix 5.x | JSONPath-агрегаторы и фильтр-выражения, суффикс `~` для имён ключей. |
| Zabbix 6.0/6.4 | Доработка preprocessing (JS), расширенные ключи Agent 2, исправления троттлинга. |
| **Zabbix 7.0 LTS** | Асинхронная обработка LLD (новые процессы `LLD Manager`/`LLD Worker`), расширение логики Overrides; раздельные «Disable/Delete lost resources» для управления потерянными ресурсами. |
| **Zabbix 7.4+** | Полноценная поддержка вложенного (Nested) обнаружения на несколько уровней; прототипы LLD-правил (Discovery prototypes) для каскадного обнаружения. |
| Zabbix 8.0 (в разработке) | Новый тип данных JSON (до 128 МиБ), поддержка JSONPath в триггерах — упрощает работу с большими и вложенными JSON, в том числе во вложенном LLD. |

### LLD в веб-интерфейсе

* **Discovery rules** (правила LLD) управляются из **Configuration → Templates (или Hosts) → Discovery**.
* Для дашбордов доступен виджет **Discovery status** («Состояние обнаружения»), отображающий последние данные и ошибки LLD.
* Используйте внутренние метрики `zabbix[process,lld worker,avg,busy]` и `zabbix[process,lld manager,avg,busy]` для отслеживания нагрузки на процессы обработки discovery (см. **[Наблюдение за процессами через внутренние метрики Zabbix](./additional_info.md#наблюдение-за-процессами-через-внутренние-метрики-zabbix)**).
