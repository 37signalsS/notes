# Zabbix — низкоуровневое обнаружение (Low-Level Discovery)

## Определения

* **Низкоуровневое обнаружение (LLD)** — технология Zabbix для автоматического обнаружения динамических сущностей на хосте и создания элементов данных, триггеров, графиков и групп хостов для них. Применяется для мониторинга файловых систем, сетевых интерфейсов, баз данных и облачных ресурсов.
* **Правило обнаружения (LLD Rule)** — конфигурационный объект (на уровне хоста или шаблона), выполняющий периодическую проверку и возвращающий JSON-данные со списком ресурсов.
* **Прототип (Prototype)** — шаблон объекта мониторинга (элемента данных, триггера, графика, хоста). Использует макросы обнаружения (например, `{#FSNAME}`) для генерации реальных сущностей.
* **Макрос обнаружения (LLD Macro)** — специальная переменная формата `{#MACRO}`, извлекаемая из JSON-ответа и используемая в прототипах.
* **Переопределение (Override)** — механизм LLD, позволяющий изменять свойства генерируемых объектов (интервал опроса, статус, теги, важность триггера) в зависимости от значений макросов.

## Основные концепции

### Принцип работы

1. **Сбор данных:** LLD-правило выполняет проверку (через Zabbix Agent, SNMP, HTTP-агент или скрипт) и получает сырые данные (обычно JSON).
2. **Предобработка (Preprocessing):** Сырые данные трансформируются в требуемый JSON-массив (через JSONPath, JavaScript и т.д.). На этом же этапе применяется фильтрация дубликатов (Throttling).
3. **Извлечение макросов:** Zabbix парсит JSON и присваивает значения макросам `{#MACRO}` для каждого найденного объекта.
4. **Фильтрация и Переопределения:** Применяются регулярные выражения для отсева ненужных сущностей (Filters) и правила модификации атрибутов (Overrides).
5. **Генерация:** На основе прототипов создаются реальные сущности.

Если объект исчезает из JSON-ответа, Zabbix помечает созданные на его основе сущности как «потерянные» (Lost) и удаляет их (или отключает) по истечении заданного периода удержания (`Keep lost resources period`).

### Формат данных и JSONPath

В современных версиях Zabbix (включая 7.0) строгий формат вида `{"data": [...]}` больше **не обязателен**. Правило LLD может принимать любой валидный JSON-массив.

Пример принимаемого массива:
```json
[
  { "disk": "/", "type": "ext4" },
  { "disk": "/home", "type": "xfs" }
]
```

Для работы с таким JSON на вкладке **LLD macros** настраивается маппинг с использованием **JSONPath**:
* `{#FSNAME}` = `$.disk`
* `{#FSTYPE}` = `$.type`

Также поддерживается суффикс `~` в JSONPath (например, `$.*~`) для извлечения имен ключей из сложных JSON-объектов.

### Переопределения (Overrides) vs Фильтры

* **Фильтр (Filter):** Решает, *нужно ли* создавать объект (например, `{#FSTYPE} matches ext4|xfs`). Если фильтр не пройден — объект отбрасывается полностью.
* **Переопределение (Override):** Решает, *как именно* будет сконфигурирован созданный объект. Выполняется после фильтров. Позволяет, например, отключить элементы данных для конкретного диска (`{#FSNAME} matches /var/log/tmp`), не удаляя их, или повысить серьезность триггера для корневого раздела (`/`). В Zabbix 7.0 поддерживается сложная логика остановки (`Stop processing`) или продолжения (`Continue overrides`) цепочки переопределений.

### Троттлинг (Throttling)

Для снижения нагрузки на базу данных Zabbix в шагах предобработки LLD-правила **обязательно** следует применять шаг **Discard unchanged with heartbeat** (например, `1h` или `1d`). Это предотвращает запись одних и тех же результатов обнаружения в базу при каждой проверке, если список объектов не изменился.

## Практические сценарии

### Использование встроенных правил

Zabbix предоставляет готовые решения для типовых задач (доступны из коробки через Zabbix Agent / Agent 2):
* **Файловые системы (`vfs.fs.discovery`):** Обнаружение разделов и мониторинг их объема.
* **Интерфейсы (`net.if.discovery`):** Автоматическое создание графиков трафика для всех портов.
* **СУБД и сервисы:** LLD для баз данных, Docker-контейнеров, systemd-сервисов. (см. **[Мониторинг PostgreSQL](./zabbix_postgresql_monitoring.md)**).

### Реализация кастомного обнаружения через скрипт

Алгоритм создания собственного LLD (например, для мониторинга пула запущенных Java-процессов):

#### 1. Подготовка скрипта
Скрипт на стороне сервера должен возвращать список процессов в формате JSON:
```bash
#!/bin/bash
echo '[{"{#APP}": "tomcat-api"}, {"{#APP}": "kafka-worker"}]'
```

#### 2. Настройка UserParameter
В конфигурации Zabbix Agent (в `/etc/zabbix/zabbix_agent2.d/`) прописывается команда вызова:
`UserParameter=custom.app.discovery,/opt/scripts/discover_apps.sh`

#### 3. Настройка LLD в веб-интерфейсе
1. Создайте LLD-правило с типом `Zabbix agent` и ключом `custom.app.discovery`. Установите интервал опроса (например, `1h`).
2. Во вкладке **Preprocessing** добавьте шаг `Discard unchanged with heartbeat` (`12h`).
3. Создайте **Item prototypes** для метрик. Для прототипов, получающих значения push-методом от скриптов, используйте тип `Zabbix trapper`.

#### 4. Отправка данных для прототипов (Trapper)
Данные для созданных прототипов отправляются утилитой `zabbix_sender`:
```bash
zabbix_sender -z <zabbix_server> -s <hostname> -k "app.memory[tomcat-api]" -o 1024
```
Подробности: **[Отправка данных через zabbix_sender](./installation.md#отправка-данных-через-zabbix_sender)**.
