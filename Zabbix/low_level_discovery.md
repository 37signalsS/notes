# Zabbix — низкоуровневое обнаружение (Low-Level Discovery)

**Актуально для:** Zabbix 7.0 LTS / 7.4 (текущая стандартная ветка); особенности готовящегося Zabbix 8.0 (на момент сверки — кандидат в релиз 8.0.0rc1) отмечены по тексту и даны по предрелизным данным.

## Определения

* **Низкоуровневое обнаружение (LLD)** — технология Zabbix для автоматического обнаружения динамических сущностей на хосте и создания элементов данных, триггеров, графиков и групп хостов для них. Применяется для мониторинга файловых систем, сетевых интерфейсов, баз данных, контейнеров и других изменяемых ресурсов.
* **Сетевое обнаружение (Network Discovery)** — отдельный механизм Zabbix для сканирования диапазонов IP-адресов с целью поиска узлов и сервисов сети; в отличие от LLD обнаруживает сами хосты, а не сущности внутри уже известного хоста.
* **Правило обнаружения (LLD Rule)** — конфигурационный объект (на уровне хоста или шаблона), выполняющий периодическую проверку и возвращающий JSON-данные со списком ресурсов. История предыдущих результатов такого правила не хранится (запоминается только последний результат).
* **Прототип (Prototype)** — шаблон объекта мониторинга (элемента данных, триггера, графика, хоста, LLD-правила). Использует макросы обнаружения (например, `{#FSNAME}`) для генерации реальных сущностей.
* **Прототип правила обнаружения (Discovery prototype)** — вложенный LLD-прототип, позволяющий создавать каскадные правила обнаружения на несколько уровней (Zabbix 7.4+).
* **Прототип хоста (Host prototype)** — специальный прототип, создающий новые хосты в Zabbix с интерфейсами и привязкой шаблонов (например, обнаружение ВМ на гипервизоре).
* **Макрос обнаружения (LLD Macro)** — специальная переменная формата `{#MACRO}`, извлекаемая из JSON-ответа и используемая в прототипах.
* **Переопределение (Override)** — механизм LLD, позволяющий изменять свойства генерируемых объектов (интервал опроса, статус, теги, важность триггера) в зависимости от значений макросов.
* **Потерянный ресурс (Lost Resource)** — ранее обнаруженная сущность, которая перестала появляться в JSON-ответе правила (или перестала проходить фильтр). Судьба ресурса определяется параметрами «Удалить потерянные ресурсы» / «Отключить потерянные ресурсы».
* **Троттлинг (Throttling)** — механизм предобработки LLD, предотвращающий избыточную запись неизменных результатов обнаружения в базу данных.

## Основные концепции

### Архитектура обработки LLD

В современных версиях Zabbix обработка результатов LLD выполняется асинхронно специализированными процессами:

* **LLD Manager** — координатор, принимающий результаты правил обнаружения и распределяющий их между воркерами.
* **LLD Workers** — параллельные процессы, выполняющие фактическую генерацию объектов из прототипов.

Количество воркеров управляется параметром `StartLLDProcessors` (по умолчанию 2, диапазон 1–100). Для крупных инсталляций с тысячами правил обнаружения увеличение количества воркеров снижает задержку обработки. Мониторинг нагрузки на процессы LLD доступен через внутренние метрики:

```bash
zabbix_get -s <server> -k "zabbix[process,lld manager,avg,busy]"
zabbix_get -s <server> -k "zabbix[process,lld worker,avg,busy]"
```

При работе через **Zabbix Proxy** результаты LLD временно хранятся в БД прокси перед отправкой на сервер. Это добавляет задержку, пропорциональную интервалу `DataSenderFrequency` и нагрузке на прокси.

### Преимущества LLD

Использование низкоуровневого обнаружения критически важно для масштабных инфраструктур (сотни и тысячи серверов):

*   **Автоматизация:** избавляет от необходимости вручную прописывать каждый диск, сетевой интерфейс или датчик температуры.
*   **Динамичность:** если на сервере появится новый диск, Zabbix обнаружит его при следующем сканировании и автоматически начнет мониторить.
*   **Снижение ошибок:** исключает человеческий фактор при настройке однотипных объектов мониторинга.
*   **Масштабируемость:** позволяет поддерживать огромную инфраструктуру небольшими силами администраторов.

### Принцип работы

1. **Сбор данных:** LLD-правило выполняет проверку (через Zabbix Agent, Agent 2, SNMP, HTTP-агент, JMX, ODBC, IPMI, скрипт, Prometheus и др.) и получает сырые данные (обычно JSON).
2. **Предобработка (Preprocessing):** сырые данные трансформируются в требуемый JSON-массив (через JSONPath, JavaScript, CSV to JSON, Prometheus to JSON и т.д.). На этом же этапе применяется троттлинг (Discard unchanged with heartbeat).
3. **Извлечение макросов:** Zabbix парсит JSON и присваивает значения макросам `{#MACRO}` для каждого найденного объекта.
4. **Фильтрация и переопределения:** применяются регулярные выражения для отсева ненужных сущностей (Filters) и правила модификации атрибутов (Overrides).
5. **Генерация:** на основе прототипов создаются реальные сущности (элементы данных, триггеры, графики, при необходимости — даже хосты).

Правило обнаружения может быть как обычным элементом, так и **зависимым элементом (Dependent item)** — в этом случае источником сырых данных для него служит другой (master) элемент. Зависеть от другого LLD-правила нельзя: родителем discovery-правила может быть только обычный элемент данных.

### Сетевое обнаружение (Network Discovery) и его отличие от LLD

**Network Discovery** — это механизм обнаружения *хостов* в сети, а не сущностей внутри уже известного хоста. Он настраивается в `Data collection → Discovery` и выполняет периодическое сканирование заданных диапазонов IP-адресов, проверяя доступность через:

* **ICMP ping** — проверка ответа на ICMP-запрос;
* **Zabbix agent / agent (active)** — проверка доступности агента и его версии;
* **SNMP** — опрос по SNMP (учитывается значение OID `sysDescr`/`sysObjectID`);
* **иные check-типы** (e.g. SSH, LDAP, HTTP и др.).

Результаты проверок собираются в **правила действий (Action)** с условиями: обнаруженный хост может быть автоматически создан (`Add host`), добавлен в группу хостов, привязан к шаблону и т.д. Дополнительно задаётся `Device uniqueness criteria` — как различать устройства (IP-адрес, имя по DNS, значение OID SNMP).

**Ключевые различия:**

| Признак | Network Discovery | Low-Level Discovery (LLD) |
| :--- | :--- | :--- |
| Что обнаруживает | Хосты (узлы сети) | Сущности внутри хоста (диски, интерфейсы, БД) |
| Область действия | На уровне всей сети/подсети | На уровне отдельного хоста или шаблона |
| Источник данных | ICMP, SNMP, checks агента | Любой item key (agent, SNMP, HTTP, JMX, скрипт) |
| Результат | Создание/регистрация хостов | Создание элементов данных, триггеров, LLD-правил, хостов |
| Настройка | `Data collection → Discovery` + Actions | Discovery rule на хосте/шаблоне |
| Типовое применение | Первичный онбординг оборудования | Динамические ресурсы изменяющейся системы |

Механизмы дополняют друг друга: Network Discovery находит новый хост и создаёт его, после чего привязанный шаблон с LLD-правилами обнаруживает сущности внутри него. См. также описание прототипов хостов (Host prototypes) выше — они позволяют создавать хосты средствами LLD, без сканирования сети.

### Формат данных и JSONPath

Начиная с версии **Zabbix 4.2** строгий формат `{"data": [...]}` **больше не обязателен** — правило LLD принимает обычный JSON-массив в корне документа:

```json
[
  { "disk": "/", "type": "ext4" },
  { "disk": "/home", "type": "xfs" }
]
```

Для обратной совместимости сервер по-прежнему распознает старую оболочку `{"data": [...]}` и автоматически извлекает из нее содержимое по пути `$.data`, однако такой формат считается устаревшим.

Существует два способа описать макросы в LLD-правиле:

1. **Макрос в имени ключа JSON.** Если поле JSON-объекта оформлено как `"{#IFNAME}": "value"`, Zabbix автоматически распознает имя макроса и его значение:
    ```json
    [
      { "{#IFNAME}": "lo" },
      { "{#IFNAME}": "eth0" }
    ]
    ```
    Такой синтаксис используется встроенными ключами агентов (например, `net.if.discovery`).
2. **Пользовательские LLD-макросы с JSONPath.** Если в JSON нет готовых имен ключей, на вкладке **LLD macros** правила задается маппинг — каждому макросу сопоставляется JSONPath:
    * `{#FSNAME}` = `$.disk`
    * `{#FSTYPE}` = `$.type`

Допустимые символы в имени LLD-макроса: `0-9`, `A-Z`, `_`, `.` (строчные буквы в именах не поддерживаются). Значением макроса могут быть только примитивы — строка, число или boolean; массивы, объекты и `null` не поддерживаются (такой макрос остаётся неразвёрнутым). В значениях LLD-макросов доступны **macro functions** (например, `.regsub("(.*)_([0-9]+)", \1)`), позволяющие извлечь часть строки по регулярному выражению; поддерживаются с Zabbix 4.0, но не применяются в фильтре LLD-правила.

JSONPath поддерживает точечную (`$.foo`) и скобочную (`$['key with special chars']`) нотацию; скобочная обязательна при наличии специальных символов или Unicode в имени поля.

Основные выразительные возможности диалекта JSONPath в Zabbix:

* Рекурсивный обход — `$..key`.
* Индекс массива — `$[0]`; выбор элементов — `$.data[*].field`.
* Условия (фильтр-выражение) — `$[?(@.size > 10)]`; поддерживаются операторы сравнения, `=~` (совпадение с regex), логические `&&`, `||`, `!`.
* Суффикс `~` (например, `$.*~`) — применить путь не к значениям, а к **именам ключей** объекта; полезно для извлечения имен из сложных вложенных структур.
* Функции в конце пути: `sum()`, `min()`, `max()`, `avg()`, `length()`, `first()`.

### Фильтры и переопределения

* **Фильтр (Filter):** решает, *нужно ли* создавать объект (например, `{#FSTYPE} matches ext4|xfs`). Если фильтр не пройден — объект отбрасывается полностью. Фильтров может быть несколько (поддерживается с версии 2.4); для каждого макроса задается отдельное условие. Доступны операторы `matches` / `does not match` (регулярное выражение PCRE) и `exists` / `does not exist` (наличие макроса в ответе). Логика объединения условий задается **типом расчета**: `And` (все условия истинны), `Or` (достаточно одного), `And/Or` (And между разными макросами, Or между условиями одного макроса) и `Custom expression` (пользовательская формула до 255 символов, например `A and (B or C)`). Если макрос, указанный в фильтре, отсутствует в JSON-данных текущего объекта, такой объект будет проигнорирован (кроме случая условия `does not exist`).
* **Переопределение (Override):** решает, *как именно* будет сконфигурирован созданный объект. Выполняется после фильтров правила. Позволяет, например, отключить элементы данных для конкретного диска (`{#FSNAME} matches /var/log/tmp`), не удаляя их, или повысить серьезность триггера для корневого раздела (`/`). Переопределения добавлены в Zabbix **4.2**.
  * Для каждого переопределения задаются **Filters** (к каким сущностям применяется) и логика цепочки: **Continue overrides** — продолжить обработку следующих переопределений; **Stop processing** — выполнить операции текущего (и предыдущих) и игнорировать последующие для совпавших строк.
  * Переопределения применяются в порядке их списка (можно перетаскивать); выполняются после фильтров самого правила.
  * Доступные действия: обнаруживать или не обнаруживать элемент/триггер/график, создавать во включенном/отключенном состоянии, изменить интервал обновления, применить теги, изменить важность триггера и т.д.

  В **Zabbix 8.0 LTS** добавлена возможность редактирования тегов для триггеров, создаваемых по LLD-правилу, что обеспечивает полный контроль над тегированием сгенерированных сущностей.

### Троттлинг (Throttling)

Для снижения нагрузки на базу данных Zabbix в шагах предобработки LLD-правила **обязательно** следует применять шаг **Discard unchanged with heartbeat** (например, `1h` или `1d`). Это предотвращает запись одних и тех же результатов обнаружения в базу при каждой проверке, если список объектов не изменился. Допускается только одна операция троттлинга на правило.

Примечание: изменение самих прототипов НЕ сбрасывает троттлинг — сброс происходит только при изменении preprocessing-шагов правила.

### Жизненный цикл объекта (Lost Resources)

Если объект исчезает из JSON-ответа (или перестает проходить фильтр), все созданные для него сущности (элементы данных, триггеры, графики, хосты) переходят в состояние «не обнаружен» (Not discovered). Их судьба управляется двумя параметрами правила (в Zabbix 7.0 и новее; ранее существовал один параметр «Keep lost resources period», переименованный в «Delete lost resources»):

* **Отключить потерянные ресурсы (`Disable lost resources`):** никогда / сразу / через заданное время — автоматически **отключить** созданные сущности (прекратить сбор новых данных), не удаляя историю. Автоматически отключенные объекты будут **снова включены**, если сущность будет обнаружена повторно. Вручную отключенные администратором объекты повторно включаться НЕ будут.
* **Удалить потерянные ресурсы (`Delete lost resources`):** никогда / сразу / через заданное значение (по умолчанию 30 дней) — **удалить** сущности после указанного срока нахождения в состоянии «не обнаружен». Значение должно быть больше значения отключения.

Рекомендации:

* Использовать «Immediately» для удаления **не рекомендуется** — при ошибочной правке фильтра можно массово удалить элементы вместе с их историей.
* Пока сущность не удалена, в списке объектов на хосте отображается индикатор «осталось дней до удаления» (прогресс-точка у имени элемента).
* Если удаление было отложено (правило или хост были отключены), объект будет удален при следующем проходе обнаружения.
* Вложенные объекты (например, триггер на основе LLD-элемента данных) при наличии потомков, помеченных на удаление, не обновляются до полного удаления этих потомков.
* В **Zabbix 8.0 LTS** процесс отложенного удаления через Housekeeper переработан для использования housekeeper table API (`ZBXNEXT-10076`), что улучшает производительность при массовом удалении потерянных ресурсов.

### Вложенное обнаружение и прототипы хостов

Одного уровня иерархии LLD часто бывает недостаточно (например, обнаружить БД, а внутри — таблицы). Начиная с **Zabbix 7.4** поддерживается **вложенное низкоуровневое обнаружение (Nested LLD)**: внутри LLD-правила создается **прототип правила обнаружения (Discovery prototype)**, и результат проверки используется как источник данных для вложенного LLD-правила. Уровни вложенности не ограничены.

**Ключевые особенности Nested LLD:**

* При выборе типа `Nested` вложенное правило использует тот же JSON-объект, что и родительское правило. Вложенное правило может использовать preprocessing для работы с другим «срезом» тех же данных, уже полученных родителем.
* Макросы `{#MACRO}` родительского LLD-правила доступны во вложенных правилах.
* В **Zabbix 8.0 LTS** макросы LLD поддерживаются в параметрах JSONPath preprocessing и в полях пользовательских LLD-макросов вложенных правил (`ZBXNEXT-10068`), что упрощает каскадную настройку.
* Если вложенное LLD-правило используется на хосте, созданном через прототип хоста, то JSON-объект, использованный для создания хоста, автоматически передается всем вложенным LLD-правилам на этом хосте.

**Прототипы хостов (Host prototypes)** позволяют LLD автоматически добавлять в мониторинг целые хосты с интерфейсами и привязывать шаблоны (например, обнаружение ВМ на гипервизоре). Прототип хоста может быть использован и как элемент правила верхнего уровня во вложенном обнаружении. Для хостов также применимы правила управления потерянными ресурсами.

### Ограничения по размеру данных

* Нет верхнего предела размера JSON для LLD-правила, если данные приходят **непосредственно на сервер** (обрабатываются в памяти, в БД не сохраняются). В **Zabbix 8.0 LTS** поддерживается новый тип данных JSON объемом до 128 MiB, что позволяет использовать LLD для сложных структурированных данных.
* Если проверка выполняется через **UserParameter** или внешний скрипт — действует ограничение на размер возвращаемого значения (**до 16 МБ** для user parameter).
* При сборе через промежуточный **Zabbix proxy** JSON временно хранится в БД прокси, поэтому действует ограничение БД на размер текстового значения (text data limits) — например, 2048 байт для IBM DB2.
* Для HTTP Agent в **Zabbix 8.0 LTS** добавлена опция **Convert to JSON**, автоматически преобразующая полученные данные в JSON перед дальнейшей обработкой.

## Практические сценарии

### Использование встроенных правил

Zabbix предоставляет готовые правила для типовых задач (большинство реализуются агентскими ключами `*discovery`):

* **Файловые системы (`vfs.fs.discovery`):** обнаружение разделов и мониторинг их объема. Макросы: `{#FSNAME}`, `{#FSTYPE}`, `{#FSDRIVETYPE}` (последний — только Windows agent).
* **Сетевые интерфейсы (`net.if.discovery`):** автоматические графики трафика для всех портов; макрос `{#IFNAME}`.
* **CPU и ядра (`system.cpu.discovery`):** автоматизация мониторинга CPU-ресурсов; макросы `{#CPU.NUMBER}`, `{#CPU.STATUS}`.
* **СУБД и сервисы:** LLD для PostgreSQL, MySQL, Docker-контейнеров, systemd-сервисов (см. **[Мониторинг PostgreSQL](./zabbix_postgresql_monitoring.md)** и связанные шаблоны).
* **SNMP OIDs:** получение списка интерфейсов (`1.3.6.1.2.1.2.2`), дисков (`1.3.6.1.2.1.25.2.3`) и т.д.
* **JMX (через Java gateway):** обнаружение Java-объектов по MBeans.
* **IPMI sensors:** автоматический сбор датчиков по IPMI.
* **Windows:** службы (`service.discovery`), счетчики производительности (`perf_counter.discovery`), WMI-запросы.
* **WMI и ODBC:** обнаружение сущностей через WMI-запросы и SQL-запросы соответствующих ODBC-мониторов.
* **Prometheus:** данные из Prometheus-метрик (тип данных + preprocessing «Prometheus to JSON»).
* **Host interfaces:** интерфейсы хостов Zabbix (например, для построения топологии) — так называемое «discovery of host interfaces».
* **Block devices:** обнаружение блочных дисков (например, для мониторинга LVM/RAID) — `vfs.dev.discovery`/шаблоны.

### Синтаксис ключей discovery в агентах

Агент Zabbix (классика) и Agent 2 отличаются синтаксисом части discovery-ключей:

* **Zabbix Agent (классика):** `vfs.fs.discovery`, `net.if.discovery`, `system.cpu.discovery`.
* **Zabbix Agent 2:** предпочтительно использовать «модернизированные» ключи и плагины, например `vfs.fs.get` (в сочетании с preprocessing/JSONPath), `net.if.discovery`, `systemd.unit.discovery`, `docker.containers.discovery`, `docker.images.discovery`.

Несколько LLD-правил могут опираться на один и тот же ключ обнаружения (например, несколько `vfs.fs.discovery`). Начиная с Zabbix agent 3.2 для этого применяется параметр конфигурации агента `Alias`, позволяющий ссылаться на один ключ под разными именами: `vfs.fs.discovery[foo]`, `vfs.fs.discovery[bar]` и т.д.

### Вложенное обнаружение: практический пример

Рассмотрим каскадное обнаружение: **instance → tablespaces → tables**.

1. Создайте LLD-правило на хосте с именем «Discover databases and tablespaces».
2. Во вкладке **LLD Macros** добавьте макрос `{#DB}` = `$.database`.
3. Создайте Item prototype для этого правила: `db.connections[{#DB}]`.
4. Во вкладке **Discovery prototypes** создайте прототип правила обнаружения с типом `Nested`.
5. В preprocessing прототипа добавьте шаг `JSONPath = $.tablespaces`.
6. Во вкладке **LLD Macros** прототипа добавьте макрос `{#TSNAME}` = `$.name`.
7. Создайте Item prototype для прототипа: `db.ts.size[{#DB}, {#TSNAME}]`.

В результате для каждой базы данных будут созданы отдельные правила, а для каждого tablespace — отдельные элементы данных.

### Реализация кастомного обнаружения через скрипт

Алгоритм создания собственного LLD (например, для мониторинга пула запущенных Java-процессов):

#### 1. Подготовка скрипта

Скрипт на стороне агента должен возвращать список процессов в формате JSON:

```bash
#!/bin/bash
echo '[{"{#APP}": "tomcat-api"}, {"{#APP}": "kafka-worker"}]'
```

#### 2. Настройка UserParameter

В конфигурации Zabbix Agent (в каталоге `/etc/zabbix/zabbix_agentd.d/`) прописывается команда вызова:

```
UserParameter=custom.app.discovery,/opt/scripts/discover_apps.sh
```

Ограничение: предельный размер возврата через UserParameter — 16 МБ.

#### 3. Настройка LLD в веб-интерфейсе

1. Создайте LLD-правило с типом `Zabbix agent` и ключом `custom.app.discovery`. Установите интервал опроса (например, `15m` — `1h`).
2. Во вкладке **Preprocessing** добавьте шаг `Discard unchanged with heartbeat` (`1h` или `1d`).
3. Сразу после настройки правила используйте кнопку **Check now** («Выполнить сейчас») для принудительного запуска обнаружения; кнопка **Test** позволяет проверить правило без внесения изменений.
4. Создайте **Item prototypes** для метрик. Для прототипов, получающих значения push-методом от скриптов, используйте тип `Zabbix trapper`.

#### 4. Отправка данных для прототипов (Trapper)

Данные для созданных прототипов отправляются утилитой `zabbix_sender`:

```bash
zabbix_sender -z <zabbix_server> -s <hostname> -k "app.memory[tomcat-api]" -o 1024
```

Подробности: **[Отправка данных через zabbix_sender](./installation.md#отправка-данных-через-zabbix_sender)**.

#### 5. Ожидаемый результат

Вот что должен увидеть администратор после первого прохода обнаружения:

```bash
zabbix_get -s 127.0.0.1 -k custom.app.discovery
# → "[{"{#APP}":"tomcat-api"},{"{#APP}":"kafka-worker"}]"
```

В **Configuration → Hosts → Discovery rules → Item prototypes** должны появиться созданные элементы данных с подставленным вместо `{#APP}` именем приложения.

### HTTP Agent и Convert to JSON

В **Zabbix 8.0 LTS** для правил типа `HTTP agent` добавлена опция **Convert to JSON** в форме LLD-правила и Discovery prototype. Она автоматически преобразует полученные данные в JSON перед дальнейшей обработкой, что упрощает создание правил для REST API, возвращающих XML, CSV или plain text.

### Производительность при большом числе правил

Для инсталляций с сотнями LLD-правил:

* Увеличивайте `StartLLDProcessors` пропорционально ядрам CPU сервера/прокси.
* Для распределения нагрузки LLD между несколькими прокси используйте **Zabbix Proxy Groups** (Zabbix 7.0+) вместо ручной привязки хостов.
* На прокси контролируйте требуемую производительность `zabbix[requiredperformance]` и длину очереди обработки LLD `zabbix[lld_queue]`.
* Избегайте слишком частых интервалов опроса для правил с большим числом сущностей — предпочтительнее использовать `Discard unchanged with heartbeat`.

### Валидация и тестирование

| Команда / действие | Описание |
| :--- | :--- |
| `zabbix_get -s <host> -k <key>` | Получить текущее значение ключа discovery (сырые данные). |
| **Check now** в веб-интерфейсе | Принудительно запустить выполнение LLD-правила. |
| **Test** в веб-интерфейсе | Проверить правило и preprocessing без внесения изменений. |
| `zabbix_sender -z <server> -s <host> -k <key> -o <value>` | Отправить тестовое значение для trapper-прототипа. |
| **Log file** (`/var/log/zabbix/server.log`, `proxy.log`) | Поиск ошибок обработки LLD: `preprocessing failed`, `invalid JSON`, `lld manager`/`lld worker`. |
| Внутренние метрики | `zabbix[process,lld manager,avg,busy]`, `zabbix[process,lld worker,avg,busy]`, `zabbix[lld_queue]` |

### Управление потерянными ресурсами

По умолчанию Zabbix хранит необнаруженные сущности 30 дней перед удалением. Рекомендуемые значения:

* **Disable lost resources:** `7d` — достаточно для обнаружения временных сбоев.
* **Delete lost resources:** `30d` — стандартный компромисс между историей и размером БД.

### Мониторинг здоровья LLD

```bash
# Загрузить среднюю загрузку LLD Manager
zabbix_get -s <server> -k "zabbix[process,lld manager,avg,busy]"

# Загрузить среднюю загрузку LLD Workers
zabbix_get -s <server> -k "zabbix[process,lld worker,avg,busy]"

# Проверить длину очереди обработки LLD
zabbix_get -s <server> -k "zabbix[lld_queue]"
```

## Устранение неисправностей

### LLD не создает объекты

**Причины и решения:**

1. **Некорректный JSON.** Проверьте вывод ключа через `zabbix_get`. Распространенные ошибки: кавычки, trailing commas, опечатки в имени макроса. Используйте JSONPath-тестер в веб-интерфейсе.
2. **Фильтр отбрасывает все объекты.** Временно отключите фильтр или задайте `.+` для отладки.
3. **Макрос не найден.** В **Zabbix 8.0 LTS** добавлена валидация наличия LLD-макросов при создании хоста/группы прототипов (`ZBX-26552`). Убедитесь, что все макросы, используемые в прототипах, определены во вкладке **LLD Macros** или присутствуют в JSON как ключи `{#MACRO}`.
4. **Троттлинг.** Если список сущностей не изменился, LLD не перезаписывает объекты. Для принудительного обновления измените preprocessing-шаг или дождитесь истечения heartbeat.
5. **Права доступа.** Убедитесь, что у пользователя/роли есть права на создание объектов в группе хоста.
6. **Конфликт уникальности.** Сущность не будет создана, если для неё уже существует объект с тем же критерием уникальности (например, элемент данных с тем же ключом или график с тем же именем). При этом правило не становится «неподдерживаемым»: остальные сущности создаются и обновляются, а в веб-интерфейсе выводится предупреждение о том, что часть сущностей создать не удалось.

### Ошибки JSONPath

* **`Invalid JSONPath`** — проверьте синтаксис: точечная нотация для обычных имен, скобочная для спецсимволов.
* **`Cannot find macro`** — макрос используется в прототипе, но не определен в правиле. В **Zabbix 8.0** макросы LLD поддерживаются в JSONPath preprocessing вложенных правил — проверьте вложенные выражения.
* **`Array/object/null not supported`** — LLD-макросы поддерживают только строки, числа и boolean. Для сложных типов используйте preprocessing (например, JavaScript) для извлечения примитивных значений.

### Проблемы с производительностью

* **Высокая загрузка `lld manager`/`lld worker`.** Увеличьте `StartLLDProcessors` или распределите правила по нескольким прокси.
* **Большой JSON (>16 МБ через UserParameter).** Перенесите логику на сервер (зависимый элемент, HTTP Agent, SNMP) или используйте новый тип данных JSON в **Zabbix 8.0 LTS** (до 128 MiB).
* **Задержки при работе через прокси.** Уменьшите `DataSenderFrequency` и проверьте на сервере загрузку процесса proxy poller (`zabbix[process,proxy poller,avg,busy]`), а также длину очереди `zabbix[lld_queue]`.
* **Падение сервера при LLD.** В **Zabbix 8.0 LTS** исправлено падение сервера, когда БД становится недоступна во время низкоуровневого обнаружения (`ZBX-27267`). Убедитесь, что используется актуальная версия.

### Потерянные ресурсы не удаляются

* Проверьте параметры **Disable lost resources** и **Delete lost resources** в правиле.
* Убедитесь, что хост и правило не отключены — при отключенном правиле удаление не выполняется.
* Проверьте, что нет вложенных объектов, помеченных на удаление (они блокируют обновление родительских сущностей).

## Лучшие практики

### Производительность и масштабирование

* Используйте **троттлинг** на всех LLD-правилах без исключения.
* Для правил, возвращающих неизменный длинный список (например, процессы), задавайте heartbeat `1h` или `1d`.
* Увеличивайте `StartLLDProcessors` только после измерения загрузки через внутренние метрики.
* Для кластеров с высокой плотностью LLD используйте **Zabbix Proxy Groups** (Zabbix 7.0+) для распределения обработки.
* Разделяйте «тяжелые» правила (много сущностей) и «легкие» (мало сущностей) по разным хостам/прокси, чтобы избежать пиковых загрузок.

### Безопасность и операции

* Не возвращайте в LLD-ответе чувствительные данные (пароли, ключи) — JSON хранится в логах и БД прокси.
* Используйте **PSK** или сертификаты для связи агентов с сервером/прокси, особенно при передаче LLD-данных через недоверенные сети.
* Ограничьте права доступа к веб-интерфейсу: создание/редактирование LLD-правил должно быть доступно только senior-инженерам.

### Тестирование и контроль изменений

* Все новые LLD-правила тестируйте через **Check now** и **Test** перед включением в production.
* Ведите журнал изменений LLD-правил: фильтры, макросы, интервалы.
* Используйте **Discovery status** виджет на дашборде для оперативного контроля последних ошибок и данных LLD.

### Резервное копирование и восстановление

* Регулярно бэкапите базу данных Zabbix — LLD-объекты хранятся в таблицах `items`, `triggers`, `graphs`, `hosts`, `hosts_templates` и др.
* При восстановлении из бэкапа учитывайте, что прототипы и макросы LLD восстанавливаются вместе с конфигурацией, но история элементов данных может быть неполной.

### LLD в веб-интерфейсе

* **Discovery rules** (правила LLD) управляются из **Configuration → Templates (или Hosts) → Discovery**.
* Для дашбордов доступен виджет **Discovery status** («Состояние обнаружения»), отображающий последние данные и ошибки LLD.
