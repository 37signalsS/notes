## Мониторинг PostgreSQL в Zabbix

Этот документ описывает различные подходы к мониторингу базы данных PostgreSQL с использованием Zabbix, а также предоставляет рекомендации по наиболее эффективным методам.

### Краткий обзор PostgreSQL

PostgreSQL — это мощная, открытая объектно-реляционная система управления базами данных (СУБД), основанная на проекте Postgres, разработанном в Калифорнийском университете в Беркли. Она известна своей надёжностью, целостностью данных и широким набором функций.

**Редакции PostgreSQL:**
*   **Ванильный PostgreSQL (ванильный Postgres):** Классическая сборка, распространяемая свободно.
*   **Postgres Pro:** Российская коммерческая СУБД от Postgres Professional, основанная на ванильном Postgres, но с дополнительными патчами ядра, оптимизациями и сертификациями для корпоративных клиентов и российских регуляторов.
*   **Postgres-XL:** Редакция, направленная на распределенные и высоконагруженные системы, обеспечивающая горизонтальное масштабирование рабочей нагрузки по кластеру из нескольких серверов БД.

**Ключевые термины и компоненты PostgreSQL:**
*   **Сервер/Экземпляр (Server/Instance):** Программа PostgreSQL, управляющая данными. В контексте операционной системы это процесс, который слушает клиентские подключения (по умолчанию порт `5432` TCP).
*   **Кластер баз данных (Database Cluster):** В терминологии PostgreSQL, это не High Availability кластер, а **набор баз данных**, управляемых одним экземпляром сервера PostgreSQL.
*   **База данных:** Хранилище данных, управляемое сервером PostgreSQL. Один экземпляр может работать с несколькими базами данных.
*   **Журнал WAL (Write-Ahead Log):** Специальное хранилище для обеспечения надёжности и возможности восстановления данных. Все транзакции сначала записываются в WAL (сразу на диск), а затем применяются к основной базе данных. Это гарантирует, что даже в случае сбоя данные могут быть восстановлены в согласованном состоянии. WAL защищает журналируемые таблицы, но не временные или нежурналируемые.

**Клиент-серверная архитектура и процессы:**
PostgreSQL работает по клиент-серверной модели. Клиентские приложения (консольные утилиты, программы на различных языках) подключаются к серверу, используя общий протокол взаимодействия.
*   **Postmaster:** Основной процесс PostgreSQL, который слушает входящие соединения. При появлении нового клиента postmaster порождает дочерний процесс (backend process).
*   **Backend Process:** Каждый клиент общается со своим собственным backend-процессом, который обрабатывает запросы клиента. Каждый backend-процесс имеет свою локальную память.
*   **Пул соединений (Connection Pool):** Для оптимизации и ограничения количества одновременных подключений к БД (каждое из которых потребляет память и ресурсы) часто используется прослойка — пул соединений. Он поддерживает фиксированное количество соединений, а клиентские запросы ставятся в очередь, используя свободные соединения из пула.
*   **Фоновые процессы:** Postmaster также порождает и наблюдает за различными фоновыми процессами (например, bgwriter, autovacuum launcher), которые выполняют внутренние задачи по обслуживанию базы данных.

**Транзакции и свойства ACID:**
Транзакция — это последовательность операций, которая сохраняет согласованность данных. Транзакции в PostgreSQL соответствуют свойствам ACID:
*   **Атомарность (Atomicity):** Транзакция либо выполняется полностью, либо не выполняется вовсе. Команда `COMMIT` фиксирует изменения, `ROLLBACK` отменяет их.
*   **Согласованность (Consistency):** Транзакции переводят базу данных из одного согласованного состояния в другое, гарантируя выполнение всех ограничений.
*   **Изоляция (Isolation):** Одновременно выполняющиеся транзакции не должны влиять друг на друга.
*   **Долговечность (Durability):** После фиксации (`COMMIT`) данные остаются сохраненными, даже в случае сбоев (благодаря WAL).

**Выполнение запросов:**
Процесс выполнения SQL-запроса в PostgreSQL включает несколько этапов:
1.  **Парсинг:** Разбор текстового запроса, синтаксический и семантический анализ.
2.  **Переписывание/Трансформация (Rewriting):** Если запрос использует представления (VIEW) или правила, он может быть переписан во внутреннее представление.
3.  **Планирование (Planning):** Планировщик запросов (Query Planner) на основе статистики и метаинформации о таблицах (системный каталог) создает оптимальный план выполнения запроса, решая, использовать ли индексы и как лучше получить данные.
4.  **Выполнение (Execution):** Запрос выполняется согласно плану, и результат возвращается клиенту.
*   **Индексы:** Структуры данных, которые ускоряют поиск и сортировку данных, улучшая производительность запросов.

**Хранение данных и буферный кэш:**
Данные хранятся на диске в обычных файлах операционной системы, логически разделенных на страницы (блоки) фиксированного размера (обычно 8 КБ).
*   **Буферный кэш (Shared Buffers):** Область общей памяти, выделяемая PostgreSQL для кэширования часто используемых страниц данных. Это позволяет сократить количество обращений к медленному диску. Измененные данные сначала попадают в буферный кэш, затем асинхронно записываются на диск (process `bgwriter`).
*   **Кэш операционной системы:** Операционная система также кэширует дисковые операции, создавая еще один уровень кэширования.

**Репликация PostgreSQL:**
PostgreSQL поддерживает репликацию для повышения отказоустойчивости и масштабируемости.
*   **Потоковая репликация (Streaming Replication):** Наиболее распространенный вид, при котором WAL-записи передаются с ведущего сервера (master) на ведомый (replica/standby) в реальном времени. Реплика "догоняет" мастер, применяя эти WAL-записи.
    *   **WAL Sender:** Процесс на мастере, передающий WAL-записи.
    *   **WAL Receiver:** Процесс на реплике, принимающий WAL-записи.
*   **Логическая репликация (Logical Replication):** Позволяет реплицировать данные на уровне отдельных таблиц или баз данных, используя механизм "публикация/подписка".
*   **Слот репликации (Replication Slot):** Механизм, гарантирующий, что ведущий сервер не удалит WAL-записи, пока реплика не подтвердит их получение. Полезно для предотвращения отставания реплики и потери данных.
*   **Автоматический failover:** Важно отметить, что PostgreSQL не имеет встроенного автоматического failover для потоковой репликации. Для этого используются внешние инструменты, такие как Patroni, которые управляют кластером и процессами повышения статуса реплики до мастера.

**Автовакуум (Autovacuum):**
Фоновый процесс, критически важный для поддержания производительности и эффективности PostgreSQL. Он отвечает за:
*   Сбор статистики по таблицам.
*   Очистку "мертвых" строк, оставшихся после `UPDATE` или `DELETE` операций (связано с механизмом многоверсионности MVCC).
*   Предотвращение зацикливания счетчиков транзакций (transaction ID wraparound).
Автовакуум должен быть всегда включен и правильно настроен.

### Настройка PostgreSQL для мониторинга Zabbix

Для эффективного мониторинга PostgreSQL с помощью Zabbix необходимо выполнить несколько базовых настроек в самой базе данных:

1.  **Создание пользователя для мониторинга:**
    Создайте в PostgreSQL специального пользователя (например, `zabbix_monitor`), который будет использоваться Zabbix для подключения и сбора метрик. Этому пользователю необходимо предоставить минимально достаточные права для чтения системных таблиц и представлений статистики (`pg_stat_activity`, `pg_stat_database` и т.д.).

2.  **Конфигурация `pg_hba.conf`:**
    Файл `pg_hba.conf` контролирует аутентификацию клиентов PostgreSQL. Для разрешения подключения пользователя `zabbix_monitor` с Zabbix Agent 2 (или Zabbix Server/Proxy при ODBC мониторинге) необходимо добавить соответствующую запись, например:
    ```
    # TYPE  DATABASE        USER            ADDRESS                 METHOD
    host    all             zabbix_monitor  127.0.0.1/32            md5
    ```
    Эта запись разрешит пользователю `zabbix_monitor` подключаться к любым базам данных с локального хоста (127.0.0.1) с аутентификацией по паролю (md5). При подключении с удаленного хоста `127.0.0.1/32` следует заменить на IP-адрес Zabbix Server/Proxy.

3.  **Тюнинг `postgresql.conf`:**
    Конфигурационный файл `postgresql.conf` содержит множество параметров, влияющих на производительность и поведение PostgreSQL. Некоторые из них критически важны для мониторинга и оптимальной работы:
    *   **`max_connections`:** Увеличьте этот параметр, чтобы обеспечить достаточное количество подключений для приложения, административных задач и мониторинга.
    *   **`shared_buffers`:** Один из наиболее важных параметров, определяющий объем общей памяти, используемой для буферного кэша. Значение по умолчанию (128MB) часто неоптимально. Рекомендуется выделять около 25% от доступной оперативной памяти сервера.
    *   **`wal_buffers`:** Определяет объем общей памяти, используемой для буферизации WAL-записей перед их записью на диск.
    *   **`checkpoint_timeout`, `max_wal_size`:** Параметры, влияющие на частоту чекпоинтов и максимальный размер WAL-файлов, что важно для производительности записи и восстановления.
    *   **`autovacuum`:** Убедитесь, что автовакуум включен (`autovacuum = on`) и настроен. Он критически важен для очистки "мертвых" строк и поддержания производительности.
    *   **`pg_stat_statements`:** Для детального мониторинга медленных запросов и сбора статистики по запросам рекомендуется включить расширение `pg_stat_statements`. Это требует добавления `pg_stat_statements` в `shared_preload_libraries` и последующей перезагрузки PostgreSQL.

    Для упрощения тюнинга `postgresql.conf` существуют специализированные утилиты, такие как `pgtune`, которые могут генерировать оптимальные параметры на основе характеристик вашего оборудования.

### Методы мониторинга PostgreSQL в Zabbix

Существует несколько подходов к мониторингу баз данных, детальное сравнение которых приведено в основной заметке **[Мониторинг Баз Данных с помощью Zabbix](./zabbix_database_monitoring.md)**.

Для PostgreSQL наиболее современным, эффективным и функциональным подходом является использование **Zabbix Agent 2** со специализированным плагином. Этот метод обеспечивает глубокий мониторинг, высокую производительность и простоту конфигурации благодаря готовым шаблонам.

#### Ключевые возможности мониторинга с Zabbix Agent 2

Шаблоны для PostgreSQL на базе Zabbix Agent 2 используют следующие механизмы:

*   **Низкоуровневое обнаружение (Low-Level Discovery, LLD):**
    *   Автоматическое обнаружение баз данных в кластере: при создании новой базы данных Zabbix автоматически начинает собирать по ней метрики.
    *   Обнаружение слотов репликации: позволяет мониторить состояние и отставание реплик.

*   **Макросы:**
    *   Позволяют гибко настраивать параметры подключения к PostgreSQL (например, `{$PG.DSN}`, `{$PG.USER}`, `{$PG.PASSWORD}`) непосредственно в Zabbix, без необходимости изменять конфигурацию агента.

*   **Мониторируемые метрики и триггеры:**
    Zabbix Agent 2 собирает обширный набор метрик, используя внутренние таблицы и представления статистики PostgreSQL:
    *   **Состояние соединений (`pg_stat_activity`):**
        *   Количество активных, простаивающих (`idle`), ожидающих (`waiting`) соединений.
        *   Триггеры на основе роста количества `waiting` соединений могут указывать на блокировки в приложении.
        *   Пики `active` соединений могут сигнализировать о высокой нагрузке.
    *   **Блокировки (`pg_locks`):**
        *   Общее количество блокировок и их типы (эксклюзивные, общие).
        *   Триггеры на превышение пороговых значений дедлоков (`Deadlocks`) или конфликтов при восстановлении (`Recovery Conflicts`).
    *   **Транзакции (`pg_stat_database`):**
        *   Количество зафиксированных (`Commit/s`) и откаченных (`Rollback/s`) транзакций.
        *   Триггеры на аномальный рост откатов могут указывать на ошибки в приложении.
    *   **Буферный кэш:**
        *   Метрики по попаданиям в кэш (`buffer hits`) и промахам (`buffer misses`), соотношение которых позволяет оценить эффективность кэширования.
        *   Данные из `pg_stat_bgwriter` о работе фоновых процессов записи (количество чекпоинтов, запись грязных страниц).
    *   **Репликация (`pg_stat_replication`):**
        *   Отставание реплик от мастера по WAL-записям (`Streaming Lag`).
        *   Триггеры на значительное отставание реплики или неработающую репликацию.
    *   **Медленные запросы (`pg_stat_statements`):**
        *   При включенном расширении `pg_stat_statements` можно мониторить самые медленные или часто выполняемые запросы.
        *   Триггеры на `Too Many Slow Queries` сигнализируют о необходимости оптимизации запросов в приложении.
    *   **Автовакуум:**
        *   Метрики, связанные с работой процесса автовакуума, и триггеры, предупреждающие о его остановке или неэффективности.
    *   **Использование WAL:**
        *   Мониторинг роста WAL-файлов (например, при сломанной реплике) и их максимального размера.

**Установка плагина PostgreSQL для Zabbix Agent 2:**
*   На Linux-системах плагин обычно устанавливается из репозиториев Zabbix (если они подключены) или скачивается и устанавливается вручную.
*   Обратите внимание, что плагин для PostgreSQL (как и для MongoDB) требует отдельной установки из-за лицензионных ограничений; он не входит в базовую поставку Zabbix Agent 2.
*   Если плагин не установлен, Zabbix Agent 2 будет сообщать, что ключи элементов данных, связанные с PostgreSQL, не поддерживаются.

### Визуализация данных

Для визуализации собранных метрик можно использовать:
*   **Встроенные дашборды Zabbix:** Шаблоны для Zabbix Agent 2 обычно включают базовые дашборды.
*   **Grafana:** Популярный инструмент для создания красивых и информативных дашбордов, который легко интегрируется с Zabbix как источником данных.

Этот метод обеспечивает глубокий мониторинг, высокую производительность и простоту конфигурации благодаря готовым шаблонам.
