# Zabbix — лучшие практики настройки

> Основные понятия и архитектура системы описаны в разделе **[Определения и основные концепции](./definitions_and_concepts.md)**.

---

## Определения

* **Гистерезис (Hysteresis)** — механизм предотвращения «дребезжания» триггера (постоянного переключения между состояниями Problem и OK) путем установки различных пороговых значений для активации и восстановления.
* **Зависимости триггеров (Trigger Dependencies)** — иерархическая связь между триггерами, позволяющая подавлять оповещения от зависимых объектов, если проблема вызвана корневой причиной (например, недоступностью коммутатора).
* **Теги (Tags)** — основной механизм классификации, фильтрации и маршрутизации событий (заменили "Applications" в старых версиях Zabbix).
* **Усталость от оповещений (Alert Fatigue)** — эффект игнорирования уведомлений персоналом из-за чрезмерного количества некритичных или ложных срабатываний.

---

## Основные концепции

Эффективная система мониторинга строится на принципах наблюдаемости, где каждое оповещение требует действия. 

Ключевые принципы:
* **Информативность:** Оповещение должно содержать контекст и метрику, вызвавшую проблему.
* **Минимизация шума:** Использование агрегирующих функций, гистерезиса и зависимостей для исключения ложных тревог на кратковременные всплески.
* **Стандартизация:** Строгое следование правилам именования шаблонов, макросов и тегов.

## Практические сценарии

### 1. Стратегия Тегирования (Tagging Taxonomy)

В Zabbix 7.0 теги — это основа для корреляции событий и маршрутизации алертов. Рекомендуется использовать иерархическую структуру тегов. Теги наследуются от шаблона к триггерам.

| Уровень | Обязательный тег | Примеры значений |
| :--- | :--- | :--- |
| **Шаблон (Template)** | `class`, `target` | `class: database`, `target: postgresql` |
| **Элемент (Item)** | `component` | `component: cpu`, `component: memory`, `component: network` |
| **Триггер (Trigger)** | `scope` | `scope: availability` (доступность), `scope: performance` (производительность), `scope: capacity` (вместимость) |

### 2. Дизайн Шаблонов (Templates)

Современный подход (начиная с 6.0) отходит от сложного наследования (Template A → Template B) в пользу **Монолитного дизайна (Monolithic Design)**. 
* Шаблоны должны быть самодостаточными для удобства экспорта и версионирования в Git.
* **Именование:** `Класс: Технология [Метод]` (например, `Database: MySQL by ODBC`).
* **Макросы:** Используйте префиксы для изоляции переменных (например, `{$MYSQL.PORT}` вместо `{$PORT}`), чтобы избежать конфликтов при привязке нескольких шаблонов к одному хосту.

### 3. Современный синтаксис и настройка триггеров

Синтаксис триггеров в новых версиях Zabbix изменился. Старый формат `{host:key.func()}` устарел. 
Новый формат: `function(/host/key,parameter) <operator> <constant>`.

#### Снижение ложных срабатываний
Избегайте триггеров на мгновенные пики (функция `last()`). Используйте агрегацию за период:
```bash
# Плохо: Сработает при случайном пике
last(/Server/system.cpu.load) > 5

# Хорошо: Сработает, если нагрузка стабильно высока 5 минут
avg(/Server/system.cpu.load,5m) > 5
```

#### Настройка Гистерезиса
Используйте отдельное **Recovery Expression**. 
* **Problem:** Температура больше 30.
* **Recovery:** Сбросить алерт, только когда температура упадет ниже 25.
```bash
# Problem Expression
last(/Room/sensor.temp) > 30

# Recovery Expression
last(/Room/sensor.temp) < 25
```

#### Использование Expression Macros
В Zabbix 7.0 для отображения значения, вызвавшего проблему, прямо в названии алерта (Event Name) используется макрос выражений `{?EXPRESSION}`.
* **Event Name:** `High CPU load: {?avg(/Host/system.cpu.load,5m)}`
* **В интерфейсе будет:** `High CPU load: 5.42`

#### Функции трендов
Для анализа больших периодов (недели) используйте функции `trendavg`, `trendmax`. Они обращаются к заранее агрегированным данным (trends), а не к сырой истории, что значительно снижает нагрузку на базу данных (см. **[Тюнинг производительности](./zabbix_troubleshooting_and_performance_tuning.md)**).

### 4. Стратегия оповещений

| Канал | Применение | Рекомендации |
| :--- | :--- | :--- |
| **Telegram / Slack** | Оперативное информирование | Использование групп для командного взаимодействия. |
| **Service Desk (Jira)** | Инцидент-менеджмент | Автоматическое создание тикетов для уровней `High` и `Disaster`. |
| **SMS / Звонки** | Критические аварии | Только для уровня `Disaster` и `scope: availability` в нерабочее время. |
