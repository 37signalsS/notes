# Лучшие практики настройки Zabbix

## 1. Определения

* **Триггер (Trigger):** Выражение (условие), которое определяет пороговое значение для элемента данных и генерирует событие (проблему) при его превышении или невыполнении.
* **Оповещение (Alert/Notification):** Сообщение, отправляемое пользователю или системе при срабатывании триггера, информирующее о возникшей проблеме.
* **Гистерезис (Hysteresis):** Механизм, предотвращающий "дребезжание" триггера путем установки разных пороговых значений для перехода в состояние "Проблема" и возврата в состояние "ОК".
* **Уровни серьезности (Severity Levels):** Классификация проблем в Zabbix (Information, Warning, Average, High, Disaster), позволяющая приоритизировать оповещения.
* **Зависимости триггеров (Trigger Dependencies):** Возможность связывать триггеры таким образом, чтобы оповещение генерировалось только для корневой причины проблемы, а не для всех зависимых объектов.

## 2. Базовые концепции

Мониторинг в Zabbix основан на сборе данных (метрики) и их последующем анализе для выявления аномалий. Триггеры играют ключевую роль в этом процессе, преобразуя сырые данные в осмысленные события. При срабатывании триггера Zabbix может выполнять различные действия, включая отправку оповещений по настроенным каналам. Грамотная настройка этих компонентов позволяет избежать "усталости от оповещений" и обеспечивает своевременное реагирование на реальные проблемы.

## 3. Практические сценарии

### 3.1. Настройка триггеров: лучшие практики

Цель грамотной настройки триггеров — своевременно информировать о *реальных* проблемах, а не генерировать "шум", к которому администраторы со временем привыкают.

#### 3.1.1. Предотвращение ложных срабатываний (Alert Fatigue)

* **Чувствительность мониторинга:** Избегайте настройки слишком чувствительных триггеров, которые срабатывают на "каждый чих". Это приводит к так называемой "усталости от оповещений" (alert fatigue), когда сотрудники перестают реагировать на уведомления, считая их несущественными.
* **Определение критичности:** Четко определите, что является критичным событием для вашей инфраструктуры. Вместо немедленного оповещения о кратковременной недоступности (например, 10 секунд), настройте триггер на срабатывание только после нескольких последовательных неудачных проверок или по истечении определенного времени (например, если сервис недоступен более 5 минут).
* **Гистерезис:** Для предотвращения "дребезжания" триггеров, когда метрика колеблется на границе порогового значения, используйте гистерезис. Задавайте разные условия для `Problem expression` (выражение проблемы) и `OK event generation` (условие восстановления). Например, проблема возникает при значении > 90%, а восстанавливается при значении < 80%.
* **Функции для анализа трендов:** Для анализа данных за длительные периоды (недели, месяцы) используйте функции, работающие с трендами (`trendavg`, `trendmax`), вместо функций для истории (`avg`, `max`). Это значительно снижает нагрузку на `Value Cache` и базу данных.
* **Пример из практики:** Триггер на "количество абонентов менее 1000" в телекоммуникационной компании. При незначительных колебаниях (999 абонентов) оповещения генерировались постоянно, к ним привыкли. В итоге, когда произошел реальный сбой оборудования и количество абонентов упало до 100-200, на аварию среагировали несвоевременно из-за игнорирования "привычных" оповещений.

#### 3.1.2. Приоритизация триггеров

* **Уровни серьезности:** Используйте встроенные уровни серьезности Zabbix (Information, Warning, Average, High, Disaster) для классификации проблем. Оповещения настраивайте в первую очередь для триггеров с высокой и чрезвычайной серьезностью. Остальные могут служить для информационных целей или для построения графиков.

#### 3.1.3. Зависимости триггеров

* **Иерархия инфраструктуры:** Используйте зависимости между триггерами для предотвращения шторма оповещений. Если вышел из строя коммутатор, за которым находятся 50 серверов, нет смысла получать 50 оповещений о недоступности серверов. Достаточно одного оповещения о недоступности коммутатора. Zabbix позволяет настраивать такие зависимости, чтобы оповещалась только корневая причина проблемы.

### 3.2. Настройка каналов оповещений: лучшие практики

Zabbix предлагает богатые возможности для настройки оповещений на основе сработавших триггеров.

* **Email:** Отправка уведомлений на электронную почту. Требует настройки SMTP-сервера и корректной конфигурации DNS (SPF, DKIM, DMARC) для предотвращения попадания писем в спам.
  * **Важно:** почтовый протокол SMTP является очень старым и требователен к настройке для обеспечения гарантированной доставки.
* **Telegram:** Удобный, быстрый и часто более надежный способ получения оповещений через Telegram-бота. Настройка, как правило, значительно проще, чем SMTP, и не требует сложных манипуляций с DNS. Большинство пользователей уже имеют Telegram с push-уведомлениями, что обеспечивает высокую вероятность своевременного получения оповещения.
* **Service Desk:** Интеграция с системами Service Desk (например, Jira, Redmine) для автоматического создания тикетов по инцидентам.
* **Чат-системы:** Поддержка интеграции с корпоративными мессенджерами, такими как Slack, Discord.
* **SMS-шлюзы:** Отправка SMS-сообщений для самых критичных уведомлений.
* **Push-уведомления:** Через специализированные приложения. Хотя такая возможность есть, часто Telegram с его встроенными push-уведомлениями является более предпочтительным решением.

### 3.3. Веб-проверки: Browser vs Web Scenarios

Zabbix предоставляет два подхода к мониторингу веб-приложений:

* **Web Scenarios (веб-сценарии):** Устаревший метод. Последовательность шагов без условной логики (нет `if/else`). Каждый шаг проверяет доступность URL, наличие строки, код ответа. Обрабатываются процессом `HTTP Poller`.
* **Browser Checks (браузерные проверки):** Современный рекомендуемый подход. Элемент данных типа `Browser`, который выполняет JavaScript-скрипт через Selenium Driver. Поддерживает ветвление, условия, скриншоты. Позволяет моделировать реальное поведение пользователя на странице.

**Рекомендация:** для нового веб-мониторинга используйте Browser Checks. Они гибче, позволяют делать скриншоты и точнее отражают состояние веб-приложения.

### 3.4. Низкоуровневое обнаружение (LLD)

* **Интервал выполнения:** Для большинства сущностей (диски, файловые системы, сетевые интерфейсы) достаточно одного раза в день. Частое выполнение LLD создаёт ненужную нагрузку.
* **Фильтрация:** Используйте фильтры в правилах LLD для исключения ненужных объектов. Например, в шаблоне VMware можно фильтровать ВМ по `Power State`, обнаруживая только `poweredOn`.
* **Nested LLD (Zabbix 7.4+):** Поддержка вложенного обнаружения на несколько уровней. Например, Proxmox: ноды → виртуальные машины → диски каждой ВМ.
* **Обработка на сервере:** LLD Workers на сервере получают данные от агентов/прокси и создают элементы/триггеры. Настройка фильтров на уровне правила LLD уменьшает объём передаваемых данных.

### 3.5. Мониторинг компонентов самого Zabbix

Обязательная практика — настроить мониторинг собственной инфраструктуры Zabbix:

* **Zabbix Server Health:** Шаблон для мониторинга ядра. Собирует метрики по кэшам, процессам, очереди, производительности.
* **Zabbix Proxy Health:** Аналогичный шаблон для каждого прокси.
* **База данных Zabbix:** Мониторинг производительности, размера таблиц, скорости записи.
* **Веб-сервер (Nginx/Apache) + PHP-FPM:** Мониторинг через соответствующие шаблоны.
* **Операционная система:** CPU, память, диск, сеть на серверах Zabbix и прокси.

Без мониторинга собственных компонентов вы можете не заметить, что Zabbix Server упал, тогда как веб-интерфейс продолжает работать.

### 3.6. Аудит событий и «шумные» триггеры

* **Регулярный аудит:** Периодически проверяйте `Monitoring -> Problems` — есть ли события, по которым никто не реагирует. Если оповещения не настроены и события просто накапливаются, отключите такие триггеры. Они создают фоновый шум.
* **`Reports -> Triggers top 100`:** Показывает самые «шумные» триггеры — кандидаты на пересмотр порогов, гистерезиса или удаление.
* **nodata() не вешать на всё:** Триггеры типа `nodata()` могут генерировать лавину событий при массовом сбое сбора данных. Применяйте их только к критичным элементам.
