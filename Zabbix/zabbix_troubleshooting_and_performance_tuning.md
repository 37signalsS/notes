# Zabbix — поиск, устранение неисправностей и тюнинг производительности

> Данная заметка дополняет **[Лучшие практики настройки Zabbix](./zabbix_best_practices.md)**, фокусируясь на глубокой диагностике и аппаратной оптимизации.

## Определения

* **Поиск и устранение неисправностей (Troubleshooting)** — процесс выявления корневых причин технических сбоев, таких как задержки в очереди, ошибки в логах или недоступность компонентов мониторинга.
* **Тюнинг производительности (Performance Tuning)** — конфигурационная и системная настройка Zabbix Server, Proxy и базы данных для обеспечения стабильной работы при высокой нагрузке.
* **NVPS (New Values Per Second)** — количество новых значений, обрабатываемых системой в секунду; основной показатель производительности Zabbix.

## Основные концепции

### Типичные симптомы проблем

* **Рост очереди (Queue):** основной индикатор перегрузки поллеров или проблем с сетевой доступностью.
* **Разрывы на графиках (Gaps):** свидетельствуют о потере данных или критических задержках записи в БД (База Данных).
* **Медленный веб-интерфейс:** чаще всего указывает на блокировки в базе данных или нехватку ресурсов PHP-FPM (FastCGI Process Manager).

### Ключевые кэши и их назначение

Для стабильной работы необходимо отслеживать утилизацию следующих кэшей:

* **History Cache:** хранит данные перед записью в БД. Переполнение указывает на медленную дисковую подсистему I/O (Input/Output — ввод-вывод) или неэффективные индексы.
* **Value Cache:** кэш для расчета триггеров. При нехватке памяти Zabbix обращается к БД, что резко снижает производительность.
* **Configuration Cache:** содержит информацию об объектах мониторинга. В Zabbix 7.0+ обновляется инкрементально.

Подробное описание кэшей и процессов приведено в официальной документации и внутренних шаблонах самодиагностики.

## Практические сценарии

### Анализ производительности процессов

Мониторинг утилизации процессов (`Zabbix busy ... process`) позволяет выявить узкие места:

1. **Pollers:** при высокой загрузке следует увеличить их количество или использовать асинхронные проверки (Zabbix 7.0+).
2. **History Syncers:** отвечают за запись в БД и расчет триггеров. Высокая загрузка — признак проблем с производительностью СУБД (Система Управления Базами Данных).
3. **Preprocessing Workers:** выполняют трансформацию данных. Рекомендуется переносить нагрузку на **Zabbix Proxy**.

### Использование инструментов диагностики

* **Системные утилиты:** `top`, `htop`, `iostat` для мониторинга ресурсов ОС (Операционная Система).
* **Логи Zabbix:** повышение уровня логирования для конкретных процессов через команду `zabbix_server -R log_level_increase`.
* **Debug Mode:** встроенный режим отладки в веб-интерфейсе для анализа SQL (Structured Query Language — язык структурированных запросов) и времени выполнения PHP-скриптов.

### Тюнинг базы данных

Для высоконагруженных систем критически важно:

1. **Партиционирование:** использование TimescaleDB для PostgreSQL или ручное партиционирование таблиц истории и трендов.
2. **Оптимизация запросов:** анализ медленных запросов через `LogSlowQueries` и системные представления СУБД.

Рекомендации по проектированию логики мониторинга (гистерезис, функции трендов) приведены в разделе **[Лучшие практики настройки Zabbix](./zabbix_best_practices.md)**.
