## Поиск и устранение неисправностей и тюнинг производительности Zabbix

### Определения

**Поиск и устранение неисправностей (Troubleshooting)** Zabbix — это процесс диагностики и решения проблем, возникающих в системе мониторинга Zabbix, включая сбои сбора данных, задержки обработки и некорректную работу триггеров.

**Тюнинг производительности (Performance Tuning)** Zabbix — это процесс оптимизации конфигурации Zabbix Server, Proxy и Agent, а также его базы данных, для обеспечения эффективной работы в условиях высокой нагрузки и предотвращения возникновения проблем с производительностью.

> Данная заметка дополняет **[общий обзор Zabbix](./zabbix_overview.md)**, фокусируясь на диагностике и оптимизации высоконагруженных инсталляций.

### Базовые концепции

#### 1. Типичные симптомы проблем с производительностью

* **Большая очередь (Zabbix Queue)**: Основной индикатор проблем со сборщиками данных или недоступностью хостов. Отображается в `Administration` -> `Queue`.
* **Разрывы на графиках (Gaps on Graphs)**: Следствие большой очереди, указывает на непоступление данных.
* **Медленная работа веб-интерфейса**: Чаще всего связана с низкой производительностью базы данных или веб-сервера.
* **Ложные срабатывания триггеров `nodata()`**: Происходят при отсутствии поступления данных в заданный интервал.
* **Ошибки в логах Zabbix Server/Proxy**: Регулярный просмотр логов (`error`) необходим для выявления проблем.

#### 2. Ключевые компоненты Zabbix и их влияние на производительность

##### 2.1. Кэши (Caches)

Zabbix использует несколько кэшей в оперативной памяти для ускорения работы. За их утилизацией следует следить с помощью шаблона `Zabbix server health`.

* **`History Cache`**: Хранит собранные данные перед записью в базу данных. Если этот кэш переполняется, это указывает на проблемы со скоростью записи в БД.
* **`History Index Cache`**: Кэш индексов для кэша истории.
* **`Value Cache` (Кэш значений)**: Критически важный кэш, используемый для вычисления триггеров на основе сырых данных истории. Если кэша не хватает для вычисления сложного триггера (например, за большой период), Zabbix будет выполнять дорогостоящие запросы к БД.
* **`Trend Cache`**: Хранит усредненные данные (тренды) перед записью в БД.
* **`Configuration Cache`**: Хранит конфигурацию мониторинга (узлы, элементы, триггеры). Zabbix Server периодически обновляет этот кэш из БД. В Zabbix 7.0 это происходит инкрементально каждые 10 секунд.

##### 2.2. Процессы (Processes)

Мониторинг утилизации процессов (`Zabbix busy ... process, %`) — основной способ выявления узких мест.

* **Сборщики данных (Data Collectors):**
  * **Pollers** (`zabbix_agent (passive)`, `simple check`): Синхронные процессы для пассивных и простых проверок.
  * **Asynchronous Pollers** (Zabbix 7.0+): Для проверок `Zabbix agent`, `HTTP agent` и `SNMP agent`. Стали асинхронными, что значительно повышает производительность. Настраиваются через `MaxConcurrentChecksPerPoller`.
  * **Trappers**: Принимают данные от активных агентов, прокси и утилиты `zabbix_sender`.
  * **Unreachable Pollers**: Опрашивают недоступные узлы. Высокая утилизация этих процессов говорит о большом количестве "мертвых" хостов в системе, которые нужно либо исправлять, либо удалять.

* **Обработка данных (Data Processing):**
  * **History Syncers (DB Syncers)**: Один из самых важных процессов. Отвечает за запись исторических данных и трендов в БД, а также за обработку триггеров. Является основным потребителем ресурсов БД.
  * **Preprocessing Workers**: Выполняют предварительную обработку данных. Эту нагрузку рекомендуется переносить на [Zabbix Proxy](./zabbix_overview.md#Компоненты).
  * **LLD Workers**: Отвечают за выполнение правил низкоуровневого обнаружения (LLD).

* **Другие процессы:**
  * **Housekeeper**: Удаляет устаревшие данные (историю, события, тренды). При больших объемах данных его работа может вызывать серьезную нагрузку на БД. **Крайне рекомендуется использовать партиционирование таблиц**, чтобы избежать проблем с `Housekeeper`.
  * **Escalators и Alerters**: Отвечают за выполнение действий (эскалаций) и отправку оповещений.

### Практические сценарии

#### 1. Инструменты для диагностики

* **Системные утилиты**: [`top`](../Linux/Diagnostics/Processes/top.md), [`htop`](../Linux/Diagnostics/Processes/htop.md), `iostat`, `vmstat` для анализа загрузки CPU, I/O и памяти на серверах Zabbix и БД.
* **Встроенные средства Zabbix**:
  * **Шаблоны `Zabbix server health` и `Zabbix proxy health`**: Для мониторинга внутренних процессов и кэшей.
  * **Дашборд очередей (`Administration -> Queue`)**: Показывает задержки по типам проверок и прокси.
  * **Отчет `Reports -> Triggers top 100`**: Позволяет выявить наиболее "шумные" триггеры. Подробнее в **[лучших практиках настройки Zabbix](./zabbix_best_practices.md)**.
  * **Логи Zabbix**: Повышение уровня логирования для конкретного процесса (`zabbix_server -R log_level_increase="<process_type>"`) для детальной отладки.
* **Диагностика базы данных**:
  * Включение `LogSlowQueries` в `zabbix_server.conf` для логирования медленных запросов к БД.
  * Использование специфичных для БД инструментов, например, `pg_stat_statements` для PostgreSQL.
* **Отладка веб-интерфейса**:
  * Включение **Debug mode** для пользователя Zabbix: добавляет отладочную информацию (SQL-запросы, время выполнения) в футер страницы. Если `SQL time` близок к `Total time`, проблема в базе данных. Если `SQL time` значительно меньше `Total time`, проблема на стороне веб-сервера (PHP-FPM, Apache/Nginx).

#### 2. Практические рекомендации по тюнингу

* **Оптимизация триггеров**:
  * Используйте функции для трендов (`trendavg`, `trendmax`) вместо функций для истории (`avg`, `max`) для анализа длительных периодов. Это снижает нагрузку на `Value Cache` и БД.
  * Применяйте гистерезис в триггерах для предотвращения "дребезжания" (разные условия для `Problem expression` и `OK event generation`).

* **Оптимизация базы данных**:
  * Используйте **PostgreSQL с расширением TimescaleDB** или настройте **партиционирование** для исторических таблиц (`history*`, `trends*`). Это значительно ускоряет работу `Housekeeper` и улучшает общую производительность. См. [Мониторинг PostgreSQL в Zabbix](./zabbix_postgresql_monitoring.md).

* **Препроцессинг**:
  * Используйте опцию **"Discard unchanged"** в шагах предобработки для экономии места в БД, не храня дублирующиеся значения.
  * Переносите всю возможную предобработку на **[Zabbix Proxy](./zabbix_overview.md#Компоненты)**.

* **Низкоуровневое обнаружение (LLD)**:
  * Увеличивайте интервал обновления для правил LLD. Для большинства сущностей достаточно одного раза в день.

* **Архитектура Zabbix**:
  * Активно используйте **[Zabbix Proxy](./zabbix_overview.md#Компоненты)** для сбора данных, позволяя Zabbix Server заниматься исключительно их обработкой.
  * Предпочитайте **[активные проверки](./zabbix_overview.md#Модель-сбора-данных-Push-модель)** пассивным для лучшей масштабируемости и снижения нагрузки на `Pollers` сервера/прокси.
  * Поддерживайте версии Server, Proxy и Agents в актуальном и согласованном состоянии для использования последних улучшений производительности.
