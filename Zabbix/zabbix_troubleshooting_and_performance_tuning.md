## Поиск и устранение неисправностей и тюнинг производительности Zabbix

> Данная заметка дополняет **[общий обзор Zabbix](./zabbix_best_practices.md)**, фокусируясь на диагностике и оптимизации высоконагруженных инсталляций.

## Определения

**Поиск и устранение неисправностей (Troubleshooting)** Zabbix — процесс диагностики и решения проблем, включая сбои сбора данных, задержки обработки и некорректную работу триггеров.

**Тюнинг производительности (Performance Tuning)** Zabbix — процесс оптимизации конфигурации Zabbix Server, Proxy и Agent, а также БД, для обеспечения эффективной работы при высокой нагрузке.

### Базовые концепции

#### 1. Типичные симптомы проблем с производительностью

* **Большая очередь (Zabbix Queue)**: Основной индикатор проблем со сборщиками данных или недоступностью хостов. Отображается в `Administration` -> `Queue`.
* **Разрывы на графиках (Gaps on Graphs)**: Следствие большой очереди, указывает на непоступление данных.
* **Медленная работа веб-интерфейса**: Чаще всего связана с низкой производительностью базы данных или веб-сервера.
* **Ложные срабатывания триггеров `nodata()`**: Происходят при отсутствии поступления данных в заданный интервал.
* **Ошибки в логах Zabbix Server/Proxy**: Регулярный просмотр логов (`error`) необходим для выявления проблем.

#### 2. Ключевые компоненты Zabbix и их влияние на производительность

##### 2.1. Кэши (Caches)

Zabbix использует несколько кэшей в оперативной памяти для ускорения работы. За их утилизацией следует следить с помощью шаблона `Zabbix server health`.

* **`History Cache`**: Хранит собранные данные перед записью в базу данных. Максимальный размер — 2 ГБ. Если этот кэш переполняется (утилизация > 60%), Zabbix прекращает приём данных от Zabbix Proxy до тех пор, пока данные не будут записаны в БД. Это указывает на проблемы со скоростью записи в БД или на перегруженность DB Syncer.
* **`History Index Cache`**: Кэш индексов для кэша истории. Рекомендуемый размер — 1/4 от `History Cache` (например, 512 МБ при 2 ГБ History Cache).
* **`Value Cache` (Кэш значений)**: Критически важный кэш, используемый для вычисления триггеров на основе сырых данных истории. Максимальный размер — 64 ГБ. Если кэша не хватает для вычисления сложного триггера (например, за большой период), Zabbix будет выполнять дорогостоящие запросы к БД. Триггеры с большими интервалами (неделя, две недели) при частом сборе метрик (раз в секунду) — основная причина перегрузки этого кэша. **Решение:** переход на функции трендов (`trendavg`, `trendmax`) для больших периодов.
* **`Trend Cache`**: Хранит усредненные данные (тренды) перед записью в БД. Тренды рассчитываются каждый час для элементов данных типов `Numeric (float)` и `Numeric (unsigned)`. Для метрик, собираемых реже одного раза в час, тренды не рассчитываются.
* **`Trend Function Cache`**: Кэш значений на основе трендов для расчёта триггеров. Аналог `Value Cache`, но для trend-функций. Максимальный размер — 8 ГБ. Используйте этот кэш, настроив триггеры на trend-функциях, для анализа длительных периодов без перегрузки `Value Cache`.
* **`Configuration Cache`**: Хранит конфигурацию мониторинга (узлы, элементы, триггеры). Максимальный размер — 64 ГБ. В Zabbix 7.0+ обновление происходит **инкрементально каждые 10 секунд** (до 7.0 — полностью раз в минуту, что было значительно медленнее). При росте конфигурации этот кэш необходимо увеличивать.

##### 2.2. Процессы (Processes)

Мониторинг утилизации процессов (`Zabbix busy ... process, %`) — основной способ выявления узких мест.

* **Сборщики данных (Data Collectors):**
  * **Pollers** (`zabbix_agent (passive)`, `simple check`): Синхронные процессы для пассивных и простых проверок.
  * **Asynchronous Pollers** (Zabbix 7.0+): Для проверок `Zabbix agent`, `HTTP agent` и `SNMP agent`. Стали асинхронными, что значительно повышает производительность. Каждый полер может работать в несколько потоков. Количество потоков настраивается через `MaxConcurrentChecksPerPoller`. Максимум 1000 поллеров × 1000 потоков = до 1 млн одновременных проверок. На практике увеличивайте количество поллеров или потоков последовательно, наблюдая за снижением утилизации.
  * **Trappers**: Принимают данные от активных агентов, прокси и утилиты `zabbix_sender`. Также отдают конфигурацию активным агентам и прокси. **Рекомендация:** для каждого активного Zabbix Proxy использовать минимум 2 trapper-процесса (один для приёма конфигурации, второй — для приёма данных).
  * **Unreachable Pollers**: Опрашивают недоступные хосты. Высокая утилизация этих процессов говорит о большом количестве "мёртвых" хостов в системе, которые нужно либо исправлять, либо удалять.
  * **SNMP Pinger**: Отвечает исключительно за проверки по протоколу ICMP (пинги).
  * **HTTP Poller**: Отвечает за веб-сценарии (устаревший метод веб-мониторинга). Не путать с асинхронным HTTP Agent Poller.
  * **Proxy Poller**: Отвечает за опрос пассивных Zabbix Proxy — загрузку конфигурации и забор собранных данных.

* **Обработка данных (Data Processing):**
  * **History Syncers (DB Syncers)**: Один из самых важных процессов. Отвечает за запись исторических данных и трендов в БД, а также за **расчёт триггеров**. Триггеры рассчитываются при поступлении новых данных; если в формуле триггера есть функции времени (`time()`, `date()` и т.д.), расчёт выполняется каждые 30 секунд. Является основным потребителем ресурсов БД.
  * **Preprocessing Workers**: Выполняют предварительную обработку данных. Начиная с Zabbix 7.0.17 / 7.2.x элементы данных, не требующие препроцессинга, обходят очередь предобработки, что ускоряет попадание данных в History Cache. Нагрузку с препроцессинга рекомендуется переносить на [Zabbix Proxy](./zabbix_best_practices.md#35-мониторинг-компонентов-самого-zabbix) — при использовании прокси препроцессинг для элементов данных выполняется на прокси, а не на сервере.
  * **LLD Workers**: Отвечают за выполнение правил низкоуровневого обнаружения (LLD). Процессы на сервере выдают задания агентам и прокси; обработка результатов и создание элементов/триггеров происходит на сервере.

* **Другие процессы:**
  * **Housekeeper**: Удаляет устаревшие данные (историю, события, тренды). При больших объёмах данных его работа может вызывать серьёзную нагрузку на БД. **Крайне рекомендуется использовать партиционирование таблиц**, чтобы избежать проблем с `Housekeeper`.
  * **Timer**: Управляет режимами обслуживания (maintenance mode). Проверяет расписания и переводит хосты в режим обслуживания по расписанию.
  * **History Poller**: Отвечает за вычисляемые элементы данных (calculated items).
  * **Escalators и Alerters**: Отвечают за выполнение действий (эскалаций) и отправку оповещений.

### Практические сценарии

#### 1. Инструменты для диагностики

* **Системные утилиты**: [`top`](../Linux/Diagnostics/Processes/top.md), [`htop`](../Linux/Diagnostics/Processes/htop.md), `iostat`, `vmstat`, `ps aux | grep zabbix` для анализа загрузки CPU, I/O и памяти на серверах Zabbix и БД.
* **Встроенные средства Zabbix**:
  * **Шаблоны `Zabbix server health` и `Zabbix proxy health`**: Для мониторинга внутренних процессов и кэшей. Включают дашборды с утилизацией кэшей, процессов, очереди.
  * **Дашборд System Information**: Показывает статус Zabbix Server (работает/упал), текущую версию, количество шаблонов, элементов данных, триггеров, состояние таблиц БД, требуемый апдейт.
  * **Дашборд очередей (`Administration -> Queue`)**: Показывает задержки по типам проверок и прокси. **Важно:** очередь хранится только в оперативной памяти сервера и обнуляется при перезагрузке. В очереди отображаются только данные, которые ещё не были собраны (например, отвалившиеся по тайм-ауту); данные, застрявшие в History Cache или на этапе препроцессинга, в очереди не видны. Доступны три представления: общая очередь, очередь по прокси, очередь по отдельным элементам данных.
  * **Отчёт `Reports -> Triggers top 100`**: Позволяет выявить наиболее "шумные" триггеры. Подробнее в **[лучших практиках настройки Zabbix](./zabbix_best_practices.md)**.
  * **Логи Zabbix**: Повышение уровня логирования для конкретного процесса (`zabbix_server -R log_level_increase="<process_type>"`) для детальной отладки. В логах напротив каждой строки указывается ID процесса — можно отфильтровать записи по ID проблемного процесса.
  * **Audit Log / Zabbix API Logs**: Позволяют отследить, какие пользователи через API запрашивают большие объёмы истории, что может вызывать нагрузку на отдельные DB Syncer.
* **Диагностика базы данных**:
  * Включение `LogSlowQueries` в `zabbix_server.conf` для логирования медленных запросов к БД.
  * Использование специфичных для БД инструментов, например, `pg_stat_statements` для PostgreSQL.
* **Отладка веб-интерфейса**:
  * Включение **Debug mode** для пользователя Zabbix (настраивается в группе пользователей): добавляет отладочную информацию (SQL-запросы, время выполнения) в футер страницы. Если `SQL time` близок к `Total time`, проблема в базе данных. Если `SQL time` значительно меньше `Total time`, проблема на стороне веб-сервера (PHP-FPM, Apache/Nginx).
* **Grafana**:
  * **Direct DB Connection**: При включении этой опции Grafana извлекает исторические данные напрямую из БД (конфигурация — через Zabbix API). Если есть реплика БД, Grafana можно настроить на реплику, чтобы не нагружать основную базу.
* **Автоматический сбор диагностики через Actions**: Можно настроить действие в Zabbix, которое при срабатывании триггера (например, высокая утилизация CPU/RAM) выполнит скрипт сбора диагностики на хосте. Результат сохраняется для последующего анализа — позволяет определить, какой процесс вызвал проблему в конкретный момент.

#### 2. Практические рекомендации по тюнингу

* **Оптимизация триггеров**:
  * Используйте функции для трендов (`trendavg`, `trendmax`) вместо функций для истории (`avg`, `max`) для анализа длительных периодов. Это снижает нагрузку на `Value Cache` и БД.
  * Применяйте гистерезис в триггерах для предотвращения "дребезжания" (разные условия для `Problem expression` и `OK event generation`).
  * Триггеры с функциями времени (`time()`, `date()`) рассчитываются каждые 30 секунд независимо от поступления данных — используйте их осознанно.

* **Оптимизация сбора данных**:
  * **Custom Intervals**: Настройте разные интервалы сбора для разного времени суток. Например, ночью и по выходным собирайте данные реже, если нагрузка на инфраструктуру минимальна.
  * **Discard unchanged / Discard unchanged with heartbeat**: Используйте шаги предобработки для отбрасывания неизменных значений (серийные номера, вендоры, статичная инвентарная информация). Нет смысла хранить дубликаты в БД.

* **Оптимизация базы данных**:
  * Используйте **PostgreSQL с расширением TimescaleDB** или настройте **партиционирование** для исторических таблиц (`history*`, `trends*`). Это значительно ускоряет работу `Housekeeper` и улучшает общую производительность. См. [Мониторинг PostgreSQL в Zabbix](./zabbix_postgresql_monitoring.md).

* **Препроцессинг**:
  * Используйте опцию **"Discard unchanged"** в шагах предобработки для экономии места в БД, не храня дублирующиеся значения.
  * Переносите всю возможную предобработку на **[Zabbix Proxy](./zabbix_best_practices.md#35-мониторинг-компонентов-самого-zabbix)**. При использовании прокси препроцессинг выполняется на нём, а не на сервере.
  * Обновитесь до Zabbix 7.0.17+ / 7.2.x+: элементы без препроцессинга теперь обходят очередь, что ускоряет обработку данных.

* **Низкоуровневое обнаружение (LLD)**:
  * Увеличивайте интервал обновления для правил LLD. Для большинства сущностей достаточно одного раза в день.
  * Используйте фильтры в правилах LLD для исключения ненужных объектов. Например, в шаблоне VMware можно отфильтровать выключенные ВМ по атрибуту `Power State` (`poweredOff`, `suspended`), чтобы обнаруживались только работающие.
  * В Zabbix 7.4+ доступен **вложенный LLD** (nested LLD) — обнаружение на несколько уровней вложенности (например, Proxmox: ноды → ВМ → диски).

* **Архитектура Zabbix**:
  * Активно используйте **[Zabbix Proxy](./zabbix_best_practices.md#35-мониторинг-компонентов-самого-zabbix)** для сбора данных, позволяя Zabbix Server заниматься исключительно их обработкой.
  * Предпочитайте **активные проверки** пассивным для лучшей масштабируемости и снижения нагрузки на `Pollers` сервера/прокси.
  * Поддерживайте версии Server, Proxy и Agents в актуальном и согласованном состоянии для использования последних улучшений производительности.
