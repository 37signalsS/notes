# Zabbix — поиск, устранение неисправностей и тюнинг производительности

> Данная заметка дополняет **[Лучшие практики настройки Zabbix](./zabbix_best_practices.md)**, фокусируясь на глубокой диагностике узких мест и аппаратной оптимизации инфраструктуры (Zabbix Server, Proxy и СУБД).

## Определения

* **Поиск и устранение неисправностей (Troubleshooting)** — процесс выявления корневых причин технических сбоев: задержки в очереди (Queue), переполнение кэшей или недоступность компонентов мониторинга.
* **Тюнинг производительности (Performance Tuning)** — конфигурационная оптимизация параметров демонов Zabbix и настроек базы данных для обработки сверхвысоких нагрузок.
* **NVPS (New Values Per Second)** — количество новых значений, записываемых системой в базу данных за секунду. Главный метрический показатель производительности мониторинга.

## Основные концепции: Анализ узких мест

### Типичные симптомы проблем

1. **Рост очереди (Zabbix Queue):** Показывает количество элементов, проверка которых запаздывает. Указывает либо на нехватку процессов сбора (Pollers), либо на таймауты сетевого оборудования.
2. **Разрывы на графиках (Gaps):** Свидетельствуют о потере данных. Возникают при переполнении `History Cache` или критических задержках записи в БД (`History Syncers` заняты на 100%).
3. **Zabbix Server is running: No:** Падение ядра системы из-за исчерпания оперативной памяти (OOM Killer) или потери соединения с базой данных.

### Мониторинг "Золотой четверки" кэшей

Для стабильной работы необходимо отслеживать утилизацию ключевых кэшей (шаблон `Zabbix server health`). Если утилизация стабильно превышает 80%, размер кэша в `zabbix_server.conf` необходимо увеличить.

* **History Cache (`HistoryCacheSize`):** Буфер для хранения входящих сырых данных перед их сбросом в БД. Переполнение означает, что дисковая подсистема БД не справляется с потоком записи (IOPS).
* **History Index Cache (`HistoryIndexCacheSize`):** Индексный кэш для History Cache. Обычно должен составлять 10-20% от его размера.
* **Value Cache (`ValueCacheSize`):** Кэш исторических данных, необходимых для вычисления триггеров. *Критически важен.* При его нехватке сервер начинает делать `SELECT` запросы напрямую в БД для каждого триггера, что моментально "убивает" производительность базы.
* **Configuration Cache (`CacheSize`):** Хранит в оперативной памяти данные о хостах, элементах данных и триггерах (размер базы конфигурации).

## Практические сценарии: Тюнинг Zabbix 7.0+

В Zabbix 7.0 произошли кардинальные архитектурные изменения, требующие новых подходов к оптимизации.

### 1. Тюнинг поллеров (Асинхронность)

Процессы опроса (`Agent`, `HTTP`, `SNMP`) стали **асинхронными**. Один процесс теперь может обрабатывать до 1000 параллельных проверок, не блокируясь в ожидании ответа.
* **Ошибка (Legacy-подход):** Устанавливать значения `StartPollers` в 500-1000. В версии 7.0 это приведет к перерасходу RAM.
* **Best Practice (7.0+):** Начинайте с небольших значений (например, `StartAgentPollers=10`). Отслеживайте метрику `Zabbix data gathering process busy %`. Увеличивайте количество процессов, только если загрузка стабильно держится выше 75%.

### 2. Оптимизация записи (Троттлинг)

Самый дешевый способ повысить NVPS — не писать мусор в базу.
* **Discard unchanged with heartbeat:** Обязательно применяйте этот шаг предобработки (Preprocessing) для статических метрик (версии ОС, статусы портов, инвентарные данные). Если порт "UP", Zabbix будет писать в базу только одно значение в час, а не каждую минуту.

### 3. Тюнинг распределенного мониторинга (Zabbix Proxy)

* **Proxy Memory Buffer:** В Zabbix 7.0 добавлен режим `ProxyBufferMode=memory`. При его активации прокси хранит собираемые данные в оперативной памяти, а не в локальной базе SQLite/MySQL. Это устраняет дисковый I/O на стороне прокси и значительно увеличивает пропускную способность.

### 4. Тюнинг базы данных (PostgreSQL + TimescaleDB)

Дисковая подсистема (IOPS) БД — главное узкое место любой инсталляции Zabbix.
1. **TimescaleDB:** Является стандартом для систем с высоким NVPS.
   * Убедитесь, что таблицы `history`, `trends` и `auditlog` (с 7.0) конвертированы в **hypertables**.
   * **Compression (Сжатие):** Включите компрессию данных старше 7 дней. Это снижает потребление места на 90% и радикально ускоряет чтение старых графиков.
2. **Оптимизация Housekeeper (Сборщик мусора):** При использовании TimescaleDB процесс удаления старых данных происходит не через `DELETE` (что грузит систему), а через "Drop Chunk" (моментальное удаление файлов с диска). Для этого в веб-интерфейсе в `Administration` → `Housekeeping` должна быть включена опция `Override item history period`.
3. **Оптимизация соединений (PgBouncer):** Если вы используете множество `History Syncers` или подключаете сотни Zabbix Proxy, используйте пулер соединений (PgBouncer) в режиме транзакций для снижения нагрузки на PostgreSQL. Подробнее о настройке Agent 2 с PgBouncer: **[Мониторинг PostgreSQL](./zabbix_postgresql_monitoring.md)**.

### Использование инструментов отладки (Runtime Control)

Вы можете повысить уровень логирования для конкретного процесса без перезапуска сервера:
```bash
# Включить отладку (Debug level 4) для всех History Syncers
zabbix_server -R log_level_increase=historysyncer

# Вернуть уровень логирования к стандартному
zabbix_server -R log_level_decrease=historysyncer
```
Встроенный **Debug Mode** в веб-интерфейсе (доступен в профиле пользователя) позволяет отследить, какие именно SQL-запросы вызывают задержки при отрисовке сложных дашбордов.
