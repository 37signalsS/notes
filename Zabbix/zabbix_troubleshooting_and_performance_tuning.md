# Zabbix — устранение неисправностей и тюнинг производительности

> Сведения актуальны для **Zabbix 7.0 LTS** и **Zabbix 8.0 LTS** (выпущена в сентябре 2026 г.). Основная долгосрочная ветка — 7.0 LTS (поддержка до 30 июня 2029). Текущая стандартная ветка — 8.0 LTS (поддержка до Q3 2029).

---

## Определения

* **Устранение неисправностей (Troubleshooting)** — процесс выявления корневых причин сбоев: задержки опроса, переполнение кэшей, недоступность компонентов инфраструктуры мониторинга.
* **Тюнинг производительности (Performance Tuning)** — конфигурационная оптимизация параметров демонов Zabbix и СУБД для обработки сверхвысоких нагрузок при минимальном расходовании ресурсов.
* **NVPS (New Values Per Second)** — количество новых значений, записываемых в базу данных за секунду. Главный метрический индикатор пропускной способности инфраструктуры мониторинга.
* **Очередь (Queue)** — список элементов данных, чей опрос запаздывает относительно запланированного интервала. Индикатор нехватки процессов сбора или завышенных таймаутов.
* **Золотая четверка кэшей (Golden Four)** — ключевые кэши Zabbix, утилизация которых определяет стабильность работы: Configuration Cache, History Cache, Value Cache, Trend Cache. В 7.0+ расширены Trend Function Cache и VMware Cache.
* **Busy % (Занятость процесса)** — относительное время, которое воркер проводит в состоянии выполнения работы. Контрольная точка для принятия решения об увеличении числа процессов (`Start*`).
* **Runtime Control** — механизм управления работающим Zabbix Server/Proxy без рестарта через команды `zabbix_server -R <command>` (повышение логирования, принудительная очистка, обновление кэша).
* **Асинхронный поллер (Async Poller)** — процесс сбора (Agent/HTTP/SNMP), обслуживающий до 1000 параллельных проверок, не блокируясь в ожидании ответа (Zabbix 7.0+).
* **tcache (Trend Function Cache)** — кэш рассчитанных результатов функций трендов (`trendavg`, `trendmax`). В Zabbix 8.0 добавлен внутренний элемент `zabbix[tcache,cache,<parameter>]` с параметром `paccessed`, показывающим долю записей, к которым было обращение за последние 24 часа.
* **HistoryProviders** — механизм хранения истории Zabbix 8.0, заменивший устаревший `HistoryStorageURL`. Поддерживает провайдеры: `sql` (основная СУБД), `elasticsearch` (текстовые данные), `clickhouse` (JSON и аналитические нагрузки). Устаревшие параметры `HistoryStorageDateIndex`, `HistoryStorageTypes`, `HistoryStorageURL` удалены в 8.0.
* **Proxy throttling (Ограничение прокси при восстановлении)** — в Zabbix 8.0 уточнена логика ограничения приёма данных от прокси при переполнении History Cache. При достижении порога сервер прекращает приём данных; при снижении утилизации до 60% сервер возобновляет обработку, но продолжает отклонять особо крупные пакеты (>10k записей) до поленного снятия давления.

## Основные концепции

### Архитектура устранения неисправностей и Four Golden Signals

Для SRE и DevOps инфраструктура мониторинга Zabbix рассматривается как любое другое критичное сервисное приложение. Классическая модель **Four Golden Signals** применяется к самому Zabbix Server и Proxy:

| **Signal** | **Zabbix-метрика / компонент** | **SRE-смысл** |
| :--- | :--- | :--- |
| **Latency** | `zabbix[process,<тип>,avg,busy]`, время вычисления триггеров | Задержка обработки запросов; рост говорит о нехватке ресурсов или блокировках |
| **Traffic** | NVPS (`zabbix[history]`, `zabbix[trends]`), скорость роста очереди | Объём операций; базовый показатель для Capacity Planning |
| **Errors** | Количество Unsupported items, сбои доставки оповещений, ошибки предобработки | Доля некорректных операций; ранний индикатор проблем конфигурации |
| **Saturation** | Утилизация кэшей (`zabbix[wcache,...]`), заполненность очереди, загрузка CPU/RAM процессов | Степень использования доступных ресурсов; переполнение приводит к каскадным сбоям |

**SLO / SLI для инфраструктуры Zabbix (примеры):**

* **SLI доступности:** доля времени, когда Zabbix Server доступен по порту 10051 и возвращает `zabbix[version]`. Цель — 99.9%.
* **SLI срочности алертинга:** 95% алертов должны быть отправлены в течение 60 секунд после перехода триггера в PROBLEM.
* **SLO утилизации кэшей:** утилизация History Cache и Value Cache не должна превышать 80% более 5 минут в месяц.

### SRE-контекст: Change Management, Capacity Planning, Post-mortem

* **Change Management:** любые изменения в конфигурации (`zabbix_server.conf`, шаблонах, триггерах) должны проходить через процедуры управления изменениями. Используйте **Runtime Control** для диагностики без рестарта и **Vault** для секретов (Zabbix 8.0 поддержирует AppRole HashiCorp Vault).
* **Capacity Planning:** основывается на NVPS. Правила: 1M NVPS ≈ 2–4 CPU / 4–8 GB RAM / SSD с 5k IOPS (PostgreSQL + TimescaleDB). Трендовые данные компрессии в TimescaleDB снижают требования к хранилищу на 90%.
* **Post-mortem:** при инцидентах Zabbix фиксируются в **Audit log** (с 7.0). Собирайте: графики `zabbix[queue,5m]`, `zabbix[process,,avg,busy]`, `zabbix[wcache,history,pused]`, логи `/var/log/zabbix/zabbix_server.log`, вывод `diaginfo`.

### Мониторинг «Золотой четверки» кэшей

Для стабильной работы необходимо отслеживать утилизацию ключевых кэшей. Если утилизация стабильно превышает **80%**, размер кэша в `zabbix_server.conf` (или `zabbix_proxy.conf`) необходимо увеличить. Контроль ведётся через шаблон `Template App Zabbix Server` (внутренние элементы `zabbix[process,...]`, `zabbix[wcache,...]`, в 8.0 — `zabbix[tcache,cache,...]`).

* **Configuration Cache (`CacheSize`):** хранит в оперативной памяти данные о хостах, элементах данных и триггерах. При переполнении снижается общая скорость сервера и замедляется применение изменений конфигурации. Управляется через `zabbix[cache,config,...]`.
* **History Cache (`HistoryCacheSize`):** буфер хранения входящих сырых данных перед сбросом в БД. Переполнение означает, что дисковая подсистема СУБД не справляется с потоком записи (IOPS) либо `History Syncers` заняты транзакциями. В 8.0 при переполнении сервер автоматически отклоняет крупные пакеты данных от прокси (>10k записей) до снижения давления. Элемент контроля — `zabbix[wcache,history,...]`.
* **Value Cache (`ValueCacheSize`):** кэх исторических данных для вычисления триггеров. *Критически важен.* При нехватке сервер выполняет прямые `SELECT` в базу для каждого вычисляемого триггера — это мгновенно снижает производительность СУБД и создаёт запаздывание по алертам. В 8.0 добавлен новый параметр `paccessed` для `zabbix[tcache,cache,...]`, показывающий актуальность записей кэша. Контроль — `zabbix[wcache,values,all]`.
* **History Index Cache (`HistoryIndexCacheSize`):** индексный кэш History Cache. Обычно составляет **10–20%** от его размера (примерно 100 байт на элемент истории).
* **Trend Cache (`TrendCacheSize`):** буфер записи агрегированных данных (trends) перед сбросом в БД.
* **Trend Function Cache (`TrendFunctionCacheSize`):** кэш рассчитанных результатов функций трендов. Критичен при большом количестве графиков за длинные периоды. В Zabbix 8.0 добавлен элемент `zabbix[tcache,cache,<parameter>]` с параметром `paccessed` (доля записей, к которым было обращение за последние 24 часа).

**Расширенный набор (7.0+):**

* **VMware Cache (`VMwareCacheSize`):** кэш данных VMware при активном VMware-мониторинге.

### Параметры кэшей: значения по умолчанию (Zabbix 7.0+)

| **Параметр (`zabbix_server.conf`)** | **По умолчанию** | **Диапазон** | **Замечания** |
| :--- | :--- | :--- | :--- |
| `CacheSize` | `32M` | 128K–64G | Кэш конфигурации |
| `CacheUpdateFrequency` | `10` | 1–3600 | Период обновления кэша; в 7.0 умолчание 60 → 10 с |
| `HistoryCacheSize` | `16M` | 128K–16G | История до записи в БД |
| `HistoryIndexCacheSize` | `4M` | 128K–16G | ~100 байт на элемент истории |
| `TrendCacheSize` | `4M` | 128K–16G | Буфер трендов |
| `TrendFunctionCacheSize` | `4M` | 128K–2G | Кэш функций трендов |
| `ValueCacheSize` | `8M` | 0, 128K–64G | Кэш для триггеров |
| `MaxHousekeeperDelete` | `5000` | 0–1000000 | Лимит удаляемых записей за цикл Housekeeper |
| `StartDBSyncers` | `4` | 1–100 | Число History Syncers |

> **Правило sizing кэшей:** начинайте со значений по умолчанию, контролируйте утилизацию через шаблон `Template App Zabbix Server` и увеличивайте только при стабильной утилизации выше **80%**. Увеличение «на глаз» без мониторинга ведёт к необоснованному расходу RAM.

## Практические сценарии

### Предварительные требования

* Zabbix Server 7.0 LTS или 8.0 LTS установлен и работает.
* СУБД (PostgreSQL / MySQL) инсталлирована, доступна и имеет достаточные IOPS.
* Подключен шаблон `Template App Zabbix Server` для самодиагностики.
* Права суперпользователя или группа `zabbix` для работы с конфигурационными файлами.

### 1. Тюнинг поллеров через асинхронность (Zabbix 7.0+)

В версии 7.0 процессы опроса **Zabbix Agent**, **HTTP-агента** и **SNMP** стали **асинхронными** — один воркер поддерживает до 1000 параллельных проверок, не блокируясь в ожидании ответа (параметр `MaxConcurrentChecksPerPoller`, по умолчанию 1000).

* **Ошибка (Legacy-подход):** устанавливать `StartPollers` в 500–1000. В 7.0/8.0 это ведёт к перерасходу оперативной памяти.
* **Best Practice (7.0+):**
  * Асинхронные воркеры включаются отдельными параметрами `StartAgentPollers`, `StartHTTPAgentPollers`, `StartSNMPPollers` (по умолчанию по **1**).
  * Для SNMP-проверок переведите элементы на новые ключи `get[]`/`walk[]` (`zabbix[process,snmp poller,avg,busy]`); в 8.0 кэширование SNMPv3 EngineID дополнительно снижает сетевой трафик.
  * Значение `StartPollers` для классических пассивных проверок можно снизить — они остаются только для не-асинхронных типов (ICMP, JMX, ODBC и прочих).
  * Начинайте с малых значений (например, `StartAgentPollers=10`) и отслеживайте метрику `zabbix[process,agent poller,avg,busy]`. Увеличивайте количество процессов, только если занятость стабильно держится выше 75–80%.

### 2. Оптимизация записи (третлинг и Discard unchanged)

Самый «дешёвый» способ повысить NVPS — не писать лишние значения в базу.

* **Step Discard unchanged with heartbeat:** шаг предобработки (Preprocessing), обязательный для статичных метрик (версии ОС, статусы портов, инвентарные данные). Если порт `UP`, Zabbix записывает одно значение в час, а не каждую минуту — экономия IOPS.
* Операция третлинга может быть только **одним** шагом в preprocessing (несколько throttling-шагов запрещено).
* **Отключайте лишние элементы и триггеры**, планируйте интервалы опроса: не все метрики нужны с частотой 1m.

### 3. Тюнинг распределённого мониторинга (Zabbix Proxy)

* **Proxy Memory Buffer:** в Zabbix 7.0 добавлен режим `ProxyBufferMode=memory`. При его активации прокси хранит собираемые данные в оперативной памяти, а не в локальной базе SQLite/MySQL. Это исключает дисковый I/O на стороне прокси и значительно увеличивает пропускную способность.
  * Ресурсы: выделите прокси достаточный объём RAM — начинайте с 512M–1G и следите за занятостью кэша.
  * Режим не допускает переполнения: при нехватке кэша прокси теряет данные — контролируйте заполнение и увеличивайте память.
  * В 8.0 уточнена логика ограничения приёма данных от прокси при переполнении History Cache: сервер отклоняет крупные пакеты (>10k записей) до снижения давления.
* **Прокси как концентратор пассивных проверок:** распределение нагрузки между прокси позволяет переносить хосты между ними, снижая пиковую нагрузку на сервер.
* **Proxy History Syncers:** для большого прокси увеличивайте `StartDBSyncers` для своевременной выгрузки данных на сервер.

### 4. Тюнинг базы данных (PostgreSQL + TimescaleDB)

Дисковая подсистема (IOPS) СУБД — главное узкое место любой инсталляции Zabbix.

1. **TimescaleDB:** стандарт для систем с высоким NVPS.
   * Убедитесь, что таблицы `history`, `trends` и `auditlog` (с 7.0) конвертированы в **hypertables**.
   * **Compression (Сжатие):** включите компрессию данных старше 7 дней. Это снижает потребление места до 90% и радикально ускоряет чтение старых графиков.
2. **Оптимизация Housekeeper:**
   * при использовании TimescaleDB удаление старых данных происходит через Drop Chunk (моментальное удаление файлов с диска). Для этого в веб-интерфейсе (`Administration → Housekeeping`) включена опция **Override item history period**.
   * Параметр `MaxHousekeeperDelete` (по умолчанию 5000) ограничивает число удалённых записей за один цикл; при отставании его увеличивают.
3. **Оптимизация соединений (PgBouncer):** при большом числе `History Syncers` или сотнях прокси используйте пул соединений в режиме транзакций. Подробнее: **[Мониторинг PostgreSQL в Zabbix](./zabbix_postgresql_monitoring.md)**.

### 5. Масштабирование хранилища истории (History Provider)

При росте NVPS разгружайте историю на специализированные хранилища:

* В **Zabbix 8.0** устаревший `HistoryStorageURL` заменён параметром **`HistoryProviders`** с форматом `<provider>[;<options>]`:
  * `sql` (по умолчанию) — история в основной СУБД;
  * `elasticsearch` — отдельное хранение текстовых типов (дашборды/поиск);
  * `clickhouse` — новинка 8.0: аналитический бэкенд для JSON и больших объёмов данных (не поддерживает тип `BIN`).
* Настройка позволяет разделить типы: LOG/TEXT → Elasticsearch, числовые → PostgreSQL, JSON → ClickHouse, снижая нагрузку записи на основной SQL-бэкенд.
* Для **Zabbix 7.0** это возможно через устаревший `HistoryStorageURL` (Elasticsearch).

> При подключении внешнего хранилища убедитесь, что `HistoryCacheSize` / `HistoryIndexCacheSize` рассчитаны с учётом извлечения данных из исторического провайдера (в 8.0 — опция `precache` в `HistoryProviders`).

### 6. Тюнинг веб-интерфейса (Frontend)

* **PHP-FPM:** установите `pm.max_children` исходя из доступной ОЗУ; включите **OPcache** (`opcache.enable=1`, `opcache.memory_consumption` ≥ 128M, `opcache.max_accelerated_files` ≥ 10000).
* **Снижение нагрузки на графики:** используйте функции трендов (`trendavg`/`trendmax`) в виджетах вместо чтения почасовой истории.
* **Индексы БД:** убедитесь, что рекомендованные индексы на таблицах `history_uint`, `history`, `trends`, `events`, `alerts`, `problem` на месте (см. схему БД Zabbix).

### 7. Пошаговый алгоритм диагностики узкого места

1. **Внутренний мониторинг:** подключите шаблон `Template App Zabbix Server` к серверу и прокси, смотрите:
   * очередь: `zabbix[queue,1m]`, `zabbix[queue,overall]`;
   * NVPS: `zabbix[history]`, `zabbix[trends]`;
   * занятость процессов: `zabbix[process,<тип>,avg,busy]`;
   * кэши: `zabbix[wcache,values,all]`, `zabbix[wcache,history,...]`, `zabbix[tcache,cache,paccessed]` (8.0+).
2. **`diaginfo`:** команды `zabbix_server -R diaginfo=<секция>` (например `historycache`/`preprocessing`/`valuecache`/`alerting`) пишут диагностику в лог.
3. **Запись в БД:** если `History Syncers` показывают `syncing history` на 100% — увеличьте `StartDBSyncers` (но аккуратно: больше соединений = больше нагрузка БД) и оптимизируйте IOPS СУБД.
4. **Логи и система:** повысьте Debug Level для конкретного процесса (см. раздел «Операции и команды»); проверьте `dmesg` на OOM-записи при падениях сервера.
5. **Debug Mode веб-интерфейса** (доступен в профиле пользователя) позволяет отследить, какие SQL-запросы вызывают задержки при отрисовке сложных дашбордов.

### 8. Использование Runtime Control для диагностики

Уровень логирования для конкретного процесса можно повышать/понижать **без перезапуска сервера**:

```bash
# Включить отладку (Debug level 4) для всех History Syncers
zabbix_server -R log_level_increase='history syncer'
# → Debug level 4 для всех history syncer

# Вернуть уровень логирования к стандартному
zabbix_server -R log_level_decrease='history syncer'
```

Дополнительные диагностические команды Runtime Control:

* `diaginfo=historycache` / `diaginfo=preprocessing` / `diaginfo=valuecache` / `diaginfo=alerting` — внутренняя диагностика секции в лог;
* `history_cache_clear=<target>` — принудительно очистить кэш истории для конкретного элемента (по ID) — добавлено в 7.4, полезно, когда элемент «застревает» и блокирует сброс;
* `config_cache_reload` — перезагрузить кэш конфигурации (после массовых изменений);
* `housekeeper_execute` — запустить Housekeeper вне расписания;
* `secrets_reload` — перезагрузить секреты из Vault (Zabbix 8.0 поддерживает HashiCorp Vault AppRole).

Полный синтаксис и список типов процессов — в **[Внутреннее устройство и процессы](./additional_info.md#управление-внутренними-процессами-runtime-control)**.

| `zabbix[tcache,cache,paccessed]` | Утилизация Trend Function Cache (8.0+) | `zabbix_get -s 127.0.0.1 -k "zabbix[tcache,cache,paccessed]"` |

### Команды Runtime Control

| Команда | Назначение | Пример |
| :--- | :--- | :--- |
| `log_level_increase='<тип>'` | Повысить уровень логирования | `zabbix_server -R log_level_increase='poller'` |
| `log_level_decrease='<тип>'` | Понизить уровень логирования | `zabbix_server -R log_level_decrease='poller'` |

| `housekeeper_execute` | Запустить Housekeeper | `zabbix_server -R housekeeper_execute` |
| `secrets_reload` | Перезагрузить секреты из Vault | `zabbix_server -R secrets_reload` |

| Секция | Назначение | Пример вывода в логе |

## Устранение неисправностей

### Типовые проблемы: причины и решения

| Проблема | Причины | Решение |
| :--- | :--- | :--- |
| Растёт Queue | Мало поллеров; высокие таймауты; `http poller` «зависает» | Увеличьте воркеры `Start*` и используйте асинхронные pollers 7.0+; проверьте `zabbix[queue,...]` |
| Разрывы (Gaps) | Переполнение History Cache (до 100% `History Syncers`), SLOW IOPS БД | Увеличьте `HistoryCacheSize`/`HistoryIndexCacheSize`, добавьте `StartDBSyncers`, включите компрессию TimescaleDB |
| `Zabbix server is running: No` | OOM Killer, потеря соединения с БД, диск полон | `dmesg|grep -i oom`, проверить подключение к БД, свободное место, увеличить RAM |
| Медленный Frontend | PHP-FPM/OPcache, нет индексов, HDD БД | Раздел «Тюнинг веб-интерфейса»; включите тренд-функции на графиках |
| Триггеры медленные | Нехватка Value Cache → прямой `SELECT` в БД | Увеличить `ValueCacheSize` и контролировать `zabbix[wcache,values,all]` |
| Unsupported items | Битые ключи, недоступность хостов | Ищите через `zabbix[host,,items_unsupported]`, отключайте некорректные |
| Медленные графики за большие периоды | Не хватает `TrendFunctionCacheSize`, нет компрессии | Увеличить кэш функций трендов, использовать `trendavg` в виджетах; в 8.0 контролируйте `paccessed` |
| Proxy теряет данные | `ProxyBufferMode=memory`, нехватка RAM | Увеличьте RAM на прокси, контролируйте заполнение кэша |
| Прокси отклоняет данные (8.0) | Переполнение History Cache на сервере, крупные пакеты >10k | Увеличьте `HistoryCacheSize`, разбейте пачки на части; в 8.0 сервер автоматически отклоняет крупные пакеты до снятия давления |

### Быстрая диагностика

```bash
# 1. Проверка очереди
zabbix_get -s 127.0.0.1 -k "zabbix[queue,5m]"
# → 0 — норма; >0 — проблемы с опросом

# 2. Проверка NVPS
zabbix_get -s 127.0.0.1 -k "zabbix[history]"
# → текущая скорость записи новых значений

# 3. Проверка утилизации кэшей
zabbix_get -s 127.0.0.1 -k "zabbix[wcache,history,pused]"
zabbix_get -s 127.0.0.1 -k "zabbix[wcache,values,all]"
zabbix_get -s 127.0.0.1 -k "zabbix[tcache,cache,paccessed]"
# → 0..100%; >80% — увеличивайте размер кэша

# 4. Проверка занятости процессов
zabbix_get -s 127.0.0.1 -k "zabbix[process,agent poller,avg,busy]"
# → 0..100%; >75% — масштабируйте воркеры

# 5. Проверка версии
zabbix_get -s 127.0.0.1 -k "zabbix[version]"
# → Zabbix Server 8.0.0 (revision ...)
```

## Лучшие практики

### Безопасность

* **Никогда не используйте суперпользователя** (`root`, `postgres`, `sa`, `SYSDBA`) для мониторинга. Создайте выделенного пользователя с минимально необходимыми правами (REPLICATION CLIENT, PROCESS, SHOW DATABASES, SELECT на системные схемы).
* **Ограничьте сетевой доступ:** пользователь мониторинга должен подключаться только с IP-адреса Zabbix Agent/Proxy.
* **Vault для секретов:** храните пароли и ключи в HashiCorp Vault. Zabbix 8.0 поддерживает AppRole и автоматическую перезагрузку секретов (`secrets_reload`).
* **Разделение обязанностей:** администратор БД не должен иметь прав на изменение конфигурации Zabbix, а администратор мониторинга — не должен иметь прав суперпользователя в СУБД.

### Производительность

* **Используйте Master/Dependent Items** для снижения нагрузки на БД. Один запрос вместо десятков.
* **Начинайте с значений по умолчанию** для всех параметров и контролируйте утилизацию через внутренние метрики. Увеличивайте только при стабильной загрузке выше 75–80%.
* **Используйте асинхронные поллеры** (Zabbix 7.0+) вместо увеличения количества синхронных процессов.
* **Мониторьте занятость поллеров:** `zabbix[process,<тип>,avg,busy]`. При устойчивой загрузке выше 75% — масштабируйте.
* **Применяйте третлинг** для статических метрик: `Discard unchanged with heartbeat` в предобработке.
* **Для ODBC всегда используйте Zabbix Proxy** — изоляция от зависаний драйвера.

### Надежность

* **Мониторинг мониторинга (Self-Monitoring):** подключите шаблон `Template App Zabbix Server` к самому Server и всем Proxy. Отслеживайте queue, NVPS, утилизацию кэшей.
* **Используйте Maintenance** для плановых работ на СУБД и инфраструктуре мониторинга.
* **Тестируйте изменения в staging** перед применением в production. Любое изменение конфигурации должно быть откатываемым.
* **Версионируйте конфигурацию в Git:** шаблоны, триггеры, параметры конфигурации — всё должно быть под контролем версий.
* **Регулярный аудит:** проверяйте Audit log (с 7.0) на предмет неавторизованных изменений.

### Масштабирование

* **Используйте Zabbix Proxy Groups** (Zabbix 8.0) для распределения сбора данных при большом числе целей мониторинга.
* **Разделите поллеры по типам:** ODBC-поллеры отдельно от обычных пассивных проверок.
* **При большом числе целей (>100)** используйте несколько Zabbix Proxy, каждый со своим набором проверок.
* **Для высоких NVPS (>100k)** используйте TimescaleDB с компрессией, несколько History Syncers, достаточный `HistoryCacheSize` (128M–512M).

### SRE: Post-mortem и Runbook Automation

При инцидентах инфраструктуры Zabbix используйте стандартизированный runbook:

1. **Сбор показателей:** `zabbix[queue,5m]`, `zabbix[process,,avg,busy]`, `zabbix[wcache,history,pused]`, `zabbix[wcache,values,all]`, `zabbix[history]`.
2. **Сбор логов:** `/var/log/zabbix/zabbix_server.log`, `dmesg | grep -i oom`, PostgreSQL logs.
3. **Диагностика:** `zabbix_server -R diaginfo=<секция>` (historycache, preprocessing, valuecache, alerting).
4. **Корректировка:** временное увеличение параметров кэшей или процессов, перезапуск проблемных процессов.
5. **Возврат к нормам:** после инцидента верните параметры к нормальным значениям и задокументируйте причину.
