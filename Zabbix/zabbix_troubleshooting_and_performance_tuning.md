# Zabbix — поиск, устранение неисправностей и тюнинг производительности

> Данная заметка дополняет **[Лучшие практики настройки Zabbix](./zabbix_best_practices.md)**, фокусируясь на глубокой диагностике узких мест и архитектурной оптимизации инфраструктуры (Zabbix Server, Proxy и СУБД). Сведения актуальны для Zabbix 7.0 LTS и 7.4; где это важно, отмечены изменения, ожидаемые в Zabbix 8.0.

## Определения

* **Поиск и устранение неисправностей (Troubleshooting)** — процесс выявления корневых причин технических сбоев: задержки в очереди (Queue), переполнение кэшей или недоступность компонентов мониторинга.
* **Тюнинг производительности (Performance Tuning)** — конфигурационная оптимизация параметров демонов Zabbix и настроек базы данных для обработки сверхвысоких нагрузок.
* **NVPS (New Values Per Second)** — количество новых значений, записываемых системой в базу данных за секунду. Главный метрический показатель производительности мониторинга.
* **Zabbix Queue (Очередь)** — список элементов данных, чей опрос запаздывает относительно запланированного интервала. Индикатор нехватки процессов сбора или завышенных таймаутов сетевых устройств.
* **Внутренние метрики (Internal checks)** — элементы данных с ключом `zabbix[...]`, которые Zabbix собирает о самом себе (загрузка процессов, заполнение кэшей, объем очередей). Используются шаблоном самодиагностики `Template App Zabbix Server`.
* **Busy % (Занятость процесса)** — относительное время нахождения воркера в состоянии выполнения работы; контрольная точка для решения об увеличении числа процессов (`Start*`).
* **Runtime Control** — механизм управления работающим Zabbix Server/Proxy без рестарта через команды `zabbix_server -R <command>` (повышение уровня логирования, принудительная очистка, обновление кэша конфигурации).
* **Асинхронный поллер (Async Poller)** — процесс сбора (Agent/HTTP/SNMP), обслуживающий до 1000 параллельных проверок, не блокируясь в ожидании ответа (Zabbix 7.0+).

## Основные концепции

### Типичные симптомы проблем

Ниже приведены классические проявления нехватки производительности и их вероятные корневые причины (полный каталог сценариев — в разделе «Типовые проблемы» ниже):

| **Симптом** | **Вероятная причина** |
| :--- | :--- |
| **Рост очереди (Zabbix Queue)** | Нехватка процессов сбора (Pollers), завышенные таймауты на сетевых устройствах, «зависшие» проверки веб-сценариев. |
| **Разрывы на графиках (Gaps)** | Переполнение History Cache, утилизация 100% `History Syncers`, недоступность БД во время всплеска записи. |
| **`Zabbix server is running: No`** | Падение ядра Zabbix Server из-за OOM Killer (нехватка RAM), потеря соединения с базой данных, исчерпание дискового пространства. |
| **Медленный веб-интерфейс (Frontend)** | Слабая конфигурация PHP-FPM/OPcache, медленные запросы к БД, отсутствие индексов на таблицах `history`/`trends`. |
| **Долгие вычисления триггеров** | Нехватка Value Cache → прямые `SELECT` в БД на каждый триггер (см. «Критические кэши»). |
| **Падение NVPS при росте хостов** | Дисковая подсистема СУБД (IOPS) не справляется; в TimescaleDB не включена компрессия, история не в совокупных таблицах. |

### Мониторинг «Золотой четверки» кэшей

Для стабильной работы необходимо отслеживать утилизацию ключевых кэшей. Если утилизация стабильно превышает **80%**, размер кэша в `zabbix_server.conf` (или `zabbix_proxy.conf`) необходимо увеличить. Контроль ведётся через шаблон `Template App Zabbix Server` (внутренние элементы `zabbix[process,...]`, `zabbix[wcache,...]`).

* **History Cache (`HistoryCacheSize`):** буфер хранения входящих сырых данных перед сбросом в БД. Переполнение означает, что дисковая подсистема СУБД не справляется с потоком записи (IOPS) либо `History Syncers` заняты транзакциями. **В 7.4** при переполнении сервер/прокси автоматически записывает диагностическую информацию о кэше; элемент данных контроля — `zabbix[wcache,history,...]`.
* **History Index Cache (`HistoryIndexCacheSize`):** индексный кэш History Cache. Обычно должен составлять **10–20%** от его размера (примерно 100 байт на элемент истории).
* **Value Cache (`ValueCacheSize`):** кэш исторических данных, необходимых для вычислений триггеров. *Критически важен.* При нехватке сервер выполняет прямые `SELECT` в базу для каждого вычисляемого триггера — это мгновенно «убивает» производительность СУБД и создаёт запаздывание по алертам. Контроль — `zabbix[wcache,values,all]` (количество попаданий и уровень заполнения). Отключение кэша (`0`) не рекомендуется.
* **Configuration Cache (`CacheSize`):** хранит в оперативной памяти данные о хостах, элементах данных и триггерах (объём базы конфигурации). При переполнении снижается общая скорость сервера и замедляется применение изменений конфигурации.

**Расширенный набор (7.0+)** помимо «золотой четверки» включает:

* **Trend Cache (`TrendCacheSize`)** — буфер записи агрегированных данных (trends) перед сбросом в БД.
* **Trend Function Cache (`TrendFunctionCacheSize`)** — кэш рассчитанных результатов функций трендов (`trendavg`, `trendmax`); критичен при большом количестве графиков за длинные периоды.
* **VMware Cache (`VMwareCacheSize`)** — кэш данных VMware при активном VMware-мониторинге.

### Параметры кэшей: значения по умолчанию (Zabbix 7.0+)

| **Параметр (`zabbix_server.conf`)** | **По умолчанию** | **Диапазон** | **Замечания** |
| :--- | :--- | :--- | :--- |
| `CacheSize` | `32M` | 128K–64G | Кэш конфигурации |
| `CacheUpdateFrequency` | `10` | 1–3600 | Период обновления кэша конфигурации; в 7.0 умолчание 60 → 10 с |
| `HistoryCacheSize` | `16M` | 128K–16G | История до записи в БД |
| `HistoryIndexCacheSize` | `4M` | 128K–16G | ~100 байт на элемент истории |
| `TrendCacheSize` | `4M` | 128K–16G | Буфер трендов |
| `TrendFunctionCacheSize` | `4M` | 128K–2G | Кэш функций трендов |
| `ValueCacheSize` | `8M` | 0, 128K–64G | Кэш для триггеров |
| `MaxHousekeeperDelete` | `5000` | 0–1000000 | Лимит удаляемых записей за цикл Housekeeper |
| `StartDBSyncers` | `4` | 1–100 | Число History Syncers |

> **Правило sizing кэшей:** начинайте со значений по умолчанию, контролируйте утилизацию через шаблон `Template App Zabbix Server` и увеличивайте только при стабильной утилизации выше **80%**. Увеличение «на глаз» без мониторинга ведёт к необоснованному расходу RAM.

## Практические сценарии

### 1. Тюнинг поллеров через асинхронность (Zabbix 7.0+)

В версии 7.0 процессы опроса **Zabbix Agent**, **HTTP-агента** и **SNMP** стали **асинхронными** — один воркер поддерживает до 1000 параллельных проверок, не блокируясь в ожидании ответа (параметр `MaxConcurrentChecksPerPoller`, по умолчанию 1000). Это кардинально изменило подход к выбору количества процессов.

* **Ошибка (Legacy-подход):** устанавливать значения `StartPollers` в 500–1000. В 7.0/7.4 это ведёт к перерасходу оперативной памяти при синхронных процессах, число которых теперь незначительно.
* **Best Practice (7.0+):**
  * Асинхронные воркеры включаются отдельными параметрами `StartAgentPollers`, `StartHTTPAgentPollers`, `StartSNMPPollers` (по умолчанию по **1**).
  * Для SNMP-проверок переведите элементы на новые ключи `get[]`/`walk[]` (`zabbix[process,snmp poller,avg,busy]`); старые элементы с прямыми OID продолжают работать на классическом `poller`, но миграция настоятельно рекомендуется.
  * Значение `StartPollers` для классических пассивных проверок можно снизить — они остаются только для не-асинхронных типов (ICMP, JMX, ODBC и прочих).
  * Начинайте с малых значений (например, `StartAgentPollers=10`) и отслеживайте метрику `zabbix[process,agent poller,avg,busy]`. Увеличивайте количество процессов, только если занятость стабильно держится выше 75–80%.

### 2. Оптимизация записи (троттлинг и Discard unchanged)

Самый «дешёвый» способ повысить NVPS — не писать лишние значения в базу.

* **Step Discard unchanged with heartbeat:** шаг предобработки (Preprocessing), обязательный для статичных метрик (версии ОС, статусы портов, инвентарные данные). Если порт `UP`, Zabbix записывает одно значение в час, а не каждую минуту — экономия IOPS.
* Операция тротлинга может быть только **одним** шагом в preprocessing (несколько throttling-шагов запрещено).
* **Отключайте лишние элементы и триггеры**, планируйте интервалы опроса: не все метрики нужны с частотой 1m.

### 3. Тюнинг распределённого мониторинга (Zabbix Proxy)

* **Proxy Memory Buffer:** в Zabbix 7.0 добавлен режим `ProxyBufferMode=memory`. При его активации прокси хранит собираемые данные в оперативной памяти, а не в локальной базе SQLite/MySQL. Это исключает дисковый I/O на стороне прокси и значительно увеличивает пропускную способность.
  * Ресурсы: выделите прокси достаточный объём RAM (данные, которые раньше жили в SQLite) — правила зависят от числа элементов и интервалов, начинайте с 512M–1G и следите за занятостью кэша.
  * Режим не допускает переполнения: при нехватке кэша прокси теряет данные — контролируйте заполнение и увеличивайте память.
* **Прокси как концентратор пассивных проверок:** распределение нагрузки между прокси позволяет переносить хосты между ними, снижая пиковую нагрузку на сервер; «сборка на прокси» переводит пассивные проверки на подконтрольный слоны сетевой доступности.
* **Proxy History Syncers:** для большого прокси увеличивайте `StartDBSyncers` для своевременной выгрузки данных на сервер.

### 4. Тюнинг базы данных (PostgreSQL + TimescaleDB)

Дисковая подсистема (IOPS) СУБД — главное узкое место любой инсталляции Zabbix.

1. **TimescaleDB:** стандарт для систем с высоким NVPS.
   * Убедитесь, что таблицы `history`, `trends` и `auditlog` (с 7.0) конвертированы в **hypertables**.
   * **Compression (Сжатие):** включите компрессию данных старше 7 дней. Это снижает потребление места до 90% и радикально ускоряет чтение старых графиков.
2. **Оптимизация Housekeeper:**
   * при использовании TimescaleDB удаление старых данных происходит не через `DELETE` (что грузит систему), а через Drop Chunk (моментальное удаление файлов с диска). Для этого в веб-интерфейсе (`Administration → Housekeeping`) включена опция **Override item history period**.
   * Параметр `MaxHousekeeperDelete` (по умолчанию 5000) ограничивает число удалённых записей за один цикл; при отставании его увеличивают.
3. **Оптимизация соединений (PgBouncer):** при большом числе `History Syncers` или сотнях прокси используйте пул соединений в режиме транзакций. Подробнее о настройке: **[Мониторинг PostgreSQL](./zabbix_postgresql_monitoring.md)**.

### 5. Масштабирование хранилища истории (History Provider)

При росте NVPS разгружайте историю на специализированные хранилища:

* В **Zabbix 8.0** устаревшая `HistoryStorageURL` заменена параметром **`HistoryProvider`** с форматом `<provider>[;<options>]`:
  * `sql` (по умолчанию) — история в основной СУБД;
  * `elasticsearch` — отдельное хранение текстовых типов (дашборды/поиск);
  * `clickhouse` — новинка 8.0: аналитический бэкенд для JSON и больших объёмов данных (не поддерживает тип `BIN`).
* Настройка позволяет разделить типы: LOG/TEXT → Elasticsearch, числовые → PostgreSQL, JSON → ClickHouse, снижая нагрузку записи на основной SQL-бэкенд.
* Для **Zabbix 7.0** это возможно через устаревший `HistoryStorageURL` (Elasticsearch).

> При подключении внешнего хранилища убедитесь, что `HistoryCacheSize` / `HistoryIndexCacheSize` рассчитаны с учётом извлечения данных из исторического провайдера (в 8.0 — опция `precache` в `HistoryProvider`).

### 6. Тюнинг веб-интерфейса (Frontend)

* **PHP-FPM:** установите `pm.max_children` исходя из доступной ОЗУ; включите **OPcache** (`opcache.enable=1`, `opcache.memory_consumption` ≥ 128M, `opcache.max_accelerated_files` ≥ 10000).
* **Снижение нагрузки на графики:** используйте функции трендов (`trendavg`/`trendmax`) в виджетах вместо чтения почасовой истории.
* **Индексы БД:** убедитесь, что рекомендованные индексы на таблицах `history_uint`, `history`, `trends`, `events`, `alerts`, `problem` на месте (см. схему БД Zabbix).

### 7. Пошаговый алгоритм диагностики узкого места

1. **Внутренний мониторинг:** подключите шаблон `Template App Zabbix Server` к серверу и прокси, смотрите:
   * очередь: `zabbix[queue,1m]`, `zabbix[queue,overall]`;
   * NVPS: `zabbix[history]`, `zabbix[trends]`;
   * занятость процессов: `zabbix[process,<тип>,avg,busy]`;
   * кэши: `zabbix[wcache,values,all]`, `zabbix[wcache,history,...]`.
2. **`diaginfo`:** команды `zabbix_server -R diaginfo=<секция>` (например `historycache`/`preprocessing`/`valuecache`) пишут диагностику в лог.
3. **Запись в БД:** если `History Syncers` показывают `syncing history` на 100% — увеличьте `StartDBSyncers` (но аккуратно: больше соединений = больше нагрузка БД) и оптимизируйте IOPS СУБД.
4. **Логи и система:** повысьте Debug Level для конкретного процесса (см. Runtime Control ниже); проверьте `dmesg` на OOM-записи при падениях сервера.
5. **Debug Mode веб-интерфейса** (доступен в профиле пользователя) позволяет отследить, какие SQL-запросы вызывают задержки при отрисовке сложных дашбордов.

### Использование Runtime Control для диагностики

Уровень логирования для конкретного процесса можно повышать/понижать **без перезапуска сервера**:

```bash
# Включить отладку (Debug level 4) для всех History Syncers
zabbix_server -R log_level_increase='history syncer'

# Вернуть уровень логирования к стандартному
zabbix_server -R log_level_decrease='history syncer'
```

Дополнительные диагностические команды Runtime Control:

* `diaginfo=historycache` / `diaginfo=preprocessing` / `diaginfo=valuecache` — внутренняя диагностика секции в лог;
* `history_cache_clear=<target>` — принудительно очистить кэш истории для конкретного элемента (по ID) — добавлено в 7.4, полезно, когда элемент «застревает» и блокирует сброс;
* `config_cache_reload` — перезагрузить кэш конфигурации (после массовых изменений);
* `housekeeper_execute` — запустить Housekeeper вне расписания;
* `secrets_reload` — перезагрузить секреты из Vault.

Полный синтаксис и список типов процессов — в **[Внутреннее устройство и процессы](./additional_info.md#управление-внутренними-процессами-runtime-control)**.

### Типовые проблемы: причины и решения

| Проблема | Причины | Решение |
| :--- | :--- | :--- |
| Растёт Queue | Мало поллеров; высокие таймауты; `http poller` «зависает» | Увеличьте воркеры `Start*` и используйте асинхронные pollers 7.0+; проверьте `zabbix[queue,...]` |
| Разрывы (Gaps) | Переполнение History Cache (до 100% `History Syners`), SLOW IOPS БД | Увеличьте `HistoryCacheSize`/`HistoryIndexCacheSize`, добавьте `StartDBSyncers`, включите компрессии TimescaleDB |
| `Zabbix server is running: No` | OOM Killer, потеря соединения с БД, диск полон | `dmesg|grep -i oom`, проверить подключение к БД, свободное место, увеличить RAM |
| Медленный Frontend | PHP-FPM/OPcache, нет индексов, HDD БД | Раздел «Тюнинг веб-интерфейса»; включите тренд-функции на графиках |
| Триггеры медленные | Нехватка Value Cache → прямой `SELECT` в БД | Увеличить `ValueCacheSize` и контролировать `zabbix[wcache,values,all]` |
| Unsupported items | Битые элементы/плохие ключи | Ищите через `zabbix[host,,items_unsupported]`, отключайте некорректные |
| Медленные графики за большие периоды | Не хватает `TrendFunctionCacheSize`, нет компре ации | Увеличить кэш функций трендов, использовать `trendavg` в виджетах |
