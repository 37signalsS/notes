# Поиск и устранение неисправностей и тюнинг производительности Zabbix

Эта заметка является дополнением к **[общему обзору Zabbix](./zabbix_overview.md)** и фокусируется на методах диагностики и оптимизации высоконагруженных инсталляций.

---

## 1. Типичные симптомы проблем с производительностью

-   **Большая очередь (Zabbix Queue)**: В разделе `Administration` -> `Queue` отображается количество элементов данных, которые Zabbix не смог опросить вовремя. Это главный индикатор проблем с производительностью сборщиков данных или недоступностью хостов.
-   **Разрывы на графиках (Gaps on Graphs)**: Прямое следствие большой очереди. Данные не поступают, и на графиках появляются пробелы.
-   **Медленная работа веб-интерфейса**: Часто связана с низкой производительностью базы данных или веб-сервера.
-   **Ложные срабатывания триггеров `nodata()`**: Возникают, когда данные не приходят в течение заданного времени.
-   **Ошибки в логах Zabbix Server/Proxy**: Необходимо регулярно проверять логи на наличие сообщений об ошибках (`error`).

## 2. Ключевые компоненты и их влияние на производительность

### 2.1. Кэши (Caches)

Zabbix использует несколько кэшей в оперативной памяти для ускорения работы. За их утилизацией необходимо следить с помощью шаблона `Zabbix server health`.

-   **`History Cache`**: Хранит собранные данные перед записью в базу данных. Если этот кэш переполняется, это указывает на проблемы со скоростью записи в БД.
-   **`History Index Cache`**: Кэш индексов для кэша истории.
-   **`Value Cache` (Кэш значений)**: Критически важный кэш, используемый для вычисления триггеров на основе сырых данных истории. Если кэша не хватает для вычисления сложного триггера (например, за большой период), Zabbix будет выполнять дорогостоящие запросы к БД.
-   **`Trend Cache`**: Хранит усредненные данные (тренды) перед записью в БД.
-   **`Configuration Cache`**: Хранит конфигурацию мониторинга (узлы, элементы, триггеры). Zabbix Server периодически обновляет этот кэш из БД. В Zabbix 7.0 это происходит инкрементально каждые 10 секунд.

### 2.2. Процессы (Processes)

Мониторинг утилизации процессов (`Zabbix busy ... process, %`) — основной способ выявления узких мест.

-   **Сборщики данных (Data Collectors):**
    -   **Pollers** (`zabbix_agent (passive)`, `simple check`): Синхронные процессы для пассивных и простых проверок.
    -   **Asynchronous Pollers** (Zabbix 7.0+): Для проверок `Zabbix agent`, `HTTP agent` и `SNMP agent`. Стали асинхронными, что значительно повышает производительность. Настраиваются через `MaxConcurrentChecksPerPoller`.
    -   **Trappers**: Принимают данные от активных агентов, прокси и утилиты `zabbix_sender`.
    -   **Unreachable Pollers**: Опрашивают недоступные узлы. Высокая утилизация этих процессов говорит о большом количестве "мертвых" хостов в системе, которые нужно либо исправлять, либо удалять.

-   **Обработка данных (Data Processing):**
    -   **History Syncers (DB Syncers)**: Один из самых важных процессов. Отвечает за запись исторических данных и трендов в БД, а также за обработку триггеров. Является основным потребителем ресурсов БД.
    -   **Preprocessing Workers**: Выполняют предварительную обработку данных. Эту нагрузку рекомендуется переносить на [Zabbix Proxy](./zabbix_overview.md#Компоненты).
    -   **LLD Workers**: Отвечают за выполнение правил низкоуровневого обнаружения (LLD).

-   **Другие процессы:**
    -   **Housekeeper**: Удаляет устаревшие данные (историю, события, тренды). При больших объемах данных его работа может вызывать серьезную нагрузку на БД. **Крайне рекомендуется использовать партиционирование таблиц**, чтобы избежать проблем с `Housekeeper`.
    -   **Escalators и Alerters**: Отвечают за выполнение действий (эскалаций) и отправку оповещений.

## 3. Инструменты для диагностики

1.  **Системные утилиты**: `top`, `htop`, `iostat`, `vmstat` для анализа загрузки CPU, I/O и памяти на сервере Zabbix и сервере БД.
2.  **Встроенные средства Zabbix**:
    -   **Шаблоны `Zabbix server health` и `Zabbix proxy health`**: Обязательны к использованию для мониторинга внутренних процессов и кэшей.
    -   **Дашборд очередей (`Administration -> Queue`)**: Показывает, какие типы проверок и какие прокси создают задержки.
    -   **Отчет `Reports -> Triggers top 100`**: Позволяет выявить самые "шумные" триггеры. Подробнее об этом в **[лучших практиках настройки Zabbix](./zabbix_best_practices.md)**.
    -   **Логи Zabbix**: Повышение уровня логирования для конкретного процесса (`zabbix_server -R log_level_increase="<process_type>"`).
3.  **Диагностика базы данных**:
    -   Включение `LogSlowQueries` в `zabbix_server.conf` для логирования медленных запросов к БД со стороны Zabbix.
    -   Использование специфичных для БД инструментов, например, `pg_stat_statements` для PostgreSQL.
4.  **Отладка веб-интерфейса**:
    -   Включение **Debug mode** для пользователя Zabbix. Это добавляет в футер страницы отладочную информацию с SQL-запросами и временем их выполнения.
    -   Если `SQL time` близок к `Total time`, проблема в базе данных.
    -   Если `SQL time` значительно меньше `Total time`, проблема на стороне веб-сервера (PHP-FPM, Apache/Nginx).

## 4. Практические рекомендации по тюнингу

-   **Оптимизация триггеров**:
    -   Для анализа данных за длительные периоды (недели, месяцы) используйте функции для трендов (`trendavg`, `trendmax`) вместо функций для истории (`avg`, `max`). Это значительно снижает нагрузку на `Value Cache` и БД.
    -   Для предотвращения "дребезжания" триггеров используйте гистерезис: задавайте разные условия для `Problem expression` и `OK event generation`. Например, проблема > 90%, а восстановление < 80%.

-   **Оптимизация базы данных**:
    -   Используйте **PostgreSQL с расширением TimescaleDB** или настройте **партиционирование** для исторических таблиц (`history*`, `trends*`). Это радикально ускоряет работу `Housekeeper` (он просто удаляет старые партиции вместо `DELETE` запросов) и улучшает общую производительность. См. [Мониторинг PostgreSQL в Zabbix](./zabbix_postgresql_monitoring.md).

-   **Препроцессинг**:
    -   Используйте опцию **"Discard unchanged"** в шагах предобработки, чтобы не хранить дублирующиеся значения и экономить место в БД.
    -   Переносите всю возможную предобработку на **[Zabbix Proxy](./zabbix_overview.md#Компоненты)**.

-   **Низкоуровневое обнаружение (LLD)**:
    -   Увеличивайте интервал обновления для правил LLD. Для большинства случаев (файловые системы, сетевые интерфейсы) достаточно одного раза в день.

-   **Архитектура**:
    -   Активно используйте **[Zabbix Proxy](./zabbix_overview.md#Компоненты)** для сбора данных. Zabbix Server должен заниматься обработкой данных, а не их сбором.
    -   Предпочитайте **[активные проверки](./zabbix_overview.md#Модель-сбора-данных-Push-модель)** пассивным. Это лучше масштабируется, снижает нагрузку на `Pollers` сервера/прокси и позволяет использовать авторегистрацию агентов.
    -   Поддерживайте версии Server, Proxy и Agents в актуальном и согласованном состоянии. Обновления часто содержат важные улучшения производительности.
