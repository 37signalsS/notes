# OpenLDAP в Kubernetes

> **Внимание!** OpenLDAP версии 2.4 достиг стадии **End of Life (EOL)** в феврале 2022 года. Использование бэкендов **HDB** и **BDB** более не рекомендуется и полностью удалено в версии 2.6. Современным стандартом является высокопроизводительный движок **MDB**.

## Определения

**OpenLDAP** — свободная реализация протокола LDAP (Lightweight Directory Access Protocol), используемая для организации централизованного хранилища информации о пользователях, группах и других сетевых ресурсах.

**MDB (Memory-Mapped Database)** — высокопроизводительный движок хранения (LMDB), используемый в OpenLDAP 2.4.44+ и являющийся единственным стандартом в 2.6+. Использует memory-mapped files для сверхбыстрого чтения.

**LDIF** (LDAP Data Interchange Format) — текстовый формат представления данных LDAP, используемый для экспорта, импорта и резервного копирования данных.

**olcSyncrepl** (Online Configuration Sync Replication) — механизм репликации OpenLDAP, позволяющий синхронизировать данные между серверами в режимах master-slave или multi-master.

**startTLS** — расширение протокола LDAP, которое позволяет установить защищенное (TLS) соединение поверх существующего незашифрованного соединения на порту 389.

**Operational Attributes** — служебные атрибуты, автоматически генерируемые LDAP-сервером (например, `creatorsName`, `createTimestamp`). Не могут быть изменены напрямую пользователями.

**entryUUID** — уникальный идентификатор записи, присваиваемый OpenLDAP-сервером. Специфичен для OpenLDAP.

**entryCSN** (Change Sequence Number) — временная метка модификации записи, используемая репликацией для разрешения конфликтов.

**memberOf** — операционный атрибут, автоматически генерируемый оверлеем `memberof`, указывающий группы, в которые входит пользователь.

## Базовые концепции

### Движок MDB в Kubernetes

Использование MDB (LMDB) в контейнеризированных средах имеет специфические особенности:

1.  **Memory-Mapped Files:** MDB отображает всю базу данных в адресное пространство памяти. Это означает, что `memory limits` в Kubernetes должны учитывать не только потребление процесса (`RSS`), но и размер файлов БД для эффективного кэширования ОС.
2.  **olcDbMaxSize:** В конфигурации MDB необходимо заранее указать максимальный размер базы. В Kubernetes это значение должно быть строго меньше (на 10-20%), чем размер `PersistentVolume`, чтобы избежать `DiskFull` ошибок.
3.  **Идемпотентность записей:** MDB обеспечивает ACID-транзакции, но крайне чувствителен к внезапным остановкам пода (SIGKILL). Рекомендуется использовать `terminationGracePeriodSeconds` не менее 30-60 секунд для корректного сброса буферов на диск.

### SSL/TLS и сетевая защита

#### LDAPS (LDAP поверх SSL/TLS)

- **Порт 636** — LDAPS (зашифрованное соединение сразу)
- **Порт 389** с **startTLS** — шифрование на обычном порту

#### Конфигурация OpenLDAP

Для включения SSL требуется три параметра в конфигурации:

1. **TLSCertificateFile** — сертификат LDAP-сервера
2. **TLSCertificateKeyFile** — ключ сертификата
3. **TLSCACertificateFile** — Certificate Authority (CA), подписавший сертификат

#### Пример Helm-чарта (values.yaml)

```yaml
ldap:
  ssl:
    enabled: true
  certManager:
    enabled: true  # Использовать cert-manager для генерации сертификатов
  # Имя issuer (не создаётся автоматически, требуется создать вручную)
  tls:
    issuer: "selfsign-ldap"
  # Параметры сертификата
  cert:
    dnsNames:
      - "ldap.example.com"
    ipAddresses:
      - "192.168.1.100"
```

**Важно:**

- При использовании cert-manager необходимо предварительно создать Issuer (self-signed или Let's Encrypt)
- В сертификате должны быть указаны DNS-имена и/или IP-адреса, по которым будут подключаться клиенты
- CA-сертификат необходимо добавить в доверенные на Linux-клиентах

#### Добавление CA в доверенные (Linux)

```bash
# Копирование CA-сертификата
cp ca.crt /usr/local/share/ca-certificates/

# Обновление хранилища сертификатов
update-ca-certificates
```

### Ручная контейнеризация как основа для автоматизации

Прежде чем рассматривать автоматизированное развертывание через Kubernetes, полезно понять процесс ручной контейнеризации OpenLDAP. Сложность этого процесса объясняет, почему Helm-чарт для OpenLDAP требует таких сложных решений, как `InitContainer` со скриптом `init.sh`.

Процесс ручного запуска OpenLDAP в контейнере (например, с помощью `nerdctl` или `docker`) включает следующие критические шаги, которые затем автоматизируются в Kubernetes:

1. **Подготовка хостовой системы**:
    - Создание на хосте директорий для персистентных данных, например `/data/openldap/data` (для базы) и `/data/openldap/run` (для сокета).
    - Установка правильных прав доступа к этим директориям (`chown 55:55`), чтобы UID и GID соответствовали пользователю `ldap` внутри контейнера.

2. **Внешняя конфигурация**:
    - Создание файла `DB_CONFIG` в директории с базой данных, обязательно включая параметр `set_flags DB_LOG_AUTOREMOVE` для автоматической очистки логов транзакций, чтобы избежать переполнения диска.
    - Подготовка основного конфигурационного файла `slapd.ldif` на хосте, который затем монтируется в контейнер. Это позволяет изменять конфигурацию без пересборки образа.

3. **Запуск контейнера со специфичными параметрами**:
    - При запуске через `nerdctl run` или `docker run` **критически важно** указать флаг `--ulimit nofile=<limit>`, так как OpenLDAP требует большого количества открытых файловых дескрипторов и завершится с неочевидной ошибкой при стандартных лимитах.
    - Монтирование директорий с данными и конфигурацией в соответствующие пути внутри контейнера (например, `/var/lib/openldap` и `/etc/openldap/slapd.ldif`).

4. **Двухфазная инициализация**:
    - **Оффлайн-фаза**: После запуска контейнера с `bash` внутри него выполняется `slapadd` для создания базы данных из `slapd.ldif`. Этот шаг требует, чтобы сервер `slapd` был остановлен.
    - **Онлайн-фаза**: Затем вручную запускается процесс `slapd`, и с помощью `ldapadd` в уже работающий сервер добавляются данные (DIT, пользователи) и конфигурация репликации (`olcSyncrepl`).

5. **Интеграция с `systemd`**:
    - Для управления контейнером как сервисом создается `systemd unit`.
    - В `ExecStart` используется команда `nerdctl run`, а в качестве `entrypoint` контейнера указывается `slapd` **без флага демонизации**. Это позволяет `systemd` отслеживать основной процесс и собирать его логи через стандартный вывод.

Все эти шаги — подготовка директорий, настройка прав, применение оффлайн-конфигурации, запуск временного сервера и применение онлайн-конфигурации — в точности повторяются в `InitContainer` в Kubernetes, но уже в автоматизированном режиме.

### Резервное копирование и восстановление

#### Экспорт через Apache Directory Studio

1.  Подключение к LDAP-серверу.
2.  Правый клик на root DN → **Export** → **Export to LDIF**.
3.  Указание Search Base (корень дерева).
4.  Выбор типа объектов (все или конкретный класс).
5.  Опция **Operational Attributes** (обязательно для полного бэкапа, включая `entryUUID` и `entryCSN`).
6.  Указание пути сохранения .ldif файла.

**Особенности LDIF с русскими символами:**
Данные на кириллице кодируются в BASE64. Рекомендуется использовать UID в качестве RDN (Relative Distinguished Name) для читаемости резервных копий и избежания проблем с кодировкой в путях.

#### Восстановление данных

**Через Apache Directory Studio (Онлайн):**
1.  Подключение к LDAP-серверу → **Import** → **LDIF Import**.
2.  **Update Existing Entries** — отключено (защита от перезаписи).
3.  **Continue on Error** — включено (пропуск существующих записей).

> **ВНИМАНИЕ!** При наличии в LDIF операционных атрибутов (`entryUUID`, `entryCSN`) онлайн-восстановление через GUI или `ldapadd` невозможно (ошибка `Entry UUID: no user modification allowed`).

**Решение для полного восстановления:**
Восстановление выполняется при **остановленном LDAP-сервере** с использованием утилиты `slapadd`. В Kubernetes это реализуется через `InitContainer` или временный под с доступом к PVC.

## Практические сценарии

### Helm-чарт для OpenLDAP в Kubernetes

#### Обоснование архитектуры

Выбор архитектуры для OpenLDAP в Kubernetes продиктован двумя ключевыми требованиями: **высокая доступность** и **особенности хранения данных**.


1. **Проблема высокой доступности**: OpenLDAP часто является ядром системы аутентификации и авторизации. Его простой недопустим. Развертывание в виде одного пода не обеспечивает надежности: в случае падения узла Kubernetes может потребоваться до нескольких минут на перезапуск пода на другой ноде, что приведет к отказу всей системы.
2. **Проблема хранения данных**:
    - Бэкенд базы данных OpenLDAP (как MDB, так и HDB) является **однопользовательским (single-writer)**. Два процесса `slapd` не могут одновременно работать с одними и теми же файлами базы данных.
    - Это исключает использование `PersistentVolume` с режимом доступа `ReadWriteMany` (RWX), который позволил бы нескольким подам использовать общее хранилище.
    - Следовательно, каждый под OpenLDAP должен иметь свой собственный, эксклюзивный том с режимом `ReadWriteOnce` (RWO).

**Решение**: Единственной жизнеспособной архитектурой является **кластер multi-master**, развернутый с помощью **StatefulSet**.

- **StatefulSet** обеспечивает каждому поду стабильный сетевой идентификатор (например, `ldap-0`, `ldap-1`) и привязывает к нему уникальный `PersistentVolumeClaim` (RWO).
- **Режим Multi-master** с использованием `olcSyncrepl` обеспечивает синхронизацию данных между подами, каждый из которых работает со своей копией базы данных.

Такая архитектура гарантирует, что при выходе из строя одного пода, остальные продолжат обслуживать запросы, обеспечивая высокую доступность.

#### Детальный разбор `values.yaml`

Этот раздел описывает ключевые параметры конфигурации Helm-чарта.

##### Глобальные параметры

- `image`: Позволяет выбрать образ для OpenLDAP 2.4 (с поддержкой HDB/MDB) или 2.6 (только MDB).
- `image.pullPolicy`: Рекомендуется `IfNotPresent` для стабильности в production, но `Always` удобен при разработке и частой смене тегов.
- `securityContext`: **Критически важный параметр.** Процесс `slapd` должен запускаться от имени непривилегированного пользователя.
  - Для версии 2.4: `runAsUser: 55`, `runAsGroup: 55`.
  - Для версии 2.6: `runAsUser: 100`, `runAsGroup: 101`.
- `service`: Определяет тип сервиса для доступа к LDAP (`ClusterIP`, `NodePort`, `LoadBalancer`). `annotations` можно использовать для конфигурации `MetalLB`, например, для назначения статического IP-адреса.
- `podAntiAffinity`: Настоятельно рекомендуется для production, чтобы распределить поды по разным узлам и избежать единой точки отказа. По умолчанию отключено для удобства в однонодовых dev-кластерах.

##### livenessProbe и readinessProbe

Пробы реализованы через исполняемый скрипт, который выполняет `ldapsearch` к корневому DIT. Это надежный способ проверить, что `slapd` не просто запущен, но и отвечает на запросы.

##### logging

- `logging.debugLevel`: Управляет уровнем детализации логов, которые `slapd` пишет в стандартный вывод. Установка значения (например, `256`) заставляет `slapd` работать в foreground-режиме, что является стандартом для контейнеризированных приложений и позволяет Kubernetes собирать логи. `256` — хороший выбор для production, включающий статистику по операциям и соединениям.

##### Параметры ldap: Конфигурация OpenLDAP

Этот блок содержит основные параметры самого `slapd`.

- `ldap.backend`: Выбор между `hdb` и `mdb`. Для версий 2.6+ следует использовать только `mdb`.
- `ldap.olcDbMaxSize`: Обязательный параметр для бэкенда `mdb`, который заранее определяет максимальный размер базы данных. В Kubernetes этот параметр должен быть согласован с объемом `PersistentVolume`.
- `ldap.olcSuffix`, `ldap.olcRootDn`, `ldap.olcRootPw`: Стандартные параметры для определения дерева (DIT) и учетных данных администратора. Пароль рекомендуется задавать через `existingSecret`.

- **`ldap.olcSizeLimit`**:
    > **ВНИМАНИЕ!** Это один из самых критических параметров. По умолчанию его значение `500`. Этот лимит влияет не только на максимальное количество записей, возвращаемых `ldapsearch`, но и на **механизм репликации**. Процесс `syncrepl` использует внутренний поиск для получения данных с другого мастера. Если количество записей в LDAP превышает `olcSizeLimit`, репликация **перестанет работать**, так как мастер-получатель не сможет выгрузить все данные с мастера-источника. Это приведет к рассинхронизации кластера. **Всегда** устанавливайте это значение значительно выше ожидаемого количества записей.

- `ldap.overlays`: Позволяет включать/отключать оверлеи, такие как `memberOf` и `refint`. `syncprov` включен по умолчанию для multi-master.

- `ldap.schemas`: Определяет, какие стандартные схемы загружать. **Порядок важен**, так как схемы имеют зависимости (например, `inetorgperson` зависит от `core`).
- `ldap.customSchemas`: Позволяет загружать кастомные схемы из внешнего S3-хранилища. Это сделано для обхода ограничения на размер `ConfigMap`. В production рекомендуется расширять стандартные схемы, а не модифицировать их.

- `ldap.dbConfig`: Секция для содержимого файла `DB_CONFIG`, используемого **только для HDB**.
    > **ВАЖНО:** Обязательно должен содержать флаг `set_flags DB_LOG_AUTOREMOVE`. Без него логи транзакций быстро заполнят диск.

- `ldap.olcAccess`: Позволяет определить ACL (Access Control Lists) прямо в `values.yaml`.

##### Блок multiMaster

Секция содержит параметры для конфигурации `olcSyncrepl`, отвечающей за репликацию между подами.

##### Бэкап и восстановление (backup и restore)

- В чарт встроен механизм бэкапа и восстановления с использованием S3-совместимого хранилища.
- **Восстановление (`restore`)**: Происходит при старте пода, если `restore.enabled=true`. Требует ручного удаления `StatefulSet` и `PVC` перед запуском.
- **Бэкап (`backup`)**: Может выполняться по расписанию (`schedule`) с помощью `CronJob`.

#### Безопасность и ресурсы

##### Сетевые политики (NetworkPolicy)

OpenLDAP является критическим компонентом инфраструктуры. Для защиты рекомендуется ограничить доступ к портам 389/636 только доверенным сегментам сети (например, подам с приложениями или IP-адресам офиса):

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: ldap-allow-trusted
spec:
  podSelector:
    matchLabels:
      app: openldap
  ingress:
  - from:
    - podSelector:
        matchLabels:
          access: ldap-client
    ports:
    - protocol: TCP
      port: 389
    - protocol: TCP
      port: 636
```

##### Лимиты ресурсов (Resources)

При использовании бэкенда **MDB** важно понимать, что он активно использует memory-mapped files. Хотя это не увеличивает потребление `RSS` (Resident Set Size) напрямую пропорционально размеру БД, рекомендуется устанавливать лимиты памяти с запасом для кеширования ОС:

```yaml
resources:
  requests:
    cpu: 500m
    memory: 1Gi
  limits:
    cpu: 1000m
    memory: 2Gi
```

##### Проблемы и ограничения чарта

1. **Rollout реплик**: При изменении `replicas` в `StatefulSet` новые поды не добавляются автоматически в конфигурацию `olcSyncrepl` на старых подах. Требуется ручное вмешательство.
2. **Prometheus Operator**: Сбор метрик настроен через стандартные аннотации (`scrape`). Поддержка `ServiceMonitor` для Prometheus Operator не встроена и требует доработки чарта.

### 2. Мониторинг OpenLDAP в Kubernetes

Для глубокого мониторинга рекомендуется использовать `openldap_exporter`.

#### Конфигурация через аннотации
```yaml
# values.yaml
monitoring:
  enabled: true
  exporter:
    image: bitnami/openldap-exporter:2.2.1
    port: 9111
  annotations:
    prometheus.io/scrape: "true"
    prometheus.io/port: "9111"
    prometheus.io/path: "/metrics"
```

#### Ключевые метрики для алертинга
- `openldap_up` — доступность сервера (0/1).
- `openldap_monitored_operations_total` — интенсивность операций (Bind, Search, Modify).
- `openldap_threads_max` vs `openldap_threads_active` — насыщение пула потоков.
- `openldap_monitored_entries` — общее количество записей в дереве.

### 3. Миграция с OpenLDAP 2.4 на 2.6 (HDB -> MDB)

Так как версия 2.6 полностью удалила поддержку бэкендов HDB/BDB, миграция «на месте» (in-place) невозможна.

**Алгоритм миграции:**
1.  **Создание дампа (2.4):** Экспорт данных в LDIF из работающего пода:
    ```bash
    kubectl exec ldap-0 -- slapcat -b "dc=example,dc=com" > dump.ldif
    ```
2.  **Обновление инфраструктуры:** Удаление старого StatefulSet и PVC (если требуется смена размера или типа хранилища).
3.  **Развертывание 2.6:** Установка `image.tag: 2.6.x` и `ldap.backend: mdb`.
4.  **Импорт данных:** Восстановление через `slapadd` в `InitContainer` или временный под.

### 4. Внешний доступ через Gateway API (TCPRoute)

LDAP требует L4-балансировки. Современный способ настройки через Gateway API:

```yaml
apiVersion: gateway.networking.k8s.io/v1alpha2
kind: TCPRoute
metadata:
  name: ldap-external
spec:
  parentRefs:
  - name: my-gateway
    sectionName: ldaps
  rules:
  - backendRefs:
    - name: openldap-service
      port: 636
```

### Детальный разбор реализации Helm-чарта для Multi-Master

Этот раздел подробно описывает внутреннее устройство кастомного Helm-чарта для развертывания отказоустойчивого multi-master кластера OpenLDAP.

#### Архитектура Helm-чарта

- **StatefulSet**: Управляет подами OpenLDAP, обеспечивая стабильные сетевые идентификаторы.
- **InitContainer**: Ключевой компонент, запускающий сложный `init.sh` скрипт для первоначальной, идемпотентной настройки.
- **Основной контейнер**: Запускает уже сконфигурированный процесс `slapd`.
- **ConfigMap**: Хранит конфигурационные файлы (`slapd.ldif`, `db.config`) и исполняемые скрипты (`init.sh`, `probe.sh`).
- **Secrets**: Используются для безопасного хранения паролей администратора и пользователя репликации.
- **Headless Service**: Обеспечивает DNS-записи для каждого пода, что критически важно для настройки репликации.

#### Логика инициализационного скрипта (`init.sh`)

Скрипт выполняется в `InitContainer` и решает сложную задачу первоначальной настройки, которая из-за особенностей OpenLDAP разделена на оффлайн и онлайн этапы.

**Идемпотентность**:

- Скрипт использует **файл-флаг** (например, `/data/init.flag`).
- При старте пода он проверяет наличие этого файла. Если файл существует, основная логика инициализации пропускается. Это предотвращает повторную конфигурацию при перезапусках пода.

**Последовательность операций при первом запуске:**

1. **Подготовка директорий**: Очищаются и создаются необходимые директории для баз данных, конфигурации (`slapd.d`), кастомных схем и runtime-файлов (pid, socket).
2. **Внедрение пароля администратора (Оффлайн)**:
    - `slapd.ldif` монтируется из `ConfigMap` как read-only.
    - Скрипт генерирует хэш пароля администратора с помощью `slap-passwd`.
    - С помощью `sed` создается временная копия `slapd.ldif`, в которую подставляется сгенерированный хэш. Прямое изменение невозможно из-за прав доступа и природы `ConfigMap`.
3. **Загрузка кастомных схем (Опционально, Оффлайн)**: Если включено, схемы загружаются из S3-хранилища с помощью `curl` в специально подготовленную директорию.
4. **Создание `cn=config` (Оффлайн)**:
    - Выполняется команда `slapadd` с подготовленным LDIF-файлом.
    - Это создает базовую конфигурационную базу данных (`cn=config`) на диске.
5. **Временный запуск `slapd`**:
    - Внутри `InitContainer` запускается фоновый процесс `slapd`.
    - Скрипт ожидает его полного запуска, опрашивая `cn=monitor` через `ldapsearch`.
6. **Инициализация DIT (Онлайн)**:
    - Создается LDIF-файл для корневого элемента дерева (например, `dc=mydomain,dc=com`).
    - С помощью `ldapadd` этот элемент добавляется в уже запущенный `slapd`. Этот шаг пропускается, если выполняется восстановление из бэкапа.
7. **Настройка репликации (Онлайн)**:
    - **Создание пользователя репликации**: `ldapadd` добавляет пользователя `cn=repl-user` с паролем из секрета.
    - **Конфигурация `olcSyncrepl`**:
        - Готовится LDIF-файл для `ldapmodify`.
        - Динамически генерируются `olcSyncrepl` записи для каждого пира в кластере. Имена пиров вычисляются на основе имени пода StatefulSet (e.g., `test-openldap-0`, `test-openldap-1`).
        - Конфигурация репликации применяется к `cn=config` с помощью `ldapmodify`. Этот онлайн-шаг необходим, так как конфигурация зависит от динамического количества реплик.
8. **Остановка временного `slapd`**: Процесс `slapd` останавливается.
9. **Создание флага**: Создается файл `/data/init.flag`, сигнализирующий об успешном завершении инициализации.

После завершения работы `InitContainer` запускается основной контейнер, который просто стартует `slapd`, используя уже полностью готовую конфигурацию.

#### Процесс отладки

Для отладки сложной логики `init.sh` применяется следующий подход:

1. Временно изменить команду запуска `InitContainer` на `sleep infinity`.
2. Запустить `helm install/upgrade`. Под останется в состоянии `Init:1/2`.
3. Выполнить `kubectl exec -it <pod-name> -c init -- /bin/bash`.
4. Внутри контейнера можно вручную по шагам запускать скрипт `init.sh`, анализируя вывод и исправляя ошибки.
