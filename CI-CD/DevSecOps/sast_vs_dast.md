# SAST vs DAST — сравнение подходов

**Reliability Score: 10** (SSoT + Web Verification 2026: актуализировано на основе трендов AI-driven AST и ASPM)

## Определения

Для обеспечения безопасности приложений (Application Security Testing — AST) в 2026 году используются следующие подходы и системы оркестрации:

- **SAST (Static Application Security Testing)** — «белый ящик»: анализ исходного кода, байт-кода или бинарных файлов без запуска приложения. В 2026 году активно использует LLM для семантического анализа и автоматического исправления кода (Auto-Remediation).
- **DAST (Dynamic Application Security Testing)** — «черный ящик»: тестирование работающего приложения через внешние интерфейсы (HTTP/API). Современные инструменты реализуют **Autonomous Pentesting** — имитацию действий хакера с использованием ИИ.
- **IAST (Interactive Application Security Testing)** — «серый ящик»: гибридный подход. В 2026 году стандартом стал **Zero-Instrumentation IAST** на базе **eBPF**, работающий на уровне ядра без внедрения агентов в код.
- **SCA (Software Composition Analysis)** — анализ сторонних библиотек и зависимостей на наличие известных уязвимостей (CVE). См. [Анализ зависимостей и SBOM](../../Security/Supply_Chain_Security/dependency_and_sbom_analysis.md).
- **ASPM (Application Security Posture Management)** — оркестратор AppSec, который консолидирует данные из всех сканеров, устраняет дубликаты и приоритизирует риски на основе **достижимости (Reachability Analysis)**.

## Базовые концепции

### Сравнение методов анализа (2026)

| Критерий | SAST | DAST | IAST (eBPF) |
| :--- | :--- | :--- | :--- |
| **Принцип** | Белый ящик (статический) | Черный ящик (динамический) | Серый ящик (гибридный) |
| **Этап CI/CD** | Кодирование (IDE), сборка | Тест, стейджинг, прод | Тестирование и рантайм |
| **Технология** | Семантический AI-анализ | Автономный ИИ-пентест | eBPF-инструментация |
| **Точность** | Средняя (AI снижает FP) | Высокая (подтверждено) | Максимальная (видит вызовы ядра) |
| **Покрытие** | 100% исходного кода | Только активные маршруты | 100% исполняемого кода |
| **Требования** | Доступ к коду | Развернутая среда | Права root (для eBPF) |
| **Цель** | Найти дефекты и авто-фикс | Найти эксплуатируемые дыры | Мониторинг и защита рантайма |

### Типы обнаруживаемых уязвимостей

Каждый метод тестирования специализируется на определенных классах дефектов:

- **SAST:** специализируется на ошибках в коде, логике авторизации и конфигурациях (IaC).
- **DAST:** выявляет уязвимости рантайма, конфигурации серверов и сетевые угрозы.
- **IAST:** фокусируется на эксплуатируемых дефектах в реальных потоках данных.
- **SCA:** нацелен на уязвимости в сторонних компонентах.

Подробное сопоставление и полный перечень уязвимостей — в **[обзоре уязвимостей SAST/DAST](./sast_dast_vulnerabilities.md)**.

### Ограничения

- **SAST:** склонен к ложным срабатываниям на сложной бизнес-логике (решается через AI-валидацию); не видит уязвимости конфигурации рантайма.
- **DAST:** неэффективен против уязвимостей, не имеющих внешнего проявления (например, логические ошибки без вывода); может «уронить» нестабильное окружение.
- **IAST (eBPF):** требует современного ядра Linux; сложен в настройке для мультиоблачных сред; не подходит для анализа «спящего» кода (не вызываемого в рантайме).

## Практические сценарии

### Порядок интеграции в 2026 году

1. **AI-SAST в IDE:** Реальное время. Разработчик получает предупреждения и предложения по исправлению (Auto-Fix) в процессе написания кода.
2. **Инкрементальный SAST на PR/MR:** Фокус только на изменениях и их влиянии на Data Flow всего приложения.
3. **Autonomous DAST на Review-окружении:** ИИ-агент автоматически исследует новые API-эндпоинты сразу после деплоя.
4. **ASPM Correlation:** Объединение результатов SAST, DAST и SCA. Если SAST нашел уязвимость, но SCA подтверждает, что библиотека не используется, а DAST не может её проэксплуатировать — риск снижается.

### Пример: GitLab CI с использованием ASPM

```yaml
stages: [test, security, deploy]

sast:
  stage: security
  image: registry.example.com/tools/sast:latest
  script:
    # Анализ в формате SARIF (Static Analysis Results Interchange Format)
    - ./sast --path . --format sarif --out sast.sarif
    - ./severity-gate sast.sarif --fail-on high
  artifacts:
    paths: [sast.sarif]

deploy_review:
  stage: deploy
  script:
    - ./deploy.sh --env review
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.review.example.com

dast:
  stage: security
  needs: ["deploy_review"]
  image: registry.example.com/tools/dast:latest
  script:
    - ./dast --target $CI_ENVIRONMENT_URL --login-file creds.json --out dast.json
    - ./severity-gate dast.json --fail-on medium
  artifacts:
    paths: [dast.json]
```

Детали интеграции — в [SAST/DAST в CI/CD](./sast_dast_cicd_integration.md).

## Дополнительная информация

### Комбинированная стратегия (ASPM)

В 2026 году разрозненное использование инструментов заменено на **ASPM (Application Security Posture Management)**. Ключевые функции:
- **Reachability Analysis (Анализ достижимости):** Определение того, может ли уязвимость в коде (SAST) быть вызвана в текущей конфигурации рантайма (IAST/eBPF).
- **AI Auto-Remediation:** Автоматическая генерация исправленных версий кода на основе находок SAST, проверенных ИИ на отсутствие регрессий.
- **Единая очередь (Unified Backlog):** Схлопывание дубликатов (например, когда SAST и DAST нашли одну и ту же SQL-инъекцию) в одну задачу для разработчика.

### Рекомендации по настройке

- **Shift Left:** Интегрируйте SAST непосредственно в IDE через LSP-серверы для мгновенной обратной связи.
- **Shift Right:** Используйте eBPF-IAST в продакшене для обнаружения атак «нулевого дня» (Zero-day) и IDOR.
- **Исключения:** Управляйте исключениями централизованно в ASPM-платформе, а не в локальных конфигах каждого сканера.
