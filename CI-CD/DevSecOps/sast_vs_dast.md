# Сравнение SAST и DAST подходов

## Определения

**SAST (Static Application Security Testing)** и **DAST (Dynamic Application Security Testing)** — это два взаимодополняющих подхода к тестированию безопасности приложений.

- **SAST** работает как «белый ящик», анализируя исходный код или байт-код до запуска приложения.
- **DAST** работает как «черный ящик», тестируя работающее приложение извне через его интерфейсы.

Корректное понимание их различий и совместное использование — основа эффективной практики DevSecOps.

## Основные концепции

### Сравнение по ключевым критериям

| Критерий | SAST | DAST |
| :--- | :--- | :--- |
| **Этап** | Ранние стадии (коммит/PR, сборка) | После развертывания (тест, стейджинг) |
| **Контекст** | Статический анализ кода | Анализ в рантайме, реальная конфигурация |
| **Скорость** | Быстро на малых изменениях; полный скан может быть долгим | Средне/долго; зависит от сложности приложения |
| **Ложные срабатывания** | Часты без настройки; требуют анализа и фильтрации | Меньше, но возможны из-за среды или аутентификации |
| **Покрытие кода** | 100% кодовой базы, включая неиспользуемый код | Только доступные извне маршруты и состояния |
| **Требования** | Доступ к исходному коду, правила/политики | Развернутая среда, тестовые учетные данные |
| **Цель** | Найти дефекты в коде до выполнения | Подтвердить возможность эксплуатации уязвимости |

### Типичные находки

- **SAST:** SQL-инъекции в коде, небезопасная (де)сериализация, ошибки в логике авторизации, использование слабых криптоалгоритмов, секреты в коде.
- **DAST:** Межсайтовый скриптинг (XSS), ошибки конфигурации сервера (неверные заголовки, листинг директорий), уязвимости сессий, CSRF.

## Практические сценарии

### Интеграция в CI/CD
Рациональный порядок интеграции:
1.  **SAST** на этапе Pull/Merge Request для быстрой обратной связи по измененному коду.
2.  **DAST** после развертывания на временном или тестовом окружении.

### Пример интеграции в GitLab CI
```yaml
stages: [test, security, deploy]

sast:
  stage: security
  image: registry.example.com/tools/sast:latest
  script:
    - ./sast --path . --format sarif --out sast.sarif
    - ./severity-gate sast.sarif --fail-on high
  artifacts:
    paths: [sast.sarif]

deploy_review:
  stage: deploy
  script:
    - ./deploy.sh --env review
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.review.example.com

dast:
  stage: security
  needs: ["deploy_review"]
  image: registry.example.com/tools/dast:latest
  script:
    - ./dast --target $CI_ENVIRONMENT_URL --login-file creds.json --out dast.json
    - ./severity-gate dast.json --fail-on medium
  artifacts:
    paths: [dast.json]
```

## Дополнительная информация

### Типичные ограничения
- **SAST** зависит от качества правил и поддержки фреймворков; может пропустить уязвимости, возникающие из-за генерации кода.
- **DAST** чувствителен к качеству тестовой среды и может не покрыть скрытые эндпоинты, недоступные без сложной навигации.

### Комбинированная стратегия
- **Shift Left:** Интеграция SAST на уровне IDE и pre-commit хуков для максимально ранней обратной связи.
- **Shift Right:** Запуск DAST в ночных сборках с полным покрытием и аутентификацией для поиска рантайм-уязвимостей.
- **Корреляция результатов:** Связывание отчетов SAST и DAST для приоритизации уязвимостей, которые не только существуют в коде, но и могут быть проэксплуатированы.

### Советы по настройке
- Начинайте с блокировки только критических уязвимостей, постепенно ужесточая правила.
- Для SAST используйте инкрементальные сканы и baseline, чтобы не замедлять CI.
- Для DAST исключайте разрушающие маршруты и настраивайте профили аутентификации.
