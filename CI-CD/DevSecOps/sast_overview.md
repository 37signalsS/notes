# Статический анализ безопасности — SAST

## Определения

**SAST (Static Application Security Testing — статическое тестирование безопасности приложений)** — метод анализа безопасности, проверяющий исходный код, байт-код или бинарные файлы приложения без его фактического запуска («тестирование белого ящика»).

Цель SAST — обнаружение уязвимостей на ранних этапах жизненного цикла разработки (**Shift Left**), когда стоимость их исправления минимальна.

## Базовые концепции

### Методы анализа

Современные SAST-сканеры используют комбинацию нескольких техник:

- **Taint Analysis (Анализ загрязнения):** отслеживание прохождения ненадёжных данных от «источника» (source, например, HTTP-параметр) до «приёмника» (sink, например, SQL-запрос).
- **Data Flow Analysis (Анализ потоков данных):** изучение того, как переменные меняют свои значения и взаимодействуют друг с другом в коде.
- **Control Flow Graph (CFG — Граф потока управления):** построение карты всех возможных путей выполнения программы для поиска логических ошибок.
- **Semantic Analysis (Семантический анализ):** проверка контекста использования функций и соответствие паттернам безопасного программирования.

### Цели и охват

- **Превентивность:** обнаружение дефектов на ранних стадиях разработки (до сборки и развёртывания).
- **Полное покрытие:** анализ всей кодовой базы, включая логику, которая редко выполняется в рантайме.
- **Зависимость от правил:** качество анализа напрямую зависит от набора правил (ruleset), поддержки языков программирования и используемых фреймворков.

### Типы обнаруживаемых уязвимостей

SAST эффективен для поиска структурных и логических ошибок в коде:

- Инъекции (SQL, Command, LDAP)
- Межсайтовый скриптинг (XSS — Cross-Site Scripting)
- Небезопасная десериализация данных
- Выход за пределы директории (Path traversal)
- Секреты в коде (пароли, API-ключи)
- Криптографические ошибки и слабые алгоритмы
- Ошибки в логике авторизации и контроля доступа

Полный список уязвимостей с сопоставлением по инструментам — в [обзоре уязвимостей SAST/DAST](./sast_dast_vulnerabilities.md).

### Ограничения

- **Ложноположительные срабатывания (False Positives):** возникают из-за отсутствия контекста выполнения (например, если данные уже прошли внешнюю валидацию).
- **Скорость:** полный анализ крупного монолитного проекта может занимать значительное время.
- **Сложность настройки:** требует адаптации правил и исключений для снижения «шума» и повышения точности.

## Практические сценарии

### Интеграция в CI/CD

Внедрение SAST на ранних этапах позволяет реализовать стратегию Shift Left. Основные точки встраивания:

- **IDE (Integrated Development Environment — интегрированная среда разработки):** плагины для проверки кода в реальном времени.
- **Pre-commit хуки:** запрет коммита при наличии критических уязвимостей.
- **Pull/Merge Request:** автоматический анализ только изменённого кода (diff).

Подробные примеры конфигураций пайплайнов приведены в [руководстве по интеграции SAST/DAST в CI/CD](./sast_dast_cicd_integration.md).

### Пример: Интеграция Semgrep в CI/CD

Semgrep позволяет быстро проверять код на соответствие политикам безопасности с помощью YAML-шаблонов.

```yaml
sast_semgrep:
  image: returntocorp/semgrep
  stage: test
  script:
    # Запуск сканирования по правилам сообщества
    - semgrep --config auto --sarif --output sast.sarif
    # → Результат: файл sast.sarif для интеграции с Dashboard безопасности
  artifacts:
    paths: [sast.sarif]
```

### Пример: Уязвимость SQL-инъекции (Python)

SAST обнаруживает использование `f-строк` или конкатенации при формировании запроса, что является небезопасным при использовании пользовательского ввода.

```python
# Уязвимо: прямое встраивание переменной в строку запроса
user_id = request.args.get("id")
sql = f"SELECT * FROM users WHERE id = {user_id}"
cursor.execute(sql)
# → Результат: SAST пометит этот блок как Critical (CWE-89: SQL Injection)
```

### Пример: Исправленный код (Prepared Statements)

Использование параметризованных запросов разделяет данные и логику запроса.

```python
# Безопасно: использование плейсхолдеров
user_id = request.args.get("id")
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
# → Результат: SAST пропустит этот код как безопасный
```

## Дополнительная информация

### Оптимизация и внедрение

- **Инкрементальный анализ:** сканирование только изменённых файлов значительно ускоряет проверки в CI/CD, обеспечивая быструю обратную связь разработчику.
- **Baseline (Базовая линия):** фиксация текущего состояния безопасности позволяет «заморозить» старые уязвимости и блокировать сборку только при появлении новых находок.
- **SARIF (Static Analysis Results Interchange Format):** стандартный JSON-формат для обмена результатами анализа, поддерживаемый большинством современных платформ (GitHub, GitLab, DefectDojo).
- **Снижение шума:** регулярный аудит правил и настройка исключений (ложные срабатывания) критичны для поддержания доверия разработчиков к инструменту.
