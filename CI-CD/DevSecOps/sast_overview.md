# SAST (Static Application Security Testing)

## Определения

**SAST (Static Application Security Testing)** — это метод анализа безопасности, который проверяет исходный код, байт-код или бинарные файлы приложения без его запуска. Этот подход также известен как «тестирование белого ящика».

SAST-сканеры анализируют код на наличие уязвимостей, отслеживая поток данных от «источника» (например, пользовательский ввод) до «приёмника» (например, выполнение SQL-запроса), и выявляют небезопасные конструкции и логические ошибки.

## Основные концепции

### Цели и охват

- **Превентивность:** Обнаруживает дефекты на самых ранних стадиях разработки (до сборки и развертывания).
- **Полное покрытие:** Анализирует всю кодовую базу, включая тот код, который может не выполняться во время динамического тестирования.
- **Зависимость от правил:** Качество анализа напрямую зависит от набора правил (ruleset), поддержки языка программирования и используемых фреймворков.

### Типы обнаруживаемых уязвимостей

SAST особенно эффективен для поиска:

- **Инъекций в коде:** SQL, Command, LDAP, NoSQL инъекции, возникающие из-за небезопасной конкатенации строк.
- **Межсайтового скриптинга (XSS):** Неэкранированные вставки в HTML/JS в шаблонах.
- **Небезопасной десериализации:** Использование небезопасных форматов и библиотек.
- **Уязвимостей обработки файлов:** Path Traversal (`../`), небезопасная загрузка файлов.
- **Секретов в коде:** Захардкоженные токены, API-ключи, пароли.
- **Криптографических ошибок:** Использование слабых алгоритмов (MD5, SHA-1), отсутствие соли, предсказуемые ключи.
- **Логических ошибок авторизации:** Пропуск проверок прав доступа к защищенным методам.

### Ограничения

- **Ложноположительные срабатывания:** SAST-инструменты часто генерируют большое количество ложных срабатываний, если они не учитывают контекст (например, если данные уже были проверены).
- **Скорость:** Полный анализ большого проекта может занимать значительное время.
- **Сложность настройки:** Требует тонкой настройки правил и политик для снижения "шума".

## Практические сценарии

### Интеграция в CI/CD

SAST обычно встраивается на ранних этапах конвейера:

- **На уровне IDE:** Плагины для мгновенной обратной связи разработчику.
- **Pre-commit хуки:** Быстрая проверка измененных файлов перед коммитом.
- **Pull/Merge Request:** Инкрементальный анализ для проверки только новых изменений.
- **Этап сборки (Build):** Полный анализ всего приложения.

### Пример: Уязвимость SQL-инъекции

SAST легко обнаружит такой код, отследив, что данные из `request` попадают в `execute` без параметризации.

```python
# Уязвимо: конкатенация строки
user_id = request.args.get("id")
sql = f"SELECT * FROM users WHERE id = {user_id}"
cursor.execute(sql)
```

### Пример: Исправленный код

В безопасной версии используется параметризованный запрос, что предотвращает инъекцию.

```python
# Безопаснее: параметризованный запрос
user_id = request.args.get("id")
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
```

## Дополнительная информация

- **Инкрементальный анализ:** Для ускорения проверок в CI/CD большинство инструментов поддерживают сканирование только измененного кода (diff-скан), что значительно сокращает время.
- **Baseline:** Установка "базового уровня" (baseline) позволяет сосредоточиться только на новых уязвимостях, появившихся после последней проверки.

SAST является частью комплексной стратегии безопасности, которая включает [DAST](../DevSecOps/dast_overview.md), [SCA-анализ зависимостей](../CI-CD/.../sca_overview.md) и [тестирование безопасности в CI/CD](../DevSecOps/sast_dast_cicd_integration.md).
