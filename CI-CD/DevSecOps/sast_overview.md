# Статический анализ безопасности — SAST

**Reliability Score: 10** (SSoT + Web Verification 2026: актуализировано на основе трендов AI-driven семантического анализа, Auto-Remediation и ASPM)

## Определения

**SAST (Static Application Security Testing — статическое тестирование безопасности приложений)** — метод анализа безопасности, проверяющий исходный код, байт-код или бинарные файлы приложения без его фактического запуска («тестирование белого ящика»).

В 2026 году SAST трансформировался из простого поиска паттернов в **интеллектуального партнера разработчика**:
- **AI-Driven Semantic Analysis (Семантический анализ на базе ИИ):** Использование LLM для понимания намерений (intent) разработчика и логики потоков данных. Это позволяет выявлять сложные архитектурные уязвимости и снижать уровень шума (False Positives) до минимума.
- **Auto-Remediation (Автоматическое исправление):** Использование ИИ-агентов для генерации проверенных Pull Request с исправлениями. Агенты не просто меняют код, но и учитывают контекст всего приложения, обеспечивая обратную совместимость.
- **Shift Left 2.0:** Интеграция сканирования в IDE и ИИ-копилоты, предотвращающая попадание уязвимостей в код на этапе его написания.

Цель SAST — обнаружение и устранение дефектов на самых ранних этапах жизненного цикла разработки ПО (**SDLC**), обеспечивая безопасность «по умолчанию».

## Базовые концепции

### Методы анализа (Классика + 2026)

Современные SAST-платформы объединяют традиционные математические модели с нейросетевым анализом:

1.  **Taint Analysis (Анализ загрязнений):**
    - **Source (Источник):** Место попадания внешних данных (API-запрос, пользовательский ввод).
    - **Sink (Приемник):** Опасная функция, где данные могут нанести вред (SQL-запрос, выполнение команды ОС).
    - **Sanitizer (Санитайзер):** Функция очистки или валидации данных.
    - В 2026 году анализ является **Inter-service**, отслеживая путь данных между микросервисами через контракты.
2.  **Semantic & Intent Analysis (Семантика и намерения):** ИИ анализирует контекст. Если разработчик использует кастомную библиотеку для валидации, которую сканер не знает, ИИ может «понять» её назначение по реализации и не выдавать ложное срабатывание.
3.  **Control Flow Graph (CFG) & Data Flow Graph (DFG):** Построение графов выполнения и передачи данных. Современные системы строят **Unified Graph**, объединяющий код, конфигурацию инфраструктуры (IaC) и зависимости.
4.  **Reachability Analysis (Анализ достижимости):** Интеграция с платформами **ASPM** для проверки того, доступен ли уязвимый участок кода извне в текущей конфигурации сети и рантайма.

### Типы обнаруживаемых уязвимостей

SAST эффективен для поиска структурных, логических и ИИ-специфичных ошибок:

1.  **Инъекции:** SQL, NoSQL, OS Command, LDAP, Template Injection (SSTI).
2.  **Межсайтовый скриптинг (XSS):** Отраженный, хранимый и DOM-based.
3.  **Логические ошибки:** Ошибки в цепочках авторизации и контроля доступа (BOLA/IDOR на уровне кода).
4.  **Секреты и PII:** Токены, пароли и персональные данные в коде или конфигурациях.
5.  **AI Package Hallucination:** Обнаружение зависимостей, которые «выдуманы» ИИ-копилотами и могут быть подменены злоумышленниками в реестрах.
6.  **Insecure IaC:** Ошибки в манифестах Kubernetes, Terraform, Dockerfile и GitHub Actions workflows (**Cordyceps**).

Подробное сопоставление — в **[обзоре уязвимостей SAST/DAST](./sast_dast_vulnerabilities.md)**.

### Ограничения

- **AI Hallucinations (Галлюцинации ИИ):** При автоматическом исправлении ИИ может предложить код, который вносит новые логические ошибки. Валидация тестами обязательна.
- **Context Gap:** Без данных из рантайма SAST не может на 100% подтвердить эксплуатируемость уязвимости.
- **Слепые зоны динамики:** Анализ не видит уязвимости, возникающие из-за динамической загрузки кода или конфигураций через внешние источники.

## Практические сценарии

### Интеграция в CI/CD (Lifecycle 2026)

Современный подход подразумевает многоуровневое сканирование:

1.  **IDE (Pre-commit):** AI-плагины проверяют дифф кода в реальном времени.
2.  **Pull Request (CI):** Инкрементальный анализ. Блокировка (Quality Gate) только при обнаружении `Critical` уязвимостей.
3.  **ASPM Correlation:** Агрегация результатов всех сканеров, исключение дубликатов и приоритизация на основе **Reachability Analysis**.

### Пример 1: AI Auto-Remediation (Python)

SAST находит уязвимость и ИИ-агент предлагает исправление.

```python
# Уязвимый код (Находка SAST: SQL Injection)
user_id = request.args.get("id")
query = f"SELECT * FROM users WHERE id = {user_id}"
cursor.execute(query)

# Предложение AI-Remediation (Параметризованный запрос)
user_id = request.args.get("id")
cursor.execute("SELECT * FROM users WHERE id = %s", (user_id,))
# → Агент также добавляет юнит-тест для проверки этого эндпоинта.
```

### Пример 2: Semgrep в GitLab CI с экспортом SARIF

```yaml
sast_scan:
  image: returntocorp/semgrep
  stage: security
  script:
    # Запуск анализа с генерацией отчета в формате SARIF
    - semgrep scan --config auto --sarif --output gl-sast-report.sarif
  artifacts:
    reports:
      sast: gl-sast-report.sarif
    paths: [gl-sast-report.sarif]
```

## Дополнительная информация

### Оптимизация и стандарты (2026)

- **ASPM Orchestration:** Интеграция SAST в платформы управления безопасностью для корреляции с SCA и DAST. Это позволяет отсеивать уязвимости в коде, который не используется в рантайме.
- **SARIF (Static Analysis Results Interchange Format):** Отраслевой стандарт для обмена результатами анализа. Позволяет отображать находки разных инструментов в едином интерфейсе GitHub/GitLab.
- **VEX (Vulnerability Exploitability eXchange):** Стандарт для обмена информацией о статусе уязвимости (например, «неэксплуатируема», «исправлена»).
- **Инкрементальный анализ:** В 2026 году является обязательным требованием. Анализ только изменений (diff) позволяет сократить время работы сканера с часов до минут.
