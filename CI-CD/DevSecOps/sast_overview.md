# Статический анализ безопасности — SAST

## Определения

**SAST (Static Application Security Testing — статическое тестирование безопасности приложений)** — метод анализа безопасности, проверяющий исходный код, байт-код или бинарные файлы приложения без его фактического запуска («тестирование белого ящика»).

В отличие от динамического анализа **[DAST](./dast_overview.md)**, SAST работает до запуска приложения и не требует рантайма.

Цель SAST — обнаружение и устранение дефектов на самых ранних этапах жизненного цикла разработки ПО (**SDLC**), обеспечивая безопасность «по умолчанию».

## Базовые концепции

### Методы анализа (Классика + 2026)

Современные SAST-платформы объединяют традиционные математические модели с углублённым статическим анализом:

1.  **Taint Analysis (Анализ загрязнений):**
    - **Source (Источник):** Место попадания внешних данных (API-запрос, пользовательский ввод).
    - **Sink (Приемник):** Опасная функция, где данные могут нанести вред (SQL-запрос, выполнение команды ОС).
    - **Sanitizer (Санитайзер):** Функция очистки или валидации данных.
    - В 2026 году анализ является **Inter-service**, отслеживая путь данных между микросервисами через контракты.
2.  **Semantic Analysis (Семантический анализ):** Анализ контекста использования кода. Если разработчик использует кастомную библиотеку для валидации, движок может учесть её реализацию и не выдавать ложное срабатывание на основе семантики, а не только текстового паттерна.
3.  **Control Flow Graph (CFG) & Data Flow Graph (DFG):** Построение графов выполнения и передачи данных. Современные системы строят **Unified Graph**, объединяющий код, конфигурацию инфраструктуры (IaC) и зависимости.
4.  **Reachability Analysis (Анализ достижимости):** Интеграция с платформами **ASPM** для проверки того, доступен ли уязвимый участок кода извне в текущей конфигурации сети и рантайма.

### Архитектура SAST-движка и виды анализа

Чтобы понимать ограничения и причины ложных срабатываний, важно представлять конвейер типичного SAST-движка:

1.  **Парсинг (Parsing):** исходный код разбирается в дерево разбора (**AST — Abstract Syntax Tree**). Лёгкие инструменты (Semgrep, grep-подобные) работают преимущественно на уровне паттернов по AST/тексту и не требуют сборки проекта.
2.  **Построение графов:** на базе AST строятся **CFG (Control Flow Graph)** — граф потока управления, **DFG (Data Flow Graph)** — граф передачи данных, и **Call Graph** — граф вызовов между функциями/методами. Тяжеловесные движки (CodeQL, SonarQube, Coverity) строят единый граф всего проекта.
3.  **Data-flow / Taint analysis:** вдоль DFG от `Source` к `Sink` распространяется метка «загрязнения». Если метка достигает опасной функции и на пути не встретился `Sanitizer` — формируется находка. Для отслеживания возможных значений без реального исполнения алгоритм может использовать абстрактную интерпретацию (abstract interpretation).
4.  **Сопоставление с правилами:** каждому пути/узлу применяются правила (паттерны, запросы к графу, эвристики). Результат — находка с CWE, уровнем серьёзности и указанием участка кода.

**Две категории инструментов:**

| Категория | Примеры | Требует сборки? | Скорость | Охват |
| :--- | :--- | :--- | :--- | :--- |
| **Лёгкие, pattern-based** | Semgrep, grep, RegEx-линтеры | Нет | Секунды–минуты | Точечные паттерны, быстрый feedback |
| **Тяжёлые, data-flow** | CodeQL, SonarQube, Coverity, Checkmarx | Часто да (Java/Scala/C/C++ через байт-код или compilation DB) | Минуты–десятки минут | Глубокий межпроцедурный анализ |

**Важно для DevOps/SRE:** часть движков требует рабочей сборки (скомпилированный байт-код либо `compile_commands.json` для C/C++). Если проект не собирается в среде раннера, такой SAST либо не запустится, либо пропустит файлы. Лёгкие инструменты (Semgrep, Bandit) этого не требуют и проще встраиваются в пайплайн.

### Типы обнаруживаемых уязвимостей

SAST эффективен для поиска структурных, логических и конфигурационных ошибок:

1.  **Инъекции:** SQL, NoSQL, OS Command, LDAP, Template Injection (SSTI).
2.  **Межсайтовый скриптинг (XSS):** Отраженный, хранимый и DOM-based.
3.  **Логические ошибки:** Ошибки в цепочках авторизации и контроля доступа (BOLA/IDOR на уровне кода).
4.  **Секреты и PII:** Токены, пароли и персональные данные в коде или конфигурациях.
5.  **Insecure IaC:** Ошибки в манифестах Kubernetes, Terraform, Dockerfile и GitHub Actions workflows.

Подробное сопоставление — в **[обзоре уязвимостей SAST/DAST](./sast_dast_vulnerabilities.md)**.

Большинство перечисленных классов напрямую отражены в **OWASP Top 10 (2021)**: инъекции и XSS — A03 (Injection); небезопасная аутентификация и контроль доступа (IDOR/BOLA) — A01/A07; секреты и PII — A02 (Cryptographic Failures) / A04 (Insecure Design); insecure IaC — A05 (Security Misconfiguration). Актуальное сопоставление CWE и примеров — в **[обзоре уязвимостей SAST и DAST](./sast_dast_vulnerabilities.md)**.

### Ограничения

- **Context Gap:** Без данных из рантайма SAST не может на 100% подтвердить эксплуатируемость уязвимости.
- **Слепые зоны динамики:** Анализ не видит уязвимости, возникающие из-за динамической загрузки кода или конфигураций через внешние источники.
- **Зависимость от сборки:** Тяжёлые движки (CodeQL, Coverity) требуют корректной конфигурации сборки; без `compile_commands.json` или байт-кода анализ будет неполным.
- **Ложные срабатывания (FP):** Агрессивные правила могут шумить на валидный код; без процесса triage и baseline инструмент становится бесполезным.

### Модель серьёзности находок и борьба с шумом

SAST не «знает» эксплуатируемость — он сообщает о потенциально опасном паттерне. Поэтому критичны две метрики:

- **False Positive (FP, ложное срабатывание):** находка, которую нельзя эксплуатировать или которой нет в реальности (например, вход уже очищен кастомным санитайзером, неизвестным движку). Много FP делает инструмент бесполезным — разработчики начинают игнорировать отчёты.
- **False Negative (FN, пропуск):** реальная уязвимость, которую движок не нашёл (нет правила, сложный контекст, динамическая диспетчеризация).

Серьёзность обычно задаётся связкой:

- **CWE (Common Weakness Enumeration)** — тип слабости (например, CWE-89 SQL Injection).
- **CVSS** — числовая оценка критичности (0–10).
- **Rule confidence / severity** — уверенность самого правила (Low/Medium/High/Critical).

Практическое правило для gate: блокировать сборку на `Critical`/`High` с высокой уверенностью, `Medium`/`Low` отправлять в triage без блокировки. Подробнее о triage и подавлении — в разделе «Обработка ложных срабатываний» ниже.

## Практические сценарии

### Интеграция в CI/CD (SDLC 2026)

Современный подход подразумевает многоуровневое сканирование:

1.  **IDE (Pre-commit):** быстрые лёгкие проверки (линтер + часть правил Semgrep) — мгновенный feedback разработчику.
2.  **Pull Request (CI):** **инкрементальный** анализ только изменений (diff) — дешево по времени и не блокирует из-за старых находок.
3.  **Nightly / релизная ветка:** **полный** анализ всего репозитория для нахождения накопленного долга.
4.  **ASPM Correlation:** Агрегация результатов всех сканеров, исключение дубликатов и приоритизация на основе **Reachability Analysis**.

### Пример 1: Semgrep в GitLab CI с экспортом SARIF

```yaml
sast_scan:
  image: returntocorp/semgrep
  stage: security
  script:
    # Запуск анализа с генерацией отчета в формате SARIF
    - semgrep scan --config auto --sarif --output gl-sast-report.sarif
  artifacts:
    reports:
      sast: gl-sast-report.sarif
    paths: [gl-sast-report.sarif]
```

Готовые примеры запуска сканеров (Semgrep, Bandit, gitleaks) на self-hosted раннерах — в **[сравнении SAST vs DAST](./sast_vs_dast.md)**. Ниже — сценарии, специфичные для обзора: развёртывание сервера, авторские правила, сканирование IaC, универсальный SARIF-gate и обработка ложных срабатываний.

### Пример 3: Авторское правило Semgrep (custom rule)

Встроенных правил (`p/ci`, `p/security`) часто недостаточно для специфики проекта (внутренние опасные функции, корпоративные стандарты). Правила Semgrep пишутся на YAML и используют паттерны по AST.

**Предусловия:** `pip install semgrep` (или Docker-образ `returntocorp/semgrep`); проект на Python.

**1. Описать правило** (файл `rules/dangerous_eval.yaml`):

```yaml
rules:
  - id: no-eval-of-user-input
    severity: ERROR
    languages: [python]
    message: "Прямой eval() пользовательского ввода — RCE"
    pattern: |
      eval($X)
    metadata:
      cwe: "CWE-95"
      category: security
```

**2. Запустить и проверить находку:**

```bash
semgrep scan --config rules/dangerous_eval.yaml --sarif -o findings.sarif
# → в findings.sarif появится запись, если в коде есть eval(...)
```

**3. Написать тест для правила** (папка `rules/tests/` с файлами `dangerous_eval.py` — должен находить — и `dangerous_eval_no.py` — не должен):

```bash
semgrep scan --config rules/dangerous_eval.yaml --test
# → OK, если все ожидания (ruleid / ok) совпали
```

**Validation:** `semgrep --test` возвращает 0 и сообщает «all tests passed»; в боевом запуске `--sarif` формирует отчёт для CI.

**Troubleshooting:**
- *Правило не срабатывает на похожий код:* Semgrep сопоставляет по структуре AST, а не по тексту — уточните `pattern` (например, `pattern-either` для нескольких вариантов) или `pattern-inside` для контекста.
- *Слишком много FP:* добавьте `pattern-not` / `pattern-not-inside`, чтобы исключить безопасные вызовы.

### Пример 4: Сканирование инфраструктурного кода (IaC) — Checkov / KICS

SAST применим не только к бизнес-логике, но и к манифестам инфраструктуры: `Dockerfile`, манифестам Kubernetes, workflow GitHub Actions. Ошибки здесь (root-пользователь в контейнере, `privileged: true`, проброшенный docker socket) — частая причина компрометации.

**Предусловия:** `pip install checkov` или `docker run bridgecrew/checkov`; либо бинарь `kics`. Репозиторий с `Dockerfile` и манифестами.

**Checkov (Dockerfile + K8s + GitHub Actions):**

```bash
checkov -d . --framework dockerfile,kubernetes,github_actions \
  --output sarif --output-file-path iac.sarif
# → находки по best-practice и CIS-бенчмаркам (CKV_DOCKER_*, CKV_K8S_*)
```

**KICS (альтернатива, те же типы):**

```bash
kics scan -p . -i Dockerfile,Kubernetes -o . --report-formats sarif
# → iac.sarif с находками, включая секреты в манифестах
```

**Validation:** в отчёте `iac.sarif` перечислены проверки вида «CKV_DOCKER_2 (Ensure that HEALTHCHECK instructions have been added)»; `checkov` печатает сводку `Passed/Failed` по каждому файлу.

**Troubleshooting:**
- *Ложные срабатывания на допустимых настройках:* используйте suppress-аннотации (например, `#checkov:skip=CKV_DOCKER_x:reason`) или файл `.checkov.yaml` с `skip_check`.
- *Kubernetes манифесты разбиты на несколько файлов:* передавайте каталог целиком (`-d`), а не один файл.
- Подробнее об эшелонированной защите IaC — в **[Defense in Depth на уровне IaC](./iac-security-defense-in-depth.md)**.

### Пример 5: Разбор SARIF и quality gate на bash (jq)

Большинство SAST-инструментов (Semgrep, CodeQL, Checkov, Trivy) умеют экспортировать результат в **SARIF** — единый формат отчёта. Это позволяет написать один универсальный gate для любого инструмента.

**Предусловия:** утилита `jq`; файл `report.sarif`, сгенерированный любым SAST-сканером.

**Скрипт gate (блокирует при наличии High/Critical):**

```bash
#!/usr/bin/env bash
set -euo pipefail
REPORT="${1:-report.sarif}"
# Посчитать находки по уровням серьёзности (поля могут различаться у разных генераторов)
crit=$(jq '[.runs[].results[] | select(.level=="error")] | length' "$REPORT")
high=$(jq '[.runs[].results[] | select(.properties.severity=="high")] | length' "$REPORT")
echo "Critical/error: $crit, High: $high"
if [ "$crit" -gt 0 ] || [ "$high" -gt 0 ]; then
  echo "SAST gate FAILED: обнаружены блокирующие находки"
  exit 1
fi
echo "SAST gate PASSED"
```

**Validation:** при пустом/безопасном отчёте скрипт печатает `SAST gate PASSED` и возвращает 0; при наличии `level=error` — печатает FAIL и возвращает 1, прерывая пайплайн.

**Troubleshooting:**
- *jq выдаёт `null` или ошибку:* разные инструменты кладут серьёзность в разные поля (`level`, `properties.severity`, `properties.issue_severity`). Адаптируйте `select(...)` под конкретный генератор SARIF или нормализуйте отчёт.
- *Хотите разрешить только известные FP:* ведите baseline — сохраняйте идентификатор находки и вычитайте его перед gate (см. Пример 7).

### Пример 6: Обработка ложных срабатываний (triage и suppression)

Чем агрессивнее правила, тем больше FP. Без процесса обработки команда начнёт игнорировать SAST. Рабочий подход:

1.  **Baseline (базовая линия):** при внедрении SAST просканируйте существующий код и «заморозьте» текущие находки как baseline. Новый код проверяется строго (блокирует), старые находки живут в отдельном трекере и закрываются планово. Это даёт мгновенный feedback без «стены» из сотен исторических FP.
2.  **Suppression с обоснованием:** подавляйте только с пояснением (почему не эксплуатируемо). В Semgrep — inline-комментарий `# nosemgrep: <rule-id>`, в Checkov — `#checkov:skip=...:reason`, в SonarQube — `// NOSONAR` (используйте осторожно).
3.  **Triage SLA:** каждая находка уровня High/Critical получает владельца и дедлайн (например, 7 дней). Форматы SARIF и VEX помогают фиксировать статус («неэксплуатируема», «исправлена»).
4.  **Ревью на PR:** SAST-находки показываются прямо в PR (GitLab Security Dashboard / GitHub code scanning). Разработчик видит контекст строки и быстро решает — править или подавить с обоснованием.

**Практический пример подавления в Semgrep:**

```python
# nosemgrep: python.lang.security.audit.dangerous-eval
result = eval(user_input)  # обоснование: ввод проходит через наш allow-list выше
```

**Validation:** количество «открытых без обоснования» FP мониторится; целевая метрика — снижение доли FP со временем за счёт уточнения правил и baseline.

**Troubleshooting:**
- *Находки снова появляются после рефакторинга:* inline-аннотации могут «отвязаться» при переименовании функции — переносите `nosemgrep` вместе с кодом.
- *Слишком много подавлений:* это сигнал, что правило неточное — напишите кастомное (Пример 3) вместо массового `nosemgrep`.

### Реагирование на инцидент (Incident Response Runbook)

При обнаружении критической уязвимости через SAST в production-коде или инфраструктуре:

1. **Изолировать:** остановить деплой, приостановить мерж ветки с уязвимым кодом, откатить релиз при необходимости.
2. **Воспроизвести:** локально запустить SAST-сканер с тем же набором правил для подтверждения находки и исключения FP.
3. **Зафиксировать:** сохранить артефакты (SARIF, логи, снифферы) в защищённое хранилище с пометкой времени.
4. **Приоритизировать:** сопоставить с данными DAST/ASPM (если доступен) для подтверждения достижимости; при отсутствии данных — консервативно считать уязвимость достижимой.
5. **Исправить:** назначить владельца и SLA; для SAST — исправление кода или конфигурации; для IaC — обновление манифеста.
6. **Проверить:** повторный скан после исправления; gate зелёный.
7. **Ретроспектива:** обновить baseline, добавить правило в кастомный набор если это повторяющаяся ошибка, закрыть тикет.

## Устранение неисправностей

### Типичные ошибки и решения

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `semgrep: command not found` | Инструмент не установлен в образе раннера | Установить `pip install semgrep` или использовать официальный Docker-образ `returntocorp/semgrep` |
| `compile_commands.json not found` | Тяжёлый анализатор (CodeQL/Coverity) требует базу данных сборки | Сгенерировать `compile_commands.json` через `cmake -DCMAKE_EXPORT_COMPILE_COMMANDS=ON` или `bear` |
| Много FP на легитимный код | Правила слишком агрессивные или неизвестные паттерны | Добавить `pattern-not`/`pattern-not-inside` в Semgrep; настроить suppression; вести baseline |
| Скан слишком долгий | Большой репозиторий, дефолтный таймаут | Использовать инкрементальный анализ (diff), ограничить scope через `--include`, увеличить ресурсы раннера |
| SonarQube server unreachable | Сервер недоступен или превышены лимиты | Проверить сетевую связность (`curl -I http://sonarqube:9000`), лицензию и квоты |
| `jq` не парсит SARIF | Поля серьёзности отличаются у разных генераторов | Адаптировать `select(.level=="error")` под конкретный инструмент или нормализовать отчёт перед gate |
| `nosemgrep` отвязался после рефакторинга | Переименование функции/файла разорвало аннотацию | Переносить `# nosemgrep` вместе с кодом; использовать rule ID вместо номера строки |
| Checkov падает на больших репозиториях | Нехватка памяти или таймаут | Увеличить лимиты (`--python-version`, `--skip-path`), запускать на выделенном раннере |
| Baseline устарел | Кодbase сильно изменился | Перегенерировать baseline планово (ежемесячно), использовать incremental suppression |
| Quality Gate не срабатывает | Пороги настроены некорректно или метрики не обновляются | Проверить конфигурацию Quality Gate в SonarQube, убедиться что анализ завершился с статусом `SUCCESS` |

## Рекомендации

### Хост-харднинг раннеров (Runner Hardening)

Раннер, на котором запускаются SAST-инструменты, должен быть изолирован и жёстко ограничен:

```bash
# /etc/systemd/system/gitlab-runner.service.d/zz-hardening.conf
[Service]
NoNewPrivileges=yes
ProtectSystem=strict
ProtectHome=read-only
PrivateTmp=yes
RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
MemoryDenyWriteExecute=yes
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM
```

Для контейнерных раннеров:
- Используйте профиль AppArmor/SELinux, например `--security-opt apparmor=docker-ci-runner`.
- Для максимальной изоляции — gVisor или Kata Containers.
- Регулярно проверяйте активные ограничения: `systemctl show gitlab-runner --property=*`

### Сетевая сегментация и управление доступом

- **SAST-раннер:** должен иметь доступ к репозиторию и серверу SonarQube, но не должен иметь прямого выхода в прод. Используйте отдельный network namespace / VLAN / docker network.
- **Egress-политики:** разрешайте только исходящие к репозиториям, артефакт-стораджу и внутреннему SonarQube/ASPM. Запретите произвольный выход в интернет.
- **Самоподписанные сертификаты:** допустимы только внутри доверенного контура; для доступа к внутренним сервисам используйте внутренний PKI.

### Ресурсы и масштабирование

- **Лёгкие инструменты (Semgrep, Bandit, gitleaks, Checkov):** укладываются в 512 МБ–1 ГБ RAM на джобу; подходят для параллельного запуска в CI.
- **SonarQube Server:** требует ≥4 ГБ RAM (рекомендуют 8 ГБ) и PostgreSQL; для команды >50 чел. выделяйте отдельный кластер с репликацией.
- **CodeQL / Coverity:** требуют значительных ресурсов на построение графа; планируйте отдельные "heavy" раннеры с 4–8 ГБ heap.
- **Хранение отчётов:** SARIF/JSON сохраняются как CI artifacts с ротацией 30–90 дней. Долгосрочное хранение — в локальное объектное хранилище (MinIO/NFS).

### Резервное копирование и восстановление CI/CD

- **Артефакты сканирования:** SARIF/JSON/HTML сохраняются как CI artifacts с ротацией 30–90 дней. Долгосрочное хранение — в локальное объектное хранилище (MinIO/NFS).
- **Конфигурации сканеров:** правила Semgrep, профили SonarQube, политики Checkov — версионируются в Git.
- **Бэкап baseline:** файлы подавлений и baseline находок должны быть в репозитории; их потеря приведёт к шторму FP при повторном внедрении.
- **SonarQube DB backup:** регулярный дамп PostgreSQL (ежедневно) и бэкап каталога `data/`; тестируйте восстановление на изолированном стенде.

### Политики и метрики

- **Gate-политика:** блокировать сборку на `Critical`/`High` с высокой уверенностью; `Medium`/`Low` — в triage без блокировки. Избегайте блокировки на «всех находках» на старте — это вызовет саботаж процесса.
- **Метрики программы:** отслеживайте Coverage (доля кода под сканированием), FP-rate, MTTR находок, долю PR с исправлениями до merge. Это показывает реальную эффективность, а не просто факт «сканер запущен».
- **Triage SLA:** каждая находка уровня High/Critical получает владельца и дедлайн (например, 7 дней). Low/Medium — планируется в спринт.

### Чек-лист минимальной защищённости (Quick Reference)

- [ ] SAST запускается на каждом PR (инкрементальный) и nightly (полный)
- [ ] Для Python/JS/Go — Semgrep или Bandit; для enterprise — SonarQube/CodeQL
- [ ] Все отчёты экспортируются в SARIF или JSON
- [ ] Quality gate блокирует на Critical/High с подтверждённой достижимостью
- [ ] Раннеры имеют хост-харднинг (NoNewPrivileges, ProtectSystem, AppArmor)
- [ ] Сетевая изоляция: SAST-раннер видит только репозиторий и сканеры
- [ ] Артефакты и baseline хранятся с ротацией и версионируются
- [ ] Triage SLA назначен (Critical ≤ 24ч, High ≤ 3 дня, Medium ≤ 7 дней)
- [ ] Baseline и подавления обновляются регулярно (ежемесячно)
- [ ] Сканеры обновляются (правила Semgrep, профили SonarQube) не реже квартала

## Дополнительная информация

### Метрики безопасности и качества кода

Для объективной оценки уровня безопасности и технического долга используются следующие метрики:

| Метрика | Описание | Цель |
| :--- | :--- | :--- |
| **Coverage** | Процент строк кода, покрытых модульными тестами. | > 80% |
| **Duplications** | Дублирующиеся блоки кода (copy-paste). | < 3% |
| **Technical Debt** | Оценка времени, необходимого для исправления всех найденных проблем. | < 5% |
| **Code Smells** | Потенциальные проблемы в коде, не влияющие на безопасность напрямую, но усложняющие поддержку. | Снижение с каждым релизом |
| **Security Hotspots** | Участки кода, требующие ручного аудита (например, использование криптографии, авторизация). | 100% ревью |
| **Reliability / Maintainability / Security Rating** | Буквенные оценки (A–E) по шкалам качества. | A или B |

### Trivy: тип анализа и место в стеке

**Trivy** выполняет **SCA (Software Composition Analysis)** — статический композиционный анализ, проверяющий не исходный код приложения, а его состав: зависимости, базовые образы, файловые системы и конфигурации IaC. В отличие от SAST (SonarQube, Semgrep), который анализирует логику и структуру кода, Trivy работает на уровне артефактов (образы, директории, файлы) и ищет известные CVE, секреты и ошибки конфигурации.

**Ключевые различия:**

| Инструмент | Тип анализа | Объект проверки | Пример |
| :--- | :--- | :--- | :--- |
| **SonarQube** | SAST | Исходный код (source code) | Поиск SQL-инъекций, insecure defaults в коде |
| **Trivy** | SCA / Compositional | Артефакты (образы, SBOM, IaC) | Поиск CVE в библиотеках `openssl`, секретов в Dockerfile |
| **DAST** | Динамический анализ | Запущенное приложение (runtime) | OWASP ZAP сканирует работающий веб-сервис |

**Важно:** Trivy не является динамическим анализатором (DAST). Сканирование запущенного контейнера (`trivy container <id>`) все равно является статическим анализом уже собранного артефакта (файловой системы), а не тестированием работающего приложения извне.

### ASPM Orchestration

Интеграция SAST в платформы управления безопасностью для корреляции с SCA и DAST. Это позволяет отсеивать уязвимости в коде, который не используется в рантайме.

### SARIF и VEX

- **SARIF (Static Analysis Results Interchange Format):** Отраслевой стандарт для обмена результатами анализа. Позволяет отображать находки разных инструментов в едином интерфейсе GitHub/GitLab.
- **VEX (Vulnerability Exploitability eXchange):** Стандарт для обмена информацией о статусе уязвимости (например, «неэксплуатируема», «исправлена»).

### Инкрементальный анализ

В 2026 году является обязательным требованием. Анализ только изменений (diff) позволяет сократить время работы сканера с часов до минут. Поддерживается большинством современных инструментов (Semgrep `--diff`, SonarQube PR Decoration, CodeQL query pack).
