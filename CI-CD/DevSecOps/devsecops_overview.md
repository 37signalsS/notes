# DevSecOps — обзор методологии

## Определения

**DevSecOps (Development, Security, Operations)** — методология интеграции практик безопасности на всех этапах жизненного цикла разработки программного обеспечения (**SDLC — Software Development Life Cycle**). Основная цель — сделать безопасность общей ответственностью команд разработки, эксплуатации и ИБ, а не отдельным этапом в конце цикла.

**AST (Application Security Testing)** — общая категория методов тестирования безопасности приложений, включающая:
- **SAST (Static AST):** анализ исходного кода без запуска приложения. Подробно: [SAST](./sast_overview.md).
- **DAST (Dynamic AST):** тестирование работающего приложения через внешние интерфейсы. Подробно: [DAST](./dast_overview.md).
- **SCA (Software Composition Analysis):** анализ сторонних библиотек и зависимостей на наличие известных уязвимостей.
- **IAST (Interactive AST):** гибридный метод, использующий агентов внутри работающего приложения.

**IaC Security (Infrastructure as Code Security)** — проверка конфигурационных файлов инфраструктуры (Terraform, CloudFormation, Ansible) на наличие ошибок безопасности до развертывания ресурсов.

## Базовые концепции

### Принципы DevSecOps

- **Shift Left (Сдвиг влево):** перенос проверок безопасности на максимально ранние этапы (IDE, Pull Requests).
- **Shift Right (Сдвиг вправо):** непрерывный мониторинг и защита приложения в процессе эксплуатации (Runtime Security).
- **Автоматизация и CI/CD:** встраивание сканеров в пайплайны для автоматической проверки каждого изменения.
- **Policy as Code (Политика как код):** формализация правил безопасности в виде кода, который может быть автоматически проверен и применен (например, OPA, Kyverno).
- **Безопасность как общая ответственность:** устранение барьеров между командами (Silos), обучение разработчиков основам безопасного кодирования.

### Инструменты и классификации

| Категория | Инструменты | Назначение |
| :--- | :--- | :--- |
| **SAST** | SonarQube, Semgrep, Bandit, Gosec | Анализ исходного кода. |
| **SCA / Container** | Trivy, Snyk, Grype | Поиск уязвимостей в библиотеках и образах. |
| **IaC Security** | Checkov, Terrascan, tfsec | Проверка конфигураций инфраструктуры. |
| **Secret Scanning** | Gitleaks, TruffleHog | Поиск секретов (ключей, токенов) в коде. |
| **DAST** | OWASP ZAP, Burp Suite, Nuclei | Тестирование работающего приложения. |
| **Policy as Code** | OPA (Open Policy Agent), Kyverno | Контроль соответствия политикам (в K8s и IaC). |
| **Runtime Security**| Falco, Tetragon | Обнаружение аномалий в работающих контейнерах. |

**Классификации и стандарты:**
- **OWASP Top 10:** список самых критичных рисков безопасности веб-приложений.
- **CWE (Common Weakness Enumeration):** перечень типов программных уязвимостей.
- **CVE (Common Vulnerabilities and Exposures):** база данных конкретных уязвимостей в ПО.

## Практические сценарии

### Жизненный цикл безопасности (DevSecOps Pipeline)

Внедрение DevSecOps подразумевает интеграцию проверок на каждом этапе:

1.  **Написание кода (IDE):** использование линтеров и плагинов для поиска уязвимостей и секретов "на лету".
2.  **Pull Request / Merge Request:**
    *   **SAST:** автоматический анализ измененного кода.
    *   **SCA:** проверка новых зависимостей на уязвимости и лицензионную чистоту.
    *   **IaC Scan:** проверка изменений в конфигурации инфраструктуры.
3.  **Сборка (Build):** сканирование получившегося Docker-образа на уязвимости (например, Trivy).
4.  **Развертывание (Deploy):**
    *   **Admission Control (K8s):** блокировка деплоя образов с критическими уязвимостями или небезопасных манифестов (например, Kyverno).
    *   **DAST:** запуск динамических тестов на стейджинге.
5.  **Эксплуатация (Run):**
    *   **Runtime Security:** мониторинг активности системных вызовов и сети для обнаружения атак.
    *   **CSPM (Cloud Security Posture Management):** непрерывный аудит настроек облачной инфраструктуры.

Подробные примеры конфигураций и скриптов для различных систем (GitLab CI, Jenkins) приведены в [руководстве по интеграции безопасности](./sast_dast_cicd_integration.md).

## Дополнительная информация

### Основные вызовы при внедрении

1.  **Высокий уровень шума:** ложноположительные срабатывания сканеров могут замедлить разработку. Необходимо профилирование правил и использование "базовых линий" (Baselines).
2.  **Культурный барьер:** необходимость обучения разработчиков и изменения их подхода к написанию кода.
3.  **Сложность интеграции:** поддержка множества языков программирования и фреймворков требует гибкой настройки инструментов.

### Метрики эффективности

- **Mean Time to Remediate (MTTR):** среднее время на исправление обнаруженной уязвимости.
- **Vulnerability Density:** количество уязвимостей на единицу объема кода.
- **Security Debt:** объем неисправленных уязвимостей в бэклоге.
