# DevSecOps: обзор методологии

## Определения

**DevSecOps** — методология интеграции задач безопасности на каждом этапе жизненного цикла разработки приложения (SDLC), обеспечивающая комплексный подход к защите. Подробная информация о жизненном цикле: [SDLC](../Core_Concepts/sdlc_overview.md).

**SAST (Static Application Security Testing)** — статический анализ кода приложения без его выполнения. Детальный обзор: [SAST](./sast_overview.md).

**DAST (Dynamic Application Security Testing)** — динамический анализ запущенного приложения во время выполнения в тестовой среде. Детальный обзор: [DAST](./dast_overview.md).

## Базовые концепции

### Принципы DevSecOps

- **Shift Left:** Раннее внедрение проверок безопасности (на этапе коммита/PR).
- **Автоматизация:** Встраивание сканеров безопасности в CI/CD-пайплайн.
- **Непрерывность:** Регулярные проверки на всех этапах (разработка, сборка, тестирование, релиз).
- **Комплексность:** Сочетание SAST, DAST, сканирования зависимостей, управления секретами.

### Инструменты и классификации

- **SAST-инструменты:** Checkov (IaC), SonarQube, Bandit (Python), Semgrep, gosec (Go).
- **DAST-инструменты:** OWASP ZAP, Burp Suite.
- **Сетевой контроль (CI-раннеры):** **[Harden-Runner](../../Github_CI/network-security.md)** (GitHub Actions).
- **Классификации уязвимостей:** CWE (Common Weakness Enumeration), CVE (Common Vulnerabilities and Exposures).

## Практические сценарии

### Интеграция SAST в GitLab CI

В платных версиях GitLab (Enterprise Edition) есть встроенный дашборд безопасности, который наглядно отображает найденные уязвимости. В бесплатной версии можно добиться схожего результата, добавив в пайплайн задачу, которая будет анализировать отчет SAST и останавливать выполнение в случае обнаружения проблем.

#### Модификация `.gitlab-ci.yml`

Для интеграции SAST необходимо внести следующие изменения в файл `.gitlab-ci.yml`:

1. **Добавить стадию `report`**: Эта стадия будет выполняться после тестирования и будет отвечать за анализ отчета о безопасности.
2. **Подключить встроенный шаблон SAST**: GitLab предоставляет готовые шаблоны для различных видов сканирования. Мы подключим `Security/SAST.gitlab-ci.yml`.
3. **Создать задачу для анализа отчета**: Мы добавим кастомную задачу, которая будет проверять артефакт (JSON-отчет), сгенерированный задачей SAST. Если отчет не пустой (т.е. найдены уязвимости), пайплайн завершится с ошибкой.

**Пример обновленного `.gitlab-ci.yml`:**

```yaml
stages:
  - test
  - report # Новая стадия для анализа отчета
  - cleanup
  # ... другие стадии

# Подключаем готовый шаблон от GitLab
include:
  - template: Security/SAST.gitlab-ci.yml

# Задача 'sast' будет создана автоматически из шаблона.
# Она выполняется на стадии 'test' и генерирует артефакт 'gl-sast-report.json'.

# Наша кастомная задача для проверки отчета
send-report:
  stage: report
  image: alpine:3.15
  before_script:
    - apk add --no-cache jq
  script:
    # Проверяем, содержит ли отчет о безопасности какие-либо уязвимости
    - |
      if [ -f "gl-sast-report.json" ] && [ $(jq '.vulnerabilities | length' gl-sast-report.json) -gt 0 ]; then
        echo "ALERT: Security issues detected! See the report artifact for details."
        # Выводим содержимое отчета для наглядности
        cat gl-sast-report.json
        # Завершаем пайплайн с ошибкой
        exit 1
      else
        echo "No security issues detected."
      fi
  artifacts:
    paths:
      - gl-sast-report.json
```

#### Анализ результатов

1. **Новые задачи в стадии `test`**: Из-за подключения шаблона `SAST`, GitLab автоматически добавит задачи, соответствующие языкам программирования в вашем проекте. Например, для Go-проекта появится задача `gosec-sast`.
2. **Выполнение сканирования**: Эти задачи сканируют код и генерируют отчет в формате `gl-sast-report.json`, который сохраняется как артефакт.
3. **Анализ отчета**: Наша задача `send-report` на стадии `report` заберет этот артефакт.
    - **Если уязвимости найдены**: Скрипт обнаружит, что JSON-файл содержит записи в массиве `vulnerabilities`, выведет сообщение об ошибке и содержимое отчета в лог, после чего завершит пайплайн с кодом `1`. Последующие стадии (кроме тех, что помечены `when: always`) не будут выполнены.
    - **Если уязвимостей нет**: Пайплайн продолжится в штатном режиме.

В логе провалившейся задачи можно будет увидеть JSON-отчет с описанием уязвимостей и ссылками на их описание в базах данных, таких как CWE, что дает разработчикам всю необходимую информацию для их устранения.
