# Введение в DevSecOps и тестирование безопасности в CI/CD

По мере развития CI/CD, вопросы безопасности становятся все более критичными. **DevSecOps** — это методология, которая интегрирует задачи безопасности на каждом этапе жизненного цикла разработки приложения, обеспечивая комплексный подход к защите.

См. также:
*   [CI/CD: Основные концепции](../ci_cd_overview.md)
*   [Управление секретами в CI/CD](./secrets_management.md)

## 1. Концепция DevSecOps

DevSecOps расширяет философию DevOps, включая безопасность в непрерывный цикл разработки, тестирования, доставки и эксплуатации. Цель — обнаружить и устранить проблемы безопасности как можно раньше, что значительно снижает стоимость их исправления и риски.

## 2. Типы тестирования безопасности в CI/CD

В контексте CI/CD используются различные методы тестирования безопасности:

### 2.1. SAST (Static Application Security Testing) — Статический анализ кода

*   **Определение:** Анализ исходного кода, байт-кода или бинарного кода приложения **без его фактического выполнения**.
*   **Когда проводится:** На ранних этапах CI, сразу после коммита кода.
*   **Преимущества:** Быстрое обнаружение уязвимостей, таких как SQL-инъекции, межсайтовый скриптинг (XSS), ошибки конфигурации, использование небезопасных библиотек.
*   **Инструменты:** Checkov (для Infrastructure as Code), SonarQube, Bandit (для Python), Semgrep.
*   **Зависимость от баз данных уязвимостей:** Часто опирается на классификации, такие как CWE (Common Weakness Enumeration), и базы данных общеизвестных уязвимостей, таких как CVE (Common Vulnerabilities and Exposures).

### 2.2. DAST (Dynamic Application Security Testing) — Динамический анализ кода

*   **Определение:** Анализ запущенного приложения **во время его выполнения** в тестовой среде.
*   **Когда проводится:** После развертывания приложения в тестовое окружение (staging, review app).
*   **Преимущества:** Позволяет выявить уязвимости, которые проявляются только во время работы приложения, например, проблемы с аутентификацией, управлением сессиями, конфигурацией окружения. Более приближен к реальным условиям.
*   **Инструменты:** OWASP ZAP, Burp Suite.

## 3. Интеграция безопасности в GitLab CI

GitLab (в платных версиях) предлагает встроенные возможности для SAST, DAST, сканирования зависимостей и контейнеров, что упрощает их интеграцию в пайплайны. Однако ничто не мешает использовать и сторонние инструменты.

Например, для статического анализа Infrastructure as Code (IaC) можно использовать **Checkov**, который сканирует файлы Terraform, CloudFormation, Kubernetes, ARM, Serverless и Dockerfile на соответствие политикам безопасности.

**Преимущества интеграции сторонних сканеров:**
*   **Гибкость:** Выбор инструмента, наиболее подходящего для вашего стека.
*   **Контроль:** Полный контроль над конфигурацией и выполнением сканирования.
*   **Раннее обнаружение:** Интеграция в CI позволяет обнаруживать проблемы безопасности до того, как код достигнет продуктивных окружений.

## 4. Практический пример: Интеграция SAST в GitLab CI

Этот раздел демонстрирует, как интегрировать статическое тестирование безопасности приложений (SAST) в пайплайн GitLab CI с использованием встроенных шаблонов GitLab. Этот метод позволяет автоматически сканировать исходный код на наличие уязвимостей при каждом коммите.

В платных версиях GitLab (Enterprise Edition) есть встроенный дашборд безопасности, который наглядно отображает найденные уязвимости. В бесплатной версии мы можем добиться схожего результата, добавив в пайплайн задачу, которая будет анализировать отчет SAST и останавливать выполнение в случае обнаружения проблем.

### 4.1. Модификация `.gitlab-ci.yml`

Для интеграции SAST необходимо внести следующие изменения в файл `.gitlab-ci.yml`:

1.  **Добавить стадию `report`**: Эта стадия будет выполняться после тестирования и будет отвечать за анализ отчета о безопасности.
2.  **Подключить встроенный шаблон SAST**: GitLab предоставляет готовые шаблоны для различных видов сканирования. Мы подключим `Security/SAST.gitlab-ci.yml`.
3.  **Создать задачу для анализа отчета**: Мы добавим кастомную задачу, которая будет проверять артефакт (JSON-отчет), сгенерированный задачей SAST. Если отчет не пустой (т.е. найдены уязвимости), пайплайн завершится с ошибкой.

**Пример обновленного `.gitlab-ci.yml`:**

```yaml
stages:
  - test
  - report # Новая стадия для анализа отчета
  - cleanup
  # ... другие стадии

# Подключаем готовый шаблон от GitLab
include:
  - template: Security/SAST.gitlab-ci.yml

# Задача 'sast' будет создана автоматически из шаблона.
# Она выполняется на стадии 'test' и генерирует артефакт 'gl-sast-report.json'.

# Наша кастомная задача для проверки отчета
send-report:
  stage: report
  image: alpine:3.15
  before_script:
    - apk add --no-cache jq
  script:
    # Проверяем, содержит ли отчет о безопасности какие-либо уязвимости
    - |
      if [ -f "gl-sast-report.json" ] && [ $(jq '.vulnerabilities | length' gl-sast-report.json) -gt 0 ]; then
        echo "ALERT: Security issues detected! See the report artifact for details."
        # Выводим содержимое отчета для наглядности
        cat gl-sast-report.json
        # Завершаем пайплайн с ошибкой
        exit 1
      else
        echo "No security issues detected."
      fi
  artifacts:
    paths:
      - gl-sast-report.json
```

### 4.2. Анализ результатов

После коммита этих изменений, пайплайн будет выглядеть иначе:

1.  **Новые задачи в стадии `test`**: Из-за подключения шаблона `SAST`, GitLab автоматически добавит задачи, соответствующие языкам программирования в вашем проекте. Например, для Go-проекта появится задача `gosec-sast`.
2.  **Выполнение сканирования**: Эти задачи сканируют код и генерируют отчет в формате `gl-sast-report.json`, который сохраняется как артефакт.
3.  **Анализ отчета**: Наша задача `send-report` на стадии `report` заберет этот артефакт.
    *   **Если уязвимости найдены**: Скрипт обнаружит, что JSON-файл содержит записи в массиве `vulnerabilities`, выведет сообщение об ошибке и содержимое отчета в лог, после чего завершит пайплайн с кодом `1`. Последующие стадии (кроме тех, что помечены `when: always`) не будут выполнены.
    *   **Если уязвимостей нет**: Пайплайн продолжится в штатном режиме.

В логе провалившейся задачи можно будет увидеть JSON-отчет с описанием уязвимостей и ссылками на их описание в базах данных, таких как CWE, что дает разработчикам всю необходимую информацию для их устранения.
