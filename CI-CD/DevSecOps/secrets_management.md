# Управление секретами в CI/CD

## Определения

**Управление секретами в CI/CD (Continuous Integration / Continuous Deployment — непрерывная интеграция и непрерывное развертывание)** — это набор практик и инструментов, нацеленных на безопасное хранение, использование, аудит и ротацию конфиденциальных данных (паролей, токенов, ключей API) на всех этапах жизненного цикла разработки программного обеспечения (SDLC — Software Development Life Cycle), от коммита кода до развертывания приложения.

**Секрет** — это любая конфиденциальная информация (пароли, API-ключи, токены доступа, TLS-сертификаты), компрометация которой может привести к несанкционированному доступу или нарушению безопасности системы.

## Основные концепции

### 1. Принцип минимальных привилегий (Least Privilege)

Украденный секрет опасен ровно настолько, насколько широки его права доступа. Главная проблема многих CI/CD-конвейеров — выдача прав «с запасом». Для минимизации ущерба следует разделять секреты по ролям и этапам пайплайна:

- **Задача сборки (build):** Компилирует код. В большинстве случаев ей не нужны никакие облачные учетные данные или секреты инфраструктуры.
- **Задача тестирования (test):** Работает с тестовыми данными. Должна иметь доступ только к тестовым базам данных и мок-сервисам. Продовые секреты здесь должны отсутствовать.
- **Задача развертывания (deploy):** Единственный этап, которому нужны продовые секреты, причем строго ограниченные только теми действиями, которые необходимы для доставки приложения.

Рекомендуется проводить регулярный аудит секретов и удалять неиспользуемые или избыточные доступы.

### 2. Предотвращение утечек: сканирование кода

Первая линия обороны — не допустить попадания секретов в систему контроля версий (Git). Для этого используются автоматизированные инструменты статического анализа, которые сканируют код и историю коммитов на наличие данных, похожих на секреты.

### 3. Безопасная доставка секретов

Хранение секретов в переменных окружения CI/CD (даже маскированных) является анти-паттерном. Такие переменные могут быть доступны администраторам платформы, случайно попасть в логи или быть доступными для всех процессов внутри задачи.

Современный подход — использование внешних специализированных хранилищ, таких как **HashiCorp Vault**, **AWS Secrets Manager** или **Google Secret Manager**.

Существует две модели получения секретов:

1. **Модель Push (Внедрение в начале):** Секреты извлекаются один раз в начале пайплайна и внедряются в окружение.
2. **Модель Pull (Получение Just-in-Time):** Задача запрашивает секреты в нужный момент. Это максимально безопасный подход, так как время жизни секрета в среде выполнения минимально.

### 4. Аутентификация без секрета (Secret-Zero)

Проблема модели Pull: как CI-задача может аутентифицироваться в хранилище, не имея изначально секрета? Эту проблему решает механизм **JWT (JSON Web Token)** аутентификации.

CI/CD платформа (например, GitLab) генерирует для каждой задачи уникальный короткоживущий токен. Внешнее хранилище (Vault) настраивается так, чтобы доверять этим токенам на основе атрибутов (проект, ветка).

### 5. Разделение хранения для разных окружений

- **Конфигурационные переменные (не секреты):** Флаги, URL-адреса, названия окружений можно хранить открыто в Git-репозитории или переменных CI/CD платформы.
- **Секретные переменные:** Пароли, токены, ключи API (Application Programming Interface) должны храниться исключительно во внешнем менеджере секретов. Доступ должен жестко ограничиваться через политики (Bound Claims), чтобы пайплайн для разработки (`dev`) не мог прочитать секреты промышленной среды (`prod`).

## Практические сценарии

### 1. Инструменты для работы с секретами: сканирование и очистка

**Trufflehog** и **Gitleaks** — популярные сканеры для поиска утечек в Git, Docker-образах и файловых системах.

**Что делать при утечке секрета:**

1. Немедленно отозвать (revoke/rotate) скомпрометированный ключ.
2. Использовать специализированные утилиты, такие как **BFG Repo-Cleaner**, для удаления следов секрета из истории коммитов.

**Пример использования Trufflehog в Docker:**

```bash
# Проверка текущего каталога
docker run --rm -it -v "$PWD:/pwd" ghcr.io/trufflesecurity/trufflehog:latest filesystem
# → Результат: вывод списка найденных секретов и их местоположения

# Проверка репозиториев организации на GitHub
docker run --rm -it -v "$PWD:/pwd" ghcr.io/trufflesecurity/trufflehog:latest github --org=your-org
# → Результат: анализ всех публичных и приватных репозиториев организации
```

### 2. Интеграция GitLab CI с HashiCorp Vault по JWT

Для максимальной защиты используются **Bound Claims** — условия, при которых токен считается валидным:

- `project_id` / `project_path`: Ограничение конкретным проектом.
- `ref_protected: true`: Секреты доступны только для защищенных (protected) веток.

Детальное руководство: [Интеграция GitLab CI с HashiCorp Vault в Kubernetes](../GitLab_CI/Tutorials/vault_kubernetes_integration.md).

### 3. Продвинутые стратегии защиты

1. **JWT + AppRole:** Аутентификация через JWT для получения доступа к AppRole, который дополнительно ограничен по **IP-адресам (Bound CIDRs — Classless Inter-Domain Routing)**.
2. **Response Wrapping (Обернутые токены):** Vault возвращает одноразовую «обертку» (wrapping token), которую можно развернуть только один раз.
3. **Эфемерные раннеры:** Использование Kubernetes для запуска каждой задачи в изолированном поде (Pod) с минимальным временем жизни.

### 4. Базовые практики: маскирование переменных

Если использование внешнего хранилища невозможно, следует использовать маскирование переменных в логах. Это базовый уровень защиты, не заменяющий менеджер секретов.

Подробное руководство: [Переменные и секреты в GitLab CI](../GitLab_CI/Concepts/gitlab_ci_variables_secrets.md).

### 5. Гибридная архитектура: локальный Vault и CI в облаке

При использовании облачных CI/CD (например, GitLab SaaS) и локального Vault:

- **Self-hosted Runners:** Агенты сборки устанавливаются внутри локальной сети. Это самый безопасный метод.
- **API Gateway / Reverse Proxy:** Публикация Vault через балансировщик с фильтрацией по IP и аутентификацией по OIDC (OpenID Connect).
