# Управление секретами в CI/CD

## Определения

**Управление секретами в CI/CD (Continuous Integration / Continuous Deployment)** — совокупность практик и инструментов для безопасного хранения, доставки, аудита и ротации конфиденциальных данных на всех этапах жизненного цикла разработки.

**Секрет** — любая чувствительная информация (пароли, API-ключи, токены, TLS-сертификаты), компрометация которой дает несанкционированный доступ к ресурсам.

**Secret-Zero (Проблема первого секрета)** — дилемма аутентификации, когда для получения секретов из хранилища (например, Vault) приложению или CI-задаче изначально требуется какой-то идентификатор или пароль.

**OIDC (OpenID Connect) / Workload Identity** — современный стандарт, позволяющий CI/CD-системе (GitLab, GitHub) подтверждать свою идентичность облачному провайдеру (AWS, GCP) без использования долгоживущих статических ключей.

## Базовые концепции

### Принцип минимальных привилегий (Least Privilege)

Украденный секрет опасен ровно настолько, насколько широки его права доступа. Главная проблема многих CI/CD-конвейеров — выдача прав «с запасом». Для минимизации ущерба следует разделять секреты по ролям и этапам пайплайна:

- **Задача сборки (build):** компилирует код. В большинстве случаев ей не нужны никакие облачные учетные данные или секреты инфраструктуры.
- **Задача тестирования (test):** работает с тестовыми данными. Должна иметь доступ только к тестовым базам данных и мок-сервисам. Продовые секреты здесь должны отсутствовать.
- **Задача развертывания (deploy):** единственный этап, которому нужны продовые секреты, причем строго ограниченные только теми действиями, которые необходимы для доставки приложения.

Рекомендуется проводить регулярный аудит секретов и удалять неиспользуемые или избыточные доступы.

### Предотвращение утечек: сканирование кода

Первая линия обороны — не допустить попадания секретов в систему контроля версий (Git). Для этого используются автоматизированные инструменты статического анализа, которые сканируют код и историю коммитов на наличие данных, похожих на секреты.

### Безопасная доставка секретов

Хранение секретов в переменных окружения CI/CD (даже маскированных) является антипаттерном. Такие переменные могут быть доступны администраторам платформы или случайно попасть в логи. См. **[Антипаттерны управления секретами](../../Vault/common_antipatterns.md)**.

Современный подход — использование внешних специализированных хранилищ (**HashiCorp Vault**, **AWS Secrets Manager**, **GCP Secret Manager**).

Существует три модели получения секретов:

1.  **Модель Push (Внедрение в начале):** секреты извлекаются один раз при старте задачи и записываются в `env` или временный файл.
2.  **Модель Pull (Just-in-Time):** задача сама запрашивает секреты через API хранилища в момент использования.
3.  **Workload Identity (Безсекретная аутентификация):** CI-задача использует временный **OIDC-токен** для обмена на временные права доступа у облачного провайдера. Это золотой стандарт безопасности 2024-2026 гг.

### Решение проблемы Secret-Zero через JWT/OIDC

Проблема: как CI-задача может авторизоваться в Vault, если у неё нет пароля?

Решение:
1.  CI-система (GitLab/GitHub) подписывает для каждой задачи временный **JWT-токен**.
2.  Задача отправляет этот токен в Vault.
3.  Vault проверяет подпись токена у CI-системы и сверяет атрибуты (название проекта, ветка).
4.  При совпадении критериев Vault выдает временный токен доступа.

### Разделение хранения для разных окружений

- **Конфигурационные переменные (не секреты):** флаги, URL-адреса, названия окружений можно хранить открыто в Git-репозитории или переменных CI/CD платформы.
- **Секретные переменные:** пароли, токены, ключи API (**Application Programming Interface**) должны храниться исключительно во внешнем менеджере секретов. Доступ должен жестко ограничиваться через политики (Bound Claims), чтобы пайплайн для разработки (`dev`) не мог прочитать секреты промышленной среды (`prod`).

## Практические сценарии

### Инструменты для работы с секретами: сканирование и очистка

**Trufflehog** и **Gitleaks** — популярные сканеры для поиска утечек в Git, Docker-образах и файловых системах.

**Shift Left: Pre-commit хуки:**
Используйте `gitleaks` или `detect-secrets` локально у разработчиков, чтобы предотвратить коммит секрета в Git.

```bash
# Пример использования Gitleaks локально
gitleaks detect --source . --verbose
# → Результат: блокировка коммита при обнаружении паттерна секрета
```

### Сценарий: GitLab + AWS через OIDC (Workload Identity)

Современный способ взаимодействия с AWS без хранения `AWS_ACCESS_KEY_ID` в секретах GitLab.

1.  **В AWS:** Создается Identity Provider для GitLab.
2.  **В AWS IAM Role:** Настраивается Trust Policy, разрешающая `sts:AssumeRoleWithWebIdentity` только для конкретного проекта GitLab.
3.  **В `.gitlab-ci.yml`:**

```yaml
deploy:
  image: amazon/aws-cli:latest
  id_tokens:
    MY_OIDC_TOKEN:
      aud: https://gitlab.example.com
  script:
    # Обмен JWT токена GitLab на временные credentials AWS
    - >
      export $(printf "AWS_ACCESS_KEY_ID=%s AWS_SECRET_ACCESS_KEY=%s AWS_SESSION_TOKEN=%s"
      $(aws sts assume-role-with-web-identity
      --role-arn arn:aws:iam::123456789:role/GitLabDeployRole
      --role-session-name "GitLabSession"
      --web-identity-token $MY_OIDC_TOKEN
      --query "Credentials.[AccessKeyId,SecretAccessKey,SessionToken]"
      --output text))
    - aws s3 ls # Теперь мы авторизованы без статических ключей
```

**Что делать при утечке секрета:**

1.  **Немедленный отзыв:** отозвать (revoke/rotate) скомпрометированный ключ или пароль.
2.  **Очистка истории:** использовать **BFG Repo-Cleaner** или `git filter-repo` для удаления следов секрета из истории коммитов Git.
3.  **Аудит:** проверить логи доступа в облаке/хранилище на предмет подозрительной активности за период утечки.

**Пример использования Trufflehog в Docker:**

```bash
# Сканирование текущего проекта (filesystem)
docker run --rm -it -v "$PWD:/pwd" ghcr.io/trufflesecurity/trufflehog:latest filesystem /pwd
# → Результат: вывод списка найденных секретов (пароли, приватные ключи)

# Сканирование организации на GitHub
docker run --rm -it ghcr.io/trufflesecurity/trufflehog:latest github --org=your-org
```

### Сценарий: GitLab + Vault (JWT аутентификация)

Для максимальной защиты используются **Bound Claims** — условия, при которых токен считается валидным:

- `project_id` / `project_path`: ограничение конкретным проектом.
- `ref_protected: true`: секреты доступны только для защищенных (protected) веток.

Детальное руководство: [Интеграция GitLab CI с HashiCorp Vault в Kubernetes](../GitLab_CI/Tutorials/vault_kubernetes_integration.md).

### Продвинутые стратегии защиты

1. **JWT + AppRole:** аутентификация через JWT для получения доступа к AppRole, который дополнительно ограничен по **IP-адресам (Bound CIDRs — Classless Inter-Domain Routing)**.
2. **Response Wrapping (обернутые токены):** Vault возвращает одноразовую «обертку» (wrapping token), которую можно развернуть только один раз.
3. **Эфемерные раннеры:** использование Kubernetes для запуска каждой задачи в изолированном поде (Pod) с минимальным временем жизни.

### Базовые практики: маскирование переменных

Если использование внешнего хранилища невозможно, следует использовать маскирование переменных в логах. Это базовый уровень защиты, не заменяющий менеджер секретов.

Подробное руководство: [Переменные и секреты в GitLab CI](../GitLab_CI/Concepts/gitlab_ci_variables_secrets.md).

### Гибридная архитектура: локальный Vault и CI в облаке

При использовании облачных CI/CD (например, GitLab SaaS) и локального Vault:

- **Self-hosted Runners:** агенты сборки устанавливаются внутри локальной сети. Это самый безопасный метод.
- **API Gateway / Reverse Proxy:** публикация Vault через балансировщик с фильтрацией по IP и аутентификацией по **OIDC (OpenID Connect)**.
