# Управление секретами в CI/CD

## Определения

**Управление секретами в CI/CD** — это набор практик и инструментов, нацеленных на безопасное хранение, использование, аудит и ротацию конфиденциальных данных (паролей, токенов, ключей API) на всех этапах жизненного цикла разработки, от коммита кода до развертывания приложения.

## Основные концепции

### 1. Принцип минимальных прав (Least Privilege)

Украденный секрет опасен ровно настолько, насколько широки его права доступа. Главная проблема многих CI/CD-пайплайнов — выдача прав "с запасом". Для минимизации ущерба при утечке следует разделять секреты по ролям и этапам пайплайна:

* **Задача сборки (build):** Компилирует код. В большинстве случаев ей не нужны никакие облачные учетные данные или секреты инфраструктуры.
* **Задача тестирования (test):** Работает с тестовыми данными. Должна иметь доступ только к тестовым базам данных и мок-сервисам. Продовые секреты здесь должны отсутствовать.
* **Задача деплоя (deploy):** Единственный этап, которому нужны продовые секреты, причем строго ограниченные только теми действиями, которые необходимы для доставки приложения.

Рекомендуется раз в квартал проводить аудит секретов и удалять неиспользуемые или избыточные доступы.

### 2. Предотвращение утечек: Сканирование кода

Первая и самая важная линия обороны — не допустить попадания секретов в систему контроля версий (Git). Для этого используются автоматизированные инструменты статического анализа, которые сканируют код и историю коммитов на наличие данных, похожих на секреты.

### 3. Безопасная доставка секретов

Хранение секретов в переменных окружения CI/CD (даже маскированных) является анти-паттерном. Такие переменные могут быть доступны администраторам CI/CD платформы, случайно попасть в логи или быть доступными для всех процессов внутри задачи, что расширяет поверхность атаки.

Современный подход — использование внешних, специализированных хранилищ, таких как **HashiCorp Vault**, **AWS Secrets Manager** или **Google Secret Manager**.

Существует две модели получения секретов из хранилища:

1. **"Push" Модель (Внедрение в начале):** Секреты извлекаются один раз в начале пайплайна и внедряются в окружение. Это проще в реализации, но секреты существуют дольше, увеличивая окно для компрометации.
2. **"Pull" Модель (Получение "Just-in-Time"):** Задача в пайплайне сама, в нужный момент, запрашивает только необходимые ей секреты. Это максимально безопасный подход, так как время жизни секрета минимально.

### 4. Аутентификация без секрета ("Secret-Zero")

"Pull" модель поднимает вопрос: как CI-задача может аутентифицироваться в хранилище, не имея изначально секрета для доступа? Эту проблему решает механизм **JWT-аутентификации**.

CI/CD платформа (например, GitLab) генерирует для каждой задачи уникальный, короткоживущий **JWT-токен**. Внешнее хранилище (Vault) настраивается так, чтобы доверять этим токенам. Роли в хранилище связывают атрибуты токена (проект, ветка) с политиками доступа, позволяя CI-задаче получить временный доступ только к разрешенным секретам.

## Практические сценарии

### 1. Инструменты для работы с секретами: Сканирование и Очистка

**Trufflehog** и **Gitleaks** — популярные сканеры, которые легко интегрируются в CI/CD пайплайны для автоматической проверки коммитов и pull-request'ов.

* **Trufflehog**: универсальный инструмент для поиска утечек в Git, файловых системах, Docker-образах и других источниках.
* **Gitleaks**: легковесный инструмент, идеально подходящий для быстрой проверки именно Git-репозиториев (например, в GitLab CI можно использовать готовый шаблон `Secret-Detection.gitlab-ci.yml`).

**Что делать при утечке секрета:**
Если секрет попал в историю Git, простого коммита с его удалением недостаточно. Необходимо:
1. **Немедленно отозвать (revoke/rotate)** скомпрометированный ключ на стороне провайдера.
2. Использовать специализированные утилиты, такие как **BFG Repo-Cleaner**, для глубокой очистки и перезаписи истории коммитов в репозитории, чтобы полностью удалить следы секрета.

**Пример использования Trufflehog в Docker:**

```bash
# Проверка текущего каталога
docker run --rm -it -v "$PWD:/pwd" ghcr.io/trufflesecurity/trufflehog:latest filesystem

# Проверка репозиториев организации на GitHub
docker run --rm -it -v "$PWD:/pwd" ghcr.io/trufflesecurity/trufflehog:latest github --org=trufflesecurity
```

### 2. Интеграция GitLab CI с HashiCorp Vault по JWT

Это реализация "Pull" модели с подходом "Secret-Zero".

**Принцип работы:**

1. **Генерация JWT:** GitLab генерирует уникальный JWT-токен (`CI_JOB_JWT_V2_TOKEN`) для каждой CI-задачи.
2. **Настройка доверия:** Vault настраивается для доверия JWT-токенам от инстанса GitLab.
3. **Создание ролей:** Роли связывают атрибуты JWT (claims) с политиками доступа.

**Ограничение доступа через Bound Claims:**
Для максимальной защиты в Vault следует настраивать **Bound Claims** — условия, при которых токен считается валидным:
* `project_id` / `project_path`: Ограничение доступа конкретным проектом.
* `namespace_id` / `namespace_path`: Ограничение группой проектов.
* `user_login` / `user_email`: Доступ разрешен только если пайплайн запущен конкретным пользователем.
* `ref`: Привязка к ветке или тегу.
* `ref_protected`: Секреты доступны только для **защищенных** (protected) веток/тегов.
* `environment_protected`: Доступ только для защищенных окружений.

**Рекомендация:** Всегда используйте `ref_protected: true` для доступа к продуктовым секретам, чтобы предотвратить их кражу через произвольные feature-ветки.

Детальное пошаговое руководство доступно в документе **[Интеграция GitLab CI с HashiCorp Vault в Kubernetes](../GitLab_CI/Tutorials/vault_kubernetes_integration.md)**.

### 3. Продвинутые стратегии: Комбинированный подход и Обернутые токены

Для высоконагруженных или критически важных систем используется многослойная защита:

1. **JWT + AppRole:**
   - CI-задача аутентифицируется через JWT и получает `RoleID` для AppRole.
   - Затем выполняется AppRole-логин, который дополнительно ограничен по **IP-адресам (Bound CIDRs)**. Это гарантирует, что даже украденный JWT-токен бесполезен вне доверенной сети раннеров.
2. **Response Wrapping (Обернутые токены):**
   - Vault возвращает не сам секрет или токен, а "обертку" (wrapping token).
   - Эту обертку можно "развернуть" (`unwrap`) **строго один раз**.
   - Если атакующий перехватил и развернул токен первым, легитимная задача получит ошибку при попытке `unwrap`, что служит мгновенным сигналом компрометации.
3. **Эфемерные раннеры (Kubernetes Executor):**
   - Использование Kubernetes для запуска каждой задачи в изолированном поде. Это минимизирует время жизни среды выполнения и предотвращает атаки типа "сосед по раннеру".

### 4. Базовые практики: Маскирование переменных

Если использование внешнего хранилища невозможно, в качестве временной меры следует использовать маскирование переменных в логах CI/CD.

> **Важно:** Маскирование — это базовый уровень защиты, а не полноценное решение. Секреты всё ещё существуют в окружении задачи и могут быть доступны администраторам CI/CD-платформы.

**Требования GitLab для маскирования:**

* Одна строка без пробелов
* Длина от 8 символов
* Символы из набора Base64 (RFC4648)

Подробное руководство по управлению переменными и секретами в GitLab CI доступно в документе **[Переменные и секреты в GitLab CI](../GitLab_CI/Concepts/gitlab_ci_variables_secrets.md)**.
