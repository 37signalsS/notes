# Атаки на CI/CD

## Определения

**Атаки на CI/CD** — класс кибератак, нацеленных на инфраструктуру непрерывной интеграции и доставки (системы контроля версий, пайплайны, билд-серверы и раннеры). Целью является получение несанкционированного доступа к исходному коду, инфраструктуре (через кражу секретов) или внедрение вредоносного кода в артефакты сборки (Supply Chain Attack).

**Pipeline Poisoning (Отравление пайплайна)** — внедрение злоумышленником вредоносных команд в конфигурацию или скрипты пайплайна, которые будут выполнены CI/CD-системой (например, раннером GitLab или агентом Jenkins).

**OIDC (OpenID Connect)** — механизм аутентификации, позволяющий CI/CD-системам получать краткосрочные токены доступа к облачным провайдерам (AWS, Azure, GCP) без хранения долгоживущих секретов.

Подробные определения **Supply Chain Attack**, **SLSA** и **SBOM** см. в [Обзоре безопасности цепочки поставок](../../Security/Supply_Chain_Security/overview.md).

## Базовые концепции

Безопасность CI/CD базируется на минимизации векторов атак, описанных в **OWASP Top 10 CI/CD Security Risks (2022/2023)**. Основные направления защиты включают:

1. Недостаточная гигиена секретов (Secret Hygiene).
2. Обход механизмов контроля потока (Bypassing Flow Control Mechanisms).
3. Прямое отравление пайплайна (Direct Pipeline Poison Execution).
4. Непрямое отравление пайплайна (Indirect Pipeline Poison Execution).
5. Отравление пайплайна через Pull Request (Poisoned Pipeline Execution, PPE).
6. Чрезмерные привилегии конвейера (Pipeline-Based Access Control — PBAC).
7. Атаки на раннеры: побег, отравление кэша и кража токенов.
8. Атаки через цепочку зависимостей (Dependency Chain Abuse).
9. Компрометация пользователей платформы.

## Практические сценарии

### 1. Утечка секретов в истории Git

**Вектор атаки:** Разработчики могут случайно закоммитить чувствительные данные (токены, пароли, ключи) в репозиторий. Даже если секрет был удален в последующих коммитах, он остается в истории Git.
**Механизм:** Злоумышленник использует утилиты вроде `trufflehog` для сканирования истории репозитория, находит хэш уязвимого коммита, выполняет `git checkout <hash>` и извлекает пароль из восстановленного файла.
**Защита:** 
- Использование внешних систем управления секретами (Vault).
- **OIDC:** Переход на краткосрочные токены вместо хранения статических ключей (AWS/GCP) в секретах репозитория.
- **Pre-commit hooks:** Блокировка коммитов с секретами на стороне разработчика (gitleaks, detect-secrets).
- См. [Управление секретами](./secrets_management.md).

### 2. Обход механизмов контроля потока

**Вектор атаки:** Пайплайн может содержать шаги проверки безопасности (например, SAST, сканирование IaC с помощью Checkov), которые блокируют сборку при нахождении проблем. Злоумышленник может отключить или обойти эти проверки.
**Механизм:**

- **Файлы исключений:** Атакующий создает в репозитории конфигурационный файл для сканера безопасности (например, `.checkov.yml` или `.gitleaksignore`), в котором прописывает разрешение на игнорирование ошибок (например, `soft_fail: true` или добавляет секретный ключ в исключения). В результате сканер отработает, но пайплайн не упадет, пропустив вредоносный код или секрет в прод.
- **Переопределение локальных шаблонов:** В системах вроде GitLab CI локальные шаблоны имеют приоритет. Переопределив скрипт сканера локально (например, прописав `exit 0`), можно успешно завершить джобу без реальных проверок.
- **Использование after_script:** Перенос вредоносной логики в `after_script` позволяет выполнить её даже при падении основного скрипта проверки.
- **Модификация конфигурации раннера:** При возможности влияния на `config.toml` раннера атакующий может полностью пропустить выполнение определенных стейджей безопасности.

### 3. Прямое отравление пайплайна

**Вектор атаки:** Злоумышленник, имеющий доступ на запись в репозиторий, напрямую модифицирует конфигурационный файл CI/CD (например, `Jenkinsfile` или `.gitlab-ci.yml`).
**Механизм:** Атакующий добавляет шаг, выводящий переменные окружения раннера. Если система CI/CD маскирует секреты в логах (заменяет их звездочками), злоумышленник может обойти это ограничение, закодировав значение: `echo $SECRET_TOKEN | base64`. Из логов извлекается base64-строка и декодируется на стороне злоумышленника.
**Защита:** Защита основных веток (Protected Branches), обязательное ревью кода (Code Review), ограничение доступа к конфигурациям CI/CD.

### 4. Непрямое отравление пайплайна

**Вектор атаки:** Если конфигурация CI/CD заблокирована для редактирования, злоумышленник ищет скрипты, которые пайплайн вызывает во время своей работы (например, `Makefile`, `build.sh`, скрипты тестов).
**Механизм:** Атакующий вносит вредоносные изменения в `Makefile` (например, добавляет команду отправки токена по сети или вывода его в `base64`). При запуске легитимного, неизмененного пайплайна CI-сервер выполнит зараженный `Makefile`.

### 5. Отравление пайплайна через Pull Request (PPE)

**Вектор атаки:** Атака на open-source или внутренние проекты, где CI/CD настроен на автоматический запуск при создании Pull Request/Merge Request.

**Механизмы:**

1. **Базовый PPE:** Злоумышленник делает форк репозитория, добавляет вредоносный код в скрипты и создает Pull Request. Если CI-система запускает пайплайн для форков с доступом к секретам, код похищает их.
2. **GitHub Actions — `pull_request_target`:** Триггер `pull_request_target` запускает пайплайн в контексте **базового репозитория** с доступом к секретам и привилегированным `GITHUB_TOKEN`. Если пайплайн выполняет `checkout` кода из PR (`ref: ${{ github.event.pull_request.head.sha }}`) и затем запускает скрипты из этого кода (например, `npm install` или `make`), злоумышленник получает полный доступ к секретам репозитория.
3. **Атака класса "Cordyceps" (Cross-Workflow Escalation):** Эксплуатация взаимодействия нескольких пайплайнов. Низкопривилегированный пайплайн (на `pull_request`) записывает вредоносные данные в артефакт. Второй, высокопривилегированный пайплайн (на `workflow_run` или `pull_request_target`), считывает этот артефакт и выполняет его содержимое, обходя статические сканеры безопасности.

**Защита:**

- **GitHub:** Никогда не делать `checkout` и запуск кода из PR внутри `pull_request_target`. Для тестов использовать только `pull_request`.
- **Одобрение:** Настройка "Require approval for all outside collaborators".
- **Изоляция:** Использование Protected Runners и Protected Variables. Изолируйте CI для PR от продуктивных секретов через использование OIDC.

### 6. Чрезмерные привилегии конвейера

**Вектор атаки:** Раннеры или агенты CI/CD имеют избыточные права в системе или сети (недостаточное управление правами, уязвимости PBAC).
**Механизм:** Злоумышленник, получивший возможность выполнить код на раннере (через Poisoning), может получить доступ к системным файлам хоста:

- Чтение конфигурации: Чтение файлов вроде `/var/jenkins_home/secrets/...` или `/etc/shadow`, если раннер выполняется от привилегированного пользователя (например, при регистрации раннера через `sudo`).
- **Скрытие активности (Reverse Shell через cron):** Для закрепления на скомпрометированном раннере атакующий может прописать запуск reverse shell в системный `cron` хоста (с планированием отложенного запуска или в фоне). Джоба при этом быстро завершается (exit 0), не привлекая внимания, а доступ к системе сохраняется.
**Защита:** Принцип наименьших привилегий, запуск раннеров в изолированных непривилегированных контейнерах без маппинга чувствительных директорий хоста, строгий контроль прав пользователя, от которого работает агент.

### 7. Атака на раннеры: побег, отравление кэша и кража токенов

**Вектор атаки:** Компрометация хостовой машины раннера или процесса сборки через уязвимости конфигурации.

**Механизм:**

1. **Побег (Escape):** Если раннер использует `docker.sock`, запущен в привилегированном режиме (`privileged: true`) или имеет опасные capability (например, через блочные устройства), злоумышленник может выполнить побег из контейнера на хостовую ОС раннера. Из хостовой системы (например, через `docker ps`) можно увидеть другие контейнеры-джобы и выполнить код внутри них (`docker exec`).
2. **Сбор токенов и секретов (Harvesting):** Оказавшись на хосте, атакующий запускает сканирование:
   - Переменных окружения чужих джоб через `/proc`.
   - Поиск SSH-ключей (`grep -r "BEGIN .* PRIVATE KEY" /`).
   - Поиск кредов от Docker Registry (в файлах вроде `~/.docker/config.json`, где хранятся base64 токены). Украденные токены можно использовать для подмены (отравления) образов (Supply Chain).

   ```bash
   # Пример концептуального скрипта для перехвата токенов на хосте
   while true; do 
     ps auxww | grep -i "JWT\|VAULT_TOKEN" >> /tmp/stolen_tokens.log
     sleep 0.1
   done
   ```

3. **Отравление кэша (Cache Poisoning):** Атакующий в своей джобе собирает модифицированный бинарник или зависимость и кладет его в общий кэш CI. При запуске основной джобы (например, в ветке `main`) легитимный процесс берет из кэша зараженный файл, который в итоге попадает на продакшен.
4. **Спуфинг раннера (Runner Spoofing):** Вместо попытки украсть токены с работающего раннера, атакующий перехватывает "окно" поллинга, представляясь легитимным раннером для CI-серверу (используя украденный токен регистрации). Задачи назначаются поддельному раннеру, который просто собирает все секреты, переменные и токены, не выполняя саму джобу.

**Последствия:** Масштабная компрометация инфраструктуры (дефейс сайтов, подмена артефактов, кража данных пользователей) через легитимные пайплайны.

**Защита:**

- **Эфемерная инфраструктура:** Использование `Kubernetes Executor` в GitLab, где для каждой задачи создается новый изолированный под, который уничтожается сразу после завершения.
- **Отказ от Docker-в-Docker (DinD):** Избегание проброса `docker.sock` и использования привилегированных контейнеров.
- **Изоляция окружений и кэшей:** Раздельные раннеры для Protected и не-Protected веток (в том числе физическое разделение нод). Использование отдельных кэшей.
- **Hardening раннеров:** Использование специализированных рантаймов (gVisor, Kata Containers), профилирование доступа (SELinux, AppArmor). Выполнение джоб от пользователя `nobody` может усложнить атаки (в частности побег), но не является «серебряной пулей».

### 8. Атака через цепочку зависимостей

**Вектор атаки:** Компрометация внешнего или внутреннего пакета либо стороннего экшена/шаблона, используемого в пайплайне.

**Механизмы:**

1. **Dependency Confusion:** Злоумышленник публикует пакет с именем внутреннего приватного пакета и завышенной версией в публичный реестр. Пакетный менеджер скачивает вредоносный пакет из публичного источника.
2. **Компрометация сторонних экшенов (GitHub Actions):** Злоумышленник получает доступ к популярному экшену и обновляет тег версии (например, `v4`) на вредоносный коммит. Все пайплайны, использующие `uses: actions/checkout@v4`, начинают выполнять вредоносный код.
3. **Poisoned Artifacts:** Подмена артефактов в промежуточном хранилище или кэше.

**Защита:**

- **SHA Pinning:** В GitHub Actions фиксировать экшены не по тегам, а по полному SHA коммита (например, `uses: actions/checkout@8ade...`). Теги мутабельны, SHA — нет.
- **Приватные реестры:** Использование Nexus/Artifactory с жестким приоритетом внутреннего реестра и зеркалированием.
- **Целостность:** Фиксация версий зависимостей (lock-файлы) по хэшам, использование SBOM и проверка соответствия уровням SLSA.

### 9. Компрометация пользователей платформы

В зависимости от роли скомпрометированного пользователя векторы атак и методы защиты различаются:

1. **Обычный разработчик (Developer):**
   - **Вектор атаки:** Внедрение вредоносного кода в ветку или Merge Request.
   - **Защита:** Обязательное ревью кода (Code Review) и использование механизма **Code Owners**. Если платформа не поддерживает `Code Owners` (например, бесплатная версия GitLab), можно реализовать проверку через CI: задача парсит список необходимых аппруверов из файла в репозитории, запрашивает API платформы (с токеном робота) и сверяет количество фактических аппруверов. Пайплайн падает, если аппрувов недостаточно, блокируя Merge.

2. **Привилегированный пользователь (Maintainer / Owner):**
   - **Вектор атаки:** Может изменить настройки проекта, отключить проверки пайплайнов, переопределить переменные или подменить раннеры на вредоносные (всегда возвращающие код 0).
   - **Защита:** Лишение разработчиков прав `Maintainer` и вынос рутинных задач (создание репозиториев, настройка прав) на внутренний портал самообслуживания (Self-Service). Чтобы проверки пайплайнов нельзя было обойти, конфигурация безопасности должна инклюдиться из **удаленного репозитория**, недоступного для редактирования (`include: remote`). Удаленный пайплайн может инклюдить локальный пайплайн разработчиков, встраивая задачи проверки безопасности так, чтобы их нельзя было переопределить. Также целесообразно отстреливать результаты проверок (сканеров) во внешнее хранилище (например, S3) и проверять их наличие перед деплоем (Особое мнение / Третья сторона).

3. **Администратор платформы:**
   - **Вектор атаки:** Имеет полный контроль, может выпускать токены на любых пользователей, заливать произвольный код или имперсонировать пользователей в интерфейсе.
   - **Защита:**
     - **Проверка подлинности коммитов:** Использование подписей коммитов, но не GPG (администратор может добавить свой публичный ключ в профиль пользователя), а **x509 сертификатов** с построением внутренней [PKI](../../Security/Concepts/pki_overview.md). Проверка подписи реализуется не средствами CI, а через серверные Git-хуки (например, `pre-receive` hook на сервере GitLab), которые валидируют коммиты по корневому сертификату до их попадания в репозиторий.
     - **Разделение CI и CD:** Изъятие деплойных прав и токенов из CI-системы. CI отвечает только за сборку артефактов и тесты, а деплоем (CD) занимается внешняя независимая система (например, [Ansible Semaphore](../../Ansible/ansible_semaphore.md)), которая пуллит артефакты и самостоятельно валидирует их (через проверку подписи коммитов) перед выкаткой.
