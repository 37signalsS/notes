# Атаки на CI/CD

## Определения

**Атаки на CI/CD** — класс кибератак, нацеленных на инфраструктуру непрерывной интеграции и доставки (системы контроля версий, пайплайны, билд-серверы и раннеры). Целью является получение несанкционированного доступа к исходному коду, инфраструктуре (через кражу секретов) или внедрение вредоносного кода в артефакты сборки (**Software Supply Chain Attack**).

**Pipeline Poisoning (Отравление пайплайна)** — внедрение злоумышленником вредоносных команд в конфигурацию или скрипты пайплайна, которые будут выполнены CI/CD-системой (например, раннером GitLab или агентом Jenkins). Различают:
*   **Direct PPE (Прямое PPE):** непосредственная модификация файлов конфигурации пайплайна (`.gitlab-ci.yml`, `Jenkinsfile`, воркфлоу GitHub Actions).
*   **Indirect PPE (Непрямое PPE):** модификация внешних скриптов, библиотек или инструментов, которые вызываются пайплайном в процессе работы (например, `Makefile`, `setup.py`, `pom.xml`, скрипты тестирования).

**Cordyceps (Квази-паразитическая атака)** — класс архитектурных уязвимостей (**Cross-Workflow Escalation**), при которых вредоносный ввод из низкопривилегированного процесса (например, линтера в Pull Request) передается в высокопривилегированный процесс (deployment workflow), позволяя захватить секреты организации. Реализуется через «отравление» общих артефактов, кэша или манипуляцию метаданными (названия веток, комментарии), которые считываются привилегированными задачами.

**NHI (Non-Human Identities)** — нечеловеческие личности (сервисные аккаунты, ключи приложений, идентичности рабочих нагрузок, токены пайплайнов), являющиеся основной целью атак в 2026 году. Из-за их широких привилегий и частого отсутствия MFA они позволяют злоумышленникам действовать скрытно («бесшумные атаки») под видом легитимной автоматизации.

**OIDC (OpenID Connect) / Workload Identity** — современный механизм аутентификации, позволяющий CI/CD-системам получать краткосрочные токены доступа к внутренним системам (реестрам артефактов, менеджерам секретов, системам развертывания) на основе доверия к издателю (IdP) без хранения долгоживущих секретов.

**ASPM (Application Security Posture Management)** — системы управления состоянием безопасности приложений, которые агрегируют данные от всех сканеров (SAST, SCA, DAST) в CI/CD для выявления сложных цепочек атак и приоритизации рисков.

**VEX (Vulnerability Exploitability eXchange)** — стандарт обмена данными о реальной эксплуатируемости уязвимостей. Позволяет подавлять ложные срабатывания сканеров в пайплайне, если уязвимый компонент не используется в атакуемом пути.

**SLSA (Supply-chain Levels for Software Artifacts)** — фреймворк безопасности цепочки поставок ПО (стабильная редакция **v1.2**, выпущена в ноябре 2025 года). Разделяет требования на **Build Track** (защита сборки, уровни L0–L3) и **Source Track** (защита кода, уровни L1–L4). v1.2 определяет уровни L0–L3 Build Track и вводит генерацию аттестаций (**Provenance**) для подтверждения целостности и происхождения артефактов.

**Граница доверия (Trust Boundary)** — концептуальная линия, пересекая которую данные переходят из доверенной зоны в недоверенную или наоборот. В CI/CD границами доверия являются: рабочая станция разработчика → система контроля версий (SCM) → CI-сервер → раннер (агент сборки) → реестр артефактов → целевая система выкладки. Каждое пересечение — потенциальная точка закрепления (pivot) злоумышленника.

**Артефакт сборки (Build Artifact)** — любой файл, пакет или образ, произведённый пайплайном (бинарник, tarball, OCI-образ, Helm-чарт, SBOM). Именно артефакты, а не исходный код, попадают в production, поэтому их целостность критична.

**Аттестация / Provenance** — подписанное заявление о том, как, где и из какого исходного кода был собран артефакт (включает хэш исходников, идентификатор билд-системы, зависимости). Позволяет потребителю проверить, что артефакт не был изменён после сборки.

**Вебхук (Webhook)** — HTTP-уведомление, которым SCM (GitLab, GitHub, Bitbucket) сообщает CI-серверу о событии (push, PR). Подпись вебхука обычно строится на HMAC-SHA256 с общим секретом; его отсутствие или слабая проверка открывают вектор подделки событий.

**Typosquatting (Тайпосквоттинг)** — публикация вредоносного пакета/образа с именем, отличающимся от легитимного на одну-две буквы (например, `reqeusts` вместо `requests`), в расчёте на опечатку при установке.

**SSRF (Server-Side Request Forgery)** — атака, при которой злоумышленник заставляет сервер выполнить произвольный сетевой запрос от своего имени, например, к внутреннему API управления или к endpoint'у вебхука CI-сервера.

Подробные определения **Supply Chain Attack**, **SBOM** и уровни **SLSA** см. в [Обзоре безопасности цепочки поставок](../../Security/Supply_Chain_Security/overview.md).

## Базовые концепции

Безопасность CI/CD базируется на концепции **Zero Trust CI/CD** и минимизации векторов атак, описанных в **OWASP Top 10 CI/CD Security Risks (v1.0, октябрь 2022; коды CICD-SEC-1 … CICD-SEC-10)**, а также в общем **OWASP Top 10 Web Application Security Risks (2021)** — в частности категории **A08:2021 – Software and Data Integrity Failures** (в черновике OWASP Top 10 2026 ей соответствует выделенная категория **A03 – Software Supply Chain Failures**). Основные направления защиты включают:

1.  **Недостаточная гигиена секретов (Secret Hygiene):** Использование статических секретов вместо Vault/OIDC.
2.  **Обход механизмов контроля потока (Bypassing Flow Control):** Пуш в обход проверок или Code Owners.
3.  **Прямое отравление пайплайна (Direct PPE):** Изменение YAML-конфигов.
4.  **Непрямое отравление пайплайна (Indirect PPE):** Изменение вспомогательных скриптов (Makefile).
5.  **PPE через Pull Request (PPE):** Эксплуатация джоб, запускаемых на внешнем коде.
6.  **Чрезмерные привилегии конвейера (PBAC):** Избыточные права раннеров.
7.  **Атаки на инфраструктуру раннеров:** Побег из контейнера, отравление кэша и кража токенов.
8.  **Атаки через цепочку зависимостей (Dependency Chain Abuse):** Dependency Confusion, компрометация экшенов.
 9.  **Недостаточная проверка целостности артефактов:** Отсутствие подписей и аттестаций.
 10. **Компрометация пользователей платформы:** Захват аккаунтов с SSO.
 11. **Shadow CI/CD:** Использование неконтролируемых сторонних систем автоматизации.

Сопоставление с классификацией OWASP (для приоритезации при реализации контролей):

| 1 | Утечка секретов / слабая гигиена | CICD-SEC-6 Insufficient Credential Hygiene |

| 3, 4, 5 | Отравление пайплайна (PPE) | CICD-SEC-4 Poisoned Pipeline Execution |
| 6 | Чрезмерные привилегии (PBAC) | CICD-SEC-5 Insufficient PBAC |

### Модель угроз и границы доверия CI/CD

Чтобы понять, почему CI/CD является высокоценной целью, необходимо разобрать его архитектуру с точки зрения доверия.

**Почему CI/CD атакуют:**
*   **Единая точка доставки.** Пайплайн — единственный легитимный путь кода в production. Компрометация любого звена даёт возможность внедрить бэкдор, который пройдёт все проверки как «свой».
*   **Концентрация секретов.** На раннерах и в CI-переменных сосредоточены ключи подписи, токены реестров, доступы к инфраструктуре, пароли БД.
*   **Имплицитное доверие инфраструктуры.** Сборочный узел по определению имеет право выполнять код и часто — развёртывать артефакты; это доверие злоумышленник перехватывает.

**Карта границ доверия (поток данных и прав):**

```
[Разработчик] --(git push)--> [SCM: GitLab/GitHub] --(webhook/API)-->
  [CI-сервер: Jenkins/GitLab CI] --(назначает задачу)--> [Раннер/Агент]
  --> [Сборка артефакта] --> [Реестр артефактов] --(CD/deploy)-->
  [Целевая инфраструктура: серверы, кластеры]
```

Недоверенный ввод (untrusted input) поступает на каждом шаге:
*   Код из PR/MR и форков — потенциально враждебен.
*   Зависимости из публичных/внутренних реестров — потенциально скомпрометированы.
*   Webhook payload от SCM — может быть подделан без проверки подписи.
*   Сторонние экшены/плагины и шаблоны — выполняются с правами пайплайна.

**Базовый принцип защиты:** любой код, данные и события, обрабатываемые пайплайном, следует считать враждебными до доказательства обратного. Отсюда вытекают три системных требования:
1.  **Изоляция** — чужой код не должен иметь доступа к секретам, хосту раннера и смежным джобам.
2.  **Минимальные привилегии (Least Privilege)** — раннер и сервисные аккаунты получают только те права, что нужны для конкретной задачи.
3.  **Целостность и верификация** — конфигурации, зависимости и артефакты проверяются по подписям/хэшам, а не по доверию к источнику.

## Практические сценарии

### 1. Утечка секретов и обход систем сканирования

**Вектор атаки:** Разработчики могут случайно закоммитить чувствительные данные (токены, пароли, ключи) в репозиторий. Даже при наличии **Push Protection** (функция блокировки пуша с секретами в GitHub/GitLab), злоумышленники ищут способы обхода.

**Механизмы:**
- **История Git:** Даже если секрет был удален в последующих коммитах, он остается в истории. Злоумышленник использует `trufflehog` или `gitleaks` для сканирования всей истории:
  ```bash
  trufflehog git file:///path/to/repo --since-commit=HEAD~50
  # → Находит скомпрометированный API-ключ в диффе коммита
  ```
- **Обход Push Protection:** Маскирование секрета (например, разбиение ключа на части) или использование `--no-verify` (если проверка только на стороне клиента).
- **Восстановление через хэш:** Злоумышленник находит хэш уязвимого коммита, выполняет `git checkout <hash>` и извлекает пароль из восстановленного файла.
- **Утечка через логи:** Если секрет не маскирован (masked) в CI, он попадает в публичные логи сборки.

**Предварительные условия (защита):** Установлен и настроен серверный сканер (`gitleaks` как pre-receive hook или в отдельной джобе), секреты вынесены во внешний менеджер (Vault).

**Защита:** 
- Использование внешних систем управления секретами (**HashiCorp Vault**).
- **OIDC:** Переход на краткосрочные токены (Workload Identity) вместо хранения статических ключей в секретах репозитория.
- **Server-side scanning:** Обязательная проверка на стороне Git-сервера, которую невозможно отключить локально.
- **GitHub Environments:** Ограничение доступа к секретам только для конкретных сред с обязательным аппрувом (Environment Protection Rules).

**Проверка (Validation):** Убедитесь, что push с секретом реально блокируется:
```bash
echo "SECRET_ACCESS_KEY=AKIAEXAMPLE" > leaked.txt
git add leaked.txt && git commit -m "test" && git push
# → Ожидается: remote rejected (secret scanning policy)
```
**Типичные ошибки (Устранение неисправностей):**
- Сканер ругается на ложные срабатывания (test-данные) → добавляйте точечные исключения через `.gitleaks.toml` (allowlist), а не отключайте сканер целиком.
- Секрет уже попал в историю → смените его **до** очистки истории (`git filter-repo`/`BFG`), так как удаление из истории не отзывает скомпрометированный ключ.

Подробнее о моделях доставки секретов — в [Управлении секретами в CI/CD](./secrets_management.md).

### 2. Обход механизмов контроля потока (Flow Control)

**Вектор атаки:** Пайплайн содержит шаги проверки безопасности (SAST, сканирование IaC), которые блокируют сборку. Злоумышленник пытается отключить или обойти эти проверки.

**Механизмы:**
- **Файлы исключений:** Атакующий создает в репозитории конфигурационный файл для сканера безопасности (например, `.checkov.yml` или `.gitleaksignore`), в котором прописывает разрешение на игнорирование ошибок (например, `soft_fail: true` или добавляет секретный ключ в исключения).
- **Переопределение локальных шаблонов:** В системах вроде GitLab CI локальные определения джоб имеют приоритет. Прописав `script: exit 0` для джобы безопасности, можно успешно пройти пайплайн без реальных проверок.
- **Использование after_script:** Перенос вредоносной логики в `after_script`, который выполняется даже при падении основного скрипта проверки.
- **Модификация конфигурации раннера:** При возможности влияния на `config.toml` раннера атакующий может полностью пропустить выполнение определенных стейджей безопасности.
- **Манипуляция CODEOWNERS:** Пуш кода в директории, не требующие аппрува от ИБ-команды.

**Защита:**
- **Required Status Checks:** Блокировка Merge Request, если обязательные сканеры не завершились успешно.
- **Immutable Includes:** Подключение шаблонов безопасности из удаленных защищенных репозиториев (`include: remote`) с фиксацией по SHA коммита.

**Проверка (Validation):** Попытайтесь слить MR, в котором `.gitleaksignore` разрешает всё (`*`), — он должен быть отклонён политикой required status checks, а не пройти.

### 3. Прямое отравление пайплайна (Direct PPE)

**Вектор атаки:** Злоумышленник, имеющий доступ на запись в репозиторий, напрямую модифицирует конфигурационный файл CI/CD (например, `Jenkinsfile` или `.gitlab-ci.yml`).

**Механизм:** Атакующий добавляет шаг, выводящий переменные окружения раннера. Если система CI/CD маскирует секреты (заменяет их звездочками), злоумышленник может обойти это ограничение, закодировав значение: `echo $SECRET_TOKEN | base64`. Из логов извлекается base64-строка и декодируется на стороне злоумышленника.

**Предварительные условия:** У атакующего есть право push в ветку с конфигом CI (защита веток отсутствует или обойдена).

**Защита:** Защита основных веток (Protected Branches), обязательное ревью кода (Code Review), ограничение доступа к конфигурациям CI/CD.

**Проверка (Validation):**
```bash
echo $SECRET_TOKEN | base64
# → происходит вывод вида: dGVzdC1zZWNyZXQtdmFsdWU=
# на стороне злоумышленника: echo 'dGVzdC1zZWNyZXQtdmFsdWU=' | base64 -d
```

### 4. Непрямое отравление пайплайна (Indirect PPE)

**Вектор атаки:** Если конфигурация CI/CD заблокирована для редактирования, злоумышленник ищет скрипты, которые пайплайн вызывает во время своей работы (например, `Makefile`, `build.sh`, `setup.py`, тесты).

**Механизм:** Атакующий вносит вредоносные изменения в `Makefile` (например, добавляет команду отправки токена по сети или вывода его в `base64`). При запуске легитимного, неизмененного пайплайна CI-сервер выполнит зараженный `Makefile`.

**Защита:** Песочница для выполнения скриптов, запрет на выполнение внешних скриптов с полными правами раннера, проверка целостности вызываемых скриптов.

**Проверка (Validation):** Контрольная сумма вызываемых скриптов фиксируется и сверяется перед запуском:
```bash
sha256sum Makefile build.sh > /var/ci/expected.sha256
# в пайплайне перед вызовом:
sha256sum -c /var/ci/expected.sha256
# → ожидается: Makefile: OK; иначе — FAILED и остановка
```

### 5. Отравление пайплайна через Pull Request (PPE) и Cordyceps

**Вектор атаки:** Атака на open-source или внутренние проекты, где CI запускается автоматически для Pull Request.

**Механизмы:**
1. **GitHub Actions — `pull_request_target`:** Этот триггер запускается в контексте **базового репозитория** с доступом к секретам и привилегированному `GITHUB_TOKEN`. Если пайплайн выполняет `checkout` кода из PR (`ref: ${{ github.event.pull_request.head.sha }}`) и затем запускает скрипты (например, `npm install` или `make`), злоумышленник получает полный доступ к секретам репозитория.
   ```yaml
   # Уязвимый воркфлоу
   on: pull_request_target
   jobs:
     test:
       runs-on: ubuntu-latest
       steps:
         - uses: actions/checkout@v4
           with:
             ref: ${{ github.event.pull_request.head.sha }}
         - run: npm install && npm test # Вредоносный npm скрипт в PR украдет секреты
   ```
 2. **Атака класса "Cordyceps" (Cross-Workflow Escalation):** Низкопривилегированный пайплайн (например, на `pull_request`) записывает вредоносные данные в артефакт или кэш. Второй, высокопривилегированный пайплайн (на `workflow_run` или `pull_request_target`), считывает этот «отравленный» артефакт и выполняет его содержимое без проверки, предоставляя атакующему доступ к секретам организации (реестры артефактов, менеджеры секретов, внутренние сервисы).

**Защита:**
- **Изоляция данных:** Никогда не делать `checkout` и запуск кода из PR внутри `pull_request_target`. Для тестов использовать только `pull_request`.
- **Approval:** Настройка "Require approval for all outside collaborators".
- **Cache Isolation:** Использование уникальных ключей кэша для каждой ветки (`cache-key: ${{ github.ref }}`).
- **OIDC Scoping:** Ограничение выдачи токенов OIDC только для доверенных веток и окружений.

**Проверка (Validation):** В настройках репозитория GitHub Actions включите `Fork pull request workflows` → «Require approval». Убедитесь, что воркфлоу с `pull_request_target` не делает `checkout` ветки PR.

### 6. Чрезмерные привилегии конвейера (PBAC)

**Вектор атаки:** Раннеры или агенты CI/CD имеют избыточные права в системе или сети (недостаточное управление правами, уязвимости PBAC).

**Механизм:** Злоумышленник, получивший возможность выполнить код на раннере (через Poisoning), может получить доступ к системным файлам хоста:
- **Чтение конфигурации:** Чтение файлов вроде `/var/jenkins_home/secrets/...` или `/etc/shadow`, если раннер выполняется от привилегированного пользователя (например, при регистрации раннера через `sudo`).
- **Скрытие активности (Reverse Shell через cron):** Для закрепления на скомпрометированном раннере атакующий может прописать запуск reverse shell в системный `cron` хоста (с планированием отложенного запуска или в фоне). Джоба при этом быстро завершается (exit 0), не привлекая внимания, а доступ к системе сохраняется.
- **Манипуляция сборочным узлом:** Изменение `/etc/hosts` для перехвата трафика к внутренним API или реестрам.

**Защита:** 
- Принцип наименьших привилегий (Least Privilege).
- Запуск раннеров в изолированных непривилегированных контейнерах без маппинга чувствительных директорий хоста.
- **Just-In-Time (JIT) Access:** Динамическое повышение прав CI-задачи только на время выполнения деплоя.
- Строгий контроль прав пользователя, от которого работает агент.

**Типичные ошибки (Устранение неисправностей):**
- Раннер установлен от `root` → переустановите от выделенного пользователя `ci-runner` без `sudo`-доступа.
- Джоб падает с «permission denied» после понижения прав → это ожидаемо; выдавайте конкретные права точечно, а не возвращайте root.

### 7. Атака на раннеры: побег, отравление кэша и кража токенов

**Вектор атаки:** Компрометация хостовой машины раннера или процесса сборки через уязвимости конфигурации.

**Механизм:**
1. **Побег (Escape):** Если раннер использует `docker.sock`, запущен в привилегированном режиме (`privileged: true`) или имеет опасные capability (например, через блочные устройства), злоумышленник может выполнить побег из контейнера на хостовую ОС раннера. Из хостовой системы (например, через `docker ps`) можно увидеть другие контейнеры-джобы и выполнить код внутри них (`docker exec`).
2. **Сбор токенов и секретов (Harvesting):** Оказавшись на хосте, атакующий запускает сканирование:
    - Переменных окружения чужих джоб через `/proc`.
    - Поиск SSH-ключей (`grep -r "BEGIN .* PRIVATE KEY" /`).
    - Поиск кредов от Docker Registry (в файлах вроде `~/.docker/config.json`, где хранятся base64 токены). Украденные токены можно использовать для подмены образов.

    ```bash
    # Пример концептуального скрипта для перехвата токенов на хосте
    while true; do 
      ps auxww | grep -i "JWT\|VAULT_TOKEN\|SECRET_TOKEN" >> /tmp/stolen_tokens.log
      sleep 0.1
    done
    ```
3. **Отравление кэша (Cache Poisoning):** Атакующий в своей джобе собирает модифицированный бинарник или зависимость и кладет его в общий кэш CI. При запуске основной джобы (например, в ветке `main`) легитимный процесс берет из кэша зараженный файл.
4. **Спуфинг раннера (Runner Spoofing):** Вместо попытки украсть токены с работающего раннера, атакующий перехватывает "окно" поллинга, представляясь легитимным раннером для CI-сервера (используя украденный токен регистрации). Задачи назначаются поддельному раннеру, который просто собирает все секреты, переменные и токены.

**Защита:**
- **Эфемерная инфраструктура:** Использование `Kubernetes Executor` в GitLab, где для каждой задачи создается новый изолированный под, который уничтожается сразу после завершения.
- **Отказ от Docker-в-Docker (DinD):** Избегание проброса `docker.sock` и использования привилегированных контейнеров.
- **Hardening раннеров:** Использование специализированных рантаймов (**gVisor**, **Kata Containers**), профилирование доступа (SELinux, AppArmor). Выполнение джоб от пользователя `nobody`.
- **eBPF-мониторинг (Tetragon):** Использование eBPF для обнаружения аномальных системных вызовов (например, попытка записи в `/etc` или открытие сетевых соединений из контейнера сборки).

Подробный разбор векторов атак в DinD — в [Docker-in-Docker: безопасность](../../Docker/docker-in-docker.md).

### 8. Атака через цепочку зависимостей

**Вектор атаки:** Компрометация внешнего или внутреннего пакета либо стороннего экшена/шаблона, используемого в пайплайне.

**Механизмы:**
1. **Dependency Confusion:** Злоумышленник публикует пакет с именем внутреннего приватного пакета и завышенной версией в публичный реестр. Пакетный менеджер скачивает вредоносный пакет из публичного источника.
2. **Компрометация сторонних экшенов (GitHub Actions):** Злоумышленник получает доступ к популярному экшену и обновляет тег версии (например, `v4`) на вредоносный коммит. Все пайплайны, использующие `uses: actions/checkout@v4`, начинают выполнять вредоносный код.
3. **Poisoned Artifacts:** Подмена артефактов в промежуточном хранилище или кэше.

**Защита:**
- **SHA Pinning:** В GitHub Actions фиксировать экшены не по тегам, а по полному SHA коммита (например, `uses: actions/checkout@8ade...`). Теги мутабельны, SHA — нет.
- **Приватные реестры:** Использование Nexus/Artifactory с жестким приоритетом внутреннего реестра и зеркалированием.
- **OpenSSF Scorecard:** Автоматизированная проверка репутации и безопасности внешних зависимостей.
    - **SBOM:** Фиксация версий зависимостей (lock-файлы) по хэшам и проверка соответствия уровням SLSA v1.2.

**Проверка (Validation):** Убедитесь, что пакетный менеджер не уходит в публичный реестр за внутренним пакетом:
```bash
# npm: запрет внешних источников для scope организации
npm config set @mycorp:registry https://nexus.internal/repository/npm/
# проверка: запрос заведомо несуществующего внутреннего пакета не должен уйти на registry.npmjs.org
npm view @mycorp/does-not-exist version
# → ожидается ошибка, а не обращение к публичному реестру
```

### 9. Компрометация пользователей платформы

В зависимости от роли скомпрометированного пользователя:

1. **Обычный разработчик (Developer):**
    - **Вектор атаки:** Внедрение вредоносного кода в ветку или Merge Request.
    - **Защита:** Обязательное ревью кода (Code Review) и использование механизма **Code Owners**. Если платформа не поддерживает `Code Owners`, можно реализовать проверку через CI, которая парсит список аппруверов через API и блокирует Merge при их отсутствии.
2. **Привилегированный пользователь (Maintainer / Owner):**
    - **Вектор атаки:** Может изменить настройки проекта, отключить проверки пайплайнов, переопределить переменные или подменить раннеры на вредоносные (всегда возвращающие код 0).
    - **Защита:** Лишение разработчиков прав `Maintainer` и вынос рутинных задач на внутренний портал самообслуживания (Self-Service). Конфигурация безопасности должна инклюдиться из **удаленного репозитория**, недоступного для редактирования (`include: remote`).
3. **Администратор платформы:**
    - **Вектор атаки:** Имеет полный контроль, может выпускать токены на любых пользователей или имперсонировать их.
    - **Защита:**
      - **Проверка подлинности коммитов:** Использование подписей коммитов (x509 сертификаты) с построением внутренней [PKI](../../Security/Concepts/pki_overview.md). Проверка подписи через серверные Git-хуки (`pre-receive`).
      - **Разделение CI и CD:** Изъятие деплойных прав из CI-системы. CD система ([Ansible Semaphore](../../Ansible/ansible_semaphore.md)) самостоятельно валидирует артефакты (через проверку подписей) перед выкаткой.

### 10. Компрометация нечеловеческих личностей (NHI)

**Вектор атаки:** Атака на сервисные аккаунты, токены пайплайнов и ключи приложений, которые используются для автоматизации без участия человека.

**Механизм:**
- **Кража токенов:** Недостаточная защита сервисных аккаунтов (отсутствие MFA, длительный TTL токенов, хранение в открытом виде) позволяет злоумышленнику перехватить идентичность и действовать от её имени.
- **Злоупотребление привилегиями:** Скомпрометированный сервисный аккаунт часто имеет более широкие права, чем человеческий пользователь (доступ к нескольким реестрам, секретным хранилищам, системам развертывания), что позволяет осуществить масштабную атаку.
- **Отсутствие ротации:** Долгоживущие токены, которые не меняются месяцами, остаются действующими даже после увольнения сотрудника или завершения проекта.

**Защита:**
- **Мониторинг NHI:** Внедрение систем анализа аномального поведения (**UEBA**) специально для сервисных аккаунтов и пайплайнов.
- **Краткосрочные права:** Использование динамических секретов и JIT (Just-In-Time) доступа с минимально необходимыми привилегиями.
- **Ротация:** Автоматическая ротация токенов через менеджер секретов (Vault) или OIDC-федерацию; отзыв токенов при завершении проекта или увольнении сотрудника.
- **Сетевая изоляция:** Ограничение доступа сервисных аккаунтов только необходимыми сервисами (принцип минимального доступа).

### 11. Shadow CI/CD (Теневая автоматизация)

**Вектор атаки:** Использование разработчиками сторонних сервисов автоматизации (например, личные аккаунты IFTTT, Zapier или Jenkins вне контура организации) для работы с корпоративным кодом.

**Механизм:** Разработчик подключает вебхуки репозитория к стороннему сервису для «удобства». Эти сервисы часто имеют слабую защиту, что позволяет атакующему перехватить код или секреты, проходящие через них.

**Защита:**
- **Audit Logs:** Непрерывный мониторинг вебхуков и интеграций в GitHub/GitLab.
- **Policy Enforcement:** Запрет на подключение внешних приложений без аппрува администратора безопасности (GitHub App Approval).
- **Discovery:** Регулярный поиск «теневых» серверов сборки в корпоративной сети.

### 12. Спуфинг вебхуков и SSRF в инфраструктуре CI/CD

**Вектор атаки:** CI-сервер принимает уведомления от SCM по HTTP (вебхуки). Если подпись payload не проверяется строго, злоумышленник может подделать событие (например, «push в main») и инициировать сборку/деплой произвольной ветки, либо использовать сервер как плацдарм для SSRF во внутреннюю сеть.

**Механизмы:**
- **Подделка вебхука (Webhook Spoofing):** Отправка POST-запроса на эндпоинт приёмника CI без валидной HMAC-подписи. Если CI доверяет любому POST с нужным путём — атакующий запускает произвольные джобы.
- **SSRF через обработчик вебхука:** Поле `clone_url` или `repository.homepage` в теле вебхука указывает на внутренний адрес (`http://169.254.169.254/...` или `http://internal-cfg:8500/`), и CI-сервер обращается к нему от своего имени, раскрывая внутренние данные в логах/ответах.
- **Replay-атаки:** Перехваченное легитимное событие воспроизводится повторно для повторного триггера деплоя.

**Предварительные условия (защита):** Секрет вебхука задан на обеих сторонах; CI-сервер настроен на строгую проверку HMAC; исходящие соединения CI ограничены.

**Защита:**
- **HMAC-валидация:** Проверка `X-Hub-Signature-256` (SHA-256 HMAC) на стороне CI для каждого события; отклонение при несовпадении.
- **Allowlist IP SCM:** Фильтрация входящих вебхуков по диапазонам адресов провайдера SCM на уровне firewall/reverse-proxy.
- **Запрет произвольных URL клона:** CI должен клонировать только с явно разрешённых хостов (allowlist доменов реестров/зеркал).
- **Одноразовые nonce / timestamp:** Защита от replay через проверку метки времени события.

**Проверка (Validation):**
```bash
# Симуляция подделанного вебхука без подписи (ожидается отказ 403)
curl -X POST https://ci.internal/webhook/gitlab \
  -H "Content-Type: application/json" \
  -d '{"object_kind":"push","ref":"main"}'
# → ожидается: HTTP 403 / "invalid signature"
```

### 13. Компрометация плагинов, shared libraries и шаблонов

**Вектор атаки:** CI-системы расширяются плагинами (Jenkins), shared libraries (Jenkins Pipeline Shared Libs, GitLab CI `include`) и сторонними шаблонами. Они выполняются с полными правами пайплайна, поэтому их компрометация равносильна компрометации самого CI.

**Механизмы:**
- **Автообновление плагинов (Jenkins):** Плагин с автоматическим обновлением до последней версии может быть перехвачен (если зеркало скомпрометировано) и подменён вредоносным релизом.
- **Shared Library из ветки `master`:** Джобы подключают библиотеку по тегу по умолчанию (`@master`), который легко изменить.
- **Вложенные include:** Цепочка `include` может тянуть конфиг из репозитория, к которому у атакующего есть write-доступ.

**Защита:**
- **Фиксация по SHA/тегу:** Shared libraries и include должны указывать конкретный тег или SHA, а не плавающую ветку.
- **Внутреннее зеркало плагинов:** Jenkins Update Site / плагины держать в проверенном внутреннем зеркале; отключить автообновление.
- **Ревью и сканирование:** Shared libraries проходят тот же code review и SAST, что и основной код.
- **RBAC на админку:** Только администраторы могут устанавливать/обновлять плагины.

**Проверка (Validation):**
```bash
# Jenkins: выгрузить список плагинов с версиями и сравнить с базовой линией
java -jar jenkins-cli.jar -s https://ci.internal/ list-plugins > plugins.current.txt
diff plugins.baseline.txt plugins.current.txt
# → ожидается: пусто (никаких несанкционированных изменений версий)
```

### 14. Отравление базовых образов, Dockerfile и тайпосквоттинг

**Вектор атаки:** Пайплайн собирает образ на основе `FROM` образа или устанавливает пакеты внутри `Dockerfile`/`Makefile`. Если используется непроверенный базовый образ, плавающий тег (`latest`) или опечаточное имя пакета, вредоносный код попадает в финальный артефакт.

**Механизмы:**
- **Вредоносный базовый образ:** Публикация в публичный/внутренний реестр образа-двойника (например, `nginx` вместо официального `library/nginx`) с закреплённым тегом, который подтягивается по имени.
- **Тайпосквоттинг в установщике:** `apt-get install reqeusts` или `pip install requets` ставит вредоносный пакет вместо легитимного.
- **Непиннинг по digest:** `FROM docker.io/library/python:3.11` без `@sha256:...` позволяет подменить содержимое тега.

**Защита:**
- **Пиннинг по digest:** Всегда фиксировать базовый образ по хэшу (`FROM library/python:3.11@sha256:...`).
- **Подпись образов (Sigstore Cosign / Notary):** Проверка подписи базового и финального образа перед сборкой и перед выкладкой (`cosign verify`).
- **Allowlist базовых образов:** Запрет `FROM` из неразрешённых реестров на уровне политики (Connaisseur, Kyverno, OPA).
- **Сканирование на этапе сборки:** Trivy/Grype в джобе пайплайна; блокировка при нахождении критичных CVE.
- **Внутренний зеркальный реестр:** Все базовые образы копируются во внутренний реестр, внешний доступ из раннеров запрещён.

**Проверка (Validation):**
```bash
# Пиннинг по digest
docker pull library/python:3.11@sha256:abcdef...
# Верификация подписи базового образа перед сборкой
cosign verify library/python@sha256:abcdef... \
  --certificate-identity-regexp 'https://github.com/library/.*' \
  --certificate-oidc-issuer 'https://token.actions.githubusercontent.com'
# → ожидается: Verification successful
```

### 15. Атаки через форки и внешние PR (Fork-based PR)

**Вектор атаки:** В публичных и крупных внутренних проектах PR приходят из форков. По умолчанию секреты и привилегированные токены **не** доступны в джобах от форков, однако ряд антипаттернов (использование `pull_request_target`, `workflow_run`, явная выдача secrets форкам) открывает доступ.

**Механизмы:**
- **`workflow_run` + форк:** Воркфлоу, запускаемый по `workflow_run` от базового репозитория, может прочитать артефакт, выложенный вредоносной джобой из форка, и выполнить его с секретами.
- **Явная выдача secrets:** Настройка, разрешающая передачу репозиторных секретов в PR из форков (в GitHub это опция «Send secrets to workflows from fork pull requests»).
- **Косвенный запуск:** Вредоносный `label`/комментарий триггерит джобу, которая выполняет код из форка.

**Защита:**
- **Безусловный запрет секретов для форков:** Секреты предоставляются только для доверенных веток/окружений.
- **Разделение триггеров:** Тестирование кода форка — только в изолированном контексте (`pull_request` без secrets); выкладка — только после merge в защищённую ветку.
- **Ручное подтверждение для внешних контрибьюторов:** GitHub «Require approval for fork pull request workflows».

**Проверка (Validation):** В настройках Actions репозитория убедитесь, что опция передачи секретов форкам выключена, а воркфлоу от форка завершается с «No secrets available» при попытке обратиться к `secrets.*`.

### 16. Манипуляция метаданными сборки, тегами релизов и версионированием

**Вектор атаки:** Злоумышленник, имеющий частичный доступ, изменяет метаданные, по которым CD принимает решение о выкладке: сдвигает git-тег, подменяет `CHANGELOG`/версию в манифесте, модифицирует файл блокировки версий.

**Механизмы:**
- **Перезапись тега:** Легитимный тег `v1.2.3` переносится на скомпрометированный коммит; CD-система выкатывает вредоносную версию, считая её релизной.
- **Фальсификация версии в артефакте:** Манифест собранного пакета (`version: 1.2.3`) не совпадает с фактическим содержимым.
- **Манипуляция lock-файлом:** Точечное изменение хэша зависимости в `package-lock.json`/`Gemfile.lock` на скомпрометированный пакет.

**Защита:**
- **Подписанные теги ( signed tags):** git-теги подписываются ключом release-team; CD проверяет подпись перед выкаткой (`git tag -v`).
- **Иммутабельные теги/артеракты:** Реестры настраиваются на запрет перезаписи тегов (Docker ` immutable tags`, Nexus `disable reupload`).
- **Аттестация в метаданных:** Версия и происхождение фиксируются в SLSA provenance и сверяются CD.

**Проверка (Validation):**
```bash
git tag -v v1.2.3
# → ожидается: gpg: Good signature from "Release Team <release@corp>"
# при подмене тега: gpg: BAD signature
```

## Операционные команды

Раздел содержит операционные команды для детектирования, форензики и реагирования на инциденты в CI/CD-инфраструктуре. Все команды предназначены для выполнения на хостах раннеров, CI-серверах и административных рабочих станциях.

### Детектирование и мониторинг

**Минимальный набор источников телеметрии:**
- Логи CI-сервера и раннеров (агрегируются в центральное хранилище/SIEM).
- Audit-логи SCM (push, изменение прав, webhook, токены).
- События ОС на хостах раннеров (auditd / eBPF / Falco).
- Сетевые flow-логи сегмента раннеров.

**Признаки аномалий (что искать в логах):**
- Base64-строки и обращения к внешним IP в логах сборки (`echo $SECRET | base64`, `curl http://<ip>/exfil`).
- Несанкционированные изменения файлов `.gitlab-ci.yml`/`Jenkinsfile` вне ревью.
- Исходящие соединения от раннеров к неразрешённым хостам (exfiltration).
- Массовое скачивание артефактов/секретов одним сервисным аккаунтом.
- Появление новых `cron`-задач, SSH-ключей или systemd-юнитов на хосте раннера.

**Команды быстрой проверки на хосте раннера:**
```bash
# Активные исходящие соединения раннера (кто куда стучит)
ss -tnp | grep -E ':443|:80' | grep -v 10.0.0.0/8

# Поиск подозрительных заданий в cron
sudo ls -la /etc/cron* /var/spool/cron/ 2>/dev/null

# Новые авторизованные ключи
sudo ls -la /home/*/.ssh/authorized_keys /root/.ssh/authorized_keys 2>/dev/null

# Свежие бинарники в /tmp и /var/tmp
find /tmp /var/tmp -type f -mmin -60 -exec ls -la {} \;
```

**Пример правила Falco (container escape / exfil):**
```yaml
- rule: CI Runner Suspicious Egress
  desc: Исходящее сетевое соединение из контейнера сборки к внешнему адресу
  condition: >
    container.id != host and
    fd.sip != "10.0.0.0/8" and fd.sip != "172.16.0.0/12" and
    fd.sip != "192.168.0.0/16" and
    (inbound_outbound == outbound)
  output: "Подозрительный исходящий трафик из раннера (ip=%fd.sip)"
  priority: WARNING
```

**Пример SIEM-правила (псевдокод):**
```
# Резкий рост числа failed-auth к CI API от одного сервисного аккаунта
count(auth.event == "failure" and target == "ci-api") by service_account > 20 within 5m
  -> alert "Возможный перебор/компрометация NHI"

# Изменение конфига пайплайна без соответствующего MR-аппрува
event == "ci_config_modified" and approver == null
  -> alert "Прямое изменение CI без ревью"
```

### Реагирование на инцидент (Incident Response Runbook)

Пошаговый план при подозрении на компрометацию пайплайна/раннера:

1. **Изоляция:** Отключить раннер (`gitlab-runner stop` / остановить агента), заблокировать его исходящий трафик на firewall, отозвать токен регистрации раннера в CI-сервере.
2. **Отзыв и ротация секретов:** Немедленно перегенерировать все секреты, к которым мог получить доступ раннер (токены реестров, ключи подписи, доступы к инфраструктуре, Vault-токены). Даже если утечки не подтверждено — ротируйте (principle of least regret).
3. **Сохранение улик (Forensics):** Снять снимок образа/контейнера и хоста ДО очистки:
   ```bash
   # Снимок процессов и сети
   sudo ps auxwwf > /evi/ps.$(date +%s).txt
   sudo ss -tnp > /evi/net.$(date +%s).txt
   sudo journalctl -u gitlab-runner --since "2 hours ago" > /evi/runner.log
   # Копия подозрительных файлов
   sudo cp -r /tmp /evi/tmp_snapshot 2>/dev/null
   ```
4. **Анализ:** Проверить логи на base64/exfil, проанализировать изменённые конфиги пайплайна (git blame по файлам CI), найти точку входа (PR, зависимость, плагин).
5. **Очистка:** Переустановить хост раннера из доверенного образа (не «лечить» in-place — persistence могла остаться в cron/systemd/kernel-модуле). Пересканировать все собранные за период компрометации артефакты.
6. **Восстановление:** Вернуть раннер в пул только после применения харднинга (см. раздел Рекомендации) и ротации токена регистрации.
7. **Postmortem:** Зафиксировать вектор, добавить недостающий контроль (required checks, пиннинг, isolation).

## Устранение неисправностей

### Типичные ошибки и решения

**Сканирование секретов:**
- **Сканер ругается на ложные срабатывания (test-данные)** → добавляйте точечные исключения через `.gitleaks.toml` (allowlist), а не отключайте сканер целиком.
- **Секрет уже попал в историю** → смените его до очистки истории (`git filter-repo`/`BFG`), так как удаление из истории не отзывает скомпрометированный ключ.

**Раннеры и изоляция:**
- **Раннер установлен от root** → переустановите от выделенного пользователя `ci-runner` без `sudo`-доступа.
- **Джоб падает с «permission denied» после понижения прав** → это ожидаемо; выдавайте конкретные права точечно, а не возвращайте root.
- **Раннер не регистрируется** → проверьте токен регистрации, URL CI-сервера и сетевое подключение; убедитесь, что порт 443 доступен из сегмента раннеров.

**Артефакты и подпись:**
- **`cosign verify` падает с «no matching signatures»** → проверьте, что реестр поддерживает OCI 1.1 Referrers API; убедитесь, что подпись выполнена тем же ключом/идентичностью.
- **Подпись не проходит в Prod** → несовпадение ключа/идентичности или digest изменён в пути; сверить key, повторно подписать, валидировать digest.

**Зависимости и кэш:**
- **Dependency Confusion детектирован** → проверьте приоритет внутреннего реестра; убедитесь, что пакетный менеджер не уходит в публичный реестр за внутренним пакетом.
- **Кэш отравлен** → отключите общий кэш для PR из форков; используйте уникальные ключи кэша для каждой ветки.

## Рекомендации

### Хост-харднинг раннеров (Runner Hardening)

Цель — сделать компрометацию раннера как можно менее полезной для атакующего и невозможной для закрепления (persistence).

**Принципы:**
- Раннер работает от выделенного непривилегированного пользователя (например, `ci-runner`), не входит в `sudoers`, не имеет доступа к `docker.sock`.
- Каждое задание выполняется в свежем, изолированном окружении (контейнер/kata/gVisor), уничтожаемом после завершения.
- Файловая система раннера — read-only там, где возможно; `/tmp`, `/var/tmp`, `/home` — приватные на джобу.

**Пример юнит-сервиса systemd с жёстким sandbox (Linux):**

```ini
# /etc/systemd/system/gitlab-runner.service.d/zz-hardening.conf
[Service]
# Запрет повышения привилегий
NoNewPrivileges=yes
# Изоляция файловой системы
ProtectSystem=strict
ProtectHome=yes
PrivateTmp=yes
# Ограничение системных вызовов (белый список базовых)
SystemCallFilter=@system-service
SystemCallErrorNumber=EPERM
# Запрет создания setuid/setgid и новых namespace с привилегиями
RestrictSUIDSGID=yes
RestrictNamespaces=yes
# Запрет прямого доступа к устройствам
PrivateDevices=yes
# Ограничение сети (разрешить только нужные outgoing, см. ниже)
# RestrictAddressFamilies=AF_INET AF_INET6 AF_UNIX
# Запрет записи в исполняемую память
MemoryDenyWriteExecute=yes
# Ограничение возможности отладки/трассировки
ProtectKernelTunables=yes
ProtectKernelModules=yes
ProtectKernelLogs=yes
ProtectControlGroups=yes
```

Применение и проверка:
```bash
sudo systemctl daemon-reload
sudo systemctl restart gitlab-runner
# Проверка активных ограничений юнита
systemctl show gitlab-runner.service -p NoNewPrivileges -p ProtectSystem -p SystemCallFilter
# → ожидается: NoNewPrivileges=yes, ProtectSystem=strict, SystemCallFilter=...
```

**seccomp-профиль (минимальный, для контейнера раннера):** запрещаем `mount`, `ptrace`, `kexec_load`, `bpf`, `setns`, `reboot` и т.п. Профиль прикладывается через `--security-opt seccomp=/etc/ci/seccomp.json` (Docker) или `securityContext.seccompProfile` (Kubernetes).

**AppArmor:** назначить раннеру профиль `docker-default` или собственный, запрещающий доступ к `/etc/shadow`, `/var/jenkins_home`, `/proc/sys`.
```bash
sudo apparmor_parser -r /etc/apparmor.d/docker-ci-runner
# в опциях контейнера: --security-opt apparmor=docker-ci-runner
```

**gVisor (runsc):** запуск раннеров в песочнице на уровне системных вызовов — эффективная защита от container escape.
```bash
# Регистрация рантайма (Docker)
sudo runsc install
sudo systemctl restart docker
# запуск агента внутри runsc
docker run --runtime=runsc --rm -it alpine sh
```

**Эфемерность:** для self-hosted раннеров использовать стратегию «один хост — одна джоба, затем снос/рестарт до чистого снимка» (snapshot-restore или переустановка образа). На платформе GitLab — `Kubernetes Executor` с `privileged = false`.

### Сетевая сегментация и управление доступом

- Раннеры размещаются в выделенном сегменте/VLAN без доступа к управляющей сети инфраструктуры.
- Исходящий трафик раннеров — по allowlist: только адреса SCM, внутреннего реестра артефактов, менеджера секретов и необходимых зеркал зависимостей. Всё остальное блокируется (default-deny egress).
- Пример ограничения egress через `iptables` (или эквивалент на уровне сети):
  ```bash
  # Разрешить только DNS и внутренний реестр/SCM, запретить всё остальное
  iptables -A OUTPUT -o lo -j ACCEPT
  iptables -A OUTPUT -p udp --dport 53 -j ACCEPT
  iptables -A OUTPUT -d 10.10.0.0/24 -j ACCEPT   # SCM + registry
  iptables -A OUTPUT -d 10.20.0.0/24 -j ACCEPT   # Vault/secret store
  iptables -A OUTPUT -j REJECT
  ```
- Запрет прямого доступа раннеров к production-сети; деплой выполняет отдельная CD-система через узкий канал.

### Резервное копирование и восстановление CI/CD

Компрометация или сбой CI-сервера не должны останавливать восстановление инфраструктуры.

- **Что бэкапить:** конфигурация CI-сервера (например, `/var/jenkins_home` или БД GitLab), список раннеров и их токенов (в зашифрованном виде), определения пайплайнов (они в репозиториях, но полезен и экспорт), метаданные реестра артефактов.
- **Секреты:** снапшоты Vault (интегрированное шифрование), но не сами значения в открытом виде в бэкапах.
- **Проверка восстановления (Validation):**
  ```bash
  # Тестовое восстановление Jenkins home в изолированную среду
  rsync -a /backup/jenkins_home/ /opt/jenkins_test_home/
  # запуск тестового инстанса и проверка, что джобы и права на месте
  ```
- **Иммутабельность бэкапов:** бэкапы только для чтения, с проверкой целостности (хэш/подпись), чтобы исключить внедрение вредоносной конфигурации через восстановление.

### Чек-лист минимальной защищённости (Quick Reference)

- [ ] Защищённые ветки (Protected Branches) + обязательный code review.
- [ ] Required status checks блокируют слияние при падении сканеров.
- [ ] Секреты только во внешнем менеджере (Vault), статические ключи отсутствуют.
- [ ] Shared libraries / include зафиксированы по SHA/тегу, не по ветке.
- [ ] Раннеры: не-root, без `docker.sock`, systemd-sandbox + seccomp + AppArmor/gVisor.
- [ ] Эфемерные раннеры или per-job изоляция.
- [ ] Зависимости и базовые образы пиннинг по digest, подпись проверяется (`cosign verify`).
- [ ] Артефакты подписаны, генерируется SLSA provenance.
- [ ] Исходящий трафик раннеров ограничен allowlist (default-deny egress).
- [ ] Централизованные логи + SIEM-правила на эксфильтрацию и изменения CI-конфигов.
- [ ] Отработанный IR-runbook и регулярные тесты восстановления из бэкапа.
