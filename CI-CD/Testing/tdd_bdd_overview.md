# TDD, BDD и ATDD: Методологии разработки через тестирование

## Определения

- **TDD (Test-Driven Development)** — разработка через тестирование. Методология, при которой тесты пишутся до реализации функционала. Фокусируется на проверке корректности кода.
- **BDD (Behavior-Driven Development)** — разработка через поведение. Расширение TDD, которое фокусируется на поведении системы с точки зрения бизнеса. Использует сценарии на естественном языке (Gherkin).
- **ATDD (Acceptance Test-Driven Development)** — разработка через приемочные тесты. Методология, объединяющая заказчиков, разработчиков и тестировщиков для создания приемочных тестов до начала разработки.

## Основные концепции

### Процесс TDD: Цикл Red-Green-Refactor

1. **RED (Красный)**: Написать минимальный тест для новой функции, который должен упасть.
2. **GREEN (Зеленый)**: Написать ровно столько кода, сколько нужно для прохождения теста.
3. **REFACTOR (Рефакторинг)**: Очистить код и тесты от дублирования, улучшить структуру, не меняя поведение.

### Три закона TDD (Роберт Мартин)

1. Нельзя писать production-код, пока не написан падающий unit-тест.
2. Нельзя писать unit-тест больше, чем необходимо для его падения (некомпиляция — это тоже падение).
3. Нельзя писать production-код больше, чем необходимо для прохождения текущего падающего теста.

### Концепция Double Loop TDD

Сочетание BDD и TDD для обеспечения качества на всех уровнях:
- **Внешний цикл (BDD)**: Написание падающего приемочного теста (поведение системы).
- **Внутренний цикл (TDD)**: Многократное повторение цикла Red-Green-Refactor для реализации логики, пока приемочный тест не станет зеленым.

### Формат сценариев BDD (Gherkin)

Используется для описания бизнес-сценариев в формате:
- **Given (Дано)**: Начальное состояние системы.
- **When (Когда)**: Действие пользователя или событие.
- **Then (Тогда)**: Ожидаемый результат.
- **And/But (И/Но)**: Дополнительные условия или проверки.

## Практические сценарии

### Пример TDD на Python (Функция суммирования)

```python
# Этап RED: Тест падает, так как функция не определена
def test_add_numbers():
    assert add(2, 3) == 5

# Этап GREEN: Минимальный код для прохождения
def add(a, b):
    return 5

# Этап REFACTOR: Корректная реализация
def add(a, b):
    return a + b
```

### Пример BDD/ATDD сценария (Авторизация)

```gherkin
Feature: Авторизация пользователя
  Scenario: Успешный вход в систему
    Given пользователь "admin" существует с паролем "pass123"
    When пользователь вводит логин "admin" и пароль "pass123"
    Then система перенаправляет пользователя на главную страницу
    And отображается сообщение "Добро пожаловать, admin"
```

### Сравнение методологий

| Аспект | TDD | BDD | ATDD |
| :--- | :--- | :--- | :--- |
| **Фокус** | Реализация и дизайн кода | Поведение системы (User Story) | Требования бизнеса (Acceptance) |
| **Участники** | Разработчики | Разработчики, QA, Аналитики | Заказчик, Разработчики, QA |
| **Уровень** | Unit-тесты | Интеграционные/E2E | Приемочные тесты |
| **Инструменты** | Pytest, JUnit, Jest | Cucumber, Behave | Robot Framework, FitNesse |

## Дополнительная информация

### Антипаттерны и типичные ошибки

- **The Mockery**: Чрезмерное использование моков, из-за чего тесты проверяют детали реализации, а не поведение.
- **The Liar**: Тест проходит, но на самом деле ничего не проверяет (отсутствие assert или проверка не того условия).
- **The Giant**: Огромные тесты, которые сложно читать и поддерживать.
- **Тестирование приватных методов**: Нарушает инкапсуляцию; следует тестировать только публичный интерфейс.

### Принципы качественных тестов

- **FIRST**: Fast (быстрые), Independent (независимые), Repeatable (повторяемые), Self-validating (самодокументированные), Timely (своевременные).
- **AAA (Arrange, Act, Assert)**: Структура теста — Подготовка, Действие, Проверка.
