# Лучшие практики Feature Toggles

## Определения

**Лучшие практики (Best Practices)** — это набор проверенных индустриальных стандартов и подходов, направленных на эффективное управление флагами функций, минимизацию технического долга и обеспечение стабильности системы.

---

## Основные концепции

### Фундаментальные правила

1.  **Именование (Naming Conventions)**: Имя флага должно быть семантичным и отражать *суть* функции, а не техническую реализацию.
    *   *Плохо:* `flag-1`, `test-new-logic`, `fix-bug-123`.
    *   *Хорошо:* `checkout-v2-redesign`, `stripe-payment-integration`.
2.  **Безопасные значения по умолчанию (Safe Defaults)**: При недоступности системы управления флагами (Network Timeout, Server 500) приложение должно переходить в наиболее стабильное состояние (обычно `False`).
3.  **Метаданные флагов**: Каждый флаг должен содержать:
    *   **Владелец (Owner)**: Команда или конкретный разработчик.
    *   **Дата создания и TTL**: Ожидаемая дата удаления.
    *   **Ссылка на задачу**: Ссылка на тикет в Jira/Linear.
4.  **Принцип «четырех глаз» (Four-eyes principle)**: Изменение критических флагов в Production (например, Kill Switches) должно требовать подтверждения от другого участника команды.

---

### Стратегии тестирования

Тестирование системы с флагами требует проверки комбинаторного взрыва состояний.

| Тип теста | Подход | Рекомендация |
| :--- | :--- | :--- |
| **Unit-тесты** | Тестирование обеих веток кода (`Toggle-aware testing`) | Используйте параметризованные тесты для автоматической проверки `True` и `False` состояний. |
| **Интеграционные тесты** | Проверка взаимодействия компонентов | Тестируйте «новое состояние» как основное, но сохраняйте тесты для «старого» до момента удаления флага. |
| **E2E / UI тесты** | Проверка критических путей пользователя | Сосредоточьтесь на проверке наиболее вероятных комбинаций флагов. Не пытайтесь протестировать все $2^n$ состояний. |

## Практические сценарии

### Сценарий 1: Процесс удаления устаревших флагов (Cleanup)

Для борьбы с техническим долгом используйте автоматизацию:

1.  **Stale Flag Detection**: Настройте сканеры кода (например, **Uber Piranha**), которые автоматически находят флаги, не менявшиеся более 30 дней.
2.  **Архивация**: Если флаг включен на 100% более 2 недель, он должен быть принудительно удален из кода.
3.  **Codemods**: Используйте скрипты для автоматической очистки `if/else` конструкций после удаления флага в системе управления.

### Сценарий 2: Мониторинг и обсервабилити

Каждая проверка флага должна сопровождаться телеметрией для анализа «радиуса поражения» (Blast Radius).

**Рекомендуемые метрики:**
*   **Exposure Rate**: Процент пользователей, увидевших новую фичу (сверка с бизнес-ожиданиями).
*   **Error Rate per Toggle**: Сравнение количества ошибок в ветках `On` и `Off`.
*   **Latency Overhead**: Задержка, вносимая SDK при вычислении правил.
*   **Stale Flags Count**: Количество флагов в системе, требующих удаления.
