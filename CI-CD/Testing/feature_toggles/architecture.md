# Архитектура систем Feature Toggles

## Определения

**Архитектура Feature Toggles** — набор компонентов и подходов для централизованного управления флагами, доставки конфигурации в приложение и принятия решений о включении/отключении функциональности.

---

## Базовые концепции

### Ключевые компоненты

```
┌─────────────────────────────────────────────────────────────┐
│                    ПРИЛОЖЕНИЕ (APPLICATION)                 │
│                                                             │
│  ┌───────────┐      ┌───────────┐      ┌───────────┐        │
│  │ Проверка  │      │ Проверка  │      │ Проверка  │        │
│  │  флага A  │      │  флага B  │      │  флага C  │        │
│  └─────┬─────┘      └─────┬─────┘      └─────┬─────┘        │
│        └──────────────────┼──────────────────┘              │
│                           │                                 │
│                   ┌───────▼───────┐                         │
│                   │   Клиент/SDK    │                         │
│                   │ Feature Toggle  │                         │
│                   └───────┬───────┘                         │
└───────────────────────────┼─────────────────────────────────┘
                            │
           ┌────────────────┼────────────────┐
           │                │                │
┌──────────▼────────┐┌──────▼──────┐┌────────▼─────────┐
│ Файл конфигурации ││ База данных ││ Внешний сервис   │
│   (YAML/JSON)     ││ (Postgres,  ││ (LaunchDarkly,   │
│                   ││  MongoDB)   ││   Unleash)       │
└───────────────────┘└─────────────┘└──────────────────┘
```

**Клиент/SDK** — библиотека в коде приложения, точка входа для проверки флагов:

| Функция | Описание |
| :--- | :--- |
| Запрос конфигурации | Получение состояния флагов из хранилища |
| Кэширование | Локальное хранение для производительности |
| Контекстные решения | Учет ID пользователя, сессии, региона |
| Safe fallback | Возврат значения по умолчанию при недоступности хранилища |

**Хранилище конфигурации** — централизованное хранилище состояния всех флагов.

---

### Сравнение подходов к хранению

| Подход | Плюсы | Минусы | Когда использовать |
| :--- | :--- | :--- | :--- |
| **Файлы конфигурации** (YAML/JSON) | Простота, версионирование в Git | Требует переразвертывания для изменения | Простые проекты, статичные флаги |
| **База данных** | Динамическое изменение через UI | Нужна своя разработка UI/API | Средняя сложность, внутреннее управление |
| **Специализированные сервисы** (LaunchDarkly, Unleash, Flagsmith) | Готовый UI, SDK, аудит, A/B-тесты, сложные правила | Зависимость от вендора, стоимость | Production, сложные сценарии, команда >5 человек |

## Практические сценарии

### Сценарий 1: Файлы конфигурации

Архитектура на основе файлов конфигурации предполагает хранение флагов непосредственно в коде или рядом с ним в форматах YAML/JSON.

**Пример структуры (YAML):**

```yaml
features:
  new-checkout:
    enabled: true
  dark-mode:
    enabled: false
  beta-feature:
    enabled: true
    strategy: percentage
    percentage: 10
```

**Процесс изменения:**

1. Изменить файл в Git.
2. Создать Pull Request.
3. После слияния — переразвертывание приложения (или перезагрузка конфигурации, если поддерживается).

**Применимость:** Статичные флаги, редкие изменения, небольшие проекты.

---

### Сценарий 2: База данных

В этой архитектуре флаги хранятся в реляционной или NoSQL базе данных, что позволяет изменять их состояние без переразвертывания приложения.

**Пример структуры таблицы (SQL):**

```sql
CREATE TABLE feature_flags (
    name VARCHAR(255) PRIMARY KEY,
    enabled BOOLEAN DEFAULT false,
    strategy VARCHAR(50),
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

**Процесс изменения:**

1. Изменение через административную панель или прямой SQL-запрос.
2. Мгновенное применение (в зависимости от политики обновления кэша в SDK).

**Применимость:** Внутренние инструменты, команды с ресурсами на разработку собственной панели управления.

---

### Сценарий 3: Специализированный сервис (Unleash, LaunchDarkly)

Архитектура с внешним сервисом управления флагами обеспечивает максимальную гибкость и функциональность «из коробки».

**Процесс изменения:**

1. Изменение состояния или правил таргетинга в веб-интерфейсе провайдера.
2. Мгновенное получение обновлений SDK через WebSocket или регулярный опрос (polling).
3. Использование встроенных инструментов аудита, метрик и A/B-тестирования.

**Применимость:** Production-системы, сложные сценарии таргетинга, канареечные релизы. Практические примеры интеграции с SDK представлены в документе **[Реализация Feature Toggles](./implementation.md#сценарий-2-интеграция-с-готовым-решением-unleash)**.
