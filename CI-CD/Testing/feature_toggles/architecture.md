# Архитектура систем Feature Toggles

## Определения

**Архитектура Feature Toggles** — это совокупность компонентов, протоколов и подходов, обеспечивающих централизованное управление состояниями флагов, их эффективную доставку в приложения и принятие решений о включении функциональности в реальном времени.

---

## Основные концепции

### Ключевые компоненты системы

```text
┌─────────────────────────────────────────────────────────────┐
│                    ПРИЛОЖЕНИЕ (APPLICATION)                 │
│                                                             │
│  ┌───────────┐      ┌───────────┐      ┌───────────┐        │
│  │ Проверка  │      │ Проверка  │      │ Проверка  │        │
│  │  флага A  │      │  флага B  │      │  флага C  │        │
│  └─────┬─────┘      └─────┬─────┘      └─────┬─────┘        │
│        └──────────────────┼──────────────────┘              │
│                           │                                 │
│                   ┌───────▼───────┐                         │
│                   │   Клиент/SDK    │                         │
│                   │ Feature Toggle  │                         │
│                   └───────┬───────┘                         │
└───────────────────────────┼─────────────────────────────────┘
                            │
           ┌────────────────┼────────────────┐
           │                │                │
┌──────────▼────────┐┌──────▼──────┐┌────────▼─────────┐
│ Файл конфигурации ││ База данных ││ Внешний сервис   │
│   (YAML/JSON)     ││ (Postgres,  ││ (LaunchDarkly,   │
│                   ││  MongoDB)   ││   Unleash)       │
└───────────────────┘└─────────────┘└──────────────────┘
```

1. **Клиент/SDK**: Библиотека, интегрированная в код приложения. Отвечает за:
   - Кэширование состояний для минимизации задержек.
   - Вычисление правил таргетинга (например, на основе ID пользователя).
   - Обеспечение отказоустойчивости (Safe Fallback).
2. **Панель управления (Admin UI)**: Интерфейс для изменения состояний флагов и правил.
3. **Хранилище данных**: Место, где хранятся текущие конфигурации (БД, файлы или облачный сервис).

### Сравнение подходов к реализации

| Подход | Преимущества | Недостатки | Сценарий использования |
| :--- | :--- | :--- | :--- |
| **Файлы конфигурации** | Максимальная простота, версионирование в Git. | Требует перезапуска или переразвертывания. | Статичные флаги, небольшие проекты. |
| **Собственная БД** | Полный контроль, отсутствие зависимости от вендоров. | Высокие затраты на разработку и поддержку UI/API. | Компании со строгими требованиями безопасности. |
| **SaaS/Open Source решения** (Unleash, LaunchDarkly) | Богатый функционал "из коробки" (аудит, стратегии). | Зависимость от внешнего сервиса, стоимость. | Enterprise-проекты, сложные стратегии (Canary, A/B). |

## Практические сценарии

### Сценарий 1: Использование файлов конфигурации (YAML)

Наиболее простой способ, не требующий дополнительной инфраструктуры.

**Пример конфигурации:**
```yaml
features:
  maintenance-mode:
    enabled: false
  new-search-algorithm:
    enabled: true
    percentage: 10
```

**Применимость:** Релизные флаги, которые редко меняются и могут быть обновлены вместе с деплоем приложения.

### Сценарий 2: Интеграция с внешним сервисом (Unleash)

Использование специализированного решения для динамического управления в масштабах всей компании.

**Процесс:**
1. SRE или Product Manager меняет состояние флага в UI Unleash.
2. Приложение получает обновление через SDK по протоколу HTTP/gRPC (или через Server-Sent Events).
3. Состояние меняется мгновенно для всех пользователей без перезапуска сервисов.

**Применимость:** Операционные флаги (Kill Switches) и экспериментальные флаги для A/B тестирования.
