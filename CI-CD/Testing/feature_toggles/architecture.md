# Архитектура систем Feature Toggles

## Определения

**Архитектура Feature Toggles** — это совокупность компонентов, протоколов и подходов, обеспечивающих централизованное управление состояниями флагов, их эффективную доставку в приложения и принятие решений о включении функциональности в реальном времени.

---

## Основные концепции

### Ключевые компоненты системы

Современная архитектура (2026+) включает уровни абстракции для обеспечения безопасности и производительности:

```text
┌──────────────────────────────┐      ┌──────────────────────────────┐
│      УРОВЕНЬ УПРАВЛЕНИЯ      │      │      УРОВЕНЬ ХРАНЕНИЯ        │
│   (Control Plane / Admin)    │      │       (Storage Layer)        │
│ ┌──────────────────────────┐ │      │ ┌──────────────────────────┐ │
│ │  Admin UI / Dashboard    │ │      │ │  Relational DB / NoSQL   │ │
│ └─────────────┬────────────┘ │      │ └─────────────┬────────────┘ │
└───────────────┼──────────────┘      └───────────────┼──────────────┘
                │                                     │
                ▼                                     ▼
┌────────────────────────────────────────────────────────────────────┐
│                  СЕРВЕР УПРАВЛЕНИЯ ФЛАГАМИ (API)                   │
│   (Evaluation Engine, Authorization, Audit Logs, Event Stream)     │
└────────────────────────────────┬───────────────────────────────────┘
                                 │
         ┌───────────────────────┴───────────────────────┐
         │                                               │
         ▼                                               ▼
┌──────────────────┐                           ┌──────────────────┐
│  RELAY / PROXY   │                           │  EDGE COMPUTING  │
│ (Local caching,  │                           │ (Cloudflare, SDK │
│  PII stripping)  │                           │  at the Edge)    │
└────────┬─────────┘                           └────────┬─────────┘
         │                                              │
         └───────────────────────┬──────────────────────┘
                                 │
                                 ▼
┌────────────────────────────────────────────────────────────────────┐
│                      ПРИЛОЖЕНИЕ (APPLICATION)                      │
│   ┌─────────────┐       ┌──────────────┐       ┌─────────────┐     │
│   │  SDK / API  │ ◄──── │  Middleware  │ ◄──── │  App Logic  │     │
│   └─────────────┘       └──────────────┘       └─────────────┘     │
└────────────────────────────────────────────────────────────────────┘
```

1.  **SDK (Evaluation Engine)**: Библиотека в коде приложения. В современных системах (Unleash, LaunchDarkly) вычисление правил (таргетинг) происходит **локально** в SDK на основе полученного набора правил, что исключает сетевые задержки.
2.  **Relay / Proxy**: Промежуточный слой. Необходим для:
    *   **Безопасности**: Маскировка чувствительных данных пользователей (PII), прежде чем они попадут в облако вендора.
    *   **Производительности**: Группировка тысяч соединений от фронтенд-клиентов в одно соединение с сервером флагов.
3.  **Event Stream (SSE/gRPC)**: Обеспечивает мгновенную доставку изменений (вместо периодического опроса/polling).

---

### Методы вычисления флагов (Evaluation)

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Local Evaluation** | SDK скачивает все правила и вычисляет результат локально. | Нулевая задержка, высокая надежность. | SDK должен знать все правила (риск утечки логики). |
| **Remote Evaluation** | SDK отправляет контекст пользователя на сервер/прокси и получает результат. | Безопасность (правила не покидают сервер). | Сетевой запрос на каждую проверку флага. |
| **Edge Evaluation** | Вычисление происходит на CDN узлах (Edge). | Баланс между скоростью и безопасностью. | Сложность синхронизации состояний. |

---

### Безопасность и аудит

*   **RBAC (Role-Based Access Control)**: Ограничение прав на включение флагов в Production (например, только SRE или Lead Developer).
*   **Audit Logs**: Каждое изменение флага должно логироваться с указанием: кто, когда, зачем (ссылка на тикет) и какое значение было до/после.
*   **Approval Flows**: Требование подтверждения от второго лица (Four-eyes principle) для критических флагов.

---

### Интеграция с Observability

Для реализации **Progressive Delivery** архитектура должна поддерживать обратную связь:
1.  **Exposure Tracking**: SDK отправляет событие в систему аналитики (Amplitude, Mixpanel) или мониторинга (Prometheus/OTel), когда пользователь «увидел» фичу.
2.  **Automated Rollback**: Система мониторинга (например, Argo Rollouts) анализирует метрики (Error Rate) и через API сервера флагов автоматически выключает флаг при деградации.

## Сравнение подходов к реализации

| Характеристика | Конфиг-файлы (Git) | Собственная БД + API | FFaaS (Unleash/LD) |
| :--- | :--- | :--- | :--- |
| **Стоимость** | Низкая | Высокая (разработка) | Средняя (подписка) |
| **Динамичность** | Низкая (Deployment) | Высокая (Runtime) | Высокая + Стратегии |
| **Таргетинг** | Нет | Ограничен | Продвинутый (Сегменты) |
| **Аудит** | Git history | Требует реализации | Встроенный |
