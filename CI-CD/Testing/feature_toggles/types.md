# Типы Feature Toggles

## Определения

**Типы Feature Toggles** — это классификация механизмов управления функциональностью по их назначению, жизненному циклу, динамичности и целевой аудитории. Правильный выбор типа флага определяет стратегию его реализации, тестирования, безопасности и удаления (cleanup).

---

## Основные концепции

### Классификация по назначению (модель Фаулера)

В современной разработке выделяют четыре основных типа флагов, различающихся по поведению и управлению.

| Тип флага | Назначение | Срок жизни | Динамичность | Владелец |
| :--- | :--- | :--- | :--- | :--- |
| **Релизные (Release)** | Скрытие незавершенных фич (Trunk-Based Development) | Дни/Недели | Низкая (статич.) | Разработка |
| **Экспериментальные (Experiment)** | A/B-тестирование, проверка продуктовых гипотез | Недели/Месяцы | Высокая | Product / Data |
| **Операционные (Ops)** | Управление надежностью (Kill Switches, Shedding) | Года/Постоянно | Критическая | SRE / DevOps |
| **Разрешений (Permission)** | Сегментация (Beta, Early Adopters, Premium) | Постоянно | Высокая | Product / Support |

#### 1. Релизные флаги (Release Toggles)
- **Цель:** Обеспечение непрерывной интеграции. Позволяют вливать код в `main` до его полной готовности.
- **Особенности:** Обычно двоичные (On/Off). Требуют строгого процесса удаления сразу после "открытия" фичи для всех.

#### 2. Экспериментальные флаги (Experiment Toggles)
- **Цель:** Сбор данных. Пользователи делятся на когорты, каждая из которых видит свой вариант реализации.
- **Особенности:** Требуют интеграции с системами аналитики. Результат переключения должен быть консистентным для одного пользователя на протяжении всего эксперимента.

#### 3. Операционные флаги (Ops Toggles)
- **Цель:** "Аварийная" защита. Позволяют мгновенно снизить нагрузку на систему без передеплоя.
- **Примеры:** 
  - **Kill Switch:** Отключение ресурсоемкого поиска или рекомендаций при перегрузке БД.
  - **Circuit Breaker:** Ручное или автоматическое прерывание связи с нестабильным внешним сервисом.

#### 4. Флаги разрешений (Permission Toggles)
- **Цель:** Управление доступом на уровне бизнес-логики.
- **Особенности:** Зачастую являются частью продукта. Например, открытие "темной темы" только для сотрудников компании перед публичным релизом.

### Техническая привязка (Static vs Dynamic)

Выбор метода связывания зависит от требуемой скорости реакции и сложности инфраструктуры.

| Характеристика | Статическое связывание | Динамическое связывание |
| :--- | :--- | :--- |
| **Место хранения** | Переменные окружения, ConfigMaps, `.env` | FFaaS (Unleash, Flagsmith), Redis, Etcd |
| **Скорость изменения** | Медленная (требует Restart/Redeploy) | Мгновенная (Runtime) |
| **Контроль версий** | Git (IaC) | Админ-панель / API |
| **Типичные флаги** | Релизные | Операционные, Экспериментальные |

### Современные паттерны классификации (2026+)

#### Клиентские vs Серверные флаги (Client vs Server-side)
- **Server-side:** Безопасная проверка на стороне сервера. Флаг никогда не покидает периметр безопасности.
- **Client-side (Frontend/Mobile):** Состояние флага передается на устройство пользователя. 
  - **Риск:** Пользователь может подсмотреть состояние флага через DevTools или декомпиляцию.
  - **Решение:** Проксирование флагов (Feature Flag Proxy) для защиты бизнес-логики.

#### Feature Flags as a Service (FFaaS)
Использование специализированных платформ (Unleash, LaunchDarkly, Flagsmith) переводит флаги из категории "конфигурации" в категорию "данных". Это позволяет:
- Использовать сложные правила (Contextual Toggles) — например, включить фичу только для пользователей из Германии с версией приложения > 2.0.
- Настраивать расписания (Scheduled Rollouts).
- Выполнять автоматический откат при срабатывании алертов (Automatic Rollback).

## Практические сценарии

### Сценарий 1: Плавная миграция на новую БД

Необходимо переключить чтение данных со старой SQL базы на новую NoSQL, минимизируя риск потери данных.

**Решение:** Операционный флаг с режимом "Shadow Read".
1. Флаг `db-migration-strategy` имеет значения: `legacy`, `shadow` (читаем из обеих, сравниваем, логируем расхождения), `new-only`.
2. Переключение в рантайме позволяет мониторить ошибки без вреда для пользователя.
3. При обнаружении проблем — мгновенный возврат в `legacy`.

### Сценарий 2: Глобальный Kill Switch для сторонней интеграции

Внешний сервис аналитики начал тормозить весь Frontend из-за блокирующих запросов.

**Решение:** Динамический операционный флаг.
1. Обертывание скрипта аналитики в проверку флага `external-analytics-enabled`.
2. SRE через панель управления (Unleash) отключает флаг для 100% пользователей.
3. Проблема устранена за секунды без вмешательства разработчиков и пайплайнов.
