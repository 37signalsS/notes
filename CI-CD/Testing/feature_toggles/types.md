# Типы Feature Toggles

## Определения

**Типы Feature Toggles** — это классификация механизмов управления функциональностью по их назначению, жизненному циклу, динамичности и целевой аудитории. Правильный выбор типа флага определяет стратегию его реализации, тестирования и удаления (cleanup).

---

## Основные концепции

### Категории флагов по назначению

#### Релизные флаги (Release Toggles)
- **Назначение:** Позволяют использовать Trunk-Based Development, вливая незавершенный код в основную ветку (`main`/`master`), скрывая его от пользователей до момента готовности.
- **Жизненный цикл:** Краткосрочный (дни или недели). Удаляются сразу после полной активации функции.
- **Динамичность:** Низкая. Часто достаточно статической конфигурации при запуске приложения.
- **Владелец:** Команда разработки.

#### Экспериментальные флаги (Experiment Toggles)
- **Назначение:** Используются для A/B-тестирования и многовариантного тестирования. Позволяют сравнивать поведение или метрики разных групп пользователей.
- **Жизненный цикл:** Среднесрочный (до завершения эксперимента и сбора статистики).
- **Динамичность:** Высокая. Требуют маршрутизации пользователей на основе идентификаторов или атрибутов.
- **Владелец:** Product Manager / Data Analyst.

#### Операционные флаги (Ops Toggles)
- **Назначение:** Управление поведением системы в реальном времени. Включают:
  - **Kill Switches (Аварийные выключатели):** Мгновенное отключение ресурсоемких функций при деградации производительности.
  - **Circuit Breakers (Автоматические размыкатели):** Автоматическое отключение интеграций при превышении порога ошибок.
- **Жизненный цикл:** Долгосрочный или постоянный. Являются частью архитектуры надежности.
- **Динамичность:** Критически высокая. Должны переключаться без перезапуска приложения.
- **Владелец:** SRE / DevOps.

#### Флаги разрешений (Permission Toggles)
- **Назначение:** Управление доступностью функций для конкретных групп пользователей (Early Adopters, Beta-тестеры, сегменты по подписке).
- **Жизненный цикл:** Долгосрочный. Могут жить годами как часть логики продукта.
- **Динамичность:** Высокая. Зависят от контекста авторизованного пользователя.
- **Владелец:** Product Manager / Support.

### Техническая привязка (Static vs Dynamic)

| Характеристика | Статическое связывание | Динамическое связывание |
| :--- | :--- | :--- |
| **Место хранения** | Конфиг-файлы, переменные окружения | База данных, Key-Value хранилища (Etcd, Consul) |
| **Переключение** | Требует перезапуска или переразвертывания | Происходит в рантайме (Runtime) |
| **Применение** | Релизные флаги | Операционные и экспериментальные флаги |
| **Сложность** | Низкая | Высокая (требует SDK или API) |

## Практические сценарии

### Сценарий 1: Плавная миграция на новый API

Разработчикам нужно заменить старый внешний API на новый, сохранив возможность быстрого отката.

**Решение:** Использовать релизный флаг с элементами Canary-релиза.

1. Код содержит обе реализации API.
2. Флаг `new-api-client` управляет выбором реализации.
3. Начальная фаза: флаг включен только для внутренних IP (Dark Launch).
4. Фаза Rollout: включение для 1%, 10%, 50% трафика.
5. После подтверждения стабильности (отсутствие ошибок в логах) флаг удаляется вместе со старым кодом.

### Сценарий 2: Защита базы данных при пиковых нагрузках

В период распродаж (Black Friday) нагрузка на поиск с тяжелыми фильтрами может обрушить БД.

**Решение:** Использование операционного флага в режиме Kill Switch.

1. В коде поиска добавляется проверка флага `heavy-filters-enabled`.
2. При достижении критического CPU на БД, SRE переключает флаг в `false`.
3. Система мгновенно скрывает сложные фильтры в интерфейсе или выдает ошибку с просьбой уточнить поиск.
4. После снижения нагрузки флаг возвращается в исходное состояние.
