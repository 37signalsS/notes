# Типы Feature Toggles

### Определения

- **Типы Feature Toggles** — это классификация флагов по их назначению, жизненному циклу и способу управления. Понимание типа помогает правильно реализовать и управлять флагом.

---

## Basic Concepts

#### 1. Релизные флаги (Release Toggles)

- **Назначение:** Скрытие от пользователей незавершенной функциональности, которая вливается в `main` в рамках Trunk-Based Development.
- **Характеристики:**
  - **Временные:** Живут от нескольких дней до нескольких недель.
  - **Бинарные:** Имеют два состояния (on/off).
  - **Цель:** После стабилизации функции флаг и старый код удаляются.

#### 2. Экспериментальные флаги (Experiment Toggles)

- **Назначение:** A/B-тестирование, Canary-релизы и другие эксперименты над пользователями.
- **Характеристики:**
  - **Длительные:** Могут жить месяцами для сбора статистически значимых данных.
  - **Многовариантные:** Могут иметь несколько состояний (A/B/C).
  - **Контекстные:** Зависят от атрибутов пользователя или сессии.

#### 3. Операционные флаги (Ops Toggles)

- **Назначение:** Управление операционной стабильностью системы. Используются как "аварийные выключатели" (Kill Switches) для отключения проблемных или ресурсоемких функций.
- **Характеристики:**
  - **Постоянные:** Являются частью архитектуры отказоустойчивости.
  - **Динамичные:** Должны иметь возможность быстрого переключения без развертывания.

#### 4. Флаги доступов (Permission Toggles)

- **Назначение:** Управление доступом к функциям для разных групп пользователей (например, "Premium" vs. "Free", "Admin" vs. "User").
- **Характеристики:**
  - **Постоянные:** Являются частью бизнес-логики и модели монетизации.
  - **Контекстные:** Зависят от роли или подписки пользователя.

### Сводная таблица

| Тип флага | Назначение | Жизненный цикл | Динамичность |
| :--- | :--- | :--- | :--- |
| **Релизный** | Скрыть незавершенный код | Временный (дни/недели) | Низкая (часто статика) |
| **Экспериментальный** | A/B-тесты, Canary | Средний (недели/месяцы) | Высокая (пользователи) |
| **Операционный** | Аварийный выключатель | Постоянный | Критически высокая (мгновенная) |
| **Доступный** | Управление доступом | Постоянный | Средняя (по ролям) |

## Practical Scenarios

#### Выбор типа флага: сценарий миграции базы данных

Требуется добавить новое поле в таблицу пользователей и постепенно перевести трафик на новую логику.

**Решение:** Использовать **[Релизный флаг](#1-релизные-флаги-release-toggles)**:
1. Миграция БД выполняется отдельно (добавление поля с null-значением)
2. Код приложения обновляется с проверкой флага `user-profile-v2`
3. Флаг включается для внутренней команды (5% трафика)
4. Постепенный rollout: 5% → 25% → 50% → 100%
5. После стабилизации флаг и старый код удаляются

#### Выбор типа флага: сценарий аварийного отключения

Критичная функция (например, рекомендательная система) создаёт высокую нагрузку на БД и требует возможности мгновенного отключения.

**Решение:** Использовать **[Операционный флаг](#3-операционные-флаги-ops-toggles)**:
- Флаг всегда присутствует в коде как точка отказа
- Переключение через UI без переразвертывания
- При деградации метрик — мгновенное отключение функции
- Fallback: возврат к упрощённой логике или кэшированным данным

#### Выбор типа флага: сценарий монетизации

Требуется предоставить расширенный функционал пользователям премиум-подписки.

**Решение:** Использовать **[Флаг доступов](#4-флаги-доступов-permission-toggles)**:
- Флаг является постоянным элементом бизнес-логики
- Проверка по роли пользователя или статусу подписки
- Изменение состояния происходит через систему биллинга, а не вручную
