# Типы Feature Toggles

## Определения

**Типы Feature Toggles** — это классификация механизмов управления функциональностью по их назначению, жизненному циклу, динамичности и целевой аудитории. Правильный выбор типа флага определяет стратегию его реализации, тестирования, безопасности и удаления (cleanup).

**Жизненный цикл флага (Flag Lifecycle)** — процесс от создания идеи до полного удаления кода. Каждому типу соответствует свой жизненный цикл и модель владения.

---

## Основные концепции

### Классификация по назначению (модель Фаулера)

В современной разработке выделяют четыре основных типа флагов, различающихся по поведению, рискам и владельцам процесса.

| Тип флага | Назначение | Срок жизни | Динамичность | Владелец |
| :--- | :--- | :--- | :--- | :--- |
| **Релизные (Release)** | Скрытие незавершенных фич (Trunk-Based Development) | Краткосрочный (дни/недели) | Низкая (статич./динамич.) | Разработка |
| **Экспериментальные (Experiment)** | A/B-тестирование, проверка продуктовых гипотез | Среднесрочный (недели/месяцы) | Высокая | Product / Data Science |
| **Операционные (Ops)** | Управление надежностью (Kill Switches, Shedding) | Долгосрочный (года/постоянно) | Критическая (Runtime) | SRE / DevOps |
| **Разрешений (Permission)** | Сегментация (Beta, Early Adopters, Premium, RBAC) | Долгосрочный (постоянно) | Высокая | Product / Support |

#### 1. Релизные флаги (Release Toggles)

*   **Цель:** Обеспечение непрерывной интеграции (CI). Позволяют вливать код в `main` до его полной готовности, не блокируя релизный пайплайн.
*   **Особенности:** Обычно двоичные (On/Off). Основной риск — накопление технического долга. Требуют жесткого контроля в бэклоге для своевременного удаления.
*   **Операционная модель (SRE/DevOps):** Владелец — команда разработки. В ночных джобах CI/CD выполняется автоматический аудит: флаги без изменений более 14 дней блокируют мерж новых PR.

#### 2. Экспериментальные флаги (Experiment Toggles)

*   **Цель:** Сбор данных и валидация гипотез. Пользователи делятся на когорты, каждая из которых видит свой вариант реализации.
*   **Особенности:** Результат переключения должен быть **липким** (sticky) — пользователь должен видеть одну и ту же версию на протяжении всего эксперимента, несмотря на перезагрузки или смену устройств.
*   **Операционная модель (SRE/DevOps):** Владелец — Product / Data Science. Обязательна статистическая проверка значимости (p-value < 0.05) перед раскаткой на 100%. TTL жестко привязан к длительности эксперимента.

#### 3. Операционные флаги (Ops Toggles)

*   **Цель:** Защита системы (Safety First). Позволяют мгновенно изменить поведение системы при возникновении инцидентов.
*   **Примеры:** 
    *   **Kill Switch:** Отключение тяжелых функций (например, рекомендаций) при критической нагрузке на БД.
    *   **Graceful Degradation:** Переключение на упрощенную версию алгоритма при отказе внешнего API.
*   **Операционная модель (SRE/DevOps):** Владелец — SRE / DevOps. По умолчанию Kill Switch всегда **включен** (`default=True`), чтобы при отказе FFaaS функция оставалась активной. Требуется four-eyes approval для переключения в Production. Интеграция с Alertmanager через webhook для автоматического отката.

#### 4. Флаги разрешений (Permission Toggles)

*   **Цель:** Управление бизнес-логикой доступа. Отличаются от RBAC тем, что управляют доступностью *функции*, а не просто правами на объект.
*   **Особенности:** Часто используются для «темных запусков» (Dark Launches) и Canary-тестирования на внутренних пользователях.
*   **Операционная модель (SRE/DevOps):** Владелец — Product / Support. Жизненный цикл привязан к тарифным планам. Изменения требуют синхронизации с CRM и биллинг-системой.

### Различие между флагами и конфигурацией

Критически важно разделять эти понятия для правильного выбора инструментария.

| Аспект | Конфигурация (Configuration) | Feature Toggles |
| :--- | :--- | :--- |
| **Природа** | Технические параметры (DB URL, timeouts) | Бизнес-логика выбора пути исполнения |
| **Изменяемость** | Редко (статично при деплое) | Часто (динамично в рантайме) |
| **Доставка** | ConfigMaps, Secrets, `.env` | FFaaS (OpenFeature), Redis, SDK |
| **Цель** | Настройка среды под приложение | Настройка приложения под пользователя/ситуацию |

---

### Техническая привязка (Static vs Dynamic)

| Характеристика | Статическое связывание | Динамическое связывание |
| :--- | :--- | :--- |
| **Место хранения** | Код, переменные окружения, Git (IaC) | FFaaS (Unleash), Redis, Etcd, Vault |
| **Скорость изменения** | Требует перезапуска/редеплоя (Rollout) | Мгновенно (Push/Polling через SDK) |
| **Аудит** | Git history | Audit Log в платформе управления флагами |
| **Типичные флаги** | Релизные (Release) | Операционные (Ops), Экспериментальные |

### Современные паттерны и архитектура (2026+)

#### Контекстуальные флаги (Context-Aware Toggles)

Решение о включении флага принимается на основе контекста запроса:
*   **Пользователь:** ID, роль, страна, время регистрации.
*   **Устройство:** Версия приложения, ОС, тип браузера.
*   **Система:** Загрузка CPU, количество ошибок в соседнем сервисе.

#### Стандарт OpenFeature (CNCF)

В 2026 году промышленным стандартом стал **OpenFeature**. Он предоставляет вендоро-независимый API, позволяющий менять поставщика флагов (например, с Flipt на Unleash) без изменения кода приложения.

#### Интеграция с наблюдаемостью (Tracing Integration)

Состояние флагов автоматически инъектируется в спаны **OpenTelemetry**. Это позволяет при анализе трейсов видеть, какая именно ветка логики сработала для конкретного ошибочного запроса.

### Критерии выбора типа флага

Выбор типа определяется риском, сроком жизни и моделью владения процессом.

| Критерий | Release | Experiment | Ops | Permission |
| :--- | :--- | :--- | :--- | :--- |
| **Приоритет** | Скорость интеграции | Данные для решения | Надежность | Бизнес-доступ |
| **Риск сбоя** | Низкий (скрыт от пользователей) | Средний (когорты) | Критический (защита системы) | Низкий (сегментация) |
| **Владелец** | Разработка | Product / Data Science | SRE / DevOps | Product / Support |
| **TTL** | 1-2 недели | Длительность эксперимента + 7 дней | Постоянно (принцип Kill Switch) | Жизненный цикл фичи |
| **Аппрув** | Tech Lead | Product Owner | SRE Lead + Change Advisory | Product + Legal |

## Практические сценарии

### Сценарий 1: Trunk-Based Development и Релизные флаги

Разработчик создает новую функциональность оплаты через криптовалюты. Код готов на 30%, но его нужно вливать в `main` ежедневно.
*   **Тип флага:** Release Toggle.
*   **Реализация:** Статический флаг `FEATURE_CRYPTO_PAYMENT=false` в коде.
*   **Результат:** Код в проде, но недоступен. CI/CD проходит успешно, риск "merge hell" минимален.

### Сценарий 2: Dark Launching (Темный запуск)

Новая система рекомендаций развернута, но мы не знаем, выдержит ли она нагрузку.
*   **Тип флага:** Permission / Ops Toggle.
*   **Реализация:** Флаг `new-recommender-v2` включается только для 1% трафика в «теневом» режиме (результат считается, но не показывается пользователю, логируется только время ответа).
*   **Результат:** Проверка производительности на реальных данных без риска для UX.

### Сценарий 3: Автоматический Kill Switch

При превышении порога 5xx ошибок в 5% на сервисе заказов, система мониторинга (Prometheus + Alertmanager) вызывает API платформы флагов.
*   **Тип флага:** Ops Toggle.
*   **Реализация:** Отключение флага `enable-third-party-coupons`.
*   **Результат:** Автоматический откат к базовой функциональности, сохранение работоспособности корзины.

### Сценарий 4: Выбор типа флага при инциденте

SRE получает алерт о деградации latency в сервисе рекомендаций. Необходимо быстро определить, какой тип флага использовать для реакции:
*   **Анализ:** Проблема затрагивает всех пользователей, требуется немедленное отключение функциональности.
*   **Решение:** Ops Toggle (Kill Switch) с `default=True` (защита активна при сбое FFaaS).
*   **Действие:** SRE включает флаг через CLI или UI, создает инцидент-тикет, прикрепляет runbook.
*   **Follow-up:** После стабилизации флаг остается включенным до завершения root-cause analysis.

```bash
# Проверка состояния операционных флагов
curl -s "$UNLEASH_URL/api/admin/projects/default/features" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN" | \
  jq '[.features[] | select(.type == "ops") | {name, enabled: .stages[]?.enabled}]'
# → [{"name":"enable-third-party-coupons","enabled":false},...]
```

## Операции и команды

### Управление типами через API FFaaS

```bash
# Создание флага с явным указанием типа (Unleash API)
curl -s -X POST "$UNLEASH_URL/api/admin/projects/default/features" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "new-payment-flow",
    "type": "release",
    "description": "Новый процесс оплаты"
  }'
# → {"name":"new-payment-flow","type":"release",...}

# Фильтрация ops-флагов, включенных в production
curl -s "$UNLEASH_URL/api/admin/projects/default/features" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN" | \
  jq '[.features[] | select(.type == "ops" and .stages[]?.enabled == true) | .name]'
# → ["killswitch-recs", "enable-third-party-coupons"]
```

### Аудит по типам

```bash
# Release флаги без TTL (кандидаты на cleanup)
curl -s "$UNLEASH_URL/api/admin/projects/default/features" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN" | \
  jq '[.features[] | select(.type == "release" and .staleData.potentiallyStale == true) | .name]'
# → ["old-flag-1", "old-flag-2"]

# Ops флаги с неверным значением по умолчанию
curl -s "$UNLEASH_URL/api/admin/projects/default/features" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN" | \
  jq '[.features[] | select(.type == "ops") | 
    select(.variants[0].name != "enabled") | {name, default: .variants[0].name}]'
# → [{"name":"killswitch-wrong-default","default":"disabled"}]
```

### Approval workflow по типам

```bash
# Включение four-eyes для ops и permission флагов
curl -s -X PUT "$UNLEASH_URL/api/admin/projects/default/settings" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "mode": "open",
    "changeRequestEnvironmentConfigs": [
      {
        "environment": "production",
        "requiredApprovals": 2,
        "requiresApproval": true
      }
    ]
  }'
# → Настройки применены
```

## Типичные ошибки и диагностика

### Релизные флаги

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Флаг "забыт" в коде на месяцы | Отсутствие TTL и процесса cleanup | `rg "is_enabled\(['\"]flag-name['\"]\)" src/` — проверка использований | Добавить cleanup-PR в Definition of Done; настроить алерт на возраст >14 дней |
| Merge hell при включении флага | Флаг затрагивает слишком много файлов | `git diff main..feature-branch --stat` — оценка объема | Декомпозировать на атомарные флаги; рефакторинг перед включением |
| Тесты покрывают только одну ветку | Отсутствие toggle-aware testing | `pytest tests/ -k flag_name` — запуск только этой ветки | Параметризовать тесты для обеих веток (On/Off) |

### Экспериментальные флаги

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Результат не липкий (sticky) | Нет session identifier в контексте | Проверить контекст: `user_id` vs `anonymous` | Использовать `user_id` или `session_id` как targeting key |
| Нет статистической значимости | Недостаточный объем выборки | Проверить метрики: `pytest tests/` — проверка p-value | Увеличить длительность; остановка при n < 1000 на группу |
| Пользователь видит обе версии | Отсутствие сессии/куки | Проверить на мобильном приложении | Bootstrap file + persistent cache для mobile |

### Операционные флаги

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Kill Switch не срабатывает | Неверное значение по умолчанию | Проверить `defaultVariant` в FFaaS | Для Ops флагов default всегда `True` (включено) |
| Задержка отключения > 30с | SDK использует polling вместо SSE | `tcpdump -i any port 8013` — проверить протокол | Переключиться на SSE или gRPC streaming |
| FFaaS недоступен, система не деградирует | Отсутствие bootstrap файла | `ls /etc/feature-flags/bootstrap.json` | Развернуть bootstrap в CI/CD; настроить volume mount |

### Флаги разрешений

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Флаг доступен всем пользователям | Отсутствие сегментации (targeting rules) | `curl $UNLEASH_URL/api/admin/projects/default/features/flag-name` — проверить constraints | Настроить targeting rules: `is_staff: true` или `beta_group: in [list]` |
| Утечка экспериментального функционала | Проверка только на клиенте | `rg "is_enabled" src/ --type js` — поиск в клиентском коде | Перенести проверку на сервер; добавить IAM |
| Не синхронизировано с CRM | Флаг не обновляется при смене тарифа | Проверить scheduled job интеграции | Добавить webhook из CRM в FFaaS при изменении тарифного плана |

## Дополнительная информация

### Управление жизненным циклом (Governance)

*   **Инвентаризация:** Регулярный аудит через CI/CD-пайплайн с использованием статического анализа и Prometheus алертов на "мертвые" флаги (100% времени в одном состоянии более 30 дней).
*   **Лимиты:** Установка жестких лимитов на количество активных релизных флагов в команде для предотвращения "комбинаторного взрыва".
*   **Синхронизация сред:** Ежедневный diff флагов между staging и production для предотвращения drift.
