# Обзор Feature Toggles

## Определения

**Feature Toggle (Feature Flag, фиче-флаг)** — это механизм разработки программного обеспечения, позволяющий динамически изменять поведение системы во время выполнения (Runtime) без изменения исходного кода и повторного развертывания (Deploy).

**Progressive Delivery (Прогрессивная поставка)** — современная эволюция CI/CD, которая использует Feature Toggles для постепенного выпуска функционала, контроля «радиуса поражения» (blast radius) и автоматизации процессов на основе метрик.

**Ключевая парадигма:** Полное отделение процесса развертывания кода (**Deployment**) от процесса открытия функционала пользователям (**Release**). Это позволяет доставлять код в эксплуатацию в любое время, активируя его только тогда, когда бизнес и система готовы.

---

## Основные концепции

### Проблема: Долгоживущие ветки и «Merge Hell»

Традиционный подход с использованием долгоживущих веток (Feature Branches) для каждой новой функции приводит к ряду проблем:
- **Сложные слияния (Merge Hell):** Накопление конфликтов за недели разработки.
- **Задержка интеграции:** Код не попадает в `main` до полной готовности, что нарушает принципы Continuous Integration.
- **Риск регрессии:** Трудно предсказать, как несколько новых фич будут взаимодействовать после слияния, так как они никогда не тестировались вместе до этого момента.

### Решение: Trunk-Based Development и Feature Toggles

Feature Toggles являются фундаментом для реализации **[Trunk-Based Development](../../../Git/git_workflows.md#3-trunk-based-development-tbd)**. Разработчики ежедневно интегрируют свой код в основную ветку, даже если функционал не завершен.

Если функция еще не готова, она инкапсулируется в логическую проверку:

```python
# Пример использования флага в коде
if feature_flags.is_enabled("modern_checkout_flow"):
    # Новая реализация (скрыта от пользователей, но присутствует в бинарном файле)
    process_modern_payment()
else:
    # Стабильная старая логика
    process_legacy_payment()
```

**Преимущества подхода:**
- **Continuous Integration (CI):** Код всегда интегрирован. Ошибки несовместимости (например, изменения в общих библиотеках) обнаруживаются мгновенно.
- **Мгновенный откат (Kill Switch):** Если в продуктивной среде обнаружена критическая ошибка, фичу можно выключить за миллисекунды через панель управления без запуска пайплайна деплоя.
- **Shift-Right Testing:** Возможность тестирования на реальных данных и пользователях в production (Canary, Dark Launch) с минимальным риском.

### Наблюдаемость и обратная связь (Feedback Loop)

В 2026 году Feature Toggles неразрывно связаны с системами мониторинга и **OpenTelemetry**:
1.  **Автоматизация:** При превышении порога 5xx ошибок или деградации латентности система управления флагами автоматически отключает вызывающий проблему флаг.
2.  **Телеметрия:** Состояние флагов передается в метаданные трейсов и логов, что позволяет при отладке точно знать, какая ветка кода сработала для конкретного запроса.

### Роль в экосистеме GitOps

В парадигме **GitOps** Feature Toggles позволяют управлять состоянием приложения декларативно. Конфигурация флагов может храниться в Git (через Custom Resources в K8s или ConfigMaps) или в специализированных внешних хранилищах (Unleash, LaunchDarkly, Vault), обеспечивая аудит и версионность изменений в рантайме.

### Компромиссы и цена использования

- **Технический долг:** Каждый флаг — это временный `if/else`. Без дисциплины удаления (Cleanup) кодовая база превращается в «спагетти».
- **Сложность тестирования:** Матрица состояний системы растет экспоненциально. Требуется автоматизация тестирования обеих веток кода (Toggle-aware testing).
- **Безопасность:** Неправильно настроенные флаги могут привести к утечке экспериментального функционала или данных.

## Предварительные требования

Для внедрения Feature Toggles в проект необходима следующая инфраструктура и практики.

### Инструментарий

| Компонент | Назначение | Примеры |
| :--- | :--- | :--- |
| **Платформа управления флагами (FFaaS)** | Централизованное хранение, настройка и вычисление состояний флагов | Unleash (self-hosted), Flipt, LaunchDarkly, Flagsmith, ConfigCat |
| **SDK приложения** | Вычисление состояния флага внутри процесса приложения | OpenFeature SDK (рекомендуется, CNCF Graduated), нативные SDK вендоров |
| **Хранилище конфигурации** | Декларативное управление флагами через Git | ConfigMaps (K8s), Vault, Consul KV, YAML/JSON файлы |
| **Система мониторинга** | Сбор телеметрии по использованию флагов и их влиянию на метрики | Prometheus + Grafana, OpenTelemetry Collector |
| **Система трассировки** | Корреляция состояния флага с конкретным запросом | Jaeger, Grafana Tempo, OpenTelemetry |

### Требования к команде

- **Процесс очистки (Cleanup):** Определенный владелец (Owner) для каждого флага и регламент удаления завершенных флагов. Без этого кодовая база деградирует за месяцы.
- **Соглашение об именовании:** Единый формат именования флагов (например, `[domain].[feature].[action]`) для предотвращения хаоса в реестре.
- **Согласование переключений:** Для критических флагов в Production — процесс аппрува (четыре глаза / four-eyes principle).

### Базовая архитектура

```text
Разработчик → Git (конфигурация флагов) → GitOps-агент → FFaaS / ConfigMap
                                                                    ↓
Приложение ← SDK ← вычисление состояния ← local cache / API
                                                                    ↓
                                                            OpenTelemetry → Мониторинг
```

## Практические сценарии

Feature Toggles позволяют реализовывать следующие стратегии:

### Canary Deployment (Канареечный релиз)

Постепенное открытие функции для групп пользователей (например, 1% → 5% → 25% → 100%). В отличие от сетевого Canary (на уровне Ingress/Envoy), флаги позволяют сегментировать пользователей по произвольным атрибутам приложения (ID, роль, регион, версия клиента).

```python
# Определение контекста пользователя для детерминированного распределения по.bucket'ам
user_context = {
    "user_id": user.id,
    "region": "EU",
    "version": "2.4.0"
}

# SDK вычисляет хеш и проверяет вхождение в диапазон (например, 0-10%)
if ff_client.is_enabled("new-payment-checkout", context=user_context):
    return render_modern_checkout()
return render_legacy_checkout()
```

### A/B/n Тестирование

Сравнение бизнес-метрик (конверсия, доход) или технических метрик разных реализаций. Ключевое требование — «липкость» (Stickiness): один и тот же пользователь должен видеть одну версию на протяжении всего эксперимента.

### Dark Launching (Темный запуск)

Отправка трафика на новую логику «в тени» (результат не показывается пользователю) для проверки производительности под реальной нагрузкой. Результат вычисляется, но не возвращается — только логируется и отправляется в телеметрию.

```python
# Теневой запуск: результат не влияет на ответ пользователю
if ff_client.is_enabled("shadow-search-v2"):
    try:
        shadow_results = v2_engine.search(query)
        compare_and_log(legacy_results, shadow_results)
    except Exception as e:
        logging.error(f"Shadow search failed: {e}")
```

### Permission Toggles (Флаги разрешений)

Включение функций только для сотрудников, бета-тестеров или пользователей с определенным уровнем подписки. Флаги управляют *наличием* функции, а IAM/RBAC — *правом* на её использование. Флаги не заменяют систему авторизации.

```python
context = {
    "user_id": user.id,
    "email": user.email,
    "is_staff": user.is_staff
}

if user.is_staff or ff_client.is_enabled("next-gen-editor", context=context):
    enable_experimental_features()
```

### Миграция БД (Expand-Contract)

Безопасное переключение между старой и новой схемой данных с использованием паттерна **Expand-Contract**. Флаг управляет только логикой *чтения/записи* данных, но не самой структурой таблиц:

1. **Expand:** Новая колонка добавляется, старая не удаляется. Оба пути кода работают.
2. **Dual Write:** Приложение пишет в обе системы. Ошибки в теневой логируются, но не блокируют.
3. **Primary Switch:** Флаг переключает чтение на новую систему.
4. **Contract:** После стабильности старая колонка/система удаляется.

### Kill Switch (Аварийный выключатель)

Мгновенное отключение ресурсоемкой или сбойной функции при деградации инфраструктуры. Флаги операционного типа (Ops Toggles) позволяют реагировать за секунды вместо минут (deploy) или часов (откат версии).

```bash
# Dynamic (Unleash): мгновенное отключение через API
curl -s -X POST "$UNLEASH_URL/api/admin/projects/billing/features/new-checkout/environments/production/off" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN"
# → {"enabled": false}
```

Подробнее см. в документе **[Сценарии использования](./scenarios.md)**.

## Предварительная настройка (Quick Start)

### Шаг 1: Выбор платформы и развёртывание

Для self-hosted варианта (без cloud-зависимостей) рекомендуется **Unleash** или **Flipt**.

```bash
# Unleash через Docker Compose
git clone https://github.com/Unleash/unleash-docker.git
cd unleash-docker
docker compose up -d
# → Доступ: http://localhost:4242 (admin/unleash4all)
```

### Шаг 2: Создание первого флага

Через UI или API:

```bash
# Создание фlags через Unleash API
curl -s -X POST "$UNLEASH_URL/api/admin/projects/default/features" \
  -H "Authorization: $UNLEASH_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "new-checkout-flow",
    "type": "release",
    "description": "Управление новым процессом оформления заказа"
  }'
# → {"name":"new-checkout-flow","type":"release",...}
```

### Шаг 3: Интеграция SDK в приложение (Python + OpenFeature)

```python
from openfeature import api
from openfeature.contrib.provider.unleash import UnleashProvider
from opentelemetry import trace

tracer = trace.get_tracer(__name__)

# Настройка провайдера (обычно в main.py / app.py)
api.set_provider(UnleashProvider(
    url="https://ff-api.internal/api",
    app_name="checkout-service"
))

# Бизнес-логика
def process_checkout(user_id: str, cart_total: float):
    client = api.get_client()
    context = {"user_id": user_id, "cart_total": cart_total}

    with tracer.start_as_current_span("checkout_process") as span:
        is_modern_v3 = client.get_boolean_value("checkout-v3-enabled", False, context)
        # Обязательная фиксация в телеметрии
        span.set_attribute("feature_flag.checkout_v3", is_modern_v3)

        if is_modern_v3:
            return run_modern_workflow(user_id)
        return run_legacy_workflow(user_id)
```

### Шаг 4: Проверка работоспособности

```bash
# Проверка через API платформы
curl -s "$UNLEASH_URL/api/client/features" \
  -H "Authorization: $UNLEASH_FRONTEND_TOKEN" | jq '.features[] | select(.name=="new-checkout-flow")'
# → {"name":"new-checkout-flow","enabled":true,...}

# Проверка через SDK (в приложении)
# Результат: True или False в зависимости от состояния флага и контекста
```

## Валидация и тестирование

### Что проверять

| Проверка | Метод | Ожидаемый результат |
| :--- | :--- | :--- |
| Флаг создан и доступен | API-запрос к платформе | Флаг возвращается в списке активных |
| Значение по умолчанию | SDK с пустым контекстом | Возвращает `False` (для новых фич) или значение `defaultVariant` |
| Таргетинг по проценту | Генерация 1000 запросов с разными `user_id` | ~10% получают `True` при настройке `10%` |
| «Липкость» (Stickiness) | Два запроса с одним `user_id` | Оба возвращают одинаковое значение |
| Fail-safe при недоступности FFaaS | Остановка сервера флагов, запрос к приложению | Приложение работает в safestate (все новые фичи выключены) |
| Инъекция в OpenTelemetry | Запрос → проверка спана в Jaeger/Tempo | Атрибут `feature_flag.*` присутствует в спане |

### Автоматизация тестирования

| Уровень теста | Подход | Практика |
| :--- | :--- | :--- |
| **Unit-тесты** | Toggle-aware testing | Параметризация для запуска тестов в обоих состояниях (`On/Off`) |
| **Интеграционные** | Shadow Testing | Новая логика в фоне, результаты сравниваются, но не возвращаются |
| **E2E / QA** | Matrix Testing | Стандартный набор (все флаги Off) + целевой (все флаги раскатки On) |
| **Смок-тесты** | Default State Validation | Проверка старта приложения при недоступности FFaaS |

## Типичные проблемы и решение

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Флаг не переключается через UI | SDK кеширует старое значение | Убедиться, что SDK настроен на polling/sse (сINCT intervals); проверить `maxAge` в конфигурации провайдера |
| Приложение падает при недоступности FFaaS | Отсутствие fail-safe значений по умолчанию | Каждая проверка флага обязана содержать fallback-значение: `get_boolean_value("flag", False)` |
| Флаги живут годами, код оброс ветвлениями | Нет процесса удаления | Expiration-даты, cleanup-PR обязательным пунктом Definition of Done, лимит активных флагов на сервис |
| Тесты взрываются от числа комбинаций | Все флаги тестируются во всех сочетаниях | CI гоняет дефолтную конфигурацию; комбинации — точечные e2e только для активных раскаток |
| Оценка флага добавляет latency | Ход в удаленную платформу на каждый вызов | Локальный flagd/sidecar, кеширование провайдера; платформа — источник истины, не hot path |
| Прод ведет себя не как staging | Разные значения флагов в средах | Декларативное управление через GitOps; diff флагов между средами — часть ревью PR |
| Утечка экспериментального функционала | Флаг доступен всем пользователям без сегментации | Настроить targeting rules: флаг доступен только определенным сегментам (staff, beta, определенный регион) |
| Неконсистентность данных при Dual Write | Флаг переключил запись до завершения Backfill | Расширенный паттерн Expand-Contract: флаг управляет только логикой чтения/записи, но не структурой таблиц |

## Ограничения и особые случая

### Когда Feature Toggles НЕ подходят

- **Простые CRUD-приложения** без альтернативных веток логики — Overhead от инфраструктуры флагов не окупается.
- **Критические пути с нулевой容忍 к latency** — каждая проверка флага добавляет вычисления (хотя и `O(1)` при локальном вычислении). В high-frequency trading или real-time bidding этот overhead может быть неприемлем.
- **Замена системы авторизации** — флаги не предназначены для обеспечения безопасности. Злоумышленник может подменить контекст на клиенте.

### Ограничения по архитектуре

- **Комбинаторный взрыв:** 10 независимых бинарных флагов дают 1024 состояния системы. Необходимо ограничивать количество одновременно активных релизных флагов на сервис (типично: 5-10).
- **Глобальные побочные эффекты:** Если два флага влияют на один глобальный ресурс (переменную окружения, запись в БД) в несовместимых режимах — возникает коллизия. Требуется группировка флагов по доменам и конфликт-тестирование.
- **Миграции БД:** Флаги не должны управлять структурой таблиц. Попытка изменять схему БД внутри логических условий флага приводит к разрыву между состоянием кода и схемы.

### Edge Cases в Production

- **Одновременное включение нескольких экспериментов:** Если два A/B-теста затрагивают один и тот же UI-компонент, результаты могут быть искажены. Необходимо выявлять пересечения и запускать их последовательно или исключать пересекающуюся аудиторию.
- **Кэширование на CDN/瀏覽器:** Если флаг определяет видимость элемента UI, а страница кэшируется CDN или браузером, пользователь может видеть устаревшее состояние. Решение: не кэшировать страницы с активными флагами или добавлять `Cache-Control: no-cache` для путей с флагами.
- **Offline-режим (Mobile):** При отсутствии сети SDK не может получить обновленное значение флага. Используйте bootstrap-файл (последнее известное состояние) или hardcoded fallback.
