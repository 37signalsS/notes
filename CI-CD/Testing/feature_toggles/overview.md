# Обзор Feature Toggles

## Определения

**Feature Toggle (Feature Flag)** — это механизм разработки программного обеспечения, позволяющий динамически изменять поведение системы во время выполнения (Runtime) без изменения исходного кода и повторного развертывания (Deploy).

**Progressive Delivery (Прогрессивная поставка)** — современная эволюция CI/CD, которая использует Feature Toggles для постепенного выпуска функционала, контроля радиуса поражения (blast radius) и автоматизации откатов на основе метрик.

**Ключевая концепция:** Полное отделение процесса развертывания кода (**Deployment**) от процесса открытия функционала пользователям (**Release**).

---

## Основные концепции

### Проблема: Долгоживущие ветки и «Merge Hell»

Традиционный подход с использованием долгоживущих веток (Feature Branches) для каждой новой функции приводит к ряду проблем:
- **Сложные слияния (Merge Hell):** Накопление конфликтов за недели разработки.
- **Задержка интеграции:** Код не попадает в `main` до полной готовности, что нарушает принципы Continuous Integration.
- **Риск регрессии:** Трудно предсказать, как несколько новых фич будут взаимодействовать после слияния.

### Решение: Trunk-Based Development и Feature Toggles

Feature Toggles являются критически важным инструментом для реализации **[Trunk-Based Development](../../../Git/git_workflows.md#3-trunk-based-development-tbd)**. Все разработчики ежедневно интегрируют свой код в основную ветку.

Если функция еще не готова, она инкапсулируется в логическую проверку:

```python
# Пример использования флага в коде
if feature_flags.is_enabled("new_payment_gateway"):
    # Новая реализация (скрыта до готовности)
    process_modern_payment()
else:
    # Стабильная старая логика
    process_legacy_payment()
```

**Преимущества подхода:**
- **Continuous Integration (CI):** Код всегда интегрирован. Ошибки несовместимости обнаруживаются мгновенно.
- **Мгновенный откат (Kill Switch):** Если в production обнаружена ошибка, фичу можно выключить за миллисекунды без передеплоя.
- **Разделение ответственности:** Инженеры отвечают за *deployment* (доставку кода), а бизнес/продукт — за *release* (открытие фичи пользователям).

### Роль в экосистеме GitOps

В парадигме **GitOps** Feature Toggles позволяют управлять состоянием приложения декларативно. Конфигурация флагов может храниться в Git или внешнем хранилище (ConfigMap в Kubernetes, Vault, LaunchDarkly), обеспечивая наблюдаемость и аудит всех изменений в рантайме.

### Компромиссы и цена использования

- **Технический долг:** Каждый флаг — это временная условная логика. Без процесса очистки (Cleanup) код становится трудночитаемым.
- **Сложность тестирования:** Матрица состояний системы растет экспоненциально с количеством флагов.
- **Управление конфигурацией:** Требуется надежная инфраструктура для доставки флагов (FFaaS — Feature Flags as a Service).

## Практические сценарии

Feature Toggles позволяют реализовывать стратегии, подробно описанные в документе **[Сценарии использования](./scenarios.md)**:

- **Canary Deployment:** Постепенное открытие функции (1% → 10% → 100% трафика).
- **A/B Тестирование:** Сравнение конверсии или производительности разных реализаций.
- **Dark Launching:** Нагрузочное тестирование нового кода в production без изменения UI для пользователя.
- **Permission Toggles:** Включение функций только для определенных групп (Beta-тестеры, сотрудники).
