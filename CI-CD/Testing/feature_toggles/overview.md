# Обзор Feature Toggles

## Определения

**Feature Toggle (Feature Flag, фиче-флаг)** — это механизм разработки программного обеспечения, позволяющий динамически изменять поведение системы во время выполнения (Runtime) без изменения исходного кода и повторного развертывания (Deploy).

**Progressive Delivery (Прогрессивная поставка)** — современная эволюция CI/CD, которая использует Feature Toggles для постепенного выпуска функционала, контроля «радиуса поражения» (blast radius) и автоматизации процессов на основе метрик.

**Ключевая парадигма:** Полное отделение процесса развертывания кода (**Deployment**) от процесса открытия функционала пользователям (**Release**). Это позволяет доставлять код в эксплуатацию в любое время, активируя его только тогда, когда бизнес и система готовы.

## Основные концепции

### Проблема: Долгоживущие ветки и «Merge Hell»

Традиционный подход с использованием долгоживущих веток (Feature Branches) для каждой новой функции приводит к ряду проблем:
- **Сложные слияния (Merge Hell):** Накопление конфликтов за недели разработки.
- **Задержка интеграции:** Код не попадает в `main` до полной готовности, что нарушает принципы Continuous Integration.
- **Риск регрессии:** Трудно предсказать, как несколько новых фич будут взаимодействовать после слияния, так как они никогда не тестировались вместе до этого момента.

### Решение: Trunk-Based Development и Feature Toggles

Feature Toggles являются фундаментом для реализации **[Trunk-Based Development](../../../Git/git_workflows.md#3-trunk-based-development-tbd)**. Разработчики ежедневно интегрируют свой код в основную ветку, даже если функционал не завершен.

Если функция еще не готова, она инкапсулируется в логическую проверку:

```python
# Пример использования флага в коде
if feature_flags.is_enabled("modern_checkout_flow"):
    # Новая реализация (скрыта от пользователей, но присутствует в бинарном файле)
    process_modern_payment()
else:
    # Стабильная старая логика
    process_legacy_payment()
```

**Преимущества подхода:**
- **Continuous Integration (CI):** Код всегда интегрирован. Ошибки несовместимости (например, изменения в общих библиотеках) обнаруживаются мгновенно.
- **Мгновенный откат (Kill Switch):** Если в продуктивной среде обнаружена критическая ошибка, фичу можно выключить за миллисекунды через панель управления без запуска пайплайна деплоя.
- **Shift-Right Testing:** Возможность тестирования на реальных данных и пользователях в production (Canary, Dark Launch) с минимальным риском.

### Наблюдаемость и обратная связь (Feedback Loop)

В 2026 году Feature Toggles неразрывно связаны с системами мониторинга и **OpenTelemetry**:
1.  **Автоматизация:** При превышении порога 5xx ошибок или деградации латентности система управления флагами автоматически отключает вызывающий проблему флаг.
2.  **Телеметрия:** Состояние флагов передается в метаданные трейсов и логов, что позволяет при отладке точно знать, какая ветка кода сработала для конкретного запроса.

### Роль в экосистеме GitOps

В парадигме **GitOps** Feature Toggles позволяют управлять состоянием приложения декларативно. Конфигурация флагов может храниться в Git (через Custom Resources в K8s или ConfigMaps) или в специализированных внешних хранилищах (Unleash, LaunchDarkly, Vault), обеспечивая аудит и версионность изменений в рантайме.

### Компромиссы и цена использования

- **Технический долг:** Каждый флаг — это временный `if/else`. Без дисциплины удаления (Cleanup) кодовая база превращается в «спагетти».
- **Сложность тестирования:** Матрица состояний системы растет экспоненциально. Требуется автоматизация тестирования обеих веток кода (Toggle-aware testing).
- **Безопасность:** Неправильно настроенные флаги могут привести к утечке экспериментального функционала или данных.

## Практические сценарии

Feature Toggles позволяют реализовывать следующие стратегии:

- **Canary Deployment:** Постепенное открытие функции для групп пользователей (например, 1% → 5% → 25% → 100%).
- **A/B/n Тестирование:** Сравнение бизнес-метрик (конверсия, доход) или технических метрик разных реализаций.
- **Dark Launching:** Отправка трафика на новую логику «в тени» (результат не показывается пользователю) для проверки производительности под реальной нагрузкой.
- **Permission Toggles:** Включение функций только для сотрудников, бета-тестеров или пользователей с определенным уровнем подписки.
- **Миграция БД:** Безопасное переключение между старой и новой схемой данных с использованием паттерна **Expand-Contract**.

Подробнее см. в документе **[Сценарии использования](./scenarios.md)**.
