# Антипаттерны Feature Toggles

## Определения

**Антипаттерн Feature Toggle** — это распространенный, но неэффективный или рискованный способ использования флагов, который приводит к неоправданному усложнению кода, росту технического долга и возникновению труднодиагностируемых ошибок.

---

## Основные концепции

### Категории антипаттернов

Антипаттерны классифицируются по области их негативного воздействия:

| Категория | Описание | Примеры |
| :--- | :--- | :--- |
| **Структурные** | Нарушение чистоты и читаемости кода | Избыточная вложенность, размазывание логики |
| **Операционные** | Ошибки управления жизненным циклом | "Мертвые" флаги, отсутствие мониторинга |
| **Архитектурные** | Ошибки проектирования систем | Миграции БД внутри флага, нарушение контрактов API |

---

## Практические сценарии

### 1. Избыточная сложность логики

**Проблема:** Создание запутанных условий, зависящих от комбинации нескольких независимых флагов. Это делает код практически нечитаемым и невозможным для полного покрытия тестами.

**Пример (Bad Practice):**
```python
if (ff.is_enabled('feature-a') and 
    ff.is_enabled('feature-b') and 
    not ff.is_enabled('feature-c')):
    execute_complex_logic()
```

**Решение:** Объединяйте зависимые флаги в один высокоуровневый переключатель или выносите логику принятия решения в специализированный сервис (Decision Service).

### 2. Вложенные флаги (Nested Toggles)

**Проблема:** Использование одной проверки флага внутри другой. Это приводит к экспоненциальному росту количества состояний системы, которые необходимо протестировать и поддерживать.

**Решение:** Стремитесь к плоской структуре проверок. Если функциональность B зависит от функциональности A, управляйте этой зависимостью на уровне системы управления флагами (например, через зависимости в Unleash).

### 3. "Мертвые" флаги и технический долг

**Проблема:** Флаги, которые были полностью внедрены на 100% трафика или навсегда отключены, но их код не был удален. Это создает "информационный шум" и увеличивает когнитивную нагрузку на разработчиков.

**Решение:** Внедрите процесс обязательной очистки (Cleanup) сразу после стабилизации фичи. См. **[процесс удаления устаревших флагов](./best_practices.md#сценарий-1-процесс-удаления-устаревших-флагов)**.

### 4. Управление схемой БД через флаги

**Проблема:** Попытка управлять миграциями базы данных (добавление колонок, таблиц) с помощью Feature Toggles. Это крайне рискованно, так как база данных имеет общее состояние, а флаги могут иметь разное значение для разных инстансов приложения.

**Решение:** Миграции БД должны быть обратно совместимыми и выполняться отдельно от включения флага. Флаг должен управлять только тем, *как* приложение использует данные, а не самой структурой данных.

### 5. Нарушение контрактов API

**Проблема:** Изменение структуры ответа или параметров запроса API в зависимости от флага. Это ломает клиентов, которые ожидают стабильного контракта.

**Решение:** Используйте версионирование API. Флаг может переключать маршрутизацию между версиями (v1 -> v2), но не менять структуру данных внутри одной версии "на лету".
