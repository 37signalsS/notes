# Анти-паттерны Feature Toggles

### Определения

- **Анти-паттерн Feature Toggle** — это распространенный, но неэффективный или рискованный способ использования флагов, который приводит к увеличению сложности кода, техническому долгу и потенциальным ошибкам.

### Основные анти-паттерны

#### 1. Слишком много флагов и сложная логика

- **Проблема:** Создание сложной, запутанной логики из комбинаций нескольких флагов. Код становится трудно читать, тестировать и поддерживать.
- **Пример:**

  ```python
  # ❌ Плохо: сложная логика
  if (ff.is_enabled('feature-a') and 
      ff.is_enabled('feature-b') and 
      not ff.is_enabled('feature-c')):
      do_something()
  ```

#### 2. Вложенные флаги (Nested Toggles)

- **Проблема:** Один флаг находится внутри логики другого. Это экспоненциально увеличивает количество состояний, которые нужно тестировать, и делает поведение системы непредсказуемым.
- **Пример:**

  ```python
  # ❌ Плохо: сложно понять и тестировать
  if ff.is_enabled('outer-feature'):
      if ff.is_enabled('inner-feature'):
          do_complex_thing()
  ```

#### 3. "Мертвые" флаги

- **Проблема:** Флаги, которые были полностью внедрены (100% трафика) или отключены, но не удалены из кода. Они загрязняют кодовую базу и создают технический долг.

#### 4. Изменение схемы БД внутри флага

- **Проблема:** Попытка управлять миграциями базы данных с помощью feature toggle. Миграции схемы должны выполняться отдельно и быть обратно совместимыми, а флаг должен управлять только логикой приложения, которая использует новую схему.
- **Пример:**

  ```sql
  -- ❌ Плохо: опасно!
  -- Миграция должна выполняться всегда, вне логики флага
  ALTER TABLE users ADD COLUMN new_field VARCHAR(255);
  ```
