# Анти-паттерны Feature Toggles

## Определения

**Анти-паттерн Feature Toggle** — распространенный, но неэффективный или рискованный способ использования флагов, приводящий к увеличению сложности кода, техническому долгу и потенциальным ошибкам.

---

## Базовые концепции

### Классификация анти-паттернов

Анти-паттерны делятся на категории по области воздействия:

| Категория | Описание | Примеры |
| :--- | :--- | :--- |
| **Структурные** | Проблемы организации кода и логики | Сложная логика, вложенные флаги |
| **Операционные** | Проблемы жизненного цикла флагов | Мертвые флаги |
| **Архитектурные** | Проблемы интеграции с другими системами | Миграции базы данных (БД), семантика API |

---

## Практические сценарии

### 1. Слишком много флагов и сложная логика

**Проблема:** Создание запутанной логики из комбинаций нескольких флагов. Код становится трудно читать, тестировать и поддерживать.

**Пример:**

```python
# Плохо: сложная логика
if (ff.is_enabled('feature-a') and
    ff.is_enabled('feature-b') and
    not ff.is_enabled('feature-c')):
    do_something()
```

**Решение:** Объединить связанные флаги в один многовариантный флаг или вынести логику в отдельный сервис решений.

---

### 2. Вложенные флаги (Nested Toggles)

**Проблема:** Один флаг находится внутри логики другого. Экспоненциально увеличивается количество состояний для тестирования, поведение системы становится непредсказуемым.

**Пример:**

```python
# Плохо: сложно понять и тестировать
if ff.is_enabled('outer-feature'):
    if ff.is_enabled('inner-feature'):
        do_complex_thing()
```

**Решение:** Использовать плоскую структуру проверок или комбинированные флаги на уровне конфигурации.

---

### 3. Мертвые флаги

**Проблема:** Флаги, полностью внедренные (100% трафика) или отключенные, но не удаленные из кода. Загрязняют кодовую базу и создают технический долг. Критично для **[релизных флагов](./types.md#1-релизные-флаги-release-toggles)**.

**Решение:** Следовать **[процессу удаления устаревших флагов](./best_practices.md#сценарий-1-процесс-удаления-устаревших-флагов)**:

1. Включить флаг для всех пользователей (100%)
2. Подождать 1–2 недели, наблюдая за стабильностью
3. Создать задачу на удаление `if/else` и самого флага
4. Удалить флаг из кода и системы управления

---

### 4. Изменение схемы БД внутри флага

**Проблема:** Управление миграциями базы данных через feature toggle. Миграции схемы должны выполняться отдельно и быть обратно совместимыми, флаг управляет только логикой приложения.

**Пример:**

```sql
-- Плохо: опасно!
-- Миграция должна выполняться всегда, вне логики флага
ALTER TABLE users ADD COLUMN new_field VARCHAR(255);
```

**Решение:** Миграции выполняются до включения флага. Флаг переключает логику приложения на использование новой схемы.

---

### 5. Флаги, изменяющие семантику API

**Проблема:** Изменение контракта API через флаг (добавление/удаление полей в JSON, изменение типа). Нарушает обратную совместимость, ломает клиентов.

**Решение:** Создать новую версию API (v2) или добавить опциональные поля, которые клиенты могут безопасно игнорировать. Флаг перенаправляет трафик на новую реализацию, контракт остается стабильным.
