# Антипаттерны Feature Toggles

## Определения

**Антипаттерн Feature Toggle** — это распространенный, но неэффективный или рискованный способ использования флагов, который приводит к росту технического долга, деградации производительности и возникновению труднодиагностируемых ошибок в рантайме.

---

## Основные концепции

### Категории антипаттернов

Антипаттерны классифицируются по области их негативного воздействия на систему и процесс разработки.

| Категория | Описание | Основной риск |
| :--- | :--- | :--- |
| **Кодовые** | Нарушение чистоты и читаемости кода | Трудности поддержки, "спагетти-код" |
| **Эксплуатационные** | Ошибки управления и мониторинга | "Мертвые" флаги, сбои в Production |
| **Архитектурные** | Ошибки проектирования и интеграции | Нарушение безопасности, деградация БД |

---

## Практические сценарии

### 1. Избыточная сложность логики

**Проблема:** Создание условий, зависящих от комбинации нескольких независимых флагов. Это делает код практически нечитаемым и невозможным для полного покрытия тестами.

**Пример (Bad Practice):**
```python
if ff.is_enabled('feature-a') and ff.is_enabled('feature-b') and not ff.is_enabled('feature-c'):
    execute_complex_logic()
```

**Решение:** Объединяйте зависимые флаги в один высокоуровневый переключатель или выносите логику принятия решения в специализированный сервис (Decision Service).

### 2. Вложенные флаги (Nested Toggles)

**Проблема:** Использование одной проверки флага внутри другой. Это приводит к экспоненциальному росту количества состояний системы.

**Решение:** Стремитесь к плоской структуре проверок. Управляйте зависимостями на уровне системы управления флагами (например, в Unleash или LaunchDarkly через родительские связи).

### 3. "Мертвые" флаги и технический долг

**Проблема:** Флаги, код которых не был удален после 100% раскатки. Это создает информационный шум и риск случайного переключения устаревшей логики.

**Решение:** 
- Используйте **Stale Flag Detectors** (автоматические сканеры кода).
- Назначайте **TTL (Time to Live)** для каждого релизного флага.
- См. **[процесс удаления флагов](./best_practices.md#сценарий-1-процесс-удаления-устаревших-флагов)**.

### 4. Нарушение безопасности (Secrets in Flags)

**Проблема:** Использование флагов для передачи секретов (API-ключи, пароли) в открытом виде.

**Решение:** Флаг должен содержать только логику (On/Off) или нечувствительные параметры. Секреты должны извлекаться из специализированных хранилищ (Vault, AWS Secrets Manager) после проверки состояния флага.

### 5. Деградация производительности (Performance Overhead)

**Проблема:** Частые удаленные вызовы к серверу управления флагами без кэширования внутри каждого запроса или цикла.

**Решение:** Используйте SDK с поддержкой локального кэширования и асинхронного обновления состояний флагов (Streaming/Polling).

### 6. "Тестовая слепота" (Testing Only One State)

**Проблема:** Тестирование кода только при включенном или только при выключенном флаге.

**Решение:** Критически важная логика должна иметь автоматизированные тесты для обоих состояний флага. Используйте параметризованные тесты для проверки всех веток.

### 7. Управление схемой БД через флаги

**Проблема:** Попытка управлять миграциями БД внутри условий флага.

**Решение:** Миграции должны быть обратно совместимыми. Флаг управляет только *использованием* данных, а не их структурой. См. **[Сценарии миграции данных](./scenarios.md#сценарий-5-миграция-данных-shadow-read-dual-write)**.
