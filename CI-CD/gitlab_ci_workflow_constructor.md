# GitLab CI как конструктор Workflow

GitLab CI — это не просто инструмент для сборки и тестирования кода. Его гибкость позволяет использовать его как универсальный конструктор для автоматизации практически любых процессов (workflow), даже не связанных напрямую с кодом, например, для задач по расписанию (аналог cron) или управления инфраструктурой.

Ключевая идея — описание всего процесса в декларативном `.gitlab-ci.yml` файле, который хранится вместе с кодом, обеспечивая версионируемость и прозрачность.

## Основные строительные блоки

-   **`stages`**: Определяют последовательность выполнения этапов (например, `build`, `test`, `deploy`). Задания внутри одного этапа выполняются параллельно, но переход к следующему этапу происходит только после успешного завершения всех заданий в текущем.
-   **`jobs`**: Конкретные задачи, выполняемые Runner'ами. Каждое задание привязано к определённому этапу.
-   **`artifacts`**: Результаты выполнения задания (собранные бинарные файлы, отчёты о тестах), которые сохраняются на сервере GitLab и могут передаваться между заданиями, даже на разных Runner'ах. Артефакты имеют срок хранения.

    GitLab CI поддерживает несколько типов специализированных отчетов и файлов для артефактов:

    -   **`artifacts:reports`**: Используется для загрузки отчетов в формате, понятном GitLab. Это позволяет визуализировать результаты тестов, покрытия кода, SAST-сканирований и других проверок прямо в интерфейсе GitLab.
        -   **`junit`**: Отчеты о модульных и интеграционных тестах в формате JUnit XML, отображаются на вкладке "Tests" в Pipeline.
        -   **`cobertura`**: Отчеты о покрытии кода, отображаются в Merge Request'ах.
        -   **`sast`**, **`dast`**, **`dependency_scanning`** и другие: Отчеты о безопасности, интегрируются в Security Dashboard.

        ```yaml
        test_job:
          stage: test
          script:
            - run_tests.sh
          artifacts:
            reports:
              junit: junit-report.xml
              cobertura: coverage.xml
        ```

    -   **`artifacts:dotenv`**: Позволяет передавать переменные окружения между заданиями в рамках одного пайплайна. Эти переменные автоматически загружаются в окружение последующих заданий, делая их доступными без необходимости явного экспорта.

        ```yaml
        setup_job:
          stage: setup
          script:
            - echo "MY_VARIABLE=hello" > build.env
            - echo "ANOTHER_VAR=world" >> build.env
          artifacts:
            reports:
              dotenv: build.env

        deploy_job:
          stage: deploy
          script:
            - echo $MY_VARIABLE $ANOTHER_VAR # Выведет "hello world"
          needs:
            - job: setup_job
              artifacts: true # Важно, чтобы артефакты были доступны
        ```
-   **`cache`**: Механизм для сохранения файлов между запусками пайплайнов на одном и том же Runner'е (например, `node_modules` или `.m2`). Его цель — ускорение сборок. Кэш не гарантирует наличие данных, в отличие от артефактов.

## Runners и Executors

**GitLab Runner** — это агент, который выполняет задания из вашего пайплайна. Он может быть установлен на отдельном сервере, в Docker-контейнере или в кластере Kubernetes. Ключевым компонентом Runner'а является **Executor** — механизм, который определяет, как и где будет выполняться скрипт задания.

Выбор Executor'а — это компромисс между скоростью, безопасностью и сложностью настройки.

### Основные типы Executors:

-   **`shell`**:
    -   **Принцип работы:** Запускает команды непосредственно на машине, где установлен Runner, от имени пользователя `gitlab-runner`.
    -   **Плюсы:**
        -   **Простота и скорость:** Нет накладных расходов на создание контейнеров или виртуальных машин.
        -   **Прямой доступ к хосту:** Удобно для задач, которым нужен прямой доступ к аппаратным ресурсам или системным сервисам (например, управление Docker-демоном хоста).
    -   **Минусы:**
        -   **Слабая изоляция:** Задания могут влиять друг на друга и на состояние хост-машины (например, изменять системные файлы, оставлять "мусор").
        -   **Конфликты зависимостей:** Все зависимости (версии Node.js, Python, и т.д.) должны быть установлены на хост-машине, что усложняет управление окружением.

-   **`docker`**:
    -   **Принцип работы:** Для каждого задания создается чистый Docker-контейнер из указанного в `image` образа. Скрипт выполняется внутри этого контейнера.
    -   **Плюсы:**
        -   **Сильная изоляция:** Окружение каждого задания полностью изолировано. Нет конфликтов зависимостей.
        -   **Гибкость окружения:** Можно использовать любой Docker-образ из любого registry, что позволяет легко подбирать нужные версии ПО для каждого задания.
        -   **Чистота:** После выполнения задания контейнер удаляется, не оставляя следов.
    -   **Минусы:**
        -   **Накладные расходы:** Требуется время на скачивание образа и запуск контейнера.
        -   **Сложности с Docker-in-Docker:** Если внутри задания нужно собирать Docker-образы (`docker build`), требуется специальная настройка (например, проброс Docker-сокета с хоста, что небезопасно, или использование инструментов вроде Kaniko).

-   **`kubernetes`**:
    -   **Принцип работы:** Для каждого задания создается новый Pod в кластере Kubernetes.
    -   **Плюсы:**
        -   **Масштабируемость и отказоустойчивость:** Позволяет динамически масштабировать количество одновременно выполняемых заданий, используя ресурсы всего кластера.
        -   Все преимущества `docker` executor (изоляция, гибкость).
    -   **Минусы:**
        -   **Сложность настройки:** Требует наличия и настройки кластера Kubernetes.

-   **`virtualbox` / `parallels`**:
    -   **Принцип работы:** Для каждого задания клонируется и запускается виртуальная машина из заранее подготовленного "золотого" образа.
    -   **Плюсы:**
        -   **Максимальная изоляция:** Полная изоляция на уровне операционной системы.
    -   **Минусы:**
        -   **Очень медленно:** Самый медленный из всех типов из-за времени на запуск ВМ.
        -   Используется редко, в основном для специфических задач (например, сборка десктопных приложений под определенную ОС).

**Рекомендация:** В большинстве случаев **`docker` executor** является лучшим выбором, так как он предоставляет отличный баланс между изоляцией, гибкостью и производительностью. Для крупных систем с высокими требованиями к масштабированию предпочтителен **`kubernetes` executor**.

## Создание переиспользуемых и композитных пайплайнов

GitLab CI предоставляет мощные механизмы для избежания дублирования кода и создания гибких, модульных пайплайнов.

### 1. `extends` — Наследование конфигураций

Механизм `extends` позволяет заданию унаследовать всю конфигурацию от другого, "скрытого" задания (начинающегося с точки). Это базовый способ переиспользования.

```yaml
.base_job:
  image: ruby:2.7
  script:
    - echo "This is from the base job."

test_job:
  extends: .base_job
  script:
    - echo "This is from the test job. It will run after the base script."
    # Важно: скрипт из .base_job будет объединён со скриптом test_job.
```

### 2. `!reference` — Ссылка на конкретные ключи

Если нужно переиспользовать не всю конфигурацию, а только её часть (например, только `script`), можно использовать YAML-якоря или тег `!reference`.

```yaml
.base_scripts:
  script:
    - echo "Step 1"
    - echo "Step 2"

job1:
  script:
    - !reference [.base_scripts, script]
    - echo "Step 3 for job1"
```

### 3. `include` — Композиция из внешних файлов

`include` — один из самых мощных механизмов, позволяющий собрать пайплайн из нескольких YAML-файлов. Это делает конфигурацию модульной и легко управляемой.

Поддерживаемые источники:

-   **`include:local`**: Файл из того же репозитория.
    ```yaml
    include: '/templates/.build-template.yml'
    ```
-   **`include:project`**: Файл из другого проекта в том же инстансе GitLab.
    ```yaml
    include:
      - project: 'my-group/my-ci-templates'
        ref: main
        file: '/maven-build.yml'
    ```
-   **`include:remote`**: Файл по URL.
    ```yaml
    include:
      - remote: 'https://example.com/ci-config.yml'
    ```
-   **`include:template`**: Встроенные шаблоны GitLab (например, для `Node.js`, `Docker`, `SAST`).
    ```yaml
    include:
      - template: Security/SAST.gitlab-ci.yml
    ```

### 4. CI/CD Catalog (Components)

Новый подход к переиспользованию, позволяющий создавать версионируемые **компоненты** — полноценные, изолированные блоки CI/CD логики, которые можно публиковать в общем каталоге и использовать в проектах.

```yaml
include:
  - component: '$CI_SERVER_HOST/my-org/my-component@1.0'
    inputs:
      stage: build
```

## Расширенное управление Workflow

### `rules` — Гибкие правила запуска

`rules` — это более мощная и гибкая альтернатива `only/except`. Они позволяют определять сложные условия для запуска заданий. Правила проверяются по порядку, и первое совпадение определяет, будет ли задание добавлено в пайплайн.

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying to production"
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"' # Запускать только для ветки main
    - if: '$CI_PIPELINE_SOURCE == "schedule"' # Запускать по расписанию
    - if: '$CI_COMMIT_TAG' # Запускать для тегов
    - when: manual # Во всех остальных случаях — запускать вручную
      allow_failure: true
```
Задачи по расписанию (Cron-like): GitLab CI можно использовать для выполнения задач по расписанию, аналогично `cron` в Linux. Это делается путем создания "Расписания" (Schedules) для пайплайна через интерфейс GitLab. В `rules` можно использовать `$CI_PIPELINE_SOURCE == "schedule"` для запуска определенных заданий только при таком типе триггера.

### `needs` — Построение направленного ациклического графа (DAG)

Ключевая возможность для оптимизации времени выполнения пайплайна. `needs` позволяет заданию стартовать, как только завершатся указанные в `needs` задания, не дожидаясь окончания всего предыдущего этапа. Это ломает строгую последовательность `stages` и превращает пайплайн в DAG.

```yaml
build:android:
  stage: build
  script:
    - ./build-android.sh

test:android:
  stage: test
  needs: ["build:android"] # Запустится сразу после build:android
  script:
    - ./test-android.sh

deploy:android:
  stage: deploy
  needs: ["test:android"]
  script:
    - ./deploy-android.sh
```

### `parallel:matrix` — Матричные сборки

Позволяет запускать одно и то же задание несколько раз с разными комбинациями переменных. Идеально для тестирования на разных версиях ПО или для разных архитектур.

```yaml
test:
  stage: test
  script: "echo 'Testing with $PROVIDER on $STACK'"
  parallel:
    matrix:
      - PROVIDER: [aws, gcp]
        STACK: [nodejs, python]
```
Этот пример создаст 4 параллельных задания `test`.

## Управление секретами

Безопасное управление секретами (паролями, токенами, ключами API) — критически важная задача в CI/CD.

-   **Переменные CI/CD (CI/CD Variables)**: В GitLab можно определить переменные проекта или группы, которые будут доступны в пайплайне.
    -   **`Masked` (Маскирование)**: Секретные значения автоматически маскируются в логах пайплайна, чтобы предотвратить их случайную утечку.
    -   **`Protected` (Защищенные)**: Переменные могут быть защищены, чтобы они были доступны только для защищенных веток и тегов (например, `main`, `production`).
    -   **`Expanded` (Развернутые)**: По умолчанию переменные разворачиваются перед выполнением скрипта.

    Используйте эти возможности для хранения секретов, но помните:
    -   Никогда не коммитьте секреты напрямую в репозиторий.
    -   Избегайте вывода секретов в логи, даже если они маскированы (например, не используйте `echo $SECRET_VAR`).
    -   Будьте осторожны с использованием переменных в скриптах, чтобы избежать случайного раскрытия.

-   **Внешние хранилища секретов (External Secret Stores)**: Для более сложного и централизованного управления секретами рекомендуется использовать специализированные решения, такие как HashiCorp Vault. GitLab CI может интегрироваться с такими системами для динамического получения секретов во время выполнения пайплайна, что минимизирует время их жизни и риски утечки.

    -   **Преимущества:**
        -   Централизованное управление и аудит.
        -   Динамическая генерация учетных данных.
        -   Автоматическая ротация секретов.

## Динамическая генерация пайплайнов

В сложных сценариях (например, в монорепозиториях) можно генерировать конфигурацию `.yml` "на лету" и запускать её как дочерний пайплайн.

**Принцип работы:**

1.  **Родительский пайплайн** содержит задание, которое анализирует изменения или другие условия.
2.  Это задание генерирует YAML-файл с необходимой конфигурацией.
3.  Сгенерированный файл объявляется как `artifact`.
4.  Другое задание в родительском пайплайне использует `trigger:include` для запуска дочернего пайплайна на основе этого артефакта.

```yaml
# .gitlab-ci.yml (родительский)
stages:
  - setup
  - build

generate-config:
  stage: setup
  script:
    - ./generate_ci_config.sh > generated-config.yml
  artifacts:
    paths:
      - generated-config.yml

run-child-pipeline:
  stage: build
  trigger:
    include:
      - artifact: generated-config.yml
        job: generate-config
    strategy: depend
```

Этот подход обеспечивает максимальную гибкость, позволяя, например, собирать и тестировать только те компоненты монорепозитория, которые были затронуты изменениями.
