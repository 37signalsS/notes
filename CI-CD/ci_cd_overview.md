# CI/CD: Обзор

## Определения

**CI/CD** — это совокупность практик, объединяющих непрерывную интеграцию (Continuous Integration), непрерывную доставку (Continuous Delivery) и непрерывное развертывание (Continuous Deployment). Представляет собой техническую реализацию автоматизации в рамках [SDLC](./Core_Concepts/sdlc_overview.md).

* **Continuous Integration (CI, Непрерывная интеграция):**
    Практика частой автоматической сборки и тестирования кода после каждого коммита в основной репозиторий. Главная цель — раннее обнаружение ошибок интеграции.

* **Continuous Delivery (CD, Непрерывная доставка):**
    Расширение CI. Каждый успешно собранный и протестированный артефакт автоматически доставляется в окружение, готовое к развертыванию. **Финальное развертывание на production требует ручного подтверждения.**

* **Continuous Deployment (CD, Непрерывное развертывание):**
    Наиболее автоматизированный подход. Каждое изменение, успешно прошедшее все этапы CI, **автоматически развертывается на production без ручного вмешательства.**

| Аспект | Continuous Delivery | Continuous Deployment |
| :--- | :--- | :--- |
| **Развертывание в прод** | **Ручное**, по кнопке | **Автоматическое** |
| **Ключевое отличие** | Требуется явное одобрение релиза | Полностью автоматизированный процесс |
| **Причина использования**| Контроль со стороны бизнеса / QA | Максимальное ускорение Time-to-Market |

## Основные концепции

### Ключевые принципы

Для построения эффективных процессов поставки необходимо придерживаться следующих фундаментальных принципов:

* **Смещение влево (Shift Left):** Интеграция проверок (тестирование, безопасность, линтинг) на максимально ранних этапах жизненного цикла разработки. Это позволяет находить ошибки тогда, когда их исправление стоит дешевле всего.
* **Сборка один раз (Build Once, Deploy Many):** Артефакт (Docker-образ, бинарный файл) должен собираться один раз на этапе CI и без изменений проходить через все окружения (Dev, Staging, Prod). Это гарантирует, что в продакшене работает именно тот код, который был протестирован.
* **Неизменяемая инфраструктура (Immutable Infrastructure):** После развертывания компоненты системы не должны модифицироваться вручную. Любые изменения вносятся через обновление кода/конфигурации и пересоздание компонентов через пайплайн.
* **Инфраструктура как код (Infrastructure as Code, IaC):** Инфраструктура и пайплайны описываются кодом (YAML, Terraform, скрипты) и хранятся в Git. Это обеспечивает версионирование, возможность ревью и быстрого восстановления.

### Практики CI/CD и DevOps

В современных компаниях CI/CD является основой DevOps-культуры:

* **Разделение ответственности:** Настройка пайплайнов — это общая задача разработки и эксплуатации. Разработчики несут ответственность за автоматизацию доставки своего кода.
* **Trunk-Based Development:** Практика частых интеграций небольших изменений в основную ветку (`main`/`trunk`) вместо использования долгоживущих feature-ветвей. Это упрощает интеграцию и ускоряет релизный цикл.

### Динамические окружения (Feature Environments)

Продвинутая практика CD, предполагающая создание временных изолированных окружений под каждую новую функциональность (feature branch).

* **Сценарий:** При создании MR пайплайн автоматически развертывает ветку в изолированное окружение (например, `feature.staging.example.com`).
* **Преимущества:** Изоляция изменений, возможность параллельного тестирования нескольких фич, автоматическая очистка ресурсов после слияния ветки.
* **Реализация в GitLab:** См. **[Окружения и развертывания в GitLab CI](./GitLab_CI/Concepts/environments_and_deployments.md)**.

### Свойства идеального CI/CD пайплайна

1. **Быстрый (Fast):** Обратная связь для разработчика за 10–15 минут.
2. **Надежный (Reliable):** Детерминированный результат без "моргающих" (flaky) тестов.
3. **Безопасный (Secure):** Проверки безопасности встроены в каждый этап.
4. **Прозрачный (Transparent):** Понятные логи и интеграция с системами уведомлений.

### Оптимизация и стандартизация

В крупных компаниях с десятками команд критически важны два аспекта:

#### 1. Методы оптимизации
Для обеспечения быстрого фидбека (Fast Feedback) используются следующие техники:
- **Кэширование (Caching):** Сохранение зависимостей (например, `node_modules`, `vendor`, `.m2`) между запусками пайплайнов для исключения их повторной загрузки.
- **Распараллеливание (Parallelization):** Запуск независимых стадий или тестов одновременно (например, параллельный запуск линтов для разных языков или распределение набора тестов по нескольким воркерам).
- **Инкрементальные сборки:** Сборка и тестирование только тех частей проекта, которые были изменены.

#### 2. Стандартизация через шаблоны
Вместо настройки пайплайна "с нуля" в каждом репозитории используется **централизованный репозиторий шаблонов**:
- Единый набор правил и стадий для всей компании (унификация).
- Разработчики подключают готовые блоки (например, `include` в GitLab CI) и настраивают только специфичные параметры (пути к Dockerfile, версии библиотек).
- Упрощается глобальное обновление процессов (например, внедрение нового сканера безопасности во все проекты одним изменением в шаблоне).

Подробное описание принципов построения (Fail-Fast, Параллелизм) приведено в документе **[Типичный поток пайплайна](./Core_Concepts/pipeline_workflow.md)**.

## Практические сценарии

### Типовой жизненный цикл изменений («Идеальный пайплайн»)

Типовой пайплайн обеспечивает баланс скорости и качества за счет последовательного прохождения этапов:

1. **Валидация (Linting):**
   - Линтинг исходного кода (проверка стиля, потенциальных ошибок).
   - Линтинг миграций БД (проверка на обратную совместимость).
   - Линтинг спецификаций API (например, OpenAPI/Swagger).
   - Поиск секретов и паролей в коде.
2. **Сборка и Unit-тесты:**
   - Проверка базовых компонентов и логики.
   - **Rootless Build:** Сборка Docker-образов без использования root-прав (например, с помощью **[Kaniko](../../Docker/Dockerfile/dockerfile_kaniko.md)**).
3. **Безопасность:** SAST (Static Application Security Testing) и анализ сторонних зависимостей (OSS scanning).
4. **Развертывание на Staging/Dev:**
   - Раскатка в предпроизводственную среду (с использованием **Helm** или **[Werf](../Tools/werf_overview.md)**).
   - Создание динамических окружений для Merge Request.
5. **Тестирование после деплоя:**
   - **Smoke-тесты:** Быстрая проверка доступности основных функций.
   - **Нагрузочные тесты:** Проверка производительности (например, с помощью **k6**).
   - **E2E-тестирование:** Сквозные тесты в среде, близкой к реальной.
6. **Развертывание на Production:**
   - Выкатка проверенного артефакта.
   - **Rollback:** Возможность быстрого отката при обнаружении проблем (например, `helm rollback`).

Детальный разбор этапов и примеры реализации см. в **[Pipeline Workflow](./Core_Concepts/pipeline_workflow.md)**.

### Helm vs GitOps для развертывания

| Критерий | Helm (Push) | ArgoCD / GitOps (Pull) |
| :--- | :--- | :--- |
| **Инструменты** | Helm, **[Werf](../Tools/werf_overview.md)**, Helmfile | Argo CD, Flux |
| **Источник правды** | CI-пайплайн + чарты | Git-репозиторий с манифестами |
| **State drift** | Возможен | Автоматическое восстановление |
| **Доступы к кластеру** | Требуются CI-системе | Не требуются (агент внутри) |
| **Откат** | Через CI-систему (`helm rollback`) | `git revert` в репозитории |
