# CI/CD: Обзор

**Актуально для:** самоуправляемые CI/CD-системы (GitLab CI/CD, Jenkins, GitHub Self-Hosted Runners) 2024–2026

> Область применения заметок: практики DevOps, SRE и SysAdmin при эксплуатации самостоятельно развёрнутых (on-prem / self-hosted) систем. Материалы, относящиеся к публичным облакам и технологиям искусственного интеллекта, в данной базе знаний не рассматриваются.

## Определения

**CI/CD** — это совокупность практик, объединяющих непрерывную интеграцию (Continuous Integration), непрерывную доставку (Continuous Delivery) и непрерывное развертывание (Continuous Deployment). Представляет собой техническую реализацию автоматизации в рамках [SDLC](./Core_Concepts/sdlc_overview.md). В зрелых инженерных организациях CI/CD становится ядром **Platform Engineering** — дисциплины, создающей внутреннюю платформу разработки (Internal Developer Platform, IDP), которая предоставляет командам самообслуживание (Self-service) и гарантирует безопасность цепочки поставок ПО (**Software Supply Chain Security**). В отличие от облачных PaaS, такая платформа может полностью разворачиваться на собственных мощностях (bare-metal, виртуальные машины, кластеры в периметре).

* **Continuous Integration (CI, Непрерывная интеграция):**
    Практика частой автоматической сборки и тестирования кода после каждого коммита в основной репозиторий. Главная цель — раннее обнаружение ошибок интеграции и обеспечение быстрого фидбека ("Fail-Fast").

* **Continuous Delivery (CD, Непрерывная доставка):**
    Расширение CI. Каждый успешно собранный и протестированный артефакт автоматически доставляется в окружение, готовое к развертыванию (например, Staging или Development). **Финальное развертывание на production требует ручного подтверждения.** Это служит «сетью безопасности», позволяя человеку оценить готовность релиза, снизить риски и обеспечить соответствие требованиям комплаенса и бизнес-задачам.

* **Continuous Deployment (CD, Непрерывное развертывание):**
    Наиболее автоматизированный подход. Каждое изменение, успешно прошедшее все этапы CI и тесты в промежуточных средах, **автоматически развертывается на production без ручного вмешательства.** Требует высокой степени зрелости процессов тестирования, мониторинга и автоматизированного отката.

| Аспект | Continuous Delivery | Continuous Deployment |
| :--- | :--- | :--- |
| **Развертывание в прод** | **Ручное**, по кнопке | **Автоматическое** |
| **Ключевое отличие** | Требуется явное одобрение релиза (человеческий фактор) | Полностью автоматизированный процесс |
| **Причина использования**| Контроль рисков, бизнес-решения, комплаенс | Максимальное ускорение Time-to-Market |

## Архитектура CI/CD

CI/CD — это архитектурный паттерн, объединяющий несколько компонентов в единый автоматизированный конвейер поставки ПО:

### Компоненты

1. **SCM (Source Control Management):** Git-репозиторий — источник правды для кода и конфигураций пайплайна.
2. **CI-сервер / Планировщик:** GitLab CI/CD, Jenkins, Tekton — принимает события из SCM, управляет выполнением пайплайна и артефактами.
3. **Раннеры / Исполнители:** Эфемерные или долгоживущие среды (VM, контейнеры, Podы), выполняющие задачи сборки, тестирования и деплоя.
4. **Реестр артефактов:** Nexus, Artifactory, Harbor — хранилище образов и пакетов, являющееся единственным источником для деплоя (Build Once, Deploy Many).
5. **Менеджер секретов:** Vault — хранилище credential с OIDC-федерацией для выдачи временных токенов.
6. **Целевые среды:** VM/bare-metal (Ansible + systemd), оркестраторы (Kubernetes), air-gapped сегменты.
7. **Наблюдаемость:** Prometheus, Grafana, Loki — метрики пайплайна и развёрнутых сервисов.

### Поток данных

```
Commit → Trigger → Lint/PaC → Build → Test → Security Scan → Registry → Deploy → Verify → Rollback
```

Каждый этап изолирован; при сбое пайплайн останавливается и уведомляет ответственных. Иммутабельные артефакты продвигаются по средам без пересборки.

## Проблемы при отсутствии CI/CD

Отсутствие автоматизации в процессе интеграции и доставки кода приводит к ряду критических проблем в разработке:

1. **Задержка тестирования (Delayed Testing):**
   Без CI тестирование обычно происходит поздно в цикле разработки, часто после слияния множества веток. Это затрудняет поиск и исправление ошибок, увеличивая риск попадания дефектов в Production.
2. **Неэффективное развертывание (Inefficient Deployment):**
   Ручной деплой в различные среды (Dev, Staging, Prod) часто приводит к несогласованности конфигураций (**Configuration Drift**) и человеческим ошибкам, что снижает стабильность приложения. Требует участия "знающих" сотрудников и SSH-доступа к серверам.
3. **Проблемы с качеством (Quality Challenges):**
   Отсутствие автоматических тестов как части процесса делает качество ПО зависимым от ресурсов и внимательности QA-инженеров, что делает процесс масштабируемым с трудом и подверженным ошибкам.
4. **Риски слияния (Merge Hell):**
   Длительная работа в изолированных ветках без регулярной интеграции приводит к сложным конфликтам при попытке объединения кода в основную ветку.
5. **Человеческий фактор и "Страх релиза":**
   Зависимость от конкретных людей (релиз-инженеров), высокий уровень стресса при деплое в Production ("shivering and anxiety") и практика запрета деплоев по вечерам или в пятницу из-за высокого риска сбоев, которые некому будет исправить.

## Ценность CI/CD для бизнеса и команд

Внедрение автоматизации приносит измеримые и качественные выгоды:

* **Исключение человеческого фактора:** Робот не забывает прогнать тесты, обновить манифесты или обновить тег образа. Процесс становится повторяемым и предсказуемым.
* **Уверенность в релизах:** Благодаря глубокому автоматизированному тестированию (Unit, E2E, DAST) на каждом этапе, команда уверена в стабильности кода перед выходом в Production.
* **Сокращение Time-to-Market:** Возможность доставлять фиксы и фичи за часы, а не недели.
* **Отсутствие Code Freeze:** Разработчикам не нужно ждать окончания ручного тестирования и деплоя — пайплайн обрабатывает изменения непрерывно.
* **Душевное спокойствие (Peace of Mind):** Исчезает необходимость в "интенсивном ручном тестировании" перед каждым выпуском. Команда может деплоить в любое время, не опасаясь внезапных проблем.

## Основные концепции

### Ключевые принципы

Для построения эффективных процессов поставки необходимо придерживаться следующих фундаментальных принципов:

* **Смещение влево (Shift Left):** Интеграция проверок (тестирование, безопасность, линтинг, оценка ресурсозатрат) на максимально ранних этапах. Это позволяет находить ошибки и неэффективности тогда, когда их исправление стоит дешевле всего. Экономическое обоснование: стоимость исправления дефекта растёт экспоненциально по мере продвижения от этапа написания кода к production (модель стоимости исправления Бумера).
* **Политика как код (Policy as Code, PaC):** Использование декларативных политик (например, **OPA/Rego**, Kyverno, Conftest) для автоматической проверки соответствия (Compliance) и безопасности на этапе CI. Это гарантирует, что в целевую среду попадут только ресурсы, соответствующие стандартам компании, и делает проверки воспроизводимыми, а не зависящими от ручного ревью.
* **Сборка один раз (Build Once, Deploy Many):** Артефакт (Docker-образ, бинарный файл, пакет) должен собираться один раз на этапе CI и без изменений проходить через все окружения (Dev, Staging, Prod). Это гарантирует идентичность протестированного и развернутого кода, устраняет расхождения между "оно работало в staging" и "упало в prod" и обеспечивает трассируемость (какой коммит соответствует какому артефакту по immutable-тегу/хешу).
* **Неизменяемая инфраструктура (Immutable Infrastructure):** После развертывания компоненты системы не должны модифицироваться вручную (никаких `ssh` и `vim` на сервере). Любые изменения вносятся через обновление кода/конфигурации и пересоздание компонентов через пайплайн. Это исключает Configuration Drift и делает среды воспроизводимыми.
* **Инфраструктура как код (Infrastructure as Code, IaC):** Инфраструктура и пайплайны описываются кодом (YAML, Terraform, Ansible, скрипты) и хранятся в Git. Это обеспечивает версионирование, возможность ревью и быстрого восстановления после инцидентов.
* **Эффективность ресурсов и оптимизация затрат инженерного времени:** Сокращение потребления вычислительных мощностей пайплайна (кэширование зависимостей, распараллеливание, инкрементальные сборки) снижает нагрузку на парк раннеров и ускоряет фидбек. Подробнее в разделе «Оптимизация и стандартизация».
* **Безопасность цепочки поставок (Software Supply Chain Security):** Гарантия целостности кода и зависимостей на всех этапах. Включает генерацию **SBOM** (Software Bill of Materials), использование **VEX** (Vulnerability Exploitability eXchange) для фильтрации ложных срабатываний, подпись артефактов (через Cosign/GPG) и соответствие уровням **SLSA** (Supply-chain Levels for Software Artifacts). Использование **эфемерных раннеров** (Ephemeral Runners) и изолированных окружений сборки предотвращает атаки через компрометацию среды сборки и исключает накопление состояния между запусками.
* **OIDC-аутентификация без статических секретов (Keyless Auth / Workload Identity):** Использование федерации удостоверений (Identity Federation) для получения пайплайном временных токенов доступа к внутренним системам — менеджеру секретов (**[Vault](../Vault/overview.md)**), реестрам артефактов, Ansible/inventory — без долгоживущих статических ключей. Каждая задача подписывает короткоживущий JWT, который обменивается на временный токен с минимальными правами; при утечке такой токен быстро истекает и не компрометирует весь флот.
* **Декларативный vs скриптовый пайплайн:** Выбор между описанием пайплайна как *желаемого состояния* (декларативный: YAML, predefined-схема, встроенная валидация) и как *последовательности программных инструкций* (скриптовый: полный язык программирования, циклы, динамическая генерация). Декларативный подход рекомендуется по умолчанию: он обеспечивает безопасность, предсказуемость и единый стандарт для команды. Скриптовый — только для сценариев, где декларативный синтаксис не позволяет выразить сложную логику без загромождения конфигурации. Подробнее: **[Глоссарий пайплайнов](./Core_Concepts/pipeline_glossary.md#декларативный-pipeline)**.

### Практики CI/CD и DevOps

В современных компаниях CI/CD является основой DevOps-культуры и **Platform Engineering**:

* **Platform Engineering и IDP:** Создание внутренней платформы разработки с использованием самостоятельно развёрнутых порталов и каталогов сервисов для предоставления разработчикам самообслуживания. CI/CD пайплайны скрыты за «Золотыми путями» (**Golden Paths**) — проверенными, стандартизированными шаблонами, которые минимизируют когнитивную нагрузку и гарантируют единые стандарты безопасности и наблюдаемости.
* **Trunk-Based Development:** Практика частых интеграций небольших изменений в основную ветку (`main`/`trunk`) вместо использования долгоживущих feature-ветвей. Это упрощает интеграцию, снижает риски Merge Hell и ускоряет релизный цикл.
* **Developer Experience (DevEx):** Ориентация на удобство разработчиков при использовании CI/CD: понятный фидбек, быстрые сборки, минимизация усилий на конфигурацию и возможность воспроизвести пайплайн локально.
* **Прогрессивная доставка (Progressive Delivery):** Развитие CD, включающее стратегии Blue/Green, Canary-релизы, Shadow-деплой и использование Feature Flags для минимизации радиуса поражения (Blast Radius) при ошибках. Подробнее в **[Стратегиях развертывания](./Core_Concepts/deployment_strategies.md)**.
* **SRE-подход к верификации релиза:** Вместо ручной проверки раскатка оценивается автоматически по метрикам надёжности (Error Rate, Latency, Saturation) и SLO/Error Budget. При деградации в окне наблюдения инициируется автоматический откат, а инцидент разбирается дежурной сменой (on-call) с составлением отчёта о первопричине (Root Cause Analysis, RCA) на основе метрик и логов.

### Тестирование в конвейере (Test Pyramid)

Для быстрого и надёжного фидбека тесты в CI организуются по пирамиде:
1. **Unit-тесты** — быстрые, изолированные, дешёвые в исполнении; должны занимать большую часть прогона.
2. **Integration/Contract-тесты** — проверка взаимодействия модулей и совместимости API микросервисов (Pact) без подъёма всей системы.
3. **E2E / Smoke-тесты** — дорогие по времени, запускаются после сборки и деплоя в preview/staging.
4. **Нагрузочные тесты** (k6, JMeter) — на выделенных стендах, а не в каждом MR.

Рекомендуемое практическое соотношение: подавляющее большинство проверок — unit/contract, минимум — E2E. Это снижает время прогона и количество «мигающих» (flaky) тестов.

### Динамические окружения (Feature Environments)

Продвинутая практика CD, предполагающая создание временных изолированных окружений под каждую новую функциональность (feature branch).

* **Сценарий:** При создании MR пайплайн автоматически развертывает ветку в изолированное окружение (например, `feature.staging.example.com` на выделенной VM или namespace).
* **Преимущества:** Изоляция изменений, возможность параллельного тестирования нескольких фич, автоматическая очистка ресурсов после слияния ветки (включая удаление DNS-записей, временных сертификатов и systemd-юнитов).
* **Реализация в GitLab:** См. **[Окружения и развертывания в GitLab CI](./GitLab_CI/Concepts/environments_and_deployments.md)**.

### Свойства идеального CI/CD пайплайна

1. **Быстрый (Fast):** Обратная связь для разработчика за 10–15 минут (оптимизируется кэшем и параллелизмом).
2. **Надёжный (Reliable):** Детерминированный результат без "моргающих" (flaky) тестов; изоляция состояния между прогонами.
3. **Безопасный (Secure):** Проверки безопасности (SAST, SCA, Secrets Detection) встроены в каждый этап; артефакты подписываются.
4. **Прозрачный (Transparent):** Понятные логи, интеграция с системами уведомлений, дашборды утилизации раннеров и метрик пайплайна в Prometheus/Grafana.

### Читаемость пайплайна

Пайплайн должен быть читаемым как код. Типовая последовательность этапов:
1. Сборка образа.
2. Тесты (юнит, интеграция, контракты).
3. Скан безопасности (SAST/SCA, секреты, образы).
4. Пуш образа в registry.
5. Plan/Apply по IaC.
6. Откат одной командой.

Логи пайплайна — это артефакт, а не то, что надо вычитать в консолях. Пагинация, кэширование и параллелизация должны быть явно видны в конфигурации.

### Оптимизация и стандартизация

В организациях с десятками команд критически важны два аспекта:

#### 1. Методы оптимизации
Для обеспечения быстрого фидбека (Fast Feedback) и снижения нагрузки на самостоятельно обслуживаемый парк раннеров используются следующие техники:
- **Кэширование (Caching):** Сохранение зависимостей (например, `node_modules`, `vendor`, `.m2`) и слоёв образов между запусками пайплайнов для исключения их повторной загрузки. Локальный кэш раннера или выделенный кэш-сервер (например, GitLab CI cache, Nexus/Artifactory) предотвращает исчерпание диска на эфемерных агентах.
- **Распараллеливание (Parallelization):** Запуск независимых стадий или тестов одновременно через DAG (Directed Acyclic Graph) и директивы `needs` / матричные сборки.
- **Инкрементальные сборки:** Сборка и тестирование только тех частей проекта (микросервисов/модулей), которые были изменены (monorepo-aware сборщики, например, Bazel, Nx, Turborepo).
- **Артефакты сборки:** Передача результатов между стадиями через внутренний registry/artifact storage вместо повторной сборки.

#### 2. Стандартизация через шаблоны
Вместо настройки пайплайна "с нуля" используется **централизованный репозиторий шаблонов**:
- Единый набор правил и стадий для всей компании (унификация).
- Разработчики подключают готовые блоки (**CI/CD Components**, reusable workflows) и настраивают параметры через `spec:inputs` / `include`.
- Упрощается глобальное обновление процессов (например, внедрение нового сканера безопасности) без правок в сотнях репозиториев.

## Практические сценарии

### Типовой жизненный цикл изменений («Идеальный пайплайн»)

Типовой пайплайн обеспечивает баланс скорости и качества за счет последовательного прохождения этапов:

1. **Валидация (Linting) и PaC:**
   - Линтинг кода, IaC-манифестов и миграций БД.
   - Проверка политик безопасности (**Policy checks**) через OPA/Kyverno/Conftest.
   - Поиск секретов и паролей в коде (например, gitleaks, trufflehog).
2. **Сборка и Unit/Contract тесты:**
   - Проверка базовых компонентов.
   - **Contract Testing (Pact):** Проверка совместимости API микросервисов без запуска всей системы.
   - **Rootless Build:** Сборка образов без root-прав (например, с помощью **[Kaniko](../Docker/Dockerfile/dockerfile_kaniko.md)** или `buildah`/`podman`).
3. **Безопасность (DevSecOps):**
   - **SAST / SCA / Secrets Detection:** Статический анализ и поиск уязвимостей в зависимостях (Trivy, Grype, Semgrep).
   - **Контейнерное сканирование:** Проверка слоев образа.
   - **Анализ VEX:** Исключение неэксплуатируемых уязвимостей из отчетов.
4. **Развертывание на Staging/Preview:**
   - Раскатка в предпроизводственную среду или создание эфемерных окружений.
   - Проверка соответствия ресурсным квотам и доступности портов/дисков на целевых хостах.
5. **Тестирование после деплоя:**
   - Smoke-тесты, нагрузочные тесты (k6) и E2E-сценарии.
6. **Аттестация и Выкатка на Production:**
   - Генерация SBOM и подпись артефакта (Cosign/GPG).
   - Развертывание (Canary/Blue-Green, GitOps-синхронизация).
   - **Верификация по SLO и RCA:** Автоматический анализ метрик (Prometheus/Loki) после деплоя. В случае аномалий (превышение Error Rate, деградация Latency) — автоматический откат и уведомление on-call инженера; разбор первопричины ведётся по логам и метрикам вручную SRE-инженером.

Детальный разбор этапов см. в **[Pipeline Workflow](./Core_Concepts/pipeline_workflow.md)**.

### Helm против GitOps для развертывания

| Критерий | Helm / Ansible (Push) | ArgoCD / Flux (Pull) |
| :--- | :--- | :--- |
| **Инструменты** | Helm, **[Ansible](../Ansible/ansible_introduction.md)**, **[Werf](./Tools/werf_overview.md)** | Argo CD, Flux |
| **Источник правды** | CI-пайплайн + чарты | Git-репозиторий с манифестами |
| **State drift** | Возможен | Автоматическое восстановление |
| **Доступы к кластеру** | Требуются CI-системе | Не требуются (агент внутри) |
| **Откат** | Через CI-систему (`helm rollback`, `ansible-playbook` / `systemctl`) | `git revert` в репозитории |

### Сценарий 1: Self-hosted эфемерный раннер (GitLab Runner на VM/bare-metal)

Эфемерные раннеры создаются под каждую задачу и уничтожаются после неё — это исключает накопление состояния, кэш-утечки между проектами и снижает радиус поражения при компрометации.

**Предварительные требования:**
- Хост с ОС Linux (Ubuntu/Debian/RHEL), Docker Engine и GitLab Runner, установленным из внутреннего репозитория.
- `config.toml` с `executor = "docker"` и флагом одноразового раннера.

```toml
# /etc/gitlab-runner/config.toml (фрагмент)
concurrent = 4
[[runners]]
  name = "self-hosted-ephemeral"
  url = "https://gitlab.internal/"
  token = "<REGISTRATION_TOKEN>"   # выдан при регистрации; хранить в Vault
  executor = "docker"
  # Эфемерность: раннер обслуживает одну задачу и завершается
  [runners.docker]
    image = "docker:24"
    privileged = false
    disable_cache = false
```

Регистрация с JIT-токеном (временный, а не долгоживущий):

```bash
gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.internal/" \
  --token "<JIT_REGISTRATION_TOKEN>" \
  --executor "docker" \
  --docker-image "docker:24" \
  --run-untagged="false"
# → Runner X registered successfully
```

Управление службой через systemd (автозапуск, перезапуск при сбое):

```bash
# /etc/systemd/system/gitlab-runner.service
# sudo systemctl enable --now gitlab-runner
# sudo systemctl status gitlab-runner  # → active (running)
```

**Валидация:** в интерфейсе GitLab раннер появляется в списке с тегом `online`; при запуске задачи в логах `journalctl -u gitlab-runner` виден старт контейнера, после завершения процесс завершается (эфемерность подтверждается отсутствием повторного использования workspace).

### Сценарий 2: Деплой на VM/bare-metal через Ansible + systemd + автооткат

Типовая схема для сервисов вне оркестратора: пайплайн собирает артефакт, раскатывает его на хосты по SSH через Ansible, обновляет systemd-юнит, проверяет healthcheck и при сбое откатывает предыдущую версию.

**Ansible playbook (фрагмент):**

```yaml
# deploy.yml
- hosts: app_servers
  become: true
  vars:
    app_version: "{{ lookup('env', 'APP_VERSION') }}"
  tasks:
    - name: Скачать артефакт из внутреннего registry
      get_url:
        url: "https://nexus.internal/repository/app/{{ app_version }}/app.tar.gz"
        dest: "/opt/app/{{ app_version }}.tar.gz"
        mode: '0644'

    - name: Распаковать релиз в версионный каталог
      unarchive:
        src: "/opt/app/{{ app_version }}.tar.gz"
        dest: "/opt/app/releases/{{ app_version }}/"
        remote_src: yes

    - name: Переключить symlink на новый релиз (atomic)
      file:
        src: "/opt/app/releases/{{ app_version }}"
        dest: "/opt/app/current"
        state: link
        force: yes

    - name: Перезапустить systemd-сервис
      systemd:
        name: app
        daemon_reload: yes
        state: restarted
        enabled: yes

    - name: Подождать healthcheck
      uri:
        url: "http://localhost:8080/healthz"
        status_code: 200
      register: health
      until: health.status == 200
      retries: 10
      delay: 3
```

**Скрипт автоматического отката (rollback.sh):**

```bash
#!/usr/bin/env bash
# Используется в пайплайне при неудачном healthcheck
set -euo pipefail
PREV=$(cat /opt/app/previous_version)
ln -sfn "/opt/app/releases/${PREV}" /opt/app/current
systemctl restart app
echo "Откат выполнен на версию ${PREV}"
# → Откат выполнен на версию 1.4.2
```

**Валидация:** после деплоя `systemctl status app` показывает `active (running)`, `curl -f http://localhost:8080/healthz` возвращает `200`. При провале healthcheck пайплайн вызывает `rollback.sh` и фиксирует инцидент в канале on-call.

### Сценарий 3: Локальный registry артефактов (Nexus/Artifactory)

Принцип **Build Once, Deploy Many** требует единого источника артефактов внутри периметра. Образ собирается один раз, пушится в Nexus/Artifactory и затем пуллится идентичным во все среды.

```bash
# Аутентификация в реестре (токен из Vault, не в переменной репозитория)
docker login nexus.internal:5000 \
  --username "$NEXUS_USER" \
  --password-stdin <<< "$NEXUS_TOKEN"
# → Login Succeeded

# Сборка и пуш с immutable-тегом (хеш коммита)
IMAGE="nexus.internal:5000/app:$(git rev-parse --short HEAD)"
docker build -t "$IMAGE" .
docker push "$IMAGE"
# → pushed: nexus.internal:5000/app:a1b2c3d
```

**Лучшая практика:** запрещать переиспользование тегов `latest` для прод-релизов; использовать только хеши/семантические версии. Жизненным циклом сборок (хранение, подпись, SBOM) управляет **[Управление артефактами](./artifact_management.md)**.

### Сценарий 4: Миграции баз данных в пайплайне

Миграции выполняются как отдельная стадия до раскатки приложения, с механизмом отката. Рекомендуется паттерн **Expand/Contract** (см. **[Стратегии развертывания](./Core_Concepts/deployment_strategies.md)**), исключающий простой при breaking changes.

```bash
# Flyway (аддитивная миграция, совместимая со старой и новой версией)
flyway -url="$DB_URL" -user="$DB_USER" -password="$DB_PASS" \
  -locations="filesystem:db/migrations" migrate
# → Successfully applied 3 migrations to schema "public" (execution time 00:02.118s)
```

**Откат миграции** (только для обратимых миграций, по согласованному плану):

```bash
flyway -url="$DB_URL" -user="$DB_USER" -password="$DB_PASS" \
  -target="<prev_version>" repair   # или undo для поддерживаемых СУБД
```

**Валидация:** `flyway info` показывает `Success` напротив применённых версий; приложение v2 стартует и проходит smoke-тест подключения к БД. Если миграция несовместима с работающей v1 — используется двухэтапный Expand/Contract, а не прямой `undo`.

### Сценарий 5: Наблюдаемость пайплайна (SRE-практика)

Пайплайн сам по себе — объект мониторинга. GitLab Runner и Jenkins экспортируют метрики в формате Prometheus, что позволяет выявлять узкие места (очереди, «мигающие» тесты, нехватку слотов).

```yaml
# prometheus.yml (фрагмент scrape)
scrape_configs:
  - job_name: 'gitlab-runners'
    static_configs:
      - targets: ['runner-01.internal:9252', 'runner-02.internal:9252']
```

Ключевые метрики: `gitlab_runner_jobs_total`, время нахождения в `pending` (Queue Time), процент занятых слотов (Runner Saturation), количество инфраструктурных падений (`No space left on device`, OOM). Визуализация — в Grafana; алерты по превышению Queue Time и Failure Rate. Подробнее: **[Наблюдаемость пайплайнов](./Core_Concepts/pipeline_observability.md)** и **[Управление парком раннеров](./runner-fleet-management.md)**.

### Сценарий 6: Управление секретами через Vault (on-prem, без статических ключей)

Вместо хранения секретов в переменных CI применяется OIDC/AppRole: пайплайн получает временный токен Vault с минимальной политикой и читает только нужные пути.

```bash
# CI-задача обменивает свой JWT (сгенерирован CI-системой) на Vault-токен
VAULT_TOKEN=$(vault write -field=token auth/jwt/login \
  role=ci-role \
  jwt="$CI_JOB_JWT")
# Чтение секрета только для staging
vault read -field=password kv/data/ci/staging/db
# → <временный пароль, не попадает в переменные репозитория>
```

Подробная настройка Vault для self-hosted раннеров — в **[Управлении секретами в CI/CD](./DevSecOps/secrets_management.md)**.

### Устранение неполадок (Troubleshooting)

| Симптом | Вероятная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Job висит в `pending` | Нехватка свободных слотов раннеров | `journalctl -u gitlab-runner`; метрика Queue Time | Масштабировать флот, проверить `concurrent` в `config.toml` |
| Flaky-тесты | Гонки, зависимость от порядка, общее состояние | Повторный прогон, изоляция теста локально | Сделать тест детерминированным; вынести в отдельную стадию |
| `No space left on device` | Нет очистки кэша/workspace на раннере | `df -h` на хосте раннера | Эфемерные раннеры; `docker system prune`; квота диска |
| OOM-kill сборки | Недостаточно RAM для задачи | `dmesg \| grep -i oom`; логи раннера | Увеличить лимит памяти; разбить сборку на шаги |
| Утечка секрета в логи | `set -x` в секретном шаге | Проверка masked-переменных в CI | Маскирование, тип переменной `File`, запрет `set -x` |
| Webhook не триггерит пайплайн | Нет сетевого доступа/сбой приёмника | Логи CI-сервера, проверка endpoint | Проверить URL webhook, TLS, firewall, retry |
| Несовпадение артефактов Dev/Prod | Повторная сборка вместо переиспользования | Проверка тегов образов | Принцип Build Once, Deploy Many; пуш в registry |

### Лучшие практики и очистка (Best Practices & Cleanup)

1. **Эфемерность:** раннеры и окружения создаются под задачу и уничтожаются после; не использовать долгоживущие shared runners для привилегированных задач.
2. **Минимальные права:** пайплайн `dev` не должен иметь доступа к секретам/хостам `prod` (через политики Vault и scopes CI).
3. **Очистка за собой:** удаление временных окружений (DNS, сертификаты, systemd-юниты, тома) в стадии `after_script`/`cleanup`, в том числе при провале пайплайна.
4. **Воспроизводимость локально:** предоставлять разработчикам команду запуска пайплайна локально (например, `act` для GitHub, `gitlab-runner exec` для GitLab) для быстрой отладки.
5. **Откат всегда готов:** план возврата версии (переключение симлинка, `helm rollback`, `git revert`) описан в runbook до начала прод-выкатки.

## Ограничения и крайние случаи

- **Air-gapped среды:** При отсутствии выхода в интернет используются локальные зеркала зависимостей (Nexus proxy, MinIO/S3 для образов), pré-downloaded образы раннеров и air-gapped бандлы. Подробнее: **[Изолированные среды](./Core_Concepts/air_gapped_environments.md)**.
- **Высокая доступность CI-инфраструктуры:** GitLab CI и Jenkins разворачиваются в кластере с репликацией БД и балансировкой. Раннеры регистрируются в нескольких экземплярах для устранения SPOF. RTO для CI-инфраструктуры обычно составляет часы; подробнее в **[Резервном копировании и DR для CI/CD](./Core_Concepts/ci_cd_backup_dr.md)**.
- **Границы прав и Multi-tenancy:** В оркестраторах (Kubernetes) namespace-изоляция; в GitLab — группы и sub-groups с scoped переменными. Паблик раннеры никогда не должны иметь доступ к `prod`-секретам.
- **Производительность при больших монореpos:** Инкрементальные сборки (Bazel, Nx, Turborepo), кэширование артефактов между коммитами и remote execution для снижения времени фидбека.

### Метрики эффективности

Эффективность процессов CI/CD измеряется с помощью индустриального стандарта — метрик **DORA**:
- **Deployment Frequency:** Частота успешных деплоев.
- **Lead Time for Changes:** Время от коммита до деплоя в прод.
- **Change Failure Rate:** Процент изменений, приведших к сбоям.
- **Failed Deployment Recovery Time:** Время восстановления после инцидента, вызванного деплоем.

Подробное описание метрик: **[Метрики DORA](./Core_Concepts/dora_metrics.md)**.
