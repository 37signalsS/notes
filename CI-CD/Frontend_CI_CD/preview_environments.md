# Превью- и ephemeral-окружения для фронтенда

## Определения

- **Preview Environment (Review App)** — временное, изолированное окружение, автоматически поднимаемое для конкретной ветки/MR и уничтожаемое при её закрытии.
- **Ephemeral Environment** — окружение, существующее ровно на время жизни задачи/ветки (не перманентное).
- **Dynamic Environment** — окружение с динамически выделяемым URL/портом, управляемое пайплайном.
- **Subdomain routing** — маршрутизация превью по уникальному поддомену (например, `mr-123.app.example.com`).
- **On-stop cleanup** — скрипт/хук, удаляющий окружение при закрытии MR.
- **TTL (Time To Live)** — автоматическое удаление окружения по истечении времени бездействия (например, `auto_stop_in: 1 day` в GitLab CI).
- **Resource Quota** — ограничение потребления CPU, памяти и диска для превью-окружения, предотвращающее перерасход ресурсов хоста/кластера.

## Основные концепции

### Зачем нужны превью-окружения
Дают возможность проверить визуальный регрессионный тест, LHCI, e2e и ручной QA именно на коде ветки до мержа в `main`. Это сокращает цикл обратной связи и ловжит проблемы, невидимые в юнит-тестах.

С точки зрения SRE, превью-окружения — это форма **Shift-right Testing**: проверка в среде, максимально приближённой к продакшену (та же сборка артефакта, те же конфиги, только изоляция данных), но без риска для пользователей.

### Архитектура и принципы работы
Превью-окружение для фронтенда строится вокруг трёх компонентов:
1. **Артефакт сборки** — `dist/` или SSR-бандл (`.next/`, `.output/`), собранный один раз на этапе `build` и передаваемый в среду без пересборки. Это исключает расхождение «того, что тестировали» и «того, что задеплоили».
2. **Хост/роутинг** — механизм, делающий превью доступным по предсказуемому URL. Для статики это каталог на web-сервере (Nginx/Angie); для SSR — выделенный порт/процесс за reverse proxy.
3. **Жизненный цикл** — пайплайн создаёт окружение на `push`/`open MR`, обновляет на каждом `push`, удаляет по `on_stop` или TTL.

Изоляция достигается на разных уровнях:
- **Файловая система:** отдельный каталог (`/srv/preview/mr-<id>/`) или отдельный release-каталог с симлинком. Для атомарности деплоя используется паттерн «каталог релиза + символическая ссылка» (release directory + symlink swap).
- **Сеть:** уникальный поддомен (`mr-<id>.app.example.com`) или уникальный порт (`4000 + MR_IID`), за Nginx-роутингом. Для SSR-процессов рекомендуется привязывать `bind` к `127.0.0.1` или внутреннему VLAN, чтобы процесс не был доступен извне кроме reverse proxy.
- **Процесс:** для SSR — отдельный Node.js-процесс на выделенном порту, управляемый systemd/PM2, не конфликтующий с другими превью. На shared host это предотвращает «утечку» состояния между разными MR.
- **Данные:** либо read-only реплика staging-бэкенда, либо выделенный набор с seed-данными. Продовая база для превью неприменима по соображениям безопасности и стабильности.

### Жизненный цикл
1. **Create:** при открытии/обновлении MR поднимается окружение (статика в каталог или SSR-процесс на выделенном порте).
2. **Update:** при каждом пуше — пересборка и обновление артефакта. Для статики — `rsync` в тот же каталог или атомарный `ln -sfn`; для SSR — перезапуск процесса с новым бандлом.
3. **Destroy:** при закрытии/мерже MR — `on_stop` удаляет ресурсы. Если `on_stop` не сработал (падение пайплайна, ошибка прав) — срабатывает TTL-очистка.

### Изоляция и именование
- Имя/порт окружения однозначно привязано к MR (`mr-123`), чтобы не конфликтовать.
- Для SSR используется изолированный процесс (порт) за nginx-роутингом по subdomain.
- Данные: либо общий staging-бэкенд (read-only/replica), либо выделенный набор с seed-данными.

### Стоимость и очистка
Превью могут накапливаться. Обязателен `on_stop` cleanup и авто-удаление «висячих» окружений по возрасту (например, старше 7 дней).

С точки зрения FinOps, неконтролируемое количество превью — основной источник нецелевых трат в frontend-инфраструктуре. Меры контроля:
- **Квоты:** лимит одновременно запущенных превью на команду/проект (например, 10 активных MR). Для Docker-сред — лимит concurrent jobs; для bare-metal — квота места под `/srv/preview`.
- **TTL:** автоматическое удаление через `auto_stop_in` (GitLab) или cron-очистку по `mtime`.
- **Disk quota:** ограничение места под каталог превью (например, 20 ГБ), чтобы один большой `dist/` не заполнил раздел.

### Безопасность
- Превью не должно иметь доступа к production-секретам. Используйте отдельный набор переменных CI или Vault-role для review-окружений.
- Для SSR-превью ограничьте `bind` на `127.0.0.1` или внутренний VLAN, чтобы процесс не был доступен извне кроме Nginx.
- На shared host применяйте изоляцию на уровне ОС (юзеры, cgroups) или, в Kubernetes, `NetworkPolicy` для запрета доступа превью к продакшен-сервисам.

### Наблюдаемость
Превью-окружения должны быть видимы в мониторинге:
- **Логи:** сбор stdout/stderr SSR-процесса и access-log Nginx в централизованное хранилище (Loki, ELK).
- **Метрики:** количество активных превью, их возраст, потребление CPU/памяти/диска.
- **Алерты:** оповещение при превышении квоты или существовании окружения старше TTL.

## Практические сценарии

### Сценарий 1: GitLab Dynamic Environment (статика)
```yaml
preview:
  stage: deploy
  environment:
    name: review/mr-$CI_MERGE_REQUEST_IID
    url: https://mr-$CI_MERGE_REQUEST_IID.app.example.com
    on_stop: stop_preview
  script:
    - npm ci && npm run build
    - rsync -az dist/ deploy@preview:/srv/preview/mr-$CI_MERGE_REQUEST_IID/
  rules:
    - if: $CI_MERGE_REQUEST_ID

stop_preview:
  stage: deploy
  script:
    - ssh deploy@preview "rm -rf /srv/preview/mr-$CI_MERGE_REQUEST_IID"
  environment:
    name: review/mr-$CI_MERGE_REQUEST_IID
    action: stop
  rules:
    - if: $CI_MERGE_REQUEST_ID
      when: manual
```

### Сценарий 2: Превью для SSR (изолированный процесс + nginx subdomain)
```bash
# Запуск SSR на уникальном порту для MR
PORT=$(( 4000 + $CI_MERGE_REQUEST_IID % 1000 ))
APP_PORT=$PORT npm run start -- -p $PORT &
# nginx роутит поддомен на этот порт (конфиг генерируется в пайплайне)
cat > /etc/nginx/conf.d/mr-$CI_MERGE_REQUEST_IID.conf <<EOF
server {
    server_name mr-$CI_MERGE_REQUEST_IID.app.example.com;
    location / { proxy_pass http://127.0.0.1:$PORT; }
}
EOF
nginx -s reload
```

### Сценарий 3: Интеграция с визуальными и сквозными тестами
```yaml
visual_on_preview:
  stage: test
  script:
    - npx playwright test --grep @visual --base-url https://mr-$CI_MERGE_REQUEST_IID.app.example.com
  artifacts:
    when: on_failure
    paths: [playwright-report/]
```

### Сценарий 4: Авто-очистка «висячих» окружений
```bash
# Cron/раннер: удаляем превью старше 7 дней
ssh deploy@preview "find /srv/preview -maxdepth 1 -type d -mtime +7 -exec rm -rf {} +"
```

## Проверка корректности

После подъёма превью-окружения необходимо убедиться, что оно действительно работает и доступно:

1. **Доступность URL:**
   ```bash
   curl -sS https://mr-123.app.example.com/ -o /dev/null -w "%{http_code}\n"
   # → 200
   ```

2. **Доступность ассетов:**
   ```bash
   CHUNK=$(curl -s https://mr-123.app.example.com/ | grep -oE 'assets/[a-z]+\.[a-f0-9]+\.js' | head -1)
   curl -s -o /dev/null -w "%{http_code}\n" "https://mr-123.app.example.com/${CHUNK}"
   # → 200
   ```

3. **SSR-процесс (если применимо):**
   ```bash
   curl -sS http://127.0.0.1:$PORT/healthz
   # → HTTP 200, тело {"status":"ok"}
   ```

4. **Заголовки кэширования (статический превью):**
   ```bash
   curl -I https://mr-123.app.example.com/assets/main.abc123.js
   # → Cache-Control: public, max-age=31536000, immutable
   ```

5. **Проверка nginx-конфига:**
   ```bash
   nginx -t
   # → nginx: configuration file /etc/nginx/nginx.conf test is successful
   ```

## Типичные проблемы

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Окружения копятся | Нет `on_stop` | Обязательный `action: stop` + cron-очистка |
| Конфликт портов SSR | Фиксированный порт | Динамический порт от MR IID |
| Превью падает | Нет изоляции БД | Seed-данные / staging-replica |
| Долгий подъём | Полная пересборка | Кэш зависимостей + affected (см. monorepo) |
| Окружение не удаляется | `on_stop` не определен, нет прав | Добавить `stop_review` с `action: stop`, проверить права сервис-аккаунта/SSH-доступ |
| Утечка памяти SSR | Нет лимитов Node.js | `--max-old-space-size` + мониторинг RSS + restart по таймауту |
| Превью доступен извне | Без ограничения `bind`/NetworkPolicy | Привязать SSR-процесс к `127.0.0.1`, включить firewall |
| Диск заполнен | Нет квоты на каталог превью | `ResourceQuota` (K8s) или `df`-мониторинг + alert |
| Висячие образы registry | Очистка по TTL не настроена | Registry Cleanup Policy или cron `docker image prune` |

## Лучшие практики
1. URL превью должен быть предсказуем и привязан к MR (`mr-<iid>`).
2. Всегда определяйте `on_stop` — иначе окружения будут копиться.
3. Для SSR изолируйте порты и не используйте общую БД с продом (только staging/replica/seed).
4. Запускайте на превью те же проверки, что в `main` (LHCI, visual, e2e), но с меньшим числом прогонов.
5. Ограничивайте число одновременных превью (квота по портам/диску).
6. Используйте `npm ci` + кэш по lock-файлу для стабильной скорости сборки.
7. Храните артефакт превью с `expire_in` (например, 7 дней), чтобы не расходовать хранилище CI.
8. Для SSR-превью настройте `graceful shutdown` (ловля `SIGTERM`), чтобы при `on_stop` процесс корректно закрывал соединения.
9. Добавьте health check (`/healthz`) в SSR-превью и проверяйте его перед запуском тестов.
10. Централизуйте логи превью: если окружение упало, логи должны быть доступны без SSH на хост (stdout → Loki/ELK).
