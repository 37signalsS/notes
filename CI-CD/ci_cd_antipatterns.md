# Анти-паттерны CI/CD

## Определения

- **Анти-паттерн CI/CD** — это распространенный, но неэффективный, рискованный или контрпродуктивный подход к проектированию и реализации конвейеров автоматизации. В отличие от случайной ошибки, анти-паттерн часто выглядит как логичное или временное решение, но в долгосрочной перспективе приводит к накоплению технического долга, замедлению процессов и увеличению вероятности инцидентов.

Анти-паттерны являются прямой противоположностью [Паттернов CI/CD](./ci_cd_patterns.md): там описано «как делать правильно», здесь — «чего делать нельзя» и почему.

## Основные концепции

### Влияние анти-паттернов на процесс поставки

Анти-паттерны в процессах CI/CD подрывают фундаментальные цели автоматизации: скорость, надежность и повторяемость. Основные последствия их применения включают:

- **Снижение доверия к автоматизации:** Частые ложноположительные или нестабильные результаты заставляют команду игнорировать сигналы пайплайна.
- **Merge Hell (ад слияний):** Проблемы при объединении долгоживущих веток кода, требующие значительных ручных усилий.
- **Невоспроизводимость окружений:** Различия между тестовыми и промышленными средами, приводящие к ошибкам, которые невозможно обнаружить до развертывания на production.
- **Уязвимости цепочки поставок (Supply Chain Vulnerabilities):** Утечки учетных данных, отравление пайплайнов или подмена артефактов.

Для ознакомления с корректными подходами к решению данных проблем обратитесь к документу **[Паттерны CI/CD](./ci_cd_patterns.md)**.

## Практические сценарии

Ниже приведен каталог из 16 наиболее критичных анти-паттернов, встречающихся при построении CI/CD-конвейеров. Для каждого даны описание, последствия, решение и практические **признаки обнаружения (Detection)** — что проверить в своём пайплайне прямо сейчас.

### 1. Долгоживущие ветки (Long-Lived Branches)

- **Описание:** Создание веток, которые существуют днями или неделями, развиваясь изолированно от основной кодовой базы (`main`).
- **Последствия:** Рискованные слияния, накопление конфликтов, сложность отката изменений.
- **Решение:** Переход к **Trunk-Based Development**. Использование короткоживущих feature-веток и [фиче-флагов](./Testing/feature_toggles/overview.md) для управления незавершенным функционалом.
- **Признаки (как обнаружить):** возраст самого старого коммита в ветке относительно `main`:

```bash
git log -1 --format='%ci' main..feature/big-rewrite
# → 2026-01-02 14:03:11  (коммит старше 2 суток — сигнал долгоживущей ветки)
```

### 2. Пересборка артефактов для разных сред

- **Описание:** Запуск отдельного процесса сборки для каждого окружения (`staging`, `production`), в результате чего создаются разные бинарные файлы или образы.
- **Последствия:** Отсутствие гарантии, что развернутый в production артефакт идентичен протестированному.
- **Решение:** Принцип **иммутабельных артефактов**. Артефакт собирается один раз, а конфигурация передается через переменные окружения. Подробнее в [Управлении артефактами](./artifact_management.md).
- **Признаки (как обнаружить):** в логах пайплайна этап `build` запускается более одного раза для одного коммита, либо образы для staging и prod имеют разные digest при одном исходнике.

### 3. Использование статических секретов (Static Secrets & Hardcoding)

- **Описание:** Хранение паролей в коде или использование долгоживущих API-токенов в настройках CI/CD вместо динамической аутентификации.
- **Последствия:** Утечка секрета ведет к полной компрометации инфраструктуры; сложность ротации.
- **Решение:** Использование **OIDC (OpenID Connect)** для keyless-авторизации (например, получение временных учётных данных из Vault по JWT-токену пайплайна) и **динамических секретов** через менеджеры секретов. Подробнее в **[Антипаттернах управления секретами](../Vault/common_antipatterns.md)** и [Управлении секретами в CI/CD](./DevSecOps/secrets_management.md).
- **Признаки (как обнаружить):** сканирование репозитория на наличие секретов перед каждым пушем:

```bash
gitleaks detect --source . --redact -v
# → Finding: DB_PASSWORD in config.py:12 (high)  (статический секрет в коде)
```

### 4. Нестабильные тесты (Flaky Tests)

- **Описание:** Тесты, результат которых меняется случайным образом без изменений в коде.
- **Последствия:** Команда перестает реагировать на падения пайплайна, пропуская реальные баги.
- **Решение:** Изоляция тестов, детерминированные данные, автоматический карантин нестабильных тестов и использование инструментов аналитики тестов.
- **Признаки (как обнаружить):** прогон с повторными запусками выявляет тесты, проходящие не с первой попытки:

```bash
pytest --reruns 3 --reruns-delay 2 tests/ 2>&1 | grep -E "passed|failed|RERUN"
# → test_login[RERUN] test_login[passed]  (тест прошёл со второй попытки → flaky)
```

Карантин нестабильных тестов, чтобы они не блокировали gate, но оставались видимыми:

```ini
# pytest.ini — карантин нестабильных тестов
[pytest]
markers =
    quarantine: тесты с нестабильным поведением, исключены из основного gate
```

### 5. Ручные действия и «Снежинки»

- **Описание:** Необходимость ручного вмешательства в процесс деплоя (SSH-доступ, ручное выполнение команд, правка конфигураций на сервере) или наличие серверов, настроенных вручную.
- **Последствия:** Человеческий фактор, невозможность быстрого восстановления (DR), дрейф конфигураций.
- **Решение:** Реализация подхода **IaC** и **GitOps**. Все изменения должны вноситься только через код. Подробнее в [Обзоре IaC](../Concepts/iac_overview.md).
- **Признаки (как обнаружить):** проверка дрейфа конфигурации относительно описанного в коде состояния:

```bash
ansible-playbook site.yml --check --diff
# → changed=3  (есть расхождения «снежинок» с описанным в коде состоянием)
```

### 6. Зависимость от ключевых сотрудников (Senior Dependency)

- **Описание:** Сценарий, при котором релиз может выполнить только один "знающий" старший инженер, так как процесс не документирован или требует уникальных прав доступа и локальных настроек.
- **Последствия:** Блокировка релизов во время отпусков или болезней сотрудников, риск остановки бизнеса при увольнении ключевого кадра.
- **Решение:** Автоматизация процесса через CI/CD инструменты, доступные всей команде, и использование Pipeline as Code.
- **Признаки (как обнаружить):** отсутствие `runbook`/документации релиза в репозитории и наличие шага деплоя, который запускается только с локальной машины конкретного инженера.

### 7. Деплой, основанный на страхе (Anxiety-driven Deployment)

- **Описание:** Коллективный страх перед развертыванием в Production ("shivering and anxiety"), приводящий к запрету деплоев по вечерам или в пятницу, а также к длительным периодам накопления изменений (Batching).
- **Последствия:** Увеличение blast radius (радиуса поражения) при сбое, так как накапливается слишком много изменений. Снижение скорости поставки.
- **Решение:** Внедрение автоматизированных тестов, Canary-развертываний и механизмов мгновенного отката для повышения уверенности команды.
- **Признаки (как обнаружить):** наличие «code freeze» окон и релизов, объединяющих более ~20–50 коммитов за раз (большой blast radius).

### 8. Монолитный и непрозрачный пайплайн

- **Описание:** Единый конвейер для всех сервисов или отсутствие видимости этапов сборки.
- **Последствия:** Медленная обратная связь, высокая сложность поддержки.
- **Решение:** Микросервисная архитектура пайплайнов и использование централизованных, версионируемых шаблонов.
- **Признаки (как обнаружить):** один job на сотни строк, покрывающий build+test+deploy слитно, без разбиения на stages:

```bash
grep -c "stage:" .gitlab-ci.yml
# → 1  (монолитный job без разбиения на этапы — анти-паттерн)
```

### 9. Игнорирование безопасности цепочки поставок (Supply Chain Blindness)

- **Описание:** Отсутствие генерации **SBOM** (Software Bill of Materials) и подписи артефактов (Artifact Signing).
- **Последствия:** Невозможность отследить уязвимости в транзитивных зависимостях и риск подмены образа в Registry.
- **Решение:** Интеграция генерации SBOM и подписи (например, Cosign/sigstore) на этапе сборки. Соответствие уровням **SLSA**.
- **Признаки (как обнаружить):** проверка подписи артефакта в гейте сборки:

```bash
cosign verify nexus.internal:5000/app@sha256:$DIGEST 2>&1 | head -1
# → Error: no matching signatures (артефакт не подписан — анти-паттерн)
syft nexus.internal:5000/app:latest -o cyclonedx-json > sbom.json   # генерация SBOM
```

### 10. Слепое доверие автоматизации (Unvalidated Automation)

- **Описание:** Автоматическое применение изменений в инфраструктуре, конфигурации или коде, сгенерированных ботами или скриптами (например, авто-мерж зависимостей, сгенерированные IaC-планы), без ручного ревью или автоматических тестов.
- **Последствия:** В продакшен попадают непроверенные изменения, создающие скрытые уязвимости или ломающие конфигурацию.
- **Решение:** Обязательное прохождение CI-гейтов (тесты, сканирование, план изменений) и ревью для любых автоматических предложений; применение изменений только после зелёного пайплайна.
- **Признаки (как обнаружить):** включённый automerge без условия успешного CI:

```bash
grep -R "automerge" renovate.json .github/ 2>/dev/null
# → "automerge": true  (риск применения без проверки)
```

### 11. Отсутствие контроля стоимости (CI/CD Cost Blindness)

- **Описание:** Бесконтрольный запуск тяжелых пайплайнов, избыточное кэширование или хранение бесконечного числа версий артефактов.
- **Последствия:** Непропорциональный рост затрат на инфраструктуру CI/CD (раннеры, хранилище, вычисления).
- **Решение:** Установка лимитов ресурсов, очистка старых артефактов и мониторинг стоимости сборки на уровне проекта. Подробнее в руководстве **[Оптимизация затрат в CI/CD](./Core_Concepts/cost-optimization.md)**.
- **Признаки (как обнаружить):** рост `queue time` раннеров и отсутствие политик retention для артефактов/логов/кэшей.

### 12. Слепой деплой без проверки состояния (Blind Deployment)

- **Описание:** Завершение пайплайна сразу после команды деплоя без проверки Health Checks и бизнес-метрик.
- **Последствия:** Ложное чувство безопасности при неработающем приложении.
- **Решение:** Внедрение Post-deployment verification и стратегий прогрессивной доставки: [Blue/Green](./Deployment_Strategies/blue_green_deployment.md) или [Canary](./Deployment_Strategies/canary_deployment.md).
- **Признаки (как обнаружить):** в пайплайне нет шага проверки после деплоя:

```bash
grep -n "healthz\|smoke\|/health" deploy.yml || echo "NO HEALTH GATE"
# → NO HEALTH GATE  (слепой деплой)
```

Корректный гейт верификации после раскатки:

```yaml
# .gitlab-ci.yml (фрагмент)
verify:
  stage: verify
  script:
    - curl -fsS https://app.internal/healthz || exit 1
    - ./scripts/check_error_rate.sh   # см. Паттерны: Continuous Verification
```

### 13. «Шаблонный ад» и теневой CI (Template Hell & Shadow CI)

- **Описание:** Создание чрезмерно сложных, глубоко вложенных и неверсионируемых шаблонов пайплайнов, которые разработчики начинают обходить, создавая свои собственные нестандартные решения.
- **Последствия:** Невозможность обновить глобальные стандарты, фрагментация инструментов, рост сложности отладки.
- **Решение:** Использование **версионируемых компонентов** (например, GitLab CI Components) с четкими контрактами (`inputs`) и предоставление IDP (Internal Developer Platform).
- **Признаки (как обнаружить):** шаблон превышает ~300–500 строк, содержит вложенность `include` глубже 3 уровней и не имеет фиксированного тега версии (`ref: main` вместо `ref: v1.2.0`).

### 14. Избыточные привилегии OIDC (OIDC Over-privilege)

- **Описание:** Использование OIDC для беспарольной авторизации, но с предоставлением пайплайну прав `AdministratorAccess` или аналогичных широких полномочий.
- **Последствия:** Скомпрометированный пайплайн (через зависимости или Poisoned Pipeline Execution) позволяет захватить всю инфраструктуру (вплоть до управляющих систем).
- **Решение:** Принцип **наименьших привилегий (PoLP)**. Привязка конкретных ролей к конкретным веткам или проектам через `sub` claim в OIDC.
- **Признаки (как обнаружить):** проверка политик, привязанных к OIDC-роли пайплайна:

```bash
vault read auth/oidc/role/ci-pipeline
# → token_policies: ["admin"]  (слишком широко — анти-паттерн)
```

### 15. Дрейф конфигурации после деплоя (Post-deployment Drift)

- **Описание:** Внесение изменений в инфраструктуру вручную после того, как она была развернута через CI/CD (например, правка `/etc/app/config.yaml` напрямую по SSH на ВМ или изменение манифеста K8s через `kubectl edit`).
- **Последствия:** Код в Git больше не соответствует реальности; следующий деплой может сломать систему или затереть важные ручные фиксы.
- **Решение:** Использование **GitOps**-контроллеров с включенным режимом `Self-healing` (автоматический откат ручных изменений).
- **Признаки (как обнаружить):** детекция дрейфа средствами IaC:

```bash
terraform plan -detailed-exitcode
# → Exit code 2: resources have drifted  (факт ручного изменения в обход IaC)
```

### 16. Страх автоматического отката (Auto-Rollback Phobia)

- **Описание:** Отключение механизмов автоматического отката при неудачном деплое из-за недоверия к тестам или сложности процесса.
- **Последствия:** Длительный простой системы при сбоях (MTTR растет), необходимость ручного вмешательства в критические моменты.
- **Решение:** Постепенное внедрение автоматизированных Smoke-тестов и использование инструментов прогрессивной доставки (Flagger, Argo Rollouts).
- **Признаки (как обнаружить):** откат выполняется вручную (`when: manual`) или отсутствует как шаг пайплайна при падении health-гейта.

## Дополнительная информация

### Устранение неполадок (Troubleshooting)

| Симптом | Вероятный анти-паттерн | Действие |
| :--- | :--- | :--- |
| Пайплайн зелёный, но прод сломан | #2 Пересборка / #12 Слепой деплой | Собирать артефакт один раз; добавить health-gate |
| Конфликты при merge длятся днями | #1 Долгоживущие ветки | Переход на TBD + feature flags |
| Секрет утёк в репозиторий | #3 Статические секреты | Ротировать; перейти на OIDC/Vault; добавить gitleaks |
| Тесты иногда падают «сами» | #4 Flaky | Карантин, изоляция, детерминированные данные |
| Серверы отличаются друг от друга | #5 Снежинки / #15 Дрейф | IaC + `ansible --check`; GitOps self-healing |
| Релиз блокируется уходом инженера | #6 Senior Dependency | Pipeline as Code, runbook, IDP |
| Затраты на CI растут нелинейно | #11 Cost Blindness | Лимиты, очистка кэша/артефактов, retention |
| Откат занимает часы вручную | #16 Auto-Rollback Phobia | Авто-smoke + прогрессивная доставка |
| Образ подменён/неизвестного происхождения | #9 Supply Chain Blindness | SBOM + `cosign verify` в гейте сборки |
| Авто-обновления зависимостей ломают прод | #10 Unvalidated Automation | Авто-мерж только после зелёного CI |

### Лучшие практики и очистка (Best Practices & Cleanup)

1. **Регулярный аудит:** раз в квартал проходить по каталогу и оценивать наличие каждого анти-паттерна в своих пайплайнах.
2. **Обязательные гейты безопасности:** `gitleaks` / `syft` / `cosign verify` — шаги, которые нельзя пропускать (`allow_failure: false`).
3. **Карантин flaky-тестов** с SLA на починку (например, 5 рабочих дней); иначе они «гниют» и подрывают доверие к CI.
4. **Наименьшие привилегии:** OIDC-роли привязывать к ветке/проекту, не выдавать `admin`.
5. **Детекция дрейфа:** `ansible --check` / `terraform plan -detailed-exitcode` в nightly CI для раннего выявления «снежинок».
6. **Чистка:** настраивать retention для артефактов, логов и кэшей раннеров; удалять эфемерные среды по TTL/после слияния MR.
7. **Документирование runbook релиза** в репозитории, чтобы исключить зависимость от конкретного инженера (#6).
8. **Версионирование шаблонов:** общие пайплайн-компоненты привязывать через тег версии, а не `main`, чтобы избежать «шаблонного ада».
