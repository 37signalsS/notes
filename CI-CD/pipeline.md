### Этапы CI/CD пайплайна

1.  **Этап 1: Валидация (1-2 минуты)**
    *   **Цель:** Первая линия обороны. Можно ли вообще работать с этим кодом?
    *   **Действия:**
        *   **Синтаксис и форматирование:** Проверка, что код написан по правилам команды.
        *   **Типы (TypeScript):** Убедиться, что все переменные имеют правильные типы.
        *   **Конфигурационные файлы:** Проверка валидности настроек.
        *   **Секреты в коде:** Поиск паролей и токенов.

2.  **Этап 2: Сборка (2-3 минуты)**
    *   **Цель:** Превращение исходного кода в работающее приложение.
    *   **Действия:**
        *   **Установка пакетов:** Скачивание всех библиотек (`npm install`).
        *   **Компиляция кода:** Транспиляция TypeScript в JavaScript.
        *   **Сборка бандлов:** Упаковка файлов для браузера.
        *   **Создание артефактов:** Сохранение результатов для следующих этапов.

3.  **Этап 3: Базовое тестирование (3-5 минут)**
    *   **Цель:** Проверка каждой функции отдельно.
    *   **Действия (параллельно):**
        *   **Юнит-тесты:** Каждая функция работает правильно.
        *   **Snapshot-тесты:** Интерфейс не изменился случайно.
        *   **Contract-тесты:** API соответствует договоренностям.
        *   **Покрытие кода:** Протестировано минимум 80%.

4.  **Этап 4: Безопасность (5-10 минут)**
    *   **Цель:** Поиск уязвимостей до того, как их найдут хакеры.
    *   **Действия:**
        *   **SAST сканирование:** Статический анализ на уязвимости.
        *   **Проверка библиотек:** Поиск известных проблем в зависимостях.
        *   **Анализ Docker:** Проверка безопасности контейнеров.
        *   **OWASP Top 10:** Защита от популярных атак.

5.  **Этап 5: Интеграционное тестирование (30-40 минут)**
    *   **Цель:** Проверка, как части системы работают вместе.
    *   **Действия:**
        *   **API-тесты:** Все эндпоинты отвечают правильно.
        *   **Тесты с базой данных:** Данные корректно сохраняются и читаются.
        *   **Внешние сервисы:** Интеграции работают.
        *   **Smoke-тесты:** Основные пользовательские пути не сломаны.

6.  **Этап 6: E2E тестирование (40-100 минут)**
    *   **Цель:** Прохождение полного пути пользователя от входа до покупки.
    *   **Действия (параллельно в разных браузерах):**
        *   **Chrome тесты:** 4 параллельных потока.
        *   **Firefox тесты:** Проверка кроссбраузерности.
        *   **Safari тесты:** Для пользователей Mac.
        *   **Мобильные тесты:** Проверка работы на телефонах.

7.  **Этап 7: Performance-тестирование (10-20 минут)**
    *   **Цель:** Убедиться, что система не тормозит.
    *   **Действия:**
        *   **Нагрузочное тестирование:** Выдержит ли система 1000 пользователей.
        *   **Скорость загрузки:** Страницы открываются < 2 секунд.
        *   **Утечки памяти:** Приложение не потребляет всю RAM.
        *   **Оптимизация запросов:** База данных не тормозит.

8.  **Этап 8: Deployment (5-10 минут)**
    *   **Цель:** Выкладка на боевой сервер.
    *   **Действия:**
        *   **Сборка Docker-образа:** Упаковка приложения.
        *   **Загрузка в registry:** Сохранение в хранилище.
        *   **Deploy on staging:** Выкладка на тестовый сервер.
        *   **Health checks:** Убедиться, что всё работает.

### Принципы организации проверок

1.  **Принцип 1: Параллельность — делаем одновременно всё, что можно**
    *   **Что можно параллелить:**
        *   **На этапе валидации:** Линтер, типы, форматирование (независимые проверки).
        *   **Юнит-тесты:** Backend и Frontend тесты (разные кодовые базы).
        *   **E2E тесты:** Разбиваем на части (sharding) + разные браузеры.
        *   **Security сканы:** SAST и проверка зависимостей (разные инструменты).
    *   **Выгода:** Вместо 120 минут последовательно → 30 минут параллельно.

2.  **Принцип 2: Последовательность — соблюдаем зависимости**
    *   **Что НЕЛЬЗЯ делать параллельно:**
        *   `Сборка → Тесты`: Нельзя тестировать несобранный код.
        *   `Тесты → Performance`: Нельзя нагружать сломанное приложение.
        *   `Все проверки → Deploy`: Нельзя выкладывать непроверенное.
    *   **Правильная цепочка:**
        `Валидация → Сборка → Тесты → Интеграция → E2E → Performance → Deploy`

3.  **Принцип 3: Fail-Fast — падаем быстро, экономим деньги**
    *   Чем раньше в пайплайне обнаруживается ошибка, тем дешевле ее исправление. Быстрый фидбэк для разработчиков — ключ к эффективности.

### Что такое артефакт сборки?

**Артефакт** — это результат процесса сборки, готовый к развертыванию или использованию в следующем этапе. Это может быть что угодно:

*   Скомпилированный бинарный файл (`.jar`, `.war`, `.exe`, Go-бинарник)
*   Docker-образ
*   Пакет для менеджера зависимостей (`.npm`, `.gem`, `.whl`)
*   Архив со статическими файлами для веб-сервера (`.zip`, `.tar.gz`)
*   Сгенерированная документация
*   Отчеты о тестировании или покрытии кода

### Почему нельзя просто хранить артефакты на CI-сервере?

Самый простой, но и самый плохой подход — оставлять артефакты на диске CI/CD-агента (например, Jenkins workspace, GitLab runner cache).

**Проблемы этого подхода:**

1.  **Ненадежность:** CI-агенты могут быть временными (особенно в облаках или Kubernetes). Их диски могут быть очищены в любой момент, и вы потеряете артефакты.
2.  **Отсутствие версионирования:** Сложно найти конкретную версию артефакта, откатиться на нее или посмотреть историю изменений.
3.  **Проблемы с производительностью:** Если для сборки одного компонента нужен артефакт другого, CI-серверу придется заново его собирать, вместо того чтобы скачать готовый.
4.  **Безопасность:** Нет контроля доступа. Любой, у кого есть доступ к CI-агенту, может получить доступ ко всем артефактам.

### Правильный подход: Репозиторий Артефактов (Artifact Repository)

Это специализированное хранилище, созданное для управления бинарными файлами и зависимостями. Его можно сравнить с Git, но для бинарников, а не для исходного кода.

### Ключевые функции репозитория артефактов:

1.  **Хостинг (Hosted Repositories):** Хранение ваших собственных, уникальных артефактов (например, `my-super-app-v1.2.0.jar`).
2.  **Проксирование (Proxy Repositories):** Кэширование публичных зависимостей (из Maven Central, PyPI, npmjs.com). Ваш CI-сервер обращается к вашему репозиторию, а тот, если у него нет нужной зависимости, скачивает ее из интернета и сохраняет у себя.
3.  **Группировка (Group Repositories):** Объединение нескольких хостируемых и прокси-репозиториев под одним URL. Для разработчика и CI-сервера это выглядит как единый источник.

### Популярные решения для хранения артефактов

| Категория | Решение | Описание |
| :--- | :--- | :--- |
| **Self-Hosted (управляемые вами)** | **JFrog Artifactory** | Один из лидеров рынка. Поддерживает огромное количество форматов. Мощный, но может быть сложным в настройке. |
| | **Sonatype Nexus Repository** | Главный конкурент Artifactory. Также очень популярен, особенно в Java-мире. Считается чуть более простым. |
| | **Harbor** | Open Source проект от [CNCF](../cncf_overview.md). Изначально создавался как реестр Docker-образов, но теперь поддерживает и другие форматы (Helm, OCI). Отлично подходит для Kubernetes. |
| **Cloud / SaaS (готовые сервисы)** | **GitHub Packages** | Интегрирован с GitHub. Удобен, если ваш код уже там. Поддерживает основные форматы. |
| | **GitLab Package Registry** | Аналогично, интегрирован с GitLab. Позволяет хранить артефакты рядом с исходным кодом и CI/CD пайплайнами. |

### Типичный CI/CD пайплайн с использованием репозитория артефактов

1.  **Триггер:** Разработчик пушит код в Git.
2.  **Запуск сборки:** CI/CD система (Jenkins, GitLab CI, GitHub Actions) запускает задачу сборки.
3.  **Получение зависимостей:**
    *   Сборочный агент (runner) обращается к **вашему репозиторию артефактов** (например, Nexus) за зависимостями (например, `spring-boot-starter-web`).
    *   Nexus проверяет свой кэш. Если зависимость есть — отдает ее. Если нет — скачивает из интернета (Maven Central), кэширует и отдает.
4.  **Сборка и тестирование:** Происходит компиляция, прогоняются тесты. В результате создается артефакт, например, `my-app:v1.5.2`.
5.  **Публикация артефакта:**
    *   CI-пайплайн **публикует (deploy/push)** этот артефакт в ваш репозиторий артефактов с уникальной версией.
    *   Артефакт становится **неизменяемым (immutable)**. Версию `1.5.2` уже нельзя перезаписать.
6.  **Развертывание (Deployment):**
    *   Задача развертывания скачивает **конкретную, версионированную** версию артефакта (`my-app:v1.5.2`) из репозитория.
    *   Артефакт разворачивается на сервере (staging, production).

### Лучшие практики

1.  **Используйте специализированный репозиторий артефактов.** Не храните их на CI-сервере или в системе контроля версий.
2.  **Версионируйте все.** Каждый артефакт должен иметь уникальную, осмысленную версию (например, по схеме SemVer `2.1.0` или с добавлением хеша коммита `2.1.0-a1b2c3d`).
3.  **Обеспечьте неизменяемость (Immutability).** Однажды опубликованный артефакт никогда не должен изменяться. Если нужны правки — выпускайте новую версию.
4.  **Разделяйте репозитории.** Используйте разные репозитории для разных стадий:
    *   `snapshots` — для сборок в процессе разработки.
    *   `releases` — для стабильных, протестированных версий.
    *   `third-party` — для зависимостей, которых нет в публичных репозиториях.
5.  **Настройте очистку.** Автоматически удаляйте старые `snapshot`-сборки, чтобы не занимать место.
6.  **Сканируйте на уязвимости.** Интегрируйте инструменты (например, JFrog Xray, Nexus Lifecycle) для сканирования артефактов и их зависимостей на известные уязвимости.

### Сканирование на секреты в коде

Обнаружение утекших секретов (ключей API, паролей, токенов) — критически важный этап в обеспечении безопасности CI/CD. Инструменты статического анализа помогают автоматизировать этот процесс.

Два популярных решения — **Trufflehog** и **Gitleaks**. Оба легко интегрируются в пайплайны (например, GitHub Actions) и могут быть настроены для проверки пул-реквестов или с помощью git-хуков.

#### **Trufflehog**

Более универсальный инструмент, который может искать утечки в различных источниках:

*   Git (включая всю историю)
*   GitHub, GitLab, CircleCI, TravisCI, Jenkins
*   Файловые системы
*   Docker-образы
*   Объектные хранилища (GCS, S3)
*   Postman, syslog, Elasticsearch

**Примеры использования в Docker:**

```bash
# Проверка текущего каталога
docker run --rm -it -v "$PWD:/pwd" trufflesecurity/trufflehog:latest filesystem

# Проверка репозиториев организации на GitHub
docker run --rm -it -v "$PWD:/pwd" trufflesecurity/trufflehog:latest github --org=trufflesecurity
```

#### **Gitleaks**

Специализированное и быстрое решение для сканирования Git-репозиториев. Отличается высокой производительностью и простотой настройки.

#### Что выбрать?

*   **Trufflehog**: подходит для глубокого и всестороннего анализа, если вам нужно работать с разными источниками данных.
*   **Gitleaks**: идеален для быстрой и простой проверки именно Git-репозиториев с минимальной настройкой.

### Создание секрета в Kubernetes

Для создания секрета в Kubernetes можно воспользоваться внешним генератором:

1.  Перейдите по ссылке: `https://secrets.trendsurfers.ru/`
2.  Выберите нужный **кластер**.
3.  Укажите **имя секрета**.
4.  Вставьте данные, которые необходимо зашифровать (например, `MY_TOKEN=uvbvyh3j23flcwu`).
5.  Скопируйте сгенерированный YAML и вставьте его в ваш файл конфигурации, например, `main.yaml`.
