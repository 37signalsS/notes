# Практическое руководство: Установка GitLab CE (Self-Hosted) с помощью Docker

Это руководство описывает процесс установки собственного сервера GitLab Community Edition (CE) с использованием Docker. Наличие self-hosted экземпляра GitLab предоставляет полный контроль над вашей DevOps-платформой.

---

## Шаг 1: Подготовка окружения на хост-машине

Вам понадобится сервер (виртуальная или физическая машина) с установленным Docker и доменным именем, которое указывает на IP-адрес этого сервера.

1.  **Создайте рабочую директорию:** Вся конфигурация, логи и данные GitLab будут храниться здесь. Это упрощает управление и резервное копирование.
    ```bash
    sudo mkdir -p /srv/gitlab
    cd /srv/gitlab
    ```

2.  **Экспортируйте переменную окружения:** Это упростит последующие команды.
    ```bash
    export GITLAB_HOME=$(pwd)
    ```

## Шаг 2: Подготовка конфигурационного файла `gitlab.rb`

GitLab настраивается через файл `/etc/gitlab/gitlab.rb` внутри контейнера. Мы создадим этот файл на хосте и смонтируем его в контейнер.

1.  **Создайте файл `config/gitlab.rb`:**
    ```bash
    mkdir -p $GITLAB_HOME/config
    touch $GITLAB_HOME/config/gitlab.rb
    ```

2.  **Добавьте базовую конфигурацию:** Самый важный параметр — `external_url`. Он должен соответствовать доменному имени, по которому будет доступен ваш GitLab. GitLab использует его для генерации всех ссылок.
    ```bash
    # Замените 'gitlab.example.com' на ваше доменное имя
    echo "external_url 'https://gitlab.example.com'" | sudo tee $GITLAB_HOME/config/gitlab.rb
    ```
    GitLab автоматически настроит встроенный Nginx и запросит SSL-сертификат от Let's Encrypt, если домен доступен извне.

## Шаг 3: Запуск Docker-контейнера GitLab

Теперь запустим контейнер GitLab, смонтировав в него подготовленные директории.

```bash
sudo docker run --detach \
  --hostname gitlab.example.com \
  --publish 443:443 --publish 80:80 \
  --name gitlab \
  --restart always \
  -v $GITLAB_HOME/config:/etc/gitlab \
  -v $GITLAB_HOME/logs:/var/log/gitlab \
  -v $GITLAB_HOME/data:/var/opt/gitlab \
  gitlab/gitlab-ce:14.8.6-ce.0
```

**Разбор команды:**
*   `--detach` или `-d`: Запускает контейнер в фоновом режиме.
*   `--hostname`: Устанавливает имя хоста контейнера (должно совпадать с доменом).
*   `--publish`: Пробрасывает порты 443 (HTTPS) и 80 (HTTP) с хоста в контейнер.
*   `--name gitlab`: Дает контейнеру удобное имя.
*   `--restart always`: Контейнер будет автоматически запускаться при перезагрузке сервера.
*   `-v ...`: Монтирует директории с хоста в контейнер для хранения конфигурации, логов и данных.
*   `gitlab/gitlab-ce:14.8.6-ce.0`: Указывается конкретная версия GitLab Community Edition.

## Шаг 4: Ожидание и проверка

Первый запуск GitLab может занять **от 5 до 15 минут**, так как он выполняет внутреннюю настройку и конфигурацию сервисов.

Вы можете следить за процессом с помощью логов:
```bash
sudo docker logs -f gitlab
```
Дождитесь, пока в логах перестанут активно появляться новые сообщения.

## Шаг 5: Получение пароля администратора

При первом запуске GitLab генерирует случайный пароль для пользователя `root`.

1.  **Убедитесь, что GitLab полностью запустился.** Процесс может занять несколько минут.
2.  **Получите пароль** из специального файла внутри контейнера:
    ```bash
sudo docker exec gitlab cat /etc/gitlab/initial_root_password
    ```
    Скопируйте выведенный пароль. Этот файл автоматически удаляется после первой реконфигурации, поэтому получить пароль нужно как можно скорее.

## Шаг 6: Первый вход

1.  Откройте в браузере ваш домен (`https://gitlab.example.com`).
2.  На странице входа введите:
    *   **Username:** `root`
    *   **Password:** Пароль, который вы скопировали на предыдущем шаге.
3.  Войдите в систему. Вам будет предложено сразу же сменить пароль.

Поздравляем, у вас есть собственный работающий сервер GitLab! Вы можете зайти в **Admin Area** для дальнейшего изучения и настройки.

## Послеустановочная настройка и лучшие практики администрирования GitLab

После установки вашего экземпляра GitLab важно правильно его настроить и следовать лучшим практикам для обеспечения безопасности и эффективной работы.

### 1. Выбор версии при установке

*   **GitLab EE (Enterprise Edition):** Рекомендуется GitLab, если в будущем возможен апгрейд до платной версии, так как EE содержит все функции.
*   **GitLab CE (Community Edition):** Выбирайте, если важна чистота лицензии (Open Source) и вам достаточно базового функционала.

### 2. Управление пользователями и доступом

*   **Избегайте работы под `root`:** После установки всегда создавайте обычного пользователя с ограниченными правами для повседневной работы. Используйте учетную запись `root` только для задач, требующих повышенных привилегий.
*   **Функция `Impersonate`:** Администраторы GitLab могут использовать эту функцию, чтобы просматривать GitLab от лица любого другого пользователя. Это очень полезно для отладки проблем, с которыми сталкиваются пользователи.
*   **Интеграция с централизованными хранилищами пользователей:** Для крупных компаний рекомендуется интеграция с LDAP, Active Directory, Radius или другими SSO-провайдерами (GitLab поддерживает более 20 провайдеров аутентификации). Это помогает избежать путаницы и централизовать управление пользователями.

### 3. Безопасность

*   **Отключение публичной регистрации:** Сразу после установки отключите возможность самостоятельной регистрации новых пользователей, если ваш GitLab не предназначен для публичного использования.
*   **Двухфакторная аутентификация (2FA):** Настоятельно рекомендуется включить 2FA для всех пользователей. GitLab позволяет принудительно требовать настройку 2FA перед первым входом в систему, блокируя доступ тем, кто ее не настроил.
*   **Ограничение доступа по IP:** При необходимости можно настроить список разрешенных IP-адресов, с которых разрешен вход в GitLab.
*   **Гранулярные права доступа:** GitLab предоставляет широкие возможности по настройке прав доступа к проектам и группам. Предоставляйте пользователям (особенно внешним, например, подрядчикам) ровно столько прав, сколько необходимо для выполнения их задач. Для подрядчиков можно настроить автоматическое истечение срока действия доступа.

### 4. Оптимизация рабочего процесса (GitLab Flow)

*   **Используйте GitLab Flow:** Это набор практик для управления ветвлением и релизами, разработанный специально для эффективного использования с GitLab. Ознакомьтесь с ним для оптимизации ваших процессов разработки. См. [Практическое руководство по использованию GitLab Flow](./gitlab_flow_tutorial.md) для пошаговой инструкции.

### 5. Обслуживание и мониторинг

*   **Автоматические обновления:** Настройте регулярное автоматическое обновление GitLab (например, раз в неделю в выходные дни). GitLab предоставляет механизмы для отображения страницы обслуживания во время обновления.
*   **Сборка мусора (Garbage Collection):** Регулярно запускайте сборщик мусора GitLab, особенно если у вас много проектов, активное CI/CD (частые релизы), и большой объем данных. Это предотвратит переполнение диска.
