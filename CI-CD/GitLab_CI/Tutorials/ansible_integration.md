# Использование Ansible в GitLab CI/CD

Ручной запуск плейбуков с локальной машины системного администратора является плохой практикой, особенно в продуктивных средах. Правильный подход — интеграция Ansible в CI/CD пайплайны, что соответствует парадигме "Инфраструктура как код" (IaaC). Это руководство описывает основные принципы и преимущества использования Ansible вместе с GitLab CI/CD.

См. также:
*   [Обзор Ansible](../Ansible/ansible_overview.md)
*   [Рекомендации по безопасности Ansible](../Ansible/ansible_security_best_practices.md)

## 1. Зачем интегрировать Ansible с GitLab?

Ansible-плейбуки, роли и конфигурации — это код. Как и любой другой код, его следует хранить в системе контроля версий (например, Git). GitLab, будучи платформой для хостинга Git-репозиториев, предоставляет мощный механизм CI/CD для автоматизации работы с этим кодом.

**Ключевые преимущества:**

1.  **Автоматизация запусков:** Плейбуки выполняются автоматически после событий в репозитории (например, слияние в `main` ветку), а не вручную. Это исключает проблемы, связанные с локальным окружением администратора (например, перезагрузка ноутбука во время выполнения плейбука).
2.  **Контроль доступа:** Доступ к продуктивным серверам есть только у **GitLab Runner**'а — специальной машины, выполняющей задачи. Разработчики и администраторы не имеют прямого доступа к продакшену. Их права разграничиваются на уровне GitLab (например, запрет на слияние в `main` без код-ревью).
3.  **Версионирование и аудит:** Каждое изменение инфраструктуры проходит через Git, оставляя четкий след: кто, когда и какое изменение внес. Любое изменение можно откатить.
4.  **Безопасность и управление секретами:** CI/CD пайплайн позволяет централизованно и безопасно управлять доступом к секретам (ключам, паролям, файлам инвентаря).

## 2. Как это работает: GitLab Runners и `.gitlab-ci.yml`

Основу интеграции составляют два компонента:

*   **GitLab Runner:** Это агент, который устанавливается на отдельную машину (или несколько машин) и регистрируется в вашем GitLab-проекте. Он постоянно опрашивает GitLab на предмет новых задач (jobs). Получив задачу, он выполняет описанные в ней скрипты. На этой машине должен быть установлен Ansible и все необходимые зависимости.

*   **`.gitlab-ci.yml`:** Это YAML-файл в корне вашего репозитория, который описывает CI/CD пайплайн.

### Структура `.gitlab-ci.yml`

Файл определяет **стадии** (`stages`) и **задачи** (`jobs`).

*   **Stages:** Последовательные этапы пайплайна, например: `lint`, `test`, `deploy`. Задачи следующей стадии не начнутся, пока успешно не завершатся все задачи предыдущей.
*   **Jobs:** Конкретные задачи внутри стадий. Каждая задача — это набор shell-команд, выполняемых на Runner'е.

**Простой пример `.gitlab-ci.yml` для запуска Ansible:**

```yaml
stages:
  - lint
  - deploy

variables:
  # Указываем Ansible использовать стандартный callback для чистого лога в CI
  ANSIBLE_STDOUT_CALLBACK: "default" 

lint-playbooks:
  stage: lint
  script:
    - ansible-lint . # Проверяем качество кода плейбуков

deploy-to-staging:
  stage: deploy
  script:
    - echo "Starting Ansible playbook deployment to staging..."
    # Основная команда для запуска плейбука
    - ansible-playbook -i inventory/staging.ini playbooks/main.yml
  rules:
    # Запускать эту задачу только для main ветки
    - if: '$CI_COMMIT_BRANCH == "main"'
```

В этом примере:
1.  Сначала на стадии `lint` запускается `ansible-lint` для проверки синтаксиса и стиля.
2.  Если линтинг успешен, на стадии `deploy` запускается команда `ansible-playbook`.
3.  Задача `deploy-to-staging` выполняется только при коммитах в `main` ветку.

## 3. Управление секретами и файлами инвентаря

Хранить файлы инвентаря с IP-адресами продакшен-серверов, SSH-ключи или пароли в открытом виде в Git-репозитории **категорически запрещено**.

### Рекомендуемые подходы:

#### 1. GitLab CI/CD Variables

Самый простой способ — использовать встроенный механизм переменных в GitLab.
*   **Путь:** В вашем проекте GitLab перейдите в `Settings -> CI/CD -> Variables`.
*   **Что хранить:** Здесь можно хранить пароли от Vault, SSH-ключи, токены API.
*   **Безопасность:** Пометьте переменные как **"Protected"** (будут доступны только для защищенных веток, например `main`) и **"Masked"** (значение будет скрыто в логах CI/CD).

**Пример использования SSH-ключа:**

1.  Создайте переменную `SSH_PRIVATE_KEY` в GitLab, вставив в ее значение содержимое вашего `id_rsa`.
2.  В `.gitlab-ci.yml` перед запуском `ansible-playbook` создайте файл с ключом:

    ```yaml
    deploy-job:
      stage: deploy
      before_script:
        # Устанавливаем правильные права на SSH-ключ
        - chmod 600 "$SSH_PRIVATE_KEY"
      script:
        # Запускаем плейбук, указывая путь к ключу
        - ansible-playbook -i inventory/prod --private-key "$SSH_PRIVATE_KEY" playbooks/main.yml
    ```

#### 2. Защищенные файлы инвентаря

Файлы инвентаря с чувствительной информацией не должны быть доступны всем, у кого есть доступ к репозиторию.

*   **Способ 1 (Внешний инклюд):** GitLab позволяет включать внешние YAML-файлы в ваш `.gitlab-ci.yml`. Вы можете создать отдельный, защищенный репозиторий только для CI-конфигурации (с инвентарем и ключами) и подключать его через директиву `include`. Это позволяет разграничить доступ к коду плейбуков и к секретам.

*   **Способ 2 (Ansible Vault):**
    1.  Зашифруйте ваши файлы инвентаря или файлы с переменными с помощью `ansible-vault`.
    2.  Безопасно храните зашифрованные файлы (`*.vault.yml`) в Git.
    3.  Пароль от Vault храните в переменной `ANSIBLE_VAULT_PASSWORD` в `Settings -> CI/CD -> Variables`.
    4.  Ansible автоматически использует эту переменную для расшифровки файлов во время выполнения плейбука.

    ```yaml
    # .gitlab-ci.yml
    deploy-job:
      stage: deploy
      script:
        # Пароль будет подставлен из переменной окружения CI/CD
        - ansible-playbook -i inventory/prod.vault.yml playbooks/main.yml
    ```
Этот подход сочетает удобство хранения кода в Git с безопасностью `ansible-vault` и GitLab CI/CD.

## 4. Практическое руководство: Настройка и запуск

Этот раздел описывает полный процесс настройки GitLab Runner для работы с Ansible, от установки до запуска плейбуков.

### 4.1. Установка и регистрация GitLab Runner

Для запуска плейбуков Ansible необходим GitLab Runner, установленный на машине, где доступен Ansible.

#### Установка Runner

1.  **Добавьте официальный репозиторий GitLab Runner:**
    ```bash
    # Для Debian/Ubuntu/Mint
    curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.deb.sh" | sudo bash

    # Для RHEL/CentOS/Fedora
    curl -L "https://packages.gitlab.com/install/repositories/runner/gitlab-runner/script.rpm.sh" | sudo bash
    ```
    Для Ubuntu может потребоваться пиннинг репозитория для установки последней версии.

2.  **Установите пакет:**
    ```bash
    # Для Debian/Ubuntu/Mint
    sudo apt-get install gitlab-runner

    # Для RHEL/CentOS/Fedora
    sudo yum install gitlab-runner
    ```
3.  **Проверьте статус сервиса:**
    ```bash
    systemctl status gitlab-runner
    ```
    Сервис должен быть в состоянии `running`.

#### Регистрация Runner

1.  В вашем проекте GitLab перейдите в `Settings -> CI/CD -> Runners` и скопируйте URL и токен для регистрации.

2.  Запустите интерактивную регистрацию на машине с Runner'ом:
    ```bash
    sudo gitlab-runner register
    ```

3.  Ответьте на вопросы в процессе регистрации:
    *   **GitLab instance URL**: Введите URL вашего GitLab.
    *   **Registration token**: Вставьте скопированный токен.
    *   **Description**: Дайте Runner'у понятное имя.
    *   **Tags**: Укажите теги (например, `ansible, linux`), по которым задачи будут направляться на этот Runner.
    *   **Executor**: Выберите `shell`. Это самый простой для отладки executor, так как все скрипты выполняются прямо на хост-машине. Он не рекомендуется для продакшена из-за рисков безопасности и отсутствия изоляции.

После регистрации Runner появится в разделе `Settings -> CI/CD -> Runners` вашего проекта.

### 4.2. Запуск Ansible Playbook из GitLab CI

Теперь создадим пайплайн для запуска плейбука.

**Структура проекта:**
```
.
├── ansible.cfg
├── hosts.ini
├── playbook.yml
└── .gitlab-ci.yml
```

**playbook.yml:**
```yaml
- name: "Ping hosts"
  hosts: all
  gather_facts: false
  tasks:
    - name: "Ping host"
      ansible.builtin.ping:
```

**hosts.ini:**
```ini
# Для подключения по паролю (менее безопасно, требует sshpass)
# testnode ansible_host=1.2.3.4 ansible_user=devops ansible_ssh_pass=secret
# Для подключения по ключу (рекомендуется)
testnode ansible_host=1.2.3.4 ansible_user=devops
```

**ansible.cfg:**
```ini
[defaults]
host_key_checking = False # Отключаем проверку ключей для упрощения
```

**Пример `.gitlab-ci.yml`:**
```yaml
stages:
  - provision

ansible_run:
  stage: provision
  tags:
    - ansible # Указываем тег нашего Runner'а
  script:
    - ansible --version # Проверяем, что Ansible доступен
    # Запускаем плейбук, используя SSH-ключ из переменной
    - echo "${SSH_PRIVATE_KEY}" > key.pem
    - chmod 600 key.pem
    - ansible-playbook playbook.yml -i hosts.ini --private-key key.pem
```

#### Использование SSH-ключей

Как показано в примере выше, безопасный способ подключения — использование SSH-ключей.

1.  В проекте GitLab создайте переменную `SSH_PRIVATE_KEY` в разделе `Settings -> CI/CD -> Variables`.
2.  Вставьте в нее содержимое **приватного** ключа, у которого есть доступ к целевым хостам.
3.  Пометьте переменную как `Masked` для предотвращения ее отображения в логах.
4.  Пайплайн, как в примере выше, создаст временный файл с ключом, установит на него правильные права (`600`) и передаст его в `ansible-playbook` через флаг `--private-key`.

Этот метод полностью соответствует подходу, описанному в разделе **"Управление секретами"**.
