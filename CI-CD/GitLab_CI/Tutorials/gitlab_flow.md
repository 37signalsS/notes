# Практическое руководство: Использование GitLab Flow

GitLab Flow — это набор практик по работе с Git, который предлагает простую и эффективную альтернативу сложным моделям, таким как GitFlow. Он тесно интегрирован с возможностями платформы GitLab, такими как Merge Requests и CI/CD.

Это руководство демонстрирует базовый цикл работы по GitLab Flow.

---

## Шаг 1: Создание ветки для новой функциональности (Feature Branch)

Основное правило — никогда не работать напрямую в `main` (или `master`) ветке. Любая новая работа (фича, багфикс) начинается в отдельной ветке.

1.  **Склонируйте репозиторий**, если вы еще не сделали этого:
    ```bash
    git clone <ваш-ssh-или-https-url-репозитория>
    cd <имя-репозитория>
    ```

2.  **Создайте новую ветку** и переключитесь на нее. Название ветки должно быть осмысленным (например, `feature/add-user-authentication` или `fix/login-bug-123`).
    ```bash
    git checkout -b feature/my-new-feature
    ```

## Шаг 2: Внесение изменений и коммиты

Работайте в своей новой ветке, вносите изменения в код. Делайте атомарные, логически завершенные коммиты.

1.  **Проверьте статус** изменений:
    ```bash
    git status
    ```

2.  **Добавьте измененные файлы** в индекс:
    ```bash
    git add .
    ```

3.  **Зафиксируйте изменения** с понятным сообщением:
    ```bash
    git commit -m "Add initial implementation of my new feature"
    ```

## Шаг 3: Отправка ветки на удаленный сервер

Когда вы готовы поделиться своей работой или хотите запустить CI/CD пайплайн для вашей ветки, отправьте ее в удаленный репозиторий.

```bash
# При первой отправке новой ветки
git push --set-upstream origin feature/my-new-feature
```
Последующие коммиты в эту ветку можно отправлять простой командой `git push`.

## Шаг 4: Создание Merge Request (MR)

Merge Request (или Pull Request в терминологии GitHub) — это центральный элемент совместной работы.

1.  После выполнения `git push`, GitLab выведет в консоль прямую ссылку для создания MR. Скопируйте и откройте ее в браузере.
2.  Либо перейдите в UI вашего проекта в GitLab, где вы увидите плашку с предложением создать MR для только что отправленной ветки.
3.  В форме создания MR:
    *   Задайте понятное **название**.
    *   Напишите подробное **описание**, объясняющее, что и зачем было сделано.
    *   **Назначьте ревьюера** (Assignee/Reviewer) — коллегу, который должен проверить ваш код.
    *   Установите галочку **"Delete source branch when merge request is accepted"**, чтобы репозиторий оставался чистым.

## Шаг 5: Ревью, CI/CD и слияние

1.  **CI/CD:** GitLab автоматически запустит пайплайн для вашей ветки. Слияние MR часто блокируется, пока все тесты и проверки в пайплайне не будут успешно пройдены.
2.  **Код-ревью:** Коллеги просматривают ваши изменения, оставляют комментарии и могут запросить доработки.
3.  **Слияние (Merge):** После успешного прохождения CI и получения одобрения (Approve) от ревьюеров, ответственный за слияние (или вы сами, если права позволяют) нажимает кнопку **Merge**.

## Шаг 6: Создание тега и релиза (опционально, но рекомендуется)

После того как важные изменения попали в `main`, хорошей практикой является создание тега для обозначения новой версии продукта.

1.  Перейдите в раздел **Deployments > Tags** в вашем проекте.
2.  Нажмите **New tag**.
3.  **Tag name:** Укажите версию, следуя семантическому версионированию (например, `v1.0.0`).
4.  **Create from:** Убедитесь, что выбрана ветка `main`.
5.  **Release notes:** Напишите здесь список изменений (changelog) для этой версии.
6.  Нажмите **Create tag**.

GitLab автоматически создаст не только тег, но и **Release** на странице **Deployments > Releases**, прикрепив к нему архивы с исходным кодом на момент создания тега.
