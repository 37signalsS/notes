# GitLab Flow: стратегии ветвления и рабочие процессы

## Определения

**GitLab Flow** — это прагматичная стратегия ветвления Git, сочетающая разработку через функциональные ветки (feature branches) с системой отслеживания задач. Она является гибким гибридом между GitHub Flow (простота) и Git Flow (структурированность), адаптированным для современных CI/CD процессов.

**Upstream First (Приоритет основной ветки)** — ключевой принцип GitLab Flow, согласно которому любые изменения (фичи, багфиксы) должны сначала попасть в основную ветку (`main`), и только после этого они могут быть перенесены («продвинуты») в ветки окружений или релизов.

## Основные концепции

### 1. Интеграция с задачами (Issues)
Любое изменение начинается с создания Issue. Это обеспечивает трассируемость: каждый коммит и Merge Request (MR) связан с конкретной бизнес-задачей или техническим багом.

### 2. Feature-ветки для всех изменений
Прямые коммиты в `main` запрещены. Вся работа ведется в кратковременных ветках.
* **Именование:** `feature/ID-description` или `bugfix/ID-description` (где ID — номер задачи).
* **Жизненный цикл:** Создание → Разработка → MR → Тестирование → Слияние → Удаление.

### 3. Merge Request (MR) как центр качества
MR в GitLab Flow — это не просто запрос на слияние, а полноценный инструмент контроля:
* **CI/CD Gates:** Пайплайны должны быть «зелеными» перед слиянием.
* **Code Review:** Обязательная проверка кода коллегами.
* **Review Apps:** Динамические окружения, позволяющие увидеть результат работы до слияния в `main`.

### 4. Защищенные ветки (Protected Branches)
Основные ветки (`main`, `production`, `stable-*`) защищены от прямого пуша и удаления. Слияние в них возможно только через MR и при прохождении всех проверок.

### 5. Гигиена истории
* **Squash and Merge:** Рекомендуется объединять множество мелких коммитов ветки в один при слиянии в `main`, чтобы сохранить историю чистой и линейной.
* **Conventional Commits:** Использование стандартизированных сообщений коммитов (`feat:`, `fix:`, `chore:`) для автоматизации генерации Changelog.

## Практические сценарии

### Сценарий 1: Базовый GitLab Flow (Continuous Deployment)
Идеально подходит для SaaS-решений, где `main` всегда готова к деплою в Production.

#### 1. Создание ветки и работа
```bash
# Обновление локального main
git checkout main
git pull origin main

# Создание ветки под задачу #123
git checkout -b feature/123-user-auth
# → Switched to a new branch 'feature/123-user-auth'

# Работа с кодом и фиксация (Conventional Commits)
git add .
git commit -m "feat(auth): add google oauth2 provider"
# → [feature/123-user-auth abc1234] feat(auth): add google oauth2 provider
```

#### 2. Отправка и создание MR
```bash
git push -u origin feature/123-user-auth
# → Branch 'feature/123-user-auth' set up to track remote branch from 'origin'.
```
*В UI GitLab создается MR. После прохождения тестов и ревью нажимается **Squash and Merge**.*

---

### Сценарий 2: GitLab Flow с ветками окружений (Continuous Delivery)
Используется, когда деплой в Production требует ручного подтверждения или проходит через этапы Staging/Pre-prod.

1.  **Ветка `main`**: Соответствует окружению **Staging**. Все фичи вливаются сюда.
2.  **Ветка `production`**: Соответствует **Production**.

#### Продвижение кода в Production:
Код никогда не правится напрямую в `production`.
1. Создается MR из `main` в `production`.
2. GitLab CI автоматически запускает тесты для проверки совместимости.
3. После аппрува выполняется слияние (Merge) — это и есть триггер деплоя на прод.

---

### Сценарий 3: GitLab Flow с ветками релизов (Versioned Software)
Для мобильных приложений, библиотек или коробочного ПО, требующего поддержки нескольких версий одновременно.

1.  Все изменения вливаются в `main`.
2.  Для выпуска версии `2.3` создается ветка `2-3-stable` от `main`.
3.  **Багфикс в релизе (Cherry-pick):**
    *   Ошибка исправляется в `main`.
    *   Исправление переносится в `2-3-stable` через `git cherry-pick`.
    *   Это гарантирует, что исправление не будет забыто в следующей версии (`main`).

## Дополнительная информация

### Лучшие практики 2025
* **Feature Flags:** Используйте переключатели функционала, чтобы вливать незавершенный код в `main` без риска для пользователей. Это уменьшает количество долгоживущих веток.
* **DevSecOps:** Интегрируйте SAST/DAST сканирование на этапе MR. GitLab Flow позволяет блокировать небезопасный код до попадания в `main`.
* **Автоматизация Cherry-picking:** Для стабильных веток используйте ботов или GitLab CI для автоматического переноса фиксов с меткой `backport`.
