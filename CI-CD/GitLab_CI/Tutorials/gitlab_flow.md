### Определения

**GitLab Flow** — это упрощенная и прагматичная стратегия ветвления Git, которая объединяет разработку, управляемую функциональностью (feature-driven development), с системой отслеживания задач (issue tracking). Она представляет собой набор лучших практик, предложенных GitLab, для обеспечения прозрачного и эффективного процесса разработки и деплоя.

### Основные концепции

* **Интеграция с задачами (Issues):** Каждое изменение в коде (новая функция, исправление бага) начинается с создания задачи (Issue). Это обеспечивает прозрачность и помогает держать команду в курсе целей каждого изменения.
* **Feature-ветки для всех изменений:** Любая работа выполняется в отдельной ветке, созданной от `main`. Прямые коммиты в `main` запрещены. Название ветки часто включает номер задачи (например, `123-fix-login-bug`).
* **Merge Request (MR) — центр всего:** Когда работа в ветке завершена, создается Merge Request (в GitHub он называется Pull Request) для слияния изменений в `main`. MR является центральной точкой для:
  * **Код-ревью:** Коллеги проверяют и обсуждают изменения.
  * **CI/CD:** Автоматически запускаются пайплайны для сборки, тестирования и сканирования кода.
  * **Обсуждения:** Вся коммуникация по изменению ведется в рамках MR.
* **Простота по сравнению с Git Flow:** GitLab Flow является более простой альтернативой [другим рабочим процессам, таким как Git Flow](../../../Git/git_workflows.md). В базовом варианте он не требует отдельных веток `develop` и `release`, что снижает сложность.
* **Ветки окружений (опционально):** Для более сложных проектов, где требуется деплой в несколько сред (например, `staging`, `production`), GitLab Flow предлагает использовать долгоживущие ветки для каждого окружения. Изменения "текут" из `main` в `staging` и затем в `production`.

### Практические сценарии

#### Базовый GitLab Flow

##### Создание Feature-ветки

Основное правило — никогда не работать напрямую в `main`. Любая новая работа (фича, багфикс) начинается в отдельной ветке, связанной с задачей.

1. **Склонируйте репозиторий**, если вы еще не сделали этого:

    ```bash
    git clone <ваш-ssh-или-https-url-репозитория>
    cd <имя-репозитория>
    ```

2. **Создайте новую ветку** и переключитесь на нее. Название ветки должно быть осмысленным (например, `feature/add-user-authentication` или `123-fix-login-bug`).

    ```bash
    git checkout -b feature/my-new-feature
    # → Switched to a new branch 'feature/my-new-feature'
    ```

##### Внесение и фиксация изменений

Работайте в своей новой ветке, вносите изменения в код. Делайте атомарные, логически завершенные коммиты.

1. **Добавьте измененные файлы** в индекс:

    ```bash
    git add .
    ```

2. **Зафиксируйте изменения** с понятным сообщением:

    ```bash
    git commit -m "feat: Add initial implementation of my new feature"
    # → [feature/my-new-feature abc1234] feat: Add initial implementation of my new feature
    ```

##### Отправка ветки на удаленный сервер

Когда вы готовы поделиться своей работой или хотите запустить CI/CD пайплайн для вашей ветки, отправьте ее в удаленный репозиторий.

```bash
# При первой отправке новой ветки
git push --set-upstream origin feature/my-new-feature
# → Branch 'feature/my-new-feature' set up to track remote branch 'feature/my-new-feature' from 'origin'.
```

##### Создание Merge Request (MR)

1. После `git push` GitLab выведет в консоль прямую ссылку для создания MR. Откройте ее в браузере.
2. В форме создания MR:
    * Задайте понятное **название**.
    * Напишите подробное **описание**, объясняя, что и зачем было сделано. Свяжите MR с соответствующей задачей.
    * **Назначьте ревьюера** (Reviewer).
    * Установите галочку **"Delete source branch when merge request is accepted"**, чтобы репозиторий оставался чистым.

##### Ревью, CI/CD и слияние

1. **CI/CD:** GitLab автоматически запустит пайплайн для вашей ветки. Слияние MR часто блокируется, пока все тесты и проверки не пройдут успешно.
2. **Код-ревью:** Коллеги просматривают ваши изменения, оставляют комментарии и могут запросить доработки.
3. **Слияние (Merge):** После успешного прохождения CI и получения одобрения (Approve) от ревьюеров, ответственный за слияние (или вы сами) нажимает кнопку **Merge**.

##### Создание тега и релиза (опционально)

После того как важные изменения попали в `main`, хорошей практикой является создание тега для обозначения новой версии продукта.

1. Перейдите в **Deployments > Tags** в вашем проекте.
2. Нажмите **New tag**.
3. **Tag name:** Укажите версию (`v1.0.0`).
4. **Create from:** Убедитесь, что выбрана ветка `main`.
5. **Release notes:** Напишите список изменений (changelog).
6. Нажмите **Create tag**.

Это автоматически создаст **Release** на странице **Deployments > Releases**.
