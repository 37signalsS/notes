# Концепции и продвинутые возможности GitLab CI/CD

## Основы GitLab CI/CD

Это руководство представляет собой введение в настройку и использование GitLab CI/CD, фокусируясь на основных концепциях и структуре файла `.gitlab-ci.yml`.

### 1. Файл `.gitlab-ci.yml`

Конфигурация пайплайна в GitLab CI/CD определяется с помощью файла `.gitlab-ci.yml`, который должен находиться в корне вашего репозитория.

#### 1.1. Именование и формат

*   **Имя файла:** `.gitlab-ci.yml` (обязательно).
*   **Формат:** YAML.
*   **Отступы:** Используйте пробелы вместо табуляции для отступов, как того требует синтаксис YAML.

GitLab автоматически распознает этот файл и активирует CI/CD для вашего проекта.

#### 1.2. Основные концепции

Файл `.gitlab-ci.yml` состоит из следующих ключевых элементов:

*   **Этапы (Stages):**
    *   `stages:` Определяют последовательность выполнения групп задач (jobs).
    *   Задачи внутри одной стадии могут выполняться параллельно, но следующая стадия начнется только после успешного завершения всех задач предыдущей.
    *   Пример: `lint`, `test`, `build`, `deploy`.

*   **Задачи (Jobs):**
    *   `job_name:` — это отдельные рабочие процессы.
    *   Каждая задача должна иметь уникальное имя. Избегайте использования зарезервированных слов GitLab (например, `stages`, `script`) в качестве названий задач.
    *   Задачи привязываются к определенным этапам.

*   **Скрипты (Script):**
    *   `script:` — это директива, которая содержит одну или несколько shell-команд, выполняемых Runner'ом для данной задачи.
    *   Команды выполняются последовательно. Если какая-либо команда завершается неудачей, вся задача (job) помечается как неуспешная.

**Простой пример структуры `.gitlab-ci.yml`:**

```yaml
stages:
  - build
  - test

build_job:
  stage: build
  script:
    - echo "Performing build..."
    - build_command

test_job_lint:
  stage: test
  script:
    - echo "Running linter..."
    - linter_command

test_job_unit:
  stage: test
  script:
    - echo "Running unit tests..."
    - unit_test_command
```

### 2. Встроенный линтер

GitLab предоставляет встроенный линтер для проверки синтаксиса вашего `.gitlab-ci.yml` файла. Это помогает выявлять тривиальные ошибки на ранних этапах. Его можно найти в веб-интерфейсе GitLab в разделе **Pipelines -> CI Lint**. При активном использовании `include` и `extends` линтер показывает **полностью "развернутую"** конфигурацию, что является незаменимым инструментом для отладки.

## GitLab CI как конструктор Workflow

GitLab CI — это не просто инструмент для сборки и тестирования кода. Его гибкость позволяет использовать его как универсальный конструктор для автоматизации практически любых процессов (workflow), даже не связанных напрямую с кодом, например, для задач по расписанию (аналог cron) или управления инфраструктурой.

Ключевая идея — описание всего процесса в декларативном `.gitlab-ci.yml` файле, который хранится вместе с кодом, обеспечивая версионируемость и прозрачность.

### Основные строительные блоки

-   **`stages`**: Определяют последовательность выполнения этапов (например, `build`, `test`, `deploy`). Задания внутри одного этапа выполняются параллельно, но переход к следующему этапу происходит только после успешного завершения всех заданий в текущем.
-   **`jobs`**: Конкретные задачи, выполняемые Runner'ами. Каждое задание привязано к определённому этапу.
-   **`artifacts`**: Результаты выполнения задания (собранные бинарные файлы, отчёты о тестах), которые сохраняются на сервере GitLab и могут передаваться между заданиями, даже на разных Runner'ах. Артефакты имеют срок хранения.

    GitLab CI поддерживает несколько типов специализированных отчетов и файлов для артефактов:

    -   **`artifacts:reports`**: Используется для загрузки отчетов в формате, понятном GitLab. Это позволяет визуализировать результаты тестов, покрытия кода, SAST-сканирований и других проверок прямо в интерфейсе GitLab.
        -   **`junit`**: Отчеты о модульных и интеграционных тестах в формате JUnit XML, отображаются на вкладке "Tests" в Pipeline.
        -   **`cobertura`**: Отчеты о покрытии кода, отображаются в Merge Request'ах.
        -   **`sast`**, **`dast`**, **`dependency_scanning`** и другие: Отчеты о безопасности, интегрируются в Security Dashboard.

        ```yaml
        test_job:
          stage: test
          script:
            - run_tests.sh
          artifacts:
            reports:
              junit: junit-report.xml
              cobertura: coverage.xml
        ```

    -   **`artifacts:dotenv`**: Позволяет передавать переменные окружения между заданиями в рамках одного пайплайна. Эти переменные автоматически загружаются в окружение последующих заданий, делая их доступными без необходимости явного экспорта.

        ```yaml
        setup_job:
          stage: setup
          script:
            - echo "MY_VARIABLE=hello" > build.env
            - echo "ANOTHER_VAR=world" >> build.env
          artifacts:
            reports:
              dotenv: build.env

        deploy_job:
          stage: deploy
          script:
            - echo $MY_VARIABLE $ANOTHER_VAR # Выведет "hello world"
          needs:
            - job: setup_job
              artifacts: true # Важно, чтобы артефакты были доступны
        ```
-   **`cache`**: Механизм для сохранения файлов между запусками пайплайнов на одном и том же Runner'е (например, `node_modules` или `.m2`). Его цель — ускорение сборок. Кэш не гарантирует наличие данных, в отличие от артефактов.

### Runners и Executors: Глубокое погружение

**GitLab Runner** — это отдельное приложение (статический бинарный файл на Go), которое не входит в основной пакет установки GitLab Omnibus. Его можно запустить практически где угодно. Runner является клиентским приложением, которое взаимодействует с двумя основными сущностями:
1.  **GitLab Server:** Runner с заданным интервалом опрашивает сервер на предмет наличия новых задач (jobs).
2.  **Среда выполнения:** Место, где фактически выполняются шаги пайплайна (скрипты).

#### Механизм регистрации и безопасность

Поскольку Runner'ы могут быть запущены кем угодно и где угодно, важно понимать механизм их подключения и риски безопасности.

*   **Теги:** Каждому Runner'у можно присвоить один или несколько тегов. Задачи в пайплайне могут быть нацелены на Runner'ы с определенными тегами.
*   **Риск:** Если у злоумышленника есть контроль над Runner'ом, теги которого совпадают с вашими, он может перехватить выполнение вашего пайплайна и получить доступ к секретам (токены, переменные окружения) и исходному коду.
*   **Защита:**
    1.  **Регистрационные токены:** Это одноразовые токены, используемые только для первоначального подключения Runner'а. Они бывают трех уровней: для конкретного проекта, для группы проектов или для всего экземпляра GitLab (shared runner). **Никогда не раскрывайте эти токены.**
    2.  **Аутентификационный токен:** В момент регистрации GitLab выдает Runner'у постоянный аутентификационный токен. Именно этот токен (в паре с URL сервера) используется для всех последующих коммуникаций и однозначно идентифицирует Runner. Он хранится в конфигурационном файле Runner'а (`config.toml`).
    3.  **Отключение общих Runner'ов:** В настройках проекта можно запретить использование shared runner'ов, чтобы гарантировать, что пайплайны будут выполняться только на ваших собственных, контролируемых Runner'ах.

#### Executors: Архитектура исполнителей

Сам Runner — это управляющий компонент. Модули, которые непосредственно взаимодействуют со средой выполнения, называются **Executors**.

*   **`shell`:** Самый простой executor. Выполняет скрипты прямо на хост-машине от имени пользователя, под которым запущен Runner. Требует, чтобы все зависимости (например, `node`, `docker`) были установлены на хосте.
*   **`ssh`:** Подключается к удаленному серверу по SSH и выполняет скрипты там.
*   **`virtualbox` / `parallels`:** Создает новую виртуальную машину для каждой задачи. Обеспечивает максимальную изоляцию, но является самым медленным.
*   **`docker`:** Наиболее популярный executor.
    *   **Принцип работы:** Для каждой задачи создается чистый Docker-контейнер из образа, указанного в `image`.
    *   **Взаимодействие с Docker Daemon:** Docker-клиент (в нашем случае, Runner) общается с Docker-демоном через сокет (TCP или Unix-сокет, по умолчанию `/var/run/docker.sock`).
    *   **"Docker-in-Docker":** Когда сам Runner запущен в Docker-контейнере, для управления Docker-демоном хоста используется трюк с монтированием сокета: `-v /var/run/docker.sock:/var/run/docker.sock`. Runner, обращаясь к сокету внутри своего контейнера, на самом деле отправляет команды Docker-демону хост-машины, который и запускает "соседние" контейнеры для выполнения задач. **Это предоставляет значительные привилегии контейнеру с Runner'ом.**
*   **`kubernetes`:**
    *   **Принцип работы:** Вместо Docker-контейнеров, для каждой задачи создается новый Pod в кластере Kubernetes.
    *   **Аутентификация:** Может использовать стандартный `kubeconfig` с клиентскими сертификатами для подключения к API-серверу Kubernetes.
    *   **Рекомендуемый подход:** Запускать сам GitLab Runner как Pod внутри кластера. В этом случае ему можно выдать `ServiceAccount` с необходимыми правами, и он автоматически обнаружит API-сервер и аутентифицируется для создания Pod'ов с задачами.

#### Настройка кэширования

Кэш используется для сохранения файлов (например, зависимостей `node_modules` или `.m2`) между запусками пайплайнов для ускорения сборок. Настройка кэша состоит из двух частей: в `.gitlab-ci.yml` (что кэшировать) и в `config.toml` Runner'а (где хранить кэш).

Существует два основных способа хранения кэша на стороне Runner'а:

1.  **Объектное хранилище (S3-совместимое):**
    *   **Принцип:** Runner загружает и скачивает zip-архивы с кэшем в S3-совместимое хранилище (MinIO, AWS S3, Ceph и т.д.).
    *   **Настройка:** В `config.toml` в секции `[runners.cache.s3]` указываются учетные данные и адрес S3-бакета. Это самый простой и надежный способ, особенно для распределенных Runner'ов.

2.  **Локальный кэш (на диске):**
    *   **Принцип:** Runner сохраняет кэш на локальном диске.
    *   **Проблема с Docker Executor:** Так как каждая задача выполняется в новом контейнере, который после завершения удаляется, кэш, сохраненный внутри контейнера, будет утерян.
    *   **Решение:** Необходимо монтировать директорию с хост-машины внутрь каждого job-контейнера. Это делается в `config.toml`:
        ```toml
        # Глобальная секция
        [runners]
          # Директория на хосте для хранения архивов с кэшем
          cache_dir = "/cache"

        # Секция Docker executor'а
        [runners.docker]
          # Монтируем директорию кэша внутрь каждого job-контейнера
          volumes = ["/cache"]
        ```
    Таким образом, когда задача сохраняет кэш в `/cache` внутри контейнера, он на самом деле попадает в директорию `/cache` на хост-машине и переживает удаление контейнера.

### Создание переиспользуемых и композитных пайплайнов

GitLab CI предоставляет мощные механизмы для избежания дублирования кода и создания гибких, модульных пайплайнов.

#### 1. `extends` — Наследование конфигураций

Механизм `extends` позволяет заданию унаследовать всю конфигурацию от другого, "скрытого" задания (начинающегося с точки). Это базовый способ переиспользования.

```yaml
.base_job:
  image: ruby:2.7
  script:
    - echo "This is from the base job."

test_job:
  extends: .base_job
  script:
    - echo "This is from the test job. It will run after the base script."
    # Важно: скрипт из .base_job будет объединён со скриптом test_job.
```

#### 2. YAML Anchors (`&`) и Aliases (`*`)

Помимо `!reference`, для переиспользования можно использовать стандартный механизм YAML — якоря (anchors) и псевдонимы (aliases). Это не является специфической функцией GitLab CI, но поддерживается его парсером.

-   **`&anchor_name`**: Задает якорь (имя) для любого элемента YAML.
-   **`*anchor_name`**: Вставляет содержимое, на которое указывает якорь.

```yaml
.after_script_template: &after_script_definition
  - echo "Cleaning up..."

job1:
  script:
    - echo "Running job 1"
  after_script:
    - *after_script_definition

job2:
  script:
    - echo "Running job 2"
  after_script:
    - *after_script_definition
```

#### 3. `include` — Композиция из внешних файлов

`include` — один из самых мощных механизмов, позволяющий собрать пайплайн из нескольких YAML-файлов. Это делает конфигурацию модульной и легко управляемой.

Поддерживаемые источники:

-   **`include:local`**: Файл из того же репозитория.
    ```yaml
    include: '/templates/.build-template.yml'
    ```
-   **`include:project`**: Файл из другого проекта в том же инстансе GitLab.
    ```yaml
    include:
      - project: 'my-group/my-ci-templates'
        ref: main
        file: '/maven-build.yml'
    ```
-   **`include:remote`**: Файл по URL.
    ```yaml
    include:
      - remote: 'https://example.com/ci-config.yml'
    ```
-   **`include:template`**: Встроенные шаблоны GitLab (например, для `Node.js`, `Docker`, `SAST`).
    ```yaml
    include:
      - template: Security/SAST.gitlab-ci.yml
    ```

#### 4. CI/CD Catalog (Components)

Новый подход к переиспользованию, позволяющий создавать версионируемые **компоненты** — полноценные, изолированные блоки CI/CD логики, которые можно публиковать в общем каталоге и использовать в проектах.

```yaml
include:
  - component: '$CI_SERVER_HOST/my-org/my-component@1.0'
    inputs:
      stage: build
```

### Эволюция переиспользуемого пайплайна: практический пример

Рассмотрим типичный путь, который проходят команды при создании и поддержке пайплайнов, и как механизмы `include` и `extends` решают возникающие проблемы.

#### Этап 1: Проблема — Дублирование кода (Boilerplate)

**Ситуация:** Команда пишет много микросервисов, и для каждого нужно собирать Docker-образ. Разработчики копируют один и тот же большой кусок YAML-кода в `.gitlab-ci.yml` каждого нового проекта.

**Пример boilerplate-кода:**
```yaml
build-docker-image:
  stage: build
  image: docker:20.10
  services:
    - docker:20.10-dind
  variables:
    IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
```

**Проблемы:**
1.  **Сложность поддержки:** Если нужно обновить версию Docker или изменить логику сборки (например, добавить сканирование), придется вручную править файлы во всех репозиториях.
2.  **Человеческий фактор:** При копировании легко допустить ошибку.
3.  **Загромождение:** `.gitlab-ci.yml` становится большим и трудночитаемым.

#### Этап 2: Решение — Централизация с помощью `include`

**Решение:** Вынести общий код в отдельный файл в центральном репозитории CI-шаблонов и подключать его с помощью `include`.

**Создаем репозиторий `ci-templates` с файлом `docker-build.yml`:**
```yaml
# ci-templates/docker-build.yml
build-docker-image:
  stage: docker-build
  image: docker:20.10
  services:
    - docker:20.10-dind
  variables:
    IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
```

**В `.gitlab-ci.yml` проекта теперь используется `include`:**
```yaml
stages:
  - docker-build # Необходимо объявить стадию из шаблона

include:
  - project: 'my-group/ci-templates'
    ref: main
    file: '/docker-build.yml'
```

**Результат:** Код централизован. Изменения вносятся в одном месте.

#### Этап 3: Проблема — Отсутствие гибкости

**Ситуация:** Шаблон `include` предоставляет готовую задачу, но не позволяет разработчикам кастомизировать ее под свои нужды (например, добавить `before_script` или передать специфичные для сборки `variables`), не отказываясь от шаблона целиком.

#### Этап 4: Решение — Гибкость с помощью `extends`

**Решение:** Превратить задачу в шаблоне в "скрытую" (начинающуюся с точки) и наследовать ее в пайплайне проекта с помощью `extends`.

**Обновляем `ci-templates/docker-build.yml`:**
```yaml
# ci-templates/docker-build.yml
# Имя задачи теперь начинается с точки, она не будет запускаться сама по себе
.docker-build-template:
  stage: build
  image: docker:20.10
  services:
    - docker:20.10-dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build 
        --build-arg CI_JOB_TOKEN=${CI_JOB_TOKEN} 
        -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA 
        .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

**В `.gitlab-ci.yml` проекта теперь используется `extends`:**
```yaml
include:
  - project: 'my-group/ci-templates'
    ref: main
    file: '/docker-build.yml'

stages:
  - build

build-my-app:
  stage: build
  extends: .docker-build-template
  variables:
    # Теперь можно добавлять свои переменные
    EXTRA_BUILD_ARG: "my-value"
  before_script:
    # И добавлять свои шаги
    - echo "Custom step before building"
```

**Результат:** Сохранены и централизация, и гибкость для кастомизации.

#### Этап 5: Абстрагирование деталей реализации (Безопасность)

**Ситуация:** Платформенная команда решает, что `docker:dind` небезопасен (требует привилегированного режима) и нужно перейти на более безопасный сборщик, например, **Kaniko**.

**Решение:** Так как все проекты используют централизованный шаблон, достаточно изменить только его.

**Обновляем `ci-templates/docker-build.yml`, заменяя Docker на Kaniko:**
```yaml
# ci-templates/docker-build.yml
.docker-build-template:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:debug
    entrypoint: [""]
  script:
    - /kaniko/executor
      --context $CI_PROJECT_DIR
      --dockerfile $CI_PROJECT_DIR/Dockerfile
      --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

**Результат:** Для конечных пользователей (разработчиков) ничего не поменялось. Их `.gitlab-ci.yml` файлы остались прежними, но сборка теперь происходит с помощью другого, более безопасного инструмента. Это демонстрирует силу абстракции через шаблоны.

#### Мораль

Команды DevOps или платформенные инженеры должны создавать и поддерживать такие шаблоны, чтобы упростить жизнь разработчикам, позволив им сосредоточиться на коде, а не на тонкостях CI/CD. Правильно спроектированные шаблоны делают "правильный" способ сборки и развертывания самым простым.

### Расширенное управление Workflow

#### `rules` — Гибкие правила запуска

`rules` — это более мощная и гибкая альтернатива устаревшим директивам `only/except`. Они позволяют определять сложные условия для включения задачи в пайплайн. Правила проверяются по порядку, и первое же совпадение определяет поведение задачи.

**Ключевые условия в `rules`:**
- **`if`**: Основное условие, которое проверяет значение переменных.
- **`changes`**: Задача добавляется в пайплайн, только если были изменены указанные файлы или пути. Это **чрезвычайно полезно для монорепозиториев**, так как позволяет запускать сборку и тесты только для затронутых компонентов.
- **`when`**: Определяет, как будет выполняться задача (`on_success`, `manual`, `always`, `delayed`).

```yaml
deploy_job:
  stage: deploy
  script:
    - echo "Deploying to production"
  rules:
    # Запускать, только если изменены файлы в директории 'backend/'
    - changes:
        - backend/**/*
    # И при этом только для ветки main
    - if: '$CI_COMMIT_BRANCH == "main"' 
    # Или для любого тега
    - if: '$CI_COMMIT_TAG'
    # Во всех остальных случаях — не запускать задачу
    - when: never
```
Задачи по расписанию (Cron-like): GitLab CI можно использовать для выполнения задач по расписанию, аналогично `cron` в Linux. Это делается путем создания "Расписания" (Schedules) для пайплайна через интерфейс GitLab. В `rules` можно использовать `$CI_PIPELINE_SOURCE == "schedule"` для запуска определенных заданий только при таком типе триггера.

#### `needs` — Построение направленного ациклического графа (DAG)

Ключевая возможность для оптимизации времени выполнения пайплайна. По умолчанию, все задачи в одной стадии (`stage`) должны успешно завершиться, прежде чем начнется следующая стадия. `needs` ломает эту строгую последовательность и превращает пайплайн в направленный ациклический граф (DAG).

Задача с директивой `needs` может стартовать, как только завершатся указанные в `needs` задачи, **не дожидаясь окончания всей их стадии**.

**Пример:**

Рассмотрим пайплайн со стадиями `build` и `test`.
- Стадия `build` содержит три параллельные задачи: `build:web` (15 сек), `build:android` (30 сек), `build:ios` (45 сек).
- Стадия `test` содержит две задачи: `test:web` и `test:all`.
- `test:web` зависит только от `build:web`.

```yaml
stages:
  - build
  - test

build:web:
  stage: build
  script:
    - sleep 15
    - echo "Web built"

build:android:
  stage: build
  script:
    - sleep 30
    - echo "Android built"

build:ios:
  stage: build
  script:
    - sleep 45
    - echo "iOS built"

test:web:
  stage: test
  needs: ["build:web"] # Эта задача зависит только от build:web
  script:
    - echo "Testing web..."

test:all:
  stage: test
  script: # Нет 'needs', значит, ждет окончания всей стадии 'build'
    - echo "Testing all platforms..."
```

**Порядок выполнения:**
1.  Запускаются все три задачи `build:*` одновременно.
2.  Через **15 секунд** `build:web` завершается.
3.  **Сразу после этого** запускается `test:web`, не дожидаясь `build:android` и `build:ios`.
4.  Через **45 секунд** `build:ios` (самая долгая задача в стадии `build`) завершается.
5.  **Только после этого** запускается `test:all`, так как она следует стандартному порядку стадий.

Таким образом, `needs` позволяет значительно ускорить получение обратной связи, запуская зависимые задачи раньше.

#### `parallel:matrix` — Матричные сборки

Позволяет запускать одно и то же задание несколько раз с разными комбинациями переменных. Идеально для тестирования на разных версиях ПО или для разных архитектур.

```yaml
test:
  stage: test
  script: "echo 'Testing with $PROVIDER on $STACK'"
  parallel:
    matrix:
      - PROVIDER: [aws, gcp]
        STACK: [nodejs, python]
```
Этот пример создаст 4 параллельных задания `test`.

### Переменные и Управление Секретами

Переменные являются ключевым элементом для создания динамичных и безопасных пайплайнов. Их можно определять на разных уровнях: в самом `.gitlab-ci.yml`, на уровне проекта или группы.

#### Типы и атрибуты переменных

В настройках проекта (`Settings > CI/CD > Variables`) можно определить переменные со следующими типами и атрибутами:

-   **Тип `Variable`**: Стандартная переменная окружения, представляющая собой пару "ключ-значение".
-   **Тип `File`**: Содержимое переменной сохраняется во временный файл на GitLab Runner'е, а сама переменная окружения содержит **путь** к этому файлу. Это предпочтительный способ для передачи многострочных данных, таких как SSH-ключи или конфигурационные файлы.

-   **Атрибут `Protected` (Защищенная)**: Переменная будет доступна **только** в пайплайнах, запущенных для защищенных веток (protected branches) или тегов (protected tags). Это критически важно для секретов, используемых при развертывании в `production`.
-   **Атрибут `Masked` (Маскированная)**: Значение переменной будет замаскировано (заменено на `[MASKED]`) в логах выполнения задач. Это помогает предотвратить случайную утечку секретов. Требования к значению для маскирования: однострочное, без пробелов, длиной не менее 8 символов.

#### Предопределенные переменные

GitLab автоматически предоставляет огромное количество предопределенных переменных в каждом пайплайне. Они обычно начинаются с префикса `CI_`.

**Ключевые примеры:**
-   `CI=true`: Позволяет скриптам надежно определять, что они запущены в среде CI/CD.
-   `CI_COMMIT_BRANCH`: Имя ветки, для которой запущен пайплайн.
-   `CI_COMMIT_SHORT_SHA`: Короткий (8 символов) хеш коммита.
-   `CI_PROJECT_NAME`: Имя проекта.
-   `CI_PIPELINE_ID`: Уникальный ID текущего пайплайна.
-   `CI_JOB_TOKEN`: Временный токен, который живет только во время выполнения задачи. Его можно использовать для аутентификации при запросах к API GitLab, доступе к GitLab Container Registry или другим репозиториям в рамках одного проекта.

Полный список предопределенных переменных доступен в официальной документации GitLab.

#### Внешние хранилища секретов и продвинутые техники

Для более сложного и централизованного управления секретами рекомендуется использовать специализированные решения.

1.  **Шифрование на уровне приложения (`ansible-vault`)**
    -   **Принцип:** Секреты шифруются с помощью инструмента вроде `ansible-vault` и в зашифрованном виде сохраняются как обычные переменные в `Settings > CI/CD > Variables`. Пароль для расшифровки (vault password) хранится в отдельном, надежном месте (например, как секрет в Kubernetes, доступный для Runner'а). В процессе выполнения пайплайна задача использует пароль для расшифровки переменных "на лету".
    -   **Преимущества:** Позволяет скрыть содержимое секретов от тех, кто имеет доступ к настройкам GitLab, но не к хранилищу пароля.
    -   **Недостатки:** Требует ручного управления паролями и процессом шифрования/дешифрования.

2.  **Интеграция с HashiCorp Vault**
    -   **Принцип:** GitLab CI/CD имеет встроенную поддержку для интеграции с HashiCorp Vault. Пайплайн не хранит в себе никаких секретов, даже зашифрованных. Вместо этого, во время выполнения задачи, Runner аутентифицируется в Vault (например, с помощью JWT-токена, уникального для каждой задачи), получает временный токен доступа и запрашивает необходимые ему секреты напрямую из Vault.
    -   **Преимущества:**
        -   **Максимальная безопасность:** Секреты никогда не покидают Vault. Пайплайн получает их динамически и на короткое время.
        -   **Централизованное управление:** Все секреты, политики доступа и аудит находятся в одном месте.
        -   **Динамические секреты:** Vault может генерировать учетные данные (например, для базы данных) "на лету" с коротким сроком жизни.

Подробное пошаговое руководство по настройке интеграции смотрите в [Практическое руководство: Интеграция GitLab CI с HashiCorp Vault](./tutorial_gitlab_ci_with_hashicorp_vault.md).

### Дочерние и мультипроектные пайплайны (Downstream Pipelines)

GitLab CI позволяет одному пайплайну запускать другие, что открывает возможности для сложных и модульных workflow.

#### Способы запуска

1.  **Мультипроектные пайплайны (`trigger:project`)**:
    Пайплайн в одном проекте может запустить пайплайн в другом. Это полезно для управления зависимостями между микросервисами (например, успешная сборка библиотеки запускает пересборку зависимого от нее сервиса).

2.  **Дочерние пайплайны (`trigger:include`)**:
    Пайплайн может запускать дочерний пайплайн в том же проекте. Это используется для динамической генерации конфигурации "на лету" или для декомпозиции сложного `.gitlab-ci.yml` на несколько логических частей.

#### Ожидание завершения (`strategy: depend`)

По умолчанию, родительская задача завершается успешно сразу после *запуска* дочернего пайплайна, не дожидаясь его результата. Чтобы дождаться завершения и получить статус (успех/неудача), необходимо использовать `strategy: depend`.

#### Пример: мультипроектный пайплайн

**Проект A (запускающий): `.gitlab-ci.yml`**
```yaml
trigger_downstream_build:
  stage: deploy
  trigger:
    project: 'my-group/my-downstream-project' # Путь к дочернему проекту
    branch: main
    strategy: depend # Ждем завершения дочернего пайплайна
```

#### Пример: динамический дочерний пайплайн

**`.gitlab-ci.yml` (родительский)**
```yaml
generate-config:
  stage: setup
  script:
    - ./generate_ci_config.sh > generated-config.yml
  artifacts:
    paths:
      - generated-config.yml

run-child-pipeline:
  stage: build
  trigger:
    include:
      - artifact: generated-config.yml
        job: generate-config
    strategy: depend
```

Этот подход обеспечивает максимальную гибкость, позволяя, например, собирать и тестировать только те компоненты монорепозитория, которые были затронуты изменениями.
