# Архитектура и масштабирование GitLab

## Определения

* **Omnibus GitLab** — официальный пакет (deb/rpm), содержащий GitLab и все его зависимости, управляемый утилитой `gitlab-ctl`. Рекомендуемый метод для self-hosted инсталляций.
* **Gitaly** — специализированный сервис Git RPC (Remote Procedure Call) для обеспечения доступа к репозиториям. Все операции с Git проходят через него.
* **Sidekiq** — фоновый обработчик задач на базе Ruby. Отвечает за асинхронные операции: отправку писем, обработку пайплайнов, создание архивов.
* **Praefect** — прокси-сервер и балансировщик для Gitaly, обеспечивающий HA (High Availability) Git-данных через кластеризацию. В современных Cloud Native архитектурах заменяется на нативный Gitaly Cluster (в процессе перехода).
* **GitLab Orbit** — графовая база данных контекста, связывающая код, пайплайны и деплои для глубокой аналитики и работы AI-агентов.
* **GitLab Geo** — решение для распределенных команд и обеспечения отказоустойчивости (DRP — Disaster Recovery Plan), позволяющее создавать зеркала инстанса GitLab в разных регионах.

## Основные концепции

### Компоненты системы

GitLab представляет собой комплекс сервисов, работающих совместно:

* **Nginx / Envoy Gateway:** Входная точка (Ingress). В Helm-чартах 19.x Envoy Gateway становится стандартом для управления трафиком.
* **GitLab Rails (Puma/Workhorse):** Основное приложение. Puma обрабатывает API и веб-запросы, Workhorse разгружает Puma от тяжелых запросов.
* **PostgreSQL:** Хранение метаданных. С версии 19.0 минимально поддерживаемая версия — **PostgreSQL 17**.
* **Redis / Valkey:** Хранилище сессий и очередей Sidekiq. Поддерживается переход на Valkey 7.2+.
* **ClickHouse:** (версия 19.x+) Используется для высокопроизводительной аналитики и хранения данных DORA-метрик.
* **Gitaly:** Доступ к файловой системе репозиториев. Поддерживает запуск в Kubernetes (StatefulSet) в шардированном режиме.
* **Registry:** Хранилище Docker-образов.
* **Object Storage:** Внешнее хранилище (S3/MinIO) для артефактов, LFS (Large File Storage), бэкапов. Обязателен для любых масштабируемых инсталляций.

### Механизм выполнения задач (CI/CD)

GitLab Server предоставляет очередь задач, которые забирают **GitLab Runners**. Раннеры общаются с сервером по HTTP/HTTPS (Pull-модель). Подробное описание архитектуры CI/CD — в [gitlab_ci_basics.md](./gitlab_ci_basics.md).

### Варианты развертывания

| Метод | Особенности | Рекомендация |
| :--- | :--- | :--- |
| **Omnibus (Package)** | Простая установка и обновление. Полный контроль над компонентами. | **Production (Single Node / Distributed)** |
| **Cloud Native Hybrid** | Rails/Sidekiq в Kubernetes, Gitaly Cluster и БД на виртуальных машинах. | **Enterprise HA / Large Scale** |
| **Helm Chart / Operator** | Полное развертывание в Kubernetes. Gitaly в K8s пока только в шардированном режиме. | **Cloud-native (Scaling focus)** |

### Управление через Omnibus

Основным инструментом управления является утилита `gitlab-ctl`. Все настройки хранятся в файле `/etc/gitlab/gitlab.rb`.

* **Применение изменений:** `sudo gitlab-ctl reconfigure`.
* **Проверка статуса:** `sudo gitlab-ctl status`.
* **Просмотр логов:** `sudo gitlab-ctl tail`.
* **Безопасность:** Файл `gitlab-secrets.json` обязателен для бэкапа, так как хранит ключи шифрования.

## Практические сценарии

### 1. Одноузловая архитектура (Single Node)

Все компоненты на одной виртуальной машине. Подходит для команд до 1000 пользователей.

* **Ресурсы:** Минимум 4 ядра / 8 ГБ RAM (рекомендуется 8/16 для активного использования CI).
* **Преимущества:** Максимально простая эксплуатация (`apt upgrade`).

### 2. Распределенная архитектура (Distributed Architecture)

Вынос нагруженных компонентов на отдельные серверы. Рекомендуется для 2000+ пользователей.

* **Gitaly:** Выносится первым при высокой нагрузке на Git-операции.
* **PostgreSQL / Redis / Valkey:** Изоляция нагрузки базы данных и кэша.
* **Object Storage (S3):** Переход на S3 обязателен для масштабирования Sidekiq и Rails.

### 3. Высокая доступность (High Availability) и кластеризация

Для организаций с 3000+ пользователей и критическими требованиями к аптайму.

* **Gitaly Cluster:** Минимум 3 ноды Gitaly под управлением Praefect для обеспечения отказоустойчивости данных.
* **Cloud Native Hybrid:** Использование Kubernetes для Stateless-частей (Rails, Sidekiq) в сочетании с внешними Managed-базами данных и Gitaly на VM.
* **Patroni / Consul:** Кластеризация PostgreSQL 17 для обеспечения высокой доступности.

## Дополнительная информация

### Использование Object Storage (S3)

Переход на S3 решает несколько критических задач:

1. **Независимость от дисков:** Позволяет горизонтально масштабировать Rails-ноды без использования NFS.
2. **Синхронизация Sidekiq:** Гарантирует доступность артефактов при обработке задач на разных серверах.
3. **Оптимизация БД:** Хранение метаданных и диффов в S3 снижает нагрузку на PostgreSQL.

### Опыт эксплуатации и рекомендации

* **Registry Separation:** Рекомендуется использовать внешний Container Registry (например, Harbor) или выносить встроенный Registry за пределы основного инстанса.
* **Gitaly на Kubernetes:** На текущий момент (19.x) Gitaly в K8s поддерживает только шардирование. Для полноценного HA с репликацией данных рекомендуется Gitaly Cluster на виртуальных машинах.
