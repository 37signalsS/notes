# Архитектура и масштабирование GitLab

## Определения

* **Omnibus GitLab** — официальный пакет (deb/rpm), содержащий GitLab и все его зависимости (PostgreSQL, Redis и другие), управляемый утилитой `gitlab-ctl`. Рекомендуемый метод для self-hosted инсталляций.
* **Gitaly** — специализированный сервис Git **RPC (Remote Procedure Call — удаленный вызов процедур)** для обеспечения доступа к репозиториям. Все операции с Git проходят через него.
* **Sidekiq** — фоновый обработчик задач на базе Ruby. Отвечает за асинхронные операции: отправку писем, обработку пайплайнов, создание архивов.
* **Praefect** — прокси-сервер и балансировщик для Gitaly, обеспечивающий **HA (High Availability — высокая доступность)** Git-данных через кластеризацию.
* **GitLab Geo** — решение для распределенных команд и обеспечения отказоустойчивости (**DRP — Disaster Recovery Plan — план аварийного восстановления**), позволяющее создавать зеркала инстанса GitLab в разных географических регионах.

## Основные концепции

### Компоненты системы

GitLab представляет собой комплекс сервисов, работающих совместно:

* **Nginx:** Входная точка (Ingress), отвечает за проксирование запросов и **SSL (Secure Sockets Layer — протокол защищенных сокетов)**.
* **GitLab Rails (Puma/Workhorse):** Основное приложение. Puma обрабатывает API и веб-запросы, Workhorse разгружает Puma от "тяжелых" запросов (Git HTTP, загрузка файлов).
* **PostgreSQL:** Хранение метаданных (пользователи, задачи, **Merge Request (MR — запрос на слияние)**, настройки).
* **Redis:** Хранилище сессий, очередей Sidekiq и кэша.
* **Gitaly:** Доступ к файловой системе репозиториев.
* **Registry:** Хранилище Docker-образов.
* **Monitoring:** Встроенные Prometheus и Grafana для самодиагностики.
* **Object Storage:** Внешнее хранилище (S3/MinIO) для артефактов, **LFS (Large File Storage — хранилище больших файлов)**, бэкапов и диффов Merge Request.

### Механизм выполнения задач (CI/CD)

GitLab Server предоставляет очередь задач, которые забирают **GitLab Runners**. Раннеры общаются с сервером по HTTP/HTTPS (Pull-модель). Подробное описание архитектуры CI/CD — в [gitlab_ci_basics.md](./gitlab_ci_basics.md).

### Варианты развертывания

| Метод | Особенности | Рекомендация |
| :--- | :--- | :--- |
| **Omnibus (Package)** | Простая установка и обновление одной командой. Самый стабильный метод. | **Production (Standard)** |
| **Docker** | Легко запустить, но сложно отлаживать и масштабировать. | **Testing / Homelab** |
| **Helm Chart / Operator** | Развертывание в Kubernetes. Подходит только для Stateless-частей. | **Cloud-native / Large scales** |

### Управление через Omnibus

Основным инструментом управления является утилита `gitlab-ctl`. Все настройки хранятся в файле `/etc/gitlab/gitlab.rb`.

* **Применение изменений:** `sudo gitlab-ctl reconfigure`.
* **Проверка статуса:** `sudo gitlab-ctl status`.
* **Просмотр логов:** `sudo gitlab-ctl tail`.
* **Безопасность:** Файл `gitlab-secrets.json` обязателен для бэкапа, так как хранит ключи шифрования базы данных.

## Практические сценарии

### 1. Одноузловая архитектура (Single Node)

Все компоненты на одной виртуальной машине. Подходит для команд до 1000 пользователей.

* **Ресурсы:** Минимум 4 ядра / 8 ГБ RAM (рекомендуется 8/16 для активного использования CI).
* **Преимущества:** Максимально простая эксплуатация (`apt upgrade`).

### 2. Распределенная архитектура (Distributed Architecture)

Вынос нагруженных компонентов на отдельные серверы. Рекомендуется для 2000–3000 пользователей.

* **Gitaly:** Выносится первым при высокой нагрузке на Git-операции.
* **PostgreSQL / Redis:** Изоляция нагрузки базы данных и кэша.
* **Object Storage (S3):** Переход с локальных дисков на S3 для хранения артефактов и LFS. Это критично для масштабирования Sidekiq.

### 3. Высокая доступность (High Availability) и кластеризация

Для организаций с 3000+ пользователей и критическими требованиями к аптайму.

* **Gitaly Cluster (Praefect):** Минимум 3 ноды Gitaly для отказоустойчивости данных.
* **Load Balancer:** Балансировка трафика между несколькими нодами GitLab Rails.
* **Patroni / Consul:** Кластеризация PostgreSQL для обеспечения высокой доступности.
* **Geo:** Репликация между регионами для минимизации задержек в распределенных командах.

## Дополнительная информация

### Использование Object Storage (S3)

Переход на S3 решает несколько критических задач:

1. **Независимость от дисков:** Упрощает горизонтальное масштабирование Rails-нод.
2. **Синхронизация Sidekiq:** При выносе Sidekiq на отдельные серверы S3 гарантирует доступность артефактов (решает проблему "невидимых" артефактов в Dynamic Child Pipelines).
3. **Оптимизация БД:** Хранение диффов MR в S3 существенно снижает нагрузку на PostgreSQL.

### Известные проблемы и опыт эксплуатации

* **Registry Separation:** Рекомендуется выносить Registry в отдельный высокодоступный сервис, чтобы обновление основного инстанса GitLab не прерывало `docker pull` в Kubernetes.
* **Backup Restore:** Восстановление большой Single Node инсталляции может занимать длительное время. Разделение на компоненты позволяет восстанавливать части системы независимо.
