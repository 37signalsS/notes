# Переменные и секреты GitLab CI/CD

## Определения

*   **Переменные CI/CD** — динамические значения, используемые для управления логикой пайплайна, конфигурацией окружений и передачи параметров между задачами.
*   **Защищенная переменная (`Protected`)** — доступна только в пайплайнах, запущенных для защищенных веток или тегов. Это основной механизм ограничения доступа к продуктовым секретам.
*   **Маскированная переменная (`Masked`)** — значение скрывается в логах выполнения заданий (заменяется на `[MASKED]`). С версии **18.3** этот атрибут применяется автоматически ко всем новым переменным. Требование: минимум 8 символов, отсутствие пробелов.
*   **Скрытая переменная (`Hidden`)** — значение полностью скрыто в интерфейсе GitLab и логах. После сохранения просмотр значения невозможен даже администраторам.
*   **Переменная типа `File`** — содержимое записывается во временный файл на Runner, а сама переменная хранит абсолютный путь к этому файлу. Используется для многострочных данных (SSH-ключи, сертификаты, конфигурации).
*   **GitLab Secrets Manager** — нативное решение для управления секретами (GA с версии **19.2**), обеспечивающее безопасное хранение, версионирование и инъекцию секретов без использования переменных окружения.
*   **OIDC (OpenID Connect)** — метод аутентификации пайплайна во внешних системах (HashiCorp Vault, AWS, GCP) с использованием краткосрочных токенов идентификации (`ID Tokens`) вместо статических паролей.

## Базовые концепции

### Иерархия и приоритет переменных (Precedence)

В GitLab 19.x действует строгий порядок приоритетов. Если переменная с одним именем определена в нескольких местах, выбирается значение из источника с наивысшим приоритетом (от 1 до 14):

1.  **Script-level variables**: Переменные, определенные внутри блока `script` (например, `export DB_NAME=test`).
2.  **Trigger variables**: Переменные, переданные через API при запуске пайплайна.
3.  **Manual variables**: Значения, введенные вручную в интерфейсе при запуске пайплайна (`Run pipeline`).
4.  **Pipeline execution policy variables**: Переменные, заданные в политиках безопасности/комплаенса на уровне группы или инстанса.
5.  **Scheduled variables**: Переменные запланированных запусков (Pipeline schedules).
6.  **Job-level variables**: Определенные внутри конкретной задачи в `.gitlab-ci.yml`.
7.  **Included variables**: Переменные из файлов, подключенных через `include`.
8.  **Global variables**: Определенные на верхнем уровне `.gitlab-ci.yml`.
9.  **Project variables**: Заданные в `Settings > CI/CD > Variables` проекта.
10. **Group variables**: Заданные на уровне группы. В случае вложенных групп приоритет имеет **ближайшая подгруппа**.
11. **Instance variables**: Заданные администратором в `Admin Area`.
12. **Dotenv variables**: Переменные, переданные из предыдущих задач через `artifacts:reports:dotenv`.
13. **Deployment variables**: Переменные, специфичные для конкретного окружения (`environment`).
14. **Predefined variables**: Системные переменные GitLab (`CI_COMMIT_SHA`, `CI_JOB_ID`). Имеют самый низкий приоритет.

### Безопасность и управление доступом

#### Защита CI_JOB_TOKEN (GitLab 18.0+)
По умолчанию доступ через `CI_JOB_TOKEN` ограничен белым списком (**Allowlist**). 
*   **Fine-grained Permissions (18.3+):** Возможность ограничивать область действия токена конкретными правами (например, только чтение Registry или только API) вместо полного наследования прав пользователя.
*   **Git Push (18.4+):** `CI_JOB_TOKEN` можно использовать для выполнения `git push` в репозиторий текущего проекта, что упрощает версионирование артефактов без PAT.

#### Расширение переменных (Expansion)
С версии **18.6** автоматическое расширение вложенных ссылок на переменные (`expand variable reference`) **отключено по умолчанию**. Это предотвращает атаки типа "инъекция переменных", если значение одной переменной содержит ссылки на другие.

#### OIDC и Secretless-подход
Для интеграции с внешними хранилищами рекомендуется использовать OIDC. Это позволяет Runner'у получать временный токен доступа от провайдера (например, Vault) на основе `CI_JOB_JWT` (или `ID Token`).

## Практические сценарии

### Сценарий 1: Работа с переменными типа File (SSH)

Использование для SSH-ключей. Переменная `SSH_KEY` настроена как `File` и `Protected`.

```yaml
deploy:
  stage: deploy
  script:
    - chmod 400 "$SSH_KEY"
    - ssh -i "$SSH_KEY" -o StrictHostKeyChecking=no user@remote-host "deploy.sh"
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

### Сценарий 2: Тонкая настройка прав CI_JOB_TOKEN

Ограничение прав токена для повышения безопасности пайплайна.

```yaml
publish_docs:
  stage: deploy
  permissions:
    contents: read
    pages: write
  script:
    - deploy_to_pages.sh --token "$CI_JOB_TOKEN"
```

### Сценарий 3: Интеграция с GitLab Secrets Manager

Нативное использование секретов без env-переменных (версия 19.2+).

```yaml
database_migration:
  stage: deploy
  secrets:
    DB_PASSWORD:
      vault: production/database/password  # Путь во встроенном хранилище
  script:
    - ./migrate.sh --password "$DB_PASSWORD"
```

### Сценарий 4: Аутентификация в Vault через OIDC (ID Tokens)

Безопасное получение секретов из внешнего Vault.

```yaml
get_vault_secrets:
  stage: .pre
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.example.com
  variables:
    VAULT_ADDR: "https://vault.example.com:8200"
  script:
    - export VAULT_TOKEN=$(vault write -field=token auth/jwt/login role=my-role jwt=$VAULT_ID_TOKEN)
    - vault kv get -field=apikey secret/my-service > apikey.txt
  artifacts:
    paths:
      - apikey.txt
```
