# Переменные и секреты GitLab CI/CD

## Определения

* **Переменные CI/CD** — динамические значения, используемые для управления логикой пайплайна, конфигурацией окружений и хранения конфиденциальных данных.
* **Защищенная переменная (`Protected`)** — доступна только в пайплайнах для защищенных веток или тегов. Критично для безопасности продуктовых сред.
* **Маскированная переменная (`Masked`)** — значение скрывается в логах выполнения заданий. С версии **18.3** этот атрибут применяется по умолчанию ко всем новым переменным.
* **Скрытая переменная (`Hidden`)** — значение полностью скрыто в интерфейсе GitLab и логах. Доступно только при создании; просмотр после сохранения невозможен.
* **Переменная типа `File`** — содержимое записывается во временный файл на Runner, а переменная хранит путь к нему. Подходит для многострочных данных (SSH-ключи, сертификаты).
* **Предопределенные переменные** — системные переменные, автоматически предоставляемые GitLab (например, `CI_COMMIT_SHA`).
* **GitLab Secrets Manager** — встроенное в GitLab (начиная с **19.0**) решение для управления секретами, заменяющее внешние системы типа HashiCorp Vault.

## Базовые концепции

### Типы и атрибуты переменных

Переменные настраиваются в `Settings > CI/CD > Variables` или описываются в `.gitlab-ci.yml`.

**Типы данных:**
* **Variable**: Обычная пара «ключ-значение», передаваемая как переменная окружения.
* **File**: Содержимое сохраняется в файл. Это единственный безопасный способ передачи многострочных секретов.

**Ключевые атрибуты:**
1. **Маскирование (`Masked`)**: Значение заменяется на `[MASKED]` в логах. Требование: минимум 8 символов, отсутствие пробелов.
2. **Защита (`Protected`)**: Ограничивает область видимости защищенными ветками. Предотвращает утечку секретов при попытке их прочитать из сторонних веток.
3. **Расширение переменных**: С версии **18.6** автоматическое расширение вложенных переменных (`expand variable reference`) отключено по умолчанию для повышения безопасности.

### Интеграция с GitLab Secrets Manager

С выходом **19.2 (GA)** встроенный менеджер секретов стал основным способом управления конфиденциальными данными.

* **Преимущества**: Нет необходимости в Secret-Zero (аутентификация происходит нативно), поддержка версионности секретов, централизованный аудит.
* **Использование**: Секреты подключаются в задании через ключевое слово `secrets`.

### Предопределенные переменные

GitLab автоматически внедряет переменные с префиксом `CI_` для предоставления контекста выполнения.

* **`CI_COMMIT_BRANCH`**: Имя ветки.
* **`CI_COMMIT_SHORT_SHA`**: Короткий хеш коммита (стандарт для тегирования образов).
* **`CI_REGISTRY_IMAGE`**: Путь к встроенному реестру контейнеров.
* **`CI_JOB_TOKEN`**: Временный токен для авторизации в рамках пайплайна (API, Registry).

## Практические сценарии

### Сценарий 1: Работа с переменными типа File

Использование для SSH-ключей или сертификатов CA.

**Настройка:** Переменная `SSH_PRIVATE_KEY` типа `File`, помеченная как `Protected`.

```yaml
deploy:
  stage: deploy
  script:
    - chmod 600 "$SSH_PRIVATE_KEY"
    - ssh -i "$SSH_PRIVATE_KEY" user@server "command"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

### Сценарий 2: Динамическое тегирование образов

Создание уникальных тегов для Docker-образов на основе контекста коммита.

```yaml
build:
  stage: build
  script:
    - |
      if [ -n "$CI_COMMIT_TAG" ]; then
        TAG="$CI_COMMIT_TAG"
      else
        TAG="$CI_COMMIT_REF_SLUG-$CI_COMMIT_SHORT_SHA"
      fi
    - docker build -t "$CI_REGISTRY_IMAGE:$TAG" .
    - docker push "$CI_REGISTRY_IMAGE:$TAG"
```

### Сценарий 3: Использование GitLab Secrets Manager

Пример подключения секрета без явного указания значений в переменных проекта.

```yaml
database_migration:
  stage: deploy
  secrets:
    DB_PASSWORD:
      vault: production/database/password  # Интеграция с нативным Secrets Manager
  script:
    - ./migrate.sh --password "$DB_PASSWORD"
```
