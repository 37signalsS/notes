### Определения

- **Переменные CI/CD** — это динамические значения, которые можно передавать в пайплайн GitLab CI/CD для управления его поведением, конфигурацией или для хранения чувствительных данных (секретов).
- **Защищенная переменная (`Protected`)** — переменная, доступная только в пайплайнах, запускаемых для защищенных веток или тегов. Используется для хранения секретов, связанных с production-средами.
- **Маскированная переменная (`Masked`)** — переменная, значение которой скрывается в логах выполнения задач. Для маскирования значение должно быть однострочным, без пробелов и длиной не менее 8 символов.
- **Переменная типа `File`** — переменная, содержимое которой GitLab Runner записывает во временный файл, а сама переменная хранит путь к этому файлу. Используется для многострочных секретов, таких как SSH-ключи.
- **Предопределенные переменные** — набор переменных, которые GitLab автоматически предоставляет в каждом пайплайне (`CI_COMMIT_BRANCH`, `CI_PROJECT_NAME` и т.д.).
- **Внешние хранилища секретов** — сторонние системы (например, HashiCorp Vault), используемые для безопасного централизованного хранения секретов.

### Основные концепции

#### Объявление и атрибуты переменных

Переменные определяются в настройках проекта (`Settings > CI/CD > Variables`) и могут иметь следующие характеристики:

- **Типы переменных:**
  - **`Variable`**: Стандартная пара "ключ-значение", передаваемая как переменная окружения.
  - **`File`**: Содержимое переменной сохраняется во временный файл на Runner'е, а в пайплайн передается путь к этому файлу. Идеально для сертификатов и ключей.

- **Атрибуты переменных:**
  - **`Protected`**: Ограничивает доступ к переменной только для пайплайнов в защищенных ветках или тегах.
  - **`Masked`**: Скрывает значение переменной в логах. Требует, чтобы значение было однострочным, без пробелов и длиной минимум 8 символов.

#### Предопределенные переменные GitLab CI

GitLab автоматически инжектирует множество предопределенных переменных, начинающихся с префикса `CI_`. Они предоставляют контекст о текущем пайплайне, коммите и проекте.

**Наиболее часто используемые:**

- `CI_COMMIT_BRANCH`: Имя текущей ветки.
- `CI_COMMIT_SHORT_SHA`: Короткий хеш (8 символов) текущего коммита.
- `CI_PROJECT_NAME`: Имя текущего проекта.
- `CI_PIPELINE_ID`: Уникальный идентификатор текущего пайплайна.
- `CI_JOB_TOKEN`: Временный токен для аутентификации при взаимодействии с GitLab API или Container Registry.

### Практические сценарии

#### Сценарий 1: Использование разных типов переменных

**Настройка переменных в `Settings > CI/CD > Variables`:**

1. `PROD_SERVER_IP` (Variable): `192.168.1.100`
2. `PROD_API_TOKEN` (Variable, Masked): `MySuperSecretApiTokenValue`
3. `PROD_SSH_KEY` (File, Protected): `-----BEGIN RSA PRIVATE KEY...`

**Задача в `.gitlab-ci.yml`:**

```yaml
deploy_production:
  stage: deploy
  script:
    - echo "Deploying to server $PROD_SERVER_IP"
    - echo "API Token is $PROD_API_TOKEN" # В логе будет [MASKED]
    - |
      # Настраиваем SSH-ключ из переменной типа File
      chmod 600 "$PROD_SSH_KEY"
      ssh -i "$PROD_SSH_KEY" user@"$PROD_SERVER_IP" "hostname"
  rules:
    - if: $CI_COMMIT_BRANCH == 'main' # 'main' является защищенной веткой
```

**Результат:**

- Задача запустится только для ветки `main`, так как `PROD_SSH_KEY` — защищенная переменная.
- В логах пайплайна вместо значения `PROD_API_TOKEN` будет отображаться `[MASKED]`.
- SSH-ключ будет безопасно использован для подключения к серверу.

#### Сценарий 2: Динамическое тегирование Docker-образа

Этот сценарий использует предопределенные переменные для создания уникального и информативного тега для Docker-образа.

```yaml
build_image:
  stage: build
  image: docker:20.10
  services:
    - docker:20.10-dind
  script:
    - |
      # Формируем тег из имени ветки и короткого хеша коммита
      if [ -n "$CI_COMMIT_TAG" ]; then
        TAG="$CI_COMMIT_TAG"
      else
        TAG="$CI_COMMIT_REF_SLUG-$CI_COMMIT_SHORT_SHA"
      fi
    - docker build -t "$CI_REGISTRY_IMAGE:$TAG" .
    - docker push "$CI_REGISTRY_IMAGE:$TAG"
```

**Результат:**

- Для ветки `feature/new-login` с коммитом `a1b2c3d4` будет создан тег `feature-new-login-a1b2c3d4`.
- Для Git-тега `v1.2.0` будет создан Docker-тег `v1.2.0`.

#### Сценарий 3: Расшифровка секретов с помощью `ansible-vault`

Этот метод позволяет хранить секреты в зашифрованном виде прямо в репозитории.

**Настройка:**

1. Создайте файл с секретами и зашифруйте его: `ansible-vault encrypt secrets.yml`.
2. В `Settings > CI/CD > Variables` добавьте переменную `VAULT_PASSWORD` со значением пароля от `ansible-vault`.

**Задача в `.gitlab-ci.yml`:**

```yaml
use_secrets:
  stage: test
  image: ansible/ansible:latest
  script:
    # 1. Расшифровываем файл с секретами "на лету"
    - ansible-vault view secrets.yml --vault-password-file <(echo "$VAULT_PASSWORD") > decrypted_secrets.txt
    # 2. Используем расшифрованные данные
    - grep "api_key" decrypted_secrets.txt
```

**Результат:**

- Секреты остаются зашифрованными в репозитории.
- Пароль для расшифровки надежно хранится в переменных GitLab CI.
- Расшифровка происходит только во время выполнения пайплайна в изолированной среде Runner'а.

#### Сценарий 4: Использование переменной типа `File` для CA-сертификата

При работе с внутренними сервисами (например, Docker-реестром Harbor), использующими TLS с сертификатами от собственного центра сертификации (CA), необходимо, чтобы клиенты в CI/CD-пайплайне доверяли этому CA.

**Настройка:**

1.  В `Settings > CI/CD > Variables` добавьте переменную `CUSTOM_CA_CERT` типа `File`.
2.  В значение переменной вставьте содержимое публичного ключа вашего CA (`ca.crt`).

**Задача в `.gitlab-ci.yml` (пример для Docker):**

```yaml
build_with_custom_ca:
  stage: build
  image: docker:20.10
  services:
    - docker:20.10-dind
  before_script:
    # Docker daemon (dind) и клиент Docker должны доверять вашему CA
    # $CUSTOM_CA_CERT содержит путь к временному файлу с сертификатом
    - mkdir -p /etc/docker/certs.d/harbor.your-domain.com
    - cp "$CUSTOM_CA_CERT" /etc/docker/certs.d/harbor.your-domain.com/ca.crt
    - docker login -u $HARBOR_USER -p $HARBOR_PASSWORD harbor.your-domain.com
  script:
    - docker build -t harbor.your-domain.com/my-project/my-image:latest .
    - docker push harbor.your-domain.com/my-project/my-image:latest
```

**Результат:**

- Переменная `CUSTOM_CA_CERT` типа `File` предоставляет безопасный и удобный способ передачи многострочного сертификата в пайплайн.
- Клиентские утилиты (`docker`, `curl`, `kaniko` и др.) могут быть настроены на использование этого сертификата для установления доверенных TLS-соединений.

### Дополнительная информация

- **Интеграция с HashiCorp Vault**: Для максимального уровня безопасности и централизации рекомендуется интегрировать GitLab CI с внешним хранилищем секретов, таким как HashiCorp Vault. Это позволяет динамически получать секреты с коротким сроком жизни, не храня их в GitLab. Подробное руководство доступно в документе [Интеграция GitLab CI с HashiCorp Vault](../Tutorials/vault_kubernetes_integration.md).
- **Полный список предопределенных переменных** доступен в [официальной документации GitLab](https://docs.gitlab.com/ee/ci/variables/predefined_variables.html).
