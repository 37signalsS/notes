# Основы GitLab CI/CD

## Определения

Иерархия компонентов в GitLab CI/CD строится по принципу "от общего к частному". Подробный глоссарий — в [pipeline_glossary.md](../../Core_Concepts/pipeline_glossary.md).

* **[Конвейер (Pipeline)](https://docs.gitlab.com/ci/pipelines/)**: Высокоуровневая структура, которая определяет полный цикл CI/CD. Состоит из этапов и запускается по различным событиям (коммит, Merge Request, расписание).
* **[Этап (Stage)](https://docs.gitlab.com/ci/yaml/stages/)**: Группирует задачи и определяет порядок их выполнения. Все задачи одного этапа выполняются параллельно, а сами этапы — последовательно.
* **[Задача (Job)](https://docs.gitlab.com/ci/jobs/)**: Минимальная единица работы. Выполняет определенный набор команд (скриптов) для сборки, тестирования или развертывания.
* **[Исполнитель (Runner)](https://docs.gitlab.com/runner/)**: Приложение, которое выполняет задачи (Jobs). Оно устанавливается на сервер или запускается в контейнере и постоянно опрашивает GitLab на предмет новых задач. Настройка — в [gitlab_ci_runners_executors.md](../Advanced/gitlab_ci_runners_executors.md).

## Базовые концепции

### Архитектура GitLab CI/CD

Для работы GitLab CI/CD необходимы три ключевых компонента:

1. **GitLab Server** — принимает код из репозитория, обнаруживает изменения (push, merge request, тег) и запускает пайплайн.
2. **GitLab Runner** — отдельный агент, который опрашивает GitLab на предмет задач и выполняет их. Runner может запускать задачи в различных окружениях:
   * **Docker Executor** — каждая задача выполняется в отдельном Docker-контейнере (наиболее распространённый вариант)
   * **Kubernetes Executor** — задачи запускаются в подах Kubernetes
   * **Shell Executor** — команды выполняются непосредственно на хост-машине (не рекомендуется для production из-за отсутствия изоляции)
   * **SSH Executor** — Runner подключается к удалённому серверу по SSH для деплоя
3. **`.gitlab-ci.yml`** — файл конфигурации в корне репозитория, описывающий пайплайн (стадии, задачи, переменные, условия запуска).

Дополнительно GitLab может включать встроенный **Container Registry** для хранения Docker-образов, собранных в пайплайне.

```
[Developer] --push--> [GitLab Server] --триггер--> [Pipeline]
                                                |
                                                v
                                          [GitLab Runner]
                                          |-- Docker Executor
                                          |-- Kubernetes Executor
                                          |-- Shell Executor
                                          |-- SSH Executor
```

Подробная информация о типах Runner'ов и Executor'ов — в [gitlab_ci_runners_executors.md](../Advanced/gitlab_ci_runners_executors.md). Установка self-hosted GitLab с Runner — в [self_hosted_installation.md](../Tutorials/self_hosted_installation.md).

### Файл `.gitlab-ci.yml`

Это YAML-файл в корне репозитория, который является единой точкой конфигурации для всего конвейера. GitLab автоматически обнаруживает его и выполняет описанные в нем инструкции.

> **Важно (GitLab 18.x):** Глобальные ключевые слова `before_script`, `after_script`, `image`, `cache` на верхнем уровне **deprecated**. Используйте [`default`](#структурные-ключевые-слова).

### Ключевые слова для управления пайплайном

#### Структурные ключевые слова

* **`stages`**: Определяет последовательность выполнения этапов. Следующий этап начнется только после успешного завершения всех задач предыдущего.
* **`image`**: Указывает Docker-образ по умолчанию для выполнения всех задач.
* **`variables`**: Определяет [переменные окружения](./gitlab_ci_variables_secrets.md), доступные внутри задач.
* **`default`**: Задает набор настроек по умолчанию, которые наследуются всеми задачами.

#### Ключевые слова для задач

* **`stage`**: Присваивает задачу определенному этапу из списка `stages`.
* **`script`**: Основной и обязательный блок. Содержит shell-команды, которые выполняет Runner.
* **`before_script` / `after_script`**: Команды, выполняемые до или после основного `script`. `after_script` выполняется даже при провале задачи.
* **`artifacts`**: Определяет файлы и директории, которые сохраняются после успешного выполнения задачи и могут быть переданы на следующие этапы. Подробнее см. **[Артефакты и кэш в GitLab CI](../Advanced/gitlab_ci_caching/cache_concepts.md)**.
* **`cache`**: Механизм сохранения файлов между запусками задач для ускорения сборок. Подробнее см. **[Артефакты и кэш в GitLab CI](../Advanced/gitlab_ci_caching/cache_concepts.md)**.
* **`needs`**: Создает направленную ациклическую графовую (DAG) зависимость между задачами, позволяя запускать их сразу после завершения зависимостей, не дожидаясь окончания всего этапа.
* **`dependencies`**: Определяет, какие артефакты из предыдущих задач нужно загрузить. По умолчанию загружаются артефакты всех предыдущих задач.

#### Управление потоком выполнения

* **`rules`**: Мощный механизм для определения условий, при которых задача будет (или не будет) добавлена в пайплайн. **Является заменой `only`/`except`** (deprecated в GitLab 18.x) и предпочтителен для использования. Поддерживает:
  * `rules:if` — условные выражения
  * `rules:changes` — изменения в файлах
  * `rules:exists` — существование файлов
  * `auto_cancel` (GitLab 16.8+) — автоотмена пайплайнов
* **`when`**: Указывает, когда запускать задачу. Например, `on_success` (по умолчанию), `on_failure`, `always` или `manual` (для ручного запуска). В контексте `workflow:rules` принимает только `always` или `never`.

### Взаимосвязь `needs` и `dependencies`

Эти два ключевых слова часто используются вместе, но решают разные задачи:

* **`needs`**: Управляет **порядком выполнения** задач, создавая DAG.
* **`dependencies`**: Управляет **передачей артефактов** между задачами.

Если задача использует `needs`, то `dependencies` по умолчанию устанавливается в `needs: [...]`. То есть, будут загружены артефакты только от тех задач, которые перечислены в `needs`. Чтобы не загружать артефакты вообще, используется `dependencies: []`.

### Механизмы переиспользования (DRY)

Для избежания дублирования кода GitLab CI предлагает несколько механизмов, таких как `extends`, `!reference` и `include`.

Подробное описание этих механизмов см. в статье: **[Создание переиспользуемых и композитных пайплайнов](../Reusable_Pipelines/overview.md)**. Продвинутые сценарии — в [gitlab_ci_advanced_workflow.md](../Advanced/gitlab_ci_advanced_workflow.md).

> **Новое в GitLab 18.x:**
>
> * **`include:cache`** (18.9, experiment) — кэширование удалённых файлов include с TTL
> * **`spec:include`** (18.9, GA) — включение внешних определений inputs
> * **`spec:inputs:rules`** (18.7, GA) — условные опции для входных параметров

## Практические сценарии

### Комплексный базовый пайплайн

Этот пример демонстрирует многие основные концепции GitLab CI в одном файле.

```yaml
# 1. Определение последовательности этапов
stages:
  - build
  - test
  - deploy

# 2. Глобальные переменные
variables:
  APP_ENV: production

# 3. Настройки по умолчанию для всех задач
default:
  image: python:3.12
  before_script:
    - pip install -r requirements.txt

# 4. Задача сборки
build_job:
  stage: build
  script:
    - python -m build
  artifacts:
    # Сохраняем собранные файлы на 1 неделю
    paths:
      - dist/
    expire_in: 1 week

# 5. Задача тестирования
test_job:
  stage: test
  # `needs` создает зависимость от `build_job`, позволяя `test_job` начаться 
  # сразу после `build_job`, не дожидаясь завершения всей стадии `build`.
  # `dependencies` автоматически наследует значение `needs`, поэтому артефакты 
  # из `build_job` будут загружены.
  needs: ["build_job"]
  script:
    - pytest -q

# 6. Задача развертывания
deploy_job:
  stage: deploy
  environment:
    name: production
    url: https://app.example.com
  # Эта задача зависит от `test_job`, но ей не нужны артефакты.
  # `needs: ["test_job"]` для порядка выполнения.
  # `dependencies: []` чтобы не скачивать артефакты.
  needs: ["test_job"]
  dependencies: []
  script:
    - ./scripts/deploy.sh $CI_COMMIT_SHORT_SHA
  # Правило: задача доступна только для ветки 'main' и запускается вручную.
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: manual
```

### Разбор примера

1. **`stages`**: Определяет три последовательных этапа: `build`, `test`, `deploy`.
2. **`default`**: Указывает, что все задачи по умолчанию будут использовать образ `python:3.12` и выполнять `pip install`.
3. **`build_job`**: Находится на этапе `build`, выполняет сборку и сохраняет директорию `dist/` как **артефакт**.
4. **`test_job`**: Зависит от `build_job` (`needs`), что позволяет ей запуститься раньше. Она автоматически загружает артефакты из `build_job`.
5. **`deploy_job`**: Зависит от `test_job`. `dependencies: []` используется для оптимизации, так как для развертывания не требуются артефакты из предыдущих задач.
6. **`rules`**: Задача `deploy_job` будет создана только для ветки `main` и потребует ручного запуска через UI.

## Дополнительная информация

* **CI Lint Tool**: Для проверки синтаксиса `.gitlab-ci.yml` перед коммитом используйте встроенный валидатор. Он находится в UI GitLab в разделе `CI/CD` -> `Editor`. Это незаменимый инструмент для отладки, так как он показывает полностью "развернутую" конфигурацию со всеми `include`.

* **Полный справочник ключевых слов**: Детальное описание всех доступных ключевых слов и их опций можно найти в [официальной документации GitLab](https://docs.gitlab.com/ci/yaml/).

* **Стратегия ветвления**: О стратегии ветвления GitLab Flow для эффективной разработки — в [gitlab_flow.md](../Tutorials/gitlab_flow.md).

> **Критичные изменения GitLab 18.x:**
>
> * **18.3**: Переменные по умолчанию маскируются (`Masked` вместо `Visible`)
> * **18.4**: `environment:kubernetes:namespace` deprecated → используйте `environment:kubernetes:dashboard:namespace`
> * **18.6**: `expand variable reference` отключён по умолчанию
> * **18.9**: `include:cache` (experiment) для кэширования remote includes
