# Анти-паттерны GitLab CI/CD

**Актуально для:** GitLab 17.x–19.x

## Определения

* **Анти-паттерн GitLab CI/CD** — специфичная для экосистемы GitLab ошибка или неэффективный подход, который выглядит как рабочее решение, но приводит к проблемам в production.
* **Pipeline sprawl** — неконтролируемый рост количества пайплайнов и задач без стандартизации.
* **YAML duplication** — дублирование конфигурации между проектами без переиспользования.
* **Secret sprawl** — распределение секретов по множеству переменных проекта/группы без централизованного управления.
* **Runner sprawl** — неконтролируемый рост Runner'ов без политик lifecycle.
* **Monolithic pipeline** — пайплайн, пытающийся сделать всё в одном месте без разделения на компоненты.

## Основные концепции

### Классификация анти-паттернов

| Категория | Влияние | Критичность |
|:---|:---|:---|
| **Безопасность** | Утечка секретов, компрометация registry | Критичная |
| **Производительность** | Медленные пайплайны, высокие затраты | Высокая |
| **Надёжность** | Нестабильные деплои, казуичные откаты | Высокая |
| **Сопровождение** | Технический долг, зависимость от ключевых сотрудников | Средняя |
| **Compliance** | Нарушение аудита, отсутствие traceability | Высокая |

### Связь с метриками DORA и надёжностью

Анти-паттерны в GitLab CI/CD напрямую влияют на четыре ключевых показателя эффективности поставки (DORA):
- **Deployment Frequency** снижается при отсутствии `interruptible` и ручных действих в пайплайне.
- **Lead Time for Changes** растёт при дублировании YAML и монолитном пайплайне.
- **Mean Time to Recovery (MTTR)** увеличивается при отсутствии автоматического отката, health-гейтов и секретов в логах.
- **Change Failure Rate** повышается при использовании `latest` тегов, пересборке артефактов для разных сред и нестабильных тестах.

## Практические сценарии

### 1. Хранение секретов в переменных окружения

- **Описание:** Использование `CI/CD Variables` для всех секретов без централизованного управления.
- **Влияние на SRE:** Утечка секретов через логи, сложность ротации, отсутствие аудита — повышает риск инцидентов и замедляет MTTR при компрометации.
- **Решение:** Использование **GitLab Secrets Manager** (19.2+) или **Vault** с OIDC. Минимизация переменных в UI GitLab.
- **Признаки:**
  - Более 50 переменных в Settings → CI/CD
  - Секреты передаются через `export` в `script`
  - Отсутствие ротации ключей

### 2. Использование `only`/`except` вместо `rules`

- **Описание:** Использование устаревших ключевых слов `only`/`except` для управления запуском.
- **Влияние на SRE:** Ограниченная гибкость, невозможность комбинировать условия, устаревание — усложняет поддержку пайплайнов при изменении процессов поставки.
- **Решение:** Миграция на `rules` с поддержкой сложных условий и `when:manual`.
- **Признаки:**
  ```yaml
  # Устаревший синтаксис
  deploy:
    only:
      - main
    except:
      - tags
  ```

### 3. Дублирование YAML между проектами

- **Описание:** Копирование пайплайнов из одного проекта в другой без переиспользования.
- **Влияние на SRE:** Технический долг, рассинхронизация изменений, сложность обновлений — снижает надёжность и скорость внедрения исправлений безопасности.
- **Решение:** Использование **CI/CD Components**, `include:project`, `include:remote`.
- **Признаки:**
  - Одинаковые блоки `before_script` в 5+ проектах
  - Изменение требует правки в десятках файлов
  - Разные версии "одинаковых" пайплайнов

### 4. Отсутствие `timeout` у длительных задач

- **Описание:** Задачи без явного таймаута, зависающие на неопределённое время.
- **Влияние на SRE:** Засорение Runner'ов, невозможность откапаться, накопление очереди — увеличивает время простоя CI-инфраструктуры и блокирует поставку.
- **Решение:** Установка `timeout` на уровне job и global `default:timeout`.
- **Признаки:**
  - Задачи висят в `running` состоянии часами
  - Runner exhausted без очевидных причин

### 5. Неправильное использование `cache`

- **Описание:** Использование `cache` для артефактов, которые должны передаваться между стадиями, или наоборот.
- **Последствия:** Кэш не гарантирует целостность, артефакты недоступны для скачивания.
- **Решение:** `cache` для зависимостей (`node_modules`, `.m2`), `artifacts` для результатов сборки.
- **Признаки:**
  ```yaml
  # Неправильно: cache для артефактов сборки
  build:
    cache:
      paths:
        - build/

  # Правильно: artifacts для передачи между стадиями
  build:
    artifacts:
      paths:
        - build/
  ```

### 6. Отсутствие `interruptible` для долгих пайплайнов

- **Описание:** Долгие задачи без `interruptible: true`, блокирующие очередь при перезапуске.
- **Влияние на SRE:** Ресурсы Runner'ов тратятся на устаревшие запуски — снижает пропускную способность CI и увеличивает queue time.
- **Решение:** `interruptible: true` для lint/test, `interruptible: false` для deploy/migration.
- **Признаки:**
  - При новом push старый пайплайн продолжает выполняться
  - Очередь задач растёт при активной разработке

### 7. Секреты в логах (Expansion injection)

- **Описание:** Переменные с `$` в значении раскрываются GitLab как ссылки на другие переменные.
- **Влияние на SRE:** Утечка секретов в логи, ошибки разбора — повышает риск компрометации и усложняет расследование инцидентов.
- **Решение:** Использование `raw: true` для переменных, содержащих `$`.
- **Признаки:**
  ```yaml
  # Опасно: $DB_PASSWORD раскроется если есть переменная DB_PASSWORD
  variables:
    CONNECTION_STRING: "jdbc:mysql://host/db?password=$DB_PASSWORD"

  # Безопасно: raw отключает раскрытие
  variables:
    CONNECTION_STRING:
      value: "jdbc:mysql://host/db?password=$DB_PASSWORD"
      options:
        raw: true
  ```

### 8. Нарушение иерархии переменных

- **Описание:** Непонимание приоритета переменных, попытка переопределить переменную на неправильном уровне.
- **Влияние на SRE:** Непредсказуемое поведение пайплайна, сложный debugging — усложняет расследование инцидентов и восстановление сервиса.
- **Решение:** Использование `spec:inputs` для явных контрактов, документирование иерархии.
- **Признаки:**
  - Переменная проекта игнорируется, хотя задана в UI
  - Две переменные с одинаковым именем на разных уровнях

### 9. Использование `latest` тегов в production

- **Описание:** Использование `:latest` тега для Docker-образов в production пайплайнах.
- **Влияние на SRE:** Непредсказуемые деплои, расхождение между staging и prod — повышает Change Failure Rate и увеличивает MTTR при сбоях.
- **Решение:** Использование immutable тегов (SHA, SemVer).
- **Признаки:**
  ```yaml
  # Опасно
  image: python:latest

  # Безопасно
  image: python:3.12.4-slim
  ```

### 10. Отсутствие GitLab Runner TLS

- **Описание:** Регистрация Runner'а без TLS-верификации (`--tls-ca-file`).
- **Влияние на SRE:** Возможность MITM-атаки при опросе Runner'ом GitLab API — компрометация CI-инфраструктуры ведёт к компрометации всех пайплайнов.
- **Решение:** Всегда используйте TLS для связи Runner ↔ GitLab.
- **Признаки:**
  ```bash
  # Опасно: отключение TLS
  gitlab-runner register --tls-ca-file "" ...

  # Безопасно: верификация сертификата
  gitlab-runner register --tls-ca-file /path/to/ca.pem ...
  ```

### 11. Неограниченный рост артефактов

- **Описание:** Отсутствие `expire_in` и retention policies для артефактов.
- **Влияние на SRE:** Заполнение storage, высокие затраты на хранение — влияет на надёжность CI и увеличивает операционные затраты.
- **Решение:** Установка `expire_in` на уровне job и project.
- **Признаки:**
  - Артефакты старше 90 дней в проекте
  - Storage usage растёт без видимой причины

### 12. Дублирование runners без tagging strategy

- **Описание:** Создание Runner'ов без тегов или с overlapping тегами.
- **Влияние на SRE:** Задачи случайно назначаются неправильным Runner'ам, конфликты — снижает стабильность CI и увеличивает время отладки.
- **Решение:** Чёткая стратегия тегирования: `docker-linux`, `kubernetes`, `windows`, `macos`.
- **Признаки:**
  - Один Runner имеет тег `docker`, другой тоже `docker`
  - Задачи "прыгают" между Runner'ами

## Устранение неполадок (Troubleshooting)

| Симптом | Вероятный анти-паттерн | Действие |
| :--- | :--- | :--- |
| Пайплайн зелёный, но прод сломан | #9 `latest` теги / #5 неправильный cache | Использовать immutable tags; перейти на artifacts для передачи между стадиями |
| Секрет утёк в логи | #7 Expansion injection / #1 secret sprawl | Добавить `raw: true`; ротировать секреты; перенести в Vault |
| Задачи зависают часами | #4 отсутствие timeout | Установить `timeout` на уровне job и `default:timeout` |
| Раннеры перегружены без причины | #6 отсутствие interruptible / #11 артефакты | Включить `interruptible: true` для lint/test; настроить `expire_in` |
| Дублирование кода между проектами | #3 YAML duplication | Перейти на CI/CD Components с фиксированными версиями |
| Деплой нестабилен, откаты частые | #9 `latest` / #2 устаревший синтаксис | Использовать immutable tags; мигрировать на `rules` |
| TLS ошибки при регистрации раннера | #10 отсутствие TLS | Указать `--tls-ca-file`; проверить срок действия сертификата |
| Переменная игнорируется | #8 иерархия переменных | Документировать уровни; использовать `spec:inputs` |
| Задачи назначаются не тому раннеру | #12 дублирование runners | Убрать overlapping теги; завести tagging strategy |
| Очередь задач растёт | #6 interruptible / #4 timeout | Включить `interruptible`; установить timeout |
| Изменения в одном проекте ломают другие | #3 YAML duplication | Внедрить shared components; добавить contract tests |
| Папка с артефактами растёт | #11 нет `expire_in` | Установить `expire_in`; настроить retention policies |

## Лучшие практики и очистка (Best Practices & Cleanup)

1. **Единый источник истины для секретов:** все секреты — в Vault или GitLab Secrets Manager; переменные UI — только для нечувствительных данных.
2. **Версионирование шаблонов:** CI/CD Components привязывать через тег версии (`ref: v1.2.0`), а не `main`, чтобы избежать неожиданных изменений.
3. **Обязательные гейты:** `timeout` для всех jobs, `interruptible` для длинных задач, `expire_in` для артефактов.
4. **Наименьшие привилегии:** Runner'ы — с минимально необходимыми правами; OIDC-роли — с scoped политиками.
5. **Визуализация пайплайнов:** использовать DAG-режим (`needs`) для сокращения общего времени и понимания зависимостей.
6. **Аудит и compliance:** retention для логов, артефактов и кэшей; traceability через `CI_PIPELINE_ID` и `CI_JOB_ID`.
7. **Регулярный аудит:** раз в квартал проверять пайплайны на предмет анти-паттернов с помощью чек-листа.
8. **Очистка Runner'ов:** настроить lifecycle policies для эфемерных раннеров; удалять неиспользуемые контейнеры и кэш.
9. **Карантин нестабильных задач:** задачи с частыми таймаутами выделять в отдельный stage с `interruptible: false` и алертингом.
10. **Документирование tagging strategy:** хранить документацию по тегам Runner'ов в репозитории с примером `.gitlab-ci.yml`.

## Ограничения и крайние случаи

- **Legacy GitLab (<17.0):** `spec:inputs` и `raw: true` для переменных доступны только в GitLab 16.7+; для более старых версий требуется ручное управление иерархией и экранирование.
- **Self-hosted Runner'ы без внешнего доступа:** TLS между Runner и GitLab требует валидного сертификата; в air-gapped средах используется внутренний CA.
- **Монопольные Runner'ы:** на одном Runner'е с overlapping тегами могут выполняться задачи из разных проектов с разными требованиями к изоляции — требуется careful capacity planning.
- **Большие монореpos:** дублирование YAML (#3) и монолитный пайплайн (#8) проявляются особенно остро из-за размера кодовой базы; инкрементальные сборки и DAG-пайплайны становятся обязательными.
- **Multi-tenancy / shared runners:** secret sprawl (#1) и overlapping tags (#12) в мультитенантных окружениях могут привести к утечке данных между проектами; namespace-изоляция и scoped политики обязательны.
- **Высокая нагрузка на CI:** при >500 параллельных jobs требуется отдельный кластер Runner'ов с автоскейлингом; отсутствие `timeout` и `interruptible` становится критичным.

### Чек-лист аудита GitLab CI

- [ ] Все секреты хранятся в Vault или GitLab Secrets Manager
- [ ] Используется `rules` вместо `only`/`except`
- [ ] Все задачи имеют `timeout`
- [ ] Артефакты имеют `expire_in`
- [ ] Используются immutable image tags
- [ ] Runner'ы имеют теги и политики lifecycle
- [ ] Настроен `interruptible` для длинных задач
- [ ] Переменные с `$` имеют `raw: true`
- [ ] TLS включён для Runner ↔ GitLab communication
- [ ] Используются CI/CD Components вместо дублирования YAML
