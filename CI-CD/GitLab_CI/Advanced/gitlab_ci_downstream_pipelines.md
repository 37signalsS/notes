### Дочерние и мультипроектные пайплайны (Downstream Pipelines)

GitLab CI позволяет одному пайплайну запускать другие, что открывает возможности для сложных и модульных workflow, особенно при необходимости разделить логику или управлять зависимостями.

#### Способы запуска и сценарии использования

1.  **Мультипроектные пайплайны (`trigger:project`)**:
    Пайплайн в одном проекте (upstream/родительский) может запустить пайплайн в другом проекте (downstream/дочерний). Это особенно полезно для:
    *   **Управления зависимостями между микросервисами:** Например, успешная сборка и публикация артефактов библиотеки может автоматически запустить пересборку и тестирование зависимых от нее микросервисов.
    *   **Разделения обязанностей и безопасности:** Если у вас есть конфиденциальная логика (например, деплой в продакшн, сканирование безопасности), вы можете вынести ее в отдельный проект с ограниченным доступом. Родительский пайплайн лишь "триггерит" этот защищенный пайплайн, не имея прямого доступа к его секретам или логике.
    *   **Централизации шаблонов и инфраструктуры:** Общие пайплайны для сборки или деплоя могут находиться в центральном репозитории, а проекты лишь вызывают их.

2.  **Дочерние пайплайны (`trigger:include`)**:
    Пайплайн может запускать дочерний пайплайн в том же проекте. Это используется для:
    *   **Динамической генерации конфигурации "на лету":** Основной `.gitlab-ci.yml` может содержать логику для генерации другого YAML-файла, который затем используется как конфигурация дочернего пайплайна. Это идеально подходит для монорепозиториев, где нужно запускать разные наборы тестов или сборок в зависимости от измененных файлов (см. "Динамическая генерация пайплайнов").
    *   **Декомпозиции сложного `.gitlab-ci.yml`:** Разбивка одного большого файла на несколько логических частей, которые запускаются последовательно или параллельно, улучшая читаемость и управляемость.
    *   **Монорепозитории:** Запуск CI/CD только для тех частей монорепозитория, которые были затронуты изменениями.

#### Ожидание завершения (`strategy: depend`)

По умолчанию, родительская задача завершается успешно сразу после *запуска* дочернего пайплайна, не дожидаясь его результата. Чтобы дождаться завершения дочернего пайплайна и получить его статус (успех/неудача) в родительском, необходимо использовать `strategy: depend`. Это критически важно для построения надежных цепочек зависимостей.

#### Наследование переменных (Variable Inheritance)

Контекст переменных и их доступность существенно различаются между дочерними и мультипроектными пайплайнами. Понимание этих различий важно для правильного построения CI/CD.

*   **Дочерние пайплайны (Child Pipelines)**:
    *   Дочерний пайплайн **наследует все предопределенные переменные GitLab CI** (например, `CI_COMMIT_SHA`, `CI_COMMIT_REF_NAME`).
    *   Также наследуются **все пользовательские переменные**, определенные на уровне проекта, группы или в родительском `.gitlab-ci.yml`.
    *   Переменные, определенные в запускающей задаче родительского пайплайна (внутри `variables:` блока этой задачи), также передаются дочернему пайплайну.

*   **Мультипроектные пайплайны (Multi-project Pipelines)**:
    *   Дочерний пайплайн **НЕ наследует пользовательские переменные** из родительского пайплайна или из настроек проекта/группы родительского проекта.
    *   Он наследует **только предопределенные переменные GitLab CI**, относящиеся к собственному проекту (например, `CI_PROJECT_PATH` дочернего проекта, а не родительского).
    *   Для передачи пользовательских переменных в мультипроектный пайплайн их необходимо **явно указать** в блоке `variables:` триггерной задачи в родительском пайплайне.

**Пример: передача переменных в мультипроектный пайплайн**

```yaml
# .gitlab-ci.yml в родительском проекте
trigger_downstream_build:
  stage: deploy
  trigger:
    project: 'my-group/my-downstream-project'
    branch: main
    strategy: depend
  variables:
    UPSTREAM_PIPELINE_ID: $CI_PIPELINE_ID # Явная передача переменной
    CUSTOM_MESSAGE: "Hello from upstream!"
```

В дочернем пайплайне `my-downstream-project` будут доступны `UPSTREAM_PIPELINE_ID` и `CUSTOM_MESSAGE`.

#### Пример: мультипроектный пайплайн

**Проект A (запускающий): `.gitlab-ci.yml`**
```yaml
trigger_downstream_build:
  stage: deploy
  trigger:
    project: 'my-group/my-downstream-project' # Путь к дочернему проекту
    branch: main
    strategy: depend # Ждем завершения дочернего пайплайна
```

#### Динамическая генерация пайплайнов

Динамическая генерация пайплайнов — это мощный паттерн, который позволяет создавать конфигурацию `.gitlab-ci.yml` "на лету" с помощью скриптов. Это особенно полезно в случаях, когда:

*   **Сложная логика выбора заданий:** Например, в монорепозитории, где необходимо запускать только те тесты или сборки, которые относятся к измененным подпроектам.
*   **Гибкое масштабирование:** Генерация множества однотипных заданий (например, для разных окружений, версий или операционных систем) без дублирования кода.
*   **Конфигурация на основе данных:** Когда структура пайплайна зависит от внешних данных или файлов конфигурации проекта.

**Принцип работы:**

1.  Один из первых шагов пайплайна запускает скрипт (на Python, Bash, Node.js и т.д.).
2.  Этот скрипт анализирует необходимые условия (например, измененные файлы, переменные окружения).
3.  На основе анализа скрипт генерирует валидный YAML-файл, который содержит часть или всю конфигурацию CI/CD.
4.  Сгенерированный YAML-файл сохраняется как артефакт.
5.  Дочерний пайплайн запускается с использованием этого сгенерированного артефакта через `trigger:include:artifact`.

**Пример с использованием Python и Jinja2:**

Предположим, у нас есть Python-скрипт `generate_pipeline.py`, который использует шаблон Jinja2 для создания заданий.

**1. `pipeline_template.j2` (Шаблон Jinja2 для генерации YAML):**

```jinja
# generated_pipeline.yml
{% for i in range(num_jobs) %}
job_{{ i }}:
  stage: build
  script:
    - echo "Running job {{ i }} with custom logic"
    - echo "This is a dynamically generated job."
  tags:
    - shell
{% endfor %}
```

**2. `generate_pipeline.py` (Python-скрипт для рендеринга шаблона):**

```python
from jinja2 import Template
import os

num_jobs = int(os.environ.get("NUM_GENERATED_JOBS", 3))

template_content = """
# generated_pipeline.yml
{% for i in range(num_jobs) %}
job_{{ i }}:
  stage: build
  script:
    - echo "Running job {{ i }} with custom logic"
    - echo "This is a dynamically generated job."
  tags:
    - shell
{% endfor %}
"""

template = Template(template_content)
generated_yaml = template.render(num_jobs=num_jobs)

with open("generated-ci-config.yml", "w") as f:
    f.write(generated_yaml)

print(f"Generated {num_jobs} jobs in generated-ci-config.yml")
```

**3. `.gitlab-ci.yml` (родительский пайплайн):**

```yaml
stages:
  - generate
  - build

generate-dynamic-config:
  stage: generate
  image: python:3.9-slim
  variables:
    NUM_GENERATED_JOBS: 5 # Пример: генерируем 5 заданий
  script:
    - pip install Jinja2
    - python generate_pipeline.py
  artifacts:
    paths:
      - generated-ci-config.yml # Важно: сгенерированный файл должен быть артефактом

run-generated-pipeline:
  stage: build
  trigger:
    include:
      - artifact: generated-ci-config.yml
        job: generate-dynamic-config # Ссылка на задание, которое сгенерировало артефакт
    strategy: depend
```

Этот подход позволяет создавать чрезвычайно гибкие и эффективные пайплайны, адаптирующиеся к изменяющимся условиям проекта. GitLab CLI Lint также будет полезен для отладки сгенерированных конфигураций, отображая их полностью развернутое представление.
