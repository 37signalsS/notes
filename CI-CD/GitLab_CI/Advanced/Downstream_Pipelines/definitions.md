# Определения Downstream-пайплайнов

## Определения

**Downstream pipeline** — любой пайплайн GitLab CI/CD, запущенный другим пайплайном (upstream). Он выполняется как независимая сущность, но сохраняет логическую связь с вызвавшим его процессом.

**Upstream pipeline** — родительский пайплайн, содержащий задание с ключевым словом `trigger`, которое инициирует запуск downstream-пайплайна.

## Основные концепции

### Типы downstream-пайплайнов

| Тип | Описание | Лимиты вложенности |
| :--- | :--- | :--- |
| **[Parent-child pipeline](./parent_child_pipelines.md)** | Запускается в том же проекте, на том же ref и commit SHA. | Макс. 2 уровня (Parent → Child → Grandchild) |
| **[Multi-project pipeline](./multi_project_pipelines.md)** | Запускается в другом проекте. | 2 уровня (через `trigger`), не ограничено (через API) |

### Механизмы передачи данных

С выходом **GitLab 17.7+** подходы к передаче данных в downstream-пайплайны разделились на современные (типизированные) и традиционные:

1. **Pipeline Inputs (Рекомендуется):** Использование блока `spec:inputs` для передачи строго типизированных параметров (string, number, boolean). Это обеспечивает валидацию данных до старта пайплайна.
2. **CI/CD Variables:** Передача переменных через секцию `variables`. Для управления наследованием используется ключевое слово `forward`.
3. **Trigger:forward:** Позволяет явно указать, какие типы переменных передавать:
    - `yaml_variables`: переменные, описанные в `.gitlab-ci.yml`.
    - `pipeline_variables`: переменные, переданные при ручном запуске или через API.

### Динамическая генерация

**Динамическая генерация пайплайнов** — паттерн, при котором основной пайплайн создаёт YAML-конфигурацию во время выполнения (например, через скрипт на Python) и запускает её как дочерний пайплайн через `trigger:include:artifact`. Подробнее: [Динамическая генерация](./dynamic_generation.md).

## Практические сценарии

### Использование Pipeline Inputs (современный подход)

Этот метод заменяет использование переменных для передачи параметров, обеспечивая валидацию.

```yaml
# Родительский .gitlab-ci.yml
trigger-child:
  stage: test
  trigger:
    include:
      - local: path/to/child.yml
        inputs:
          stage_name: "production"
          run_security_scans: true
```

### Управление наследованием переменных (trigger:forward)

Используется, когда нужно ограничить поток переменных в дочерний проект.

```yaml
# Родительский .gitlab-ci.yml
trigger-multi-project:
  stage: deploy
  variables:
    LOCAL_VAR: "secret"
  trigger:
    project: 'group/downstream-project'
    forward:
      yaml_variables: false     # LOCAL_VAR не будет передан
      pipeline_variables: true  # Переменные из API/UI будут переданы
```

## Дополнительная информация

### Технические лимиты

- **Размер иерархии:** Одна цепочка триггеров (дерево всех связанных пайплайнов) ограничена **1000** downstream-пайплайнами. При превышении возникает ошибка `downstream pipeline tree is too large`.
- **Глубина вложенности (Nesting):** При использовании ключевого слова `trigger` лимит составляет **2 уровня**. Для обхода этого лимита в специфических сценариях можно использовать прямой вызов GitLab API через `curl` в секции `script`.
- **Rate Limits:** Существуют ограничения на количество создаваемых downstream-пайплайнов в минуту для предотвращения DDoS-атак на инфраструктуру GitLab Runner.

### Сценарии использования

- **Микросервисная архитектура:** запуск тестов зависимых сервисов при изменении общего контракта API.
- **Монорепозитории:** запуск CI только для тех модулей, в которых произошли изменения.
- **Разделение прав доступа:** вынос этапа деплоя в отдельный защищённый проект, к которому имеют доступ только администраторы.
- **Оптимизация .gitlab-ci.yml:** декомпозиция огромных файлов конфигурации на мелкие, логически завершённые части.
