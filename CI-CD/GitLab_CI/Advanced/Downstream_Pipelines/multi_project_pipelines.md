# Multi-project пайплайны

## Определения

**Multi-project pipeline (Межпроектный пайплайн)** — downstream-пайплайн, запускаемый в другом проекте GitLab. Используется для координации процессов CI/CD и управления зависимостями между различными репозиториями.

## Основные концепции

### Ключевые характеристики

- **Инициация:** запускается из пайплайна стороннего проекта через триггер.
- **Гибкость:** upstream-пайплайн может указывать конкретную ветку (`ref`) дочернего проекта и передавать необходимые переменные.
- **Видимость:** отображается в списке пайплайнов целевого (downstream) проекта.
- **Вложенность:** не имеет технических ограничений на уровни вложенности, в отличие от [parent-child](./parent_child_pipelines.md).
- **Контекст:** выполняется в контексте и с настройками целевого проекта.

### Безопасность и права доступа

Для обеспечения безопасности (права доступа, Deploy Tokens, конфиденциальность проектов) следуйте **[лучшим практикам](./best_practices.md)**.

### Наследование переменных

Передача данных в multi-project пайплайны имеет специфические ограничения: переменные проекта/группы и маскированные переменные не наследуются автоматически. Подробные правила описаны в документе **[Наследование переменных](./variable_inheritance.md)**.

## Практические сценарии

### Передача параметров между проектами

Пример передачи уникальных идентификаторов сборки в дочерний проект.

```yaml
trigger_downstream_build:
  stage: deploy
  trigger:
    project: 'my-group/my-downstream-project'
    branch: main
    strategy: depend
  variables:
    UPSTREAM_PIPELINE_ID: $CI_PIPELINE_ID
    CUSTOM_MESSAGE: "Запуск из родительского пайплайна"
```

### Синхронизация статусов выполнения

Использование `strategy: depend` позволяет родительской задаче ожидать завершения дочернего пайплайна. Подробнее: [Стратегии выполнения](./strategies.md).

```yaml
trigger_downstream:
  stage: deploy
  trigger:
    project: 'my-group/my-downstream-project'
    branch: main
    strategy: depend
```

## Дополнительная информация

### Варианты использования

- Координация деплоя микросервисной архитектуры.
- Разделение зон ответственности (например, отделение кода приложения от инфраструктурных скриптов).
- Централизованное управление CI/CD шаблонами.
- Реализация сложных цепочек поставок в мультирепозиторных средах.
