# Межпроектные пайплайны (Multi-project Pipelines)

## Определения

**Межпроектный пайплайн (Multi-project Pipeline)** — это тип downstream-пайплайна, который запускается в другом проекте GitLab. Этот механизм используется для координации процессов CI/CD между независимыми репозиториями, управления сложными зависимостями (например, в микросервисной архитектуре) и разделения ответственности между командами разработки и эксплуатации.

## Основные концепции

### Ключевые характеристики

- **Инициация:** Запускается из родительского (upstream) проекта через ключевое слово `trigger:project`.
- **Гибкость:** Upstream-пайплайн может указывать конкретную ветку (`ref`) целевого проекта и передавать параметры.
- **Видимость:** Пайплайн отображается в списке запусков целевого (downstream) проекта, но сохраняет визуальную связь с родительским проектом в графе стадий.
- **Вложенность:** В отличие от [родительско-дочерних пайплайнов](./parent_child_pipelines.md), межпроектные вызовы через API не имеют жестких технических ограничений на уровни вложенности (при использовании `trigger` лимит составляет 2 уровня).
- **Контекст:** Выполняется в контексте настроек, переменных и прав целевого проекта.

### Безопасность и CI_JOB_TOKEN

В современных версиях GitLab (17.0+) безопасность межпроектных взаимодействий строится на модели **Zero Trust**.

1. **Inbound Allowlist (Обязательно):** Для того чтобы один проект мог запустить пайплайн в другом или получить его артефакты, он должен быть явно добавлен в «белый список» в настройках целевого проекта: `Settings > CI/CD > Job token permissions`.
2. **Fine-grained Permissions (GitLab 18.3+):** Возможность ограничивать область действия `CI_JOB_TOKEN` конкретными правами (например, только чтение реестра или API), вместо полного наследования прав пользователя.
3. **Авторизация через Git Push (GitLab 18.4+):** Использование `CI_JOB_TOKEN` для выполнения `git push` в репозиторий без использования Personal Access Tokens (PAT).

### Наследование переменных

При межпроектном вызове действуют строгие правила изоляции:
- **Переменные проекта/группы** родителя НЕ наследуются автоматически.
- **Маскированные переменные** (Masked Variables) при передаче через `trigger:variables` могут потерять свойство маскирования в downstream-проекте.
- **Pipeline Variables:** Переменные, переданные через `trigger`, становятся переменными уровня пайплайна в целевом проекте (высокий приоритет).

Подробности см. в документе **[Наследование переменных](./variable_inheritance.md)**.

## Практические сценарии

### Синхронизация статусов через mirror

Использование `strategy: mirror` (GitLab 18.6+) — наиболее надежный способ синхронизации. Родительское задание ждет завершения и в точности повторяет финальный статус (включая `skipped` или `manual`).

```yaml
# Проект: app-frontend
deploy-to-infrastructure:
  stage: deploy
  trigger:
    project: 'infrastructure/deploy-manager'
    branch: main
    strategy: mirror
  variables:
    SERVICE_NAME: "frontend"
    ARTIFACT_VERSION: $CI_COMMIT_TAG
```

### Использование артефактов через needs:project

Нативный способ получения артефактов из родительского проекта без использования API-вызовов и токенов доступа.

```yaml
# Проект: app-testing (Downstream)
integration-tests:
  stage: test
  needs:
    - project: 'apps/main-api'
      job: 'build-assets'
      ref: main
      artifacts: true
  script:
    - ./run-tests.sh --source dist/
```

### Подписка на пайплайны (Pipeline Subscriptions)

Альтернативный способ запуска: вместо того чтобы Upstream толкал изменения, Downstream проект «подписывается» на обновления. Настраивается в `Settings > CI/CD > Subscriptions`.

## Дополнительная информация

### Варианты использования

- **Микросервисы:** Обновление общей библиотеки инициирует сборку всех зависимых сервисов.
- **GitOps и инфраструктура:** Код приложения триггерит пайплайн в репозитории с Terraform-манифестами.
- **Централизованное тестирование:** Вынос тяжелых E2E тестов в отдельный проект для разгрузки основных пайплайнов.
- **Релиз-менеджмент:** Координация деплоя нескольких компонентов одной версии продукта.
