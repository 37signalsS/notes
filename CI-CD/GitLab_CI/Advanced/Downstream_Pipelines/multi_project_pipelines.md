# Межпроектные пайплайны (Multi-project Pipelines)

## Определения

**Межпроектный пайплайн (Multi-project Pipeline)** — это тип downstream-пайплайна, который запускается в отдельном проекте GitLab. Этот механизм служит мостом между независимыми репозиториями, позволяя связывать жизненные циклы разных компонентов (например, запуск тестов приложения при обновлении общей библиотеки) и разделять права доступа между командами (Dev vs Ops).

## Основные концепции

### Ключевые характеристики

- **Инициация:** Запускается через директиву `trigger:project` в YAML или через Pipeline Triggers API (curl).
- **Изоляция:** Выполняется полностью в контексте целевого проекта (свои раннеры, переменные, права).
- **Вложенность:** При использовании YAML-директивы `trigger` лимит вложенности составляет **2 уровня** (Parent -> Multi-project Child -> Grandchild). Вызовы напрямую через API не имеют этого ограничения, но несут риск циклической зависимости.
- **Синхронизация:** С версии GitLab 18.6 стратегия `mirror` позволяет родительскому заданию принимать финальный статус дочернего процесса в другом проекте.
- **Reporting:** При использовании `strategy: mirror` и правильной настройке Job Token, отчеты о безопасности и тестах агрегируются в родительский Merge Request (v18.9+).

### Безопасность и модель Zero Trust (v18.x)

В современных версиях GitLab (18.0+) безопасность межпроектных взаимодействий строится на модели **Zero Trust**. Старые настройки "Limit access from this project" удалены.

1.  **Authorized Projects (Scope):** Для того чтобы Проект А мог запустить пайплайн в Проекте Б, Проект Б должен явно авторизовать Проект А. Это настраивается в `Settings > CI/CD > Job Token Permissions > Authorized groups and projects`.
2.  **Fine-grained Permissions (v18.3+):** Возможность ограничивать `CI_JOB_TOKEN` конкретными скоупами (например, только `read_registry`). Это предотвращает ситуацию, когда токен задачи получает полные права пользователя на целевой проект.
3.  **Исключение PAT:** Использование `CI_JOB_TOKEN` для межпроектных триггеров и доступа к артефактам является SSoT-стандартом. Передача Personal Access Tokens (PAT) через переменные запрещена по соображениям безопасности.

### Наследование переменных

При межпроектном вызове действуют строгие правила изоляции:
- **Переменные проекта/группы** родителя НЕ наследуются автоматически.
- **Маскированные секреты:** При передаче через `trigger:variables` маскирование может быть потеряно, если в дочернем проекте не настроено идентичное правило маскировки.
- **Pipeline Variables:** Переменные, переданные через `trigger`, становятся переменными уровня пайплайна в целевом проекте (имеют высший runtime приоритет).

Подробности см. в документе **[Наследование переменных](./variable_inheritance.md)**.

## Практические сценарии

### Синхронизация статусов через mirror

Использование `strategy: mirror` (GitLab 18.6+) — наиболее надежный способ синхронизации. Родительское задание ждет завершения и в точности повторяет финальный статус (включая `skipped` или `manual`).

```yaml
# Проект: app-frontend
deploy-to-infrastructure:
  stage: deploy
  trigger:
    project: 'infrastructure/deploy-manager'
    branch: main
    strategy: mirror
  variables:
    SERVICE_NAME: "frontend"
    ARTIFACT_VERSION: $CI_COMMIT_TAG
```

### Использование артефактов через needs:project

Нативный способ получения артефактов из родительского проекта без использования API-вызовов и токенов доступа.

```yaml
# Проект: app-testing (Downstream)
integration-tests:
  stage: test
  needs:
    - project: 'apps/main-api'
      job: 'build-assets'
      ref: main
      artifacts: true
  script:
    - ./run-tests.sh --source dist/
```

### Подписка на пайплайны (Pipeline Subscriptions)

Альтернативный способ запуска: вместо того чтобы Upstream "толкал" изменения, Downstream проект «подписывается» на обновления родителя.
- **Где:** `Settings > CI/CD > Pipeline subscriptions`.
- **Ограничение:** Подписки работают **только для веток по умолчанию** (default branches) обоих проектов.
- **Применение:** Автоматическое обновление документации или пересборка Docker-образа при обновлении базового слоя.

## Дополнительная информация

### Технические нюансы и ограничения

- **Deadlock Risk:** При использовании `strategy: mirror` родительская задача занимает слот Runner'а. Если много проектов одновременно триггерят друг друга, может возникнуть ситуация взаимной блокировки (Deadlock) при нехватке лимитов Runner'а.
- **Recursion:** Хотя GitLab не ограничивает вложенность API-вызовов так жестко, как YAML-триггеры, злоупотребление ведет к невозможности отследить цепочку в UI.
- **Артефакты:** Для работы `needs:project` целевой проект **обязательно** должен авторизовать источник в настройках Job Token.
