# Parent-child пайплайны

## Определения

**Parent-child pipeline (Родительско-дочерний пайплайн)** — тип downstream-пайплайна, который запускается и выполняется в рамках того же проекта, что и родительский. Основная цель — декомпозиция сложных конфигураций `.gitlab-ci.yml` и изоляция логически независимых этапов сборки.

## Основные концепции

### Характеристики и ограничения

- **Контекст выполнения:** задачи дочернего пайплайна наследуют `ref` и `commit SHA` родительского запуска.
- **Глубина вложенности:** ограничена двумя уровнями (родитель -> ребёнок -> внук).
- **Видимость:** дочерние пайплайны скрыты из общего списка пайплайнов проекта и доступны только через интерфейс родительского пайплайна.
- **Запуск:** инициируется исключительно через ключевое слово `trigger` в родительской конфигурации.
- **Ресурсы:** используются те же раннеры и общие настройки проекта, что и для основного пайплайна.
- **Жизненный цикл:** при отмене родительского пайплайна все активные дочерние процессы также прерываются (если они помечены как `interruptible`).

## Практические сценарии

### Базовая конфигурация триггера

Пример организации вызова внешнего файла конфигурации внутри того же репозитория.

```yaml
# .gitlab-ci.yml (родительский)
stages:
  - test
  - deploy

child-pipeline-trigger:
  stage: test
  trigger:
    include:
      - local: ci/child-pipeline-config.yml
    strategy: depend
```

### Конфигурация дочернего пайплайна

Файл, содержащий логику конкретного этапа (например, тестирование микросервиса).

```yaml
# ci/child-pipeline-config.yml
stages:
  - test

unit_tests:
  stage: test
  script:
    - npm install
    - npm test
  tags:
    - docker
```

### Динамическая генерация

Метод позволяет формировать файл конфигурации «на лету» с помощью скриптов (Python, Bash) и запускать его как дочерний пайплайн. Это критично для монорепозиториев со сложной логикой изменений. Подробнее в документе **[Динамическая генерация](./dynamic_generation.md)**.

## Дополнительная информация

### Варианты использования

- Разделение монолитного `.gitlab-ci.yml` на независимые модули.
- Изоляция ресурсоёмких задач (expensive jobs) для лучшего управления очередями.
- Упрощение визуализации пайплайна за счёт группировки задач.
- Реализация сложной логики ветвления, недоступной в рамках одного файла.
