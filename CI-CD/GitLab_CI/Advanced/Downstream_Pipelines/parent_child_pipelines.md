# Родительско-дочерние пайплайны (Parent-Child Pipelines)

## Определения

**Родительско-дочерний пайплайн (Parent-Child Pipeline)** — это тип downstream-пайплайна, который запускается и выполняется в рамках того же проекта, что и родительский. Основная цель — декомпозиция сложных конфигураций `.gitlab-ci.yml`, изоляция логически независимых этапов и оптимизация времени выполнения за счёт селективного запуска задач.

## Основные концепции

### Характеристики и возможности

- **Контекст выполнения:** Дочерний пайплайн по умолчанию наследует `ref` и `commit SHA` родительского запуска.
- **Глубина вложенности:** Технический предел составляет **2 уровня** (Parent → Child → Grandchild). При попытке запустить третий уровень возникнет ошибка.
- **Изоляция:** Дочерние пайплайны имеют собственные стадии (stages), которые не зависят от стадий родителя. Это позволяет избежать конфликтов при именовании этапов.
- **Видимость:** В общем списке пайплайнов проекта отображается только родительский запуск. Дочерние пайплайны доступны через интерфейс визуализации (Graph) родителя.
- **Синхронизация статусов:** Использование `strategy: mirror` (GitLab 18.6+) позволяет родительскому заданию точно отражать статус дочернего процесса, включая промежуточные состояния.

### Передача параметров через Inputs (GitLab 17.7+)

Использование `spec:inputs` является рекомендуемым стандартом для передачи данных в дочерние пайплайны. Это обеспечивает строгую типизацию (string, number, boolean, array) и валидацию данных до момента запуска.

## Практические сценарии

### Настройка триггера с типизированными параметрами

Пример организации вызова дочернего пайплайна с передачей параметров для разных окружений.

**1. Конфигурация дочернего пайплайна (`ci/child-config.yml`):**
```yaml
spec:
  inputs:
    environment:
      type: string
      default: development
      options: [development, staging, production]
    run_tests:
      type: boolean
      default: true
---
test-job:
  rules:
    - if: '"$[[ inputs.run_tests ]]" == "true"'
  script:
    - echo "Running tests for $[[ inputs.environment ]]"

deploy-job:
  stage: deploy
  script:
    - echo "Deploying to $[[ inputs.environment ]]"
```

**2. Родительский пайплайн (`.gitlab-ci.yml`):**
```yaml
trigger-production-deploy:
  stage: deploy
  trigger:
    include:
      - local: ci/child-config.yml
        inputs:
          environment: production
          run_tests: false
    strategy: mirror
  rules:
    - if: $CI_COMMIT_TAG
```

### Селективный запуск (rules:changes)

Автоматический запуск дочернего пайплайна только при изменении файлов в конкретной директории (идеально для монорепозиториев).

```yaml
auth-service-pipeline:
  trigger:
    include: services/auth/.gitlab-ci.yml
    strategy: mirror
  rules:
    - changes:
        - services/auth/**/*
```

## Дополнительная информация

### Жизненный цикл и ресурсы

- **Отмена:** При отмене родительского пайплайна дочерние процессы также прерываются (если задачи помечены как `interruptible`).
- **Раннеры:** Дочерние пайплайны используют те же Runner-слоты, что и родительский проект. Задания-триггеры с `strategy: mirror` или `depend` занимают слот раннера всё время ожидания.
- **Динамическая генерация:** Дочерние пайплайны могут запускаться на основе артефактов, созданных в родительском процессе. Подробнее: **[Динамическая генерация](./dynamic_generation.md)**.

### Преимущества подхода

- Упрощение визуализации пайплайна за счёт группировки сотен задач в логические блоки.
- Возможность реализации сложной логики ветвления, недоступной в рамках одного файла.
- Повышение производительности за счёт исключения ненужных проверок через `rules:changes`.
