# Родительско-дочерние пайплайны (Parent-Child Pipelines)

## Определения

**Родительско-дочерний пайплайн (Parent-Child Pipeline)** — это тип downstream-пайплайна, который запускается в рамках того же проекта, что и основной процесс. Ключевым элементом реализации является **Bridge Job** — специальная задача в родительском пайплайне, содержащая директиву `trigger`. Основная цель — декомпозиция конфигураций, изоляция логики микросервисов и оптимизация времени выполнения через селективный запуск.

## Основные концепции

### Характеристики и технические лимиты

- **Контекст выполнения:** Дочерний пайплайн наследует `ref` и `commit SHA` родителя. Это позволяет тестировать код в рамках одного и того же состояния репозитория.
- **Глубина вложенности:** Ограничена **2 уровнями** (Родитель → Ребенок → Внук). Третий уровень инициировать невозможно.
- **Лимит иерархии:** Одна цепочка триггеров может содержать до **1000 downstream-пайплайнов** суммарно (актуально для массовых матричных запусков).
- **Изоляция стадий:** Дочерние пайплайны имеют независимые наборы стадий (`stages`), что исключает конфликты имен и позволяет строить более гибкие графы выполнения.
- **Синхронизация (High Fidelity):** Использование `strategy: mirror` (GitLab 18.6+) является стандартом. Оно гарантирует, что статус Bridge Job в точности повторяет статус дочернего процесса (включая `manual` и `skipped`).

### Передача параметров через Inputs (GitLab 18.9+)

В современных версиях GitLab (18.9+) рекомендуется использовать директиву **`trigger:inputs`**. В отличие от переменных, входы (inputs) валидируются на этапе компиляции YAML. Если обязательный параметр отсутствует, пайплайн не будет создан, что предотвращает ошибки в середине выполнения.

## Практические сценарии

### Настройка триггера с типизированными параметрами

Пример вызова дочернего пайплайна с использованием современного синтаксиса `inputs`.

**1. Конфигурация дочернего пайплайна (`ci/child-config.yml`):**
```yaml
spec:
  inputs:
    environment:
      type: string
      default: development
      options: [development, staging, production]
    run_tests:
      type: boolean
      default: true
---
test-job:
  rules:
    - if: '"$[[ inputs.run_tests ]]" == "true"'
  script:
    - echo "Running tests for $[[ inputs.environment ]]"

deploy-job:
  stage: deploy
  script:
    - echo "Deploying to $[[ inputs.environment ]]"
```

**2. Родительский пайплайн (`.gitlab-ci.yml`):**
```yaml
trigger-production-deploy:
  stage: deploy
  trigger:
    include: ci/child-config.yml
    inputs: # Синтаксис GitLab 18.9+
      environment: production
      run_tests: false
    strategy: mirror
  rules:
    - if: $CI_COMMIT_TAG
```

### Селективный запуск (rules:changes)

Автоматический запуск дочернего пайплайна только при изменении файлов в конкретной директории (идеально для монорепозиториев).

```yaml
auth-service-pipeline:
  trigger:
    include: services/auth/.gitlab-ci.yml
    strategy: mirror
  rules:
    - changes:
        - services/auth/**/*
```

## Дополнительная информация

### Жизненный цикл и ресурсы

- **Bridge Job Mechanics:** Задание-триггер в родительском пайплайне остается в статусе `running` до завершения дочернего процесса, если используется `strategy: mirror` или `depend`. Это занимает лимит конкурентности (concurrency) вашего Runner'а.
- **Отмена:** При отмене родительского пайплайна дочерние процессы прерываются автоматически (при условии `interruptible: true`).
- **Динамическая генерация:** Дочерние пайплайны могут запускаться на основе артефактов, созданных в родительском процессе. Это SSoT паттерн для сложных монорепозиториев. Подробнее: **[Динамическая генерация](./dynamic_generation.md)**.

### Преимущества подхода

- **Визуальная декомпозиция:** Группировка сотен задач в логические блоки (Child Graphs), что упрощает аудит пайплайна.
- **Сложное ветвление:** Реализация логики, недоступной в плоском YAML (например, разные наборы стадий для разных модулей).
- **Производительность:** Экономия CI-минут через `rules:changes` на уровне триггера.
