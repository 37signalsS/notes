# Pipeline Subscriptions (Подписки на пайплайны)

**Актуально для:** GitLab 17.x–19.x

## Определения

**Pipeline Subscription** — механизм GitLab CI/CD, при котором downstream-проект автоматически запускает свой пайплайн при успешном завершении upstream-пайплайна в ветке по умолчанию. Это инвертированный триггер: вместо того чтобы upstream запускал downstream, downstream сам подписывается на события upstream.

**Upstream-проект** — проект, чьи пайплайны служат источником событий для подписки.

**Downstream-проект** — проект, содержащий подписку; его пайплайн запускается автоматически при событии в upstream.

**Subscription trigger** — внутренний механизм GitLab, который создает downstream-пайплайн при получении события `Pipeline Hook` от upstream-проекта.

## Основные концепции

### Архитектура и жизненный цикл

Pipeline Subscriptions работают через вебхуки и внутреннюю шину событий GitLab:

1.  **Создание подписки:** Downstream-проект настраивает подписку на upstream-проект через `Settings > CI/CD > Pipeline subscriptions`.
2.  **Активация:** При успешном завершении пайплайна в upstream-ветке по умолчанию GitLab отправляет событие `Pipeline Hook` downstream-проекту.
3.  **Запуск downstream:** Downstream-проект создает новый пайплайн на основе своего `.gitlab-ci.yml` в той же ветке, что и upstream.
4.  **Синхронизация:** Downstream-пайплайн выполняется независимо; upstream не ожидает его завершения (fire-and-forget).

### Ключевые характеристики

- **Ветка по умолчанию:** Подписки работают **только** для веток по умолчанию (`main`, `master`). Триггер на произвольную ветку или тег через подписки невозможен.
- **Изоляция:** Downstream-пайплайн запускается в контексте downstream-проекта с его Runner'ами, переменными и правами.
- **Без параметров:** Подписка не передает параметры автоматически. Downstream-пайплайн запускается без переменных upstream, кроме предопределенных (`CI_COMMIT_SHA`, `CI_COMMIT_REF_NAME` и др.).
- **Односторонняя связь:** Подписка создает связь только от upstream к downstream. Для обратной связи используйте `trigger:project` или API.

### Ограничения

- **Только default branch:** Подписка не срабатывает для feature-веток, тегов или MR-пайплайнов.
- **Нет валидации параметров:** Downstream-пайплайн запускается без знания контекста upstream (версия, окружение).
- **Нет стратегий:** Не поддерживаются `strategy: mirror` или `depend` — подписка всегда fire-and-forget.
- **Зависимость от вебхуков:** Если вебхук не доставлен, подписка не сработает.

## Практические сценарии

### Сценарий 1: Автоматическая пересборка образа при обновлении базового образа

Upstream-проект (`base-images`) собирает базовый Docker-образ. Downstream-проект (`my-app`) подписан на успешные пайплайны `base-images` в `main` и автоматически пересобирает свое приложение с новым базовым образом.

**Настройка в downstream-проекте (`my-app`):**
1. Перейдите в `Settings > CI/CD > Pipeline subscriptions`.
2. Нажмите `Subscribe to a project`.
3. Введите путь upstream-проекта: `group/base-images`.
4. Выберите ветку: `main`.

**`.gitlab-ci.yml` в `my-app`:**
```yaml
rebuild-app:
  stage: build
  script:
    - docker build --build-arg BASE_IMAGE=registry.example.com/base-images/python:3.12 -t my-app:$CI_COMMIT_SHA .
    - docker push my-app:$CI_COMMIT_SHA
  rules:
    - if: $CI_PIPELINE_SOURCE == "pipeline"
```

### Сценарий 2: Автоматическое обновление зависимой библиотеки

Upstream-проект (`shared-lib`) публикует новую версию библиотеки. Downstream-проект (`app-service`) подписан на успешные пайплайны `shared-lib` и автоматически запускает интеграционные тесты с новой версией.

**Настройка подписки:** Аналогична сценарию 1, upstream = `group/shared-lib`.

**`.gitlab-ci.yml` в `app-service`:**
```yaml
test-with-new-lib:
  stage: test
  script:
    - npm install @group/shared-lib@latest
    - npm test
  rules:
    - if: $CI_PIPELINE_SOURCE == "pipeline"
```

### Сценарий 3: Каскадное обновление нескольких downstream-проектов

Несколько downstream-проектов подписаны на один upstream-проект. При успешном пайплайне upstream все они запускаются параллельно.

**Настройка:**
- `service-a` подписан на `group/shared-lib`
- `service-b` подписан на `group/shared-lib`
- `service-c` подписан на `group/shared-lib`

При успешном пайплайне `shared-lib` в `main` все три сервиса автоматически запустят свои пайплайны.

## Диагностика и устранение неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| Подписка не срабатывает | Upstream-пайплайн запущен не в default branch | Подписки работают только для default branch. Используйте `trigger:project` для произвольных веток. |
| Подписка не срабатывает | Upstream-пайплайн завершился с ошибкой | Подписка срабатывает только при `success`. Проверьте статус upstream-пайплайна. |
| Подписка не срабатывает | Downstream-проект удален или недоступен | Проверьте существование downstream-проекта и права доступа. |
| Downstream-пайплайн не запускается | В `.gitlab-ci.yml` downstream нет `rules` или `workflow:rules`, фильтрующих `pipeline` source | Добавьте `rules: - if: $CI_PIPELINE_SOURCE == "pipeline"` в downstream-задачи. |
| Подписка сработала, но переменные пустые | Подписка не передает переменные upstream | Используйте `needs:project` или `trigger:project` для передачи контекста. |
| Подписка исчезла после перемещения проекта | Подписка привязана к полному пути проекта | После перемещения upstream или downstream удалите старую подписку и создайте новую. |

## Best Practices

### Настройка и эксплуатация

1. **Используйте для автоматических пересборок:** Pipeline Subscriptions идеальны для каскадного обновления зависимых проектов при изменении общего ресурса (базовый образ, библиотека).
2. **Не используйте для production-деплоев:** Подписки работают только для default branch и не передают контекст. Для production используйте явные `trigger:project` с `strategy: mirror`.
3. **Фильтруйте по `CI_PIPELINE_SOURCE`:** В downstream-проекте добавляйте `rules: - if: $CI_PIPELINE_SOURCE == "pipeline"` для предотвращения запуска задач при ручном запуске пайплайна.
4. **Мониторьте доставку вебхуков:** Настройте алерт на `last_delivery_at` для вебхуков `Pipeline Hook` в upstream-проекте.
5. **Документируйте подписки:** Ведите реестр всех Pipeline Subscriptions с указанием upstream/downstream проектов и назначения.

### SRE: Мониторинг и алертинг

- **Метрика:** Количество downstream-пайплайнов, запущенных через подписку, за час.
- **Алерт:** Если downstream-проект не запустил пайплайн после успешного upstream в default branch — проверьте подписку и вебхуки.
- **Алерт:** Downstream-пайплайн завершился `failed` после подписки — проверьте конфигурацию downstream и доступность Runner'ов.

### SRE: Инцидент-респонс

При расследовании проблем с Pipeline Subscriptions:

1. Проверьте статус подписки в downstream-проекте:
    ```bash
    # Через UI: Settings > CI/CD > Pipeline subscriptions
    # Публичный API для перечисления подписок не документирован;
    # используйте проверку доставки вебхуков и UI для валидации.
    ```

2. Проверьте доставку вебхуков в upstream-проекте:
   ```bash
   curl --header "PRIVATE-TOKEN: $TOKEN" \
     "https://gitlab.example.com/api/v4/projects/$UPSTREAM_ID/hooks" | \
     jq '.[] | select(.pipeline_events == true) | {id, url, last_delivery_at, last_error_message}'
   ```

3. Проверьте пайплайны downstream-проекта:
   ```bash
   curl --header "PRIVATE-TOKEN: $TOKEN" \
     "https://gitlab.example.com/api/v4/projects/$DOWNSTREAM_ID/pipelines?ref=main&per_page=5" | \
     jq '.[] | {id, status, created_at, source}'
   ```

4. При массовом отказе подписок проверьте:
   - Статус вебхуков в upstream-проектах.
   - Доступность downstream-проектов (не удалены, не приватны без доступа).
   - Лимиты API GitLab (rate limiting при массовых событиях).

5. Документируйте паттерн инцидента: upstream-проект, downstream-проект, статус подписки, время события, диагностические команды.

### Sysadmin: Предварительные требования и валидация

- **RBAC:** Для создания подписки в downstream-проекте требуется роль Maintainer или Owner. Убедитесь, что оператор имеет права на настройку CI/CD в downstream-проекте.
- **Вебхуки:** GitLab должен иметь исходящий доступ к downstream-проекту по HTTPS. Проверьте, что firewall не блокирует порт 443/8443.
- **TLS:** GitLab не отправляет вебхуки на HTTP (кроме localhost в development). Убедитесь, что сертификат downstream-вебхук-приёмника валиден и не истёк.
- **DNS:** GitLab кэширует DNS на 5 минут. При смене IP downstream-вебхук-приёмника старый IP может использоваться до истечения кэша.
- **Время:** Синхронизируйте время между GitLab, upstream и downstream (NTP). Это критично для проверки JWT-подписи вебхуков.
- **Runner'ы:** Настройте Runner'ы с высокой доступностью для downstream-проектов. Подписки не передают контекст об ошибках upstream, поэтому downstream должен иметь изолированные Runner'ы.

### Валидация рабочей конфигурации

1. **Создайте тестовую подписку** в downstream-проекте на upstream-проект.
2. **Запустите успешный пайплайн** в upstream-ветке по умолчанию.
3. **Проверьте доставку вебхука:**
    ```bash
    # Проверьте последние доставки вебхуков в upstream-проекте
    curl --header "PRIVATE-TOKEN: $TOKEN" \
      "https://gitlab.example.com/api/v4/projects/$UPSTREAM_ID/hooks" | \
      jq '.[] | select(.pipeline_events == true) | {id, url, last_delivery_at, last_error_message}'
    ```
4. **Проверьте создание downstream-пайплайна:**
    ```bash
    # Проверьте пайплайны downstream-проекта
    curl --header "PRIVATE-TOKEN: $TOKEN" \
      "https://gitlab.example.com/api/v4/projects/$DOWNSTREAM_ID/pipelines?ref=main&per_page=5" | \
      jq '.[] | {id, status, created_at, source}'
    ```
5. **Проверьте, что downstream-пайплайн запустился с источником `pipeline`:**
    ```bash
    # В downstream-проекте должен быть фильтр по CI_PIPELINE_SOURCE
    # Убедитесь, что в .gitlab-ci.yml есть rules: - if: $CI_PIPELINE_SOURCE == "pipeline"
    ```

### Compliance и аудит

- **Реестр подписок:** Ведите реестр всех Pipeline Subscriptions с указанием upstream/downstream проектов, ветки и назначения. Обновляйте при каждом изменении.
- **Аудит вебхуков:** Включите аудит вебхуков в upstream-проектах (`Settings > Webhooks > Audit log`) для отслеживания доставки событий.
- **Сегрегация duties:** Разделите права на создание подписок (DevOps team) и права на запуск пайплайнов (application teams).
- **Ограничение scope:** Подписки должны использоваться только для некритичных автоматических пересборок. Для production-деплоев используйте явные триггеры с approval gates.

### Очистка и откат

- **Удаление подписки:** При перемещении или удалении upstream-проекта удалите подписку в downstream-проекте через `Settings > CI/CD > Pipeline subscriptions`.
- **Отключение downstream-пайплайна:** Для временного отключения используйте `rules: []` в downstream-задачах. Это безопаснее, чем удаление подписки.
- **Валидация после отката:** После удаления подписки проверяйте, что downstream-проект не запускает пайплайны автоматически.

### Disaster Recovery

- **Восстановление подписки:** При восстановлении upstream-проекта из резервной копии создайте подписку заново. Старая подписка не восстанавливается автоматически.
- **Fallback на trigger:** Для критичных downstream-проектов подготовьте явный `trigger:project` в upstream-проекте как fallback на случай отказа подписки.
- **Аварийный запуск downstream:** Если подписка не сработала, запустите downstream-пайплайн вручную через Web UI или API.

### Self-managed инсталляции

- **Вебхуки и firewall:** Убедитесь, что GitLab может доставлять вебхуки между проектами внутри инстанса. Проверьте firewall и DNS.
- **Мониторинг очереди вебхуков:** Мониторьте размер очереди не доставленных вебхуков через Admin API. GitLab повторяет неуспешные вебхуки до 3 раз с интервалом ~1 минуты.
- **Версионирование GitLab:** Pipeline Subscriptions доступны в GitLab 17.0+. Убедитесь, что все проекты в цепочке используют совместимые версии.
- **Резервные Runner'ы:** Настройте Runner'ы с высокой доступностью для downstream-проектов, так как подписки не передают контекст об ошибках upstream.
- **TLS и сертификаты:** GitLab не отправляет вебхуки на HTTP (кроме localhost в development). Убедитесь, что сертификат downstream-вебхук-приёмника валиден и не истёк.
- **Сеть:** При доставке вебхуков между сегментами сети откройте порт 443/8443 в обоих направлениях.
- **Rate Limit:** По умолчанию ~60 запросов/минуту для REST API. Для инстансов с высокой нагрузкой лимиты могут быть увеличены администратором.

## Edge Cases и известные проблемы

- **Подписка при переименовании проекта:** Подписка привязана к полному пути проекта. При переименовании upstream или downstream подписка перестает работать. Решение: удалите старую подписку и создайте новую.
- **Подписка при перемещении между группами:** При перемещении upstream-проекта в другую группу подписка разрывается. Решение: пересоздайте подписку после перемещения.
- **Вебхук не доставлен:** GitLab повторяет неуспешные вебхуки до 3 раз с интервалом ~1 минуты. После 3 неудач доставка прекращается. Решение: проверьте доступность downstream-вебхук-приёмника и настройте API polling как fallback.
- **Downstream-пайплайн запускается repeatedly:** Если upstream-проект имеет несколько пайплайнов в default branch (например, scheduled и push), подписка сработает для каждого успешного пайплайна. Решение: добавьте фильтрацию по `CI_PIPELINE_SOURCE` в downstream.
- **Циклические подписки:** Если проект A подписан на проект B, а проект B — на проект A, это может привести к бесконечному запуску пайплайнов. GitLab не блокирует циклические подписки явно. Решение: избегайте циклических зависимостей и используйте реестр подписок для аудита.
