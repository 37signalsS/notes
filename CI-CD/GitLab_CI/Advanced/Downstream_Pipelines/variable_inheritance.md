# Наследование переменных в downstream-пайплайнах

## Определения

**Наследование переменных** — высокоуровневый механизм проброса контекста из родительского (upstream) задания в среду выполнения дочернего (downstream) процесса. Технически это означает инъекцию значений в среду окружения (Environment) Runner'а, на котором будет выполняться дочерняя задача, с учетом правил фильтрации (`forward`) и приоритетов GitLab CI.

## Основные концепции

### Иерархия приоритетов (GitLab 19.x)

Переменные, переданные в downstream-пайплайн, в его контексте получают статус **Trigger/Pipeline Variables**. Это критически важно для отладки: они переопределяют большинство настроек проекта.

**Порядок приоритетов в дочернем пайплайне (от высшего к низшему):**
1.  **Trigger Variables:** Переменные, переданные явно через блок `trigger:variables` или API.
2.  **Pipeline Inputs:** Значения из `spec:inputs` (интерполируются на этапе компиляции YAML).
3.  **Forwarded Variables:** Переменные, проброшенные через `trigger:forward`.
4.  **Project/Group Variables:** Переменные, заданные в настройках дочернего проекта.
5.  **Dotenv Reports:** Переменные из загруженных артефактов `artifacts:reports:dotenv`.
6.  **Job Variables:** Блок `variables` внутри конкретной задачи в дочернем YAML.
7.  **Predefined Variables:** Встроенные переменные GitLab (`CI_*`).

### Механизмы передачи (trigger:forward)

Ключевое слово `forward` управляет автоматическим потоком данных.

| Параметр | Описание | По умолчанию (P-C) | По умолчанию (M-P) |
| :--- | :--- | :---: | :---: |
| **`yaml_variables`** | Переменные из блоков `variables` родительского пайплайна. | `true` | `false` |
| **`pipeline_variables`** | Переменные, с которыми был запущен родитель (API/Web UI). | `true` | `false` |

**Почему лимиты отличаются?**
-   **Parent-Child (P-C):** Выполняется в том же проекте, поэтому по умолчанию разрешена максимальная интеграция.
-   **Multi-Project (M-P):** Выполняется в другом проекте (возможно, другой команды). По умолчанию передача закрыта для обеспечения безопасности и изоляции контекста (Zero Trust).

**Пример безопасного ограничения:**
```yaml
trigger-multi-project:
  trigger:
    project: security/scanner
    forward:
      yaml_variables: true      # Передать конфигурацию сканера
      pipeline_variables: false # Не передавать токены ручного запуска
```

### Блокировка наследования (inherit)

Для полной изоляции дочернего пайплайна от глобальных переменных родительского файла используется `inherit:variables:false`. Это предотвращает конфликт имен.

```yaml
isolated-job:
  inherit:
    variables: false # Не брать переменные из глобального блока upstream
  variables:
    DOCKER_IMAGE: "alpine:latest"
  trigger:
    include: child.yml
```

## Практические сценарии

### Использование Pipeline Inputs (Рекомендуемый стандарт 18.x)

С выходом **GitLab 18.0** использование `spec:inputs` становится предпочтительным способом передачи параметров конфигурации.

**Преимущества:**
- **Валидация:** проверка типов (`string`, `number`, `boolean`) до старта пайплайна.
- **Неизменяемость:** инпуты интерполируются в YAML до создания пайплайна и не могут быть переопределены в runtime.
- **Безопасность:** чёткая спецификация ожидаемых данных.

**Вызов с использованием inputs:**
```yaml
deploy-production:
  trigger:
    include:
      - local: ci/deploy-template.yml
        inputs:
          stage_name: "prod"
          replica_count: 3
```

### Динамическая передача через dotenv

Используется для передачи данных, которые генерируются во время выполнения (например, ID артефакта или динамический тег образа).

```yaml
# Upstream
generate-build:
  stage: build
  script:
    - echo "IMAGE_TAG=$(date +%s)" > build.env
  artifacts:
    reports:
      dotenv: build.env

# Downstream (автоматически получит IMAGE_TAG как переменную пайплайна)
trigger-deploy:
  stage: deploy
  trigger: my-group/deploy-project
```

## Дополнительная информация

### Рекомендации по безопасности

- **Не передавайте маскированные секреты:** При передаче через `trigger:variables` в Multi-project пайплайны свойство маскирования может быть потеряно, если в дочернем проекте не настроено идентичное правило маскировки. Это ведет к утечке секретов в логи.
- **Используйте OIDC (ID Tokens):** Вместо проброса паролей из upstream, используйте `id_tokens` в дочернем пайплайне для прямой аутентификации в Vault/AWS. Это соответствует модели **Zero Trust**.
- **Изолируйте контекст:** Используйте `forward:pipeline_variables:false`, если не уверены в безопасности данных, вводимых пользователями при ручном запуске.
- **Лимиты Dotenv:** Помните, что размер `.env` файла ограничен **5 МБ**.
