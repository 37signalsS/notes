# Лучшие практики Downstream-пайплайнов

## Определения

**Best Practices (Лучшие практики)** — проверенные методы и подходы при работе с downstream-пайплайнами, направленные на обеспечение безопасности, производительности и удобства сопровождения (maintainability).

## Основные концепции

### Ключевые принципы

- **Используйте `inputs` вместо `variables`** (GitLab 17+) — типизированные параметры с валидацией
- **`strategy: depend` для отчётов** — необходимо для корректного отображения тестов, безопасности и качества кода (security, code quality)
- **`strategy: mirror` для синхронизации статусов** — критично для зависимых стадий (stages)
- **Версионирование шаблонов** — используйте фиксированные теги (`ref: 'v1.2.3'`) для `include`
- **Минимальные права** — использование Deploy Tokens с ограниченными правами для multi-project пайплайнов
- **Ограничение вложенности** — соблюдение лимита parent-child пайплайнов (максимум 2 уровня)
- **Безопасность переменных** — блокировка наследования masked variables для предотвращения утечек
- **Мониторинг** — обязательная настройка timeout и логирование связей upstream/downstream

## Практические сценарии

### Версионирование шаблонов

Используйте параметр `ref` для подключения шаблонов из других проектов. Это предотвращает внезапные поломки пайплайна при обновлении общих конфигураций.

```yaml
trigger:
  include:
    - project: 'group/ci-templates'
      ref: 'v1.2.3'
      file: 'pipeline.yml'
```

### Минимальные права для multi-project пайплайнов

Всегда проверяйте права пользователя на запуск в downstream-проекте. Для автоматизации multi-project пайплайнов рекомендуется использовать Deploy Tokens с минимально необходимыми правами. Избегайте передачи секретных переменных в открытом виде.

```yaml
deploy:
  trigger:
    project: 'group/production'
    token: $DEPLOY_TOKEN
```

### Ограничение вложенности

- **Parent-child:** технический предел — 2 уровня вложенности (parent -> child -> grandchild)
- **Multi-project:** формальных ограничений нет, но следует избегать глубоких иерархий для упрощения отладки

### Безопасность переменных

Не передавайте masked variables в multi-project pipelines из-за риска их раскрытия (unmask) в downstream-проекте. Используйте `inherit: variables: false` для явного контроля передаваемых данных.

```yaml
secure-trigger:
  trigger:
    include: sensitive.yml
  inherit:
    variables: false
  variables:
    SAFE_VAR: value
```

Проверяйте уровень конфиденциальности проектов при организации взаимодействия между ними.

### Мониторинг и отладка

- Используйте `needs` для точного управления зависимостями между задачами
- Всегда настраивайте `timeout` для предотвращения зависания пайплайнов
- Логируйте идентификаторы upstream/downstream для быстрого поиска связанных запусков

## Дополнительная информация

### Чеклист перед запуском в эксплуатацию

- [ ] Используется механизм `inputs` вместо `variables` (для GitLab 17+)
- [ ] Указана стратегия `strategy: depend` для сбора отчётов
- [ ] Применена стратегия `strategy: mirror` для критичных зависимостей
- [ ] Шаблоны зафиксированы через конкретные версии (`ref`)
- [ ] Настроены минимальные права (Deploy Tokens)
- [ ] Исключена передача secret/masked variables без необходимости
- [ ] Вложенность пайплайнов не превышает 2 уровней
- [ ] Установлены корректные timeout для всех триггеров

### Распространённые ошибки

- **Отсутствие `strategy: depend`** — результаты тестов и сканирований не отображаются в Merge Request (MR)
- **Передача masked variables в другие проекты** — высокий риск утечки конфиденциальных данных
- **Чрезмерная вложенность parent-child** — значительное усложнение визуализации и отладки
- **Отсутствие версионирования** — нестабильность CI/CD при обновлении общих компонентов
- **Использование `variables` для передачи параметров** — отсутствие типизации и валидации входных данных
