# Лучшие практики Downstream-пайплайнов

## Определения

**Лучшие практики (Best Practices)** — это набор проверенных архитектурных и технических подходов, направленных на обеспечение безопасности, предсказуемости и оптимального использования ресурсов при проектировании иерархических пайплайнов в GitLab CI/CD.

## Основные концепции

### Архитектурные принципы

- **Zero Trust и POLP (Принцип наименьших привилегий):** В GitLab 18.0+ безопасность межпроектных связей строится на явном разрешении доступа. Использование `CI_JOB_TOKEN` ограничено контекстом проекта-владельца до момента добавления вызывающего проекта в **Inbound Allowlist**. Это предотвращает несанкционированный доступ к артефактам, API и реестрам контейнеров. С 18.3+ доступны **Fine-grained Permissions** для тонкой настройки областей доступа токена (только `read_registry`, только `api` и т.д.).
- **Декларативные контракты (spec:inputs):** Переход от неявной передачи данных через глобальные переменные к явному описанию интерфейса в блоке `spec:inputs`. Это обеспечивает валидацию параметров на этапе компиляции YAML и предотвращает запуск дочерних процессов с некорректными данными. Поддерживает типы `string`, `number`, `boolean`, `array`, а также `options` и `regex` для строгой валидации.
- **Синхронизация состояний (High Fidelity):** Применение `strategy: mirror` для критических этапов жизненного цикла (Production Deploy, Security Compliance). Это гарантирует, что статус родительского задания в точности отражает результат дочернего процесса, включая специфические состояния `manual` и `skipped`. Единственная стратегия, поддерживающая агрегацию Security Reports (SAST, DAST, SBOM) в MR родителя (GitLab 18.9+).
- **Изоляция контекста (Data Leakage Control):** Строгий контроль наследования через `trigger:forward`. По умолчанию рекомендуется отключать передачу переменных YAML (`yaml_variables: false`), чтобы избежать случайной утечки внутренних настроек родительского пайплайна в дочерние проекты. Для multi-project передача закрыта полностью по умолчанию.
- **Валидация конфигурации:** Перед коммитом `.gitlab-ci.yml` необходимо проверять синтаксис через **Pipeline Lint** (`Settings > CI/CD > Pipeline editor` или `glab ci lint`). Это критично для динамически генерируемых конфигураций, где ошибки в YAML не видны до момента запуска Bridge Job.
- **Принцип активной диагностики:** Мониторинг Bridge Jobs через API (`GET /api/v4/projects/:id/pipelines/:pipeline_id/bridges`) для раннего обнаружения deadlock, зависших заданий и несоответствия статусов. Рекомендуется настройка алертов при превышении 80% использования слотов Runner'а.

### Ключевые инструменты управления

| Инструмент | Назначение | Рекомендация к применению |
| :--- | :--- | :--- |
| **`spec:inputs`** | Типизированные параметры | Обязательно для всех Parent-Child пайплайнов и переиспользуемых модулей. |
| **`strategy: mirror`** | Синхронизация жизненного цикла | Использовать для деплоев и агрегации Security Reports (GitLab 18.9+). |
| **`needs:project`** | Кросс-проектные артефакты | Современная альтернатива `curl/API`. Поддерживает Zero Trust и не требует токенов доступа. |
| **`trigger:forward`** | Фильтрация переменных | Всегда ограничивать `yaml_variables` для предотвращения конфликтов имен. |
| **`environment`** | Видимость развертываний | Указывать в Bridge Job для корректного отображения MR-виджетов и истории окружений. |
| **`timeout`** | Защита от зависания | Устанавливать явно для Bridge Job: 20-30% запаса от суммарного времени downstream. Для `manual` действий — `timeout: 7 days`. |
| **`interruptible`** | Auto-cancel при пуше | Устанавливать `true` для downstream-задач, которые могут быть безопасно отменены при новом коммите. |
| **`allow_failure`** | Контроль блокировки | Явно задавать для Bridge Job: `false` для критичных деплоев, `true` для некритичных проверок. |
| **CI Lint / Pipeline Editor** | Валидация YAML | Проверять конфигурацию перед коммитом, особенно для динамических пайплайнов и `spec:inputs`. |

## Практические сценарии

### Настройка Zero Trust доступа (GitLab 18.0+)

Для того чтобы Upstream-проект мог запустить триггер или скачать артефакты из Downstream-проекта, необходимо настроить доверительные отношения.

**Пошаговая инструкция:**
1. Перейдите в **целевой** (Downstream) проект.
2. Откройте `Settings > CI/CD > Token Access`.
3. Убедитесь, что переключатель **«Limit access to this project»** включен (режим Zero Trust).
4. В поле «Allow access to the following projects» введите полный путь к **родительскому** (Upstream) проекту.
5. Нажмите «Add project». Теперь Bridge Job из родительского проекта сможет успешно инициировать триггер.

### Безопасная передача параметров через Inputs

Использование `inputs` вместо переменных предотвращает инъекции и ошибки типизации.

```yaml
# Upstream .gitlab-ci.yml
deploy-service:
  stage: deploy
  trigger:
    include:
      - local: 'ci/deploy-template.yml'
    inputs:
      target_env: "production"
      replica_count: 3
      enable_monitoring: true
```

### Кросс-проектное получение артефактов без API

Используйте `needs:project` для нативного скачивания артефактов из другого проекта в рамках иерархии.

```yaml
# В Downstream-проекте
integration-test:
  stage: test
  needs:
    - project: 'group/build-artifacts-repo'
      job: 'build-binary'
      ref: main
      artifacts: true
```

### Предотвращение Deadlock на Runner'ах

При использовании синхронных стратегий (`mirror`, `depend`) Upstream-задание занимает слот Runner'а всё время, пока работает Downstream.

**Рекомендации по оптимизации:**
- **Разделение тегов:** Используйте разные `tags` для Bridge Job и рабочих задач Downstream-пайплайна. Это позволит им запускаться на разных пулах Runner'ов.
- **Асинхронный триггер:** Если вам не нужно ждать завершения (например, отправка логов или уведомлений), не указывайте `strategy`.
- **Мониторинг Concurrency:** При использовании матричных триггеров (`parallel:matrix`) убедитесь, что `concurrency` Runner'а превышает суммарное количество одновременно ожидающих задач.
- **Разбиение матриц:** При > 5 инстансах в `parallel:matrix` с `mirror` рассмотрите разбиение на отдельные триггеры с `fire and forget` для предотвращения блокировки.

### Настройка timeout для Bridge Job

Таймаут Bridge Job должен учитывать суммарное время выполнения всех стадий downstream-пайплайна, время ожидания в очереди Runner'а и время ожидания `manual` действий.

```yaml
# Рекомендуемый паттерн
trigger-deploy:
  stage: deploy
  trigger:
    project: 'ops/deploy-repo'
    strategy: mirror
  timeout: 30 minutes  # Для автоматического деплоя
  # timeout: 7 days    # Для сценариев с manual-подтверждением

# Без timeout Bridge Job упадет через 1 час (по умолчанию)
```

**Правило:** Устанавливайте `timeout` на 20-30% больше суммарного времени downstream. Для сценариев с `manual` действиями используйте `timeout: 7 days` или больше.

### Мониторинг Deadlock через API

Проактивный мониторинг Bridge Jobs для раннего обнаружения deadlock и зависших заданий.

```bash
# Просмотр всех Bridge Jobs в пайплайне
curl --header "PRIVATE-TOKEN: $TOKEN" \
  "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/pipelines/$PIPELINE_ID/bridges" | \
  jq '.[] | {id, name, status, stage}'

# Подсчет активных Bridge Jobs (потенциальный deadlock)
curl --header "PRIVATE-TOKEN: $TOKEN" \
  "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/pipelines/$PIPELINE_ID/bridges" | \
  jq '[.[] | select(.status == "running")] | length'

# Проверка статуса downstream-пайплайна
curl --header "PRIVATE-TOKEN: $TOKEN" \
  "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/pipelines/$DOWNSTREAM_ID" | \
  jq '{id, status, finished_at}'
```

**Целевые метрики:**
| Метрика | Целевое значение |
| :--- | :--- |
| Runner slot utilization (Bridge Jobs) | < 30% |
| Deadlock incidents | 0 |
| Bridge Job timeout rate | < 5% |

### Multi-service цепочка с mirror

Паттерн для параллельного тестирования нескольких микросервисов с агрегацией результатов в родительском пайплайне.

```yaml
# Базовый шаблон для всех сервисов
.test-service:
  stage: test
  trigger:
    strategy: mirror
  allow_failure: false  # Провал любого сервиса блокирует интеграцию

test-auth:
  extends: .test-service
  trigger:
    include: services/auth/ci.yml

test-payment:
  extends: .test-service
  trigger:
    include: services/payment/ci.yml

test-notification:
  extends: .test-service
  trigger:
    include: services/notification/ci.yml

# Интеграционные тесты запускаются только после успеха всех сервисов
integration-test:
  stage: integration
  script:
    - ./run-integration-tests.sh
  needs: [test-auth, test-payment, test-notification]
```

**Важно:** Если хотя бы один сервис упадет, `allow_failure: false` заблокирует `integration-test`.

## Дополнительная информация

### Технические лимиты и ограничения

- **Глубина триггеров:** Максимальная вложенность составляет **2 уровня** (Родитель -> Ребенок -> Внук). Третий уровень инициировать через `trigger` невозможно. Обходные пути: Pipeline Triggers API или плоская архитектура.
- **Размер дерева:** Вся иерархия связанных триггерами пайплайнов не может превышать **1000** объектов. Превышение вызывает ошибку `Downstream pipeline tree is too large`.
- **Защита от циклов:** GitLab анализирует цепочку триггеров. Если обнаружена попытка запустить тот же проект с тем же `commit SHA`, триггер будет заблокирован для предотвращения рекурсивного DDoS инфраструктуры.
- **Таймауты:** Таймаут родительской Bridge Job должен учитывать суммарное время выполнения всех стадий дочернего пайплайна плюс время ожидания в очереди. По умолчанию — **1 час**. Для `manual` действий увеличивайте до 7 дней.
- **`needs` + `trigger`:** Задача с `trigger` не может иметь `needs` — Bridge Job не может быть зависимостью для других задач. Используйте `stages` для порядка или `strategy: depend/mirror` для связи через статус.
- **`parallel:matrix` + `mirror`:** Bridge Job ждет завершения **всех** инстансов матрицы. При > 5 инстансах рассмотрите разбиение на отдельные триггеры.
- **Pipeline Subscriptions:** Работают только для **веток по умолчанию** (main/master). Триггер на произвольную ветку через подписки невозможен.
- **Размер конфигурации:** Максимальный размер дочернего YAML-файла (включая все вложенные `include`) составляет **5 МБ**.

### Чеклист проверки пайплайна

**Безопасность:**
- Настроен **Inbound Allowlist** для обеспечения безопасности `CI_JOB_TOKEN` (Settings > CI/CD > Token Access).
- Используются **Fine-grained Permissions** для тонкой настройки областей доступа токена (GitLab 18.3+).
- Переменные передаются через `spec:inputs` вместо `trigger:variables` для предотвращения инъекций.
- В multi-project триггерах `forward: yaml_variables: false` (изоляция по умолчанию).

**Параметризация:**
- Параметры передаются через `spec:inputs` с указанием типов (`string`, `number`, `boolean`).
- Обязательные параметры имеют значения по умолчанию или `options` для ограничения выбора.
- Дочерний пайплайн проверен через **CI Lint** или Pipeline Editor.

**Стратегия и синхронизация:**
- Выбрана стратегия `strategy: mirror` для процессов, влияющих на релиз.
- В Bridge Job указан `environment` для отображения статуса деплоя в MR.
- Явно задан `allow_failure` для Bridge Job (не полагаться на значение по умолчанию).
- Установлен `timeout` для Bridge Job с запасом 20-30% от суммарного времени downstream.

**Структура:**
- Иерархия вложенности триггеров не превышает 2 уровней.
- Используются разные `tags` для Bridge Jobs и рабочих задач (предотвращение deadlock).
- Задачи с `interruptible: true` для downstream, которые могут быть безопасно отменены.
- Проверена доступность артефактов через `needs:project`.

### Распространенные ошибки

**Безопасность и доступ:**
- **Игнорирование Zero Trust:** Попытка запустить триггер в приватный проект без добавления инициатора в Allowlist (ошибка `403 Forbidden`). Решение: добавить проект-источник в `Settings > CI/CD > Token Access`.
- **Утечка маскированных секретов:** При передаче секретов через `trigger:variables` в другой проект свойство Masked может быть потеряно. Решение: использовать OIDC (`id_tokens`) или HashiCorp Vault.

**Параметризация:**
- **YAML Variable Overwrite:** Случайное переопределение системных переменных дочернего проекта из-за использования `forward: yaml_variables: true`. Решение: использовать уникальные префиксы или отключать `yaml_variables`.
- **Отсутствие валидации:** Передача пустых или некорректных строк через `trigger:variables` вместо использования строгих `inputs`. Решение: мигрировать на `spec:inputs`.
- **`inputs` ошибка при запуске:** Несоответствие типов (строка вместо числа). Решение: проверить `spec:inputs` дочернего пайплайна через Pipeline Lint.

**Стратегия и синхронизация:**
- **Bridge Job `success` при падении downstream:** Не указана стратегия (`mirror`/`depend`). Без стратегии Bridge Job всегда завершается `success` после запуска. Решение: добавить `strategy: mirror`.
- **`failed` вместо `canceled` при `depend`:** `depend` не различает `failed` и `canceled` — оба приводят к `failed` на родителе. Решение: мигрировать на `mirror`.
- **Статус `skipped` отображается как `success`:** Используется `depend` вместо `mirror`. `depend` аппроксимирует `skipped` -> `success`.

**Структура и ресурсы:**
- **Runner Deadlock:** Все слоты `concurrency` заняты Bridge Jobs при использовании `mirror`. Решение: увеличить `concurrency`, использовать разные теги или `fire and forget`.
- **`needs` + `trigger` конфликт:** Bridge Job не может иметь `needs`. Решение: убрать `needs` из задачи с `trigger` или перенести зависимость на уровень stages.
- **`circular reference detected`:** Кольцевая зависимость триггеров (A -> B -> A). Решение: разорвать цикл, использовать DAG с `needs` вместо вложенных триггеров.

## Мониторинг и рекомендации SRE

### Ключевые метрики

| Метрика | Описание | Целевое значение |
| :--- | :--- | :--- |
| **Bridge Job duration** | Время от запуска Bridge Job до получения финального статуса downstream. | Зависит от downstream |
| **Runner slot utilization** | Доля слотов Runner'а, занятых Bridge Jobs. | < 30% |
| **Deadlock incidents** | Количество ситуаций, когда все слоты заняты Bridge Jobs. | 0 |
| **Strategy distribution** | Соотношение `mirror`/`depend`/fire-and-forget. | `mirror` > 60% для критичных задач |
| **Manual approval wait time** | Среднее время ожидания ручного подтверждения. | Мониторьте для SLA |
| **Bridge Job timeout rate** | Доля Bridge Jobs, упавших по таймауту. | < 5% |

### Рекомендации SRE

1. **Стандартизируйте `mirror`** для всех критичных процессов (деплой, security, compliance). `depend` допустима только для legacy.
2. **Мониторьте concurrency** — настройте алерт при достижении > 80% использования слотов Runner'а.
3. **Используйте разные теги** для Bridge Jobs и рабочих задач для предотвращения deadlock.
4. **Устанавливайте `timeout`** явно для Bridge Job — не полагайтесь на значение по умолчанию (1ч).
5. **Документируйте стратегии** — ведите реестр какие проекты используют какую стратегию и почему.
6. **Тестируйте auto-cancel** — убедитесь, что `interruptible` настроен корректно для downstream-задач.
7. **Ревизия `depend`** — при наличии GitLab 18.6+ планируйте миграцию на `mirror`.
8. **Настройте `allow_failure`** явно — по умолчанию Bridge Job с `mirror` наследует `allow_failure: false` от родителя.
