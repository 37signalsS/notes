# Лучшие практики Downstream-пайплайнов

## Определения

**Best Practices (Лучшие практики)** — это набор проверенных архитектурных и технических подходов при проектировании Downstream-пайплайнов в GitLab CI/CD. Они направлены на повышение безопасности, прозрачности процессов и оптимизацию ресурсов инфраструктуры.

## Основные концепции

### Архитектурные принципы

- **Принцип наименьших привилегий (POLP):** Использование строго ограниченных разрешений для `CI_JOB_TOKEN` при межпроектном взаимодействии (введено в GitLab 18.0).
- **Типизация входных данных:** Предпочтение использования `inputs` вместо глобальных переменных для обеспечения контракта данных и ранней валидации (GitLab 17.7+).
- **Синхронность состояний:** Выбор корректной стратегии (`mirror` или `depend`) для обеспечения видимости результатов в родительском Merge Request.
- **Изоляция окружений:** Использование явной привязки к `environment` в заданиях-триггерах для корректного отслеживания деплоев.

### Ключевые инструменты управления

| Инструмент | Назначение | Рекомендация |
| :--- | :--- | :--- |
| **`spec:inputs`** | Типизированные параметры | Использовать для всех Parent-Child пайплайнов |
| **`strategy: mirror`** | Зеркалирование статуса | Рекомендуется для критических этапов деплоя (GitLab 18.2+) |
| **`needs:project`** | Передача артефактов | Нативный способ получения артефактов из Upstream вместо API |
| **`forward`** | Наследование переменных | Явное ограничение передачи переменных для безопасности |

## Практические сценарии

### Безопасность CI_JOB_TOKEN (GitLab 18.0+)

С версии 18.0 GitLab требует явного включения проектов в **Job Token Allowlist** для доступа к их ресурсам (API, контейнеры, пакеты).

**Рекомендация:**
1. В настройках проекта (`Settings > CI/CD > Token Access`) добавьте только необходимые Downstream-проекты.
2. Используйте **Fine-grained permissions** для ограничения прав токена (например, только `read_registry`).

### Передача артефактов через needs:project

Вместо использования `curl` и API-токенов для скачивания артефактов из родительского пайплайна, используйте встроенный механизм.

```yaml
# В Downstream-проекте
fetch-artifacts:
  stage: build
  needs:
    - project: 'group/upstream-project'
      job: 'build-assets'
      ref: $CI_COMMIT_REF_NAME
      artifacts: true
```

### Отображение деплоев в Upstream-проекте

Чтобы история развертываний отображалась в Merge Request родительского проекта, указывайте `environment` в задании-триггере.

```yaml
deploy-production:
  stage: deploy
  environment: production
  trigger:
    project: 'ops/deploy-project'
    strategy: mirror
```

### Версионирование шаблонов

Для стабильности CI/CD всегда фиксируйте версию подключаемого пайплайна через `ref`.

```yaml
trigger-child:
  trigger:
    include:
      - project: 'shared/ci-library'
        ref: 'v2.1.0'
        file: 'templates/docker-build.yml'
```

## Дополнительная информация

### Чеклист перед запуском в эксплуатацию

- [ ] Включена типизация через `spec:inputs` для валидации параметров.
- [ ] Использована стратегия `strategy: mirror` для отслеживания реального статуса.
- [ ] Настроен Allowlist для `CI_JOB_TOKEN` (для Multi-project).
- [ ] Указан `environment` для задач деплоя.
- [ ] Для Parent-Child глубина вложенности не превышает 2 уровней.
- [ ] Настроены корректные `timeout` для заданий-триггеров.

### Распространенные ошибки

- **Использование переменных для секретов:** Передача паролей и ключей через `trigger:variables` в Multi-project пайплайны. Секреты должны извлекаться напрямую в Downstream через Vault или AWS Secrets Manager.
- **Отсутствие стратегии:** Завершение Upstream-пайплайна до того, как Downstream реально начал работу, что ведет к «зеленым» пайплайнам при сломанном деплое.
- **Циклические зависимости:** Проектирование цепочек `A -> B -> A`, что приводит к бесконечным запускам и исчерпанию лимитов.
- **Игнорирование ограничений Runner:** Запуск сотен дочерних пайплайнов без учета количества доступных слотов на раннерах.
