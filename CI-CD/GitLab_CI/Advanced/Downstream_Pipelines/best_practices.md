# Лучшие практики Downstream-пайплайнов

## Определения

**Best Practices (Лучшие практики)** — это набор проверенных архитектурных и технических подходов при проектировании Downstream-пайплайнов в GitLab CI/CD. Они направлены на повышение безопасности, прозрачности процессов и оптимизацию ресурсов инфраструктуры.

## Основные концепции

### Архитектурные принципы

- **Принцип наименьших привилегий (POLP):** Использование строго ограниченных разрешений для `CI_JOB_TOKEN`. В GitLab 18.0+ введена модель **Zero Trust**, требующая наличия проекта-инициатора в **Inbound Allowlist** целевого проекта.
- **Типизация и контракты (GitLab 17.7+):** Использование `spec:inputs` для передачи параметров в триггеры. Это заменяет неявные глобальные переменные на явный API-контракт, обеспечивая валидацию до запуска пайплайна.
- **Синхронность и изоляция:** Выбор `strategy: mirror` для критических процессов (деплой, комплаенс) и асинхронного запуска для массовых фоновых задач, чтобы не блокировать слоты Runner'ов.
- **Предотвращение утечек (Data Leakage Control):** Использование `trigger:forward` для фильтрации переменных, предотвращая попадание чувствительных данных из родительского контекста в дочерние проекты.

### Ключевые инструменты управления

| Инструмент | Назначение | Рекомендация |
| :--- | :--- | :--- |
| **`spec:inputs`** | Типизированные параметры | Обязательно для всех Parent-Child и каталожных компонентов |
| **`strategy: mirror`** | Зеркалирование статуса | Для деплоя и агрегации Security Reports (v18.9+) |
| **`needs:project`** | Передача артефактов | Предпочтительнее API/curl (нативная интеграция, Zero Trust) |
| **`trigger:forward`** | Наследование переменных | Рекомендуется отключать `yaml_variables` по умолчанию |

## Практические сценарии

### Реализация модели Zero Trust (GitLab 18.0+)

Доступ одного проекта к ресурсам другого (через `CI_JOB_TOKEN`) теперь закрыт по умолчанию.

**Настройка доступа (Inbound Allowlist):**
1. В **целевом** проекте (который предоставляет артефакты или API) перейдите в `Settings > CI/CD > Token Access`.
2. Включите опцию "Limit access to this project".
3. Добавьте путь к **родительскому** (upstream) проекту в список разрешенных.
4. **Fine-grained permissions:** Укажите конкретные области доступа (например, только `read_registry` или `read_api`), если это поддерживается версией GitLab.

### Предотвращение утечки переменных (Forward Control)

Избегайте неявной передачи всех переменных родителя в дочерний пайплайн.

```yaml
# Пример безопасного триггера
secure-trigger:
  stage: test
  trigger:
    include: child.yml
    forward:
      yaml_variables: false     # Не передавать глобальные переменные этого файла
      pipeline_variables: true  # Передавать только переменные, заданные при запуске
```

### Передача артефактов через needs:project

Вместо использования `curl` и API-токенов для скачивания артефактов из родительского пайплайна, используйте встроенный механизм.

```yaml
# В Downstream-проекте
fetch-artifacts:
  stage: build
  needs:
    - project: 'group/upstream-project'
      job: 'build-assets'
      ref: $CI_COMMIT_REF_NAME
      artifacts: true
```

### Отображение деплоев в Upstream-проекте

Чтобы история развертываний отображалась в Merge Request родительского проекта, указывайте `environment` в задании-триггере.

```yaml
deploy-production:
  stage: deploy
  environment: production
  trigger:
    project: 'ops/deploy-project'
    strategy: mirror
```

### Версионирование шаблонов

Для стабильности CI/CD всегда фиксируйте версию подключаемого пайплайна через `ref`.

```yaml
trigger-child:
  trigger:
    include:
      - project: 'shared/ci-library'
        ref: 'v2.1.0'
        file: 'templates/docker-build.yml'
```

### Предотвращение Deadlock при массовых триггерах

При использовании `strategy: mirror` или `depend` родительское задание занимает слот Runner'а всё время ожидания.

**Опасный сценарий:**
У Runner'а лимит `concurrency: 10`. Пайплайн запускает матрицу из 10 заданий-триггеров с `strategy: mirror`. Все 10 слотов заняты ожиданием. Дочерние пайплайны не могут запуститься, так как нет свободных слотов. Возникает **Deadlock** (взаимная блокировка).

**Решение:**
1. Используйте асинхронный запуск (без `strategy`) для массовых задач.
2. Либо увеличьте лимит `concurrency` на Runner'ах.
3. Используйте разные теги (`tags`) для upstream и downstream задач.

## Дополнительная информация

### Технические лимиты и ограничения

- **Глубина вложенности (Recursion):** GitLab ограничивает вложенность Downstream-пайплайнов **2 уровнями** (Родитель -> Ребенок -> Внук). Попытка запустить 3-й уровень приведет к ошибке `downstream pipeline could not be created`.
- **Защита от циклов:** GitLab блокирует попытки триггера того же проекта с тем же `ref` и `commit SHA` для предотвращения бесконечных циклов.
- **Таймауты:** Помните, что время выполнения родительского задания-триггера должно превышать суммарное время дочернего пайплайна, иначе upstream упадет по таймауту, не дождавшись результата.

### Чеклист перед запуском в эксплуатацию

- [ ] Включена типизация через `spec:inputs` для валидации параметров.
- [ ] Использована стратегия `strategy: mirror` для отслеживания реального статуса.
- [ ] Настроен **Inbound Allowlist** для `CI_JOB_TOKEN` в целевых проектах.
- [ ] Указан `environment` для задач деплоя (для видимости в MR).
- [ ] Для Parent-Child глубина вложенности не превышает 2 уровней.
- [ ] Настроены корректные `timeout` (upstream > downstream).
- [ ] Оценена нагрузка на Runner'ы (риск Deadlock при использовании синхронных стратегий).

### Распространенные ошибки

- **Использование переменных для секретов:** Передача паролей и ключей через `trigger:variables` в Multi-project пайплайны. Секреты должны извлекаться напрямую в Downstream через Vault или AWS Secrets Manager.
- **Отсутствие стратегии:** Завершение Upstream-пайплайна до того, как Downstream реально начал работу, что ведет к «зеленым» пайплайнам при сломанном деплое.
- **Циклические зависимости:** Проектирование цепочек `A -> B -> A`, что приводит к блокировке или ошибкам валидации.
- **Игнорирование ограничений Runner:** Запуск сотен дочерних пайплайнов без учета количества доступных слотов на раннерах.
