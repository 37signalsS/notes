# Стратегии выполнения downstream-пайплайнов

## Определения

**Downstream-стратегия (Strategy)** — высокоуровневый параметр в ключевом слове `trigger`, связывающий жизненный цикл родительского (upstream) задания и запускаемого им пайплайна. Технически это механизм синхронизации состояний и агрегации метаданных (артефактов, отчетов) через внутреннюю шину событий GitLab.

## Основные концепции

### Стратегия mirror (Рекомендуемая)

**Назначение:** Полное зеркалирование (High Fidelity) состояния downstream-пайплайна в родительское задание. Введена в **GitLab 18.6** как стандарт для Enterprise-инсталляций.

**Технические нюансы:**
- **Точность статусов:** В отличие от `depend`, стратегия `mirror` пробрасывает *любой* финальный статус. Если downstream пропущен (`skipped`) или ожидает действия (`manual`), родительское задание примет ровно этот же статус.
- **Auto-cancel Propagation:** Поддерживает двустороннюю отмену. При отмене родительского пайплайна downstream также останавливается, и наоборот.
- **Агрегация отчётов (GitLab 18.9+):** Позволяет родительскому Merge Request отображать результаты тестов (JUnit) и безопасности (SAST/DAST/SBOM) из дочерних процессов в реальном времени.
- **Матричные Downstream:** Если downstream запускается через `parallel:matrix`, `mirror` будет ждать завершения *всех* инстансов матрицы перед установкой финального статуса.

```yaml
# Пример использования зеркалирования
trigger_job:
  trigger:
    include: child-pipeline.yml
    strategy: mirror
```

### Стратегия depend (Legacy)

**Назначение:** Базовое ожидание завершения. Считается устаревшей (Legacy) для новых проектов после появления `mirror`.

**Особенности и ограничения:**
- **Неточные статусы:** Часто интерпретирует специфические состояния (`skipped`, `manual`) как `success` или `blocked` на стороне родителя, что мешает корректной работе `rules` и `needs` в последующих стадиях.
- **Упрощенная агрегация:** Работает только для стандартных JUnit отчетов; расширенная поддержка Security Dashboard в MR может работать нестабильно.

### Fire and Forget (Асинхронный запуск)

Если параметр `strategy` не указан, GitLab использует асинхронную модель.

**Поведение:**
- Родительское задание переходит в статус `success` сразу после того, как downstream-пайплайн успешно поставлен в очередь.
- **Минус:** Ошибки в downstream не блокируют родительский пайплайн.
- **Плюс:** Мгновенное освобождение ресурсов Runner'а в upstream.

## Практические сценарии

### Настройка для тестов и безопасности

Для полного соблюдения комплаенса и отображения уязвимостей в интерфейсе родительского MR необходимо использовать `mirror`.

```yaml
test-and-scan:
  stage: test
  trigger:
    include: tests-and-security.yml
    strategy: mirror
  allow_failure: false # Ошибка в downstream заблокирует деплой
```

### Мультипроектный деплой с ожиданием

Когда важно, чтобы основной пайплайн (например, сборка артефакта) не завершился, пока не отработает деплой в инфраструктурном проекте.

```yaml
deploy-infrastructure:
  stage: deploy
  trigger:
    project: 'ops/terraform-deploy'
    branch: main
    strategy: mirror
```

## Дополнительная информация

### Сравнение стратегий

| Характеристика | Без стратегии | `strategy: depend` | `strategy: mirror` |
| :--- | :---: | :---: | :---: |
| **Ожидание завершения** | Нет | Да | Да |
| **Синхронизация статуса** | Нет | Частично | **Полная** |
| **Агрегация отчётов** | Нет | Да | **Да** |
| **Поддержка Auto-cancel** | Нет | Ограниченно | **Да** |
| **Слот Runner'а** | **Освобождается** | Занят | **Занят** |
| **Рекомендуемая версия** | Любая | Legacy | **>= 18.6** |

### Управление ресурсами и Runner'ами

Использование `mirror` или `depend` создает **синхронную зависимость** между пайплайнами, что накладывает ограничения на инфраструктуру:

1.  **Оккупация слотов:** Upstream-задание остается в статусе `running` всё время, пока выполняется downstream. Это означает, что оно занимает лимит конкурентности (concurrency) вашего Runner'а.
2.  **Риск Deadlock:** Если лимит Runner'а (например, 10 слотов) полностью занят upstream-заданиями, которые ждут свои downstream-пайплайны, а те не могут запуститься из-за отсутствия свободных слотов — возникает "зависание" всей очереди.
3.  **Рекомендация:** Для массовых запусков (матричные триггеры) используйте Runner'ы с высоким лимитом `concurrency` или асинхронную модель (без `strategy`), если синхронизация статуса не критична.
