# Динамическая генерация дочерних пайплайнов

**Актуально для:** GitLab 18.6+ / 19.x

## Определения

**Динамическая генерация пайплайнов** — это продвинутый паттерн проектирования CI/CD, при котором конфигурация пайплайна (`.gitlab-ci.yml`) не является статическим файлом в репозитории, а создаётся программно во время выполнения родительского (upstream) задания.

Технически этот процесс реализуется через механизм **Trigger by Artifact**:
- Родительское задание генерирует YAML или JSON файл.
- Файл сохраняется как артефакт.
- Последующее задание-триггер (Bridge Job) считывает этот артефакт и инициирует создание дочернего пайплайна на основе его содержимого.

## Архитектура и жизненный цикл

Процесс динамического запуска интегрирован во внутреннюю шину событий GitLab и проходит следующие этапы:

1.  **Этап генерации (Generation Stage):**
     - Выполняется на стандартном Runner'е.
     - Скрипт (Python, Go, Node.js или Bash) собирает необходимые данные (состояние инфраструктуры, список измененных файлов, метаданные из внешних систем конфигурирования).
    - Результат записывается в файл (обычно `generated-ci.yml`).
2.  **Этап сохранения (Persistence):**
    - Генерируемый файл объявляется в секции `artifacts:paths`. Это критически важно: без этого Bridge Job не сможет получить доступ к конфигурации.
3.  **Этап инициации (Bridge Job):**
    - Задание с директивой `trigger:include:artifact` ссылается на созданный файл.
    - GitLab Rails парсит артефакт, проверяет его валидность и создает дочерний пайплайн.
    - Если используется `strategy: mirror`, родительское задание ждет завершения дочернего процесса.

## Технические лимиты и ограничения

-   **Размер конфигурации:** Максимальный размер сгенерированного файла (включая все вложенные `include`) составляет **5 МБ**.
-   **Глубина вложенности:** Лимит триггеров — **2 уровня** (Родитель -> Ребенок -> Внук). Попытка инициировать 3-й уровень через динамический артефакт приведет к ошибке валидации.
-   **Валидация:** Ошибки синтаксиса в сгенерированном файле не останавливают задачу-генератор, но приводят к падению задачи-триггера со статусом `Downstream pipeline could not be created`.
-   **Reporting (GitLab 18.9+):** Динамические пайплайны полностью поддерживают агрегацию Security Reports (SAST, DAST, SBOM) и JUnit тестов в родительский Merge Request при использовании `strategy: mirror`.
-   **Контекст выполнения:** Дочерний пайплайн наследует `ref` и `commit SHA` родителя, но работает в изолированном пространстве имен переменных, если не настроен `trigger:forward`.

## Безопасность и YAML Injection

При генерации YAML-файлов из строк (особенно при обработке пользовательского ввода или имен веток) существует критический риск **YAML Injection** — внедрения вредоносного кода в структуру пайплайна.

**Опасный сценарий (Bad Practice):**
```python
# ОПАСНО: риск инъекции через job_name, если в нем есть символ новой строки
f.write(f"{job_name}:\n  script: echo 'Start'")
```

**Рекомендованные меры безопасности:**
1.  **Использование типизированных входов (`spec:inputs`):** Генерируйте статическую логику с блоком спецификации и передавайте данные через триггер. Это гарантирует валидацию типов до начала выполнения скриптов.
2.  **Сериализация (JSON/YAML):** Никогда не формируйте файл через конкатенацию строк. Используйте `json.dumps()` (Python/Node.js) или `yaml.safe_dump()` (PyYAML). GitLab нативно поддерживает JSON как формат конфигурации.
3.  **Экранирование:** Если генерация идет через Bash, используйте `printf %q` для безопасного экранирования строк.

## Практические сценарии

### Сценарий 1: Использование Python и Jinja2 (Паттерн шаблонизации)

Наиболее гибкий метод для создания сложных, масштабируемых структур.

**1. Шаблон Jinja2 (`pipeline.j2`):**
```jinja
spec:
  inputs:
    target_env:
      default: 'development'
---
{% for service in services %}
deploy-{{ service.name }}:
  stage: deploy
  script:
    - echo "Деплой {{ service.name }} на порт {{ service.port }} в окружение $[[ inputs.target_env ]]"
  environment: $[[ inputs.target_env ]]
{% endfor %}
```

**2. Генератор (`generate_pipeline.py`):**
```python
from jinja2 import Template
import json

# Данные могут быть получены из API или БД
data = {
    "services": [
        {"name": "auth", "port": 8080},
        {"name": "gateway", "port": 3000},
        {"name": "worker", "port": 9000}
    ]
}

with open("pipeline.j2", "r") as f:
    template = Template(f.read())

with open("generated-config.json", "w") as f:
    # Генерируем JSON, так как он проще в отладке и безопаснее
    f.write(template.render(data))
```

**3. Родительский пайплайн (`.gitlab-ci.yml`):**
```yaml
generate-job:
  stage: build
  script:
    - python3 generate_pipeline.py
  artifacts:
    paths: [generated-config.json]

trigger-dynamic:
  stage: deploy
  trigger:
    include:
      - artifact: generated-config.json
        job: generate-job
    inputs:
      target_env: "production"
    strategy: mirror
```

### Сценарий 2: Селективный CI для монорепозитория

Автоматическое создание пайплайна только для измененных компонентов.

```yaml
generate-changes-config:
  stage: .pre
  script:
    - # Получаем список измененных директорий первого уровня
    - CHANGED_DIRS=$(git diff --name-only $CI_COMMIT_BEFORE_SHA...$CI_COMMIT_SHA | cut -d/ -f1 | sort -u)
    - python3 scripts/generate_from_changes.py "$CHANGED_DIRS"
  artifacts:
    paths: [generated-pipeline.yml]

trigger-changes:
  stage: test
  trigger:
    include:
      - artifact: generated-pipeline.yml
        job: generate-changes-config
    strategy: mirror
```

### Сценарий 3: Динамические матрицы (Dynamic Parallel Matrix)

Создание задач на основе динамического списка инфраструктурных узлов или сервисов.

```python
import json

datacenters = ["dc-eu-1", "dc-eu-2", "dc-ap-1", "dc-am-1"]
config = {
    "infra-audit": {
        "parallel": {
            "matrix": [{"DATACENTER": datacenters}]
        },
        "script": ["ansible-playbook -i inventory-$DATACENTER.yml audit.yml"]
    }
}
print(json.dumps(config))
```

## Диагностика и устранение неполадок

### Типичные ошибки

| Ошибка | Возможная причина | Решение |
| :--- | :--- | :--- |
| `Downstream pipeline could not be created` | Ошибка синтаксиса в сгенерированном файле. | Проверьте файл через `cat` в логах и скопируйте в CI Lint. |
| `Artifact not found` | Файл не объявлен в `artifacts:paths` или задача-генератор упала. | Проверьте секцию `artifacts` и статус задачи-генератора. |
| `Grandchild pipeline limit exceeded` | Попытка запустить триггер внутри динамического пайплайна, который уже является дочерним. | Используйте плоскую структуру или API-вызовы для глубокой вложенности. |
| `YAML injection detected` | Использование недопустимых конструкций или попытка обхода безопасности. | Перейдите на генерацию через `json.dumps()`. |

### Инструменты отладки

1.  **Инспекция артефактов:** Всегда скачивайте сгенерированный файл из интерфейса GitLab, чтобы увидеть итоговый вид конфигурации.
2.  **Логирование:** Добавляйте `cat generated-file.yml` в конец скрипта генерации для быстрого просмотра в консоли Runner'а.
3.  **GitLab CLI (`glab`):** Валидация сгенерированного файла локально: `glab ci lint generated-config.yml`.

## Best Practices для динамической генерации

### Управление артефактами

- **Версионирование генераторов:** Храните скрипты и шаблоны генерации в отдельной директории с явным версионированием. Это позволяет откатить изменения при проблемах с динамической конфигурацией.
- **Ограничение размера:** Контролируйте размер сгенерированного файла на этапе генерации. Превышение 5 МБ приведет к ошибке валидации downstream-пайплайна.
- **Retention policies:** Настройте срок хранения артефактов с динамическими конфигурациями через `artifacts:expire_in`. Это предотвращает переполнение хранилища и снижает риск использования устаревших конфигураций.
- **Изоляция артефактов:** Для каждого downstream-проекта используйте уникальные имена артефактов. Общие имена артефактов при параллельных пайплайнах могут привести к конфликтам.

### Безопасность генерации

- **Принцип наименьших привилегий для генератора:** Задача-генератор должна иметь только права на запись артефактов. Не давайте ей доступ к секретам, если они не требуются для формирования конфигурации.
- **Аудит шаблонов:** Ведите историю изменений для всех Jinja2/шаблонных файлов. Изменения в шаблонах должны проходить code review, так как они влияют на конфигурацию пайплайнов.
- **Запрет на динамический импорт:** Не используйте пользовательский ввод для загрузки внешних шаблонов или модулей во время генерации. Это предотвращает supply-chain атаки через компрометацию внешних источников.
- **Валидация типов на выходе:** После генерации JSON/YAML выполняйте проверку схемы перед сохранением артефакта. Ошибки на этом этапе дешевле, чем падение downstream-пайплайна.

## Анализ преимуществ и рисков

| Характеристика | Преимущества | Риски и недостатки |
| :--- | :--- | :--- |
| **Гибкость** | Адаптация пайплайна под любые внешние условия «на лету». | Высокий порог входа, сложность отладки. |
| **Оптимизация** | Запуск только необходимых задач, экономия ресурсов Runner'ов. | Риск **Deadlock** при использовании синхронных стратегий. |
| **Поддержка** | Сокращение объема статического YAML-кода. | Зависимость от работоспособности внешних скриптов и библиотек. |

## Edge Cases и известные проблемы

- **Артефакт перезаписан параллельным пайплайном:** При одновременном запуске двух upstream-пайплайнов артефакт с одинаковым именем может быть перезаписан. Решение: используйте уникальные имена артефактов, включающие `$CI_PIPELINE_ID` или `$CI_COMMIT_SHA`.
- **Генератор завершился успешно, но артефакт пуст:** Ошибка логики в скрипте генерации может создать пустой файл, который проходит валидацию. Решение: добавляйте проверку размера файла в скрипт генерации (`test -s generated-config.yml || exit 1`).
- **Устаревший артефакт из кэша GitLab:** При повторном запуске пайплайна GitLab может использовать кэшированный артефакт вместо свежего. Решение: добавляйте уникальный идентификатор в имя артефакта или используйте `dependencies` явно.
- **`trigger:include:artifact` с некорректным `job`:** Если имя задачи-генератора указано неверно, Bridge Job завершится ошибкой `Artifact not found`. Решение: проверяйте имя задачи через API или интерфейс GitLab.
- **YAML Injection через пользовательский ввод:** Ветки с именами, содержащими символы новой строки или управляющие последовательности YAML, могут сломать структуру сгенерированного файла. Решение: санитизируйте все внешние данные перед записью в YAML/JSON.
- **Секреты в логах генерации:** Если генератор использует секреты для формирования конфигурации, они могут попасть в логи Runner'а. Решение: используйте `masked` переменные или `id_tokens` и никогда не выводите секреты в stdout.

### SRE: Инцидент-респонс

При расследовании инцидента, связанного с динамической генерацией:

1. Проверьте статус задачи-генератора:
   ```bash
   curl --header "PRIVATE-TOKEN: $TOKEN" \
     "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/pipelines/$PIPELINE_ID/jobs?scope=success" | \
     jq '.[] | select(.name | startswith("generate")) | {id, name, status, finished_at}'
   # → {"id": 101, "name": "generate-changes-config", "status": "success", "finished_at": "2026-09-28T10:00:00Z"}
   ```

2. Скачайте и inspect артефакт через API:
   ```bash
   curl --header "PRIVATE-TOKEN: $TOKEN" \
     "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/jobs/$JOB_ID/artifacts/generated-pipeline.yml" | \
     head -n 50
   # → Первые 50 строк сгенерированного файла
   ```

3. Валидируйте сгенерированный файл:
   ```bash
   curl --request POST \
     --header "PRIVATE-TOKEN: $TOKEN" \
     --header "Content-Type: application/json" \
     --data '{"content": "'"$(cat generated-pipeline.yml | sed 's/\"/\\\"/g')"'"}' \
     "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/ci/lint" | \
     jq '.status, .errors'
   # → "valid", []
   ```

4. При массовом падении динамических пайплайнов проверьте:
   - Логи задачи-генератора на наличие ошибок сериализации.
   - Целостность шаблонов Jinja2 в репозитории.
   - Состояние хранилища артефактов GitLab.

5. Документируйте паттерн инцидента: какой генератор сломался, какая версия шаблона, какие данные на входе привели к некорректной генерации.

### Compliance и аудит

- **Версионирование шаблонов:** Все шаблоны Jinja2 и скрипты генерации должны храниться в репозитории с включенным аудитом изменений (GitLab audit events). Любое изменение, влияющее на пайплайны, требует approval merge request.
- **Артефакт как артефакт compliance:** Сгенерированные `.gitlab-ci.yml` файлы являются артефактами с высоким уровнем критичности. Настройте retention policies и защиту от удаления через `artifacts:protected: true`.
- **Аудит входных данных:** Если генератор использует данные из внешних API, документируйте источник и формат данных. Регулярно проверяйте, что внешние системы не возвращают неожиданные значения.
- **Сегрегация duties:** Разделите права на изменение шаблонов (DevOps team) и права на запуск пайплайнов (CI/CD). Это предотвращает несанкционированную модификацию логики пайплайнов.

### Очистка и откат

- **Откат шаблона:** При проблемах с динамической генерацией откатите измененный шаблон или скрипт генерации к последней рабочей версии через Git. Это безопаснее, чем редактирование артефактов вручную.
- **Очистка артефактов:** Удалите устаревшие артефакты через интерфейс GitLab или API, чтобы предотвратить использование сломанных конфигураций. Проверяйте `artifacts:expire_in` для задач-генераторов.
- **Отключение динамической генерации:** Для экстренного отключения используйте `rules: []` в задаче-триггере. Это сохранит историю изменений и позволит быстро вернуть генерацию при восстановлении.
- **Валидация после отката:** После отката шаблона проверяйте Pipeline Lint и запускайте тестовый пайплайн перед возвратом в production.

### Disaster Recovery

- **Резервное копирование шаблонов:** Храните шаблоны и скрипты генерации в отдельном репозитории или в subtree основного репозитория. Это позволяет восстановить генерацию при потере ветки.
- **Fallback на статический конфиг:** Подготовьте статический `.gitlab-ci.yml` fallback, который запускается, когда динамическая генерация недоступна. Используйте `rules` для автоматического переключения при ошибках генерации.
- **Восстановление артефактов:** При сбое хранилища артефактов (self-managed) динамические пайплайны не смогут получить конфигурацию. Восстановите хранилище и перезапустите задачи-генераторы.
- **Аварийный запуск без артефактов:** Если артефакт недоступен, подготовьте inline-конфигурацию для критичных пайплайнов, чтобы минимизировать downtime.

### Self-managed инсталляции

- **Хранилище артефактов:** Убедитесь, что object storage (или локальный диск) для артефактов настроен с репликацией. Потеря артефактов означает невозможность запуска downstream-пайплайнов.
- **Мониторинг Sidekiq:** Задачи создания downstream-пайплайнов обрабатываются через Sidekiq. Мониторьте очередь `create_downstream_pipeline` на задержки. При высокой нагрузке увеличьте количество воркеров.
- **Резервное копирование базы данных:** Метаданные артефактов и пайплайнов хранятся в PostgreSQL. Регулярно выполняйте backup и проверяйте целостность связей `ci_builds`, `ci_artifacts` и `ci_pipelines`.
- **Резервные Runner'ы:** Для задач-генераторов настройте Runner'ы с высокой доступностью. Если генератор не может выполниться, downstream-пайплайн не запустится.
- **Версионирование GitLab:** Использование `trigger:include:artifact` с JSON-конфигурациями требует GitLab 17.0+. Агрегация Security Reports для динамических пайплайнов работает с GitLab 18.9+ только при `strategy: mirror`.
