# Конструктор рабочих процессов GitLab CI/CD

## Определения

**Рабочий процесс (Workflow/Pipeline)** — это логическая последовательность стадий и задач, описывающая жизненный цикл сборки, тестирования и развертывания ПО. В GitLab CI/CD пайплайны строятся из модульных блоков:

- **`stages` и `jobs`**: Скелет пайплайна. Определяют *что* делать и в какой *очередности*. Подробные определения — в **[Основах GitLab CI/CD](../Concepts/gitlab_ci_basics.md)**.
- **`artifacts`**: Файлы и отчеты, передаваемые между стадиями. См. **[Артефакты в GitLab CI](./gitlab_ci_caching/gitlab_ci_artifacts.md)**.
- **`cache`**: Инструмент для сохранения зависимостей (`node_modules`, `.m2`) между запусками. См. **[Обзор кэширования](./gitlab_ci_caching/caching_overview.md)**.
- **`needs`**: Директива для создания **DAG (Directed Acyclic Graph)**, позволяющая запускать задачи сразу после готовности их зависимостей.
- **`rules`**: Условия включения задач в пайплайн на основе переменных, изменений файлов или событий.

## Основные концепции

### Построение логики выполнения

Эффективный рабочий процесс опирается на правильное распределение задач и управление зависимостями:

1. **Линейная модель (Stages)**: Порядок выполнения задается списком `stages`. Каждая стадия запускается только после успешного завершения всех задач предыдущей.
2. **Графовая модель (DAG/needs)**: Использование `needs` позволяет задачам игнорировать границы стадий и запускаться немедленно. Это критично для ускорения пайплайнов, где тесты не зависят от всех этапов сборки.
3. **Глобальное управление (`workflow:rules`)**: Позволяет фильтровать запуск всего пайплайна целиком (например, запрет запуска для WIP-коммитов).

### Передача данных и отчетность

Для взаимодействия между задачами и интеграции результатов в интерфейс GitLab используются специализированные типы артефактов:

- **Передача файлов**: Основной способ передачи бинарных файлов и пакетов между стадиями.
- **Отчеты (`artifacts:reports`)**: Позволяют GitLab визуализировать результаты тестов, покрытия кода и безопасности непосредственно в Merge Request.
- **Переменные окружения (`artifacts:dotenv`)**: Механизм для динамической передачи переменных (например, ID деплоя или версии) между задачами через `.env`-файлы.

### Оптимизация и DRY

- **Кэширование**: Сохраняет временные данные для ускорения повторных запусков. В отличие от артефактов, кэш не гарантирует наличие данных.
- **Переиспользование**: Использование `extends`, `!reference` и `include` позволяет строить сложные пайплайны из небольших, тестируемых блоков. См. **[Переиспользование пайплайнов](../Reusable_Pipelines/overview.md)**.

## Практические сценарии

### Сценарий 1: Ускорение через DAG (`needs`)

Пример, где тесты фронтенда запускаются сразу после его сборки, не дожидаясь окончания долгой сборки бэкенда.

```yaml
stages:
  - build
  - test

build:frontend:
  stage: build
  script: npm run build
  artifacts:
    paths: [dist/frontend/]

build:backend:
  stage: build
  script: sleep 300 && ./build_heavy_binary.sh # Долгая задача

test:frontend:
  stage: test
  needs: ["build:frontend"] # Запустится сразу, как завершится build:frontend
  script: npm test
```

### Сценарий 2: Интеграция отчетов о тестах и покрытии

Использование современного синтаксиса для отображения результатов в MR.

```yaml
test:job:
  stage: test
  script:
    - pytest --junitxml=junit.xml --cov=app --cov-report=xml
  artifacts:
    reports:
      junit: junit.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
```

### Сценарий 3: Динамическая передача переменных через `dotenv`

Создание переменных в одной задаче и их использование в последующих.

```yaml
setup:version:
  stage: .pre
  script:
    - echo "DEPLOY_ID=$(date +%s)" > build.env
  artifacts:
    reports:
      dotenv: build.env

deploy:app:
  stage: deploy
  script:
    - echo "Deploying version $DEPLOY_ID"
  dependencies:
    - setup:version
```

### Сценарий 4: Условный запуск для монорепозиториев

Запуск тестов только при изменении файлов в соответствующей директории.

```yaml
test:ui:
  stage: test
  rules:
    - changes:
        - "ui/**/*"
  script:
    - cd ui && npm test
```

## Дополнительная информация

- **CI Lint**: Всегда проверяйте синтаксис через инструмент Lint в Editor пайплайнов GitLab.
- **Отладка**: Используйте `when: always` для сохранения логов и артефактов при падении задач.
- **Безопасность**: Используйте `secret_detection` и никогда не передавайте секреты через артефакты.
