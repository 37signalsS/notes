# Конструктор рабочих процессов GitLab CI/CD

## Определения

**Рабочий процесс (Workflow/Pipeline)** — это логическая последовательность стадий и задач, описывающая жизненный цикл сборки, тестирования и развертывания ПО. В GitLab CI/CD пайплайны строятся из модульных блоков:

- **`stages` и `jobs`**: Скелет пайплайна. Определяют *что* делать и в какой *очередности*. Подробные определения — в **[Основах GitLab CI/CD](../Concepts/gitlab_ci_basics.md)**.
- **`artifacts`**: Файлы и отчеты, передаваемые между стадиями. См. **[Артефакты в GitLab CI](./gitlab_ci_caching/gitlab_ci_artifacts.md)**.
- **`cache`**: Инструмент для сохранения зависимостей (`node_modules`, `.m2`) между запусками. См. **[Обзор кэширования](./gitlab_ci_caching/caching_overview.md)**.
- **`needs`**: Директива для создания **DAG (Directed Acyclic Graph)**, позволяющая запускать задачи сразу после готовности их зависимостей.
- **`rules`**: Условия включения задач в пайплайн на основе переменных, изменений файлов или событий.
- **`include` и `extends`**: Механизмы переиспользования кода. `include` позволяет подключать внешние YAML-файлы или компоненты, `extends` — наследовать конфигурацию задач. См. **[Обзор переиспользуемых пайплайнов](../Reusable_Pipelines/overview.md)**.
- **`trigger`**: Запуск зависимых (downstream) пайплайнов в других проектах или дочерних пайплайнов в текущем. См. **[Родительско-дочерние пайплайны](./Downstream_Pipelines/parent_child_pipelines.md)**.

## Философия конструктора

### Базовые блоки конструктора
1.  **Jobs (Задачи)**: Независимые единицы работы в изолированных контейнерах.
2.  **Stages (Стадии)**: Группы параллельных задач.
3.  **Artifacts (Артефакты)**: Результаты сборки, передаваемые дальше.
4.  **Cache (Кэш)**: Временные данные для ускорения повторных запусков.
5.  **Components (Компоненты)**: Современные, версионируемые блоки логики из **[CI/CD Catalog](../Reusable_Pipelines/ci_cd_catalog_components.md)**.

### Принципы проектирования
-   **Атомарность**: Одна задача — одна ответственность (отдельно билд, отдельно тест, отдельно деплой). Избегайте огромных скриптов в одной задаче.
-   **Изоляция**: Каждая задача выполняется в "свежем" контейнере. Обмен данными — только через артефакты или кэш.
-   **Fail Fast**: Проверки (линтеры, тесты) должны быть в самом начале, чтобы не тратить ресурсы на заведомо ошибочные пайплайны.
-   **DRY (Don't Repeat Yourself)**: Используйте шаблоны, `extends` и компоненты для исключения дублирования YAML-кода.
-   **Версионируемость**: При использовании внешних шаблонов всегда фиксируйте версию (commit SHA или tag), чтобы изменения в шаблонах не "сломали" рабочий пайплайн неожиданно.

## Передача данных и отчетность

### Артефакты vs Кэш: когда что использовать

Выбор между артефактами и кэшем зависит от цели передачи данных. Артефакты гарантированно доставляют результаты сборки между стадиями, тогда как кэш ускоряет последующие запуски за счет переиспользования зависимостей.

Подробное техническое сравнение, уровни хранения и стратегии оптимизации — в **[Обзоре кэширования и артефактов](./gitlab_ci_caching/caching_overview.md)**.

**Рекомендация:** Всегда используйте `expire_in` для артефактов (например, `1h` или `1 week`), чтобы автоматически очищать старые сборки и экономить место в хранилище проекта.

### Переменные окружения (Variables)

Переменные обеспечивают динамику и гибкость конструктора:
-   **Predefined Variables**: Автоматические переменные GitLab (`CI_COMMIT_SHA`, `CI_PIPELINE_ID`).
-   **Custom Variables**: Задаются в интерфейсе (Settings -> CI/CD -> Variables).
-   **Protected**: Доступны только в защищенных ветках/тегах.
-   **Masked**: Скрываются в логах (для паролей и токенов).

**Интеграция с Vault**: Для хранения критичных секретов (конфиги K8s, API-ключи) рекомендуется использовать внешние хранилища типа **HashiCorp Vault**. это позволяет избежать "секретов в секретах" и централизованно управлять доступом.

## Оптимизация и производительность

### Кэширование зависимостей
Правильное кэширование (например, для Node.js) может сократить время сборки в 3 и более раз (с 15 минут до 5). Кэш привязывается к проекту и ключу (например, хэш `package-lock.json`).

### Динамическая передача переменных через `dotenv`
Используется для передачи данных, которые становятся известны только во время выполнения задачи (например, версия образа или ID деплоя).

```yaml
setup:version:
  stage: .pre
  script:
    - echo "IMAGE_TAG=v1.2.$CI_PIPELINE_I" > build.env
  artifacts:
    reports:
      dotenv: build.env
```

## Продвинутые строительные блоки

### Матричные сборки (`parallel:matrix`)
Позволяют запускать одну задачу несколько раз с разными комбинациями переменных. Идеально для тестирования разных версий языков или платформ.

```yaml
test:matrix:
  stage: test
  parallel:
    matrix:
      - PROVIDER: [aws, gcp, azure]
        STACK: [dev, prod]
  script:
    - deploy_to $PROVIDER --env $STACK
```

### Управление окружениями (`environment`)
Связывает задачу с конкретной средой развертывания, позволяя отслеживать историю деплоев в UI GitLab.

- **`url`**: Ссылка на развернутое приложение.
- **`on_stop`**: Задача для очистки окружения (например, удаление Review App).
- **`auto_stop_in`**: Время жизни временного окружения.

### Группы ресурсов (`resource_group`)
Используются для сериализации выполнения задач. Если несколько пайплайнов пытаются запустить деплой на один и тот же сервер, `resource_group` гарантирует, что они будут выполняться строго по очереди, предотвращая конфликты.

### Опциональные зависимости (`needs:optional`)
Начиная с **GitLab 17.4**, директива `needs` поддерживает флаг `optional: true`. Это позволяет задаче зависеть от другой задачи, которая может быть не включена в текущий пайплайн (например, из-за `rules`).

## Практические сценарии

### Сценарий 1: Ускорение через DAG (`needs`)

Пример, где тесты фронтенда запускаются сразу после его сборки, не дожидаясь окончания долгой сборки бэкенда.

```yaml
stages:
  - build
  - test

build:frontend:
  stage: build
  script: npm run build
  artifacts:
    paths: [dist/frontend/]

build:backend:
  stage: build
  script: sleep 300 && ./build_heavy_binary.sh # Долгая задача

test:frontend:
  stage: test
  needs: ["build:frontend"] # Запустится сразу, как завершится build:frontend
  script: npm test
```

### Сценарий 2: Интеграция отчетов о тестах и покрытии

Использование современного синтаксиса для отображения результатов в MR.

```yaml
test:job:
  stage: test
  script:
    - pytest --junitxml=junit.xml --cov=app --cov-report=xml
  artifacts:
    reports:
      junit: junit.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
```

### Сценарий 3: Динамическая передача переменных через `dotenv`

Создание переменных в одной задаче и их использование в последующих.

```yaml
setup:version:
  stage: .pre
  script:
    - echo "DEPLOY_ID=$(date +%s)" > build.env
  artifacts:
    reports:
      dotenv: build.env

deploy:app:
  stage: deploy
  script:
    - echo "Deploying version $DEPLOY_ID"
  dependencies:
    - setup:version
```

### Сценарий 4: Условный запуск для монорепозиториев

Запуск тестов только при изменении файлов в соответствующей директории.

```yaml
test:ui:
  stage: test
  rules:
    - changes:
        - "ui/**/*"
  script:
    - cd ui && npm test
```

### Сценарий 5: Матричное тестирование на разных версиях Node.js

```yaml
test:node:
  image: node:$NODE_VERSION
  parallel:
    matrix:
      - NODE_VERSION: ['18', '20', '22']
  script:
    - npm install
    - npm test
```

### Сценарий 6: Запуск дочернего пайплайна с передачей параметров (GitLab 18.0)

Использование `spec:inputs` для типизированной передачи параметров в дочерний пайплайн.

```yaml
trigger_deploy:
  stage: deploy
  trigger:
    include:
      - local: path/to/child-ci.yml
    inputs:
      env: production
      version: $CI_COMMIT_SHORT_SHA
```

## Дополнительная информация

- **CI Lint**: Всегда проверяйте синтаксис через инструмент Lint в Editor пайплайнов GitLab. Он показывает финальный "смерженный" YAML со всеми включенными файлами.
- **Отладка**: Используйте `when: always` для сохранения логов и артефактов при падении задач.
- **Безопасность**:
  - Используйте `secret_detection` для автоматического поиска ключей в коде.
  - **Никогда** не передавайте секреты через артефакты (они доступны для скачивания).
  - Используйте **Masked Variables** или интеграцию с **HashiCorp Vault**.
- **Pipeline Execution Policies**: Современный способ принудительного выполнения проверок (например, безопасности) на уровне группы, заменяющий устаревшие Compliance Pipelines.
- **GitLab Duo**: Используйте AI-помощника для генерации конфигураций `.gitlab-ci.yml` и объяснения сложных ошибок в логах.
