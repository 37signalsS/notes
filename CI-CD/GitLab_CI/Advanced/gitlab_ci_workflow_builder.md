# Конструктор рабочих процессов GitLab CI

## Определения

В GitLab CI/CD рабочие процессы (пайплайны) строятся из базовых строительных блоков:

- **`stages`** и **`jobs`**: Основные элементы, определяющие последовательность этапов и конкретные задачи. Подробные определения — в **[Основах GitLab CI/CD](../Concepts/gitlab_ci_basics.md)**.
- **`artifacts`**: Механизм сохранения и передачи результатов выполнения между задачами. Подробнее см. в **[Артефактах в GitLab CI](../Advanced/gitlab_ci_caching/gitlab_ci_artifacts.md)**.
- **`cache`**: Инструмент для ускорения повторных сборок за счет сохранения временных данных. Подробнее см. в **[Кэшировании в GitLab CI](../Advanced/gitlab_ci_caching/caching_overview.md)**.

## Основные концепции

### Построение логики выполнения

Эффективный рабочий процесс опирается на правильное распределение задач по стадиям и управление зависимостями между ними.

- **Последовательность стадий**: Порядок выполнения задается списком `stages`. Каждая следующая стадия запускается только после успешного завершения всех задач предыдущей.
- **Параллельное выполнение**: Все задачи (`jobs`) внутри одной стадии запускаются одновременно, если доступны свободные Runner'ы.
- **Управление сбоями**: По умолчанию провал любой задачи останавливает выполнение всех последующих стадий пайплайна.

### Передача данных и отчетность

Для взаимодействия между задачами и интеграции результатов в интерфейс GitLab используются специализированные типы артефактов:

- **Передача файлов**: Артефакты являются единственным надежным способом передачи результатов сборки (бинарные файлы, пакеты) между стадиями.
- **Отчеты (`artifacts:reports`)**: Позволяют GitLab анализировать результаты тестов, покрытия кода и безопасности, отображая их непосредственно в Merge Request.
- **Переменные окружения (`artifacts:dotenv`)**: Механизм для динамической передачи переменных (например, версии сборки или ID инфраструктуры) между задачами на разных стадиях через `.env`-файлы.

### Оптимизация сборок

Кэширование используется для сохранения зависимостей проекта (`node_modules`, `.m2`, `venv`) между разными запусками пайплайнов. В отличие от артефактов, кэш не гарантирует наличие данных и не предназначен для передачи критических результатов сборки.

## Практические сценарии

### Сценарий 1: Передача артефактов между стадиями

Пример сборки приложения на стадии `build` и передачи скомпилированного файла на стадию `test`.

```yaml
stages:
  - build
  - test

build_app:
  stage: build
  script:
    - echo "Building the application..."
    - echo "my-app-binary" > my-app
  artifacts:
    paths:
      - my-app

test_app:
  stage: test
  script:
    - echo "Testing the application..."
    - cat my-app
  dependencies:
    - build_app
```

### Сценарий 2: Интеграция отчетов о тестах и покрытии

Использование `artifacts:reports` для визуализации результатов тестирования в интерфейсе GitLab.

```yaml
test_job:
  stage: test
  script:
    - run_tests.sh # Генерирует junit-report.xml и coverage.xml
  artifacts:
    reports:
      junit: junit-report.xml
      cobertura: coverage.xml
```

### Сценарий 3: Динамическая передача переменных через `dotenv`

Создание переменных в одной задаче и их использование в последующих.

```yaml
stages:
  - setup
  - deploy

setup_job:
  stage: setup
  script:
    - echo "DEPLOY_VERSION=1.2.3" > build.env
  artifacts:
    reports:
      dotenv: build.env

deploy_job:
  stage: deploy
  script:
    - echo "Deploying version $DEPLOY_VERSION"
  dependencies:
    - setup_job
```
