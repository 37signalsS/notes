# Конструктор рабочих процессов GitLab CI

## Определения

- **`stages`**: Высокоуровневая последовательность этапов пайплайна (например, `build`, `test`, `deploy`). Задания внутри одного этапа выполняются параллельно.
- **`jobs`**: Конкретные задачи, выполняемые Runner'ами. Каждое задание привязано к этапу и содержит инструкции для выполнения.
- **`artifacts`**: Механизм сохранения результатов выполнения задания (бинарные файлы, отчёты) и передачи их между заданиями на разных этапах и Runner'ах.
- **`cache`**: Механизм кэширования файлов (зависимости, временные файлы) между запусками пайплайнов для ускорения сборок.

## Основные концепции

### Поток выполнения

- Порядок `stages` определяет логику пайплайна: переход к следующему этапу происходит после успешного завершения всех заданий текущего.
- Все `jobs` внутри одного `stage` запускаются параллельно (при наличии свободных Runner'ов).
- При провале хотя бы одного `job` в `stage` пайплайн по умолчанию останавливается.

### Передача данных: `artifacts`

Артефакты — гарантированный способ передачи данных между `jobs`. Они сохраняются на сервере GitLab после успешного завершения задания и доступны для скачивания из UI и последующих заданий.

**Специализированные типы артефактов:**

- **`artifacts:reports`**: Интеграция отчетов в интерфейс GitLab (тесты, покрытие кода, уязвимости).
- **`artifacts:dotenv`**: Передача переменных окружения между `jobs` через `.env`-файл.

### Ускорение сборок: `cache`

Кэш ускоряет повторные запуски пайплайнов за счет сохранения файлов (`node_modules`, `.m2`) между `jobs`.

- **Отличие от артефактов:** Кэш не гарантирует сохранность данных. Основная цель — ускорение, а не передача критических результатов.
- **Область видимости:** Кэш может быть общим для всех пайплайнов проекта.
- **Подробнее:** см. документ [Кэширование и артефакты в GitLab CI/CD](./gitlab_ci_caching.md).

### Практические сценарии

#### Сценарий 1: Передача артефактов между стадиями

Этот пример показывает, как собрать приложение на стадии `build` и передать скомпилированный бинарный файл на стадию `test`.

```yaml
stages:
  - build
  - test

build_app:
  stage: build
  script:
    - echo "Building the application..."
    - echo "my-app-binary" > my-app
  artifacts:
    paths:
      - my-app # Сохраняем файл 'my-app' как артефакт

test_app:
  stage: test
  script:
    - echo "Testing the application..."
    - cat my-app # Файл 'my-app' автоматически загружен и доступен
  dependencies:
    - build_app # Явно указываем, что это задание зависит от артефактов 'build_app'
```

#### Сценарий 2: Интеграция отчетов о тестах и покрытии

Здесь `artifacts:reports` используется для загрузки в GitLab отчетов о результатах тестов (`junit`) и покрытии кода (`cobertura`), что позволяет видеть их прямо в интерфейсе Merge Request.

```yaml
test_job:
  stage: test
  script:
    - run_tests.sh # Этот скрипт генерирует junit-report.xml и coverage.xml
  artifacts:
    reports:
      junit: junit-report.xml
      cobertura: coverage.xml
```

#### Сценарий 3: Передача переменных окружения с помощью `dotenv`

Задание `setup_job` создает файл `build.env` и объявляет его `dotenv` артефактом. Переменные из этого файла (`MY_VARIABLE`) автоматически становятся доступны в последующих заданиях, таких как `deploy_job`.

```yaml
stages:
  - setup
  - deploy

setup_job:
  stage: setup
  script:
    - echo "MY_VARIABLE=hello-world" > build.env
    - echo "ANOTHER_VAR=123" >> build.env
  artifacts:
    reports:
      dotenv: build.env

deploy_job:
  stage: deploy
  script:
    - echo "Deploying with MY_VARIABLE=$MY_VARIABLE" # Выведет "Deploying with MY_VARIABLE=hello-world"
    - echo "ANOTHER_VAR is $ANOTHER_VAR" # Выведет "ANOTHER_VAR is 123"
  dependencies:
    - setup_job # Указываем зависимость от задания, создающего dotenv артефакт
```
