# Конструктор рабочих процессов GitLab CI/CD

## Определения

**Рабочий процесс (Workflow/Pipeline)** — это логическая последовательность стадий и задач, описывающая жизненный цикл сборки, тестирования и развертывания ПО. В GitLab CI/CD пайплайны строятся из модульных блоков:

- **`stages` и `jobs`**: Скелет пайплайна. Определяют *что* делать и в какой *очередности*. Подробные определения — в **[Основах GitLab CI/CD](../Concepts/gitlab_ci_basics.md)**.
- **`artifacts`**: Файлы и отчеты, передаваемые между стадиями. См. **[Артефакты в GitLab CI](./gitlab_ci_caching/gitlab_ci_artifacts.md)**.
- **`cache`**: Инструмент для сохранения зависимостей (`node_modules`, `.m2`) между запусками. См. **[Обзор кэширования](./gitlab_ci_caching/caching_overview.md)**.
- **`needs`**: Директива для создания **DAG (Directed Acyclic Graph)**, позволяющая запускать задачи сразу после готовности их зависимостей.
- **`rules`**: Условия включения задач в пайплайн на основе переменных, изменений файлов или событий.

## Философия конструктора

### Базовые блоки конструктора
1.  **Jobs (Задачи)**: Независимые единицы работы в изолированных контейнерах.
2.  **Stages (Стадии)**: Группы параллельных задач.
3.  **Artifacts (Артефакты)**: Результаты сборки, передаваемые дальше.
4.  **Cache (Кэш)**: Временные данные для ускорения повторных запусков.

### Принципы проектирования
-   **Атомарность**: Одна задача — одна ответственность (отдельно билд, отдельно тест, отдельно деплой). Избегайте огромных скриптов в одной задаче.
-   **Изоляция**: Каждая задача выполняется в "свежем" контейнере. Обмен данными — только через артефакты или кэш.
-   **Fail Fast**: Проверки (линтеры, тесты) должны быть в самом начале, чтобы не тратить ресурсы на заведомо ошибочные пайплайны.

## Передача данных и отчетность

### Артефакты vs Кэш: когда что использовать

| Характеристика | Артефакты (Artifacts) | Кэш (Cache) |
| :--- | :--- | :--- |
| **Цель** | Передача результатов между стадиями | Ускорение сборки (зависимости) |
| **Надежность** | **Максимальная** (хранятся на сервере GitLab) | Не гарантирована (может отсутствовать) |
| **Доступность** | Всем последующим задачам пайплайна | Только задачам с тем же ключом кэша |
| **Влияние на квоты** | Занимают место в хранилище проекта | Обычно не влияют на квоты хранилища |
| **Примеры** | `.jar`, `.zip`, бинарные файлы, отчеты | `node_modules`, `.m2/repository`, кэш Gradle |

**Рекомендация:** Используйте `expire_in` для артефактов (например, `1h` или `1 week`), чтобы автоматически очищать старые сборки и экономить место.

### Переменные окружения (Variables)

Переменные обеспечивают динамику и гибкость конструктора:
-   **Predefined Variables**: Автоматические переменные GitLab (`CI_COMMIT_SHA`, `CI_PIPELINE_ID`).
-   **Custom Variables**: Задаются в интерфейсе (Settings -> CI/CD -> Variables).
-   **Protected**: Доступны только в защищенных ветках/тегах.
-   **Masked**: Скрываются в логах (для паролей и токенов).

**Интеграция с Vault**: Для хранения критичных секретов (конфиги K8s, API-ключи) рекомендуется использовать внешние хранилища типа **HashiCorp Vault**. это позволяет избежать "секретов в секретах" и централизованно управлять доступом.

## Оптимизация и производительность

### Кэширование зависимостей
Правильное кэширование (например, для Node.js) может сократить время сборки в 3 и более раз (с 15 минут до 5). Кэш привязывается к проекту и ключу (например, хэш `package-lock.json`).

### Динамическая передача переменных через `dotenv`
Используется для передачи данных, которые становятся известны только во время выполнения задачи (например, версия образа или ID деплоя).

```yaml
setup:version:
  stage: .pre
  script:
    - echo "IMAGE_TAG=v1.2.$CI_PIPELINE_I" > build.env
  artifacts:
    reports:
      dotenv: build.env
```

## Практические сценарии

### Сценарий 1: Ускорение через DAG (`needs`)

Пример, где тесты фронтенда запускаются сразу после его сборки, не дожидаясь окончания долгой сборки бэкенда.

```yaml
stages:
  - build
  - test

build:frontend:
  stage: build
  script: npm run build
  artifacts:
    paths: [dist/frontend/]

build:backend:
  stage: build
  script: sleep 300 && ./build_heavy_binary.sh # Долгая задача

test:frontend:
  stage: test
  needs: ["build:frontend"] # Запустится сразу, как завершится build:frontend
  script: npm test
```

### Сценарий 2: Интеграция отчетов о тестах и покрытии

Использование современного синтаксиса для отображения результатов в MR.

```yaml
test:job:
  stage: test
  script:
    - pytest --junitxml=junit.xml --cov=app --cov-report=xml
  artifacts:
    reports:
      junit: junit.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
```

### Сценарий 3: Динамическая передача переменных через `dotenv`

Создание переменных в одной задаче и их использование в последующих.

```yaml
setup:version:
  stage: .pre
  script:
    - echo "DEPLOY_ID=$(date +%s)" > build.env
  artifacts:
    reports:
      dotenv: build.env

deploy:app:
  stage: deploy
  script:
    - echo "Deploying version $DEPLOY_ID"
  dependencies:
    - setup:version
```

### Сценарий 4: Условный запуск для монорепозиториев

Запуск тестов только при изменении файлов в соответствующей директории.

```yaml
test:ui:
  stage: test
  rules:
    - changes:
        - "ui/**/*"
  script:
    - cd ui && npm test
```

## Дополнительная информация

- **CI Lint**: Всегда проверяйте синтаксис через инструмент Lint в Editor пайплайнов GitLab.
- **Отладка**: Используйте `when: always` для сохранения логов и артефактов при падении задач.
- **Безопасность**: Используйте `secret_detection` и никогда не передавайте секреты через артефакты.
