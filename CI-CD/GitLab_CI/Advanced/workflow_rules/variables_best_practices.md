# Переменные и лучшие практики CI/CD

## Определения

- **Встроенные переменные (Predefined Variables):** Динамические значения, автоматически внедряемые GitLab в среду выполнения задачи (контекст коммита, ветки, пайплайна).
- **Входные параметры (spec:inputs):** (GitLab 17.0+) Декларативный интерфейс конфигурации с поддержкой типов (`string`, `number`, `boolean`, `array`). В отличие от переменных, они интерполируются на этапе компиляции YAML, что делает их более надежными для шаблонов.
- **Маскированные переменные (Masked Variables):** Механизм фильтрации вывода логов. Требуют соблюдения определенных форматов (Base64, отсутствие пробелов) для корректной работы регулярных выражений маскировщика.
- **Environment Scoped Variables:** Переменные, доступность которых ограничена конкретным окружением (`environment: name`).

## Базовые концепции

В 2026 году (GitLab 19.x) парадигма управления данными в CI/CD окончательно перешла от "глобальных неявных строк" к **архитектуре с явными контрактами** через `spec:inputs`.

### Эволюция управления данными

1. **Этап 1 (Legacy):** Использование глобальных переменных на уровне проекта. Риск: случайное переопределение, отсутствие документации.
2. **Этап 2 (Intermediate):** Наследование через `extends` и `!reference`. Улучшение DRY, но отсутствие валидации.
3. **Этап 3 (Modern):** Использование **CI/CD Components** и `spec:inputs`. Полная типизация, автоматическая документация и изоляция контекста.

### Ограничение области видимости (Scoping)

Для обеспечения безопасности и предотвращения ошибок конфигурации используйте следующие механизмы:

- **Environment Scope:** Переменные для `production` не должны быть доступны в `staging`. Это настраивается в интерфейсе GitLab при создании переменной.
- **Protected Scoping:** Устанавливайте флаг `Protected`, чтобы переменная была доступна только в защищенных ветках (`main`, `stable`).
- **Input Interpolation (17.7+):** Вы можете использовать значения одних входов для формирования других:
  ```yaml
  spec:
    inputs:
      project_name:
      image_tag:
        default: "$[[ inputs.project_name ]]-latest"
  ```

## Практические сценарии

### Сценарий 1: Управление жизненным циклом через workflow

Использование `workflow:rules` совместно с `auto_cancel` позволяет экономить ресурсы и предотвращать конфликты.

```yaml
workflow:
  auto_cancel:
    on_new_commit: interruptible
    on_job_failure: all
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - when: never
```

**Рекомендации:**
- **Используйте fail-fast:** `on_job_failure: all` немедленно останавливает весь пайплайн при ошибке в любой задаче.
- **Защищайте деплои:** Для задач развертывания всегда устанавливайте `interruptible: false`, чтобы автоотмена не прервала процесс посередине.

### Сценарий 2: Типизация входных данных в шаблонах

Создание надежных переиспользуемых компонентов с использованием `spec:inputs`.

```yaml
spec:
  inputs:
    deploy_env:
      type: string
      default: staging
      options: [staging, production]
    replicas:
      type: number
      default: 2
---
deploy_task:
  script:
    - ./deploy.sh --env $[[ inputs.deploy_env ]] --count $[[ inputs.replicas ]]
```

**Сценарий 3: Безопасное использование секретов**

Отказ от долгоживущих токенов в пользу динамической аутентификации и строгого контроля прав.

**Рекомендации:**

-   **OIDC/JWT:** Используйте `id_tokens` для аутентификации в облачных провайдерах (AWS, GCP) или Vault. Это устраняет необходимость хранения статических `AWS_ACCESS_KEY_ID` в переменных проекта.
-   **Ограничение прав (GitLab 19.2+):** Включите настройку "Minimum role to use pipeline variables" на уровне **Maintainer**. Это предотвращает несанкционированное использование секретов разработчиками с низкими привилегиями через кастомные пайплайны.
-   **Маскирование секретов:** Всегда включайте опцию `Mask variable` для токенов и паролей. Помните о лимитах: значения менее 8 символов или содержащие спецсимволы, ломающие логи, могут не маскироваться корректно.

## Дополнительная информация

### Приоритет переменных (GitLab 19.x)

При конфликте имен GitLab соблюдает строгую иерархию (от высшего к низшему):

1.  **Trigger variables:** Переменные, переданные через API или Web UI при ручном запуске.
2.  **Scheduled variables:** Переменные из расписания (Schedules).
3.  **Job variables:** Блок `variables` внутри конкретной задачи.
4.  **Workflow variables:** Блок `variables` внутри `workflow:rules`.
5.  **Pipeline Inputs:** Значения из `spec:inputs` (интерполированные через `[[ inputs.name ]]`).
6.  **Project variables:** Переменные, заданные в настройках проекта (`Settings > CI/CD > Variables`).
7.  **Group variables:** Переменные, заданные на уровне группы.
8.  **Instance variables:** Переменные, заданные администратором всего инстанса.
9.  **Predefined variables:** Встроенные переменные GitLab (`CI_*`).
10. **Default variables:** Блок `variables` внутри секции `default`.

### Лучшие практики (Do's and Don'ts)

| Действие | Рекомендация | Почему? |
| :--- | :--- | :--- |
| **Do** | Использовать `spec:inputs` | Обеспечивает валидацию типов и явный интерфейс для шаблонов. |
| **Do** | Ограничивать область видимости | Используйте `environment: name` в переменных проекта для защиты продакшена. |
| **Don't** | Передавать секреты в CLI | Значения переменных видны в логах, если они не замаскированы. Используйте файлы (`type: file`). |
| **Don't** | Злоупотреблять глобальными `variables` | Глобальные переменные загромождают контекст и могут быть случайно переопределены. |
