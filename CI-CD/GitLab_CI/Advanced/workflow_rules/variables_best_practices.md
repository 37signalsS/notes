# Переменные и лучшие практики CI/CD

## Определения

- **Встроенные переменные (Predefined Variables):** Переменные, автоматически предоставляемые GitLab (контекст коммита, ветки, пайплайна). Основной инструмент для `rules` и `workflow`.
- **Входные параметры (spec:inputs):** (версия 17.0+) Декларативный способ описания интерфейса пайплайна с поддержкой типов данных и валидации. Рекомендуемая альтернатива классическим переменным для шаблонов и компонентов.
- **Маскированные переменные (Masked Variables):** Секреты, значения которых скрываются в логах выполнения задач.

## Базовые концепции

В 2026 году (GitLab 19.x) подход к управлению данными в пайплайнах сместился от "свободных строк" к строго типизированным и проверяемым входным данным.

### Ключевые переменные управления

| Переменная | Назначение | Примеры значений |
| :--- | :--- | :--- |
| `$CI_PIPELINE_SOURCE` | Источник триггера | `push`, `merge_request_event`, `schedule`, `api` |
| `$CI_COMMIT_BRANCH` | Текущая ветка | `main`, `feature/auth-fix` |
| `$CI_MERGE_REQUEST_IID` | ID запроса на слияние | Используется для условий `rules:if` в MR |
| `$CI_COMMIT_REF_PROTECTED` | Статус защиты ветки | `true` (для защищенных веток) |
| `$CI_DEFAULT_BRANCH` | Главная ветка проекта | Обычно `main` |

### Переход на явные входные параметры (spec:inputs)

Вместо использования глобальных переменных, которые могут быть случайно перезаписаны, используйте `spec:inputs` в начале файла. Это обеспечивает:
- **Валидацию типов:** (string, number, boolean).
- **Ограничение значений:** через параметр `options`.
- **Безопасность:** переменные не "утекают" в дочерние пайплайны без явного проброса.

## Практические сценарии

### Сценарий 1: Управление жизненным циклом через workflow

Использование `workflow:rules` совместно с `auto_cancel` позволяет экономить ресурсы и предотвращать конфликты.

```yaml
workflow:
  auto_cancel:
    on_new_commit: interruptible
    on_job_failure: all
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
    - when: never
```

**Рекомендации:**
- **Используйте fail-fast:** `on_job_failure: all` немедленно останавливает весь пайплайн при ошибке в любой задаче.
- **Защищайте деплои:** Для задач развертывания всегда устанавливайте `interruptible: false`, чтобы автоотмена не прервала процесс посередине.

### Сценарий 2: Типизация входных данных в шаблонах

Создание надежных переиспользуемых компонентов с использованием `spec:inputs`.

```yaml
spec:
  inputs:
    deploy_env:
      type: string
      default: staging
      options: [staging, production]
    replicas:
      type: number
      default: 2
---
deploy_task:
  script:
    - ./deploy.sh --env $[[ inputs.deploy_env ]] --count $[[ inputs.replicas ]]
```

### Сценарий 3: Безопасное использование секретов

Отказ от долгоживущих токенов в пользу динамической аутентификации.

**Рекомендации:**
- **OIDC/JWT:** Используйте `id_tokens` для аутентификации в AWS, GCP или Vault без сохранения статических паролей в переменных.
- **Ограничение прав:** В настройках проекта (v19.2+) включите ограничение "Minimum role to use pipeline variables" на уровень **Maintainer**, чтобы разработчики использовали только валидированные `spec:inputs`.

## Дополнительная информация

### Приоритет переменных

При конфликте имен GitLab соблюдает иерархию (от высшего к низшему):
1. Переменные, заданные вручную при запуске (API/Web UI).
2. Переменные в блоке `job:variables`.
3. Переменные в блоке `workflow:rules:variables`.
4. Входные параметры `spec:inputs`.
5. Переменные проекта и группы.
