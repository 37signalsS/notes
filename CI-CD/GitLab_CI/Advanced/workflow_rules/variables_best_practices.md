# Переменные и лучшие практики

## Определения

**Встроенные переменные CI/CD** — предопределённые переменные, автоматически предоставляемые GitLab в каждом пайплайне. В контексте управления рабочими процессами они являются основным инструментом для принятия решений в директивах `rules` и `workflow`.

Подробное описание типов переменных: [Переменные и секреты GitLab CI](../../Concepts/gitlab_ci_variables_secrets.md).

## Основные концепции

Для эффективного управления потоком выполнения (workflow) используются переменные, описывающие контекст запуска пайплайна.

### Ключевые переменные для управления пайплайном

| Переменная | Описание | Пример |
| :--- | :--- | :--- |
| `$CI_PIPELINE_SOURCE` | Источник запуска | `push`, `merge_request_event`, `schedule`, `api`, `web` |
| `$CI_COMMIT_BRANCH` | Ветка коммита | `main`, `feature/my-feature` |
| `$CI_MERGE_REQUEST_TARGET_BRANCH_NAME` | Целевая ветка Merge Request (MR) | `main`, `develop` |
| `$CI_COMMIT_TAG` | Тег Git | `v1.2.3` |
| `$CI_OPEN_MERGE_REQUESTS` | Список открытых MR для данного коммита | `group/project!123` |
| `$CI_COMMIT_REF_PROTECTED` | Флаг защищённой ветки или тега | `true`, `false` |
| `$CI_DEFAULT_BRANCH` | Ветка по умолчанию для проекта | `main`, `master` |

Полный список: [Predefined variables](https://docs.gitlab.com/ee/ci/variables/predefined_variables.html).

## Практические сценарии

### Сценарий 1: Оптимизация глобального управления пайплайном

Использование `workflow:rules` позволяет избежать дублирования пайплайнов (например, при пуше в ветку с открытым MR) и централизованно управлять логикой запуска.

**Рекомендации:**
- **Используйте `workflow:rules` вместо `only/except`**: Директивы `only/except` считаются устаревшими. `workflow:rules` предоставляет более гибкий механизм.
- **Соблюдайте порядок правил**: GitLab использует первое совпадение. Специфичные условия (например, для `main`) должны идти перед общими.
- **Избегайте дублирования**: Если пайплайн отфильтрован на уровне `workflow`, не дублируйте ту же проверку в `rules` каждой задачи.

### Сценарий 2: Монорепозитории и ускорение обратной связи

В сложных проектах важно минимизировать время выполнения пайплайна, запуская только необходимые проверки.

**Рекомендации:**
- **Используйте `rules:changes`**: В монорепозиториях это позволяет запускать сборку и тесты только для изменённых компонентов.
- **Стройте DAG с `needs`**: Директива `needs` позволяет задачам запускаться сразу после завершения зависимостей, не дожидаясь окончания всей стадии (stage). Это критично для быстрых тестов и линтеров. Подробно: [DAG с использованием needs](./dag_with_needs.md).

### Сценарий 3: Безопасное развёртывание и масштабирование

Управление параллелизмом и безопасностью при деплое в различные окружения.

**Рекомендации:**
- **Защита от гонок с `resource_group`**: Гарантирует, что в один момент времени выполняется только один деплой в конкретное окружение. Подробнее: [Матричные сборки и сериализация](./matrix_builds_and_serialization.md).
- **Матричные сборки с `parallel:matrix`**: Позволяют тестировать код на множестве версий или архитектур без дублирования кода задач. Подробнее: [Матричные сборки и сериализация](./matrix_builds_and_serialization.md).
- **Использование `spec:inputs`**: Для параметризации пайплайнов и компонентов (GitLab 17+) используйте типизированные входные данные вместо обычных переменных окружения для повышения безопасности и валидации.

## Дополнительная информация

### Безопасность и переиспользование

- **Аутентификация через OIDC**: Для доступа к облачным провайдерам (AWS, GCP, Azure) используйте временные токены (OIDC/JWT) вместо долгоживущих секретов. Подробнее: [OIDC аутентификация](https://docs.gitlab.com/ee/ci/secrets/authenticate_with_oidc.html).
- **Компоненты GitLab**: Для создания переиспользуемых блоков CI/CD-логики используйте каталог компонентов (GitLab 17+).
