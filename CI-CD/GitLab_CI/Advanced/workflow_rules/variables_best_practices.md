# Переменные и Best Practices

## Определения

**Встроенные переменные CI/CD** — предопределённые переменные, автоматически предоставляемые GitLab в каждом пайплайне. Используются для управления потоком работ и доступа к метаданным.

## Основные концепции

**Ключевые переменные для workflow:**

| Переменная | Описание | Пример |
| :--- | :--- | :--- |
| `$CI_PIPELINE_SOURCE` | Источник запуска | `push`, `merge_request_event`, `schedule`, `api`, `web` |
| `$CI_COMMIT_BRANCH` | Ветка коммита | `main`, `feature/my-feature` |
| `$CI_MERGE_REQUEST_TARGET_BRANCH_NAME` | Целевая ветка MR | `main`, `develop` |
| `$CI_COMMIT_TAG` | Тег | `v1.2.3` |
| `$CI_OPEN_MERGE_REQUESTS` | Открытые MR | `group/project!123` |
| `$CI_COMMIT_REF_PROTECTED` | Защищённая ветка | `true`, `false` |
| `$CI_DEFAULT_BRANCH` | Default branch | `main`, `master` |

Полный список: [Predefined variables](https://docs.gitlab.com/ee/ci/variables/predefined_variables.html).

## Рекомендации и лучшие практики

- **Используйте `workflow:rules` вместо `only/except`**. Директивы `only/except` считаются устаревшими. `workflow:rules` предоставляет более гибкий и мощный механизм для управления жизненным циклом пайплайнов.

- **Соблюдайте порядок правил**. GitLab проверяет правила последовательно и использует первое совпадение. Размещайте более специфичные правила перед общими. Завершайте список правилом `when: never` для предотвращения нежелательных запусков.

- **Избегайте дублирования логики**. Если пайплайн фильтруется на глобальном уровне с помощью `workflow:rules`, не дублируйте ту же логику в `rules` на уровне задач. Это упрощает конфигурацию и снижает риск ошибок.

- **Оптимизируйте пайплайны в монорепозиториях с `changes`**. Для ускорения работы в монорепозиториях используйте `rules:changes`, чтобы запускать задачи только тогда, когда изменяются связанные компоненты.
  > **Примечание:** `changes` не работает в `workflow:rules`, только на уровне задач (`job:rules`).

- **Ускоряйте пайплайны с помощью DAG и `needs`**. Для построения эффективных пайплайнов используйте направленные ациклические графы (DAG) с директивой `needs`. Это позволяет запускать независимые задачи параллельно, не дожидаясь завершения всей стадии. Подробно: [DAG с `needs`](./dag_with_needs.md).

- **Предотвращайте гонки состояний при развертывании с `resource_group`**. Чтобы гарантировать, что в любой момент времени выполняется только одна задача по развертыванию в определенное окружение (например, `production`), используйте `resource_group`. Подробнее: [сериализация развертываний](./matrix_builds_and_serialization.md).

- **Расширяйте тестовое покрытие с помощью `parallel:matrix`**. Для тестирования кода на совместимость с различными версиями ПО, архитектурами или окружениями используйте матричные сборки. Это позволяет избежать дублирования кода и упрощает поддержку тестовых сценариев. Подробнее: [матричные сборки](./matrix_builds_and_serialization.md).

- **Используйте `spec:inputs` для параметризации пайплайнов (GitLab 17+)**. Вместо переменных окружения для передачи параметров в пайплайн используйте типизированные входные данные. Это обеспечивает валидацию, явное описание и повышенную безопасность.

- **Повышайте безопасность с OIDC-аутентификацией**. Для аутентификации в облачных провайдерах (AWS, GCP, Azure) используйте временные JWT-токены (`$CI_JOB_JWT_V2_TOKEN` или `$CI_JOB_JWT_TOKEN`) вместо статичных долгоживущих секретов. Подробнее: [Workload Identity Federation](https://docs.gitlab.com/ee/ci/secrets/authenticate_with_oidc.html).

- **Переиспользуйте конфигурацию с помощью компонентов GitLab (GitLab 17+)**. Для создания переиспользуемых и легко поддерживаемых блоков CI/CD-логики используйте компоненты. Они позволяют инкапсулировать логику и использовать типизированные входы для настройки. Подробнее: [GitLab CI/CD Components](https://docs.gitlab.com/ee/ci/components/).
