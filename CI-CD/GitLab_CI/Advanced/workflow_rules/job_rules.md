# Правила запуска задач (rules)

## Определения

`rules` — рекомендуемый способ контроля запуска отдельных задач. Правила проверяются по порядку (first match), первое совпадение определяет поведение задачи.

**Поддерживаемые ключи и их технические детали:**
- `if`: Логические выражения на основе переменных. Поддерживают сравнение (`==`, `!=`), регулярные выражения (`=~`, `!~`) и логические операторы (`&&`, `||`). Оценка происходит в момент создания пайплайна.
- `changes`: Запуск при изменении конкретных файлов.
  - `paths`: Массив путей (glob-паттерны).
  - `compare_to`: Базовая ветка или коммит для сравнения. С версии GitLab 17.2 поддерживает использование CI/CD переменных (например, `compare_to: '$TARGET_BRANCH'`), что критически важно для монорепозиториев и MR-пайплайнов.
- `exists`: Запуск при наличии файлов в репозитории. Раскрытие переменных в путях работает корректно, включая слэши (улучшено в GitLab 17.3+).
  - `paths`: Массив путей к файлам.
  - `project` (GitLab 17.0+): Позволяет проверять существование файла в *другом* проекте.
  - `ref` (GitLab 17.0+): Позволяет проверять существование файла на конкретной ветке или теге.
- `when`: Режим запуска задачи при совпадении правила (`on_success`, `manual`, `never`, `always`, `on_failure`, `delayed`).
- `start_in`: Время задержки (например, `3 hours`, `10 minutes`) используется *только* в связке с `when: delayed`.
- `allow_failure`: Управление критичностью ошибки. Может принимать булево значение (`true`/`false`) или блок `exit_codes` (массив кодов, например `[137, 255]`) для игнорирования специфических кодов завершения скрипта.
- `variables`: Переопределение переменных окружения специально для конкретного сработавшего правила. Имеет приоритет над глобальными переменными, но ниже ручного запуска.
- `needs`: Динамическое переопределение зависимостей (DAG). Позволяет подменять массив родительских задач (артефактов) в зависимости от сработавшего условия (GitLab 16.0+).

## Основные концепции

По умолчанию задачи запускаются согласно разделу `stages`. Директива `rules` переопределяет это поведение:

- Задача включается в пайплайн только при совпадении правила.
- Если ни одно правило не совпало — задача исключается.
- `when: never` в начале списка правил позволяет явно блокировать запуск в нежелательных условиях.

**Динамические зависимости (rules:needs):**
Позволяет менять список родительских задач в зависимости от условий (например, на ветке `main` ждать сборку артефакта, а на feature-ветке — нет).

### Ограничение: видимость переменных

Правила `rules` вычисляются в момент создания пайплайна. Это означает:
1. Переменные из других задач (через `artifacts:reports:dotenv`) **недоступны** в блоке `rules`.
2. Переменные, созданные в `script`, не влияют на выполнение правил.
3. Доступны только предопределённые переменные GitLab (`CI_*`), переменные проекта, группы и переменные, переданные при триггере.

```yaml
# ОШИБКА: переменная из другой job недоступна в rules
next_job:
  rules:
    - if: '$UPSTREAM_VERSION == "1.0"' # $UPSTREAM_VERSION не будет видна здесь
```

## Практические сценарии

**Запуск только для Merge Request:**

```yaml
test_job:
  stage: test
  script:
    - npm run test
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
```

**Запуск для MR в определённую ветку:**

```yaml
test_mr_to_main:
  script:
    - npm run test
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event" && $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"'
```

**Запуск при изменении файлов (монорепозитории):**

```yaml
# Запуск только при изменении frontend-кода
test_frontend:
  script:
    - npm run test
  rules:
    - changes:
        - "frontend/**/*"
        - "package.json"
        - "pnpm-lock.yaml"

# Запуск только при изменении backend-кода
test_backend:
  script:
    - pytest
  rules:
    - changes:
        - "backend/**/*"
        - "requirements.txt"
```

**Точное отслеживание изменений (compare_to):**
В монорепозиториях важно сравнивать изменения не только с текущим коммитом, но и с базовой веткой (особенно для новых веток).

```yaml
test_component:
  rules:
    - changes:
        paths:
          - "component/**/*"
        compare_to: 'refs/heads/main' # сравнение с main
```

**Динамические зависимости (needs):**
Разный набор зависимых задач для разных веток.

```yaml
deploy:
  rules:
    - if: '$CI_COMMIT_BRANCH == "main"'
      needs: ["build_prod", "test_all"]
    - if: '$CI_COMMIT_BRANCH != "main"'
      needs: ["build_dev"] # более быстрый путь для разработчиков
```

**Условная обработка ошибок (exit_codes):**
Продолжать выполнение, если задача упала с определённым кодом.

```yaml
optional_scan:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "push"'
      allow_failure:
        exit_codes:
          - 137 # OOM или специфический код сканера
```

**Комбинированное правило для деплоя:**

```yaml
deploy_job:
  stage: deploy
  script:
    - ./deploy.sh
  rules:
    # Автоматический деплой для main
    - if: '$CI_COMMIT_BRANCH == "main"'
      when: on_success
    # Ручной деплой для staging
    - if: '$CI_COMMIT_BRANCH == "staging"'
      when: manual
    # Запрет для остальных веток
    - when: never
```

**Проверка файлов во внешнем репозитории (GitLab 17.0+):**
Полезно для централизованных шаблонов, проверяющих наличие манифестов стандартов безопасности или специфических конфигураций.
```yaml
compliance_check:
  script: echo "Checking compliance..."
  rules:
    - exists:
        paths: ["security-policy.yaml"]
        project: "org/security-standards"
        ref: "main"
      when: always
    - when: never
```

**Динамическое сравнение ветки в монорепозитории (GitLab 17.2+):**
Использование переменных в `compare_to` позволяет гибко настраивать логику `changes` для разных веток, что критично для ускорения CI.
```yaml
test_frontend:
  script: npm run test
  rules:
    - changes:
        paths: ["frontend/**/*"]
        # Сравнение с целевой веткой MR или с main для обычных пушей
        compare_to: '${CI_MERGE_REQUEST_TARGET_BRANCH_NAME:-main}'
```

**Компоненты и входные параметры (spec:inputs, GitLab 17.x):**
Использование входных параметров в условиях `rules` для создания переиспользуемых модулей.
```yaml
spec:
  inputs:
    environment:
      default: "staging"
---
deploy:
  rules:
    - if: '$[[ inputs.environment ]] == "production"'
      when: manual
    - when: on_success
  script:
    - ./deploy.sh $[[ inputs.environment ]]
```

## Дополнительная информация

### Ключевые условия (Детально)

| Условие | Описание и технические нюансы | Пример |
| :--- | :--- | :--- |
| `if` | Оценка логических выражений. Поддерживает переменные, regex (`=~`) и операторы (`&&`, `||`). Оценка происходит на этапе создания пайплайна. | `if: '$CI_COMMIT_BRANCH =~ /^feature\/.*/'` |
| `changes` | Триггер на изменение путей. Отлично работает в MR-пайплайнах, но для обычных push-событий сравнивает только последний коммит, если не указан `compare_to`. | `changes: - "src/**/*"` |
| `compare_to` | Уточнение базы для `changes`. С версии 17.2 может принимать переменные (`$TARGET_BRANCH`). | `compare_to: 'refs/heads/main'` |
| `exists` | Триггер на наличие файлов. С версии 17.0 поддерживает кросс-проектные проверки через `project` и `ref`. | `exists: - "Dockerfile"` |

### Режимы запуска (when) и их поведение

| Режим | Описание | Примечание |
| :--- | :--- | :--- |
| `on_success` | Выполняется, если все задачи на предыдущих стадиях завершились успешно. | Значение по умолчанию. |
| `on_failure` | Запускается только если хотя бы одна задача на предыдущей стадии упала. | Часто используется для алертинга или очистки (cleanup). |
| `always` | Выполняется независимо от статуса предыдущих задач. | Идеально для финальной очистки ресурсов. |
| `manual` | Требует явного ручного запуска пользователем в UI или через API. | Блокирует последующие стадии, если не указан `allow_failure: true`. |
| `delayed` | Откладывает запуск задачи на время, указанное в `start_in` (макс. 1 неделя). | Используется для rate limiting или ожидания внешних процессов. |
| `never` | Задача полностью исключается из графа выполнения пайплайна. | Используется как блокирующее правило в начале списка `rules`. |
