# Построение DAG с использованием needs

## Определения

**needs**: Директива для создания **направленного ациклического графа (DAG)**. Позволяет запускать задачи сразу после завершения их зависимостей, не дожидаясь окончания всей стадии (stage).

**Типы зависимостей и ключи:**
- **Внутри пайплайна (job):** Базовая зависимость от задачи в том же пайплайне.
- **Опциональная (`optional: true`):** Пайплайн не упадет, если зависимая задача не добавлена в граф (например, исключена через `rules`).
- **Кросс-проектная (`project`):** Получение артефактов из другого репозитория. В GitLab 17.0+ требует настройки **Inbound Allowlist** (Zero Trust) в целевом проекте.
- **Пайплайн-зависимость (`pipeline`):** Зависимость от конкретного ID пайплайна, часто используется в связке с `trigger` (Downstream Pipelines).
- **Матричная зависимость (`parallel:matrix`):** (GitLab 16.3+) Динамическая связь между конкретными инстансами параллельных матричных сборок. Позволяет избежать ожидания всей матрицы.

## Основные концепции

По умолчанию задачи в стадии выполняются параллельно, а стадии — последовательно. `needs` нарушает эту модель:

- Задача запускается **сразу** после завершения указанных в `needs` задач.
- Не нужно ждать окончания всей стадии.
- Создается **направленный ациклический граф (DAG)**.

**Важно:** `needs` автоматически устанавливает `dependencies`, загружая артефакты от указанных задач. Для отмены загрузки артефактов используйте: `artifacts: false`.

### Опциональные зависимости (optional)

Используется в динамических пайплайнах, где некоторые задачи могут не существовать в зависимости от условий (MR, ветка, тег).

```yaml
deploy:
  stage: deploy
  needs:
    - job: "security-scan"
      optional: true  # Пайплайн не упадет, если security-scan пропущен
```

### Кросс-проектные зависимости (project)

Позволяет построить цепочку поставок между разными репозиториями, скачивая артефакты напрямую без использования API-скриптов.
**Важно (GitLab 17.0+):** Согласно модели Zero Trust, проект-источник должен явно разрешить вашему проекту доступ к своим пайплайнам через **Inbound Allowlist** в настройках CI/CD (**Token Access**).

```yaml
integration-test:
  stage: test
  needs:
    - project: "my-group/backend-api"
      job: "build-assets"
      ref: "main"
      artifacts: true
```

### Немедленный запуск (needs: [])

Пустой массив `needs: []` означает, что задача не зависит ни от одной другой задачи и запускается **сразу** при старте пайплайна, независимо от стадий. Используется для независимых задач: нотификации, линтеры, сбор метрик.

```yaml
lint:
  stage: test
  needs: []
  script:
    - npm run lint
```

## Практические сценарии

### Ускорение пайплайна с использованием `needs` (DAG)

**Пример: независимые тесты не ждут долгих сборок**

```yaml
stages:
  - build
  - test

build:web:
  stage: build
  script:
    - npm run build:web
  artifacts:
    paths:
      - dist/web/

build:android:
  stage: build
  script:
    - ./gradlew assembleDebug
  artifacts:
    paths:
      - app/build/outputs/apk/

build:ios:
  stage: build
  script:
    - xcodebuild -scheme MyApp
  artifacts:
    paths:
      - build/ios/

# Запускается сразу после build:web, не ждёт android/ios
test:web:
  stage: test
  needs: ["build:web"]
  script:
    - npm run test:web

# Ждёт окончания всей стадии build (классическое поведение)
test:all:
  stage: test
  script:
    - npm run test:all
```

**Порядок выполнения:**

1. Все три `build:*` запускаются параллельно.
2. Через 15 сек `build:web` завершается → **сразу** запускается `test:web`.
3. Через 45 сек `build:ios` завершается → запускается `test:all`.

**Оптимизация с `dependencies: []`:**

```yaml
deploy:
  stage: deploy
  needs: ["test:web"]
  dependencies: []  # Не загружать артефакты, только порядок выполнения
  script:
    - echo "Deploying..."
```

Для сериализации развертываний и защиты от гонок состояний используется `resource_group` ([matrix_builds_and_serialization.md](./matrix_builds_and_serialization.md)).

### Сложный DAG с несколькими зависимостями

```yaml
lint:
  stage: test
  script:
    - npm run lint

test:unit:
  stage: test
  script:
    - npm run test:unit

test:integration:
  stage: test
  needs: ["lint", "test:unit"]
  script:
    - npm run test:integration

deploy:
  stage: deploy
  needs: ["test:integration"]
  script:
    - ./deploy.sh
```

**Граф выполнения:**

```
lint ──┬─→ test:integration ──→ deploy
        │
test:unit ──┘
```

### Динамические матричные зависимости (needs:parallel:matrix)

До GitLab 16.3 задачи тестирования, использующие матрицу, должны были ждать завершения *всей* матрицы сборки. Теперь можно настроить зависимости 1:1, чтобы каждый инстанс теста ждал только свой инстанс сборки.

```yaml
build:
  stage: build
  parallel:
    matrix:
      - PROVIDER: [aws, gcp, azure]
  script:
    - echo "Building for $PROVIDER"

test:
  stage: test
  parallel:
    matrix:
      - PROVIDER: [aws, gcp, azure]
  needs:
    - job: build
      parallel:
        matrix:
          - PROVIDER: [$PROVIDER] # test:aws будет ждать только build:aws
  script:
    - echo "Testing for $PROVIDER"
```

## Дополнительная информация

### Особенности загрузки артефактов и `dependencies`

При использовании `needs` поведение загрузки артефактов меняется:
1. По умолчанию скачиваются артефакты **только** от задач, перечисленных в `needs`, а не от всех задач предыдущих стадий.
2. Использование `dependencies: []` вместе с `needs` отключает загрузку вообще, оставляя только DAG-зависимость (максимальное ускорение).
3. Ключ `artifacts: false` внутри элемента `needs` позволяет точечно отключить скачивание артефакта от конкретной задачи:

```yaml
deploy:
  needs:
    - job: "build:backend"
      artifacts: true  # Скачать бинарник
    - job: "lint:code"
      artifacts: false # Зависеть от успеха линтера, но отчеты не качать
```

### Технические ограничения
- **Лимит зависимостей:** Максимальное количество задач в массиве `needs` по умолчанию ограничено 50 (настраивается администратором инстанса).
- **Стадийная последовательность:** Если задача А зависит от задачи Б (`needs: [Б]`), задача А должна находиться в той же стадии, что и Б, или в стадии, которая определена *позже* в глобальном списке `stages`. Нельзя зависеть от задачи из "будущей" стадии.
- **Вложенность:** `needs` нельзя использовать для зависимости от задачи внутри дочернего пайплайна (Parent-Child) напрямую; используйте `bridge jobs` для передачи статуса.
