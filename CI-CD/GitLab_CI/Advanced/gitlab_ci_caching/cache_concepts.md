# Концепции кэширования и артефактов в GitLab CI

## Определения

**Кэширование в GitLab CI** — механизм сохранения файлов и директорий между запусками задач или пайплайнов для ускорения сборки за счёт повторного использования зависимостей.

**Артефакты в GitLab CI** — файлы или директории, сохраняемые после выполнения задачи и передаваемые между стадиями пайплайна для доставки результатов сборки.

**Распределённый кэш** — механизм хранения кэша в централизованном хранилище (S3, GCS), доступном всем Runner'ам.

**Локальный кэш** — кэш, хранящийся на конкретном Runner'е и доступный только задачам, выполняющимся на этом Runner'е.

## Основные концепции

### Архитектура кэширования

Кэширование в GitLab CI работает на двух уровнях:

1. **Локальное хранилище** — кэш сохраняется в директории Runner'а (`/home/gitlab-runner/.local/share/gitlab-runner/cache`). Доступен только задачам на этом Runner'е.
2. **Распределённое хранилище** — кэш загружается в объектное хранилище (S3, GCS). Доступен всем Runner'ам проекта.

### Кэш vs. Артефакты

| Признак | Кэш (`cache`) | Артефакты (`artifacts`) |
| :--- | :--- | :--- |
| **Назначение** | Ускорение задач | Передача результатов |
| **Гарантия** | Не гарантируется | Гарантируются |
| **Хранение** | Локально на Runner / S3 | На сервере GitLab |
| **Срок жизни** | Бессрочно (до очистки) | 30 дней по умолчанию |
| **Область** | Проект / ветка / задача | Задача → последующие стадии |

**Кэш** используется для зависимостей (`node_modules`, `.m2`, `vendor`), которые не критичны и могут быть воссозданы.

**Артефакты** используются для результатов сборки (бинарники, отчёты, пакеты), которые должны сохраняться и передаваться.

### Жизненный цикл кэша

1. **Создание** — задача выполняет `cache:policy: pull-push` или `push`, кэш архивируется и сохраняется.
2. **Поиск** — при запуске задачи GitLab ищет кэш по ключу (основной → fallback).
3. **Загрузка** — кэш распаковывается в рабочую директорию перед выполнением `script`.
4. **Обновление** — после успешного выполнения кэш перезаписывается (при `pull-push`).
5. **Очистка** — вручную через UI/API или автоматически при переполнении.

### Типы ключей кэша

| Тип | Пример | Когда использовать |
| :--- | :--- | :--- |
| Статический | `key: "global-cache"` | Глобальный кэш для всех |
| Динамический | `key: "$CI_COMMIT_REF_SLUG"` | Раздельный кэш по веткам |
| По файлам | `key: { files: [package-lock.json] }` | Автообновление при изменении зависимостей |
| Fallback | `fallback_keys: [cache-main]` | Резервный кэш при отсутствии основного |

Подробнее о ключах и политиках — в [ключи кэша](./cache_keys.md).

## Практические сценарии

### Сценарий 1: Выбор между кэшем и артефактами

**Кэш:**

```yaml
cache:
  key:
    files:
      - package-lock.json
  paths:
    - node_modules/
```

**Артефакты:**

```yaml
artifacts:
  paths:
    - dist/
  expire_in: 1 week
```

### Сценарий 2: Комбинация кэша и артефактов

```yaml
build:
  stage: build
  script:
    - npm ci
    - npm run build
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - node_modules/
    policy: pull-push
  artifacts:
    paths:
      - dist/
    expire_in: 1 week
```

Полный пример — в [обзор кэширования и артефактов](./caching_overview.md#пример-комбинации).

## Дополнительная информация

### Настройка распределённого кэша

Для включения распределённого кэша требуется конфигурация Runner'а:

```toml
# /etc/gitlab-runner/config.toml
[runners.cache]
  Type = "s3"
  Shared = true
  [runners.cache.s3]
    ServerAddress = "s3.amazonaws.com"
    BucketName = "gitlab-runner-cache"
    Insecure = false
```

### Ограничения

- Максимум 4 кэша на задачу
- Размер кэша ограничен настройками сервера (по умолчанию 100 МБ)
- Кэш не гарантируется — может быть удалён в любой момент

### Рекомендации

1. Используйте ключи по файлам зависимостей для автоматического обновления кэша
2. Разделяйте кэш для разных типов зависимостей (npm, pip, maven)
3. Не кэшируйте файлы, которые могут содержать секреты или чувствительные данные
4. Для артефактов всегда устанавливайте `expire_in`, кроме релизных сборок
