# Лучшие практики кэширования в GitLab CI

## Определения

**Лучшие практики кэширования** — набор проверенных рекомендаций по эффективному использованию механизма кэширования в GitLab CI для ускорения сборок, минимизации ошибок и оптимизации использования хранилища.

**Политика кэширования (`policy`)** — параметр, определяющий, загружает ли задача кэш, сохраняет его или выполняет оба действия (`pull`, `push`, `pull-push`).

## Основные концепции и лучшие практики

### 1. Используйте ключи по файлам зависимостей

Ключи на основе файлов зависимостей обеспечивают автоматическое обновление кэша при изменении версий пакетов.

**Рекомендуется:**

```yaml
cache:
  key:
    files:
      - package-lock.json
  paths:
    - node_modules/
```

**Не рекомендуется:**

```yaml
cache:
  key: "global-cache"  # Кэш не будет обновляться при изменении зависимостей
  paths:
    - node_modules/
```

### 2. Разделяйте кэш для разных задач

Разделение кэша предотвращает конфликты и уменьшает размер каждого кэша.

```yaml
build:
  cache:
    key: "build-cache"
    paths:
      - .npm/
      - .cache/

test:
  cache:
    key: "test-cache"
    paths:
      - .jest-cache/
```

### 3. Используйте правильную политику (`policy`)

| Политика | Описание | Когда использовать |
| :--- | :--- | :--- |
| `pull-push` (по умолчанию) | Загружает и сохраняет кэш | Задачи, которые обновляют зависимости |
| `pull` | Только загружает, не сохраняет | Задачи, которые только потребляют кэш (тесты, линтеры) |
| `push` | Только сохраняет, не загружает | Задачи, которые только создают кэш |

**Пример:**

```yaml
# Задача, которая обновляет зависимости
install:
  cache:
    policy: pull-push

# Задача, которая только использует кэш
lint:
  cache:
    policy: pull
```

Подробнее о политиках и ключах: [ключи кэша и политики](./cache_keys.md).

### 4. Кэшируйте только необходимые файлы

**Рекомендуется:**

```yaml
cache:
  paths:
    - node_modules/
    - .npm/
    - vendor/
```

**Не рекомендуется:**

```yaml
cache:
  paths:
    - .git/          # Не нужно, Git уже есть
    - dist/          # Это артефакт, а не кэш
    - "*.log"        # Логи не нужны
```

## Практические сценарии и решение проблем

### Сценарий 1: Очистка кэша через UI

1. Перейдите в **Build → Cache** в интерфейсе GitLab
2. Нажмите **Remove caches**

### Сценарий 2: Очистка кэша через API

```bash
curl --request DELETE --header "PRIVATE-TOKEN: <your_token>" \
  "https://gitlab.example.com/api/v4/projects/<project_id>/cache"
```

### Сценарий 3: Автоматическая очистка по расписанию

```yaml
cleanup_cache:
  stage: .pre
  script:
    - echo "Cleaning cache"
  cache:
    key: "old-cache"
    paths: []
    policy: push
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
```

### Сценарий 4: Комбинация кэша и артефактов

Кэш ускоряет установку зависимостей, артефакты передают результаты сборки — см. [комбинацию кэша и артефактов](./gitlab_ci_artifacts.md#сценарий-3-комбинация-кэша-и-артефактов).

### Решение типичных проблем (Troubleshooting)

#### Кэш не загружается

**Проблема:** Задача не находит кэш.

**Возможные причины:**

1. Неправильный ключ кэша
2. Кэш был удалён
3. Разные Runner'ы (кэш локален для Runner)

**Решение:**

```yaml
cache:
  key: "$CI_COMMIT_REF_SLUG"  # Должен совпадать с задачей, создавшей кэш
```

#### Кэш устарел

**Проблема:** Зависимости не обновляются.

**Решение:**

```yaml
cache:
  key:
    files:
      - package-lock.json
```

#### Кэш слишком большой

**Проблема:** Долгая загрузка/выгрузка кэша.

**Решение:**

```yaml
cache:
  paths:
    - node_modules/
  exclude:
    - node_modules/**/*.md
    - node_modules/**/test/
```

## Дополнительная информация

### Ограничения кэширования

- Максимум 4 кэша на задачу
- Кэш привязан к Runner (при использовании локального хранилища)
- Распределённый кэш требует настройки S3
