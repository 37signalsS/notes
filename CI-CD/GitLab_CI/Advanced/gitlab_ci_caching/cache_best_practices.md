# Лучшие практики кэширования в GitLab CI

## Определения

**Лучшие практики кэширования** — набор проверенных архитектурных решений по использованию кэша для минимизации времени сборки при соблюдении безопасности и стабильности пайплайнов.

**Инвалидация кэша** — процедура принудительного обновления содержимого кэша. Самый надежный способ — изменение `prefix` или одного из файлов в `cache:key:files`.

**Cache Poisoning (Отравление кэша)** — состояние, при котором в общий кэш (например, для всех веток) попадают некорректные или вредоносные данные из экспериментальной ветки, ломающие сборку в основной ветке (`main`).

**Gitaly Load (Нагрузка на Gitaly)** — потребление ресурсов сервера при вычислении хешей файлов для ключей кэша. Злоупотребление `cache:key:files` в огромных репозиториях может приводить к таймаутам создания пайплайна.

## Основные концепции

### 1. Стратегия выбора ключей и производительность

Выбор ключа определяет не только точность попадания в кэш, но и скорость работы самого GitLab.

*   **Хеширование lock-файлов (Стандарт):** Использование `cache:key:files` гарантирует актуальность зависимостей. 
*   **Технический нюанс (Gitaly):** Каждый файл в списке `files` требует обращения к Gitaly (хранилищу Git). В GitLab 17.1+ введено ограничение: **не более 4 записей кэша** на одну задачу. Если у вас 10 мелких кэшей, объедините их, чтобы избежать ошибок валидации.
*   **Префиксы для изоляции:** Всегда добавляйте `prefix` (например, `node-v20-`), чтобы при обновлении рантайма гарантированно получить чистый кэш без конфликтов бинарных зависимостей.

### 2. Оптимизация процесса загрузки и выгрузки

С версий GitLab 16.2 - 19.x появились критические оптимизации:

*   **`FF_SKIP_NOOP_CACHE` (GitLab 17.x+):** Включите эту переменную (`"true"`), чтобы Runner не тратил время и трафик на повторную загрузку (upload) кэша, если его содержимое не изменилось с момента скачивания. Это радикально ускоряет стадию `after_script` в задачах, где зависимости не меняются.
*   **Zstd и FastZip:** Для кэшей более 500 МБ обязательно используйте `FF_USE_FASTZIP: "true"` и `CACHE_COMPRESSION_LEVEL: "fast"`. Это снижает нагрузку на CPU Runner'а и сокращает время архивации.

### 3. Резервные ключи (Fallback Keys)

Для предотвращения "холодного запуска" в новых feature-ветках используйте до 5 резервных ключей. Алгоритм GitLab будет искать кэш по порядку, пока не найдет первое совпадение.

```yaml
cache:
  - key:
      files: [package-lock.json]
      prefix: "npm-$CI_COMMIT_REF_SLUG"
    fallback_keys:
      - "npm-$CI_DEFAULT_BRANCH" # Если lock-файл новый, берем базу из main
      - "npm-default"
    paths: [node_modules/]
```

### 4. Паттерн "Setup-Consumer" (Политики)

Это самый эффективный способ управления конкурентным доступом к кэшу:

1.  **Задача Setup:** (например, `install_deps`) использует `policy: pull-push`. Только она имеет право обновлять кэш.
2.  **Задачи-потребители (Consumers):** (тесты, линтеры) используют `policy: pull`. Это гарантирует, что 20 параллельных тестов не будут одновременно пытаться перезаписать один и тот же файл в S3, исключая риск повреждения архива.

## Практические сценарии

### Сценарий 1: Принудительное обновление кэша (Invalidation)

Если кэш "отравлен" или поврежден, используйте один из методов:

1.  **UI:** Перейдите в **Build → Cache** и нажмите кнопку **Clear runner caches**. Это инвалидирует кэш для всех Runner'ов проекта.
2.  **API:** Выполните DELETE запрос к API GitLab для очистки кэша проекта.
3.  **YAML:** Измените `prefix` в ключе кэша (например, с `v1` на `v2`). Это самый надежный способ для конкретной задачи.

### Сценарий 2: Кэширование в монорепозитории

Используйте `files` с указанием конкретных путей к lock-файлам микросервисов, чтобы задачи одного сервиса не зависели от изменений в другом.

```yaml
frontend:cache:
  key:
    files:
      - frontend/package-lock.json
    prefix: frontend-v1
  paths:
    - frontend/node_modules/
```

### Сценарий 3: Использование кэша Docker-слоев (BuildKit)

Вместо стандартного `cache:`, для Docker-образов используйте возможности BuildKit (регистр кэша), что гораздо эффективнее для слоев образа. См. подробности в [практических сценариях](./cache_scenarios.md#сценарий-5---кэширование-слоёв-docker-через-registry-buildkit).

## Дополнительная информация

### Чек-лист лучших практик

1.  **Не кэшируйте артефакты:** Файлы, созданные вашей сборкой (бинарники, дистрибутивы), передавайте через `artifacts`.
2.  **Исключайте лишнее:** Используйте `exclude` или точные `paths`, чтобы не упаковывать логи, временные файлы и `.git`.
3.  **Следите за размером:** Если распаковка кэша занимает больше времени, чем установка "с нуля", кэширование вредно. Оптимальный размер — до 500 МБ.
4.  **Изоляция защищенных веток:** Помните, что по умолчанию кэш из `protected branches` недоступен обычным веткам. Используйте `unprotect: true`, только если понимаете риски безопасности.

### Устранение неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| Кэш не найден | Разные ключи или разные Runner'ы | Проверьте `key` и убедитесь, что используется Distributed Cache (S3). |
| Кэш не обновляется | Ключ привязан к статической строке | Используйте `files: [lock-file]` в конфигурации ключа. |
| Медленный Pipeline | Слишком большой кэш или медленный zip | Включите `zstd` (16.2+) и `FF_USE_FASTZIP`. |
| Таймаут создания Pipeline | Перегрузка Gitaly из-за `cache:key:files` | Сократите количество файлов в `files` или количество кэшей (макс 4). |
