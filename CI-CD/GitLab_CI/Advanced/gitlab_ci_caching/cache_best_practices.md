# Лучшие практики кэширования в GitLab CI

## Определения

**Лучшие практики кэширования** — набор проверенных рекомендаций по эффективному использованию механизма кэширования для ускорения пайплайнов, оптимизации ресурсов хранилища и обеспечения консистентности сборок.

**Инвалидация кэша** — процесс принудительного обновления или сброса кэша при изменении зависимостей или возникновении ошибок.

**Холодный запуск (Cold Start)** — ситуация, когда задача запускается без существующего кэша (например, в новой ветке или при смене ключа), что приводит к полной установке зависимостей.

## Основные концепции

### 1. Стратегия выбора ключей

Правильный выбор ключа — критический фактор для баланса между скоростью и актуальностью данных.

*   **Используйте хеширование файлов зависимостей (Рекомендуется):** Это гарантирует, что кэш обновится только при изменении `package-lock.json`, `go.sum`, `Cargo.lock` и т.д.
*   **Добавляйте префиксы для версионности:** При обновлении мажорной версии языка (Node.js 18 → 20) меняйте `prefix` в ключе, чтобы избежать конфликтов скомпилированных бинарных файлов.
*   **Избегайте статических ключей:** Глобальные ключи (например, `key: "all-branches"`) приводят к "отравлению" кэша (cache poisoning), когда изменения из одной ветки ломают сборки в других.

### 2. Оптимизация производительности

С версии GitLab 16.x и 17.x появились инструменты, значительно ускоряющие работу с кэшем:

*   **Zstd сжатие (16.2+):** Если ваши Runner'ы поддерживают zstd, это обеспечит более быструю упаковку/распаковку при меньшем размере архива по сравнению с традиционным zip.
*   **Флаг `FF_USE_FASTZIP`:** Включение конкурентного zip (`FF_USE_FASTZIP: "true"`) ускоряет архивацию на многоядерных системах.
*   **Уровень сжатия:** Используйте `CACHE_COMPRESSION_LEVEL: "fast"` или `"fastest"`. В CI/CD экономия процессорного времени важнее экономии нескольких мегабайт места в S3.

### 3. Резервные ключи (Fallback Keys)

Для предотвращения "холодного запуска" в новых feature-ветках всегда настраивайте `fallback_keys` (до 5 ключей в GitLab 16.0+).

```yaml
cache:
  - key: "$CI_COMMIT_REF_SLUG"
    fallback_keys:
      - "$CI_DEFAULT_BRANCH"  # Используем кэш из 'main', если в ветке его еще нет
      - "global-cache"
    paths:
      - vendor/
```

### 4. Использование политик и множественного кэша

*   **Применяйте `policy: pull`:** В задачах тестирования, линтинга и деплоя, которые только потребляют зависимости, но не добавляют новые. Это сокращает время задачи за счет пропуска этапа загрузки архива на сервер в конце.
*   **Разделяйте кэши (до 4 на задачу):** Отделяйте стабильные системные зависимости от часто меняющегося кэша инструментов или компиляции.

## Практические сценарии

### Сценарий 1: Принудительное обновление кэша (Invalidation)

Если кэш "отравлен" или поврежден, используйте один из методов:

1.  **UI:** Перейдите в **Build → Cache** и нажмите кнопку **Clear runner caches**. Это инвалидирует кэш для всех Runner'ов проекта.
2.  **API:** Выполните DELETE запрос к API GitLab для очистки кэша проекта.
3.  **YAML:** Измените `prefix` в ключе кэша (например, с `v1` на `v2`). Это самый надежный способ для конкретной задачи.

### Сценарий 2: Кэширование в монорепозитории

Используйте `files` с указанием конкретных путей к lock-файлам микросервисов, чтобы задачи одного сервиса не зависели от изменений в другом.

```yaml
frontend:cache:
  key:
    files:
      - frontend/package-lock.json
    prefix: frontend-v1
  paths:
    - frontend/node_modules/
```

### Сценарий 3: Использование кэша Docker-слоев (BuildKit)

Вместо стандартного `cache:`, для Docker-образов используйте возможности BuildKit (регистр кэша), что гораздо эффективнее для слоев образа. См. подробности в [практических сценариях](./cache_scenarios.md#сценарий-5---кэширование-слоёв-docker-через-registry-buildkit).

## Дополнительная информация

### Чек-лист лучших практик

1.  **Не кэшируйте артефакты:** Файлы, созданные вашей сборкой (бинарники, дистрибутивы), передавайте через `artifacts`.
2.  **Исключайте лишнее:** Используйте `exclude` или точные `paths`, чтобы не упаковывать логи, временные файлы и `.git`.
3.  **Следите за размером:** Если распаковка кэша занимает больше времени, чем установка "с нуля", кэширование вредно. Оптимальный размер — до 500 МБ.
4.  **Изоляция защищенных веток:** Помните, что по умолчанию кэш из `protected branches` недоступен обычным веткам. Используйте `unprotect: true`, только если понимаете риски безопасности.

### Устранение неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| Кэш не найден | Разные ключи или разные Runner'ы | Проверьте `key` и убедитесь, что используется Distributed Cache (S3). |
| Кэш не обновляется | Ключ привязан к статической строке | Используйте `files: [lock-file]` в конфигурации ключа. |
| Медленный Pipeline | Слишком большой кэш или медленный zip | Включите `zstd` (16.2+) и `FF_USE_FASTZIP`. |
