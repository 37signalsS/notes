# Кэширование и артефакты в GitLab CI — обзор

## Определения

**Кэширование в GitLab CI** — механизм сохранения файлов и директорий между запусками задач или пайплайнов для ускорения сборки за счёт повторного использования зависимостей (`node_modules`, `.m2`, `vendor`).

**Артефакты в GitLab CI** — файлы или директории, сохраняемые после выполнения задачи и передаваемые между стадиями пайплайна для доставки результатов сборки.

**Распределённый кэш** — механизм хранения кэша в централизованном хранилище (S3, GCS), доступном всем Runner'ам проекта.

**Локальный кэш** — кэш, хранящийся на конкретном Runner'е и доступный только задачам, выполняющимся на этом Runner'е.

## Основные концепции

### Сравнение кэша и артефактов

| Признак | Кэш (`cache`) | Артефакты (`artifacts`) |
| :--- | :--- | :--- |
| **Назначение** | Ускорение задач (зависимости) | Передача результатов (билды, отчёты) |
| **Основная область** | Между **пайплайнами** (разные запуски) | Между **джабами** (внутри одного пайплайна) |
| **Гарантия** | Не гарантируется (может быть удалён) | Гарантируются на сервере GitLab |
| **Хранение** | Локально на Runner'е или в S3/GCS | На сервере GitLab |
| **Срок жизни** | Бессрочно (до очистки или вручную) | Настраивается через `expire_in` |
| **Область** | По умолчанию — для всего проекта | Только для конкретной задачи |
| **Скорость** | Быстрее (локально на Runner) | Медленнее (загрузка/скачивание) |

**Важно:** Для критически важных файлов используйте артефакты. Кэш может быть удалён в любой момент. Параметр `expire_in` **не работает** для кэша и предназначен только для артефактов.

### Архитектура кэширования

Кэширование в GitLab CI работает на двух уровнях:

1. **Локальное хранилище** — кэш сохраняется в директории Runner'а. Доступен только задачам на этом Runner'е.
2. **Распределённое хранилище (S3, GCS)** — кэш загружается в объектное хранилище. Доступен всем Runner'ам проекта.

### Жизненный цикл кэша

1. **Поиск** — GitLab ищет кэш по ключу (основной → `fallback_keys`).
2. **Загрузка** — кэш распаковывается в рабочую директорию перед `script`.
3. **Обновление** — после успеха кэш перезаписывается (при `policy: pull-push`).
4. **Очистка** — вручную через UI/API или при переполнении Runner'а.

### Хранение локального кэша

| Тип Runner | Путь по умолчанию |
| :--- | :--- |
| Shell | `/home/gitlab-runner/cache/<user>/<project>/<key>/cache.zip` |
| Docker | `/var/lib/docker/volumes/<id>/_data/<user>/<project>/<key>/cache.zip` |

## Дополнительная информация

### Настройка распределённого кэша

Требуется конфигурация Runner'а (`/etc/gitlab-runner/config.toml`):

```toml
[runners.cache]
  Type = "s3"
  Shared = true
  [runners.cache.s3]
    ServerAddress = "s3.amazonaws.com"
    BucketName = "gitlab-runner-cache"
    AccessKey = "YOUR_ACCESS_KEY"
    SecretKey = "YOUR_SECRET_KEY"
    Insecure = false
```

### Рекомендации

1. Используйте ключи по файлам зависимостей для автоматического обновления кэша.
2. Разделяйте кэш для разных типов зависимостей (NPM, Pip, Maven).
3. Не кэшируйте секреты или чувствительные данные.
4. Для артефактов всегда устанавливайте `expire_in`.
5. Используйте распределённый кэш для командной работы.

### Устранение неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| Кэш не загружается | Неправильный ключ | Проверьте совпадение ключа между задачами |
| Кэш устарел | Статический ключ | Используйте ключи по файлам зависимостей |
| Долгая загрузка | Большой размер кэша | Исключите лишние файлы через `exclude` |
| Ошибка `expire_in` | Параметр в `cache` | Удалите `expire_in` из секции `cache`, он только для артефактов |
