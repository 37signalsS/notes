# Кэширование и артефакты в GitLab CI — обзор

## Определения

**Кэширование в GitLab CI** — механизм сохранения временных данных (зависимостей, кэша компилятора) между запусками пайплайнов для сокращения времени выполнения. Кэш является хранилищем с гарантией **"best-effort"**: GitLab Runner может удалить его в любой момент для освобождения места.

**Артефакты в GitLab CI** — гарантированное хранилище для передачи результатов сборки (бинарные файлы, отчеты) между стадиями внутри одного пайплайна. Артефакты сохраняются на стороне сервера GitLab и доступны для скачивания через UI/API.

**Распределённый кэш (Distributed Cache)** — централизованное хранение данных в объектном хранилище (S3/MinIO/GCS), позволяющее любым Runner'ам проекта (включая динамические узлы в Kubernetes) использовать общую базу зависимостей.

**Локальный кэш** — данные, хранящиеся непосредственно на диске конкретного Runner'а. Недоступны при переключении задачи на другой узел.

## Основные концепции

### Сравнение кэша и артефактов

| Характеристика | Кэш (`cache`) | Артефакты (`artifacts`) |
| :--- | :--- | :--- |
| **Цель** | Оптимизация скорости (зависимости) | Результаты сборки и отчеты |
| **Жизненный цикл** | Между разными пайплайнами | Между стадиями одного пайплайна |
| **Надежность** | Низкая (может быть удален) | **Высокая** (гарантированная доставка) |
| **Скачивание в UI** | Недоступно | Доступно через кнопку "Download" |
| **Место хранения** | Runner или внешнее S3-хранилище | Сервер GitLab (через API) |
| **Количество** | До **4** отдельных кэшей на задачу | Без жесткого лимита (по объему) |
| **Протокол** | Внутренние механизмы Runner'а | HTTP/HTTPS (REST API GitLab) |

**Важно:** Никогда не используйте кэш для передачи критически важных файлов (например, JAR-архива для деплоя). Если файл обязателен для следующей стадии — используйте **артефакты**. Подробнее о глубокой настройке артефактов — в **[gitlab_ci_artifacts.md](./gitlab_ci_artifacts.md)**.

### Архитектура и уровни хранения

1. **Локальный уровень:** Самый быстрый доступ, но ограничен одним Runner'ом. Подходит для выделенных Bare-metal серверов.
   - **Пути хранения (Shell):** `/home/gitlab-runner/cache/<project-path>/<key>/cache.zip`
2. **Удалённый уровень (Distributed Cache):** Необходим для современных "облачных" инсталляций (Kubernetes, Docker Swarm). 
   - С версии **16.2** по умолчанию используется сжатие **Zstd**, которое в разы быстрее классического Zip.
   - Для экстремальной скорости на Runner'ах рекомендуется включать `FF_USE_FASTZIP`.

### Жизненный цикл кэша в задаче

1. **Восстановление (Restore):** Перед выполнением `before_script` GitLab Runner проверяет наличие кэша по ключу. Если используется несколько кэшей (до 4), они восстанавливаются последовательно.
2. **Выполнение:** Задача использует файлы из кэша.
3. **Архивация (Archive):** После завершения скрипта (зависит от `when`) Runner запаковывает указанные пути и загружает их в хранилище. По умолчанию используется политика `pull-push`.

### Механизмы изоляции

По умолчанию кэш изолирован для каждой ветки и проекта. В GitLab введена дополнительная защита для **защищённых веток** (`protected branches`), предотвращающая доступ к их кэшу из обычных веток.

- **Защищённые ветки:** Кэш доступен только задачам на защищённых ветках.
- **Обычные ветки:** Кэш изолирован от защищённых.
- **Параметр `unprotect`:** Позволяет задачам на обычных ветках использовать кэш из защищённых веток (см. [настройку ключей](./cache_keys.md#защита-и-изоляция-кэша)).

## Дополнительная информация

### Настройка распределённого кэша (S3/MinIO)

Пример конфигурации в `/etc/gitlab-runner/config.toml`:

```toml
[runners.cache]
  Type = "s3"
  Path = "cache"
  Shared = true
  [runners.cache.s3]
    ServerAddress = "s3.amazonaws.com"
    BucketName = "gitlab-cache"
    BucketLocation = "us-east-1"
    AuthenticationType = "iam" # Рекомендуется для AWS (IAM Role)
    # AccessKey = "ACCESS_KEY" # Используйте, если нет IAM Role
    # SecretKey = "SECRET_KEY"
    Insecure = false
```

### Современные флаги производительности

Для ускорения работы с кэшем и артефактами рекомендуется добавить следующие переменные в `.gitlab-ci.yml`:

```yaml
variables:
  FF_USE_FASTZIP: "true"          # Использование быстрого конкурентного zip
  CACHE_COMPRESSION_LEVEL: "fast" # Уровень сжатия кэша (fast, fastest, default, slow, slowest)
  ARTIFACT_COMPRESSION_LEVEL: "fast"
```

### Рекомендации по оптимизации
1. **Иерархия ключей:** Используйте `fallback_keys` (до 5 ключей) для ускорения сборки новых веток.
2. **Политики:** Применяйте `policy: pull` для задач, которые не обновляют зависимости.
3. **Zstd сжатие:** Если ваш Runner версии 16.2+, используйте zstd для ускорения пайплайнов с большими зависимостями.

### Устранение неполадок

| Проблема | Решение |
| :--- | :--- |
| Кэш не передаётся между стадиями | Проверьте, что ключ `key` совпадает. Кэш по умолчанию изолирован между ветками. |
| Кэш растёт бесконечно | GitLab не чистит старые ключи автоматически. Используйте кнопку "Clear runner caches" в UI. |
| Ошибка распаковки | Убедитесь, что пути в `paths` относительны корню проекта. |
