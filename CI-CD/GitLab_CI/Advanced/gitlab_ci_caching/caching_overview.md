# Кэширование и артефакты в GitLab CI — Обзор

## Определения

**Кэширование в GitLab CI** — механизм сохранения файлов и директорий между запусками задач или пайплайнов. Основная цель — ускорение сборки за счёт повторного использования зависимостей (`node_modules`, `vendor/`, `.m2/`).

**Артефакты в GitLab CI** — файлы или директории, которые сохраняются после выполнения задачи и передаются между стадиями пайплайна. Артефакты хранятся на сервере GitLab и используются для передачи результатов сборки, отчётов тестирования, бинарных файлов.

Подробные определения и сравнение: [Концепции кэширования](./cache_concepts.md).

## Основные концепции

### Кэш vs. Артефакты

**Кэш** используется для зависимостей (`node_modules`, `.m2`, `vendor`), которые не критичны и могут быть воссозданы.

**Артефакты** используются для результатов сборки (бинарники, отчёты, пакеты), которые должны сохраняться и передаваться.

### Когда что использовать

**Используйте кэш (`cache`), когда:**

- Нужно ускорить установку зависимостей (`npm install`, `pip install`, `mvn dependency:resolve`)
- Файлы не критичны и могут быть воссозданы
- Требуется доступ к данным между разными пайплайнами одной ветки
- Работаете с временными файлами компиляции (`.o`, `.class`, `__pycache__`)

**Используйте артефакты (`artifacts`), когда:**

- Нужно передать файлы между стадиями пайплайна (сборка → тесты → деплой)
- Файлы критичны и должны сохраняться (бинарники, пакеты, отчёты)
- Требуется скачать результат конкретной задачи (например, `junit.xml` для отчёта)
- Готовите файлы для публикации (Docker-образ, deb/rpm пакет, релизный архив)

### Пример комбинации

```yaml
build:
  stage: build
  script:
    - npm ci
    - npm run build
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - node_modules/
    policy: pull-push
  artifacts:
    paths:
      - dist/
    expire_in: 1 week

test:
  stage: test
  script:
    - npm test
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - node_modules/
    policy: pull
  dependencies:
    - build
  artifacts:
    reports:
      junit: test-results.xml
```

В этом примере:

- **Кэш** ускоряет установку зависимостей в обеих задачах
- **Артефакты** передают собранный код из `build` в `test` и сохраняют отчёт о тестах

## Дополнительная информация

### Архитектура кэширования

Кэширование в GitLab CI работает на двух уровнях:

1. **Локальное хранилище** — кэш сохраняется в директории Runner'а. Доступен только задачам на этом Runner'е.
2. **Распределённое хранилище (S3, GCS)** — кэш загружается в объектное хранилище. Доступен всем Runner'ам проекта.

### Ограничения

| Ограничение | Значение |
| :--- | :--- |
| Максимум кэшей на задачу | 4 |
| Размер кэша | Ограничен настройками сервера (по умолчанию 100 МБ) |
| Срок хранения артефактов | 30 дней по умолчанию |
| Гарантия кэша | Не гарантируется (может быть удалён) |
| Гарантия артефактов | Гарантируются на сервере GitLab |

### Рекомендации

1. **Используйте ключи по файлам зависимостей** для автоматического обновления кэша
2. **Разделяйте кэш и артефакты** — кэш для зависимостей, артефакты для результатов
3. **Настраивайте `expire_in`** для артефактов, чтобы избежать переполнения хранилища
4. **Используйте распределённый кэш** для больших команд и нескольких Runner'ов

### Troubleshooting

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| Кэш не загружается | Неправильный ключ | Проверьте совпадение ключа между задачами |
| Кэш устарел | Статический ключ | Используйте ключи по файлам зависимостей |
| Долгая загрузка | Большой размер кэша | Исключите лишние файлы через `exclude` |
| Артефакты не передаются | Нет `dependencies` | Проверьте зависимости между задачами |
