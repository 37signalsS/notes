# Кэширование и артефакты в GitLab CI — обзор

## Определения

**Кэширование в GitLab CI** — механизм сохранения файлов и директорий между запусками задач или пайплайнов для ускорения сборки за счёт повторного использования зависимостей (`node_modules`, `.m2`, `vendor`). Кэш предназначен для временных данных, которые могут быть воссозданы.

**Артефакты в GitLab CI** — файлы или директории, сохраняемые после выполнения задачи и передаваемые между стадиями пайплайна для доставки результатов сборки (бинарные файлы, отчёты о тестировании). Артефакты гарантированно передаются между задачами внутри одного пайплайна.

**Распределённый кэш (Distributed Cache)** — механизм хранения кэша в централизованном объектном хранилище (S3, GCS, Azure Blob, MinIO), доступном всем Runner'ам проекта. Начиная с GitLab 16.2, поддерживается сжатие **zstd**, которое значительно ускоряет процесс упаковки и распаковки.

**Локальный кэш** — кэш, хранящийся непосредственно в файловой системе конкретного Runner'а (обычно в Docker volumes или локальной директории). Доступен только тем задачам, которые запускаются на этом же Runner'е.

## Основные концепции

### Сравнение кэша и артефактов

Кэш и артефакты часто путают, но они служат разным целям.

| Признак | Кэш (`cache`) | Артефакты (`artifacts`) |
| :--- | :--- | :--- |
| **Назначение** | Ускорение (зависимости, кэш компилятора) | Результаты (сборки, логи, отчёты) |
| **Передача** | Между **пайплайнами** (разные запуски) | Между **стадиями** (внутри одного запуска) |
| **Надёжность** | Не гарантируется (может отсутствовать) | Гарантированы на сервере GitLab |
| **Место хранения** | Runner или объектное хранилище | Сервер GitLab (через API) |
| **Срок жизни** | До очистки или переполнения | Настраивается через `expire_in` |
| **Количество** | До 4 отдельных кэшей на задачу | Без жёсткого лимита (зависит от размера) |
| **Очистка** | Кнопка в UI или API | Автоматически по истечении срока |

**Важно:** Никогда не используйте кэш для передачи критически важных результатов сборки. Если файл необходим для следующей стадии пайплайна — используйте `artifacts`.

### Архитектура и уровни хранения

1. **Локальный уровень:** Самый быстрый. Кэш хранится в виде архива на диске Runner'а. Для ускорения рекомендуется включать переменную `FF_USE_FASTZIP: "true"`.
2. **Удалённый уровень (Distributed Cache):** Позволяет использовать один и тот же кэш на разных Runner'ах. С версии 16.2 поддерживается алгоритм **zstd**, обеспечивающий лучшее соотношение скорости и степени сжатия по сравнению с `zip`.

**Пути хранения локального кэша:**
- **Shell Runner:** `/home/gitlab-runner/cache/<project-path>/<key>/cache.zip`
- **Docker Runner:** Внутри именованных Docker volumes или примонтированных директорий хоста.

### Жизненный цикл кэша в задаче

1. **Восстановление (Restore):** Перед выполнением `before_script` GitLab Runner проверяет наличие кэша по ключу. Если используется несколько кэшей (до 4), они восстанавливаются последовательно.
2. **Выполнение:** Задача использует файлы из кэша.
3. **Архивация (Archive):** После завершения скрипта (зависит от `when`) Runner запаковывает указанные пути и загружает их в хранилище. По умолчанию используется политика `pull-push`.

### Механизмы изоляции

По умолчанию кэш изолирован для каждой ветки и проекта. В GitLab введена дополнительная защита для **защищённых веток** (`protected branches`), предотвращающая доступ к их кэшу из обычных веток.

- **Защищённые ветки:** Кэш доступен только задачам на защищённых ветках.
- **Обычные ветки:** Кэш изолирован от защищённых.
- **Параметр `unprotect`:** Позволяет задачам на обычных ветках использовать кэш из защищённых веток (см. [настройку ключей](./cache_keys.md#защита-и-изоляция-кэша)).

## Дополнительная информация

### Настройка распределённого кэша (S3/MinIO)

Пример конфигурации в `/etc/gitlab-runner/config.toml`:

```toml
[runners.cache]
  Type = "s3"
  Path = "cache"
  Shared = true
  [runners.cache.s3]
    ServerAddress = "s3.amazonaws.com"
    BucketName = "gitlab-cache"
    BucketLocation = "us-east-1"
    AuthenticationType = "iam" # Рекомендуется для AWS (IAM Role)
    # AccessKey = "ACCESS_KEY" # Используйте, если нет IAM Role
    # SecretKey = "SECRET_KEY"
    Insecure = false
```

### Современные флаги производительности

Для ускорения работы с кэшем и артефактами рекомендуется добавить следующие переменные в `.gitlab-ci.yml`:

```yaml
variables:
  FF_USE_FASTZIP: "true"          # Использование быстрого конкурентного zip
  CACHE_COMPRESSION_LEVEL: "fast" # Уровень сжатия кэша (fast, fastest, default, slow, slowest)
  ARTIFACT_COMPRESSION_LEVEL: "fast"
```

### Рекомендации по оптимизации
1. **Иерархия ключей:** Используйте `fallback_keys` (до 5 ключей) для ускорения сборки новых веток.
2. **Политики:** Применяйте `policy: pull` для задач, которые не обновляют зависимости.
3. **Zstd сжатие:** Если ваш Runner версии 16.2+, используйте zstd для ускорения пайплайнов с большими зависимостями.

### Устранение неполадок

| Проблема | Решение |
| :--- | :--- |
| Кэш не передаётся между стадиями | Проверьте, что ключ `key` совпадает. Кэш по умолчанию изолирован между ветками. |
| Кэш растёт бесконечно | GitLab не чистит старые ключи автоматически. Используйте кнопку "Clear runner caches" в UI. |
| Ошибка распаковки | Убедитесь, что пути в `paths` относительны корню проекта. |
