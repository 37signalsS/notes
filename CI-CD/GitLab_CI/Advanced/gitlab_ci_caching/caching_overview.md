# Кэширование и артефакты в GitLab CI — обзор

## Требования и предварительные условия

### Версия GitLab и поддержка функций

| Функция | Минимальная версия | Примечание |
| :--- | :--- | :--- |
| `cache:key` (статический) | 8.10+ | Ключ по умолчанию |
| `cache:key:files` | 11.3+ | Хеш по содержимому lock-файлов |
| `cache:key:prefix` | 11.3+ | Статический префикс к хешу файлов |
| `cache:policy` (`pull`/`push`) | 8.10+ | Асимметричные политики |
| `cache:when` | 8.8+ | Условия сохранения кэша |
| `fallback_keys` (до 5) | 16.0+ | Цепочка поиска альтернативных ключей |
| `zstd` сжатие | 16.2+ | Алгоритм по умолчанию |
| `FF_USE_FASTZIP` | 13.1+ | Конкурентная упаковка |
| `CACHE_COMPRESSION_LEVEL` | 16.11+ | Управление уровнем сжатия |
| `CACHE_LIMIT` | 13.12+ | Ограничение размера кэша |

### Необходимые знания

- Базовый синтаксис `.gitlab-ci.yml` и жизненный цикл пайплайна
- Предопределённые переменные (`$CI_COMMIT_REF_SLUG`, `$CI_JOB_NAME`, `$CI_DEFAULT_BRANCH`, `$CI_NODE_INDEX`)
- Настройка Runner'ов и Distributed Cache (S3/MinIO)
- Принципы безопасного кэширования (cache poisoning, isolation)
- Различие между кэшем и артефактами (подробнее — в [сравнении механизмов](#сравнение-кэша-и-артефактов) ниже)

### Целевая аудитория

Справочник предназначен для DevOps-инженеров, SRE и системных администраторов, работающих с on-premise и гибридной инфраструктурой. Примеры ориентированы на оптимизацию времени сборки и безопасное кэширование зависимостей в распределённых командах Shared Runners.

## Определения

**Кэширование (Caching)** — механизм временного сохранения данных (зависимостей, кэша компилятора, промежуточных слоёв) между запусками различных пайплайнов для сокращения времени выполнения за счёт исключения повторной загрузки или сборки. Кэш работает по принципу **"best-effort"**: GitLab Runner не гарантирует его сохранность и может удалить файлы для освобождения места на диске или в S3.

**Артефакты (Artifacts)** — гарантированное хранилище результатов выполнения задачи (бинарные файлы, отчёты, логи), предназначенное для передачи данных между стадиями (stages) внутри одного пайплайна. В отличие от кэша, артефакты передаются на сервер GitLab и доступны для скачивания через интерфейс или API.

**Распределённый кэш (Distributed Cache)** — централизованное хранилище (обычно S3-совместимое), позволяющее различным Runner'ам (включая динамические поды в Kubernetes) использовать общий набор данных. Это критично для масштабируемых инфраструктур, где одна задача может запуститься на узле A, а следующая — на узле B.

**Локальный кэш (Local Cache)** — данные, хранящиеся непосредственно на файловой системе Runner'а. Это самый быстрый способ доступа, но он привязан к конкретному узлу.

## Основные концепции

### Сравнение кэша и артефактов

| Характеристика | Кэш (`cache`) | Артефакты (`artifacts`) |
| :--- | :--- | :--- |
| **Основная цель** | Ускорение сборки (зависимости) | Результаты сборки, отчёты |
| **Жизненный цикл** | Между разными пайплайнами | Внутри одного пайплайна |
| **Гарантия доставки** | Низкая (может отсутствовать) | **Высокая** (обязательны для пайплайна) |
| **Доступ в UI** | Нет | Да (кнопка "Download") |
| **Место хранения** | Runner или S3/MinIO | Сервер GitLab (через API) |
| **Лимиты** | До 4 кэшей на job (GitLab 13.10+) | По объёму (настраивается в плане) |
| **Зависимости** | Не зависит от `dependencies/needs` | Прямая связь с `dependencies` |
| **Срок хранения** | Настраивается на Runner'е | Параметр `expire_in` |
| **Cache Poisoning** | Риск при `policy: push` из MR | Минимальный риск |
| **Кросс-проект** | Недоступен (изолирован по проекту) | Через `needs`/`dependencies` |
| **Размер** | Ограничен диском Runner'а/S3 bucket | По объёму диска GitLab |

**Архитектурный нюанс:** Кэш предназначен для данных, которые *можно пересобрать* в случае утери. Артефакты предназначены для данных, которые *нельзя потерять* (например, билд для деплоя). Подробнее о настройке артефактов — в **[gitlab_ci_artifacts.md](./gitlab_ci_artifacts.md)**.

### Архитектура и уровни хранения

Современный GitLab Runner поддерживает многоуровневую систему оптимизации передачи данных:

1. **Локальный уровень (Fastest):** Использование томов Docker или директорий Shell-раннера.
   - **Механика:** Runner ищет локальный zip-архив в `/home/gitlab-runner/cache/` (путь настраивается).
2. **Удалённый уровень (Distributed):** Интеграция с объектными хранилищами.
   - **Механика:** Runner скачивает кэш по протоколу HTTP/S3, распаковывает его локально перед задачей и упаковывает/загружает обратно после выполнения.
3. **Уровень Registry:** Кэширование Docker-слоёв через Container Registry (BuildKit).
   - **Механика:** Используется отдельный тег `$CI_REGISTRY_IMAGE/cache:latest` для хранения слоёв. Не зависит от Distributed Cache.

#### Механизмы сжатия (Zstd и Fastzip)

С 2024 года стандартом производительности в GitLab CI стали два механизма:

- **Zstd (Zstandard):** Алгоритм сжатия от Meta, который заменил классический Zip.
  - **Преимущество:** Zstd обеспечивает значительно более высокую скорость распаковки (в 3-5 раз быстрее Zip) при сопоставимом или лучшем уровне сжатия. Это критично для `node_modules`, где тысячи мелких файлов.
  - **Поддержка:** GitLab Runner 16.2+ использует Zstd по умолчанию при наличии поддержки на стороне ОС.
- **Fastzip (`FF_USE_FASTZIP`):** Внутренняя реализация Runner'а на языке Go, использующая конкурентную обработку.
  - **Принцип:** Стандартный zip работает в один поток. Fastzip распределяет задачу упаковки/распаковки по всем доступным CPU-ядрам (используя `GOMAXPROCS`), что радикально сокращает время "подготовки" среды в задаче.
  - **Применение:** Особенно эффективен при большом количестве мелких файлов (上千 мелких файлов в `node_modules`).

#### Сравнение алгоритмов сжатия

| Алгоритм | Скорость упаковки | Скорость распаковки | Размер архива | Рекомендация |
| :--- | :--- | :--- | :--- | :--- |
| **zip** (по умолчанию 8.10) | Низкая | Низкая | Средний | Legacy |
| **zstd** (по умолчанию 16.2+) | Высокая | Очень высокая | Малый | Рекомендуется |
| **zstd:1** (fast) | Очень высокая | Очень высокая | Средний | Fast CI |
| **zstd:19** (slow) | Низкая | Высокая | Минимальный | Малый размер |

### Жизненный цикл кэша в задаче

1. **Восстановление (Restore):** Перед выполнением `before_script` GitLab Runner проверяет наличие кэша по ключу. Если используется несколько кэшей (до 4), они восстанавливаются последовательно.
2. **Выполнение:** Задача использует файлы из кэша.
3. **Архивация (Archive):** После завершения скрипта (зависит от `when`) Runner запаковывает указанные пути и загружает их в хранилище. По умолчанию используется политика `pull-push`.

### Механизмы изоляции

По умолчанию кэш изолирован для каждой ветки и проекта. В GitLab введена дополнительная защита для **защищённых веток** (`protected branches`), предотвращающая доступ к их кэшу из обычных веток.

- **Защищённые ветки:** Кэш доступен только задачам на защищённых ветках.
- **Обычные ветки:** Кэш изолирован от защищённых.
- **Параметр `unprotect`:** Позволяет задачам на обычных ветках использовать кэш из защищённых веток (см. [настройку ключей](./cache_keys.md#защита-и-изоляция-кэша)).
- **Параметр `Shared`:** В Distributed Cache все Runner'ы одного проекта делят общий кэш, но это увеличивает риск конкурентной записи.

## Практические сценарии

### Предварительные требования (Prerequisites)

Для успешного использования кэширования необходимо убедиться в соблюдении следующих условий:

- **Версия Runner:** 16.2+ (для полной поддержки Zstd и множественного кэширования).
- **Сетевая доступность:** Runner должен иметь доступ к S3/MinIO по портам 80/443.
- **Права доступа (IAM):** Для S3 требуется политика с правами `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` и `s3:ListBucket` для указанного бакета.
- **Локальные ресурсы:** Достаточное количество свободного места на диске Runner'а для временной распаковки (минимум в 2 раза больше размера `paths`).
- **Время (NTP):** Синхронизация времени критична для Distributed Cache (pre-signed URL имеют TTL).

## Граничные случаи и ограничения

#### Технические лимиты

| Параметр | Лимит | Рекомендация |
| :--- | :--- | :--- |
| Кэшей на задачу | 4 (GitLab 13.10+) | Используйте минимально необходимое количество |
| Файлов в `cache:key:files` | 2 (Gitaly лимит) | Оставьте только lock-файлы |
| `fallback_keys` | 5 (GitLab 16.0+) | Достаточно для большинства сценариев |
| Размер кэша | Ограничен диском Runner'а или S3 bucket | Настройте Lifecycle в S3 |
| `prefix` в `key:files` | Без лимита | Используйте короткие префиксы |

#### Особые сценарии

1. **Конкурентная запись (Concurrent Writes):** Если две параллельные задачи с одним и тем же ключом пытаются загрузить кэш, последняя завершившаяся задача перезапишет данные предыдущей. Используйте `policy: pull` для всех задач, кроме одной "мастер-сборки".

2. **Лимит размера:** В GitLab Runner есть ограничение на размер одного zip-архива (по умолчанию ~5GB, настраивается в Runner конфигурации). Большие кэши лучше разбивать на несколько (до 4 штук).

3. **Cache Miss:** Если кэш не найден, задача продолжится (best-effort). Всегда проектируйте скрипты так, чтобы они могли собрать зависимости с нуля (например, `npm install` без кэша).

4. **Пустой lock-файл:** Если `cache:key:files` ссылается на пустой файл, хеш будет детерминированным и кэш НЕ обновится при изменении зависимостей. Решение: добавьте проверку в `before_script`:
   ```yaml
   before_script:
     - test -s package-lock.json || (echo "ERROR: lock file missing" && exit 1)
   ```

5. **Множественные lock-файлы:** Если ОДИН из файлов в `cache:key:files` не изменился, кэш НЕ обновится даже если другой файл изменился. Решение: используйте отдельные кэши для разных экосистем.

6. **Кэш и `interruptible: false`:** Прерванная задача не сохраняет кэш. Если кэш важен для прерываемых задач, используйте `cache:when: always` (осторожно — кэш сохраняется даже при падении).

7. **Изоляция в матричных сборках:** Все матричные задачи делят один кэш с одним ключом. Решение: используйте уникальный ключ для каждой комбинации:
   ```yaml
   test:
     parallel:
       matrix:
         - PYTHON_VERSION: ["3.10", "3.11", "3.12"]
     cache:
       key: py${PYTHON_VERSION}-deps  # Уникальный ключ
   ```

8. **Кэширование в Docker-контейнерах:** Docker-контейнер ephemeral, локальный кэш недоступен. Решение: используйте Distributed Cache (S3/MinIO).

## Лучшие практики

### Выбор типа ключа

| Сценарий | Рекомендуемый ключ | Причина |
| :--- | :--- | :--- |
| Lock-файлы (npm, pip, bundler) | `cache:key:files` | Детерминированная инвалидация |
| Go-модули без `go.sum` | `cache:key:prefix` | Хеш всего `vendor/` |
| Глобальные утилиты (tflint, hadolint) | Статический ключ (`"tools-v2"`) | Неизменяемые бинарники |
| Матричные сборки | `key: $CI_JOB_NAME-$TARGET` | Изоляция по комбинации |
| Feature-ветки → main | `fallback_keys: [main]` | Использование кэша main |
| Шардинг тестов | `key: $CI_JOB_NAME-$CI_NODE_INDEX` | Уникальность шарда |

### Асимметричные политики

| Тип задачи | `cache:policy` | Причина |
| :--- | :--- | :--- |
| Установка зависимостей (`npm ci`, `pip install`) | `pull-push` | Кэш создаётся и обновляется |
| Тесты (`npm test`, `pytest`) | `pull` | Только чтение кэша |
| Линтеры (`eslint`, `pylint`) | `pull` | Не должны перезаписывать кэш |
| Сборка (`go build`, `cargo build`) | `pull` | Артефакты в artifacts, не в кэш |
| Deploy | `pull` | Кэш для зависимостей, не для деплоя |

### Организация кэша

| Практика | Описание | Приоритет |
| :--- | :--- | :--- |
| Префикс по проекту/сервису | `myproject-npm-$CI_COMMIT_REF_SLUG` | Высокий |
| Разделение тяжёлых зависимостей | `node_modules` отдельно от `dist/` | Средний |
| `fallback_keys` в 2 уровнях | main → global | Средний |
| Документирование ключей в README | Для новых членов команды | Низкий |

### Безопасность

| Практика | Описание | Приоритет |
| :--- | :--- | :--- |
| Не использовать `unprotect: true` для зависимостей | Cache poisoning через MR | Критический |
| `policy: pull` для тестов | Предотвращение перезаписи кэша | Высокий |
| `fallback_keys` вместо статических ключей | Изоляция веток + кэш main | Высокий |
| Ограничение `files` до 2 файлов | Предотвращение Gitaly timeout | Средний |

## Устранение неполадок

### Диагностика через логи Runner'а

```bash
# Поиск логов кэша
grep -i "cache" /var/log/gitlab-runner/*.log

# Проверка конфигурации Runner'а
cat /etc/gitlab-runner/config.toml | grep -A10 "\[cache\]"

# Просмотр локального кэша
ls -la /home/gitlab-runner/cache/
du -sh /home/gitlab-runner/cache/
```

### Диагностика через API

```bash
# Просмотр всех кэшей проекта
curl --header "PRIVATE-TOKEN: $TOKEN" \
  "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/cache" | \
  jq '.[] | {key, size, created_at, last_used_at}'

# Очистка кэша по ключу
curl --request DELETE --header "PRIVATE-TOKEN: $TOKEN" \
  "https://gitlab.example.com/api/v4/projects/$PROJECT_ID/cache?key=$CACHE_KEY"
```

### Таблица устранения неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| `Cache not found` | Неверный ключ или изоляция веток | Проверьте, что ключ совпадает. Используйте `fallback_keys`. |
| `Permission denied` на S3 | Недостаточно прав у IAM Role | Добавьте `s3:ListBucket` и `s3:PutObject`. |
| Кэш распаковался, но пуст | Пути в `paths` указаны абсолютно | Используйте только относительные пути от корня проекта. |
| Медленная загрузка кэша | Узкое место в сети или CPU | Включите `FF_USE_FASTZIP` и проверьте `Zstd`. |
| `Gitaly Timeout` при создании Pipeline | Слишком много файлов в `cache:key:files` (максимум 2) | Используйте статический ключ с префиксом или якоря YAML. |
| `Archive is up to date!` и кэш не обновляется | `FF_SKIP_NOOP_CACHE` работает корректно | Это нормальное поведение — файлы не изменились. |
| `No space left on device` при загрузке кэша | Размер кэша превышает диск Runner'а | Очистите кэш через UI (Clear runner caches) или увеличьте лимит. |
| `Cache key is invalid` | Использование запрещённых символов в ключе | Используйте только буквы, цифры, `-`, `_`, `/`. |

## Дополнительная информация

### Настройка распределённого кэша

#### Пример для S3 / MinIO
Конфигурация в `/etc/gitlab-runner/config.toml`:

```toml
[runners.cache]
  Type = "s3"
  Path = "cache"
  Shared = true
  [runners.cache.s3]
    ServerAddress = "s3.amazonaws.com" # Или локальный MinIO: "minio.example.com"
    BucketName = "gitlab-cache"
    BucketLocation = "us-east-1"
    AuthenticationType = "iam" # Рекомендуется для AWS. Для MinIO используйте "access-key"
    # AccessKey = "ACCESS_KEY"
    # SecretKey = "SECRET_KEY"
    Insecure = false
```

#### Пример для Azure Blob Storage
```toml
[runners.cache]
  Type = "azure"
  Path = "cache"
  Shared = true
  [runners.cache.azure]
    AccountName = "myaccount"
    AccountKey = "mykey"
    ContainerName = "gitlab-cache"
```

### Тюнинг производительности и Fastzip

Для экстремального ускорения на многоядерных системах используйте расширенную настройку переменных в `.gitlab-ci.yml`:

```yaml
variables:
  # Включает конкурентную упаковку (использует все ядра CPU)
  FF_USE_FASTZIP: "true"
  
  # Баланс между скоростью передачи и нагрузкой на CPU
  # fast/fastest — для медленных дисков/сети
  # slow/slowest — если CPU перегружен, но сеть быстрая
  CACHE_COMPRESSION_LEVEL: "fast"
  
  # Пропуск сжатия для уже сжатых файлов (бинарники, картинки)
  # Позволяет сэкономить CPU на "пустом" пережатии
  CACHE_REQUEST_TIMEOUT: 3600 # Увеличение таймаута для очень больших кэшей
```
