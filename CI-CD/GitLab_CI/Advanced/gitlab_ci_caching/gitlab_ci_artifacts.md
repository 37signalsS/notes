# Артефакты в GitLab CI

## Определения

**Артефакт (Artifact)** — файлы или директории, которые сохраняются после выполнения задачи (job) и передаются между стадиями пайплайна. Артефакты хранятся централизованно на сервере GitLab и предназначены для доставки результатов сборки (бинарные файлы), отчетов и метаданных.

**Отчет (Report)** — специализированный тип артефакта, который GitLab автоматически парсит и визуализирует в интерфейсе (Merge Request, вкладка Tests). Примеры: JUnit XML, отчеты о покрытии кода, сканы безопасности.

**Зависимости (Dependencies)** — механизм явного указания задач, артефакты которых должны быть загружены в текущую задачу. Позволяет оптимизировать время выполнения, исключая загрузку лишних данных.

Подробное сравнение с механизмом кэширования: [Обзор кэширования](./caching_overview.md).

## Основные концепции

### Эфемерность среды и передача данных

GitLab Runner (особенно при использовании Docker или Kubernetes Executor) запускает каждую задачу в изолированной эфемерной среде. После завершения задачи среда уничтожается вместе со всеми локальными изменениями.

Артефакты решают проблему передачи данных между задачами:
1. **Архивация:** После выполнения скриптов Runner упаковывает указанные пути в `.zip` архив.
2. **Загрузка:** Архив передается на сервер GitLab.
3. **Восстановление:** В задачах последующих стадий Runner скачивает архив и распаковывает его в рабочую директорию.

```yaml
# Пример: Передача бинарного файла между стадиями
build_app:
  stage: build
  script:
    - go build -o app main.go
  artifacts:
    paths:
      - app
    expire_in: 1 hour

test_app:
  stage: test
  script:
    - ./app --version  # Файл 'app' доступен благодаря артефактам
```

По умолчанию артефакты задачи доступны **во всех задачах последующих стадий** того же пайплайна. Для передачи артефактов между разными пайплайнами (downstream pipelines) используются механизмы [multi-project pipelines](../Downstream_Pipelines/multi_project_pipelines.md) и [parent-child pipelines](../Downstream_Pipelines/parent_child_pipelines.md).

### Ключевые параметры конфигурации

| Параметр | Описание | Пример |
| :--- | :--- | :--- |
| `paths` | Список файлов и директорий для сохранения | `paths: [bin/, dist/*.jar]` |
| `exclude` | Файлы, которые НЕ нужно включать в артефакты | `exclude: ["**/*.log"]` |
| `expire_in` | Срок хранения (по умолчанию 30 дней) | `expire_in: 1 week`, `never` |
| `name` | Имя архива для скачивания через UI | `name: "$CI_JOB_NAME-$CI_COMMIT_REF_NAME"` |
| `when` | Условие сохранения (`on_success`, `on_failure`, `always`) | `when: always` |
| `reports` | Специальные отчеты для визуализации в GitLab | `reports: {junit: test.xml}` |
| `public` | Доступность артефактов в публичных проектах | `public: false` |
| `untracked` | Включать файлы, не отслеживаемые Git | `untracked: true` |

### Управление зависимостями и производительность

По умолчанию каждая задача скачивает артефакты **всех** задач предыдущих стадий. В больших проектах это может приводить к значительному замедлению из-за загрузки сотен мегабайт ненужных данных.

#### Оптимизация через `dependencies` и `needs`
- **`dependencies: []`** — отключает загрузку любых артефактов в задачу.
- **`dependencies: [build_job]`** — загружает артефакты только из указанных задач.
- **`needs` (DAG)** — если используется `needs`, GitLab автоматически загружает артефакты только от задач, перечисленных в блоке `needs`. Если нужны артефакты от других задач (из предыдущих стадий, но не в `needs`), необходимо явно указать их в `dependencies`.

#### Сжатие и флаги ускорения
Для ускорения работы с артефактами (особенно в GitLab 16.x/17.x+) рекомендуется использовать следующие переменные:

```yaml
variables:
  FF_USE_FASTZIP: "true"             # Включает быстрый конкурентный zip
  ARTIFACT_COMPRESSION_LEVEL: "fast"  # Уровни: fastest, fast, default, slow, slowest
```

### Отчеты через артефакты

GitLab автоматически обрабатывает специальные типы отчетов и отображает их в Merge Request и на вкладке Pipeline:

```yaml
test:
  stage: test
  script:
    - pytest --junitxml=test-results.xml --cov=app --cov-report=xml
  artifacts:
    reports:
      junit: test-results.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
```

**Основные типы отчетов:**
- `junit` — результаты тестирования.
- `coverage_report` — покрытие кода тестами.
- `codequality` — анализ качества кода (Lint).
- `dotenv` — динамические переменные окружения для последующих задач.
- `terraform` — планы и результаты выполнения Terraform.
- `sast`, `dast`, `secret_detection` — отчеты безопасности.
- `accessibility` — результаты тестирования доступности интерфейса.

### Срок хранения и лимиты

Срок хранения задается параметром `expire_in`. Формат: `<число> <единица>` (`1 hour`, `7 days`, `30 days`) или `never` (бессрочно).

| Значение | Когда использовать |
| :--- | :--- |
| `1 week` | Временные артефакты (промежуточные сборки, логи) |
| `30 days` | По умолчанию (баланс между доступностью и местом в хранилище) |
| `never` | Релизные артефакты, которые не должны удаляться автоматически |

**Примечание:** Максимальный размер артефакта настраивается на уровне экземпляра GitLab. Лимиты можно проверить в **Admin Area → Settings → General → Continuous Integration and Deployment**.

## Практические сценарии

### Сценарий 1: Передача временных артефактов

`build` стадия создает артефакт, `test` стадия его использует:

```yaml
stages:
  - build
  - test

build:
  stage: build
  script:
    - ./gradlew clean build
    - mkdir -p dist && cp build/libs/app.jar dist/app-1.2.3-${CI_COMMIT_SHORT_SHA}.jar
    - sha256sum dist/* > dist/checksums.txt
  artifacts:
    paths:
      - dist/
    expire_in: 7 days

release:
  stage: release
  script: make release
  artifacts:
    paths: [release/*.tar.gz]
    expire_in: never
```

### Сценарий 2: Отчёты о тестах и покрытии

```yaml
test:
  stage: test
  script:
    - pytest --junitxml=test-results.xml --cov=app --cov-report=xml
  artifacts:
    paths:
      - test-results/
    reports:
      junit: test-results.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml
    expire_in: 1 week
```

### Сценарий 3: Комбинация кэша и артефактов

Кэш ускоряет установку зависимостей, артефакты передают результаты сборки — подробнее см. в документе: **[Практические сценарии кэширования](./cache_scenarios.md)**.

### Сценарий 4: Отладка — сохранение логов при падении задачи

Артефакты полезны не только для передачи файлов между задачами, но и для отладки. Если задача завершается с ошибкой, логи приложения могут помочь в диагностике, даже если они не попали в стандартный вывод (stdout).

```yaml
integration_test:
  stage: test
  script:
    - ./run_tests.sh --log-file=test-debug.log 2>&1
  artifacts:
    paths:
      - test-debug.log
    expire_in: 3 days
    when: always  # Сохранять артефакты независимо от результата задачи
```

Ключевой параметр `when: always` гарантирует, что артефакты будут сохранены даже при failed-задаче. Это позволяет скачать и проанализировать логи после сбоя через интерфейс GitLab (кнопка **Job Artifacts** на странице задачи).

### Просмотр артефактов в интерфейсе GitLab

После выполнения задачи с артефактами в GitLab появляется секция **Job Artifacts** на странице задачи. Доступные действия:

- **Download** — скачать архив со всеми артефактами задачи.
- **Browse** — просмотр содержимого архива (для поддерживаемых форматов, например HTML-отчеты).

Артефакты также доступны через API GitLab:

```bash
# Скачать артефакты конкретной задачи
curl --header "PRIVATE-TOKEN: <token>" \
  "https://gitlab.example.com/api/v4/projects/<id>/jobs/<job_id>/artifacts"
```

## Дополнительная информация

### Общие рекомендации

1. **Устанавливайте `expire_in`** для временных артефактов, чтобы избежать переполнения хранилища.
2. **Используйте `dependencies`** для явного указания задач, артефакты которых действительно нужны.
3. **Применяйте `reports`** для автоматической интеграции результатов тестирования в интерфейс GitLab.
4. **Исключайте лишние файлы** через `exclude` для уменьшения размера архива и ускорения пайплайна.
5. **Для релизных артефактов** используйте `expire_in: never`.
6. **Для отладки** используйте `when: always`, чтобы артефакты сохранялись даже при падении задачи.
