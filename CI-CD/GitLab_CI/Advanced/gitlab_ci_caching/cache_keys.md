# Ключи кэша и политики в GitLab CI

## Определения

**Ключ кэша (`cache:key`)** — уникальный идентификатор, определяющий область и версию кэша в хранилище (Distributed Cache или локальный диск Runner'а). В отличие от артефактов, кэш является хранилищем с гарантией "best-effort": GitLab может удалить старый кэш для освобождения места.

**Политика кэширования (`cache:policy`)** — параметр, определяющий режим взаимодействия задачи с хранилищем: загрузка (`pull`), сохранение (`push`) или полный цикл (`pull-push`).

**Fallback key** — список резервных ключей, используемых для поиска альтернативных версий кэша при отсутствии точного совпадения по основному ключу.

## Основные концепции

### Типы ключей

#### Статический ключ
```yaml
cache:
  key: "global-npm-cache"
  paths:
    - node_modules/
```
**Использование:** Общий кэш для всех задач. Рекомендуется использовать статические ключи только для данных, которые не зависят от состояния кода (например, базовые SDK), так как существует риск "отравления" кэша некорректными данными из экспериментальных веток.

#### Динамический ключ на базе переменных
```yaml
cache:
  key: "$CI_COMMIT_REF_SLUG"
  paths:
    - vendor/
```
**Использование:** Изоляция кэша по веткам. Предотвращает конфликты при параллельной разработке разных фич.
- **`$CI_JOB_NAME_SLUG`**: Привязывает кэш к конкретной задаче, что полезно, если разные задачи используют разные версии зависимостей.
- **`$CI_CONCURRENT_ID`**: Используется для изоляции кэша между параллельными запусками одной и той же задачи на одном Runner'е (требует Distributed Cache для эффективности).

#### Ключ по хешу файлов (Рекомендуется)
```yaml
cache:
  key:
    files:
      - package-lock.json
      - Gemfile.lock
    prefix: "prod-deps-$CI_JOB_NAME"
  paths:
    - node_modules/
```
**Использование:** GitLab вычисляет SHA256 хеш содержимого указанных файлов.
- **`prefix`**: Позволяет добавить статический префикс к хешу, что критично при обновлении рантаймов (например, Node.js 18 -> 20), когда хеш `package-lock.json` тот же, но бинарные зависимости несовместимы.
- **Лимиты (17.x):** GitLab ограничивает количество Gitaly-вызовов при вычислении хеша для предотвращения таймаутов в огромных монорепозиториях.

### Множественное кэширование (Multiple Caches)

С версии GitLab 13.10 вы можете определять до **4 независимых кэшей** в одной задаче. Это позволяет эффективно разделять зависимости (например, `node_modules` и кэш сборки `dist/cache`).

```yaml
test_job:
  cache:
    - key: npm-$CI_COMMIT_REF_SLUG
      paths: [node_modules/]
      policy: pull
    - key: build-assets
      paths: [dist/cache/]
      policy: pull-push
```
**Важно:** Все кэши одной задачи при передаче на Runner упаковываются в единый контекст выполнения, но хранятся в S3/MinIO как отдельные объекты.

### Защита и изоляция кэша

С версии GitLab 15.0 по умолчанию включена изоляция кэша между **защищёнными** (`protected`) и **незащищёнными** ветками. Это критично для предотвращения атак типа "cache poisoning", когда вредоносный код в feature-ветке может подменить зависимости, используемые при сборке в `main`.

**Механизм работы:**
GitLab автоматически добавляет суффикс к ключу кэша:
- `-protected` для защищённых веток.
- `-non_protected` для всех остальных.

**Параметр `unprotect`:**
Позволяет принудительно разрешить незащищённым веткам доступ к кэшу защищённых веток.
```yaml
cache:
  key: "shared-cache"
  paths: [bin/]
  unprotect: true
```
**Важно:** Использование `unprotect: true` рекомендуется только для статических данных или инструментов, которые не меняются в ходе пайплайна. Для зависимостей (`node_modules`) лучше использовать **односторонний pull**: настроить `fallback_keys` для feature-веток на чтение кэша из `main`.

Глобально это поведение управляется в `Settings > CI/CD > General pipelines > Use separate caches for protected branches`.

### Политики кэширования

Определяют, как задача взаимодействует с хранилищем в начале и в конце выполнения.

| Политика | Описание | Когда использовать |
| :--- | :--- | :--- |
| `pull-push` (по умолчанию) | Скачивает в начале, загружает в конце | Задачи сборки, обновляющие зависимости |
| `pull` | Только скачивает, не сохраняет | Тесты, линтеры, деплой (ускоряет пайплайн) |
| `push` | Только загружает, не скачивает | Задачи первичной подготовки кэша |

**Параметр `when`:**
Определяет условие сохранения кэша:
- `on_success` (по умолчанию) — только при успешном завершении задачи.
- `on_failure` — только при падении задачи.
- `always` — сохранять в любом случае.

### Резервные ключи — Fallback Keys

Позволяют использовать кэш от другой ветки (например, `main`), если для текущей ветки кэш ещё не сформирован. Начиная с GitLab 16.0, можно указывать до **5** резервных ключей.

```yaml
test:
  cache:
    - key: cache-$CI_COMMIT_REF_SLUG
      fallback_keys:
        - cache-$CI_DEFAULT_BRANCH
        - cache-common
      paths:
        - vendor/ruby
```

**Алгоритм поиска:**
1. Поиск по основному `key`.
2. Поочерёдный поиск по списку `fallback_keys` (до 5 записей).
3. Если ни один кэш не найден — запуск задачи "с нуля".

## Дополнительная информация

### Технические ограничения и нюансы

1. **Множественность:** Не более **4 независимых кэшей** на одну задачу.
2. **Резервирование:** Максимум **5 ключей** в списке `fallback_keys`.
3. **Хеширование файлов:** `cache:key:files` поддерживает максимум **2 файла**. При использовании больших монорепозиториев GitLab накладывает лимиты на количество обращений к Gitaly для предотвращения перегрузки сервера при генерации пайплайна.
4. **Хранение:** Кэш — это временное хранилище. GitLab Runner не гарантирует наличие кэша при каждом запуске.
5. **Пути:** Все пути в `paths` должны быть относительными и находиться внутри директории `$CI_PROJECT_DIR`.

### Рекомендации по производительности

1. **`FF_USE_FASTZIP: "true"`**: Переменная окружения для Runner, включающая использование более быстрого алгоритма сжатия (написан на Go).
2. **`zstd` сжатие**: Если ваш Runner версии 16.2+, GitLab использует `zstd` по умолчанию, что значительно быстрее стандартного `zip`.
3. **`policy: pull`**: Всегда используйте эту политику для задач тестирования и линтинга. Это экономит время на архивацию и загрузку (push) кэша обратно в хранилище.
