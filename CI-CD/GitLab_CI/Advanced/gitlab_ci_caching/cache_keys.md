# Ключи кэша и политики в GitLab CI

## Определения

**Ключ кэша (`cache:key`)** — уникальный идентификатор, определяющий область и версию кэша. При изменении ключа GitLab создаёт новый кэш. По умолчанию (если ключ не указан) используется ключ `default`.

**Политика кэширования (`cache:policy`)** — параметр, определяющий режим работы с кэшем: загрузка (`pull`), сохранение (`push`) или оба действия (`pull-push`).

**Fallback key** — резервный ключ, используемый для поиска кэша, если основной ключ не найден.

## Основные концепции

### Типы ключей

#### Статический ключ
```yaml
cache:
  key: "global-npm-cache"
  paths:
    - node_modules/
```
**Использование:** Общий кэш для всех задач и веток. Не рекомендуется для production из-за высокого риска использования неактуальных зависимостей и конфликтов между ветками.

#### Динамический ключ — переменные
```yaml
cache:
  key: "$CI_COMMIT_REF_SLUG"
  paths:
    - vendor/
```
**Использование:** Раздельный кэш для каждой ветки. Изолирует состояние веток, предотвращая перезапись кэша при параллельной разработке. Полезные переменные:
- `$CI_JOB_NAME_SLUG` — для кэша, привязанного к конкретной задаче.
- `$CI_DEFAULT_BRANCH` — для доступа к кэшу основной ветки.

#### Ключ по файлам зависимостей — рекомендуется
```yaml
cache:
  key:
    files:
      - package-lock.json
      - Gemfile.lock
    prefix: "prod-deps"
  paths:
    - node_modules/
    - vendor/ruby
```
**Использование:** GitLab вычисляет SHA256 хеш содержимого файлов (до 2 файлов). Кэш обновляется автоматически только при изменении зависимостей. Параметр `prefix` позволяет разделить кэши для разных окружений или версий рантайма.

### Защита и изоляция кэша

По умолчанию кэши, созданные на защищённых ветках (`protected branches`), изолированы. Задачи на незащищённых ветках не могут получить к ним доступ или перезаписать их.

**Параметр `unprotect`:**
```yaml
cache:
  key: "shared-cache"
  paths:
    - bin/
  unprotect: true
```
Если установлено `true`, задачи на незащищённых ветках получают доступ к кэшу, созданному на защищённых ветках.

### Политики кэширования

Определяют, как задача взаимодействует с хранилищем в начале и в конце выполнения.

| Политика | Описание | Когда использовать |
| :--- | :--- | :--- |
| `pull-push` (по умолчанию) | Скачивает в начале, загружает в конце | Задачи сборки, обновляющие зависимости |
| `pull` | Только скачивает, не сохраняет | Тесты, линтеры, деплой (ускоряет пайплайн) |
| `push` | Только загружает, не скачивает | Задачи первичной подготовки кэша |

**Параметр `when`:**
Определяет условие сохранения кэша:
- `on_success` (по умолчанию) — только при успешном завершении задачи.
- `on_failure` — только при падении задачи.
- `always` — сохранять в любом случае.

### Резервные ключи — Fallback Keys

Позволяют использовать кэш от другой ветки (например, `main`), если для текущей ветки кэш ещё не сформирован. Начиная с GitLab 16.0, можно указывать до **5** резервных ключей.

```yaml
test:
  cache:
    - key: cache-$CI_COMMIT_REF_SLUG
      fallback_keys:
        - cache-$CI_DEFAULT_BRANCH
        - cache-common
      paths:
        - vendor/ruby
```

**Алгоритм поиска:**
1. Поиск по основному `key`.
2. Поочерёдный поиск по списку `fallback_keys` (до 5 записей).
3. Если ни один кэш не найден — запуск задачи "с нуля".

## Дополнительная информация

### Ограничения
- **Количество:** Не более 4 кэшей на одну задачу.
- **Размер:** Ограничен настройками сервера (обычно 5 ГБ для GitLab.com).
- **Файлы:** `cache:key:files` поддерживает максимум 2 файла.
- **Пути:** Должны находиться внутри директории проекта (`$CI_PROJECT_DIR`).

### Рекомендации
1. **Используйте `pull` в тестах:** Это экономит время и ресурсы хранилища, так как тесты обычно не меняют зависимости.
2. **Версионируйте префиксы:** При обновлении версии языка (например, Node.js 18 → 20) меняйте `prefix`, чтобы избежать конфликтов бинарных зависимостей.
3. **Очищайте кэш:** При возникновении странных ошибок сборки используйте кнопку "Clear runner caches" в UI GitLab.
