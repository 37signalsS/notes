# Валидация и версионирование пайплайнов GitLab CI/CD

## Определения

- **Валидация пайплайнов** — процесс проверки синтаксиса, интерполяции переменных и логической корректности файлов `.gitlab-ci.yml`. 
- **CI Lint API (Dry Run)** — расширенный метод валидации (GitLab 16.11+), который имитирует создание пайплайна, проверяя права доступа, наличие образов и корректность `rules` в текущем контексте.
- **Версионирование шаблонов** — практика использования фиксированных версий (через Git-теги, SHA или SemVer) для подключаемых ресурсов, обеспечивающая стабильность инфраструктуры.
- **Pipeline Execution Policies** — механизм принудительного исполнения и версионирования политик безопасности и комплаенса на уровне организации (GitLab 17.x).

## Основные концепции

### Зачем нужна валидация?

При усложнении конфигурации (множество `include`, вложенные `inputs`, динамические дочерние пайплайны) проверка синтаксиса становится критичной:

- **Предотвращение поломки основной ветки** — ошибки интерполяции и цикличные зависимости отлавливаются до слияния.
- **Проверка `spec:inputs`** — валидация типов данных и обязательных параметров в компонентах каталога.
- **Enforcement (Принуждение)** — использование политик выполнения гарантирует, что даже если разработчик изменит версию шаблона в своем проекте, критические проверки безопасности будут выполнены по утвержденной версии.

### Подходы к версионированию

1. **Традиционный (Git-теги/SHA)**: Использование `ref: v1.0.0` или `ref: <commit_sha>`. Обеспечивает максимальную стабильность, но требует ручного обновления при патчах.
2. **Семантический (CI/CD Catalog)**: Использование `include:component` с поддержкой частичных соответствий:
   - `@1.2.3` — строгая фиксация.
   - `@1.2` — автоматическое получение `patch` обновлений (эквивалент `~1.2.0`).
   - `@1` — автоматическое получение `minor` и `patch` обновлений (эквивалент `^1.0.0`).
3. **Динамический (Ветки)**: Использование `ref: main`. Удобно для разработки, но опасно для продакшена (любое изменение в шаблоне может сломать сотни пайплайнов).

## Практические сценарии

### Сценарий 1: Валидация через Lint API с режимом Dry Run

В отличие от обычной проверки синтаксиса, `dry_run: true` проверяет, сможет ли пайплайн запуститься для конкретной ветки.

```yaml
validate_logic:
  stage: lint
  image: alpine:3.21
  script:
    - apk add --no-cache curl jq
    - |
      # Подготовка JSON с параметром dry_run
      content=$(cat .gitlab-ci.yml)
      data=$(jq --null-input --arg yaml "$content" '{content: $yaml, dry_run: true}')
      
      response=$(curl --fail -sS \
            --header "PRIVATE-TOKEN: ${CI_LINT_TOKEN}" \
            --header "Content-Type: application/json" \
            --data "$data" \
            "${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/ci/lint")
      
      if [[ $(echo "$response" | jq '.valid') != "true" ]]; then
        echo "Pipeline logic errors detected:"
        echo "$response" | jq -r '.errors[]'
        exit 1
      fi
```

### Сценарий 2: Версионирование компонентов каталога

Использование различных стратегий обновления для разных окружений.

```yaml
include:
  # Для критичных сборок — полная фиксация
  - component: $CI_SERVER_FQDN/org/security-scan@1.5.2
  
  # Для общих утилит — получение исправлений безопасности (patch)
  - component: $CI_SERVER_FQDN/org/helpers@2.1
    inputs:
      debug: "true"

  # Для инструментов разработки — всегда свежий minor
  - component: $CI_SERVER_FQDN/org/linter@3
```

### Сценарий 3: Локальная валидация и отладка (glab)

Инструмент `glab` позволяет увидеть финальный вид YAML после всех `include` и `extends`.

```bash
# Валидация с учетом текущих переменных окружения
glab ci lint --dry-run

# Просмотр "развернутого" YAML для поиска ошибок в наследовании
glab ci lint --show-expanded
```

### Сценарий 4: Валидация динамически генерируемых пайплайнов

При использовании **Parent-Child Pipelines** с генерацией артефакта.

```yaml
generate_and_validate:
  stage: prepare
  script:
    - python3 gen_pipeline.py > child-pipeline.yml
    - # Валидация сгенерированного файла перед триггером
    - glab ci lint child-pipeline.yml || exit 1
  artifacts:
    paths: [child-pipeline.yml]
```

## Дополнительная информация

### Pipeline Execution Policies (GitLab 17.x)

Это высший уровень управления версиями. Организация может создать проект с политиками, который будет «внедрять» задачи во все проекты группы.
- **Необходмость**: Заменяет устаревшие Compliance Pipelines.
- **Гарантия**: Разработчики не могут переопределить или пропустить эти задачи.
- **Версионирование**: Сама политика может ссылаться на конкретный тег компонента, обеспечивая единообразие во всем холдинге.
