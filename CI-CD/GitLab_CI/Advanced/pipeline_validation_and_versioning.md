# Валидация и версионирование пайплайнов GitLab CI/CD

## Определения

- **Валидация пайплайнов** — процесс проверки синтаксиса и логической корректности файлов `.gitlab-ci.yml` и подключаемых ресурсов. Основной инструмент — **GitLab CI Lint API**.
- **Версионирование шаблонов** — практика использования фиксированных версий (через Git-теги или SHA) для подключаемых файлов (`include`), обеспечивающая стабильность и предсказуемость сборки.
- **CI/CD Components** — современный стандарт GitLab для создания, версионирования и публикации переиспользуемых блоков конфигурации с встроенной типизацией и валидацией.

## Основные концепции

### Зачем нужна валидация?

При усложнении конфигурации (множество `include`, сложные `rules`, динамические пайплайны) проверка синтаксиса «на глаз» становится невозможной. Автоматическая валидация решает следующие задачи:

- **Предотвращение поломки основной ветки** — ошибки синтаксиса отлавливаются до слияния (Merge Request).
- **Валидация динамических пайплайнов** — проверка генерируемого YAML-кода перед его выполнением.
- **Гарантия корректности компонентов** — проверка того, что изменения в общем шаблоне не нарушают спецификацию.

### Подходы к версионированию

Использование `include` без указания версии (`ref`) создает хрупкую связь: любое изменение в источнике немедленно влияет на все зависимые проекты.

1. **Традиционный (Git-теги)**: Использование `ref: v1.0.0` в директиве `include:project`.
2. **Современный (CI/CD Catalog)**: Использование `include:component` с поддержкой семантического версионирования (SemVer). Это позволяет использовать частичные версии (например, `@1.2`), автоматически получая исправления (patch), но защищая от ломающих изменений (major).

## Практические сценарии

### Сценарий 1: Автоматическая валидация шаблонов через Lint API

Этот метод позволяет проверять YAML-файлы в репозитории шаблонов, даже если они не являются полноценным пайплайном.

```yaml
stages:
  - lint

validate_templates:
  stage: lint
  image: alpine:3.21
  rules:
    - if: $CI_COMMIT_BRANCH
      when: always
  before_script:
    - apk add --no-cache curl jq
  script:
    - |
      find templates -type f \( -name '*.yml' -o -name '*.yaml' \) -print0 | while IFS= read -r -d $'\0' file;
      do
        printf "Validating %s\n" "${file}"
        yaml_content=$(cat "${file}")
        
        # Формируем JSON-тело запроса
        data=$(jq --null-input --arg yaml "${yaml_content}" '. | {content: $yaml}')
        
        # Отправка запроса к GitLab CI Lint API
        response=$(curl --fail -sS --show-error \
              --header "PRIVATE-TOKEN: ${GITLAB_PRIVATE_TOKEN}" \
              --header "Content-Type: application/json" \
              --data "$data" \
              "${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/ci/lint")
        
        # Проверка статуса валидации
        if ! valid=$(printf "%s" "$response" | jq --raw-output '.valid'); then
          printf "Validation failed for %s:\n" "${file}"
          printf "%s" "$response" | jq -r '.errors[]'
          exit 1
        fi
        
        printf "Validation successful for %s\n\n" "${file}"
      done
```

> **Важно:** Переменная `GITLAB_PRIVATE_TOKEN` должна иметь права `api` и быть помечена как **Masked**.

### Сценарий 2: Версионирование через Git-теги

Использование тегов гарантирует, что пайплайн не сломается при обновлении репозитория с шаблонами.

```yaml
include:
  - project: 'devops/ci-templates'
    file: '/build/docker.yaml'
    ref: 'v2.1.0' # Фиксированная версия
```

При переходе на новую версию рекомендуется сначала протестировать её в отдельной ветке:
```yaml
include:
  - project: 'devops/ci-templates'
    file: '/build/docker.yaml'
    ref: 'feature/new-build-logic' # Временная ветка для теста
```

### Сценарий 3: Локальная валидация через GitLab CLI (glab)

Для быстрой проверки пайплайна без коммита в репозиторий используйте утилиту `glab`.

```bash
# Проверка текущего .gitlab-ci.yml
glab ci lint

# Проверка пайплайна с учетом всех include (развернутый вид)
glab ci lint --show-expanded
```

## Дополнительная информация

### Особенности CI/CD Catalog (GitLab 16+)

Для новых проектов рекомендуется переходить на **CI/CD Components**. Они предоставляют:
- **Автоматическую документацию** на основе блока `spec:inputs`.
- **Семантическое версионирование** (обязательно для публикации в каталоге).
- **Визуальный каталог** для поиска проверенных решений в рамках организации.
