# Продвинутые рабочие процессы GitLab CI/CD

## Определения

**Продвинутые рабочие процессы (Advanced Workflows)** — это совокупность методов и директив для построения сложных, масштабируемых и отказоустойчивых пайплайнов. Они позволяют реализовать динамическое управление задачами, оптимизировать потребление ресурсов и обеспечить соответствие корпоративным стандартам безопасности.

**Ключевые инструменты и директивы:**

- **`rules` и `workflow:rules`**: Условное управление запуском задач и всего пайплайна на основе контекста (ветки, переменные, изменения файлов).
- **`needs` (DAG)**: Создание направленных ациклических графов для запуска задач сразу по готовности зависимостей.
- **`parallel:matrix`**: Параллелизация однотипных задач с разными параметрами.
- **`resource_group`**: Сериализация задач для предотвращения гонок состояний (например, при деплое).
- **Pipeline Components & Inputs**: Современный стандарт (GitLab 17+) для создания типизированных и версионируемых модулей с использованием `spec:inputs`.
- **OIDC (ID tokens)**: Безопасная аутентификация во внешних системах (AWS, GCP, Vault) без использования долгоживущих секретов.
- **Pipeline Execution Policies**: Механизм принудительного выполнения задач безопасности и соответствия (compliance) на уровне группы или инстанса (GitLab 17.x).

## Основные концепции

### Оптимизация и производительность

Современные пайплайны должны быть быстрыми и экономичными. Основные методы:

1. **Ациклические графы (DAG)**: Директива `needs` позволяет задачам игнорировать границы стадий.
   - **`needs:optional`**: Позволяет зависеть от задачи, которая может быть не включена в пайплайн (GitLab 17.4+).
2. **Матричные сборки**: Использование `parallel:matrix` для параллельного тестирования. Для сокращения времени ожидания рекомендуется комбинировать с `needs`.
3. **Автоматическая отмена (`workflow:auto_cancel`)**:
   - **`on_new_commit`**: Отменяет старые пайплайны при пуше в ту же ветку. Режимы: `conservative` (не отменять критичные), `interruptible` (только помеченные задачи), `none`.
   - **`on_job_failure`**: Режим `all` немедленно останавливает весь пайплайн при падении любой задачи, экономя время и деньги (особенно в облачных раннерах).
4. **Прерывание задач (`interruptible`)**: Задаче необходимо явно указать `interruptible: true`, чтобы она могла быть отменена механизмом `auto_cancel`.

### Безопасность и Compliance

1.  **Zero Trust через ID Tokens**: Использование временных JWT-токенов (`id_tokens`) для федерации идентичности (Workload Identity Federation). Это исключает компрометацию статических ключей.
2.  **Pipeline Execution Policies**: Позволяют администраторам групп внедрять обязательные стадии (например, `security-scan`) во все проекты без изменения их `.gitlab-ci.yml`. Это гарантирует, что разработчики не смогут обойти проверки безопасности.
3.  **Masked & Protected Variables**: Использование маскирования для предотвращения утечки секретов в логи и ограничение доступа к переменным только в защищенных ветках.

### Сложные структуры пайплайнов

1.  **Parent-Child Pipelines**: Решение для монорепозиториев. Позволяет разделять конфигурацию на основной (родительский) и дочерние пайплайны.
    -   **Преимущества**: Изоляция логики сервисов, запуск только измененных частей (через `rules:changes`).
    -   **Триггер**: `trigger: include: artifact: ...` или `trigger: include: local: ...`.
2.  **Dynamic Pipeline Generation**: Программная генерация YAML-конфигурации "на лету" (обычно через Python или Bash).
    -   **Сценарий**: Когда пайплайн зависит от внешних данных или контекста, который невозможно описать статически (например, деплой на 20+ динамических окружений).

### Отладка и мониторинг

-   **`CI_DEBUG_TRACE: "true"`**: Переменная, включающая максимально подробный вывод всех команд и переменных окружения. Крайне полезна при поиске скрытых ошибок в сложных скриптах.
-   **Логирование**: Рекомендуется выводить подробные трейсы и использовать атомарные задачи для упрощения локализации ошибок.

## Практические сценарии

### Сценарий 1: Динамическое управление (rules)

Использование `workflow:rules` для предотвращения дублирования пайплайнов в Merge Request. Подробнее — в **[Правилах запуска задач](./workflow_rules/job_rules.md)**.

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
    - when: never # Исключает дубли при пуше в ветку с открытым MR
```

### Сценарий 2: Аутентификация в HashiCorp Vault через OIDC

Использование `id_tokens` для получения секретов из Vault без статических токенов.

```yaml
get_secrets:
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.example.com
  variables:
    VAULT_ADDR: "https://vault.example.com"
    VAULT_AUTH_PATH: "jwt/gitlab"
    VAULT_AUTH_ROLE: "my-app-role"
  script:
    - export VAULT_TOKEN=$(vault write -field=token auth/${VAULT_AUTH_PATH}/login role=${VAULT_AUTH_ROLE} jwt=${VAULT_ID_TOKEN})
    - vault kv get -field=password secret/data/db
```

### Сценарий 3: Динамическая генерация пайплайна

Генерация конфигурации на основе измененных файлов (полезно для монорепозиториев с сотнями модулей).

```yaml
generate-pipeline:
  stage: .pre
  script:
    - python3 generate_ci.py > generated-config.yml
  artifacts:
    paths: [generated-config.yml]

trigger-child:
  stage: build
  trigger:
    include:
      - artifact: generated-config.yml
        job: generate-pipeline
    strategy: mirror
```

### Сценарий 4: Матричное тестирование и ресурсы

Тестирование на разных версиях с сериализацией деплоя через `resource_group`.

```yaml
deploy_prod:
  stage: deploy
  resource_group: production_deploy
  parallel:
    matrix:
      - REGION: [us-east-1, eu-central-1]
  script:
    - deploy_to $REGION
```

## Дополнительная информация

### Сравнение областей действия

| Директива | Уровень | Основная задача | Особенности |
| :--- | :--- | :--- | :--- |
| **`workflow:rules`** | Глобальный | Фильтрация событий | Определяет, будет ли создан пайплайн вообще. |
| **`job:rules`** | Задача | Логика внутри пайплайна | Позволяет пропускать задачи или менять их атрибуты. |
| **`needs`** | Задача | Порядок выполнения (DAG) | Обход стадий, `needs:optional` для динамики. |
| **`resource_group`** | Задача | Сериализация (мьютекс) | Режимы `oldest_first`, `newest_first`, `unordered`. |

### Ограничения и лимиты

- **Лимиты задач**: В GitLab SaaS и Self-managed существуют лимиты на количество задач в одном пайплайне (обычно 10 000) и глубину вложенности `include`.
- **Версионность**: При использовании **CI/CD Catalog** всегда фиксируйте версию компонента (`@1.2.3`), а не `main`, для стабильности пайплайнов.
