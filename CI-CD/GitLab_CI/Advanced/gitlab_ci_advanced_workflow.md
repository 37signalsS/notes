# Продвинутые рабочие процессы GitLab CI/CD

## Определения

**Продвинутые рабочие процессы (Advanced Workflows)** — это совокупность методов и директив для построения сложных, масштабируемых и отказоустойчивых пайплайнов. Они позволяют реализовать динамическое управление задачами, оптимизировать потребление ресурсов и обеспечить соответствие корпоративным стандартам безопасности.

**Ключевые инструменты и директивы:**

- **`rules` и `workflow:rules`**: Условное управление запуском задач и всего пайплайна на основе контекста (ветки, переменные, изменения файлов).
- **`needs` (DAG)**: Создание направленных ациклических графов для запуска задач сразу по готовности зависимостей.
- **`parallel:matrix`**: Параллелизация однотипных задач с разными параметрами.
- **`resource_group`**: Сериализация задач для предотвращения гонок состояний (например, при деплое).
- **Pipeline Components & Inputs**: Современный стандарт (GitLab 17+) для создания типизированных и версионируемых модулей.
- **OIDC (ID tokens)**: Безопасная аутентификация во внешних системах (AWS, GCP, Vault) без долгоживущих секретов.

## Основные концепции

### Оптимизация и производительность

Современные пайплайны должны быть быстрыми и экономичными. Для этого используются:

1. **Ациклические графы (DAG)**: Директива `needs` позволяет задачам игнорировать границы стадий. Это сокращает время выполнения, так как тесты могут начаться сразу после сборки своего компонента, не дожидаясь окончания сборки других.
2. **Матричные сборки**: Позволяют одной конфигурацией запустить десятки задач (например, тестирование на разных версиях Node.js и БД).
3. **Автоматическая отмена (`workflow:auto_cancel`)**: Экономит ресурсы, отменяя старые пайплайны при появлении нового коммита в ту же ветку или при провале критичной задачи (fail-fast).
   - **`on_new_commit`**: `conservative` (не отменять критичные), `interruptible` (только прерываемые), `none`.
   - **`on_job_failure`**: `all` (немедленная отмена всех задач при провале любой).
4. **Прерывание задач (`interruptible`)**: Позволяет системе безопасно отменять задачи, если они больше не актуальны.

### Модульность и DRY

С версии **17.0** GitLab фокусируется на **CI/CD Components** вместо сырых `include`:

- **Components**: Хранятся в CI/CD Catalog, поддерживают версионирование (семантическое) и инкапсуляцию.
- **Inputs**: Директива `spec:inputs` обеспечивает строгую типизацию параметров, передаваемых в компоненты или шаблоны, что предотвращает ошибки конфигурации.

### Безопасность и соответствие (Compliance)

Для enterprise-интеграций используются:

- **ID tokens**: Заменяют устаревший `CI_JOB_JWT_TOKEN`. Позволяют генерировать OIDC-совместимые токены с настраиваемой аудиторией (`aud`) для безопасного взаимодействия с облаками.
- **Pipeline Execution Policies**: Позволяют администраторам принудительно запускать проверки безопасности (SAST, DAST) во всех проектах группы, гарантируя соблюдение стандартов без возможности их обхода разработчиками.
- **Deployment Approvals**: Защита окружений через обязательное подтверждение деплоя ответственными лицами.

## Практические сценарии

### Сценарий 1: Динамическое управление (rules)

Использование `workflow:rules` для предотвращения дублирования пайплайнов в Merge Request. Подробнее — в **[Правилах запуска задач](./workflow_rules/job_rules.md)**.

```yaml
workflow:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
    - when: never # Исключает дубли при пуше в ветку с открытым MR
```

### Сценарий 2: Использование ID tokens (OIDC)

Современный способ аутентификации в AWS без хранения `AWS_ACCESS_KEY_ID` в переменных.

```yaml
deploy:
  id_tokens:
    AWS_ID_TOKEN:
      aud: https://aws.amazon.com
  script:
    - # Использование токена для получения временных credentials через AWS STS
```

### Сценарий 3: Матричные сборки и ресурсы

Тестирование на разных версиях с ограничением параллелизма для деплоя. Подробнее — в **[Матричных сборках и сериализации](./workflow_rules/matrix_builds_and_serialization.md)**.

```yaml
test:
  parallel:
    matrix:
      - DB_VERSION: ["15", "16", "17"]
        NODE_VERSION: ["20", "22"]
  script:
    - run_tests.sh $DB_VERSION $NODE_VERSION
```

## Дополнительная информация

### Сравнение областей действия

| Директива | Уровень | Основная задача |
| :--- | :--- | :--- |
| `workflow:rules` | Глобальный | Фильтрация событий (push, MR, schedule) |
| `job:rules` | Задача | Логика внутри пайплайна |
| `needs` | Задача | Порядок выполнения (DAG) |
| `resource_group` | Задача | Сериализация (мьютекс) |

### Ограничения

- **Лимиты пайплайнов**: Максимальное количество задач в пайплайне и глубина вложенности `include` настраиваются на уровне инстанса.
- **Версионность**: Компоненты рекомендуется подключать с указанием конкретной версии (`@v1.2.3`), а не `main`, для стабильности пайплайнов.
