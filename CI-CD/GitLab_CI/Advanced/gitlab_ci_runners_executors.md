# Обзор GitLab Runner и Executor

## Определения

**[GitLab Runner](https://docs.gitlab.com/runner/)** — это агент (приложение на языке Go), который опрашивает сервер GitLab на наличие заданий (jobs), выполняет их и возвращает результат (логи, артефакты) обратно. Runner работает по принципу исходящих соединений (Pull-модель) — ему не нужен входящий доступ из интернета.

**[Executor](https://docs.gitlab.com/runner/executors/)** — модуль внутри Runner, определяющий среду выполнения скриптов (контейнер Docker, под Kubernetes, shell-сессия на хосте и др.).

**Токен аутентификации (Authentication Token)** — современный способ (с GitLab 16.0+) связи Runner'а с инстансом. В отличие от старых регистрационных токенов, аутентификационный токен (начинается с `glrt-`) создается в интерфейсе GitLab и сразу определяет область видимости, теги и конфигурацию Runner'а. Префикс может варьироваться (например, `glrt-t1_` для некоторых типов), что позволяет системе типизировать токены на уровне БД.

**Fleeting & Taskscaler** — новая архитектура автоскейлинга (GitLab 17.0+), заменяющая `docker+machine`.
- **Fleeting**: Библиотека и система плагинов (AWS, GCP, Azure), которая абстрагирует управление виртуальными машинами (инстансами). Она отвечает за создание, удаление и проверку состояния узлов.
- **Taskscaler**: Модуль планирования, который управляет жизненным циклом задач на инстансах, предоставляемых Fleeting.
- **Преимущество**: Высокая производительность, поддержка эфемерных ВМ без оверхеда `docker-machine` и прямая интеграция с облачными группами автоскейлинга (ASG/MIG).

## Основные концепции

### Типы Runner по области видимости

| Тип | Где настраивается | Кто может использовать | Основное применение |
| :--- | :--- | :--- | :--- |
| **Shared** | Admin Area | Все проекты инстанса | Общие задачи сборки, небольшие проекты |
| **Group** | Group Settings | Все проекты и подгруппы в группе | Командные ресурсы, специфические зависимости |
| **Project** | Project Settings | Только данный проект | Критичные задачи, доступ к закрытой инфраструктуре |

### Сравнение Executor'ов

| Executor | Изоляция | Сложность | Масштабирование | Рекомендуемое применение |
| :--- | :--- | :--- | :--- | :--- |
| **`shell`** | Отсутствует | Очень низкая | Нет | Локальные задачи, быстрые скрипты на хосте |
| **`docker`** | Высокая | Низкая | Ограничено хостом | Стандарт для большинства CI задач |
| **`kubernetes`** | Высокая | Высокая | Динамическое | Высокая нагрузка, K8s-инфраструктура |
| **`virtualbox`** | Полная (VM) | Высокая | Нет | Тестирование в специфических ОС |
| **`docker-autoscaler`** | Высокая | Средняя | Динамическое (Cloud) | Современная замена `docker+machine` через Fleeting |
| **`instance`** | Полная (VM) | Средняя | Динамическое | Максимальная изоляция (EC2/GCP) через Fleeting |

#### Shell Executor
Задания выполняются от имени пользователя `gitlab-runner`. 
- **Риски:** Задачи имеют доступ к файловой системе хоста и могут влиять на другие задания. 
- **Преимущества:** Прямой доступ к аппаратному обеспечению (GPU без Docker-поддержки) и **максимальная производительность** за счет отсутствия слоев виртуализации/контейнеризации.

#### Docker Executor
Самый популярный тип. Каждое задание запускается в новом контейнере. 
- **Конфигурация:** Образ указывается в `.gitlab-ci.yml` (`image: name`). 
- **Docker-in-Docker (DinD):** Используется для сборки образов и работы с `testcontainers`. Требует `privileged = true` в `config.toml`. Подробный разбор архитектуры и безопасности см. в SSoT-файле: **[Docker-in-Docker](../../../Docker/docker-in-docker.md)**.


#### VirtualBox / Parallels Executor
Используется в специфических случаях, когда требуется запуск полноценной виртуальной машины.
- **Применение:** Desktop-тестирование, сборка под Windows/macOS (если нет нативных раннеров). Обеспечивает полную изоляцию на уровне гипервизора.

## Управление нагрузкой и конфигурация

### Особенности работы и безопасности

1. **Коммуникация:** Runner опрашивает GitLab через HTTPS. В современных версиях для стриминга логов и интерактивных терминалов используется GRPC. Достаточно разрешить исходящий трафик на порт 443 к GitLab.
2. **Защищенные Runner'ы (Protected):** Могут выполнять задания только из защищенных веток и тегов. Предотвращают кражу секретов продуктивных сред через сторонние MR.
3. **Изоляция:** Для высокой безопасности рекомендуется использовать `docker` или `instance` executors. `shell` executor считается небезопасным для публичных проектов.
4. **Конкурентность (`concurrent`):** Общий лимит задач на весь агент, задаваемый в корне `config.toml`.

### Файл конфигурации `config.toml`

Обычно находится в `/etc/gitlab-runner/config.toml`.

```toml
concurrent = 10              # Общий лимит задач для всех Runner'ов на хосте
check_interval = 0           # Частота опроса GitLab (0 = по умолчанию 3 сек)
log_level = "info"

[session_server]             # Интерактивный терминал в UI GitLab
  session_timeout = 1800
  listen_address = "[::]:8093"

[[runners]]
  name = "docker-fleeting-aws"
  url = "https://gitlab.example.com/"
  token = "glrt-t1_XXXXXXXX"  # Authentication Token (с префиксом типа)
  executor = "docker-autoscaler"
  
  [runners.autoscaler]
    plugin = "aws"           # Fleeting плагин для AWS
    capacity_per_instance = 1
    max_instances = 20
    
    [runners.autoscaler.plugin_config]
      name = "ci-runners-asg"
      region = "us-east-1"

  [runners.docker]
    image = "alpine:latest"
    privileged = false        # Рекомендуется false (безопасность)
    volumes = ["/cache", "/var/run/docker.sock:/var/run/docker.sock"]
    pull_policy = ["always", "if-not-present"]
  
  [runners.cache]
    Type = "s3"              # Распределенный кэш для автомасштабируемых раннеров
    Shared = true
    [runners.cache.s3]
      ServerAddress = "s3.amazonaws.com"
      BucketName = "gitlab-cache"
      BucketLocation = "us-east-1"
```

## Практические сценарии

### Сценарий 1: Ускорение сборки через теги (Tags)

Назначение задачи на Runner с мощным CPU или GPU.

```yaml
build:gpu_optimized:
  stage: build
  tags:
    - gpu
    - cuda-12
  script:
    - nvcc --version
```

### Сценарий 2: Использование переменных для выбора Executor/Образа

Хотя Executor жестко задан в `config.toml`, вы можете динамически управлять средой через образы или выбирать нужный пул раннеров через переменные и теги.

```yaml
test:multi_version:
  stage: test
  image: $TEST_IMAGE
  parallel:
    matrix:
      - TEST_IMAGE: ["python:3.10", "python:3.11", "python:3.12"]
  script:
    - python --version
```

## Дополнительная информация

### Новая модель регистрации (GitLab 16.0+)
Старая модель с регистрационными токенами считается устаревшей. Теперь процесс выглядит так:
1. Создание записи Runner в интерфейсе GitLab (Admin -> Runners или Project -> CI/CD -> Runners).
2. Получение `glrt-` токена.
3. Запуск команды `gitlab-runner register --token glrt-...` (конфигурация подтягивается с сервера или задается локально).
