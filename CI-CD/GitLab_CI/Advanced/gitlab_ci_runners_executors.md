### Определения

**[GitLab Runner](https://docs.gitlab.com/runner/)** — это отдельное приложение (статический бинарный файл на Go), которое выполняет задания (jobs) из пайплайнов GitLab CI/CD. Runner является клиентом, который с заданным интервалом опрашивает сервер GitLab на предмет наличия новых задач и выполняет их в указанной среде.

**[Executor](https://docs.gitlab.com/runner/executors/)** — это модуль внутри GitLab Runner, который непосредственно взаимодействует со средой выполнения и определяет, *как* и *где* будут выполняться скрипты (например, в Docker-контейнере, на хост-машине через shell или в Kubernetes Pod).

**Типы Runner'ов:**

* **Shared** (общие): Доступны для всех проектов на экземпляре GitLab. Управляются администратором GitLab.
* **Group** (групповые): Доступны для всех проектов и подгрупп в определенной группе.
* **Specific** (проектные): Привязаны к конкретному проекту. Наиболее безопасный и контролируемый вариант.

**Теги (`tags`)**: Метки, которые присваиваются Runner'ам при регистрации (например, `docker`, `linux`, `gpu`) и используются в `.gitlab-ci.yml` для точного выбора исполнителя для конкретной задачи.

### Основные концепции

#### Механизм регистрации и безопасность

1. **Регистрационный токен:** Это **одноразовый** токен, используемый только для первоначальной регистрации Runner'а. **Никогда не раскрывайте его и не "хардкодьте" в скриптах.**
2. **Аутентификационный токен:** После успешной регистрации GitLab выдает Runner'у постоянный аутентификационный токен, который хранится в файле `config.toml`. Именно этот токен используется для всех последующих коммуникаций.
3. **Защищенные Runner'ы (`protected`):** Опция, которая разрешает Runner'у выполнять задачи только из защищенных веток (protected branches) или защищенных тегов (protected tags). Это критически важно для безопасности production-развертываний.

#### Сравнение ключевых Executor'ов

| Executor | Изоляция | Скорость | Управление зависимостями | Сценарии использования |
| :--- | :--- | :--- | :--- | :--- |
| **`shell`** | Низкая (выполняется на хосте) | Очень высокая | Ручная установка на хост | Простые задачи, доверенная среда, доступ к аппаратным ресурсам. |
| **`docker`** | Высокая (контейнер на задачу) | Высокая | Автоматическая (через `image:`) | **Самый популярный.** Чистая среда для каждой задачи, версионирование зависимостей. |
| **`kubernetes`** | Высокая (Pod на задачу) | Высокая | Автоматическая (через `image:`) | Оркестрация в Kubernetes, автомасштабирование, динамическое выделение ресурсов. |

* **Docker-in-Docker:** Когда сам Runner запущен в Docker, для сборки образов внутри CI-задачи используется трюк с монтированием сокета: `-v /var/run/docker.sock:/var/run/docker.sock`. Это эффективно, но **предоставляет контейнеру с Runner'ом root-доступ к хостовой системе.** Более безопасной альтернативой является использование **[Kaniko](../Dockerfile/dockerfile_kaniko.md)**.

### Практические сценарии

В этом разделе показано, как **использовать** уже зарегистрированные Runner'ы. Подробные инструкции по установке и регистрации см. в руководстве **[Регистрация GitLab Runner](../Tutorials/runner_registration.md)**.

#### Сценарий 1: Выбор Runner'а по тегам

Задача будет выполнена только на том Runner'е, у которого есть тег `docker` и `postgres`.

```yaml
test-db:
  stage: test
  tags:
    - docker
    - postgres
  script:
    - echo "Эта задача требует Runner с Docker и доступом к Postgres."
    - psql -h postgres -U user -d db -c "SELECT 1;"
```

#### Сценарий 2: Использование Docker Executor с сервисами

Эта задача запускается в контейнере `python:3.9`, а также рядом с ним поднимается сервисный контейнер `postgres:13.1`. Они находятся в одной Docker-сети и видят друг друга по имени (`postgres`).

```yaml
python-tests:
  stage: test
  image: python:3.9
  tags:
    - docker # Указываем, что нам нужен Runner с Docker Executor
  services:
    - name: postgres:13.1
      alias: postgres
  variables:
    POSTGRES_DB: testdb
    POSTGRES_USER: runner
    POSTGRES_PASSWORD: ""
    POSTGRES_HOST_AUTH_METHOD: trust # Для тестов
  script:
    - pip install psycopg2-binary
    - python tests/test_db_connection.py # Скрипт, который подключается к postgres
```

### Дополнительная информация

#### Рекомендации и лучшие практики

* **Изолируйте рабочие нагрузки:** Используйте `tags` для разделения Runner'ов для разных сред (например, `dev`, `prod`) и разных задач (`build`, `deploy`).
* **Предпочитайте Specific Runner'ы:** Для production-задач всегда используйте `Specific Runner`'ы, привязанные к конкретному проекту, и отключайте `Shared Runner`'ы в настройках проекта.
* **Используйте `protected` флаг:** Защищайте Runner'ы, ответственные за деплой, чтобы они работали только с защищенными ветками.
* **Мониторинг:** Следите за состоянием и загрузкой вашего парка Runner'ов. GitLab предоставляет базовые метрики, но для серьезного мониторинга можно использовать Prometheus.
* **Безопасность Docker Executor:** Помните о рисках, связанных с монтированием Docker-сокета. Рассмотрите `Kaniko` или другие альтернативы для сборки образов в CI.
