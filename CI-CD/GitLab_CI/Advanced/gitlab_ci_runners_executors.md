### Определения

**GitLab Runner** — это отдельное приложение (статический бинарный файл на Go), которое выполняет задания (jobs) из пайплайнов GitLab CI/CD. Runner является клиентом, который с заданным интервалом опрашивает сервер GitLab на предмет наличия новых задач и выполняет их в указанной среде.

**Executor** — это модуль внутри GitLab Runner, который непосредственно взаимодействует со средой выполнения и определяет, *как* и *где* будут выполняться скрипты (например, в Docker-контейнере, на хост-машине через shell или в Kubernetes Pod). Сам Runner является лишь управляющим компонентом.

**Типы Runner'ов:**
*   **Shared** (общие): Доступны для всех проектов на экземпляре GitLab.
*   **Group** (групповые): Доступны для всех проектов в определенной группе.
*   **Specific** (проектные): Привязаны к конкретному проекту.

### Основные концепции

#### Механизм регистрации и безопасность

Процесс подключения Runner'а к GitLab и его безопасность строятся на следующих элементах:

1.  **Регистрационные токены:** Это **одноразовые** токены, используемые только для первоначальной регистрации Runner'а. Они бывают трех уровней: для всего экземпляра (shared), для группы или для конкретного проекта. **Никогда не раскрывайте эти токены.**

2.  **Аутентификационный токен:** После успешной регистрации GitLab выдает Runner'у постоянный аутентификационный токен, который хранится в `config.toml`. Именно этот токен используется для всех последующих коммуникаций и однозначно идентифицирует Runner.

3.  **Теги (`tags`):** Каждому Runner'у можно присвоить теги (например, `docker`, `linux`, `gpu`). Задачи в `.gitlab-ci.yml` могут быть нацелены на Runner'ы с определенными тегами.
    *   **Риск:** Если у злоумышленника есть контроль над Runner'ом с такими же тегами, как у вас, он может перехватить выполнение вашего пайплайна, получив доступ к секретам и исходному коду.

#### Меры защиты
*   **Используйте "защищенные" Runner'ы (`protected`):** Включает Runner только для защищенных веток или тегов, предотвращая его использование в feature-ветках.
*   **Используйте `specific` Runner'ы:** Привязка Runner'а к конкретному проекту является наиболее безопасным вариантом.
*   **Отключайте общие Runner'ы:** В настройках проекта можно запретить использование shared runner'ов, чтобы гарантировать, что пайплайны выполняются только на ваших контролируемых Runner'ах.

### Типы Executor'ов: Сравнение

| Executor | Изоляция | Скорость | Управление зависимостями | Сценарии использования |
| :--- | :--- | :--- | :--- | :--- |
| **`shell`** | Низкая (выполняется на хосте) | Очень высокая | Ручная установка на хост | Простые задачи, доверенная среда, доступ к аппаратным ресурсам. |
| **`ssh`** | Низкая (выполняется на удаленном хосте) | Высокая | Ручная установка на удаленный хост | Управление удаленными серверами, развертывание. |
| **`virtualbox` / `parallels`** | Очень высокая (новая ВМ на каждую задачу) | Очень низкая | Управление образами ВМ | Задачи, требующие полной изоляции или специфичной ОС. |
| **`docker`** | Высокая (контейнер на задачу) | Высокая | Автоматическая (через `image:`) | **Самый популярный.** Чистая среда для каждой задачи, версионирование зависимостей. |
| **`kubernetes`** | Высокая (Pod на задачу) | Высокая | Автоматическая (через `image:`) | Оркестрация в Kubernetes, автомасштабирование, динамическое выделение ресурсов. |

#### `docker` Executor
Для каждой задачи создается чистый Docker-контейнер из образа, указанного в `image`. Runner взаимодействует с Docker-демоном через сокет (по умолчанию `/var/run/docker.sock`).

*   **"Docker-in-Docker":** Когда сам Runner запущен в Docker-контейнере, для управления Docker-демоном хоста используется трюк с монтированием сокета: `-v /var/run/docker.sock:/var/run/docker.sock`. Runner, обращаясь к сокету внутри своего контейнера, на самом деле отправляет команды Docker-демону хост-машины. **Это предоставляет значительные привилегии контейнеру с Runner'ом.**

#### `kubernetes` Executor
Для каждой задачи создается новый Pod в кластере Kubernetes.

*   **Рекомендуемый подход:** Запускать сам GitLab Runner как Pod внутри кластера. В этом случае ему можно выдать `ServiceAccount` с необходимыми правами, и он автоматически обнаружит API-сервер и аутентифицируется для создания Pod'ов с задачами.
