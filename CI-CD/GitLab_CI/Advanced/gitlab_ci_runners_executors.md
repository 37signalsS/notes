### Определения

**[GitLab Runner](https://docs.gitlab.com/runner/)** — это отдельное приложение (статический бинарный файл на Go), которое выполняет задания (jobs) из пайплайнов GitLab CI/CD. Runner является клиентом, который с заданным интервалом опрашивает сервер GitLab на предмет наличия новых задач и выполняет их в указанной среде.

**[Executor](https://docs.gitlab.com/runner/executors/)** — это модуль внутри GitLab Runner, который непосредственно взаимодействует со средой выполнения и определяет, *как* и *где* будут выполняться скрипты (например, в Docker-контейнере, на хост-машине через shell или в Kubernetes Pod).

**Теги (`tags`)**: Метки, которые присваиваются Runner'ам при регистрации (например, `docker`, `linux`, `gpu`) и используются в `.gitlab-ci.yml` для точного выбора исполнителя для конкретной задачи.

### Основные концепции

#### Типы Runner'ов и область видимости

| Тип | Область видимости | Контроль окружения | Безопасность секретов | Очередь | Стоимость |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Shared** (общий) | Вся инстанция/группа | Ограниченный | Ниже | Общая | Эффективное использование |
| **Specific** (проектный) | Конкретный проект/группа | Полный | Выше | Локальная | Выделенные ресурсы |

- **Shared Runner**: Общий для всей инстанции GitLab. Подходит для типовых задач и распределения нагрузки.
- **Group Runner**: Доступен для всех проектов и подгрупп в определенной группе.
- **Specific Runner**: Закреплен за конкретным проектом. Используется для задач с особыми требованиями: кастомные зависимости, повышенные права или доступ в приватную сеть.
- **Protected Runner**: Выполняет задания только из защищенных веток или тегов. Критически важен для задач развертывания.
- **Locked Runner**: Привязан к проекту и не может быть назначен другим проектам.

#### Сравнение ключевых Executor'ов

| Executor | Изоляция | Скорость | Управление зависимостями | Сценарии использования |
| :--- | :--- | :--- | :--- | :--- |
| **`shell`** | Низкая (выполняется на хосте) | Очень высокая | Ручная установка на хост | Простые задачи, доверенная среда, доступ к аппаратным ресурсам. |
| **`docker`** | Высокая (контейнер на задачу) | Высокая | Автоматическая (через `image:`) | **Самый популярный.** Чистая среда для каждой задачи. |
| **`docker-in-docker`** | Высокая (но с риском) | Средняя | Автоматическая (через `image:`) | Сборка Docker-образов внутри CI. Требует `privileged` режима. |
| **`kubernetes`** | Очень высокая (Pod на задачу) | Высокая | Автоматическая (через `image:`) | Оркестрация в Kubernetes, автомасштабирование, динамическое выделение ресурсов. |

- **Безопасность `docker-in-docker`**: Использование Docker-in-Docker (dind) через монтирование сокета (`-v /var/run/docker.sock:/var/run/docker.sock`) эффективно, но **предоставляет контейнеру с Runner'ом root-доступ к хостовой системе.** Более безопасной альтернативой является использование **[Kaniko](../Dockerfile/dockerfile_kaniko.md)**.

#### Файл конфигурации `config.toml`

Это основной файл конфигурации GitLab Runner, где определяются глобальные параметры и настройки для каждого зарегистрированного runner.

**Пример `config.toml` с Docker Executor и S3-кэшем:**
```ini
# Глобальный лимит на количество одновременно выполняемых задач
concurrent = 4

# Секция для конкретного runner
[[runners]]
  name = "project-docker-runner"
  url = "https://gitlab.example.com"
  token = "REDACTED"
  executor = "docker"
  # Настройки для Docker executor
  [runners.docker]
    image = "alpine:3.20" # Образ по умолчанию
    privileged = false
    disable_entrypoint_overwrite = true
    volumes = ["/cache"]
    shm_size = 0
  # Настройки кэширования
  [runners.cache]
    Type = "s3"
    Shared = true
    [runners.cache.s3]
      ServerAddress = "s3.example.com"
      BucketName = "gitlab-cache"
      Insecure = false
```

### Практические сценарии

Подробные инструкции по установке и регистрации см. в руководстве **[Регистрация GitLab Runner](../Tutorials/runner_registration.md)**.

#### Сценарий 1: Выбор Runner'а по тегам

Задача `test:db` будет выполнена только на Runner'е с тегами `docker` и `postgres`, а задача `test:app` — на Runner'е с тегом `k8s`.

```yaml
stages:
  - test

test:db:
  stage: test
  tags:
    - docker
    - postgres
  script:
    - echo "Эта задача требует Runner с Docker и доступом к Postgres."
    - psql -h postgres -U user -d db -c "SELECT 1;"

test:app:
  stage: test
  tags:
    - k8s
  script:
    - pytest -q
```

#### Сценарий 2: Использование Kubernetes Runner

Для динамического масштабирования и изоляции используется Kubernetes Executor, который создает отдельный Pod для каждой задачи.

**Пример `values.yaml` для Helm-чарта GitLab Runner:**
```yaml
gitlabUrl: https://gitlab.example.com
runnerRegistrationToken: "REDACTED"
runners:
  tags: "k8s,linux"
  privileged: false
  pollTimeout: 180
  helpers:
    # Вспомогательный образ для работы с кэшем и артефактами
    image: registry.gitlab.com/gitlab-org/gitlab-runner/gitlab-runner-helper:x86_64-latest
  cache:
    cacheType: s3
    s3ServerAddress: s3.example.com
    s3BucketName: gitlab-cache
metrics:
  enabled: true
rbac:
  create: true
```
Автомасштабирование обеспечивается самим Kubernetes.

### Дополнительная информация

#### Рекомендации и лучшие практики

- **Изолируйте рабочие нагрузки:** Используйте `tags` для разделения Runner'ов для разных сред (`dev`, `prod`) и разных задач (`build`, `deploy`, `test`).
- **Предпочитайте Specific Runner'ы:** Для production-задач всегда используйте `Specific Runner`'ы, привязанные к конкретному проекту, и отключайте `Shared Runner`'ы в настройках проекта.
- **Используйте `protected` и `locked` флаги:** Защищайте Runner'ы, ответственные за деплой, чтобы они работали только с защищенными ветками и были привязаны к конкретным проектам.
- **Политика для Shared Runner:**
    - Отключайте опцию `run_untagged_jobs` и всегда требуйте явного указания тегов.
    - Ограничивайте максимальное время выполнения задачи (`timeout` в `config.toml` или настройках проекта).
    - Разделяйте пулы Shared Runner'ов по классам задач (например, легкие линтеры и тяжелые сборки).
- **Наблюдаемость и обслуживание:**
    - Включите `metrics_server` в конфигурации Runner'а для сбора метрик в формате Prometheus. Это позволит отслеживать загрузку, длину очереди и длительность выполнения задач.
    - Используйте `session_server` для возможности подключения к интерактивным терминалам в CI/CD.
    - Регулярно обновляйте версию Runner'а для получения новых функций и исправлений безопасности.
- **Безопасность Docker Executor:** Помните о рисках, связанных с `privileged` режимом и монтированием Docker-сокета. Рассмотрите **[Kaniko](../Dockerfile/dockerfile_kaniko.md)** или другие альтернативы для сборки образов в CI.
