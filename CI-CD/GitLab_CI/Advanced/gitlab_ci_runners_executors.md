# GitLab CI: Исполнители (Runners) и их типы (Executors)

## Определения

- **[GitLab Runner](https://docs.gitlab.com/runner/)**: Отдельное приложение, которое выполняет задания (jobs) из пайплайнов GitLab CI/CD. Runner опрашивает сервер GitLab, забирает задачи и выполняет их в указанной среде.
- **[Executor](https://docs.gitlab.com/runner/executors/)**: Модуль внутри Runner'а, который определяет, *как* и *где* будут выполняться скрипты (например, в Docker-контейнере, на хосте через shell или в Kubernetes Pod).
- **Теги (`tags`)**: Метки, которые присваиваются Runner'ам (`docker`, `linux`, `gpu`) и используются в `.gitlab-ci.yml` для выбора исполнителя для конкретной задачи.

## Основные концепции

#### 1. Типы Runner'ов (по области видимости)

| Тип | Область видимости | Контроль | Безопасность |
| :--- | :--- | :--- | :--- |
| **Shared** (общий) | Вся инстанция GitLab | Ограниченный | Ниже |
| **Group** (групповой) | Все проекты в группе | Частичный | Средняя |
| **Specific** (проектный) | Конкретный проект | Полный | Выше |

- **Specific Runner** является предпочтительным для задач с особыми требованиями (секреты, доступ в приватную сеть).
- **Protected Runner** выполняет задания только из защищенных веток, что критично для задач развертывания.

#### 2. Типы Executor'ов (по среде выполнения)

| Executor | Изоляция | Скорость | Управление зависимостями | Основной сценарий |
| :--- | :--- | :--- | :--- | :--- |
| **`shell`** | Низкая | Очень высокая | Ручная установка на хост | Простые задачи, доступ к железу. |
| **`docker`** | Высокая | Высокая | Автоматическая (`image:`) | **Самый популярный.** Чистая среда на каждую задачу. |
| **`kubernetes`**| Очень высокая| Высокая | Автоматическая (`image:`) | Оркестрация в Kubernetes, автомасштабирование. |

В рамках одного пайплайна часто комбинируют задачи, выполняемые на разных типах executor'ов. Например, этап сборки может использовать `docker` executor для создания чистого, изолированного окружения, в то время как этап развертывания будет использовать `shell` executor на целевой машине для прямого выполнения команд `docker-compose` или `systemctl`. Выбор executor'а для задачи осуществляется с помощью тегов.

#### 3. Файл конфигурации `config.toml`

Основной файл конфигурации GitLab Runner, где определяются глобальные параметры и настройки для каждого зарегистрированного runner.

```toml
# Глобальный лимит одновременно выполняемых задач
concurrent = 4

[[runners]]
  name = "project-docker-runner"
  url = "https://gitlab.example.com/"
  token = "REDACTED"
  executor = "docker"
  [runners.docker]
    image = "alpine:latest"
    privileged = false
  [runners.cache]
    Type = "s3"
    [runners.cache.s3]
      ServerAddress = "s3.example.com"
      BucketName = "gitlab-cache"
```

## Практические сценарии

#### Сценарий 1: Выбор Runner'а по тегам

Задача `test:db` будет выполнена только на Runner'е с тегами `docker` и `postgres`.

```yaml
test:db:
  stage: test
  tags:
    - docker
    - postgres
  script:
    - psql -h postgres -U user -d db -c "SELECT 1;"
```

> **Примечание**: Если ни один активный Runner не соответствует требуемому набору тегов, задача не упадет, а будет находиться в состоянии `pending` (ожидание) до тех пор, пока подходящий Runner не появится в сети.

#### Сценарий 2: Использование Kubernetes Executor

Для динамического масштабирования и изоляции используется Kubernetes Executor, который создает отдельный Pod для каждой задачи. Настраивается через Helm-чарт GitLab Runner.

```yaml
# values.yaml для Helm-чарта
gitlabUrl: https://gitlab.example.com
runnerRegistrationToken: "REDACTED"
runners:
  tags: "k8s,linux"
  # ... другие настройки
```

## Дополнительная информация

#### Рекомендации и лучшие практики

- **Изолируйте рабочие нагрузки:** Используйте `tags` для разделения Runner'ов для разных сред (`dev`, `prod`).
- **Сетевая изоляция:** Выделяйте CI/CD инфраструктуру в отдельные подсети без прямого доступа в интернет. Особое внимание уделите **Protected Runner'ам** (выполняющим задачи из защищенных веток и имеющим доступ к prod-секретам) — они должны находиться в строго изолированной подсети с жесткими правилами Firewall для предотвращения попыток проброса reverse shell или кражи токенов.
- **Предпочитайте Specific Runner'ы:** Для production-задач всегда используйте `Specific Runner`'ы и отключайте `Shared Runner`'ы.
- **Безопасность Docker: Сборка образов**: Для сборки Docker-образов внутри Docker-executor'а избегайте небезопасных подходов:
  - **`privileged = true`**: Предоставляет контейнеру полный доступ к хост-системе, что является серьезной угрозой безопасности.
  - **Docker-in-Docker (`dind`)**: Требует привилегированного режима для запуска Docker-демона внутри контейнера.
  - **Монтирование сокета Docker (`/var/run/docker.sock`)**: Позволяет контейнеру управлять Docker-демоном на хосте, что эквивалентно root-доступу.

  **Рекомендация**: Используйте **[Kaniko](../../../Docker/Dockerfile/dockerfile_kaniko.md)** — инструмент собирает образы в userspace без привилегированного доступа или Docker-демона.
  - Подробное сравнение подходов DinD, DooD и Kaniko: **[Docker-in-Docker: Запуск Docker внутри контейнера](../../../Docker/docker-in-docker.md)**.
- **Наблюдаемость:** Включите `metrics_server` в `config.toml` для сбора метрик в формате Prometheus.
- **Практическое применение:** Пошаговые инструкции по регистрации Runner'а см. в руководстве **[Регистрация GitLab Runner](../Tutorials/runner_registration.md)**.
- **Интеграция с Kubernetes:** Детальная настройка Kubernetes Executor описана в **[Интеграция GitLab CI с Kubernetes](./gitlab_kubernetes_integration_guide.md)**.
- **Базовые концепции:** Для понимания контекста CI/CD обратитесь к **[Основам GitLab CI/CD](../Concepts/gitlab_ci_basics.md)** и **[Глоссарию элементов CI/CD](../../Core_Concepts/pipeline_glossary.md)**.
