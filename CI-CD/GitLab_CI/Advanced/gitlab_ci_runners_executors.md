# Исполнители (Runners) и их типы (Executors) в GitLab CI

## Определения

- **[GitLab Runner](https://docs.gitlab.com/runner/)**: Отдельное приложение (агент), которое выполняет задания (jobs) из пайплайнов GitLab CI/CD. Runner опрашивает сервер GitLab, забирает задачи и выполняет их в изолированной или хостовой среде.
- **[Executor](https://docs.gitlab.com/runner/executors/)**: Модуль внутри Runner, определяющий среду выполнения скриптов (контейнер Docker, под Kubernetes, shell-сессия на хосте и др.).
- **Теги (`tags`)**: Метки, присваиваемые Runner (например, `docker`, `production`, `gpu`), которые используются в конфигурации `.gitlab-ci.yml` для назначения задачи конкретному исполнителю.

## Основные концепции

### Типы Runner по области видимости

| Тип | Область видимости | Управление | Применение |
| :--- | :--- | :--- | :--- |
| **Shared** (общие) | Вся инстанция GitLab | Администратор инстанции | Публичные проекты, общие задачи |
| **Group** (групповые) | Все проекты внутри группы | Владелец группы | Командные ресурсы, общие секреты группы |
| **Specific** (проектные) | Конкретный проект | Владелец проекта | Специфическое ПО, доступ к закрытой сети |

- **Protected Runner**: Выполняет задания только из защищенных веток или тегов. Критично для задач развертывания (Deploy) на продуктивные окружения.
- **Run untagged jobs**: Опция, позволяющая Runner брать задачи без указанных тегов.

### Типы Executor по среде выполнения

| Executor | Изоляция | Скорость | Управление зависимостями | Основной сценарий |
| :--- | :--- | :--- | :--- | :--- |
| **`shell`** | Низкая | Очень высокая | Ручная установка на хост | Прямой доступ к железу, простые скрипты |
| **`docker`** | Высокая | Высокая | Автоматическая (`image:`) | Изолированные сборки, чистая среда |
| **`kubernetes`** | Очень высокая | Высокая | Автоматическая (`image:`) | Динамическое масштабирование в кластере |

#### Shell Executor
Задания выполняются непосредственно в shell-сессии на хост-машине Runner.
- **Плюсы:** Минимальные накладные расходы, доступ ко всем ресурсам сервера.
- **Минусы:** Отсутствие изоляции (задачи могут влиять друг на друга), необходимость ручной подготовки окружения.

#### Docker Executor
Каждая задача запускается в новом контейнере на базе указанного образа.
- **Плюсы:** Полная изоляция, предсказуемость окружения, зависимости упакованы в образ.
- **Минусы:** Требуется Docker-демон на хосте, накладные расходы на запуск контейнера.

#### Kubernetes Executor
Runner создает отдельный Pod для каждой задачи в кластере Kubernetes.
- **Плюсы:** Автоматическое масштабирование, эффективное использование ресурсов кластера.
- **Минусы:** Сложность настройки, зависимость от доступности кластера.

### Конфигурационный файл `config.toml`

Все настройки зарегистрированных Runner хранятся в файле `config.toml`.

```toml
# Глобальный лимит одновременных задач
concurrent = 4

[[runners]]
  name = "docker-runner-01"
  url = "https://gitlab.example.com/"
  token = "TOKEN_VALUE"
  executor = "docker"
  [runners.docker]
    image = "alpine:latest"
    # privileged = true требуется только для DinD
    privileged = false
  [runners.cache]
    Type = "s3"
    [runners.cache.s3]
      ServerAddress = "s3.example.com"
      BucketName = "gitlab-cache"
```

## Практические сценарии

### Сценарий 1: Выбор Runner по тегам

Назначение задачи на специфический Runner (например, с установленной базой данных).

```yaml
test:database:
  stage: test
  tags:
    - docker
    - postgres-16
  script:
    - psql -h postgres -U user -d db -c "SELECT 1;"
```

### Сценарий 2: Использование Kubernetes Executor для масштабирования

Динамическое создание ресурсов под нагрузку. Настройка выполняется через Helm-чарт GitLab Runner.

```yaml
# Пример фрагмента .gitlab-ci.yml для K8s
k8s_job:
  stage: build
  tags:
    - kubernetes
  script:
    - echo "Running in a dynamic Kubernetes pod"
```

## Дополнительная информация

### Рекомендации по безопасности

- **Минимизация привилегий**: Избегайте использования `privileged = true` в Docker Executor. Для сборки образов используйте **[Kaniko](../../../Docker/Dockerfile/dockerfile_kaniko.md)**.
- **Изоляция секретов**: Отключайте Shared Runners для проектов с критическими данными, используйте Specific Runners.
- **Защита окружений**: Применяйте Protected Runners для деплоя на Production.
- **Методы сборки образов**: Подробное сравнение способов запуска Docker внутри CI приведено в статье **[Docker-in-Docker](../../../Docker/docker-in-docker.md)**.
