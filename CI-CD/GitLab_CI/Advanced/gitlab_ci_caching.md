### Определения

**Кэширование в GitLab CI** — это механизм, который позволяет сохранять файлы и директории между запусками задач (job) или пайплайнов. Его основная цель — ускорение выполнения сборки за счет повторного использования уже загруженных зависимостей (`node_modules`, `vendor/`, `.m2/`) или других промежуточных файлов.

**Кэш vs. Артефакты**

| Признак | Кэш (`cache`) | Артефакты (`artifacts`) |
| :--- | :--- | :--- |
| **Назначение** | Ускорение задач (например, зависимости) | Передача результатов работы между стадиями (бинарные файлы, отчеты) |
| **Гарантия** | **Не гарантируется.** Runner может удалить кэш в любой момент. | **Гарантируются.** Артефакты хранятся на сервере GitLab определенное время (`expire_in`). |
| **Область** | По умолчанию — для всего проекта. Можно настроить для задачи или ветки. | Только для конкретной задачи. Передаются в последующие стадии. |
| **Загрузка** | Загружается и извлекается в рабочей директории Runner'а. | Загружаются на сервер GitLab, а затем скачиваются другими задачами. |
| **Скорость** | Быстрее, так как хранятся локально на Runner'е. | Медленнее из-за загрузки/скачивания на/с сервера GitLab. |

Для критически важных файлов, которые должны быть гарантированно доступны в последующих задачах, используйте [артефакты](../Advanced/gitlab_ci_workflow_builder.md#artifacts-results-of-job-execution).

### Основные концепции

#### Ключ кэша (`cache:key`)

Ключ определяет уникальность кэша. Когда ключ изменяется, GitLab Runner создает новый кэш вместо использования старого. Это основной механизм контроля над тем, когда кэш должен быть перестроен.

* **Глобальный кэш:** Определяется на верхнем уровне и используется всеми задачами по умолчанию.
* **Локальный кэш:** Определяется внутри конкретной задачи и переопределяет глобальные настройки.

#### Политики кэширования (`cache:policy`)

Политика определяет, как задача взаимодействует с кэшем.

* `pull-push` (по умолчанию) — Загружает кэш перед выполнением задачи и сохраняет его после успешного завершения.
* `pull` — Только загружает кэш. Не сохраняет изменения после выполнения. Используется в задачах, которые только потребляют кэш (например, тесты).
* `push` — Только сохраняет кэш. Не загружает его в начале. Используется в задачах, которые только создают кэш.

### Практические сценарии

#### 1. Кэширование на основе содержимого файла зависимостей (рекомендуемый способ)

Это наиболее эффективная стратегия, так как кэш перестраивается только при изменении файла зависимостей.

```yaml
# Кэширование зависимостей Node.js
cache:
  key:
    files:
      - package-lock.json # Ключ кэша зависит от хэша этого файла
  paths:
    - node_modules/
  policy: pull # В последующих задачах только загружаем

install_dependencies:
  stage: build
  script:
    - npm ci
  cache:
    key:
      files:
        - package-lock.json
    paths:
      - node_modules/
    policy: pull-push # Эта задача обновляет кэш
```

#### 2. Кэширование на основе ветки

Создает отдельный кэш для каждой ветки. Полезно, когда зависимости могут различаться между feature-ветками.

```yaml
# Разные кэши для разных веток
cache:
  key: "$CI_COMMIT_REF_SLUG" # Используется имя ветки или тега
  paths:
    - vendor/
```

#### 3. Общий (глобальный) кэш

Один и тот же кэш используется для всех пайплайнов и веток. Подходит для зависимостей, которые редко меняются.

```yaml
# Глобальный кэш для Maven-зависимостей
cache:
  key: "global-maven-cache"
  paths:
    - .m2/repository/
```

#### 4. Полный пример для NPM-проекта

```yaml
variables:
  npm_config_cache: "$CI_PROJECT_DIR/.npm"

# Глобально определяем, что нужно кэшировать
cache:
  key:
    files:
      - package-lock.json
  paths:
    - node_modules/
    - .npm/
  policy: pull # По умолчанию задачи только загружают кэш

install_dependencies:
  stage: build
  script:
    - npm ci --cache .npm --prefer-offline
  cache:
    # Переопределяем политику для этой задачи
    policy: pull-push # Эта задача загружает и обновляет кэш

test_job:
  stage: test
  script:
    - npm run test
  # Эта задача использует глобальные настройки `cache` (политика `pull`)
```

### Дополнительная информация

* **Кэш не гарантирован:** GitLab Runner может очистить кэш в любой момент, например, при нехватке дискового пространства. Не используйте кэш для хранения артефактов сборки или критически важных данных.
* **Скорость:** Кэш работает значительно быстрее артефактов, так как он обычно хранится на том же хосте, где работает Runner, что исключает затраты на сетевую передачу.
