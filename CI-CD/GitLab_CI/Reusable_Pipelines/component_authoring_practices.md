# Практики создания GitLab CI/CD Components: как не докатиться до монолитных шаблонов

**Актуально для:** GitLab 19.x (компоненты и CI/CD Catalog GA с 17.0; текущая линейка — 19.4.x)

> Практики из доклада Александра Кувыкина (DevOps-инженер) о культуре написания CI/CD в крупной компании. Механика компонентов, `spec:inputs` и каталога описана в [Каталоге компонентов](./ci_cd_catalog_components.md); здесь — анатомия компонента, изоляция, версионирование, тестирование и документирование на практике.

## Определения

**Монолитный шаблон CI/CD** — общий шаблон конвейера, который нельзя универсально использовать в разных сценариях: большой файл (тысячи строк), много зависимостей (между джобами и на внешние сервисы), смесь скрытых и публичных джобов.

**Инкапсуляция** — сокрытие внутренностей шаблона за локальным интерфейсом `inputs`: переменные, джобы и секреты компонента не просачиваются в глобальную область конвейера.

**Обвязка (wrapper)** — файл `template.yaml` компонента: entry point рендеринга, который подключает файл логики, пробрасывает `inputs` и описывает взаимодействие джобов (`image`, `rules`, `needs`, `stage`, `tags`).

**Логика (jobs)** — файл `jobs.yaml` компонента: только скрытые джобы, описанные максимально абстрактно (`before_script`, `script`, `after_script`, `artifacts`, `cache`) без связей и взаимодействий.

**Namespace скрытого джоба** — часть имени скрытого джоба до двойного двоеточия в конвенции `.repo:component::job`, уникально идентифицирующая источник джоба.

**Пререлизная версия компонента** — версия SemVer с суффиксом (например, `2.0.0-rc.1`), публикуемая в каталог для тестирования; не выбирается частичными версиями и `~latest`.

## Основные концепции

### Проблемы монолитных шаблонов

Как растёт монолит: стартап (три джоба, один язык, один файл) → клиенты и инвесторы → новые джобы (кэш зависимостей, сканеры безопасности) → новые языки (Ruby, Go) → отдельные файлы на язык плюс общий `common template` → команды с особыми требованиями (два Python-проекта, свои воркеры, Airflow вместо канарейки, «дайте пару джобов из общего файла»). В этот момент `common template` становится монолитом.

Три проблемы монолита:

1. **Тестирование.** Нельзя проверить один джоб из дальней части конвейера: монолит тащит завязки на внешние сервисы, поэтому тестовый пайплайн сначала требует креды для остальных джобов, кучу переменных или заглушек (переопределение скриптов, правил). Метафора из доклада: слона не запихнёшь в МРТ, чтобы диагностировать пальец.
2. **Расширяемость.** Инженер, впервые увидевший шаблон на тысячу строк, теряет часы на понимание, прежде чем добавить фичу; первые попытки редко успешны.
3. **Переиспользование.** Выдрать подходящий джоб из общего шаблона — квест (он глубоко пустил корни), поэтому инженер проще пишет свой.

### Инкапсуляция: противоположность монолитности

**Переменные.** Глобальная секция `variables` — зло: два похожих шаблона (например, для Python-проектов и воркеров), включённые в один конвейер, оверрайдят значение одной и той же переменной (побеждает второй `include`). Тот же конфликт ломает интеграцию GitLab с Vault, когда шаблоны задают `VAULT_ADDR` как `vault-stage` и `vault-prod`, и конвейер обращается не к тому инстансу. В компонентах глобальные ключи (`variables`, `default`, `stages`, `workflow`) не применяются: документация GitLab относит их к категории «avoid» — они влияют на все джобы конвейера потребителя, включая джобы вне компонента. Документированные альтернативы: конфигурация непосредственно в каждом джобе (даже с дублированием) или скрытые джобы с `extends` под уникальными именами. Параметризация идёт через `inputs`, которые действуют локально.

**Джобы.** Имена джобов статичны: два одинаковых имени нельзя хранить в одном конвейере, поэтому шаблон невозможно включить дважды. Скрытые джобы (с точки) не решают проблему — в конвейере придётся вручную переопределять публичный джоб от каждого скрытого. Решение: `inputs` инициализируются до инициализации джоба (интерполяция выполняется на этапе компиляции пайплайна), поэтому имена джобов шаблонизируются (например, через вход `job_suffix`), и компонент можно включать дважды с разными значениями.

**Секреты.** Инкапсулируются через `inputs`: в значении входа передаётся ссылка на переменную проекта, переменную группы или dotenv-артефакт. Верифицированная деталь: значение входа может раскрывать CI/CD-переменные через функцию интерполяции `expand_vars` (`$[[ inputs.x | expand_vars ]]`); раскрываются только переменные, допустимые в `include` и не помеченные masked, вложенное раскрытие не поддерживается — masked-переменная приходит в компонент как литеральная строка `$VAR` (см. [документацию GitLab по inputs](https://docs.gitlab.com/ci/inputs/)).

### Анатомия компонента: логика и обвязка

GitLab ищет компоненты в папке `templates/`. Структура компонента:

```text
templates/
└── <component>/
    ├── template.yaml   # entry point: обвязка
    └── jobs.yaml       # скрытые джобы: чистая логика
```

- **`jobs.yaml`** — только скрытые джобы, максимально абстрактные: `before_script`, `script`, `after_script`, `artifacts`, `cache`. Никаких `needs`, `dependencies`, `rules`, `stage` — чистая полезная нагрузка. Файл можно безбоязненно включать в другие компоненты: ничего «лишнего» не прилетит.
- **`template.yaml`** — обвязка: `include` файла `jobs.yaml`, проброс принятых `inputs` внутрь и `extends` от скрытых джобов. Поля взаимодействия (`image`, `rules`, `needs`, `stage`, `tags`) описываются здесь.

**Именование скрытых джобов** — конвенция `.repo:component::job`:

- точка в начале — скрытый джоб;
- имя репозитория, двоеточие, имя компонента, двойное двоеточие, имя джоба;
- часть до двойного двоеточия — namespace джоба, уникально идентифицирующий источник.

Бонус: в Pipeline Editor сразу видно, откуда прилетел джоб (например, `python-cicd:package::test`) — пропадает «конвейерная запутанность», когда непонятно, что откуда растёт.

**Контекст компонента** (beta в 18.6, GA в 18.7) — компонент интерполирует собственные метаданные (`$[[ component.name ]]`, `$[[ component.version ]]`, `$[[ component.sha ]]`, `$[[ component.reference ]]`), объявив их в `spec:component`. Применение: тегировать образы версией компонента или логировать версию без проброса через `inputs` (см. [Каталог компонентов](./ci_cd_catalog_components.md)).

### Переиспользование логики между компонентами

Два подхода:

1. `include` файла `jobs.yaml` другого компонента и `extends` от нужного скрытого джоба.
2. Общая папка `common/` с `jobs.yaml` общих джобов; включается в те компоненты, где нужен. В namespace скрытого джоба указывается `common` вместо имени компонента.

### Изоляция по репозиториям

Компоненты разнесены по компактным репозиториям по семантическому признаку с суффиксом `-cicd`: `docker-cicd`, `airflow-cicd`, `helm-cicd`, `k8s-cicd`. Преимущества:

- **Контроль доступа** — в компактном репозитории назначаются maintainers и ограничивается редактирование для остальных (см. [Merge request approval rules](../Tutorials/merge_request_approval_rules.md) и CODEOWNERS);
- **Меньше связей** — инженер не идёт путём наименьшего сопротивления («рядом лежит подходящий компонент, просто инклюдю»), а следует регламенту;
- **Навигация в каталоге** — по имени сразу понятно, к чему относится шаблон.

## Практические сценарии

**Предварительные условия.** Для публикации компонента: GitLab 17.0+, проект с директорией `templates/`, включённый переключатель «CI/CD Catalog project» (Settings → General → Visibility, project features, permissions) и релизы, создаваемые только джобом с ключевым словом `release` — Releases в UI для проектов компонентов отключён. Для потребления компонента: доступ к проекту-источнику на уровне не ниже Reporter (для private-проектов).

### Сценарий 1: Структура репозитория компонента

```text
component-repo/
├── doc/
│   └── images/          # скриншоты рендеренного пайплайна для README
├── templates/
│   └── <component>/
│       ├── template.yaml
│       └── jobs.yaml
├── test/                # тестовые проекты-потребители
├── .gitlab-ci.yml       # пайплайн самого компонента (обязателен для релиза)
├── LICENSE.md           # рекомендация документации GitLab
└── README.md
```

Папка `doc/` — не требование GitLab, а практика компании; `LICENSE.md` — рекомендация документации. `templates/` — единственное место, откуда GitLab читает компоненты; файлы за его пределами в каталог не публикуются. В директории компонента каталогом релизится только `template.yaml`; вспомогательные файлы (например, `jobs.yaml`) остаются в репозитории и подключаются через `include:local` — документированный GitLab способ разнесения логики компонента по файлам.

### Сценарий 2: Двойной include одного компонента

Задача: один конвейер содержит и deps, и worker — два включения одного компонента с разными входами.

```yaml
# .gitlab-ci.yml потребителя
include:
  - component: $CI_SERVER_FQDN/org/python-cicd/package@1.2.0
    inputs:
      job_suffix: deps
  - component: $CI_SERVER_FQDN/org/python-cicd/package@1.2.0
    inputs:
      job_suffix: worker
```

Внутри компонента имена джобов шаблонизируются входом:

```yaml
# templates/package/template.yaml
spec:
  inputs:
    job_suffix:
      type: string
      description: "Suffix to uniquify job names when the component is included twice"
---
include:
  - local: '/templates/package/jobs.yaml'

package-deps-$[[ inputs.job_suffix ]]:
  extends: .python-cicd:package::deps
  stage: build
  image: python:3.12

package-worker-$[[ inputs.job_suffix ]]:
  extends: .python-cicd:package::worker
  stage: test
  image: python:3.12
  needs: [package-deps-$[[ inputs.job_suffix ]]]
```

> **Примечание:** `jobs.yaml` не объявляет `spec:inputs`, поэтому пробрасывать входы в локальный `include` нельзя — входы доступны только в том файле, где они объявлены. Локальный `include` гарантирует одинаковый Git SHA для обоих файлов компонента.

```yaml
# templates/package/jobs.yaml — только скрытые джобы, без связей
.python-cicd:package::deps:
  before_script:
    - pip install -r requirements.txt
  script:
    - pip install .
  cache:
    key: deps
    paths:
      - .venv/

.python-cicd:package::worker:
  script:
    - python -m worker
  artifacts:
    paths:
      - dist/
```

> **Примечание:** для той же задачи (уникализация имён при повторном подключении) в базе знаний рекомендуется вход `job_name_prefix`, в официальной документации — `job-prefix`; механизм тот же, выбор префикса или суффикса — дело стиля. См. [Каталог компонентов](./ci_cd_catalog_components.md).

### Сценарий 3: Семвер-автоматизация и пререлизы

- Релизный пайплайн компонента (ветка master): джоб `bump` генерирует dotenv-артефакт с версией, который пробрасывается в релизный джоб, выпускающий пререлизную версию компонента.
- Формат пререлиза в описанной практике: `<major>.<minor>` + `rc` + ID merge request + порядковый номер пререлиза (в расшифровке показано как `2.0-rc.29-1`, где 29 — ID MR, 1 — порядковый номер). В терминах SemVer это запись вида `2.0.0-rc.29.1`. ID MR включают, потому что в одном репозитории могут работать несколько инженеров одновременно и существовать несколько пререлизов.
- **Мягкие ссылки** — компромисс вместо ветки master: `@1.2` автоматически подхватывает патчи, `@1` — минорные версии. Проверено по документации GitLab: частичные версии выбирают последнюю подходящую опубликованную версию, но никогда — пререлизы.
- **Лейблы MR вместо Conventional Commits.** Инженеры пишут в коммитах что хотят; тип изменения выбирается в MR из выпадающего списка с цветными лейблами (`feat` / `fix` / `breaking change`). Это снижает сопротивление: не нужно держать в голове формат коммита и править его при ошибке. О Conventional Commits и их автоматизации — в [Управлении релизами и SemVer](../Advanced/release_management_and_semver.md).

### Сценарий 4: Тестирование компонента

- В репозитории компонента — папка `test/` с тестовыми проектами-потребителями (в докладе: два проекта — Python-приложение и воркер — сильно различаются конфигурацией и даже образами джобов).
- Тесткейсы — через `include` файла `template.yaml` (entry point компонента) с разными значениями `inputs`: один шаблон, несколько тесткейсов благодаря инкапсулированности компонента.
- Тесты ставятся перед релизным джобом: CI/CD обязателен для публикации компонента (релиз создаётся пайплайном), поэтому зелёные тесты — естественный гейт перед выпуском версии.
- Меньше связей — проще тестировать: проверять фичу можно прямо в репозитории компонента, не включая его в большой конвейер микросервиса.

Локальная валидация до коммита — `glab ci config compile` раскрывает все `include`, `extends` и интерполяцию `inputs` и проверяет конфигурацию без запуска раннера:

```bash
glab ci config compile > resolved.yml && echo "OK: конфигурация валидна"
# → OK: конфигурация валидна
```

### Сценарий 5: Документирование

- Поле `description` у каждого входа — «по-человечески»; GitLab рендерит его в каталоге в таблице: назначение, дефолтное значение, тип, способ подключения.
- README: скриншот рендеренного пайплайна (комплимент потребителю — не нужно представлять в голове, как после шаблонизации имён будет выглядеть конвейер), пример использования с базовыми входами, перечень нужных `stage` и `variables` (секреты и глобальные настройки передаются через входы компонента).
- Согласно документации GitLab, дублировать описания входов в README не нужно — они отображаются на странице компонента автоматически; README стоит ссылать на опубликованный компонент.

### Сценарий 6: Синхронизация компонентов между инстансами (Git Mirroring)

Кейс: общие шаблоны для группы компаний-партнёра. Компоненты компактные и изолированные, поэтому их несложно сделать универсальными сразу для двух GitLab. Компоненты адресуются через `$CI_SERVER_FQDN`, поэтому `include:component` резолвится только внутри того же инстанса GitLab — отсюда mirroring как документированный способ обмена компонентами между инстансами. Синхронизация — встроенная фича GitLab Git Mirroring: коммиты из ветки master зеркалятся в GitLab партнёра, где запускается конвейер на базе SemVer-компонента и выпускает очередную версию компонента. Порядок настройки зеркала: создать группу для компонентов, настроить pull-mirror проекта, включить переключатель «CI/CD Catalog project» в зеркале и опубликовать релиз тегом (обычно последним SemVer-тегом). Mirroring компонентов между инстансами — документированный GitLab подход (см. [FAQ каталога](https://about.gitlab.com/blog/faq-gitlab-ci-cd-catalog) и [документацию](https://docs.gitlab.com/ci/components/#use-a-gitlabcom-component-on-gitlab-self-managed)).

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Конфликт переменных в конвейере | Два шаблона задают одну глобальную переменную через `include` | Перейти на компоненты; параметры — только через `inputs`. Глобальную секцию `variables` в компонентах не применять |
| `Duplicate job name` при двойном include | Имена джобов статичны | Шаблонизировать имена входом (`job_suffix` / `job_name_prefix`) |
| Сломались все конвейеры после правки шаблона | `include` из дефолтной ветки (master) | Фиксировать версию SemVer; для автообновлений — частичные версии `@1.2` / `@1` |
| Пререлиз не находится по `@2.0` | Частичные версии и `~latest` никогда не выбирают пререлизы | Указывать полный SemVer пререлиза, например `@2.0.0-rc.1` |
| `content not found` при `@~latest` или частичной версии | В проекте-каталоге нет опубликованных релизов (тег без релиза в каталог не попадает) | Создать релиз джобом с `release`; для тестов указывать полный SemVer или SHA |
| Секрет не раскрывается в значении входа | Masked-переменные не раскрываются через `expand_vars` | Передавать немаскированные переменные или использовать `secrets:` / OIDC; см. [документацию](https://docs.gitlab.com/ci/inputs/) |

## Лучшие практики

- Конвейер — список компонентов. Не смешивать компоненты с простыми шаблонами: у шаблонов нет чётких правил, и монолитность начинает расти снова.
- Инкапсулировать всё: переменные — через `inputs`, джобы — через шаблонизацию имён, секреты — через входы.
- Проектировать CD как набор компонентов: согласовывать входы/выходы (артефакт, кэш) с потребителями до написания джобов.
- Связи между компонентами (`needs`, `dependencies`) — через входы (например, вход `needs` с именем джоба соседнего компонента). Идеально — разруливать стейджами; входы — решение, когда стейджи не помогают.
- Мотивировать обновления: мягкие версии (`@1.2`) для патчей; для строгого контроля — Renovate, чей штатный менеджер `gitlabci` отслеживает ссылки `component:` в `.gitlab-ci.yml` (depType `repository`) (см. [Автоматизацию обновления зависимостей](../../dependency_automation.md)).
- Аудит чужих компонентов перед использованием: компоненты в каталоге публикует кто угодно — проверять, что токены и секреты в исходном коде используются только по назначению, и закреплять критичные компоненты на SHA (см. [Каталог компонентов](./ci_cd_catalog_components.md), раздел безопасности).
- Очистка: отключение переключателя «CI/CD Catalog project» (Settings → General) убирает проект из каталога и уничтожает метаданные опубликованных версий; сам репозиторий и теги остаются, повторная публикация — новым релизом.
- Версионирование должно быть удобным, чтобы не отпугнуть инженеров: автоматизировать SemVer и выбирать тип изменения лейблом MR.
