# GitLab CI: Эволюция переиспользуемого пайплайна

## Определения

**Эволюция переиспользуемых пайплайнов** — процесс последовательного совершенствования архитектуры CI/CD конфигурации, направленный на снижение дублирования, повышение безопасности и упрощение поддержки через переход от копирования кода к версионированным компонентам.

**Контекст:** Данный документ описывает путь развития пайплайнов от простейших скриптов до зрелой экосистемы CI/CD Catalog и будущих GitLab Steps, разделенный на уровни зрелости.

## Основные концепции

### Этапы развития и уровни зрелости

| Этап | Метод | Ключевая характеристика | Основная проблема |
| :--- | :--- | :--- | :--- |
| **1** | [Копирование (Boilerplate)](./evolution/evolution_boilerplate.md) | Каждый проект имеет полную копию кода | Невозможность массовых обновлений |
| **2** | [Централизация (Include)](./evolution/evolution_include.md) | Использование `include:project` для общих файлов | Жесткая структура, "хрупкость" при изменениях |
| **3** | [Гибкость (Extends)](./evolution/evolution_extends.md) | Наследование от скрытых заданий (`.base_job`) | Конфликты переменных, отсутствие типизации |
| **4** | [Абстракция (Implementation)](./evolution/evolution_kaniko.md) | Сокрытие деталей реализации (например, Kaniko) | Неявный интерфейс через переменные |
| **5** | [Компоненты (Catalog)](./evolution/evolution_components.md) | Версионирование (SemVer), типизация, UI-каталог | Требует высокой квалификации DevOps |
| **6** | **Шаги (GitLab Steps)** | Мелкозернистые, переиспользуемые шаги внутри заданий | Находится в стадии активной разработки (Experimental) |

### Сравнение подходов по характеристикам

| Характеристика | Этап 2 (Include) | Этап 3 (Extends) | Этап 5 (Catalog) | Этап 6 (Steps) |
| :--- | :--- | :--- | :--- | :--- |
| **Версионирование** | Теги/Ветки | Теги/Ветки | **SemVer (Release)** | **SemVer** |
| **Интерфейс** | Глобальные переменные | Переменные задания | **Явные inputs** | **Явные inputs/outputs** |
| **Изоляция** | Низкая | Средняя | **Полная** | **Контейнерная (Step)** |
| **Документация** | README | README | **Автоматическая (UI)** | **Автоматическая** |

## Практические сценарии

### Сценарий 1: Технический триггер для перехода

| Ситуация | Решение | Результат |
| :--- | :--- | :--- |
| Изменение версии линтера требует правки в 20 проектах | Переход 1 → 2 | Обновление в одном месте в `shared-templates` |
| Проектам нужны разные аргументы для одной и той же задачи сборки | Переход 2 → 3 | Использование `extends` для переопределения `variables` |
| Необходимо сменить Docker на Kaniko без правок в проектах | Переход 3 → 4 | Инкапсуляция логики внутри шаблона (Abstraction) |
| Проекты случайно затирают переменные, нужные для работы шаблона | Переход 4 → 5 | Использование `inputs` для изоляции параметров |
| Командам сложно искать доступные шаблоны и их параметры | Переход 5 → 5 | Публикация в CI/CD Catalog с визуальным поиском |

### Сценарий 2: Выбор стратегии для Enterprise

Для крупных организаций рекомендуется пропускать этап 1 и сразу внедрять этап 3 с быстрым переходом к этапам 5 и 6:

1. **Стандартизация:** Создание репозитория-источника для каждого технологического стека (Java, Python, Go).
2. **Абстракция инструментов:** Например, замена Docker на Kaniko или внедрение сканеров безопасности (Trivy) происходит прозрачно для разработчика внутри шаблона.
3. **Версионирование:** Использование жестких ссылок на теги (`ref: v1.2.0`) обязательно для предотвращения падения пайплайнов при обновлении шаблонов.

### Сценарий 3: Чек-лист оценки текущего уровня

*   **Уровень 1-2:** Пайплайны обновляются вручную? Ссылки на шаблоны ведут на ветку `master`?
*   **Уровень 3-4:** Используются ли скрытые задания (`.`) для наследования? Скрыта ли логика реализации инструментов от конечного пользователя?
*   **Уровень 5:** Используется ли интерполяция `$[[ inputs.key ]]`? Проходят ли компоненты независимое тестирование перед релизом?
