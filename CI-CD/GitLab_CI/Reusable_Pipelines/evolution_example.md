# GitLab CI: Эволюция переиспользуемого пайплайна (практический пример)

## Определения

**Эволюция переиспользуемых пайплайнов** — последовательный подход к организации CI/CD конфигурации в GitLab, переходящий от простого дублирования к зрелым версионированным компонентам с явным интерфейсом.

**Контекст:** Документ описывает практический путь команды от boilerplate-кода к CI/CD Components через 5 этапов зрелости.

---

## Основные концепции

### Этапы эволюции

| Этап | Подход | Описание |
| :--- | :--- | :--- |
| **1** | [Дублирование кода](./evolution/stage1_boilerplate.md) | Проблема — копирование одинаковой конфигурации в каждый проект |
| **2** | [Централизация с `include`](./evolution/stage2_include.md) | Вынос общего кода в центральный репозиторий шаблонов |
| **3** | [Гибкость с `extends`](./evolution/stage3_extends.md) | Наследование и кастомизация шаблонов |
| **4** | [Абстрагирование (Kaniko)](./evolution/stage4_kaniko.md) | Прозрачное обновление без изменения проектов |
| **5** | [CI/CD Components](./evolution/stage5_components.md) | Типизация, валидация, каталог |

### Сводная таблица эволюции

| Этап | Подход | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **1** | Дублирование | Простота начала | Нет поддержки, стандартизации |
| **2** | `include:project` | Централизация | Нет гибкости |
| **3** | `include` + `extends` | Централизация + гибкость | Нет типизации, безопасности |
| **4** | Абстракция (Kaniko) | Безопасность, прозрачность | Нет явного интерфейса |
| **5** | CI/CD Components | Типизация, валидация, каталог | Высокая сложность настройки |

## Практические сценарии

### Сценарий 1: Выбор этапа по размеру команды

| Размер команды | Количество проектов | Рекомендуемый этап | Обоснование |
| :--- | :--- | :--- | :--- |
| 1–3 разработчика | 1–3 проекта | Этап 2–3 (`include` + `extends`) | Минимальная сложность, достаточная централизация |
| 5–10 разработчиков | 5–10 проектов | Этап 3–4 (абстракция) | Баланс гибкости и безопасности |
| 10+ разработчиков | 10+ проектов | Этап 5 (Components) | Полная типизация, валидация, каталог |
| Публичные компоненты | Любое | Этап 5 (Components с каталогом) | Semver, UI-каталог, автоматическая документация |

### Сценарий 2: Критерии перехода к следующему этапу

| Триггер | Переход | Действие |
| :--- | :--- | :--- |
| Дублирование в 3+ проектах | 1 → 2 | Создание репозитория `ci-templates` |
| Потребность в кастомизации | 2 → 3 | Скрытые job + `extends` |
| Требования безопасности | 3 → 4 | Переход с `docker:dind` на Kaniko |
| Потребность в типизации | 4 → 5 | Внедрение `spec:inputs`, каталог |

### Сценарий 3: Оценка зрелости команды

**Вопросы для самооценки:**

1. Сколько проектов используют одинаковую CI-конфигурацию?
2. Как быстро вносится изменение во все проекты?
3. Есть ли версионирование шаблонов?
4. Проходят ли шаблоны автоматическую валидацию?
5. Есть ли каталог компонентов с поиском?

**Рекомендация:** Начните с этапа 2 и двигайтесь постепенно по мере роста команды и проектов.
