# GitLab CI: Эволюция переиспользуемого пайплайна

## Определения

**Эволюция переиспользуемых пайплайнов** — системный процесс последовательного совершенствования архитектуры CI/CD конфигураций. Направлен на минимизацию дублирования кода (принцип DRY), повышение безопасности инфраструктуры, обеспечение масштабируемости и упрощение поддержки через переход от прямого копирования YAML-кода к версионированным, типизированным компонентам.

**Модель зрелости CI/CD (Maturity Model)** — иерархическая структура этапов развития пайплайнов, где каждый следующий уровень решает фундаментальные проблемы предыдущего, повышая уровень абстракции и изоляции.

## Основные концепции

### Этапы развития и уровни зрелости

| Уровень | Метод | Ключевая характеристика | Основная проблема |
| :--- | :--- | :--- | :--- |
| **1** | [Копирование (Boilerplate)](./evolution/evolution_boilerplate.md) | Прямое копирование YAML между проектами. | Невозможность централизованных обновлений и исправлений. |
| **2** | [Централизация (Include)](./evolution/evolution_include.md) | Подключение общих файлов через `include:project`. | Жесткость: сложно адаптировать шаблон под нужды конкретного проекта. |
| **3** | [Наследование (Extends)](./evolution/evolution_extends.md) | Использование `extends` от скрытых заданий (`.base`). | Неявный интерфейс, риск случайного переопределения переменных. |
| **4** | [Абстракция деталей](./evolution/evolution_kaniko.md) | Инкапсуляция инструментов (например, Kaniko) внутри шаблона. | Сложность отладки «черного ящика» для разработчиков. |
| **5** | [CI/CD Components (Catalog)](./evolution/evolution_components.md) | Типизированные входы (`inputs`), SemVer, UI-каталог. | Высокий порог входа для проектирования интерфейсов. |
| **6** | **GitLab Steps** | Изолированные контейнерные шаги вместо Bash-скриптов. | Статус экспериментальной технологии (Active Development). |

### Техническое сравнение подходов

| Характеристика | Этап 2 (Include) | Этап 3 (Extends) | Этап 5 (Catalog) | Этап 6 (Steps) |
| :--- | :--- | :--- | :--- | :--- |
| **Версионирование** | Теги или Commit SHA | Теги или Commit SHA | **Релизы SemVer** | **SemVer** |
| **Интерфейс** | Глобальные переменные | Переменные задания | **Декларативные inputs** | **Inputs / Outputs** |
| **Изоляция** | Отсутствует | Частичная (Variables) | **Полная (Scope)** | **Контейнерная (Run)** |
| **Валидация** | Синтаксическая | Синтаксическая | **Типизация данных** | **Строгие схемы** |

## Практические сценарии

### Сценарий 1: Технические триггеры для миграции

| Ситуация | Решение (Переход) | Результат |
| :--- | :--- | :--- |
| Регулярные ошибки в Bash-скриптах из-за опечаток в переменных | **4 → 5 (Catalog)** | Ошибки отлавливаются на этапе Pipeline Lint благодаря типизации. |
| Необходимость смены Docker на Buildah без уведомления разработчиков | **3 → 4 (Abstraction)** | Логика меняется только в центральном шаблоне, проекты не меняются. |
| Огромные `.gitlab-ci.yml` (более 1000 строк) | **1 → 2 (Include)** | Файл разбивается на логические модули (build, test, security). |
| Конфликты переменных между разными включенными шаблонами | **4 → 5 (Catalog)** | Каждый компонент работает в своем изолированном пространстве имен. |

### Сценарий 2: Архитектура Enterprise-уровня

Для крупных организаций с 100+ микросервисами рекомендуется пропускать начальные этапы и внедрять гибридную модель:

1.  **Platform Repository:** Единый проект (например, `org/ci-catalog`), содержащий компоненты для всех стандартных операций (сборка, деплой в K8s, сканирование).
2.  **Versioning Policy:** Запрет на использование веток (`master`, `main`) в `include`. Только фиксированные теги.
3.  **Governance:** Принудительное внедрение проверок безопасности через **Pipeline Execution Policies** (вместо старых Compliance Pipelines), которые подключают компоненты Stage 5 на уровне всей группы GitLab.

### Сценарий 3: Чек-лист перехода на новый уровень

*   **Переход на Уровень 5:**
    *   Все входные параметры описаны в блоке `spec:inputs`.
    *   Компонент имеет файл `README.md`, сгенерированный автоматически или вручную по спецификации.
    *   Существуют интеграционные тесты (в папке `tests/`), проверяющие работоспособность компонента перед релизом.
*   **Отказ от Legacy (Уровень 1-2):**
    *   Удалены прямые вызовы `docker login` и `docker build` из локальных конфигов.
    *   Все внешние зависимости зафиксированы по версиям (ref).
