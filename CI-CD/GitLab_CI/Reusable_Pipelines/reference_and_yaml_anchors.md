# GitLab CI: Механизмы !reference и якоря YAML

## Определения

**`!reference`** — специализированный тег GitLab CI для явной ссылки на фрагменты конфигурации других заданий или секций. Позволяет извлекать и вставлять части настроек (`script`, `rules`, `variables`, `tags`, `image`, `services`, `cache`, `artifacts`) с полной поддержкой валидации через CI Lint. Работает даже между файлами, подключёнными через `include`.

**Якорь YAML (YAML Anchor, `&`)** — стандартный механизм сериализации данных языка YAML для маркировки блока конфигурации с целью его последующего повторного использования.

**Ссылка YAML (YAML Alias, `*`)** — механизм YAML для вставки содержимого, помеченного якорем.

**Скрытое задание (Hidden Job)** — задание, имя которого начинается с точки (`.base_job`). Оно не добавляется в пайплайн напрямую планировщиком, а служит исключительно контейнером или шаблоном для фрагментов конфигурации.

## Базовые концепции

### Сравнение !reference и якорей YAML

Хотя оба механизма служат для соблюдения принципа DRY (Don't Repeat Yourself), GitLab рекомендует отдавать приоритет `!reference` из-за лучшей интеграции с инструментами проверки и поддержки межфайловых ссылок.

| Критерий | `!reference` | Якоря YAML (`&`) / Ссылки (`*`) |
| :--- | :--- | :--- |
| **Уровень обработки** | Компилятор GitLab CI | Парсер YAML (до логики пайплайна) |
| **Валидация Lint** | Полная поддержка | Ограниченная (только синтаксис YAML) |
| **Область видимости** | **Весь пайплайн** (через `include`) | Только текущий файл |
| **Гибкость** | Доступ к любым элементам (даже индексам массивов) | Только полная вставка помеченного блока |
| **Читаемость** | Высокая (явный синтаксис) | Средняя (чувствительность к порядку определения) |
| **Рекомендация** | Основной инструмент | Для локального слияния словарей (Merge Key) |

> **Важное ограничение:** Теги `!reference` не поддерживают интерполяцию переменных `inputs` (например, `$[[ inputs.name ]]`). Они разрешаются на финальном этапе компиляции пайплайна, когда инпуты уже подставлены в другие места.

### Синтаксис !reference

Тег позволяет ссылаться на задание и путь к конкретному ключу внутри него.

**Формат:**
`!reference [<имя_задания>, <ключ_1>, <ключ_2>, ...]`

**Технические нюансы:**
1.  **Глубина вложенности:** Допускается до **10 уровней** вложенных ссылок `!reference`.
2.  **Ленивое разрешение (Lazy Resolution):** В новых версиях GitLab (17.x+) теги `!reference` разрешаются после слияния всех файлов `include`. Это означает, что вы можете ссылаться на задание, которое определено в файле, подключенном позже.

### Синтаксис якорей YAML

Механизм работает на уровне парсера YAML. Ссылка (`*`) не может быть использована до того, как в файле определён Якорь (`&`).

**Пример:**
```yaml
.setup_script: &setup
  - apt-get update -qy
  - apt-get install -y git

test_job:
  script:
    - *setup
    - npm test
```

## Практические сценарии

### Сценарий 1: Атомарное переиспользование скриптов через !reference

Наиболее частое применение — создание библиотеки общих скриптов настройки окружения, которые можно вставлять в любую часть списка `script`.

```yaml
.common_env:
  script:
    - echo "Инициализация..."
    - export DEBIAN_FRONTEND=noninteractive

build:
  stage: build
  script:
    - !reference [.common_env, script]
    - ./build.sh
```

### Сценарий 2: Использование конкретных элементов списков (v17.2+)

`!reference` позволяет выбрать один конкретный элемент из массива (например, тег или образ), что невозможно сделать с помощью YAML Anchors.

```yaml
.runner_configs:
  tags: [docker, high-cpu, gpu]

ml_task:
  tags:
    - !reference [.runner_configs, tags, 2] # Выберет только "gpu"
  script:
    - train.py
```

### Сценарий 3: Переиспользование правил (rules)

Позволяет централизованно управлять сложными условиями запуска заданий без дублирования длинных списков `if`.

```yaml
.mr_rules:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'
    - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'

lint:
  stage: test
  rules:
    - !reference [.mr_rules, rules]
  script:
    - npm run lint
```

### Сценарий 4: Комбинация !reference и extends

Сочетание двух механизмов обеспечивает максимальную гибкость: `extends` для наследования общей структуры и `!reference` для точечной вставки специфичных фрагментов.

```yaml
.base_node:
  image: node:22-alpine
  before_script:
    - npm ci

.notify:
  - echo "Отправка уведомления в Slack..."

deploy:
  extends: .base_node
  script:
    - npm run deploy
  after_script:
    - !reference [.notify]
```

### Сценарий 5: Слияние словарей (Merge Key) через YAML Anchors

YAML Anchors остаются незаменимыми при необходимости слияния объектов (например, словарей `variables`) с переопределением части значений.

```yaml
.db_config: &db_defaults
  variables:
    DB_PORT: "5432"
    DB_USER: "readonly"

production:
  variables:
    <<: *db_defaults # Вставка дефолтов
    DB_HOST: "prod-db.internal"
    DB_USER: "admin" # Переопределение readonly на admin
```

## Дополнительная информация

### Ограничения и особенности механизмов

| Ограничение | `!reference` | Якоря YAML |
| :--- | :--- | :--- |
| **Межфайловые ссылки** | **Да** (через `include`) | Нет (только внутри одного файла) |
| **Глубина вложенности** | До **10** уровней | Без жёстких системных лимитов |
| **Поддержка inputs** | **Нет** (разрешаются позже инпутов) | Нет |
| **Слияние словарей** | Только полная замена ключа | Поддерживает Merge Key (`<<`) |

### Распространённые ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `unknown anchor` | Ссылка на несуществующий якорь или задание | Проверьте опечатки и наличие `include`. |
| `circular reference` | Рекурсия: А -> Б -> А | Разорвите цепочку ссылок. |
| `must be an array` | Неверный синтаксис `!reference` | Убедитесь, что аргументы указаны в `[]`. |

### Валидация и отладка

Для проверки того, как GitLab развернул все ваши ссылки и подстановки, используйте GitLab CLI (`glab`):

```bash
# Проверка синтаксиса текущего пайплайна
glab ci lint

# Просмотр финального (expanded) YAML со всеми подстановками
glab ci lint --show-expanded
```
