# GitLab CI: Механизмы !reference и якоря YAML

## Определения

**`!reference`** — специальный тег GitLab CI для явной ссылки на фрагменты конфигурации других заданий или секций. Позволяет извлекать и вставлять части настроек (`script`, `rules`, `variables`, `tags`, `image`, `services`, `cache`, `artifacts`) с полной поддержкой валидации через CI Lint. Работает даже между файлами, подключёнными через `include`.

**Якорь YAML (YAML Anchor, `&`)** — стандартный механизм языка YAML для маркировки блока конфигурации с целью его последующего повторного использования.

**Ссылка YAML (YAML Alias, `*`)** — механизм YAML для вставки содержимого, помеченного якорем.

**Скрытое задание (Hidden Job)** — задание, имя которого начинается с точки (`.`). Оно не запускается как часть пайплайна, а служит шаблоном или контейнером для фрагментов конфигурации.

## Базовые концепции

### Сравнение !reference и якорей YAML

Хотя оба механизма служат для минимизации дублирования кода (DRY — Don't Repeat Yourself), GitLab рекомендует отдавать приоритет `!reference` из-за лучшей интеграции с инструментами проверки и поддержки межфайловых ссылок.

| Критерий | `!reference` | Якоря YAML (`&`) / Ссылки (`*`) |
| :--- | :--- | :--- |
| **Тип** | Тег GitLab CI | Стандарт YAML |
| **Валидация Lint** | Полная поддержка | Ограниченная поддержка |
| **Читаемость** | Высокая (явный синтаксис) | Средняя (требует знания спецификации YAML) |
| **Гибкость** | Доступ к любым элементам (списки, вложенные ключи) | Только полная вставка помеченного блока |
| **Область видимости** | **Весь пайплайн** (работает между `include`) | Текущий файл (не работает между `include`) |
| **Рекомендация** | Предпочтительно | Для простых локальных случаев и слияния словарей |

> **Важное ограничение:** Теги `!reference` не поддерживают интерполяцию переменных `inputs` (например, `$[[ inputs.name ]]`). Если вам нужно передавать параметры в подключаемые шаблоны, используйте механизмы `extends` или **CI/CD Components**.

### Синтаксис !reference

Тег позволяет ссылаться на задание и путь к конкретному ключу внутри него.

**Формат:**
`!reference [<имя_задания>, <ключ_1>, <ключ_2>, ...]`

**Примеры использования:**

- Ссылка на весь скрипт: `script: !reference [.base, script]`
- Ссылка на конкретную команду из списка: `script: [ !reference [.base, script, 0] ]` # → Выберет первую строку скрипта
- Ссылка на элемент списка тегов: `tags: [ !reference [.config, tags, 0] ]`
- Ссылка на вложенную переменную: `variables: !reference [.env, variables, DB_HOST]`

### Синтаксис якорей YAML

Механизм работает на уровне парсера YAML до того, как GitLab начнёт обрабатывать логику CI.

**Пример:**

```yaml
.setup: &setup_anchor
  - apt-get update
  - apt-get install -y git

test:
  script:
    - *setup_anchor
    - npm test
```

## Практические сценарии

### Сценарий 1: Переиспользование скриптов через !reference

Наиболее частое применение — создание библиотеки общих скриптов настройки окружения.

```yaml
.common_setup:
  script:
    - echo "Инициализация окружения..." # → Инициализация окружения...
    - npm ci

build:
  stage: build
  script:
    - !reference [.common_setup, script]
    - npm run build

test:
  stage: test
  script:
    - !reference [.common_setup, script]
    - npm test
```

### Сценарий 2: Использование конкретных элементов списков

`!reference` позволяет выбрать один элемент из массива, что невозможно сделать с помощью YAML Anchors.

```yaml
.runner_configs:
  tags:
    - docker
    - high-cpu

heavy_job:
  tags:
    - !reference [.runner_configs, tags, 1] # → Тег "high-cpu"
  script:
    - build_project.sh
```

### Сценарий 3: Переиспользование правил (rules)

Позволяет централизованно управлять условиями запуска заданий.

```yaml
.mr_only:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

lint:
  stage: test
  rules:
    - !reference [.mr_only, rules]
  script:
    - npm run lint
```

### Сценарий 4: Комбинация !reference и extends

Сочетание двух механизмов обеспечивает максимальную гибкость: `extends` для общей структуры и `!reference` для вставки специфичных фрагментов.

```yaml
.base_node:
  image: node:20-alpine
  before_script:
    - npm ci

.notify_script:
  - echo "Отправка уведомления о статусе..." # → Отправка уведомления о статусе...

deploy:
  extends: .base_node
  script:
    - npm run deploy
  after_script:
    - !reference [.notify_script]
```

### Сценарий 5: Слияние словарей (Merge Key) в YAML

YAML Anchors остаются полезными при необходимости слияния объектов (например, словарей переменных) с переопределением части значений. Обратите внимание, что YAML Merge Key (`<<`) — это расширение YAML 1.1, которое GitLab продолжает поддерживать.

```yaml
.db_config: &db_defaults
  variables:
    DB_PORT: "5432"
    DB_USER: "admin"

staging:
  variables:
    <<: *db_defaults
    DB_HOST: "staging.db"

production:
  variables:
    <<: *db_defaults
    DB_HOST: "prod.db"
    DB_USER: "root" # Переопределение admin
```

## Дополнительная информация

### Ограничения и особенности механизмов

| Ограничение | `!reference` | Якоря YAML |
| :--- | :--- | :--- |
| **Межфайловые ссылки** | **Да** (через `include`) | Нет (только внутри одного файла) |
| **Глубина вложенности** | До **10** уровней | Без жёстких ограничений |
| **Поддержка inputs** | **Нет** (разрешаются до интерполяции) | Нет |
| **Проверка (Lint)** | Выявляет битые ссылки | Не выявляет отсутствие якоря до исполнения |

**Lazy Resolution (Ленивое разрешение):** В новых версиях GitLab (17.x+) теги `!reference` разрешаются после полного слияния всех YAML-файлов. Это гарантирует корректную работу даже при сложных вложенных `include`.

### Распространённые ошибки

- **Битые ссылки:** `!reference: unknown anchor` — задание или ключ не найдены. Всегда проверяйте конфигурацию через CI Lint.
- **Циклическая зависимость:** задание А ссылается на задание Б, которое в свою очередь ссылается на А.
- **Порядок в YAML:** Ссылка (`*`) не может быть использована до того, как определён Якорь (`&`). Это критично для больших файлов.

### Валидация

Для проверки иерархии и просмотра развёрнутого вида конфигурации рекомендуется использовать GitLab CLI (`glab`):

```bash
# Проверка синтаксиса текущего пайплайна
glab ci lint

# Просмотр финального YAML со всеми подстановками и включёнными файлами
glab ci lint --show-expanded
```
