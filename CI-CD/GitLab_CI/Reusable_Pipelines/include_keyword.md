# GitLab CI: Механизм `include`

## Определения

**`include`** — механизм GitLab CI для подключения внешних YAML-файлов к конфигурации пайплайна. Позволяет создавать модульные, переиспользуемые конфигурации, разделяя огромные файлы настроек на логические блоки или подключая централизованные библиотеки шаблонов.

**Важно:** Файлы `include` обрабатываются на этапе компиляции пайплайна **первыми**. Затем они сливаются с основной конфигурацией `.gitlab-ci.yml`. При совпадении имен заданий (jobs) локальная конфигурация всегда имеет приоритет и перезаписывает включённую (Merge behavior).

## Базовые концепции

### Типы `include`

| Тип | Описание | Когда использовать |
| :--- | :--- | :--- |
| **`include:local`** | Файл в том же репозитории и ветке | Разделение конфигурации внутри проекта (модульность) |
| **`include:project`** | Файл из другого проекта на том же инстансе | Централизованные шаблоны для всей организации (SSoT) |
| **`include:remote`** | Файл по HTTP/HTTPS URL | Сторонние шаблоны, публичные библиотеки, внешние инструменты |
| **`include:template`** | Встроенные шаблоны GitLab | Стандартные решения: SAST, DAST, Auto DevOps |
| **`include:component`** | CI/CD компонент из каталога | Современные версионируемые модули с `spec:inputs` |

### Синтаксис

#### Краткая форма (только для `local`)

```yaml
include:
  - '.gitlab-ci/build.yml'
  - '.gitlab-ci/test.yml'
```

#### Полная форма

Рекомендуется для повышения читаемости и поддержки расширенных параметров.

```yaml
include:
  - local: '.gitlab-ci/build.yml'

  - project: 'infrastructure/ci-templates'
    ref: v2.4.0
    file: '/docker/build-kaniko.yml'

  - remote: 'https://example.com/global-defaults.yml'
    # Проверка целостности (GitLab 17.9+)
    integrity: 'sha256-L3/GAoKaw0Arw6hDCKeKQlV1QPEgHYxGBHsH4zG1IY8='

  - template: 'Security/SAST.gitlab-ci.yml'

  - component: '$CI_SERVER_FQDN/group/component-name@1.2.0'
```

### `include:local`

Подключает файл из того же репозитория. По умолчанию используется та же ветка, в которой запущен пайплайн.

**Ограничения:**
- Путь должен быть относительным или начинаться с `/` (от корня репозитория).
- Нельзя подключать файлы через Git submodules (они не видны парсеру YAML).
- Допустимые расширения: `.yml` или `.yaml`.

### `include:project`

Позволяет использовать файлы из других проектов внутри одного инстанса GitLab. Это фундамент для создания корпоративной библиотеки шаблонов.

**Рекомендации по версионированию:**
- **Тег (SemVer):** Рекомендуется (`ref: v1.2.0`) для стабильности.
- **Commit SHA:** Максимальная стабильность (защита от подмены тега).
- **Ветка:** Не рекомендуется для production (изменения в ветке могут «уронить» сотни пайплайнов).

### `include:remote`

Подключает файлы по публичному URL. Полезно для использования общих инструментов безопасности или интеграций.

**Новые возможности:**
- **`integrity`**: SHA256-хеш (Base64) для проверки того, что удаленный файл не был изменен злоумышленниками (v17.9+).
- **`cache`**: (GitLab 18.9+, эксперимент) Позволяет кэшировать удаленный файл на стороне GitLab для ускорения старта пайплайна.

### `include:template`

Использует библиотеку готовых шаблонов, поставляемых самим GitLab. Список доступных шаблонов можно найти в репозитории [GitLab.org/gitlab/lib/gitlab/ci/templates](https://gitlab.com/gitlab-org/gitlab/-/tree/master/lib/gitlab/ci/templates).

### `include:component`

Подключает типизированные модули из CI/CD Catalog (v16.0+). Это наиболее современный и безопасный способ переиспользования. Подробнее в [CI/CD Catalog](./ci_cd_catalog_components.md).

### Дополнительные параметры

#### `include:inputs`

Передача входных параметров в подключаемый файл. Работает для компонентов и шаблонов, содержащих блок `spec:inputs`.

```yaml
include:
  - project: 'shared/templates'
    file: 'build.yml'
    inputs:
      stage: pre-build
      verbose: true
```

#### `include:rules`

Условное включение файлов. Файл подключается только если условие истинно.

```yaml
include:
  - local: '.gitlab-ci/deploy-prod.yml'
    rules:
      - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
```

**Критический нюанс:** Переменные в `include:rules` вычисляются в момент создания пайплайна. Переменные из `dotenv` артефактов других заданий здесь **недоступны**.

### Ограничения и приоритеты

| Ограничение | Значение | Описание |
| :--- | :--- | :--- |
| **Максимум включений** | **150** | Общее количество файлов (включая вложенные) |
| **Время ожидания** | **30 секунд** | Лимит на загрузку каждого внешнего ресурса |
| **Глубина вложенности** | Не ограничена явно | Рекомендуется не более 3 уровней для отладки |
| **Приоритет слияния** | **Локальный > Include** | Задания в корневом `.gitlab-ci.yml` переопределяют импортированные |

## Практические сценарии

### Сценарий 1: Модульная конфигурация проекта

Разделение конфигурации по зонам ответственности:
```yaml
include:
  - local: '.gitlab-ci/security.yml' # Настройки безопасности (Security Team)
  - local: '.gitlab-ci/tests.yml'    # Описание тестов (QA Team)
  - local: '.gitlab-ci/deploy.yml'   # Логика деплоя (DevOps Team)
```

### Сценарий 2: Централизация стандартов (SSoT)

Все проекты компании используют единый стандарт сборки Docker-образов, зафиксированный в проекте `shared-infrastructure`. При обновлении стандарта (например, внедрении Kaniko) изменения вносятся один раз.

## Дополнительная информация

### Валидация и отладка

Для проверки того, как GitLab развернул все ваши `include` и `inputs`, используйте инструмент **Pipeline Lint**:

1. **Web UI**: `CI/CD -> Editor`. Перейдите на вкладку `Pipeline Lint` и выберите опцию **«Show expanded YAML»**.
2. **GitLab CLI (`glab`)**:
   ```bash
   # Просмотр финального смерженного YAML в терминале
   glab ci lint --show-expanded
   ```
3. **API**: Отправьте запрос на `/api/v4/projects/:id/ci/lint` с параметром `include_merged_yaml=true`.

### Распространённые ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `file does not exist` | Неверный путь или файл отсутствует в `ref` | Проверьте опечатки и наличие тега/ветки в удаленном проекте. |
| `exceeded max includes` | Циклические или слишком глубокие `include` | Проверьте, не подключают ли файлы друг друга по кругу. |
| `include timeout` | Внешний URL недоступен или тормозит | Проверьте доступность для `remote` или используйте `local` копии. |
