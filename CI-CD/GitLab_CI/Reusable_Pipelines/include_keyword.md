# GitLab CI: Механизм `include`

## Определения

**`include`** — это ключевой механизм GitLab CI/CD, предназначенный для композиции конфигурационных файлов. Он позволяет подключать внешние YAML-ресурсы, разделяя монолитные описания пайплайнов на логические, повторно используемые модули или подключая централизованные библиотеки шаблонов.

**Раскрытие (Expansion)** — процесс, при котором GitLab загружает все включенные файлы и объединяет их в единую структуру до начала валидации и выполнения заданий.

**Важно:** Файлы `include` обрабатываются на этапе компиляции пайплайна **первыми**. Затем они сливаются с основной конфигурацией `.gitlab-ci.yml`. При совпадении имен заданий (jobs) локальная конфигурация всегда имеет приоритет и перезаписывает включённую (Merge behavior). Это позволяет использовать шаблоны как "базовые классы", переопределяя их логику под конкретные нужды проекта.

## Базовые концепции

### Архитектура слияния (Merge Behavior)

Когда GitLab встречает `include`, он выполняет глубокое слияние (deep merge) структур. Приоритет слияния определяется порядком:
1. Задания в самом `.gitlab-ci.yml` (наивысший приоритет).
2. Задания из файлов `include` (приоритет зависит от порядка: нижний в списке переопределяет верхний).

**Типы слияния для ключей:**
- **Словари (Hashes):** (например, `variables`, `cache:paths`) сливаются по ключам. Локальные ключи переопределяют или дополняют родительские.
- **Массивы (Arrays):** (например, `script`, `rules`, `tags`) **полностью замещаются**. Если в импортированном файле в `script` 10 строк, а в локальном вы переопределили `script` одной строкой — итоговое задание будет содержать только 1 локальную строку.

### Типы `include`

| Тип | Описание | Когда использовать |
| :--- | :--- | :--- |
| **`include:local`** | Файл в том же репозитории и ветке | Разделение конфигурации внутри проекта (модульность). |
| **`include:project`** | Файл из другого проекта на том же инстансе | Централизованные шаблоны для всей организации (SSoT). |
| **`include:remote`** | Файл по HTTP/HTTPS URL | Сторонние шаблоны, публичные библиотеки, внешние инструменты. |
| **`include:template`** | Встроенные шаблоны GitLab | Стандартные решения: SAST, DAST, Auto DevOps. |
| **`include:component`** | CI/CD компонент из каталога | Современные версионируемые модули с `spec:inputs`. |

### Синтаксис

#### Краткая форма (только для `local`)
```yaml
include:
  - '.gitlab-ci/build.yml'
  - '.gitlab-ci/test.yml'
```

#### Полная форма
Рекомендуется для повышения читаемости и поддержки расширенных параметров (ref, inputs, rules).
```yaml
include:
  - local: '.gitlab-ci/build.yml'

  - project: 'infrastructure/ci-templates'
    ref: v2.4.0
    file: '/docker/build-kaniko.yml'

  - remote: 'https://example.com/global-defaults.yml'
    integrity: 'sha256-L3/GAoKaw0Arw6hDCKeKQlV1QPEgHYxGBHsH4zG1IY8=' # Проверка целостности (v17.9+)

  - template: 'Security/SAST.gitlab-ci.yml'

  - component: '$CI_SERVER_FQDN/group/component-name@1.2.0'
```

### Детальный разбор типов подключения

#### `include:local`
Подключает файл из того же репозитория. По умолчанию используется та же ветка, в которой запущен пайплайн.
- **Ограничения:** Путь должен быть относительным или начинаться с `/` (от корня). Нельзя использовать Git submodules (они не видны парсеру YAML). Допустимы расширения `.yml` или `.yaml`.

#### `include:project`
Фундамент для корпоративной библиотеки шаблонов.
- **Версионирование (`ref`):**
    - **Тег (SemVer):** Рекомендуется (`ref: v1.2.0`) для стабильности.
    - **Commit SHA:** Максимальная безопасность (защита от перезаписи тега).
    - **Ветка:** Не рекомендуется для production (изменения могут сломать сотни пайплайнов одновременно).

#### `include:remote`
Подключает файлы по публичному URL. 
- **`integrity` (v17.9+):** SHA256-хеш (Base64) для защиты от атак типа Supply Chain (проверка, что файл не подменен).
- **`cache` (v18.9+, эксперимент):** Кэширование удаленного файла на стороне GitLab для ускорения старта пайплайна.

#### `include:template`
Использует встроенную библиотеку GitLab. Полный список шаблонов: [GitLab CI Templates](https://gitlab.com/gitlab-org/gitlab/-/tree/master/lib/gitlab/ci/templates).
*Примечание: В 2026 году рекомендуется постепенно переходить с `template` на `component` для лучшего контроля версий.*

#### `include:component`
Наиболее современный и безопасный способ. Подключает типизированные модули из CI/CD Catalog. Подробнее в [CI/CD Catalog](./ci_cd_catalog_components.md).

## Продвинутые параметры

### Параметризация через `include:inputs` (v16.0+)
Позволяет передавать входные параметры в подключаемый файл, содержащий блок `spec:inputs`. Это обеспечивает строгую типизацию и валидацию конфигурации.

```yaml
include:
  - project: 'shared/templates'
    file: 'build.yml'
    inputs:
      stage: pre-build
      verbose: true
      docker_version: "27.0"
```

### Условное включение через `include:rules`
Позволяет подключать файлы только при выполнении определенных условий (ветка, переменные, наличие файлов).

```yaml
include:
  - local: '.gitlab-ci/deploy-prod.yml'
    rules:
      - if: '$CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH'
  - local: '.gitlab-ci/security-scans.yml'
    rules:
      - exists:
          - docker-compose.yml
```

**Критический нюанс:** Переменные в `include:rules` вычисляются в момент **создания** пайплайна. Переменные, передаваемые через `dotenv` артефакты от предыдущих заданий, здесь **недоступны**, так как слияние YAML происходит до запуска любого задания.

## Практические сценарии

### Сценарий 1: Модульная конфигурация проекта (Domain-driven CI)
Разделение ответственности между командами:
```yaml
include:
  - local: '.gitlab-ci/security.yml' # Настройки безопасности (Security Team)
  - local: '.gitlab-ci/tests.yml'    # Описание тестов (QA Team)
  - local: '.gitlab-ci/deploy.yml'   # Логика деплоя (DevOps Team)
```

### Сценарий 2: Централизация стандартов (SSoT) и миграция на Kaniko
Все проекты компании используют единый стандарт сборки Docker-образов через `include:project`. При обновлении стандарта (например, переход с Docker-in-Docker на Kaniko для безопасности) изменения вносятся один раз в центральном репозитории `shared-infrastructure`, и все проекты получают обновление автоматически (если они не зафиксированы на SHA).

### Сценарий 3: Использование динамических входов (Inputs)
Создание универсального шаблона деплоя, который адаптируется под тип приложения (Frontend/Backend) через параметры `inputs`.

## Валидация и отладка

Для эффективной работы с `include` необходимо проверять итоговый результат слияния:

1.  **Web UI (Merged YAML):** В `CI/CD -> Editor` перейдите на вкладку **"View merged YAML"**. Это единственный способ увидеть пайплайн так, как его видит GitLab Runner.
2.  **GitLab CLI (`glab`):**
    ```bash
    # Просмотр финального развернутого YAML в терминале
    glab ci lint --show-expanded
    ```
3.  **Dry Run через API:** Эндпоинт `/api/v4/projects/:id/ci/lint` с параметром `include_merged_yaml=true`.

## Устранение неполадок

### Системные ограничения и лимиты

| Ограничение | Значение | Описание |
| :--- | :--- | :--- |
| **Максимум файлов** | **150** | Общее кол-во файлов (включая рекурсию) |
| **Таймаут загрузки** | **30 секунд** | Лимит на каждый внешний запрос (`remote`/`project`) |
| **Глубина вложенности** | Не ограничена явно | Рекомендуется до 3-5 уровней для удобства отладки |
| **Размер YAML** | **5 МБ** | Лимит на итоговый смерженный файл |

### Сводная таблица ошибок

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `file does not exist` | Неверный путь или файл отсутствует в `ref` | Проверьте опечатки, наличие файла в целевой ветке/теге. |
| `exceeded max includes` | Циклические или слишком глубокие `include` | Устраните кольцевые ссылки (A -> B -> A). |
| `include timeout` | Внешний URL недоступен или тормозит | Проверьте сеть или используйте локальные копии шаблонов. |
| `rules condition failed` | Ошибка в синтаксисе `if` или отсутствие переменной | Проверьте доступность переменных на этапе компиляции. |
