# GitLab CI: Механизм `extends`

## Определения

**`extends`** — ключевое слово GitLab CI, предназначенное для наследования конфигурации от одного или нескольких "скрытых" заданий. Этот механизм является фундаментом для реализации принципа DRY (Don't Repeat Yourself) в пайплайнах, позволяя создавать модульные, расширяемые и легко сопровождаемые конфигурации.

**Скрытое задание (Hidden Job)** — задание, имя которого начинается с точки (например, `.base_job`). Такие задания игнорируются планировщиком GitLab и не запускаются в пайплайне напрямую. Они выполняют роль абстрактных классов или шаблонов, предоставляя структуру и параметры для реальных рабочих задач через механизм наследования.

## Основные концепции

### Архитектура и жизненный цикл разрешения

Механизм `extends` работает на этапе компиляции пайплайна (Pipeline Compilation). Для понимания итогового поведения важно знать последовательность обработки директив:

1.  **Разрешение `include`**: Собирается полный YAML-документ из всех локальных и внешних источников.
2.  **Интерполяция `inputs`**: В подключаемых шаблонах подставляются значения параметров.
3.  **Обработка `variables`**: Разрешаются статические переменные (динамические переменные окружения разрешаются только в Runner).
4.  **Применение `extends`**: Выполняется слияние структур заданий.
5.  **Разрешение `!reference`**: Финальная вставка фрагментов кода (например, частей скриптов).

### Механизм обратного глубокого слияния (Reverse Deep Merge)

GitLab применяет алгоритм, при котором дочернее задание (содержащее `extends`) имеет абсолютный приоритет над родительским шаблоном.

#### Поведение для различных типов данных

| Тип ключа | Поведение | Технические нюансы |
| :--- | :--- | :--- |
| **`variables`** | **Глубокое слияние** | Словари объединяются. При совпадении имен переменных значение из дочернего задания перезаписывает родительское. |
| **`script`, `before_script`, `after_script`** | **Перезапись (Overwrite)** | Массив строк полностью заменяется. Слияние (конкатенация) списков команд не происходит. |
| **`rules`** | **Перезапись (Overwrite)** | Список условий в дочернем задании полностью заменяет родительский список. |
| **`tags`** | **Перезапись (Overwrite)** | Дочерний список тегов (селекторов Runner) заменяет родительский целиком. |
| **`artifacts`, `cache`** | **Перезапись (Overwrite)** | Перезаписывается весь объект. Если в дочернем задании переопределен только `paths`, то родительские `expire_in` или `policy` будут утеряны. |
| **`image`, `services`, `stage`** | **Перезапись (Overwrite)** | Прямая замена значения скаляра или списка сервисов. |
| **`allow_failure`, `when`, `timeout`, `retry`** | **Перезапись (Overwrite)** | Прямая замена значения. |

> **Важно:** Поскольку массивы `script` не сливаются, для дополнения логики родителя (а не её полной замены) необходимо использовать механизм [**`!reference`**](./reference_and_yaml_anchors.md).

### Множественное наследование

`extends` поддерживает наследование от списка родительских заданий:

```yaml
extends: [.parent_a, .parent_b, .parent_c]
```

**Алгоритм слияния:** справа налево. 
1. Сначала `.parent_b` сливается с `.parent_a` (приоритет у B).
2. Результат сливается с `.parent_c` (приоритет у C).
3. Итоговая структура сливается с самим дочерним заданием (приоритет у дочернего задания).

### Взаимодействие с другими директивами

- **`needs` (DAG):** `extends` не наследует зависимости `needs` автоматически. Каждое задание должно определять свои `needs` самостоятельно, либо наследовать их через `extends` как часть структуры.
- **`default` (Глобальные настройки):** Значения из `extends` имеют приоритет над глобальными настройками `default`.
- **`id_tokens` (v17.x+):** Рекомендуется выносить конфигурацию OIDC/JWT аутентификации в базовые шаблоны (`.auth_base`), чтобы проекты могли безопасно подключаться к облачным ресурсам через `extends`.

### Сравнение с другими механизмами переиспользования

| Характеристика | `extends` | `!reference` | `inputs` | YAML Anchors (`&`) |
| :--- | :--- | :--- | :--- | :--- |
| **Объект воздействия** | Задание целиком | Любой блок | Параметризованный файл | Блок в одном файле |
| **Межфайловость** | Да (через `include`) | Да | Да | Нет |
| **Тип слияния** | Reverse deep merge | Инъекция кода | Интерполяция | Shallow merge (`<<`) |
| **Гибкость** | Высокая | Максимальная | Максимальная | Низкая |

## Практические сценарии

### Предварительные условия

Для успешного применения сценариев необходимо:
- GitLab версии 11.3+ (для базового `extends`) или 16.0+ (для комбинации с `inputs`).
- Настроенный GitLab Runner с соответствующими тегами.
- Доступ к репозиториям с общими шаблонами (права Developer+).

### Сценарий 1: Шаблонизация по окружениям (Environment Scoping)

Использование двоеточия в именах заданий позволяет визуально группировать реализации одного шаблона в интерфейсе GitLab.

```yaml
.build_template:
  stage: build
  image: docker:27.0
  variables:
    ENV: "undefined"
  script:
    - echo "Building for $ENV"
    - docker build --build-arg TARGET_ENV=$ENV -t $CI_REGISTRY_IMAGE:$ENV .

build:dev:
  extends: .build_template
  variables:
    ENV: "dev"

build:prod:
  extends: .build_template
  variables:
    ENV: "prod"
```

### Сценарий 2: Комбинация `include` и `extends` (Enterprise Standard)

Основной паттерн для централизованного управления стандартами CI/CD во всей организации.

**Централизованный файл (`templates/docker.yml` в проекте `shared/ci-templates`):**
```yaml
.docker_base:
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_NAME .
    - docker push $IMAGE_NAME
```

**Рабочий пайплайн проекта (`.gitlab-ci.yml`):**
```yaml
include:
  - project: 'shared/ci-templates'
    file: 'templates/docker.yml'
    ref: 'v2.1.0' # Использование тегов для стабильности

build_app:
  extends: .docker_base
  variables:
    IMAGE_NAME: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

### Сценарий 3: Ловушка переопределения объектов (Artifacts/Cache)

При наследовании важно помнить, что блоки объектов переопределяются целиком.

```yaml
.base_test:
  script: npm test
  artifacts:
    paths:
      - coverage/
    expire_in: 1 week

special_test:
  extends: .base_test
  artifacts:
    paths:
      - custom-reports/
  # ОШИБКА: expire_in будет ПОТЕРЯН, так как блок artifacts в дочернем задании
  # полностью заменил родительский блок.
```

**Правильный подход (Relocation):** Если требуется дополнить пути, используйте `!reference` для вставки родительских путей в дочерний массив.

### Сценарий 4: Многоуровневое наследование (Hierarchy)

Создание иерархии "База -> Технология -> Сценарий".

```yaml
.base_config:
  tags: [docker]
  interruptible: true

.python_base:
  extends: .base_config
  image: python:3.11
  before_script:
    - pip install pytest

test_unit:
  extends: .python_base
  script: pytest tests/unit
```

## Валидация и отладка

### Использование GitLab CLI (`glab`)

Для проверки итогового вида пайплайна после всех `extends` и `include` используйте:

```bash
# Просмотр полной (развернутой) конфигурации
glab ci lint --show-expanded

# Проверка синтаксиса текущего файла
glab ci lint

# Проверка пайплайна с учетом переменных
glab ci lint --dry-run --variable CI_PIPELINE_SOURCE=push
```

### Инструменты Web UI

1. **Pipeline Editor**: Вкладка "View merged YAML" — самый надежный способ увидеть финальную структуру.
2. **CI Lint**: Встроенный валидатор в разделе CI/CD.

## Устранение неполадок

### Сводная таблица типичных ошибок

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `circular reference detected` | Кольцевое наследование (`A extends B, B extends A`) | Разорвите цепочку `extends` или используйте `!reference`. |
| `exceeded max levels` | Глубина наследования > 11 уровней | Упростите иерархию, объединив часть шаблонов. |
| `unknown extends` | Родительский шаблон не найден в текущем контексте | Проверьте опечатки или наличие `include` с нужным файлом. |
| `script: can't be blank` | Переопределение `script` пустым значением или его отсутствие в родителе | Если переопределяете `script`, обязательно укажите хотя бы одну команду. |
| Исчезновение параметров кэша/артефактов | Поверхностная перезапись блоков объектов | Проверьте, не перезаписан ли весь блок `artifacts` или `cache` в дочернем задании. |

## Особенности и ограничения

1. **Лимит уровней**: До 11 уровней наследования. Рекомендуется не более 3 уровней для обеспечения читаемости.
2. **Область видимости**: Задания видны только после слияния всех `include`. Вы не можете наследоваться от задания, которое было исключено правилами `rules` в родительском файле.
3. **Отсутствие конкатенации**: `extends` никогда не соединяет строки скриптов или списки тегов. Только замена.
