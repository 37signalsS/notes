# GitLab CI: Механизм `extends`

## Определения

**`extends`** — ключевое слово GitLab CI, предназначенное для наследования конфигурации от одного или нескольких «скрытых» заданий. Этот механизм является фундаментом для реализации принципа DRY (Don't Repeat Yourself) в пайплайнах, позволяя создавать модульные, расширяемые и легко сопровождаемые конфигурации. Работает на этапе компиляции пайплайна (Stage 3 зрелости CI/CD).

**Скрытое задание (Hidden Job)** — задание, имя которого начинается с точки (например, `.base_job`). Такие задания игнорируются планировщиком GitLab и не запускаются в пайплайне напрямую. Они выполняют роль абстрактных классов или шаблонов, предоставляя структуру и параметры для реальных рабочих задач через механизм наследования. Внутри шаблонов-библиотек рекомендуется использовать префикс, соответствующий назначению (`.build-`, `.test-`, `.deploy-`), для визуальной группировки.

**Обратное глубокое слияние (Reverse Deep Merge)** — алгоритм объединения конфигураций GitLab CI, при котором дочернее задание (содержащее `extends`) имеет абсолютный приоритет над родительским шаблоном. Скаляры и хеши объединяются, а массивы (`script`, `rules`, `tags`) **полностью замещаются** — это принципиальное отличие от большинства систем слияния.

**Контекст этапа:** Третий уровень зрелости CI/CD. Переход от простой централизации ([этап include](./evolution/evolution_include.md)) к созданию гибких библиотек, где общая логика хранится в центре, а проекты-потребители могут адаптировать её под свои специфические нужды без модификации исходного шаблона.

> [!WARNING]
> **Лимиты и лучшие практики:**
> - GitLab ограничивает глубину наследования `extends` до **11 уровней**. Рекомендуется не более **3 уровней** для обеспечения читаемости и сопровождаемости.
> - При нарушении лимита пайплайн не компилируется с ошибкой `exceeded max levels of inheritance`.
> - Избегайте «глубоких» иерархий (База → Язык → Фреймворк → Сервис → Окружение). Предпочитайте «плоские» структуры с комбинированием через `extends: [.base, .specific]`.
> - Массивы `script`, `before_script`, `after_script` **не дополняются, а полностью заменяются**. Для конкатенации используйте `!reference`.
> - YAML Anchors (`&`/`*`) **не работают между файлами**. При выносе кода в шаблоны всегда заменяйте их на `!reference`.
> - GitLab 18.x/19.x считает устаревшими глобальные `before_script`, `image`, `cache` на верхнем уровне YAML — рекомендуется блок `default`.

## Основные концепции

### Архитектура и жизненный цикл разрешения

Механизм `extends` работает на этапе компиляции пайплайна (Pipeline Compilation). Для понимания итогового поведения важно знать последовательность обработки директив:

1.  **Разрешение `include`**: Собирается полный YAML-документ из всех локальных и внешних источников.
2.  **Интерполяция `inputs`**: В подключаемых шаблонах подставляются значения параметров.
3.  **Обработка `variables`**: Разрешаются статические переменные (динамические переменные окружения разрешаются только в Runner).
4.  **Применение `extends`**: Выполняется слияние структур заданий.
5.  **Разрешение `!reference`**: Финальная вставка фрагментов кода (например, частей скриптов).

> **Важно:** Порядок обработки объясняет, почему:
> - `inputs` нельзя использовать для динамического формирования имен переменных в том же блоке `variables` (шаг 2 до шага 3).
> - `!reference` не может обращаться к переменным, определенным в том же блоке (шаг 5 после шага 4).
> - Локальные задания всегда перезаписывают включенные через `include` (шаг 1).

### Эволюционное преимущество перед YAML-якорями

На ранних этапах развития часто применяются якоря YAML (`&` и `*`). Однако `extends` обладает критическими преимуществами:

| Критерий | `extends` | YAML Anchors (`&`/`*`) | `!reference` |
| :--- | :--- | :--- | :--- |
| **Межфайловое взаимодействие** | **Да** (через `include`) | Нет (только один файл) | **Да** |
| **Читаемость** | Высокая | Средняя | Средняя |
| **Многоуровневость** | До 11 уровней | Ограничена вложенностью | Неограниченная |
| **Ленивое разрешение** | Да (этап компиляции) | Нет (парсер YAML) | Да (этап компиляции) |
| **Валидация Lint** | Полная | Только синтаксис YAML | Полная |
| **Тип слияния** | Reverse deep merge | Shallow merge (`<<`) | Инъекция кода |
| **Рекомендация** | Наследование заданий | Только локальные словари | Точечная вставка фрагментов |

> **Важно:** Якоря YAML (`&`/`*`) не работают между файлами. При выносе кода в шаблоны всегда заменяйте их на `!reference` или `extends`.

### Механизм обратного глубокого слияния (Reverse Deep Merge)

GitLab применяет алгоритм, при котором дочернее задание (содержащее `extends`) имеет абсолютный приоритет над родительским шаблоном.

#### Поведение для различных типов данных

| Тип ключа | Поведение | Технические нюансы |
| :--- | :--- | :--- |
| **`variables`** | **Глубокое слияние** | Словари объединяются. При совпадении имен переменных значение из дочернего задания перезаписывает родительское. |
| **`script`, `before_script`, `after_script`** | **Перезапись (Overwrite)** | Массив строк полностью заменяется. Слияние (конкатенация) списков команд не происходит. |
| **`rules`** | **Перезапись (Overwrite)** | Список условий в дочернем задании полностью заменяет родительский список. |
| **`tags`** | **Перезапись (Overwrite)** | Дочерний список тегов (селекторов Runner) заменяет родительский целиком. |
| **`artifacts`, `cache`** | **Перезапись (Overwrite)** | Перезаписывается весь объект. Если в дочернем задании переопределен только `paths`, то родительские `expire_in` или `policy` будут утеряны. |
| **`image`, `services`, `stage`** | **Перезапись (Overwrite)** | Прямая замена значения скаляра или списка сервисов. |
| **`allow_failure`, `when`, `timeout`, `retry`** | **Перезапись (Overwrite)** | Прямая замена значения. |

> **Важно:** Поскольку массивы `script` не сливаются, для дополнения логики родителя (а не её полной замены) необходимо использовать механизм [**`!reference`**](./reference_and_yaml_anchors.md).

### Обход замены массивов через `!reference`

Механизм `!reference` позволяет «впрыскивать» фрагменты родительского конфига в дочернее задание, решая проблему полной замены массивов:

```yaml
# templates/common.yml
.setup_docker:
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY

# Проект: дополнение скрипта (не замена)
build:
  extends: .docker-build-base
  script:
    - !reference [.setup_docker, script]
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

> Подробнее о синтаксисе и ограничениях `!reference` читайте в [Механизм !reference и YAML Anchors](./reference_and_yaml_anchors.md).

### Множественное наследование и приоритет

Задание может наследоваться от списка шаблонов: `extends: [.base_1, .base_2]`. Слияние происходит **справа налево**: значения из `.base_2` переопределяют `.base_1`, а итоговый результат сливается с самим дочерним заданием (наивысший приоритет у дочернего).

```yaml
# Приоритет: .specific > .language > .infra > дочернее задание
build-app:
  extends: [.infra-base, .language-base, .specific-build]
  variables:
    CUSTOM_VAR: "overridden"  # Абсолютный приоритет
```

### Безопасность и приоритет переменных

При наследовании через `extends` возникают риски, связанные с конфликтами переменных:

1.  **Приоритет источников:** Переменные, заданные в `.gitlab-ci.yml` проекта, **всегда** имеют приоритет над переменными из `extends`. Переменные CI/CD Settings проекта (UI) — выше YAML. Переменные группы/инстанса — выше проектных.
2.  **Глобальные переменные vs `extends`:** Если шаблон использует переменную `DOCKER_HOST`, а проект переопределяет её в `variables`, дочернее значение перезапишет родительское. Это безопасно для намеренного переопределения, но опасно для случайного.
3.  **Секреты в `extends`:** Не храните секреты в скрытых заданиях шаблонов. Используйте `CI_JOB_TOKEN`, `id_tokens` (OIDC) или внешние менеджеры секретов (Vault).
4.  **Pipeline Execution Policies:** При использовании GitLab Premium/Ultimate политики выполнения могут принудительно добавлять задания, которые **нельзя** переопределить через `extends`.

### Взаимодействие с другими директивами

- **`needs` (DAG):** `extends` не наследует зависимости `needs` автоматически. Каждое задание должно определять свои `needs` самостоятельно, либо наследовать их через `extends` как часть структуры.
- **`default` (Глобальные настройки):** Значения из `extends` имеют приоритет над глобальными настройками `default`.
- **`id_tokens` (v17.x+):** Рекомендуется выносить конфигурацию OIDC/JWT аутентификации в базовые шаблоны (`.auth_base`), чтобы проекты могли безопасно подключаться к ресурсам через `extends`.
- **`rules` внутри `include`:** Условное подключение шаблонов (`include:rules`) выполняется **до** обработки `extends`, что позволяет подключать шаблоны динамически.
- **`secrets` (v19.x+):** Конфигурация динамического извлечения секретов из внешних менеджеров не наследуется через `extends` — каждый шаблон должен определять свои `secrets` явно.

### Сравнение с другими механизмами переиспользования

| Характеристика | `extends` | `!reference` | `inputs` | YAML Anchors (`&`) |
| :--- | :--- | :--- | :--- | :--- |
| **Объект воздействия** | Задание целиком | Любой блок | Параметризованный файл | Блок в одном файле |
| **Межфайловость** | Да (через `include`) | Да | Да | Нет |
| **Тип слияния** | Reverse deep merge | Инъекция кода | Интерполяция | Shallow merge (`<<`) |
| **Типизация** | Нет | Нет | Да (`string`, `number`, `boolean`, `array`) | Нет |
| **Валидация** | Синтаксическая | Синтаксическая | Типы + regex + options | Только синтаксис YAML |
| **Рекомендация** | Наследование заданий | Точечная вставка фрагментов | Декларативный интерфейс | Только локальные словари |

## Практические сценарии

### Предварительные условия

Для успешного применения сценариев необходимо:
- GitLab версии 11.3+ (для базового `extends`) или 16.0+ (для комбинации с `inputs`).
- Настроенный GitLab Runner с соответствующими тегами.
- Доступ к репозиториям с общими шаблонами (права Developer+).
- Для версионирования шаблонов — политика использования SemVer-тегов (`ref: vX.Y.Z`).

### Сценарий 1: Базовый шаблон сборки с кастомизацией

Центральная библиотека предоставляет стандарт сборки, а проект дополняет его специфичными переменными.

**Централизованный файл (`templates/docker.yml` в проекте `shared/ci-templates`):**
```yaml
.docker_base:
  image: docker:29.8
  services:
    - docker:29.8-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_NAME .
    - docker push $IMAGE_NAME
```

**Рабочий пайплайн проекта (`.gitlab-ci.yml`):**
```yaml
include:
  - project: 'shared/ci-templates'
    file: 'templates/docker.yml'
    ref: 'v2.1.0' # Использование тегов для стабильности

build_app:
  extends: .docker_base
  variables:
    IMAGE_NAME: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    # Добавление новой переменной к родительским
    APP_VERSION: "v1.2.3"
    # Переопределение существующей
    DOCKER_BUILDKIT: "0"
```

### Сценарий 2: Многоуровневое технологическое наследование (Hierarchy)

Создание иерархии «База → Технология → Сценарий» позволяет разделять ответственность между инфраструктурой и разработкой.

```yaml
# Уровень 1: Инфраструктурный стандарт (управляет SRE/Platform-команда)
.infra-base:
  tags: [docker-runner]
  interruptible: true
  retry:
    max: 2
    when: [runner_system_failure, stuck_or_timeout_failure]

# Уровень 2: Технологический стек (управляет DevOps-командой)
.python_base:
  extends: .infra-base
  image: python:3.11
  before_script:
    - pip install -r requirements.txt
  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths: [.pip/]
    policy: pull-push

# Уровень 3: Конкретная задача проекта (управляет разработчиками)
test_unit:
  extends: .python_base
  script:
    - pytest tests/unit
  artifacts:
    reports:
      junit: reports/junit.xml
    expire_in: 7 days

test_integration:
  extends: .python_base
  script:
    - pytest tests/integration
  services:
    - postgres:16
  variables:
    POSTGRES_DB: test_db
```

**Преимущество:** Инфраструктурная команда управляет `retry` и `tags`, DevOps-команда — `image` и `cache`, разработчики — `script` и `artifacts`.

### Сценарий 3: Шаблонизация по окружениям (Environment Scoping)

Использование двоеточия в именах заданий позволяет визуально группировать реализации одного шаблона. Это стандартный паттерн для централизованного управления деплоем.

```yaml
# ci-templates/deploy.yml
.deploy-base:
  stage: deploy
  image: bitnami/kubectl:latest
  variables:
    ENVIRONMENT: "undefined"
  script:
    - kubectl set image deployment/$APP $APP:$CI_COMMIT_SHA -n $ENVIRONMENT
    - kubectl rollout status deployment/$APP -n $ENVIRONMENT --timeout=300s
  environment:
    name: $ENVIRONMENT

# Проект: вызов по окружениям
deploy:dev:
  extends: .deploy-base
  variables:
    ENVIRONMENT: "dev"
  rules:
    - if: $CI_COMMIT_BRANCH == "develop"

deploy:staging:
  extends: .deploy-base
  variables:
    ENVIRONMENT: "staging"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy:production:
  extends: .deploy-base
  variables:
    ENVIRONMENT: "production"
  rules:
    - if: $CI_COMMIT_TAG
  when: manual
```

### Сценарий 4: Переопределение правил запуска (rules)

Поскольку `rules` — это массив, его переопределение требует полного дублирования логики, если нужно сохранить базовые правила.

```yaml
.base-rules:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

deploy-job:
  extends: .base-rules
  rules:
    # Базовое правило MR будет потеряно, если не указать его здесь явно
    - if: $CI_COMMIT_TAG
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

**Решение через `!reference`:** Для сохранения базовых правил без дублирования используйте `!reference`:

```yaml
.deploy-rules:
  rules:
    - if: $CI_COMMIT_TAG
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

deploy-job:
  rules:
    - !reference [.deploy-rules, rules]
    - if: $CI_PIPELINE_SOURCE == "schedule"
      when: never
```

### Сценарий 5: Комбинация `!reference` и `extends` (гибридный паттерн)

`extends` задает архитектуру задания, а `!reference` впрыскивает специфичную логику, решая проблему замены массивов.

```yaml
# templates/common.yml
.check_licenses:
  script:
    - echo "Проверка лицензий..."
    - trivy fs --scanners license .

.cleanup_workspace:
  after_script:
    - rm -rf .cache
    - echo "Workspace очищен"

# templates/docker-build.yml
.docker-build-base:
  image: docker:29.8
  services:
    - docker:29.8-dind
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

# Проект: расширение шаблона дополнительными шагами
build-app:
  extends: .docker-build-base
  script:
    - !reference [.check_licenses, script]
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  after_script:
    - !reference [.cleanup_workspace, after_script]
```

### Сценарий 6: Ловушка переопределения объектов (Artifacts/Cache)

Частая ошибка: переопределение только части блока `artifacts` или `cache` приводит к потере родительских параметров.

```yaml
.base_test:
  script: npm test
  artifacts:
    paths:
      - coverage/
    expire_in: 1 week

# ОШИБКА: expire_in будет ПОТЕРЯН
special_test:
  extends: .base_test
  artifacts:
    paths:
      - custom-reports/
    # expire_in от родителя ПОТЕРЯН, т.к. весь блок artifacts заменён
```

**Правильный подход:** Используйте `!reference` для вставки родительских значений или дублируйте полный блок:

```yaml
# Правильно: полное дублирование блока
special_test:
  extends: .base_test
  artifacts:
    paths:
      - coverage/
      - custom-reports/
    expire_in: 1 week

# Альтернатива: !reference для частичного дополнения
special_test_v2:
  extends: .base_test
  artifacts:
    paths:
      - !reference [.base_test, artifacts, paths]
      - custom-reports/
    expire_in: 1 week
```

### Сценарий 7: Отладка итоговой конфигурации

Перед коммитом необходимо проверить, как `extends` и `!reference` повлияли на итоговую конфигурацию.

```bash
# Просмотр полной (развернутой) конфигурации
glab ci lint --show-expanded

# Проверка синтаксиса с имитацией переменных
glab ci lint --dry-run --variable CI_PIPELINE_SOURCE=merge_request_event

# Экспорт полного YAML для анализа
glab ci lint --show-expanded > full_pipeline.yml
cat full_pipeline.yml | grep -A5 "test-unit"
```

### Сценарий 8: Enterprise-паттерн «Platform CI»

Для крупных организаций (100+ проектов):

```yaml
# Центральный репозиторий: shared/ci-templates
# Шаблон с !reference для SSH-деплоя
.ssh_deploy_base:
  stage: deploy
  image: alpine:3.19
  before_script:
    - apk add --no-cache openssh-client
  script:
    - ssh -o StrictHostKeyChecking=no $DEPLOY_USER@$DEPLOY_HOST "cd /app && docker pull $IMAGE && docker-compose up -d"

# Проект: включение шаблона с кастомизацией
include:
  - project: 'shared/ci-templates'
    file: '/templates/ssh-deploy.yml'
    ref: 'v3.0.0'

deploy_staging:
  extends: .ssh_deploy_base
  variables:
    DEPLOY_HOST: "staging.internal"
    DEPLOY_USER: "deploy-bot"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy_production:
  extends: .ssh_deploy_base
  variables:
    DEPLOY_HOST: "prod.internal"
    DEPLOY_USER: "deploy-bot"
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
  when: manual
```

## Валидация и отладка

### Инструменты валидации

| Инструмент | Назначение | Команда / Доступ |
| :--- | :--- | :--- |
| **Pipeline Editor** | Визуальный просмотр раскрытого YAML с подсветкой ошибок интерполяции `inputs`. | Web UI → CI/CD → Pipeline Editor → вкладка «View merged YAML» |
| **GitLab CLI (`glab`)** | Локальная проверка синтаксиса и раскрытие `include`/`extends`/`inputs`. | `glab ci lint` / `glab ci lint --show-expanded` |
| **CI Lint API** | Программная проверка через HTTP (для использования в CI-пайплайнах шаблонов). | `POST /api/v4/projects/:id/ci/lint` |
| **Dry Run (v16.11+)** | Глубокая валидация, имитирующая создание пайплайна. Проверяет права, наличие образов, корректность `rules`. | `glab ci lint --dry-run --variable CI_PIPELINE_SOURCE=merge_request_event` |

### Чек-лист валидации

Перед коммитом убедитесь:
- [ ] `glab ci lint` проходит без ошибок.
- [ ] `glab ci lint --show-expanded` показывает корректный раскрытый YAML.
- [ ] Блок `spec:inputs` заполнен и синтаксически верен (для компонентов).
- [ ] Все внутренние ссылки (относительные пути) проверены и работают.
- [ ] Создан релиз с тегом SemVer (для компонентов CI/CD Catalog).

### Отладка в логах

При возникновении ошибок с переменными добавьте команду `export` или `env` в `script`, чтобы увидеть финальные значения, полученные в результате слияния:

```yaml
script:
  - export  # Показать все переменные окружения
  - env | grep -E "^(CI_|DOCKER_)"  # Фильтр по префиксу
  - echo "IMAGE_TAG=$CI_COMMIT_SHORT_SHA"
```

### CI Lint API (программная проверка)

```bash
curl --request POST \
  --header "PRIVATE-TOKEN: $TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"content": "include:\n  - project: shared/ci-templates\n    file: templates/build.yml"}' \
  "https://gitlab.example.com/api/v4/ci/lint?include_merged_yaml=true"
```

## Устранение неполадок

### Сводная таблица типичных ошибок

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `circular reference detected` | Кольцевое наследование (`A extends B, B extends A`). | Разорвите цепочку `extends` или используйте `!reference`. Проверьте всю цепочку через `glab ci lint --show-expanded`. |
| `exceeded max levels` | Глубина наследования `extends` > 11 уровней. | Упростите иерархию шаблонов. Старайтесь не превышать 3–4 уровня вложенности. |
| `unknown extends` | Родительский шаблон не найден в текущем контексте. | Проверьте опечатки или наличие `include` с нужным файлом. Убедитесь, что `include` подключает нужный файл. |
| `script: can't be blank` | Переопределение `script` пустым значением или его отсутствие в родителе. | Если переопределяете `script`, обязательно укажите хотя бы одну команду. |
| Исчезновение параметров кэша/артефактов | Поверхностная перезапись блоков объектов. | Проверьте, не перезаписан ли весь блок `artifacts` или `cache` в дочернем задании. Используйте `!reference` или дублируйте полный блок. |
| Переменные не переопределяются | Переменная задана на уровне CI/CD Settings проекта (UI) или группы. | Учтите приоритет: переменные настроек GitLab выше переменных в YAML. Локальные переменные в `.gitlab-ci.yml` важнее `extends`. |
| `included file not found` | Неверный путь в `include:project` или отсутствие прав у `CI_JOB_TOKEN`. | Проверьте путь от корня репозитория шаблонов и `Visibility` проекта. Убедитесь, что в настройках проекта включён `Token Access`. |
| `Input 'X' must match regex` | При комбинации с `inputs`: переданное значение нарушает правила валидации. | Проверьте входные данные на соответствие регулярному выражению из `spec:inputs`. |
| Изменение шаблона ломает проекты | Родительский шаблон изменил структуру (добавил обязательный ключ или переименовал переменную). | Используйте SemVer для версионирования шаблонов. Закрепляйте версию через `ref: vX.Y.Z` в `include:project`. |

### Логика диагностики

При ошибке с `extends` следуйте алгоритму:
1. **Проверьте итоговый YAML:** `glab ci lint --show-expanded` — видны ли задания после слияния.
2. **Проверьте приоритеты:** Локальные задания всегда важнее включенных через `include`.
3. **Проверьте типы данных:** Массивы заменяются целиком, словари сливаются.
4. **Проверьте версию:** Убедитесь, что `ref` в `include:project` указывает на SemVer-тег, а не на ветку.

## Особенности и ограничения

1. **Лимит уровней**: До 11 уровней наследования. Рекомендуется не более 3 уровней для обеспечения читаемости.
2. **Область видимости**: Задания видны только после слияния всех `include`. Вы не можете наследоваться от задания, которое было исключено правилами `rules` в родительском файле.
3. **Отсутствие конкатенации**: `extends` никогда не соединяет строки скриптов или списки тегов. Только замена. Для конкатенации используйте `!reference`.
4. **Запрет глобальных ключей в компонентах**: Компоненты CI/CD Catalog не могут использовать `stages:`, `default:`, `workflow:` — они навязывают поведение всему проекту.
5. **YAML Anchors не работают между файлами**: При выносе кода в шаблоны всегда заменяйте их на `!reference`.

## Преимущества и недостатки

| Преимущество | Описание |
| :--- | :--- |
| **Масштабируемость** | Позволяет обновлять логику в одном шаблоне для сотен проектов. Централизованное управление стандартами. |
| **Типизация** | Создает четкие стандарты заданий (Build, Test, Deploy) внутри организации. Иерархия шаблонов отражает архитектуру. |
| **Гибкость** | Проекты переопределяют только нужные ключи, сохраняя остальные настройки от центральной команды. |
| **Совместимость** | Работает с любым типом Runner и версией GitLab 11.3+. Интегрируется с `!reference`, `inputs`, `include`. |
| **Изоляция контекста** | Скрытое задание не запускается напрямую — только как шаблон. Риск случайного запуска минимален. |

| Недостаток | Описание | Решение |
| :--- | :--- | :--- |
| **Скрытая сложность** | При глубокой вложенности (>3 уровней) сложно понять итоговый `script` без спецсредств. | Используйте Pipeline Editor / `glab ci lint --show-expanded`. |
| **Хрупкость** | Изменение структуры родительского шаблона может привести к неожиданному поведению. | Используйте SemVer для версионирования шаблонов. |
| **Замена массивов** | Массивы (`script`, `rules`, `tags`) не дополняются, а полностью замещаются. | Для обхода используйте `!reference`. |
| **Лимит вложенности** | Максимум 11 уровней наследования. | Практический лимит — 3–4 уровня. |
