# GitLab CI: Механизм `extends`

## Определения

**`extends`** — ключевое слово GitLab CI для наследования конфигурации от одного или нескольких "скрытых" заданий (начинающихся с точки `.`). Позволяет избегать дублирования кода внутри одного файла `.gitlab-ci.yml` или ресурсов, подключенных через `include`.

**Скрытое задание (Hidden Job)** — задание, имя которого начинается с точки (`.base_job`). Оно не добавляется в пайплайн напрямую планировщиком GitLab, а служит исключительно шаблоном (абстрактным классом) для наследования другими заданиями.

## Основные концепции

### Механизм слияния конфигураций

При использовании `extends` GitLab выполняет **обратное глубокое слияние (reverse deep merge)**. Это означает, что параметры из родительского задания копируются в дочернее, но дочернее задание имеет абсолютный приоритет при совпадении ключей.

#### Поведение для различных типов ключей

| Тип ключа | Поведение | Особенности |
| :--- | :--- | :--- |
| **`variables`** | **Глубокое слияние** | Дочерние значения переопределяют родительские; новые переменные добавляются в итоговый словарь. |
| **`script`, `before_script`, `after_script`** | **Перезапись (Overwrite)** | Дочерний массив строк полностью заменяет родительский. Слияние строк не происходит. |
| **`rules`** | **Перезапись (Overwrite)** | Список условий в дочернем задании полностью заменяет родительский список. |
| **`tags`** | **Перезапись (Overwrite)** | Дочерний список тегов заменяет родительский целиком. |
| **`artifacts`, `cache`** | **Перезапись (Overwrite)** | Перезаписывается весь блок объекта (например, при переопределении `paths` теряется родительский `expire_in`). |
| **`image`, `services`, `stage`** | **Перезапись (Overwrite)** | Прямая замена значения скаляра или списка сервисов. |
| **`allow_failure`, `when`, `timeout`, `retry`** | **Перезапись (Overwrite)** | Прямая замена значения. |

> **Важно:** Скрипты и массивы (rules, tags) **не конкатенируются**. Для переиспользования отдельных фрагментов скрипта без потери родительской логики используйте механизм [`!reference`](./reference_and_yaml_anchors.md).

### Множественное наследование

`extends` поддерживает наследование от списка родительских заданий:

```yaml
extends: [.parent_a, .parent_b, .parent_c]
```

**Порядок слияния:** справа налево. Последнее задание в списке (`.parent_c`) имеет наивысший приоритет и может переопределять значения, заданные в предыдущих шаблонах (`.parent_b` и `.parent_a`).

```yaml
.base_defaults:
  image: alpine:3.20
  tags:
    - docker-runner

.test_rules:
  rules:
    - if: '$CI_PIPELINE_SOURCE == "merge_request_event"'

.custom_vars:
  variables:
    TEST_ENV: staging

my_test_job:
  extends: [.base_defaults, .test_rules, .custom_vars]
  script:
    - echo "Running tests in $TEST_ENV"
```

### Сравнение с другими механизмами

| Характеристика | `extends` | `!reference` | `inputs` |
| :--- | :--- | :--- | :--- |
| **Объект воздействия** | Задание (job) целиком | Любой блок (script, rules) | Параметризованный файл |
| **Тип слияния** | Reverse deep merge | Вставка (инъекция) кода | Интерполяция значений |
| **Гибкость** | Высокая для структур | Максимальная для фрагментов | Максимальная для шаблонов |
| **Валидация** | CI Lint | CI Lint | CI Lint |

## Практические сценарии

### Сценарий 1: Шаблонизация по окружениям

Использование двоеточия в именах заданий позволяет визуально группировать реализации одного шаблона:

```yaml
.build_template:
  stage: build
  image: docker:27.0
  variables:
    ENV: "undefined"
  script:
    - echo "Building for $ENV"
    - docker build --build-arg TARGET_ENV=$ENV -t $CI_REGISTRY_IMAGE:$ENV .

build:dev:
  extends: .build_template
  variables:
    ENV: "dev"

build:prod:
  extends: .build_template
  variables:
    ENV: "prod"
```

### Сценарий 2: Комбинация `include` и `extends`

Основной паттерн для корпоративных стандартов CI/CD.

**Централизованный файл (`templates/docker.yml`):**
```yaml
.docker_base:
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_NAME .
    - docker push $IMAGE_NAME
```

**Рабочий пайплайн проекта (`.gitlab-ci.yml`):**
```yaml
include:
  - project: 'shared/ci-templates'
    file: 'templates/docker.yml'
    ref: 'v2.1.0'

build_app:
  extends: .docker_base
  variables:
    IMAGE_NAME: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

### Сценарий 3: Переопределение сложных блоков (Ловушка с `artifacts`)

При наследовании важно помнить, что блоки объектов переопределяются целиком, а не сливаются по полям.

```yaml
.base_test:
  script: npm test
  artifacts:
    paths:
      - coverage/
    expire_in: 1 week

special_test:
  extends: .base_test
  artifacts:
    paths:
      - custom-reports/
  # ВНИМАНИЕ: expire_in будет ПОТЕРЯН, так как блок artifacts в дочернем задании
  # полностью заменил родительский блок.
```

## Дополнительная информация

### Взаимодействие с `inputs` (GitLab 16+)

Механизм `extends` выполняется **после** интерполяции `inputs`. Это позволяет создавать динамические цепочки наследования. Однако, вы не можете передать `inputs` напрямую в родительское задание через `extends`; `inputs` работают только на уровне `include`.

### Ограничения

1. **Глубина наследования:** До 11 уровней (согласно лимитам GitLab). Рекомендуется не более 3 уровней для обеспечения сопровождаемости.
2. **Область видимости:** `extends` работает только с заданиями, доступными в текущем скомпилированном контексте (после выполнения всех `include`).
3. **Запрет на циклы:** Круговое наследование (`A extends B`, `B extends A`) вызывает фатальную ошибку конфигурации.

### Валидация через CLI

Для проверки итогового вида пайплайна после всех `extends` и `include` используйте GitLab CLI (`glab`):

```bash
# Просмотр полной (развернутой) конфигурации
glab ci lint --show-expanded

# Проверка синтаксиса текущего файла
glab ci lint

# Проверка пайплайна в конкретном проекте
glab ci lint --project group/my-project
```

### Сводная таблица типичных ошибок

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `circular reference detected` | Кольцевое наследование | Разорвите цепочку `extends` или используйте `!reference`. |
| `exceeded max levels` | Глубина > 11 уровней | Упростите иерархию, объединив часть шаблонов. |
| `unknown extends` | Родительский шаблон не найден | Проверьте опечатки или наличие `include` с нужным файлом. |
| `script: can't be blank` | Переопределение `script` пустым значением | Если переопределяете `script`, обязательно укажите хотя бы одну команду. |
