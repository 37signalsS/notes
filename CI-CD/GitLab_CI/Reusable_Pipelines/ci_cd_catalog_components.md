# GitLab CI: Каталог компонентов

## Определения

**Каталог компонентов (CI/CD Catalog)** — современный подход GitLab к управлению переиспользуемыми конфигурациями, позволяющий создавать версионируемые, типизированные и изолированные блоки логики. Компоненты позволяют организовать "библиотеку инструментов" для всей компании, скрывая сложность реализации за четко определенным интерфейсом.

**Компонент** — автономный блок конфигурации (YAML-файл в директории `templates/`), содержащий метаданные входных параметров и описание заданий.

**`spec:inputs`** — декларативное описание "публичного интерфейса" компонента. Определяет ожидаемые параметры, их типы данных (`string`, `number`, `boolean`, `array`), значения по умолчанию и правила валидации.

**Интерполяция** — механизм подстановки переданных значений параметров в конфигурацию через синтаксис `$[[ inputs.<name> ]]`. 
> **Важно:** Интерполяция происходит на этапе компиляции пайплайна **до** разрешения ключевых слов `variables` и `extends`. Это гарантирует, что значения входов будут доступны во всех частях конфигурации.

## Основные концепции

### Сравнение компонентов и механизма `include`

Компоненты являются эволюцией традиционного подхода `include:project`, предлагая строгую структуру и расширенный контроль.

| Критерий | `include:project` | CI/CD Catalog (Components) |
| :--- | :--- | :--- |
| **Версионирование** | Теги, ветки, SHA | **SemVer** (обязательно для публикации) |
| **Типизация** | Нет (только строки) | **Да** (`spec:inputs` с проверкой типов) |
| **Валидация** | Только синтаксис YAML | **Полная** (проверка контракта входов) |
| **Документация** | Ручная (README.md) | **Автоматическая** (генерация из спецификации) |
| **Изоляция** | Средняя | **Высокая** (изолированные области видимости) |

### Архитектура компонента

Для обеспечения корректной работы каталога и возможности публикации, репозиторий должен следовать стандартной структуре:

```text
component-repo/
├── templates/
│   ├── build.yml          # Файл компонента (содержит spec: и ---)
│   └── deploy.yml         # Дополнительный компонент в том же проекте
├── README.md              # Документация, отображаемая в UI каталога
└── .gitlab-ci.yml         # Пайплайн для тестирования самого компонента
```

### Синтаксис `spec:inputs`

Директива `spec:inputs` позволяет задавать типы данных, значения по умолчанию и правила валидации.

```yaml
spec:
  inputs:
    stage:
      default: test
      type: string
      description: "Стадия пайплайна, на которой запускается задание"
    environment:
      type: string
      default: dev
      options: [dev, staging, prod] # Ограничение выбора (UI dropdown)
    parallel_limit:
      type: number
      default: 1
    enable_feature:
      type: boolean
      default: false
    allowed_regions:
      type: array
      default: ["us-east-1", "eu-central-1"] # Поддержка массивов (v17.5+)
    version_tag:
      type: string
      regex: '^v\d+\.\d+\.\d+$' # Валидация через регулярные выражения
---
# Конец секции спецификации, далее следует логика YAML
```

**Особенности:**
- **Тип `array`**: Позволяет передавать списки значений для итерации или использования в `tags`.
- **`description`**: Текст отображается в интерфейсе каталога как документация к параметру.
- **`options`**: Превращает текстовое поле в выпадающий список при ручном запуске пайплайна.
- Параметры без `default` являются **обязательными**; пайплайн не запустится, если они не переданы.
- Входы могут ссылаться на другие входы (интерполяция внутри блока `spec`, v17.7+).

### Механизм интерполяции и контекст

Помимо входов от пользователя, компоненты имеют доступ к собственным метаданным через **Интерполяцию контекста (v18.6+)**:

| Переменная | Описание |
| :--- | :--- |
| `$[[ inputs.<name> ]]` | Значение, переданное пользователем. |
| `$[[ component.name ]]` | Имя текущего компонента. |
| `$[[ component.version ]]` | Версия (тег или SHA), указанная при вызове. |
| `$[[ component.sha ]]` | Полный Commit SHA версии компонента. |

## Практические сценарии

### Сценарий 1: Подключение компонента из официального каталога

Использование стандартных инструментов (например, Secret Detection) с фиксированной версией.

```yaml
include:
  - component: '$CI_SERVER_FQDN/group/security/secret-detection@1.0.0'
    inputs:
      stage: security
      scan_path: './src'
```

### Сценарий 2: Создание собственного Docker-компонента

Универсальный шаблон для сборки образов с использованием современных практик.

**Файл `templates/build.yml`:**
```yaml
spec:
  inputs:
    stage:
      default: build
    dockerfile:
      default: Dockerfile
---
build_image:
  stage: $[[ inputs.stage ]]
  image: docker:27.0
  services:
    - docker:27.0-dind
  script:
    - docker build -f $[[ inputs.dockerfile ]] -t $CI_REGISTRY_IMAGE:$[[ component.version ]] .
```

### Сценарий 3: Компонент для полного жизненного цикла (Multi-job)

Компоненты могут содержать связанные цепочки заданий, объединенных общей логикой.

```yaml
# templates/nodejs-pipeline.yml
spec:
  inputs:
    node_version:
      default: "22"
---
install:
  stage: .pre
  image: node:$[[ inputs.node_version ]]
  script:
    - npm ci

test:
  stage: test
  image: node:$[[ inputs.node_version ]]
  script:
    - npm test
  needs: [install]
```

### Сценарий 4: Управление стратегией обновлений

Выбор между стабильностью и автоматическим получением исправлений через SemVer.

```yaml
include:
  # 1. Фиксированная версия (рекомендуется для критических систем)
  - component: '$CI_SERVER_FQDN/group/component@1.2.5'

  # 2. Мажорная версия (автоматическое получение patch и minor обновлений)
  - component: '$CI_SERVER_FQDN/group/component@1'

  # 3. Указатель на последний релиз (требует наличия созданного Release)
  - component: '$CI_SERVER_FQDN/group/component@~latest'
```

### Сценарий 5: Валидация входных данных через regex

Использование регулярных выражений предотвращает передачу некорректных данных (например, инъекций в скрипты).

```yaml
spec:
  inputs:
    replicas:
      type: number
      regex: '^[1-5]$' # Ограничение от 1 до 5 реплик
---
deploy:
  script:
    - echo "Deploying $[[ inputs.replicas ]] instances"
```

### Сценарий 6: Вложенные компоненты (Nested Components)

Компоненты могут вызывать другие компоненты. **Критически важно:** входы родительского компонента не пробрасываются "вниз" автоматически, их нужно передавать явно.

```yaml
spec:
  inputs:
    image_tag:
      default: latest
---
include:
  - component: $[[ component.name ]]/security-scanners@$[[ component.version ]]
    inputs:
      severity_level: high

build_job:
  image: custom-builder:$[[ inputs.image_tag ]]
  script:
    - build.sh
```

## Дополнительная информация

- **Версионирование**: Для публикации в каталоге обязательно использование SemVer. Проект должен быть помечен как "Catalog resource" (`Settings -> General -> Visibility`).
- **Будущее (GitLab Steps)**: Начиная с GitLab 19.0, вводится механизм **GitLab Steps**. Это следующий этап эволюции (Stage 6), позволяющий переиспользовать конкретные шаги внутри задания с полной контейнерной изоляцией, заменяя громоздкие Bash-скрипты.
