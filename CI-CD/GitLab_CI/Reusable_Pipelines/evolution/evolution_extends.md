# Гибкость шаблонов через механизм extends

**Актуально для:** GitLab CI 19.x; Docker 29.x (DinD); Kubernetes 1.37.x.

## Определения

**`extends`** — директива GitLab CI для реализации наследования конфигурации. Она позволяет заданию (job) заимствовать параметры из другого задания (обычно «скрытого»), обеспечивая переиспользование кода без нарушения принципа DRY (Don't Repeat Yourself). Механизм работает на этапе компиляции пайплайна и выполняет обратное глубокое слияние (reverse deep merge), где дочернее задание имеет абсолютный приоритет над родительским шаблоном.

**Скрытое задание (Hidden Job)** — задание, имя которого начинается с точки (например, `.base-template`). Такие задания игнорируются планировщиком GitLab и не запускаются в пайплайне напрямую, служа исключительно фундаментом для других задач. Внутри шаблонов-библиотек рекомендуется использовать префикс, соответствующий назначению (`.build-`, `.test-`, `.deploy-`), для визуальной группировки.

**Обратное глубокое слияние (Reverse Deep Merge)** — алгоритм объединения конфигураций GitLab CI, при котором дочернее задание (содержащее `extends`) имеет абсолютный приоритет над родительским. Скаляры и хеши объединяются, а массивы (`script`, `rules`, `tags`) **полностью замещаются** — это принципиальное отличие от большинства систем слияния.

**Контекст этапа:** Третий уровень зрелости CI/CD. Переход от простой централизации ([этап include](./evolution_include.md)) к созданию гибких библиотек, где общая логика хранится в центре, а проекты-потребители могут адаптировать её под свои специфические нужды без модификации исходного шаблона.

> [!WARNING]
> **Лимиты и лучшие практики:**
> - GitLab ограничивает глубину наследования `extends` до **11 уровней**. Рекомендуется не более **3 уровней** для обеспечения читаемости и сопровождаемости.
> - При нарушении лимита пайплайн не компилируется с ошибкой `exceeded max levels of inheritance`.
> - Избегайте «глубоких» иерархий (База → Язык → Фреймворк → Сервис → Окружение). Предпочитайте «плоские» структуры с комбинированием через `extends: [.base, .specific]`.
> - Глобальные `image`, `services`, `cache`, `before_script`, `after_script` на верхнем уровне YAML объявлены устаревшими (GitLab 18.x, удаление планируется в 19.0+). В шаблонах задавайте их через блок `default:`.

## Эволюционное преимущество перед предыдущим этапом

На этапе [include](./evolution_include.md) проекты получили возможность подключать централизованные шаблоны. Однако `include` сам по себе не предоставляет кастомизации — подключённый шаблон остаётся «монолитным»: проект не может изменить стадию, образ или набор команд без дублирования всего YAML. `extends` решает эту проблему, добавляя слой наследования.

| Характеристика | Этап 2 (Include) | Этап 3 (Extends) |
| :--- | :--- | :--- |
| **Кастомизация** | Невозможна без правки шаблона | Проект переопределяет нужные ключи |
| **Многоуровневость** | Только прямое подключение | Цепочки наследования (до 11 уровней) |
| **DRY-индекс** | Средний (шаблон один, но монолитный) | Высокий (общая база + локальная адаптация) |
| **Риск коллизий** | Низкий (файл изолирован) | Средний (глобальные переменные могут конфликтовать) |
| **Сложность отладки** | Минимальная (виден исходный файл) | Средняя (требуется Pipeline Editor / `glab ci lint`) |

**Ключевой переход:** от «подключай и используй как есть» к «подключай и адаптируй под себя». Каждый проект получает возможность изменять только те аспекты конфигурации, которые специфичны для него, сохраняя остальные настройки от центральной команды.

## Базовые концепции

### Эволюционное преимущество перед YAML-якорями

На ранних этапах развития часто применяются якоря YAML (`&` и `*`). Однако `extends` обладает критическими преимуществами:
1.  **Межфайловое взаимодействие:** Якоря работают только в пределах одного файла. `extends` позволяет наследовать логику из файлов, подключенных через `include`.
2.  **Читаемость:** Синтаксис `extends` более прозрачен и лучше поддерживается инструментами статического анализа GitLab.
3.  **Многоуровневость:** `extends` поддерживает цепочки наследования (до 11 уровней), в то время как глубокая вложенность якорей быстро становится неуправляемой.
4.  **Ленивое разрешение:** `extends` обрабатывается на этапе компиляции пайплайна, что позволяет безопасно ссылаться на задания из любых подключённых через `include` файлов.

> **Важно:** Якоря YAML (`&`/`*`) не работают между файлами. При выносе кода в шаблоны всегда заменяйте их на `!reference` или `extends`.

### Правила слияния данных: глубокое погружение

Понимание того, как GitLab объединяет ключи, критично для избежания ошибок «исчезнувших скриптов». Алгоритм **reverse deep merge** работает следующим образом:

| Тип ключа | Поведение при слиянии | Технические нюансы |
| :--- | :--- | :--- |
| **`variables`** | **Глубокое слияние** | Словари объединяются. Совпадающие ключи перезаписываются дочерними значениями. |
| **`script`, `before_script`, `after_script`** | **Полная замена** | Массив строк не дополняется, а **полностью заменяется**. Если в родителе 10 строк, а в дочернем — 1, итоговое задание будет содержать только 1 строку. |
| **`rules`** | **Полная замена** | Список условий полностью заменяется. Дочернее задание должно явно продублировать базовые правила, если они должны сохраниться. |
| **`tags`** | **Полная замена** | Дочерний список тегов (селекторов Runner) заменяет родительский целиком. |
| **`artifacts`, `cache`** | **Полная замена** | Перезаписывается весь объект. Если в дочернем задании переопределён только `paths`, то родительские `expire_in` и `policy` будут утеряны. |
| **`image`, `services`, `stage`** | **Полная замена** | Прямая замена значения скаляра или списка сервисов. |
| **`allow_failure`, `when`, `timeout`, `retry`** | **Полная замена** | Прямая замена значения. |

> **Критическое замечание:** Поскольку массивы `script` не сливаются, для дополнения логики родителя (а не её полной замены) необходимо использовать механизм [`!reference`](../reference_and_yaml_anchors.md).

### Обход замены массивов через `!reference`

Механизм `!reference` позволяет «впрыскивать» фрагменты родительского конфига в дочернее задание, решая проблему полной замены массивов:

```yaml
# templates/common.yml
.setup_docker:
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY

# Проект: дополнение скрипта (не замена)
build:
  extends: .docker-build-base
  script:
    - !reference [.setup_docker, script]
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

> Подробнее о синтаксисе и ограничениях `!reference` читайте в [Механизм !reference и YAML Anchors](../reference_and_yaml_anchors.md).

### Множественное наследование и приоритет

Задание может наследоваться от списка шаблонов: `extends: [.base_1, .base_2]`. Слияние происходит **справа налево**: значения из `.base_2` переопределяют `.base_1`, а итоговый результат сливается с самим дочерним заданием (наивысший приоритет у дочернего).

```yaml
# Приоритет: .specific > .language > .infra > дочернее задание
build-app:
  extends: [.infra-base, .language-base, .specific-build]
  variables:
    CUSTOM_VAR: "overridden"  # Абсолютный приоритет
```

**Порядок обработки директив GitLab CI:**
1. Разрешение `include` (сборка полного YAML)
2. Интерполяция `inputs` (подстановка параметров)
3. Обработка `variables` (статические переменные)
4. Применение `extends` (слияние структур заданий)
5. Разрешение `!reference` (вставка фрагментов кода)

### Безопасность и приоритет переменных

При наследовании через `extends` возникают риски, связанные с конфликтами переменных:

1.  **Приоритет источников:** Переменные, заданные в `.gitlab-ci.yml` проекта, **всегда** имеют приоритет над переменными из `extends`. Переменные CI/CD Settings проекта (UI) — выше YAML. Переменные группы/инстанса — выше проектных.
2.  **Глобальные переменные vs `extends`:** Если шаблон использует переменную `DOCKER_HOST`, а проект переопределяет её в `variables`, дочернее значение перезапишет родительское. Это безопасно для намеренного переопределения, но опасно для случайного.
3.  **Секреты в `extends`:** Не храните секреты в скрытых заданиях шаблонов. Используйте `CI_JOB_TOKEN`, `id_tokens` (OIDC) или внешние менеджеры секретов (Vault).
4.  **Pipeline Execution Policies:** При использовании GitLab Premium/Ultimate политики выполнения могут принудительно добавлять задания, которые **нельзя** переопределить через `extends`.

### Взаимодействие с другими директивами

- **`needs` (DAG):** `extends` не наследует зависимости `needs` автоматически. Каждое задание должно определять свои `needs` самостоятельно, либо наследовать их через `extends` как часть структуры.
- **`default` (Глобальные настройки):** Значения из `extends` имеют приоритет над глобальными настройками `default`. Начиная с GitLab 18.x глобальные `image`, `services`, `cache`, `before_script`, `after_script` на верхнем уровне YAML считаются устаревшими — выносите их в блок `default:`, чтобы шаблоны не ломались при будущем удалении.
- **`id_tokens` (OIDC):** Синтаксис доступен с GitLab 15.7, а с 16.4 блок `id_tokens` можно задавать глобально в `default:` — тогда он применяется ко всем заданиям и наследуется через `extends`. Устаревшие переменные `CI_JOB_JWT`/`CI_JOB_JWT_V2` удалены в 17.0 — используйте только `id_tokens`. Рекомендуется выносить конфигурацию OIDC/JWT аутентификации в базовые шаблоны (`.auth_base`), чтобы проекты могли безопасно подключаться к ресурсам через `extends`.
- **`secrets` (Vault / Secrets Manager):** Динамическое извлечение секретов через ключ `secrets` (Vault — давняя поддержка; native GitLab Secrets Manager, ключ `gitlab_secrets_manager`, — public beta с GitLab 19.0). Работа полагается на корректно настроенные `id_tokens`; при наследовании через `extends` проверяйте итоговую конфигурацию `glab ci lint --show-expanded` и объявляйте секреты там, где они действительно нужны.
- **`rules` внутри `include`:** Условное подключение шаблонов (`include:rules`) выполняется **до** обработки `extends`, что позволяет подключать шаблоны динамически.

## Предварительные условия

Для использования механизмов наследования необходимо:
- **GitLab Runner:** настроенный с Docker или Kubernetes исполнителем. Для `extends` нет особых требований к типу раннера — механизм работает на уровне компиляции пайплайна.
- **Доступ к шаблонам:** Наличие прав `read_repository` (роль `Reporter`+) к проекту с общими шаблонами (при использовании `include:project`). Для приватных групп может потребоваться настройка `Token Access`.
- **Согласованность стадий:** Стадии (`stages`), указанные в шаблонах, должны быть определены в локальном файле `.gitlab-ci.yml`, иначе пайплайн не пройдет валидацию.
- **Версия GitLab:** Базовый `extends` работает с любой версии GitLab. Для комбинации с `inputs` рекомендуется GitLab 16.0+. Для `id_tokens` — GitLab 15.7+ (глобальный `default:` — с 16.4), а для Secrets Manager — GitLab 19.0+.

### Рекомендуемый стек версий

| Компонент | Минимальная версия | Рекомендуемая версия |
| :--- | :--- | :--- |
| GitLab | 11.3 | 19.x |
| GitLab Runner | 12.0 | 17.x+ |
| `!reference` | 13.9 | 17.2+ (индексы массивов) |
| `inputs` + `extends` | 16.0 | 17.x+ |
| `id_tokens` (OIDC) | 15.7 | 16.4+ (глобально через `default:`) |
| `secrets` (Vault) | 13.4 | 17.x+ (`gitlab_secrets_manager` — public beta с 19.0) |
| `default:` (вместо глобальных `image`/`before_script`) | любая | рекомендуется (глобальные ключи объявлены устаревшими) |

## Практические сценарии

### Сценарий 1: Базовый шаблон сборки с кастомизацией

Центральная библиотека предоставляет стандарт сборки, а проект дополняет его специфичными переменными.

```yaml
# ci-templates/docker-build.yml
.docker-build-base:
  stage: build
  image: docker:29.8
  services:
    - docker:29.8-dind
  variables:
    DOCKER_BUILDKIT: "1"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

Локальная адаптация в проекте:
```yaml
# .gitlab-ci.yml проекта
include:
  - project: 'shared/ci-templates'
    file: '/docker-build.yml'

build-app:
  extends: .docker-build-base
  variables:
    # Добавление новой переменной к родительским
    APP_VERSION: "v1.2.3"
    # Переопределение существующей
    DOCKER_BUILDKIT: "0"
```

### Сценарий 2: Многоуровневое технологическое наследование

Создание иерархии позволяет разделять ответственность между инфраструктурой и разработкой.

```yaml
# Уровень 1: Инфраструктурный стандарт
.infra-base:
  interruptible: true
  tags: [docker-runner]

# Уровень 2: Технологический стек (Node.js)
.node-base:
  extends: .infra-base
  image: node:22-alpine
  before_script:
    - npm ci --cache .npm/
  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths: [.npm/]

# Уровень 3: Конкретная задача проекта
test-unit:
  extends: .node-base
  script:
    - npm test
```

### Сценарий 3: Переопределение правил запуска (rules)

Поскольку `rules` — это массив, его переопределение требует полного дублирования логики, если нужно сохранить базовые правила.

```yaml
.base-rules:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

deploy-job:
  extends: .base-rules
  rules:
    # Базовое правило MR будет потеряно, если не указать его здесь явно
    - if: $CI_COMMIT_TAG
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

### Сценарий 4: Шаблонизация по окружениям (Environment Scoping)

Использование двоеточия в именах заданий позволяет визуально группировать реализации одного шаблона. Это стандартный паттерн для централизованного управления деплоем.

```yaml
# ci-templates/deploy.yml
.deploy-base:
  stage: deploy
  # Официальный образ kubectl; версия закреплена, не latest.
  # bitnami/kubectl более не публикуется в Docker Hub (каталог перенесён в
  # bitnamilegacy без обновлений безопасности).
  image:
    name: registry.k8s.io/kubectl:v1.37.0
    entrypoint: [""]
  variables:
    ENVIRONMENT: "undefined"
  script:
    - kubectl set image deployment/$APP $APP:$CI_COMMIT_SHA -n $ENVIRONMENT
    - kubectl rollout status deployment/$APP -n $ENVIRONMENT --timeout=300s
  environment:
    name: $ENVIRONMENT

# Проект: вызов по окружениям
deploy:dev:
  extends: .deploy-base
  variables:
    ENVIRONMENT: "dev"
  rules:
    - if: $CI_COMMIT_BRANCH == "develop"

deploy:staging:
  extends: .deploy-base
  variables:
    ENVIRONMENT: "staging"
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy:production:
  extends: .deploy-base
  variables:
    ENVIRONMENT: "production"
  rules:
    - if: $CI_COMMIT_TAG
  when: manual
```

### Сценарий 5: Комбинация `!reference` и `extends` (гибридный паттерн)

`extends` задает архитектуру задания, а `!reference` впрыскивает специфичную логику, решая проблему замены массивов.

```yaml
# templates/common.yml
.check_licenses:
  script:
    - echo "Проверка лицензий..."
    - trivy fs --scanners license .

.cleanup_workspace:
  after_script:
    - rm -rf .cache
    - echo "Workspace очищен"

# templates/docker-build.yml
.docker-build-base:
  image: docker:29.8
  services:
    - docker:29.8-dind
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

# Проект: расширение шаблона дополнительными шагами
build-app:
  extends: .docker-build-base
  script:
    - !reference [.check_licenses, script]
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  after_script:
    - !reference [.cleanup_workspace, after_script]
```

### Сценарий 6: Ловушка переопределения объектов (Artifacts/Cache)

Частая ошибка: переопределение только части блока `artifacts` или `cache` приводит к потере родительских параметров.

```yaml
.base_test:
  script: npm test
  artifacts:
    paths:
      - coverage/
    expire_in: 1 week

# ОШИБКА: expire_in будет ПОТЕРЯН
special_test:
  extends: .base_test
  artifacts:
    paths:
      - custom-reports/
    # expire_in от родителя ПОТЕРЯН, т.к. весь блок artifacts заменён
```

**Правильный подход:** Используйте `!reference` для вставки родительских значений или дублируйте полный блок:

```yaml
# Правильно: полное дублирование блока
special_test:
  extends: .base_test
  artifacts:
    paths:
      - coverage/
      - custom-reports/
    expire_in: 1 week

# Альтернатива: !reference для частичного дополнения
special_test_v2:
  extends: .base_test
  artifacts:
    paths:
      - !reference [.base_test, artifacts, paths]
      - custom-reports/
    expire_in: 1 week
```

### Сценарий 7: Многоуровневое наследование с иерархией ответственности

Создание иерархии «Инфраструктура → Технологический стек → Конкретная задача» с четким разделением ответственности.

```yaml
# Уровень 1: Инфраструктурный стандарт (управляет SRE/Platform-команда)
.infra-base:
  tags: [docker-runner]
  interruptible: true
  retry:
    max: 2
    when: [runner_system_failure, stuck_or_timeout_failure]

# Уровень 2: Технологический стек (управляет DevOps-командой)
.node-base:
  extends: .infra-base
  image: node:22-alpine
  before_script:
    - npm ci --cache .npm/
  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths: [.npm/]
    policy: pull-push

# Уровень 3: Конкретная задача проекта (управляет разработчиками)
test-unit:
  extends: .node-base
  script:
    - npm run test:unit
  artifacts:
    reports:
      junit: reports/junit.xml
    expire_in: 7 days

test-integration:
  extends: .node-base
  script:
    - npm run test:integration
  services:
    - postgres:18
  variables:
    POSTGRES_DB: test_db
```

### Сценарий 8: Отладка итоговой конфигурации

Перед коммитом необходимо проверить, как `extends` и `!reference` повлияли на итоговую конфигурацию.

```bash
# Просмотр полной (развернутой) конфигурации
glab ci config compile

# Проверка синтаксиса с имитацией переменных
glab ci lint --dry-run --ref <branch>

# Экспорт полного YAML для анализа
glab ci config compile > full_pipeline.yml
cat full_pipeline.yml | grep -A5 "test-unit"
```

**Чеклист валидации:**
1. `Pipeline Editor` → вкладка «View merged YAML» — визуальная проверка итога
2. `glab ci lint --show-expanded` — локальная проверка перед пушем
3. Логи задачи: добавьте `export` или `env` в `script` для проверки финальных значений переменных

### Сценарий 9: Миграция с этапа Include на extends

Ключевой переход эволюции — превращение «монолитного» шаблона (этап 2) в библиотеку скрытых заданий (этап 3). Ниже показан рефакторинг без изменения поведения для потребителей.

**До: монолитный шаблон, где каждый job дублирует подготовку окружения**
```yaml
# ci-templates/backend.yml (этап 2)
build-backend:
  stage: build
  image: docker:29.8
  services:
    - docker:29.8-dind
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .

test-backend:
  stage: test
  image: docker:29.8
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
  services:
    - postgres:18
  script:
    - npm test
```

**После: декомпозиция на атомарные скрытые задания и сборка через `extends`**
```yaml
# ci-templates/backend.yml (этап 3)
.docker-login:
  image: docker:29.8
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY

.docker-base:
  extends: .docker-login
  stage: build
  variables:
    DOCKER_BUILDKIT: "1"

build-backend:
  extends: .docker-base
  script:
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .

test-backend:
  extends: .docker-login
  stage: test
  services:
    - postgres:18
  script:
    - npm test
```

**Порядок миграции (devops-практика):**
1. **Аудит дублирования:** `grep -n "before_script" ci-templates/*.yml` — одинаковые блоки подготовки станут кандидатами на вынос.
2. **Декомпозиция:** вынесите повторяющиеся блоки (`image`, `before_script`, `tags`, `cache`) в атомарные скрытые задания; каждый блок отвечает за одну зону ответственности.
3. **Сборка иерархии:** соберите задания через `extends` и проверьте, что итоговый YAML идентичен прежнему (`glab ci lint --show-expanded`, сравнение diff).
4. **Семантическая фиксация:** закрепите новую версию шаблона SemVer-тегом (`v3.0.0`) и обновите `ref` в `include:project` у пилотного проекта.
5. **Canary-роллаут:** распространяйте на группы/инстанс постепенно (пилотный проект → группа → весь инстанс), отслеживая статус пайплайнов. Откат — переключение `ref` на прежний тег.

> **Правило:** на этапе 3 потребители работают только с именами скрытых заданий (`extends: .docker-login`), а не с их содержимым. Интерфейс шаблона — имена скрытых заданий и переменные, которые они ожидают.

## Валидация

Для проверки итоговой конфигурации после слияния всех `extends` и `include` используйте комбинацию инструментов:

### Локальная валидация (GitLab CLI)

```bash
# Быстрая проверка синтаксиса
glab ci lint

# Полный разбор с отображением итогового YAML
glab ci config compile

# Проверка с имитацией переменных окружения
glab ci lint --dry-run --ref <branch>

# Экспорт полной конфигурации для аудита
glab ci config compile > expanded.yml
```

### Валидация через Web UI

1.  **Pipeline Editor:** В интерфейсе GitLab (`Build -> Pipeline Editor`) используйте вкладку **«View merged YAML»**. Это эталонная конфигурация того, как сервер видит ваш пайплайн после всех слияний.
2.  **CI Lint API:** Программная проверка через HTTP-запросы (используется в CI-пайплайнах самих шаблонов):
    ```bash
    curl --request POST \
      --header "PRIVATE-TOKEN: $TOKEN" \
      --header "Content-Type: application/json" \
      --data '{"content": "include:\n  - project: shared/ci-templates\n    file: templates/build.yml"}' \
      "https://gitlab.example.com/api/v4/ci/lint?include_merged_yaml=true"
    ```

### Отладка в логах

При возникновении ошибок с переменными добавьте команду `export` или `env` в `script`, чтобы увидеть финальные значения, полученные в результате слияния:

```yaml
script:
  - export  # Показать все переменные окружения
  - env | grep -E "^(CI_|DOCKER_)"  # Фильтр по префиксу
  - echo "IMAGE_TAG=$CI_COMMIT_SHORT_SHA"
```

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Исчез `before_script` из шаблона | Дочернее задание определило свой `before_script` (массивы замещаются, не дополняются). | Используйте `!reference` для вставки родительского скрипта в дочерний: `before_script: !reference [.base, before_script]`. |
| `script` пуст или отсутствует | Переопределение `script` пустым значением или его отсутствие в родителе. | Если переопределяете `script`, обязательно укажите хотя бы одну команду. Проверьте, не заменили ли вы массив родительского скрипта. |
| Переменные не переопределяются | Переменная задана на уровне CI/CD Settings проекта (UI) или группы. | Учтите приоритет: переменные настроек GitLab выше переменных в YAML. Локальные переменные в `.gitlab-ci.yml` важнее `extends`. |
| Ошибка: `job extends unknown base` | Шаблон не загружен через `include` или опечатка в имени задания. | Проверьте вкладку "View merged YAML" в Pipeline Editor. Убедитесь, что `include` подключает нужный файл. |
| Циклическая зависимость | `A` наследует `B`, а `B` наследует `A` (прямая или через цепочку). | Разорвите цикл, выделив общую логику в независимый скрытый шаблон `.base-C`. |
| `circular reference detected` | Кольцевое наследование `extends`. | Проверьте всю цепочку наследования. Используйте `glab ci lint --show-expanded` для визуализации. |
| `exceeded max levels` | Глубина наследования `extends` > 11 уровней. | Упростите иерархию шаблонов. Старайтесь не превышать 3-4 уровня вложенности. |
| `script: can't be blank` | Переопределение `script` пустым значением. | Укажите хотя бы одну команду в `script` дочернего задания. |
| Артефакты/кэш «потеряны» | Поверхностная перезапись блока объектов (переопределён только один ключ). | Проверьте, не перезаписан ли весь блок `artifacts` или `cache` в дочернем задании. Используйте `!reference` или дублируйте полный блок. |
| `included file not found` | Неверный путь в `include:project` или отсутствие прав у `CI_JOB_TOKEN`. | Проверьте путь от корня репозитория шаблонов и `Visibility` проекта. Убедитесь, что в настройках проекта включён `Token Access` (Allowlist). |
| `Input 'X' must match regex` | При комбинации с `inputs`: переданное значение нарушает правила валидации. | Проверьте входные данные на соответствие регулярному выражению из `spec:inputs`. |
| Изменение шаблона ломает проекты | Родительский шаблон изменил структуру (добавил обязательный ключ или переименовал переменную). | Используйте SemVer для версионирования шаблонов. Закрепляйте версию через `ref: vX.Y.Z` в `include:project`. |

## Лучшие практики и очистка

**Проектирование иерархии:**
- Ограничивайте глубину наследования 3 уровнями, отдавайте предпочтение плоской композиции `extends: [.infra-base, .specific]`.
- Имя скрытого задания — это публичный интерфейс шаблона. Используйте осмысленные префиксы (`.build-`, `.test-`, `.deploy-`, `.auth-`) и не меняйте их без SemVer-мажора.
- Декомпозируйте по зонам ответственности (инфраструктура / технологический стек / конкретная задача) — см. Сценарий 7.

**Версионирование и роллаут:**
- Закрепляйте шаблон SemVer-тегом (`ref: vX.Y.Z`) в `include:project`; не используйте `ref: main` — изменение мгновенно ломает сотни пайплайнов.
- Распространяйте новую ревизию канарейкой: пилотный проект → группа → инстанс. Откат — переключение `ref` на прежний тег.
- Любое публичное изменение имени скрытого задания или добавляемой переменной — breaking change. Анонсируйте его в changelog шаблона.

**Безопасность:**
- Не храните секреты в скрытых заданиях. Для аутентификации используйте `CI_JOB_TOKEN`, `id_tokens` (OIDC) или блок `secrets` (Vault / GitLab Secrets Manager).
- Объявляйте секреты точечно, в заданиях, которые их потребляют; избегайте выноса секретных значений в переменные уровня шаблона.

**Контроль качества шаблона (в самом CI шаблонного репозитория):**
- Добавьте job, который прогоняет `glab ci lint --show-expanded` на каждый MR в шаблоны и сверяет раскрытый YAML с эталоном.
- Добавьте тест, гарантирующий, что скрытые задания не «протекают» в пайплайн как реальные (проверка списка заданий через CLI).

**Сериализация гонок:**
- Если несколько заданий через `extends` пишут в общий ресурс (кэш, реестр), добавьте `resource_group` — `extends` не даёт никаких гарантий взаимного исключения.

**Очистка:**
- Регулярно удаляйте неиспользуемые скрытые задания: `rg "extends:.*\.old-template" ci-templates/` показывает, кто ссылается на шаблон; отсутствие ссылок → удаление.
- После миграции на этап 4 (Kaniko) закрывайте неиспользуемые `ref`-версии шаблонов политиками очистки реестра (`Package Registry cleanup`), а не блокировкой новых версий.
- При удалении скрытого задания сначала выпустите мажорную версию без него и дождитесь, пока все потребители перейдут на новый `ref`.

## Преимущества и недостатки подхода

| Характеристика | Описание |
| :--- | :--- |
| **Масштабируемость** | Позволяет обновлять логику в одном шаблоне для сотен проектов. Централизованное управление стандартами. |
| **Типизация** | Создает четкие стандарты заданий (Build, Test, Deploy) внутри организации. Иерархия шаблонов отражает архитектуру. |
| **Гибкость** | Проекты переопределяют только нужные ключи, сохраняя остальные настройки от центральной команды. |
| **Совместимость** | Работает с любым типом Runner и версией GitLab 11.3+. Интегрируется с `!reference`, `inputs`, `include`. |
| **Изоляция контекста** | Скрытое задание (с префиксом `.`) не запускается напрямую — только как шаблон через `extends`. Риск случайного запуска промежуточного слоя минимален. |
| **Скрытая сложность (Минус)** | При глубокой вложенности (>3 уровней) сложно понять итоговый `script` без спецсредств (Pipeline Editor, `glab ci lint`). |
| **Хрупкость (Минус)** | Изменение структуры родительского шаблона может привести к неожиданному поведению в дочерних заданиях. Требует SemVer-версионирования. |
| **Замена массивов (Минус)** | Массивы (`script`, `rules`, `tags`) не дополняются, а полностью замещаются. Для обхода required `!reference`. |
| **Лимит вложенности (Минус)** | Максимум 11 уровней наследования. Практический лимит — 3-4 уровня. |
