# Гибкость шаблонов через механизм extends

## Определения

**`extends`** — директива GitLab CI для реализации наследования конфигурации. Она позволяет заданию (job) заимствовать параметры из другого задания (обычно «скрытого»), обеспечивая переиспользование кода без нарушения принципа DRY (Don't Repeat Yourself).

**Скрытое задание (Hidden Job)** — задание, имя которого начинается с точки (например, `.base-template`). Такие задания игнорируются планировщиком GitLab и не запускаются в пайплайне напрямую, служа исключительно фундаментом для других задач.

**Обратное глубокое слияние (Reverse Deep Merge)** — алгоритм объединения конфигураций, при котором параметры дочернего задания накладываются на родительские. Дочерние значения имеют абсолютный приоритет при совпадении ключей.

**Контекст этапа:** Третий уровень зрелости CI/CD. Переход от простой централизации ([этап include](./evolution_include.md)) к созданию гибких библиотек, где общая логика хранится в центре, а проекты-потребители могут адаптировать её под свои специфические нужды.

## Базовые концепции

### Эволюционное преимущество перед YAML-якорями

На ранних этапах развития часто применяются якоря YAML (`&` и `*`). Однако `extends` обладает критическими преимуществами:
1.  **Межфайловое взаимодействие:** Якоря работают только в пределах одного файла. `extends` позволяет наследовать логику из файлов, подключенных через `include`.
2.  **Читаемость:** Синтаксис `extends` более прозрачен и лучше поддерживается инструментами статического анализа GitLab.
3.  **Многоуровневость:** `extends` поддерживает цепочки наследования (до 11 уровней), в то время как глубокая вложенность якорей быстро становится неуправляемой.

### Правила слияния данных

Понимание того, как GitLab объединяет ключи, критично для избежания ошибок «исчезнувших скриптов»:

-   **Скаляры и Хеши (Слияние):** Ключи `image`, `stage`, `variables`, `retry`, `artifacts` объединяются. Если в дочернем задании определена переменная, которая уже есть в родителе, будет использовано дочернее значение.
-   **Массивы (Замещение):** Списки `script`, `before_script`, `after_script`, `tags`, `rules` **не объединяются**. Если дочернее задание определяет `script`, родительский скрипт полностью игнорируется.
-   **Множественное наследование:** Задание может наследоваться от списка шаблонов: `extends: [.base_1, .base_2]`. Слияние происходит справа налево: значения из `.base_2` переопределяют `.base_1`.

## Предварительные условия

Для использования механизмов наследования необходимо:
- **Доступ к шаблонам:** Наличие прав `read_repository` к проекту с общими шаблонами (при использовании `include:project`).
- **Согласованность стадий:** Стадии (`stages`), указанные в шаблонах, должны быть определены в локальном файле `.gitlab-ci.yml`, иначе пайплайн не пройдет валидацию.
- **Версия GitLab:** Для корректной работы множественного наследования рекомендуется использовать GitLab 12.0+.

## Практические сценарии

### Сценарий 1: Базовый шаблон сборки с кастомизацией

Центральная библиотека предоставляет стандарт сборки, а проект дополняет его специфичными переменными.

```yaml
# ci-templates/docker-build.yml
.docker-build-base:
  stage: build
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    DOCKER_BUILDKIT: "1"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

Локальная адаптация в проекте:
```yaml
# .gitlab-ci.yml проекта
include:
  - project: 'shared/ci-templates'
    file: '/docker-build.yml'

build-app:
  extends: .docker-build-base
  variables:
    # Добавление новой переменной к родительским
    APP_VERSION: "v1.2.3"
    # Переопределение существующей
    DOCKER_BUILDKIT: "0"
```

### Сценарий 2: Многоуровневое технологическое наследование

Создание иерархии позволяет разделять ответственность между инфраструктурой и разработкой.

```yaml
# Уровень 1: Инфраструктурный стандарт
.infra-base:
  interruptible: true
  tags: [docker-runner]

# Уровень 2: Технологический стек (Node.js)
.node-base:
  extends: .infra-base
  image: node:22-alpine
  before_script:
    - npm ci --cache .npm/
  cache:
    key: "$CI_COMMIT_REF_SLUG"
    paths: [.npm/]

# Уровень 3: Конкретная задача проекта
test-unit:
  extends: .node-base
  script:
    - npm test
```

### Сценарий 3: Переопределение правил запуска (rules)

Поскольку `rules` — это массив, его переопределение требует полного дублирования логики, если нужно сохранить базовые правила.

```yaml
.base-rules:
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

deploy-job:
  extends: .base-rules
  rules:
    # Базовое правило MR будет потеряно, если не указать его здесь явно
    - if: $CI_COMMIT_TAG
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

## Валидация

Для проверки итоговой конфигурации после слияния всех `extends` и `include`:
1.  **Pipeline Editor:** В интерфейсе GitLab (`Build -> Pipeline Editor`) используйте вкладку **«Full configuration»**. Это SSoT (Single Source of Truth) того, как сервер видит ваш пайплайн.
2.  **CI Lint:** Используйте встроенный линтер для проверки синтаксиса перед коммитом.
3.  **Логи задачи:** При возникновении ошибок с переменными добавьте команду `export` или `env` в `script`, чтобы увидеть финальные значения, полученные в результате слияния.

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| Исчез `before_script` из шаблона | Дочернее задание определило свой `before_script`. | Используйте `!reference` для вставки родительского скрипта в дочерний. |
| Переменные не переопределяются | Переменная задана на уровне CI/CD Settings проекта. | Учтите приоритет: переменные настроек GitLab выше переменных в YAML. |
| Ошибка: `job extends unknown base` | Шаблон не загружен через `include` или опечатка в имени. | Проверьте вкладку "View merged YAML" в Pipeline Editor. |
| Циклическая зависимость | `A` наследует `B`, а `B` наследует `A`. | Разорвите цикл, выделив общую логику в независимый скрытый шаблон `.base-C`. |

## Преимущества и недостатки подхода

| Характеристика | Описание |
| :--- | :--- |
| **Масштабируемость** | Позволяет обновлять логику в одном шаблоне для сотен проектов. |
| **Типизация** | Создает четкие стандарты заданий (Build, Test, Deploy) внутри организации. |
| **Сложность (Минус)** | При глубокой вложенности (>3 уровней) сложно понять итоговый `script` без спецсредств. |
| **Хрупкость (Минус)** | Изменение структуры родительского шаблона может привести к неожиданному поведению в дочерних заданиях. |
