# Гибкость шаблонов через `extends`

## Определения

**`extends`** — механизм наследования конфигурации в GitLab CI. Позволяет заданию (job) наследовать настройки от другого задания (обычно скрытого).

**Скрытое задание (Hidden Job)** — задание с именем, начинающимся на точку (например, `.docker-build-template`). Оно не запускается в пайплайне напрямую, а служит шаблоном для других заданий.

**Контекст этапа:** Решение проблемы жёсткой конфигурации, возникшей после централизации шаблонов (этап [include](./evolution_include.md)). `extends` позволяет проектам-потребителям кастомизировать полученные шаблоны под свои нужды, не меняя их исходный код.

## Базовые концепции

### Зачем нужен `extends` вместо YAML-якорей

На этом этапе часто возникает вопрос выбора между `extends` и YAML-якорями (`&` и `*`). Ключевое отличие: **якоря не работают через границы файлов**. Если ваш шаблон находится в центральном репозитории и подключается через `include`, вы не сможете использовать его якоря в текущем проекте. `extends` полностью решает эту проблему, работая со всей объединённой конфигурацией.

### Принцип работы

```yaml
# Шаблон (не выполняется)
.base-job:
  image: docker:27.0
  script:
    - echo "Base script"

# Реальный job (наследуется от шаблона)
my-job:
  extends: .base-job
  variables:
    MY_VAR: "value"
```

При наследовании применяется механизм **обратного глубокого слияния (reverse deep merge)**. Дочерние элементы переопределяют родительские. Подробные правила слияния (обработка `script`, `variables`, `rules`) описаны в SSoT-документе — [Механизм `extends`](../extends_keyword.md).

## Практические сценарии

### Централизованный шаблон с поддержкой кастомизации

**Репозиторий:** `group/ci-templates`  
**Файл:** `docker-build.yml`

```yaml
# ci-templates/docker-build.yml
.docker-build-template:
  stage: build
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build \
        --build-arg CI_JOB_TOKEN=${CI_JOB_TOKEN} \
        -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA \
        .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

### Использование и переопределение в проекте

Проект подключает шаблон и адаптирует его: меняет переменные, добавляет шаги подготовки или изменяет условия запуска.

```yaml
# .gitlab-ci.yml проекта
include:
  - project: 'group/ci-templates'
    ref: v2.0.0
    file: '/docker-build.yml'

stages:
  - build

build-app:
  extends: .docker-build-template
  variables:
    DOCKER_BUILDKIT: "1"
    IMAGE_TAG: "custom-release"
  before_script:
    - echo "Подготовка специфичных для проекта зависимостей"
    - npm install --only=production
```

### Преимущества и недостатки подхода

| Характеристика | Описание |
| :--- | :--- |
| **Централизация** | Общая логика хранится в одном месте, упрощая сопровождение. |
| **Гибкость** | Проекты могут добавлять свои `variables`, `before_script`, `after_script` или переопределять `image`. |
| **Безопасность (Минус)** | Использование `docker:dind` всё ещё требует привилегированного режима (`privileged: true`). |
| **Сложность обновления** | Обратная совместимость: изменение имен переменных в шаблоне может "сломать" кастомизацию в десятках проектов. |
