# Абстрагирование деталей реализации с Kaniko

## Определения

**Абстрагирование деталей реализации** — стратегический этап развития CI/CD, при котором внутренняя логика выполнения задач (инструментарий, команды, настройки среды) скрывается внутри общего шаблона. Это позволяет изменять технологический стек (например, заменять Docker на Kaniko) без внесения правок в сотни клиентских проектов.

**Kaniko** — специализированная утилита для сборки контейнерных образов внутри контейнера или Kubernetes-кластера без необходимости использования привилегированного режима (`privileged`) или доступа к Docker-демону. 
> **Статус проекта (2025):** Оригинальный репозиторий Google (`GoogleContainerTools/kaniko`) архивирован. В актуальных пайплайнах рекомендуется использовать форк от сообщества — `osscontainertools/kaniko`.

**Контекст этапа:** Переход от простых общих шаблонов к концепции "CI/CD как сервис", где потребитель управляет только бизнес-параметрами сборки, не заботясь о базовой инфраструктуре и безопасности среды выполнения.

## Базовые концепции

### Зачем нужно абстрагирование

На предыдущих этапах эволюции (например, [Гибкость с extends](./evolution_extends.md)) проекты напрямую использовали `docker:dind`. Это приводило к ряду проблем:

1.  **Безопасность:** Необходимость запуска контейнеров в привилегированном режиме (`privileged: true`), что является критической уязвимостью в общих кластерах.
2.  **Зависимость:** При желании сменить Docker на более быстрый или безопасный инструмент (Buildah, Kaniko) пришлось бы переписывать `script` во всех проектах.
3.  **Хрупкость:** Изменение параметров авторизации в реестре или обновление версии Docker требовало ручной синхронизации во всей организации.

### Принцип "Черного ящика"

Вместо того чтобы проект знал о вызовах `docker build`, он передает в шаблон только метаданные: путь к `Dockerfile`, имя образа и контекст сборки. Все остальное (выбор образа исполнителя, аутентификация в GitLab Registry, параметры кэширования) инкапсулировано в шаблоне.

```text
┌────────────────────────────────────────────────────────────┐
│  Центральный шаблон: docker-build.yml                      │
│  - Image: osscontainertools/kaniko (v1.28.0)               │
│  - Script: /kaniko/executor --cache=true ...               │
│  - Auth: автоматическая генерация config.json              │
└────────────────────────────────────────────────────────────┘
                          ↑ (Input: Variables)
┌────────────────────────────────────────────────────────────┐
│  Проект: .gitlab-ci.yml                                    │
│  - variables: DOCKERFILE: "app/Dockerfile"                 │
│  - extends: .docker-build-template                         │
└────────────────────────────────────────────────────────────┘
```

## Практические сценарии

### Настройка централизованного шаблона

В этом примере создается шаблон, который самостоятельно подготавливает окружение для Kaniko и выполняет сборку, скрывая все сложности от конечного пользователя.

```yaml
# ci-templates/docker-build.yml
.docker-build-template:
  stage: build
  image:
    # Используем версию debug, так как она содержит shell для before_script
    name: osscontainertools/kaniko:v1.28.0-debug
    entrypoint: [""]
  variables:
    # Дефолтные значения, которые проект может переопределить
    DOCKERFILE: Dockerfile
    CONTEXT: $CI_PROJECT_DIR
    DESTINATION: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    # Возможность передачи специфичных флагов без изменения скрипта
    EXTRA_ARGS: ""
  before_script:
    # Подготовка конфига авторизации для Kaniko (скрытая деталь)
    - mkdir -p /kaniko/.docker
    - echo "{\"auths\":{\"$CI_REGISTRY\":{\"auth\":\"$(printf "%s:%s" "$CI_REGISTRY_USER" "$CI_REGISTRY_PASSWORD" | base64 | tr -d '\n')\"}}}" > /kaniko/.docker/config.json
  script:
    - /kaniko/executor \
        --context "$CONTEXT" \
        --dockerfile "$DOCKERFILE" \
        --destination "$DESTINATION" \
        --cache=true \
        --cache-repo="$CI_REGISTRY_IMAGE/cache" \
        --cache-ttl=24h \
        $EXTRA_ARGS
```

### Использование в проекте

Для проекта переход с Docker на Kaniko проходит незаметно. Конфигурация остается декларативной и чистой.

```yaml
# .gitlab-ci.yml проекта
include:
  - project: 'group/ci-templates'
    ref: v1.0.0
    file: '/docker-build.yml'

build-app:
  extends: .docker-build-template
  variables:
    DOCKERFILE: "src/Dockerfile"
    # Для многостадийных сборок можно передать target через EXTRA_ARGS
    EXTRA_ARGS: "--target production"
```

### Важные технические нюансы

1.  **Работа с внутренними реестрами (Self-signed certificates):**
    Если используется корпоративный Registry с собственным CA, Kaniko потребует передачи сертификата. В абстрагированном шаблоне это решается через `before_script`:
    ```bash
    - cp $INTERNAL_CA_CERT /kaniko/ssl/certs/ca-certificates.crt
    ```
    Или использованием флага `--registry-certificate $REGISTRY=$CERT_PATH`.

2.  **Многостадийные сборки (Multi-stage builds):**
    Kaniko поддерживает `--target`. Если в Dockerfile несколько стадий, необходимо убедиться, что промежуточные слои также кэшируются (`--cache=true`).

3.  **Безопасность (Non-root):**
    Хотя Kaniko не требует `privileged`, по умолчанию он часто запускается от root. Для максимальной безопасности (Pod Security Standards: Restricted) следует использовать `executor` от пользователя с низкими привилегиями, что требует корректной настройки прав на `/kaniko` в образе.

4.  **Ограничения FS:**
    Kaniko распаковывает слои в собственную файловую систему. Это может вызвать конфликты, если в Dockerfile выполняются операции с системными путями, которые уже заняты самим Kaniko (например, `/kaniko`).

### Преимущества и недостатки подхода

| Характеристика | Описание |
| :--- | :--- |
| **Безопасность** | Полный отказ от `privileged` режима. Работает в Kubernetes с Pod Security Standards: Restricted. |
| **Масштабируемость** | Возможность централизованно добавить сканирование образов или отправку метрик во все проекты одновременно. |
| **Сложность отладки** | Ошибки внутри "скрытого" скрипта сложнее диагностировать разработчикам приложений без доступа к шаблону. |
| **Отсутствие типизации** | Параметры передаются через неявные переменные (решается на [следующем этапе](./evolution_components.md)). |
