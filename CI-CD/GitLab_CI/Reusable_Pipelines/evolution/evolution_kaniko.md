# Абстрагирование деталей реализации с Kaniko

## Определения

**Абстрагирование деталей реализации** — четвёртый этап эволюции pipelines, заключающийся в сокрытии внутренней логики шаблона от потребителей. Позволяет обновлять инструменты build (например, переход с Docker на Kaniko) без необходимости изменять конфигурацию в десятках зависимых проектов.

**Kaniko** — инструмент для build containers без доступа к Docker-демону, обеспечивающий более высокий уровень безопасности в CI/CD.

**Контекст этапа:** Решение проблемы безопасности и "прозрачное" обновление инфраструктуры build.

## Базовые концепции

### Почему этот этап важен

На предыдущих этапах проекты использовали `docker:dind`, что требовало привилегированного режима (`privileged: true`). При переходе на более безопасный [Kaniko](../../../../Docker/Dockerfile/dockerfile_kaniko.md) в централизованном шаблоне проекты не должны заметить изменений, так как детали реализации скрыты за интерфейсом переменных.

### Принцип абстрагирования

```
┌─────────────────────────────────────────────────────────┐
│  Шаблон: group/ci-templates/docker-build.yml            │
│  Внутренняя реализация: docker:dind → Kaniko            │
│  (изменения только внутри шаблона)                       │
└─────────────────────────────────────────────────────────┘
                          ↓
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Проект 1    │  │  Проект 2    │  │  Проект N    │
│  (конфигурация .gitlab-ci остается прежней)        │
└──────────────┘  └──────────────┘  └──────────────┘
```

## Практические сценарии

### Обновление централизованного шаблона

В репозитории `group/ci-templates` мы меняем реализацию в `docker-build.yml`, заменяя Docker-команды на вызовы Kaniko.

```yaml
# ci-templates/docker-build.yml
.docker-build-template:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:debug
    entrypoint: [""]
  variables:
    DOCKERFILE: Dockerfile
    CONTEXT: $CI_PROJECT_DIR
  script:
    - /kaniko/executor \
        --context $[[ CONTEXT ]] \
        --dockerfile $[[ DOCKERFILE ]] \
        --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA \
        --cache=true \
        --cache-repo=$CI_REGISTRY_IMAGE/cache
```

### Стабильность для проектов

Проекты продолжают использовать тот же шаблон через `extends`, не заботясь о том, какая технология используется "под капотом":

```yaml
# .gitlab-ci.yml проекта
include:
  - project: 'group/ci-templates'
    ref: v1.0.0
    file: '/docker-build.yml'

build-my-app:
  extends: .docker-build-template
  variables:
    DOCKERFILE: "app/Dockerfile"
```

### Преимущества и проблемы

| Характеристика | Описание |
| :--- | :--- |
| **Преимущества** | Повышение безопасности без нарушения работы команд, возможность централизованного внедрения кэширования и оптимизаций. |
| **Проблемы** | Всё ещё отсутствует явная типизация входных параметров (решается на следующем этапе), сложность отладки "скрытой" логики. |
