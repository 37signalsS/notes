# Проблема дублирования кода в GitLab CI (Boilerplate)

**Актуально для:** GitLab CI 19.x; Docker 29.x (DinD); Alpine Linux 3.24.x.

## Определения

**Boilerplate-код (Шаблонный код)** — избыточные фрагменты конфигурации, которые копируются в каждый новый проект без существенных изменений. В GitLab CI это проявляется в виде идентичных определений стадий (`stages`), базовых образов (`image`), скриптов сборки (`script`) и блоков подготовки окружения (`before_script`), жестко зашитых в локальные файлы `.gitlab-ci.yml`.

**Configuration Drift (Дрейф конфигураций)** — прогрессирующее расхождение между изначально одинаковыми пайплайнами. Возникает из-за локальных исправлений багов или обновлений версий в одном проекте, которые не переносятся в другие, что приводит к хаосу в управлении инфраструктурой.

**O(N) Complexity of Maintenance** — концепция, описывающая рост затрат на поддержку инфраструктуры. При использовании boilerplate-кода любая глобальная правка (например, обновление версии Docker, закрытие уязвимости или изменение SSH-политики) требует `N` изменений в `N` репозиториях.

**Copy-Paste Anti-Pattern (Антипаттерн копирования)** — системная проблема, при которой разработчики тиражируют конфигурации через `Ctrl+C` → `Ctrl+V` вместо использования механизмов переиспользования (`extends`, `include`, `!reference`, `inputs`). Является основным источником технического долга на этапе зрелости «Stage 1».

**Inline-проверка (Guard check)** — проверка условия непосредственно в теле задания (`if [ -z "$VAR" ]; then exit 1; fi`). Не является ошибкой сама по себе, но при копировании в десятки проектов она превращается в ещё один дубль: проверка живёт в копии, а не в источнике истины.

**Контекст этапа:** Первый уровень зрелости CI/CD («Stage 1»). Это естественная точка старта для небольших команд (1–3 сервиса), которая быстро превращается в основной источник технического долга при росте количества микросервисов. Согласно [Эволюции переиспользуемых пайплайнов](../evolution_example.md), этот этап характеризуется максимальной гибкостью при нулевой сопровождаемости.

> [!WARNING]
> **Признаки нахождения на этапе Boilerplate** (полный диагностический чек-лист — в разделе [Валидация](#валидация)):
> - Файл `.gitlab-ci.yml` содержит более 50 строк кода, не считая бизнес-логики (тесты, деплой).
> - Для создания пайплайна в новом сервисе разработчик открывает старый сервис и делает `Ctrl+C` → `Ctrl+V`.
> - Обновление версии базового образа (например, `alpine:3.23`) требует создания Merge Request'ов в нескольких репозиториях.
> - Один и тот же `before_script` (SSH-агент, Docker-login, Ansible) дублируется в 10+ проектах.
> - Уязвимость в скрипте сборки, обнаруженная в одном проекте, с вероятностью 100% присутствует во всех остальных.
> - YAML Anchors (`&`/`*`) используются как будто они переносятся между файлами — но область их действия ограничена одним файлом.

## Базовые концепции

### Архитектура типичного Boilerplate-пайплайна

```
┌──────────────────────────────────────────────────────────────────┐
│  Проект A: .gitlab-ci.yml (120 строк)                           │
│  ┌────────────────────────────────────────────────────────────┐  │
│  │ stages: [build, test, deploy]                              │  │
│  │ variables: { DOCKER_DRIVER: overlay2, IMAGE: ... }         │  │
│  │ .setup_docker: { script: [docker login, docker build...] } │  │
│  │ build: { extends: .setup_docker, stage: build }            │  │
│  │ test:  { stage: test, script: [pytest] }                   │  │
│  │ deploy:{ stage: deploy, script: [scp deploy.sh] }          │  │
│  └────────────────────────────────────────────────────────────┘  │
│                                                                  │
│  Скопировано 1:1 в ↓                                             │
│                                                                  │
│  Проект B: .gitlab-ci.yml (120 строк)                           │
│  Проект C: .gitlab-ci.yml (120 строк)                           │
│  ...                                                             │
│  Проект N: .gitlab-ci.yml (120 строк)                           │
│                                                                  │
│  Итого: N × 120 строк = N × потенциальных багов                  │
└──────────────────────────────────────────────────────────────────┘
```

Ключевое свойство этой схемы — у неё **нет точки отказа и точки исправления одновременно**. Изменение в одном файле не распространяется на остальные автоматически, но и не может быть отменено автоматически: операция «откатить обновление Docker во всей организации» не имеет обратного номера, только N отдельных Merge Request'ов.

### Системные причины возникновения

Дублирование кода чаще всего является не ошибкой конкретного разработчика, а следствием незрелости процессов:

1.  **Отсутствие платформенного мышления:** Инфраструктура воспринимается как набор разрозненных скриптов, а не как продукт или сервис.
2.  **Страх «Breaking Changes»:** Из-за отсутствия механизмов версионирования шаблонов проще скопировать рабочий код, чем пытаться создать общую библиотеку, которая может сломать чужие сборки.
3.  **Низкая прозрачность:** Разработчики не знают о существовании лучших практик в соседних командах и «изобретают велосипед» при создании каждого нового сервиса.
4.  **Отсутствие центрального каталога:** Нет выделенного репозитория для шаблонов, поэтому каждый проект хранит свои копии.
5.  **Незнание механизмов переиспользования:** Разработчики не знают о `extends`, `!reference`, `include`, YAML Anchors или считают их излишне сложными.

Отдельно стоит выделить **организационную** причину, которую не видно в коде: у платформенной команды нет ни мандата, ни бюджета на сопровождение общих шаблонов. Пока стоимость ведения шаблона не назначена конкретному владельцу, boilerplate дешевле центрального репозитория — он просто «бесплатен» для того, кто его пишет, и оплачивается всеми остальными.

### Анатомия типичного Boilerplate

Ниже представлен пример конфигурации, которая «кочует» из проекта в проект. Основная проблема — жесткое связывание (tight coupling) логики сборки с версией инструментария и параметрами реестра.

```yaml
# Пример кода, требующего удаления на следующих этапах
stages:
  - build
  - test

variables:
  # Проблема: DOCKER_DRIVER не читается ни одной командой этого задания —
  # наследие до-DinD конфигураций. Тем не менее строка копируется во все проекты.
  DOCKER_DRIVER: overlay2
  CONTAINER_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_REF_SLUG

docker-build:
  stage: build
  image: docker:29.8
  services:
    - docker:29.8-dind
  script:
    # Проблема: логика авторизации и сборки не инкапсулирована
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build --pull -t $CONTAINER_IMAGE .
    - docker push $CONTAINER_IMAGE
```

Обратите внимание на два дефекта, невидимые при поверхностном чтении:

- **`docker login ... -p $CI_JOB_TOKEN`.** Флаг `-p` передаёт токен аргументом командной строки, то есть он попадает в список процессов контейнера (`/proc/*/cmdline`) и в вывод shell с трассировкой. GitLab маскирует значение в логах, но маскирование не устраняет exposures на уровне ОС. Официальная рекомендация GitLab и Docker — `--password-stdin`.
- **Рассинхрон `DOCKER_TLS_CERTDIR` и тома `/certs/client`.** `DOCKER_TLS_CERTDIR` задаёт каталог, в котором клиент ищет сертификаты, а точка входа образа `docker:cli` на её основе выбирает транспорт: если в `$DOCKER_TLS_CERTDIR/client` лежат непустые `ca.pem`, `cert.pem` и `key.pem`, выставляется `DOCKER_HOST=tcp://docker:2376` и `DOCKER_CERT_PATH=$DOCKER_TLS_CERTDIR/client`; если каталог задан, но сертификатов нет — `tcp://docker:2375`, то есть **без TLS**. Сертификаты создаёт DinD-сервис, а доступны они заданию только через общий том `/certs/client`, смонтированный в `config.toml`. Потеря любой из двух частей при слиянии конфигураций даёт `Cannot connect to the Docker daemon` уже на этапе запуска. Значение `DOCKER_TLS_CERTDIR: ""` отключает TLS, и тогда `DOCKER_HOST: tcp://docker:2375` необходимо задать явно.

### Типичные паттерны дублирования

#### 1. Блоки подготовки окружения (before_script)

Наиболее частый источник дублирования. Один и тот же `before_script` копируется в десятки проектов:

```yaml
# Этот блок повторяется в 30+ проектах
before_script:
  - apk add --no-cache openssh-client curl
  - eval $(ssh-agent -s)
  - chmod 600 "$SSH_PRIVATE_KEY"
  - ssh-add "$SSH_PRIVATE_KEY"
  - mkdir -p ~/.ssh && chmod 700 ~/.ssh
  - echo "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
```

**Решение (Stage 2+):** Вынести в `include:project` шаблон или использовать `extends`:
```yaml
# templates/ssh-setup.yml
.ssh_base:
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - ssh-add "$SSH_PRIVATE_KEY"
    - mkdir -p ~/.ssh && chmod 700 ~/.ssh
    - echo "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
```

#### 2. Генерация конфигурационных файлов через heredoc

Классический паттерн boilerplate — генерация файлов через `cat > file << 'EOF'`:

```yaml
# Паттерн, который кочует из проекта в проект
generate_config:
  script:
    - |
      cat > /etc/nginx/conf.d/default.conf << 'EOF'
      server {
          listen 80;
          server_name $CI_PROJECT_NAME;
          location / {
              proxy_pass http://localhost:8080;
          }
      }
      EOF
```

**Решение (Stage 2+):** Вынести heredoc-шаблон в отдельный YAML-файл и подключать через `include:local` или `!reference`.

#### 3. SSH-деплой без изоляции

Самый опасный boilerplate — прямо в `.gitlab-ci.yml` зашиты SSH-команды для деплоя:

```yaml
# Опасный паттерн: SSH-ключи в variables, деплой через ssh
deploy_production:
  stage: deploy
  script:
    - ssh $DEPLOY_USER@$DEPLOY_HOST "docker pull $IMAGE && docker restart app"
  variables:
    DEPLOY_HOST: "192.168.1.100"  # IP-адрес зашит прямо в YAML
```

**Решение (Stage 4+):** Инкапсулировать деплой в скрытое задание с `extends` или использовать компоненты (Stage 5).

#### 4. Inline-проверки вместо инкапсуляции

Разработчики пытаются сделать код «более безопасным», добавляя проверки, но не меняя архитектуру:

```yaml
# Inline-проверки не решают проблему дублирования
build:
  script:
    - |
      if [ -z "$CI_REGISTRY_USER" ]; then
        echo "ERROR: CI_REGISTRY_USER is not set"
        exit 1
      fi
      docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
      docker build -t $IMAGE .
```

**Решение:** Inline-проверки полезны, но не заменяют централизацию. Правильный подход — вынести логику в шаблон с `spec:inputs` (Stage 5), где валидация происходит на этапе CI Lint, до запуска задания.

### Механизмы переиспользования (для сравнения)

| Механизм | Этап зрелости | Назначение | Ограничение |
| :--- | :--- | :--- | :--- |
| **YAML Anchors (`&`/`*`)** | 1 (костыль) | Копирование блоков в рамках одного файла | Действуют только внутри файла, в котором объявлены; между файлами не работают |
| **`extends`** | 3 | Наследование от скрытых заданий | Сливает хеши, но не массивы: `script`, `before_script`, `after_script` заменяются целиком. Глубина наследования — 11 уровней |
| **`!reference`** (13.9+) | 3+ | Точечная вставка фрагментов кода | Вложенность разрешена до 10 уровней, но только внутри `script`, `before_script`, `after_script` (14.8+) |
| **`include`** | 2 | Подключение внешних файлов | Не типизирует входы; до 150 подключений на пайплайн, включая вложенные |
| **`spec:inputs`** (16.0+) | 5 | Параметризация подключаемых файлов | Валидация значений по `type` и `options` — на этапе создания пайплайна; SemVer обязателен только при публикации в CI/CD-каталоге |
| **`include:inputs`** (17.0+) | 5 | Передача значений входов в подключаемый файл | Значение обязано совпадать с объявленным `type` и быть одним из `options` |

Разница между `spec:inputs` и `include:inputs` существенна: механизм входов (`spec:inputs`) стал общедоступным в 16.0, а передача значений при подключении (`include:inputs`) — только в 17.0. Ссылка на 16.0 для обоих — типичная ошибка, из-за которой шаблон «должен работать», но падает на развёртывании с GitLab 16.x.

### Почему `script`, `before_script`, `after_script` не сливаются

Критическое техническое ограничение, которое необходимо понимать на этапе Boilerplate: алгоритм слияния через `extends` — «closest scope wins» с обратным глубоким слиянием по ключам. **Хеши объединяются, массивы — нет.** Ключи последнего (самого близкого) уровня всегда перекрывают определения других уровней.

Если в родителе 10 строк, а в дочернем — 1, итоговое задание будет содержать только 1 строку. Это неочевидно и является источником типичной ошибки: разработчик добавляет шаг к `before_script` и молча теряет логин в реестр:

```yaml
.docker_base:
  before_script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker pull $IMAGE

my_deploy:
  extends: .docker_base
  before_script:
    - echo "Deploying..."  # Результат: только эта строка, docker login ПОТЕРЯН
```

**Обход:** Используйте `!reference` для вставки родительских команд:
```yaml
my_deploy:
  extends: .docker_base
  before_script:
    - !reference [.docker_base, before_script]
    - echo "Deploying..."  # Обе строки сохранены
```

### Почему `default` не решает ту же задачу, что `extends`

Блок `default` часто предлагают как замену глобальному `before_script`, и это правильная рекомендация, но у неё есть ограничение, которое ломает ожидания: **`default` не сливается с конфигурацией задания.** При создании пайплайна каждое значение из `default` копируется в задания, которые этот ключевое слово не определяют; если задание определяет его само — значение из `default` для этого задания не используется вовсе.

```yaml
default:
  image: alpine:3.24
  before_script:
    - apk add --no-cache openssh-client

build:
  before_script:
    - echo "своя подготовка"   # image из default применится, before_script — нет
  script: make build

test:
  script: make test            # сработают и image, и before_script из default
```

Практическое следствие для этапа Boilerplate: `default` убирает дублирование на уровне всего пайплайна, но не решает задачу «один шаблон → много заданий с разными надстройками». Для этого нужен `extends` (или `!reference`). Разделение ответственности:

| Задача | Механизм |
| :--- | :--- |
| Одинаковая базовая настройка для всех заданий пайплайна | `default:` |
| Общий образ, кэш или теги для группы заданий | скрытое задание + `extends` |
| Дописать шаг к `script` родителя без потери родительских шагов | `!reference` |
| Общие файлы конфигурации между репозиториями | `include` |

Поддерживаемые в `default` ключевые слова: `after_script`, `artifacts`, `before_script`, `cache`, `hooks`, `id_tokens`, `image`, `interruptible`, `retry`, `services`, `tags`.

## Предварительные условия

Для осознанного перехода с этапа Boilerplate необходимо:

- **Инвентаризация:** Провести аудит всех `.gitlab-ci.yml` в организации и выявить повторяющиеся блоки. Методы — в разделе [Валидация](#валидация).
- **Репозиторий-хранилище:** Выделить отдельный проект (например, `shared/ci-templates`) для хранения шаблонов.
- **Доступ:** Настроить права на чтение (Developer+) для всех проектов, которые будут подключать шаблоны.
- **Согласование:** Определить единый набор стадий и образов для организации.
- **Владелец:** Назначить команду, отвечающую за шаблоны, и регламент их изменения. Без владельца центральный репозиторий деградирует в новое подобие boilerplate — только теперь с задержкой обновления.
- **Baseline:** Зафиксировать текущее состояние (`glab ci config compile` по каждому проекту), чтобы иметь точку отсчёта для отката и оценки эффекта.

Требования к среде, на которой выполняется аудит и миграция:

| Компонент | Требование |
| :--- | :--- |
| GitLab | 17.0 и выше — иначе недоступен `include:inputs` |
| GitLab CLI (`glab`) | Аутентифицирован (`glab auth status`), доступен локально или в CI-задании |
| Права в `shared/ci-templates` | Developer+ для всех подключающих проектов |
| Хранилище зеркал | Локальные клоны или read-only зеркала всех `.gitlab-ci.yml` для offline-аудита |

## Практические сценарии

### Риски и скрытые затраты

1.  **Инфраструктурная фрагментация (Technical Sprawl):**
    В компании одновременно используются десятки версий одного и тот же инструмента (например, Python 3.9 в одном сервисе и 3.12 в другом для идентичных задач). Это делает невозможным оптимизацию Runner'ов и кэширования.
2.  **Цена ошибки растёт вместе с числом проектов:**
    Уязвимость в скрипте сборки, обнаруженная в одном проекте, с вероятностью 100% присутствует во всех остальных. Время реакции на инцидент безопасности (MTTR) растет пропорционально количеству репозиториев.
3.  **Блокировка инноваций:**
    Попытка внедрить современный инструмент (например, замена DinD на Kaniko) превращается в проект длиною в месяцы, так как требует ручного обновления сотен файлов.
4.  **Фрагментация среды выполнения:**
    Разные проекты используют разные версии базовых образов (`alpine:3.23` vs `alpine:3.24`), что затрудняет кэширование слоев и управление уязвимостями. Здесь же накапливается риск: версии, вышедшие из поддержки, продолжают использоваться просто потому, что их обновление никто не инициировал.
5.  **Дублирование конфигураций серверов:**
    Конфигурации nginx, sysctl, trusted certs генерируются через `cat > file << 'EOF'` в каждом проекте — любое изменение (например, обновление TLS-политики) требует правки сотен файлов.
6.  **Непредсказуемый откат:**
    Устранение неверного изменения требует N откатов. Если часть из них не выполнена, организация получает «половину отката» — состояние, которого нет ни в одном описании и которое невозможно воспроизвести.

### Сценарий 1: Деплой на сервер по SSH (Boilerplate)

Типичный boilerplate-пайплайн для деплоя на физический сервер через SSH.

```yaml
# Этот блок дублируется в 20+ проектах
stages:
  - build
  - deploy

variables:
  DOCKER_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

build:
  stage: build
  image: docker:29.8
  services:
    - docker:29.8-dind
  script:
    - echo "$CI_JOB_TOKEN" | docker login $CI_REGISTRY -u $CI_REGISTRY_USER --password-stdin
    - docker build --pull -t $DOCKER_IMAGE .
    - docker push $DOCKER_IMAGE

deploy_production:
  stage: deploy
  image: alpine:3.24
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - chmod 600 "$SSH_PRIVATE_KEY"
    - ssh-add "$SSH_PRIVATE_KEY"
    - mkdir -p ~/.ssh && chmod 700 ~/.ssh
    - echo "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
  script:
    - ssh $DEPLOY_USER@$DEPLOY_HOST "
        echo \"$CI_JOB_TOKEN\" | docker login $CI_REGISTRY -u $CI_REGISTRY_USER --password-stdin &&
        docker pull $DOCKER_IMAGE &&
        docker stop my-app || true &&
        docker rm my-app || true &&
        docker run -d --name my-app -p 80:8080 --restart always $DOCKER_IMAGE
      "
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
      when: manual
```

**Где здесь дублирование:**
- `before_script` с SSH-агентом — 7 строк, копируемых в каждый проект.
- `docker login` — повторяется в `build` и `deploy`.
- IP-адрес сервера зашит в переменную `DEPLOY_HOST`.

**Что здесь ещё не так (помимо дублирования):**

- `docker stop ... || true && docker rm ...` — в POSIX shell `&&` и `||` имеют **одинаковый приоритет** и вычисляются слева направо, поэтому выражение разбирается как `(docker stop my-app || true) && docker rm my-app`, а не так, как ожидает читатель, привыкший к приоритету `&&` из учебников по булевой логике. В данном случае цепочка `&&` после `docker rm` теряет смысл: при неудаче `docker rm` следующие команды не выполнятся, но пайплайн не упадёт, потому что `|| true` снял ошибку раньше. Для деплоя корректнее разбить операции на отдельные строки `script` с явными проверками.
- Выполнение `docker login` на целевом хосте требует, чтобы у пользователя деплоя были права на реестр. `$CI_JOB_TOKEN` выдаётся со scope проекта, выполняющего пайплайн, — передавать его наружу по SSH в контексте `known_hosts`-аутентификации стоит осознанно.
- `rules: - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH` без fallback-правила: если условие не выполнено, задание не создаётся вовсе (это корректное поведение `rules`, в отличие от устаревшего `only`).

### Сценарий 2: Генерация nginx-конфига (heredoc boilerplate)

Классический паттерн генерации конфигурационных файлов через heredoc:

```yaml
deploy_nginx:
  stage: deploy
  script:
    - |
      cat > /etc/nginx/conf.d/mr-$CI_MERGE_REQUEST_IID.conf <<EOF
      upstream backend {
          server 127.0.0.1:8080;
      }
      server {
          listen 80;
          server_name mr-$CI_MERGE_REQUEST_IID.review.example.com;
          location / {
              proxy_pass http://backend;
              proxy_set_header Host \$host;
              proxy_set_header X-Real-IP \$remote_addr;
          }
      }
      EOF
    - nginx -s reload
```

**Проблема:** Конфиг nginx зашит в YAML. Изменение прокси-заголовков требует правки в каждом проекте. Дополнительно: после `nginx -s reload` нет проверки валидности конфигурации — при синтаксической ошибке в heredoc nginx не перезапустится, но пайплайн отрапортует об успехе. Корректная последовательность — `nginx -t` перед `reload`.

**Решение (Stage 2):** Вынести конфиг в отдельный шаблон:
```bash
# templates/nginx/reverse_proxy.conf.template
server {
    listen 80;
    server_name ${MR_IID}.review.example.com;
    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

### Сценарий 3: SSH-ключи и known_hosts (Boilerplate)

Паттерн, который повторяется в каждом проекте, использующем SSH-деплой:

```yaml
# Генерация SSH-ключа
generate_key:
  script:
    - ssh-keygen -t ed25519 -C "gitlab-ci-deploy" -f deploy_key -N ""
    # deploy_key (приватный) → в переменную SSH_PRIVATE_KEY
    # deploy_key.pub (публичный) → добавить в authorized_keys

# Деплой с ssh-agent
deploy:
  before_script:
    - apk add --no-cache openssh-client
    - eval $(ssh-agent -s)
    - chmod 600 "$SSH_PRIVATE_KEY"
    - ssh-add "$SSH_PRIVATE_KEY"
    - mkdir -p ~/.ssh && chmod 700 ~/.ssh
    - echo "$SSH_KNOWN_HOSTS" > ~/.ssh/known_hosts
  script:
    - ssh -o StrictHostKeyChecking=no $USER@$HOST "deploy.sh"
```

> [!WARNING]
> **Два дефекта безопасности в этом блоке.**
> 1. `ssh-keygen ... -N ""` создаёт приватный ключ **без пароля** и генерирует его прямо в задании. Результат задания попадает в артефакты и логи на время жизни job'а. Ключ должен создаваться локально у владельца инфраструктуры, а в GitLab передаваться только как переменная типа `File` с флагом `masked` и `protected`.
> 2. `StrictHostKeyChecking=no` отключает проверку подлинности сервера и открывает путь к MITM. Проверка должна выполняться по заранее полученному `known_hosts`, а не отключаться.

**Генерация `known_hosts` (обязательный шаг перед первым деплоем):**
```bash
ssh-keyscan -H <deploy_host>
# → Вывод скопируйте в переменную SSH_KNOWN_HOSTS
```
`SSH_KNOWN_HOSTS` следует хранить как переменную типа `File`, а не как многострочную строку: при хранении в типе `File` значение не попадает в вывод `glab variable list` и не требует ручного экранирования переводов строк.

**Генерация SSH-ключа (правильный порядок действий):**
```bash
# Выполняется локально, вне CI
ssh-keygen -t ed25519 -C "gitlab-ci-deploy" -f deploy_key -N ""
# → deploy_key (приватный) → в переменную SSH_PRIVATE_KEY (тип: File, masked + protected)
# → deploy_key.pub (публичный) → добавьте в ~/.ssh/authorized_keys на целевом сервере
```

### Сценарий 4: Установка системных пакетов и настройка sysctl

Boilerplate для подготовки среды выполнения на серверах:

```yaml
# Дублируется в 15+ проектах для Production-серверов
setup_server:
  stage: prepare
  script:
    - |
      cat > /etc/sysctl.d/99-ci.conf << 'EOF'
      net.core.somaxconn = 65535
      net.ipv4.tcp_max_syn_backlog = 65535
      vm.swappiness = 10
      fs.file-max = 2097152
      EOF
    - sysctl --system
    - apt-get update && apt-get install -y docker.io nginx certbot
```

**Проблема:** Конфигурация sysctl и список пакетов зашиты в YAML. Обновление политики безопасности требует правки каждого проекта.

**Дополнительные дефекты sysadmin-конфигурации в этом фрагменте:**

- `sysctl --system` перечитывает **все** файлы в `/etc/sysctl.d/`, а не только созданный. На хосте с расхождяющимися политиками это приводит к недетерминированному результату; для точечного применения используйте `sysctl -p /etc/sysctl.d/99-ci.conf`.
- Значения `net.core.somaxconn` и `net.ipv4.tcp_max_syn_backlog` дублируют лимиты, которые обычно задаёт `nginx`/`systemd` через сокет-опции. Прежде чем зашивать их в пайплайн, проверьте фактические лимиты на хосте: `ss -lnt` показывает `Send-Q`, обрезанный до `somaxconn`, и расхождение не видно без сверки.
- `apt-get install` без `apt-get upgrade` и без фиксации версий делает сборку невоспроизводимой по той же причине, что и неверсионированный образ.
- Для повторяемого применения sysctl и списка пакетов корректный инструмент — Ansible или конфигурационное управление хостами (например, `ansible.posix.sysctl` и `ansible.builtin.apt`), а не heredoc в CI.

### Сценарий 5: Настройка trusted certificates (CA Bundle)

Boilerplate для добавления корпоративных сертификатов:

```yaml
# Дублируется во всех проектах, работающих с внутренними реестрами
install_ca:
  before_script:
    - |
      cat > /usr/local/share/ca-certificates/internal-ca.crt << 'EOF'
      -----BEGIN CERTIFICATE-----
      MIIDxTCCAq2gAwIBAgIJAJC1...
      -----END CERTIFICATE-----
      EOF
    - update-ca-certificates
    - mkdir -p /etc/docker/certs.d/$CI_REGISTRY
    - cp /usr/local/share/ca-certificates/internal-ca.crt /etc/docker/certs.d/$CI_REGISTRY/ca.crt
```

**Проблема:** Сертификат зашит прямо в YAML. Обновление CA требует правки во всех проектах. Приватный ключ не должен попадать в репозиторий ни в каком виде — ни в base64, ни в heredoc.

**Дополнительные дефекты:**

- На образе на базе Alpine пакет `ca-certificates` может отсутствовать, и `update-ca-certificates` завершится с «command not found» до того, как проблема станет очевидной. Установка пакета должна идти до копирования сертификата.
- `update-ca-certificates` пересобирает весь bundle и печатает предупреждение, если сертификат с истёкшим `notAfter` уже добавлен. Собирать bundle вручную через `cat /usr/local/share/ca-certificates/*.crt > /etc/ssl/certs/ca-certificates.crt` **не следует**: команда перезаписывает файл целиком, и все системные корневые сертификаты, которые туда попали при установке пакета `ca-certificates`, из него исчезают. Результат внешне похож на успех, но TLS-проверка перестаёт работать для любых публичных сервисов. Правильный вариант — только `update-ca-certificates`, а если нужно добавить сертификат вручную, поместить его в `/usr/local/share/ca-certificates/` и дать пакетному скрипту пересобрать bundle.
- Для Docker отдельный каталог `/etc/docker/certs.d/<host>/ca.crt` необходим, только если TLS-сертификат реестра выпущен не доверенным центром; для реестра GitLab на том же инстансе встроенного CA обычно достаточно.

**Решение (Stage 2):** Хранить сертификат в отдельном репозитории и подключать через `include:project` или artifact.

### Сценарий 6: Конфигурация Ansible Vault

Паттерн для хранения пароля Ansible Vault в пайплайне:

```yaml
ansible_deploy:
  stage: deploy
  before_script:
    - pip install ansible
    - echo "$ANSIBLE_VAULT_PASSWORD" > .vault_pass
    - chmod 600 .vault_pass
  script:
    - ansible-playbook -i inventory/ \
        --vault-password-file .vault_pass \
        playbooks/deploy.yml
  after_script:
    - rm -f .vault_pass  # Очистка
```

**Проблема:** `before_script` с `.vault_pass` дублируется в каждом проекте, использующем Ansible.

**Дополнительные дефекты:**

- `pip install ansible` без фиксации версии делает деплой невоспроизводимым; фиксировать нужно и версию `ansible`, и версию `ansible-core`.
- `echo "$ANSIBLE_VAULT_PASSWORD" > .vault_pass` записывает секрет в файл рабочего каталога. `after_script` выполняется в новой оболочке, имеет отдельный таймаут (по умолчанию 5 минут, `RUNNER_AFTER_SCRIPT_TIMEOUT`) и при таймауте не выполняется вовсе. Надёжнее передавать файл через stdin: `printenv ANSIBLE_VAULT_PASSWORD | ansible-playbook --vault-password-file /dev/stdin ...` — тогда секрет не попадает на диск.
- Очистка в `after_script` не является гарантией: при `on_failure` задания файл остаётся до уничтожения рабочей директории, а при отмене задания runner'а `after_script` может не выполниться вовсе.

### Сценарий 7: Мониторинг и метрики через heredoc

Генерация конфигурации Prometheus Pushgateway через heredoc:

Длительность сборки измеряется в `script`, а статус задания — в `after_script`, потому что именно там `CI_JOB_STATUS` имеет конечное значение:

```yaml
report_metrics:
  script:
    - |
      START=$(date +%s)
      # ... полезная работа: сборка, тесты ...
      DURATION=$(( $(date +%s) - START ))
      cat <<EOF | curl -sf --data-binary @- "http://prometheus-pushgateway:9091/metrics/job/frontend-ci/instance/${CI_JOB_ID}"
      # HELP ci_build_duration_seconds Build duration in seconds
      # TYPE ci_build_duration_seconds gauge
      ci_build_duration_seconds ${DURATION}
      EOF
  after_script:
    # CI_JOB_STATUS принимает значения success / failed / canceled, а не числа,
    # поэтому для gauge требуется явное преобразование.
    - |
      if [ "$CI_JOB_STATUS" = "canceled" ]; then exit 0; fi
      if [ "$CI_JOB_STATUS" = "success" ]; then METRIC=1; else METRIC=0; fi
      cat <<EOF | curl -sf --data-binary @- "http://prometheus-pushgateway:9091/metrics/job/frontend-ci/instance/${CI_JOB_ID}"
      # HELP ci_build_last_success Result of the last finished job (1 = success, 0 = failed)
      # TYPE ci_build_last_success gauge
      ci_build_last_success ${METRIC}
      EOF
```

**Что здесь было неверно в исходном boilerplate и почему это важно:**

- Метрика `build_duration_seconds`, заполняемая значением `$(date +%s)`, отдавала **UNIX-время начала**, а не длительность. В Grafane такой ряд выглядит правдоподобно и монотонно растёт, из-за чего расхождение с реальным временем сборки обнаруживается не сразу. Длительность обязана быть разностью двух отметок, снятых в одном блоке `script`.
- `build_success 1` — константа, а не измерение: она не меняется при сбоях, и алерт на неё не срабатывает никогда. Реальный статус задания доступен в переменной `CI_JOB_STATUS` (значения — `success`, `failed`, `canceled`), но её следует читать в `after_script`.
- Подстановка `CI_JOB_STATUS` прямо в тело метрики дала бы нечисловое значение (`ci_build_last_status failed`), что Pushgateway примет, а Prometheus отбросит при разборе. Gauge требует преобразования в 1/0 — этот шаг нельзя пропускать.

> [!WARNING]
> **Две ловушки `after_script`, о которых чаще всего забывают.**
> 1. Команды `after_script` выполняются в **новой оболочке**, отдельной от `before_script` и `script`. Переменные, объявленные в `script` (`START`, `DURATION`), в `after_script` недоступны — получите пустое значение и, как следствие, некорректную метрику. Общие значения передавайте через артефакты или CI/CD-переменные, а не через экспорт переменных оболочки.
> 2. `after_script` не влияет на код выхода задания: даже если он упадёт, задание завершится успешно. И при отмене задания во время выполнения `after_script` переменная `CI_JOB_STATUS` имеет значение `canceled` — рекомендуемый паттерн состоит в проверке этого значения в начале блока и досрочном выходе.

### Сценарий 8: Сравнение Boilerplate и централизованного подхода

**До (Boilerplate):**
```yaml
# Каждый проект содержит 120+ строк идентичного кода
stages: [build, test, deploy]
variables: { DOCKER_DRIVER: overlay2, IMAGE: ... }
.build_job: { image: docker:29.8, services: [...], script: [...] }
build: { extends: .build_job, stage: build }
test: { stage: test, script: [pytest] }
deploy: { stage: deploy, script: [ssh deploy.sh] }
# ... ещё 80 строк
```

**После (Stage 2 — Include):**
```yaml
# .gitlab-ci.yml сокращается до 15-25 строк
include:
  - project: 'shared/ci-templates'
    file: 'templates/docker-build.yml'
    ref: 'refs/tags/v2.1.0'

build:
  extends: .docker_base
  variables:
    IMAGE_NAME: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

Однозначность `ref` — не стилевое предпочтение. Если в репозитории существуют ветка и тег с одинаковым именем, короткое имя `ref` становится неоднозначным, и GitLab CI начинает вести себя непредсказуемо: зафиксированы случаи, когда пайплайн, запущенный для ветки, считался теговым, а переменная `CI_COMMIT_TAG` получала непустое значение для коммита, который тегом не является ([gitlab-org/gitlab#219583](https://gitlab.com/gitlab-org/gitlab/-/issues/219583)). Полное имя референса (`refs/tags/v2.1.0`) снимает неоднозначность по построению. Полный 40-символьный SHA коммита — самый стабильный вариант: он неизменяем по определению, но теряет читаемость и делает обновление шаблона ручной операцией, поэтому на практике используют `refs/tags/` с SemVer.

## Валидация

### Инструменты поиска

Использование GitLab API или локального поиска по коду (`grep`) в зеркалированных репозиториях:

```bash
# Поиск всех проектов, использующих устаревшую версию Docker
grep -rl "image: docker:20.10" ./all-projects/

# Поиск идентичных скриптов логина в реестр (сколько проектов содержат)
grep -rl "docker login -u \$CI_REGISTRY_USER" ./all-projects/ | wc -l

# Поиск дублирования SSH-блоков
grep -rl "eval \$(ssh-agent -s)" ./all-projects/ | wc -l

# Поиск heredoc-паттернов (генерация конфигов)
grep -rl "cat .*<<.*EOF" ./all-projects/ --include="*.yml" | wc -l

# Поиск зашитых IP-адресов (антипаттерн) — с исключением версий вида 1.2.3.4
grep -roE "(^|[^0-9.])([0-9]{1,3}\.){3}[0-9]{1,3}([^0-9.]|$)" ./all-projects/ \
  --include="*.yml" | grep -v "image:" | wc -l

# Проверка наличия центрального репозитория шаблонов
ls -d shared/ci-templates/ 2>/dev/null || echo "NO CENTRAL TEMPLATE REPO"

# Сколько проектов ещё используют устаревшую only/except вместо rules
grep -rlE "^\s+(only|except):" ./all-projects/ --include=".gitlab-ci.yml" | wc -l
```

Флаги `-r` (рекурсивно) и `-l` (только имена файлов) в комбинации дают количество **проектов**, а не количество вхождений — именно эта величина определяет трудоёмкость миграции. Подсчёт вхождений (`wc -l` без `-l` на выводе `grep -r`) завышает оценку в разы и делает план миграции нереалистичным.

### Проверка конфигурации

```bash
# Статическая проверка синтаксиса и схемы текущего .gitlab-ci.yml
glab ci lint

# Полностью слитая конфигурация: все include разрешены, extends развёрнуты,
# !reference подставлены. Это эталон того, что увидит runner
glab ci config compile > expanded.yml

# Имитация создания пайплайна (GitLab 16.11+) с контекстом ветки
glab ci lint --dry-run --ref main

# Список заданий, которые будут созданы
glab ci lint --include-jobs
```

> [!NOTE]
> У `glab ci lint` нет флага `--show-expanded` — такой синтаксис широко тиражируется, но команда его не поддерживает и завершается ошибкой разбора флагов. Раскрытие `include`/`extends`/`!reference` выполняет отдельная команда `glab ci config compile`, которая печатает полностью слитый YAML в stdout. Подробности — в [Валидации и версионировании пайплайнов](../../Advanced/pipeline_validation_and_versioning.md).

Аудит конфигурации соседних проектов выполняется тем же набором команд с указанием репозитория:

```bash
# Проверка удалённого проекта
glab ci lint -R "group/microservice-a"

# Выгрузка раскрытой конфигурации для сравнения с эталоном
glab ci config compile -R "group/microservice-a" > "microservice-a.expanded.yml"
```

Массовая проверка группы выполняется циклом по списку проектов, полученному через API:

```bash
# Получить список проектов группы
glab api "groups/<group_id>/projects?per_page=100&include_subgroups=true" \
  | jq -r '.[].path_with_namespace' > projects.txt

# Проверить каждый проект
while read -r repo; do
  if glab ci lint -R "$repo" > /dev/null 2>&1; then
    echo "OK   $repo"
  else
    echo "FAIL $repo"
  fi
done < projects.txt
```

Дополнительный уровень проверки — встроенный CI Lint API, который возвращает итоговый YAML и выполняет проверку в контексте конкретного события:

```bash
jq -n --rawfile content .gitlab-ci.yml \
  '{content: $content, dry_run: true, include_jobs: true, ref: "main"}' \
  | curl --request POST \
      --header "PRIVATE-TOKEN: $GITLAB_TOKEN" \
      --header "Content-Type: application/json" \
      --data-binary @- \
      "https://gitlab.example.com/api/v4/projects/$CI_PROJECT_ID/ci/lint" \
  | jq '{valid, errors, warnings}'
# → {"valid": true, "errors": [], "warnings": []}
```

Собирать тело запроса через подстановку в строку (`sed 's/"/\\"/g'` или конкатенацию с одинарными кавычками) нельзя: YAML содержит переводы строк и обратные слэши, которые такой способ не экранирует, и на любом реальном файле запрос уходит с невалидным JSON. `jq --rawfile` читает файл как строку и сериализует его корректно.

### Диагностический чек-лист этапа

Проект находится на этапе Boilerplate, если выполняется хотя бы одно условие:

1.  Файл `.gitlab-ci.yml` содержит более 50 строк кода, не считая бизнес-логики (тесты, деплой).
2.  Для создания пайплайна в новом сервисе разработчик открывает старый сервис и делает `Ctrl+C` → `Ctrl+V`.
3.  Обновление версии базового образа (например, `alpine:3.24`) требует создания Merge Request'ов в нескольких репозиториях.
4.  Один и тот же `before_script` (SSH, Docker, Ansible) встречается более чем в 3 проектах.
5.  В `.gitlab-ci.yml` есть heredoc-блоки (`cat > file << 'EOF'`) с зашитыми конфигурациями (nginx, sysctl, certificates).
6.  YAML Anchors (`&`/`*`) используются в расчёте на перенос между файлами — их область действия ограничена одним файлом.
7.  Нет выделенного репозитория для шаблонов (shared/ci-templates).
8.  Конфликты имен переменных между шаблонами разных команд решаются через переименование, а не через изоляцию (`$[[ inputs ]]`).
9.  Используются глобальные `before_script`, `image`, `services`, `cache` на верхнем уровне файла вместо блока `default:`.
10. Присутствуют `only` / `except` — устаревшие директивы, заменённые на `rules`.

Пункты 9 и 10 добавлены потому, что оба состояния — прямое наследие boilerplate-подхода, и оба фиксируются в ходе миграции «бесплатно», без выделения отдельного проекта.

## Устранение неполадок: Старт миграции

| Трудность | Описание | Первые шаги |
| :--- | :--- | :--- |
| **Огромный объем работы** | Невозможно обновить 100 проектов сразу. | Начните с создания одного шаблона для самого частого типа задач (например, `docker-build`). |
| **Сопротивление команд** | Разработчики привыкли «владеть» своим пайплайном. | Продавайте переход через уменьшение количества кода в их репозиториях (120 строк → 15 строк). |
| **Разные версии инструментов** | Пайплайны уже слишком сильно разошлись (Drift). | Сначала приведите их к единому виду вручную, прежде чем выносить в шаблон. |
| **Нет центрального шаблона** | Не выделен репозиторий для шаблонов. | Создайте `shared/ci-templates` с базовым `docker-build.yml` и `ssh-deploy.yml`. |
| **Конфликты имен заданий** | Шаблон определяет задание `build`, которое уже есть в проекте. | Используйте префиксы в именах заданий или `inputs` для переименования. |
| **Устаревшие YAML Anchors** | Используются `&`/`*` вместо `!reference`. | Замените `*anchor_name` на `!reference [.job_name, key]`. YAML Anchors не работают между файлами. |
| **Отсутствие версионирования** | Шаблоны подключаются через ветку `main`, а не теги. | Внедрите SemVer: `ref: 'refs/tags/v2.1.0'` вместо `ref: 'main'`. |
| **Незнание `default` блока** | Глобальные `before_script`, `image`, `services`, `cache` на верхнем уровне. | Перенесите в `default:` — эти глобальные директивы устарели в пользу `default`. |
| **Устаревшие `only` / `except`** | Управление условиями запуска через `only`/`except`. | Переведите на `rules` — `only` и `except` устарели и могут быть удалены. |
| **Ложное ожидание от `default`** | Ожидается слияние `default` с настройками задания. | Помните: `default` не сливается с заданием — задайте ключевое слово в задании явно. |
| **Секреты в variables** | SSH-ключи, пароли зашиты в переменные проекта. | Используйте тип `File` для SSH-ключей и `known_hosts`, маскируйте секреты (`masked` + `protected`). |
| **Токен в аргументах команды** | `docker login -p $CI_JOB_TOKEN` и подобные конструкции. | Передавайте секрет через stdin: `echo "$TOKEN" \| docker login --password-stdin`. |

## Лучшие практики и очистка

### Порядок миграции

1. **Зафиксировать baseline.** Сохранить `glab ci config compile` по каждому проекту. Это и есть точка отката: без неё «откатить миграцию» означает «восстановить то, что было», а восстановить нечего.
2. **Выбрать один сценарий.** Начинать с самого частого блока (обычно — сборка образа), а не с самого сложного. Первый успешный шаблок задаёт команду и регламент для остальных.
3. **Версионировать с первого дня.** `ref: 'refs/tags/v0.1.0'` создаётся до подключения, а не после. Шаблон без тега не имеет отката.
4. **Мигрировать инкрементально, по одному проекту.** Каждый проект — отдельный Merge Request с проверкой `glab ci config compile` в CI.
5. **Не удалять старый код в том же MR.** Сначала подключить шаблон рядом со старым кодом и убедиться, что результат идентичен, затем удалять. Одновременная замена усложняет расследование инцидента.
6. **Закрыть путь возврата.** После того как N проектов переведены, boilerplate-вариант в них больше не нужен — но только после того, как это отражено в документации проекта.

### Гигиена и предотвращение регрессии

| Практика | Как реализовать | Что предотвращает |
| :--- | :--- | :--- |
| Линт конфигурации в pre-push | `glab ci lint` в локальном hook или в pre-commit | Синтаксические ошибки до появления в MR |
| Проверка слитой конфигурации | `glab ci config compile > expanded.yml && git diff --exit-code expanded.yml` в CI | Непреднамеренное изменение итогового пайплайна шаблоном |
| Политика на уровне группы | [`Pipeline Execution Policies`](../../Advanced/pipeline_validation_and_versioning.md) для принудительного включения заданий безопасности | Обход обязательных проверок на уровне проекта |
| Единый формат имён заданий | Шаблон задаёт `stage` и `tags`, проект — только `script` | Расхождение в разметке, из-за которого задание не попадает на нужный runner |
| Регулярный пересмотр версий образов | Поиск устаревших тегов (см. [Валидацию](#валидация)) | Образы вне линии поддержки в работающих пайплайнах |
| Учёт дрейфа шаблонов | Сравнение `expanded.yml` между проектами одной команды | Расхождение, возникшее из-за ручной правки в одном проекте |

### Откат и очистка

Откат миграции выполняется на уровне Merge Request'а или тега шаблона:

```bash
# 1. Найти коммит, в котором проект переведён на шаблон
git log --oneline -- .gitlab-ci.yml | grep -i "migrate\|шаблон\|template"
# → a1b2c3d ci: migrate to ci-templates

# 2. Откатить изменения файла конфигурации на этом коммите
git revert a1b2c3d
# → Восстановлена прежняя версия .gitlab-ci.yml

# 3. Проверить результат до отправки
glab ci lint
glab ci config compile > /tmp/after-revert.yml
```

Откат самого шаблона — отдельная операция: удалить тег `v2.1.0` недостаточно, поскольку подключения выполняются по имени тега, и без него пайплайн перестаёт разрешаться. Нужно выпустить новый тег (`v2.1.1`) с исправлением и оставить старый — обратная совместимость подключений важнее чистоты репозитория.

Очистка после завершения миграции:

- Удалить локальные копии `expanded.yml` и временные выгрузки конфигурации — они не должны попадать в коммиты.
- Удалить из проекта неиспользуемые скрытые задания (`.name`), оставшиеся после перехода на внешние шаблоны: они не выполняются, но засоряют конфигурацию и сбивают с толку при чтении.
- Снять с GitLab-переменных устаревшие `SSH_KNOWN_HOSTS` и `DEPLOY_*`, если деплой переведён на другой механизм. Переменные остаются в интерфейсе годами, и их наличие намекает, что путь деплоя прежний.

## Преимущества и недостатки

### Преимущества этапа Boilerplate

| Преимущество | Описание |
| :--- | :--- |
| **Нулевой порог входа** | Не требует знания `extends`, `!reference`, `include` или SemVer. |
| **Максимальная гибкость** | Каждый проект может настроить пайплайн под себя без ограничений шаблонов. |
| **Быстрый старт** | Новый сервис можно запустить за минуты, скопировав `.gitlab-ci.yml` из соседнего проекта. |
| **Простая отладка** | Весь код пайплайна в одном файле, не нужно разбирать цепочки `include`/`extends`. |
| **Отсутствие каскадных сбоев** | Изменение в одном проекте не может сломать чужие сборки. |

Последнее преимущество — оборотная сторона отсутствия связности: оно достигается именно за счёт того, что изменения не распространяются, и исчезает при переходе на централизацию.

### Недостатки этапа Boilerplate

| Недостаток | Описание | Масштаб проблемы |
| :--- | :--- | :--- |
| **O(N) обновления** | Любое изменение шаблона требует правки N репозиториев. | Линейный рост с числом проектов |
| **Configuration Drift** | Пайплайны расходятся из-за локальных правок. | Непредсказуемое поведение |
| **Уязвимости** | Баг/уязвимость в шаблоне присутствует во всех проектах. | Критический риск безопасности |
| **Фрагментация среды** | Разные версии инструментов в разных проектах. | Невозможность кэширования |
| **Нет аудита** | Невозможно узнать, кто и когда изменил логику сборки. | Отсутствие трассировки |
| **Блокировка инноваций** | Замена инструмента (DinD → Kaniko) — проект на месяцы. | Торможение развития |
| **Дублирование конфигов** | heredoc-блоки с nginx, sysctl, certs копируются в каждый проект. | Нарушение DRY |
| **Нет типизации** | Ошибки в переменных ловятся только в runtime (после запуска). | Медленная обратная связь |
| **Дефекты, размножающиеся копированием** | Ошибка `-p` вместо `--password-stdin`, `StrictHostKeyChecking=no`, неверная метрика длительности тиражируются вместе с кодом. | Один дефект → N неисправленных пайплайнов |
| **Невозможность отката** | Нет общего идентификатора версии конфигурации. | Восстановление только вручную, по N MR |
