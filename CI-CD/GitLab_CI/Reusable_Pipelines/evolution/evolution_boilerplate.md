# Проблема дублирования кода в GitLab CI (Boilerplate)

## Определения

**Boilerplate-код** — повторяющаяся конфигурация, которая копируется в каждый проект без изменений или с минимальными правками. В контексте GitLab CI это идентичные блоки заданий (jobs) в файлах `.gitlab-ci.yml` разных репозиториев.

**Контекст этапа:** Начальная точка развития CI/CD в организации, когда каждый микросервис или проект владеет собственной копией логики сборки и доставки, что приводит к фрагментации инфраструктурных знаний.

## Базовые концепции

### Причины возникновения дублирования

| Причина | Описание |
| :--- | :--- |
| **Отсутствие централизации** | Отсутствует единая библиотека проверенных шаблонов. |
| **Принцип «Copy-Paste»** | Разработчики копируют проверенный `.gitlab-ci.yml` из старых проектов в новые без глубокого анализа. |
| **Низкий порог входа** | На старте проще скопировать 20 строк кода, чем проектировать абстракции. |
| **Карго-культ** | Копирование настроек (например, флагов оптимизации или переменных) без понимания их влияния на текущий проект. |

### Типичный пример boilerplate-кода

Ниже приведен пример стандартной сборки, которая в неизменном виде встречается в десятках проектов организации.

```yaml
# .gitlab-ci.yml в каждом из 10+ проектов
build-docker-image:
  stage: build
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
```

## Практические сценарии

### Риски и последствия дублирования

| Тип риска | Последствие |
| :--- | :--- |
| **Технический долг** | Изменение версии Docker или политики безопасности требует ручного обновления сотен репозиториев. |
| **Безопасность** | Уязвимость, найденная в одном скрипте сборки, автоматически распространяется на всю экосистему и остается там месяцами. |
| **Сложность аудита** | Невозможно быстро проверить соответствие всех пайплайнов корпоративным стандартам. |
| **Дрейф конфигураций** | Проекты постепенно модифицируют свои копии, что делает невозможным внедрение общих платформенных инструментов в будущем. |

### Психологический эффект для команды

1. **Страх изменений:** DevOps-инженеры боятся обновлять базовые образы или инструменты, так как не могут гарантировать результат в 50+ разных проектах.
2. **Демотивация:** Разработчики тратят время на отладку инфраструктурного кода, который уже был отлажен в соседнем отделе.
3. **Фрагментация знаний:** Знания о пайплайне "запираются" внутри конкретного проекта, а не становятся частью платформенного опыта.
