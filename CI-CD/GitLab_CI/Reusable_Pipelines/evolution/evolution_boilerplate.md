# Проблема дублирования кода в GitLab CI (Boilerplate)

## Определения

**Boilerplate-код** — повторяющаяся конфигурация, которая копируется в каждый проект без изменений или с минимальными правками. В контексте GitLab CI это идентичные блоки заданий (jobs), скрипты сборки и переменные в файлах `.gitlab-ci.yml` разных репозиториев.

**Configuration Drift (Дрейф конфигураций)** — состояние, при котором идентичные изначально пайплайны начинают постепенно различаться из-за локальных правок в проектах, что делает невозможным их централизованное обновление.

**Контекст этапа:** Начальная точка развития CI/CD в организации. Каждый микросервис или проект владеет собственной копией логики сборки и доставки, что приводит к фрагментации инфраструктурных знаний и накоплению технического долга.

## Базовые концепции

### Причины возникновения дублирования

| Причина | Описание |
| :--- | :--- |
| **Отсутствие централизации** | Отсутствует единая библиотека проверенных и одобренных платформенной командой шаблонов. |
| **Принцип «Copy-Paste»** | Разработчики копируют проверенный `.gitlab-ci.yml` из старых проектов в новые для экономии времени. |
| **Низкий порог входа** | На старте проще скопировать 20 строк кода, чем проектировать абстракции и управлять зависимостями. |
| **Карго-культ** | Копирование настроек (флагов компиляции, параметров кэширования) без понимания их влияния на конкретный стек проекта. |

### Типичный пример boilerplate-кода

Пример стандартной сборки, которая в неизменном виде встречается в десятках проектов. Любое изменение (например, добавление `--build-arg` для безопасности) потребует правок в каждом репозитории.

```yaml
# .gitlab-ci.yml в каждом из 10+ проектов
build-docker-image:
  stage: build
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
```

## Практические сценарии

### Риски и последствия (Белые пятна)

1.  **Technical Sprawl (Техническое разрастание):**
    Использование разных версий инструментов (Docker, линтеры, SDK) в проектах одного типа. Это усложняет отладку и поддержку инфраструктуры (Runner'ов).
2.  **Security Gaps (Пробелы в безопасности):**
    Если в скрипте сборки допущена ошибка (например, незащищенный экспорт переменных), она масштабируется на все проекты. Исправление такой ошибки превращается в многонедельный марафон по всем репозиториям.
3.  **Сложность внедрения инноваций:**
    Переход на более эффективные инструменты (например, замена Docker на Kaniko для безопасности) становится невозможным из-за объема ручной работы по переписыванию пайплайнов.
4.  **Фрагментация экспертизы:**
    Знания о том, "почему это работает", остаются у конкретных разработчиков, а не консолидируются в платформенной команде.

### Психологический эффект для команды

*   **Страх изменений:** DevOps-инженеры избегают обновления глобальных Runner'ов или базовых образов, так как не могут предсказать последствия для сотен уникальных (но похожих) пайплайнов.
*   **Демотивация:** Высококвалифицированные инженеры тратят время на рутинную отладку идентичного инфраструктурного кода.
*   **Иллюзия стабильности:** Кажущаяся "простота" копирования на самом деле скрывает огромные затраты на поддержку в долгосрочной перспективе.
