# Проблема дублирования кода в GitLab CI (Boilerplate)

## Определения

**Boilerplate-код** — повторяющаяся конфигурация, которая копируется в каждый проект без изменений. В контексте GitLab CI — идентичные job-конфигурации в `.gitlab-ci.yml` разных проектов.

**Контекст проблемы:** Команда разрабатывает несколько микросервисов, для каждого требуется одинаковая конфигурация сборки Docker-образов.

## Базовые концепции

### Почему возникает boilerplate

| Причина | Описание |
| :--- | :--- |
| **Отсутствие централизации** | Нет единого репозитория шаблонов |
| **Копирование конфигурации** | Разработчики копируют `.gitlab-ci.yml` между проектами |
| **Незнание механизмов переиспользования** | Отсутствие опыта с `include`, `extends` |

### Пример boilerplate-кода

```yaml
# .gitlab-ci.yml в каждом из 10+ проектов
build-docker-image:
  stage: build
  image: docker:20.10
  services:
    - docker:20.10-dind
  variables:
    IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
```

## Практические сценарии

### Проблемы boilerplate-подхода

| Проблема | Описание |
| :--- | :--- |
| **Сложность поддержки** | При изменении версии Docker или логики сборки требуется править 10+ файлов |
| **Человеческий фактор** | При копировании легко допустить ошибку (опечатка, устаревшая версия) |
| **Загромождение** | `.gitlab-ci.yml` становится большим, трудным для чтения |
| **Отсутствие стандартизации** | Каждый проект может иметь свою версию конфигурации |

### Последствия для команды

1. **Время на обновления:** Изменение в 10 проектах занимает часы вместо минут
2. **Дрейф конфигураций:** Проекты постепенно расходятся по версиям и настройкам
3. **Сложность онбординга:** Новым разработчикам трудно понять, какая конфигурация актуальна
