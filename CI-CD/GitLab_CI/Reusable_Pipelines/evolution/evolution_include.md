# Централизация шаблонов через механизм include

**Актуально для:** GitLab CI 19.x; Docker 29.x (DinD); Kubernetes 1.37.x.

## Определения

**`include`** — ключевой механизм GitLab CI/CD для композиции конфигурационных файлов. Позволяет подключать внешние YAML-ресурсы (локальные файлы, проекты, удалённые URL, встроенные шаблоны GitLab и компоненты каталога), разделяя монолитные описания пайплайнов на логические, повторно используемые модули. Обработка `include` происходит **первым этапом** компиляции пайплайна — до `extends`, `inputs` и валидации.

**Централизация шаблонов** — второй качественный этап эволюции CI/CD, направленный на устранение дублирования конфигурации путем выноса повторяющейся логики в единый репозиторий-библиотеку. Этот подход превращает «одноразовые» скрипты в стандартизированные сервисы сборки и доставки.

**Configuration Drift (Расхождение конфигураций)** — проблема, при которой пайплайны разных проектов начинают сильно отличаться друг от друга из-за ручного копирования и локальных правок. Массовое обновление стандартов безопасности становится невозможным без централизации.

**Контекст этапа:** Решение критических проблем [этапа Boilerplate](./evolution_boilerplate.md), таких как невозможность быстрого внедрения стандартов безопасности и огромные трудозатраты на поддержку сотен идентичных файлов `.gitlab-ci.yml`.

```
│       сборки образов      сканирования    деплоя         │

         │                   │                │
         │ include:project   │ include:       │ include:
         │ (ref: v1.5.2)     │ template       │ component
         ▼                   ▼                ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Сервис А    │  │  Сервис Б    │  │  Сервис N    │
│  .gitlab-ci  │  │  .gitlab-ci  │  │  .gitlab-ci  │

└──────────────┘  └──────────────┘  └──────────────┘
```

## Эволюционное преимущество перед предыдущим этапом

На этапе [Boilerplate](./evolution_boilerplate.md) каждый проект содержал полную копию CI/CD-конфигурации. При изменении стандарта (например, добавлении сканера безопасности) требовалось вручную править сотни репозиториев — процесс, занимающий недели и подверженный ошибкам. `include` решает эту проблему, вводя модель «подключай и используй».

| Характеристика | Этап 1 (Boilerplate) | Этап 2 (Include) |
| :--- | :--- | :--- |
| **Хранение логики** | В каждом проекте (дублирование) | В центральном репозитории (эталон) |
| **Обновление стандарта** | Ручные правки в сотнях репозиториев | Одна правка в центральном шаблоне |
| **Версионирование** | Неуправляемое (каждый проект живёт своей жизнью) | Git-теги, SemVer, фиксация через `ref` |
| **Время внедрения патча** | Дни–недели (массовый пр). Часы (Canary через переменные версий) | Мгновенно (для проектов без фиксации на SHA) |
| **Configuration Drift** | Неизбежен со временем | Минимален (централизованное управление) |
| **Кастомизация** | Полная (каждый проект уникален) | Ограничена (шаблон «монолитный» без `extends`) |
| **Стоимость ошибки** | Локальная (только один проект) | Глобальная (ошибка в шаблоне ломает все проекты) |

**Ключевой переход:** от «каждый проект содержит свой CI» к «проекты подключают общий CI». Ценою этого перехода становится жёсткость шаблонов — решается на следующем этапе ([extends](./evolution_extends.md)).

## Практики эксплуатации библиотеки шаблонов (SRE/DevOps)

### Версионирование, роллаут и откат

- Каждая ревизия шаблона — SemVer-тег. Продовые пайплайны используют только теги (`ref: vX.Y.Z`), а не ветки.
- Внедряйте новую ревизию поэтапно: пилотный проект → группа проектов → все потребители. Для этого держите переменную версии шаблона на уровне группы (например, `CI_TEMPLATES_REF`) и переключайте потребителей одним изменением.
- Откат — это переключение `ref` на предыдущий тег. Держите минимум две последних поддерживаемых ревизии для быстрого плана отката.
- Брейкинг-изменения (переименование переменной, удаление ключа шаблона) анонсируйте в changelog и выпускайте мажорной версией — см. `evolution_extends.md`.

### Непрерывное тестирование самих шаблонов

- Собственный CI у библиотеки шаблонов: на каждый MR прогоняйте `glab ci config compile` и сверяйте раскрытый YAML с эталоном.
- Добавьте smoke-тест пилотного проекта: после публикации нового тега запустите тестовый пайплайн потребителя и проверьте его прохождение до роската на всех.
- Перед обновлением используйте `include:rules` + `CI_COMMIT_REF_NAME` для пробного включения новых шаблонов в окружении staging.

### Наблюдаемость и аудит (SRE)

- Логируйте номер версии шаблона в каждом пайплайне: `variables: TEMPLATE_VERSION: v2.4.0` + `echo "template: $TEMPLATE_VERSION"` — по логам сразу видно, на каких ревизиях шаблонов построен пайплайн.
- Ведите реестр потребителей (проект → используемый `ref`), чтобы при аудите безопасности понимать радиус действия уязвимого шаблона.
- Экспорт: держите актуальный экспорт полной конфигурации (`glab ci config compile`) в артефактах для аудита и воспроизведения состояния пайплайна.

### Очистка

- Удаляйте неиспользуемые шаблоны и мёртвые git-теги: поиск ссылок на шаблон (`rg "ref: v1\\.` . --glob '.gitlab-ci.yml'`) показывает потребителей; отсутствие ссылок → кандидат на удаление.
- После миграции потребителей на новый `ref` отключайте старые версии шаблонов политиками очистки, а не разовым удалением — внезапное удаление тега ломает работающие пайплайны.
- Мигрируйте устаревшие инструменты в шаблонах централизованно (как переход Docker-in-Docker → Kaniko), сверяя образ по SSoT-файлам контейнеров.
