# Централизация шаблонов через `include:project`

## Определения

**Централизация шаблонов** — второй этап эволюции CI/CD пайплайнов, направленный на вынос повторяющейся конфигурации из локальных проектов в единый репозиторий-библиотеку. Это первый шаг к превращению CI/CD из набора скриптов в управляемый сервис.

**`include:project`** — директива GitLab CI, позволяющая подключать YAML-файлы из других репозиториев в рамках одного инстанса GitLab. Это основной инструмент для создания корпоративных стандартов сборки и деплоя.

**Контекст этапа:** Решение проблемы "копипасты" и расхождения конфигураций (Configuration Drift), возникших на этапе [Boilerplate](./evolution_boilerplate.md).

## Базовые концепции

### Архитектура централизованного подхода

Вместо того чтобы каждый проект владел собственной реализацией процесса, он "арендует" её у центрального репозитория. Это разделяет ответственность: DevOps-команда управляет шаблонами в `ci-templates`, а разработчики используют их в своих проектах.

```text
┌─────────────────────────────────────────────────────────┐
│  Библиотека шаблонов: group/ci-templates                │
│  └── docker-build.yml (авторитетный источник логики)    │
└─────────────────────────────────────────────────────────┘
                          |
                          | include:project (ref: tag)
                          V
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Проект 1    │  │  Проект 2    │  │  Проект N    │
│  .gitlab-ci  │  │  .gitlab-ci  │  │  .gitlab-ci  │
└──────────────┘  └──────────────┘  └──────────────┘
```

### Принцип "Единого стандарта"

Централизация позволяет DevOps-инженерам обновлять логику сразу во всех проектах. Если меняется стандарт безопасности (например, необходимо добавить сканирование образов), изменения вносятся в один файл в `group/ci-templates`, и все проекты получают обновление автоматически (или при обновлении версии).

**Стратегии версионирования (Критически важно):**
Использование `ref: master` или `ref: main` — главная ошибка на этом этапе. Любое изменение в центральном шаблоне может мгновенно сломать сборку во всей организации.

1.  **Git-теги (Рекомендуется):** Фиксация стабильных версий (`ref: v1.2.0`). Позволяет проектам обновляться контролируемо.
2.  **Commit SHA:** Максимальная стабильность, исключающая подмену тегов.
3.  **Ветки:** Допустимо только для окружений разработки (например, `ref: dev-feature`).

## Практические сценарии

### Создание эталонного шаблона

**Репозиторий:** `group/ci-templates`  
**Файл:** `docker-build.yml`

```yaml
# ci-templates/docker-build.yml
# Использование скрытого задания для предотвращения автозапуска
.docker-build-base:
  stage: build
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

### Подключение шаблона в проекте

Локальный `.gitlab-ci.yml` становится декларативным. Он определяет *что* делать, а не *как*.

```yaml
# .gitlab-ci.yml проекта
include:
  - project: 'group/ci-templates'
    ref: v1.5.0 # Фиксация версии для стабильности
    file: '/docker-build.yml'

stages:
  - build

# Активация задания из шаблона
build-app:
  extends: .docker-build-base
```

### Технические нюансы и ограничения

*   **Лимиты вложенности:** GitLab ограничивает глубину вложенных `include` (до 100 файлов), что важно учитывать при создании сложных иерархий.
*   **Конфликты имен:** Если локальный проект определяет задание с тем же именем, что и в `include`, локальное задание переопределит параметры шаблона (Merge behavior).
*   **Доступность:** Проект, подключающий шаблоны, должен иметь права доступа к репозиторию `ci-templates` (обычно через членство в группе или public доступ).

### Преимущества и недостатки

| Характеристика | Описание |
| :--- | :--- |
| **Масштабируемость** | Один инженер может поддерживать пайплайны для 100+ проектов. |
| **Стандартизация** | Гарантия того, что все проекты собираются по единому одобренному пайплайну. |
| **Жесткость (Минус)** | Шаблоны часто становятся слишком сложными из-за попыток угодить всем проектам через `if/else` в скриптах. |
| **Configuration Drift** | Проекты могут "застревать" на старых тегах шаблонов, требуя аудита версий. |
