# Централизация шаблонов через механизм include:project

## Определения

**Централизация шаблонов** — второй качественный этап эволюции CI/CD, направленный на устранение дублирования конфигурации путем выноса повторяющейся логики в единый репозиторий-библиотеку. Этот подход превращает «одноразовые» скрипты в стандартизированные сервисы сборки и доставки.

**`include:project`** — директива GitLab CI для подключения YAML-файлов из других репозиториев в рамках одного инстанса GitLab. Она позволяет создавать общие библиотеки заданий, которые версионируются независимо от кода приложений.

**Configuration Drift (Расхождение конфигураций)** — проблема, при которой пайплайны разных проектов начинают сильно отличаться друг от друга из-за ручного копирования и локальных правок, что делает массовое обновление инфраструктуры невозможным.

**Контекст этапа:** Решение критических проблем [этапа Boilerplate](./evolution_boilerplate.md), таких как невозможность быстрого внедрения стандартов безопасности и огромные трудозатраты на поддержку сотен идентичных файлов `.gitlab-ci.yml`.

## Базовые концепции

### Архитектура «CI/CD как сервис»

В этой модели ответственность четко разделена:
- **DevOps-команда:** управляет репозиторием `shared/ci-templates`, обеспечивая стабильность, безопасность и актуальность инструментов сборки.
- **Разработчики:** выступают потребителями, подключая нужные модули и фокусируясь на бизнес-логике приложения.

```text
┌───────────────────────────────────────────────────────────┐
│  Центральная библиотека: shared/ci-templates              │
│  └── docker-build.yml (SSoT для логики сборки)            │
└───────────────────────────────────────────────────────────┘
                          │
                          │ include:project (ref: tag/SHA)
                          ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Сервис А    │  │  Сервис Б    │  │  Сервис N    │
│  .gitlab-ci  │  │  .gitlab-ci  │  │  .gitlab-ci  │
└──────────────┘  └──────────────┘  └──────────────┘
```

### Стратегии версионирования и стабильности

Использование `ref: master` или `ref: main` категорически не рекомендуется для промышленной эксплуатации. Любое изменение в центральном файле может мгновенно привести к остановке всех сборок в компании.

1.  **Git-теги (Золотой стандарт):** Фиксация версии через семантическое версионирование (`ref: v2.1.0`). Позволяет проектам обновляться планомерно после тестирования новой версии шаблона.
2.  **Commit SHA:** Максимальный уровень безопасности и неизменности. Исключает риск «переповешивания» тега на другой коммит.
3.  **Переменные версий:** Управление версией шаблона через CI-переменные проекта, что упрощает массовое обновление (Canary Rollout для CI).

## Предварительные условия

Для внедрения централизации необходимо:
- **Доступ к репозиторию:** Проекты-потребители должны иметь права на чтение (`Reporter`+) репозитория с шаблонами. Для приватных групп может потребоваться настройка `Token Access`.
- **Единый инстанс:** Директива `project` работает только в пределах одного инстанса GitLab. Для внешних подключений используется `include:remote`.
- **Глобальные переменные:** Наличие в проектах-потребителях предопределенных переменных, которые ожидает шаблон (например, `$CI_REGISTRY_IMAGE`).

## Практические сценарии

### Сценарий 1: Создание переиспользуемого модуля сборки

В библиотеке создается шаблон, использующий скрытые задания (`.job_name`) для предотвращения автоматического запуска при подключении.

```yaml
# shared/ci-templates/docker-build.yml
.docker-build-base:
  stage: build
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    DOCKER_DRIVER: overlay2
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - docker push $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
```

### Сценарий 2: Декларативное использование в проекте

Файл `.gitlab-ci.yml` проекта становится максимально лаконичным, описывая только этапы и подключаемые модули.

```yaml
# my-app/.gitlab-ci.yml
include:
  - project: 'shared/ci-templates'
    ref: 'v1.5.2'
    file: '/docker-build.yml'

stages:
  - build
  - test
  - deploy

# Активация задания через наследование
build-docker-image:
  extends: .docker-build-base
```

### Сценарий 3: Условное подключение (Edge Case)

Использование `rules` внутри `include` позволяет подключать шаблоны только при определенных условиях (например, наличие файла или специфическое окружение).

```yaml
include:
  - project: 'shared/ci-templates'
    file: '/security-scanners.yml'
    rules:
      - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

## Валидация

Для проверки корректности подключения и развертывания шаблонов:
1.  **Pipeline Editor (Merged YAML):** Используйте вкладку «View merged YAML» в редакторе пайплайнов. Это единственный способ увидеть финальную конфигурацию, которую будет выполнять Runner.
2.  **GitLab CLI (`glab`):** Команда `glab ci lint --show-expanded` позволяет получить развернутый YAML прямо в терминале.
3.  **Trace variables:** Проверьте, что переменные из шаблона корректно переопределяются локальными значениями.

## Устранение неполадок

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Included file not found` | Неверный путь к файлу или опечатка в имени проекта. | Проверьте путь от корня репозитория шаблонов и Visibility проекта. |
| `Job name conflict` | Задание в проекте имеет то же имя, что и в `include`. | Используйте скрытые задания в шаблонах или префиксы в именах. |
| `Project not found` | У Runner или пользователя нет прав на чтение репозитория шаблонов. | Проверьте настройки `Token Access` в репозитории шаблонов. |
| `Include limit exceeded` | Глубина вложенности `include` превысила 100 уровней. | Проведите рефакторинг иерархии, избегайте циклических подключений. |

## Преимущества и недостатки подхода

| Характеристика | Описание |
| :--- | :--- |
| **Масштабируемость** | Возможность внедрять критические патчи безопасности во все проекты одной правкой. |
| **Чистота кода** | Удаление сотен строк YAML-кода из прикладных репозиториев. |
| **Жесткость (Минус)** | Сложность адаптации «монолитного» шаблона под уникальные нужды проекта без `extends`. |
| **Скрытые зависимости** | Падение центрального репозитория или ошибки в нем блокируют работу всей компании. |
