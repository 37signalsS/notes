# Централизация шаблонов через `include:project`

## Определения

**Централизация шаблонов** — второй этап эволюции CI/CD пайплайнов, направленный на вынос повторяющейся конфигурации из локальных проектов в единый репозиторий-библиотеку.

**Контекст этапа:** Переход от копирования YAML-кода (Stage 1: [Boilerplate](./evolution_boilerplate.md)) к использованию механизма [include:project](../include_keyword.md#includeproject) для переиспользования логики сборки, тестирования и деплоя.

## Базовые концепции

### Архитектура централизованного подхода

Вместо того чтобы каждый проект владел собственной реализацией процесса, он "арендует" её у центрального репозитория.

```text
┌─────────────────────────────────────────────────────────┐
│  Библиотека шаблонов: group/ci-templates                │
│  └── docker-build.yml (авторитетный источник логики)    │
└─────────────────────────────────────────────────────────┘
                          |
                          | include:project (ref: tag)
                          V
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Проект 1    │  │  Проект 2    │  │  Проект N    │
│  .gitlab-ci  │  │  .gitlab-ci  │  │  .gitlab-ci  │
└──────────────┘  └──────────────┘  └──────────────┘
```

### Принцип "Единого стандарта"

Централизация позволяет DevOps-инженерам обновлять логику сразу во всех проектах. Если меняется стандарт сборки или параметры безопасности, изменения вносятся в один файл в `group/ci-templates`.

**Версионирование (Критически важно):**
Использование `ref: master` или `ref: main` является антипаттерном на этом этапе. Любое изменение в центральном шаблоне может мгновенно "уронить" сотни пайплайнов в организации.
- **Рекомендация:** Всегда фиксируйте версию через теги (`ref: v1.2.0`) или конкретные commit SHA.

## Практические сценарии

### Создание эталонного шаблона

**Репозиторий:** `group/ci-templates`  
**Файл:** `docker-build.yml`

```yaml
# ci-templates/docker-build.yml
build-docker-image:
  stage: docker-build
  image: docker:27.0
  services:
    - docker:27.0-dind
  variables:
    DOCKER_TLS_CERTDIR: "/certs"
    IMAGE_TAG: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_JOB_TOKEN $CI_REGISTRY
    - docker build -t $IMAGE_TAG .
    - docker push $IMAGE_TAG
```

### Подключение шаблона в проекте

В файле `.gitlab-ci.yml` целевого проекта код сокращается до минимума.

```yaml
# .gitlab-ci.yml проекта
stages:
  - docker-build

include:
  - project: 'group/ci-templates'
    ref: v1.0.0 # Стабильная версия
    file: '/docker-build.yml'
```

### Преимущества и недостатки

| Характеристика | Описание |
| :--- | :--- |
| **Централизация** | Стандартизация процессов во всей компании. Один фикс исправляет проблему везде. |
| **Чистота кода** | Локальный `.gitlab-ci.yml` становится декларативным и коротким. |
| **Жесткость** | Проектам сложно изменить одну команду внутри шаблона (решается на [следующем этапе](./evolution_extends.md)). |
| **Риск регрессий** | Ошибки в шаблоне без версионирования блокируют работу всех команд. |
