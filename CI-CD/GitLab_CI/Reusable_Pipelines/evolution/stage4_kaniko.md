# Абстрагирование деталей реализации с Kaniko

## Определения

**Kaniko** — инструмент для сборки Docker-образов в Kubernetes и CI/CD без необходимости в привилегированном режиме. Разработан Google.

**Абстрагирование деталей реализации** — подход, при котором внутренняя реализация шаблона скрывается от потребителей. Изменения в шаблоне не требуют изменений в проектах.

**Контекст этапа:** Решение проблемы безопасности `docker:dind` (требует `privileged`) через переход на Kaniko в централизованном шаблоне.

## Базовые концепции

### Почему Kaniko безопаснее `docker:dind`

| Аспект | `docker:dind` | Kaniko |
| :--- | :--- | :--- |
| **Привилегии** | Требует `privileged: true` | Работает без привилегий |
| **Изоляция** | Полный Docker-демон | Только сборка образа |
| **Кэширование** | Через Docker-слой | Через отдельный репозиторий |
| **Безопасность** | Потенциальный escape | Изолированный процесс |

### Принцип абстрагирования

```
┌─────────────────────────────────────────────────────────┐
│  Шаблон: group/ci-templates/docker-build.yml            │
│  Внутренняя реализация: docker:dind → Kaniko            │
│  (изменения внутри шаблона)                             │
└─────────────────────────────────────────────────────────┘
                          ↓
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Проект 1    │  │  Проект 2    │  │  Проект N    │
│  (без изменений в конфигурации)                     │
└──────────────┘  └──────────────┘  └──────────────┘
```

### Синтаксис переменных Kaniko

| Синтаксис | Описание |
| :--- | :--- |
| `$[[ VARIABLE ]]` | Подстановка переменных GitLab CI в строках |
| `$VARIABLE` | Стандартная подстановка shell |

### Кэширование в Kaniko

```yaml
--cache=true                    # Включить кэширование
--cache-repo=registry/cache     # Репозиторий для кэша слоёв
```

## Практические сценарии

### Обновление шаблона на Kaniko

**Репозиторий:** `group/ci-templates`

**Файл:** `docker-build.yml`

```yaml
# ci-templates/docker-build.yml
.docker-build-template:
  stage: build
  image:
    name: gcr.io/kaniko-project/executor:debug
    entrypoint: [""]
  variables:
    DOCKERFILE: Dockerfile
    CONTEXT: $CI_PROJECT_DIR
  script:
    - /kaniko/executor \
        --context $[[ CONTEXT ]] \
        --dockerfile $[[ DOCKERFILE ]] \
        --destination $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA \
        --cache=true \
        --cache-repo=$CI_REGISTRY_IMAGE/cache
```

### Результат для проектов

**Проекты не требуют изменений!** Их `.gitlab-ci.yml` остаются прежними:

```yaml
# .gitlab-ci.yml проекта (без изменений)
include:
  - project: 'group/ci-templates'
    ref: v1.0.0
    file: '/docker-build.yml'

build-my-app:
  extends: .docker-build-template
  variables:
    DOCKERFILE: "app/Dockerfile"
```

### Преимущества подхода

| Преимущество | Описание |
| :--- | :--- |
| **Прозрачное обновление** | Проекты не требуют изменений |
| **Безопасность** | Kaniko не требует привилегированного режима |
| **Кэширование** | Встроенное кэширование слоёв через Kaniko |

### Новые проблемы

| Проблема | Описание |
| :--- | :--- |
| **Отсутствие типизации** | Нет явного интерфейса для входных параметров |
| **Слабая валидация** | Невозможно валидировать переменные до выполнения |
| **Документирование** | Требуется ручная документация параметров |

**Следующий этап:** [CI/CD Components](./stage5_components.md) решает проблемы типизации через явный интерфейс (`spec:inputs`) и автоматическую валидацию.
