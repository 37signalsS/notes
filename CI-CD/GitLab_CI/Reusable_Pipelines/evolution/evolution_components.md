# CI/CD Catalog Components — зрелый подход к переиспользованию

## Определения

**CI/CD Components** — финальный, пятый этап эволюции пайплайнов GitLab. Представляет собой версионируемые, типизированные блоки конфигурации с четко определенным интерфейсом и возможностью публикации в общем каталоге.

**`spec:inputs`** — декларативное описание входных параметров компонента, обеспечивающее типизацию и автоматическую валидацию.

**CI/CD Catalog** — визуальный интерфейс в GitLab для поиска, версионирования и документирования доступных компонентов.

**Контекст этапа:** Переход от неявных зависимостей через переменные к строгому контракту и каталогизации.

## Базовые концепции

### Почему Components лучше предыдущих этапов

На этапе [абстрагирования с Kaniko](./evolution_kaniko.md) мы скрыли детали реализации, но интерфейс взаимодействия оставался "невидимым" (через переменные окружения). CI/CD Components решают эту проблему, превращая пайплайн в полноценный программный модуль.

| Характеристика | Этап 4 (Абстракция) | Этап 5 (Components) |
| :--- | :--- | :--- |
| **Интерфейс** | Неявный (переменные) | Явный (`spec:inputs`) |
| **Валидация** | В рантайме (может упасть) | На этапе Lint (до запуска) |
| **Документация** | Ручная в README | Автоматическая из метаданных |
| **Версионирование** | Теги в Git | Полноценный Semver в каталоге |
| **Поиск** | По репозиториям | В UI-каталоге компонентов |

### Архитектура модуля

Компонент — это самодостаточная единица. Он содержит как метаданные (описание входов), так и саму логику пайплайна.

```
┌─────────────────────────────────────────────────────────────┐
│  Репозиторий компонента: group/ci-components/docker-build   │
│  ├── .gitlab-ci.yml      (описание интерфейса spec:inputs)  │
│  └── templates/                                             │
│      └── build.yml       (логика с интерполяцией входов)    │
└─────────────────────────────────────────────────────────────┘
```

## Практические сценарии

### Создание типизированного компонента

В отличие от простых шаблонов, здесь мы явно указываем, какие параметры ожидает компонент.

```yaml
# .gitlab-ci.yml компонента
spec:
  inputs:
    stage:
      default: build
    dockerfile:
      default: Dockerfile
    enable_cache:
      type: boolean
      default: true

---
docker-build-job:
  stage: $[[ inputs.stage ]]
  image: gcr.io/kaniko-project/executor:debug
  script:
    - /kaniko/executor \
        --dockerfile $[[ inputs.dockerfile ]] \
        --cache=$[[ inputs.enable_cache ]]
```

### Публикация и использование

1. **Релиз:** Создается тег `v1.0.0` и GitLab Release. Компонент автоматически появляется в каталоге группы/инстанса.
2. **Использование:** Проект подключает компонент через `include:component`.

```yaml
# .gitlab-ci.yml проекта
include:
  - component: '$CI_SERVER_FQDN/group/ci-components/docker-build@1.0.0'
    inputs:
      stage: build
      dockerfile: app/Dockerfile
      enable_cache: true
```
