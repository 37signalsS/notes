# Компоненты CI/CD каталога — зрелый подход к переиспользованию

## Определения

**CI/CD Components** — финальный (на текущий момент) этап эволюции пайплайнов GitLab. Представляет собой версионируемые, типизированные блоки конфигурации с четко определенным интерфейсом и возможностью публикации в корпоративном или публичном каталоге.

**`spec:inputs`** — декларативное описание входных параметров компонента, обеспечивающее строгую типизацию, валидацию данных и автоматическую генерацию документации в интерфейсе GitLab.

**CI/CD Catalog** — централизованный реестр в GitLab для поиска, версионирования и управления жизненным циклом компонентов. Позволяет организовать "магазин инструментов" для DevOps-инженеров и разработчиков.

**Контекст этапа:** Переход от неявных зависимостей через глобальные переменные окружения к строгому контракту (API) и модульной архитектуре.

## Базовые концепции

### Эволюционное преимущество компонентов

На этапе [абстрагирования с Kaniko](./evolution_kaniko.md) детали реализации были скрыты, но интерфейс взаимодействия оставался неявным. CI/CD Components превращают пайплайн в полноценный программный модуль.

| Характеристика | Этап 4 (Абстракция) | Этап 5 (Components) |
| :--- | :--- | :--- |
| **Интерфейс** | Неявный (переменные) | Явный (`spec:inputs`) |
| **Валидация** | В рантайме (ошибки при выполнении) | На этапе создания пайплайна (Linter) |
| **Типизация** | Только строки | String, Number, Boolean, Array, Options |
| **Версионирование** | Теги в Git (вручную) | Полноценный SemVer + релизы каталога |
| **Изоляция** | Конфликты переменных возможны | Интерполяция `inputs` минимизирует конфликты |

### Тестирование компонентов (Component Testing)

В отличие от обычных шаблонов, компоненты требуют обязательного тестирования перед публикацией. Стандартная структура репозитория компонента включает папку `tests/`, где проверяются:
- Корректность раскрытия YAML (CI Lint).
- Выполнение задач в реальных условиях (Integration tests).
- Отработка различных комбинаций входных параметров.

### Вложенные компоненты (Nested Components)

Зрелый подход предполагает возможность использования одних компонентов внутри других. Это позволяет строить сложные иерархии (например, компонент `microservice-template` может вызывать компоненты `docker-build`, `security-scan` и `k8s-deploy`), сохраняя при этом инкапсуляцию.

## Практические сценарии

### Создание компонента с валидацией

В этом примере используется расширенный синтаксис `inputs`, включая валидацию через регулярные выражения и перечисления.

```yaml
# templates/docker-build.yml
spec:
  inputs:
    stage:
      default: build
      description: "Стадия сборки"
    image_tag:
      type: string
      default: "latest"
      # Валидация формата тега (только цифры, точки и тире)
      regex: ^[a-zA-Z0-9.-]+$
    build_engine:
      type: string
      options:
        - kaniko
        - buildah
      default: kaniko
    push_to_registry:
      type: boolean
      default: true

---
docker-build:
  stage: $[[ inputs.stage ]]
  image: 
    name: osscontainertools/kaniko:v1.28.0-debug
    entrypoint: [""]
  script:
    - /kaniko/executor \
        --dockerfile Dockerfile \
        --destination $CI_REGISTRY_IMAGE:$[[ inputs.image_tag ]] \
        --no-push=$[[ not inputs.push_to_registry ]]
  rules:
    - if: '"$[[ inputs.build_engine ]]" == "kaniko"'
```

### Использование компонента из каталога

Проект подключает компонент через `include:component`. Все параметры проверяются GitLab до запуска пайплайна.

```yaml
# .gitlab-ci.yml проекта
include:
  - component: '$CI_SERVER_FQDN/group/ci-components/docker-build@1.5.0'
    inputs:
      image_tag: $CI_COMMIT_SHORT_SHA
      build_engine: kaniko
      push_to_registry: true
```

### Глобальные входы пайплайна (Pipeline-wide inputs)

Начиная с GitLab 17.11, механизм `spec:inputs` можно использовать в корневом `.gitlab-ci.yml`. Это позволяет создавать структурированные формы запуска пайплайна в интерфейсе GitLab ("Run Pipeline"), заменяя хаотичные текстовые поля переменных на выпадающие списки и чекбоксы.

## Преимущества и недостатки подхода

| Характеристика | Описание |
| :--- | :--- |
| **Надежность** | Строгая проверка типов и регулярные выражения предотвращают передачу некорректных данных. |
| **Удобство поиска** | Визуальный каталог с поиском и документацией заменяет чтение сотен YAML-файлов. |
| **Версионирование** | Поддержка SemVer позволяет безопасно обновлять инструменты, не ломая старые проекты. |
| **Порог входа (Минус)** | Требуется знание синтаксиса интерполяции `$[[ inputs.name ]]` и правил работы каталога. |
