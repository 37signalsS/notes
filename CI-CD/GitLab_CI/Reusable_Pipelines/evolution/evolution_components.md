# Компоненты CI/CD каталога — зрелый подход к переиспользованию

## Определения

**CI/CD Components** — пятый, наиболее совершенный этап эволюции пайплайнов GitLab. Это модульные, версионируемые блоки конфигурации, обладающие строгим программным интерфейсом (API) и предназначенные для публикации в корпоративном или публичном каталоге.

**`spec:inputs`** — директива для декларативного описания входных параметров компонента. Она обеспечивает строгую типизацию, обязательную валидацию данных и автоматическое формирование документации.

**CI/CD Catalog** — централизованный реестр GitLab для обнаружения, управления версиями и контроля жизненного цикла компонентов. Позволяет организовать экосистему инструментов, доступную всей организации.

**Интерполяция входных данных** — механизм подстановки значений параметров через синтаксис `$[[ inputs.name ]]`, который выполняется GitLab *до* развертывания YAML-конфигурации, что исключает конфликты имен с переменными окружения.

**Контекст этапа:** Переход от неявных, хрупких зависимостей на базе глобальных переменных окружения к контракту «CI как код», обеспечивающему изоляцию и предсказуемость.

## Базовые концепции

### Эволюционное преимущество перед шаблонами

На этапе [абстрагирования с Kaniko](./evolution_kaniko.md) детали реализации скрывались, но интерфейс взаимодействия оставался «серым» — проект должен был знать, какие переменные ожидает шаблон. Компоненты решают эту проблему, превращая пайплайн в типизированный программный модуль.

| Характеристика | Уровень 4 (Абстракция) | Уровень 5 (Components) |
| :--- | :--- | :--- |
| **Интерфейс** | Неявный (переменные `variables`) | Явный контракт (`spec:inputs`) |
| **Валидация** | В момент исполнения (Runtime) | До запуска пайплайна (Pre-flight) |
| **Типизация** | Только строки | String, Number, Boolean, Array, Options |
| **Изоляция** | Возможны конфликты имен переменных | Полная изоляция через интерполяцию |
| **Документирование** | Ручное (README) | Автоматическое (на основе `spec`) |

### Архитектура версионирования (SemVer)

В отличие от простых `include:project`, где версии часто хаотичны, компоненты в каталоге ориентированы на **Semantic Versioning (SemVer)**:
- **Major (@1):** Значительные изменения API, требующие правки в проектах.
- **Minor (@1.2):** Новые функции без нарушения обратной совместимости.
- **Patch (@1.2.3):** Исправления ошибок, применяемые автоматически при подписке на минорную версию.

### Тестирование компонентов

Репозиторий компонента — это программный продукт. Стандартная структура включает директорию `tests/`, где реализуются:
1.  **Синтаксические тесты:** Проверка корректности `spec:inputs` и интерполяции через `glab ci lint`.
2.  **Интеграционные тесты:** Запуск реальных пайплайнов с различными комбинациями параметров для проверки итогового поведения.
3.  **Негативные тесты:** Проверка того, что пайплайн отклоняется (fails) при передаче некорректных типов данных или нарушении `regex`.

## Предварительные условия

Для использования и создания компонентов необходимо:
- **Версия GitLab:** 16.0+ (для базового функционала) или 18.x+ (для поддержки массивов и сложных валидаций).
- **Структура репозитория:** Наличие файла `templates/*.yml` и файла `README.md`.
- **Права доступа:** Роль `Maintainer` для публикации в каталоге и `Reporter` для использования из приватных проектов.

## Практические сценарии

### Сценарий 1: Создание компонента с глубокой валидацией

Компонент должен защищать инфраструктуру от некорректных данных с помощью типов и регулярных выражений.

```yaml
# templates/build.yml
spec:
  inputs:
    stage:
      default: build
      type: string
      description: "Стадия пайплайна"
    node_version:
      type: number
      default: 22
      description: "Мажорная версия Node.js"
    environment:
      type: string
      options: [development, staging, production]
      default: development
    scan_vulnerabilities:
      type: boolean
      default: true
    image_prefix:
      type: string
      regex: ^[a-z0-9-]+$ # Только строчные буквы, цифры и тире
      default: "app"

---
node-build:
  stage: $[[ inputs.stage ]]
  image: node:$[[ inputs.node_version ]]-alpine
  script:
    - npm ci
    - npm run build
    - echo "Building for $[[ inputs.environment ]]"
  rules:
    - if: '$[[ inputs.scan_vulnerabilities ]] == true'
      variables:
        SCAN_TARGET: "$[[ inputs.image_prefix ]]:latest"
```

### Сценарий 2: Подключение компонента в проект

Использование компонента становится безопасным и предсказуемым. Если проект передаст `node_version: "latest"` вместо числа, GitLab заблокирует создание пайплайна.

```yaml
# .gitlab-ci.yml проекта
include:
  - component: '$CI_SERVER_FQDN/org/components/node-toolkit/build@2.1'
    inputs:
      stage: fast-build
      environment: production
      node_version: 20
      image_prefix: "my-microservice"
```

### Сценарий 3: Глобальные входы пайплайна (Pipeline-wide inputs)

Начиная с версии GitLab 17.11, можно описывать `spec:inputs` в корневом `.gitlab-ci.yml`. Это превращает страницу «Run Pipeline» в удобную форму с выпадающими списками.

```yaml
# .gitlab-ci.yml (корневой файл проекта)
spec:
  inputs:
    deploy_target:
      options: [staging, production]
      default: staging

---
deploy:
  script:
    - ./deploy.sh --target=$[[ inputs.deploy_target ]]
```

## Валидация

Для обеспечения качества компонентов:
1.  **Merged YAML:** Проверяйте результат интерполяции `$[[ inputs.name ]]` в Pipeline Editor.
2.  **Catalog Preview:** Используйте вкладку «Catalog» в репозитории компонента, чтобы увидеть, как параметры будут отображаться для пользователей.
3.  **Versions Trace:** Убедитесь, что теги Git соответствуют выпускам (Releases) в интерфейсе GitLab.

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `Unknown input: 'name'` | Параметр используется в YAML, но не описан в `spec:inputs`. | Добавьте описание параметра в секцию `spec`. |
| `Input 'X' must match regex` | Переданное значение нарушает правила валидации. | Проверьте входные данные на соответствие регулярному выражению. |
| `Component not found` | Неверный путь или отсутствие релиза в каталоге. | Проверьте корректность пути `$FQDN/group/project/name@version`. |
| Конфликты `stages` | Компонент использует стадию, не описанную в проекте. | Передавайте имя стадии через `inputs` или используйте стандартные стадии. |
