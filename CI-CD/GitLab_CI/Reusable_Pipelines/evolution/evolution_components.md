# Компоненты CI/CD каталога — зрелый подход к переиспользованию

## Определения

**CI/CD Components** — финальный этап эволюции пайплайнов GitLab. Представляет собой версионируемые, типизированные блоки конфигурации с четко определенным интерфейсом и возможностью публикации в общем каталоге.

**`spec:inputs`** — декларативное описание входных параметров компонента, обеспечивающее строгую типизацию, валидацию данных и автоматическую генерацию документации.

**CI/CD Catalog** — интерфейс в GitLab для поиска, версионирования и управления жизненным циклом компонентов внутри организации или в публичном доступе.

**Контекст этапа:** Переход от неявных зависимостей через переменные окружения к строгому контракту (интерфейсу) и централизованной каталогизации.

## Базовые концепции

### Эволюционное преимущество компонентов

На этапе [абстрагирования с Kaniko](./evolution_kaniko.md) детали реализации были скрыты, но интерфейс взаимодействия оставался "невидимым" (через переменные). CI/CD Components превращают пайплайн в полноценный программный модуль с явным API.

| Характеристика | Этап 4 (Абстракция) | Этап 5 (Components) |
| :--- | :--- | :--- |
| **Интерфейс** | Неявный (переменные) | Явный (`spec:inputs`) |
| **Валидация** | В рантайме (ошибки при выполнении) | На этапе компиляции (Pipeline Lint) |
| **Типизация** | Только строки | String, Number, Boolean, Array, Options |
| **Версионирование** | Теги в Git | Полноценный SemVer в каталоге |
| **Документация** | Ручная в README | Автоматическая из спецификации |

### Вложенные компоненты (Nested Components)

Зрелый подход предполагает возможность использования одних компонентов внутри других. Это позволяет строить сложные иерархии (например, компонент `java-service` может внутри себя вызывать компоненты `docker-build` и `security-scan`), сохраняя при этом изоляцию и модульность.

## Практические сценарии

### Создание компонента со строгой типизацией

В этом примере мы используем расширенные возможности `spec:inputs`, включая перечисления (`options`) и булевы флаги.

```yaml
# .gitlab-ci.yml компонента
spec:
  inputs:
    stage:
      default: build
    dockerfile:
      default: Dockerfile
    build_engine:
      type: string
      options:
        - kaniko
        - buildah
      default: kaniko
    enable_cache:
      type: boolean
      default: true

---
docker-build-job:
  stage: $[[ inputs.stage ]]
  image: 
    name: gcr.io/kaniko-project/executor:v1.24.0-debug
    entrypoint: [""]
  rules:
    - if: '"$[[ inputs.build_engine ]]" == "kaniko"'
  script:
    - /kaniko/executor \
        --dockerfile $[[ inputs.dockerfile ]] \
        --cache=$[[ inputs.enable_cache ]]
```

### Использование компонента из каталога

Проект подключает компонент через `include:component`. Все параметры проверяются GitLab до запуска пайплайна.

```yaml
# .gitlab-ci.yml проекта
include:
  - component: '$CI_SERVER_FQDN/group/ci-components/docker-build@1.2.0'
    inputs:
      stage: build
      dockerfile: src/Dockerfile
      build_engine: kaniko
      enable_cache: true
```

### Преимущества и недостатки

| Характеристика | Описание |
| :--- | :--- |
| **Безопасность** | Строгая проверка типов предотвращает инъекции и ошибки конфигурации. |
| **Удобство** | Автоматическая публикация в UI-каталоге упрощает поиск инструментов внутри компании. |
| **Сложность** | Требует изменения привычек разработчиков и более детального проектирования интерфейсов. |
| **Изоляция** | Компоненты работают в собственных контекстах, минимизируя конфликты переменных. |
