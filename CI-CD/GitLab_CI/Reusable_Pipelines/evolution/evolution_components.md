# Компоненты CI/CD каталога — зрелый подход к переиспользованию

**Актуально для:** GitLab CI 19.x; минимальные версии отдельных возможностей указаны в таблице версий.

## Определения

**CI/CD Components** — пятый, наиболее совершенный этап эволюции пайплайнов GitLab. Это модульные, версионируемые блоки конфигурации, обладающие строгим программным интерфейсом (API) и предназначенные для публикации в корпоративном или публичном каталоге.

**`spec:inputs`** — директива для декларативного описания входных параметров компонента. Обеспечивает строгую типизацию, обязательную валидацию данных и автоматическое формирование документации в интерфейсе GitLab.

**CI/CD Catalog** — централизованный реестр GitLab для обнаружения, управления версиями и контроля жизненного цикла компонентов. Позволяет организовать экосистему инструментов, доступную всей организации.

**Интерполяция входных данных** — механизм подстановки значений параметров через синтаксис `$[[ inputs.name ]]`, который выполняется GitLab *до* развертывания YAML-конфигурации, что исключает конфликты имен с переменными окружения.

**Контекстная интерполяция компонента (18.6 — beta, 18.7 — GA)** — механизм, позволяющий компонентам получить доступ к собственным метаданным (`$[[ component.name ]]`, `$[[ component.version ]]`, `$[[ component.sha ]]`, `$[[ component.reference ]]`) без необходимости их явной передачи через `inputs`. Механизм включался фиче-флагом `ci_component_context_interpolation`, по умолчанию был включён и стал GA в 18.7.

**Контекст этапа:** Пятый уровень зрелости CI/CD. Переход от неявных, хрупких зависимостей на базе глобальных переменных окружения к контракту «CI как код», обеспечивающему изоляцию, предсказуемость и автоматическую документацию.

> [!WARNING]
> **Лимиты и ограничения:**
> - Максимум компонентов на проект-ресурс: **100** (18.5+; ранее 10 в 16.0, 30 в 16.9).
> - Максимум входов у одного пайплайна: **20** (`spec:inputs` верхнего уровня). Для одного входа допускается до **50** значений в `options`.
> - Строка внутри входа: **< 1 КБ**; суммарное содержимое входов: **< 1 МБ**.
> - Лимит вложенности `include` (включая компоненты): **150 файлов** (настраивается администратором Self-Managed).
> - Размер одного YAML-файла: `max_yaml_size_bytes`, по умолчанию **2 МБ** (17.3+); глубина вложенности YAML: `max_yaml_depth`, по умолчанию **100**.
> - Глубина наследования `extends`: **11 уровней** (внутренняя константа `MAX_NESTING_LEVELS = 10` в `lib/gitlab/ci/config/extendable/entry.rb`). Рекомендуется не более 3–4.
> - Вложенность массивов в `script`, `before_script`, `after_script` и `rules`: `MAX_NESTING_LEVEL = 10`.
> - В компоненте запрещены глобальные ключи `stages`, `default`, `workflow` и `include` верхнего уровня. В блоке `spec:` разрешены только ключи `inputs`, `component` и `description`.
> - `spec:include` использовать **нельзя** — компонент обязан быть самодостаточным.

### Архитектура компонентов

```
┌──────────────────────────────────────────────────────────────┐
│  CI/CD Catalog: org/ci-catalog (Catalog Resource)            │
│                                                              │
│  ┌────────────────┐  ┌────────────────┐  ┌───────────────┐  │
│  │ templates/     │  │ templates/     │  │ templates/    │  │
│  │  build.yml     │  │  deploy.yml    │  │  security/    │  │
│  │  (spec:inputs) │  │  (spec:inputs) │  │   template.yml│  │
│  │  ---           │  │  ---           │  │   ---         │  │
│  │  # реализация  │  │  # реализация  │  │   # реализация│  │
│  └───────┬────────┘  └───────┬────────┘  └──────┬────────┘  │
│          │                   │                   │            │
│          │ SemVer (v1.2.0)   │ SemVer            │ SemVer     │
│          │ + spec:inputs     │ + spec:inputs     │ + inputs   │
│          │ + README.md       │ + README.md       │ + README   │
└──────────┼───────────────────┼───────────────────┼────────────┘
           │                   │                   │
           │ include:component │ include:component │ include:
           │ @1.2.0            │ @2.0.0            │ component
           ▼                   ▼                   ▼
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Проект A    │  │  Проект B    │  │  Проект N    │
│  .gitlab-ci  │  │  .gitlab-ci  │  │  .gitlab-ci  │
│  6 строк     │  │  8 строк     │  │  5 строк     │
└──────────────┘  └──────────────┘  └──────────────┘
```

> **Важно о структуре каталога.** Допустимы ровно два варианта размещения файла компонента: `templates/<name>.yml` либо `templates/<name>/template.yml`. Схема `templates/security/scan.yml` **не является** компонентом — при попытке подключения каталог не найдёт файл. Имя компонента, соответственно, может содержать только буквы, цифры, `_`, `-` и `.`.

## Эволюционное преимущество перед предыдущим этапом

На этапе [абстрагирования с Kaniko](./evolution_kaniko.md) детали реализации скрывались, но интерфейс взаимодействия оставался «серым» — проект должен был знать, какие переменные ожидает шаблон, иначе пайплайн падал уже во время исполнения. Компоненты превращают пайплайн в типизированный программный модуль с контрактом, проверяемым до запуска.

| Характеристика | Уровень 4 (Абстракция) | Уровень 5 (Components) |
| :--- | :--- | :--- |
| **Интерфейс** | Неявный (переменные `variables`) | Явный контракт (`spec:inputs`) |
| **Валидация** | В момент исполнения (Runtime) | До запуска пайплайна (Pre-flight) |
| **Типизация** | Только строки | String, Number, Boolean, Array, Options |
| **Изоляция** | Возможны конфликты имен переменных | Полная изоляция через интерполяцию `$[[ ]]` |
| **Документирование** | Ручное (README) | Автоматическое (на основе `spec`) |
| **Версионирование** | Произвольное (теги, ветки) | SemVer (обязательно для каталога) |
| **Безопасность** | Зависит от исполнителя | OIDC (`id_tokens`), Commit SHA, Supply Chain |
| **Витрина и поиск** | Нет (нужно знать путь) | Каталог с поиском, описаниями и usage-аналитикой |

**Ключевой переход:** от «скрытой реализации с неявными договорённостями» к «типизированному контракту с версионированной публикацией и встроенной документацией». Платой за переход становится необходимость публиковать релиз и управлять SemVer-жизненным циклом.

## Базовые концепции

### Эволюционное преимущество перед шаблонами

Компоненты являются качественной эволюцией традиционного подхода `include:project`, предлагая расширенный контроль и безопасность.

| Критерий | `include:project` | CI/CD Catalog (Components) |
| :--- | :--- | :--- |
| **Версионирование** | Теги, ветки, SHA | **SemVer** (обязательно для публикации) |
| **Типизация** | Нет (только строки) | **Да** (`spec:inputs` с проверкой типов) |
| **Валидация** | Только синтаксис YAML | **Глубокая** (проверка контракта входов до запуска) |
| **Документация** | Ручная (README.md) | **Автоматическая** (генерация из спецификации в UI) |
| **Изоляция** | Средняя | **Высокая** (изолированные области видимости `$[[ ]]`) |
| **Аудит использования** | Ограниченный | **Полный** (аналитика ресурсов каталога — 18.9+; детали использования компонентов — 19.0+, Premium/Ultimate) |

### Архитектура версионирования (SemVer)

В отличие от простых `include:project`, где версии часто хаотичны, компоненты в каталоге ориентированы на **Semantic Versioning (SemVer)**:

- **Major (@1):** Значительные изменения API, требующие правки в проектах. Автоматические обновления не происходят.
- **Minor (@1.2):** Новые функции без нарушения обратной совместимости. Автоматически получает patch-обновления.
- **Patch (@1.2.3):** Исправления ошибок. При использовании частичного указания (`@1.2`) патчи применяются автоматически.
- **~latest:** Указатель на последний релиз, помеченный как **Release**. Пре-релизы (RC, beta) игнорируются.
- **Commit SHA:** Максимальная безопасность (защита от перезаписи тега). Рекомендуется для production.

> **Ограничение `~latest` и частичных версий.** Механизмы `~latest`, `@1` и `@1.2` работают **только** с компонентами, опубликованными в каталоге. Для обычных `include:component` по `project`/`ref` доступно только точное имя тега или SHA. Публикация в каталоге дополнительно требует, чтобы тег релизной версии **был создан как GitLab Release** — простой git-тег без релиза не попадает в каталог.

**Правила разрешения версий:**

1. **SHA vs Тег:** Если имя тега совпадает с коротким SHA, приоритет отдаётся **SHA**.
2. **Тег vs Ветка:** При совпадении имен приоритет отдаётся **тегу**.
3. **Логика `~latest`:** Выбирает самый свежий релиз, игнорируя пре-релизы.
4. **Разрешение масок:** Запрос `@1.2` перенаправляется на самый старший патч-релиз (например, `1.2.8`).
5. **Версии-исключения:** Пре-релизную версию (например, `2.0.0-rc1`) нельзя получить частичным указанием — только точным `@2.0.0-rc1`.

### Архитектура и структура проекта

Для корректной работы механизмов поиска и публикации репозиторий должен следовать строгому стандарту иерархии:

```text
component-repo/
├── templates/
│   ├── build.yml                    # Вариант 1: плоский файл (вызов: .../component-repo/build)
│   └── security/
│       └── template.yml             # Вариант 2: подкаталог (вызов: .../component-repo/security)
├── README.md                        # Документация, отображаемая в интерфейсе каталога
├── LICENSE.md                       # Рекомендуется для публичных каталогов
├── tests/                           # Интеграционные тесты работоспособности (рекомендация)
├── .gitlab-ci.yml                   # Пайплайн для тестирования и релиза самого компонента
└── CHANGELOG.md                     # Описание изменений по версиям
```

Каталог `templates/` — единственное место, из которого GitLab читает компоненты. Файлы за его пределами в каталог **не публикуются** и видны только как исходники репозитория.

### Блок `spec`: полный синтаксис

В компоненте блок `spec` может содержать ровно три ключа: `inputs`, `component` и `description`. Если блок не нужен — оставьте `spec:` пустым.

```yaml
spec:
  description: "Сборка и тестирование приложения на Node.js"
  component:
    - name
    - sha
    - version
    - reference
  inputs:
    stage:
      default: test
      type: string
      description: "Стадия пайплайна, на которой запускается задание"
    environment:
      type: string
      default: dev
      options: [dev, staging, prod]   # Ограничение выбора (UI dropdown)
    parallel_limit:
      type: number
      default: 1
    enable_feature:
      type: boolean
      default: false
    allowed_regions:
      type: array
      default: ["eu-central-1"]       # Поддержка массивов
    version_tag:
      type: string
      regex: '^v\d+\.\d+\.\d+$'       # Валидация через регулярные выражения
---
# Конец секции спецификации, далее следует реализация YAML
```

**Технические нюансы:**

- **Пустой `spec`:** блок `spec:inputs:` без содержимого невалиден — GitLab возвращает `Build component error: Spec must be a valid json schema`. Правильная запись без входов — просто `spec:`.
- **Обязательность:** параметры без `default` являются обязательными; GitLab заблокирует создание пайплайна, если они не переданы.
- **Тип `array`:** позволяет передавать списки значений для итерации в `parallel:matrix` или использования в `tags`. Поддержка массивов в `options` появилась в **19.0**.
- **`regex`:** работает **только** с `type: string`. Нельзя применять к `number` и `boolean`.
- **`options`:** несовместим с `type: boolean`. Если задан `default`, он обязан присутствовать в списке `options`, иначе пайплайн не создастся.
- **Значения, вводимые пользователем:** `default: null` оставляет поле пустым и обязывает пользователя заполнить его при ручном запуске пайплайна.
- **`options`:** превращает текстовое поле в выпадающий список в UI. Условные (каскадные) списки задаются через `spec:inputs:rules` (18.7+).
- **Лимиты:** до 50 значений в `options` одного входа; до 20 входов у одного пайплайна.

### Жизненный цикл интерполяции (Resolution Order)

Понимание порядка обработки критично для отладки:

1. **Разрешение `include`:** GitLab собирает все файлы компонентов, шаблонов и локальных файлов.
2. **Интерполяция `inputs`:** Значения подставляются во все блоки YAML (включая `script`, `rules`, `variables`). Теги `!reference` разрешаются **после** инпутов — передать `inputs` внутрь ссылки `!reference` напрямую невозможно.
3. **Обработка `variables`:** Разрешаются переменные. Значения из `inputs` уже доступны для использования внутри блока `variables`.
4. **Разрешение `extends`:** Наследование выполняется над уже интерполированным YAML. Финальное слияние структур и вставка фрагментов кода.

### Контекстная интерполяция компонента (18.6+)

Компоненты имеют доступ к собственным метаданным, но **только к тем полям, которые явно объявлены** в `spec:component`. Без объявления `$[[ component.* ]]` недоступен.

| Переменная | Описание | Пример значения |
| :--- | :--- | :--- |
| **`$[[ component.name ]]`** | Техническое имя текущего компонента. | `docker-build` |
| **`$[[ component.version ]]`** | Версия (тег или SHA), указанная при вызове. | `1.5.2` |
| **`$[[ component.sha ]]`** | Полный Commit SHA версии компонента. | `e3262fdb...` |
| **`$[[ component.reference ]]`** | Ссылка на страницу компонента в каталоге. | `https://gitlab.com/my-org/ci-catalog/-/components/docker-build/1.5.2` |

**Когда `component.version` возвращает `null`:**

- компонент **не является** ресурсом каталога;
- в пути указана **ветка или commit SHA**, а не релизная версия.

Поэтому `$[[ component.version ]]` нельзя использовать как гарантированно непустое значение. `component.reference` возвращает всегда ровно то, что стоит после `@`: для `@1.0` вернётся `1.0`, тогда как `component.version` может вернуть `1.0.2`; для `@~latest` — `~latest`; для `@abc123` — `abc123`, а `component.version` — `null`.

**Пример:** автоматический выбор версии инструментов, соответствующей версии самого компонента:

```yaml
# templates/build.yml
spec:
  component:
    - version
    - sha
---
build_job:
  image: custom-registry/tools:$[[ component.version ]]
  script:
    - echo "Компонент $[[ component.version ]] (SHA: $[[ component.sha ]])"
    - run-build.sh
```

### Безопасность и цепочка поставок (Supply Chain Security)

- **Изоляция контекста:** интерполяция `$[[ inputs.* ]]` выполняется в изолированной области видимости, исключая конфликты имен между независимыми модулями.
- **Контроль версий:** поддержка Commit SHA (`@abc123de...`) гарантирует неизменность кода компонента и защищает от атак типа «отравление тега» (tag poisoning).
- **OIDC (id_tokens):** использование `id_tokens` внутри компонентов позволяет реализовать Zero Trust аутентификацию без долгоживущих секретов:
  ```yaml
  build_image:
    id_tokens:
      SIGSTORE_ID_TOKEN:
        aud: sigstore
    script:
      - cosign sign $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
  ```
- **Verified component creators (16.11+ на GitLab.com, 18.1+ на Self-Managed и Dedicated):** каталог помечает компоненты, опубликованные проектами, прошедшими верификацию, что отделяет доверенный код от анонимного.
- **Pipeline Execution Policies (17.x+):** принудительное внедрение компонентов на уровне группы проектов. Эти задания невозможно отключить или переопределить в локальном `.gitlab-ci.yml`.
- **Целостность входов (19.0+):** значения, переданные через `inputs`, фиксируются вместе с пайплайном и не могут быть подменены последующими изменениями спецификации компонента.

### Тестирование компонентов

Репозиторий компонента — это программный продукт. Стандартная структура включает директорию `tests/`, где реализуются:

1. **Синтаксические тесты:** проверка корректности `spec:inputs` и интерполяции через `glab ci lint`.
2. **Интеграционные тесты:** запуск реальных пайплайнов с различными комбинациями параметров для проверки итогового поведения.
3. **Негативные тесты:** проверка того, что пайплайн отклоняется (fails) при передаче некорректных типов данных или нарушении `regex`.
4. **Кросс-проектные тесты:** проверка компонента в контексте других проектов через `glab ci lint --project my-org/target-app --show-expanded`.

## Предварительные условия

Для использования и создания компонентов необходимо:

- **GitLab:** 17.0+ (GA CI/CD Catalog и компонентов), 18.7+ для контекстной интерполяции `component.*`, 18.9+ для аналитики каталога, 19.0+ для деталей использования компонентов и фиксации входов.
- **Структура репозитория:** каталог `templates/` с YAML-файлами в форме `<name>.yml` или `<name>/template.yml`, файл `README.md` в корне.
- **Статус проекта:** проект должен быть помечен как «Catalog resource» в `Settings > General > Visibility, project features, permissions > CI/CD Catalog project`. Включить тумблер может только роль **Owner**.
- **Права доступа:** `Maintainer` или `Owner` — для публикации релиза в каталоге; `Developer` и выше — для вызова компонента из проекта. Если исходный проект компонента **приватный**, пользователь, запускающий пайплайн, должен иметь в нём роль не ниже **`Reporter`**. Для внутренних проектов достаточно любого аутентифицированного пользователя, для публичных — членство не требуется.
- **GitLab Runner:** настроенный исполнитель (например, Docker). Компоненты не требуют особых типов раннеров — они работают на уровне компиляции пайплайна.
- **SemVer:** публикация в каталоге требует тегов SemVer, созданных как GitLab Release.
- **Описание проекта:** для отображения в каталоге проект должен иметь заполненное описание (`description`).

## Практические сценарии

### Сценарий 1: Создание компонента с глубокой валидацией

Компонент должен защищать инфраструктуру от некорректных данных с помощью типов и регулярных выражений.

```yaml
# templates/build.yml
spec:
  description: "Сборка Node.js-приложения"
  inputs:
    stage:
      default: build
      type: string
      description: "Стадия пайплайна"
    node_version:
      type: number
      default: 22
      description: "Мажорная версия Node.js"
    environment:
      type: string
      options: [development, staging, production]
      default: development
    scan_vulnerabilities:
      type: boolean
      default: true
    image_prefix:
      type: string
      regex: ^[a-z0-9-]+$ # Только строчные буквы, цифры и тире
      default: "app"
---
node-build:
  stage: $[[ inputs.stage ]]
  image: node:$[[ inputs.node_version ]]-alpine
  script:
    - npm ci
    - npm run build
    - echo "Building for $[[ inputs.environment ]]"
  rules:
    - if: '$[[ inputs.scan_vulnerabilities ]] == true'
      variables:
        SCAN_TARGET: "$[[ inputs.image_prefix ]]:latest"
```

### Сценарий 2: Подключение компонента в проект

Использование компонента становится безопасным и предсказуемым. Если проект передаст `node_version: "latest"` вместо числа, GitLab заблокирует создание пайплайна.

```yaml
# .gitlab-ci.yml проекта
include:
  - component: '$CI_SERVER_FQDN/org/components/node-toolkit/build@2.1'
    inputs:
      stage: fast-build
      environment: production
      node_version: 20
      image_prefix: "my-microservice"
```

> **Переменная `$CI_SERVER_FQDN` подставляется только в пределах одного инстанса.** Ссылка вида `$CI_SERVER_FQDN/org/...` работает для Self-Managed/Dedicated, но при использовании компонентов с GitLab.com в проекте другого инстанса подстановка даст неверный адрес. Для кросс-инстансных зависимостей указывайте FQDN явно.

### Сценарий 3: Глобальные входы пайплайна (Pipeline-wide inputs)

Описывая `spec:inputs` в корневом `.gitlab-ci.yml`, вы превращаете страницу «Run Pipeline» в форму с выпадающими списками и проверкой типов.

```yaml
# .gitlab-ci.yml (корневой файл проекта)
spec:
  inputs:
    deploy_target:
      options: [staging, production]
      default: staging
    replicas:
      type: number
      default: 2
    approver:                 # default: null — поле обязательно для заполнения
      type: string
      default: null
---
deploy:
  script:
    - ./deploy.sh --target=$[[ inputs.deploy_target ]] --replicas=$[[ inputs.replicas ]]
```

> **Лимит:** один пайплайн принимает не более **20** входов. Плановая форма, расписания пайплайнов и ручной запуск используют один и тот же механизм.

### Сценарий 4: Миграция с `include:project` на компоненты

**До (Legacy):** пайплайны зависят от веток, что делает их нестабильными.

```yaml
include:
  - project: 'group/ci-templates'
    file: '/docker-build.yml'
    ref: main
```

**После (Modern):** использование компонентов с SemVer и типизированными входами.

```yaml
include:
  - component: '$CI_SERVER_FQDN/group/ci-components/docker-build@1.5.0'
    inputs:
      image: docker:29
      push_registry: true
```

**Алгоритм миграции:**

1. **Спецификация:** опишите контракт в `spec:inputs` в исходном шаблоне.
2. **Рефакторинг:** замените обращения к переменным `$VAR` на интерполяцию `$[[ inputs.var ]]`; запретите глобальные ключи (`stages`, `default`, `workflow`).
3. **Самодостаточность:** перенесите зависимости внутрь компонента; `spec:include` использовать нельзя.
4. **Релиз:** создайте тег SemVer и GitLab Release через ключ `release:` в `.gitlab-ci.yml` репозитория компонента.
5. **Проверка:** используйте `glab ci lint --show-expanded` для подтверждения корректности.
6. **Публикация:** пометьте проект как «Catalog resource» (роль Owner), затем выполните релиз.

```yaml
# .gitlab-ci.yml репозитория компонента — публикация релиза.
# Начиная с GitLab 19.0 ключ release: работает через glab CLI;
# образ release-cli удалён.
release:
  image: registry.gitlab.com/gitlab-org/cli:latest
  script:
    - echo "Publishing component $CI_COMMIT_TAG"
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
  release:
    tag_name: $CI_COMMIT_TAG
    name: "Component $CI_COMMIT_TAG"
    description: './CHANGELOG.md'
```

> **Особенности `release:` в GitLab 19.x:** релиз создаётся командой `glab release create` и аутентифицируется через `CI_JOB_TOKEN` (переопределяется `GITLAB_TOKEN`, `GITLAB_ACCESS_TOKEN` или `OAUTH_TOKEN`). Если релиз с таким `tag_name` уже существует, он **не обновляется**, а задание завершается ошибкой — перед повторным запуском проверьте `glab release list`. Для Shell executor `glab` должен быть установлен на хосте раннера.

### Сценарий 5: Компонент для монорепозитория (Selective CI)

Эффективное управление сборкой через селективный запуск заданий на основе путей.

```yaml
# templates/module-builder.yml
spec:
  inputs:
    module_path:
      type: string
    build_command:
      default: "make build"
---
build-module:
  stage: build
  script:
    - cd $[[ inputs.module_path ]]
    - $[[ inputs.build_command ]]
  rules:
    - changes:
        - $[[ inputs.module_path ]]/**/*
```

### Сценарий 6: Цепочка компонентов (Component Chaining)

Создание «золотых пайплайнов» организации путем каскадного подключения модулей.

```yaml
# templates/standard-pipeline.yml
spec:
  inputs:
    app_name:
      type: string
---
include:
  - component: '$CI_SERVER_FQDN/org/linter@2.0.0'
  - component: '$CI_SERVER_FQDN/org/docker-builder@3.1.0'
    inputs:
      image_name: $[[ inputs.app_name ]]
```

> **Внимание:** каждый вложенный компонент учитывается в общем лимите **150 `include`**. Собственного лимита глубины цепочки компонентов GitLab не устанавливает — ограничение задаётся этим общим счётчиком включений и `MAX_NESTING_LEVEL = 10` для вложенных массивов в `script`/`rules`.

### Сценарий 7: Постепенное внедрение (Canary Rollout)

Безопасное тестирование новых версий критических инструментов на части проектов.

```yaml
include:
  # 90% проектов на стабильной версии
  - component: '$CI_SERVER_FQDN/org/security-scan@1.5.0'
    rules:
      - if: '$CI_PROJECT_ID % 10 != 0'
  # 10% проектов тестируют RC
  - component: '$CI_SERVER_FQDN/org/security-scan@2.0.0-rc1'
    rules:
      - if: '$CI_PROJECT_ID % 10 == 0'
```

### Сценарий 8: Контекстная адаптация (18.6+)

Компонент автоматически определяет версию инструментов на основе собственной версии. Обратите внимание: поля `component.*` должны быть объявлены в `spec:component`.

```yaml
# templates/scanner.yml
spec:
  component:
    - version
    - sha
---
run-scan:
  image: custom-registry/scanner:$[[ component.version ]]
  script:
    - scanner-cli --path .
    - echo "Running scanner version $[[ component.version ]] (SHA: $[[ component.sha ]])"
```

### Сценарий 9: Валидация входных данных через regex

Защита пайплайна от некорректных значений (например, лимитов ресурсов).

```yaml
spec:
  inputs:
    # ВНИМАНИЕ: regex работает только с type: string.
    # Для числового ограничения применяйте type: number + options.
    replicas:
      type: string
      regex: '^[1-5]$' # Ограничение от 1 до 5 экземпляров
      description: "Количество реплик"
    region:
      type: string
      regex: '^(eu|us)-(west|east|central)-[0-9]$'
    max_parallel:
      type: number
      options: [2, 4, 8] # Числовой вариант: фиксированный набор допустимых значений
---
deploy:
  script:
    - echo "Scaling to $[[ inputs.replicas ]] nodes in $[[ inputs.region ]] (parallel: $[[ inputs.max_parallel ]])"
```

### Сценарий 10: Вложенные компоненты (Nested Components)

Явная передача параметров по иерархии вложенности. **Важно:** автоматического проброса инпутов нет, всё передаётся явно.

```yaml
# templates/parent.yml
spec:
  inputs:
    stage_name:
      default: test
---
include:
  - component: $CI_SERVER_FQDN/my-org/child@1.0.0
    inputs:
      target_stage: $[[ inputs.stage_name ]]
parent_job:
  stage: $[[ inputs.stage_name ]]
  script:
    - echo "Parent running in $[[ inputs.stage_name ]]"
```

### Сценарий 11: Компонент без входов

Не всем компонентам нужна параметризация. Пустой `spec` — валидный вариант.

```yaml
# templates/base-lint.yml
spec:
---
default_lint:
  image: alpine:latest
  script:
    - apk add --no-cache shellcheck
    - shellcheck ./scripts/*.sh
```

### Сценарий 12: Управление зависимостями компонентов (DevOps/SRE)

Компоненты — не изолированные артефакты: они тянут за собой образы, пакеты и внешние сервисы. Эксплуатационный подход требует их явного учёта.

```bash
# Инвентаризация: какие компоненты подключены во всех проектах группы
glab api "/groups/my-org/projects?include_subgroups=true&per_page=100" \
  | jq -r '.[].path_with_namespace' | while read -r p; do
    glab api "projects/${p//\//%2F}/repository/files/.gitlab-ci.yml/raw?ref=main" 2>/dev/null \
      | grep -oE 'component:.*@[^ ]+' | sed "s|^|${p}: |"
  done

# Проверка соответствия используемых версий последним релизам каталога
glab api "projects/my-org%2Fci-components/releases" | jq -r '.[] | "\(.tag_name)\t\(.released_at)"'
```

**Практические правила для платформенной команды:**

- **Зеркалирование на Self-Managed.** Компоненты с GitLab.com можно зеркалировать в собственный инстанс для независимости от внешнего сервиса. Учтите, что `$CI_SERVER_FQDN` в зеркале укажет на ваш инстанс — пути `$CI_SERVER_FQDN/org/...` нужно будет пересмотреть.
- **Фиксация на SHA в production.** Частичные версии и `~latest` удобны в разработке, но для критичных пайплайнов используйте полный commit SHA: это исключает отравление тега и делает конфигурацию воспроизводимой.
- **Аудит через usage-аналитику.** В GitLab 19.0 (Premium/Ultimate) раздел **Analyze > CI/CD Catalog** показывает, какие проекты используют каждый компонент. Это основной инструмент для оценки blast radius перед breaking change.
- **Откат.** Breaking change требует мажорного тега. Старый мажор остаётся доступен для всех проектов, зафиксировавших `@1.x.0` — «горячий» откат сводится к смене версии в `.gitlab-ci.yml` без изменения кода компонента.

## Валидация

Для обеспечения качества компонентов используйте комбинацию инструментов:

### Локальная валидация (GitLab CLI)

```bash
# Быстрая проверка синтаксиса
glab ci lint

# Полный разбор с отображением итогового YAML
glab ci config compile

# Валидация компонента в контексте другого (целевого) проекта
glab ci config compile --project my-org/target-app

# Экспорт для аудита
glab ci config compile > expanded.yml
```

### Валидация через API (Автоматизация)

`POST /projects/:id/ci/lint` принимает JSON с полем `content`. Раскрытый YAML возвращается только при передаче **query-параметра** `include_merged_yaml=true` (в теле запроса такого поля нет).

```bash
# include_merged_yaml передаётся в query string, content — в теле
curl --request POST \
  --header "PRIVATE-TOKEN: $TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"content": "include:\n  - component: gitlab.example.com/org/comp@1.0.0"}' \
  "https://gitlab.example.com/api/v4/projects/<id>/ci/lint?include_merged_yaml=true" \
  | jq -r '.valid, (.errors[]? // empty)'
# → true

# Симуляция пайплайна на конкретном ref с перечислением итоговых заданий
curl --request POST \
  --header "PRIVATE-TOKEN: $TOKEN" \
  --header "Content-Type: application/json" \
  --data '{"content": "'"$(cat .gitlab-ci.yml)"'", "dry_run": true, "dry_run_ref": "main", "include_jobs": true}' \
  "https://gitlab.example.com/api/v4/projects/<id>/ci/lint" \
  | jq -r '.jobs[].name'
# → node-build
# → run-scan
```

### Валидация через Web UI

1. **Pipeline Editor:** вкладка **View merged YAML** — единственный способ увидеть результат интерполяции инпутов и контекста.
2. **Catalog Preview:** проверка отображения спецификации и README в реестре компонентов организации.
3. **Versions Trace:** убедитесь, что используемые теги соответствуют Releases в интерфейсе GitLab, иначе `~latest` и частичные версии их не найдут.

### Чек-лист перед публикацией

- [ ] Секция `spec:inputs` заполнена и синтаксически верна (либо оставлен пустой `spec:`).
- [ ] Глобальные ключи `stages`, `default`, `workflow` из компонента удалены.
- [ ] `spec:include` не используется — компонент самодостаточен.
- [ ] Каждый `input` имеет поле `description`; критические параметры ограничены `regex` или `options`.
- [ ] Файлы лежат в `templates/` в форме `<name>.yml` или `<name>/template.yml`.
- [ ] Компонент прошёл проверку через `glab ci lint --show-expanded`.
- [ ] Проект описан и помечен как «Catalog resource» (роль Owner).
- [ ] `README.md` содержит примеры подключения и описание каждого входного параметра.
- [ ] Создан релиз SemVer — тег создан ключом `release:` (не только git-тег).
- [ ] В репозитории создана папка `tests/` с интеграционными тестами.

## Устранение неполадок

### Системные ограничения и лимиты

| Ограничение | Значение | Настройка администратора | Описание |
| :--- | :--- | :--- | :--- |
| **Максимум компонентов на проект** | **100** (18.5+) | Нет | Количество файлов в `templates/` |
| **Максимум входов у пайплайна** | **20** | Нет | Включая `spec:inputs` компонентов верхнего уровня |
| **Значений в `options` одного входа** | **50** | Нет | Длина выпадающего списка |
| **Строка внутри входа** | **< 1 КБ** | Нет | Ограничение `StringOrScriptOrArray` |
| **Суммарное содержимое входов** | **< 1 МБ** | Нет | Общий объём входов пайплайна |
| **Включений `include`** | **150** | Да (`max_includes` и др., кластерные настройки CI/CD) | Суммарное число файлов, включая компоненты и вложенные включения; повторное включение одного файла тоже считается |
| **Время разрешения всех include** | **30 с** | Нет | Таймаут на загрузку и слияние всей конфигурации |
| **Размер одного YAML-файла** | **2 МБ** | Да (`max_yaml_size_bytes`, 17.3+) | Изменение в сторону уменьшения разрешено |
| **Суммарный раскрытый YAML** | **314,6 МБ** | Да (`ci_max_total_yaml_size_bytes`) | 2 МБ × 150 включений; вверх не увеличивается |
| **Глубина вложенности YAML** | **100** | Да (`max_yaml_depth`) | Верхняя граница уменьшения — 1 |
| **Заданий в пайплайне** | Зависит от тарифа | Да (`max_pipelines_per_commit_user` и др.) | На Self-Managed часть лимитов по умолчанию **выключена** (значение 0) |
| **Уровней `extends`** | **11** | Нет | Внутренняя константа `MAX_NESTING_LEVELS = 10` |
| **Вложенность массивов в `script`/`rules`** | **10** | Нет | `MAX_NESTING_LEVEL` в `entry/processable.rb` |

> **Осторожно с лимитом 5 МБ.** Он существует, но относится не к раскрытому YAML компонентов, а к артефактам, передаваемым в **динамический дочерний пайплайн** (`max_artifacts_content_include_size`, диапазон 1–10 МБ). Для обычного `include:component` действуют лимиты из таблицы выше.

### Сводная таблица ошибок

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Unknown input: 'X'` | Параметр используется в YAML, но не описан в `spec:inputs`. | Добавьте параметр в секцию `spec`. |
| `Input 'X' must match regex` | Значение нарушает правила валидации. | Проверьте входные данные на соответствие регулярному выражению. |
| `Component '<ref>' - content not found` | Запрошены `~latest` или частичная версия, но релиз в каталоге не создан. | Создайте GitLab Release для тега или укажите точную версию `@1.2.3`. |
| `Component not found` | Неверный путь/имя либо проект не помечен как ресурс каталога. | Проверьте путь `$FQDN/group/project/name@version` и статус «Catalog resource». |
| `Build component error: Spec must be a valid json schema` | Блок `spec:inputs` объявлен, но пуст. | Замените `spec:inputs:` на пустой `spec:` либо опишите хотя бы один вход. |
| `Duplicate job name` | Компонент не объявляет `spec:inputs` префикса, а имена заданий совпали. | Добавьте вход `job_name_prefix` и используйте его в именах заданий. |
| Задания с одинаковым именем сливаются | Это **не ошибка**: задания с совпадающим именем объединяются по правилам `deep_merge`, и `script` дописывается. | Если слияние нежелательно, разведите имена через `job_name_prefix`. |
| `Input type mismatch` | Несоответствие типов (например, строка вместо числа). | Убедитесь, что типы в `inputs` и `spec` совпадают (string, number, boolean). |
| `Component content not found` | Файл компонента отсутствует по указанному пути. | Проверьте форму пути: `templates/<name>.yml` или `templates/<name>/template.yml`. |
| `Invalid global key: default` | Использование блока `default` в компоненте. | Перенесите настройки (image, tags) непосредственно в задания компонента или используйте скрытые задания (`.base`). |
| `Invalid global key: stages` | Использование `stages` в компоненте. | Передавайте имя стадии через `inputs` или используйте стандартные стадии проекта. |
| `include` is not allowed here | Использован `spec:include`. | Удалите его: компонент должен быть самодостаточным. |
| `Maximum 150 includes are allowed!` | Превышен суммарный лимит включений. | Объедините мелкие `local include` файлы, используйте `!reference` для фрагментов кода. |
| `Expanded configuration size exceeds max` | Итоговый YAML превышает `ci_max_total_yaml_size_bytes` (314,6 МБ). | Сократите комментарии и дублирование; переходите на `extends` и `!reference`. |
| `nesting too deep in extends` | Глубина наследования превышена (максимум 11 уровней). | Упростите иерархию шаблонов, держитесь 3–4 уровней. |
| Циклическое включение | Компонент подключает сам себя (прямо или транзитивно). | Разорвите цикл: выделите общее в отдельный компонент нижнего уровня. |
| Изменение версии ломает проекты | Major-обновление сломало обратную совместимость. | Внедрите SemVer. Никогда не меняйте логику в текущем мажорном теге. |
| Задание `release` падает на существующем релизе | `release:tag_name` уже существует: релиз **не обновляется**, задание завершается ошибкой. | Проверьте `glab release list`; для повторного прогона сначала удалите релиз. |
| `401 Unauthorized` при создании релиза | `GITLAB_TOKEN`/`GITLAB_ACCESS_TOKEN`/`OAUTH_TOKEN` переопределяет `CI_JOB_TOKEN` и не имеет нужных scope. | Удалите эти переменные из задания либо выдайте токену необходимые права. |
| `Image not found: release-cli` (19.x) | `release-cli` удалён в GitLab 19.0. | Используйте `registry.gitlab.com/gitlab-org/cli:latest` — ключ `release:` работает через `glab`. |
| `... too many includes` за 30 секунд | Превышен таймаут разрешения конфигурации (30 с) — слишком много или слишком «тяжёлые» включения. | Сократите число включений, отключите кеш на уровне компонента, пересмотрите рекурсивные цепочки. |

## Лучшие практики и очистка

**Проектирование компонентов**

- **Один компонент — одна ответственность.** Компонент, который «и собирает, и деплоит, и сканирует», невозможно версионировать: любое изменение ломает всех потребителей.
- **Никаких глобальных ключей.** `stages`, `default`, `workflow` внутри компонента запрещены. Стадию передавайте через `inputs`, `image` и `tags` задавайте в самих заданиях.
- **Избегайте жёстких привязок к инстансу.** Не зашивайте `$CI_SERVER_FQDN` и `$CI_API_V4_URL` внутрь компонента: это делает его непереносимым между Self-Managed, Dedicated и зеркалами.
- **Документируйте каждый вход.** `description` — единственный источник документации, который увидит пользователь в UI каталога.
- **Самодостаточность вместо композиции.** `spec:include` запрещён; если нужна композиция — вызывайте вложенные компоненты из заданий (как в [Сценарии 6](#сценарий-6-цепочка-компонентов-component-chaining)), помня об общем лимите 150 включений.
- **Префикс имён заданий.** Добавьте вход `job_name_prefix` и используйте `$[[ inputs.job_name_prefix ]]-task`. Без этого задания с одинаковыми именами будут молча сливаться, а конфликтующие определения — перезаписывать друг друга.

**Жизненный цикл и версии**

- **SemVer — обязателен.** Breaking change → мажор, новая обратносовместимая функция → минор, исправление → патч.
- **Релиз создаётся ключом `release:`.** Создание git-тега вручную недостаточно: без GitLab Release тег не попадёт в каталог, и `~latest` его не увидит.
- **Release notes — часть контракта.** Пользователь читает их при выборе версии; не пишите « various improvements ».

**Эксплуатация**

- **Проверяйте blast radius перед breaking change.** В GitLab 19.0+ раздел **Analyze > CI/CD Catalog** показывает список проектов, использующих компонент. Для версий до 19.0 используйте инвентаризацию через `glab api` (см. [Сценарий 12](#сценарий-12-управление-зависимостями-компонентов-devopssre)).
- **Фиксируйте критичные пайплайны на SHA.** Частичные версии и `~latest` — для разработки и некритичных задач; в production — полный commit SHA.
- **Версия компонента ≠ версия инструмента.** Компонент `docker-build@1.5.0` может тянуть любой образ. Держите образ в `inputs` с SemVer-значением по умолчанию, чтобы обновление было явным.

**Очистка и откат**

```bash
# Полный откат: удаление проекта-компонента не удаляет
# сами компоненты у потребителей — ссылки на них становятся битыми.
# Перед удалением проверьте потребителей:
glab api "projects/my-org%2Fci-components/repository/tree?path=templates&ref=main" \
  | jq -r '.[].name'
# → build.yml
# → deploy.yml
# → security

# Проверка остаточных артефактов после отката версии
glab api "projects/my-org%2Ftarget-app/pipelines?ref=main&per_page=5" \
  | jq -r '.[] | "\(.id)\t\(.status)\t\(.created_at)"'
```

- **Удаление компонента — ломающая операция.** Проверьте, что ни один проект его не подключает, прежде чем удалять файл из `templates/`.
- **Откат через мажорный тег.** Потребители, зафиксировавшие `@1.4.0`, продолжают работать после выхода `@2.0.0`. Это и есть основной механизм безопасного breaking change.
- **Отключение тумблера «CI/CD Catalog project» удаляет метаданные каталога.** После этого история и сведения об использовании компонента теряются без возможности восстановления — не отключайте тумблер как «временную меру».

## Преимущества и недостатки подхода

### Преимущества

- **Валидация до запуска.** Ошибка в контракте обнаруживается при создании пайплайна, а не в логе задания через 40 минут после старта.
- **Изоляция.** Интерполяция `$[[ ]]` не конфликтует с пользовательскими переменными окружения.
- **Версионирование.** Семантические версии и возможность зафиксировать commit SHA дают воспроизводимость и защиту от отравления тегов.
- **Автоматическая документация.** Описания входов и README отображаются в каталоге без ручного ведения документации отдельно.
- **Аудируемость.** Аналитика каталога (18.9+) и детали использования (19.0+) дают ответ на вопрос «кто использует этот компонент» без ручного обхода репозиториев.
- **Безопасная цепочка поставок.** Verified component creators, OIDC-аутентификация и `Pipeline Execution Policies` работают поверх каталога как единого контролируемого периметра.
- **Централизованный стандарт с безопасным breaking change.** Старый мажор остаётся доступен, откат — это смена одной строки.

### Недостатки

- **Строгие правила написания.** Запрет глобальных ключей и `spec:include` делает перенос существующего `include`-шаблона в компонент нетривиальной задачей.
- **Стоимость входа.** Нужны отдельный репозиторий, релизный пайплайн, тесты и дисциплина SemVer. Для 1–3 проектов это избыточно.
- **Зависимость от платформы.** Каталог — серверная функция GitLab: полностью локальная разработка компонента без инстанса невозможна.
- **Эксплуатационная нагрузка.** Компоненты тянут образы и пакеты; нужен процесс обновления (Dependabot/Renovate для образов, регламент релизов) и контроль за устареванием.
- **Затруднённый отладчик.** Проблема в `$[[ ]]`-интерполяции диагностируется только через `glab ci lint --show-expanded` или `View merged YAML`; пошаговой отладки интерполяции нет.
- **Каскадная цена ошибки.** Ошибка в популярном компоненте ломает все подключившие проекты одновременно — обязательны тесты и Canary-развёртывание.
