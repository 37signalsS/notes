# Переиспользуемые пайплайны GitLab CI: Обзор

## Определения

**Переиспользуемые и композитные пайплайны** в GitLab CI — это архитектурный подход к проектированию CI/CD, направленный на создание модульных, типизированных и версионируемых конфигураций. Основная цель — соблюдение принципа DRY (Don't Repeat Yourself), минимизация дублирования кода, стандартизация процессов безопасности и ускорение доставки ПО за счет использования проверенных строительных блоков.

### Ключевые термины

- **Раскрытый YAML (Expanded YAML)** — финальная конфигурация, сформированная после выполнения всех инструкций `include`, `extends` и интерполяции `inputs`. Именно этот файл исполняется сервером GitLab.
- **Шаблон (Template)** — YAML-файл, содержащий базовую логику заданий, предназначенный для подключения в другие проекты.
- **Компонент (Component)** — версионируемый блок конфигурации с явно определенным интерфейсом (`spec:inputs`), опубликованный в CI/CD Catalog.

### Сводная таблица механизмов

| Механизм | Назначение | Область применения | Версия GitLab |
| :--- | :--- | :--- | :--- |
| **`extends`** | Глубокое наследование конфигурации от скрытых заданий (начинаются с `.`) | Внутри файла / `include` | Любая |
| **`!reference`** | Точечная вставка фрагментов кода (скриптов, правил) | Межфайловое использование | 13.9+ |
| **`include`** | Подключение внешних файлов (local, project, remote, template) | Межпроектная интеграция | Любая |
| **`inputs`** | Параметризация подключаемых файлов через `$[[ inputs.key ]]` | Компоненты и шаблоны | 16.0+ |
| **CI/CD Catalog** | Реестр версионируемых и документированных компонентов | Корпоративный уровень | 16.2+ |
| **`trigger`** | Запуск дочерних (Downstream) пайплайнов для изоляции контекста | Сложные многоуровневые системы | Любая |

## Основные концепции

### Эволюция подходов к переиспользованию

Развитие CI/CD в организации обычно проходит путь от хаотичного копирования кода до создания внутренней экосистемы компонентов. Подробный разбор представлен в документе **[Эволюция переиспользуемых пайплайнов](./evolution_example.md)**.

1.  **Boilerplate** — прямое копирование YAML-кода. Максимальная гибкость, нулевая сопровождаемость.
2.  **Централизация (include)** — хранение шаблонов в выделенном репозитории.
3.  **Гибкость (extends)** — кастомизация центральных шаблонов под нужды конкретных сервисов.
4.  **Абстракция (Kaniko/Steps)** — сокрытие технических деталей реализации инструментов.
5.  **Типизация (Catalog)** — переход к компонентам с SemVer и строгими интерфейсами.

### Механизм обратного глубокого слияния (Reverse Deep Merge)

При использовании `extends` и `include` GitLab применяет алгоритм слияния, где дочернее задание имеет абсолютный приоритет.

- **Хеши (Hashes):** Ключи (например, в `variables`) объединяются. Если ключи совпадают, значение из дочернего задания перезаписывает родительское.
- **Массивы (Arrays):** Важное ограничение — массивы (например, `script`, `rules`, `tags`) **не дополняются, а полностью замещаются**. Если в родительском задании 10 строк скрипта, а в дочернем — 1, итоговое задание будет содержать только 1 строку. Для обхода этого поведения используется механизм `!reference`.

Детальные правила и примеры слияния описаны в SSoT-файле: **[Механизм `extends`](./extends_keyword.md)**.

### Безопасность и политики исполнения

Переиспользуемые пайплайны являются фундаментом корпоративной безопасности (DevSecOps):
- **Pipeline Execution Policies:** Позволяют принудительно внедрять сканеры (SAST, DAST) на уровне всей группы проектов. Эти задания нельзя отключить в локальном `.gitlab-ci.yml`.
- **Изоляция токенов:** Использование `CI_JOB_TOKEN` требует явного разрешения (Allowlist) в настройках проекта для доступа к ресурсам других репозиториев, что критично при использовании внешних шаблонов.

## Практические сценарии

### Предварительные условия

Для эффективного внедрения переиспользуемых пайплайнов необходимо:
1. Выделенный репозиторий для хранения шаблонов/компонентов.
2. Настроенный доступ к проектам (права Developer+ для чтения шаблонов через `include:project`).
3. Для CI/CD Catalog — проект должен быть помечен как "Catalog resource" в настройках.

### Сценарий 1: Наследование структуры через `extends`

Подходит для создания базовых образов заданий внутри одного проекта или при использовании простых библиотек.

```yaml
# .gitlab-ci.yml
.base_test:
  image: python:3.9
  before_script:
    - pip install -r requirements.txt
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

unit_tests:
  extends: .base_test
  script:
    - pytest tests/unit
```

### Сценарий 2: Атомарная вставка через `!reference`

Используется для переиспользования общих фрагментов скрипта без потери специфики дочернего задания.

```yaml
# templates/common.yml
.setup_docker:
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY

# .gitlab-ci.yml
build:
  script:
    - !reference [.setup_docker, script]
    - docker build -t $IMG_NAME .
```

Подробнее о синтаксисе: **[Механизм !reference](./reference_and_yaml_anchors.md)**.

### Сценарий 3: Современный компонент с типизацией (GitLab 16+)

Рекомендуемый подход для крупных организаций, обеспечивающий стабильность и самодокументированность.

```yaml
# templates/deploy.yml (в проекте-каталоге)
spec:
  inputs:
    environment:
      description: "Целевое окружение"
      options: ["staging", "production"]
    replicas:
      type: number
      default: 2
---
deploy_job:
  script:
    - echo "Deploying to $[[ inputs.environment ]] with $[[ inputs.replicas ]] replicas"
```

Использование в проекте:
```yaml
include:
  - component: $CI_SERVER_FQDN/org/ci-components/deploy@1.2.0
    inputs:
      environment: "production"
```

## Валидация и отладка

Для проверки корректности сборки пайплайна используйте следующие инструменты:
1. **Pipeline Editor:** Вкладка "View merged YAML" показывает итоговый вид конфигурации после всех слияний.
2. **GitLab CLI (`glab`):** Команда `glab ci lint --show-expanded` позволяет валидировать локальные изменения перед коммитом.
3. **CI Lint API:** Программная проверка через HTTP-запросы (используется в CI-пайплайнах самих шаблонов).

Подробнее в руководстве: **[Валидация и версионирование](../Advanced/pipeline_validation_and_versioning.md)**.

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `circular reference detected` | Кольцевое наследование `extends` | Проверьте цепочку наследования, разорвите циклы. |
| Переменные из `include` не видны | Конфликт приоритетов | Проверьте итоговый YAML; локальные переменные всегда важнее. |
| Ошибка `inputs` | Несоответствие типа или отсутствие обязательного поля | Проверьте блок `spec:inputs` в подключаемом файле. |
| `include` не находит файл | Отсутствие прав или неверная ветка | Проверьте параметр `ref` и права доступа к проекту. |

## Ограничения и особенности

- **Лимит вложенности:** GitLab ограничивает глубину вложенных `include` (обычно до 50 уровней) и `extends` (до 11 уровней).
- **Порядок обработки:** 
  1. Разрешение `include`.
  2. Интерполяция `inputs`.
  3. Обработка `variables`.
  4. Применение `extends`.
  5. Разрешение `!reference`.
- **YAML Anchors:** Не работают между файлами. Всегда заменяйте их на `!reference` при выносе кода в шаблоны.
