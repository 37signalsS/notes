# Переиспользуемые пайплайны GitLab CI: Обзор

### Определения

**Переиспользуемые и композитные пайплайны** в GitLab CI — это подход к организации конфигурации CI/CD, который позволяет создавать модульные, легко управляемые и обновляемые пайплайны. Это достигается за счет повторного использования общих фрагментов кода и логики, избегая дублирования и упрощая поддержку.

- **`extends`**: Механизм, позволяющий заданию наследовать всю конфигурацию от одного или нескольких "скрытых" заданий (начинающихся с точки `.`). Это базовый способ переиспользования конфигураций внутри одного файла `.gitlab-ci.yml`.
- **`!reference`, YAML Anchors (`&`) и Aliases (`*`)**: Механизмы для повторного использования фрагментов конфигурации. `!reference` — это специальный тег GitLab CI, а YAML Anchors и Aliases — стандартный механизм YAML.
- **`include`**: Мощный механизм, позволяющий собрать пайплайн из нескольких YAML-файлов, расположенных локально, в других проектах, по удаленным URL или использовать встроенные шаблоны GitLab.
- **CI/CD Catalog (Components)**: Наиболее современный и рекомендуемый подход GitLab к переиспользованию, позволяющий создавать версионируемые, строго типизированные и публикуемые в общем каталоге компоненты — полноценные, изолированные блоки CI/CD логики.

### Основные концепции

#### Эволюция подходов к переиспользованию

| Подход | Уровень | Сложность | Версионирование | Изоляция |
| :--- | :--- | :--- | :--- | :--- |
| **YAML Anchors (`&`)** | Один файл | Низкая | Нет | Низкая |
| **`extends`** | Один файл / include | Средняя | Нет | Средняя |
| **`!reference`** | Один файл / include | Средняя | Нет | Средняя |
| **`include`** | Несколько файлов | Высокая | Рекомендуется теги | Высокая |
| **CI/CD Catalog** | Компоненты | Высокая | **Полное** (semver) | **Полная** |

#### Когда использовать каждый подход

- **YAML Anchors** — для простых повторений внутри одного файла (менее предпочтительно из-за ограниченной поддержки GitLab)
- **`extends`** — для наследования конфигураций между задачами в рамках одного проекта
- **`!reference`** — для вставки конкретных фрагментов (скриптов, переменных) без наследования всей конфигурации
- **`include`** — для модульной организации пайплайнов и шаринга между проектами
- **CI/CD Catalog** — для создания публичных или внутренних библиотек переиспользуемых компонентов с версионированием

### Практические сценарии

#### Сценарий 1: Выбор переиспользуемого пайплайна

| Сценарий | Рекомендуемый подход |
| :--- | :--- |
| Несколько jobs с одинаковой конфигурацией в одном файле | [`extends`](./extends_keyword.md) |
| Общие скрипты между jobs без полного наследования | [`!reference`](./reference_and_yaml_anchors.md) |
| Вынос конфигурации в отдельные файлы одного проекта | [`include:local`](./include_keyword.md) |
| Шаринг шаблонов между проектами | [`include:project`](./include_keyword.md) |
| Публичная библиотека компонентов | [CI/CD Catalog](./ci_cd_catalog_components.md) |

#### Сценарий 2: Эволюция от простого к сложному

1. **Начальный этап**: Используйте `extends` для базовых job-шаблонов внутри одного `.gitlab-ci.yml`
2. **Рост проекта**: Вынесите общие шаблоны в отдельные файлы и подключайте через `include`
3. **Масштабирование**: Создайте централизованный репозиторий шаблонов и используйте `include:project` с тегами
4. **Зрелость**: Переходите на CI/CD Catalog для строгого версионирования и типизированных интерфейсов

Подробный пример эволюции см. в статье: **[Эволюция переиспользуемых пайплайнов](./evolution_example.md)**.
