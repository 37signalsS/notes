# Переиспользуемые пайплайны GitLab CI: Обзор

## Определения

**Переиспользуемые и композитные пайплайны** в GitLab CI — это системный подход к проектированию CI/CD, направленный на создание модульных, версионируемых и легко сопровождаемых конфигураций. Основная цель — исключение дублирования кода (DRY), стандартизация процессов безопасности и ускорение разработки за счет использования готовых блоков.

### Ключевые механизмы

| Механизм | Назначение | Уровень |
| :--- | :--- | :--- |
| **`extends`** | Наследование конфигурации от скрытых заданий (начинаются с `.`) | Внутри файла / `include` |
| **`!reference`** | Явная вставка фрагментов кода (скриптов, правил) без наследования | Внутри файла / `include` |
| **`include`** | Подключение внешних файлов (local, project, remote, template) | Межпроектный |
| **`inputs`** | Типизированная параметризация подключаемых файлов через `$[[ inputs.key ]]` | Межпроектный |
| **CI/CD Catalog** | Реестр версионируемых и документированных компонентов (Stage 5) | Корпоративный / Global |
| **`trigger`** | Запуск дочерних (Downstream) пайплайнов для изоляции контекста | Пайплайн целиком |

> **Внимание:** YAML Anchors (`&` / `*`) являются стандартом YAML, но имеют серьезное ограничение — они не работают между разными файлами. В современных пайплайнах их рекомендуется заменять на `!reference` или `inputs`.

## Основные концепции

### Эволюция подходов к переиспользованию

Развитие CI/CD в организации обычно проходит через несколько этапов зрелости. Подробный разбор представлен в статье **[Эволюция переиспользуемых пайплайнов](./evolution_example.md)**.

1.  **Stage 1: Boilerplate** — Копирование YAML-кода между проектами.
2.  **Stage 2: include:project** — Централизация логики в едином репозитории.
3.  **Stage 3: extends** — Добавление гибкости через наследование.
4.  **Stage 4: Abstraction** — Сокрытие деталей реализации (например, Kaniko).
5.  **Stage 5: CI/CD Catalog** — Переход к типизированным компонентам с SemVer.
6.  **Stage 6: GitLab Steps** — (Будущее) Глубокая изоляция шагов сборки и отказ от Bash-скриптов.

### Принципы слияния конфигураций

При использовании `extends` и `include` GitLab применяет механизм **обратного глубокого слияния (reverse deep merge)**. Дочернее задание имеет приоритет и переопределяет ключи родительского.
- **Массивы:** (например, `script`) полностью замещаются, а не дополняются.
- **Хеши:** (например, `variables`) сливаются по ключам.

Детальные правила описаны в SSoT-документе: **[Механизм `extends`](./extends_keyword.md)**.

### Безопасность и политики исполнения

Современные корпоративные стандарты требуют не только переиспользования, но и принудительного исполнения проверок:
- **Pipeline Execution Policies:** Механизм принудительного внедрения заданий безопасности (сканеры, проверки) на уровне группы, которые невозможно пропустить или переопределить в дочернем проекте.
- **Zero Trust CI_JOB_TOKEN:** С версии GitLab 17.0 доступ токена к другим проектам должен быть явно разрешен в настройках (Allowlist), что предотвращает утечку данных через переиспользуемые скрипты.

## Практические сценарии

### Выбор оптимального инструмента

| Сценарий | Рекомендуемый подход | Обоснование |
| :--- | :--- | :--- |
| Повтор кода в одном файле | [`extends`](./extends_keyword.md) | Минимальная сложность |
| Вставка части скрипта в разные задания | [`!reference`](./reference_and_yaml_anchors.md) | Избежание дублирования Bash-логики |
| Стандарт сборки для всей группы проектов | `include:project` + `inputs` | Централизация с валидацией параметров |
| Публикация инструмента для всей компании | [CI/CD Catalog](./ci_cd_catalog_components.md) | Версионирование (SemVer) и UI-каталог |

### Пример современного компонента (GitLab 16+)

Использование `spec:inputs` обеспечивает строгую типизацию и предотвращает ошибки конфигурации.

```yaml
# templates/security-scan.yml
spec:
  inputs:
    scanner_type:
      default: "trivy"
      options: ["trivy", "gitleaks"]
    fail_on_error:
      type: boolean
      default: true
---
scan_job:
  script:
    - run_scan --type $[[ inputs.scanner_type ]] --strict $[[ inputs.fail_on_error ]]
```
