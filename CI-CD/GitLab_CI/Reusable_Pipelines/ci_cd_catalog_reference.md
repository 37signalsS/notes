# GitLab CI: Каталог компонентов — справочная информация

## Определения

**Справочная информация** — технические подробности, параметры API, команды CLI и история изменений CI/CD Components, дополняющие основные концептуальные документы.

**Валидация компонента** — процесс автоматической проверки синтаксиса, структуры `spec:inputs` и корректности интерполяции переменных перед публикацией или использованием.

**Публикация** — процесс регистрации Git-тега репозитория в общем каталоге GitLab для обеспечения его доступности другим проектам.

## Основные концепции

### Структура проекта компонента

Для корректной работы каталога и поддержки вложенности репозиторий должен следовать стандартной иерархии:

```text
├── templates/
│   ├── build.yml         # Основной файл компонента (содержит spec: и ---)
│   ├── deploy.yml        # Дополнительный компонент в том же проекте
│   └── security/
│       └── scan.yml      # Вложенная структура разрешена
├── tests/                # Рекомендуемая папка для интеграционных тестов
├── README.md             # Документация (автоматически парсится каталогом)
└── .gitlab-ci.yml        # Пайплайн для CI/CD самого компонента
```

### Форматы версий компонентов

Для подключения компонентов через директиву `include:component` используются различные способы указания версии.

| Формат | Пример | Назначение |
| :--- | :--- | :--- |
| **SemVer (полный)** | `@1.2.0` | Стабильные релизы в продакшене. |
| **SemVer (частичный)** | `@1.2` или `@1` | Автоматическое получение patch/minor обновлений. |
| **Commit SHA** | `@e3262fd...` | Максимальная фиксация состояния (audit trail). |
| **~latest** | `@~latest` | Последняя стабильная версия (требует наличия релиза). |
| **Ветка** | `@main` | Исключительно для разработки и тестирования. |

> **Best Practice (Безопасность):** Для критически важных пайплайнов в продакшене рекомендуется использовать **Commit SHA**. Это единственный надежный способ защиты от «отравления» цепочки поставок (Supply Chain Attack), так как Git-теги могут быть перемещены или удалены.

### Правила разрешения версий

При возникновении неоднозначности GitLab следует приоритетам:

1.  При совпадении имени тега и SHA — приоритет отдаётся **SHA**.
2.  При совпадении имени тега и ветки — приоритет отдаётся **тегу**.
3.  Указатель `~latest` игнорирует pre-release версии (например, `1.0.1-rc`).
4.  Частичные версии (например, `@1.2`) автоматически разрешаются до последнего доступного patch-релиза в рамках этой минорной версии.

### Управление публикацией и аналитика

**Publication Allowlist (18.7+):**
Администраторы могут ограничивать список проектов, имеющих право публиковать компоненты в корпоративный каталог. Это предотвращает появление в каталоге черновиков и непроверенных решений.
`Settings -> CI/CD -> Catalog -> Publication Allowlist`

**Аналитика компонентов (19.0+):**
В каталоге появилась панель аналитики (Components Analytics), которая показывает:
- **Общая статистика:** количество использований и уровень адаптации в организации.
- **Детальный аудит (Ultimate):** список всех проектов и конкретных версий, использующих компонент. Позволяет выявлять проекты на уязвимых версиях.

### Динамический выбор входных данных (18.7)

При ручном запуске пайплайна через интерфейс GitLab («Run Pipeline») теперь поддерживаются каскадные списки. Значения в одном поле `inputs` могут автоматически фильтроваться в зависимости от выбора в предыдущем, что значительно упрощает конфигурацию сложных систем.

## Практические сценарии

### Сценарий 1: Валидация через CLI и API

**Использование GitLab CLI (`glab`):**
Проверка итогового YAML после обработки всех `include` и `extends` является обязательным шагом перед коммитом.

```bash
# 1. Проверка синтаксиса текущего проекта
glab ci lint

# 2. Просмотр полностью развернутой конфигурации (expanded)
glab ci lint --show-expanded

# 3. Валидация компонента в контексте другого проекта
glab ci lint --project my-org/target-app --show-expanded
```

**Использование API:**
Позволяет автоматизировать проверки во внешних инструментах.

```bash
curl --request POST --header "PRIVATE-TOKEN: <token>" \
  "https://gitlab.example.com/api/v4/projects/<id>/ci/lint" \
  --data '{"content": "include:\n  - component: $CI_SERVER_FQDN/group/comp@1.0.0"}'
```

### Сценарий 2: Публикация компонента

Для появления компонента в каталоге необходимо выполнение условий:
1. Наличие файла в папке `templates/` (с блоком `spec:`).
2. Наличие тега в формате SemVer.
3. Созданный GitLab Release, привязанный к этому тегу.

**Пример задания для автоматизации релиза:**

```yaml
release:
  stage: deploy
  image: registry.gitlab.com/gitlab-org/release-cli:latest
  rules:
    - if: $CI_COMMIT_TAG =~ /^v\d+\.\d+\.\d+$/
  script:
    - echo "Publishing component version $CI_COMMIT_TAG"
  release:
    tag_name: $CI_COMMIT_TAG
    name: "Release $CI_COMMIT_TAG"
    description: "Component release version $CI_COMMIT_TAG. See CHANGELOG.md for details."
```

### Сценарий 3: Устранение типичных ошибок

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Spec must be a valid json schema` | Ошибка в блоке `spec:inputs` | Проверьте отступы и наличие двоеточия после `spec:`. |
| `content not found` | Версия не существует или нет доступа | Проверьте тег/SHA и права доступа к репозиторию компонента. |
| `invalid input type` | Тип значения не совпадает с `type` | Убедитесь, что передаёте string, boolean или number согласно схеме. |
| `regex validation failed` | Значение не прошло проверку regex | Скорректируйте передаваемое значение согласно регулярному выражению в `inputs`. |

### Сценарий 4: Поиск компонентов через API

Для построения собственных дэшбордов или инструментов автоматизации можно использовать эндпоинты каталога.

```bash
# Список всех доступных компонентов проекта
curl --header "PRIVATE-TOKEN: <token>" \
  "https://gitlab.example.com/api/v4/projects/<id>/ci/components"

# Детальная информация о конкретной версии компонента
curl --header "PRIVATE-TOKEN: <token>" \
  "https://gitlab.example.com/api/v4/projects/<id>/ci/components/<name>/versions/1.0.0"
```

## Дополнительная информация

### Сводная таблица API и CLI

| Инструмент | Команда / Эндпоинт | Назначение |
| :--- | :--- | :--- |
| **API** | `GET /projects/:id/ci/components` | Список компонентов в проекте. |
| **API** | `POST /projects/:id/ci/lint` | Валидация пайплайна (с параметром `include_merged_yaml=true`). |
| **CLI** | `glab ci lint` | Проверка синтаксиса и раскрытие YAML. |
| **Git** | `git tag -a v1.0.0` | Создание версии для публикации. |

### История изменений

| Версия GitLab | Статус / Изменение |
| :--- | :--- |
| **16.10** | SemVer стал обязательным для публикации в каталоге. |
| **17.0** | Статус General Availability (GA). Лимит размера YAML увеличен до 5МБ. |
| **18.6** | Введена интерполяция контекста компонента через `$[[ component.* ]]`. |
| **18.7** | Динамические формы ввода в UI, Publication Allowlist и статус GA для контекстной интерполяции. |
| **19.0** | Аналитика использования компонентов (Components Analytics) и фиксация входов при инициализации. |

### Интерполяция контекста компонента

Начиная с версии 18.6, компоненты могут обращаться к собственным метаданным без необходимости передачи их через `inputs`. Это позволяет создавать более универсальные решения.

| Поле | Описание | Пример значения |
| :--- | :--- | :--- |
| `$[[ component.name ]]` | Имя текущего компонента. | `docker-build` |
| `$[[ component.version ]]` | Версия (тег или SHA), указанная при вызове. | `1.5.2` |
| `$[[ component.sha ]]` | Полный Commit SHA версии компонента. | `e3262fdb...` |

**Пример использования:**
Автоматический выбор образа инструментов, версия которого совпадает с версией компонента.

```yaml
build-task:
  image: custom-registry/ci-tools:$[[ component.version ]]
  script:
    - run-build.sh
```
