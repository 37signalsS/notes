# GitLab CI: Каталог компонентов — ограничения

## Определения

**Лимит компонентов** — системное ограничение GitLab на количество уникальных CI/CD компонентов (определяемых по путям в директории `templates/`), которое может содержать один проект, помеченный как ресурс каталога.

**Лимит вложенности include** — совокупное ограничение на количество YAML-файлов, которые могут быть импортированы в рамках одного процесса компиляции пайплайна. Учитывает локальные файлы, проекты, удаленные ресурсы и компоненты.

**Глобальные ключи (Global Keywords)** — зарезервированные директивы GitLab CI (`stages`, `default`, `workflow`, `variables` верхнего уровня), определяющие поведение всего конвейера. Большинство из них запрещены в компонентах для обеспечения их функциональной изоляции.

**Раскрытая конфигурация (Expanded YAML)** — итоговый объект конфигурации, полученный после завершения всех операций импорта (`include`), наследования (`extends`) и разрешения параметров (`inputs`). Именно этот объект проходит финальную валидацию на стороне сервера.

## Основные концепции

### Количественные ограничения (Актуально на 2026 год)

Ограничения введены для предотвращения атак типа «отказ в обслуживании» (DoS) на парсер YAML и обеспечения стабильной производительности сервера при генерации графа задач.

| Ограничение | Значение | Версия GitLab | Архитектурный контекст |
| :--- | :--- | :--- | :--- |
| **Максимум компонентов на проект** | **100** | 18.5+ | Лимит на количество YAML-файлов в `templates/` проекта-ресурса. |
| **Лимит вложенности include** | **150** | Все | Суммарное количество узлов в дереве зависимостей `include`. |
| **Глубина цепочки компонентов** | **10** | Все | Лимит на последовательное подключение: `A -> B -> ... -> J`. |
| **Максимальное количество заданий** | **1000** | Все | Общий лимит `jobs` в одном пайплайне после раскрытия всех циклов. |
| **Размер раскрытого YAML** | **5 МБ** | 17.0+ | Объем текстовых данных, передаваемых на обработку GitLab Rails. |
| **Максимум входов (spec:inputs)** | **50** | 16.10+ | Лимит уникальных параметров в секции спецификации одного файла. |
| **Рекурсия переменных** | **10** | Все | Глубина разрешения вложенных переменных в блоке `variables`. |

### Структурные ограничения и изоляция

Для обеспечения «чистоты» компонентов и исключения побочных эффектов при их подключении, GitLab накладывает жесткие правила на содержимое YAML-файлов компонентов (секция после разделителя `---`):

1.  **Запрет глобальных конфигураций:**
    - `stages:` — Компонент не должен навязывать структуру стадий всему проекту. Имена стадий должны передаваться через `inputs`.
    - `default:` — Настройки (например, `image` или `before_script` по умолчанию) запрещены, так как они глобально влияют на все задания проекта, включая те, что не относятся к компоненту.
    - `workflow:` — Логика запуска пайплайна (trigger rules) всегда находится на стороне проекта-потребителя.
2.  **Ограничения секции спецификации (`spec:`):**
    - В блоке `spec:` разрешен только ключ `inputs`.
    - Нельзя использовать `include` внутри `spec:`. Все зависимости компонента должны описываться в секции реализации (после `---`).
3.  **Порядок интерполяции:**
    - `inputs` разрешаются на самом раннем этапе — **до** обработки `variables` и `extends`. Это делает невозможным динамическое формирование имен переменных через инпуты внутри одного и того же блока `variables`.

## Практические сценарии

### Предварительные условия

Для аудита и управления лимитами необходимо:
1. Доступ к GitLab CLI (`glab`) версии 1.40+.
2. Права `Owner` для изменения настроек Self-Managed инстанса.
3. Установленная утилита `yq` для анализа сложных структур.

### Сценарий 1: Аудит потребления ресурсов пайплайном

При проектировании корпоративной библиотеки важно понимать запас прочности по лимитам.

```bash
# 1. Подсчёт количества уникальных компонентов в репозитории
find templates/ -name "*.yml" | grep -v "test" | wc -l

# 2. Получение полностью развернутого YAML для замера объема
# ВАЖНО: Команда учитывает все вложенные include и расширение inputs
glab ci lint --show-expanded > full_pipeline.yml

# 3. Проверка размера итогового файла (лимит 5МБ)
du -h full_pipeline.yml

# 4. Анализ количества заданий после раскрытия (лимит 1000)
grep "^[a-zA-Z0-9_-]\+:" full_pipeline.yml | grep -v "inputs:" | wc -l
```

### Сценарий 2: Стратегии обхода лимита вложенности (Include optimization)

Если ваша архитектура CI/CD достигает порога в 150 файлов, используйте следующие паттерны оптимизации:

1.  **Паттерн «Плоская композиция»:** Вместо иерархии `App -> Library -> Base -> OS`, подключайте все зависимости параллельно в корневом `.gitlab-ci.yml`. Это уменьшает глубину дерева и делает связи явными.
2.  **Использование `!reference`:** Вместо выноса каждой мелкой функции в отдельный YAML-файл (создающий `include`), используйте один «файл-словарь» со скрытыми заданиями. Подключайте его один раз и вставляйте блоки кода через `!reference`.
3.  **OCI-компоненты (Будущее):** Рассмотрите возможность публикации компонентов как артефактов в Container Registry (если поддерживается версией), что ускоряет загрузку по сравнению с Git-протоколом.

### Сценарий 3: Решение конфликтов стадий

Поскольку `stages` запрещены в компонентах, используйте паттерн «Динамическая стадия».

**Файл компонента (`templates/build.yml`):**
```yaml
spec:
  inputs:
    stage:
      default: build
---
job_name:
  stage: $[[ inputs.stage ]]
  script:
    - make build
```

**Файл проекта:**
```yaml
stages:
  - compile
  - deploy

include:
  - component: $CI_SERVER_FQDN/org/build@1.0.0
    inputs:
      stage: compile # Явное сопоставление со стадией проекта
```

## Валидация и устранение неполадок

### Инструменты диагностики

- **CI Lint API:** Основной инструмент для проверки лимитов до коммита. Возвращает детальные сообщения о нарушении структурных ограничений.
- **Pipeline Editor:** Вкладка "View merged YAML" визуально подсвечивает ошибки интерполяции `inputs`.

### Типичные ошибки и способы решения

| Ошибка | Причина | Способ исправления |
| :--- | :--- | :--- |
| `Too many includes` | Дерево импортов > 150 узлов. | Объедините мелкие `local include` файлы. Используйте `!reference` для фрагментов кода. |
| `Component limit reached` | В проекте-каталоге > 100 файлов в `templates/`. | Разделите одну огромную библиотеку на несколько специализированных (например, `infra-catalog`, `app-catalog`). |
| `Invalid global key: default` | Использование блока `default` в компоненте. | Перенесите настройки (image, tags) непосредственно в задания компонента или используйте скрытые задания (`.base`). |
| `Expanded YAML too large` | Итоговый конфиг > 5 МБ. | Сократите количество комментариев в шаблонах. Используйте наследование `extends` вместо копирования блоков. |
| `Maximum levels of inheritance` | Глубина `extends` > 11. | Упростите иерархию шаблонов. Старайтесь не превышать 3-4 уровня вложенности. |
