# GitLab CI: Каталог компонентов — ограничения

## Определения

**Лимит компонентов** — максимальное количество CI/CD компонентов, которое может содержать один проект GitLab.

**Лимит вложенности include** — системное ограничение на количество директив `include`, обрабатываемых при компиляции одного пайплайна (включая компоненты, проекты, локальные файлы и шаблоны).

**Глобальные ключи** — директивы верхнего уровня (`stages:`, `default:`, `workflow:`), которые управляют поведением всего пайплайна и запрещены внутри компонентов для обеспечения их модульности и изоляции.

**Раскрытая конфигурация (Expanded YAML)** — финальный YAML-файл, сформированный после выполнения всех инструкций `include`, `extends` и завершения интерполяции `inputs`.

## Основные концепции

### Количественные ограничения (2026)

| Ограничение | Значение | Версия GitLab | Технический контекст |
| :--- | :--- | :--- | :--- |
| **Максимум компонентов на проект** | **100** | 18.5+ | Применяется к количеству уникальных путей в `templates/`. |
| **Лимит вложенности include** | **150** | Все | Общее количество файлов в «дереве» импортов. |
| **Глубина вложенности компонентов** | **10** | Все | Максимальное количество уровней цепочки `component A -> B -> C`. |
| **Максимальное количество заданий** | **1000** | Все | Общий лимит `jobs` после всех раскрытий. |
| **Размер раскрытого YAML** | **5 МБ** | 17.0+ | Объем итоговой конфигурации для обработки сервером. |
| **Максимум входов (spec:inputs)** | **50** | 16.10+ | Лимит уникальных ключей в секции спецификации одного файла. |
| **Рекурсия переменных** | **10** | Все | Глубина вложенности при раскрытии `$VARIABLE_A: $VARIABLE_B`. |

### Эволюция лимитов (Архив изменений)

| Версия GitLab | Лимит компонентов | Ключевое изменение |
| :--- | :--- | :--- |
| 16.0 – 16.8 | 10 | Начальный релиз механизма Catalog. |
| 16.9 – 18.4 | 30 | Поддержка средних корпоративных библиотек. |
| 18.5+ | 100 | Текущий стандарт для крупных Enterprise-платформ. |

### Структурные и логические ограничения

Для предотвращения коллизий и обеспечения предсказуемости поведения, внутри файлов компонентов (секция после `---`) запрещено использование:

1.  **Глобальные ключи:**
    - `stages:` — Должны определяться только в корневом `.gitlab-ci.yml`. Компоненты должны использовать стандартные стадии или `inputs` для выбора стадии.
    - `default:` — Настройки (например, `before_script` или `image` по умолчанию) должны быть локализованы внутри заданий компонента.
    - `workflow:` — Логика запуска всего пайплайна находится в зоне ответственности владельца проекта.
2.  **Спецификация (spec:):**
    - В секции спецификации (до `---`) запрещено использовать любые ключи, кроме `inputs`.
    - `include` внутри `spec:` запрещен. Импорты других компонентов возможны только в секции конфигурации.
3.  **Интерполяция:**
    - `inputs` интерполируются **до** обработки `extends` и `variables`. Это означает, что `inputs` нельзя использовать для динамического формирования имен переменных, которые будут использоваться в том же блоке `variables`.

## Практические сценарии

### Сценарий 1: Аудит использования лимитов

Для крупных инстансов важно отслеживать потребление ресурсов пайплайнами.

```bash
# Подсчёт количества файлов компонентов в репозитории
find templates/ -name "*.yml" | wc -l

# Проверка пайплайна на лимит include через GitLab CLI
glab ci lint --show-expanded > expanded.yml
ls -lh expanded.yml # Контроль размера 5МБ
```

### Сценарий 2: Управление лимитами в Self-Managed (Admin)

Администраторы могут корректировать лимит вложенности `include`, если архитектура компании требует глубоких иерархий.

**Настройка через консоль Rails (при критических проблемах):**

```ruby
# Изменение лимита include до 200
ApplicationSetting.current.update(ci_max_includes: 200)
```

**Через API:**

```bash
curl --request PUT --header "PRIVATE-TOKEN: <admin_token>" \
  "https://gitlab.example.com/api/v4/application/settings?ci_max_includes=200"
```

### Сценарий 3: Стратегии обхода ограничений (White spots)

При достижении лимитов рекомендуется применять следующие паттерны:

-   **Композиция вместо вложенности:** Избегайте «матрёшек» (`A include B include C`). Подключайте все нужные компоненты параллельно в основном `.gitlab-ci.yml`.
-   **Использование !reference:** Если вам нужно переиспользовать фрагмент кода 50 раз, `!reference` не создает дополнительных HTTP-запросов и не увеличивает счетчик `include`.
-   **Пре-компиляция:** Для экстремально сложных пайплайнов используйте [Dynamic Child Pipelines](../Advanced/Downstream_Pipelines/parent_child_pipelines.md), где часть YAML генерируется скриптом на лету.

## Дополнительная информация

### Диагностика типичных ошибок

| Сообщение об ошибке | Причина | Решение |
| :--- | :--- | :--- |
| `Too many includes` | Достигнут порог в 150 файлов. | Проверьте циклические зависимости и объедините мелкие `local include`. |
| `Component limit reached` | В проекте более 100 компонентов. | Разделите библиотеку на несколько специализированных проектов (например, `net-tools`, `build-tools`). |
| `Invalid global key: stages` | Попытка задать `stages` в компоненте. | Удалите блок `stages` из файла компонента. Передавайте имя стадии через `inputs`. |
| `Expanded YAML too large` | Итоговый файл > 5 МБ. | Удалите избыточные комментарии, используйте YAML Anchors для сокращения повторяющихся блоков. |
