# GitLab CI: Каталог компонентов — ограничения

## Определения

**Лимит компонентов** — максимальное количество CI/CD компонентов, которое может содержать один проект GitLab.

**Лимит вложенности include** — максимальное количество директив `include`, которые могут быть обработаны при построении одного пайплайна (включая компоненты, проекты, шаблоны).

**Глобальные ключи** — директивы верхнего уровня (`stages:`, `default:`, `workflow:`), влияющие на весь пайплайн целиком и запрещённые внутри компонентов для обеспечения их изоляции.

**Раскрытая конфигурация (Expanded YAML)** — итоговый YAML-файл, сформированный после выполнения всех инструкций `include`, `extends` и интерполяции `inputs`.

## Основные концепции

### Количественные ограничения

| Ограничение | Значение | Версия GitLab | Примечание |
| :--- | :--- | :--- | :--- |
| Максимум компонентов на проект | **100** | 18.5+ | До 18.5 — 30 компонентов, до 16.9 — 10 компонентов |
| Лимит вложенности include | **150** | Все | Для self-managed настраивается через `ci_max_includes` |
| Глубина вложенности компонентов | **10** | Все | Максимальное количество уровней "компонент внутри компонента" |
| Максимальное количество заданий | **1000** | Все | Общий лимит заданий (jobs) в одном пайплайне |
| Размер раскрытого YAML | **5 МБ** | 17.0+ | До 17.0 лимит составлял 1 МБ для некоторых инстансов |

### Эволюция лимита компонентов

| Версия GitLab | Лимит | Изменение |
| :--- | :--- | :--- |
| 16.0 – 16.8 | 10 | Начальный лимит |
| 16.9 – 18.4 | 30 | Увеличен в 3 раза |
| 18.5+ | 100 | Увеличен в 3.3 раза |

### Структурные и логические ограничения

Внутри файлов компонентов запрещено использование следующих ключей для предотвращения конфликтов с основной конфигурацией проекта:

1. **Глобальные ключи:**
    - `stages:` — этапы должны определяться в корневом файле пайплайна.
    - `default:` — настройки по умолчанию не должны распространяться за пределы компонента.
    - `workflow:` — правила создания пайплайна управляются на уровне проекта.
2. **Директива `spec:include`**: компоненты должны быть самодостаточными. Они могут содержать `include` только в секции конфигурации (после `---`), но не в секции спецификации (`spec:`).
3. **Версионирование**: для публикации в каталоге обязательно использование SemVer (например, `1.2.3`). Использование веток (`@main`) разрешено только для локального тестирования.

## Практические сценарии

### Сценарий 1: Проверка количества компонентов в проекте

Для оценки текущего использования лимита компонентов можно использовать CLI или API GitLab.

```bash
# Подсчёт количества файлов конфигурации компонентов в репозитории
git ls-files '**/.gitlab-ci.yml' | wc -l

# Получение списка компонентов через API
curl --header "PRIVATE-TOKEN: <your_token>" \
  "https://gitlab.example.com/api/v4/projects/<project_id>/ci/components"
```

### Сценарий 2: Увеличение лимита include в Self-Managed экземплярах

Администраторы могут изменить глобальный лимит вложенности при наличии архитектурной необходимости.

**Через интерфейс администратора:**

1. Перейдите в `Admin > Settings > CI/CD > General Pipelines`.
2. Найдите параметр `Maximum includes` (по умолчанию 150).
3. Установите новое значение и сохраните изменения.

**Через API:**

```bash
curl --request PUT --header "PRIVATE-TOKEN: <admin_token>" \
  "https://gitlab.example.com/api/v4/application/settings" \
  --data "ci_max_includes=200"
```

### Сценарий 3: Оптимизация при достижении лимитов

Если пайплайн приближается к лимиту в 150 include или 5 МБ размера, рекомендуется:

- **Консолидация**: Объединять логически связанные задания в один компонент.
- **Использование `!reference`**: Замена множественных `include:local` на вставки фрагментов кода внутри одного файла.
- **Очистка конфигурации**: Использование `rules` вместо создания множества дублирующих заданий с разными условиями.
- **Уменьшение вложенности**: Избегайте цепочек, где один компонент включает в себя другой без явной необходимости.

## Дополнительная информация

### Валидация ограничений

Для проверки конфигурации на соответствие лимитам используйте инструмент CI Lint перед пушем изменений.

```bash
# Проверка конфигурации с раскрытием всех include и оценкой размера
glab ci lint --show-expanded
```

### Типичные ошибки и их причины

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Too many includes` | Превышен лимит 150 подключений | Уменьшите количество `include` или используйте `!reference` |
| `Component limit reached` | Превышен лимит 100 компонентов в проекте | Распределите компоненты по разным репозиториям |
| `Invalid global key in component` | Использование `stages:` или `default:` в компоненте | Перенесите эти ключи в основной `.gitlab-ci.yml` проекта |
| `Expanded YAML too large` | Размер файла после интерполяции превысил 5 МБ | Оптимизируйте скрипты и переменные, удалите дублирование |
