# Паттерны CI/CD

## Определения

**Паттерн CI/CD** — проверенный, эффективный и воспроизводимый подход к решению типовых задач в процессах непрерывной интеграции, доставки и развертывания. Применение паттернов направлено на минимизацию рисков при релизах, сокращение Time-to-Market и повышение стабильности систем.

Паттерны являются прямыми решениями для соответствующих [анти-паттернов CI/CD](./ci_cd_antipatterns.md).

## Основные концепции

### Ключевые паттерны поставки

Для построения надежных и быстрых пайплайнов используются следующие паттерны:

1. **Trunk-Based Development (TBD):** Модель разработки с единой основной веткой. Минимизирует "ад слияния" (merge hell) и ускоряет интеграцию. Подробности в **[Рабочие процессы в Git](../Git/git_workflows.md#3-trunk-based-development-tbd)**.
2. **Feature Flags (фиче-флаги):** Управление доступностью кода во время выполнения. Позволяет разделять деплой (доставку кода) и релиз (открытие функционала пользователям). См. **[Обзор Feature Toggles](./Testing/feature_toggles/overview.md)**.
3. **Fail Fast (быстрый отказ):** Проектирование пайплайна таким образом, чтобы самые быстрые и критичные проверки (линтинг, unit-тесты) выполнялись первыми. Если они не проходят, пайплайн останавливается немедленно, экономя время и ресурсы.
4. **Build Once, Deploy Many (сборка один раз):** Создание **Immutable Artifacts** (иммутабельных артефактов) на раннем этапе. Один и тот же бинарный файл или Docker-образ проходит через все окружения, что исключает ошибки из-за разницы в процессе сборки. См. **[Управление артефактами](./artifact_management.md)**.
5. **Separation of Config and Code:** Вынос всех настроек, специфичных для окружений, за пределы кода и артефакта (использование переменных окружения, секретов, ConfigMap). Это позволяет одному артефакту работать в любой среде.

### Классификация паттернов

* **Организационные:** TBD, Branch Protection (правила защиты веток) — определяют культуру взаимодействия и политики безопасности.
* **Технические:** Feature Flags, Immutable Artifacts, Fail Fast — реализуются на уровне архитектуры приложения и конфигурации пайплайнов.
* **Релизные:** Blue/Green, Canary, Dark Launches — паттерны развертывания, направленные на минимизацию рисков для пользователей. См. **[Стратегии развертывания](./Deployment_Strategies/comparison.md)**.

## Практические сценарии

### Комбинирование паттернов в пайплайне

Типовой жизненный цикл изменения с применением комплекса паттернов:

1. **Разработка (TBD + Fail Fast):**
    * Создается короткоживущая ветка. При пуше в CI сначала запускаются линтеры и тесты (Fail Fast).
    * Новая функциональность инкапсулируется в **[фиче-флаг](./Testing/feature_toggles/overview.md)**.

2. **Сборка и Продвижение (Build Once + Config Separation):**
    * После слияния с `main` собирается один Docker-образ (Build Once).
    * Этот образ развертывается на Staging, а затем на Production. Различия (URL БД, ключи API) передаются через переменные окружения (Separation of Config and Code).

3. **Релиз (Feature Flags + Decoupling):**
    * Код уже в продакшене, но фича выключена флагом.
    * Релиз происходит путем переключения флага для группы пользователей (Canary) или для всех сразу, без пересборки и нового деплоя.

4. **Откат (Rollback):**
    * В случае проблем фича мгновенно выключается флагом. Если проблема в инфраструктуре — выполняется откат на предыдущую версию иммутабельного артефакта.
