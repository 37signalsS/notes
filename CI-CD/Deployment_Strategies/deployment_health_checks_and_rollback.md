# Проверки здоровья (Health Checks) и Откат (Rollback)

## Определения

**Проверки здоровья (Health Checks)** — это основной механизм принятия решений при Blue-Green и Canary-развертываниях. Они позволяют автоматически определять готовность новой версии к приёму трафика, фиксировать деградации и инициировать откат до стабильной версии. Качество сигналов и строгость порогов напрямую влияют на скорость и безопасность выпуска.

## Основные концепции

### Виды проверок здоровья (Probes)

| Вид проверки | Цель | Источник сигнала | Когда срабатывает | Риск ошибок |
| :--- | :--- | :--- | :--- | :--- |
| **Liveness** | Обнаружить зависшее/зациклённое приложение. | Локальная проверка процесса. | Рестарт контейнера/сервиса. | Ложноположительные → флип-флоп рестарты. |
| **Readiness** | Разрешить/запретить отправку трафика на инстанс. | Доступность зависимостей, пулов, кэшей. | Перед включением в балансировку. | Ложноотрицательные → простаивание ресурсов. |
| **Startup** | Дать время на "прогрев" тяжеловесного приложения. | Отложенная Liveness-проверка. | В начале жизненного цикла пода. | Медленное обнаружение реальных падений при запуске. |
| **Бизнес-эндпоинт** | Проверить критические пользовательские сценарии. | Синтетические тесты доменных операций. | Перед повышением доли трафика. | Сложность реализации и поддержки. |
| **Наблюдаемость** | Анализ метрик, логов, трейсов. | Ошибки 5xx, латентность, saturation. | Во время Canary / после переключения. | Требует зрелой системы телеметрии. |

> **Вывод**: Комбинация `Readiness` + бизнес-проверок + SLO-метрик дает наиболее надежный сигнал для автоматического принятия решений.

### Критерии успешности и автоматизация

*   **Метрики**: Уровень ошибок (5xx, failed requests), латентность (p95/p99), насыщение ресурсов (CPU/Memory/GC), скорость изменения.
*   **Пороговые правила**: «уровень ошибок < 1%, p95 < 300 мс, рост 4xx не более чем на 20%».
*   **Окна наблюдения**: Минимум 5–10 минут стабильности под реальным трафиком.
*   **Сравнительный анализ**: Сопоставление метрик канарейки с контрольной группой (стабильной версией).
*   **Гейты в пайплайне**: Повышение доли трафика только при прохождении всех критериев.

## Практические сценарии

### Пример конфигурации проб в Kubernetes

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: app
          image: registry/myapp:2.3.1
          ports:
            - containerPort: 8080
          # Проверка готовности к приему трафика
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 3
          # Проверка "живучести" приложения
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
          # Проверка для долгого старта
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            failureThreshold: 30
            periodSeconds: 5
```

### Пример автоматического отката

Пример шага в CI/CD пайплайне, который проверяет метрики канарейки и инициирует откат при деградации.

```bash
set -e

# Запрашиваем метрики из Prometheus
ERROR_RATE=$(curl -s "$PROM_URL/api/v1/query" --data-urlencode "query=rate(http_requests_errors_total{app="myapp",version="canary"}[5m]) / rate(http_requests_total{app="myapp",version="canary"}[5m])" | jq -r '.data.result[0].value[1]')
P95=$(curl -s "$PROM_URL/api/v1/query" --data-urlencode "query=histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{app="myapp",version="canary"}[5m])) by (le))" | jq -r '.data.result[0].value[1]')

# Сравниваем с пороговыми значениями
if (( $(echo "$ERROR_RATE > 0.01 || $P95 > 0.3" | bc -l) )); then
  echo "Degradation detected. Rolling back..."
  kubectl rollout undo deployment/myapp
  exit 1
fi
```

### Стратегии и практики отката

*   **Blue-Green**: Мгновенный возврат трафика на «синюю» среду. «Зеленая» среда сохраняется для расследования. Важно дождаться корректного завершения (`drain`) активных соединений.
*   **Canary**: Прекращение увеличения доли трафика и возврат веса маршрутизации к 100% на стабильную версию.
*   **Стандартные механизмы**:
    *   `kubectl rollout undo deployment/myapp`
    *   `helm rollback myapp <REVISION>`
*   **Feature Flags**: Отключение проблемной функции без полного отката, что снижает радиус поражения.
*   **Миграции данных**: Использование подхода `expand–migrate–contract` для обратной совместимости схемы. Откат на уровне схемы требует тщательного планирования до релиза.

## Дополнительная информация

### Типичные ошибки

*   `readinessProbe` проверяет только HTTP 200, но не проверяет доступность критически важных зависимостей (БД, кэш, очереди).
*   Слишком агрессивные пороги проверок, приводящие к каскадным перезапускам (`flip-flop`).
*   Отсутствие "прогрева" кэша и пулов соединений перед переключением в Blue-Green.
*   Откат к версии приложения, несовместимой с обновленной схемой БД или форматом сообщений в очередях.
*   Игнорирование сезонности трафика и типа пользовательской нагрузки при оценке метрик канарейки.
