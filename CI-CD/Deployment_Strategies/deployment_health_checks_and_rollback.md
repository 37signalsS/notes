# Проверки здоровья и откат развертывания

## Определения

**Проверка здоровья (Health Check)** — автоматизированный механизм оценки состояния приложения, используемый оркестраторами и CI/CD-системами для принятия решения о готовности новой версии к приему трафика или необходимости перезапуска.

**Откат (Rollback)** — процесс возврата системы к предыдущему стабильному состоянию (версии кода, конфигурации или схемы данных) при обнаружении аномалий или сбоев после выпуска.

## Основные концепции

### Механизмы проверок в Kubernetes

Kubernetes использует три типа проб для управления жизненным циклом контейнеров. Начиная с версии 1.24, поддерживается нативный протокол gRPC для всех типов проб.

| Тип пробы | Назначение | Реакция на сбой |
| :--- | :--- | :--- |
| **`startupProbe`** | Проверяет, завершилось ли ли длительное выполнение запуска (например, прогрев кэша). | Контейнер убивается и перезапускается. Остальные пробы отключены до успеха этой. |
| **`readinessProbe`** | Определяет, готов ли экземпляр принимать входящий трафик. | Под исключается из балансировки (**Service** / **Ingress**), но не перезапускается. |
| **`livenessProbe`** | Определяет работоспособность процесса (отсутствие дедлоков, зависаний). | Контейнер перезапускается согласно `restartPolicy`. |

**Ключевые параметры настройки:**
- `initialDelaySeconds`: Задержка перед первой проверкой.
- `periodSeconds`: Частота выполнения проверки.
- `failureThreshold`: Количество последовательных неудач до признания пробы проваленной.
- `terminationGracePeriodSeconds`: Время, выделяемое приложению на корректное завершение работы (**Graceful Shutdown**) перед принудительной остановкой при обновлении или откате.

### Управление историей и глубина отката

В Kubernetes Deployment параметр **`revisionHistoryLimit`** (по умолчанию 10) определяет количество старых **ReplicaSets**, сохраняемых в кластере. Это напрямую влияет на возможность быстрого отката через `kubectl rollout undo`: если лимит равен 0, мгновенный откат через оркестратор невозможен.

### Стратегии отката и их влияние

| Стратегия | Механизм | Время восстановления | Риски и особенности |
| :--- | :--- | :--- | :--- |
| **Rolling Update** | `kubectl rollout undo` | Среднее | Поэтапная замена; риск сосуществования двух "плохих" версий при медленном анализе. |
| **Blue-Green** | Переключение балансировщика | Мгновенное | Требует 2x ресурсов; самый безопасный метод для мгновенного восстановления. |
| **Canary** | Остановка раскатки (Abort) | Очень быстрое | Позволяет остановить влияние на малую долю пользователей. |
| **Feature Flags** | Выключение флага | Мгновенное | Позволяет скрыть проблемный функционал без передеплоя всего приложения. |

## Практические сценарии

### Настройка проб с поддержкой gRPC (Kubernetes 1.24+)

Использование нативного gRPC исключает необходимость включения дополнительных утилит (например, `grpc-health-probe`) в образ контейнера.

```yaml
spec:
  containers:
  - name: grpc-app
    image: my-grpc-server:v1.2.0
    readinessProbe:
      grpc:
        port: 9000 # Стандартный порт gRPC Health Check
      initialDelaySeconds: 5
```

### Автоматизированный откат в пайплайне

Пример логики для CI/CD (например, GitLab CI или Jenkins), которая выполняет откат при превышении порога ошибок в **Prometheus**.

```bash
# Получаем Error Rate за последние 5 минут
ERROR_RATE=$(curl -s "http://prometheus:9090/api/v1/query?query=rate(errors_total[5m])/rate(requests_total[5m])" | jq -r '.data.result[0].value[1]')

# Если ошибок > 5%, откатываем Deployment
if [ "$(echo "$ERROR_RATE > 0.05" | bc)" -eq 1 ]; then
  kubectl rollout undo deployment/web-app
  echo "Rollback initiated due to high error rate: $ERROR_RATE"
  exit 1
fi
```

### Анализ после отката (Post-mortem)

Откат — это только начало процесса исправления. Обязательные шаги после восстановления:
1. **Фиксация артефактов:** Сохранение логов и дампов памяти из "упавших" экземпляров (в K8s поды могут быть удалены сразу после отката).
2. **Анализ причин (Root Cause Analysis):** Почему Health Checks не выявили проблему до начала раскатки?
3. **Обновление стратегии:** Добавление новых тестов или корректировка порогов проб, чтобы предотвратить повторение инцидента.

## Дополнительная информация

### Типовые ошибки и ловушки

- **Слишком короткие таймауты:** Приводят к "ложным" откатам при временных сетевых задержках или высокой нагрузке на API.
- **Отсутствие проверки зависимостей:** `readinessProbe` должен возвращать успех только если доступны критичные зависимости (например, БД), иначе приложение начнет принимать запросы, которые не сможет обработать.
- **Игнорирование `revisionHistoryLimit`:** Установка малого значения лимита может привести к невозможности отката на версию N-2, если в кластере было несколько быстрых деплоев.
