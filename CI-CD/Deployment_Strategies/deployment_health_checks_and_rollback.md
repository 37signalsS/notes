# Проверки здоровья (Health Checks) и Откат (Rollback) в CI/CD

### Определения

- **Проверка здоровья (Health Check)**: В контексте развертывания — это автоматизированный сигнал, который сообщает CI/CD-системе о состоянии новой версии приложения. На основе этого сигнала принимается решение о продолжении выкатки или ее отмене.
- **Откат (Rollback)**: Автоматизированный или ручной процесс возврата к предыдущей стабильной версии приложения при обнаружении критической ошибки или деградации производительности в новой версии.

### Основные концепции

#### 1. Типы проверок как сигналы для автоматизации

Kubernetes предоставляет три основных типа проб, которые служат источниками сигналов для управления развертыванием.

- **`readinessProbe` (Проба готовности)**
  - **Сигнал:** "Готов ли экземпляр принимать трафик?" Используется для безопасного ввода новых версий в эксплуатацию.
  - **Подробнее:** [**Детальное описание Readiness Probes**](../../Kubernetes/Base/probes.md#2-readinessprobe-проба-готовности).
- **`livenessProbe` (Проба жизнеспособности)**
  - **Сигнал:** "Работает ли приложение, или оно зависло?" Используется для перезапуска нездоровых экземпляров.
  - **Подробнее:** [**Детальное описание Liveness Probes**](../../Kubernetes/Base/probes.md#1-livenessprobe-проба-жизнеспособности).
- **`startupProbe` (Проба запуска)**
  - **Сигнал:** "Завершило ли приложение свой долгий запуск?" Предотвращает преждевременные рестарты от `livenessProbe`.
  - **Подробнее:** [**Детальное описание Startup Probes**](../../Kubernetes/Base/probes.md#3-startupprobe-проба-запуска).

Помимо этого, ключевым сигналом является **анализ метрик наблюдаемости** (ошибки, задержка), что детально рассмотрено в [мониторинге Canary-развертываний](./canary_monitoring_and_gating.md).

#### 2. Принципы надежного отката

- **Автоматизация:** Решение об откате должно приниматься автоматически на основе метрик, а не человеком.
- **Скорость:** Процесс отката должен быть максимально быстрым, чтобы минимизировать влияние на пользователей.
- **Безопасность данных:** Стратегия отката должна учитывать совместимость с версией схемы БД.

### Практические сценарии

#### Сценарий 1: Конфигурация проб в Kubernetes

Этот пример показывает, как настроить все три типа проб для Deployment. Для более глубокого понимания конфигурации см. основной документ о пробах.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: app
          image: registry/myapp:2.3.1
          ports:
            - containerPort: 8080
          # Проверка готовности к приему трафика
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 3
          # Проверка "живучести" приложения
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
          # Проверка для долгого старта
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            failureThreshold: 30
            periodSeconds: 5
```

#### Сценарий 2: Автоматический откат на основе метрик

Этот шаг в CI/CD пайплайне проверяет метрики Canary-версии и инициирует откат при деградации.

```bash
set -e

# Запрашиваем метрики из Prometheus
ERROR_RATE=$(curl -s "$PROM_URL/api/v1/query" --data-urlencode "query=rate(http_requests_errors_total{app="myapp",version="canary"}[5m]) / rate(http_requests_total{app="myapp",version="canary"}[5m])" | jq -r '.data.result[0].value[1]')
P95=$(curl -s "$PROM_URL/api/v1/query" --data-urlencode "query=histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket{app="myapp",version="canary"}[5m])) by (le))" | jq -r '.data.result[0].value[1]')

# Сравниваем с пороговыми значениями
if (( $(echo "$ERROR_RATE > 0.01 || $P95 > 0.3" | bc -l) )); then
  echo "Degradation detected. Rolling back..."
  kubectl rollout undo deployment/myapp
  exit 1
fi
```

### Стратегии и практики отката

- **Blue-Green**: Мгновенный возврат трафика на «синюю» среду. «Зеленая» среда сохраняется для расследования. Важно дождаться корректного завершения (`drain`) активных соединений.
- **Canary**: Прекращение увеличения доли трафика и возврат веса маршрутизации к 100% на стабильную версию.
- **Стандартные механизмы**:
  - `kubectl rollout undo deployment/myapp`
  - `helm rollback myapp <REVISION>`
- **Feature Flags**: Отключение проблемной функции без полного отката, что снижает радиус поражения.
- **Миграции данных**: Использование подхода `expand–migrate–contract` для обратной совместимости схемы. Откат на уровне схемы требует тщательного планирования до релиза.

### Дополнительная информация

#### Типичные ошибки

- `readinessProbe` проверяет только HTTP 200, но не проверяет доступность критически важных зависимостей (БД, кэш, очереди).
- Слишком агрессивные пороги проверок, приводящие к каскадным перезапускам (`flip-flop`).
- Отсутствие "прогрева" кэша и пулов соединений перед переключением в Blue-Green.
- Откат к версии приложения, несовместимой с обновленной схемой БД или форматом сообщений в очередях.
- Игнорирование сезонности трафика и типа пользовательской нагрузки при оценке метрик канарейки.
