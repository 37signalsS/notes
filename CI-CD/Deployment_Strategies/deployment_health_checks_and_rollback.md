# Проверки здоровья и откат развертывания

## Определения

**Проверка здоровья (Health Check)** — автоматизированный механизм оценки состояния приложения, используемый оркестраторами и CI/CD-системами для принятия решения о готовности новой версии к приему трафика или необходимости перезапуска.

- **Откат (Rollback)** — процесс возврата системы к предыдущему стабильному состоянию (версии кода, конфигурации или схемы данных) при обнаружении аномалий или сбоев после выпуска.
- **Гейтинг (Gating)** — методология использования Health Checks как "шлюзов" для прогрессивной раскатки (если проверки не пройдены, раскатка блокируется).
- **Автоматический судья (Judge / Analysis Engine)** — внешний компонент (например, Argo Rollouts или Kayenta), принимающий решение об откате на основе анализа временных рядов (метрики Prometheus/VictoriaMetrics).

## Основные концепции

### Триада проб (Kubernetes Probes)

В современных средах (2026) надежность релиза базируется на трех уровнях проверки. Подробный синтаксис см. в **[Пробах в Kubernetes](../../Kubernetes/Base/probes.md)**.

1.  **`startupProbe` (Защита при старте):**
    - **Цель:** Изоляция процесса прогрева (Warm-up). Пока эта проба не пройдена, остальные проверки отключены.
    - **2026 Context:** Критична для LLM-моделей и тяжелых Java-приложений с долгим JIT.
2.  **`readinessProbe` (Управление трафиком):**
    - **Цель:** Определение готовности обслуживать запросы. При сбое экземпляр исключается из балансировки (EndpointSlice).
    - **Важно:** Должна проверять локальную готовность, но учитывать доступность критических зависимостей.
3.  **`livenessProbe` (Самоисцеление):**
    - **Цель:** Детекция тупиковых состояний (Deadlocks, OOM). При сбое контейнер перезапускается.
    - **Риск:** Слишком агрессивная liveness-проба может вызвать каскадный перезапуск всех подов при временной деградации БД.

### Архитектура автоматизированного отката

Современный процесс Rollback (2026) перешел от ручных команд к автоматизации на основе **Золотых сигналов**:
1.  **Сбор данных:** Агент (Prometheus) собирает Error Rate и Latency.
2.  **Анализ:** Судья сравнивает метрики новой версии с эталоном (Baseline).
3.  **Действие:** Если отклонение выше порога (например, рост 5xx на 2%), инициируется `kubectl rollout undo` или переключение весов в Gateway API.

### Глубина истории и артефакты

Параметр `revisionHistoryLimit` определяет, на сколько шагов назад можно вернуться мгновенно.
- **Рекомендация:** Минимум 5-10 ревизий.
- **Артефакты:** При откате поды удаляются. Для анализа причин (RCA) необходимо настроить автоматический сбор дампов (CrashLoopBackOff) и внешнее логирование.

## Практические сценарии

### 1. Настройка проб для gRPC и HTTP/3 (Kubernetes 1.30+)

Использование нативных механизмов для современных протоколов.

```yaml
spec:
  containers:
  - name: api-service
    image: my-app:v2.4.0
    # gRPC проверка (стандарт 2026)
    readinessProbe:
      grpc:
        port: 9000
      initialDelaySeconds: 5
    # HTTP/3 проверка через exec (если балансировщик не поддерживает L7 пробы)
    livenessProbe:
      exec:
        command: ["/usr/bin/check-quic", "--port", "443"]
      periodSeconds: 10
```

### 2. Автоматический Rollback в GitLab CI (Bash + Prometheus)

Сценарий для простых пайплайнов без использования сложных операторов.

```bash
# Проверка Error Rate через 5 минут после деплоя
ERROR_RATE=$(curl -s "http://vm-select:8481/select/0/prometheus/api/v1/query" \
  --data-urlencode 'query=sum(rate(http_errors_total[5m])) / sum(rate(http_requests_total[5m]))' \
  | jq -r '.data.result[0].value[1]')

if (( $(echo "$ERROR_RATE > 0.02" | bc -l) )); then
  echo "CRITICAL: Error rate $ERROR_RATE > 2%. Initiating Rollback..."
  kubectl rollout undo deployment/api-server
  exit 1
fi
```

### 3. Использование AnalysisTemplate (Argo Rollouts)

Декларативный гейтинг — стандарт для Kubernetes в 2026 году.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate
spec:
  metrics:
  - name: success-rate
    interval: 2m
    successCondition: result[0] >= 0.98
    failureLimit: 3
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{status!~"5.*"}[2m])) 
          / 
          sum(rate(http_requests_total[2m]))
```

## Устранение неполадок (Troubleshooting)

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Циклический рестарт (Liveness Flapping)** | Слишком короткий таймаут пробы при высокой нагрузке. | Увеличить `timeoutSeconds` или `failureThreshold`. |
| **Трафик на "зомби"-поды** | Приложение зависло, но readiness-проба еще не успела сработать. | Уменьшить `periodSeconds` для Readiness; внедрить Circuit Breaker на клиенте. |
| **Откат невозможен** | `revisionHistoryLimit` установлен в 0 или 1. | Увеличить лимит истории в манифесте Deployment. |
| **Откат БД сломал код** | Откат кода (Rollback) произошел без отката схемы данных. | Использовать паттерн **[Expand-Contract](../../Databases/Concepts/migrations/expand_contract.md)** для обеспечения совместимости. |
| **Stuck Rollout** | Новая версия не проходит `startupProbe`. | Проверить логи `kubectl logs --previous` и ресурсы (CPU/RAM). |

## Дополнительная информация

### Лучшие практики

1.  **Graceful Shutdown:** При получении `SIGTERM` (начало отката или обновления) приложение должно завершить текущие запросы. Используйте `terminationGracePeriodSeconds` (минимум 30-60с).
2.  **Разделение зависимостей:** `readinessProbe` может проверять БД, но `livenessProbe` — **никогда**. Иначе падение БД приведет к рестарту всего прикладного слоя (каскадная авария).
3.  **In-Place Resize (2026):** При обновлении лимитов ресурсов через VPA/HPA (без перезапуска пода), пробы продолжают работать. Убедитесь, что таймауты проб учитывают возможные задержки при изменении CPU.
