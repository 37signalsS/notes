# A/B-тестирование в Kubernetes (A/B Testing)

## Определения

**A/B-тестирование (A/B Testing)** — стратегия развертывания, ориентированная на проверку бизнес-гипотез и UX-метрик. В отличие от Canary-релизов, целью которых является техническая стабильность, A/B-тестирование направляет разные группы пользователей на разные версии приложения для сравнения их эффективности (конверсия, вовлеченность).

**Сегментация трафика** — процесс разделения пользователей на группы на основе определенных атрибутов (HTTP-заголовки, Cookie, геолокация, ID пользователя) для направления на соответствующие версии приложения.

**Feature Flags (Переключатели функций)** — механизм управления доступностью функционала в коде без необходимости повторного развертывания артефактов.

## Ключевые принципы

1.  **Бизнес-фокус:** Основная цель — не "упадет ли сервер?", а "увеличится ли количество покупок?".
2.  **Длительность:** Тестирование обычно длится от нескольких дней до нескольких недель для сбора статистически значимых данных.
3.  **Идентификация пользователя:** Система должна гарантировать, что один и тот же пользователь видит одну и ту же версию приложения в течение всего эксперимента (**Sticky Sessions**).
4.  **Сравнение:** Всегда существует контрольная группа (Version A) и одна или несколько тестовых групп (Version B, C...).

## Реализация в Kubernetes

В Kubernetes A/B-тестирование реализуется на уровне маршрутизации трафика (L7) или внутри самого приложения.

### 1. Использование Service Mesh (Istio / Linkerd)
Наиболее мощный и гибкий способ, позволяющий управлять трафиком на основе любых HTTP-атрибутов.

```yaml
# Пример Istio VirtualService для A/B тестирования по заголовку
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: frontend-ab-test
spec:
  hosts:
  - frontend.example.com
  http:
  - match:
    - headers:
        x-user-type:
          exact: "premium"
    route:
    - destination:
        host: frontend
        subset: v2 # Новая версия для премиум-пользователей
  - route:
    - destination:
        host: frontend
        subset: v1 # Версия для всех остальных
```

### 2. Продвинутые Ingress-контроллеры
Некоторые контроллеры (NGINX Ingress, Traefik) поддерживают аннотации для разделения трафика по Cookie или заголовкам.

### 3. Feature Flags (LaunchDarkly, Unleash, Flipt)
Управление логикой происходит внутри кода приложения. Kubernetes развертывает обе версии (или одну с включенными флагами), а внешняя система решает, какой код исполнять для конкретного пользователя.

## Инструменты реализации

| Инструмент | Уровень | Метод управления |
| :--- | :--- | :--- |
| **Istio / Linkerd** | L7 (Network) | Маршрутизация по заголовкам/cookie. |
| **Argo Rollouts** | Controller | Автоматизация A/B через анализ метрик (AnalysisTemplate). |
| **Unleash / Flipt** | App Level | Feature Flags (максимальная гибкость сегментации). |
| **Optimizely / Google Optimize** | Client Side | Внедрение изменений на уровне браузера (подходит для простых UI-тестов). |

## Преимущества и недостатки

### Преимущества
* **Принятие решений на основе данных:** Точное понимание влияния изменений на бизнес.
* **Снижение рисков:** Плохая гипотеза затрагивает только часть аудитории.
* **Персонализация:** Возможность тестировать функционал на специфических сегментах.

### Недостатки
* **Сложность инфраструктуры:** Требуется L7-маршрутизация и системы аналитики.
* **Совместимость данных:** Разные версии приложения должны работать с одной БД (требуется [Expand-Contract](../../Databases/Concepts/migrations/expand_contract.md)).
* **Риск "отравления" метрик:** Неправильная сегментация может исказить результаты эксперимента.
* **Статистическая погрешность:** Для надежных выводов требуется большой объем трафика.
