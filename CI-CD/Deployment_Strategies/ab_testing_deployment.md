# A/B-тестирование в Kubernetes (A/B Testing)

## Определения

**A/B-тестирование (A/B Testing)** — стратегия прогрессивной поставки (Progressive Delivery), ориентированная на проверку бизнес-гипотез и UX-метрик. В отличие от технических стратегий (Canary), целью которых является стабильность, A/B-тестирование направляет сегментированные группы пользователей на разные версии приложения для сравнения их эффективности.

- **Контрольная группа (Control Group / Version A)** — группа пользователей, работающая со стабильной, текущей версией продукта.
- **Экспериментальная группа (Treatment Group / Version B)** — группа пользователей, получающая новый функционал или интерфейс.
- **Статистическая значимость (Statistical Significance)** — показатель того, что разница в результатах групп A и B не является случайной (обычно проверяется через p-value < 0.05).
- **Сегментация трафика** — разделение входящего потока запросов на основе атрибутов (HTTP-заголовки, Cookie, регион, ID пользователя).
- **Липкие сессии (Sticky Sessions)** — механизм, гарантирующий, что конкретный пользователь будет видеть одну и ту же версию приложения на протяжении всего эксперимента.

## Основные концепции

### Разделение ответственности: Сеть vs Код

A/B-тестирование может быть реализовано на двух уровнях, каждый из которых имеет свои преимущества:

1.  **Инфраструктурный уровень (L7 Routing):**
    - Управляется через **Gateway API**, **Service Mesh** (Istio, Linkerd) или Ingress.
    - Идеален для тестирования крупных изменений (новые версии сервисов, полная замена фронтенда).
    - Не требует изменения кода приложения для сегментации.

2.  **Прикладной уровень (Feature Flags):**
    - Управляется через системы управления флагами (**Unleash**, **LaunchDarkly**) и стандарт **OpenFeature**.
    - Позволяет проводить множество независимых экспериментов внутри одного сервиса.
    - Максимально гибкая сегментация (по логике приложения, правам доступа, данным из БД).

### Проблема сосуществования версий

Длительность A/B-тестов (от нескольких дней до недель) накладывает жесткие требования на инфраструктуру:
- **Совместимость данных:** База данных должна поддерживать обе версии одновременно. Обязательно использование паттерна **[Expand-Contract](../../Databases/Concepts/migrations/expand_contract.md)**.
- **Наблюдаемость:** Метрики (Prometheus/OpenTelemetry) должны быть обогащены тегами версии или идентификаторами эксперимента.

## Практические сценарии

### 1. Маршрутизация через Gateway API (Стандарт 2026)

Использование `HTTPRoute` для сегментации трафика по значению Cookie.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: frontend-ab-test
spec:
  parentRefs:
  - name: internal-gateway
  hostnames: ["shop.example.com"]
  rules:
  - matches:
    - headers:
      - name: "cookie"
        value: ".*user_segment=beta.*" # Регулярное выражение для сегмента
        type: RegularExpression
    backendRefs:
    - name: frontend-v2
      port: 80
  - backendRefs:
    - name: frontend-v1
      port: 80
```

### 2. Автоматизация бизнес-метрик через Argo Rollouts

Argo Rollouts может выступать в роли "судьи", анализируя бизнес-показатели (например, конверсию из внешних систем) перед продвижением версии.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: conversion-rate-check
spec:
  metrics:
  - name: order-success-rate
    interval: 1h
    successCondition: result >= 0.15 # Ожидаемая конверсия > 15%
    provider:
      prometheus:
        address: http://prometheus.monitoring.svc.cluster.local:9090
        query: |
          sum(rate(order_created_total{version="{{args.version}}"}[1h])) 
          / 
          sum(rate(http_requests_total{version="{{args.version}}"}[1h]))
```

### 3. Feature Flags на прикладном уровне (Unleash)

Интеграция через OpenFeature SDK позволяет переключать логику без перезапуска подов.

```python
# Пример использования OpenFeature Python SDK
from openfeature import api

client = api.get_client()
show_new_checkout = client.get_boolean_value("new-checkout-flow", False)

if show_new_checkout:
    return render_v2()
else:
    return render_v1()
```

## Устранение неполадок (Troubleshooting)

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **"Прыгающий" интерфейс** | Отсутствие Sticky Sessions или сброс Cookie. | Настроить Session Affinity на балансировщике или использовать хеширование ID пользователя в SDK. |
| **Отравление метрик (Metric Poisoning)** | Один пользователь попал в несколько конфликтующих экспериментов. | Использование "взаимоисключающих групп" (Exclusion Groups) в системе Feature Flags. |
| **SRM (Sample Ratio Mismatch)** | Распределение трафика (например, 50/50) не соответствует реальности. | Проверка корректности работы хэш-алгоритмов балансировщика. |
| **Разрыв сессий при Rollout** | Удаление старых подов прерывает текущие пользовательские сессии. | Настройка `terminationGracePeriodSeconds` и Graceful Shutdown. |

## Дополнительная информация

### Сравнение с Canary Deployment

| Характеристика | Canary Deployment | A/B Testing |
| :--- | :--- | :--- |
| **Основной риск** | Технический (ошибки 5xx, Latency) | Бизнес-риск (падение выручки, отток) |
| **Длительность** | Минуты / Часы | Дни / Недели |
| **Аудитория** | Случайный % трафика | Специфические сегменты |
| **Решение об откате** | Автоматическое (SRE Golden Signals) | Ручное или бизнес-гейтинг |

---

### Совет по собеседованию

**Вопрос:** Почему A/B тестирование сложнее Canary-релиза с технической точки зрения?

**Ответ:** A/B тестирование требует гораздо более длительного сосуществования версий в Production. Это заставляет команду поддерживать обратную совместимость базы данных и API в течение недель, а не минут. Кроме того, требуется интеграция с системами бизнес-аналитики и обеспечение "липкости" сессий, что усложняет конфигурацию L7-маршрутизации.
