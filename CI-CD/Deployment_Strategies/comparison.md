# Сравнение стратегий развертывания: Blue-Green vs. Canary

## Определения

Выбор стратегии развертывания влияет на управление рисками, время простоя и требования к инфраструктуре. **Blue-Green** и **Canary** — две популярные, но принципиально разные стратегии.

## Основные концепции

### Критерии оценки

* **Планируемый простой**: Ожидаемая недоступность во время переключения.
* **Радиус влияния (Blast Radius)**: Доля пользователей, на которых распространяется ошибка при сбое.
* **Скорость отката (Rollback)**: Время и сложность возврата к предыдущей версии.
* **Совместимость с данными**: Риски, связанные с миграцией схемы БД.
* **Наблюдаемость**: Скорость обнаружения (MTTD) и время восстановления (MTTR).
* **Стоимость**: Дополнительные инфраструктурные ресурсы.
* **Сложность маршрутизации**: Требования к L7-маршрутизации, флагам, сегментации.

### Сравнительная таблица

| Критерий | Blue-Green | Canary |
| :--- | :--- | :--- |
| **Планируемый простой** | Практически нулевой (при грамотном `drain` соединений) | Отсутствует (трафик перераспределяется постепенно) |
| **Радиус влияния при сбое** | 100% трафика сразу после переключения | Ограничен процентом/сегментом канарейки |
| **Скорость отката** | Мгновенная (смена маршрута на `Blue` среду) | Быстрая (возврат трафика к старой версии) |
| **Риски миграций данных** | Требует бинарной совместимости схемы | Предпочтительна для поэтапных миграций и проверки совместимости |
| **Наблюдаемость (MTTD/MTTR)**| MTTD зависит от качества пре-релизного тестирования | Более ранний сигнал на малой доле трафика, что снижает MTTR |
| **Стоимость** | Высокая (две полные среды) | Ниже (если канарейка узкая), но растет с увеличением доли |
| **Сложность маршрутизации** | Простая (смена backend-пула) | Высокая (требуются процентные сплиты/сегментация на L7) |
| **Предсказуемость релиза** | Высокая ("большой рубильник") | Плавная кривая риска, но более длительное время выкатки |

## Практические сценарии

### Факторы выбора

* **Нагрузка и SLA**:
  * **Blue-Green**: Подходит для жестких SLO на доступность, где плановый простой недопустим, но риск одномоментного сбоя приемлем.
  * **Canary**: Локализует риск, что предпочтительнее для сверхкритичных систем.
* **Совместимость API/схем**:
  * **Canary**: Идеальна при эволюции схемы БД, так как позволяет проверить обратную совместимость на малом подмножестве трафика.
* **Ресурсы и бюджет**:
  * **Blue-Green**: Требует удвоенных ресурсов.
  * **Canary**: Может выполняться на ограниченном пуле серверов.
* **Пользовательская сегментация**:
  * **Canary**: Является преимуществом при наличии возможности маршрутизации по регионам, типам подписки и т.д.

### Типовые сценарии применения

* **Высокорисковый релиз ядра платежей**: **Canary** с 1–5% трафика и строгим автоматическим контролем метрик.
* **Релиз статического фронтенда**: **Blue-Green** с атомарным переключением CDN Origin.
* **Срочный hotfix**: **Blue-Green** для максимально быстрого развертывания и мгновенного отката при необходимости.
* **Этапная миграция API**: **Canary** по версиям клиентов или регионам с постепенным расширением доли.

### Пример маршрутизации и автоматизации

* **L7-сплит трафика (Istio):**

    ```yaml
    apiVersion: networking.istio.io/v1beta1
    kind: VirtualService
    metadata:
      name: payments
    spec:
      hosts: ["payments.example.internal"]
      http:
      - route:
        - destination:
            host: payments
            subset: stable
          weight: 90
        - destination:
            host: payments
            subset: canary
          weight: 10
    ```

* **Автоматизация решения (псевдокод):**

    ```python
    if error_rate_5xx > 1.0 or p95_latency_ms > 300:
      set_traffic_split(stable=100, canary=0)
    else:
      step_up_canary(+10)
    ```

**Ключевые сигналы для автоматизации:** доля 5xx, p95/p99 задержки, деградация бизнес-метрик (например, конверсия), рост потребления ресурсов.
