# Rolling Update

### Определения

- **Rolling Update (Поэтапное обновление)** — это стратегия развертывания, при которой экземпляры приложения (поды, виртуальные машины) обновляются поочередно или небольшими группами. Новая версия постепенно заменяет старую, обеспечивая непрерывную доступность сервиса за счет того, что часть экземпляров всегда остается в рабочем состоянии.

### Основные концепции

#### Ключевые идеи

- **Постепенная замена**: Вместо одномоментного обновления всей системы, замена происходит итеративно.
- **Сохранение доступности**: Во время обновления общая емкость сервиса временно снижается, но он никогда не уходит в полный офлайн.
- **Контролируемый процесс**: Можно управлять количеством одновременно обновляемых, создаваемых и недоступных экземпляров.
- **Автоматический откат (встроенный)**: Большинство систем, реализующих Rolling Update, поддерживают автоматический возврат к предыдущей версии в случае сбоя новых экземпляров.

#### Параметры управления в Kubernetes

В Kubernetes стратегия `RollingUpdate` для `Deployment` управляется двумя основными параметрами:

- **`maxUnavailable`**: Максимальное количество подов, которые могут быть недоступны во время обновления. Может быть задано как абсолютное число (например, `1`) или процент (например, `25%`).
- **`maxSurge`**: Максимальное количество подов, которое можно создать сверх желаемого числа реплик. Это позволяет системе сначала поднять новый под, дождаться его готовности и только потом погасить старый. Может быть задано как абсолютное число или процент.

| `maxUnavailable` | `maxSurge` | Описание |
| :--- | :--- | :--- |
| **0** | **>0** | **Surge-only**: Сначала создаются новые поды, потом останавливаются старые. Требует временного увеличения ресурсов. |
| **>0** | **0** | **Unavailable-only**: Сначала останавливаются старые поды, потом создаются новые. Вызывает временное снижение пропускной способности. |
| **>0** | **>0** | **Гибкий вариант (по умолчанию)**: Kubernetes может гибко управлять процессом, соблюдая оба ограничения. |

### Практические сценарии

#### Пример Rolling Update в Kubernetes Deployment

Это стандартная стратегия для `Deployment`, если не указано иное.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25% # Во время обновления может быть недоступно до 25% подов (здесь 2 или 3 пода)
      maxSurge: 1 # Можно создать 1 дополнительный под сверх 10
  template:
    spec:
      containers:
        - name: app
          image: my-registry/my-app:v2.0.0 # Обновляем на новую версию
          # Важно! readinessProbe необходим для корректного Rolling Update
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
```

Процесс обновления будет выглядеть так:

1. Kubernetes создает 1 новый под (`v2.0.0`). Теперь подов 11.
2. Он ждет, пока новый под пройдет `readinessProbe`.
3. После готовности нового пода, Kubernetes удаляет один старый под (`v1.0.0`). Подов снова 10.
4. Этот процесс повторяется, пока все 10 подов не будут обновлены.

### Дополнительная информация

#### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- | :--- |
| **Нулевой или минимальный простой** | **Временное сосуществование двух версий** (может вызвать проблемы) |
| **Простота и встроенная поддержка** (во многих оркестраторах) | **Медленный откат**: Откат — это такой же rolling update, но в обратную сторону. |
| **Низкие накладные расходы на инфраструктуру** | **Сложность работы с БД**: Требует обратной и прямой совместимости схемы данных. |
| **Автоматизация процесса** | **Снижение общей производительности** во время обновления. |

#### Когда использовать Rolling Update?

- Это стратегия по умолчанию для большинства stateless-приложений.
- Когда требуется обновление без простоя, а риски, связанные с временным наличием двух версий, приемлемы.
- Когда важна экономия ресурсов по сравнению с Blue-Green.
