# Rolling Update — поэтапное обновление

## Определения

**Rolling Update (Поэтапное обновление)** — стратегия **Deployment**, при которой экземпляры приложения (**Pods**, виртуальные машины) обновляются поочередно или небольшими группами. Новая версия постепенно заменяет старую, обеспечивая непрерывную доступность сервиса за счет того, что часть экземпляров всегда остается в рабочем состоянии.

## Основные концепции

### Ключевые идеи

- **Постепенная замена** — замена происходит итеративно, а не одномоментно.
- **Сохранение доступности** — общая емкость сервиса временно снижается, но сервис не уходит в полный офлайн.
- **Контролируемый процесс** — управление количеством одновременно обновляемых, создаваемых и недоступных экземпляров.
- **Автоматический откат** — большинство **orchestrators** поддерживают автоматический возврат к предыдущей версии при сбое новых экземпляров.

### Параметры управления в Kubernetes

В Kubernetes стратегия `RollingUpdate` для `Deployment` управляется двумя параметрами:

- **`maxUnavailable`** — максимальное количество **Pods**, которые могут быть недоступны во время обновления (абсолютное число или процент, например `1` или `25%`).
- **`maxSurge`** — максимальное количество **Pods**, которое можно создать сверх желаемого числа реплик (абсолютное число или процент).

| `maxUnavailable` | `maxSurge` | Описание |
| :--- | :--- | :--- |
| **0** | **>0** | **Surge-only** — сначала создаются новые **Pods**, потом останавливаются старые. Требует временного увеличения ресурсов. |
| **>0** | **0** | **Unavailable-only** — сначала останавливаются старые **Pods**, потом создаются новые. Вызывает временное снижение пропускной способности. |
| **>0** | **>0** | **Гибкий вариант (по умолчанию)** — Kubernetes гибко управляет процессом, соблюдая оба ограничения. |

## Практические сценарии

### Пример Rolling Update в Kubernetes Deployment

Стратегия по умолчанию для `Deployment`, если не указано иное.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 25% # До 25% Pods недоступно (2-3 пода)
      maxSurge: 1 # 1 дополнительный Pod сверх 10
  template:
    spec:
      containers:
        - name: app
          image: my-registry/my-app:v2.0.0
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 5
            periodSeconds: 5
```

Процесс обновления на уровне подов (под капотом — через ReplicaSet):

1. Kubernetes создает 1 новый **Pod** (`v2.0.0`) → 11 **Pods**.
2. Ожидание прохождения `readinessProbe`.
3. После готовности — удаление одного старого **Pod** (`v1.0.0`) → 10 **Pods**.
4. Повторение до обновления всех 10 **Pods**.

На уровне ReplicaSet это выглядит как рост нового RS (0→N) и убывание старого (N→0). Старый RS сохраняется для отката. Подробнее — **[Управление жизненным циклом Deployment](../../Kubernetes/Base/Deployment/lifecycle_management.md)**.

## Дополнительная информация

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Нулевой или минимальный простой** | **Временное сосуществование двух версий** (может вызвать проблемы совместимости) |
| **Простота и встроенная поддержка** (в **orchestrators**) | **Медленный откат** — откат является таким же **Rolling Update** в обратную сторону |
| **Низкие накладные расходы на инфраструктуру** | **Сложность работы с БД** — требует обратной и прямой совместимости схемы данных ([Expand-Contract](../../Databases/Concepts/migrations/expand_contract.md)) |
| **Автоматизация процесса** | **Снижение общей производительности** во время обновления |

### Когда использовать

- Стратегия по умолчанию для большинства **stateless**-приложений.
- Когда требуется обновление без простоя, а риски временного наличия двух версий приемлемы.
- Когда важна экономия ресурсов по сравнению с **Blue-Green**.
