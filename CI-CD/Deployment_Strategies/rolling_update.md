# Rolling Update — поэтапное обновление

## Определения

**Rolling Update (Поэтапное обновление)** — стратегия развертывания (**Deployment**), при которой экземпляры приложения (**Pods**, виртуальные машины, контейнеры) обновляются поочередно или небольшими группами. Новая версия постепенно заменяет старую, обеспечивая непрерывную доступность сервиса за счет того, что часть экземпляров всегда остается в рабочем состоянии и готова принимать трафик через **Load Balancer**.

## Основные концепции

### Ключевые идеи

- **Итеративность** — замена происходит шагами, размер которых контролируется параметрами стратегии.
- **Нулевое время простоя (Zero Downtime)** — пользователи не испытывают перебоев, так как часть подов всегда готова принимать трафик. Это критично для бизнес-приложений.
- **Эффективность ресурсов** — в каждый момент времени обновляется только часть кластера, что оптимизирует использование ресурсов по сравнению с Blue-Green подходом.
- **Контроль и тестирование** — новые версии легче контролировать; поды, не прошедшие проверку готовности, автоматически исключаются из ротации.
- **Проверка готовности (Readiness Probe)** — Kubernetes проверяет готовность нового пода перед тем, как удалять старый. Правильная настройка проб исключает попадание трафика на не до конца инициализированное приложение.

### Параметры управления в Kubernetes

Помимо базовых ограничений количества подов, Kubernetes предоставляет тонкие настройки процесса:

- **`maxUnavailable`** — максимальное количество подов, которые могут быть недоступны во время обновления (например, `25%` или `1`). Гарантирует минимальный уровень доступности сервиса.
- **`maxSurge`** — количество дополнительных подов, которые можно создать сверх желаемого количества реплик (например, `1`). Позволяет запустить новые поды *перед* удалением старых, сохраняя высокую емкость.
- **`minReadySeconds`** — время ожидания после того, как под перешел в состояние `Ready`, прежде чем он будет считаться действительно рабочим.
- **`progressDeadlineSeconds`** — время ожидания прогресса развертывания.
- **`revisionHistoryLimit`** — количество старых ReplicaSets для отката.


| `maxUnavailable` | `maxSurge` | Режим работы | Влияние на ресурсы |
| :--- | :--- | :--- | :--- |
| **0** | **>0** | **Surge-only** | Требует временного запаса ресурсов для новых подов. |
| **>0** | **0** | **Unavailable-only** | Экономит ресурсы, но снижает пропускную способность сервиса. |
| **>0** | **>0** | **Смешанный** | Баланс между скоростью и стабильностью (стандарт по умолчанию). |

## Практические сценарии

### Пример в Kubernetes (Deployment)

Критически важным является наличие `readinessProbe`, без которой Kubernetes начнет удалять старые поды сразу после запуска процесса контейнера, не дожидаясь его готовности.

```yaml
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 1
      maxSurge: 2
  template:
    spec:
      terminationGracePeriodSeconds: 30 # Время на завершение текущих запросов
      containers:
        - name: app
          image: my-app:v2.0.0
          readinessProbe:
            httpGet:
              path: /healthz
              port: 8080
```

### Пример в Docker Swarm

В Docker Swarm параметры обновления задаются в секции `update_config` файла `docker-compose.yml`.

```yaml
services:
  web:
    image: my-app:v2.0.0
    deploy:
      replicas: 5
      update_config:
        parallelism: 2         # Сколько контейнеров обновлять одновременно
        delay: 10s             # Задержка между группами обновлений
        order: start-first     # Сначала запустить новый, потом удалить старый
        failure_action: rollback # Откат при сбое
      healthcheck:
        test: ["CMD", "curl", "-f", "http://localhost/health"]
        interval: 5s
        timeout: 3s
        retries: 3
```

## Дополнительная информация

### Риски и особенности

1. **Совместимость версий (N+1)**: Во время Rolling Update в кластере одновременно работают две версии кода. Это требует обязательной прямой и обратной совместимости API и схемы базы данных. См. паттерн **[Expand-Contract](../../Databases/Concepts/migrations/expand_contract.md)**.
2. **Graceful Shutdown**: Старые экземпляры должны корректно завершать обработку текущих соединений перед остановкой. В Kubernetes это регулируется `terminationGracePeriodSeconds` и обработкой сигнала `SIGTERM`.
3. **Sticky Sessions**: Если пользователи привязаны к конкретным экземплярам через сессии, обновление может привести к сбросу сессий при удалении старых подов.

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Минимальный простой** без дублирования всей инфраструктуры. | **Версионный дрифт** (разные версии кода отвечают пользователям). |
| **Экономия ресурсов** по сравнению с Blue-Green. | **Сложность тестирования** состояния, когда работают обе версии. |
| **Встроенная поддержка** большинством CI/CD инструментов. | **Медленный откат** (требует такого же постепенного процесса). |
