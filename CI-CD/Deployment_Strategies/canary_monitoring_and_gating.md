# Мониторинг и оценка трафика при Canary-развертывании

## Определения

**Мониторинг при поэтапном выпуске** — процесс непрерывного сравнения технических и продуктовых метрик новой версии (**Canary**) с эталонной версией (**Stable** или **Baseline**) в режиме реального времени. 

Основная задача мониторинга — автоматизация принятия решения о продвижении релиза (**Gating**). Это позволяет обнаруживать регрессии (рост ошибок, замедление ответов) на малых сегментах трафика и автоматически останавливать раскатку до того, как проблема затронет всех пользователей.

## Основные концепции

### Использование контрольной группы (Baseline)

При сравнении 5% Canary-трафика со стабильной версией (95%) возникает проблема статистической достоверности и влияния внешних факторов. 

**Паттерн Baseline:**
- **Stable (Baseline)** — небольшая группа подов (того же размера, что и Canary), на которых запущена текущая стабильная версия кода.
- **Canary** — группа подов с новой версией кода.
- **Преимущество:** Сравнение Canary с Baseline (а не со всей Stable-группой) позволяет исключить влияние "шума" инфраструктуры, так как обе группы имеют идентичный размер, время жизни и условия нагрузки.

### Ключевые сигналы (SRE Golden Signals)

Для принятия решения о безопасности релиза используются четыре "золотых сигнала", дополненные бизнес-метриками.

| Сигнал | Описание для Canary | Метрики (Prometheus/VictoriaMetrics) |
| :--- | :--- | :--- |
| **Errors (Ошибки)** | Рост доли 5xx/4xx ответов относительно Baseline. | `http_requests_total{status=~"5.."}` |
| **Latency (Задержка)** | Увеличение p95/p99 времени ответа. | `http_request_duration_seconds_bucket` |
| **Traffic (Трафик)** | Аномальное распределение запросов (дисбаланс). | `http_requests_total` |
| **Saturation (Насыщение)** | Утилизация ресурсов CPU/RAM на один экземпляр. | `container_cpu_usage_seconds_total` |

## Практические сценарии

### Точные PromQL-запросы для оценки

Сравнение должно учитывать относительное изменение (Ratio), а не абсолютные значения.

**1. Проверка уровня ошибок (Error Rate Ratio):**
Сравниваем долю ошибок на Canary с долей ошибок на Baseline. Если отношение > 2 (ошибок в два раза больше), это сигнал к откату.

```promql
# Отношение доли ошибок Canary к Baseline
(
  sum(rate(http_requests_total{job="my-app", version="canary", status=~"5.."}[5m]))
  /
  sum(rate(http_requests_total{job="my-app", version="canary"}[5m]))
)
/
(
  sum(rate(http_requests_total{job="my-app", version="baseline", status=~"5.."}[5m]))
  /
  sum(rate(http_requests_total{job="my-app", version="baseline"}[5m]))
) > 2
```

**2. Сравнение задержки p95:**
Проверка, что новая версия не замедлила ответы более чем на 20% по сравнению с текущей.

```promql
# p95 Canary / p95 Baseline
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{version="canary"}[5m])))
/
histogram_quantile(0.95, sum by (le) (rate(http_request_duration_seconds_bucket{version="baseline"}[5m]))) > 1.2
```

### Автоматизация через Argo Rollouts (AnalysisTemplate)

Современный подход в Kubernetes — декларативное описание критериев успеха в `AnalysisTemplate`.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata:
  name: success-rate-check
spec:
  metrics:
  - name: success-rate
    interval: 2m
    successCondition: result[0] > 0.95
    failureLimit: 3
    provider:
      prometheus:
        address: http://prometheus:9090
        query: |
          sum(rate(http_requests_total{version="canary", status!~"5.."}[2m])) 
          / 
          sum(rate(http_requests_total{version="canary"}[2m]))
```

## Дополнительная информация

### Стратегии принятия решений (Gating)

1. **Автоматический гейтинг (Automated Gating):** Контроллер (Argo Rollouts, Flagger) сам принимает решение об увеличении трафика на основе `AnalysisTemplate`.
2. **Ручной гейтинг (Manual Approval):** Пайплайн останавливается на определенных этапах (например, на 20% трафика) и ждет подтверждения инженера после визуального анализа дашбордов.
3. **Комбинированный подход:** Автоматический откат при критических сбоях и ручное подтверждение для перехода к 100% раскатке.

### Ловушки и рекомендации

- **Прогрев (Warm-up):** Не начинайте анализ в первые 60-120 секунд после запуска новых подов. JIT-компиляция и заполнение кэшей могут давать ложные всплески задержки.
- **Статистическая значимость:** При крайне низком трафике (единицы запросов в секунду) любые ошибки дают огромные проценты. Используйте фильтр `and sum(rate(...)) > 10` для исключения анализа на пустом трафике.
- **Бизнес-метрики:** Технические метрики могут быть в норме, но конверсия может упасть из-за багов в UI. Интегрируйте данные из систем продуктовой аналитики.
