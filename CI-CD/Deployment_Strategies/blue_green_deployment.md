# Сине-зеленое развертывание (Blue-Green Deployment)

## Определения

**Сине-зеленое развертывание (Blue-Green Deployment)** — стратегия выпуска, при которой поддерживаются две идентичные и полностью функциональные среды: активная (**Blue**), обслуживающая текущих пользователей, и пассивная (**Green**), принимающая новую версию. После успешной валидации новой версии весь трафик мгновенно переключается с Blue на Green. 

Главная цель — достижение **Zero Downtime** (нулевого времени простоя) и обеспечение возможности мгновенного отката к предыдущей версии в случае сбоя.

**Характер стратегии:** Это подход типа **«всё или ничего»**. Переключение происходит для 100% трафика одновременно, что требует высокой уверенности в релизе перед активацией Green-среды.

## Основные концепции

### Ключевые идеи

- **Идентичные среды** — поддерживаются две полностью одинаковые инфраструктуры: **Blue** (текущая стабильная) и **Green** (новая версия). В любой момент времени «живой» является только одна из них.
- **Атомарное переключение** — перевод трафика происходит одним действием на уровне сетевого слоя (балансировщик, сервис или DNS). Это минимизирует время простоя до секунд.
- **Мгновенный откат (Rollback)** — если в Green-версии обнаружена критическая ошибка, трафик мгновенно переключается обратно на Blue-среду, которая всё это время оставалась активной и готовой к нагрузке.
- **Тестирование в производственных условиях** — Green-среда является зеркалом продакшена. Это позволяет проводить финальные проверки и дымное тестирование (Smoke Testing) на реальных конфигурациях перед тем, как открыть доступ пользователям.

### Жизненный цикл релиза

1. **Подготовка (Standby)** — развертывание новой версии в пассивной среде (Green).
2. **Верификация (Smoke Testing)** — выполнение тестов здоровья и интеграционных тестов в среде Green.
3. **Прогрев (Warm-up)** — инициализация пулов соединений и кэшей перед приемом нагрузки.
4. **Переключение (Cutover)** — мгновенная перенастройка маршрутизатора на Green.
5. **Наблюдение (Post-deployment Monitoring)** — мониторинг бизнес-метрик (конверсия, доход) и технических сигналов.
6. **Завершение (Decommissioning)** — после подтверждения стабильности Blue-среда останавливается или становится резервной для следующего цикла.

### Методы переключения трафика

| Метод | Механизм | Особенности и риски |
| :--- | :--- | :--- |
| **Балансировщик (L7/L4)** | Изменение целевой группы (Target Group). | Самый быстрый и надежный способ. |
| **Service Mesh (Istio)** | Изменение весов в VirtualService (100% на новую версию). | Позволяет управлять трафиком на уровне микросервисов. |
| **DNS** | Изменение CNAME или A-записи. | **Риск TTL:** кэширование DNS на стороне клиента может задержать переключение на часы. |
| **Kubernetes Service** | Смена селектора (Selector) в объекте Service. | Просто в реализации. **Риск потери сессий:** резкое переключение трафика может привести к обрыву текущих соединений и потере данных сессий, если они не вынесены во внешнее хранилище. |

## Практические сценарии

### Нативная реализация в Kubernetes (Standard)

В стандартном Kubernetes стратегия Blue-Green реализуется через создание двух независимых объектов `Deployment` и одного объекта `Service`, который выступает в роли переключателя трафика.

1.  **Определение Deployment:** Создаются два манифеста — для «синей» (текущей) и «зеленой» (новой) версий. Они различаются метками (labels) и версиями образов.

    ```yaml
    # app-blue.yaml
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: app-blue
    spec:
      replicas: 3
      selector:
        matchLabels:
          app: my-app
          version: blue
      template:
        metadata:
          labels:
            app: my-app
            version: blue
        spec:
          containers:
          - name: my-app
            image: my-app:v1
    ```

    ```yaml
    # app-green.yaml (новая версия)
    apiVersion: apps/v1
    kind: Deployment
    metadata:
      name: app-green
    spec:
      replicas: 3
      selector:
        matchLabels:
          app: my-app
          version: green
      template:
        metadata:
          labels:
            app: my-app
            version: green
        spec:
          containers:
          - name: my-app
            image: my-app:v2
    ```

2.  **Настройка Service:** Изначально сервис указывает на «синюю» версию через селектор.

    ```yaml
    apiVersion: v1
    kind: Service
    metadata:
      name: my-app-service
    spec:
      type: LoadBalancer
      ports:
      - port: 80
        targetPort: 80
      selector:
        app: my-app
        version: blue  # Изначально установлен синий цвет
    ```

3.  **Переключение трафика:** После того как «зеленая» версия развернута и проверена, селектор сервиса обновляется для перенаправления трафика.

    ```bash
    # Мгновенное переключение на зеленую версию
    kubectl patch service my-app-service -p '{"spec":{"selector":{"version":"green"}}}'
    ```

### Реализация через Argo Rollouts

Argo Rollouts расширяет возможности Kubernetes, предоставляя объект `Rollout` для автоматизации Blue-Green процессов.

```yaml
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata:
  name: my-app
spec:
  replicas: 4
  strategy:
    blueGreen:
      activeService: my-app-active    # Сервис для пользователей
      previewService: my-app-preview  # Сервис для предварительного тестирования
      autoPromotionEnabled: false      # Требовать ручного подтверждения перед переключением
```

### Лучшие практики в Kubernetes

-   **Паритет сред (Environment Parity):** Синяя и зеленая среды должны быть идентичны (оборудование, конфигурации, версии системного ПО), чтобы избежать ошибок, специфичных для окружения.
-   **Автоматизированное тестирование:** Запуск автоматических тестов (Smoke, Regression) в «зеленой» среде перед переключением трафика является обязательным этапом.
-   **Комплексный мониторинг:** Необходимо отслеживать не только технические метрики (CPU/RAM, 5xx ошибки), но и бизнес-показатели в реальном времени сразу после переключения.
-   **Разделение компонентов (Decoupling):** Изоляция сервисов минимизирует влияние обновлений на другие части системы и повышает общую стабильность.
-   **Сложность управления данными:** Переключение уровня приложения происходит мгновенно, но уровень данных (БД) требует особого внимания для обеспечения целостности (см. раздел про БД ниже).

### Совет для собеседования

**Вопрос:** Вы только что переключили трафик на «зеленую» среду, и инструменты мониторинга зафиксировали всплеск критических ошибок. Какова процедура отката и в чем ее преимущество?

**Ответ:** Процедура отката заключается в немедленном перенаправлении трафика обратно в стабильную «синюю» среду (в Kubernetes — исправление селектора сервиса).
**Основное преимущество** — скорость. Откат происходит почти мгновенно, так как «старая» версия все еще запущена и готова к работе. Это минимизирует негативное влияние на пользователей, пока команда расследует причины сбоя в «зеленой» среде в автономном режиме.

### Работа с базой данных и слой данных

Совместимость схемы БД — основное препятствие для Blue-Green. Если Green-версия применит деструктивную миграцию (например, удаление колонки), Blue-версия мгновенно выйдет из строя.

**Решение:** Обязательное использование паттерна **[Expand-Contract](../../Databases/Concepts/migrations/expand_contract.md)**.
1. Сначала выполняется миграция, расширяющая схему (Expand), совместимая с обеими версиями кода.
2. После стабилизации Green-среды выполняется очистка (Contract).

### Управление состоянием (Session Stickiness)

При атомарном переключении трафика активные пользовательские сессии могут быть потеряны.

- **Проблема:** Если сессии хранятся в памяти приложения, пользователи столкнутся с разлогином.
- **Решение:** Вынос состояния во внешние хранилища (**Distributed Cache** — Redis, Memcached) или использование **Sticky Sessions** (с осторожностью, так как это мешает мгновенному переключению всех пользователей).

## Дополнительная информация

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Нулевой простой** при корректной настройке. | **Высокая стоимость** — требует полной дубликации инфраструктуры (2x ресурсов), что делает стратегию дорогой. |
| **Безопасный откат** — старая версия готова принять трафик мгновенно. | **Риск «всё или ничего»** — любая ошибка в Green сразу аффектит 100% пользователей. |
| **Отсутствие дрейфа версий** — в кластере всегда только одна активная версия кода. | **Сложность данных** — риск рассинхронизации данных при откате, если Green уже записала новые данные. |
| | **Проблемы с DNS** — зависимость от настроек кэширования у клиентов. |
