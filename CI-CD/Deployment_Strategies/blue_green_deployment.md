# Blue-Green Deployment

## Определения

**Blue-Green** — это стратегия выпуска, при которой поддерживаются две идентичные продакшен-среды: активная (Blue) обслуживает пользователей, а пассивная (Green) принимает новую версию. После валидации Green весь трафик переключается с Blue на Green одним действием на уровне маршрутизации. Главная цель — минимизировать простой и риски, обеспечивая мгновенный откат.

## Основные концепции

### Ключевые идеи

*   **Дублирование среды**: Инфраструктура, конфигурации и зависимости максимально идентичны, чтобы исключить «drift».
*   **Детерминированное переключение**: Трафик переводится на Green атомарно через балансировщик или DNS, без «частичных» состояний.
*   **Быстрый rollback**: Возврат к Blue — это обратное переключение трафика, без перекатываний.
*   **Независимость от времени**: Подготовка релиза в Green происходит без влияния на текущий продакшен.

| Аспект | Blue (активная) | Green (кандидат) |
| :--- | :--- | :--- |
| **Код** | Стабильная версия | Новая версия |
| **Трафик** | 100% | 0% (до переключения) |
| **Наблюдение** | Бизнес-метрики | Технические проверки и синтетические тесты |
| **Риск** | Минимальный | Контролируемый до переключения |

### Поток выпуска

1.  Сборка артефакта и развёртывание в среду Green.
2.  Запуск автоматических проверок: готовность, контрактные тесты, проверка конфигураций, дымовые сценарии.
3.  Подготовка слоя данных: миграции в режиме, совместимом с обеими версиями (подход expand–migrate–contract).
4.  Синхронизация состояний: сессии, кэш, статические файлы, флаги функциональности.
5.  Переключение трафика на Green. Наблюдение за ключевыми метриками.
6.  Деактивация Blue или перевод в горячий резерв на время наблюдения.

## Практические сценарии

### Переключение трафика

Чаще всего применяется балансировщик или переключение селектора сервиса. В контейнерной оркестрации удобно работать через метки.

**Пример переключения в Kubernetes через изменение селектора Service:**

```bash
# Проверяем готовность Green
kubectl rollout status deploy app-green

# Переключаем Service на версии с меткой version=green
kubectl patch service app-svc -p '{
  "spec": { "selector": { "app": "app", "version": "green" } }
}'

# Опционально: дренируем старые соединения
kubectl delete pod -l app=app,version=blue --grace-period=30 --wait=false
```

При использовании DNS важно заранее снизить TTL, иначе часть клиентов продолжит обращаться к Blue до истечения кэша. На балансировщике следует включать проверки готовности и «drain» для корректного завершения активных соединений.

### Работа с данными

*   **Схема БД**: Миграции сначала добавляют новые сущности и поля без удаления старых (expand), затем приложение начинает их использовать, и только после успешного переключения удаляются устаревшие части (contract).
*   **Сессии и кэш**: Хранение во внешнем устойчивом сторе (Redis/Memcached) позволяет свободно переключать трафик между средами.
*   **Файлы и артефакты**: Используйте общие хранилища (S3-совместимые бакеты или сетевые тома) с версионированием.
*   **Идемпотентность**: Скрипты миграций и инициализации должны безопасно выполняться повторно.

## Дополнительная информация

### Преимущества и издержки

*   **Преимущества**: Минимальный простой, быстрый откат, предсказуемость и чистое разделение старой/новой версии.
*   **Издержки**: Удвоение инфраструктурных ресурсов, усложнение управления данными, требования к строгой дисциплине конфигураций и тестов до переключения.
