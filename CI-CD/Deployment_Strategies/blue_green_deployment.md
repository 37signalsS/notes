# Blue-Green Deployment

### Определения

- **Blue-Green Deployment** — это стратегия выпуска, при которой поддерживаются две идентичные продакшен-среды: активная ("Blue") обслуживает пользователей, а пассивная ("Green") принимает новую версию. После валидации "Green" весь трафик мгновенно переключается с "Blue" на "Green" одним действием на уровне маршрутизации. Главная цель — минимизировать простой и риски, обеспечивая мгновенный откат.

### Основные концепции

#### Ключевые идеи

- **Дублирование среды**: Инфраструктура, конфигурации и зависимости "Blue" и "Green" сред максимально идентичны.
- **Атомарное переключение**: Трафик переводится на "Green" одним действием (например, смена DNS-записи или селектора в Service), без промежуточных состояний.
- **Быстрый откат**: Возврат на "Blue" — это такое же атомарное переключение трафика в обратную сторону.
- **Независимое тестирование**: Новая версия в "Green" среде проходит все необходимые тесты без влияния на "Blue" среду.

| Аспект | Blue (активная) | Green (кандидат) |
| :--- | :--- | :--- |
| **Код** | Стабильная версия | Новая версия |
| **Трафик** | 100% | 0% (до переключения) |
| **Наблюдение** | Бизнес-метрики | Технические проверки, smoke-тесты |

#### Поток выпуска

1. Новый артефакт развертывается в "Green" среду.
2. Выполняются автоматические проверки: health checks, контрактные тесты, E2E-тесты.
3. Подготавливается слой данных: выполняются миграции БД, совместимые с обеими версиями кода.
4. Происходит "прогрев" кэшей и пулов соединений в "Green" среде.
5. Трафик атомарно переключается на "Green" среду.
6. Ведется наблюдение за ключевыми бизнес-метриками и техническими показателями.
7. После подтверждения стабильности "Blue" среда деактивируется или остается в качестве горячего резерва.

### Практические сценарии

#### Переключение трафика в Kubernetes

Самый распространенный способ — изменение селектора у Kubernetes Service, который направляет трафик на поды.

```bash
# 1. Проверяем готовность подов "Green" версии
kubectl rollout status deployment/app-green

# 2. Атомарно переключаем Service на поды с меткой version=green
kubectl patch service app-svc -p '{
  "spec": { "selector": { "app": "app", "version": "green" } }
}'

# 3. После подтверждения стабильности можно удалить "Blue" развертывание
# kubectl delete deployment/app-blue
```

#### Работа с базой данных

Совместимость схемы БД с двумя версиями приложения — самая сложная часть Blue-Green. Неправильное управление миграциями может привести к потере данных или полной неработоспособности одной из версий.

- **Решение:** Используется подход **"Expand-Contract"** (также известный как "Parallel Change").
    1. **Expand (Расширение):** Сначала выкатывается миграция, которая добавляет новые столбцы/таблицы, но не удаляет и не изменяет старые. На этом этапе обе версии приложения (Blue и Green) должны корректно работать с обновленной схемой.
    2. **Migrate (Миграция):** После переключения трафика на "Green", новый код начинает использовать новую схему (читать и писать в новые столбцы/таблицы).
    3. **Contract (Сужение):** После полного вывода "Blue" из эксплуатации и подтверждения стабильности "Green" выкатывается еще одна миграция, которая удаляет старые, уже неиспользуемые столбцы/таблицы.

#### Управление состоянием и сессиями

При переключении трафика пользовательские сессии могут быть потеряны, если они хранятся локально в памяти экземпляров приложения.

- **Проблема:** Пользователь, чья сессия была на "Blue" инстансе, после переключения попадает на "Green" инстанс, где его сессии нет. Это приводит к необходимости повторной аутентификации.
- **Решение:** Использование внешнего, общего хранилища сессий (например, Redis, Memcached). Обе среды, "Blue" и "Green", должны быть настроены на работу с этим общим хранилищем. Это гарантирует, что сессия пользователя сохранится при переключении между средами.

### Дополнительная информация

#### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- | :--- |
| **Быстрый и надежный откат** | **Удвоение стоимости инфраструктуры** |
| **Минимальный или нулевой простой** | **Сложность управления состоянием** (требует совместимости БД и общего хранилища сессий) |
| **Простота концепции** | **Риск неполной идентичности сред** (конфигурации могут "разъехаться") |
| **Тестирование в production-like среде** | **"Big bang" релиз**: все пользователи получают новую версию одновременно, что увеличивает радиус поражения в случае ошибки. |
