# Shadow Deployment — теневое развертывание

## Определения

**Shadow Deployment (Теневое развертывание)**, также известное как **Traffic Mirroring (Зеркалирование трафика)** — стратегия развертывания, при которой реальный пользовательский трафик копируется и отправляется на новую версию сервиса ("shadow"), не затрагивая основной поток запросов. Ответы от теневой версии игнорируются и не возвращаются пользователю. Основная цель — протестировать новую версию под реальной нагрузкой без риска для пользователей.

## Основные концепции

### Ключевые идеи

- **Копирование трафика** — входящие запросы к стабильной версии дублируются на уровне прокси или service mesh.
- **Отсутствие влияния на пользователя** — пользователь получает ответ только от стабильной ("primary") версии. Результаты работы "shadow" версии никак не влияют на пользователя.
- **Тестирование под реальной нагрузкой** — позволяет проверить производительность, выявить ошибки и регрессии в условиях, максимально приближенных к боевым.
- **Безопасность для stateful-сервисов** — критически важно, чтобы "shadow" версия не выполняла операции, изменяющие состояние (например, запись в базу данных, отправка сообщений в очередь), или использовала изолированные окружения (stub-сервисы, временная БД).

### Схема работы

1. Вся система работает на стабильной версии **V1**.
2. Новая версия **V2 (shadow)** развертывается параллельно.
3. На уровне маршрутизатора (например, Istio VirtualService, Nginx) настраивается зеркалирование: 100% трафика идет на **V1**, а его копия ("fire and forget") — на **V2**.
4. Анализ метрик, логов и трейсов от **V2** в сравнении с поведением **V1**.
5. Поиск аномалий: рост ошибок, увеличение задержки, утечки памяти.
6. После подтверждения стабильности **V2** проводится полноценное развертывание с помощью другой стратегии (например, Blue-Green или Rolling Update).

## Практические сценарии

### Реализация с помощью Istio

Istio позволяет настроить зеркалирование трафика с помощью `VirtualService`.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app-mirror
spec:
  hosts:
    - "my-app.example.com"
  http:
    - route:
        # 100% трафика направляется на стабильную версию v1
        - destination:
            host: my-app
            subset: v1
          weight: 100
      # Та же самая порция трафика зеркалируется на v2 (shadow)
      mirror:
        host: my-app
        subset: v2
      # Указывает процент зеркалируемого трафика (по умолчанию 100%)
      mirror_percent: 100
```

## Дополнительная информация

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Максимальная безопасность для пользователя** (нулевой радиус поражения) | **Удвоенная стоимость инфраструктуры** (как в Blue-Green) |
| **Тестирование на реальном трафике** | **Сложность для stateful-сервисов** (риск двойной записи) |
| **Проверка производительности** | **Отсутствие проверки полного цикла** (ответы shadow игнорируются) |
| **Выявление редких ошибок** | **Требует продвинутых инструментов** (Service Mesh) |

### Когда использовать

- Перед выкаткой критически важных изменений с высокой ценой ошибки.
- Для тестирования производительности на реальном профиле нагрузки.
- Для проверки кода, не изменяющего состояние (рефакторинг алгоритмов).
- Как финальный этап проверки перед Canary или Blue-Green развертыванием.
