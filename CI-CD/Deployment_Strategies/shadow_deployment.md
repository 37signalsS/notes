# Теневое развертывание (Shadow Deployment)

## Определения

**Теневое развертывание (Shadow Deployment)**, также известное как **Зеркалирование трафика (Traffic Mirroring)** — стратегия развертывания, при которой реальный пользовательский трафик копируется и направляется на новую версию сервиса (**v2/Shadow**), не затрагивая основной поток запросов к стабильной версии (**v1/Primary**). Ответы от теневой версии полностью игнорируются инфраструктурой и никогда не возвращаются пользователю.

Основная цель — валидация новой версии под реальной производственной нагрузкой при **нулевом риске** для пользователей (**Blast Radius = 0**). Это позволяет выявить ошибки, узкие места в производительности и проблемы стабильности до того, как код станет доступен клиентам.

## Основные концепции

### Ключевые идеи

- **Дублирование запросов (Fire and Forget)** — входящий запрос клонируется. Оригинал идет в v1, копия — в v2. Система не ждет ответа от теневой версии перед отправкой основного ответа пользователю.
- **Изоляция результатов** — ответы теневой версии всегда отбрасываются. Пользователь видит только ответ из стабильной версии.
- **Сравнение поведения (Comparison Engine)** — ответы теневой версии логируются и сравниваются с ответами стабильной версии для поиска функциональных расхождений.
- **Тестирование нефункциональных требований** — проверка производительности (Latency), потребления ресурсов (CPU, Memory) и стабильности на реальном профиле трафика.

### Проблема Stateful-сервисов

Наибольшая сложность и **самый большой риск** теневого развертывания заключается в непредвиденных побочных эффектах от операций, изменяющих состояние (stateful operations). Если сервис выполняет запись, теневая версия может продублировать записи в базу данных или вызвать сторонний платежный API, что приведет к реальным проблемам.

**Методы решения и предотвращения:**
1. **Изолированная БД (Shadow DB)** — теневая версия пишет в копию базы данных.
2. **Заглушки (Mocks/Stubs)** — использование имитируемых или "заглушенных" нижестоящих сервисов для любых вызовов с отслеживанием состояния.
3. **Режим "только чтение" (Read-only API)** — обеспечение того, чтобы зеркальный трафик попадал только на конечные точки API, доступные только для чтения.
4. **Очистка данных (Data Scrubber)** — использование прокси для удаления или подмены токенов/секретов в зеркалируемых запросах.

## Практические сценарии

### Реализация через Istio (Service Mesh)

Istio поддерживает зеркалирование на уровне L7 через ресурс `VirtualService`. Операция выполняется по принципу "выстрелил и забыл" (fire-and-forget) — прокси не ждет ответа от теневой версии перед возвратом ответа пользователю от стабильной версии.

**VirtualService для зеркалирования:**

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app-virtualservice
spec:
  hosts:
    - my-app-service
  http:
    - route:
        - destination:
            host: my-app-service
            subset: stable # Основной пункт назначения (v1)
          weight: 100
      mirror:
        host: my-app-service
        subset: shadow # Теневой пункт назначения (v2)
      mirrorPercentage:
        value: 100.0 # Процент зеркалируемого трафика
```

**DestinationRule для определения подмножеств:**

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: my-app-destinationrule
spec:
  host: my-app-service
  subsets:
    - name: stable
      labels:
        version: v1
    - name: shadow
      labels:
        version: v2
```

### Реализация через Gateway API (GAMMA)

В 2026 году индустриальным стандартом является **Gateway API**. Зеркалирование настраивается через фильтр `RequestMirror` в ресурсе `HTTPRoute`.

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: my-app-shadow
spec:
  parentRefs:
  - name: my-app-service
    kind: Service
  rules:
  - filters:
    - type: RequestMirror
      requestMirror:
        backendRef:
          name: my-app-shadow-service # Куда зеркалировать (v2)
          port: 8080
    backendRefs:
    - name: my-app-stable-service # Основной бэкенд (v1)
      port: 8080
      weight: 100
```

### Реализация через NGINX (Ingress)

NGINX поддерживает модуль `ngx_http_mirror_module`, который позволяет дублировать запросы в другой бэкенд.

```nginx
location / {
    mirror /mirror;
    proxy_pass http://backend_stable;
}

location = /mirror {
    internal;
    proxy_pass http://backend_shadow;
}
```

### Инструменты для анализа и воспроизведения

- **GoReplay** — инструмент для захвата и воспроизведения HTTP-трафика в реальном времени. Позволяет не только зеркалировать, но и изменять скорость потока или фильтровать запросы.
- **Diffy (Twitter)** — выступает в роли прокси, который отправляет запрос на Stable, Shadow и Baseline версии, сравнивая ответы и подсвечивая расхождения в JSON-структурах, игнорируя шум (метки времени, ID запросов).

## Дополнительная информация

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Нулевой риск** — ошибки в Shadow-версии никак не влияют на пользователя. | **Двойная стоимость** — требуется полная копия ресурсов инфраструктуры. |
| **Реальный профиль трафика** — выявление пограничных случаев (edge cases), которые сложно покрыть тестами. | **Сложность настройки** — требует продвинутой сетевой инфраструктуры (Service Mesh). |
| **Проверка масштабируемости** — оценка поведения под реальной нагрузкой. | **Проблема Side Effects** — сложность тестирования логики с записью в БД или внешними API. |

### Мониторинг и наблюдаемость

При теневом развертывании важно разделять алертинг:
- Ошибки в **Shadow** версии не должны вызывать срабатывание дежурных инженеров (on-call).
- Метрики **Shadow** версии должны иметь соответствующие метки (tags/labels), чтобы не смешиваться с метриками **Primary** в общих дашбордах.

### Сравнение: Shadow vs Canary

| Характеристика | Shadow Deployment (Mirroring) | Canary Deployment |
| :--- | :--- | :--- |
| **Основная цель** | Тестирование нефункциональных требований (производительность, стабильность). | Тестирование функциональности и принятия функций пользователями. |
| **Риск для пользователя** | **Нулевой**. Пользователи не видят ответов новой версии. | **Минимальный**. Небольшая группа пользователей взаимодействует с новой версией. |
| **Обратная связь** | Технические метрики (latency, ошибки) и сравнение ответов. | Реальная обратная связь от пользователей и бизнес-метрики конверсии. |
| **Когда выбирать** | Когда нужно проверить поведение под полной нагрузкой без риска. | Когда нужно проверить гипотезу или новую функцию на живых пользователях. |

### Советы для собеседования

**Вопрос:** В каких случаях вы бы предпочли теневое развертывание канареечному выпуску?
**Ответ:** Теневое развертывание выбирается, когда основной целью является проверка производительности и стабильности новой версии под производственной нагрузкой без риска для пользователей. Канареечный релиз лучше подходит для тестирования функциональности и восприятия новых фич реальными пользователями. Shadow — для нефункционального тестирования, Canary — для функционального.

**Вопрос:** В чем заключается самый большой риск теневых развертываний и как его предотвратить?
**Ответ:** Самый большой риск — непредвиденные побочные эффекты от операций с сохранением состояния (запись в БД, вызовы платежных API). Для предотвращения следует использовать имитированные (mocked/stubbed) нижестоящие сервисы или направлять зеркальный трафик только на эндпоинты, доступные только для чтения.
