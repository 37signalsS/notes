# Теневое развертывание (Shadow Deployment)

## Определения

**Теневое развертывание (Shadow Deployment)**, также известное как **Зеркалирование трафика (Traffic Mirroring)** — стратегия развертывания, при которой реальный пользовательский трафик копируется и направляется на новую версию сервиса (**Shadow**), не затрагивая основной поток запросов. Ответы от теневой версии игнорируются оркестратором или прокси и не возвращаются пользователю. 

Основная цель — валидация новой версии под реальной нагрузкой в боевом окружении при **нулевом риске** для пользователей (Blast Radius = 0).

## Основные концепции

### Ключевые идеи

- **Дублирование запросов (Fire and Forget)** — входящий запрос клонируется. Оригинал идет в стабильную версию (**Primary**), копия — в теневую.
- **Изоляция результатов** — побочные эффекты теневой версии не должны влиять на пользователя или производственные данные.
- **Сравнение поведения (Comparison Engine)** — ответы теневой версии логируются и сравниваются с ответами стабильной версии для поиска функциональных расхождений.
- **Нагрузочное тестирование** — проверка производительности (Latency, CPU, Memory) на реальном профиле трафика без искусственных синтетических тестов.

### Проблема Stateful-сервисов

Наибольшая сложность теневого развертывания заключается в работе с операциями, изменяющими состояние (запись в БД, отправка уведомлений, платежи).

**Методы решения:**
1. **Изолированная БД (Shadow DB)** — теневая версия пишет в копию базы данных.
2. **Режим "только чтение" (Dry Run Mode)** — приложение в теневом режиме имитирует запись в логах, но физически не вызывает методы мутации.
3. **Очистка данных (Data Scrubber)** — использование прокси для удаления или подмены токенов/секретов в зеркалируемых запросах.

## Практические сценарии

### Реализация через Istio (Service Mesh)

Istio поддерживает зеркалирование на уровне L7 через ресурс `VirtualService`.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app-shadow
spec:
  hosts:
    - "my-app.example.com"
  http:
    - route:
        - destination:
            host: my-app
            subset: v1 # Стабильная версия
          weight: 100
      mirror:
        host: my-app
        subset: v2 # Теневая версия
      mirror_percent: 100 # Процент зеркалируемого трафика
```

### Реализация через NGINX (Ingress)

NGINX поддерживает модуль `ngx_http_mirror_module`, который позволяет дублировать запросы в другой бэкенд.

```nginx
location / {
    mirror /mirror;
    proxy_pass http://backend_stable;
}

location = /mirror {
    internal;
    proxy_pass http://backend_shadow;
}
```

### Инструменты для анализа и воспроизведения

- **GoReplay** — инструмент для захвата и воспроизведения HTTP-трафика в реальном времени. Позволяет не только зеркалировать, но и изменять скорость потока или фильтровать запросы.
- **Diffy (Twitter)** — выступает в роли прокси, который отправляет запрос на Stable, Shadow и Baseline версии, сравнивая ответы и подсвечивая расхождения в JSON-структурах, игнорируя шум (метки времени, ID запросов).

## Дополнительная информация

### Преимущества и недостатки

| Преимущества | Недостатки |
| :--- | :--- |
| **Нулевой риск** — ошибки в Shadow-версии никак не влияют на пользователя. | **Двойная стоимость** — требуется полная копия ресурсов инфраструктуры. |
| **Реальный профиль трафика** — выявление пограничных случаев (edge cases), которые сложно покрыть тестами. | **Сложность настройки** — требует продвинутой сетевой инфраструктуры (Service Mesh). |
| **Проверка масштабируемости** — оценка поведения под реальной нагрузкой. | **Проблема Side Effects** — сложность тестирования логики с записью в БД или внешними API. |

### Мониторинг и наблюдаемость

При теневом развертывании важно разделять алертинг:
- Ошибки в **Shadow** версии не должны вызывать срабатывание дежурных инженеров (on-call).
- Метрики **Shadow** версии должны иметь соответствующие метки (tags/labels), чтобы не смешиваться с метриками **Primary** в общих дашбордах.
