# Canary Deployment

## Определения

**Канареечное развертывание (Canary Deployment)** — стратегия выпуска, при которой новая версия приложения ("canary") выкатывается для небольшой контролируемой группы пользователей, в то время как основная масса продолжает использовать стабильную версию. Подход позволяет оценить влияние изменений в реальных условиях и минимизировать риски перед полным развертыванием.

## Основные концепции

### Цели и предпосылки

**Цель:** Снижение риска инцидентов путем раннего обнаружения проблем на малой доле трафика.

**Предпосылки:**

- **Управление трафиком (Traffic Splitting)** — возможность точно направлять процент трафика на разные версии сервиса.
- **Наблюдаемость** — раздельный мониторинг метрик для стабильной и канареечной версий.
- **Автоматизация** — механизмы для автоматического увеличения доли трафика или отката на основе анализа метрик.

### Этапы канареечного релиза

1. **Подготовка** — сборка и версионирование нового артефакта.
2. **Параллельное развертывание** — новая (canary) версия развертывается рядом со стабильной, изначально без трафика.
3. **Начальный трафик** — небольшой процент пользователей (1–5%) направляется на canary-версию.
4. **Анализ и мониторинг** — активное наблюдение за техническими и бизнес-метриками canary-версии в сравнении со стабильной.
5. **Поэтапное увеличение** — при нормальных метриках доля трафика постепенно увеличивается (1% → 10% → 50% → 100%).
6. **Завершение** — после успешной проверки на 100% трафика новая версия становится стабильной.
7. **Деактивация** — старая версия выводится из эксплуатации.

### Требования к инфраструктуре

- **Service Mesh или Ingress-контроллер** — для маршрутизации трафика (Istio, NGINX, Traefik).
- **Система мониторинга** — для сбора и анализа метрик (Prometheus, Grafana).
- **CI/CD-пайплайн** — для автоматизации процесса выкатки.

## Практические сценарии

### Реализация с помощью Istio

Istio позволяет гибко управлять весами трафика между версиями сервиса через `VirtualService`.

```yaml
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app
spec:
  hosts:
    - "my-app.example.com"
  http:
    - route:
        - destination:
            host: my-app
            subset: stable
          weight: 95
        - destination:
            host: my-app
            subset: canary
          weight: 5
```

Изменение весов выполняется декларативно обновлением манифеста. Для автоматизации процесса используются инструменты вроде Argo Rollouts.

### Реализация через Feature Toggles

Альтернативный подход — управление на уровне кода с помощью [флагов функций](../Testing/feature_toggles/scenarios.md). Флаг определяет, какая версия логики выполняется для конкретного пользователя на основе хеша ID или других атрибутов.

## Дополнительная информация

### Мониторинг и автоматическое принятие решений (Gating)

Ключ к успешному Canary — автоматический анализ метрик. Детальный разбор метрик, PromQL-запросов и порогов описан в документе [Мониторинг и оценка трафика при Canary](./canary_monitoring_and_gating.md).

**Что анализировать:**

- Уровень ошибок (5xx, 4xx).
- Задержки (latency p95, p99).
- Использование ресурсов (CPU, Memory).
- Бизнес-метрики (конверсия, количество заказов).

**Как анализировать:** Показатели canary-версии сравниваются со стабильной. Резкое отклонение (деградация) должно автоматически останавливать выкатку.

### Canary vs. A/B Testing

Обе методологии используют разделение трафика, но цели принципиально различаются.

| Аспект | Canary Deployment | A/B Testing |
| :--- | :--- | :--- |
| **Основная цель** | Снижение риска при выкатке новой версии | Проверка бизнес-гипотезы (например, "новая кнопка увеличит конверсию") |
| **Аудитория** | Небольшая случайная группа пользователей или внутренние тестеры | Четко определенные статистически значимые сегменты пользователей |
| **Длительность** | Краткосрочно (минуты/часы) | Долгосрочно (дни/недели до набора статистики) |
| **Критерии успеха** | Технические метрики в норме (нет роста ошибок, задержек) | Продуктовые и бизнес-метрики показывают улучшение |
| **Результат** | Полная выкатка новой версии или откат | Выбор наиболее успешного варианта (A или B) как постоянного |

### Best Practices

- **Начинайте с малого** — стартовый процент трафика 1–5%.
- **Определите критерии успеха** — заранее установите пороги для метрик.
- **Используйте circuit breakers** — для автоматической остановки при деградации.
- **Прогревайте кэш** — перед увеличением трафика дайте время на инициализацию.
- **Автоматизируйте процесс** — ручное управление увеличивает риск человеческой ошибки.
