# Canary Deployments: Пошаговое внедрение

### Определения

- **Канареечное развертывание (Canary Deployment)** — это стратегия выпуска, при которой новая версия приложения ("canary") выкатывается для небольшой, контролируемой группы пользователей, в то время как большинство продолжает использовать стабильную версию. Такой подход позволяет оценить влияние изменений в реальных условиях и минимизировать риски перед полным развертыванием.

### Основные концепции

#### Цели и предпосылки

- **Цель:** Снижение риска инцидентов путем раннего обнаружения проблем на малой доле трафика.
- **Предпосылки:**
  - **Управление трафиком (Traffic Splitting):** Возможность точно направлять процент трафика на разные версии сервиса.
  - **Наблюдаемость:** Раздельный мониторинг метрик для стабильной и канареечной версий.
  - **Автоматизация:** Механизмы для автоматического увеличения доли трафика или отката на основе анализа метрик.

#### Этапы канареечного релиза

1. **Подготовка:** Собирается и версионируется новый артефакт.
2. **Параллельное развертывание:** Новая (canary) версия развертывается рядом со стабильной. Изначально на нее не подается трафик.
3. **Начальный трафик:** Небольшой процент пользователей (1-5%) направляется на canary-версию.
4. **Анализ и мониторинг:** Идет активное наблюдение за техническими и бизнес-метриками canary-версии в сравнении со стабильной.
5. **Поэтапное увеличение:** Если метрики в норме, доля трафика на canary-версию постепенно увеличивается (например, 1% → 10% → 50% → 100%).
6. **Завершение:** После успешной проверки на 100% трафика новая версия становится стабильной.
7. **Деактивация:** Старая версия выводится из эксплуатации.

### Практические сценарии

#### Реализация с помощью Service Mesh (Istio)

Istio позволяет гибко управлять весами трафика между разными версиями сервиса с помощью `VirtualService`.

```yaml
# VirtualService для направления 95% трафика на stable и 5% на canary
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: my-app
spec:
  hosts:
    - "my-app.example.com"
  http:
    - route:
        - destination:
            host: my-app
            subset: stable # Ссылка на Deployment стабильной версии
          weight: 95
        - destination:
            host: my-app
            subset: canary # Ссылка на Deployment canary-версии
          weight: 5
```

Изменение весов выполняется декларативно, обновляя этот манифест.

### Дополнительная информация

#### Мониторинг и автоматическое принятие решений (Gating)

Ключ к успешному Canary — автоматический анализ метрик.

- **Что анализировать:** Уровень ошибок (5xx), задержки (latency), использование ресурсов (CPU/Memory), а также ключевые бизнес-метрики (например, конверсия, количество заказов).
- **Как анализировать:** Сравниваются показатели canary-версии с показателями стабильной. Резкое отклонение (деградация) должно автоматически останавливать выкатку.
- **Подробнее:** Детальный разбор метрик, PromQL-запросов и порогов для автоматизации описан в документе **[Мониторинг и оценка трафика при Canary](./canary_monitoring_and_gating.md)**.

#### Canary vs. A/B Testing

Хотя обе методологии используют разделение трафика, их цели принципиально различаются.

| Аспект | Canary Deployment | A/B Testing |
| :--- | :--- | :--- |
| **Основная цель** | **Снижение риска** при выкатке новой версии. | **Проверка бизнес-гипотезы** (например, "новая кнопка увеличит конверсию"). |
| **Аудитория** | Небольшая, часто случайная группа пользователей или внутренние тестеры. | Четко определенные, статистически значимые сегменты пользователей. |
| **Длительность** | Краткосрочно (от нескольких минут до часов). | Долгосрочно (дни или недели, до набора статистики). |
| **Критерии успеха** | **Технические метрики** в норме (нет роста ошибок, задержек). | **Продуктовые и бизнес-метрики** показывают улучшение (конверсия, вовлеченность). |
| **Результат** | Полная выкатка новой версии или ее откат. | Выбор наиболее успешного варианта (A или B) как постоянного. |
