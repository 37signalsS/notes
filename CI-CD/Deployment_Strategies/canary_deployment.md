# Canary Deployments: Пошаговое внедрение

## Определения

**Канареечное развертывание (Canary Deployment)** — это контролируемое и поэтапное включение трафика на новую версию сервиса с постоянной валидацией метрик и возможностью оперативного отката. Подход снижает риск инцидентов, выделяя небольшую «канареечную» долю аудитории, на которой проверяется корректность изменений до полного выпуска.

## Основные концепции

### Цели и предпосылки

*   Управляемое изменение доли трафика (traffic splitting) между стабильной и новой версиями.
*   Автоматизированные проверки качества (SLO/SLA, алерты, бюджет ошибок).
*   Механизм быстрого отката без простоя.
*   Независимая наблюдаемость для каждой версии (метрики, логи, трейсинг).
*   Предварительная совместимость схем БД, миграций и контрактов API.

### Этапы канареечного релиза

1.  **Подготовка**: Соберите артефакт новой версии, подпишите и сохраните в реестре, обозначьте версию (например, v2).
2.  **Параллельный деплой**: Разверните стабильную (v1) и канареечную (v2) версии рядом. Стабильная получает весь трафик, канареечная — 0%.
3.  **Старт трафика**: Направьте 0.5–1% пользовательского трафика на v2. Включите синтетические проверки и нагрузку малого объёма.
4.  **Наблюдаемость**: Отслеживайте ключевые показатели для v2 (ошибки, латентность, ресурсные лимиты, бизнес-метрики).
5.  **Пошаговое наращивание**: Увеличивайте долю (1% → 5% → 10% → 25% → 50% → 100%), соблюдая «стабилизационные окна» между шагами.
6.  **Автоматизация гейтсов**: Фиксируйте пороги срабатывания автоматической паузы/отката (guardrails).
7.  **Завершение**: При достижении 100% переведите стабильный трафик на v2, оставьте наблюдение в повышенном режиме.
8.  **Деактивация**: Аккуратно выведите v1 из эксплуатации, убедившись в завершении фоновых задач и отсутствии «залипших» сессий.

## Практические сценарии

### Техническая реализация (Kubernetes + Istio)

Предполагается, что вы развернули два Deployment: `app v1` (stable) и `app v2` (canary) с меткой `version`.

**Пример DestinationRule и VirtualService для взвешенного трафика:**

```yaml
apiVersion: networking.istio.io/v1beta1
kind: DestinationRule
metadata:
  name: app
spec:
  host: app.default.svc.cluster.local
  subsets:
    - name: stable
      labels:
        version: v1
    - name: canary
      labels:
        version: v2
---
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: app
spec:
  hosts:
    - app.example.local
  http:
    - route:
        - destination:
            host: app.default.svc.cluster.local
            subset: stable
          weight: 99
        - destination:
            host: app.default.svc.cluster.local
            subset: canary
          weight: 1
```

Пошаговое изменение весов может выполняться через `kubectl patch`:

```bash
kubectl patch virtualservice app --type merge -p '{
  "spec": {"http":[{"route":[
    {"destination":{"host":"app.default.svc.cluster.local","subset":"stable"},"weight":95},
    {"destination":{"host":"app.default.svc.cluster.local","subset":"canary"},"weight":5}
  ]}]}
}'
```

## Дополнительная информация

### Метрики, гейты и алерты

**Рекомендуемые гейты (пороги):**

*   **Ошибки 5xx (канареечная версия)**: <1% от запросов.
*   **P95 латентности**: Не хуже стабильной более чем на X%.
*   **Доля успешных бизнес-событий**: В пределах допусков.
*   **Потребление ресурсов**: Без троттлинга и OOM.

**Примеры выражений для контроля (Prometheus):**

*   Доля ошибок:
    ```promql
    rate(http_requests_total{app="app",version="v2",status=~"5.."}[5m]) /
    rate(http_requests_total{app="app",version="v2"}[5m])
    ```
*   Квантиль задержки:
    ```promql
    histogram_quantile(0.95, sum by (le) (
      rate(http_request_duration_seconds_bucket{app="app",version="v2"}[5m])
    ))
    ```

### Типичные риски и приёмы

*   Миграции данных выполняются с обратной совместимостью (expand → deploy → contract).
*   Sticky-сессии и кеши согласуются с роутингом канарейки.
*   Feature flags помогают ограничить воздействие функций без повторного деплоя.
*   Трафик для ботов, админов и внутренней когорты можно направлять в канарейку первыми.
*   Авто-rollback интегрируется через контроллеры прогрессивного релиза (например, операторы, применяющие политики гейтов).
