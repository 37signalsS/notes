# Управление парком раннеров (Runner Fleet Management)

**Актуально для:** GitLab CI, GitHub Actions, Jenkins 2024–2026

> Область применения заметок: практики DevOps, SRE и SysAdmin при эксплуатации самостоятельно развёрнутых (on-prem / self-hosted) систем. Материалы, относящиеся к публичным облакам и технологиям искусственного интеллекта, в данной базе знаний не рассматриваются.

## Определения

**Управление парком раннеров (Runner Fleet Management)** — это совокупность административных, политических и технических процессов по обеспечению CI/CD мощностями в масштабах организации. Фокус смещается с настройки отдельного раннера на управление сотнями и тысячами исполнителей как единым ресурсом.

**Политики распределения ресурсов (Resource Allocation Policies)** — набор правил, определяющих, какие команды, проекты или типы задач имеют приоритетный доступ к вычислительным мощностям.

**Квотирование (Quotas)** — жесткие или мягкие ограничения на потребление ресурсов (минуты выполнения, количество параллельных джоб, CPU/RAM) на уровне групп пользователей или департаментов.

**Оркестратор флота (Fleet Orchestrator)** — компонент (например, GitLab Taskscaler или GitHub Runner Controller), который управляет жизненным циклом раннеров: созданием, регистрацией, мониторингом здоровья и удалением.

**Золотой образ (Golden Image)** — предварительно настроенный и протестированный шаблон ОС или контейнера, содержащий стандартный набор инструментов, библиотек и средств безопасности.

**Эфемерный раннер (Ephemeral Runner)** — исполнитель, который после выполнения одной (или ограниченного числа) задач уничтожается и заменяется свежим. Исключает накопление состояния (side-effects), кэша атак и «сноубола» зависимостей между джобами.

**Плотность упаковки (Bin-packing)** — стратегия размещения нескольких параллельных джоб на один узел так, чтобы минимизировать неиспользуемые остатки CPU/RAM и снизить число физических узлов.

## Архитектура управления флотом

Современный парк раннеров строится на базе трехуровневой архитектуры:

1.  **Уровень управления (Control Plane):** CI/CD сервер (GitLab, GitHub, Jenkins), который распределяет задачи и хранит метаданные о состоянии флота.
2.  **Уровень координации (Orchestration Layer):** Автоскейлеры и контроллеры (например, **KEDA** для кластера оркестратора (Kubernetes) или **Fleeting** для динамических пулов инстансов, в т.ч. на собственных гипервизорах). Они принимают решение о масштабировании на основе длины очереди или расписания.
3.  **Уровень исполнения (Execution Layer):** Непосредственно раннеры (VM, контейнеры, Bare Metal, Pod в кластере оркестратора), где выполняется код джобы.

### Жизненный цикл раннера (Lifecycle)

1.  **Provisioning:** Динамическое создание вычислительного ресурса (виртуальная машина, Pod в кластере оркестратора).
2.  **Registration:** Автоматическая регистрация раннера в CI-системе с использованием временных токенов (JIT Config).
3.  **Execution:** Выполнение одной или нескольких задач (в зависимости от политики эфемерности).
4.  **Deregistration:** Корректное удаление раннера из списка активных в Control Plane.
5.  **Termination/Cleanup:** Уничтожение ресурса для предотвращения накопления состояния (Side-effects).

### Стратегии исполнения: эфемерные vs постоянные раннеры

| Свойство | Эфемерные (Ephemeral) | Постоянные (Persistent/Static) |
| :--- | :--- | :--- |
| **Жизнь узла** | Создаётся под задачу, удаляется после | Живёт недели/месяцы |
| **Воспроизводимость** | Максимальная (всегда чистое окружение) | Риск «дрейфа» конфигурации |
| **Безопасность** | Поверхность атаки не накапливается | Требует регулярного патчинга и очистки |
| **Cold Start** | Выше (загрузка ОС/образа) | Ниже (узел уже готов) |
| **Стоимость/амортизация** | Платим только за время задачи | Платим за простой тоже |
| **Где применять** | Тесты, сборки, непривилегированный код | Долгие интеграционные стенды, кэш-зависимые задачи |

Рекомендация: по умолчанию — эфемерные раннеры; постоянные оставлять только для узкоспециализированных долгоживущих стендов с контролируемым доступом.

## Политические и административные аспекты (Governance)

1.  **Централизация vs Децентрализация:**
    - **Централизованный флот (Shared Runners):** Единая команда Platform Engineering управляет пулом ресурсов. Обеспечивает стандартизацию, патчинг безопасности и экономию за счет масштаба.
    - **Децентрализованный флот (Specific/Project Runners):** Команды сами запускают свои раннеры для специфических нужд (например, доступ к локальному стенду). Требует жестких политик (Policy-as-Code) для предотвращения нарушения безопасности.
2.  **Управление токенами:** Переход от долгоживущих регистрационных токенов к динамическим (например, через **OIDC** или **App Tokens**), что исключает компрометацию всего флота при утечке одного ключа. Жизненный цикл секретов и хранение в менеджере (Vault) описаны в разделе **[Безопасность секретов](./DevSecOps/secrets_management.md)**.
3.  **Стандартизация окружений:** Использование инструментов типа **Packer** или **Docker** для сборки идемпотентных образов. Все инструменты должны устанавливаться из доверенных внутренних репозиториев.

## Политики распределения ресурсов (Resource Allocation Policies)

Эффективное распределение мощностей (Resource Scheduling):

*   **Приоритизация (Priority Classes):** Использование `PriorityClass` в кластере оркестратора (Kubernetes) для вытеснения (preemption) джоб разработки в пользу релизных пайплайнов.
*   **Affinity и Taints/Tolerations:**
    - **Taints:** Пометка узлов с GPU или Apple Silicon, чтобы на них не попадали обычные джобы.
    - **Affinity:** Привязка тяжелых сборок к узлам с локальными NVMe дисками.
*   **Fair Share (Справедливость):** Ограничение максимального количества параллельных слотов на одного пользователя/проект, чтобы один «тяжелый» пайплайн не заблокировал весь флот.

## Квотирование и лимиты (Quotas)

### Техническая реализация квот

1.  **ResourceQuotas в кластере оркестратора (Kubernetes):** Ограничение суммарного потребления в неймспейсе, где живут раннеры.
    ```yaml
    apiVersion: v1
    kind: ResourceQuota
    metadata:
      name: ci-runners-quota
      namespace: gitlab-runners
    spec:
      hard:
        pods: "100"
        requests.cpu: "200"
        requests.memory: 500Gi
        limits.cpu: "400"
        limits.memory: 800Gi
    ```
2.  **Minutes Quotas (GitLab/GitHub):** Настройка лимитов на уровне групп через API или интерфейс администратора.
3.  **Concurrency Limits:** Параметр `concurrent` в `config.toml` GitLab Runner или `max_parallel` в матричных сборках.

## Планирование мощностей (Capacity Planning)

Планирование емкости флота — задача SRE/Platform: переплата за простой vs задержки (queue time) при нехватке.

**Базовая формула оценки пиковой емкости (в слотах):**

```
пиковые_слоты ≈ (среднее_число_параллельных_джоб_в_пик × среднее_время_джоб_сек) / допустимое_время_ожидания_сек × запас(headroom)
```

Где `запас` обычно 1.2–1.3 (20–30% на всплески и обслуживание узлов).

**Практические шаги (SysAdmin):**
- Собрать историю из очереди (Prometheus/Grafana) за 2–4 недели, выделить p95/p99 параллелизма.
- Выбрать размер узла под **bin-packing**: если средняя джоба требует 2 CPU / 4 GiB, узел на 16 CPU / 32 GiB вместит ~7–8 параллельных джоб с запасом, а не 8 «впритык» (риск OOM при всплеске).
- Учитывать «тяжелые» джоб (интеграционные тесты, сборки монолита) отдельно — выносить на выделенные узлы через Taints, чтобы они не вытесняли обычные.
- Регулярно пересматривать: рост числа команд линейно увеличивает слоты, но эффективность упаковки падает при фрагментации.

Подробная FinOps-методология и метрики стоимости — в **[Оптимизация затрат в CI/CD](./Core_Concepts/cost-optimization.md)**.

## Стратегии масштабирования и экономика

### Автомасштабирование (Autoscaling)

*   **Reactive Scaling:** Масштабирование по факту появления джоб в очереди. Минимум затрат, но возможны задержки при старте (Cold Start).
*   **Predictive Scaling:** Использование исторических данных для подготовки мощностей к пикам нагрузки (например, к 10:00 утра в понедельник).
*   **KEDA (Kubernetes Event-driven Autoscaling):** Рекомендуемый подход для кластера оркестратора (Kubernetes). Скалер опрашивает API GitLab/GitHub и масштабирует Deployment раннеров на основе количества ожидающих джоб.

### Экономическая оптимизация

*   **Прерываемые инстансы:** Использование дешевых прерываемых инстансов (собственные узлы с вытеснением или гипервизорная консолидация) позволяет существенно снизить стоимость флота. Для этого джобы должны поддерживать механизм **Retry** и быть атомарными.
*   **ARM64:** Перевод части флота на ARM-архитектуру (собственные серверы Ampere/Apple Silicon или ARM-ВМ) обеспечивает лучшее соотношение цена/производительность (до 40% экономии по сравнению с x86) при технической возможности кросс-компиляции.
*   **Warm Pools:** Группа «подогретых» инстансов, которые уже прошли стадию загрузки ОС, но еще не взяли задачу. Снижает время старта с минут до секунд.

### Здоровье флота: draining, graceful shutdown и проверки (SRE)

- **Кордонирование (Cordon):** При обнаружении деградации узел выводится из ротации (не принимает новые джобы), текущие дорабатываются.
- **Drain и замена:** Узел с неисправимой проблемой (битый диск, утечка памяти процесса сборки) — завершить активные джобы (или корректный retry) и уничтожить, запустив свежий из золотого образа.
- **Graceful shutdown:** Раннер должен корректно обработать `SIGTERM` — либо дождаться конца текущей джобы, либо вернуть её в очередь (retry), не оставляя «висящих» задач.
- **Профилактика частых инцидентов:** `No space left on device` — мониторинг свободного места на `/var/lib/docker`, `/tmp` и автоочистка (`docker system prune`, очистка кэша пакетных менеджеров); `CPU steal` высокий — признак перепродажи (oversubscription) гипервизором, сигнал к перераспределению.

## Безопасность флота (Runner Security)

Раннеры по определению выполняют недоверенный код (чужие PR, сторонние зависимости), поэтому являются критичной поверхностью атаки цепочки поставок.

- **Сетевая изоляция:** Раннеры — в выделенном сегменте/VLAN без доступа в приватные подсети управления; разрешён только egress до нужных внутренних реестров артефактов и зеркал пакетов. Запрет прямого доступа раннеров к секретам инфраструктуры.
- **Минимум привилегий (least privilege):** Раннер получает только токен для своего проекта/группы; pull-токены для прод-сред — из менеджера секретов, а не из переменных репозитория. Принципы защиты секретов — в **[Безопасность секретов](./DevSecOps/secrets_management.md)**.
- **Динамические токены и OIDC:** JIT-регистрация + федерация через OIDC вместо статических токенов; обязательная ротация. Общие принципы — в **[DevSecOps: Обзор](./DevSecOps/devsecops_overview.md)**.
- **Эфемерность как контрмера:** Уничтожение узла после задачи снижает риск кэш-отравления (cache poisoning) и накопления скомпрометированного состояния.
- **Изоляция кэша/артефактов:** Не разделять кэш и артефакты между проектами без проверки происхождения — иначе возможна атака через подмену зависимости в общем кэше.

## Мониторинг и наблюдаемость (Observability)

Ключевые метрики эффективности флота:

1.  **Queue Time (Lead Time to Start):** Время, которое джоба проводит в статусе `pending`. Целевой показатель для Tier-1 — менее 10 секунд.
2.  **Runner Saturation:** Процент занятых слотов относительно общей емкости флота. Оптимальное значение — 70-80%.
3.  **Failure Rate (Infrastructure-related):** Количество падений джоб из-за ошибок инфраструктуры (например, `No space left on device` или инфраструктурные таймауты).
4.  **Cost per Job:** Финансовая метрика, помогающая оценить эффективность использования прерываемых инстансов и квот.

Эти метрики напрямую влияют на **[Метрики DORA](./Core_Concepts/dora_metrics.md)** (Deployment Frequency, Lead Time for Changes, MTTR).

**Инструментарий:**
- Экспорт метрик через **Prometheus** (GitLab Runner имеет встроенный `/metrics` эндпоинт).
- Визуализация в **Grafana** (Dashboards для отслеживания утилизации нод и очередей).
- Подробный подход к мониторингу пайплайнов — в **[Наблюдаемость пайплайнов](./Core_Concepts/pipeline_observability.md)**.

## Практические сценарии

### Сценарий 1: Масштабируемый флот в кластере оркестратора с KEDA (GitLab)

Пример настройки `ScaledObject` для автоматического масштабирования раннеров на основе очереди (self-hosted GitLab):

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: gitlab-runner-scaler
spec:
  scaleTargetRef:
    name: gitlab-runner-deployment
  minReplicaCount: 1
  maxReplicaCount: 50
  triggers:
  - type: gitlab
    metadata:
      url: https://gitlab.corp.local          # self-hosted инстанс
      tokenFromEnv: GITLAB_READ_TOKEN # Токен с правами read_api
      registrationTokenFromEnv: RUNNER_TOKEN
```

### Сценарий 2: Эфемерные раннеры на собственных гипервизорах (Fleeting + libvirt/KVM)

Вместо инстансов внешних провайдеров пул поднимается на своих гипервизорах. После каждой задачи VM уничтожается — состояние не накапливается.

```toml
[[runners]]
  name = "kvm-ephemeral-fleet"
  executor = "docker-autoscaled"
  [runners.autoscaler]
    plugin = "libvirt"        # собственный гипервизор, без привязки к внешним провайдерам
    capacity_per_instance = 1
    max_instances = 50
    [runners.autoscaler.plugin_config]
      uri = "qemu:///system"
      template = "ci-runner-ubuntu-22.04"  # золотой образ ВМ
```

Ключевые параметры (`uri`, `template`) зависят от выбранного гипервизора (libvirt/KVM, VMware). Важно: `executor = "docker-autoscaled"` (или `custom`) + эфемерная VM дают модель «одна джоба — один свежий узел».

### Сценарий 3: Статический пул self-hosted раннеров (systemd)

Для небольших контурoв или долгоживущих стендов раннер ставится как системный сервис:

```bash
# Установка и регистрация GitLab Runner (self-hosted инстанс)
sudo gitlab-runner install --user gitlab-runner --working-directory /srv/gitlab-runner
sudo gitlab-runner register \
  --non-interactive \
  --url "https://gitlab.corp.local" \
  --token "$RUNNER_REGISTRATION_TOKEN" \
  --executor "docker" \
  --description "static-docker-$(hostname)" \
  --tag-list "linux,docker,shared" \
  --run-untagged="true" \
  --locked="false"
sudo systemctl enable --now gitlab-runner
```

Ограничение параллелизма задаётся в `/etc/gitlab-runner/config.toml` (`concurrent = N`). Такие раннеры не масштабируются сами — их число контролирует администратор (см. Планирование мощностей).

### Сценарий 4: Мониторинг флота (Prometheus + Grafana, PromQL)

```yaml
# scrape-конфиг: опрашиваем /metrics каждого раннера
scrape_configs:
  - job_name: gitlab-runner
    static_configs:
      - targets: ['runner-1.corp.local:9252', 'runner-2.corp.local:9252']
```

Полезные запросы:

```promql
# Текущий размер очереди (джоб в ожидании)
gitlab_runner_queue_size

# Занятые раннеры (running)
sum(gitlab_runner_jobs{state="running"})

# Доля инфраструктурных падений (сигнал к cordon/drain)
rate(gitlab_runner_job_failures_total{reason="runner_system_failure"}[5m])

# Утилизация слотов
sum(gitlab_runner_jobs{state="running"}) / count(gitlab_runner_jobs) * 100
```

Алерты строятся на `gitlab_runner_queue_size > 0` за длительное окно и на росте `runner_system_failure`.

### Сценарий 5: GitHub Actions Runner Controller на собственном кластере

Для self-hosted раннеров GitHub Actions используется ARC (actions-runner-controller), управляющий pod-раннерами внутри собственного кластера оркестратора. В текущей версии ARC — пара Helm-чартов (`gha-runner-scale-set-controller` + `gha-runner-scale-set`): controller-manager в одном namespace, эфемерные runner-поды в другом; listener масштабирует поды по числу назначенных job'ов, регистрация — через JIT-токены. Это даёт те же преимущества эфемерности, что и KEDA/GitLab, без привязки к внешним провайдерам. Подробная настройка ARC (Helm, GitHub App auth, containerMode dind/kubernetes, custom images, метрики, troubleshooting) — в **[dedicated файле](../Github_CI/actions_runner_controller.md)**.

> Примечание: прежние autoscaling-режимы ARC с CRD `RunnerDeployment`/`RunnerScaleSet` (API `actions.summerwind.net/v1alpha1`) объявлены legacy и поддерживаются только сообществом — см. раздел «Legacy-режим сообщества» в dedicated файле.

## Ограничения и крайние случаи

- **Air-gapped среды:** В изолированных сетях раннер не может тянуть образы из публичных реестров. Решение — pré-downloaded golden images на узлы или внутренние зеркала (Nexus, Harbor, MinIO). Подробнее: **[Изолированные среды (Air-gapped)](./Core_Concepts/air_gapped_environments.md)**.
- **Нагрузка на control plane:** Частая регистрация/deregistration эфемерных раннеров создаёт шум в API CI-сервера. Ограничьте `check_interval` и используйте JIT Config, чтобы не хранить старые токены.
- **Cold start эфемерных раннеров:** Загрузка ОС/образа добавляет латентность. Для latency-чувствительных пайплайнов — warm pools или постоянные раннеры с контролируемым доступом.
- **Multi-tenancy и кэш:** Общий кэш между проектами — поверхность атаки (cache poisoning). Изолируйте кэш по namespace/project или используйте scoped S3-бакеты.
- **Устаревшие/проприетарные гипервизоры:** Не все гипервизоры имеют плагины для Fleeting/Taskscaler. Для VMware, OpenStack, Proxmox, libvirt — проверьте актуальность плагина перед внедрением.
- **Регуляторные требования:** В regulated industries требуется audit trail: какой раннер, какой токен, какой джоб, какие секреты использовались. Включайте structured logging и централизованный сбор логов.
- **Noisy neighbor:** При bin-packing на одном узле «тяжёлый» джоб может выедать CPU/RAM у соседних. Используйте cgroups/Docker resource limits и выделенные узлы через Taints.

## Устранение неполадок (Troubleshooting)

| Симптом | Вероятная причина | Действие |
| :--- | :--- | :--- |
| Очередь растёт, раннеры idle | Неверные теги, `concurrent` слишком низкий, нет matching runner | Проверить теги джоба и раннеров, `concurrent` в `config.toml` |
| Джобы зависают в `pending` | Нет свободных слотов, автокейлер не работает | Метрика Queue Time; проверить health autoscaler, minReplicaCount |
| Cold start > 60 сек | Тяжёлый golden image, холодный кэш зависимостей | Оптимизировать образ, включить warm pool, предварительный pull зависимостей |
| `No space left on device` | Логи/кэш/артефакты заполнили диск | Настроить `docker system prune`, ограничить retention артефактов, мониторинг диска |
| Кэш отравлён (cache poisoning) | Общий кэш между проектами | Изолировать кэш, использовать ephemeral runners для недоверенного кода |
| Раннер не deregister после удаления | Устаревшая запись в CI-сервере | Скрипт очистки через API; настроить TTL на регистрацию |
| Токен регистрации истёк | Долгоживущий статический токен | Переход на JIT Config / OIDC; мониторинг срока действия токена |
| Раннер скомпрометирован | Утечка через workspace или кэш | Уничтожить узел, rebuild из golden image, отозвать токен |

## Дополнительная информация

### Рекомендации

1. По умолчанию — эфемерные раннеры; постоянные оставлять только для специализированных долгоживущих стендов с контролируемым доступом.
2. Используйте золотые образы (Packer, Docker) для идемпотентного развёртывания; все инструменты — из доверенных внутренних репозиториев.
3. Переход с долгоживущих регистрационных токенов на динамические (JIT Config, OIDC) — исключает компрометацию всего флота при утечке одного ключа.
4. Мониторьте флот как инфраструктуру: Queue Time, Runner Saturation, Failure Rate — это SRE-метрики с алертами, а не разовые проверки.
5. Настраивайте bin-packing с запасом 20–30% на headroom; выделяйте «тяжёлые» джобы на отдельные узлы через Taints.
6. В air-gapped средах pré-downloaded образы или внутренние зеркала; запрещайте раннерам прямой выход в публичный Internet.
7. Изолируйте кэш и артефакты между проектами — иначе общий кэш становится вектором атаки (cache poisoning).
8. Регулярно выполняйте drain/cordon при обновлениях и инцидентах; завершайте активные джобы gracefully через `SIGTERM`.
9. Ограничивайте `concurrent` и `limit` на уровне раннера, чтобы один «тяжёлый» пайплайн не занимал весь флот.
10. Включайте structured logging и централизованный сбор логов для audit trail и расследования инцидентов.
