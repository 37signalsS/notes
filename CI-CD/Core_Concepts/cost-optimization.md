# Оптимизация затрат в CI/CD (FinOps)

Руководство по управлению расходами на инфраструктуру автоматизации, обеспечению прозрачности затрат и внедрению культуры бережливого использования облачных ресурсов.

## Определения

- **CI/CD FinOps** — практика управления облачными затратами на инфраструктуру автоматизации (раннеры, окружения, хранилище артефактов), направленная на достижение баланса между скоростью поставки и эффективностью расходов.
- **Infracost** — инструмент оценки стоимости инфраструктурных изменений (IaC) непосредственно в Pull/Merge Request.
- **Spot-инстанции (AWS/GCP/Yandex)** — избыточные мощности облачных провайдеров, предоставляемые со значительной скидкой (до 90%), но с возможностью прерывания в любой момент.
- **Fleeting (GitLab)** — архитектура масштабирования GitLab Runner, использующая облачные плагины для динамического управления парком эфемерных исполнителей.
- **Облачные потери (Cloud Waste)** — затраты на зарезервированные, но не используемые ресурсы (например, «забытые» Review Apps или избыточно выделенные CPU/RAM для простых задач).
- **Удельная стоимость сборки (Unit Cost per Build)** — метрика, показывающая среднюю стоимость одного прохождения пайплайна, используемая для оценки ROI автоматизации.
- **Сайзинг (Right-sizing)** — процесс подбора оптимальных характеристик ресурсов (CPU, RAM, Disk) под конкретную нагрузку задачи CI/CD.

## Базовые концепции

### 1. Управление исполнителями (Runner Scaling)

Оптимизация затрат на раннеры строится на переходе от постоянно включенных серверов к модели «по запросу»:

- **Эфемерность:** Раннеры создаются только при наличии задачи и удаляются сразу после её завершения, исключая оплату простоя.
- **Автоскейлинг:** Динамическое изменение количества инстансов в зависимости от длины очереди задач.
- **Смешанные стратегии:** Использование надежных On-Demand инстансов для критических задач (Deploy, Production Hotfix) и дешевых Spot-инстансов для обычных билдов и тестов.

### 2. Жизненный цикл окружений (Environment Lifecycle)

Динамические окружения (Review Apps) — основной источник нецелевых трат из-за их большого количества.

- **TTL (Time To Live):** Каждое динамическое окружение должно иметь жестко заданный срок жизни (например, 24 часа или до закрытия Merge Request).
- **Автоматическая остановка (Auto-stop):** Выключение или удаление ресурсов в нерабочее время (например, остановка кластеров БД или K8s-узлов ночью и в выходные).
- **Общие ресурсы (Shared Resources):** Использование одного кластера БД с разделением по логическим базам/схемам или одного Ingress-контроллера для всех Review Apps вместо создания полных копий инфраструктуры.

### 3. Квотирование и лимиты

Предотвращение влияния «шумных соседей» и бесконтрольного потребления ресурсов:

- **Resource Quotas:** Ограничение суммарного потребления ресурсов на уровне проекта или пространства имен (Namespace).
- **Default Limits:** Обязательное указание `requests` и `limits` для каждой задачи CI, чтобы простые операции (например, линтинг) не резервировали избыточные мощности.
- **Artifact Retention:** Политики автоматической очистки старых образов, логов и артефактов, основанные на их возрасте или статусе ветки.

### 4. Оптимизация сетевых затрат (Network Cost Awareness)

- **Egress-трафик:** Перенос Registry и S3-бакетов в тот же регион/зону, где работают раннеры, для минимизации платы за передачу данных.
- **Локальное кэширование:** Использование прокси-серверов для внешних зависимостей (Nexus, Artifactory, Pull-through cache для Docker) для сокращения внешнего трафика.

## Практические сценарии

### Сценарий 1: Внедрение Infracost в пайплайн

Интеграция позволяет разработчику увидеть стоимость изменений инфраструктуры до их применения (Shift-left FinOps).

```yaml
infracost:
  stage: validate
  image:
    name: infracost/infracost:ci-0.10
    entrypoint: [""]
  variables:
    INFRACOST_API_KEY: $INFRACOST_API_KEY
    TF_ROOT: terraform/
  script:
    # Генерация базового состояния
    - infracost breakdown --path=$TF_ROOT --format=json --out-file=infracost-base.json
    # Сравнение с текущими изменениями
    - infracost diff --path=$TF_ROOT --format=json --compare-to=infracost-base.json --out-file=infracost-diff.json
    # Публикация комментария в Merge Request
    - infracost comment gitlab --path=infracost-diff.json --repo=$CI_PROJECT_PATH --merge-request=$CI_MERGE_REQUEST_IID --token=$GITLAB_TOKEN
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
```

### Сценарий 2: Настройка GitLab Runner на Spot-инстансах с Fleeting

Использование Spot-инстансов AWS для масштабирования Docker-исполнителей.

**Файл конфигурации `config.toml`:**
```toml
[[runners]]
  name = "aws-spot-autoscaler"
  executor = "docker-autoscaler"
  [runners.autoscaler]
    plugin = "aws"
    capacity_per_instance = 1
    max_instances = 100
    idle_count = 2
    idle_time = "20m"
    [runners.autoscaler.plugin_config]
      name = "ci-runners-asg" # Имя Auto Scaling Group в AWS
      # ASG должна быть настроена на использование Spot Instances с диверсификацией типов
```

### Сценарий 3: Управление TTL для динамических окружений

Настройка автоматического удаления Review Apps в GitLab CI.

```yaml
deploy_review:
  stage: deploy
  script:
    - ./deploy.sh
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    url: https://$CI_COMMIT_REF_SLUG.example.com
    on_stop: stop_review
    auto_stop_in: 1 day  # Окружение удалится автоматически через 24 часа

stop_review:
  stage: cleanup
  script:
    - helm uninstall my-app-$CI_COMMIT_REF_SLUG
  when: manual
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
```

### Сценарий 4: Очистка артефактов в GitLab Registry

Использование политик очистки для предотвращения бесконтрольного роста хранилища.

**Настройка через интерфейс (Project Settings -> Packages and registries):**
- **Keep the most recent:** 10 тегов.
- **Keep tags matching:** `master`, `production`, `v.*`.
- **Remove tags older than:** 30 days.
- **Remove tags matching:** `.*-dev`, `build-.*`.

## Валидация

Для проверки эффективности оптимизации необходимо контролировать следующие показатели:

1.  **Проверка Unit Cost:** Рассчитайте среднюю стоимость пайплайна до и после внедрения изменений с помощью **Kubecost** или **Cloud Health**.
2.  **Аудит Spot-прерываний:** Убедитесь, что процент падений задач из-за прерывания Spot-инстансов не превышает допустимый порог (обычно < 5%).
3.  **Контроль Cloud Waste:** Еженедельный отчет о ресурсах без тегов TTL или «осиротевших» (orphaned) томах/IP.
4.  **Мониторинг кэша:** Проверка Cache Hit Rate — низкий показатель означает излишние затраты на трафик и время сборки.

## Устранение неисправностей

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Высокий процент отказов на Spot** | Недостаток мощностей выбранного типа инстанса в зоне. | Диверсифицируйте типы инстансов в настройках автоскейлера. |
| **Review Apps не удаляются** | Ошибка в `on_stop` скрипте или отсутствие прав у раннера. | Проверьте логи стадии `cleanup` и права доступа к K8s/Cloud API. |
| **Рост затрат на трафик (Egress)** | Раннеры тянут тяжелые образы из другого региона. | Настройте локальный Docker Mirror (Pull-through cache). |
| **Пайплайны стали работать медленнее** | Слишком жесткие лимиты CPU/RAM для задач. | Проведите профилирование нагрузки и скорректируйте `requests/limits`. |

## Ограничения и граничные случаи

- **Spot Availability:** В периоды высокого спроса Spot-инстансы могут быть недоступны. Всегда имейте резервный пул On-Demand инстансов с низким приоритетом.
- **Stateful workloads:** Инструменты автоматизации, требующие сохранения состояния на диске, плохо подходят для Spot-инстансов.
- **Затраты на внедрение:** Сложные системы FinOps (например, кастомные скрипты очистки) сами требуют ресурсов на разработку и поддержку. Оценивайте окупаемость сложности.
- **Data Locality:** Регуляторные требования могут запрещать перенос данных (артефактов) в другие регионы ради экономии.

## Дополнительная информация

### Лучшие практики

1.  **Кэширование зависимостей:** Сохраняйте `node_modules`, `.m2`, `venv` между запусками. Это сокращает время использования платных раннеров.
2.  **Multi-stage builds:** Собирайте компактные образы (Alpine, Distroless). Меньше размер — меньше плата за хранение и трафик.
3.  **Fail-Fast:** Размещайте самые дешевые и быстрые проверки (линтинг, статический анализ) в начале пайплайна, чтобы не тратить деньги на запуск тяжелых тестов в заведомо ошибочном коде.
4.  **Использование Graviton (ARM):** Инстансы на базе ARM часто на 20-40% дешевле при аналогичной производительности для задач CI (компиляция, тесты).
