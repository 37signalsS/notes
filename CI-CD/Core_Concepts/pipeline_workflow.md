# Типичный поток пайплайна

## Определения

- **Поток пайплайна (Pipeline Workflow)** — логически упорядоченная последовательность этапов (Stages) и задач (Jobs), обеспечивающая автоматизированную доставку изменений кода от момента фиксации (commit) до развертывания в продуктивной среде.

- **Ворота качества (Quality Gates)** — автоматизированные точки контроля в пайплайне, которые проверяют соответствие кода установленным критериям (покрытие тестами, отсутствие уязвимостей, соблюдение лимитов FinOps). Если критерии не выполнены, продвижение пайплайна блокируется.

- **Направленный ациклический граф (Directed Acyclic Graph, DAG)** — метод организации пайплайна, при котором задачи запускаются сразу после выполнения своих прямых зависимостей, не дожидаясь завершения всей стадии.

- **Эфемерные окружения (Ephemeral Environments / Preview Apps)** — временные изолированные экземпляры приложения, создаваемые пайплайном «на лету» (обычно для Merge Request) для функционального тестирования и ревью.

## Основные концепции

### Принципы эффективного пайплайна (Стандарты 2026)

Современный пайплайн должен быть быстрым, безопасным и прозрачным:

1.  **Fail-Fast (Падай быстро):** Самые быстрые и критические проверки (линтеры, Unit-тесты) выполняются в первую очередь. Это обеспечивает мгновенную обратную связь разработчику.
2.  **Параллелизм и DAG:** Использование директив `needs` (в GitLab CI) для построения графа зависимостей, что сокращает общее время выполнения за счет обхода синхронных барьеров стадий.
3.  **Иммутабельность артефактов:** Артефакт (например, Docker-образ) собирается один раз на ранних этапах и без изменений продвигается через все среды (Staging -> Prod).
4.  **Аттестация и SBOM:** Генерация программного счета материалов (**SBOM**) и подпись артефакта (соответствие уровням **SLSA**) для обеспечения безопасности цепочки поставок.
5.  **OIDC-First (OpenID Connect):** Отказ от статических секретов в пользу временных токенов при взаимодействии с облачными провайдерами (AWS, GCP, Yandex Cloud) и хранилищами секретов (**[Vault](../../Vault/vault_overview.md)**).
6.  **Shift-Left Security & FinOps:** Интеграция сканеров безопасности и инструментов оценки стоимости (например, **Infracost**) на этапе сборки. Подробнее в **[Оптимизации затрат в CI/CD](./cost-optimization.md)**.

### Структура канонического пайплайна

Жизненный цикл изменений в современном конвейере:

1.  **Валидация (Validate / Lint)**
    *   Проверка стиля кода (Linters) и форматирования.
    *   Проверка IaC-манифестов (Terraform, Helm, Kubernetes).
    *   **Secret Detection:** Поиск случайно закоммиченных паролей и токенов.
2.  **Тестирование (Test)**
    *   Unit-тестирование с генерацией отчетов о покрытии (Coverage).
    *   Интеграционные тесты с изоляцией зависимостей (например, через **Testcontainers**).
3.  **Сборка и Аттестация (Build & Attest)**
    *   Сборка бинарных файлов или образов.
    *   Генерация **SBOM** (CycloneDX или SPDX).
    *   Подпись артефакта (Cosign/Sigstore).
4.  **Безопасность (Security Scan)**
    *   **SCA (Software Composition Analysis):** Поиск уязвимостей в сторонних библиотеках.
    *   **SAST:** Статический анализ безопасности кода.
    *   **Container Scanning:** Поиск CVE в слоях Docker-образа.
5.  **Финансовый контроль (FinOps Gate)**
    *   Автоматическая оценка изменения стоимости инфраструктуры при изменении IaC-кода. Блокировка при превышении бюджета.
6.  **Развертывание в Preview (Deploy Preview)**
    *   Автоматическое создание эфемерного окружения для ветки.
    *   Запуск динамических тестов (**DAST**) и сквозных сценариев (**E2E**).
7.  **Верификация после слияния (Post-merge Verification)**
    *   Повторный прогон пайплайна в ветке `main` после слияния. Гарантирует, что интеграция прошла успешно и код готов к выкатке.
8.  **Продуктивное развертывание (Production Deploy)**
    *   Выкатка через **GitOps** (Pull Model) или Push-стратегии (Canary, Blue-Green).
    *   **Агентная верификация (Agentic Verification):** AI-агенты анализируют метрики (Error Rate, Latency) сразу после деплоя и автоматически инициируют Rollback при аномалиях.

## Практические сценарии

### Реализация оптимизированного пайплайна (GitLab CI)

Пример конфигурации с использованием DAG, кэширования и OIDC:

```yaml
stages:
  - validate
  - test
  - build
  - security
  - deploy-preview
  - deploy-prod

# Глобальные настройки кэша
default:
  cache:
    key: ${CI_COMMIT_REF_SLUG}
    paths:
      - .npm/
      - vendor/

# 1. Валидация (Fail-Fast)
lint_code:
  stage: validate
  script:
    - npm run lint
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

# 2. Тестирование
unit_tests:
  stage: test
  script:
    - npm test -- --coverage
  artifacts:
    reports:
      junit: report.xml
      coverage_report:
        coverage_format: cobertura
        path: coverage.xml

# 3. Сборка с DAG и OIDC
build_image:
  stage: build
  needs: ["unit_tests"] # DAG: запускается сразу после тестов
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.example.com
  script:
    - # Получение временных прав через OIDC в Vault
    - docker build -t $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA .
    - syft . -o cyclonedx-json=sbom.json
  artifacts:
    paths: [sbom.json]

# 4. Сканирование безопасности
security_scan:
  stage: security
  needs: ["build_image"]
  script:
    - trivy image --exit-code 1 $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA
    - trivy sbom sbom.json

# 5. Эфемерное окружение
deploy_review:
  stage: deploy-preview
  script:
    - helm upgrade --install review-$CI_COMMIT_REF_SLUG ./chart
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    on_stop: stop_review
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"

# 6. Прод (с ручным подтверждением)
deploy_prod:
  stage: deploy-prod
  when: manual
  script:
    - ./deploy.sh production $CI_COMMIT_SHORT_SHA
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

### Стратегии оптимизации пайплайна

1.  **Test Impact Analysis (TIA):** Запуск только тех тестов, которые затрагивают измененные файлы. Сокращает время `test` стадии на 50-80%.
2.  **Использование BuildKit:** Оптимизация сборки Docker-образов через кэширование слоев и параллельную сборку стадий Multi-stage.
3.  **Динамическая генерация пайплайнов:** Для монорепозиториев — создание конфигурации CI «на лету» только для измененных модулей.
4.  **Упреждающее кэширование:** Использование внешних S3-хранилищ для обмена кэшем между разными раннерами.
