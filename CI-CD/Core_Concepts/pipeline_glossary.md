# Глоссарий пайплайнов CI/CD

## Определения

- **Глоссарий пайплайнов** — справочный документ, содержащий определения ключевых элементов и терминов, используемых при построении конвейеров непрерывной интеграции и доставки ПО (**CI/CD — Continuous Integration / Continuous Delivery**).
- **Назначение** — стандартизация терминологии и предоставление быстрых ссылок на детальную документацию по каждому компоненту процесса автоматизации.
- **Контур применения** — материал описывает самостоятельно развёрнутые (self-hosted) CI/CD-системы: собственные раннеры (GitLab Runner, Jenkins, self-hosted GitHub Actions), внутренние реестры (Nexus, Artifactory, MinIO, Harbor) и локальные сети ЦОДа, без привязки к внешним провайдерам.

## Базовые компоненты

### Пайплайн (Pipeline) {#пайплайн-pipeline}
**Описание:** Автоматизированный процесс, описывающий жизненный цикл изменений кода от сборки до развертывания. Пайплайн объединяет триггеры, этапы, задачи и исполнителей в единый воспроизводимый поток, управляемый как код (Pipeline as Code). Современные пайплайны часто включают автоматические откаты, гейты качества и финансовые проверки.
**Подробнее:** **[CI/CD: Обзор](../ci_cd_overview.md)**, **[Типичный поток пайплайна](./pipeline_workflow.md)**, **[SDLC: Обзор](./sdlc_overview.md)**.

### Триггер (Trigger) {#триггер-trigger}
**Описание:** Событие, инициирующее автоматический запуск пайплайна.
**Примеры:** `push` в репозиторий, создание Merge Request, расписание (cron), вызов через API/Webhook.
```yaml
# GitLab CI: запуск по расписанию и при пуше в ветку main
nightly:
  rules:
    - if: $CI_PIPELINE_SOURCE == "schedule"
build_main:
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```
**Подробнее:** **[Основы GitLab CI](../GitLab_CI/Concepts/gitlab_ci_basics.md)**, **[Программная автоматизация (API/Webhook)](../GitLab_CI/Advanced/api_and_webhooks_automation.md)**.

### Исполнитель (Runner / Agent) {#исполнитель-runner-agent}
**Описание:** Изолированная среда (машина, контейнер, Pod в кластере оркестратора), выполняющая конкретные задачи пайплайна. Раннеры бывают общими (Shared) и специфичными для проекта (Specific), а также могут масштабироваться автоматически (autoscaling) или быть вытесняемыми (best-effort) для экономии ресурсов.
**Подробнее:** **[Обзор GitLab Runners и Executor](../GitLab_CI/Advanced/gitlab_ci_runners_executors.md)**, **[Управление парком раннеров](../runner-fleet-management.md)**.

### Этап (Stage) {#этап-stage}
**Описание:** Логическая группа задач, выполняемых на определённой фазе жизненного цикла (например, `build`, `test`, `security`, `deploy`). Стадии определяют последовательность: задачи одной стадии запускаются параллельно, а следующая стадия начинается только после успеха предыдущей (если не используется DAG).
**Подробнее:** **[Типовые стадии пайплайна](../GitLab_CI/Concepts/gitlab_ci_basics.md#типовые-стадии-пайплайна)**.

### Задача (Job / Step) {#задача-job-step}
**Описание:** Минимальная единица работы в пайплайне — конкретный скрипт или команда, выполняемая исполнителем в изолированном контексте. Задача имеет код возврата (exit code): 0 — успех, ненулевой — ошибка (триггерит retry или падение пайплайна).
**Подробнее:** **[Ключевые слова для управления пайплайном](../GitLab_CI/Concepts/gitlab_ci_basics.md#ключевые-слова-для-управления-пайплайном)**.

### Пайплайн как код (Pipeline as Code) {#pipeline-as-code}
**Описание:** Практика хранения описания пайплайна в файле репозитория (`.gitlab-ci.yml`, `Jenkinsfile`, `GitHub Actions workflow`), что обеспечивает версионирование, code review и воспроизводимость конфигурации CI/CD наравне с приложением.

### Декларативный пайплайн (Declarative Pipeline) {#декларативный-pipeline}
**Описание:** Подход к описанию CI/CD-конвейера, при котором указывается *желаемое состояние* (что должно произойти: этапы, условия, артефакты), а не последовательность программных инструкций. Декларативный пайплайн имеет предопределённую схему, встроенную валидацию и ограничивает свободу действий runtime, что повышает безопасность и предсказуемость. Примеры: `.gitlab-ci.yml`, GitHub Actions workflows, Jenkins Declarative Pipeline.

### Скриптовый пайплайн (Scripted Pipeline) {#скриптовый-pipeline}
**Описание:** Подход к описанию CI/CD-конвейера, при котором пайплайн представляет собой последовательность программных инструкций (procedural code) с возможностью циклов, условного ветвления, вызова внешних методов и динамической генерации этапов. Требует от автора знания языка runtime (Groovy для Jenkins, Python/Bash для кастомных скриптов) и несёт риск недетерминированного поведения. Пример: Jenkins Scripted Pipeline, кастомные CI-скрипты на Python.

### Сравнение подходов

| Характеристика | Декларативный | Скриптовый |
| :--- | :--- | :--- |
| **Фокус** | Желаемое состояние (что) | Процесс (как) |
| **Читаемость** | Высокая: единая структура секций | Средняя: зависит от стиля автора |
| **Валидация** | На этапе парсинга (schema validation) | Только при выполнении |
| **Гибкость** | Ограничена predefined-директивами | Неограниченная: циклы, условия, вызовы методов |
| **Безопасность** | Встроенные ограничения (Script Security) | Требует approve-механизмов для небезопасных методов |
| **Поддерживаемость** | Проще онбординг и аудит | Требует экспертизы в языке runtime |
| **Динамика** | Ограничена (требует `script`-блоков или плагинов) | Полная: генерация stages/параметров в runtime |
| **Инструменты** | GitLab CI, GitHub Actions, Jenkins Declarative | Jenkins Scripted, кастомные CI-скрипты |

### Рекомендации по выбору

1.  **По умолчанию** используйте декларативный синтаксис — он обеспечивает предсказуемость, безопасность и единый стандарт для команды.
2.  **Скриптовый пайплайн** применяйте только для сценариев, где декларативный подход не позволяет выразить логику без загромождения конфигурации `script`-блоками: динамическая генерация этапов, сложная оркестрация, интеграция с внешними API в цикле.
3.  **Не смешивайте** подходы в одном файле конфигурации.
4.  **Выносите** сложную логику в переиспользуемые компоненты (GitLab CI Components, GitHub Reusable Workflows, Jenkins Shared Libraries), чтобы декларативный пайплайн оставался декларативным.

### Параллелизм и ограничения (Concurrency / Quotas) {#concurrency}
**Описание:** Механизмы ограничения одновременно выполняемых пайплайнов/задач (concurrency) и потребления ресурсов (quotas/limits) для предотвращения монополизации пула раннеров и эффекта «шумного соседа».
```yaml
deploy_prod:
  stage: deploy
  concurrency: production   # только один пайплайн в production одновременно
```

### Повторные попытки и таймауты (Retry / Timeout) {#retry-timeout}
**Описание:** Политика автоматического перезапуска упавшей задачи (retry) при транзиторных сбоях и ограничение максимального времени выполнения (timeout), защищающее от зависших задач, занимающих раннер впустую.
```yaml
test:
  retry: 2
  timeout: 10 minutes
```

## Управление данными и артефактами

### Артефакт (Artifact) {#артефакт-artifact}
**Описание:** Результат выполнения задачи (бинарные файлы, отчёты о тестах, образы), сохраняемый для передачи между этапами или для последующего скачивания. В отличие от кэша, артефакт гарантированно сохраняется и версионируется.
**Подробнее:** **[Управление артефактами](../artifact_management.md)**.

### Кэш (Cache) {#кэш-cache}
**Описание:** Временное хранилище (например, `node_modules`, `.m2/repository`) для ускорения повторных запусков пайплайна. В отличие от артефактов, сохранность кэша не гарантируется. Эффективность кэширования измеряется метрикой Cache Hit Rate.
**Пример:** ключ кэша по ветке и хешу lock-файла — инвалидируется при смене зависимостей:
```yaml
cache:
  key: ${CI_COMMIT_REF_SLUG}-${CI_PROJECT_ID}
  paths:
    - node_modules/
```
**Подробнее:** **[Кэширование в CI](../GitLab_CI/Advanced/gitlab_ci_caching/caching_overview.md)**.

### Реестр образов (Container Registry / OCI Registry) {#реестр-образов}
**Описание:** Хранилище для OCI-совместимых артефактов (контейнерные образы, Helm-чарты, SBOM). Современные реестры поддерживают версионирование, подпись образов и политики очистки (retention).
**Подробнее:** **[Docker Registry](../../Docker/docker_registries.md)**.

### Программный счёт материалов (SBOM) {#sbom}
**Описание:** Декларативный список всех компонентов, библиотек и зависимостей артефакта. Генерируется автоматически на этапе сборки и используется для анализа уязвимостей и лицензий. Непрерывно обновляемый SBOM (Living SBOM) позволяет отслеживать изменения состава по мере выпуска новых версий зависимостей.
**Подробнее:** **[DevSecOps: Обзор](../DevSecOps/devsecops_overview.md)**.

### Происхождение и аттестация (Provenance / Attestation) {#provenance}
**Описание:** Криптографически подписанные метаданные о том, как, где и из какого исходного кода был собран артефакт. Аттестации подтверждают прохождение проверок (тесты, сканирование) и лежат в основе цепочки поставок (см. SLSA).

### Неизменяемый артефакт (Immutable Artifact) {#immutable-artifact}
**Описание:** Артефакт, который собирается один раз и не изменяется при продвижении между окружениями (promotion). Это гарантирует, что в production попадает именно то, что тестировалось, и упрощает откат (rollback).

### Воспроизводимая сборка (Reproducible Build) {#reproducible-build}
**Описание:** Сборка, при которой одинаковый исходный код и окружение всегда дают бит-в-бит идентичный артефакт (детерминизм версий, отсутствие временных меток и абсолютных путей). Основа доверия к поставке и верификации provenance.

## Окружения и доставка

### Среда / Окружение (Environment) {#среда-environment}
**Описание:** Инфраструктурный контекст, где развертывается и работает приложение (например, `development`, `staging`, `production`).
**Подробнее:** **[Окружения в GitLab CI](../GitLab_CI/Concepts/environments_and_deployments.md)**.

### Эфемерные окружения (Ephemeral / Dynamic Environments) {#dynamic-environments}
**Описание:** Временные изолированные среды, создаваемые «на лету» под каждый Merge Request. Позволяют проводить ручное ревью или сквозное тестирование в изоляции от других веток. Критичны для экономии ресурсов при наличии TTL и автоостановки (см. **[Оптимизацию затрат](./cost-optimization.md)**).

### Продвижение по средам (Promotion) {#promotion}
**Описание:** Процесс переноса проверенного неизменяемого артефакта из одной среды в следующую (dev → staging → prod) без пересборки, что снижает риск расхождения версий.

### Стратегии развёртывания (Deployment Strategies) {#deployment-strategies}
**Описание:** Способы обновления работающего сервиса с минимизацией простоя и риска:
- **Rolling Update** — постепенная замена старых инстансов новыми без остановки сервиса.
- **Blue-Green** — две идентичные среды; трафик мгновенно переключается с Blue (старая) на Green (новая), что даёт мгновенный откат.
- **Canary** — новая версия сначала получает малую долю трафика (например, 10%), и при нормальных SLO постепенно расширяется на 100%.
```yaml
# Canary: поднимаем новую версию параллельно и мониторим SLO
canary:
  stage: deploy
  script:
    - docker compose -f docker-compose.canary.yml up -d   # 10% трафика у балансировщика
rollback:
  stage: deploy
  when: on_failure
  script:
    - docker compose -f docker-compose.prod.yml up -d     # возврат к стабильной версии
```

### Откат (Rollback) {#rollback}
**Описание:** Возврат системы к предыдущей стабильной версии артефакта/конфигурации при обнаружении инцидента после деплоя. Эффективен при неизменяемых артефактах и наличии метрик (SLO) для автоматического триггера.

### GitOps {#gitops}
**Описание:** Методология непрерывного развертывания, где Git является единственным источником истины для состояния инфраструктуры. Оператор внутри кластера (Pull Model) обеспечивает синхронизацию между Git и реальной средой.
**Подробнее:** **[GitOps: Обзор](../../GitOps/GitOps_overview.md)**.

### Самосогласование (Self-healing / Reconciliation) {#self-healing}
**Описание:** Процесс автоматического устранения расхождений (Configuration Drift) между желаемым состоянием (в Git) и фактическим состоянием системы. См. также **Дрейф конфигурации**.

### Обнаружение дрейфа (Drift Detection) {#drift-detection}
**Описание:** Регулярная проверка, что фактическая инфраструктура соответствует описанной в коде (IaC). Расхождения (drift) сигнализируют о ручных изменениях в обход пайплайна и требуют приведения к эталону (reconciliation).

### Внутренняя платформа разработчика (Internal Developer Platform, IDP) {#idp}
**Описание:** Набор инструментов и технологий, собранных платформенной командой (**Platform Engineering**) для создания «золотых путей» (Golden Paths). IDP позволяет разработчикам самостоятельно разворачивать ресурсы и пайплайны, не погружаясь в детали реализации инфраструктуры.
**Подробнее:** **[Эволюция Platform Engineering](../../Concepts/devops_overview.md#эволюция-platform-engineering)**.

## Безопасность и конфигурация

### Управление секретами (Secrets Management) {#secrets-management}
**Описание:** Процесс безопасного хранения и передачи чувствительных данных (пароли, ключи API) в задачи пайплайна. Секреты не должны попадать в логи и должны иметь минимально необходимые права (least privilege).
**Подробнее:** **[Управление секретами в CI/CD](../DevSecOps/secrets_management.md)**.

### OIDC (OpenID Connect) {#oidc}
**Описание:** Метод беспарольной аутентификации пайплайна во внешних системах (например, HashiCorp Vault, провайдеры идентификации) через получение временных токенов на основе установленного доверия (trust) между CI-платформой и целевой системой. Исключает долгоживущие статические креды.
```yaml
# GitLab CI: получение токена Vault через OIDC (self-hosted)
vault_read:
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.internal
  script:
    - export TOKEN=$(vault write -field=token auth/jwt/login role=ci jwt=$VAULT_ID_TOKEN)
```

### SLSA (Supply-chain Levels for Software Artifacts) {#slsa}
**Описание:** Фреймворк и набор стандартов для обеспечения целостности артефактов и защиты всей цепочки поставок ПО от коммита до продакшена. Определяет уровни (L0–L3) гарантий происхождения (provenance).

### VEX (Vulnerability Exploitability eXchange) {#vex}
**Описание:** Стандарт обмена данными, позволяющий уточнить, является ли обнаруженная уязвимость реально эксплуатируемой в конкретной конфигурации приложения, что радикально снижает шум в отчетах безопасности.

## Оптимизация и качество

### Ворота качества (Quality Gate) {#quality-gate}
**Описание:** Автоматизированная точка контроля в пайплайне, блокирующая его выполнение при несоблюдении критериев (например, Coverage < 80% или наличие критических уязвимостей).
```yaml
test:
  stage: test
  script:
    - pytest --cov=app --cov-fail-under=80   # пайплайн упадёт при покрытии < 80%
```

### Направленный ациклический граф (Directed Acyclic Graph, DAG) {#dag}
**Описание:** Способ организации зависимостей между задачами, позволяющий запускать Job сразу после завершения её предшественников, не дожидаясь окончания всей стадии (Stage). Используется для ускорения пайплайнов.
```yaml
build:   { stage: build,  script: [make build] }
test_unit: { stage: test, needs: [build], script: [make unit] }
test_e2e: { stage: test, needs: [build], script: [make e2e] }
deploy:  { stage: deploy, needs: [test_unit, test_e2e] }
```
**Подробнее:** **[Оптимизация пайплайнов](./pipeline_workflow.md#реализация-оптимизированного-пайплайна)**.

### Метрики DORA {#dora}
**Описание:** Ключевые показатели эффективности (Deployment Frequency, Lead Time for Changes, Change Failure Rate, Time to Restore Service), позволяющие оценить зрелость DevOps-процессов.
**Подробнее:** **[Метрики DORA](./dora_metrics.md)**.

### SRE-метрики: SLO / SLI / Error Budget {#slo-sli}
**Описание:** Подходы SRE к надёжности:
- **SLI (Service Level Indicator)** — измеряемая метрика (например, доля успешных запросов).
- **SLO (Service Level Objective)** — целевое значение SLI (например, 99.9% успешных запросов за 30 дней).
- **Error Budget** — допустимая доля нарушений SLO; при её исчерпании деплои замораживаются в пользу стабилизации.
Применяется в пайплайне для автоматического разрешения canary-релизов и триггера отката.

### Финансовые ворота (FinOps Gate) {#finops-gate}
**Описание:** Автоматическая проверка стоимости изменений (инфраструктуры/окружений) на этапе CI. Блокирует продвижение, если планируемые затраты превышают установленный лимит (см. **[Оптимизацию затрат](./cost-optimization.md)**).

### Наблюдаемость пайплайнов (Pipeline Observability) {#pipeline-observability}
**Описание:** Применение инструментов мониторинга (OpenTelemetry, eBPF, Prometheus) к самим процессам CI/CD для выявления узких мест, «мигающих» (flaky) тестов и анализа критического пути в DAG.
```yaml
# Пример: экспорт длительности задачи как метрики через otel-cli
report:
  stage: report
  script:
    - otel-cli span --service ci --name job-duration --duration $(measure)
```
**Подробнее:** **[Наблюдаемость пайплайнов](./pipeline_observability.md)**.

## Практические сценарии

### Жизненный цикл изменений в пайплайне

1.  **Событие в Git** (коммит или MR) инициирует **Триггер**.
2.  **Пайплайн** стартует и при необходимости запрашивает временные доступы через **OIDC** (например, к Vault).
3.  **Исполнители** (Runners) запускают задачи, используя **Кэш** для ускорения сборки.
4.  На этапе сборки генерируется **SBOM** и **Provenance/Attestation** (уровень SLSA).
5.  Прохождение **Quality Gates** (тесты, покрытие, безопасность VEX) и **FinOps Gates** (анализ стоимости).
6.  Успешный **Артефакт** пушится в **OCI Registry** как неизменяемый образ.
7.  Через **Promotion**/GitOps-оператор (ArgoCD/Flux) выполняется **Reconciliation**, развёртывая код в целевую **Среду** по стратегии (rolling/canary).
8.  **Pipeline Observability** и **SRE-метрики (SLO/Error Budget)** собирают телеметрию для анализа эффективности потока и принятия решения об откате.

### Пример: Canary-релиз с автоматическим откатом (SRE/SysAdmin)

```yaml
deploy_canary:
  stage: deploy
  script:
    - docker compose -f docker-compose.canary.yml up -d
    # мониторинг SLO в течение 10 мин; если Error Budget исчерпан — откат
  environment:
    name: production-canary

verify_slo:
  stage: verify
  needs: [deploy_canary]
  script:
    - check-slo --window 10m --threshold 99.9   # падает при нарушении SLO

promote:
  stage: deploy
  needs: [verify_slo]
  when: on_success
  script:
    - docker compose -f docker-compose.prod.yml up -d   # расширяем canary до 100%

rollback:
  stage: deploy
  when: on_failure
  script:
    - docker compose -f docker-compose.prod.yml up -d   # возврат к стабильной версии
```

### Пример: эфемерное окружение с TTL (DevOps)

```yaml
review_env:
  stage: deploy
  script:
    - docker compose -f docker-compose.review.yml -p "review-$CI_COMMIT_REF_SLUG" up -d
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    on_stop: stop_review
    auto_stop_in: 1 day          # автоудаление через 24ч (экономия ресурсов)

stop_review:
  stage: cleanup
  script:
    - docker compose -f docker-compose.review.yml -p "review-$CI_COMMIT_REF_SLUG" down -v
  when: manual
  environment:
    name: review/$CI_COMMIT_REF_SLUG
    action: stop
```

### Пример: безопасная передача секретов через OIDC (DevSecOps/SysAdmin)

```yaml
fetch_secret:
  id_tokens:
    VAULT_ID_TOKEN:
      aud: https://vault.internal
  script:
    - export TOKEN=$(vault write -field=token auth/jwt/login role=ci jwt=$VAULT_ID_TOKEN)
    - export DB_PASSWORD=$(vault read -field=password secret/ci/db)
    # секрет используется только в рантайме задачи, не пишется в логи
```
