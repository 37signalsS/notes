# Глоссарий пайплайнов CI/CD

## Определения

- **Глоссарий пайплайнов** — справочный документ, содержащий определения ключевых элементов и терминов, используемых при построении конвейеров непрерывной интеграции и доставки ПО (**CI/CD — Continuous Integration / Continuous Delivery**).

- **Назначение** — стандартизация терминологии и предоставление быстрых ссылок на детальную документацию по каждому компоненту процесса автоматизации.

## Основные концепции

### Пайплайн (Pipeline) {#пайплайн-pipeline}
**Описание:** Автоматизированный процесс, описывающий жизненный цикл изменений кода от сборки до развертывания. Состоит из последовательности этапов (Stages) и задач (Jobs).
**Подробнее:** **[CI/CD: Обзор](../ci_cd_overview.md)**, **[Типичный поток пайплайна](./pipeline_workflow.md)**.

### Триггер (Trigger) {#триггер-trigger}
**Описание:** Событие, инициирующее автоматический запуск пайплайна.
**Примеры:** `push` в репозиторий, создание Merge Request, расписание (cron) или вызов через API/Webhook.
**Подробнее:** **[Управление потоком выполнения в GitLab CI](../GitLab_CI/Concepts/gitlab_ci_basics.md#управление-потоком-выполнения)**.

### Исполнитель (Runner / Agent) {#исполнитель-runner-agent}
**Описание:** Изолированная среда (машина, контейнер, Pod), выполняющая задачи пайплайна.
**Подробнее:** **[Обзор GitLab Runners](../GitLab_CI/Advanced/gitlab_ci_runners_executors.md)**.

### Этап (Stage) {#этап-stage}
**Описание:** Логическая группа задач, выполняемых на определенной фазе жизненного цикла (например, `build`, `test`, `deploy`). Этапы обычно выполняются последовательно.
**Подробнее:** **[Стадии пайплайна](../GitLab_CI/Concepts/gitlab_ci_basics.md#типовые-стадии-пайплайна-lifecycle)**.

### Задача (Job / Step) {#задача-job-step}
**Описание:** Минимальная единица работы — конкретный скрипт или команда, выполняемая исполнителем.
**Подробнее:** **[Ключевые слова для задач](../GitLab_CI/Concepts/gitlab_ci_basics.md#ключевые-слова-для-задач)**.

### Артефакт (Artifact) {#артефакт-artifact}
**Описание:** Результат выполнения задачи (бинарные файлы, отчеты, образы), который сохраняется и может передаваться между этапами.
**Подробнее:** **[Управление артефактами](../artifact_management.md)**.

### Кэш (Cache) {#кэш-cache}
**Описание:** Временное хранилище файлов (например, `node_modules`, `.m2`) для ускорения повторных запусков пайплайна. Сохранность кэша не гарантируется (в отличие от артефактов).
**Подробнее:** **[Кэширование в CI](../GitLab_CI/Advanced/gitlab_ci_caching/caching_overview.md)**.

### Среда / Окружение (Environment) {#среда-environment}
**Описание:** Инфраструктурное окружение, в котором развертывается приложение (например, `dev`, `staging`, `production`).
**Подробнее:** **[Окружения в GitLab CI](../GitLab_CI/Concepts/environments_and_deployments.md)**.

### Переменные (Variables) {#переменные-variables}
**Описание:** Параметры конфигурации (ключ-значение), используемые для настройки поведения пайплайна без изменения кода. Могут быть предопределенными (CI_COMMIT_SHA) или пользовательскими.
**Подробнее:** **[Переменные в GitLab CI](../GitLab_CI/Concepts/gitlab_ci_variables_secrets.md)**.

### Управление секретами (Secrets Management) {#управление-секретами-management}
**Описание:** Безопасное хранение и передача чувствительных данных (паролей, токенов) в задачи пайплайна.
**Подробнее:** **[Управление секретами в CI/CD](../DevSecOps/secrets_management.md)**.

### Реестр образов (Container Registry) {#реестр-образов}
**Описание:** Хранилище для скомпилированных артефактов в виде контейнерных образов (например, Docker Registry).
**Подробнее:** **[Docker Registry](../../Docker/Docker_registries/docker_registries_overview.md)**.

### Ворота качества (Quality Gate) {#quality-gate}
**Описание:** Условие или порог метрик (например, покрытие тестами >80%, отсутствие критических уязвимостей), которые пайплайн должен пройти для перехода к следующему этапу.
**Подробнее:** **[DORA метрики](./dora_metrics.md)**.

### Параллелизм и DAG (Directed Acyclic Graph) {#dag}
**Описание:** Способы оптимизации пайплайна: запуск независимых задач одновременно (Parallelism) или настройка явных зависимостей между задачами (Needs/DAG) для обхода последовательного выполнения этапов.
**Подробнее:** **[Оптимизация пайплайнов](./pipeline_workflow.md#принципы-построения-пайплайна)**.

## Практические сценарии

### Жизненный цикл изменений в пайплайне

Взаимосвязь компонентов в типичном потоке:

1. **Триггер** (событие в Git) создает экземпляр **пайплайна**.
2. **Пайплайн** считывает **переменные** и **секреты** для конфигурации.
3. Код проходит через **этапы** (`build`, `test`, `scan`).
4. **Задачи** внутри этапов забирают **кэш** для скорости и отдают **артефакты** по завершении.
5. На каждом этапе срабатывают **Quality Gates**.
6. Если проверки успешны, артефакт (например, Docker-образ) пушится в **Registry**.
7. Финальная задача развертывает артефакт в целевую **среду** (Environment).
