# Глоссарий пайплайнов CI/CD

## Определения

- **Глоссарий пайплайнов** — справочный документ, содержащий определения ключевых элементов и терминов, используемых при построении конвейеров непрерывной интеграции и доставки ПО (**CI/CD — Continuous Integration / Continuous Delivery**).

- **Назначение** — стандартизация терминологии и предоставление быстрых ссылок на детальную документацию по каждому компоненту процесса автоматизации.

## Базовые компоненты

### Пайплайн (Pipeline) {#пайплайн-pipeline}
**Описание:** Автоматизированный процесс, описывающий жизненный цикл изменений кода от сборки до развертывания. В 2026 году пайплайны часто управляются через **Agentic Orchestration** (AI-агенты).
**Подробнее:** **[CI/CD: Обзор](../ci_cd_overview.md)**, **[Типичный поток пайплайна](./pipeline_workflow.md)**.

### Триггер (Trigger) {#триггер-trigger}
**Описание:** Событие, инициирующее автоматический запуск пайплайна.
**Примеры:** `push` в репозиторий, создание Merge Request, расписание (cron), вызов через API/Webhook или событие в AI-агенте.
**Подробнее:** **[Основы GitLab CI](../GitLab_CI/Concepts/gitlab_ci_basics.md)**.

### Исполнитель (Runner / Agent) {#исполнитель-runner-agent}
**Описание:** Изолированная среда (машина, контейнер, Pod), выполняющая задачи пайплайна.
**Подробнее:** **[Обзор GitLab Runners](../GitLab_CI/Advanced/gitlab_ci_runners_executors.md)**.

### Этап (Stage) {#этап-stage}
**Описание:** Логическая группа задач, выполняемых на определенной фазе жизненного цикла (например, `build`, `test`, `deploy`).
**Подробнее:** **[Типовые стадии пайплайна](../GitLab_CI/Concepts/gitlab_ci_basics.md#типовые-стадии-пайплайна)**.

### Задача (Job / Step) {#задача-job-step}
**Описание:** Минимальная единица работы — конкретный скрипт или команда, выполняемая исполнителем.
**Подробнее:** **[Ключевые слова для управления пайплайном](../GitLab_CI/Concepts/gitlab_ci_basics.md#ключевые-слова-для-управления-пайплайном)**.

## Управление данными и артефактами

### Артефакт (Artifact) {#артефакт-artifact}
**Описание:** Результат выполнения задачи (бинарные файлы, отчеты, образы), сохраняемый для передачи между этапами.
**Подробнее:** **[Управление артефактами](../artifact_management.md)**.

### Кэш (Cache) {#кэш-cache}
**Описание:** Временное хранилище (например, `node_modules`) для ускорения повторных запусков. Сохранность не гарантируется.
**Подробнее:** **[Кэширование в CI](../GitLab_CI/Advanced/gitlab_ci_caching/caching_overview.md)**.

### Реестр образов (Container Registry) {#реестр-образов}
**Описание:** OCI-совместимое хранилище для контейнерных образов.
**Подробнее:** **[Docker Registry](../../Docker/Docker_registries/docker_registries_overview.md)**.

### Программный счет материалов (SBOM) {#sbom}
**Описание:** Декларативный список всех компонентов и зависимостей артефакта. В 2026 году используется **Living SBOM** для анализа уязвимостей в реальном времени.
**Подробнее:** **[DevSecOps: Обзор](../DevSecOps/devsecops_overview.md)**.

## Окружения и доставка

### Среда / Окружение (Environment) {#среда-environment}
**Описание:** Инфраструктура, где развертывается приложение (например, `dev`, `staging`, `prod`).
**Подробнее:** **[Окружения в GitLab CI](../GitLab_CI/Concepts/environments_and_deployments.md)**.

### Динамические окружения (Ephemeral / Dynamic Environments) {#dynamic-environments}
**Описание:** Временные изолированные среды, создаваемые автоматически под каждый Merge Request для ручного или E2E тестирования.

### GitOps {#gitops}
**Описание:** Методология CD, где Git — единственный источник истины, а агент внутри кластера (Pull Model) обеспечивает соответствие фактического состояния желаемому.
**Подробнее:** **[GitOps: Обзор](../../GitOps/GitOps_overview.md)**.

### Самосогласование (Self-healing / Reconciliation) {#self-healing}
**Описание:** Процесс автоматического устранения дрейфа конфигурации (configuration drift) между Git и реальной средой.

## Безопасность и конфигурация

### Управление секретами (Secrets Management) {#secrets-management}
**Описание:** Безопасное хранение чувствительных данных.
**Подробнее:** **[Управление секретами в CI/CD](../DevSecOps/secrets_management.md)**.

### OIDC (OpenID Connect) {#oidc}
**Описание:** Современный метод аутентификации пайплайна в облачных провайдерах (AWS, GCP, Vault) без использования долгоживущих статических токенов.

### SLSA (Supply-chain Levels for Software Artifacts) {#slsa}
**Описание:** Фреймворк для обеспечения целостности артефактов и защиты цепочки поставок ПО.

### VEX (Vulnerability Exploitability eXchange) {#vex}
**Описание:** Стандарт обмена данными о том, эксплуатируема ли конкретная уязвимость в данном контексте, что снижает количество ложных срабатываний безопасности.

## Оптимизация и качество

### Ворота качества (Quality Gate) {#quality-gate}
**Описание:** Автоматизированная точка контроля (порог покрытия тестами, отсутствие критических уязвимостей), блокирующая продвижение пайплайна.

### Параллелизм и DAG (Directed Acyclic Graph) {#dag}
**Описание:** Оптимизация через одновременный запуск задач или настройку явных зависимостей (`needs`) для обхода жесткой последовательности этапов.
**Подробнее:** **[Оптимизация пайплайнов](./pipeline_workflow.md#принципы-построения-пайплайна)**.

### Метрики DORA {#dora}
**Описание:** Отраслевой стандарт оценки эффективности: Lead Time, Deployment Frequency, Change Failure Rate, Time to Restore.
**Подробнее:** **[Метрики DORA](./dora_metrics.md)**.

### Финансовые ворота (FinOps Gate) {#finops-gate}
**Описание:** Автоматическая оценка стоимости изменений инфраструктуры (IaC) до их слияния в основную ветку.

## Практические сценарии

### Жизненный цикл изменений в пайплайне

1. **Триггер** (событие в Git) создает **пайплайн**.
2. **Пайплайн** запрашивает временные токены через **OIDC**.
3. Код проходит через **этапы** (`build`, `test`, `scan`).
4. **Задачи** используют **кэш** и генерируют **артефакты** (включая **SBOM**).
5. На каждом этапе срабатывают **Quality Gates** и **FinOps Gates**.
6. Успешный артефакт пушится в **Registry** с аттестацией **SLSA**.
7. **GitOps-оператор** обнаруживает изменение и обновляет целевую **среду**, выполняя **Self-healing**.
