# Обзор: Стадии и Стратегии Развертывания в CI/CD

Этот документ представляет собой сводку по различным стадиям и стратегиям развертывания (деплоя), используемым в современных CI/CD пайплайнах.

## Стадии развертывания (Deployment Stages)

Процесс развертывания — это не один этап, а, как правило, последовательность из нескольких стадий в CI/CD пайплайне. Вот типичная структура:

### 1. `deploy` (Развертывание)
*   **Цель:** Непосредственная выкатка новой версии приложения в целевое окружение (`development`, `staging`, `production`).
*   **Действия:** На этом этапе выполняются команды `helm upgrade`, `kubectl apply`, `ansible-playbook` или `ssh` для доставки артефакта (например, Docker-образа) на сервер или в кластер.
*   **Источник:** [Проектирование комплексного CI/CD пайплайна](./ci_cd_practical_guide_overview.md)

### 2. `validate_deployment` (Валидация развертывания)
*   **Цель:** Убедиться, что только что развернутое приложение работает корректно.
*   **Действия:** Запуск smoke-тестов (проверка доступности основных эндпоинтов) или E2E-тестов для проверки ключевых пользовательских сценариев. Если этот этап проваливается, это сигнал для запуска отката.
*   **Источник:** [Проектирование комплексного CI/CD пайплайна](./ci_cd_practical_guide_overview.md)

### 3. `release` (Создание релиза)
*   **Цель:** Формализация выпуска новой версии.
*   **Действия:** Обычно запускается вручную. Создание Git-тега, генерация Changelog, публикация релиза в интерфейсе GitLab.
*   **Источник:** [Практическое руководство: Использование GitLab Flow](./gitlab_flow_tutorial.md)

### 4. `rollback` (Откат)
*   **Цель:** Быстрое возвращение к предыдущей стабильной версии в случае сбоя.
*   **Действия:** Эта задача чаще всего запускается вручную. GitLab имеет встроенный механизм отката, который просто перезапускает предыдущую успешную задачу развертывания. Также можно реализовать явную задачу, например, с помощью `helm rollback`.
*   **Источник:** [Управление окружениями и откат изменений в GitLab CI](./gitlab_ci_environments_and_rollbacks.md)

## Варианты (Стратегии) развертывания

Существует несколько фундаментально разных подходов к организации развертывания.

### 1. Императивная "Push" модель (Прямое развертывание)

CI/CD пайплайн напрямую подключается к серверам и отдает им команды, что и как делать.

*   **С помощью SSH:** Самый простой способ. Пайплайн подключается к серверу и выполняет заранее написанный скрипт (например, `docker pull`, `docker run`).
    *   **Источник:** [Руководство по развертыванию Full Stack](./gitlab_ci_cd_full_stack_deployment_guide.md)
*   **С помощью Ansible:** Более структурированный подход. Пайплайн запускает `ansible-playbook`, который декларативно описывает состояние сервера. Ansible берет на себя всю логику по настройке и развертыванию.
    *   **Источник:** [Использование Ansible в GitLab CI/CD](./ansible_with_gitlab_ci.md)

### 2. Декларативная "Push" модель (Развертывание в Kubernetes)

CI/CD пайплайн по-прежнему "проталкивает" (push) изменения, но делает это декларативно, описывая *желаемое состояние* в Kubernetes.

*   **С помощью `kubectl`:** Пайплайн выполняет `kubectl apply -f <manifests.yml>`, применяя манифесты Kubernetes, которые хранятся в репозитории.
*   **С помощью Helm:** Наиболее популярный метод. Пайплайн использует команду `helm upgrade --install` для управления релизами. Это позволяет использовать шаблоны, управлять зависимостями и версиями.
    *   **Недостатки "Push" модели:** Основная проблема — **рассинхронизация состояния (state drift)**, когда реальное состояние кластера со временем начинает отличаться от того, что описано в Git (например, из-за ручных исправлений).
    *   **Источники:** [Стратегии интеграции GitLab CI с Kubernetes](./gitlab_kubernetes_integration_strategies.md), [Развертывание в Kubernetes с помощью GitLab CI и Helm](./gitlab_ci_kubernetes_helm_deploy.md)

### 3. Декларативная "Pull" модель (GitOps)

Самый современный и безопасный подход, решающий проблемы "Push" модели.

*   **Принцип:** Git-репозиторий — **единственный источник правды**. CI/CD пайплайн **не имеет прямого доступа к кластеру**. Его задача — только собрать Docker-образ и обновить YAML-манифест в репозитории конфигурации.
*   **Механизм:** Внутри Kubernetes работает специальный агент (например, **ArgoCD**), который постоянно следит за Git-репозиторием. Обнаружив расхождение между Git и кластером, он "притягивает" (pull) изменения и приводит кластер в соответствие.
*   **Преимущества:**
    *   Безопасность: У CI/CD нет критически важных доступов.
    *   Надежность: Исключается рассинхронизация состояния.
    *   Простота отката: Достаточно сделать `git revert` в репозитории конфигурации.
*   **Источники:** [Стратегии интеграции GitLab CI с Kubernetes](./gitlab_kubernetes_integration_strategies.md), [GitOps и ArgoCD](../../GitOps/ArgoCD.md)

### 4. Встроенная интеграция GitLab-Kubernetes (Не рекомендуется)

*   **Описание:** Исторически первый подход, который GitLab предлагал "из коробки". Позволяет автоматически создавать окружения, разворачивать приложения и т.д.
*   **Почему не рекомендуется:** Требует полных прав администратора (`cluster-admin`) в кластере, что небезопасно. Механизм может быть хрупким и конфликтовать с другими инструментами управления кластером.
*   **Источник:** [Стратегии интеграции GitLab CI с Kubernetes](./gitlab_kubernetes_integration_strategies.md)
