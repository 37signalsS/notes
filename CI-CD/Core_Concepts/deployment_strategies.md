# Стратегии и модели развертывания

## Определения

- **Модель развертывания (Deployment Model)** — архитектурный подход, определяющий способ доставки изменений в целевую среду. Ключевое различие заключается в управлении потоком команд: **Push** (активное проталкивание из CI) или **Pull** (автономное притягивание агентом).

- **Стратегия развертывания (Rollout Strategy)** — технический метод обновления работающего приложения (например, Blue/Green, Canary). Определяет, как происходит замена старой версии (v1) на новую (v2) с точки зрения трафика и ресурсов.

- **Развертывание (Deployment) vs Выпуск (Release)** — разделение процесса на техническую доставку кода (Deployment) и открытие доступа пользователям к новому функционалу (Release).

- **Progressive Delivery (Прогрессивная поставка)** — развитие идей CI/CD, подразумевающее постепенную раскатку функционала с использованием инструментов управления трафиком и **Feature Flags**.

- **State Drift (Рассинхронизация состояния)** — расхождение между желаемым состоянием системы (описанным в Git) и реальным состоянием в кластере, возникшее из-за ручных правок или сбоев.

## Основные концепции

### Модели развертывания: Push vs Pull

#### Push-модель (Императивная и Декларативная)
CI-пайплайн инициирует соединение с целевой средой.
- **Императивная:** Прямое выполнение команд через **[SSH](../../Linux/Security/ssh/ssh_overview.md)** или API. Инструмент: **[Ansible](../../Ansible/ansible_introduction.md)**.
- **Декларативная:** CI отправляет манифесты в оркестратор (`kubectl apply`). Инструмент: **[Helm](../../Kubernetes/ToolsUtilities/Helm/helm_overview.md)**.
- **Риски:** Требует хранения секретов (ключей доступа) внутри CI-системы; сложность борьбы со State Drift.

#### Pull-модель (GitOps)
Агент внутри кластера отслеживает изменения в Git-репозитории и приводит систему к нужному состоянию.
- **Инструменты:** **[ArgoCD](../../GitOps/ArgoCD/argocd_overview.md)**, **[Flux](../../GitOps/flux.md)**.
- **Преимущества:** Высокая безопасность (кластер не "светит" API наружу), автоматическое устранение State Drift.
- **Подробнее:** **[Обзор GitOps](../../GitOps/GitOps_overview.md)**.

### Стратегии развертывания

| Стратегия | Принцип работы | Риск простоя | Сложность |
| :--- | :--- | :--- | :--- |
| **Recreate** | Удаление v1 → запуск v2. | Высокий | Низкая |
| **Rolling Update** | Поэтапная замена экземпляров v1 на v2. | Нет | Средняя |
| **Blue/Green** | Полный запуск v2 рядом с v1 → переключение трафика. | Нет | Высокая |
| **Canary** | Раскатка v2 на % пользователей с мониторингом. | Нет | Очень высокая |
| **Shadow** | Дублирование трафика на v2 без ответа пользователю. | Нет | Очень высокая |

#### Вспомогательные методы
- **Feature Flags:** Позволяют "развернуть" код, но оставить функционал выключенным до момента принятия решения о релизе.
- **A/B Testing:** Сравнение двух версий для оценки бизнес-метрик (не путать с Canary, который оценивает техническую стабильность).

### Принцип иммутабельности
**Single Immutable Artifact** — артефакт (Docker-образ) собирается **один раз** на этапе CI и проходит через все среды без изменений. Переменные окружения и секреты внедряются в момент старта.
**Анти-паттерн:** Пересборка образа для каждого окружения. Подробнее: **[Анти-паттерны CI/CD](../ci_cd_antipatterns.md)**.

## Практические сценарии

### Выбор стратегии в зависимости от типа приложения

1. **Монолиты / Legacy:** Часто используют **Recreate** или **Rolling Update** (если приложение поддерживает работу разных версий с одной БД).
2. **Микросервисы в Kubernetes:** Стандарт — **Rolling Update**. При высоких требованиях к надежности — **Canary**.
3. **Критичные системы (FinTech):** **Blue/Green** для мгновенного отката или **Shadow** для проверки под реальной нагрузкой.

### Управление трафиком
Для реализации сложных стратегий (Canary, Blue/Green) требуются внешние инструменты управления трафиком:
- **Service Mesh:** Istio, Linkerd.
- **Ingress Controllers:** NGINX, Traefik.
