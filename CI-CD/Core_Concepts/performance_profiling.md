# Профилирование производительности (SRE)

## Определения

- **Profiling** — сбор данных о том, где тратится CPU/память/IO во время работы программы.
- **CPU-bound / IO-bound / Memory-bound** — классы узких мест (процессор, ввод-вывод, память).
- **Flame Graph** — визуализация стека вызовов по времени: ширина = доля затрат.
- **pprof** — профайлер для Go/Python (HTTP-endpoint или файл).
- **perf** — системный профайлер Linux (Performance Events), работает на уровне ядра (см. [perf](../../Linux/Diagnostics/Performance/perf.md)).
- **Tail Latency** — задержка на верхних перцентилях (p95/p99/p999); «среднее» скрывает проблемы (см. [Анализ tail latency](../../Linux/Diagnostics/Performance/diagnosing_tail_latency.md)).
- **Continuous Profiling** — постоянный сбор профилей в проде для сравнения регрессий (см. [Continuous Profiling](../../Concepts/continuous_profiling.md)).

## Основные концепции

### Метод: сначала метрики, потом профиль

Не профилируйте наугад. Сначала метрики (CPU%, latency p99, GC pause) показывают *где* проблема (раннер? сервис? стадия сборки?), затем профиль показывает *что* именно (какой вызов). Это экономит время и исключает «просадку из головы».

### Чтение flame graph

Ищите широкие «полки» у основания — функции, съедающие большую долю времени. Узкие пики наверху — редкие, но глубокие пути (например, блокировка).

### Типы узких мест

- **CPU-bound**: высокий `usr%`, мало `iowait`. Профиль покажет горячие функции.
- **IO-bound**: высокий `iowait`/ожидание сети. Профилирование покажет места чтения/записи.
- **Memory-bound**: рост RSS, GC-пазы, OOM. Профиль выделений укажет источник.

### Tail latency vs среднее

Средняя задержка может быть 50 мс при p99 = 2 с. Для SRE важны перцентили; регрессии проявляются именно на хвосте. Связано с алертами из [Наблюдаемости пайплайнов](./pipeline_observability.md).

## Практические сценарии

### Сценарий 1: Системное профилирование (perf)

```bash
perf record -g -p $(pidof my_service) sleep 30   # 30 секунд выборки стека
perf report                                    # интерактивный анализ по функциям
# Для flame graph:
perf script | stackcollapse-perf.pl | flamegraph.pl > flame.svg
```

### Сценарий 2: pprof для Go-сервиса

```bash
# Включить профилирование (net/http/pprof) и снять CPU-профиль
go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30
# Или heap:
go tool pprof http://localhost:6060/debug/pprof/heap
# Визуализация: web (откроет граф) или команды top
```

### Сценарий 3: Применение к раннеру/сервису CI

1. Метрики показали, что стадия `build` тормозит на IO → `iostat -x 1` подтвердил высокий `await` диска.
2. `perf` на процессе сборки выявил частые `fsync` из-за кэша в `tmpfs` по умолчанию.
3. Решение: перенести кэш сборки на быстрый локальный том → p99 стадии упал в 3 раза.

## Дополнительная информация

### Типичные ошибки

- **Профилировать в проде без разрешения/нагрузки** — искажённые или рискованные данные.
- **Путать среднее и p99** — реальные жалобы пользователей скрыты за средним.
- **Оптимизировать без метрик** — «улучшение» не подтверждено цифрами.
- **Игнорировать GC/память** — утечки проявляются как медленный деград со временем.
