# GitOps Pipeline Example

## Определения

**GitOps Pipeline** — это конвейер доставки ПО, реализующий [GitOps-подход](../../GitOps/GitOps_overview.md), где CI-система отвечает за сборку артефактов, а CD-система декларативно управляет состоянием кластера на основе манифестов в Git.

## Основные концепции

### Разделение ответственности

Пайплайн разделен на две независимые части:

1. **CI (Continuous Integration):** Проверка кода, сборка и публикация артефактов (Docker-образ и Helm-чарт).
2. **CD (Continuous Delivery):** Синхронизация состояния кластера через GitOps-агент (например, [ArgoCD](../../GitOps/ArgoCD/argocd_overview.md)).

### Инструменты

- **CI-инструмент:** GitHub Actions
- **CD-инструмент:** ArgoCD

## Практические сценарии

### Поток выполнения

#### 1. Работа в фича-ветке (`feature-branch`)

- **Триггер:** `git push` в фича-ветку или создание Pull Request в `main`.
- **Действия (GitHub Actions):**
  - Линтинг и статический анализ.
  - Unit-тесты.
  - (Опционально) Сборка образа для preview-окружений (артефакт не публикуется в основной реестр).

#### 2. Слияние в `main` (CI-часть)

- **Триггер:** Merge Pull Request в ветку `main`.
- **Действия (GitHub Actions):**
  1. Интеграционные тесты.
  2. Сборка Docker-образа с тегом версии (например, `v1.2.3` или `main-<short-sha>`).
  3. Публикация Docker-образа в OCI-реестр (Docker Hub, Harbor, GHCR).
  4. Сборка и публикация Helm-чарта:
     - Версия `appVersion` в `Chart.yaml` обновляется до версии Docker-образа.
     - Версия чарта (`version`) инкрементируется.
     - Чарт упаковывается и публикуется в OCI-реестр.
  5. Обновление GitOps-репозитория (Handoff to CD):
     - CI-пайплайн клонирует репозиторий с манифестами Kubernetes (например, `my-apps-manifests`).
     - Обновляется `values.yaml` или `Application` манифест для ArgoCD с новой версией чарта.
     - Изменения коммитятся и пушатся в GitOps-репозиторий.

#### 3. Развертывание (CD-часть)

- **Триггер:** ArgoCD обнаруживает новый коммит в GitOps-репозитории.
- **Действия (ArgoCD):**
  1. Сравнение "живого" состояния в кластере с новым состоянием из Git.
  2. Обнаружение расхождения (новая версия чарта) и запуск синхронизации.
  3. Скачивание Helm-чарта из OCI-реестра, рендеринг шаблонов и применение в Kubernetes.
  4. Kubernetes выполняет rolling update подами с новой версией Docker-образа.

### Преимущества подхода

- **Разделение зон ответственности:** CI отвечает за артефакты, CD — за декларативное состояние кластера.
- **Безопасность:** Учетные данные кластера не покидают его пределы.
- **Аудируемость:** Все изменения состояния кластера фиксируются в Git.
- **Воспроизводимость:** Состояние инфраструктуры описывается декларативно.
