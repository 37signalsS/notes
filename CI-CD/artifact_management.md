### Определения

- **Артефакт** — это результат процесса сборки, готовый к развертыванию или использованию на следующем этапе (например, бинарный файл, Docker-образ, архив).
- **Репозиторий артефактов (Artifact Repository)** — это специализированное хранилище для управления бинарными файлами и зависимостями, которое действует как Git, но для бинарников.
- **GitLab Package Registry** — встроенный в GitLab репозиторий артефактов, поддерживающий различные форматы пакетов (npm, Maven, Generic и др.).

### Основные концепции

#### Зачем нужен репозиторий артефактов?

Хранение артефактов на диске CI/CD-агента ненадежно, так как агенты могут быть временными, а их диски — очищены. Специализированный репозиторий решает эти проблемы, обеспечивая:

- **Надежность и долговечность:** Артефакты хранятся централизованно и не зависят от жизненного цикла CI-агентов.
- **Версионирование и отслеживаемость:** Каждому артефакту присваивается уникальная версия, что позволяет легко откатываться к предыдущим сборкам.
- **Производительность:** Повторные сборки ускоряются за счет кэширования зависимостей и повторного использования готовых артефактов.
- **Безопасность:** Позволяет настроить гранулированный контроль доступа к артефактам.

#### Типы репозиториев

- **Хостинг (Hosted):** Хранение ваших собственных, уникальных артефактов.
- **Проксирование (Proxy):** Кэширование публичных зависимостей из внешних источников (Maven Central, PyPI, npmjs.com).
- **Группировка (Group):** Объединение нескольких репозиториев под одним URL для упрощения конфигурации.

#### Популярные решения

| Категория | Решение | Описание |
| :--- | :--- | :--- |
| **Self-Hosted** | **JFrog Artifactory**, **Sonatype Nexus**, **Harbor** | Мощные, гибкие решения для развертывания в собственной инфраструктуре. |
| **Cloud / SaaS** | **GitLab/GitHub Packages**, **AWS/Google/Azure Artifacts**| Интегрированные решения от платформ и облачных провайдеров. |

#### Типичный CI/CD пайплайн с репозиторием артефактов

1. **Триггер:** Коммит в Git.
2. **Запуск сборки:** CI/CD система запускает пайплайн.
3. **Получение зависимостей:** Сборочный агент запрашивает зависимости у репозитория артефактов.
4. **Сборка и тестирование:** Создается версионированный, неизменяемый (immutable) артефакт.
5. **Публикация артефакта:** Пайплайн публикует артефакт в репозиторий.
6. **Развертывание:** Задача развертывания скачивает конкретную версию артефакта и доставляет ее в целевое окружение.

### Практические сценарии

#### Публикация и использование Generic-пакета в GitLab

Этот сценарий показывает, как опубликовать произвольный файл (generic package) в GitLab Package Registry и затем использовать его в другой задаче.

##### Шаг 1: Публикация артефакта

Создадим задачу `publish_artifact`, которая создает текстовый файл и загружает его в реестр с помощью `curl` и предопределенных переменных GitLab CI.

```yaml
stages:
  - package
  - use

variables:
  PACKAGE_NAME: 'my-awesome-package'
  PACKAGE_VERSION: '1.0.0'
  FILE_NAME: 'artifact.txt'

publish_artifact:
  stage: package
  image: curlimages/curl:latest
  script:
    - echo "Creating and publishing package..."
    - echo "This is my artifact content" > ${FILE_NAME}
    - |
      curl --fail --header "JOB-TOKEN: ${CI_JOB_TOKEN}" --upload-file ${FILE_NAME} \
        "${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/packages/generic/${PACKAGE_NAME}/${PACKAGE_VERSION}/${FILE_NAME}"
```

- **`JOB-TOKEN: ${CI_JOB_TOKEN}`**: Безопасный способ аутентификации в API GitLab.
- **URL**: Формируется по строгому шаблону для Generic-пакетов.

После успешного выполнения этой задачи в разделе `Deploy > Package Registry` вашего проекта появится пакет `my-awesome-package` версии `1.0.0`.

##### Шаг 2: Использование артефакта

Задача `use_artifact` скачивает ранее опубликованный пакет и использует его.

```yaml
use_artifact:
  stage: use
  image: curlimages/curl:latest
  script:
    - echo "Downloading and using package..."
    - |
      curl --fail --location --header "JOB-TOKEN: ${CI_JOB_TOKEN}" \
        "${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/packages/generic/${PACKAGE_NAME}/${PACKAGE_VERSION}/${FILE_NAME}" \
        --output ${FILE_NAME}
    - echo "Downloaded artifact content:"
    - cat ${FILE_NAME}
```

**Результат:** Эта задача скачает `artifact.txt` из GitLab Package Registry и выведет его содержимое в лог, демонстрируя, что артефакт был успешно сохранен и получен.

### Дополнительная информация

#### Лучшие практики

1. **Используйте специализированный репозиторий:** Не храните артефакты на CI-сервере или в Git.
2. **Версионируйте все:** Каждый артефакт должен иметь уникальную, осмысленную версию.
3. **Обеспечьте неизменяемость (Immutability):** Опубликованный артефакт никогда не должен изменяться. Для исправлений выпускайте новую версию.
4. **Разделяйте репозитории:** Используйте отдельные репозитории для разных стадий (`snapshots`, `releases`).
5. **Настройте очистку:** Автоматически удаляйте устаревшие `snapshot`-сборки.
6. **Сканируйте на уязвимости:** Интегрируйте инструменты сканирования (JFrog Xray, Nexus Lifecycle) для проверки артефактов.
