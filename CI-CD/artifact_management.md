# Управление артефактами

**Актуально для:** self-hosted CI/CD-инфраструктура (GitLab CI, Jenkins, GitHub Self-Hosted Runners) с локальными реестрами (Nexus, Artifactory, Harbor, Zot) 2024–2026

> Область применения заметок: практики DevOps, SRE и SysAdmin при эксплуатации самостоятельно развёрнутых (on-prem / self-hosted) систем. Материалы, относящиеся к публичным облакам и технологиям искусственного интеллекта, в данной базе знаний не рассматриваются.

## Определения

- **Артефакт (Artifact)** — в контексте CI/CD — это материальный результат процесса сборки, который далее используется на этапах тестирования, доставки и эксплуатации. В отличие от исходного кода, артефакт является производным, собранным или сгенерированным объектом с фиксированным содержимым и метаданными, обеспечивающими его однозначную идентификацию и повторяемость.
- **Репозиторий артефактов (Artifact Repository)** — это специализированное хранилище для управления бинарными файлами и зависимостями, которое действует как Git, но для бинарных данных.
- **Реестр OCI (OCI Registry)** — современный стандарт хранилища (OCI Distribution Spec 1.1+), поддерживающий не только контейнерные образы, но и Helm-чарты, Terraform-модули, Wasm-бинарники и метаданные.
- **Политика хранения (Retention Policy)** — это набор правил, которые регулируют жизненный цикл артефактов: сроки их хранения, критерии для удаления или архивации (например, по времени, по количеству версий, по использованию).
- **Реестр пакетов (Package Registry)** — встроенное или внешнее хранилище для управления пакетами различных форматов (npm, Maven, Generic и др.). Примером является GitLab Package Registry.
- **SBOM (Software Bill of Materials)** — структурированный перечень всех компонентов, библиотек и зависимостей артефакта. В 2026 году является обязательным для комплаенса (например, EU CRA).
- **CBOM (Cryptography Bill of Materials)** — подвид SBOM, фиксирующий используемые криптографические алгоритмы и ключи для оценки устойчивости к квантовым атакам.
- **Аттестация (Attestation)** — криптографически подписанный документ, подтверждающий факт выполнения определенного действия в пайплайне (например, «сканирование пройдено» или «сборка выполнена на доверенном агенте»).
- **VEX (Vulnerability Exploitability eXchange)** — стандарт обмена данными о применимости уязвимостей, позволяющий вендорам официально подтверждать, что CVE не влияет на продукт, несмотря на наличие уязвимой библиотеки.
- **Referrers API (OCI 1.1)** — механизм, позволяющий связывать метаданные (подписи, SBOM, VEX) с основным артефактом без изменения его хэша (digest), формируя граф зависимостей внутри реестра.
- **Zot** — современный, сверхлегкий и высокопроизводительный OCI-native реестр, оптимизированный для работы с расширениями OCI 1.1 и метаданными.

## Основные концепции

### Зачем нужны артефакты?

- **Повторяемость и надежность:** Один и тот же бинарный файл или образ разворачивается во всех средах, что гарантирует консистентность. Артефакты хранятся централизованно и не зависят от жизненного цикла временных CI-агентов.
- **Трассируемость и версионирование:** Можно установить точное соответствие между коммитом, сборкой, тестами и развернутой версией. Каждому артефакту присваивается уникальная версия, что позволяет легко откатываться к предыдущим сборкам.
- **Безопасность цепочки поставок (Supply Chain Security):** Контроль целостности через хэши и криптографические подписи, использование фреймворков (например, **SLSA v1.2**), изоляция доверенного хранилища и гранулированный контроль доступа. В 2026 году фокус сместился на достижение **SLSA Level 3/4**.
- **Контроль качества:** Результаты тестов (JUnit XML), отчеты о покрытии кода, **SBOM** и сканы безопасности фиксируются как сопутствующие артефакты, подтверждая качество сборки.
- **Производительность:** Повторные сборки ускоряются за счет кэширования зависимостей и повторного использования готовых артефактов.

### Основные свойства артефактов

- **Неизменяемость (Immutability):** Артефакт с конкретной версией не перезаписывается. Для любых изменений выпускается новая версия. Это критично для воспроизводимости и безопасности.
- **Идентифицируемость (Identifiability):** Каждый артефакт имеет уникальный идентификатор (версия, метка коммита, ID пайплайна, digest).
- **Проверяемость (Verifiability):** Целостность подтверждается контрольными суммами (SHA-256/512), а подлинность — криптографическими подписями (Sigstore/Cosign).
- **Воспроизводимость (Reproducibility):** **Воспроизводимые сборки (Reproducible Builds)** гарантируют, что из одинаковых исходных данных и окружения всегда получается побайтово идентичный артефакт. Это исключает внедрение вредоносного кода на этапе сборки.

### Типы артефактов и их назначение

| Тип артефакта | Примеры | Назначение | Типичное хранилище |
| :--- | :--- | :--- | :--- |
| Исполняемые и библиотеки | `jar`, `war`, `dll`, `so` | Поставка приложений и модулей | Репозитории пакетов/бинарей |
| Пакеты | `deb`, `rpm`, `npm`, `pip wheel` | Установка через менеджеры пакетов | Регистры пакетов |
| Контейнерные образы | Docker image, OCI bundle | Упаковка среды выполнения | Контейнерные регистры (см. [Реестры Docker-образов](../Docker/docker_registries.md)) |
| Операционные пакеты | Helm chart, манифесты K8s | Описания развертывания | Chart-репозитории, OCI-реестры |
| Отчеты и метрики | `junit.xml`, `coverage.xml` | Подтверждение качества | Хранилище артефактов CI |
| Метаданные безопасности | **SBOM**, **CBOM**, аттестации | Анализ состава и аудит безопасности | OCI-реестры (Referrers API) |

### Продвинутая дистрибуция и оптимизация хранения

Эффективное управление артефактами тесно связано с оптимизацией ресурсов и масштабированием внутри периметра:

1.  **P2P Дистрибуция (Peer-to-Peer):** Применение технологий вроде **Dragonfly** или **Uber Kraken** позволяет распространять тяжелые образы в крупных кластерах, минимизируя нагрузку на центральный Registry и сетевые каналы.
2.  **Оптимизация хранения (Storage Optimization):**
    *   **Storage Tiering:** Автоматический перенос редко используемых артефактов (например, сборок feature-веток) в «холодные» хранилища (выделенный NFS-архив, объектное хранилище с пониженным классом доступа или ленточные библиотеки).
    *   **Smart Retention:** Интеграция реестра с оркестратором (Kubernetes) для удаления артефактов, на которые не ссылаются активные рабочие нагрузки и которые не помечены как «релизные».
    *   **Дедупликация:** Использование файловых систем и реестров с поддержкой дедупликации слоев на уровне всего хранилища.

### Работа в изолированных средах (Air-gapped)

В высокозащищенных или критических инфраструктурах управление артефактами требует специальных стратегий синхронизации при отсутствии прямого доступа к Интернету:
- **Sneakernet:** Физический перенос данных на отчуждаемых носителях.
- **Data Diodes:** Использование аппаратных средств для однонаправленной передачи.
- **Intermediate Registries:** Зеркалирование через промежуточные «прыжковые» реестры.
Подробные стратегии и инструменты описаны в разделе **[Изолированные среды (Air-gapped)](./Core_Concepts/air_gapped_environments.md)**.

## Версионирование артефактов

Распространенные схемы:

- **Семантическое версионирование (SemVer):** `MAJOR.MINOR.PATCH`. Пример: `1.4.0`, пре-релиз: `1.5.0-rc.2`, метаданные сборки: `1.4.0+build.57`.
- **Календарное версионирование (CalVer):** `YYYY.MM[.DD]`. Пример: `2025.10.10` для частых выпусков.
- **Комбинированные схемы:** SemVer + суффикс короткого SHA коммита (`1.4.0+gabc1234`) для точной трассировки.

Для образов контейнеров рекомендуется использовать семантические теги для удобства человека и **пин по digest** (уникальный хэш содержимого, например `sha256:...`) для машинной точности, избегая плавающих тегов (`latest`) в продуктивных средах.

### Метаданные и теги

Метаданные и теги — два механизма описания артефактов, которые обеспечивают отслеживаемость, поиск и управляемое продвижение версий.

| Аспект | Метаданные | Теги |
| :--- | :--- | :--- |
| **Структура** | Ключ–значение, иногда вложенная (`ci.pipeline=1234`) | Строковые ярлыки (`1.4.2`, `latest`, `prod`) |
| **Назначение** | Поиск, фильтрация, автоматизация политик | Маркировка версий и каналов поставки (rc, stable) |
| **Изменяемость** | Обычно изменяемые, аудируемые | Часто переназначаемые (плавающие), но релизные теги должны быть иммутабельными |

Рекомендуется включать в имя и/или метаданные: семантическую версию, короткий SHA коммита, идентификатор сборки и целевую платформу.

```bash
# Пример формирования имени и фиксации контрольной суммы
APP=myapp
VER=1.4.0
SHA=$(git rev-parse --short HEAD)
BUILD=${CI_PIPELINE_ID:-local}
ART="${APP}-${VER}+build.${BUILD}-${SHA}-linux-amd64.tar.gz"

tar -czf "dist/$ART" bin/ config/
sha256sum "dist/$ART" > "dist/$ART.sha256"
```

### Жизненный цикл артефактов в конвейере

1.  **Сборка и генерация SBOM/CBOM:** Компиляция приложения и создание детального состава ПО, включая криптографический профиль.
2.  **Обогащение (Enrichment):** Сканирование на уязвимости (SCA) и прикрепление результатов как OCI-метаданных через Referrers API.
3.  **Публикация:** Загрузка в специализированное хранилище (репозиторий артефактов, регистр образов).
4.  **Подпись и Аттестация (Signing & Provenance):** Создание аттестации происхождения (Build L3) и подпись артефакта через Sigstore/Cosign.
5.  **Валидация политик (Policy as Code):** Автоматическая проверка артефакта на соответствие корпоративным стандартам (наличие SBOM, отсутствие критических CVE, валидная подпись) перед допуском к деплою.
6.  **Продвижение (Promotion):** Маркировка и перенос статуса сборки между средами (dev → stage → prod) без физической пересборки.
7.  **Хранение и очистка:** Автоматизированные политики `retention` и оптимизация хранилища.

## Практические сценарии

### Сценарий 1: Работа с GitLab CI

В GitLab CI артефакты используются как для передачи данных между этапами пайплайна, так и для долгосрочного хранения пакетов.

- **Временные артефакты:** Используются для передачи результатов сборки в задачи тестирования и развертывания. Подробную конфигурацию см. в разделе [Артефакты в GitLab CI](./GitLab_CI/Advanced/gitlab_ci_caching/gitlab_ci_artifacts.md).
- **GitLab Package Registry:** Позволяет публиковать и использовать версионированные пакеты (npm, Maven, Generic).

```yaml
# Пример публикации Generic-пакета в GitLab
publish_package:
  stage: package
  script:
    - |
      curl --fail --header "JOB-TOKEN: ${CI_JOB_TOKEN}" --upload-file ${FILE_NAME} \
        "${CI_API_V4_URL}/projects/${CI_PROJECT_ID}/packages/generic/${PACKAGE_NAME}/${PACKAGE_VERSION}/${FILE_NAME}"
```

### Сценарий 2: Интеграция с Nexus и Artifactory

**Maven и Sonatype Nexus:**

```xml
<!-- settings.xml -->
<settings>
  <servers>
    <server>
      <id>nexus-releases</id>
      <username>${env.NEXUS_USER}</username>
      <password>${env.NEXUS_PASS}</password>
    </server>
  </servers>
  <profiles>
    <profile>
      <id>release</id>
      <properties>
        <altDeploymentRepository>nexus-releases::default::https://nexus.local/repository/maven-releases/</altDeploymentRepository>
      </properties>
    </profile>
  </profiles>
</settings>
```

**JFrog CLI и Artifactory:**

```bash
jf c add art --url=https://art.local --user=$USER --password=$PASS --interactive=false
mvn -B deploy -DaltDeploymentRepository=artifactory::default::https://art.local/artifactory/my-maven-local
jf rt build-publish my-build $CI_PIPELINE_ID
```

### Сценарий 3: Управление метаданными через OCI Referrers (ORAS)

Современный способ прикрепления SBOM к образу без изменения его digest.

```bash
# Публикация SBOM как связанного артефакта
oras attach --artifact-type application/spdx+json \
  registry.local/my-app:v1.0.0 \
  ./app-sbom.spdx

# Просмотр графа зависимостей (discover)
oras discover registry.local/my-app:v1.0.0
```

### Сценарий 4: Внедрение Policy as Code при деплое (Kyverno)

Блокировка деплоя образов, у которых отсутствует валидная аттестация SBOM.

```yaml
# Фрагмент политики Kyverno для проверки аттестаций
verifyImages:
- imageReferences:
  - "registry.local/my-app:*"
  attestations:
  - predicateType: https://cyclonedx.org/bom/v1.6
    attestors:
    - entries:
      - keys:
          publicKeys: |-
            -----BEGIN PUBLIC KEY-----
            ...
```

### Сценарий 5: Продвижение артефакта между средами без пересборки (Promotion)

Принцип **Build Once, Deploy Many** требует, чтобы один и тот же digest переносился из dev-репозитория в prod-репозиторий внутри периметра без повторной компиляции. Это гарантирует, что в прод попадает именно протестированный бинарь.

```bash
# Вариант A: skopeo (registry-to-registry, без docker daemon)
skopeo copy \
  docker://nexus.internal:5000/app-dev:1.4.0@sha256:$DIGEST \
  docker://nexus.internal:5000/app-prod:1.4.0

# Вариант Б: ретег того же digest через regctl (артeфакт не копируется, меняется только ссылка)
regctl tag set nexus.internal:5000/app:1.4.0 --digest sha256:$DIGEST
regctl tag rm  nexus.internal:5000/app:1.4.0-rc.2
```

> Проверка: убедитесь, что `sha256sum` скачанного из `app-prod` артефакта совпадает с `sha256` из `app-dev` — это подтверждает идентичность сборки.

### Сценарий 6: Генерация SBOM и уязвимостный гейт в пайплайне (syft + grype)

Практика devsecops/sysadmin: состав фиксируется и проверяется до допуска к деплою; пайплайн падает при критичных CVE.

```bash
# Генерация SBOM (CycloneDX)
syft nexus.internal:5000/app:1.4.0 -o cyclonedx-json > sbom.json

# Сканирование уязвимостей строго по SBOM (детерминированно, офлайн)
grype sbom:sbom.json --fail-on high

# Подпись SBOM и привязка к образу через Referrers API (cosign attest)
cosign attest --predicate sbom.json --type cyclonedx app:1.4.0
```

### Сценарий 7: Воспроизводимая сборка (Reproducible Builds)

Системный подход к тому, чтобы из одного коммита и окружения всегда получался побайтово идентичный бинарь (исключает внедрение кода на этапе сборки).

```bash
# Go: убираем абсолютные пути и встраиваемые метаданные сборки
go build -trimpath -buildvcs=false \
  -ldflags="-buildid= -X main.version=1.4.0" \
  -o dist/app-linux-amd64 .

# Детерминизм: две сборки из одного коммита дают одинаковый хэш
sha256sum dist/app-linux-amd64
```

Дополнительно: отключать CGO (`CGO_ENABLED=0`) для кроссплатформенной идентичности и фиксировать порядок/версии зависимостей (lock-файлы, `go.sum`).

### Сценарий 8: Очистка и автоматизация retention (Cleanup)

SRE-практика предотвращения исчерпания диска реестра: удаление устаревших тегов и неиспользуемых манифестов.

```bash
# Удаление тегов старше 30 дней (regctl + date)
regctl tag ls nexus.internal:5000/app | while read t; do
  created=$(regctl manifest get --format '{{.Created}}' nexus.internal:5000/app:"$t")
  age=$(( ( $(date +%s) - $(date -d "$created" +%s) ) / 86400 ))
  [ "$age" -gt 30 ] && regctl tag rm nexus.internal:5000/app:"$t"
done

# Удаление манифеста по digest (освобождение места на уровне слоёв)
oras manifest delete nexus.internal:5000/app@sha256:$DIGEST --force
```

Серверные альтернативы: cleanup-политики Nexus (Scheduled Tasks), AQL-запросы Artifactory и retention-правила Harbor — настраиваются в UI/API и не требуют крона.

## Ограничения и крайние случаи

- **Air-gapped среды:** Управление артефактами здесь становится критическим: невозможность подтянуть зависимости из публичных источников делает фатальными пересборку артефактов (#2) и отсутствие локальных зеркал. Подробнее: **[Изолированные среды (Air-gapped)](./Core_Concepts/air_gapped_environments.md)**.
- **Высокая доступность реестра:** Сам реестр артефактов становится SPOF. Для Nexus/Artifactory/Harbor применяется active-passive с shared storage или active-active с репликацией; для Zot — edge/replica-топологии. RTO реестра обычно часы; детали бэкапа/восстановления — в **[Резервном копировании и DR для CI/CD](./Core_Concepts/ci_cd_backup_dr.md)**.
- **Регуляторные требования (финансы, госсектор):** Каждый артефакт должен иметь неизменяемую SBOM, криптографическую подпись и audit-log доступа к реестру. Дрейф состава или отсутствие provenance становятся Compliance-риском.
- **Большие монореpos:** Объём артефактов и время их хранения растут нелинейно. Жесткие retention-политики, Storage Tiering и инкрементальные сборки становятся обязательными, а не опциональными.
- **Multi-tenancy / shared runners:** В мультитенантных окружениях артефакты одного проекта не должны быть доступны другому. namespace-изоляция в реестре, scoped RBAC и отдельные бакеты/репозитории на проект — обязательны.

## Дополнительная информация

### Инструменты хранения: Nexus vs Artifactory vs Harbor vs Zot

| Критерий | Sonatype Nexus Repository | JFrog Artifactory | VMware Harbor | Zot |
| :--- | :--- | :--- | :--- | :--- |
| **Режимы репозиториев** | hosted, proxy, group | local, remote, virtual | Native OCI Registry | OCI-native |
| **Поддержка форматов** | Maven, npm, PyPI, NuGet, Docker и др. | Все форматы | Docker, Helm, OCI Artifacts | Только OCI |
| **Метаданные сборок** | Компоненты, теги, атрибуты | Build Info (полная трассировка) | OCI Referrers API (v2.10+) | Referrers / Extensions |
| **Продвижение** | Staging/Release, теги | Promotion API/CLI | Tag Retention, Replication | API / CLI |
| **Безопасность** | RBAC, Nexus Lifecycle (SCA) | RBAC, JFrog Xray (SCA) | Trivy, Cosign, Notary | RBAC, OCI extensions |
| **OCI 1.1 Support** | Частично | Полная поддержка | Полная поддержка | Native Support |
| **Масштабируемость** | Средняя | Высокая (HA) | Высокая (P2P) | Экстремальная (Edge) |

### Лучшие практики

1.  **Используйте специализированный репозиторий:** Не храните артефакты на CI-сервере (кроме временных) или в Git.
2.  **Версионируйте все:** Каждый артефакт должен иметь уникальную, осмысленную версию (SemVer или CalVer).
3.  **Обеспечьте неизменяемость (Immutability):** Опубликованный артефакт никогда не должен изменяться. Запрещайте перезапись релизных тегов.
4.  **Активное использование SBOM и CBOM:** Не просто создавайте отчеты, а блокируйте пайплайны при обнаружении критических уязвимостей или запрещенных крипто-алгоритмов.
5.  **Разделяйте репозитории:** Используйте отдельные репозитории для разных стадий (`snapshots`, `releases`, `dev`, `prod`).
6.  **Сканируйте на уязвимости:** Интегрируйте SCA-инструменты (Trivy, Xray, Nexus Lifecycle) для автоматической проверки на каждом этапе.
7.  **Обогащайте метаданными:** Добавляйте в CI контекст сборки (ID пайплайна, SHA коммита) через OCI labels или Referrers API.
8.  **Используйте digest для деплоя:** В продуктивных средах деплойте по `sha256` digest, а теги используйте как удобные алиасы для человека.
9.  **Keyless-подписи:** Уходите от GPG в сторону Sigstore для упрощения управления доверием в CI/CD без управления секретами.
10. **Применяйте политики очистки (Cleanup):** Настраивайте retention на основе возраста/количества версий и используйте Storage Tiering для экономии места (см. Сценарий 8).

### Устранение неполадок (Troubleshooting)

| Симптом | Вероятная причина | Действие |
| :--- | :--- | :--- |
| Образ по тегу отличается от ожидаемого | Плавающий тег (`latest`) / перезапись релиза | Деплой по digest; запретить перезапись релизных тегов (Best Practice #3) |
| SBOM не генерируется | `syft` не поддерживает тип артефакта | Проверить тип (dir, image, alpine); использовать плагин CycloneDX |
| Подпись не проходит `cosign verify` | Неверный публичный ключ / артефакт изменён | Сверить key, повторно подписать, валидировать digest |
| Растёт место на диске реестра | Нет retention-политик | Настроить cleanup по возрасту/количеству (Сценарий 8) |
| Дрейф состава между средами | Пересборка вместо promotion | Продвижение по digest без rebuild (Сценарий 5) |
| `skopeo copy` падает с 401 | Истёкший/неверный токен реестра | Обновить токен из Vault через OIDC; не хранить статический пароль |
