# Управление артефактами в CI/CD

## Определения

**Артефакт** — это результат процесса сборки, готовый к развертыванию или использованию на следующем этапе. Примерами могут служить:

*   Скомпилированный бинарный файл (`.jar`, `.war`, `.exe`, Go-бинарник).
*   Docker-образ.
*   Пакет для менеджера зависимостей (`.npm`, `.gem`, `.whl`).
*   Архив со статическими файлами для веб-сервера (`.zip`, `.tar.gz`).
*   Сгенерированная документация.
*   Отчеты о тестировании или покрытии кода.

**Репозиторий артефактов (Artifact Repository)** — это специализированное хранилище для управления бинарными файлами и зависимостями. Его можно сравнить с Git, но для бинарников, а не для исходного кода.

## Основные концепции

### Проблемы хранения артефактов на CI-сервере

Подход, при котором артефакты остаются на диске CI/CD-агента (например, в Jenkins workspace или кэше GitLab runner), является ненадежным и приводит к ряду проблем:

1.  **Ненадежность:** CI-агенты часто бывают временными, особенно в облачных средах или Kubernetes. Их диски могут быть очищены, что приведет к потере артефактов.
2.  **Отсутствие версионирования:** Затрудняется поиск конкретной версии артефакта, откат на нее и отслеживание истории изменений.
3.  **Низкая производительность:** Если для сборки одного компонента требуется артефакт другого, CI-серверу приходится заново его собирать вместо того, чтобы скачать готовый.
4.  **Угрозы безопасности:** Отсутствует гранулированный контроль доступа. Любой, кто имеет доступ к CI-агенту, может получить доступ ко всем артефактам.

### Ключевые функции репозитория артефактов

1.  **Хостинг (Hosted Repositories):** Хранение собственных уникальных артефактов (например, `my-super-app-v1.2.0.jar`).
2.  **Проксирование (Proxy Repositories):** Кэширование публичных зависимостей из таких источников, как Maven Central, PyPI, npmjs.com. CI-сервер обращается к локальному репозиторию, который, в свою очередь, скачивает и кэширует внешние зависимости.
3.  **Группировка (Group Repositories):** Объединение нескольких хостируемых и прокси-репозиториев под одним URL-адресом, что упрощает конфигурацию для клиентов.

## Практические сценарии

### Популярные решения

| Категория | Решение | Описание |
| :--- | :--- | :--- |
| **Self-Hosted** | **JFrog Artifactory** | Лидер рынка с поддержкой множества форматов. Мощный, но сложный в настройке. |
| | **Sonatype Nexus Repository** | Главный конкурент Artifactory, популярен в Java-экосистеме, считается более простым. |
| | **Harbor** | Open Source проект от CNCF, изначально созданный как реестр Docker-образов, но теперь поддерживающий и другие форматы (Helm, OCI). |
| **Cloud / SaaS** | **GitHub Packages** | Интегрирован с GitHub, удобен для проектов, размещенных на этой платформе. |
| | **GitLab Package Registry** | Аналогично GitHub Packages, интегрирован с GitLab. Позволяет хранить артефакты рядом с кодом и пайплайнами. |
| | **AWS CodeArtifact, Google Artifact Registry, Azure Artifacts** | Решения от крупных облачных провайдеров, глубоко интегрированные в их экосистемы. |
| **Для Docker-образов** | **Docker Hub** | Публичный реестр по умолчанию. См. [реестры Docker](../Docker/docker_registries.md). |
| | **Amazon ECR, Google GCR, Azure ACR** | Специализированные реестры контейнеров от облачных провайдеров. |
| **Объектное хранилище** | **Amazon S3, Google Cloud Storage** | Подходит для хранения "сырых" артефактов, но без функций проксирования и управления метаданными. |

### Типичный CI/CD пайплайн

1.  **Триггер:** Разработчик отправляет код в Git.
2.  **Запуск сборки:** CI/CD система (Jenkins, GitLab CI) запускает пайплайн.
3.  **Получение зависимостей:** Сборочный агент обращается к локальному репозиторию артефактов за зависимостями. Если их нет в кэше, репозиторий скачивает их из внешних источников.
4.  **Сборка и тестирование:** Код компилируется, тесты выполняются, и создается версионированный артефакт (например, `my-app:v1.5.2`).
5.  **Публикация артефакта:** Пайплайн публикует неизменяемый (immutable) артефакт в репозиторий. Перезапись существующей версии запрещена.
6.  **Развертывание:** Задача развертывания скачивает конкретную версию артефакта из репозитория и доставляет ее в целевое окружение (staging, production).

## Дополнительная информация

### Лучшие практики

1.  **Используйте специализированный репозиторий:** Не храните артефакты на CI-сервере или в системе контроля версий.
2.  **Версионируйте все:** Каждый артефакт должен иметь уникальную, осмысленную версию (например, семантическую, по хешу коммита или номеру сборки).
3.  **Обеспечьте неизменяемость (Immutability):** Опубликованный артефакт никогда не должен изменяться. Для исправлений выпускайте новую версию.
4.  **Разделяйте репозитории:** Используйте отдельные репозитории для разных стадий и типов артефактов (`snapshots`, `releases`, `third-party`).
5.  **Настройте очистку:** Автоматически удаляйте устаревшие `snapshot`-сборки для экономии места.
6.  **Сканируйте на уязвимости:** Интегрируйте инструменты сканирования (например, JFrog Xray, Nexus Lifecycle) для проверки артефактов и их зависимостей.
