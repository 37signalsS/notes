# GitLab CI/CD: Best Practices and Security

## Маскирование переменных в CI/CD

Чтобы скрыть важную переменную в логе рабочего процесса CI/CD, можно использовать встроенный функционал GitLab, а именно - поставить в свойствах переменной галочку "Mask variable".
Подробнее в официальной документации: https://docs.gitlab.com/ee/ci/variables/#mask-a-custom-variable
Однако не всякую переменную возможно скрыть, есть закрытый список требований. Какого требования к содержимому переменной нет в документации? (Этот вопрос, видимо, для самопроверки или обсуждения).

## Автопроверка выполнения заданий

Мы добавили новую функцию — автопроверку выполнения заданий на наших стендах. Если вы хотите понять, правильно ли всё сделано и выполнены ли все ключевые пункты задания — выполняйте его на наших стендах, а затем (не останавливая стенд!) нажмите кнопку внизу «Проверить». Если какой-то пункт не выполнен или сделан неправильно, автоматика даст вам обратную связь. Однако для правильной работы проверки необходимо строго придерживаться инструкций к заданию — к примеру, если назвать репозиторий не так, то проверка его не найдёт.
Этот функционал находится в стадии внедрения, поэтому при каких-либо проблемах не стесняйтесь писать в поддержку.

## Добавление статического анализа кода (SAST) в пайплайн

GitLab предлагает немало возможностей для улучшения безопасности вашего проекта.
Ознакомиться с ними можно тут: https://docs.gitlab.com/ee/user/application_security/index.html#quick-start

Для прохождения этой практики будет достаточно любого fork'a репозитория https://gitlab.slurm.io/edu/ci-cd/cicd-app
Вся работа будет проводиться в GitLab и на runner, и не затрагивать другие этапы CI/CD, если они у вас уже описаны в файле `.gitlab-ci.yml`.

Для подключения SAST достаточно добавить в корень pipeline'a нужный шаблон:

```yaml
include:
  - template: Security/SAST.gitlab-ci.yml
```

И после этого на этапе `test` (если он у вас уже есть с таким именем - добавится параллельный job) у вас будет проводиться тестирование.
Говоря конкретно про SAST, имеется довольно большой набор сканеров: https://docs.gitlab.com/ee/user/application_security/sast/index.html#supported-languages-and-frameworks

Эти подключаемые шаблоны не сверхсекретные, и их можно посмотреть например вот тут: `https://qgitlab.com/gitlab-org/gitlab//[tree/master/lib/gitlab/ci/templates/Security` или на локальном диске, где установлен ваш GitLab.

Всё это замечательно работает в платных версиях, подробнее можно почитать тут: https://docs.gitlab.com/ee/user/application_security/sast/index.html

Однако мы пойдем чуть дальше, и внедрим немного автоматики в бесплатную версию GitLab CE.
Нам понадобится примерно такой pipeline (пример заточен под наше учебное приложение на Go):

```yaml
stages:
  - build
  - test
  - report

include:
  - template: Security/SAST.gitlab-ci.yml

gosec-sast:
  artifacts:
    paths:
      - gl-sast-report.json
    reports:
      sast: gl-sast-report.json

send-reports:
  stage: report
  artifacts:
    paths:
      - gl-sast-report.json
    reports:
      sast: gl-sast-report.json
  script:
    - content=$(cat gl-sast-report.json)
    - |
      if [ "${content}" = "[]" ]
      then
        echo "Your code looks good"
      else
        echo "ALERT! Problems detected, see report";
        exit 1
      fi
```

Логика такая - на этапе `test` сканер генерирует артефакт, а затем на этапе `report` мы показываем в лог содержимое отчёта и проверяем.
Если там не пусто - выдаём alert и код выхода 1, что стопорит дальнейшие шаги pipeline'a.
Таким же образом можно подключать другие сканеры из шаблонов GitLab.
