# Консенсус Raft в Consul

**Актуально для:** Consul 2.0.x / 1.22.x / 1.20.x / 1.19.x

## Определения

**Механизм консенсуса** в Consul отвечает за поддержание согласованного (consistent) и отказоустойчивого состояния между серверами кластера. Для этой цели Consul использует протокол **Raft**. В терминах CAP-теоремы Consul является **CP-системой**, отдающей приоритет строгой согласованности и устойчивости к разделению сети.

Все критические данные — [каталог сервисов](./consul_service_catalog.md), [KV-хранилище](./consul_kv_store.md), [ACL](./consul_acl.md) и конфигурация Service Mesh — проходят через реплицируемый лог Raft. Consul использует собственную реализацию библиотеки HashiCorp Raft (также применяемую в Vault и Nomad), которая гарантирует целостность данных при сбоях. Общие принципы алгоритма описаны в [Алгоритме Raft в etcd](../etcd/raft_consensus.md).

Начиная с Consul 1.15.0, по умолчанию используется бэкенд **WAL LogStore** (Write-Ahead Log), который заменяет BoltDB. WAL предоставляет более высокую производительность записи и не блокирует обслуживание снапшотов. Для обратной совместимости BoltDB доступен через параметр `raft_logstore.backend`, но его использование не рекомендуется.

Consul использует **MemDB** для поддержания согласованного лога. Это позволяет продолжать принимать новые транзакции во время создания снапшотов, исключая простои.

## Основные концепции

### Принципы Raft в Consul

- **Кворум:** Только **серверы** Consul участвуют в принятии решений. Для работы кластера из `N` серверов необходим кворум из `(N/2)+1` голосующих узлов.
- **Роли узлов:**
    - **Лидер (Leader):** Узел, принимающий все запросы на запись и координирующий репликацию.
    - **Последователь (Follower):** Голосующий узел (`Voter`), который реплицирует данные и участвует в выборах.
    - **Обучающийся (Learner):** Неголосующий узел (v1.11+). Используется для безопасного расширанения кластера: он получает данные от лидера, но не влияет на кворум, пока не синхронизируется.
    - **Неголосующий (Non-voter / Read Replica):** Доступно в Enterprise. Узел, который реплицирует данные для обслуживания тяжелых запросов на чтение, не влияя на стабильность кворума.
- **Термы и выборы:** Жизненный цикл разделен на **термы** (эпохи). Если последователи не получают Heartbeats от лидера, они инициируют выборы, становясь **кандидатами**.

### Процесс репликации и WAL

1. Запрос на запись поступает на лидера.
2. Лидер записывает операцию в свой **WAL (Write Ahead Log)** на диске и добавляет в локальный лог Raft.
3. Лидер рассылает запись (`AppendEntries` RPC) последователям.
4. Последователи записывают данные в свой WAL и подтверждают получение.
5. При достижении кворума запись считается **зафиксированной (Committed)**.
6. Лидер применяет изменение к **FSM (Finite State Machine)** в памяти и уведомляет клиента.

Consul блокирует записи до тех пор, пока лог не будет одновременно зафиксирован и применен. Это обеспечивает строгую согласованность для режима `consistent` в HTTP API.

### Механизмы согласованного чтения (ReadIndex)

Для обеспечения строгой согласованности (`consistent` чтения) Consul реализует механизм **ReadIndex**:
- При получении запроса на чтение лидер запоминает свой текущий индекс фиксации.
- Лидер отправляет Heartbeat большинству узлов, чтобы подтвердить свой статус.
- Ответ возвращается клиенту только после подтверждения лидерства, что исключает «грязное чтение» в случае, если лидер был изолирован от сети (Split-brain).

### Автоматизация через Autopilot

Autopilot автоматизирует обслуживание Raft-кворума:
- **Dead Server Cleanup:** Автоматическое удаление неисправных серверов из кворума (параметр `CleanupDeadServers`, по умолчанию `true`). При отключении Autopilot удаление занимает 72 часа.
- **Server Stabilization:** Время (`ServerStabilizationTime`, по умолчанию `10s`), в течение которого новый сервер должен быть стабилен перед получением статуса `voter`.
- **Health Tracking:** Отслеживание задержек `LastContact` (критично более `200ms`, параметр `LastContactThreshold`) и отставания логов `MaxTrailingLogs` (по умолчанию `250`).
- **MinQuorum:** Минимальное количество здоровых голосующих серверов, необходимое для поддержания кворума (по умолчанию `0`).

**Различие `MaxTrailingLogs` и `raft_trailing_logs`:** `MaxTrailingLogs` — порог Autopilot для определения нездоровья сервера (по умолчанию 250). `raft_trailing_logs` — количество записей лога, оставляемых на диске после снапшота (по умолчанию 10000, начиная с Consul 1.5.3). Это разные параметры с разными целями.

### Зоны избыточности (Redundancy Zones — Enterprise)

Позволяет распределять серверы по зонам доступности (AZ) для повышения отказоустойчивости:
- В каждой AZ назначается один активный `voter`. Остальные серверы в зоне — `non-voters`.
- При отказе `voter`, Autopilot автоматически повышает одного из `non-voters` в той же AZ до статуса голосующего.
- **Результат:** Защита от сбоя целой зоны без раздувания Raft-кворума до 7+ узлов.

## Предварительные требования

- **Кластер:** 3 или 5 серверов Consul для HA, кворум `(N/2)+1`. Большее количество серверов замедляет Raft из-за увеличения времени репликации.
- **Диск:** SSD/NVMe с задержкой `fsync` < 10ms. Raft блокируется на `fsync` при записи в WAL, поэтому дисковая подсистема критична для стабильности.
- **Сеть:** Низкая задержка между серверами (< 10ms для LAN). Для гео-распределенных кластеров используйте `raft_multiplier` для компенсации задержек.
- **Time synchronization:** NTP/Chrony на всех серверах; Raft зависит от согласованных часов.
- **ACL:** Включены с `default_policy = "deny"` и распределёнными токенами для управления доступом к операторским командам.
- **Резервное копирование:** Регулярные снапшоты через `consul snapshot save` или snapshot agent (Enterprise).
- **Наблюдаемость:** Метрики Raft в Prometheus (`consul_raft_commitTime`, `consul_raft_leader_lastContact`, `consul_raft_peers`, `MaxTrailingLogs`).

## Практические сценарии

### Безопасное добавление серверов (Learners)

При добавлении нового сервера в кластер (особенно при замене старых узлов) рекомендуется использовать роль **Learner**. Это предотвращает риск потери кворума, если новый узел начнет скачивать большой снапшот и не сможет вовремя отвечать на запросы.

1.  **Добавление:** Узел автоматически входит как Learner, если в кластере уже есть полный кворум.
2.  **Синхронизация:** Проверьте статус синхронизации:
    ```bash
    consul operator raft list-peers
    # → узел будет помечен как "learner"
    ```
3.  **Повышение (Promotion):** Autopilot автоматически повысит узел до `voter`, как только он синхронизирует достаточное количество логов.

### Ручная передача лидерства

Используется для планового обслуживания узда-лидера, чтобы избежать резкого прерывания запросов.

```bash
# Передача лидерства другому конкретному узлу
consul operator raft transfer-leader -address="10.0.0.5:8300"
# → команда вернёт управление после успешной передачи
```

### Снапшоты и компакция лога

Чтобы лог не рос бесконечно, Consul создает снапшоты (snapshot) и удаляет старые записи лога (компакция) при достижении `raft_snapshot_threshold` (по умолчанию 16384 записи).

```bash
# Создание резервной копии состояния кластера
consul snapshot save backup.snap
# → Snapshot saved successfully

# Восстановление из снапшота (требуется стабильный кластер с лидером)
consul snapshot restore backup.snap
# → Snapshot restored successfully
```

Для регулярного создания снапшотов без остановки кластера используйте **Consul Snapshot Agent** (Enterprise) или планируйте выполнение `consul snapshot save` через cron с использованием стейтлесс токена с соответствующими ACL-разрешениями.

### Диагностика кластера

```bash
# Список участников кворума и их статусы
consul operator raft list-peers
# → вывод таблицы с id, address, voter status, leader status

# Проверка здоровья глазами Autopilot
consul operator autopilot health
# → вывод состояния серверов, времени последнего контакта, trailing logs
```

### Очистка неисправного пира (remove-peer)

Если сервер permanently вышел из строя и не может быть восстановлен, удалите его из Raft-конфигурации:

```bash
# Удаление по адресу
consul operator raft remove-peer -address="10.0.0.3:8300"
# → Peer removed successfully

# Или по ID
consul operator raft remove-peer -id="<server-id>"
# → Peer removed successfully
```

**Очистка после операции:** Убедитесь, что сервер удален из конфигурации через `consul operator raft list-peers`. Если сервер еще visible в `consul members`, выполните `consul force-leave <name>` для полного исключения из Gossip.

## Лучшие практики

- **HA:** 3 или 5 серверов; больше замедляет Raft.
- **Диск:** Используйте NVMe/SSD с задержкой `fsync` < 10ms. Raft блокируется на `fsync` при записи в WAL.
- **Сеть:** Низкая задержка между серверами (< 10ms для LAN). Для гео-распределенных кластеров настройте `raft_multiplier` для увеличения тайм-аутов.
- **Автопилот:** Оставьте включенным (`CleanupDeadServers = true`). В тестовых окружениях можно отключить.
- **Time Sync:** NTP/Chrony на всех серверах; Raft зависит от согласованных часов.
- **Бэкапы:** Регулярные снапшоты через `consul snapshot save` или snapshot agent. Храните снапшоты вне кластера.
- **Learners:** Используйте Learner при добавлении/замене серверов для безопасной синхронизации.
- **Наблюдаемость:** Мониторьте `consul_raft_leader_lastContact`, `MaxTrailingLogs`, `consul_raft_commitTime`, `consul_raft_peers`.

## Граничные случаи

- **WAL LogStore:** По умолчанию с Consul 1.15.0. BoltDB доступен для обратной совместимости, но не рекомендуется.
- **Quorum Loss:** При потере кворума кластер переходит в read-only для `stale` чтений. Для восстановления требуется ручное создание `peers.json`.
- **Leader Flapping:** Частые перевыборы лидера вызываются дисковыми задержками (`await > 10ms`) или contention на CPU. Используйте выделенные инстансы и приоритизацию процесса.
- **Гео-распределение:** Увеличение `raft_multiplier` компенсирует сетевые задержки, но увеличивает время обнаружения сбоев.
- **Enterprise Redundancy Zones:** Требуют лицензии Enterprise. Автоматическое повышение non-voter происходит только внутри одной AZ.
- **`raft_trailing_logs` vs `MaxTrailingLogs`:** Не путайте параметр Raft `raft_trailing_logs` (default 10000) с Autopilot `MaxTrailingLogs` (default 250). Первый управляет объемом лога после снапшота, второй — порогом для Autopilot health check.

## Устранение неполадок

### Потеря кворума (Quorum Loss)

Если большинство серверов вышли из строя, кластер переходит в режим "Read-Only" (для `stale` чтений) и перестает принимать записи.

**Процедура ручного восстановления:**
1.  Остановите Consul на всех оставшихся серверах.
2.  В директории данных (`data_dir/raft/`) создайте файл `peers.json`.
3.  Формат файла (только для выживших узлов):
    ```json
    [
      {
        "id": "node-uuid-can-be-found-in-node-id-file",
        "address": "10.0.0.1:8300",
        "non_voter": false
      }
    ]
    ```
4.  Запустите Consul. Узел принудительно станет лидером и сформирует новый кворум.
    ```bash
    # → agent.server: found peers.json file, recovering Raft configuration...
    # → agent.server: raft recovery found new config
    # → agent.server: raft recovery deleted peers.json
    ```
5.  **Очистка после восстановления:** Добавьте новые серверы через Learner role, чтобы избежать повторного потери кворума.

### Задержки Raft (Leader Flapping)

Ищите в логах ошибки `Raft: Heartbeat timeout`.

- **Причина 1: Дисковая задержка.** Raft блокируется на `fsync`. Используйте `iostat` для проверки `await`. Требование: **< 10ms**.
    ```bash
    # Диагностика
    iostat -x 1 5
    # → await < 10.00 ms для диска с data_dir
    ```
- **Причина 2: CPU Starvation.** Если сервер Consul делит CPU с тяжелыми процессами, он может не успеть отправить heartbeat.
    ```bash
    # Проверка нагрузки
    top -b -n 1 | grep consul
    # → %CPU < 80% для стабильной работы
    ```
- **Решение:** Используйте NVMe/SSD и установите приоритет процесса (`nice`, `cpulimit` или выделенные инстансы).

### Тюнинг тайм-аутов Raft

Для гео-распределенных кластеров (WAN) может потребоваться увеличение тайм-аутов в конфигурации. По умолчанию `raft_multiplier = 5` (эквивалентно минимальным серверам). Для production рекомендуется `raft_multiplier = 1`:

```hcl
performance {
  raft_multiplier = 1 # Высокопроизводительный режим для production
}
```

**Валидация изменений:**
```bash
# Проверка текущего значения
consul operator raft list-peers
# → Health tracking: LastContact < 200ms

# Применение конфигурации
consul reload
# → Configuration reload triggered

# Мониторинг после изменений
watch -n 1 'consul operator raft list-peers'
# → стабильные значения без flapping
```

### Повышение trailing logs при отставании

Если follower не успевает за лидером из-за большого снапшота и высокой нагрузки записи:

```hcl
raft {
  trailing_logs = 20000 # Увеличить с дефолта 10000
}
```

**Валидация:**
```bash
# Мониторинг метрики
curl -s http://localhost:8500/v1/metrics | grep 'consul.raft.rpc.installSnapshot'
# → частота установки снапшотов должна снизиться

# Проверка trailing logs
consul operator raft list-peers
# → trailing logs <= установленного порога
```
