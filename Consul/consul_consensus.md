# Определения

**Механизм консенсуса** в Consul отвечает за поддержание согласованного (consistent) и отказоустойчивого состояния между серверами кластера. Для этой цели Consul использует протокол **Raft**. Это фундаментальный механизм для обеспечения [высокой доступности (High Availability)](../Concepts/High_Availability/ha_overview.md) в распределенных системах.

Все критические данные — [каталог сервисов](./consul_service_catalog.md), [KV (Key-Value) хранилище](./consul_kv_store.md), ACL (Access Control List — список контроля доступа) и конфигурация Service Mesh — проходят через реплицируемый лог Raft. Это гарантирует их целостность при сбоях отдельных серверов. Общие принципы работы алгоритма описаны в [Алгоритме Raft в etcd](../etcd/raft_consensus.md).

# Основные концепции

## Принципы Raft в Consul

- **Кворум:** Только **серверы** Consul участвуют в Raft-кворуме. Для отказоустойчивости кластера из `N` серверов необходимо, чтобы `(N/2)+1` серверов были работоспособны. Рекомендуемое число серверов — 3 или 5.
- **Лидер и последователи:** В каждый момент времени в кворуме есть только один **лидер** (`Leader`), который принимает все запросы на запись. Остальные серверы являются **последователями** (`Followers`) и пассивно реплицируют данные от лидера.
- **Термы и выборы:** Жизненный цикл кластера разделен на **термы** (`terms`) — периоды времени с монотонно возрастающим номером. Если последователи перестают получать "хартбиты" (heartbeats) от лидера, они инициируют новые выборы, становясь **кандидатами** (`Candidate`).

## Процесс репликации записи

1. Запрос на изменение (например, `consul kv put`) поступает на лидера.
2. Лидер добавляет операцию в свой локальный лог.
3. Лидер рассылает запись (`AppendEntries` RPC — Remote Procedure Call) всем последователям.
4. Последователи подтверждают получение и запись в свой лог.
5. Когда лидер получает подтверждение от большинства (кворума), запись считается **закоммиченной** (`committed`).
6. Лидер применяет изменение к своей конечной машине состояний (state machine) и уведомляет клиента об успехе.

## Безопасность и целостность

- **Leader Safety:** В одном терме не может быть двух лидеров.
- **Split-brain:** При сетевом разделении только та часть кластера, которая сохранила кворум, сможет выбрать лидера.
- **Log Matching:** Если записи в логах разных серверов имеют одинаковый индекс и терм, то все предыдущие записи также совпадают.

## Снапшоты и компакция лога

Чтобы реплицируемый лог не рос бесконечно, Consul периодически создает **снапшоты** (snapshot — снимок текущего состояния) и удаляет старые записи лога (**компакция**). Для резервного копирования используется команда `consul snapshot save`.

# Практические сценарии

## Режимы согласованности чтения

Consul предоставляет три режима для чтения данных через API (Application Programming Interface):

- `default`: Баланс между скоростью и актуальностью. Запрос может быть обслужен любым сервером, если он подтвердил лидерство текущего лидера.
- `stale`: Чтение с любого сервера (включая последователей) без проверки у лидера. Самый быстрый режим (низкая задержка), но может вернуть данные с задержкой в несколько миллисекунд.
- `consistent`: Чтение с обязательной проверкой лидерства через кворум. Гарантирует получение самой последней закоммиченной версии данных.

```bash
# Чтение с гарантированной согласованностью
consul kv get -consistent my-key
```

## Управление через Autopilot

Механизм **Autopilot** (представлен в версии 0.8) автоматизирует обслуживание кластера:
- **Dead Server Cleanup:** Автоматическое удаление неисправных серверов из кворума после таймаута.
- **Server Health Check:** Новые серверы не становятся полноценными участниками кворума (Voters), пока не пройдут период стабилизации.
- **Redundancy Zones (Enterprise):** Учет зон доступности при формировании кворума для исключения выхода из строя большинства при сбое одной стойки/зоны.

## Диагностика кластера

```bash
# Список участников кворума и их статусы
consul operator raft list-peers

# Ручное удаление узла, если Autopilot отключен или не справляется
consul operator raft remove-peer -id <NodeID>
```
