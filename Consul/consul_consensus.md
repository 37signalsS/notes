# Определения

**Механизм консенсуса** в Consul отвечает за поддержание согласованного (consistent) и отказоустойчивого состояния между серверами кластера. Для этой цели Consul использует протокол **Raft**. Это фундаментальный механизм для обеспечения [высокой доступности (High Availability)](../Concepts/High_Availability/ha_overview.md) в распределенных системах.

Все критические данные — [каталог сервисов](./consul_service_catalog.md), [KV-хранилище](./consul_kv_store.md), ACL и конфигурация Service Mesh — проходят через реплицируемый лог Raft. Это гарантирует их целостность при сбоях отдельных серверов. Общие принципы работы алгоритма описаны в [Алгоритме Raft в etcd](../etcd/raft_consensus.md).

# Основные концепции

## Принципы Raft в Consul

- **Кворум:** Только **серверы** Consul участвуют в Raft-кворуме. Для отказоустойчивости кластера из `N` серверов необходимо, чтобы `(N/2)+1` серверов были работоспособны. Рекомендуемое число серверов — **3** или **5**.
- **Лидер и последователи:** В каждый момент времени в кворуме есть только один **лидер** (`Leader`), который принимает все запросы на запись. Остальные серверы являются **последователями** (`Followers`) и пассивно реплицируют данные от лидера.
- **Термы и выборы:** Жизненный цикл кластера разделен на **термы** (`terms`) — периоды времени с монотонно возрастающим номером. Если последователи перестают получать "хартбиты" (heartbeats) от лидера, они инициируют новые выборы, становясь **кандидатами** (`Candidate`). Consul использует рандомизированные таймеры для исключения конфликтов.

## Процесс репликации записи

1. Запрос на изменение (например, `consul kv put`) поступает на лидера.
2. Лидер добавляет операцию в свой локальный лог.
3. Лидер рассылает запись (`AppendEntries` RPC) всем последователям.
4. Последователи подтверждают получение и запись в свой лог.
5. Когда лидер получает подтверждение от большинства (кворума), запись считается **закоммиченной** (`committed`).
6. Лидер применяет изменение к своей конечной машине состояний (state machine) и уведомляет клиента об успехе.

## Безопасность и целостность

- **Leader Safety:** В одном терме не может быть двух лидеров.
- **Split-brain:** При сетевом разделении только та часть кластера, которая сохранила кворум, сможет выбрать лидера.
- **Log Matching:** Если записи в логах разных серверов имеют одинаковый индекс и терм, то все предыдущие записи также совпадают.

## Автоматизация через Autopilot

Механизм **Autopilot** (представлен в версии 0.8) автоматизирует обслуживание кластера на основе параметров здоровья:
- **LastContactThreshold (200ms):** Интервал времени, прошедший с момента последнего контакта сервера с лидером. Если превышен — сервер нездоров.
- **MaxTrailingLogs (250):** Максимальное отставание последователя по количеству записей в логе Raft.
- **ServerStabilizationTime (10s):** Время, в течение которого новый сервер должен оставаться стабильным, прежде чем он будет повышен до статуса «голосующего» (`voter`).
- **CleanupDeadServers:** Автоматическое удаление неисправных серверов из кворума после таймаута.

## Зоны избыточности (Redundancy Zones — Enterprise)

Позволяет распределять серверы по зонам доступности (AZ) для повышения отказоустойчивости:
- В каждой AZ назначается один активный `voter`. Остальные серверы в зоне — `non-voters`.
- При отказе `voter`, Autopilot автоматически повышает одного из `non-voters` в той же AZ до статуса голосующего.
- **Результат:** Защита от сбоя целой зоны без раздувания Raft-кворума до 7+ узлов.

# Практические сценарии

## Режимы согласованности чтения

Consul предоставляет три режима для чтения через API:
- `default`: Баланс. Запрос обслуживается лидером, который подтверждает свое лидерство внутренним тайм-аутом.
- `stale`: Чтение с любого сервера (включая последователей). Самый быстрый режим (низкая задержка), но допускает задержку данных в миллисекунды.
- `consistent`: Чтение с обязательной проверкой лидерства через кворум. Гарантирует абсолютную актуальность.

```bash
# Чтение с гарантированной согласованностью
consul kv get -consistent my-key
```

## Снапшоты и компакция лога

Чтобы лог не рос бесконечно, Consul создает снапшоты (snapshot) и удаляет старые записи лога (компакция).
```bash
# Создание резервной копии состояния кластера
consul snapshot save backup.snap

# Восстановление из снапшота
consul snapshot restore backup.snap
```

## Диагностика кластера

```bash
# Список участников кворума и их статусы
consul operator raft list-peers

# Проверка здоровья глазами Autopilot
consul operator autopilot health
```

# Дополнительная информация

### Устранение неполадок (Troubleshooting)

- **Потеря кворума (Quorum Loss):** Если большинство серверов вышло из строя, кластер перестанет отвечать на запись.
    - **Решение:** Вручную создайте файл `peers.json` в `data_dir` на единственном выжившем сервере, оставив в нем только его ID и адрес, и перезапустите Consul.
- **Задержки Raft (Leader Flapping):** Ищите в логах ошибки `Raft: Heartbeat timeout`. Обычно это вызвано перегрузкой диска (I/O) или CPU.
    - **Рекомендация:** Используйте **NVMe/SSD** для `data_dir` и выделенные ресурсы для серверов Consul.
