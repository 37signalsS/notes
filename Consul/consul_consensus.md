# Определения

**Механизм консенсуса** в Consul отвечает за поддержание согласованного состояния (consistent state) между серверами кластера. Для этой цели Consul использует протокол **Raft**.

Все критичные данные — каталог сервисов, KV-хранилище, ACL, конфигурация Connect — проходят через реплицируемый лог Raft, что гарантирует их отказоустойчивость и целостность.

# Базовые концепции

## Архитектура Raft в Consul

- **Кворум:** Кластер Consul состоит из **серверов** и **клиентов**. Только серверы участвуют в Raft-кворуме. Для отказоустойчивости кластера из `N` серверов необходимо, чтобы `(N/2)+1` серверов были работоспособны. Рекомендуемое число серверов — 3 или 5.
- **Лидер и последователи:** В каждый момент времени в кворуме есть только один **лидер** (`Leader`), который принимает все запросы на запись. Остальные серверы являются **последователями** (`Followers`) и пассивно реплицируют данные от лидера.
- **Термы и выборы:** Жизненный цикл кластера разделен на **термы** (`terms`) — периоды времени с монотонно возрастающим номером. В каждом терме может быть только один лидер. Если последователи перестают получать "хартбиты" от лидера, они инициируют новые выборы, переходя в состояние **кандидата** (`Candidate`).

## Процесс репликации

1.  Клиентский запрос на изменение (например, `consul kv put`) поступает на лидера.
2.  Лидер добавляет операцию в свой локальный лог.
3.  Лидер рассылает запись (`AppendEntries`) всем последователям.
4.  Последователи подтверждают получение записи.
5.  Когда лидер получает подтверждение от большинства (кворума), запись считается **закоммиченной** (`committed`).
6.  Лидер применяет изменение к своей конечной машине состояний (state machine) и уведомляет клиента об успехе.

## Безопасность и целостность

Raft обеспечивает следующие гарантии:
- **Единственность лидера:** В одном терме не может быть двух лидеров.
- **Защита от split-brain:** В случае сетевого разделения только та часть кластера, которая сохранила кворум, сможет выбрать лидера и продолжить обрабатывать запросы на запись. Меньшинство будет отклонять их.
- **Целостность лога:** Записи в логе не могут быть "перезаписаны" или утеряны после коммита.

## Снапшоты и компакция лога

Чтобы реплицируемый лог не рос бесконечно, Consul периодически выполняет:
- **Снапшоты:** Создает снимок текущего состояния (state machine).
- **Компакцию:** Удаляет старые записи лога, которые уже были включены в снапшот.

Отстающие или новые серверы могут быстро восстановить свое состояние, получив последний снапшот от лидера, а затем применив недостающие записи из лога.

# Практические сценарии

## Режимы согласованности чтения

Consul предоставляет несколько режимов для чтения данных:
- `default`: Оптимизированный режим, балансирующий между скоростью и актуальностью.
- `stale`: Чтение с любого сервера без проверки у лидера. Самый быстрый, но может вернуть устаревшие данные.
- `consistent`: Чтение, направленное к лидеру. Гарантирует получение самой последней закоммиченной версии данных, но имеет большую задержку.

```bash
# Чтение с настройками по умолчанию
consul kv get my-key

# Чтение с гарантированной согласованностью
consul kv get -consistent my-key
```

## Управление кластером

```bash
# Посмотреть список участников Raft-кворума и текущего лидера
consul operator raft list-peers
```

## Конфигурация сервера

Пример минимальной конфигурации для серверного узла:
```json
{
  "server": true,
  "bootstrap_expect": 3,
  "datacenter": "dc1",
  "retry_join": ["10.0.1.1", "10.0.1.2", "10.0.1.3"]
}
```
- `bootstrap_expect`: Указывает Consul ожидать указанное количество серверов перед тем, как инициировать кворум.

Современные версии Consul включают механизм **Autopilot**, который автоматизирует многие задачи по управлению кластером, такие как очистка неработающих серверов и управление обновлениями.
