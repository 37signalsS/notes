# Определения

**Service Catalog** (Каталог служб) в Consul — это централизованный реестр, который хранит информацию о всех зарегистрированных сервисах, их экземплярах (инстансах), местоположении (IP, порт) и состоянии здоровья. Это ядро механизма Service Discovery.

# Базовые концепции

## Ключевые сущности

| Сущность | Описание | Ключевые поля |
| :--- | :--- | :--- |
| **Datacenter (DC)** | Логическая группа узлов, обычно соответствующая физическому ЦОД или региону облака. | `name` |
| **Node** | Узел (хост), на котором запущен агент Consul и зарегистрированы сервисы. | `Node`, `Address`, `Meta` |
| **Service** | Экземпляр приложения, доступный по сети. | `Name`, `ID`, `Address`, `Port`, `Tags`, `Meta` |
| **Check** | Проверка состояния, привязанная к сервису или узлу. | `Status`, `Type`, `Interval` |
| **Partition/Namespace** | Административные границы для изоляции каталогов (функция Consul Enterprise). | `namespace`, `partition` |

**Name vs ID:**
- `Name` — логическое имя сервиса (например, `api-gateway`).
- `ID` — уникальный идентификатор конкретного экземпляра (например, `api-gateway-1`).
Несколько экземпляров с одинаковым `Name` образуют пул для балансировки нагрузки.

## Регистрация сервисов

Сервисы могут быть зарегистрированы несколькими способами:
- **Статически:** через конфигурационные файлы агента (`/etc/consul.d/`).
- **Динамически:** через HTTP API или CLI локального агента.
- **Автоматически:** через интеграции, например, с Kubernetes (синхронизация с `kube-dns`) или Nomad.

### Пример регистрации (HCL)

Файл `web.hcl`:
```hcl
service {
  name    = "web"
  id      = "web-1"
  address = "10.0.1.12"
  port    = 8080
  tags    = ["v1", "blue"]
  meta    = { team = "app", tier = "frontend" }

  check {
    name     = "web-health"
    http     = "http://10.0.1.12:8080/health"
    interval = "10s"
    timeout  = "2s"
  }
}
```
Регистрация через CLI: `consul services register ./web.hcl`

Теги (`Tags`) и метаданные (`Meta`) являются мощным инструментом для фильтрации и управления трафиком.

# Практические сценарии

## Доступ к каталогу

### Через HTTP API
- **Все сервисы:** `GET /v1/catalog/services`
- **Экземпляры сервиса:** `GET /v1/catalog/service/<service_name>`
- **"Здоровые" экземпляры:** `GET /v1/health/service/<service_name>`

По умолчанию API-запросы могут обслуживаться в режиме `stale` (нестрогая согласованность) для скорости. Для получения гарантированно актуальных данных добавьте параметр `?consistent`.

### Через CLI
- **Список сервисов:** `consul catalog services`
- **Узлы с сервисом:** `consul catalog nodes -service <service_name>`
- **"Здоровые" экземпляры:** `consul health service <service_name> --passing`

## DNS-интерфейс

Агент Consul предоставляет DNS-сервер (по умолчанию на порту `8600`), который позволяет обнаруживать сервисы через стандартные DNS-запросы.

- **A-записи:** `web.service.consul` вернет IP-адреса "здоровых" экземпляров.
- **SRV-записи:** `_web._tcp.service.consul` вернет IP, порты, веса и приоритеты.

Примеры запросов:
```bash
# A-запись
dig @127.0.0.1 -p 8600 web.service.consul

# SRV-запись
dig @127.0.0.1 -p 8600 _web._tcp.service.consul SRV
```
DNS-ответы по умолчанию включают только экземпляры с `passing` статусом проверок.

## Фильтрация

- **По тегам:** `v1.web.service.consul` вернет только экземпляры с тегом `v1`.
- **По состоянию:** DNS по умолчанию возвращает только `passing`. API позволяет запрашивать все и фильтровать на стороне клиента.
- **По метаданным:** API поддерживает язык выражений `filter` для гибкой фильтрации по полям `Meta`.
