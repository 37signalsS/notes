# Определения

**Каталог служб (Service Catalog)** в Consul — это централизованный реестр, содержащий информацию обо всех зарегистрированных сервисах, их экземплярах (инстансах), метаданных, сетевых адресах и [статусах работоспособности](./consul_health_checks.md). Каталог является фундаментом для механизмов обнаружения сервисов (Service Discovery) и управления связностью в распределенных системах.

В современных версиях (Consul 1.22+) каталог перешел на архитектуру **Catalog v2**, которая разделяет понятия "сервис" и "нагрузка" (workload), позволяя более гибко управлять мультипортовыми приложениями и мультикластерными топологиями.

# Основные концепции

## Ключевые сущности каталога

| Сущность | Описание | Основные поля |
| :--- | :--- | :--- |
| **Datacenter (DC)** | Логическая группа узлов с низкой сетевой задержкой. | `name` |
| **Admin Partition** | (Enterprise) Высший уровень изоляции для разделения административных границ. | `name` |
| **Namespace** | Логическая изоляция внутри раздела для разных команд или окружений. | `name`, `partition` |
| **Workload** | (Catalog v2) Абстракция над экземпляром приложения (например, Pod в K8s). | `WorkloadIdentity` |
| **Node** | Узел (хост), на котором запущен агент Consul. | `Node`, `Address`, `Meta` |
| **Service** | Логическое определение приложения, объединяющее один или несколько портов. | `Name`, `ID`, `Ports`, `Tags`, `Meta` |

## Мультипортовые сервисы (Catalog v2)

Начиная с версии 1.22, один экземпляр сервиса может иметь несколько именованных портов. Это позволяет обращаться к `http`, `grpc` или `metrics` одного и того же приложения через разные DNS-имена, не регистрируя сервис трижды.

## Группы идентичности (Sameness Groups)

Механизм логического объединения идентичных сервисов, распределенных по разным разделам (Partitions) или пиринговым кластерам (Peers).
- **Failover:** Автоматическое переключение трафика на резервные инстансы в другом кластере при сбое локальных.
- **Упрощение:** Позволяет клиентам использовать единое DNS-имя для доступа к глобально распределенному сервису.

## Регистрация и синхронизация

1. **Динамическая регистрация:** Через HTTP API локального агента (`/v1/agent/service/register`).
2. **Статическая конфигурация:** Через HCL-файлы в директории конфигурации агента.
3. **Catalog Sync:** Автоматическая синхронизация из внешних оркестраторов (Kubernetes через `consul-k8s`).
4. **Антиэнтропия:** Процесс постоянной сверки локального состояния агента с глобальным каталогом для исправления расхождений.

# Практические сценарии

## Регистрация мультипортового сервиса (HCL)

Пример конфигурации современного приложения (`order-service.hcl`):

```hcl
service {
  name    = "order-service"
  id      = "order-1"
  address = "10.42.0.25"
  
  # Определение списка портов (Consul 1.22+)
  ports = [
    {
      name    = "http"
      port    = 8080
      default = true  # Основной порт для обычных DNS-запросов
    },
    {
      name = "metrics"
      port = 9090
    },
    {
      name = "admin"
      port = 9500
    }
  ]

  tags = ["v2", "prod"]
  meta = { team = "billing" }

  check {
    name     = "HTTP Health Check"
    http     = "http://10.42.0.25:8080/health"
    interval = "10s"
  }
}
```

## Способы обнаружения

### DNS Интерфейс (Рекомендуемый)

Consul предоставляет встроенный DNS-сервер (порт 8600) с поддержкой новых типов запросов:
- **Стандартный:** `order-service.service.consul` (вернет IP и `default` порт).
- **Именованный порт:** `metrics.order-service.service.consul` (вернет порт 9090).
- **Sameness Group:** `order-service.billing-group.sg.consul` (глобальный поиск инстансов).
- **SRV-записи:** `_http._tcp.order-service.service.consul` (метаданные о порте и весе).

### HTTP API

- **Все инстансы сервиса:** `GET /v1/catalog/service/order-service`
- **Фильтрация по метаданным:**
```bash
curl "http://localhost:8500/v1/catalog/service/order-service?filter=Service.Meta.team==\"billing\""
```
- **Consistent чтение:** Используйте `?consistent`, чтобы гарантированно получить данные от лидера Raft.

## Подготовленные запросы (Prepared Queries)

Позволяют создавать шаблоны запросов со сложной логикой переключения (failover).

```json
{
  "Name": "order-geo-failover",
  "Service": {
    "Service": "order-service",
    "OnlyPassing": true,
    "SamenessGroup": "global-order-group"
  },
  "DNS": { "TTL": "10s" }
}
```
Запрос через DNS: `order-geo-failover.query.consul`.

# Лучшие практики

- **Используйте ID для инстансов:** Всегда явно задавайте `id` (например, включая имя хоста), чтобы избежать конфликтов при перезапуске сервиса.
- **DNS Caching:** Настраивайте минимальный TTL (1–5 сек) на стороне клиентов, чтобы обеспечить быструю реакцию на изменения в каталоге.
- **DNS Views (Enterprise):** Используйте для разделения ответов DNS в зависимости от IP-адреса источника запроса.
- **Здоровье прежде всего:** Обнаружение сервисов по умолчанию должно использовать фильтр `?passing`, чтобы не направлять трафик на неисправные узлы.
