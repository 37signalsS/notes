# Определения

**Проверки состояния (Health Checks)** в Consul — это механизм непрерывной оценки работоспособности сервисов и узлов. На основе результатов этих проверок Consul динамически обновляет [каталог служб](./consul_service_catalog.md), влияя на маршрутизацию трафика.

# Основные концепции

## Статусы проверок

Каждая проверка может находиться в одном из следующих состояний:

- `passing` (зеленый): Сервис работает корректно.
- `warning` (желтый): Сервис работает, но есть проблемы (например, высокая нагрузка). Трафик продолжает поступать.
- `critical` (красный): Сервис неисправен. Consul автоматически исключает его из списков, возвращаемых через DNS и API (для `health` эндпоинта).
- `unknown`: Статус проверки неизвестен (начальное состояние).

## Типы проверок

Consul поддерживает несколько типов проверок, позволяя выбрать наиболее подходящий для конкретного сервиса:

| Тип | Назначение | Пример использования |
| :-- | :--- | :--- |
| **HTTP** | Проверка ответа веб-сервиса по указанному URL. | `GET /health` должен вернуть `200 OK`. |
| **TCP** | Проверка доступности TCP-порта. | Убедиться, что порт базы данных открыт. |
| **gRPC** | Проверка gRPC-сервиса через стандартный health checking protocol. | `grpc.health.v1.Health/Check`. |
| **Script**| Выполнение внешнего скрипта. Статус определяется по коду возврата. | Проверка свободного места на диске или валидности лицензии. |
| **TTL** | "Push" модель: сервис должен сам периодически отправлять "хартбиты" (heartbeats). | Мониторинг асинхронных `cron` задач. |
| **Alias** | Агрегирование статуса другого узла или сервиса. | Статус веб-сервера зависит от статуса его базы данных. |

## Принцип работы

1. **Локальное выполнение:** Проверки настраиваются в определении сервиса и выполняются локальным агентом Consul.
2. **Обновление статуса:** Агент обновляет статус проверки локально.
3. **Распространение:** Информация о статусах распространяется по кластеру через gossip-протокол и реплицируется на серверы.
4. **Реакция:** Клиенты, запрашивающие сервис, получают только "здоровые" экземпляры.

# Практические сценарии

## Настройка отказоустойчивой проверки

Пример HTTP-проверки с параметрами для защиты от ложных срабатываний:

```hcl
service {
  name = "payments"
  port = 8080
  checks = [
    {
      name = "http-ready-check",
      http = "http://127.0.0.1:8080/health/ready",
      interval = "10s",
      timeout = "2s",

      // Требуется 2 успешные проверки подряд, чтобы перейти в 'passing'
      success_before_passing = 2,

      // Требуется 3 неудачные проверки подряд, чтобы перейти в 'critical'
      failures_before_critical = 3,

      // Автоматически дерегистрировать сервис, если он неисправен более 1 минуты
      deregister_critical_service_after = "1m"
    }
  ]
}
```

## Разделение проверок Liveness и Readiness

- **Liveness (жизнеспособность):** Простая проверка, что процесс запущен и отвечает. Отказ означает, что контейнер нужно перезапустить.

  ```hcl
  check {
    name = "api-liveness"
    http = "http://localhost/live"
    interval = "5s"
  }
  ```

- **Readiness (готовность):** Более сложная проверка, что сервис готов принимать трафик (например, есть подключение к БД). Отказ означает, что сервис нужно временно убрать из балансировки.

  ```hcl
  check {
    name = "api-readiness"
    http = "http://localhost/ready"
    interval = "10s"
  }
  ```
