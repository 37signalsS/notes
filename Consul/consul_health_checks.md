# Определения

**Health checks** в Consul — это механизм оценки работоспособности сервисов и инфраструктурных компонентов. На основе этих проверок принимаются решения о маршрутизации трафика, что позволяет системе динамически адаптироваться к сбоям.

# Базовые концепции

## Задачи Health Checks

- **Предотвращение трафика на нерабочие инстансы:** Исключение из ротации неготовых или деградирующих сервисов.
- **Ускорение обнаружения отказов:** Быстрая реакция на сбои и сокращение времени восстановления (MTTR).
- **Поддержка стратегий развертывания:** Возможность перевода сервиса в режим обслуживания (`maintenance mode`) без изменения кода.
- **Улучшение наблюдаемости:** Статусы `passing`, `warning` и `critical` сигнализируют о состоянии сервиса до его полного отказа.

## Принцип работы

1.  **Локальное выполнение:** Проверки выполняются агентом Consul локально, рядом с сервисом.
2.  **Динамические статусы:** Каждая проверка имеет один из трех статусов: `passing` (работает), `warning` (предупреждение) или `critical` (сбой).
3.  **Исключение из DNS/API:** Инстансы со статусом `critical` по умолчанию исключаются из ответов DNS и HTTP API.
4.  **Репликация состояния:** Информация о статусах распространяется по кластеру через gossip-протокол.

## Типы проверок

| Тип | Ключи в определении | Назначение | Пример |
| :-- | :--- | :--- | :--- |
| **HTTP** | `http`, `method`, `header`, `interval`, `timeout` | Веб-сервисы с эндпоинтом `/health` | Проверка HTTP-статуса `200 OK` и содержимого ответа. |
| **TCP** | `tcp`, `interval`, `timeout` | Простая проверка доступности TCP-порта | Проверка, открыт ли порт, без анализа логики приложения. |
| **gRPC** | `grpc`, `grpc_use_tls`, `interval` | gRPC-сервисы | Быстрая проверка через стандартный gRPC health checking protocol. |
| **Script**| `script`, `interval`, `timeout` | Сложные, кастомные проверки | Проверка свободного места на диске, доступности зависимостей, валидности лицензий. |
| **TTL** | `ttl` (обновляется через API) | Push-модель для асинхронных задач | Сервис самостоятельно отправляет "хартбиты", подтверждая свою работоспособность. |

# Практические сценарии

## Настройка проверок

- **Интервалы и таймауты:** Рекомендуется устанавливать интервалы (`interval`) в диапазоне `5-10s` и таймауты (`timeout`) `1-2s` для быстрого обнаружения сбоев.
- **Дебаунс:** Параметры `success_before_passing` и `failures_before_critical` помогают избежать ложных срабатываний при кратковременных сбоях.
- **Автоматическая дерегистрация:** Параметр `deregister_critical_service_after` удаляет сервис из каталога, если он долгое время находится в статусе `critical`.
- **Разделение проверок:**
    - **Liveness:** Проверяет, что процесс запущен и не завис.
    - **Readiness:** Убеждается, что сервис готов принимать трафик (например, есть подключение к БД).

## Пример: HTTP-проверка

Файл определения сервиса `payments.hcl`:
```json
{
  "service": {
    "name": "payments",
    "port": 8080,
    "checks": [
      {
        "name": "http-ready",
        "http": "http://127.0.0.1:8080/health/ready",
        "method": "GET",
        "interval": "10s",
        "timeout": "2s",
        "success_before_passing": 2,
        "failures_before_critical": 3,
        "deregister_critical_service_after": "1m"
      }
    ]
  }
}
```

Минимальный HTTP-эндпоинт на Python:
```python
from http.server import BaseHTTPRequestHandler, HTTPServer
import socket

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path == "/health/ready":
            try:
                # Проверяем доступность зависимости (например, БД)
                socket.create_connection(("db.internal", 5432), timeout=0.2).close()
                self.send_response(200)
                self.end_headers()
                self.wfile.write(b"OK")
            except Exception:
                self.send_response(503)
                self.end_headers()
                self.wfile.write(b"NOT READY")
        else:
            self.send_response(404)
            self.end_headers()

HTTPServer(("0.0.0.0", 8080), Handler).serve_forever()
```
Эта конфигурация гарантирует, что Consul будет направлять трафик только на экземпляры, которые действительно готовы к работе.
