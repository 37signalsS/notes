# Определения

**Проверки состояния (Health Checks)** в Consul — это механизм непрерывного мониторинга работоспособности узлов и сервисов. На основе результатов этих проверок Consul динамически обновляет [каталог служб](./consul_service_catalog.md), исключая неисправные экземпляры из пула балансировки трафика. Проверки состояния являются фундаментом для реализации паттернов отказоустойчивости и [наблюдаемости (Observability)](../Concepts/Observability_and_Monitoring/observability_definitions.md).

# Основные концепции

## Статусы проверок

Результат каждой проверки относится к одному из четырех состояний:

- `passing`: Компонент полностью работоспособен. Только такие экземпляры возвращаются через DNS-интерфейс.
- `warning`: Сервис работает с отклонениями (например, высокая нагрузка или частичная потеря функционала). Трафик продолжает поступать, но статус служит сигналом для систем мониторинга.
- `critical`: Сервис неисправен. Consul автоматически исключает его из результатов DNS и фильтрованных API-запросов.
- `unknown`: Статус не определен (например, во время инициализации или при сбое самого механизма проверки).

## Уровни проверок

1. **Проверка узла (Node Check):** Привязывается к хосту. Если проверка узла переходит в `critical`, все сервисы на этом узле также помечаются как неисправные. Типичный пример — проверка свободного места на диске или доступности SSH.
2. **Проверка сервиса (Service Check):** Привязывается к конкретному инстансу приложения. Влияет только на доступность этого сервиса в каталоге.

## Пороги срабатывания (Thresholds)

Для предотвращения "дребезга" (flapping) — ситуации, когда сервис быстро меняет статус — используются пороги:
- `success_before_passing`: Количество последовательных успешных проверок для перехода в статус `passing`.
- `failures_before_critical`: Количество последовательных неудачных проверок для перехода в статус `critical`.

## Идентификация проверок

- **Name:** Понятное описание проверки (например, "HTTP Health Check").
- **ID:** Уникальный идентификатор в рамках узла. Если не указан, совпадает с `Name`. Рекомендуется явно указывать `ID` для управления через API.

# Типы проверок

Consul поддерживает различные методы мониторинга, от простых сетевых проверок до сложных скриптов:

| Тип | Назначение | Особенности |
| :--- | :--- | :--- |
| **HTTP/HTTPS** | Опрос эндпоинта. | Код 2xx — `passing`, 429 — `warning`, остальные — `critical`. |
| **TCP** | Проверка доступности порта. | Успешное TCP-соединение — `passing`. |
| **gRPC** | Нативная проверка gRPC-сервисов. | Использует стандарт `grpc.health.v1`. Требует указания `grpc_use_tls`. |
| **H2ping** | Проверка через HTTP/2. | Использует HTTP/2 PING-фреймы для минимизации нагрузки. |
| **TTL** | "Push"-модель (сервис шлет статус). | Идеально для Cron-задач и асинхронных процессов. |
| **Alias** | Зависимость от другого сервиса. | Статус синхронизируется с указанным `service_id` или `node_id`. |
| **Script/Args** | Выполнение внешней команды. | Код возврата: 0 (`passing`), 1 (`warning`), остальные (`critical`). |
| **Docker** | Команда внутри контейнера. | Выполняется через `docker exec`. |
| **OSService** | Проверка системной службы. | Нативная поддержка SystemD и Windows Services. |

## Проверки в Service Mesh (Application Health Checks)

В контексте Service Mesh (Consul Connect) проверки могут выполняться прокси-сервером (Envoy). Это позволяет проверять работоспособность приложения через тот же сетевой путь, по которому идет основной трафик, учитывая настройки mTLS и конфигурацию сети Mesh.

# Практические сценарии

## Настройка отказоустойчивой HTTP-проверки

Пример конфигурации сервиса на языке HCL (HashiCorp Configuration Language) с защитой от ложных срабатываний:

```hcl
service {
  name = "api-gateway"
  port = 8080
  checks = [
    {
      id      = "api-health"
      name    = "HTTP Readiness Probe"
      http    = "http://localhost:8080/ready"
      method  = "GET"
      interval = "10s"
      timeout  = "2s"

      // Статус станет passing только после 2 успешных попыток
      success_before_passing = 2
      
      // Статус станет critical только после 3 неудач подряд
      failures_before_critical = 3

      // Автоматическое удаление сервиса из каталога через 30 минут неисправности
      deregister_critical_service_after = "30m"
    }
  ]
}
```

## Использование TTL для фоновых задач

Для задач без сетевого порта сервис должен периодически отправлять сигнал "живучести".

```hcl
check {
  id    = "backup-job"
  name  = "Nightly Backup Status"
  notes = "Обновляется скриптом бэкапа"
  ttl   = "25h" 
}
```

Обновление статуса через API:
```bash
curl http://localhost:8500/v1/agent/check/pass/backup-job?note="Бэкап завершен"
```

## Автоматическая дерегистрация

Параметр `deregister_critical_service_after` предотвращает накопление "мертвых" записей в динамических средах (Docker/Kubernetes). 
- Рекомендуемое значение: от `1m` до `24h`.
- Если агент Consul завершает работу некорректно, записи будут удалены по истечении таймаута сессии.
