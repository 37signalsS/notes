# Архитектура Consul

**Актуально для:** Consul 2.0.x / 1.22.x / 1.21.x / 1.20.x / 1.19.x

## Определения

**Архитектура Consul** базируется на децентрализованной агентной модели и протоколах распределенного консенсуса. Система разделена на две функциональные плоскости:
- **Control Plane (Плоскость управления):** Совокупность серверов Consul, которые хранят состояние кластера, управляют конфигурациями и обеспечивают консенсус.
- **Data Plane (Плоскость данных):** Совокупность агентов, sidecar-прокси (Envoy) и компонентов Dataplane, которые обеспечивают фактическую передачу трафика, регистрацию сервисов и выполнение проверок здоровья.

**Ключевые сущности:**
- **Агент (Agent):** Основной демон Consul, работающий на каждом узле. Может функционировать в режиме клиента или сервера.
- **Дата-центр (Datacenter):** Логическая единица инфраструктуры с низкой сетевой задержкой, в рамках которой работает Raft-кворум серверов.
- **Каталог (Catalog):** Агрегированное представление состояния всех сервисов и узлов, формируемое на основе данных от агентов.

## Основные компоненты

### Роли узлов и режимы работы

Consul поддерживает три модели развертывания компонентов управления:

1. **Сервер (Server):**
   - **Хранение данных:** Содержит авторитетную копию [каталога сервисов](./consul_service_catalog.md), [KV-хранилища](./consul_kv_store.md) и ACL.
   - **Консенсус:** Участвует в [алгоритме Raft](./consul_consensus.md) для репликации логов и выбора лидера.
   - **Масштабирование:** Рекомендуется 3 или 5 серверов. Большее количество замедляет запись из-за Raft-кворума.
   - **Порт:** `8300` (TCP) для RPC-взаимодействия.

2. **Клиент (Agent Client — Legacy):**
   - **Локальный мониторинг:** Выполняет [проверки состояния (Health Checks)](./consul_health_checks.md) и кэширует данные для снижения нагрузки на серверы.
   - **Антиэнтропия:** Периодически синхронизирует локальное состояние с серверами для устранения расхождений.
   - **Интерфейс:** Предоставляет API на `127.0.0.1:8500`.

3. **Consul Dataplane (Modern/Agentless):**
   - **Назначение:** Заменяет клиентские агенты в средах вроде Kubernetes или на выделенных серверах.
   - **Механизм:** Envoy-прокси подключается напрямую к серверам Consul по gRPC (порт 8502).
   - **Преимущество:** Устраняет необходимость в Gossip-трафике между тысячами узлов и упрощает sidecar-инъекцию.

### Кэширование на стороне агента (Agent Caching)

Кэширование на агентах — это критический механизм обеспечения высокой доступности (HA) и производительности. Оно позволяет приложениям выполнять обнаружение сервисов (Service Discovery), даже если агент полностью изолирован от серверов Consul (например, при сетевом разрыве).

#### 1. Механизм Background Refresh

Используется по умолчанию для большинства запросов к каталогу и здоровью сервисов (например, `/v1/health/service/:service`).

- **Принцип работы:** При первом запросе агент инициирует блокирующий запрос к серверу и сохраняет результат в локальной памяти. В дальнейшем агент поддерживает актуальность данных в фоновом режиме, обновляя их сразу после получения уведомления от сервера об изменениях.
- **HA при изоляции:** Если связь с серверами потеряна, агент продолжает отдавать последние известные данные из кэша.
- **Срок жизни (TTL):** По умолчанию записи хранятся до **3 суток (72 часа)**. Это позволяет системе пережить длительные аварии на контрольном слое.
- **Заголовок `Age`:** В ответе API агент передает время (в секундах) с момента последнего успешного обновления данных от сервера.

#### 2. Simple Caching и `stale-if-error`

Применяется для эндпоинтов, не поддерживающих фоновое обновление (например, Prepared Queries).

- **`max-age`:** Определяет время, в течение которого данные в кэше считаются «свежими».
- **`stale-if-error`:** Директива, указывающая агенту: *«Если `max-age` истек, но серверы недоступны или вернули ошибку, продолжай отдавать старые данные в течение X секунд»*.
- **Преимущество:** Предотвращает возврат ошибки 500 клиентскому приложению при кратковременных сбоях сети.

#### 3. Рекомендации для Senior-инженеров

Для реализации паттерна **Fail-static** (сохранение работоспособности на старых данных при аварии):
1. **Всегда используйте `?cached`:** Приложения должны запрашивать данные через локальный агент с этим параметром, чтобы задействовать кэш.
2. **Настройка `reconnect_timeout`:** Убедитесь, что таймаут переподключения агента к кластеру соответствует или превышает время жизни кэша (72ч), чтобы узлы не удалялись из каталога раньше, чем восстановится связь.
3. **Мониторинг задержки:** Отслеживайте заголовок `Age` в ответах discovery-запросов. Если значение растет линейно — узел находится в изоляции.

## Сетевые протоколы и порты

### Таблица портов

| Порт | Протокол | Назначение |
| :--- | :--- | :--- |
| **8300** | TCP | Server RPC: коммуникация Server-to-Server и Client-to-Server. |
| **8301** | TCP/UDP | LAN Gossip: обмен данными о состоянии узлов внутри дата-центра. |
| **8302** | TCP/UDP | WAN Gossip: федерация и обмен данными между дата-центрами. |
| **8500** | TCP | HTTP API: доступ к управлению и UI. |
| **8501** | TCP | HTTPS API: защищенный интерфейс (рекомендуется для Production). |
| **8502** | TCP | gRPC API: основной порт для Consul Dataplane и xDS (Envoy). |
| **8600** | TCP/UDP | DNS Interface: обнаружение сервисов через DNS. |

## Безопасность и шифрование

Consul разделяет безопасность на два уровня: **Connect CA** (для [Service Mesh](./consul_service_mesh.md)) и **Agent TLS** (для защиты RPC, HTTPS и Gossip между агентами).

### Механизм auto_encrypt

Позволяет клиентам автоматически получать свои TLS-сертификаты от серверов Consul, упрощая управление PKI в динамических средах.

#### Конфигурация Сервера

Серверы должны иметь настроенный CA и разрешать выпуск сертификатов для клиентов.
```hcl
tls {
  defaults {
    ca_file   = "/opt/consul/tls/consul-agent-ca.pem"
    cert_file = "/opt/consul/tls/server.pem"
    key_file  = "/opt/consul/tls/server-key.pem"
    verify_incoming = true
    verify_outgoing = true
  }
}

auto_encrypt {
  allow_tls = true
}
```

#### Конфигурация Клиента

Клиенту достаточно иметь только файл корневого CA для проверки подлинности серверов при первом подключении.
```hcl
tls {
  defaults {
    ca_file         = "/opt/consul/tls/consul-agent-ca.pem"
    verify_outgoing = true
  }
}

auto_encrypt {
  tls = true
}
```

### Ротация сертификатов Agent TLS (Step-by-Step)

Для обновления CA без простоя кластера используется метод «комбинированного бандла».

1. **Генерация нового CA:** Создайте новые файлы `new-ca.pem` и `new-ca-key.pem`.
2. **Создание бандла:** Объедините новый и старый CA в один файл:
   `cat new-ca.pem old-ca.pem > combined-ca.pem`
3. **Обновление серверов:**
   - Разверните `combined-ca.pem` на все серверы.
   - Обновите `ca_file` в конфиге и выполните rolling restart (сначала Follower, затем Leader).
4. **Обновление клиентов:**
   - Если используется `auto_encrypt`, клиенты получат новый бандл автоматически.
   - Иначе — повторите шаг 3 для всех клиентов.
5. **Выпуск новых сертификатов:** Сгенерируйте сертификаты узлов, подписанные **новым CA**, и разверните их на агенты.
6. **Финальный рестарт:** Выполните rolling restart всех узлов. Теперь они используют новые сертификаты, доверяя им через новый CA в бандле.
7. **Очистка:** Удалите старый CA из `combined-ca.pem` и выполните финальный reload конфигурации.

### Механизмы Gossip (Serf)

Consul использует gossip-протокол на базе библиотеки Serf, реализующей протокол **SWIM** (Scalable Weakly-consistent Infection-style Process Group Membership protocol).
- **Масштабируемость:** Нагрузка на сеть от Gossip-протокола является константной (O(1)) для каждого узла, независимо от общего размера кластера.
- **LAN Gossip:** Использует SWIM для обнаружения сбоев агентов за секунды через периодические пинги и косвенные проверки (indirect probes).
- **WAN Gossip:** Связывает серверы разных ДЦ. По этому каналу передаются данные о доступности удаленных регионов и осуществляется пересылка запросов между дата-центрами.

### Шифрование Gossip (Gossip Encryption)

Для обеспечения безопасности Gossip-трафика (LAN и WAN) Consul использует симметричное шифрование.
- **Алгоритм:** Используется **AES-256-GCM**, что обеспечивает как конфиденциальность, так и проверку целостности сообщений.
- **Общий ключ:** Все агенты в кластере должны использовать один и тот же 32-байтовый ключ (Base64).
- **Защита:** Шифрование предотвращает перехват данных о состоянии узлов (Service Discovery) и несанкционированное присоединение узлов к кластеру.
- **Влияние на производительность:** Современные процессоры с поддержкой AES-NI выполняют шифрование с минимальными накладными расходами.

## Внутренние механизмы

### Антиэнтропия (Anti-entropy)

Механизм автоматического исправления расхождений между локальным состоянием агента и глобальным каталогом на серверах.
- **Синхронизация:** Агент периодически вычисляет хэш своего локального состояния (сервисы, проверки) и сравнивает его с хэшем на сервере.
- **Конфликты:**
    - Сервер считается авторитетным источником для **Каталога** (реестра узлов и сервисов).
    - Агент считается авторитетным источником для **Статуса проверок здоровья** (Health Checks), так как он выполняет их локально.
- **Anti-entropy Sync:** Если хэши не совпадают, агент отправляет обновленное состояние через RPC.

### Многопользовательская изоляция (Enterprise)

Для крупных организаций Consul предоставляет механизмы логического разделения ресурсов, глубоко интегрированные с **[системой ACL](./consul_acl.md)**:
- **Namespaces (Пространства имен):** Позволяют изолировать сервисы, политики ACL и KV-ключи. Команды могут использовать одинаковые имена сервисов в разных неймспейсах без конфликтов.
- **Admin Partitions (Административные разделы):** Обеспечивают более жесткую изоляцию на уровне каталога и сетевых областей. Разделы используют общие серверы (Control Plane) и Raft-кворум, но имеют полностью независимые пространства имен и сервисные каталоги.

### Стриминг (Streaming)

В Consul 1.9.0 был представлен механизм **Streaming** (на базе gRPC) как замена блокирующим запросам через HTTP Long Polling. В последующих релизах поддержка streaming была расширена на дополнительные эндпоинты.
- **Оптимизация:** Вместо открытия тысяч HTTP Long Polling соединений, агенты поддерживают один gRPC поток. Сервер транслирует изменения только при их возникновении.
- **Производительность:** Снижает нагрузку на CPU серверов и задержки в обновлении состояния прокси (Envoy) в 10–20 раз.
- **Включение:** Для клиентов используется параметр `use_streaming_backend`. Для серверов — `rpc.enable_streaming`.

### Топологии и масштабирование

Consul хорошо масштабируется до тысяч узлов, но при росте кластера возникают специфические нагрузки на Control Plane.

#### Лимиты и рекомендации

- **Размер ДЦ:** Рекомендуемый «мягкий» лимит — **5000 узлов** на один дата-центр. При превышении этого порога нагрузка на Gossip и CPU серверов возрастает экспоненциально.
- **Масштабирование чтения:** Для обработки миллионов запросов на обнаружение используйте **`stale` чтение**. Это позволяет распределить нагрузку на чтение между всеми серверами (включая фолловеров), снижая давление на Лидера.

#### Вызовы при масштабировании (Scalability Challenges)

1.  **Нагрузка от Антиэнтропии:**
    При росте количества клиентов тысячи агентов одновременно выполняют сверку состояния (sync). Это может вызвать всплески CPU на Лидере Raft, так как каждый sync требует обработки и записи в каталог.
2.  **Шторм Gossip-трафика:**
    В крупных кластерах стандартный интервал Gossip (`200ms`) может создавать заметную нагрузку на сеть. Для кластеров > 5000 узлов требуется увеличение интервалов и тюнинг параметров `memberlist`.
3.  **IO-нагрузка от Raft-снимков:**
    Если в кластере много записей (частые смены статусов, обновления KV), Consul часто создает снимки состояния (FSM snapshots) на диск. Слишком частая запись больших снимков вызывает IO-задержки, что может привести к потере лидерства.

### Подготовленные запросы (Prepared Queries)

Позволяют определять сложные правила поиска сервисов на стороне сервера:
- **Failover:** Автоматическое переключение на другой ДЦ, если локальный сервис недоступен.
- **Фильтрация:** Поиск по тегам, метаданным или статусу здоровья через единый алиас.
- **Пример:** Вызов `query-name.query.consul` вернет ближайший здоровый инстанс согласно политике.

### Блокирующие запросы (Blocking Queries)

Используют заголовок `X-Consul-Index` для получения мгновенных уведомлений об изменениях данных в KV или каталоге.
- Если индекс в запросе совпадает с текущим индексом сервера, запрос "зависает" до изменения данных или таймаута (по умолчанию 5 минут).
- При использовании streaming бэкенда в ответе появляется заголовок `X-Consul-Query-Backend: streaming`.

### Watches и Events

- **Watch:** Высокоуровневая обертка, запускающая `handler` (скрипт или HTTP) при изменении типа данных (nodes, service, checks, key, keyprefix).
- **Custom Events:** Рассылка легковесных уведомлений по всему кластеру через Gossip. Не сохраняются в Raft, подходят для триггеров деплоя или очистки кэша.

## Практические сценарии

### 1. Базовый кластер (3 сервера)

Минимальный отказоустойчивый кластер Consul состоит из трех серверов, распределенных по разным Availability Zones.

```bash
# Сервер 1 (bootstrapping)
consul agent -server -bootstrap-expect=3 -data-dir=/tmp/consul -node=server1 -bind=<IP1> -client=0.0.0.0
# → agent: Synced node info
# → raft: Initial configuration complete
```

```bash
# Сервер 2 и 3 (join)
consul agent -server -bootstrap-expect=3 -data-dir=/tmp/consul -node=server2 -bind=<IP2> -client=0.0.0.0 -retry-join=<IP1>
consul agent -server -bootstrap-expect=3 -data-dir=/tmp/consul -node=server3 -bind=<IP3> -client=0.0.0.0 -retry-join=<IP1>
# → agent: Synced node info
```

### 2. Включение шифрования Gossip

```bash
# Генерация ключа
consul keygen
# → YwgWlBvicJN17UOYcutXLpJSZsw5aWpLEEWqgK635zA=

# На всех узлах добавить в конфиг:
echo 'encrypt = "YwgWlBvicJN17UOYcutXLpJSZsw5aWpLEEWqgK635zA="' >> /etc/consul.d/encryption.hcl
consul reload
# → configuration reloaded
```

### 3. Включение TLS и auto_encrypt

```bash
# На серверах: включить auto_encrypt и TLS
# consul.hcl
tls {
  defaults {
    ca_file   = "/etc/consul.d/tls/consul-agent-ca.pem"
    cert_file = "/etc/consul.d/tls/server.pem"
    key_file  = "/etc/consul.d/tls/server-key.pem"
    verify_incoming = true
    verify_outgoing = true
  }
}
auto_encrypt {
  allow_tls = true
}

# На клиентах: достаточно корневого CA
# client.hcl
tls {
  defaults {
    ca_file         = "/etc/consul.d/tls/consul-agent-ca.pem"
    verify_outgoing = true
  }
}
auto_encrypt {
  tls = true
}
consul reload
# → configuration reloaded
```

### 4. Включение Consul Dataplane (Kubernetes)

```bash
# В values.yaml Helm чарта:
connectInject:
  enabled: true
  apiGateway:
    enabled: false  # включается отдельно
  # Dataplane включается автоматически в Kubernetes-средах
  # вместо классических клиентских агентов

helm upgrade --install consul hashicorp/consul -f values.yaml
# → Release "consul" has been upgraded
```

### 5. Настройка WAN Federation

```bash
# На серверах secondary дата-центра:
consul agent -server -bootstrap-expect=3 -data-dir=/tmp/consul -node=server1-dc2 -bind=<IP> -client=0.0.0.0 -datacenter=dc2 -retry-join-wan=<IP-primary-dc1>
# → agent: Synced node info
# → wan: joined
```

## Устранение неполадок (Troubleshooting)

### Проблемы Gossip (LAN/WAN)

Симптомы: Узлы помечены как `failed` в `consul members`, хотя процессы запущены.
- **Диагностика портов:** Gossip использует **UDP** для проверок (ping) и **TCP** для передачи состояния (push/pull). Часто брандмауэры блокируют UDP, что приводит к ложным срабатываниям детектора сбоев.
- **Инструментарий:** `consul monitor -log-level=debug` для отслеживания событий Serf.

### Отладка Consul Dataplane

Симптомы: Сервисы в Kubernetes не регистрируются или прокси не получают конфигурацию.
- **Проверка xDS:** Dataplane подключается к серверу по **gRPC (порт 8502)**. Убедитесь, что порт открыт и TLS-сертификаты валидны.
- **Логи:** Проверьте логи пода `consul-dataplane` на наличие ошибок аутентификации. Подробные инструкции по диагностике прав в **[Troubleshooting ACL](./consul_acl.md#устранение-неполадок-troubleshooting)**.

### Проблемы консенсуса Raft

Симптомы: Ошибка `No cluster leader` при записи.
- **Диагностика:** Проверьте состояние кворума через `consul operator raft list-peers`.
- **Решение:** Подробные инструкции по восстановлению в [Consul Consensus](./consul_consensus.md#устранение-неполадок-troubleshooting).

### Проблемы с TLS

Если агенты не могут подключиться из-за TLS-ошибок:

```bash
consul info | grep -E "tls|verify"
# → проверьте verify_incoming и verify_outgoing
```

## Лучшие практики

- **Количество серверов:** Развертывайте 3 или 5 серверов на дата-центр. Большее количество замедляет Raft без повышения отказоустойчивости.
- **Шифрование:** Включайте Gossip encryption и Agent TLS на всех узлах. Используйте `auto_encrypt` для автоматической ротации сертификатов клиентов.
- **Изоляция:** Используйте Admin Partitions и Namespaces для мультитенантности вместо отдельных кластеров.
- **Масштабирование:** Не превышайте 5000 клиентских агентов на дата-центр. При необходимости разбивайте на несколько ДЦ или используйте Admin Partitions.
- **Сетевые требования:** Открывайте только необходимые порты. Gossip требует UDP 8301/8302; Raft требует TCP 8300.
- **Синхронизация времени:** На всех узлах должен быть настроен NTP/Chrony. Raft зависит от согласованных часов.
- **Мониторинг:** Собирайте метрики через `/v1/agent/metrics` endpoint или Prometheus. Отслеживайте `raft.leader`, `raft.replication`, `serf.member`.
- **Ротация ключей:** Регулярно ротируйте gossip-ключ через `consul keyring` (`-install`, `-use`, `-remove`) и TLS-сертификаты через Vault или `auto_encrypt`.
- **Ресурсы серверов:** Выделяйте серверам достаточно CPU и диска для Raft/WAL. При write-heavy нагрузке увеличивайте `ulimit -n` до 65535 и выше.
- **Версии:** Используйте одинаковые версии Consul на всех узлах. При обновлении следуйте recommended upgrade order: servers → clients → proxies.

## Граничные случаи

- **Ограничение Dataplane с Vault:** Если используется Vault как бэкенд для сертификатов, убедитесь, что Vault Agent Injector корректно работает с Dataplane. В некоторых конфигурациях Vault может требовать классических клиентских агентов для доступа к секретам.
- **WAN Federation vs Cluster Peering:** Начиная с Consul 1.13, Cluster Peering является стабильной альтернативой WAN Federation. Используйте Peering для новых мультикластерных развертываний, так как он обеспечивает более безопасную и управляемую связность.
- **Network Segments:** При превышении 5000 узлов в дата-центре используйте сетевые сегменты (network segments) для разбиения gossip-пула на несколько независимых групп.
- **Learner nodes:** При расширении кластера с 3 до 5 серверов используйте Learner nodes (v1.11+), чтобы новый узел синхронизировался без влияния на кворум.
- **Snapshot restore и streaming:** При восстановлении из снапшота в Consul 1.15.x–1.18.x streaming-подписки могут возвращать устаревшие данные. Восстанавливайтесь на Consul 1.19.0+ или перезапускайте клиенты после восстановления.
- **OpenShift:** Consul поддерживает部署 в OpenShift через `global.openshift.enabled: true` в Helm чарте. Это автоматически добавляет необходимые SecurityContextConstraints.
- **Лимиты файловых дескрипторов:** Для write-heavy кластеров увеличьте `ulimit -n` минимум до 65535. По умолчанию значение 1024 недостаточно для кластеров с большим количеством сервисов.
