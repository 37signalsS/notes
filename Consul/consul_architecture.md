# Определения

**Архитектура Consul** построена на децентрализованной агентной модели. Основная идея заключается в том, что на каждом узле инфраструктуры работает легковесный **агент**, который либо сам хранит состояние (в роли сервера), либо взаимодействует с централизованным набором **серверов**, обеспечивая обнаружение сервисов и проверку их состояния.

# Основные компоненты

## Роли узлов: Сервер и Клиент

Consul запускается из единого бинарного файла, но может работать в одном из двух режимов:

- **Сервер (Server):**
  - **Хранение данных:** Содержит авторитетную копию [каталога сервисов](./consul_service_catalog.md), [KV-хранилища](./consul_kv_store.md) и настроек безопасности (ACL).
  - **Консенсус:** Участвует в [Raft-алгоритме](./consul_consensus.md) для выбора лидера и репликации данных.
  - **Управление:** Рекомендуется развертывать 3 или 5 серверов для обеспечения отказоустойчивости (кворума).
  - **Порт:** Основное взаимодействие между серверами происходит по порту `8300` (TCP — Transmission Control Protocol).

- **Клиент (Client/Agent):**
  - **Локальный интерфейс:** Предоставляет сервисам на узле доступ к API (Application Programming Interface) через `localhost`.
  - **Проверки:** Выполняет локальные [проверки состояния (Health Checks)](./consul_health_checks.md).
  - **Проксирование:** Перенаправляет запросы на чтение и запись к серверам через RPC (Remote Procedure Call).
  - **Масштабируемость:** Может обслуживать тысячи клиентов в одном дата-центре.

# Сетевые протоколы и порты

Consul использует сложную систему сетевого взаимодействия для обеспечения скорости и надежности.

### Таблица портов

| Порт | Протокол | Назначение |
| :--- | :--- | :--- |
| **8300** | TCP | Server RPC: взаимодействие между серверами и клиентами. |
| **8301** | TCP/UDP | LAN Gossip: обмен данными внутри одного дата-центра. |
| **8302** | TCP/UDP | WAN Gossip: федерация между разными дата-центрами. |
| **8500** | TCP | HTTP API: пользовательский интерфейс и программный доступ. |
| **8501** | TCP | HTTPS API: защищенный интерфейс (рекомендуется для Production). |
| **8600** | TCP/UDP | DNS Interface: обнаружение сервисов через DNS-запросы. |

### Механизмы Gossip (Serf)

Consul использует gossip-протокол на базе библиотеки Serf для двух целей:
1. **LAN Gossip (порт 8301):** Все агенты в одном ДЦ (Дата-центр) обмениваются "слухами" о состоянии узлов. Это позволяет мгновенно обнаруживать падение узла без опроса центральных серверов.
2. **WAN Gossip (порт 8302):** Только серверы из разных ДЦ обмениваются данными для поддержки федерации.

# Топологии и масштабирование

## WAN Federation (Классическая федерация)

Традиционный способ объединения нескольких ДЦ. Серверы в каждом ДЦ связаны через WAN Gossip. Позволяет делать запросы к сервисам в удаленных регионах через локальный агент: `service-name.service.remote-dc.consul`.

## Cluster Peering (Современный подход)

Представлен в Consul 1.14+. Позволяет устанавливать прямые связи между независимыми кластерами без необходимости объединения их в общую WAN-сетку.
- **Преимущества:** Упрощенная сетевая топология, поддержка перекрывающихся IP-пространств, изоляция управления.
- **Использование:** Рекомендуется для мультиоблачных и мультиарендных (multi-tenant) сред.

## Consul Dataplane (Agentless)

В современных инсталляциях (особенно в Kubernetes) Consul поддерживает работу без запуска агента-клиента на каждом узле. Envoy прокси взаимодействует напрямую с серверами управления, что снижает потребление ресурсов и упрощает эксплуатацию.

# Практические механизмы

## Блокирующие запросы (Blocking Queries)

Механизм **long polling**, позволяющий клиентам мгновенно узнавать об изменениях в каталоге или KV без постоянного опроса.
- Клиент отправляет запрос с индексом `X-Consul-Index`.
- Сервер "подвешивает" запрос до тех пор, пока данные не изменятся или не выйдет таймаут.

## Watches и Обработчики

**Watch** — это высокоуровневая абстракция над блокирующими запросами. Позволяет запускать внешний скрипт или HTTP-вызов при изменении данных (например, при падении сервиса или обновлении ключа в KV).

```hcl
// Пример watch на изменение статуса сервиса
watch {
  type    = "service"
  service = "web"
  handler = "/usr/local/bin/notify.sh"
}
```

## Пользовательские события (Custom Events)

Consul позволяет рассылать произвольные события по всему кластеру через gossip-протокол. Это эффективный способ уведомления всех узлов о каком-либо событии (например, начале деплоя) без нагрузки на серверы Raft.
- События распространяются по принципу "best-effort" (максимальные усилия без гарантии доставки).
- Могут быть перехвачены через `watch` типа `event`.
