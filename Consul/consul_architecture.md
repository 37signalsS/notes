# Определения

**Архитектура Consul** построена на основе агентной модели. На каждом узле инфраструктуры (физическом сервере, ВМ или контейнере) работает легковесный **агент**, который взаимодействует с централизованным набором **серверов**, поддерживающих согласованное состояние кластера.

# Основные концепции

## Роли узлов: Сервер и Клиент

Consul имеет два режима работы, которые запускаются из одного бинарного файла:

- **Сервер (Server):**
  - Хранит и реплицирует состояние кластера (информацию из [каталога сервисов](./consul_service_catalog.md), [KV-хранилища](./consul_kv_store.md), ACL и др.).
  - Участвует в [Raft-консенсусе](./consul_consensus.md) для обеспечения отказоустойчивости и выбора лидера.
  - Отвечает на запросы от клиентов.
  - Рекомендуется 3 или 5 серверов на дата-центр для формирования кворума.

- **Клиент (Client):**
  - Запускается на каждом узле, где работают сервисы.
  - Перенаправляет запросы (RPC) к серверам.
  - Выполняет локальные [проверки состояния (health checks)](./consul_health_checks.md).
  - Кэширует данные для ускорения ответов и снижения нагрузки на серверы.
  - Участвует в gossip-протоколе для обнаружения других агентов и обмена информацией о состоянии.

## Протоколы взаимодействия

- **Gossip Protocol (на базе Serf):** Используется для управления членством в кластере. Все агенты (клиенты и серверы) участвуют в gossip-пуле для обмена информацией о доступности узлов и распространения событий. Это быстрый, но в конечном счете согласованный механизм.
- **RPC (Remote Procedure Call):** Используется для коммуникации между агентами (клиент-сервер и сервер-сервер).
- **Consensus Protocol (Raft):** Используется серверами для репликации критичных данных, гарантируя строгую согласованность. Детали описаны в [документе о консенсусе](./consul_consensus.md).

## Поддержка нескольких ЦОД (Multi-DC)

Consul изначально спроектирован для работы в географически распределенных средах. Это ключевой элемент обеспечения [высокой доступности (High Availability)](../Concepts/High_Availability/ha_overview.md) в распределенных системах.

- Каждый дата-центр (ДЦ) имеет свой независимый кластер Consul со своим кворумом серверов.
- Кластеры могут быть объединены в **WAN-федерацию**, что позволяет обнаруживать сервисы из других ДЦ.
- Запросы к сервисам в другом ДЦ проксируются через локальные серверы на серверы удаленного ДЦ.

# Практические сценарии

## Блокирующие запросы и Watches

Для эффективной реакции на изменения вместо постоянного опроса Consul использует **блокирующие запросы (long polling)**. Клиент делает запрос с последним известным индексом состояния (`X-Consul-Index`). Сервер удерживает соединение открытым и отвечает только тогда, когда индекс состояния обновляется, или по таймауту.

```bash
# Этот запрос будет ждать изменения состояния сервиса 'web' до 5 минут
curl "http://127.0.0.1:8500/v1/health/service/web?passing&wait=5m&index=3142"
```

На основе этого механизма работает утилита `consul watch` — обработчик, который выполняет скрипт при изменении определенных данных.

```hcl
// Пример конфигурации watches
watches = [
  {
    type    = "event"
    name    = "deploy"
    handler = "/usr/local/bin/reload_app.sh"
  },
  {
    type    = "checks"
    service = "api"
    handler = "/usr/local/bin/on_health_change.sh"
  }
]
```

## Пользовательские события (Custom Events)

Consul позволяет рассылать произвольные события по всему кластеру через gossip-протокол. Это можно использовать для уведомлений, запуска деплоя или других кастомных задач.

```bash
# Отправка события 'deploy' с полезной нагрузкой
consul event -name=deploy v1.2.3
```

Все агенты, у которых настроен `watch` на это событие, выполнят соответствующий `handler`.
