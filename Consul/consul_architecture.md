# Определения

**Архитектура Consul** построена на основе агентной модели, где на каждом узле инфраструктуры работает легковесный **агент**. Агенты взаимодействуют друг с другом и с централизованным набором **серверов**, которые поддерживают согласованное состояние кластера.

# Базовые концепции

## Роли узлов: Агент и Сервер

Consul имеет два типа узлов, которые запускаются из одного бинарного файла:

- **Сервер (Server):**
    - Хранит и реплицирует состояние кластера (каталог сервисов, KV, ACL).
    - Участвует в [Raft-консенсусе](./consul_consensus.md) для обеспечения отказоустойчивости.
    - Отвечает на запросы от клиентов.
    - Рекомендуется 3 или 5 серверов на дата-центр для формирования кворума.

- **Клиент (Client/Agent):**
    - Запускается на каждом узле, где работают сервисы.
    - Перенаправляет запросы (RPC) к серверам.
    - Выполняет локальные [проверки состояния (health checks)](./consul_health_checks.md).
    - Кэширует данные для ускорения ответов и снижения нагрузки на серверы.
    - Участвует в gossip-протоколе для обнаружения других агентов.

## Протоколы взаимодействия

- **Gossip Protocol (Serf):** Используется для управления членством в кластере. Все агенты участвуют в gossip-пуле для обмена информацией о доступности узлов и распространения событий. Это быстрый, но в конечном счете согласованный механизм.
- **Raft Consensus:** Используется серверами для репликации критичных данных. Гарантирует строгую согласованность.
- **RPC (Remote Procedure Call):** Используется для коммуникации между агентами и серверами.

## Механизм триггеров и реакции на изменения

Consul реагирует на изменения в кластере через систему триггеров.

**На стороне агента:**
- **Изменение статуса Health Check:** Переход проверки в состояние `critical` инициирует обновление каталога.
- **Регистрация/дерегистрация сервиса:** Локальные изменения отправляются на серверы.
- **Gossip-события:** Обнаружение нового узла (`join`) или сбой (`fail`) обновляют локальное представление о кластере.

**На стороне сервера:**
- **Коммиты в Raft-лог:** Любое изменение состояния (добавление сервиса, запись в KV) инкрементирует **индекс** и пробуждает блокирующие запросы.
- **Выбор нового лидера:** Смена лидера инвалидирует кэши и заново устанавливает long-polling соединения.

## Блокирующие запросы и Watches

Для эффективной реакции на изменения Consul использует **блокирующие запросы (long polling)**. Вместо того чтобы постоянно опрашивать сервер, клиент делает запрос с последним известным индексом (`X-Consul-Index`). Сервер удерживает соединение открытым и отвечает только тогда, когда индекс состояния становится больше, или по таймауту.

```bash
# Запрос, который будет ждать изменения состояния сервиса web до 5 минут
curl "http://127.0.0.1:8500/v1/health/checks/web?passing&wait=5m&index=3142"
```

На основе этого механизма работают `consul watch` — обработчики, которые выполняют скрипт или команду при изменении определенных данных (ключа в KV, статуса сервиса, события).

```json
{
  "watches": [
    {
      "type": "event",
      "name": "deploy",
      "handler": "/usr/local/bin/reload.sh"
    },
    {
      "type": "checks",
      "service": "web",
      "handler": "/usr/local/bin/on-health-change.sh"
    }
  ]
}
```

## Пользовательские события

Consul позволяет рассылать произвольные события по всему кластеру через gossip-протокол. Это используется для нотификаций, запуска деплоя или других кастомных задач.

```bash
# Отправка события
consul event -name=deploy v1.2.3
```
Все агенты, у которых настроен `watch` на событие `deploy`, выполнят соответствующий `handler`.

## Поддержка нескольких ЦОД (Multi-DC)

Consul изначально спроектирован для работы в географически распределенных средах.
- Каждый дата-центр (ДЦ) имеет свой независимый кластер Consul (свой кворум серверов).
- Кластеры могут быть объединены в **WAN-федерацию**, что позволяет обнаруживать сервисы из других ДЦ.
- Запросы к сервисам в другом ДЦ проксируются через локальные серверы.
