# Consul Service Mesh (Connect)

## Определения

**Consul Connect (Service Mesh)** — это инфраструктурный слой, обеспечивающий безопасное взаимодействие между сервисами с использованием Mutual TLS (mTLS), автоматическую авторизацию (Intentions) и наблюдаемость трафика.

**Data Plane (Слой данных)** — сеть прокси-серверов (обычно Envoy), которые работают рядом с каждым экземпляром сервиса, перехватывают весь входящий и исходящий трафик и применяют политики безопасности и маршрутизации.

**Control Plane (Слой управления)** — кластер серверов Consul, который управляет конфигурацией прокси, выпускает сертификаты TLS и хранит реестр сервисов.

**Mesh Gateway** — специализированный компонент для обеспечения связности между сервисами в разных дата-центрах или кластерах (Multi-cluster/Multi-cloud), работающий как входная/выходная точка для межкластерного трафика.

## Основные концепции

### Прокси-сайдкар (Envoy)
Вместо того чтобы встраивать логику сетевого взаимодействия в код приложения, Consul использует паттерн Sidecar.
*   **Envoy Proxy:** Промышленный стандарт L7-прокси, который инжектируется в Pod (Kubernetes) или запускается рядом с процессом (VM).
*   **Локальное взаимодействие:** Приложение общается с прокси через `localhost`. Прокси берет на себя поиск адреса (Service Discovery), шифрование и передачу данных.
*   **Init-контейнеры:** В Kubernetes подготавливают сетевое окружение Pod для перехвата трафика прокси-сервером.

### Динамический реестр сервисов
Consul поддерживает актуальный список всех живых экземпляров сервисов.
*   **Авторегистрация:** Прокси-агенты автоматически регистрируют свои сервисы в центральном реестре при запуске.
*   **Health Checks:** Если сервис становится нездоровым, прокси обновляет статус в реестре, и трафик перестает направляться на этот экземпляр.

### Безопасность и mTLS
Consul Connect обеспечивает шифрование трафика "из коробки" без изменения кода приложений.
*   **Mutual TLS:** Шифрование трафика между прокси и проверка подлинности обоих сторон соединения.
*   **Идентификация:** Каждому сервису выдается уникальный TLS-сертификат, который служит его "паспортом".
*   **Терминация TLS:** Приложение отправляет незашифрованный трафик на прокси (внутри Pod), прокси шифрует его перед отправкой в сеть и дешифрует на принимающей стороне.

### Намерения (Intentions) и микросегментация
Механизм управления доступом на уровне сервисов (а не IP-адресов).
*   **Микросегментация:** Позволяет задавать правила: "Сервису A разрешено обращаться к сервису B, но запрещено к сервису C".
*   **L4 и L7 политики:** Возможность блокировать трафик на основе имен сервисов или конкретных HTTP-путей и методов.
*   **Уменьшение поверхности атаки:** По умолчанию можно запретить все соединения и разрешать только необходимые.

### Телеметрия и наблюдаемость
Поскольку весь трафик проходит через прокси, Consul автоматически собирает метрики.
*   **Унификация:** Все прокси (Envoy) отдают метрики в едином формате.
*   **RED-метрики:** Запросы (Requests), Ошибки (Errors), Длительность (Duration).
*   **Интеграция:** Нативная поддержка вывода данных в Prometheus, Grafana, Datadog.

## Архитектура

### Взаимодействие компонентов
1.  **Consul Servers (Control Plane):** Хранят конфигурацию, политики и выпускают сертификаты.
2.  **Consul Clients:** Запускаются на каждом узле, обеспечивают связь прокси с серверами.
3.  **Envoy Proxies (Data Plane):** Обрабатывают фактический трафик между сервисами.

### Межкластерная связность (Multi-cluster)
Consul позволяет объединять независимые кластеры (например, AWS EKS и Google GKE) в единую сервисную сетку.
*   **Mesh Gateways:** Проксируют трафик между кластерами через защищенные каналы.
*   **Федерация:** Серверы в разных кластерах обмениваются информацией о доступных сервисах.
*   **Failover:** При сбое сервиса в одном кластере, трафик может быть автоматически перенаправлен на аналогичный сервис в другом кластере.

### Гибридные среды (VM и Kubernetes)
Consul рассматривает виртуальные машины (VM) как "граждан первого класса".
*   **Единая сетка:** Сервис в Kubernetes может прозрачно обращаться к базе данных на VM, используя те же механизмы mTLS и Intentions.
*   **Коннекторы:** Агенты Consul на VM подключаются к Control Plane так же, как и Pod-ы в K8s.

## Практические сценарии

### Интеграция с Kubernetes
Развертывание в Kubernetes обычно выполняется через официальный Helm-чарт.

**Основные настройки Helm (values.yaml):**
```yaml
global:
  connectInject:
    enabled: true        # Включение автоматической инъекции прокси
    default: true        # Инъекция во все Pod по умолчанию
  tls:
    enabled: true        # Включение TLS между компонентами
meshGateway:
  enabled: true          # Включение шлюзов для multi-cluster
ui:
  enabled: true
  service:
    type: LoadBalancer
```

**Аннотации Pod для управления инъекцией:**
*   `consul.hashicorp.com/connect-inject: "true"` — принудительная инъекция прокси.
*   `consul.hashicorp.com/connect-service-upstreams: "service-name:port"` — явное указание зависимостей (бэкендов), к которым будет обращаться сервис через `localhost`.
*   `consul.hashicorp.com/transparent-proxy: "true"` — автоматический перехват трафика без явного указания апстримов (рекомендуется для новых версий).
