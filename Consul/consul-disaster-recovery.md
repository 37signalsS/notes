# Резервное копирование и восстановление (DR)

# Определения

**Disaster Recovery (DR)** в Consul — это совокупность процессов и инструментов, направленных на минимизацию времени простоя и предотвращение потери данных при катастрофических сбоях (потеря всех серверов, повреждение дисков, человеческая ошибка). Основным механизмом защиты является **Snapshot** — атомарный снимок состояния кластера (KV, ACL, каталог, Service Mesh).

# Основные компоненты

Для обеспечения надежности необходимо реализовать два уровня защиты:
1.  **Автоматизированные бэкапы:** Регулярное создание снапшотов и их выгрузка во внешнее хранилище.
2.  **План восстановления:** Проверенный алгоритм действий по поднятию кластера "с нуля" из имеющегося снимка.

# Автоматизация бэкапов

## 1. Сценарий для Community Edition (Cron)

Поскольку в OSS-версии нет встроенного агента бэкапов, используется системный `cron`.

### Скрипт бэкапа (`consul-backup.sh`)
```bash
#!/bin/bash
BACKUP_DIR="/var/backups/consul"
TIMESTAMP=$(date +%Y%m%d%H%M)
FILENAME="${BACKUP_DIR}/consul-${TIMESTAMP}.snap"
export CONSUL_HTTP_TOKEN="<MANAGEMENT_TOKEN>"

mkdir -p $BACKUP_DIR

# Снапшот с флагом -stale позволяет делать бэкап не только с лидера
consul snapshot save -stale "$FILENAME"

# Очистка старых бэкапов (старше 7 дней)
find $BACKUP_DIR -type f -name "*.snap" -mtime +7 -delete

# Рекомендуется: выгрузка в облако/S3
# aws s3 cp "$FILENAME" s3://my-consul-backups/
```

## 2. Сценарий для Enterprise (Snapshot Agent)

Consul Enterprise предоставляет `snapshot agent`, который работает как демон и берет на себя управление расписанием и ретеншеном.

```json
{
  "snapshot_agent": {
    "http_addr": "127.0.0.1:8500",
    "token": "YOUR_ACL_TOKEN",
    "snapshot": {
      "interval": "1h",
      "retain": 24
    },
    "aws_storage": {
      "s3_bucket": "my-consul-backups",
      "s3_region": "us-east-1"
    }
  }
}
```

# Сценарии восстановления (Disaster Recovery)

## Сценарий 1: Восстановление на новом кластере (Total Loss)

Используется, если все старые серверы утеряны и развернуты новые узлы с новыми IP-адресами.

### Шаг 1: Принудительное формирование кворума (`peers.json`)
Чтобы выполнить команду `restore`, в новом кластере должен быть выбран Лидер.
1.  Остановите Consul на всех новых серверах.
2.  Узнайте ID каждого узла (`cat /opt/consul/data/node-id`).
3.  Создайте файл `/opt/consul/data/raft/peers.json` на одном из серверов:
    ```json
    [
      { "id": "UUID-1", "address": "10.0.1.10:8300", "voter": true },
      { "id": "UUID-2", "address": "10.0.1.11:8300", "voter": true },
      { "id": "UUID-3", "address": "10.0.1.12:8300", "voter": true }
    ]
    ```
4.  Запустите Consul. Файл `peers.json` будет поглощен, и кластер выберет лидера.

### Шаг 2: Восстановление данных
1.  Установите токен из старого кластера (он сохранен в снапшоте):
    ```bash
    export CONSUL_HTTP_TOKEN="<OLD_MANAGEMENT_TOKEN>"
    ```
2.  Выполните восстановление:
    ```bash
    consul snapshot restore backup.snap
    ```

## Сценарий 2: Потеря кворума (Quorum Loss)

Если часть серверов жива, но их недостаточно для большинства (например, 1 из 3).

1.  Остановите выживший сервер.
2.  Создайте `peers.json`, содержащий **только этот один сервер**.
3.  Запустите его. Он станет лидером в кластере из одного узла.
4.  Добавьте новые пустые серверы, они синхронизируют данные от лидера.

# Лучшие практики

- **Снапшот перед изменениями:** Всегда делайте ручной бэкап перед обновлением версии или масштабными правками в KV.
- **Хранение ключей:** Снапшот шифрует данные внутри, но не шифрует сам файл. Для защиты используйте шифрование на уровне хранилища (S3 SSE, GPG).
- **Проверка бэкапов:** Периодически проверяйте валидность файлов:
  ```bash
  consul snapshot inspect backup.snap
  ```
- **Gossip Encryption:** При восстановлении на новые узлы убедитесь, что в конфиге `consul.hcl` указан тот же `encrypt` ключ, что был на старом кластере.
