# Определения

**Consul** — это комплексное решение от HashiCorp для обнаружения, конфигурации, сегментации и защиты сервисов в динамических, распределенных средах. Он предоставляет единый инструмент для решения ключевых задач в микросервисных архитектурах.

# Основные концепции

Consul построен на нескольких фундаментальных компонентах, каждый из которых решает свою задачу:

- **[Архитектура](./consul_architecture.md):** Consul работает на основе **агентов**, которые запускаются на каждом узле. Небольшое количество **серверов** поддерживает состояние кластера с помощью [протокола консенсуса Raft](./consul_consensus.md), а **клиенты** выполняют локальные задачи и проксируют запросы.

- **[Каталог служб (Service Catalog)](./consul_service_catalog.md):** Предоставляет централизованный реестр для регистрации и обнаружения сервисов через DNS или HTTP API. Это устраняет необходимость в статических IP-адресах и позволяет клиентам находить сервисы по имени.

- **[Проверки состояния (Health Checking)](./consul_health_checks.md):** Постоянно отслеживает работоспособность сервисов и узлов. Неработоспособные экземпляры автоматически исключаются из списка доступных, предотвращая направление трафика на сбойные компоненты.

- **[Хранилище "ключ-значение" (Key/Value Store)](./consul_kv_store.md):** Распределенное иерархическое хранилище для динамической конфигурации, флагов функций (`feature flags`) и координации распределенных систем.

- **Сервисная сетка (Service Mesh):** Через компонент **Consul Connect** обеспечивает безопасное mTLS-шифрование трафика между сервисами, реализует политики контроля доступа (Intentions) и L7-маршрутизацию. Подробнее о концепциях Service Mesh в [обзоре Service Mesh](../Service_Mesh/service_mesh_concepts.md).

- **Поддержка нескольких ЦОД:** Изначально спроектирован для работы в географически распределенных средах, объединяя сервисы из разных дата-центров через WAN-федерацию. Это ключевой элемент [высокой доступности (High Availability)](../Concepts/High_Availability/ha_overview.md) в распределенных системах.

# Практические сценарии

### Динамическое обнаружение сервиса

1. **Регистрация:** Сервис `backend` при старте регистрируется в локальном агенте Consul, сообщая свой IP и порт.
2. **Проверка:** Агент Consul на узле `backend` периодически проверяет его работоспособность (например, через HTTP-эндпоинт).
3. **Обнаружение:** Сервис `frontend` запрашивает у Consul адрес для `backend.service.consul`.
4. **Ответ:** Consul через DNS или API возвращает актуальный адрес работоспособного экземпляра `backend`. Если их несколько, `frontend` получает список и может балансировать нагрузку на своей стороне.
