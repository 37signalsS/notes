# Определения

**Consul** — это современная платформа от HashiCorp для обнаружения, конфигурации и обеспечения безопасности сервисов в гибридных и мультиоблачных средах. В 2024–2025 годах Consul эволюционировал от классической агентской модели к архитектуре **Dataplane-first**, становясь универсальной плоскостью управления (Control Plane) для микросервисов, запущенных в Kubernetes, серверных средах (ECS, Fargate) и на выделенных серверах.

# Основные концепции

Consul объединяет несколько критически важных функций для управления современной инфраструктурой:

- **[Архитектура и режимы работы](./consul_architecture.md):**
    - **Modern (Dataplane):** Использование **Consul Dataplane** — легковесного компонента, заменяющего тяжелые клиентские агенты. Устраняет необходимость в Gossip-протоколе между узлами, обеспечивая прямое подключение прокси (Envoy) к серверам по gRPC.
    - **Legacy (Agent-based):** Система состоит из **серверов**, поддерживающих состояние кластера через [протокол Raft](./consul_consensus.md), и **клиентов** (агентов), работающих на каждом узле. Агенты используют **Gossip Protocol (на базе Serf)** для быстрого обнаружения сбоев.
- **[Каталог служб (Service Catalog)](./consul_service_catalog.md):** Центральный реестр "здоровых" экземпляров сервисов. Обнаружение происходит через DNS или HTTP API. В версии v1.17+ поддерживает **Multi-port services**, позволяя регистрировать несколько портов приложения под одним именем сервиса с единым sidecar-прокси.
- **[Проверки состояния (Health Checking)](./consul_health_checks.md):** Гибкие механизмы мониторинга (HTTP, TCP, gRPC, скрипты), которые позволяют Consul автоматически изолировать неисправные инстансы от трафика.
- **[KV-хранилище (Key/Value Store)](./consul_kv_store.md):** Иерархическое распределенное хранилище для динамической конфигурации, координации лидеров и управления флагами функций (`feature flags`).
- **[Сервисная сетка (Consul Service Mesh)](./consul_service_mesh.md):** Обеспечивает безопасное взаимодействие через mTLS. В современных инсталляциях управляется через политики **Service Intentions** и поддерживает **Sameness Groups** для упрощенного failover между кластерами. Для обработки трафика используются прокси-серверы (Envoy) или облегченный **Consul Dataplane**.
- **Безопасность (ACL):** Система контроля доступа (Access Control List) обеспечивает аутентификацию и авторизацию для всех операций в Consul (чтение KV, регистрация сервисов, доступ к API).
- **Мультикластерность:**
    - **Cluster Peering (GA):** Основной механизм соединения независимых кластеров без общей корневой CA. Вытесняет сложную WAN-федерацию.
    - **Sameness Groups:** Логическое объединение идентичных сервисов в разных регионах для автоматического переключения трафика при сбоях.

# Практические сценарии

### Динамическое обнаружение и балансировка

1. **Регистрация:** Приложение при запуске сообщает агенту Consul свои параметры (IP, порт, теги).
2. **Проверка:** Consul проверяет эндпоинт `/health` приложения.
3. **Обнаружение:** Другие сервисы запрашивают `api.service.consul` через DNS.
4. **Балансировка:** Consul возвращает список только тех IP, которые прошли проверку состояния, обеспечивая клиентскую балансировку нагрузки.

### Управление конфигурацией без перезагрузки

Consul KV позволяет хранить параметры приложения (например, уровень логирования или адрес БД). Приложения могут использовать утилиту `consul-template` для автоматического обновления конфигурационных файлов и перезапуска процессов при изменении данных в KV, либо подписываться на изменения через API.

### Глобальная отказоустойчивость через Cluster Peering

1. **Пиринг:** Установка связи между кластером в Европе и кластером в США через обмен токенами пиринга.
2. **Объединение:** Создание `Sameness Group` для критически важного сервиса `billing`.
3. **Маршрутизация:** Если все экземпляры `billing` в Европе станут "нездоровыми", Consul автоматически перенаправит запросы европейских клиентов на инстансы в США.
