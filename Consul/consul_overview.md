# Определения

**Consul** — это современная платформа от HashiCorp для обнаружения, конфигурации и обеспечения безопасности сервисов в гибридных и мультиоблачных средах. В рамках **CAP-теоремы** Consul является **CP-системой**, отдающей приоритет строгой согласованности (Consistency) и устойчивости к разделению сети (Partition tolerance) за счет использования протокола консенсуса Raft.

В отличие от таких систем, как etcd или Zookeeper, Consul является специализированным решением для **Service Networking**, предоставляя "из коробки" DNS-интерфейс, проверки состояния (health checks) и полноценную сервисную сетку (Service Mesh). В 2024–2025 годах платформа эволюционировала от классической агентской модели к архитектуре **Dataplane-first**, становясь универсальной плоскостью управления (Control Plane) для микросервисов в Kubernetes, серверных средах (ECS, Fargate) и на выделенных серверах.

# Основные концепции

Consul объединяет несколько критически важных функций для управления современной инфраструктурой:

- **[Архитектура и режимы работы](./consul_architecture.md):**
    - **Modern (Dataplane):** Использование **Consul Dataplane** — легковесного компонента, заменяющего тяжелые клиентские агенты. Это кардинально снижает потребление ресурсов (memory footprint) в Kubernetes, устраняя необходимость в Gossip-протоколе между рабочими узлами и обеспечивая прямое подключение прокси (Envoy) к серверам по gRPC.
    - **Legacy (Agent-based):** Классическая модель с **серверами**, поддерживающими состояние через [Raft](./consul_consensus.md), и **клиентами** (агентами) на каждом узле. Агенты используют **Gossip Protocol (Serf)** для обнаружения сбоев и распределения проверок здоровья.
- **[Каталог служб (Service Catalog)](./consul_service_catalog.md):** Центральный реестр "здоровых" экземпляров. Поддерживает **Multi-port services** (v1.17+), позволяя регистрировать несколько портов приложения (например, app и metrics) под одним именем.
- **[Consul API Gateway](./consul-api-gateway.md):** Современное решение для управления входящим трафиком на базе **Kubernetes Gateway API**. Заменяет устаревший Ingress Gateway, обеспечивая безопасную маршрутизацию внешних запросов в Service Mesh.
- **[Проверки состояния (Health Checking)](./consul_health_checks.md):** Механизмы мониторинга (HTTP, TCP, gRPC), позволяющие Consul динамически исключать неисправные узлы из балансировки.
- **[KV-хранилище (Key/Value Store)](./consul_kv_store.md):** Иерархическое распределенное хранилище для динамической конфигурации и координации лидеров.
- **[Сервисная сетка (Consul Service Mesh)](./consul_service_mesh.md):** Обеспечивает **Zero Trust Network** через mTLS-шифрование трафика. Управляется через политики **Service Intentions** и поддерживает **Sameness Groups** для упрощенного failover между кластерами.
- **[Система управления доступом (ACL)](./consul_acl.md):** Система контроля доступа, работающая по принципу **Default Deny**. Обеспечивает строгую аутентификацию и авторизацию для всех операций: от чтения KV до доступа к API через токены или внешние методы (Kubernetes, OIDC).
- **Мультикластерность:**
    - **Cluster Peering (GA):** Механизм соединения независимых кластеров без общей корневой CA, вытесняющий сложную WAN-федерацию.
    - **Sameness Groups:** Логическое объединение идентичных сервисов в разных регионах для автоматического переключения трафика при сбоях.

# Практические сценарии

## Динамическое обнаружение и балансировка

1. **Регистрация:** Приложение при запуске сообщает агенту Consul свои параметры (IP, порт, теги). Реализуется паттерн [самостоятельной регистрации](../Concepts/service-discovery-overview.md#самостоятельная-регистрация-self-registration).
2. **Проверка:** Consul проверяет эндпоинт `/health` приложения.
3. **Обнаружение:** Другие сервисы запрашивают `api.service.consul` через DNS.
4. **Балансировка:** Consul возвращает список только тех IP, которые прошли проверку состояния, обеспечивая [клиентскую балансировку нагрузки](../Concepts/service-discovery-overview.md#1-обнаружение-на-стороне-клиента-client-side-discovery).

## Запуск локального окружения (Dev Mode)

Для быстрой разработки и тестирования Consul предоставляет режим **Dev Mode**, который запускает сервер в памяти без сохранения состояния.

```bash
# Запуск локального сервера с UI
consul agent -dev -ui

# Проверка состояния узлов
consul members
```

## Управление конфигурацией без перезагрузки

Consul KV позволяет хранить параметры приложения (например, уровень логирования или адрес БД). Приложения могут использовать утилиту `consul-template` для автоматического обновления конфигурационных файлов и перезапуска процессов при изменении данных в KV, либо подписываться на изменения через API.

## Глобальная отказоустойчивость через Cluster Peering

1. **Пиринг:** Установка связи между кластером в Европе и кластером в США через обмен токенами пиринга.
2. **Объединение:** Создание `Sameness Group` для критически важного сервиса `billing`.
3. **Маршрутизация:** Если все экземпляры `billing` в Европе станут "нездоровыми", Consul автоматически перенаправит запросы европейских клиентов на инстансы в США.

## Автоматизация сетевой инфраструктуры (NIaC)

Consul позволяет автоматизировать настройку внешних устройств (балансировщиков, брандмауэров) при изменении состава сервисов.

- **Consul-Terraform-Sync (CTS):** Утилита отслеживает изменения в каталоге сервисов и автоматически запускает модули Terraform для обновления конфигурации сетевых устройств (например, F5 BIG-IP, Palo Alto Networks).
- **Terraform Provider:** Позволяет описывать политики ACL, KV-ключи и Intentions в виде кода.

## Мониторинг и наблюдаемость

Для обеспечения стабильности кластера необходимо отслеживать ключевые метрики, доступные через эндпоинт `/v1/agent/metrics` в формате Prometheus.

### Критические метрики Control Plane

| Группа | Метрика | Описание | Порог (Alert) |
| :--- | :--- | :--- | :--- |
| **Raft** | `consul_raft_leader_lastContact` | Время с момента последнего контакта лидера с фолловерами. | `> 200ms` |
| **Raft** | `consul_raft_state_leader` | Текущий статус лидерства (1 — лидер, 0 — нет). | Перевыборы > 2 за 5 мин |
| **Gossip** | `consul_memberlist_health_score` | Общий счетчик здоровья Gossip (0 — идеально). | `> 0` |
| **Gossip** | `consul_serf_lan_member_flap` | Количество "дребезга" статусов узлов (dead/alive). | `> 5` за 10 мин |
| **License** | `consul_system_licenseExpiration` | Количество часов до истечения Enterprise лицензии. | `< 720h` (30 дней) |
| **HA** | `consul_autopilot_healthy` | Общий статус здоровья кластера по версии Autopilot. | `0` (Unhealthy) |

### Рекомендации по настройке Telemetry
Для корректного сбора метрик в конфигурации агента должен быть включен блок `telemetry`:
```hcl
telemetry {
  prometheus_retention_time = "60s"
  disable_hostname = true # Рекомендуется для Kubernetes, чтобы избежать дублирования
}
```

### Правила алертинга (Prometheus Alert Rules)

Для настройки оповещений рекомендуется использовать следующие PromQL-запросы.

| Название алертига | PromQL-запрос | Описание |
| :--- | :--- | :--- |
| **ConsulNoLeader** | `sum(consul_raft_state_leader) == 0` | В кластере отсутствует активный лидер Raft. |
| **HighRaftLatency** | `consul_raft_leader_lastContact > 500` | Задержка контакта лидера с фолловерами > 500мс (нестабильность сети/CPU). |
| **FrequentElections** | `changes(consul_raft_state_leader[15m]) > 2` | Слишком частая смена лидера (нестабильность кворума). |
| **GossipDegraded** | `consul_memberlist_health_score > 2` | Проблемы со здоровьем Gossip-протокола (возможны ложные срабатывания сбоев). |
| **NodeFailedGossip** | `consul_serf_lan_member_status == 4` | Узел помечен как "failed" в пуле Gossip. |
| **AutopilotUnhealthy** | `min(consul_autopilot_healthy) == 0` | Общий статус кластера по версии Autopilot — нездоров. |
