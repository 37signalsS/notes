# Определения

**Consul KV** — это встроенное распределённое хранилище типа "ключ-значение". Оно предназначено для хранения конфигурации, динамических переменных, флагов функций (`feature flags`) и для координации распределённых сервисов.

# Основные концепции

## Модель данных и согласованность

- **Ключи:** Организуются иерархически, подобно путям в файловой системе (например, `config/app/feature_x`).
- **Значения:** Непрозрачные бинарные данные (байты), ограниченные по умолчанию размером в 512 KB.
- **Индексы (`ModifyIndex`):** Каждый ключ имеет индекс, который инкрементируется при каждом изменении. Это основа для отслеживания версий и создания `watch`-механизмов.
- **Согласованность чтения:**
    - `default`: Режим по умолчанию, может вернуть слегка устаревшие данные, но с минимальной задержкой.
    - `stale`: Чтение с любого сервера без проверки у лидера. Самый быстрый, но наименее актуальный.
    - `consistent`: Запрос направляется к лидеру [Raft-кластера](./consul_consensus.md), гарантируя получение самой последней закоммиченной версии данных.

## Атомарные операции

- **Check-And-Set (CAS):** Атомарная операция, которая позволяет записать новое значение только в том случае, если `ModifyIndex` ключа совпадает с ожидаемым. Это защищает от гонок обновлений при конкурентной записи.
- **Транзакции:** Consul поддерживает атомарные транзакции, которые могут объединять несколько операций (`set`, `get`, `cas`, `delete`) в одну. Транзакция либо выполняется целиком, либо отклоняется.

## Сессии и блокировки

Consul KV поддерживает механизм **сессий**, который позволяет реализовать распределенные блокировки (`distributed locks`). Клиент создает сессию с TTL и захватывает ключ с привязкой к этой сессии. Если клиент выходит из строя и перестает обновлять TTL, сессия истекает, и блокировка автоматически освобождается. Это используется для реализации паттерна выбора лидера (`leader election`).

# Практические сценарии

## Управление конфигурацией через CLI

```bash
# Запись значения
consul kv put config/prod/db/url "postgres://db.prod:5432/app"

# Чтение значения
consul kv get config/prod/db/url

# Рекурсивное чтение всех ключей с префиксом
consul kv get -recurse config/prod/

# Удаление ключа
consul kv delete app/prod/db/url

# Рекурсивное удаление
consul kv delete -recurse app/prod/
```

## Операции через HTTP API

```bash
# Запись значения
curl --request PUT --data 'enabled=true' http://127.0.0.1:8500/v1/kv/app/prod/featureA

# Чтение (значение в формате base64)
curl http://127.0.0.1:8500/v1/kv/app/prod/featureA

# Чтение "сырого" значения
curl http://127.0.0.1:8500/v1/kv/app/prod/featureA?raw
```

## Отслеживание изменений (Blocking Queries)

Вместо постоянного опроса (polling), клиенты могут использовать блокирующие запросы, которые ожидают изменения `modifyIndex` ключа.

```bash
# 1. Выполнить первый запрос и сохранить значение заголовка X-Consul-Index
curl -i http://127.0.0.1:8500/v1/kv/app/prod/featureA

# 2. Выполнить блокирующий запрос с полученным index, ожидая до 10 минут
curl "http://127.0.0.1:8500/v1/kv/app/prod/featureA?index=<prev_index>&wait=10m"
```
Сервер вернет ответ, как только значение изменится или по истечении таймаута.

Альтернатива — использование `consul watch` на агенте:
```bash
consul watch -type=keyprefix -prefix=app/prod/ 'bash -c "date; echo changed"'
```

## Транзакции

Consul поддерживает атомарные транзакции, которые могут объединять несколько операций (`set`, `get`, `cas`, `delete`).

```bash
# Пример транзакции с операцией CAS
curl --request PUT http://127.0.0.1:8500/v1/txn -d '
[
  {
    "KV": {
      "Verb": "cas",
      "Key": "app/prod/version",
      "Value": "MQ==", # "1" в base64
      "Index": 42
    }
  }
]'
```
