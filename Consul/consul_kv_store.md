# Определения

**Consul KV (Key-Value Store)** — это встроенное распределённое иерархическое хранилище, предназначенное для динамической конфигурации, управления флагами функций (`feature flags`), координации распределённых систем и реализации механизмов выбора лидера. Все данные в KV-хранилище реплицируются между серверами через [протокол консенсуса Raft](./consul_consensus.md).

В архитектуре Consul KV является частью **Finite State Machine (FSM)**. Все операции записи проходят через реплицируемый лог Raft, что гарантирует линеаризуемость (linearizability) изменений. В современных системах Consul KV выполняет роль «распределенного `/etc`», обеспечивая высокую доступность и строгую согласованность для критически важных метаданных инфраструктуры.

# Основные концепции

## Модель данных и индексы

- **Иерархические ключи:** Ключи организуются в виде дерева, аналогично файловой системе (например, `config/prod/database/url`). Это позволяет эффективно управлять правами доступа через префиксы.
- **Значения:** Непрозрачные бинарные данные.
    - **Лимит:** По умолчанию размер ограничен **512 КБ** на один ключ.
    - **Настройка:** С версии 1.5.3 лимит можно изменить через параметр `kv_max_value_size`, но значительное превышение может привести к деградации производительности Raft.
- **Флаги (`Flags`):** Беззнаковое 64-битное целое число, сохраняемое вместе со значением. Используется приложениями для хранения метаданных (например, типа контента, версии схемы или кодировки).
- **Система индексов:**
    - `CreateIndex`: Индекс состояния кластера на момент создания ключа.
    - `ModifyIndex`: Индекс последнего изменения. Используется для механизмов `watch` и атомарных операций CAS.
    - `LockIndex`: Количество раз, когда ключ был успешно захвачен сессией.

## Согласованность и производительность

Consul предоставляет три режима для операций чтения:
- `default`: Баланс. Запрос обрабатывается лидером, который подтверждает свое лидерство через внутренний тайм-аут без кворума. Обеспечивает строгую согласованность в большинстве случаев.
- `stale`: **Максимальная производительность.** Чтение с любого сервера (включая последователей). Позволяет увеличить пропускную способность чтения в 50+ раз, но допускает задержку данных в несколько миллисекунд.
- `consistent`: **Максимальная надежность.** Требует подтверждения лидерства через кворум для каждого запроса. Гарантирует отсутствие «грязного» чтения.

## Атомарность и транзакции

- **Check-And-Set (CAS):** Операция, которая позволяет обновить значение ключа только в том случае, если его текущий `ModifyIndex` совпадает с переданным параметром. Это предотвращает состояние гонки (`race conditions`) при одновременном обновлении данных разными клиентами.
- **Транзакции:** Позволяют сгруппировать до **64 операций** (`put`, `get`, `delete`, `cas`) в один атомарный блок. Если одна операция в транзакции завершается неудачей, весь блок отклоняется.

## Жизненный цикл записи (Lifecycle of a Write)

Кажедое изменение в KV-хранилище (put, delete, transaction) проходит через строгую последовательность этапов для обеспечения согласованности:
1.  **Прием запроса:** Клиент отправляет запрос на Consul Agent (HTTP или RPC). Агент пересылает запрос текущему **Лидеру** кластера.
2.  **Запись в Raft Log:** Лидер добавляет операцию в свой локальный лог Raft.
3.  **Репликация:** Лидер рассылает запись последователям (Followers). Операция считается «зафиксированной» (`committed`), как только большинство серверов подтвердят запись в свои логи.
4.  **Применение в FSM:** После фиксации Лидер применяет изменение к своей **Finite State Machine** (хранилищу в памяти).
5.  **Ответ:** Лидер возвращает результат клиенту.
*Важно:* Из-за необходимости сетевой репликации и записи на диск (fsync) для каждой операции, KV-хранилище не предназначено для сверхвысоких нагрузок на запись.

## Сессии и блокировки

Механизм **сессий** позволяет реализовать распределенные блокировки (`distributed locks`) и семафоры:
1.  **Создание сессии:** Клиент создает сессию, указывая `Name`, `Node`, `Checks` (связанные проверки здоровья) и `TTL` (от 10с до 24ч).
2.  **Heartbeats:** Клиент обязан периодически продлевать сессию (`renew`), иначе она истечет.
3.  **Захват ключа (`acquire`):** Операция записи с параметром `?acquire=<session_id>`. Если ключ свободен, он привязывается к сессии, а `LockIndex` увеличивается.
4.  **Поведение при истечении (`Behavior`):**
    - `release` (по умолчанию): Блокировка просто снимается, ключ остается.
    - `delete`: Ключ автоматически удаляется (полезно для временных записей о состоянии узлов).

Это является основой для паттерна **выбора лидера (Leader Election)**, где несколько узлов пытаются захватить один и тот же ключ; победитель считается лидером.

## Изоляция (Enterprise)

В Enterprise-версии Consul доступны **Namespaces** и **Admin Partitions**, которые позволяют логически изолировать KV-пространства для разных команд или окружений в рамках одного кластера, предотвращая конфликты имен и упрощая управление ACL.

# Практические сценарии

## Использование CLI для управления конфигурацией

```bash
# Запись значения с флагом
consul kv put -flags=42 config/app/max_connections 100

# Чтение в режиме stale (высокая скорость, чтение с любого сервера)
consul kv get -stale config/app/max_connections

# Рекурсивное чтение метаданных всех ключей в директории
consul kv get -recurse -detailed config/app/

# Рекурсивное удаление всей ветки конфигурации
consul kv delete -recurse config/app/

# Атомарное обновление (CAS)
# Успешно, если ModifyIndex равен 148
consul kv put -cas -modifyindex=148 config/app/max_connections 200
```

## Работа с транзакциями через API

Позволяют выполнить до 64 операций атомарно.

```bash
curl -X PUT --data '[
  { "KV": { "Verb": "delete", "Key": "config/old_key" } },
  { "KV": { "Verb": "set", "Key": "config/new_key", "Value": "YmFzZTY0X2VuY29kZWRfdmFsdWU=" } }
]' http://127.0.0.1:8500/v1/txn
```

## Импорт и экспорт данных

Используется для миграций, резервного копирования или клонирования окружений. Данные передаются в формате JSON.

```bash
# Экспорт всех ключей по префиксу в файл
consul kv export config/app/ > app_config_backup.json

# Импорт ключей из файла
consul kv import @app_config_backup.json
```

## Управление доступом (ACL) для KV

Для защиты данных в KV-хранилище необходимо использовать систему ACL. Права доступа настраиваются на уровне ключей и префиксов. Полное описание системы прав, токенов и методов аутентификации приведено в **[Системе управления доступом (ACL)](./consul_acl.md)**.

Пример политики `app-reader.hcl`, разрешающей чтение только для конкретного префикса:

```hcl
key_prefix "config/app/" {
  policy = "read"
}

# Разрешаем запись только для флага обслуживания
key "config/app/maintenance_mode" {
  policy = "write"
}
```
Применение: `consul acl policy create -name "app-reader-policy" -rules @app-reader.hcl`.

## Автоматизация через consul-template

**Consul-template** — это стандарт де-факто для доставки конфигураций. Утилита подписывается на изменения (watch) и обновляет файлы на лету.

Пример использования `tree` для динамического формирования списка параметров:
```go-template
# app.conf.ctmpl
{{ range tree "config/app/features/" }}
{{ .Key }} = {{ .Value }}
{{ end }}

max_conns = {{ keyOrDefault "config/app/max_connections" "50" }};
```
**Совет:** Настройте отправку сигнала `SIGHUP` приложению после обновления конфига, чтобы оно перечитало настройки без полной перезагрузки.

## Блокирующие запросы (Long Polling)

Клиенты могут эффективно ожидать изменений, используя заголовок `X-Consul-Index`.

```bash
# Получаем текущий индекс
curl -v http://127.0.0.1:8500/v1/kv/config/app/max_connections
# < X-Consul-Index: 148

# Ожидаем изменений (запрос висит до изменения данных или таймаута)
curl "http://127.0.0.1:8500/v1/kv/config/app/max_connections?index=148&wait=5m"
```

## Реализация блокировки через API

```bash
# 1. Создание сессии
curl -X PUT -d '{"Name": "lock-session", "TTL": "15s"}' http://127.0.0.1:8500/v1/session/create
# -> {"ID": "adf4238a-882b-9ddc-4a9d-5b6758e4159e"}

# 2. Захват ключа
curl -X PUT http://127.0.0.1:8500/v1/kv/service/leader?acquire=adf4238a-882b-9ddc-4a9d-5b6758e4159e
# -> true (если захват удался)
```

# Устранение неполадок и краевые случаи

## Ошибки CAS (Check-And-Set)
При использовании CAS клиент может получить ошибку (409 Conflict), если другой процесс обновил ключ быстрее.
- **Решение:** Реализовать стратегию «Retry with Exponential Backoff». Перед повторной попыткой необходимо снова прочитать ключ, чтобы получить актуальный `ModifyIndex`.

## Сетевые разделения (Network Partitions)
Consul KV приоритизирует согласованность (Consistency) над доступностью (Availability) согласно CP-модели теоремы CAP.
- **Влияние:** При потере кворума (majority) запись в KV становится невозможной.
- **Чтение:** `consistent` и `default` чтения будут возвращать ошибку. Только `stale` чтения продолжат работать, но могут возвращать устаревшие данные.

## Деградация производительности Raft
Частые изменения или хранение объектов близких к лимиту (512 КБ) увеличивают размер снимков состояния (snapshots) и объем пересылаемых логов Raft.
- **Симптомы:** Увеличение задержек (latency), рост загрузки CPU на серверах, частые перевыборы лидера.
- **Рекомендация:** Используйте Consul KV только для метаданных. Крупные конфиги лучше хранить в специализированных хранилищах или как артефакты, оставляя в KV только ссылки/хеши.

# Лучшие практики

- **Иерархическая структура:** Организуйте ключи по принципу файловой системы: `config/env/app/service/setting`. Это упрощает настройку ACL и рекурсивное чтение.
- **Использование `stale` чтений:** Для конфигураций, где задержка в доли секунды не критична, всегда используйте `stale`. Это значительно снижает нагрузку на Raft-кворум.
- **Минимизация Watches:** Не устанавливайте «вотчи» на тысячи отдельных ключей. Эффективнее следить за общим префиксом (директорией).
- **Кэширование агентом:** Используйте параметр `use_cache: true` в конфигурации агентов Consul для локального обслуживания запросов на чтение.

# Когда не следует использовать Consul KV

- **Как основную базу данных:** Consul не предназначен для хранения миллионов записей или больших объемов данных.
- **Для хранения секретов без шифрования:** Данные в KV по умолчанию не зашифрованы. Для паролей и ключей используйте [интеграцию с Vault](../Vault/guides/vault_with_consul_backend.md).
- **Для высокочастотных записей:** Каждая запись проходит через Raft-консенсус и пишется на диск. Сотни записей в секунду могут привести к деградации кластера.

# Дополнительная информация

- **Лимиты:** Рекомендуется хранить только небольшие объемы данных. Большие значения (>512 КБ) и частые изменения в KV могут негативно влиять на стабильность [Raft-консенсуса](./consul_consensus.md) из-за увеличения размера логов и времени репликации.
- **Безопасность:** Доступ к ключам и префиксам должен строго ограничиваться через [систему ACL](./consul_architecture.md).
