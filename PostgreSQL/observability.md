# Full-Stack Observability для PostgreSQL

Обеспечение наблюдаемости (observability) для баз данных, таких как PostgreSQL, является критически важной задачей. Проблемы с производительностью БД часто неочевидны: стандартные метрики (CPU, память) могут быть в норме, но система в целом деградирует из-за неоптимальных запросов, блокировок или неправильной конфигурации. Full-stack observability позволяет связать активность на уровне приложения с поведением внутри базы данных, чтобы точно ответить на вопрос **"почему система тормозит?"**.

Ключевая идея — прокинуть сквозной **контекст трассировки** от клиентского запроса через все микросервисы вплоть до конкретного SQL-запроса, исполняемого в PostgreSQL.

## Три столпа Observability в контексте PostgreSQL

1.  **Метрики (Metrics):** Предоставляют агрегированную числовую информацию о состоянии БД.
    *   **Источники:** `pg_stat_statements`, `pg_stat_database`, `pg_stat_user_tables`, `pg_locks` и др.
    *   **Инструменты сбора:** [Prometheus Exporter для PostgreSQL](../Prometheus/exporters.md) (`postgres_exporter`), который как раз использует эти `pg_stat` представления.
    *   **Что отслеживать:**
        *   Количество запросов в секунду, среднее/пиковое время выполнения.
        *   Cache hit rate.
        *   Количество и длительность блокировок.
        *   Задержка репликации (`replication lag`).
        *   Статистика работы `VACUUM`.

2.  **Логи (Logs):** Содержат записи о конкретных событиях.
    *   **Источники:** Лог-файлы PostgreSQL.
    *   **Что отслеживать:**
        *   Медленные запросы (с помощью `log_min_duration_statement`).
        *   Планы выполнения медленных запросов (с помощью `auto_explain`).
        *   Ошибки, `deadlocks`.
        *   Сообщения от `sqlcommenter`.
    *   **Корреляция:** Для связи логов с трассировками критически важно, чтобы в лог попадал `trace_id`. Это достигается через `sqlcommenter`.

3.  **Трассировки (Traces):** Позволяют отследить полный путь выполнения запроса.
    *   **Задача:** Увидеть SQL-запрос как один из "спанов" (span) в общей трассировке (trace) запроса.
    *   **Ключевой механизм:** **[SQLCommenter](../OpenTelemetry/opentelemetry_overview.md#практический-пример-инструментация-запросов-к-postgresql)**. Библиотеки инструментирования в приложении добавляют к SQL-запросу комментарий с `trace_id`, например `/*traceparent='00-...'*/`.
    *   **Сбор внутри БД:** Расширение **`pg_tracing`** способно "понять" этот комментарий и создать дочерние спаны для внутренних операций PostgreSQL (парсинг, планирование, исполнение), продолжая таким образом цепочку трассировки.

## Инструменты и расширения

### 1. `pg_stat_statements`
Стандартное расширение для сбора статистики по выполненным запросам.
*   **Функционал:** Собирает агрегированные данные: количество вызовов, общее и среднее время выполнения, информация о чтении/записи блоков.
*   **Использование:** Основа для `postgres_exporter`. Позволяет находить самые "дорогие" запросы в системе.
*   **Недостатки:** Не предоставляет планы запросов и имеет ограниченную детализацию.

### 2. `auto_explain`
Модуль, который автоматически логирует планы выполнения для медленных запросов.
*   **Функционал:** Когда запрос превышает `log_min_duration_statement`, его `EXPLAIN` план записывается в лог.
*   **Использование:** Помогает понять, *почему* конкретный запрос выполняется медленно (например, из-за `Seq Scan` вместо `Index Scan`).
*   **Важно:** Необходимо использовать сэмплирование (`auto_explain.sample_rate`), чтобы избежать чрезмерной нагрузки на production-системах.

### 3. `pg_stat_monitor`
Более продвинутая альтернатива `pg_stat_statements`.
*   **Функционал:**
    *   Собирает статистику в разрезе времени (поминутные срезы).
    *   Умеет захватывать и хранить планы запросов.
    *   Предоставляет гистограммы времени выполнения.
*   **Недостатки:** Создает более высокую нагрузку по сравнению с `pg_stat_statements`.

### 4. `sqlcommenter`
Это не расширение, а **конвенция и набор библиотек** для добавления метаданных в SQL-комментарии.
*   **Принцип:** `SELECT * FROM users;` -> `SELECT * FROM users /*application='backend',controller='users',traceparent='...'*/;`
*   **Польза:**
    1.  Метаданные попадают в логи PostgreSQL, что позволяет фильтровать и анализировать `slow query log` в контексте конкретного сервиса или эндпоинта.
    2.  `traceparent` используется расширением `pg_tracing` для сквозной трассировки.
*   **Реализация:** Существуют библиотеки для популярных ORM и драйверов (SQLAlchemy, Psycopg, GORM и др.), которые делают это автоматически.
    *   См. [Примеры для OpenTelemetry](../OpenTelemetry/opentelemetry_overview.md#практический-пример-инструментация-запросов-к-postgresql).

### 5. `pg_tracing` (экспериментальный)
Наиболее мощный инструмент для глубокой наблюдаемости внутри PostgreSQL.
*   **Функционал:**
    *   Создает спаны для различных фаз выполнения запроса (parsing, planning, execution, I/O, locks).
    *   Читает `traceparent` из `sqlcommenter` и связывает свои спаны с родительским спаном приложения.
    *   **Напрямую экспортирует спаны** по протоколу OTLP в коллектор ([Grafana Alloy](../Grafana/grafana_alloy_overview.md) или OpenTelemetry Collector). Это намного эффективнее, чем парсинг логов.
*   **Требования:**
    *   На данный момент требует сборки PostgreSQL из исходного кода или использования готового Docker-образа с этим расширением.
    *   Считается экспериментальным, но активно развивается.

## Архитектура Full-Stack Observability

Типичный современный стек выглядит следующим образом:

1.  **Приложение:** Инструментируется с помощью **OpenTelemetry SDK**. При выполнении запросов к БД через ORM/драйвер автоматически добавляется комментарий **`sqlcommenter`** с `traceparent`.
2.  **PostgreSQL:**
    *   Установлено расширение **`pg_tracing`**.
    *   `pg_tracing` перехватывает запрос, видит `traceparent`, создает детализированные дочерние спаны для стадий выполнения SQL и отправляет их по протоколу OTLP.
    *   Параллельно `postgres_exporter` собирает метрики из `pg_stat_*`.
    *   Логи пишутся в файл и также содержат `sqlcommenter`.
3.  **Grafana Alloy (Агент):**
    *   Принимает трейсы от приложения и `pg_tracing`.
    *   Скрапит метрики с `postgres_exporter`.
    *   Читает лог-файлы, парсит их, извлекает `trace_id` из комментариев и обогащает ими метаданные логов.
    *   Отправляет все три типа данных в бэкенды Grafana Stack.
4.  **Grafana Stack (Бэкенд):**
    *   **[Tempo](../Grafana/tempo_details.md):** Хранит трейсы.
    *   **[Loki](../Grafana/loki_details.md):** Хранит логи.
    *   **[Mimir](../Mimir/mimir_overview.md)/Prometheus:** Хранит метрики.
5.  **Grafana (Визуализация):**
    *   Предоставляет единый интерфейс, где можно увидеть метрики, найти аномалию, перейти к трейсам, увидеть медленный спан с SQL-запросом и тут же посмотреть все логи, связанные с этим трейсом.

Этот подход обеспечивает глубокую, взаимосвязанную картину производительности всей системы.
