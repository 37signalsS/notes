# Рабочий процесс анализа производительности PostgreSQL

Чтобы систематически находить и устранять проблемы с производительностью в PostgreSQL, рекомендуется следовать проверенному рабочему процессу.

## 1. Начните с основ (Keep It Simple)

Прежде чем углубляться в сложные настройки, проверьте самые очевидные и частые причины проблем.

- **Человеческий фактор и недавние изменения:**
  - Проанализируйте недавние коммиты и изменения в коде приложения. Часто проблемы с производительностью появляются после развертывания нового кода с неоптимальными запросами.
  - Используйте систему контроля версий (например, Git) для всех изменений, связанных с базой данных, включая миграции схем и изменения в конфигурации.

- **Окружение и соседи:**
  - Убедитесь, что рядом с PostgreSQL на том же сервере не запущены другие ресурсоемкие процессы, которые могут "воровать" CPU, RAM или дисковый I/O. Базы данных, как правило, требуют выделенных ресурсов.

## 2. Анализ на уровне ОС

Проблемы с производительностью БД часто коренятся в ограничениях на уровне операционной системы. 70-80% тюнинга PostgreSQL — это тюнинг Linux.

- **Основные утилиты для мониторинга:**
  - `top` / `htop` / `atop`: Мониторинг использования CPU и RAM в реальном времени. Обратите внимание на равномерность загрузки ядер и на процессы, потребляющие больше всего ресурсов.
  - `iostat`: Анализ нагрузки на дисковую подсистему (операции чтения/записи, время ожидания).
  - `df`: Проверка свободного места на дисках.
  - `free` / `vmstat`: Проверка использования оперативной памяти и swap.

- **Проверка OOM Killer:** Проверьте системные логи (`dmesg`), чтобы убедиться, что `oom-killer` (Out-of-Memory Killer) не убивал процесс PostgreSQL.

## 3. Анализ на уровне базы данных

- **`pg_stat_activity`**: Первый шаг для ответа на вопрос "что происходит в базе прямо сейчас?".
  - Ищите запросы с `state = 'active'`, которые выполняются очень долго.
  - Особое внимание уделяйте состоянию `idle in transaction`. Такие сессии удерживают блокировки и мешают работе `VACUUM`. Их необходимо отслеживать и завершать.

- **`pg_stat_statements`**: Используйте это расширение для поиска самых "дорогих" запросов в системе по совокупным показателям.
  - **Топ запросов по общему времени выполнения (`total_exec_time`):** Запросы, которые в сумме создают наибольшую нагрузку.
  - **Топ запросов по среднему времени выполнения (`mean_exec_time`):** Отдельные медленные запросы.
  - **Топ запросов по количеству вызовов (`calls`):** Очень частые, но, возможно, быстрые запросы, которые в сумме могут создавать нагрузку.

## 4. Глубокий анализ конкретного запроса

После того как медленный запрос найден, используйте `EXPLAIN ANALYZE` для детального изучения его плана выполнения.

- **Чтение плана:** План выполнения читается "изнутри наружу" и "снизу вверх". Начинайте анализ с самых вложенных операций с наибольшей стоимостью (`cost`) и реальным временем выполнения (`actual time`).
- **Поиск проблемных операций:**
  - `Sequential Scan (Seq Scan)` на больших таблицах — главный кандидат на оптимизацию. Возможно, отсутствует необходимый индекс.
  - Неверные оценки количества строк (`rows`): если планировщик сильно ошибается в оценке количества строк (например, `rows=1` при реальном `rows=100000`), это может указывать на устаревшую статистику. Выполните `ANALYZE my_table;`.
  - Неоптимальные типы `JOIN`.

## 5. Оптимизация и проверка

На основе анализа плана вы можете применить одну из стратегий оптимизации:

- **Добавить или изменить индекс:** Наиболее частое решение.
- **Переписать запрос:** Упростить, разбить на части, использовать другие конструкции.
- **Предварительная агрегация:** Создать материализованные представления или сводные таблицы для тяжелых аналитических запросов.
- **Изменить конфигурацию PostgreSQL:** Например, увеличить `work_mem` для конкретной сессии, если в плане есть дорогостоящие дисковые сортировки.
- **Собрать статистику:** `ANALYZE table_name;`

После внесения изменений **обязательно** повторно выполните `EXPLAIN ANALYZE`, чтобы убедиться, что план действительно улучшился.
