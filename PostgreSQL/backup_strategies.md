# Стратегии резервного копирования PostgreSQL

Эффективное резервное копирование является критически важным для обеспечения сохранности данных и восстановления после сбоев. PostgreSQL предлагает несколько подходов к резервному копированию: логическое и физическое.

## Лучшие практики и терминология

1.  **Правило "3-2-1" резервирования данных:**
    *   Иметь не менее **трех** экземпляров данных.
    *   Хранить копии не менее чем на **двух** различных носителях.
    *   Хранить не менее **одной** копии данных за пределами офиса (на удаленной площадке).
2.  **RTO (Recovery Time Objective):** Целевое время восстановления — время, требуемое на восстановление резервной копии.
3.  **RPO (Recovery Point Objective):** Целевая точка восстановления — точка во времени, на которую должны быть восстановлены данные (например, до 24 часов с момента сбоя).
4.  **Уровни резервного копирования:**
    *   **Полное (Full):** Копируется весь набор данных. Для восстановления требуется только эта копия.
    *   **Дифференциальное (Differential):** Копируются только изменения с момента последнего полного резервного копирования. Для восстановления требуется последняя полная и последняя дифференциальная копии.
    *   **Инкрементальное (Incremental):** Копируются только изменения с момента последнего *любого* резервного копирования (полного, дифференциального или инкрементального). Для восстановления нужна полная копия, последняя дифференциальная (если есть) и все инкрементальные копии после неё.

## Логическое резервное копирование

Логический бэкап сохраняет данные в виде SQL-операторов или в других текстовых форматах.

### Преимущества:
*   Можно сделать копию отдельного объекта (например, таблицы или базы данных).
*   Можно восстановить на кластере с другой основной версией PostgreSQL.
*   Можно восстановить на другой архитектуре сервера.

### Недостатки:
*   Невысокая скорость по сравнению с физическим резервным копированием, особенно для больших объемов данных.

### Инструменты и команды:

#### 1. Команда `COPY` (для отдельных таблиц)

Используется для экспорта/импорта данных одной таблицы.

*   **Экспорт данных в файл:**
    ```sql
    COPY your_table TO '/path/to/your_table_backup.csv' WITH (FORMAT CSV, HEADER, DELIMITER ',');
    ```
    -   `FORMAT CSV`: Указывает формат CSV.
    -   `HEADER`: Включает заголовок столбцов в файл.
    -   `DELIMITER ','`: Определяет разделитель полей (по умолчанию - табуляция).
*   **Импорт данных из файла (восстановление):**
    ```sql
    TRUNCATE TABLE your_table; -- Очистка таблицы перед восстановлением (опционально)
    COPY your_table FROM '/path/to/your_table_backup.csv' WITH (FORMAT CSV, HEADER, DELIMITER ',');
    ```
    **Важно:** Если при экспорте был задан специфический разделитель, его необходимо указать и при импорте. PostgreSQL автоматически экранирует специальные символы в данных.

#### 2. Утилита `pg_dump` (для баз данных)

Создает резервную копию базы данных, которая может быть выведена в SQL-скрипт или в специальный формат архива.

*   **Вывод в SQL-скрипт:**
    ```bash
    pg_dump -U postgres -d your_database > /path/to/your_database_backup.sql
    ```
    -   Сохраняет базу данных как последовательность SQL-команд.
    -   По умолчанию не создает пользователей и табличные пространства (их нужно создавать заранее).
*   **Вывод в сжатый SQL-скрипт (gzip):**
    ```bash
    pg_dump -U postgres -d your_database | gzip > /path/to/your_database_backup.sql.gz
    ```
    - Для восстановления потребуется сначала распаковать архив:
    ```bash
    gunzip -c /path/to/your_database_backup.sql.gz | psql -U postgres -d your_database
    ```
*   **Вывод в сжатый архив (tar):**
    ```bash
    pg_dump -U postgres -d your_database -F t -f /path/to/your_database_backup.tar
    ```
    -   `F t`: Указывает формат tar.
    -   Удобно для сжатия и хранения.
*   **Вывод в специальный формат (custom, с оглавлением):**
    ```bash
    pg_dump -U postgres -d your_database -F c -f /path/to/your_database_backup.dump
    ```
    -   `F c`: Указывает формат custom.
    -   Позволяет выборочно восстанавливать объекты и поддерживает параллельное восстановление.
    -   Сжат по умолчанию.
*   **Параллельное выполнение (для больших баз):**
    ```bash
    pg_dump -U postgres -d your_database -j 4 -F d -f /path/to/your_database_backup_dir
    ```
    -   `j 4`: Количество параллельных потоков.
    -   `F d`: Формат "directory" (каталог), обязателен для параллельного `pg_dump`.

#### 3. Утилита `pg_restore` (для восстановления из `pg_dump` архивов)

Восстанавливает базу данных из архивов, созданных `pg_dump` (форматы `custom`, `tar`, `directory`).

*   **Восстановление из SQL-скрипта (через `psql`):**
    ```bash
    psql -U postgres -d your_database -f /path/to/your_database_backup.sql
    ```
*   **Восстановление из архива (custom/tar/directory):**
    ```bash
    pg_restore -U postgres -d your_database /path/to/your_database_backup.dump
    # или для директории с параллельным восстановлением:
    pg_restore -U postgres -d your_database -j 4 /path/to/your_database_backup_dir
    ```
    -   Позволяет выборочно восстанавливать объекты (таблицы, схемы и т.д.).
    -   Поддерживает параллельное выполнение (`-j`).

#### 4. Утилита `pg_dumpall` (для всего кластера)

Создает полную копию всего кластера PostgreSQL, включая глобальные объекты (роли, табличные пространства).

*   **Создание полного дампа:**
    ```bash
    pg_dumpall -U postgres > /path/to/full_cluster_backup.sql
    ```
*   **Восстановление:**
    ```bash
    psql -U postgres -f /path/to/full_cluster_backup.sql postgres
    ```
    -   Восстановление происходит последовательно, без параллелизации.
    -   Идеально для миграции всего кластера или его полной пересоздания.

## Физическое резервное копирование

Физический бэкап работает на уровне файлов файловой системы, копируя файлы данных и журналы предзаписи (WAL).

### Преимущества:
*   Позволяет восстановить кластер в любой момент времени (point-in-time recovery) благодаря WAL-журналам.
*   Высокая скорость копирования для больших баз данных, так как копируются напрямую файлы.

### Недостатки:
*   Нельзя восстановить отдельные базы данных или объекты, только весь кластер целиком.
*   Восстановление возможно только на той же основной версии PostgreSQL и на той же архитектуре.

### Виды физического резервирования:

1.  **Холодный бэкап:**
    *   Выполняется, когда база данных полностью остановлена.
    *   Требуется скопировать только файлы данных (`PGDATA`).
    *   Если сервер был остановлен некорректно, дополнительно требуются WAL-сегменты.
2.  **Горячий бэкап:**
    *   Выполняется на работающем экземпляре базы данных.
    *   Требуется скопировать как файлы данных, так и все WAL-сегменты, сгенерированные во время копирования.
    *   Необходимо контролировать, чтобы сервер сохранял WAL-файлы на время копирования основных данных.

### Инструменты и команды:

#### 1. Утилита `pg_basebackup`

Создает полную бинарную копию кластера, включая файлы данных и WAL-сегменты. Подключается к серверу по протоколу репликации.

*   **Создание базовой резервной копии:**
    ```bash
    pg_basebackup -h localhost -p 5432 -U postgres -D /path/to/backup_directory -F p -Xs -P -R
    ```
    -   `h`, `p`, `U`: Параметры подключения к серверу.
    -   `D /path/to/backup_directory`: Целевой каталог для бэкапа.
    -   `F p`: Указывает формат `plain` (обычный, не сжатый).
    -   `Xs`: Включает WAL-файлы в бэкап.
    -   `P`: Показывает прогресс.
    -   `R`: Создает файл `standby.signal` и `postgresql.auto.conf` (или `recovery.conf` для старых версий) для настройки восстановления/реплики.
*   **Восстановление:**
    1.  Развернуть созданную автономную копию в новый (или пустой) каталог данных.
    2.  Запустить PostgreSQL. Он автоматически начнет процесс восстановления, используя WAL-файлы, если они были включены в бэкап или доступны из WAL-архива.
    
    **Важно:** Для восстановления на определенный момент времени может потребоваться настроить WAL-архивирование (`archive_mode`, `archive_command`) на мастере.
