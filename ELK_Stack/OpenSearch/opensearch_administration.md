# OpenSearch: Администрирование и устранение неполадок

> Эта заметка является частью обзора [OpenSearch](./opensearch_overview.md) и рассматривает ключевые аспекты администрирования кластера OpenSearch, включая управление конфигурацией безопасности и решение распространенных проблем.

## Определения

* **opensearch-security**: плагин безопасности OpenSearch для защиты кластера (аутентификация, авторизация, шифрование TLS (Transport Layer Security)).
* **Security REST API**: интерфейс REST (Representational State Transfer) API (Application Programming Interface) для управления пользователями, ролями и сопоставлениями (маппингами) через протокол HTTP (HyperText Transfer Protocol). Предпочтительный метод для повседневных операций.
* **securityadmin.sh**: утилита для полного сброса и принудительного применения конфигурации безопасности из файлов формата YAML. Используется в аварийных ситуациях.
* **Внутренний индекс безопасности** (`.opendistro_security`): скрытый индекс OpenSearch для хранения активной конфигурации безопасности.

## Основные концепции

### Модель конфигурации безопасности

* **Первый запуск**: при первом запуске кластера плагин безопасности инициализирует конфигурацию (пользователей, роли, маппинги) из YAML-файлов (`internal_users.yml`, `roles.yml` и др.), которые монтируются в поды (например, из секретов Kubernetes).
* **Последующие запуски**: после первой инициализации вся конфигурация загружается во внутренний скрытый индекс OpenSearch. Файлы YAML в подах **больше не используются** для оперативного управления. Кластер доверяет только данным из своего внутреннего индекса.

### Методы управления конфигурацией

#### Современный подход: REST API

Для повседневного управления пользователями, ролями и маппингами следует использовать Security REST API. Это предпочтительный и наиболее безопасный метод.

```bash
# Получение информации о пользователе 'admin'
curl -k -u admin:new_password "https://opensearch-host:9200/_plugins/_security/api/internalusers/admin"

# Обновление роли 'my_role' из файла role.json (формат JSON — JavaScript Object Notation)
curl -k -u admin:new_password -XPUT "https://opensearch-host:9200/_plugins/_security/api/roles/my_role" \
-H "Content-Type: application/json" -d @role.json
```

#### Устаревший подход: securityadmin.sh

Утилита `securityadmin.sh` предназначена для **полного сброса и принудительного применения** конфигурации из YAML-файлов. Она полезна в аварийных ситуациях, например, при потере пароля администратора или необходимости восстановить конфигурацию из системы контроля версий Git.

> **Внимание**: `securityadmin.sh` полностью **перезаписывает** всю конфигурацию безопасности в кластере данными из файлов. Все изменения, сделанные через API, будут потеряны. Используйте с осторожностью.

**Порядок использования:**

1. Зайти в один из master-подов: `kubectl exec -it opensearch-master-0 -- /bin/bash`.
2. Перейти в директорию `plugins/opensearch-security/tools`.
3. Выполнить скрипт, указав пути к файлам конфигурации и сертификатам администратора.

```bash
./securityadmin.sh \
  -f /path/to/internal_users.yml \
  -cacert /path/to/root-ca.pem \
  -cert /path/to/admin-cert.pem \
  -key /path/to/admin-key.pem \
  -h opensearch-master-service-name
```

## Практические сценарии

### Ошибка 502 при доступе к OpenSearch Dashboards

**Проблема**: Helm-чарт для `opensearch-dashboards` может иметь некорректно настроенную пробу готовности `readinessProbe`. Под помечается как `Ready` до того, как веб-сервер внутри контейнера действительно начнет отвечать на запросы. Это может приводить к временным ошибкам `502 Bad Gateway` при доступе через Ingress сразу после деплоя или рестарта.

**Решение**:

* **Кастомизация `readinessProbe`**: измените `readinessProbe` в `values.yaml` для `opensearch-dashboards`, чтобы он проверял реальный эндпоинт, который становится доступным только после полной загрузки (например, страницу логина).
* **Увеличение таймаутов**: временно можно увеличить таймауты и количество повторных попыток в `readinessProbe`, чтобы дать сервису больше времени на запуск.
