# OpenSearch: Администрирование и устранение неполадок

> Эта заметка является частью обзора [OpenSearch](./opensearch_overview.md) и рассматривает ключевые аспекты администрирования кластера OpenSearch, включая управление конфигурацией безопасности и решение распространенных проблем.

## Управление конфигурацией безопасности

Плагин безопасности OpenSearch (`opensearch-security`) является центральным компонентом для защиты кластера. Понимание его модели конфигурации критически важно.

### Модель конфигурации

- **Первый запуск:** При первом запуске кластера плагин безопасности инициализирует свою конфигурацию (пользователей, роли, маппинги) из YAML-файлов (`internal_users.yml`, `roles.yml` и др.), которые монтируются в поды (например, из Kubernetes Secrets).
- **Последующие запуски:** После первой инициализации вся конфигурация безопасности загружается во внутренний скрытый индекс OpenSearch (`.opendistro_security` или аналогичный). Файлы YAML в подах **больше не используются** для оперативного управления. Кластер доверяет только данным из своего внутреннего индекса.

### Применение изменений и сброс паролей

#### Современный подход: REST API

Для повседневного управления пользователями, ролями и маппингами следует использовать **Security REST API**. Это предпочтительный и наиболее безопасный метод.

```bash
# Пример: получение информации о пользователе 'admin'
curl -k -u admin:new_password "https://opensearch-host:9200/_plugins/_security/api/internalusers/admin"

# Пример: обновление роли 'my_role' из файла role.json
curl -k -u admin:new_password -XPUT "https://opensearch-host:9200/_plugins/_security/api/roles/my_role" 
-H "Content-Type: application/json" -d @role.json
```

#### Устаревший подход: `securityadmin.sh`

Утилита `securityadmin.sh` предназначена для **полного сброса и принудительного применения** конфигурации из YAML-файлов. Она полезна в аварийных ситуациях, например, при потере пароля администратора или необходимости восстановить конфигурацию из Git.

> **Внимание:** `securityadmin.sh` полностью **перезаписывает** всю конфигурацию безопасности в кластере данными из файлов. Все изменения, сделанные через API, будут потеряны. Используйте с осторожностью.

**Как использовать:**

1. Зайдите в один из master-подов: `kubectl exec -it opensearch-master-0 -- /bin/bash`.
2. Перейдите в директорию `plugins/opensearch-security/tools`.
3. Выполните скрипт, указав пути к файлам конфигурации и сертификатам администратора.

    ```bash
    ./securityadmin.sh 
      -f /path/to/internal_users.yml 
      -cacert /path/to/root-ca.pem 
      -cert /path/to/admin-cert.pem 
      -key /path/to/admin-key.pem 
      -h opensearch-master-service-name
    ```

## Устранение неполадок

### Ошибка 502 при доступе к OpenSearch Dashboards

**Проблема:** Helm-чарт для `opensearch-dashboards` может иметь некорректно настроенный `readinessProbe`. Под помечается как `Ready` до того, как веб-сервер внутри контейнера действительно начнет отвечать на запросы. Это может приводить к временным ошибкам `502 Bad Gateway` при доступе через Ingress сразу после деплоя или рестарта.

**Решение:**

- **Кастомизация `readinessProbe`:** Измените `readinessProbe` в `values.yaml` для `opensearch-dashboards`, чтобы он проверял реальный эндпоинт, который становится доступным только после полной загрузки. Например, можно проверять страницу логина.
- **Увеличение таймаутов:** Временно можно увеличить таймауты и количество повторных попыток в `readinessProbe`, чтобы дать сервису больше времени на запуск.
