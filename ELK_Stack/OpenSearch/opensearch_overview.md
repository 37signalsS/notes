# Обзор OpenSearch

## Определения

**OpenSearch** — это полностью открытый, распределенный поисковый и аналитический движок, являющийся форком (ответвлением) **Elasticsearch** и **Kibana**. Проект был инициирован Amazon Web Services (AWS) в ответ на изменение лицензионной политики Elastic.

OpenSearch предлагает тот же функционал, что и Elasticsearch, включая полнотекстовый поиск, аналитику логов, мониторинг приложений и анализ безопасности, но под полностью свободной лицензией Apache 2.0.

## Основные концепции

### Причины появления OpenSearch

Основной причиной создания OpenSearch стало изменение лицензии Elasticsearch и Kibana компанией Elastic, начиная с версии 7.11. Новая лицензия (Elastic License v2 и SSPL) накладывает ограничения на использование продуктов в коммерческих SaaS-решениях, что вызвало обеспокоенность в сообществе.

OpenSearch является полностью открытой альтернативой, поддерживаемой консорциумом технологических компаний, и сохраняет совместимость с API Elasticsearch.

### Компоненты

*   **OpenSearch**: Ядро, аналогичное Elasticsearch, для хранения, поиска и анализа данных.
*   **OpenSearch Dashboards**: Веб-интерфейс для визуализации и анализа данных, аналог Kibana.

## Практический сценарий: Развертывание в Kubernetes

OpenSearch, как и Elasticsearch, является сложной распределенной системой. При развертывании в Kubernetes важно учитывать несколько аспектов.

### Архитектура развертывания через Helm

Из видео-примера видно, что Helm-чарт для OpenSearch может иметь упрощенную структуру по сравнению с чартами для Elasticsearch.

*   **Мульти-ролевые ноды**: Вместо того чтобы определять каждую роль (master, data, ingest) как отдельный компонент StatefulSet или Deployment, чарт OpenSearch может разворачивать поды, которые совмещают в себе все роли.
    ```yaml
    # Пример из values.yaml Helm-чарта
    roles:
      - master
      - ingest
      - data
      - remote_cluster_client
    ```
    Такой подход упрощает конфигурацию для небольших и средних инсталляций, но для высоконагруженных продуктивных систем рекомендуется разделять роли по разным группам нод.

*   **Кластеризация**: Установка нескольких реплик (`replicas: 2`) с мульти-ролевыми нодами уже обеспечивает базовый уровень отказоустойчивости.

*   **Конфигурация**:
    *   **TLS**: По умолчанию чарты могут использовать "левые" самоподписанные сертификаты. Для продуктивного использования их необходимо заменять на валидные.
    *   **Логирование**: OpenSearch (как и Elasticsearch) использует `log4j`. По умолчанию логи могут выводиться в строковом формате. Для перевода логов в **JSON** (что является лучшей практикой для последующего парсинга) требуется кастомизация конфигурации `log4j.properties`. Если соответствующий JSON-layout класс не включен в контейнер, это может потребовать сборки собственного образа.

*   **Системные требования**:
    *   **Память**: OpenSearch, как Java-приложение, требователен к оперативной памяти. Лимиты и реквесты должны быть настроены с запасом.
    *   **`vm.max_map_count`**: Для корректной работы требуется увеличение системного параметра ядра Linux `vm.max_map_count`. В Kubernetes это обычно делается через `initContainer` с привилегированным доступом или через конфигурацию хостовых систем.
    *   **Персистентность**: Обязательно использование `PersistentVolume` для хранения данных. Производительность дисковой подсистемы (локальные SSD, быстрые сетевые хранилища) критически важна.

### Доступ к OpenSearch

*   **API**: Доступ к API OpenSearch внутри кластера осуществляется через Service типа `ClusterIP`. Выставлять API наружу через Ingress обычно не рекомендуется из соображений безопасности.
*   **Dashboards**: Доступ к веб-интерфейсу OpenSearch Dashboards осуществляется через `Ingress`.
