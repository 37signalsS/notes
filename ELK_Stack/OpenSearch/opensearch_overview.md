# OpenSearch: Обзор

## Определения

* **OpenSearch** — это полностью открытый, распределенный поисковый и аналитический движок с открытым исходным кодом (лицензия Apache 2.0). Проект был создан как форк Elasticsearch 7.10.2 и Kibana 7.10.2 после изменения лицензионной политики компании Elastic.
* **OpenSearch Dashboards** — веб-интерфейс для визуализации данных, управления кластером и анализа безопасности (форк Kibana).
* **Data Prepper** — серверный компонент для приема, фильтрации, трансформации и маршрутизации данных телеметрии (логи, метрики, трассировки) в OpenSearch.

## Основные концепции

### История и лицензирование

OpenSearch появился в 2021 году как ответ сообщества (под руководством AWS) на переход Elasticsearch на несвободные лицензии (SSPL и Elastic License v2). OpenSearch гарантирует отсутствие ограничений на использование в коммерческих SaaS-решениях и сохраняет совместимость со многими инструментами экосистемы Elasticsearch.

### Ключевые отличия и возможности

В отличие от современных версий Elasticsearch, многие функции в OpenSearch доступны бесплатно "из коробки":

* **Встроенная безопасность (Security Plugin)**: Шифрование TLS, аутентификация через AD/LDAP/SAML, управление доступом на уровне полей и строк (RBAC/FGAC).
* **Управление жизненным циклом (ISM)**: Автоматизация ротации, сжатия и удаления индексов на основе политик.
* **Segment Replication (версия 2.3+)**: Механизм репликации данных на уровне файлов сегментов Lucene (вместо повторного выполнения запросов на репликах), что снижает нагрузку на CPU узлов данных.
* **Удаленное хранилище (Remote Backed Storage)**: Возможность хранения первичных данных в объектных хранилищах (S3), что повышает надежность и упрощает масштабирование.
* **Anomaly Detection**: Использование алгоритмов машинного обучения для поиска отклонений в данных в реальном времени.

### Компоненты системы

1. **Движок (Core)**: Отвечает за индексацию, хранение и распределенный поиск.
2. **Dashboards**: UI для аналитики и администрирования.
3. **Плагины**: Интегрированные решения для Security, Alerting, SQL-запросов, k-NN поиска и Observability.

## Практические сценарии

### Использование как хранилища для Jaeger

OpenSearch является стандартным бэкендом для хранения трассировок в системе **[Jaeger](../../Jaeger/jaeger_overview.md)**.

* **Принцип работы**: Компонент `jaeger-collector` записывает данные напрямую в индексы OpenSearch. Jaeger самостоятельно управляет структурой индексов (создает ежедневные индексы `jaeger-span-YYYY-MM-DD`).
* **Особенности**: Этот метод не требует дополнительных компонентов, но данные в таком формате **недоступны** для анализа через плагин OpenSearch Observability. Для кросс-аналитики (логи + трейсы в одном UI) рекомендуется использовать OTLP и Data Prepper.

### Централизованное логирование и ISM

OpenSearch идеально подходит для хранения терабайтов логов благодаря встроенному плагину **Index State Management (ISM)**.

* **Задача**: Хранить логи 30 дней, переносить их на "холодные" узлы через 7 дней и удалять по истечении срока.
* **Реализация**: Создается политика ISM, которая прикрепляется к шаблону индекса. Все процессы происходят автоматически внутри кластера без внешних скриптов (в отличие от старых версий ELK, где требовался Curator).

### Плагин Observability и Data Prepper

Для создания единой платформы мониторинга используется следующая архитектура:
`Приложение -> OpenTelemetry Collector -> Data Prepper -> OpenSearch`

* **Observability Plugin**: Позволяет объединять логи, метрики и трейсы в единые дашборды, строить карты сервисов (Service Map) и проводить расследование инцидентов (Trace Analytics).
* **Data Prepper**: Выполняет роль "тяжелого" обработчика, способного преобразовывать OTLP-данные в формат, оптимизированный для аналитики OpenSearch.
