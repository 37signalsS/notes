# Обзор OpenSearch

## Определения

**OpenSearch** — это полностью открытый, распределенный поисковый и аналитический движок, являющийся форком (ответвлением) **Elasticsearch** и **Kibana**. Проект был инициирован Amazon Web Services (AWS) в ответ на изменение лицензионной политики Elastic.

OpenSearch предлагает тот же функционал, что и Elasticsearch, включая полнотекстовый поиск, аналитику логов, мониторинг приложений и анализ безопасности, но под полностью свободной лицензией Apache 2.0.

## Основные концепции

### Причины появления OpenSearch

Основной причиной создания OpenSearch стало изменение лицензии Elasticsearch и Kibana компанией Elastic, начиная с версии 7.11. Новая лицензия (Elastic License v2 и SSPL) накладывает ограничения на использование продуктов в коммерческих SaaS-решениях, что вызвало обеспокоенность в сообществе.

OpenSearch является полностью открытой альтернативой, поддерживаемой консорциумом технологических компаний, и сохраняет совместимость с API Elasticsearch.

### Компоненты

*   **OpenSearch**: Ядро, аналогичное Elasticsearch, для хранения, поиска и анализа данных.
*   **OpenSearch Dashboards**: Веб-интерфейс для визуализации и анализа данных, аналог Kibana.

## Практические сценарии и администрирование

### Развертывание в Kubernetes с помощью Helm

Официальный Helm-чарт OpenSearch предлагает гибкий подход к развертыванию, основанный на управлении группами нод с разными ролями.

#### Философия Helm-чарта

-   **Модульность:** В отличие от некоторых других чартов (например, для Elasticsearch), где все типы нод (master, data, ingest) настраиваются в одном `values.yaml`, чарт OpenSearch использует иной подход. Вы используете **один и тот же чарт**, но с **разными values-файлами** для развертывания каждой группы нод.
    -   `helm install opensearch-master -f values-master.yaml`
    -   `helm install opensearch-data -f values-data.yaml`
    -   `helm install opensearch-dashboard -f values-dashboard.yaml`
-   **Горизонтальное масштабирование:** Такой подход позволяет независимо масштабировать каждую группу ролей (например, добавлять только data-ноды), просто изменяя `replicaCount` в соответствующем values-файле и выполняя `helm upgrade`.

#### Разделение ролей

Для production-окружений критически важно разделять роли по разным группам нод для обеспечения стабильности и производительности.
-   **Master-ноды:** Отвечают за управление состоянием кластера. Обычно требуется 3 реплики для кворума.
-   **Data-ноды:** Хранят и индексируют данные. Требуют больше всего дискового пространства и I/O.
-   **Ingest-ноды:** Выполняют предварительную обработку документов перед индексацией.
-   **Ко-локация ролей:** Для небольших инсталляций допустимо совмещать роли (например, `data` и `ingest`) в одной группе нод.

#### Ключевые параметры конфигурации (`values.yaml`)

При настройке `values.yaml` для каждой группы нод следует обратить внимание на следующие параметры:

-   **Кластеризация:**
    -   `clusterName`: Должен быть **идентичным** во всех `values.yaml` файлах, относящихся к одному кластеру OpenSearch.
    -   `masterService`: Имя Kubernetes-сервиса, указывающего на master-ноды. Также должно быть **идентичным** во всех `values.yaml`, чтобы data/ingest ноды могли найти мастер.

-   **Безопасность и TLS:**
    -   `allowUnsafeDemoCertificates: false`: Обязательно установите в `false` для production, чтобы отключить небезопасные демонстрационные сертификаты.
    -   `security.tls.transport.pemcert_filepath`: Путь к TLS-сертификату для коммуникации между нодами (порт 9300).
    -   `security.tls.http.pemcert_filepath`: Путь к TLS-сертификату для HTTP API (порт 9200).
    -   `security.nodes_dn`: Белый список Subject Distinguished Names (DN) сертификатов, которым разрешено присоединяться к кластеру в качестве нод.
    -   `security.admin_dn`: DN сертификата суперпользователя, который имеет полные права на кластер.
    -   `secretMounts`: Механизм для монтирования Kubernetes Secrets (с сертификатами и ключами) в поды.

-   **Логирование:**
    -   Для включения **JSON-логов** (рекомендуется для автоматизированного парсинга) необходимо раскомментировать секцию `log4j2.properties` и указать `OpenSearchJsonLayout` в качестве layout'а.

-   **Высокая доступность (High Availability):**
    -   `podAntiAffinity`: Используйте `podAntiAffinity` по `kubernetes.io/hostname`, чтобы гарантировать, что реплики master-нод будут распределены по разным физическим узлам Kubernetes.
    -   `podManagementPolicy: Parallel`: Для StatefulSet'ов (master и data ноды) установка этой политики обеспечивает rolling update без даунтайма (сначала поднимается новая реплика, затем гасится старая). **Критически важно** иметь корректно настроенные `readinessProbe`, иначе возможен простой.

-   **Системные параметры (`sysctl`):**
    -   OpenSearch требует `vm.max_map_count >= 262144`.
    -   Вместо установки `sysctl.enabled: true` в чарте (что требует привилегированных подов), рекомендуется настраивать этот параметр на всех worker-нодах кластера заранее (например, через Ansible или startup-скрипты).

### Администрирование и устранение неполадок

#### Первоначальная конфигурация и сброс паролей

-   **Первый запуск:** При первом запуске кластера плагин безопасности инициализирует свою конфигурацию (пользователей, роли, маппинги) из YAML-файлов, которые монтируются в поды из Kubernetes Secrets (`internal_users.yml`, `roles.yml` и др.).
-   **Последующие запуски:** После первой инициализации конфигурация хранится во внутреннем индексе OpenSearch, и файлы в Secrets больше не используются.
-   **Сброс пароля или применение новой конфигурации:** Если вы потеряли пароль администратора или хотите принудительно применить изменения из конфигурационных YAML-файлов, необходимо воспользоваться утилитой `securityadmin.sh`:
    1.  Зайдите в один из master-подов: `kubectl exec -it opensearch-master-0 -- /bin/bash`.
    2.  Перейдите в директорию `plugins/opensearch-security/tools`.
    3.  Выполните скрипт `securityadmin.sh`, указав пути к файлам конфигурации и сертификатам администратора. Этот скрипт принудительно обновит конфигурацию безопасности в кластере.
    
    > **Примечание:** Эта утилита помечена как устаревшая и может быть заменена в будущих версиях.

#### Проблема с Readiness Probe в OpenSearch Dashboards

-   Helm-чарт для `opensearch-dashboards` может иметь некорректно настроенный `readinessProbe`. Под может быть помечен как `Ready` задолго до того, как веб-сервер внутри контейнера действительно начнет отвечать на запросы. Это может приводить к временным ошибкам `502 Bad Gateway` при доступе через Ingress сразу после деплоя или рестарта.

### Использование OpenSearch как хранилища для Jaeger

Помимо собственного плагина Observability, OpenSearch часто используется как простое и надежное хранилище для трейсов, собираемых системой **Jaeger**.

*   **Принцип работы:** В этой конфигурации Jaeger (компонент `jaeger-collector`) настроен на использование OpenSearch как своего бэкенда. Он самостоятельно управляет жизненным циклом данных, создавая ежедневные индексы для спанов и сервисов (например, `jaeger-span-2023-10-27`, `jaeger-service-2023-10-27`).
*   **Чтение данных:** Запросы на получение трейсов из Jaeger UI обрабатываются компонентом `jaeger-query`, который обращается напрямую к этим индексам в OpenSearch.

> **Важно:** Трейсы, сохраненные Jaeger в своих собственных индексах, **несовместимы** с дашбордами плагина `Observability`. Для использования нативного UI трейсинга в OpenSearch требуется отправка данных в формате OTLP через **Data Prepper**, как описано в следующем разделе. Эти два подхода к хранению трейсов в OpenSearch являются взаимоисключающими с точки зрения их анализа в UI.

## Плагин Observability

OpenSearch предоставляет встроенный плагин **Observability**, который позволяет анализировать трейсы, метрики и логи в едином интерфейсе. Это бесплатная альтернатива аналогичным платным функциям в стеке Elastic.

### Архитектура для сбора трейсов

Для использования дашбордов трейсинга в OpenSearch Observability требуется специальный формат данных. Трассы, сохраненные напрямую из Jaeger, несовместимы с этим модулем.

Для решения этой задачи используется компонент **Data Prepper**.

*   **Data Prepper**: Это отдельный сервис, который действует как коллектор и процессор данных. Он получает телеметрические данные, преобразует их в нужный для OpenSearch формат и сохраняет в соответствующие индексы.
    *   **Требование к формату**: Data Prepper принимает данные только в формате **OTLP (OpenTelemetry Protocol)**.
    *   **Pipelines**: Конфигурируется через пайплайны, которые описывают источник (`source`), обработчики (`processor`) и приемник (`sink`). Например, для трейсов он создает два индекса: один для сырых данных (`trace-analytic-row`) и один для карты сервисов (`trace-analytic-service-map`).

Типичная архитектура для сбора трейсов выглядит следующим образом:
`Приложение -> OTLP Collector -> Data Prepper -> OpenSearch`

Здесь **OTLP Collector** собирает данные от приложений (он может принимать различные форматы, включая Jaeger) и пересылает их в **Data Prepper** в формате OTLP. Data Prepper, в свою очередь, обрабатывает их и складывает в OpenSearch.
