# OpenSearch: Развертывание в Kubernetes с помощью Helm

> Эта заметка является частью обзора [OpenSearch](./opensearch_overview.md) и детально рассматривает процесс развертывания кластера в Kubernetes с использованием официального Helm-чарта.

Официальный Helm-чарт OpenSearch предлагает гибкий и модульный подход к развертыванию, основанный на управлении группами нод с разными ролями.

## Философия Helm-чарта

- **Модульность:** В отличие от некоторых других чартов (например, для Elasticsearch), где все типы нод (master, data, ingest) настраиваются в одном `values.yaml`, чарт OpenSearch использует иной подход. Вы используете **один и тот же чарт**, но с **разными values-файлами** для развертывания каждой группы нод.
  - `helm install opensearch-master -f values-master.yaml`
  - `helm install opensearch-data -f values-data.yaml`
  - `helm install opensearch-dashboard -f values-dashboard.yaml`
- **Горизонтальное масштабирование:** Такой подход позволяет независимо масштабировать каждую группу ролей (например, добавлять только data-ноды), просто изменяя `replicaCount` в соответствующем values-файле и выполняя `helm upgrade`.

## Разделение ролей

Для production-окружений критически важно разделять роли по разным группам нод для обеспечения стабильности и производительности.

- **Master-ноды:** Отвечают за управление состоянием кластера. Обычно требуется 3 реплики для кворума.
- **Data-ноды:** Хранят и индексируют данные. Требуют больше всего дискового пространства и I/O.
- **Ingest-ноды:** Выполняют предварительную обработку документов перед индексацией.
- **Ко-локация ролей:** Для небольших инсталляций допустимо совмещать роли (например, `data` и `ingest`) в одной группе нод.

## Ключевые параметры конфигурации (`values.yaml`)

При настройке `values.yaml` для каждой группы нод следует обратить внимание на следующие параметры:

- **Кластеризация:**
  - `clusterName`: Должен быть **идентичным** во всех `values.yaml` файлах, относящихся к одному кластеру OpenSearch.
  - `masterService`: Имя Kubernetes-сервиса, указывающего на master-ноды. Также должно быть **идентичным** во всех `values.yaml`, чтобы data/ingest ноды могли найти мастер.

- **Безопасность и TLS:**
  - `allowUnsafeDemoCertificates: false`: Обязательно установите в `false` для production, чтобы отключить небезопасные демонстрационные сертификаты.
  - `security.tls.transport.pemcert_filepath`: Путь к TLS-сертификату для коммуникации между нодами (порт 9300).
  - `security.tls.http.pemcert_filepath`: Путь к TLS-сертификату для HTTP API (порт 9200).
  - `security.nodes_dn`: Белый список Subject Distinguished Names (DN) сертификатов, которым разрешено присоединяться к кластеру в качестве нод.
  - `security.admin_dn`: DN сертификата суперпользователя, который имеет полные права на кластер.
  - `secretMounts`: Механизм для монтирования Kubernetes Secrets (с сертификатами и ключами) в поды.

- **Логирование:**
  - Для включения **JSON-логов** (рекомендуется для автоматизированного парсинга) необходимо раскомментировать секцию `log4j2.properties` и указать `OpenSearchJsonLayout` в качестве layout'а.

- **Высокая доступность (High Availability):**
  - `podAntiAffinity`: Используйте `podAntiAffinity` по `kubernetes.io/hostname`, чтобы гарантировать, что реплики master-нод будут распределены по разным физическим узлам Kubernetes.
  - `podManagementPolicy: Parallel`: Для StatefulSet'ов (master и data ноды) установка этой политики обеспечивает rolling update без даунтайма (сначала поднимается новая реплика, затем гасится старая). **Критически важно** иметь корректно настроенные `readinessProbe`, иначе возможен простой.

- **Системные параметры (`sysctl`):**
  - OpenSearch требует `vm.max_map_count >= 262144`.
  - Вместо установки `sysctl.enabled: true` в чарте (что требует привилегированных подов), рекомендуется настраивать этот параметр на всех worker-нодах кластера заранее (например, через Ansible или startup-скрипты).
