# OpenSearch: Развертывание в Kubernetes с помощью Helm

> Эта заметка является частью обзора [OpenSearch](./opensearch_overview.md) и детально рассматривает процесс развертывания кластера в Kubernetes с использованием официального Helm-чарта.

## Определения

* **Helm-чарт OpenSearch**: официальный Helm-пакет для развертывания кластера OpenSearch в Kubernetes с модульным подходом к управлению ролями узлов.
* **values.yaml**: основной файл конфигурации Helm-чарта, определяющий параметры для каждой группы узлов (master, data, ingest, dashboards).
* **masterService**: сервис Kubernetes, указывающий на управляющие (master) узлы. Используется для обнаружения кластера остальными участниками.

## Основные концепции

### Архитектура Helm-чарта

* **Модульность**: в отличие от чартов Elasticsearch, где все типы узлов настраиваются в одном файле `values.yaml`, чарт OpenSearch использует один и тот же чарт с разными конфигурационными файлами для каждой группы:
  * `helm install opensearch-master -f values-master.yaml`
  * `helm install opensearch-data -f values-data.yaml`
  * `helm install opensearch-dashboard -f values-dashboard.yaml`
* **Горизонтальное масштабирование**: независимое масштабирование групп ролей через изменение параметра `replicaCount` в соответствующем файле и выполнение команды `helm upgrade`.

### Разделение ролей узлов

Для промышленных (production) окружений критически важно разделять роли по разным группам узлов:

* **Управляющие узлы (Master nodes)**: управление состоянием кластера. Требуется минимум 3 реплики для обеспечения кворума.
* **Узлы данных (Data nodes)**: хранение и индексация данных. Требуют значительных ресурсов дискового пространства и операций ввода-вывода (Input/Output, I/O).
* **Инжест-узлы (Ingest nodes)**: предварительная обработка документов перед индексацией.
* **Совмещение ролей**: для небольших инсталляций допустимо совмещать роли (например, `data` и `ingest`) в одной группе узлов.

### Ключевые параметры конфигурации

| Категория | Параметр | Описание |
| :--- | :--- | :--- |
| **Кластеризация** | `clusterName` | Должен быть идентичным во всех файлах `values.yaml` внутри одного кластера |
| | `masterService` | Имя сервиса управляющих узлов. Должно совпадать во всех конфигурациях |
| **Безопасность** | `allowUnsafeDemoCertificates: false` | Отключение демонстрационных сертификатов для промышленных сред |
| | `security.tls.transport.pemcert_filepath` | Путь к сертификату TLS (Transport Layer Security) для межсерверного взаимодействия (порт 9300) |
| | `security.tls.http.pemcert_filepath` | Путь к сертификату TLS для HTTP (HyperText Transfer Protocol) интерфейса программирования приложений (Application Programming Interface, API) (порт 9200) |
| | `security.nodes_dn` | Список отличительных имен (Distinguished Name, DN) сертификатов узлов |
| | `security.admin_dn` | Отличительное имя (DN) сертификата администратора |
| | `secretMounts` | Механизм монтирования секретов (Secrets) Kubernetes с сертификатами |
| **Логирование** | `log4j2.properties` | Включение логов в формате JSON (JavaScript Object Notation) через `OpenSearchJsonLayout` для автоматизированного парсинга |
| **Отказоустойчивость** | `podAntiAffinity` | Правила распределения реплик по разным физическим узлам Kubernetes |
| | `podManagementPolicy: Parallel` | Стратегия обновления StatefulSet без простоя |
| **Системные** | `vm.max_map_count` | Требуется значение не менее `262144`. Настраивается на узлах Kubernetes заранее |

## Практические сценарии

### Развертывание промышленного кластера

1. **Подготовка сертификатов**: создайте секреты Kubernetes, содержащие сертификаты TLS для транспортного и HTTP протоколов.
2. **Создание конфигурационных файлов**: подготовьте файлы для каждой группы ролей с идентичными значениями `clusterName` и `masterService`.
3. **Настройка параметров ядра**: убедитесь, что на всех рабочих узлах установлен параметр `vm.max_map_count` в значение `262144` или выше.
4. **Установка**: выполните команду `helm install` для каждой группы в последовательности: master → data → dashboards.
5. **Проверка**: убедитесь, что все компоненты перешли в состояние готовности (Ready).

### Настройка высокой доступности (High Availability)

* **Распределение узлов**: используйте механизмы `podAntiAffinity` для исключения размещения нескольких управляющих узлов на одном физическом сервере.
* **Обновление без простоев**: используйте параметр `podManagementPolicy: Parallel` для ускорения процесса обновления и минимизации влияния на доступность.
* **Пробы готовности (Readiness probes)**: настройте точные проверки состояния сервисов для предотвращения преждевременного направления трафика на запускающиеся узлы.
