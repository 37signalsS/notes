# OpenSearch: Развертывание в Kubernetes с помощью Helm

> Эта заметка является частью обзора [OpenSearch](./opensearch_overview.md) и детально рассматривает процесс развертывания кластера в Kubernetes с использованием официального Helm-чарта.

## Определения

* **Helm-чарт OpenSearch**: Официальный Helm-чарт для развертывания кластера OpenSearch в Kubernetes с модульным подходом к управлению ролями нод.
* **values.yaml**: Файл конфигурации Helm-чарта, определяющий параметры для каждой группы нод (master, data, ingest, dashboards).
* **masterService**: Kubernetes-сервис, указывающий на master-ноды. Используется для обнаружения кластера остальными нодами.

## Основные концепции

### Философия Helm-чарта

* **Модульность**: В отличие от чартов Elasticsearch, где все типы нод настраиваются в одном `values.yaml`, чарт OpenSearch использует **один и тот же чарт** с **разными values-файлами** для каждой группы нод:
  * `helm install opensearch-master -f values-master.yaml`
  * `helm install opensearch-data -f values-data.yaml`
  * `helm install opensearch-dashboard -f values-dashboard.yaml`
* **Горизонтальное масштабирование**: Независимое масштабирование групп ролей через изменение `replicaCount` в соответствующем values-файле и выполнение `helm upgrade`.

### Разделение ролей

Для production-окружений критически важно разделять роли по разным группам нод:

* **Master-ноды**: Управление состоянием кластера. Требуется 3 реплики для кворума.
* **Data-ноды**: Хранение и индексация данных. Требуют максимального дискового пространства и I/O.
* **Ingest-ноды**: Предварительная обработка документов перед индексацией.
* **Ко-локация ролей**: Для небольших инсталляций допустимо совмещать роли (например, `data` и `ingest`) в одной группе нод.

### Ключевые параметры конфигурации

| Категория | Параметр | Описание |
| :--- | :--- | :--- |
| **Кластеризация** | `clusterName` | Должен быть **идентичным** во всех `values.yaml` файлах кластера |
| | `masterService` | Имя сервиса master-нод. Должно быть **идентичным** во всех `values.yaml` |
| **Безопасность** | `allowUnsafeDemoCertificates: false` | Отключить демонстрационные сертификаты для production |
| | `security.tls.transport.pemcert_filepath` | TLS-сертификат для меж nodoвой коммуникации (порт 9300) |
| | `security.tls.http.pemcert_filepath` | TLS-сертификат для HTTP API (порт 9200) |
| | `security.nodes_dn` | Белый список DN сертификатов нод |
| | `security.admin_dn` | DN сертификата суперпользователя |
| | `secretMounts` | Механизм монтирования Kubernetes Secrets с сертификатами |
| **Логирование** | `log4j2.properties` | Включить JSON-логи через `OpenSearchJsonLayout` для автоматизированного парсинга |
| **High Availability** | `podAntiAffinity` | Распределение реплик master-нод по разным узлам Kubernetes (`kubernetes.io/hostname`) |
| | `podManagementPolicy: Parallel` | Rolling update без даунтайма для StatefulSet'ов |
| **Системные** | `vm.max_map_count` | Требуется `>= 262144`. Настраивать на worker-нодах заранее (не через чарт) |

## Практические сценарии

### Развертывание production-кластера

1. **Подготовка сертификатов**: Создайте Kubernetes Secrets с TLS-сертификатами для транспорта и HTTP.
2. **Создание values-файлов**: Подготовьте отдельные файлы для master, data и dashboards с идентичными `clusterName` и `masterService`.
3. **Настройка sysctl**: Убедитесь, что на всех worker-нодах установлен `vm.max_map_count >= 262144`.
4. **Установка чарта**: Выполните `helm install` для каждой группы нод в порядке: master → data → dashboards.
5. **Проверка готовности**: Убедитесь, что все поды перешли в статус `Running` и `Ready`.

### Настройка высокой доступности

* **Распределение master-нод**: Используйте `podAntiAffinity` для распределения по разным физическим узлам.
* **Rolling update**: Установите `podManagementPolicy: Parallel` для StatefulSet'ов master и data нод.
* **Readiness probe**: Настройте корректные проверки готовности для предотвращения простоев при обновлении.
