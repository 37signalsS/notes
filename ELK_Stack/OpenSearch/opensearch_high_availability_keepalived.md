# Отказоустойчивость OpenSearch с помощью Keepalived (Floating VIP)

**Актуально для:** OpenSearch 3.9.x; Keepalived 2.2.8 (Ubuntu 24.04, пакет `1:2.2.8-1build2`) / upstream 2.4.3 (июль 2026)

> Эта заметка рассматривает реализацию высокой доступности (HA) для API OpenSearch с использованием плавающего IP-адреса (VIP). Клиенты взаимодействуют с кластером через единую точку входа, которая автоматически переключается между узлами при сбоях. Заметка является частью обзора [OpenSearch](./opensearch_overview.md); общая теория Keepalived и VRRP (принцип работы Active-Passive, версии VRRPv2/VRRPv3, BFD, тайминги failover) описана в [Keepalived: Обзор и настройка HA](../../Networking/ServicesAndTools/keepalived_overview.md) — здесь сфокусированы аспекты, специфичные именно для кластера OpenSearch.

## Определения

* **Keepalived**: системный демон для Linux, обеспечивающий высокую доступность (HA) через управление виртуальным IP-адресом (VIP) на базе протокола VRRP.
* **Virtual IP (VIP)**: плавающий IP-адрес, который логически принадлежит всему кластеру, но физически назначен только одному активному узлу (MASTER) в конкретный момент времени.
* **VRRP (Virtual Router Redundancy Protocol)**: сетевой протокол, используемый для обнаружения отказов MASTER-узла и автоматического выбора нового владельца VIP. Работает поверх IP с номером протокола 112 (не TCP/UDP-порт).
* **Unicast VRRP**: режим работы, при котором пакеты VRRP отправляются на конкретные IP-адреса участников кластера (в отличие от Multicast), что является стандартом для облачных сред (AWS, GCP, Azure), где мультикаст часто заблокирован.
* **Non-local Bind**: параметр ядра Linux (`net.ipv4.ip_nonlocal_bind`), позволяющий процессам привязываться к IP-адресам, которые физически не назначены ни одному интерфейсу на текущем хосте (необходимо для запуска OpenSearch на BACKUP-узлах при бинде непосредственно к VIP).
* **Split-brain**: состояние, при котором несколько узлов одновременно считают себя MASTER и назначают себе VIP из-за проблем с сетевой связностью (heartbeats не проходят).
* **Preemption (Вытеснение)**: поведение, при котором восстановленный узел с более высоким приоритетом принудительно забирает роль MASTER у текущего владельца.
* **Gratuitous ARP (GARP)**: беззапросный ARP-ответ, который новый MASTER рассылает в L2-сегмент после получения VIP, чтобы коммутаторы и клиенты обновили записи ARP-кэша (соответствие IP → MAC). Без GARP клиенты продолжают слать трафик на MAC старого узла до истечения TTL кэша.

## Основные концепции

### Архитектура отказоустойчивости

Для обеспечения HA используется кластер из 3 узлов (например, на Ubuntu 24.04).
- OpenSearch слушает на порту 9200.
- Виртуальный IP (VIP): `10.0.1.10/24`.

**Целевая конфигурация узлов:**

| Имя узла | Физический IP | Роль Keepalived | Приоритет |
| :--- | :--- | :--- | :--- |
| **os-node-1** | 10.0.1.1 | MASTER (BACKUP*) | 103 |
| **os-node-2** | 10.0.1.2 | BACKUP | 102 |
| **os-node-3** | 10.0.1.3 | BACKUP | 101 |

*\*Примечание: Для использования стратегии `nopreempt` все узлы в конфиге указываются как BACKUP, а MASTER выбирается на основе приоритета при первом запуске.*

VIP обеспечивает HA только **точки входа клиентов** (HTTP API, порт 9200). Внутрикластерное транспортное взаимодействие OpenSearch (порт 9300, discovery, репликация шардов) всегда идет по физическим IP: параметры `discovery.seed_hosts` и `cluster.initial_cluster_manager_nodes` должны содержать физические адреса узлов, но никогда — VIP. Иначе при миграции VIP кластер начнет «переезжать» целиком и потеряет кворум.

Ограничение L2: VIP обязан находиться в том же broadcast-домене (L2-подсети), что и физические IP узлов — VRRP-анонсы не маршрутизируются. Для узлов в разных ЦОД, связанных только L3-каналом, схема неприменима; там используются BGP anycast или DNS-failover (см. [Keepalived: Обзор](../../Networking/ServicesAndTools/keepalived_overview.md), раздел «Ограничение L2 и альтернативы»).

### Как работает VRRP (кратко для контекста)

Узлы объединены в виртуальный роутер с идентификатором `virtual_router_id` (VRID, 1–255), уникальным в пределах L2-сегмента. Каждый узел имеет статический приоритет (1–255). MASTER каждые `advert_int` секунд рассылает анонсы (advertisements) со своим приоритетом; BACKUP-узлы слушают их. Если анонсы не приходят в течение `master_down_interval` (≈ `3 × advert_int` + skew-поправка `(256 − priority)/256`, то есть ~3–4 секунды при `advert_int 1`), узел с наибольшим приоритетом объявляет себя MASTER и назначает себе VIP. Состояния экземпляра: `INIT` → `BACKUP` → `MASTER`; при провале проверок (`track_script`, `track_interface`) узел уходит в `FAULT`, полностью освобождая участие в выборах, а после восстановления проверок возвращается в `BACKUP`.

Важно различать два механизма детекции отказа, работающих последовательно:

1. **Сбой сервиса** (OpenSearch упал/RED): обнаруживается скриптом проверки за `interval × fall` секунд; приоритет узла снижается на величину `weight`, что заставляет его уступить роль соседям без разрыва VRRP-связности.
2. **Сбой узла целиком** (kernel panic, питание, сеть): анонсы перестают приходить, соседи выбирают нового мастера за ~3–4 секунды по таймауту.

Худший случай полного failover — сумма обоих: до `interval × fall + master_down_interval` (~10 секунд при настройках из этой заметки: 6 с детекта скриптом + ~3,6 с таймаута выборов).

### Нелокальная привязка IP (Non-local Bind)

В конфигурации HA критически важно включить `net.ipv4.ip_nonlocal_bind=1`. Без этого параметра OpenSearch на BACKUP-узлах может не запуститься или выдать ошибку при попытке бинда к VIP, который им еще не принадлежит. Это обеспечивает мгновенную готовность бэкенда при миграции IP.

Нюанс: если OpenSearch слушает все интерфейсы (`network.host: "0.0.0.0"`), ядро позволяет бинд на `0.0.0.0` без данного параметра, и сервис стартует на любом узле независимо от наличия VIP. `ip_nonlocal_bind=1` становится строго обязательным, когда какой-либо компонент (сам OpenSearch, sidecar-прокси, экспортер метрик) привязывается явно к адресу VIP или когда требуется, чтобы сервис отвечал на VIP сразу после его появления. Параметр включается «про запас» на всех узлах — он безвреден и снимает целый класс ошибок запуска.

### Защита от Split-brain и мигания (Flapping)

1.  **Unicast Mode**: Использование Unicast вместо Multicast исключает влияние VRRP-трафика соседних кластеров и обходит ограничения облачных провайдеров.
2.  **Health Check Script**: Использование "глубокой" проверки (Cluster Health API) вместо простой проверки порта 9200 гарантирует, что VIP переедет, если OpenSearch запущен, но кластер находится в состоянии `RED`.
3.  **Nopreempt Strategy**: Предотвращает "мигание" VIP, когда восстановившийся мастер-узел забирает роль обратно, вызывая второй разрыв соединений. Для OpenSearch стабильность сессий важнее, чем работа именно на "первом" узле.

Дополнительная защита: строгие симметричные правила firewall для VRRP-трафика между пирами (см. сценарий настройки сети ниже) и мониторинг логов на предмет сообщений о форсированной смене мастера.

### Проблема ARP-кэша и Gratuitous ARP

Failover на уровне IP сам по себе недостаточен: Ethernet-коммуникация адресуется MAC-адресами. После переезда VIP новый MASTER обязан оповестить L2-сегмент, что теперь IP `10.0.1.10` соответствует его MAC. Keepalived делает это автоматически, отправляя серию gratuitous ARP после перехода в MASTER; поведение настраивается глобальными директивами:

```text
# /etc/keepalived/keepalived.conf, секция global_defs
global_defs {
    router_id os-node-1          # идентификатор узла в логах и статистике
    vrrp_garp_master_delay      5    # пауза перед повторной серией GARP после смены мастера (по умолчанию 5с)
    vrrp_garp_master_repeat     5    # число GARP-пакетов в серии (по умолчанию 5)
    vrrp_garp_master_refresh   60    # периодическая "подпитка" ARP-кэшей (по умолчанию 0 = выключено)
}
```

Именование важно: в `global_defs` GARP-директивы имеют префикс `vrrp_` (`vrrp_garp_master_delay`), внутри `vrrp_instance` — нет (`garp_master_delay`). Директивы без префикса в `global_defs` — неизвестные ключевые слова, и конфигурация не загрузится. Keepalived отправляет первую серию GARP сразу при переходе в MASTER, а `vrrp_garp_master_delay` задаёт паузу перед повторной серией.

Практическое следствие: короткий всплеск ошибок соединения в первые секунды после failover — норма (клиенты, чьи TCP-сессии были привязаны к старому узлу, рвутся гарантированно). Если же ошибки длятся минуты — проблема в GARP (фильтрация unsolicited ARP гипервизором/коммутатором) либо в DNS-закреплении клиента за конкретным узлом.

### TLS-сертификаты и SAN с VIP

Клиенты обращаются к `https://10.0.1.10:9200` (или к DNS-имени, указывающему на VIP). Сертификат HTTP-слоя OpenSearch должен содержать VIP и/или это DNS-имя в Subject Alternative Name, иначе каждый клиент будет получать ошибку проверки сертификата и будет вынужден использовать `-k/--insecure`. Правильная практика — внутренний CA выпускает один сертификат со списком SAN: физические IP всех узлов + VIP + DNS-имена. Транспортное шифрование между узлами (9300) при этом может использовать отдельные per-node сертификаты — оно не связано с клиентским входом через VIP.

### Место схемы среди альтернатив

Floating VIP — самый простой механизм HA точки входа, не требующий дополнительного ПО на клиентах. Альтернативы: балансировщик (HAProxy/Nginx перед узлами — добавляет собственную точку отказа, которую снова нужно резервировать через тот же Keepalived), DNS round-robin (не решает быстрый failover из-за TTL записей), client-side retry по списку узлов (надежно, но требует поддержки в каждом клиенте). На практике VIP часто комбинируют с retry-логикой клиентов: VIP переживает отказы узлов, retry переживает краткие разрывы при самой миграции. Тот же паттерн применяется и к другим сервисам: пример настройки связки Keepalived + VRRP для веб-сервера описан в [Angie HA с Keepalived](../../WebServers/Angie/angie_ha_with_keepalived.md), а общие механизмы failover — в [Механизмы переключения при отказе](../../Concepts/High_Availability/ha_failover_mechanisms.md).

## Практические сценарии

### 1. Подготовка системы и OpenSearch

На всех узлах кластера выполните настройку ядра и сети.

```bash
# Разрешение привязки к нелокальным IP
echo "net.ipv4.ip_nonlocal_bind = 1" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
# → net.ipv4.ip_nonlocal_bind = 1

# Проверка значения
sysctl net.ipv4.ip_nonlocal_bind
# → net.ipv4.ip_nonlocal_bind = 1
```

Настройка OpenSearch на прослушивание всех интерфейсов:

```yaml
# /etc/opensearch/opensearch.yml
network.host: "0.0.0.0"

# Discovery строго по физическим IP, не по VIP:
discovery.seed_hosts: ["10.0.1.1", "10.0.1.2", "10.0.1.3"]
```

```bash
# Перезапуск сервиса и проверка слушающих сокетов
sudo systemctl restart opensearch
ss -tlnp | grep -E ':(9200|9300)'
# → LISTEN 0 4096 *:9200 ... users:(("opensearch",pid=...))
# → LISTEN 0 4096 *:9300 ... users:(("opensearch",pid=...))
```

### 2. Установка и настройка Keepalived

Установите необходимые пакеты на всех узлах:
```bash
sudo apt update && sudo apt install keepalived curl jq -y

keepalived --version
# → Keepalived v2.2.8 (пакет Ubuntu 24.04: 1:2.2.8-1build2; актуальный upstream — 2.4.3, июль 2026)
```

Создайте скрипт проверки `/etc/keepalived/check_opensearch.sh`:
```bash
#!/bin/bash
# Проверка здоровья API. Возвращаем 0 для green/yellow, 1 для red/down.
STATUS=$(curl -s -k -m 2 "https://localhost:9200/_cluster/health" | grep -oP '(?<="status":")[^"]*')
if [ "$STATUS" = "green" ] || [ "$STATUS" = "yellow" ]; then exit 0; else exit 1; fi
```
`chmod +x /etc/keepalived/check_opensearch.sh`

**Учетные данные и безопасность скрипта.** При включенном security-плагине эндпоинт `/_cluster/health` требует авторизацию — без нее `curl` получит `401`, переменная останется пустой, и скрипт всегда будет возвращать 1, уводя VIP с исправного узла. Варианты решения:

```bash
# Вариант А: учетные данные в скрипте (обязательна защита файла)
STATUS=$(curl -sk -m 2 -u "$OS_USER:$OS_PASS" \
  "https://localhost:9200/_cluster/health" | grep -oP '(?<="status":")[^"]*')

# Вариант Б: парсинг через jq (переносимее regex)
STATUS=$(curl -sk -m 2 -u "$OS_USER:$OS_PASS" \
  "https://localhost:9200/_cluster/health" | jq -r '.status')
```

Начиная с keepalived 2.x скрипты по умолчанию выполняются от пользователя `keepalived_script` (если он создан), иначе от root; при запуске от root на старте проверяется, что файл скрипта и весь путь к нему недоступны на запись другим пользователям — иначе скрипт не запустится (keepalived записывает ошибку в лог). Если скрипт содержит креды — создайте служебного пользователя и ограничьте права:

```bash
sudo useradd -r -s /sbin/nologin -M keepalived_script
sudo chown root:keepalived_script /etc/keepalived/check_opensearch.sh
sudo chmod 750 /etc/keepalived/check_opensearch.sh   # чтение/запуск только для группы
```

Для проверки выделите служебного пользователя OpenSearch с ролью, имеющей только право `cluster:monitor/health` (создание пользователей и ролей описано в [Администрирование OpenSearch](./opensearch_administration.md)). Флаг `-k` можно убрать после выпуска сертификата с SAN, включающим VIP/DNS-имя (см. соответствующий раздел выше).

#### Пример конфигурации (Узел 1)
Создайте `/etc/keepalived/keepalived.conf` (для остальных узлов измените `priority` и `unicast_src_ip`).

```keepalived
vrrp_script chk_opensearch {
    script "/etc/keepalived/check_opensearch.sh"
    interval 2
    fall 3
    rise 2
    timeout 5
    weight -20
}

vrrp_instance VI_OS {
    state BACKUP
    nopreempt
    interface ens160          # Имя вашего интерфейса
    virtual_router_id 53      # Должен быть уникальным в сети
    priority 103              # 103, 102, 101 соответственно
    advert_int 1
    
    unicast_src_ip 10.0.1.1   # IP этого узла
    unicast_peer {
        10.0.1.2
        10.0.1.3
    }

    virtual_ipaddress {
        10.0.1.10/24 dev ens160 label ens160:vip
    }

    track_script {
        chk_opensearch
    }
}
```

### 3. Разбор параметров конфигурации

| Параметр | Описание |
| :--- | :--- |
| **vrrp_script** | Блок логики проверки здоровья сервиса. |
| **script** | Путь к исполняемому файлу проверки (рекомендуется API check). |
| **interval** | Период запуска скрипта в секундах (2 = проверка каждые 2с). |
| **fall / rise** | Сколько подряд неудачных/успешных запусков нужно для смены состояния (гистерезис против flapping). |
| **timeout** | Максимальное время выполнения скрипта; превышение считается неудачей (защита от зависшего `curl`). |
| **weight -20** | Динамическое снижение приоритета при сбое скрипта. Значение должно превышать разницу приоритетов между соседями (103−102=1), чтобы гарантировать передачу роли; запас −20 безопасен и при этом сохраняет узел участником выборов (при weight ≤ −(priority) узел ушел бы в FAULT). |
| **state BACKUP** | Начальное состояние; для `nopreempt` обязательно BACKUP на всех узлах. |
| **nopreempt** | Отключает автоматический возврат VIP на узел с высшим приоритетом. |
| **interface** | Интерфейс, на котором слушаются анонсы и назначается VIP. |
| **virtual_router_id** | Уникальный ID группы 1–255 в пределах L2-сегмента (защита от конфликтов с другими кластерами). |
| **priority** | Статический приоритет узла 1–255; выбирается узел с наибольшим значением. |
| **advert_int** | Интервал анонсов мастера в секундах; таймаут выборов ≈ 3 × advert_int. |
| **unicast_src_ip / unicast_peer** | Собственный IP и список IP других узлов (cloud-ready режим). |
| **label ens160:vip** | Создание алиаса интерфейса для удобства диагностики в `ip a`. |
| **track_script** | Привязка результата скрипта к приоритету экземпляра VRRP. |

Дополнительно доступны хуки `notify_master` / `notify_backup` / `notify_fault` / `notify_stop` (при остановке keepalived) внутри `vrrp_instance` — пользовательские скрипты, выполняемые при смене состояний (например, отправка алерта в мессенджер или переключение DNS-записи). Для контроля здоровья самого сетевого интерфейса используется блок `track_interface { ens160 }`: без него отказ NIC не понизит приоритет, пока жив сам процесс keepalived.

### 4. Настройка сетевого экрана

VRRP-пакеты идут поверх IP с номером протокола **112** — это не TCP- и не UDP-порт, поэтому правила вида «разрешить порт 112» через типовые интерфейсы ufw/firewalld не работают напрямую. Разрешите протокол только между пирами:

```bash
# iptables (на каждом узле — разрешить VRRP от двух пиров)
sudo iptables -A INPUT -p 112 -s 10.0.1.2 -j ACCEPT
sudo iptables -A INPUT -p 112 -s 10.0.1.3 -j ACCEPT

# nftables
sudo nft add rule inet filter input ip protocol vrrp ip saddr { 10.0.1.2, 10.0.1.3 } accept

# Проверка прохождения анонсов (запустить на одном узле, смотреть поток пакетов)
sudo tcpdump -i ens160 -nn vrrp
# → 10.0.1.2 > 10.0.1.3: VRRPv2, Advertisement, vrid 53, prio 102, intv 1
```

Для ufw протокол добавляется вручную в `/etc/ufw/before.rules` строкой `-A ufw-before-input -p 112 -j ACCEPT` перед правилом `ufw-track-input`, затем `sudo ufw reload`.

### 5. Запуск и базовая верификация

```bash
sudo systemctl enable --now keepalived

# Состояние сервиса
systemctl status keepalived --no-pager | head -5
# → Active: active (running) since ...

# Кто владеет VIP сейчас (искать inet 10.0.1.10/24 ...)
ip addr show ens160
# → inet 10.0.1.10/24 scope global secondary ens160:vip

# Логи смены состояний в реальном времени
journalctl -u keepalived -f
# → VRRP_Instance(VI_OS) Entering MASTER STATE
# → VRRP_Instance(VI_OS) Entering BACKUP STATE

# Проверка ответа API через VIP с внешней машины
curl -sk https://10.0.1.10:9200/
# → {"name" : "os-node-1", ... ,"cluster_name" : "...", "version" : {...}}
```

Повторите `ip addr show` на всех узлах: VIP должен присутствовать ровно на одном.

### 6. Тестирование отказоустойчивости

Проведите следующие тесты:

1.  **Остановка OpenSearch**: `sudo systemctl stop opensearch` на MASTER.
    *   **Ожидаемый результат**: Через `interval * fall` (6 сек) VIP пропадает с текущего узла и появляется на узле с приоритетом 102.
2.  **Имитация Split-brain**: Блокировка VRRP-трафика (IP-протокол 112, не UDP-порт) в одну сторону — например, `sudo iptables -A OUTPUT -p 112 -d <peer_ip> -j DROP` на одном из узлов.
    *   **Ожидаемый результат**: Узел, не получающий анонсы, объявит себя MASTER. Защита — строгие правила FW и мониторинг логов `Keepalived: VRRP_Instance(VI_OS) forcing new master keepalived`.
3.  **Восстановление (Recovery)**: Запустите OpenSearch на исходном мастере.
    *   **Ожидаемый результат**: Благодаря `nopreempt`, VIP останется на текущем узле. MASTER перейдет в состояние `BACKUP` и будет ждать сбоя текущего лидера.
4.  **Полный отказ узла**: `sudo reboot` активного MASTER.
    *   **Ожидаемый результат**: Анонсы прекращаются; новый мастер избирается по таймауту ~3–4 секунды (`master_down_interval`). Клиенты, переподключившиеся после серии GARP, продолжают работать с тем же адресом.

Критерий прохождения всех тестов: `curl -sk https://10.0.1.10:9200/_cluster/health` отвечает после каждого шага сценария (за исключением окон миграции длительностью до ~10 секунд).

### 7. Мониторинг Keepalived

```bash
# Снимок статистики VRRP (запись в /tmp/keepalived.stats)
sudo kill -USR2 $(cat /run/keepalived.pid)
# или через встроенный resolver номера сигнала:
sudo kill -s $(keepalived --signum=STATS) $(cat /run/keepalived.pid)

# Метрики для Prometheus через community-экспортер
# https://github.com/mehdy/keepalived-exporter — состояние экземпляра, счетчики переходов
```

Не путайте сигналы: `SIGUSR2` (`STATS`) пишет статистику в `/tmp/keepalived.stats`, а `SIGUSR1` (`DATA`) — конфигурацию в `/tmp/keepalived.data`.

Минимальный набор алертов: отсутствие VRRP Instance в состоянии MASTER на любом узле, рост числа переходов состояния за час (признак flapping), расхождение владельца VIP между узлами. Диагностические приемы (`tcpdump -nn vrrp`, разбор логов, статистика) подробно описаны в разделе [Диагностика](../../Networking/ServicesAndTools/keepalived_overview.md#диагностика) обзора Keepalived.

### Граничные случаи и ограничения

* **RED-кластер на всех узлах.** Если кластер в состоянии `RED` на всех узлах, health-скрипт падает везде одновременно; приоритеты снижаются одинаково, и VIP остаётся на узле с наибольшим базовым приоритетом. Схема констатирует проблему (алерт на отсутствие `green`/`yellow`), но не может «вылечить» кластер: VIP продолжает отвечать, а запись в кластер недоступна.
* **Субсекундные интервалы анонсов.** Дробный `advert_int` (например, `0.5`) работает только с `vrrp_version 3`: VRRPv3 передаёт интервал в центисекундах (минимум `0.01`), а VRRPv2 округляет дробную часть до целых секунд. Ускоряет выборы нового мастера до ~1,5 с, но требует стабильного L2-канала — на lossy-сетях ложные переключения учащаются.
* **Потеря пакетов в сети.** При нестабильном канале увеличьте устойчивость опцией `down_timer_adverts` (например, `10`): мастер считается недоступным после 10 пропущенных анонсов вместо 3. Опция не соответствует RFC (доступна с keepalived 2.1.x), но оправдана в сетях с потерями.
* **Аутентификация анонсов.** Для unicast-деплоев, где анонсы проходят через маршрутизаторы, в Keepalived 2.4.0+ доступно расширение `auth_hmac` (HMAC-SHA256-подпись каждого анонса) — рекомендуемая защита от spoofing/replay. Все узлы виртуального роутера обязаны работать на одной версии 2.4.1+ (формат trailer изменился между 2.4.0 и 2.4.1). В Ubuntu 24.04 (2.2.8) недоступно.
* **Лёгкая альтернатива скрипту.** `vrrp_track_process` (с keepalived 2.0) отслеживает существование процесса без shell-вызова — быстрее и дешевле, но проверяет только живость процесса: RED-кластер с живым процессом приоритет не понизит. Для OpenSearch оставьте API-проверку.

## Лучшие практики

* **Учения по расписанию.** Прогоните сценарий 6 (остановка сервиса, отказ узла, recovery) не реже раза в квартал: failover, не проверенный на практике, не работает.
* **Конфигурация в системе управления конфигурацией.** Развертывайте `keepalived.conf` и health-скрипт через Ansible (см. [Развертывание с помощью Ansible](./opensearch_ansible_deployment.md)); ручные правки на узлах расходятся и приводят к рассинхронизации `virtual_router_id` и приоритетов.
* **Различные приоритеты.** Приоритеты узлов должны быть различны (103/102/101): равные приоритеты делают выбор мастера при старте недетерминированным.
* **Симметричность firewall.** Проверяйте правила VRRP в обоих направлениях (`iptables -L INPUT -v -n` и `iptables -L OUTPUT -v -n`): однонаправленная блокировка — классическая причина split-brain.
* **Мониторинг переходов, а не только VIP.** Следите за счётчиком переходов состояния (keepalived-exporter): его рост — ранний признак нестабильности сети или скрипта проверки, задолго до потери доступности.
* **TLS без `-k`.** Выпускайте сертификат с SAN, включающим VIP и DNS-имя, чтобы клиенты не отключали проверку сертификата (см. раздел «TLS-сертификаты и SAN с VIP»).
* **Runbook обслуживания.** Задокументируйте принудительную передачу VIP при плановом обслуживании узла: `sudo systemctl stop keepalived` на MASTER — VIP уходит на соседа без ожидания таймаутов.

## Устранение неполадок

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| VIP не появляется ни на одном узле | Firewall блокирует протокол 112; разные `virtual_router_id` у пиров; неверный `interface` | Проверить `tcpdump -i ens160 vrrp`; сверить VRID и имя интерфейса во всех конфигах |
| Два узла одновременно MASTER | Однонаправленная блокировка VRRP-трафика; несимметричные правила FW | Восстановить симметрию правил; искать в логах `forcing new master` |
| Клиент получает ошибки соединения минуты после failover | ARP-кэши не обновились: GARP отфильтрован гипервизором/коммутатором или клиент закреплен за старым MAC | Настроить `garp_master_repeat/refresh`; проверить политику unsolicited ARP на сетевом оборудовании |
| VIP постоянно переезжает с узла на узел | Health check нестабилен (таймауты curl при нагрузке); preemption включен | Увеличить `fall`/`timeout`, включить `nopreempt` |
| Скрипт проверки всегда возвращает 1 при живом кластере | 401 Unauthorized из-за security-плагина; нет прав на выполнение скрипта | Добавить `-u` с кредами служебного пользователя; проверить chmod/chown и путь (script security) |
| Узел навсегда в состоянии FAULT | Провал `track_interface` или скрипта после старта | `journalctl -u keepalived`; исправить причину провала — узел сам вернется в BACKUP |
| OpenSearch на BACKUP-узле не биндится к адресу | Отсутствует `net.ipv4.ip_nonlocal_bind=1` при явном бинде к VIP | Включить sysctl либо слушать `0.0.0.0` |

## Очистка окружения

Откат схемы HA выполняется на каждом узле:

```bash
sudo systemctl disable --now keepalived
sudo rm /etc/keepalived/keepalived.conf /etc/keepalived/check_opensearch.sh

# Убрать строку net.ipv4.ip_nonlocal_bind из /etc/sysctl.conf, затем:
sudo sysctl -w net.ipv4.ip_nonlocal_bind=0
```

После остановки keepalived VIP снимается автоматически; если адрес «завис» на интерфейсе — удалить вручную: `sudo ip addr del 10.0.1.10/24 dev ens160`. Сам кластер OpenSearch продолжит работу: клиенты переключаются на прямые физические адреса или DNS.
