# OpenSearch: Управление жизненным циклом индексов (ISM)

Index State Management (ISM) — часть плагина Index Management, которая избавляет администратора от ручной рутины обслуживания временных рядов: ротации, оптимизации сегментов, переноса на дешевые уровни хранения и удаления устаревших индексов. Актуальная документация соответствует ветке OpenSearch 3.x; ключевые возможности уровня хранения (searchable snapshots) общедоступны начиная с версии 2.7.

## Определения

* **Index State Management (ISM)** — плагин OpenSearch, предназначенный для автоматизации задач по управлению индексами (ротация, оптимизация, перенос на разные уровни хранения, удаление) на основе заданных политик. Является функциональным аналогом **Index Lifecycle Management (ILM)** в Elasticsearch. Политика описывается как конечный автомат; фоновое задание обходит управляемые индексы раз в 5 минут (настраивается), проверяет условия и выполняет действия.
* **Rollover (Ротация)** — процесс создания нового индекса для записи, когда текущий достигает определенных лимитов (размер, возраст, количество документов). Это позволяет поддерживать оптимальный размер шардов. Для работы требует либо алиас записи (`is_write_index: true` + настройка `plugins.index_state_management.rollover_alias`), либо Data Stream, где механика ротации встроена изначально.
* **Force Merge** — процедура объединения сегментов Lucene для уменьшения их количества, что ускоряет поиск и освобождает место на диске за счет удаления помеченных на удаление документов. Рекомендуется выполнять до помещения индекса в снапшот — чтение из удаленного хранилища идет посегментно, и меньшее число сегментов ускоряет запросы.
* **Remote Store (Удаленное хранилище)** — возможность OpenSearch загружать сегменты и метаданные в объектное хранилище (S3) практически в реальном времени, параллельно с локальной записью. Отличать от searchable snapshots: Remote Store работает постоянно для активных индексов (цель — надежность и быстрое восстановление), а searchable snapshots — модель хранения «источник данных в объектном хранилище» для холодных данных. Состояние загрузки контролируется через Remote Store Stats API.
* **Searchable Snapshots (Поисковые снимки)** — технология (GA с версии 2.7), позволяющая выполнять поисковые запросы напрямую по данным, хранящимся в снимках (S3), без полного восстановления индекса на узлы. Индекс восстанавливается с типом хранилища `remote_snapshot`: метаданные лежат локально, сегменты скачиваются и кэшируются по мере обращения. Для восстановления требуется хотя бы один узел с ролью `warm`; соотношение объема удаленных данных к размеру локального кэша регулируется настройкой `cluster.filecache.remote_data_ratio`.
* **Политика (Policy)** — JSON-документ, описывающий состояния индекса (`states`), выполняемые в них операции (`actions`) и условия смены состояний (`transitions`). Привязывается к индексу явно или автоматически через `ism_template`.

## Основные концепции

### Фазы жизненного цикла индекса

В OpenSearch ISM политика представляет собой конечный автомат, где индекс переходит из одного состояния в другое при выполнении определенных условий (**Transitions**).

1.  **Горячая фаза (Hot)**:
    *   Индексы открыты для записи и активного поиска.
    *   Используются быстрые носители (NVMe/SSD).
    *   Основное действие: `rollover` (переключение на новый индекс).
2.  **Тёплая фаза (Warm)**:
    *   Индекс закрыт для записи (`read_only`), но часто запрашивается.
    *   Оптимизация: `force_merge` до 1 сегмента, уменьшение количества реплик для экономии места.
    *   Может использоваться перенос на более дешевые HDD через действие `allocation` (например, `"require": { "temp": "warm" }`).
3.  **Холодная фаза (Cold)**:
    *   Данные запрашиваются редко.
    *   Два механизма перевода в холодный уровень:
        *   действие **`cold_storage`** — ISM создает снимок индекса в настроенном репозитории, удаляет локальные копии; данные остаются доступны для поиска как remote snapshot;
        *   явный конвейер **`snapshot` → `convert_index_to_remote`** — то же самое, но с раздельным контролем каждого шага (удобно для аудита и повторных попыток).
    *   Индекс остается видимым и доступным для поиска; латентность запросов выше, так как сегменты читаются из объектного хранилища через локальный кэш.
4.  **Удаление (Delete)**:
    *   Окончательное удаление индекса или его перевод в долгосрочный архив (Snapshot) перед удалением.

### Компоненты политики

*   **States**: Состояния, в которых может находиться индекс (например, `hot`, `delete`). Индекс находится ровно в одном состоянии; при входе в состояние действия выполняются последовательно, после их завершения проверяются условия переходов. Обязательное поле политики `default_state` задает начальное состояние.
*   **Actions**: Операции, выполняемые внутри состояния (например, `rollover`, `snapshot`, `notification`). Полный перечень — в таблице ниже.
*   **Transitions**: Логика перехода между состояниями на основе условий (`min_index_age`, `min_doc_count`, `min_size`, `min_primary_shard_size`, `cron`).
*   **ISM Template**: Автоматическое применение политики к новым индексам по маске имени (`index_patterns`, `priority`). Действует только для индексов, созданных после привязки политики — существующие индексы подключаются вручную.
*   **Error Notification**: Блок `error_notification` политики — отправка сообщения через плагин Notifications при сбое любого действия (например, неудачном rollover).

### Поддерживаемые действия (Actions)

| Группа | Действие | Назначение |
| :--- | :--- | :--- |
| Запись и доступ | `read_only` | Перевод индекса в режим только чтение |
| Запись и доступ | `read_write` | Возврат режима чтения-записи |
| Запись и доступ | `close` / `open` | Закрытие индекса (не ищется, не нагружает кластер) и открытие обратно |
| Ротация и размещение | `rollover` | Создание нового индекса для записи при достижении лимитов |
| Ротация и размещение | `allocation` | Перенос шардов на узлы по атрибутам (`require`, `include`, `exclude`) |
| Ротация и размещение | `replica_count` | Изменение числа реплик |
| Ротация и размещение | `index_priority` | Приоритет индекса при восстановлении после сбоя кластера |
| Оптимизация | `force_merge` | Объединение сегментов Lucene (`max_num_segments`) |
| Оптимизация | `shrink` | Уменьшение числа первичных шардов (`num_new_shards`) |
| Оптимизация | `rollup` | Свертка исторических данных в агрегированные индексы |
| Хранение и архив | `snapshot` | Создание снимка в указанный репозиторий |
| Хранение и архив | `cold_storage` | Перевод в холодный уровень через searchable snapshot |
| Хранение и архив | `convert_index_to_remote` | Конвертация индекса в searchable snapshot на указанном репозитории |
| Хранение и архив | `stop_replication` | Остановка cross-cluster replication для индекса |
| Служебные | `delete` | Удаление индекса |
| Служебные | `alias` | Добавление/удаление алиасов у индекса |
| Служебные | `notification` | Точечная отправка уведомления в середине политики |

### Условия переходов (Transition Conditions)

| Условие | Отсчитывается от | Типичное применение |
| :--- | :--- | :--- |
| `min_index_age` | Даты создания индекса | Классические временные политики: 30d, 90d |
| `min_doc_count` | Количества документов | Ротация мелких индексов |
| `min_size` | Суммарного размера индекса (вместе с репликами) | Ротация по объему |
| `min_primary_shard_size` | Размера наибольшего первичного шарда | Контроль оптимального размера шарда (30–50 ГБ) |
| `cron` | Расписания (5 полей: минута час день месяц день недели, с таймзоной) | Обслуживание вне пиковых часов |

Ограничение: возраст индекса считается от даты создания, а не от последней записи — для потоков, «доживающих» неделями без новых документов, закладывайте это в сроки удаления.

### Как работает движок ISM

* После привязки политики к индексу создается фоновое задание, которое по умолчанию выполняется каждые **5 минут** (кластерная настройка `plugins.index_state_management.job_interval`); на Amazon OpenSearch Service фактический интервал составляет 5–8 минут из-за случайного разброса запусков.
* Задания не выполняются, пока состояние кластера **red**.
* Параметр jitter (случайная задержка запуска, диапазон 0–1) распределяет старты заданий во времени, предотвращая одновременную нагрузку от сотен индексов.
* Автоматическое применение политики через `ism_template` охватывает только новые индексы; существующие подключаются через API `_ism/add` или установкой legacy-настройки `opendistro.index_state_management.policy_id` на уровне индекса.

## Практические сценарии

Все примеры совместимы с веткой OpenSearch 3.x; канонический префикс эндпоинтов — `_plugins/_ism/policies/`.

### 1. Политика долгосрочного хранения (полный цикл, 3 года)

Сценарий для критически важных логов: Hot (7 дней или 30 ГБ) -> Warm (оптимизация) -> Cold (S3) -> Delete через 3 года с момента создания.

```json
PUT /_plugins/_ism/policies/long_term_retention
{
  "policy": {
    "description": "7д Hot (или 30ГБ), Warm, Cold в S3, удаление через 1095 дней",
    "default_state": "hot",
    "states": [
      {
        "name": "hot",
        "actions": [
          {
            "rollover": {
              "min_primary_shard_size": "30gb",
              "min_index_age": "7d"
            }
          }
        ],
        "transitions": [{ "state_name": "warm" }]
      },
      {
        "name": "warm",
        "actions": [
          { "replica_count": { "number_of_replicas": 1 } },
          { "force_merge": { "max_num_segments": 1 } },
          { "read_only": {} }
        ],
        "transitions": [{ "state_name": "cold" }]
      },
      {
        "name": "cold",
        "actions": [{ "cold_storage": {} }],
        "transitions": [
          {
            "state_name": "delete",
            "conditions": { "min_index_age": "1095d" }
          }
        ]
      },
      {
        "name": "delete",
        "actions": [{ "delete": {} }]
      }
    ],
    "ism_template": {
      "index_patterns": ["logs-prod-*"],
      "priority": 10
    }
  }
}
# → {"_id":"long_term_retention","primary_term":1,"seq_no":0,"policy":{...}}
```

Ключевые решения: `force_merge` до 1 сегмента выполняется до перевода в холодное хранилище — это ускоряет последующие запросы из S3; реплики сокращаются до 1 только после ротации (горячий индекс сохраняет отказоустойчивость записи); возраст для удаления считается от даты создания индекса, поэтому суммарный срок жизни предсказуем независимо от момента ротации. Для действия `cold_storage` заранее зарегистрируйте репозиторий снимков (сценарий 3).

### 2. Полный цикл настройки rollover с нуля

Пошаговое развертывание классической схемы на алиасах (официальный workflow проекта; тестовые пороги — чтобы увидеть результат за минуты).

**Шаг 1. Политика с авто-применением по маске:**

```json
PUT _plugins/_ism/policies/rollover_policy
{
  "policy": {
    "description": "Тестовая политика ротации",
    "default_state": "rollover",
    "states": [
      {
        "name": "rollover",
        "actions": [
          { "rollover": { "min_doc_count": 1 } }
        ],
        "transitions": []
      }
    ],
    "ism_template": {
      "index_patterns": ["log*"],
      "priority": 100
    }
  }
}
# → {"_id":"rollover_policy","primary_term":1,"seq_no":0,...}
```

**Шаг 2. Шаблон индекса с настройкой алиаса ротации:**

```json
PUT _index_template/ism_rollover
{
  "index_patterns": ["log*"],
  "template": {
    "settings": {
      "plugins.index_state_management.rollover_alias": "log"
    }
  }
}
```

**Шаг 3. Создание первого индекса с алиасом записи:**

```json
PUT log-000001
{
  "aliases": {
    "log": { "is_write_index": true }
  }
}
```

**Шаг 4. Запись документа и проверка:**

```json
POST log/_doc
{ "message": "dummy" }
```

```bash
GET _plugins/_ism/explain/log-000001?pretty
# → В ответе: "policy_id":"rollover_policy", "state":{"name":"rollover"},
# → "info" содержит статус действия rollover; после выполнения задания
# → появится индекс log-000002, а алиас log переключится на него.
```

Механика: без настройки `rollover_alias` в шаблоне действие завершится ошибкой (`Missing rollover alias`); алиас обязан существовать до первой ротации, и ровно один индекс должен быть помечен `is_write_index: true`. Для конкретного индекса ротацию можно исключить настройкой `index.plugins.index_state_management.rollover_skip: true`.

### 3. Холодное хранение на S3: подготовка и проверка

Предварительные требования для действий `cold_storage` / `convert_index_to_remote`:

1. Установленный на узлах плагин `repository-s3` (входит в стандартный дистрибутив).
2. Зарегистрированный репозиторий снимков:

```json
PUT _snapshot/cold-repo
{
  "type": "s3",
  "settings": {
    "bucket": "opensearch-cold-storage",
    "region": "eu-central-1"
  }
}
# → {"acknowledged":true}
```

3. Хотя бы один узел с ролью `warm` — он обслуживает восстановление типа `remote_snapshot` и локальный кэш сегментов.
4. Права Security: пользователю/роли ISM нужны разрешения на операции со снимками (`manage_snapshots`, доступ к кластерным операциям репозитория).

Проверка результата после перехода индекса в холодное состояние:

```bash
GET logs-prod-000003/_settings?pretty
# → "settings": { "index": { "store": { "type": "remote_snapshot" }, ... } }

GET _cat/nodes?v&h=name,node.role
# → Узлы с ролью w (warm) должны присутствовать в списке.
```

Настройте соотношение кэша: `cluster.filecache.remote_data_ratio: 5` (объем холодных данных не должен превышать размер кэша warm-узлов более чем в 5 раз, иначе запросы будут упираться в диск). Помните о стоимости: объектные хранилища тарифицируют запросы — массовые сканирования холодных данных заметно дороже локальных чтений.

Альтернативная схема с раздельным контролем шагов (удобна для аудита):

```json
PUT _plugins/_ism/policies/searchable_snapshots_policy
{
  "policy": {
    "description": "Снимок и конвертация в searchable snapshot после 90 дней",
    "default_state": "hot_state",
    "states": [
      {
        "name": "hot_state",
        "actions": [],
        "transitions": [{
          "state_name": "snapshot_state",
          "conditions": { "min_index_age": "90d" }
        }]
      },
      {
        "name": "snapshot_state",
        "actions": [
          {
            "snapshot": {
              "repository": "cold-repo",
              "snapshot": "{{ctx.index}}"
            }
          }
        ],
        "transitions": [{ "state_name": "cold_state", "conditions": {} }]
      },
      {
        "name": "cold_state",
        "actions": [
          { "convert_index_to_remote": { "repository": "cold-repo" } }
        ],
        "transitions": []
      }
    ]
  }
}
```

Ограничение: действие `convert_index_to_remote` в связке с Data Streams имело известные проблемы в ветке 3.x (форум проекта, весна 2026) — перед продакшеном протестируйте на своей версии; для обычных индексов конвейер работает стабильно.

### 4. Вариант с Data Streams

Для Data Streams отдельная настройка `rollover_alias` не нужна: ротация встроена в сам механизм потоков, а ISM управляет backing-индексами (`.ds-*`) как обычными индексами.

```json
PUT _index_template/logs-k8s
{
  "index_patterns": ["logs-k8s*"],
  "data_stream": {},
  "template": {
    "settings": {
      "number_of_shards": 3
    }
  }
}

PUT _plugins/_ism/policies/ds_retention
{
  "policy": {
    "description": "Retention для data stream логов Kubernetes",
    "default_state": "hot",
    "states": [
      {
        "name": "hot",
        "actions": [
          { "rollover": { "min_primary_shard_size": "40gb", "min_index_age": "1d" } }
        ],
        "transitions": [
          { "state_name": "delete", "conditions": { "min_index_age": "30d" } }
        ]
      },
      {
        "name": "delete",
        "actions": [{ "delete": {} }]
      }
    ],
    "ism_template": {
      "index_patterns": [".ds-logs-k8s*", "logs-k8s*"],
      "priority": 100
    }
  }
}
```

Проверка привязки политики к backing-индексам потока:

```bash
GET _plugins/_ism/explain/.ds-logs-k8s-2026.08.01-000001?pretty
# → "policy_id":"ds_retention","enabled":true
```

Поддержка Data Streams заявлена и в Elasticsearch ILM — миграция между системами по этой части прямолинейна (см. сравнение в конце документа).

### 5. Уведомления об ошибках в Slack

ISM поддерживает интеграцию с плагином Notifications для отправки сообщений при сбое действий (например, неудачном rollover из-за переполнения индекса).

Подготовка: в Dashboards откройте **Notifications > Channels > Create channel**, тип Slack, вставьте Incoming Webhook URL; запомните Config ID созданного канала.

Встраивание в политику (блок уровня `policy`, рядом со `states`):

```json
"error_notification": {
  "channel": {
    "id": "L9xJbXwB4Wp"
  },
  "message_template": {
    "source": "Ошибка ISM в индексе {{ctx.index}}: {{ctx.cause}}"
  }
}
```

Рекомендация документации: при использовании авто-ротации обязательно настраивайте error notification — молчаливый сбой rollover приводит к неограниченному росту горячего индекса. Точечные уведомления в середине жизненного цикла (например, «индекс уходит в архив») делаются действием `notification` внутри состояния — там же доступны переменные `{{ctx.index}}` и другие поля контекста.

### 6. Архивация снимком перед удалением

Если данные нельзя терять даже после истечения retention, добавьте состояние архивации:

```json
{
  "name": "archive",
  "actions": [
    {
      "snapshot": {
        "repository": "backup-repo",
        "snapshot": "archived-{{ctx.index}}"
      }
    },
    { "delete": {} }
  ],
  "transitions": []
}
```

Действия выполняются последовательно: сначала создается снимок `archived-<имя_индекса>` в репозитории `backup-repo`, затем индекс удаляется. Если создание снимка провалится, удаление не начнется — политика останется в состоянии ошибки до вмешательства (retry вручную или исправление причины). Имя снимка поддерживает подстановку контекста: `{{ctx.index}}`.

### 7. Сжатие индексов после ротации (shrink)

Индексы, созданные с большим числом шардов ради скорости записи, можно сжать после прекращения записи:

```json
{
  "name": "shrink",
  "actions": [
    {
      "shrink": {
        "num_new_shards": 1,
        "target_index_name_template": {
          "source": "shrunken-{{ctx.index}}"
        }
      }
    }
  ],
  "transitions": []
}
```

Помещайте shrink в состояние, следующее за rollover: индекс должен прекратить прием записи. Результат — новый индекс `shrunken-<имя>` с одним первичным шардом вместо исходного множества; старый индекс удаляется ISM после успешной операции. Типичное применение: горячие индексы на 6–12 шардах сжимать до 1–2 шардов в теплой зоне.

### 8. Управление через интерфейс Dashboards

Полный аналог API доступен в разделе **Index Management**:

1. **State management policies > Create policy**: сборка политики в визуальном редакторе (выбор действий и условий мышью) или напрямую в JSON-редакторе. В поле **ISM templates** задается маска авто-применения; запрещенные символы паттерна: `:` `"` `+` `/` `\` `|` `?` `#` `>` `<`.
2. **Managed indices**: выбор индексов > **Apply policy** (указание policy_id и preview политики); для политик с rollover — кнопка **Add rollover alias** (алиас должен существовать заранее).
3. Операции над управляемыми индексами: **Change policy** (перевод в другое состояние), **Remove policy** (отвязка), **Retry policy** (повтор после ошибки).
4. Таблица Managed indices показывает текущее состояние каждого индекса, время входа в него и последние ошибки — быстрый способ проверить работоспособность без Explain API.

## Управление через REST API

### Просмотр статуса (Explain API)

Позволяет узнать, в каком состоянии находится индекс и какое действие выполняется в данный момент. Поддерживает шаблоны имен:

```http
GET /_plugins/_ism/explain/logs-prod-*
```
# → Ответ содержит policy_id, текущее состояние (state), info со статусом действия,
# → step_info (детали ошибок), переходное состояние и время начала текущей фазы.

### Полный набор эндпоинтов

| Операция | Запрос |
| :--- | :--- |
| Создать/обновить политику | `PUT /_plugins/_ism/policies/<policy_id>` |
| Получить политику | `GET /_plugins/_ism/policies/<policy_id>` |
| Список политик | `GET /_plugins/_ism/policies` |
| Удалить политику | `DELETE /_plugins/_ism/policies/<policy_id>` |
| Привязать политику к индексам | `POST /_plugins/_ism/add/<index>` + `{"policy_id": "..."}` |
| Отвязать политику | `POST /_plugins/_ism/remove/<index>` |
| Перевести индекс в состояние | `POST /_plugins/_ism/change_policy/<index>` + `{"state": "..."}` |
| Повтор после ошибки | `POST /_plugins/_ism/retry/<index>` |
| Статистика плагина | `GET /_plugins/_ism/stats` |

Статистика полезна для мониторинга объема работы ISM: количество управляемых индексов, выполненных действий, ошибок по типам.

### Принудительное управление политиками

*   **Применить политику к существующему индексу**:
    ```http
    POST /_plugins/_ism/add/logs-old-index
    { "policy_id": "long_term_retention" }
    ```
*   **Изменить состояние индекса вручную**:
    ```http
    POST /_plugins/_ism/change_policy/logs-prod-000001
    { "state": "warm" }
    ```
*   **Повторный запуск после ошибки (Retry)**:
    ```http
    POST /_plugins/_ism/retry/logs-prod-000001
    ```

Legacy-вариант привязки через настройки индекса (работает во всех ветках):

```json
PUT logs-old-index/_settings
{ "opendistro.index_state_management.policy_id": "long_term_retention" }
```

## Дополнительная информация

### Настройки кластера ISM

Изменяются через `_cluster/settings` (блок `persistent`):

```json
PUT _cluster/settings
{
  "persistent": {
    "plugins.index_state_management.job_interval": 10,
    "plugins.index_state_management.jitter": 0.6
  }
}
# → {"acknowledged":true,"persistent":{"plugins":{"index_state_management":{...}}}}
```

| Настройка | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `plugins.index_state_management.enabled` | `true` | Включение/выключение плагина целиком |
| `plugins.index_state_management.job_interval` | `5` (минут) | Частота обхода управляемых индексов |
| `plugins.index_state_management.jitter` | `0–1` | Разброс стартов заданий для сглаживания нагрузки |
| `index.plugins.index_state_management.rollover_skip` | `false` | Исключить конкретный индекс из авто-ротации (на уровне индекса) |

Уменьшение интервала ускоряет реакцию политик в тестовых средах, но увеличивает накладные расходы — для продакшена оставляйте значения по умолчанию.

### Рекомендации по настройке

*   **Размер шардов**: Оптимальный размер первичного шарда — 30-50 ГБ. Используйте `min_primary_shard_size` для контроля.
*   **Force Merge**: Не запускайте `force_merge` на горячих индексах, в которые еще идет запись, так как это создаст огромную нагрузку на I/O. Обратное следствие: перед помещением в холодное хранилище merge до 1 сегмента желателен — чтение из объектного хранилища идет посегментно.
*   **Приоритет (Priority)**: Если индекс совпадает с несколькими `ism_template`, будет выбрана политика с наибольшим значением `priority`.
*   **Error notification обязателен** при использовании авто-ротации: сбой rollover без уведомления приводит к неограниченному росту горячего индекса.
*   **Тестируйте политики на минимальных порогах** (`min_doc_count: 1`) на стенде — конечный автомат проще отладить за минуты, чем ждать суток в продакшене.

### Устранение неполадок (Troubleshooting)

1.  **Индекс завис в состоянии `Attempting to rollover`**:
    *   Проверьте наличие алиаса для записи (`write_alias`). Для обычных индексов (не Data Streams) алиас обязан существовать, а настройка `plugins.index_state_management.rollover_alias` — присутствовать в шаблоне индекса.
    *   Проверьте права доступа пользователя, под которым работает плагин.
2.  **Ошибка `Snapshot in progress`**:
    *   ISM не может выполнить действие (например, `delete`), если для этого индекса в данный момент создается снимок другим процессом. Дождитесь завершения или выполните retry позже.
3.  **Нехватка места для Cold Storage**:
    *   Убедитесь, что репозиторий снимков (S3) доступен и имеет валидные учетные данные.
4.  **Ошибка `Missing rollover alias`**:
    *   Действие rollover не найдет целевой алиас, если он не задан настройкой в шаблоне. Исправьте шаблон; для уже созданных индексов установите настройку вручную и выполните retry.
5.  **Политика не применяется к старым индексам**:
    *   Ожидаемое поведение: `ism_template` действует только на новые индексы. Для существующих используйте `POST /_plugins/_ism/add/<index>`.
6.  **Сбой `convert_index_to_remote` на Data Streams**:
    *   Известные проблемы связки с потоками данных отмечались сообществом в ветке 3.x. Проверяйте релизные заметки своей версии; обходной путь — конвертация после отвязки от потока либо использование `cold_storage`.
7.  **Диагностика**: раздел **ISM Error Prevention** официальной документации описывает типовые ошибки и их решения; детали конкретного сбоя всегда доступны в поле `step_info` ответа Explain API.

### Сравнение OpenSearch ISM и Elasticsearch ILM

| Характеристика | OpenSearch ISM | Elasticsearch ILM |
| :--- | :--- | :--- |
| **Data Streams** | Полная поддержка | Полная поддержка (+ отдельный упрощенный механизм DLM в 8.x) |
| **Cold Storage** | Через Searchable Snapshots (S3): `cold_storage`, `convert_index_to_remote` | Через Frozen/Cold tiers |
| **Модель** | Гибкий конечный автомат (произвольные переходы) | Линейная модель (Hot -> Warm -> Cold -> Frozen -> Delete) |
| **Расписания** | Условие `cron` в любом переходе | Привязка фаз ко времени ротации (`min_age`) |
| **Уведомления** | Встроены (через Notifications) | Через Watcher (требует Platinum/Enterprise) |

Гибкость конечного автомата ISM (любые переходы между состояниями, включая возвраты) делает его удобным для нестандартных сценариев; линейная модель ILM проще для типовых случаев, но менее вариативна. Подробный разбор стороны Elasticsearch: [Elasticsearch: Жизненный цикл индексов (ILM)](../Elasticsearch/elasticsearch_ilm_and_retention.md).
