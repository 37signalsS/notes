# OpenSearch: Управление жизненным циклом индексов (ISM)

## Определения

* **Index State Management (ISM)** — плагин OpenSearch, предназначенный для автоматизации задач по управлению индексами (ротация, оптимизация, перенос на разные уровни хранения, удаление) на основе заданных политик. Является функциональным аналогом **Index Lifecycle Management (ILM)** в Elasticsearch.
* **Rollover (Ротация)** — процесс создания нового индекса для записи, когда текущий достигает определенных лимитов (размер, возраст, количество документов). Это позволяет поддерживать оптимальный размер шардов.
* **Force Merge** — процедура объединения сегментов Lucene для уменьшения их количества, что ускоряет поиск и освобождает место на диске за счет удаления помеченных на удаление документов.
* **Remote Store (Удаленное хранилище)** — возможность OpenSearch 2.x хранить данные сегментов и метаданные в объектных хранилищах (S3), что позволяет реализовать экономичное хранение архивных данных.
* **Searchable Snapshots (Поисковые снимки)** — технология, позволяющая выполнять поисковые запросы напрямую по данным, хранящимся в снимках (S3), без необходимости полного восстановления индекса на узлы данных.

## Основные концепции

### Фазы жизненного цикла индекса

В OpenSearch ISM политика (Policy) представляет собой конечный автомат, где индекс переходит из одного состояния в другое при выполнении определенных условий (**Transitions**).

1.  **Горячая фаза (Hot)**:
    *   Индексы открыты для записи и активного поиска.
    *   Используются быстрые носители (NVMe/SSD).
    *   Основное действие: `rollover` (переключение на новый индекс).
2.  **Тёплая фаза (Warm)**:
    *   Индекс закрыт для записи (`read_only`), но часто запрашивается.
    *   Оптимизация: `force_merge` до 1 сегмента, уменьшение количества реплик для экономии места.
    *   Может использоваться перенос на более дешевые HDD через действие `allocation`.
3.  **Холодная фаза (Cold)**:
    *   Данные запрашиваются редко.
    *   В OpenSearch 2.x активно используется перенос в **Cold Storage** через действие `cold_storage`. Данные перемещаются в S3, а локальные копии удаляются. Индекс остается видимым и доступным для поиска.
4.  **Удаление (Delete)**:
    *   Окончательное удаление индекса или его перевод в долгосрочный архив (Snapshot) перед удалением.

### Компоненты политики

*   **States**: Состояния, в которых может находиться индекс (например, `hot`, `delete`).
*   **Actions**: Операции, выполняемые внутри состояния (например, `rollover`, `snapshot`, `notification`).
*   **Transitions**: Логика перехода между состояниями на основе условий (`min_index_age`, `min_doc_count`, `cron`).
*   **ISM Template**: Автоматическое применение политики к новым индексам по маске имени.

## Практические сценарии

### 1. Политика долгосрочного хранения (3 года)

Сценарий для критически важных логов. Используется переход Hot -> Warm -> Cold -> Delete.

```json
PUT /_plugins/_ism/policy/long_term_retention
{
  "policy": {
    "description": "Хранение: 7д Hot (или 30ГБ), 30д Warm, 1095д Удаление",
    "default_state": "hot",
    "states": [
      {
        "name": "hot",
        "actions": [
          {
            "rollover": {
              "min_primary_shard_size": "30gb",
              "min_index_age": "7d"
            }
          }
        ],
        "transitions": [{ "state_name": "warm" }]
      },
      {
        "name": "warm",
        "actions": [
          { "replica_count": { "number_of_replicas": 1 } },
          { "force_merge": { "max_num_segments": 1 } },
          { "read_only": {} }
        ],
        "transitions": [
          {
            "state_name": "delete",
            "conditions": { "min_index_age": "1095d" }
          }
        ]
      },
      {
        "name": "delete",
        "actions": [{ "delete": {} }]
      }
    ],
    "ism_template": {
      "index_patterns": ["logs-prod-*"],
      "priority": 10
    }
  }
}
```

### 2. Использование Cold Storage (Searchable Snapshots)

Сценарий для экономии места на дисках узлов за счет использования S3.

```json
{
  "name": "cold",
  "actions": [
    {
      "cold_storage": {}
    }
  ],
  "transitions": [
    {
      "state_name": "delete",
      "conditions": { "min_index_age": "90d" }
    }
  ]
}
```

### 3. Уведомления об ошибках в Slack

ISM поддерживает интеграцию с плагином Notifications для отправки сообщений при сбое действий.

```json
"error_notification": {
  "channel": {
    "config_id": "L9xJbXwB4Wp..."
  },
  "message_template": {
    "source": "Ошибка ISM в индексе {{ctx.index}}: {{ctx.cause}}"
  }
}
```

## Управление через REST API

### Просмотр статуса (Explain API)

Позволяет узнать, в каком состоянии находится индекс и какое действие выполняется в данный момент.

```http
GET /_plugins/_ism/explain/logs-prod-000001
```
# → Ответ содержит step_info (ошибки), переходное состояние и время начала текущей фазы.

### Принудительное управление политиками

*   **Применить политику к существующему индексу**:
    ```http
    POST /_plugins/_ism/add/logs-old-index
    { "policy_id": "long_term_retention" }
    ```
*   **Изменить состояние индекса вручную**:
    ```http
    POST /_plugins/_ism/change_policy/logs-prod-000001
    { "state": "warm" }
    ```
*   **Повторный запуск после ошибки (Retry)**:
    ```http
    POST /_plugins/_ism/retry/logs-prod-000001
    ```

## Дополнительная информация

### Рекомендации по настройке

*   **Размер шардов**: Оптимальный размер первичного шарда — 30-50 ГБ. Используйте `min_primary_shard_size` для контроля.
*   **Force Merge**: Не запускайте `force_merge` на горячих индексах, в которые еще идет запись, так как это создаст огромную нагрузку на I/O.
*   **Приоритет (Priority)**: Если индекс совпадает с несколькими `ism_template`, будет выбрана политика с наибольшим значением `priority`.

### Устранение неполадок (Troubleshooting)

1.  **Индекс завис в состоянии `Attempting to rollover`**:
    *   Проверьте наличие алиаса для записи (`write_alias`). Для обычных индексов (не Data Streams) алиас обязателен.
    *   Проверьте права доступа пользователя, под которым работает плагин.
2.  **Ошибка `Snapshot in progress`**:
    *   ISM не может выполнить действие (например, `delete`), если для этого индекса в данный момент создается снимок другим процессом.
3.  **Нехватка места для Cold Storage**:
    *   Убедитесь, что репозиторий снимков (S3) доступен и имеет валидные учетные данные.

### Сравнение OpenSearch ISM и Elasticsearch ILM

| Характеристика | OpenSearch ISM | Elasticsearch ILM |
| :--- | :--- | :--- |
| **Data Streams** | Полная поддержка | Полная поддержка |
| **Cold Storage** | Через Searchable Snapshots (S3) | Через Frozen/Cold tiers |
| **Модель** | Гибкий конечный автомат (произвольные переходы) | Линейная модель (Hot -> Warm -> Cold -> Frozen -> Delete) |
| **Уведомления** | Встроены (через Notifications) | Через Watcher (требует Platinum/Enterprise) |
