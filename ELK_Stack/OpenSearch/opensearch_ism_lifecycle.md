# OpenSearch: Управление жизненным циклом индексов (ISM)

Reliability: 10 (Актуально для OpenSearch 2.x)

## Определения

* **Index State Management (ISM)** — плагин OpenSearch, предназначенный для автоматизации задач по управлению индексами (ротация, оптимизация, перенос на разные уровни хранения, удаление) на основе заданных политик. Является функциональным аналогом **Index Lifecycle Management (ILM)** в Elasticsearch.
* **Rollover (Ротация)** — процесс создания нового индекса для записи, когда текущий достигает определенных лимитов (размер, возраст, количество документов). Это позволяет поддерживать оптимальный размер шардов.
* **Force Merge** — процедура объединения сегментов Lucene для уменьшения их количества, что ускоряет поиск и освобождает место на диске за счет удаления помеченных на удаление документов.
* **Remote Store (Удаленное хранилище)** — возможность OpenSearch 2.x хранить данные сегментов и метаданные в объектных хранилищах (S3), что позволяет реализовать экономичное хранение архивных данных.

## Основные концепции

### Фазы жизненного цикла индекса

В OpenSearch ISM политика (Policy) представляет собой конечный автомат, где индекс переходит из одного состояния в другое при выполнении условий (Transitions).

1. **Горячая фаза (Hot)**:
   - Индексы открыты для записи и активного поиска.
   - Используются быстрые носители (NVMe/SSD).
   - Основное действие: `rollover` (переключение на новый индекс).
2. **Тёплая фаза (Warm)**:
   - Индекс закрыт для записи (Read-only), но часто запрашивается.
   - Оптимизация: `force_merge` до 1 сегмента, уменьшение количества реплик для экономии места.
   - Может использоваться перенос на более дешевые HDD (если настроены атрибуты узлов).
3. **Холодная фаза (Cold)**:
   - Данные запрашиваются редко.
   - В OpenSearch 2.x активно используется перенос в **Cold Storage** (фактически — создание снимка в S3 и удаление локальных данных, при этом индекс остается доступным для поиска через Searchable Snapshots).
4. **Удаление (Delete)**:
   - Окончательное удаление индекса или его перевод в долгосрочный архив (Snapshot) перед удалением.

## Практические сценарии

### 1. Политика долгосрочного хранения (3 года)

Сценарий для критически важных логов, которые должны храниться 3 года. Используется автоматический переход Hot -> Warm -> Cold -> Delete.

```json
PUT /_plugins/_ism/policy/long_term_retention
{
  "policy": {
    "description": "Политика хранения: 7д Hot, 30д Warm, 1095д Удаление",
    "default_state": "hot",
    "states": [
      {
        "name": "hot",
        "actions": [
          {
            "rollover": {
              "min_index_age": "7d",
              "min_primary_shard_size": "30gb"
            }
          }
        ],
        "transitions": [
          {
            "state_name": "warm"
          }
        ]
      },
      {
        "name": "warm",
        "actions": [
          { "replica_count": { "number_of_replicas": 1 } },
          { "force_merge": { "max_num_segments": 1 } },
          { "read_only": {} }
        ],
        "transitions": [
          {
            "state_name": "delete",
            "conditions": { "min_index_age": "1095d" }
          }
        ]
      },
      {
        "name": "delete",
        "actions": [
          { "delete": {} }
        ]
      }
    ],
    "ism_template": {
      "index_patterns": ["logs-prod-*"],
      "priority": 10
    }
  }
}
```

### 2. Кратковременное хранение с мгновенным удалением

Для логов разработки (debug), которые не нужны дольше 24 часов.

```json
PUT /_plugins/_ism/policy/debug_logs_policy
{
  "policy": {
    "description": "Удаление через 24 часа",
    "default_state": "hot",
    "states": [
      {
        "name": "hot",
        "actions": [],
        "transitions": [
          {
            "state_name": "delete",
            "conditions": { "min_index_age": "24h" }
          }
        ]
      },
      {
        "name": "delete",
        "actions": [ { "delete": {} } ]
      }
    ],
    "ism_template": {
      "index_patterns": ["logs-debug-*"],
      "priority": 100
    }
  }
}
```

### 3. Интеграция с Snapshot (Архивация перед удалением)

Если данные нельзя просто удалить, можно настроить создание снимка в S3 (Repository) перед фазой удаления.

```json
{
  "name": "archive",
  "actions": [
    {
      "snapshot": {
        "repository": "s3-backups",
        "snapshot": "archive-{{ctx.index}}"
      }
    }
  ],
  "transitions": [
    { "state_name": "delete" }
  ]
}
```

## Дополнительная информация

### Рекомендации по настройке

* **Размер шардов**: Стремитесь к размеру первичного шарда в 30-50 ГБ. Используйте `min_primary_shard_size` в действии `rollover`.
* **Приоритет шаблонов**: Если индекс подпадает под несколько шаблонов ISM, сработает тот, у которого выше `priority`.
* **Retry (Повторы)**: В случае ошибки (например, нехватка места для Snapshot) ISM будет повторять попытку. Параметры повторов настраиваются глобально или в действии.
