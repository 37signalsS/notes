# Elasticsearch: Индексирование, маппинг и жизненный цикл

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и углубленно раскрывает темы управления индексами, схемами данных (mapping) и их жизненным циклом (ILM) в Elasticsearch. Для ознакомления с базовыми понятиями, обратитесь к [общему обзору Elasticsearch](./elasticsearch_overview.md).

## Термины и определения

* **Маппинг (Mapping)**: Схема данных для индекса, определяющая поля, их типы (`text`, `keyword`, `date` и т.д.) и способ индексации. Аналог `CREATE TABLE` в SQL.
* **Поток данных (Data Stream)**: Абстракция для управления данными временных рядов (логи, метрики), которая автоматически работает с ILM для ротации и управления служебными индексами.
* **Шаблон индекса (Index Template)**: Набор преднастроенных параметров (`settings`) и маппингов (`mappings`), который автоматически применяется к новым индексам или потокам данных по шаблону имени (`logs-*`).
* **Компонентный шаблон (Component Template)**: Переиспользуемый блок конфигурации (маппинги, настройки, алиасы), который можно включать в несколько шаблонов индексов.
* **ILM (Index Lifecycle Management)**: Политика управления жизненным циклом индекса. Подробно описана в заметке **[Жизненный цикл индексов и политики хранения](./elasticsearch_ilm_and_retention.md)**.

## Базовые концепции

### Динамический и явный маппинг

* **Динамический (Dynamic Mapping)**: Elasticsearch автоматически определяет тип поля на основе первого документа. Удобно для старта, но опасно в production из-за риска "взрыва маппинга" и неверного определения типов.
* **Явный (Explicit Mapping)**: Рекомендуемый подход. Полный контроль над типами полей, что экономит ресурсы и предотвращает конфликты. В production рекомендуется использовать `dynamic: "strict"` для запрета новых полей.

### Сравнение ключевых типов полей

| Тип | Назначение | Анализ | Агрегации/Сортировка |
| :--- | :--- | :--- | :--- |
| **`text`** | Полнотекстовый поиск. | Да (разбиение на слова, нижний регистр и т.д.). | Нет (дорого, требует `fielddata`). |
| **`keyword`**| Точное совпадение, фильтрация, агрегации, сортировка. | Нет (хранится "как есть"). | Да (эффективно). |

### Вложенные структуры: `object` vs `nested`

* `object`: Тип по умолчанию для JSON-объектов. Внутренне структура "сплющивается", что нарушает связи в массивах объектов и может приводить к неверным результатам поиска.
* `nested`: Позволяет индексировать массивы объектов как независимые мини-документы, сохраняя связи и обеспечивая корректность запросов. Более ресурсоемок.

## Практические сценарии

### Современный подход: Data Streams, ILM и шаблоны

Для данных временных рядов, таких как логи или метрики, современный подход заключается в использовании потоков данных (Data Streams), которые бесшовно интегрируются с ILM и шаблонами.

**Шаг 1: Создание политики ILM**

Перед настройкой шаблонов необходимо определить политику управления жизненным циклом. Полное руководство по настройке фаз и действий см. в заметке **[Elasticsearch: Жизненный цикл индексов (ILM)](./elasticsearch_ilm_and_retention.md)**.

**Шаг 2: Создание компонентного шаблона для маппингов**

Это позволяет переиспользовать схему данных в разных потоках.

```bash
curl -X PUT "localhost:9200/_component_template/logs-mappings" -H 'Content-Type: application/json' -d'
{
  "template": {
    "mappings": {
      "dynamic": "strict",
      "properties": {
        "@timestamp": { "type": "date" },
        "message": { "type": "text" },
        "level": { "type": "keyword" },
        "user": {
          "properties": {
            "id": { "type": "keyword" }
          }
        }
      }
    }
  }
}' # → {"acknowledged": true}
```

**Шаг 3: Создание главного шаблона индекса для потока данных**

Этот шаблон связывает всё вместе: он указывает, что все индексы, соответствующие `logs-*`, должны быть частью потока данных, использовать наш компонентный шаблон для маппинга и управляться политикой ILM.

```bash
curl -X PUT "localhost:9200/_index_template/logs-template" -H 'Content-Type: application/json' -d'
{
  "index_patterns": ["logs-*"],
  "data_stream": {},
  "composed_of": ["logs-mappings"],
  "template": {
    "settings": {
      "index.lifecycle.name": "logs-policy"
    }
  },
  "priority": 200
}' # → {"acknowledged": true}
```

**Шаг 4: Индексация данных**

Теперь просто отправляйте документы напрямую в поток данных `logs-my-service`. Elasticsearch автоматически создаст первый служебный индекс (например, `.ds-logs-my-service-2024.01.01-000001`) и будет управлять его ротацией в соответствии с политикой ILM.

```bash
curl -X POST "localhost:9200/logs-my-service/_bulk" -H 'Content-Type: application/json' -d'
{ "create": {} }
{ "@timestamp": "2024-01-01T12:00:00Z", "level": "info", "message": "User logged in", "user": { "id": "user123" } }
' # → {"took": 15, "errors": false, "items": [...]}
```

### Изменение существующего маппинга

Изменять тип существующего поля в индексах, которые уже содержат данные, **нельзя**. Для потоков данных процедура миграции схемы выглядит так:

1. Создать новый компонентный шаблон с обновленным маппингом (v2).
2. Обновить главный шаблон индекса, чтобы он использовал новый компонентный шаблон v2.
3. Выполнить операцию `rollover` для потока данных. Это создаст новый служебный индекс с v2-маппингом. Новые данные будут писаться в него.
4. Старые данные остаются в индексах с v1-маппингом. При необходимости их можно переиндексировать в новый поток данных с помощью **reindex API**.

## Дополнительная информация

* **Производительность агрегаций**: Для агрегаций и сортировки используйте поля, у которых включены `doc_values` (это `keyword`, `numeric`, `date` и др. по умолчанию). Включать `fielddata` для полей типа `text` — очень дорогостоящая операция по потреблению оперативной памяти.
* **Runtime fields**: Поля, значения которых вычисляются "на лету" во время выполнения запроса. Они обеспечивают гибкость для экспериментов со схемой без переиндексации, но увеличивают задержку поиска по сравнению со статически индексируемыми полями.
