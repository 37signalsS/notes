# Elasticsearch: Индексы, маппинг и жизненный цикл

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и углубленно раскрывает темы управления индексами, схемами данных (mapping) и их жизненным циклом (ILM) в Elasticsearch.

## Определения

*   **Алиас (Alias)**: Стабильное имя (указатель), которое может ссылаться на один или несколько индексов. Используется для бесшовного переключения между индексами (например, при обновлении данных или ротации).
*   **Маппинг (Mapping)**: Схема данных для индекса, определяющая поля и их типы (`text`, `keyword`, `date`, `object`, `nested` и т.д.), а также то, как они должны индексироваться.
*   **Шаблон индекса (Index Template)**: Набор предварительно определенных настроек (`settings`) и маппингов (`mappings`), который автоматически применяется к новым индексам, соответствующим заданному шаблону имени (например, `logs-*`).
*   **ILM (Index Lifecycle Management)**: Политика управления жизненным циклом индекса, которая автоматизирует такие операции, как `rollover` (ротация), перемещение данных между стадиями хранения (hot/warm/cold) и удаление.

## Основные концепции

### Индекс, шарды, реплики и алиасы

Индекс в Elasticsearch — это логическое пространство для хранения документов. Физически он состоит из одного или нескольких **шардов** (shards).

*   **Шарды**: Количество первичных шардов задаётся при создании индекса и не может быть изменено. Оно определяет максимальную степень параллелизма для данного индекса.
*   **Реплики**: Копии первичных шардов. Их число можно изменять динамически. Реплики обеспечивают отказоустойчивость и масштабируют производительность на чтение.
*   **Алиасы**: Позволяют абстрагироваться от реальных имен индексов. Это ключевой механизм для проведения миграций и управления временными данными без простоя.

### Схема (mapping): типы полей и анализ

Маппинг определяет, как Elasticsearch обрабатывает и хранит поля документа.

*   **Сравнение `text` и `keyword`**:
    *   `text`: Предназначен для полнотекстового поиска. Содержимое проходит через анализатор (разбивается на токены, приводится к нижнему регистру и т.д.). Не подходит для сортировки и агрегаций.
    *   `keyword`: Хранится "как есть", единым токеном. Идеален для точных совпадений, фильтрации, сортировки и агрегаций.
*   **Сравнение `object` и `nested`**:
    *   `object`: Тип по умолчанию для вложенных JSON-объектов. Внутренне структура "сплющивается", что может приводить к неверным результатам при поиске по нескольким полям внутри массива объектов.
    *   `nested`: Позволяет индексировать массивы объектов как независимые документы, обеспечивая корректность запросов. Является более ресурсоемким.
*   **Подходы к маппингу**:
    *   **Явный (Explicit Mapping)**: Рекомендуемый подход. Полный контроль над типами полей, что экономит ресурсы и предотвращает конфликты.
    *   **Динамический (Dynamic Mapping)**: Elasticsearch автоматически определяет тип поля на основе первого документа. Удобно для старта, но в продуктивной среде рекомендуется ограничивать с помощью `dynamic: "strict"` (запрещает новые поля) или `dynamic_templates`.

## Практические сценарии

### Создание индекса с явным маппингом

Пример создания индекса для логов с определением типов полей, включая вложенные.

```bash
curl -X PUT 'http://localhost:9200/logs-2025.10.10' -H 'Content-Type: application/json' -d '{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "@timestamp": { "type": "date" },
      "message":    { "type": "text", "analyzer": "standard" },
      "level":      { "type": "keyword" },
      "user": {
        "type": "text",
        "fields": {
          "keyword": { "type": "keyword", "ignore_above": 256 }
        }
      },
      "geo": {
        "properties": {
          "ip":   { "type": "ip" },
          "lat":  { "type": "float" },
          "lon":  { "type": "float" }
        }
      }
    }
  }
}'
```

### Шаблоны индексов (Index Templates)

Composable templates позволяют применять стандартные настройки, маппинги и алиасы ко всем новым индексам, соответствующим шаблону `logs-*`.

```bash
curl -X PUT 'http://localhost:9200/_index_template/logs-template' 
-H 'Content-Type: application/json' -d '{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
    "mappings": {
      "dynamic": "strict",
      "dynamic_templates": [{
        "strings_as_keyword": {
          "match_mapping_type": "string",
          "mapping": { "type": "keyword", "ignore_above": 256 }
        }
      }],
      "properties": { "@timestamp": { "type": "date" } }
    },
    "aliases": { "logs-read": {}, "logs-write": {} }
  },
  "priority": 100
}'
```

### Управление жизненным циклом (ILM)

Политика ILM автоматизирует ротацию и удаление индексов.

1.  **Создание политики**:
    ```bash
    curl -X PUT 'http://localhost:9200/_ilm/policy/logs-policy' -H 'Content-Type: application/json' -d '{
      "policy": {
        "phases": {
          "hot": { "actions": { "rollover": { "max_size": "50gb", "max_age": "7d" } } },
          "delete": { "min_age": "30d", "actions": { "delete": {} } }
        }
      }
    }'
    ```

2.  **Создание первого индекса для записи**:
    ```bash
    curl -X PUT 'http://localhost:9200/logs-000001' -H 'Content-Type: application/json' -d '{
      "aliases": { "logs-write": { "is_write_index": true }, "logs-read": {} }
    }'
    ```
    *Все новые данные пишутся в алиас `logs-write`. ILM автоматически создаст новый индекс `logs-000002` при выполнении условия `rollover`.*

## Дополнительная информация

### Эволюция схемы и производительность

*   **Изменение схемы**: Изменять тип существующего поля **нельзя**. Для серьезных изменений используется **reindex API**: данные из старого индекса переиндексируются в новый с правильным маппингом, после чего на него переключается алиас.
*   **Производительность агрегаций**: Для агрегаций и сортировки используйте поля, у которых включены `doc_values` (`keyword`, `numeric`, `date` и др. по умолчанию). Включать `fielddata` для полей типа `text` — дорогостоящая операция по потреблению памяти.
*   **Runtime fields**: Поля, значения которых вычисляются во время выполнения запроса ("на лету"). Они обеспечивают гибкость, но увеличивают задержку поиска по сравнению с индексируемыми полями.
