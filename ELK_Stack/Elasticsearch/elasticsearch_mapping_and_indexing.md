# Elasticsearch: Индексирование, маппинг и жизненный цикл

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и углубленно раскрывает темы управления индексами, схемами данных (mapping) и их жизненным циклом (ILM) в Elasticsearch. Для ознакомления с базовыми понятиями, обратитесь к [общему обзору Elasticsearch](./elasticsearch_overview.md).

## Определения

* **Маппинг (Mapping)**: Схема данных для индекса, определяющая поля, их типы (`text`, `keyword`, `date` и т.д.) и способ индексации. Аналог `CREATE TABLE` в SQL.
* **Шаблон индекса (Index Template)**: Набор преднастроенных параметров (`settings`) и маппингов (`mappings`), который автоматически применяется к новым индексам по шаблону имени (`logs-*`).
* **ILM (Index Lifecycle Management)**: Политика управления жизненным циклом индекса, которая автоматизирует операции ротации (`rollover`), перемещения данных между стадиями хранения (hot/warm/cold) и удаления.
* **Алиас (Alias)**: Стабильное имя (указатель), которое может ссылаться на один или несколько индексов. Ключевой инструмент для бесшовного переключения между индексами.

## Основные концепции

### Динамический и явный маппинг

* **Динамический (Dynamic Mapping)**: Elasticsearch автоматически определяет тип поля на основе первого документа. Удобно для старта, но опасно в production из-за риска "взрыва маппинга" и неверного определения типов.
* **Явный (Explicit Mapping)**: Рекомендуемый подход. Полный контроль над типами полей, что экономит ресурсы и предотвращает конфликты. В production рекомендуется использовать `dynamic: "strict"` для запрета новых полей.

### Сравнение ключевых типов полей

| Тип | Назначение | Анализ | Агрегации/Сортировка |
| :--- | :--- | :--- | :--- |
| **`text`** | Полнотекстовый поиск. | Да (разбиение на слова, нижний регистр и т.д.). | Нет (дорого, требует `fielddata`). |
| **`keyword`**| Точное совпадение, фильтрация, агрегации, сортировка. | Нет (хранится "как есть"). | Да (эффективно). |

### Вложенные структуры: `object` vs `nested`

* `object`: Тип по умолчанию для JSON-объектов. Внутренне структура "сплющивается", что нарушает связи в массивах объектов и может приводить к неверным результатам поиска.
* `nested`: Позволяет индексировать массивы объектов как независимые мини-документы, сохраняя связи и обеспечивая корректность запросов. Более ресурсоемок.

## Практические сценарии

### Создание индекса с явным маппингом

Пример создания индекса для логов с определением типов полей, включая вложенные.

```bash
curl -X PUT 'http://localhost:9200/logs-2025.10.10' -H 'Content-Type: application/json' -d '{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  },
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "@timestamp": { "type": "date" },
      "message":    { "type": "text", "analyzer": "standard" },
      "level":      { "type": "keyword" },
      "user": {
        "type": "text",
        "fields": {
          "keyword": { "type": "keyword", "ignore_above": 256 }
        }
      },
      "geo": {
        "properties": {
          "ip":   { "type": "ip" },
          "lat":  { "type": "float" },
          "lon":  { "type": "float" }
        }
      }
    }
  }
}'
```

### Шаблоны индексов (Index Templates)

Composable templates позволяют применять стандартные настройки, маппинги и алиасы ко всем новым индексам, соответствующим шаблону `logs-*`.

```bash
curl -X PUT 'http://localhost:9200/_index_template/logs-template' 
-H 'Content-Type: application/json' -d '{
  "index_patterns": ["logs-*"],
  "template": {
    "settings": { "number_of_shards": 3, "number_of_replicas": 1 },
    "mappings": {
      "dynamic": "strict",
      "dynamic_templates": [{
        "strings_as_keyword": {
          "match_mapping_type": "string",
          "mapping": { "type": "keyword", "ignore_above": 256 }
        }
      }],
      "properties": { "@timestamp": { "type": "date" } }
    },
    "aliases": { "logs-read": {}, "logs-write": {} }
  },
  "priority": 100
}'
```

### Управление жизненным циклом (ILM) с ротацией (Rollover)

Политика ILM автоматизирует ротацию и удаление индексов.

1. **Создание политики**:

    ```bash
    curl -X PUT 'http://localhost:9200/_ilm/policy/logs-policy' -H 'Content-Type: application/json' -d '{
      "policy": {
        "phases": {
          "hot": { "actions": { "rollover": { "max_size": "50gb", "max_age": "7d" } } },
          "delete": { "min_age": "30d", "actions": { "delete": {} } }
        }
      }
    }
    ```

2. **Создание первого индекса для записи**:

    ```bash
    curl -X PUT 'http://localhost:9200/logs-000001' -H 'Content-Type: application/json' -d '{
      "aliases": { "logs-write": { "is_write_index": true }, "logs-read": {} }
    }'
    ```

    *Теперь все данные пишутся в алиас `logs-write`. ILM автоматически создаст новый индекс `logs-000002` и переключит на него алиас при достижении условий `rollover`.*

### Изменение существующего маппинга

Изменять тип существующего поля **нельзя**. Процедура миграции схемы:

1. Создать новый шаблон с корректным маппингом.
2. Создать новый индекс на основе этого шаблона.
3. Запустить **reindex API** для копирования и преобразования данных из старого индекса в новый.
4. Атомарно переключить алиас чтения/записи со старого индекса на новый.

## Дополнительная информация

* **Производительность агрегаций**: Для агрегаций и сортировки используйте поля, у которых включены `doc_values` (это `keyword`, `numeric`, `date` и др. по умолчанию). Включать `fielddata` для полей типа `text` — очень дорогостоящая операция по потреблению оперативной памяти.
* **Runtime fields**: Поля, значения которых вычисляются "на лету" во время выполнения запроса. Они обеспечивают гибкость для экспериментов со схемой без переиндексации, но увеличивают задержку поиска по сравнению со статически индексируемыми полями.
