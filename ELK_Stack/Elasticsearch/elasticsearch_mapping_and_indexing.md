# Elasticsearch: Индексирование, маппинг и жизненный цикл

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и углубленно раскрывает темы управления индексами, схемами данных (mapping) и их жизненным циклом (ILM) в Elasticsearch. Для ознакомления с базовыми понятиями, обратитесь к [общему обзору Elasticsearch](./elasticsearch_overview.md).

## Термины и определения

* **Маппинг (Mapping)**: Определение структуры документа, типов его полей и способов их индексации. Аналог схемы таблицы в реляционных БД.
* **Поток данных (Data Stream)**: Единая точка входа для записи и поиска данных временных рядов. Состоит из нескольких скрытых индексов (`backing indices`), управляемых автоматически.
* **Шаблон индекса (Index Template)**: Конфигурация, которая автоматически применяется к новым индексам. В современных версиях строится из компонентных шаблонов.
* **Компонентный шаблон (Component Template)**: Модульный блок (настройки или маппинг), который можно переиспользовать в разных индексных шаблонах.
* **Runtime Fields**: Поля, вычисляемые в момент выполнения запроса. Позволяют изменять схему данных без переиндексации.

## Базовые концепции

### Динамический и явный маппинг

* **Явный (Explicit Mapping)**: Рекомендуемый подход для production. Позволяет точно задать типы данных, анализаторы и параметры хранения.
* **Динамический (Dynamic Mapping)**: Elasticsearch сам определяет тип поля при первом появлении.
  * `dynamic: "true"` — (по умолчанию) новые поля добавляются в маппинг автоматически.
  * `dynamic: "strict"` — новые поля вызывают ошибку (защита от "взрыва маппинга").
  * `dynamic: "runtime"` — новые поля добавляются как `runtime fields` (не индексируются, но доступны для поиска).

### Ключевые типы полей

| Тип | Назначение | Особенности |
| :--- | :--- | :--- |
| **`text`** | Полнотекстовый поиск. | Проходит через анализаторы. Не поддерживает агрегации по умолчанию. |
| **`keyword`**| Точное совпадение. | Быстрая фильтрация, агрегации и сортировка. Использует `doc_values`. |
| **`constant_keyword`** | Поле с одинаковым значением. | Оптимизирует хранение для всех документов в индексе. |
| **`wildcard`** | Поиск по маске и regex. | Эффективнее, чем `text` или `keyword` для поиска подстрок. |
| **`match_only_text`** | Поиск без позиционной информации. | Экономит место на диске по сравнению с `text`. |

### Предотвращение "взрыва маппинга"

Слишком большое количество полей (десятки тысяч) замедляет работу кластера и потребляет много памяти мастером. Контролируйте это через настройки индекса:
* `index.mapping.total_fields.limit`: Лимит полей (по умолчанию 1000).
* `index.mapping.depth.limit`: Глубина вложенности объектов (по умолчанию 20).

### Вложенные структуры: `object` vs `nested`

* `object`: Тип по умолчанию для JSON-объектов. Внутренне структура "сплющивается", что нарушает связи в массивах объектов и может приводить к неверным результатам поиска.
* `nested`: Позволяет индексировать массивы объектов как независимые мини-документы, сохраняя связи и обеспечивая корректность запросов. Более ресурсоемок.

## Практические сценарии

### Современный подход: Data Streams и компонентные шаблоны

В Elasticsearch 8.x для данных временных рядов рекомендуется использовать Data Streams в сочетании с компонентными шаблонами.

**Шаг 1: Создание компонентного шаблона для маппингов**

```bash
# Переменная $ELASTIC_PASSWORD должна содержать пароль пользователя elastic
curl -u elastic:$ELASTIC_PASSWORD -k -X PUT "https://localhost:9200/_component_template/logs-mappings" \
-H 'Content-Type: application/json' -d'
{
  "template": {
    "mappings": {
      "dynamic": "strict",
      "properties": {
        "@timestamp": { "type": "date" },
        "message": { "type": "text" },
        "level": { "type": "keyword" },
        "user": {
          "properties": {
            "id": { "type": "keyword" }
          }
        }
      }
    }
  }
}' # → {"acknowledged": true}
```

**Шаг 2: Создание индексного шаблона для потока данных**

Здесь мы можем включить оптимизации, такие как `synthetic _source` (уменьшает размер индекса за счет отсутствия хранения оригинального JSON) и режим `time_series` (TSDB).

```bash
curl -u elastic:$ELASTIC_PASSWORD -k -X PUT "https://localhost:9200/_index_template/logs-template" \
-H 'Content-Type: application/json' -d'
{
  "index_patterns": ["logs-*"],
  "data_stream": {},
  "composed_of": ["logs-mappings"],
  "template": {
    "settings": {
      "index.lifecycle.name": "logs-policy",
      "index.mode": "time_series",  # Режим TSDB (требует определенных типов полей)
      "index.mapping.store_source": "synthetic" # Оптимизация хранилища в 8.x
    }
  },
  "priority": 200
}' # → {"acknowledged": true}
```

**Шаг 3: Индексация данных**

```bash
curl -u elastic:$ELASTIC_PASSWORD -k -X POST "https://localhost:9200/logs-my-service/_bulk" \
-H 'Content-Type: application/json' -d'
{ "create": {} }
{ "@timestamp": "2024-01-01T12:00:00Z", "level": "info", "message": "User logged in", "user": { "id": "user123" } }
' # → {"took": 15, "errors": false, "items": [...]}
```

### Изменение существующего маппинга

Изменять тип существующего поля в индексах, которые уже содержат данные, **нельзя**. Для потоков данных процедура миграции выглядит так:

1. **Создание новой версии шаблона**: Обновите компонентный шаблон (например, `logs-mappings-v2`).
2. **Обновление индексного шаблона**: Укажите в `composed_of` новый компонентный шаблон.
3. **Ротация (Rollover)**: Выполните `POST /logs-my-service/_rollover`. Новый служебный индекс будет создан с актуальным маппингом.
4. **Переиндексация (при необходимости)**: Если нужно изменить старые данные, используйте `_reindex` API из старого служебного индекса в новый поток данных.

### Runtime Fields для гибкости

Если вы не уверены в маппинге или поле нужно только временно, добавьте его как `runtime`:

```bash
curl -u elastic:$ELASTIC_PASSWORD -k -X PUT "https://localhost:9200/logs-my-service/_mapping" \
-H 'Content-Type: application/json' -d'
{
  "runtime": {
    "http.response.status_code": {
      "type": "keyword",
      "script": {
        "source": "emit(doc[\"status\"].value.toString())"
      }
    }
  }
}'
```

## Дополнительная информация

* **Производительность агрегаций**: Для агрегаций и сортировки используйте поля, у которых включены `doc_values` (это `keyword`, `numeric`, `date` и др. по умолчанию). Включать `fielddata` для полей типа `text` — очень дорогостоящая операция по потреблению оперативной памяти.
* **Runtime fields**: Поля, значения которых вычисляются "на лету" во время выполнения запроса. Они обеспечивают гибкость для экспериментов со схемой без переиндексации, но увеличивают задержку поиска по сравнению со статически индексируемыми полями.
