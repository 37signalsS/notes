# Elasticsearch: Обзор

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и служит основной точкой входа для изучения Elasticsearch.

## Определения

* **Elasticsearch** — это распределенный RESTful поисковый и аналитический движок. Концептуально Elasticsearch **всегда является кластером**, даже если запущен в единственном экземпляре (Single Node Cluster).
* **Инвертированный индекс** — это структура данных, используемая в Elasticsearch, которая перечисляет каждое уникальное слово, встречающееся в любом документе, и идентифицирует все документы, в которых оно встречается. Это обеспечивает чрезвычайно быстрый поиск по ключевым словам.
* **Узел (Node)** — отдельный экземпляр (сервер) Elasticsearch в кластере.
* **Кластер (Cluster)** — совокупность одного или нескольких узлов, которые совместно хранят все данные и обеспечивают индексацию и поиск.

## Основные концепции

### Роли узлов

В современных версиях Elasticsearch (8.x+) роли узлов стали более гранулярными, что позволяет точно настраивать использование ресурсов. Основные роли:

* **Мастер-узел (Master Node)**: Управляет состоянием кластера (метаданные, создание/удаление индексов, "здоровье" узлов).
  * Для отказоустойчивости требуется **[кворум](](../../Databases/Concepts/replication.md#проблема-split-brain-и-кворум)**: `(N/2) + 1` мастер-узлов.
  * Защищает от ситуации **[Split-Brain](](../../Databases/Concepts/replication.md#проблема-split-brain-и-кворум)**.
* **Узлы данных (Data Nodes)**: Хранят данные и выполняют операции поиска/агрегации. Делятся на **Data Tiers** (уровни данных):
  * `data_content`: Для обычных индексов, не относящихся к временным рядам.
  * `data_hot`: Для активной записи и самого частого поиска (обычно на SSD).
  * `data_warm`: Для данных, которые ищутся реже и больше не обновляются.
  * `data_cold`: Для архивных данных (редкий поиск, оптимизация под плотность хранения).
  * `data_frozen`: Специальный уровень для **Searchable Snapshots** (поиск напрямую по данным в объектном хранилище типа S3).
* **Инжест-узел (Ingest Node)**: Выполняет предварительную обработку документов через `ingest pipelines` (аналог легкого Logstash внутри ES) перед их индексацией.
* **Координирующий узел (Coordinating Node)**: Узел без специальных ролей (или любой узел по умолчанию). Принимает запросы от клиентов, распределяет их по узлам данных и собирает финальный результат.
* **ML-узел (Machine Learning Node)**: Выполняет задачи машинного обучения (детекция аномалий, прогнозирование). Требует лицензии уровня Platinum/Enterprise.
* **Узел удаленного кластера (Remote Cluster Client)**: Позволяет узлу выступать в роли клиента для выполнения Cross-Cluster Search (CCS) или Cross-Cluster Replication (CCR).

### Индексы, Шарды и Реплики

* **Индекс (Index)**: Логическое пространство имен для группы документов, аналог таблицы в реляционных базах данных.
* **[Шард (Shard)](../../Databases/Concepts/sharding.md)**: Осколок или часть индекса. Индекс разбивается на шарды для горизонтального масштабирования.
  * Количество основных (Primary) шардов **нельзя изменить** после создания индекса, так как это число участвует в формуле распределения данных. Изменение количества шардов требует переиндексации (Reindex) — создания нового индекса и переливки данных.
  * Шарды позволяют распределить нагрузку на **запись** между узлами.
* **[Реплика (Replica)](../../Databases/Concepts/replication.md)**: Копия основного шарда.
  * Обеспечивает отказоустойчивость и масштабирование поисковых запросов (**на чтение**).
  * Реплика никогда не размещается на том же узле, где находится её основной шард.
  * Количество реплик можно изменять "на лету".

### Статусы "здоровья" кластера

Статус кластера определяется состоянием его самого "больного" индекса:

* **Green**: Все основные шарды и их реплики доступны и распределены по узлам. Идеальное состояние.
* **Yellow**: Все основные шарды доступны, но часть реплик не распределена (например, не хватает узлов для их размещения). Данные доступны, но отказоустойчивость снижена. Кластер может автоматически перейти в Green после добавления узлов или завершения ребалансировки.
* **Red**: Хотя бы один основной шард недоступен (и нет доступных реплик для его замены). **Кластер недоступен** для работы (не принимает записи и может не отдавать данные по поврежденным индексам). Требуется вмешательство администратора для восстановления данных.

### Безопасность по умолчанию

Начиная с версии 8.0, функции безопасности (Security) в Elasticsearch включены автоматически:

* **Аутентификация и RBAC**: Встроенный пользователь `elastic` (суперпользователь) и система Role-Based Access Control для разграничения прав.
* **TLS/SSL**: Весь трафик между узлами (порт 9300) и между клиентами и кластером (порт 9200) шифруется по умолчанию. При первом запуске Elasticsearch генерирует собственный CA и сертификаты.
* **Токены регистрации (Enrollment Tokens)**: Используются для безопасного и быстрого присоединения новых узлов или Kibana к кластеру без ручной настройки сертификатов.
* **API Keys и Service Tokens**: Современные способы аутентификации приложений и сервисов (например, Filebeat или Kibana), заменяющие использование статических логинов/паролей.

> Подробности по настройке безопасности в мультинодовом кластере см. в [Руководстве по настройке кластера](../Tutorials/cluster_setup.md).

### Потоки данных (Data Streams)

Для работы с данными временных рядов (логи, метрики, события) в современных версиях Elasticsearch используется абстракция **[Data Stream](./elasticsearch_mapping_and_indexing.md#современный-подход-data-streams-ilm-и-шаблоны)**. Она упрощает управление такими данными, автоматически интегрируясь с политиками ILM и шаблонами индексов. Вместо того чтобы писать в конкретный индекс или алиас, вы отправляете данные напрямую в поток, а Elasticsearch управляет созданием и ротацией скрытых служебных индексов (`backing indices`) за вас.

## Практические сценарии

### Архитектура Hot-Warm-Cold-Frozen

Паттерн для оптимизации затрат на хранение данных с разной частотой доступа, который автоматизируется с помощью политик **[ILM (Index Lifecycle Management)](./elasticsearch_ilm_and_retention.md)**.

* **Hot**: Самые свежие данные на быстрых SSD для активной записи и поиска.
* **Warm**: Данные только для чтения на более медленных дисках.
* **Cold/Frozen**: Архивные данные на самых дешевых носителях (HDD, объектные хранилища).

> Подробное описание ILM, политик хранения и ротации находится в заметке **[Elasticsearch: Жизненный цикл индексов и политики хранения](./elasticsearch_ilm_and_retention.md)**. О маппинге и шаблонах читайте в **[Elasticsearch: Индексирование и маппинг](./elasticsearch_mapping_and_indexing.md)**.

### Обслуживание кластера

Для корректного выключения узла без немедленной ребалансировки шардов (например, для обслуживания ОС или дисков):

1. **Отключить аллокацию реплик**:

    ```bash
    # Использование -k необходимо, если используются самоподписанные сертификаты
    # Переменная $ELASTIC_PASSWORD должна содержать пароль пользователя elastic
    curl -u elastic:$ELASTIC_PASSWORD -k -X PUT "https://localhost:9200/_cluster/settings" \
    -H 'Content-Type: application/json' -d'
    { "persistent": { "cluster.routing.allocation.enable": "primaries" } }'
    ```

2. Выполнить работы и перезапустить узел. Кластер сначала перейдет в статус `Yellow`, так как реплики не будут аллоцироваться.
3. **Вернуть аллокацию в штатный режим**:

    ```bash
    curl -u elastic:$ELASTIC_PASSWORD -k -X PUT "https://localhost:9200/_cluster/settings" \
    -H 'Content-Type: application/json' -d'
    { "persistent": { "cluster.routing.allocation.enable": "all" } }'
    ```

> Примечание: В Elasticsearch 8.x взаимодействие с API по умолчанию происходит по протоколу **HTTPS**.

## Дополнительная информация

### Оптимизация производительности

* **Размер Хипа (JVM Heap)**: Устанавливайте одинаковые значения для `-Xms` и `-Xmx`, но **никогда не выделяйте более ~31 ГБ**. Это связано с технологией **Compressed Ordinary Object Pointers (сжатые указатели)** в JVM. Подробнее о лимитах и тюнинге см. в SSoT-файле **[Управление и тюнинг Java (JVM)](../../Linux/Development/java_management.md)**.
* **Отключение Swap**: Swap на серверах с Elasticsearch должен быть **полностью отключен**, чтобы избежать длительных пауз сборщика мусора (GC), которые критически влияют на стабильность узла.
* **Интервал обновления (`refresh_interval`)**: Для данных, не требующих мгновенной видимости (например, логи), увеличьте интервал до `30s` или выше в шаблоне индекса. Это значительно снижает нагрузку на запись за счет уменьшения количества создаваемых сегментов Lucene.

### Ключевые настройки `elasticsearch.yml`

* **`cluster.name`**: Имя кластера. Узлы объединяются в кластер только если у них совпадает это имя.
* **`node.name`**: Уникальное имя узла внутри кластера.
* **`network.host`**: IP-адрес, на котором будет слушать Elasticsearch. `0.0.0.0` — все интерфейсы, но требует настройки `discovery`.
* **`discovery.type`**: Установите в `single-node` для запуска одного узла без формирования кластера (отключает проверку кворума).
* **`path.data`**: Путь к директории с данными. Можно указать список путей для разных дисков.
* **`discovery.seed_hosts`**: Список адресов других узлов для поиска соседей при старте кластера.
* **`cluster.initial_master_nodes`**: Указывается **только при первом запуске** нового кластера для выбора первого мастера.
* **`xpack.security.enabled`**: Управление функциями безопасности (в 8.x по умолчанию `true`).
* **`xpack.security.http.ssl.enabled`**: Включение HTTPS для клиентских подключений.
* **`cluster.routing.allocation.disk.watermark_*`**: Пороги заполнения диска (`low: 85%`, `high: 90%`, `flood_stage: 95%`). При достижении `flood_stage` индексы на узле переводятся в режим `read-only`.
