# Elasticsearch: Обзор

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и служит основной точкой входа для изучения Elasticsearch.

## Определения

* **Elasticsearch** — это распределенный RESTful поисковый и аналитический движок. Являясь сердцем Elastic Stack, он централизованно хранит данные для быстрого поиска, точной настройки релевантности и мощной аналитики, которая легко масштабируется.
* **Инвертированный индекс** — это структура данных, используемая в Elasticsearch, которая перечисляет каждое уникальное слово, встречающееся в любом документе, и идентифицирует все документы, в которых оно встречается. Это обеспечивает чрезвычайно быстрый поиск по ключевым словам.
* **Узел (Node)** — отдельный экземпляр (сервер) Elasticsearch в кластере.
* **Кластер (Cluster)** — совокупность одного или нескольких узлов, которые совместно хранят все данные и обеспечивают индексацию и поиск.

## Основные концепции

### Роли узлов

Узлы могут выполнять разные роли, которые можно комбинировать:

* **Мастер-узел (Master Node)**: Управляет состоянием кластера (метаданные, "здоровье" узлов). Для отказоустойчивости требуется кворум: `(N/2) + 1` мастер-узлов.
* **Узел данных (Data Node)**: Хранит данные (шарды) и выполняет операции индексации, поиска и агрегации. Требователен к CPU, RAM и дискам.
* **Инжест-узел (Ingest Node)**: Выполняет предварительную обработку документов перед их индексацией.
* **Координирующий узел (Coordinating Node)**: Принимает запросы, распределяет их по узлам данных и собирает результаты. Любой узел по умолчанию является координирующим.

### Индексы, Шарды и Реплики

* **Индекс (Index)**: Логическое пространство имен для группы документов, аналог таблицы в реляционных базах данных.
* **Шард (Shard)**: Часть индекса. Индекс разбивается на шарды для горизонтального масштабирования. Количество основных шардов **нельзя изменить** после создания индекса.
* **Реплика (Replica)**: Копия основного шарда. Обеспечивает отказоустойчивость и масштабирование поисковых запросов. Количество реплик можно изменять.

### Статусы "здоровья" кластера

* **Green**: Все основные шарды и их реплики доступны. Кластер полностью здоров.
* **Yellow**: Все основные шарды доступны, но не все реплики. Данные в сохранности, но отказоустойчивость снижена.
* **Red**: Один или нескольких основных шардов недоступны. Возможна потеря данных, часть запросов не будет выполняться.

### Потоки данных (Data Streams)

Для работы с данными временных рядов (логи, метрики, события) в современных версиях Elasticsearch используется абстракция **Data Stream**. Она упрощает управление такими данными, автоматически интегрируясь с политиками ILM и шаблонами индексов. Вместо того чтобы писать в конкретный индекс или алиас, вы отправляете данные напрямую в поток, а Elasticsearch управляет созданием и ротацией скрытых служебных индексов (`backing indices`) за вас.

## Практические сценарии

### Архитектура Hot-Warm-Cold-Frozen

Паттерн для оптимизации затрат на хранение данных с разной частотой доступа, который автоматизируется с помощью политик **ILM (Index Lifecycle Management)**.

* **Hot**: Самые свежие данные на быстрых SSD для активной записи и поиска.
* **Warm**: Данные только для чтения на более медленных дисках.
* **Cold/Frozen**: Архивные данные на самых дешевых носителях (HDD, объектные хранилища).

> Подробное описание ILM, маппинга, шаблонов и потоков данных находится в заметке **[Elasticsearch: Индексирование, маппинг и жизненный цикл](./elasticsearch_mapping_and_indexing.md)**.

### Обслуживание кластера

Для корректного выключения узла без немедленной ребалансировки шардов:

1. **Отключить аллокацию реплик**:

    ```bash
    curl -X PUT "localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d'
    { "persistent": { "cluster.routing.allocation.enable": "primaries" } }'
    ```

2. Выполнить работы и перезапустить узел.
3. **Вернуть аллокацию в штатный режим**:

    ```bash
    curl -X PUT "localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d'
    { "persistent": { "cluster.routing.allocation.enable": "all" } }'
    ```

## Дополнительная информация

### Оптимизация производительности

* **Размер Хипа (JVM Heap)**: Устанавливайте одинаковые значения для `-Xms` и `-Xmx`, но **никогда не выделяйте более ~31 ГБ**. Это связано с технологией **Compressed Ordinary Object Pointers (сжатые указатели)** в JVM. До этого порога JVM может использовать 4-байтовые указатели вместо 8-байтовых, что значительно экономит память и повышает производительность. Оставшаяся оперативная память будет эффективно использована операционной системой для кэширования файлов на уровне диска.
* **Отключение Swap**: Swap на серверах с Elasticsearch должен быть **полностью отключен**, чтобы избежать длительных пауз сборщика мусора (GC), которые критически влияют на стабильность узла.
* **Интервал обновления (`refresh_interval`)**: Для данных, не требующих мгновенной видимости (например, логи), увеличьте интервал до `30s` или выше в шаблоне индекса. Это значительно снижает нагрузку на запись за счет уменьшения количества создаваемых сегментов Lucene.

### Ключевые настройки `elasticsearch.yml`

* **`path.data`**: Указывайте несколько путей к разным физическим дискам (`/mnt/disk1, /mnt/disk2`), чтобы Elasticsearch мог параллельно утилизировать их I/O.
* **`discovery.seed_hosts`**: В production всегда используйте явное перечисление мастер-узлов (`["es-node1:9300", "es-node2:9300"]`).
* **`cluster.initial_master_nodes`**: Этот параметр **критически важен** при первоначальной настройке кластера. Он указывает, какие из узлов должны участвовать в выборах первого мастера. Задается только при самой первой инициализации кластера и не должен меняться впоследствии. Пример: `["es-node1", "es-node2"]`.
* **`cluster.routing.allocation.disk.watermark_*`**: Настройте пороги заполнения диска (`low: 85%`, `high: 90%`, `flood_stage: 95%`), чтобы Elasticsearch мог вовремя реагировать на нехватку места, перемещая шарды с переполненных узлов.
