# Elasticsearch: Обзор и ключевые концепции

> Эта заметка является частью обзора [ELK стека](../../elk_stack_overview.md) и служит основной точкой входа для изучения Elasticsearch.

**Elasticsearch** — это распределенный RESTful поисковый и аналитический движок, способный решать растущее число задач. Будучи сердцем Elastic Stack, он централизованно хранит ваши данные для быстрого поиска, точной настройки релевантности и мощной аналитики, которая легко масштабируется.

> "ELK — это чрезвычайно мощный, но и сложный инструмент. Правильная первоначальная настройка и понимание архитектуры являются залогом стабильной и производительной работы. Если сделать "по умолчанию", то с ростом нагрузки вы гарантированно столкнетесь с большим количеством проблем."

---

## 1. Основные концепции: Архитектура кластера

Понимание архитектуры — ключ к построению стабильного и масштабируемого кластера.

### 1.1. Роли узлов

Каждый инстанс Elasticsearch в кластере называется **узлом (node)**. Узлы могут выполнять разные роли, и эти роли можно комбинировать.

-   **Мастер-узел (Master Node)**
    -   **Обязанности**: Управляет состоянием кластера. Знает, какие индексы и шарды существуют, на каких узлах они расположены, отслеживает "здоровье" узлов. Обрабатывает создание и удаление индексов.
    -   **Рекомендации**: Для отказоустойчивости необходимо иметь как минимум 3 мастер-узла. Это выделенные узлы, которые не хранят данные и не обрабатывают поисковые запросы.

-   **Узел данных (Data Node)**
    -   **Обязанности**: Хранит данные (шарды индексов) и выполняет операции с данными: индексацию (запись), поиск (чтение), агрегацию.
    -   **Рекомендации**: Это самые ресурсоемкие узлы. Им требуется много CPU, RAM и быстрые диски.

-   **Инжест-узел (Ingest Node)**
    -   **Обязанности**: Выполняет предварительную обработку документов перед их индексацией (по аналогии с `filter` в Logstash).
    -   **Рекомендации**: Может быть полезен для снятия нагрузки с Logstash или клиентов. Часто эту роль совмещают с узлами данных.

-   **Координирующий узел (Coordinating Node)**
    -   **Обязанности**: Принимает запросы от клиентов, распределяет их по узлам данных, собирает результаты и отправляет обратно клиенту. Любой узел по умолчанию является координирующим.
    -   **Рекомендации**: В больших кластерах иногда выделяют отдельные координирующие узлы.

### 1.2. Индексы, Шарды и Реплики

- **Индекс (Index)**: Логическое пространство имен, объединяющее группу документов. Аналог таблицы в реляционных базах данных.

- **Шард (Shard)**: Индекс разбивается на мелкие, управляемые части — **шарды**. Каждый шард является самостоятельным экземпляром поискового движка Lucene. Это позволяет распределять нагрузку и масштабировать хранение.
    - **Количество шардов**: Задается при создании индекса и **не может быть изменено**. Неверный выбор может привести к проблемам с производительностью.
    - **Рекомендации**: Размер шарда от 10 до 50 ГБ для логов и временных рядов.

- **Реплика (Replica)**: Копия основного шарда.
    - **Назначение**: Обеспечивает **отказоустойчивость** (реплика становится основным шардом при сбое узла) и **производительность поиска** (реплики обрабатывают запросы на чтение).
    - **Количество реплик**: Можно изменять в любой момент.

### 1.3. Статусы кластера и кворум

-   **Green**: Кластер полностью работоспособен. Все шарды и реплики доступны.
-   **Yellow**: Все основные шарды доступны, но не все реплики. Кластер работает, но отказоустойчивость снижена.
-   **Red**: Один или несколько основных шардов недоступны. Потеря данных или невозможность доступа к ним.

**Кворум и Split-Brain**: Для защиты от ситуации **Split-Brain** (раскол кластера на несколько независимых частей) необходимо иметь кворум мастер-узлов: `(N/2) + 1`, где N — общее число мастер-узлов. Именно поэтому рекомендуется иметь 3 или более мастер-узлов.

## 2. Практические сценарии и руководства

### 2.1. Руководства по развертыванию
-   **Быстрый старт с Docker**: [Практическое руководство по настройке ELK (Elastic Stack)](../Tutorials/practical_setup_with_docker.md)
-   **Построение кластера**: [Руководство: Настройка кластера Elasticsearch 8](../Tutorials/cluster_setup.md)
-   **Подход к развертыванию на физических серверах**: На одной мощной ноде (например, 128 ГБ RAM) можно запускать **несколько инстансов Elasticsearch в Docker-контейнерах**, выделяя каждому ограниченный объем RAM (до 31 ГБ) и пробрасывая отдельный физический диск. Это обеспечивает изоляцию по I/O и эффективную утилизацию ресурсов.

### 2.2. Обслуживание кластера

Простое выключение узла вызывает немедленную ребалансировку шардов. **Правильная процедура**:

1.  **Отключить аллокацию шардов**, чтобы предотвратить их перемещение.
    ```bash
    curl -X PUT "localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d'
    { "persistent": { "cluster.routing.allocation.enable": "primaries" } }'
    ```
2.  (Опционально) **Исключить узел из аллокации**, чтобы переместить с него все шарды (если узел выводится надолго).
3.  Провести работы и перезапустить узел.
4.  **Вернуть настройки аллокации** в исходное состояние (`"cluster.routing.allocation.enable": "all"`).

## 3. Продвинутые детали и лучшие практики

### 3.1. Оптимизация производительности

#### Оптимизация JVM

-   **Размер Хипа — Правило 31 ГБ**: **Никогда не выделяйте для хипа Elasticsearch (`-Xms`, `-Xmx`) более 31 ГБ памяти.** При превышении этого порога JVM отключает сжатые указатели, что резко увеличивает потребление памяти и снижает производительность CPU. Оставшуюся память ОС эффективно использует для кэширования файлов.
-   **Сборщик мусора (GC)**: Длительные паузы GC — главный враг стабильности. Рекомендуется использовать **G1GC** (по умолчанию в новых версиях) и настраивать соотношение поколений в пользу `Young Generation` (`-XX:NewRatio=2`), где "умирает" большинство временных объектов.

#### Интервал обновления (`refresh_interval`)

-   **Проблема**: По умолчанию (`1s`) частые обновления индекса создают множество мелких сегментов и провоцируют частые запуски GC.
-   **Решение**: Если мгновенная видимость данных некритична (например, для логов), увеличьте этот интервал в шаблоне индекса до `30s` или выше. Это одно из самых эффективных изменений для снижения нагрузки.
    ```json
    { "settings": { "index": { "refresh_interval": "30s" } } }
    ```

### 3.2. Лучшие практики конфигурации

#### Шаблоны Индексов (Index Templates)

Используйте шаблоны для автоматического применения настроек (количество шардов, реплик, маппинги) ко всем новым индексам, соответствующим паттерну (`logstash-*`). Это позволяет централизованно управлять конфигурацией.

#### Конфигурация `elasticsearch.yml`

-   **`path.data`**: Вместо RAID-массивов предоставьте Elasticsearch несколько отдельных дисков: `path.data: /mnt/disk1, /mnt/disk2`. Elasticsearch распределит шарды по ним, утилизируя параллелизм дисковой подсистемы.
-   **Discovery**: В продакшене всегда используйте **unicast discovery**, явно перечисляя адреса мастер-узлов: `discovery.seed_hosts: ["10.0.0.1", "10.0.0.2"]`.
-   **Disk Watermarks**: Настройте пороги заполнения диска (`85%` low, `90%` high), чтобы Elasticsearch вовремя прекращал выделение новых шардов на узел и начинал их перемещение.

#### Системные настройки

-   **Отключение Swap**: Swap на серверах с Elasticsearch должен быть **полностью отключен**. Сброс данных JVM в swap приводит к длительным паузам GC и неработоспособности узла.

### 3.3. Архитектура Hot-Warm-Cold (Ярусы данных)

Это популярный паттерн для оптимизации затрат на хранение данных с разной частотой доступа.

-   **Hot (Горячий) ярус**: Самые свежие и часто используемые данные. Узлы — мощные серверы с быстрыми SSD.
-   **Warm (Теплый) ярус**: Менее свежие данные, только чтение. Узлы — менее мощные серверы с более медленными дисками.
-   **Cold (Холодный) ярус**: Архивные данные. Узлы — серверы с большими и дешевыми HDD.

Реализуется с помощью **Shard Allocation Awareness** и автоматизируется политиками **ILM (Index Lifecycle Management)**, которые перемещают индексы между ярусами.
