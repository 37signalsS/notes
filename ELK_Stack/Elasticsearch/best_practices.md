# Elasticsearch

> Эта заметка является частью обзора [ELK стека](../../elk_stack_overview.md) и содержит набор лучших практик по настройке и эксплуатации Elasticsearch.

## Шаблоны Индексов (Index Templates)

**Проблема**: При создании новых индексов (например, ежедневных для логов) необходимо каждый раз применять одни и те же настройки: количество шардов, реплик, маппинги полей.

**Решение**: Используйте **шаблоны индексов**. Шаблон автоматически применяется ко всем новым индексам, имена которых соответствуют заданному паттерну (например, `logstash-*`).

-   **Что настраивать в шаблоне**:

    -   `settings`: Количество шардов и реплик, `refresh_interval` и другие параметры индекса.
    -   `mappings`: Типы данных для полей. Критически важно явно указывать типы для `ip`, `date`, `keyword`, чтобы поиск и агрегации работали корректно.
    -   **Отключение `_source`**: Если исходный документ (полная строка лога) не нужен для анализа и достаточно разобранных полей, его хранение можно отключить, чтобы сэкономить дисковое пространство.

        ```json
        {
          "mappings": {
            "_source": {
              "enabled": false
            }
          }
        }
        ```

## Конфигурация `elasticsearch.yml`

### Хранение данных

-   **`path.data`**: Вместо использования RAID-массивов для дисков, лучше предоставить Elasticsearch несколько дисков, перечислив их в `path.data`. Elasticsearch будет распределять шарды по ним, эффективно используя параллелизм дисковой подсистемы.

    ```yaml
    path.data: /mnt/disk1, /mnt/disk2
    ```

### Сетевые настройки

-   **Discovery**: В продакшене **отключайте multicast discovery** и используйте **unicast discovery**. Явно перечислите адреса мастер-узлов, чтобы избежать случайного присоединения "чужих" узлов к вашему кластеру.

    ```yaml
    discovery.seed_hosts: ["10.0.0.1", "10.0.0.2", "10.0.0.3"]
    ```

### Управление ребалансировкой

-   **`cluster.routing.allocation.cluster_concurrent_rebalance`**: Ограничьте количество шардов, которые могут одновременно ребалансироваться в кластере (например, до `1`). Это замедлит процесс ребалансировки при добавлении/удалении узла, но значительно снизит влияние на производительность кластера во время этого процесса.
-   **Disk Watermarks (Пороги заполнения диска)**:
    -   `cluster.routing.allocation.disk.watermark.low`: Порог, при котором Elasticsearch перестает выделять новые шарды на узел (например, `85%`).
    -   `cluster.routing.allocation.disk.watermark.high`: Порог, при котором Elasticsearch начинает активно перемещать шарды с узла на другие (например, `90%`).

## Системные настройки

-   **Отключение Swap**: Elasticsearch крайне чувствителен к производительности диска. Сброс данных JVM в swap может привести к многосекундным паузам GC и полной неработоспособности узла. Swap на серверах с Elasticsearch должен быть **полностью отключен**.
-   **Количество ядер**: На системах с большим количеством ядер (>64) Elasticsearch может неверно определить их количество. Рекомендуется задавать некоторые параметры параллелизма вручную (см. [заметку по тюнингу JVM](./jvm_tuning.md)).

## Обслуживание кластера

**Проблема**: Простое выключение узла для проведения работ (обновление ОС, замена диска) приведет к тому, что кластер посчитает узел "упавшим" и немедленно начнет ребалансировку шардов, что создает ненужную нагрузку.

**Правильная процедура**:

1.  **Отключить аллокацию шардов**. Это предотвратит перемещение шардов.
    ```bash
    curl -X PUT "localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d'
    {
      "persistent": {
        "cluster.routing.allocation.enable": "primaries"
      }
    }
    '
    ```
    *Лекция предлагала `none`, но `primaries` является более безопасным вариантом, который позволяет создавать новые индексы.*

2.  **Исключить узел из аллокации (опционально, для полного освобождения узла)**. Это скажет кластеру переместить существующие шарды с этого узла. Этот шаг нужен, если узел выводится надолго.

    ```bash
    curl -X PUT "localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d'
    {
      "transient": {
        "cluster.routing.allocation.exclude._ip": "IP_АДРЕС_УЗЛА"
      }
    }
    '
    ```

3.  Подождать завершения миграции шардов с узла (если шаг 2 выполнялся).
4.  Провести работы по обслуживанию и перезапустить узел.
5.  **Вернуть настройки аллокации** в исходное состояние.

    ```bash
    curl -X PUT "localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d'
    {
      "persistent": {
        "cluster.routing.allocation.enable": "all"
      },
      "transient": {
        "cluster.routing.allocation.exclude._ip": null
      }
    }
    ```

## 5. Развертывание (Deployment)

Из лекции был предложен следующий практический подход для развертывания, особенно для сред без Kubernetes или при желании плотной утилизации ресурсов:

-   **Использовать мощные физические серверы**.
-   На одной мощной ноде (например, 128 ГБ RAM, много дисков) запускать **несколько инстансов Elasticsearch в Docker-контейнерах**.
-   Каждому инстансу выделять ограниченный объем памяти (например, 8-16 ГБ, но не более 31 ГБ) и **пробрасывать отдельный физический диск** (`path.data`).
-   Такой подход обеспечивает изоляцию по дисковому вводу-выводу и позволяет эффективно утилизировать ресурсы одного сервера, создавая иллюзию нескольких независимых узлов.
