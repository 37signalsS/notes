# Архитектура кластера Elasticsearch

> Эта заметка является частью обзора [ELK стека](../../elk_stack_overview.md) и описывает архитектурные основы Elasticsearch.

## 1. Роли узлов

Каждый инстанс Elasticsearch в кластере называется **узлом (node)**. Узлы могут выполнять разные роли, и эти роли можно комбинировать.

-   **Мастер-узел (Master Node)**
    -   **Обязанности**: Управляет состоянием кластера. Знает, какие индексы и шарды существуют, на каких узлах они расположены, отслеживает "здоровье" узлов. Обрабатывает создание и удаление индексов.
    -   **Рекомендации**: Для отказоустойчивости необходимо иметь как минимум 3 мастер-узла. Это выделенные узлы, которые не хранят данные и не обрабатывают поисковые запросы. Они не требуют много CPU или дискового пространства.

-   **Узел данных (Data Node)**
    -   **Обязанности**: Хранит данные (шарды индексов) и выполняет операции с данными: индексацию (запись), поиск (чтение), агрегацию.
    -   **Рекомендации**: Это самые ресурсоемкие узлы. Им требуется много CPU, RAM и быстрые диски. Узлы данных можно разделять по "температуре" данных (hot, warm, cold).

-   **Инжест-узел (Ingest Node)**
    -   **Обязанности**: Выполняет предварительную обработку документов перед их индексацией (по аналогии с `filter` в Logstash).
    -   **Рекомендации**: Может быть полезен для снятия нагрузки с Logstash или клиентов. Часто эту роль совмещают с узлами данных.

-   **Координирующий узел (Coordinating Node)**
    -   **Обязанности**: Принимает запросы от клиентов, распределяет их по узлам данных, собирает результаты и отправляет обратно клиенту. Любой узел по умолчанию является координирующим.
    -   **Рекомендации**: В больших кластерах иногда выделяют отдельные координирующие узлы, которые не имеют других ролей.

## 2. Индексы, Шарды и Реплики

### Индекс (Index)

**Индекс** в Elasticsearch — это логическое пространство имен, которое объединяет группу документов. Аналог таблицы в реляционных базах данных. Например, можно создавать ежедневные индексы для логов (`logs-2025-11-20`).

### Шард (Shard)

Поскольку один индекс может вырасти до огромных размеров, Elasticsearch разбивает его на более мелкие, управляемые части, называемые **шардами**. Каждый шард, по сути, является самостоятельным экземпляром поискового движка Lucene.

-   **Преимущества**:
    -   **Распределение нагрузки на запись:** Запросы на запись могут быть распределены между несколькими узлами.
    -   **Масштабирование хранения:** Позволяет хранить огромные объемы данных, распределяя их по серверам.
    -   **Параллельная обработка:** Поисковые запросы выполняются параллельно на всех шардах индекса, что ускоряет операции.

-   **Основной шард (Primary Shard)**: При индексации документ сначала попадает в один из основных шардов.

-   **Количество шардов**: **Критически важно!** Количество основных шардов для индекса **задается при его создании и не может быть изменено** в дальнейшем. Чтобы изменить количество шардов, необходимо создать новый индекс и переиндексировать в него данные из старого.
-   **Рекомендации по количеству**:
    -   Не создавайте слишком много маленьких шардов. Каждый шард потребляет ресурсы CPU и памяти.
    -   Ориентир: примерно **20-25 шардов на 1 ГБ хипа JVM** на узле данных.
    -   Размер шарда: для логов и временных рядов оптимальным считается размер шарда от 10 до 50 ГБ.

### Реплика (Replica)

**Реплика** — это копия основного шарда.

-   **Преимущества**:
    -   **Отказоустойчивость**: Реплики хранятся на других узлах, отличных от узла с основным шардом. Если узел с основным шардом выходит из строя, одна из его реплик автоматически становится основным шардом, предотвращая потерю данных.
    -   **Производительность поиска**: Реплики могут обрабатывать поисковые запросы наравне с основными шардами. Это позволяет увеличить пропускную способность кластера по чтению.

-   **Особенности**:
    -   Реплика не имеет смысла, если хранится на том же узле, что и первичный шард.
    -   **Количество реплик**: Можно изменять в любой момент времени без переиндексации.

**Пример**: У нас есть кластер из 3 узлов. Мы создаем индекс с 3 основными шардами и 1 репликой (`number_of_shards: 3`, `number_of_replicas: 1`). Elasticsearch распределит 3 основных шарда и 3 реплики по узлам так, чтобы основной шард и его копия никогда не находились на одном узле.

## 3. Статусы кластера и кворум

### Статусы кластера

Elasticsearch использует цветовую индикацию для отображения состояния кластера:

-   **Green (Зеленый):** Кластер полностью работоспособен. Все первичные шарды и их реплики доступны и распределены корректно. Это идеальное состояние.
-   **Yellow (Желтый):** Кластер работоспособен, но не все реплики доступны. Все первичные шарды доступны, но одна или несколько реплик отсутствуют или не распределены. Кластер может обрабатывать запросы на чтение и запись, но его отказоустойчивость снижена. Часто возникает, если количество узлов меньше, чем требуется для размещения всех реплик (например, 1 узел с 1 репликой).
-   **Red (Красный):** Кластер неработоспособен или частично неработоспособен. Один или несколько первичных шардов недоступны. Это означает потерю данных или невозможность доступа к ним. Требует немедленного вмешательства.

### Кворум и Split-Brain

**Кворум** — это минимальное количество мастер-узлов, которые должны быть доступны для того, чтобы кластер мог выбрать главного мастера. Это защищает от проблемы **Split-Brain (расщепление мозга)**.

**Split-Brain** — это ситуация, когда из-за сетевых проблем кластер разделяется на две или более изолированные группы, и каждая из них пытается выбрать своего мастера. Это приводит к рассинхронизации состояния кластера и потенциальной потере данных.

Для кластера из `N` мастер-узлов кворум составляет `(N/2) + 1`. Например, для 3 мастер-узлов кворум равен 2. Если один из узлов "отвалится", оставшиеся два смогут выбрать мастера и продолжить работу. Если останется только один, он не сможет принимать решения, и кластер станет read-only. Именно поэтому рекомендуется иметь 3 или более мастер-узлов.

## 4. Архитектура Hot-Warm-Cold (Ярусы данных)

Это популярный паттерн для управления данными с разной частотой доступа, позволяющий оптимизировать затраты на хранение.

-   **Hot (Горячий) ярус**:
    -   **Данные**: Самые свежие, часто индексируемые и запрашиваемые данные (например, логи за сегодня).
    -   **Узлы**: Самые мощные серверы с быстрыми SSD (NVMe), большим количеством RAM и CPU.
    
-   **Warm (Теплый) ярус**:
    -   **Данные**: Менее свежие данные, к которым обращаются реже (например, логи за прошлую неделю). Индексация в них уже не идет, только чтение.
    -   **Узлы**: Менее мощные серверы, можно использовать более медленные SSD или быстрые HDD.

-   **Cold (Холодный) ярус**:
    -   **Данные**: Архивные данные, доступ к которым нужен крайне редко (логи за прошлый год).
    -   **Узлы**: Серверы с большими и дешевыми HDD.

**Реализация**: Осуществляется с помощью **Shard Allocation Awareness**. Узлам присваиваются теги (атрибуты), например `node.attr.data_tier: hot`. Затем с помощью политик **ILM (Index Lifecycle Management)** настраивается автоматическое перемещение индексов между ярусами по истечении определенного времени.
