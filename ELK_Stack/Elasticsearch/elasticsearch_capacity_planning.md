# Elasticsearch: Capacity Planning и проектирование кластера

> Заметка посвящена расчету параметров кластера Elasticsearch: размера шардов, числа узлов, объемов диска, heap и пропускной способности. Базовые понятия (шарды, роли узлов, data tiers) описаны в [обзоре Elasticsearch](./elasticsearch_overview.md); ILM/слойная архитектура — в [ILM и политиках хранения](./elasticsearch_ilm_and_retention.md).

## Определения

* **Capacity Planning (Планирование мощностей)** — процесс определения количества узлов, дискового пространства, RAM и CPU, необходимых для стабильной работы кластера под projected нагрузку.
* **Shard Sizing (Размер шардов)** — целевой объем данных на одном первичном шарде. Влияет на скорость индексации, восстановление после сбоев и нагрузку на master-узел.
* **Hot-Warm Architecture** — разделение узлов по ролям хранения: `hot` (SSD, активная запись), `warm` (HDD/бюджетный SSD, поиск), `cold`/`frozen` (объектное хранилище, архив).
* **Oversharding (Избыточное шардирование)** — создание слишком большого числа шардов относительно объема данных и heap кластера. Приводит к замедлению выборов мастера и восстановления.
* **JVM Heap** — память, выделенная JVM Elasticsearch. Максимум 31 ГБ (для Compressed OOPs). Вторую половину RAM JVM не должна занимать — она нужна Lucene page cache.
* **Page Cache (Кэш страниц ОС)** — неиспользуемая RAM, которую ОС использует для кэширования файлов Lucene. От размера page cache напрямую зависит скорость поиска.
* **Write amplification (Усиление записи)** — коэффициент, показывающий, сколько байт фактически записано на диск относительно исходного объема данных. Увеличенное значение — признак неоптимальных настроек merge/refresh.
* **Recovery bandwidth (Пропускная способность восстановления)** — скорость, с которой реплика восстанавливает данные с primary шарда. Ограничивается `indices.recovery.max_bytes_per_sec`.
* **Shard rebalancing (Перебалансировка)** — автоматическое перемещение шардов между узлами для выравнивания нагрузки. Занимает I/O и сеть, поэтому во время пиковой нагрузки может быть ограничена.

## Основные концепции

### Правило размера шардов

| Тип данных | Целевой размер первичного шарда | Максимальный |
| :--- | :--- | :--- |
| Логи / метрики (временные ряды) | 30–50 ГБ | 100 ГБ |
| Поисковые индексы (документы) | 20–30 ГБ | 50 ГБ |
| Векторные индексы (k-NN) | 10–20 ГБ | 50 ГБ |

Основания для ограничений:

* **Восстановление после сбоя**: время восстановления пропорционально размеру шарда. Шард 100 ГБ восстанавливается в 2–3 раза дольше, чем шард 30 ГБ.
* **Нагрузка на master**: каждый шард — это метаданные в кластерном состоянии. Тысячи шардов замедляют выборы и публикацию состояния.
* **Merge efficiency**: мелкие шарды сливаются inefficiently, крупные — медленно.

### Правило heap и RAM

```
Heap = 50% физической RAM, но не более 31 ГБ
Оставшаяся RAM → page cache Lucene
```

| RAM сервера | JVM Heap | Page Cache |
| :--- | :--- | :--- |
| 16 ГБ | 8 ГБ | 8 ГБ |
| 32 ГБ | 16 ГБ | 16 ГБ |
| 64 ГБ | 31 ГБ | 33 ГБ |
| 128 ГБ | 31 ГБ | 97 ГБ |

**Почему 31 ГБ**: JVM использует Compressed OOPs (32-битные указатели) до этого порога. При 32 ГБ и выше указатели расширяются до 64 бит, что увеличивает потребление памяти и снижает производительность.

### Правило шардов на узел

```
Шардов на узел = 20–25 на 1 ГБ heap
```

Пример:

* Узел с 16 ГБ heap → максимум 320–400 шардов
* Узел с 31 ГБ heap → максимум 620–775 шардов
* Узел с 8 ГБ heap → максимум 160–200 шардов

### Роли узлов и их sizing

| Роль | CPU | RAM | Диск | Сеть |
| :--- | :--- | :--- | :--- | :--- |
| Master | 4–8 cores | 16–32 ГБ | Не требуется (только метаданные) | 1 Гбит/с |
| Data Hot | 8–16 cores | 32–64 ГБ (heap 16–31 ГБ) | NVMe 500 ГБ–2 ТБ | 10 Гбит/с |
| Data Warm | 4–8 cores | 16–32 ГБ | HDD/SSD 2–8 ТБ | 1 Гбит/с |
| Data Cold/Frozen | 2–4 cores | 8–16 ГБ | Не требуется (данные в S3) | 10 Гбит/с |
| Coordinating | 8–16 cores | 32–64 ГБ | Не требуется | 10 Гбит/с |
| Ingest | 4–8 cores | 16–32 ГБ | Зависит от pipeline | 1 Гбит/с |

### Формула расчета

```
Общее число шардов = (Объем данных / Целевой размер шарда) × Количество реплик
Число узлов = Общее число шардов / Шардов на узел
```

Пример:

* 1 ТБ логов, целевой размер шарда 50 ГБ → 20 первичных шардов
* С 1 репликой → 40 шардов всего
* При 20 шардах на узел (16 ГБ heap) → 2 узла данных минимум
* С запасом на рост: 3 узла данных + 3 master-eligible

## Практические сценарии

**Предварительные требования для всех сценариев**:

```bash
export ES="https://localhost:9200"
export PASS="<пароль пользователя elastic>"
curl -u elastic:$PASS -k "$ES"   # → {"name" : "es-node-1", ..., "tagline" : "You Know, for Search"}
```

### 1. Расчет кластера для логов приложения

Сценарий: 3 приложения генерируют 50 ГБ логов в сутки, retention 30 дней.

```bash
# 1. Рассчитать общий объем данных
# 50 ГБ/день × 30 дней = 1500 ГБ = 1.5 ТБ
# С overhead на сегменты и реплики × 1.3 → ~2 ТБ

# 2. Определить целевой размер шарда
# Для логов: 50 ГБ целевой, максимум 100 ГБ
# 2 ТБ / 50 ГБ = 40 шардов (с overhead ~35 первичных шардов)

# 3. Определить число реплик
# Для production: 1 реплика (failover один узел)
# Итого: 35 × 2 = 70 шардов

# 4. Определить число узлов
# При 25 шардах на узел (16 ГБ heap): 70 / 25 ≈ 3 узла
# С запасом: 5 узлов (3 hot + 2 warm)
```

Рекомендуемая конфигурация:

```yaml
# 3 hot-узла (NVMe 500 ГБ каждый)
node.roles: [ data_hot, data_content, ingest ]
node.attr.temp: hot

# 2 warm-узла (HDD 4 ТБ каждый)
node.roles: [ data_warm ]
node.attr.temp: warm

# 3 master-eligible узла (16 ГБ RAM каждый)
node.roles: [ master ]
```

```json
// ILM политика с учетом sizing
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" }
        }
      },
      "warm": {
        "min_age": "7d",
        "actions": {
          "shrink": { "number_of_shards": 1 },
          "forcemerge": { "max_num_segments": 1 },
          "allocate": { "require": { "temp": "warm" } }
        }
      },
      "delete": {
        "min_age": "30d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

### 2. Расчет кластера для метрик (TSDB)

Сценарий: 1000 хостов, каждый отправляет 100 метрик каждые 15 секунд, retention 90 дней.

```bash
# 1. Рассчитать объем данных
# 1000 хостов × 100 метрик × 4 измерения/час × 24 часа × 90 дней
# ≈ 864 000 000 документов

# 2. Оценить размер с downsampling
# Детальные данные (7 дней): ~100 ГБ
# Downsampled 1h (83 дня): ~30 ГБ
# Итого: ~130 ГБ

# 3. Определить число шардов
# Целевой размер 30 ГБ → 5 шардов (с запасом)
```

```json
{
  "settings": {
    "index.mode": "time_series",
    "index.mapping.source.mode": "synthetic",
    "number_of_shards": 5,
    "number_of_replicas": 1
  }
}
```

### 3. Расчет кластера для векторного поиска

Сценарий: 10 миллионов документов с векторами 768 измерений (float32), retention бессрочный.

```bash
# 1. Рассчитать объем векторов
# 10M документов × 768 dims × 4 bytes = 30 ГБ сырых векторов
# С HNSW графами и Lucene overhead × 3 → ~90 ГБ

# 2. Определить целевой размер шарда
# Для векторных индексов: 10–20 ГБ
# 90 ГБ / 15 ГБ = 6 шардов

# 3. Определить RAM для k-NN
# Граф HNSW хранится в page cache (off-heap)
# Для 10M векторов 768d: ~8–12 ГБ page cache
# Heap: 16–31 ГБ (для агрегаций и запросов)
# Итого: 64 ГБ RAM минимум на узел
```

```json
{
  "mappings": {
    "properties": {
      "embedding": {
        "type": "dense_vector",
        "dims": 768,
        "index": true,
        "index_options": {
          "type": "int8_hnsw",
          "m": 32,
          "ef_construction": 200
        }
      }
    }
  }
}
```

### 4. Определение размера hot-warm tier

Сценарий: кластер на 2 ТБ логов с ILM Hot-Warm-Cold.

```bash
# 1. Рассчитать объем hot-хранилища
# Активный индекс: 50 ГБ × 3 шарда = 150 ГБ на день
# Hot retention: 7 дней → ~1 ТБ
# С репликами × 2 → 2 ТБ на hot-узлы

# 2. Рассчитать warm-хранилища
# Данные за 30 дней минус 7 hot = 23 дня
# 50 ГБ/день × 23 = 1.15 ТБ
# После shrink (1 шард) и force merge: ~800 ГБ
# С репликами × 2 → 1.6 ТБ

# 3. Итого:
# Hot: 3 узла × 1 ТБ NVMe = 3 ТБ (с запасом 50%)
# Warm: 2 узла × 4 ТБ HDD = 8 ТБ (с запасом 100%)
```


```json

    }
  }

```

```bash
# 4. Установить алерты на接近 лимита

```

### 6. Сценарий роста: добавление узлов

Сценарий: кластер на 3 узлах, нагрузка выросла в 2 раза, нужно масштабировать.

```bash
# 1. Проверить текущую нагрузку
curl -u elastic:$PASS -k "$ES/_cat/nodes?v&h=name,node.role,heap.percent,disk.used_percent,cpu,load_1m"

# 2. Добавить новый узел с ролью data_hot
# На новом узле (elasticsearch.yml):
node.roles: [ data_hot, data_content, ingest ]
node.attr.temp: hot

# 3. Elasticsearch автоматически начнет relocate шарды
curl -u elastic:$PASS -k "$ES/_cat/allocation?v"
# → shards перебалансируются на новый узел

# 4. Контроль скорости relocation
curl -u elastic:$PASS -k -X PUT "$ES/_cluster/settings" \
-H 'Content-Type: application/json' -d'
{
  "persistent": {
    "indices.recovery.max_bytes_per_sec": "100mb"
  }
}'
```

### 7. Расчет пропускной способности сети

Сценарий: планирование сети для кластера на 5 узлов.

| Компонент | Входящий трафик | Исходящий трафик | Комментарий |
| :--- | :--- | :--- | :--- |
| Индексация | bulk-запросы от приложений | Репликация на другие узлы | 1 Гбит/с на узел данных |
| Поиск | Запросы от приложений | Merge результатов с шардов | 1 Гбит/с на узел данных |
| Recovery | Данные с primary | Данные на replica | Пиковая нагрузка при добавлении узла |
| Cross-cluster | Запросы к удаленному кластеру | Результаты поиска | Только для CCR/CCS |

```bash
# Проверить текущую нагрузку на сеть
curl -u elastic:$PASS -k "$ES/_nodes/stats/transport?pretty"
```

### 8. Разработка SLA и RTO/RPO

| Параметр | Значение | Обоснование |
| :--- | :--- | :--- |
| RPO (Recovery Point Objective) | 15 минут | Translog flush каждые 5 минут + durability `request` |
| RTO (Recovery Time Objective) | 30 минут | Время восстановления primary шарда 50 ГБ с NVMe |
| SLA доступности | 99.9% | ~8.7 часов простоя в год |
| SLA поиска | 99.95% | ~4.4 часа простоя в год |

Для уменьшения RTO:

```bash
# 1. Увеличить скорость recovery
curl -u elastic:$PASS -k -X PUT "$ES/_cluster/settings" \
-H 'Content-Type: application/json' -d'
{
  "persistent": {
    "indices.recovery.max_bytes_per_sec": "200mb",
    "cluster.routing.allocation.node_concurrent_recoveries": 4,
    "cluster.routing.allocation.cluster_concurrent_rebalance": 2
  }
}'
```

## Дополнительная информация

### Формулы для расчетов

**Объем диска**:

```
Диск = (Данные × Количество реплик × 1.3) + Запас на merge (20%)
```

**Число шардов**:

```
Шарды = CEILING(Объем данных / Целевой размер шарда)
```

**Число узлов**:

```
Узлы = CEILING((Шарды × Реплики) / Шардов_на_узел)
```

**Heap**:

```
Heap = MIN(50% RAM, 31 ГБ)
```

### Проверочный список capacity planning

- [ ] Оценен дневной объем индексируемых данных (ГБ/день)
- [ ] Определен retention периода (дни/месяцы/годы)
- [ ] Рассчитан общий объем данных с overhead
- [ ] Выбран целевой размер шарда (30–50 ГБ для логов)
- [ ] Определено число реплик (1 для dev, 1–2 для prod)
- [ ] Рассчитано общее число шардов
- [ ] Определено число узлов по формуле (с запасом 20–30%)
- [ ] Проверен лимит шардов на узел (`max_shards_per_node`)
- [ ] Установлены disk watermarks (85%/90%/95%)
- [ ] Настроен Prometheus алертинг на heap, disk, pending tasks
- [ ] Протестировано восстановление из snapshot на стенде
