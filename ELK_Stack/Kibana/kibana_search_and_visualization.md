# Kibana: Поиск, визуализация и управление

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и детально рассматривает инструменты Kibana для исследования данных, их визуализации и управления. Данные актуальны для версий **8.19 (LTS, поддержка до 15.07.2027)** и **9.4/9.5** (текущий минор — 9.5.5). Базовые понятия, требования к ресурсам, настройка `kibana.yml` и безопасность описаны в [Kibana: Обзор](./kibana_overview.md).

## Определения

* **KQL (Kibana Query Language)** — упрощенный язык запросов для быстрой фильтрации. Поддерживает интуитивный синтаксис и автодополнение полей. Принципиально умеет только фильтровать: агрегации, трансформации и сортировка выполняются другими средствами (Lens, ES|QL).
* **Lucene Query Syntax** — классический и гибкий язык запросов, поддерживающий регулярные выражения (RegEx), нечеткий поиск (fuzzy) и сложные логические группировки. Полезен для глубокой отладки условий поиска там, где возможностей KQL недостаточно.
* **ES|QL (Elasticsearch Query Language)** — современный потоковый (piped) язык запросов. Позволяет фильтровать, агрегировать и трансформировать данные «на лету» прямо в процессе выполнения запроса. Техническое превью появилось в Elasticsearch 8.11, общедоступный статус (GA) — с версии 8.14.
* **Runtime Fields** — вычисляемые поля («схема при чтении»). Позволяют извлекать или модифицировать данные без переиндексации индекса. Определяются на языке Painless в маппинге индекса или прямо в Data View.
* **Lens** — основной визуальный конструктор. Использует принцип drag-and-drop для быстрого создания диаграмм и автоматически подбирает их тип на основе структуры данных. Поддерживает формулы (Formula), справочные линии (reference lines), сдвиги времени (time shift) и источники данных на базе ES|QL.
* **Lookup Index** — индекс, созданный в специальном режиме `index.mode: lookup`. Служит правой таблицей для SQL-подобного соединения `LOOKUP JOIN` в ES|QL: содержит справочные данные (активы, threat intel, справочники клиентов), обновляется напрямую. Ограничен одним шардом — отсюда практический потолок ~2,1 млрд документов (лимит Lucene на шард).
* **Saved Object** — любой сохраненный артефакт Kibana: запрос (saved query), сессия Discover, визуализация, дашборд, Data View, алерт. Хранится в системных индексах Elasticsearch и экспортируется в формате NDJSON.
* **Saved query** — сохраненный текст запроса, фильтры и (опционально) диапазон времени; переиспользуется в любом приложении со строкой запроса. Не доступен для ES|QL-запросов — для ES|QL редактор хранит историю запросов и избранное.
* **Discover session (saved search)** — сохраненная сессия Discover: запрос, фильтры, выбранные колонки, порядок сортировки и Data View. Основной способ добавить таблицу результатов на дашборд.

## Основные концепции

Как работают языки запросов, как устроены данные в Kibana и какие возможности даёт каждый язык.

### Сравнение языков запросов

В современных версиях Kibana выбор языка зависит от сложности задачи:

| Характеристика | KQL | Lucene | ES\|QL |
| :--- | :--- | :--- | :--- |
| **Стиль** | Фильтрация | Полнотекстовый поиск | Потоковая трансформация |
| **Синтаксис** | `field: value` | `field:"value" AND ...` | `FROM index \| WHERE ... \| STATS ...` |
| **Агрегации** | Через UI (Lens) | Через UI (Lens) | **Встроены в запрос** |
| **RegEx** | Нет | Да (`/pattern/`) | Да (через функции `GROK`, `RLIKE`) |
| **Нечеткий поиск** | Нет | Да (`term~`) | Ограниченно (`MATCH` с опциями) |
| **Операторы** | `and`/`or`/`not` (регистронезависимы) | `AND`/`OR`/`NOT` (только верхний регистр) | `AND`/`OR`/`NOT` (ключевые слова регистронезависимы) |
| **Сложность** | Низкая | Средняя | Высокая (но мощная) |
| **Где выполняется** | Разбор на стороне Kibana, затем DSL | Разбор на стороне Kibana, затем DSL | Движком Elasticsearch (поколоночно) |
| **Рекомендация** | Быстрый поиск в Discover | Глубокая отладка, RegEx | Аналитика, сложные отчеты |

Полнотекстовый поиск в ES|QL: с 9.1 (GA) доступны функции `MATCH`, `MATCH_PHRASE`, `QSTR` (query string) и `KQL` — они работают как соответствующие Query DSL-запросы и существенно быстрее `LIKE`/`RLIKE` на больших данных. `MATCH` поддерживает опции `fuzziness`, `prefix_length`, `max_expansions`, `analyzer` (для индексированных text-полей).

### Модель представления данных

Kibana не изменяет исходные документы в Elasticsearch. `Data View` служит абстракцией, которая описывает структуру индексов: какие поля доступны, их типы и формат отображения (например, форматирование чисел или дат). В Data View можно также объявлять собственные runtime fields и ограничивать список полей (source filtering), что ускоряет загрузку дашбордов.

В версиях 9.x акцент смещен на **ES|QL**, который может работать напрямую с индексами или алиасами (`FROM logs-*`), минуя необходимость предварительного создания Data View для аналитических задач — в том числе в Discover (режим **Try ES|QL**) и в Lens-визуализациях на ES|QL. Тем не менее Data View остаются обязательными для классических визуализаций Lens, дашбордов и корректной работы фильтров по времени.

### Синтаксис KQL

KQL — язык только для фильтрации: он не агрегирует, не трансформирует и не сортирует данные. Ключевые правила:

* **Точность совпадения зависит от типа поля.** Для `keyword`, числовых, дата и boolean полей значение должно совпадать точно, включая регистр и пунктуацию. Для `text` полей значение анализируется: запрос `message: connection refused` найдет документы с терминами в любом порядке; для поиска точной фразы используйте кавычки — `message: "connection refused"`.
* **Логические операторы** — `and`, `or`, `not` (регистр не важен), группировка круглыми скобками. Для одного поля есть сокращение: `http.request.method: (GET OR POST OR DELETE)`.
* **Диапазоны**: `http.response.bytes > 10000 and http.response.bytes <= 20000`. Поддерживается Date Math: `@timestamp < now-2w` («раньше, чем две недели назад»).
* **Wildcards**: только `*` (ноль и более символов), например `machine.os: win*`. Начальные wildcards (`*name`) разрешены: advanced setting `query:allowLeadingWildcards` имеет значение по умолчанию `true`; если его отключить (чтобы снизить нагрузку от широких запросов), Kibana вернёт ошибку «Leading wildcards are disabled». Wildcards работают по полям типов keyword/text/wildcard, но не по числовым и датам.
* **Проверка существования поля**: `field: *`; отсутствие — `not field: *`.
* **Экранирование.** Следующие символы экранируются обратным слэшем вне кавычек: `\():<>"*{}`. Пример: `http.request.referrer: https\://example.com` или в кавычках `http.request.referrer: "https://example.com"`.
* **Вложенные (nested) поля** требуют специального синтаксиса, гарантирующего совпадение условий внутри одного вложенного документа: `user: { first: "John" and last: "Smith" }`. Для вложенных полей внутри вложенных указывайте полный путь: `user.names: { first: "John" and last: "Smith" }`. Отдельные группы в одном запросе могут совпадать с разными документами: `items: { name: banana } and items: { stock: 9 }`.
* **Ограничения:** нет RegEx, fuzzy-поиска, proximity-поиска, бустинга (`term^2`) и wildcard `?`. Для этого переключайтесь на Lucene-синтаксис.

Примеры типовых запросов:

```text
# Все 5xx ошибки за период
http.response.status_code: 5*

# Медленные запросы конкретного сервиса, кроме healthcheck
service.name: checkout and event.duration > 500000000 and not url.path: "/health"

# Либо ошибка авторизации, либо запрет доступа — и поле обязательно заполнено
(http.response.status_code: 401 or http.response.status_code: 403) and user.name: *

# Вложенное поле: один элемент массива должен удовлетворять обоим условиям
user: { first: "John" and last: "Smith" }
```

**Фильтр по метаданным Kubernetes (flattened-поля с wildcard):**

```text
# Поды веб-сервиса в продакшене
kubernetes.pod.name: web-* AND kubernetes.namespace: prod
```

### Возможности Lucene Query Syntax

Lucene включается переключателем языка слева от строки поиска. Отличия и дополнительные возможности относительно KQL:

* Операторы **только в верхнем регистре**: `AND`, `OR`, `NOT`.
* **Нечеткий поиск** по расстоянию Левенштейна: `hostnme~1` найдет `hostname`.
* **Proximity-поиск** — термины фразы в пределах N позиций: `"connection timeout"~3`.
* **Регулярные выражения** между слэшами: `response: /4[0-9]{2}/`.
* **Интервалы**: `bytes:[1000 TO 5000]`, `{}` — строгое неравенство, `[]` — включительно.
* **Существование поля**: `_exists_:user.agent`.

### Архитектура ES|QL: команды и ограничения

ES|QL строит вычислительный конвейер (pipeline): результат каждой команды передается следующей. Запрос всегда начинается с **source-команды**, за которой следуют **processing-команды**:

| Команда | Тип | Назначение |
| :--- | :--- | :--- |
| `FROM index` | Source | Чтение индекса, алиаса или data stream |
| `TS index_pattern` | Source (preview 9.2–9.3, GA 9.4) | Метрики TSDS: включает time-series функции в первом `STATS` |
| `PROMQL` | Source (preview 9.4, GA 9.5) | Нативное выполнение PromQL-запросов |
| `ROW ...` | Source | Генерация тестовой строки (удобно для экспериментов) |
| `SHOW INFO` | Source | Информация о развертывании (тип, версия) |
| `WHERE condition` | Processing | Фильтрация строк (`==`, `!=`, `>`, `LIKE`, `RLIKE`, `IN`, `IS NOT NULL`) |
| `EVAL x = expr` | Processing | Добавление вычисляемого поля |
| `STATS agg BY field` | Processing | Агрегации: `COUNT`, `COUNT_DISTINCT`, `SUM`, `AVG`, `MIN`, `MAX`, `MEDIAN`, `PERCENTILE`, `STD_DEV`, `VARIANCE`, `SAMPLE`, `TOP`, `EARLIEST`/`LATEST`/`FIRST`/`LAST` (9.4) и др.; `VALUES` — preview |
| `INLINE STATS` | Processing (preview 9.2, GA 9.3) | Промежуточная агрегация без разрыва конвейера; сохраняет все колонки входа |
| `SORT / LIMIT` | Processing | Сортировка и ограничение результата; `LIMIT N BY group` — лимит строк на группу |
| `KEEP / DROP / RENAME` | Processing | Управление колонками результата |
| `DISSECT / GROK` | Processing | Разбор неструктурированных строк по шаблону; в GROK суффикс `:int`/`:float` конвертирует тип |
| `ENRICH policy` | Processing | Обогащение данными enrich-политики (индексы времени выполнения запроса) |
| `LOOKUP JOIN idx ON field` | Processing (preview 8.18/9.0, GA 9.1) | SQL-подобный LEFT JOIN с lookup-индексом |
| `MV_EXPAND field` | Processing | Разворачивание многозначных полей в отдельные строки |
| `CATEGORIZE(message)` | Processing (GA 9.1) | Автоматическая кластеризация похожих сообщений логов |
| `CHANGE_POINT x ON t` | Processing (preview 9.1, GA 9.2; Platinum) | Статистическое обнаружение точек изменения ряда |
| `FORK ( ... ) ( ... )` | Processing (preview 9.1–9.3, GA 9.4) | До 8 параллельных ветвей над одними входными строками; колонка `_fork` |
| `SAMPLE p` | Processing (preview 9.1–9.4, GA 9.5) | Выборка доли строк `p` (0 < p < 1) |

Ключевые ограничения и особенности:

* **Лимит результата:** по умолчанию возвращается до 1000 строк; явно заданный `LIMIT` может поднять максимум до 10 000. Лимиты настраиваются динамическими настройками кластера `esql.query.result_truncation_default_size` и `esql.query.result_truncation_max_size`. Для TS/PROMQL-запросов дефолт — 10 000 строк, максимум — 10 000 000 (`esql.query.timeseries_result_truncation_*`). Для больших объемов данных агрегируйте через `STATS`, а не выводите сырые строки.
* **`_source` обязателен:** ES|QL не поддерживает конфигурации с отключенным `_source`; запросы к таким индексам завершатся ошибкой.
* **Unmapped-поля:** по умолчанию ссылка на незамаппленное поле возвращает ошибку. Директива `SET unmapped_fields="load"` разрешает загрузку значений из `_source` — медленнее, а фильтры и сортировка по таким полям могут вызвать полный скан.
* **Многозначные поля:** сравнения работают по любому значению; для явной работы используйте функции `MV_COUNT`, `MV_CONTAINS` (preview 9.2), `MV_DEDUPE`, `MV_SORT` и команду `MV_EXPAND`.
* **NULL-логика:** отсутствующие значения проверяются операторами `IS NULL` / `IS NOT NULL`; сравнение `== null` для отсутствующих полей не сработает ожидаемым образом.
* **Устойчивость (8.19/9.1+):** настройка `allow_partial_results` включена по умолчанию — запрос завершается частичными результатами, если часть шардов временно недоступна (например, во время rolling upgrade); неудачные операции на уровне шардов повторяются автоматически. Cross-Cluster Search для ES|QL GA (Enterprise-фича).
* **Наблюдаемость запросов:** query logs сохраняют логи всех ES|QL-запросов (анализ использования и трендов); Live Query Monitoring API (tech preview) показывает выполняющиеся запросы с данными профилирования.
* **Производительность:** ES|QL использует специализированный поколоночный движок (columnar engine) — агрегации выполняются существенно быстрее классических aggregation-based запросов на больших объемах.

### Временные ряды: команда TS и метрики TSDS

`TS` — source-команда для time series data streams (TSDS). Ключевое отличие от `FROM`: первый `STATS` после `TS` поддерживает time-series агрегации, которые вычисляются **по каждому временному ряду отдельно** (inner-агрегация), а затем объединяются внешней агрегацией (outer) по группам:

```esql
TS metrics-*
| WHERE TRANGE(1 hour)
| STATS req_rate = SUM(RATE(http.requests.total)) BY host, TBUCKET(5 minutes)
```

* **Counter-метрики** (сбрасываемые при рестарте): `RATE(field)` — среднее приращение в секунду с корректной обработкой сбросов; `IRATE` — мгновенная скорость между двумя последними точками; `INCREASE` — абсолютное приращение за окно.
* **Gauge-метрики**: `AVG_OVER_TIME`, `LAST_OVER_TIME` (подразумевается по умолчанию, если inner-функция не указана), `STDDEV_OVER_TIME`, `VARIANCE_OVER_TIME`, `DELTA`, `IDELTA`, `DERIV`.
* **Группировка и время**: `TBUCKET(interval)` — корзины по времени, выровненные по календарным границам (GA 9.2); `TRANGE(interval)` — фильтр по диапазону `@timestamp` (GA 9.3), эквивалент `@timestamp >= NOW() - 1 hour`.
* **Ограничения:** нельзя вкладывать две time-series функции друг в друга; `TS` нельзя комбинировать с `FORK` до первого `STATS`; в `BY` вместе с time-series функцией допустимы только grouping-функции (`TBUCKET`) или внешние агрегации.
* После первого `STATS` конвейер становится обычной таблицей — дальше можно цеплять `EVAL`, `SORT`, второй `STATS` и производные метрики (например, перцентили скоростей по кластерам).

### Многозначные поля

ES|QL-поля могут содержать несколько значений. Сравнения и агрегации работают по любому из значений; для явной работы есть multivalue-функции:

* **Манипуляции**: `MV_APPEND`, `MV_SORT`, `MV_DEDUPE` (удаление дубликатов), `MV_DIFFERENCE` (preview 9.4)
* **Выбор значения**: `MV_FIRST`, `MV_LAST`, `MV_MIN`, `MV_MAX`
* **Предикаты**: `MV_CONTAINS(field, value)` — проверка вхождения (preview 9.2)
* **Счет**: `MV_COUNT`
* Команда `MV_EXPAND field` разворачивает многозначное поле в отдельные строки — после нее `WHERE` фильтрует по каждому значению отдельно.

### FORK и переиспользование запросов

* **FORK** (preview 9.1–9.3, GA 9.4) прогоняет одни и те же входные строки через до 8 независимых ветвей и объединяет результаты в одну таблицу, добавляя колонку-дискриминатор `_fork`. У каждой ветви есть неявный `LIMIT 1000`; в одном запросе допустим только один `FORK`.

```esql
FROM employees
| FORK ( WHERE emp_no == 10001 )
( WHERE emp_no == 10002 )
| KEEP emp_no, _fork
| SORT emp_no
// → emp_no=10001, _fork=fork1; emp_no=10002, _fork=fork2
```text

* **View** — именованный запрос, сохраненный как виртуальный индекс: любой `FROM view_name` переиспользует его. **FROM-subquery** — вложенный запрос внутри другого. `IN subquery` — фильтрация строк по результатам вложенного запроса. Все три механизма динамические (выполняются в момент запроса) и объединяют колонки, заполняя отсутствующие null-значениями.

### Runtime Fields против EVAL

Оба механизма создают поля «на чтение», но применимы в разных ситуациях:

| Критерий | Runtime Fields (Data View) | EVAL (ES|QL) |
| :--- | :--- | :--- |
| Где определяется | Data View или маппинг индекса | Внутри конкретного запроса |
| Область действия | Все визуализации и фильтры | Только текущий конвейер |
| Язык | Painless | ES|QL expressions |
| Когда использовать | Поле нужно многократно в дашбордах | Разовая трансформация внутри анализа |

Правило выбора: если вычисление нужно одному расследованию — используйте `EVAL`; если поле востребовано постоянно — оформляйте его как runtime field в Data View, чтобы не дублировать логику во всех запросах.

## Практические сценарии

Последовательные рабочие сценарии — от быстрого поиска инцидента до экспорта объектов в GitOps.

### Предварительные требования

Для воспроизведения сценариев необходимы:

1. Работающая пара Elasticsearch + Kibana версий 8.19 или 9.x. Если стенда нет — разверните по руководству [Развертывание ELK стека в Docker Compose](../Tutorials/practical_setup_with_docker.md).
2. Учетная запись с ролью, дающей права `read` на индексы `logs-*` и доступ к приложениям Discover/Dashboard (проверить: **Stack Management → Roles**).
3. Тестовые данные. Быстрый вариант — демо-набор: **Integrations → Sample Data → Other sample data sets → Sample web logs** (создаст Data View `kibana_sample_data_logs` с ~10 тыс. документов веб-логов).
4. Проверка готовности:

```bash
# Статус кластера должен быть green/yellow
curl -sk -u elastic:$PASSWORD https://localhost:9200/_cluster/health?pretty
# → "status" : "green"

# Наличие данных в целевых индексах
curl -sk -u elastic:$PASSWORD "https://localhost:9200/_cat/indices/logs-*?v"
# → таблица с колонками health, index, docs.count
```

### Быстрый поиск инцидента в Discover (KQL)

**Задача:** найти всплеск ошибок аутентификации за последний час.

1. Откройте **Discover**, выберите Data View с логами (например, `logs-*`).
2. Установите интервал времени: Last 1 hour (правый верхний угол).
3. Введите запрос:

```text
event.dataset: auth and message: "failed password" and not user.name: svc-monitor
```text

4. Добавьте поля в таблицу кнопкой "+" рядом с именем поля: `user.name`, `source.ip`, `host.name`. Клик по значению поля в боковой панели добавляет фильтр; рядом с агрегируемым полем доступна кнопка **Visualize** — Kibana создаст подходящую визуализацию.

### Анализ инцидента с помощью ES|QL

**Задача:** выявить топ-10 IP-адресов, с которых поступает наибольшее количество запросов с ошибками 404, и рассчитать их средний объем трафика.

```esql
FROM logs-*
| WHERE http.response.status_code == 404
| STATS count = COUNT(*), avg_bytes = AVG(http.response.body.bytes) BY source.ip
| WHERE count > 100
| SORT count DESC
| LIMIT 10
```

Построчное объяснение:

* `FROM logs-*` — источник: все индексы логов;
* `WHERE ... == 404` — оставляем только ошибки 404;
* `STATS ... BY source.ip` — агрегируем сразу в запросе: количество и средний размер ответа на каждый IP;
* `WHERE count > 100` — фильтруем уже агрегированный результат (второй WHERE после STATS — легальная практика);
* `SORT ... DESC | LIMIT 10` — топ-10.

Этот запрос можно выполнить в **Discover** (меню приложения → **Try ES|QL**) и мгновенно превратить в визуализацию кнопкой **Save visualization to dashboard** над графиком результатов. Редактор ES|QL автодополняет команды и функции, а для `LOOKUP JOIN` подсказывает lookup-индексы и поля соединения.

**Проверка:** таблица результатов содержит ровно до 10 строк с колонками `source.ip`, `count`, `avg_bytes`; над результатами отображается плашка с временем выполнения запроса.

### Парсинг неструктурированных логов (DISSECT и GROK)

Когда логи приходят единой строкой, ES|QL позволяет разобрать их на лету, без ingest-пайплайнов и переиндексации:

* `DISSECT` — быстрый разбор по фиксированному шаблону с разделителями (без регулярных выражений);
* `GROK` — разбор через именованные регулярные выражения (гибче, но медленнее).

```esql
// DISSECT: стабильный формат "дата время метод путь статус"
ROW message = "2026-08-20 12:33:01 GET /api/v1/users 200"
| DISSECT message "%{date} %{time} %{verb} %{path} %{status}"
| EVAL ts = DATE_PARSE("yyyy-MM-dd HH:mm:ss", CONCAT(date, " ", time)), code = TO_LONG(status)
| KEEP ts, verb, path, code
// → одна строка: ts=2026-08-20T12:33:01.000Z, verb=GET, path=/api/v1/users, code=200
```text

```esql
// GROK: форматы с вариациями, с преобразованием типов суффиксами :int/:float
FROM logs-legacy-*
| GROK message "%{IP:client_ip} %{WORD:method} %{URIPATHPARAM:request} %{NUMBER:bytes:int}"
| EVAL bytes = COALESCE(bytes, 0)
| KEEP client_ip, method, request, bytes
| LIMIT 100
// → строки с распарсенными колонками client_ip, method, request, bytes
```

**Выбор инструмента:** если формат стабилен — `DISSECT` (быстрее и дешевле); если части строки могут меняться местами или отсутствовать — `GROK`.

### Обогащение данных: LOOKUP JOIN и ENRICH

**Задача:** сопоставить IP-адреса из логов со списком угроз (threat intel) прямо во время запроса.

**Шаг 1. Создайте lookup-индекс** (один раз; требует Elasticsearch 8.18+; в ветках 9.x команда общедоступна с 9.1; lookup-индекс ограничен одним шардом):

```bash
PUT threat-intel
{
  "settings": { "index.mode": "lookup" },
  "mappings": {
    "properties": {
      "source.ip":   { "type": "keyword" },
      "reputation":  { "type": "keyword" },
      "category":    { "type": "keyword" }
    }
  }
}
# → {"acknowledged":true,"shards_acknowledged":true}
```text

**Шаг 2. Загрузите справочные данные:**

```bash
POST _bulk
{"index":{"_index":"threat-intel","_id":"1"}}
{"source.ip":"203.0.113.5","reputation":"malicious","category":"C2_SERVER"}
{"index":{"_index":"threat-intel","_id":"2"}}
{"source.ip":"198.51.100.2","reputation":"suspicious","category":"SCANNER"}
# → "errors": false, "items": [...]
```

**Шаг 3. Выполните соединение:**

```esql
FROM logs-*
| WHERE http.response.status_code == 404
| STATS attempts = COUNT(*) BY source.ip
| SORT attempts DESC
| LIMIT 1000
| LOOKUP JOIN threat-intel ON source.ip
| WHERE reputation IS NOT NULL
| KEEP source.ip, attempts, reputation, category
// → строки вида: source.ip=203.0.113.5, attempts=142, reputation=malicious, category=C2_SERVER
```text

Особенности семантики: это LEFT OUTER JOIN — строки без совпадений сохраняются (с пустыми колонками справа). При нескольких совпадениях `ENRICH` создает многозначное поле, а `LOOKUP JOIN` — несколько строк. Для топ-N запросов сортируйте и ограничивайте выборку до `LOOKUP JOIN` — оптимизатор ES|QL по возможности переносит `WHERE` до соединения, а сама команда быстрее, когда строк для соединения немного.

Возможности GA-версии (9.1): соединение по полям совместимых числовых типов (long с integer), алиасы lookup-индекса, `date_nanos`. С 9.2: соединение по списку полей и по выражению с `AND` (preview), удаленные lookup-join в cross-cluster запросах.

Альтернатива для старых версий — `ENRICH`: политика создается один раз и синхронизируется по команде `_execute`, обогащение привязано к ingest-пайплайну либо вызывается в запросе (`| ENRICH policy-name ON field WITH new_field`). `ENRICH` оптимизирован для небольших редко меняющихся справочников; `LOOKUP JOIN` проще в сопровождении: не нужны политики, индекс обновляется напрямую.

### Временные ряды и поиск аномалий (BUCKET, CHANGE_POINT)

**Задача:** найти момент, когда количество серверных ошибок резко изменилось.

```esql
FROM logs-web-*
| WHERE http.response.status_code >= 500
| STATS errors = COUNT(*) BY bucket = BUCKET(@timestamp, 15 minutes)
| SORT bucket
| CHANGE_POINT errors ON bucket AS change_type, pvalue
| KEEP bucket, errors, change_type, pvalue
| LIMIT 200
```

Как это работает:

* `BUCKET(@timestamp, 15 minutes)` — корзины фиксированного размера. Для автоматического подбора размера задайте целевое число корзин и диапазон: `BUCKET(@timestamp, 25, "2026-01-01T00:00:00Z", "2026-02-01T00:00:00Z")` — интервал подберется под диапазон (в дашбордах вместо явных границ можно использовать переменные `?_tstart`/`?_tend`).
* `CHANGE_POINT` статистически определяет точки резкого изменения ряда и возвращает тип изменения и p-value: значение ниже 0.05 означает статистически значимое изменение.

Версионные ограничения: команда в preview с 9.1, GA с 9.2; **требует лицензии Platinum/Enterprise**. Для детекции нужно минимум 22 значения в ряду; учитываются первые 1000 значений. Возможные типы изменений: `dip`, `spike`, `step_change`, `trend_change`, `distribution_change`. С 9.5 детекция выполняется независимо по группам (`BY`).

**Проверка:** в момент инцидента строка `change_type` будет содержать `spike`/`step_change` с малым `pvalue`.

### Метрики TSDS: скорость событий и сбросы счётчиков (TS, RATE)

**Задача:** сравнить интенсивность запросов по хостам за последний час, не искажая результат сбросами счётчиков при рестартах сервисов.

```esql
TS metrics-*
| WHERE TRANGE(1 hour)
| STATS requests_per_sec = SUM(RATE(http.requests.total)) BY host, TBUCKET(5 minutes)
| SORT host, TBUCKET
```text

Почему не `SUM` по сырым значениям: counter сбрасывается в ноль при рестарте процесса, и сумма по сырым сэмплам смешивает значения до и после сброса. `RATE` сначала вычисляет приращение внутри каждого временного ряда (с обработкой сбросов), а внешний `SUM` складывает приращения по рядам — результат корректен при любых рестартах.

**Проверка:** результат содержит колонки `host`, `TBUCKET` (тип datetime) и `requests_per_sec` (double); при отсутствии inner-функции ES|QL неявно использует `LAST_OVER_TIME`.

### Построение визуализации в Lens с формулами

**Задача:** доля ошибок 5xx от общего трафика + линия SLO 99.9%.

1. **Dashboard → Create dashboard → Create visualization** (откроется Lens).
2. Выберите Data View `logs-*` (или `kibana_sample_data_logs`).
3. Перетащите `@timestamp` в горизонтальную ось — построится гистограмма по времени.
4. В вертикальную ось добавьте метрику и переключитесь на вкладку **Formula**:

```text
count(kql='http.response.status_code >= 500') / count()
```text

Формула считает долю ошибок: функция `count(kql='...')` принимает KQL-условие внутри агрегации. Установите Value format → **Percent**.
5. Добавьте слой **Reference lines** со статическим значением `0.001` и подписью `SLO 99.9%` — порог допустимого уровня ошибок. Типы линий: **Static** (константа), **Quick functions** (перцентили и др.), **Formula** (вычисляемая).
6. Для таблицы «топ-5 URL по времени ответа»: создайте вторую панель типа **Table**, метрика `average(event.duration)`, разбивка по `url.path` с Top values = 5 и сортировкой по убыванию.
7. Сохраните панель (**Save and return**) — она появится на дашборде.

Полезные приемы формул:

```text
// Процент от общего числа документов всех бакетов
count() / overall_sum(count())

// Сравнение с предыдущей неделей (time shift)
count(shift="1w")

// Разнонаправленная столбчатая диаграмма: успехи вверх, ошибки вниз
count(kql='http.response.status_code < 400') * -1
count(kql='http.response.status_code >= 400')
```

Функция **Filters** позволяет применить несколько KQL-фильтров и наложить фильтр на отдельный слой — визуализировать отфильтрованные и нефильтрованные данные одновременно. Полный справочник функций доступен по кнопке-книжке в левом нижнем углу редактора формул.

**Совместимость с наследием:** legacy-редакторы (TSVB, aggregation-based визуализации, панели Timelion) deprecated — их удаление запланировано в Kibana 10.0; новые графики создаются в Lens. Приложение Timelion удалено в 7.16, но тип панели Timelion на дашбордах сохранен для сложных выражений `.es(...)`. Canvas deprecated с 9.0 (удаление также в 10.0). Существующие панели TSVB продолжают отображаться на дашбордах; их можно открыть и пересобрать в Lens (функция открытия TSVB в Lens появилась в 8.x).

**Проверка:** наведите курсор на график — тултип показывает значение формулы на точке времени; справочная линия отображается пунктиром; изменение фильтра дашборда пересчитывает все панели.

### Создание интерактивных дашбордов (9.4+)

В Kibana 9.4 элементы управления стали полноценными панелями дашборда:

* **Draggable controls**: controls — обычные панели, которые можно перетаскивать в любое место дашборда и изменять по размеру. Новые controls по умолчанию закреплены вверху (pinned) и применяются ко всем панелям.
* **Pin/Unpin и scoping**: открепите control (**Unpin**), чтобы переместить его в тело дашборда; помещенный внутрь сворачиваемой секции control автоматически ограничивает область действия панелями этой секции — один дашборд может обслуживать несколько сценариев без взаимных сбросов фильтров.
* **Variable controls** (preview с 9.0; в 9.0–9.1 назывались ES|QL controls): заполняют выпадающие списки результатами ES|QL-запроса — например, только те `host.name`, которые были активны за последний час. Применяются только к ES|QL-визуализациям, ссылающимся на переменную control; цепочечное связывание — через `?variable_name` в запросе другого control.
* **Time slider**: ползунок диапазона времени с анимацией изменения данных.
* **Drilldowns** между дашбордами работают для ES|QL-визуализаций (9.4); панели фильтров (filter pills) вверху дашборда сворачиваются в строку после порога.

Пошаговый сценарий сборки:

1. **Dashboard → Create dashboard → Add panel → Controls**.
2. Добавьте **Options list** по полю `host.name` — выпадающий список значений для фильтрации.
3. Добавьте **Range slider** по `event.duration` для фильтрации медленных запросов (только числовые поля).
4. Перетащите панели управления рядом с ключевыми графиками и уменьшите их размер — они работают как обычные панели дашборда.
5. Настройте область действия: у панели-контрола укажите, применяется ли он ко всему дашборду или к выбранным панелям (scoping).
6. Добавьте остальные панели (Lens-графики, таблицы) и сохраните дашборд с говорящим именем и тегом проекта.

Кросс-фильтрация работает «из коробки»: клик по сегменту диаграммы применяет соответствующий фильтр ко всему дашборду (если scoping не ограничил действие).

**Проверка:** выбор значения в Options list мгновенно обновляет связанные панели; в строке фильтров появляется соответствующее условие.

### Drilldowns: навигация с панели дашборда

Drilldown — настроенное действие по клику на значение панели: он переносит выбранное значение, фильтры и диапазон времени в другое место, сохраняя контекст расследования.

Три типа drilldown:

* **Dashboard** — переход на другой дашборд с фильтрами/временем исходной панели (например, из сводки в детальный дашборд с фильтром по выбранному host).
* **URL** — переход на внешний сайт по шаблону с переменными Handlebars: `{{kibanaUrl}}`, `context.panel.*` (фильтры, запрос, time range), `event.*` (значение точки/строки клика).
* **Discover** — переход к документам, которые стоят за визуализацией.

Создание (дашборд в режиме **Edit**):

1. Меню панели → **Create drilldown**.
2. Выбрать тип (**Go to dashboard** / **Go to URL** / **Go to Discover**), задать имя.
3. Для dashboard-типа — выбрать дашборд-назначение и опции переноса: **Use filters and query from origin dashboard**, **Use date range from origin dashboard**.
4. Для URL-типа — задать триггер (**Single click**, **Context menu**, **Range selection**, **Table row click** — зависит от панели) и сам URL-шаблон; все доступные для шаблона переменные показываются кнопкой **Add variable**.
5. **Create drilldown** → **сохранить дашборд**.

Использование: наведение на значение (сегмент, точка, ячейка) → знак `+` / меню → выбрать drilldown. Меню панели → **Manage drilldowns** — правка, копирование и удаление (drilldown хранится вместе с дашбордом и привязан к конкретной панели, между панелями не переиспользуется).

Требования: полный доступ (**All**) к фиче **Dashboard** для создания; поддерживаются панели Lens, Maps, TSVB, Vega, агрегационные визуализации, Discover session; для ES|QL-визуализаций drilldowns доступны с 9.4 (см. раздел выше).

### Экспорт и импорт объектов через UI и API (GitOps)

Через UI: **Stack Management → Saved Objects** — экспорт/импорт с фильтрами по типу и тегам, опция включения связанных объектов (визуализаций, Data View) вместе с дашбордом.

Через API (для автоматизации):

```bash
export KBN="https://localhost:5601"
# API-ключ создается в Stack Management -> API Keys
export AUTH="Authorization: ApiKey ${KIBANA_API_KEY}"

# Экспорт всех дашбордов со связанными объектами в NDJSON
curl -sk -X POST "${KBN}/api/saved_objects/_export" \
  -H "kbn-xsrf: true" -H "${AUTH}" \
  -H 'Content-Type: application/json' \
  -d '{"type": ["dashboard"], "includeReferencesDeep": true}' \
  -o dashboards.ndjson
# → создается файл dashboards.ndjson: по одной JSON-строке на объект

# Импорт в другом окружении (createNewCopies избегает конфликтов идентификаторов)
curl -sk -X POST "${KBN}/api/saved_objects/_import?createNewCopies=true" \
  -H "kbn-xsrf: true" -H "${AUTH}" \
  --form file=@dashboards.ndjson
# → {"success":true,"successCount":12,"successResults":[...]}
```

Параметры: `createNewCopies=true` создает копии с новыми ID (безопасный перенос), `overwrite=true` замещает объекты с теми же ID (актуализация окружения), `?spaceId=` задает целевое пространство. Полученный `.ndjson` коммитится в Git и деплоится через CI — стандарт управления конфигурацией Kibana как кодом.

### Управление Data View (index patterns) через API

Data View (ранее Index Pattern) можно создавать и перечислять программно — удобно для bootstrap новых окружений и CI/CD:

```bash
export KBN="http://kibana:5601"
export AUTH="Authorization: ApiKey ${KIBANA_API_KEY}"

# Создать Data View для логов с полем времени
curl -X POST "${KBN}/api/saved_objects/index-pattern" \
  -H "kbn-xsrf: true" -H "${AUTH}" \
  -H 'Content-Type: application/json' \
  -d '{"attributes":{"title":"logs-*","timeFieldName":"@timestamp"}}'
# → {"id":"logs-*","name":"","type":"index-pattern", ...}

# Список всех зарегистрированных Data View
curl -s "${KBN}/api/saved_objects/_find?type=index-pattern" \
  -H "kbn-xsrf: true" -H "${AUTH}" | jq '.saved_objects[].attributes.title'
# → logs-*
```

**Примечание:** в 9.x тип `index-pattern` в Saved Objects API сохраняет обратную совместимость с 8.x; UI-терминология — Data View, API-имя — index-pattern.

**Dashboards и Visualizations API** (эксперимент в 9.4, GA в 9.5.0): программное создание дашбордов и визуализаций. Панели размещаются на 48-колоночной сетке; поддерживаются визуализации (data view и ES|QL), сессии Discover, изображения, markdown, ссылки и ES|QL-контролы (`esql_control`); закрепленные controls (`pinned_panels`) применяются ко всем панелям дашборда.

**ES|QL REST API** — для автоматизированной выгрузки данных и отчетов:

```bash
# Синхронный запрос в CSV (форматы: json, csv, tsv, txt, yaml, arrow, cbor, smile)
curl -sk -u elastic:$PASSWORD -X POST "https://localhost:9200/_query?format=csv" \
  -H 'Content-Type: application/json' \
  -d '{"query": "FROM logs-* | WHERE log.level == \"error\" | KEEP @timestamp, service.name, message | LIMIT 100"}'
# → CSV-таблица результатов

# Асинхронный запрос для тяжелых выборок
curl -sk -u elastic:$PASSWORD -X POST "https://localhost:9200/_query/async" \
  -H 'Content-Type: application/json' \
  -d '{"query": "FROM logs-* | STATS count = COUNT(*) BY service.name", "wait_for_completion_timeout": "2s", "keep_on_completion": true}'
# → {"id": "...", "is_running": true}

# Забрать результат по id (keep_alive по умолчанию 5 дней)
curl -sk -u elastic:$PASSWORD "https://localhost:9200/_query/async/<id>?wait_for_completion_timeout=30s"
# → {"is_running": false, "took": 48, "columns": ...}
```text

Параметры запроса: `columnar=true` — колоночный формат вывода (JSON/YAML/CBOR/smile), `filter` — предварительная фильтрация документов через Query DSL, `drop_null_columns`, `time_zone`. Асинхронный запрос можно остановить API остановки, а результат удалить до истечения `keep_alive`.

**Проверка:** после импорта откройте дашборд в целевом окружении и убедитесь, что все панели отображают данные (отсутствующий Data View или индексы — самая частая причина пустых панелей).

### Запросы через Dev Tools Console

Dev Tools (Console) — интерактивная консоль для прямых запросов к Elasticsearch API. Удобен для отладки и ad-hoc аналитики:

```
GET logs-*/_search
{
  "query": {"match": {"level": "error"}},
  "size": 10
}
```

Нажмите **Play** (▶) или `Ctrl+Enter` — результат появится в правой части. История запросов сохраняется между сессиями.

## Дополнительная информация

Справочные материалы: управление saved objects, продвинутая аналитика, troubleshooting и лучшие практики.

### Управление объектами (Saved Objects)

* **NDJSON и GitOps**: Все объекты (дашборды, визуализации) экспортируются в формате `.ndjson`. Это стандарт для версионирования настроек Kibana в Git и автоматизированного деплоя через API (см. сценарий выше).
* **Tags**: Используйте теги для группировки объектов по проектам (например, `Project: Alpha`, `Tier: Frontend`), что упрощает поиск при наличии сотен дашбордов. Теги поддерживают собственную палитру цветов и фильтрацию в списке Saved Objects.
* **Именование:** договоритесь о схеме именования, например `[Team] Purpose - Type` (`[Payments] Checkout errors - Dashboard`) — при сотнях объектов это ускоряет навигацию сильнее, чем теги.

### Background search вместо Search sessions

Долгие запросы в Discover и на дашбордах можно отдавать в фон, не блокируя работу в Kibana:

* **Search sessions устарели с 8.15**, с **9.2** их заменяет **background search**; существующие сессии при апгрейде не теряются — они становятся background searches.
* Признак обеих функций — один и тот же ключ `kibana.yml`: `data.search.sessions.enabled` (по умолчанию `false`). Если на предыдущей версии feature уже был включён, после апгрейда он включается автоматически.
* Результаты хранятся `data.search.sessions.defaultExpiration` — по умолчанию `7d`; продление выполняется в UI (More actions → Extend). Число повторных попыток фоновой отправки — `data.search.sessions.maxUpdateRetries` (по умолчанию `10`).
* **Discover session** (сохранённая сессия) — другой объект: это сохранённый запрос с колонками и сортировкой, который кладётся на дашборд и участвует в reporting. Background search — механизм исполнения, Discover session — сохранённый артефакт; они независимы.

### Продвинутая аналитика



* **Vega и Vega-Lite**: Если возможностей Lens недостаточно, используйте Vega для создания полностью кастомных визуализаций на базе JSON-спецификаций. Vega-панели могут выполнять произвольные Elasticsearch-запросы (`url: { index: ... }`) и объединять несколько источников данных в одном графике — недоступное для Lens ограничение. С 9.5 к панелям Vega с ES|QL применяются диапазон времени, строка запроса, фильтры и controls дашборда.
* **Maps Layers**: Слои карт, в том числе **ES|QL-слой** — вставьте ES|QL-запрос, возвращающий хотя бы одно гео-поле (`geo_point`/`geo_shape`), и точки или полигоны отрисуются на карте без индексации промежуточных данных; доступны также слои Documents, Clusters и Choropleth (с границами EMS). Для гео-фильтрации в самом ES|QL доступны функции `ST_DISTANCE`, `ST_WITHIN`, `ST_INTERSECTS`, `ST_CONTAINS`, `ST_DISJOINT` по полям `geo_point`/`geo_shape`.

### Типичные проблемы и их решение (Troubleshooting)

1. **Discover пустой, хотя данные точно есть.**
   Причины: выбран неверный интервал времени; в Data View указано не то поле времени; индекс не содержит документов.
   Диагностика: `GET _cat/indices/logs-*?v` в Dev Tools — проверить `docs.count`; расширить time picker на Last 1 year; проверить поле времени в настройках Data View.
2. **Ошибка синтаксиса KQL (Unexpected token).**
   Причина: неэкранированные спецсимволы `\():<>"*{}` в значении.
   Решение: заключите значение в кавычки или экранируйте символы: `url.path: "/api/v1/users?id=42"`.
3. **Результаты ES|QL внезапно обрезаются (ровно 1000 строк).**
   Причина: лимит по умолчанию.
   Решение: добавьте явный `LIMIT` (максимум 10 000) или перепишите запрос через `STATS` — вывод миллионов сырых строк антипаттерн даже при высоком лимите. Лимиты настраиваются настройками кластера `esql.query.result_truncation_default_size` / `esql.query.result_truncation_max_size`.
4. **ES|QL: `Unknown index` или ошибка о неподдерживаемом типе поля.**
   Причины: индекс не существует/нет прав; некоторые типы полей пока не поддерживаются; `_source` отключен в маппинге.
   Решение: проверьте имя и права доступа; убедитесь, что `_source` включен; неподдерживаемые типы обработайте приведением (`TO_STRING`, `TO_IP`).
5. **ES|QL: ошибка на поле, которое точно существует в данных.**
   Причина: поле не замапплено (unmapped) — по умолчанию ES|QL возвращает ошибку.
   Решение: директива `SET unmapped_fields="load"` разрешает загрузку из `_source` (медленнее; фильтры по таким полям могут вызвать полный скан).
6. **Ошибка «The content length (...) is bigger than the maximum allowed string».**
   Причина: запрос ко множеству индексов без фильтров возвращает слишком большой ответ.
   Решение: ограничьте поля командами `KEEP`/`DROP`, сузьте шаблон индексов, добавьте `WHERE`.
7. **Дашборд открывается десятки секунд.**
   Причины: больше ~20 панелей; слишком широкий шаблон индексов (`logs-*` за год); top-N агрегации по высококардинальным полям.
   Решение: сузьте шаблон (например, `logs-payments-*`), сократите число панелей, ограничьте размер top values, используйте фильтры по умолчанию; полный разбор механизма и настроек — [Производительность дашбордов и запросов](./kibana_dashboard_performance.md).
8. **HTTP 403 при открытии данных.**
   Причина: роли не хватает привилегии `read` на индекс либо нет доступа к Space, где лежит объект.
   Решение: **Stack Management → Roles** — добавить привилегию индекса или назначить Space; проверить от имени проблемного пользователя.
9. **`LOOKUP JOIN` завершается ошибкой `Unknown index [threat-intel]`.**
   Причина: индекс создан без режима lookup.
   Решение: пересоздайте индекс с `"settings": {"index.mode": "lookup"}` (см. сценарий выше); также проверьте совместимость типов ключа соединения.
10. **Новое поле не появляется в Lens.**
    Причина: кэш списка полей Data View.
    Решение: **Stack Management → Data Views → [ваш Data View]** → нажать иконку обновления полей; если поле виртуальное — создать runtime field.
11. **В режиме ES|QL в Discover недоступна строка фильтров.**
    Причина: в ES|QL-режиме UI фильтров не включен по дизайну.
    Решение: фильтруйте командой `WHERE` в запросе; для интерактивной фильтрации используйте controls и кнопки фильтрации в таблице и списке полей.
12. **Discover показывает не более 10 000 строк.**
    Причина: лимит отображения Discover в ES|QL-режиме.
    Решение: агрегируйте через `STATS`; для сырых выборок используйте ES|QL REST API с `format=csv`.
13. **`CHANGE_POINT`: ошибка лицензии или `indeterminable`.**
    Причина: команда требует лицензии Platinum/Enterprise; для детекции нужно минимум 22 значения в ряду (учитываются первые 1000).
    Решение: проверьте лицензию; расширьте диапазон времени или уменьшите размер корзин `BUCKET`.
14. **KQL: «Leading wildcards are disabled».**
    Причина: запрос начинается с `*`, а advanced setting `query:allowLeadingWildcards` был отключён (значение по умолчанию — `true`).
    Решение: включите `query:allowLeadingWildcards` (**Stack Management → Advanced Settings**) либо перестройте запрос на суффиксный wildcard (`machine.os: win*`).
15. **Saved query не сохраняется для ES|QL-запроса.**
    Причина: saved queries не поддерживают ES|QL.
    Решение: используйте историю запросов и избранное в ES|QL-редакторе; для переиспользования сохраняйте визуализацию или Discover session.
16. **URL дашборда становится неприлично длинным (обрывается в прокси или браузере).**
    Причина: Kibana хранит состояние фильтров/визуализаций в URL.
    Решение: включите advanced setting `state:storeInSessionStorage` (**Stack Management → Advanced Settings**) — состояние части URL переносится в browser session storage, URL остаётся коротким.

### Лучшие практики и очистка окружения

* **Язык под задачу:** KQL — быстрая фильтрация в Discover и на дашбордах; ES|QL — вся аналитика и ad-hoc расследования; Lucene — только когда нужен RegEx/fuzzy/proximity.
* **Сохраняйте частые запросы** как saved queries (KQL/Lucene) с осмысленными именами — это документирует расследования и делает их воспроизводимыми. Для ES|QL используйте историю и избранное редактора; тяжелые аналитические запросы закрепляйте как сохраненные визуализации.
* **Тяжелые запросы сначала в Dev Tools:** выполните ES|QL через Console, оцените время (`took`) и объем выборки, и лишь потом закрепляйте запрос в панели дашборда. Для долгих выборок используйте async API (`POST /_query/async`).
* **Метрики — через TS:** для TSDS-индексов используйте `TS` вместо `FROM`: `RATE` корректно обрабатывает сбросы счётчиков, чего не делает `SUM` по сырым значениям.
* **Изоляция:** используйте Spaces для разделения проектов, теги — для таксономии внутри Space; ограничивайте шаблоны индексов наиболее узкими достаточными.
* **Очистка тестовых артефактов** (важно для опрятности продакшена): удаляйте временные Data View, тестовые дашборды и lookup-индексы после завершения работы:

```bash
# Удаление saved object по типу и id
curl -sk -X DELETE "${KBN}/api/saved_objects/dashboard/<dashboard-id>" \
  -H "kbn-xsrf: true" -H "${AUTH}"
# → HTTP 200, тело {}

# Удаление тестового lookup-индекса
curl -sk -u elastic:$PASSWORD -X DELETE "https://localhost:9200/threat-intel"
# → {"acknowledged":true}
```

* **Резервирование:** регулярно экспортируйте Saved Objects в NDJSON (UI или API) и храните в Git — восстановление окружения сводится к одному `_import`.
