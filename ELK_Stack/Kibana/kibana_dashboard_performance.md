# Kibana: Производительность дашбордов и запросов

> **Актуально для:** Kibana 8.19 / 9.x

Медленный дашборд — это почти всегда либо слишком широкий запрос (диапазон, шаблон индексов, кардинальность), либо неподходящие настройки исполнения поиска. Эта заметка — о механизме выполнения запросов дашбордом, диагностике через Inspector и настройках Advanced Settings / `kibana.yml`, влияющих на скорость. Ресурсы самого процесса Kibana — в [Обзоре](./kibana_overview.md), тюнинг Elasticsearch — в [Search tuning](../Elasticsearch/elasticsearch_search_tuning.md).

## Определения

* **Inspector** — встроенный инспектор запросов: меню панели → **Inspect** показывает уходящий в Elasticsearch запрос и статистику выполнения (время, hits, состав агрегаций). Главный инструмент диагностики «какая именно панель тормозит».
* **Advanced Settings** (`Stack Management → Advanced Settings`) — пользовательские настройки поиска и визуализаций (`search:timeout`, `courier:*`, `histogram:*`); применяются ко всему инстансу Kibana.
* **`_msearch`** — эндпоинт Elasticsearch, которым Kibana отправляет поисковые запросы панелей дашборда.
* **Уровни таймаутов Kibana → ES** — `elasticsearch.shardTimeout` (ожидание ответа от шард, `30000` мс, `0` — отключить), `elasticsearch.requestTimeout` (общий ответ ES, `30000` мс) и `search:timeout` (лимит времени поискового запроса в Advanced Settings, `600000` мс). Таблица `kibana.yml`-таймаутов — в [Эксплуатации](./kibana_production_operations.md).

## Основные концепции

### Как дашборд исполняет запросы

При открытии дашборда Kibana отправляет запросы всех панелей (пакетно, через `_msearch`) и отрисовывает результаты по мере их поступления, но **видимость дашборда «собирается» целиком: время открытия определяется самой медленной панелью**. Отсюда практический вывод: одна тяжёлая агрегация на дашборде из 20 панелей ухудшает впечатление от всех 20.

Стоимость запроса на стороне Kibana складывается из:

1. **Ширины выборки** — диапазон времени и шаблон индексов (`logs-*` за год против `logs-payments-*` за час).
2. **Кардинальности** — top-N по полю с миллионами значений (например, `url.path` с параметрами) не падает от таймаута, а просто возвращает невыполнимую агрегацию.
3. **Плотности гистограмм** — количество бакетов ограничивается настройками `histogram:*` (см. ниже).
4. **Побочных эффектов UI** — подсветка совпадений, автодополнение, автообновление каждые N секунд добавляют запросы поверх панельных.
5. **Таймаутов** — Kibana обрывает запрос на трёх уровнях; дефолт `search:timeout` (10 минут) выше, чем `elasticsearch.requestTimeout` (30 секунд), поэтому на практике ответ чаще обрезается по `requestTimeout`/`shardTimeout`, а `search:timeout` страхует крайние случаи.

### Таймауты: как они взаимодействуют

* `elasticsearch.shardTimeout: 30000` — ES ждёт ответа от шард; по истечении возвращаются **частичные результаты** (панель может отрисоваться «не полностью» без явной ошибки).
* `elasticsearch.requestTimeout: 30000` — общий таймаут Kibana на ответ бэкенда; превышение — ошибка запроса.
* `search:timeout: 600000` (Advanced Settings, мс) — лимит времени выполнения поискового запроса; `0` — отключить и давать запросу завершиться (тогда нагрузка удерживается сокетами Kibana — учитывайте `elasticsearch.maxSockets`).

Долгие аналитические запросы вручную не «удлиняются» переключением одного таймаута: поднимать имеет смысл все три значения согласованно, либо выносить тяжёлую аналитику в async/фоновый режим (см. практики).

## Практические сценарии

### Диагностика: найти виновника

1. Откройте дашборд, включите **Edit** → меню панели → **Inspect** → вкладка **Requests** — actual запрос к ES; вкладка статистик — время и hits.
2. Сузьте диапазон времени до минимально нужного и сравните время — если панель ускоряется линейно, дело в объёме данных, а не в запросе.
3. Воспроизведите запрос в **Dev Tools** и оцените `took`; профилирование самого запроса (`POST _search/profile`) — в [Search tuning](../Elasticsearch/elasticsearch_search_tuning.md).
4. Проверьте, не включено ли автообновление (`timepicker:refreshIntervalDefaults`) — панели перезапрашиваются в фоне и создают видимость «постоянно тянущегося» дашборда.

### Настройки Advanced Settings, влияющие на скорость

`Stack Management → Advanced Settings` (общие для инстанса):

| Настройка | Дефолт | Влияние |
| :--- | :--- | :--- |
| `search:timeout` | `600000` мс | Лимит времени поискового запроса; `0` — без лимита |
| `histogram:maxBars` | `1000` | Потолок плотности гистограмм: Kibana тестовым запросом увеличивает интервал бакетов при превышении; ограничивается от `search.max_buckets` в ES |
| `histogram:barTarget` | `100` | Целевое число столбцов для интервала `auto` у date-гистограмм |
| `courier:setRequestPreference` | `Session ID` | `Session ID` — повторный use shard cache; `None` — запросы разносятся по копиям шард (может быть быстрее, но результаты зависят от refresh-состояния); `Custom` — своё значение через `courier:customRequestPreference` (дефолт `_local`) |
| `courier:maxConcurrentShardRequests` | `0` | `max_concurrent_shard_requests` для `_msearch`; `0` — значение по умолчанию ES |
| `courier:ignoreFilterIfFieldNotInIndex` | `false` | `true` — фильтр не применяется к панели, чья Data View не содержит поля фильтра: меньше невыполнимых фильтров на мульти-дашбордах |
| `doc_table:highlight` | `true` | Подсветка результатов в Discover-панелях; замедляет запросы с большими документами — отключить, если подсветка не нужна |
| `autocomplete:valueSuggestionMethod` | — | `terms_enum` — быстрее, значения приблизительные (и несовместим с DLS); `terms_agg` — точнее и по популярности, но медленнее |
| `labs:dashboard:deferBelowFold` | `false` (Experimental) | Отложенная загрузка панелей ниже первого экрана: не видимые при открытии панели запрашиваются при прокрутке |
| `timepicker:refreshIntervalDefaults` | `{"pause": true, "value": 60000}` | Дефолтный автоинтервал обновления; по умолчанию автообновление на паузе |

Настройки, разобранные в другой заметке и здесь не дублируемые: `state:storeInSessionStorage` (короткие URL), `query:allowLeadingWildcards` (KQL) — [Поиск, визуализация и управление](./kibana_search_and_visualization.md).

### Оптимизация дашборда

* **Диапазон и шаблон**: узкий time range и конкретный шаблон индексов (`logs-payments-*` вместо `logs-*`) — самый большой выигрыш почти всегда.
* **Число панелей и кардинальность**: держите дашборд в районе ~20 панелей; в top-N агрегациях используйте поля с контролируемой кардинальностью и ограничивайте размер выборки.
* **Source filtering в Data View** — исключите ненужные поля из выборки документов (классическое средство для широких логов; применяется в настройках Data View).
* **Подсветка и автодополнение**: `doc_table:highlight: false` и `autocomplete:valueSuggestionMethod: terms_enum` снимают фоновую нагрузку.
* **Фоновый режим для долгих запросов**: background search (`data.search.sessions.enabled`) отдаёт долгие запросы в фон — [Поиск, визуализация и управление](./kibana_search_and_visualization.md).
* **Отложенная загрузка**: включите `labs:dashboard:deferBelowFold` для длинных дашбордов (Experimental — проверьте на своей версии).
* **Границы таймаутов**: если запросы штатно упираются в 30 секунд — это либо сигнал на тюнинг запроса (ES), либо согласованное увеличение `elasticsearch.shardTimeout`/`requestTimeout`/`search:timeout` под действительно долгую аналитику.

### Согласованный пример (kibana.yml + Advanced Settings)

```yaml
# kibana.yml — границы ответов Kibana → ES
elasticsearch.requestTimeout: 30000
elasticsearch.shardTimeout: 30000   # 0 — ждать все шарды; помните про maxSockets
```

```jsonc
// Advanced Settings (через UI; значения — дефолты)
// search:timeout = 600000
// doc_table:highlight = false        // если подсветка не нужна
// courier:setRequestPreference = "Session ID"
// labs:dashboard:deferBelowFold = true  // для длинных дашбордов
```

## Troubleshooting

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Дашборд открывается десятки секунд | Много панелей, широкий шаблон/диапазон, top-N по высококардинальному полю | Сузить шаблон и time range, сократить панели, ограничить top values (см. также [Troubleshooting поиска](./kibana_search_and_visualization.md)) |
| Панели отрисовываются частично, без ошибки | Сработал `elasticsearch.shardTimeout` — пришли частичные результаты шард | Ускорить запрос либо увеличить `shardTimeout` согласованно с `requestTimeout` |
| Ошибка таймаута на тяжёлой панели | `elasticsearch.requestTimeout` / `search:timeout` меньше времени агрегации | Тюнинг запроса (ES) либо согласованное увеличение обоих таймаутов |
| Дашборд постоянно тянет ES в фоне | Включён автоинтервал обновления (`timepicker:refreshIntervalDefaults`) | Поставить `pause: true` либо увеличить `value` |
| Автодополнение KQL подвисает на больших данных | `terms_agg` на высококардинальном поле | `autocomplete:valueSuggestionMethod: terms_enum` (учесть ограничение DLS) |
| Discover-панели тормозят на больших документах | Включена подсветка (`doc_table:highlight`) | Отключить подсветку |
| Ни одна настройка не помогает, ES грузится | Узкое место на стороне Elasticsearch | [Search tuning](../Elasticsearch/elasticsearch_search_tuning.md): профилирование, кэши, маппинг |

## Best Practices

* **Профилируйте панель, а не дашборд**: Inspector → конкретный запрос → Dev Tools → `_search/profile`; без этого любые настройки — стрельба вслепую.
* **Сначала данные, потом настройки**: сужение диапазона и шаблона даёт порядки, Advanced Settings — проценты.
* **Одна точка правды по `kibana.yml`-таймаутам** — таблица в [Эксплуатации](./kibana_production_operations.md); меняйте `shardTimeout`/`requestTimeout`/`search:timeout` только вместе.
* **Держите автообновление выключенным** по умолчанию (`pause: true`) и включайте его точечно — на дашбордах оперативного дежурства.
* **Долгую аналитику выносите из интерактива**: async-запросы и ES|QL REST API вместо многоминутных панелей ([Поиск, визуализация и управление](./kibana_search_and_visualization.md)).
* **Не плодите «супердашборды»**: несколько адресных дашбордов диагностируются и тюнятся проще, чем один на все сигналы.
