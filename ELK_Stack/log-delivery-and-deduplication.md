# Логи: семантика доставки, идемпотентность и дедупликация

**Актуально для:** Elastic Stack 9.5.x / 8.19 LTS

## Определения

*   **At-least-once** — конвейер доставляет каждое событие **минимум один раз**: возможны дубли, но не потери. Стандартная семантика Filebeat, буферов и consumer'ов с подтверждением после чтения.
*   **At-most-once** — каждое событие **не более одного раза**: потери возможны, дублей нет. Возникает, когда подтверждение уходит раньше, чем данные гарантированно сохранены.
*   **Exactly-once** — доставка ровно один раз: нет ни потерь, ни дублей. Для логов достигается дорогой синхронизацией всего конвейера и, как правило, **избыточна** ([EFK-пайплайн](Tutorials/fluentbit_kafka_vector_opensearch_pipeline.md)).
*   **Идемпотентная запись** — повторная запись того же события не меняет итоговое состояние хранилища. Для Elasticsearch идемпотентность достигается **детерминированным `_id`**: одинаковое содержимое → один и тот же `_id` → второго документа не появляется.
*   **`_id` (document ID)** — идентификатор документа в индексе. Задаётся явно (создателем запроса/ingest-пайплайном) или генерируется Elasticsearch автоматически (случайный — тогда дубли физически неотличимы).
*   **Fingerprint** — процессор (Elasticsearch ingest, Filebeat/Elastic Agent) и фильтр Logstash, вычисляющий хеш из набора полей документа; используется как детерминированный `_id` или поле `document_id` на стороне шлюза. Хеш считается от конкатенации пар «поле|значение» (`|field1|value1|field2|value2|`); список полей процессор сортирует алфавитно — ключ детерминирован. Дефолты алгоритма различаются: в ingest-процессоре — `SHA-1`, в Filebeat — `sha256` (у Filebeat также опция `encoding`: `hex`/`base32`/`base64`, дефолт `hex`).
*   **PQ (Persistent Queue)** — дисковая очередь Logstash между input и output; **DLQ (Dead Letter Queue)** — очередь событий, которые output не смог отправить ([эксплуатация PQ/DLQ](Logstash/logstash_multiline_aggregate_dlq_pq_ops.md)).
*   **ACK** — подтверждение получения данных от следующего звена (агент → шлюз → Elasticsearch); именно момент ACK определяет, что считать «доставленным» и где возможен повтор.

## Основные концепции

### Гарантии по компонентам стека

| Звено | Семантика по умолчанию | Что это значит на практике |
|---|---|---|
| Filebeat → выход | **At-least-once** | Состояние (registry) подтверждается после отправки; сбой между отправкой и подтверждением → повторное чтение/отправка → **возможны дубли** |
| Буферы агентов/шлюзов (disk buffer, PQ) | **At-least-once** | После рестарта недочитанные чанки пере-дочитываются — это штатное поведение ([Fluent Bit/Vector пайплайн](Tutorials/fluentbit_kafka_vector_opensearch_pipeline.md)) |
| Kafka: consumer | **At-least-once**, пока offset не закоммичен после успешной отправки | Сбой между записью в OpenSearch/ES и коммитом offset → повтор ([там же](Tutorials/fluentbit_kafka_vector_opensearch_pipeline.md)) |
| Logstash → Elasticsearch | Ретраи при ошибках вывода, PQ/DLQ как страховка | Повторная отправка после сбоя ответа → возможен повтор документа; события в DLQ при ручной/фоновой переотправке доставляются заново ([DLQ/PQ](Logstash/logstash_multiline_aggregate_dlq_pq_ops.md)) |
| Elasticsearch | Хранит ровно то, что пришло | Дубли «не считаются» сервером: **два разных `_id` с одинаковым содержимым — это два документа**. Детерминированный `_id` превращает повтор в перезапись или отклонение (см. ниже) |

Общая теория семантику доставки (ретраи, коммиты, брокеры) — в [Kafka: Гарантии доставки](../Kafka/delivery_guarantees.md); здесь — только её проявление в логовом конвейере ELK.

### Модель: at-least-once + идемпотентный приём = «ровно один раз» для логов

Строить сквозной exactly-once конвейер дорого и незачем. Инженерная практика: **оставляем дешёвую at-least-once доставку, а приём в Elasticsearch делаем идемпотентным** — тогда дубли либо не создаются, либо перезаписываются, и итоговое состояние хранилища не зависит от числа повторов. Именно такой подход подразумевается формулировкой «exactly-once для логов обычно избыточна; дедупликация — задача хранилища» ([EFK-пайплайн](Tutorials/fluentbit_kafka_vector_opensearch_pipeline.md)).

### Семантика повторной записи с одинаковым `_id`

Ответственное различение, определяющее, что произойдёт с дублем:

*   **Data stream (типовой случай для логов)** — принимает только `op_type: create`: повтор с тем же `_id` **отклоняется с конфликтом (409), документ не перезаписывается** — семантика *first-write-wins*. Дубль просто не появляется. Повторяющиеся 409 в статусах bulk-элементов — признак сработавшей дедупликации, а не сбоя доставки; убедитесь, что они не затапливают логи шлюза/мониторинг ошибок.
*   **Обычный индекс (alias с write-индексом, не TSDS)** — операция `index` с тем же `_id` **перезаписывает документ** (*last-write-wins*, версия растёт). Повтор не раздувает индекс, но «побеждает» более поздняя версия.
*   **TSDS (`index.mode: time_series`)** — **кастомные `_id` не поддерживаются**, дубликаты data points отклоняются самим движком ([Mapping и индексация](Elasticsearch/elasticsearch_mapping_and_indexing.md)) — дедупликация по `_id` здесь неприменима.
*   Операция `create` (`PUT /<index>/_create/<_id>`) при существующем `_id` возвращает **409** ([Mapping и индексация](Elasticsearch/elasticsearch_mapping_and_indexing.md), [Reindex и обновления](Elasticsearch/elasticsearch_reindex_updates.md)).

### Откуда в логах берутся дубли

1.  **Штатные ретраи at-least-once**: сеть/ES недоступны → агент или шлюз повторил отправку после восстановления.
2.  **Пере-чтение после рестарта**: агент стартует с неподтверждённым состоянием/буфером и дочитывает данные заново.
3.  **Ротация файлов**: устаревшая стратегия **copytruncate** в версиях < 9.0 с native-идентификацией могла **дублировать** события (и терять строки при копировании) — см. [Filebeat, граничные случаи](filebeat_overview.md).
4.  **Перенос состояния (`take_over`)**: захват состояний активных входов не поддерживается и ведёт к дублированию или потере ([Filebeat](filebeat_overview.md)).
5.  **Догоняющие загрузки** за пересекающиеся временные окна (ручной импорт, повторный reindex без фиксированного `_id`).
6.  **Двойной сборщик**: два агента/инстанса настроены читать один и тот же файл/поток.
7.  **Переотправка из DLQ/PQ** после инцидента ([Logstash](Logstash/logstash_multiline_aggregate_dlq_pq_ops.md)).

Важно: **время доставки и `@timestamp` чтения меняются при каждом повторе** — поэтому дубль нельзя отфильтровать по времени; механизм защиты — только детерминированный идентификатор (см. сценарии). Семантика времени в конвейере — в [Логи: временные метки и запоздавшие события](log-timestamps-and-late-events.md).

## Практические сценарии

Предварительные требования: доступ к Elasticsearch с кластерной привилегией `manage_pipeline` (создание ingest-пайплайнов) и правом записи в целевой индекс/data stream; доступ к конфигурации агента/шлюза (Filebeat/Logstash) с возможностью рестарта.

### 1. Детерминированный `_id` через ingest-пайплайн (fingerprint)

```bash
curl -s -u elastic:$PASS -k -X PUT "$ES/_ingest/pipeline/dedup?pretty" -H 'Content-Type: application/json' -d '{
  "processors": [
    {
      "fingerprint": {
        "fields": ["service.name", "host.name", "log.file.path", "log.offset", "message"],
        "target_field": "_id",
        "method": "SHA-256"
      }
    }
  ]
}'
# → {"acknowledged":true}
```

Привязка: `POST <index>/_doc?pipeline=dedup` (ручные запросы), `default_pipeline: dedup` в index template (рекомендуется — работает для всех писателей), либо `?pipeline=dedup` в bulk. Параметры `fingerprint`: `fields` (обязательный), `target_field` (по умолчанию `fingerprint`), `method` (`MD5`/`SHA-1` — умолчание/`SHA-256`/`SHA-512`/`MurmurHash3`), `salt`, `ignore_missing`.

Правила выбора полей — **критически важны**:

*   включайте только **стабильные бизнес-поля**: содержимое события + естественный ключ источника (`host.name`, `log.file.path`+`log.offset`, `trace.id` и т.п.);
*   **не включайте** поля, меняющиеся при каждой доставке: `@timestamp` момента чтения, `agent.ephemeral_id`, `event.ingested` — иначе повтор получит другой хеш, и дедуп не сработает;
*   ставьте fingerprint **первым** процессором, до обработчиков (grok и др.), изменяющих исходные поля.

Поведение при срабатывании: data stream → **отклонение дубля (409, first-write-wins)**; обычный индекс → **перезапись (last-write-wins)**.

Валидация: повторный `POST` того же документа — у обычного индекса растёт `_version` при неизменном `_id` (`GET /<index>/_doc/<_id>`), у data stream — `409` в ответе; сам пайплайн: `GET _ingest/pipeline/dedup` → `{"dedup":{...}}`. Граничный случай: если **все** поля из `fields` отсутствуют в документе, процессор молча завершается, не выставляя `_id` — документ уходит со случайным `_id` и дедуп для него не работает; контроль — аудит (сценарий 3).

### 2. Дедупликация на стороне Filebeat (без правки ES)

```yaml
# filebeat.yml
processors:
  - fingerprint:
      fields: ["service.name", "host.name", "log.file.path", "log.offset", "message"]
      target_field: "@metadata._id"
      method: sha256   # дефолт Filebeat — sha256; поля сортируются алфавитно, хеш — от |field|value| пар
```

Хеш уезжает в служебном поле `@metadata._id` и становится `_id` документа при выводе в Elasticsearch (`@metadata` не индексируется как обычное поле — оно передаётся только для вывода): повторная доставка того же события перезаписывает документ, а не создаёт новый. Кодировка хеша — опция `encoding` (`hex`/`base32`/`base64`, дефолт `hex`). `ignore_missing` по умолчанию `false` — отсутствие любого поля из `fields` даёт ошибку процессора; если поле может отсутствовать, ставьте `ignore_missing: true` (но тогда при отсутствии **всех** полей `_id` не выставится — сценарий 1, граничный случай).

Если событие содержит **естественный ключ** (например, `event.transaction_id` в JSON), хешировать не нужно — используйте ключ напрямую:

```yaml
# вариант 1: настройка входа для JSON-данных
filebeat.inputs:
  - type: filestream
    json.document_id: "event.transaction_id"
# вариант 2: процессор decode_json_fields
processors:
  - decode_json_fields:
      document_id: "event.transaction_id"
      fields: ["message"]
      max_depth: 1
      target: ""
# вариант 3: нет естественного ключа — сгенерировать ES-совместимый ID
processors:
  - add_id: ~   # дефолтный target_field — @metadata._id, type: elasticsearch
```

Если логи идут через Logstash, идентификатор нужно сохранить (иначе `@metadata` не дойдёт до Elasticsearch):

```ruby
output {
  elasticsearch {
    hosts => ["https://es:9200"]
    document_id => "%{[@metadata][_id]}"
    index => "logs-app-%{{yyyy.MM.dd}}"
  }
}
```

Тот же приём — фильтром Logstash целиком (logstash-filter-fingerprint), когда Filebeat не участвует; каноническая форма — хеш в `@metadata`, чтобы не индексировать служебное поле:

```ruby
filter {
  fingerprint {
    source => ["service.name", "host.name", "message"]
    target => "[@metadata][fingerprint]"
    method => "SHA256"
  }
}
output {
  elasticsearch {
    hosts => ["https://es:9200"]
    document_id => "%{[@metadata][fingerprint]}"
    index => "logs-app-%{+yyyy.MM.dd}"
  }
}
```

Эквиваленты в Elastic Agent: процессоры `add_id` и `fingerprint` доступны в advanced-конфигурации интеграции (секция `processors`); для копирования существующего ключа события в `@metadata._id` — процессор `copy_fields`.

### 3. Аудит: есть ли дубли прямо сейчас

```esql
FROM logs-app-*
| STATS total = COUNT(*), uniq = COUNT(DISTINCT message)
| EVAL dup_candidates = total - uniq
```

`dup_candidates > 0` — в выборке есть повторяющиеся сообщения (оценка сверху: полный дубль — подмножество таких случаев). Точнее — считать по вашему естественному ключу (несколько полей сначала свести `EVAL key = CONCAT(host.name, "|", message)`). Запрос выполняется через `POST /_query` — см. [ES|QL](Elasticsearch/esql-query-language.md). Аудит проводите **до** включения дедупликации и повторно **после** — дублирование должно перестать расти.

Дедупликация на стороне запроса (без изменения конвейера — для разовых выборок и дашбордов): в ES|QL — `SORT` + `LIMIT 1 BY <поля>` (оставляет одну строку на комбинацию полей; `DEDUP` — синтаксический сахар для дедупликации по всем столбцам сразу, проверяйте статус команды в вашей версии); в Search API — параметр `collapse` (группировка hits по значению поля, аналог «только первый hit на ключ»).

### 4. Проверка, что дубли не «лечатся» ретраями вхолостую

```bash
# статусы bulk: 409 среди items — сработавшая дедупликация в data stream
curl -s -u elastic:$PASS -k "$ES/_bulk?pretty" -H 'Content-Type: application/json' --data-binary @bulk.ndjson | jq '.items[] | .index.status' | sort | uniq -c
# → например: 971 200 / 29 409
```

Если видите резкий рост **5xx/429** — это реальные ошибки доставки (кластер перегружен), их разбирают отдельно ([Troubleshooting индексации](Elasticsearch/elasticsearch_troubleshooting_indexing.md)); **409** при включённой дедупликации — ожидаемый результат.

## Устранение неполадок

| Симптом | Причина | Решение |
|---|---|---|
| Число документов растёт быстрее, чем события на источнике | Повторная доставка at-least-once без идемпотентного приёма | Включить дедупликацию (сценарий 1 или 2) |
| После рестарта агента/шлюза «шквал» старых событий | Пере-чтение неподтверждённого состояния/буфера | Штатное поведение; убедиться, что включён дедуп (`_id`) |
| Дубли после ротации логов | copytruncate (версии < 9.0) или `take_over` активных входов | Перейти на ротацию через переоткрытие файла, см. [Filebeat](filebeat_overview.md) |
| Дубли после переотправки из DLQ | Ручная/фоновая переотправка без фиксированного `_id` | Дедупликация на приёме; переотправлять с сохранением ключа ([Logstash](Logstash/logstash_multiline_aggregate_dlq_pq_ops.md)) |
| `409` в bulk при дедупликации | Data stream отклонил повтор с тем же `_id` (first-write-wins) | Ожидаемо; приглушить шум логирования шлюза, но **не** отключать дедуп |
| Ошибка отклонения записи: кастомный `_id`/дубликат точки | Документ ушёл в **TSDS** — кастомные `_id` там запрещены | Дедуп по `_id` для метрик TSDS неприменим; чинить на источнике/шлюзе ([Mapping](Elasticsearch/elasticsearch_mapping_and_indexing.md)) |
| После включения fingerprint документы «пропали» из поиска | Хеш считался от нестабильных полей → каждый повтор получает новый `_id` | Пересобрать состав `fields` (сценарий 1, правила выбора полей) |
| Ошибки процессора fingerprint в Filebeat / документы со случайным `_id` | Поле из `fields` отсутствует: при `ignore_missing: false` (дефолт) — ошибка процессора; при отсутствии всех полей — `_id` не выставляется и дедуп молча не работает | `ignore_missing: true` для опциональных полей; аудит (сценарий 3) покажет документы без детерминированного `_id` |
| Дедуп включён, но старые дубли остались | Механизм предотвращает **новые** дубли, историю не чистит | Аудит (сценарий 3); чистка истории — отдельная задача через [Reindex и обновления](Elasticsearch/elasticsearch_reindex_updates.md) |
| `status: 409` в элементах bulk без включённой дедупликации | Явный `create`/`_create` с существующим `_id` (ручные запросы, `op_type`) | Проверить логику записи: `index` для обновления, `create` только для новых ([Reindex и обновления](Elasticsearch/elasticsearch_reindex_updates.md)) |

## Best Practices

*   **Не гонитесь за сквозным exactly-once** — стройте at-least-once + идемпотентный приём в Elasticsearch; для логов это дешевле и достаточно.
*   **Дедуп-ключ — из стабильных полей**, без времени приёма/доставки; ревьюйте состав `fields` как часть релиза пайплайна.
*   **Естественный ключ важнее хеша**: если событие содержит уникальный идентификатор (`event.transaction_id`, `request_id`), используйте `json.document_id`/`decode_json_fields`/`document_id` — дешевле процессора и без риска коллизий хеша; хешируйте, только когда естественного ключа нет.
*   **Fingerprint — первым процессором**, до изменяющих поле обработок (grok/dissect/обогащение).
*   **Помните о first-write-wins в data streams**: дубль отклоняется, «последняя версия» не вытесняет первую. Если логам нужна именно перезапись — это уже не data stream, а alias с write-индексом (обычный индекс, last-write-wins).
*   **409 при дедупликации — не авария**; наоборот, их появление подтверждает, что защита работает. Следите, чтобы они не маскировали настоящие 5xx/429.
*   **Аудит до и после** (сценарий 3): без измерения вы не узнаете, что дубли реально ушли.
*   **Ретраи и DLQ/PQ оставляйте включёнными**: они защищают от потерь; потери дороже дублей, которые теперь сдерживает идемпотентный приём.
*   **Двойной сборщик — тоже источник дублей**: одна роль агента на один источник, проверяйте при масштабировании.
