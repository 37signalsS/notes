# Logstash: Конвейеры, фильтры и производительность

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и предоставляет углубленное описание архитектуры конвейеров (pipelines) в Logstash, использования фильтров, условной логики и методов оптимизации производительности.
>
> **Базовые понятия** ([архитектура Pipeline](./logstash_overview.md#стадии-обработки-данных), [плагины](./logstash_overview.md#стадии-обработки-данных)) — в [общем обзоре Logstash](./logstash_overview.md).

## Определения

* **Событие (Event)** — базовая единица данных в Logstash. Представляет собой JSON-подобную структуру с полями. Основные поля: `@timestamp` (время события), `message` (исходное сообщение), `tags` (метки).
* **Поле `@metadata`** — специальная область в событии для временных данных. Содержимое этого поля **не отправляется** в плагины вывода (`output`). Используется для хранения промежуточных флагов, временных переменных и метаинформации, необходимой только в процессе обработки.
* **ECS (Elastic Common Schema)** — общий стандарт именования полей в Elastic Stack. Следование ECS позволяет корректно коррелировать данные из разных источников (например, логи Logstash и метрики Metricbeat) и использовать стандартные дашборды в Kibana.
* **DLQ (Dead Letter Queue)** — механизм записи событий, которые не были приняты целевой системой (например, из-за конфликта маппинга в Elasticsearch). Позволяет не терять данные и анализировать причины отказов.

## Основные концепции

### Рекомендации по порядку фильтров

Эффективность конвейера напрямую зависит от порядка плагинов:

1. **Нормализация:** Начинайте с быстрых операций `mutate` (переименование, удаление лишних полей).
2. **Первичный разбор:** Используйте `dissect` для данных с фиксированными разделителями. Он значительно быстрее `grok`.
3. **Сложный парсинг:** Используйте `grok` только там, где `dissect` не справляется (неструктурированные строки).
4. **Типизация:** Фильтр `date` должен применяться как можно раньше, чтобы установить правильный `@timestamp`.
5. **Обогащение:** Тяжелые операции (`geoip`, `jdbc_streaming`, `translate`) выполняйте в самом конце, после того как данные отфильтрованы и очищены.
6. **Финальная очистка:** Удаляйте вспомогательные поля и поля `@metadata` (если они не удалились автоматически).

### Условная логика и ветвление

Выражения `if/else` позволяют гибко управлять потоком данных:

```ruby
filter {
  if [log][file][path] =~ /access\.log/ {
    # Обработка только для access-логов
    mutate { add_tag => ["nginx_access"] }
  } else if [log][level] == "ERROR" {
    # Специфическая логика для ошибок
    mutate { add_field => { "[@metadata][alert]" => "true" } }
  } else {
    # Все остальные логи
    drop { } 
  }
}
```

### Обратное давление (Backpressure)

Logstash реализует механизм адаптивного управления потоком. Если стадия `output` не успевает отправлять данные (например, Elasticsearch перегружен), Logstash замедляет работу фильтров, а затем и прием данных в `input`. Это предотвращает переполнение памяти и потерю событий при использовании `Persistent Queues`.

## Практические сценарии

### Настройка ECS-совместимого конвейера

Пример маппинга произвольных данных в стандартные поля ECS:

```ruby
filter {
  grok {
    match => { "message" => "%{IP:client_ip} %{WORD:http_method} %{URIPATH:url_path}" }
  }
  
  mutate {
    # Маппинг в ECS
    rename => { "client_ip" => "[source][ip]" }
    rename => { "http_method" => "[http][request][method]" }
    rename => { "url_path" => "[url][path]" }
    add_field => { "[ecs][version]" => "8.0.0" }
  }
}
```

### Использование Pipeline-to-Pipeline

Разделение конвейеров на "приемники" и "обработчики" повышает надежность и читаемость.

1. **`pipelines.yml`**:
    ```yaml
    - pipeline.id: ingress
      path.config: "/etc/logstash/conf.d/01-ingress.conf"
    - pipeline.id: processing
      path.config: "/etc/logstash/conf.d/02-processing.conf"
    ```

2. **Ingress конвейер (`01-ingress.conf`)**:
    ```ruby
    input { beats { port => 5044 } }
    output { pipeline { send_to => "shared_processing" } }
    ```

3. **Processing конвейер (`02-processing.conf`)**:
    ```ruby
    input { pipeline { address => "shared_processing" } }
    filter { # Тяжелая логика парсинга # }
    output { elasticsearch { ... } }
    ```

## Дополнительная информация

### Мониторинг и отладка

* **Monitoring API**: Logstash предоставляет HTTP API (по умолчанию на порту 9600) для получения метрик производительности:
  `curl -XGET 'localhost:9600/_node/stats/pipelines?pretty'`
* **Dots Codec**: Для быстрой проверки пропускной способности можно использовать кодек `dots` в выводе `stdout`. Каждое событие будет отображаться как точка в консоли.
* **Slow Log**: Включение логирования медленных событий в `logstash.yml`:
    ```yaml
    slowlog.threshold.warn: 2s
    slowlog.threshold.info: 1s
    ```

### Оптимизация производительности

| Параметр | Описание | Рекомендация |
| :--- | :--- | :--- |
| `pipeline.workers` | Количество потоков фильтрации. | Равно количеству ядер CPU. |
| `pipeline.batch.size` | Кол-во событий за одну итерацию. | 125–500 (увеличивайте для роста пропускной способности). |
| `queue.type` | Тип очереди. | `persisted` для надежности в production. |
| `jvm.options` | Память JVM. | 4-8 ГБ обычно достаточно для большинства задач. |
