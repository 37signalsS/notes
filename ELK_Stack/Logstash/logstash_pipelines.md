# Logstash: Конвейеры, фильтры и производительность

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и предоставляет углубленное описание архитектуры конвейеров (pipelines) в Logstash, использования фильтров, условной логики и методов оптимизации производительности.
>
> **Базовые понятия** ([архитектура Pipeline](./logstash_overview.md#архитектура-конвейера-pipeline), [плагины](./logstash_overview.md#основные-концепции)) — в [общем обзоре Logstash](./logstash_overview.md).

## Определения

* **Событие (Event)**: Базовая единица данных в Logstash. JSON-подобная структура с полями. Служебные поля: `@timestamp` (время события), `message` (исходное сообщение), `tags` (метки).
* **Поле `@metadata`**: Специальная область в событии для временных данных. Не отправляется в `output`. Используется для флагов, временных значений, трассировочных ID.
* **DLQ (Dead Letter Queue)**: Внутренняя очередь для событий, которые не удалось отправить через `output` плагин (например, из-за ошибки маппинга в Elasticsearch). Защищает от потери данных.

## Основные концепции

### Рекомендации по порядку фильтров

Порядок фильтров в конвейере критически влияет на производительность:

* Начинайте с быстрых и дешевых операций (`mutate`, `prune`).
* Используйте `dissect` вместо `grok` для данных с фиксированными разделителями (быстрее в разы).
* Приводите временные метки фильтром `date` как можно раньше.
* Тяжелые операции (сложный `grok`, `geoip`) выполняйте после максимальной фильтрации и очистки.
* Удаляйте ненужные поля перед отправкой в `output`.

### Условная логика

Выражения `if/else` позволяют создавать ветвления в обработке в зависимости от содержимого события.

```ruby
filter {
  if "nginx" in [tags] {
    grok { match => { "message" => "%{NGINXACCESS}" } }
  } else if [kubernetes][container][name] =~ /auth/ {
    json { source => "message" }
  } else {
    # Отбросить все, что не подошло
    drop { }
  }

  mutate {
    # Использовать значение из метаданных
    add_field => { "ingest_id" => "%{@metadata[trace_id]}" }
  }
}
```

## Практические сценарии

### Пример конфигурации конвейера

Типичный конвейер для приема, разбора и отправки логов.

```ruby
input {
  beats { port => 5044 }
  tcp { port => 5000 codec => json }
}

filter {
  # 1. Быстрые мутации и добавление тегов
  mutate {
    add_tag => ["raw"]
    rename => { "host" => "[host][name]" }
  }

  # 2. Разбор неструктурированных логов (grok - медленный)
  grok {
    match => { "message" => "%{COMBINEDAPACHELOG}" }
    tag_on_failure => ["_grok_fail"]
  }

  # 3. Быстрый разбор по разделителям (dissect - быстрый)
  dissect {
    mapping => { "message" => "%{ts} %{level} %{msg}" }
  }

  # 4. Приведение временной метки
  date {
    match => ["ts", "ISO8601", "dd/MMM/yyyy:HH:mm:ss Z"]
    timezone => "UTC"
  }

  # 5. Обогащение данных (geoip - медленный)
  geoip {
    source => "[clientip]"
    target => "[geo]"
  }

  # 6. Очистка перед отправкой
  mutate { remove_field => ["message", "agent", "beat"] }
}

output {
  elasticsearch {
    hosts => ["http://es:9200"]
    index => "logs-%{+yyyy.MM.dd}"
  }
  # Для отладки
  stdout { codec => rubydebug }
}
```

### Множественные конвейеры (Pipeline-to-Pipeline)

Для разделения логики (например, один конвейер для приема данных, другой для нормализации) используются множественные конвейеры, определенные в `pipelines.yml`. Связь между ними настраивается через `input` и `output` плагины `pipeline`. Такой подход улучшает читаемость, позволяет переиспользовать конвейеры обработки и изолировать потоки данных.

1. **`pipelines.yml`**:

    ```yaml
    - pipeline.id: inputs-pipeline
      path.config: "/etc/logstash/conf.d/10-inputs.conf"
    - pipeline.id: normalization-pipeline
      path.config: "/etc/logstash/conf.d/20-normalize.conf"
    ```

2. **`10-inputs.conf` (отправка в другой конвейер)**:

    ```ruby
    input { beats { port => 5044 } }
    output {
      pipeline { send_to => [normalize_queue] }
    }
    ```

3. **`20-normalize.conf` (прием из другого конвейера)**:

    ```ruby
    input {
      pipeline { address => normalize_queue }
    }
    filter {
      # ... логика нормализации ...
    }
    output { elasticsearch { ... } }
    ```

## Дополнительная информация

### Производительность и надёжность

* **Воркеры и батчи (`pipeline.workers`, `pipeline.batch.size`)**:
  * pipeline.workers: Число потоков для стадии filter. Рекомендуется устанавливать равным числу ядер CPU (центральный процессор).
  * `pipeline.batch.size`: Размер пакета событий. Увеличение значения повышает пропускную способность (throughput), но ценой увеличения задержки (latency).
* **Очереди (`queue.type`)**:
  * **In-memory (в памяти)**: Быстро, но данные теряются при перезапуске Logstash.
  * **Persisted (персистентная)**: Данные сохраняются на диск, что защищает от потерь при сбоях и перезапусках. Рекомендуется для production.

    ```yaml
    # logstash.yml
    queue.type: persisted
    queue.max_bytes: 4gb
    dead_letter_queue.enable: true
    ```

* **Dead Letter Queue (DLQ)**: Включайте DLQ для сохранения событий, которые не были приняты `output`-плагином. Это позволяет анализировать и повторно обрабатывать проблемные данные.

### Таблица часто используемых фильтров

| Фильтр | Задача |
| :--- | :--- |
| **grok** | Мощный разбор неструктурированных строк с помощью паттернов. |
| **dissect** | Быстрый разбор строк по фиксированным разделителям. |
| **json** | Декодирование JSON-строки в поля события. |
| **kv** | Разбор пар `key=value` из строки. |
| **date** | Парсинг текстовой метки времени и установка ее в поле `@timestamp`. |
| **geoip** | Обогащение данных геолокацией на основе IP-адреса. |
| **mutate** | Базовые операции: переименование, удаление, добавление полей, конвертация типов. |
| **drop** | Полное удаление (отбрасывание) события. |
| **prune** | Удаление полей из события на основе списков разрешенных/запрещенных. |
| **anonymize** | Маскировка или хэширование чувствительных данных (ПДн — персональные данные, email, IP). |
