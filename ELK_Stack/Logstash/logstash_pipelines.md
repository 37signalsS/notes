# Logstash: Конвейеры, фильтры и производительность

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и предоставляет углубленное описание архитектуры конвейеров (pipelines), использования фильтров, условной логики и методов оптимизации производительности в версиях 8.x и 9.x.
>
> **Базовые понятия** ([архитектура Pipeline](./logstash_overview.md#стадии-обработки-данных), [плагины](./logstash_overview.md#стадии-обработки-данных)) — в [общем обзоре Logstash](./logstash_overview.md).

## Определения

* **Событие (Event)** — базовая единица данных, представляющая собой JSON-подобную структуру с обязательными полями `@timestamp` (время события), `message` (исходный текст) и `@metadata`.
* **Поле `@metadata`** — служебная область для временных данных. Содержимое этого поля **не отправляется** в плагины вывода (`output`), что позволяет передавать флаги и переменные между фильтрами без засорения финального индекса.
* **Aggregate Filter** — плагин для объединения нескольких событий в одно на основе общего идентификатора (например, сборка логов многострочного запроса или расчет времени выполнения задачи).
* **Dead Letter Queue (DLQ)** — очередь событий, которые не удалось записать в целевую систему. Позволяет повторно обработать данные после исправления маппинга или сетевых проблем.
* **Persistent Queue (PQ)** — дисковый буфер, обеспечивающий сохранность данных при перезагрузке узла и реализующий механизм адаптивного управления потоком (Backpressure).

## Основные концепции

### Рекомендации по порядку фильтров

Эффективность конвейера в 2026 году определяется правилом "Dissect first, Grok last":

1. **Нормализация (mutate):** Начинайте с переименования полей и удаления лишних данных.
2. **Первичный разбор (dissect):** Используйте для данных с фиксированными разделителями. Это в 5 раз быстрее `grok`.
3. **Сложный парсинг (grok):** Применяйте только для неструктурированных остатков строк.
4. **Типизация и время (date):** Применяйте как можно раньше для установки корректного `@timestamp`, особенно при обработке исторических данных.
5. **Обогащение (geoip, elastic_integration):** В версиях 8.19+ используйте `elastic_integration` для вызова Ingest Pipelines Elasticsearch, чтобы перенести тяжелую логику (User-Agent, GeoIP) на сторону кластера.
6. **Агрегация (aggregate):** Выполняйте в самом конце, когда все данные уже распарсены и типизированы.

### Работа с Aggregate Filter

Плагин `aggregate` является однопоточным по своей природе, так как требует соблюдения порядка событий.
- **Ограничение:** Для корректной работы конвейер **обязан** иметь `pipeline.workers: 1` и `pipeline.ordered: true`.
- **Изоляция:** Рекомендуется выносить логику агрегации в отдельный изолированный конвейер через `pipeline-to-pipeline`, чтобы не замедлять прием данных в многопоточных конвейерах.
- **Очистка памяти:** Всегда используйте `timeout` или `inactivity_timeout` для удаления старых карт агрегации из памяти.

### Процессинг на Ruby

Фильтр `ruby` позволяет выполнять произвольный код. 
- **Thread Safety:** Код в секции `code` должен быть потокобезопасным, если используется более одного воркера.
- **Производительность:** Избегайте использования Ruby для простых операций, которые можно выполнить через `mutate`.
- **Исключения:** Оборачивайте сложную логику в `begin/rescue`, чтобы ошибка в коде не привела к остановке всего конвейера.

## Практические сценарии

### Использование Pipeline-to-Pipeline с изоляцией агрегации

Сценарий разделения: многопоточный прием (Beats) → однопоточная агрегация → многопоточный вывод (Elasticsearch).

**`pipelines.yml`**:
```yaml
- pipeline.id: main-ingress
  pipeline.workers: 4
  path.config: "/etc/logstash/conf.d/01-ingress.conf"
- pipeline.id: aggregation-logic
  pipeline.workers: 1
  pipeline.ordered: true
  path.config: "/etc/logstash/conf.d/02-aggregate.conf"
```

**Конвейер агрегации (`02-aggregate.conf`)**:
```ruby
input { pipeline { address => "aggregate_stream" } }

filter {
  aggregate {
    task_id => "%{task_identifier}"
    code => "map['total_size'] ||= 0; map['total_size'] += event.get('bytes')"
    push_map_as_event_on_timeout => true
    timeout => 300 # 5 минут
  }
}

output { 
  elasticsearch { 
    hosts => ["${ES_URL}"]
    index => "aggregated-metrics"
  } 
}
```

### Пример оптимизированного парсинга (Dissect + Grok)

```ruby
filter {
  # Быстрый разбор заголовка лога
  dissect {
    mapping => { "message" => "[%{timestamp}] %{level} %{service}: %{rest_msg}" }
  }

  # Сложный разбор только остатка сообщения
  if [rest_msg] =~ /failed/ {
    grok {
      match => { "rest_msg" => "Reason: %{GREEDYDATA:error_reason}" }
    }
  }
}
```

## Дополнительная информация

### Мониторинг производительности

В версиях 9.x добавлена расширенная метрика `worker_utilization`.
- **Проверка утилизации воркеров**:
  `curl -XGET 'localhost:9600/_node/stats/pipelines?pretty' | grep worker_utilization`
- **Анализ Backpressure**: Если `queue_size` в Persistent Queue растет, а `worker_utilization` близок к 100%, необходимо увеличить количество воркеров или оптимизировать фильтры.

### Оптимизация и тюнинг (Logstash 9.x)

| Параметр | Рекомендуемое значение | Описание |
| :--- | :--- | :--- |
| `pipeline.buffer.type` | `heap` (по умолчанию в 9.x) | Упрощает управление памятью. Для старых систем можно вернуть `direct`. |
| `pipeline.batch.size` | `250 – 500` | Оптимально для сбалансированной пропускной способности и задержки. |
| `jvm.options` | `4GB – 8GB` | "Золотой стандарт" для Heap. Не рекомендуется выделять более 31 ГБ. |
| `pipeline.ordered` | `true` (для агрегации) | Гарантирует порядок событий внутри батча. Сильно снижает скорость. |
| `dead_letter_queue.enable` | `true` | Обязательно для production-сред для предотвращения потери данных. |

### Управление Dead Letter Queue

События из DLQ можно перечитать с помощью плагина ввода `dead_letter_queue`:
```ruby
input {
  dead_letter_queue {
    path => "/var/lib/logstash/dead_letter_queue"
    commit_offsets => true
    pipeline_id => "main-ingress"
  }
}
```
Это позволяет исправить ошибки в фильтрах и запустить повторную обработку только проблемных данных.
