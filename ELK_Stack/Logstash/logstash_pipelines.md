# Logstash: Конвейеры, фильтры и производительность

**Актуально для:** Logstash 8.19 (LTS) / 9.5.x

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и предоставляет углубленное описание архитектуры конвейеров (pipelines), использования фильтров, условной логики и методов оптимизации производительности в версиях 8.x и 9.x.
>
> **Базовые понятия** ([архитектура Pipeline](./logstash_overview.md#стадии-обработки-данных), [плагины](./logstash_overview.md#стадии-обработки-данных)) — в [общем обзоре Logstash](./logstash_overview.md).

## Определения

* **Событие (Event)** — базовая единица данных, представляющая собой JSON-подобную структуру с обязательными полями `@timestamp` (время события), `message` (исходный текст) и `@metadata`.
* **Поле `@metadata`** — служебная область для временных данных. Содержимое этого поля **не отправляется** в плагины вывода (`output`), что позволяет передавать флаги и переменные между фильтрами без засорения финального индекса.
* **Aggregate Filter** — плагин для объединения нескольких событий в одно на основе общего идентификатора (например, сборка логов многострочного запроса или расчет времени выполнения задачи).
* **Dead Letter Queue (DLQ)** — очередь событий, которые не удалось записать в целевую систему. Позволяет повторно обработать данные после исправления маппинга или сетевых проблем.
* **Persistent Queue (PQ)** — дисковый буфер, обеспечивающий сохранность данных при перезагрузке узла и реализующий механизм адаптивного управления потоком (Backpressure).
* **Flow-метрики** — производные показатели Monitoring API (`worker_utilization`, `queue_backpressure`, `*_throughput`), рассчитываемые как скорость изменения базовых счетчиков относительно времени. Показывают не «сколько событий обработано», а «как система справляется прямо сейчас» (окна `current`, `last_1_minute`, `last_5_minutes`, `last_15_minutes`, `lifetime`).
* **Inflight Count** — число событий, одновременно находящихся «в полете» внутри конвейера: произведение `pipeline.workers × pipeline.batch.size`. Определяет требования к heap: именно столько событий может быть в памяти фильтров единовременно.
* **Pipeline-to-Pipeline (P2P)** — встроенная маршрутизация между конвейерами одного узла: output-плагин `pipeline { send_to => [...] }` передает события во вход `pipeline { address => "..." }` другого конвейера. Используется для разделения быстрого приема и медленной обработки.

## Основные концепции

### Рекомендации по порядку фильтров

Эффективность конвейера определяется правилом "Dissect first, Grok last":

1. **Нормализация (mutate):** Начинайте с переименования полей и удаления лишних данных.
2. **Первичный разбор (dissect):** Используйте для данных с фиксированными разделителями. Значительно быстрее `grok` (один проход по разделителям, без регулярных выражений; точный выигрыш зависит от шаблона и данных).
3. **Сложный парсинг (grok):** Применяйте только для неструктурированных остатков строк.
4. **Типизация и время (date):** Применяйте как можно раньше для установки корректного `@timestamp`, особенно при обработке исторических данных.
5. **Обогащение (geoip, elastic_integration):** В версиях 8.19+ используйте `elastic_integration` для вызова Ingest Pipelines Elasticsearch, чтобы перенести тяжелую логику (User-Agent, GeoIP) на сторону кластера.
6. **Агрегация (aggregate):** Выполняйте в самом конце, когда все данные уже распарсены и типизированы.

Почему порядок важен: `dissect` разбивает строку по фиксированным разделителям за один проход, тогда как `grok` исполняет регулярные выражения поверх движка Oniguruma — при неудачном шаблоне происходит перебор альтернатив (backtracking), стоимость которого растет нелинейно от длины строки. Каждый фильтр, отбросивший лишнее до `grok`, сокращает объем текста, который придется разбирать регулярками. Кроме того, ранняя фильтрация мусора (`if [level] == "DEBUG" { drop {} }`) экономит ресурсы всех последующих стадий.

### Модель исполнения: воркеры, батчи и порядок событий

Понимание этой модели обязательно перед любым тюнингом:

1. **Воркеры (`pipeline.workers`).** Потоки, параллельно вычитывающие события из очереди конвейера. По умолчанию равно числу ядер CPU. Для IO-bound плагинов (запись в Elasticsearch, HTTP-обогащение) допустимо значение выше числа ядер — потоки много времени ждут сеть; для CPU-bound (grok, mutate) рост сверх ядер дает деградацию из-за переключений контекста.
2. **Батчи (`pipeline.batch.size`, по умолчанию 125).** Воркер вычитывает до N событий из очереди за одну итерацию и прогоняет весь батч через filter → output. Крупные батчи эффективнее для выходных плагинов (Elasticsearch собирает bulk-запрос из целого батча), но увеличивают потребление памяти.
3. **Задержка батча (`pipeline.batch.delay`, мс, по умолчанию 50).** Максимум времени ожидания добора событий до полного батча. Верхняя оценка добавляемой задержки: `batch.delay × batch.size`.
4. **Упорядоченность (`pipeline.ordered`).** Управляет гарантиями порядка внутри воркера: `auto` (по умолчанию) включает строгий порядок автоматически при одном воркере и отключает его при нескольких; `true` — принудительно (Logstash откажется стартовать, если `pipeline.workers > 1`); `false` — порядок не гарантируется. При `workers > 1` глобальный порядок соблюсти невозможно в принципе.
5. **Подтверждение (ACK).** Событие считается обработанным только после успешного вывода выходным плагином; при включенной PQ подтверждение возвращается очереди после записи на диск чекпоинта — так обеспечивается at-least-once семантика.

С 9.2 (technical preview) доступен сбор метрик реальных размеров батчей через `pipeline.batch.metrics.sampling_mode`: `disabled`, `minimal` (по умолчанию — подмножество батчей) или `full` (каждый батч). Метрики измеряют число событий и объем в байтах фактических батчей и подсказывают, оправдан ли рост `pipeline.batch.size` (см. раздел тюнинга). Учтите: включение сбора увеличивает потребление heap каждым конвейером.

### Работа с Aggregate Filter

Плагин `aggregate` не потокобезопасен для одного `task_id`: документация требует устанавливать одного воркера (`-w 1` / `pipeline.workers: 1`), иначе события задачи могут обработаться вне последовательности, и результат будет некорректным.
- **Ограничение:** Для корректной работы конвейер должен иметь `pipeline.workers: 1` и `pipeline.ordered: true` (со значением `ordered: true` при `workers > 1` Logstash не стартует — см. модель исполнения выше).
- **Изоляция:** Рекомендуется выносить логику агрегации в отдельный изолированный конвейер через `pipeline-to-pipeline`, чтобы не замедлять прием данных в многопоточных конвейерах.
- **Очистка памяти:** Всегда используйте `timeout` или `inactivity_timeout` для удаления старых карт агрегации из памяти.

Ключевые опции плагина:

| Опция | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `task_id` | обязателен | Sprintf-выражение общего ключа задачи, например `%{transaction_id}` |
| `code` | обязательна | Ruby-код обработки; доступны `event` (текущее событие), `map` (состояние задачи), `map_meta` (метаданные карты: таймауты, timestamps) и `new_event_block.call(event)` для немедленной эмиссии новых событий |
| `timeout` | `1800` | Секунды с первого события задачи, после которых карта считается устаревшей и удаляется |
| `inactivity_timeout` | — | Сброс карты после N секунд без новых событий (должен быть меньше `timeout`) |
| `push_map_as_event_on_timeout` | `false` | Эмитировать накопленную карту отдельным событием при таймауте |
| `push_previous_map_as_event` | `false` | Выдавать карту предыдущей задачи при появлении нового `task_id` (корректно только когда задачи идут строго последовательно: все события task1, затем все task2) |
| `end_of_task` | `false` | Удалить карту после завершающего события задачи |
| `map_action` | `create_or_update` | Разрешить создание (`create`), только обновление (`update`) или оба режима |
| `timeout_code` | — | Ruby-код для события, генерируемого при таймауте (код выполняется на уже заполненной карте) |
| `timeout_tags` | `[]` | Теги, добавляемые к событию таймаута (для маршрутизации) |
| `timeout_task_id_field` | — | Поле в событии таймаута, куда записать `task_id` (корреляция таймаутов) |
| `timeout_timestamp_field` | — | Вычислять таймаут по временной метке события, а не по системному времени — для исторических логов (должна быть задана на первом aggregate-фильтре) |
| `map_count_warning_threshold` | `5000` | Порог числа карт в памяти для предупреждения в лог (повторяется каждые 20% от порога; `0` отключает предупреждения) |
| `aggregate_maps_path` | — | Файл персистенции карт между рестартами; допустим только один такой фильтр на конвейер (карты разделяются на уровне конвейера) |

Все timeout-опции (`timeout`, `inactivity_timeout`, `timeout_code`, `push_map_as_event_on_timeout`, `push_previous_map_as_event`, `timeout_timestamp_field`, `timeout_task_id_field`, `timeout_tags`) должны быть определены только в одном aggregate-фильтре на шаблон `task_id` в конвейере — иначе Logstash выдаст ошибку конфигурации при старте.

Нюансы: без явного `timeout` всё равно действует дефолтный лимит 1800 секунд с первого события задачи — карты не живут вечно, но для задач с непрерывным потоком событий карта удерживается до истечения `timeout`, поэтому явные таймауты рекомендуются (типичная причина OOM — забытые таймауты при долгоживущих задачах). Если задачи приходят строго последовательно, связка `push_previous_map_as_event` + новый `task_id` эмитирует результат быстрее, чем ожидание таймаута. Если в `code` возникает исключение, ошибка логируется, а событие получает тег `_aggregateexception` — фильтруйте его для диагностики.

### Процессинг на Ruby

Фильтр `ruby` позволяет выполнять произвольный код. 
- **Thread Safety:** Код в секции `code` должен быть потокобезопасным, если используется более одного воркера.
- **Производительность:** Избегайте использования Ruby для простых операций, которые можно выполнить через `mutate`.
- **Исключения:** Оборачивайте сложную логику в `begin/rescue`, чтобы ошибка в коде не привела к остановке всего конвейера.

Дополнительные правила: не вызывайте `event.to_hash` ради доступа к одному-двум полям — он копирует все событие в Ruby Hash; используйте `event.get("field")` / `event.set("field", value)` и `event.cancel` для удаления события из потока. Инициализируйте неизменяемые структуры (словари, скомпилированные шаблоны) вне блока `code`, в `init`-блоке фильтра, чтобы они создавались один раз на воркер, а не на каждое событие.

### Часто используемые фильтры: date, translate, split, clone, throttle, fingerprint

Эти плагины закрывают типовые задачи на стыке стадий: типизация времени, обогащение по словарю, разбиение и дублирование событий, ограничение частоты и генерация идентификаторов. Grok/mutate/aggregate разобраны в разделах выше; полный обзор входов и выходов — в заметке [Входы, выходы и маршрутизация](./logstash_inputs_outputs.md).

**`date`** — устанавливает `@timestamp` из поля события. Без него событие получает время прихода в Logstash, что недопустимо для исторических данных и логов с задержкой доставки:

```ruby
filter {
  date {
    match => ["logdate", "MMM dd HH:mm:ss", "ISO8601"]  # поле + один или несколько форматов
    target => "@timestamp"      # по умолчанию
    timezone => "Europe/Moscow" # если в данных нет таймзоны
    # precision => "ns"         # наносекунды (переключает парсинг на java.time)
  }
}
```

Литералы форматов: `ISO8601`, `UNIX` (секунды, float/int), `UNIX_MS`, `TAI64N`. Неудача парсинга помечает событие тегом `_dateparsefailure` (маршрутизируйте такие события на разбор). Внимание: по умолчанию парсинг идет через joda-time с точностью до миллисекунд; `precision => "ns"` меняет движок на `java.time` — синтаксис форматов похож, но не идентичен (например, таймзона-ID `VV` поддерживается только в `java.time`).

**`translate`** — обогащение по словарю (замена значений без регулярных выражений):

```ruby
filter {
  translate {
    source => "[http][response][status_code]"
    target => "[http][response][status_description]"
    dictionary => { "200" => "OK", "500" => "Server Error" }
    fallback => "Unknown"
  }
}
```

`source` обязателен; словарь — либо хэш `dictionary`, либо файл `dictionary_path` (YAML/JSON/CSV, одновременно нельзя); `fallback` подставляется при отсутствии совпадения. Файл перечитывается по `refresh_interval` (300 с по умолчанию; значение ≤ 300 дополнительно проверяет mtime), при этом `refresh_behaviour` определяет, сливать новые записи в старый словарь (`merge`) или заменять его целиком (`replace`). Словари до 100 000 пар проверены разработчиками; при очень больших YAML имеет смысл `yaml_load_strategy => "streaming"` (меньше памяти). В ECS-режиме `target` по умолчанию совпадает с `source` — получается замена на месте. Обратите внимание: опции `field` и `destination` устарели с 3.3.0 (заменены на `source`/`target`).

**`split`** — разбиение одного события на несколько по разделителю (строки массива, элементы JSON или многострочный текст):

```ruby
filter {
  split {
    field => "message"      # по умолчанию
    terminator => "\n"      # по умолчанию; для JSON-массива не нужен
    target => "line"        # куда класть часть (по умолчанию — в само поле)
  }
}
```

Каждая часть — полная копия события с измененным полем. Фильтр расширяет батч: с 9.4.1 разросшиеся батчи автоматически дробятся обратно до `pipeline.batch.size` перед передачей в output.

**`clone`** — дублирование события для разведения потоков:

```ruby
filter {
  clone {
    clones => ["audit_copy"]   # обязательный массив меток
  }
}
```

Копия получает метку в поле `type` (ECS отключен) или в массив `tags` (ECS включен) и продолжает путь через конвейер с этого места — дальше условиями по метке событие можно отправить в разные выходы. Оригинал не изменяется.

**`throttle`** — ограничение числа событий по ключу за период (защита от шторма алертов):

```ruby
filter {
  throttle {
    key => "%{host}"         # обязательный ключ группировки (поддерживает %{field})
    before_count => 3        # до 3-го события — «молчим» (throttled)
    after_count => 5         # после 5-го — снова «молчим»
    period => 3600           # окно подсчета, с (по умолчанию 60)
    max_age => 7200          # время жизни таймслота, с (≥ 2×period)
    add_tag => "throttled"
  }
  if "throttled" in [tags] {
    drop { }                 # события-сверхнормативы отбрасываются
  }
}
```

События, прошедшие через фильтр, помечаются (сucceed events — с `add_tag`), отсеченные считаются «throttled»; типичная схема — tag + `drop` либо пропуск мимо алертинга. `max_counters` (100 000) ограничивает память: не используйте UUID в качестве `key`.

**`fingerprint`** — детерминированный хэш полей, в первую очередь для стабильного `document_id` (повторная доставка обновит документ вместо создания дубликата):

```ruby
filter {
  fingerprint {
    source => ["message", "[host][name]"]
    method => "SHA1"         # обязательный; также SHA256/SHA384/SHA512, MD5,
                             # MURMUR3, MURMUR3_128, IPV4_NETWORK, UUID, PUNCTUATION
    target => "fingerprint"  # по умолчанию; в ECS — [event][hash]
    concatenate_sources => true  # хэшировать конкатенацию всех source, а не последнего
  }
}
output {
  elasticsearch {
    document_id => "%{fingerprint}"
  }
}
```

`key` задает HMAC-ключ (для криптографических методов) или длину префикса подсети (`IPV4_NETWORK`, например `16` превратит `1.2.3.4` в `1.2.0.0`); `base64encode => true` включает base64 вместо hex; `method => "UUID"` дает случайный UUID (для детерминированного id не подходит — используйте хэш-метод). В ECS-режиме результат пишется в `[event][hash]`.

## Практические сценарии

### Использование Pipeline-to-Pipeline с изоляцией агрегации

Сценарий разделения: многопоточный прием (Beats) → однопоточная агрегация → многопоточный вывод (Elasticsearch).

**`pipelines.yml`**:
```yaml
- pipeline.id: main-ingress
  pipeline.workers: 4
  path.config: "/etc/logstash/conf.d/01-ingress.conf"
- pipeline.id: aggregation-logic
  pipeline.workers: 1
  pipeline.ordered: true
  path.config: "/etc/logstash/conf.d/02-aggregate.conf"
```

**Приемный конвейер (`01-ingress.conf`)** — принимает данные и пересылает их по адресу `aggregate_stream`:

```ruby
input {
  beats {
    port => 5044
    id => "beats_ingress"
  }
}

filter {
  # легкая нормализация допустима здесь — она выполняется 4 воркерами параллельно
  mutate {
    lowercase => ["service"]
  }
}

output {
  pipeline {
    send_to => ["aggregate_stream"]
  }
}
```

**Конвейер агрегации (`02-aggregate.conf`)**:
```ruby
input { pipeline { address => "aggregate_stream" } }

filter {
  aggregate {
    task_id => "%{task_identifier}"
    code => "map['total_size'] ||= 0; map['total_size'] += event.get('bytes')"
    push_map_as_event_on_timeout => true
    timeout => 300 # 5 минут
  }
}

output { 
  elasticsearch { 
    hosts => ["${ES_URL}"]
    index => "aggregated-metrics"
  } 
}
```

Механика: `address` — виртуальный адрес внутри процесса (входной плагин `pipeline` слушает его), `send_to` передает событие по этому адресу; конвейеры независимы — у каждого своя очередь, свои воркеры и свои настройки PQ. Событие при передаче **полностью копируется** на heap для каждого получателя: модификации в конвейере-получателе не влияют на событие отправителя, но P2P увеличивает потребление памяти. Выходной плагин `pipeline` **блокируется**, если получатель заблокирован или недоступен (at-least-once по умолчанию, `ensure_delivery => true`); с `ensure_delivery => false` событие отбрасывается, когда получатель в фазе старта/перезагрузки (но не когда заблокированы его плагины). При `send_to` на несколько адресов заполнение PQ любого получателя останавливает все выходы на этом адресе. Ошибка в имени адреса обнаруживается на этапе проверки конфигурации: несуществующий адрес даст `[ERROR]` при старте конвейера-отправителя.

### Пример оптимизированного парсинга (Dissect + Grok)

```ruby
filter {
  # Быстрый разбор заголовка лога
  dissect {
    mapping => { "message" => "[%{timestamp}] %{level} %{service}: %{rest_msg}" }
  }

  # Сложный разбор только остатка сообщения
  if [rest_msg] =~ /failed/ {
    grok {
      match => { "rest_msg" => "Reason: %{GREEDYDATA:error_reason}" }
    }
  }
}
```

Валидация примера на тестовой строке без поднятия инфраструктуры:

```bash
echo '[2026-08-23T10:00:00] ERROR payments: Reason: connection failed after 30s' | \
bin/logstash -e '
input { stdin{} }
filter {
  dissect { mapping => { "message" => "[%{timestamp}] %{level} %{service}: %{rest_msg}" } }
  if [rest_msg] =~ /failed/ {
    grok { match => { "rest_msg" => "Reason: %{GREEDYDATA:error_reason}" } }
  }
}
output { stdout { codec => rubydebug } }
'
# → "timestamp" => "2026-08-23T10:00:00"
#   "level" => "error"... "service" => "payments"
#   "rest_msg" => "Reason: connection failed after 30s"
#   "error_reason" => "connection failed after 30s"
```

### Диагностика узкого места через Flow Metrics

Пошаговая методика определения причины отставания конвейера (Logstash 8.x/9.x):

**Шаг 1. Сохраните метрики проблемного конвейера** (здесь и далее ID `main` замените на свой из `pipelines.yml`):

```bash
curl -s 'localhost:9600/_node/stats/pipelines/main' > /tmp/pipeline-stats.json
jq '.pipelines.main | {events, flow}' /tmp/pipeline-stats.json
# → {"events":{"in":10526691,"filtered":10525882,"out":10525882,...},
#    "flow":{"worker_utilization":{"current":93.09,"lifetime":92.18},...}}
```

**Шаг 2. Найдите самый дорогой плагин** — сравните `worker_millis_per_event` по плагинам:

```bash
jq -r '.pipelines.main.plugins.filters[], .pipelines.main.plugins.outputs[] |
       [.name, .flow.worker_millis_per_event.current] | @tsv' /tmp/pipeline-stats.json
# → dissect        0.003
# → geoip          1.276      ← подозреваемый
# → elasticsearch  0.411
```

**Шаг 3. Интерпретируйте комбинацию показателей** (официальная методика Elastic):

| Наблюдение | Диагноз | Действие |
| :--- | :--- | :--- |
| `worker_utilization` ≈ 100%, `queue_backpressure` > 0 | Конвейер насыщен (saturated): воркеров не хватает либо фильтры тяжелые | Добавить воркеров (CPU есть в запасе) или оптимизировать дорогой плагин из шага 2 |
| `worker_utilization` ≈ 100%, CPU узла исчерпан | Ресурсное ограничение CPU-bound фильтров | Масштабировать горизонтально (второй узел) или вынести обогащение в `elastic_integration` |
| `worker_utilization` ≈ 0% | Конвейер голодает (starved): input не поставляет данные | Уменьшить `pipeline.workers` для экономии памяти/CPU; проверить источник |
| `queue_persisted_growth_events` стабильно > 0 (с PQ) | Очередь поглощает растущий лаг — выходной этап не успевает | Проверить здоровье Elasticsearch; рост должен стремиться к нулю/минусу |
| Батчи постоянно полные (P50/P90 ≈ `batch.size`) при низком backpressure | Здоровый конвейер с запасом | Можно осторожно увеличить `pipeline.batch.size` |

**Шаг 4. Проверьте результат изменения** — повторите замер через 5–15 минут и сравните окна `last_15_minutes` с прежними значениями `lifetime`.

## Дополнительная информация

### Мониторинг производительности

Ключевой инструмент диагностики — flow-метрики Node Stats API (порт 9600), рассчитываемые по окнам `current`, `last_1_minute`, `last_5_minutes`, `last_15_minutes` и `lifetime`.

- **Проверка утилизации воркеров**:
  `curl -XGET 'localhost:9600/_node/stats/pipelines?pretty' | grep worker_utilization`
- **Анализ Backpressure**: Если `queue_size` в Persistent Queue растет, а `worker_utilization` близок к 100%, необходимо увеличить количество воркеров или оптимизировать фильтры.

Основные flow-метрики конвейера:

| Метрика | Смысл | Норма |
| :--- | :--- | :--- |
| `worker_utilization` | % времени, который воркеры заняты обработкой | Заметно ниже 100 в пиках |
| `worker_concurrency` | Среднее число занятых воркеров | Ниже `pipeline.workers` |
| `queue_backpressure` | Безразмерная доля времени, которую inputs простаивали, упираясь в очередь | Близко к 0; нельзя сравнивать разные конвейеры между собой |
| `input/filter/output_throughput` | Скорость прохождения событий (событий/с) по стадиям | Стадии должны совпадать; разрыв = накопление лага |
| `queue_persisted_growth_bytes/events` | Скорость роста/сокращения PQ (только при `queue.type: persisted`) | Тренд к нулю или отрицательный |

Метрики доступны и на уровне отдельных плагинов (`plugins.filters[].flow.worker_utilization`, `worker_millis_per_event`) — это позволяет точно указать, какой фильтр съедает емкость воркеров, без профилирования вслепую. С 9.4 в `GET /_node/stats` доступны histogram-метрики размеров батчей (распределение по числу событий и байтам за lifetime и окна 1/5/15 минут, включая перцентили p50/p90) — они показывают реальное распределение, а не только среднее. Готовая пошаговая процедура диагностики — в разделе «Диагностика узкого места через Flow Metrics» выше. Для постоянного наблюдения направляйте те же метрики в кластер через Elastic Agent (integration Logstash): дашборды строятся поверх идентичных полей.

### Оптимизация и тюнинг (Logstash 9.x)

| Параметр | Рекомендуемое значение | Описание |
| :--- | :--- | :--- |
| `pipeline.buffer.type` | `heap` (по умолчанию с 9.0) | Дефолт 9.0 — heap; `direct` остался для входных плагинов Elastic Agent, Beats, TCP и HTTP, которым нужна прямая память (breaking change 9.0, #16500). |
| `pipeline.batch.size` | `250 – 500` | Оптимально для сбалансированной пропускной способности и задержки. |
| `pipeline.batch.output_chunking.growth_threshold_factor` | `1000` (по умолчанию, с 9.4.1) | Автоматически дробит разросшиеся батчи (фильтры `split`/`clone`) обратно до `pipeline.batch.size` перед передачей output — ограничивает расширение памяти. |
| `pipeline.recoverable` | `auto` (с 9.4.1; по умолчанию `false`) | Восстановление конвейера после краха: `auto` — только для PQ-конвейеров, `true` — для любых (риск потери данных на memory-очереди), `false` — без автоматического восстановления. |
| `jvm.options` | `4GB – 8GB` | "Золотой стандарт" для Heap. Не рекомендуется выделять более 31 ГБ. |
| `pipeline.ordered` | `true` (для агрегации) | Гарантирует порядок событий; требует `pipeline.workers: 1` — со множеством воркеров Logstash не стартует. |
| `dead_letter_queue.enable` | `true` | Обязательно для production-сред для предотвращения потери данных. |

Правила безопасного тюнинга (по официальному руководству Elastic):

1. **Считайте inflight count** (`workers × batch.size`): память под пик должна вмещать это число событий плюс запас на всплески больших событий. Меняйте множители по одному и измеряйте эффект — часть изменений снижает производительность.
2. **Определяйте класс плагина**: CPU-bound плагины масштабируются воркерами только пока есть свободный CPU; IO-bound (сеть/диск) выигрывают от воркеров и крупных батчей даже при высоком использовании CPU, пока внешняя система не давит backpressure.
3. **Используйте метрику батчей**: с 9.2 (technical preview) настройка `pipeline.batch.metrics.sampling_mode` (`disabled`/`minimal` по умолчанию/`full`) включает сбор реальных размеров батчей — числа событий и байтов. Постоянно неполные батчи (P50/P90 заметно меньше лимита) — сигнал НЕ увеличивать размер (растет лишь латентность); смешанные перцентили указывают на взрывной трафик. Учтите рост потребления heap при включении сбора.
4. **Не путайте симптомы**: высокий backpressure + полные батчи = бутылочное горло ниже по потоку (масштабируйте воркеров/ресурсы), низкий backpressure + неполные батчи = недогруженный конвейер (тюнинг не нужен).
5. Число воркеров может превышать число ядер — выходные плагины часто ждут сеть; проверяйте гипотезу инструментами JVM (`jstack`, VisualVM): входы видны как потоки `[<id>]<input_name`, воркеры — как `[<id>]>workerN`, где `<id>` — идентификатор конвейера.

### Управление Dead Letter Queue

Настройки уровня `logstash.yml` (DLQ включается независимо от типа очереди — `queue.type: persisted` не требуется):

```yaml
dead_letter_queue.enable: true              # включение DLQ (по умолчанию false)
dead_letter_queue.max_bytes: 1024mb         # размер на каждый конвейер (дефолт 1024mb)
dead_letter_queue.flush_interval: 5000      # мс: задержка между записью события и его доступностью для чтения (мин. 1000)
dead_letter_queue.flush_check_interval: 1000 # мс: период проверки «застоявшихся» сегментов (мин. 1000; появилась в 9.4.1)
# dead_letter_queue.retain.age: 7d          # автоудаление событий старше значения (единицы d/h/m/s)
# path.dead_letter_queue: /var/lib/logstash/dead_letter_queue  # дефолт: path.data/dead_letter_queue
```

Ограничения: только локальная файловая система (NFS не поддерживается); один каталог DLQ нельзя использовать двумя инстансами Logstash одновременно.

События попадают в DLQ при ответе Elasticsearch 400 (ошибка маппинга/парсинга документа); сетевые отказы и 429 туда не пишутся — они обрабатываются retry-логикой output. Файлы сегментов лежат в `/var/lib/logstash/dead_letter_queue/<pipeline_id>/` и нумеруются последовательно, новый сегмент начинается с каждым рестартом.

События из DLQ можно перечитать с помощью плагина ввода `dead_letter_queue`:
```ruby
input {
  dead_letter_queue {
    path => "/var/lib/logstash/dead_letter_queue"
    commit_offsets => true
    pipeline_id => "main-ingress"
  }
}
```
Это позволяет исправить ошибки в фильтрах и запустить повторную обработку только проблемных данных. Каждое событие из DLQ содержит исходное событие, служебное поле `[@metadata][dead_letter_queue]` с причиной отказа (plugin_id, plugin_type, reason) и временем попадания в очередь — используйте их для маршрутизации исправлений. Параметр `commit_offsets => true` (по умолчанию) продвигает позицию чтения, поэтому запускайте перечитывающий конвейер только после устранения первопричины; для многократного просмотра событий без сохранения состояния ставьте `commit_offsets => false`. Опция `clean_consumed => true` (с 8.4.0, требует `commit_offsets => true`) дополнительно удаляет полностью вычитанные сегменты, освобождая диск. Опция `start_timestamp` позволяет начать перечит с заданного момента (ISO8601). События, снова не прошедшие обработку, в DLQ не возвращаются — маршрутизируйте их явно (условие по `[@metadata][dead_letter_queue]`).

Контроль переполнения: при достижении `max_bytes` поведение определяет `dead_letter_queue.storage_policy`: `drop_newer` (по умолчанию) отвергает новые события, которые не поместятся в лимит, а `drop_older` вытесняет старейшие события для освобождения места. Выбирайте политику осознанно: с `drop_newer` при переполнении новые ошибки теряются — мониторьте объем каталога и алертите до достижения лимита:

```bash
du -sh /var/lib/logstash/dead_letter_queue/*/
# → 512M  /var/lib/logstash/dead_letter_queue/main/
```

### Типичные проблемы и их решение (Troubleshooting)

1. **Растет память при агрегации (OOM).**
   Причина: карты задач с непрерывным потоком событий удерживаются до истечения `timeout` (дефолт 1800 с) — при долгоживущих задачах и забытых таймаутах память растёт без ограничений.
   Решение: выставьте оба таймаута; при рестартах без потери состояния — `aggregate_maps_path`; контроль числа карт — настройка `map_count_warning_threshold` (по умолчанию 5000): при превышении порога в лог пишется предупреждение каждые 20% от порога, `0` отключает предупреждения.
2. **Агрегация иногда теряет события или считает неверно.**
   Причина: воркеров больше одного — порядок нарушается.
   Решение: `pipeline.workers: 1` + `pipeline.ordered: true` в выделенном конвейере; прием оставьте в многопоточном ingress через P2P.
3. **Конвейер стал медленным после включения `ordered: true`.**
   Причина: строгий порядок ограничивает параллелизм даже там, где он не нужен.
   Решение: включайте `ordered` только в конвейере с `aggregate`/`sort`-логикой; в остальных оставляйте `auto`.
4. **`grok` обрабатывает тысячи событий в секунду хуже остальных фильтров.**
   Диагноз: `worker_millis_per_event` у `grok` на порядок выше соседей (см. методику Flow Metrics).
   Решение: разбирайте заголовок `dissect`-ом; в `grok` якорите шаблоны (`^...$`), избегайте жадных `%{GREEDYDATA}` в середине паттерна; тестируйте шаблоны в Kibana Grok Debugger.
5. **OOM при пиковом трафике без видимой нагрузки в среднем.**
   Причина: inflight count (`workers × batch.size`) слишком велик для heap при редких гигантских событиях.
   Решение: снизьте `pipeline.batch.size`, увеличьте heap, ограничьте размер событий на входе.
6. **События не доходят до второго конвейера P2P.**
   Причины: опечатка в `address`/`send_to` (ловится `-t` только частично — ошибка привязки проявляется в логе старта), конвейер-получатель упал.
   Решение: сверяйте имена адресов символ в символ; проверяйте `journalctl -u logstash` на `[ERROR]` старта обоих конвейеров.
7. **DLQ переполнена.**
   Причина: достигнут `dead_letter_queue.max_bytes`; при политике по умолчанию (`drop_newer`) новые ошибки отвергаются и теряются.
   Решение: увеличьте `dead_letter_queue.max_bytes`, при необходимости переключите `dead_letter_queue.storage_policy` на `drop_older`, настройте автоочистку `dead_letter_queue.retain.age`, ускорьте цикл переработки (input `dead_letter_queue` + `commit_offsets`), алертите по объему каталога.

### Лучшие практики и очистка окружения

* **Изоляция ответственности:** быстрый прием, тяжелая обработка и агрегация — три разных конвейера, связанных P2P; каждый со своими воркерами, очередью и бюджетом памяти.
* **Никакой агрегации в общем ingress:** однопоточный конвейер агрегации никогда не должен стоять на пути основного потока событий.
* **Таймауты обязательны** для любого состояния в памяти (aggregate, фильтры с кэшами) — память конвейера не резиновая.
* **Изменяйте один параметр за раз** и измеряйте flow-метрики до/после в окне `last_15_minutes`; одновременное изменение нескольких настроек делает выводы недостоверными.
* **DLQ включена везде**, где output пишет в Elasticsearch; объем каталога мониторится, переработка отработана как процедура.
* Очистка стенда после экспериментов:

```bash
# Остановить Logstash (все конвейеры, включая P2P-связки)
sudo systemctl stop logstash

# Удалить временные конфиги экспериментов
sudo rm /etc/logstash/conf.d/01-ingress.conf /etc/logstash/conf.d/02-aggregate.conf

# Очистить состояние экспериментов (осторожно: невыгруженные события будут потеряны)
sudo rm -rf /var/lib/logstash/dead_letter_queue/* /var/lib/logstash/queue/*
sudo rm -f /var/lib/logstash/.aggregate_maps*

# Проверить освобождение портов
ss -tlnp | grep -E '5044|9600'
# → пустой вывод
```
