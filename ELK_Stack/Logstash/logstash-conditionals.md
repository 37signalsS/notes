# Logstash: Условные операторы и sprintf

**Актуально для:** Logstash 8.19 (LTS) / 9.5.x

## Определения

**Conditional (условный оператор)** — конструкция `if` / `else if` / `else` в конфигурации конвейера, которая применяет ветку `filter` или `output` к событию только при выполнении выражения. Это единственный встроенный механизм ветвления в конфигурации конвейера; произвольная логика возможна только в `ruby`-фильтре (см. [Процессинг на Ruby](./logstash_pipelines.md#процессинг-на-ruby)).

**Expression (выражение)** — условие внутри conditional: сравнение полей события с литералами или друг с другом, регулярное совпадение, проверка вхождения (`in`), логическая комбинация подвыражений.

**Field reference (ссылка на поле)** — синтаксис обращения к полю события. Литерал вложенного поля — путь из фрагментов в квадратных скобках: `[top-level field][nested field]`. Имя поля верхнего уровня можно писать без скобок.

**Sprintf format** — строковый шаблон с подстановками: `%{field}` вставляет значение поля события, `%{+FORMAT}` / `%{{FORMAT}}` — отформатированное время `@timestamp`.

**`@metadata`** — служебная область события: её значения доступны в условиях и sprintf, но не передаются в output-плагины и не индексируются (подробно — [Вложенные условия и `@metadata` как промежуточный флаг](#вложенные-условия-и-metadata-как-промежуточный-флаг)).

## Основные концепции

### Синтаксис условий

```ruby
if EXPRESSION {
  ...
} else if EXPRESSION {
  ...
} else {
  ...
}
```

Условия могут быть вложенными друг в друга без ограничений; подвыражения группируются скобками `(...)`. Пример — удаление служебного поля только для события входа:

```ruby
filter {
  if [action] == "login" {
    mutate { remove_field => "secret" }
  }
}
```

В одной ветке можно комбинировать несколько выражений:

```ruby
output {
  if [loglevel] == "ERROR" and [deployment] == "production" {
    pagerduty { ... }
  }
}
```

### Операторы

| Категория | Операторы | Примечание |
| :--- | :--- | :--- |
| Сравнение | `==`, `!=`, `<`, `>`, `<=`, `>=` | Сравниваются значения сопоставимых типов; несопоставимые типы (например, `100` и `"100"`) — ошибка вычисления, см. ниже |
| Регулярное выражение | `=~`, `!~` | Паттерн справа, проверяемая строка слева |
| Вхождение | `in`, `not in` | Семантика зависит от типа правого операнда (см. ниже) |
| Булева логика | `and`, `or`, `nand`, `xor` | |
| Отрицание | `!` | Унарный оператор, применяется к выражению в скобках |

### Семантика `in` / `not in`

Один и тот же оператор ведёт себя по-разному в зависимости от типа правой стороны:

```ruby
filter {
  if [foo] in [foobar] {              # значение поля foo входит в коллекцию foobar
    mutate { add_tag => "field in field" }
  }
  if [foo] in "foo" {                 # значение поля содержится в строке-литерале (проверка подстроки)
    mutate { add_tag => "field in string" }
  }
  if "hello" in [greeting] {          # строка-литерал содержится в поле-коллекции
    mutate { add_tag => "string in field" }
  }
  if [foo] in ["hello", "world", "foo"] {   # поле равно одному из элементов списка
    mutate { add_tag => "field in list" }
  }
  if [missing] in [alsomissing] {     # оба поля отсутствуют — ложь
    mutate { add_tag => "shouldnotexist" }
  }
  if !("foo" in ["hello", "world"]) { # отрицание всего выражения в скобках
    mutate { add_tag => "shouldexist" }
  }
}
```

Когда применено к строке, `in` означает «является подстрокой»; когда применено к коллекции — «коллекция содержит точное значение». Типичный производственный приём — фильтрация по тегам неудачных парсингов:

```ruby
output {
  if "_grokparsefailure" not in [tags] {
    elasticsearch { hosts => ["${ES_URL}"] }
  }
}
```

### Когда выражение ложно

Выражение `if [foo]` возвращает `false` во всех случаях:

* поле `[foo]` отсутствует в событии;
* значение поля — `false`;
* значение поля — `null`;
* строковое представление значения пусто (`""`) или равно `"false"`.

Официальная документация перечисляет только первые три случая, но поведение шире: функция истинности в исходниках Logstash (`EventCondition.valueIsTruthy`) проверяет строковое представление значения, поэтому к ложным относятся также пустая строка и `"false"`, а любое другое непустое значение (в том числе `"0"` и `" "`) — истинно. Практическое следствие: поле с текстовым содержимым `"false"` не пройдёт условие `if [foo]`, хотя поле существует.

Отличить «поля нет» от «поле ложно» в конфигурации нельзя. Поэтому условие «на существование» пишут как `if [foo]`, а для различимости логического `false` и отсутствия поле лучше привести к явному строковому/числовому значению через `mutate`.

Если выражение вызывает ошибку при вычислении (например, сравнение целого `100` со строкой `"100"`), обработка события останавливается, а в лог пишется warning. Чтобы получить полный текст сообщения на момент ошибки, поднимите уровень логирования до `debug` ([Logging](https://www.elastic.co/docs/reference/logstash/logging)).

### Порядок вычисления условий и независимость веток

Условие вычисляется в момент исполнения собственной позиции в конфигурации:

* **В `filter`** условие видит только то, что уже существует на этой позиции: поля, пришедшие со входа или от кодека, и поля, добавленные предшествующими фильтрами. Поле, которое добавит фильтр, стоящий ниже по тексту, условие выше не увидит — это одна из причин, по которой поле в итоговом событии «есть», а условие ложно (раздел выше). Порядок исполнения фильтров и требования к его организации — в [Рекомендациях по порядку фильтров](./logstash_pipelines.md#рекомендации-по-порядку-фильтров).
* **В `output`** условия вычисляются после завершения всех фильтров конвейера, поэтому там доступны все поля события, включая `@metadata`, вычисленное в `filter`.

Блок `if / else if / else` — взаимоисключительная группа: выполнится ровно одна ветка. Раздельные `if` в одном `output` независимы: если совпало несколько — выполнится несколько, и событие уйдёт в несколько выходов. Если не совпало ни одно условие — данный выход не выполняется и событие ему не достаётся; поэтому цепочку условий в `output` заканчивают `else`.

### Где работают условные операторы и ссылки на поля

Field references, sprintf и conditionals **не работают в блоках `input`**: входы порождают события, полей к этому моменту ещё нет. Эти конструкции применяются только в `filter` и `output`.

### Ссылки на поля (field references)

Базовый синтаксис — `[fieldname]`; для вложенных полей указывается полный путь. Для данного события

```json
{
  "agent": "Mozilla/5.0 (compatible; MSIE 9.0)",
  "ip": "192.168.24.44",
  "request": "/index.html",
  "response": { "status": 200, "bytes": 52353 },
  "ua": { "os": "Windows 7" }
}
```

поле `os` адресуется как `[ua][os]`, поле верхнего уровня `request` — как `request`. Ссылки используются в трех местах: литералы в условных выражениях, строковые аргументы плагинов и sprintf-шаблоны:

```ruby
filter {
  if [@metadata][date] and [@metadata][time] {
    mutate {
      add_field => {
        "[@metadata][timestamp]" => "%{[@metadata][date]} %{[@metadata][time]}"
      }
    }
  }
}
```

Если имя поля само содержит квадратные скобки, для его адресации нужны escape-последовательности. Глобально настраиваются три режима:

* `none` (по умолчанию) — обработка escape не выполняется, поля с литеральными скобками через Event API недоступны;
* `percent` — URI-кодирование UTF-8 байт: `[` → `%5B`, `]` → `%5D`;
* `ampersand` — HTML-кодирование: `[` → `&#91;`, `]` → `&#93;`.

### Sprintf: подстановка полей и времени

Значение любого поля подставляется в строку по синтаксису `%{field}` (для вложенных — `%{[response][status]}`):

```ruby
output {
  statsd {
    increment => "apache.%{[response][status]}"
  }
}
```

Форматирование времени задаётся вместо имени поля:

* `%{{FORMAT}}` — **современный** синтаксис на базе `java.time.format.DateTimeFormatter` (например, `%{{yyyy.MM.dd.HH}}`);
* `%{+FORMAT}` — **устаревший** синтаксис joda-time (например, `%{+YYYY.MM.dd}`); поддерживается для обратной совместимости, форматы двух систем не взаимозаменяемы;
* `%{{TIME_NOW}}` — свежая отметка времени в момент обработки (аналог `@timestamp` события здесь и сейчас).

```ruby
output {
  file {
    path => "/var/log/%{type}.%{{yyyy.MM.dd.HH}}"
  }
}
```

Метка времени Logstash — момент на UTC-шкале, поэтому sprintf-форматирование даёт результат, который может не совпадать с локальным часовым поясом машины.

### Ограничение: sprintf даты/времени в conditionals

Sprintf date/time **в условных выражениях не поддерживается** — конструкция `if "%{{HH}}:%{{mm}}" < "16:30"` не вычисляется, а сравнивает буквальную строку-шаблон. Рабочий обходной путь — вынести formatted-время в поле (типично в `@metadata`) и уже поле использовать в условии:

```ruby
filter {
  mutate {
    add_field => {
      "[@metadata][time]" => "%{{HH}}:%{{mm}}"
    }
  }
  if [@metadata][time] < "16:30" {
    mutate {
      add_field => {
        "string_compare" => "%{{HH}}:%{{mm}} is before 16:30"
      }
    }
  }
}
```

## Практические сценарии

### Маршрутизация потоков по полям события

Классика — разводка по индексам Elasticsearch в секции `output`; другие паттерны (дублирование потока, пересылка в другой конвейер, несколько выходов Elasticsearch) — в заметке [Входы, выходы и маршрутизация](./logstash_inputs_outputs.md#маршрутизация-в-output):

```ruby
output {
  if [service] == "payments" and [level] == "ERROR" {
    elasticsearch { hosts => ["${ES_URL}"] index => "logs-payments-error" }
  } else if [service] == "payments" {
    elasticsearch { hosts => ["${ES_URL}"] index => "logs-payments" }
  } else {
    elasticsearch { hosts => ["${ES_URL}"] index => "logs-generic" }
  }
}
```

Цепочка выше — взаимоисключительная: выполнится ровно одна ветка. Чтобы событие могло уйти сразу в несколько выходов, условия задают раздельными `if` (см. раздел «Порядок вычисления условий»).

### Отсечение шума и защитные ветки в filter

```ruby
filter {
  # отбросить debug-события до тяжелых фильтров ниже
  if [level] == "DEBUG" {
    drop { }
  }

  # служебные эндпоинты health/readiness — тоже не пишем в индекс
  if [request] =~ /^\/(health|ready|metrics)/ {
    drop { }
  }

  # тяжелое обогащение — только для продовых сервисов
  if [env] == "prod" and [service] != "healthcheck" {
    geoip { source => "[client][ip]" }
  }
}
```

Условие оценивается **до** вхождения в ветку, поэтому дорогие фильтры (`geoip`, `elasticsearch`) всегда оборачиваются условием — это дешевле, чем выполнять их и отбрасывать результат.

### Вложенные условия и `@metadata` как промежуточный флаг

```ruby
filter {
  if [log_type] == "production" {
    mutate { add_field => { "[@metadata][target_index]" => "prod-%{{yyyy.MM.dd}}" } }
  } else {
    mutate { add_field => { "[@metadata][target_index]" => "unknown-%{{yyyy}}" } }
  }
}
output {
  if [@metadata][target_index] {
    elasticsearch {
      hosts => ["${ES_URL}"]
      index => "%{[@metadata][target_index]}"
    }
  }
}
```

`@metadata` не попадает в итоговый документ — условие по нему ничего не засоряет в Elasticsearch. Посмотреть значения `@metadata` при отладке такого условия можно только кодеком `rubydebug` с флагом `metadata => true` (`stdout { codec => rubydebug { metadata => true } }`) — остальные кодеки служебную область не показывают ([кодеки в заметке о входах/выходах](./logstash_inputs_outputs.md#кодеки-и-кодировки)).

### Проверка ветвлений на тестовом событии

Маршрутизацию проверяют на одном событии, не подключая боевые выходы: метка в каждой ветке (`add_tag`) показывает, какой путь выбрал конвейер.

```bash
echo '{"level":"ERROR","env":"prod"}' | bin/logstash -e '
  input { stdin { codec => json } }
  filter {
    if [level] == "ERROR" and [env] == "prod" {
      mutate { add_tag => ["branch:error"] }
    } else {
      mutate { add_tag => ["branch:other"] }
    }
  }
  output { stdout { codec => rubydebug } }'
# → "tags" => ["branch:error"]   — событие пошло в ожидаемую ветку
```

`bin/logstash -t` проверит синтаксис такой конфигурации, но выражения не вычислит — фактический путь события виден только на прогоне (см. п. 5 ниже и [локальную отладку фильтров](./logstash_pipelines.md#локальная-отладка-фильтров)). Перед прогоном убедитесь, что тестовое событие содержит те же поля и типы, что и боевые: расхождение типов — самая частая причина невыполнения условия (п. 1 ниже).

## Типичные проблемы и их решение (Troubleshooting)

1. **Условие не срабатывает, хотя поле «есть».**
   Причина: значение поля — `false`, `null`, пустая строка `""`, строка `"false"` либо поле отсутствует — всё это ложь (полный список — раздел «Когда выражение ложно» выше). Также частая ошибка — сравнение числа со строкой (`[status] == "200"` при числовом `200`).
   Диагностика: пропустите событие через `stdout { codec => rubydebug }` и посмотрите фактические типы значений.
   Решение: сравнивать с тем типом, что реально в событии; привести тип заранее через `mutate { convert => ... }`.
2. **В логе warning об ошибке вычисления условия, событие «зависает» на стадии.**
   Причина: несопоставимые типы в сравнении — обработка события останавливается на ошибке.
   Решение: поднять уровень логов до `debug`, найти ветку с ошибочным сравнением, исправить типы.
3. **В условии вместо времени — буквальный шаблон `%{{HH}}`.**
   Причина: sprintf date/time в conditionals не поддерживается.
   Решение: обходной путь через `[@metadata]` (раздел «Ограничение» выше).
4. **Условие в блоке `input` игнорируется.**
   Причина: в `input` ещё нет полей события — field references, sprintf и conditionals там не работают.
   Решение: перенести логику в `filter` или `output`.
5. **`bin/logstash -t` сообщает Configuration OK, но условие ведёт себя неверно.**
   Причина: `-t` проверяет синтаксис конфигурации, но не вычисляет выражения на реальных событиях.
   Решение: прогон тестовой строки через `echo ... | bin/logstash -e '...'` с `stdout { codec => rubydebug }` (см. [локальную отладку фильтров](./logstash_pipelines.md#локальная-отладка-фильтров)).
6. **Событие не появилось ни в одном выходе, хотя конфигурация валидна.**
   Причина: каждый output-плагин проверяет условия отдельно; если не совпало ни одно условие ни у одного выхода, событие не будет никуда отправлено.
   Диагностика: временно добавьте завершающую ветку `else { stdout { codec => rubydebug } }` и проверьте фактические значения полей, на которые рассчитывают условия.
   Решение: завершить цепочку условий `else` либо поправить условия (типы значений — п. 1, порядок вычисления — п. 7).
7. **Поле в событии «есть», но условие его не видит.**
   Причина: условие вычисляется в своей позиции конфигурации — поле, добавленное фильтром, стоящим ниже по тексту, к этому моменту ещё не существует (раздел «Порядок вычисления условий» выше).
   Решение: перенести условие ниже фильтра, добавляющего поле, либо вычислять признак раньше — например, в отдельном `mutate` перед условием.

## Лучшие практики

* Держите условия короткими; вложенность глубже 2–3 уровней затрудняет чтение — выносите промежуточные признаки в `@metadata`.
* Для проверки принадлежности к списку используйте `in` — это идиоматичнее цепочки `or`.
* Служебные флаги и производные значения (имя индекса, признак маршрута) храните в `@metadata`, чтобы не индексировать их.
* Завершайте цепочку маршрутизации `else`, чтобы у «непопавших» событий был детерминированный путь.
* Явно фиксируйте намерение ветвления: взаимоисключительные маршруты — одна цепочка `if/else if/else`, независимые — отдельные `if`.
* Оборачивайте дорогие фильтры условием до вызова, а не фильтруйте результат после.
* Отладочные метки веток (`branch:*`) и временные `else`-заглушки убирайте после проверки, чтобы не засорять `tags` в индексе.
