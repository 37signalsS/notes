# Logstash: Backpressure, batching и поведение Input-плагинов

**Актуально для:** Logstash 8.17+ / 9.x

## Определения

- **Backpressure (обратное давление)** — механизм защиты от переполнения очереди: когда выходной этап (output) не успевает обрабатывать события и очередь заполняется (особенно `queue.type: persisted`), Logstash приостанавливает приём новых событий на входных плагинах, чтобы избежать неконтролируемого роста памяти/диска и потерь.
- **Pipeline workers** (`pipeline.workers`) — количество параллельных воркеров конвейера, обрабатывающих батчи событий (по умолчанию — число CPU-ядер хоста).
- **Batch** — порция событий, которую воркер забирает за одну итерацию из очереди (`pipeline.batch.size`, по умолчанию 125).
- **Batch delay** (`pipeline.batch.delay`, мс, по умолчанию 50) — максимальное время ожидания добора событий в батч до его отправки на обработку.
- **Inflight count** — количество событий, одновременно находящихся в обработке внутри конвейера: `pipeline.workers × pipeline.batch.size`. Ключевой фактор потребления Heap.
- **Flow control** — внутренняя логика Logstash (pipeline flow), регулирующая скорость чтения (input) в зависимости от заполненности очереди и производительности filter/output.

## Основные концепции

### Взаимосвязь workers, batch.size, batch.delay

- **Workers.** Каждый воркер работает независимо и последовательно прогоняет батч: Input-очередь → Filter → Output. Увеличение `pipeline.workers` повышает параллелизм (черезput), но увеличивает `inflight count` и нагрузку на output (особенно на Elasticsearch с bulk).
- **Batch size.** Больший батч эффективнее для batch-ориентированных output'ов (меньше HTTP-запросов, лучше использование bulk в ES), но увеличивает пиковое потребление памяти на батч и латентность (события дольше ждут добора батча).
- **Batch delay.** Если поток событий прерывистый (спайки с паузами), `batch.delay` позволяет «добрать» события в неполный батч вместо отправки мелких батчей каждые итерации. Чем меньше delay — ниже латентность, чем больше — выше throughput.

**Рекомендуемая формула зависимости (практическая):**
- `inflight count = pipeline.workers × pipeline.batch.size` — оценка одновременных событий в памяти.
- Верхняя оценка добавляемой задержки на стадии добора батча: `pipeline.batch.delay × pipeline.batch.size` (максимальное время ожидания между получением события и его обработкой в фильтре). Реальная задержка обычно ниже и зависит от скорости поступления событий.

### Backpressure: когда и как срабатывает

Logstash использует **backpressure** для выравнивания скорости приёма и вывода:

1. Output не успевает подтверждать (ACK) обработанные события.
2. Очередь (memory или persisted) заполняется. При `queue.type: persisted` заполнение отслеживается по `queue.max_bytes` (и `queue.max_events`).
3. Flow controller снижает скорость забора событий из очереди input'ами. Input-плагины **приостанавливают приём** новых данных (не отбрасывают уже полученные события).
4. Как только output начинает справляться и очередь опустошается — приём возобновляется.

Ключевое свойство: **backpressure — это пауза чтения (throttling), а не потеря событий**. События, уже принятые во входной буфер/очередь Logstash, сохраняются (at-least-once при PQ). Новые события временно не принимаются до снятия давления.

### Метрика queue_backpressure

Индикатор активного backpressure — `queue_backpressure`: безразмерная доля времени, которую input-плагины проводят в простое, упираясь в заполненную очередь. Метрика не сравнивается между разными конвейерами, но позволяет отслеживать динамику одного конвейера во времени: рост означает, что inputs блокируются из-за переполненной очереди. При `queue.type: persisted` ключевой сопровождающий индикатор — `queue_persisted_growth_events`: положительное значение означает, что дисковая очередь поглощает лаг, и она должна стремиться к нулю или отрицательным значениям (отрицательное = воркеры догоняют накопленный лаг).

### Поведение Input-плагинов при backpressure

Разные input-плагины реагируют на приостановку чтения по-разному (важно для оценки потерь на границе с источником):

| Input | Тип источника | Поведение при backpressure | Комментарий |
|---|---|---|---|
| **`beats`** | TCP (протокол Beats, длинное соединение) | **Пауза приёма/торможение потока.** Filebeat/Elastic Agent видят, что Logstash не читает (TCP backpressure), замедляют отправку, могут накапливать события в собственном очереди (spool). | Не теряет события на уровне агента при штатном backpressure; агенты имеют собственные буферы (file/registry + spool). |
| **`tcp`** | TCP-сокет | **TCP flow control.** Logstash перестаёт читать из сокета → TCP receive window заполняется → отправитель замедляется/блокируется. Соединение остаётся открытым. | Данные в TCP-буферах ОС не теряются. Потери возможны только если отправитель не держит буфер (fire-and-forget) или обрывает соединение по таймауту. |
| **`udp`** | UDP (датаграммы) | **Нет надёжного backpressure.** Logstash не может «приостановить» отправителя по UDP. При переполнении входного буфера (`buffer_size`, `queue_size`) **новые датаграммы отбрасываются**. | UDP по своей природе best-effort. Потери при пиковых нагрузках/долгом backpressure — ожидаемы. |
| **`http`** | HTTP (keep-alive) | **Блокировка ответов/приостановка приёма.** При заполненной очереди плагин приостанавливает чтение запросов — клиенты могут получать таймауты/ретраи (зависит от клиента). | При правильной ретрай-логике клиента события не теряются (at-least-once на стороне клиента). |
| **`kafka`** | Consumer (pull) | **Замедление потребления.** Logstash читает батчами (poll). Backpressure уменьшает скорость обработки → consumer lag растёт, но **Kafka хранит сообщения** (retention). | Классический safe-случай: потерь нет, растёт lag. |
| **`redis`** (list) | BLPOP/RPOP | **Приостановка чтения.** Плагин блокируется/замедляется при переполнении очереди конвейера — сообщения остаются в Redis (если не вытеснены по политикам). | Без потерь, при условии достаточного объёма Redis. |
| **`jdbc`** | Polling (SQL) | **Poll замедляется/откладывается.** Плагин выбирает данные по расписанию/инкременту; backpressure не заставляет «откатить» уже прочитанные строки, но может сдвинуть следующий цикл (рост задержки обработки). | Критично корректно вести watermark/инкрементный ID (не терять и не дублировать при ретраях). |
| **`file`** | Файловый tail | **Замедление чтения/позиция хранится.** Logstash хранит смещение в sincedb (registry). При backpressure чтение приостанавливается, позиция **не** теряется. После снятия давления обработка продолжается с сохранённого смещения. | Потерь нет (at-least-once). Возможен рост отставания (lag). |

### Latency vs Throughput: выбор batch.size/batch.delay

| Приоритет | Рекомендуемые значения | Обоснование |
|---|---|---|
| **Низкая латентность** (real-time алерты, near-real-time) | `pipeline.batch.size: 50–100`, `pipeline.batch.delay: 10–25ms` | Меньшие батчи + меньшая задержка добора → события выходят быстрее. Цена — чуть ниже throughput (больше HTTP-запросов в output). |
| **Высокий throughput** (массовый поток логов) | `pipeline.batch.size: 250–500`, `pipeline.batch.delay: 50–100ms` | Оптимально для bulk-вывода (ES). Меньше накладных расходов на батчи, выше утилизация воркеров. Латентность выше. |
| **Сбалансированный (default)** | `pipeline.batch.size: 125`, `pipeline.batch.delay: 50ms` | Универсальный компромисс для большинства production-нагрузок. |
| **Латентность + спайки (bursty traffic)** | `pipeline.batch.size: 100–150`, `pipeline.batch.delay: 20–50ms` | Позволяет добирать батч в пики, не раздувая его чрезмерно в паузах. |

**Правило практики:** смотрите на **реальные размеры батчей** (Logstash 9.2+ `pipeline.batch.metrics.sampling_mode: full/minimal`) — если P50/P90 батчей стабильно близки к `batch.size` и backpressure низкий, есть смысл осторожно увеличить `batch.size`. Если батчи часто неполные — увеличивать `batch.delay` нецелесообразно, лучше держать текущие значения.

### Влияние inflight count на Heap

`inflight count = workers × batch.size` — максимальное число событий, одновременно находящихся в памяти (filter/output path). Крупные события (JSON с вложениями, большие стектрейсы) сильнее влияют на Heap, чем счёт событий.

**Рекомендуемая эвристика:** Heap = 50–75% от RAM узла, размер Heap обычно 4–8 ГБ для типовых нагрузок, не более 31 ГБ (JVM compressed OOPs). При росте батчей/воркеров обязательно отслеживайте пиковый Heap (`_node/stats/jvm`) и OOM.

### Backpressure vs потери: сравнительная таблица

| Очередь | Backpressure | Потери при backpressure | Потери при аварийном падении | Zero-downtime reload |
|---|---|---|---|---|
| **`queue.type: memory`** | Да (пауза input) | **Нет** (уже принятые события держатся в памяти) | **Да** (inflight + очередь в памяти) | **Нет** (очередь теряется при остановке конвейера) |
| **`queue.type: persisted`** | Да (пауза input) | **Нет** (события на диске, input приостановлен) | **Минимальны** (только inflight, не чекпоинтнутые события при жёстком `kill -9` без drain). При штатной остановке (`SIGTERM`) с `queue.drain: true` — 0 потерь | **Да** (дисковая очередь сохраняется) |

**Вывод:** backpressure сам по себе **не вызывает потерь**. Потери характерны для:
- **UDP** (нет TCP-backpressure)
- **Memory queue + жёсткий рестарт/авария** (неперсистентная очередь)
- Экстренное завершение с `pipeline.unsafe_shutdown: true` (разрешает потерю inflight)

## Практические сценарии

### Балансировка latency vs throughput (практические рецепты)

**1. Поток логов приложений (burst-traffic), важна латентность**

```yaml
# pipelines.yml / logstash.yml (часть параметров конвейера)
pipeline.workers: 2
pipeline.batch.size: 80
pipeline.batch.delay: 20
```

**2. Высокопроизводительный приём Beats → ES (bulk-heavy)**

```yaml
pipeline.workers: 4        # ~CPU cores (с учётом I/O)
pipeline.batch.size: 300
pipeline.batch.delay: 50
```

**3. Чувствительный к памяти конвейер с большими событиями (stacktraces)**

```yaml
pipeline.workers: 2
pipeline.batch.size: 50   # уменьшить inflight
pipeline.batch.delay: 30
```

> Всегда проверяйте по `_node/stats/pipelines` (`worker_utilization`, `events.in/out`, queue growth), а не угадывайте.

### Диагностика backpressure

Проверка состояния очереди и backpressure:

```bash
curl -s 'localhost:9600/_node/stats/pipelines?pretty' | \
  jq '.pipelines.main.queue, .pipelines.main.events, .pipelines.main.flow'
```

Ключевые индикаторы:

| Метрика | Нормальное значение | Что означает |
|---|---|---|
| `queue.size` (events/bytes) | ~0 в стабильном состоянии | Рост >0 — вход быстрее выхода (backpressure активен или набирается лаг) |
| `queue_persisted_growth_events/bytes` | **0 или отрицательная** в стабильном состоянии | Положительный тренд длительное время — output не успевает (узкое место). Должен стремиться к 0. |
| `flow.worker_utilization` (0–1) | 0.6–0.8 | <0.4 — недогружен (избыточные workers или батчи мелкие). >0.9 — близко к пределу (риск backpressure в пики). |
| `events.duration_in_millis` | Стабильный, без резких всплесков | Резкий рост — фильтры/плагины замедлились (CPU/I/O). |
| `events.queue_push_duration_in_millis` | Низкий, стабильный | Рост — задержки при записи в PQ (диск I/O). |

### Мониторинг батчей (Logstash 9.2+)

Включить сбор метрик реальных размеров батчей (для принятия решения об увеличении `batch.size`):

```yaml
# logstash.yml
pipeline.batch.metrics.sampling_mode: full  # minimal | full | disabled
```

Анализировать распределение размеров батчей в `_node/stats` (histograms по событиям/байтам, перцентили p50/p90). **Практическое правило:** если P90 батчей стабильно ≈ `pipeline.batch.size`, а `queue_persisted_growth_*` ~0 и `worker_utilization` <0.85 — можно осторожно увеличить `batch.size` на 10–25% (пошагово, с мониторингом Heap).

### Практика выбора workers

Эмпирическое правило: `pipeline.workers = number of CPU cores` (для CPU-bound фильтров). Для I/O-bound (много output-запросов в ES/Kafka) часто **не** имеет смысла ставить `workers >> CPU`: bottleneck уходит в output/сеть/кластер. Лучше тестировать пошагово: +1 worker, смотреть `worker_utilization`, throughput, backpressure.

## Лучшие практики (Best Practices)

1. **Используйте `queue.type: persisted` для production-нагрузок.** Только дисковая очередь даёт защиту от потерь при backpressure, перезапусках и авариях. Memory-очередь теряет все события при падении процесса.
2. **Следите за `inflight count` при тюнинге.** Меняйте `pipeline.workers` и `pipeline.batch.size` по одному, измеряя эффект. Их произведение — верхняя оценка числа событий в памяти; пиковые всплески крупных событий требуют дополнительного запаса Heap.
3. **Не гонитесь за throughput в ущерб латентности.** Крупные батчи эффективнее для bulk-вывода, но увеличивают латентность и пиковое потребление памяти. Выбирайте режим по приоритету задачи (таблица выше).
4. **Следите за `queue_persisted_growth_events`.** При устойчивом положительном тренде — output не успевает, это узкое место, а не особенность backpressure. Решение — внизу потока (масштабирование output/кластера), а не в увеличении батчей.
5. **Не увеличивайте `batch.size` при неполных батчах.** Если P50/P90 стабильно ниже `pipeline.batch.size` — конвейер недогружен, рост размера только добавит латентность.
6. **Контролируйте Heap.** Heap = 50–75% ОЗУ узла, типично 4–8 ГБ, максимум 31 ГБ (JVM compressed OOPs). Мониторьте пиковые значения через `_node/stats/jvm` и следите за частотой Full GC.
7. **Осторожно с `pipeline.batch.metrics.sampling_mode: full`.** Включает сбор метрик реальных размеров батчей, но увеличивает потребление Heap каждым конвейером. Используйте для диагностики, при необходимости переключайте на `minimal` в production.
8. **Для burst-трафика выбирайте средние батчи и умеренный `batch.delay`.** Позволяет добирать батчи в пики, не раздувая их чрезмерно в паузах.
9. **При backpressure и полных батчах смотрите вниз по потоку.** Высокий `queue_backpressure` + полные батчи = бутылочное горло в output/фильтрах. Низкий backpressure + неполные батчи = конвейер недогружен, тюнинг не нужен.
10. **Для UDP-источников планируйте потери.** UDP не поддерживает backpressure; при переполнении входного буфера датаграммы отбрасываются. Используйте надёжные протоколы (TCP, Beats, Kafka) для критических данных.
