# Logstash: Multiline, агрегация, DLQ и эксплуатация PQ

**Актуально для:** Logstash 8.19 (LTS) / 9.5.x

## Определения

- **Multiline codec** — кодек в Logstash (`codec => multiline`) для склейки нескольких строк входного потока в одно событие (напр. Java stacktrace, многострочные логи). Работает на **входной** стороне для сырых потоков (`tcp`/`udp`/`file`).
- **Multiline на агенте** — парсер `multiline` в Filebeat/Elastic Agent. Применяется **до** отправки в Logstash. Рекомендуется, когда несколько хостов/агентов шлют логи через один `beats`-вход.
- **Aggregate filter** (`aggregate`) — фильтр для корреляции связанных событий в рамках конвейера (start/end события, транзакции). Требует аккуратного управления таймаутами и памятью.
- **Dead Letter Queue (DLQ)** — очередь событий, которые не удалось доставить/обработать в целевом output (напр. ошибки Elasticsearch mapping, постоянные 4xx). События можно проанализировать и повторно обработать после исправления проблемы.
- **Persistent Queue (PQ)** — дисковая очередь Logstash (`queue.type: persisted`), обеспечивающая сохранность событий при backpressure, перезапусках, hot-reload. Размер задаётся `queue.max_bytes` на **каждый** конвейер.
- **Queue drain** — штатная процедура опустошения очереди при остановке Logstash (`SIGTERM`) с `queue.drain: true` (по умолчанию поведение управляется конфигурацией). Позволяет корректно завершить работу без потери событий в очереди.

## Предпосылки и предварительная настройка (Prerequisites)

Перед внедрением multiline, aggregate, DLQ и PQ убедитесь в следующем:

1. **Версия Logstash.** Актуальные ветки — 8.19 (LTS) и 9.5.x (последний стейбл-релиз — 9.5.5, октябрь 2026). Критические отличия:
   - **9.2** — появление сжатия PQ (ZSTD, опция `queue.compression`), rollback-barrier: очередь со сжатыми событиями не читается версиями ниже 9.2.
   - **9.4.1** — параметр `pipeline.recoverable: auto` (восстановление упавших конвейеров при `config.reload.automatic`), опция `dead_letter_queue.flush_check_interval`.
   - **9.5** — `ssl.reload.automatic` (автоперезагрузка TLS-файлов), обновление Kafka Integration до 12.x (Kafka client 4.x, breaking changes для `partitioner`).
2. **Пользователь.** С 9.0 запуск от root запрещён (`allow_superuser: false` по умолчанию). Сервис работает от пользователя `logstash`.
3. **Диск под `path.data`.** На одном томе живут PQ, DLQ и sincedb-файлы. Требования:
   - Ёмкость: суммарный `queue.max_bytes` всех конвейеров + объём DLQ + запас.
   - IOPS и latency — критичны: медленный диск (HDD) резко увеличивает `events.queue_push_duration_in_millis` и вызывает backpressure. Для production — SSD/NVMe.
   - Персистентность: том не должен пропадать при пересоздании контейнера (в k8s — PVC/StatefulSet, не `emptyDir`).
4. **Heap JVM.** Типично 4–8 ГБ для стандартных нагрузок, не более 31 ГБ (JVM compressed OOPs). Задаётся в `jvm.options` или `LS_JAVA_OPTS`. Рекомендуется равные `-Xms`/`-Xmx`.
5. **Доступ к Monitoring API.** По умолчанию `127.0.0.1:9600`. Для внешнего мониторинга — `api.http.host: 0.0.0.0` сBasic auth (`api.auth.type: basic`) и TLS (`api.ssl.enabled: true`).
6. **Для aggregate-конвейеров:** одно ядро CPU на конвейер (или изоляция через Pipeline-to-Pipeline). Проверьте, что в конвейере нет неперезагружаемых плагинов, если планируется `config.reload.automatic`.

## Основные концепции

### Multiline: где правильно склеивать

Ключевое правило (уже отражено в заметках, но систематизируем):

- **Используйте multiline на агенте (Filebeat/Elastic Agent)**, если логи приходят через `beats`-вход **от нескольких источников/хостов одновременно**. Причина: `multiline`-кодек в Logstash буферизует строки в рамках **одного TCP-потока/соединения**. При смешении потоков разных хостов в одном `beats`-входе строки разных логов могут некорректно склеиваться.
- **Используйте multiline-кодек в Logstash** только для **сырых потоков**, где нет агента: `tcp`, `udp`, `file` (редко), либо когда **весь** поток идёт строго от одного источника в рамках одного входного соединения.
- **Никогда** не включайте `multiline`-кодек в `beats`-input при подключении множества агентов. Это классическая ошибка, приводящая к «перемешанным» многострочным событиям.

**Сравнительная таблица**

| Сценарий | Место склейки | Пояснение |
|---|---|---|
| **Filebeat → Logstash (beats)**, много хостов | **Filebeat (multiline парсер)** | Агент группирует многострочность до отправки. Logstash получает уже готовые события. |
| **Сырой syslog-over-tcp от одного приложения** | **Logstash (`codec => multiline`)** | Поток однородный, один источник. |
| **Сырой лог-файл через `tcp`/`netcat** | **Logstash (`codec => multiline`)** | Нет агента, нужен разбор многострочности. |
| **UDP-поток (best-effort)** | **Осторожно** | UDP фрагментация + потери усложняют multiline. Предпочтительно агент (если есть). |

### Типичные проблемы multiline и диагностика

| Проблема | Причина | Диагностика | Решение |
|---|---|---|---|
| **Частично склеенные/разбитые стектрейсы** | Неправильный `pattern`, `negate`, `what` | Тестировать на реальных образцах: `input { stdin{} } codec { multiline {...} } output { stdout { codec => rubydebug } }` | Подобрать `pattern` по первому/типичному маркеру (например `^\s+` для Java, `^\tat `, `^Caused by:`) |
| **Смешение стектрейсов разных хостов** | Multiline в `beats`-input при нескольких агентах | Сравнить `host`/`[@metadata][beat]` в полученных событиях — видны чужие строки | Убрать `multiline` из `beats`-input, настроить multiline в Filebeat |
| **«Зависание» буфера (timeout-эффект)** | Буфер не закрывается до истечения `timeout` (редко) или поток прервался | Увеличение `timeout`/наблюдение за событиями с задержкой | Настроить корректный `pattern` (должен надёжно определять начало новой записи). При tcp-потоках также помогает `tcp_keep_alive` |
| **Потеря первой/последней строки** | Неверная комбинация `negate` + `what` | Локальный тест через `echo -e` с реальным фрагментом | Проверить логику: `negate => true` означает «строка **не** соответствует pattern — присоединять к предыдущей» |

### Граничные случаи multiline (Edge Cases)

| Ситуация | Особенность поведения | Рекомендация |
|---|---|---|
| **Событие превышает `max_bytes`** | Кодек режет событие на `max_bytes` и помечает тегом `multiline` (по умолчанию); остаток стектрейса распадается на отдельные события. | Установите `max_bytes` выше типового максимального стектрейса с запасом 20–30%. Для Java-логов — не менее 10 KiB, для C++/Go — проверить реальные размеры. |
| **Очень длинные стектрейсы (> `max_lines`)** | Параметр `max_lines` (по умолчанию 500) обрывает склейку; остаток начинает новое событие. | Установите `max_lines` на уровне максимального ожидаемого числа фреймов стектрейса. Слишком низкое значение калечит стектрейсы, слишком высокое — рискует упереться в `max_bytes`. |
| **Неполная последняя строка (без `\n`)** | При `tcp`/`udp` буфер удерживает незакрытую строку до появления следующей или истечения `auto_flush_interval`. | Для потоков с паузами включите `auto_flush_interval` (например 5–10 с) — защищает от «висячих» событий. |
| **Пустые строки внутри стектрейса** | Если `pattern` не матчит пустые строки, они могут treated как начало новой записи. | Используйте `pattern => "^\s*$"` как дополнительный маркер продолжения, если пустые строки встречаются в стектрейсах. |
| **Кодировка (charset)** | По умолчанию `UTF-8`. Логи в `ISO-8859-1`/`windows-1251` требуют явного `charset`. | Укажите `charset` в кодеке multiline, если источник использует не-UTF-8 кодировку. |
| **Смешанные кодировки в одном потоке** | Кодек работает на уровне байтов, поэтому переключение кодировки внутри потока ломает склейку. | Гарантируйте однородную кодировку на уровне источника. |

### Корреляция событий: Aggregate filter (практика)

`aggregate` полезен для сборки пары `start`→`end`, расчёта длительности, группировки по ключу (`task_id`, `request_id`, `trace_id`). Подробный разбор всех опций, нюансов потокобезопасности и примеров конфигурации — в [заметке о конвейерах](./logstash_pipelines.md#работа-с-aggregate-filter).

**Ключевые практики (производственные):**

- **Ключ агрегации обязателен.** Используйте уникальный идентификатор (request_id/trace_id/correlation_id). Без него легко смешать разные транзакции.
- **Таймаут агрегации.** `timeout` (секунды) — максимальное время жизни незакрытой агрегации. По истечении таймаута фильтр выполнит `timeout_code` (если задан). **Всегда** задавайте осмысленный таймаут (не слишком большой) во избежание утечек памяти.
- **`push_map_as_event_on_timeout => true`** — позволяет выпустить событие по таймауту (partial result), что лучше чем просто потерять данные.
- **Единый воркер.** `aggregate` хранит состояние в памяти **текущего воркера**. Если событие с тем же ключом может попасть в **разные воркеры** одного конвейера — агрегация **не сработает**. Решение: либо `pipeline.workers: 1` для конвейера с агрегацией, либо вынести агрегацию в **отдельный однопоточный pipeline** и связать через Pipeline-to-Pipeline ([см. logstash_pipelines.md](./logstash_pipelines.md)).
- **Очистка.** Используйте `remove_field` для временных полей. Не храните гигантские объекты в `map_action`.
- **Защита от роста.** Следите за числом одновременно открытых агрегаций. При большом потоке «орphaned» start'ов (без end) память растёт. Таймаут + мониторинг — обязательны.

### Граничные случаи и подводные камни Aggregate

| Ситуация | Проблема | Решение |
|---|---|---|
| **Одновременные задачи с одинаковым `task_id`** | Карта агрегации перезаписывается — данные теряются. | Гарантируйте уникальность `task_id` (включайте timestamp, UUID, комбинацию host+pid+sequence). |
| **Исключение в `code`** | Логируется как ошибка, событие получает тег `_aggregateexception`, конвейер продолжает работу. | Маршрутизируйте `_aggregateexception` в отдельный индекс/конвейер для анализа. |
| **Рестарт конвейера с `aggregate_maps_path`** | Карты персистятся в файл; допустим только один такой фильтр на конвейер. | Используйте `aggregate_maps_path` для сохранения состояния между рестартами. |
| **Партиционированные источники (Kafka)** | События одной транзакции могут приходить к разным воркерам — агрегация ломается. | Единый воркер (`pipeline.workers: 1`) или изоляция через Pipeline-to-Pipeline. |
| **Большое число карт в памяти** | `map_count_warning_threshold` (по умолчанию 5000) генерирует предупреждения в лог каждые 20% от порога. | Отслеживайте рост числа карт; при превышении — анализируйте, какие `task_id` не закрываются. |
| **`push_previous_map_as_event` + непоследовательные задачи** | Результат предыдущей задачи эмитируется prematurely, если задачи чередуются. | Используйте только при строго последовательном потоке задач. |

### Dead Letter Queue (DLQ): эксплуатация

DLQ включается глобально/на уровне конвейера:

```yaml
# logstash.yml (глобально)
dead_letter_queue.enable: true
dead_letter_queue.max_bytes: 2gb
dead_letter_queue.storage_policy: drop_newer  # drop_newer | drop_older
```

**Практика эксплуатации:**

- **Включать в продакшене.** `dead_letter_queue.enable: true` — рекомендуемый минимум. Позволяет сохранить «проблемные» события вместо их потери при постоянных ошибках output (напр. неверный mapping ES).
- **Мониторинг размера.** Отслеживайте объём DLQ (`_node/stats` или размер каталога `path.data/dead_letter_queue/`). При постоянном росте — **не игнорировать**: чаще всего это либо битый mapping, либо некорректный формат событий.
- **Хранение и ротация.** DLQ хранит события на диске. `dead_letter_queue.max_bytes` ограничивает размер. При переполнении срабатывает `storage_policy`: `drop_newer` (по умолчанию) — отвергает новые попадающие в DLQ события; `drop_older` — вытесняет самые старые.
- **Повторная обработка (retry).** События из DLQ можно извлечь и повторно прогнать через исправленный конвейер. Типовой путь:
  1. Анализировать причину (ошибка в output, теги `_elasticsearch_lookup_failure`, `_grokparsefailure` контекст)
  2. Исправить конфигурацию конвейера/маппинг ES
  3. Настроить временный конвейер с input `dead_letter_queue` и отправить события в исправленный pipeline. Подробная процедура, опции `commit_offsets`, `clean_consumed`, `start_timestamp` и анализ поля `[@metadata][dead_letter_queue]` — в [заметке о конвейерах](./logstash_pipelines.md#управление-dead-letter-queue).
- **Не держать вечно.** DLQ — временный буфер для расследования/повтора. После успешной повторной обработки очищайте старые записи.

### Persistent Queue (PQ): эксплуатационные детали

**Базовые настройки (`logstash.yml`):**

```yaml
queue.type: persisted
queue.max_bytes: 4gb        # размер КАЖДОЙ очереди конвейера
queue.checkpoint.writes: 1024
queue.compression: none     # zstd (9.2+) — trade-off
```

**Эксплуатационные нюансы:**

- **Расчёт под простой output.** Формула из практики: `поток_байт/с × часы_простоя_выхода × 3600 × 1.10`. Пример: при 10 МБ/с и допустимом простое ES 12 часов — ~476 ГБ «буфер» с запасом. Диск под PQ должен вмещать **суммарный** `queue.max_bytes` **всех** конвейеров **всех** узлов + объём DLQ.
- **Восстановление после аварийного завершения.** При `queue.type: persisted` Logstash при старте читает состояние очереди с диска и восстанавливает незаконченные события. События, не попавшие в последний чекпоинт (`fsync` head-страницы), при **жёстком** завершении (`SIGKILL`) теоретически могут быть потеряны — именно поэтому важен штатный drain (`SIGTERM`).
- **`queue.drain: true`.** При корректной остановке (`systemctl stop logstash`) Logstash дожидается опустошения очереди (queue.size → 0) перед выходом. Это ключевой момент zero-downtime-like останова.
- **Сжатие ZSTD (`queue.compression: zstd`) — Logstash 9.2+.** Экономит место на диске, но добавляет CPU-нагрузку при записи/чтении. **Нельзя** переносить очередь со сжатием на версию Logstash < 9.2 — формат несовместим. Включайте только после валидации на той же минор/патч-ветке, планируя откат.
- **Диск под PQ.** Критичны **IOPS и latency** (не только ёмкость). Медленный диск (HDD) сильно увеличивает `queue_push_duration_in_millis` → backpressure. Для production предпочтительны SSD/NVMe.
- **Потеря `path.data`.** Если том с `path.data` пересоздан (emptyDir в k8s без PV, потерянный volume) — дисковая очередь **теряется**. Именно поэтому `path.data` должен быть **персистентным** томом.
- **Ограничения по размеру.** `queue.max_bytes` > 2 ГБ работал, но в ранних 9.2 были известные нюансы — держите в голове при миграции. Всегда сверяйтесь с версией, но общая практика — не делать один конвейер с гигантским `max_bytes` без необходимости (лучше несколько конвейеров при разной нагрузке).
- **Рост PQ в стабильном состоянии.** Если `queue_persisted_growth_events` стабильно > 0 при исправно работающем output — это однозначный сигнал: **узлов/пропускной способности не хватает** (либо output лаг, либо CPU/IO у Logstash). Не «лечится» только увеличением `max_bytes` — нужно решать bottleneck.

## Практические сценарии

### Диагностика роста DLQ

1. **Проверить объём**: `du -sh /var/lib/logstash/dead_letter_queue/` (или смотреть в Monitoring API при наличии метрик)
2. **Найти причину**: изучить логи Logstash (`journalctl -u logstash -n 100`) — типичные ошибки: `mapper_parsing_exception`, `document_parsing_exception`, `illegal_argument_exception` в ES output
3. **Исправить корень**: поправить mapping, фильтры (grok/json), либо валидировать события перед выводом
4. **Повторная обработка**: после фикса прогнать события из DLQ через тестовый/исправленный конвейер. Не оставляйте DLQ расти бесконтрольно

### Алертинг: минимальный prod-чек-лист

Основан на `_node/stats/pipelines` + Monitoring API. Критерии для алертов (ориентиры, подгонять под нагрузку):

| Метрика | Триггер | Приоритет | Действие |
|---|---|---|---|
| **`queue_persisted_growth_events`** (тренд 5–15 мин) | > 0 стабильно | **Критический** | Проверить output (ES/Kafka), backpressure, worker_utilization. Риск переполнения PQ. |
| **`queue.size` / `queue.max_bytes`** | > 70–80% | **Высокий** | Резко растёт лаг. Увеличить ёмкость/узлы или снизить входящий поток. |
| **`flow.worker_utilization`** | > 0.9 (длительно) | **Высокий** | Конвейер на пределе. Рассмотреть увеличение workers/batch.size (с осторожностью) или масштабирование. |
| **DLQ размер** | Рост > X МБ/ч или > порога | **Средне-высокий** | Найти и исправить причину (mapping/валидация). |
| **`events.queue_push_duration_in_millis`** | Резкий рост vs базовый | **Средне-высокий** | Проблема с I/O диска под PQ (медленный диск/перегрузка). |
| **`events.out` < `events.in` (тренд)** | Длительный разрыв | **Высокий** | Output не справляется. Смотреть логи output-плагина, здоровье целевой системы. |
