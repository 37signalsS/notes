# Logstash

> Эта заметка является частью обзора [ELK стека](../elk_stack_overview.md) и служит основной точкой входа для изучения Logstash.

## Определения

**Logstash** — это серверный конвейер обработки данных (Dataflow Engine), который позволяет принимать, обрабатывать и отправлять данные из множества источников в рамках Elastic Stack.

## Основные концепции

### Ключевые характеристики

- **Модульность:** Функциональность расширяется с помощью плагинов. Практически все в Logstash является плагином (вводы, фильтры, выводы, кодеки).
- **Масштабируемость и отказоустойчивость:** Logstash может работать в кластере. Он не хранит данные постоянно, но может использовать персистентную очередь на диске для предотвращения потери сообщений при сбоях.
- **Централизованная обработка:** Позволяет вынести тяжелые операции по обработке (парсинг, обогащение) с агентов на выделенный пул серверов Logstash.

### Архитектура конвейера (Pipeline)

1. **Input (Ввод):** Описывает, откуда и как получать данные.
2. **Filter (Фильтр):** Опциональная секция для обработки, изменения и обогащения данных.
3. **Output (Вывод):** Описывает, куда отправлять обработанные данные.

#### Input-плагины

- `beats`: Для приема данных от агентов Elastic (Filebeat, Metricbeat и т.д.).
- `kafka`: Чтение из топиков Kafka.
- `file`: Чтение из файлов.
- `syslog`: Прием данных по протоколу Syslog.
- `http`, `tcp`, `udp`: Прием данных по сети.

#### Filter-плагины

- **`grok`**: Мощный инструмент для парсинга неструктурированных текстовых данных. В отличие от регулярных выражений, `grok` использует именованные паттерны, что делает выражения более читаемыми и переиспользуемыми.
- **`dissect`**: Более простой и быстрый способ парсинга структурированных строк на основе разделителей.
- **`mutate`**: Позволяет выполнять общие преобразования: переименование, удаление, добавление полей.
- **`json`**: Парсинг JSON-строк в структуру Logstash.
- **`geoip`**: Обогащение данных геолокационной информацией на основе IP-адреса.
- **`aggregate`**: Агрегация нескольких событий в одно.
- **Маскировка данных**: С помощью фильтров можно исключать или маскировать чувствительные данные (ПДн, номера карт).

#### Output-плагины

- `elasticsearch`: Отправка данных в Elasticsearch (основной сценарий).
- `kafka`: Отправка данных в Kafka.
- `file`: Запись в файл.
- `http`: Отправка данных на HTTP-эндпоинт.
- `s3`: Запись в Amazon S3.
- `zabbix`: Отправка данных в Zabbix (через zabbix trapper).

## Практические сценарии

### Конфигурация

- **`logstash.yml`**: Основной конфигурационный файл для настроек самого Logstash (API, воркеры, пути).
- **`pipelines.yml`**: Определяет, какие конвейеры запускать и где находятся их конфигурации.
- **`*.conf`**: Файлы с описанием логики конвейеров (`input`, `filter`, `output`).
- **`jvm.options`**: Настройки Java Virtual Machine (размер хипа `Xms`, `Xmx`).

### Пример конфигурации для приема от Filebeat

Ниже представлен базовый пример конфигурации Logstash, который настроен для приема логов от Filebeat по протоколу Beats и последующей отправки их в Elasticsearch.

```conf
input {
  beats {
    port => 5044
  }
}

filter {
  # Дополнительная обработка логов при необходимости (например, grok-парсинг, mutate, json)
  # Пример: парсинг JSON, если логи приходят в этом формате
  # json {
  #   source => "message"
  #   target => "json_data"
  # }
}

output {
  elasticsearch {
    hosts => ["http://elasticsearch.example.com:9200"]
    index => "docker-logs-%{+YYYY.MM.dd}"
  }
}
```

### Использование для извлечения метрик из логов

С помощью фильтров (`grok`, `dissect`) Logstash может парсить текстовые логи, извлекать из них числовые значения (например, код ответа из лога Nginx) и преобразовывать их в метрики для дальнейшей агрегации и визуализации. Несмотря на гибкость, этот подход является **самым ресурсоемким** по сравнению с Push- и Pull-моделями сбора метрик.

> Подробное сравнение стратегий сбора метрик: **[Стратегии сбора метрик](../Concepts/Observability_and_Monitoring/observability_overview.md#стратегии-сбора-метрик)**.

## Дополнительная информация

### Производительность и недостатки

- **Ресурсоемкость:** Logstash написан на Java (JRuby) и работает на JVM, что делает его довольно требовательным к CPU и оперативной памяти.
- **Сложность:** Конфигурация и отладка, особенно с использованием `grok`, может быть сложной.

Для детального разбора конвейеров, фильтров и вопросов производительности, см. **[Logstash: Конвейеры, фильтры и производительность](./logstash_pipelines.md)**.

### Сравнение Logstash и Vector

**[Vector](../../Vector/vector_overview.md)** — это высокопроизводительный аналог, написанный на Rust, который также предназначен для сбора, преобразования и маршрутизации логов и метрик.

| Характеристика      | Logstash                               | Vector                                       |
| ------------------- | -------------------------------------- | -------------------------------------------- |
| **Язык**            | JRuby (на JVM)                         | Rust                                         |
| **Производительность** | Низкая                                 | Очень высокая (в разы быстрее Logstash)      |
| **Потребление ресурсов** | Высокое (CPU, RAM)                     | Низкое                                       |
| **Функциональность**  | Очень высокая, огромное число плагинов | Хорошая, но уступает Logstash                |
| **Конфигурация**    | Собственный формат, может быть сложной | TOML, YAML, JSON, более простая и декларативная |
| **Экосистема**      | Зрелая, часть Elastic Stack            | Растущая, сильное сообщество                 |

#### Когда что выбирать?

- **Logstash**:
  - Если вы уже глубоко интегрированы в **Elastic Stack**.
  - Если вам нужна **экзотическая функциональность** или плагин, которого нет в Vector.
  - Если производительность и потребление ресурсов **не являются критическим** фактором.

- **Vector**:
  - Если **производительность и низкое потребление ресурсов** являются главным приоритетом.
  - Для большинства **стандартных сценариев** сбора, обработки и перенаправления логов.
  - Если вам нужна гибкая маршрутизация данных в **различные системы хранения** (не только Elasticsearch).
