# Logstash: Конфигурация, перезагрузка и zero-downtime

**Актуально для:** Logstash 8.17+ / 9.x

## Определения

- **Горячая перезагрузка (Hot reload)** — перехват изменений конфигурации конвейеров (файлы `.conf`) без остановки основного процесса Logstash. Реализуется либо через `config.reload.automatic: true` (автопроверка), либо вручную через сигнал `SIGHUP` (POSIX).
- **`config.reload.automatic`** — опция в `logstash.yml`, при которой Logstash периодически проверяет файлы конфигурации на изменения и при обнаружении валидной новой конфигурации выполняет горячую перезагрузку.
- **SIGHUP** (`kill -HUP <pid>`) — ручной триггер перезагрузки конфигурации конвейеров. Альтернатива автопроверке.
- **Zero-downtime** — минимизация или отсутствие простоя при применении изменений конфигурации: при успешной hot-reload входящие события продолжают обрабатываться, очереди сохраняются (при `queue.type: persisted`).
- **Static settings** — настройки уровня `logstash.yml` (и `jvm.options`), которые **не** подхватываются hot-reload. Для их применения требуется полный перезапуск процесса.
- **`pipeline.recoverable`** — управляет автоматическим восстановлением упавшего конвейера при `config.reload.automatic`. Значения: `false` (по умолчанию — не восстанавливать), `auto` (восстанавливать только если `queue.type: persisted`), `true` (восстанавливать всегда, **риск потерь** при ephemeral-очереди). Требует, чтобы все плагины конвейера были reloadable.

## Предпосылки и предварительная настройка (Prerequisites)

Перед включением hot-reload убедитесь:

1. **`queue.type: persisted` для production.** Hot-reload с memory-очередью **не** гарантирует zero-downtime — события, находившиеся в очереди при остановке старого конвейера, теряются. Дисковая очередь сохраняет события между переключениями конвейеров.
2. **Все плагины конвейера должны быть reloadable.** Некоторые input/output-плагины взаимодействуют с ресурсами ОС, которые нельзя освободить без перезапуска. Их использование блокирует hot-reload. Классический пример — `stdin` (открывает STDIN, не может быть переключён). Проверьте, что в конвейере нет неперезагружаемых плагинов (см. раздел «Ограничения»).
3. **Конфигурация валидна перед включением reload.** Прогоните `logstash -t` до включения `config.reload.automatic`. Невалидная конфигурация при первом reload будет отклонена, но старый конвейер продолжит работать.
4. **Достаточно места под `path.data`** для дисковой очереди (при `queue.type: persisted`). При hot-reload PQ не очищается — старые данные остаются до обработки новым конвейером.
5. **Корректные пути в `path.config` / `pipelines.yml`.** Hot-reload отслеживает только файлы, попадающие в эти пути. Опечатки в путях означают, что изменения не будут замечены.
6. **Конфигурация хранится в `.conf`-файлах.** Inline-конфигурация через `-e` не поддерживает `config.reload.automatic` (опция недоступна при `-e`).

## Основные концепции

### Что именно подхватывается при hot-reload

Горячая перезагрузка затрагивает **только конфигурацию конвейеров**: содержимое файлов `.conf`, подключаемых через `path.config` и `pipelines.yml`. Не подхватываются:

- `logstash.yml` — требует перезапуска
- `jvm.options`, переменные окружения (`LS_*`) — требуют перезапуска
- `logstash.keystore` — изменения Keystore применяются только после перезапуска (Keystore не перечитывается по SIGHUP; см. [Logstash Production](./logstash_production.md))

Автоматическая перезагрузка TLS-файлов (`ssl.reload.automatic`) существует в Logstash 9.5+ и требует `config.reload.automatic: true`.

### Механика перезагрузки

1. Logstash отслеживает изменения в файлах, указанных в `path.config`/`pipelines.yml`. Интервал проверки — `config.reload.interval` (по умолчанию `3s`; в `logstash.yml` значение указывается с единицей измерения, напр. `3s`).
2. При обнаружении изменений вычисляется новая конфигурация. Выполняется **валидация** новой конфигурации.
3. Если новая конфигурация **валидна** — старые конвейеры останавливаются «мягко», новые запускаются. При `queue.type: persisted` события, находившиеся в очереди на момент reload, остаются в дисковой очереди и будут обработаны новым экземпляром конвейера (zero-downtime для сохраненных событий).
4. Если новая конфигурация **невалидна** — текущие конвейеры продолжают работать без изменений. Ошибки валидации попадают в логи Logstash.

### Автоматическое восстановление упавших конвейеров (`pipeline.recoverable`)

Когда `config.reload.automatic: true` включён, Logstash может автоматически перезапускать конвейер, который **упал по вине конфигурации/плагина** (например, исключение в Ruby-коде фильтра), вместо того чтобы оставаться без конвейера до ручного перезапуска. Параметр `pipeline.recoverable` управляет этим поведением:

| Значение | Поведение | Риск |
|---|---|---|
| **`false`** (по умолчанию) | Упавший конвейер **не** восстанавливается. Logstash продолжает работать без него. Требует ручного вмешательства. | Нет риска потерь, но есть простой. |
| **`auto`** | Восстанавливает конвейер **только если** `queue.type: persisted`. | Безопасно: PQ сохраняет события, восстановленный конвейер продолжает обработку с диска. |
| **`true`** | Восстанавливает **всегда**, даже при `queue.type: memory`. | **Риск потерь**: при ephemeral-очереди и падении inflight-события теряются. Используйте осознанно. |

**Требование:** все плагины в конвейере должны быть reloadable (иначе восстановление не сработает). При несовместимости Logstash логирует предупреждение при старте.

**Семантика at-least-once при восстановлении:** конвейер, упавший во время обработки батча, может повторно обработать те же события, которые уже были отправлены в output (если output не поддерживает идемпотентность — возможны дубли). Это неизбежное следствие at-least-once-семантики PQ.

### Отличие hot-reload от полного рестарта

| Критерий | `config.reload.automatic` / `SIGHUP` | Полный рестарт (`systemctl restart` / `kill` + запуск) |
|---|---|---|
| **Что меняется** | Только `.conf`/`pipelines.yml` | Всё: `logstash.yml`, JVM, плагины, окружение |
| **Влияние на PQ (persisted)** | Минимальное. Дисковая очередь сохраняется между перезапусками конвейеров. События в очереди/«inflight» при корректной остановке не теряются (at-least-once). | Требует корректного `drain`. При `pipeline.unsafe_shutdown: false` Logstash пытается дождаться завершения; при экстренном/нештатном завершении возможны потери inflight-событий. |
| **Время простоя** | ~0 при успешной валидации (concurrency-модель переключения конвейеров) | Зависит от старта JVM, инициализации плагинов, восстановления PQ |
| **Когда применять** | Изменение фильтров/input/output-плагинов, условий, grok-паттернов, добавление/удаление веток конвейера | Изменение `queue.type`, `pipeline.workers`, `pipeline.batch.size`, `heap`, TLS глобальные настройки, обновление Keystore |

### Поведение очередей при hot-reload

- **`queue.type: memory`** — ин-мемори очередь теряется при остановке старого конвейера. Hot-reload в этом случае **не** zero-downtime: события, ещё не отправленные в output, могут быть потеряны. Для продакшена крайне не рекомендуется без веской причины.
- **`queue.type: persisted`** — события хранятся на диске. При мягком переключении конвейеров после успешного reload старый конвейер корректно останавливается, а новый подхватывает дисковую очередь. При штатном hot-reload потерь не ожидается.
- **Inflight-события** — при успешном hot-reload Logstash дожидается завершения обработки батчей старого конвейера в рамках корректного останова (soft shutdown) перед полным переключением, сохраняя at-least-once-семантику.

## Практические сценарии

### Включение автоматической перезагрузки

В `/etc/logstash/logstash.yml`:

```yaml
config.reload.automatic: true
config.reload.interval: 3s        # интервал проверки (3s — дефолт)
```

Проверка конфигурации **до перезапуска** сервиса:

```bash
sudo /usr/share/logstash/bin/logstash --path.settings /etc/logstash -t
```

После успешной проверки можно перезапустить Logstash (только для применения изменений в `logstash.yml`) или сразу включить автоматический reload.

### Ручной reload через SIGHUP

Узнать PID Logstash:

```bash
systemctl show --property MainPID --value logstash
# или
pgrep -a logstash | head -1
```

Отправить сигнал:

```bash
sudo kill -HUP $(pgrep -x logstash)
```

В логах при успешном reload должно появиться что-то вроде:

```text
[INFO ][logstash.runner          ] Reloading pipeline {"pipeline.id"=>"main"}
[INFO ][logstash.pipeline        ] Pipeline "main" is configured correctly
[INFO ][logstash.pipeline        ] Pipeline started {"pipeline.id"=>"main"}
```

При невалидной конфигурации reload **не** применяется, логи содержат `[ERROR]` с причиной, старый конвейер продолжает работу.

### Проверка валидности без запуска

Используйте `-t` (`--config.test_and_exit`) в CI и перед деплоем:

```bash
/usr/share/logstash/bin/logstash --path.settings /etc/logstash -t
# Docker пример
docker run --rm -v $(pwd)/config:/usr/share/logstash/config logstash:9.5.5 -t
```

**Важно:** `-t` проверяет синтаксис и базовую валидность конфигурации (разбор `.conf`, корректность синтаксиса Ruby-выражений в условиях), но **не** проверяет:
- Корректность grok-паттернов во всех комбинациях с реальными данными
- Работоспособность lookup-плагинов (`elasticsearch`, `memcached` и др.) в момент проверки
- Доступность внешних ресурсов
- Логику условий, приводящую к ошибкам при реальной обработке

### Zero-downtime деплой конфига

Типовой подход для продакшена:

1. **Валидация в CI**: `logstash -t` на PR с изменением `.conf`
2. **Тест на staging**: прогон с репрезентативными образцами событий (smoke-тест пайплайна). Можно через `stdin` + `stdout { codec => rubydebug }` локально либо через тестовый пайплайн на стейдже
3. **Деплой файлов**: скопировать новую конфигурацию на узел(ы) Logstash (rsync/ansible/config-manager)
4. **Проверка перед применением**: `logstash -t` на целевом узле (быстрая проверка)
5. **Применение**: `kill -HUP <pid>` либо дождаться срабатывания `config.reload.automatic`. При нескольких узлах применять поштучно с проверкой метрик
6. **Проверка после reload**: мониторинг `_node/stats/pipelines`, логи, отсутствие роста DLQ, сравнение `events.in/out`

### Диагностика проблем reload

| Симптом | Возможная причина | Решение |
|---|---|---|
| **Reload не срабатывает при изменении файла** | `config.reload.automatic: false`, неверный `path.config`, файл не попадает под отслеживание | Включить `config.reload.automatic: true`, проверить пути в `pipelines.yml`/`logstash.yml`, убедиться что изменения реально сохранены (mtime) |
| **Reload падает, старый пайплайн продолжает работать** | Синтаксическая ошибка в новой конфигурации, неверный `patterns_dir`, конфликт плагинов | Смотреть логи на предмет `[ERROR]` при reload, проверить `logstash -t`, откатить конфиг |
| **После reload очередь не растёт, но события не выходят** | Ошибка в фильтрах новой конфигурации, приводящая к блокировке батча | Проверить логи, временно откатить, прогнать smoke-тест с теми же событиями |
| **События теряются при reload (memory queue)** | `queue.type: memory` | Перевести на `queue.type: persisted`. При memory-очереди hot-reload **не** гарантирует zero-downtime |

### Ограничения и граничные случаи

**Неперезагружаемые плагины.** Input и output-плагины взаимодействуют с ресурсами ОС, которые нельзя освободить без перезапуска. При обнаружении такого плагина в конвейере hot-reload **блокируется** — конфигурация не будет перезагружена, а Logstash логирует причину. Классические примеры:
- **`stdin`** — открывает STDIN, не может быть переключён.
- Плагины, держащие открытые сокеты/файловые дескрипторы без корректного `close` при остановке.
- Плагины, использующие глобальное состояние (например, кэши на уровне плагина, не сбрасываемое при остановке).

**Проверка:** перед включением `config.reload.automatic` убедитесь, что все плагины в конвейере поддерживают reload. В логах при старте с `config.reload.automatic: true` и неперезагружаемым плагином появится предупреждение.

**Inline-конфигурация.** `-e "input { ... }"` не поддерживает `config.reload.automatic`. Опция игнорируется, если конфигурация задана через `-e`.

**`config.reload.interval` и деградация производительности.** Интервал проверки — `3s` по умолчанию. Слишком маленький интервал (например, `1s`) увеличивает частоту статусных проверок файлов (inotify), но сам по себе не влияет на throughput. Слишком большой — задержка между изменением и применением. Значение `3s` — разумный компромисс.

**Hot-reload и плагины с состоянием.** Плагины, хранящие состояние в памяти (например, `aggregate`, кэши, словари `translate`), при переключении конвейера **теряют это состояние** — новый экземпляр начинает с чистого состояния. Это может привести к временной потереше функциональности (например, неправильной агрегации) или изменению поведения. Выносите состояенные плагины в отдельные конвейеры или используйте Pipeline-to-Pipeline.

**Hot-reload и `pipeline.workers` / `pipeline.batch.size`.** Эти параметры задаются в `pipelines.yml` или `logstash.yml`. Изменение их через hot-reload **не** влияет на текущие воркеры — они перезапускаются как часть переключения конвейера, но общий процесс JVM остаётся. При изменении `pipeline.workers` в `pipelines.yml` новое значение применяется при следующем reload.

**Hot-reload и TLS.** `ssl.reload.automatic` (Logstash 9.5+) требует `config.reload.automatic: true`. Автоматическая перезагрузка сертификатов может увеличивать потребление inotify-слотов (watch) — при большом количестве TLS-файлов следите за лимитами ОС.

**Hot-reload и `logstash.keystore`.** Keystore **не** перечитывается при hot-reload. Изменения в `logstash.keystore` применяются только после полного перезапуска. Секреты в `.conf`-файлах через `${VAR}` остаются working — они читаются при старте каждого конвейера из Keystore, но сам Keystore не перечитывается.

**Hot-reload и `pipeline.unsafe_shutdown`.** При `true` Logstash может завершиться мгновенно без ожидания обработки батчей. Hot-reload не влияет на это поведение, но при переключении конвейеров старый конвейер всё равно останавливается «мягко» (soft shutdown), если это возможно.

**Hot-reload и multiple pipelines.** При `pipelines.yml` с несколькими конвейерами reload переключает **все** конвейеры одновременно. Если один конвейер невалиден — reload не применяется ни для одного (атомарность). Откатить можно только полным перезапуском.

## Лучшие практики (Best Practices)

1. **Для production — только `queue.type: persisted` + `config.reload.automatic: true`.** Дисковая очередь даёт zero-downtime при reload и защиту от потерь. Memory-очередь делает hot-reload бессмысленным с точки зрения сохранности.
2. **`pipeline.recoverable: auto` при `queue.type: persisted`.** Позволяет Logstash автоматически восстанавливать упавшие конвейеры без простоя. `true` — только осознанно, с пониманием риска потерь при ephemeral-очереди.
3. **Проверяйте конфигурацию `logstash -t` перед каждым изменением.** Это быстрая проверка синтаксиса. Не она заменяет smoke-тест на реальных данных, но ловит опечатки до деплоя.
4. **Деплой поштучно, с проверкой метрик.** При нескольких узлах Logstash применять `kill -HUP` на один узел, ждать `_node/stats/pipelines`, проверять отсутствие роста DLQ и `events.in/out`, потом следующий. При `config.reload.automatic` можно дать интервалу сработать, но при критичных изменениях — ручной control.
5. **Следите за отсутствием неперезагружаемых плагинов.** `stdin` и подобные блокируют hot-reload. Если конвейер их использует — reload не сработает, и это будет выглядеть как «reload не срабатывает».
6. **Состояственные плагины выносите в отдельные конвейеры.** `aggregate`, `translate`, кэши теряют состояние при переключении конвейера. Используйте Pipeline-to-Pipeline для изоляции.
7. **Keystore обновляйте через полный перезапуск.** Hot-reload не перечитывает `logstash.keystore`. Планируйте окна для обновления секретов отдельно от изменений `.conf`.
8. **`config.reload.interval: 3s` — разумный дефолт.** Не снижайте без причины: частые проверки добавляют накладные расходы на inotify, но не влияют на throughput.
9. **Валидируйте TLS-файлы отдельно.** `ssl.reload.automatic` требует `config.reload.automatic: true` и следит за изменением сертификатов. При большом количестве TLS-файлов контролируйте inotify-лимиты ОС (`/proc/sys/fs/inotify/max_user_watches`).
10. **Для burst-трафика и непредсказуемых изменений — `config.reload.automatic: true`.** Ручной `SIGHUP` подходит для контролируемых деплоев; автоматический — для сред с частыми правками конфигурации.
