# Практическое руководство: Построение отказоустойчивого конвейера логов с Fluent Bit, Kafka, Vector и OpenSearch

Это руководство описывает архитектуру и практические шаги для создания масштабируемого и надежного конвейера для сбора, обработки и хранения логов, основанного на реальном сценарии.

## 1. Проблема: Потеря логов в высоконагруженных системах

В стандартной архитектуре сбора логов, где легковесный агент (например, **Fluent Bit**) отправляет данные напрямую в хранилище (например, **Elasticsearch** или **OpenSearch**), существует серьезный риск потери данных.

Причины:
*   **Противодавление (Back-pressure)**: Если хранилище перегружено и не может обрабатывать входящий поток логов с достаточной скоростью, оно начинает отвечать медленнее или временно отказывать в приеме данных.
*   **Переполнение буфера агента**: У Fluent Bit есть внутренний буфер для обработки временных сбоев. Однако этот буфер ограничен в размере. При длительной недоступности или медленной работе хранилища буфер переполняется, и агент начинает отбрасывать новые логи.

Результат: вы теряете критически важные данные, которые могут быть необходимы для отладки, анализа безопасности или мониторинга.

## 2. Решение: Архитектура с асинхронной буферизацией

Для решения этой проблемы внедряется промежуточный, персистентный буфер на базе **Apache Kafka**.

**Схема конвейера:**

`Fluent Bit` -> `Kafka` -> `Vector` -> `OpenSearch`

### Роли компонентов:

1.  **[Fluent Bit](../../Kubernetes/MonitoringLogging/EFK/fluentbit/fluent_comparison.md)**:
    *   **Роль**: Легковесный агент-сборщик.
    *   **Задача**: Устанавливается на всех узлах. Собирает логи с хостов и из контейнеров Kubernetes. Минимально обрабатывает их (добавляет метаданные) и максимально быстро отправляет в Kafka.

2.  **[Apache Kafka](../../Kafka/kafka_for_monitoring.md)**:
    *   **Роль**: Отказоустойчивый, персистентный буфер.
    *   **Задача**: Принимает на себя весь входящий поток логов. "Сглаживает" пиковые нагрузки. Если последующие компоненты (Vector, OpenSearch) недоступны, Kafka надежно хранит данные на диске, предотвращая их потерю.

3.  **[Vector](../../../Vector/vector_overview.md)**:
    *   **Роль**: Агрегатор, трансформер, роутер.
    *   **Задача**: Выступает в качестве "моста" между Kafka и OpenSearch.
        *   **Читает** данные из топиков Kafka (то, что не умеет Fluent Bit).
        *   **Трансформирует** данные "на лету": парсит JSON, преобразует форматы полей, удаляет ненужную информацию.
        *   **Решает проблему совместимости**: Заменяет точки на подчеркивания в именах полей (`kubernetes.labels` -> `kubernetes_labels`), что критически важно для корректной индексации в OpenSearch.
        *   **Отправляет** обработанные данные в OpenSearch.

4.  **[OpenSearch](../OpenSearch/opensearch_overview.md)**:
    *   **Роль**: Долгосрочное хранилище и аналитический движок.
    *   **Задача**: Индексирует полученные от Vector логи и предоставляет мощные инструменты для полнотекстового поиска, агрегации и визуализации через OpenSearch Dashboards.

## 3. Ключевые моменты конфигурации

### Fluent Bit: Отправка в Kafka

Ключевая часть — настройка `[OUTPUT]` для отправки логов в разные топики Kafka в зависимости от их тега.

*См. практический пример в [Буферизация и маршрутизация в Fluent Bit](../../Kubernetes/MonitoringLogging/EFK/fluentbit/buffering_routing.md#сценарий-4-отправка-логов-в-kafka-для-буферизации).*

### Vector: Трансформация данных из Kafka

Это самый важный этап обработки. Vector использует язык **VRL (Vector Remap Language)** для сложных преобразований.

*См. подробный разбор конфигурации и VRL-скрипта в [Обзоре Vector](../../../Vector/vector_overview.md#23-практический-сценарий-роутер-логов-из-kafka-в-opensearch).*

## 4. Выводы

Данная архитектура обеспечивает:
*   **Надежность**: Гарантированная доставка логов даже при сбоях или перегрузках компонентов.
*   **Масштабируемость**: Каждый компонент может масштабироваться независимо. Можно добавлять больше брокеров Kafka, партиций в топиках или экземпляров Vector для увеличения пропускной способности.
*   **Гибкость**: Централизованная обработка в Vector позволяет легко изменять логику парсинга и обогащения, не трогая конфигурацию агентов на тысячах хостов.
*   **Производительность**: Агенты на хостах выполняют минимум работы, что снижает их влияние на производительность основных приложений.
