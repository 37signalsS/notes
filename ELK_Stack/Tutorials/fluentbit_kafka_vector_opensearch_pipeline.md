# Руководство: Построение отказоустойчивого конвейера логов (Fluent Bit, Kafka, Vector, OpenSearch)

> Данное руководство описывает архитектуру и практические шаги по созданию масштабируемого конвейера сбора, обработки и хранения логов.
>
> Базовые понятия: [Fluent Bit](../../Kubernetes/MonitoringLogging/EFK/fluentbit/fluent_comparison.md), [Kafka](../../Kafka/kafka_overview.md), [Vector](../../Vector/vector_overview.md), [OpenSearch](../OpenSearch/opensearch_overview.md).

## Определения

* **Конвейер логов (Logging Pipeline)**: последовательность компонентов для сбора, трансформации и доставки логов. Типовая схема: `Агент → Буфер → Агрегатор → Хранилище`.
* **Асинхронная буферизация**: механизм защиты от потери данных путем использования промежуточного персистентного хранилища (Kafka) между отправителем и получателем.
* **Противодавление (Backpressure)**: состояние системы, при котором принимающий компонент не успевает обрабатывать входящий поток данных, что приводит к необходимости замедления или блокировки отправителя для предотвращения потери данных.

## Основные концепции

### Проблема: Потеря данных в высоконагруженных системах

При прямой отправке логов из агента в хранилище (например, `Fluent Bit → OpenSearch`) возникают следующие риски:

* **Ограниченность локального буфера**: внутренний буфер агентов сбора данных (Fluent Bit) имеет лимит. При длительной недоступности хранилища буфер переполняется, и новые логи начинают отбрасываться.
* **Отсутствие гарантий при пиковых нагрузках**: резкий всплеск количества логов может привести к отказу хранилища или замедлению индексации, что вызывает каскадный сбой всей системы сбора.

### Решение: Архитектура с Kafka в качестве буфера

Использование Apache Kafka как промежуточного слоя позволяет разделить процессы генерации и потребления логов (Decoupling).

**Схема конвейера:**
`Fluent Bit → Kafka → Vector → OpenSearch`

### Роли компонентов в конвейере

| Компонент | Роль | Основная задача |
| :--- | :--- | :--- |
| **Fluent Bit** | Агент-сборщик | Сбор логов с хостов и контейнеров Kubernetes, обогащение метаданными, отправка в Kafka |
| **Kafka** | Персистентный буфер | Прием потока логов, сглаживание пиковых нагрузок, хранение данных на диске до момента их обработки |
| **Vector** | Агрегатор и трансформер | Чтение данных из Kafka, парсинг (VRL), фильтрация, маршрутизация и отправка в OpenSearch |
| **OpenSearch** | Хранилище | Индексация, полнотекстовый поиск и визуализация данных |

### Преимущества архитектуры

* **Отказоустойчивость**: данные сохраняются в Kafka даже при временной недоступности хранилища или агрегатора.
* **Масштабируемость**: каждый компонент можно масштабировать независимо (увеличение партиций в Kafka, запуск дополнительных инстансов Vector).
* **Гибкость обработки**: Vector позволяет выполнять сложную трансформацию данных в централизованном слое без изменения конфигурации сотен агентов сбора.

## Практические сценарии

### Настройка маршрутизации в Fluent Bit

Для обеспечения отказоустойчивости на стороне агента настраивается отправка в топики Kafka. Важно использовать теги для разделения потоков данных.

> Пример настройки выходных плагинов и управления буферизацией приведен в заметке [Буферизация и маршрутизация в Fluent Bit](../../Kubernetes/MonitoringLogging/EFK/fluentbit/buffering_routing.md).

### Трансформация данных в Vector

Vector потребляет данные из Kafka и выполняет их обработку перед индексацией. Для преобразований используется язык **VRL (Vector Remap Language)**.

Типовые операции трансформации:

* Преобразование форматов (например, из неструктурированного текста в JSON).
* Переименование полей для соответствия схеме (например, `labels` → `kubernetes_labels`).
* Удаление конфиденциальных данных (Masking).
* Маршрутизация в разные индексы OpenSearch на основе метаданных.

> Описание синтаксиса VRL и примеры конфигурации консьюмеров доступны в [Обзоре Vector](../../Vector/vector_overview.md).

## Дополнительная информация

### Мониторинг и эксплуатация

* **Контроль лага (Consumer Lag)**: критически важная метрика для Kafka. Высокий лаг означает, что Vector не успевает обрабатывать входящие логи.
* **Производительность**: для повышения пропускной способности рекомендуется увеличивать количество партиций в топиках Kafka и использовать горизонтальное масштабирование Vector.
* **Безопасность**: обязательная настройка TLS между всеми компонентами, использование SASL/SCRAM для аутентификации в Kafka и RBAC (Role-Based Access Control) в OpenSearch.
