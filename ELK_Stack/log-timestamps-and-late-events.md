# Логи: временные метки, запоздавшие события и рассинхрон часов

**Актуально для:** Elastic Stack 9.5.x / 8.19 LTS

## Определения

*   **`@timestamp`** — основное поле времени события в ECS (тип `date`). По смыслу ECS — момент **происхождения** события: время из записи источника, а если источник времени не дал — момент первичного получения пайплайном. Используется как time field дата-вью логов: фильтры «последние 15 минут», сортировка в Discover, корзины на дашбордах, ретеншн по времени.
*   **`event.created`** — момент, когда агент или пайплайн **впервые увидели** событие (не следует путать с временем самого события — это `@timestamp`). Разность `event.created - @timestamp` — задержка от происхождения до первого чтения; если значения совпадают, используется `@timestamp`.
*   **`event.ingested`** — момент, когда событие было принято на индексацию в Elasticsearch (ECS: «arrived in the central data store»). Заполняется из метаданных ingest (`_ingest.timestamp`) процессором `set`. В нормальных условиях, без вмешательства в событие, ECS ожидает хронологию `@timestamp` < `event.created` < `event.ingested`.
*   **`_ingest.timestamp`** — служебное поле ingest-пайплайна: время, когда Elasticsearch получил запрос на индексацию данного документа. В индекс не попадает само по себе — только через явный `set`.
*   **Late arrival (запоздавшее событие)** — событие, попавшее в стек позже, чем произошло: из-за буферизации агента, недоступности сети/ES, долгих ретраев, ручного до-догоняющего импорта.
*   **Out-of-order (переупорядоченность)** — когда события в источнике/потоке приходят не по возрастанию времени: потоки из нескольких нод, чтение нескольких файлов, конкурирующие писатели.
*   **Clock skew (дрейф часов)** — расхождение системных часов разных хостов; в логах выглядит как «событие из будущего» или «из прошлого» относительно `event.ingested`.

## Основные концепции

### Кто и когда проставляет время

Смысловые слои одного события (сторона «раньше» → «позже»; хронологический порядок полей — типовое ожидание ECS):

```
время события (источник)  →  первое чтение агентом/пайплайном  →  момент приёма в Elasticsearch
      @timestamp                 event.created                        event.ingested
```

Практические источники значения `@timestamp`:

*   **Filebeat (filestream)** — пока время из строки не извлечено парсером, в `@timestamp` попадает момент **чтения/получения** события, а не время из её содержимого. Если в строке есть собственное время (формат приложения, syslog-заголовок), его нужно разобрать явно (парсер входа, процессор `timestamp` или `date` на приёме) — иначе события уйдут со временем чтения. Процессор `timestamp` разбирает указанное поле по `layouts` (Go-форматы плюс `UNIX`/`UNIX_MS`; параметр обязателен), по умолчанию пишет результат в `@timestamp` (`target_field`), `timezone` по умолчанию UTC, а опция `test` проверяет успешность парсинга ещё при загрузке конфигурации.
*   **Logstash, фильтр `date`** — разбирает строку по заданному формату и **перезаписывает** `@timestamp` временем из лога; при неудаче парсинга на событие вешается тег `_dateparsefailure` (см. [Logstash: Входы и выходы](Logstash/logstash_inputs_outputs.md)).
*   **Elasticsearch, ingest-процессор `date`** — аналогично на приёме, включая выбор целевого поля и зоны времени (см. [Ingest Pipelines, «Работа с датами»](Elasticsearch/elasticsearch_ingest_pipelines.md)).
*   **Различные входы** (syslog, journald, container-входы) могут разбирать штатные заголовки времени источника — проверяйте фактическое поведение своего входа на тестовом событии (`GET <index>/_search`).

Правило: **`@timestamp` должен описывать событие, а не момент доставки**. Время доставки — это `event.ingested`; когда оба нужны, они разнесены по разным полям.

### Что ломают запоздавшие события и дрейф часов

1.  **Временные фильтры Kibana.** Дашборд «за последние 15 минут» отсекает по `@timestamp`. Событие, произошедшее 20 минут назад, но доставленное сейчас, в окно «now-15m» уже не попадёт — оно появится при расширении окна, «назад во времени».
2.  **Сортировка и водопады логов.** Discover сортирует по `@timestamp DESC`; запоздавшие события вставляются «в середину» уже просмотренного диапазона. Порядок одинаковых `@timestamp` между собой не детерминирован — для стабильной сортировки добавляйте вторичное поле (`event.ingested`, `log.offset`).
3.  **Индексация по дате события.** При маршрутизации документов в индекс по дате (`date_index_name` в ingest, шаблоны индексов с датой в имени) запоздавшее событие попадёт в **старый** индекс: пока он записываем — это корректно (данные догоняют), если же индекс закрыт/удалён по ретеншну — документ будет отклонён или уйдёт не туда. Форматирование даты под имя индекса описан в [Ingest Pipelines](Elasticsearch/elasticsearch_ingest_pipelines.md).
4.  **Дрейф часов искажает вычисляемые интервалы.** `event.ingested - @timestamp` на хосте с отстающими часами станет отрицательным (событие «из будущего»); на хосте с опережающими — аномально большим. Распределение этой разности — основной способ найти нездоровые хосты (сценарий 2).
5.  **Переупорядоченность на источнике.** Агрегаты «по времени прихода» и мониторинг задержки доставки считают по фактическому порядку — переупорядоченные потоки дают шум. Порядок записи в Elasticsearch определяется моментом приёма bulk-запроса, а не `@timestamp`: окончательный порядок задаётся **только на чтении** (сортировкой).

### Поздние события и data streams

Обычный data stream принимает документы в свой write-индекс независимо от значения `@timestamp`: само по себе «старое» событие — не ошибка индексации. Исключение — **TSDS** (`index.mode: time_series`): туда документ уходит в backing-индекс, чей временной диапазон покрывает его `@timestamp`, поэтому попадание в нужный временной слот обеспечивает сам `@timestamp`. Подробности режимов индексации — в [Mapping и индексации](Elasticsearch/elasticsearch_mapping_and_indexing.md).

## Практические сценарии

Предварительные требования: доступ к Elasticsearch с кластерной привилегией `manage_pipeline` (создание пайплайнов — сценарии 1 и 3) и правом чтения целевых индексов (сценарии 2 и 4); доступ к конфигурации агента/Logstash; право настройки NTP на хостах (сценарий 5).

### 1. Записывать `event.ingested` для всех документов

```bash
curl -s -u elastic:$PASS -k -X PUT "$ES/_ingest/pipeline/ecs-ingested?pretty" -H 'Content-Type: application/json' -d '{
  "processors": [
    {
      "set": {
        "field": "event.ingested",
        "value": "{{{_ingest.timestamp}}}"
      }
    }
  ]
}'
# → {"acknowledged":true}
```

Привязка пайплайна: `POST <index>/_doc?pipeline=ecs-ingested`, через `default_pipeline` в шаблоне индекса или на стороне шлюза (Logstash `pipeline => "ecs-ingested"`). Теперь у каждого документа есть обе точки отсчёта.

### 2. Найти хосты с дрейфом часов (ES|QL)

```esql
FROM logs-*
| WHERE event.ingested IS NOT NULL AND @timestamp IS NOT NULL
| EVAL lag = DATE_DIFF("second", @timestamp, event.ingested)
| STATS max_lag = MAX(lag), min_lag = MIN(lag) BY host.name
| SORT max_lag DESC
| LIMIT 20
```

Интерпретация: `min_lag < 0` — хост «из будущего» (опережает), устойчиво отрицательные значения — претензия к NTP; аномально большие `max_lag` — либо сбой доставки (буфер/ретраи), либо часы сильно отстают. Запрос выполняется через `POST /_query` — см. [ES|QL](Elasticsearch/esql-query-language.md). В многоступенчатых конвейерах (агент → шлюз/Logstash → Elasticsearch) разность раскладывается на два отрезка: `event.created - @timestamp` — задержка от происхождения до первого чтения агентом (по ECS — мониторинг способности агента/пайплайна угнаться за источником), а `event.ingested - event.created` — задержка транспорта и приёма.

### 3. Извлечь время из строки лога, а не из момента чтения

```bash
curl -s -u elastic:$PASS -k -X PUT "$ES/_ingest/pipeline/parse-app-time?pretty" -H 'Content-Type: application/json' -d '{
  "processors": [
    {
      "date": {
        "field": "app.ts",
        "target_field": "@timestamp",
        "formats": ["yyyy-MM-dd'T'HH:mm:ss.SSSXXX", "ISO8601"],
        "timezone": "UTC",
        "on_failure": [
          { "tag": "date-fail" }
        ]
      }
    }
  ]
}'
# → {"acknowledged":true}
```

Если разобрать не удалось — событие не выбрасываем: оставляем исходное значение (например, в `message` или `app.ts`) и вешаем тег `date-fail`; момент приёма при этом уже зафиксирован в `event.ingested` (сценарий 1), а исходное значение времени остаётся в `app.ts` для ручного разбора. Полный разбор дат и `date_index_name` — в [Ingest Pipelines](Elasticsearch/elasticsearch_ingest_pipelines.md); эквивалент на стороне Logstash — фильтр `date` ([Logstash: Входы и выходы](Logstash/logstash_inputs_outputs.md)). Детали процессора: `output_format` по умолчанию `yyyy-MM-dd'T'HH:mm:ss.SSSXXX`; `@timestamp` с маппингом `date` индексируется как миллисекунды эпохи, исходный формат и зона сохраняются в `_source`.

### 4. Верифицировать фактический `@timestamp` входа

```bash
# отправить тестовую строку с заведомо старым временем, затем:
curl -s -u elastic:$PASS -k "$ES/logs-*/_search?pretty" -H 'Content-Type: application/json' -d '{
  "size": 1,
  "sort": [{"@timestamp": "desc"}],
  "query": {"match": {"message": "TESTMARKER-2023"}}
}'
```

Сравните `@timestamp` документа с временем в строке: совпадают — вход парсит время сам; отличаются — `@timestamp` это момент чтения, нужен сценарий 3.

### 5. NTP как первая линия обороны

Без синхронизации часов «корректное время» в логах невозможно в принципе:

```bash
timedatectl status
# → System clock synchronized: yes   (иначе: timedatectl set-ntp true)
chronyc tracking   # для chrony: Reference ID, System clock offset
```

Настройка NTP/chrony в контексте стенда — в [Tutorials: Cluster Setup](Tutorials/cluster_setup.md). Помните: контейнеры делят часы хоста — чинить надо хост, а не под.

## Устранение неполадок

| Симптом | Вероятная причина | Действие |
|---|---|---|
| Событие не видно на дашборде, но в индексе есть | `@timestamp` старее окна фильтра | Расширить окно; для «догоняющих» загрузок использовать `event.ingested` как временную шкалу доставки |
| `@timestamp` совпадает с моментом чтения, а не из строки | Вход не парсит время строки | Сценарий 3 (`date`-процессор) или фильтр `date` в Logstash |
| Тег `_dateparsefailure` (Logstash) / событие с нетронутой датой | Формат в логе не совпал с шаблоном | Поправить `match`-паттерны; сырое значение сохранить в отдельном поле |
| Событие «из будущего» (`event.ingested < @timestamp`) | Опережающие часы хоста | NTP/chrony на хосте (сценарий 5) |
| Полоса аномальных задержек у одного хоста | Дрейф или локальные буферы агента | ES|QL из сценария 2; проверить агента и NTP |
| Логи в Discover идут не в том порядке | Одинаковые `@timestamp`, нет вторичного ключа | Добавить в сортировку `event.ingested` / `log.offset` |
| Документ отклонён при индексации по дате | Датированный индекс уже закрыт/удалён по ретеншну | Пересмотреть ретеншн/ILM ([ILM и ретеншн](Elasticsearch/elasticsearch_ilm_and_retention.md)), маршрутизацию `date_index_name` |
| После рестарта сервиса события шквалом «в прошлое» | Буфер агента доставился после простоя | Ожидаемо: сортировка — по `@timestamp`, порядок приёма не важен; при необходимости отметить источник тегом |
| События syslog «из будущего» в первые дни года | У локальной метки RFC 3164 (`Jan 23 14:09:01`) нет года и зоны — год достраивается из часов агента | Ожидаемый артефакт парсера `syslog` (`format: rfc3164`), не путать с дрейфом (сценарий 5); для точности — `format: rfc5424` |

## Best Practices

*   **`@timestamp` = время события, `event.ingested` = время приёма.** Разделяйте сразу, иначе невозможно отличить медленный источник от запоздавшей доставки.
*   **Парсьте время из строки явно** на входе (ingest `date` / Logstash `date`) и проверяйте теги ошибок парсинга как часть мониторинга пайплайна.
*   **NTP на всех хостах** — до того, как разбирать «странное время» в логах; дрейф часов порождает проблемы, маскирующиеся под ошибки агентов.
*   **Не считайте по времени прихода то, что важно считать по времени события** — и наоборот: задержка доставки меряется по `event.ingested`, интервалы инцидента — по `@timestamp`.
*   **Вторичный ключ сортировки** для воспроизводимых выборок: `event.ingested`, `log.offset`, sequence-числа источника.
*   **Дашборды «живого» окна** сознательно шире ожидаемой задержки доставки; критичные алерты — по событиям, а не по «данным на экране».
*   **Дрейф-мониторинг** (сценарий 2) включить регулярно: он дешевле, чем разбор каждого инцидента с «неправильным» временем.
