# Grafana Mimir

## 1. Определения

**Grafana Mimir** — это горизонтально масштабируемое, высокодоступное и мульти-тенантное решение для долгосрочного хранения метрик, полностью совместимое с [Prometheus](../Prometheus/overview.md). Проект разработан Grafana Labs как часть интегрированного стека наблюдаемости ([Loki](../Loki/loki_overview.md), [Grafana](../Grafana/grafana_overview.md), [Tempo](../Tempo/index.md), Mimir).

**История:** Mimir является форком и развитием проекта **Cortex**. Grafana Labs взяла Cortex за основу, значительно доработала его и в 2022 году представила как Mimir, сделав его ключевым компонентом своего облачного и on-premise стека. Он появился как современный ответ на растущую популярность альтернативных решений для долгосрочного хранения, таких как [VictoriaMetrics](../VictoriaMetrics/overview.md) и [Thanos](../Prometheus/scaling/thanos_overview.md).

**Mimir 3.0 (ноябрь 2025):** Крупнейшее обновление архитектуры:

- **Декаплированная архитектура** — разделение путей чтения и записи через асинхронный ingest-слой на базе Kafka
- **Mimir Query Engine (MQE)** — новый потоковый движок запросов, снижающий использование памяти до 92%
- **Эффективность** — снижение использования ресурсов до 15%, увеличение пропускной способности

Основная задача Mimir — агрегировать метрики из множества кластеров Prometheus, предоставляя единую точку для глобального запроса данных и решая фундаментальные проблемы масштабирования и долгосрочного хранения, присущие стандартному Prometheus.

## 2. Базовые концепции

### Архитектурная философия

Архитектура Mimir разделяет общие принципы с другими компонентами Grafana Stack ([Loki](../Loki/loki_overview.md), [Tempo](../Tempo/index.md)):

- **Язык:** Все компоненты написаны на **Go**.
- **Режим развертывания:** Может быть запущен как в виде **одного бинарного файла** (монолит) для простых инсталляций, так и в виде набора **горизонтально масштабируемых микросервисов**.
- **Хранилище:** Для долгосрочного хранения данных используется **объектное хранилище** (S3, GCS, MinIO), что делает хранение дешевым и надежным.

### Архитектурные изменения в Mimir 3.0

**Mimir 3.0 (ноябрь 2025)** принес фундаментальные изменения в архитектуру:

| Изменение | Описание | Преимущество |
| :--- | :--- | :--- |
| **Разделение путей чтения/записи** | Асинхронный ingest-слой на базе Kafka | Стабильная скорость запросов при высокой нагрузке на запись |
| **Mimir Query Engine (MQE)** | Потоковый движок выполнения запросов | Снижение использования памяти до 92% |
| **Декаплированная архитектура** | Независимое масштабирование компонентов | Устранение узких мест, повышение отказоустойчивости |

**До Mimir 3.0:** Путь записи и путь чтения были связаны, что приводило к деградации производительности запросов при пиковой нагрузке на ingestion.

**После Mimir 3.0:** Данные принимаются через Kafka, что буферизует нагрузку и позволяет пути чтения работать независимо.

### Основные компоненты

Mimir состоит из набора микросервисов, каждый из которых выполняет свою роль и может масштабироваться независимо:

- **Distributor:** Принимает метрики от Prometheus через `remote_write` API. Валидирует данные, обеспечивает соблюдение лимитов для каждого тенента и направляет их на несколько инжестеров (с репликацией).
- **Ingester:** Получает данные от Distributor, хранит их в памяти в виде временных рядов и периодически "сбрасывает" сжатые блоки данных (TSDB blocks) в объектное хранилище.
- **Querier:** Обрабатывает запросы на языке PromQL. Он запрашивает самые свежие данные у инжестеров, а исторические данные — у компонента `store-gateway`.
- **Query Frontend:** Опциональный, но рекомендуемый компонент для ускорения запросов. Кэширует результаты, разбивает большие запросы на более мелкие и может ставить их в очередь, чтобы избежать перегрузки. Активно использует кэширование (например, с помощью Memcached).
- **Store-Gateway:** "Шлюз" к объектному хранилищу. Он сканирует бакеты на наличие новых блоков данных, загружает их метаданные и предоставляет их запросчикам для выполнения исторических запросов.
- **Compactor:** Оптимизирует блоки данных в объектном хранилище, уплотняя (объединяя) их и удаляя устаревшие данные. Это ускоряет запросы и экономит место.
- **Ruler:** Отвечает за выполнение правил записи (recording rules) и алертов (alerting rules) в формате Prometheus в разрезе каждого тенента.
- **Alertmanager:** Принимает алерты от Ruler, дедуплицирует их, группирует и отправляет в настроенные каналы уведомлений (Slack, PagerDuty и т.д.).

### Ключевые преимущества

- **Горизонтальная масштабируемость:** Все компоненты Mimir можно масштабировать независимо, что позволяет обрабатывать триллионы активных временных рядов.
- **Долгосрочное хранение:** Использует дешевые и надежные объектные хранилища для хранения метрик за длительные периоды (годы).
- **Высокая доступность:** Репликация данных между компонентами (например, тройная репликация между инжестерами) обеспечивает отказоустойчивость и сохранность данных.
- **Мульти-тенатность:** Встроенная поддержка изоляции данных, запросов и лимитов для разных команд или клиентов.
- **Глобальный обзор:** Позволяет выполнять запросы к метрикам со всех ваших Prometheus-серверов в одном месте.

### Ключевые концепции

- **Remote Write API** — стандартный протокол Prometheus для отправки метрик в удалённое хранилище. Подробнее: [Prometheus remote_read_write](../Prometheus/scaling/remote_read_write.md).
- **PromQL** — язык запросов к метрикам, полностью поддерживаемый Mimir. Подробнее: [PromQL functions](../Prometheus/concepts/promql/functions.md).
- **Мульти-тенантность** — изоляция данных через HTTP-заголовок `X-Scope-OrgID`.
- **TSDB Blocks** — сжатые блоки данных временных рядов, хранимые в объектном хранилище. Подробнее: [TSDB concepts](../Prometheus/concepts/tsdb.md).

### Сравнение с альтернативами

**Сравнение производительности (2025):**

| Характеристика | VictoriaMetrics | Thanos | Grafana Mimir |
| :--- | :--- | :--- | :--- |
| **Производительность записи** | 1M+ сэмплов/сек (single-node), 10M+ (cluster) | Ограничена Prometheus, +10% overhead | 500K-2M сэмплов/сек на pod |
| **Задержка запросов (<2ч)** | 20-50ms | 50-100ms | 30-80ms |
| **Задержка запросов (>24ч)** | 100-500ms | 200ms-2s | 150ms-1s |
| **Сжатие данных** | до 10x | 2-4x | 2-3x |
| **Мин. требования VPS** | 2 vCPU, 4GB RAM, 100GB NVMe | 4 vCPU, 8GB RAM, 200GB NVMe | 8 vCPU, 16GB RAM, 300GB NVMe |
| **Мульти-тенантность** | Базовая (tenant ID) | Через external labels | Полная изоляция |
| **Сложность развёртывания** | Низкая (single binary) | Средняя (multiple components) | Высокая (microservices) |

**Архитектурные различия:**

| Решение | Паттерн | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **VictoriaMetrics** | Unified Platform | Простота, агрессивное сжатие (10x), низкие требования к ресурсам | Базовая мульти-тенантность |
| **Thanos** | Sidecar-паттерн | Бесшовная миграция с Prometheus, CNCF-совместимость | Высокая операционная сложность |
| **Grafana Mimir** | Микросервисы | Полная изоляция тенантов, per-tenant rate limiting | Высокие требования к ресурсам, требует Kubernetes |

**Рекомендации по выбору (2025):**

- **VictoriaMetrics:** Приоритет — простота эксплуатации и стоимость, single-tenant или базовая мульти-тенантность, ограниченная экспертиза для распределённых систем.
- **Thanos:** Есть существующая Prometheus-инфраструктура, требуется постепенная миграция без простоев, предпочтение экосистеме CNCF.
- **Grafana Mimir:** Строгие требования к мульти-тенантности и compliance, крупные enterprise-развёртывания с выделенной командой, интеграция с Grafana Enterprise.

## 3. Практические сценарии

### Централизованное хранилище для множества кластеров

1. **Локальные агенты:** В каждом контуре (например, в каждом кластере Kubernetes) разворачивается пара высокодоступных серверов **Prometheus**.
2. **Короткий срок хранения:** Локальные Prometheus настраиваются на очень короткий срок хранения данных (retention period), например, от 2 до 6 часов. Их задача — только собирать метрики и как можно скорее пересылать их дальше.
3. **Пересылка данных:** Каждый Prometheus использует `remote_write` для отправки всех собираемых метрик в единый кластер **Mimir**.
4. **Централизованный анализ:** Кластер Mimir агрегирует данные со всех источников. Для визуализации используется единый **Grafana**, подключенный к Mimir как к основному источнику данных.

Такая архитектура снижает нагрузку на локальные Prometheus, повышает отказоустойчивость (при сбое локального сервера теряются только последние минуты метрик, которые уже были отправлены в Mimir) и предоставляет единую точку для анализа и построения дашбордов по всей инфраструктуре.

### Требования к ресурсам

**Минимальные требования для Mimir (на pod):**

| Компонент | vCPU | RAM | Дисковое пространство |
| :--- | :--- | :--- | :--- |
| **Distributor** | 2 | 4GB | — |
| **Ingester** | 4 | 8GB | Временное (буфер) |
| **Querier** | 4 | 8GB | — |
| **Query Frontend** | 2 | 4GB | — |
| **Store-Gateway** | 4 | 16GB | Кэш метаданных |
| **Compactor** | 4 | 8GB | Временное для компaction |

**Рекомендуемые требования для production (на pod):**

| Компонент | vCPU | RAM | Примечание |
| :--- | :--- | :--- | :--- |
| **Distributor** | 4-8 | 8-16GB | Масштабировать по нагрузке на запись |
| **Ingester** | 8-16 | 16-32GB | Зависит от объёма данных в памяти |
| **Querier** | 8-16 | 16-32GB | Зависит от сложности запросов |
| **Store-Gateway** | 8-16 | 32-64GB | Большой кэш метаданных |

**Объектное хранилище:**

- **S3-совместимое:** Yandex Object Storage, MinIO, Ceph
- **Рекомендуемая пропускная способность:** от 1 Gbps
- **Ретеншн:** Настраивается (обычно 1-5 лет)

### Развёртывание в Kubernetes

**Helm-чарт:** `grafana/mimir`

```bash
# Добавление репозитория
helm repo add grafana https://grafana.github.io/helm-charts
helm repo update

# Установка Mimir (базовая конфигурация)
helm install mimir grafana/mimir \
  --namespace mimir \
  --create-namespace \
  --set minio.enabled=true \
  --set enterprise.enabled=false
```

**Конфигурация `remote_write` в Prometheus:**

```yaml
# prometheus.yml
remote_write:
  - url: http://mimir-distributor.mimir.svc.cluster.local:8080/api/v1/push
    headers:
      X-Scope-OrgID: <tenant-id>
    # Опционально: аутентификация
    # basic_auth:
    #   username: <username>
    #   password: <password>
```

**Конфигурация Grafana (datasource):**

```yaml
# grafana-datasources.yaml
apiVersion: 1
datasources:
  - name: Mimir
    type: prometheus
    url: http://mimir-querier.mimir.svc.cluster.local:9009/prometheus
    access: proxy
    isDefault: true
    jsonData:
      httpMethod: POST
      timeInterval: 1m
```

### Интеграция с Grafana Alloy

**Grafana Alloy** — рекомендуемый агент для сбора и отправки метрик в Mimir (замена Promtail и Grafana Agent):

```alloy
// config.alloy
prometheus.scrape "default" {
  targets = [{"__address__" = "localhost:9090"}]
  forward_to = [prometheus.remote_write.mimir.receiver]
}

prometheus.remote_write "mimir" {
  endpoint {
    url = "http://mimir-distributor.mimir.svc.cluster.local:8080/api/v1/push"
    headers = {
      "X-Scope-OrgID" = "tenant-1"
    }
  }
}
```

Подробнее: [Grafana Alloy](../Grafana/grafana_alloy_overview.md)
