# Grafana Mimir

## Определения

**Grafana Mimir** — это горизонтально масштабируемое, высокодоступное и мульти-тенантное решение для долгосрочного хранения метрик, полностью совместимое с [Prometheus](../Prometheus/overview.md). Проект разработан Grafana Labs как часть интегрированного стека наблюдаемости (Loki, Grafana, Tempo, Mimir).

Mimir является форком и развитием проекта **Cortex**. Grafana Labs взяла Cortex за основу, значительно доработала его и в 2022 году представила как Mimir, сделав его ключевым компонентом своего облачного и on-premise стека. Он появился как современный ответ на растущую популярность альтернативных решений для долгосрочного хранения, таких как [VictoriaMetrics](../VictoriaMetrics/overview.md) и [Thanos](../Prometheus/scaling/thanos_overview.md).

Основная задача Mimir — агрегировать метрики из множества кластеров Prometheus, предоставляя единую точку для глобального запроса данных и решая фундаментальные проблемы масштабирования и долгосрочного хранения, присущие стандартному Prometheus.

## Базовые концепции

### Архитектурная философия

Архитектура Mimir разделяет общие принципы с другими компонентами Grafana Stack ([Loki](../Loki/loki_overview.md), [Tempo](../Tempo/tempo_overview.md)):

* **Язык:** Все компоненты написаны на **Go**.
* **Режим развертывания:** Может быть запущен как в виде **одного бинарного файла** (монолит) для простых инсталляций, так и в виде набора **горизонтально масштабируемых микросервисов**.
* **Хранилище:** Для долгосрочного хранения данных используется **объектное хранилище** (S3, GCS, MinIO), что делает хранение дешевым и надежным.

### Основные компоненты

Mimir состоит из набора микросервисов, каждый из которых выполняет свою роль и может масштабироваться независимо:

* **Distributor:** Принимает метрики от Prometheus через `remote_write` API. Валидирует данные, обеспечивает соблюдение лимитов для каждого тенента и направляет их на несколько инжестеров (с репликацией).
* **Ingester:** Получает данные от Distributor, хранит их в памяти в виде временных рядов и периодически "сбрасывает" сжатые блоки данных (TSDB blocks) в объектное хранилище.
* **Querier:** Обрабатывает запросы на языке PromQL. Он запрашивает самые свежие данные у инжестеров, а исторические данные — у компонента `store-gateway`.
* **Query Frontend:** Опциональный, но рекомендуемый компонент для ускорения запросов. Кэширует результаты, разбивает большие запросы на более мелкие и может ставить их в очередь, чтобы избежать перегрузки. Активно использует кэширование (например, с помощью Memcached).
* **Store-Gateway:** "Шлюз" к объектному хранилищу. Он сканирует бакеты на наличие новых блоков данных, загружает их метаданные и предоставляет их запросчикам для выполнения исторических запросов.
* **Compactor:** Оптимизирует блоки данных в объектном хранилище, уплотняя (объединяя) их и удаляя устаревшие данные. Это ускоряет запросы и экономит место.
* **Ruler:** Отвечает за выполнение правил записи (recording rules) и алертов (alerting rules) в формате Prometheus в разрезе каждого тенента.
* **Alertmanager:** Принимает алерты от Ruler, дедуплицирует их, группирует и отправляет в настроенные каналы уведомлений (Slack, PagerDuty и т.д.).

### Ключевые преимущества

* **Горизонтальная масштабируемость:** Все компоненты Mimir можно масштабировать независимо, что позволяет обрабатывать триллионы активных временных рядов.
* **Долгосрочное хранение:** Использует дешевые и надежные объектные хранилища для хранения метрик за длительные периоды (годы).
* **Высокая доступность:** Репликация данных между компонентами (например, тройная репликация между инжестерами) обеспечивает отказоустойчивость и сохранность данных.
* **Мульти-тенатность:** Встроенная поддержка изоляции данных, запросов и лимитов для разных команд или клиентов.
* **Глобальный обзор:** Позволяет выполнять запросы к метрикам со всех ваших Prometheus-серверов в одном месте.

## Практические сценарии

### Централизованное хранилище для множества кластеров

1. **Локальные агенты:** В каждом контуре (например, в каждом кластере Kubernetes) разворачивается пара высокодоступных серверов **Prometheus**.
2. **Короткий срок хранения:** Локальные Prometheus настраиваются на очень короткий срок хранения данных (retention period), например, от 2 до 6 часов. Их задача — только собирать метрики и как можно скорее пересылать их дальше.
3. **Пересылка данных:** Каждый Prometheus использует `remote_write` для отправки всех собираемых метрик в единый кластер **Mimir**.
4. **Централизованный анализ:** Кластер Mimir агрегирует данные со всех источников. Для визуализации используется единый **Grafana**, подключенный к Mimir как к основному источнику данных.

Такая архитектура снижает нагрузку на локальные Prometheus, повышает отказоустойчивость (при сбое локального сервера теряются только последние минуты метрик, которые уже были отправлены в Mimir) и предоставляет единую точку для анализа и построения дашбордов по всей инфраструктуре.
