# OpenTelemetry: Архитектура и Сигналы

## Определения

**Сигналы (Signals)** в OpenTelemetry — это стандартизированные типы телеметрических данных. К ним относятся трассировки, метрики и логи. Единая модель данных и семантические конвенции позволяют коррелировать сигналы между собой, обеспечивая глубокую наблюдаемость системы.

Все сигналы разделяют общую структуру метаданных:

- **Resource:** Атрибуты, описывающие источник телеметрии (например, `service.name`, `host.name`).
- **Instrumentation Scope:** Атрибуты, идентифицирующие библиотеку, которая сгенерировала телеметрию (например, `io.opentelemetry.django`).

### Уровни стабильности сигналов

| Сигнал | Статус | Примечание |
|--------|--------|------------|
| **Трассировки** | `stable` | Полностью стабильны |
| **Метрики** | `stable` | Стабильны с 2024 |
| **Логи** | `stable` | Стабильны с конца 2024 |
| **Профили** | `alpha` | В разработке |

## Основные концепции

### 1. Трассировки (Traces)

Представляют собой дерево **спанов (Spans)**, иллюстрирующее путь выполнения запроса через распределённую систему.

- **Модель данных:** Каждый спан имеет имя, `trace_id`, `span_id`, родительский `span_id`, временные метки (начало, конец, продолжительность), атрибуты, события и статус выполнения (ok/error).
- **Контекст (Context Propagation):** Механизм передачи контекста выполнения между сервисами. [W3C Trace Context](https://www.w3.org/TR/trace-context/) — стандарт для передачи `trace_id` и `span_id` (обычно в HTTP-заголовках `traceparent`).
- **Baggage (Багаж):** Дополнительный механизм передачи произвольных пользовательских метаданных (key-value) вместе с контекстом трассировки сквозь все микросервисы.

### 2. Метрики (Metrics)

Агрегированные числовые измерения, собранные за определённый период.

- **Категории:**
  - **Системные / Ресурсные:** загрузка CPU, памяти, статистика Garbage Collector.
  - **Прикладные (Технические):** время ответа (latency), количество запросов (RPS), частота ошибок.
  - **Прикладные (Бизнес):** конверсия, количество оформленных заказов.
- **Модель данных:** OTel определяет несколько типов метрик: `Sum` / `Counter` (монотонно растущий или сбрасываемый счётчик), `Gauge` (мгновенное значение, которое может увеличиваться и уменьшаться), `Histogram` (распределение значений по бакетам, используется для расчета перцентилей, например p95).
- **Агрегация:** В отличие от других моделей, OTel SDK может производить предварительную агрегацию метрик перед экспортом, снижая нагрузку на сеть и хранилище.

### 3. Логи (Logs)

Записи о событиях, произошедших в определённый момент времени.

- **Модель данных:** `LogRecord` содержит временную метку, уровень важности (`severity`), тело сообщения и атрибуты.
- **Корреляция:** Если лог записывается в контексте активного спана, он автоматически обогащается `trace_id` и `span_id`, что позволяет связать его с конкретной трассировкой.

### Корреляция сигналов

Ключевая возможность OTel — связывание различных сигналов для получения полной картины:

- **Трассировки и Логи:** Логи автоматически связываются с трассировками через `trace_id`.
- **Трассировки и Метрики:** Механизм **Exemplars** позволяет прикреплять к измерениям метрик (особенно в гистограммах) `trace_id` конкретных запросов, которые повлияли на это измерение.

## Практические сценарии

### Конвейер обработки сигналов в Collector

OpenTelemetry Collector использует конвейеры (pipelines) для независимой обработки каждого типа сигнала. Это позволяет, например, отправлять метрики в Prometheus, а трассировки — в Jaeger.

Пример конфигурации `config.yaml` для Collector:

```yaml
receivers:
  otlp: # Приёмник данных по протоколу OTLP
    protocols:
      grpc:
      http:

processors:
  batch: # Группирует данные в пакеты перед отправкой
  memory_limiter: # Предотвращает исчерпание памяти
    check_interval: 1s
    limit_percentage: 75
  attributes: # Добавляет или изменяет атрибуты
    actions:
      - key: environment
        value: "production"
        action: insert

exporters:
  prometheus: # Экспортёр метрик для Prometheus
    endpoint: "0.0.0.0:9464"
  jaeger: # Экспортёр трассировок для Jaeger
    endpoint: "jaeger-collector:14250"
    tls:
      insecure: true
  logging: # Отладочный экспортёр, выводит данные в консоль
    loglevel: debug

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch, memory_limiter]
      exporters: [jaeger, logging]
    metrics:
      receivers: [otlp]
      processors: [batch, memory_limiter]
      exporters: [prometheus]
```

Подробнее о генерации этих сигналов в коде см. в разделе **[Инструментация и SDK](./instrumentation_sdk.md)**.

## Дополнительная информация

### Сравнение сигналов

| Сигнал      | Форма данных | Назначение | Особенности |
|-------------|---|---|---|
| Трассировки | Дерево спанов | Диагностика пути и задержек запроса | Возможна **сэмплинг** (head/tail) для снижения объёма данных. |
| Метрики     | Временные ряды | Мониторинг здоровья и трендов системы | Данные **агрегируются** перед отправкой. |
| Логи        | Записи событий | Детальный анализ ошибок и аудит | Могут **фильтроваться** и обогащаться `trace_id` для контекста. |

> **Важно:** Экспортёр Zipkin устарел. Рекомендуется использовать OTLP или нативные экспортёры бэкендов.
