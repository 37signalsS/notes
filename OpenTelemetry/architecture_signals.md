# OpenTelemetry: Архитектура и сигналы

## Определения

**Сигналы (Signals)** в OpenTelemetry — это стандартизированные типы телеметрических данных. К ним относятся трассировки, метрики, логи и профили. Единая модель данных и семантические конвенции позволяют коррелировать сигналы между собой, обеспечивая глубокую наблюдаемость системы.

**Статус на июль 2026 года:**
- Проект OpenTelemetry официально имеет статус **CNCF Graduated**.
- Основные сигналы (Traces, Metrics, Logs) полностью стабильны.
- Сигнал **Profiles** находится в статусе **Public Alpha** (акцент на eBPF-профилировании).

Все сигналы разделяют общую структуру метаданных через **Resource** (описание источника) и **Instrumentation Scope** (описание библиотеки-генератора).

## Основные концепции

### 1. Трассировки (Traces)

Представляют собой дерево **спанов (Spans)**, иллюстрирующее путь выполнения запроса через распределённую систему.
- **Контекст (Context Propagation):** Передача `trace_id` и `span_id` между сервисами (стандарт W3C Trace Context).
- **Baggage:** Передача произвольных метаданных (key-value) сквозь всю цепочку вызовов.
- Подробнее: **[Трассировки: детали](../Concepts/Observability_and_Monitoring/traces_deep_dive.md)**.

### 2. Метрики (Metrics)

Агрегированные числовые измерения производительности и состояния системы.
- **Типы:** `Sum` (счётчик), `Gauge` (текущее значение), `Histogram` (распределение).
- **Native Histograms:** Поддержка экспорта высокоточных гистограмм (стандарт Prometheus 2026).
- Подробнее: **[Метрики: детали](../Concepts/Observability_and_Monitoring/metrics_deep_dive.md)**.

### 3. Логи (Logs)

Записи о событиях, обогащённые контекстом трассировки для быстрой диагностики.
- **Корреляция:** Автоматическая привязка `trace_id` и `span_id` к каждой записи при наличии активного спана.
- Подробнее: **[Логи: детали](../Concepts/Observability_and_Monitoring/logs_deep_dive.md)**.

### 4. Профили (Profiles)

Новый тип сигнала (Alpha) для непрерывного профилирования (Continuous Profiling). Позволяет анализировать потребление ресурсов (CPU, Memory) на уровне функций кода и сопоставлять их с конкретными трейсами.

### Корреляция сигналов

OpenTelemetry обеспечивает бесшовный переход между типами данных:

- **Трассировки ↔ Логи:** Сквозной `trace_id` позволяет в один клик увидеть все логи конкретного запроса.
- **Трассировки ↔ Метрики (Exemplars):** Механизм **Exemplars** прикрепляет `trace_id` к точкам на графиках метрик.
  - **Mimir:** Полная поддержка хранения и визуализации Exemplars.
  - **VictoriaMetrics:** Фокус на «едином сигнале» и Native Histograms; классические Exemplars поддерживаются ограниченно.
- **Трассировки ↔ Профили:** Позволяет ответить на вопрос: «Почему этот конкретный спан длился 5 секунд?» путём анализа профиля CPU за этот период.

### Архитектура Collector: Коннекторы (Connectors)

В 2026 году коннекторы стали ключевым элементом архитектуры Collector, позволяя производным сигналам рождаться из первичных:
- **SpanMetrics Connector:** Генерирует метрики (RPS, ошибки, задержки) на основе входящего потока трассировок.
- **ServiceGraph Connector:** Строит карту зависимостей сервисов, анализируя связи между спанами.
- **Routing Connector:** Маршрутизирует данные в разные пайплайны на основе атрибутов.

## Практические сценарии

### Конвейер Collector с использованием коннекторов

Пример конфигурации, где метрики генерируются прямо в коллекторе из трейсов:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
      http:

connectors:
  spanmetrics: # Генерация RED-метрик из трейсов
    histogram:
      explicit:
        buckets: [2ms, 10ms, 50ms, 250ms, 1s, 5s]

processors:
  batch:
    timeout: 5s
  resourcedetection: # Автоматическое определение облака/K8s
    detectors: [env, system, k8snode, gcp]

exporters:
  prometheus:
    endpoint: "0.0.0.0:9464"
  otlp/tempo:
    endpoint: "tempo:4317"
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [resourcedetection, batch]
      exporters: [otlp/tempo, spanmetrics] # Экспорт в бэкенд и в коннектор
    metrics:
      receivers: [otlp, spanmetrics] # Прием данных от SDK и от коннектора
      processors: [resourcedetection, batch]
      exporters: [prometheus]
```

## Дополнительная информация

### Сравнение стабильности и применения (2026)

| Сигнал | Статус | Основное применение | Особенности |
| :--- | :--- | :--- | :--- |
| **Трассировки** | **Stable** | Анализ распределённых запросов | Требуют сэмплинга (Tail Sampling) |
| **Метрики** | **Stable** | Мониторинг SLO и алертинг | Агрегируются на уровне SDK/Collector |
| **Логи** | **Stable** | Детальное расследование (Post-mortem) | Высокий объём данных, требуют индексации |
| **Профили** | **Alpha** | Оптимизация ресурсов и производительности | Низкий оверхед через eBPF |

### Рекомендации по выбору экспортеров

- **Забудьте про Zipkin/Jaeger-thrift:** Используйте только **OTLP**.
- **High-Load:** Для передачи больших объёмов данных между коллекторами используйте **OTLP/Arrow**.
- **Storage:** Grafana LGTM (Loki, Grafana, Tempo, Mimir) обеспечивает наилучшую нативную поддержку корреляции OTel-сигналов.
