# OpenTelemetry (OTel): Обзор

## Определения

**OpenTelemetry (OTel)** — это открытый, независимый от поставщика стандарт и набор инструментов для сбора, обработки и экспорта телеметрических данных. Проект является частью [Cloud Native Computing Foundation (CNCF)](https://www.cncf.io/).

Цель OTel — унифицировать инструментирование облачных приложений для обеспечения наблюдаемости (observability). Он возник в результате слияния проектов **OpenTracing** и **OpenCensus**.

Телеметрия в OpenTelemetry основана на трёх "столпах" (сигналах):
1.  **Трассировки (Traces):** Детализированная информация о жизненном цикле запроса в распределённой системе.
2.  **Метрики (Metrics):** Агрегированные числовые данные о производительности и состоянии системы.
3.  **Логи (Logs):** Записи о конкретных событиях.

## Основные концепции

Архитектура OpenTelemetry состоит из нескольких ключевых, взаимосвязанных компонентов:

- **[Сигналы (Signals)](./architecture_signals.md):** Основа OTel. Трассировки, метрики и логи имеют стандартизированную модель данных, что обеспечивает их единообразную обработку и корреляцию.
- **[API и SDK](./instrumentation_sdk.md):** Набор библиотек для инструментирования кода. **API** предоставляет интерфейсы для генерации телеметрии, а **SDK** — их конкретную реализацию, управляющую сэмплированием, обработкой и экспортом данных.
- **[Протокол OTLP](./otlp_protocol.md):** Унифицированный протокол для передачи телеметрических данных. Он определяет единый формат для всех сигналов, что упрощает их передачу и приём.
- **Collector:** Центральный компонент, который действует как конвейер. Он получает данные от множества источников, обрабатывает их (фильтрует, обогащает, сэмплирует) и экспортирует в различные системы хранения и анализа (бэкенды). Это позволяет отделить логику управления телеметрией от кода приложений.

## Практические сценарии

### Сбор телеметрии в микросервисной архитектуре
В типичной среде микросервисов каждое приложение инструментируется с помощью OpenTelemetry SDK. SDK собирает телеметрию и отправляет её по протоколу OTLP на **OpenTelemetry Collector**, который может быть развёрнут как агент на узле или как отдельный сервис-шлюз.

Collector обрабатывает входящие данные и направляет их в соответствующие бэкенды: трассировки в Jaeger или Tempo, метрики в Prometheus или Mimir, а логи — в Loki или Elasticsearch.

### Корреляция запросов к базе данных
Для сквозной трассировки, уходящей вглубь базы данных, используется механизм **SQLCommenter**. Он автоматически добавляет к SQL-запросам комментарий с контекстом трассировки (`trace_id`, `span_id`).

```sql
-- Стандартный запрос
SELECT * FROM users WHERE id = 1;

-- Запрос с контекстом трассировки
SELECT * FROM users WHERE id = 1 /*traceparent='00-abc...-def...-01'*/;
```
Это позволяет таким инструментам, как `pg_tracing` в PostgreSQL, связывать выполнение запроса в БД с конкретным спаном в приложении.

## Дополнительная информация

### Интеграция с бэкендами
Гибкость OTel позволяет использовать его с широким спектром бэкендов. Популярные стеки:

*   **Стек Grafana Labs:** [Loki](../Loki/loki_overview.md) (логи), [Tempo](../Tempo/tempo_overview.md) (трассировки), [Mimir](../Mimir/mimir_overview.md) (метрики) и [Grafana](../Grafana/grafana_overview.md) для визуализации.
*   **Стек ELK/OpenSearch:** [Elasticsearch](../ELK_Stack/Elasticsearch/elasticsearch_overview.md) как единое хранилище для всех трёх сигналов.
*   **Другие:** [Jaeger](../Jaeger/jaeger_overview.md) для трассировок, а также коммерческие платформы (Datadog, New Relic).
