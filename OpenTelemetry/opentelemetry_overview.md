# OpenTelemetry (OTel)

## Определения

**OpenTelemetry** — это открытый стандарт и набор инструментов для сбора, обработки и экспорта телеметрических данных (логов, метрик и трассировок). Проект является частью [Cloud Native Computing Foundation (CNCF)](https://www.cncf.io/) и находится в статусе *Incubating*.

OTel стандартизирует сбор телеметрии, которая традиционно делится на три "столпа" наблюдаемости (observability):
1.  **Метрики (Metrics):** Агрегированные числовые данные.
2.  **Логи (Logs):** Записи о событиях.
3.  **Трассировки (Traces):** Детализированная информация о жизненном цикле запроса в распределённой системе.

В последнее время к ним добавляется четвёртый столп — **профилирование (Profiling)**, часто реализуемое с помощью технологии eBPF. Детали можно найти в [Continuous Profiling](../Profiling/continuous_profiling.md).

OTel возник в результате слияния проектов **OpenTracing** и **OpenCensus**. Его цель — предоставить единый стандарт для инструментирования облачных приложений, независимый от вендора мониторинга.

## Основные понятия и архитектура

Ключевыми компонентами OpenTelemetry являются **API**, **SDK**, **Collector** и **OTLP Protocol**. Они формируют гибкую архитектуру для управления телеметрией.

- **[Архитектура и сигналы](./architecture_signals.md)**: Подробное описание трёх столпов наблюдаемости, их моделей данных, потоков и механизмов корреляции.
- **[Инструментация и SDK](./instrumentation_sdk.md)**: Обзор автоматической и ручной инструментализации, роли компонентов API и SDK, а также практические примеры настройки.
- **[Протокол OTLP](./otlp_protocol.md)**: Детальное описание структуры данных протокола OTLP, иерархии контейнеров и форматов сигналов.

### OpenTelemetry Collector
**Collector** — это центральный компонент, который действует как конвейер для телеметрических данных. Он получает данные в различных форматах, обрабатывает их (фильтрация, обогащение, сэмплирование) и экспортирует в один или несколько бэкендов.

Архитектура коллектора состоит из:
- **Receivers (Приёмники):** Принимают данные (push/pull).
- **Processors (Обработчики):** Обрабатывают данные "на лету".
- **Exporters (Экспортёры):** Отправляют данные в бэкенды.
- **Pipelines (Конвейеры):** Определяют путь данных от приёмника к экспортёру.

Использование Collector'а позволяет отделить логику сбора и обработки телеметрии от самих приложений.

## Практические сценарии

### Конфигурация трассировки
Трассировка всего подряд неэффективна, поэтому её следует включать по запросу или использовать сэмплирование.

Пример конфигурации сэмплирования:
```yaml
spec:
  containers:
  - name: app
    env:
    - name: OTEL_EXPORTER_OTLP_ENDPOINT
      value: "http://jaeger-collector:4317"
    - name: OTEL_SERVICE_NAME
      value: "api-server"
    - name: OTEL_TRACES_SAMPLER
      value: "parentbased_traceidratio"
    - name: OTEL_TRACES_SAMPLER_ARG
      value: "0.1"  # Сэмплировать 10% трейсов
```

### Инструментация запросов к PostgreSQL
Для связи трассировки с операциями в базе данных используется **SQLCommenter**. Он добавляет к каждому SQL-запросу комментарий с метаданными трассировки (`trace_id`, `span_id`).

```sql
-- Исходный запрос:
SELECT * FROM users WHERE id = 123;
-- Превращается в:
SELECT * FROM users WHERE id = 123 /*traceparent='00-abc...-def...-01'*/;
```
Этот комментарий может быть использован расширениями вроде `pg_tracing` для продолжения цепочки трассировки внутри PostgreSQL. Примеры реализации на Python и Go можно найти в статье про [инструментацию и SDK](./instrumentation_sdk.md).

## Дополнительная информация

### Архитектура и Бэкенды
Гибкость OpenTelemetry позволяет интегрировать его с разнообразными системами хранения и анализа данных.

#### Системы хранения (Backends)
OpenTelemetry Collector может отправлять данные в различные бэкенды. Популярные решения можно сгруппировать в стеки:

*   **Стек Grafana Labs:**
    *   [Loki](../Loki/loki_overview.md) для логов.
    *   [Tempo](../Tempo/tempo_overview.md) для трассировок.
    *   [Mimir](../Mimir/mimir_overview.md) или [Prometheus](../Prometheus/overview.md) для метрик.
    *   Визуализация: [Grafana](../Grafana/grafana_overview.md).
*   **Стек ELK/OpenSearch:**
    *   [Elasticsearch](../ELK_Stack/Elasticsearch/elasticsearch_overview.md) или OpenSearch используется как единое хранилище для логов, метрик и трассировок.
*   **Другие инструменты:**
    *   [Jaeger](../Jaeger/jaeger_overview.md): Популярное решение для хранения и визуализации трассировок.
    *   Коммерческие платформы: Datadog, New Relic, Dynatrace и др.

#### Пример эталонной архитектуры
Официальный демонстрационный проект OpenTelemetry (`opentelemetry-demo`) является отличным примером микросервисного приложения, инструментированного с помощью OTel. Его архитектура включает фронтенд, множество микросервисов, брокер сообщений и базу данных, а телеметрия собирается через Collector и отправляется в различные бэкенды (Prometheus, Jaeger, Loki).
