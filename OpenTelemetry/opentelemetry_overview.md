# OpenTelemetry (OTel): Обзор

## Определения

**OpenTelemetry (OTel)** — это открытый, независимый от поставщика стандарт и набор инструментов для сбора, обработки и экспорта телеметрических данных. Проект является частью [Cloud Native Computing Foundation (CNCF)](https://www.cncf.io/).

Цель OTel — унифицировать инструментирование облачных приложений для обеспечения наблюдаемости (observability). Он возник в результате слияния проектов **OpenTracing** и **OpenCensus** в 2019 году.

Телеметрия в OpenTelemetry основана на трёх "столпах" (сигналах):

1. **Трассировки (Traces):** Детализированная информация о жизненном цикле запроса в распределённой системе.
2. **Метрики (Metrics):** Агрегированные числовые данные о производительности и состоянии системы.
3. **Логи (Logs):** Записи о конкретных событиях.
4. **Профили (Profiles):** *В разработке* — непрерывный сбор данных о потреблении ресурсов (CPU, memory).

## Основные концепции

Архитектура OpenTelemetry состоит из нескольких ключевых, взаимосвязанных компонентов:

- **[Сигналы (Signals)](./architecture_signals.md):** Основа OTel. Трассировки, метрики и логи имеют стандартизированную модель данных, что обеспечивает их единообразную обработку и корреляцию.
- **[API и SDK](./instrumentation_sdk.md):** Набор библиотек для инструментирования кода. **API** предоставляет интерфейсы для генерации телеметрии, а **SDK** — их конкретную реализацию, управляющую сэмплированием, обработкой и экспортом данных.
- **[Протокол OTLP](./otlp_protocol.md):** Унифицированный протокол для передачи телеметрических данных. Он определяет единый формат для всех сигналов, что упрощает их передачу и приём.
- **Collector:** Центральный компонент, который действует как конвейер для телеметрических данных.
  - **Архитектура:** Collector имеет четкую архитектуру, состоящую из:
    - **Receivers (Приемники):** Принимают данные в различных форматах (OTLP, Jaeger, Prometheus, Zipkin и др.).
    - **Processors (Обработчики):** Обрабатывают данные на лету (фильтрация, обогащение, сэмплирование, группировка).
    - **Exporters (Экспортеры):** Отправляют обработанные данные в один или несколько бэкендов (OTLP, Jaeger, Loki, Prometheus и др.).
  - **Дистрибутивы:**
    - **Core (`otel/opentelemetry-collector`):** Минимальный дистрибутив с проверенными стабильными компонентами. Рекомендуется для production.
    - **Contrib (`otel/opentelemetry-collector-contrib`):** Расширенный дистрибутив с экспериментальными и специализированными компонентами.
  - **Модель стабильности:** Компоненты маркируются уровнями стабильности (`stable`, `beta`, `alpha`, `development`). Stable-дистрибутивы включают только стабильные компоненты по умолчанию.

## Практические сценарии

### Сценарий: Миграция с Jaeger на OpenSearch Observability

Этот сценарий демонстрирует, как использовать OpenTelemetry для интеграции существующих приложений с бэкендом, требующим OTLP, таким как **OpenSearch Observability**.

**Проблема:** Приложения инструментированы для отправки трейсов в формате Jaeger, но OpenSearch Observability требует формат OTLP и использует свой компонент [**Data Prepper**](../ELK_Stack/OpenSearch/opensearch_overview.md) для приема данных.

**Решение:** Развернуть **OTLP Collector** как замену Jaeger Agent/Collector.

**Архитектура:**
`Приложение -> OTLP Collector -> Data Prepper -> OpenSearch`

1. **OTLP Collector** разворачивается как `DaemonSet` в Kubernetes, чтобы он был доступен на каждой ноде, имитируя поведение Jaeger Agent.
2. **Конфигурация Collector:**
    - **Receiver:** Настраивается на прием данных в формате Jaeger (`jaeger`).
    - **Exporter:** Настраивается на отправку данных в формате OTLP (`otlp`) на эндпоинт `Data Prepper`.
3. **Приложение** продолжает отправлять данные в формате Jaeger, но теперь их получает OTLP Collector.

#### Практические трудности и решения

В ходе реализации такой схемы могут возникнуть проблемы, требующие корректировки архитектуры:

- **Проблема несовместимости полей:** OTLP Collector корректно преобразует спаны из формата Jaeger в OTLP. Однако некоторые поля, опциональные в Jaeger (например, `name` у событий), могут быть обязательными для `Data Prepper`. Если `Data Prepper` отбрасывает спаны из-за таких несоответствий, решением может быть переконфигурация приложения для отправки данных напрямую в **нативном формате OTLP**.
  - **Итоговая архитектура:** `Приложение (в OTLP-формате) -> OTLP Collector -> Data Prepper -> OpenSearch`.

- **Проблема с конфигурацией эндпоинта:** Библиотеки OTel SDK могут требовать указания эндпоинта коллектора в виде полного URL. В Kubernetes это затрудняет использование `hostIP` пода-коллектора.
  - **Решение:** Вместо прямого обращения на `hostIP`, создается Kubernetes `Service` для OTLP Collector. Приложение настраивается на отправку данных на этот сервис. Это упрощает конфигурацию, но может снизить производительность из-за дополнительного сетевого хопа.

### Сценарий: Прямая отправка трейсов в Jaeger Agent в Kubernetes

Этот сценарий описывает эффективный способ настройки приложения для отправки трейсов напрямую в Jaeger Agent, развернутый в Kubernetes как `DaemonSet`.

**Цель:** Минимизировать сетевые задержки и упростить сетевой путь, отправляя UDP-пакеты с трейсами с пода приложения напрямую на Jaeger Agent, работающий на том же узле.

**Архитектура:**
`Приложение (Pod) -> Jaeger Agent (DaemonSet на том же Node)`

**Решение:** Использовать **Downward API** для передачи IP-адреса хоста (`hostIP`) в под приложения как переменную окружения.

**Конфигурация приложения:**

В манифесте `Deployment` приложения необходимо настроить переменные окружения для OTel SDK.

```yaml
# В манифесте Deployment приложения
spec:
  template:
    spec:
      containers:
      - name: my-python-app
        env:
        # Указываем SDK, какой экспортер использовать
        - name: OTEL_TRACES_EXPORTER
          value: "jaeger"
        # Передаем IP адрес хоста, на котором запущен под, в переменную окружения.
        # Jaeger Agent должен быть развернут как DaemonSet с hostNetwork: true.
        - name: OTEL_EXPORTER_JAEGER_AGENT_HOST
          valueFrom:
            fieldRef:
              fieldPath: status.hostIP
        - name: OTEL_EXPORTER_JAEGER_AGENT_PORT
          value: "6831" # Стандартный UDP порт агента
```

Этот паттерн позволяет избежать использования Kubernetes `Service`, `kube-proxy` и связанных с ними NAT-преобразований для трафика телеметрии, что положительно сказывается на производительности.

### Корреляция запросов к базе данных

Для сквозной трассировки, уходящей вглубь базы данных, используется механизм **SQLCommenter**. Он автоматически добавляет к SQL-запросам комментарий с контекстом трассировки (`trace_id`, `span_id`).

```sql
-- Стандартный запрос
SELECT * FROM users WHERE id = 1;

-- Запрос с контекстом трассировки
SELECT * FROM users WHERE id = 1 /*traceparent='00-abc...-def...-01'*/;
```

Это позволяет таким инструментам, как `pg_tracing` в PostgreSQL, связывать выполнение запроса в БД с конкретным спаном в приложении.

## Дополнительная информация

### Интеграция с бэкендами

Гибкость OTel позволяет использовать его с широким спектром бэкендов. Популярные стеки:

- **Стек Grafana Labs:** [Loki](../Loki/loki_overview.md) (логи), [Tempo](../Tempo/index.md) (трассировки), [Mimir](../Mimir/mimir_overview.md) (метрики) и [Grafana](../Grafana/grafana_overview.md) для визуализации. Для сбора данных используется [Grafana Alloy](../Grafana/grafana_alloy_overview.md) — агент на базе OTel Collector с языком конфигурации River.
- **Стек ELK/OpenSearch:** [Elasticsearch](../ELK_Stack/Elasticsearch/elasticsearch_overview.md) / [OpenSearch](../ELK_Stack/OpenSearch/opensearch_overview.md) как единое хранилище для всех трёх сигналов. Data Prepper используется как конвейер для OTLP.
- **Jaeger:** [Jaeger v2](../Jaeger/jaeger_overview.md) для трассировок (построен на OTel Collector).
- **Другие:** Коммерческие платформы (Datadog, New Relic, Dynatrace) поддерживают OTLP нативно.

### Альтернативы OTel Collector

| Агент | Основан на | Язык конфигурации | Фокус |
|-------|------------|-------------------|-------|
| **OTel Collector** | — | YAML | Универсальный, любой OTel-бэкенд |
| **Grafana Alloy** | OTel Collector | River (HCL) | Экосистема Grafana (Loki, Mimir, Tempo) |
| **Fluent Bit** | — | Lua/ YAML | Логи, легковесный |
