# OpenTelemetry: Обзор

## Определения

**OpenTelemetry (OTel)** — это открытый, независимый от поставщика стандарт и набор инструментов для сбора, обработки и экспорта телеметрических данных (метрик, трассировок, логов и профилей). Проект является частью [Cloud Native Computing Foundation (CNCF)](https://www.cncf.io/).

**Статус в 2026 году:**
- Проект официально имеет статус **CNCF Graduated**.
- Является индустриальным стандартом де-факто для реализации концепции **Observability (Наблюдаемости)**.
- Основные сигналы (Traces, Metrics, Logs) находятся в статусе **General Availability (GA)**.
- Сигнал **Profiles** (непрерывное профилирование) интегрирован в основной стандарт и широко поддерживается в экосистеме.
- Протокол **OTLP/Arrow** принят как стандарт для высоконагруженных сред.

### Ключевые характеристики

- **Унифицированный инструментарий:** Единый набор API и инструментов для работы со всеми типами сигналов, что исключает необходимость использования разрозненных агентов.
- **Кросс-языковая поддержка:** Комплексные SDK для всех популярных языков программирования (Java, Go, Python, Rust, JavaScript и др.).
- **Корреляция по дизайну:** Единая модель данных позволяет бесшовно переходить от метрик к трейсам, а от трейсов — к логам и профилям.
- **Гибкость:** Расширяемая архитектура коллектора для построения произвольных пайплайнов обработки.

Телеметрия в OTel основана на стандартизированных сигналах и семантических конвенциях (**Semantic Conventions**), что гарантирует единообразие данных независимо от используемого языка программирования или бэкенда.

## Основные концепции

Архитектура OpenTelemetry построена на принципах модульности и разделения ответственности:

### Компоненты системы

1.  **[API и SDK](./instrumentation_sdk.md):**
    - **API:** Унифицированный интерфейс для генерации телеметрии. Позволяет авторам библиотек добавлять инструментацию без привязки к конкретной реализации.
    - **SDK:** Конкретная реализация API, отвечающая за сбор, агрегацию, сэмплирование и экспорт данных. Поддерживает автоматическую и ручную инструментацию.
2.  **[Протокол OTLP](./otlp_protocol.md):** Высокопроизводительный протокол на базе gRPC/HTTP для передачи всех типов сигналов. Версия **OTLP/Arrow** обеспечивает колоночное сжатие для экономии трафика.
3.  **Collector:** Универсальный прокси-сервер, который может работать как локальный агент или централизованный шлюз.

### Анатомия Collector

Collector позволяет строить гибкие цепочки обработки данных (Pipelines):
-   **Receivers (Приемники):** Принимают данные (OTLP, Prometheus, Jaeger, Zipkin, AWS X-Ray и др.).
-   **Processors (Обработчики):** Выполняют модификацию данных. В 2026 году стандартом для трансформации стал **Transform Processor** (использующий OTTAL — OpenTelemetry Transformation Language). Также активно используются `resourcedetection` (обогащение метаданными инфраструктуры) и `memory_limiter`.
-   **Exporters (Экспортеры):** Отправляют данные в системы хранения (Tempo, Loki, Mimir, ClickHouse, Elastic, Kafka).
-   **Connectors (Коннекторы):** Связывают разные пайплайны (например, генерация метрик на основе входящих трейсов через `spanmetrics`).
-   **Extensions (Расширения):** Служебные функции (Health check, Auth, Pprof, управление конфигурацией).

### Режимы развертывания

-   **Sidecar / Agent:** Разворачивается рядом с приложением. Рекомендуется для первичной агрегации и добавления локального контекста (Pod IP, Hostname).
-   **Gateway (Шлюз):** Централизованный кластер коллекторов для агрегации, маршрутизации, Tail-based сэмплирования и управления доступом к бэкендам.
-   **Sidecar-less (eBPF):** Сбор телеметрии на уровне ядра без модификации приложений через **OTel eBPF Agent**. Позволяет получать данные даже из закрытых бинарных файлов.

## Безопасность и управление

В современной инфраструктуре OpenTelemetry предоставляет встроенные механизмы защиты данных:
-   **Аутентификация и авторизация:** Расширения `oidc`, `header_auth` и `saml` для контроля доступа к Collector.
-   **Фильтрация PII:** Использование `transform` процессора для маскирования чувствительных данных (пароли, личные данные) на этапе сбора.
-   **Telemetry Schemas:** Механизм управления версиями семантических конвенций для обеспечения совместимости данных при обновлении SDK или коллектора.

## Практические сценарии

### Сценарий: Унификация мониторинга в гетерогенной среде

**Проблема:** Часть сервисов использует старые агенты Jaeger, часть — Prometheus, а новые требования бизнеса включают сбор логов и профилей в единую систему.

**Решение:** Использование OTel Collector как универсального адаптера.

**Конфигурация (Pipeline):**
1.  **Прием:** Collector принимает трейсы по протоколу `jaeger` и метрики по `otlp`.
2.  **Обработка:** Процессор `resourcedetection` добавляет атрибуты Kubernetes. `transform` процессор нормализует имена метрик к стандарту OTel.
3.  **Экспорт:** Трейсы уходят в **Tempo**, метрики — в **Mimir**, логи — в **Loki**, а профили — в **Pyroscope** по единому протоколу OTLP.

### Сценарий: Сквозная трассировка через базы данных

Для корреляции действий приложения с нагрузкой на БД используется стандарт **sqlcommenter**. SDK OpenTelemetry автоматически добавляет контекст трассировки в SQL-запросы.

```sql
-- Пример запроса, обогащенного OTel
SELECT * FROM orders WHERE id = 123 /*traceparent='00-4bf92...-01'*/;
```
Это позволяет СУБД (например, PostgreSQL с расширением `pg_tracing`) фиксировать время выполнения конкретного запроса в рамках общего распределенного трейса, связывая задержки на уровне БД с конкретными вызовами в коде.

## Дополнительная информация

### Выбор дистрибутива Collector

-   **Core:** Минимальный набор компонентов для максимальной стабильности и безопасности.
-   **Contrib:** Содержит огромное количество приемников и экспортеров от сообщества для интеграции с legacy-системами.
-   **Vendor-specific (например, Grafana Alloy):** Дистрибутивы, оптимизированные под конкретные экосистемы с дополнительными функциями (например, River-конфигурация).

### Лучшие практики (2026)

-   **Semantic Conventions First:** Всегда используйте стандартные атрибуты (например, `http.status_code` вместо `status`). Это ключ к автоматическим дашбордам и корреляции.
-   **OTLP Everywhere:** Используйте OTLP как единственный протокол взаимодействия между SDK, агентами и шлюзами.
-   **Tail-based Sampling:** Настраивайте сэмплирование на уровне Gateway Collector, чтобы гарантированно сохранять трейсы с ошибками или высокой задержкой.
-   **Monitoring of Monitoring:** Мониторинг очередей и нагрузки самого коллектора обязателен для предотвращения потери данных наблюдаемости.
