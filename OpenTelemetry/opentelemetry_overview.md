# OpenTelemetry: Обзор

## Определения

**OpenTelemetry (OTel)** — это открытый, независимый от поставщика стандарт и набор инструментов для сбора, обработки и экспорта телеметрических данных (метрик, трассировок, логов и профилей). Проект является частью [Cloud Native Computing Foundation (CNCF)](https://www.cncf.io/).

**Статус на июль 2026 года:**
- Проект официально имеет статус **CNCF Graduated** (с мая 2026).
- Является индустриальным стандартом де-факто для реализации концепции **Observability (Наблюдаемости)**.
- Возник в результате слияния проектов **OpenTracing** и **OpenCensus**.

### Ключевые характеристики

- **Унифицированный инструментарий:** Единый набор API и инструментов для сбора трассировок, метрик и журналов.
- **Кросс-языковая поддержка:** Комплексные SDK для всех популярных языков программирования.
- **Совместимость с бэкендами:** Нативная поддержка экспорта данных в Jaeger, Zipkin, Prometheus и другие системы.
- **Гибкость:** Расширяемая архитектура коллектора для построения произвольных пайплайнов обработки.

Телеметрия в OTel основана на стандартизированных сигналах и семантических конвенциях (**Semantic Conventions**), что гарантирует единообразие данных независимо от используемого языка программирования или бэкенда.

## Основные концепции

Архитектура OpenTelemetry построена на модульности и расширяемости:

### Компоненты системы

1.  **[API и SDK](./instrumentation_sdk.md):**
    - **API:** Унифицированный интерфейс для генерации телеметрии. Позволяет библиотекам быть инструментированными без привязки к конкретной реализации OTel.
    - **SDK:** Конкретная реализация API, отвечающая за сбор, агрегацию, сэмплирование и экспорт данных.
2.  **[Протокол OTLP](./otlp_protocol.md):** Высокопроизводительный протокол на базе gRPC/HTTP для передачи всех типов сигналов.
3.  **Collector:** Универсальный прокси-сервер и конвейер для обработки телеметрии.

### Анатомия Collector

Collector позволяет строить гибкие цепочки обработки данных (Pipelines):
-   **Receivers (Приемники):** Принимают данные в форматах OTLP, Prometheus, Jaeger, Zipkin, OAI и др.
-   **Processors (Обработчики):** Выполняют модификацию данных на лету (фильтрация PII, обогащение атрибутами K8s, сэмплирование, батчинг).
-   **Exporters (Экспортеры):** Отправляют данные в системы хранения (Tempo, Loki, Mimir, ClickHouse, Elastic).
-   **Connectors (Коннекторы):** Специальные компоненты, связывающие разные пайплайны (например, генерация метрик на основе входящих трейсов).
-   **Extensions (Расширения):** Служебные функции (Health check, Pprof, ZPages для диагностики коллектора).

### Режимы развертывания

-   **Sidecar / Agent:** Разворачивается рядом с приложением (в том же поде или на том же узле как DaemonSet). Рекомендуется для первичной агрегации и добавления локального контекста.
-   **Gateway (Шлюз):** Централизованный кластер коллекторов для финальной обработки, маршрутизации и балансировки нагрузки перед отправкой в бэкенды.
-   **Sidecar-less (eBPF):** Сбор телеметрии на уровне ядра без модификации подов приложений (через OTel eBPF Agent).

## Практические сценарии

### Сценарий: Унификация мониторинга в гетерогенной среде

**Проблема:** Часть сервисов использует старые агенты Jaeger, часть — Prometheus, а новые требования бизнеса включают сбор логов в единую систему.

**Решение:** Использование OTel Collector как универсального адаптера.

**Конфигурация (Pipeline):**
1.  **Прием:** Collector настраивается на прием `jaeger` (UDP/gRPC) и `otlp`.
2.  **Обработка:** Процессор `resourcedetection` автоматически добавляет атрибуты облачного провайдера и Kubernetes.
3.  **Экспорт:** Трейсы уходят в **Tempo**, метрики — в **Mimir**, логи — в **Loki** по единому протоколу OTLP.

### Сценарий: Сквозная трассировка через базы данных

Для корреляции действий приложения с нагрузкой на БД используется стандарт **sqlcommenter**. SDK OpenTelemetry автоматически добавляет контекст трассировки в SQL-запросы в виде комментариев.

```sql
-- Пример запроса, обогащенного OTel
SELECT * FROM orders WHERE id = 123 /*traceparent='00-4bf92...-01'*/;
```
Это позволяет СУБД (например, PostgreSQL с расширением `pg_tracing`) фиксировать время выполнения конкретного запроса в рамках общего распределенного трейса.

## Дополнительная информация

### Выбор дистрибутива Collector

-   **Core:** Минимальный набор компонентов, поддерживаемый основной командой OTel. Максимальная стабильность.
-   **Contrib:** Огромное количество приемников и экспортеров от сообщества. Необходим для интеграции с legacy-системами.
-   **Vendor-specific (например, Grafana Alloy):** Дистрибутивы от вендоров, оптимизированные под их экосистемы и предлагающие дополнительные функции (например, River-конфигурация в Alloy).

### Лучшие практики (2026)

-   **OTLP Everywhere:** Используйте OTLP как основной протокол взаимодействия между всеми компонентами.
-   **Collector Monitoring:** Мониторинг самого коллектора (длина очередей, падения спанов) обязателен. Если коллектор перегружен — вы теряете наблюдаемость.
-   **Tail-based Sampling:** Настраивайте сэмплирование на уровне Gateway Collector, чтобы гарантированно сохранять трейсы с ошибками, отбрасывая избыточные успешные запросы.
