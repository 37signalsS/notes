# OpenTelemetry: Протокол OTLP

> **Актуальность:** 2025-2026. OTLP 1.9.0, новая схема конфигурации Collector.

## Определения

**OTLP (OpenTelemetry Protocol)** — это унифицированный протокол передачи данных, разработанный для отправки телеметрических сигналов (трассировок, метрик, логов) из приложения в Collector или совместимый бэкенд. Он определяет стандартную схему данных на основе Protocol Buffers (Protobuf), что обеспечивает высокую эффективность и строгую типизацию.

OTLP спроектирован для использования поверх различных транспортных протоколов, чаще всего **gRPC** и **HTTP/1.1**.

### Версии протокола (2025-2026)

| Версия | Дата | Изменения |
|--------|------|-----------|
| **OTLP 1.9.0** | 2026 | Поддержка Profiles API, улучшения для логов |

## Основные концепции

### Иерархия данных

OTLP использует общую вложенную структуру для всех сигналов, что позволяет эффективно передавать метаданные:

1. **Resource:** Контейнер верхнего уровня. Описывает источник телеметрии через атрибуты (`service.name`, `host.name`). Все данные внутри одного `Resource` сообщения принадлежат одной и той же сущности.
    - `ResourceSpans`
    - `ResourceMetrics`
    - `ResourceLogs`
2. **Instrumentation Scope:** Группирует телеметрию по библиотеке, которая её сгенерировала (например, `io.opentelemetry.spring-webmvc` версии `5.3`).
    - `ScopeSpans`
    - `ScopeMetrics`
    - `ScopeLogs`
3. **Signal Records:** Непосредственно записи данных: массив спанов, метрик или логов.

### Структура сигналов в OTLP

- **Трассировки (Span):** Содержат имя, `kind` (server, client), временные метки, атрибуты, события, ссылки на другие спаны и статус. Идентификаторы `trace_id` и `span_id` передаются как байтовые массивы.
- **Метрики (Metric):** Включают имя, описание, единицу измерения и один из типов данных (`Gauge`, `Sum`, `Histogram`). Каждая метрика содержит точки данных (`DataPoint`) с временными метками, атрибутами и значением.
- **Логи (LogRecord):** Включают тело сообщения (`Body`), уровень важности (`Severity`), временную метку и атрибуты. Для корреляции содержат поля `trace_id` и `span_id`.

### Атрибуты

Атрибуты (пары ключ-значение) являются универсальным механизмом для добавления метаданных на любом уровне иерархии. OTLP определяет унифицированный тип `AnyValue` для значений, который поддерживает примитивы, массивы и вложенные структуры.

## Практические сценарии

### Пример OTLP/HTTP в формате JSON

Ниже представлен сокращённый пример OTLP-сообщения, передаваемого по HTTP. Он демонстрирует иерархию `Resource` → `Scope` → `Metric` для метрики типа `Gauge`.

```json
{
  "resourceMetrics": [
    {
      "resource": {
        "attributes": [
          {"key": "service.name", "value": {"stringValue": "payment-api"}},
          {"key": "service.version", "value": {"stringValue": "1.4.2"}}
        ]
      },
      "scopeMetrics": [
        {
          "scope": {
            "name": "io.opentelemetry.http-server",
            "version": "1.0.0"
          },
          "metrics": [
            {
              "name": "http.server.active_requests",
              "description": "Number of in-flight HTTP requests",
              "unit": "{request}",
              "gauge": {
                "dataPoints": [
                  {
                    "timeUnixNano": "1717428123000000000",
                    "asInt": "15",
                    "attributes": [
                      {"key": "http.method", "value": {"stringValue": "POST"}},
                      {"key": "http.route", "value": {"stringValue": "/v1/charge"}}
                    ]
                  }
                ]
              }
            }
          ]
        }
      ]
    }
  ]
}
```

Трассировки и логи передаются в аналогичной структуре, меняется только содержимое полей `resourceSpans` или `resourceLogs`.

## Дополнительная информация

### Транспорты

- **OTLP/gRPC:** Бинарный, высокопроизводительный протокол. Использует стандартные порты `4317` (insecure) и `4318` (secure). Является предпочтительным для межсервисного взаимодействия.
- **OTLP/HTTP:** Текстовый (JSON) протокол, более простой для отладки и совместимый с существующей инфраструктурой (прокси, балансировщики). Использует стандартные порты `4318` (insecure/secure).
- **OTLP/HTTP+Protobuf:** Компромиссный вариант — бинарный Protobuf поверх HTTP. Поддерживается в Collector с 2025 года.

### Новая схема конфигурации Collector (2025)

С 2025 года OTel Collector использует новую схему конфигурации с явным указанием версий компонентов:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

exporters:
  otlp:
    endpoint: tempo:4317
    tls:
      insecure: true

service:
  pipelines:
    traces:
      receivers: [otlp]
      exporters: [otlp]
```

**Изменения:**
- Упрощённая структура без избыточных вложенностей
- Явное указание версий компонентов для воспроизводимости
- Поддержка нескольких конфигураций через include
