# OpenTelemetry: Протокол OTLP

## Определения

**OTLP (OpenTelemetry Protocol)** — это унифицированный протокол передачи данных, предназначенный для отправки телеметрических сигналов (трассировок, метрик, логов и профилей) из приложения в Collector или совместимый бэкенд. Он определяет стандартную схему данных на основе Protocol Buffers (Protobuf), что обеспечивает высокую эффективность и строгую типизацию.

**Статус на 2026 год:**
- **Core Signals (Трейсы, Метрики, Логи):** Стабильны (OTLP v1.x).
- **Profiles:** Публичная Alpha.
- **CNCF Status:** Проект OpenTelemetry официально перешёл в категорию **Graduated** (июль 2026).

OTLP спроектирован для использования поверх различных транспортных протоколов, чаще всего **gRPC**, **HTTP/1.1** и **OTLP/Arrow**.

## Основные концепции

### Иерархия данных

OTLP использует общую вложенную структуру для всех сигналов, что позволяет эффективно передавать метаданные:

1.  **Resource:** Контейнер верхнего уровня. Описывает источник телеметрии через атрибуты (`service.name`, `host.name`). Все данные внутри одного `Resource` сообщения принадлежат одной и той же сущности.
2.  **Instrumentation Scope:** Группирует телеметрию по библиотеке, которая её сгенерировала (например, `io.opentelemetry.spring-webmvc` версии `5.3`).
3.  **Signal Records:** Непосредственно записи данных (массив спанов, метрик, логов или профилей).

### Структура сигналов в OTLP

-   **Трассировки (Span):** Содержат имя, `kind`, временные метки, атрибуты, события и ссылки. Идентификаторы передаются как байтовые массивы.
-   **Метрики (Metric):** Включают точки данных (`DataPoint`) с временными метками и значениями (`Gauge`, `Sum`, `Histogram`, `ExponentialHistogram`).
-   **Логи (LogRecord):** Включают тело сообщения (`Body`), уровень важности (`Severity`), временную метку и контекст (trace_id/span_id) для корреляции.
-   **Профили (Profile):** Колончатая структура для передачи данных непрерывного профилирования (Alpha).

### OTLP/Arrow (OTAP)

**OTLP/Arrow** — это расширение протокола, использующее формат Apache Arrow для передачи данных.
-   **Преимущества:** Обеспечивает до 10-кратного улучшения сжатия по сравнению со стандартным Protobuf за счёт колончатого представления данных.
-   **Применение:** Рекомендуется для высоконагруженных систем с миллионами спанов/метрик в секунду для снижения затрат на сеть и CPU.

## Практические сценарии

### Пример OTLP/HTTP (JSON)

Демонстрация иерархии для метрики типа `Gauge`:

```json
{
  "resourceMetrics": [
    {
      "resource": {
        "attributes": [
          {"key": "service.name", "value": {"stringValue": "payment-api"}}
        ]
      },
      "scopeMetrics": [
        {
          "scope": {"name": "http-server", "version": "1.0.0"},
          "metrics": [
            {
              "name": "http.server.active_requests",
              "gauge": {
                "dataPoints": [
                  {
                    "timeUnixNano": "1717428123000000000",
                    "asInt": "15",
                    "attributes": [{"key": "http.method", "value": {"stringValue": "POST"}}]
                  }
                ]
              }
            }
          ]
        }
      ]
    }
  ]
}
```

### Безопасность и аутентификация

OTLP поддерживает стандартные механизмы защиты:
-   **TLS/mTLS:** Обязателен для передачи через публичные сети.
-   **Заголовки (Headers):** Передача API-ключей или токенов через `x-otlp-api-key` или стандартный `Authorization`.
-   **Сжатие:** Поддержка `gzip` и `zstd` (рекомендуется `zstd` для лучшего баланса скорости/сжатия).

### Обработка частичного успеха (Partial Success)

При отправке батча данных Collector может вернуть статус `Partial Success`. Это означает, что часть сигналов была принята, а часть — отклонена (например, из-за нарушения схемы). SDK OpenTelemetry версии 1.x умеют обрабатывать эти ответы, не переотправляя успешно принятые данные.

## Дополнительная информация

### Транспорты и порты

| Транспорт | Порт | Особенности |
| :--- | :--- | :--- |
| **gRPC** | `4317` | Бинарный, HTTP/2, высокая производительность. |
| **HTTP/JSON** | `4318` | Текстовый, проще для отладки и прохождения через Proxy. |
| **HTTP/Protobuf** | `4318` | Бинарный Protobuf поверх HTTP. |
| **Arrow** | `4317/8` | Колончатый формат для High-Load. |

### Схема конфигурации Collector

Современная конфигурация (2026) с использованием Arrow и сжатия:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
        arrow: true # Включение поддержки Arrow
      http:
        endpoint: 0.0.0.0:4318

exporters:
  otlp:
    endpoint: "my-backend:4317"
    compression: zstd
    headers:
      "x-api-key": "${env:API_KEY}"
    tls:
      ca_file: /etc/otel/ca.crt

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp]
```
