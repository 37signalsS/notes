# OpenTelemetry: Протокол OTLP

## Определения

**OTLP (OpenTelemetry Protocol)** — это унифицированный протокол передачи данных, предназначенный для отправки телеметрических сигналов (трассировок, метрик, логов и профилей) из приложения в Collector или совместимый бэкенд. Он определяет стандартную схему данных на основе Protocol Buffers (Protobuf), что обеспечивает высокую эффективность, компактность и строгую типизацию.

**Статус в августе 2026 года:**
- **Все сигналы (Traces, Metrics, Logs, Profiles):** Стабильны (GA) и поддерживаются в рамках версии OTLP v1.x.
- **CNCF Status:** Проект OpenTelemetry официально имеет статус **Graduated** (с мая 2026).
- **Приоритеты:** OTLP/Arrow признан основным стандартом для высоконагруженных систем (High-Load), а gRPC остается предпочтительным транспортом для межсервисного взаимодействия.

## Основные концепции

### Иерархия данных

OTLP использует общую вложенную структуру для всех сигналов, что позволяет эффективно передавать метаданные и снижать избыточность:

1.  **Resource:** Контейнер верхнего уровня. Описывает источник телеметрии через атрибуты (`service.name`, `host.name`, `k8s.pod.name`). Все данные внутри одного сообщения `Resource` принадлежат одной и той же логической сущности.
2.  **Instrumentation Scope:** Группирует телеметрию по библиотеке или компоненту, который её сгенерировал (например, `io.opentelemetry.java-agent` версии `2.x`).
3.  **Signal Records:** Непосредственно записи данных (массив спанов, метрик, логов или профилей).

### Структура сигналов в OTLP

-   **Трассировки (Span):** Содержат имя, тип (`kind`), временные метки (start/end), атрибуты, события (`Events`) и ссылки (`Links`). Идентификаторы `trace_id` и `span_id` передаются как байтовые массивы.
-   **Метрики (Metric):** Включают точки данных (`DataPoint`) с временными метками и значениями. Поддерживаются типы `Gauge`, `Sum` (Monotonic/Non-monotonic), `Histogram` и `ExponentialHistogram` (Native Histograms).
-   **Логи (LogRecord):** Включают тело сообщения (`Body`), уровень важности (`Severity`), временную метку и контекст (`trace_id`/`span_id`) для бесшовной корреляции.
-   **Профили (Profile):** Используют колончатую структуру для передачи данных непрерывного профилирования, обеспечивая минимальный оверхед при передаче стеков вызовов.

### Кодирование данных (Encoding)

-   **Protobuf (Бинарный):** Основной формат для Production. Использует бинарное представление, минимизируя трафик и нагрузку на CPU.
-   **JSON (Текстовый):** Используется преимущественно для отладки, веб-инструментов и в Serverless-средах. Строго соответствует схеме Protobuf.

### Распространение контекста (Context Propagation)

OTLP обеспечивает передачу контекста наблюдаемости между узлами:
-   **W3C Trace Context:** Нативная поддержка заголовков `traceparent` и `tracestate` во всех транспортах.
-   **Baggage:** Передача пользовательских метаданных (key-value) сквозь всю цепочку вызовов.

## Транспорт и протоколы

### Сравнение реализаций

| Характеристика | gRPC | HTTP/1.1 (JSON/Protobuf) | OTLP/Arrow |
| :--- | :--- | :--- | :--- |
| **Порт по умолчанию** | `4317` | `4318` | `4317` (через gRPC) |
| **Транспорт (L4/L7)** | HTTP/2 (Binary) | HTTP/1.1 (Text/Binary) | HTTP/2 (Columnar) |
| **Производительность** | Высокая | Средняя | Максимальная |
| **Сценарий** | Backend-to-Backend | Web, Serverless, Proxy | High-Load, Collector-to-Collector |

### OTLP/Arrow (OTAP)

**OTLP/Arrow** — это расширение протокола, использующее формат Apache Arrow для колоночного представления данных.
-   **Преимущества:** Обеспечивает до 10-кратного улучшения сжатия по сравнению со стандартным Protobuf за счёт группировки схожих записей.
-   **Применение:** Рекомендуется при объемах трафика свыше 100 000 сигналов/сек или при передаче данных через дорогостоящие каналы связи.

## Практические сценарии

### Пример OTLP/HTTP (JSON)

Демонстрация иерархии для метрики типа `Gauge`:

```json
{
  "resourceMetrics": [
    {
      "resource": {
        "attributes": [
          {"key": "service.name", "value": {"stringValue": "payment-api"}}
        ]
      },
      "scopeMetrics": [
        {
          "scope": {"name": "http-server", "version": "1.0.0"},
          "metrics": [
            {
              "name": "http.server.active_requests",
              "gauge": {
                "dataPoints": [
                  {
                    "timeUnixNano": "1717428123000000000",
                    "asInt": "15",
                    "attributes": [{"key": "http.method", "value": {"stringValue": "POST"}}]
                  }
                ]
              }
            }
          ]
        }
      ]
    }
  ]
}
```

### Балансировка нагрузки L7 для gRPC

Так как gRPC использует долгоживущие HTTP/2 соединения, обычная балансировка L4 (TCP) приводит к неравномерному распределению нагрузки.
**Решение:** Использование L7-балансировщиков (Angie, Nginx, Envoy), которые умеют терминировать gRPC и распределять отдельные запросы (Streams) внутри одного соединения по разным узлам Collector.

### Обработка частичного успеха (Partial Success)

Если батч данных содержит некорректные записи (например, нарушение семантических конвенций), Collector может вернуть статус `Partial Success`.
-   **Действие SDK:** Современные SDK логируют ошибки, но не переотправляют батч повторно, чтобы избежать бесконечных циклов ретраев и дублирования корректных данных.

### Безопасность и аутентификация

-   **Шифрование:** Использование TLS/mTLS (порты 4317/4318) обязательно для всех внешних соединений.
-   **Аутентификация:**
    -   API-ключи: заголовок `x-otlp-api-key`.
    -   JWT/OAuth2: заголовок `Authorization` с валидацией через `oidc` расширение в Collector.
-   **Сжатие:** Рекомендуется `zstd` (лучший баланс скорости и степени сжатия в 2026 году) или `gzip`.

## Дополнительная информация

### Схема конфигурации Collector (2026)

Современная конфигурация с использованием Arrow и Zstd:

```yaml
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
        arrow: true # Включение поддержки Arrow
      http:
        endpoint: 0.0.0.0:4318

exporters:
  otlp:
    endpoint: "my-backend:4317"
    compression: zstd
    headers:
      "x-api-key": "${env:API_KEY}"
    tls:
      ca_file: /etc/otel/ca.crt

service:
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlp]
```

### Рекомендации по настройке (Best Practices)

-   **Persistent Queues:** Используйте `sending_queue` с дисковым хранилищем (`file_storage`) на стороне экспортеров Collector для предотвращения потери данных при сбоях сети.
-   **Батчинг:** Всегда настраивайте `batch` процессор для уменьшения количества сетевых запросов и повышения эффективности сжатия.
-   **Управление ресурсами:** Используйте `memory_limiter` процессор перед всеми остальными для предотвращения OOM при пиковых нагрузках.
