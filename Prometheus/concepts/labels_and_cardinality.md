# Лейблы и кардинальность в Prometheus

В данном разделе рассматривается фундаментальная модель данных Prometheus, основанная на многомерных временных рядах, и критическое понятие кардинальности, которое является определяющим фактором производительности, масштабируемости и стабильности системы мониторинга.

## Определения

* **Лейблы (Labels):** Ключевой элемент модели данных [Prometheus](../overview.md). Представляют собой пары `ключ="значение"`, которые добавляют [метрикам](./metric_types/overview.md) контекст и дополнительные измерения. Каждая уникальная комбинация лейблов для одного имени метрики создает новый объект в базе данных.
* **Временной ряд (Time Series):** Поток маркированных временем значений (сэмплов), относящихся к одной и той же метрике и одному и тому же набору лейблов. Идентифицируется парой `{__name__="metric_name", label1="val1", ...}`.
* **Кардинальность (Cardinality):** Количество уникальных временных рядов. В контексте одной метрики — это количество уникальных комбинаций значений её лейблов. В масштабе сервера — общее число активных серий в **[TSDB](./tsdb.md)**.
* **Высокая кардинальность (High Cardinality):** Ситуация, когда метрики имеют избыточное количество уникальных значений меток (например, ID пользователей или запросов), что приводит к экспоненциальному росту потребления ресурсов.
* **Churn Rate (Текучесть рядов):** Скорость, с которой старые временные ряды перестают получать данные и создаются новые. Высокий Churn Rate создает нагрузку на индекс даже при стабильном общем количестве активных рядов.

> **См. также:** [Внутреннее устройство TSDB](./tsdb.md) — глубокое погружение в механизмы хранения и индексации.

## Базовые концепции

### Роль лейблов в многомерном анализе

Лейблы позволяют выполнять сложные операции фильтрации и агрегации без необходимости создания тысяч отдельных метрик. Вместо плоских имен вроде `http_errors_api_v1_500` используется структурированный подход:
`http_requests_total{api_version="v1", status="500", method="POST"}`.
Это позволяет одной командой PromQL вычислить, например, общий процент ошибок по всем методам и версиям API.

### Поддержка UTF-8 и OpenTelemetry (v3.0+)

Начиная с версии 3.0, Prometheus перешёл на полную поддержку UTF-8 в именах метрик и лейблов. Это критично для интеграции с **OpenTelemetry (OTel)**, так как позволяет сохранять нативные имена атрибутов:
*   `http.server.request.duration{service.instance.id="xyz"}` — теперь является валидным временным рядом.
*   Ранее точки и другие символы требовали автоматической замены на подчеркивания (`_`), что приводило к потере семантики.

### Нативные гистограммы (Native Histograms): технический прорыв

Одним из главных инструментов борьбы с кардинальностью в Prometheus v3.x стали **Native Histograms**.

1.  **Классический подход (Classic Histograms):**
    Для гистограммы с 10 бакетами создается 10+ отдельных временных рядов с лейблом `le="<bucket_value>"`, плюс ряды для `_sum` и `_count`.
    *   Пример структуры:
        ```
        http_request_duration_seconds_bucket{le="0.1"}
        http_request_duration_seconds_bucket{le="0.5"}
        ...
        http_request_duration_seconds_sum
        http_request_duration_seconds_count
        ```
    Это "взрывает" кардинальность, особенно при использовании множества лейблов.

2.  **Нативный подход (Native Histograms):**
    Все данные распределения упаковываются в **один** временной ряд.
    *   **Техническая реализация:** используется динамическая экспоненциальная сетка бакетов. Вместо создания множества серий с лейблом `le`, структура гистограммы хранится внутри каждого сэмпла как сложный объект.
    *   **Результат:** снижение нагрузки на индекс TSDB в 10–50 раз при сохранении или улучшении точности вычислений квантилей.

### Зарезервированные и внутренние лейблы

*   `__name__`: Служебный лейбл для имени метрики. Запрос `up` эквивалентен `{__name__="up"}`.
*   `__address__`: Первичный адрес цели (IP:Port), используется до этапа релабелинга.
*   `__meta_*`: Метаданные от систем обнаружения сервисов (например, `__meta_kubernetes_pod_name`). Доступны только на этапе конфигурации сбора.
*   Метки, начинающиеся и заканчивающиеся на `__`, считаются внутренними и удаляются после завершения [relabeling](../service_discovery_and_relabeling.md).

### Почему высокая кардинальность — это угроза?

1.  **RAM (Memory):** Для каждого временного ряда Prometheus держит в памяти "Head" кусок (индексы и последние сэмплы). При 1 млн рядов потребление RAM может составлять 4–8 ГБ и более.
2.  **CPU:** Расчёт агрегаций (например, `sum by (user_id)`) по миллионам рядов требует колоссальных вычислительных мощностей.
3.  **Inverted Index:** Кардинальность раздувает файл `index` в блоках TSDB. Поиск по лейблам с миллионами значений становится медленным, так как приходится сканировать огромные списки идентификаторов серий (postings).
4.  **OOM Killer:** Самый частый исход — аварийная остановка процесса из-за нехватки памяти при попытке выполнить "тяжелый" запрос.

## Практические сценарии

### Расчёт потенциальной кардинальности

Формула: `Общая кардинальность = Π (количество уникальных значений каждого лейбла)`.

**Пример:**
Метрика `http_requests_total` с лейблами:
*   `method`: 5 значений (GET, POST, ...)
*   `status`: 10 значений (200, 404, ...)
*   `path`: 100 значений (/api/v1/login, ...)
*   **Кардинальность:** 5 × 10 × 100 = **5 000 рядов**.

Если добавить `user_id` (1 000 000 пользователей):
5 × 10 × 100 × 1 000 000 = **5 000 000 000 рядов**. Это приведет к немедленному падению любого стандартного экземпляра Prometheus.

### Анализ кардинальности через PromQL

**1. Топ-10 метрик по количеству серий:**
```promql
topk(10, count by (__name__) ({__name__=~".+"}))
```

**2. Метрики с аномальным ростом за последний час:**
```promql
topk(10, count by (__name__) ({__name__=~".+"}) - count by (__name__) ({__name__=~".+"} offset 1h))
```

**3. Подсчёт уникальных значений конкретного лейбла для метрики:**
```promql
# Сколько уникальных путей (path) видит метрика
count(count by (path) (http_requests_total))
```

**4. Анализ Churn Rate (создание новых серий):**
```promql
# Скорость создания новых рядов в секунду
rate(prometheus_tsdb_head_series_created_total[5m])
```

**5. Поиск "мусорных" лейблов (высокая вариативность):**
```promql
# Список метрик, где количество серий превышает 5000
count by (__name__) ({__name__=~".+"}) > 5000
```

### Использование Metadata API

Prometheus предоставляет API для анализа метаданных и лейблов, что полезно для поиска источников высокой кардинальности без выполнения тяжелых PromQL-запросов.

**Получить все уникальные значения лейбла:**
```bash
curl -G 'http://localhost:9090/api/v1/label/path/values' --data-urlencode 'start=-2h'
```

**Получить кардинальность через статус API (TSDB Status):**
```bash
curl 'http://localhost:9090/api/v1/status/tsdb'
```
Этот эндпоинт возвращает JSON с топ-10 метрик по количеству серий, топ-10 лейблов по количеству значений и другую статистику.

### Защита через Scrape Limits

Устанавливайте жесткие границы в `prometheus.yml`, чтобы защитить сервер от "взрыва" данных.

```yaml
scrape_configs:
  - job_name: 'api-service'
    # Лимиты сбора (Scrape Limits):
    sample_limit: 10000        # Ошибка, если таргет отдает >10000 метрик
    target_limit: 50           # Максимум 50 инстансов в этом задании
    label_limit: 60            # Максимум 60 лейблов на одну серию
    label_name_length_limit: 64
    label_value_length_limit: 512
    
    # Лимиты на этапе релабелинга:
    metric_relabel_configs:
      - source_labels: [user_id]
        action: labeldrop       # Удаление опасного лейбла, если он просочился
```

### Борьба с Churn Rate

В динамических средах (Kubernetes) ряды часто "умирают" из-за смены имен подов.

**Лучшие практики по снижению Churn Rate:**
1.  **Агрегация по Workload:** В лейблах используйте имя Deployment/StatefulSet вместо имени пода, если детализация до пода не критична для данной метрики.
2.  **Удаление эфемерных лейблов:** Удаляйте лейблы вроде `pod_template_hash` или `controller_revision_hash` на этапе релабелинга.
3.  **Нормализация путей (URL):** Если приложение не шаблонизирует пути, делайте это в Prometheus:
    ```yaml
    metric_relabel_configs:
      - source_labels: [path]
        regex: '/api/v1/users/[0-9]+'
        target_label: path
        replacement: '/api/v1/users/:id'
    ```
4.  **Scrape Interval:** Увеличение интервала с 15с до 60с для второстепенных сервисов снижает нагрузку на индекс.

### Алерты на высокую кардинальность

```yaml
groups:
- name: cardinality_management
  rules:
  # Алерт на общее количество рядов
  - alert: PrometheusHighSeriesCount
    expr: prometheus_tsdb_head_series > 1000000
    for: 15m
    labels:
      severity: warning
    annotations:
      summary: "Высокое количество временных рядов"
      description: "Текущее число активных рядов: {{ $value }}"

  # Алерт на взрывной рост новых рядов
  - alert: CardinalityExplosion
    expr: rate(prometheus_tsdb_head_series_created_total[5m]) > 500
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "Взрыв кардинальности обнаружен"
      description: "Скорость создания новых рядов: {{ $value | humanize }} серий/сек"
```

## Дополнительная информация

### Рекомендации по ресурсам (Prometheus v3.x)

| Кол-во рядов | CPU | RAM | Режим работы |
| :--- | :--- | :--- | :--- |
| до 100 000 | 2 ядра | 4 ГБ | Single Instance |
| 100k — 1M | 4–8 ядер | 8–16 ГБ | Single Instance / Agent |
| 1M — 5M | 8–16 ядер | 32–64 ГБ | Оптимизированный TSDB |
| > 5M | 16+ ядер | 128 ГБ+ | Рекомендуется **[масштабирование](../scaling/overview.md)** |

### Инструментарий для глубокого анализа

**promtool tsdb analyze:**
Позволяет провести офлайн-анализ базы данных на диске. Это самый мощный способ найти "виновников" кардинальности.
```bash
promtool tsdb analyze /path/to/tsdb/data
```
Результат покажет:
*   Топ-10 метрик по количеству серий.
*   Топ-10 лейблов по количеству значений.
*   Метрики с самым большим размером на диске.

**Prometheus Web UI (v3.0+):**
Новый интерфейс включает вкладку **Explain** в консоли запросов, которая показывает количество затронутых рядов для каждого этапа выполнения запроса.
