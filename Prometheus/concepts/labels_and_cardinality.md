# Лейблы и кардинальность в Prometheus

## Определения

* **Лейблы (Labels):** Фундаментальная часть модели данных [Prometheus](../overview.md). Представляют собой пары `ключ="значение"`, которые добавляют [метрикам](./metric_types.md) измерения или "контекст".
* **Временной ряд (Time Series):** Отдельная последовательность значений метрики, идентифицируемая уникальной комбинацией имени метрики и ее лейблов. Каждая уникальная комбинация лейблов для одного имени метрики формирует отдельный **[временной ряд](./tsdb.md)**.
* **Кардинальность (Cardinality):** Количество уникальных временных рядов. Определяется числом уникальных комбинаций лейблов.
* **Высокая кардинальность (High Cardinality):** Состояние, когда метрики имеют слишком много уникальных значений лейблов, что приводит к созданию огромного количества временных рядов. Является одной из самых частых и серьезных проблем при работе с Prometheus.

> **См. также:** [TSDB и влияние кардинальности на хранение](./tsdb.md) — как кардинальность влияет на производительность базы данных.

## Основные концепции

### Роль лейблов

Лейблы позволяют фильтровать, группировать и агрегировать данные. Они добавляют метрикам контекст, отвечая на вопросы «кто?», «откуда?» и «с какими параметрами?» была получена метрика. Вместо того чтобы создавать множество метрик вроде `http_requests_total_api_v1_post` и `http_requests_total_api_v2_get`, используется одна метрика с лейблами:

```
http_requests_total{path="/api/v1", method="post"}
http_requests_total{path="/api/v2", method="get"}
```

### Зарезервированные лейблы

Имя метрики по сути также является лейблом: `__name__=<имя_метрики>`. Существуют и другие внутренние лейблы, которые начинаются и заканчиваются двумя знаками подчеркивания (например, `__scheme__`, `__address__`).

### Почему высокая кардинальность — это плохо?

1. **Высокое потребление памяти:** Prometheus хранит в памяти метаданные и недавние сэмплы для каждого временного ряда. Большое количество рядов напрямую ведет к росту потребления RAM.
2. **Снижение производительности:** Запросы ([PromQL](./promql.md)) становятся медленнее, так как им приходится обрабатывать больше данных.
3. **Нагрузка на TSDB:** Увеличивается размер индекса в базе данных, что замедляет запись и сжатие данных.
4. **Риск OOM (Out Of Memory):** В крайних случаях Prometheus может исчерпать всю доступную память и быть остановлен системой (OOM Killer).

### Формула расчёта кардинальности

```
Общая кардинальность = Σ(уникальные комбинации лейблов для каждой метрики)
```

**Пример:**
* Метрика `http_requests_total` с лейблами:
  * `method`: 5 значений (GET, POST, PUT, DELETE, PATCH)
  * `status`: 10 значений (200, 201, 400, 404, 500, ...)
  * `path`: 100 значений (/api/users, /api/orders, ...)
* **Кардинальность:** 5 × 10 × 100 = **5 000 временных рядов**

Если добавить `user_id` (1 000 000 пользователей): 5 × 10 × 100 × 1 000 000 = **5 000 000 000 рядов** — это приведёт к падению Prometheus.

## Практические сценарии

### Как избежать высокой кардинальности: лучшие практики

Основное правило: **Никогда не используйте в значениях лейблов данные с высокой степенью уникальности.**

**Что НЕЛЬЗЯ использовать в лейблах:**

* **ID пользователей, сессий, запросов:** `user_id="1be5...f9d"`, `session_id="xyz..."`
* **Email-адреса, IP-адреса клиентов**
* **Временные метки (timestamps)**
* Любые другие неограниченные или непредсказуемые значения.

**Пример плохого дизайна:**

Предположим, у нас есть метрика `http_requests_total`.

* `http_requests_total{method="GET", status="200"}` — **Низкая кардинальность**. У нас ограниченное число методов и статусов.
* `http_requests_total{method="GET", path="/api/users/1"}`
* `http_requests_total{method="GET", path="/api/users/2"}`
    ...
    `http_requests_total{method="GET", path="/api/users/100000"}` — **Высокая кардинальность**. Если у вас 100 000 пользователей и вы включаете их ID в URL, вы создадите 100 000 временных рядов. Вместо этого URL должен быть шаблонизирован (например, на этапе [relabeling](../service_discovery_and_relabeling.md)): `http_requests_total{method="GET", path="/api/users/:id"}`.

**Что МОЖНО использовать в лейблах:**

* Имена сервисов, джоб (`job="node-exporter"`).
* Имена инстансов (`instance="server-1"`).
* Эндпоинты API (`path="/api/users"`).
* Коды ответов HTTP (`status="500"`).
* Типы окружения (`env="production"`).

### Примеры PromQL для анализа кардинальности

**Подсчёт количества временных рядов для метрики:**

```promql
# Количество временных рядов для http_requests_total
count(http_requests_total)

# Количество рядов по каждой метрике (топ-10)
topk(10, count by (__name__) ({__name__=~".+"}))
```

**Поиск метрик с высокой кардинальностью:**

```promql
# Метрики с более чем 1000 временных рядов
count by (__name__) ({__name__=~".+"}) > 1000
```

**Анализ лейблов с высокой кардинальностью:**

```promql
# Сколько уникальных значений имеет лейбл path
count by (path) (http_requests_total)

# Сколько уникальных инстансов
count by (instance) (up)
```

### Алерты на высокую кардинальность

**Алерт на общее количество рядов:**

```yaml
- alert: HighCardinality
  expr: count({__name__=~".+"}) > 100000
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "Высокая кардинальность в Prometheus"
    description: "Общее количество временных рядов: {{ $value | humanize }}"
```

**Алерт на быстрый рост кардинальности:**

```yaml
- alert: RapidCardinalityGrowth
  expr: |
    deriv(count({__name__=~".+"})[1h]) > 1000
  for: 15m
  labels:
    severity: critical
  annotations:
    summary: "Быстрый рост кардинальности"
    description: "Скорость роста: {{ $value | humanize }} рядов/час"
```

**Алерт на метрику с аномально высокой кардинальностью:**

```yaml
- alert: HighCardinalityMetric
  expr: |
    count by (__name__) ({__name__=~".+"}) > 5000
  for: 30m
  labels:
    severity: warning
  annotations:
    summary: "Метрика {{ $labels.__name__ }} имеет высокую кардинальность"
    description: "Количество рядов: {{ $value | humanize }}"
```

> **См. также:** [Rules и алертинг](../rules.md) — руководство по созданию правил.

### Практика: шаблонизация URL

**Проблема:** В приложении URL с ID пользователей попадает в лейблы:

```
http_requests_total{path="/api/users/123"}
http_requests_total{path="/api/users/456"}
```

**Решение 1: Изменение кода приложения**

```python
# Вместо этого:
labels = {"path": f"/api/users/{user_id}"}

# Используйте:
labels = {"path": "/api/users/:id"}
```

**Решение 2: Relabeling в Prometheus**

```yaml
scrape_configs:
  - job_name: 'api'
    metric_relabel_configs:
      - source_labels: [path]
        regex: '/api/users/[^/]+'
        target_label: path
        replacement: '/api/users/:id'
```

> **См. также:** [Service Discovery и Relabeling](../service_discovery_and_relabeling.md) — полное руководство.

## Дополнительная информация

### Churn Rate

Помимо статической кардинальности, существует проблема **churn rate** — скорости, с которой временные ряды появляются и исчезают. Это характерно для сред с коротким временем жизни объектов, например, контейнеров в Kubernetes. Частая смена состава временных рядов также создает нагрузку на Prometheus, так как он вынужден хранить метаданные даже для "мертвых" рядов до тех пор, пока они не будут удалены из [TSDB](./tsdb.md).

**Метрики для отслеживания churn rate:**

```promql
# Скорость создания новых рядов
rate(prometheus_tsdb_head_series_created_total[5m])

# Скорость удаления рядов
rate(prometheus_tsdb_head_series_removed_total[5m])

# Текущее количество активных рядов
prometheus_tsdb_head_series
```

> **Подробное описание:** [TSDB — Churn Rate](./tsdb.md#churn-rate-скорость-обновления-рядов).

### Рекомендации по лимитам кардинальности

| Размер Prometheus | Рекомендуемый лимит рядов | Максимальный лимит |
|---|---|---|
| Малый (1 CPU, 2GB RAM) | 10 000 – 50 000 | 100 000 |
| Средний (2 CPU, 4GB RAM) | 50 000 – 200 000 | 500 000 |
| Крупный (4+ CPU, 8GB+ RAM) | 200 000 – 500 000 | 1 000 000+ |

**Важно:** Эти значения приблизительные. Фактические лимиты зависят от:
* Сложности запросов PromQL
* Частоты скрейпинга
* Настроек retention period
* Аппаратных ресурсов
