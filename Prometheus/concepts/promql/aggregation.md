# Агрегация в PromQL

## Определения

**Агрегация** — операция объединения множества временных рядов в один результат. Операторы агрегации принимают **instant vector** (вектор мгновенных значений) и возвращают агрегированный вектор с уменьшенным количеством рядов.

Актуально для **Prometheus v3.0+**, включая стабильную поддержку **Native Histograms** и экспериментальные операторы лимитирования.

**Ключевые модификаторы:**

- `by (<label_list>)` — группировка по указанным лейблам. Все лейблы, не указанные в списке, удаляются из результата.
- `without (<label_list>)` — агрегация по всем лейблам, **кроме** указанных. Используется, когда нужно сохранить большинство лейблов, удалив лишь специфические (например, `instance` или `pod`).
- **Поддержка UTF-8 (v3.0):** Модификаторы теперь корректно работают с именами лейблов, содержащими любые символы (например, `sum by ("http.status.code")`).

## Базовые концепции

### Синтаксис агрегации

Операторы агрегации могут записываться двумя способами:

```promql
# Способ 1: Модификатор после имени оператора
<aggr_op> [parameter] by(<labels>) (<vector_expr>)

# Способ 2: Модификатор после выражения
<aggr_op> [parameter] (<vector_expr>) by(<labels>)
```

### Механика `by` и `without`

Понимание разницы между `by` и `without` критично для контроля лейблов в результате.

| Модификатор | Поведение | Пример |
|:---|:---|:---|
| `by (le, method)` | Сохраняет **только** указанные лейблы | `sum by (le, method) (rate(bucket[5m]))` |
| `without (instance, pod)` | Сохраняет **все**, кроме указанных | `sum without (instance, pod) (container_memory)` |

**Правила:**
- При `by` в результате остается **ровно** указанный набор лейблов.
- При `without` в результате остается **все, кроме** указанных, включая системные (`__name__` не сохраняется).
- Если после `by`/`without` все ряды попадают в одну группу, результат — один ряд.
- Если ни один ряд не проходит фильтрацию, результат — **пустой вектор** (без строк).

### Векторное сопоставление vs агрегация

| Механизм | Область применения | Кардинальность | Пример |
|:---|:---|:---|:---|
| **Агрегация** (`by`/`without`) | Объединение рядов **внутри одного** вектора | N → 1 или N → M | `sum by (job) (up)` |
| **Vector Matching** (`on`/`ignoring`) | Сопоставление **двух** векторов при бинарной операции | many-to-one | `a * on(instance) group_left() b` |

> **Важно:** Агрегация никогда не пересекает границы векторов. Для объединения данных из двух метрик используйте бинарные операторы с `on`/`ignoring` или `group_left`/`group_right`. Подробнее — [Операции с векторами](./vector_operations.md).

### Порядок вычислений и вложенная агрегация

Prometheus вычисляет агрегацию **после** всех внутренних выражений. Это означает:

```promql
# Правильно: сначала rate, потом агрегация
sum by (job) (rate(http_requests_total[5m]))

# Ошибочно: сначала агрегируем сырые счетчики, потом rate
# Это приведет к некорректному учету сбросов
rate(sum(http_requests_total)[5m])
```

**Вложенная агрегация:**
- `sum(sum by (...))` можно заменить на `sum by (...)` для снижения нагрузки.
- Вложенные агрегации с разными модификаторами вычисляются последовательно, снизу вверх.

### Агрегация и пустые результаты

Если ни один ряд не проходит условие агрегации, Prometheus возвращает пустой вектор:

```promql
# Если нет рядов с code="5xx", результат — пустой вектор
sum(rate(http_requests_total{code="5xx"}[5m]))
# → (empty result)
```

Для диагностики используйте `count_over_time` или `absent_over_time`:

```promql
# Проверка: есть ли данные в принципе
count_over_time(http_requests_total[5m])
# → 0 (нет данных)

# Алерт на отсутствие данных после агрегации
absent(sum by (job) (rate(http_requests_total[5m]))) == 1
```

### Операторы мгновенной агрегации

| Оператор | Описание | Пример |
|----------|----------|--------|
| `sum()` | Сумма значений. Поддерживает **Native Histograms** (суммирует бакеты). | `sum by (job) (up)` |
| `avg()` | Среднее арифметическое. Для Native Histograms вычисляет среднее распределение. | `avg(node_load1)` |
| `count()` | Количество временных рядов в группе. | `count(up == 1)` |
| `min()`, `max()` | Минимальное или максимальное значение. | `max(node_cpu_seconds_total)` |
| `stddev()`, `stdvar()` | Стандартное отклонение и дисперсия. | `stddev(http_request_duration_seconds)` |
| `topk(k, v)` | `k` рядов с наибольшими значениями. | `topk(5, rate(http_requests_total[5m]))` |
| `bottomk(k, v)` | `k` рядов с наименьшими значениями. | `bottomk(3, node_memory_MemFree_bytes)` |
| `limitk(k, v)` | Ограничивает результат `k` рядами (без сортировки). | `limitk(10, up)` |
| `limit_ratio(r, v)` | Возвращает долю `r` (0-1) от общего количества рядов. | `limit_ratio(0.1, up)` |
| `count_values(label, v)` | Считает количество рядов для каждого уникального значения `v`. | `count_values("version", build_info)` |
| `quantile(φ, v)` | φ-квантиль (0 ≤ φ ≤ 1) по значениям в векторе. | `quantile(0.95, rate(http_requests_total[5m]))` |
| `group()` | Группирует ряды, устанавливая значение в `1`. | `group by (region) (up)` |

**Особенности использования:**
- **Native Histograms (v3.0):** Операторы `sum` и `avg` автоматически выполняют *reconciliation* (согласование), если у рядов в группе разные разрешения бакетов (buckets resolution).
- **`topk` и `bottomk`**: Нестабильны для визуализации на графиках (линии могут прерываться при изменении состава топ-листа).
- **`limitk` и `limit_ratio` (v3.0 exp):** Позволяют эффективно сэмплировать или ограничивать выборку при работе с очень высокой кардинальностью, когда точный порядок не важен.
- **`count_values`**: Создает новый лейбл (аргумент 1), значением которого становится значение метрики.
- **`group()`**: Полезен для проверки наличия ряда с определенным набором лейблов. Возвращает `1` для каждого уникального набора лейблов.
- **`quantile()` vs `histogram_quantile()`**: `quantile()` работает на значениях в векторе (в памяти), а `histogram_quantile()` работает на классических гистограммах с лейблом `le`. Подробнее — [Перцентили и квантили](../metric_types/percentiles.md).

### Агрегация по времени (..._over_time)

Эти функции принимают **range vector** и возвращают **instant vector**, выполняя вычисления внутри временного окна для *каждого* ряда отдельно.

| Функция | Описание |
|---------|----------|
| `avg_over_time(range)` | Среднее значение в интервале. |
| `min_over_time(range)`, `max_over_time(range)` | Минимум/максимум в интервале. |
| `sum_over_time(range)` | Сумма всех значений в интервале. |
| `count_over_time(range)` | Количество точек (сэмплов) в интервале. |
| `first_over_time(range)`, `last_over_time(range)` | Самое старое / самое новое значение в интервале. |
| `stddev_over_time(range)`, `stdvar_over_time(range)` | Отклонение и дисперсия в интервале. |
| `quantile_over_time(φ, range)` | φ-квантиль значений в интервале. |
| `mad_over_time(range)` | Медианное абсолютное отклонение (поиск аномалий). |
| `present_over_time(range)` | Возвращает `1`, если в интервале есть данные. |
| `absent_over_time(range)` | Возвращает `1`, если в интервале нет данных. |

**Особенности:**
- **`absent_over_time()`** — критична для алертинга. Возвращает `1` (истина), если за указанный интервал нет ни одной точки. Это позволяет детектировать полное пропадание метрики.
- **`present_over_time()`** — обратная операция: возвращает `1`, если данные есть, даже если их значение `0`.
- **`first_over_time` / `last_over_time`** — полезны для определения момента старта/остановки процесса.
- **`mad_over_time`** — медианное абсолютное отклонение. Устойчиво к выбросам, поэтому подходит для поиска аномалий.

## Практические сценарии

### Выбор между `by` и `without`

Используйте `without`, когда вы хотите сохранить контекст (например, `application`, `env`), но агрегировать эфемерные лейблы:

```promql
# Агрегируем все поды, сохраняя информацию о приложении и окружении
sum without (pod, instance) (container_memory_usage_bytes)
# → {application="api", env="prod"} 2147483648
```

Используйте `by`, когда вам нужен строго определенный набор лейблов в результате:

```promql
# Сумма запросов только в разрезе HTTP-методов
sum by (method) (http_requests_total)
# → {method="GET"} 500, {method="POST"} 120
```

### Агрегация нативных гистограмм (v3.0)

Нативные гистограммы не требуют группировки по лейблу `le`.

```promql
# Суммарное распределение латентности по всем инстансам сервиса
sum by (service) (rate(http_request_duration_seconds[5m]))
# → {service="auth"} (Native Histogram с суммарными бакетами)
```

### Расчёт доли ошибок в процентах

```promql
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m])) * 100
# → {} 2.5
```

### Поиск аномалий через медианное отклонение

```promql
# Ряды, чьё значение сильно отклоняется от медианы за последний час
node_load1 > (
  avg_over_time(node_load1[1h]) + 3 * mad_over_time(node_load1[1h])
)
# → {instance="node-4"} 15.2 (при среднем 1.5)
```

### Inventory версий через `count_values`

```promql
# Подсчет количества инстансов по версии
count_values("version", build_info)
# → {version="v1.2.3"} 12, {version="v1.2.4"} 8
```

### Проверка наличия групп через `group()`

```promql
# Какие деплойменты имеют хотя бы один running под
group by (deployment, namespace) (kube_pod_info)
# → {deployment="api", namespace="prod"} 1
```

### Детектирование пропавших метрик после агрегации

```promql
# Алерт: отсутствуют данные по какому-либо job после агрегации
count by (job) (up) < count(job)
# → (пустой результат, если все job присутствуют)
```

### Ограничение кардинальности через `limitk`

```promql
# Оставить только 10 самых активных namespace (без сортировки)
limitk(10, sum by (namespace, pod) (container_cpu_usage_seconds_total))
# Полезно для дашбордов с высокой кардинальностью
```

### Агрегация для федерации (Multi-cluster)

```promql
# В recording rule на leaf-ноде:
# Сумма RPS по всем кластерам
sum by (service, region) (rate(requests_total[5m]))

# На master-ноде федераation просто суммирует уже агрегированные ряды
```

## Дополнительная информация

### Предостережения

- **Агрегация Counter**: Никогда не агрегируйте "сырые" счетчики напрямую (`sum(http_requests_total)`). Сначала `rate()` или `increase()`, затем `sum()`. В обратном порядке сбросы счетчиков (resets) при рестартах подов приведут к некорректным результатам.
- **Агрегация Native Histograms (v3.0)**: `sum` и `avg` **не позволяют** смешивать обычные float-метрики и гистограммы в одной группе агрегации. Ряды несовпадающих типов будут исключены из результата.
- **Агрегация Summary**: Квантили из Summary нельзя усреднять или суммировать. Используйте `max` для оценки худшего случая или перейдите на Histogram.
- **Агрегация Classic Histogram**: Для получения верного квантиля через `histogram_quantile` всегда используйте `sum by (le)`.
- **Неаддитивные величины**: Нельзя суммировать температуры, проценты загрузки CPU (средняя по ядрам) или медианы напрямую. Используйте `avg` вместо `sum`.
- **Эфемерные лейблы**: Избегайте `by (pod, instance)` в долгоживущих recording rules, так как поды пересоздаются. Используйте `by (deployment, namespace)`.

### Подзапросы (Subqueries) и агрегация

Подзапросы позволяют применять функции `..._over_time` к результатам мгновенных вычислений:

```promql
# Максимальный пятиминутный RPS, зафиксированный за последние сутки
max_over_time(sum(rate(http_requests_total[5m]))[24h:1m])
# → {} 450.0
```

**Производительность:**
- Подзапрос вычисляет внутренний запрос для каждого шага. При `range=24h` и `step=1m` это 1440 вычислений.
- Рекомендуемый шаг: не менее `4 * scrape_interval`.
- Подробнее о синтаксисе — [Операции с векторами](./vector_operations.md).

### Типичные ошибки агрегации

| Ошибка | Причина | Решение |
|--------|---------|---------|
| `sum(rate(...))` vs `rate(sum(...))` | Неправильный порядок функций | Сначала `rate()`, затем `sum()` для корректного учета сбросов |
| Отсутствует `le` в `sum by (le)` | Классические гистограммы разбиваются | Добавьте `le` в модификатор `by` |
| Суммирование неаддитивных метрик | Температура, процент | Используйте `avg()` вместо `sum()` |
| Смесь типов в агрегации (v3.0) | Float + Native Histogram в одной группе | Разделите запрос или фильтруйте по типу |
| `topk`/`bottomk` на графиках | Нестабильность состава топ-листа | Используйте `topk` только в алертах или таблицах |
| `count_values` с конфликтом имен | Новый лейбл совпадает с существующим | Переименуйте аргумент `count_values("ver", metric)` |
| Пустой результат после `without` | Удалены все лейблы, включая `__name__` | Добавьте хотя бы один лейбл в `by` |
| `absent_over_time` на сервис-дискавери | Метрика отсутствует, а не устарела | Используйте `up == 0 or absent_over_time(up[5m])` |

### Производительность агрегации

| Операция | Стоимость | Рекомендация |
|----------|-----------|--------------|
| `sum by (job)` | Низкая | Безопасно для алертов и дашбордов |
| `sum by (pod)` | Средняя | Осторожно с высокой кардинальностью |
| `sum by (le)` | Средняя | Обязательно для классических гистограмм |
| `topk(10, ...)` | Средняя | Ограничьте `k` для производительности |
| `limitk(100, ...)` | Низкая | Эффективна для высококардинальных метрик |
| `avg_over_time(...[1h])` | Высокая | Увеличьте `step` в range query |
| Подзапрос `[...:1m]` | Очень высокая | Используйте шаг ≥ 4× scrape_interval |
