# Селекторы и операторы PromQL

## Определения

**Селектор (Selector)** — выражение для выбора временных рядов по имени метрики и [лейблам](../labels_and_cardinality.md). Селектор определяет набор временных рядов, над которыми выполняются дальнейшие операции PromQL. Селектор является фундаментом любого запроса: он фильтрует данные до любых вычислений.

**Матчер (Matcher)** — оператор сравнения внутри селектора (`{...}`), фильтрующий временные ряды по значениям лейблов. Матчеры применяются ко всем лейблам сериализованного ряда, включая служебные (`__name__`, `job`, `instance`).

**Оператор** — математическая, сравнительная или логическая операция, применяемая к векторам и скалярам.

**Subquery (Подзапрос)** — синтаксис, позволяющий выполнять запросы над диапазоном времени, возвращая range vector из результатов выполнения instant-запроса с заданным интервалом.

## Базовые концепции

### Типы векторов в селекторах

В селекторах используются три основных типа векторов (подробнее см. [Типы данных PromQL](./data_types.md)):

* **Instant Vector** — набор временных рядов, содержащий по одному значению на конкретный момент времени.
* **Range Vector** — набор временных рядов, содержащий массив значений за интервал времени (синтаксис `[duration]`).
* **Subquery** — позволяет использовать функции над результатами других запросов за период (синтаксис `[range:resolution]`).

**Единицы времени:** `s` (секунды), `m` (минуты), `h` (часы), `d` (дни), `w` (недели), `y` (годы).

### Матчеры лейблов

Для фильтрации по лейблам внутри селектора используются четыре типа матчеров:

| Матчер | Описание | Пример |
|:---|:---|:---|
| `=` | Точное равенство | `job="node-exporter"` |
| `!=` | Неравенство | `method!="GET"` |
| `=~` | Соответствие регулярному выражению | `job=~"api-server\|web-server"` |
| `!~` | Несоответствие регулярному выражению | `status!~"5.."` |

**Системный лейбл `__name__`:** используется для фильтрации по имени метрики. Это позволяет выбирать несколько метрик одним селектором через регулярные выражения.
*   Пример: `{__name__=~"http_requests_.*"}` выберет все метрики, начинающиеся с этого префикса.
*   `metric_name{label="val"}` эквивалентно `{__name__="metric_name", label="val"}`.

**UTF-8 поддержка:** Начиная с Prometheus 2.55/3.0, поддерживаются любые UTF-8 символы в именах лейблов. Если имя содержит спецсимволы, используйте кавычки: `{"имя лейбла"="значение"}`.

### Семантика матчеров и регулярных выражений

**Регулярные выражения (RE2):** Prometheus использует движок RE2, который гарантирует линейное время выполнения и защищает от catastrophic backtracking. Однако сложные паттерны всё равно создают нагрузку на CPU при скейлинге.

**Автоматическое якорение:** Матчеры `=~` и `!~` автоматически добавляют привязку к началу и концу строки (`^...$`). Например, `job=~"api"` эквивалентно `job=~"^api$"`. Для частичного совпадения используйте `.*`: `job=~".*api.*"`.

**Регистрозависимость:** Все матчеры чувствительны к регистру. Для нечувствительного поиска используйте `(?i)` в regex: `job=~"(?i)API"`.

**Служебные лейблы:** В каждом селекторе неявно присутствует лейбл `__name__` при использовании короткого синтаксиса `metric_name{...}`. Явное указание `__name__` позволяет комбинировать метрики в одном селекторе.

### Модификаторы времени

| Модификатор | Описание | Пример |
|:---|:---|:---|
| `offset <duration>` | Сдвиг запроса в прошлое или будущее | `http_requests_total offset 1d` |
| `@ <timestamp>` | Фиксация на конкретное время (Unix timestamp) | `node_memory_MemAvailable_bytes @ 1609459200` |

* **Отрицательный offset:** `offset -1h` сдвигает запрос в будущее (полезно для тестирования и прогнозов).
* **Модификатор @:** может принимать `start()` и `end()` внутри range-запросов.
* **Правило 4 точек для offset:** При использовании `offset` убедитесь, что окно `[range]` всё ещё содержит минимум 4 точки скрейпинга относительно смещённого времени.

### Математические операторы

Применяются между двумя скалярами, скаляром и вектором, или двумя векторами:

| Оператор | Описание |
|:---|:---|
| `+` | Сложение |
| `-` | Вычитание |
| `*` | Умножение |
| `/` | Деление |
| `%` | Остаток от деления |
| `^` | Возведение в степень |
| `atan2` | Арктангенс от двух аргументов | `atan2(vector1, vector2)` |

**Выполнение:** Операторы вычисляются поэлементно после сопоставления лейблов. При отсутствии совпадения пар элементы исключаются из результата.

### Операторы сравнения

`==`, `!=`, `>`, `<`, `>=`, `<=`.
С модификатором `bool` возвращают `0` или `1` вместо фильтрации.

### Логические операторы

Работают только с **instant vector**:

| Оператор | Описание | Сохранение лейблов |
|:---|:---|:---|
| `and` | Пересечение множеств по лейблам. | Сохраняет лейблы левого вектора |
| `or` | Объединение множеств. | Сохраняет лейблы левого вектора |
| `unless` | Исключение элементов правого множества из левого. | Сохраняет лейблы левого вектора |

**Важно:** Логические операторы всегда возвращают исходное значение из левого вектора. Они не изменяют числовые значения, а только фильтруют ряды на основе совпадения лейблов.

### Приоритет операторов

От высшего к низшему:
1. `^`
2. `*`, `/`, `%`, `atan2`
3. `+`, `-`
4. `==`, `!=`, `<=`, `<`, `>=`, `>`
5. `and`, `unless`
6. `or`

**Практическое следствие:** В выражении `a + b * c` умножение выполняется раньше сложения. Для изменения порядка используйте скобки: `(a + b) * c`.

### Внутренний алгоритм сопоставления селекторов

Prometheus строит хеш-таблицу для каждого вектора по ключам сопоставления. При выполнении бинарной операции:
1. Каждый вектор нормализуется: удаляются временные метки, лейблы сортируются в каноническом порядке.
2. Для каждого элемента левого вектора Prometheus ищет точное совпадение ключей в правом векторе.
3. Если совпадение найдено — выполняется операция. Если нет — ряд исключается из результата (в арифметике возвращается пустой вектор).
4. При использовании `on()` или `ignoring()` хеш строится только по указанным ключам, что позволяет сопоставлять векторы с разными наборами лейблов.

**Почему это важно для SRE:** Понимание хеш-механики объясняет, почему десяток лишних лейблов в селекторе (например, `pod` вместо `deployment`) превращает рабочий запрос в пустой результат. Подробнее о влиянии кардинальности — [Лейблы и кардинальность](../labels_and_cardinality.md).

## Практические сценарии

### Фильтрация метрик по окружению и сервису

```promql
# Только production-инстансы API-сервера
up{env="production", job="api-server"}
# → {instance="10.0.0.1:8080", job="api-server", env="production"} 1
```

### Использование подзапросов (Subqueries)

Полезно, когда нужно вычислить rate от rate или агрегацию за период.

```promql
# Максимальное значение 5-минутного рейта за последний час с шагом 1 минута
max_over_time(rate(http_requests_total[5m])[1h:1m])
# → value_at_t0, value_at_t1...
```

### Сравнение с порогом (bool)

```promql
# Возвращает 1 если загрузка > 80%, иначе 0
(node_load1 > bool 0.8)
# → {instance="host1"} 1
```

### Сдвиг времени в будущее

```promql
# Метрика через час относительно текущего момента (для тестирования/прогнозов)
process_cpu_seconds_total offset -1h
```

### Выбор нескольких метрик через regex имени

```promql
# Агрегация всех метрик API-запросов (total, duration, errors) по инстансу
sum({__name__=~"api_http_.*"}) by (instance)
```

### Процент ошибок HTTP 5xx

```promql
sum(rate(http_requests_total{code=~"5.."}[5m]))
/
sum(rate(http_requests_total[5m]))
* 100
# → 2.5
```

### Обнаружение отсутствующих метрик (absent)

```promql
# Алерт если метрика up отсутствует для критического job более 5 минут
absent(up{job="critical-service"})
# → {} 1 (если нет данных)
```

### Сравнение с базовой линией через offset

```promql
# RPS сейчас против недельной давленности (средний baseline)
sum(rate(http_requests_total[5m]))
/
sum(rate(http_requests_total[5m] offset 7d)) > 1.5
# → 1.8 (рост трафика на 80% относительно прошлой недели)
```

### Фильтрация по нескольким значениям через regex

```promql
# Ошибки только для методов POST и PUT
sum(rate(http_requests_total{method=~"POST|PUT", status=~"5.."}[5m])) by (method)
# → {method="POST"} 1.2
```

### Объединение метрик через `or` (fallback)

```promql
# RPS: используем http_requests_total, если есть, иначе nginx_requests_total
http_requests_total or on(instance) nginx_requests_total
# → {instance="lb-1"} 1200.5
```

### Исключение технических запросов через `unless`

```promql
# Ошибки на всех эндпоинтах, кроме /health (исключаем проверки)
sum by (path) (rate(http_requests_total{status=~"5.."}[5m]))
unless
sum by (path) (rate(http_requests_total{path="/health"}[5m]))
# → {path="/api/login"} 2.1
```

## Дополнительная информация

### Взаимосвязь с типами данных

* **Instant vector** — единственный тип, который рисуется на графиках напрямую.
* **Range vector** — аргумент функций (`rate()`, `increase()`).
* **Арифметические операции** между вектором и скаляром применяются к каждому ряду. Между двумя векторами — только при совпадении лейблов (см. [Операции с векторами](./vector_operations.md)).

### Типовые ошибки селекторов и диагностика

| Ошибка | Причина | Решение |
|:---|:---|:---|
| Пустой селектор `{}` | Отсутствует имя метрики или лейблы | Добавьте `__name__` или хотя бы один матчер |
| `many-to-many matching not allowed` | Два вектора имеют несколько совпадающих рядов | Предварительно агрегируйте (`sum by (...)`) |
| Пустой результат при `and`/`or`/`unless` | Лейблы не совпали в левом и правом векторе | Проверьте модификаторы `on()`/`ignoring()` |
| `group_left` с логическим оператором | Запрещено в PromQL | Используйте арифметику с `bool` или перестройте запрос |
| `expected type range vector` | Функции скорости применены к instant vector | Добавьте `[5m]` к селектору |
| `expected type instant vector` | Функция ожидает instant vector, а передан range vector | Оберните в функцию: `rate(metric[5m])` |
| `vector cannot contain metrics with the same labelset` | Дубликаты лейблов после `on`/`ignoring` | Уберите дубликаты через агрегацию или добавьте уникальный лейбл |

### Производительность селекторов

| Паттерн | Стоимость | Рекомендация |
|:---|:---|:---|
| Точный матcher `=` | Низкая | Безопасно для high-cardinality. |
| Regex `=~` с простым паттерном | Средняя | Безопасно; избегайте `.*` в начале. |
| Regex `=~` с `.*prefix.*` | Высокая | Полное сканирование всех рядов; используйте точный матчер или префиксный regex `^prefix`. |
| Regex с alternation `a\|b\|c` | Средняя | RE2 обрабатывает эффективно, но длинные списки замедляют выборку. |
| Множество матчеров `{a="1", b="2", ...}` | Низкая | Безопасно; каждый матчер индексируется отдельно. |
| Нативные гистограммы в селекторе | Средняя | Фильтрация происходит по instance-лейблам; бакеты не фильтруются отдельно. |

### Предостережения

* **Regex и якоря:** Матчеры `=~` и `!~` автоматически используют привязку к началу и концу строки (`^...$`).
* **Native Histograms (Prometheus 3.x):** Арифметические и сравнительные операторы работают с Native Histograms прозрачно. Сравнение происходит с суммой (sum) или границами корзин в зависимости от контекста. При операциях между Native Histogram и Float-вектором результат сохраняет структуру гистограммы, если это математически применимо.
* **Точность float:** Prometheus использует 64-битные числа с плавающей запятой, что может приводить к микро-погрешностям при делении.
* **Пустой селектор:** Запрос `{}` вернёт ошибку. Необходимо указать либо имя метрики, либо хотя бы один непустой матчер лейбла.
* **Порядок выполнения:** Операторы выполняются слева направо в рамках одного уровня приоритета.
* **Staleness и селекторы:** Селектор не скрывает устаревшие данные автоматически. Если таргет перестал скрейпить, серия остаётся в выборке до истечения `lookback delta` (по умолчанию 5 минут). Для детекции отсутствия данных используйте `absent()`.
* **Offset в combination с range:** `metric[5m] offset 1h` сначала сдвигает окно на 1 час в прошлое, затем берёт 5-минутный диапазон оттуда. Нельзя использовать `offset` внутри range-селектора функции (например, `rate(metric[5m] offset 1h)` — синтаксически неверно). Правильно: `rate(metric offset 1h[5m])`.

### Выбор типа селектора под задачу SRE

| Задача | Рекомендуемый селектор | Пример |
|:---|:---|:---|
| Мониторинг конкретного таргета | Точный матcher по `job` + `instance` | `up{job="node-exporter", instance="10.0.0.1:9100"}` |
| Агрегация по окружению | Матcher по `env` | `up{env="production"}` |
| Фильтрация по паттерну имени | Regex по `__name__` | `{__name__=~"node_filesystem_.*"}` |
| Исключение служебных метрик | Отрицательный regex | `{__name__!~"prometheus_.*|go_.*"}` |
| Детект отсутствия данных | `absent()` | `absent(up{job="critical-service"})` |
| Сравнение с прошлым | `offset` | `rate(http_requests_total[5m] offset 7d)` |
| Фиксированный момент времени | `@` | `node_memory_MemAvailable_bytes @ 1609459200` |
| Объединение альтернативных метрик | `or` | `http_requests_total or on(instance) nginx_requests_total` |
| Исключение已知 проблем | `unless` | `rate(http_requests_total[5m]) unless rate(http_requests_total{path="/health"}[5m])` |

### Сравнение Prometheus matchers и Alertmanager matchers

Хотя синтаксис похож (`{label="value"}`), между PromQL-селекторами и Alertmanager matchers есть ключевые различия:

| Аспект | PromQL | Alertmanager |
|:---|:---|:---|
| Regex-синтаксис | RE2 (Google) | RE2 (Google) |
| Якорение | Автоматическое (`^...$`) | Требуется явное `^` и `$` |
| Пустой matcher | `{}` — ошибка | `{}` — разрешено (матчит всё) |
| Поддержка `!~` | Да | Да (v0.22+) |
| Поддержка `on()`/`ignoring` | Нет (неприменимо) | Нет (неприменимо) |
