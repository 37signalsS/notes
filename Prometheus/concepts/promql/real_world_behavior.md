# Поведение метрик PromQL в реальных сценариях

## Определения

**Поведение метрик в реальных условиях** — особенности работы с метриками Prometheus при рестартах сервисов, потере связи с таргетами (staleness), несовпадении временных окон с точками скрейпинга (extrapolation) и репликации приложений. Эти особенности критически влияют на корректность [функций PromQL](./functions.md) и точность [алертинга](../../rules.md).

**Ключевой принцип:** Prometheus — не биллинговая система. В основе его работы лежат вероятностные алгоритмы, экстраполяция и сглаживание. Метрики предназначены для оценки состояния, трендов и доступности систем, а не для расчёта данных с точностью до цента или единичного запроса.

**Устаревание данных (Staleness / Lookback Delta)** — механизм Prometheus, при котором последнее известное значение метрики продолжает возвращаться в ответ на запросы еще 5 минут (по умолчанию) после того, как таргет перестал отвечать.

**Экстраполяция (Extrapolation)** — математическое вычисление значений на границах временного окна (range vector) на основе тренда внутри этого окна. Применяется в функциях `rate()`, `increase()`, `delta()`.

**Lookback Delta** — интервал времени, в течение которого Prometheus ищет последнюю точку данных для ряда в момент запроса. По умолчанию составляет 5 минут, но может быть переопределён через `--query.lookback-delta` в конфигурации Prometheus.

**Stale Marker** — специальный маркер (`stale NaN`), который экспортер или целевой объект может явно передать для указания, что ряд больше не актуален. При получении такого маркера Prometheus немедленно помечает ряд как отсутствующий, минуя стандартный lookback delta.

**Created Timestamp** — временная метка создания временного ряда, передаваемая через Remote Write 2.0. Позволяет внешним хранилищам (VictoriaMetrics, Mimir) и самому Prometheus корректно обрабатывать сбросы счётчиков (counter resets) при долгих периодах отсутствия данных.

## Базовые концепции

### Механизм lookback delta и stale markers

При выполнении запроса Prometheus должен вернуть значение для каждого уникального набора лейблов. Если данных нет в точный момент времени запроса, движок PromQL выполняет поиск вглубь истории:

1. **Поиск последней точки:** Prometheus ищет последнюю точку данных в пределах `lookback delta` (по умолчанию 5 минут).
2. **Возврат найденного значения:** Если точка найдена, она возвращается как текущее значение ряда.
3. **Помечение stale:** Если данных нет в течение `lookback delta`, ряд помечается как `stale` и исчезает с графиков и результатов запросов.
4. **Немедленная пометка:** При получении явного `stale nan` от экспортера ряд помечается как отсутствующий немедленно, без ожидания lookback delta.

**Прагматическое значение для SRE:**
- Алерт, основанный на `rate()`, может оставаться активным до 5 минут после падения таргета, так как PromQL продолжает видеть последнее значение.
- Графики не "мерцают" при пропуске одного скрейпа из-за кратковременной сетевой задержки.

### Экстраполяция и дробные значения (Rate / Increase)

Функции `rate()` и `increase()` вычисляют изменение счётчика внутри временного окна (например, `[5m]`). Однако точки скрейпинга (scrape points) почти никогда идеально не совпадают с началом и концом заданного окна.

Prometheus решает это с помощью **экстраполяции**: он вычисляет среднюю скорость роста между первой и последней точкой в окне, а затем достраивает этот тренд до самых границ окна.

**Алгоритм экстраполяции:**
1. Определяются первая и последняя точки в окне `[range]`.
2. Вычисляется скорость изменения: `(последнее_значение - первое_значение) / (время_последней - время_первой)`.
3. Скорость экстраполируется до границ окна с учётом возможных сбросов.
4. Для `rate()` результат делится на длину окна в секундах; для `increase()` — умножается на длину окна.

**Реальные последствия для SRE:**
1. **Дробные целые:** Функция `increase(http_requests_total[5m])` может вернуть `4.28`, даже если количество запросов строго целое. Это математическое следствие экстраполяции.
2. **Не точные сравнения:** **Категорически запрещено** писать алерты вида `increase(errors[1m]) == 1`. Из-за экстраполяции результат может быть `0.95` или `1.05`. Всегда используйте `>= 1` или `> 0`.
3. **Обработка медленного старта:** Если сервис только запустился и успел ответить только на один скрейп (одна точка), `rate` и `increase` не смогут вычислить скорость (нужно минимум 2 точки) и вернут пустой результат (отсутствие данных).

### Устаревание данных (Staleness)

Когда контейнер падает или сеть обрывается, Prometheus не записывает автоматически значение `0`. Движок PromQL использует механизм **lookback delta**.

- Если данных нет в точный момент времени запроса, PromQL ищет последнюю точку данных в прошлом (до 5 минут назад по умолчанию).
- Это позволяет графикам не "мерцать", если один скрейп был пропущен из-за кратковременной сетевой задержки.
- Через 5 минут метрика объявляется **stale** (устаревшей) и исчезает с графиков.

**Проблема с алертами:** Алерт на основе `rate()` может «висеть» в активном состоянии еще до 5 минут после падения таргета, потому что PromQL продолжает экстраполировать данные на основе старых точек.

### Обработка рестартов (Counter vs Gauge)

При деплоях и сбоях сервисы перезапускаются. Метрики типа Counter сбрасываются в 0 и начинают отсчитываться заново. Это штатное поведение.

**Как функции обрабатывают сбросы (Resets):**

| Функция | Тип метрики | Обработка сброса |
|:---|:---|:---|
| `rate()`, `irate()` | Counter | **Учитывает** — корректно вычисляет скорость, понимая, что `100 -> 0 -> 5` — это прирост на 5, а не падение. |
| `increase()` | Counter | **Учитывает** — корректно вычисляет абсолютный прирост. |
| `deriv()` | Gauge | **Не учитывает** — выдаст резкий отрицательный скачок при сбросе (не применять к Counter!). |
| `delta()`, `idelta()`| Gauge | **Не учитывает** — просто вычисляет разницу `v_last - v_first`. |
| `predict_linear()` | Gauge | **Не учитывает** — линейная регрессия не детектирует сбросы. |

**Алгоритм обработки сбросов в `rate()`:**
1. Prometheus сканирует все точки в окне `[range]`.
2. Если обнаруживает уменьшение значения (например, `100 → 5`), интерпретирует это как сброс.
3. Прирост вычисляется как `(начало_окна - 0) + (конец_окна - 0)`.
4. Для `rate()` результат делится на длину окна в секундах.

**Обработка сбросов через Created Timestamps (Remote Write 2.0):**
При использовании удалённого хранения (VictoriaMetrics, Mimir) точное время создания ряда передаётся вместе с данными. Это позволяет стороне-приёмнику корректно обрабатывать сбросы, которые произошли во время недоступности Prometheus, повышая точность `rate()` и `increase()` в федеративных конфигурациях.

### Реплики и коллизии лейблов

При наличии нескольких реплик одного приложения Prometheus собирает метрики с идентичными базовыми лейблами. Без уникализации (добавления лейблов инстансов) данные разных реплик записываются в **один временной ряд**, что приводит к хаосу на графиках и ошибкам `many-to-one matching`.

**Решение:** каждая реплика обязана иметь **уникальный лейбл**.

| Среда | Источник уникального лейбла | Пример |
|:---|:---|:---|
| Kubernetes | Service Discovery (SD) | `pod="api-7d4f8b-xk2mn"` |
| Docker Swarm | SD / Конфигурация | `container_label_com_docker_swarm_task_name="api.1.x"` |
| VMs / Bare Metal | SD / Static configs | `instance="node-1:9100"` |

Ряды разделяются уникальными лейблами, после чего их необходимо правильно агрегировать, пряча лейбл реплики:
```promql
sum(rate(http_requests_total[5m])) by (job, path)
```

### Выбор интервала: `rate()` vs `irate()`

Две основные функции для оценки скорости изменения имеют принципиально разное назначение:

| Критерий | `rate(v[range])` | `irate(v[range])` |
|:---|:---|:---|
| **Алгоритм** | Использует **все точки** в окне, строит усредненный тренд. | Использует **только две последние** точки в окне. |
| **Сглаживание** | Сглаживает кратковременные всплески (spikes). | Экстремально чувствительна к пикам. |
| **Алертинг** | **Рекомендуется.** Стабильная база для принятия решений. | **Запрещено.** Вызовет флаппинг алертов от малейших скачков. |
| **Дашборды (Общие)**| Отлично подходит для понимания общего тренда. | Делает график «рваным» и нечитаемым на больших интервалах. |
| **Troubleshooting** | Может скрывать микро-спайки, приведшие к ООМ. | **Идеально** для пошагового «зума» графиков при расследовании инцидентов. |
| **Производительность** | Низкая стоимость. | Низкая стоимость. |

**Правило 4 точек:** Для корректного вычисления `rate()` в окне должно гарантированно находиться минимум 4 точки scrape. При `scrape_interval = 15s` минимальный безопасный интервал = `1m`. При `30s` = `2m`.

### Выбор интервала для range vector и Grafana `$__rate_interval`

Интервал (например, `[5m]`) должен быть связан с частотой сбора метрик (`scrape_interval`).

В Grafana традиционно использовалась переменная `$__interval` (зависящая от масштаба (zoom) графика). Это приводило к катастрофе: при сильном приближении окна `$__interval` мог стать меньше `scrape_interval`, и графики исчезали.

**Решение:** Всегда использовать **`$__rate_interval`** в Grafana. Эта переменная гарантирует: `max($__interval, 4 * scrape_interval)`.

### Особенности нативных гистограмм (Prometheus v3.0+)

Нативные гистограммы используют разреженные экспоненциальные корзины. При арифметических операциях и экстраполяции Prometheus v3.0 автоматически согласовывает разрешение корзин (bucket reconciliation).

**Важно для SRE:**
- Не смешивайте обычные float-метрики и нативные гистограммы в одной группе агрегации. Ряды несовпадающих типов будут исключены из результата.
- `histogram_quantile()` для нативных гистограмм не требует лейбла `le`, что упрощает запросы и снижает кардинальность.

### Поведение при высокочастотном скрейпинге

При `scrape_interval < 1s` (например, для детального мониторинга CPU):
- Окно `rate()` должно быть увеличено пропорционально (минимум `4 * scrape_interval`).
- `irate()` становится более полезным, так как улавливает кратковременные всплески, которые `rate()` усреднит.
- Увеличивается нагрузка на TSDB из-за большего количества точек.

## Практические сценарии

### Корректная агрегация RPS (Счётчиков) по репликам

**Золотое правило PromQL:** Сначала `rate()`, затем `sum()`. Никогда не наоборот. Если сначала сложить `sum()`, информация о сбросах счётчиков (resets) отдельных реплик будет потеряна, что приведет к ложным пикам.

```promql
# ПРАВИЛЬНО: Вычисляем rate каждой реплики отдельно, затем суммируем
sum(rate(http_requests_total[5m])) by (job, method)

# НЕПРАВИЛЬНО: Приведет к диким скачкам графиков при рестарте любого pod'а
rate(sum(http_requests_total)[5m])
```

### Алертинг на наличие ошибок (с учётом экстраполяции)

Из-за экстраполяции `increase()` мы не можем проверять равенство единице. Правильный подход — использовать `rate` (что математически эквивалентно) или `> 0`.

```promql
# Обнаружение ошибок. > 0 гарантированно сработает на >= 1 ошибки.
rate(http_errors_total{job="payment-gateway"}[5m]) > 0
```

### Поиск нестабильных сервисов (Рестарты)

Функция `resets()` анализирует падения счётчика до нуля. Поскольку uptime (`process_start_time_seconds` или счетчики CPU) сбрасываются при перезапуске, это идеальный индикатор CrashLoopBackOff.

```promql
# Обнаружение рестартов — больше 3 за час
resets(process_cpu_seconds_total[1h]) > 3
```

### Обнаружение "тихих" отказов (Stale + Absent)

Когда таргет полностью исчезает (не только падает, но и удаляется), стандартный staleness может не сработать. Используйте `absent_over_time()` для детекции полного отсутствия данных:

```promql
# Сервис не отправлял метрики 15 минут
absent_over_time(up{job="critical-service"}[15m])
```

### Детекция утечек памяти и OOM

Для Gauge-метрик (память) используйте `deriv()` для выявления стабильного роста:

```promql
# Память стабильно растёт последние 15 минут — возможна утечка
deriv(process_resident_memory_bytes[15m]) > 0
```

**Внимание:** `deriv()` использует линейную регрессию и не учитывает сбросы. При рестарте приложения он выдаст аномально низкое (отрицательное) значение.

### Прогноз заполнения диска и памяти

Используйте `predict_linear()` для проактивного планирования:

```promql
# Алерт: диск заполнится менее чем за 4 часа
predict_linear(node_filesystem_free_bytes{mountpoint="/"}[1h], 4 * 3600) < 0

# Память закончится через 2 часа при текущем тренде
predict_linear(node_memory_MemAvailable_bytes[1h], 3600 * 2) < 0
```

**Требования к окну:**
- Минимум 1 час данных для стабильного прогноза.
- Чем больше окно, тем точнее прогноз, но тем выше нагрузка.

### Обнаружение "мерцающих" метрик (Flapping)

Функция `changes()` подсчитывает количество изменений значения метрики за интервал:

```promql
# Метрика меняла значение более 20 раз за последний час
changes(node_status[1h]) > 20
```

**Применение:** Обнаружение нестабильных проверок (probes), переключающихся флагов конфигурации, проблем с сетевыми интерфейсами.

### Настройка Grafana дашбордов для динамического масштаба

```promql
# Корректный запрос для панели Grafana (RPS)
sum by (status) (rate(http_requests_total[$__rate_interval]))
```

### Диагностика: почему запрос возвращает пустой результат

| Причина | Тип проблемы | Проверка | Решение |
|:---|:---|:---|:---|
| Метрика отсутствует | Нет данных в TSDB | `up{job="..."}` | Проверьте scrape targets |
| `rate()` на instant vector | Ошибка типа | В логе PromQL: `expected type range vector` | Добавьте `[5m]` |
| Слишком маленькое окно | Меньше 2 точек | `count_over_time(metric[1m])` | Увеличьте окно до `4 * scrape_interval` |
| Несовпадение лейблов | Пустое множество | `count(metric)` vs `count(metric * on() group_left() other)` | Проверьте модификаторы `on`/`ignoring` |
| Staleness | Данные устарели | `timestamp(metric) < time() - 600` | Проверьте доступность таргета |
| Float64 погрешность | Сравнение на точное равенство | `node_load1 == 0.85` (ненадёжно) | Используйте пороговые значения: `>`, `<`, `abs(...) < 0.001` |

### Обработка повторяющихся скрейпов и дубликатов

Prometheus автоматически обрабатывает дубликаты точек с одинаковым timestamp. Однако при нестабильной сети могут появляться "проплешины" — интервалы без данных короче `scrape_interval`.

**Диагностика проплешин:**
```promql
# Количество точек в окне (должно быть >= 4 для rate())
count_over_time(http_requests_total[5m])
```

### Валидация freshness данных для алертинга

```promql
# Разница между текущим временем и последней точкой (в секундах)
time() - timestamp(up{job="critical-service"})
# → {instance="app-1"} 12.5 (данные свежие)

# Алерт: данные устарели более чем на 10 минут
time() - timestamp(up{job="critical-service"}) > 600
```

## Дополнительная информация

### Частые причины ложных срабатываний алертов (Flapping)

| Ошибка | Последствие | Решение |
|:---|:---|:---|
| Использование `irate()` в алертинге | Ложные алерты на любой микро-спайк трафика | Использовать `rate()` с окном `5m` или `10m` |
| Окно `rate()` слишком маленькое (например, `[1m]`) | Высокий шум, ложные срабатывания, пропуски точек | Использовать окно минимум в 3-4 раза больше `scrape_interval` |
| Проверка счетчика на точное значение `== X` | Алерт не сработает из-за дробной экстраполяции | Проверять на пороги: `> X`, `< X` |
| Алерт без задержки `for` | Ложное срабатывание при секундной задержке сети | Использовать `for: 3m` (минимум) в правилах |
| Сравнение `absent()` для метрики равной 0 | Алерт не сработает | Использовать `absent()` только для полного отсутствия серии; для проверки на 0 используйте `== 0` |
| Слишком большое окно `predict_linear()` | Прогноз становится неточным | Ограничьте окно 1–24 часа |

### Шпаргалка: что использовать

| Задача | Функция | Окно (Интервал) |
|:---|:---|:---|
| RPS на обзорном дашборде | `rate()` | `$__rate_interval` |
| Алерт на SLA / Error Rate | `rate()` | От `5m` до `1h` (с `for`) |
| Прогноз заполнения диска | `predict_linear()` | От `1h` до `24h` |
| Детект рестартов / CrashLoop | `resets()` | `1h` |
| Отладка пиков / Оптимизация | `irate()` | `$__interval` (при сильном зуме) |
| Утилизация ресурсов (CPU) | `rate()` | `$__rate_interval` |
| Детекция флаппинга метрик | `changes()` | `30m`–`1h` |
| Прогноз исчерпания памяти | `predict_linear()` | `1h`–`4h` |
| Проверка отсутствия данных | `absent_over_time()` | `5m`–`15m` |
| Текущее значение метрики | `timestamp()` / `time()` | — |

### Производительность запросов

Некоторые функции и паттерны имеют повышенную стоимость вычислений:

| Операция | Стоимость | Рекомендация |
|:---|:---|:---|
| `rate()` / `irate()` | Низкая | Безопасно использовать в алертах. |
| `predict_linear()` | Средняя | Ограничьте окно 1–24 часа. |
| `histogram_quantile()` | Средняя/Высокая | Сначала агрегируйте `sum by (le)`, затем вычисляйте квантиль. |
| `..._over_time()` с окном >24h | Высокая | Избегайте для высококардинальных метрик. |
| `label_replace()` со сложным regex | Средняя | Используйте простые паттерны; тестируйте на `promtool`. |
| Подзапрос `[24h:1m]` | Высокая | 1440 вычислений на каждый ряд; используйте recording rules. |

### Ограничения и известные поведенческие особенности

1. **Float64 точность:** Из-за ограничений представления чисел с плавающей запятой сравнение на точное равенство ненадёжно. Используйте диапазоны или пороги: `abs(node_load1 - expected_load) < 0.001`.
2. **Округление в `increase()`:** Результат всегда может содержать дробную часть из-за экстраполяции. Не используйте `==` или `!=` для целочисленных счётчиков.
3. **Сбросы при деплое:** При rolling update пода его метрики сбрасываются. `rate()` корректно обрабатывает это, но `sum(rate(...)) by (pod)` создаст новый ряд с нулевым значением, который будет изображаться на графике как резкий скачок вниз.
4. **Задержка данных:** Prometheus не имеет информации о задержке доставки метрик от экспортера. `timestamp()` показывает время, когда Prometheus получил точку, а не когда экспортер её сгенерировал.
5. **Запись правил (Recording Rules):** При вычислении recording rules Prometheus использует тот же механизм extrapolation. Убедитесь, что правило вычисляется не чаще, чем `scrape_interval`, иначе вы получите пустые результаты.
