# Поведение метрик PromQL в реальных сценариях

## Определения

**Поведение метрик в реальных условиях** — особенности работы с метриками Prometheus при рестартах сервисов, репликации приложений и выборе интервалов запросов. Эти особенности влияют на корректность [функций PromQL](./functions.md) и точность [алертинга](../../rules.md).

**Ключевой принцип:** метрики Prometheus — не источник точных данных для биллинга. Производные, перцентили и агрегирующие функции вносят погрешности. Метрики предназначены для оценки состояния систем, а не для точных расчётов.

## Базовые концепции

### Обработка рестартов (Counter vs Gauge)

При деплоях и сбоях сервисы перезапускаются. Counter-метрики сбрасываются в 0 и начинают отсчитываться заново — это штатное поведение, заложенное в модель данных Prometheus.

**Как функции обрабатывают сбросы:**

| Функция | Тип метрики | Обработка сброса |
|:---|:---|:---|
| `rate()` | Counter | **Учитывает** — корректно вычисляет скорость |
| `increase()` | Counter | **Учитывает** — корректно вычисляет прирост |
| `deriv()` | Gauge | **Не учитывает** — некорректный результат при сбросе |
| `delta()` | Gauge | Разница `v_last - v_first`, без обработки сбросов |

Подробно в [Счётчики](../metric_types/counter.md) и [Измерители](../metric_types/gauge.md).

### Реплики и коллизии лейблов

При наличии нескольких реплик одного приложения Prometheus собирает метрики с идентичными наборами лейблов. Без уникафикации данные разных реплик попадают в **один временной ряд**, что делает невозможным корректную агрегацию.

**Проблема:**

```text
# реплика 1:
api_http_requests_total{method="POST", url="/login"} 2
# реплика 2:
api_http_requests_total{method="POST", url="/login"} 3
```

Оба значения попадают в один ряд. Невозможно определить фактическое количество запросов на каждой реплике.

**Решение:** каждая реплика добавляет **уникальный лейбл** — hostname, pod ID, replica name ([Лейблы и кардинальность](../labels_and_cardinality.md)):

```text
# реплика 1:
api_http_requests_total{method="POST", url="/login", replica="app_1"} 2
# реплика 2:
api_http_requests_total{method="POST", url="/login", replica="app_2"} 3
```

Ряды разделяются, корректная агрегация через `sum()`:

```promql
sum(rate(api_http_requests_total[5m]))
```

**Источники уникальных лейблов:**

| Источник | Лейбл | Пример |
|:---|:---|:---|
| Kubernetes pod | `pod` | `api-7d4f8b-xk2mn` |
| Docker container | `container_id` | `a1b2c3d4e5f6` |
| Node exporter | `instance` | `node-1:9100` |
| Application SDK | `replica`, `instance_id` | задаётся разработчиком |

**Важно:** `instance` лейбл Prometheus добавляет автоматически (адрес таргета). Для pod'ов в Kubernetes через service discovery добавляются `pod`, `namespace`, `node`.

### Выбор интервала для range vector

Интервал `rate()`/`increase()` влияет на гладкость графика и чувствительность к всплескам:

| Интервал | Результат | Применение |
|:---|:---|:---|
| Большой (15m+) | Гладкий график, виден тренд | Дашборды, алертинг |
| Средний (5m) | Баланс шума и детализации | Стандартный выбор |
| Малый (1–2m) | Видны пики и скачки | Отладка, расследование инцидентов |
| < 2 точек | Нет результата | Некорректный выбор |

Минимальный интервал — **2×scrape_interval** (обычно 1 минута при scrape_interval = 30s).

**Правило 4 точек:** для корректного `rate()` в окне должно быть минимум 4 точки scrape. При scrape_interval = 15s минимальный интервал = 1m.

### Grafana: `$__rate_interval` vs `$__interval`

Для Grafana используется переменная **`$__rate_interval`** вместо `$__interval`:

| Переменная | Поведение | Риск |
|:---|:---|:---|
| `$__rate_interval` | `max($__interval, 4×scrape_interval)` | Гарантирует ≥4 точек |
| `$__interval` | Автоподбор по zoom графика | Может быть < scrape_interval |

**Исключение:** Clickhouse как источник данных — парсер не поддерживает графановские интервалы, требуется кастомная переменная.

Подробно в [Grafana: Шаблонизация](../../../Grafana/grafana_templating.md).

## Практические сценарии

### Алертинг на рестарты приложений

```promql
# Обнаружение рестартов — больше 3 за час
resets(process_start_time_seconds[1h]) > 3
```

Функция `resets()` считает количество сбросов — индикатор нестабильности сервиса. Подробнее в [Счётчики](../metric_types/counter.md).

### Утилизация CPU по репликам

```promql
# Средний CPU по всем репликам, сгруппированный по instance
avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100
```

Каждый `instance` — отдельная реплика. `avg by (instance)` даёт утилизацию на узел.

### Прогноз нехватки диска

```promql
# Прогноз через 4 часа по данным за последний час
predict_linear(node_filesystem_free_bytes{mountpoint="/"}[1h], 3600 * 4) < 0
```

Линейная экстраполяция. Срабатывает до исчерпания ресурса — превентивный алертинг ([Измерители](../metric_types/gauge.md)).

### Корректная агрегация RPS по репликам

```promql
# Суммарный RPS всех реплик
sum(rate(http_requests_total[5m]))
```

Уникальные лейблы реплик обеспечивают разделение рядов. `sum()` корректно складывает rate всех инстансов ([Счётчики](../metric_types/counter.md)).

### Настройка Grafana дашбордов

```promql
# Корректный запрос для панели Grafana
sum(rate(http_requests_total[$__rate_interval]))
```

Использование `$__rate_interval` гарантирует корректный результат при любом zoom графика.

## Дополнительная информация

### Влияние на алертинг

Некорректный выбор функции или интервала приводит к **ложным срабатываниям**:

| Ошибка | Последствие | Решение |
|:---|:---|:---|
| `deriv()` при рестарте Gauge | Скачок до некорректных значений | Использовать `delta()` или raw Gauge |
| Короткий интервал `rate()` | Шум и ложные пики | Минимум 5m для алертинга |
| Коллизия лейблов реплик | Заниженные значения на графике | Уникальные лейблы на реплику |
| `$__interval` вместо `$__rate_interval` | Пропуск точек при zoom | Всегда `$__rate_interval` |

Для задержки срабатывания алерта используется `for` в [Rules](../../rules.md).

### `rate()` vs `irate()`

| Критерий | `rate()` | `irate()` |
|:---|:---|:---|
| Точки | Все в окне | 2 последние |
| Шум | Сглаживает | Чувствителен |
| Алертинг | **Рекомендуется** | Не рекомендуется |
| Отладка | Менее информативен | Видны резкие скачки |

### Шпаргалка: что использовать

| Задача | Функция | Интервал |
|:---|:---|:---|
| RPS на дашборде | `rate()` | `$__rate_interval` или 5m |
| Алерт на ошибки | `rate()` + `for 5m` | 5m |
| Прогноз диска | `predict_linear()` | 1h |
| Детект рестартов | `resets()` | 1h |
| Отладка пиков | `irate()` | 1–2m |
| Утилизация CPU | `rate()` или `irate()` | 5m |
