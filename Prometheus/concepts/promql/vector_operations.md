# Операции с векторами в PromQL

> **Reliability Score: 10/10** (SSoT)
> **Freshness Trigger:** Регулярное обновление с учётом актуальных версий Prometheus (v2.x). Проверено в 2026 году.

## Определения

**Сопоставление векторов (Vector Matching)** — механизм PromQL, определяющий, какие элементы двух векторов (instant vectors) комбинируются при выполнении бинарных операций. По умолчанию сопоставление происходит по **полному совпадению всех лейблов**.

**Бинарные операторы (Binary Operators)** — операторы, выполняющие действия над двумя векторами (или скалярами), инициирующие механизм сопоставления векторов. Включают арифметические (`+`, `-`, `*`, `/`, `%`, `^`), операторы сравнения (`==`, `!=`, `>`, `<`, `>=`, `<=`) и логические/множественные операторы (`and`, `or`, `unless`).

**Функции манипуляции лейблами (Label Manipulation Functions)** — встроенные функции PromQL (`label_replace`, `label_join`) для создания, изменения и объединения лейблов. Используются для нормализации данных перед векторными операциями, чтобы обеспечить правильное сопоставление.

**Подзапрос (Subquery)** — синтаксис, позволяющий применить функции диапазона (range functions, например `..._over_time`) к результатам запросов, возвращающих instant vector, с указанием собственного временного интервала и шага вычисления.

## Базовые концепции

### Типы операций и поведение сопоставления

В зависимости от типа бинарного оператора, сопоставление векторов ведет себя по-разному:

1.  **Арифметические операторы и операторы сравнения:** Вычисляют значения между совпавшими рядами. По умолчанию операторы сравнения работают как фильтры (удаляют ряды, для которых условие ложно). При добавлении модификатора `bool` операторы сравнения возвращают `0` (ложь) или `1` (истина) вместо фильтрации. Поддерживают модификаторы кардинальности `group_left` и `group_right`.
2.  **Логические операторы (`and`, `or`, `unless`):** Работают с векторами как с математическими множествами. Они не изменяют числовые значения (всегда возвращают исходное значение из левого вектора), а только фильтруют ряды на основе совпадения лейблов. **Не поддерживают** модификаторы `many-to-one` или `one-to-many` (запрещено использовать `group_left` и `group_right`).

### Стратегии сопоставления (Vector Matching)

#### Сопоставление "Один-к-одному" (One-to-one)

Каждый элемент левого вектора сопоставляется **строго одному** элементу правого вектора с **идентичным** набором лейблов (существующих в обоих векторах). Это поведение по умолчанию.

```promql
# Сопоставление по точному совпадению всех лейблов (method, path, instance, job и т.д.)
http_requests_total / http_errors_total
```

#### Сопоставление "Многие-к-одному" и "Один-ко-многим" (Many-to-one / One-to-many)

Когда у одного вектора **больше** лейблов (более высокая кардинальность), чем у другого, прямое совпадение один-к-одному невозможно. В этих случаях необходимо явно указать направление сопоставления с помощью модификаторов `group_left` и `group_right`:

| Модификатор | Когда использовать | Какие лейблы сохраняются в результате |
|:---|:---|:---|
| `group_left` | В правом векторе меньше лейблов (many-to-one) | Все лейблы из левого (many) + явно указанные из правого (one) |
| `group_right` | В левом векторе меньше лейблов (one-to-many) | Все лейблы из правого (many) + явно указанные из левого (one) |

```promql
# Many-to-one: у node_cpu_seconds_total есть лейблы cpu и mode, которых нет у up.
# Мы берем значение из левого вектора, умножаем на up (1 или 0) и сохраняем 
# все оригинальные лейблы левого вектора (cpu, mode, instance, job).
node_cpu_seconds_total * on(instance, job) group_left() up
```

#### Фильтрация лейблов для сопоставления (`on` / `ignoring`)

По умолчанию PromQL сравнивает **все** доступные лейблы. Модификаторы `on` и `ignoring` сужают набор лейблов, по которым осуществляется поиск совпадений:

| Модификатор | Описание |
|:---|:---|
| `on(<label_list>)` | Сопоставлять векторы **только** по указанным лейблам (строгий белый список). |
| `ignoring(<label_list>)` | Сопоставлять по всем лейблам, **кроме** указанных (чёрный список). |

```promql
# Игнорировать лейблы cpu и mode при поиске соответствия между левым и правым вектором.
# Сопоставление произойдет по оставшимся общим лейблам (например, instance, job).
node_cpu_seconds_total * ignoring(cpu, mode) group_left() up
```

### Подзапросы (Subqueries)

Синтаксис: `<instant_query>[<range>:<step>]`

Подзапросы позволяют выполнить вычисление мгновенного вектора (instant query) для определенного исторического окна времени с заданным шагом. Это необходимо для применения функций, ожидающих range vector (например, `rate()`, `max_over_time()`), к результату других динамических вычислений, возвращающих instant vector.

```promql
# rate() возвращает instant vector. 
# Чтобы найти пиковый rate() за сутки, мы делаем из него range vector с помощью подзапроса [24h:1m]
max_over_time(rate(http_requests_total[5m])[24h:1m])
```

- `5m` — окно оценки внутреннего `rate()`.
- `24h` — общий временной диапазон подзапроса.
- `1m` — шаг (step), с которым внутренний запрос выполняется на протяжении 24 часов. Если оставить пустым (`[24h:]`), используется глобальный интервал оценки Prometheus.

## Практические сценарии

### Обогащение метрик лейблами из другой метрики (Many-to-one)

Классический паттерн экспортеров — хранение метаданных (версия, архитектура, роль) в отдельной информационной метрике со значением `1`. Чтобы добавить эти данные к рабочим метрикам, используется `group_left`.

```promql
# Добавляем лейбл version из kube_deployment_labels к метрике http_requests_total.
# Левый вектор (requests) имеет высокую кардинальность.
# Правый вектор (labels) имеет меньшую кардинальность, но содержит метаданные.
sum by (deployment, version) (
  http_requests_total 
  * on(deployment, namespace) group_left(version) 
  kube_deployment_labels
)
```

Модификатор `group_left(version)` инструктирует движок PromQL перенести значение лейбла `version` из правого вектора (совпавшего элемента) в результирующий вектор.

### Применение порогового значения к группе метрик (One-to-many)

Сценарий, в котором скаляр или метрика настройки с низкой кардинальностью применяется в качестве динамического порога к вектору с высокой кардинальностью. Вектор с низкой кардинальностью обязан располагаться справа (если используется `group_left`) или применяться модификатор `group_right`.

```promql
# Сравнение потребления памяти каждого контейнера с лимитом, заданным в другой метрике
container_memory_usage_bytes 
  / on(container, pod) group_left() 
  kube_pod_container_resource_limits{resource="memory"} > 0.8
```

### Использование логических операторов как фильтров

Логические операторы позволяют находить пересечения и разности множеств без изменения исходных значений (в результат всегда прокидывается значение левого операнда).

```promql
# Вывести количество запросов (левый вектор), но только для тех сервисов, 
# которые сейчас доступны (правый вектор up == 1)
# Значение (число запросов) останется от http_requests_total
http_requests_total and on(instance, job) up == 1
```

### Подготовка лейблов перед сопоставлением (`label_replace`)

Если в двух метриках логически связанные сущности названы по-разному (например, `host` в системной метрике и `instance` в бизнес-метрике), прямое сопоставление невозможно. Лейбл необходимо предварительно скопировать.

```promql
# Копируем значение лейбла host в новый лейбл instance перед выполнением сопоставления
label_replace(my_custom_metric, "instance", "$1", "host", "(.*)") 
  * on(instance) group_left(job) 
  up
```

### Прогнозирование с использованием подзапросов

Подзапросы крайне полезны для предварительного сглаживания данных перед применением математической экстраполяции, что значительно снижает влияние кратковременных всплесков.

```promql
# Вычисляем среднее количество свободного места с шагом 5 минут за последний час,
# затем строим линейный прогноз на 4 часа вперёд. Возвращаем ряды, которые закончатся (< 0).
predict_linear(
  avg_over_time(node_filesystem_free_bytes[5m])[1h:5m],
  3600 * 4
) < 0
```

## Дополнительная информация

### Взаимосвязь с другими операциями

- **Селекторы и матчеры** — применяются для начальной фильтрации перед векторными операциями ([Селекторы и операторы](./selectors_operators.md)).
- **Агрегация (`by`, `without`)** — группирует временные ряды внутри **одного** вектора. Не следует путать это с `group_left` / `group_right`, которые описывают кардинальность сопоставления между **двумя** векторами ([Агрегация](./aggregation.md)).

### Предостережения и лучшие практики

- **Множество результатов many-to-many:** Если оба вектора содержат несколько рядов с идентичными лейблами в контексте выражения сопоставления (`on` / `ignoring`), PromQL завершит запрос ошибкой `many-to-many matching not allowed`. В Prometheus отсутствует встроенное сопоставление "многие-ко-многим". Запрос необходимо переработать (обычно с помощью агрегации) так, чтобы с одной стороны гарантированно была уникальность рядов.
- **Логические операторы и `on()`:** Модификаторы `on()` и `ignoring()` полностью поддерживаются для операторов `and`, `or`, `unless`. Однако `group_left()` и `group_right()` с логическими операторами **запрещены**.
- **Операторы сравнения с `bool`:** Выражение `up == 1` фильтрует вектор, удаляя ряды, где `up` не равен 1. Выражение `up == bool 1` оставляет все изначальные ряды вектора, но заменяет их значения на `1` (истина) или `0` (ложь).
- **Производительность подзапросов:** Вложенные вычисления (подзапросы) создают высокую нагрузку на процессор Prometheus, поскольку он должен вычислить внутренний запрос для каждого шага (`step`).
  - Рекомендуемый шаг подзапроса: не менее 4–5× `scrape_interval`.
  - Указание явного шага `[1h:5m]` вместо дефолтного `[1h:]` позволяет контролировать количество дискретных точек вычисления и предотвращать перегрузку сервера.
