# Операции с векторами в PromQL

## Определения

**Сопоставление векторов (Vector Matching)** — механизм PromQL, определяющий, какие элементы двух векторов (instant vectors) комбинируются при выполнении бинарных операций. По умолчанию сопоставление происходит по **полному совпадению всех лейблов**.

Актуально для **Prometheus v3.0+**, включая поддержку имен лейблов в UTF-8 и нативную совместимость с OpenTelemetry (OTLP).

**Бинарные операторы (Binary Operators)** — операторы, выполняющие действия над двумя векторами (или скалярами), инициирующие механизм сопоставления. Включают арифметические (`+`, `-`, `*`, `/`, `%`, `^`), сравнения (`==`, `!=`, `>`, `<`, `>=`, `<=`) и логические (`and`, `or`, `unless`). В v3.0 бинарные операции поддерживают автоматическое **согласование бакетов** (bucket reconciliation) для нативных гистограмм.

**Функции манипуляции лейблами** — встроенные функции (`label_replace`, `label_join`) для нормализации данных перед сопоставлением. В Prometheus v3.0 функции метаданных (например, `info()`) позволяют обогащать метрики лейблами без использования сложных векторных джойнов.

**Подзапрос (Subquery)** — синтаксис, позволяющий применить функции диапазона (например, `rate()`) к результатам мгновенных запросов за исторический период с заданным шагом.

## Базовые концепции

### Типы операций и поведение сопоставления

В зависимости от типа бинарного оператора, сопоставление векторов ведет себя по-разному:

1.  **Арифметические операторы и операторы сравнения:** Вычисляют значения между совпавшими рядами. По умолчанию операторы сравнения работают как фильтры (удаляют ряды, для которых условие ложно). При добавлении модификатора `bool` операторы сравнения возвращают `0` (ложь) или `1` (истина) вместо фильтрации. Поддерживают модификаторы кардинальности `group_left` и `group_right`.
2.  **Логические операторы (`and`, `or`, `unless`):** Работают с векторами как с математическими множествами. Они не изменяют числовые значения (всегда возвращают исходное значение из левого вектора), а только фильтруют ряды на основе совпадения лейблов. **Не поддерживают** модификаторы `many-to-one` или `one-to-many` (запрещено использовать `group_left` и `group_right`).

### Стратегии сопоставления (Vector Matching)

#### Сопоставление "Один-к-одному" (One-to-one)

Каждый элемент левого вектора сопоставляется **строго одному** элементу правого вектора с **идентичным** набором лейблов. 

**Пример:**
```promql
# Сопоставление по всем лейблам (method, path, instance, job)
http_requests_total / http_errors_total
# → {method="GET", path="/api"} 50.0 (при 100 запросах и 2 ошибках)
```

#### Сопоставление "Многие-к-одному" и "Один-ко-многим" (Many-to-one / One-to-many)

Когда у одного вектора **больше** лейблов (выше кардинальность), чем у другого, необходимо явно указать направление сопоставления с помощью `group_left` или `group_right`:

| Модификатор | Когда использовать | Результат |
|:---|:---|:---|
| `group_left` | Правый вектор — «справочник» (one), левый — «данные» (many) | Лейблы из левого + указанные из правого |
| `group_right` | Левый вектор — «справочник» (one), правый — «данные» (many) | Лейблы из правого + указанные из левого |

**Native Histograms (v3.0):** При выполнении арифметики над нативными гистограммами (например, `sum(hist) / count(hist)`) Prometheus автоматически приводит корзины к общему разрешению перед вычислением.

#### Фильтрация лейблов (`on` / `ignoring`)

Позволяют сузить или расширить набор лейблов для сопоставления.

| Модификатор | Описание |
|:---|:---|
| `on(<label_list>)` | Использовать **только** указанные лейблы (белый список). |
| `ignoring(<label_list>)` | Использовать все, **кроме** указанных (черный список). |

**Поддержка UTF-8 (v3.0):** Если имя лейбла содержит спецсимволы, оно заключается в кавычки: `on("http.method", "app.version")`.

```promql
# Игнорировать cpu и mode при сопоставлении по instance и job
node_cpu_seconds_total * ignoring(cpu, mode) group_left() up
# → {cpu="0", mode="user", instance="node-1"} 0.85
```

### Подзапросы (Subqueries)

Синтаксис: `<instant_query>[<range>:<step>]`

Подзапросы позволяют выполнить вычисление мгновенного вектора для исторического окна времени с заданным шагом. Это необходимо для применения функций диапазона (например, `max_over_time()`) к результатам динамических вычислений.

**Особенности:**
- **Правило 4 точек:** При использовании `rate()` внутри подзапроса убедитесь, что `range` покрывает минимум 4 точки скрейпинга для стабильности.
- **Производительность:** Подзапросы ресурсоемки. Рекомендуемый шаг (`step`) — не менее `4 * scrape_interval`.

```promql
# Пиковый rate() за сутки с разрешением в 1 минуту
max_over_time(rate(http_requests_total[5m])[24h:1m])
# → {} 450.2
```

## Практические сценарии

### Обогащение через `info()` (Prometheus v3.0+)

Экспериментальная функция `info()` заменяет сложные `group_left` для добавления метаданных (версия, ОС и т.д.).

```promql
# Добавить информацию о версии приложения из build_info к метрике запросов
info(http_requests_total, build_info)
# → {method="GET", version="v1.2.3"} 100
```

### Обогащение метрик лейблами (Many-to-one)

Классический подход через `group_left`, если `info()` недоступна.

```promql
# Добавляем лейбл version из kube_deployment_labels
sum by (deployment, version) (
  http_requests_total 
  * on(deployment, namespace) group_left(version) 
  kube_deployment_labels
)
# → {deployment="api", version="v2.1"} 500
```

### Применение порогового значения (One-to-many)

```promql
# Сравнение потребления памяти контейнера с его лимитом
container_memory_usage_bytes 
  / on(container, pod) group_left() 
  kube_pod_container_resource_limits{resource="memory"} > 0.8
# → {pod="worker-1"} 0.85
```

### Использование логических операторов как фильтров

```promql
# Вывести RPS только для сервисов, которые сейчас UP
rate(http_requests_total[5m]) and on(instance, job) up == 1
# → {instance="node-1"} 10.5
```

### Подготовка лейблов перед сопоставлением (`label_replace`)

```promql
# Копируем значение host в instance перед сопоставлением
label_replace(my_custom_metric, "instance", "$1", "host", "(.*)") 
  * on(instance) group_left(job) 
  up
# → {instance="host-1", job="app"} 42
```

### Прогнозирование с использованием подзапросов

```promql
# Прогноз исчерпания диска на основе сглаженного среднего за час
predict_linear(
  avg_over_time(node_filesystem_free_bytes[5m])[1h:5m],
  3600 * 4
) < 0
# → {device="/dev/sda1"} 1
```

## Дополнительная информация

### Взаимосвязь с другими операциями

- **Селекторы и матчеры** — применяются для начальной фильтрации перед векторными операциями ([Селекторы и операторы](./selectors_operators.md)).
- **Агрегация (`by`, `without`)** — группирует временные ряды внутри **одного** вектора. Не следует путать это с `group_left` / `group_right`, которые описывают кардинальность сопоставления между **двумя** векторами ([Агрегация](./aggregation.md)).

### Предостережения и лучшие практики

- **Множество результатов many-to-many:** Если оба вектора содержат несколько рядов с идентичными лейблами в контексте выражения сопоставления (`on` / `ignoring`), PromQL завершит запрос ошибкой `many-to-many matching not allowed`. В Prometheus отсутствует встроенное сопоставление "многие-ко-многим". Запрос необходимо переработать (обычно с помощью агрегации) так, чтобы с одной стороны гарантированно была уникальность рядов.
- **Логические операторы и `on()`:** Модификаторы `on()` и `ignoring()` полностью поддерживаются для операторов `and`, `or`, `unless`. Однако `group_left()` и `group_right()` с логическими операторами **запрещены**.
- **Операторы сравнения с `bool`:** Выражение `up == 1` фильтрует вектор, удаляя ряды, где `up` не равен 1. Выражение `up == bool 1` оставляет все изначальные ряды вектора, но заменяет их значения на `1` (истина) или `0` (ложь).
- **Производительность подзапросов:** Вложенные вычисления (подзапросы) создают высокую нагрузку на процессор Prometheus, поскольку он должен вычислить внутренний запрос для каждого шага (`step`).
  - Рекомендуемый шаг подзапроса: не менее 4–5× `scrape_interval`.
  - Указание явного шага `[1h:5m]` вместо дефолтного `[1h:]` позволяет контролировать количество дискретных точек вычисления и предотвращать перегрузку сервера.
