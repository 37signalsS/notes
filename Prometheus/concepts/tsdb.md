# Внутреннее устройство Prometheus TSDB

## Определения

* **TSDB (Time Series Database):** Сердце [Prometheus](../overview.md), его собственная база данных временных рядов, спроектированная для эффективной записи, сжатия метрик и быстрого чтения при запросах. Модель данных Prometheus подобна [модели Loki](../../Loki/loki_overview.md), где метрики и логи используют схожий подход к организации.
* **Сэмпл (Sample):** Одна точка данных, состоящая из значения (`float64`) и временной метки (`int64`, timestamp).
* **Временной ряд (Time Series):** Поток сэмплов, принадлежащих одной и той же метрике с идентичным набором [лейблов](./labels_and_cardinality.md).
* **Чанк (Chunk):** Сжатый контейнер для сэмплов одного временного ряда, обычно содержащий до 120 сэмплов.
* **Блок (Block):** Директория на диске, содержащая данные за определённый промежуток времени (по умолчанию — 2 часа). Внутри блока находятся чанки, индекс и метаданные.
* **Head Block (Головной блок):** Активный блок в оперативной памяти (RAM), который принимает все новые входящие сэмплы.
* **WAL (Write-Ahead Log):** Журнал упреждающей записи, куда все входящие сэмплы сначала записываются на диск для обеспечения сохранности данных при сбоях. Подробнее см. [Журнал предзаписи (WAL)](../../Databases/Concepts/write_ahead_log.md).
* **Сжатие (Compaction):** Процесс, в ходе которого несколько блоков объединяются в один более крупный блок для оптимизации хранения и ускорения запросов.
* **Индекс (Index):** Файл внутри каждого блока, содержащий структуры для быстрого поиска временных рядов по их лейблам.

### Зачем нужны TSDB

Метрики нужно куда-то складывать и потом делать выборки. Эту задачу решают специализированные БД — Time Series Database.

**Особенности TSDB:**

* **Обработка временны́х рядов:** Однотипные измерения, привязанные ко времени.
* **Оптимизация:** Хранение числа, записанного через равные интервалы времени.
* **Пример:** Для сбора ежедневной температуры воздуха достаточно хранить `[(day1, t1), (day2, t2), ...]` и больше ничего.

**Главная особенность:** TSDB нужны, чтобы сохранять время и одно число, привязанное к этому времени.

**Специфика TSDB:**

* **Реляционные БД:** Ограниченная поддержка SQL или её отсутствие.
* **Типы данных:** Урезаны по сравнению с традиционными БД.
* **Оптимизация:** На постоянную непрерывную запись.

**Языки запросов:** Поскольку TSDB не используют SQL, они применяют собственные метрико-ориентированные языки запросов, оптимизированные для работы с временными рядами. Например, InfluxDB изначально имел SQL-подобные запросы, но на больших объёмах возникли проблемы с high availability.

> **См. также:** [Лейблы и кардинальность](./labels_and_cardinality.md) — влияние кардинальности на производительность TSDB.

## Основные понятия

### Логика и архитектура хранения

Чтобы понять, почему TSDB устроен именно так, можно рассмотреть проблему хранения данных с миллионов "термометров".

* **Проблема №1: Миллионы файлов.** Если создавать отдельный файл для каждого источника (термометра), это приведет к миллионам файлов и огромному количеству мелких операций записи (I/O), что неэффективно для дисковой системы.
* **Проблема №2: Один большой файл.** Если писать все данные в один общий файл, он быстро станет гигантским. Чтение данных для одного графика потребует сканирования всего файла, что крайне медленно.

**Решение Prometheus TSDB:**

1. **Активные данные в RAM:** Чтобы ускорить запись, все новые данные сначала попадают в **Head Block** в оперативной памяти. RAM выдерживает огромное количество операций записи и обеспечивает мгновенный доступ.
2. **Защита через WAL:** Поскольку RAM энергозависима, все входящие сэмплы немедленно дублируются в **Write-Ahead Log (WAL)** на диске. В случае сбоя Prometheus восстановит Head Block из WAL.
3. **Сброс на диск блоками:** Периодически (раз в 2 часа) Head Block "закрывается" и как единое целое записывается на диск в виде **блока**. Это превращает множество мелких операций записи в одну крупную, что гораздо эффективнее для диска.
4. **Индексация лейблов:** Хранить полный набор лейблов для каждого сэмпла было бы расточительно. Поэтому TSDB присваивает каждой уникальной комбинации лейблов (каждому временному ряду) числовой ID. В чанках и блоках хранятся только эти ID, а маппинг `ID -> набор лейблов` хранится в **индексе** блока. Это значительно экономит место.
5. **Сжатие (Compaction):** Со временем множество мелких (2-часовых) блоков объединяются в более крупные (например, 8-часовые, суточные). Это уменьшает количество файлов на диске и ускоряет запросы за длительные периоды времени.

### Жизненный цикл сэмпла

1. Prometheus опрашивает таргет и получает новые сэмплы.
2. Сэмплы немедленно записываются в файлы **WAL** на диске для обеспечения долговечности.
3. Одновременно сэмплы помещаются в **Head Block** в оперативной памяти. Внутри него они группируются в чанки.
4. Каждые 2 часа (по умолчанию) Head Block "закрывается" и записывается на диск как новый постоянный **Блок**. На его месте в памяти создается новый пустой Head Block.
5. В фоновом режиме запускается процесс **Compaction**, который объединяет старые, более мелкие блоки в более крупные, уменьшая количество файлов и оптимизируя индекс.

### Визуализация архитектуры

```
┌─────────────────────────────────────────────────────────────┐
│                        Prometheus                            │
├─────────────────────────────────────────────────────────────┤
│  Scrape → WAL (disk) → Head Block (RAM) → Block (disk)     │
│                              │              │                │
│                              │              └─> Compaction   │
│                              │                 (merge)       │
│                              └─> Recovery    └─> Retention  │
│                                  after crash     (delete)   │
└─────────────────────────────────────────────────────────────┘
```

## Практические сценарии

### Модульная архитектура хранения и внешние бэкенды

Внутренняя TSDB Prometheus эффективна для относительно небольших объемов данных. При этом Prometheus спроектирован с модульной архитектурой, позволяющей интегрироваться с внешними системами хранения для решения задач [масштабирования и долгосрочного хранения](../scaling/overview.md).

* **Интерфейс адаптера:** Prometheus записывает и считывает данные не напрямую, а через унифицированный [интерфейс адаптера (remote read/write)](../scaling/remote_read_write.md). Это означает, что для Prometheus неважно, куда именно записываются метрики; ему нужен лишь адаптер, реализующий необходимые функции для работы с данными.
* **Гибкость:** Такой подход позволяет подключать различные сторонние Time Series Database в качестве бэкендов для хранения данных, которые могут предложить лучшую масштабируемость, долгосрочное хранение или кластеризацию.
* **Примеры внешних TSDB бэкендов:**
  * **[VictoriaMetrics](../../VictoriaMetrics/overview.md):** Высокопроизводительное, горизонтально масштабируемое и более универсальное решение, популярное для Prometheus.
  * **[Thanos](../scaling/thanos_overview.md):** Решение для обеспечения глобального обзора, высокой доступности и долгосрочного хранения метрик Prometheus, тесно ориентированное на работу в Kubernetes.
  * **[Mimir](../../Mimir/mimir_overview.md):** Еще одно горизонтально масштабируемое решение от Grafana Labs.
  * **Другие:** Существуют адаптеры для таких систем, как [ClickHouse](../../Databases/clickhouse.md), Elasticsearch, Graphite, InfluxDB, Kafka, что позволяет использовать их для хранения данных Prometheus в зависимости от конкретных требований.

### Мониторинг TSDB

**Ключевые метрики для отслеживания состояния TSDB:**

```promql
# Размер TSDB на диске (байты)
prometheus_tsdb_storage_blocks_bytes

# Количество блоков на диске
prometheus_tsdb_storage_blocks

# Время последней компакции
prometheus_tsdb_compactions_total

# Количество активных рядов в Head Block
prometheus_tsdb_head_series

# Количество сэмплов в памяти
prometheus_tsdb_head_samples_appended_total

# Размер WAL (байты)
prometheus_tsdb_wal_size_bytes
```

**Алерты на проблемы с TSDB:**

```yaml
# Алерт на высокую кардинальность
- alert: HighTSDBCardinality
  expr: prometheus_tsdb_head_series > 100000
  for: 15m
  labels:
    severity: warning
  annotations:
    summary: "Высокая кардинальность TSDB"
    description: "Количество рядов: {{ $value | humanize }}"

# Алерт на быстрый рост рядов (churn rate)
- alert: HighChurnRate
  expr: |
    rate(prometheus_tsdb_head_series_created_total[5m]) > 1000
  for: 10m
  labels:
    severity: critical
  annotations:
    summary: "Высокий churn rate"
    description: "Создаётся {{ $value | humanize }} рядов/сек"

# Алерт на заполнение диска
- alert: TSDBDiskAlmostFull
  expr: |
    (prometheus_tsdb_storage_blocks_bytes / prometheus_tsdb_storage_blocks_bytes_limit) > 0.85
  for: 30m
  labels:
    severity: warning
  annotations:
    summary: "TSDB диск заполнен на {{ $value | humanizePercentage }}"
```

> **См. также:** [Rules и алертинг](../rules.md), [promtool](../promtool_and_best_practices.md).

### Анализ TSDB с помощью promtool

```bash
# Анализ дампа TSDB (покажет топ метрик по кардинальности)
promtool tsdb analyze /path/to/tsdb/data

# Анализ конкретного блока
promtool tsdb analyze --block-id <block-id> /path/to/tsdb/data

# Дамп метаданных
promtool tsdb dump /path/to/tsdb/data
```

## Дополнительная информация

### Ключевые принципы и ограничения

Архитектура TSDB основана на нескольких компромиссах, направленных на максимальную производительность записи и чтения диапазонов данных.

* **Отсутствие выборочного удаления:** В TSDB Prometheus намеренно отсутствует возможность удаления отдельных строк (сэмплов). Это позволяет использовать более простые и быстрые механизмы хранения с линейным распределением данных, что существенно ускоряет выборку данных за определенный период времени.
* **Эффективное удаление по сроку хранения:** Удаление устаревших данных не является ресурсоемкой операцией, поскольку Prometheus просто удаляет целые блоки данных, вышедшие за пределы установленного срока хранения (`retention period`).
* **Единый срок хранения:** Нельзя задавать разные периоды хранения для разных метрик. Глобальная настройка `retention` (см. [параметры `retention`](../configuration.md#storage-retention)) применяется ко всем данным в TSDB.
* **"Вечные" серии:** Если вы перестали собирать метрику или вывели из эксплуатации хост, связанные с ними данные (временные ряды и их место в индексе) нельзя выборочно удалить из базы. Они будут удалены только тогда, когда истечет срок хранения всего блока, содержащего последний сэмпл этой метрики. Это напрямую связано с проблемой `Churn Rate`.

### Проблемы производительности TSDB

#### Высокая кардинальность

Как уже было описано в [labels_and_cardinality](./labels_and_cardinality.md), большое количество уникальных временных рядов (высокая кардинальность) приводит к разрастанию индекса, что требует больше RAM и замедляет запросы.

#### Churn Rate (Скорость обновления рядов)

**Churn Rate** — это скорость, с которой временные ряды появляются и исчезают. В отличие от статической кардинальности (общее число рядов), churn характеризует именно **динамику изменения** состава рядов.

* **Причина:** Частое создание и удаление объектов, генерирующих метрики. Классический пример — контейнеры или поды в Kubernetes, которые могут создаваться для выполнения коротких задач и быстро удаляться. Каждый новый под с уникальными лейблами создает новые временные ряды.
  * **Аналогия:** Представьте три термометра. Один работает стабильно, и Prometheus собирает с него полные чанки по 120 сэмплов. Два других работают нестабильно — то активны, то нет. С них получаются неполные чанки с малым количеством сэмплов.
* **Последствия:**
    1. **Неэффективное сжатие:** Появляются неполные чанки. Они содержат мало сэмплов, но занимают место на диске и хуже сжимаются.
    2. **Разбухание индекса и метаданных:** TSDB вынуждена хранить в индексе информацию даже о тех временных рядах, которые уже неактивны. Индекс увеличивается, что повышает потребление памяти.
    3. **Замедление Compaction:** Процесс сжатия работает медленнее, так как обрабатывает большое количество мелких и неэффективных чанков.
    4. **Рост потребления RAM и нагрузки на WAL.**

Высокий churn rate может быть даже более опасен, чем высокая статическая кардинальность.

* **Как отслеживать:** Для более глубокого анализа проблем с производительностью TSDB можно использовать [`promtool tsdb analyze`](../promtool_and_best_practices.md#promtool-tsdb-analyze). Основные метрики для отслеживания churn rate включают:
  * `prometheus_tsdb_head_series`: Текущее количество активных временных рядов.
  * `rate(prometheus_tsdb_head_series_created_total[5m])`: Скорость создания новых рядов.
  * `rate(prometheus_tsdb_head_series_removed_total[5m])`: Скорость удаления старых рядов.

    Если скорости создания и удаления рядов высокие и постоянно "прыгают", это явный признак высокого churn rate.

### Настройка retention period

**Параметры командной строки:**

```bash
prometheus \
  --storage.tsdb.path=/prometheus \
  --storage.tsdb.retention.time=15d \
  --storage.tsdb.retention.size=10GB
```

| Параметр | Описание | По умолчанию |
|---|---|---|
| `--storage.tsdb.path` | Путь к данным TSDB | `./data` |
| `--storage.tsdb.retention.time` | Время хранения данных | `15d` |
| `--storage.tsdb.retention.size` | Максимальный размер TSDB | `0` (без ограничений) |
| `--storage.tsdb.min-block-duration` | Минимальная длительность блока | `2h` |
| `--storage.tsdb.max-block-duration` | Максимальная длительность блока | `2h` |
| `--storage.tsdb.wal-segment-size` | Размер сегмента WAL | `128MB` |

> **См. также:** [Configuration](../configuration.md) — полная справка по параметрам.

### Оптимизация производительности TSDB

**Рекомендации:**

1. **Следите за кардинальностью:** Используйте [best practices](./labels_and_cardinality.md) для избежания высокой кардинальности.
2. **Настройте retention:** Выберите разумный период хранения в зависимости от доступного диска.
3. **Выделите достаточно RAM:** Минимум 2GB для малых инсталляций, 8GB+ для крупных.
4. **Используйте SSD:** TSDB чувствительна к скорости диска, особенно при compaction.
5. **Мониторьте churn rate:** Высокий churn rate опаснее статической кардинальности.
6. **Рассмотрите внешнее хранилище:** Для долгосрочного хранения используйте [VictoriaMetrics](../../VictoriaMetrics/overview.md), [Thanos](../scaling/thanos_overview.md) или [Mimir](../../Mimir/mimir_overview.md).
