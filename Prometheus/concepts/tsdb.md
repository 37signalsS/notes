# Внутреннее устройство Prometheus TSDB

## Определения

* **TSDB (Time Series Database):** Собственная база данных временных рядов [Prometheus](../overview.md), спроектированная для эффективной записи, экстремального сжатия метрик и быстрого чтения при запросах.
* **Сэмпл (Sample):** Единичная точка данных, состоящая из значения (`float64`) и временной метки (`int64`, timestamp в миллисекундах).
* **Временной ряд (Time Series):** Поток сэмплов, принадлежащих одной и той же метрике с идентичным набором [лейблов](./labels_and_cardinality.md).
* **Чанк (Chunk):** Сжатый контейнер для сэмплов одного временного ряда, обычно содержащий до 120 сэмплов. В современных версиях используются **m-map chunks** — заполненные чанки сбрасываются на диск и отображаются в память через `mmap`.
* **Блок (Block):** Директория на диске, содержащая данные за определённый промежуток времени (по умолчанию — 2 часа). Включает в себя чанки, индекс и метаданные.
* **Head Block (Головной блок):** Активная область в оперативной памяти (RAM), которая принимает все новые входящие сэмплы до их записи в постоянный блок.
* **WAL (Write-Ahead Log):** Журнал упреждающей записи на диске. Все входящие сэмплы сначала фиксируются в WAL для обеспечения сохранности данных при сбоях. См. [Журнал предзаписи (WAL)](../../Databases/Concepts/write_ahead_log.md).
* **WBL (Write-Behind Log):** Специализированный журнал для данных вне порядка (Out-of-Order), появившийся в стабильном виде в Prometheus v3.
* **Сжатие (Compaction):** Процесс объединения нескольких блоков в один более крупный для оптимизации хранения и ускорения запросов.
* **Индекс (Index):** Файл внутри каждого блока, содержащий инвертированные структуры для быстрого поиска временных рядов по их лейблам.
* **Нативные гистограммы (Native Histograms):** Формат хранения (Sparse Histograms) в Prometheus v3, где все бакеты упакованы в **один** временной ряд с динамическими границами.
* **Out-of-Order (OOO) Ingestion:** Возможность базы принимать данные, временная метка которых меньше (старше), чем у уже записанных данных.

## Базовые концепции

### Зачем нужны TSDB

Метрики нужно куда-то складывать и потом делать выборки. Эту задачу решают специализированные БД — Time Series Database.

**Особенности TSDB:**

* **Обработка временны́х рядов:** Однотипные измерения, привязанные ко времени.
* **Оптимизация:** Хранение числа, записанного через равные интервалы времени.
* **Пример:** Для сбора ежедневной температуры воздуха достаточно хранить `[(day1, t1), (day2, t2), ...]` и больше ничего.

**Главная особенность:** TSDB нужны, чтобы сохранять время и одно число, привязанное к этому времени.

**Специфика TSDB:**

* **Реляционные БД:** Ограниченная поддержка SQL или её отсутствие.
* **Типы данных:** Урезаны по сравнению с традиционными БД (в основном float64).
* **Оптимизация:** На постоянную непрерывную запись (Append-only).

**Языки запросов:** Поскольку TSDB не используют SQL, они применяют собственные метрико-ориентированные языки запросов (PromQL), оптимизированные для работы с временными рядами. Например, InfluxDB изначально имел SQL-подобные запросы, но на больших объёмах возникли проблемы с производительностью и high availability.

> **См. также:** [Лейблы и кардинальность](./labels_and_cardinality.md) — влияние кардинальности на производительность TSDB.

### Логика и архитектура хранения

Чтобы понять, почему TSDB устроен именно так, можно рассмотреть проблему хранения данных с миллионов "термометров".

* **Проблема №1: Миллионы файлов.** Если создавать отдельный файл для каждого источника (термометра), это приведет к миллионам файлов и огромному количеству мелких операций записи (I/O), что неэффективно для дисковой системы.
* **Проблема №2: Один большой файл.** Если писать все данные в один общий файл, он быстро станет гигантским. Чтение данных для одного графика потребует сканирования всего файла, что крайне медленно.

**Решение Prometheus TSDB:**

1. **Активные данные в RAM:** Чтобы ускорить запись, все новые данные сначала попадают в **Head Block** в оперативной памяти. RAM выдерживает огромное количество операций записи и обеспечивает мгновенный доступ.
2. **Защита через WAL/WBL:** Поскольку RAM энергозависима, все входящие сэмплы немедленно дублируются в **Write-Ahead Log (WAL)** на диске. В случае сбоя Prometheus восстановит Head Block из WAL. Для данных вне порядка (OOO) используется **Write-Behind Log (WBL)**. В Prometheus v3 WAL сжимается по умолчанию, что экономит место.
3. **Механизм m-map чанков:** Как только чанк временного ряда в Head-блоке заполняется (~120 сэмплов), он записывается на диск в папку `chunks_head` и отображается в память через `mmap`. Это позволяет держать в RAM только активные (незаполненные) чанки, что радикально снижает потребление памяти при миллионах рядов.
4. **Сброс на диск блоками:** Периодически (раз в 2 часа) данные из Head Block и m-map чанков "закрываются" и записываются на диск в виде **блока**. Это превращает множество мелких операций записи в одну крупную.
5. **Индексация лейблов:** Хранить полный набор лейблов для каждого сэмпла было бы расточительно. Поэтому TSDB присваивает каждой уникальной комбинации лейблов (каждому временному ряду) числовой ID. В чанках и блоках хранятся только эти ID, а маппинг `ID -> набор лейблов` хранится в **индексе** блока. Это значительно экономит место.
6. **Сжатие (Compaction):** Со временем множество мелких (2-часовых) блоков объединяются в более крупные (например, 8-часовые, суточные). Это уменьшает количество файлов на диске и ускоряет запросы.

### Жизненный цикл сэмпла

1. Prometheus опрашивает таргет и получает новые сэмплы.
2. Сэмплы записываются в файлы **WAL** (или **WBL** для OOO) на диске.
3. Сэмплы помещаются в **Head Block** в RAM. Внутри него они группируются в чанки.
4. При заполнении чанка он сбрасывается в `chunks_head` и становится доступен через `mmap`.
5. Каждые 2 часа (по умолчанию) Head Block "закрывается" и записывается на диск как новый постоянный **Блок**. Создается индекс блока.
6. В фоновом режиме запускается процесс **Compaction**, который объединяет старые, более мелкие блоки в более крупные, оптимизируя индекс и удаляя дубликаты.

### Визуализация архитектуры

```text
┌─────────────────────────────────────────────────────────────┐
│                        Prometheus v3                        │
├─────────────────────────────────────────────────────────────┤
│  Scrape → WAL/WBL (disk) → Head Block (RAM) → Block (disk) │
│                               │               │              │
│                               │               └─> Compaction │
│                               │                  (merge)     │
│             M-map Chunks <────┴─> Recovery    └─> Retention  │
│             (chunks_head)         after crash    (delete)    │
└─────────────────────────────────────────────────────────────┘
```

## Практические сценарии

### Модульная архитектура хранения и внешние бэкенды

Внутренняя TSDB эффективна для оперативного мониторинга. Для долгосрочного хранения используется [remote read/write](../scaling/remote_read_write.md).

* **Интерфейс адаптера:** Prometheus записывает и считывает данные через унифицированный интерфейс. Ему нужен лишь адаптер, реализующий необходимые функции.
* **Примеры внешних TSDB бэкендов:**
  * **[VictoriaMetrics](../../VictoriaMetrics/overview.md):** Высокая плотность хранения, агрессивное сжатие.
  * **[Thanos](../scaling/thanos_overview.md):** Глобальный обзор, хранение блоков в S3/GCS.
  * **[Mimir](../../Mimir/mimir_overview.md):** Горизонтально масштабируемое решение от Grafana Labs.

### Мониторинг TSDB

**Ключевые метрики для отслеживания состояния TSDB:**

```promql
# Размер TSDB на диске (байты)
prometheus_tsdb_storage_blocks_bytes

# Количество активных рядов в Head Block
prometheus_tsdb_head_series

# Скорость создания рядов (Churn Rate)
rate(prometheus_tsdb_head_series_created_total[5m])

# Размер WAL на диске
prometheus_tsdb_wal_size_bytes

# Количество сэмплов вне порядка (Out-of-Order)
prometheus_tsdb_out_of_order_samples_appended_total
```

**Алерты на проблемы с TSDB:**

```yaml
# Алерт на высокую кардинальность
- alert: HighTSDBCardinality
  expr: prometheus_tsdb_head_series > 1000000
  for: 15m
  labels:
    severity: warning
  annotations:
    summary: "Высокая кардинальность TSDB"
    description: "Количество активных рядов превысило 1 млн: {{ $value }}"

# Алерт на быстрый рост рядов (churn rate)
- alert: HighChurnRate
  expr: rate(prometheus_tsdb_head_series_created_total[5m]) > 5000
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "Высокий churn rate"
    description: "Создаётся {{ $value | humanize }} новых рядов/сек. Проверьте эфемерные лейблы."

# Алерт на заполнение диска
- alert: TSDBDiskAlmostFull
  expr: (prometheus_tsdb_storage_blocks_bytes / prometheus_tsdb_storage_blocks_bytes_limit) > 0.85
  for: 30m
  labels:
    severity: critical
  annotations:
    summary: "TSDB диск заполнен на 85%"
```

### Анализ TSDB с помощью promtool

```bash
# Анализ дампа TSDB (топ метрик по кардинальности)
promtool tsdb analyze /path/to/tsdb/data

# Анализ конкретного блока
promtool tsdb analyze --block-id <block-id> /path/to/tsdb/data

# Проверка целостности блоков
promtool tsdb check-blocks /path/to/tsdb/data
```

## Дополнительная информация

### Ключевые принципы и ограничения

* **Отсутствие выборочного удаления:** В TSDB Prometheus нельзя удалить отдельные сэмплы. Это упрощает хранение и ускоряет выборку.
* **Эффективное удаление по сроку хранения:** Prometheus удаляет данные целыми блоками, вышедшими за `retention period`.
* **Единый срок хранения:** Настройка `retention` применяется ко всем данным в базе глобально.
* **"Вечные" серии:** Данные о метрике сохраняются в блоке до его полного удаления, даже если сбор метрики прекращен. Это причина проблемы `Churn Rate`.

### Проблемы производительности TSDB

#### Высокая кардинальность
Большое количество уникальных рядов раздувает индекс, что требует больше RAM и замедляет запросы.
1.  **RAM (Memory):** Для каждого временного ряда Prometheus держит в памяти структуру индекса и последние сэмплы. При 1 млн рядов потребление RAM может составлять 8–16 ГБ.
2.  **CPU:** Расчёт агрегаций по миллионам рядов требует колоссальных вычислительных мощностей.
3.  **Inverted Index:** Кардинальность раздувает файл `index`. Поиск замедляется из-за сканирования огромных списков идентификаторов серий.
4.  **OOM Killer:** Аварийная остановка процесса из-за нехватки памяти при тяжелых запросах.
См. [labels_and_cardinality](./labels_and_cardinality.md).

#### Churn Rate (Скорость обновления рядов)
Это скорость, с которой временные ряды появляются и исчезают.
* **Причина:** Короткоживущие объекты (поды в K8s).
* **Аналогия:** Представьте три термометра. Один работает стабильно (с него идут полные чанки по 120 сэмплов). Два других работают нестабильно — то активны, то нет. С них получаются неполные чанки, которые плохо сжимаются и занимают лишнее место в индексе.
* **Последствия:** Разбухание индекса за счет "мертвых" рядов, замедление компакции, рост нагрузки на RAM.

### Настройка параметров хранения (Prometheus v3)

| Параметр | Описание | По умолчанию |
|---|---|---|
| `--storage.tsdb.retention.time` | Время хранения данных | `15d` |
| `--storage.tsdb.retention.size` | Максимальный размер базы | `0` (без лимита) |
| `--storage.tsdb.out-of-order.time-window` | Окно для OOO-данных | `0s` (нужно включить) |
| `--storage.tsdb.wal-compression` | Сжатие WAL-логов | `true` |
| `--storage.tsdb.min-block-duration` | Минимальная длительность блока | `2h` |

### Рекомендации по ресурсам (Prometheus v3.x)

| Кол-во рядов | CPU | RAM | Режим работы |
| :--- | :--- | :--- | :--- |
| до 100 000 | 2 ядра | 4 ГБ | Single Instance |
| 100k — 1M | 4–8 ядер | 8–16 ГБ | Single Instance / Agent |
| 1M — 5M | 8–16 ядер | 32–64 ГБ | Оптимизированный TSDB |
| > 5M | 16+ ядер | 128 ГБ+ | Рекомендуется **[масштабирование](../scaling/overview.md)** |

### Оптимизация производительности

1. **Следите за кардинальностью:** Не используйте ID пользователей или хэши в лейблах.
2. **Используйте SSD:** TSDB крайне чувствительна к латентности диска при записи WAL.
3. **Мониторьте churn rate:** Высокий churn опаснее статической кардинальности.
4. **Нативные гистограммы (v3):** Используйте их для снижения количества рядов при работе с распределениями.
