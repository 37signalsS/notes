# Внутреннее устройство Prometheus TSDB

## Определения

* **TSDB (Time Series Database):** Собственная база данных временных рядов [Prometheus](../overview.md), спроектированная для эффективной записи, экстремального сжатия метрик и быстрого чтения при запросах.
* **Сэмпл (Sample):** Единичная точка данных, состоящая из значения (`float64`) и временной метки (`int64`, timestamp в миллисекундах).
* **Временной ряд (Time Series):** Поток сэмплов, принадлежащих одной и той же метрике с идентичным набором [лейблов](./labels_and_cardinality.md).
* **Чанк (Chunk):** Сжатый контейнер для сэмплов одного временного ряда, обычно содержащий до 120 сэмплов. В современных версиях используются **m-map chunks** — заполненные чанки сбрасываются на диск и отображаются в память через `mmap`. Сжатие чанков выполняется по алгоритму **XOR** (Gorilla-style): разницы между последовательными значениями и временными метками кодируются переменной длиной, что обеспечивает коэффициент сжатия до 1.37 байта на сэмпл для типичных метрик.
* **Блок (Block):** Директория на диске, содержащая данные за определённый промежуток времени (по умолчанию — 2 часа). Включает в себя чанки, индекс и метаданные.
* **Head Block (Головной блок):** Активная область в оперативной памяти (RAM), которая принимает все новые входящие сэмплы до их записи в постоянный блок.
* **WAL (Write-Ahead Log):** Журнал упреждающей записи на диске. Все входящие сэмплы сначала фиксируются в WAL для обеспечения сохранности данных при сбоях. См. [Журнал предзаписи (WAL)](../../Databases/Concepts/write_ahead_log.md).
* **WBL (Write-Behind Log):** Специализированный журнал для данных вне порядка (Out-of-Order), появившийся в стабильном виде в Prometheus v3.
* **Сжатие (Compaction):** Процесс объединения нескольких блоков в один более крупный для оптимизации хранения и ускорения запросов.
* **Индекс (Index):** Файл внутри каждого блока, содержащий инвертированные структуры для быстрого поиска временных рядов по их лейблам. Включает **symbol table** (отображение строк лейблов в числовые ID) и **postings lists** (списки series ID для каждой пары лейбл=значение).
* **Нативные гистограммы (Native Histograms):** Формат хранения (Sparse Histograms) в Prometheus v3, где все бакеты упакованы в **один** временной ряд с динамическими границами.
* **Out-of-Order (OOO) Ingestion:** Возможность базы принимать данные, временная метка которых меньше (старше), чем у уже записанных данных.
* **Tombstone (Маркер удаления):** Запись в индексе блока, помечающая временной ряд как удалённый. Физическое удаление данных происходит только во время полной компакции блока.
* **Series ID:** Уникальный 64-битный идентификатор временного ряда внутри блока. Используется в чанках и инвертированном индексе вместо полного набора лейблов для экономии места.
* **Segment (Сегмент WAL):** Файл фиксированного размера (по умолчанию 512 МБ) в директории WAL. При заполнении сегмента создаётся новый, старый архивируется или удаляется после записи данных в блоки.

## Базовые концепции

### Зачем нужны TSDB

Метрики нужно куда-то складывать и потом делать выборки. Эту задачу решают специализированные БД — Time Series Database.

**Особенности TSDB:**

* **Обработка временны́х рядов:** Однотипные измерения, привязанные ко времени.
* **Оптимизация:** Хранение числа, записанного через равные интервалы времени.
* **Пример:** Для сбора ежедневной температуры воздуха достаточно хранить `[(day1, t1), (day2, t2), ...]` и больше ничего.

**Главная особенность:** TSDB нужны, чтобы сохранять время и одно число, привязанное к этому времени.

**Специфика TSDB:**

* **Реляционные БД:** Ограниченная поддержка SQL или её отсутствие.
* **Типы данных:** Урезаны по сравнению с традиционными БД (в основном float64).
* **Оптимизация:** На постоянную непрерывную запись (Append-only).

**Языки запросов:** Поскольку TSDB не используют SQL, они применяют собственные метрико-ориентированные языки запросов (PromQL), оптимизированные для работы с временными рядами. Например, InfluxDB изначально имел SQL-подобные запросы, но на больших объёмах возникли проблемы с производительностью и high availability.

> **См. также:** [Лейблы и кардинальность](./labels_and_cardinality.md) — влияние кардинальности на производительность TSDB.

### Логика и архитектура хранения

Чтобы понять, почему TSDB устроен именно так, можно рассмотреть проблему хранения данных с миллионов "термометров".

* **Проблема №1: Миллионы файлов.** Если создавать отдельный файл для каждого источника (термометра), это приведет к миллионам файлов и огромному количеству мелких операций записи (I/O), что неэффективно для дисковой системы.
* **Проблема №2: Один большой файл.** Если писать все данные в один общий файл, он быстро станет гигантским. Чтение данных для одного графика потребует сканирования всего файла, что крайне медленно.

**Решение Prometheus TSDB:**

1. **Активные данные в RAM:** Чтобы ускорить запись, все новые данные сначала попадают в **Head Block** в оперативной памяти. RAM выдерживает огромное количество операций записи и обеспечивает мгновенный доступ.
2. **Защита через WAL/WBL:** Поскольку RAM энергозависима, все входящие сэмплы немедленно дублируются в **Write-Ahead Log (WAL)** на диске. В случае сбоя Prometheus восстановит Head Block из WAL. Для данных вне порядка (OOO) используется **Write-Behind Log (WBL)**. В Prometheus v3 WAL сжимается по умолчанию, что экономит место.
3. **Механизм m-map чанков:** Как только чанк временного ряда в Head-блоке заполняется (~120 сэмплов), он записывается на диск в папку `chunks_head` и отображается в память через `mmap`. Это позволяет держать в RAM только активные (незаполненные) чанки, что радикально снижает потребление памяти при миллионах рядов.
4. **Сброс на диск блоками:** Периодически (раз в 2 часа) данные из Head Block и m-map чанков "закрываются" и записываются на диск в виде **блока**. Это превращает множество мелких операций записи в одну крупную.
5. **Индексация лейблов:** Хранить полный набор лейблов для каждого сэмпла было бы расточительно. Поэтому TSDB присваивает каждой уникальной комбинации лейблов (каждому временному ряду) числовой ID. В чанках и блоках хранятся только эти ID, а маппинг `ID -> набор лейблов` хранится в **индексе** блока. Это значительно экономит место.
6. **Сжатие (Compaction):** Со временем множество мелких (2-часовых) блоков объединяются в более крупные (например, 8-часовые, суточные). Это уменьшает количество файлов на диске и ускоряет запросы.

#### Структура инвертированного индекса

Индекс каждого блока состоит из двух основных компонентов:

* **Symbol Table:** Отображает строковые значения лейблов в уникальные числовые ID. Например, `job="prometheus"` может иметь ID 42. Это позволяет хранить в чанках и постлистах компактные числа вместо строк.
* **Postings Lists (Списки идентификаторов):** Для каждого уникального `label_id = value_id` хранится отсортированный список `series_id`, которые содержат эту пару. При выполнении PromQL-запроса TSDB пересекает постлисты соответствующих селекторов, получая итоговый набор рядов.

Поиск по индексу происходит за logarithmic time относительно количества серий, что делает запросы быстрыми даже при миллионах рядов.

#### Формат чанков и XOR-сжатие

Каждый чанк содержит сэмплы одного временного ряда. Значения и временные метки хранятся в сжатом виде:

* **Timestamps:** Разница между последовательными метками кодируется переменной длиной (Gorilla-style). При стандартном интервале скрапинга (15–60 секунд) разницы малы и занимают 1–2 байта.
* **Values:** Значения `float64` кодируются по алгоритму XOR: вычисляется XOR текущего и предыдущего значения, затем ведущие и хвостовые нули отбрасываются. Для стабильных метрик (например, `up`) это даёт 0–1 байт на сэмпл.
* **Результат:** При типичном интервале 15 секунд и стабильных метрик чанк на 120 сэмплов занимает 120–200 байт вместо 1920 байт (120 × 16 байт несжатых float64).

#### Формат WAL

WAL разделён на сегменты фиксированного размера (по умолчанию 512 МБ). Каждый сегмент состоит из записей:

* **Запись (Record):** Содержит сериализованные сэмплы, метаданные блока или служебные события. Каждая запись имеет 4-байтовый CRC32 для контроля целостности.
* **Сегментация:** При достижении порога размера создаётся новый сегмент. Старые сегменты удаляются только после того, как все содержащиеся в них сэмплы были записаны в постоянные блоки.
* **Сжатие:** В Prometheus v3 WAL сжимается по умолчанию (snappy), что снижает объём на диске на 60–80%.

#### Структура блока на диске

Каждый блок — это директория с файлами:

```
<block-id>/
├── chunks_head/          # M-map чанки (заполненные чанки Head-блока)
├── chunks/               # Чанки постоянных блоков (сжатые)
├── index                 # Инвертированный индекс (symbol table + postings)
├── tombstones            # Маркеры удаления (если есть)
├── deletion.mark         # Файл-маркер, если блок помечен на удаление
└── meta.json             # Метаданные блока (minTime, maxTime, stats)
```

* **`chunks/`:** Файлы по 64 МБ (по умолчанию), содержащие сжатые чанки нескольких временных рядов.
* **`index`:** Самый важный файл для запросов. Размер пропорционален кардинальности.
* **`tombstones`:** Создаётся при удалении серий через API. Удаление происходит только при компакции.
* **`deletion.mark`:** Пустой файл, сигнализирующий, что блок должен быть удалён при следующей компакции.

### Жизненный цикл сэмпла

1. Prometheus опрашивает таргет и получает новые сэмплы.
2. Сэмплы записываются в файлы **WAL** (или **WBL** для OOO) на диске.
3. Сэмплы помещаются в **Head Block** в RAM. Внутри него они группируются в чанки.
4. При заполнении чанка он сбрасывается в `chunks_head` и становится доступен через `mmap`.
5. Каждые 2 часа (по умолчанию) Head Block "закрывается" и записывается на диск как новый постоянный **Блок**. Создается индекс блока.
6. В фоновом режиме запускается процесс **Compaction**, который объединяет старые, более мелкие блоки в более крупные, оптимизируя индекс и удаляя дубликаты.
7. При превышении `retention` блоки и соответствующие сегменты WAL удаляются.

### Out-of-Order (OOO) Ingestion

Prometheus v3 поддерживает приём данных с временными метками, отстающими от уже записанных:

* **Окно OOO:** Настраивается через `--storage.tsdb.out-of-order.time-window`. Включение OOO требует явного указания окна (например, `1h`), что защищает от случайного приёма устаревших данных.
* **WBL:** Данные вне порядка записываются в **Write-Behind Log**, а не в основной WAL. Это предотвращает фрагментацию основного журнала и упрощает восстановление.
* **Производительность:** OOO-данные требуют дополнительных операций поиска в индексе и медленнее вставляются. Используйте OOO только когда это необходимо (например, задержки в сети или буферизация на агентах).
* **Мониторинг:** Метрика `prometheus_tsdb_out_of_order_samples_appended_total` показывает количество успешно записанных OOO-сэмплов.

### Визуализация архитектуры

```text
┌─────────────────────────────────────────────────────────────┐
│                        Prometheus v3                        │
├─────────────────────────────────────────────────────────────┤
│  Scrape → WAL/WBL (disk) → Head Block (RAM) → Block (disk) │
│                               │               │              │
│                               │               └─> Compaction │
│                               │                  (merge)     │
│             M-map Chunks <────┴─> Recovery    └─> Retention  │
│             (chunks_head)         after crash    (delete)    │
└─────────────────────────────────────────────────────────────┘
```

## Практические сценарии

### Файловая структура TSDB на диске

Понимание структуры каталогов необходимо для диагностики, резервного копирования и очистки.

```
/var/lib/prometheus/
├── wal/                        # WAL сегменты
│   ├── 00000000
│   ├── 00000001
│   └── checkpoint.000002/      # Чекпоинт (снимок Head-блока)
├── chunks_head/                # M-map чанки активного Head-блока
└── <block-id>/                 # Постоянные блоки (2-часовые)
    ├── chunks/
    ├── index
    └── meta.json
```

* **`wal/`:** Содержит сегменты WAL и чекпоинты. Чекпоинт создаётся при каждом сбросе Head-блока и позволяет ускорить восстановление.
* **`chunks_head/`:** Файлы с заполненными чанками, отображёнными через `mmap`. Размер файлов зависит от количества рядов.
* **`<block-id>/`:** Каждый блок имеет уникальный ID (временную метку создания). Блоки Read-Only после создания.

### Резервное копирование и восстановление

**Вариант 1: Снэпшот через HTTP API (онлайн, без остановки)**

```bash
# Создание снэпшота
curl -X POST http://localhost:9090/api/v1/admin/tsdb/snapshot

# Результат:
# {"data":{"name":"20230916T153745Z-<hash>"}}

# Снэпшот создаётся в каталоге <storage.tsdb.path>/snapshots/
```

**Вариант 2: Файловый бэкап (офлайн, требует остановки Prometheus)**

```bash
# 1. Остановка Prometheus
systemctl stop prometheus

# 2. Архивирование данных
tar -czf /backup/prometheus-tsdb-$(date +%Y%m%d).tar.gz -C /var/lib/prometheus .

# 3. Запуск Prometheus
systemctl start prometheus
```

**Восстановление:**

```bash
# 1. Остановка Prometheus
systemctl stop prometheus

# 2. Восстановление данных
tar -xzf /backup/prometheus-tsdb-20230916.tar.gz -C /var/lib/prometheus

# 3. Запуск Prometheus
systemctl start prometheus
```

> **Важно:** WAL содержит данные, ещё не записанные в блоки. Для полного восстановления нужны и блоки, и WAL. При восстановлении из снэпшота Prometheus начнёт восстанавливать Head-блок из WAL автоматически.

### Настройка файловой системы и дисков

TSDB критична к латентности диска и надёжности хранения.

**Рекомендации по файловой системе:**

| Файловая система | Рекомендация | Примечание |
| :--- | :--- | :--- |
| **XFS** | Рекомендуется | Лучшая производительность при большом количестве файлов (XFS имеет высокий лимит inodes). |
| **ext4** | Допустима | Требует мониторинга количества inodes (`df -i`). |
| **ZFS** | Допустима с tuned | Требует выделения отдельного dataset для WAL и careful tuning `recordsize`. |
| **Btrfs** | Не рекомендуется | Известны проблемы с производительностью при большом количестве мелких файлов. |

**Mount options (XFS):**

```bash
# /etc/fstab
/dev/nvme1n1 /var/lib/prometheus xfs defaults,noatime,nodiratime,logbsize=256k 0 2
```

* **`noatime,nodiratime`:** Отключение записи времени доступа. Снижает лишние I/O-операции.
* **`logbsize=256k`:** Увеличение размера журнала XFS для лучшей производительности при批量ной записи.

**Разделение дисков:**

```bash
# Рекомендуемая схема (если возможно):
# /var/lib/prometheus/wal   → быстрый SSD (NVMe) — критично для записи
# /var/lib/prometheus/      → основной SSD (SATA/NVMe) — хранение блоков
```

WAL наиболее чувствителен к латентности, так как каждый сэмпл требует fsync.

### Мониторинг TSDB

**Ключевые метрики для отслеживания состояния TSDB:**

```promql
# Размер TSDB на диске (байты)
prometheus_tsdb_storage_blocks_bytes

# Количество активных рядов в Head Block
prometheus_tsdb_head_series

# Скорость создания рядов (Churn Rate)
rate(prometheus_tsdb_head_series_created_total[5m])

# Размер WAL на диске
prometheus_tsdb_wal_size_bytes

# Количество сэмплов вне порядка (Out-of-Order)
prometheus_tsdb_out_of_order_samples_appended_total

# Задержка сброса Head Block (в секунды)
time() - max(prometheus_tsdb_commit_timestamp_seconds)

# Количество чанков в Head Block
prometheus_tsdb_head_chunks

# Количество блоков на диске
prometheus_tsdb_blocks_loaded
```

**HTTP API для диагностики TSDB:**

```bash
# Статус TSDB (топ метрик по кардинальности, использование диска)
curl -s http://localhost:9090/api/v1/status/tsdb | jq .

# Создание снэпшота (онлайн)
curl -X POST http://localhost:9090/api/v1/admin/tsdb/snapshot

# Удаление серий по селектору (помечает как удалённые)
curl -X POST -d '{"match":{"__name__="old_metric"}}' http://localhost:9090/api/v1/admin/tsdb/delete_series

# Проверка готовности
curl -s http://localhost:9090/-/ready
```

### Анализ TSDB с помощью promtool

```bash
# Анализ дампа TSDB (топ метрик по кардинальности)
promtool tsdb analyze /path/to/tsdb/data

# Анализ конкретного блока
promtool tsdb analyze --block-id <block-id> /path/to/tsdb/data

# Проверка целостности блоков
promtool tsdb check-blocks /path/to/tsdb/data

# Дамп сырых данных (series/samples) в текстовом виде
promtool tsdb dump /path/to/tsdb/data
```

> **Примечание:** `promtool tsdb analyze` требует остановки Prometheus или работы с копией данных. Для живого сервера используйте `/api/v1/status/tsdb`.

### Устранение неполадок WAL

**Типичные ошибки и решения:**

| Ошибка | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| **WAL Corruption** | `panic: runtime error: index out of range` на старте | Некорректное завершение процесса, повреждение сегментов | Проверить сегменты в `wal/`. В крайнем случае удалить содержимое `wal/` (потеря последних 2 часов данных). |
| **WAL растёт** | Диск заполняется | Бэкенд long-term storage недоступен, блоки не записываются | Проверить доступность remote_write endpoint. Увеличить размер диска. |
| **Медленная запись** | Высокая латентность скрапинга | WAL на медленном диске (HDD), недостаточно IOPS | Переместить WAL на NVMe SSD. Проверить `iostat -x 1`. |
| **OOM при восстановлении** | Процесс убит при старте | WAL слишком большой, Head-блок не помещается в RAM | Увеличить `limits.memory` в Kubernetes. Рассмотреть Agent Mode для Edge-узлов. |

### Управление retention и удалением данных

Prometheus удаляет данные **целыми блоками**, а не отдельными сэмплами. Это упрощает хранение и ускоряет выборку.

**Механика удаления:**

1. **Retention by time:** При `--storage.tsdb.retention.time=15d` Prometheus удаляет блоки, у которых `maxTime` старше `now() - 15d`.
2. **Retention by size:** При `--storage.tsdb.retention.size=50GB` удаляются самые старые блоки, пока общий размер не опустится ниже лимита.
3. **Удаление через API:** `DELETE /api/v1/admin/tsdb/delete_series` помечает серии как удалённые (tombstones). Физическое удаление происходит при следующей компакции.
4. **Deletion Mark:** Файл `deletion.mark` в блоке сигнализирует, что блок должен быть удалён. Compaction удаляет такие блоки при следующем проходе.

**Практические рекомендации:**

* **Не смешивайте** `retention.time` и `retention.size` без понимания последствий. Обычно достаточно одного параметра.
* **Retention 15–30 дней** — стандарт для локальной TSDB. Для более длительного хранения используйте remote_write в VictoriaMetrics, Thanos или Mimir.
* **Не удаляйте файлы вручную** из каталога TSDB. Используйте API или retention. Ручное удаление приведёт к коррупции индекса.

### Резервное копирование и восстановление (Disaster Recovery)

#### Стратегии бэкапа

| Стратегия | RPO | RTO | Сложность | Когда использовать |
|:---|:---|:---|:---|:---|
| **API snapshot** | ~2 часа (по WAL) | 10-30 минут | Низкая | Малые среды, dev/test |
| **LVM/ZFS snapshot** | Моментальный | 5-15 минут | Средняя | Bare-metal, production |
| **rsync с компакцией** | 15-30 минут | 30-60 минут | Низкая | Remote backup |
| **S3 через Thanos/VM** | Real-time | Minutes | Средняя | Где уже используется LTS |

#### Бэкап через API snapshot (онлайн)

```bash
# Создание снэпшота (не требует остановки Prometheus)
curl -X POST http://localhost:9090/api/v1/admin/tsdb/snapshot

# Ответ:
# {"data":{"name":"20230916T153745Z-<hash>"}}

# Снэпшот хранится в <storage.tsdb.path>/snapshots/<name>/
# Это полная копия блоков на момент создания. Копируйте её в надёжное место.

# Проверка размера
du -sh /var/lib/prometheus/snapshots/*

# Копирование на remote storage
rsync -avz /var/lib/prometheus/snapshots/ backup-server:/backups/prometheus/

# Очистка старых снэпшотов (оставить 3 последних)
ls -t /var/lib/prometheus/snapshots/ | tail -n +4 | xargs -I {} rm -rf /var/lib/prometheus/snapshots/{}
```

#### Бэкап через LVM snapshot

```bash
# Создание снэпшота ФС (моментальный)
lvcreate --size 10G --snapshot --name prom-snap /dev/vg0/prometheus

# Монтирование и копирование
mount /dev/vg0/prom-snap /mnt/snap
tar -czf /backup/prom-$(date +%Y%m%d).tar.gz -C /mnt/snap .

# Удаление снэпшота
umount /mnt/snap
lvremove --force /dev/vg0/prom-snap
```

> **Важно:** LVM-снэпшот создаётся моментально, но требует наличия места в VG для записи изменений (COW). Убедитесь, что у вас достаточно места.

#### Бэкап через ZFS snapshot

```bash
# Создание снэпшота
zfs snapshot tank/prometheus@backup-$(date +%Y%m%d)

# Экспорт снэпшота
zfs send tank/prometheus@backup-$(date +%Y%m%d) | gzip > /backup/prom-$(date +%Y%m%d).zfs.gz

# Удаление снэпшота
zfs destroy tank/prometheus@backup-$(date +%Y%m%d)
```

#### Восстановление из снэпшота

```bash
# 1. Остановить Prometheus
systemctl stop prometheus

# 2. Удалить текущие данные (ОСТОРОЖНО!)
rm -rf /var/lib/prometheus/blocks/*
rm -rf /var/lib/prometheus/wal/*

# 3. Распаковать бэкап
tar -xzf /backup/prom-20230916.tar.gz -C /var/lib/prometheus/

# 4. Проверить права
chown -R prometheus:prometheus /var/lib/prometheus

# 5. Запустить Prometheus
systemctl start prometheus

# 6. Верификация
curl -s http://localhost:9090/api/v1/status/tsdb | jq '.data'
```

#### Автоматизация бэкапа (cron)

```bash
# /etc/cron.d/prometheus-backup
0 */4 * * * prometheus /usr/local/bin/prometheus-backup.sh

# /usr/local/bin/prometheus-backup.sh
#!/bin/bash
set -euo pipefail

BACKUP_DIR="/backup/prometheus"
SNAP_NAME="backup-$(date +%Y%m%d-%H%M)"
RETENTION_DAYS=7

# Создание снэпшота
curl -sS -X POST http://localhost:9090/api/v1/admin/tsdb/snapshot > /dev/null

# Копирование
SNAP_DIR=$(ls -td /var/lib/prometheus/snapshots/* | head -1)
tar -czf "${BACKUP_DIR}/${SNAP_NAME}.tar.gz" -C "${SNAP_DIR}" .

# Очистка
find ${BACKUP_DIR} -name "backup-*.tar.gz" -mtime +${RETENTION_DAYS} -delete

echo "[$(date)] Backup completed: ${SNAP_NAME}"
```

## Дополнительная информация

### Ключевые принципы и ограничения

* **Отсутствие выборочного удаления:** В TSDB Prometheus нельзя удалить отдельные сэмплы. Это упрощает хранение и ускоряет выборку.
* **Эффективное удаление по сроку хранения:** Prometheus удаляет данные целыми блоками, вышедшими за `retention period`.
* **Единый срок хранения:** Настройка `retention` применяется ко всем данным в базе глобально.
* **"Вечные" серии:** Данные о метрике сохраняются в блоке до его полного удаления, даже если сбор метрики прекращен. Это причина проблемы `Churn Rate`.

### Проблемы производительности TSDB

#### Высокая кардинальность

Большое количество уникальных рядов раздувает индекс, что требует больше RAM и замедляет запросы.
1. **RAM (Memory):** Для каждого временного ряда Prometheus держит в памяти структуру индекса и последние сэмплы. При 1 млн рядов потребление RAM может составлять 8–16 ГБ.
2. **CPU:** Расчёт агрегаций по миллионам рядов требует колоссальных вычислительных мощностей.
3. **Inverted Index:** Кардинальность раздувает файл `index`. Поиск замедляется из-за сканирования огромных списков идентификаторов серий.
4. **OOM Killer:** Аварийная остановка процесса из-за нехватки памяти при тяжелых запросах.
См. [labels_and_cardinality](./labels_and_cardinality.md).

#### Churn Rate (Скорость обновления рядов)

Это скорость, с которой временные ряды появляются и исчезают.
* **Причина:** Короткоживущие объекты (поды в K8s).
* **Аналогия:** Представьте три термометра. Один работает стабильно (с него идут полные чанки по 120 сэмплов). Два других работают нестабильно — то активны, то нет. С них получаются неполные чанки, которые плохо сжимаются и занимают лишнее место в индексе.
* **Последствия:** Разбухание индекса за счет "мертвых" рядов, замедление компакции, рост нагрузки на RAM.

#### Compaction Stall (Зависание компакции)

При очень большом объёме данных (>1 млн серий) фоновый Compaction может не успевать за записью, что приводит к лагам запросов и росту WAL. Решение — снизить частоту сброса Head Block через `--storage.tsdb.max-block-duration` или увеличить CPU/Disk IO.

### Настройка параметров хранения (Prometheus v3)

| Параметр | Описание | По умолчанию |
| :--- | :--- | :--- |
| `--storage.tsdb.retention.time` | Время хранения данных | `15d` |
| `--storage.tsdb.retention.size` | Максимальный размер бады | `0` (без лимита) |
| `--storage.tsdb.out-of-order.time-window` | Окно для OOO-данных | `0s` (нужно включить) |
| `--storage.tsdb.wal-compression` | Сжатие WAL-логов | `true` |
| `--storage.tsdb.min-block-duration` | Минимальная длительность блока | `2h` |
| `--storage.tsdb.max-block-duration` | Максимальная длительность блока | `2h` |

### Рекомендации по ресурсам (Prometheus v3.x)

| Кол-во рядов | CPU | RAM | Режим работы |
| :--- | :--- | :--- | :--- |
| до 100 000 | 2 ядра | 4 ГБ | Single Instance |
| 100k — 1M | 4–8 ядер | 8–16 ГБ | Single Instance / Agent |
| 1M — 5M | 8–16 ядер | 32–64 ГБ | Оптимизированный TSDB |
| > 5M | 16+ ядер | 128 ГБ+ | Рекомендуется **[масштабирование](../scaling/overview.md)** |

### Оптимизация производительности

1. **Следите за кардинальностью:** Не используйте ID пользователей или хэши в лейблах.
2. **Используйте SSD:** TSDB крайне чувствительна к латентности диска при записи WAL.
3. **Мониторьте churn rate:** Высокий churn опаснее статической кардинальности.
4. **Нативные гистограммы (v3):** Используйте их для снижения количества рядов при работе с распределениями.
5. **Remote Write 2.0:** Включите String Interning для снижения нагрузки на сеть и CPU при отправке данных в LTS.

### Диагностика и устранение неполадок

#### Сценарий 1: Prometheus не запускается, ошибка WAL

```bash
# Проверка логов
journalctl -u prometheus -n 50 --no-pager

# Если ошибка связана с WAL, проверьте целостность сегментов
ls -la /var/lib/prometheus/wal/

# В крайнем случае: удалите WAL (потеря последних 2 часов)
systemctl stop prometheus
rm -rf /var/lib/prometheus/wal/*
systemctl start prometheus
```

#### Сценарий 2: Высокое потребление RAM

```bash
# Проверка метрики
curl -s 'http://localhost:9090/api/v1/query?query=prometheus_tsdb_head_series' | jq .

# Если > 1M рядов:
# 1. Проверьте metric_relabel_configs на предмет высококардинальных лейблов
# 2. Включите Native Histograms (если используете гистограммы)
# 3. Увеличьте limits.memory
# 4. Рассмотрите переход на Prometheus Agent + Remote Write
```

#### Сценарий 3: Медленные запросы

```bash
# Проверьте активные запросы
curl -s 'http://localhost:9090/api/v1/query_range?query=up&start=...&end=...&step=15s'

# Типичные причины:
# - Слишком широкий временной диапазон без Recording Rules
# - Regex в селекторах (.* expensive)
# - Высокая кардинальность в запросе (sum by (user_id))
```

#### Сценарий 4: Диск заполняется

```bash
# Проверка размера TSDB
du -sh /var/lib/prometheus/
df -h /var/lib/prometheus/

# Если блоки занимают много места:
# 1. Уменьшите retention.time (например, с 30d до 15d)
# 2. Включите wal-compression (если выключено)
# 3. Проверьте, нет ли "мертвых" метрик, которые продолжают собираться
```
