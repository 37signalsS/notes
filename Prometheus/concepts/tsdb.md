# Внутреннее устройство Prometheus TSDB

**TSDB (Time Series Database)** — это сердце Prometheus, его собственная база данных временных рядов. Она спроектирована для чрезвычайно эффективной записи и сжатия огромного количества метрик и их быстрого чтения при запросах.

## Основные понятия и компоненты

*   **Сэмпл (Sample):** Одна точка данных, состоящая из значения (`float64`) и временной метки (`int64`, timestamp).
*   **Временной ряд (Time Series):** Поток сэмплов, принадлежащих одной и той же метрике с идентичным набором лейблов.
*   **Чанк (Chunk):** Сжатый контейнер для сэмплов одного временного ряда. Обычно содержит до 120 сэмплов.
*   **Блок (Block):** Директория на диске, содержащая данные за определённый промежуток времени (по умолчанию — 2 часа). Внутри блока находятся чанки, индекс и метаданные.
*   **Head Block (Головной блок):** "Активный" блок, который находится в оперативной памяти (RAM) и принимает все новые входящие сэмплы.
*   **WAL (Write-Ahead Log):** Журнал упреждающей записи. Все входящие сэмплы сначала записываются в WAL на диске, и только потом обрабатываются в памяти. Это гарантирует сохранность данных при внезапном падении или перезапуске Prometheus. При старте Prometheus перечитывает WAL, чтобы восстановить Head Block.
*   **Сжатие (Compaction):** Процесс, в ходе которого несколько блоков объединяются в один более крупный блок (например, несколько 2-часовых блоков сливаются в один 8-часовой). Это оптимизирует хранение и ускоряет запросы за длительные периоды.
*   **Индекс (Index):** Файл внутри каждого блока, который содержит структуры для быстрого поиска временных рядов по их лейблам.

## Логика и архитектура хранения

Чтобы понять, почему TSDB устроен именно так, можно рассмотреть проблему хранения данных с миллионов "термометров".

*   **Проблема №1: Миллионы файлов.** Если создавать отдельный файл для каждого источника (термометра), это приведет к миллионам файлов и огромному количеству мелких операций записи (I/O), что неэффективно для дисковой системы.
*   **Проблема №2: Один большой файл.** Если писать все данные в один общий файл, он быстро станет гигантским. Чтение данных для одного графика потребует сканирования всего файла, что крайне медленно.

**Решение Prometheus TSDB:**

1.  **Активные данные в RAM:** Чтобы ускорить запись, все новые данные сначала попадают в **Head Block** в оперативной памяти. RAM выдерживает огромное количество операций записи и обеспечивает мгновенный доступ.
2.  **Защита через WAL:** Поскольку RAM энергозависима, все входящие сэмплы немедленно дублируются в **Write-Ahead Log (WAL)** на диске. В случае сбоя Prometheus восстановит Head Block из WAL.
3.  **Сброс на диск блоками:** Периодически (раз в 2 часа) Head Block "закрывается" и как единое целое записывается на диск в виде **блока**. Это превращает множество мелких операций записи в одну крупную, что гораздо эффективнее для диска.
4.  **Индексация лейблов:** Хранить полный набор лейблов для каждого сэмпла было бы расточительно. Поэтому TSDB присваивает каждой уникальной комбинации лейблов (каждому временному ряду) числовой ID. В чанках и блоках хранятся только эти ID, а маппинг `ID -> набор лейблов` хранится в **индексе** блока. Это значительно экономит место.
5.  **Сжатие (Compaction):** Со временем множество мелких (2-часовых) блоков объединяются в более крупные (например, 8-часовые, суточные). Это уменьшает количество файлов на диске и ускоряет запросы за длительные периоды времени.

### Модульная архитектура хранения и внешние бэкенды

Внутренняя TSDB Prometheus эффективна для относительно небольших объемов данных. При этом Prometheus спроектирован с модульной архитектурой, позволяющей интегрироваться с внешними системами хранения для решения задач масштабирования и долгосрочного хранения.

*   **Интерфейс адаптера:** Prometheus записывает и считывает данные не напрямую, а через унифицированный интерфейс адаптера. Это означает, что для Prometheus неважно, куда именно записываются метрики; ему нужен лишь адаптер, реализующий необходимые функции для работы с данными.
*   **Гибкость:** Такой подход позволяет подключать различные сторонние Time Series Database в качестве бэкендов для хранения данных, которые могут предложить лучшую масштабируемость, долгосрочное хранение или кластеризацию.
*   **Примеры внешних TSDB бэкендов:**
    *   **VictoriaMetrics:** Высокопроизводительное, горизонтально масштабируемое и более универсальное решение, популярное для Prometheus.
    *   **Thanos:** Решение для обеспечения глобального обзора, высокой доступности и долгосрочного хранения метрик Prometheus, тесно ориентированное на работу в Kubernetes.
    *   **Mimir:** Еще одно горизонтально масштабируемое решение от Grafana Labs.
    *   **Другие:** Существуют адаптеры для таких систем, как ClickHouse, Elasticsearch, Graphite, InfluxDB, Kafka, что позволяет использовать их для хранения данных Prometheus в зависимости от конкретных требований.

## Жизненный цикл сэмпла

1.  Prometheus опрашивает таргет и получает новые сэмплы.
2.  Сэмплы немедленно записываются в файлы **WAL** на диске для обеспечения долговечности.
3.  Одновременно сэмплы помещаются в **Head Block** в оперативной памяти. Внутри него они группируются в чанки.
4.  Каждые 2 часа (по умолчанию) Head Block "закрывается" и записывается на диск как новый постоянный **Блок**. На его месте в памяти создается новый пустой Head Block.
5.  В фоновом режиме запускается процесс **Compaction**, который объединяет старые, более мелкие блоки в более крупные, уменьшая количество файлов и оптимизируя индекс.

## Ключевые принципы и ограничения

Архитектура TSDB основана на нескольких компромиссах, направленных на максимальную производительность записи и чтения диапазонов данных.

*   **Отсутствие выборочного удаления:** В TSDB Prometheus намеренно отсутствует возможность удаления отдельных строк (сэмплов). Это позволяет использовать более простые и быстрые механизмы хранения с линейным распределением данных, что существенно ускоряет выборку данных за определенный период времени.
*   **Эффективное удаление по сроку хранения:** Удаление устаревших данных не является ресурсоемкой операцией, поскольку Prometheus просто удаляет целые блоки данных, вышедшие за пределы установленного срока хранения (`retention period`).
*   **Единый срок хранения:** Нельзя задавать разные периоды хранения для разных метрик. Глобальная настройка `retention` применяется ко всем данным в TSDB.
*   **"Вечные" серии:** Если вы перестали собирать метрику или вывели из эксплуатации хост, связанные с ними данные (временные ряды и их место в индексе) нельзя выборочно удалить из базы. Они будут удалены только тогда, когда истечет срок хранения всего блока, содержащего последний сэмпл этой метрики. Это напрямую связано с проблемой `Churn Rate`.

## Проблемы производительности TSDB

### Высокая кардинальность

Как уже было описано в [[./labels_and_cardinality.md]], большое количество уникальных временных рядов (высокая кардинальность) приводит к разрастанию индекса, что требует больше RAM и замедляет запросы.

### Churn Rate (Скорость обновления рядов)

**Churn Rate** — это скорость, с которой временные ряды появляются и исчезают. В отличие от статической кардинальности (общее число рядов), churn характеризует именно **динамику изменения** состава рядов.

*   **Причина:** Частое создание и удаление объектов, генерирующих метрики. Классический пример — контейнеры или поды в Kubernetes, которые могут создаваться для выполнения коротких задач и быстро удаляться. Каждый новый под с уникальными лейблами создает новые временные ряды.
    *   **Аналогия:** Представьте три термометра. Один работает стабильно, и Prometheus собирает с него полные чанки по 120 сэмплов. Два других "глючат" — то работают, то нет. С них получаются "обрезанные" чанки с малым количеством сэмплов.
*   **Последствия:**
    1.  **Неэффективное сжатие:** Появляются "обрезанные" чанки (как от "глючных" термометров). Они содержат мало сэмплов, но занимают место на диске и хуже сжимаются.
    2.  **Разбухание индекса и метаданных:** TSDB вынуждена хранить в индексе информацию даже о тех временных рядах, которые уже неактивны ("мертвы"). Индекс пухнет, что увеличивает потребление памяти.
    3.  **Замедление Compaction:** Процесс сжатия начинает работать медленнее, так как ему приходится обрабатывать большое количество мелких и неэффективных чанков.
    4.  **Рост потребления RAM и нагрузки на WAL.**

Высокий churn rate может быть даже более опасен, чем высокая статическая кардинальность.

*   **Как отслеживать:**
    *   `prometheus_tsdb_head_series`: Текущее количество активных временных рядов.
    *   `rate(prometheus_tsdb_head_series_created_total[5m])`: Скорость создания новых рядов.
    *   `rate(prometheus_tsdb_head_series_removed_total[5m])`: Скорость удаления старых рядов.

    Если скорости создания и удаления рядов высокие и постоянно "прыгают", это явный признак высокого churn rate.
