# Типы метрик в Prometheus: Обзор

## Определения

**Типы метрик** в [Prometheus](../../overview.md) — это классификация временных рядов по их семантике, определяющая логику изменения значений во времени. Prometheus использует эти типы для корректной обработки данных: учета сбросов счетчиков при рестартах, интерполяции гистограмм и нативного отображения метаданных.

Правильный выбор типа метрики является фундаментом для построения достоверных запросов на языке [PromQL](../promql/functions.md), настройки точного [алертинга](../../rules.md) и обеспечения масштабируемости хранилища [TSDB](../tsdb.md).

## Основные концепции

### Классификация типов данных

В актуальной версии Prometheus (v3.x) выделяются пять фундаментальных типов метрик. Каждый тип оптимизирован под конкретные задачи мониторинга.

| Тип метрики | Описание | Основное применение | SSoT файл |
|:---|:---|:---|:---|
| **Counter** | Кумулятивный счетчик: только растет или сбрасывается в 0. | Подсчет событий (запросы, ошибки, трафик). | [Counter](./counter.md) |
| **Gauge** | Измеритель: значение произвольно меняется в обе стороны. | Мгновенные состояния (RAM, CPU, температура). | [Gauge](./gauge.md) |
| **Histogram** | Группировка значений в статические диапазоны (buckets). | Анализ распределений, SLA и перцентилей. | [Histogram](./histogram.md) |
| **Native Histogram** | Высокоточная гистограмма с динамической сеткой (v3.0+). | Современный стандарт для Latency и распределений. | [Histogram](./histogram.md) |
| **Summary** | Расчет квантилей на стороне приложения (клиента). | Точные квантили для одиночных инстансов. | [Summary](./summary.md) |

### Критерии выбора типа метрики

1.  **Счетчик (Counter) против Измерителя (Gauge):**
    *   Если значение может уменьшаться в процессе нормальной работы (например, количество активных соединений), используйте **Gauge**.
    *   Если значение уменьшается только при перезагрузке процесса (сброс в 0), используйте **Counter**.
2.  **Гистограмма (Histogram) против Сводки (Summary):**
    *   **Histogram:** Позволяет агрегировать данные по нескольким инстансам (сервисам, кластерам). Требует PromQL для вычисления перцентилей.
    *   **Summary:** Не подлежит агрегации. Дает высокую точность для отдельного процесса, но "фиксирует" квантили в коде приложения.
3.  **Native Histograms (Нативные гистограммы):**
    *   Рекомендуется для всех новых проектов в экосистеме Prometheus v3.x. Они решают проблему ручного подбора корзин (`le` label) и значительно снижают нагрузку на хранилище за счет сжатия данных в одном временном ряду.

### Совместимость с OpenTelemetry и OTLP

Prometheus v3.0+ нативно поддерживает протокол OTLP, что позволяет принимать метрики напрямую от OpenTelemetry SDK. Маппинг типов данных осуществляется по следующей схеме:

| Prometheus Type | OpenTelemetry Signal | Агрегация (Temporality) |
|:---|:---|:---|
| **Counter** | Sum (Monotonic) | Cumulative |
| **Gauge** | Gauge / Sum (Non-Monotonic) | Cumulative / Delta |
| **Histogram** | Histogram (Explicit Buckets) | Cumulative |
| **Native Histogram** | Exponential Histogram | Cumulative |
| **Summary** | Summary (Legacy) | Cumulative |

Благодаря поддержке **UTF-8** в именах метрик и меток (v3.x), Prometheus сохраняет исходную структуру OTel (например, `http.server.request.duration`), устраняя необходимость в трансформации имен.

## Практические сценарии

### Сценарий 1: Инструментация типичных операций

| Бизнес-кейс | Тип метрики | Имя (Naming) |
|:---|:---|:---|
| Количество выполненных заданий | **Counter** | `jobs_completed_total` |
| Потребление памяти процессом | **Gauge** | `process_resident_memory_bytes` |
| Время выполнения SQL-запроса | **Native Histogram** | `db_query_duration_seconds` |
| Версия и билд приложения | **Gauge (Info)** | `app_info` (значение 1) |

### Сценарий 2: Правильная агрегация в PromQL

Ошибки в порядке функций приводят к неверным результатам из-за игнорирования сбросов счетчиков.

*   **Counter (Правильно):** `sum by (job) (rate(requests_total[5m]))` — сначала вычисляем скорость с учетом рестартов, затем суммируем.
*   **Gauge (Правильно):** `avg by (instance) (node_load1)` — прямое усреднение текущих значений.
*   **Histogram (Правильно):** `histogram_quantile(0.95, sum by (le) (rate(latency_bucket[5m])))` — агрегация корзин перед расчетом квантиля.

### Сценарий 3: Переход на метаданные и единицы измерения (v3.x)

С внедрением **Remote Write 2.0** и обновленного Metadata API, Prometheus передает информацию о типах и единицах измерения во внешние системы.
*   **Действие:** При объявлении метрики в коде (например, на Go или Python) всегда указывайте `Unit` (например, `seconds`).
*   **Результат:** Grafana и другие визуализаторы смогут автоматически подставлять `s`, `ms`, `GiB` на оси графиков, основываясь на метаданных из Prometheus.

## Дополнительная информация

### Соглашения по именованию

1.  **Суффикс `_total`:** Обязателен для всех счетчиков (`Counter`).
2.  **Базовые единицы:** Используйте `seconds`, `bytes`, `meters`, `celsius`. Избегайте производных единиц (`ms`, `kb`) в именах метрик.
3.  **Лейблы:** Используйте лейблы для размерностей с низкой кардинальностью (env, method, status_code). Не помещайте уникальные ID (user_id) в лейблы.

### Маппинг функций PromQL

| Тип метрики | Рекомендуемые функции | Запрещенные функции |
|:---|:---|:---|
| **Counter** | `rate()`, `increase()`, `resets()` | `delta()`, `deriv()`, `predict_linear()` |
| **Gauge** | `delta()`, `deriv()`, `predict_linear()` | `rate()`, `increase()` |
| **Histogram** | `histogram_quantile()`, `histogram_fraction()` | `rate()` напрямую (только для `_bucket`) |
