# Тип метрики Summary (Сводка)

## Определения

**Summary** — это тип метрики в [Prometheus](../../overview.md), предназначенный для измерения распределения наблюдаемых событий (например, длительности выполнения запросов или размеров ответов). 

В отличие от [Гистограмм](./histogram.md), которые собирают данные в настраиваемые корзины на стороне сервера, Summary вычисляет квантили (перцентили) на стороне **клиента** (внутри приложения или экспортёра) и отдаёт их в готовом виде. Это обеспечивает высокую точность распределения для конкретного процесса, но ограничивает возможности агрегации данных по кластеру.

Summary создаёт три типа временных рядов:

| Ряд | Описание |
|:---|:---|
| `{quantile="<φ>"}` | Значение φ-квантили (например, `quantile="0.95"` для p95). |
| `_sum` | Кумулятивный счётчик ([Counter](./counter.md)) суммы всех наблюдаемых значений. |
| `_count` | Кумулятивный счётчик ([Counter](./counter.md)) общего количества наблюдений. |

Квантили и допустимая погрешность задаются статически при инициализации метрики в коде приложения.

## Основные концепции

### Поведение Summary

| Свойство | Описание |
|:---|:---|
| **Направление** | `_sum` и `_count` только растут (кумулятивны); `{quantile}` принимает произвольные значения. |
| **Сброс (Reset)** | `_sum` и `_count` сбрасываются при рестарте; квантили рассчитываются заново на основе новых данных. |
| **Вычисление** | Происходит в памяти приложения с использованием алгоритмов потокового квантилевания. |
| **Агрегация** | Квантили **нельзя** математически корректно агрегировать между инстансами. |
| **Точность** | Обеспечивает высокую точность для конкретных, заранее определенных уровней квантилей. |

### Алгоритм квантилевания (CKMS)

Большинство клиентских библиотек Prometheus используют алгоритм **CKMS** (Cormode-Korn-Muthukrishnan-Srivastava) для вычисления квантилей в потоке данных без необходимости хранения всех значений. 
*   **Принцип:** Алгоритм поддерживает сжатое представление распределения, гарантируя, что возвращаемое значение квантиля находится в пределах заданной погрешности `ε`.
*   **Objectives:** При настройке Summary указываются целевые квантили и их `ε`. Например, квантиль `0.99` с погрешностью `0.001` гарантирует, что результат будет находиться между 98.9-м и 99.1-м перцентилями реального распределения.

### Скользящее окно (Sliding Window)

Summary вычисляет квантили не за всё время жизни приложения, а за **скользящее окно** (обычно 5–10 минут). 
*   **Сегментация:** Окно разбивается на несколько временных сегментов (например, 5 сегментов по 1 минуте).
*   **Ротация:** По истечении минуты самый старый сегмент сбрасывается, и его данные перестают влиять на расчет. Это позволяет метрике отражать актуальное состояние системы («здесь и сейчас»), а не усреднять данные за сутки.

### Метаданные и Prometheus v3.x

Начиная с версии 3.0, Prometheus значительно улучшил работу с типами данных через протокол **[Remote Write 2.0](../../scaling/remote_read_write.md)**:
*   **Передача типов:** Информация о том, что серия является частью Summary, теперь передается нативно во внешние хранилища (Mimir, VictoriaMetrics). Это позволяет инструментам визуализации автоматически идентифицировать квантили.
*   **Единицы измерения:** Поддержка метаданных позволяет явно указывать единицы (например, `seconds`), что упрощает автоматическое масштабирование осей на дашбордах.

## Сравнение с распределениями

В современной экосистеме (2025–2026) выбор между Summary, классической Histogram и Native Histogram критичен для производительности.

| Критерий | Summary | Classic Histogram | Native Histogram (v3.0) |
|:---|:---|:---|:---|
| **Место вычисления** | Приложение (Клиент) | Сервер (PromQL) | Сервер (PromQL) |
| **Агрегируемость** | Нет (только по инстансу) | Да (полная) | Да (высокоточная) |
| **Точность** | Задана в коде | Зависит от корзин | Экспоненциальная сетка |
| **Нагрузка на TSDB** | Низкая (4–6 рядов) | Высокая (ряд на корзину) | Низкая (1 ряд) |
| **Гибкость** | Статическая | Статическая (le лейблы) | Динамическая |

**Рекомендация:** Используйте **Summary**, когда вам нужны «идеально точные» перцентили для одного процесса и вы не планируете их суммировать (например, мониторинг специфических внутренних очередей или физических параметров). В остальных случаях (Latency API по кластеру) переходите на **Native Histograms**.

## Практические сценарии

### Сценарий 1: Прямой доступ к квантилю (Одиночный инстанс)

Используется для мониторинга критических задержек в монолитных приложениях или специфических компонентах инфраструктуры.

```promql
# 99-й перцентиль времени обработки gRPC-запросов (p99)
grpc_server_handling_seconds{quantile="0.99", grpc_method="GetUser"}
```

### Сценарий 2: Расчёт среднего времени ответа (Average)

Составляющие `_sum` и `_count` являются счётчиками. Для них действует **строгое правило агрегации**: сначала вычисляется скорость (`rate`), затем производится суммирование (`sum`).

```promql
# Среднее = Сумма скоростей изменений / Сумма скоростей событий
sum(rate(http_request_duration_seconds_sum[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```
*Нарушение этого порядка (sum перед rate) приведет к искажению данных при рестартах приложений.*

### Сценарий 3: Поиск худшего инстанса (Max p99)

Хотя усреднять квантили нельзя, можно найти максимальное значение среди всех реплик, чтобы выявить проблемный узел.

```promql
# Максимальный p95 среди всех реплик (худший случай в кластере)
max(grpc_server_handling_seconds{quantile="0.95"}) by (job)
```

## Дополнительная информация

### Конфигурация в коде (Go)

Пример настройки Summary с использованием библиотеки `client_golang`.

```go
var requestDuration = prometheus.NewSummary(prometheus.SummaryOpts{
    Name: "http_request_duration_seconds",
    Help: "Распределение длительности HTTP-запросов.",
    // Objectives: ключ - квантиль, значение - допустимая ошибка (ε).
    Objectives: map[float64]float64{
        0.5:  0.05,  // Медиана с точностью 5%
        0.9:  0.01,  // p90 с точностью 1%
        0.99: 0.001, // p99 с точностью 0.1%
    },
    // MaxAge: сколько времени данные хранятся в скользящем окне
    MaxAge: 10 * time.Minute,
    // AgeBuckets: количество сегментов внутри MaxAge
    AgeBuckets: 5,
})
```

### Типовые ошибки

*   **Агрегация через `avg()` или `sum()`**: Приводит к математически некорректным результатам, так как квантили не аддитивны.
*   **Игнорирование нагрузки на RAM**: Summary хранит структуры данных (стейты CKMS) в памяти процесса. При высокой кардинальности меток (labels) это может привести к OOM-killer.
*   **Отсутствие `rate()` для `_sum` и `_count`**: Деление «сырых» значений показывает среднее за всё время работы процесса, а не за актуальный интервал, и ломается при рестартах.

### Соответствие OpenTelemetry

В OpenTelemetry сигнал `Summary` рассматривается как legacy-тип, используемый в основном для совместимости с Prometheus. Современные OTel SDK предпочитают `Histogram` (Exponential), которые маппятся в Native Histograms. Если вы проектируете новую систему на базе OTel, избегайте использования типа Summary.
