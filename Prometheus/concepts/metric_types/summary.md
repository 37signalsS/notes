# Summary (Сводка)

## Определения

**Summary** — тип метрики в [Prometheus](../../overview.md) для измерения распределения наблюдаемых событий. В отличие от [Histogram](./histogram.md), Summary вычисляет квантили (перцентили) на стороне клиента — в экспортёре или клиентской библиотеке — и отдаёт их в готовом виде.

Summary создаёт три вида временных рядов:

| Ряд | Описание |
|-----|----------|
| `{quantile="<φ>"}` | Значение φ-квантили (например, `quantile="0.95"` для p95) |
| `_sum` | Общая сумма всех наблюдаемых значений |
| `_count` | Общее количество наблюдений |

Квантили задаются при создании метрики в коде приложения и фиксируются — добавить новый квантиль без передеплоя нельзя.

## Основные концепции

### Поведение Summary

| Свойство | Описание |
|----------|----------|
| **Направление** | `_sum` и `_count` только растут (как Counter); `{quantile}` — произвольные значения |
| **Сброс** | `_sum` и `_count` сбрасываются при рестарте, обрабатываются через `rate()` |
| **Квантили** | Не сбрасываются — это моментальные снимки распределения |
| **Агрегация** | `_sum` и `_count` — можно; `{quantile}` — нельзя |

### Почему квантили Summary нельзя агрегировать

Квантиль — это позиция в упорядоченном наборе данных. Усреднение позиций из разных наборов не даёт позицию объединённого набора:

```text
Реплика A: [9, 9, 9, 9, 9]       → p95 = 9
Реплика B: [1, 1, ..., 1] (×100) → p95 = 1

avg(p95) = (9 + 1) / 2 = 5  — МАТЕМАТИЧЕСКИ БЕССМЫСЛЕННО
```

Честный p95 объединённого набора (105 значений) ≈ 1, так как 100 из 105 значений равны 1.

**Решение:** Для агрегации используйте `max()` (покажет худший сценарий) или работайте только с `_sum` и `_count`. Подробный разбор представлен в разделе [Агрегация Summary](./percentiles.md#сценарий-3-почему-summary-нельзя-агрегировать).

### Скользящее окно (Sliding window)

Клиентские библиотеки Prometheus вычисляют квантили за ограниченный период (обычно 5–10 минут). Это называется скользящим окном (sliding window). Старые наблюдения постепенно удаляются из расчёта. Параметры окна (размер, количество сэмплов) задаются при создании Summary и зависят от конкретной библиотеки.

### Сравнение с Histogram

| Критерий | Summary | Histogram |
|----------|---------|-----------|
| **Где вычисляются квантили** | Клиент (экспортёр) | Сервер (Prometheus, `histogram_quantile()`) |
| **Агрегация квантилей** | Нельзя | Можно (`sum by (le)`) |
| **Точность квантилей** | Точная (для одного инстанса) | Приблизительная (зависит от настроек корзин) |
| **Гибкость** | Фиксированные квантили | Любые квантили через PromQL |
| **Нагрузка** | Выше на клиент | Выше на сервер (TSDB) |
| **Основной сценарий** | Один процесс, точные квантили | Распределённая система, агрегация по репликам |

**Рекомендация:** Для микросервисов и распределённых систем используйте **Histogram**. Для мониторинга одиночного процесса, где критична точность квантилей — **Summary**.

## Практические сценарии

### Сценарий 1: Прямой доступ к квантили

```promql
# 99-й перцентиль времени обработки gRPC-запросов (уже вычислен на клиенте)
grpc_server_handling_seconds{quantile="0.99", grpc_method="GetUser"}

# Медиана (50-й перцентиль)
grpc_server_handling_seconds{quantile="0.5", grpc_method="GetUser"}
```

**Важно:** Данные значения являются моментальными снимками. Их нельзя агрегировать через `avg()` или `sum()` по инстансам.

### Сценарий 2: Среднее время ответа (корректная агрегация)

```promql
# Среднее = сумма / количество (обе метрики агрегируются безопасно)
sum(rate(grpc_server_handling_seconds_sum[5m]))
/
sum(rate(grpc_server_handling_seconds_count[5m]))
```

### Сценарий 3: Отображение нескольких инстансов на одном графике

```promql
# Максимальный p95 среди всех реплик (худший сценарий)
max(grpc_server_handling_seconds{quantile="0.99"}) without (instance)
```

**Примечание:** Данный подход может давать ложноположительные оповещения, если задержка наблюдается только на одной реплике из многих.

### Сценарий 4: Формат экспозиции Summary

Пример ответа эндпоинта `/metrics`:

```text
# HELP grpc_server_handling_seconds RPC handling latency
# TYPE grpc_server_handling_seconds summary
grpc_server_handling_seconds{quantile="0.5",grpc_method="GetUser"} 0.012
grpc_server_handling_seconds{quantile="0.9",grpc_method="GetUser"} 0.045
grpc_server_handling_seconds{quantile="0.99",grpc_method="GetUser"} 0.128
grpc_server_handling_seconds_sum{grpc_method="GetUser"} 75.3
grpc_server_handling_seconds_count{grpc_method="GetUser"} 1250
```

Подробности в документе [Формат экспозиции](./exposition_format.md).

## Дополнительная информация

### Типовые ошибки

| Ошибка | Почему это неверно | Как правильно |
|--------|-------------------|---------------|
| `avg(metric{quantile="0.95"})` | Квантили нельзя усреднять | `max(metric{quantile="0.95"})` |
| `sum(metric{quantile="0.95"})` | Сумма квантилей не имеет физического смысла | Агрегируйте `_sum` и `_count` |
| Использование Summary для микросервисов | Невозможно корректно агрегировать данные по репликам | Используйте Histogram |
| Мониторинг квантили без учёта скользящего окна | Неизвестен временной интервал расчёта | Изучите документацию используемой библиотеки |

### Когда Summary предпочтительнее Histogram

* **Одиночный процесс** — отсутствует необходимость агрегировать данные по нескольким инстансам.
* **Требуются точные квантили** — аппроксимация, используемая в Histogram, недопустима для задачи.
* **Заранее известны границы распределения** — можно зафиксировать необходимые квантили (0.5, 0.9, 0.95, 0.99).
* **Оптимизация TSDB** — Summary создаёт меньше временных рядов по сравнению с Histogram с большим количеством корзин.

### Конфигурация квантилей в клиентских библиотеках

Пример настройки на языке Go (библиотека `prometheus/client_golang`):

```go
summary := prometheus.NewSummary(prometheus.SummaryOpts{
    Name: "http_request_duration_seconds",
    Help: "HTTP request latency",
    Objectives: map[float64]float64{
        0.5:  0.05,   // p50 с допустимой ошибкой ±5%
        0.9:  0.01,   // p90 с допустимой ошибкой ±1%
        0.99: 0.001,  // p99 с допустимой ошибкой ±0.1%
    },
})
```

Параметр `Objectives` определяет целевые квантили и их точность. Повышение точности увеличивает потребление ресурсов на стороне приложения.
