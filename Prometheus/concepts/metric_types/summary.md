# Summary (Сводка)

## Определения

**Summary** — это тип метрики в [Prometheus](../../overview.md), предназначенный для измерения распределения наблюдаемых событий (например, длительности выполнения запросов или размеров ответов). 

В отличие от [Histogram](./histogram.md), которая собирает данные в настраиваемые корзины на стороне сервера, Summary вычисляет квантили (перцентили) на стороне **клиента** (внутри приложения или экспортёра) и отдаёт их в готовом виде. Это позволяет получить высокую точность распределения для отдельного инстанса, но накладывает ограничения на агрегацию данных по кластеру.

Summary создаёт три типа временных рядов:

| Ряд | Описание |
|:---|:---|
| `{quantile="<φ>"}` | Значение φ-квантили (например, `quantile="0.95"` для p95). |
| `_sum` | Кумулятивный счётчик ([Counter](./counter.md)) суммы всех наблюдаемых значений. |
| `_count` | Кумулятивный счётчик ([Counter](./counter.md)) общего количества наблюдений. |

Квантили задаются статически при инициализации метрики в коде приложения.

## Основные концепции

### Поведение Summary

| Свойство | Описание |
|:---|:---|
| **Направление** | `_sum` и `_count` только растут; `{quantile}` — произвольные значения. |
| **Сброс (Reset)** | `_sum` и `_count` сбрасываются при рестарте; квантили рассчитываются заново за текущее окно. |
| **Вычисление** | На стороне клиента с использованием алгоритмов потокового квантилевания (например, CKMS). |
| **Агрегация** | Квантили **нельзя** математически корректно агрегировать между инстансами. |
| **Точность** | Высокая точность для конкретных, заранее заданных квантилей. |

### Почему квантили Summary нельзя агрегировать

Квантиль — это значение, ниже которого падает определённая доля выборки. Усреднение или суммирование таких значений из разных наборов данных (реплик) даёт математически ложный результат, так как веса выборок не учитываются.

**Наглядный пример:**
*   **Реплика A:** [9, 9, 9, 9, 9] → p95 = 9.
*   **Реплика B:** [1, 1, ..., 1] (100 значений) → p95 = 1.
*   **Ошибочный расчёт:** `avg(p95) = (9 + 1) / 2 = 5`.
*   **Реальный p95:** В объединённом наборе из 105 значений 100 значений равны 1. Реальный p95 будет равен 1.

**Следствие:** Если вам нужна агрегация перцентилей по кластеру (например, «p99 по всем API-серверам»), используйте **Histogram**. Для Summary используйте `max()` только чтобы выявить худший инстанс.

### Скользящее окно (Sliding Window)

Поскольку Summary вычисляется в памяти приложения, он не может хранить все данные за всё время. Клиентские библиотеки используют скользящее окно (обычно 5–10 минут), разделенное на несколько временных сегментов. По мере движения времени старые сегменты очищаются, и расчёт квантилей всегда отражает «свежее» распределение.

### Сравнение с Histogram

| Критерий | Summary | Histogram |
|:---|:---|:---|
| **Место вычисления** | Клиент (экспортёр) | Сервер (Prometheus) |
| **Агрегируемость** | Нет (только `_sum` и `_count`) | Да (через `sum by (le)`) |
| **Точность** | Высокая (настраиваемая) | Зависит от границ корзин (buckets) |
| **Гибкость** | Фиксированные квантили в коде | Любые квантили в PromQL |
| **Нагрузка** | Выше на приложение (CPU/RAM) | Выше на TSDB (хранение корзин) |

## Практические сценарии

### Сценарий 1: Прямой доступ к квантилю (Одиночный инстанс)

Если у вас запущен один экземпляр приложения и вам нужны точные перцентили латентности без настройки корзин.

```promql
# 99-й перцентиль времени обработки gRPC-запросов
grpc_server_handling_seconds{quantile="0.99", grpc_method="GetUser"}
```

### Сценарий 2: Расчёт среднего времени ответа (Average)

Составляющие `_sum` и `_count` являются счётчиками. Для них действует **строгое правило агрегации**: сначала вычисляется скорость (`rate`), затем производится суммирование (`sum`).

```promql
# КОРРЕКТНО: Среднее = Сумма скоростей изменений / Сумма скоростей событий
sum(rate(http_request_duration_seconds_sum[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```
*Нарушение этого порядка (sum перед rate) приведет к неверным данным при рестартах инстансов.*

### Сценарий 3: Поиск худшего инстанса (Max p99)

Хотя усреднять квантили нельзя, можно найти максимальное значение среди всех реплик, чтобы выявить проблему.

```promql
# Максимальный p95 среди всех реплик (худший сценарий)
max(grpc_server_handling_seconds{quantile="0.95"}) by (job)
```

### Сценарий 4: Формат экспозиции (Exposition Format)

Пример выдачи метрики Summary в формате plain text:

```text
# HELP http_request_duration_seconds Latency of HTTP requests.
# TYPE http_request_duration_seconds summary
http_request_duration_seconds{quantile="0.5"} 0.052
http_request_duration_seconds{quantile="0.9"} 0.145
http_request_duration_seconds{quantile="0.99"} 0.521
http_request_duration_seconds_sum 124.5
http_request_duration_seconds_count 2500
```

## Дополнительная информация

### Конфигурация в коде (Go)

Пример настройки Summary с использованием официальной библиотеки `prometheus/client_golang`. Параметр `Objectives` определяет список квантилей и допустимую погрешность (error margin).

```go
var requestDuration = prometheus.NewSummary(prometheus.SummaryOpts{
    Name: "http_request_duration_seconds",
    Help: "Распределение длительности HTTP-запросов.",
    // Ключ - квантиль, значение - допустимая ошибка.
    // Например, 0.5 (медиана) с ошибкой 0.05 означает точность от 0.45 до 0.55.
    Objectives: map[float64]float64{
        0.5:  0.05,
        0.9:  0.01,
        0.99: 0.001,
    },
    // Максимальный возраст данных в скользящем окне
    MaxAge: 10 * time.Minute,
})
```

### Типовые ошибки

*   **Агрегация через `avg()` или `sum()`**: Как было показано выше, это приводит к математически бессмысленным значениям.
*   **Игнорирование нагрузки на RAM**: Поскольку Summary хранит данные для расчёта квантилей в памяти приложения, использование большого количества уникальных лейблов (High Cardinality) может привести к значительному потреблению оперативной памяти.
*   **Отсутствие `rate()` для `_sum` и `_count`**: Попытка разделить сырые значения `_sum / _count` не учитывает рестарты и показывает среднее за «всё время жизни», а не за актуальный период.

### Когда использовать Summary вместо Histogram

1.  **Высокая точность**: Если аппроксимация Histogram в конкретных точках недопустима.
2.  **Экономия в TSDB**: Если у вас сотни инстансов и вам нужны только p50 и p99, Summary создаст 4 ряда (p50, p99, sum, count), в то время как Histogram с 20 корзинами создаст 22 ряда на каждый инстанс.
3.  **Непредсказуемые границы**: Если вы не знаете заранее диапазон значений (латентность может быть от 1мс до 100с), настроить корзины Histogram сложно, а Summary адаптируется автоматически.
