# Перцентили и квантили: теория и практика

## Определения

**Перцентиль (percentile)** — это статистическая величина, показывающая значение, ниже которого лежит определённый процент наблюдений в наборе данных. 

**Квантиль (quantile)** — обобщение перцентиля, где уровень указывается в долях от 0 до 1. 
*   **0.95-квантиль** соответствует **95-му перцентилю (p95)**.
*   **0.5-квантиль** — это **медиана (p50)**.

В мониторинге перцентили незаменимы для анализа **Latency** (задержек), так как они позволяют отсечь аномальные выбросы и увидеть реальный опыт большинства пользователей. Среднее арифметическое в таких задачах часто бесполезно, так как один запрос со временем выполнения 60 секунд «испортит» статистику для тысячи запросов по 10 мс.

## Основные концепции

### Сравнение статистических мер

| Метрика | Что показывает | Устойчивость к выбросам | Применение |
|:---|:---|:---|:---|
| **Среднее (Mean)** | Сумма / Количество | Очень низкая | Общий объем ресурсов (например, трафик). |
| **Медиана (p50)** | Типичный случай | Высокая | Понимание нормальной работы системы. |
| **p95 / p99** | Хвосты распределения | Высокая | Контроль **SLA/SLO** и «плохого» опыта. |
| **Максимум** | Худший случай | Нулевая | Поиск критических багов, таймаутов, утечек. |

### Расчет в Prometheus: Гистограммы и интерполяция

При использовании классических гистограмм (`Histogram`) Prometheus не знает точных значений внутри корзин. Он знает только, сколько событий попало в диапазон $\le le$. Для вычисления квантиля используется **линейная интерполяция**:

1.  Находится корзина, в которую попадает искомый квантиль.
2.  Предполагается, что значения внутри этой корзины распределены **равномерно**.
3.  Вычисляется точка внутри диапазона корзины.

**Проблема точности:** Если корзины слишком широкие (например, `[100мс, 1000мс]`), а ваши реальные задержки группируются около 110мс, `histogram_quantile` может вернуть 500мс просто из-за математики интерполяции.

### Нативные гистограммы и точность (v3.0+)

В Prometheus v3.0 внедрены **Native Histograms**, которые решают проблему точности классических гистограмм:
*   **Экспоненциальная сетка:** Вместо ручного подбора границ используются сотни или тысячи динамических бакетов с фиксированной относительной погрешностью (например, 1%).
*   **Исключение интерполяции:** Благодаря высокой плотности бакетов ошибка интерполяции становится пренебрежимо малой, что дает «истинные» перцентили без настройки.

### Критическое правило агрегации

Для вычисления квантилей на основе гистограмм (которые являются набором Counter-метрик) необходимо строго соблюдать порядок операций: **сначала вычисляется скорость (`rate`), затем производится агрегация (`sum`)**.

*   **ПРАВИЛЬНО:** `histogram_quantile(0.95, sum by (le) (rate(http_duration_bucket[5m])))`
*   **ОШИБОЧНО:** `histogram_quantile(0.95, rate(sum by (le) (http_duration_bucket)[5m]))`

*Почему это важно:* Суммирование «сырых» счётчиков до вычисления скорости игнорирует рестарты инстансов. Если один из десяти подов перезагрузится, его счётчик сбросится в 0, и `rate(sum(...))` воспримет это как аномальное падение, что полностью исказит результат.

## Инструментарий PromQL

В PromQL существуют три способа работы с квантилями, которые часто путают.

### histogram_quantile() vs quantile()

1.  **`histogram_quantile(phi, buckets)` (Функция):**
    *   **Назначение:** Вычисляет квантиль на основе распределения данных по корзинам гистограммы.
    *   **Вход:** Инстанс-вектор корзин (`le` лейблы или Native Histograms).
    *   **Применение:** Анализ Latency, размеров ответов.

2.  **`quantile(phi, vector)` (Оператор агрегации):**
    *   **Назначение:** Вычисляет квантиль среди *текущих значений* нескольких временных рядов.
    *   **Пример:** `quantile(0.95, node_load1)` вернет значение нагрузки, которое выше, чем у 95% серверов в данный момент.
    *   **Применение:** Анализ равномерности распределения нагрузки по кластеру.

### quantile_over_time()

*   **Назначение:** Вычисляет квантиль значений *одного* временного ряда за интервал времени.
*   **Пример:** `quantile_over_time(0.99, rate(http_requests_total[1m])[1h:1m])`.
*   **Применение:** Поиск пиковых нагрузок (Burstiness) за период для конкретного сервиса.

## Практические сценарии

### Сценарий 1: Реализация в коде (Go)

Как перцентили задаются на уровне приложения при использовании библиотеки `client_golang`.

**Для Summary (Точные квантили на клиенте):**
```go
var summary = prometheus.NewSummary(prometheus.SummaryOpts{
    Name: "api_latency_summary_seconds",
    Objectives: map[float64]float64{
        0.5:  0.05,   // Медиана с точностью 5%
        0.95: 0.01,   // p95 с точностью 1%
        0.99: 0.001,  // p99 с точностью 0.1%
    },
})
```

**Для Histogram (Корзины для интерполяции на сервере):**
```go
var histogram = prometheus.NewHistogram(prometheus.HistogramOpts{
    Name:    "api_latency_histogram_seconds",
    Buckets: []float64{0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0},
})
```

### Сценарий 2: Выявление «тяжелых хвостов» (Tail Latency)

Анализ разрыва между p50 и p99 позволяет диагностировать тип проблем:
- **p50 и p99 растут вместе:** Проблема в общей производительности (нехватка CPU, медленная БД для всех).
- **p50 стабилен, p99 растёт:** Проблема затрагивает только часть запросов (блокировки, Lock contention, GC pauses, «тяжелые» запросы от части клиентов).

### Сценарий 3: Мониторинг SLO на основе перцентилей

Цель (SLO): 99% запросов должны выполняться быстрее 200 мс.

```promql
# Алерт, если p99 превышает 200мс в течение 5 минут
histogram_quantile(0.99, 
  sum by (le) (rate(http_request_duration_seconds_bucket[5m]))
) > 0.2
```

## Дополнительная информация

### Визуализация: Heatmaps (Тепловые карты)

Перцентильные линии (p50, p95, p99) на графике дают хороший обзор, но скрывают детали распределения. Для глубокого анализа рекомендуется использовать **Heatmaps** в Grafana:
*   Они отображают все корзины гистограммы одновременно.
*   Интенсивность цвета показывает количество событий в корзине.
*   Позволяют увидеть бимодальные распределения (когда у сервиса два выраженных "типичных" времени ответа), которые перцентили могут маскировать.

### Влияние на TSDB

*   **Classic Histograms:** Создают `N` временных рядов (где `N` — количество корзин). Это может привести к взрыву кардинальности при наличии многих лейблов.
*   **Native Histograms:** Хранят все данные в одном временном ряду, что значительно снижает нагрузку на индекс и диск.
