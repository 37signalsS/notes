# Перцентили и квантили: теория и практика

## Определения

**Перцентиль (percentile)** — это статистическая величина, показывающая значение, ниже которого лежит определённый процент наблюдений в наборе данных. 

**Квантиль (quantile)** — обобщение перцентиля, где уровень указывается в долях от 0 до 1. 
*   **0.95-квантиль** соответствует **95-му перцентилю**.
*   **0.5-квантиль** — это **медиана**.

В мониторинге перцентили незаменимы для анализа **Latency** (задержек), так как они позволяют отсечь аномальные выбросы и увидеть реальный опыт большинства пользователей. Среднее арифметическое в таких задачах бесполезно, так как один запрос со временем выполнения 60 секунд «испортит» статистику для тысячи запросов по 10 мс.

## Основные концепции

### Сравнение статистических мер

| Метрика | Что показывает | Устойчивость к выбросам | Применение |
|:---|:---|:---|:---|
| **Среднее (Mean)** | Сумма / Количество | Очень низкая | Общий объем ресурсов (например, трафик). |
| **Медиана (p50)** | Типичный случай | Высокая | Понимание нормальной работы системы. |
| **p95 / p99** | Хвосты распределения | Высокая | Контроль **SLA/SLO** и «плохого» опыта. |
| **Максимум** | Худший случай | Нулевая | Поиск критических багов, таймаутов. |

### Математика в Prometheus: Линейная интерполяция

При использовании классических гистограмм (`Histogram`) Prometheus не знает точных значений внутри корзин. Он знает только, сколько событий попало в диапазон. Для вычисления квантиля используется **линейная интерполяция**:

1.  Находится корзина, в которую попадает искомый квантиль.
2.  Предполагается, что значения внутри этой корзины распределены **равномерно**.
3.  Вычисляется точка внутри диапазона корзины.

**Проблема точности:** Если корзины слишком широкие (например, `[100мс, 1000мс]`), а ваши реальные задержки группируются около 110мс, `histogram_quantile` может вернуть 500мс просто из-за математики интерполяции. Для решения этой проблемы в Prometheus v3.0 внедрены **Native Histograms**, которые используют экспоненциальную сетку и почти исключают ошибку интерполяции.

### Критическое правило агрегации

Для вычисления квантилей на основе гистограмм (которые являются набором Counter-метрик) необходимо строго соблюдать порядок операций: **сначала вычисляется скорость (`rate`), затем производится агрегация (`sum`)**.

*   **ПРАВИЛЬНО:** `histogram_quantile(0.95, sum by (le) (rate(http_duration_bucket[5m])))`
*   **ОШИБОЧНО:** `histogram_quantile(0.95, rate(sum by (le) (http_duration_bucket)[5m]))`

*Почему это важно:* Суммирование «сырых» счётчиков до вычисления скорости игнорирует рестарты инстансов. Если один из десяти подов перезагрузится, его счётчик сбросится в 0, и `rate(sum(...))` воспримет это как аномальный скачок или падение, что полностью исказит перцентиль.

## Практические сценарии

### Сценарий 1: Реализация в коде (Go)

Как перцентили задаются на уровне приложения при использовании библиотеки `client_golang`.

**Для Summary (Точные квантили на клиенте):**
```go
var summary = prometheus.NewSummary(prometheus.SummaryOpts{
    Name: "api_latency_summary_seconds",
    Objectives: map[float64]float64{
        0.5:  0.05,   // Медиана с точностью 5%
        0.95: 0.01,   // p95 с точностью 1%
        0.99: 0.001,  // p99 с точностью 0.1%
    },
})
```

**Для Histogram (Корзины для интерполяции на сервере):**
```go
var histogram = prometheus.NewHistogram(prometheus.HistogramOpts{
    Name:    "api_latency_histogram_seconds",
    // Границы корзин определяют точность интерполяции
    Buckets: []float64{0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0},
})
```

### Сценарий 2: Выявление «тяжелых хвостов» (Tail Latency)

Анализ разрыва между p50 и p99 позволяет диагностировать тип проблем:
- **p50 и p99 растут вместе:** Проблема в общей производительности (нехватка CPU, медленная БД для всех).
- **p50 стабилен, p99 растёт:** Проблема затрагивает только часть запросов (блокировки, Lock contention, GC pauses, «тяжелые» запросы от части клиентов).

### Сценарий 3: Проблема агрегации Summary

Квантили из Summary нельзя усреднять. Если у вас 10 реплик, и вы выполните `avg(latency{quantile="0.99"})`, вы получите число, не имеющее физического смысла. 

**Решение:**
1.  Использовать **Histogram** для агрегации по кластеру.
2.  Для Summary использовать `max()`, чтобы видеть самый плохой инстанс.

## Дополнительная информация

### Особенности работы с `histogram_quantile`

1.  **Лейбл `le`**: При агрегации через `sum` необходимо всегда сохранять лейбл `le` в блоке `by`.
2.  **Корзина `+Inf`**: Всегда должна присутствовать в данных, иначе функция не сможет определить общее количество событий и вернет `NaN`.
3.  **Влияние на TSDB**: Классические гистограммы создают большое количество временных рядов (кол-во корзин * кол-во инстансов). Тщательно выбирайте границы корзин, чтобы не перегрузить базу данных.
