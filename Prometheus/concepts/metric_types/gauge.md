# Тип метрики Gauge (Измеритель)

## Определения

**Gauge** — это тип метрики в [Prometheus](../../overview.md), представляющий собой одно числовое значение, которое может произвольно увеличиваться и уменьшаться во времени.

В отличие от [Counter](./counter.md), который фиксирует накопленные значения (счётчики), Gauge используется для измерения **текущего состояния** системы («здесь и сейчас»). Примерами могут служить температура, использование оперативной памяти, количество активных потоков или уровень заряда батареи.

В TSDB Gauge хранится с тем же внутренним форматом чанков, что и Counter, но без семантики монотонности. Для Prometheus это просто временной ряд, который может как расти, так и уменьшаться.

## Основные концепции

### Поведение Gauge

| Свойство | Описание |
|---|---|
| **Направление** | Произвольное: значение может расти, убывать или оставаться неизменным. |
| **Сброс (Resets)** | Не обрабатывается встроенными функциями `rate`/`increase`. После рестарта приложения Gauge просто начинает отдавать новое актуальное значение. |
| **Отрицательные значения** | Допустимы (например, температура или баланс счета). |
| **Агрегация** | Суммирование (`sum`) осмысленно только для аддитивных величин (например, общая память кластера). Для неаддитивных (температура) чаще используются `avg`, `min`, `max`. |
| **Суффикс** | Рекомендуется использовать базовые единицы измерения (например, `_bytes`, `_celsius`, `_seconds`). |

### Staleness и пропуски данных

Gauge не имеет встроенной защиты от потери данных. Если экспортёр перестаёт отдавать метрику (падение таргета, обрыв сети, перезапуск процесса), Prometheus продолжает возвращать последнее известное значение в течение **5 минут** (lookback delta по умолчанию). По истечении этого окна ряд помечается как **stale** и исчезает с графиков и из результатов запросов.

**Ключевые отличия от Counter при потере данных:**

- **Counter:** если экспортёр упал и перезапустился, значение сбрасывается в 0. Функции `rate()` и `increase()` корректно обработают этот сброс.
- **Gauge:** если экспортёр упал, значение не сбрасывается в 0 — оно просто перестаёт обновляться. После stale-периода ряд исчезает. При возврате таргета в строй Gauge появляется с новым актуальным значением, и Prometheus начинает новый временной ряд.

**Практическое значение для SRE:**
- Алерт на основе Gauge может «висеть» в активном состоянии до 5 минут после падения таргета, если условие проверяет последнее сохранённое значение.
- Для детектирования полного отсутствия данных используйте `absent_over_time()` или `absent()`. См. [Поведение метрик в реальных сценариях](../promql/real_world_behavior.md).

### Особенности Prometheus v3.x и OpenTelemetry

В актуальных версиях Prometheus (v3.0+) работа с Gauge получила значительные улучшения:

- **Remote Write 2.0:** При передаче данных во внешние хранилища (Mimir, VictoriaMetrics) метаданные Gauge (тип, описание, единицы измерения) теперь передаются нативно. Это позволяет инструментам визуализации (Grafana, Perses) автоматически настраивать оси и префиксы (например, отображать `bytes` как `GiB`).
- **Поддержка UTF-8:** Благодаря поддержке UTF-8 в именах метрик, Gauge может иметь имена, соответствующие стандартам OpenTelemetry (например, `process.runtime.go.goroutines`), без принудительной замены точек на подчеркивания.
- **Интеграция с OpenTelemetry:** Метрики типа `Gauge` и `Non-monotonic Sum` из OTel SDK напрямую маппятся в Prometheus Gauge. Asynchronous Gauges (которые собираются периодически) являются идеальным источником для этого типа.

### Почему Gauge — это «моментальный снимок»

Gauge фиксирует состояние в момент сбора (scrape). Если между двумя скрейпами произошёл резкий скачок значения и возврат в исходное состояние, Prometheus может не зафиксировать этот пик (проблема "aliasing"). Для критических всплесков, которые нельзя пропускать, лучше использовать [Histogram](./histogram.md) или специальные Gauge-агрегаторы на стороне приложения (например, сохранение `max` значения между скрейпами).

### Функции PromQL для Gauge

Эти функции анализируют поведение метрики внутри заданного временного окна (`range vector`) и возвращают мгновенный вектор (`instant vector`).

| Функция | Назначение | Особенности |
|---|---|---|
| `deriv(v[range])` | Скорость изменения (производная) | Рассчитывается методом линейной регрессии. Показывает тренд (например, байт в секунду). |
| `predict_linear(v[range], t)` | Прогноз значения через `t` секунд | Экстраполирует текущий тренд. Идеально для алертов о нехватке места на диске. |
| `delta(v[range])` | Общее изменение за период | Вычисляет разницу между первой и последней точкой в окне: `v_last - v_first`. |
| `idelta(v[range])` | Мгновенная разница | Разница между двумя последними точками. Аналог `irate` для Gauge. |
| `changes(v[range])` | Частота изменений | Подсчитывает количество раз, когда значение метрики менялось в заданном окне. |

### Функции агрегации во времени (Range Vector Functions)

Для Gauge критически важны функции, позволяющие анализировать историю изменений за интервал:

- `avg_over_time(v[range])`: среднее значение (например, средняя загрузка CPU за час).
- `min_over_time(v[range])` / `max_over_time(v[range])`: поиск экстремумов (пиков и просадок).
- `sum_over_time(v[range])`: общая сумма значений (используется редко, например, для интервальных показателей, выраженных через Gauge).
- `last_over_time(v[range])`: последнее зафиксированное значение в интервале.

### Паттерн Info-метрик

Gauge часто используется для передачи статических метаданных (версия ПО, версия ядра, конфигурация). Такие метрики называются **Info-metrics**.

**Пример:**
```text
# Значение всегда 1, полезная информация — в лейблах
node_info{version="1.8.2", kernel="6.1.0-21-amd64", instance="server-1"} 1
```
Это позволяет в PromQL объединять (`join`) динамические метрики с метаданными через оператор `on` или `group_left`.

### Инструментация Gauge: клиентские библиотеки

Создание Gauge в коде приложения ничем не отличается от Counter по сложности, но требует иного подхода к семантике: значение задаётся явно, а не инкрементируется.

**Go (client_golang):**
```go
import "github.com/prometheus/client_golang/prometheus"

activeConnections := prometheus.NewGauge(prometheus.GaugeOpts{
    Namespace: "myapp",
    Name:      "active_connections",
    Help:      "Current number of active TCP connections.",
})

// Установка значения
activeConnections.Set(42)
// Или увеличение/уменьшение
activeConnections.Inc()
activeConnections.Dec()
activeConnections.Add(5)
activeConnections.Sub(3)
```

**Python (prometheus_client):**
```python
from prometheus_client import Gauge

active_connections = Gauge(
    'myapp_active_connections',
    'Current number of active TCP connections',
    ['server', 'protocol']
)

active_connections.labels(server='web-01', protocol='http').set(42)
active_connections.labels(server='web-01', protocol='http').inc()
active_connections.labels(server='web-01', protocol='http').dec()
```

**Важно:** Gauge следует использовать для значений, которые приложение может получить напрямую из своего состояния. Для событийных метрик (количество запросов, ошибок) используйте Counter.

### Поведение при рестарте

В отличие от Counter, Gauge **не требует специальной обработки сбросов** в PromQL. После перезапуска приложения экспортер сразу отдаёт актуальное состояние. Однако стоит помнить:

1. Рестарт экспортёра между скрейпами не сбрасывает Gauge в 0. Prometheus просто не получит точку за этот интервал. Если таргет не ответит в течение 5 минут, ряд станет stale и исчезнет с графиков.
2. Функция `deriv()` может выдать кратковременный аномальный результат, если в окно попал рестарт с резким изменением значения.
3. Если Gauge используется для отслеживания времени (например, `process_start_time_seconds`), то после рестарта значение изменится скачкообразно, что является ожидаемым поведением.

Подробнее о механизмах stale markers и lookback delta см. в [Поведение метрик PromQL в реальных сценариях](../promql/real_world_behavior.md).

## Практические сценарии

### Сценарий 1: Утилизация памяти (в процентах)

```promql
# Формула: (1 - Свободно / Всего) * 100
(1 - node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes) * 100
```
**Применение:** Мониторинг ресурсов хоста. Позволяет оценить реальный дефицит RAM с учетом кэшей ОС.

### Сценарий 2: Прогноз переполнения диска

```promql
# Сработает, если диск заполнится (свободное место < 0) в течение ближайших 4 часов
predict_linear(node_filesystem_free_bytes{mountpoint="/"}[1h], 4 * 3600) < 0
```
**Применение:** Проактивное оповещение. Помогает избежать инцидентов до того, как место закончится физически.

### Сценарий 3: Детекция утечек памяти (Memory Leak)

```promql
# Положительная производная в течение длительного времени
deriv(process_resident_memory_bytes[15m]) > 0
```
**Применение:** Если производная стабильно выше нуля, это явный признак постепенного потребления ресурсов без их освобождения.

### Сценарий 4: Количество изменений состояния (Flapping)

```promql
# Как часто сервис менял статус за последний час
changes(service_status[1h]) > 10
```
**Применение:** Выявление нестабильных компонентов, которые часто перезапускаются или "мигают" статусом доступности.

### Сценарий 5: Статус сервиса (Health Check)

```promql
# Значение 1 — OK, 0 — Критично
up{job="my-api"} == 0
```
**Применение:** Базовый мониторинг доступности таргетов через встроенную метрику Prometheus.

### Сценарий 6: Отслеживание "свежести" данных (Staleness)

Часто используется Gauge, хранящий Unix-timestamp последнего успешного события (бэкапа, синхронизации).

```promql
# Алерт, если с последнего бэкапа прошло более 24 часов
time() - backup_last_success_timestamp_seconds > 24 * 3600
```
**Применение:** Мониторинг фоновых задач и Cron-скриптов.

### Сценарий 7: Мониторинг очередей и пула соединений

Gauge идеален для метрик, которые могут как расти, так и уменьшаться в рамках нормальной работы.

```promql
# Предупреждение, если в очереди накопилось более 1000 сообщений
rabbitmq_queue_messages{queue="orders"} > 1000

# Средний размер пула соединений за 5 минут
avg_over_time(db_connections_active[5m])
```
**Применение:** Мониторинг брокеров сообщений, пулов БД, кэшей. Позволяет детектировать застои до переполнения.

### Сценарий 8: Температура и здоровье оборудования

```promql
# Температура CPU выше 90°C
node_hwmon_temp_celsius{sensor="coretemp"} > 90

# Количество деградированных дисков в RAID
node_mdraid_disks_degraded > 0
```
**Применение:** Проактивный мониторинг железа через `node_exporter` и `smartctl` экспортёры. Позволяет предотвратить отказы оборудования.

### Сценарий 9: Обнаружение отсутствующих данных

Если критически важно, чтобы метрика всегда отдавала значение, используйте `absent_over_time()`:

```promql
# Алерт, если метрика "last_backup" не обновлялась более 1 часа
absent_over_time(backup_last_success_timestamp_seconds[1h])

# Алерт, если Gauge "service_up" отсутствует (экспортёр упал)
absent(service_up{job="payment"})
```
**Применение:** Гарантированная детекция падения экспортёров или остановки фоновых задач.

### Сценарий 10: Recording rules для Gauge

Для сложных или frequently-запрашиваемых Gauge-выражений создавайте Recording Rules. Это снижает нагрузку на Prometheus и ускоряет дашборды.

```yaml
groups:
  - name: gauges.rules
    rules:
      - record: node:memory:utilization:ratio
        expr: 1 - (node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes)
      - record: job:active_connections:avg
        expr: avg by (job) (myapp_active_connections)
      - record: instance:disk:free:bytes
        expr: node_filesystem_free_bytes{mountpoint="/"}
```

**Применение:** Предварительный расчёт производных, усреднений и прогнозов. Имена recording rules следуют паттерну `entity:metric:operation`.

### Устранение неполадок

| Симптом | Возможная причина | Диагностика | Решение |
|---|---|---|---|
| Gauge резко упал в 0 | Экспортёр перезапустился и начал отдавать 0 вместо реального значения | Проверить логи экспортёра, сравнить `up` метрику | Исправить экспортёр; если это push-метрика, убедиться что Pushgateway не сбрасывает данные |
| График обрывается (stale) | Таргет недоступен > 5 минут | `absent(metric_name)` | Проверить сеть, Service Discovery, статус таргета |
| `predict_linear` даёт отрицательное значение при положительном дефиците | Недостаточно истории в окне `[range]` (менее 4 точек) | Увеличить окно или проверить интервал скрейпинга | Использовать окно `[2h]` вместо `[1h]` при `scrape_interval=30s` |
| `deriv()` показывает отрицательный тренд при рестарте | В окно попал рестарт приложения | Исключить момент рестарта из окна или использовать `avg_over_time` | Использовать `max_over_time` для определения пика, а не `deriv` |
| Сумма Gauge по кластеру не имеет смысла | Агрегированы неаддитивные величины | Проверить PromQL на наличие `sum(temperature_celsius)` | Заменить на `avg` или `max` по инстансам |

## Дополнительная информация

### Формат экспорта

В текстовом формате Prometheus (Exposition Format) Gauge объявляется следующим образом:

```text
# HELP node_memory_mem_available_bytes Available memory in bytes.
# TYPE node_memory_mem_available_bytes gauge
node_memory_mem_available_bytes{instance="server-1"} 4294967296
```

### Рекомендации по именованию

1. **Используйте базовые единицы:** `_bytes`, `_seconds`, `_celsius`, `_ratio` (для долей от 0 до 1).
2. **Избегайте `_total`:** Этот суффикс строго зарезервирован для [Counter](./counter.md).
3. **Отражайте состояние:** Имена должны отвечать на вопрос «сколько чего сейчас» (например, `active_connections`, `temperature_celsius`).
4. **Info-метрики:** Рекомендуется суффикс `_info` (например, `app_build_info`).
5. **Единицы измерения в v3:** В Prometheus v3.0 рекомендуется явно указывать `UNIT` в экспортере, если это поддерживается клиентской библиотекой.

### Сравнение с Counter

| Характеристика | Gauge | Counter |
|---|---|---|
| **Динамика** | Вверх и вниз | Только вверх (кроме сбросов) |
| **Функции** | `delta`, `deriv`, `predict_linear`, `changes` | `rate`, `irate`, `increase`, `resets` |
| **Рестарты** | Продолжает с текущего значения | Сбрасывается в 0 |

Более подробное сравнение функций и обработки сбросов см. в [Тип метрики Counter](./counter.md) и [Поведение метрик PromQL в реальных сценариях](../promql/real_world_behavior.md).

### Типовые ошибки

- **Использование `rate()`:** Функция `rate` ожидает монотонно растущий счётчик. Применение её к Gauge даст некорректные или отрицательные результаты при падении значений.
- **Суммирование неаддитивных величин:** `sum(temperature_celsius)` не имеет физического смысла. Используйте `avg_over_time` или `avg`.
- **Пропуск кратковременных пиков:** Использование Gauge для высокочастотных событий (например, длительность запроса). Для этого используйте [Histogram](./histogram.md) или [Summary](./summary.md).
- **Игнорирование stale markers:** Если Gauge исчез после падения таргета, алерт на его основе может не сработать. Всегда добавляйте `absent_over_time()` для критически важных метрик.

### Pushgateway и пакетные задачи

Для Cron-задач, которые завершаются и не поддерживают постоянный HTTP-сервер, используется Pushgateway. Gauge в этом контексте часто передаёт метку времени последнего успешного запуска:

```bash
cat <<EOF | curl --data-binary @- http://pushgateway:9091/metrics/job/backup_job
# TYPE backup_last_success_timestamp_seconds gauge
backup_last_success_timestamp_seconds{instance="backup-01"} $(date +%s)
EOF
```

**Важно:** Pushgateway не изменяет семантику метрики. Если несколько запусков отправляют одно и то же значение, оно просто перезаписывается. Для метрик, которые должны расти (счётчики запусков), используйте Counter и утилиту `pushadd`.

### Textfile collector (node_exporter)

Для сбора метрик от скриптов и Cron-задач без Pushgateway используется textfile collector:

```bash
#!/bin/bash
# /usr/local/bin/backup-metrics.sh
METRICS_FILE="/var/lib/prometheus/node-exporter/backup-metrics.prom"
TMP_FILE=$(mktemp)

cat > "$TMP_FILE" <<EOF
# HELP backup_last_success_timestamp_seconds Timestamp of last successful backup.
# TYPE backup_last_success_timestamp_seconds gauge
backup_last_success_timestamp_seconds $(date +%s)
EOF

mv "$TMP_FILE" "$METRICS_FILE"
```

node_exporter автоматически подхватывает файлы из каталога и отдаёт их на скрейпинг.

### Антипаттерны

- **Gauge для событий:** Не используйте Gauge для подсчёта событий (запросов, ошибок). Для этого предназначен Counter.
- **Gauge с высокой частотой обновления:** Если Gauge меняется несколько раз в секунду, это может создать чрезмерную нагрузку на TSDB. Убедитесь, что scrape interval соотносится с природой метрики.
- **Суммирование неаддитивных Gauge:** `sum(temperature_celsius)` бессмысленно. Используйте `avg` или `max`.
- **Игнорирование кардинальности:** Не добавляйте в Gauge лейблы с высокой кардинальностью (user_id, request_id, session_id). Это приведёт к взрыву числа временных рядов в TSDB. См. [Лейблы и кардинальность](../labels_and_cardinality.md).
- **Gauge вместо состояния в лейблах:** Вместо `service_status{service="api"} 1` и `service_status{service="api"} 0` лучше использовать метрику-индикатор с лейблом `status="up|down"` или два отдельных Gauge. Это упрощает агрегацию.

### Кардинальность и Gauge

Gauge-метрики часто становятся источником неожиданного роста кардинальности, особенно когда они экспортируются с пер-инстансными или пер-задачными лейблами. Каждое уникальное сочетание лейблов создаёт отдельный временной ряд в TSDB.

**Пример проблемной метрики:**
```text
process_memory_bytes{pid="1234"} 52428800
process_memory_bytes{pid="1235"} 33554432
```

При 10 000 процессов в кластере это создаст 10 000 рядов. Если добавить лейбл `host`, кардинальность вырастет в разы.

**Рекомендация:** Используйте агрегированные метрики (`sum by (job, instance)`) на стороне экспортёра или создавайте Recording Rules для сворачивания пер-экземплярных данных перед записью в TSDB.
