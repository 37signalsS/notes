# Гистограмма (Histogram)

## Определения

**Гистограмма (Histogram)** — это тип метрики в [Prometheus](../../overview.md), предназначенный для измерения распределения наблюдаемых величин (например, длительности запросов или размеров ответов). 

Гистограмма группирует значения в настраиваемые диапазоны — **корзины (buckets)** — и предоставляет два дополнительных счётчика: общую сумму всех наблюдений и их общее количество. Это позволяет вычислять перцентили (квантили) на стороне сервера, что делает гистограммы незаменимыми для анализа «хвостов» распределения (tail latency) в распределённых системах.

## Основные концепции

### Поведение классической гистограммы

| Свойство | Описание |
|:---|:---|
| **Направление** | Значения в корзинах (`_bucket`), сумма (`_sum`) и количество (`_count`) являются кумулятивными счётчиками ([Counter](./counter.md)) и только растут. |
| **Сброс (Reset)** | Происходит при перезапуске приложения. Корректно обрабатывается функциями `rate()` и `increase()`. |
| **Агрегация** | Допускается суммирование корзин по инстансам (`sum by (le)`), что позволяет вычислять общие перцентили для всего кластера. |
| **Интерполяция** | Квантили вычисляются методом линейной интерполяции внутри границ корзины. |

### Структура временных рядов

Одна классическая гистограмма создаёт несколько временных рядов:

| Ряд | Тип | Описание |
|:---|:---|:---|
| `<имя>_bucket{le="<upper_bound>"}` | Counter | Счётчик значений, которые меньше или равны верхней границе (`le` — less or equal). |
| `<имя>_sum` | Counter | Общая сумма всех наблюдаемых значений. |
| `<имя>_count` | Counter | Общее количество наблюдений (эквивалентно значению корзины `le="+Inf"`). |

### Нативные гистограммы (Native Histograms / v3.0+)

Начиная с Prometheus v3.0, нативные гистограммы (также известные как экспоненциальные) стали стабильной технологией. Их отличия:
- **Отсутствие лейбла `le`**: Все корзины хранятся в одном временном ряду в виде компактного разреженного массива.
- **Динамическая точность**: Границы корзин определяются экспоненциально, обеспечивая фиксированную относительную погрешность.
- **Экономия ресурсов**: Занимают значительно меньше места в TSDB и снижают нагрузку при запросах по сравнению с классическими гистограммами с большим количеством корзин.

### Критическое правило агрегации

Для всех составляющих гистограммы (`_bucket`, `_sum`, `_count`), которые являются счётчиками, действует строгое правило: **сначала вычисляется скорость (`rate`), затем производится агрегация (`sum`)**.

*   **ПРАВИЛЬНО:** `sum by (le) (rate(http_request_duration_seconds_bucket[5m]))`
*   **ОШИБОЧНО:** `rate(sum by (le) (http_request_duration_seconds_bucket)[5m])`

Нарушение этого порядка приведет к полной потере информации о сбросах счётчиков при рестартах подов, что сделает данные на графиках и в алертинге недостоверными.

## Практические сценарии

### Сценарий 1: Вычисление 95-го перцентиля латентности

```promql
# Вычисление 95-го перцентиля по всем инстансам за последние 5 минут
histogram_quantile(0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket[5m]))
)
```

### Сценарий 2: Расчёт среднего времени ответа

Среднее значение полезно для понимания общего тренда, хотя оно и скрывает выбросы.

```promql
# Среднее = Сумма скоростей изменений / Сумма скоростей событий
sum(rate(http_request_duration_seconds_sum[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```

### Сценарий 3: Доля запросов в рамках SLA (SLO)

Если целевой показатель — 99% запросов быстрее 500мс.

```promql
# Процент запросов быстрее или равных 0.5с
sum(rate(http_request_duration_seconds_bucket{le="0.5"}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m])) * 100
```

### Сценарий 4: Выявление «медленных» эндпоинтов

```promql
# 99-й перцентиль с разбивкой по путям (лейбл path)
histogram_quantile(0.99,
  sum by (le, path) (rate(http_request_duration_seconds_bucket[5m]))
)
```

## Дополнительная информация

### Настройка корзин в коде (Go)

Пример использования официальной библиотеки `prometheus/client_golang`. Выбор границ корзин напрямую влияет на точность `histogram_quantile`.

```go
var requestDuration = prometheus.NewHistogram(prometheus.HistogramOpts{
    Name:    "http_request_duration_seconds",
    Help:    "Длительность HTTP-запросов в секундах.",
    // Рекомендуется использовать экспоненциальный шаг или границы, 
    // близкие к вашим целевым SLA.
    Buckets: []float64{0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10},
})
```

**Рекомендации:**
- Не используйте слишком много корзин (оптимально 10–15). Каждая корзина — это отдельный временной ряд в TSDB.
- Для нативных гистограмм (Native Histograms) границы корзин не задаются вручную, библиотека управляет ими автоматически.

### Сравнение с типом Summary

| Критерий | Histogram | Summary |
|:---|:---|:---|
| **Место вычисления** | Сервер (PromQL) | Клиент (приложение) |
| **Агрегируемость** | Да (по кластеру/сервису) | Нет (только по инстансу) |
| **Точность** | Приблизительная (интерполяция) | Высокая (точная) |
| **Нагрузка на TSDB** | Высокая (при большом кол-ве корзин) | Низкая |

### Типовые ошибки

1.  **Линейная интерполяция**: Prometheus предполагает равномерное распределение данных внутри корзины. Если корзина слишком широкая (например, от 100мс до 1с), вычисленный квантиль будет неточным.
2.  **Забытый лейбл `le` при агрегации**: Если в `sum by (...)` не указан лейбл `le`, вы потеряете структуру гистограммы, и функция `histogram_quantile` вернет ошибку или пустой результат.
3.  **Использование Histogram для низкочастотных событий**: Если за интервал `rate` попадает слишком мало данных, вычисление квантилей будет крайне нестабильным.
