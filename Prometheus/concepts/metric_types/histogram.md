# Гистограмма (Histogram)

## Определения

**Гистограмма (Histogram)** — тип метрики в [Prometheus](../../overview.md), предназначенный для отслеживания распределения наблюдаемых величин. Гистограмма группирует значения в настраиваемые корзины (buckets) и предоставляет два дополнительных счётчика: общую сумму всех наблюдений и их общее количество. Основное применение — измерение латентности (задержек), размеров запросов и времени выполнения операций.

## Основные концепции

### Поведение гистограммы

| Свойство | Описание |
|:---|:---|
| **Направление** | Значения в корзинах (`_bucket`), а также сумма (`_sum`) и количество (`_count`) только растут. |
| **Сброс** | Обрабатывается аналогично типу Counter (через функцию `rate()`). |
| **Агрегация** | Допускается суммирование по инстансам, что является ключевым преимуществом перед типом Summary. |
| **Суффиксы** | `_bucket{le="..."}`, `_sum`, `_count` (добавляются автоматически). |

### Структура метрик Histogram

Одна гистограмма создаёт несколько временных рядов в базе данных:

| Ряд | Тип | Описание |
|:---|:---|:---|
| `<имя>_bucket{le="<upper_bound>"}` | Counter | Кумулятивный счётчик значений, которые меньше или равны верхней границе (upper bound). |
| `<имя>_sum` | Counter | Общая сумма всех наблюдаемых значений. |
| `<имя>_count` | Counter | Общее количество наблюдений (совпадает со значением корзины `le="+Inf"`). |

### Ключевые преимущества

- **Вычисление квантилей на стороне сервера:** Функция `histogram_quantile()` в языке запросов PromQL позволяет вычислять любые перцентили после сбора данных.
- **Агрегируемость:** Гистограммы от нескольких реплик приложения можно суммировать (`sum by (le)`) и только после этого вычислять перцентили. Это критически важно для распределённых систем и отличает гистограммы от [Summary](./summary.md).
- **Гибкость:** На основе одной метрики можно вычислить среднее значение, перцентили и количество запросов, превышающих заданный порог.

### Настройка корзин (buckets)

Границы корзин определяются при создании гистограммы в коде приложения. Выбор границ напрямую влияет на точность функции `histogram_quantile()`:

| Параметр | Описание |
|:---|:---|
| **Количество** | Рекомендуется использовать от 5 до 15 корзин. |
| **Границы** | Зависят от ожидаемого распределения (например, для латентности API: `0.01, 0.05, 0.1, 0.5, 1, 5, 10`). |
| **`+Inf`** | Автоматическая корзина, которая всегда присутствует и содержит общее количество наблюдений. |
| **Точность** | Зависит от плотности корзин в интересующем диапазоне значений. |

**Рекомендации по настройке:**

- Начинайте с 5–7 корзин, охватывающих типичный диапазон значений.
- Увеличивайте плотность корзин в критически важных диапазонах (например, в районе целевого SLA (Service Level Agreement) — 50–200 мс для API).
- Избегайте слишком широких корзин, так как это снижает точность вычисления перцентилей.
- Избегайте чрезмерного количества корзин, чтобы не вызвать взрывной рост кардинальности метрик.

## Практические сценарии

### Сценарий 1: Вычисление 95-го перцентиля латентности по кластеру

```promql
# 95-й перцентиль длительности запросов
histogram_quantile(0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
)
```

**Разбор запроса:**

- `sum(rate(..._bucket[5m])) by (le)` — агрегация скоростей роста корзин по всем инстансам.
- `histogram_quantile(0.95, ...)` — вычисление значения 95-го перцентиля на основе агрегированных данных.
- Результат возвращается в единицах измерения исходной метрики (в данном примере — секунды).

### Сценарий 2: Расчёт среднего времени ответа

```promql
# Среднее время = сумма скоростей / количество скоростей
sum(rate(http_request_duration_seconds_sum[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```

Применяется для отслеживания общего тренда производительности. Метод устойчив к единичным выбросам.

### Сценарий 3: Подсчёт количества медленных запросов

```promql
# Количество запросов в секунду, которые выполнялись дольше 1 секунды
sum(rate(http_request_duration_seconds_count[5m])) 
- 
sum(rate(http_request_duration_seconds_bucket{le="1"}[5m]))
```

Используется для алертинга на деградацию производительности — определение количества запросов, нарушающих установленные границы.

### Сценарий 4: Контроль SLA (Service Level Agreement)

```promql
# Доля запросов, выполненных быстрее 0.5 секунды
sum(rate(http_request_duration_seconds_bucket{le="0.5"}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```

Применяется для мониторинга SLO (Service Level Objective) — определение процента запросов, соответствующих целевым показателям.

### Сценарий 5: Группировка перцентилей по лейблам

```promql
# 99-й перцентиль с разбивкой по эндпоинтам (путям запросов)
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le, path)
)
```

Позволяет сравнивать производительность различных частей приложения на одном графике.

## Дополнительная информация

### Сравнение с типом Summary

| Критерий | Гистограмма (Histogram) | Сводка (Summary) |
|:---|:---|:---|
| **Агрегация** | Допускается суммирование корзин по инстансам. | Нельзя корректно агрегировать квантили по инстансам. |
| **Место вычисления** | На стороне сервера (Prometheus) через `histogram_quantile()`. | На стороне клиента (экспортёр или библиотека). |
| **Точность** | Приблизительная, зависит от плотности корзин. | Высокая точность для конкретного инстанса. |
| **Нагрузка** | Меньшая нагрузка на клиентское приложение. | Большая нагрузка на клиентское приложение. |
| **Основной сценарий** | Анализ производительности распределённых систем. | Мониторинг одного процесса, где не требуется агрегация. |

**Важное замечание:** Если приложение экспортирует данные в формате Summary, их невозможно объединить для получения общей картины по кластеру. Для анализа задержек в распределённых системах рекомендуется использовать Histogram.

### Экспорт в текстовом формате Prometheus

Пример представления гистограммы при сборе метрик (scrape):

```text
# HELP http_request_duration_seconds HTTP request latency in seconds.
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.1"} 240
http_request_duration_seconds_bucket{le="0.5"} 980
http_request_duration_seconds_bucket{le="1.0"} 1200
http_request_duration_seconds_bucket{le="+Inf"} 1250
http_request_duration_seconds_sum 75.3
http_request_duration_seconds_count 1250
```

### Типовые ошибки

- **Использование `histogram_quantile()` без `sum by (le)`:** Это приведёт к вычислению перцентиля для каждого инстанса отдельно, что часто не является целью.
- **Неправильный выбор корзин:** Слишком малое количество корзин даёт низкую точность, а слишком большое — перегружает TSDB (Time Series Database) из-за высокой кардинальности.
- **Агрегация по лейблам до вызова функции:** Любая агрегация (например, `sum`) должна обязательно сохранять лейбл `le`, иначе данные о распределении будут потеряны.
