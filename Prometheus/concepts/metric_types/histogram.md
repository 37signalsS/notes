# Histogram (Гистограмма)

## Определения

**Histogram** — метрика в [Prometheus](../../overview.md) для отслеживания распределения наблюдаемых событий. Histogram группирует значения в настраиваемые корзины (buckets) и предоставляет счётчик и сумму всех наблюдений. Используется для измерения латентности, размеров запросов, времени выполнения операций.

> **См. также:** [Типы метрик](./overview.md) — обзор всех типов метрик.

## Основные концепции

### Поведение Histogram

| Свойство | Описание |
|---|---|
| **Направление** | Корзины (`_bucket`) только растут, `_sum` и `_count` — тоже |
| **Сброс** | Обрабатывается как Counter (через `rate()`) |
| **Агрегация** | **Можно** суммировать по инстансам — ключевое преимущество перед Summary |
| **Суффиксы** | `_bucket{le="..."}`, `_sum`, `_count` (автоматические) |

### Структура метрик Histogram

Один Histogram создаёт **множество временных рядов**:

| Ряд | Тип | Описание |
|---|---|---|
| `<имя>_bucket{le="<upper_bound>"}` | Counter | Кумулятивный счётчик значений ≤ upper_bound |
| `<имя>_sum` | Counter | Общая сумма всех наблюдаемых значений |
| `<имя>_count` | Counter | Общее количество наблюдений (совпадает с `le="+Inf"`) |

### Ключевые преимущества

- **Вычисление квантилей на стороне сервера** — `histogram_quantile()` в PromQL позволяет вычислять любые перцентили после сбора данных
- **Агрегируемость** — гистограммы от нескольких реплик можно суммировать (`sum by (le)`) и только потом считать перцентили. Это главное отличие от [Summary](./summary.md)
- **Гибкость** — можно вычислить средний, перцентили, количество запросов медленнее порога — всё из одной метрики

### Настройка корзин (buckets)

Корзины задаются при создании Histogram в коде приложения. Выбор корзин влияет на точность `histogram_quantile()`:

| Параметр | Описание |
|---|---|
| **Количество** | 5–15 корзин — типичный диапазон |
| **Границы** | Зависят от ожидаемого распределения (латентность API: `0.01, 0.05, 0.1, 0.5, 1, 5, 10`) |
| **`+Inf`** | Автоматическая корзина — всегда добавляется, содержит все наблюдения |
| **Точность** | Зависит от плотности корзин в интересующем диапазоне |

**Рекомендации:**

- Начните с 5–7 корзин, покрывающих ожидаемый диапазон значений
- Увеличьте плотность корзин в критичном диапазоне (например, 50–200ms для API)
- Избегайте слишком широких корзин — потеря точности перцентилей
- Избегайте слишком узких — рост кардинальности метрик

## Практические сценарии

### Сценарий 1: 95-й перцентиль латентности по кластеру

```promql
# 95-й перцентиль длительности запросов
histogram_quantile(0.95,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
)
```

**Разбор:**

- `sum(rate(..._bucket[5m])) by (le)` — агрегация корзин по всем инстансам
- `histogram_quantile(0.95, ...)` — вычисление 95-го перцентиля
- Результат в секундах (имя метрики содержит `_seconds`)

### Сценарий 2: Среднее время ответа

```promql
# Среднее время = сумма / количество
sum(rate(http_request_duration_seconds_sum[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```

**Применение:** Общий тренд производительности, не чувствителен к выбросам.

### Сценарий 3: Количество запросов медленнее порога

```promql
# Запросов в секунду медленнее 1 секунды
sum(rate(http_request_duration_seconds_bucket{le="1"}[5m]))
```

**Применение:** Алерт на деградацию производительности — сколько запросов превышает SLA.

### Сценарий 4: Процент запросов в SLA

```promql
# Доля запросов быстрее 0.5s
sum(rate(http_request_duration_seconds_bucket{le="0.5"}[5m]))
/
sum(rate(http_request_duration_seconds_count[5m]))
```

**Применение:** SLO-мониторинг — доля запросов, укладывающихся в SLA.

### Сценарий 5: Перцентиль с группировкой по лейблам

```promql
# 99-й перцентиль по каждому эндпоинту
histogram_quantile(0.99,
  sum(rate(http_request_duration_seconds_bucket[5m])) by (le, path)
)
```

**Применение:** Сравнение латентности разных эндпоинтов на одном графике.

## Дополнительная информация

### Сравнение с Summary

| Критерий | Histogram | Summary |
|---|---|---|
| **Агрегация** | **Можно** агрегировать (вычислять `rate()` и `sum()` по инстансам) | **Нельзя** корректно агрегировать квантили |
| **Вычисление квантилей** | На стороне сервера (Prometheus) через `histogram_quantile()` | На стороне клиента (экспортёр) |
| **Точность квантилей** | Приблизительная, зависит от настроек корзин | Точная, но только для одного инстанса |
| **Производительность** | Меньше нагрузка на клиент | Больше нагрузка на клиент |
| **Основной сценарий** | Анализ производительности распределённых систем (например, 95-й перцентиль latency по всему кластеру) | Мониторинг одного конкретного процесса, где агрегация не нужна |

**Важно:** Если приложения вместо Histogram пишут Summary — их уже нельзя объединить или сложить. Квантили от разных реплик с Summary нельзя агрегировать в Prometheus.

**Рекомендация:** Для анализа задержек (latency) или размеров запросов в распределённых системах **почти всегда следует использовать Histogram**.

### Экспорт в формате Prometheus

```
  # HELP http_request_duration_seconds HTTP request latency in seconds.
  # TYPE http_request_duration_seconds histogram
  http_request_duration_seconds_bucket{le="0.1"} 240
  http_request_duration_seconds_bucket{le="0.5"} 980
  http_request_duration_seconds_bucket{le="1.0"} 1200
  http_request_duration_seconds_bucket{le="+Inf"} 1250
  http_request_duration_seconds_sum 75.3
  http_request_duration_seconds_count 1250
```

- **Частые ошибки:**
  - ❌ Использование `histogram_quantile()` без `sum by (le)` — перцентиль посчитается для каждого инстанса отдельно
  - ❌ Слишком мало корзин — неточные перцентили
  - ❌ Слишком много корзин — взрыв кардинальности, нагрузка на TSDB
  - ❌ Агрегация по лейблам кроме `le` до `histogram_quantile()` — потеря данных распределения

- **Связь с алертингом:** Histogram — основа алертов на латентность. См. [Примеры алертов](./alerts.md) — алерт `HighLatency` на основе 95-го перцентиля.
