# Язык запросов PromQL

## Определения

**PromQL (Prometheus Query Language)** — это мощный **функциональный язык запросов**, разработанный для работы с многомерными данными временных рядов в [Prometheus](./overview.md). В отличие от SQL, он оптимизирован для вычислений и агрегаций над временными рядами. PromQL позволяет выбирать и агрегировать данные в реальном времени, результаты чего могут быть отображены в [Grafana](../../Grafana/grafana_overview.md), таблицах или использованы внешними системами через [HTTP API](../prometheus_api.md).

> **См. также:** [Типы метрик](./metric_types.md) — counter, gauge, histogram, summary.

### Типы данных

PromQL оперирует четырьмя основными типами данных:

* **Instant vector (вектор мгновенных значений)**: Набор временных рядов, где для каждого ряда есть только одна точка данных (последняя). Это самый частый результат запроса.
* **Range vector (вектор диапазона значений)**: Набор временных рядов, где для каждого ряда сохранен диапазон точек данных за определенный промежуток времени.
* **Scalar (скаляр)**: Простое числовое значение с плавающей точкой.
* **String (строка)**: Строковое значение (в настоящее время в PromQL напрямую не используется).

### Детали реализации типов

#### Instant vector

Массив из key-value, где key — метрика с лейблами, а value — значение в запрошенный момент времени. Это единственный тип, который рисуется на графиках.

**Почему такая структура:** Один запрос может вернуть сразу несколько временных рядов. Каждая метрика с разными значениями лейблов — это разные ряды. Поэтому instant vector всегда возвращается набором key-value, где ключ — это полное описание ряда (имя метрики и все лейблы), чтобы отличать один ряд от другого.

Один instant vector привязан к одному timestamp. Для получения полезных данных (для отображения на графике) к запросам обычно добавляются диапазон времени и шаг, а в ответе возвращаются наборы instant vector-ов, попавшие под диапазон.

**Важно:** Если в запрошенный timestamp нет значения в БД, Prometheus будет искать значения с timestamp меньше, по умолчанию в пределах 5 минут.

#### Range vector

Массив из key-value, где key — метрика, а value — это значение в запрошенный момент времени + массив из [предыдущих значений за какой-то интервал].

Range vector используется для функций, которые считают «изменение за интервал»: `rate()`, `delta()`, `deriv()` и других. Для вычисления производной или дельты нужно иметь хотя бы два значения функции.

**На что влияет интервал в квадратных скобках:**

* **Больше интервал** — более гладкий результат, виден тренд (общая картина)
* **Меньше интервал** — более шумный результат, видны пики и резкие скачки
* **Слишком малый интервал** (менее 2 точек) — нет результата

Range vector нельзя напрямую вывести на график. Его нужно сначала обработать функцией и получить instant vector.

#### Типы в API (vector и matrix)

При работе с веб-интерфейсом Prometheus или API можно заметить, что типы данных называются **vector** и **matrix**:

| Запрос | Вкладка | Тип в JSON | Описание |
|--------|---------|------------|----------|
| `metric{}` | Table | `vector` | Instant vector на один момент времени (добавляется `time`) |
| `metric{}[1m]` | Table | `matrix` | Range vector: текущая точка + массив прошлых точек |
| `metric{}` | Graph | `matrix` | Instant vector за диапазон (start, end, step) |
| `metric{}[1m]` | Graph | **Ошибка** | Range vector нельзя запросить за диапазон |

**Почему matrix для графика:** Одиночный instant vector не нарисуешь на графике — это просто точка в один момент времени. Для графика нужно много точек за диапазон, поэтому в запросе передаются `start`, `end`, `step`. В value лежит массив вида `[(timestamp1, val1), (timestamp2, val2), ...]`.

## Основные концепции

### Селекторы и Матчеры

Селекторы используются для выбора временных рядов на основе имени метрики и [лейблов](./labels_and_cardinality.md).

* **Вектор мгновенных значений (Instant Vector)**: `node_memory_mem_available_bytes{job="node-exporter"}`
* **Вектор диапазона значений (Range Vector)**: `node_network_receive_bytes_total[5m]`
  * *Единицы времени:* `s`, `m`, `h`, `d`, `w`, `y`.
  * Векторы диапазона нельзя напрямую отобразить на графике, они используются в функциях, таких как `rate()`.

Для фильтрации по лейблам внутри селектора (`{...}`) используются **матчеры**:

* `=`: Точное равенство.
* `!=`: Неравенство.
* `=~`: Соответствие регулярному выражению.
* `!~`: Несоответствие регулярному выражению.

*Пример:* `http_requests_total{job=~"api-server|web-server", method!="GET"}`

### Модификаторы времени

* `offset <duration>`: Позволяет получить данные из прошлого. `sum(http_requests_total) offset 1d`
* `@ <timestamp>`: Позволяет указать точное время для выполнения запроса. `node_memory_MemAvailable_bytes @ 1609459200`

### Операторы

#### Математические операторы

`+`, `-`, `*`, `/`, `%`, `^`. Применяются к скалярам и векторам.

#### Операторы сравнения

`==`, `!=`, `>`, `<`, `>=`, `<=`. Применяются к скалярам и векторам. С модификатором `bool` возвращают `0` или `1`.

*Пример:* `node_cpu_seconds_total > bool 3`

#### Логические операторы (только для `instant vector`)

* `and` (И): Элементы `vector1`, для которых есть элементы в `vector2` с тем же набором меток.
* `or` (ИЛИ): Все элементы `vector1` плюс уникальные элементы `vector2`.
* `unless` (ИСКЛЮЧАЯ): Элементы `vector1`, для которых нет совпадений в `vector2`.

## Практические сценарии

### Операторы агрегации

Позволяют агрегировать данные по нескольким временным рядам. Используются с `by` (группировка по лейблам) или `without` (исключение лейблов из группировки).

* `sum()`: сумма значений.
* `avg()`: среднее значение.
* `count()`: количество временных рядов.
* `min()`, `max()`: минимальное и максимальное значения.
* `stddev()`, `stdvar()`: стандартное отклонение и дисперсия.
* `topk(k, ...)` / `bottomk(k, ...)`: `k` наибольших/наименьших значений.
* `count_values("label", ...)`: количество элементов с одинаковым значением лейбла.
* `quantile(φ, ...)`: φ-квантиль (0 ≤ φ ≤ 1).

*Пример:* `sum by (path) (http_requests_total)` — сумма запросов для каждого `path`.

### Функции

PromQL имеет большой набор функций, которые можно разделить по типам метрик, с которыми они работают. Подробнее о типах метрик см. в **[Типы метрик в Prometheus](./metric_types.md)**.

#### Функции для счётчиков (Counters)

* `rate(v range-vector)`: **Средняя скорость** увеличения в секунду. Учитывает сбросы счётчика.
  * `rate(node_network_receive_bytes_total[5m])`
  * Считает скорость прироста в секунду (запросов/сек)
  * Подходит только для counter, т.к. полагается на возрастание
  * Учитывает сбросы метрики на 0, например при рестартах приложений
  * Экстраполируется
  * **Рекомендация:** Используйте `rate()` для большинства сценариев с counter

* `irate(v range-vector)`: **Мгновенная скорость** увеличения (использует две последние точки). Чувствителен к скачкам.
  * Подходит для резко прыгающих счетчиков
  * Более чувствителен к шуму, чем `rate()`

* `increase(v range-vector)`: Абсолютный прирост за диапазон.
  * `increase(http_requests_total{app="nginx"}[5m])`
  * Считает прирост за интервал (сколько запросов пришло)
  * Подходит только для counter, т.к. полагается на возрастание
  * Учитывает сбросы счетчика на 0, например при рестарте
  * Экстраполируется (поэтому бывают дроби даже когда прирост целый)
  * **Важно:** По сути это сахар для `rate() × интервал`. Например, для интервала в 1 час:
    * `rate(metric[1h])`
    * `increase(metric[1h])/3600`
  * **Рекомендация:** Лучше использовать `rate()`, так советуют в документации

* `resets(v range-vector)`: Количество сбросов счётчика.
  * Полезно для обнаружения рестартов приложений

#### Функции для измерителей (Gauges)

* `changes(v range-vector)`: Количество изменений значения.

* `deriv(v range-vector)`: Производная (скорость изменения) с использованием линейной регрессии.
  * `deriv(ram_free{host="postgresql"}[5m])`
  * Считает производную, т.е. прирост в секунду
  * Подходит только для gauge
  * **Не учитывает сбросы в 0** — может сойти с ума при рестарте приложения
  * Аналог `rate()`, но для метрик, которые могут убывать или скакать туда-сюда

* `predict_linear(v range-vector, t scalar)`: Прогнозирует значение через `t` секунд. Полезно для [алертинга](../rules.md).
  * `predict_linear(node_filesystem_free_bytes[1h], 3600 * 4) < 0` — прогноз нехватки места на диске через 4 часа.

* `delta(v range-vector)`: Разница между первым и последним значением в интервале.
  * `delta(ram_free{host="postgresql"}[5m])`
  * Считает разницу за интервал
  * Подходит только для gauge
  * Промежуточные значения отбрасываются — можно пропустить резкое изменение, которое быстро откатилось
  * Экстраполируется (поэтому бывают дроби даже когда изменение целое)
  * Вроде бы похож на более грубую версию `increase()`, но используется для метрик, которые могут убывать или скакать туда-сюда

#### Функции для гистограмм (Histograms)

* `histogram_quantile(φ float, b histogram)`: Вычисляет φ-квантиль (0 ≤ φ ≤ 1). Это основной способ использования гистограмм для расчета перцентилей.
  * `histogram_quantile(0.95, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))`
  * **Подробнее:** [Перцентили и квантили](./metric_types.md#перцентили-и-квантили)

#### Функции для сводок (Summaries)

Summary вычисляет квантили на стороне клиента, поэтому в PromQL нет специальных функций для работы с ними — квантили уже готовы в метриках.

* **Пример запроса 95-го перцентиля из Summary:**
  * `http_duration_summary{quantile="0.95"}`

> **Важно:** Квантили из Summary **нельзя агрегировать** по нескольким инстансам. Для распределенных систем используйте Histogram + `histogram_quantile()`. Подробнее см. в [Типы метрик — Summary](./metric_types.md#4-summary-сводка) и [Агрегация Summary](./metric_types.md#агрегация-summary-проблема-и-решение).

### Агрегация по времени (`..._over_time`)

Эти функции агрегируют значения *каждого* временного ряда в диапазоне и возвращают мгновенный вектор.

* `avg_over_time(v range-vector)`: Скользящее среднее.
* `max_over_time()`, `min_over_time()`, `sum_over_time()`, и др.
* `count_over_time()`: Количество точек в диапазоне.
* `first_over_time()`, `last_over_time()`: Первое/последнее значение.
* `stddev_over_time()`, `stdvar_over_time()`: Стандартное отклонение/дисперсия.
* `quantile_over_time(φ, v range-vector)`: φ-квантиль в диапазоне.

### Шаблоны выражений

#### Мониторинг инфраструктуры

* **Утилизация CPU по instance (в %):**

    ```promql
    avg by (instance) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100
    ```

* **Использование памяти (в %):**

    ```promql
    (1 - node_memory_mem_available_bytes / node_memory_mem_total_bytes) * 100
    ```

* **Использование диска (в %):**

    ```promql
    (1 - node_filesystem_avail_bytes / node_filesystem_size_bytes) * 100
    ```

* **Входящий сетевой трафик (байт/сек):**

    ```promql
    rate(node_network_receive_bytes_total[5m])
    ```

#### Мониторинг приложений

* **Доля ошибок HTTP 5xx:**

    ```promql
    sum(rate(http_requests_total{code=~"5.."}[5m]))
    /
    sum(rate(http_requests_total[5m]))
    ```

* **95-й перцентиль времени ответа:**

    ```promql
    histogram_quantile(0.95, 
      sum(rate(http_request_duration_seconds_bucket[5m])) by (le)
    )
    ```

* **RPS (запросов в секунду):**

    ```promql
    sum(rate(http_requests_total[5m]))
    ```

#### Мониторинг Kubernetes

* **Количество подов в состоянии Running:**

    ```promql
    sum(kube_pod_status_phase{phase="Running"})
    ```

* **Использование CPU контейнером (в ядрах):**

    ```promql
    rate(container_cpu_usage_seconds_total[5m])
    ```

* **Использование памяти контейнером:**

    ```promql
    container_memory_usage_bytes
    ```

#### Алертинг

* **Проверка отсутствия метрики (для алертинга):**

    ```promql
    absent(up{job="my-critical-service"})
    ```

* **Сервис недоступен:**

    ```promql
    up{job="api-server"} == 0
    ```

* **Прогноз нехватки диска через 4 часа:**

    ```promql
    predict_linear(node_filesystem_free_bytes[1h], 3600 * 4) < 0
    ```

* **Высокая загрузка CPU (>80% в течение 10 минут):**

    ```promql
    avg by (instance) (irate(node_cpu_seconds_total{mode="idle"}[5m])) * 100 < 20
    ```

> **См. также:** [Rules и алертинг](../rules.md) — создание правил для Alertmanager.

## Дополнительная информация

### Сопоставление векторов

PromQL позволяет производить операции между векторами.

* **Один к одному (One-to-one)**: Операция выполняется между элементами с идентичными наборами лейблов.
* **Многие к одному (Many-to-one)**: Используются ключевые слова `group_left` или `group_right` для указания "главного" вектора, чьи лейблы сохранятся в результате.
* **Фильтрация сопоставления**:
  * `on(<label_list>)`: Указывает, по каким лейблам сопоставлять векторы.
  * `ignoring(<label_list>)`: Указывает, какие лейблы игнорировать при сопоставлении.

**Пример many-to-one с group_left:**

```promql
# Добавляем лейбл job из метрики up к метрике node_cpu_seconds_total
node_cpu_seconds_total * group_left(job) up
```

### Функции для работы с метками (Labels)

* `label_replace(v, dst_label, replacement, src_label, regex)`: Создает новую метку `dst_label` на основе `regex`, примененного к `src_label`.
* `label_join(v, dst_label, separator, src_label_1, ...)`: Объединяет значения нескольких меток в одну.

**Пример label_replace (шаблонизация URL):**

```promql
# Преобразуем /api/users/123 в /api/users/:id
label_replace(
  http_requests_total,
  "templated_path",
  "/api/users/:id",
  "path",
  "/api/users/[^/]+"
)
```

### Прочие функции

* `absent()`: Возвращает `1`, если переданный вектор пуст, иначе — пустой результат.
* `sort()` / `sort_desc()`: Сортировка вектора по значению.
* `round()`, `ceil()`, `floor()`: Функции округления.
* `time()`: Возвращает текущее время в формате Unix time.
* `holt_winters()`: Реализует двойное экспоненциальное сглаживание для прогнозирования и очистки данных от шума.
* `clamp(v, min, max)`: Ограничивает значение в диапазоне.
* `clamp_max(v, max)` / `clamp_min(v, min)`: Ограничивает значение максимумом/минимумом.

### Subqueries (подзапросы)

Subqueries позволяют применять функции диапазона к функциям instant vector:

```promql
# Среднее значение rate за последний час с шагом 5 минут
avg_over_time(rate(http_requests_total[5m])[1h:5m])

# Максимум 95-го перцентиля за день
max_over_time(
  histogram_quantile(0.95, sum(rate(http_duration_bucket[5m])) by (le))[1d:1h]
)
```

## Поведение метрик в реальных сценариях

### (Не)Персистентность метрик

Сервисы, которые выставляют метрики, не живут вечно — они рано или поздно обновятся или перезапустятся. Их метрики при этом сбросятся и начнут отсчитываться с нуля. **Это нормально** и учтено в модели данных и запросов Prometheus.

**Важно помнить:**

* Метрики не про точность, а про усредненные значения. Есть много операций и тонкостей, при которых данные теряют точность, и это нормально — производные, перцентили, разные corner cases. За всем не уследишь, поэтому заранее считаем, что данные не 100% точные. Метрики вообще не подходят для какого-нибудь биллинга, а вот для оценки состояния систем — вполне.

* **Не нужно** писать метрики в БД на своей стороне или как-то обеспечивать их персистентность.

**Как разные функции обрабатывают рестарты:**

| Функция | Тип метрики | Обработка сброса в 0 |
|---------|-------------|---------------------|
| `rate()` | Counter | **Учитывает** сбросы, ожидает возрастание |
| `increase()` | Counter | **Учитывает** сбросы, ожидает возрастание |
| `deriv()` | Gauge | **Не учитывает** сбросы, может сойти с ума |
| `delta()` | Gauge | Не обрабатывает специально, просто разница |

**Примеры:**

* **Counter:** Нормально сделать счетчик «сколько приложение обработало запросов» и начинать его с нуля после рестарта. `rate()` учитывает такую ситуацию.

* **Gauge:** Используется для показателей, которые не отсчитываются с нуля, например, свободная RAM. Когда приложение перезапустилось, метрика сразу будет показывать актуальное значение и периодически его обновлять. `deriv()` не обрабатывает ситуации, когда метрика сбросилась в ноль — обычно это и не нужно.

**Важность для алертинга:**

На первый взгляд может казаться, что некоторые функции похожи и делают одно и то же, а «шторм» метрик при деплоях или когда приложение упало — это секундная мелочь. Но это станет важно, когда вы захотите сделать алерты. С алертами эта особенность станет огромной головной болью, причиной ложных срабатываний, костылей и переписываний. **Лучше сразу разобраться, как ведут себя метрики при рестартах приложений, и пользоваться подходящими функциями в запросах.**

### Реплики приложения

Если у вас есть несколько реплик одного приложения, скорее всего каждая реплика будет писать метрики с одинаковыми лейблами. **Это станет проблемой**, потому что Prometheus соберет с разных реплик одинаковые показания:

```text
# реплика 1:
api_http_requests_total{method="POST", url="/login"} 2
# реплика 2:
api_http_requests_total{method="POST", url="/login"} 3
```

Раз лейблы одинаковые, то эти два значения, собранные в примерно один и тот же timestamp, попадут в один и тот же временной ряд! То есть, у нас будет мешанина из противоречивых данных. При построении графика это будут две очень близкие друг к другу точки. При следующем scrape ситуация повторится.

**Результат:** Сколько запросов было обработано на самом деле всеми репликами? Сначала 5, потом 7, но эту информацию мы уже никак не достанем — она вся сложена в один последовательный ряд.

**Решение:** Каждая реплика должна добавлять какой-то **уникальный для себя лейбл** — имя реплики, hostname, id pod-а в kubernetes, что угодно, позволяющее отличить метрику этой реплики от другой:

```text
# реплика 1:
api_http_requests_total{method="POST", url="/login", replica="app_1"} 2
# реплика 2:
api_http_requests_total{method="POST", url="/login", replica="app_2"} 3
```

Тогда значения сложатся в разные ряды, и можно будет посчитать их сумму, или вывести на графики по отдельности, если понадобится.

### Выбор интервала для range vector

**Для запросов, которые пишутся руками во время экспериментов:**

* Хотите сглаженный график, чтобы было видно, что с ним происходит в целом — берите интервал побольше
* Если нужно видеть, как значение «скачет» — берите поменьше, но не менее 1 минуты (2×scrape_interval, который обычно 30 секунд)

**Для запросов в Grafana:**

* Используйте переменную **`$__rate_interval`** (и ни в коем случае не `$__interval`)
* Важно учитывать текущий масштаб графика

**Важно:** Если вместо Prometheus используется Clickhouse, из-за бага в парсере запросов кликхауса вы не сможете использовать графановские умные интервалы — используйте свой кастомный.
