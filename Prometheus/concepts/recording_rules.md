# Правила записи (Recording Rules)

В Prometheus есть возможность периодически выполнять PromQL-запрос, сохранять его результат как новый, полностью отдельный временной ряд, и делать его доступным для последующих запросов. Этот механизм называется **правилами записи (recording rules)**.

## Зачем нужны Recording Rules?

### 1. Оптимизация производительности

Если у вас есть "тяжелые" запросы (содержащие сложные вычисления или агрегирующие большое количество данных), которые часто используются, например, в дашбордах Grafana, это создает значительную нагрузку на Prometheus. Каждый раз при обновлении дашборда Prometheus вынужден заново выполнять все вычисления.

С помощью recording rules можно предварительно вычислить результат такого запроса и сохранить его в виде новой, простой метрики. Вместо того чтобы каждый раз выполнять сложное вычисление, дашборд будет запрашивать уже готовые, предвычисленные данные, что существенно снижает нагрузку на Prometheus.

### 2. Упрощение сложных запросов и обход ограничений

PromQL не поддерживает вложенные запросы (subqueries) в том же виде, как это делает, например, SQL. Попытка выполнить сложную функцию поверх результата другой сложной функции может закончиться ошибкой.

Например, запрос вида `max_over_time(sum(my_metric)[5m])` не будет работать.

Recording rules позволяют обойти это ограничение. Вы можете создать правило, которое вычисляет внутреннюю часть запроса (`sum(my_metric)`) и сохраняет ее как новую метрику (например, `my_metric:sum`). После этого вы можете легко применить к ней любую другую функцию: `max_over_time(my_metric:sum[5m])`.

### 3. Создание абстракций для внешних систем

Если вы используете метрики из Prometheus во внешних системах (например, для автоматизации масштабирования в Kubernetes), вы создаете зависимость от конкретных имен метрик и их лейблов. Если источник данных (экспортер) изменит названия метрик, вам придется обновлять конфигурацию во всех внешних системах.

Recording rules позволяют создать "абстрактный" слой. Вы можете определить правило, которое берет исходную метрику (с любым названием) и сохраняет ее под стабильным, логичным именем, которое вы контролируете. В этом случае, если оригинальное имя метрики изменится, вам достаточно будет поправить только одно правило записи в Prometheus, и все внешние системы продолжат работать без изменений.

## Недостатки и рекомендации

Несмотря на все преимущества, злоупотреблять правилами записи не стоит. Каждое правило создает новый временной ряд, который хранится в базе данных Prometheus, что **увеличивает потребление дискового пространства**.

**Рекомендация:** Используйте recording rules только тогда, когда это действительно необходимо для оптимизации производительности часто используемых, тяжелых запросов или для упрощения сложных конструкций PromQL.

## Практическое руководство по настройке Rules

### Общие сведения

Правила (Rules) описываются в отдельном конфигурационном файле в формате YAML. Prometheus поддерживает загрузку правил из нескольких файлов. Правила загружаются только при отсутствии ошибок во всех файлах. Для проверки синтаксиса можно использовать утилиту `promtool`.

```bash
promtool check rules /path/to/example.rules.yml
```

**Важно:** Prometheus не отслеживает изменения в файлах с правилами в реальном времени. После любого изменения требуется как минимум выполнить `reload`, чтобы Prometheus применил новые настройки.

Чтобы загрузить правила в Prometheus, список файлов с правилами необходимо указать в основном конфигурационном файле `prometheus.yml`.

```yaml
rule_files:
  - "rules_file1.yml"
  - "rules_file2.yml"
  - "rules/*.yml"
```

### Синтаксис файла с правилами

Все правила объединяются в группы. Правила внутри одной группы выполняются последовательно с регулярным интервалом. Разные группы могут выполняться в разное время для снижения пиковой нагрузки на Prometheus.

```yaml
groups:
  - name: example
    interval: 10s
    rules:
    - record: job:process_cpu_seconds:rate5m
      expr: sum without(instance)(rate(process_cpu_seconds_total[5m]))
      labels:
        team: sre
```

*   `name`: Имя группы правил. Должно быть уникальным.
*   `interval`: (Опционально) Интервал, с которым будут вычисляться правила в группе. По умолчанию используется `global.evaluation_interval`.
*   `record`: Имя новой метрики, которую создаст правило.
*   `expr`: PromQL-выражение для вычисления.
*   `labels`: (Опционально) Список меток, которые будут добавлены к новой метрике.

### Именование Rules

Prometheus рекомендует придерживаться определенного формата именования для правил записи, чтобы упростить их понимание.

**Общий вид:** `level:metric:operations`

1.  `level`: Уровень агрегации на основе лейблов. Обычно включает `job` и другие значимые лейблы.
2.  `metric`: Имя исходной метрики. Суффикс `_total` у счетчиков принято опускать.
3.  `operations`: Список операций и функций, примененных к метрике (например, `rate5m`, `sum`).

**Примеры:**

```yaml
# Рассчитывает рейты для метрики request_latency_seconds_count
- record: instance_path:request_latency_seconds_count:rate5m
  expr: rate(request_latency_seconds_count{job="myjob"}[5m])

# Рассчитывает соотношение ошибок к общему числу запросов
- record: job:request_failures_per_requests:ratio_rate5m
  expr: |
      sum without (instance, path)(rate(request_failures_total[5m]))
    /
      sum without (instance, path)(rate(requests_total[5m]))
```

### Антипаттерны использования Rules

1.  **Не перемещайте значения лейблов в имя метрики.** Это сильно ограничивает возможности дальнейшей агрегации.
2.  **Не создавайте правила для всех метрик по умолчанию.** Это приводит к лишним расходам дискового пространства и ресурсов CPU. Правила нужны в основном для тяжелых, часто используемых запросов.
3.  **Не используйте правила для исправления имен или лейблов.** Для этого существует механизм `relabel_configs`. Создание нового временного ряда через `record` приводит к потере исходной временной метки.

### Практика: Настройка Rules

Следующие шаги выполняются на сервере, где установлен Prometheus.

1.  **Создаем файл с правилами:** `rules.yml`
    ```bash
    cat <<EOF > /etc/prometheus/rules.yml
    groups:
    - name: slurm-edu-example-node-exporter-rules
      rules:
      # Подсчет количества CPU на каждом узле.
      - record: instance:node_cpus:count
        expr: count(node_cpu_seconds_total{mode="idle"}) without (cpu,mode)

      # Утилизация CPU по каждому ядру.
      - record: instance_cpu:node_cpu_seconds_not_idle:rate5m
        expr: sum(rate(node_cpu_seconds_total{mode!="idle"}[5m])) without (mode)

      # Утилизация CPU по каждому режиму (user, system, etc).
      - record: instance_mode:node_cpu_seconds:rate5m
        expr: sum(rate(node_cpu_seconds_total[5m])) without (cpu)

      # Общая утилизация CPU в процентах.
      - record: instance:node_cpu_utilization:ratio
        expr: sum(instance_mode:node_cpu_seconds:rate5m{mode!="idle"}) without (mode) / instance:node_cpus:count
    EOF
    ```

2.  **Проверяем синтаксис правил:**
    ```bash
    promtool check rules /etc/prometheus/rules.yml
    ```

3.  **Добавляем файл с правилами в `prometheus.yml`:**
    Откройте `/etc/prometheus/prometheus.yml` и добавьте путь к файлу в секцию `rule_files`.

    ```yaml
    rule_files:
      - "rules.yml"
    ```

4.  **Проверяем основную конфигурацию:**
    ```bash
    promtool check config /etc/prometheus/prometheus.yml
    ```

5.  **Перезагружаем конфигурацию Prometheus:**
    ```bash
    systemctl reload prometheus.service
    ```
    > **Примечание:** `reload` предпочтительнее, чем `restart`, так как в случае ошибки в конфигурации сервис не остановится, а просто продолжит работать со старой конфигурацией.

6.  **Проверяем в веб-интерфейсе:**
    Откройте UI Prometheus (`http://<ip_адрес>:9090`) и перейдите в раздел **Status -> Rules**. Вы должны увидеть вашу новую группу правил. Новые метрики (например, `instance:node_cpu_utilization:ratio`) станут доступны для запросов.
