
## Определения

*   **Prometheus Pushgateway**: Компонент-посредник в экосистеме Prometheus, предназначенный для решения проблем Pull-модели при работе с короткоживущими задачами (например, cron-скрипты), которые могут завершиться до очередного опроса. Он позволяет собирать метрики от таких периодических задач, которые завершаются до того, как Prometheus успеет их опросить.

---

## Основные понятия

Pushgateway — это компонент-посредник в экосистеме Prometheus, предназначенный для одного специфического случая: приёма метрик от короткоживущих или периодических задач, которые завершаются быстрее, чем Prometheus успевает их опросить (scrape).

Этот компонент является частью общей **[концепции наблюдаемости (observability)](../Concepts/Observability_and_Monitoring/observability_overview.md)** и иногда используется при **[проектировании мониторинга в распределенных системах](../Concepts/Observability_and_Monitoring/designing_high-load_monitoring_in_distributed_systems.md)**, однако его применение требует понимания ограничений.

### Назначение и принцип работы

В стандартной pull-модели Prometheus сам решает, когда и какие сервисы опрашивать. Однако некоторые задачи, например, `cron-job` для резервного копирования, запускаются, выполняются несколько секунд или минут и завершаются. Prometheus может просто не успеть их "поймать" для сбора метрик.

Pushgateway решает эту проблему, выступая в роли кеша для метрик:
1.  Короткоживущая задача по завершении своей работы **отправляет (push)** свои метрики (например, `backup_duration_seconds`, `backup_status 1`) в Pushgateway.
2.  Prometheus, в свою очередь, по своему обычному расписанию **опрашивает (pull)** Pushgateway как постоянно доступный таргет и забирает из него последние сохраненные метрики.

### Когда использовать Pushgateway (Правильный сценарий)

Единственный легитимный сценарий использования — это сбор метрик от **сервисов, которые не могут быть опрошены**. В первую очередь, это batch-задачи или скрипты, которые запускаются по расписанию и существуют короткое время.

### Анти-паттерны (Когда Pushgateway использовать НЕЛЬЗЯ)

**ВНИМАНИЕ:** Попытка использовать Pushgateway для обхода стандартной pull-модели и превращения Prometheus в push-систему является **грубейшей архитектурной ошибкой**.

Идея использовать Pushgateway для перевода всего мониторинга на push-модель является ошибочной. Этот компонент следует использовать с осторожностью, помня о его особенностях:

1.  **Потеря метрики `up`:** Prometheus всегда будет показывать, что Pushgateway доступен (`up = 1`), но это ничего не говорит о работоспособности самой задачи, которая отправляет метрики. Вы не сможете автоматически определить, "жива" ли ваша задача, так как Prometheus опрашивает посредника, а не сам сервис.
2.  **Единая точка отказа:** Если Pushgateway выйдет из строя, вы потеряете метрики от всех задач, которые в него пишут.
3.  **"Вечное" хранение метрик:** Pushgateway не удаляет метрики автоматически после их сбора Prometheus'ом. Он хранит их до тех пор, пока они не будут удалены вручную через его API. Это может привести к тому, что Prometheus будет вечно собирать устаревшие метрики от уже не работающих задач, создавая иллюзию актуальности.
4.  **Сложная логика группировки**: Pushgateway требует, чтобы клиенты сами управляли своими метками (особенно `instance`), что усложняет конфигурацию.

> **Вывод:** Если сервис можно опросить (scrape) — его нужно опрашивать. Используйте Pushgateway только для короткоживущих задач. Подробнее об этом также упомянуто в **[общем обзоре Prometheus](./overview.md)**.

### Группировка метрик

Ключ группировки метрик в Pushgateway — это метка `job` вместе со всеми остальными метками, указанными в URL. Например, метрики, отправленные по URL:
- `/metrics/job/job1/instance/a`
- `/metrics/job/job1/instance/b`

будут принадлежать к разным группам.

Если значение метки содержит спецсимволы (например, `/`), его необходимо закодировать в **base64** и добавить к имени метки суффикс `@base64`.
- **Пример для `path="/var/log"`:** `/metrics/job/my_job/path@base64/L3Zhci9lb2c=`

### Методы HTTP API

-   `POST`: **Добавляет или обновляет** метрики в указанной группе. Существующие в группе метрики, которых нет в теле запроса, остаются без изменений.
-   `PUT`: **Полностью заменяет** все метрики в группе на те, что переданы в теле запроса. Если выполнить `PUT` с пустым телом, это приведет к удалению всех метрик для данной группы.
-   `DELETE`: **Удаляет всю группу** метрик, идентифицируемую по URL. Это основной способ борьбы с "устаревшими" метриками.

### Управление жизненным циклом метрик

Так как Pushgateway не удаляет метрики автоматически, за их жизненный цикл отвечает клиент. Лучшая практика — задача должна сама удалять свои метрики перед завершением работы.

**Пример:** Удаление метрик для `instance=server1` в `job=my_batch_job`.
```bash
curl -X DELETE http://localhost:9091/metrics/job/my_batch_job/instance/server1
```
Эту команду следует встраивать в конец вашего batch-скрипта.

## Практические сценарии

### Установка

Подробные инструкции по ручной установке Pushgateway в виде `systemd`-сервиса находятся в заметке **[Руководство по ручной установке](./installation/from_binary.md#5-установка-pushgateway)**.

### Отправка метрик

Метрики отправляются в Pushgateway с помощью HTTP-запроса. Группировка метрик происходит на основе URL.

**Пример:** Отправка метрик о результате выполнения batch-задачи.
```bash
# Определяем метрики и их значения
cat <<EOF | curl --data-binary @- http://localhost:9091/metrics/job/my_batch_job/instance/server1
# TYPE batch_duration_seconds gauge
# HELP batch_duration_seconds Duration of the batch job in seconds
batch_duration_seconds 34.4

# TYPE batch_records_processed_total counter
# HELP batch_records_processed_total Total number of processed records
batch_records_processed_total 1024

# TYPE batch_last_success_timestamp gauge
# HELP batch_last_success_timestamp Timestamp of the last successful completion
batch_last_success_timestamp $(date +%s)
EOF
```
*   `job/my_batch_job` и `instance/server1` станут метками `job="my_batch_job"` и `instance="server1"` для всех отправленных метрик.

### Настройка Prometheus

В конфигурационный файл `prometheus.yml` необходимо добавить новую задачу для сбора метрик с Pushgateway.

```yaml
# /etc/prometheus/prometheus.yml

scrape_configs:
  - job_name: 'pushgateway'
    # honor_labels: true — критически важная настройка.
    # Она говорит Prometheus не перезаписывать метки job и instance,
    # которые уже были установлены клиентом при отправке в Pushgateway.
    honor_labels: true
    static_configs:
      - targets: ['localhost:9091']
```
После перезагрузки конфигурации Prometheus начнет собирать метрики, которые хранятся в Pushgateway.

### Конфигурация в Kubernetes

При развертывании в Kubernetes Pushgateway может быть включен и настроен с помощью Helm-чарта Prometheus, как описано в заметке о **[конфигурации Helm-чарта](./kubernetes/helm_chart_configuration.md)**.

## Дополнительная информация

### Ключи запуска

| Флаг | Значение по умолчанию | Описание |
| :--- | :--- | :--- |
| `--web.listen-address` | `:9091` | Адрес и порт, который будет слушать Pushgateway. |
| `--web.telemetry-path`| `/metrics` | Путь к собственным метрикам Pushgateway. |
| `--persistence.file` | `-` | Файл для сохранения метрик между перезапусками. Если не указан, метрики хранятся в памяти. |
| `--persistence.interval`| `5m` | Интервал сохранения данных в файл. |
| `--web.enable-admin-api`| `false` | Разрешает использование административных эндпоинтов (например, для очистки всех метрик). |
| `--log.level` | `info` | Уровень логирования (`debug`, `info`, `warn`, `error`). |
