# Pushgateway

Компонент-посредник в экосистеме [Prometheus](./overview.md) для приёма метрик от короткоживущих задач.

## Определение

**Pushgateway** — это промежуточный сервис (receiver), предназначенный для сбора метрик от эфемерных (ephemeral) или пакетных (batch) задач, которые завершаются быстрее, чем Prometheus успевает их опросить по стандартному интервалу скрейпинга.

| Параметр | Значение |
|---|---|
| **Назначение** | Буферизация метрик для кратковременных задач |
| **Порт по умолчанию** | `9091` |
| **Репозиторий** | [prometheus/pushgateway](https://github.com/prometheus/pushgateway) |

> **Установка:** подробные инструкции находятся в разделе [Установка Pushgateway](./installation/pushgateway_installation.md).

## Основные концепции

### Принцип работы

Pushgateway позволяет реализовать push-модель для задач, которые невозможно опросить стандартным способом:

| Шаг | Действие |
|---|---|
| 1 | Кратковременная задача завершает работу и отправляет метрики в Pushgateway методом **push** |
| 2 | Prometheus по расписанию опрашивает Pushgateway методом **pull** и забирает сохранённые данные |

Подробно: [Scrape-модель](./overview.md#scrape-модель), [Стратегии сбора метрик](../Concepts/Observability_and_Monitoring/metrics_collection_strategies.md).

### Когда использовать

Pushgateway рекомендуется использовать только в тех сценариях, где сервис **не может быть опрошен**:

- Batch-задачи (CronJob), выполняющиеся реже интервала скрейпинга Prometheus.
- Эфемерные задачи, которые исчезают сразу после выполнения.
- Сервисы за Firewall или NAT, до которых Prometheus не может дотянуться.

### Антипаттерны

Использование Pushgateway в качестве общей точки сбора для перевода всей системы на push-модель является архитектурной ошибкой.

| Проблема | Описание |
|---|---|
| **Потеря метрики `up`** | Prometheus показывает `up=1` для самого Pushgateway, что не отражает реальное состояние исходной задачи |
| **Единая точка отказа** | Отказ Pushgateway приводит к потере метрик от всех подключённых к нему задач |
| **Отсутствие автоматической очистки** | Метрики хранятся в Pushgateway «вечно» до явного удаления, что приводит к сбору устаревших данных |
| **Риск коллизий лейблов** | Управление метками (особенно `instance`) перекладывается на клиента, что усложняет консистентность данных |

**Правило:** если сервис доступен по сети для опроса — его необходимо опрашивать напрямую.

### Группировка метрик

Для изоляции метрик разных задач используется ключ группировки, состоящий из метки `job` и дополнительных пользовательских лейблов, передаваемых в URL.

| Пример URL | Результирующие метки |
|---|---|
| `/metrics/job/backup/instance/db1` | `job="backup", instance="db1"` |
| `/metrics/job/backup/instance/db2` | `job="backup", instance="db2"` |

Если значения лейблов содержат спецсимволы, используется кодирование **base64** с суффиксом `@base64`:
`/metrics/job/my_job/path@base64/L3Zhci9sb2c=`

### HTTP API

Pushgateway предоставляет API для управления группами метрик:

| Метод | Поведение |
|---|---|
| **POST** | Добавляет или обновляет метрики в указанной группе. Метрики, не переданные в текущем запросе, но уже существующие в группе, сохраняются. |
| **PUT** | Полностью заменяет содержимое группы. PUT с пустым телом эквивалентен удалению. |
| **DELETE** | Удаляет всю группу метрик по указанному пути. |

### Управление жизненным циклом данных

Pushgateway не удаляет метрики автоматически после того, как Prometheus их собрал. Клиентское приложение должно самостоятельно отправлять запрос на удаление после завершения работы:

```bash
curl -X DELETE http://localhost:9091/metrics/job/my_batch_job/instance/server1
```

## Практические сценарии

### Отправка метрик из Bash-скрипта

Пример интеграции в CronJob для мониторинга длительности и статуса бэкапа:

```bash
cat <<EOF | curl --data-binary @- http://localhost:9091/metrics/job/backup/instance/db-server
# HELP backup_duration_seconds Duration of backup job in seconds
# TYPE backup_duration_seconds gauge
backup_duration_seconds 34.4
# HELP backup_status Status of backup (1=success, 0=failure)
# TYPE backup_status gauge
backup_status 1
EOF
```

### Настройка Prometheus для сбора данных

Для корректного сохранения меток, установленных клиентом, в конфигурации Prometheus необходимо использовать параметр `honor_labels`.

```yaml
scrape_configs:
  - job_name: 'pushgateway'
    honor_labels: true
    static_configs:
      - targets: ['localhost:9091']
```

> **Kubernetes:** примеры настройки в облачных средах см. в разделе [Конфигурация компонентов Kube-Prometheus-Stack](./kubernetes/Kube_Prometheus_Stack_Helm/other_components_config.md).

## Дополнительная информация

### Альтернативные решения

| Решение | Подход | Сценарий |
|---|---|---|
| **Pushgateway** | Промежуточный буфер | Классические CronJob, пакетная обработка |
| **Telegraf** | Агрегатор-конвертер | Множество разнородных источников данных |
| **StatsD Exporter** | Транслятор протоколов | Приложения, изначально использующие StatsD |

### Ключевые параметры запуска

| Флаг | По умолчанию | Описание |
|---|---|---|
| `--web.listen-address` | `:9091` | Адрес и порт веб-интерфейса |
| `--persistence.file` | `-` | Путь к файлу для сохранения метрик при перезагрузке (если пусто — хранение только в RAM) |
| `--persistence.interval` | `5m` | Частота сброса данных из памяти на диск |
| `--web.enable-admin-api` | `false` | Включение API администратора (позволяет удалять все группы сразу) |
