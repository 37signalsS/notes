# Обзор Prometheus

В экосистеме Cloud Native [Prometheus](./overview.md) является стандартом де-факто для мониторинга и оповещения. Это система с открытым исходным кодом, входящая в состав CNCF (второй проект после [Kubernetes](../Kubernetes/kubernetes_overview.md) по значимости), предназначенная для сбора и обработки метрик в реальном времени.

> **Важно:** Актуальная документация описывает **Prometheus v3.x** (релиз ноября 2024 года). Версии 2.x перешли в статус поддержки, многие функции (Native Histograms, OTLP) стали стандартными или значительно улучшены.

## Определения

*   **Prometheus** — это автономная система мониторинга, которая собирает метрики (числовые показатели) с контролируемых объектов, сохраняет их в виде временных рядов (Time Series), позволяет выполнять запросы на языке PromQL и генерировать оповещения.
*   **Временной ряд (Time Series)** — последовательность значений одной метрики, распределённых во времени, идентифицируемая уникальным набором меток (labels).
*   **Скрапинг (Scraping)** — основной метод сбора данных в Prometheus, при котором сервер сам опрашивает HTTP-эндпоинты целей.
*   **Экспортер (Exporter)** — вспомогательный агент, который транслирует метрики из сторонних систем (БД, ОС, сети) в формат, понятный Prometheus.

## Основные концепции

### Многомерная модель данных

Prometheus идентифицирует данные через имя метрики и набор пар `ключ=значение` (labels). 
*   **UTF-8 Support (v3.x):** Начиная с версии 3.0, Prometheus поддерживает любые символы UTF-8 в именах метрик и меток, что критично для полной совместимости с OpenTelemetry (например, точки в именах: `http.server.duration`).
*   **Кардинальность:** Количество уникальных комбинаций меток напрямую влияет на потребление памяти. Подробнее: [Лейблы и кардинальность](./concepts/labels_and_cardinality.md).

### Методы сбора данных

| Метод | Описание | Применение |
| :--- | :--- | :--- |
| **Pull (Scraping)** | Prometheus опрашивает `/metrics` по HTTP. | Стандарт для долгоживущих сервисов. |
| **Native OTLP (v3.x)** | Прямой приём данных по протоколу OTLP (Push). | Интеграция с OpenTelemetry без лишних агентов. |
| **Pushgateway** | Промежуточное звено для кратковременных задач. | Cronjobs, Batch-скрипты. |

### Нативные гистограммы (Native Histograms)

В Prometheus v3.x **Native Histograms** стали стабильной технологией. В отличие от "классических" гистограмм, они:
*   Не требуют ручного определения границ бакетов (`le` label).
*   Занимают значительно меньше места в хранилище (один временной ряд вместо десятков).
*   Обеспечивают высокую точность за счёт динамической экспоненциальной сетки.

### Архитектура системы

| Компонент | Роль в системе | Ссылка |
| :--- | :--- | :--- |
| **Prometheus Server** | Сбор (Scrape/OTLP), хранение (TSDB), вычисления. | — |
| **TSDB** | Локальное хранилище временных рядов на диске. | [TSDB — концепции](./concepts/tsdb.md) |
| **PromQL Engine** | Выполнение запросов. В v3 включает "Explain" и Query Builder. | [PromQL](./concepts/promql/functions.md) |
| **Alertmanager** | Дедупликация, группировка и доставка оповещений. | [Alertmanager](./alertmanager.md) |
| **Service Discovery** | Автоматическое обнаружение целей (K8s, EC2, Consul). | [Relabeling](./service_discovery_and_relabeling.md) |
| **Remote Storage** | Интеграция с внешними БД для долгого хранения. | [Remote Read/Write](./scaling/remote_read_write.md) |

### Пользовательский интерфейс (New Web UI)

В версии 3.0 представлен полностью обновлённый интерфейс на базе React и Mantine:
*   **Tree-view Explorer:** Визуализация сложных запросов в виде иерархии (наследие PromLens).
*   **Explain Tab:** Детальное объяснение того, как вычисляется запрос и что означают результаты.
*   **Metrics Explorer:** Улучшенный поиск по доступным метрикам и их метаданным.

## Практические сценарии

### Жизненный цикл метрики в современной среде

1.  **Инструментация:** Приложение использует клиентскую библиотеку или SDK OpenTelemetry.
2.  **Передача данных:**
    *   *Классика:* Приложение выставляет `/metrics` для сбора сервером.
    *   *Современно:* Приложение пушит данные в Prometheus по протоколу OTLP (требуется флаг `--web.enable-otlp-receiver`).
3.  **Обработка:** Prometheus применяет [правила записи (Recording Rules)](./rules.md) для оптимизации тяжелых расчетов.
4.  **Анализ:** Инженер использует вкладку "Explain" в новом UI для отладки сложного PromQL-запроса.
5.  **Оповещение:** При срабатывании [правила алертинга](./rules.md) данные уходят в Alertmanager, который маршрутизирует их в Slack или PagerDuty.

### Сравнение с альтернативами (2025-2026)

| Характеристика | Prometheus | Zabbix | VictoriaMetrics |
| :--- | :--- | :--- | :--- |
| **Модель сбора** | Pull / OTLP Push | Гибридная (Agent/Push) | Pull / Push (vmagent) |
| **Масштабирование** | Через Remote Write | Кластеризация БД | Нативное (Cluster mode) |
| **Хранение** | TSDB (локально) | Реляционная БД | TSDB (оптимизировано) |
| **Сложность** | Средняя (K8s-native) | Высокая (Legacy-friendly) | Низкая (Single binary) |

## Дополнительная информация

### Масштабирование и долгосрочное хранение

Для преодоления ограничений одиночного сервера Prometheus используются внешние решения через протокол **Remote Write 2.0**:
*   **[Grafana Mimir](../Mimir/mimir_overview.md)** — горизонтальное масштабирование и мульти-тенантность.
*   **[VictoriaMetrics](../VictoriaMetrics/overview.md)** — высокая производительность и плотность хранения.
*   **[Thanos](./scaling/thanos_overview.md)** — неограниченное хранение в S3/GCS.
