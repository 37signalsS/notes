# Prometheus: Обзор

## Определения

**Prometheus** — это система мониторинга и оповещения с открытым исходным кодом, ставшая стандартом де-факто в Cloud Native экосистеме. Изначально он разрабатывался компанией SoundCloud, инженеры которой вдохновлялись системой **Borgmon** от Google. Позже проект был передан в Cloud Native Computing Foundation (CNCF), где стал одним из ключевых проектов после [Kubernetes](../Kubernetes/kubernetes_overview.md).

Со временем ограничения Prometheus в масштабировании и долгосрочном хранении привели к появлению таких решений, как [Mimir](../Mimir/mimir_overview.md) и [VictoriaMetrics](../VictoriaMetrics/overview.md).

### Парадигмы мониторинга

В мире мониторинга можно выделить две основные парадигмы, и Prometheus является ярким представителем второй:

1.  **Fault Monitoring (Мониторинг отказов)**:
    *   **Цель**: Ответить на вопрос "Работает ли сервис прямо сейчас?".
    *   **Принцип**: Система периодически проверяет бинарное состояние сервиса (up/down).
    *   **Примеры**: Nagios, Icinga, [Zabbix](../Zabbix/zabbix_overview.md).

2.  **History/Trend Monitoring (Исторический или трендовый мониторинг)**:
    *   **Цель**: Анализировать поведение системы во времени.
    *   **Принцип**: Система непрерывно собирает и хранит временные ряды метрик (например, загрузку CPU) для анализа трендов и прогнозирования.
    *   **Примеры**: Prometheus, Graphite.

Prometheus фокусируется на **History Monitoring**, что позволяет использовать мощный язык запросов для сложного анализа и проактивного алертинга.

### Whitebox vs Blackbox Мониторинг

*   **Whitebox Monitoring (Мониторинг "белого ящика"):** Мониторинг внутренних механизмов системы, когда мы знаем, как она работает и какие метрики отдает. Prometheus преимущественно ориентирован на этот подход.
*   **Blackbox Monitoring (Мониторинг "черного ящика"):** Мониторинг сервиса снаружи, без знания его внутренней структуры (например, проверка доступности порта). Реализуется с помощью **[Blackbox Exporter](./exporters.md#blackbox_exporter)**.

## Базовые концепции: Архитектура и Философия

### Ключевые философские принципы

#### Pull-модель (Модель опроса)
В отличие от многих систем, использующих push-модель, Prometheus работает по **pull-модели**. Сервер Prometheus сам активно опрашивает (scrapes) целевые сервисы по HTTP для сбора метрик.

*   **Преимущества:** Централизованный контроль, простота экспортеров и возможность автоматически обнаруживать неработающие инстансы.
*   **Сравнение:** Подробное сравнение различных стратегий сбора метрик (Push, Pull, из логов) рассмотрено в заметке: **[Стратегии сбора метрик](../Concepts/Observability_and_Monitoring/metrics_collection_strategies.md)**.

#### Многомерная модель данных
Данные в Prometheus хранятся в виде **временных рядов (time series)**, которые идентифицируются **именем метрики** и набором пар ключ-значение, называемых **лейблами (labels)** (например, `http_requests_total{method="POST"}`).

> Подробнее о том, как правильно использовать лейблы и избегать проблем с производительностью, читайте в заметке **[Лейблы и кардинальность](./concepts/labels_and_cardinality.md)**.

#### [Service Discovery](./service_discovery_and_relabeling.md)
В динамичных средах, таких как Kubernetes, Prometheus автоматически обнаруживает новые источники метрик (таргеты) благодаря интеграции с API Kubernetes, [Consul](../Consul/consul_overview.md), AWS EC2 и другими системами. Это позволяет адаптироваться к изменениям в инфраструктуре без ручного вмешательства.

#### Язык запросов PromQL
Для работы с данными используется мощный функциональный язык запросов **[PromQL (Prometheus Query Language)](./concepts/promql.md)**. Он позволяет выбирать, агрегировать и выполнять сложные вычисления над временными рядами в реальном времени.

### Архитектурные компоненты

1.  **Prometheus Server:**
    Центральный компонент, написанный на Go, который выполняет опрос, хранение и обработку метрик.
    *   **Scraping Engine:** Движок, отвечающий за опрос таргетов по HTTP (pull-модель).
    *   **[TSDB (Time Series Database)](./concepts/tsdb.md):** Встроенная база данных временных рядов.
    *   **PromQL Engine:** Движок для выполнения запросов на языке PromQL.
    *   **Web UI:** Встроенный веб-интерфейс (по умолчанию на порту `:9090`), который имеет ограниченный функционал и используется в основном для отладки и проверки состояния. Основные разделы интерфейса:
        *   **Alerts:** Показывает активные алерты и их состояние, а также из каких файлов были загружены правила.
        *   **Graph:** Позволяет выполнять запросы на языке PromQL (с автодополнением) и просматривать результаты в виде таблицы или интерактивного графика.
        *   **Status:** Содержит различную отладочную информацию:
            *   `Runtime & Build Information`: Информация о времени работы сервера, используемых ресурсах и т.д.
            *   `Command-Line Flags`: Ключи, с которыми был запущен Prometheus.
            *   `Configuration`: Текущая загруженная [конфигурация](./configuration.md) Prometheus.
            *   `Rules`: Загруженные [правила алертинга и записи](./rules.md), время их последней проверки и длительность выполнения.
            *   `Targets`: Все настроенные цели (sources) для сбора метрик и их текущее состояние (UP/DOWN).
            *   `Service Discovery`: Показывает все цели, обнаруженные через механизмы Service Discovery, и их мета-лейблы.

2.  **[Exporters (Экспортеры)](./exporters.md):**
    Вспомогательные утилиты, которые запускаются на целевых системах, собирают с них данные и предоставляют их в формате Prometheus по HTTP-эндпоинту. Примеры: `node_exporter` (метрики хоста), `cadvisor` (метрики контейнеров).

3.  **Service Discovery:** В динамических средах (Kubernetes, облака) отслеживать IP-адреса вручную невозможно. Prometheus автоматически обнаруживает новые таргеты для опроса благодаря интеграции с API Kubernetes, Consul, AWS EC2 и другими системами.

4.  **[Pushgateway](../pushgateway.md):** Компонент-посредник для сбора метрик от кратковременных или периодически запускаемых задач (например, cron-задач, batch-скриптов), которые завершаются раньше, чем Prometheus успевает их опросить. Подробнее о принципах работы, случаях использования и анти-паттернах Pushgateway см. в отдельной заметке.


5.  **Alertmanager:** Управляет оповещениями. Он получает от Prometheus уведомления о сработавших правилах (алертах), а затем дедуплицирует, группирует и отправляет их в нужные каналы (Slack, PagerDuty, email). Подробнее см. в [alertmanager](./alertmanager.md).

6.  **Визуализация: Grafana**: Хотя у Prometheus есть собственный простой веб-интерфейс для выполнения запросов (PromQL) и построения графиков, стандартом для визуализации метрик является **[Grafana](../Grafana/grafana_overview.md)**. Grafana подключается к Prometheus как к источнику данных и позволяет создавать сложные, интерактивные дашборды для наглядного представления состояния системы.

## Сравнение с традиционными системами

В отличие от старых систем, таких как Zabbix, Prometheus изначально создавался для динамичных облачных сред и лучше справляется с большим количеством метрик и высокой кардинальностью, характерной для микросервисов.

| Характеристика          | Prometheus                                                                   | Zabbix (традиционный подход)                                                        |
| :---------------------- | :--------------------------------------------------------------------------- | :---------------------------------------------------------------------------------- |
| **Архитектура**         | Микросервисная, распределенная. Каждый компонент отвечает за свою задачу.    | Монолитная. Единый сервер, который выполняет множество функций.                     |
| **Хранение метрик**     | Встроенная Time Series Database (TSDB), оптимизированная для временных рядов. | Реляционная база данных (PostgreSQL, MySQL), что может приводить к проблемам производительности при большом объеме временных рядов и очередях. |
| **Модель сбора данных** | **Pull-модель (опрос)**: Сервер Prometheus сам подключается к экспортерам и забирает метрики. Позволяет эффективно обнаруживать недоступность целей. Имеет компонент Pushgateway для кратковременных задач. | **Push-модель (отправка)**: Агенты активно отправляют метрики на сервер. Активные проверки агента могут имитировать pull-модель, но это не решает фундаментальных проблем архитектуры. |
| **Гибкость/Масштабируемость** | Высокая. Легко масштабируется горизонтально за счет распределения компонентов и pull-модели.   | Ограниченная. Масштабирование усложняется из-за монолитности и узких мест в БД при большом количестве push-агентов.     |
| **Язык запросов**       | PromQL — мощный функциональный язык для анализа временных рядов.               | Менее гибкие механизмы фильтрации и агрегации данных.                              |
| **Целевая среда**       | Динамичные облачные среды, Kubernetes, микросервисы.                         | Более статичные инфраструктуры, физические сервера, традиционные приложения.       |
| **Проблемы**            | Не всегда удобен для мониторинга кратковременных задач (решается Pushgateway). | Проблемы с производительностью и очередями при высокой нагрузке, сложность в работе с метриками высокой кардинальности.                               |
