# Обзор Prometheus

## Парадигмы мониторинга

В мире мониторинга можно выделить две основные парадигмы:

1.  **Fault Monitoring (Мониторинг отказов)**:
    *   **Цель**: Ответить на вопрос "Работает ли сервис прямо сейчас?".
    *   **Принцип**: Система с определенной периодичностью проверяет доступность сервиса или соответствие метрики пороговому значению (например, доступен ли 80-й порт). Если несколько проверок подряд оказываются неудачными, система генерирует алерт о том, что сервис неисправен.
    *   **Примеры систем**: Nagios, Icinga, Zabbix.
    *   **Результат**: Бинарное состояние (up/down, ok/critical). Помогает реагировать на уже случившиеся инциденты.

2.  **History/Trend Monitoring (Исторический или трендовый мониторинг)**:
    *   **Цель**: Анализировать поведение системы во времени.
    *   **Принцип**: Система непрерывно собирает и хранит временные ряды метрик (например, загрузку CPU, количество запросов в секунду). Эти данные используются для построения графиков и анализа трендов.
    *   **Примеры систем**: Prometheus, Graphite.
    *   **Результат**: Глубокое понимание динамики системы. Позволяет не только находить "узкие места" и причины сбоев постфактум (например, увидев резкий рост нагрузки после выката новой версии), но и прогнозировать будущие проблемы. Например, анализируя скорость заполнения диска, можно предсказать, когда на нем закончится место, и принять меры заранее, а не в момент отказа.

Prometheus является ярким представителем **History Monitoring**. Он фокусируется на сборе и анализе метрик как временных рядов, что позволяет использовать мощный язык запросов PromQL для сложного анализа и проактивного алертинга.

Prometheus — это система мониторинга и оповещения с открытым исходным кодом, изначально разработанная в SoundCloud. С момента своего создания в 2012 году, Prometheus стал одним из ключевых проектов Cloud Native Computing Foundation (CNCF) после Kubernetes.

## Ключевые особенности и философия

### Pull-модель (Модель опроса)

В отличие от многих других систем, которые работают по push-модели (когда источники сами отправляют данные), Prometheus использует **pull-модель**. Это означает, что сервер Prometheus сам активно опрашивает (scrapes) целевые эндпоинты (endpoints) по HTTP для сбора метрик.

*   **Преимущества:**
    *   Централизованный контроль над тем, как часто и какие цели опрашивать.
    *   Простота настройки экспортеров: им нужно только предоставить HTTP-эндпоинт с метриками.
    *   Возможность обнаруживать неработающие инстансы, если они не отвечают на запросы.

### Service Discovery

Современные инфраструктуры, особенно в облаках и Kubernetes, очень динамичны. Prometheus автоматически обнаруживает новые источники метрик (таргеты) благодаря интеграции с различными механизмами Service Discovery:
*   API Kubernetes, Consul, AWS EC2 и др.
*   Статические конфигурационные файлы.

Это позволяет Prometheus адаптироваться к изменениям в инфраструктуре без ручного вмешательства.

### Многомерная модель данных

Данные в Prometheus хранятся в виде **временных рядов (time series)**, которые идентифицируются:
1.  **Именем метрики** (например, `http_requests_total`).
2.  Набором пар **ключ-значение**, называемых **лейблами (labels)** (например, `method="POST"`, `path="/api"`).

Эта модель позволяет гибко агрегировать и фильтровать данные с помощью языка запросов PromQL.

## Архитектура

Prometheus представляет собой экосистему компонентов, где центральную роль играет сам сервер.

1.  **Prometheus Server:** Основной компонент, который выполняет опрос метрик, их хранение и обработку.
    *   **Scraping Engine:** Движок, отвечающий за опрос таргетов по HTTP (pull-модель).
    *   **TSDB (Time Series Database):** Встроенная база данных временных рядов, оптимизированная для хранения и запросов метрик.
    *   **PromQL Engine:** Движок для выполнения запросов на языке PromQL.
    *   **Web UI:** Встроенный веб-интерфейс для выполнения запросов и просмотра статуса системы.

2.  **Exporters (Экспортеры):** Так как Prometheus сам опрашивает цели, ему нужны "поставщики" метрик. Экспортеры — это вспомогательные утилиты, которые запускаются на целевых системах, собирают с них данные и предоставляют их в формате Prometheus по HTTP-эндпоинту. Примеры:
    *   `node_exporter`: для метрик хост-системы (CPU, RAM, диск).
    *   `cadvisor`: для метрик контейнеров.
    *   Сотни других для баз данных, веб-серверов, оборудования и т.д.

3.  **Service Discovery:** В динамических средах (Kubernetes, облака) отслеживать IP-адреса вручную невозможно. Prometheus автоматически обнаруживает новые таргеты для опроса благодаря интеграции с API Kubernetes, Consul, AWS EC2 и другими системами.

4.  **Pushgateway:** Компонент, решающий проблему сбора метрик с кратковременных задач (например, cron-задач). Такие задачи не могут ждать, пока Prometheus их опросит. Вместо этого они "проталкивают" (push) свои метрики в Pushgateway, который Prometheus уже опрашивает как обычный, долгоживущий таргет.

5.  **Alertmanager:** Управляет оповещениями. Он получает от Prometheus уведомления о сработавших правилах (алертах), а затем дедуплицирует, группирует и отправляет их в нужные каналы (Slack, PagerDuty, email).

## Сравнение с традиционными системами

В отличие от старых систем, таких как Zabbix, которые были разработаны для более статичной инфраструктуры, Prometheus изначально создавался для динамических облачных сред. Он лучше справляется с большим количеством метрик и высокой кардинальностью, характерной для микросервисных архитектур.
