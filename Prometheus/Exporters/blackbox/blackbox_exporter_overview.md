# Blackbox Exporter — Обзор и основные концепции

## Определения

**Blackbox Exporter** — официальный инструмент Prometheus для реализации **blackbox-мониторинга** (внешнего наблюдения). В отличие от классических экспортеров (например, Node Exporter), он не собирает внутренние метрики системы или приложения, а имитирует поведение внешнего клиента, проверяя доступность, корректность и производительность сервисов по сети.

*   **Multi-Target Exporter:** один экземпляр экспортера может опрашивать неограниченное количество целей, что упрощает масштабирование.
*   **Поддерживаемые протоколы:** HTTP(S) (включая HTTP/2 и HTTP/3), TCP, ICMP (Ping), DNS, gRPC, Unix Domain Sockets.
*   **Актуальная версия:** `v0.28.0` (2025/2026), полностью совместим с экосистемой Prometheus 3.0.
*   **Порт по умолчанию:** `9115`.
*   **Репозиторий:** [prometheus/blackbox_exporter](https://github.com/prometheus/blackbox_exporter).

**Ключевые понятия:**
*   **Probe (проверка)** — единичная выполненная проверка цели (например, HTTP GET или ICMP Ping).
*   **Module (модуль)** — именованный набор настроек в `blackbox.yml`, определяющий тип проверки, таймаут и критерии успешности.
*   **Prober (исполнитель проверки)** — компонент, реализующий конкретный протокол (http, tcp, icmp, dns, grpc, unix).
*   **Target (цель)** — проверяемый хост, URL, IP-адрес или путь к сокету.
*   **Synthetic Monitoring (синтетический мониторинг)** — подход, при котором система периодически имитирует действия реального пользователя для проверки работоспособности сервиса.

## Основные концепции

### Сравнение подходов: Whitebox vs Blackbox

| Характеристика | Whitebox (Внутренний) | Blackbox (Внешний) |
| :--- | :--- | :--- |
| **Объект наблюдения** | Внутреннее состояние (CPU, RAM, очереди) | Внешнее поведение (доступность, SSL, время ответа) |
| **Метод сбора** | Прямой опрос `/metrics` приложения | Имитация запроса пользователя через прокси-экспортер |
| **Точка зрения** | "Как чувствует себя система?" | "Видит ли пользователь сервис?" |
| **Пример** | `node_exporter`, `mysqld_exporter` | `blackbox_exporter` |
| **Применение** | Отладка, профилирование, внутренние алерты | Контроль SLA/SLO, проверка сетевой связности |

### Принцип работы (Multi-Target Scrape)

Blackbox Exporter использует паттерн делегированного опроса. Prometheus отправляет запрос не на целевой сервис, а на эндпоинт `/probe` самого экспортера, передавая параметры цели в URL.

1.  **Запрос (Scrape):** Prometheus обращается к `http://blackbox:9115/probe?target=example.com&module=http_2xx`.
2.  **Выполнение (Probing):** Экспортер инициирует проверку (например, GET-запрос к `example.com`), используя настройки указанного модуля.
3.  **Сбор и возврат:** Экспортер собирает результаты (время ответа, коды состояния, детали TLS) и возвращает их Prometheus в текстовом формате.

**Важные эндпоинты:**
*   `/metrics` — внутренние метрики самого экспортера (количество запросов, ошибки конфигурации, время работы процесса).
*   `/probe` — результаты сетевых проверок целевых систем.

### Архитектура и жизненный цикл запроса

Внутренний цикл обработки одного запроса `/probe` включает следующие этапы:

1.  **Прием запроса:** Экспортер получает HTTP GET на `/probe` с параметрами `target`, `module` и необязательными `auth_*` параметрами.
2.  **Парсинг и валидация:** Извлекается целевой адрес и имя модуля. Выполняется проверка существования модуля в конфигурации. При отсутствии модуля экспортер возвращает ошибку 400 с детализацией.
3.  **Инициализация контекста:** Создается объект проверки с учетом таймаутов, политик повторных попыток и настроек протокола из конфигурации модуля.
4.  **Выполнение проебера (Prober):** В зависимости от типа модуля, выполняется соответствующая проверка:
    *   **HTTP:** установка TCP/TLS соединения, отправка запроса, обработка редиректов, валидация кода состояния и тела ответа (включая CEL-выражения).
    *   **TCP:** установка соединения, опциональный обмен данными по сценарию «запрос-ответ», валидация байтовых последовательностей.
    *   **ICMP:** формирование Echo Request, отправка, измерение времени отклика (требует `CAP_NET_RAW`).
    *   **DNS:** формирование запроса, отправка через UDP/TCP/DoT, валидация RCODE и записей ответа.
    *   **gRPC:** установка соединения, вызов Health Check, проверка статуса.
    *   **Unix:** подключение к доменному сокету, опциональный обмен данными.
5.  **Формирование метрик:** Результаты преобразуются в временные ряды Prometheus. Для каждой фазы HTTP запроса генерируется отдельная метрика `probe_http_duration_seconds` с лейблом `phase`.
6.  **Возврат ответа:** Prometheus получает текстовый формат с метриками. В случае сбоя `probe_success` устанавливается в `0`, метрики времени ответа могут содержать `NaN`.

### Сетевое размещение и топология

Правильное размещение Blackbox Exporter критично для точности результатов:

*   **Внутренние сервисы:** Размещайте экспортер в той же сети (VLAN/VPC), что и проверяемые цели, чтобы исключить задержки внешнего роутинга из измерений. Используйте внутренние DNS-имена.
*   **Внешние сервисы (сайты, API):** Размещайте экспортер в DMZ или в сети, топологически близкой к конечным пользователям. Это обеспечивает релевантность замеров доступности.
*   **Изоляция:** Экспортер должен иметь сетевое соединение только с целями и Prometheus. Ограничьте исходящий трафик фаерволлом (egress filtering).
*   **Масштабирование:** При большом количестве целей (>1000) или высокой частоте проверок (>30s) используйте несколько инстансов экспортера за балансировщиком нагрузки для распределения давления на целевые сервисы.

### Модель безопасности и права

Blackbox Exporter работает по принципу минимальных привилегий:

*   **Пользователь:** Запускайте процесс от выделенного непривилегированного пользователя (например, `blackbox`).
*   **Capabilities для ICMP:** Для выполнения Ping без root выдачийте бинарному файлу capability `cap_net_raw`:
    ```bash
    sudo setcap cap_net_raw+ep /usr/local/bin/blackbox_exporter
    ```
    В Docker используйте `cap_add: [NET_RAW]`.
*   **Защита эндпоинтов:** Если экспортер доступен из ненадежных сетей, используйте `web-config.yml` с TLS и Basic Auth через `exporter-toolkit`.
*   **Фаерволл:** Ограничьте доступ к порту `9115` только IP-адресами серверов Prometheus. Никогда не открывайте порт в публичную сеть без аутентификации.

### Ограничения и особенности

*   **Статистическая модель:** Экспортер не сохраняет историю — он stateless. Все временные ряды хранятся в TSDB Prometheus.
*   **Зависимость от сетевого пути:** Результаты probe отражают состояние сетевого пути между экспортером и целью, а не только состояние самого приложения.
*   **Влияние фаерволлов:** На уровне хоста или сети ICMP часто блокируется фаерволлом. Для проверки доступности порта используйте TCP-проверки.
*   **URL-кодирование:** Параметр `target` должен быть корректно URL-encoded при передаче специальных символов. Prometheus relabeling обрабатывает это автоматически для большинства случаев.
*   **Конфигурация как код:** Изменения в `blackbox.yml` требуют перезагрузки экспортера, если не используется флаг `--config.enable-auto-reload`.

## Практические сценарии

### Предварительные требования

**Аппаратные требования:**
*   Минимум 1 CPU core и 128 MiB RAM для развертывания до 500 целей с интервалом проверки 15s.
*   Для >1000 целей или интервала <10s рекомендуется 2+ cores и 256 MiB RAM.

**Программные требования:**
*   ОС: Linux (Debian/Ubuntu, RHEL/CentOS, Alpine) или любая ОС, поддерживающая контейнеризацию.
*   Права: доступ для установки бинарника в `/usr/local/bin` и создания пользователя `blackbox`. Для ICMP — возможность установки `cap_net_raw`.
*   Сеть: доступность целевых портов (обычно 80, 443, 53, 5432 и др.) из хоста, где размещен экспортер.

**Проверка среды:**
```bash
# Проверка разрешения DNS (экспортер должен резолвить имена целей)
dig +short example.com

# Проверка TCP-соединения к цели
nc -zv target-host 443

# Проверка доступности порта 9115 (если экспортер уже запущен)
curl -s -o /dev/null -w "%{http_code}" http://localhost:9115/metrics
# → 200
```

### Сценарии развертывания

Подробные пошаговые инструкции приведены в документе [Установка и настройка](./blackbox_exporter_installation_and_setup.md). Ниже — краткий обзор методов:

| Метод | Сценарий | Ключевые особенности |
| :--- | :--- | :--- |
| **Binary + systemd** | Bare-metal, виртуальные машины | Полный контроль, native ICMP через `AmbientCapabilities` |
| **Docker / Compose** | Контейнеризированные среды | Изоляция, быстрый запуск; ICMP требует `cap_add: [NET_RAW]` |
| **Kubernetes (Helm)** | Кластеры K8s | Автоматизация через чарты (версия v11.17+), Probe CRD |
| **Ad-hoc (binary)** | Разовые проверки, отладка | Запуск без установки: `./blackbox_exporter --config.file=blackbox.yml` |

### Сценарии мониторинга

| Сценарий | Модуль | Ожидаемый результат |
| :--- | :--- | :--- |
| **Веб-сайт (HTTP/2/3)** | `http_2xx` | Статус 200, валидный SSL, ответ < 2с |
| **API Endpoint** | `http_post_2xx` | Корректный ответ на POST-запрос с JSON-body |
| **База данных** | `tcp_connect` | TCP-порт (например, 5432) открыт и принимает соединения |
| **Сетевая связность** | `icmp` | Хост отвечает на Ping (требуется `cap_net_raw`) |
| **DNS-резолвинг** | `dns_udp` | Запись `A` возвращает ожидаемый IP-адрес |
| **gRPC Service** | `grpc` | Сервис поддерживает Health Check Protocol и возвращает `SERVING` |
| **SSL-сертификаты** | `http_2xx` | Мониторинг даты истечения сертификата через `probe_ssl_earliest_cert_expiry` |
| **Локальные сокеты** | `unix_socket` | Проверка сервисов, слушающих на `/var/run/service.sock` |

**Пример модуля HTTP с базовой авторизацией:**
```yaml
modules:
  http_auth_basic:
    prober: http
    timeout: 5s
    http:
      method: GET
      basic_auth:
        username: "monitoring"
        password: "secret"
      valid_status_codes: [200]
```

**Пример модуля ICMP:**
```yaml
modules:
  icmp_ping:
    prober: icmp
    timeout: 3s
    icmp:
      preferred_ip_protocol: "ip4"
      payload_size: 56
```

**Пример модуля DNS с валидацией MX:**
```yaml
modules:
  dns_mx:
    prober: dns
    timeout: 5s
    dns:
      query_name: "example.com"
      query_type: "MX"
      validate_answer_rrs:
        fail_if_matches_regexp: [".*NXDOMAIN.*"]
```

Детальные примеры конфигурации модулей для всех протоколов приведены в документе [Конфигурация модулей](./blackbox_exporter_modules_configuration.md).

### Интеграция с Prometheus

#### Стандартная конфигурация Relabeling

Поскольку адрес цели передается как параметр, в конфигурации Prometheus используется механизм `relabel_configs` для динамической подмены адреса скрейпинга:

```yaml
scrape_configs:
  - job_name: 'blackbox'
    metrics_path: /probe
    params:
      module: [http_2xx]
    static_configs:
      - targets:
        - https://prometheus.io
        - https://github.com
    relabel_configs:
      - source_labels: [__address__]
        target_label: __param_target    # 1. Записываем адрес цели в параметр target
      - source_labels: [__param_target]
        target_label: instance          # 2. Сохраняем адрес цели в лейбле instance для удобства
      - target_label: __address__
        replacement: 127.0.0.1:9115     # 3. Указываем адрес самого Blackbox Exporter для скрейпинга
```

#### Интеграция с Kubernetes Service Discovery

При использовании `kubernetes_sd_configs` экспортер автоматически обнаруживает сервисы по аннотациям:

```yaml
scrape_configs:
  - job_name: 'kubernetes-services-blackbox'
    metrics_path: /probe
    params:
      module: [http_2xx]
    kubernetes_sd_configs:
      - role: service
    relabel_configs:
      - source_labels: [__meta_kubernetes_service_annotation_blackbox_exporter]
        regex: true
        action: keep
      - source_labels: [__meta_kubernetes_service_annotation_blackbox_exporter_module]
        target_label: __param_module
      - source_labels: [__address__]
        target_label: __param_target
      - target_label: __address__
        replacement: blackbox-exporter.monitoring.svc.cluster.local:9115
```

#### Интеграция с NetBox

При использовании NetBox в качестве источника истины для инфраструктуры можно автоматически синхронизировать цели проверок через Ansible или скрипты, генерирующие `static_configs` на основе данных NetBox API.

### Валидация работоспособности

После развертывания выполните следующие проверки:

**1. Проверка доступности эндпоинта `/probe` (ad-hoc):**
```bash
# Проверка доступности сайта через модуль http_2xx
curl "http://localhost:9115/probe?target=google.com&module=http_2xx"

# Проверка DNS-резолвинга
curl "http://localhost:9115/probe?target=8.8.8.8&module=dns_google"
```
Ожидаемый результат: HTTP 200 с текстовым форматом Prometheus, содержащим метрики `probe_success`, `probe_duration_seconds` и др.

**2. Проверка внутренних метрик экспортера:**
```bash
curl -s http://localhost:9115/metrics | grep -E "blackbox_|up"
```
Ожидаемый результат: метрики `blackbox_exporter_build_info`, `blackbox_exporter_config_last_reload_successful` (1), `up` (1).

**3. Проверка в Prometheus:**
В интерфейсе Prometheus (Status → Targets) убедитесь, что targets в job `blackbox` имеют состояние `UP` и последний scrape завершился успешно.

```promql
# Проверка успешности всех проверок за последние 5 минут
avg_over_time(probe_success[5m])

# Проверка доступности самого экспортера
up{job="blackbox"}
```

**4. Проверка задержек:**
```bash
curl -s "http://localhost:9115/probe?target=example.com&module=http_2xx" | grep probe_duration_seconds
```
Убедитесь, что время ответа находится в пределах ожидаемого SLA (например, <2s для внутренних сервисов, <5s для внешних).

### Типичные проблемы и устранение неполадок

1.  **Ошибка `socket: permission denied`**
    *   **Причина:** Недостаточно прав для ICMP или привязки к привилегированным портам.
    *   **Решение:** Выполните `sudo setcap cap_net_raw+ep /usr/local/bin/blackbox_exporter` или добавьте `cap_add: [NET_RAW]` в Docker Compose. Проверьте: `getcap /usr/local/bin/blackbox_exporter`.

2.  **Ошибка `Invalid module`**
    *   **Причина:** Модуль, указанный в параметре `module`, отсутствует в файле `blackbox.yml` или опечатка в имени.
    *   **Решение:** Проверьте конфигурацию: `grep -A5 'http_2xx:' /etc/blackbox_exporter/blackbox.yml`. Убедитесь в отсутствии опечаток в параметре `module` в Prometheus или в URL.

3.  **Несоответствие таймаутов**
    *   **Причина:** Таймаут в модуле (`timeout` в `blackbox.yml`) больше, чем `scrape_timeout` в Prometheus.
    *   **Решение:** Установите `timeout` в модуле на 500мс-1с меньше, чем `scrape_timeout`. Например, если `scrape_timeout: 10s`, используйте `timeout: 9s` в модуле.

4.  **DNS-резолвинг не работает**
    *   **Причина:** Экспортер не может разрешить имя цели. Проверьте `/etc/resolv.conf` в контейнере или на хосте. Убедитесь, что корпоративный DNS доступен из сети экспортера.
    *   **Диагностика:** `docker exec -it blackbox_exporter cat /etc/resolv.conf` или `dig @<resolver> target.com`.

5.  **TLS-ошибки (handshake failure, certificate verify failed)**
    *   **Причина:** Устаревший сертификат на цели, несовместимость версий TLS, неправильный SNI.
    *   **Решение:** Используйте `insecure_skip_verify: false` и явно укажите `server_name` в `tls_config` для корректной передачи SNI. Проверьте поддержку TLS 1.2+ на цели.

6.  **Метрики `probe_success` постоянно `0` при доступном сервисе**
    *   **Причина:** Неправильный модуль (например, `http_2xx` для TCP-сервиса), редиректы, которые не обрабатываются, или блокировка фаерволлом.
    *   **Решение:** Используйте `follow_redirects: true` для HTTP. Убедитесь, что модуль соответствует протоколу цели.

7.  **Высокое время ответа (latency) без потерь пакетов**
    *   **Причина:** Маршрутизация через узкие места, DNS-задержки, TLS-handshake на стороне цели.
    *   **Решение:** Используйте `probe_http_duration_seconds` с лейблом `phase` для диагностики фазы задержки. Рассмотрите размещение экспортера ближе к цели.

### Лучшие практики

*   **Размещение:** Размещайте экспортер в той же сети, что и большинство целей. Для внешних проверок используйте географически распределенные инстансы или сторонние синтетические мониторы.
*   **Масштабирование:** Один инстанс может обслуживать тысячи целей, но ограничьте частоту проверок до разумного минимума (обычно 15s, 30s или 60s) чтобы не создавать DDoS-эффект на целевые сервисы.
*   **Безопасность:**
    *   Никогда не открывайте порт 9115 в публичную сеть без TLS и Basic Auth.
    *   Используйте `web-config.yml` с валидными сертификатами.
    *   Ограничьте доступ на уровне фаерволла только IP Prometheus.
*   **Таймауты:** Всегда настраивайте `timeout` в модуле меньше, чем `scrape_timeout` в Prometheus. Рекомендуемая разница — 500мс-1с.
*   **Мониторинг самого экспортера:** Добавьте в Prometheus проверку эндпоинта `/metrics` экспортера с помощью `up{job="blackbox_exporter"}`. Оптимальный интервал — 30s.
*   **Именование:** Используйте осмысленные имена модулей, отражающие тип проверки (`http_2xx`, `tcp_postgres`, `dns_external`).
*   **Cardinality (кардинальность):** Избегайте использования высококардинальных лейблов в `target`. Каждый уникальный target создает отдельный временной ряд. Для >10 000 уникальных целей используйте шардирование.
*   **Версионирование конфигурации:** Храните `blackbox.yml` в системе контроля версий (Git). При использовании `--config.enable-auto-reload` убедитесь, что ошибки конфигурации не приводят к падению экспортера.
*   **Очистка:** При деинсталляции удалите бинарник, конфигурационные файлы, пользователя `blackbox` и unit systemd. В Kubernetes удалите Helm-релиз и связанные Probe/ServiceMonitor ресурсы.

### Крайние случаи и ограничения

*   **ICMP и фаерволлы:** На уровне хоста или сети ICMP часто блокируется фаерволлом по умолчанию. Для проверки доступности хоста используйте TCP-проверки на порт 80 или 443.
*   **HTTP/3 (QUIC):** Поддержка HTTP/3 требует, чтобы целевой сервер поддерживал протокол QUIC (обычно на порту 443/UDP). Экспортер автоматически откатится на HTTP/2 или HTTP/1.1, если HTTP/3 недоступен.
*   **Unix Domain Sockets:** Проверки через `unix` пробер работают только когда экспортер и целевой сервис находятся на одном хосте. Путь к сокету должен быть доступен для чтения пользователю, от которого работает экспортер.
*   **IPv6:** При включенном `ip_protocol_fallback: true` экспортер сначала попытается IPv4, а при недоступности — IPv6. Убедитесь, что целевой хост имеет корректную AAAA запись.
*   **Проксирование HTTP-запросов:** Blackbox Exporter поддерживает переменные окружения `HTTP_PROXY`, `HTTPS_PROXY` и `NO_PROXY` для маршрутизации HTTP-проверок через прокси. Конфигурация прокси в `blackbox.yml` отсутствует.
*   **Максимальная длина URL:** Ограничение на длину параметра `target` составляет ~8KB (ограничение HTTP GET). Для проверки ресурсов с длинными URL используйте POST-модули.
*   **Prometheus Target Flapping:** Если цель постоянно переходит между UP и DOWN, проверьте стабильность сети и настройте `for:` в правилах алертинга для подавления шума.

## Decision Tree: Какой подход мониторинга выбрать

### Blackbox vs Whitebox

```
Нужно ли знать ВНУТРЕННЕЕ состояние системы?
├── Да → Whitebox (Node Exporter, приложение с /metrics)
│   └── Цель: диагностика причины сбоя (CPU, RAM, очереди)
└── Нет → Проверить доступность для ПОЛЬЗОВАТЕЛЯ?
    ├── Да → Blackbox Exporter
    │   └── Цель: "Видит ли пользователь сервис?"
    └── Нужна трассировка → Distributed Tracing (Jaeger, Tempo)
```

**Когда использовать Whitebox:**
- Отладка производительности (CPU, RAM, Disk, Network)
- Мониторинг внутренних очередей и соединений с БД
- Профилирование JVM, Go runtime
- Поиск первопричины (Root Cause Analysis)

**Когда использовать Blackbox:**
- Проверка доступности API endpoints извне
- Мониторинг SSL-сертификатов и TLS
- Проверка DNS-резолвинга
- Валидация работы балансировщиков нагрузки
- Проверка доступности баз данных через TCP

**Когда использовать оба подхода:**
- Полноценная observability-стратегия
- Blackbox ловит сбой (симптом), Whitebox помогает найти причину

### Synthetic Monitoring vs Real User Monitoring (RUM)

```
Нужны ли данные о РЕАЛЬНЫХ пользователях?
├── Да → RUM (Grafana Faro, OpenTelemetry)
│   └── Цель: Core Web Vitals, реальный опыт
└── Нет → Нужны данные при НУЛЕВОМ трафике?
    ├── Да → Synthetic Monitoring (Blackbox Exporter)
    │   └── Цель: проверка доступности до появления трафика
    └── Нет → Нужна ВОСПРОИЗВОДИМОСТЬ измерений?
        ├── Да → Synthetic Monitoring
        │   └── Цель: одинаковые условия каждый раз
        └── Нет → RUM
```

**Сравнение:**

| Критерий | Synthetic (Blackbox) | RUM |
|:---|:---|:---|
| **Данные при нулевом трафике** | Да | Нет |
| **Воспроизводимость** | Высокая (фиксированные условия) | Низкая (разные устройства/сети) |
| **Географическое покрытие** | Определяется расположением экспортера | Реальные пользователи по всему миру |
| **Core Web Vitals** | Ограниченно (без JS-рендеринга) | Полностью |
| **Обнаружение до инцидента** | Проактивное | Реактивное |
| **Стоимость** | $0 (open-source) | Зависит от провайдера |

**Рекомендация:** Используйте оба подхода. Synthetic мониторинг ловит регрессию до деплоя и проверяет базовую доступность. RUM подтверждает влияние на реальных пользователей.

### Blackbox Exporter vs SaaS-мониторинг

```
Есть ли команда для поддержки инфраструктуры мониторинга?
├── Да → Нужен контроль над данными?
│   ├── Да → Blackbox Exporter
│   │   └── Данные не покидают инфраструктуру
│   └── Нет → Нужно глобальное гео-покрытие?
│       ├── Да → Гибрид (Blackbox + SaaS)
│       │   └── Blackbox: внутренние сервисы
│       │   └── SaaS: внешние проверки из разных регионов
│       └── Нет → Blackbox Exporter
└── Нет → SaaS-решение (Checkly, UptimeRobot)
    └── Минимальные ресурсы на поддержку
```

**Подробнее:** [Blackbox Exporter vs SaaS](./blackbox_exporter_vs_saas.md)

## Дополнительная информация

### Нововведения и технические особенности (v0.28.0+)

*   **HTTP/3 (QUIC):** Полная поддержка пробинга через протокол HTTP/3, что критично для современных веб-приложений и CDN.
*   **Автоматическая перезагрузка (Auto-Reload):** Флаг `--config.enable-auto-reload` позволяет экспортеру отслеживать изменения в `blackbox.yml` и обновлять модули без перезапуска или отправки SIGHUP.
*   **gRPC Metadata:** Возможность передачи пользовательских заголовков (metadata) в gRPC-запросах для авторизации или специфических проверок.
*   **TCP Byte Matching:** Расширенный TCP-пробер позволяет выполнять проверку не только факта соединения, но и содержимого ответа на уровне байтов.
*   **CEL (Common Expression Language):** Поддержка CEL-выражений для валидации JSON-ответов и заголовков, что снижает зависимость от регулярных выражений и повышает читаемость конфигурации.
*   **Unix Domain Sockets:** Поддержка проверки локальных сервисов через Unix-сокеты (протоколы `unix`, `unixgram`, `unixpacket`).
