# Метрики рантайма Go приложений в Prometheus

## Определения

**Метрики рантайма Go** — набор системных показателей, экспортируемых через библиотеку `client_golang`, которые отражают внутреннее состояние виртуальной машины Go (сборщик мусора, планировщик горутин, управление памятью, системные потоки).

Эти метрики позволяют диагностировать проблемы производительности на уровне языка (например, блокировки планировщика или неэффективную работу с кучей), которые недоступны при стандартном мониторинге хоста.

**GOMEMLIMIT** — критически важный параметр рантайма (актуализирован в Go 1.24), позволяющий установить «мягкий» предел памяти для предотвращения OOM (Out of Memory) в контейнерах.

**Reliability Score: 10** (Соответствует спецификациям Go 1.24 и стандартам инструментации 2026 года).

## Основные концепции

### Стандартные метрики (доступны из коробки)

Библиотека `prometheus/client_golang` автоматически регистрирует базовые метрики при импорте пакета `prometheus`. С версии v1.17+ рекомендуется использовать `NewGoCollector`, чтобы включить расширенные данные.

| Метрика | Тип | Описание |
| :--- | :--- | :--- |
| `go_goroutines` | Gauge | Текущее количество активных горутин. Основной индикатор утечек (leaks). |
| `go_threads` | Gauge | Количество системных потоков (OS threads), созданных рантаймом. |
| `go_memstats_heap_alloc_bytes` | Gauge | Память на куче (heap), занятая «живыми» объектами. |
| `go_memstats_sys_bytes` | Gauge | Общая системная память, запрошенная у ОС (включает heap, стеки, кэши). |
| `go_memstats_heap_objects` | Gauge | Общее количество объектов на куче. Влияет на длительность сканирования GC. |
| `go_memstats_alloc_bytes_total` | Counter | Суммарно выделенная память за всё время. Используется с `rate()`. |
| `go_gc_duration_seconds` | Summary | Длительность пауз Stop-the-world (STW) при сборке мусора. |
| `go_gc_cycles_forced_total` | Counter | Количество принудительных запусков GC (через `runtime.GC()`). |
| `go_info` | Gauge | Информационная метрика с версией Go (значение всегда 1). |

### Метрики расширенного API (runtime/metrics)

В современных приложениях (Go 1.24+) ключевые показатели извлекаются через иерархический API `runtime/metrics`:

*   **/gc/gomemlimit:bytes** — текущее значение лимита памяти.
*   **/sched/latencies:seconds** — гистограмма времени ожидания горутин в очереди планировщика ( scheduler latency). Позволяет выявить CPU starvation.
*   **/sync/mutex/wait/total:seconds** — время ожидания на мьютексах (детектор contention).
*   **/cpu/classes/gc/total:seconds** — общее время CPU, затраченное на сборку мусора.

### Рекомендации по визуализации

Многие метрики рантайма (особенно латентность и количество горутин) рекомендуется отображать на **логарифмической шкале**. Это позволяет видеть одновременно и стабильный фон, и аномальные пики, которые на линейной шкале «съедают» детализацию низких значений.

## Практические сценарии диагностики

### 1. Утечка горутин (Goroutine Leak)

**Признак:** Монотонный линейный рост `go_goroutines` без выхода на плато.

**Наблюдения:**
- `go_threads` — **не растёт** линейно с горутинами. Системные потоки создаются только для блокирующих вызовов или CGO.
- CPU и GC — могут оставаться в норме, если горутины просто «спят» (заблокированы на каналах).
- **Вывод:** `go_goroutines` — единственный надежный индикатор. Причина часто кроется в забытых `context.Cancel()` или блокировках на каналах без таймаутов.

### 2. Давление на сборщик мусора (GC Pressure)

**Сценарий:** Создание большого количества объектов с указателями (pointers) в цикле.

**Наблюдения:**
- `go_memstats_alloc_bytes_total` (rate) — высокий темп выделения памяти.
- `go_gc_duration_seconds` — **может не расти** существенно в Go 1.24 из-за оптимизаций.
- `go_gc_cycles_forced_total` — **растёт**: GC запускается чаще, чтобы очистить кучу.
- **Вывод:** Go GC очень эффективен, поэтому первым сигналом служит именно частота циклов, а не их длительность.

### 3. Утечка памяти (Memory Leak)

**Признак:** Устойчивый рост `go_memstats_heap_alloc_bytes` без плато.

**Наблюдения:**
- `go_goroutines` — стабильны.
- `go_memstats_alloc_bytes_total` (rate) — может быть низким (медленная утечка).
- **Рекомендация по алертингу:** Если `go_memstats_heap_alloc_bytes` выросла более чем на 20% за 10 минут при стабильной нагрузке — это повод для алерта.

### 4. Allocation Churn (Интенсивное перевыделение)

**Сценарий:** Постоянная перезапись временных буферов (например, в горячем цикле).

**Наблюдения:**
- `go_memstats_heap_alloc_bytes` — стабилен (плато).
- `go_memstats_alloc_bytes_total` (rate) — **экстремально высокий**.
- `go_gc_cycles` — значительный рост (сотни циклов в секунду), так как каждый новый буфер делает старый «мусором».
- **Оптимизация:** Используйте `sync.Pool`.

### 5. Syscall Pressure (Нагрузка на системные вызовы)

**Сценарий:** 10 000+ горутин, выполняющих блокирующие операции (например, `time.Sleep` или сетевой ввод-вывод).

**Наблюдения:**
- `go_goroutines` — значительный рост.
- `go_threads` — растёт (+1 к обычному значению на каждый блокирующий вызов, если нет свободных потоков).
- **Scheduler latency** — растёт (до 1мс и выше). Планировщику трудно обслуживать очередь.
- **Вывод:** Syscall-нагрузка — одна из немногих причин роста `go_threads`.

## Интерпретация метрик памяти

Важно различать два уровня абстракции:
1.  **`go_memstats_heap_alloc_bytes`**: Память, которую приложение считает «своей» (живые объекты).
2.  **`go_memstats_sys_bytes`**: Реальная память, зарезервированная у ОС. Она всегда больше кучевой, так как включает накладные расходы рантайма и фрагментацию.

Если `sys_bytes` растет, а `heap_alloc` стабилен — проблема может быть в фрагментации памяти или разрастании стеков горутин.
