# Метрики рантайма Go приложений в Prometheus

## Определения

**Метрики рантайма Go** — набор метрик, экспортируемых Go-приложением через библиотеку `client_golang`, которые отражают внутреннее состояние Go runtime (сборщик мусора, планировщик горутин, управление памятью, системные потоки). Позволяют диагностировать проблемы производительности на уровне языка, недоступные при стандартном мониторинге хоста (CPU, память).

## Основные концепции

### Стандартные метрики (доступны из коробки)

Библиотека `prometheus/client_golang` автоматически регистрирует метрики Go runtime при импорте пакета `prometheus`:

| Метрика | Тип | Описание |
| :--- | :--- | :--- |
| `go_goroutines` | Gauge | Текущее количество горутин |
| `go_threads` | Gauge | Количество системных потоков (OS threads), созданных Go runtime |
| `go_memstats_heap_alloc_bytes` | Gauge | Память, выделенная на куче (heap) в данный момент |
| `go_memstats_sys_bytes` | Gauge | Системная память, запрошенная у ОС |
| `go_memstats_heap_objects` | Gauge | Количество объектов на куче |
| `go_memstats_alloc_bytes_total` | Counter | Суммарно выделенная память за всё время (скорость — `rate()`) |
| `go_gc_duration_seconds` | Summary | Время, затраченное на сборку мусора (GC) |
| `go_gc_cycles_forced_total` | Counter | Количество принудительных запусков GC |
| `go_info` | Gauge | Версия Go (информационная метрика со значением 1) |

### Метрики, требующие ручного извлечения

Некоторые метрики рантайма не экспортируются автоматически. Их необходимо доставать через пакет `runtime/metrics` из стандартной библиотеки Go и регистрировать как кастомные метрики Prometheus.

Ключевая метрика — **латентность планировщика горутин** (scheduler latency) — время, которое планировщик Go тратит на выбор горутин для выполнения. Извлекается через `/sched/pauses/total/gc:seconds` и аналогичные метрики из `runtime/metrics`.

### Метрики: рекомендации по шкалам

Многие метрики рантайма Go рекомендуется визуализировать с **логарифмической шкалой** — это одновременно отображает и фоновые значения, и аномальные всплески, которые на линейной шкале были бы незаметны на фоне пиков.

## Практические сценарии

### 1. Утечка горутин (Goroutine Leak)

**Признак:** монотонный рост `go_goroutines` без снижения.

**Влияние на другие метрики:**
- `go_threads` — **не растёт** линейно с ростом горутин. Системные потоки создаются только при необходимости (блокирующие syscalls, CGO, GC).
- CPU usage, scheduler latency — без изменений при умеренном количестве горутин (до ~2000).
- Память, GC — без изменений (если горутины не выделяют память).

**Вывод:** `go_goroutines` — единственный надёжный индикатор утечки горутин. Остальные метрики могут не показывать аномалий.

### 2. Давление на GC (GC Pressure)

Сценарий: создаётся большое количество объектов с указателями в цикле, плюс фоновое выделение памяти.

**Наблюдения на метриках:**
- `go_threads` — может появиться +1 дополнительный поток (предположительно для обработки GC).
- `go_memstats_heap_alloc_bytes` / `go_memstats_sys_bytes` — растут до плато, затем переиспользуются. Системная и кучевая память могут не совпадать — это нормально.
- `go_memstats_alloc_bytes_total` (rate) — высокий уровень выделения памяти каждую секунду.
- `go_gc_duration_seconds` — **не растёт** существенно. Go GC (начиная с версии 1.23) оптимизирован и справляется быстро.
- `go_gc_cycles_forced_total` (rate) — **растёт**: GC запускается чаще.

**Вывод:** `go_gc_duration_seconds` остаётся низким даже при интенсивном выделении памяти с указателями. Рост частоты циклов GC (`go_gc_cycles`) — первый сигнал, а не длительность. Go GC высокоэффективен для таких сценариев.

### 3. Утечка памяти (Memory Leak)

**Признак:** устойчивый рост `go_memstats_heap_alloc_bytes` без выхода на плато.

**Влияние:**
- `go_goroutines`, `go_threads` — без изменений.
- CPU, scheduler latency — незначительный рост (если утечка медленная).
- `go_memstats_alloc_bytes_total` (rate) — низкий, почти незаметный.
- `go_gc_duration_seconds`, `go_gc_cycles` — минимальные.

**Рекомендация по алертингу:** если потребление памяти (`go_memstats_heap_alloc_bytes`) выросло более чем на 10-20% за последние 5 минут — это повод для алерта. Go-приложения редко страдают от утечек памяти при использовании линтеров и тестов, но это возможно.

### 4. Allocation Churn (интенсивное выделение памяти)

Сценарий: в цикле постоянно перезаписывается одна и та же переменная (без `append`, просто новое присваивание). Предыдущий буфер становится недоступен и требует очистки GC.

**Наблюдения:**
- `go_threads` — может вырасти на 1 (поток для обработки GC).
- CPU usage — растёт (постоянная работа).
- Scheduler latency — незначительный рост (наносекунды → микросекунды).
- `go_memstats_heap_alloc_bytes` — растёт до плато.
- `go_memstats_alloc_bytes_total` (rate) — высокий (схож с GC Pressure).
- `go_gc_duration_seconds` — без изменений.
- `go_gc_cycles` — **значительный рост** (сотни циклов в секунду против десятков в сценарии GC Pressure), так как каждый новый буфер требует немедленной очистки предыдущего.

**Отличие от GC Pressure:** в GC Pressure объекты добавляются в слайс и периодически чистятся; в Allocation Churn каждый новый буфер делает предыдущий мусором, что вызывает более частые циклы GC.

### 5. Syscall Pressure (нагрузка на системные вызовы)

Сценарий: большое количество горутин (например, 10 000), каждая выполняет `time.Sleep(1ms)`. `Sleep` внутри реализован через системные вызовы.

**Наблюдения:**
- `go_goroutines` — значительный рост.
- `go_threads` — растёт (+1 к обычному значению). Go runtime выделяет отдельный поток для обработки syscalls, чтобы не блокировать остальные потоки.
- CPU usage — растёт (даже Sleep требует переключения контекста).
- Scheduler latency — растёт (до ~1ms задержки). Планировщику приходится обслуживать тысячи горутин.
- `go_memstats_*` — без существенных изменений (память не выделялась).
- `go_gc_duration_seconds` — незначительный рост (шумный сосед: syscall-потоки загружают CPU, GC не хватает ресурсов).
- `go_gc_cycles` — без изменений.

**Вывод:** syscall-нагрузка влияет на количество потоков и латентность планировщика. Для точной диагностики рекомендуется профилирование.

### Интерпретация метрик памяти

Важно различать две метрики:
- `go_memstats_heap_alloc_bytes` — память на куче (heap), которую активно использует приложение.
- `go_memstats_sys_bytes` — системная память, запрошенная у ОС (включает heap, стеки горутин, внутренние структуры рантайма).

Они могут не совпадать — это нормально. Системная память может быть больше кучевой, так как включает резервы и накладные расходы рантайма.
