# Расширяемость экспортеров Prometheus — Концепции

## Определения

**Расширяемость экспортеров** — архитектурная возможность добавления кастомных метрик в систему мониторинга через внешние агенты, скрипты или интеграцию кода.

**Collector (Коллектор)** — внутренний интерфейс в экспортере или клиентской библиотеке, отвечающий за сбор группы связанных метрик (например, `cpuCollector` в `node_exporter`).

**Exporter-Toolkit** — стандартный набор инструментов для разработки экспортеров на Go, обеспечивающий поддержку TLS и базовой аутентификации.

**См. также:** [Обзор экспортеров](../overview.md), [Типы метрик](../../concepts/metric_types/overview.md).

## Основные концепции

Механизмы расширения мониторинга делятся на четыре категории в зависимости от уровня интеграции:

### 1. Textfile Collector (Пассивный сбор)

Встроенный модуль `node_exporter`, читающий файлы формата `.prom` из локальной директории.
- **Когда:** периодические задачи (cron), однострочные bash-скрипты, системные отчеты.
- **Плюсы:** экстремальная простота, отсутствие постоянно запущенного процесса.
- **Минусы:** риск устаревания данных (stale data), если файл не обновляется.
- **Подробнее:** [Textfile Collector](./textfile_collector.md).

### 2. Script Exporter (Активный сбор)

Внешний сервис, который запускает произвольные скрипты в ответ на HTTP-запрос от Prometheus.
- **Когда:** проверки на месте (on-demand), сложные проверки доступности (аналог Blackbox, но для скриптов).
- **Плюсы:** свежесть данных, выполнение логики только при скрапинге.
- **Минусы:** нагрузка на CPU при частых запусках тяжелых скриптов.

### 3. Собственные экспортеры (Sidecar / Агенты)

Отдельные приложения на базе клиентских библиотек для систем без нативной поддержки Prometheus (Legacy БД, сетевое оборудование).
- **Когда:** требуется сложная логика трансформации данных, кэширование или поддержка TLS/Auth.
- **Архитектура:** обычно реализуется как отдельный процесс или Sidecar-контейнер.
- **Руководство:** [Создание собственных экспортеров](./custom_exporters.md).

### 4. Прямая инструментация (Client Libraries)

Встраивание сбора метрик непосредственно в исходный код приложения.
- **Когда:** мониторинг бизнес-логики, внутренних очередей, времени обработки запросов.
- **Плюсы:** максимальная точность, отсутствие задержек на передачу между агентами.
- **Подробнее:** [Клиентские библиотеки](./client_libraries.md).

## Практические сценарии

### Именование метрик

* **Регистр и символы:** только нижний регистр `[a-zA-Z0-9_:]`.
* **Префикс (Namespace):** должен указывать на имя приложения или экспортера (например, `haproxy_`, `nginx_`).
* **Суффиксы типа:**
  * `_total` — для Counter (обязательно).
  * `_created` — время создания серии (Unix timestamp).
  * `_info` — для метаданных (значение всегда `1`).
* **Единицы измерения:** обязательны в названии в базовых единицах (например: `_seconds`, `_bytes`, `_joules`, `_celsius`).

**Примеры именования:**
```text
# Плохо: request_count
# Хорошо: http_requests_total

# Плохо: mem_usage
# Хорошо: process_memory_working_set_bytes
```

### Дизайн лейблов

* **Кардинальность:** Избегайте [высокой кардинальности](../../concepts/labels_and_cardinality.md). Никогда не используйте ID пользователей, email или полные URL в лейблах.
* **Неизменность (SSoT):** Экспортер должен выдавать только «сырые» данные о цели. Лейблы инфраструктуры (`cluster`, `env`, `datacenter`) должны добавляться через [Service Discovery](../../service_discovery_and_relabeling.md) на стороне Prometheus.
* **Атомарность:** Лейблы должны быть ортогональны. Если вы меняете значение лейбла, агрегация по остальным должна сохранять смысл.

### Безопасность и архитектура кода

1.  **Pull-модель:** Данные должны собираться *в момент запроса*. Избегайте фонового сбора в кэш, если это не продиктовано скоростью работы целевой системы.
2.  **Защита эндпоинта:** Используйте `exporter-toolkit` для реализации TLS и Basic Auth. Не оставляйте экспортеры открытыми в публичных сетях.
3.  **Порты:** Следуйте [Default Port Allocations](https://github.com/prometheus/prometheus/wiki/Default-port-allocations). Для частных разработок резервируйте порты в диапазоне `9100-9999`.

## Дополнительная информация

### Типичные ошибки (Anti-patterns)

- **Timestamp вручную:** Не выставляйте время сбора метрики в экспортере. Prometheus сам проставит время получения данных.
- **Missing HELP/TYPE:** Всегда описывайте метрики. Это критично для OpenMetrics и понимания данных другими инженерами.
- **Слишком много метрик:** Лучше 10 качественных метрик, чем 100 «на всякий случай». Каждая метрика потребляет ресурсы RAM в Prometheus.
