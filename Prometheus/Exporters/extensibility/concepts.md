# Расширяемость экспортеров Prometheus — Концепции

## Определения

**Расширяемость экспортеров** — возможность добавления произвольных метрик в Prometheus через внешние скрипты или создания собственных экспортеров с использованием клиентских библиотек.

## Основные концепции

Существует три основных механизма расширения встроенных возможностей мониторинга:

### 1. Textfile Collector

Механизм `node_exporter` для сбора произвольных метрик через внешние скрипты, которые записывают данные в файлы формата `.prom`. Это оптимальный вариант для bash/python-скриптов или когда невозможно встроить метрики в код самого приложения. Подробнее о механизме: [Textfile Collector](./textfile_collector.md).

### 2. Собственные экспортеры

Создание отдельных экспортеров (как отдельных сервисов или сайдкар-контейнеров) с использованием клиентских библиотек Prometheus. Применяется для систем, которые не поддерживают экспорт в формате Prometheus "из коробки" (например, специализированное железо, проприетарные базы данных). Руководство: [Создание собственных экспортеров](./custom_exporters.md).

### 3. Прямая инструментация (клиентские библиотеки)

Непосредственное встраивание генерации метрик в код вашего приложения. Это наиболее эффективный и предпочтительный способ мониторинга бизнес-логики. Подробнее: [Клиентские библиотеки](./client_libraries.md).

## Практические сценарии

### Именование метрик

* **Формат:** только нижний регистр `[a-zA-Z0-9_:]`.
* **Суффиксы:**
  * `_total` — для типа counter (обязательно).
  * `_sum`, `_count`, `_bucket` — для типа histogram.
  * `_info` — для метрик, содержащих только информацию (версия, конфигурация) и имеющих значение `1`.
* **Префиксы:** избегать `process_`, `scrape_` (они зарезервированы системой).
* **Единицы измерения:** всегда включать в название (например: `_seconds`, `_bytes`, `_count`).

**Примеры правильных имён:**

```text
nginx_http_request_duration_seconds
mysql_queries_total
app_memory_usage_bytes
node_cpu_seconds_total
```

### Выбор лейблов

* **Делегирование Service Discovery:** не использовать в лейблах информацию об инфраструктуре (`region`, `zone`, `cluster`, `az`, `datacenter`, `customer`). За добавление этого контекста отвечает механизм [Service Discovery](../../service_discovery_and_relabeling.md).
* **Контроль кардинальности:** категорически избегать [высокой кардинальности](../../concepts/labels_and_cardinality.md) (не использовать в лейблах `request_id`, `user_id`, `email`, IP-адреса).
* **Смысл при агрегации:** метрика должна иметь смысл при агрегации по своему лейблу. Не разделять кардинально разные сущности (например, операции `read` и `write` для диска) с помощью лейбла — в таких случаях создаются две разные метрики.

**Примеры правильных лейблов:**

```text
http_requests_total{method="GET",status="200"}
mysql_queries_total{database="users"}
```

### Рекомендации по написанию кода

* Получение данных в собственном экспортере должно происходить исключительно в момент HTTP-запроса от Prometheus (при скрапинге).
* Не выставлять временные метки (timestamp) для метрик вручную, это задача сервера Prometheus.
* Использовать стандартные порты, сверяясь со списком [Default Port Allocations](https://github.com/prometheus/prometheus/wiki/Default-port-allocations). Для кастомных проектов обычно выделяется диапазон 9100-9200.
