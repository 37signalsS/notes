# Расширяемость экспортеров Prometheus — Концепции

## Определения

**Расширяемость экспортеров** — архитектурная возможность добавления пользовательских метрик в систему мониторинга через внешние агенты, скрипты, прямую инструментацию или интеграцию по протоколу OTLP.

**Collector (Коллектор)** — внутренний интерфейс в экспортере или клиентской библиотеке, отвечающий за сбор группы связанных метрик (например, `cpuCollector` в `node_exporter`). В Prometheus 3.0 коллекторы могут возвращать Native Histograms.

**Exporter-Toolkit** — стандартный набор инструментов для разработки экспортеров на Go, обеспечивающий поддержку TLS, базовой аутентификации и динамической конфигурации.

**OTLP (OpenTelemetry Protocol)** — протокол передачи сигналов (метрик, логов, трейсов), ставший нативным для Prometheus 3.0 через встроенный OTLP-receiver.

**Pushgateway** — промежуточный буфер для сбора метрик от кратковременных (ephemeral) задач, которые завершаются быстрее, чем происходит цикл скрапинга. Преобразует Push-модель в Pull-модель для Prometheus. Подробнее: [Pushgateway](../../pushgateway.md).

**Stale Marker (Маркер устаревания)** — специальное значение `stale NaN`, передаваемое экспортером для принудительного удаления временного ряда из TSDB без ожидания стандартного `lookback delta` (5 минут).

**Scrape Protocol (Протокол скрейпинга)** — формат, используемый при передаче метрик от экспортера к Prometheus. В Prometheus 3.0+ поддерживается явный приоритет протоколов через `scrape_protocols`.

**См. также:** [Обзор экспортеров](../overview.md), [Типы метрик](../../concepts/metric_types/overview.md), [Формат экспозиции](../../concepts/metric_types/exposition_format.md).

## Основные концепции

Механизмы расширения мониторинга в 2026 году делятся на семь основных категорий. Выбор категории зависит от типа monitored-системы, требований к актуальности данных и архитектурных ограничений.

### 1. Textfile Collector (Пассивный сбор)

Встроенный модуль `node_exporter`, читающий файлы формата `.prom` из локальной директории.

- **Когда:** периодические задачи (cron), однострочные bash-скрипты, системные отчеты о состоянии RAID или бэкапов.
- **Плюсы:** экстремальная простота, не требует постоянно запущенного кастомного процесса, отсутствие зависимостей.
- **Минусы:** риск «протухания» данных (stale data), если скрипт перестал обновлять файл; отсутствие native histograms в текстовом формате.
- **Развертывание:** активируется флагом `--collector.textfile.directory`. Директория должна быть доступна на запись только для процессов-генераторов и на чтение для `node_exporter`.
- **Ресурсы:** минимальные (только disk I/O при скрапинге).
- **Валидация:** `curl -s http://localhost:9100/metrics | grep -E '^# TYPE' | head` — в выводе должны присутствовать метрики из `.prom` файлов.
- **Подробнее:** [Textfile Collector](./textfile_collector.md).

### 2. Script Exporter (Активный сбор по требованию)

Внешний сервис (например, `prometheus-script-exporter` или аналоги), который запускает произвольные скрипты в ответ на HTTP-запрос от Prometheus.

- **Когда:** проверки на месте (on-demand), имитация действий пользователя, сложные проверки сетевой доступности, интеграция с CLI-утилитами без готовых экспортеров.
- **Плюсы:** данные собираются ровно в момент скрапинга, высокая актуальность, гибкость логики.
- **Минусы:** нагрузка на CPU при частом запуске «тяжелых» скриптов (например, Python с импортами); время отклика напрямую влияет на `scrape_timeout`.
- **Развертывание:** отдельный процесс или контейнер. Рекомендуется использовать `scrape_timeout` не менее 30s.
- **Ресурсы:** зависят от частоты скрапинга и веса скриптов.
- **Валидация:** `curl -s "http://localhost:8080/probe?target=db01"` — проверка, что скрипт выполняется и возвращает валидный формат.

### 3. Собственные экспортеры (Sidecar / Агенты)

Отдельные приложения на базе клиентских библиотек для систем без нативной поддержки Prometheus (Legacy БД, проприетарное сетевое оборудование).

- **Когда:** требуется сложная трансформация данных, кэширование, поддержка TLS/Auth, Remote Write 2.0, Native Histograms.
- **Архитектура:** обычно реализуется как отдельный процесс или Sidecar-контейнер в Kubernetes. Для high-load систем рекомендуется паттерн Background Polling с кэшированием.
- **Развертывание:** systemd unit, Docker-контейнер, Kubernetes Sidecar.
- **Ресурсы:** от 50MB RAM (простой экспортер) до 1GB+ (при кэшировании больших объемов).
- **Валидация:** `curl -s http://localhost:9101/metrics | promtool check metrics` — проверка формата; `up` метрика должна показывать `1`.
- **Руководство:** [Создание собственных экспортеров](./custom_exporters.md).

### 4. Прямая инструментация (Client Libraries)

Встраивание сбора метрик непосредственно в исходный код приложения.

- **Когда:** мониторинг бизнес-логики, внутренних очередей, времени обработки запросов, использование Native Histograms, связь с трейсами через Exemplars.
- **Плюсы:** максимальная точность, минимальные задержки, поддержка экземпляров (exemplars) для связки с трейсами, отсутствие отдельных процессов.
- **Минусы:** требует изменения кода приложения, привязка к конкретному языку.
- **Развертывание:** встраивается в бинарник приложения. Эндпоинт `/metrics` обслуживается тем же процессом.
- **Ресурсы:** минимальные накладные расходы (встроенный в приложение процесс).
- **Валидация:** `curl -s http://app:8080/metrics | grep -E '^(# TYPE|# HELP)' | head` — проверка HELP/TYPE.
- **Подробнее:** [Клиентские библиотеки](./client_libraries.md).

### 5. Интеграция через OTLP (Push/Pull)

Использование протокола OpenTelemetry для прямой отправки данных в Prometheus 3.0.

- **Когда:** приложения, инструментированные OTel SDK, унификация стека observability (метрики + логи + трейсы), Serverless-функции (Push-модель).
- **Плюсы:** вендор-нейтральность, нативная поддержка UTF-8 имен (например, `http.server.duration`), унификация с трейсами и логами.
- **Минусы:** дополнительный компонент (OTel Collector) в архитектуре; требует настройки OTLP-receiver на стороне Prometheus.
- **Развертывание:** Prometheus с флагом `--web.enable-otlp-receiver` или через OpenTelemetry Collector с экспортом в Prometheus.
- **Ресурсы:** OTel Collector добавляет 100-300MB RAM на инстанс.
- **Валидация:** проверка портов 4317 (gRPC) и 4318 (HTTP) на стороне Prometheus; `curl -s http://localhost:4318/v1/metrics` — должен возвращать `405 Method Not Allowed` (требуется POST).
- **Включение:** Активируется флагом `--web.enable-otlp-receiver`.

### 6. Pushgateway (Push-to-Pull мост)

Промежуточный сервис для приема метрик от кратковременных задач (Cron, batch-пайплайны), которые завершаются быстрее цикла скрапинга.

- **Когда:** мониторинг завершающихся задач, системные отчеты за период, ситуации, когда Pull-модель невозможна (Firewall/NAT).
- **Плюсы:** простота интеграции с существующими скриптами, поддержка группировки метрик по `job` и дополнительным лейблам.
- **Минусы:** отсутствие TTL — если задача не отправляет данные, Pushgateway хранит устаревшие значения бесконечно; метрика `up` отражает статус Pushgateway, а не самой задачи.
- **Развертывание:** отдельный контейнер или VM. В Kubernetes рекомендуется отдельный Namespace с NetworkPolicy.
- **Ресурсы:** ~50-100MB RAM; потребление растет с количеством уникальных `grouping keys`.
- **Валидация:** `curl -s http://localhost:9091/metrics | grep -E '^# TYPE' | head`; проверка, что метрики имеют лейбл `job`.
- **Подробнее:** [Pushgateway](../../pushgateway.md).

### 7. Probe-based расширяемость (Blackbox Exporter)

Мультитаргетный паттерн, при котором один экземпляр экспортера выполняет проверки множества целей по их адресам, передаваемым в параметре запроса.

- **Когда:** проверка доступности внешних эндпоинтов (HTTP, HTTPS, TCP, ICMP, DNS), мониторинг с точки зрения внешнего наблюдателя, SLA-проверки.
- **Архитектура:** Prometheus скрейпит Blackbox Exporter с параметром `?target=<address>`. Экспортер выполняет проверку и возвращает метрики доступности и задержки.
- **Плюсы:** один экспортер на сотни целей, централизованная конфигурация модулей проверки.
- **Минусы:** дополнительный hop в архитектуре; необходимость корректной настройки `relabel_configs`.
- **Развертывание:** как отдельный процесс. Важно: `scrape_timeout` должен превышать таймаут проверки в модуле Blackbox.
- **Ресурсы:** ~30-50MB RAM; нагрузка на CPU зависит от количества модулей и частоты проверок.
- **Валидация:** `curl -s "http://blackbox:9115/probe?target=example.com&module=http_2xx"` — возвращает `probe_success{...} 1`.
- **Подробнее:** [Blackbox Exporter — обзор](../blackbox/blackbox_exporter_overview.md).

### Пассивные vs Активные механизмы

| Характеристика | Пассивные (Textfile, Pushgateway) | Активные (Exporter, OTLP Push) |
|:---|:---|:---|
| **Инициатор сбора** | Внешний скрипт / приложение | Экспортер / Prometheus |
| **Актуальность данных** | Зависит от внешнего расписания | Максимальная в момент скрапинга |
| **Надежность** | Риск stale data при сбое скрипта | Зависит от доступности экспортера |
| **Сложность отладки** | Высокая (разделены скрипт и сбор) | Низкая (единый процесс) |
| **Ресурсы на стороне Prometheus** | Минимальные | Зависят от количества целей |

| Критерий | Textfile | Script Exporter | Custom Exporter | Client Library | OTLP | Pushgateway | Blackbox |
|:---|:---|:---|:---|:---|:---|:---|:---|
| **Тип monitored-системы** | Статические метрики | Ad-hoc проверки | Legacy API/БД | Собственное приложение | OTel-instrumented | Ephemeral задачи | Внешние эндпоинты |
| **Доступ к исходному коду** | Не требуется | Не требуется | Не требуется | Требуется | Не требуется | Не требуется | Не требуется |
| **Частота обновления** | Низкая/средняя | По требованию | Средняя/высокая | Высокая | Средняя/высокая | Низкая | Средняя |
| **Сложность трансформации** | Простая | Средняя | Высокая | Высокая | Средняя | Простая | Средняя |
| **Поддержка Native Histograms** | Нет | Зависит от реализации | Да | Да | Да | Да (v1.9+) | Да |
| **Exemplars** | Нет | Нет | Да | Да | Да | Нет | Нет |
| **Overhead на инфраструктуру** | Минимальный | Средний | Средний/высокий | Минимальный | Средний | Средний | Низкий |

### Протоколы скрейпинга и формат экспозиции

Начиная с Prometheus v2.49 и особенно в v3.0+, поддерживается явный выбор формата через `scrape_protocols`. Это расширяемость на уровне протокола без изменения кода экспортера.

```yaml
scrape_configs:
  - job_name: 'modern-app'
    scrape_protocols:
      - OpenMetricsText
      - PrometheusProtobuf
      - OpenTelemetryProtobuf
    static_configs:
      - targets: ['app1:8080']
```

**Приоритет протоколов:** Prometheus последовательно пытается использовать первый доступный протокол из списка. `OpenMetricsText` предпочтительнее для совместимости; `Protobuf` — для производительности при больших объемах Native Histograms.

**Влияние на экспортер:** Экспортер должен корректно обрабатывать заголовок `Accept` от Prometheus. Клиентские библиотеки Prometheus делают это автоматически; для кастомных экспортеров требуется явная поддержка.

## Практические сценарии

### Именование метрик (Prometheus 3.0+)

С появлением поддержки UTF-8 в Prometheus 3.x, правила именования стали более гибкими, но рекомендации по консистентности сохраняются:

* **Регистр и символы:** Рекомендуется нижний регистр `[a-z0-9_.]`. Точки (`.`) теперь официально разрешены и рекомендуются при интеграции с OpenTelemetry.
* **Namespace:** Префикс должен указывать на имя приложения или экспортера (например, `haproxy_`, `nginx_`, `system.`).
* **Суффиксы типа:**
  * `_total` — для Counter (обязательно).
  * `_created` — время создания серии.
  * `_info` — для метаданных (значение всегда `1`).
* **Базовые единицы:** Обязательны в названии (базовые единицы СИ): `_seconds`, `_bytes`, `_joules`, `_celsius`.

**Примеры именования:**
```text
# Старый стиль (v2): process_memory_working_set_bytes
# OTel стиль (v3): process.memory.working_set.bytes
```

### Дизайн лейблов и ресурсных атрибутов

* **Кардинальность:** Основной риск стабильности мониторинга. Никогда не используйте динамические данные (ID сессий, email, полные URL) в лейблах.
* **Resource Attributes (OTLP):** При использовании OTLP атрибуты ресурса (`service.name`, `k8s.pod.name`) автоматически преобразуются в лейблы или метаданные.
* **Service Discovery:** Экспортер должен отдавать только «сырые» данные. Лейблы инфраструктуры (`env`, `zone`, `cluster`) добавляются через [Relabeling](../../service_discovery_and_relabeling.md) на стороне Prometheus.

### Использование Native Histograms

В 2026 году при разработке экспортеров рекомендуется переходить от классических гистограмм к Native Histograms:
* **Точность:** Не требуют ручного подбора бакетов.
* **Эффективность:** Занимают в 3–5 раз меньше места в TSDB при гораздо большей точности квантилей.
* **Библиотеки:** Используйте последние версии `client_golang` или `client_python` с поддержкой экспоненциальных бакетов.

### Валидация работоспособности экспортера

После развертывания любого механизма расширения выполните стандартный набор проверок:

**1. Доступность эндпоинта:**
```bash
curl -s http://localhost:9100/metrics | head -n 20
# → # HELP node_cpu_seconds_total ...
# → # TYPE node_cpu_seconds_total counter
```

**2. Проверка формата:**
```bash
curl -s http://localhost:9100/metrics | promtool check metrics
# → SUCCESS: 123 metrics
```

**3. Проверка метрики `up`:**
```bash
curl -s http://localhost:9100/metrics | grep '^up'
# → up 1
```

**4. Проверка в Prometheus UI:**
```bash
# В Targets Prometheus UI должны отсутствовать ошибки для job экспортера
curl -s http://localhost:9090/api/v1/targets | jq '.data.activeTargets[] | select(.job=="node_exporter") | .health'
# → "up"
```

### Управление жизненным циклом метрик и stale markers

При graceful shutdown экспортер должен явно передавать `stale NaN` для всех метрик, чтобы Prometheus немедленно прекращал отслеживание рядов. Это критично для снижения churn rate в динамических средах.

**Пример на Go (client_golang):**
```go
func (c *MyCollector) Collect(ch chan<- prometheus.Metric) {
    if shuttingDown {
        for _, desc := range c.descriptors {
            ch <- prometheus.NewInvalidMetric(desc, math.Float64frombits(valueOfStaleNaN))
        }
        return
    }
    // нормальный сбор
}
```

**Алерт на несвоевременное обновление (для Textfile Collector):**
```promql
time() - myapp_backup_last_run_seconds > 90000
```

**Опасность:** При аварийном завершении экспортер не передает `stale NaN`. Prometheus будет считать ряд активным в течение 5 минут (lookback delta). При массовом перезапуске это создает пиковую нагрузку на индекс TSDB.

### Таймауты, лимиты ресурсов и производительность

| Параметр | Рекомендация | Обоснование |
|:---|:---|:---|
| `scrape_timeout` | < `scrape_interval` на 2–3s | Предотвращение наложения скрапингов |
| `scrape_interval` (инфраструктура) | 30–60s | Баланс актуальности и нагрузки |
| `scrape_interval` (приложения) | 5–15s | Более частый сбор для критичных сервисов |
| CPU limit (экспортер) | 0.5–2 ядра | Зависит от паттерна сбора |
| Memory limit (экспортер) | 128–512MB | Для кэширующих экспортеров — до 2GB |
| Максимум файлов в Textfile Collector | < 500 | Node Exporter парсит все файлы при каждом скрапинге |

**Производительность Prometheus при большом количестве экспортеров:**
При 500 целях с 1000 метрик каждая TSDB записывает ~500K samples/цикл. Это требует:
- WAL на NVMe SSD (высокая IOPS)
- Head Block RAM: ~8–16 ГБ на 1M активных рядов
- scrape_interval: не ниже 15s для предотвращения перегрева индекса

### Чек-лист SRE перед развертыванием экспортера

1. **Выбран оптимальный механизм** — см. критерии выбора выше.
2. **Имена метрик соответствуют конвенциям** — нижний регистр, `_total` для счетчиков, базовые единицы в названии.
3. **Лейблы не содержат высококардинальных значений** — нет email, ID сессий, полных URL.
4. **Настроен `scrape_timeout`** — меньше `scrape_interval` минимум на 2 секунды.
5. **Настроены лимиты ресурсов** — CPU и Memory limits для контейнера/systemd unit.
6. **Реализован stale marker** — экспортер передает `stale NaN` при shutdown (или используется `_last_run_seconds` для Textfile).
7. **Эндпоинт защищен** — TLS, Basic Auth или сетевая изоляция (Firewall/NetworkPolicy).
8. **Протестирован формат** — `promtool check metrics` проходит без ошибок.
9. **Настроены алерты** — `up` метрика, отсутствие данных (`absent_over_time`).
10. **Документирована зависимость** — при сбое экспортера какие алерты должны сработать.

## Дополнительная информация

### Матрица совместимости версий Prometheus и возможностей

| Возможность | Prometheus v2.40 | Prometheus v2.49+ | Prometheus v3.0+ |
|:---|:---|:---|:---|
| **Native Histograms** | Частичная | Полная | Полная + sparse |
| **UTF-8 в именах** | Нет | Частичная (escaping) | Полная |
| **OpenMetrics 2.0** | Нет | Да | Да |
| **OTLP Receiver** | Нет | Нет | Да (нативный) |
| **scrape_protocols** | Нет | Да (Protobuf, OpenMetrics) | Да (+ OTLP) |
| **Exemplars** | Нет | Да | Да |

### Выбор протокола: OpenMetrics vs OTLP

| Сценарий | Рекомендуемый протокол | Причина |
| :--- | :--- | :--- |
| **Legacy / Infra** | OpenMetrics (Pull) | Простота, совместимость с Service Discovery. |
| **Собственные экспортеры** | OpenMetrics (Pull) | Стандарт, широкая поддержка в client_golang. |
| **OTel-instrumented приложения** | OTLP (Pull/Push) | Унификация с трейсами, гибкость имен (UTF-8). |
| **Edge / IoT** | OTLP (Push) | Работа за NAT, отсутствие входящих соединений. |

### Типичные ошибки (Anti-patterns)

- **Timestamp в экспортере:** По умолчанию Prometheus сам ставит время скрапинга. Указывайте timestamp вручную только для исторических данных или Textfile Collector (через `_last_run_seconds`).
- **Отсутствие метаданных:** Пропуск `# HELP` и `# TYPE` затрудняет использование данных и ломает интеграцию с инструментами визуализации.
- **Игнорирование кардинальности:** Создание тысяч временных рядов на один инстанс ведет к деградации производительности Prometheus.
- **Hardcoded лейблы в экспортере:** Добавление `env`, `zone`, `cluster` в коде экспортера делает его непереносимым между окружениями. Используйте [Relabeling](../../service_discovery_and_relabeling.md).
- **Отсутствие graceful shutdown:** При аварийном завершении экспортер не передает `stale NaN`. Prometheus хранит «фантомные» ряды до 5 минут.
- **Слишком широкие права у Textfile Collector:** Директория с метриками должна быть доступна на запись только генераторам, на чтение — `node_exporter`.

### Ограничения и edge cases

- **Textfile Collector и Native Histograms:** Формат `.prom` поддерживает только классические бакеты. Для нативных гистограмм используйте OTLP или бинарный Protobuf.
- **Script Exporter и concurrency:** Если Prometheus делает параллельные запросы к Script Exporter, убедитесь, что скрипты потокобезопасны или экспортер использует очередь.
- **Pushgateway и репликация:** Pushgateway — single point of failure. Для production развертывайте минимум 2 инстанса за балансировщиком с sticky sessions (ключ — grouping key).
- **OTLP и UTF-8:** При использовании UTF-8 имен убедитесь, что версия Grafana >= 11 корректно экранирует символы для предотвращения XSS.

### Безопасность экспортеров

Экспортеры часто имеют доступ к критическим системным вызовам или данным БД. Рекомендации:

- **TLS и аутентификация:** Используйте `exporter-toolkit` для настройки TLS и Basic Auth. Никогда не оставляйте эндпоинты открытыми в публичных сетях. Подробнее: [Безопасность Prometheus](../../security.md).
- **Минимальные привилегии:** Запуск процесса от не-root пользователя с доступом только к необходимым ресурсам.
- **Сетевая изоляция:** Ограничение доступа к порту экспортера на уровне Firewall (только для IP серверов мониторинга) или NetworkPolicy.
