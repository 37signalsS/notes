# Архитектура мониторинга с Prometheus

**Prometheus** — это современная система мониторинга и оповещения с открытым исходным кодом, изначально разработанная в SoundCloud. Она стала стандартом де-факто для мониторинга в облачных и контейнерных средах, особенно в экосистеме Kubernetes.

## Ключевые особенности и архитектура

В отличие от классических систем мониторинга (таких как Nagios или Zabbix), Prometheus спроектирован для работы в динамичных средах, где сервисы и инфраструктура могут постоянно изменяться.

### 1. Модель сбора данных: Pull vs. Push

- **Pull-модель (основная):** Prometheus-сервер периодически сам опрашивает (scrapes) целевые системы (таргеты) по HTTP, забирая у них метрики. Это основной и рекомендуемый способ сбора данных.
  - **Преимущества:**
    - Централизованная конфигурация: все таргеты настраиваются на стороне Prometheus.
    - Легкость отладки: можно просто открыть URL метрик в браузере и увидеть, что отдает таргет.
    - Упрощает мониторинг: Prometheus знает, какие таргеты доступны, а какие нет.

- **Push-модель (для специфических задач):** Для короткоживущих задач (например, batch-jobs), которые могут завершиться до того, как Prometheus их опросит, используется промежуточный компонент **Pushgateway**. Задача отправляет свои метрики в Pushgateway, а Prometheus уже забирает их оттуда.

> Подробное сравнение различных стратегий сбора метрик (Push, Pull, из логов) рассмотрено в заметке: **[Стратегии сбора метрик](../Concepts/metrics_collection_strategies.md)**.


### 2. Экспортеры (Exporters)

Чтобы Prometheus мог собирать метрики с системы или приложения, на них должен быть запущен **экспортер**. Экспортер — это небольшое приложение, которое собирает внутренние метрики и предоставляет их по HTTP в формате, понятном для Prometheus.

- **Node Exporter:** Самый распространенный экспортер, который собирает системные метрики с хоста Linux (CPU, память, диски, сеть и т.д.).
- **Другие экспортеры:** Существует огромное количество готовых экспортеров для баз данных (MySQL, PostgreSQL), веб-серверов (Nginx), брокеров сообщений и многого другого.

### 3. База данных временных рядов (TSDB)

Prometheus хранит все собранные данные в локальной **базе данных временных рядов (Time Series Database, TSDB)**, которая оптимизирована для хранения и запроса данных вида "метка-значение-время".

- **Метрика:** Каждая метрика имеет имя и набор пар "ключ-значение", называемых **метками (labels)**. Например: `http_requests_total{method="POST", handler="/api/users"}`.
- **Хранение:** Данные хранятся на локальном диске сервера Prometheus. Система не рассчитана на долгосрочное кластерное хранение "из коробки", но может интегрироваться с внешними хранилищами (например, VictoriaMetrics, Thanos).

### 4. Service Discovery

В динамических средах (например, Kubernetes) IP-адреса сервисов постоянно меняются. Механизм **Service Discovery** позволяет Prometheus автоматически обнаруживать новые таргеты для мониторинга, интегрируясь с API облачных провайдеров, Kubernetes, Consul и т.д.

### 5. Система оповещений: Alertmanager

Prometheus не отправляет оповещения напрямую. Его задача — на основе заданных правил (`alerting rules`) генерировать события (алерты) и отправлять их в отдельный компонент — **Alertmanager**.

**Alertmanager** отвечает за:
- **Дедупликацию:** Объединяет одинаковые алерты в одно уведомление.
- **Группировку:** Группирует связанные алерты (например, все алерты из одного кластера) в одно сообщение.
- **Маршрутизацию:** Отправляет уведомления в разные каналы (Email, Slack, Telegram, PagerDuty) в зависимости от меток алерта.
- **Подавление (Silencing):** Позволяет временно "заглушить" алерты во время плановых работ.

### 6. Визуализация: Grafana

Хотя у Prometheus есть собственный простой веб-интерфейс для выполнения запросов (PromQL) и построения графиков, стандартом для визуализации метрик является **Grafana**.

Grafana подключается к Prometheus как к источнику данных и позволяет создавать сложные, интерактивные дашборды для наглядного представления состояния системы.
