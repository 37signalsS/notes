# Alertmanager: Обзор, настройка и высокая доступность

**Alertmanager** — это компонент стека [[./overview.md|Prometheus]], который отвечает за обработку оповещений (алертов), отправленных серверами Prometheus. Его главная задача — не просто пересылать алерты, а управлять ими: дедуплицировать, группировать, заглушать и маршрутизировать их в правильные каналы, чтобы в идеальном мире один инцидент генерировал только одно уведомление.

## 1. Определения и базовые концепции

### Разделение ролей Prometheus и Alertmanager

В системе оповещений две подсистемы отвечают за обработку алертов:
1.  **Prometheus:** Проверяет текущие данные на соответствие заданным [[./rules.md|правилам оповещений (`alerting rules`)]]. Если условие выполнено, Prometheus не отправляет алерт напрямую, а лишь вызывает "хук" (webhook) к системе обработки алертов.
2.  **Alertmanager:** Получает эти вызовы от Prometheus, обрабатывает их и генерирует конечное сообщение, которое затем будет отправлено получателям.

Такое разделение позволяет использовать один Alertmanager для нескольких экземпляров Prometheus, что значительно упрощает настройку уведомлений.

### Конвейер обработки оповещений

Для эффективного управления алертами Alertmanager использует конвейер обработки, состоящий из нескольких стадий.

1.  **Группировка (Grouping):**
    *   Очень мощный механизм, который позволяет группировать схожие уведомления в одно.
    *   **Пример:** Если база данных, обслуживающая 20 микросервисов, становится недоступной, Alertmanager может сгруппировать 20 алертов от этих сервисов в одно общее уведомление о недоступности базы данных.

2.  **Подавление (Inhibition):**
    *   Концепция, позволяющая подавлять одни алерты при наличии других, более общих.
    *   **Пример:** Если весь дата-центр недоступен (сработал алерт `DataCenterDown`), логично не получать уведомления о недоступности каждого отдельного сервера или сервиса в этом дата-центре. Правило подавления может автоматически "заглушить" все специфичные алерты, пока активен более глобальный.

3.  **"Замалчивание" (Silencing):**
    *   Позволяет вручную отключать уведомления для алертов с определенными метками на заданный период времени.
    *   **Пример:** Если о проблеме уже известно и над ней работают, или если проводятся плановые технические работы, можно создать "silence", чтобы не получать лишних уведомлений.

4.  **Маршрутизация (Routing):**
    *   В сложных системах с множеством команд и зон ответственности, роутинг позволяет направлять алерты нужным получателям.
    *   **Пример:** Алерты, связанные с базой данных (например, `owner=dba_team`), отправляются команде администраторов БД, а алерты от фронтенд-приложений — команде фронтенда.

5.  **Троттлинг и повторы:**
    *   **Задержка (`group_wait`):** Alertmanager может задерживать отправку первого уведомления, чтобы дождаться всех алертов, входящих в одну группу.
    *   **Повторные уведомления (`repeat_interval`):** Alertmanager может повторно отправлять уведомления через заданные промежутки времени, как будильник, до тех пор, пока алерт не будет устранен.

6.  **Отправка (Notification):**
    *   Последний этап, на котором сконфигурированные и обработанные уведомления отправляются в конечные системы: Email, Slack, PagerDuty, Webhooks и т.д.

### Веб-интерфейс Alertmanager

Веб-интерфейс Alertmanager по умолчанию доступен по порту `9093`. Он имеет несколько основных разделов:

*   **Alerts:** Отображает текущие активные алерты с возможностью фильтрации по лейблам.
*   **Groups:** Позволяет просматривать сгруппированные алерты.
*   **Silences:** Управляет "замалчиваниями" (создание, редактирование, удаление).
*   **Status:** Отображает техническую информацию о работе Alertmanager, включая его конфигурацию и состояние кластера (в режиме HA).

## 2. Настройка и конфигурация

> **Руководство по установке**: Инструкции по ручной установке Alertmanager находятся в заметке [[./installation/from_binary.md#4-установка-alertmanager]].

### 2.1. Ключи запуска Alertmanager

| Ключ | Значение по умолчанию | Описание |
| :--- | :--- | :--- |
| `--config.file` | `alertmanager.yml` | Имя конфигурационного файла. |
| `--storage.path` | `data/` | Путь, куда сохраняются данные. |
| `--data.retention` | `120h` | Как долго хранить данные. |
| `--web.listen-address` | `:9093` | Адрес и порт для UI и API. |
| `--cluster.listen-address` | `"0.0.0.0:9094"` | Адрес для HA кластера (gossip). Пустое значение отключает HA. |
| `--cluster.peer` | `-` | Адреса пиров в HA кластере. |
| `--log.level` | `info` | Уровень логирования: `debug`, `info`, `warn`, `error`. |

### 2.2. Структура `alertmanager.yml`

#### Блок `global`

Здесь объявляются глобальные параметры по умолчанию.

*   `resolve_timeout`: (default: `5m`) Время, через которое алерт считается решенным, если он не был обновлен.
*   `smtp_*`: Глобальные настройки для отправки почты.

#### Блок `route`

В этом блоке настраивается древовидная структура маршрутизации оповещений.

*   `receiver`: Имя получателя по умолчанию для корневого маршрута.
*   `group_by`: Набор меток для агрегации алертов. `['...']` отключает группировку.
*   `continue`: (default: `false`) Если `false`, обработка прекращается при первом совпадении.
*   `match` / `match_re`: Список меток для точного или regex-совпадения, определяющий выбор маршрута.
*   `group_wait`, `group_interval`, `repeat_interval`: Временные интервалы для группировки и повторной отправки.
*   `routes`: Вложенные маршруты.


```yaml
route:
  receiver: 'default-receiver'
  group_by: [cluster, alertname]
  routes:
  - receiver: 'db-team'
    match_re:
      service: mysql|postgres
  - receiver: 'frontend-team'
    match:
      team: frontend
```

#### Блок `receivers`

Именованная конфигурация одного или нескольких получателей (email, Slack, PagerDuty, webhook и др.).

#### Блок `inhibit_rules`

Позволяет подавлять одни алерты при наличии других.
*   `target_match` / `target_match_re`: Метки алерта, который будет подавлен.
*   `source_match` / `source_match_re`: Метки алерта, который должен уже существовать для срабатывания правила.
*   `equal`: Набор меток, которые должны совпадать в обоих алертах.

## 3. Практический сценарий: Настройка и тестирование

1.  **Создаем конфигурационный файл**

    Предполагается, что у вас есть настроенный почтовый сервер. Замените плейсхолдеры `<...>` на реальные данные.

    ```bash
    cat <<EOF > /etc/alertmanager/alertmanager.yml
    global:
      smtp_smarthost: smtp.yandex.ru:465
      smtp_from: '<user name>@edu-prom.slurm.io'
      smtp_auth_username: '<user name>@edu-prom.slurm.io'
      smtp_auth_password: '<Password>'

    route:
      group_by: ['alertname', 'service']
      group_wait: 30s
      group_interval: 5m
      repeat_interval: 1h
      receiver: team-monitoring

      routes:
      - match:
          service: prom
        receiver: team-ops
      - match:
          severity: (warnings|error|critical)
        receiver: team-monitoring

inhibit_rules:
- source_match:
    severity: 'critical'
    alertname: PrometheusConfigurationReload
  target_match:
    severity: 'critical'

receivers:
- name: 'team-ops'
  email_configs:
    - to: '<email_1>'
      send_resolved: true
      require_tls: false
- name: 'team-monitoring'
  email_configs:
    - to: '<email_2>'
      send_resolved: true
    EOF
    ```
    **Логика данной конфигурации:**
    *   Все сообщения с `service: prom` отправляются команде `team-ops`.
    *   Все алерты с `severity: critical, error, warning` отправляются команде `team-monitoring`.
    *   Если активен алерт `PrometheusConfigurationReload`, другие алерты с `severity: critical` будут подавлены.
    > Для визуализации и отладки сложных деревьев маршрутизации можно воспользоваться [официальным редактором](https://www.prometheus.io/webtools/alerting/routing-tree-editor/).

2.  **Перезагружаем Alertmanager:**
    ```bash
    systemctl reload alertmanager.service
    ```

3.  **Тестирование**

    *   **Сломайте конфиг [[./configuration.md|Prometheus]]**, добавив в начало `prometheus.yml` невалидный символ, и перезагрузите его (`systemctl reload prometheus.service`). Должен прийти алерт об ошибке конфигурации.
    *   **Остановите `node_exporter`** на нескольких серверах (`systemctl stop node_exporter.service`). В UI Prometheus появятся алерты `ExporterDown`. Новых email приходить не должно, так как работает правило подавления.
    *   **Исправьте конфиг Prometheus** и перезагрузите его. Теперь должно прийти уведомление о решении проблемы с конфигурацией и общее уведомление о недоступности нескольких экспортеров.

## 4. Продвинутые детали: Высокая доступность (High Availability)

Для обеспечения отказоустойчивости (см. также [[./scaling/overview.md|масштабирование Prometheus]]) Alertmanager разворачивается в виде кластера из нескольких экземпляров.

### Архитектура и принцип работы

Alertmanager имеет встроенную поддержку кластеризации, основанную на **gossip-протоколе**. Это позволяет экземплярам обмениваться информацией о полученных алертах, созданных "подавлениях" (silences) и отправленных уведомлениях.

Ключевая функция кластера — **дедупликация уведомлений**. Если несколько экземпляров Prometheus отправляют один и тот же алерт разным экземплярам Alertmanager, кластерный механизм гарантирует, что конечное уведомление будет отправлено **только один раз**.

### Настройка кластера вручную

Для создания кластера необходимо запустить как минимум два (рекомендуется три для кворума) экземпляра Alertmanager, указав им адреса соседей через флаг `--cluster.peer`.

**На сервере 1:**
```bash
# /etc/sysconfig/alertmanager
OPTIONS="... --cluster.peer <server2_IP>:9094"
```

**На сервере 2:**
```bash
# /etc/sysconfig/alertmanager
OPTIONS="... --cluster.peer <server1_IP>:9094"
```
*   Порт `9094` (по умолчанию) используется для gossip-коммуникации.
*   После изменения опций перезапустите сервисы Alertmanager.
*   Проверить состояние кластера можно в веб-интерфейсе любого из экземпляров на вкладке **Status**.

### Настройка в Kubernetes

В Kubernetes настройка кластера значительно упрощается при использовании Helm-чарта `kube-prometheus-stack`. Достаточно установить количество реплик > 1:

```yaml
alertmanager:
  replicaCount: 3
```
Helm-чарт автоматически сгенерирует конфигурацию, в которой поды Alertmanager будут обнаруживать друг друга через внутренний DNS Kubernetes.
