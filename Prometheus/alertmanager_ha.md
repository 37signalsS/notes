# Высокая доступность для Alertmanager

**Alertmanager** — критически важный компонент стека мониторинга, отвечающий за дедупликацию, группировку и маршрутизацию оповещений. Выход из строя единственного экземпляра Alertmanager может привести к тому, что вы не получите важных уведомлений о сбоях.

Для обеспечения отказоустойчивости Alertmanager разворачивается в виде кластера из нескольких экземпляров.

## Архитектура и принцип работы

Alertmanager имеет встроенную поддержку кластеризации, основанную на **gossip-протоколе**. Это позволяет экземплярам Alertmanager обмениваться информацией о полученных алертах и принятых решениях.

**Принцип работы кластера:**

1.  **Обнаружение:** Экземпляры Alertmanager должны знать адреса друг друга для формирования кластера. Это настраивается с помощью флагов командной строки (`--cluster.peer`).
2.  **Обмен состоянием:** Используя gossip-протокол, экземпляры синхронизируют между собой информацию о:
    *   Входящих алертах.
    *   Созданных "подавлениях" (silences).
    *   Отправленных уведомлениях.
3.  **Дедупликация уведомлений:** Это ключевая функция кластера. Если несколько экземпляров Prometheus отправляют один и тот же алерт разным экземплярам Alertmanager, кластерный механизм гарантирует, что конечное уведомление (например, в Slack или PagerDuty) будет отправлено **только один раз**. Один из узлов кластера берет на себя ответственность за отправку.

Благодаря этому, можно направлять алерты от всех экземпляров Prometheus на все экземпляры Alertmanager, и система сама разберется с дубликатами.

## Настройка кластера

Для создания кластера необходимо запустить как минимум два (рекомендуется три для кворума) экземпляра Alertmanager, указав им адреса соседей.

Пример флагов для запуска трех экземпляров:

**Alertmanager 1:**
```bash
./alertmanager --cluster.peer=AM2_IP:9094 --cluster.peer=AM3_IP:9094 ...
```

**Alertmanager 2:**
```bash
./alertmanager --cluster.peer=AM1_IP:9094 --cluster.peer=AM3_IP:9094 ...
```

**Alertmanager 3:**
```bash
./alertmanager --cluster.peer=AM1_IP:9094 --cluster.peer=AM2_IP:9094 ...
```

*   Порт `9094` (по умолчанию) используется для gossip-коммуникации.
*   `--cluster.listen-address` используется, чтобы указать адрес, который будет слушать данный экземпляр.

### Настройка в Kubernetes

В Kubernetes настройка кластера значительно упрощается, особенно при использовании Helm-чарта `kube-prometheus-stack`.

Для включения высокой доступности достаточно изменить следующие параметры в `values.yaml`:

```yaml
alertmanager:
  ## Количество реплик Alertmanager. Для HA установите значение > 1.
  ## Рекомендуется 3 для стабильного кворума.
  replicaCount: 3

  alertmanagerSpec:
    ## Если используется StatefulSet, поды будут иметь предсказуемые имена
    ## (e.g., alertmanager-main-0, alertmanager-main-1), что позволяет
    ## автоматически настроить обнаружение пиров.
    # ...
```

Helm-чарт автоматически сгенерирует конфигурацию, в которой поды Alertmanager будут обнаруживать друг друга через внутренний DNS Kubernetes, избавляя от необходимости прописывать IP-адреса вручную.

## Проверка работы кластера

После запуска кластера вы можете проверить его состояние, обратившись к веб-интерфейсу любого из экземпляров Alertmanager по адресу `/#/status`. На этой странице будет отображен список всех членов кластера и их состояние.

## Практическое руководство: Настройка HA-кластера вручную

Этот раздел описывает настройку кластера Alertmanager на двух виртуальных машинах.

1.  **Устанавливаем второй Alertmanager:**
    *   Подключитесь к второму серверу (`server1`).
    *   Установите Alertmanager, следуя стандартной [инструкции по установке](./alertmanager_setup.md).

2.  **Настраиваем кластер:**

    Настройка производится через флаг `--cluster.peer`, который указывает экземпляру адрес его соседа для обмена информацией по gossip-протоколу.

    2.1. **На `server1`** измените файл с опциями запуска (`/etc/sysconfig/alertmanager`), добавив IP-адрес первого сервера (`monitoring`):
    ```bash
    # /etc/sysconfig/alertmanager на server1
    OPTIONS="--config.file=/etc/alertmanager/alertmanager.yml \
      --storage.path=/var/lib/alertmanager/ \
      --cluster.peer <monitoring_IP>:9094"
    ```
    > **NB!** Обратите внимание, что используется порт `9094`, который по умолчанию предназначен для gossip-коммуникации.

    2.2. **Перезапустите Alertmanager на `server1`:**
    ```bash
    systemctl restart alertmanager.service
    ```

    2.3. **На сервере `monitoring`** проделайте аналогичную операцию, указав IP-адрес `server1`:
    ```bash
    # /etc/sysconfig/alertmanager на monitoring
    OPTIONS="--config.file=/etc/alertmanager/alertmanager.yml \
      --storage.path=/var/lib/alertmanager/ \
      --cluster.peer <server1_IP>:9094"
    ```

    2.4. **Перезапустите Alertmanager на `monitoring`:**
    ```bash
    systemctl restart alertmanager.service
    ```

3.  **Проверяем работу:**
    Откройте в браузере веб-интерфейс любого из Alertmanager и перейдите на страницу статуса: `http://<любой_из_IP>:9093/#/status`.
    
    На странице в разделе **Peers** вы должны увидеть оба экземпляра Alertmanager как членов кластера.
