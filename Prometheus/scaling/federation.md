# Федерация Prometheus

Федерация в Prometheus — это специализированный механизм, позволяющий одному Prometheus Server собирать метрики с других Prometheus Server'ов. Это полезно для агрегации данных из нескольких источников, создания иерархических систем мониторинга и решения задач долгосрочного хранения метрик.

## Принцип работы Федерации

Федерация реализуется через специальный `endpoint` на Prometheus Server, при обращении к которому можно получить список всех метрик и их значений на момент запроса.

### Сценарии использования

1.  **Агрегация данных из нескольких дата-центров:** Если у вас есть несколько дата-центров, в каждом из которых развернут свой Prometheus Server, федерация позволяет собрать все эти данные в одном центральном Prometheus Server для удобной визуализации и эффективного алертинга.
2.  **Шардирование Prometheus:** Можно использовать федерацию для создания шардированной архитектуры, где один Prometheus Server собирает данные с серверов, другой — с приложений, а затем все эти данные агрегируются в одном вышестоящем Prometheus Server. Вокруг этого центрального сервера уже строится система визуализации и алертинга.
3.  **Долгосрочное хранение метрик:** Разработчики Prometheus не рекомендуют использовать его для длительного хранения метрик (оптимальный срок — около 14 дней). Федерация может быть решением этой проблемы. Несколько Prometheus Server'ов могут собирать данные с высокой частотой, а вышестоящий Prometheus Server через федерацию собирает с них данные с гораздо более низкой частотой. Таким образом, создается группа Prometheus Server'ов: одни хранят оперативные данные с высокой детализацией, другие — исторические данные с меньшей детализацией.

## Нюансы и важные настройки

### Служебные метки `instance` и `job`

Prometheus Server автоматически добавляет служебные метки `instance` и `job` в процессе скрапинга. При получении метрик через федерацию с нижестоящего Prometheus Server эти метки уже присутствуют. По умолчанию вышестоящий Prometheus перезапишет их, что не всегда желательно.

**Решение:** Используйте настройку `honor_labels: true` в конфигурации скрапинга для федерации. Эта настройка указывает Prometheus Server сохранять оригинальные значения для всех меток, полученных от нижестоящего сервера.

```yaml
scrape_configs:
  - job_name: 'federate'
    scrape_interval: 15s
    honor_labels: true # Сохранять оригинальные метки
    # ... другие настройки
```

### Идентификация источника метрик с `external_labels`

В некоторых случаях необходимо знать, с какого именно Prometheus Server была получена та или иная метрика.

**Решение:** Используйте настройку `external_labels` в глобальной конфигурации Prometheus Server. Эта настройка позволяет добавить дополнительную метку ко всем метрикам, собираемым данным Prometheus Server.

```yaml
global:
  external_labels:
    cluster: 'main-cluster' # Пример метки для идентификации кластера
    prom_instance: 'prom-01' # Пример метки для идентификации экземпляра Prometheus
```

Благодаря этой дополнительной метке всегда можно определить источник метрики.

### Ограничения: Потеря исторических данных

Важная особенность и ограничение федерации заключается в том, как Prometheus обрабатывает временные ряды. Вышестоящий сервер обращается к `/federate` эндпоинту нижестоящего и получает **только последние значения** для каждой метрики на момент запроса.

Это означает, что если нижестоящий Prometheus собирает метрики каждые 15 секунд, а вышестоящий опрашивает его раз в 5 минут, то все промежуточные данные, собранные за эти 5 минут, будут **потеряны** для верхнеуровневого сервера.

Из-за этого федерация не предназначена для создания точной копии исторических данных. Она служит для:
*   Агрегации текущего состояния системы.
*   Сбора данных с пониженной детализацией для долгосрочного хранения (с осознанной потерей точности).

## Конфигурация Федерации

Пример конфигурации `scrape_configs` для федерации:

```yaml
scrape_configs:
  - job_name: 'federate'
    scrape_interval: 1m # Частота сбора данных с нижестоящих Prometheus
    honor_labels: true
    metrics_path: '/federate' # Стандартный путь для федерации
    params:
      'match[]':
        - '{job="prometheus"}' # Пример: собирать метрики только с job="prometheus"
        - '{__name__=~"job:.*"}' # Пример: собирать агрегированные метрики
    static_configs:
      - targets:
          - 'prom-dc1.example.com:9090' # Адрес нижестоящего Prometheus Server
          - 'prom-dc2.example.com:9090'
```

**Пояснения:**

*   `job_name: 'federate'`: Имя задания скрапинга для федерации.
*   `scrape_interval`: Интервал, с которым вышестоящий Prometheus будет запрашивать метрики у нижестоящих.
*   `honor_labels: true`: Сохраняет оригинальные метки.
*   `metrics_path: '/federate'`: Указывает, что Prometheus должен обращаться к `/federate` endpoint'у нижестоящего сервера.
*   `params: 'match[]'`: Позволяет фильтровать, какие метрики будут собираться. Можно указать PromQL-запросы для выбора конкретных метрик.
*   `static_configs`: Определяет список нижестоящих Prometheus Server'ов, с которых будут собираться данные.

Федерация Prometheus является мощным инструментом для построения масштабируемых и отказоустойчивых систем мониторинга, но требует внимательного подхода к конфигурации и понимания ее особенностей.
