# Федерация Prometheus
> **Федерация** — один из подходов к **[[./overview.md|масштабированию Prometheus]]**.

## 1. Определения

**Федерация** в Prometheus — это иерархическая конфигурация, при которой один сервер Prometheus (вышестоящий) опрашивает другой (нижестоящий) для получения данных. Этот механизм позволяет агрегировать или отфильтровывать временные ряды с других серверов.

---

## 2. Основные концепции

### Принцип работы
Федерация использует стандартный эндпоинт `/federate`. При обращении к нему нижестоящий сервер отдает **последние значения** временных рядов, соответствующих параметру `match[]` в запросе. Таким образом, вышестоящий сервер не получает полную историю метрик, а лишь их срез на момент опроса.

### Сценарии использования

1.  **Агрегация данных из нескольких источников:** Если у вас есть несколько дата-центров или проектов, каждый со своим Prometheus, федерация позволяет собрать ключевые метрики в одном центральном сервере для получения общей картины.
2.  **Шардирование Prometheus:** Можно создать архитектуру, где разные серверы Prometheus отвечают за разные группы таргетов (например, один за инфраструктуру, другой за приложения), а "главный" сервер агрегирует с них данные.
3.  **Долгосрочное хранение (с понижением детализации):** Вышестоящий сервер может с низкой частотой (например, раз в 5-10 минут) собирать данные с нижестоящих, которые, в свою очередь, опрашивают таргеты с высокой частотой (например, раз в 15 секунд). Это позволяет хранить исторические данные дольше, но с потерей гранулярности.

## 3. Практические сценарии

### Пример конфигурации
Конфигурация для вышестоящего (федерирующего) сервера:
```yaml
# /etc/prometheus/prometheus.yml
scrape_configs:
  - job_name: 'federate'
    scrape_interval: 1m
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{job="prometheus"}'      # Собирать метрики с job="prometheus"
        - '{__name__=~"job:.*"}'   # Собирать агрегированные метрики (rules)
    static_configs:
      - targets:
          - 'prom-dc1.example.com:9090'
          - 'prom-dc2.example.com:9090'
```

### Пошаговая настройка
Рассмотрим настройку, где главный сервер `monitoring` собирает метрики с двух нижестоящих: `server1` и `server2`.

**Шаг 1. Настройка нижестоящих Prometheus**

На серверах `server1` и `server2` настройте Prometheus для сбора метрик только с локального `node_exporter`.
Конфигурация (`/etc/prometheus/prometheus.yml`):
```bash
cat <<EOF > /etc/prometheus/prometheus.yml
global:
  scrape_interval:     15s
  evaluation_interval: 15s
alerting:
  alertmanagers:
  - static_configs:
    - targets: ['<monitoring_IP>:9093']
scrape_configs:
  - job_name: 'prometheus'
    static_configs:
    - targets: ['localhost:9090']
  - job_name: 'node_exporter'
    static_configs:
    - targets: ['<server_ip>:9100']
EOF

systemctl restart prometheus.service
```

**Шаг 2. Настройка главного (федерирующего) Prometheus**

На сервере `monitoring` укажите в конфигурации нижестоящие серверы в качестве таргетов.
Конфигурация (`/etc/prometheus/prometheus.yml`):
```bash
cat <<EOF > /etc/prometheus/prometheus.yml
global:
  scrape_interval:     15s
  evaluation_interval: 15s
alerting:
  alertmanagers:
  - static_configs:
    - targets: ['localhost:9093']
scrape_configs:
  - job_name: 'federate'
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{job=~"node.+"}'
    static_configs:
    - targets:
      - '<server1_IP>:9090'
      - '<server2_IP>:9090'
EOF

systemctl restart prometheus.service
```

**Шаг 3. Проверка**
1.  Откройте UI главного Prometheus (`http://<monitoring_ip>:9090/targets`) и убедитесь, что в секции `federate` появились два активных таргета.
2.  Выполните PromQL-запрос `node_load1`. Должны отобразиться два временных ряда — по одному от каждого сервера.

## 4. Ограничения и нюансы конфигурации

*   **Потеря исторических данных:** Главный недостаток федерации — вышестоящий сервер получает **только последние значения** метрик. Все промежуточные значения, собранные между опросами, теряются. Это делает федерацию неподходящей для создания точных копий исторических данных.
*   **`honor_labels: true`:** Обязательная опция, которая указывает вышестоящему серверу не перезаписывать метки (`job`, `instance`), полученные от нижестоящего.
*   **`external_labels`:** Настройка на нижестоящем сервере, позволяющая добавить уникальную метку (например, `cluster: 'main-dc'`) для различения источников данных на вышестоящем сервере.
*   **Фильтрация метрик (`params`):** Всегда используйте параметр `match[]` для фильтрации метрик. Сбор всех временных рядов без фильтра может создать чрезмерную нагрузку на сеть и сервер.
