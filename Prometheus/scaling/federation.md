# Федерация Prometheus

> **Федерация** — иерархический подход к **[масштабированию Prometheus](./overview.md)**, при котором вышестоящий сервер опрашивает нижестоящие инстансы через эндпоинт `/federate`.
>
> **См. также:** [PromQL](../concepts/promql/selectors_operators.md), [Remote Read/Write](./remote_read_write.md) — альтернативный способ масштабирования.

## Определения

**Федерация** — механизм Prometheus, позволяющий одному серверу (вышестоящему) извлекать выборочные временные ряды с других серверов (нижестоящих) через HTTP-эндпоинт `/federate`. Вышестоящий сервер получает только последние значения метрик на момент опроса, а не полную историю.

---

## Основные концепции

### Принцип работы

Вышестоящий Prometheus опрашивает нижестоящие инстансы через эндпоинт `/federate`, указывая в параметре `match[]` селекторы нужных временных рядов. Нижестоящий сервер возвращает **только последние значения** метрик, соответствующих селекторам.

Ключевые особенности:

- **Не полная история:** передаётся срез метрик на момент опроса, промежуточные значения теряются.
- **Агрегация:** обычно вышестоящий сервер забирает уже агрегированные ряды (recording rules), а не сырые метрики.
- **`honor_labels: true`:** обязательная опция — предотвращает перезапись лейблов (`job`, `instance`) вышестоящим сервером.
- **`external_labels`:** настраиваются на нижестоящем сервере для уникальной идентификации источника (например, `cluster: dc1`).

### Сценарии использования

| Сценарий | Описание |
|---|---|
| **Агрегация из нескольких источников** | Сбор ключевых метрик (`up`, `requests_total`) из нескольких дата-центров или проектов на центральный сервер |
| **Шардирование** | Разные Prometheus отвечают за разные группы таргетов; вышестоящий агрегирует данные |
| **Долгосрочное хранение (пониженная детализация)** | Вышестоящий сервер опрашивает нижестоящие с низкой частотой (5–10 мин), снижая гранулярность, но увеличивая срок хранения |

## Практические сценарии

### Базовая конфигурация вышестоящего сервера

```yaml
# /etc/prometheus/prometheus.yml — вышестоящий сервер
scrape_configs:
  - job_name: 'federate'
    scrape_interval: 1m
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{job="prometheus"}'        # Метрики самого Prometheus
        - '{__name__=~"job:.*"}'    # Агрегированные метрики (recording rules)
    static_configs:
      - targets:
          - 'prom-dc1.example.com:9090'
          - 'prom-dc2.example.com:9090'
```

### Пошаговая настройка

**Шаг 1. Настройка нижестоящих Prometheus**

На каждом нижестоящем сервере добавить `external_labels` для уникальной идентификации:

```yaml
# /etc/prometheus/prometheus.yml — нижестоящий сервер
global:
  scrape_interval: 15s
  evaluation_interval: 15s
  external_labels:
    cluster: 'dc1'  # Уникальная метка для каждого сервера

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['<monitoring_ip>:9093']

scrape_configs:
  - job_name: 'prometheus'
    static_configs:
      - targets: ['localhost:9090']
  - job_name: 'node_exporter'
    static_configs:
      - targets: ['<server_ip>:9100']
```

**Шаг 2. Настройка вышестоящего сервера**

```yaml
# /etc/prometheus/prometheus.yml — вышестоящий сервер
global:
  scrape_interval: 15s
  evaluation_interval: 15s

alerting:
  alertmanagers:
    - static_configs:
        - targets: ['localhost:9093']

scrape_configs:
  - job_name: 'federate'
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{job=~"node.+"}'
    static_configs:
      - targets:
          - '<server1_ip>:9090'
          - '<server2_ip>:9090'
```

**Шаг 3. Проверка**

1. Открыть `http://<monitoring_ip>:9090/targets` — в секции `federate` должны быть активные таргеты.
2. Выполнить запрос `node_load1` — должны отобразиться ряды с лейблами `cluster="dc1"`, `cluster="dc2"`.

## Дополнительная информация

### Недостатки и ограничения

| Ограничение | Описание |
|---|---|
| **Потеря гранулярности** | Вышестоящий сервер получает только последние значения; промежуточные сэмплы теряются |
| **Потеря лейблов** | При агрегации часть исходных лейблов может быть утрачена |
| **Отсутствие горизонтального масштабирования** | Не решает проблему дискового пространства и долговременного хранения |
| **Расхождение данных** | Возможны дубликаты и рассинхронизация между нижестоящими серверами |
| **Нагрузка без фильтрации** | Сбор всех рядов без `match[]` создаёт избыточную нагрузку на сеть и CPU |

### Рекомендации

- **Всегда использовать `match[]`:** фильтрация метрик обязательна — сбор всех временных рядов без селектора перегружает сеть и сервер.
- **Настраивать `external_labels`:** каждый нижестоящий сервер должен иметь уникальную метку (например, `cluster: dc1`) для идентификации источника.
- **Забирать агрегаты:** предпочтительно опрашивать recording rules, а не сырые метрики — это снижает объём передаваемых данных.
- **`honor_labels: true`:** обязательная опция в scrape_config — предотвращает перезапись лейблов `job` и `instance`.

### Когда использовать федерацию

Федерация подходит для:

- Простых задач агрегации из нескольких кластеров
- Сценариев с ограниченными ресурсами, где развёртывание Thanos/VictoriaMetrics избыточно
- Временных решений до перехода на remote_write

Для построения масштабируемой системы мониторинга предпочтительны **[Remote Read/Write](./remote_read_write.md)**, **[Thanos](./thanos_overview.md)** или **[VictoriaMetrics](../../VictoriaMetrics/overview.md)**.
