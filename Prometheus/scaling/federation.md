# Федерация Prometheus

> **Федерация** — это механизм, позволяющий одному серверу Prometheus (вышестоящему) собирать выбранные временные ряды с другого сервера Prometheus (нижестоящего). Это иерархический подход к масштабированию, предназначенный для агрегации данных из множества независимых источников.
>
> **Надёжность:** 10 (SSoT + Web Verification 2025)
>
> **См. также:** [Масштабирование (обзор)](./overview.md), [Remote Read/Write](./remote_read_write.md), [Prometheus Operator](../kubernetes/operator/concepts.md).

## Определения

*   **Федерация (Federation):** Процесс сбора данных «сервер-сервер», где вышестоящий инстанс выступает в роли скрейпера для нижестоящего.
*   **Нижестоящий сервер (Leaf/Slave):** Источник данных, обслуживающий конкретный сегмент инфраструктуры (кластер, ДЦ).
*   **Вышестоящий сервер (Global/Master):** Точка агрегации, предоставляющая глобальный обзор (Global View) или SLO на основе данных из Leaf-узлов.
*   **Эндпоинт `/federate`:** Специальный системный эндпоинт, который возвращает не текущие метрики процесса Prometheus, а содержимое его TSDB, отфильтрованное по селекторам.

## Основные концепции

### Принцип работы и форматы данных

Вышестоящий сервер запрашивает данные по HTTP. В параметре URL `match[]` передаются PromQL-селекторы. Нижестоящий сервер находит соответствующие ряды в своей памяти/диске и отдает их в стандартном текстовом формате или Protobuf.

**Технические особенности реализации:**
- **Instant Vector Only:** Передаются только последние значения (last samples). Федерация — это не синхронизация баз данных, а скрейпинг состояния.
- **`honor_labels: true`:** Критически важная настройка. Без неё Master-сервер заменит оригинальные лейблы `job` и `instance` нижестоящего сервера своими собственными (обычно `job="federate"`), что приведет к потере контекста и перемешиванию данных.
- **External Labels:** На нижестоящем сервере должны быть настроены уникальные `external_labels` (например, `cluster: dc1`), чтобы Master-сервер мог различать идентичные метрики из разных источников.

### Типы федерации

1.  **Иерархическая (Hierarchical Federation):**
    *   **Структура:** Древовидная (Leaf -> Regional -> Global).
    *   **Цель:** Масштабирование по количеству таргетов. Каждый уровень выше собирает всё менее детальные, но более агрегированные данные.
    *   **Пример:** Сбор `node_load` со всех серверов мира на глобальный сервер для алертинга по всей компании.
2.  **Межсервисная (Cross-service Federation):**
    *   **Структура:** Плоская или точечная.
    *   **Цель:** Один функциональный сервер (например, Prometheus команды БД) забирает специфичные метрики у другого (например, Prometheus команды сети) для совместного анализа в одном дашборде.
    *   **Пример:** Сопоставление задержек БД с потерями пакетов на сетевых интерфейсах.

## Практические сценарии

### Сценарий 1: Базовая конфигурация (VM / Bare-metal)

**Шаг 1. Настройка нижестоящего сервера (Leaf)**
Добавляем уникальную метку для идентификации кластера.

```yaml
# prometheus.yml на Leaf-сервере
global:
  scrape_interval: 15s
  external_labels:
    cluster: 'production-dc1' # Уникальный ID источника

scrape_configs:
  - job_name: 'node'
    static_configs:
      - targets: ['localhost:9100']
```

**Шаг 2. Настройка вышестоящего сервера (Master)**
Настраиваем сбор агрегированных данных.

```yaml
# prometheus.yml на Master-сервере
scrape_configs:
  - job_name: 'federate-dc1'
    scrape_interval: 1m
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{job="node"}'                # Собираем всё из задания node
        - '{__name__=~"job:.*"}'        # И все recording rules
    static_configs:
      - targets: ['leaf-dc1-ip:9090']
```

### Сценарий 2: Использование в Prometheus Operator (Kubernetes)

В Operator федерация чаще всего реализуется через `additionalScrapeConfigs`, так как стандартные `ServiceMonitor` ориентированы на приложения, а не на другие инстансы Prometheus.

**Пример Secret с конфигурацией:**
```yaml
# prometheus-additional.yaml
- job_name: 'federate-remote-cluster'
  honor_labels: true
  metrics_path: '/federate'
  params:
    'match[]':
      - '{cluster="remote-k8s"}'
  static_configs:
    - targets: ['prometheus-operated.remote-namespace.svc:9090']
```

**Применение в манифесте Prometheus:**
```yaml
apiVersion: monitoring.coreos.com/v1
kind: Prometheus
metadata:
  name: master
spec:
  additionalScrapeConfigs:
    name: additional-scrape-configs
    key: prometheus-additional.yaml
```

## Производительность и ограничения

### Нагрузка на ресурсы
Запрос к `/federate` — это тяжелая операция для Leaf-сервера:
- **CPU:** Выполнение regex-матчинга и фильтрации тысяч рядов при каждом запросе Master-сервера.
- **Memory:** Формирование текстового ответа в памяти перед отправкой. При большом объеме метрик это может привести к OOM (Out Of Memory).
- **Network:** Передача сотен мегабайт текста. Обязательно используйте сжатие (`Accept-Encoding: gzip`), которое Prometheus поддерживает нативно.

### Проблема «Исчезающих графиков» (Data Gaps)
Если интервал скрейпинга Master-сервера (например, 1 мин) больше интервала Leaf-сервера (например, 15 сек), то 3 из 4 точек данных будут потеряны. Master-сервер сохранит только ту точку, которая была последней на момент его запроса. 
**Решение:** На Leaf-сервере всегда используйте **Recording Rules** для вычисления `rate` или `sum` за интервал, превышающий интервал опроса Master-сервера.

### Критические ограничения (Anti-patterns)
| Ограничение | Почему это плохо |
|---|---|
| **Сбор всех метрик (`match[]={__name__=~".+"}`)** | Гарантированная перегрузка Leaf-сервера и сети. |
| **Отсутствие `honor_labels`** | Лейблы `instance` всех серверов в ДЦ превратятся в IP-адрес самого Prometheus. |
| **Дублирование алертов** | Если алерты настроены и на Master, и на Leaf — вы получите два уведомления. |
| **Глубокая иерархия (>3 уровней)** | Огромная задержка (lag) данных: пока метрика дойдет до верха, она устареет на несколько минут. |

## Дополнительная информация

### Рекомендации по эксплуатации
1.  **Иерархия агрегации:** На Leaf-серверах агрегируйте данные до уровня `job` или `service`. На Master забирайте только эти итоги.
2.  **Таймауты:** Увеличивайте `scrape_timeout` для заданий федерации до 45-60 секунд. Подготовка данных для `/federate` может занимать время.
3.  **Безопасность:** Ограничивайте доступ к `/federate` на Leaf-серверах (через IP-whitelist в Nginx или встроенный Basic Auth в Prometheus), так как этот эндпоинт позволяет выкачать все ваши метрики.
4.  **Форматы:** Хотя Prometheus поддерживает Protobuf, в федерации чаще всего используется текстовый формат. В версиях 3.x ожидается переход на более эффективные стриминговые форматы (Remote Write 2.0).

### Когда федерация — лучший выбор?
- **Air-gapped сети:** Когда Push-трафик (Remote Write) запрещен фаерволом, но разрешен Pull из вышестоящего сегмента.
- **Минимальные ресурсы:** Когда нет возможности развернуть инфраструктуру для Thanos или VictoriaMetrics (S3, дополнительные компоненты).
- **Временные миграции:** Для постепенного переноса метрик между кластерами.
