# Федерация Prometheus

> **Федерация** является одним из подходов к **[[./overview.md|масштабированию Prometheus]]**.

**Федерация** в Prometheus — это конфигурация, при которой один Prometheus-сервер выступает источником данных для другого. Это специализированный механизм, позволяющий "вышестоящему" серверу собирать (scrape) агрегированные или отфильтрованные метрики с "нижестоящих" серверов.

Такой подход полезен для создания иерархических систем мониторинга, агрегации данных из нескольких источников или решения задач долгосрочного хранения метрик с пониженной детализацией.

---

## 1. Определения и Основные концепции

### Принцип работы
Федерация реализуется через специальный HTTP-эндпоинт `/federate`. При обращении к этому эндпоинту нижестоящий Prometheus-сервер отдает **последние значения** для всех временных рядов, которые соответствуют параметру `match[]` в запросе.

### Сценарии использования

1.  **Агрегация данных из нескольких источников:** Если у вас есть несколько дата-центров или проектов, каждый со своим Prometheus, федерация позволяет собрать ключевые метрики в одном центральном сервере для получения общей картины.
2.  **Шардирование Prometheus:** Можно создать архитектуру, где разные серверы Prometheus отвечают за разные группы таргетов (например, один за инфраструктуру, другой за приложения), а "главный" сервер агрегирует с них данные.
3.  **Долгосрочное хранение (с понижением детализации):** Вышестоящий сервер может с низкой частотой (например, раз в 5-10 минут) собирать данные с нижестоящих, которые, в свою очередь, опрашивают таргеты с высокой частотой (например, раз в 15 секунд). Это позволяет хранить исторические данные дольше, но с потерей гранулярности.

---

## 2. Продвинутые детали и Конфигурация

### Ограничения: Потеря исторических данных
Важная особенность и ограничение федерации: вышестоящий сервер получает **только последние значения** для каждой метрики на момент запроса. Все промежуточные значения, собранные нижестоящим сервером между опросами, будут **потеряны** для верхнеуровневого сервера. Из-за этого федерация не предназначена для создания точной копии исторических данных.

### Нюансы конфигурации

*   **`honor_labels: true`**: Обязательная настройка, которая указывает вышестоящему серверу **не перезаписывать** метки (`job`, `instance`), полученные от нижестоящего.
*   **`external_labels`**: Позволяет добавить на нижестоящем сервере уникальную метку (например, `cluster: 'main-dc'`), чтобы на вышестоящем сервере можно было различать источники данных.
*   **Фильтрация метрик (`params`)**: В конфигурации `scrape_configs` обязательно используется параметр `match[]`, чтобы указать, какие именно метрики нужно забирать. Сбор всех метрик без фильтрации может создать огромную нагрузку.

### Пример конфигурации

```yaml
# Конфигурация для вышестоящего (федерирующего) сервера
scrape_configs:
  - job_name: 'federate'
    scrape_interval: 1m 
    honor_labels: true
    metrics_path: '/federate' 
    params:
      'match[]':
        - '{job="prometheus"}'       # Собирать метрики с job="prometheus"
        - '{__name__=~"job:.*"}'    # Собирать агрегированные метрики (rules)
    static_configs:
      - targets:
          - 'prom-dc1.example.com:9090'
          - 'prom-dc2.example.com:9090'
```

## 3. Практический сценарий: Настройка федерации

Это руководство описывает настройку федерации, где один главный сервер Prometheus (`monitoring`) собирает метрики с двух нижестоящих серверов (`server1`, `server2`).

### Шаг 3.1: Настройка нижестоящих Prometheus

Настройте экземпляры Prometheus на серверах `server1` и `server2` так, чтобы каждый из них собирал метрики только с локального `node_exporter`.

На каждом из серверов (`server1` и `server2`) приведите конфигурационный файл к следующему виду, подставив реальные IP-адреса:
```bash
cat <<EOF > /etc/prometheus/prometheus.yml
global:
  scrape_interval:     15s 
  evaluation_interval: 15s 

alerting:
  alertmanagers:
  - static_configs:
    - targets:
      - <monitoring_IP>:9093

scrape_configs:
  - job_name: 'prometheus'
    static_configs:
    - targets: ['localhost:9090']
  - job_name: 'node_exporter'
    static_configs:
    - targets:
        - <server_ip>:9100
EOF

systemctl restart prometheus.service
```

### Шаг 3.2: Настройка главного (федерирующего) Prometheus

На сервере `monitoring` замените конфигурацию `prometheus.yml` на следующую, подставив IP-адреса `server1` и `server2`:
```bash
cat <<EOF > /etc/prometheus/prometheus.yml
global:
  scrape_interval:     15s
  evaluation_interval: 15s

alerting:
  alertmanagers:
  - static_configs:
    - targets:
      - localhost:9093

scrape_configs:
  - job_name: 'federate'
    honor_labels: true
    metrics_path: '/federate'
    params:
      'match[]':
        - '{job=~"node.+"}'
    static_configs:
    - targets:
      - '<server1_IP>:9090'
      - '<server2_IP>:9090'
EOF

systemctl restart prometheus.service
```

### Шаг 3.3: Проверка работы

1.  Откройте веб-интерфейс главного Prometheus (`http://<monitoring_ip>:9090/targets`). В разделе `federate` должны появиться два активных таргета.
2.  Выполните запрос `node_load1`. В результате должны отобразиться два временных ряда — по одному от каждого нижестоящего сервера.
