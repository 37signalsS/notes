# Thanos

## Определения

Thanos — это проект с открытым исходным кодом, который является надстройкой над Prometheus и решает его фундаментальные архитектурные ограничения. Поскольку Prometheus изначально проектировался как система оперативного мониторинга, в него не были заложены инструменты для длительного хранения метрик. Thanos расширяет возможности Prometheus, превращая его в высокодоступную систему мониторинга с возможностью практически неограниченного хранения данных.

Thanos решает ключевые проблемы масштабирования Prometheus, предоставляя:

- **Глобальный обзор метрик:** Возможность выполнять запросы к данным со всех экземпляров Prometheus в одном месте.
- **Долгосрочное хранение:** Интеграция с дешевыми и надежными объектными хранилищами.
- **Высокая доступность:** Архитектура, устойчивая к сбоям отдельных компонентов.

> **См. также:** [TSDB](../concepts/tsdb.md) — устройство локального хранилища Prometheus, [Remote Read/Write](./remote_read_write.md) — альтернативный способ масштабирования.

## Основные концепции

### Thanos Sidecar

- **Назначение:** `Sidecar` — это основной компонент, который запускается как сопроводительный процесс (в том же Pod'е) для каждого экземпляра Prometheus.
- **Функции:**
    1. **Загрузка данных в Object Storage:** Периодически (по умолчанию каждые 2 часа) `Sidecar` выгружает завершенные блоки данных (TSDB blocks) из локального хранилища Prometheus в централизованное объектное хранилище. Это делает сам Prometheus "полу-stateless", так как локально он хранит только самые свежие данные.
        - **Поддерживаемые хранилища:** S3-совместимые (MinIO, Ceph, Yandex Object Storage), OpenStack Swift и другие.
    2. **API для запросов:** Предоставляет `Thanos Query` доступ к свежим данным (за последние ~2 часа), которые еще не были выгружены в Object Storage, напрямую из памяти Prometheus.

### Thanos Query

- **Назначение:** Центральный узел для выполнения запросов в масштабах всей системы.
- **Функции:**
  - **Единая точка входа:** Реализует API, полностью совместимый с Prometheus, что позволяет легко интегрировать его в существующую экосистему (например, с Grafana) без изменений.
  - **Агрегация данных:** При получении PromQL-запроса `Thanos Query` "распараллеливает" его, одновременно обращаясь ко всем необходимым источникам:
    - К `Thanos Sidecar` для получения самых свежих, "оперативных" данных.
    - К `Thanos Store Gateway` для получения исторических данных из объектного хранилища.
  - **Дедупликация:** "На лету" объединяет и дедуплицирует данные, полученные от нескольких реплик одного и того же Prometheus, обеспечивая целостный и непротиворечивый результат.

### Thanos Store Gateway

- **Назначение:** Шлюз ("адаптер") для доступа к историческим данным, хранящимся в объектном хранилище.
- **Функции:**
  - Реализует Store API, через который `Thanos Query` может запрашивать данные из долгосрочного хранилища.
  - "Знает", как эффективно находить и извлекать нужные блоки метрик из бакетов S3 или других совместимых хранилищ.
  - Применяет интеллектуальное кэширование метаданных (индексов блоков), что значительно ускоряет выполнение запросов за длительные периоды.

### Thanos Ruler

- **Назначение:** Выполнение правил записи (`recording rules`) и алертинга (`alerting rules`) на основе "глобального" набора данных.
- **Функции:**
  - Позволяет определять правила, которые оперируют данными со всех подключенных кластеров, доступных через `Thanos Query`.
  - Периодически выполняет запросы к `Thanos Query`, оценивает правила и, в случае срабатывания, отправляет алерты в Alertmanager.

## Практические сценарии

### Принцип работы в HA-связке

1. **Сбор данных:** Два или более идентичных экземпляра Prometheus собирают метрики с одних и тех же таргетов. Рядом с каждым работает `Thanos Sidecar`.
2. **Запросы:** Grafana отправляет запрос в `Thanos Query` (или `Query Frontend`).
3. **Обработка запроса:**
    - `Thanos Query` запрашивает свежие данные у всех `Sidecar`-ов.
    - Одновременно он запрашивает исторические данные у `Thanos Store`.
    - Получив данные от всех источников, `Thans Query` выполняет дедупликацию (так как данные пришли от нескольких реплик Prometheus) и возвращает единый, целостный результат.
4. **Хранение:** В фоне `Sidecar`-ы выгружают данные в Object Storage, а `Compactor` их оптимизирует.

Такая архитектура позволяет пережить отказ любого компонента (включая один из Prometheus-серверов) без потери данных и с сохранением полной работоспособности системы мониторинга.

## Дополнительная информация

Компоненты и процессы для оптимизации хранения и ускорения запросов в больших инсталляциях.

### Thanos Compactor

- **Назначение:** Фоновый "обслуживающий" процесс для оптимизации данных в объектном хранилище.
- **Функции:**
  - **Сжатие (Compaction):** Объединяет небольшие блоки данных (например, 2-часовые), выгруженные `Sidecar`-ами, в более крупные (например, суточные), что повышает эффективность хранения и значительно ускоряет запросы за большие временные диапазоны.
  - **Понижение дискретизации (Downsampling):** Создает агрегированные версии старых данных с меньшим разрешением (например, усредняет сэмплы за 5 минут или за час). Это позволяет хранить исторические данные гораздо компактнее, жертвуя гранулярностью. Например, данные старше 30 дней могут храниться с 5-минутным разрешением, а старше года — с часовым.
  - **Постоянная дедупликация:** В отличие от `Thanos Query`, который дедуплицирует данные в реальном времени для каждого запроса, `Compactor` может выполнять дедупликацию уже сохраненных блоков от HA-пар Prometheus, экономя место в хранилище.

### Thanos Query Frontend

- **Назначение:** Опциональный компонент, который ставится перед Thanos Query для ускорения и стабилизации работы с запросами.
- **Функции:**
  - **Кэширование:** Кэширует результаты запросов, что значительно ускоряет работу дашбордов в Grafana.
  - **Разбиение запросов:** Может разбивать большие запросы на несколько мелких, чтобы избежать перегрузки Query-узлов.
