# Обзор Thanos

Thanos — это проект с открытым исходным кодом, который расширяет возможности Prometheus, превращая его в высокодоступную систему мониторинга с возможностью долгосрочного хранения метрик. Его название происходит от греческого слова "бессмертный", что отражает цель проекта — создать "неубиваемую" систему мониторинга.

Thanos решает ключевые проблемы масштабирования Prometheus, предоставляя:
-   **Глобальный обзор метрик:** Возможность выполнять запросы к данным со всех экземпляров Prometheus в одном месте.
-   **Долгосрочное хранение:** Интеграция с объектными хранилищами (S3-совместимыми) для практически безграничного хранения метрик.
-   **Высокая доступность:** Архитектура, устойчивая к сбоям отдельных компонентов.

## Архитектура и компоненты

Thanos состоит из набора компонентов, каждый из которых выполняет свою задачу. Взаимодействие между компонентами обычно происходит по протоколу gRPC.

### 1. Thanos Sidecar

-   **Назначение:** `Sidecar` запускается как сопроводительный процесс для каждого экземпляра Prometheus.
-   **Функции:**
    1.  **Загрузка данных в Object Storage:** Периодически (например, каждые 2 часа) `Sidecar` выгружает блоки данных из локального хранилища Prometheus в централизованное объектное хранилище. Это делает сам Prometheus "полу-stateless", так как локально он хранит только самые свежие данные.
    2.  **API для запросов:** Предоставляет Thanos Query доступ к свежим данным (за последние ~2 часа), которые еще не были выгружены в Object Storage.

### 2. Thanos Query

-   **Назначение:** Центральный узел для выполнения запросов.
-   **Функции:**
    -   Предоставляет Prometheus-совместимый API, что позволяет использовать его с Grafana без дополнительных настроек.
    -   Принимает PromQL-запросы и "распараллеливает" их, обращаясь ко всем необходимым источникам данных:
        -   К **Sidecar'ам** для получения свежих данных.
        -   К **Thanos Store** для получения исторических данных из Object Storage.
    -   **Дедупликация:** Объединяет данные от нескольких реплик одного и того же Prometheus, удаляя дубликаты.

### 3. Thanos Store Gateway

-   **Назначение:** Шлюз для доступа к историческим данным в объектном хранилище.
-   **Функции:**
    -   Реализует API, который Thanos Query использует для запроса данных из Object Storage.
    -   Эффективно находит и извлекает нужные блоки метрик.
    -   Может кэшировать метаданные для ускорения запросов.

### 4. Thanos Compactor

-   **Назначение:** Фоновый процесс для оптимизации данных в Object Storage.
-   **Функции:**
    -   **Сжатие (Compaction):** Объединяет небольшие блоки данных в более крупные, что повышает эффективность хранения и скорость запросов.
    -   **Понижение дискретизации (Downsampling):** Создает агрегированные версии старых данных (например, усредняет данные за 5 минут или за час). Это значительно уменьшает объем, занимаемый старыми метриками, ценой потери гранулярности. Например, данные старше 30 дней могут храниться с 5-минутным разрешением, а старше года — с часовым.

### 5. Thanos Ruler

-   **Назначение:** Выполнение правил записи и алертинга на основе глобальных данных.
-   **Функции:**
    -   Позволяет определять правила, которые будут применяться ко всем данным, доступным через Thanos Query.
    -   Отправляет сработавшие алерты в Alertmanager.

### 6. Thanos Query Frontend

-   **Назначение:** Опциональный компонент, который ставится перед Thanos Query.
-   **Функции:**
    -   **Кэширование:** Кэширует результаты запросов, что значительно ускоряет работу дашбордов в Grafana.
    -   **Разбиение запросов:** Может разбивать большие запросы на несколько мелких, чтобы избежать перегрузки Query-узлов.

## Принцип работы в HA-связке

1.  **Сбор данных:** Два или более идентичных экземпляра Prometheus собирают метрики с одних и тех же таргетов. Рядом с каждым работает `Thanos Sidecar`.
2.  **Запросы:** Grafana отправляет запрос в `Thanos Query` (или `Query Frontend`).
3.  **Обработка запроса:**
    -   `Thanos Query` запрашивает свежие данные у всех `Sidecar`-ов.
    -   Одновременно он запрашивает исторические данные у `Thanos Store`.
    -   Получив данные от всех источников, `Thanos Query` выполняет дедупликацию (так как данные пришли от нескольких реплик Prometheus) и возвращает единый, целостный результат.
4.  **Хранение:** В фоне `Sidecar`-ы выгружают данные в Object Storage, а `Compactor` их оптимизирует.

Такая архитектура позволяет пережить отказ любого компонента (включая один из Prometheus-серверов) без потери данных и с сохранением полной работоспособности системы мониторинга.
