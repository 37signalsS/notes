# Thanos: Глобальное масштабирование и долгосрочное хранение

> **Thanos** — это высокомасштабируемая система сбора и хранения метрик, которая превращает локальные инстансы Prometheus в единое глобальное облако данных с практически неограниченным сроком хранения.
>
> **Надёжность:** 10 (SSoT + Web Verification 2025)
>
> **См. также:** [Масштабирование (обзор)](./overview.md), [VictoriaMetrics](../../VictoriaMetrics/overview.md), [Mimir](../../Mimir/mimir_overview.md), [Remote Read/Write](./remote_read_write.md).

## Определения

Thanos решает три фундаментальные проблемы классического Prometheus:
1.  **Retention (Хранение):** Локальная TSDB не предназначена для хранения петабайт данных годами. Thanos выгружает данные в дешевые объектные хранилища (S3).
2.  **Global View (Единое окно):** Позволяет выполнять PromQL-запросы сразу по всем кластерам из одной точки (Grafana), дедуплицируя данные от HA-пар.
3.  **Horizontal Scalability (Масштабируемость):** Разделяет функции сбора (Sidecar/Receive) и выполнения запросов (Query), позволяя масштабировать их независимо.

## Основные концепции

### Компоненты системы (Архитектура 2025)

| Компонент | Назначение | Ключевые функции и особенности |
|---|---|---|
| **Sidecar** | Прокси для Prometheus | Выгружает TSDB-блоки в S3 каждые 2ч; проксирует gRPC-запросы от Query к локальной памяти Prometheus. |
| **Store Gateway** | Шлюз к S3 | Позволяет Query запрашивать исторические данные из объектного хранилища. Использует агрессивное кэширование индексов. |
| **Query** | Агрегатор (Querier) | Точка входа для PromQL. Собирает данные со всех Store API (Sidecars + Store Gateways), дедуплицирует ряды. |
| **Query Frontend** | Оптимизатор запросов | Разбивает тяжелые запросы на мелкие куски (split-by-day), кэширует результаты в Redis/Memcached. |
| **Compactor** | Санитар хранилища | Выполняет **downsampling** (понижение дискретизации), слияние мелких блоков и удаление данных по retention. |
| **Receiver** | Ingestor (Push-модель) | Принимает метрики по Remote Write. Используется для мульти-тенантности и в сетях, где Master не может достучаться до Leaf. |
| **Ruler** | Глобальные правила | Выполняет Recording и Alerting rules поверх данных в Thanos Query (агрегированные алерты). |

### Продвинутые механизмы оптимизации

#### 1. Индексное кэширование (Index Caching)
Store Gateway тратит больше всего времени на поиск нужных рядов внутри огромных блоков в S3.
- **In-memory:** Быстро, но ограничено RAM одного пода. При рестарте кэш пустой («холодный старт»).
- **Redis (Рекомендуется):** Позволяет делить кэш между всеми репликами Store Gateway и сохранять его при перезапусках. Ускоряет «первое открытие» дашборда за 30 дней в 5-10 раз.

#### 2. Query Pushdown
Механизм, при котором часть вычислений (например, фильтрация по лейблам) передается от `Query` вниз к `Store Gateway` или `Sidecar`. Это радикально снижает объем данных, передаваемых по сети между компонентами.

#### 3. Downsampling (Понижение дискретизации)
Compactor создает две дополнительные копии данных:
- **5m resolution:** Для запросов за период от 1 до 30 дней.
- **1h resolution:** Для запросов за период >30 дней.
Это позволяет Grafana строить графики за 1 год за доли секунды, считывая в 60 раз меньше точек.

## Практические сценарии

### Сценарий 1: Глобальный HA-кластер (Sidecar-модель)

Это классический путь для инфраструктуры в нескольких дата-центрах.

1.  **Сбор:** В каждом ДЦ стоит пара Prometheus (HA-пара) с `thanos-sidecar`.
2.  **Дедупликация:** В конфигурации Query указывается `replica-label` (обычно `prometheus_replica`). Query сравнивает два ряда с одинаковыми метками и разным `replica-label`, отдавая пользователю чистый поток без дублей.
3.  **Хранение:** Sidecar выгружает данные в S3. Compactor в центральном кластере оптимизирует эти данные.

**Пример конфигурации Prometheus Operator (CRD):**
```yaml
apiVersion: monitoring.coreos.com/v1
kind: Prometheus
metadata:
  name: k8s-prometheus
spec:
  replicas: 2
  thanos:
    version: v0.38.1
    objectStorageConfig:
      key: thanos.yaml
      name: thanos-objstore-config # Secret с настройками S3
  externalLabels:
    cluster: "prod-europe-1"
    prometheus_replica: "$(POD_NAME)" # Важно для дедупликации
```

### Сценарий 2: Мульти-тенантность и Thanos Receive

Если у вас сотни изолированных команд, которым нужно «просто отдавать метрики», используется Receive.

1.  **Центральный кластер:** Группа `Thanos Receive` в режиме `Router + Ingestor`.
2.  **Изоляция:** Каждая команда шлет данные с HTTP-заголовком `THANOS-TENANT`. Receiver раскладывает их по разным папкам в S3.
3.  **Безопасность:** Receiver поддерживает репликацию данных между своими узлами (по умолчанию factor 3), что гарантирует сохранность данных до их выгрузки в S3.

### Сценарий 3: Настройка жизненного цикла в Object Storage (Lifecycle)

Thanos сам удаляет данные через Compactor (`--retention.resolution-raw=90d`), но для надежности и экономии на облаке рекомендуется настраивать политики на уровне корзины.

**Пример политики для AWS S3 / Yandex Cloud:**
- **Raw data:** Перенос в `Standard-IA` (Infrequent Access) через 90 дней.
- **Downsampled data (1h):** Хранение в `Standard` бессрочно (занимает мало места).
- **Abort Incomplete Multipart Uploads:** Удалять через 7 дней (экономит деньги при сбоях загрузки Sidecar).

## Безопасность и Эксплуатация

### Сетевая безопасность (mTLS)
Поскольку Thanos Query общается с компонентами по gRPC, в распределенных сетях передача идет в открытом виде.
- **Рекомендация:** Используйте флаги `--grpc-client-tls-*` и `--grpc-server-tls-*` для настройки mTLS между всеми компонентами.
- **Альтернатива:** Использование Service Mesh (Istio/Linkerd), который обеспечит mTLS прозрачно.

### Мониторинг самого Thanos (Thanos Mixin)
Нельзя мониторить Thanos тем же Prometheus, который он обслуживает (циклическая зависимость).
1.  **Mixin:** Используйте [Thanos Mixin](https://github.com/thanos-io/thanos/tree/main/mixin) — готовый набор алертов и дашбордов.
2.  **Ключевые метрики:**
    - `thanos_store_gateway_index_cache_hit_ratio_total`: эффективность кэша Store.
    - `thanos_compactor_halted`: если `1`, значит Compactor столкнулся с конфликтом блоков и остановился — данные перестали сжиматься!
    - `thanos_query_frontend_queries_dropped_total`: признак перегрузки запросами.

## Дополнительная информация

### Поддерживаемые объектные хранилища
- **Amazon S3** (и любые совместимые: MinIO, Ceph RGW, Yandex Object Storage).
- **Google Cloud Storage**.
- **Azure Blob Storage**.
- **OpenStack Swift**.

### Сравнение с альтернативами

| Функция | Thanos | VictoriaMetrics | Grafana Mimir |
|---|---|---|---|
| **Сложность** | Средняя (много компонентов) | Низкая (единый бинарник) | Высокая (микросервисы) |
| **Хранилище** | Только S3 | Диск или S3 | Только S3 |
| **Query Speed** | Средняя (зависит от кэша) | Высокая | Очень высокая |
| **Мульти-тенантность** | Через Receiver | Нативная | Нативная |

### Рекомендации по Retention
- **Prometheus:** 2h–6h (только для оперативного алертинга).
- **Thanos Raw:** 30–90 дней.
- **Thanos 5m:** 1 год.
- **Thanos 1h:** Бессрочно.
