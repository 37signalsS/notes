# Масштабирование Prometheus

> Масштабирование Prometheus требуется при росте инфраструктуры, когда локальная TSDB (Time Series Database) и single-instance архитектура перестают справляться с нагрузкой.
>
> **См. также:** [Федерация](./federation.md), [Remote Read/Write](./remote_read_write.md), [Thanos](./thanos_overview.md), [VictoriaMetrics](../../VictoriaMetrics/overview.md), [Mimir](../../Mimir/mimir_overview.md).

## Определения

Необходимость в масштабировании возникает при следующих условиях:

| Проблема | Описание |
|---|---|
| **Высокая нагрузка на запись** | >1 млн сэмплов/сек; локальный диск и CPU не справляются с WAL (Write-Ahead Logging) и Compaction |
| **Длительное хранение (Retention)** | TSDB не предназначена для хранения >30–60 дней; год данных на локальном диске приводит к медленным запросам и высоким затратам на хранение |
| **Множество кластеров** | Десятки независимых Prometheus-серверов требуют глобального обзора метрик и централизованного управления правилами |

## Базовые концепции

### Базовая отказоустойчивость (HA — High Availability)

Высокая доступность достигается **дублированием компонентов** — запуском двух и более идентичных экземпляров Prometheus с одинаковой конфигурацией и Alertmanager в режиме кластера.

**Принцип работы:**

| Компонент | Механизм |
|---|---|
| **Prometheus Server** | Несколько экземпляров независимо собирают одни и те же метрики (pull-модель) |
| **Alertmanager** | Кластер на gossip-протоколе для дедупликации алертов |

**Ограничения базового HA:**

| Ограничение | Описание |
|---|---|
| **Расхождение данных** | Экземпляры никогда не имеют идентичных наборов метрик |
| **Визуализация** | Grafana получает дублированные ряды; требуется HAProxy в режиме standby или выбор одного источника |
| **Не решает масштабирование** | HA обеспечивает отказоустойчивость алертинга, но не решает проблемы нагрузки на запись и длительного хранения |

> Подробная настройка HA с HAProxy: [Установка Prometheus](../installation/overview.md).

### Стратегии масштабирования

Когда базового HA недостаточно, применяются следующие подходы:

| Стратегия | Описание | Когда использовать | Ссылка |
|---|---|---|---|
| **Federation** | Иерархическая агрегация: вышестоящий сервер опрашивает нижестоящие через `/federate` | Простая агрегация из нескольких кластеров, временное решение | [federation](./federation.md) |
| **Sharding** | Разделение целей между несколькими экземплярами Prometheus для снижения нагрузки на запись | Высокая нагрузка (>1 млн samples/s), множество таргетов, динамические среды | [sharding](#шардирование-sharding) |
| **Remote Read/Write** | Делегирование хранения внешним системам; Prometheus работает как агент сбора | Долгосрочное хранение, глобальный обзор, предпочтительный современный подход | [remote_read_write](./remote_read_write.md) |

### Шардирование (Sharding)

Шардирование распределяет нагрузку между несколькими экземплярами Prometheus. Различают три подхода:

| Подход | Описание | Когда применять |
|---|---|---|
| **Функциональный** | Каждый Prometheus отвечает за конкретный домен (например, один — за метрики БД, другой — за метрики Kubernetes) | Чёткое разделение ответственности между командами, изоляция данных |
| **Географический** | Отдельные Prometheus в каждом регионе / дата-центре | Распределённая инфраструктура, независимость зон |
| **Хэш-шардирование** | Таргеты распределяются на основе хэша от `__address__` (через `hashmod` в `relabel_configs`) | **Динамические среды (Kubernetes):** много однотипных таргетов, требуется автоматическая балансировка |

**Хэш-шардирование через hashmod:**

```yaml
# Конфигурация идентична для всех шардов, отличается только total_shards и shard_id
scrape_configs:
  - job_name: 'kubernetes-pods'
    relabel_configs:
      - source_labels: [__address__]
        modulus: 3           # total_shards — количество шардов
        target_label: __tmp_hash
        action: hashmod
      - source_labels: [__tmp_hash]
        regex: '^0$'         # shard_id — номер текущего шарда (0, 1, 2...)
        action: keep
```

**Требуется глобальный запросный слой** (Thanos Query, Mimir, Grafana), чтобы объединять данные из всех шардов в единую точку.

**Недостатки шардирования:**
- Пересекающиеся метрики (например, `http_requests_total`) в разных шардах требуют единого запросного слоя с дедупликацией
- Алертинг должен быть централизован (Alertmanager кластер), иначе одна и та же проблема вызовет алерты из каждого шарда
- При функциональном шардировании сложнее определить, в каком шарде искать конкретную метрику

## Практические сценарии

### Базовый HA с HAProxy

Реализация стратегии «дублирования компонентов» с HAProxy в режиме standby обеспечивает отказоустойчивый доступ к Prometheus со стороны Grafana.

**Краткий алгоритм:**

1. Установить два идентичных экземпляра Prometheus ([Установка](../installation/overview.md)).
2. Настроить HAProxy: `server1` — основной (`check`), `server2` — резервный (`check backup`).
3. В Grafana указать `http://<haproxy_ip>:80` как единственный источник данных.
4. Проверить: поочерёдно остановить `prometheus.service` на каждом сервере — графики в Grafana должны оставаться доступными.

> Подробная инструкция с конфигурациями HAProxy и Grafana: [Установка Prometheus](../installation/overview.md).

## Дополнительная информация

### Решения для долгосрочного хранения (LTS — Long-Term Storage)

| Решение | Архитектура | Хранилище | Сложность | Ссылка |
|---|---|---|---|---|
| **Thanos** | Sidecar + Query + Store Gateway | S3-совместимое объектное | Средняя | [thanos_overview](./thanos_overview.md) |
| **VictoriaMetrics** | Единый бинарник или кластер | Собственный формат | Низкая | [VictoriaMetrics](../../VictoriaMetrics/overview.md) |
| **Grafana Mimir** | Горизонтально масштабируемый кластер | S3-совместимое объектное | Высокая | [Mimir](../../Mimir/mimir_overview.md) |

### Преимущества и недостатки удалённого хранения

| Преимущество | Описание |
|---|---|
| **Горизонтальное масштабирование** | Централизованные хранилища работают в кластере, хранят петабайты данных |
| **Долгосрочное хранение** | Метрики хранятся годами без деградации производительности |
| **Глобальный обзор** | Запросы по всем кластерам из единой точки (Grafana) |
| **Отказоустойчивость** | Локальные Prometheus становятся stateless для долгосрочных данных; перезапуск без потери истории |

| Недостаток | Описание |
|---|---|
| **Сложность архитектуры** | Вместо одного YAML-файла — распределённая система с множеством компонентов |
| **Отладка** | Проблемы могут быть на стороне агента, адаптера или центрального хранилища — требуется диагностика по всей цепочке |
