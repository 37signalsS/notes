# Масштабирование Prometheus

Масштабирование Prometheus требуется при росте инфраструктуры, когда локальная TSDB (Time Series Database) и архитектура с одним экземпляром (single-instance) перестают справляться с нагрузкой на запись, хранение или выполнение запросов.

## Определения

Необходимость в масштабировании возникает при достижении следующих лимитов:

| Проблема | Описание | Индикаторы |
|---|---|---|
| **Нагрузка на запись** | Превышение лимитов CPU/RAM при сборе метрик (ingestion) | >1 млн сэмплов/сек, высокая нагрузка на WAL и Compaction |
| **Кардинальность** | Слишком большое количество уникальных временных рядов | Взрывной рост оперативной памяти, замедление запросов |
| **Retention (Хранение)** | TSDB не предназначена для хранения больших объемов данных годами | Заполнение диска, деградация производительности при чтении старых данных |
| **Глобальный обзор** | Сложность работы с десятками независимых серверов | Требуется единая точка входа для Grafana и централизованный алертинг |

## Базовые концепции

### Когда требуется масштабирование: количественные пороги

Решение о масштабировании должно приниматься на основе метрик, а не интуиции. Ниже приведены пороговые значения, при превышении которых стандартный single-instance Prometheus теряет стабильность:

| Показатель | Зона комфорта | Предупреждение | Критический режим | Действие |
|---|---|---|---|---|
| **Активные серии (Head Block)** | < 500 000 | 500k–1M | > 1M | Увеличить RAM, включить Native Histograms, настроить sharding |
| **Скорость создания серий (churn)** | < 100/сек | 100–500/сек | > 500/сек | Анализ efemeridal labels, metric_relabel_configs |
| **Скорость сэмплов/сек** | < 200k | 200k–500k | > 1M | Переход на Remote Write / Sharding |
| **Размер WAL на диске** | < 50% retention | 50–80% | > 80% | Проверить сеть/доступность LTS, увеличить max_shards |
| **Задержка Compaction** | < 2h | 2–6h | > 6h | Увеличить CPU/Disk IO, проверить фрагментацию |

**Ключевые метрики для мониторинга лимитов:**
```promql
# Активные серии в Head Block
prometheus_tsdb_head_series

# Скорость создания новых серий
rate(prometheus_tsdb_head_series_created_total[5m])

# Размер WAL
prometheus_tsdb_wal_size_bytes

# Задержка сброса Head Block (в секундах)
time() - max(prometheus_tsdb_commit_timestamp_seconds)
```

### Внутренние механизмы TSDB, влияющие на масштабирование

Понимание жизненного цикла данных в TSDB необходимо для выбора правильной стратегии масштабирования. Подробнее: [Внутреннее устройство TSDB](../concepts/tsdb.md).

**Цепочка обработки сэмпла:**
1. **Scrape** → получение данных от таргетов.
2. **WAL/WBL** → запись на диск для надежности (даже при сбое питания данные не теряются).
3. **Head Block (RAM)** → актуальные данные в оперативной памяти для мгновенного доступа.
4. **Block (disk)** → каждые 2 часа Head Block закрывается и записывается на диск.
5. **Compaction** → фоновое слияние мелких блоков в крупные, оптимизация индекса.

**Связь с масштабированием:**
- **Head Block в RAM:** Потребление памяти напрямую пропорционально количеству активных серий. При >1M рядов требуется 32–64 ГБ RAM.
- **WAL и Compaction:** При высокой скорости записи (>500k samples/s) WAL и процесс Compaction создают значительную нагрузку на диск и CPU. Это приводит к лагам даже при достаточном объеме RAM.
- **m-map чанки:** Заполненные чанки отображаются в память через mmap. При миллионах рядов это снижает RAM, но увеличивает количество файловых дескрипторов.

### Вертикальное масштабирование (Vertical Scaling)

Самый простой способ, заключающийся в выделении дополнительных ресурсов существующему инстансу.

- **Лимиты ресурсов:** Prometheus эффективно использует многопоточность для скрейпинга, но выполнение запросов и Compaction TSDB могут упираться в производительность одного ядра и скорость I/O диска.
- **Тюнинг Go:** Настройка переменной окружения `GOGC` (по умолчанию 100) позволяет управлять частотой сборки мусора. Увеличение (например, до 200+) снижает нагрузку на CPU за счет большего потребления RAM.
- **In-place Pod Vertical Scaling:** В Kubernetes 1.31+ поддерживается изменение `limits` и `requests` без перезапуска пода. Это критично для Prometheus, так как позволяет избежать долгого прогрева кешей и WAL при рестарте из-за нехватки памяти.
- **Memory Management:** Использование флагов `--storage.tsdb.min-block-duration` и `--storage.tsdb.max-block-duration` позволяет косвенно влиять на потребление памяти при индексации блоков.

### Базовая отказоустойчивость (HA — High Availability)

Высокая доступность достигается **дублированием компонентов**. Запускаются два идентичных экземпляра Prometheus, которые независимо опрашивают одни и те же цели.

- **Принцип работы:** Оба сервера собирают данные (pull-модель), но только один (или оба через дедупликатор) отправляет алерты в кластер Alertmanager.
- **Ограничения:** Реплики никогда не идентичны на 100% (расхождение в миллисекундах при скрейпинге); Grafana видит дубликаты рядов, если не настроен внешний слой дедупликации (Thanos Query или VictoriaMetrics).

### Режим агента (Prometheus Agent Mode)

Эффективный сбор данных без локального хранения (введен в v2.32.0).

- **Суть:** Запуск с флагом `--enable-feature=agent`. В этом режиме TSDB заменяется на облегченный WAL.
- **Преимущества:** Потребляет на 30–40% меньше ресурсов (CPU/RAM), не хранит данные локально, не выполняет правила (alerting/recording).
- **Применение:** Идеально подходит для "граничных" (edge) кластеров, которые только собирают метрики и сразу отправляют их в центральное хранилище через Remote Write.

### Стратегии масштабирования

| Стратегия | Описание | Когда использовать |
|---|---|---|
| **Federation** | Иерархическая агрегация: вышестоящий сервер опрашивает нижестоящие | Простая агрегация из нескольких кластеров, перенос части метрик |
| **Sharding** | Распределение целей между несколькими экземплярами для снижения нагрузки | Очень высокая нагрузка (>1 млн samples/s), тысячи таргетов |
| **Remote Write 2.0** | Отправка данных во внешние системы (LTS) с оптимизацией | **Стандарт 2025-2026:** долгосрочное хранение, глобальный обзор |

### Матрица выбора стратегии

Выбор стратегии зависит от трех факторов: объема данных, требований к задержке и бюджета на инфраструктуру.

| Условие | Рекомендуемая стратегия | Почему |
|---|---|---|
| < 500k samples/s, retention < 30 дней | Вертикальное масштабирование | Нет необходимости в сложной архитектуре |
| 500k–1M samples/s, retention 30–90 дней | Remote Write 2.0 в LTS (VictoriaMetrics/Mimir) | Простота внедрения, сохранение локального запроса |
| > 1M samples/s, тысячи таргетов | Sharding + Remote Write 2.0 | Распределение нагрузки между инстансами |
| Несколько дата-центров, воздушная изоляция | Федерация или Thanos Receive | Работает через фаерволы, не требует Push |
| Год+ retention, глобальный обзор | Thanos / VictoriaMetrics Cluster / Mimir | Объектное хранилище + downsampling |
| Edge-кластеры, низкий ресурс | Prometheus Agent Mode + Remote Write | Минимальное потребление CPU/RAM |

### Шардирование (Sharding)

Шардирование распределяет нагрузку на скрейпинг между несколькими инстансами.

1. **Функциональное:** Разделение по доменам (один инстанс для K8s, другой для БД).
2. **Хэш-шардирование:** Распределение таргетов внутри одного задания (job) на основе хэша.

**Пример хэш-шардирования (через `hashmod`):**
```yaml
scrape_configs:
  - job_name: 'my-large-app'
    relabel_configs:
      - source_labels: [__address__]
        modulus: 4           # Всего 4 шарда
        target_label: __tmp_hash
        action: hashmod
      - source_labels: [__tmp_hash]
        regex: '^0$'         # Этот инстанс — шард №0
        action: keep
```
> **Совет:** При использовании [Prometheus Operator](../kubernetes/operator/high_availability.md) шардирование настраивается одной строкой в манифесте (`shards: N`), и оператор сам распределяет хэши через автоматическую конфигурацию `hashmod`.

### Удаленная запись (Remote Write 2.0)

В 2025-2026 годах протокол Remote Write 2.0 стал стандартом для масштабируемых архитектур.

- **String Interning:** Значительное снижение объема передаваемых данных (до 60%) за счет передачи идентификаторов строк вместо полных имен меток и значений в каждом пакете.
- **Метаданные и экземпляры:** Передача типов метрик и экземпляров (exemplars) в потоке данных, что критично для интеграции с распределенной трассировкой (Tracing).
- **Created Timestamps:** Позволяет корректно обрабатывать сбросы счетчиков (counter resets) на стороне приемника, что повышает точность вычислений в PromQL.

## Практические сценарии

### Сценарий 1: Классический HA с балансировщиком (Bare-metal/VM)

Обеспечивает переключение между двумя инстансами Prometheus.

1. Запустить два сервера Prometheus с идентичной конфигурацией.
2. Настроить балансировщик (HAProxy/Nginx): `server1` — основной, `server2` — резервный (`backup`).
3. Grafana запрашивает данные с виртуального IP балансировщика.
4. **Минус:** Возможны небольшие расхождения в данных ("ступеньки") на графиках при переключении из-за разницы во времени скрейпинга (джиттера).

### Сценарий 2: Современный стек (Cloud Native)

Оптимальный путь для Kubernetes и гибридных инфраструктур.

1. **Сбор:** Множество инстансов Prometheus в режиме **Agent Mode** или **Grafana Alloy**.
2. **Транспорт:** Протокол **Remote Write 2.0** (с поддержкой OTLP).
3. **Хранение:** Централизованное горизонтально масштабируемое хранилище ([VictoriaMetrics](../../VictoriaMetrics/overview.md), [Mimir](../../Mimir/mimir_overview.md) или [Thanos](./thanos_overview.md)).
4. **Алертинг:** Правила обработки (Recording/Alerting) выполняются на стороне LTS-хранилища для обеспечения глобального контекста.

### Сценарий 3: Capacity Planning — определение точки масштабирования

Пошаговая процедура оценки необходимости масштабирования на существующей инфраструктуре.

**Шаг 1. Сбор базовых метрик в течение 7 дней:**
```promql
# Средняя скорость сэмплов/сек
sum(rate(prometheus_tsdb_head_samples_appended_total[1h]))

# Пиковая кардинальность
max(prometheus_tsdb_head_series)

# Рост диска за сутки
increase(prometheus_tsdb_storage_blocks_bytes[24h])
```

**Шаг 2. Оценка ресурсов:**
- **RAM:** ~1 ГБ на каждые 100 000 активных серий + 4 ГБ базовый overhead.
- **Диск:** Оценить прирост TSDB за неделю × retention (например, 100 ГБ/неделя × 90 дней = 900 ГБ).
- **CPU:** 1 ядро на каждые 300–500k samples/s для скрейпинга + отдельное ядро на тяжелые запросы.

**Шаг 3. Прогноз на 6 месяцев:**
Если текущий рост кардинальности или количества таргетов составляет 20%/мес, через 6 месяцев потребуется удвоение ресурсов или внедрение sharding.

### Сценарий 4: Миграция с single-instance на масштабируемую архитектуру

Поэтапный переход без простояя мониторинга.

**Этап 1. Подготовка LTS:**
Развернуть VictoriaMetrics/Mimir/Thanos в отдельном Namespace. Настроить Remote Write в параллель:
```yaml
# Включить дублирующую remote_write-очередь
remote_write:
  - url: 'http://victoriametrics:8428/api/v1/write'
    name: 'lts-primary'
  - url: 'http://prometheus-main:9090/api/v1/write'
    name: 'lts-backup'
```
**Этап 2. Проверка целостности данных:**
Сравнить количество серий и метрик в Grafana между старым и новым источником данных.

**Этап 3. Переключение Grafana:**
Изменить URL источника данных на Query-уровень LTS (Thanos Query, VictoriaMetrics single).

**Этап 4. Остановка скрейпинга на старом сервере:**
Перевести Prometheus в режим Agent или полностью остановить, оставив LTS как authoritative источник.

## Диагностика и решение проблем

| Проблема | Причина | Решение |
|---|---|---|
| **Высокое потребление RAM** | Взрыв кардинальности или утечка памяти Go | Проверить `prometheus_tsdb_head_series`, удалить efemeridal labels, настроить GOGC |
| **Высокая нагрузка на диск** | Слишком быстрый рост WAL или отсутствие Compaction | Проверить `prometheus_tsdb_wal_size_bytes`, увеличить IOPS, отключить debug-логи |
| **Задержка алертов** | Правила выполняются на перегруженном инстансе | Вынести правила на Thanos Ruler / Mimir Ruler, снизить `evaluation_interval` |
| **Джиттер графиков при HA** | Разница во времени скрейпинга между репликами | Настроить `--query.lookback-delta` или использовать внешний слой дедупликации |
| **Потеря данных при Remote Write** | Переполнение очереди или недоступность LTS | Увеличить `max_shards` и `capacity`, настроить мониторинг `prometheus_remote_storage_dropped_samples_total` |
| **Medusa эффект (зависание Prometheus)** | Выполнение тяжелого PromQL-запроса | Использовать `--query.max-concurrency` и `--query.timeout`, добавить Redis-кэш через Thanos Query Frontend |
| **Федерация "забивает" Leaf-сервер** | Слишком широкий селектор в `match[]` | Добавить recording rules на Leaf, ограничить федерацию агрегатами |

## Граничные случаи и ограничения

### Вертикальное масштабирование
- **Потолок одного инстанса:** Практический лимит — 64 ядра и 128 ГБ RAM. Beyond этого выгода от вертикального масштабирования резко падает из-за contention на уровне ядра и шины памяти.
- **Compaction Stall:** При очень большом объеме данных (>1 млн серий) фоновый Compaction может не успевать за записью, что приводит к лагам запросов и росту WAL. Решение — снизить частоту сброса Head Block через `--storage.tsdb.max-block-duration`.

### Шардирование
- **Глобальные алерты:** При функциональном шардировании глобальные алерты (например, "CPU > 80% на всем кластере") требуют федерации или Thanos Ruler.
- **Согласованность external_labels:** При смене `external_labels` без очистки S3/данных Thanos可能出现 блокировка компактора. Всегда делайте бэкап перед изменением.

### Федерация
- **Только Instant Vector:** Федерация передает последние значения, не историю. Для анализа трендов используйте recording rules на Master-уровне.
- **Обратная совместимость:** Начиная с Prometheus 3.0, `/federate` поддерживает UTF-8 в именах метрик. Старые клиенты могут требовать escaping.

### Remote Write 2.0
- **At-least-once delivery:** При сбоях сети возможны дубликаты. LTS-хранилище должно поддерживать идемпотентность.
- **WAL Backfill:** При долгом недоступствии LTS (>retention) Prometheus удалит данные из WAL, что приведет к пробелам. Для критичных сценариев используйте `--storage.tsdb.retention.time` ≥ 2× ожидаемого downtime.

### Prometheus 3.x (Agent Mode и OTLP)
- **Agent Mode не выполняет правила:** Recording и Alerting rules в этом режиме отсутствуют. Всю логику обработки переносите на LTS.
- **OTLP HA:** Входящий OTLP-трафик не балансируется между репликами автоматически. Используйте внешний балансировщик (MetalLB, IPVS).

## Дополнительная информация

### Сравнение решений для долгосрочного хранения (LTS)

| Решение | Архитектура | Хранилище | Сильные стороны |
|---|---|---|---|
| **Thanos** | Децентрализованная (Sidecar) | Объектное (S3/GCS) | Прозрачное расширение существующего Prometheus |
| **VictoriaMetrics** | Монолит или Кластер | Локальные диски / PV | **Экстремальная производительность**, сжатие данных, простота |
| **Grafana Mimir** | Микросервисная | Объектное (S3/GCS) | Мульти-тенантность, изоляция данных, масштаб в миллиарды серий |

### Лучшие практики (2025–2026)

1. **Разделяйте скрейпинг и хранение:** Используйте Prometheus только как "умный агент" (Agent Mode), отдавая долгосрочное хранение и тяжелые запросы специализированным системам.
2. **Native Histograms:** Используйте нативные гистограммы (введены в v2.40) для снижения кардинальности и объема занимаемого места на диске (до 40% экономии по сравнению с классическими гистограммами).
3. **Используйте объектные хранилища:** Для Thanos/Mimir хранение данных в S3 обходится значительно дешевле, чем на блочных дисках.
4. **Управляйте кардинальностью:** Удаляйте ненужные лейблы на этапе скрейпинга через `metric_relabel_configs`. Подробнее: [Метки и кардинальность](../concepts/labels_and_cardinality.md).
5. **Downsampling:** Для хранения данных дольше года обязательно настройте понижение дискретизации (downsampling) в LTS, чтобы ускорить построение графиков за большие периоды.

### Мониторинг масштабируемой архитектуры

При переходе на распределенную архитектуру критически важно отслеживать здоровье всей цепочки передачи данных:

```promql
# Процент dropped samples в Remote Write
rate(prometheus_remote_storage_dropped_samples_total[5m]) 
  / sum(rate(prometheus_remote_storage_samples_total[5m])) * 100

# Задержка отправки данных в LTS (секунды)
prometheus_remote_storage_highest_timestamp_in_seconds 
  - prometheus_remote_storage_queue_highest_sent_timestamp_seconds

# Эффективность кэша индексов (Thanos)
thanos_store_gateway_index_cache_hit_ratio_total
```
