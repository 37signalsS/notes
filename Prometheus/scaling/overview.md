# Масштабирование Prometheus

Prometheus гениален в своей простоте, но его архитектура, ориентированная на один узел с локальным хранилищем, имеет пределы масштабируемости. Когда инфраструктура разрастается, возникает необходимость в централизованном, отказоустойчивом и долгосрочном хранении метрик.

## Проблема стандартного подхода к HA

Официальная документация Prometheus предлагает для высокой доступности (HA) запускать два идентичных экземпляра Prometheus, которые собирают одни и те же метрики, и использовать Alertmanager для дедупликации оповещений.

**Почему этот подход неполноценен:**

*   **Проблема визуализации:** Этот метод решает проблему только для алертинга. При визуализации метрик в Grafana вы столкнетесь с дублированием данных, так как Grafana будет получать идентичные временные ряды от двух разных источников. Это требует создания сложных и неудобных решений на уровне дашбордов или использования балансировщика, который не решает проблему полностью.
*   **Не решает проблему масштабирования:** Этот подход удваивает ресурсы, но не решает фундаментальных проблем с нагрузкой и длительным хранением.

По этим причинам для серьезных инсталляций требуются более продвинутые стратегии масштабирования.

## Когда Prometheus "перерастает" себя?

Три основных признака того, что пора задуматься о масштабировании:

1.  **Высокая нагрузка на запись:** Более 1 миллиона сэмплов в секунду. Локальный диск и CPU начинают не справляться с процессами WAL и Compaction.
2.  **Требуется длительное хранение (Retention):** Локальная TSDB не предназначена для хранения данных дольше 30-60 дней. Попытка хранить данные за год на локальном диске приведет к огромным затратам на хранение и крайне медленным запросам.
3.  **Множество кластеров и инстансов:** Управление десятками отдельных Prometheus-серверов, их правилами и алертами становится неэффективным. Требуется "глобальный" обзор всех метрик.

## Стратегии масштабирования

### 1. Federation (Федерация)

**Как это работает:** Один "верхнеуровневый" Prometheus опрашивает другие "нижестоящие" инстансы Prometheus. Он забирает у них не все данные, а обычно уже агрегированные временные ряды.

*   **Плюсы:**
    *   Относительно простой способ получить общую картину по нескольким кластерам (например, агрегировать метрику `up` со всех инстансов).
*   **Минусы:**
    *   **Потеря гранулярности:** Верхнеуровневый Prometheus видит только агрегированные данные, теряя исходные лейблы.
    *   **Не масштабируется:** Не решает проблему дискового пространства и длительного хранения.
    *   **Проблемы с синхронизацией:** Могут возникать расхождения данных и дублирование метрик.

**Вывод:** Федерация — это временное решение или "костыль". Она подходит для простых задач агрегации, но не для построения полноценного, масштабируемого хранилища.

### 2. Remote Read/Write (Удаленное чтение/запись)

Это современный и предпочтительный подход к масштабированию. В этой архитектуре Prometheus перестает быть монолитной системой с базой данных и становится **агентом по сбору метрик**.

**Как это работает:**
1.  Каждый локальный экземпляр Prometheus собирает метрики в своем окружении (кластере, дата-центре).
2.  С помощью механизма **`remote_write`** он отправляет все собранные сэмплы в реальном времени в централизованное, распределенное хранилище (Long-Term Storage).
3.  Это центральное хранилище берет на себя задачи по долгосрочному хранению, обеспечению отказоустойчивости, дедупликации и обработке "глобальных" запросов.

**Популярные решения для долгосрочного хранения (Long-Term Storage):**

*   **[Thanos](./thanos_overview.md):** Проект экосистемы CNCF, тесно интегрированный с Prometheus. Использует подход с `sidecar`-контейнером, который выгружает данные в облачное объектное хранилище (например, S3). Предоставляет глобальный вид для запросов и выполняет дедупликацию данных.

*   **[VictoriaMetrics](../../VictoriaMetrics/overview.md):** Высокопроизводительное решение, которое использует собственный формат хранения и не зависит от объектных хранилищ. Prometheus отправляет в него данные через `remote_write`. Считается более простым в настройке и эффективным по использованию ресурсов.

*   **[Grafana Mimir](../Mimir/mimir_overview.md):** Горизонтально масштабируемое решение от Grafana Labs, также использующее `remote_write` и объектное хранилище. Является форком проекта Cortex.

**Преимущества:**
*   **Горизонтальное масштабирование:** Централизованные хранилища спроектированы для работы в кластере и могут хранить петабайты данных.
*   **Долгосрочное хранение:** Позволяет хранить метрики годами.
*   **Глобальный обзор:** Возможность выполнять запросы по данным со всех кластеров из единой точки (например, из Grafana).
*   **Отказоустойчивость:** Локальные экземпляры Prometheus становятся "stateless" (без состояния) с точки зрения долгосрочных данных. Их можно перезапускать или удалять без потери истории метрик.

**Недостатки:**
*   **Потеря простоты:** Архитектура значительно усложняется. Вместо одного конфигурационного файла Prometheus появляется сложная распределенная система, которую нужно настраивать и обслуживать.
*   **Сложность отладки:** При возникновении проблем сложнее определить источник — это проблема на стороне агента Prometheus или в центральном хранилище.

## Выбор подхода

Каждый подход имеет свои компромиссы. Для небольших и средних инсталляций достаточно одного экземпляра Prometheus. Когда требования к хранению и масштабам растут, переход на архитектуру с `remote_write` и централизованным хранилищем становится неизбежным.
