# Масштабирование Prometheus

Масштабирование Prometheus требуется при росте инфраструктуры, когда локальная TSDB (Time Series Database) и архитектура с одним экземпляром (single-instance) перестают справляться с нагрузкой на запись, хранение или выполнение запросов.

## Определения

Необходимость в масштабировании возникает при достижении следующих лимитов:

| Проблема | Описание | Индикаторы |
|---|---|---|
| **Нагрузка на запись** | Превышение лимитов CPU/RAM при сборе метрик (ingestion) | >1 млн сэмплов/сек, высокая нагрузка на WAL и Compaction |
| **Кардинальность** | Слишком большое количество уникальных временных рядов | Взрывной рост оперативной памяти, замедление запросов |
| **Retention (Хранение)** | TSDB не предназначена для хранения больших объемов данных годами | Заполнение диска, деградация производительности при чтении старых данных |
| **Глобальный обзор** | Сложность работы с десятками независимых серверов | Требуется единая точка входа для Grafana и централизованный алертинг |

## Базовые концепции

### Вертикальное масштабирование (Vertical Scaling)

Самый простой способ, заключающийся в выделении дополнительных ресурсов существующему инстансу.

*   **Лимиты ресурсов:** Prometheus эффективно использует многопоточность для скрейпинга, но выполнение запросов и Compaction TSDB могут упираться в производительность одного ядра и скорость I/O диска.
*   **Тюнинг Go:** Настройка переменной окружения `GOGC` (по умолчанию 100) позволяет управлять частотой сборки мусора. Увеличение (например, до 200+) снижает нагрузку на CPU за счет большего потребления RAM.
*   **In-place Pod Vertical Scaling:** В Kubernetes 1.31+ поддерживается изменение `limits` и `requests` без перезапуска пода. Это критично для Prometheus, так как позволяет избежать долгого прогрева кешей и WAL при рестарте из-за нехватки памяти.
*   **Memory Management:** Использование флагов `--storage.tsdb.min-block-duration` и `--storage.tsdb.max-block-duration` позволяет косвенно влиять на потребление памяти при индексации блоков.

### Базовая отказоустойчивость (HA — High Availability)

Высокая доступность достигается **дублированием компонентов**. Запускаются два идентичных экземпляра Prometheus, которые независимо опрашивают одни и те же цели.

*   **Принцип работы:** Оба сервера собирают данные (pull-модель), но только один (или оба через дедупликатор) отправляет алерты в кластер Alertmanager.
*   **Ограничения:** Реплики никогда не идентичны на 100% (расхождение в миллисекундах при скрейпинге); Grafana видит дубликаты рядов, если не настроен внешний слой дедупликации (Thanos Query или VictoriaMetrics).

### Режим агента (Prometheus Agent Mode)

Эффективный сбор данных без локального хранения (введен в v2.32.0).

*   **Суть:** Запуск с флагом `--enable-feature=agent`. В этом режиме TSDB заменяется на облегченный WAL.
*   **Преимущества:** Потребляет на 30–40% меньше ресурсов (CPU/RAM), не хранит данные локально, не выполняет правила (alerting/recording).
*   **Применение:** Идеально подходит для "граничных" (edge) кластеров, которые только собирают метрики и сразу отправляют их в центральное хранилище через Remote Write.

### Стратегии масштабирования

| Стратегия | Описание | Когда использовать |
|---|---|---|
| **Federation** | Иерархическая агрегация: вышестоящий сервер опрашивает нижестоящие | Простая агрегация из нескольких кластеров, перенос части метрик |
| **Sharding** | Распределение целей между несколькими экземплярами для снижения нагрузки | Очень высокая нагрузка (>1 млн samples/s), тысячи таргетов |
| **Remote Write 2.0** | Отправка данных во внешние системы (LTS) с оптимизацией | **Стандарт 2025-2026:** долгосрочное хранение, глобальный обзор |

### Шардирование (Sharding)

Шардирование распределяет нагрузку на скрейпинг между несколькими инстансами.

1.  **Функциональное:** Разделение по доменам (один инстанс для K8s, другой для БД).
2.  **Хэш-шардирование:** Распределение таргетов внутри одного задания (job) на основе хэша.

**Пример хэш-шардирования (через `hashmod`):**
```yaml
scrape_configs:
  - job_name: 'my-large-app'
    relabel_configs:
      - source_labels: [__address__]
        modulus: 4           # Всего 4 шарда
        target_label: __tmp_hash
        action: hashmod
      - source_labels: [__tmp_hash]
        regex: '^0$'         # Этот инстанс — шард №0
        action: keep
```
> **Совет:** При использовании [Prometheus Operator](../kubernetes/operator/high_availability.md) шардирование настраивается одной строкой в манифесте (`shards: N`), и оператор сам распределяет хэши через автоматическую конфигурацию `hashmod`.

### Удаленная запись (Remote Write 2.0)

В 2025-2026 годах протокол Remote Write 2.0 стал стандартом для масштабируемых архитектур.

*   **String Interning:** Значительное снижение объема передаваемых данных (до 60%) за счет передачи идентификаторов строк вместо полных имен меток и значений в каждом пакете.
*   **Метаданные и экземпляры:** Передача типов метрик и экземпляров (exemplars) в потоке данных, что критично для интеграции с распределенной трассировкой (Tracing).
*   **Created Timestamps:** Позволяет корректно обрабатывать сбросы счетчиков (counter resets) на стороне приемника, что повышает точность вычислений в PromQL.

## Практические сценарии

### Сценарий 1: Классический HA с балансировщиком (Bare-metal/VM)

Обеспечивает переключение между двумя инстансами Prometheus.

1.  Запустить два сервера Prometheus с идентичной конфигурацией.
2.  Настроить балансировщик (HAProxy/Nginx): `server1` — основной, `server2` — резервный (`backup`).
3.  Grafana запрашивает данные с виртуального IP балансировщика.
4.  **Минус:** Возможны небольшие расхождения в данных ("ступеньки") на графиках при переключении из-за разницы во времени скрейпинга (джиттера).

### Сценарий 2: Современный стек (Cloud Native)

Оптимальный путь для Kubernetes и гибридных облаков.

1.  **Сбор:** Множество инстансов Prometheus в режиме **Agent Mode** или **Grafana Alloy**.
2.  **Транспорт:** Протокол **Remote Write 2.0** (с поддержкой OTLP).
3.  **Хранение:** Централизованное горизонтально масштабируемое хранилище ([VictoriaMetrics](../../VictoriaMetrics/overview.md), [Mimir](../../Mimir/mimir_overview.md) или [Thanos](./thanos_overview.md)).
4.  **Алертинг:** Правила обработки (Recording/Alerting) выполняются на стороне LTS-хранилища для обеспечения глобального контекста.

## Дополнительная информация

### Сравнение решений для долгосрочного хранения (LTS)

| Решение | Архитектура | Хранилище | Сильные стороны |
|---|---|---|---|
| **Thanos** | Децентрализованная (Sidecar) | Объектное (S3/GCS) | Прозрачное расширение существующего Prometheus |
| **VictoriaMetrics** | Монолит или Кластер | Локальные диски / PV | **Экстремальная производительность**, сжатие данных, простота |
| **Grafana Mimir** | Микросервисная | Объектное (S3/GCS) | Мульти-тенантность, изоляция данных, масштаб в миллиарды серий |

### Лучшие практики (2025–2026)

1.  **Разделяйте скрейпинг и хранение:** Используйте Prometheus только как "умный агент" (Agent Mode), отдавая долгосрочное хранение и тяжелые запросы специализированным системам.
2.  **Native Histograms:** Используйте нативные гистограммы (введены в v2.40) для снижения кардинальности и объема занимаемого места на диске (до 40% экономии по сравнению с классическими гистограммами).
3.  **Используйте объектные хранилища:** Для Thanos/Mimir хранение данных в S3 обходится значительно дешевле, чем на блочных дисках.
4.  **Управляйте кардинальностью:** Удаляйте ненужные лейблы на этапе скрейпинга через `metric_relabel_configs`. Подробнее: [Метки и кардинальность](../concepts/labels_and_cardinality.md).
5.  **Downsampling:** Для хранения данных дольше года обязательно настройте понижение дискретизации (downsampling) в LTS, чтобы ускорить построение графиков за большие периоды.
