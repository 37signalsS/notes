# Масштабирование Prometheus

Prometheus гениален в своей простоте, но его архитектура, ориентированная на один узел с локальным хранилищем, имеет пределы масштабируемости. Когда инфраструктура разрастается, возникает необходимость в централизованном, отказоустойчивом и долгосрочном хранении метрик.

## Базовая отказоустойчивость: дублирование компонентов

Система мониторинга является ключевым элементом любой production-среды, и ее стабильность напрямую влияет на скорость реакции на инциденты. Prometheus предлагает несколько подходов для обеспечения высокой доступности (HA).

Самый простой способ — это **дублирование компонентов**.

1.  **Дублирование Prometheus Server:**
    *   Запускаются два или более экземпляра Prometheus с идентичной конфигурацией. Поскольку Prometheus работает по pull-модели, с его дублированием не возникает проблем — каждый экземпляр будет независимо собирать один и тот же набор метрик.
    *   Единственное требование — обеспечить идентичность конфигураций на всех серверах.

2.  **Дублирование Alertmanager:**
    *   Экземпляры Alertmanager также дублируются.
    *   Чтобы избежать отправки дублированных уведомлений, когда оба сервера Prometheus шлют одинаковые алерты, Alertmanager настраивается в режиме кластера. Это позволяет инстансам общаться между собой по gossip-протоколу и дедуплицировать уведомления.
    *   Дополнительно, если в Alertmanager настроена группировка и задержка (`group_wait`), он сможет эффективно "схлопывать" одинаковые алерты, пришедшие почти одновременно от разных Prometheus, в одно оповещение.

### Проблемы базового подхода

Эта простая схема решает задачу отказоустойчивости для алертинга, но создает проблемы для визуализации данных.

*   **Расхождение данных:** Поскольку два экземпляра Prometheus собирают метрики в разное время (пусть и с небольшой разницей), их наборы данных никогда не будут на 100% идентичны.
*   **Проблема визуализации в Grafana:** Если подключить Grafana к обоим серверам, она будет получать дублированные, но слегка отличающиеся временные ряды. Для построения корректных графиков необходимо, чтобы все запросы для одного дашборда уходили на один и тот же экземпляр Prometheus.
*   **Решение с прокси:** Простейший способ решить эту проблему — разместить между Grafana и серверами Prometheus прокси-балансировщик (например, HAProxy) в режиме `standby` (основной/резервный). В этом случае Grafana всегда обращается к одному активному серверу, а в случае его отказа автоматически переключается на резервный.

## Проблема стандартного подхода к HA

Официальная документация Prometheus предлагает для высокой доступности (HA) запускать два идентичных экземпляра Prometheus, которые собирают одни и те же метрики, и использовать Alertmanager для дедупликации оповещений.

**Почему этот подход неполноценен:**

*   **Проблема визуализации:** Этот метод решает проблему только для алертинга. При визуализации метрик в Grafana вы столкнетесь с дублированием данных, так как Grafana будет получать идентичные временные ряды от двух разных источников. Это требует создания сложных и неудобных решений на уровне дашбордов или использования балансировщика, который не решает проблему полностью.
*   **Не решает проблему масштабирования:** Этот подход удваивает ресурсы, но не решает фундаментальных проблем с нагрузкой и длительным хранением.

По этим причинам для серьезных инсталляций требуются более продвинутые стратегии масштабирования.

## Когда Prometheus "перерастает" себя?

Три основных признака того, что пора задуматься о масштабировании:

1.  **Высокая нагрузка на запись:** Более 1 миллиона сэмплов в секунду. Локальный диск и CPU начинают не справляться с процессами WAL и Compaction.
2.  **Требуется длительное хранение (Retention):** Локальная TSDB не предназначена для хранения данных дольше 30-60 дней. Попытка хранить данные за год на локальном диске приведет к огромным затратам на хранение и крайне медленным запросам.
3.  **Множество кластеров и инстансов:** Управление десятками отдельных Prometheus-серверов, их правилами и алертами становится неэффективным. Требуется "глобальный" обзор всех метрик.

## Стратегии масштабирования

### 1. Federation (Федерация)

**Как это работает:** Один "верхнеуровневый" Prometheus опрашивает другие "нижестоящие" инстансы Prometheus. Он забирает у них не все данные, а обычно уже агрегированные временные ряды.

*   **Плюсы:**
    *   Относительно простой способ получить общую картину по нескольким кластерам (например, агрегировать метрику `up` со всех инстансов).
*   **Минусы:**
    *   **Потеря гранулярности:** Верхнеуровневый Prometheus видит только агрегированные данные, теряя исходные лейблы.
    *   **Не масштабируется:** Не решает проблему дискового пространства и длительного хранения.
    *   **Проблемы с синхронизацией:** Могут возникать расхождения данных и дублирование метрик.

**Вывод:** Федерация — это временное решение или "костыль". Она подходит для простых задач агрегации, но не для построения полноценного, масштабируемого хранилища.

### 2. Remote Read/Write (Удаленное чтение/запись)

Это современный и предпочтительный подход к масштабированию, позволяющий решить проблему ограниченного дискового пространства локального хранилища. В этой архитектуре Prometheus может делегировать хранение данных внешним системам.

> Подробнее о параметрах конфигурации см. в заметке **[[./remote_read_write.md]]**.

**Как это работает:**

Prometheus разделяет процессы удаленной записи (`remote_write`) и чтения (`remote_read`).

*   **Remote Write:** Локальный экземпляр Prometheus отправляет собранные метрики в **адаптер**, который уже отвечает за их сохранение в удаленном хранилище. Такая архитектура позволяет легко расширять список поддерживаемых хранилищ, не изменяя код самого Prometheus. Некоторые хранилища могут поддерживать только запись.

*   **Remote Read:** При выполнении запроса, который охватывает данные в удаленном хранилище, Prometheus запрашивает у адаптера необходимые данные за указанный промежуток времени.

**Ключевой момент:** Вся обработка данных (агрегация, вычисление функций) по-прежнему производится на стороне самого Prometheus-сервера. Это означает, что при выполнении "тяжелых" запросов за длительный период времени Prometheus сначала выгрузит огромный объем "сырых" данных из удаленного хранилища, и ему потребуется достаточно оперативной памяти и CPU для их обработки. Этот аспект необходимо учитывать при планировании ресурсов.

В конечном итоге, при использовании `remote_write`, локальный Prometheus часто выступает в роли **агента по сбору метрик**:
1.  Он собирает метрики в своем окружении (кластере, дата-центре).
2.  С помощью `remote_write` он отправляет все собранные сэмплы в реальном времени в централизованное хранилище.
3.  Центральное хранилище берет на себя задачи по долгосрочному хранению, обеспечению отказоустойчивости, дедупликации и обработке "глобальных" запросов.

**Популярные решения для долгосрочного хранения (Long-Term Storage):**

*   **[Thanos](./thanos_overview.md):** Проект экосистемы CNCF, тесно интегрированный с Prometheus. Использует подход с `sidecar`-контейнером, который выгружает данные в облачное объектное хранилище (например, S3). Предоставляет глобальный вид для запросов и выполняет дедупликацию данных.

*   **[VictoriaMetrics](../../VictoriaMetrics/overview.md):** Высокопроизводительное решение, которое использует собственный формат хранения и не зависит от объектных хранилищ. Prometheus отправляет в него данные через `remote_write`. Считается более простым в настройке и эффективным по использованию ресурсов.

*   **[Grafana Mimir](../Mimir/mimir_overview.md):** Горизонтально масштабируемое решение от Grafana Labs, также использующее `remote_write` и объектное хранилище. Является форком проекта Cortex.

**Преимущества:**
*   **Горизонтальное масштабирование:** Централизованные хранилища спроектированы для работы в кластере и могут хранить петабайты данных.
*   **Долгосрочное хранение:** Позволяет хранить метрики годами.
*   **Глобальный обзор:** Возможность выполнять запросы по данным со всех кластеров из единой точки (например, из Grafana).
*   **Отказоустойчивость:** Локальные экземпляры Prometheus становятся "stateless" (без состояния) с точки зрения долгосрочных данных. Их можно перезапускать или удалять без потери истории метрик.

**Недостатки:**
*   **Потеря простоты:** Архитектура значительно усложняется. Вместо одного конфигурационного файла Prometheus появляется сложная распределенная система, которую нужно настраивать и обслуживать.
*   **Сложность отладки:** При возникновении проблем сложнее определить источник — это проблема на стороне агента Prometheus или в центральном хранилище.

## Выбор подхода

Каждый подход имеет свои компромиссы. Для небольших и средних инсталляций достаточно одного экземпляра Prometheus. Когда требования к хранению и масштабам растут, переход на архитектуру с `remote_write` и централизованным хранилищем становится неизбежным.

## Практический сценарий: Настройка базового HA с HAProxy

Этот документ описывает настройку высокодоступного (HA) кластера Prometheus с использованием HAProxy в качестве балансировщика нагрузки. Этот сценарий реализует стратегию "дублирования компонентов".

### 1. Установка и настройка Prometheus в режиме HA

Этот шаг необходимо выполнить на двух серверах (server1 и server2) для создания дублирующих экземпляров Prometheus.

#### 1.1 Установка Prometheus

Установите Prometheus на серверы `server1` и `server2`. Инструкции по установке можно найти в документе [[../installation/from_binary.md]].

#### 1.2 Настройка `prometheus.yml`

На каждом из серверов Prometheus обновите конфигурационный файл. Эта конфигурация настраивает каждый экземпляр на сбор метрик с нескольких `node_exporter` и указывает `alertmanager` в качестве цели для алертов.

```bash
# Замените плейсхолдеры на реальные IP-адреса
cat <<EOF > /etc/prometheus/prometheus.yml
global:
  scrape_interval:     15s 
  evaluation_interval: 15s 

alerting:
  alertmanagers:
  - static_configs:
    - targets:
      - <monitoring_ip>:9093

scrape_configs:
  - job_name: 'prometheus'
    static_configs:
    - targets: ['localhost:9090']
  - job_name: 'node_exporter'
    static_configs:
    - targets:
        - <monitoring_ip>:9100
        - <server1_ip>:9100
        - <server2_ip>:9100
EOF
```

#### 1.3 Перезапуск и проверка
```bash
systemctl restart prometheus.service
# Проверьте, что Prometheus работает на порту 9090
curl -XGET -IL http://localhost:9090/graph
```

### 2. Настройка HAProxy

Для обеспечения отказоустойчивости доступа к экземплярам Prometheus со стороны Grafana, установим и настроим HAProxy на отдельном сервере.

#### 2.1 Установка HAProxy
```bash
# Для CentOS/RHEL
yum install -y haproxy
# Для Debian/Ubuntu
apt-get install -y haproxy
```

#### 2.2 Настройка `haproxy.cfg`

Эта конфигурация настраивает HAProxy на проксирование запросов с порта `80` на один из серверов Prometheus. `server1` будет основным (`check`), а `server2` — резервным (`check backup`).

```bash
# /etc/haproxy/haproxy.cfg
# Замените плейсхолдеры на реальные IP-адреса
cat <<EOF > /etc/haproxy/haproxy.cfg 
global
 daemon
 maxconn 256
defaults
 mode http
 timeout connect 5000ms
 timeout client 50000ms
 timeout server 50000ms
listen stats
 bind *:9999
 stats enable
 stats hide-version
 stats uri /stats
 stats auth admin:admin@123
frontend prom
 bind *:80
 use_backend prom
backend prom
 server prom1 <server1_IP>:9090 check
 server prom2 <server2_IP>:9090 check backup
EOF
```

#### 2.3 Запуск HAProxy
```bash
systemctl start haproxy.service
```

### 3. Настройка Grafana

#### 3.1 Добавление Data Source

Добавьте новый источник данных (Data Source) в Grafana:
-   **Name**: `Prometheus HA`
-   **URL**: `http://<haproxy_ip>:80` (адрес сервера с HAProxy)

#### 3.2 Добавление Dashboard

Импортируйте дашборд, например, с ID `1860`. При импорте **важно** в качестве источника данных (`Prometheus data source`) выбрать созданный ранее `Prometheus HA`.

### 4. Проверка отказоустойчивости

Для проверки, что HA-схема работает корректно, поочередно останавливайте сервис Prometheus на `server1` и `server2` и убедитесь, что графики в Grafana продолжают отображаться.

```bash
# На server1, затем на server2
systemctl stop prometheus.service
```
