# Утилита PromTool и лучшие практики эксплуатации

## 1. Утилита `promtool`

**PromTool** — это утилита, входящая в состав [Prometheus](./overview.md) и предназначенная для статической проверки (линтер) корректности файлов конфигурации, правил и метрик. Это незаменимый инструмент для автоматизации и обеспечения стабильности.

### 1.1. Основные команды

#### `promtool check config <path_to_prometheus.yml>`

Проверяет основной конфигурационный файл `prometheus.yml` на синтаксическую корректность. Обязателен к использованию в CI/CD перед применением изменений.

**Пример:**
```bash
promtool check config /etc/prometheus/prometheus.yml
# В случае успеха выведет "SUCCESS" и вернет exit code 0.
```

#### `promtool check rules <path_to_rules_file.yml>`

Проверяет файлы с [правилами записи и оповещений](./rules.md) на наличие синтаксических ошибок и логическую корректность выражений PromQL.

**Пример:**
```bash
promtool check rules /etc/prometheus/rules/*.yml
```

#### `promtool check metrics`

Валидирует метрики, получаемые от экспортера, на соответствие формату и стандартам Prometheus. Эта команда читает метрики из стандартного ввода (stdin), что позволяет легко интегрировать ее с `curl`.

**Пример:** Проверка метрик, отдаваемых `node_exporter`.
```bash
curl -s http://localhost:9100/metrics | promtool check metrics
```
Инструмент выведет предупреждения или ошибки, если найдет проблемы, например, отсутствие `HELP` комментариев или некорректные типы метрик.

### 1.2. Прочие возможности

*   `promtool tsdb dump`: Позволяет сделать дамп данных из [базы данных Prometheus (TSDB)](./concepts/tsdb.md) для отладки.
*   `promtool debug`: Предоставляет различную отладочную информацию о работающем сервере Prometheus.

## 2. Лучшие практики эксплуатации

### 2.1. Управление ресурсами (Resource Management)

Всегда определяйте [запросы (`requests`) и лимиты (`limits`)](../Kubernetes/Scheduling/qos_limit_and_requests.md) по CPU и памяти для контейнеров Prometheus и его компонентов, особенно в [Kubernetes](../Kubernetes/kubernetes_overview.md). Prometheus может быть очень требователен к оперативной памяти, и отсутствие лимитов может привести к нестабильности всего узла.

```yaml
# Пример для Kubernetes
resources:
  requests:
    memory: "2Gi"
    cpu: "500m"
  limits:
    memory: "4Gi"
    cpu: "1"
```

### 2.2. Версионирование компонентов

Никогда не используйте тег `latest` для [Docker-образов](../Docker/Dockerfile/dockerfile_best_practices.md) Prometheus, [Alertmanager](./alertmanager.md) или [экспортеров](./exporters.md). Всегда указывайте конкретную, протестированную версию (например, `prom/prometheus:v2.53.1`). Синтаксис конфигурации, флаги запуска и поведение могут меняться между версиями, что может привести к неожиданным сбоям при автоматическом обновлении.

### 2.3. Контроль кардинальности

Высокая кардинальность (количество уникальных временных рядов) — одна из главных причин высокого потребления ресурсов и низкой производительности Prometheus.
*   **Избегайте** использования в метках (labels) данных с высокой степенью уникальности: ID пользователей, хэши запросов, email-адреса.
*   Регулярно отслеживайте метрики, связанные с количеством временных рядов, и используйте `promtool tsdb analyze` для поиска "проблемных" метрик.

> Подробнее см. **[Лейблы и кардинальность в Prometheus](./concepts/labels_and_cardinality.md)**.

### 2.4. Отказоустойчивость и долгосрочное хранение (HA & LTS)

Локальная TSDB Prometheus не предназначена для долгосрочного хранения и не имеет встроенных механизмов кластеризации. Для production-окружений необходимо использовать внешние решения.

*   **Подход:** Использовать архитектуру с `remote_write`, где локальные экземпляры Prometheus выступают в роли агентов, отправляющих метрики в централизованное, масштабируемое хранилище.
*   **Решения:**
    *   **[VictoriaMetrics](../VictoriaMetrics/overview.md)**: Высокопроизводительное и эффективное по ресурсам решение.
    *   **[Thanos](./scaling/thanos_overview.md)**: Глубоко интегрированное с Prometheus решение, использующее объектные хранилища (S3).
    *   **[Grafana Mimir](../Mimir/mimir_overview.md)**: Горизонтально масштабируемое решение от Grafana Labs.

> Подробнее об архитектурных подходах см. **[Масштабирование Prometheus](./scaling/overview.md)**.
> Конфигурация удаленной записи описана в **[Prometheus Remote Read/Write](./scaling/remote_read_write.md)**.

### 2.5. Управление конфигурацией в [CI/CD](../CI-CD/ci_cd_overview.md)

*   **[GitOps](../GitOps/GitOps_overview.md)**: Храните все конфигурационные файлы Prometheus (`prometheus.yml`) и файлы правил (`*.rules.yml`) в системе контроля версий [Git](../Git/git_basics.md).
*   **Автоматическая валидация**: Внедрите `promtool check config` и `promtool check rules` в ваш CI/CD-пайплайн. Любое изменение конфигурации должно проходить проверку автоматически, прежде чем попасть в production. Это предотвращает развертывание некорректных конфигураций, которые могут остановить сбор метрик.
