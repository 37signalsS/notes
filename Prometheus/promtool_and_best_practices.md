# Prometheus: promtool и лучшие практики

## Определения

В данном разделе рассматриваются инструменты валидации и рекомендации по эксплуатации [Prometheus](./overview.md).

* **`promtool`** — официальная CLI-утилита для статической проверки конфигурации, правил алертинга и записи, а также для анализа состояния базы данных TSDB.
* **Кардинальность (Cardinality)** — количество уникальных временных рядов в системе. Является ключевым фактором, определяющим потребление оперативной памяти и нагрузку на диск. Подробности: [Лейблы и кардинальность](./concepts/labels_and_cardinality.md).
* **Долгосрочное хранение (LTS)** — архитектурный подход к хранению метрик за пределами локальной TSDB Prometheus для обеспечения их доступности на длительных временных интервалах. Подробности: [Обзор масштабирования](./scaling/overview.md).

> **См. также:** [Обзор Prometheus](./overview.md), [Конфигурация](./configuration.md), [Правила](./rules.md).

## Основные концепции

### Валидация конфигурации

Ошибки в основном конфигурационном файле или в файлах правил приводят к остановке сбора метрик или некорректной работе оповещений. Статическая проверка через `promtool` — обязательный этап конвейера CI/CD или ручного обновления перед выполнением Hot Reload.

### Управление ресурсами

Prometheus потребляет значительные ресурсы CPU и RAM. В средах Kubernetes критически важно задавать явные `requests` и `limits`, чтобы избежать OOM (Out Of Memory) или деградации производительности.

### Контроль кардинальности

Высокая кардинальность — основная причина проблем с производительностью Prometheus.

**Антипаттерны в именовании лейблов:**

* Использование уникальных ID (user_id, session_id, email).
* Использование хэшей запросов или полных URL с динамическими сегментами.

**Рекомендации:**

* Агрегируйте данные на этапе [Relabeling](./service_discovery_and_relabeling.md) (например, заменяйте `/api/v1/user/12345` на `/api/v1/user/:id`).
* Используйте `promtool tsdb analyze` для регулярного мониторинга churn rate и выявления метрик-лидеров по количеству серий.

### Отказоустойчивость

Локальная TSDB спроектирована для оперативного мониторинга и не является кластерным решением. Для построения отказоустойчивых систем в промышленной эксплуатации (Production) рекомендуется использовать внешние хранилища через механизм `remote_write`.

## Практические сценарии

### Использование promtool для проверки

**1. Проверка основного файла конфигурации:**

```bash
promtool check config /etc/prometheus/prometheus.yml
```

**2. Валидация файлов с правилами:**

```bash
promtool check rules /etc/prometheus/rules/*.yml
```

**3. Проверка формата метрик экспортера:**
Позволяет убедиться, что кастомный экспортер отдает данные в корректном формате:

```bash
curl -s http://localhost:9100/metrics | promtool check metrics
```

### Анализ состояния TSDB

Поиск метрик с высокой кардинальностью в работающей базе или в отдельных блоках данных:

```bash
# Анализ текущего состояния
promtool tsdb analyze /path/to/tsdb/data

# Анализ конкретного блока по его ID
promtool tsdb analyze --block-id <block-id> /path/to/tsdb/data
```

### Процедурные лучшие практики

* **GitOps:** храните конфигурацию (`prometheus.yml`) и правила в Git. Все изменения должны проходить через `promtool check` в пайплайне перед применением.
* **Версионирование:** никогда не используйте тег `:latest` для образов в Production. Закрепляйте конкретную версию приложения: `prom/prometheus:v3.11.1`.
* **Лимиты ресурсов (Kubernetes):**

```yaml
resources:
  requests:
    memory: "2Gi"
    cpu: "500m"
  limits:
    memory: "4Gi"
    cpu: "1"
```

## Дополнительная информация

### Сводная таблица команд promtool

| Команда | Описание |
|---|---|
| `promtool check config <file>` | Полная валидация YAML-конфигурации |
| `promtool check rules <file>` | Проверка синтаксиса файлов правил |
| `promtool check metrics` | Валидация формата экспозиции из стандартного ввода |
| `promtool tsdb analyze <path>` | Статистика по кардинальности и лейблам |
| `promtool tsdb dump <path>` | Вывод сырых данных из TSDB |
