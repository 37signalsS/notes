# Сводка лекции: Мониторинг Kubernetes с помощью Kube-Prometheus-Stack

Эта заметка обобщает ключевые моменты из демо-занятия, посвященного развертыванию и использованию стека `kube-prometheus-stack` для мониторинга в Kubernetes.

## 1. Введение и цели

*   **Задача:** Научиться развертывать комплексную систему мониторинга в Kubernetes для отслеживания состояния как самого кластера, так и запускаемых в нем приложений.
*   **Решение:** Использование Helm-чарта `kube-prometheus-stack`, который является отраслевым стандартом и значительно упрощает развертывание.

## 2. Обзор экосистемы Prometheus

Prometheus — это мощная **time series database (TSDB)** и целая экосистема для мониторинга, изначально разработанная в Google как Borgmon. Она предназначена для сбора и хранения метрик, а также для обработки запросов по ним. Основные компоненты включают:

*   **Prometheus Server:** Центральный компонент для сбора, хранения и обработки метрик. Разворачивается как `StatefulSet`. Осуществляет сбор метрик по модели pull-based, активно опрашивая (scrapes) целевые эндпоинты экспортеров по HTTP. Имеет встроенный механизм `service discovery` для автоматического обнаружения целей в динамических средах.
*   **Alertmanager:** Отдельная сущность, отвечающая за дедупликацию, группировку и маршрутизацию оповещений, сгенерированных Prometheus. Он получает алерты от Prometheus и отправляет их в различные каналы связи.
*   **Push Gateway:** Компонент, предназначенный для сбора метрик от кратковременных или периодически запускаемых задач (например, `cron` job), которые не могут быть опрошены Prometheus напрямую. Эти задачи "проталкивают" (push) свои метрики в Push Gateway, откуда Prometheus их уже забирает по своей стандартной pull-модели.
*   **Экспортеры:** Программы, которые собирают метрики из различных систем (ОС, базы данных, приложения) и преобразуют их в текстовый формат, понятный Prometheus, предоставляя по HTTP-эндпоинту (обычно `/metrics`). Примеры: `node-exporter` для метрик хоста, `kube-state-metrics` для метрик объектов Kubernetes.
*   **Grafana:** Инструмент для мощной визуализации метрик, создания интерактивных дашбордов и настройки алертов. Работает с Prometheus как с основным источником данных.

## 3. Ключевые компоненты `kube-prometheus-stack`

Этот Helm-чарт устанавливает и настраивает целую экосистему компонентов, значительно упрощая развертывание и управление мониторингом в Kubernetes:

*   **Prometheus Server:** Как описано выше, сфокусирован на сборе и хранении метрик кластера и приложений.
*   **Prometheus Operator:** Является "мозгом" системы. Это контроллер Kubernetes, который расширяет API с помощью Custom Resource Definitions (CRD). Он управляет конфигурацией Prometheus и других компонентов, автоматически преобразуя декларативные CRD-манифесты в реальные объекты кластера (StatefulSet, ConfigMap, Secret и т.д.).
*   **Grafana:** Для визуализации метрик, поставляется с набором готовых дашбордов для Kubernetes.
*   **Alertmanager:** Для управления и маршрутизации оповещений, с возможностью кластеризации для высокой доступности.
*   **Node Exporter:** Собирает метрики с узлов Kubernetes (CPU, RAM, диск, сеть и т.д.). Разворачивается как `DaemonSet`, что обеспечивает его запуск на каждом узле кластера. Читает данные из `/proc` и `/sys` файловых систем Linux.
*   **Kube-State-Metrics:** Специализированный экспортер, который генерирует метрики о состоянии объектов Kubernetes (деплойменты, поды, сервисы, ноды и т.д.), слушая Kubernetes API. Эти метрики предоставляют ценную информацию о здоровье и производительности кластера.
    *   **Примеры полезных метрик:**
        *   `kube_deployment_status_replicas_unavailable`: Отслеживает количество недоступных реплик для деплойментов. Значение больше нуля может указывать на проблемы.
        *   `kube_node_status_capacity_memory_bytes`: Показывает общую емкость памяти для каждой ноды.
        *   `kube_pod_container_status_restart_total`: Суммарное количество перезапусков контейнера. Постоянный рост указывает на нестабильность приложения.
        *   `kube_pod_container_status_ready`: Показывает готовность контейнера (1 - готов, 0 - нет). Позволяет быстро выявлять неработоспособные поды.
    *   **Рекомендации:**
        *   **Избирательный подход:** Сосредоточьтесь на сборе только тех метрик, которые действительно необходимы для мониторинга и алертинга.
        *   **Оптимизация:** При установке `kube-state-metrics` можно исключить сбор ненужных метрик, чтобы снизить нагрузку на Prometheus и API-сервер.

## 4. Процесс развертывания (практика)

1.  **Подготовка:**
    *   Создается отдельный `namespace` для мониторинга (например, `monitoring`).
    *   Добавляется Helm-репозиторий `prometheus-community`.

2.  **Установка через Helm:**
    *   Используется команда `helm install`.
    *   Ключевым элементом является кастомизация через файл `values.yaml`.

3.  **Настройка `values.yaml`:**
    *   **Prometheus:**
        *   `retention`: Срок хранения метрик в локальном хранилище Prometheus (например, `31d`).
        *   `requests` и `limits`: Запросы и лимиты ресурсов (CPU, Memory).
        *   `persistentVolume`: Конфигурация постоянного хранилища. Использует `volumeClaimTemplate` с указанием `storageClassName` (например, `DigitalOcean Block Storage`), `accessModes` (например, `ReadWriteOnce`) и `size`.
    *   **Grafana:**
        *   `root_url`: Важный параметр для генерации корректных ссылок в Grafana (например, для приглашений пользователей).
        *   `adminPassword`: Пароль для пользователя `admin`. Рекомендуется использовать `Secret` для хранения.
        *   `sidecar.dashboards.enabled: true`: Позволяет Grafana автоматически подгружать дашборды из `ConfigMap`, помеченных специальными лейблами. Это реализует подход "Dashboards as Code".
        *   `additionalGrafanaPlugins`: Позволяет устанавливать дополнительные плагины (например, `grafana-worldmap-panel`).
        *   `persistence`: Настройка постоянного хранилища для Grafana, чтобы сохранять дашборды, созданные через UI, и другие настройки.
    *   **Node Exporter:**
        *   `relabeling`: Настройка правил для обогащения метрик, например, для добавления читаемого имени узла (`node`) в метрики `node-exporter` (используя `__meta_kubernetes_pod_node_name`).

### Доступ к веб-интерфейсам

После установки для доступа к веб-интерфейсам Grafana или Prometheus можно использовать `kubectl port-forward`, если Ingress не настроен. Это эквивалентно SSH-туннелю и позволяет получить доступ к сервисам, работающим внутри кластера, через локальный порт на вашей машине.

*   **Для Grafana (порт 3000):**
    ```bash
    kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80
    ```
    Затем откройте `http://localhost:3000` в браузере. (Имя сервиса может отличаться, например, `prometheus-grafana`).
*   **Для Prometheus (порт 9090):**
    ```bash
    kubectl -n monitoring port-forward svc/kube-prometheus-stack-prometheus 9090:9090
    ```
    Затем откройте `http://localhost:9090` в браузере. (Имя сервиса может отличаться, например, `prometheus-kube-prometheus-prometheus`).

Это позволяет быстро проверить работоспособность и посмотреть дашборды/таргеты без необходимости настройки Ingress.

## 5. Как это работает: Prometheus Operator и CRD

`kube-prometheus-stack` основан на паттерне "Оператор".

*   **Оператор** — это контроллер, который расширяет API Kubernetes с помощью **Custom Resource Definitions (CRD)**.
*   Вместо того чтобы вручную править сложный `prometheus.yml`, вы описываете желаемое состояние с помощью простых CRD-манифестов. Оператор следит за этими CRD и автоматически преобразует их в реальные объекты кластера (StatefulSet, ConfigMap, Secret и т.д.).

### Ключевые CRD:

*   **`ServiceMonitor`**:
    *   Описывает, как Prometheus должен обнаруживать и собирать метрики с группы подов, объединенных одним `Service`.
    *   Использует `selector` для поиска нужных сервисов по их лейблам.
    *   **Важный нюанс**: Prometheus Operator **не** направляет Prometheus на ClusterIP сервиса. Вместо этого он обращается к Kubernetes API, находит `Endpoints` объекта `Service` (которые содержат реальные IP-адреса подов, стоящих за сервисом) и генерирует соответствующую конфигурацию `scrape_config` для Prometheus. Это позволяет собирать метрики со всех подов, а не только с одного случайного, если бы использовался `ClusterIP`.
    *   **Лейбл `release`**: Для корректной работы `ServiceMonitor` в Helm-установке `kube-prometheus-stack` необходимо, чтобы `ServiceMonitor` имел лейбл `release`, совпадающий с названием вашей Helm-инсталляции (например, `release: otus`). Это критически важно, так как без него Prometheus Operator не сможет найти и обработать `ServiceMonitor`.

*   **`PodMonitor`**:
    *   Аналогичен `ServiceMonitor`, но позволяет мониторить поды напрямую по их лейблам, без необходимости создавать для них сервис.

*   **`PrometheusRule`**:
    *   Позволяет декларативно описывать правила алертинга и записи (`recording rules`). Оператор автоматически загружает их в Prometheus.

*   **`Probe`**:
    *   Используется для мониторинга внешних систем (например, веб-сайтов) с помощью `blackbox-exporter`.

## 6. Мониторинг внешних ресурсов

Лекция затронула важные способы мониторинга систем, находящихся **вне Kubernetes**, что часто является актуальной задачей в гибридных инфраструктурах:

1.  **Blackbox-мониторинг:**
    *   Используется `blackbox-exporter` для выполнения внешних проверок доступности (HTTP, TCP, ICMP) произвольных ресурсов.
    *   Настраивается либо через CRD `Probe` (при использовании `kube-prometheus-stack`), либо путем включения `ServiceMonitor` для `blackbox-exporter` и указания целей через его параметры.
    *   Пример: проверка доступности внешнего URL (`google.com`) или внутреннего IP-адреса не-Kubernetes узла (`192.168.1.77`).
    *   **Совет из лекции**: Используйте `Probe` CRD для удобной декларативной настройки blackbox-проверок.

2.  **Whitebox-мониторинг (для систем с Prometheus-метриками):**
    *   Если внешний сервис (например, ВМ, физический сервер) уже отдает метрики в формате Prometheus (например, на нем запущен `node-exporter`), его можно добавить в конфигурацию Prometheus, запущенного в Kubernetes.
    *   Это делается через секцию `prometheus.prometheusSpec.additionalScrapeConfigs` в `values.yaml` Helm-чарта. Сюда можно вписать статические конфигурации (`static_configs`) для целей вне Kubernetes:
        ```yaml
        prometheus:
          prometheusSpec:
            additionalScrapeConfigs:
              - job_name: 'external-non-k8s-host'
                static_configs:
                  - targets: ['192.168.1.100:9100'] # IP и порт node-exporter на внешней ВМ
                    labels:
                      env: 'production'
        ```
    *   **Ключевое условие**: Необходимо обеспечить сетевую связность между Prometheus в Kubernetes и внешними целями.
    *   **Совет из лекции**: Вместо попыток "обратной" интеграции (мониторинга Kubernetes из внешнего Prometheus) эффективнее и проще использовать Prometheus внутри Kubernetes для мониторинга внешних систем, так как это упрощает обслуживание и обеспечивает доступ ко всем преимуществам Prometheus Operator.

## 7. Observability: Метрики, Логи, Трассировка

Важно четко различать роли различных инструментов в Observability (наблюдаемости):

*   **Метрики (Prometheus):** Отвечают на вопрос "**Что происходит?**" или "**Где система работает не так, как мы хотим?**". Помогают понять общее состояние системы, тенденции, утилизацию ресурсов. Метрики — это агрегированные числа, показывающие картину в целом. Они менее пригодны для выяснения "Кто сломал?" или "Почему конкретная транзакция упала?".
*   **Логи (ELK Stack, Grafana Loki):** Отвечают на вопрос "**Почему это произошло?**" или "**Что конкретно случилось?**". Содержат детальную информацию о событиях, происходящих в системе. Могут быть очень полезны для диагностики ошибок, особенно если логи обогащены уникальным `request.id` для сквозного отслеживания запросов через различные микросервисы.
*   **Трассировка (Jaeger, OpenTelemetry):** Отвечает на вопрос "**Как это произошло?**" или "**Какая цепочка вызовов привела к проблеме?**". Позволяет проследить полный путь запроса через распределенную систему, выявить узкие места и задержки в конкретных микросервисах. Это наиболее подходящий инструмент для диагностики проблем, связанных с запросами, проходящими через несколько сервисов.

Каждый из этих инструментов имеет свою специализацию и дополняет друг друга, предоставляя полную картину наблюдаемости системы.

## 8. Выводы

*   `kube-prometheus-stack` — это мощное и гибкое решение, которое является стандартом для мониторинга в Kubernetes.
*   Понимание паттерна "Оператор" и ключевых CRD (`ServiceMonitor`, `PrometheusRule`) является основой для эффективной работы со стеком.
*   Helm и файл `values.yaml` предоставляют широкие возможности для кастомизации под конкретные нужды.
*   Для всестороннего понимания состояния системы необходим комплексный подход, включающий метрики, логи и трассировку.
