# Детальная настройка Helm-чарта Prometheus

## Обзор `values.yaml`

## Глобальные параметры и RBAC

*   `rbac.create`: `true`
    *   **Описание:** Создает все необходимые роли и привязки (Roles, RoleBindings) для работы Prometheus в кластере.
    *   **Рекомендация:** Оставить `true`. Для повышенной безопасности рекомендуется развернуть Prometheus на тестовом стенде с включенным RBAC и изучить создаваемые роли и привязки, чтобы убедиться в отсутствии избыточных разрешений.

*   `podSecurityPolicy.enabled`: `false`
    *   **Описание:** Включает создание PodSecurityPolicy для компонентов Prometheus.
    *   **Рекомендация:** Устанавливать в `true` только в том случае, если в вашем кластере уже используются и принудительно применяются PodSecurityPolicy. Если вы не уверены, проконсультируйтесь с коллегами, так как это важный параметр безопасности кластера. Если же вы точно знаете, что в вашем продакшн-кластере PSP не используется, то оставьте `false`, так как включение PSP в этом случае ничего не даст.

*   `serviceAccount.create`: `true`
    *   **Описание:** Создает ServiceAccount для каждого компонента.
    *   **Рекомендация:** Оставить `true`.

*   `imagePullSecrets`:
    *   **Описание:** Позволяет указать секреты для доступа к приватным репозиториям образов.
    *   **Рекомендация:** Использовать, если образы хранятся в приватном реестре.

## Конфигурация Alertmanager

Alertmanager — компонент, отвечающий за обработку и отправку оповещений.

*   `alertmanager.enabled`: `true`
    *   **Рекомендация:** Оставить включенным для управления алертами.

*   `alertmanager.priorityClassName`: `""`
    *   **Описание:** Позволяет задать `PriorityClass` для подов Alertmanager. PriorityClass используется для вытеснения менее важных подов в случае нехватки ресурсов. Например, если в кластере запущены и development, и production окружения, то production поды более важны, и у них PriorityClass будет выше. По умолчанию в кластере существуют PriorityClass для системных компонентов (например, `kube-system`), но для клиентских приложений они обычно не используются.
    *   **Рекомендация:** Использовать, если в кластере активно применяется приоритизация подов (например, для разделения production и development окружений) и вы хотите, чтобы Alertmanager имел определенный приоритет. В противном случае можно оставить пустым.

*   `alertmanager.ingress.enabled`: `false`
    *   **Описание:** Создает Ingress-ресурс для доступа к веб-интерфейсу Alertmanager.
    *   **Рекомендация:** Можно оставить выключенным, так как веб-интерфейс Alertmanager минималистичен и основной интерфейс для работы — это Prometheus и Grafana.

*   `alertmanager.persistentVolume.enabled`: `true`
    *   **Описание:** Включает использование PersistentVolume для сохранения состояния Alertmanager.
    *   **Рекомендация (Production):** Обязательно `true`. Это обеспечивает сохранение данных о подавленных алертах (silences) и другой информации при перезапуске пода, делая его stateful. Режим доступа по умолчанию `ReadWriteOnce`.
    *   `storageClass`: Необходимо указать имя существующего в кластере `StorageClass`. Например: `local-storage`.
    *   `size`: Размер диска подбирается эмпирически. На начальном этапе можно установить `2Gi`, но в дальнейшем необходимо пристально наблюдать за потреблением дискового пространства и корректировать размер по мере необходимости. Ключ для ротации старых метрик будет рассмотрен позже.

*   `alertmanager.replicaCount`: `1`
    *   **Рекомендация (Production):** Установить значение больше `1` (например, `2` или `3`) для обеспечения высокой доступности. Для тестовых стендов достаточно одной реплики.

*   `alertmanager.resources`:
    *   **Описание:** Запросы (requests) и лимиты (limits) по CPU и Memory.
    *   **Рекомендация:** Подбираются эмпирически.
        1.  **Способ 1 (Стартовые значения):** Установить минимальные значения (например, `requests: cpu: 100m, memory: 32Mi; limits: cpu: 200m, memory: 64Mi`), затем активно следить за потреблением ресурсов после запуска системы мониторинга. Если приложение упирается в потолок, постепенно увеличивать ресурсы.
        2.  **Способ 2 (Без лимитов):** Запустить без указания ресурсов, пристально наблюдать и мониторить потребление в течение нескольких дней (например, 7-10 дней). Собрать статистику в разные периоды и на основе средних значений выставить адекватные лимиты и реквесты. Волшебных способов выставления ресурсов не существует, только эмпирический подход.

## Конфигурация `kube-state-metrics`

*   `kube-state-metrics.enabled`: `true`
    *   **Описание:** Включает развертывание `kube-state-metrics`, который генерирует метрики о состоянии объектов Kubernetes (Deployments, Pods, Nodes и т.д.).
    *   **Рекомендация:** Оставить `true`. Это один из ключевых источников метрик о состоянии кластера.

## Конфигурация ConfigMapReload

ConfigMapReload — это вспомогательный компонент, который автоматически перезагружает конфигурацию Prometheus и Alertmanager при изменении соответствующих ConfigMap.

*   `configmapReload.enabled`: `true`
    *   **Описание:** Включает развертывание `configmap-reload` контейнера.
    *   **Рекомендация:** Оставить `true` для автоматической перезагрузки конфигураций без ручного вмешательства.

## Конфигурация Node Exporter

Node Exporter собирает метрики с хостовых машин (узлов Kubernetes).

*   `nodeExporter.enabled`: `true`
    *   **Рекомендация:** Оставить `true` для сбора метрик с нод.

*   `nodeExporter.hostNetwork`: `true`
    *   **Описание:** Позволяет подам Node Exporter использовать сетевой namespace хоста (`hostNetwork: true`) и PID namespace хоста (`hostPID: true`).
    *   **Рекомендация:** Оставить `true` для корректного сбора сетевых метрик и метрик процессов с хоста.

*   `nodeExporter.tolerations`:
    *   **Описание:** Позволяет подам Node Exporter размещаться на master-нодах, которые по умолчанию имеют `taint` (например, `NoSchedule`), запрещающий запуск на них обычных подов.
    *   **Рекомендация:** Добавить `toleration`, чтобы собирать метрики со всех узлов кластера, включая мастеры. Чтобы узнать точный `taint`, можно выполнить `kubectl describe node <master-node-name>`.
        ```yaml
        tolerations:
          - operator: "Exists"
            effect: "NoSchedule"
        ```

*   `nodeExporter.resources`:
    *   **Рекомендация:** Как и для других компонентов, задать минимальные значения и наблюдать.

## Конфигурация Prometheus Server

Это основной компонент системы мониторинга. Общие рекомендации и лучшие практики по работе с Prometheus описаны в документе [PromTool и лучшие практики Prometheus](../promtool_and_best_practices.md). Концептуальное описание конфигурации сервера, включая Service Discovery и `relabel_configs`, можно найти в [Обзоре конфигурации сервера Prometheus](./service_discovery.md).

*   `prometheus.enabled`: `true`
    *   **Рекомендация:** Оставить `true`.

*   `prometheus.prometheusSpec.scrapeInterval`, `scrapeTimeout`, `evaluationInterval`:
    *   `scrapeInterval`: Частота сбора метрик с таргетов. Подбирается эмпирически. Если метрик собирается большой объем, то есть смысл собирать их реже (например, `30s` или `1m`). Если метрик немного, то можно собирать их чаще.
    *   `scrapeTimeout`: Время, по истечении которого Prometheus будет считать, что сбор метрик с таргета не удался.
    *   `evaluationInterval`: Как часто Prometheus должен вычислять правила алертинга. Это значение также подбирается эмпирически. Например, если настроено правило на проверку количества ETCD-узлов (не менее трех), то при уменьшении их числа до двух, сигнал будет передан в AlertManager через указанный `evaluationInterval`.

*   `prometheus.prometheusSpec.remoteWrite`, `remoteRead`:
    *   **Описание:** Настройки для интеграции с внешними долгосрочными хранилищами (например, [VictoriaMetrics](../VictoriaMetrics/victoria_metrics_overview.md), Thanos, M3DB).
    *   **Рекомендация:** Использовать в production для долгосрочного хранения метрик, так как хранение больших объемов данных в самом Prometheus неэффективно и может привести к деградации производительности.
*   `prometheus.ingress.enabled`: `true`
    *   **Описание:** Включает Ingress для доступа к веб-интерфейсу Prometheus.
    *   `hosts`: Необходимо указать DNS-имя для доступа.
        ```yaml
        hosts:
          - prometheus.S4999.edu.slurm.io # Пример DNS-имени, используемого в стендах пользователя
        ```
    *   `annotations`: Можно использовать для автоматического получения TLS-сертификатов от `cert-manager` (например, `cert-manager.io/cluster-issuer: "letsencrypt-prod"`).

*   `prometheus.persistentVolume.enabled`: `true`
    *   **Рекомендация (Production):** Обязательно `true`.
    *   `storageClass`: Указать имя `StorageClass`. Например: `local-storage`.
    *   `size`: Размер подбирается в зависимости от количества метрик и `retention`. Для старта можно использовать `5Gi` (для тестовых целей) или `10Gi` (для более нагруженных сред). В production размер подбирается эмпирически.

*   `prometheus.replicaCount`: `1`
    *   **Рекомендация (Production):** Установить значение больше `1` для высокой доступности.

*   `prometheus.prometheusSpec.retention`: `15d`
    *   **Описание:** Срок хранения метрик в локальном хранилище Prometheus. Метрики старше этого срока будут удалены.
    *   **Рекомендация:** Настраивается эмпирически в зависимости от доступного дискового пространства, требований к хранению и влияния на нагрузку сервера. Если объем метрик слишком велик, и кластер не справляется, следует уменьшить срок хранения. Для долгосрочного хранения используется `remoteWrite`.

*   `prometheus.prometheusSpec.retentionSize`: `""

`    *   **Описание:** (Альфа-версия) Позволяет ограничивать хранилище по размеру (например, `50GB`), а не только по времени.

    *   **Рекомендация:** Использовать с осторожностью, так как это экспериментальная функция.



## Конфигурация Push Gateway



Push Gateway используется для сбора метрик от кратковременных или периодически запускаемых задач, которые не могут быть "собраны" (scraped) Prometheus напрямую.



*   `pushgateway.enabled`: `true`

    *   **Описание:** Включает развертывание Push Gateway.

    *   **Рекомендация:** Оставить `true` по умолчанию, если нет необходимости его отключать. В данном контексте он не используется, но может быть полезен в других сценариях.



## Настройка Persistent Volumes (PV)

Если ваш `StorageClass` не поддерживает динамическое создание томов (dynamic provisioning), вам потребуется создать PersistentVolume вручную. Это актуально, например, при использовании `local-storage`.

**Пример манифеста PV:**
```yaml
apiVersion: v1
kind: PersistentVolume
metadata:
  name: pv-prometheus-1
spec:
  capacity:
    storage: 5Gi
  accessModes:
    - ReadWriteOnce
  storageClassName: local-storage
  local:
    path: /mnt/local-pv-1 # Путь на хостовой машине, который должен существовать
  nodeAffinity:
    required:
      nodeSelectorTerms:
        - matchExpressions:
            - key: kubernetes.io/hostname
              operator: In
              values:
                - node-1 # Имя ноды, на которой будет использоваться PV
```
**Важно:** Перед применением манифеста необходимо убедиться, что директория, указанная в `local.path`, существует на соответствующей ноде. Для каждой ноды, где будет использоваться PV, необходимо создать отдельный PV-манифест, указывающий на уникальный путь и имя ноды. **Не забудьте создать эти директории на целевых узлах кластера перед применением PV-манифестов.**

## Процесс установки

1.  **Скачать чарт локально:**
    ```bash
    helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
    helm repo update
    helm pull prometheus-community/prometheus --untar
    ```
    **Рекомендация:** Всегда работайте с локальной копией чарта. Это позволяет версионировать конфигурацию (`values.yaml`) вместе с кодом вашего приложения и интегрировать развертывание в CI/CD. Установка через CI/CD помогает избежать несоответствий версий и конфигураций, которые могут привести к болезненным проблемам при обновлении.

2.  **Создать PV (при необходимости):**
    ```bash
    kubectl apply -f pv-manifests/
    ```

3.  **Установить чарт:**
    ```bash
    helm install prometheus ./prometheus \
      --namespace monitoring \
      --create-namespace \
      -f values.yaml
    ```
    **Примечание:** Если при установке возникают ошибки, например, из-за пустых списков в `values.yaml` (как в строке 493 в примере), убедитесь, что все списки корректно заполнены или закомментированы. После успешной установки проверьте статус подов (`kubectl get pods -n monitoring`), PV/PVC (`kubectl get pv,pvc -n monitoring`) и Ingress (`kubectl get ingress -n monitoring`).

## Авторизация в веб-интерфейсе

Доступ к веб-интерфейсу Prometheus без аутентификации является проблемой безопасности. Существует несколько подходов к ее решению:

1.  **Через Ingress:** Исторически доступ к интерфейсу Prometheus защищался через Basic Auth на уровне Ingress. Это позволяет настроить окно ввода логина и пароля при доступе к Prometheus через Ingress.
2.  **Закрытый контур:** Не выставлять Prometheus наружу, держать его в закрытых контурах с подключением через VPN. Это наиболее безопасный вариант, но не всегда возможный.
3.  **Нативная авторизация Prometheus:** В новых версиях Prometheus появилась **нативная поддержка Basic Auth**, которую можно настроить непосредственно в конфигурации самого Prometheus. Это более современный и безопасный способ. Также появилась возможность авторизации по TLS-сертификатам. Подробности можно можно найти в `release notes` соответствующей версии Prometheus.
