# Prometheus Operator: Глубокое погружение

Каждый раз, когда вы устанавливаете новый Kubernetes Cluster, вам необходимо развернуть определенный набор программного обеспечения, и система мониторинга входит в этот набор. Современные системы мониторинга, такие как Prometheus, Alertmanager и Grafana, состоят из большого числа компонентов и требуют сложной конфигурации. Prometheus Operator был создан для упрощения работы с этой системой мониторинга как с единым целым. Устанавливая Prometheus Operator, вы получаете Grafana с набором дашбордов, стандартные наборы экспортеров, Prometheus и Alertmanager, а также хороший набор предустановленных настроек.

Прежде чем перейти непосредственно к Prometheus Operator, давайте разберемся, что такое оператор в Kubernetes и как они работают.

## Что такое Оператор в Kubernetes?

Изначально в Kubernetes была возможность создавать только базовые абстракции, такие как Pod, Deployment, Service и т.д. При появлении этих объектов в работу включался `controller-manager`, который знал, что делать с этими объектами и производил соответствующие манипуляции в кластере. Со временем этого стало недостаточно, и была придумана концепция **Custom Resource Definition (CRD)**.

*   **Custom Resource Definition (CRD):** По сути, это расширение кластера Kubernetes, которое дает возможность создавать свои собственные абстракции. CRD описывает, какие поля могут содержаться в данном YAML-файле, какой у него `kind` и т.д. После создания CRD кластер "узнает" о новом типе абстракции.
*   **Custom Resource (CR):** Это экземпляр пользовательской абстракции, созданный на основе CRD.
*   **Оператор:** После создания CRD и соответствующего CR ничего не произойдет, поскольку `controller-manager` ничего не знает, что делать с этими Custom Resources. Для этого необходимо установить в кластере свой собственный `controller-manager`, который называется **Оператор**. По сути, операторы являются теми же `controller-manager`'ами, только работают они с Custom Resource Definition и Custom Resource.

На этой логике построена работа Prometheus Operator.

## Custom Resources Prometheus Operator

Prometheus Operator использует несколько Custom Resources для управления компонентами мониторинга:

### Prometheus

Данный Custom Resource отвечает за то, какие абстракции должны быть созданы в кластере для установки Prometheus-сервера.

### Alertmanager

Аналогичный Custom Resource есть и для Alertmanager.

### ServiceMonitor

Разработчики Prometheus Operator придумали свой собственный механизм обнаружения сервисов (Service Discovery) через Custom Resource, который называется `ServiceMonitor`. В этом CR описывается:
*   За каким сервисом нужно следить.
*   Какие порты должны использоваться в этом сервисе.
*   Дополнительная информация, такая как частота сбора метрик (`scrape interval`) и путь к метрикам (`metrics path`).

**Принцип работы ServiceMonitor:**
1.  Вы создаете `ServiceMonitor` для сервиса (например, `XXX`). Эти данные сохраняются в Kube API Server.
2.  В кластере запущен Pod с Prometheus Operator. Приложение в этом Pod отслеживает появление и изменение объектов типа `ServiceMonitor`.
3.  Как только появляется новый `ServiceMonitor`, Prometheus Operator обновляет `Secret`, в котором содержится конфигурационный файл Prometheus, добавляя туда соответствующие настройки (Endpoints, которые находятся за этим сервисом).
4.  После обновления `Secret` вступает в дело контейнер `prometheus-config-reloader`, запущенный в Pod с Prometheus-сервером.
5.  `prometheus-config-reloader` отслеживает изменения в `Secret` с конфигурационным файлом Prometheus. Как только он видит изменения, он обновляет у себя конфигурационный файл Prometheus и дает команду Prometheus-серверу по HTTP перечитать конфигурационный файл.
6.  Таким образом, поды, связанные с сервисом, добавляются в мониторинг Prometheus.

### PodMonitor

Изначально этого Custom Resource в Prometheus Operator не было. Он был добавлен, поскольку не все поды имеют службы, но их все равно необходимо мониторить. `PodMonitor` позволяет напрямую описывать поды для мониторинга, минуя необходимость создания сервисов.

### Probe

Данный Custom Resource описывает ингрессы и может быть использован для обновления конфигурационных файлов и для мониторинга с использованием, например, Blackbox Exporter.

### PrometheusRule

В этом Custom Resource задаются правила, которые используются в дальнейшем в Prometheus (например, правила записи или правила алертов). Работает по такому же принципу, как и `ServiceMonitor`:
1.  Мы описываем список правил в `PrometheusRule`.
2.  Prometheus Operator отслеживает появление данного Custom Resource.
3.  Генерирует из него `ConfigMap` с определенными аннотациями.
4.  `prometheus-config-reloader` обнаруживает появление нового `ConfigMap`, монтирует его в Pod с Prometheus-сервером и отдает команду Prometheus-серверу перечитать конфигурационные файлы.

### AlertmanagerConfig

Содержит набор правил для Alertmanager и работает по тому же принципу, что и все вышеперечисленные Custom Resources.

## Управление Grafana с Prometheus Operator

Графана работает почти точно так же, как и другие компоненты, но есть небольшой нюанс. Для загрузки новых дашбордов или источников данных (datasources) в Grafana нет специального Custom Resource, но зато используются `ConfigMap`'ы.

**Принцип работы с Grafana:**
1.  Мы создаем `ConfigMap` с определенными аннотациями, содержащий дашборды или источники данных.
2.  В Pod с Grafana есть два служебных контейнера: `grafana-datasource-reloader` и `grafana-dashboard-reloader`.
3.  Эти контейнеры отслеживают появление `ConfigMap`'ов с определенными аннотациями.
4.  Если такие `ConfigMap`'ы появляются, они монтируют их в Pod с Grafana и отдают команду Grafana о том, что ей нужно перечитать конфигурационные файлы, список дашбордов или список источников данных.

## Важные аспекты при работе с Prometheus, Alertmanager и Grafana

### Prometheus

*   **Высокая доступность:** Prometheus, как правило, устанавливается в кластер как `StatefulSet`. У `StatefulSet`'ов есть определенная особенность: если выходит из строя нода, на которой запущен `StatefulSet`, он не перезапускается на других нодах даже по истечении `eviction-timeout`. Поэтому, чтобы гарантировать минимальную доступность Prometheus, его необходимо устанавливать минимум в две копии.
*   **Аутентификация:** Prometheus не имел встроенной аутентификации в ранних версиях, но в последних версиях она появилась, и ее нужно использовать. В более ранних версиях использовалось сочетание Basic-аутентификации на Ingress плюс Network Policy, чтобы ограничить доступ к Prometheus внутри кластера. Это делается с одной простой целью: если злоумышленник получит доступ к одному из ваших подов, он сможет напрямую обратиться к Prometheus-серверу. В нем содержится огромное количество информации, которая существенно упростит жизнь злоумышленнику и подскажет, что и как можно атаковать. В частности, из Prometheus можно получить версию Kubernetes, что позволит поискать уже известные уязвимости для данной версии.
*   **Retention Size:** У Prometheus в Kubernetes-кластере есть настройка, которая позволяет ограничить количество хранимых данных. Мы можем ограничивать Prometheus не только по тому, как долго он хранит данные, но и по размеру. Это очень важно по двум причинам:
    1.  Prometheus может устанавливаться с `emptyDir`, то есть по сути он будет писать на физическую ноду. Если не ограничить размер, то в какой-то момент из-за ошибки разработчиков мы можем увидеть резкий скачок по размеру данных, и у Prometheus просто закончится свободное место.
    2.  Даже когда никто нигде не ошибся, данных просто может стать больше, и в какой-то момент Persistent Volume, который используется в Prometheus, закончится, и мы останемся без системы мониторинга. Данная настройка позволяет избежать подобных ситуаций.

### Alertmanager

*   **Высокая доступность:** Alertmanager также запускается как `StatefulSet`. Идея ровно такая же, как и для Prometheus. Единственное отличие: его нужно запускать минимум в 3 копии, потому что Alertmanager умеет собираться самостоятельно в кластер, обмениваться данными для дедупликации уведомлений, и ему требуется большинство (кворум), поэтому 3 копии.
*   **Аутентификация:** Для Alertmanager все то же самое, что и с Prometheus: не надо никого пускать туда, куда ему не надо ходить.

### Grafana

*   **Управление дашбордами:** Когда мы устанавливаем Grafana из Prometheus Operator, там есть некий набор предустановленных дашбордов. Они удобны и покрывают на старте 99% потребностей. При этом механизм загрузки этих дашбордов в Grafana заключается в том, что они подтягиваются с сайта Grafana по ID. В любой момент эти дашборды могут поменяться. И при перезапуске Pod с Grafana мы увидим совершенно другие дашборды в нашем веб-интерфейсе, что не очень хорошо.
*   **Хранение дашбордов:** Дашборды, которые рисуются под наши приложения и нужды, мы применяем в качестве `ConfigMap`'ов. Если что-то происходит или меняется, они могут быть потеряны. Поэтому единственным правильным решением является хранение всех дашбордов в Git (например, GitLab) и применение их отдельно в виде `ConfigMap`.

На практике Prometheus Operator часто устанавливается с помощью Helm-чартов, что позволяет гибко настраивать его использование.
