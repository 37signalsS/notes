# Prometheus Operator

**Prometheus Operator** был создан для упрощения управления стеком [[../overview.md|Prometheus]], [[../alertmanager.md|Alertmanager]] и [[../../Grafana/grafana_overview.md|Grafana]] как единым целым. Он является ядром популярного Helm-чарта `kube-prometheus-stack`. Устанавливая его, вы получаете не просто Prometheus, а целую экосистему: Grafana с набором дашбордов, стандартные [[../exporters.md|экспортеры]], Alertmanager и, что самое главное, мощный механизм для декларативного управления конфигурацией.

## 1. Определения

В основе Prometheus Operator лежит концепция **Оператора Kubernetes**. Вкратце, оператор — это специализированный контроллер, который использует [[../../Kubernetes/Concepts/kubernetes_operators.md#2.1.-Custom-Resource-Definitions-(CRD)|пользовательские ресурсы (Custom Resources)]] для управления приложениями и их компонентами. Он автоматизирует задачи, которые обычно требуют вмешательства человека.

Prometheus Operator следит за появлением и изменением "своих" кастомных ресурсов и автоматически преобразует их в реальные объекты кластера: [[../../Kubernetes/Base/statefulset.md|StatefulSet'ы]] для Prometheus, [[../../Kubernetes/Base/configmap.md|ConfigMap'ы]] с конфигурацией, [[../../Kubernetes/Base/secret.md|Secret'ы]] и т.д.

> Подробное описание концепции, её назначения и принципов работы находится в основной заметке: **[[../../Kubernetes/Concepts/kubernetes_operators.md|Kubernetes Операторы]]**.

## 2. Основные концепции: архитектура и Custom Resources

Prometheus Operator расширяет API Kubernetes набором специализированных CRD для декларативного управления всеми компонентами стека мониторинга.

### Prometheus

Данный Custom Resource (`kind: Prometheus`) отвечает за развертывание и конфигурацию самого Prometheus-сервера. Оператор, видя этот ресурс, создает соответствующий `StatefulSet`, `Service`, `ConfigMap`'ы и другие необходимые объекты.

### Alertmanager

Аналогичный Custom Resource (`kind: Alertmanager`) используется для управления экземплярами [[../alertmanager.md|Alertmanager]].

### ServiceMonitor

Это один из самых важных CRD. `ServiceMonitor` позволяет декларативно описать, как Prometheus должен обнаруживать и собирать метрики с группы подов, объединенных одним [[../../Kubernetes/Networking/service.md|сервисом (Service)]]. Более подробно механика обнаружения сервисов, включая сравнение с нативным подходом, описана в заметке о [[../service_discovery.md|Service Discovery в Kubernetes]].

*   **Как это работает:**
    1.  Вы создаете `ServiceMonitor`, в котором с помощью `selector`'а указываете, за сервисами с какими лейблами нужно следить.
    2.  Prometheus Operator обнаруживает этот `ServiceMonitor`.
    3.  Он **не** направляет Prometheus на ClusterIP сервиса. Вместо этого он обращается к API Kubernetes, находит `Endpoints` объекта `Service` и получает реальные IP-адреса всех подов, стоящих за этим сервисом.
    4.  Оператор генерирует соответствующую конфигурацию (`scrape_config`) и обновляет `Secret`, в котором хранится полный конфигурационный файл Prometheus (`prometheus.yml`).
    5.  Внутри пода Prometheus работает специальный контейнер `prometheus-config-reloader`. Он замечает, что `Secret` с конфигурацией изменился.
    6.  `config-reloader` обновляет файл на диске внутри пода и отправляет Prometheus-серверу HTTP-запрос на перезагрузку конфигурации.
    7.  Prometheus перечитывает конфиг и начинает опрашивать новые цели.

Этот механизм позволяет автоматически мониторить сервисы, просто добавив им нужный лейбл и создав `ServiceMonitor`.

### PodMonitor

Аналогичен `ServiceMonitor`, но был добавлен позже. Позволяет мониторить поды напрямую по их лейблам, без необходимости объединять их `Service`'ом. Это полезно для подов, которые не предоставляют сетевой сервис, но экспортируют метрики. Хорошим примером использования является автоматический сбор метрик с баз данных, как описано в заметке о [[../../Databases/PostgreSQL/Operations/kubernetes_deployment.md#включение-мониторинга-для-prometheus-operator|развертывании PostgreSQL в Kubernetes]].

### Probe

Данный Custom Resource (`kind: Probe`) используется для мониторинга "черным ящиком" (blackbox monitoring) с помощью **[[../exporters.md#blackbox_exporter|Blackbox Exporter]]**.
В `Probe` вы описываете цель (например, `google.com`) и модуль проверки (например, `http_2xx`). Prometheus Operator на основе этого генерирует конфигурацию, чтобы Prometheus опрашивал не саму цель, а Blackbox Exporter, передавая ему цель как параметр.

### PrometheusRule

Этот CRD позволяет декларативно управлять [[../rules.md|правилами записи (recording rules) и оповещений (alerting rules)]].

*   **Принцип работы:**
    1.  Вы описываете правила в манифесте `kind: PrometheusRule`.
    2.  Prometheus Operator отслеживает этот ресурс.
    3.  Он генерирует из него `ConfigMap`, содержащий файлы с правилами.
    4.  `prometheus-config-reloader` обнаруживает этот `ConfigMap`, монтирует его в под Prometheus и отдает команду на перезагрузку правил.

### AlertmanagerConfig
Данный CRD предоставляет способ декларативно настраивать маршрутизацию и получателей для [[../alertmanager.md|Alertmanager]], являясь альтернативой управлению конфигурацией через один центральный `Secret`.

## 3. Практические сценарии и применение

### Управление Grafana

Для [[../../Grafana/grafana_overview.md|Grafana]] нет специального CRD, но используется похожий механизм на основе [[../../Kubernetes/Base/configmap.md|ConfigMap'ов]] с определенными лейблами/аннотациями, что является примером [[../../Grafana/grafana_provisioning.md|провижининга]].

*   **Принцип работы:**
    1.  Вы создаете `ConfigMap`, содержащий JSON-модель дашборда или конфигурацию источника данных.
    2.  В поде с Grafana работают служебные [[../../Kubernetes/Base/pod.md#паттерн-сайдкар-sidecar|контейнеры-сайдкары]] (например, `grafana-dashboard-reloader`).
    3.  Эти сайдкары отслеживают появление `ConfigMap`'ов с нужными аннотациями.
    4.  При их обнаружении они монтируют содержимое в Grafana и дают ей команду перечитать конфигурацию.

### Полезные метрики и рекомендации

*   **Примеры полезных метрик:**
    *   `kube_deployment_status_replicas_unavailable`: Отслеживает количество недоступных реплик для деплойментов. Значение больше нуля может указывать на проблемы.
    *   `kube_node_status_capacity_memory_bytes`: Показывает общую емкость памяти для каждой ноды.
    *   `kube_pod_container_status_restart_total`: Суммарное количество перезапусков контейнера. Постоянный рост указывает на нестабильность приложения.
    *   `kube_pod_container_status_ready`: Показывает готовность контейнера (1 - готов, 0 - нет). Позволяет быстро выявлять неработоспособные поды.
*   **Рекомендации:**
    *   **Избирательный подход:** Сосредоточьтесь на сборе только тех метрик, которые действительно необходимы для мониторинга и алертинга.
    *   **Оптимизация:** При установке `kube-state-metrics` можно исключить сбор ненужных метрик, чтобы снизить нагрузку на Prometheus и API-сервер.

## 4. Продвинутые детали: высокая доступность и безопасность

### Prometheus

*   **Высокая доступность:** Prometheus, как правило, устанавливается в кластер как [[../../Kubernetes/Base/statefulset.md|StatefulSet]]. У `StatefulSet`'ов есть определенная особенность: если выходит из строя нода, на которой запущен `StatefulSet`, он не перезапускается на других нодах даже по истечении `eviction-timeout`. Поэтому, чтобы гарантировать минимальную доступность Prometheus, его необходимо устанавливать минимум в две копии.
*   **Аутентификация:** Prometheus не имел встроенной аутентификации в ранних версиях, но в последних версиях она появилась, и ее нужно использовать. В более ранних версиях использовалось сочетание Basic-аутентификации на [[../../Kubernetes/Networking/ingress.md|Ingress]] плюс Network Policy, чтобы ограничить доступ к Prometheus внутри кластера. Это делается с одной простой целью: если злоумышленник получит доступ к одному из ваших подов, он сможет напрямую обратиться к Prometheus-серверу. В нем содержится огромное количество информации, которая существенно упростит жизнь злоумышленнику и подскажет, что и как можно атаковать. В частности, из Prometheus можно получить версию Kubernetes, что позволит поискать уже известные уязвимости для данной версии.
*   **Retention Size:** У Prometheus в Kubernetes-кластере есть настройка, которая позволяет ограничить количество хранимых данных. Мы можем ограничивать Prometheus не только по тому, как долго он хранит данные, но и по размеру. Это очень важно по двум причинам:
    1.  Prometheus может устанавливаться с [[../../Kubernetes/Base/pod.md#основные-типы-томов|emptyDir]], то есть по сути он будет писать на физическую ноду. Если не ограничить размер, то в какой-то момент из-за ошибки разработчиков мы можем увидеть резкий скачок по размеру данных, и у Prometheus просто закончится свободное место.
    2.  Даже когда никто нигде не ошибся, данных просто может стать больше, и в какой-то момент [[../../Kubernetes/Storage/pv_and_pvc.md|Persistent Volume]], который используется в Prometheus, закончится, и мы останемся без системы мониторинга. Данная настройка позволяет избежать подобных ситуаций.

### Alertmanager

*   **Высокая доступность:** Alertmanager также запускается как `StatefulSet`. Идея ровно такая же, как и для Prometheus. Единственное отличие: его нужно запускать минимум в 3 копии, потому что Alertmanager умеет собираться самостоятельно в кластер, обмениваться данными для дедупликации уведомлений, и ему требуется большинство (кворум), поэтому 3 копии. Детальнее см. [[../alertmanager.md#4.-продвинутые-детали-высокая-доступность-high-availability|Alertmanager HA]].
*   **Аутентификация:** Для Alertmanager все то же самое, что и с Prometheus: не надо никого пускать туда, куда ему не надо ходить.

### Grafana

*   **Управление дашбордами:** Когда мы устанавливаем Grafana из Prometheus Operator, там есть некий набор предустановленных дашбордов. Они удобны и покрывают на старте 99% потребностей. При этом механизм загрузки этих дашбордов в Grafana заключается в том, что они подтягиваются с сайта Grafana по ID. В любой момент эти дашборды могут поменяться. И при перезапуске Pod с Grafana мы увидим совершенно другие дашборды в нашем веб-интерфейсе, что не очень хорошо.
*   **Хранение дашбордов:** Дашборды, которые рисуются под наши приложения и нужды, мы применяем в качестве `ConfigMap`'ов. Если что-то происходит или меняется, они могут быть потеряны. Поэтому единственным правильным решением является хранение всех [[../../Grafana/grafana_dashboards.md|дашбордов в Git]] (например, GitLab) и применение их отдельно в виде `ConfigMap`. См. также [[../../Git/git_workflows.md|рабочие процессы в Git]].
