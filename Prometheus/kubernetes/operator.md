# Prometheus Operator: Глубокое погружение

Каждый раз, когда вы устанавливаете новый Kubernetes Cluster, вам необходимо развернуть определенный набор программного обеспечения, и система мониторинга входит в этот набор. Современные системы мониторинга, такие как Prometheus, Alertmanager и Grafana, состоят из большого числа компонентов и требуют сложной конфигурации.

**Prometheus Operator** был создан для упрощения управления этим стеком как единым целым. Он является ядром популярного Helm-чарта `kube-prometheus-stack`. Устанавливая его, вы получаете не просто Prometheus, а целую экосистему: Grafana с набором дашбордов, стандартные экспортеры, Alertmanager и, что самое главное, мощный механизм для декларативного управления конфигурацией.

Прежде чем перейти непосредственно к Prometheus Operator, давайте разберемся, что такое оператор в Kubernetes и как они работают.

## Что такое Оператор в Kubernetes?

Изначально в Kubernetes была возможность создавать только базовые абстракции, такие как Pod, Deployment, Service и т.д. При появлении этих объектов в работу включался `controller-manager`, который знал, что делать с этими объектами и производил соответствующие манипуляции в кластере. Со временем этого стало недостаточно, и была придумана концепция **Custom Resource Definition (CRD)**.

*   **Custom Resource Definition (CRD):** По сути, это расширение API-сервера Kubernetes, которое дает возможность создавать свои собственные абстракции. CRD описывает, какие поля могут содержаться в данном YAML-файле, какой у него `kind` и т.д. После создания CRD кластер "узнает" о новом типе абстракции.
*   **Custom Resource (CR):** Это экземпляр пользовательской абстракции, созданный на основе CRD.
*   **Оператор:** После создания CRD и соответствующего CR ничего не произойдет, поскольку `controller-manager` ничего не знает, что делать с этими Custom Resources. Для этого необходимо установить в кластере свой собственный `controller-manager`, который называется **Оператор**. По сути, операторы являются теми же `controller-manager`'ами, только работают они с кастомными, а не встроенными ресурсами.

На этой логике построена работа Prometheus Operator. Он следит за появлением и изменением "своих" кастомных ресурсов и автоматически преобразует их в реальные объекты кластера: `StatefulSet`'ы для Prometheus, `ConfigMap`'ы с конфигурацией, `Secret`'ы и т.д.

## Custom Resources Prometheus Operator

Prometheus Operator использует несколько Custom Resources для декларативного управления компонентами мониторинга.

### Prometheus

Данный Custom Resource (`kind: Prometheus`) отвечает за развертывание и конфигурацию самого Prometheus-сервера. Оператор, видя этот ресурс, создает соответствующий `StatefulSet`, `Service`, `ConfigMap`'ы и другие необходимые объекты.

### Alertmanager

Аналогичный Custom Resource (`kind: Alertmanager`) используется для управления экземплярами Alertmanager.

### ServiceMonitor

Это один из самых важных CRD. `ServiceMonitor` позволяет декларативно описать, как Prometheus должен обнаруживать и собирать метрики с группы подов.

*   **Как это работает:**
    1.  Вы создаете `ServiceMonitor`, в котором с помощью `selector`'а указываете, за сервисами с какими лейблами нужно следить.
    2.  Prometheus Operator обнаруживает этот `ServiceMonitor`.
    3.  Он **не** направляет Prometheus на ClusterIP сервиса. Вместо этого он обращается к API Kubernetes, находит `Endpoints` объекта `Service` и получает реальные IP-адреса всех подов, стоящих за этим сервисом.
    4.  Оператор генерирует соответствующую конфигурацию (`scrape_config`) и обновляет `Secret`, в котором хранится полный конфигурационный файл Prometheus (`prometheus.yml`).
    5.  Внутри пода Prometheus работает специальный контейнер `prometheus-config-reloader`. Он замечает, что `Secret` с конфигурацией изменился.
    6.  `config-reloader` обновляет файл на диске внутри пода и отправляет Prometheus-серверу HTTP-запрос на перезагрузку конфигурации.
    7.  Prometheus перечитывает конфиг и начинает опрашивать новые цели.

Этот механизм позволяет автоматически мониторить сервисы, просто добавив им нужный лейбл и создав `ServiceMonitor`.

### PodMonitor

Аналогичен `ServiceMonitor`, но был добавлен позже. Позволяет мониторить поды напрямую по их лейблам, без необходимости объединять их `Service`'ом. Это полезно для подов, которые не предоставляют сетевой сервис, но экспортируют метрики.

### Probe

Данный Custom Resource (`kind: Probe`) используется для мониторинга "черным ящиком" (blackbox monitoring) с помощью **Blackbox Exporter**.
В `Probe` вы описываете цель (например, `google.com`) и модуль проверки (например, `http_2xx`). Prometheus Operator на основе этого генерирует конфигурацию, чтобы Prometheus опрашивал не саму цель, а Blackbox Exporter, передавая ему цель как параметр.

### PrometheusRule

Этот CRD позволяет декларативно управлять правилами записи (recording rules) и оповещений (alerting rules).

*   **Принцип работы:**
    1.  Вы описываете правила в манифесте `kind: PrometheusRule`.
    2.  Prometheus Operator отслеживает этот ресурс.
    3.  Он генерирует из него `ConfigMap`, содержащий файлы с правилами.
    4.  `prometheus-config-reloader` обнаруживает этот `ConfigMap`, монтирует его в под Prometheus и отдает команду на перезагрузку правил.

### AlertmanagerConfig

Содержит набор правил маршрутизации для Alertmanager и работает по тому же принципу, что и все вышеперечисленные Custom Resources.

## Управление Grafana

Для Grafana нет специального CRD, но используется похожий механизм на основе `ConfigMap`'ов с определенными лейблами/аннотациями.

*   **Принцип работы:**
    1.  Вы создаете `ConfigMap`, содержащий JSON-модель дашборда или конфигурацию источника данных.
    2.  В поде с Grafana работают служебные контейнеры-сайдкары (например, `grafana-dashboard-reloader`).
    3.  Эти сайдкары отслеживают появление `ConfigMap`'ов с нужными аннотациями.
    4.  При их обнаружении они монтируют содержимое в Grafana и дают ей команду перечитать конфигурацию.

## Важные аспекты при работе с Prometheus, Alertmanager и Grafana

### Prometheus

*   **Высокая доступность:** Prometheus, как правило, устанавливается в кластер как `StatefulSet`. У `StatefulSet`'ов есть определенная особенность: если выходит из строя нода, на которой запущен `StatefulSet`, он не перезапускается на других нодах даже по истечении `eviction-timeout`. Поэтому, чтобы гарантировать минимальную доступность Prometheus, его необходимо устанавливать минимум в две копии.
*   **Аутентификация:** Prometheus не имел встроенной аутентификации в ранних версиях, но в последних версиях она появилась, и ее нужно использовать. В более ранних версиях использовалось сочетание Basic-аутентификации на Ingress плюс Network Policy, чтобы ограничить доступ к Prometheus внутри кластера. Это делается с одной простой целью: если злоумышленник получит доступ к одному из ваших подов, он сможет напрямую обратиться к Prometheus-серверу. В нем содержится огромное количество информации, которая существенно упростит жизнь злоумышленнику и подскажет, что и как можно атаковать. В частности, из Prometheus можно получить версию Kubernetes, что позволит поискать уже известные уязвимости для данной версии.
*   **Retention Size:** У Prometheus в Kubernetes-кластере есть настройка, которая позволяет ограничить количество хранимых данных. Мы можем ограничивать Prometheus не только по тому, как долго он хранит данные, но и по размеру. Это очень важно по двум причинам:
    1.  Prometheus может устанавливаться с `emptyDir`, то есть по сути он будет писать на физическую ноду. Если не ограничить размер, то в какой-то момент из-за ошибки разработчиков мы можем увидеть резкий скачок по размеру данных, и у Prometheus просто закончится свободное место.
    2.  Даже когда никто нигде не ошибся, данных просто может стать больше, и в какой-то момент Persistent Volume, который используется в Prometheus, закончится, и мы останемся без системы мониторинга. Данная настройка позволяет избежать подобных ситуаций.

### Alertmanager

*   **Высокая доступность:** Alertmanager также запускается как `StatefulSet`. Идея ровно такая же, как и для Prometheus. Единственное отличие: его нужно запускать минимум в 3 копии, потому что Alertmanager умеет собираться самостоятельно в кластер, обмениваться данными для дедупликации уведомлений, и ему требуется большинство (кворум), поэтому 3 копии.
*   **Аутентификация:** Для Alertmanager все то же самое, что и с Prometheus: не надо никого пускать туда, куда ему не надо ходить.

### Grafana

*   **Управление дашбордами:** Когда мы устанавливаем Grafana из Prometheus Operator, там есть некий набор предустановленных дашбордов. Они удобны и покрывают на старте 99% потребностей. При этом механизм загрузки этих дашбордов в Grafana заключается в том, что они подтягиваются с сайта Grafana по ID. В любой момент эти дашборды могут поменяться. И при перезапуске Pod с Grafana мы увидим совершенно другие дашборды в нашем веб-интерфейсе, что не очень хорошо.
*   **Хранение дашбордов:** Дашборды, которые рисуются под наши приложения и нужды, мы применяем в качестве `ConfigMap`'ов. Если что-то происходит или меняется, они могут быть потеряны. Поэтому единственным правильным решением является хранение всех дашбордов в Git (например, GitLab) и применение их отдельно в виде `ConfigMap`.

На практике Prometheus Operator чаще всего устанавливается с помощью Helm-чарта `kube-prometheus-stack`, что позволяет гибко настраивать его использование.
