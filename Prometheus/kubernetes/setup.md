# Установка Prometheus в Kubernetes

В данном документе описывается процесс установки "ванильной" версии Prometheus в кластер Kubernetes с использованием Helm, а также настройка `kube-state-metrics` для сбора метрик состояния кластера.

## Обзор установки Prometheus

Все концепции, рассмотренные ранее, справедливы и для Kubernetes, но существуют важные нюансы.

*   **Персистентность данных:** По умолчанию поды в Kubernetes не сохраняют свое состояние. Чтобы данные Prometheus не терялись при перезапуске пода, необходимо использовать `PersistentVolumes`.
*   **Service Discovery:** Хотя у Prometheus есть встроенный механизм service discovery для Kubernetes, его возможности могут быть ограничены для сложных сценариев.

По этим причинам для развертывания в production-среде рекомендуется использовать **Prometheus Operator**.

### Prometheus Operator

**Prometheus Operator** [Prometheus Operator](./operator.md) — это сторонний open-source проект, построенный на базе паттерна "оператор" в Kubernetes. Операторы — это специальные контроллеры, которые расширяют API Kubernetes, позволяя управлять сложными приложениями через нативные для Kubernetes ресурсы (CRD).

Prometheus Operator постоянно отслеживает изменения в API кластера и автоматически обновляет конфигурацию Prometheus, избавляя от ручного вмешательства.

**Преимущества установки через Prometheus Operator (обычно с помощью Helm-чарта `kube-prometheus-stack`):**
*   **Комплексная установка:** Устанавливаются все основные компоненты: Prometheus, Alertmanager, Grafana и необходимые экспортеры.
*   **Автоматизация:** Конфигурация Prometheus генерируется и обновляется автоматически на основе состояния кластера.
*   **Готовые алерты:** В комплекте идет набор базовых правил алертинга, покрывающих основные потребности мониторинга кластера.

### Подходы к установке

1.  **Prometheus Operator (Рекомендуемый):** Более продвинутый и автоматизированный способ, использующий кастомные ресурсы (CRD) для управления стеком мониторинга. Это стандарт де-факто для production-инсталляций.
2.  **"Ванильная" установка (без оператора):** Прямая установка Prometheus с использованием стандартных манифестов или Helm-чартов. Этот подход более "ручной", но позволяет глубже понять внутреннюю конфигурацию Prometheus.

Мы будем устанавливать Prometheus через Helm, что позволит нам изучить структуру чарта, его `values.yaml` и основные параметры конфигурации.

## Установка Prometheus с помощью Helm

Процесс установки включает в себя скачивание Helm-чарта Prometheus, его настройку через `values.yaml` и развертывание в кластере.

### 1. Подготовка Helm-чарта

**Важное замечание:** Исторически Prometheus-чарты могли находиться в репозитории `stable` Helm, однако этот репозиторий **устарел** и больше не поддерживается для Prometheus. Для установки актуальных версий Prometheus следует использовать официальный репозиторий Prometheus Community.

Сначала необходимо получить Helm-чарт Prometheus. Вы можете скачать его и изучить его структуру:

```bash
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm pull prometheus-community/prometheus --untar
```

После распаковки чарта вы сможете изучить его файлы, включая `Chart.yaml`, `values.yaml` и директорию `templates/`. Особое внимание следует уделить `values.yaml`, так как через него осуществляется основная настройка Prometheus.

### 2. Настройка `values.yaml`

В файле `values.yaml` вы можете настроить различные аспекты Prometheus, такие как:

*   Количество реплик
*   Конфигурация хранилища (TSDB)
*   Правила сбора метрик (scrape_configs)
*   Интеграция с Alertmanager
*   Настройки сетевого доступа (Service, Ingress)

Для "ванильной" установки важно понимать, как конфигурируются `scrape_configs` для обнаружения целей мониторинга. Подробное описание конфигурации сервера Prometheus, включая Service Discovery и `relabel_configs`, можно найти в документе [Обзор конфигурации сервера Prometheus](./service_discovery.md). Практическое руководство по настройке `values.yaml` для Helm-чарта представлено в [Детальная настройка Helm-чарта Prometheus](./helm_chart_configuration.md).

### 3. Развертывание Prometheus

После настройки `values.yaml` вы можете развернуть Prometheus в вашем кластере Kubernetes:

```bash
helm install my-prometheus prometheus-community/prometheus -f my-values.yaml --namespace monitoring --create-namespace
```

Где `my-prometheus` — это имя вашего релиза, а `my-values.yaml` — ваш настроенный файл `values.yaml`.

### 4. Проверка установки

После установки убедитесь, что все компоненты Prometheus запущены и работают корректно. Вы можете проверить поды, сервисы и другие ресурсы в пространстве имен `monitoring`.

## Мониторинг состояния кластера с `kube-state-metrics`

`kube-state-metrics` — это специализированный экспортер, который слушает Kubernetes API и генерирует метрики о состоянии объектов Kubernetes, таких как поды, деплойменты, ноды, PersistentVolumes и т.д. Эти метрики предоставляют ценную информацию о здоровье и производительности кластера.

### Установка `kube-state-metrics`

`kube-state-metrics` часто устанавливается как часть общего Helm-чарта Prometheus или как отдельный чарт.

```bash
helm install kube-state-metrics prometheus-community/kube-state-metrics --namespace monitoring
```

### Использование метрик `kube-state-metrics`

После установки Prometheus будет автоматически обнаруживать и собирать метрики с `kube-state-metrics`. Вы сможете использовать эти метрики в Grafana для построения дашбордов или в Alertmanager для настройки оповещений о состоянии кластера.

`kube-state-metrics` предоставляет обширный набор метрик, позволяющих получить глубокое представление о состоянии кластера Kubernetes. Ниже приведены примеры наиболее полезных метрик и сценарии их использования:

*   **`kube_deployment_status_replicas_unavailable`**: Эта метрика отслеживает количество недоступных реплик для деплойментов. Значение больше нуля может указывать на проблемы с деплойментом, требующие внимания. Например, если все реплики находятся в состоянии `Ready`, значение метрики будет `0`.
    *   *Пример использования:* Настройка алерта, срабатывающего, если `kube_deployment_status_replicas_unavailable > 0` для критически важных приложений. Рекомендуется уточнять это правило, добавляя метки для конкретных бизнес-критичных деплойментов.

*   **`kube_node_status_capacity_memory_bytes`**: Показывает общую емкость памяти (в байтах) для каждой ноды. Полезна для мониторинга доступных ресурсов кластера и планирования нагрузки. Метрика включает метку `node`, что позволяет различать ноды.
    *   *Пример использования:* Для преобразования значения в килобайты можно использовать выражение `kube_node_status_capacity_memory_bytes / 1024`. Это можно проверить с помощью вывода `kubectl describe node <node-name>`. Аналогичные метрики доступны для CPU (`kube_node_status_capacity_cpu_cores`) и дискового пространства. Это позволяет эффективно управлять ресурсами на уровне нод.

*   **`kube_pod_container_status_restart_total`**: Суммарное количество перезапусков контейнера пода. Высокое или постоянно растущее значение указывает на нестабильность приложения.
    *   *Пример использования:* Хотя простой запрос `kube_pod_container_status_restart_total > 0` может показать поды, которые перезапускались, более эффективным будет алерт `sum(rate(kube_pod_container_status_restart_total[30m])) by (pod, namespace) > 2`. Этот алерт сработает, если под перезапускался более двух раз в течение 30 минут, помогая выявлять такие проблемы, как утечки памяти, приводящие к каскадным перезапускам.

*   **`kube_pod_container_status_ready`**: Метрика, показывающая готовность контейнера пода (1, если готов; 0, если нет). Позволяет быстро выявлять неработоспособные поды.
    *   *Пример использования:* Запрос `kube_pod_container_status_ready == 0` покажет поды, которые не находятся в состоянии "Ready". Это критически важно для обнаружения подов, застрявших в состоянии `Pending` или других нездоровых состояниях, что позволяет оперативно реагировать.

### Важность выбора метрик

`kube-state-metrics`, как и другие экспортеры, собирает большое количество метрик. Однако сбор всех доступных метрик может привести к значительному потреблению ресурсов Prometheus и увеличению нагрузки на API-сервер Kubernetes.

**Рекомендации:**

*   **Избирательный подход:** Сосредоточьтесь на сборе только тех метрик, которые действительно необходимы для мониторинга здоровья, производительности и алертинга ваших приложений и инфраструктуры.
*   **Оптимизация конфигурации:** При установке `kube-state-metrics` через Helm или при настройке Prometheus можно исключить сбор ненужных метрик, чтобы снизить нагрузку.
*   **Регулярный аудит:** Периодически пересматривайте собираемые метрики и удаляйте те, которые больше не используются или не приносят ценности.
