# Обзор лекции: Prometheus как новый виток систем мониторинга (сравнение с Zabbix, ELK)

Данная заметка суммирует ключевые аспекты и практические моменты из лекции "Prometheus как новый виток систем мониторинга и логирования", охватывая его историю, архитектурные особенности, сравнение с традиционными системами мониторинга (Zabbix) и практические демонстрации.

## 1. История и философия Prometheus

*   **Происхождение:** Разработан в Google (под названием Borgmon) как система мониторинга для их контейнерного оркестратора Borg (предшественник Kubernetes).
*   **Open Source:** Передан в CNCF (Cloud Native Computing Foundation) — инициативу по разработке и поддержке облачных приложений. Впервые реализован в SoundCloud в 2019 году.
*   **CNCF Landscape:** Prometheus является частью обширной экосистемы CNCF, включающей Kubernetes, Helm, CoreDNS и многие другие проекты, ориентированные на облачную разработку.

## 2. Whitebox vs Blackbox Мониторинг

Prometheus преимущественно ориентирован на **Whitebox Monitoring**, но поддерживает и Blackbox.

*   **Whitebox Monitoring:**
    *   Мониторинг внутренних механизмов системы, когда мы точно знаем, как она работает, какие метрики отдает и как их анализировать.
    *   Prometheus ориентирован на этот подход, так как он умеет собирать, хранить и анализировать огромное количество метрик, глубоко понимая их формат и логику. Это отличает его от старых систем типа Zabbix, которые чаще выполняли простые проверки.
*   **Blackbox Monitoring:**
    *   Мониторинг сервиса как "черного ящика", когда нам доступны только внешние параметры (например, IP-адрес и порт).
    *   Позволяет проверить доступность сервиса (например, TCP-чек) без глубокого знания его внутренней структуры.
    *   Реализуется с помощью **Blackbox Exporter**, который опрашивает внешний ресурс и предоставляет его статус в формате Prometheus.

## 3. Pull vs Push Модель сбора метрик

Prometheus преимущественно использует **Pull-модель**.

*   **Pull-модель (Prometheus):**
    *   Система мониторинга (Prometheus) сама активно забирает метрики из сервисов по HTTP.
    *   **Преимущества:** Централизованный контроль, простота настройки экспортеров (они лишь отдают метрики), обнаружение неработающих инстансов. В отличие от Push-модели, Pull-архитектура легко масштабируется: при росте числа сервисов можно добавить больше экземпляров Prometheus, которые будут опрашивать свою часть сервисов, а данные агрегировать в общем хранилище.
    *   В современных средах (Kubernetes, Consul) Prometheus может использовать Service Discovery для динамического обнаружения эндпоинтов приложений.
*   **Push-модель (Zabbix, традиционный подход):**
    *   Сервисы сами отправляют свои метрики в систему мониторинга.
    *   **Недостатки:** Создает высокую нагрузку на сервер мониторинга и плохо масштабируется. Когда тысячи серверов одновременно отправляют метрики, центральный узел (например, Zabbix-сервер) становится узким местом.
*   **Комбинированная модель (Pushgateway):**
    *   Для кратковременных задач (batch jobs) или сервисов, которые не могут быть опрошены напрямую, используется **Pushgateway**. Приложение отправляет метрики в Pushgateway, а Prometheus уже забирает их оттуда по Pull-модели.

## 4. Внутреннее устройство Prometheus TSDB

Prometheus использует собственную базу данных временных рядов (Time Series Database, TSDB).

*   **Отличие от реляционных БД:** TSDB хранит временные метки и их значения (`timestamp` и `value`), оптимизирована для работы с упорядоченными данными по времени.
*   **Retention:** Настройка срока хранения метрик, после которого старые данные удаляются.
*   **Эффективность хранения:** Позволяет эффективно управлять дискретизацией (точностью) хранения данных в зависимости от их "возраста" (например, более старые данные хранятся с меньшей точностью).
*   **Модульная архитектура хранения:** Prometheus хранит данные не напрямую, а через **интерфейс адаптера**. Это позволяет подключать различные внешние TSDB в качестве бэкендов для долгосрочного хранения или повышения производительности на больших объемах.
    *   **Примеры бэкендов:** VictoriaMetrics, Thanos (для Kubernetes), ClickHouse, Elasticsearch, Graphite, InfluxDB, Kafka.
    *   VictoriaMetrics и Thanos являются наиболее популярными решениями для масштабируемого хранения. VictoriaMetrics — более универсальное решение, в то время как Thanos тесно интегрирован с Kubernetes.

## 5. Экспортеры

Экспортеры — это программы, которые собирают метрики из сторонних систем и преобразуют их в формат Prometheus.

*   **`node_exporter`:** Стандартный экспортер для Linux-хостов, собирающий метрики CPU, памяти, дисков, сети и т.д.
    *   **Механизм работы:** `node_exporter` не обращается к ядру напрямую, а читает и парсит данные из виртуальных файловых систем Linux, таких как `/proc` и `/sys` (например, `/proc/meminfo` для информации о памяти).
    *   **Расширяемость:** Поддерживает сбор метрик с внешних приложений или пользовательских скриптов (например, для fail2ban). Такие скрипты могут формировать файлы с метриками в специальном формате, а `node_exporter` будет их читать и отдавать Prometheus.
*   **Широкий спектр:** Существует огромное количество готовых экспортеров для баз данных (MySQL, PostgreSQL), веб-серверов (Nginx), брокеров сообщений и т.д. Можно написать и собственный экспортер, даже на Bash.

## 6. Практические аспекты

*   **Конфигурация Prometheus (`prometheus.yml`):**
    *   `global`: Общие параметры, такие как `scrape_interval` (частота опроса таргетов).
    *   `scrape_configs`: Определяет задания (`job_name`) и цели (`targets`) для сбора метрик. Prometheus может мониторить сам себя (localhost:9090).
*   **Формат метрик:** Prometheus отдает метрики в текстовом формате. Каждая метрика сопровождается служебными комментариями, которые описывают ее тип (`Gauge`, `Counter`, `Summary`, `Histogram`).
*   **Графический интерфейс Prometheus:** Встроенный веб-интерфейс (`/graph`) позволяет выполнять запросы на PromQL и просматривать метрики.
*   **Визуализация с Grafana:**
    *   Grafana подключается к Prometheus как источник данных.
    *   Используются готовые дашборды (например, для `node_exporter`), которые можно импортировать по ID из каталога Grafana.
