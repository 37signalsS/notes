# Экспортеры Prometheus

**Экспортер (Exporter)** — это программа, которая собирает метрики из сторонней системы и преобразует их в формат, понятный Prometheus. Экспортеры действуют как "переводчики" или "адаптеры" между Prometheus и системой, которую необходимо мониторить.

## Принцип работы

1.  Экспортер запрашивает данные у целевой системы (например, у базы данных или у операционной системы).
2.  Он преобразует полученные данные в текстовый формат метрик Prometheus.
3.  Экспортер открывает HTTP-эндпоинт (обычно `/metrics`), по которому Prometheus может забрать (scrape) эти метрики.

Экспортер не хранит метрики и не знает о существовании Prometheus. Он просто постоянно парсит данные и отдает их по запросу. Как часто Prometheus будет приходить за этими данными, настраивается в его конфигурации (`scrape_interval`).

## Примеры популярных экспортеров

Существует огромное количество экспортеров для самых разных систем.

### `node_exporter`

Один из самых распространенных экспортеров. Он собирает метрики с хост-машины (сервера).
*   **Собираемые метрики:** загрузка CPU, использование памяти, дисковое пространство, сетевая активность и многое другое.
*   **Источник данных:** `node_exporter` не обращается напрямую к ядру. Он читает и парсит файлы из виртуальных файловых систем Linux, таких как `/proc` и `/sys`. Например, для получения информации о памяти он читает `/proc/meminfo`.

### `cAdvisor` (Container Advisor)

Предоставляет метрики о запущенных контейнерах. Он позволяет отслеживать потребление ресурсов (CPU, память, сеть, I/O) для каждого контейнера. `cAdvisor` является неотъемлемой частью мониторинга в средах Docker и Kubernetes.

### Другие экспортеры

Существуют экспортеры практически для всего:
*   Базы данных (`mysqld_exporter`, `postgres_exporter`).
*   Веб-серверы (`nginx-prometheus-exporter`).
*   Брокеры сообщений (`rabbitmq_exporter`, `kafka_exporter`).
*   И даже для экзотических систем, таких как 1С.

## Лучший экспортер — это его отсутствие

Идеальная ситуация — когда приложению или системе не нужен отдельный экспортер. Это возможно, если приложение **само умеет отдавать метрики** в формате Prometheus. Такой подход называется **нативной инструментацией (native instrumentation)**.

*   **Преимущества:**
    *   Упрощение архитектуры мониторинга (не нужно разворачивать и обслуживать дополнительный компонент).
    *   Более точные и релевантные бизнес-метрики, так как они генерируются непосредственно из кода приложения.

**Пример:**
В экосистеме Java для фреймворка Spring Boot существует зависимость **Actuator**. При ее подключении приложение автоматически начинает отдавать множество метрик (включая метрики JVM, хипа, потоков) по эндпоинту `/actuator/prometheus`. Prometheus'у остается только добавить этот эндпоинт в свою конфигурацию.
