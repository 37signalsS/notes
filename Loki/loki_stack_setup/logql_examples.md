# Примеры LogQL запросов для Kubernetes

## Определения

**LogQL** (Log Query Language) — специализированный язык запросов для системы Loki, вдохновлённый синтаксисом PromQL. Он позволяет эффективно извлекать данные из логов, фильтровать их по метаданным и содержанию, преобразовывать в числовые метрики и выполнять сложные агрегации для мониторинга и алертинга.

**Структура запроса:** `{селектор_потока} | конвейер_обработки`

Конвейер обработки может включать:
*   **Фильтры строк** (текстовый поиск).
*   **Парсеры** (извлечение структуры из текста).
*   **Фильтры полей** (математические и логические условия).
*   **Форматирование** (изменение вида вывода).
*   **Агрегации** (превращение в временные ряды).

**Stream (Поток):** Уникальная комбинация лейблов (labels), определяющая группу логов. Все логи с одинаковым набором лейблов принадлежат одному потоку. LogQL запрос сначала фильтрует streams через селектор `{...}`, затем обрабатывает строки внутри отфильтрованных streams.

**Label Selector (Селектор лейблов):** Часть запроса в фигурных скобках `{app="api", env="prod"}`, аналогичная PromQL. Фильтрует streams на уровне TSDB Index, что является самой быстрой операцией. Использует операторы `=`, `!=`, `=~` (regex), `!~` (negated regex).

**Instant Vector:** Результат запроса без диапазона `[]` — Loki возвращает самое последнее значение для каждого matching stream. Используется в Grafana для панелей типа Stat или single-value.

**Range Vector:** Результат запроса с диапазоном `[5m]` — Loki возвращает все значения за указанный период. Используется для агрегирующих функций (`rate()`, `avg_over_time()` и т.д.).

**Парсер (Parser):** Операция конвейера (`| json`, `| logfmt`, `| pattern`), которая извлекает поля из текста строки лога. Парсинг — ресурсоёмкая операция CPU, поэтому его всегда следует применять после фильтров строк.

**Structured Metadata (Структурированные метаданные):** Механизм Loki 3.x, позволяющий фильтровать по полям без создания новых лейблов. В LogQL доступ через оператор `| level="debug"` без явного указания парсера. Метаданные передаются агентом (Alloy) вместе с логом.

**`__error__` и `__error_details__`:** Специальные поля, добавляемые парсерами (`| json`, `| logfmt`, `| pattern`) при ошибке разбора. `__error__` содержит тип ошибки, `__error_details__` — детали (например, `json: unknown field ...`). Используются для отладки парсинга.

**Bloom Filter (в контексте запросов):** Вероятностная структура Loki 3.x, позволяющая быстро отсеять чанки, не содержащие искомую строку. Ускоряет grep-подобные запросы в 10–50 раз. В LogQL эффективность зависит от использования точных фильтров строк (`|= "exact"`) — они могут быть проверены через Bloom-фильтры на уровне чанков без чтения данных.

**Retention (в контексте запросов):** Запросы за пределами `retention_period` возвращают пустой результат. Loki не хранит данные дольше указанного периода, поэтому запросы за 90+ дней при retention=30d вернут пустоту без ошибки.

## Основные концепции

### Синтаксис и семантика запросов

LogQL запрос состоит из двух обязательных частей:

1.  **Селектор stream:** `{namespace="prod", app=~"api-.*"}` — фильтрация по индексированным лейблам.
2.  **Конвейер (pipeline):** последовательность операторов `|`, обрабатывающих строки логов.

**Варианты запросов:**

| Тип | Синтаксис | Использование |
| :--- | :--- | :--- |
| **Log query** | `{app="api"} \| json \| status="error"` | Поиск и фильтрация логов |
| **Metric query** | `sum by (app) (rate({app="api"}[5m]))` | Временные ряды для графиков |
| **Instant** | `{app="api"} \| json \| unwrap latency` | Текущее значение (без `[]`) |
| **Range** | `... [5m]` | Значения за период (для агрегаций) |

**Порядок выполнения:**
1.  Loki фильтрует streams через TSDB Index по селектору.
2.  Для оставшихся streams читаются чанки из инжестеров (свежие данные в памяти) и хранилища (история).
3.  Строки последовательно проходят конвейер: фильтры строк → парсеры → фильтры полей → форматирование.
4.  Если запрос содержит агрегацию, строки преобразуются в числовые ряды и сворачиваются по указанным лейблам.

### Оптимизация (Blocking Rule)

Всегда применяйте фильтры по строкам (`|=`, `!=`, `|~`) **ПЕРЕД** парсерами (`| json`, `| pattern`). Это позволяет Loki отсечь ненужные данные на раннем этапе, не тратя ресурсы CPU на парсинг строк, которые все равно будут отфильтрованы. Кроме того, фильтры строк могут быть проверены через Bloom-фильтры без чтения полных чанков.

### Операции в конвейере обработки

| Операция | Синтаксис | Назначение |
| :--- | :--- | :--- |
| **Фильтр строк** | `|= "text"`, `!= "text"` | Поиск или исключение подстроки (самый быстрый метод) |
| **Regex-фильтр** | `\|~ "regex"`, `!~ "regex"` | Фильтрация по регулярному выражению |
| **JSON-парсер** | `\| json` | Автоматическое извлечение полей из JSON-логов |
| **Logfmt-парсер** | `\| logfmt` | Извлечение полей из формата `key=value` |
| **Pattern-парсер** | `\| pattern "<format>"` | Извлечение данных из неструктурированных логов по шаблону |
| **Фильтр полей** | `\| field >= 500` | Фильтрация по значениям, извлечённым парсером |
| **Unwrap** | `\| unwrap label` | Превращение поля в числовой ряд для агрегации |
| **Line Format** | `\| line_format "{{.msg}}"` | Переформатирование текста строки лога для отображения |
| **Label Format** | `\| label_format service="{{.container}}"` | Создание/изменение временных лейблов в выводе |
| **Label Replace** | `\| label_replace instance, "$1", "instance", "(.*)", "$1:3100"` | Извлечение подстроки из значения лейбла в новый лейбл |
| **Drop** | `\| drop {field1, field2}` | Удаление полей из вывода (снижает объём передаваемых данных) |
| **Keep** | `\| keep {msg, level}` | Оставить только указанные поля (обратное drop) |
| **Dedup** | `\| dedup` | Удаление дублирующихся строк в результате запроса |

### Парсеры: нюансы и ограничения

**JSON (`| json`):**
*   Автоматически парсит JSON-объект в строке лога.
*   Поддерживает вложенные поля через точечную нотацию: `| .http.status`.
*   При ошибке парсинга добавляет `__error__` и `__error_details__`.
*   **Вариант:** `| json | level="error"` — фильтрация по полю внутри JSON.
*   **Вариант:** `| json | unwrap duration_ms` — преобразование числового поля.

**Logfmt (`| logfmt`):**
*   Парсит формат `key=value key2="value2"`, распространённый в Go-приложениях.
*   Эффективнее JSON для простых ключ-значений, так как не требует скобок и кавычек.
*   Пример: `{job="varlogs"} | logfmt | level="error"`.

**Pattern (`| pattern "<format>"`):**
*   Извлекает поля из неструктурированного текста по шаблону.
*   Формат: `<тип> <имя>` для каждого поля. Типы: `<ip>`, `<int>`, `<float>`, `<word>`, `< quoted>`, `<_>` (пропустить), `<timestamp>`.
*   **Важно:** `<timestamp>` требует, чтобы поле в логе совпадало с форматом RFC3339Nano.
*   Пример Nginx: `| pattern "<ip> - - [<timestamp>] \"<method> <path> <_>\" <status> <size>"`.
*   Pattern значительно проще и быстрее regex для фиксированных форматов.

### Агрегирующие функции

В Loki 3.x агрегации позволяют строить графики на основе частоты появления событий или значений внутри логов.

| Функция | Описание | Пример |
| :--- | :--- | :--- |
| **`rate()`** | Количество строк в секунду | `rate({app="api"}[5m])` |
| **`count_over_time()`** | Общее количество строк за период | `count_over_time({app="db"}[1h])` |
| **`sum by(label)`** | Суммирование по группам | `sum by (level) (rate(...))` |
| **`avg_over_time()`** | Среднее значение числового поля | `avg_over_time(... \| unwrap duration[5m])` |
| **`quantile_over_time()`** | Расчет перцентиля | `quantile_over_time(0.99, ... \| unwrap latency[5m])` |
| **`bytes_rate()`** | Скорость передачи данных в байтах | `bytes_rate({job="mysql"}[1m])` |
| **`bytes_over_time()`** | Общий объём данных за период | `bytes_over_time({namespace="prod"}[24h])` |
| **`stddev_over_time()`** | Стандартное отклонение числового поля | `stddev_over_time(... \| unwrap latency[5m])` |
| **`stdvar_over_time()`** | Дисперсия числового поля | `stdvar_over_time(... \| unwrap latency[5m])` |
| **`min_over_time()`** | Минимальное значение за период | `min_over_time(... \| unwrap cpu[5m])` |
| **`max_over_time()`** | Максимальное значение за период | `max_over_time(... \| unwrap cpu[5m])` |
| **`absent_over_time()`** | 1 если данных нет, 0 если есть | `absent_over_time({job="critical"}[5m])` |
| **`absent()`** | 1 если streams не существует | `absent({job="missing-service"})` |
| **`count_values_over_time()`** | Количество каждого уникального значения | `count_values_over_time("level", {app="api"} \| logfmt [5m])` |
| **`topk(k, expr)`** | Top-k по значению агрегата | `topk(10, sum by (pod) (rate({namespace="prod"}[5m])))` |
| **`bottomk(k, expr)`** | Bottom-k по значению агрегата | `bottomk(3, sum by (pod) (rate({namespace="prod"}[5m])))` |
| **`first_over_time()`** | Первое значение в периоде | `first_over_time(... \| unwrap temp[1h])` |
| **`last_over_time()`** | Последнее значение в периоде | `last_over_time(... \| unwrap temp[1h])` |

### Производительность и оптимизация запросов

Понимание взаимодействия LogQL с архитектурой Loki критично для написания эффективных запросов.

**Уровни фильтрации Loki (от быстрого к медленному):**

1.  **TSDB Index (лейблы в селекторе):** Самая быстрая операция. Loki определяет, какие streams содержат нужные лейблы, и пропускает остальные.
2.  **Bloom Filter (фильтры строк):** В Loki 3.x позволяет отсеять чанки, не содержащие подстроку, без чтения данных. Работает только для точных подстрок (`|= "text"`), не работает для regex.
3.  **Chunk scan (полное чтение):** Если Bloom-фильтр не отсеял чанк, Loki читает его и применяет regex/парсеры. Самый медленный этап.

**Правила оптимизации:**

| Правило | Объяснение |
| :--- | :--- |
| **Фильтры лейблов первыми** | Селектор `{app="api", env="prod"}` должен быть максимально конкретным. Избегайте `{namespace=~".+"}` без дополнительных условий. |
| **Фильтры строк до парсеров** | `|= "error"` перед `| json`. Bloom-фильтры ускорят substring-фильтрацию. |
| **Избегайте regex если возможно** | `|= "timeout"` в 5–10 раз быстрее `|~ "time.*out"`. Regex не может использовать Bloom-фильтры. |
| **Ограничьте диапазон** | `[5m]` вместо `[24h]` если возможно. Чем меньше диапазон, тем меньше чанков нужно прочитать. |
| **Упростите парсеры** | `| logfmt` легче чем `| json` для простых форматов. `| pattern` легче regex. |
| **Уберите ненужные лейблы из агрегации** | `sum by (app) (...)` вместо `sum by (app, pod, instance)` — меньше групп для сворачивания. |
| **Используйте `__error__` для отладки парсинга** | `| json | __error__!=""` — быстро найти строки, которые не парсятся. |

**Пример оптимизации запроса:**

```logql
// Медленный запрос: парсит все логи за час
sum by (app) (rate({namespace="prod"} | json | unwrap duration_ms [1h]))

// Быстрый запрос: фильтрует по подстроке, потом парсит, ограничивает диапазон
sum by (app) (rate({namespace="prod"} |= "request" | json | unwrap duration_ms [5m]))
```

## Практические сценарии

### Базовые запросы Kubernetes

Поиск логов по стандартным метаданным, добавляемым агентом (Alloy/Promtail).

```logql
// Все логи из конкретного пространства имен
{namespace="production"}

// Логи конкретного пода с исключением контейнеров-прокси
{pod="api-server-7db6576", container!="istio-proxy"}

// Поиск по нескольким сервисам одновременно
{app=~"auth-.*|billing-.*", env="prod"}

// Логи конкретного контейнера за последние 15 минут
{namespace="production", container="app"} [15m]

// Все логи, кроме debug
{namespace="production"} != "level=debug"
```

### Базовые запросы для Linux-систем

Запросы для анализа логов, собранных с физических серверов или виртуальных машин через Promtail/Alloy.

```logql
// Поиск по конкретной задаче (job)
{job="varlogs"}

// Поиск конкретного текста во всех системных логах
{job="varlogs"} |= "docker"

// Фильтрация по имени файла (точный поиск)
{filename="/var/log/syslog"}

// Выбор нескольких файлов через регулярное выражение (OR)
{filename=~"/var/log/kern.log|/var/log/syslog"}

// Комбинированный поиск: ошибка в API логах
{job="api_logs"} |= "error" != "timeout"

// Системные логи systemd journald через Alloy
{job="journald"} |= "failed" | logfmt | _SYSTEMD_UNIT="nginx.service"
```

**Интерфейс Grafana Explore:**
*   **Builder:** Визуальный конструктор для тех, кто только начинает изучать LogQL. Позволяет выбирать лейблы из выпадающих списков.
*   **Code:** Режим прямого ввода запроса. Необходим для сложных агрегаций и использования функций, недоступных в конструкторе.

### SRE и DevOps сценарии (On-Call, Incident Response)

Практические запросы для типичных операционных сценариев.

**Триаж при срабатывании алерта:**

```logql
// Быстрый поиск всех ошибок в сервисе за последние 10 минут
{app="payment-gateway", env="prod"} |= "error" [10m]

// Количество ошибок по уровням
sum by (level) (count_over_time({app="payment-gateway"} |= "error" [10m]))

// Поиск stack trace (первые строки ошибки)
{app="payment-gateway"} |= "goroutine" | pattern "<_> <_> <_> <message>" | message=~".*panic.*"
```

**Анализ взрывной нагрузки (Blast Radius):**

```logql
// Поиск всех сервисов, которые упоминают упавший сервис
{namespace="prod"} |= "payment-gateway" [5m]

// Зависимости по traceID: найти все логи связанные с проблемным запросом
{traceID="abc123"} | label_format service="{{.container}}"

// Количество запросов к проблемному сервису
sum by (source_app) (rate({app="payment-gateway"} [5m]))
```

**Планирование ёмкости (Capacity Planning):**

```logql
// Объём логов по namespace за 7 дней
sum by (namespace) (bytes_over_time({namespace=~".+"}[7d]) / 1024 / 1024 / 1024)

// Рост количества streams (показатель cardinality)
loki_ingester_streams_created_total - increase(loki_ingester_streams_created_total[1d])

// Топ-10 контейнеров по частоте запросов к Loki (можно отфильтровать abusive queries)
topk(10, sum by (app) (rate({namespace="prod"} [5m])))
```

### Анализ неструктурированных логов через Pattern

Парсер `pattern` значительно проще регулярных выражений для логов с фиксированным форматом (например, Nginx).

```logql
// Анализ логов Nginx: поиск медленных ответов
{app="nginx-ingress"} 
| pattern "<ip> - - [<timestamp>] \"<method> <path> <_>\" <status> <size> \"<_>\" \"<_>\" <request_time>"
| status >= 400 or request_time > 1.0

// Статистика HTTP методов
{app="nginx-ingress"}
| pattern "<ip> - - [<_>] \"<method> <_> <_>\" <status> <_>"
| sum by (method, status) (count_over_time([5m]))

// Извлечение user agent
{app="nginx-ingress"}
| pattern "<_> \"<_>\" <_> \"<user_agent>\""
| topk(5, sum by (user_agent) (count_over_time([1h])))
```

### Работа со структурированными данными (JSON)

Современные приложения часто пишут логи в JSON. Loki позволяет работать с ними как с объектами.

```logql
// Расчет 95-го перцентиля времени ответа
quantile_over_time(0.95,
  {app="backend"}
  | json
  | unwrap duration_ms [10m]
)

// Фильтрация по вложенным полям и форматирование вывода
{app="order-service"}
| json
| status="error"
| line_format "Ошибка в заказе {{.order_id}}: {{.error_msg}}"

// Парсинг вложенных объектов: http.request.method
{app="api-gateway"}
| json
| .http.request.method="POST"
| .http.response.status_code >= 500
| line_format "{{.http.request.method}} {{.http.request.path}} -> {{.http.response.status_code}}"

// Отладка парсинга: найти строки, которые не удалось распарсить
{app="backend"} | json | __error__!="" | line_format "PARSE ERROR: {{.line}} | {{.__error_details__}}"

// Unwrap с обработкой ошибок: только валидные числа
{app="metrics-exporter"} | json | unwrap value on __error__="" [5m]
```

### Использование Structured Metadata (Loki 3.x)

В Loki 3.x можно фильтровать по метаданным, которые не являются индексируемыми метками (лейблами), что предотвращает раздувание индекса.

```logql
// Фильтрация по структурированным метаданным (без парсинга тела лога)
{app="payment-gateway"} | level="debug" and region="us-east-1"

// Комбинация лейблов и structured metadata
{app="payment-gateway", env="prod"} | traceID="abc123" | level="error"

// Извлечение structured metadata через line_format
{app="payment-gateway"} | level="error" | line_format "[{{.region}}] {{.msg}}"

// Фильтрация по traceID без создания лейбла traceID (сохраняет низкую cardinality)
{app="payment-gateway"} | traceID=~".{32}" [5m]
```

**Важно:** Structured metadata передаётся агентом (Alloy) через поле `__meta_*` или напрямую через API. Убедитесь, что конфигурация Alloy включает соответствующие поля в `logfmt` или `json` stage.

### Сценарии безопасности и аудита

```logql
// Обнаружение Brute Force атак (более 20 попыток входа с одного IP за минуту)
sum by (ip) (
  rate({job="auth-service"} |= "login_failed" | pattern "<_> IP:<ip> <_>" [1m])
) > 20

// Поиск доступа к чувствительным файлам
{job="system-log"} |~ "access denied|sudoers|shadow"

// Аудит изменений в Kubernetes (kube-apiserver)
{job="kube-apiserver"} |= "create\|update\|delete" | logfmt | verb!="get\|list\|watch"

// Обнаружение подозрительных DNS-запросов
{app="coredns"} | logfmt | regexp "^(?!.*google).*" | query=".onion\|.xyz"

// Проверка отозванных сертификатов
{app="nginx-ingress"} |= "ssl_certificate revoked" [1h]
```

### Корреляция и трассировка (Distributed Tracing)

Связывание логов разных микросервисов через единый идентификатор транзакции.

```logql
// Поиск пути запроса через все сервисы по Trace ID
{namespace="prod"} |= "a1b2c3d4e5f6" 
| label_format service="{{.container}}"
| line_format "[{{.service}}] {{.message}}"

// Количество сервисов, затронутых одним запросом
count by (traceID) ({namespace="prod"} |= "traceID" | logfmt | traceID="abc123")

// Время ответа сервиса по traceID
{namespace="prod"} |= "traceID=abc123" | json | unwrap duration_ms
| sum by (app) (duration_ms)

// Корреляция логов с метриками Prometheus через лейблы
{namespace="prod"} |= "latency" | json | unwrap latency_ms [1m]
// Grafana сможет связать этот запрос с графиком latency из Prometheus через общий лейбл `namespace`
```

### Анализ стоимости и объёма данных

Позволяет понять, какие сервисы генерируют больше всего логов и потребляют место в хранилище.

```logql
// Топ-10 контейнеров по объему передаваемых данных (МБ/сек)
topk(10, sum by (container) (bytes_rate({namespace="prod"}[5m]) / 1024 / 1024))

// Подсчет объема логов за последние 24 часа по приложениям
sum by (app) (bytes_over_time({namespace=~".+"}[24h]) / 1024 / 1024 / 1024)

// Эффективность сжатия: отношение сырых данных к сжатым
sum by (app) (bytes_over_time({namespace="prod"}[1h])) 
/ sum by (app) (count_over_time({namespace="prod"}[1h])) 
/ 1024

// Выявление подозрительного роста объёма логов (>2x за день)
sum by (app) (bytes_over_time({namespace="prod"}[1h])) 
/ (sum by (app) (bytes_over_time({namespace="prod"}[25h]) - bytes_over_time({namespace="prod"}[24h]))) 
> 2
```

### Визуализация в Grafana

При создании дашбордов используйте следующие типы запросов:

1.  **Time Series (График ошибок):**
    `sum by (app) (rate({namespace="prod"} |= "error" [1m]))`
2.  **Stat (Общее кол-во критических событий):**
    `sum(count_over_time({env="prod"} | level="critical" [24h]))`
3.  **Table (Список последних ошибок с контекстом):**
    `{app="api"} | json | status="error" | keep msg, error_code, user_id`
4.  **Logs (Столбик логов):**
    `{app="api"} |= "error" | limit 100`
5.  **Gauge (Процентиль latency):**
    `quantile_over_time(0.95, {app="api"} | json | unwrap latency_ms [5m])`

### Устранение неполадок LogQL

#### Диагностика пустых результатов

```logql
// Проверка: существуют ли данные вообще
{namespace="prod"} [1h]

// Проверка: существует ли конкретный stream
{namespace="prod", app="target-app"} [1h]

// Проверка: существует ли конкретный лейбл
count by (app) ({namespace="prod"} [1h])

// Проверка парсинга: все ли строки парсятся корректно
{app="backend"} | json | __error__!="" | line_format "ERROR: {{.line}} | {{.__error_details__}}"

// Проверка фильтра: не отфильтровывается ли всё на раннем этапе
{app="backend"} |= "expected-text" [1h]
```

#### Диагностика медленных запросов

```logql
// Замер времени выполнения через Loki API
curl -G -s "http://loki:3100/loki/api/v1/query_range" \
  --data-urlencode 'query={app="api"} |= "error" [1h]' \
  --data-urlencode 'start=now-1h' \
  --data-urlencode 'end=now' \
  -w "\nВремя: %{time_total}s\n"

// Проверка, сколько streams совпало с селектором
count by (app) ({app=~".+"} [1h])

// Проверка размера результата (ограничьте limit)
{app="api"} |= "error" [1h] | limit 10

// Отключение кэша для чистого замера
curl -G -s "http://loki:3100/loki/api/v1/query_range?query={app='api'}[1h]" \
  -H "X-Cache-Bypass: true"
```

#### Типичные ошибки LogQL

| Ошибка | Возможная причина | Решение |
| :--- | :--- | :--- |
| **"query timeout"** | Слишком широкий селектор или диапазон, отсутствие фильтров строк | Уменьшите диапазон, добавьте фильтры строк перед парсерами, увеличьте `query_timeout` в конфиге Loki. |
| **"streams selector missing"** | В запросе отсутствует селектор `{...}` | Добавьте селектор stream: `{app="api"} \| json` |
| **"parse error" в pattern** | Несоответствие формата pattern реальным логам | Проверьте порядок полей в pattern. Используйте `<_>` для пропуска неизвестных полей. |
| **"parse error" в json** | Строка не является валидным JSON | Проверьте `__error_details__` через `| json | __error__!=""`. Используйте `| pattern` для частичного парсинга. |
| **"invalid parameter" в unwrap** | Поле отсутствует или имеет нечисловое значение | Убедитесь, что парсер извлек поле. Используйте `unwrap duration on __error__=""`. |
| **"vector cannot contain metrics"** | Попытка смешать логи и метрики в одной агрегации | Убедитесь, что `unwrap` применён до агрегации. |
| **Пустой результат при наличии данных** | Слишком узкий фильтр, неправильный regex, опечатка в лейбле | Проверьте `{app="api"} [1h]` без парсера. Проверьте точность regex (Go flavor). |
| **"max series exceeded"** | Агрегация порождает слишком много временных рядов | Уменьшите число группировок `by (label)`. Увеличьте `max_query_series` в limits_config. |
| **"entry out of order" в результатах** | Данные пришли с неправильной временной меткой | Это системная ошибка Loki, а не запроса. Проверьте конфигурацию агента (`respect_prev_timestamp`). |

### Инструменты экосистемы

**Logcli:** CLI-утилита для отладки запросов и управления кластером из терминала.

```bash
# Выполнение запроса из командной строки
logcli query '{app="api"} |= "error" [1h]' --limit=100

# Экспорт результатов в CSV
logcli query '{app="api"} |= "error" [1h]' --output=csv > errors.csv

# Проверка метрик инжестера
logcli series '{app="api"}' --from=now-1h

# Поиск labels
logcli labels --from=now-24h

# Проверка tenant limits
logcli limits tenant=fake

# Проверка статуса Bloom-фильтров (Loki 3.x)
logctl bloom --query={app="api"} --from=now-1h --to=now
```

**Loki Canary:** Инструмент для мониторинга потерь данных и задержек записи.

**Grafana Alloy:** Современный агент, заменяющий Promtail. [Настройка Alloy](./alloy_installation.md).

### Лучшие практики

1.  **Лейблы:** Используйте статические, низкокардинальные лейблы (cluster, service, env, container). Никогда не используйте идентификаторы запросов, IP-адреса пользователей или временные метки как лейблы.
2.  **Structured Metadata:** Для высококардинальных данных (trace_id, user_id, session_id) используйте structured metadata (Loki 3.x) вместо лейблов.
3.  **Порядок операций:** Всегда фильтры строк (`|=`, `!=`) → парсеры (`| json`) → фильтры полей → `unwrap` → агрегации.
4.  **Regex:** Избегайте сложных regex с backtracking. Используйте `| pattern` для фиксированных форматов. Избегайте `|~` если достаточно `|=`.
5.  **Диапазон запросов:** Используйте минимально возможный диапазон `[]`. Для алертов 1–5 минут, для графиков 5–15 минут, для аудита 24 часа–7 дней.
6.  **Aggregation:** Используйте `by (label)` только для необходимых лейблов. Избыточные лейблы увеличивают время сворачивания и потребление RAM Querier.
7.  **Сэмплирование:** Для высоконагруженных систем применяйте head-based или adaptive сэмплирование на стороне агента для INFO/DEBUG логов.
8.  **Retention:** Настраивайте `retention_period` согласно политике хранения. Для production: 7–30 дней для оперативных логов, 90+ дней для аудита.
9.  **Мониторинг:** Следите за метриками `loki_ingester_memory_chunks`, `loki_request_duration_seconds`, `loki_distributor_sent_bytes_total`.
10. **Валидация:** После каждого изменения конфигурации проверяйте `/ready` и выполните тестовый LogQL запрос.
11. **Объектное хранилище:** Для production всегда используйте S3/MinIO, а не filesystem. Файловая система не обеспечивает репликацию и при сбое диска данные теряются.
12. **Аутентификация:** Всегда включайте `auth_enabled: true` и передавайте `X-Scope-OrgID` через Gateway.
13. **Дубликаты:** Убедитесь, что downstream системы (Grafana, алерты) обрабатывают дубликаты корректно, особенно при использовании `dedup`.
14. **Structured Metadata:** Для частых фильтров по высококардинальным полям используйте structured metadata вместо парсинга тела лога.

### Ограничения и edge cases

1.  **Bloom-фильтры:** Имеют вероятность false positive (обычно < 1%). Для критичных сценариев, где требуется 100% точность, используйте фильтры как предварительный этап, а не единственный механизм.
2.  **Structured Metadata:** В текущей версии не поддерживается индексация structured metadata (только фильтрация). Для частых фильтров по высококардинальным полям рассмотрите использование отдельного stream с фильтрацией на уровне агента.
3.  **Max Query Length:** Запросы по слишком широкому временному диапазону (например, несколько лет) могут приводить к таймаутам. Ограничьте `max_query_length` в `limits_config`.
4.  **WAL Recovery:** При восстановлении из WAL после сбоя доставка логов может быть дублирована (at-least-once семантика). Убедитесь, что downstream системы (например, Grafana) обрабатывают дубликаты корректно.
5.  **Filesystem storage:** В Single Binary/Simple Scalable режимах filesystem не поддерживает горизонтальное масштабирование. Для > 100 ГБ/день используйте S3.
6.  **Regex Performance:** Сложные regex с backtracking (например, `.*`) могут вызывать зависание Querier. Используйте `| pattern` или упрощайте regex.
7.  **Timezone:** Loki хранит все временные метки в UTC. Убедитесь, что Grafana и клиенты корректно обрабатывают timezone.
8.  **Case Sensitivity:** Фильтры строк (`|=`) чувствительны к регистру. Для case-insensitive поиска используйте regex: `|~ "(?i)error"`.
9.  **Unicode:** Loki поддерживает UTF-8. Однако некоторые regex-конструкции могут вести себя неожиданно с Unicode-символами. Тестируйте pattern-парсер с кириллицей отдельно.
10. **Max Series:** Агрегации с большим числом уникальных значений (например, `sum by (request_id)`) могут превышать `max_query_series`. Используйте `topk` для ограничения результата.
11. **Empty Results:** Запросы за пределами retention возвращают пустой результат без ошибки. Это корректное поведение. Убедитесь, что диапазон запроса покрывает период, когда данные уже поступили в Loki.
12. **Concurrent Queries:** Ограничьте количество одновременных запросов через `max_concurrent` в Query Frontend. Слишком много параллельных тяжелых запросов может привести к OOM Querier.
