# Обзор Loki

Loki — это горизонтально масштабируемая, высокодоступная, мульти-тенантовая система агрегации логов, разработанная Grafana Labs. Она была анонсирована в 2018 году и достигла статуса General Availability (GA) в 2019. Loki написан на Go и распространяется под лицензией **AGPLv3**, что гарантирует его открытость.

Система вдохновлена Prometheus и использует аналогичный подход к индексации, фокусируясь на метаданных (метках), а не на полном тексте логов. Это позволяет значительно снизить затраты на хранение по сравнению с традиционными системами, такими как Elasticsearch.

## Ключевые особенности

*   **Экономичное хранение:** Loki индексирует только метки (labels) для каждого потока логов, а сами данные логов сжимает и хранит в виде "чанков" (chunks) в объектном хранилище (например, S3, GCS) или в файловой системе. Это делает его на порядок дешевле систем с полнотекстовой индексацией.
*   **Prometheus-подобная модель данных:** Лог в Loki — это пара (набор лейблов, текстовое сообщение). Для каждого уникального набора лейблов вычисляется хэш, который становится идентификатором потока (**Stream ID**). Все логи с одинаковым набором лейблов попадают в один и тот же поток и группируются в один "чанк". Как только хотя бы один лейбл меняется, создается новый поток с новым Stream ID. Этот подход, практически идентичный TSDB из Prometheus, значительно упрощает корреляцию между метриками и логами.
*   **LogQL:** Мощный язык запросов, синтаксически похожий на PromQL, который позволяет фильтровать, преобразовывать и агрегировать логи.
*   **Масштабируемость и высокая доступность:** Loki может работать как в виде единого бинарного файла (монолит), так и в виде набора горизонтально масштабируемых микросервисов.
*   **Мульти-тенатность:** Встроенная поддержка изоляции данных для разных команд или клиентов (tenants) через специальный HTTP-заголовок `X-Scope-OrgID`.
*   **Интеграция с Grafana:** Глубокая интеграция с Grafana для визуализации, анализа и создания алертов по логам. У Loki нет собственного UI.

## Архитектура

Loki может быть запущен в двух режимах: монолитном и распределенном.

### Монолитный режим
Все компоненты работают как один процесс в рамках одного бинарного файла. Этот режим подходит для небольших инсталляций, тестов и изучения.

### Распределенный (микросервисный) режим
Для обеспечения высокой доступности и масштабируемости Loki разделяется на независимые компоненты, каждый из которых может масштабироваться отдельно. Это позволяет гибко настраивать систему под разные типы нагрузки (на запись или на чтение).

*   **Gateway:** Не является частью Loki, но рекомендуется к использованию. Обычно это Nginx или другой reverse proxy, который выступает единой точкой входа и маршрутизирует запросы к соответствующим компонентам Loki.
*   **Distributor (Диспетчер):** Принимает потоки логов от клиентов, валидирует их, нормализует метки (например, сортируя их по алфавиту для консистентности Stream ID) и направляет на инжестеры с заданным фактором репликации (по умолчанию 3).
*   **Ingester (Инжестер):** Получает данные от диспетчера, объединяет сообщения в "чанки" (chunks) в памяти, а затем сохраняет их в долгосрочное хранилище (object storage).
*   **Querier (Запросчик):** Обрабатывает запросы LogQL. Он запрашивает данные как у инжестеров (для недавних, "горячих" логов из кэша), так и напрямую из долгосрочного хранилища.
*   **Query Frontend:** Опциональный, но крайне рекомендуемый компонент для больших инсталляций. Ставится перед Querier'ами и ускоряет чтение за счет кэширования результатов (с использованием Redis или Memcached), разбиения больших запросов на мелкие и их распараллеливания.
*   **Ruler:** Отвечает за выполнение правил алертинга. Он периодически выполняет запросы LogQL и отправляет оповещения в Prometheus Alertmanager.
*   **Compactor:** Фоновый процесс, отвечающий за оптимизацию данных в хранилище (дедупликация, сжатие) и применение политик хранения (retention, TTL).
*   **Index Gateway** и **Query Scheduler:** Опциональные компоненты, которые помогают управлять и распараллеливать запросы в очень крупных кластерах.

## Установка и клиенты

### Способы установки
*   **Бинарный файл:** Скачать готовый бинарник для Linux, macOS.
*   **Docker:** Использовать официальный Docker-образ.
*   **Kubernetes:** Развернуть с помощью официального Helm-чарта (рекомендуемый способ для продакшена).
*   **Grafana Cloud:** Использовать Loki как сервис.

### Отправка данных в Loki (Клиенты)
Данные в Loki можно отправлять с помощью широкого спектра инструментов:
*   **Grafana Alloy:** Рекомендуемый Grafana Labs универсальный агент.
*   **Promtail:** "Классический" агент, специально созданный для Loki.
*   **Fluentd / Fluent Bit**
*   **Vector**
*   **Logstash**
*   **OpenTelemetry Collector**
*   Напрямую из приложения с помощью библиотек для разных языков программирования.

## Язык запросов LogQL

LogQL (Log Query Language) используется для запросов к логам в Loki. Он состоит из двух основных частей:

1.  **Селектор потока логов (Log Stream Selector):** Фильтрует логи по их меткам. Заключается в фигурные скобки `{}`.
    ```logql
    {namespace="default", container="app"}
    ```
2.  **Фильтр (Log Pipeline):** Обрабатывает и фильтрует строки логов, найденные селектором. Может содержать:
    *   **Фильтры по тексту:** `|= "error"` (содержит строку), `!= "debug"` (не содержит).
    *   **Фильтры по регулярным выражениям:** `|~ "status=5.."` (соответствует regex), `!~ "status=200"`.
    *   **Парсеры:** `| json`, `| logfmt` для извлечения полей из структурированных логов.
    *   **Фильтры по извлеченным полям:** После парсинга можно фильтровать по значениям полей, например, `| json | status_code >= 500`.
    *   **Агрегирующие функции:** `rate()`, `count_over_time()`, `sum()` для вычисления метрик на основе логов.

**Пример запроса:**
```logql
// Найти все логи из контейнера nginx, содержащие слово "api",
// распарсить их как JSON и показать только те, где время ответа (duration) больше 500мс.
{container="nginx"} |= "api" | json | duration > 500
```

**Пример создания метрики из логов:**
```logql
// Рассчитать долю логов с уровнем "error" от общего числа логов для приложения "my-app"
sum(rate({app="my-app", level="error"}[1m])) / sum(rate({app="my-app"}[1m]))
```

## Loki vs. Elasticsearch

| Характеристика | Loki | Elasticsearch |
| :--- | :--- | :--- |
| **Индексация** | Только метаданные (метки) | Полнотекстовая индексация всего документа |
| **Хранилище** | Значительно **меньше** (в 5-10 раз). | Большой объем из-за индекса. |
| **Стоимость** | **Низкая**. Требует меньше дискового пространства и CPU. | **Высокая**. Требует больше дисков и CPU для индексации. |
| **Скорость запросов (старые данные)** | **Медленнее** для неструктурированных логов. Требует сканирования объектов в хранилище ("grep-подобный" поиск). | **Быстрее** за счет полнотекстового индекса. |
| **Простота** | Проще в настройке и эксплуатации. | Сложнее, требует управления кластером, шардами, индексами. |
| **Язык запросов** | LogQL (похож на PromQL) | Lucene Query Syntax, KQL, Elasticsearch DSL |

**Вывод:** Loki является отличным выбором, если приоритетом является **экономия ресурсов и затрат**, а скорость доступа к очень старым логам не критична. Elasticsearch лучше подходит для сценариев, где требуется **быстрый полнотекстовый поиск** по большим объемам исторических данных.

### Практические соображения при выборе

Помимо технических характеристик, при выборе между Loki и Elasticsearch стоит учитывать следующие практические аспекты, основанные на опыте сообщества:

*   **Язык запросов и интерфейс (Query Language and Interface):** Если ваша команда уже активно использует Prometheus и Grafana, переход на Loki будет естественным. Использование LogQL, похожего на PromQL, и единый интерфейс Grafana для метрик и логов — ключевое преимущество, упрощающее работу и снижающее когнитивную нагрузку (не нужно переключаться между Grafana и Kibana).
*   **Стоимость и ресурсы (Cost and Resources):** Loki часто оказывается значительно экономичнее, особенно если нет жестких требований к скорости полнотекстового поиска по старым данным. Экономия достигается за счет меньших требований к дисковому пространству и вычислительным мощностям. Если оптимизация расходов на инфраструктуру является приоритетом, стоит провести сравнительное тестирование для вашего конкретного случая.
*   **Зрелость и сообщество (Maturity and Community):** Elasticsearch — более зрелый и консервативный продукт с огромным сообществом и исчерпывающей документацией. Найти решение проблемы для Elasticsearch почти всегда проще. Loki — более молодая технология, ее сообщество меньше, и иногда можно столкнуться с проблемами, ответы на которые придется искать в GitHub issues или находить самостоятельно.
*   **Профиль команды и проекта (Team and Project Profile):**
    *   **Elasticsearch** — это надежный, стабильный выбор для команд, которые предпочитают проверенные решения и где важна доступность экспертизы на рынке.
    *   **Loki** — отличный выбор для энтузиастов и команд, готовых к экспериментам и более глубокой настройке системы. Особенно хорошо подходит для новых проектов, где еще не сложилась экосистема логирования.
*   **Миграция (Migration):** Если у вас уже внедрен и отлажен стек на базе Elasticsearch, переход на Loki оправдан только при наличии весомых причин, таких как значительная экономия средств или стратегическое решение о переходе на экосистему Grafana.

## Инструменты командной строки (CLI)

*   **`logcli`:** Официальный инструмент для взаимодействия с Loki из терминала. Позволяет выполнять запросы LogQL, просматривать потоки логов и управлять кластером. Может быть полезен для автоматизации задач в shell-скриптах.
*   **`loki-tool`:** Утилита для управления кластером, валидации правил и работы с индексами.
*   **`loki-canary`:** Небольшая утилита для мониторинга производительности и здоровья кластера Loki. Она генерирует тестовые логи, отправляет их в Loki, а затем проверяет их доступность и целостность, собирая метрики о задержках.
