# PostgreSQL: Высокие нагрузки и масштабирование

Эта заметка основана на материалах лекции о методах масштабирования и оптимизации PostgreSQL для работы с большими данными и под высокими нагрузками.

---

## 1. Анализ производительности и тюнинг

Когда запросы начинают выполняться медленно, первым шагом является анализ плана выполнения.

### `EXPLAIN ANALYZE`

Команда `EXPLAIN ANALYZE` — основной инструмент для диагностики производительности запросов. Она не просто показывает план, который построил планировщик, но и выполняет запрос, отображая реальное время и ресурсы, затраченные на каждом этапе.

**Ключевые метрики для анализа:**
-   **`planning time`**: Время, затраченное на построение плана запроса.
-   **`execution time`**: Реальное время выполнения запроса.
-   **`cost`**: Оценочная стоимость выполнения. Первое число — стоимость начала, второе — общая.
-   **`rows`**: Оценочное количество строк.
-   **`actual time`**: Реальное время выполнения узла плана.
-   **`rows`**: Реальное количество строк, возвращенное узлом.

**Типы сканирования:**
-   **`Seq Scan` (Sequential Scan):** Полный перебор таблицы. Планировщик выбирает его, когда таблица маленькая или когда запрос должен вернуть большую часть строк, и использование индекса становится неэффективным.
-   **`Index Scan`:** Поиск по индексу. Эффективен для точечных запросов или выборок небольшого процента данных.
-   **`Bitmap Scan`:** Комбинированный метод. Сначала по индексу создается "битовая карта" строк, а затем эти строки последовательно считываются с диска. Это эффективнее, чем `Index Scan`, когда нужно выбрать значительное, но не подавляющее, количество строк.

### Индексы

Неправильное использование индексов — частая причина низкой производительности.

-   **Низкая кардинальность:** Индекс на поле с малым количеством уникальных значений (например, `boolean` или пол) почти бесполезен. `Seq Scan` будет быстрее.
-   **Типы индексов:**
    -   **B-Tree:** Стандартный, подходит для большинства операций (`=`, `>`, `<`, `BETWEEN`).
    -   **Hash:** Эффективен только для точных совпадений (`=`). Быстрее и компактнее B-Tree для таких задач.
    -   **GIN:** Идеален для поиска внутри составных типов, таких как `jsonb` или массивы.
    -   **BRIN (Block Range INdex):** Эффективен для очень больших таблиц, данные в которых физически упорядочены (например, по дате). Хранит минимальное и максимальное значение для диапазона блоков, что делает его очень компактным.

### Ключевые параметры конфигурации (`postgresql.conf`)

-   **`shared_buffers`**: Основной кэш PostgreSQL в оперативной памяти. Хранит страницы данных и индексов. Рекомендуемое значение — **25% от RAM** на выделенном сервере.
-   **`work_mem`**: Память, выделяемая для операций сортировки, хэширования и других сложных операций в рамках одного запроса. Этот буфер выделяется на каждую операцию, поэтому слишком большое значение может быстро исчерпать RAM при большом количестве одновременных запросов.
-   **`maintenance_work_mem`**: Память для служебных операций, таких как `VACUUM`, `CREATE INDEX`, `ALTER TABLE`. Увеличение этого параметра может значительно ускорить эти операции.
-   **`effective_cache_size`**: Подсказка планировщику о том, сколько памяти доступно для кэширования данных операционной системой. Это помогает ему точнее оценить стоимость `Index Scan` по сравнению с `Seq Scan`. Рекомендуемое значение — **50-75% от RAM**.

## 2. Стратегии масштабирования

### Вертикальное масштабирование

-   **Суть:** Увеличение ресурсов (CPU, RAM, диски) на одном сервере.
-   **Плюсы:** Простота. Не требует изменений в приложении.
-   **Минусы:** Дороговизна и наличие физического предела.

### Горизонтальное масштабирование

-   **Суть:** Распределение данных и нагрузки по нескольким серверам.
-   **Методы:** [Репликация](../Concepts/replication.md), [Шардирование](../Concepts/sharding.md), Партиционирование.
-   **Плюсы:** Потенциально бесконечная масштабируемость, использование более дешевого оборудования.
-   **Минусы:** Значительное усложнение архитектуры.

## 3. Встроенное партиционирование (Partitioning)

**Партиционирование** — это разделение одной большой таблицы на несколько мелких физических таблиц (партиций), которые остаются единой логической сущностью. Это встроенный механизм PostgreSQL, похожий на шардирование, но в пределах одного сервера.

**Преимущества:**
-   **`Partition Pruning`:** Планировщик автоматически отсекает партиции, которые не могут содержать запрашиваемые данные, что резко ускоряет запросы.
-   **Ускорение `VACUUM`:** Служебные операции выполняются на уровне партиций, что более эффективно.
-   **Управление данными:** Старые партиции можно легко архивировать или удалять (`DROP PARTITION`), что работает мгновенно.

### Типы партиционирования

1.  **`RANGE` (по диапазону):** Самый частый случай. Идеально подходит для временных рядов (например, партиционирование по месяцам или годам).

    ```sql
    CREATE TABLE orders (
        order_id bigserial,
        order_date date NOT NULL,
        ...
    ) PARTITION BY RANGE (order_date);

    -- Создание партиций для каждого года
    CREATE TABLE orders_2023 PARTITION OF orders
        FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

    CREATE TABLE orders_2024 PARTITION OF orders
        FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');
    ```

2.  **`LIST` (по списку):** Используется, когда ключ партиционирования имеет фиксированный набор значений.

    ```sql
    CREATE TABLE customers (
        customer_id bigserial,
        country_code text NOT NULL,
        ...
    ) PARTITION BY LIST (country_code);

    CREATE TABLE customers_europe PARTITION OF customers
        FOR VALUES IN ('DE', 'FR', 'PL');

    CREATE TABLE customers_asia PARTITION OF customers
        FOR VALUES IN ('CN', 'JP', 'KR');
    ```

3.  **`HASH` (по хэшу):** Равномерно распределяет данные по партициям на основе хэша от ключа. Используется, когда нет очевидного ключа для `RANGE` или `LIST`.

## 4. Шардирование и распределенные системы

Когда партиционирования на одном сервере недостаточно, переходят к распределенным системам.

-   **Citus Data:** Расширение для PostgreSQL, которое превращает его в распределенную базу данных. Использует концепцию **распределенных таблиц** и **таблиц-справочников**. Запросы координируются через мастер-узел и параллельно выполняются на воркер-узлах.

-   **Greenplum:** Массивно-параллельная СУБД на основе PostgreSQL, оптимизированная для аналитических нагрузок (OLAP).

-   **YugabyteDB:** Распределенная SQL база данных, совместимая с PostgreSQL на уровне протокола. Обеспечивает горизонтальную масштабируемость и отказоустойчивость "из коробки".

## 5. Интеграция с ClickHouse для аналитики

Для сложных аналитических запросов (OLAP) реляционные СУБД, такие как PostgreSQL (OLTP), часто неэффективны. Отличное решение — гибридный подход.

-   **PostgreSQL (OLTP):** Используется для транзакционных нагрузок: запись данных, частые точечные чтения и обновления.
-   **ClickHouse (OLAP):** Колоночная СУБД, созданная для сверхбыстрой аналитики.

**Схема интеграции:**

1.  **Запись данных:** Все транзакционные данные по-прежнему пишутся в PostgreSQL.
2.  **Передача данных:** Настраивается механизм репликации данных из PostgreSQL в ClickHouse. Популярный способ — через **Change Data Capture (CDC)** с использованием **Debezium** и **Kafka**.
    -   `Debezium` отслеживает изменения в WAL (Write-Ahead Log) PostgreSQL.
    -   Изменения публикуются в топик `Kafka`.
    -   ClickHouse, используя специальный движок `Kafka`, подписывается на этот топик и в реальном времени обновляет свои таблицы.
3.  **Выполнение запросов:**
    -   Быстрые транзакционные запросы (например, "получить заказ по ID") идут в PostgreSQL.
    -   Тяжелые аналитические запросы (например, "посчитать средний чек по всем категориям товаров за последний год") идут в ClickHouse и выполняются на порядки быстрее.

Этот подход позволяет использовать сильные стороны обеих систем, достигая высокой производительности как для транзакций, так и для аналитики.
