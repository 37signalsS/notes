# PostgreSQL: Обзор

## Определения

**PostgreSQL** — это мощная, объектно-реляционная система управления базами данных (ОРСУБД) с открытым исходным кодом. Она строго следует стандарту SQL, поддерживает транзакции ([ACID](../Concepts/acid.md)) и известна своей надежностью, функциональностью и производительностью.

**OLTP-система:** PostgreSQL относится к классу OLTP-систем (Online Transactional Processing), оптимизированных для частых коротких транзакций (создание заказа, обновление профиля). Для аналитических нагрузок (OLAP) на больших объёмах данных существуют специализированные решения, такие как [ClickHouse](../clickhouse.md).

Ключевые особенности:

- **Расширяемость:** Позволяет определять собственные типы данных, операторы и функции.
- **Объектно-реляционная модель:** Поддерживает наследование и сложные объекты.
- **Геопространственные данные:** Мощные возможности для работы с геоданными через расширение PostGIS.
- **Надежная репликация:** Предоставляет устойчивые механизмы [физической и логической репликации](./Concepts/replication.md).
- **ACID-гарантии:** Полная поддержка атомарности, согласованности, изоляции и долговечности транзакций.

## Основные концепции

- **Архитектура:** Внутренние механизмы работы, серверные процессы, жизненный цикл запроса и хранение данных. **[Подробнее](./Concepts/architecture.md)**.
- **Роли (Roles):** Фундаментальная сущность для управления доступом. В PostgreSQL нет разделения на "пользователей" и "группы" — все является ролями.
- **WAL (Write-Ahead Logging):** Механизм, гарантирующий надежность данных. Все изменения сначала записываются в журнал (WAL), и только потом в файлы данных. Это основа для транзакций ACID, [репликации](./Concepts/replication.md) и восстановления на момент времени (PITR).
- **MVCC и блокировки:** Механизмы управления параллельным доступом для изоляции транзакций. **[Подробнее](./Concepts/concurrency_and_locking.md)**.

## Ограничения PostgreSQL для аналитики

PostgreSQL часто называют "базой данных для 95% задач", но для аналитических нагрузок на больших объёмах данных существуют ограничения:

### Архитектурные ограничения

1. **Строковое хранение данных:**
   - Данные хранятся построчно, что неэффективно для агрегирующих запросов
   - При SELECT читаются все столбцы строки, даже если нужны некоторые
   - Отсутствие колоночного хранения снижает степень сжатия

2. **Узкое горлышко на запись:**
   - Ванильный PostgreSQL: один мастер (запись + чтение) + реплики (только чтение)
   - Вся запись идёт через один сервер
   - Синхронная репликация блокирует мастер до подтверждения от реплик

3. **Ограниченное количество соединений:**
   - Базовый лимит: ~100 подключений (можно увеличить до 400–500)
   - Каждое подключение — отдельный процесс ОС
   - Требуется пулер подключений (PgBouncer) для высоких нагрузок

4. **Масштабирование записи:**
   - Шардирование не встроено в ядро (требуются расширения: Citus, Greenplum)
   - Ре-шардирование — сложная и рискованная операция
   - Транзакции между шардами требуют двухфазного коммита

### Признаки необходимости миграции на OLAP

Рассмотрите переход на специализированное OLAP-хранилище (например, ClickHouse), если:

- **Медленные аналитические запросы:** Запросы с `GROUP BY`, `COUNT`, `SUM` на таблицах от 10 млн строк выполняются десятки секунд
- **Дашборды тормозят:** BI-отчёты загружаются дольше 5–10 секунд
- **Аналитика мешает продукту:** Тяжёлые SELECT повышают latency для обычных пользователей
- **Ночная аналитика:** Приходится запускать отчёты ночью, чтобы не мешать дневной нагрузке
- **Материализованные представления не справляются:** Обновление занимает минуты, блокирует запросы
- **Объём данных:** Таблицы превысили 1–10 ТБ и продолжают расти
- **Правило 80/20:** 20% запросов потребляют 80% CPU

**Важно:** До 1 ТБ данных и простых аналитических запросов PostgreSQL справляется при правильной индексации и партиционировании.
