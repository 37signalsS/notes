# Foreign Data Wrappers (FDW)

**Актуально для:** PostgreSQL 13–18 (postgres_fdw, file_fdw; возможности PG 19 помечены отдельно — на октябрь 2026 в Beta 4)

## Определения и терминология

* **Foreign Data Wrapper (FDW):** Механизм PostgreSQL, реализующий стандарт `SQL/MED` (SQL Management of External Data), который позволяет обращаться к внешним источникам данных (базам данных, файлам, выводу программ) через стандартный SQL-интерфейс.
* **Внешний сервер (Foreign Server):** Объект, описывающий параметры подключения к удалённому источнику (хост, порт, имя БД, таймауты).
* **Сопоставление пользователей (User Mapping):** Связь между локальным пользователем PostgreSQL и учётными данными (логин, пароль) на внешнем сервере.
* **Внешняя таблица (Foreign Table):** Прокси-объект, который выглядит как обычная таблица, но перенаправляет запросы к данным во внешней системе. Столбцы сопоставляются со столбцами удалённой таблицы **по имени**, а не по позиции; внешняя таблица может объявлять меньше столбцов или в другом порядке.
* **Опции FDW:** Параметры, задаваемые на уровне обёртки, сервера, сопоставления или внешней таблицы. Опция уровня таблицы переопределяет опцию уровня сервера (но только для этой таблицы).
* **Продвижение предиката (Predicate Pushdown):** Оптимизация, при которой условия фильтрации (`WHERE`) передаются на сторону внешнего источника для минимизации сетевого трафика.
* **Продвижение агрегации (Aggregation Pushdown):** Выполнение агрегатных функций (`SUM`, `AVG`, `COUNT`) на стороне источника (зависит от драйвера).
* **Асинхронное выполнение (Async Execution):** Параллельный запрос данных с нескольких внешних таблиц (параметр `async_capable`, PG 14+).
* **Параллельный коммит (Parallel Commit):** Одновременная фиксация транзакций на нескольких внешних серверах (параметр `parallel_commit`, PG 15+).

## Основные концепции

FDW превращает PostgreSQL в **федеративную базу данных** или **хаб данных**. В отличие от старого механизма `dblink`, FDW интегрирован в планировщик запросов, что позволяет оптимизировать сложные выборки, объединяющие локальные и удалённые данные, и стандартным синтаксисом обращаться к удалённым объектам.

Современные FDW (особенно `postgres_fdw`) поддерживают не только чтение (`SELECT`), но и **модификацию данных (`INSERT`, `UPDATE`, `DELETE`, `COPY`, `TRUNCATE`)**, что позволяет использовать PostgreSQL как единый интерфейс управления распределённой инфраструктурой.

При выполнении запроса PostgreSQL проходит следующие этапы:

1. **Планирование:** Оптимизатор определяет, какие части дерева запроса можно «протолкнуть» (pushdown) на внешний сервер.
2. **Выполнение:** Драйвер устанавливает соединение, преобразует план в нативный запрос источника (например, SQL для другой СУБД) и получает результаты.
3. **Агрегация:** Локальный узел `Foreign Scan` возвращает данные для дальнейшей обработки (например, JOIN с локальной таблицей или финальная сортировка).

Ключевое преимущество FDW по сравнению с ETL-процессами — **доступ к данным в реальном времени** без необходимости их копирования и поддержки сложных конвейеров по перекачке данных.

### Оптимизации (Pushdown)

Эффективность FDW сильно зависит от того, насколько «умным» является драйвер.

* **Без pushdown:** Драйвер забирает все данные из источника, и вся фильтрация, сортировка и агрегация происходят на стороне PostgreSQL. Это неэффективно и создаёт большой сетевой трафик.
* **С pushdown:** Драйвер преобразует части SQL-запроса в команды, понятные внешнему источнику:
  * `WHERE status = 'active'` превращается в аналогичный фильтр на стороне удалённой СУБД.
  * `ORDER BY` и `LIMIT` также могут быть выполнены удалённо.
  * `JOIN` между двумя внешними таблицами, находящимися на *одном и том же* внешнем сервере (и для одного сопоставления пользователей), выполняется на этом сервере.
  * **CASE (PG 15):** Выражения `CASE` продвигаются на удалённую сторону в `postgres_fdw`.
  * **Subquery Pushdown (PG 17):** Подзапросы `EXISTS` и `IN` передаются на удалённую сторону в `postgres_fdw`.

**Ограничение по безопасности:** по умолчанию на удалённую сторону отправляются только условия, использующие встроенные типы, операторы и функции. Условия с функциями из расширений проверяются локально после получения строк. Чтобы продвигать и их, перечислите расширения в серверной опции `extensions` (через запятую) — но только если они установлены в **совместимых версиях** на обоих серверах, иначе удалённые запросы могут давать сбои или неверные результаты.

## Требования и подготовка

### Сетевая связность

* **Доступ по сети:** PostgreSQL-сервер должен иметь доступ к IP-адресу и порту внешнего источника (например, 5432 для PostgreSQL, 3306 для MySQL).
* **Брандмауэр:** Правила фильтрации трафика (iptables/nftables, сетевые ACL) должны разрешать исходящие соединения с сервера-потребителя и входящие на сервере-источнике.
* **Таймаут подключения:** Для диагностики недоступных источников задавайте `connect_timeout` (опция libpq) в параметрах сервера, иначе соединение может висеть до системного таймаута TCP.

### Системные зависимости

* **Библиотеки драйверов:** Для работы расширений (кроме встроенных `postgres_fdw` и `file_fdw`) могут потребоваться клиентские библиотеки соответствующей СУБД в ОС: `libpq-dev` (Debian/Ubuntu) / `postgresql-devel` (RHEL) для PostgreSQL, `libmariadb-dev` / `mariadb-devel` для `mysql_fdw`, `freetds-dev` / `freetds-devel` (FreeTDS) для `tds_fdw`.
* **Установка расширения:** Файлы расширения должны присутствовать в директории `SHAREDIR/extension` инстанса PostgreSQL (для пакетов из PGDG/репозиториев ОС это так; при сборке из исходников — `make install`).

### Права доступа

* **Права в БД:** `CREATE EXTENSION postgres_fdw` и `CREATE SERVER` требуют прав **суперпользователя** (либо `USAGE` на обёртке, явно выданного суперпользователем).
* **IMPORT FOREIGN SCHEMA:** Требуется `USAGE` на внешнем сервере и `CREATE` в целевой локальной схеме.
* **Права на источник:** Учётная запись из `USER MAPPING` должна обладать правами `SELECT` (и `INSERT/UPDATE/DELETE`, если планируется модификация) на удалённые объекты.

## Практические сценарии

### Алгоритм настройки и валидации (postgres_fdw)

1. **Установка расширения:**
    ```sql
    CREATE EXTENSION postgres_fdw;
    -- → CREATE EXTENSION
    ```

2. **Определение внешнего сервера:**
    Рекомендуется сразу настраивать параметры производительности и безопасности. Значения по умолчанию опций указаны в скобках.
    ```sql
    CREATE SERVER remote_server
        FOREIGN DATA WRAPPER postgres_fdw
        OPTIONS (
            host '192.168.1.10',
            port '5432',
            dbname 'remote_db',
            connect_timeout '10',    -- таймаут подключения, сек (нет)
            fetch_size '1000',       -- строк за один сетевой запрос (100)
            batch_size '100',        -- строк за одну вставку (1; PG 14+)
            async_capable 'on',      -- параллельные запросы к нескольким таблицам (off; PG 14+)
            parallel_commit 'on',    -- параллельный коммит транзакций (off; PG 15+)
            parallel_abort 'on',     -- параллельный откат транзакций (off; PG 16+)
            use_remote_estimate 'on' -- запрашивать стоимость у удалённого сервера (off)
        );
    ```
    Любые опции, принимаемые libpq (например, `sslmode`, `connect_timeout`), можно указывать в `OPTIONS` сервера — исключения: `user`/`password` (задаются в user mapping) и `client_encoding` (наследуется от локальной кодировки).

3. **Сопоставление пользователей:**
    ```sql
    CREATE USER MAPPING FOR current_user
        SERVER remote_server
        OPTIONS (user 'app_user', password 'secure_password');
    ```

4. **Создание и импорт внешних таблиц:**
    ```sql
    -- Автоматический импорт всей схемы
    IMPORT FOREIGN SCHEMA public
    FROM SERVER remote_server
    INTO local_schema;

    -- Проверка наличия таблицы
    \dE local_schema.remote_table
    ```
    Параметры импорта (в `OPTIONS` команды `IMPORT FOREIGN SCHEMA`): `import_collate` (включать `COLLATE`, по умолчанию `true`), `import_default` (включать выражения `DEFAULT`, `false` — осторожно с `nextval()`: она может вычисляться иначе локально), `import_generated` (включать `GENERATED`, `true`), `import_not_null` (включать `NOT NULL`, `true`). Ограничения, кроме `NOT NULL`, **не импортируются** никогда — выражение CHECK может вычисляться по-разному на двух серверах; при необходимости добавляйте их вручную. Партицированные таблицы и наследники импортируются только при явном перечислении в `LIMIT TO`, иначе автоматически исключаются.

5. **Валидация подключения:**
    ```sql
    SELECT count(*) FROM local_schema.remote_table;
    --  count
    -- -------
    --   5000
    -- (1 row)
    ```

### Массовая вставка (Batching) и COPY

Параметр `batch_size` (PG 14+) группирует несколько `INSERT` в один запрос, что радикально снижает нагрузку на сеть. Фактический размер пакета ограничен лимитом libpq в 65535 параметров на запрос: при `columns × batch_size > 65535` размер пакета автоматически уменьшается. С PG 16 `batch_size` также применяется к `COPY` во внешние таблицы (там пакет ограничен 1000 строками).

```sql
COPY local_schema.remote_table FROM '/path/to/data.csv' WITH (FORMAT csv);
-- → COPY N
```

### Обновление данных

`postgres_fdw` поддерживает `INSERT`, `UPDATE`, `DELETE`, `COPY` и `TRUNCATE` (последний — с PG 14) на внешних таблицах.

**Важно про `ON CONFLICT`:** поддерживается только `ON CONFLICT DO NOTHING` (без спецификации вывода по уникальному индексу; удалённый сервер должен быть PostgreSQL 9.5+). Конструкция `ON CONFLICT DO UPDATE` (UPSERT) **не поддерживается** `postgres_fdw` ни в одной версии до 18 включительно — попытка использовать её вызовет ошибку. Для UPSERT-логики применяйте `MERGE` (PG 15+) локально или `dblink`, либо обновляйте строки явным `UPDATE` после проверки существования.

```sql
INSERT INTO remote_orders (id, status)
VALUES (101, 'shipped')
ON CONFLICT DO NOTHING;
-- → INSERT 0 1
```

### Чтение файлов и вывода программ (file_fdw)

`file_fdw` (входит в состав PostgreSQL) даёт **только читаемый** доступ к файлам в файловой системе сервера или к выводу программ — в формате, совместимом с `COPY FROM`. Типичное применение для SRE — запросы к CSV-логам PostgreSQL и к выводу диагностических команд.

```sql
CREATE EXTENSION file_fdw;

CREATE SERVER pglog FOREIGN DATA WRAPPER file_fdw;

CREATE FOREIGN TABLE pglog (
  log_time timestamp(3) with time zone,
  user_name text,
  database_name text,
  error_severity text,
  message text
) SERVER pglog
OPTIONS (filename 'log/postgresql.csv', format 'csv', header 'true');

SELECT log_time, message FROM pglog WHERE error_severity = 'ERROR';
```

* Опции: `filename` **или** `program` (только одна из двух), `format`, `header`, `delimiter`, `quote`, `escape`, `null`, `default`, `encoding`, `on_error`, `reject_limit`, `log_verbosity` (три последние — PG 18); для столбцов — `force_not_null`/`force_null`. Опция `FORCE_QUOTE` **не поддерживается**.
* Относительные пути `filename` отсчитываются от каталога данных (`PGDATA`).
* `program` выполняется **оболочкой**; никогда не подставляйте в команду недоверенные данные — используйте фиксированную строку команды.
* Смена табличных опций требует прав суперпользователя либо членства в `pg_read_server_files` (для `filename`) или `pg_execute_server_program` (для `program`).
* `EXPLAIN` для такой таблицы показывает имя файла/программы и размер файла.
* При работе с ротируемыми логами предусмотрите обработку ротации (внешняя таблица указывает на конкретный файл).

### Примеры популярных FDW

* **`postgres_fdw`:** Официальный драйвер для PostgreSQL (входит в состав). Поддерживает pushdown, пакетную вставку, параллельные сканирования, `ON CONFLICT DO NOTHING`.
    - **Хаб данных:** Получение данных из нескольких баз без сторонних инструментов.
    - **Шардинг:** Распределение одной большой базы на несколько инстансов (вертикальная или горизонтальная логика); детали — в [Масштабирование PostgreSQL](../Concepts/scaling.md).
    - **Миграция:** Бесшовная миграция данных или объединение разрозненных БД.
* **`file_fdw`:** Чтение CSV/текстовых файлов и вывода программ на сервере (см. сценарий выше).
* **`mysql_fdw` / `tds_fdw`:** Интеграция с MySQL/MariaDB и SQL Server (Sybase); требуют клиентских библиотек (`libmariadb-dev`, FreeTDS).
* **`oracle_fdw`:** Драйвер для связи с Oracle DB. Требует установленного `Oracle Instant Client`.
* **`sqlite_fdw`:** Легковесный драйвер для работы с локальными файлами SQLite.
* **`clickhouse_fdw`:** Интеграция с ClickHouse (подробнее в **[Интеграция PostgreSQL и ClickHouse](./clickhouse.md)**).
* **`multicorn2`:** Наследник Multicorn, позволяющий писать FDW на Python 3 (сам Multicorn — Python 2, не развивается; совместимость multicorn2 с мажорными версиями PG следует проверять перед установкой).
* **`dblink`:** Не FDW, а старый механизм ручных запросов к удалённым серверам; сохраняется для случаев, где FDW неудобен (например, динамические подключения в коде).

### Анализ производительности (`EXPLAIN`)

При анализе плана запроса (`EXPLAIN VERBOSE`) к внешней таблице появляется узел `Foreign Scan`.

```sql
EXPLAIN (VERBOSE, COSTS FALSE) SELECT * FROM remote_orders WHERE id = 10;
```

```text
                      QUERY PLAN
------------------------------------------------------
 Foreign Scan on public.remote_orders
   Output: id, customer_id, order_date
   Remote SQL: SELECT id, customer_id, order_date FROM public.orders WHERE id = 10
```

Ключевая строка — `Remote SQL`. Она показывает, какой именно запрос был отправлен на внешний сервер. Если в `Remote SQL` присутствует условие `WHERE`, значит, predicate pushdown сработал успешно.

**Стоимостные опции** (уровень сервера; `use_remote_estimate` — и уровня таблицы):

* `use_remote_estimate` (по умолчанию `false`) — запрашивать у удалённого сервера `EXPLAIN` и его оценки числа строк и стоимости. Даёт точные планы, но каждое планирование стоит одного сетевого раунд-трипа (заметно повышает `Planning Time`).
* `fdw_startup_cost` (по умолчанию `100`) — надбавка к startup cost сканирования: установка соединения, разбор и планирование на удалённой стороне.
* `fdw_tuple_cost` (по умолчанию `0.2`; до PG 17 был `0.01`) — надбавка к стоимости на строку: сетевые задержки. Повышайте при высокой латентности канала, понижайте в локальных сетях.
* `analyze_sampling` (`auto`) — метод выборки при `ANALYZE` внешней таблицы: `off` (перенос всех данных локально), `random`, `system`, `bernoulli`, `auto` (рекомендуемый метод автоматически).

Без локальной статистики (`pg_class.reltuples = -1`, число строк неизвестно) планировщик работает вслепую: соединение уходит на удалённый сервер вместо локального Hash Join или наоборот. Обновление статистики — `ANALYZE` по внешней таблице (выборка строк с удалённого сервера); автоматический анализ (autovacuum) для внешних таблиц **не работает** — запускайте `ANALYZE` по расписанию. Механика подробно разобрана в [Планировщик: внешние таблицы](../Concepts/planner_internals.md).

### Сводка возможностей по версиям PostgreSQL

| Версия | Изменения postgres_fdw / FDW |
| :--- | :--- |
| **PG 14** | `batch_size` (пакетная вставка), `async_capable` (параллельное сканирование нескольких внешних таблиц), `TRUNCATE` внешних таблиц, `IMPORT FOREIGN SCHEMA ... LIMIT TO`, функции `postgres_fdw_get_connections()`, `postgres_fdw_disconnect()` / `postgres_fdw_disconnect_all()`, автоматическое переподключение при перезапуске удалённого сервера |
| **PG 15** | `parallel_commit`, pushdown выражений `CASE`, GUC `postgres_fdw.application_name` (с escape-последовательностями `%a`, `%c`, `%C`, `%u`, `%d`, `%p`) |
| **PG 16** | `parallel_abort`, `analyze_sampling` (эффективный `ANALYZE`), пакетирование `COPY` во внешние таблицы (`batch_size`, лимит 1000 строк), триггеры `TRUNCATE` на внешних таблицах |
| **PG 17** | Pushdown подзапросов `EXISTS` и `IN`, дефолт `fdw_tuple_cost` повышен с `0.01` до `0.2`, именованные wait events `PostgresFdw*` (тип `Extension`), pushdown join-квалификаций |
| **PG 18** | `use_scram_passthrough` (SCRAM pass-through — без паролей в каталогах), расширенный вывод `postgres_fdw_get_connections()` (`used_in_xact`, `closed`, `user_name`, `remote_backend_pid`), `CREATE FOREIGN TABLE ... LIKE`; `file_fdw`: опции `on_error`, `reject_limit`, `log_verbosity` |
| **PG 19 (devel)** | `import_stats` (импорт готовой удалённой статистики при `ANALYZE`), подписки через postgres_fdw-сервер (`CREATE SUBSCRIPTION ... SERVER`), pushdown `INNER JOIN` с возвращающими множества функциями; `ON CONFLICT DO SELECT` — но `DO UPDATE` по-прежнему не поддерживается |

## Устранение неисправностей

| Симптом | Вероятная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `connection timeout` / зависание запроса | Недоступность порта или хоста, правила брандмауэра, отсутствие `connect_timeout` | `pg_stat_activity` (wait event `PostgresFdwConnect`), `nc -zv host port` с сервера PostgreSQL | Открыть порт, задать `connect_timeout` в опциях сервера |
| `permission denied` | Нет прав у пользователя в `USER MAPPING` на удалённой стороне или нет `USAGE` на сервере локально | Проверить гранты на удалённых объектах, `\deu+` | Выдать права на удалённой стороне / `GRANT USAGE ON FOREIGN SERVER` |
| `schema mismatch` / ошибки типов | Структура внешней таблицы устарела или типы/collation не совпадают с удалённой таблицей | Сравнить `\dE+` с удалённой `\d` | Повторить `IMPORT FOREIGN SCHEMA`; держать типы и collation идентичными |
| `function does not exist` на удалённой стороне | Встроенная функция, появившаяся после версии удалённого сервера, была «отправлена» на него | Текст ошибки; `EXPLAIN VERBOSE` (`Remote SQL`) | Обернуть внешнюю таблицу в подзапрос с `OFFSET 0` (optimization fence) и применять функцию локально |
| Индекс не используется / Seq Scan | Устаревшая локальная статистика внешней таблицы (`reltuples = -1`) | `SELECT reltuples FROM pg_class WHERE relname = '...'` | `ANALYZE` по внешней таблице; `use_remote_estimate` |
| `Planning Time` вырос после включения `use_remote_estimate` | Удалённый `EXPLAIN` на каждом планировании | `EXPLAIN (ANALYZE)` — сравнение `Planning Time` | `use_remote_estimate` только для проблемных таблиц; `ANALYZE` + `import_stats` (PG 19) |
| Данные в транзакции «не меняются» на удалённой стороне | Удалённая транзакция открывается на уровне `REPEATABLE READ` (или `SERIALIZABLE`), поэтому последовательные запросы в одной локальной транзакции видят один снимок даже при `READ COMMITTED` | Логика приложения | Учитывать семантику снимка; при необходимости коммитить транзакцию между запросами |
| Ошибки в представлениях/триггерах на удалённой стороне | Удалённая сессия FDW имеет `search_path = pg_catalog` | Логи удалённого сервера | Schema-квалифицировать имена в функциях представлений/триггеров или задать `SET search_path` в `CREATE FUNCTION` |
| `COPY FREEZE` на внешней таблице | `COPY FREEZE` запрещён для внешних таблиц (PG 18+) | Текст ошибки | `COPY` без `FREEZE` |
| Исчерпание подключений на удалённом сервере | Каждая локальная сессия держит соединение на каждое сопоставление пользователей | `pg_stat_activity` на удалённом сервере; `postgres_fdw_get_connections(true)` | `keep_connections 'off'` для короткоживущих сессий, `postgres_fdw_disconnect_all()`, пулер |

## Лучшие практики

1. **Оценивайте стоимость правильно:** для критичных запросов включите `use_remote_estimate` на уровне конкретных таблиц (не сервера целиком — раунд-трип на каждое планирование); для остальных собирайте локальную статистику регулярным `ANALYZE`.
2. **Настраивайте `fdw_tuple_cost` под канал:** при WAN/высокой латентности повышайте (`0.5`–`1.0`), чтобы планировщик предпочитал получать меньше строк; в локальной сети можно понижать.
3. **Управляйте соединениями:** по умолчанию соединения к внешнему серверу сохраняются на время сессии (`keep_connections 'on'`). Для короткоживущих сессий — `keep_connections 'off'` (соединение закрывается в конце транзакции). Явно закрыть: `SELECT postgres_fdw_disconnect('имя_сервера');` / `postgres_fdw_disconnect_all();`.
4. **Следите за подключениями на удалённой стороне:** каждая локальная сессия × каждое сопоставление пользователей = одно соединение. При большом числе локальных бэкендов это давит на `max_connections` удалённого сервера — учитывайте это в ёмкостном планировании.
5. **Мониторьте wait events:** тип `Extension` с событиями `PostgresFdwConnect` (ожидание подключения), `PostgresFdwGetResult` (ожидание результата запроса), `PostgresFdwCleanupResult` (ожидание отката транзакции на удалённой стороне). Анализ времени выполнения — через `pg_stat_statements`.
6. **Аккуратно с `extensions`:** продвигайте функции расширений на удалённую сторону только при гарантированно идентичных версиях расширений на обоих серверах.
7. **Аккуратно с паролями:** пароль в `USER MAPPING` виден суперпользователю в каталогах; для непривилегированных пользователей представление `pg_user_mappings` маскирует опции. Предпочтительнее SSL-сертификаты (`sslcert`/`sslkey` в user mapping — только для суперпользователя) или SCRAM pass-through (`use_scram_passthrough`, PG 18).
8. **Очистка:** удаляйте зависимости в обратном порядке — `DROP FOREIGN TABLE`, `DROP USER MAPPING`, `DROP SERVER`, `DROP EXTENSION postgres_fdw` (последнее каскадно удаляет зависящие внешние таблицы при `CASCADE`).

## Дополнительная информация

### Ограничения и риски

* **Производительность сети:** FDW чувствителен к задержкам (latency) и пропускной способности. Большие JOIN-ы между внешними таблицами разных серверов могут работать медленно, если данные пересылаются на локальный сервер для обработки.
* **Транзакции и 2PC:** `postgres_fdw` **не поддерживает** подготовку удалённых транзакций к двухфазному коммиту (`PREPARE TRANSACTION`). Удалённая транзакция коммитится/откатывается вместе с локальной, но без атомарности 2PC: при сбое между коммитом на удалённой стороне и коммитом локально состояние может разойтись. Критичные сценарии проектируйте с учётом этого (идемпотентные повторы, проверка состояния).
* **Уровень изоляции:** удалённая транзакция использует `SERIALIZABLE`, если локальная `SERIALIZABLE`, иначе — `REPEATABLE READ`. Это обеспечивает консистентность снимка при множественных сканированиях, но удивляет при локальном `READ COMMITTED`: последовательные запросы в одной транзакции видят одни и те же данные удалённой таблицы.
* **Лимиты подключений:** каждая сессия, обращающаяся к FDW, удерживает открытое соединение с удалённым сервером (на каждое сопоставление пользователей). Используйте `keep_connections 'off'` или PgBouncer для экономии ресурсов.
* **`ONLY` не действует:** опция `ONLY` в `SELECT`, `UPDATE`, `DELETE` и `TRUNCATE` игнорируется при доступе к внешней таблице.
* **Совместимость версий:** `postgres_fdw` работает с удалёнными серверами начиная с PostgreSQL 8.3 (только чтение — с 8.1). Но: встроенная функция, появившаяся в более новой версии, чем удалённый сервер, может быть отправлена на него и вызвать ошибку «function does not exist» — обход через подзапрос с `OFFSET 0`.
* **Типы и collation:** настоятельно рекомендуется объявлять столбцы внешней таблицы с точно теми же типами и collation, что и на удалённой стороне — иначе удалённый сервер может интерпретировать условия иначе локального, с трудновыявляемыми аномалиями.

### Безопасность

* **Шифрование трафика:** Используйте SSL для защиты данных при передаче между серверами:
    ```sql
    ALTER SERVER remote_server OPTIONS (ADD sslmode 'require');
    ```
* **Хранение паролей:** Пароли в `USER MAPPING` хранятся в системных каталогах и доступны суперпользователю (представление `pg_user_mappings` маскирует их для остальных).
    * **Рекомендация:** SSL-сертификаты для аутентификации вместо паролей (`sslcert`/`sslkey` в user mapping; создавать/менять такие сопоставления может только суперпользователь).
    * **SCRAM pass-through (PG 18):** опция `use_scram_passthrough` позволяет использовать SCRAM-хеши вместо паролей в открытом виде. Требования: удалённый сервер запрашивает `scram-sha-256`; идентичные SCRAM-секреты (соль и итерации) у пользователей на всех хостах; текущая сессия тоже должна подключаться по SCRAM.
    * **Параметр `password_required 'false'`:** если на удалённой стороне настроена доверенная аутентификация (`trust`, `cert`), можно отключить требование пароля. Устанавливать может **только суперпользователь**, и только для конкретного сопоставления — не для роли `PUBLIC`: иначе любой пользователь может эскалировать привилегии до системного пользователя PostgreSQL (CVE-2007-3278, CVE-2007-6601).
* **Удалённое окружение:** сессии FDW открываются с `search_path = pg_catalog`, `TimeZone = UTC`, `DateStyle = ISO`, `IntervalStyle = postgres`, `extra_float_digits = 3`. Это защищает от подмены объектов, но ломает функции, выполняемые на удалённой стороне через представления/триггеры, если они не schema-квалифицированы.

### Сравнение FDW и ETL-процессов

| Характеристика | Foreign Data Wrapper (FDW) | Extract, Transform, Load (ETL) |
| :--- | :--- | :--- |
| **Доступ к данным** | В реальном времени (real-time) | С задержкой (пакетный) |
| **Хранение данных** | Источник (без дублирования) | Копируются в целевую БД (DWH) |
| **Трансформация** | Ограничена мощностью SQL | Сложные преобразования (Python/Java) |
| **Нагрузка** | В момент выполнения запроса | Во время работы ETL-задания |
| **Сценарий** | Оперативная аналитика, Master Data | Хранилища данных, историческая отчетность |

### Диагностические запросы

```sql
-- Список всех внешних серверов
SELECT * FROM pg_foreign_server;

-- Просмотр сопоставлений пользователей (пароли видны только суперпользователю/владельцу)
SELECT * FROM pg_user_mappings;

-- Открытые FDW-соединения текущей сессии (с проверкой статуса, Linux)
SELECT * FROM postgres_fdw_get_connections(true);
--  server_name | user_name | valid | used_in_xact | closed | remote_backend_pid

-- Явно закрыть соединения к серверу / ко всем серверам
SELECT postgres_fdw_disconnect('remote_server');
SELECT postgres_fdw_disconnect_all();

-- Текущие активные подключения к внешним серверам
SELECT pid, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'Extension'
  AND wait_event LIKE 'PostgresFdw%';
```

В psql: `\dE` — внешние таблицы, `\des` — внешние серверы, `\deu` — сопоставления пользователей (показывает пароли — будьте осторожны), `\dew` — обёртки данных.
