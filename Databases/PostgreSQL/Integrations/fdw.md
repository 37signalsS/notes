# Foreign Data Wrappers (FDW)

## 1. Определения

* **Foreign Data Wrapper (FDW):** Механизм в PostgreSQL, который позволяет обращаться к внешним источникам данных так, как будто они являются обычными таблицами внутри самой базы данных.
* **Внешняя таблица (Foreign Table):** "Виртуальная" таблица в PostgreSQL, которая служит прокси для данных, физически хранящихся во внешней системе (другой СУБД, файле, веб-сервисе).
* **Продвижение предиката (Predicate Pushdown):** Оптимизация, при которой FDW-драйвер не извлекает все данные из источника, а "продвигает" условия фильтрации (например, из `WHERE`) на сторону внешней системы. Это позволяет отфильтровать данные на источнике и передавать по сети только необходимый результат.
* **Продвижение агрегации (Aggregation Pushdown):** Аналогичная оптимизация для агрегатных функций (`COUNT`, `SUM` и др.), которые могут вычисляться на стороне внешней системы.

## 2. Основные концепции

FDW является стандартным расширением PostgreSQL, реализующим часть стандарта `SQL/MED` (SQL Management of External Data). Этот механизм превращает PostgreSQL в **федеративную базу данных** или **хаб данных**, который может служить единой точкой входа для запросов к множеству разнородных систем.

При выполнении запроса к внешней таблице PostgreSQL делегирует часть операций FDW-драйверу:

1. **Планирование:** Оптимизатор PostgreSQL анализирует запрос и решает, какие его части можно безопасно выполнить на стороне внешнего источника (pushdown).
2. **Выполнение:** FDW-драйвер подключается к внешней системе, выполняет оптимизированный запрос (например, `SELECT ... WHERE ...` к другой СУБД или HTTP-запрос к API), получает данные и итеративно возвращает их в PostgreSQL.
3. **Агрегация:** PostgreSQL получает результаты и выполняет оставшиеся операции (например, `JOIN` с локальными таблицами или функции, которые не удалось "продвинуть").

Ключевое преимущество FDW по сравнению с ETL-процессами — **доступ к данным в реальном времени** без необходимости их копирования и поддержки сложных конвейеров по перекачке данных.

### Оптимизации (Pushdown)

Эффективность FDW сильно зависит от того, насколько "умным" является драйвер.

* **Без pushdown:** Драйвер забирает все данные из источника, и вся фильтрация, сортировка и агрегация происходят на стороне PostgreSQL. Это неэффективно и создает большой сетевой трафик.
* **С pushdown:** Драйвер преобразует части SQL-запроса в команды, понятные внешнему источнику.
  * `WHERE status = 'active'` превращается в аналогичный фильтр на стороне удаленной СУБД.
  * `ORDER BY` и `LIMIT` также могут быть выполнены удаленно.
  * `JOIN` между двумя внешними таблицами, находящимися на *одном и том же* внешнем сервере, может быть выполнен на этом сервере.

## 3. Практические сценарии

### 3.1. Структура настройки

1. **`CREATE EXTENSION ...`:** Установка FDW-драйвера.

    ```sql
    CREATE EXTENSION postgres_fdw;
    ```

2. **`CREATE SERVER ...`:** Определение подключения к внешнему источнику.

    ```sql
    CREATE SERVER my_remote_pg_server
        FOREIGN DATA WRAPPER postgres_fdw
        OPTIONS (host '192.168.1.10', port '5432', dbname 'remote_db');
    ```

3. **`CREATE USER MAPPING ...`:** Сопоставление локального пользователя PostgreSQL с учетными данными для входа на внешний сервер.

    ```sql
    CREATE USER MAPPING FOR local_user
        SERVER my_remote_pg_server
        OPTIONS (user 'remote_user', password 'secret');
    ```

4. **`CREATE FOREIGN TABLE ...`:** Создание внешней таблицы.

    ```sql
    CREATE FOREIGN TABLE remote_orders (
        id INT,
        customer_id INT,
        order_date DATE
    )
    SERVER my_remote_pg_server
    OPTIONS (schema_name 'public', table_name 'orders');
    ```

    В качестве альтернативы можно импортировать схему целиком:

    ```sql
    IMPORT FOREIGN SCHEMA public
    FROM SERVER my_remote_pg_server
    INTO local_schema;
    ```

### 3.2. Примеры FDW-драйверов

* **`postgres_fdw`:** "Золотой стандарт" для подключения к другим базам PostgreSQL. Поддерживает полный pushdown предикатов, агрегаций и `JOIN`.
* **`file_fdw`:** Встроенный драйвер для чтения данных из файлов (CSV, TSV) на сервере, где работает PostgreSQL. Не поддерживает pushdown.
* **`mysql_fdw`:** Для подключения к MySQL/MariaDB. Поддерживает pushdown предикатов.
* **[Интеграция с ClickHouse](./clickhouse.md):** Используется `clickhouse_fdw` для аналитических запросов.
* **Драйверы для NoSQL:** Существуют драйверы для MongoDB, Redis, Elasticsearch.
* **`www_fdw`:** Для выполнения HTTP-запросов к веб-сервисам.
* **`multicorn`:** Фреймворк для быстрого создания собственных FDW-драйверов на Python.

### 3.3. Анализ производительности (`EXPLAIN`)

При анализе плана запроса (`EXPLAIN VERBOSE`) к внешней таблице появляется узел `Foreign Scan`.

```sql
EXPLAIN (VERBOSE, COSTS FALSE) SELECT * FROM remote_orders WHERE id = 10;
```

```
                      QUERY PLAN
------------------------------------------------------
 Foreign Scan on public.remote_orders
   Output: id, customer_id, order_date
   Remote SQL: SELECT id, customer_id, order_date FROM public.orders WHERE id = 10
```

Ключевая строка — `Remote SQL`. Она показывает, какой именно запрос был отправлен на внешний сервер. Если в `Remote SQL` присутствует условие `WHERE`, значит, predicate pushdown сработал успешно.

## 4. Дополнительная информация

### Ограничения и риски

* **Производительность сети:** FDW чувствителен к задержкам в сети.
* **Транзакции:** PostgreSQL не предоставляет двухфазный коммит (2PC) для FDW "из коробки". Транзакция, затрагивающая и локальные, и внешние таблицы, не будет атомарной между системами.
* **Лимиты подключений:** Множественные запросы к внешним таблицам могут исчерпать лимит соединений на удаленном сервере. Рекомендуется использовать пулер соединений (например, PgBouncer) перед PostgreSQL, если он выступает в роли хаба.
* **Качество драйвера:** Эффективность FDW напрямую зависит от качества реализации конкретного драйвера и его способности к pushdown-оптимизациям.

### FDW vs ETL

| Характеристика | Foreign Data Wrapper (FDW) | Extract, Transform, Load (ETL) |
| :--- | :--- | :--- |
| **Доступ к данным** | В реальном времени (real-time) | С задержкой (пакетный) |
| **Хранение данных** | Данные остаются в источнике | Данные копируются в хранилище |
| **Сложность** | Низкая, настраивается через SQL | Высокая, требует отдельных инструментов (Airflow, NiFi) |
| **Нагрузка** | В момент запроса | В момент выполнения ETL-процесса |
| **Сценарий** | Быстрая интеграция, real-time аналитика | Построение DWH, сложные преобразования |
