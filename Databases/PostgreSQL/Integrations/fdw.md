# Foreign Data Wrappers (FDW)

## Определения

* **Foreign Data Wrapper (FDW):** Механизм в PostgreSQL, реализующий стандарт `SQL/MED` (SQL Management of External Data), который позволяет обращаться к внешним источникам данных (базам данных, файлам, API) через стандартный SQL-интерфейс.
* **Внешний сервер (Foreign Server):** Объект в PostgreSQL, описывающий параметры подключения к удаленному источнику (хост, порт, имя БД, таймауты).
* **Сопоставление пользователей (User Mapping):** Связь между локальным пользователем PostgreSQL и учетными данными (логин, пароль) на внешнем сервере.
* **Внешняя таблица (Foreign Table):** Прокси-объект, который выглядит как обычная таблица, но перенаправляет запросы к данным во внешней системе.
* **Продвижение предиката (Predicate Pushdown):** Оптимизация, при которой условия фильтрации (`WHERE`) передаются на сторону внешнего источника для минимизации сетевого трафика.
* **Продвижение агрегации (Aggregation Pushdown):** Выполнение агрегатных функций (`SUM`, `AVG`, `COUNT`) на стороне источника.
* **Асинхронное выполнение (Async Execution):** Возможность параллельного запроса данных с нескольких внешних серверов (параметр `async_capable` с PG 14).
* **Параллельный коммит (Parallel Commit):** Возможность одновременной фиксации транзакций на нескольких внешних серверах (с PG 15).

## Основные концепции

FDW превращает PostgreSQL в **федеративную базу данных** или **хаб данных**. В отличие от старого механизма `dblink`, FDW интегрирован в планировщик запросов, что позволяет оптимизировать сложные выборки, объединяющие локальные и удаленные данные.

Современные FDW (особенно `postgres_fdw`) поддерживают не только чтение (SELECT), но и **модификацию данных (INSERT, UPDATE, DELETE)**, что позволяет использовать PostgreSQL как единый интерфейс управления распределенной инфраструктурой.

При выполнении запроса PostgreSQL проходит следующие этапы:

1. **Планирование:** Оптимизатор определяет, какие части дерева запроса можно «протолкнуть» (pushdown) на внешний сервер.
2. **Выполнение:** Драйвер устанавливает соединение, преобразует план в нативный запрос источника (например, SQL для другой СУБД) и получает результаты.
3. **Агрегация:** Локальный узел `Foreign Scan` возвращает данные для дальнейшей обработки (например, JOIN с локальной таблицей или финальная сортировка).

Ключевое преимущество FDW по сравнению с ETL-процессами — **доступ к данным в реальном времени** без необходимости их копирования и поддержки сложных конвейеров по перекачке данных.

### Оптимизации (Pushdown)

Эффективность FDW сильно зависит от того, насколько "умным" является драйвер.

* **Без pushdown:** Драйвер забирает все данные из источника, и вся фильтрация, сортировка и агрегация происходят на стороне PostgreSQL. Это неэффективно и создает большой сетевой трафик.
* **С pushdown:** Драйвер преобразует части SQL-запроса в команды, понятные внешнему источнику.
  * `WHERE status = 'active'` превращается в аналогичный фильтр на стороне удаленной СУБД.
  * `ORDER BY` и `LIMIT` также могут быть выполнены удаленно.
  * `JOIN` между двумя внешними таблицами, находящимися на *одном и том же* внешнем сервере, может быть выполнен на этом сервере.
  * **Subquery Pushdown (PG 17):** Поддержка передачи подзапросов `EXISTS` и `IN` на удаленную сторону в `postgres_fdw`.

## Практические сценарии

### Алгоритм настройки

1. **`CREATE EXTENSION ...`:** Установка FDW-драйвера в текущую базу данных.

    ```sql
    CREATE EXTENSION postgres_fdw;
    ```

2. **`CREATE SERVER ...`:** Определение параметров внешнего источника.

    ```sql
    CREATE SERVER remote_server
        FOREIGN DATA WRAPPER postgres_fdw
        OPTIONS (
            host '192.168.1.10', 
            port '5432', 
            dbname 'remote_db', 
            batch_size '100',      -- Ускорение массовой вставки (PG 14+)
            async_capable 'on',    -- Параллельное выполнение запросов (PG 14+)
            parallel_commit 'on'   -- Параллельный коммит транзакций (PG 15+)
        );
    ```

3. **`CREATE USER MAPPING ...`:** Сопоставление локального пользователя с учетными данными на внешнем сервере.

    ```sql
    CREATE USER MAPPING FOR current_user
        SERVER remote_server
        OPTIONS (user 'app_user', password 'secure_password');
    ```

4. **Создание внешней таблицы:**

    **Ручное создание:**
    ```sql
    CREATE FOREIGN TABLE remote_orders (
        id INT,
        customer_id INT,
        order_date DATE
    )
    SERVER remote_server
    OPTIONS (schema_name 'public', table_name 'orders');
    ```

    **Импорт схемы (рекомендуется):**
    ```sql
    IMPORT FOREIGN SCHEMA public
    LIMIT TO (orders, customers)
    FROM SERVER remote_server
    INTO local_schema;
    ```

5. **Сбор статистики (Критично!):** Без актуальной статистики планировщик не сможет построить эффективный план.
    ```sql
    ANALYZE remote_orders;
    ```

### Примеры популярных FDW

* **`postgres_fdw`:** Официальный драйвер для PostgreSQL. Поддерживает полный pushdown, пакетную вставку (batching), параллельные сканирования и **UPSERT (PG 17)**.
    - **Преимущества:** Позволяет получать данные из нескольких баз без сторонних инструментов (хаб данных).
    - **Шардинг:** Может использоваться для распределения одной большой базы на несколько инстансов в вертикальной или горизонтальной логике (шардирование через FDW).
    - **Миграция:** Помогает проводить бесшовную миграцию данных или объединять разрозненные БД.
* **`file_fdw`:** Чтение данных напрямую из CSV/текстовых файлов на сервере. Поддерживает `COPY` и работу с логами сервера.
* **`mysql_fdw` / `tds_fdw`:** Интеграция с MySQL/MariaDB и SQL Server (Sybase).
* **`oracle_fdw`:** Промышленный драйвер для связи с Oracle DB.
* **`sqlite_fdw`:** Легковесный драйвер для работы с локальными файлами SQLite.
* **`clickhouse_fdw`:** Высокопроизводительная интеграция с ClickHouse (подробнее в **[Интеграция PostgreSQL и ClickHouse](./clickhouse.md)**).
* **`multicorn2`:** Современный наследник Multicorn, позволяющий писать FDW на Python 3.

### Анализ производительности (`EXPLAIN`)

При анализе плана запроса (`EXPLAIN VERBOSE`) к внешней таблице появляется узел `Foreign Scan`.

```sql
EXPLAIN (VERBOSE, COSTS FALSE) SELECT * FROM remote_orders WHERE id = 10;
```

```text
                      QUERY PLAN
------------------------------------------------------
 Foreign Scan on public.remote_orders
   Output: id, customer_id, order_date
   Remote SQL: SELECT id, customer_id, order_date FROM public.orders WHERE id = 10
```

Ключевая строка — `Remote SQL`. Она показывает, какой именно запрос был отправлен на внешний сервер. Если в `Remote SQL` присутствует условие `WHERE`, значит, predicate pushdown сработал успешно.

### Новые возможности по версиям (Summary)

* **PG 14:** `batch_size` для `INSERT`, `TRUNCATE` внешних таблиц, асинхронные запросы (`async_capable`).
* **PG 15:** Параллельный коммит (`parallel_commit`).
* **PG 16:** Улучшение `COPY` для `postgres_fdw`, поддержка `GENERIC_PLAN` в EXPLAIN.
* **PG 17:** Поддержка `ON CONFLICT` (UPSERT) для `postgres_fdw`, pushdown для `EXISTS` и `IN`.

## Дополнительная информация

### Ограничения и риски

* **Производительность сети:** FDW чувствителен к задержкам (latency) и пропускной способности. Большие JOIN-ы между внешними таблицами могут работать медленно, если данные пересылаются на локальный сервер для обработки.
* **Транзакции:** PostgreSQL не гарантирует атомарность транзакций (2PC) между локальной и внешней базой "из коробки" (требуется настройка внешнего сервера и драйвера, поддерживающего 2PC). Ошибка записи в удаленную таблицу может оставить локальную транзакцию в неопределенном состоянии.
* **Лимиты подключений:** Каждая сессия, обращающаяся к FDW, может удерживать открытое соединение с удаленным сервером. Используйте `keep_connections 'off'` или PgBouncer для экономии ресурсов.
* **Безопасность:** Пароли в `USER MAPPING` хранятся в системных каталогах. Рекомендуется использовать SSL-сертификаты или `password_required 'false'` для доверенных соединений.

### Рекомендации по эксплуатации

1. **Используйте `use_remote_estimate`:** Опция заставляет планировщик запрашивать примерную стоимость выполнения на удаленном сервере, что дает более точные планы.
2. **Параллелизм:** С PG 11+ PostgreSQL может выполнять сканирование внешних таблиц параллельно, если драйвер это поддерживает.
3. **Мониторинг:** Отслеживайте `wait_event` типа `Extension` или сетевые ожидания. Используйте `pg_stat_statements` для анализа времени `Foreign Scan`.

### Сравнение FDW и ETL

| Характеристика | Foreign Data Wrapper (FDW) | Extract, Transform, Load (ETL) |
| :--- | :--- | :--- |
| **Доступ к данным** | В реальном времени (real-time) | С задержкой (пакетный) |
| **Хранение данных** | Источник (без дублирования) | Копируются в целевую БД (DWH) |
| **Трансформация** | Ограничена мощностью SQL | Сложные преобразования (Python/Java) |
| **Нагрузка** | В момент выполнения запроса | Во время работы ETL-задания |
| **Сценарий** | Оперативная аналитика, Master Data | Хранилища данных, историческая отчетность |

### Типичные ошибки

* **`connection timeout`:** Проверьте доступность порта и правила Firewall/Security Groups.
* **`schema mismatch`:** Структура внешней таблицы устарела. Используйте `IMPORT FOREIGN SCHEMA` повторно.
* **`permission denied`:** Проверьте права пользователя в `USER MAPPING` на удаленной стороне.
