# Интеграция PostgreSQL и ClickHouse

Совместное использование PostgreSQL и ClickHouse — это популярный гибридный подход, который позволяет использовать сильные стороны каждой из систем: PostgreSQL для транзакционной нагрузки (OLTP) и ClickHouse для аналитической (OLAP).

- **PostgreSQL (OLTP):** Обрабатывает частые, короткие транзакции (например, создание заказа, обновление профиля пользователя). Гарантирует целостность данных (ACID).
- **ClickHouse (OLAP):** Обрабатывает сложные аналитические запросы по большим объемам данных. Обеспечивает высокую скорость агрегации и построения отчетов.

## Способы интеграции

### 1. Периодическая пакетная загрузка (Batch Loading)

Это самый простой способ интеграции.

**Как это работает:**
1.  Создается скрипт, который с определенной периодичностью (например, раз в час или раз в день) выгружает данные из PostgreSQL (например, с помощью `COPY ... TO STDOUT`).
2.  Выгруженные данные (обычно в формате CSV или TSV) загружаются в ClickHouse (например, с помощью `clickhouse-client`).

Этот подход прост в реализации, но данные в аналитической системе будут иметь задержку. Он хорошо подходит для задач, где не требуется аналитика в реальном времени.

### 2. Использование Foreign Data Wrapper (FDW)

Этот способ позволяет запрашивать данные из ClickHouse напрямую в PostgreSQL.

**Архитектура:** `PostgreSQL ↔ clickhouse_fdw`

**Как это работает:**
1.  В PostgreSQL устанавливается расширение `clickhouse_fdw`.
2.  Создается "внешняя таблица" (`FOREIGN TABLE`), которая маппится на таблицу в ClickHouse.
3.  После этого можно выполнять `SELECT` запросы к этой внешней таблице из PostgreSQL. Запрос будет прозрачно перенаправлен в ClickHouse, а результаты возвращены в PostgreSQL.

Этот метод удобен, когда необходимо объединять "горячие" транзакционные данные из PostgreSQL с "холодными" аналитическими данными из ClickHouse в одном запросе.

### 3. Репликация данных в реальном времени (CDC - Change Data Capture)

Это наиболее продвинутый способ, обеспечивающий практически мгновенную синхронизацию данных.

**Архитектура:** `PostgreSQL → Debezium → Kafka → ClickHouse`

**Как это работает:**
1.  **PostgreSQL:** Настраивается [логическая репликация](../Concepts/replication.md). Все изменения (`INSERT`, `UPDATE`, `DELETE`) записываются в Write-Ahead Log (WAL).
2.  **Debezium:** Коннектор для Kafka Connect, который "читает" WAL PostgreSQL, преобразует изменения в структурированные события и отправляет их в топик Apache Kafka.
3.  **Apache Kafka:** Выступает в роли надежного буфера для потока событий изменений.
4.  **ClickHouse:** В ClickHouse создается таблица с движком `Kafka`. Эта таблица "подписывается" на топик в Kafka, считывает из него события и вставляет данные в основную (материализованную) таблицу ClickHouse.

Этот подход позволяет создать real-time аналитическую систему, где данные появляются в ClickHouse с минимальной задержкой после их изменения в PostgreSQL.

## Практические соображения

### Денормализация данных

Ключевой аспект эффективного использования ClickHouse — минимизация или полное исключение операций `JOIN` во время аналитических запросов, так как они выполняются значительно медленнее, чем в традиционных СУБД.

Поэтому при переносе данных из нормализованной схемы PostgreSQL в ClickHouse рекомендуется применять **денормализацию**. Вместо репликации нескольких связанных таблиц (например, `orders`, `customers`, `products`) в процессе ETL (Extract, Transform, Load) их объединяют в одну "широкую" таблицу в ClickHouse.

**Пример:**

В PostgreSQL у вас могут быть таблицы:
- `orders` (order_id, customer_id, order_date)
- `customers` (customer_id, customer_name, region)

При загрузке в ClickHouse создается одна таблица `orders_wide`, которая содержит предварительно объединенные данные:
- `orders_wide` (order_id, order_date, customer_id, customer_name, region)

Такой подход позволяет выполнять аналитические запросы по одной большой таблице без необходимости в `JOIN`, что максимально использует преимущества колоночного хранения ClickHouse.
