# Интеграция PostgreSQL и ClickHouse

## Определения

**Гибридная архитектура OLTP + OLAP** — подход, позволяющий использовать сильные стороны двух типов систем:

- **PostgreSQL (OLTP — Online Transactional Processing):** Обработка частых, коротких транзакций (создание заказа, обновление профиля) с гарантией целостности данных ([ACID — Atomicity, Consistency, Isolation, Durability](../../Concepts/acid.md)).
- **[ClickHouse](../../clickhouse.md) (OLAP — Online Analytical Processing):** Обработка сложных аналитических запросов по большим объемам данных с высокой скоростью агрегации и построения отчетов.

## Основные концепции

### Принцип денормализации

Ключевой аспект эффективного использования ClickHouse — минимизация или полное исключение операций `JOIN` во время аналитических запросов, так как они выполняются значительно медленнее, чем в традиционных СУБД.

Поэтому при переносе данных из нормализованной схемы PostgreSQL в ClickHouse рекомендуется применять **денормализацию**. Вместо репликации нескольких связанных таблиц (например, `orders`, `customers`) в процессе ETL (Extract, Transform, Load) их объединяют в одну "широкую" таблицу в ClickHouse.

**Пример:**

- **Источник (PostgreSQL):** `orders` (id, customer_id) и `customers` (id, name).
- **Приемник (ClickHouse):** Одна таблица `orders_wide` (order_id, customer_id, customer_name).

Это позволяет выполнять аналитические запросы к одной таблице без `JOIN`, максимально используя преимущества колоночного хранения ClickHouse.

## Практические сценарии

### Периодическая пакетная загрузка

Это самый простой способ интеграции.

**Принцип работы:**

1. Создается скрипт, который с определенной периодичностью (например, раз в час или раз в день) выгружает данные из PostgreSQL (например, с помощью `COPY ... TO STDOUT`).
2. Выгруженные данные (обычно в формате CSV (Comma-Separated Values) или TSV (Tab-Separated Values)) загружаются в ClickHouse (например, с помощью `clickhouse-client`).

**Преимущества:**

- Простота реализации
- Минимальные требования к инфраструктуре

**Недостатки:**

- Данные в аналитической системе имеют задержку (от часа до суток)
- Не подходит для аналитики в реальном времени

**Рекомендации:**

- Пакетная загрузка: от 100 000 до 1 000 000 строк за одну вставку
- Частота вставок: не чаще одного раза в секунду для одной таблицы

### Внешние таблицы (FDW)

**[Foreign Data Wrappers (FDW)](./fdw.md)** — механизм PostgreSQL, позволяющий обращаться к ClickHouse как к обычной таблице. Это удобный способ объединять "горячие" транзакционные данные из PostgreSQL с "холодными" аналитическими данными из ClickHouse в одном SQL-запросе.

**Архитектура:** `PostgreSQL ↔ clickhouse_fdw`

**Принцип работы:**

1. В PostgreSQL устанавливается расширение `clickhouse_fdw`.
2. С помощью `CREATE SERVER` и `CREATE FOREIGN TABLE` настраивается подключение к таблице в ClickHouse.
3. Запросы `SELECT` к внешней таблице прозрачно перенаправляются в ClickHouse для выполнения.

**Преимущества:**

- Прозрачность для приложений (ClickHouse как обычная таблица)
- Возможность объединять транзакционные и аналитические данные

**Недостатки:**

- Запросы выполняются через PostgreSQL, что создает дополнительную нагрузку
- Не подходит для передачи больших объемов данных

### Репликация данных в реальном времени (CDC)

Это наиболее продвинутый способ, обеспечивающий практически мгновенную синхронизацию данных через механизм CDC (Change Data Capture).

**Архитектура:** `PostgreSQL → Debezium → Kafka → ClickHouse`

**Принцип работы:**

1. **PostgreSQL:** Настраивается [логическая репликация](../Concepts/replication.md). Все изменения (`INSERT`, `UPDATE`, `DELETE`) записываются в WAL (Write-Ahead Log).
2. **Debezium:** Коннектор для Kafka Connect, который читает WAL PostgreSQL, преобразует изменения в структурированные события и отправляет их в топик Apache Kafka.
3. **[Apache Kafka](../../../Kafka/kafka_for_monitoring.md):** Выступает в роли надежного буфера для потока событий изменений.
4. **ClickHouse:** Подключается к Kafka через движок `Kafka`. Подробнее см. **[Интеграция ClickHouse и Kafka](../../ClickHouse/clickhouse_kafka_integration.md)**.

### Нативные движки ClickHouse для PostgreSQL

ClickHouse предоставляет встроенные механизмы для прямого взаимодействия с PostgreSQL без промежуточных звеньев (кроме сетевого соединения).

#### Табличный движок `PostgreSQL`
Позволяет создать таблицу в ClickHouse, которая является "прокси" к таблице в PostgreSQL.

```sql
CREATE TABLE ch_postgres_table (
    id UInt64,
    name String
) ENGINE = PostgreSQL('host:port', 'database', 'table', 'user', 'password', 'schema');
```

#### Базовый движок `PostgreSQL`
Позволяет подключить всю базу данных PostgreSQL целиком. Все таблицы будут видны в ClickHouse автоматически.

```sql
CREATE DATABASE postgres_db 
ENGINE = PostgreSQL('host:port', 'database', 'user', 'password', 'schema');
```

#### Табличная функция `postgresql()`
Удобна для разовых запросов или джойнов "на лету" без создания постоянных структур.

```sql
SELECT * FROM postgresql('host:port', 'database', 'table', 'user', 'password');
```

### Словари (Dictionaries) как источник данных

Словари в ClickHouse — это структуры данных, которые хранятся в оперативной памяти и оптимизированы для быстрой подстановки (lookup). PostgreSQL часто используется как источник для таких справочников.

**Преимущества:**
- Данные "подогреты" в оперативной памяти.
- Чрезвычайно высокая скорость доступа.
- Автоматическое обновление данных по расписанию.

```sql
CREATE DICTIONARY users_dict (
    id UInt64,
    name String
)
PRIMARY KEY id
SOURCE(POSTGRESQL(port 5432 host 'localhost' user 'user' password 'pass' db 'db' table 'users'))
LAYOUT(HASHED())
LIFETIME(MIN 300 MAX 600); -- Обновлять каждые 5-10 минут
```

### Материализованные представления ClickHouse

ClickHouse предоставляет два типа материализованных представлений для автоматической обработки данных.

#### Материализованные представления на основе триггеров

**Принцип работы:**

- Реагируют только на `INSERT` в исходную таблицу
- Данные хранятся в отдельной таблице
- Автоматически обновляются при вставке новых данных

**Пример использования с Kafka:** см. **[Интеграция ClickHouse и Kafka](../../ClickHouse/clickhouse_kafka_integration.md)**.

#### Обновляемые материализованные представления

**Принцип работы:**

- Обновляются по расписанию (cron-подобный синтаксис)
- Аналог материализованных представлений PostgreSQL
- Минимальный интервал обновления: 1 минута

**Пример:**

```sql
CREATE MATERIALIZED VIEW daily_orders_mv
REFRESH EVERY 1 HOUR
AS SELECT 
    toDate(order_date) AS date,
    count() AS orders_count,
    sum(amount) AS total_amount
FROM orders
GROUP BY date;
```

**Преимущества:**

- Плановое обновление по расписанию
- Подходит для агрегированных отчетов

**Недостатки:**

- Не подходит для данных реального времени
- Минимальный интервал: 1 минута

## Дополнительная информация

### Выбор способа интеграции

| Способ | Задержка | Сложность | Подходит для |
| :--- | :--- | :--- | :--- |
| **Пакетная загрузка** | Часы / дни | Низкая | Исторические данные, отчеты T-1 (предыдущий день) |
| **Внешние таблицы (FDW)** | Мгновенно | Средняя | Смешанные запросы (OLTP + OLAP) со стороны PostgreSQL |
| **Нативные движки CH** | Мгновенно | Низкая | Смешанные запросы со стороны ClickHouse, ETL |
| **CDC (Kafka)** | Секунды | Высокая | Аналитика реального времени, дашборды |
| **Словари (CH)** | Минуты | Средняя | Быстрые Lookups справочников в ClickHouse |
| **Materialized View** | Секунды / минуты | Средняя | Агрегации, предварительные расчеты |
