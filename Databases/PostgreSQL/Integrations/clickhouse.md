# Интеграция PostgreSQL и ClickHouse

## Определения

**Гибридная архитектура (HTAP)** — использование комбинации систем для обработки транзакционных (OLTP) и аналитических (OLAP) нагрузок в рамках одного продукта или экосистемы.

*   **PostgreSQL (OLTP):** Система-источник «горячих» транзакционных данных. Гарантирует целостность через [ACID](../../Concepts/acid.md).
*   **ClickHouse (OLAP):** Система-приемник «холодных» или исторических данных для высокоскоростной аналитики.
*   **CDC (Change Data Capture):** Технология отслеживания изменений в базе данных (обычно через чтение логов транзакций) для их репликации в реальном времени.

## Основные концепции

### Денормализация данных

В PostgreSQL данные обычно хранятся в нормализованном виде (много связанных таблиц) для минимизации избыточности. В ClickHouse операции `JOIN` являются дорогостоящими, поэтому основным подходом является **денормализация**.

При интеграции рекомендуется:
1.  **Объединение таблиц:** На этапе переноса данных (ETL/ELT) объединять связанные таблицы в одну «широкую» таблицу.
2.  **Материализация справочников:** Вместо хранения ID внешних ключей записывать текстовые значения (например, имя клиента вместо `customer_id`).
3.  **Использование массивов и вложенных структур:** ClickHouse эффективно работает с типами `Array` и `Nested`, что позволяет хранить связанные данные внутри одной строки.
4.  **Native JSON (v24.8+):** Использование нового типа `JSON` в ClickHouse для прямого маппинга `JSONB` из PostgreSQL с сохранением типизации и высокой скорости поиска по вложенным полям.
5.  **Использование `ReplacingMergeTree`:** При использовании CDC (PeerDB, Kafka) на стороне ClickHouse необходимо использовать движок `ReplacingMergeTree` с указанием колонки-версии (например, `updated_at` или `lsn` из PostgreSQL) для автоматического схлопывания дубликатов при обновлениях.

### Маппинг типов данных

Для корректной работы интеграции важно учитывать различия в типах данных:

| PostgreSQL Type | ClickHouse Type | Комментарий |
| :--- | :--- | :--- |
| `UUID` | `UUID` | Нативная поддержка в обеих системах |
| `JSONB` | `JSON` / `String` | В CH v24.8+ рекомендуется `JSON` |
| `INET` / `CIDR` | `IPv4` / `IPv6` | CH автоматически парсит строки IP |
| `TIMESTAMP` | `DateTime64` | Рекомендуется сохранять точность до миллисекунд |
| `NUMERIC` | `Decimal` | Требует явного указания точности (P, S) |
| `BYTEA` | `String` | Бинарные данные передаются как строки |

### Разделение данных по времени (Hot/Cold)

*   **Hot data:** Последние данные (например, за последние 24 часа или текущий месяц), которые часто меняются. Хранятся в PostgreSQL.
*   **Cold data:** Исторические данные, которые используются только для чтения и анализа. Хранятся в ClickHouse.
*   **Warm data:** Промежуточный слой, который может реплицироваться в ClickHouse в реальном времени для оперативной отчетности.

## Практические сценарии

### Пакетная загрузка (Bulk Load)

Самый простой способ для разового или периодического переноса данных.

*   **Механизм:** Выгрузка из PostgreSQL через `COPY` в CSV/TSV и загрузка в ClickHouse через `clickhouse-client`.
*   **Инструмент `clickhouse-local`:** Позволяет выполнять SQL-запросы к локальным файлам или напрямую к PostgreSQL без развертывания полного сервера CH. Это идеальный инструмент для ad-hoc задач и быстрых ETL-скриптов.
    ```bash
    clickhouse-local --query "INSERT INTO ch_table SELECT * FROM postgresql('host:port', 'db', 'table', 'user', 'password')"
    ```
*   **Рекомендации:** Оптимальный размер пачки (batch) — от 100 тыс. до 1 млн строк.

### Внешние таблицы (FDW)

Использование **[clickhouse_fdw](./fdw.md)** на стороне PostgreSQL.

*   **Назначение:** Чтение данных из ClickHouse для джойнов с локальными таблицами PG.
*   **Ограничение:** Не рекомендуется для массовой перекачки данных (ETL), так как PostgreSQL становится «бутылочным горлышком».
*   **Настройка:** Требует установки расширения в ОС и в саму базу данных.

### Репликация в реальном времени (CDC)

Обеспечивает минимальную задержку (Lag) между системами за счет чтения логов транзакций (WAL).

1.  **PeerDB (Open Source / Managed):**
    *   Стандарт индустрии в 2026 году для интеграции PG → CH (приобретен ClickHouse).
    *   **Преимущества:** Высокая надежность, поддержка сложных схем, автоматическое управление слотами репликации и прозрачная обработка `UPDATE/DELETE`.
    *   **ClickPipes:** Облачная реализация PeerDB для пользователей ClickHouse Cloud.

2.  **Классический стек (Kafka):** `PostgreSQL → Debezium → Kafka → ClickHouse`.
    *   Надежно, масштабируемо, поддерживает сложную трансформацию.
    *   **Kafka2 (v26.7+):** Использование нового движка в ClickHouse для гарантии доставки **Exactly-once** и упрощенного управления оффсетами.
    *   Подробнее: **[Интеграция ClickHouse и Kafka](../../ClickHouse/clickhouse_kafka_integration.md)**.

3.  **Altinity Sink Connector:** Специализированный коннектор для Kafka Connect, оптимизированный под ClickHouse. Позволяет эффективно использовать движок `ReplacingMergeTree` для синхронизации изменяемых данных.

#### Настройка PostgreSQL для CDC
Для работы любого CDC-решения необходимо включить логическую репликацию:
```ini
# postgresql.conf
wal_level = logical
max_replication_slots = 10
max_wal_senders = 10
```

### Нативные возможности ClickHouse

ClickHouse может напрямую взаимодействовать с PostgreSQL как на уровне отдельных таблиц, так и на уровне баз данных.

#### Движок базы данных `MaterializedPostgreSQL` (Experimental)
Создает копию базы данных PostgreSQL и поддерживает ее в актуальном состоянии через логическую репликацию.
*   **Статус:** Остается экспериментальным в 2026 году. Требует `SET allow_experimental_database_materialized_postgresql = 1`.
*   **Ограничения:**
    *   Требует Primary Key во всех таблицах.
    *   Не поддерживает автоматическую репликацию DDL (требуется `DETACH/ATTACH` базы).
    *   Не поддерживает `TRUNCATE` и большие `TOAST` данные.
*   **Пример:**
```sql
CREATE DATABASE pg_mirror
ENGINE = MaterializedPostgreSQL('host:port', 'database', 'user', 'password');
```

#### Именованные коллекции (Named Collections)
Для повышения безопасности рекомендуется использовать именованные коллекции в конфигурации ClickHouse (`/etc/clickhouse-server/config.d/postgres.xml`). Это позволяет избежать хранения паролей в SQL-запросах.
```sql
-- В запросе используется имя коллекции вместо параметров подключения
SELECT * FROM postgresql(pg_production, table='users');
```

#### Движок таблиц `PostgreSQL`
Создает прокси-таблицу в ClickHouse. Данные не копируются, а запрашиваются из PG при каждом обращении к таблице CH. Удобно для небольших таблиц-справочников.
```sql
CREATE TABLE ch_table (id UInt64, name String)
ENGINE = PostgreSQL('host:port', 'database', 'table', 'user', 'password', 'schema');
```

#### Движок базы данных `PostgreSQL`
Позволяет подключить всю схему PostgreSQL как внешнюю БД. В отличие от `MaterializedPostgreSQL`, данные не хранятся в ClickHouse, а проксируются.
```sql
CREATE DATABASE pg_db
ENGINE = PostgreSQL('host:port', 'database', 'user', 'password', 'schema');
```

### Обратная интеграция: `pg_clickhouse`
Расширение для PostgreSQL, позволяющее прозрачно делегировать тяжелые аналитические запросы в ClickHouse.
*   **Механизм:** PostgreSQL перехватывает план запроса и, если он содержит агрегации по большим таблицам, отправляет его в ClickHouse через FDW или нативный протокол.
*   **Результат:** Приложение продолжает работать с PostgreSQL, но получает производительность ClickHouse для OLAP-задач.

### Словари (Dictionaries)

Словари в ClickHouse кэшируют данные из PostgreSQL в оперативной памяти, что обеспечивает сверхбыстрый доступ (lookups).

*   **Преимущества:** Данные всегда «подогреты», обновление происходит в фоне по расписанию.
*   **Использование:** Идеально для замены `JOIN` со справочниками на функцию `dictGet()`.
```sql
CREATE DICTIONARY users_dict (
    id UInt64,
    name String
)
PRIMARY KEY id
SOURCE(POSTGRESQL(port 5432 host 'localhost' user 'user' password 'pass' db 'db' table 'users'))
LAYOUT(HASHED())
LIFETIME(MIN 300 MAX 600);
```

### Материализованные представления (MV)

Используются для автоматической трансформации данных «на лету» при их поступлении в ClickHouse (например, из Kafka).

*   **Классические MV:** Срабатывают только на новые вставки (`INSERT`). Используются для денормализации и агрегации.
*   **Refreshable MV:** Обновляются целиком по расписанию. Подходят для тяжелых отчетов, где не важна репликация в реальном времени.

## Лучшие практики и оптимизация

1.  **Мониторинг Lag:** При использовании CDC критически важно мониторить задержку между `lsn` в PostgreSQL и последним обработанным смещением в ClickHouse. В PeerDB/ClickPipes это доступно через встроенные дашборды.
2.  **Параллельная вставка:** Для `PostgreSQL` engine используйте настройку `external_table_functions_use_nulls = 1` и убедитесь, что ClickHouse может читать данные в несколько потоков, если таблица в PG секционирована.
3.  **Индексы:** В ClickHouse `ORDER BY` должен соответствовать наиболее частым фильтрам в аналитических запросах, а не повторять Primary Key из PostgreSQL.
4.  **Batching:** Всегда стремитесь к объединению мелких вставок в пачки от 10-100 тыс. строк. Прямые одиночные `INSERT` из приложения в ClickHouse недопустимы.
5.  **Schema Evolution:** При использовании CDC заранее планируйте DDL-изменения. Большинство инструментов требуют временной остановки репликации для изменения типов колонок или удаления полей.

## Дополнительная информация

### Сравнение способов интеграции

| Способ | Задержка (Lag) | Нагрузка на PG | Сложность | Типовой сценарий |
| :--- | :--- | :--- | :--- | :--- |
| **Bulk Load** | Высокая | Низкая | Низкая | Исторические данные (разово) |
| **FDW / Native Engines** | Мгновенно | Высокая | Низкая | Ad-hoc запросы, справочники |
| **MaterializedPostgreSQL** | Секунды | Средняя | Средняя | Репликация простых схем (Experimental) |
| **PeerDB / ClickPipes** | < 1 сек | Низкая | Средняя | Промышленный CDC (Стандарт 2026) |
| **CDC (Kafka)** | Секунды | Низкая | Высокая | Сложный ETL, много систем-приемников |
| **Dictionaries** | Минуты | Средняя | Средняя | Кэширование справочников в RAM |
