# Интеграция PostgreSQL и ClickHouse

## Определения

**Гибридная архитектура OLTP+OLAP** — подход, позволяющий использовать сильные стороны двух типов систем:

- **PostgreSQL (OLTP):** Обработка частых, коротких транзакций (создание заказа, обновление профиля) с гарантией целостности данных ([ACID](../../Concepts/acid.md)).
- **[ClickHouse](../../clickhouse.md) (OLAP):** Обработка сложных аналитических запросов по большим объемам данных с высокой скоростью агрегации и построения отчётов.

## Основные концепции

### Принцип денормализации

Ключевой аспект эффективного использования ClickHouse — минимизация или полное исключение операций `JOIN` во время аналитических запросов, так как они выполняются значительно медленнее, чем в традиционных СУБД.

Поэтому при переносе данных из нормализованной схемы PostgreSQL в ClickHouse рекомендуется применять **денормализацию**. Вместо репликации нескольких связанных таблиц (например, `orders`, `customers`) в процессе ETL их объединяют в одну "широкую" таблицу в ClickHouse.

**Пример:**

- **Источник (PostgreSQL):** `orders` (id, customer_id) и `customers` (id, name).
- **Приемник (ClickHouse):** Одна таблица `orders_wide` (order_id, customer_id, customer_name).

Это позволяет выполнять аналитические запросы к одной таблице без `JOIN`, максимально используя преимущества колоночного хранения ClickHouse.

## Практические сценарии

### Периодическая пакетная загрузка (Batch Loading)

Это самый простой способ интеграции.

**Как это работает:**

1. Создается скрипт, который с определенной периодичностью (например, раз в час или раз в день) выгружает данные из PostgreSQL (например, с помощью `COPY ... TO STDOUT`).
2. Выгруженные данные (обычно в формате CSV или TSV) загружаются в ClickHouse (например, с помощью `clickhouse-client`).

**Преимущества:**

- Простота реализации
- Минимальные требования к инфраструктуре

**Недостатки:**

- Данные в аналитической системе имеют задержку (от часа до суток)
- Не подходит для аналитики в реальном времени

**Рекомендации:**

- Пакетная загрузка: от 100 000 до 1 000 000 строк за одну вставку
- Частота вставок: не чаще одного раза в секунду для одной таблицы

### Foreign Data Wrapper (FDW)

**[Foreign Data Wrappers (FDW)](./fdw.md)** — механизм PostgreSQL, позволяющий обращаться к ClickHouse как к обычной таблице. Это удобный способ объединять "горячие" транзакционные данные из PostgreSQL с "холодными" аналитическими данными из ClickHouse в одном SQL-запросе.

**Архитектура:** `PostgreSQL ↔ clickhouse_fdw`

**Как это работает:**

1. В PostgreSQL устанавливается расширение `clickhouse_fdw`.
2. С помощью `CREATE SERVER` и `CREATE FOREIGN TABLE` настраивается подключение к таблице в ClickHouse.
3. Запросы `SELECT` к внешней таблице прозрачно перенаправляются в ClickHouse для выполнения.

**Преимущества:**

- Прозрачность для приложений (ClickHouse как обычная таблица)
- Возможность джойнить транзакционные и аналитические данные

**Недостатки:**

- Запросы выполняются через PostgreSQL, что создаёт дополнительную нагрузку
- Не подходит для передачи больших объёмов данных

### Репликация данных в реальном времени (CDC)

Это наиболее продвинутый способ, обеспечивающий практически мгновенную синхронизацию данных.

**Архитектура:** `PostgreSQL → Debezium → Kafka → ClickHouse`

**Как это работает:**

1. **PostgreSQL:** Настраивается [логическая репликация](../Concepts/replication.md). Все изменения (`INSERT`, `UPDATE`, `DELETE`) записываются в Write-Ahead Log (WAL).
2. **Debezium:** Коннектор для Kafka Connect, который "читает" WAL PostgreSQL, преобразует изменения в структурированные события и отправляет их в топик Apache Kafka.
3. **[Apache Kafka](../../../Kafka/kafka_for_monitoring.md):** Выступает в роли надежного буфера для потока событий изменений.
4. **ClickHouse:** В ClickHouse создается таблица с движком `Kafka`. Эта таблица "подписывается" на топик в Kafka, считывает из него события и вставляет данные в основную (материализованную) таблицу ClickHouse.

**Преимущества:**

- Минимальная задержка (секунды)
- Надёжность за счёт буферизации в Kafka
- Поддержка различных форматов: `JSONEachRow`, `CSV`, `Avro`, `Parquet`, `Protobuf`

**Недостатки:**

- Сложность архитектуры (требует Kafka, Debezium)
- Дополнительные операционные затраты

### Материализованные представления ClickHouse

ClickHouse предоставляет два типа материализованных представлений для автоматической обработки данных:

#### Trigger-based материализованные представления

**Принцип работы:**

- Реагируют только на `INSERT` в исходную таблицу
- Данные хранятся в отдельной таблице
- Автоматически обновляются при вставке новых данных

**Пример использования с Kafka:**

```sql
-- Таблица для чтения из Kafka
CREATE TABLE kafka_queue (
    order_id UInt64,
    customer_id UInt64,
    amount Float64
) ENGINE = Kafka('kafka_broker:9092', 'orders_topic', 'group_id', 'JSONEachRow');

-- Конечная таблица для хранения данных
CREATE TABLE orders (
    order_id UInt64,
    customer_id UInt64,
    amount Float64
) ENGINE = MergeTree()
ORDER BY order_id;

-- Материализованное представление для автоматической вставки
CREATE MATERIALIZED VIEW orders_mv TO orders AS
SELECT order_id, customer_id, amount
FROM kafka_queue;
```

**Преимущества:**

- Автоматическая обработка данных без скриптов
- Минимальная задержка
- "Ленивое" обновление — только при INSERT

#### Refreshable материализованные представления

**Принцип работы:**

- Обновляются по расписанию (cron-подобный синтаксис)
- Аналог материализованных представлений PostgreSQL
- Минимальный интервал обновления: 1 минута

**Пример:**

```sql
CREATE MATERIALIZED VIEW daily_orders_mv
REFRESH EVERY 1 HOUR
AS SELECT 
    toDate(order_date) AS date,
    count() AS orders_count,
    sum(amount) AS total_amount
FROM orders
GROUP BY date;
```

**Преимущества:**

- Плановое обновление по расписанию
- Подходит для агрегированных отчётов

**Недостатки:**

- Не подходит для данных реального времени
- Минимальный интервал: 1 минута

## Дополнительная информация

### Выбор способа интеграции

| Способ | Задержка | Сложность | Подходит для |
| :--- | :--- | :--- | :--- |
| **Пакетная загрузка** | Часы/дни | Низкая | Исторические данные, отчёты T-1 |
| **FDW** | Мгновенно | Средняя | Смешанные запросы (OLTP + OLAP) |
| **CDC (Kafka)** | Секунды | Высокая | Аналитика реального времени, дашборды |
| **Materialized View** | Секунды/минуты | Средняя | Агрегации, предварительные расчёты |
