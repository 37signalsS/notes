# Интеграция PostgreSQL и ClickHouse

## 1. Определения

**Гибридная архитектура OLTP+OLAP** — это подход, который позволяет использовать сильные стороны двух типов систем:

- **PostgreSQL (OLTP):** Обрабатывает частые, короткие транзакции (создание заказа, обновление профиля), гарантируя целостность данных ([ACID](../../Concepts/acid.md)).
- **[ClickHouse](../../clickhouse.md) (OLAP):** Обрабатывает сложные аналитические запросы по большим объемам данных, обеспечивая высокую скорость агрегации и построения отчетов.

## 2. Основные концепции

### Принцип денормализации

Ключевой аспект эффективного использования ClickHouse — минимизация или полное исключение операций `JOIN` во время аналитических запросов, так как они выполняются значительно медленнее, чем в традиционных СУБД.

Поэтому при переносе данных из нормализованной схемы PostgreSQL в ClickHouse рекомендуется применять **денормализацию**. Вместо репликации нескольких связанных таблиц (например, `orders`, `customers`) в процессе ETL их объединяют в одну "широкую" таблицу в ClickHouse.

**Пример:**

- **Источник (PostgreSQL):** `orders` (id, customer_id) и `customers` (id, name).
- **Приемник (ClickHouse):** Одна таблица `orders_wide` (order_id, customer_id, customer_name).

Это позволяет выполнять аналитические запросы к одной таблице без `JOIN`, максимально используя преимущества колоночного хранения ClickHouse.

## 3. Практические сценарии: Способы интеграции

### 1. Периодическая пакетная загрузка (Batch Loading)

Это самый простой способ интеграции.

**Как это работает:**

1. Создается скрипт, который с определенной периодичностью (например, раз в час или раз в день) выгружает данные из PostgreSQL (например, с помощью `COPY ... TO STDOUT`).
2. Выгруженные данные (обычно в формате CSV или TSV) загружаются в ClickHouse (например, с помощью `clickhouse-client`).

Этот подход прост в реализации, но данные в аналитической системе будут иметь задержку. Он хорошо подходит для задач, где не требуется аналитика в реальном времени.

### 2. Использование Foreign Data Wrapper (FDW)

**[Foreign Data Wrappers (FDW)](./fdw.md)** — это мощный механизм PostgreSQL, позволяющий обращаться к ClickHouse как к обычной таблице. Это удобный способ объединять "горячие" транзакционные данные из PostgreSQL с "холодными" аналитическими данными из ClickHouse в одном SQL-запросе.

**Архитектура:** `PostgreSQL ↔ clickhouse_fdw`

**Как это работает:**

1. В PostgreSQL устанавливается расширение `clickhouse_fdw`.
2. С помощью `CREATE SERVER` и `CREATE FOREIGN TABLE` настраивается подключение к таблице в ClickHouse.
3. Запросы `SELECT` к внешней таблице прозрачно перенаправляются в ClickHouse для выполнения.

### 3. Репликация данных в реальном времени (CDC - Change Data Capture)

Это наиболее продвинутый способ, обеспечивающий практически мгновенную синхронизацию данных.

**Архитектура:** `PostgreSQL → Debezium → Kafka → ClickHouse`

**Как это работает:**

1. **PostgreSQL:** Настраивается [логическая репликация](../Concepts/replication.md). Все изменения (`INSERT`, `UPDATE`, `DELETE`) записываются в Write-Ahead Log (WAL).
2. **Debezium:** Коннектор для Kafka Connect, который "читает" WAL PostgreSQL, преобразует изменения в структурированные события и отправляет их в топик Apache Kafka.
3. **[Apache Kafka](../../../Kafka/kafka_for_monitoring.md):** Выступает в роли надежного буфера для потока событий изменений.
4. **ClickHouse:** В ClickHouse создается таблица с движком `Kafka`. Эта таблица "подписывается" на топик в Kafka, считывает из него события и вставляет данные в основную (материализованную) таблицу ClickHouse.
