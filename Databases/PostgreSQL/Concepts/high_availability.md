# PostgreSQL High Availability

## Definitions

* **Высокая доступность (High Availability, HA):** Способность системы продолжать функционировать при частичных сбоях (например, отказе одного из серверов) за счет избыточности и автоматизации.
* **Отработка отказа (Failover):** Процесс автоматического переключения на резервный компонент (например, реплику) при сбое основного.
* **Split-Brain:** Критическая ошибка в кластерных системах, при которой из-за нарушения связи два узла одновременно решают, что они являются главными (мастерами), что приводит к рассинхронизации данных. Общая концепция описана в **[Репликация баз данных](../../../Concepts/replication.md#проблема-split-brain-и-решение-через-кворум)**.

## Basic Concepts

### Replication as HA Foundation

Основой любой HA-стратегии является наличие как минимум одной синхронизированной резервной копии сервера (реплики), готовой взять на себя нагрузку. Подробнее см. **[Репликация в PostgreSQL](./replication.md)**.

### Automatic Failover Problem

В ручном режиме при сбое мастера администратор должен сам "повысить" реплику до нового мастера (`pg_ctl promote`). Это создает простой и несет риск человеческой ошибки.

### Cluster Managers Solution

Для минимизации простоя и предотвращения проблемы "Split-Brain" используются специализированные системы, обеспечивающие **автоматическую отработку отказа (Automatic Failover)**.

## Practical Scenarios

### Patroni

**Patroni** — это open-source стандарт де-факто для создания отказоустойчивых кластеров PostgreSQL. Он автоматизирует управление жизненным циклом кластера, используя внешнее распределенное хранилище конфигурации (DCS) для координации.

* **Ключевые особенности Patroni:**
  * **Автоматический Failover:** Patroni непрерывно отслеживает состояние мастера. Если мастер становится недоступным, он автоматически выбирает лучшую реплику и повышает ее до нового мастера.
  * **Защита от Split-Brain:** Для хранения состояния кластера (кто мастер, какие есть реплики) Patroni использует `etcd`, `Consul` или `ZooKeeper` как единый источник правды, что предотвращает "Split-Brain".
  * **Восстановление бывшего мастера:** Когда отказавший мастер возвращается в строй, Patroni автоматически настраивает его как реплику к новому мастеру, используя `pg_rewind`.
* **Развертывание в Kubernetes:** Для производственных сред в Kubernetes рекомендуется использовать специализированные операторы, такие как [CloudNativePG](../Operations/kubernetes_deployment.md), которые часто используют принципы Patroni под капотом.

### Load Balancing and Read/Write Split

В HA-конфигурациях приложения не должны подключаться напрямую к узлам БД. Для решения вопроса отказоустойчивости и маршрутизации используется **балансировщик нагрузки**. Стандартом для PostgreSQL в связке с Patroni является **HAProxy**.

* **Как это работает:** Patroni предоставляет **REST API**, через которое можно в любой момент узнать текущую роль каждого узла в кластере (например, `master`, `replica`). Балансировщик нагрузки регулярно опрашивает этот API (health checks).
* **Маршрутизация трафика:**
  * Запросы на **запись** (INSERT, UPDATE, DELETE) направляются только на узел, который API пометил как `master`.
  * Запросы на **чтение** (SELECT) могут распределяться между всеми работоспособными узлами в режиме `Hot Standby`.
* **Инструменты балансировки:**
  * **HAProxy:** Основной инструмент. Через `http-check` опрашивает API Patroni на порту 8008. На основе кода ответа (200 — мастер, 503 — реплика) динамически переключает трафик. Часто используется вместе с **Keepalived** для обеспечения отказоустойчивости самого балансировщика (VIP-адрес).
  * **PgBouncer:** Легковесный пулер соединений. Обычно ставится между HAProxy и PostgreSQL для управления количеством сессий.
  * **Odyssey:** Современный многопоточный пулер соединений от Яндекса, альтернатива PgBouncer.

Связка **Patroni + HAProxy (+ Keepalived)** позволяет создать полностью автоматизированный и [масштабируемый](./scaling.md) кластер.
