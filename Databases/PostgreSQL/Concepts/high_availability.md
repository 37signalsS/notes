# Отказоустойчивость PostgreSQL (High Availability)

**Актуально для:** PostgreSQL 15–18

## Определения

- **Высокая доступность (High Availability, HA)** — архитектурный подход, обеспечивающий минимизацию времени простоя системы (Downtime) и непрерывность обслуживания запросов за счет автоматического переключения на резервные узлы.
- **RPO (Recovery Point Objective)** — целевая точка восстановления; максимально допустимый объем потери данных в случае аварии. При асинхронной репликации RPO > 0 (равно асинхронному лагу реплики в момент сбоя), при синхронной — RPO = 0.
- **RTO (Recovery Time Objective)** — целевое время восстановления; время, необходимое системе для обнаружения сбоя и автоматического переключения на реплику (Failover). В DCS-кластере (Patroni) RTO складывается из: истечения TTL лидерского ключа + выборы нового мастера + накат WAL на промоутнутой реплике + переключения трафика балансировщиком. На каждый компонент влияют: латентность до DCS, производительность дисков реплик и `recovery_prefetch` — в PostgreSQL 18 он по умолчанию установлен в `try` и предзагружает блоки данных при накате WAL, сокращая I/O-ожидание на Standby и при промоции.
- **Кворум (Quorum)** — математический принцип принятия решений большинством голосов (`floor(N/2) + 1`). Гарантирует легитимность выбора нового мастера и предотвращает разделение кластера.
- **DCS (Distributed Configuration Store)** — распределенное, консистентное хранилище (etcd, Consul, ZooKeeper, Kubernetes), используемое для хранения состояния кластера и реализации механизма распределенных блокировок (**Leader Lock**).
- **Split-Brain** — критическое состояние "раздвоения личности", при котором два узла одновременно считают себя мастерами. Ведет к неконсистентности и повреждению данных.
- **Fencing (Изоляция)** — метод принудительного отсечения старого мастера от ресурсов (сети, дисков или прав записи) для предотвращения Split-Brain.
- **Switchover** — плановая передача роли мастера на один из Standby-узлов (например, для обслуживания железа). В отличие от Failover, выполняется контролируемо без потери данных.

## Базовые концепции

### Режимы репликации и целевое RPO

В HA-кластере RPO и задержка записи (commit latency) — прямой trade-off, определяемый режимом репликации:

| Режим | Как работает | RPO при сбое Primary | Влияние на Latency | Когда использовать |
| :--- | :--- | :--- | :--- | :--- |
| **Асинхронная** (по умолчанию) | Primary подтверждает транзакцию после локальной записи WAL | Равен асинхронному лагу в момент сбоя (0 — секунды; минуты при отставании реплики) | Минимальное | Базовый режим; допустима минимальная потеря |
| **Синхронная** | Primary ждет подтверждения записи WAL на Standby (`synchronous_standby_names`) | 0 | +RTT сети на каждый commit | Финансовые системы, требования RPO = 0 |
| **Кворумная синхронная** (`ANY N`) | Primary ждет подтверждения от N из M Standby | 0 | Ниже, чем у строгой синхронной: commit подтверждает самый быстрый из N | RPO = 0 с терпимостью к одному отказавшему Standby |

Ключевые свойства:

- В синхронном режиме при отсутствии доступной синхронной реплики мастер **блокирует транзакции** (CP-поведение); в асинхронном продолжает принимать записи (AP-поведение). Детали `synchronous_commit` и `synchronous_standby_names` — в [Репликация в PostgreSQL](./replication.md).
- Синхронная репликация между географически удаленными узлами непрактична (RTT добавляется к каждой транзакции). Для междусайтного DR используют асинхронную репликацию + архивирование WAL.
- Параметр `maximum_lag_on_failover` (Patroni) ограничивает, с каким лагом реплика имеет право на промоцию — защищает от failover на отстающую копию.

### Теорема CAP и компромиссы HA
PostgreSQL как реляционная СУБД в распределенной среде подчиняется теореме CAP. При построении HA-кластера выбирается баланс:
- **Consistency (CP)**: Использование синхронной репликации. Если ни одна реплика не подтвердила запись, мастер блокирует транзакции. Приоритет сохранности данных над доступностью.
- **Availability (AP)**: Использование асинхронной репликации. Запись продолжается даже в изоляции. Приоритет доступности на запись, возможен риск потери последних данных (RPO > 0).

### Жизненный цикл Failover (Sequence)
Типовой процесс переключения в кластере под управлением Patroni + etcd:
1.  **Сбой мастера**: Процесс PostgreSQL падает или сервер зависает.
2.  **Истечение TTL**: Patroni на мастере не может обновить ключ в etcd. Через заданный `ttl` ключ удаляется автоматически.
3.  **Leader Election**: Реплики замечают отсутствие лидера и начинают борьбу за ключ в DCS.
4.  **Анализ LSN**: Узлы обмениваются информацией о своей актуальности (Log Sequence Number). Узел с максимальным LSN имеет приоритет на промоцию.
5.  **Promotion**: Победивший узел становится новым Primary, остальные перестраиваются на него.
6.  **Fencing**: Если старый мастер ожил, он обязан убедиться, что лидерство потеряно, прежде чем принимать запросы (через проверку Leader Lock или срабатывание Watchdog).
7.  **Возврат прежнего мастера**: Узел возвращается в кластер репликой — при `use_pg_rewind` Patroni выполняет `pg_rewind` относительно нового мастера, иначе снимает новую `basebackup`. Механизм `pg_rewind` описан в [Репликация в PostgreSQL](./replication.md).

### Switchover и Failover: различие и операции

Switchover и Failover — разные операции с разными гарантиями:

| | Switchover | Failover |
| :--- | :--- | :--- |
| Сценарий | Плановый: обслуживание, обновление железа, перенос в другую зону | Аварийный: мастер упал, завис или недоступен |
| Команда | `patronictl switchover <cluster> --leader <текущий> --candidate <реплика>` | `patronictl failover <cluster> --candidate <реплика>` |
| Ожидание догонки кандидата | Да: старый мастер демутируется, кандидат дожидается синхронизации, затем промоутится | Нет: кандидат промоутится немедленно |
| Потеря закоммиченных данных | Нет | Возможна (WAL, не успевший дойти до кандидата, теряется) |
| Планирование на время | Да (`--scheduled`) | Нет |

Перед плановым обслуживанием автоматику ставят на паузу, чтобы исключить нежелательных выборов:

```bash
patronictl -c /etc/patroni.yml pause <cluster>   # → кластер в режиме maintenance, failover отключен
patronictl -c /etc/patroni.yml resume <cluster>  # → автоматика возобновлена
```

## Практические сценарии

### Предварительные требования

Минимальные требования к окружению HA-кластера с DCS:

- **Количество узлов**: минимум 3 узла PostgreSQL и 3 узла DCS (нечетное число). Из двух узлов DCS кворум не формируется при любом отказе; два узла PostgreSQL дают риск Split-Brain при network partition.
- **Сеть**: стабильная связь узлов с DCS с низкой латентностью (< 10 мс); трафик репликации и heartbeat целесообразно вынести в отдельный VLAN/интерфейс.
- **Синхронизация времени**: NTP/chrony на всех узлах — расхождение часов ломает lease'ы DCS и TLS.
- **Watchdog**: доступность `/dev/watchdog` (модуль `softdog`) или аппаратного watchdog (IPMI/iDRAC/iLO) на каждом узле.
- **Диски**: производительность реплик определяет лаг и RTO; WAL — на быстром хранении.

Полная практическая реализация (установка Patroni + etcd + HAProxy, конфигурация, health-checks) — в [Отказоустойчивый кластер PostgreSQL (Patroni, etcd, HAProxy)](../Operations/high_availability_patroni.md).

### Архитектура Patroni (Стандарт индустрии)
Patroni — это шаблон (Python-агент), который "оборачивает" процесс PostgreSQL и берет на себя всю логику HA. Он управляет репликацией, выполняет выбор нового лидера и предоставляет REST API для балансировщиков. В качестве DCS поддерживаются etcd, Consul, ZooKeeper и Kubernetes (Lease API).

**Механизмы защиты (Deep Dive):**
- **Watchdog (Linux Kernel)**: Patroni использует `/dev/watchdog`. Если агент не сбросит таймер вовремя (например, из-за 100% утилизации CPU или зависания Python), ядро инициирует **Hard Reboot** сервера. Это самый надежный метод Fencing.
- **Leader Lock**: Ключ в etcd имеет короткий TTL (обычно 10–30с). Мастер обязан подтверждать свое право на лидерство чаще, чем раз в `loop_wait` секунд.

### Балансировка трафика и пулы соединений
Для прозрачности переключения используется связка **HAProxy + PgBouncer**.

1.  **HAProxy**:
    - Опрашивает API Patroni (`GET /master`) на всех узлах.
    - Направляет трафик только на узел, вернувший HTTP 200.
    - Читающие запросы (Read Scale) направляются на узлы с `GET /replica`.
2.  **PgBouncer**:
    - В режиме **Transaction Pooling** удерживает клиентские соединения.
    - При Failover запросы встают в очередь на короткое время, пока HAProxy переключает бэкенд на нового мастера. Приложение "видит" лишь небольшую задержку выполнения транзакции.

Альтернативы выделенному балансировщику: плавающий VIP через Keepalived/VRRP, DNS с коротким TTL. Архитектура отказоустойчивости самого балансировщика описана в [Отказоустойчивом кластере (Patroni, etcd, HAProxy)](../Operations/high_availability_patroni.md).

### Синхронизация слотов репликации (PG 17+)
В PostgreSQL 17 решена критическая проблема HA: потеря логических подписок при сбое физического мастера.

- **Проблема**: Логические слоты живут только на Primary. При Failover новый мастер не знает о подписчиках, и логическая репликация требует повторной передачи данных.
- **Решение** — failover слотов. Механизм требует одновременного выполнения условий:
    1. Слот/подписка создана с флагом `failover = true` (`CREATE SUBSCRIPTION ... FAILOVER` или `pg_create_logical_replication_slot('slot', 'pgoutput', false, true)`).
    2. На физическом Standby включен `sync_replication_slots = on` (PG 17+, по умолчанию `off`) — Standby копирует и поддерживает логические failover-слоты с мастера.
    3. Между Primary и Standby существует физический слот репликации (в Patroni его создает оркестратор).
    4. На Standby включен `hot_standby_feedback = on` (обязательное условие синхронизации).
- **Гарантия порядка**: На Primary параметр `synchronized_standby_slots` перечисляет физические слоты Standby — логическое декодирование не "убегает" впереди физической реплики, что гарантирует: в момент failover Standby опережает подписчика.
- **Практика**: Синхронизация слотов асинхронная, поэтому перед плановым switchover убедитесь, что слоты скопированы на Standby (в `pg_replication_slots` колонка `synced = true`). Тогда после failover логические потребители (CDC, ETL) продолжают работу с новым Primary без повторной передачи данных.

## Валидация состояния кластера

### Проверка состояния

```bash
# Состояние кластера: ожидается ровно один Leader, остальные — синхронизированы
patronictl -c /etc/patroni.yml list
# → таблица Member / Host / Role / State / TL / Lag; один узел с Role *leader, у остальных State "streaming"/"syncing"

# Проверки через REST API Patroni (порт 8008 по умолчанию)
curl -s -o /dev/null -w '%{http_code}' http://10.0.0.1:8008/master
# → 200 только на текущем мастере, 503 — на репликах

# Кворум DCS
etcdctl endpoint health --cluster
# → все узлы etcd "healthy"
```

```sql
-- "Я Primary?" — false должно возвращаться ровно на одном узле кластера
SELECT pg_is_in_recovery();

-- Состояние репликации и лаг (replay) на Primary
SELECT client_addr, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn)) AS lag
FROM pg_stat_replication;
```

Детальные запросы мониторинга — в [Репликация в PostgreSQL](./replication.md), таблица метрик и автоматические проверки — в [Отказоустойчивом кластере (Patroni, etcd, HAProxy)](../Operations/high_availability_patroni.md).

### Оценка RTO

RTO при автоматическом failover оценивается как сумма компонентов:

```
RTO ≈ TTL (30 c) + выборы (секунды) + накат WAL на промоутнутом узле + повторная проверка HAProxy (2–3 c)
```

Для типового 3-узлового кластера с TTL 30 c и сетью с латентностью < 1 мс RTO составляет 30–45 c. Сокращать TTL ниже 30 c целесообразно только при высоконадежной DCS-сети. Фактическое RTO измеряется регулярными DR-учениями (см. Золотые правила).

## Сравнение HA-решений

| Характеристика | Patroni (DCS-based) | CloudNativePG (K8s Native) | repmgr (Legacy) |
| :--- | :--- | :--- | :--- |
| **Управление** | Автоматическое (консенсус DCS: etcd/Consul/ZooKeeper/K8s) | Декларативное (CRD / K8s API, Lease) | Полуавтоматическое |
| **Split-Brain** | Watchdog + Leader Lock | Lease API + Fencing | Высокий риск |
| **Сложность** | Высокая (нужен внешний DCS-кластер) | Средняя (нужен Kubernetes-кластер, внешний DCS не нужен) | Низкая |
| **Версия PG** | 9.3–18 | 14–18 | 9.x+ |
| **Инфраструктура** | Bare-metal, VM | Kubernetes (в том числе on-prem) | VM |

## Типичные проблемы и Troubleshooting

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| **Бесконечный рестарт мастера** | Срабатывает Watchdog из-за нехватки ресурсов агенту. | Увеличьте приоритет процесса Patroni (`nice`, `ionice`) или ресурсы VM. |
| **Multiple Primaries** | Ошибка Fencing или отсутствие связи с DCS. | Проверьте сетевую связность до etcd. Включите аппаратный STONITH. |
| **Реплика не промоутится** | Слишком большой Replication Lag. | Настройте `maximum_lag_on_failover` в Patroni. Ускорьте диски на репликах. |
| **DCS Quorum Lost** | Отказ 2-х узлов etcd из 3-х. | Восстановите etcd из бэкапа или принудительно пересоздайте кворум. |
| **Синхронная репликация блокирует запись** | Недоступна синхронная реплика (сеть, диск, падение PostgreSQL). | Проверьте `sync_state` в `pg_stat_replication` и сеть до Standby; для неотложных некритичных записей — `SET LOCAL synchronous_commit = local`. |
| **Возвратившийся узел не присоединяется к кластеру** | WAL бывшего мастера рассинхронизировался с новым Primary (сбой был длительным). | Возврат через `pg_rewind` (`use_pg_rewind` в Patroni) или новую `basebackup`; ручное "приклеивание" узла к кластеру недопустимо. |
| **Трафик после failover идет на старый мастер** | HAProxy еще не перепроверил бэкенд или кеширует соединение. | Проверьте `GET /master` на всех узлах (200 должен возвращать только новый мастер), `show stat` в HAProxy и интервал `inter` health-check. |

## Золотые правила HA (Golden Rules)

1.  **Нечетный кворум**: Всегда используйте минимум 3 узла для DCS (etcd/Consul) и 3 узла базы данных.
2.  **Изоляция сети**: Выносите трафик репликации и heartbeat в отдельные VLAN/интерфейсы.
3.  **Аппаратный Watchdog**: Включайте `/dev/watchdog` (программный или IPMI) для гарантированного Fencing.
4.  **Синхронность с умом**: Используйте синхронную репликацию только если бизнес-логика не допускает потерю данных (финансы). Помните о деградации Latency.
5.  **Регулярное тестирование**: Проводите "DR-учения" (Chaos Testing) раз в квартал — отключайте питание мастера и замеряйте реальный RTO.
