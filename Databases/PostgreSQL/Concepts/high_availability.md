# Отказоустойчивость PostgreSQL (High Availability)

## Определения

- **Высокая доступность (High Availability, HA)** — архитектурный подход, обеспечивающий минимизацию времени простоя системы и непрерывность обслуживания запросов.
- **RPO (Recovery Point Objective)** — целевая точка восстановления; допустимый объем потери данных в случае аварии. При асинхронной репликации RPO > 0, при синхронной — RPO = 0.
- **RTO (Recovery Time Objective)** — целевое время восстановления; время, необходимое для переключения на резервный узел. В современных кластерах (Patroni) составляет 30–60 секунд.
- **Кворум (Quorum)** — минимально необходимое количество голосов в распределенной системе для принятия легитимного решения (например, выбора мастера). Рассчитывается как `(N/2) + 1`.
- **DCS (Distributed Configuration Store)** — распределенное хранилище (etcd, Consul), обеспечивающее консистентность метаданных кластера и механизм блокировок (Leader Lock).
- **Split-Brain** — критическое состояние кластера, при котором два или более узла одновременно считают себя мастерами, что ведет к повреждению данных.
- **Fencing (Изоляция)** — принудительная изоляция неисправного мастера от записи данных. Механизмы: STONITH (Shoot The Other Node In The Head), программный Watchdog или сетевая изоляция.

## Базовые концепции

### Теорема CAP и PostgreSQL
В контексте HA PostgreSQL часто приходится выбирать между **Consistency** (согласованностью) и **Availability** (доступностью):
- **Синхронная репликация**: Приоритет консистентности. Если реплика недоступна, мастер останавливает запись. Кластер жертвует доступностью ради сохранности каждой транзакции.
- **Асинхронная репликация**: Приоритет доступности. Запись продолжается даже при потере связи с репликами. Возможна потеря последних транзакций при failover.

### Метрики надежности кластера

| Тип репликации | RPO | Производительность | Применение |
| :--- | :--- | :--- | :--- |
| **Асинхронная** | > 0 | Максимальная | Большинство стандартных приложений |
| **Синхронная** | 0 | Ниже (зависит от network latency) | Финансовые транзакции, критичные данные |
| **Кворумная** | 0 | Средняя | Баланс между надежностью и скоростью |

### Роль консенсуса (Raft/Paxos)
Основа современной отказоустойчивости — внешняя координация через DCS.
1.  **Leader Election**: Узел захватывает ключ в DCS на определенное время (TTL).
2.  **Heartbeat**: Patroni постоянно обновляет TTL ключа. Если мастер «завис», TTL истекает.
3.  **Демократия**: Оставшиеся узлы проверяют свои позиции по LSN (Log Sequence Number) и выбирают наиболее актуальный для промоции.

## Практические сценарии

### Архитектура Patroni (Стандарт индустрии)
Patroni управляет жизненным циклом инстанса PostgreSQL, интегрируясь с DCS.

**Механизмы защиты от Split-Brain:**
- **Leader Lock**: Только владелец ключа в etcd может быть мастером.
- **Watchdog (Linux)**: Если Patroni не может обновить TTL ключа из-за зависания ОС, Watchdog принудительно перезагружает сервер по таймеру.
- **Fencing через API**: Приложение/балансировщик опрашивает API Patroni и отключает трафик к узлам, не являющимся мастерами.

### Обслуживание кластера (Maintenance)
Для проведения работ на мастере (апгрейд ОС, замена железа) используется режим **Pause/Maintenance**:
1.  Кластер переводится в режим `pause` через `patronictl`.
2.  Patroni перестает автоматически переключать роли при остановке БД.
3.  После работ выполняется ручной `switchover` и снятие режима паузы.

### Балансировка и пулы соединений (HAProxy + PgBouncer)
Для прозрачного Failover используется многослойная схема:
1.  **L4 Балансировщик (HAProxy)**: Проверяет статус через HTTP API Patroni (`/master`).
2.  **Пулер соединений (PgBouncer/Odyssey)**: 
    - Сглаживает всплески соединений.
    - В режиме **Transaction Pooling** позволяет приложениям пережить кратковременный Failover без обрыва всех сессий (кроме текущей транзакции).
3.  **Virtual IP (Keepalived)**: Позволяет клиентам обращаться к одной точке входа, которая может переключаться между активными балансировщиками.

### Сравнение решений для HA

| Инструмент | Управление | Хранение состояния | Плюсы | Минусы |
| :--- | :--- | :--- | :--- | :--- |
| **Patroni** | Python-агент | etcd / Consul | Автоматизация, API, гибкость | Требует DCS (etcd) |
| **repmgr** | CLI + демон | Внутри PostgreSQL | Не требует внешних систем | Сложнее предотвратить Split-Brain |
| **Stolon** | Прокси-слой | etcd / Consul | Нативная изоляция через прокси | Высокая сложность, вносит доп. задержки |

### PostgreSQL HA в Kubernetes (CloudNativePG)
Современные операторы (CloudNativePG) отказываются от Patroni в пользу нативных ресурсов K8s:
- **API Server как DCS**: Kubernetes сам выступает хранилищем состояния.
- **Нативные пробы**: Kubernetes Liveness/Readiness пробы заменяют проверки Patroni.
- **Self-healing**: Автоматическое пересоздание подов и переливка данных.

## Дополнительная информация

### Рекомендации
- **Нечетное число узлов DCS**: Минимум 3 узла etcd для обеспечения кворума.
- **Изоляция сети**: Используйте выделенные каналы для репликации, чтобы избежать задержек (Replication Lag) из-за пользовательского трафика.
- **Тестирование Failover**: Регулярно проводите «Chaos Testing» (отключение питания, обрыв сети) для проверки реального RTO.
