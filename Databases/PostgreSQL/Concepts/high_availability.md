# Отказоустойчивость PostgreSQL

## Определения

- **Высокая доступность (High Availability, HA)**: Свойство системы минимизировать время простоя. Общие принципы описаны в **[обзоре High Availability](../../../Concepts/High_Availability/ha_overview.md)**.
- **Кластерный менеджер (Cluster Manager)**: Специализированное ПО (например, Patroni), которое автоматизирует управление жизненным циклом PostgreSQL, обеспечивая мониторинг и автоматическое переключение ролей.
- **DCS (Distributed Configuration Store)**: Внешнее распределенное хранилище (etcd, Consul, ZooKeeper), используемое кластерным менеджером для хранения состояния системы и координации выбора лидера.
- **Лидер (Leader)**: Узел кластера, выполняющий роль основного сервера (Master) и принимающий запросы на запись.

## Базовые концепции

### Репликация как основа HA

Любая стратегия обеспечения отказоустойчивости PostgreSQL базируется на наличии как минимум одной актуальной реплики.

- **Асинхронная репликация**: Высокая производительность, но риск потери данных при сбое.
- **Синхронная репликация**: Гарантия сохранности данных ценой задержки на запись.
Подробнее механизмы описаны в **[Репликация в PostgreSQL](./replication.md)**.

### Проблема автоматического переключения (Failover)

При ручном управлении сбой мастера требует вмешательства администратора для повышения реплики (`pg_ctl promote`), что увеличивает время восстановления (MTTR) и вносит риск человеческой ошибки. Механизмы автоматизации описаны в **[Failover и Heartbeat](../../../Concepts/High_Availability/ha_failover_mechanisms.md)**.

### Предотвращение Split-Brain

Критически важно исключить ситуацию, когда два узла считают себя мастерами. В PostgreSQL это решается через механизмы кворума в DCS и использование **STONITH (Shoot The Other Node In The Head)** или аналогичных методов изоляции (fencing). См. **[проблема Split-Brain в репликации](../../../Concepts/replication.md#проблема-split-brain-и-решение-через-кворум)**.

## Практические сценарии

### Patroni: Стандарт де-факто

**Patroni** — это шаблон (template) для создания отказоустойчивых решений на базе PostgreSQL. Он работает как "обертка" над процессом `postgres`.

- **Ключевые функции**:
  - **Автоматический Failover**: При потере связи с DCS или падении процесса мастер-узел снимает с себя роль лидера. Реплики инициируют выборы нового лидера через DCS.
  - **Управление конфигурацией**: Изменение параметров `postgresql.conf` через DCS сразу на всем кластере.
  - **Интеграция с pg_rewind**: Автоматическая синхронизация бывшего мастера с новым после сбоя.
- **Kubernetes**: Для облачных сред используются операторы (например, **CloudNativePG**), реализующие логику Patroni в виде нативных ресурсов Kubernetes. См. **[Развертывание в Kubernetes](../Operations/kubernetes_deployment.md)**.

### Механизм failover в Patroni

Patroni использует **TTL-bound leader key** в DCS (etcd):

1. **Heartbeat**: master держит leader key в etcd с TTL и обновляет его каждые N секунд (по умолчанию 10 с).
2. **Потеря связи**: если master теряет связь с etcd (сеть, падение), он не может обновить ключ. До истечения TTL Patroni переводит master в режим **pause** — мастер прекращает принимать writes, даже если с клиентами связь есть.
3. **Выборы**: когда TTL истекает, реплики обнаруживают это и через **CAS (compare-and-swap)** в etcd проверяют, что lock свободен. Реплика с наибольшим LSN (наименьшим WAL-лагом) забирает lock и становится новым primary.
4. **Возврат старого master**: после восстановления связи с etcd старый master обнаруживает, что больше не leader, и автоматически демотируется до standby. При расхождении WAL используется **pg_rewind** для синхронизации.
5. **Split-brain невозможен**: только один узел может удерживать etcd lock в любой момент времени.

### Patroni при падении DC

- Patroni автоматически инициирует failover, если replica в другом DC доступна и может достичь etcd.
- Мониторинг: `patronictl list`.
- После восстановления old primary — убедиться, что он вернулся как replica (не primary).
- Перед switchback (обратным переключением) проверить репликационный лаг.

### Сценарий: Падение мастера под нагрузкой (Crash Failover)

**Исходное состояние:** Patroni-кластер (3 ноды) + etcd (3 ноды) + HAProxy, синхронная репликация.

**Автоматический failover:**

1. **Timeout лидерного ключа**: мастер обновляет leader key в etcd каждые 10 с. При падении мастера обновление прекращается. Через TTL (30 с) ключ истекает.
2. **Election**: реплики обнаруживают свободный lock и через CAS в etcd инициируют выборы. Побеждает реплика с наименьшим WAL-лагом (наибольший LSN).
3. **Промоция**: Patroni выполняет `pg_ctl promote` на выбранной реплике — она становится новым мастером.
4. **HAProxy**: health check на `/primary` возвращает `200 OK` для нового мастера. Трафик writes переключается автоматически.

**Действия администратора после failover:**

1. Проверить состояние кластера:
   ```bash
   patronictl list
   # →
   # +------------+--------------+---------+---------+----+-----------+
   # | Cluster    | Member       | Host    | Role    | TL | Lag in MB |
   # +------------+--------------+---------+---------+----+-----------+
   # | pg-cluster | pg-cluster-0 | 1.2.3.4 | Leader  |  2 |           |
   # | pg-cluster | pg-cluster-1 | 1.2.3.5 | Replica |  2 |         0 |
   # | pg-cluster | pg-cluster-2 | 1.2.3.6 | Replica |  2 |         0 |
   # +------------+--------------+---------+---------+----+-----------+
   ```
   Убедиться: один узел — `running` как `master` (Leader), остальные — `running` как `replica`.

2. Дождаться возврата старого мастера. При подключении Patroni автоматически:
   - Определяет, что узел больше не leader.
   - Запускает `pg_rewind` для синхронизации timeline (полный base backup не требуется).
   - Переводит узел в standby и запускает репликацию с нового мастера.

   Если старый мастер не может синхронизироваться (повреждённые WAL) — выполнить `pg_basebackup` с нового мастера.

**Ключевые настройки для RPO=0:**

```yaml
# patroni.yml
synchronous_mode: true
postgresql:
  parameters:
    synchronous_commit: 'on'                # или 'remote_apply'
    synchronous_standby_names: '*'          # любая синхронная реплика
```

Подробнее об уровнях синхронности — [Репликация](./replication.md#уровни-synchronous_commit).

**Защита от промоции отстающей реплики:**

```yaml
maximum_lag_on_failover: 1048576  # 1 MB — реплика с лагом больше не участвует в выборах
```

**Резервное копирование:**

- **pgBackRest**: инкрементальные бэкапы, параллельное сжатие, нативное S3.
- **WAL archiving**: непрерывная архивация → PITR на любой момент времени.
- Подробнее — [Backup and Recovery](./backup_and_recovery.md).

### Балансировка и разделение трафика (Read/Write Split)

Для прозрачного переключения приложений используются балансировщики, которые опрашивают API Patroni (health checks) для определения текущей роли узла.

1. **HAProxy**: Классический балансировщик. Опрашивает порт Patroni (обычно 8008). Подробная конфигурация приведена в разделе **[HAProxy: Отказоустойчивая балансировка PostgreSQL](../../../WebServers/haproxy_overview.md#отказоустойчивая-балансировка-postgresql-patroni)**.
    - Порт отвечает `200 OK`, если узел — лидер.
    - Порт отвечает `503 Service Unavailable`, если узел — реплика.
2. **Keepalived**: Обеспечивает плавающий IP (VIP) между несколькими экземплярами HAProxy для устранения SPOF на уровне балансировки.
3. **Пулеры соединений**: **PgBouncer** или **Odyssey** устанавливаются между балансировщиком и БД для эффективного управления сессиями.

### Пример архитектуры кластера

Типовая схема отказоустойчивого кластера:
`Приложение -> Keepalived (VIP) -> HAProxy -> Patroni (PostgreSQL) + etcd (DCS)`.

Практический пример реализации доступен в разделе: **[HA-кластер PostgreSQL с Patroni в Docker Compose](../../../Docker/Docker_compose/docker_compose_advanced_topics.md#пример-ha-кластер-postgresql-с-patroni)**.
