# Высокая доступность (High Availability) в PostgreSQL

### Определения

* **Высокая доступность (High Availability, HA):** Способность системы продолжать функционировать при частичных сбоях (например, отказе одного из серверов) за счет избыточности и автоматизации.
* **Отработка отказа (Failover):** Процесс автоматического переключения на резервный компонент (например, реплику) при сбое основного.
* **Split-Brain:** Критическая ошибка в кластерных системах, при которой из-за нарушения связи два узла одновременно решают, что они являются главными (мастерами), что приводит к рассинхронизации данных.

### Основные концепции

1. **Фундамент — репликация:** Основой любой HA-стратегии является наличие как минимум одной синхронизированной резервной копии сервера (реплики), готовой взять на себя нагрузку. Подробнее см. **[Репликация в PostgreSQL](./replication.md)**.
2. **Проблема — автоматизация:** В ручном режиме при сбое мастера администратор должен сам "повысить" реплику до нового мастера (`pg_ctl promote`). Это создает простой и несет риск человеческой ошибки.
3. **Решение — менеджеры кластера:** Для минимизации простоя и предотвращения проблемы "Split-Brain" используются специализированные системы, обеспечивающие **автоматическую отработку отказа (Automatic Failover)**.

### Практические сценарии

#### Решение №1: Patroni

**Patroni** — это open-source стандарт де-факто для создания отказоустойчивых кластеров PostgreSQL. Он автоматизирует управление жизненным циклом кластера, используя внешнее распределенное хранилище конфигурации (DCS) для координации.

* **Ключевые особенности Patroni:**
  * **Автоматический Failover:** Patroni непрерывно отслеживает состояние мастера. Если мастер становится недоступным, он автоматически выбирает лучшую реплику и повышает ее до нового мастера.
  * **Защита от Split-Brain:** Для хранения состояния кластера (кто мастер, какие есть реплики) Patroni использует `etcd`, `Consul` или `ZooKeeper` как единый источник правды, что предотвращает "Split-Brain".
  * **Восстановление бывшего мастера:** Когда отказавший мастер возвращается в строй, Patroni автоматически настраивает его как реплику к новому мастеру, используя `pg_rewind`.
* **Развертывание в Kubernetes:** Для производственных сред в Kubernetes рекомендуется использовать специализированные операторы, такие как [CloudNativePG](../Operations/kubernetes_deployment.md), которые часто используют принципы Patroni под капотом.

#### Роль балансировщиков нагрузки и разделение трафика (Read/Write Split)

В HA-конфигурациях приложения не должны подключаться напрямую к узлам БД. Вместо этого используется балансировщик, который является единой точкой входа. Связка Patroni и балансировщика позволяет реализовать эффективную схему разделения нагрузки.

*   **Как это работает:** Patroni предоставляет **REST API**, через которое можно в любой момент узнать текущую роль каждого узла в кластере (например, `master`, `replica`). Балансировщик нагрузки регулярно опрашивает этот API.
*   **Маршрутизация трафика:**
    *   Запросы на **запись** (INSERT, UPDATE, DELETE) направляются только на узел, который API пометил как `master`.
    *   Запросы на **чтение** (SELECT) могут распределяться между всеми работоспособными узлами: как `master`, так и `replica`.
*   **Инструменты:**
    *   **HAProxy:** Может выступать в роли "умного" прокси, который через `http-check` опрашивает API Patroni и на основе ответа динамически направляет трафик в разные бэкенды (один для записи, другой для чтения).
    *   **PgBouncer:** Легковесный пулер соединений, который снижает нагрузку на PostgreSQL и также может быть настроен для базовой маршрутизации.

Связка **Patroni + Балансировщик** позволяет создать полностью автоматизированный и [масштабируемый](./scaling.md) кластер с разделением нагрузки по чтению и записи.
