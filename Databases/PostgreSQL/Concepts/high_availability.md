# Отказоустойчивость PostgreSQL

## Определения

- **Высокая доступность (High Availability, HA)** — свойство системы минимизировать время простоя и обеспечивать непрерывность сервиса.
- **RPO (Recovery Point Objective)** — максимально допустимый объем потери данных при сбое (в PostgreSQL зависит от типа репликации).
- **RTO (Recovery Time Objective)** — максимально допустимое время восстановления системы после сбоя (в Patroni обычно составляет 30–60 секунд).
- **Кластерный менеджер (Cluster Manager)** — ПО (например, Patroni), автоматизирующее мониторинг, выбор лидера и восстановление узлов.
- **DCS (Distributed Configuration Store)** — распределенное хранилище (etcd, Consul), используемое кластером для координации и хранения состояния (Leader Lock).
- **Fencing (Изоляция)** — механизм предотвращения ситуации, когда старый мастер продолжает принимать запись после сбоя (защита от Split-Brain).

## Базовые концепции

### Метрики надежности кластера

| Параметр | Асинхронная репликация | Синхронная репликация |
| :--- | :--- | :--- |
| **RPO** | > 0 (возможна потеря WAL-логов) | 0 (данные подтверждены на реплике) |
| **RTO** | Низкий (быстрая промоция) | Может быть выше из-за ожидания подтверждений |
| **Производительность** | Максимальная (нет задержек сети) | Ниже (зависит от latency между узлами) |

### Репликация как фундамент HA
Отказоустойчивость невозможна без актуальной копии данных. В PostgreSQL HA строится на базе потоковой репликации. Основная задача HA-менеджера — автоматизировать процесс `pg_ctl promote`. Подробнее см. **[Репликация в PostgreSQL](./replication.md)**.

### Роль кворума и DCS
Для исключения **Split-Brain** (ситуации «двух мастеров») используется внешнее хранилище с поддержкой консенсуса (Raft/Paxos).
1.  **Лидерный ключ**: Только один узел может удерживать ключ в DCS.
2.  **TTL (Time To Live)**: Если мастер падает, он перестает обновлять TTL ключа в DCS.
3.  **Перевыборы**: Когда ключ истекает, реплики начинают процесс выбора нового лидера.

## Практические сценарии

### Patroni: Отраслевой стандарт
**Patroni** — это Python-приложение, работающее как управляющая оболочка над процессом PostgreSQL.

**Алгоритм работы при сбое мастера:**
1.  **Детекция**: Мастер не смог обновить TTL ключа в etcd (сетевой раздел или падение).
2.  **Защита**: Patroni на старом мастере переводит БД в `read-only` или выключает её (fencing).
3.  **Выборы**: Реплики сравнивают свои LSN (Log Sequence Number). Реплика с наиболее актуальными данными забирает lock в etcd.
4.  **Промоция**: Выбранная реплика становится новым мастером (`primary`).
5.  **Переключение трафика**: Балансировщик (HAProxy) видит смену ролей через API Patroni (порт 8008).

### Отказоустойчивость в Kubernetes
В K8s традиционный Patroni часто заменяется специализированными операторами:

- **CloudNativePG (CNPG)** — современный оператор, который не требует etcd/Patroni, а использует нативные примитивы Kubernetes (API-сервер) для управления кворумом.
- **Zalando Postgres Operator** — использует Patroni внутри контейнеров.
Подробнее см. **[Развертывание в Kubernetes](../Operations/kubernetes_deployment.md)**.

### Балансировка и Read/Write Split
Для прозрачного доступа приложения к кластеру используется связка:
1.  **HAProxy**: Опрашивает API Patroni. Если `/primary` возвращает 200 — это мастер. Если `/replica` — это реплика для чтения.
2.  **Keepalived**: Обеспечивает виртуальный IP (VIP) для HAProxy, устраняя единую точку отказа на уровне балансировщика.
3.  **PgBouncer / Odyssey**: Пулеры соединений для эффективной работы с тысячами клиентских сессий.

### Сценарий: Восстановление после Failover
После того как мастер был заменен, старый мастер должен вернуться в кластер как реплика.
1.  **pg_rewind**: Инструмент, который «отматывает» WAL-логи старого мастера до точки расхождения с новым, исключая необходимость полной переливки данных (base backup).
2.  **Автоматизация**: Patroni выполняет `pg_rewind` автоматически, если это настроено в `postgresql.parameters`.
