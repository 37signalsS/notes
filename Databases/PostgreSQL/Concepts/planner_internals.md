# Математика планировщика PostgreSQL (Cost Model)

## Определения

**Планировщик (Query Planner/Optimizer)** — компонент PostgreSQL, который анализирует поступивший запрос и строит дерево путей выполнения, выбирая наиболее эффективный (самый дешевый) план на основе стоимостной модели.

*   **Стоимость (Cost)** — абстрактная, безразмерная величина, представляющая оценку времени выполнения операции. Базовая единица измерения — чтение одной последовательной страницы с диска (`seq_page_cost = 1.0`).
*   **Startup Cost (Начальная стоимость)** — оценка затрат до момента возврата первой строки (например, время на построение хеш-таблицы в Hash Join).
*   **Total Cost (Общая стоимость)** — полная оценка затрат до завершения работы узла плана.
*   **Селективность (Selectivity)** — число от 0 до 1, представляющее долю строк, которые будут возвращены предикатом (например, `WHERE status = 'active'`).
*   **Кардинальность (Cardinality)** — ожидаемое количество строк, возвращаемых узлом плана. Рассчитывается как `Total Rows * Selectivity`.
*   **MCV (Most Common Values)** — список наиболее часто встречающихся значений в столбце и их относительная частота. Позволяет точно оценивать селективность для неравномерно распределенных данных.
*   **Histogram (Гистограмма)** — разбиение диапазона значений столбца на корзины равной частоты. Помогает оценивать селективность для условий диапазона (`>`, `<`, `BETWEEN`).
*   **Correlation (Корреляция)** — статистическая связь между физическим порядком строк на диске и логическим порядком значений в столбце.
*   **Effective Cache Size** — параметр планировщика, оценивающий объем доступного дискового кэша (OS + Postgres), влияющий на вероятность того, что Index Scan не потребует реального I/O.

## Базовые концепции

### Жизненный цикл планирования

1.  **Parsing/Rewriting**: Преобразование SQL в дерево запроса и применение правил (Views, RLS).
2.  **Path Generation**: Генерация возможных способов выполнения (Paths). Для каждого узла (Scan, Join, Sort) создаются альтернативные пути.
3.  **Path Selection**:
    *   **Dynamic Programming**: Используется для небольшого количества соединений (обычно < 12). Тщательный перебор комбинаций.
    *   **GEQO (Genetic Query Optimizer)**: Включается при превышении `geqo_threshold`. Использует эвристические генетические алгоритмы для поиска «достаточно хорошего» плана, когда полный перебор слишком дорог.
4.  **Plan Generation**: Превращение выбранного пути в финальный план выполнения.

### Стоимостная модель (Cost Model)

Планировщик суммирует затраты на ввод-вывод (I/O) и обработку данных процессором (CPU).

**Основные константы стоимости (GUC):**

| Параметр | Значение по умолчанию | Описание |
| :--- | :--- | :--- |
| `seq_page_cost` | 1.0 | Чтение одной страницы последовательно. |
| `random_page_cost` | 4.0 | Чтение одной страницы в случайном порядке (HDD). |
| `cpu_tuple_cost` | 0.01 | Обработка одного кортежа (строки). |
| `cpu_index_tuple_cost` | 0.005 | Обработка одной записи в индексе. |
| `cpu_operator_cost` | 0.0025 | Выполнение оператора или функции. |
| `parallel_setup_cost` | 1000.0 | Затраты на запуск параллельных воркеров. |
| `parallel_tuple_cost` | 0.1 | Затраты на передачу кортежа между процессами. |

**Базовая формула Seq Scan:**
`Total Cost = (N_Pages * seq_page_cost) + (N_Rows * cpu_tuple_cost) + (N_Rows * Filter_Cost)`

### Сбор и анализ статистики

Данные хранятся в системном каталоге `pg_statistic`, но для чтения удобно использовать представление `pg_stats`.

*   **n_distinct**: Количество уникальных значений. Отрицательное число означает долю от общей таблицы (например, -1 = уникальный столбец).
*   **Correlation**: Значения близки к 1 или -1 делают Index Scan чрезвычайно эффективным, так как данные читаются почти последовательно.
*   **Extended Statistics**: Позволяет учитывать зависимость между колонками (Multivariate Statistics).
    *   `dependencies`: Для функциональных зависимостей (например, `zip_code` определяет `city`).
    *   `ndistinct`: Количество уникальных комбинаций колонок.

### Алгоритмы соединений (Join Strategies)

1.  **Nested Loop**:
    *   *Принцип*: Для каждой строки из внешней таблицы сканируется внутренняя.
    *   *Когда выбирается*: Малые выборки, наличие эффективного индекса на внутренней таблице.
    *   *Startup Cost*: Близка к 0.
2.  **Merge Join**:
    *   *Принцип*: Обе таблицы сортируются по ключу соединения, затем объединяются в один проход.
    *   *Когда выбирается*: Большие наборы данных, ключи уже отсортированы (индексом) или требуется сортировка для последующих операций.
    *   *Startup Cost*: Высокая (затраты на сортировку).
3.  **Hash Join**:
    *   *Принцип*: Строится хеш-таблица для внутренней таблицы в RAM, затем внешняя таблица сканируется и проверяется по хешу.
    *   *Когда выбирается*: Большие несортированные наборы, которые помещаются в `work_mem`.
    *   *Startup Cost*: Высокая (построение хеш-таблицы).

## Практические сценарии

### Предварительные требования

*   Права суперпользователя или владельца таблицы для изменения настроек статистики.
*   Установленное расширение `pg_stat_statements` для мониторинга часто выполняемых планов (рекомендуется).

### 1. Тюнинг весов под оборудование (SSD/NVMe)

Если база работает на быстрых SSD/NVMe дисках, стандартный `random_page_cost = 4.0` заставляет планировщик «бояться» индексов.

```sql
-- Для всей системы в postgresql.conf
random_page_cost = 1.1

-- Для конкретной сессии для теста
SET random_page_cost = 1.1;

-- Для конкретного табличного пространства (если SSD только там)
ALTER TABLESPACE fast_ssd SET (random_page_cost = 1.1);
```
**Результат**: Планировщик начнет чаще использовать `Index Scan` вместо `Seq Scan`.

### 2. Устранение ошибок оценки при корреляции колонок

Если запрос содержит `WHERE country = 'US' AND city = 'New York'`, планировщик перемножит их селективности, считая их независимыми, что приведет к заниженной кардинальности.

**Решение — Расширенная статистика:**
```sql
CREATE STATISTICS stts_city_country (dependencies) ON city, country FROM users;
ANALYZE users;
```
Проверка сбора статистики:
```sql
SELECT stxname, stxkeys, stxdependencies FROM pg_statistic_ext WHERE stxname = 'stts_city_country';
```

### 3. Анализ точности планировщика через EXPLAIN

Ключевой метод диагностики — сравнение `rows` (оценка) и `actual rows` (реальность).

```sql
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM orders WHERE status = 'shipped' AND created_at > '2026-01-01';
```
**На что смотреть:**
- **Rows vs Actual Rows**: Расхождение более чем в 10 раз говорит об устаревшей статистике или функциональной зависимости.
- **Buffers**: `shared hit` (из кэша) vs `shared read` (с диска). Если `read` велик, возможно, `effective_cache_size` настроен неверно.
- **Planning Time**: Если планирование занимает сотни мс, возможно, слишком велик `from_collapse_limit` или `join_collapse_limit`.

### 4. Исправление устаревшей статистики

Если после массовой вставки планировщик выбирает плохие планы:

```sql
-- Быстрый анализ конкретной таблицы
ANALYZE VERBOSE users;

-- Увеличение детализации для конкретной колонки (больше корзин в гистограмме)
ALTER TABLE users ALTER COLUMN status SET STATISTICS 500;
ANALYZE users;
```

## Дополнительная информация

### JIT-компиляция

Начиная с PostgreSQL 11, планировщик может компилировать выражения на лету (LLVM).
*   `jit_above_cost`: Порог (default 100000), выше которого включается JIT.
*   `jit_optimize_above_cost`: Порог (default 500000), выше которого применяются агрессивные оптимизации JIT.

### GEQO (Genetic Query Optimizer)

Если запрос содержит слишком много JOIN-ов, планировщик переключается на генетический поиск.
*   `geqo_threshold`: По умолчанию 12. Если таблиц в соединении больше, точный перебор отключается.
*   **Риск**: При GEQO план может меняться случайным образом между запусками одного и того же запроса.
