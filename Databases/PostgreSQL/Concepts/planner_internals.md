# Математика планировщика PostgreSQL (Cost Model)

**Актуально для:** PostgreSQL 15–18 (поддерживаемые релизы на октябрь 2026). PostgreSQL 14 переходит в EOL в ноябре 2026; описанные здесь особенности cost model совпадают с 15+. PostgreSQL 19 описан как Beta 4 (сентябрь 2026); GA ожидается во второй половине 2026, детали могут меняться.

## Определения

**Планировщик (Query Planner/Optimizer)** — компонент PostgreSQL, который анализирует поступивший запрос и строит дерево путей выполнения, выбирая наиболее эффективный (самый дешевый) план на основе стоимостной модели.

*   **Стоимость (Cost)** — абстрактная, безразмерная величина, представляющая оценку времени выполнения операции. Базовая единица измерения — чтение одной последовательной страницы с диска (`seq_page_cost = 1.0`).
*   **Startup Cost (Начальная стоимость)** — оценка затрат до момента возврата первой строки (например, время на построение хеш-таблицы в Hash Join).
*   **Total Cost (Общая стоимость)** — полная оценка затрат до завершения работы узла плана.
*   **Селективность (Selectivity)** — число от 0 до 1, представляющее долю строк, которые будут возвращены предикатом (например, `WHERE status = 'active'`).
*   **Кардинальность (Cardinality)** — ожидаемое количество строк, возвращаемых узлом плана. Рассчитывается как `Total Rows * Selectivity`.
*   **MCV (Most Common Values)** — список наиболее часто встречающихся значений в столбце и их относительная частота. Позволяет точно оценивать селективность для неравномерно распределенных данных.
*   **Histogram (Гистограмма)** — разбиение диапазона значений столбца на корзины равной частоты. Помогает оценивать селективность для условий диапазона (`>`, `<`, `BETWEEN`).
*   **Correlation (Корреляция)** — статистическая связь между физическим порядком строк на диске и логическим порядком значений в столбце.
*   **Effective Cache Size (`effective_cache_size`)** — параметр планировщика, оценивающий объем доступного дискового кэша (OS + Postgres), влияющий на вероятность того, что Index Scan не потребует реального I/O.
*   **Path (Путь)** — усеченное представление плана, содержащее ровно ту информацию, которая нужна планировщику для принятия решения. Полное дерево плана (Plan) строится только один раз — после выбора самого дешёвого пути.
*   **Custom Plan (Кастомный план)** — план, построенный заново под конкретные значения параметров подготовленного запроса. Учитывает селективность по фактическим значениям, но требует времени планирования при каждом выполнении.
*   **Generic Plan (Обобщённый план)** — план, не зависящий от значений параметров. Строится один раз и переиспользуется, но теряет знание о распределении данных для конкретных значений.
*   **Query ID (Идентификатор запроса)** — хеш-значение, идентифицирующее текст запроса с выделенными константами. Используется `pg_stat_statements`, журналированием и (с PostgreSQL 19) механизмом plan advice.
*   **plan_cache_mode** — параметр, определяющий, когда для подготовленного запроса используется generic plan, а когда custom plan.

## Базовые концепции

### Жизненный цикл планирования

1.  **Parsing/Rewriting**: Преобразование SQL в дерево запроса и применение правил (Views, RLS).
2.  **Path Generation**: Генерация возможных способов выполнения (Paths). Для каждого узла (Scan, Join, Sort) создаются альтернативные пути.
3.  **Path Selection**:
    *   **Dynamic Programming**: Используется для небольшого количества соединений (обычно < 12). Тщательный перебор комбинаций.
    *   **GEQO (Genetic Query Optimizer)**: Включается, когда число элементов `FROM` достигает `geqo_threshold`. Использует эвристические генетические алгоритмы для поиска «достаточно хорошего» плана, когда полный перебор слишком дорог.
4.  **Plan Generation**: Превращение выбранного пути в финальный план выполнения.

### Пределы свёртки: `from_collapse_limit` и `join_collapse_limit`

Планировщик не перебирает все возможные порядки соединения. Перед началом перебора он сворачивает дерево запроса в плоский список элементов `FROM`, и размер этого списка ограничен двумя параметрами.

| Параметр | Значение по умолчанию | Что ограничивает |
| :--- | :--- | :--- |
| `from_collapse_limit` | 8 | Слияние подзапросов с вышестоящим запросом (subquery pull-up). |
| `join_collapse_limit` | Значение `from_collapse_limit` | Разворачивание явных конструкций `JOIN` в плоский список (кроме `FULL JOIN`). |

Механика: если после слияния получается список не длиннее заданного лимита, свёртка выполняется; иначе поддерево остаётся отдельным элементом `FROM` и планируется изолированно. Оба параметра — компромисс между временем планирования и качеством плана:

*   **Меньшее значение** — планирование быстрее, но перебор неполон: подзапрос приходится обрабатывать как «чёрный ящик», его нельзя переставить вместе с остальными таблицами, а стоимость его результата оценивается грубо.
*   **Большее значение** — выше вероятность найти оптимальный порядок соединения, но время планирования растёт. Рост экспоненциальный по числу таблиц, а не линейный, поэтому лимиты нельзя увеличивать «на всякий случай».

Значение `join_collapse_limit = 1` запрещает любую перестановку явных `JOIN`: соединения выполняются в том порядке, в каком они записаны в тексте запроса. Это приём для тонкой настройки конкретного запроса — планировщик находит оптимальный порядок не всегда, поэтому его можно задать явно. Действует только на явный синтаксис `JOIN`; порядок перечисления таблиц в `FROM` не затрагивается.

Верхняя граница ограничена: если значение достигает `geqo_threshold` или превышает его, планирование переключается на GEQO и результат становится неоптимальным.

```sql
-- Диагностика: какой лимит отвечает за медленное планирование
SHOW from_collapse_limit;
SHOW join_collapse_limit;
SHOW geqo_threshold;
```
```text
 from_collapse_limit
---------------------
 8
(1 row)
```

Фактическое время планирования видно в выводе `EXPLAIN (ANALYZE, ...)` — строка `Planning Time` (в обычном `EXPLAIN` без `ANALYZE` она не выводится).

### Партиционирование и планировщик

При большом числе партиций планировщик тратит существенную часть времени на перебор возможных путей. Два параметра помогают управлять этим:

*   **`enable_partitionwise_join`** (по умолчанию `off`): при включении для каждой пары партиций строится отдельный узел соединения. Это снижает затраты на исполнение (уменьшается объём данных, проходящих через `Append`), но увеличивает время планирования и размер плана. Эффективно при числе партиций до нескольких десятков; при сотнях планировщик сам предпочитает обычный `Append`.
*   **`enable_partitionwise_aggregate`** (по умолчанию `off`): аналогично для `GROUP BY`. Если запрос агрегирует данные по ключу партиционирования, планировщик может выполнить агрегацию внутри каждой партиции, а затем объединить результаты.

Для SRE: при переходе с RANGE-партиционирования по дням на HASH или на крупные RANGE-интервалы время планирования может упасть в десятки раз, даже без изменения `enable_partitionwise_*`. Параметры `from_collapse_limit` и `join_collapse_limit` становятся более эффективными, когда число элементов `FROM` перестаёт расти пропорционально числу партиций.

### Генерация путей: какие варианты вообще рассматриваются

Планировщик не придумывает планы из ничего — набор кандидатов определяется структурой запроса и наличием индексов:

*   **Seq Scan** генерируется всегда — это запасной вариант, существующий для каждой таблицы.
*   **Index Scan** генерируется, если условие запроса соответствует ключу индекса и оператор входит в его operator class. Дополнительно индексный путь строится, если порядок строк индекса совпадает с `ORDER BY` или может пригодиться для merge join.
*   **Index Only Scan** — разновидность index scan, использующая Visibility Map: страницы, где все строки видны всем транзакциям, читаются без обращения к heap. От планировщика зависит только выбор узла, а фактическая применимость определяется состоянием VM.
*   **Bitmap Heap Scan** — генерируется, когда условие подходит индексу, но требует обращения к большому числу строк: сначала строится битовая карта по индексу, затем строки читаются из heap в физическом порядке.
*   **Соединения** рассматриваются только после того, как построены все пути для отдельных отношений. Планировщик предпочитает пары, между которыми в `WHERE` есть условие соединения (`WHERE rel1.attr1 = rel2.attr2`); пары без условия соединения рассматриваются лишь тогда, когда иначе присоединить отношение не к чему.

Практическое следствие: если индекс не может быть использован из-за структуры условия, увеличение `random_page_cost` или `work_mem` его не «включит» — нужно менять сам запрос (приведение типа, переписывание предиката, изменение индекса).

### Стоимостная модель (Cost Model)

Планировщик суммирует затраты на ввод-вывод (I/O) и обработку данных процессором (CPU).

**Основные константы стоимости (GUC):**

| Параметр | Значение по умолчанию | Описание |
| :--- | :--- | :--- |
| `seq_page_cost` | 1.0 | Чтение одной страницы последовательно. |
| `random_page_cost` | 4.0 | Чтение одной страницы в случайном порядке (HDD). |
| `cpu_tuple_cost` | 0.01 | Обработка одного кортежа (строки). |
| `cpu_index_tuple_cost` | 0.005 | Обработка одной записи в индексе. |
| `cpu_operator_cost` | 0.0025 | Выполнение оператора или функции. |
| `parallel_setup_cost` | 1000.0 | Затраты на запуск параллельных воркеров. |
| `parallel_tuple_cost` | 0.1 | Затраты на передачу кортежа между процессами. |
| `effective_cache_size` | 4GB | Оценка объема кэша, доступного одному запросу. Не резервирует и не выделяет память. |
| `min_parallel_table_scan_size` | 8MB | Минимальный объем данных таблицы, при котором параллельный скан вообще рассматривается. |
| `min_parallel_index_scan_size` | 512kB | Аналогично для индекса; влияет также на решение о параллельном VACUUM индекса. |
| `jit_above_cost` | 100000 | Порог стоимости, выше которого включается JIT-компиляция. Значение -1 отключает JIT. |
| `jit_inline_above_cost` | 500000 | Порог для инлайнинга функций и операторов в JIT. |
| `jit_optimize_above_cost` | 500000 | Порог для дорогих оптимизаций LLVM. |

Важные свойства шкалы:

*   Все константы — произвольные. Их общее масштабирование не меняет выбор плана: важны только соотношения. Например, можно задать всю шкалу в миллисекундах, но это не делает оценки точнее — точность зависит от калибровки, а не от единицы измерения.
*   Значение `random_page_cost` ниже `seq_page_cost` физически бессмысленно, хотя система это допускает. Равные значения (`random_page_cost = seq_page_cost`) осмысленны для базы, полностью помещающейся в RAM.
*   Официальной методики определения «идеальных» значений не существует. Константы следует рассматривать как среднее по реальному профилю нагрузки установки; подстройка по двум-трём экспериментам рискованна.

**Базовая формула Seq Scan:**
`Total Cost = (N_Pages * seq_page_cost) + (N_Rows * cpu_tuple_cost) + (N_Rows * Filter_Cost)`

Упрощённо стоимость Index Scan складывается из стоимости чтения страниц индекса (последовательных в начале обхода) и страниц heap, к которым происходит возврат (случайных, поэтому умножаемых на `random_page_cost`). Именно поэтому планировщик с большим `random_page_cost` «не любит» индексы, а корреляция (`correlation`, близкая к ±1) удешевляет index scan: строки в heap идут в том же порядке, что и в индексе.

**Когда важна startup cost, а когда total cost:**

*   В `EXISTS`, `LIMIT` без `ORDER BY` и других случаях, где исполнение прекращается после первого подходящего набора строк, планировщик минимизирует **startup cost**.
*   Для полного-result запроса минимизируется **total cost**. При наличии `LIMIT` планировщик интерполирует между двумя оценками.

Методы доступа (`Seq Scan`, `Index Scan`, `Bitmap Heap Scan`, `Index Only Scan`, `TID Scan`) подробно разобраны в разделе [Оптимизация производительности](../Operations/performance_tuning.md). Здесь важно понимать, что все они — конкурентные кандидаты в рамках одного узла плана, и выбор делается исключительно по стоимости. То же верно для алгоритмов соединения: это не «настройка соединения», а выбор одного из нескольких узлов плана.

### Прочие параметры, влияющие на оценку плана

Помимо констант стоимости, на решение планировщика влияет несколько параметров, которые не относятся ни к `enable_*`, ни к шкале стоимости:

| Параметр | По умолчанию | На что влияет |
| :--- | :--- | :--- |
| `cursor_tuple_fraction` | 0.1 | Доля строк курсора, которую планировщик считает необходимой получить. Меньшие значения смещают выбор в сторону планов с быстрым стартом (дешёвый startup cost, дорогое получение всех строк), большие — в сторону минимизации total cost. Максимум 1.0 — курсор планируется как обычный запрос. |
| `recursive_worktable_factor` | 10.0 | Средний размер рабочей таблицы рекурсивного запроса как множитель размера начального нерекурсивного члена. Заниженное значение склоняет планировщик к Nested Loop, завышенное — к Hash/Merge Join. |
| `hash_mem_multiplier` | 2.0 | Множитель `work_mem` для хеш-таблиц. Планировщик использует его при оценке Hash Join и хеш-агрегации: если хеш-таблица не помещается в лимит, стоимость включает внешние батчи. |

**Для SRE:** `cursor_tuple_fraction` стоит проверить, если приложение или отчётный инструмент работает через серверные курсоры и страдает от того, что первые строки приходят медленно. Отчётность часто выигрывает от низкого значения (0.01–0.05) — она возвращает первые строки почти сразу, даже если общий проход дорог. Для обычных запросов параметр не действует.

`recursive_worktable_factor` настраивают по профилю запросов: для графовых и кратчайших путей, где «разрастание» на шаг небольшое, разумны значения 1.0–2.0, для рекурсивных обходов с широким ветвлением — по умолчанию 10.0 или выше. Неверное значение даёт неверный алгоритм соединения рабочей таблицы с остальными отношениями, а это, в свою очередь, определяет весь план.

### Память, кэширование и планировщик

Планировщик принимает решения, опираясь не только на статистику столбцов, но и на представление о доступной оперативной памяти:

*   **`shared_buffers`** — объём shared buffer cache PostgreSQL. Приблизительно соответствует 25 % оперативной памяти сервера. Планировщик считает, что запросы будут обслуживаться из этого кэша; если он настроен недостаточно, `effective_cache_size` даёт завышенную оценку и планировщик «ожидает» слишком много cache hits.
*   **`effective_cache_size`** — оценка объёма кэша, доступного для одного запроса (OS page cache + `shared_buffers`). Приблизительно соответствует 75 % оперативной памяти. От этого параметра зависит вероятность выбора Index Scan: чем он выше, тем дешевле планировщик оценивает случайные страницы индекса и heap.
*   **`work_mem`** — объём памяти на **один узел** плана (сорт, хеш-таблица, агрегат). Если операция не помещается в `work_mem`, она spills to disk (внешняя сортировка или партиционированная хеш-таблица), что планировщик оценивает как дополнительные I/O. Следовательно, недостаток `work_mem` может заставить планировщик отвергнуть Hash Join в пользу Nested Loop, даже если данные большие.
*   **`maintenance_work_mem`** — объём памяти на DDL-операции (`CREATE INDEX`, `VACUUM`, `ALTER TABLE`). Планировщик не учитывает его при оценке стоимости выполнения запросов, но для SRE это ключевой параметр: при его недостатке `CREATE INDEX CONCURRENTLY` завершается дольше и чаще вызывает fragmentation.

**Практическое правило для SRE:** настройте `shared_buffers` и `effective_cache_size` так, чтобы их соотношение примерно соответствовало реальному разделению памяти между PostgreSQL и ОС. Изменяйте их одновременно: изменение только `effective_cache_size` без `shared_buffers` даёт противоречивые оценки.

### Алгоритмы соединений (Join Strategies)

1.  **Nested Loop**:
    *   *Принцип*: Для каждой строки из внешней таблицы сканируется внутренняя.
    *   *Когда выбирается*: Малые выборки, наличие эффективного индекса на внутренней таблице.
    *   *Startup Cost*: Близка к 0.
2.  **Merge Join**:
    *   *Принцип*: Обе таблицы сортируются по ключу соединения, затем объединяются в один проход.
    *   *Когда выбирается*: Большие наборы данных, ключи уже отсортированы (индексом) или требуется сортировка для последующих операций.
    *   *Startup Cost*: Высокая (затраты на сортировку).
3.  **Hash Join**:
    *   *Принцип*: Строится хеш-таблица для внутренней таблицы в RAM, затем внешняя таблица сканируется и проверяется по хешу.
    *   *Когда выбирается*: Большие несортированные наборы, которые помещаются в `work_mem`.
    *   *Startup Cost*: Высокая (построение хеш-таблицы).
4.  **Memoize** (PostgreSQL 14+):
    *   *Принцип*: Узел кеширует результаты параметризованного скана внутри nested loop, чтобы при повторном значении параметра не выполнять scan заново.
    *   *Когда выбирается*: Внешняя сторона nested loop возвращает много повторяющихся значений ключа, внутренняя сторона — параметризованный скан.
    *   *Управление*: `enable_memoize` (по умолчанию `on`).
5.  **Semi Join / Anti Join**:
    *   *Принцип*: `Semi Join` возвращает строки внешней стороны, для которых нашлось совпадение (проверка «есть ли»); `Anti Join` — для которых совпадения нет. Оба исключают размножение строк при множественным совпадениях.
    *   *Когда выбирается*: `WHERE EXISTS (...)`, `NOT IN`, `IN`. PostgreSQL 18 расширил условия преобразования в Right Semi Join, PostgreSQL 19 разрешил использовать Memoize для ANTI JOIN с уникальной внутренней стороной.

### Сбор и анализ статистики

Данные хранятся в системном каталоге `pg_statistic`, но для чтения удобно использовать представление `pg_stats`.

*   **n_distinct**: Количество уникальных значений. Отрицательное число означает долю от общей таблицы (например, -1 = уникальный столбец).
*   **Correlation**: Значения близки к 1 или -1 делают Index Scan чрезвычайно эффективным, так как данные читаются почти последовательно.
*   **Statistics Target (Цель статистики)**: Глубина детализации выборки. Задаётся глобально через `default_statistics_target` (по умолчанию 100) и индивидуально через `ALTER TABLE ... ALTER COLUMN ... SET STATISTICS`. Более высокое значение даёт более точные оценки, но увеличивает время `ANALYZE`.
*   **Extended Statistics (Расширенная статистика)**: Позволяет учитывать зависимость между колонками (Multivariate Statistics). Виды, доступные в `CREATE STATISTICS`:
    *   `dependencies`: Для функциональных зависимостей (например, `zip_code` определяет `city`).
    *   `ndistinct`: Количество уникальных комбинаций колонок.
    *   `mcv`: Список наиболее частых комбинаций значений — влияет на оценку соединений, когда планировщик умножает селективности.
    *   `expressions`: Статистика по выражениям, в том числе индексированным.

    Расширенная статистика хранится в `pg_statistic_ext` (метаданные) и `pg_statistic_ext_data` (сами данные), читается через представление `pg_stats_ext`.

**Когда обновляется статистика.** Сбор статистики запускает autovacuum — при числе изменённых строк, превышающем порог `autovacuum_analyze_threshold` (по умолчанию 50 кортежей) плюс `autovacuum_analyze_scale_factor` (по умолчанию 0.1, то есть 10% от размера таблицы) процентов. На больших таблицах это означает, что после массовой вставки `ANALYZE` может не запуститься неделями. Пороги можно ужесточить на уровне таблицы:

```sql
-- Порог, не зависящий от размера таблицы
ALTER TABLE users SET (autovacuum_analyze_scale_factor = 0.01);
```

**Статистика не переносится вместе с данными.** Обычный `pg_dump` / `pg_restore` статистику не переносит — после восстановления база имеет пустую `pg_statistic` до первого `ANALYZE`, а планировщик до этого момента работает вслепую (см. [Статистика после восстановления и обновления кластера](#5-статистика-после-восстановления-и-обновления-кластера)).

**Пограничные случаи сбора статистики.** Несколько особенностей `ANALYZE` регулярно становятся источником «необъяснимых» планов:

*   **Выборка каждый раз разная.** `ANALYZE` читает случайную выборку строк, а не всю таблицу, поэтому статистика немного меняется при каждом запуске — даже если данные не изменились. Обычно это даёт мизерный дрейф оценок, но в редких случаях планировщик меняет выбор плана именно из-за повторного `ANALYZE`. Если такой случай повторяется на одном и том же запросе, увеличьте statistics target для проблемных столбцов — более крупная выборка уменьшает разброс.
*   **`SET STATISTICS 0` полностью отключает сбор.** Для столбцов, которые никогда не участвуют в `WHERE`, `GROUP BY` или `ORDER BY`, статистика бесполезна, а `ANALYZE` на ней тратит время и место в `pg_statistic`. Обратная сторона: после такого отключения планировщик ничего не знает о столбце, и любое его использование в запросе даст оценку по умолчанию.
*   **Точность `n_distinct` ограничена.** Даже при максимальном statistics target оценка числа уникальных значений остаётся приблизительной. Если из-за неё выбирается неверный план, точное значение задаётся вручную: `ALTER TABLE t ALTER COLUMN c SET (n_distinct = 50000);` — это разовая плата за правильный план на очень неравномерном столбце.
*   **Партиционированные таблицы.** `ANALYZE` рекурсивно собирает статистику по всем партициям (`ONLY` отключает рекурсию), но autovacuum **не обрабатывает партиционированные таблицы** — он работает только с их партициями. Если данные меняются только через партиции определённого типа, статистика корневого уровня устаревает, и нужен периодический ручной `ANALYZE`.
*   **Внешние таблицы.** `ANALYZE` без списка таблиц их **не обрабатывает** — внешние таблицы анализируются только при явном указании, и не все FDW поддерживают `ANALYZE` вообще. Подробно — в сценарии [Планировщик без статистики: внешние таблицы](#9-планировщик-без-статистики-внешние-таблицы).
*   **Пустая таблица.** Если таблица полностью пуста, `ANALYZE` не записывает новую статистику — прежние значения сохраняются.

### GEQO (Genetic Query Optimizer)

Если запрос содержит слишком много JOIN-ов, планировщик переключается на генетический поиск.

| Параметр | По умолчанию | Что делает |
| :--- | :--- | :--- |
| `geqo_threshold` | 12 | Число элементов `FROM`, начиная с которого включается GEQO вместо полного перебора. Конструкция `FULL OUTER JOIN` считается одним элементом. |
| `geqo` | `on` | Включение GEQO. В продакшене отключать не следует — порог даёт более тонкое управление. |
| `geqo_effort` | 5 (диапазон 1–10) | Прямого действия не имеет — только рассчитывает значения по умолчанию для остальных параметров GEQO. |
| `geqo_pool_size` | 0 (подбирается автоматически) | Размер популяции — число одновременно исследуемых вариантов порядка соединения. Ноль означает «вычислить из `geqo_effort` и числа таблиц»; полезные значения обычно 100–1000. |
| `geqo_generations` | 0 (подбирается автоматически) | Число поколений — итераций алгоритма. Ноль означает «вычислить из `geqo_pool_size`». |
| `geqo_selection_bias` | 2.0 (диапазон 1.50–2.00) | Давление отбора внутри популяции. |
| `geqo_seed` | 0 (диапазон 0–1) | Начальное значение генератора случайных чисел, которым GEQO выбирает пути в пространстве порядков соединения. Варьирование значения меняет набор исследуемых путей и позволяет найти как лучший, так и худший план. |

**GEQO воспроизводим, а не случаен.** При фиксированном `geqo_seed` генератор случайных чисел инициализируется только этим значением (`geqo_set_seed()` → `pg_prng_fseed()`, файл `geqo_random.c`), и других источников случайности в алгоритме нет. Поэтому при неизменных данных, тексте запроса и `geqo_seed` GEQO возвращает один и тот же план.

Практическое следствие для диагностики: если один и тот же текст запроса даёт разные планы, GEQO как источник вариативности проверять не нужно. Сначала смотрите на custom/generic plan, недефолтные настройки сессии и число доступных параллельных воркеров. План «поедет» только если изменился сам `geqo_seed` — например, после правки `postgresql.conf`, `ALTER DATABASE ... SET geqo_seed` или наследования настроек от роли.

Варьирование `geqo_seed` используют осознанно как измерение: один и тот же запрос прогоняют с несколькими значениями seed, чтобы проверить, насколько чувствителен класс запросов к GEQO. Если планы различаются сильно, запрос стоит переписать (разбить подзапросами, упростить граф соединений, вынести фильтры) или ограничить для него `join_collapse_limit`, а не полагаться на удачу конкретного seed.

### Ограничения по времени

Параметры времени не влияют на выбор плана, но изменяют контекст его выполнения:

*   **`statement_timeout`**: прерывает запрос по таймауту. Планировщик не учитывает это ограничение при оценке стоимости — план может быть «правильным», но запрос всё равно будет убит, если он не успевает завершиться.
*   **`lock_timeout`**: прерывает ожидание блокировки. Планировщик не учитывает вероятность блокировки; для запросов, чувствительных к конкуренции, `lock_timeout` работает как аварийный предохранитель, а не как элемент оптимизации.
*   **`idle_in_transaction_session_timeout`**: закрывает сессию, которая долго находится в `idle in transaction`. Косвенно влияет на планировщик: утечка транзакций приводит к устареванию snapshot и, как следствие, к искажённой статистике (например, `pg_stat_user_tables.n_dead_tup` растёт, но `ANALYZE` не отражает реальное распределение).

### Планирование подготовленных запросов и кеш планов

Подготовленные запросы (`PREPARE`, параметризованные запросы в драйверах, любые запросы внутри PL/pgSQL) кешируются вместе с планом. При каждом выполнении планировщик решает, какой план использовать:

*   **Custom plan** — строится заново с подстановкой фактических значений параметров. Оценки точны, но планирование повторяется при каждом выполнении.
*   **Generic plan** — используется оценка по средней селективности, сам план не перестраивается. Планирование дёшево, но качество оценки падает.

Параметр `plan_cache_mode` управляет этим выбором:

| Значение | Поведение |
| :--- | :--- |
| `auto` (по умолчанию) | Решение принимается автоматически: первые пять выполнений строят custom plan, далее сравнивается средняя стоимость custom и generic планов, и выигрывающий используется для последующих запусков. |
| `force_custom_plan` | Всегда custom plan. Планирование дороже, оценки точнее. |
| `force_generic_plan` | Всегда generic plan. Дешевле по CPU, но может резко ухудшить план при неравномерном распределении значений. |

Значение проверяется в момент выполнения кешированного плана, а не в момент `PREPARE`.

```sql
PREPARE orders_by_cust(int) AS
  SELECT * FROM orders WHERE customer_id = $1;

-- Как выглядит план при фактическом значении параметра
EXPLAIN (ANALYZE, BUFFERS) EXECUTE orders_by_cust(42);

-- Как выглядит generic plan для того же текста запроса (не выполняет его)
EXPLAIN (GENERIC_PLAN) SELECT * FROM orders WHERE customer_id = $1;
```

`EXPLAIN (GENERIC_PLAN)` (PostgreSQL 16+) нельзя совмещать с `ANALYZE`: он показывает только оценки для плана, не зависящего от значений параметров. Именно расхождение между этими двумя выводами — прямой признак «запахивания параметров» (parameter sniffing) в рабочем запросе.

Симптомы, при которых стоит проверить `plan_cache_mode`:

*   Запрос внезапно замедлился «после того, как заработал» — типичный переход на generic plan, при котором оценка перестала учитывать фактические значения.
*   В PL/pgSQL-функции планирование каждого вызова даёт заметную нагрузку — `force_custom_plan` или переписывание в SQL-функцию.
*   В `pg_stat_statements` (PostgreSQL 19) появились счётчики generic и custom планов — их резкий перекос говорит о том, какой режим реально используется.

### Параллельный запрос

Часть плана выполняется в отдельных процессах — воркерах. Это влияет и на стоимость, и на реальное потребление ресурсов:

*   Параллельный Scan рассматривается только если планировщик считает, что будет прочитано больше `min_parallel_table_scan_size` (8MB) данных таблицы или `min_parallel_index_scan_size` (512kB) данных индекса.
*   Каждый Gather-узел запускает воркеров и платит `parallel_setup_cost` (по умолчанию 1000) — это плата за накладные расходы, из-за которой параллельность не включается ради маленьких выборок.
*   Передача кортежа от воркера к лидеру стоит `parallel_tuple_cost` (по умолчанию 0.1). Чем больше строк возвращает запрос, тем дороже параллельная схема в модели планировщика.
*   `max_parallel_workers_per_gather` (по умолчанию 2) ограничивает число воркеров на один Gather-узел; фактически доступное число дополнительно ограничено `max_worker_processes` (по умолчанию 8) и `max_parallel_workers`. Если воркеров не хватило, план выполняется с меньшим их числом — это и есть источник «нестабильной» производительности параллельных запросов.
*   Значение 0 у `max_parallel_workers_per_gather` полностью отключает параллельное выполнение — полезно как средство локализации проблемы, а не как постоянная настройка.

Важно: параллельность не ускоряет саму работу, она переносит её на дополнительные процессы. Каждый воркер — отдельный процесс со своим `work_mem`, поэтому см. [бюджет `work_mem`](../Operations/performance_tuning.md) перед увеличением числа воркеров.

### Connection Pooling и кеш планов

При работе через connection pool (например, PgBouncer) важно учитывать, где хранится кеш планов:

*   **Session pooling / Transaction pooling:** в режиме transaction pooling каждый execute prepared statement может идти через другой серверный процесс PostgreSQL. Так как кеш планов привязан к backend, подготовленный план не всегда переиспользуется. Это увеличивает `Planning Time` и может привести к неожиданному всплеску CPU.
*   **Prepared statements в драйверах (JDBC, libpq):** если драйвер кеширует prepared statements на стороне приложения, а PgBouncer работает в transaction pooling, PostgreSQL получает каждый раз новый `PREPARE`, и планировщик заново строит generic plan. На практике это означает, что настройка `plan_cache_mode` на стороне сервера теряет смысл — важно управлять кешем на стороне драйвера.
*   **Диагностика:** сравните `Planning Time` в `EXPLAIN (ANALYZE)` при прямом подключении и через PgBouncer. Если через пул планирование занимает заметно больше, проблема не в планировщике, а в отсутствии переиспользования планов между бэкендами.

В сильно нагруженных продакшен-средах с PgBouncer предпочитайте SQL-функции (не PL/pgSQL), если запросы простые: функции компилируются целиком и не требуют отдельного планирования при каждом вызове.

**`max_prepared_statements` — штатное решение, а не повод отказываться от transaction pooling.** Начиная с PgBouncer 1.21 пул умеет отслеживать протокольные именованные prepared statements в режимах transaction и statement pooling: каждому уникальному тексту запроса присваивается внутреннее имя вида `PGBOUNCER_<id>`, и если на новом серверном соединении нужный prepared statement ещё не подготовлен, PgBouncer готовит его прозрачно перед выполнением. Кеш планов на стороне PostgreSQL при этом переиспользуется, а `Planning Time` возвращается к нормальным значениям.

```ini
# pgbouncer.ini — для PgBouncer 1.21+
max_prepared_statements = 100
```

Значение `0` (по умолчанию) полностью отключает поддержку prepared statements в этих режимах и возвращает описанное выше поведение. Число управляет размером LRU-кеша prepared statements на одном серверном соединении: слишком маленькое значение вытеснит часто используемые запросы и вернёт проблему. Побочный эффект — дополнительный расход памяти: на PostgreSQL удерживается больше подготовленных планов, а сам PgBouncer хранит тексты запросов. Настройка, ограничения и совместимость с драйверами разобраны в [Настройка PgBouncer](../Operations/pgbouncer_setup.md).

Оговорка по совместимости: не все клиентские библиотеки корректно работают с этой схемой. В частности, PHP/PDO совместим только начиная с PHP 8.4 с libpq 17; для более старых сборок prepared statements на стороне клиента лучше отключить, чем мириться с ошибками.

### Управление методами планирования: параметры `enable_*`

Параметры семейства `enable_*` — это грубый, но единственный способ «заставить» планировщик выбрать другой тип узла. Все они по умолчанию `on`, и ни один из них не может полностью запретить соответствующий узел: планировщик лишь «не любит» отключённый вариант, а если другого нет — использует его.

| Параметр | За что отвечает |
| :--- | :--- |
| `enable_seqscan` | Seq Scan |
| `enable_indexscan` | Index Scan и Index Only Scan |
| `enable_indexonlyscan` | Index Only Scan (требует включённого `enable_indexscan`) |
| `enable_bitmapscan` | Bitmap Scan |
| `enable_tidscan` | TID Scan (поиск по `ctid`) |
| `enable_nestloop` | Nested Loop Join |
| `enable_mergejoin` | Merge Join |
| `enable_hashjoin` | Hash Join (в т.ч. parallel hash) |
| `enable_hashagg` | HashAggregate |
| `enable_sort` | Явные узлы Sort |
| `enable_incremental_sort` | Incremental Sort — досортировка префикса уже отсортированного потока |
| `enable_material` | Materialize |
| `enable_memoize` | Memoize |
| `enable_gathermerge` | Gather Merge |
| `enable_parallel_append` | Parallel Aware Append |
| `enable_parallel_hash` | Hash Join с parallel hash |
| `enable_partition_pruning` | Отсечение партиций и генерация планов с runtime pruning |
| `enable_partitionwise_join` | Partitionwise Join (по умолчанию `off`) |
| `enable_partitionwise_aggregate` | Partitionwise Aggregate (по умолчанию `off`) |
| `enable_distinct_reordering` | Перестановка ключей `DISTINCT` под порядок входных строк |
| `enable_group_by_reordering` | Построение `GROUP BY` в порядке дочернего узла |
| `enable_presorted_aggregate` | Предварительная сортировка для агрегатов с `ORDER BY`/`DISTINCT` |
| `enable_self_join_elimination` | Удаление избыточных self join (PostgreSQL 18+, по умолчанию `on`) |
| `enable_async_append` | Async Aware Append (PostgreSQL 14+) |

**Практическое правило:** отключение `enable_*` — это диагностический инструмент, а не решение.

```sql
-- Проверка гипотезы: действительно ли index scan лучше, чем решил планировщик
BEGIN;
SET LOCAL enable_seqscan = off;
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'shipped';
ROLLBACK;
```

Если выигрыш есть — проблема в модели стоимости (статистика, `random_page_cost`, `effective_cache_size`), и лечится она точнее. Если после отключения `enable_seqscan` планировщик всё равно выбрал Seq Scan — значит, альтернативного пути просто не существует, и вопрос в другом (нет индекса, несовместимый тип, индекс не используется из-за условия).

Отдельный параметр — `constraint_exclusion` (по умолчанию `partition`): он управляет исключением таблиц по противоречащим `CHECK`-ограничениям для классического наследования. Для декларативно партиционированных таблиц аналогичный механизм включается через `enable_partition_pruning`.

Начиная с PostgreSQL 18, если выбранный план всё же содержит узел, для которого отключён соответствующий `enable_*`, такой узел помечается строкой `Disabled: true` прямо в дереве плана. Это показывает, какой именно параметр действовал на решение, и избавляет от необходимости угадывать его перебором.

```sql
SET enable_seqscan = off;
EXPLAIN SELECT * FROM unit;
```
```text
                QUERY PLAN
-------------------------------------------------
 Seq Scan on unit  (cost=0.00..21.30 rows=1130 width=44)
   Disabled: true
(2 rows)
```

### Изменения планировщика по версиям

Ниже — только изменения, влияющие на стоимостную модель, статистику и диагностику планов.

**PostgreSQL 16:**
*   Появилась опция `EXPLAIN (GENERIC_PLAN)` — возможность увидеть generic plan для параметризованного запроса.

**PostgreSQL 17:**
*   Появились опции `EXPLAIN (SERIALIZE ...)` (стоимость преобразования результата в текст/бинарный формат) и `EXPLAIN (MEMORY)` (точный объём памяти, потреблённый планировщиком, и память с учётом накладных расходов аллокатора).

**PostgreSQL 18 (стабильный релиз, текущий минорный 18.6 на октябрь 2026):**
*   **Skip scan** для B-tree индексов: многостолбцовый индекс может использоваться, даже если ограничений на первые (ранние) столбцы нет или они неравенственные. Меняет набор вообще возможных путей — часть запросов, требовавших отдельных индексов, теперь может обслуживаться одним.
*   **Удаление избыточных self join** (`enable_self_join_elimination`, по умолчанию `on`): дерево запроса разбирается и заменяется эквивалентным одиночным сканом. Работает только для обычных таблиц.
*   **EXPLAIN (ANALYZE) автоматически включает BUFFERS.** Отдельно указывать `BUFFERS` больше не обязательно, но привычка писать его явно сохраняется для совместимости текста запросов с более старыми версиями.
*   **Дробные оценки строк** в выводе `EXPLAIN` (ранее округлялись до целых), счётчик обращений к индексу (`Index Searches`) в `EXPLAIN ANALYZE` и пометка `Disabled: true` у узлов, выбранных вопреки отключённому `enable_*`.
*   Перестановка ключей `SELECT DISTINCT` (`enable_distinct_reordering`) и отбрасывание избыточных колонок в `GROUP BY`, функционально зависящих от уникального индекса.
*   **Асинхронный I/O**: параметры `io_method`, `io_combine_limit`, `io_max_combine_limit`; значения `effective_io_concurrency` и `maintenance_io_concurrency` по умолчанию увеличены до 16. Механика и тюнинг: [Асинхронный ввод-вывод](../Operations/async_io.md).
*   **`pg_upgrade` сохраняет статистику оптимизатора** (расширенная статистика при этом не переносится; есть флаг `--no-statistics`); `pg_dump` получил опции `--statistics`, `--statistics-only`, `--no-statistics`; `vacuumdb` — опцию `--missing-stats-only`. Добавлены функции `pg_restore_relation_stats()`, `pg_restore_attribute_stats()`, `pg_clear_relation_stats()` и `pg_clear_attribute_stats()`.
*   `pg_stat_all_tables` и его варианты получили `total_analyze_time` и `total_autoanalyze_time`; `ANALYZE VERBOSE` выводит WAL, CPU и среднее время чтения.
*   `VACUUM` и `ANALYZE` по умолчанию обрабатывают дочерние таблицы наследования; ключевое слово `ONLY` отключает это (и полезно для партиционированных таблиц, которые autovacuum не обслуживает целиком).
*   Расширение `pg_overexplain` для расширенной диагностики вывода `EXPLAIN`.

**Примечание по поддержке:** PostgreSQL 14 получает исправления до ноября 2026, после чего его поддержка прекращается. Cost model и GEQO в 14 и 15 могут давать разные планы; перед апгрейдом проверяйте эталонные запросы.

**PostgreSQL 19 (Beta 4 на октябрь 2026; GA ожидается во второй половине 2026):**
*   **JIT по умолчанию отключён.** Порог JIT-активации признан ненадёжным; площадкам с большими аналитическими запросами требуется включать `jit` вручную. Это меняет поведение именно крупных запросов, для которых JIT и включался.
*   **Plan advice: `pg_plan_advice` и `pg_stash_advice`.** Вместо inline-подсказок в тексте SQL решение о плане описывается отдельной строкой, которую можно получить из плана и применить через GUC:

    ```sql
    -- Получить advice для текущего плана
    EXPLAIN (COSTS OFF, PLAN_ADVICE) SELECT ...;

    -- Применить
    SET pg_plan_advice.advice = 'JOIN_ORDER(o c) HASH_JOIN(c) SEQ_SCAN(o c)';

    -- Автоматическое применение по query id (расширение pg_stash_advice)
    -- pg_stash_advice.stash_name = 'prod' в postgresql.conf
    SELECT pg_create_advice_stash('prod');
    SELECT pg_set_stashed_advice('prod', 1234567890, 'SEQ_SCAN(o c) NO_GATHER(o c)');
    ```

    Механизм даёт обратную связь о том, какие указания были применены, а какие проигнорированы. Advice живут вне текста запроса, применяются по query id и требуют загрузки модулей через `shared_preload_libraries`; при этом они **закрепляют** текущий план — при изменении распределения данных закреплённый план может стать плохим.
*   Учитываются startup cost частичных путей (partial paths), улучшены оценки селективности при больших statistics target, корректная статистика для функций, возвращающих `boolean`; разрешена расширенная статистика на виртуальных генерируемых столбцах.
*   **Импорт статистики с удалённых серверов**: FDW получил обратный вызов для импорта готовой удалённой статистики; в `postgres_fdw` это включается опцией `import_stats` на уровне сервера или внешней таблицы. Значение по умолчанию — `auto` у `analyze_sampling`, выборка строк, если импорт не удался.
*   **Система очков autovacuum**: веса `autovacuum_analyze_score_weight`, `autovacuum_vacuum_score_weight`, `autovacuum_vacuum_insert_score_weight`, `autovacuum_multixact_freeze_score_weight`, `autovacuum_freeze_score_weight` и представление `pg_stat_autovacuum_scores` определяют порядок обработки таблиц; новый параметр `log_autoanalyze_min_duration` логирует длительные анализы от autovacuum.
*   `vacuumdb --analyze-only` и `--analyze-in-stages` при отсутствии целей теперь обрабатывают партиционированные таблицы (раньше пропускали); появился `vacuumdb --dry-run`. Отрицательные значения `pg_aggregate.aggtransspace` означают неограниченное потребление памяти, что учитывается планировщиком.
*   `pg_dump` научился включать восстанавливаемую расширенную статистику; добавлены функции `pg_restore_extended_stats()` и `pg_clear_extended_stats()`.
*   `pg_stat_statements` получил счётчики generic и custom планов; `auto_explain` — параметры `log_io` и `log_extension_options`; в `EXPLAIN ANALYZE` появилась опция `IO` и оценки кеша Memoize.
*   Хуки планировщика переработаны: `get_relation_info_hook` удалён, добавлены `build_simple_rel_hook`, `planner_setup_hook`, `planner_shutdown_hook`, `joinrel_setup_hook`, `join_path_setup_hook`. Это имеет значение только для расширений, вмешивающихся в планирование.

### JIT-компиляция

Начиная с PostgreSQL 11, планировщик может компилировать выражения на лету (LLVM).
*   `jit`: Включён по умолчанию в PostgreSQL 15–18; **в PostgreSQL 19 выключен по умолчанию**.
*   `jit_above_cost`: Порог (по умолчанию 100000), выше которого включается JIT. Значение -1 отключает JIT-компиляцию.
*   `jit_inline_above_cost`: Порог (по умолчанию 500000) для инлайнинга функций и операторов.
*   `jit_optimize_above_cost`: Порог (по умолчанию 500000), выше которого применяются агрессивные оптимизации JIT.
*   `jit_expressions` (по умолчанию `on`): компилировать ли сами выражения. Отключение убирает основную часть накладных расходов, сохраняя компиляцию деформации кортежей.
*   `jit_tuple_deforming` (по умолчанию `on`): компилировать ли разбор строк при доступе к столбцам.
*   `jit_provider`: имя реализации JIT-поставщика. Меняется крайне редко — только при отладке самого JIT.
*   JIT увеличивает время планирования. Если в `EXPLAIN (ANALYZE)` присутствует блок `JIT:`, а запрос при этом укладывается в сотни миллисекунд, компиляция почти наверняка не окупается.

**Читаем блок `JIT:` в выводе `EXPLAIN (ANALYZE)`.** Он содержит четыре компонента, каждый из которых — отдельный вид накладных расходов, и их важно различать:

```text
 JIT:
   Functions: 6
   Options: Inlining true, Optimization true, Expressions true, Deforming true
   Timing: Generation 1.284 ms, Inlining 45.031 ms, Optimization 45.031 ms, Emission 3.699 ms
```

*   **Generation** — построение LLVM-модуля.
*   **Inlining** и **Optimization** — обе фазы управляются порогами `jit_inline_above_cost` и `jit_optimize_above_cost`; именно они обычно дают основную часть времени, особенно при большом числе функций.
*   **Emission** — генерация машинного кода.
*   **Timing** суммируется в `Planning Time`, а не в `Execution Time`. Если сумма `Timing` сопоставима с `Execution Time`, JIT не окупается даже при формально высокой стоимости запроса.

**Для SRE:** на OLTP-профиле JIT — источник бесполезного CPU на планировании. Запросы с `jit_above_cost` вполне достижимы при массовых UPDATE/DELETE на больших таблицах, где стоимость плана считается высокой, но реальное время исполнения измеряется миллисекундами. `jit = off` на транзакционных базах и `jit = on` на аналитических — обычная и безопасная разделение; общий бюджет памяти и CPU при этом см. в [Оптимизации производительности](../Operations/performance_tuning.md). Обратите внимание на смену поведения при переходе на PostgreSQL 19: там JIT уже выключен по умолчанию, и площадкам с тяжёлой аналитикой его придётся включать явно.

## Практические сценарии

### Предварительные требования

*   Права суперпользователя или владельца таблицы для изменения настроек статистики.
*   Установленное расширение `pg_stat_statements` для мониторинга часто выполняемых планов (рекомендуется).

### 1. Тюнинг весов под оборудование (SSD/NVMe)

Если база работает на быстрых SSD/NVMe дисках, стандартный `random_page_cost = 4.0` заставляет планировщик «бояться» индексов.

```sql
-- Для всей системы в postgresql.conf
random_page_cost = 1.1

-- Для конкретной сессии для теста
SET random_page_cost = 1.1;

-- Для конкретного табличного пространства (если SSD только там)
ALTER TABLESPACE fast_ssd SET (random_page_cost = 1.1);
```
**Результат**: Планировщик начнет чаще использовать `Index Scan` вместо `Seq Scan`.

Оговорки к этому приёму:

*   Значение подбирается под фактическое оборудование и профиль нагрузки, а не копируется из чужих конфигураций. `1.1` — разумная отправная точка для SSD/NVMe, но не универсальная истина.
*   На уровне сессии (`SET`) параметр действует только до конца транзакции или сессии, что делает такой тест безопасным.
*   На уровне табличного пространства переопределяются `seq_page_cost` и `random_page_cost` — это жестче, чем кажется: такое пространство получит «дешёвые» случайные чтения для всех находящихся в нём таблиц и индексов.
*   Для PostgreSQL 18 с включённым асинхронным I/O (`io_method`) разрыв между последовательным и случайным доступом меньше, а настройки `io_combine_limit`/`io_max_combine_limit` влияют на реальную картину сильнее, чем стоимостные константы. Значения стоит пересобирать после включения AIO, а не переносить из конфигурации, написанной до него.

### 2. Устранение ошибок оценки при корреляции колонок

Если запрос содержит `WHERE country = 'US' AND city = 'New York'`, планировщик перемножит их селективности, считая их независимыми, что приведет к заниженной кардинальности.

**Решение — Расширенная статистика:**
```sql
CREATE STATISTICS stts_city_country (dependencies) ON city, country FROM users;
ANALYZE users;
```
Проверка сбора статистики:
```sql
SELECT stxname, stxkeys, stxdependencies FROM pg_statistic_ext WHERE stxname = 'stts_city_country';
```

Для условий на комбинации значений, когда перемножение селективностей даёт ошибку в обе стороны (и занижение, и завышение), добавляется `mcv`; для вычисляемых выражений в условии — `expressions`:

```sql
CREATE STATISTICS stts_orders_deep (ndistinct, mcv) ON (lower(email)), status, country FROM orders;
ANALYZE orders;

-- Что именно собрано
SELECT statistics_name, kinds, attnames, exprs FROM pg_stats_ext
 WHERE statistics_name = 'stts_orders_deep';
```

### 3. Анализ точности планировщика через EXPLAIN

Ключевой метод диагностики — сравнение `rows` (оценка) и `actual rows` (реальность).

```sql
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM orders WHERE status = 'shipped' AND created_at > '2026-01-01';
```
**На что смотреть:**
- **Rows vs Actual Rows**: Расхождение более чем в 10 раз говорит об устаревшей статистике или функциональной зависимости.
- **Buffers**: `shared hit` (из кэша) vs `shared read` (с диска). Если `read` велик, возможно, `effective_cache_size` настроен неверно.
- **Planning Time**: Если планирование занимает сотни мс, возможно, слишком велик `from_collapse_limit` или `join_collapse_limit`.

**Основные опции `EXPLAIN`:**

| Опция | Назначение | Доступна с |
| :--- | :--- | :--- |
| `ANALYZE` | Выполнить запрос и показать фактические времена и количества строк | — |
| `BUFFERS` | Статистика обращений к буферам: `shared hit`, `shared read`, `temp read/write` | — (в PG 18 входит в `ANALYZE` автоматически) |
| `VERBOSE` | Список выходных колонок узла, имена триггеров, query id | — |
| `SETTINGS` | Параметры, влияющие на планирование, со значениями, отличными от встроенных по умолчанию | — |
| `GENERIC_PLAN` | План, не зависящий от значений параметров `$1`, `$2` | 16 |
| `SERIALIZE TEXT/BINARY` | Время и буферы на преобразование результата в текст/бинарный формат (требует `ANALYZE`) | 17 |
| `MEMORY` | Точный объём памяти планировщика | 17 |
| `WAL` | Объём сгенерированного WAL, число full page images (требует `ANALYZE`) | 15 |
| `TIMING OFF` | Отключить тайминги узлов, оставив только фактические количества строк | — |
| `FORMAT JSON/YAML/XML` | Машиночитаемый вывод для автоматической обработки | — |

**Осторожно с `ANALYZE`:**

*   Запрос действительно выполняется. Побочные эффекты `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE TABLE AS` сохраняются, даже если результат отброшен. Безопасный способ:

    ```sql
    BEGIN;
    EXPLAIN (ANALYZE, BUFFERS) UPDATE orders SET status = 'archived' WHERE id = 42;
    ROLLBACK;
    ```

*   Измерение времени в каждом узле добавляет накладные расходы. Для очень тяжёлых запросов `EXPLAIN (ANALYZE, TIMING OFF)` даёт фактические количества строк практически без искажения времени.
*   `Planning Time` в `EXPLAIN EXECUTE` включает и время получения плана из кеша, и время перепланирования, если оно было.

### 4. Исправление устаревшей статистики

Если после массовой вставки планировщик выбирает плохие планы:

```sql
-- Быстрый анализ конкретной таблицы
ANALYZE VERBOSE users;

-- Увеличение детализации для конкретной столбца (больше корзин в гистограмме)
ALTER TABLE users ALTER COLUMN status SET STATISTICS 500;
ANALYZE users;
```

Пороги autovacuum, из-за которых статистика может долго не обновляться на крупных таблицах, задаются на уровне таблицы:

```sql
ALTER TABLE events SET (
  autovacuum_analyze_scale_factor = 0.01,  -- 1% вместо 10%
  autovacuum_analyze_threshold  = 1000
);
```

Проверка состояния статистики по таблицам:

```sql
SELECT relname, n_live_tup, n_dead_tup,
       last_analyze, last_autoanalyze,
       last_vacuum, last_autovacuum
  FROM pg_stat_user_tables
 WHERE n_live_tup > 100000
 ORDER BY n_live_tup DESC
 LIMIT 20;
```

Массовый пересчёт статистики по кластеру (без vacuum, только анализ):

```bash
vacuumdb --analyze-only -j 8 -d mydb
# Только таблицы, у которых статистика отсутствует (PostgreSQL 18+):
vacuumdb --analyze-only --missing-stats-only -j 8 -d mydb
```

### 5. Статистика после восстановления и обновления кластера

Отдельная и часто недооцениваемая причина «внезапно плохих планов» — процедуры, которые не переносят статистику.

| Процедура | Что происходит со статистикой |
| :--- | :--- |
| `pg_restore` из обычного `pg_dump` | Статистика не переносится, до первого `ANALYZE` планировщик работает без данных о распределении. |
| `pg_dump --statistics` (18+) и `pg_restore --statistics-only` (18+) | Статистика включается в выгрузку; `pg_restore` может восстановить только статистику, не трогая данные. |
| `pg_upgrade` (18+) | Статистика оптимизатора сохраняется; **расширенная статистика не переносится**. Её нужно пересоздать и пересобрать. |
| `pg_upgrade` (15–17) | Статистика не переносится — обязательный `ANALYZE` после обновления. |
| `pg_restore_relation_stats()` / `pg_restore_attribute_stats()` (18+) | Точечное восстановление статистики отдельных отношений и столбцов из выгрузки — альтернатива полному `ANALYZE`, когда важно сохранить именно исходные оценки, а не пересчитать их. |
| `pg_restore_extended_stats()` (19) | Восстанавливает расширенную статистику из выгрузки, сделанной `pg_dump` версии 19. |
| `pg_clear_extended_stats()` (19) | Удаляет расширенную статистику — безопасный откат неудачно созданного объекта `CREATE STATISTICS`. |

Порядок действий после логического восстановления в любом случае: `ANALYZE` целевых таблиц, затем проверка планов эталонных запросов. Скрипты post-migration перечислены в [Логические бэкапы и миграция](../Operations/logical_backup_migration.md).

### 6. Автоматический сбор планов: auto_explain

Если запросы тормозят в проде и поймать их вручную невозможно, планы медленных запросов логируются автоматически расширением `auto_explain` (не требует `CREATE EXTENSION` — это модуль, загружаемый библиотекой):

```ini
# postgresql.conf
session_preload_libraries = 'auto_explain'
auto_explain.log_min_duration = '500ms'
auto_explain.log_analyze = on
auto_explain.log_buffers = on
auto_explain.log_timing = off
auto_explain.log_settings = on
auto_explain.log_nested_statements = on
auto_explain.sample_rate = 0.1
```

Ключевые параметры:

| Параметр | По умолчанию | Комментарий |
| :--- | :--- | :--- |
| `auto_explain.log_min_duration` | -1 (выключено) | Порог времени выполнения. `0` — логировать все планы. |
| `auto_explain.log_analyze` | off | Логировать `EXPLAIN ANALYZE` вместо `EXPLAIN`. |
| `auto_explain.log_timing` | on | Тайминги узлов. Влияет только при `log_analyze = on`. |
| `auto_explain.log_buffers` / `log_wal` | off | Соответствуют опциям `BUFFERS` и `WAL`; требуют `log_analyze = on`. |
| `auto_explain.log_settings` | off | Показывать недефолтные параметры планирования — прямая причина большинства «неожиданных» планов. |
| `auto_explain.log_nested_statements` | off | Включать запросы внутри PL/pgSQL-функций. |
| `auto_explain.sample_rate` | 1.0 | Доля логируемых запросов. |
| `auto_explain.log_format` | text | text, json, xml, yaml. Для парсинга логов разумно `json`. |

**Нагрузка от самого инструмента.** При `log_analyze = on` тайминги считаются для **всех** выполняемых запросов, а не только для тех, что попадут в лог. Поэтому:

*   `auto_explain.log_timing = off` оставляет фактические количества строк и буферы, снимая основную часть накладных расходов.
*   `sample_rate` снижает частоту логирования, но не устраняет накладные расходы `log_analyze`.
*   Параметры меняет только суперпользователь; в обычном режиме они задаются в `postgresql.conf` и действуют во всех новых сессиях.
*   Планы попадают в серверный лог — их объём следует учитывать при настройке ротации и при работе с персональными данными: текст запроса и его параметры логируются вместе с планом (`auto_explain.log_parameter_max_length` управляет усечением значений параметров).

### 7. Мониторинг планировщика для SRE

Планировщик — это «чёрный ящик», пока вы не включите сбор планов и не начнёте сопоставлять их с бизнес-инцидентами. Минимальный набор представлений и алертов для кластера:

**Ключевые представления:**

*   `pg_stat_statements` — поиск запросов с наибольшим `mean_exec_time` и `mean_plan_time` (PostgreSQL 19+). Столбцы `generic_plans` и `custom_plans` (19+) показывают, какой режим реально используется.
*   `pg_stat_user_tables` — `last_analyze` / `last_autoanalyze`. Если для крупных таблиц (>100 000 строк) они старше `autovacuum_analyze_scale_factor`, статистика устарела.
*   `pg_stat_activity` — активные запросы с большим `Planning Time`, а также запросы в состоянии `lock` или `idle in transaction`.

**Кастомные запросы для алертов:**

```sql
-- 1. Устаревшая статистика (таблицы >100k строк, не анализировались сутки)
SELECT relname, last_analyze, last_autoanalyze, n_live_tup
  FROM pg_stat_user_tables
 WHERE n_live_tup > 100000
   AND (last_analyze IS NULL OR last_analyze < now() - interval '1 day')
 ORDER BY n_live_tup DESC;

-- 2. Запросы с аномальным временем планирования (PG 19+)
SELECT query, calls, mean_plan_time, mean_exec_time
  FROM pg_stat_statements
 WHERE mean_plan_time > 100  -- мс
 ORDER BY mean_plan_time DESC
 LIMIT 10;

-- 3. Запросы, которые могут «прыгать» между custom и generic plan (PG 19+)
SELECT query, calls, generic_plans, custom_plans,
       round(generic_plans::numeric / nullif(calls,0), 2) AS generic_ratio
  FROM pg_stat_statements
 WHERE calls > 1000
   AND generic_plans > 0
   AND custom_plans > 0
 ORDER BY (abs(generic_plans - custom_plans)) DESC
 LIMIT 20;
```

**Интеграция с мониторингом:**
*   Экспортируйте `pg_stat_statements` и `pg_stat_user_tables` через `postgres_exporter` или аналоги.
*   Алерт на `mean_plan_time > 100ms` для топ-10 запросов.
*   Алерт на `last_analyze IS NULL` для таблиц >1M строк.
*   При включённом `auto_explain` учитывайте объём логов: при нагрузке >1000 QPS конфигурация `log_analyze = on` может заполнить диск за часы. Используйте `sample_rate` или `log_min_duration` не ниже 1–2 секунд.

**Затраты времени на анализ (PostgreSQL 18+).** `pg_stat_all_tables` и его варианты получили столбцы `total_analyze_time` и `total_autoanalyze_time` (рядом с `total_vacuum_time` и `total_autovacuum_time`). Это позволяет отличить дорогой `ANALYZE` от дешёвого не только по факту выполнения, но и по стоимости:

```sql
-- Таблицы, на которые анализ уходит дороже всего
SELECT relname, n_live_tup,
       total_analyze_time, total_autoanalyze_time,
       last_analyze, last_autoanalyze
  FROM pg_stat_user_tables
 ORDER BY total_analyze_time + total_autoanalyze_time DESC
 LIMIT 20;
```

Высокое `total_autoanalyze_time` при высокой частоте запусков — признак того, что пороги autovacuum для таблицы слишком чувствительны либо statistics target завышен. Подробности о самом процессе обслуживания — в [Внутреннее устройство VACUUM](./vacuum_internals.md).

**Приоритизация автообслуживания (PostgreSQL 19+).** Autovacuum получил систему очков, определяющую порядок обработки таблиц, с весами `autovacuum_analyze_score_weight`, `autovacuum_vacuum_score_weight`, `autovacuum_vacuum_insert_score_weight`, `autovacuum_multixact_freeze_score_weight` и `autovacuum_freeze_score_weight`, а также представление `pg_stat_autovacuum_scores`. Это уже не «round-robin по времени срабатывания порога»: таблицы с самой высокой оценкой обслуживаются первыми. Практическое следствие для SRE — при нехватке ресурсов автовакуума деградацию видно по очередности, а не по факту пропуска, поэтому `pg_stat_autovacuum_scores` стоит включить в дашборд. Новый параметр `log_autoanalyze_min_duration` логирует длительные запуски анализа от autovacuum (ранее `log_autovacuum_min_duration` покрывал только vacuum).

**Планирование обслуживания статистики.** Массовый пересчёт удобно делать не только через `vacuumdb` (см. сценарий [Исправление устаревшей статистики](#4-исправление-устаревшей-статистики)), но и через планировщик самой СУБД. Полезно сначала посмотреть, что именно будет выполнено: `vacuumdb --dry-run` (PostgreSQL 19+) печатает команды без их запуска. А `vacuumdb --analyze-only` и `--analyze-in-stages` в PostgreSQL 19 стали обрабатывать партиционированные таблицы, когда цели не указаны, — ранее они их пропускали, и это поведение теперь совпадает с обычным `ANALYZE`.

**Особенность миграции:** PostgreSQL 14 переходит в EOL в ноябре 2026. Если в кластере остались инстансы 14.x, проверьте планы эталонных запросов до апгрейда: cost model и GEQO между 14 и 15 могут давать разные планы для одних и тех же данных.

### 8. Запросы, которые «скачут» между планами

Симптом: один и тот же запрос по ночам и в дневное время выполняется то за 5 мс, то за 5 секунд, при неизменных данных и одинаковых параметрах.

Порядок проверки:

1. **Сравнить планы.** Включить `auto_explain.log_settings = on` и сопоставить недефолтные параметры в «хорошем» и «плохом» выводе. Планирование может идти в сессии приложения с другими GUC, чем у диагностического.
2. **Проверить кеш планов.** Если запрос параметризованный — сравнить custom и generic plan (см. [Планирование подготовленных запросов](#планирование-подготовленных-запросов-и-кеш-планов)).
3. **Проверить актуальность статистики** по таблице из плана.
4. **Проверить, не включён ли GEQO** для этого запроса, и не менялся ли `geqo_seed`. При фиксированном seed GEQO воспроизводим, поэтому само по себе его включение план не «скачет» — но смена seed в конфигурации или в `ALTER DATABASE ... SET` меняет набор исследуемых путей и может дать другой результат. Если после правки конфигурации план изменился, проверьте этот параметр в первую очередь.
5. **Проверить параллельность.** При нехватке воркеров план с `Gather` выполняется с меньшим их числом — производительность прыгает в зависимости от текущей загрузки кластера.
6. **Проверить `Planning Time`.** Если оно растёт со временем, проблема в размере запроса или в раздутых `from_collapse_limit`/`join_collapse_limit`, а не в данных.

### 9. Планировщик без статистики: внешние таблицы

Самая частая причина «планировщик ведёт себя неадекватно» в федеративных и шардированных setups — то, что планировщик **не знает ничего** о внешних таблицах, пока для них явно не выполнен `ANALYZE`.

Без `ANALYZE` локальная оценка для внешней таблицы строится вслепую: `pg_class.reltuples` содержит `-1`, то есть число строк **неизвестно**, и планировщик работает с оценкой по умолчанию. Документация `postgres_fdw` формулирует это прямо: локальная оценка «вряд ли будет точной, если нет локальных копий статистики удалённой таблицы». Отсюда типичные симптомы: соединение уводится на удалённый сервер вместо локального Hash Join, планируется Nested Loop там, где нужен Hash Join, либо, наоборот, движок решает перелить обе удалённые таблицы к себе целиком и соединять локально.

Проверка — одна строка: у внешней таблицы `reltuples` равен `-1`, пока не собрана статистика.

```sql
SELECT c.relname,
       c.reltuples::bigint   AS est_rows,
       c.repages,
       l.last_analyze
  FROM pg_class c
  LEFT JOIN pg_stat_all_tables l ON l.relid = c.oid
 WHERE c.relkind = 'f'
 ORDER BY c.relname;
```

Три способа дать планировщику данные, и у них разная цена:

| Способ | Что делает | Цена |
| :--- | :--- | :--- |
| `ANALYZE` по внешней таблице | Читает выборку удалённых данных и строит **локальную** статистику, как для обычной таблицы. | Разовый сетевой трафик. Статистика устаревает сама — autovacuum её не обновляет. |
| `use_remote_estimate` | `postgres_fdw` выполняет удалённый `EXPLAIN` на каждом планировании и берёт оценки оттуда. | Раунд-трип на каждый план — заметно повышает `Planning Time`. |
| `import_stats` (PG 19) | `ANALYZE` не читает данные, а **импортирует** готовую удалённую статистику локально. | Дёшево, но актуальность удалённой статистики — на вас. |

```sql
-- Вариант 1: собрать локальную статистику один раз
ANALYZE remote_orders;

-- Вариант 2: брать оценки у удалённого сервера
ALTER SERVER remote OPTIONS (SET use_remote_estimate 'true');

-- Вариант 2a: то же только для одной таблицы
ALTER FOREIGN TABLE remote_orders OPTIONS (SET use_remote_estimate 'true');

-- Вариант 3 (PostgreSQL 19): импортировать удалённую статистику вместо выборки
ALTER FOREIGN TABLE remote_orders OPTIONS (SET import_stats 'true');
```

Настройка `import_stats` работает только для удалённых объектов, у которых может быть обычная статистика: обычных таблиц (не наследников) и материализованных представлений. Если импорт не удался, PostgreSQL откатывается к выборке строк. Размер выборки при `ANALYZE` регулируется опцией `analyze_sampling` (`auto` по умолчанию) — для больших удалённых таблиц полный перенос данных недопустим.

**Для SRE:** у внешних таблиц нет автовакуума, поэтому локальная статистика не обновляется сама и никакой алерт об устаревшей статистике её не поймает. Вводите регулярный `ANALYZE` по внешним таблицам в то же окно, что и остальной `vacuumdb --analyze-only`. Полная механика FDW — в [Foreign Data Wrappers (FDW)](../Integrations/fdw.md).

## Устранение неисправностей

| Симптом | Вероятная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Seq Scan вместо Index Scan на большой таблице | Устаревшая статистика, высокий `random_page_cost`, заниженный `effective_cache_size`, отсутствие нужного индекса | `EXPLAIN (ANALYZE, BUFFERS)`; `SELECT reltuples, relpages FROM pg_class ...` против фактического размера | `ANALYZE`, настройка стоимостных констант, создание индекса |
| Оценка строк отличается от факта в десятки раз | Битая функциональная зависимость между колонками, неравномерное распределение, нехватка MCV | Сравнение `rows` и `actual rows`, `EXPLAIN (VERBOSE)` | Расширенная статистика (`dependencies`, `mcv`), повышение statistics target |
| Планирование занимает сотни мс | Слишком много элементов `FROM`, высокие лимиты свёртки, большое число партиций | `Planning Time` в `EXPLAIN (ANALYZE)`, `EXPLAIN (MEMORY)` (17+) | Уменьшить `from_collapse_limit`/`join_collapse_limit`, упростить запрос, отключить `enable_partitionwise_*` |
| План «прыгает» между запусками | Переход между custom и generic plan, смена `geqo_seed`, нехватка параллельных воркеров | `EXPLAIN (GENERIC_PLAN)` против `EXPLAIN EXECUTE`; `auto_explain` в лог; проверить историю правок `postgresql.conf` | `plan_cache_mode`, разбор загрузки воркеров, возврат `geqo_seed` к прежнему значению |
| После `pg_restore` / `pg_upgrade` всё работает медленнее | Статистика отсутствует или устарела | Пустая `pg_statistic`, `last_analyze IS NULL` в `pg_stat_user_tables` | `ANALYZE` (или `pg_dump`/`pg_upgrade` версии 18+ с сохранением статистики) |
| `EXPLAIN (ANALYZE, BUFFERS)` показывает много `temp read` | `work_mem` не хватает на сортировку или хеш-таблицу | `Batches: N` в узлах `Sort`/`Hash`, `temp read`/`temp write` | Локально поднять `work_mem`; см. [бюджет `work_mem`](../Operations/performance_tuning.md) |
| План не меняется при `SET enable_indexscan = off` | Альтернативного пути нет: нет индекса, предикат не может его использовать | `EXPLAIN` после отключения параметра | Изменить запрос или индекс, а не настройки планировщика |
| Hash Join с `Batches: N > 1` | Хеш-таблица не помещается в `work_mem × hash_mem_multiplier` | `Batches`, `Memory Usage` в выводе узла `Hash` | Увеличить `work_mem` или `hash_mem_multiplier`, проверить фактическую параллельность запроса |
| Внешняя сортировка или партиционированный хеш вместо в‑оперативных | `work_mem` недостаточен для узла (сорт, хеш, агрегат) | `EXPLAIN (ANALYZE)` — `Sort Method: external merge`, `Batches: N` | Подобрать `work_mem` под типичные выборки; для экземпляра — `ALTER ROLE` или `ALTER DATABASE` |
| Seq Scan вместо Index Scan на SSD | `random_page_cost` завышен, `effective_cache_size` занижен или `shared_buffers` слишком мал | `EXPLAIN (ANALYZE, BUFFERS)` — `shared read` vs `shared hit` | Скорректировать `random_page_cost` (1.1–1.5 для SSD/NVMe) и `effective_cache_size` под реальный объём ОС‑кэша |
| Высокий `Planning Time` через PgBouncer | Transaction pooling: кеш планов не переиспользуется между бэкендами | Сравнить `Planning Time` при прямом подключении и через пул | Использовать SQL‑функции, настроить драйверский кеш prepared statements или перейти на session pooling |
| План с сотнями узлов `Append` при партиционировании | Число партиций велико, `enable_partitionwise_join`/`aggregate` включены без нужды | `EXPLAIN` — число узлов в плане, `Planning Time` | Уменьшить число партиций, увеличить интервал партиционирования, отключить `enable_partitionwise_*` для этого класса запросов |
| Планировщик «не знает» внешнюю таблицу: соединение уходит на удалённый сервер или, наоборот, данные переливаются локально | У внешней таблицы нет локальной статистики, `reltuples = -1` | `SELECT reltuples FROM pg_class WHERE relkind = 'f'` | `ANALYZE` по внешней таблице либо `use_remote_estimate` / `import_stats` — см. сценарий [Планировщик без статистики: внешние таблицы](#9-планировщик-без-статистики-внешние-таблицы) |
| План изменился сразу после очередного `ANALYZE`, хотя данные не менялись | `ANALYZE` читает случайную выборку; при пограничной стоимости слегка изменившаяся оценка перевернула выбор | Сравнить планы до и после; проверить `rows` в узлах | Повысить statistics target для столбцов, участвующих в оценке |
| Отчётность через курсор отдаёт первые строки медленно | `cursor_tuple_fraction` (по умолчанию 0.1) не оптимален для инструмента, который читает курсор целиком или почти целиком | `EXPLAIN` — сравнить `startup cost` и `total cost` в плане | Уменьшить `cursor_tuple_fraction` для быстрого старта либо увеличить до 1.0 для минимизации total cost |
| `Planning Time` у запросов через PgBouncer заметно выше, чем при прямом подключении | Transaction pooling без `max_prepared_statements`: кеш планов не переиспользуется между бэкендами | Сравнить `Planning Time` при прямом подключении и через пул | Задать `max_prepared_statements` (PgBouncer 1.21+) — см. [Connection Pooling и кеш планов](#connection-pooling-и-кеш-планов) |
| `JIT:` в `EXPLAIN (ANALYZE)` есть, а запрос отрабатывает за миллисекунды | JIT компилируется по оценке стоимости, которая на транзакционном профиле часто завышена | Сумма `Timing` в блоке `JIT:` против `Execution Time` | `jit = off` на OLTP-базах, `jit = on` на аналитических |

## Лучшие практики

*   **Начинайте со статистики, а не с GUC.** Практически все «неправильные» решения планировщика — следствие неверной оценки, а не неверного веса. `ANALYZE` и расширенная статистика бесплатны; изменение констант стоимости затрагивает все запросы кластера сразу.
*   **Не увеличивайте `from_collapse_limit` / `join_collapse_limit` «на всякий случай».** Рост времени планирования экспоненциален, а при достижении `geqo_threshold` качество плана ухудшается.
*   **Меняйте стоимостные константы под конкретное оборудование и профиль нагрузки** и закрепляйте результат измерениями, а не переносом чужих значений. Значение, будучи полезным для одной установки, способно ухудшить планы другой.
*   **Используйте `enable_*` как диагностику, а не как конфигурацию.** Если принудительное отключение узла улучшает результат — фиксируйте это как показание к работе со статистикой или индексом.
*   **Включайте `auto_explain.log_settings`.** Это самый дешёвый способ узнать, какие недефолтные параметры действовали в момент принятия решения.
*   **Ограничивайте накладные расходы диагностики.** `TIMING OFF` вместо `TIMING`, `sample_rate`, `log_timing = off` при `log_analyze = on`. Особенно важно в проде, где диагностика не должна ломать то, что она измеряет.
*   **Учитывайте объём логов.** План с `log_analyze` на продакшен-нагрузке — это десятки мегабайт в час; настройте `log_min_duration` осмысленно и проверьте политику ротации.
*   **Закрепляйте планы осознанно.** `join_collapse_limit = 1`, `plan_cache_mode = force_custom_plan`, а в PostgreSQL 19 — plan advice. Любой из этих приёмов ослабляет адаптацию планировщика к изменившимся данным; закреплённый план устаревает и становится источником инцидента, который сложнее диагностировать, чем обычная ошибка оценки.
*   **После любых массовых операций (restore, upgrade, загрузка данных, смена `work_mem`/`random_page_cost`) проверяйте планы эталонных запросов**, а не только факт успешного завершения операции.
*   **Сопоставляйте `shared_buffers` и `effective_cache_size` с реальной конфигурацией ОС.** Недостаток `shared_buffers` делает `effective_cache_size` бессмысленным; его завышение приводит к тому, что планировщик ожидает слишком много cache hits и выбирает индексы, которых нет.
*   **Учитывайте connection pooling при диагностике.** Сравнивайте `Planning Time` при прямом подключении и через PgBouncer; если через пул оно выше — проблема не в cost model, а в отсутствии переиспользования кеша планов между бэкендами. Не отказывайтесь от transaction pooling из-за этого: `max_prepared_statements` в PgBouncer 1.21+ решает задачу без смены режима пула.
*   **Не путайте воспроизводимый GEQO со случайным планом.** GEQO детерминирован при фиксированном `geqo_seed`. Если план изменился — ищите смену seed, custom/generic plan, настройки сессии или доступность воркеров, а не «рандомизацию GEQO».
*   **Собирайте статистику для внешних таблиц по расписанию.** У них нет автовакуума, поэтому ни `ANALYZE`, ни алерты об устаревшей статистике не сработают сами.
*   **Не поднимайте `jit` на OLTP-базах «на всякий случай».** Порог активации основан на оценке стоимости, а не на измеренном времени; на транзакционном профиле он регулярно срабатывает впустую.
*   **Мониторьте `pg_stat_user_tables.last_analyze` и `pg_stat_statements.mean_plan_time` (PG 19+).** Это дешевле и надёжнее, чем пытаться «угадать» правильные `random_page_cost` по чужим статьям.
*   **При партиционировании измеряйте время планирования, а не только время выполнения.** При переходе с дневных RANGE на HASH или месячные интервалы `Planning Time` может снизиться на порядок, что даёт больший выигрыш, чем подстройка весов.
