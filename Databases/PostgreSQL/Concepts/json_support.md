# Поддержка JSON в PostgreSQL

## Определения

- **JSON (JavaScript Object Notation)**: Легкий текстовый формат обмена данными. В PostgreSQL представлен двумя основными типами: `json` и `jsonb`.
- **json (Plain JSON)**: Текстовый тип данных, хранящий точную копию входного текста. Сохраняет форматирование, пробелы и порядок ключей. Требует парсинга при каждом обращении к внутренним элементам.
- **jsonb (Binary JSON)**: Бинарный тип данных, хранящий декомпозированную структуру. Парсинг происходит один раз при вставке. Не сохраняет пробелы и порядок ключей, но поддерживает эффективную индексацию и быстрый доступ.
- **TOAST (The Oversized Attribute Storage Technique)**: Механизм PostgreSQL для хранения больших атрибутов. Документы размером более ~2 КБ автоматически сжимаются и выносятся во внетабличное хранилище, что экономит место, но увеличивает время доступа при чтении.
- **SQL/JSON**: Набор стандартных функций и операторов (SQL:2016), внедренных в PostgreSQL (особенно активно в версиях 15–17) для унифицированной работы с JSON-данными.

## Базовые концепции

### Сравнение типов json и jsonb

| Характеристика | `json` | `jsonb` | `hstore` (расширение) |
| :--- | :--- | :--- | :--- |
| **Хранение** | Текст "как есть" | Бинарная иерархия | Текстовые пары ключ-значение |
| **Вставка** | Быстрая | Медленнее | Быстрая |
| **Чтение** | Медленное | Быстрое | Быстрое (плоская структура) |
| **Индексация** | Нет | **GIN**, GiST, B-Tree | GIN, GiST |
| **Особенности** | Сохраняет формат | Эффективный поиск | Только строковые ключи и значения |

**hstore** полезен для:
- Объединения в одной базе объектов с разными атрибутами без изменения схемы (например, характеристики разных категорий товаров: "жанр" для книг, "страна" для ручек).
- Обеспечения "чистоты" базы за счет использования нескольких колонок вместо множества разреженных столбцов.

### Хранение и производительность (MVCC и TOAST)

PostgreSQL использует модель **MVCC**. При обновлении любого поля в `jsonb`-документе СУБД создает **полную копию** всей строки (включая весь JSON-объект).
Это приводит к:
- **Раздуванию (Bloat)**: частое обновление документов увеличивает размер таблицы.
- **I/O нагрузке**: запись больших документов создает нагрузку на диск.
- **Нагрузке на Autovacuum**: требуется частая очистка старых версий.

**Рекомендация:** Часто меняющиеся атрибуты (счетчики, статусы) следует выносить в обычные колонки таблицы.

### Индексация

1. **GIN (Generalized Inverted Index)**:
   - `jsonb_ops` (по умолчанию): индексирует каждый ключ и значение. Поддерживает операторы вхождения (`@>`) и наличия (`?`).
   - `jsonb_path_ops`: индексирует только полные пути. Индекс компактнее и быстрее, но поддерживает только оператор вхождения (`@>`).

2. **B-Tree (индексы на выражения)**:
   Эффективен для поиска по конкретному ключу верхнего уровня.
   ```sql
   CREATE INDEX idx_orders_customer_id ON orders ((data->>'customer_id'));
   ```

## Практические сценарии

### Основные операторы и сабскриптинг

| Оператор | Описание | Пример |
| :--- | :--- | :--- |
| `->` | Получить элемент как JSON | `data->'user'` |
| `->>` | Получить элемент как текст | `data->>'email'` |
| `[]` | Сабскриптинг (PG 14+) | `data['profile']['name']` |
| `@>` | Проверка вхождения | `data @> '{"status": "active"}'` |
| `?` | Наличие ключа | `data ? 'tags'` |

### SQL/JSON Пути (JsonPath)

Позволяет использовать сложные выражения для поиска внутри документов (PG 12+).

```sql
-- Поиск пользователей старше 25 лет
SELECT * FROM users 
WHERE jsonb_path_exists(data, '$.profile.age ? (@ > 25)');
```

### Расширение jsquery
**jsquery** предоставляет более мощный язык запросов и эффективную индексацию для `jsonb`.
- **Зачем:** Поддерживает гибкие запросы к вложенным полям и массивам с использованием специализированных индексов (GIN).
- **Преимущество:** Значительно ускоряет полнотекстовый поиск внутри JSON и работу с динамическими структурами по сравнению со стандартными операторами.

### JSON_TABLE (PostgreSQL 17)

Революционная функция, позволяющая превращать JSON в реляционную таблицу "на лету".

```sql
SELECT jt.*
FROM orders,
     JSON_TABLE(data, '$.items[*]'
       COLUMNS (
         item_name text PATH '$.name',
         price numeric PATH '$.price',
         quantity int PATH '$.qty'
       )
     ) AS jt;
```

### Сравнение с MongoDB

| Характеристика | PostgreSQL (`jsonb`) | MongoDB |
| :--- | :--- | :--- |
| **Согласованность** | Строгий **ACID** | На уровне документа |
| **Связи (Joins)** | Нативные SQL-джойны | Ограниченно (`$lookup`) |
| **Обновления** | Перезапись всей строки (MVCC) | Частичное обновление (In-place) |
| **Аналитика** | Мощный SQL + JSON_TABLE | Aggregation Framework |

## Дополнительная информация

### Лимиты и валидация

- **Максимальный размер**: 1 ГБ для `jsonb`. Оптимально — до 1-2 МБ.
- **Схемы**: PostgreSQL не поддерживает нативную JSON Schema для валидации из коробки. Рекомендуется использовать `CHECK`-ограничения с функцией `jsonb_matches_schema` (если установлено расширение) или проверять структуру на уровне приложения.

### Когда использовать JSON в PostgreSQL

- **Динамические атрибуты**: Когда набор полей меняется от записи к записи (например, характеристики товаров разных категорий).
- **Интеграция с API**: Хранение ответов внешних систем в исходном виде.
- **Прототипирование**: Ускорение разработки на ранних этапах.

### Когда НЕ использовать JSON в PostgreSQL

- **Строгая схема**: Если данные имеют четкую структуру, реляционные колонки всегда быстрее и экономнее по месту.
- **Частые частичные обновления**: Приводит к быстрому раздуванию базы.
