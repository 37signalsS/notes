# Поддержка JSON в PostgreSQL

## Определения

- **JSON (JavaScript Object Notation)** — легкий текстовый формат обмена данными. В PostgreSQL представлен двумя типами данных: `json` и `jsonb`.
- **json (Plain JSON)** — текстовый тип данных, хранящий точную копию входного текста. Сохраняет форматирование, пробелы и порядок ключей. Требует повторного парсинга при каждом обращении.
- **jsonb (Binary JSON)** — бинарный тип данных, хранящий декомпозированную структуру. Парсинг происходит один раз при вставке. Не сохраняет пробелы и порядок ключей, но поддерживает эффективную индексацию.
- **TOAST (The Oversized Attribute Storage Technique)** — механизм PostgreSQL для хранения больших атрибутов. Если документ превышает порог (обычно 2 КБ), он выносится во внешние таблицы хранения, что влияет на скорость доступа.

## Базовые концепции

### Сравнение типов json и jsonb

| Характеристика | `json` | `jsonb` |
| :--- | :--- | :--- |
| **Хранение** | Текст "как есть" | Бинарная иерархия |
| **Вставка** | Быстрая (без обработки) | Медленнее (требуется парсинг) |
| **Чтение** | Медленное (парсинг при чтении) | Быстрое (готовая структура) |
| **Индексация** | Нет (только полнотекстовый поиск) | **GIN**, GiST, B-Tree (выражения) |
| **Порядок ключей** | Сохраняется | Не сохраняется |

### Хранение и производительность (MVCC и TOAST)

PostgreSQL использует модель **MVCC (Multi-Version Concurrency Control)**. При обновлении даже одного поля в `jsonb`-документе (например, через `jsonb_set`), СУБД создает **полную копию** всего документа.
Это приводит к следующим последствиям:

- **Раздувание (Bloat)**: частое обновление документов быстро увеличивает размер таблицы и индексов.
- **I/O нагрузка**: запись больших документов (особенно вынесенных в TOAST) создает высокую нагрузку на дисковую подсистему.
- **Нагрузка на Autovacuum**: системе требуется чаще очищать старые версии документов.

**Рекомендация:** Часто меняющиеся атрибуты (счетчики, статусы) следует выносить в обычные колонки таблицы.

### Индексация

1. **GIN (Generalized Inverted Index)**:
   - `jsonb_ops` (по умолчанию): индексирует каждый ключ и значение. Поддерживает все операторы вхождения и наличия.
   - `jsonb_path_ops`: индексирует только пути. Индекс компактнее и быстрее, но поддерживает только оператор вхождения `@>`.

2. **B-Tree (индексы на выражения)**:
   Если поиск всегда идет по конкретному ключу, эффективнее создать обычный B-Tree индекс:

   ```sql
   CREATE INDEX idx_orders_customer_id ON orders ((data->>'customer_id'));
   ```

## Практические сценарии

### Основные операторы и функции

| Оператор | Описание | Пример |
| :--- | :--- | :--- |
| `->` | Получить элемент как JSON | `data->'user'` |
| `->>` | Получить элемент как текст | `data->>'email'` |
| `#>` | Получить объект по пути | `data#>'{profile, name}'` |
| `@>` | Проверка вхождения | `data @> '{"status": "active"}'` |
| `?` | Наличие ключа | `data ? 'tags'` |

### Сравнение с MongoDB

Использование `jsonb` позволяет превратить PostgreSQL в документоориентированную СУБД, сохраняя преимущества реляционной модели.

| Характеристика | PostgreSQL (`jsonb`) | MongoDB |
| :--- | :--- | :--- |
| **Согласованность** | Строгий **ACID** для всей строки | Базово — на уровне документа |
| **Связи (Joins)** | Нативные SQL-джойны с таблицами | Ограниченно (через `$lookup`) |
| **Обновления** | Перезапись всего документа | In-place (частичное обновление) |
| **Масштабирование** | Вертикальное (шардирование через расширения) | Горизонтальное (шардирование из коробки) |
| **Индексация** | **GIN** (индексирует всё сразу) | Разнообразные типы индексов |

**Преимущество единого хранилища:**
Вместо разделения данных между PostgreSQL (структурированные поля: login, email) и MongoDB (динамические атрибуты), можно хранить всё в одной таблице. Это гарантирует атомарность изменений и упрощает инфраструктуру (не нужно поддерживать вторую БД).

### Когда использовать JSON в PostgreSQL

- **Гибкие атрибуты пользователя**: Когда у разных пользователей разный набор параметров (атрибуты авторизации, настройки профиля).
- **Слабоструктурированные данные**: Характеристики товаров, метаданные аналитики.
- **Прототипирование**: Когда схема данных еще не устоялась.
- **Нагрузка до средних значений**: При миллионах документов на одном инстансе JSONB работает отлично.

### Когда НЕ использовать JSON в PostgreSQL

- **Экстремальный трафик**: Если требуются миллиарды документов и горизонтальное масштабирование записи "из коробки" (лучше MongoDB).
- **Частые частичные обновления**: Если документ огромный, а меняется в нем одно маленькое поле 100 раз в секунду (PostgreSQL будет каждый раз переписывать весь документ).
- **Динамическое создание индексов**: Если нужно создавать индексы в рантайме под любые запросы (в MongoDB это более гибко).


## Дополнительная информация

- **Лимиты**: Максимальный размер одного `jsonb` документа — 1 ГБ, однако производительность резко падает при размере более 1-2 МБ.
- **Валидация**: PostgreSQL проверяет корректность формата JSON при вставке. Для проверки схем можно использовать `CHECK` ограничения или внешние расширения.
