# Масштабирование PostgreSQL

## 1. Определения

*   **Вертикальное масштабирование (Scale-Up):** Увеличение ресурсов на существующем сервере (CPU, RAM, более быстрые диски). Этот подход прост, но имеет физические и экономические пределы.
*   **Горизонтальное масштабирование (Scale-Out):** Распределение данных и/или нагрузки на несколько серверов. Этот подход более сложен, но потенциально обеспечивает неограниченную масштабируемость.
*   **Партиционирование (Partitioning):** Разделение одной большой таблицы на несколько меньших физических таблиц (партиций) *в пределах одного сервера*. Хотя это происходит на одном узле, это является формой горизонтального разделения данных.

## 2. Основные концепции

В PostgreSQL горизонтальное масштабирование достигается тремя основными способами:
1.  **Масштабирование чтения (Read Scaling):** Нагрузка от `SELECT`-запросов распределяется по нескольким серверам-репликам. Это самая простая в реализации стратегия.
2.  **Партиционирование:** Большая таблица делится на части, что ускоряет запросы и обслуживание за счет работы с меньшими объемами данных. Это встроенный механизм PostgreSQL.
3.  **Шардирование:** Данные физически разделяются по разным серверам. В PostgreSQL это реализуется с помощью сторонних расширений.

## 3. Практические сценарии

### 3.1. Масштабирование чтения с помощью репликации

Помимо обеспечения [высокой доступности](./high_availability.md), репликация является ключевым методом для **масштабирования нагрузки на чтение**. Запросы на чтение (`SELECT`) распределяются между несколькими репликами, что снижает нагрузку на основной сервер (мастер), который концентрируется на обработке операций записи.

> Подробно механизмы физической и логической репликации описаны в заметке **[Типы репликации в PostgreSQL](./replication.md)**.

### 3.2. Партиционирование (Встроенный механизм)

**Преимущества:**
- **Ускорение запросов:** Планировщик может отсекать (partition pruning) те партиции, которые заведомо не содержат нужных данных.
- **Ускорение обслуживания:** `VACUUM` или перестроение индексов можно выполнять на отдельных партициях.

#### Встроенные методы партиционирования:

1.  **По диапазону (Range Partitioning):** Данные распределяются по партициям на основе диапазона значений ключевого столбца. Идеально подходит для временных рядов (например, партиционирование по дате).

    ```sql
    CREATE TABLE orders (
        order_id INT,
        order_date DATE,
        ...
    ) PARTITION BY RANGE (order_date);

    CREATE TABLE orders_2023 PARTITION OF orders
        FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
    ```

2.  **По списку (List Partitioning):** Данные распределяются на основе принадлежности значения ключевого столбца к определенному списку. Подходит для разделения по категориям, регионам и т.д.

    ```sql
    CREATE TABLE customers (
        customer_id INT,
        region_code INT,
        ...
    ) PARTITION BY LIST (region_code);

    CREATE TABLE customers_europe PARTITION OF customers
        FOR VALUES IN (1, 2, 3);
    ```

3.  **По хешу (Hash Partitioning):** Данные распределяются по партициям на основе хеш-значения ключевого столбца. Используется для равномерного распределения данных, когда нет очевидного ключа для разделения по диапазону или списку.

    ```sql
    CREATE TABLE users (
        user_id INT,
        username TEXT,
        ...
    ) PARTITION BY HASH (user_id);

    -- Создание нескольких партиций для равномерного распределения
    CREATE TABLE users_part_0 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 0);
    CREATE TABLE users_part_1 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 1);
    CREATE TABLE users_part_2 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 2);
    CREATE TABLE users_part_3 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 3);
    ```

### 3.3. Шардирование (с помощью расширений)

**Шардирование** — это следующий шаг после партиционирования, который подразумевает физическое распределение данных (шардов) по разным серверам.

> Подробно общая теория рассмотрена в заметке **[Шардирование](../../../Databases/Concepts/sharding.md)**.

В "чистом" PostgreSQL нет встроенной поддержки шардирования, но его можно реализовать с помощью расширений:
- **[Citus](../../citus.md):** Превращает PostgreSQL в распределенную базу данных с архитектурой на основе **координатора**.
- **[Greenplum](../../greenplum.md):** Форк PostgreSQL, построенный по **"shared-nothing"** архитектуре, где каждый узел независим.
- Другие решения, такие как YugabyteDB и [TimescaleDB](../timescaledb.md) (для временных рядов).
