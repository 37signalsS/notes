# Масштабирование PostgreSQL

## Определения

- **Вертикальное масштабирование (Scale-Up)**: Увеличение вычислительных мощностей одного сервера (CPU, RAM, пропускная способность дисковой подсистемы, IOPS).
    - *Преимущества:* Простота реализации, отсутствие сетевых задержек, полная поддержка ACID без оверхеда на сеть.
    - *Ограничения:* Физический предел оборудования (упираемся в потолок CPU/RAM), экспоненциальный рост стоимости ("железо" для Scale-Up стоит дороже), риск единой точки отказа (SPOF).
- **Горизонтальное масштабирование (Scale-Out)**: Распределение нагрузки и данных между несколькими независимыми узлами (инстансами).
    - *Преимущества:* Теоретически неограниченный рост, высокая отказоустойчивость кластера.
    - *Ограничения:* Сложность управления, влияние CAP-теоремы, сетевые задержки при взаимодействии узлов.
- **Партиционирование (Partitioning)**: Логическое разделение одной большой таблицы на несколько физических сегментов (партиций) внутри одного инстанса. Оптимизирует производительность запросов (Partition Pruning) и упрощает обслуживание (Maintenance: `VACUUM`, `REINDEX`).
- **Шардирование (Sharding)**: Распределение партиций по разным физическим серверам. Каждый шард является самостоятельным инстансом, хранящим часть общего датасета. Подробнее: **[Шардирование баз данных](../../Concepts/sharding.md)**.
- **Логическая репликация**: Передача изменений на уровне отдельных строк и таблиц. Является основой для построения гибких топологий масштабирования, миграций между версиями и Cross-Shard JOIN.

## Базовые концепции

Стратегия масштабирования выбирается исходя из типа нагрузки: **Read-heavy** (чтение) или **Write-heavy** (запись).

### Масштабирование чтения (Read Scaling)

Реализуется через создание **[Реплик](./replication.md)** (Standby).

1.  **Физическая репликация**: Потоковая передача WAL. Реплики являются точными копиями мастера (Hot Standby).
2.  **Балансировка через драйвер (PG 16+)**:
    Параметр `load_balance_hosts=random` позволяет клиенту выбирать случайный узел из списка без внешнего балансировщика.
    ```ini
    # Строка подключения (connection string)
    postgresql://user:pass@host1,host2,host3/db?load_balance_hosts=random&target_session_attrs=read-only
    ```
3.  **Балансировка через Proxy**: Применение **HAProxy** или облачных балансировщиков для распределения трафика между пулом реплик.
4.  **Пул соединений (Connection Pooling)**:
    Использование **PgBouncer** или **Odyssey** обязательно. PostgreSQL создает процесс на каждое соединение, что при масштабировании потребляет много RAM.
    - *PgBouncer:* Легковесный, стандарт индустрии. Режим `transaction pooling` идеален для масштабирования.
    - *Odyssey:* Многопоточный, лучше справляется с экстремально большим количеством соединений.
    - Подробнее: **[Настройка PgBouncer](../Operations/pgbouncer_setup.md)**.

### Масштабирование записи (Write Scaling)

Наиболее сложная задача, требующая изменения архитектуры данных для распределения нагрузки на запись.

1.  **Декларативное партиционирование**:
    - Снижает нагрузку на индексы (они становятся меньше).
    - Упрощает `VACUUM` (работает в рамках партиции).
    - **Partition-wise Join/Aggregate**: (PG 12+) Позволяет выполнять соединения и агрегацию партиционированных таблиц параллельно, если они партиционированы по одному ключу.
2.  **Шардирование через расширения (Citus)**: Позволяет прозрачно распределять данные по кластеру серверов. Координатор распределяет запросы, воркеры выполняют их.
3.  **Ручное шардирование (FDW)**: Использование `postgres_fdw` для связи нескольких независимых инстансов PostgreSQL.
4.  **Масштабируемость WAL (PG 17)**: Улучшенная обработка логов транзакций при высокой конкуренции, снижающая блокировки в высоконагруженных системах.

## Практические сценарии

### Предварительные требования

1.  **Версия PostgreSQL**: 15+ для полноценной работы `NULLS NOT DISTINCT` и оптимизаций B-Tree. Для PG 17 доступна ускоренная очистка памяти VACUUM.
2.  **Сетевая инфраструктура**: При горизонтальном масштабировании (FDW, Citus) критична задержка (Latency) и пропускная способность сети (рекомендуется 10Gbps+).
3.  **Мониторинг**: Настроенный `pg_stat_statements` и отслеживание Replication Lag (задержки репликации).

### 1. Декларативное партиционирование

Начиная с PostgreSQL 11, партиционирование стало зрелым инструментом.

**Ключевые возможности (PG 16/17):**
- **Partition Pruning**: Оптимизатор исключает ненужные партиции. В PG 16 значительно ускорен поиск в LIST-партициях.
- **Поддержка ограничений (PG 17)**: Поддержка `IDENTITY` колонок и `EXCLUSION` ограничений.
- **Maintenance**: Быстрое удаление старых данных через `DETACH PARTITION` и `DROP TABLE`. Для checkpoint, traces и других временных данных важны временной ключ, partition pruning и политика retention; подробнее — **[PostgreSQL для памяти ИИ-агентов](../Operations/agent-memory.md)**.

```sql
-- Пример: Партиционирование по дате (Range)
CREATE TABLE orders (
    id bigserial,
    order_date timestamptz not null,
    customer_id int,
    amount numeric,
    PRIMARY KEY (id, order_date)
) PARTITION BY RANGE (order_date);

-- Создание партиции
CREATE TABLE orders_2024_q1 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');
```

**Сценарий: Переход на партиции без простоя (Zero-Downtime)**
1. Создать новую партиционированную таблицу `orders_new`.
2. Создать триггер на `orders`, который дублирует новые записи в `orders_new`.
3. Фоновым процессом переливать исторические данные.
4. В рамках транзакции переименовать таблицы.

### 2. Ручное шардирование через Foreign Data Wrappers (FDW)

Метод "шардирования для бедных", встроенный в ядро. Позволяет обращаться к таблицам на другом сервере как к локальным.

**Пример 1: Шардирование по хэшу (для равномерного распределения)**
```sql
-- На узле-координаторе:
CREATE EXTENSION postgres_fdw;
CREATE SERVER worker1_server FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host '10.0.0.5', dbname 'worker_db');
CREATE USER MAPPING FOR current_user SERVER worker1_server OPTIONS (user 'remote_user', password 'remote_pass');

-- Создание внешней таблицы-партиции
CREATE FOREIGN TABLE orders_sh1 PARTITION OF orders
    FOR VALUES WITH (MODULUS 4, REMAINDER 0)
    SERVER worker1_server OPTIONS (table_name 'orders_local');
```

**Пример 2: Шардирование по списку (для регионального распределения)**
```sql
CREATE FOREIGN TABLE sales_europe PARTITION OF sales
    FOR VALUES IN ('EU', 'UK')
    SERVER worker1_server OPTIONS (table_name 'sales_local');
```

*Оптимизация в PG 17:* Улучшена передача (pushdown) подзапросов `EXISTS` и `IN` на удаленные серверы.

### 3. Распределенный PostgreSQL с Citus

**[Citus](../../citus.md)** — расширение, превращающее PostgreSQL в распределенную СУБД (MPP).

- **Распределенные таблицы**: Данные режутся на шарды и раскладываются по воркерам.
  ```sql
  SELECT create_distributed_table('orders', 'customer_id');
  ```
- **Справочные таблицы (Reference Tables)**: Копируются на все узлы для быстрыx `JOIN` с распределенными таблицами.
  ```sql
  SELECT create_reference_table('products');
  ```

### 4. Сравнение методов шардирования

| Характеристика | Citus (Extension) | Postgres FDW (Native) | Application-side |
| :--- | :--- | :--- | :--- |
| **Прозрачность** | Высокая (один SQL интерфейс) | Средняя (нужны FOREIGN таблицы) | Низкая (логика в коде) |
| **Сложные JOIN** | Да (Colocated JOIN) | Ограниченно (Pushdown) | Нет (ручная сборка) |
| **Транзакции** | ACID (через 2PC) | Частично ACID | Ручное управление (Saga) |
| **Решардинг** | Автоматизированный | Ручной (сложный) | Зависит от кода |
| **Overhead** | Координатор | Сетевые задержки | Минимальный |

### 5. Распределенные транзакции (2PC) в PostgreSQL

Двухфазная фиксация (Two-Phase Commit, 2PC) — протокол, обеспечивающий атомарность изменений на нескольких независимых узлах.

#### Механика работы
1.  **Phase 1 (PREPARE):** Координатор посылает команду `PREPARE TRANSACTION 'id'`. Узлы проверяют возможность записи и фиксируют данные в WAL, но не делают их видимыми для других.
2.  **Phase 2 (COMMIT/ROLLBACK):** Если все узлы ответили "OK", координатор посылает `COMMIT PREPARED 'id'`. Если хотя бы один упал — `ROLLBACK PREPARED`.

#### Нюансы эксплуатации
- **max_prepared_transactions:** Этот параметр на воркерах должен быть ≥ `max_connections`, иначе `PREPARE` упадет с ошибкой. По умолчанию равен 0.
- **Риск "подвисших" транзакций:** Если координатор упал между фазами, транзакция на воркерe остается в состоянии PREPARED навсегда, удерживая блокировки.
    - *Решение:* Мониторинг `pg_prepared_xacts` и ручная очистка (или автоматика Citus).
- **Производительность:** 2PC требует минимум 3 синхронных записи в WAL (prepare на воркерах, запись решения на координаторе, commit на воркерах), что увеличивает Latency в 2-4 раза.
- **Видимость:** До финального коммита данные на воркерах не видны другим транзакциям (согласно правилам изоляции).

### 6. Новые возможности PG 17 для масштабирования

#### pg_createsubscriber
Утилита для быстрого превращения физической реплики в логическую, упрощая миграции и создание новых узлов без долгого простоя.
```bash
pg_createsubscriber -d "host=master_node dbname=mydb" -s "host=standby_node dbname=mydb" -p 5432 -D /var/lib/postgresql/data
```

#### Синхронизация слотов репликации
Позволяет логическим подписчикам бесшовно переключаться на новую реплику при Failover. Это критично для отказоустойчивого масштабирования.
```sql
-- В postgresql.conf на Primary и Standby
sync_replication_slots = on
```

#### Инкрементальные бэкапы
Нативная поддержка инкрементального резервного копирования на основе WAL-суммирования. Снижает нагрузку на инфраструктуру при росте БД.
```bash
# Создание инкрементального бэкапа относительно полного
pg_basebackup -D /path/to/backup --incremental=/path/to/full_backup_manifest
```

## Диагностика и устранение проблем (Troubleshooting)

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Replication Lag** | Медленная сеть или диски на Standby. | `SELECT * FROM pg_stat_replication;` Проверить утилизацию дисков. |
| **Hot Shard** | Неудачный ключ шардирования. | Анализ распределения данных по шардам, переезд на другой ключ (например, UUID). |
| **Bloat на партициях** | Редкий VACUUM при высокой записи. | Уменьшение `autovacuum_vacuum_scale_factor` для конкретных партиций. |
| **Slow Cross-Shard JOIN** | Тяжелые соединения между узлами. | Использование Reference Tables или денормализация данных. |

## Обслуживание при масштабировании (Maintenance)

1.  **Новый механизм VACUUM (PG 17)**: Использует структуру **TidStore**, которая потребляет до 20 раз меньше памяти (RAM). Это критично для гигантских таблиц.
2.  **Streaming I/O**: Ускоряет последовательное сканирование данных и работу `ANALYZE`, что важно для больших кластеров.
3.  **Роль MAINTAIN**: Позволяет делегировать задачи по обслуживанию (VACUUM, REINDEX, ANALYZE) без предоставления прав суперпользователя.

## Дополнительная информация

### Когда масштабирование может навредить

- **Overhead на планирование**: При количестве партиций > 1000 время планирования запроса (Planning Time) растет.
- **Cross-shard запросы**: Если запрос требует данных с многих шардов (Fan-out), производительность резко падает.
- **Глобальные индексы**: Их отсутствие в PG требует включения ключа партиционирования в `UNIQUE`/`PK`.

### Сравнение технологий

| Технология | Тип | Основной кейс |
| :--- | :--- | :--- |
| **Native Partitioning** | Встроенное | Очистка данных (TTL), оптимизация внутри узла. |
| **Patroni + HAProxy** | HA + Read Scale | Стандартный стек для отказоустойчивых реляционных БД. |
| **Citus** | Расширение | Высокая нагрузка на запись, Multi-tenant SaaS, аналитика. |
| **Greenplum** | Fork (MPP) | Тяжелая аналитика, хранилища данных (DWH). |
| **TimescaleDB** | Расширение | Временные ряды (IoT, метрики) с авто-партиционированием. |
