# Масштабирование PostgreSQL

## Определения

* **Вертикальное масштабирование (Scale-Up):** Увеличение ресурсов (CPU, RAM, диски) на существующем сервере. Подход прост, но ограничен физическими и экономическими пределами.
* **Горизонтальное масштабирование (Scale-Out):** Распределение данных и/или нагрузки на несколько серверов. Подход сложнее, но обеспечивает практически неограниченную масштабируемость.
* **Партиционирование (Partitioning):** Разделение большой таблицы на несколько физических таблиц-партиций *в пределах одного сервера*. Является формой горизонтального разделения данных на одном узле.

## Основные концепции

В PostgreSQL горизонтальное масштабирование достигается тремя основными способами:

1. **Масштабирование чтения (Read Scaling):** Нагрузка от `SELECT`-запросов распределяется по нескольким серверам-репликам. Это самая простая в реализации стратегия.
2. **Партиционирование:** Большая таблица делится на части для ускорения запросов и обслуживания. Это встроенный механизм PostgreSQL.
3. **Шардирование:** Данные физически разделяются по разным серверам. Реализуется с помощью сторонних расширений.

## Практические сценарии

### Масштабирование чтения с помощью репликации

Помимо обеспечения [высокой доступности](./high_availability.md), репликация является ключевым методом для масштабирования нагрузки на чтение. `SELECT`-запросы распределяются между репликами, что снижает нагрузку на основной сервер (мастер), который концентрируется на операциях записи.

> Подробно механизмы репликации описаны в заметке **[Репликация в PostgreSQL](./replication.md)**.

### Партиционирование (встроенный механизм)

**Преимущества:**

* **Ускорение запросов:** Планировщик отсекает (partition pruning) партиции, которые заведомо не содержат нужных данных.
* **Ускорение обслуживания:** `VACUUM` или перестроение индексов можно выполнять на отдельных, меньших партициях.

#### Встроенные методы партиционирования

1. **По диапазону (Range Partitioning):** На основе диапазона значений ключа. Идеально для временных рядов (например, по дате).

    ```sql
    CREATE TABLE orders (order_date DATE, ...) PARTITION BY RANGE (order_date);
    CREATE TABLE orders_2023 PARTITION OF orders
        FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
    ```

2. **По списку (List Partitioning):** На основе принадлежности значения к списку. Подходит для разделения по категориям или регионам.

    ```sql
    CREATE TABLE customers (region_code INT, ...) PARTITION BY LIST (region_code);
    CREATE TABLE customers_europe PARTITION OF customers
        FOR VALUES IN (1, 2, 3);
    ```

3. **По хешу (Hash Partitioning):** На основе хеш-значения ключа. Для равномерного распределения данных.

    ```sql
    CREATE TABLE users (user_id INT, ...) PARTITION BY HASH (user_id);
    CREATE TABLE users_p0 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 0);
    CREATE TABLE users_p1 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 1);
    -- и т.д.
    ```

### Шардирование (с помощью расширений)

**Шардирование** — это следующий шаг, подразумевающий физическое распределение партиций (шардов) по разным серверам.

> Подробно общая теория рассмотрена в заметке **[Шардирование](../../../Databases/Concepts/sharding.md)**.

В "ванильном" PostgreSQL нет встроенной поддержки шардирования, но она реализуется через расширения:

* **[Citus](../../citus.md):** Превращает PostgreSQL в распределенную БД с архитектурой на основе **координатора**.
* **[Greenplum](../../greenplum.md):** Форк PostgreSQL с архитектурой **"shared-nothing"**, где каждый узел независим.
* Другие решения, такие как YugabyteDB и **[TimescaleDB](../../timescaledb.md)** (для временных рядов).

**Важно:** При шардировании критически важна стратегия резервного копирования и восстановления. См. **[Резервное копирование и восстановление](./backup_and_recovery.md)**.

## Дополнительные сведения

### Что выбрать: Партиционирование или Шардирование?

* **Партиционирование** — это тактика оптимизации **внутри одного сервера**. Выбирайте его, когда:
  * Самые большие таблицы помещаются на один сервер, но запросы к ним становятся медленными.
  * Нужно ускорить обслуживание (архивацию старых данных, `VACUUM`).
* **Шардирование** — это стратегия масштабирования **на несколько серверов**. Выбирайте его, когда:
  * Объем данных превышает емкость одного сервера.
  * Нагрузка на запись (write) настолько высока, что один сервер не справляется.

**Миграции при масштабировании:** Переход от партиционирования к шардированию требует тщательного планирования миграций схемы. Подробнее в **[Миграции схем](./schema_migrations.md)**.
