# Масштабирование PostgreSQL

## Определения

- **Вертикальное масштабирование (Scale-Up)**: Увеличение мощности текущего сервера (CPU, RAM, дисковая подсистема). Самый простой путь, ограниченный физическим пределом "железа" и стоимостью.
- **Горизонтальное масштабирование (Scale-Out)**: Распределение данных и нагрузки между несколькими независимыми серверами.
- **Партиционирование (Partitioning)**: Разделение одной большой логической таблицы на несколько физических частей (партиций) внутри одного экземпляра СУБД.
- **Шардирование (Sharding)**: Распределение партиций одной таблицы по разным физическим серверам (узлам). Теоретические основы описаны в **[Шардирование](../../Concepts/sharding.md)**.

## Базовые концепции

Масштабирование в PostgreSQL реализуется тремя основными стратегиями в зависимости от типа нагрузки:

### Масштабирование чтения (Read Scaling)

Самый простой и эффективный способ снизить нагрузку на основной сервер (мастер). Реализуется через **[Репликацию](./replication.md)**.

- Запросы на запись (INSERT, UPDATE, DELETE) идут на мастер.
- Запросы на чтение (SELECT) распределяются между одной или несколькими репликами (Hot Standby).

### Декларативное партиционирование

Встроенный механизм PostgreSQL для разделения данных. Позволяет ускорить запросы за счет исключения ненужных партиций (Partition Pruning) и упростить обслуживание (удаление старых данных через `DROP TABLE`).

### Шардирование через расширения

Поскольку в стандартном PostgreSQL нет встроенной поддержки распределенных таблиц на нескольких узлах, используются специализированные решения (Citus, Greenplum), которые управляют распределением шардов и координацией запросов.

## Практические сценарии

### 1. Декларативное партиционирование (внутри одного узла)

PostgreSQL поддерживает три метода распределения данных по партициям.

**Партиционирование по диапазону (Range):**
Обычно используется для временных рядов (логи, транзакции по дате).

```sql
CREATE TABLE orders (
    order_id int,
    order_date date not null
) PARTITION BY RANGE (order_date);

CREATE TABLE orders_2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
```

**Партиционирование по списку (List):**
Для разделения по категориям (например, по регионам или статусам).

```sql
CREATE TABLE customers (
    id int,
    region text
) PARTITION BY LIST (region);

CREATE TABLE customers_europe PARTITION OF customers
    FOR VALUES IN ('EU', 'UK');
```

**Партиционирование по хешу (Hash):**
Для равномерного распределения данных, когда нет явного критерия диапазона или списка.

```sql
CREATE TABLE users (
    id int
) PARTITION BY HASH (id);

CREATE TABLE users_p0 PARTITION OF users FOR VALUES WITH (MODULUS 4, REMAINDER 0);
```

### 2. Масштабирование записи через Citus

**[Citus](../../citus.md)** — расширение, превращающее PostgreSQL в распределенную базу данных с архитектурой «Координатор — Воркеры».

Подробное описание архитектуры, типов таблиц и специфики работы с индексами в распределенной среде приведено в основном файле: **[Citus — распределенный PostgreSQL](../../citus.md)**.

### 3. Выбор стратегии: Partitioning vs Sharding

| Критерий | Партиционирование | Шардирование (Citus) |
| :--- | :--- | :--- |
| **Локация данных** | Один сервер | Несколько серверов |
| **Цель** | Ускорение чтение/обслуживания | Масштабирование записи и объема |
| **Сложность** | Низкая (встроено) | Высокая (требуется расширение) |
| **Предел** | Ресурсы одного сервера | Практически неограниченно |

## Дополнительная информация

### Ограничения масштабирования PostgreSQL

1. **Единая точка записи**: В стандартной репликации только один мастер может принимать запись.
2. **Сложность ре-шардирования**: Перераспределение данных между узлами в Citus или Greenplum — тяжелая операция, требующая планирования.
3. **Аналитические запросы (OLAP)**: Для обработки петабайт данных с тяжелыми JOIN'ами стандартный PostgreSQL может быть неэффективен из-за отсутствия MPP-архитектуры.

### Аналитические альтернативы (OLAP)

Если горизонтальное масштабирование PostgreSQL становится слишком сложным или дорогим для аналитики, рассматриваются:

- **[ClickHouse](../../clickhouse.md)**: Колоночная СУБД для сверхбыстрой аналитики.
- **[Greenplum](../../greenplum.md)**: Массивно-параллельная система (MPP) на базе PostgreSQL.
- **[TimescaleDB](../../timescaledb.md)**: Расширение для временных рядов с автоматическим управлением партициями.
