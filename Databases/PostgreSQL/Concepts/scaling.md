# Масштабирование PostgreSQL

Когда производительности одного сервера PostgreSQL перестает хватать, необходимо применять стратегии масштабирования.

## Вертикальное и горизонтальное масштабирование

- **Вертикальное масштабирование (Scale-Up):** Увеличение ресурсов на существующем сервере (CPU, RAM, более быстрые диски). Этот подход прост в реализации, но имеет физические и экономические пределы.
- **Горизонтальное масштабирование (Scale-Out):** Распределение данных и нагрузки на несколько серверов. Этот подход более сложен, но потенциально обеспечивает неограниченную масштабируемость.

## Партиционирование (Partitioning)

Партиционирование — это основной встроенный в PostgreSQL механизм для горизонтального масштабирования в пределах одного сервера. Он позволяет разбить одну большую логическую таблицу на несколько меньших физических таблиц (партиций).

**Преимущества партиционирования:**
- **Ускорение запросов:** Планировщик запросов может отсекать (partition pruning) те партиции, которые заведомо не содержат нужных данных, сканируя только релевантное подмножество.
- **Ускорение обслуживания:** Операции, такие как `VACUUM` или перестроение индексов, могут выполняться на отдельных партициях, не затрагивая всю таблицу.
- **Уменьшение размера индексов:** Индексы создаются для каждой партиции отдельно, они меньше по размеру и работа с ними происходит быстрее.
- **Параллельное выполнение:** Запросы, затрагивающие несколько партиций, могут выполняться параллельно.

### Встроенные методы партиционирования

1.  **По диапазону (Range Partitioning):** Данные распределяются по партициям на основе диапазона значений ключевого столбца. Идеально подходит для временных рядов (например, партиционирование по дате).

    ```sql
    CREATE TABLE orders (
        order_id INT,
        order_date DATE,
        ...
    ) PARTITION BY RANGE (order_date);

    CREATE TABLE orders_2023 PARTITION OF orders
        FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');
    ```

2.  **По списку (List Partitioning):** Данные распределяются на основе принадлежности значения ключевого столбца к определенному списку. Подходит для разделения по категориям, регионам и т.д.

    ```sql
    CREATE TABLE customers (
        customer_id INT,
        region_code INT,
        ...
    ) PARTITION BY LIST (region_code);

    CREATE TABLE customers_europe PARTITION OF customers
        FOR VALUES IN (1, 2, 3);
    ```

3.  **По хешу (Hash Partitioning):** Данные распределяются по партициям на основе хеш-значения ключевого столбца. Используется для равномерного распределения данных, когда нет очевидного ключа для разделения по диапазону или списку.

    ```sql
    CREATE TABLE users (
        user_id INT,
        username TEXT,
        ...
    ) PARTITION BY HASH (user_id);

    -- Создание нескольких партиций для равномерного распределения
    CREATE TABLE users_part_0 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 0);
    CREATE TABLE users_part_1 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 1);
    CREATE TABLE users_part_2 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 2);
    CREATE TABLE users_part_3 PARTITION OF users
        FOR VALUES WITH (MODULUS 4, REMAINDER 3);
    ```

## Шардирование (Sharding)

Шардирование — это следующий шаг после партиционирования, который подразумевает физическое распределение данных (шардов) по разным серверам.

В отличие от партиционирования, **в "чистом" PostgreSQL нет встроенной поддержки шардирования**. Для его реализации требуются сторонние расширения или специализированные форки PostgreSQL.

Большинство таких решений работают по одному из двух принципов:
- **Архитектура с координатором:** Один узел (координатор или менеджер) принимает запросы, знает, на каких узлах-воркерах лежат нужные данные, распределяет по ним подзапросы и собирает результат. Пример: **Citus**.
- **"Shared-nothing" архитектура:** Каждый узел в кластере является независимым и хранит свою часть данных. Узлы взаимодействуют друг с другом напрямую для выполнения распределенных запросов. Пример: **Greenplum**.

## Масштабирование чтения с помощью репликации

Помимо обеспечения высокой доступности, репликация является ключевым методом для **масштабирования нагрузки на чтение (read scaling)**. Запросы на чтение (`SELECT`) могут быть распределены между несколькими репликами, что значительно снижает нагрузку на основной сервер (мастер), который концентрируется на обработке операций записи.

Подробно механизмы физической и логической репликации описаны в заметке **[Типы репликации в PostgreSQL](./replication.md)**.

**Важно:** Масштабирование чтения с помощью репликации достигается ценой увеличения задержек при записи. Мастер-серверу необходимо не только записать данные локально, но и дождаться их отправки и применения на репликах, что может замедлить операции `INSERT`, `UPDATE` и `DELETE`.
