# Масштабирование PostgreSQL

## Определения

- **Вертикальное масштабирование (Scale-Up)**: Увеличение вычислительных мощностей одного сервера (CPU, RAM, пропускная способность дисковой подсистемы). Основное ограничение — физический предел оборудования и экспоненциальный рост стоимости.
- **Горизонтальное масштабирование (Scale-Out)**: Распределение нагрузки и данных между несколькими независимыми узлами. Требует механизмов синхронизации и балансировки.
- **Партиционирование (Partitioning)**: Логическое разделение одной большой таблицы на несколько физических сегментов (партиций) внутри одного инстанса. Оптимизирует производительность запросов и обслуживание (Maintenance).
- **Шардирование (Sharding)**: Распределение данных по разным физическим серверам (узлам). Теоретический базис описан в разделе **[Шардирование](../../Concepts/sharding.md)**.
- **Логическая репликация**: Механизм передачи изменений на уровне отдельных строк и таблиц, позволяющий строить гибкие топологии масштабирования.

## Базовые концепции

Стратегия масштабирования выбирается исходя из типа нагрузки: чтение (Read-heavy) или запись (Write-heavy).

### Масштабирование чтения (Read Scaling)

Реализуется через создание **[Реплик](./replication.md)** (Standby).

1.  **Физическая репликация**: Потоковая передача WAL. Реплики являются точными копиями мастера (Hot Standby).
2.  **Балансировка нагрузки (Клиентская, PG 16+)**:
    Параметр `load_balance_hosts=random` позволяет клиенту выбирать случайный узел из списка без внешнего балансировщика.
    ```ini
    # Строка подключения (connection string)
    postgresql://user:pass@host1,host2,host3/db?load_balance_hosts=random&target_session_attrs=read-only
    ```
3.  **Балансировка через Proxy**: Применение HAProxy или специализированных решений (например, балансировщики в облаках).
4.  **Пул соединений**: Использование **PgBouncer** или **Odyssey** обязательно для управления тысячами соединений. Подробнее: **[Настройка PgBouncer](../Operations/pgbouncer_setup.md)**.

### Масштабирование записи (Write Scaling)

Наиболее сложная задача, требующая изменения архитектуры данных для распределения нагрузки на запись.

1.  **Декларативное партиционирование**: Снижает нагрузку на индексы и упрощает `VACUUM` внутри одного узла.
2.  **Шардирование через расширения (Citus)**: Позволяет прозрачно распределять данные по кластеру серверов.
3.  **Ручное шардирование (FDW)**: Использование `postgres_fdw` для связи нескольких независимых инстансов PostgreSQL.
4.  **Масштабируемость WAL (PG 17)**: Улучшенная обработка логов транзакций при высокой конкуренции.

## Практические сценарии

### 1. Декларативное партиционирование

Начиная с PostgreSQL 11, партиционирование стало зрелым инструментом.

**Ключевые возможности (PG 16/17):**
- **Partition Pruning**: Оптимизатор исключает ненужные партиции. В PG 16 значительно ускорен поиск в LIST-партициях.
- **Поддержка ограничений (PG 17)**: Поддержка `IDENTITY` колонок и `EXCLUSION` ограничений.
- **Maintenance**: Быстрое удаление старых данных через `DETACH PARTITION` и `DROP TABLE`.

```sql
-- Пример: Партиционирование по дате (Range)
CREATE TABLE orders (
    id bigserial,
    order_date timestamptz not null,
    customer_id int,
    amount numeric,
    PRIMARY KEY (id, order_date)
) PARTITION BY RANGE (order_date);

-- Создание партиции
CREATE TABLE orders_2024_q1 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2024-04-01');
```

### 2. Ручное шардирование через Foreign Data Wrappers (FDW)

Метод "шардирования для бедных", встроенный в ядро. Позволяет обращаться к таблицам на другом сервере как к локальным.

**Архитектура "Partitioning + FDW":**
Наиболее продвинутый способ нативного шардирования — создание головной таблицы с декларативным партиционированием, где каждая партиция является `FOREIGN TABLE`, указывающей на свой узел-воркер.
- **Partition Pruning:** Планировщик автоматически отсекает обращения к узлам-воркерам, чьи данные не попадают под условия `WHERE`.
- **Параллельное сканирование:** С PG 14+ запросы к нескольким внешним шардам могут выполняться асинхронно (`async_capable`).

```sql
-- На узле-координаторе:
CREATE EXTENSION postgres_fdw;
CREATE SERVER worker1_server FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host '10.0.0.5', dbname 'worker_db');
CREATE USER MAPPING FOR current_user SERVER worker1_server OPTIONS (user 'remote_user', password 'remote_pass');

-- Создание внешней таблицы-партиции
CREATE FOREIGN TABLE orders_sh1 PARTITION OF orders
    FOR VALUES WITH (MODULUS 4, REMAINDER 0)
    SERVER worker1_server OPTIONS (table_name 'orders_local');

-- В PG 17 улучшена передача (pushdown) подзапросов EXISTS и IN на удаленные серверы.
```

### 3. Распределенный PostgreSQL с Citus

**[Citus](../../citus.md)** — расширение, превращающее PostgreSQL в распределенную СУБД (MPP).

- **Распределенные таблицы**: Данные режутся на шарды и раскладываются по воркерам.
  ```sql
  SELECT create_distributed_table('orders', 'customer_id');
  ```
- **Справочные таблицы (Reference Tables)**: Копируются на все узлы для быстрыx `JOIN` с распределенными таблицами.
  ```sql
  SELECT create_reference_table('products');
  ```

### 4. Новые возможности PG 17 для масштабирования

#### pg_createsubscriber
Утилита для быстрого превращения физической реплики в логическую, упрощая миграции и создание новых узлов без долгого простоя.
```bash
pg_createsubscriber -d "host=master_node dbname=mydb" -s "host=standby_node dbname=mydb" -p 5432 -D /var/lib/postgresql/data
```

#### Синхронизация слотов репликации
Позволяет логическим подписчикам бесшовно переключаться на новую реплику при Failover. Это критично для масштабирования логической репликации в высокодоступных средах.
```sql
-- Настройка в postgresql.conf на Primary и Standby
# sync_replication_slots = on
```

#### Инкрементальные бэкапы
Нативная поддержка инкрементального резервного копирования в PG 17 на основе WAL-суммирования. Это снижает нагрузку на сеть и диски при бэкапе терабайтных баз.
```bash
# Создание инкрементального бэкапа относительно полного
pg_basebackup -D /path/to/backup --incremental=/path/to/full_backup_manifest
```

## Обслуживание при масштабировании (Maintenance)

1.  **Новый механизм VACUUM (PG 17)**: Использует структуру **TidStore**, которая потребляет до 20 раз меньше памяти (RAM). Это предотвращает деградацию производительности и "раздувание" (bloat) на очень больших таблицах при интенсивном масштабировании записи.
2.  **Streaming I/O**: Ускоряет последовательное сканирование данных и работу `ANALYZE`, что критично для поддержания актуальной статистики в больших кластерах.
3.  **Роль MAINTAIN**: В PG 17 введена роль `MAINTAIN`, позволяющая делегировать задачи по обслуживанию (VACUUM, REINDEX, ANALYZE) без предоставления прав суперпользователя.

## Дополнительная информация

### Когда масштабирование может навредить

- **Overhead на планирование**: При количестве партиций > 1000 время планирования запроса может начать существенно расти.
- **Cross-shard запросы**: Если запрос требует данных с многих шардов (Fan-out), производительность резко падает. Правильный выбор **ключа шардирования** — критический фактор.

### Сравнение технологий

| Технология | Тип | Основной кейс |
| :--- | :--- | :--- |
| **Native Partitioning** | Встроенное | Оптимизация внутри одного сервера, очистка данных. |
| **Citus** | Расширение | Высокая нагрузка на запись (SaaS, аналитика). |
| **Greenplum** | Fork (MPP) | Тяжелая аналитика, хранилища данных (DWH). |
| **TimescaleDB** | Расширение | Временные ряды (IoT, метрики) с авто-партиционированием. |
