# Масштабирование PostgreSQL

## Определения

- **Вертикальное масштабирование (Scale-Up)**: Увеличение ресурсов текущего сервера (CPU, RAM, диск). Простой, но дорогой путь, ограниченный физическими возможностями оборудования.
- **Горизонтальное масштабирование (Scale-Out)**: Распределение нагрузки и данных между несколькими серверами.
- **Партиционирование (Partitioning)**: Разделение одной большой логической таблицы на несколько физических частей (партиций) внутри одного экземпляра СУБД.
- **Шардирование (Sharding)**: Распределение частей данных по разным физическим серверам (узлам). Теоретические основы описаны в **[Шардировании](../../Concepts/sharding.md)**.
- **Логическая репликация**: Механизм передачи изменений данных на уровне отдельных таблиц или строк, позволяющий масштабировать специфические рабочие нагрузки или интегрировать данные между микросервисами.

## Базовые концепции

Стратегия масштабирования выбирается исходя из типа нагрузки: чтение (Read-heavy) или запись (Write-heavy).

### Масштабирование чтения (Read Scaling)

Самый распространенный сценарий. Реализуется через создание **[Реплик](./replication.md)** (Hot Standby).

1.  **Физическая репликация**: Полная копия мастера. Реплики доступны только для чтения.
2.  **Балансировка**: Для распределения запросов между репликами используются балансировщики (HAProxy, балансировщики облачных провайдеров) или умные драйверы приложений.
3.  **Пул соединений**: Использование **PgBouncer** или **Odyssey** обязательно для эффективного управления тысячами соединений при горизонтальном масштабировании.

### Масштабирование записи (Write Scaling)

Наиболее сложная задача для реляционных СУБД, так как стандартный PostgreSQL поддерживает только одного активного мастера на запись (Single Master).

1.  **Декларативное партиционирование**: Снижает нагрузку на индексы и упрощает `VACUUM` внутри одного узла, подготавливая базу к шардированию.
2.  **Шардирование через расширения (Citus)**: Позволяет прозрачно распределять данные по кластеру серверов.
3.  **Ручное шардирование (FDW)**: Использование `postgres_fdw` для связи нескольких независимых инстансов PostgreSQL.
4.  **Разделение микросервисов**: Вынос части таблиц в отдельные базы данных с использованием логической репликации для синхронизации общих справочников.

## Практические сценарии

### 1. Современное декларативное партиционирование

Начиная с PostgreSQL 11, партиционирование стало зрелым инструментом.

**Ключевые возможности:**
- **Partition Pruning**: Оптимизатор исключает ненужные партиции на этапе планирования и выполнения запроса.
- **Индексы и ключи**: Поддержка уникальных индексов (если ключ партиционирования входит в индекс) и внешних ключей.
- **Maintenance**: Быстрое удаление старых данных через `DETACH PARTITION` и `DROP TABLE`.

```sql
-- Пример: Партиционирование по дате (Range)
CREATE TABLE logs (
    id bigserial,
    log_date timestamptz not null,
    message text
) PARTITION BY RANGE (log_date);

-- Создание партиции
CREATE TABLE logs_2024_01 PARTITION OF logs
    FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
```

### 2. Ручное шардирование через Foreign Data Wrappers (FDW)

Метод "шардирования для бедных", встроенный в ядро. Позволяет обращаться к таблицам на другом сервере как к локальным.

1. На узле-координаторе создается внешняя таблица (`FOREIGN TABLE`), указывающая на узел-воркер.
2. Логика распределения данных реализуется через `VIEW` или триггеры на координаторе.
3. *Ограничение*: Низкая производительность при сложных `JOIN` между узлами и отсутствие распределенных транзакций "из коробки".

### 3. Распределенный PostgreSQL с Citus

**[Citus](../../citus.md)** — стандарт де-факто для горизонтального масштабирования PostgreSQL.

- **Распределенные таблицы**: Данные режутся на шарды и раскладываются по воркерам.
- **Справочные таблицы (Reference Tables)**: Копируются на все узлы для быстрыx `JOIN` с распределенными таблицами.
- **Прозрачность**: Приложение работает с координатором как с обычной БД.

## Дополнительная информация

### Когда масштабирование вредно

- **Маленькие данные**: На данных объемом < 100 ГБ партиционирование может замедлить работу из-за усложнения планов запросов.
- **Неправильный ключ шардирования**: Ошибочный выбор ключа (например, шардирование по `id` при частых запросах по `city_id`) приведет к тому, что каждый запрос будет обходить все узлы кластера (Fan-out query).
- **Слишком много партиций**: При количестве партиций > 1000–2000 время планирования запроса (Planning time) начинает существенно расти.

### Сравнение решений

| Решение | Тип | Основной кейс |
| :--- | :--- | :--- |
| **Native Partitioning** | Встроенное | Оптимизация внутри одного сервера, очистка старых данных. |
| **Citus** | Расширение | Высокая нагрузка на запись (SaaS, аналитика в реальном времени). |
| **Greenplum** | Fork (MPP) | Тяжелая аналитика, хранилища данных (DWH). |
| **TimescaleDB** | Расширение | Временные ряды (IoT, метрики) с автоматическим созданием партиций. |
