# Оптимизация PL/pgSQL: Функции и триггеры

**Актуально для:** PostgreSQL 13–18

Методы повышения производительности серверного процедурного кода в PostgreSQL, минимизация накладных расходов на выполнение и лучшие практики написания функций и триггеров на языке PL/pgSQL. Файл ориентирован на разработку и эксплуатацию (DevOps/SRE): диагностика «скрытых» тормозов, мониторинг и безопасное развертывание серверного кода.

## Определения

**PL/pgSQL (Procedural Language/PostgreSQL SQL Procedural Language)** — загружаемый процедурный язык, работающий внутри серверного процесса PostgreSQL. Объединяет SQL с управляющими структурами (циклы, условия, обработка исключений).

*   **Переключение контекста (Context Switching):** Передача управления и данных между SQL-исполнителем ядра (C) и интерпретатором PL/pgSQL при каждом вызове функции или выполнении SQL-оператора из функции.
*   **Волатильность (Volatility):** Атрибут функции (`IMMUTABLE`/`STABLE`/`VOLATILE`), определяющий, насколько стабилен результат при одинаковых входных данных. Ключевой параметр для оптимизаций планировщика.
*   **Инлайнинг (Inlining):** Подстановка тела функции непосредственно в запрос-plan вместо вызова функции как отдельного объекта. Работает только для функций `LANGUAGE sql`; PL/pgSQL-функции не инлайнятся ни в одной из поддерживаемых версий.
*   **Параллельная безопасность (Parallel Safety):** Атрибут (`PARALLEL UNSAFE`/`RESTRICTED`/`SAFE`), указывающий, может ли функция выполняться в параллельных worker-процессах.
*   **COST и ROWS:** Подсказки планировщику: `COST` — относительная стоимость вызова (в единицах `cpu_operator_cost`, по умолчанию 100 для не-C языков), `ROWS` — ожидаемое число строк для set-returning функции (по умолчанию 1000).
*   **Generic/Custom plan:** Два режима кэширования плана подготовленного оператора: custom-план строится под конкретные значения параметров, generic — один раз и переиспользуется для всех значений.
*   **Подтранзакция (Subtransaction):** Изолированная точка сохранения, создаваемая каждым блоком `BEGIN ... EXCEPTION` в PL/pgSQL; имеет накладные расходы на старт и коммит.

## Базовые концепции

### Как работает PL/pgSQL под капотом

При первом вызове функции в сессии интерпретатор разбирает её текст и строит внутреннее бинарное дерево инструкций. SQL-выражения и операторы внутри тела **не** компилируются сразу: каждый из них при первом выполнении превращается в подготовленный оператор (через `SPI_prepare`), а дальнейшие вызовы переиспользуют его. Из этого следуют эксплуатационно важные свойства:

*   Редко посещаемые ветки кода не платят за разбор никогда посещенных операторов — но и ошибки в них не обнаруживаются до реального выполнения (тривиальные синтаксические ошибки ловятся при создании функции, семантические — нет).
*   Кэш операторов ведется **для каждой комбинации (триггерная функция, таблица)**: одна функция на нескольких таблицах не путает типы столбцов между таблицами.
*   Полиморфные функции (`anyelement` и т.п.) кэшируют операторы отдельно для каждой комбинации фактических типов аргументов.
*   Поля переменных типа `record` должны сохранять типы от вызова к вызову — тип определяется при первом выполнении выражения. Для динамических типов используйте `EXECUTE`.

### Переключение контекста

При вызове функции из SQL-запроса (или при выполнении оператора внутри функции) происходит сохранение состояния SQL-исполнителя, конвертация аргументов, выполнение тела и обратная конвертация. На вызовах в цикле по строкам (row-by-row) эти накладные расходы доминируют над полезной работой — основная причина, по которой PL/pgSQL-медленнее чистого SQL на больших наборах данных.

### Волатильность функции

Правильная разметка позволяет планировщику исключить лишние вычисления и строить лучшие планы (в том числе функциональные индексы — см. [Индексы](./indexes.md)).

| Категория | Гарантии (по документации) | Оптимизация планировщика |
| :--- | :--- | :--- |
| **VOLATILE** (по умолчанию) | Значение может меняться даже в рамках одного сканирования. **Любая функция с побочными эффектами обязана быть VOLATILE** (иначе вызовы могут быть оптимизированы прочь). | Вызывается для каждой строки; не подставляется в план; часто ограничивает параллельное выполнение. |
| **STABLE** | Не меняет БД; в рамках **одного сканирования таблицы** возвращает одинаковый результат для одинаковых аргументов. Подходит для функций, зависящих от чтения БД или параметров сессии (например, `current_timestamp`). | Один результат на сканирование. **Не подходит для AFTER-триггеров**, читающих строки, измененные текущей командой. |
| **IMMUTABLE** | Не меняет БД; результат зависит **только** от аргументов. | Вызов с константными аргументами подставляется на этапе планирования; допускается создавать **индексы по выражению**. |

Дополнительно: `LEAKPROOF` (только суперпользователь) — функция не выдаёт информации об аргументах, кроме возвращаемого значения; влияет на порядок условий в security-barrier views и RLS-политиках.

### Кэширование планов: custom и generic

PL/pgSQL использует механизм подготовленных операторов (SPI), поэтому правила те же, что для `PREPARE` (см. [Планировщик: математика и кэш планов](./planner_internals.md)):

*   Первые **пять** выполнений параметризованного оператора идут с custom-планом (строится под фактические значения). Затем строится generic-план и используется далее, если его оценочная стоимость не настолько выше средней custom-плана, чтобы повторное планирование оказалось выгоднее (поведение с PostgreSQL 12).
*   **Перекошенные данные (skewed data):** если план сильно зависит от значений параметров, generic-план может быть катастрофически хуже. Диагностика — `EXPLAIN EXECUTE func(...)`: generic-план содержит символы `$n`, custom — подставленные значения. Управление — `plan_cache_mode = force_custom_plan` (или `force_generic_plan`).
*   План автоматически перепланируется при DDL-изменениях объектов, обновлении статистики (`ANALYZE`) и при смене `search_path` между вызовами.

### Инлайнинг и выбор языка

Простые вычисления выгодно писать как `LANGUAGE sql` — такие функции планировщик может инлайнить в вызывающий запрос, а тело, заданное формой `BEGIN ATOMIC ... END`, парсится на этапе создания и отслеживает зависимости (работает `DROP ... CASCADE`). PL/pgSQL не инлайнится — её тело выполняется отдельным интерпретатором, поэтому для скалярных вычислений без управляющей логики `LANGUAGE sql` всегда быстрее.

### Параллельная безопасность

По умолчанию все функции `PARALLEL UNSAFE` — их присутствие в запросе заставляет планировщик строить последовательный план. Маркировка (см. CREATE FUNCTION):

*   `PARALLEL SAFE` — нет записи в БД, нет доступа к последовательностям, нет изменений настроек, нет сессионного состояния.
*   `PARALLEL RESTRICTED` — выполняется только в leader-процессе (доступ к временным таблицам, курсорам, подготовленным операторам, `setseed()` и т.п.).

Ошибочная маркировка `SAFE` для фактически `RESTRICTED`/`UNSAFE` функции приводит к ошибкам или неправильным ответам в параллельных запросах; при сомнениях оставляйте `UNSAFE`.

## Практические сценарии

### 1. Триггеры: условия WHEN и переходные таблицы

Триггеры — самый частый источник «скрытых» тормозов при `INSERT/UPDATE`.

**Условное выполнение (WHEN):** выносите проверки в заголовок триггера — интерпретатор не запускается вовсе, если условие ложно:

```sql
CREATE TRIGGER trg_audit_log
BEFORE UPDATE ON orders
FOR EACH ROW
WHEN (OLD.status IS DISTINCT FROM NEW.status) -- Выполнится только при реальной смене статуса
EXECUTE FUNCTION process_audit_log();
```

**Переходные таблицы (Transition Tables, PG 10+):** для триггеров уровня оператора (`FOR EACH STATEMENT`) доступны наборы всех измененных строк одним SQL-запросом вместо цикла по строкам:

```sql
CREATE TRIGGER trg_bulk_update
AFTER UPDATE ON products
REFERENCING OLD TABLE AS deleted_rows NEW TABLE AS inserted_rows
FOR EACH STATEMENT
EXECUTE FUNCTION sync_cache_bulk();
```

Переходные таблицы доступны **только** для statement-триггеров; для row-триггеров используйте `OLD`/`NEW`.

### 2. Подсказки планировщику: COST и ROWS

`COST` задается в единицах `cpu_operator_cost` (для set-returning функции — на каждую возвращенную строку), большее значение заставляет планировщик реже вызывать функцию и аккуратнее выбирать порядок JOIN-ов. `ROWS` корректирует оценку кардинальности (по умолчанию 1000 — частая причина плохих планов для функций, реально возвращающих очень мало или очень много строк):

```sql
CREATE OR REPLACE FUNCTION get_complex_report(user_id int)
RETURNS SETOF data_table AS $$
    ...
$$ LANGUAGE plpgsql STABLE
COST 10000 -- Подсказка: функция в 100 раз тяжелее стандартной (10000/100)
ROWS 50;   -- Подсказка: функция вернет примерно 50 строк, а не 1000 по умолчанию
```

### 3. Массивы и множества вместо циклов

PL/pgSQL неэффективно обрабатывает циклы по большим наборам данных. Всегда предпочитайте агрегацию в массивы и оператор `ANY`, а там, где возможно, — одно множество-выражение:

```sql
-- Плохо (многократные вызовы SELECT в цикле)
FOREACH id_val IN ARRAY input_ids LOOP
    SELECT price INTO temp_val FROM products WHERE id = id_val;
    ...
END LOOP;

-- Хорошо (один SELECT с фильтром по массиву)
SELECT array_agg(price) INTO prices_array
FROM products
WHERE id = ANY(input_ids);
```

### 4. Динамический SQL: format() и EXECUTE ... USING

Имена таблиц/столбцов нельзя параметризовать в статическом SQL — только через `EXECUTE`, что платит полный разбор и планирование на каждом выполнении. Сборку строки делайте через `format()`: `%I` экранирует идентификаторы, `%L` — литералы. **Значения** лучше передавать через `USING` — они подставляются как параметры, а не конкатенируются в строку (устойчиво к инъекциям и не засоряет кэш уникальными строками):

```sql
CREATE OR REPLACE FUNCTION archive_table(tbl_name text, cutoff timestamptz) RETURNS void AS $$
BEGIN
    EXECUTE format('INSERT INTO archive.%I SELECT * FROM public.%I WHERE created_at < $1',
                   tbl_name, tbl_name)
    USING cutoff;
END;
$$ LANGUAGE plpgsql;
```

Важно: каждая уникальная строка `EXECUTE` создает **новый** кэшированный подготовленный оператор в сессии — в длинных сессиях с множеством динамических вариантов это раздувает кэш (см. раздел «Диагностика»).

### 5. Безопасный SECURITY DEFINER

`SECURITY DEFINER` выполняет функцию с правами владельца — стандартный инструмент для выдачи ограниченных прав без grant на таблицы. Обязательный минимум безопасности (иначе любой может подменить объекты через `pg_temp`):

```sql
BEGIN;
CREATE FUNCTION check_password(uname text, pass text) RETURNS boolean AS $$
DECLARE passed boolean;
BEGIN
    SELECT (pwd = pass) INTO passed FROM admin.pwds WHERE username = uname;
    RETURN passed;
END;
$$ LANGUAGE plpgsql
    SECURITY DEFINER
    SET search_path = admin, pg_temp; -- доверенные схемы, pg_temp — последним
REVOKE ALL ON FUNCTION check_password(text, text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION check_password(text, text) TO admins;
COMMIT;
```

Правила: `pg_temp` обязательно в конце `search_path` (иначе временная таблица маскирует настоящую); `REVOKE ... FROM PUBLIC` + `GRANT` — в той же транзакции, чтобы не было окна доступа для всех; функция с `SET`-клаузой восстанавливает параметр при выходе (`SET LOCAL` внутри ограничивается функцией, обычный `SET` — нет). Реальный пример — функция `get_auth` в [настройке PgBouncer](../Operations/pgbouncer_setup.md).

### 6. Обработка ошибок, RAISE, ASSERT

Блок `BEGIN ... EXCEPTION` создает подтранзакцию: это надежный способ локальной восстановимости, но не бесплатный — не оборачивайте в `EXCEPTION` горячие циклы «на всякий случай». Для сообщений используйте `RAISE` (уровни `DEBUG`/`LOG`/`INFO`/`NOTICE`/`WARNING`/`EXCEPTION`), для деталей ошибки — `GET STACKED DIAGNOSTICS`.

```sql
BEGIN
    UPDATE orders SET status = 'paid' WHERE id = order_id;
    IF NOT FOUND THEN
        RAISE EXCEPTION 'order % not found', order_id
            USING ERRCODE = 'foreign_key_violation';
    END IF;
EXCEPTION
    WHEN OTHERS THEN
        GET STACKED DIAGNOSTICS v_detail = PG_EXCEPTION_DETAIL;
        RAISE WARNING 'update failed: % / %', SQLERRM, v_detail;
END;
```

`ASSERT condition [, message]` — проверка внутренних инвариантов (по умолчанию включена, `plpgsql.check_asserts = on`; это user-settable параметр). Сбой поднимает `ASSERT_FAILURE`. По документации, `ASSERT` — для обнаружения багов программы, а не для обычных ошибок ввода (те — через `RAISE`); `WHEN OTHERS` **не** перехватывает `ASSERT_FAILURE`.

### 7. Ловушки компиляции и кэширования

*   **Литерал `'now'`:** в `INSERT ... VALUES (logtxt, 'now')` парсер на этапе анализа превращает `'now'` в константу типа timestamp — и она остаётся неизменной на всё время сессии. Используйте функцию `now()` или `current_timestamp`.
*   **Конфликт имён переменной и столбца:** по умолчанию PL/pgSQL выдаёт ошибку при неоднозначности (`plpgsql.variable_conflict = error`, менять может только суперпользователь). Решения: переименовать переменную (конвенция `v_`/`p_`), квалифицировать ссылку (`src.foo` для столбца, `block.foo` для переменной через метку блока) либо `#variable_conflict use_variable` в начале тела функции.
*   **Подстановка переменных** работает только в `SELECT/INSERT/UPDATE/DELETE/MERGE` (и командах, их содержащих); для utility-операторов (`ALTER`, `COPY` и т.п.) нужен динамический `EXECUTE`.

### 8. Профилирование с plprofiler

`pg_stat_statements` и `pg_stat_activity` показывают только **внешний** вызов — PL/pgSQL «прячет» внутренние операторы. Расширение plprofiler (репозиторий `bigsql/plprofiler`, поддержка PG 14–18, пакеты PGDG: `plprofiler_18` / `postgresql-18-plprofiler`) собирает статистику через debug-instrumentation hooks и строит Flame Graph по wall-clock времени, проведенному в PL/pgSQL-коде:

```bash
# RHEL/Rocky/Alma/Fedora (PGDG):
dnf install plprofiler_18
# Debian/Ubuntu:
apt install postgresql-18-plprofiler
```

```bash
# postgresql.conf (требуется restart):
shared_preload_libraries = 'plprofiler'
```

```sql
CREATE EXTENSION plprofiler;
```

```bash
plprofiler run -d mydb --command "SELECT sales_report(2026, 9);" --output report.html
# → report.html: Flame Graph + топ-10 функций по self_time (total_time - children_time)
```

Статистика собирается per call stack (число вызовов, кумулятивное время, время в дочерних вызовах), per function и per statement. Объекты расширения создаются от роли `plprofiler`, что упрощает гранты.

## Диагностика и мониторинг

### Статистика по функциям

`pg_stat_user_functions` требует `track_functions` в `postgresql.conf`: для PL/pgSQL достаточно значения **`pl`** (значение `all` дополнительно покрывает SQL- и C-функции, но дороже по накладным расходам). Параметр reloadable (контекст `PGC_SUSET`: `ALTER SYSTEM` + `pg_reload_conf()` или `SET` суперпользователем; перезапуск не нужен), детали — в [Мониторинг хранимых объектов](./stored_objects_debugging.md):

```sql
SELECT funcname, calls,
       round(total_time::numeric / calls, 3) AS avg_total_ms,
       round(self_time::numeric / calls, 3)  AS avg_self_ms
FROM pg_stat_user_functions
WHERE calls > 0
ORDER BY total_time DESC;
-- → funcname   | calls | avg_total_ms | avg_self_ms
-- → calc_tax   | 48210 |       1.842  |      1.810    <-- почти всё время в самой функции
-- → get_rates  | 48210 |       0.021  |      0.004    <-- время в дочерних вызовах
```

`total_time` включает вложенные вызовы функций, `self_time` — только собственное время: разница между ними указывает, где искать «тяжелую» логику.

### Что видно извне

*   `auto_explain.log_nested_statements = on` — в лог попадают операторы **внутри** PL/pgSQL-функций (подробнее в [Планировщике](./planner_internals.md) и [Наблюдаемости](../Operations/observability.md)).
*   Блокировки и ожидания: функция, выполняющая DDL или долгий `UPDATE`, видна в `pg_stat_activity`/`pg_locks` как обычная сессия (методика — в [Конкурентном доступе и блокировках](./concurrency_and_locking.md)).
*   Кэш подготовленных операторов сессии: `pg_prepared_statements` показывает и клиентские `PREPARE`, и внутренние кэши PL/pgSQL. Чистка — `DEALLOCATE ALL` или `DISCARD PLANS` (только кэши планов; `DISCARD ALL` дополнительно сбрасывает временные таблицы, последовательности и advisory-локи, но не может выполняться внутри транзакции).

### Статический анализ и тесты (CI)

Ошибки в редких ветках PL/pgSQL обнаруживаются только при выполнении — поэтому в CI полезны:

*   **plpgsql_check** (`github.com/okbob/plpgsql_check`, PG 14–19) — линтер, проверяющий встроенные SQL-операторы семантически на этапе создания функции:

    ```sql
    CREATE EXTENSION plpgsql_check;
    SELECT * FROM plpgsql_check_function('my_function()', fatal_errors := false);
    -- → вывод найденных ошибок: отсутствующие столбцы, неиспользуемые переменные и т.п.
    ```

*   **pgTAP** (`pgtap.org`, репозиторий `theory/pgtap`) — фреймворк юнит-тестов, TAP-выход и xUnit-стиль:

    ```sql
    CREATE EXTENSION pgtap;
    CREATE OR REPLACE FUNCTION test_calc_tax() RETURNS SETOF TEXT LANGUAGE plpgsql AS $$
    BEGIN
        RETURN NEXT is(calc_tax(100), 20, 'tax 20% of 100');
    END;
    $$;
    SELECT * FROM test_calc_tax();
    ```

## Поиск и устранение неисправностей

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| **Высокий CPU при вызовах функции** | Циклы по строкам, многократные переключения контекста. | Перепишите логику на чистый SQL, используйте массивы/агрегаты; сравните с `LANGUAGE sql`-функцией. |
| **Планировщик выбирает плохой план (Seq Scan)** | Неверная волатильность функции в `WHERE` или generic-план при перекошенных данных. | Проверьте `VOLATILE` vs `STABLE/IMMUTABLE`; `EXPLAIN EXECUTE func(...)` ( `$n` = generic-план); `plan_cache_mode = force_custom_plan`. |
| **Ошибка только при реальном вызове** | Семантические ошибки в редких ветках не ловятся при `CREATE FUNCTION` (ленивая компиляция операторов). | `plpgsql_check_function()` в CI; покрытие тестами (pgTAP). |
| **Рост `pg_prepared_statements` в длинной сессии** | Динамический SQL: каждая уникальная строка `EXECUTE` — новый кэшированный оператор. | Параметризуйте значения через `USING`; `DEALLOCATE ALL` / `DISCARD PLANS`; переподключение сессии. |
| **Функция не параллелится** | `PARALLEL UNSAFE` (по умолчанию). | Если функция не пишет в БД и не использует сессионное состояние — `PARALLEL SAFE`; временные таблицы/курсоры — `RESTRICTED`. |
| **Ошибка «column ... is not a variable» / неоднозначность** | Конфликт имён переменной и столбца таблицы. | Переименование (`v_`/`p_`), квалификация (`src.col`, `block.var`) или `#variable_conflict`. |
| **SECURITY DEFINER: «permission denied» или доступ к чужим объектам** | `search_path` ищет `pg_temp` первым — подмена объектов. | `SET search_path = admin, pg_temp` (pg_temp последним); `REVOKE`/`GRANT` в одной транзакции с созданием. |
| **Функция «зависает» при применении миграции** | `CREATE OR REPLACE FUNCTION` ждёт сессий, работающих со старой версией (очередь AccessExclusiveLock). | Проверьте `pg_locks`/`pg_stat_activity`; применяйте в окне миграций (см. [Схема-миграции](./schema_migrations.md)). |
| **`pg_stat_user_functions` пуста** | `track_functions = none`. | `track_functions = pl` (для PL/pgSQL) + reload конфига. |

## Лучшие практики

1.  **SQL превыше всего:** если задачу решает один SQL-запрос (CTE, оконные функции, множества) — решайте на SQL; для скалярных вычислений — `LANGUAGE sql` (инлайнинг).
2.  **Минимизация вложенности:** избегайте вызовов PL/pgSQL-функций из других PL/pgSQL-функций в глубоких циклах.
3.  **STRICT-функции:** `RETURNS NULL ON NULL INPUT` (`STRICT`) — PostgreSQL не вызывает функцию при NULL-аргументе.
4.  **Аргументы через `%TYPE`:** `arg table.column%TYPE` снижает хрупкость при изменении схемы.
5.  **Осознанное развертывание:** `CREATE OR REPLACE FUNCTION` меняет тело, но **не** сигнатуру, не тип возврата, владельца и права; смена типов — `DROP` + `CREATE` (ломает зависимые views/триггеры). Функции — часть миграций (см. [Схема-миграции](./schema_migrations.md)); `pg_dump` сохраняет их определения.
6.  **Перегрузка с умом:** функции с одинаковым именем, но разными типами аргументов — разные функции; при значениях по умолчанию возможна неоднозначность вызова (`foo(int)` vs `foo(int, int DEFAULT 42)`).
7.  **Очистка после экспериментов:** `DROP FUNCTION [IF EXISTS] name(args);`, `RESET track_functions`, `DROP EXTENSION plprofiler;`, `DISCARD PLANS` / `DEALLOCATE ALL` для сессии.

## Вопросы на собеседованиях

1.  Почему PL/pgSQL-функция медленнее эквивалентного SQL-запроса на большом наборе данных? (переключение контекста, row-by-row исполнение)
2.  Чем отличаются custom и generic планы в PL/pgSQL и когда используется каждый? (правило пяти выполнений, `plan_cache_mode`, `EXPLAIN EXECUTE`)
3.  Почему `IMMUTABLE`-функция в `WHERE` может дать неправильный результат, если она читает таблицу? (подстановка на этапе планирования; чтение БД — только `STABLE`)
4.  Как безопасно написать `SECURITY DEFINER`-функцию? (`SET search_path` с `pg_temp` последним, `REVOKE`/`GRANT` в транзакции)
5.  Что происходит с кэшем операторов, когда триггерная функция используется на нескольких таблицах? (отдельный кэш на пару функция+таблица)
6.  Почему ошибка в редкой ветке функции не обнаруживается при `CREATE FUNCTION`? (ленивая компиляция операторов при первом выполнении; как ловить — plpgsql_check/pgTAP)
7.  Как профилировать вложенные вызовы PL/pgSQL, если `pg_stat_statements` показывает только внешний вызов? (plprofiler, Flame Graph по wall-clock)
8.  Чем `zero_damaged_pages`-style «обнуление» тут не поможет — то есть: почему `EXCEPTION WHEN OTHERS` в горячем цикле — плохая практика? (подтранзакции имеют стоимость; ловить следует конкретные условия)
