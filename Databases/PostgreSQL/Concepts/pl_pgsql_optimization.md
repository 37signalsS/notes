# Оптимизация PL/pgSQL: Функции и триггеры

В данном документе рассматриваются методы повышения производительности серверного процедурного кода в PostgreSQL, минимизация накладных расходов на выполнение и лучшие практики написания расширений на языке PL/pgSQL.

## Определения

**PL/pgSQL (Procedural Language/PostgreSQL)** — расширяемый процедурный язык программирования, работающий внутри ядра PostgreSQL. Он объединяет мощь SQL с управляющими структурами (циклы, условия, обработка исключений).

*   **Переключение контекста (Context Switching):** Ресурсозатратный процесс передачи управления и данных между основным SQL-движком (написанным на C) и интерпретатором PL/pgSQL.
*   **Волатильность (Volatility):** Характеристика функции, определяющая, насколько стабилен ее результат при одинаковых входных данных. Ключевой параметр для кэширования планов.
*   **Инлайнинг (Inlining):** Способность планировщика "встраивать" тело функции непосредственно в основной SQL-запрос, избегая вызова функции как отдельного объекта (доступно в основном для простых SQL-функций).
*   **Параллельная безопасность (Parallel Safety):** Атрибут, указывающий, может ли функция безопасно выполняться в параллельных рабочих процессах (worker processes).
*   **Стоимость (COST):** Числовой коэффициент, подсказывающий планировщику относительную нагрузку функции (по умолчанию 100 для PL/pgSQL).

## Базовые концепции

### Механизм переключения контекста

PostgreSQL использует два разных исполнителя для SQL и PL/pgSQL. При каждом вызове функции внутри запроса:
1.  Текущее состояние SQL-исполнителя сохраняется.
2.  Выделяется память под стек интерпретатора PL/pgSQL.
3.  Аргументы конвертируются во внутренние типы PL/pgSQL.
4.  Выполняется тело функции.
5.  Результат конвертируется обратно, стек очищается, SQL-движок возобновляет работу.

**Нагрузка:** На больших выборках (10^6+ строк) время переключения контекста может занимать до 60-80% всего времени выполнения запроса.

### Категории волатильности

Правильная разметка функции позволяет планировщику исключить лишние вычисления.

| Категория | Гарантии | Оптимизация планировщика |
| :--- | :--- | :--- |
| **VOLATILE** | Нет (по умолчанию). Результат может меняться всегда. | Выполняется для каждой строки. Параллельное выполнение часто ограничено. |
| **STABLE** | Результат неизменен в рамках **одного снимка данных** (транзакции). | Вызовы с одинаковыми аргументами в одном запросе могут быть заменены одним значением. |
| **IMMUTABLE** | Результат зависит **только** от аргументов и никогда не меняется. | Вычисляется один раз на этапе планирования. Позволяет создавать **индексы по выражению**. |

### Кэширование планов запросов
Интерпретатор PL/pgSQL автоматически кэширует планы выполнения всех SQL-запросов, находящихся внутри функции, после первого вызова в рамках сессии. Это экономит время на парсинг и планирование, но может быть неэффективно, если данные сильно перекошены (skewed data).

## Практические сценарии

### 1. Оптимизация триггеров через условия и переходные таблицы

Триггеры — самый частый источник "скрытых" тормозов при `INSERT/UPDATE`.

**Условное выполнение (WHEN):**
Выносите базовые проверки из кода функции в заголовок триггера. Это предотвратит запуск интерпретатора, если условия не мета.
```sql
CREATE TRIGGER trg_audit_log
BEFORE UPDATE ON orders
FOR EACH ROW
WHEN (OLD.status IS DISTINCT FROM NEW.status) -- Выполнится только при реальной смене статуса
EXECUTE FUNCTION process_audit_log();
```

**Переходные таблицы (Transition Tables) (PG 10+):**
Для триггеров `AFTER STATEMENT` можно использовать `REFERENCING NEW TABLE AS ...`, что позволяет обработать всю пачку измененных строк одним SQL-запросом вместо цикла по строкам.
```sql
CREATE TRIGGER trg_bulk_update
AFTER UPDATE ON products
REFERENCING OLD TABLE AS deleted_rows NEW TABLE AS inserted_rows
FOR EACH STATEMENT
EXECUTE FUNCTION sync_cache_bulk();
```

### 2. Подсказки планировщику: COST и ROWS

Если функция выполняет тяжелые вычисления или сложные запросы, планировщик должен знать об этом, чтобы правильно выбрать порядок JOIN-ов.

```sql
CREATE OR REPLACE FUNCTION get_complex_report(user_id int)
RETURNS SETOF data_table AS $$
    ...
$$ LANGUAGE plpgsql STABLE
COST 10000 -- Подсказка: функция в 100 раз тяжелее стандартной
ROWS 50;    -- Подсказка: функция вернет примерно 50 строк
```

### 3. Использование массивов вместо циклов

PL/pgSQL неэффективно обрабатывает циклы по большим наборам данных. Всегда предпочитайте агрегацию в массивы и оператор `ANY`.

```sql
-- Плохо (многократные вызовы SELECT в цикле)
FOREACH id_val IN ARRAY input_ids LOOP
    SELECT price INTO temp_val FROM products WHERE id = id_val;
    ...
END LOOP;

-- Хорошо (один SELECT с фильтром по массиву)
SELECT array_agg(price) INTO prices_array 
FROM products 
WHERE id = ANY(input_ids);
```

### 4. Безопасный динамический SQL

Использование `EXECUTE` необходимо для динамических имен таблиц, но опасно с точки зрения SQL-инъекций и накладных расходов. Используйте `format()` для безопасной сборки строк.

```sql
CREATE OR REPLACE FUNCTION archive_table(tbl_name text) RETURNS void AS $$
BEGIN
    -- %I безопасно экранирует идентификаторы (имена таблиц/колонок)
    -- %L безопасно экранирует литералы (значения)
    EXECUTE format('INSERT INTO archive.%I SELECT * FROM public.%I WHERE created_at < %L', 
                   tbl_name, tbl_name, now() - interval '1 month');
END;
$$ LANGUAGE plpgsql;
```

## Диагностика и мониторинг

### Расширение plprofiler
Лучший инструмент для поиска узких мест в коде функций. Позволяет получить "Flame Graph" выполнения PL/pgSQL.

### Системная статистика
Мониторинг через `pg_stat_user_functions` (требует `track_functions = all` в конфиге):
```sql
SELECT 
    funcname, 
    calls, 
    total_time / calls AS avg_time, 
    self_time / calls AS avg_self_time
FROM pg_stat_user_functions 
WHERE calls > 0 
ORDER BY total_time DESC;
```

## Поиск и устранение неисправностей

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| **Высокий CPU при работе функции** | Многократные переключения контекста или циклы. | Перепишите логику на чистый SQL или используйте массивы/агрегаты. |
| **Планировщик выбирает плохой план (Seq Scan)** | Неверная волатильность функции в `WHERE`. | Проверьте, не помечена ли функция как `VOLATILE` вместо `STABLE/IMMUTABLE`. |
| **Утечка памяти в долгих сессиях** | Накопление планов запросов в кэше функции. | Используйте `DISCARD PLANS` или переподключайте сессию. |
| **Функция блокирует параллелизм** | Пометка `PARALLEL UNSAFE` (по умолчанию). | Если функция не пишет в БД и не использует переменные сессии, поставьте `PARALLEL SAFE`. |

## Дополнительная информация

### Золотые правила разработки
1.  **SQL превыше всего:** Если задачу можно решить одним сложным SQL-запросом (даже с CTE и окнными функциями) — решайте её на SQL.
2.  **Минимизация вложенности:** Избегайте вызова PL/pgSQL функций из других PL/pgSQL функций в глубоких циклах.
3.  **Strict функции:** Используйте `RETURNS NULL ON NULL INPUT` (или `STRICT`), чтобы PostgreSQL не тратил ресурсы на вызов функции, если один из аргументов `NULL`.
