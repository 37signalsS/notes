# Large Objects (LO) в PostgreSQL: Архитектура, Администрирование и Очистка

## Определения

**Large Objects (LO)** — специализированный механизм PostgreSQL для хранения и управления двоичными данными большого объема (BLOB), размер которых может достигать **4 ТБ**. В отличие от стандартных типов данных, Large Objects хранятся вне бизнес-таблиц, что позволяет обходить ограничение в 1 ГБ на размер отдельного поля (типичное для `bytea` или `text`).

*   **OID (Object Identifier):** 4-байтовое беззнаковое целое число, используемое PostgreSQL как уникальный идентификатор объекта. В бизнес-таблицах хранится только этот OID, который служит ссылкой на данные в системных таблицах.
*   **Orphan Large Objects ("Сиротские" объекты):** Записи в `pg_largeobject`, на которые больше не ссылается ни одна строка в пользовательских таблицах. Возникают из-за того, что СУБД не отслеживает связи между OID в таблицах и объектами в хранилище LO автоматически.
*   **vacuumlo:** Внешняя утилита (поставляется в пакете `postgresql-client`), предназначенная для поиска и удаления "сиротских" объектов путем сканирования всей базы данных.
*   **Расширение `lo`:** Модуль из состава `contrib`, предоставляющий тип данных `lo` и триггеры для автоматического вызова `lo_unlink` при удалении или обновлении строк, что решает проблему целостности.

## Сравнение: bytea vs Large Objects

Выбор между `bytea` и Large Objects критичен для производительности и удобства эксплуатации.

| Характеристика | bytea | Large Objects (LO) |
| :--- | :--- | :--- |
| **Макс. размер** | 1 ГБ | 4 ТБ |
| **Хранение** | Внутри таблицы (или TOAST) | В системной таблице `pg_largeobject` |
| **Доступ** | Стандартный SQL (`SELECT`, `UPDATE`) | Специальный API (`lo_open`, `lo_read`, `lo_seek`) |
| **Случайный доступ** | Нет (чтение всей записи) | Да (чтение/запись произвольного смещения) |
| **Транзакционность** | Полная (MVCC) | Полная, но OID не удаляются автоматически |
| **Репликация** | Логическая и физическая | **Только физическая** (логическая не поддерживает) |
| **Сжатие** | Да (через TOAST) | Нет (хранятся как есть) |

## Архитектура и внутреннее устройство

Large Objects физически распределены по двум основным системным таблицам.

### 1. pg_largeobject_metadata
Хранит метаданные каждого объекта:
- `oid`: Уникальный идентификатор объекта.
- `lomowner`: Владелец объекта (OID роли).
- `lomacl`: Права доступа (Access Control List).

### 2. pg_largeobject
Содержит фактические данные, разбитые на блоки (chunks):
- `loid`: OID объекта, к которому относится блок.
- `pageno`: Номер блока (начиная с 0).
- `data`: Сами данные (тип `bytea`).

**Размер блока:** По умолчанию составляет **2 КБ** (2048 байт). Это значение жестко задано в исходном коде и не может быть изменено без пересборки PostgreSQL. Такое дробление позволяет эффективно читать середину файла, не загружая его целиком.

## Практическое администрирование

### 1. Базовые операции через SQL

Для выполнения этих функций часто требуются права суперпользователя или членство в роли `pg_read_server_files` / `pg_write_server_files`.

```sql
-- 1. Создание пустого объекта
SELECT lo_create(0); -- Возвращает OID, например 16458

-- 2. Импорт файла с диска сервера
SELECT lo_import('/var/lib/postgresql/backups/report.pdf'); 

-- 3. Экспорт данных в файл на диске сервера
SELECT lo_export(16458, '/tmp/exported_report.pdf');

-- 4. Удаление объекта (критично для предотвращения утечек)
SELECT lo_unlink(16458);
```

### 2. Работа с данными внутри SQL (Server-Side API)

PostgreSQL позволяет манипулировать содержимым LO напрямую через SQL-функции, имитирующие работу с файловыми дескрипторами.

```sql
BEGIN;
-- Открытие объекта (режим: 262144 - чтение, 131072 - запись)
-- На практике используются функции-обертки
SELECT lo_open(16458, 131072); -- Возвращает дескриптор (fd)

-- Запись данных по дескриптору
SELECT lowrite(0, '\xDEADC0DE'); -- 0 - дескриптор из предыдущего шага

-- Чтение 10 байт со смещения 0
SELECT loread(lo_open(16458, 262144), 10);
COMMIT;
```

### 3. Автоматизация удаления (расширение `lo`)

Чтобы избежать накопления "сиротских" объектов, рекомендуется использовать расширение `lo`.

```sql
-- Установка расширения
CREATE EXTENSION IF NOT EXISTS lo;

-- Использование типа данных lo и триггера
CREATE TABLE user_files (
    id serial PRIMARY KEY,
    file_data lo -- Тип-обертка над OID
);

-- Создание триггера для автоматического lo_unlink
CREATE TRIGGER t_cleanup_files
    BEFORE UPDATE OR DELETE ON user_files
    FOR EACH ROW EXECUTE FUNCTION lo_manage(file_data);
```

## Очистка и обслуживание

### Использование vacuumlo
Если расширение `lo` не используется, необходимо регулярно запускать `vacuumlo`. Утилита находит все OID, хранящиеся в колонках типа `oid` или `lo` во всех таблицах, и сравнивает их с `pg_largeobject`.

**Регламент запуска:**
```bash
# 1. Анализ (без удаления)
vacuumlo -n -h localhost -U postgres -p 5432 my_database

# 2. Удаление с выводом деталей
vacuumlo -v -h localhost -U postgres my_database
```

**Особенности:**
- `vacuumlo` блокирует таблицу `pg_largeobject` на время удаления, но чтение данных из других таблиц разрешено.
- Для очень больших БД процесс может быть длительным, так как требует полного сканирования всех таблиц на наличие OID.

### Мониторинг и диагностика

```sql
-- Проверка Bloat (раздувания) системной таблицы
SELECT pg_size_pretty(pg_total_relation_size('pg_largeobject')) AS total_size,
       pg_size_pretty(pg_relation_size('pg_largeobject')) AS data_size;

-- Поиск ТОП-5 самых больших LO
SELECT loid, 
       pg_size_pretty(sum(octet_length(data))) as size
FROM pg_largeobject
GROUP BY loid
ORDER BY sum(octet_length(data)) DESC
LIMIT 5;
```

## Безопасность и права доступа

До версии PostgreSQL 9.0 Large Objects не имели системы прав. Сейчас доступ управляется аналогично таблицам.

```sql
-- Предоставление прав на чтение конкретного объекта
GRANT SELECT ON LARGE OBJECT 16458 TO web_user;

-- Смена владельца
ALTER LARGE OBJECT 16458 OWNER TO senior_admin;
```

**Важно:** Для `lo_import` и `lo_export` пользователь базы данных должен иметь соответствующие права на уровне ОС или входить в роль `pg_read_server_files` / `pg_write_server_files`.

## Влияние на SRE-процессы

### Резервное копирование (pg_dump)
- **Флаг `--blobs`:** По умолчанию `pg_dump` включает Large Objects. Однако при использовании ключа `-t` (dump конкретной таблицы) блобы **исключаются**. Всегда добавляйте `--blobs` при выборочном бэкапе.
- **Производительность:** Миллионы мелких LO катастрофически замедляют логический бэкап, так как каждый объект читается отдельным запросом. В таких случаях предпочтительнее `bytea` или физический бэкап.

### Репликация
- **Физическая (Streaming Replication):** Работает безупречно, так как копирует изменения на уровне блоков диска.
- **Логическая репликация:** **Не поддерживает** передачу Large Objects. При попытке реплицировать таблицу с типом `lo` или `oid`, указывающим на LO, данные на реплике будут отсутствовать (OID будет скопирован, но объекта в `pg_largeobject` не будет).
- **Workaround:** Преобразование в `bytea` перед репликацией или использование триггеров для ручного копирования через `COPY`.

## Поиск и устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **Рост диска при пустых таблицах** | Накопление Orphan LO. | Запустите `vacuumlo`. |
| **`Permission denied` при lo_import** | Нет прав у процесса Postgres в ОС. | Проверьте права на директорию или используйте клиентский импорт через `\lo_import` в `psql`. |
| **Медленный pg_dump** | Слишком много мелких объектов. | Мигрируйте на `bytea` или используйте физические бэкапы (`pg_basebackup`). |
| **`invalid large object descriptor`** | Попытка работы с LO вне транзакции. | Оберните вызовы `lo_open` и последующие в `BEGIN...COMMIT`. |

## Золотые правила (SRE Best Practices)

1.  **Порог 1 ГБ:** Используйте LO только если данные гарантированно превысят 1 ГБ или требуется случайный доступ (чтение кусками).
2.  **Используйте `lo_manage`:** Всегда внедряйте расширение `lo` и соответствующие триггеры на этапе проектирования схемы.
3.  **Изоляция метаданных:** Не храните конфиденциальные данные в LO без настройки прав в `pg_largeobject_metadata`.
4.  **Мониторинг:** Настройте алертинг на размер таблицы `pg_largeobject`. Резкий рост часто указывает на баг в приложении (забытый `lo_unlink`).
