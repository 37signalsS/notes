# Вспомогательные расширения PostgreSQL

## Определения

- **Расширение (Extension)** — программный модуль, дополняющий PostgreSQL новыми типами данных, функциями, операторами или индексами. Состоит из управляющего файла (`.control`), SQL-скрипта установки и опционально разделяемой библиотеки (`.so`).
- **Trusted Extension** — расширение, помеченное разработчиками как безопасное. Обычный пользователь (не суперпользователь) может устанавливать его самостоятельно, если имеет право `CREATE` в текущей базе данных.
- **Shared Preload Libraries** — модули, требующие загрузки в оперативную память при старте сервера (`shared_preload_libraries`). Без этой настройки расширение может не работать или работать не полностью (например, `pg_stat_statements`).
- **Extensions Whitelist** — параметр безопасности (в облачных окружениях или через `extwlist`), ограничивающий список расширений, доступных для установки.

## Механика и управление

### Как работают расширения
При выполнении `CREATE EXTENSION`, PostgreSQL:
1.  Находит файл `<name>.control` в каталоге `SHAREDIR/extension`.
2.  Выполняет SQL-скрипт из этого же каталога.
3.  Регистрирует объекты расширения в системном каталоге `pg_extension`.

### Обновление и версионирование
Расширения имеют собственные версии, независимые от версии PostgreSQL.
- **Проверка доступных версий**: `SELECT * FROM pg_available_extension_versions;`
- **Обновление**: `ALTER EXTENSION <name> UPDATE TO '<new_version>';`
*Примечание: Простое обновление бинарных файлов на диске не обновляет логику в базе данных.*

## Основные расширения

### Мониторинг и диагностика

#### pg_stat_statements (Золотой стандарт)
Фиксирует статистику по всем выполненным запросам (время, I/O, кол-во строк).
- **Зачем:** Выявление "тяжелых" запросов и планирование оптимизации.
- **Конфигурация**: Требует `shared_preload_libraries = 'pg_stat_statements'`.
- **Новое в 2026**: Улучшенная поддержка JIT-статистики и параллельных запросов.

#### pgaudit (Аудит безопасности)
Обеспечивает детальное протоколирование действий пользователей (DDL, SELECT, ROLE изменения).
- **Зачем:** Соответствие требованиям безопасности (PCI DSS, SOC2) и расследование инцидентов.
- **Особенности**: Позволяет настроить сессионный или объектный аудит.

#### amcheck
Проверка логической целостности структур данных.
- **Применение**: Поиск несоответствий в индексах и связях с таблицами. Детальное руководство по использованию для спасения данных см. в **[Corruption Recovery](./corruption_recovery.md)**.
- **Пример**: `SELECT bt_index_parent_check('idx_name', true);` для проверки связей между страницами B-Tree.

#### pageinspect
Низкоуровневый анализ содержимого страниц данных.
- **Применение**: Ручное чтение битых страниц, анализ заголовков и отдельных записей (items).
- **Подробности**: Сценарии использования описаны в **[Corruption Recovery](./corruption_recovery.md)**.

### Автоматизация и обслуживание

#### pg_cron (Планировщик задач)
Позволяет запускать SQL-команды по расписанию прямо внутри БД (аналог `cron`).
- **Зачем:** Регулярная очистка логов, обновление материализованных представлений, сбор кастомной статистики.
- **Конфигурация**: Требует загрузки в `shared_preload_libraries` и настройки `cron.database_name`.

#### pg_repack (Онлайн-очистка)
Перестраивает таблицы и индексы без эксклюзивной блокировки (`ACCESS EXCLUSIVE`).
- **Зачем:** Устранение раздувания (Bloat) на "живых" нагруженных системах, где `VACUUM FULL` невозможен.

### Специализированные типы и поиск

#### pgvector (AI и RAG)
Добавляет поддержку векторных данных и поиска по сходству (HNSW, IVFFlat).
- **Зачем:** Хранение эмбеддингов для LLM-приложений и поиск похожих объектов.
Подробнее: **[pgvector: Векторный поиск](../pgvector.md)**.

#### postgis (Геоданные)
Превращает PostgreSQL в полноценную пространственную БД.
- **Зачем:** Работа с координатами, картами и сложной геометрией.

#### citext и unaccent
- **citext**: Регистронезависимый текст (удобно для Email).
- **unaccent**: Удаление диакритики (ё -> е, é -> e) для нормализации поиска.

## Практические сценарии

### 1. Безопасная установка в отдельную схему
Рекомендуется изолировать расширения от бизнес-таблиц для предотвращения конфликтов имен.

```sql
-- 1. Создание схемы
CREATE SCHEMA extensions;

-- 2. Установка (объекты будут созданы в этой схеме)
CREATE EXTENSION pgcrypto SCHEMA extensions;

-- 3. Настройка пути поиска для пользователей
ALTER ROLE app_user SET search_path TO public, extensions;
```

### 2. Анализ "тяжелых" запросов по I/O
После включения `pg_stat_statements` и `track_io_timing = on`:

```sql
SELECT 
    query, 
    calls, 
    round(total_exec_time::numeric, 2) as total_ms,
    round((blk_read_time + blk_write_time)::numeric, 2) as io_ms
FROM pg_stat_statements
ORDER BY io_ms DESC
LIMIT 10;
```

### 3. Планирование задач через pg_cron
Автоматическое обновление статистики каждую ночь в 03:00.

```sql
SELECT cron.schedule('daily-analyze', '0 3 * * *', 'ANALYZE VERBOSE my_large_table');
```

## Диагностика и Troubleshooting

- **Ошибка `could not open control file`**: Расширение не установлено в системе (отсутствуют файлы в `/usr/share/postgresql/.../extension`).
- **Расширение не видно в `pg_available_extensions`**: Проверьте путь `PG_CONFIG --sharedir`.
- **Ошибка при `DROP EXTENSION`**: Расширение может иметь зависимости. Используйте `CASCADE`, но будьте осторожны: это удалит все зависимые объекты (колонки типов расширения и т.д.).
- **Версионный конфликт**: Если бинарный файл обновлен, но скрипт нет — выполните `ALTER EXTENSION ... UPDATE`.

## Золотые правила (Security & Ops)

1.  **Принцип минимизации**: Каждое расширение — это потенциальная уязвимость и нагрузка на память. Удаляйте неиспользуемые.
2.  **Схемная изоляция**: Никогда не ставьте расширения в `public` в многопользовательских базах.
3.  **Ограничение прав**: Отзывайте `EXECUTE` у `PUBLIC` для функций чувствительных расширений (например, `pg_read_file` из `adminpack`).
4.  **Мониторинг ресурсов**: Расширения, использующие `shared_preload_libraries`, потребляют общую память. Закладывайте это при расчете `shared_buffers`.
