# Полнотекстовый поиск (FTS) в PostgreSQL

## Определения

- **FTS (Full Text Search)** — встроенный механизм PostgreSQL для поиска документов на естественном языке. Позволяет находить слова с учетом морфологии (склонения, спряжения), стоп-слов и релевантности.
- **tsvector** — специальный бинарный тип данных, представляющий документ в виде оптимизированного списка лексем (нормализованных слов) с позиционной информацией и весами.
- **tsquery** — тип данных для поискового запроса, поддерживающий логические операторы (`&` AND, `|` OR, `!` NOT), фразовый поиск (`<->`) и веса.
- **Лексема (Lexeme)** — нормализованная форма слова (например, «бежать», «бежит» → `беж`).
- **Стемминг (Stemming)** — процесс приведения слова к его основе путем отсечения окончаний и суффиксов (часто через алгоритмы **Snowball**).
- **Словарь (Dictionary)** — программный компонент, отвечающий за нормализацию токенов и удаление стоп-слов. Могут работать каскадно.
- **Парсер (Parser)** — компонент, разбивающий сырой текст на токены различных типов (слова, цифры, email, URL и т.д.).
- **Ranking Normalization (Нормализация ранга)** — метод корректировки веса документа в зависимости от его длины или количества найденных слов.
- **GIN (Generalized Inverted Index)** — основной тип индекса для FTS, хранящий список документов для каждой лексемы.

## Базовые концепции

### Архитектура поиска
Процесс преобразования текста в поисковый вектор (`to_tsvector`) включает три этапа:
1.  **Токенизация**: Разбиение строки на составляющие с помощью парсера.
2.  **Обработка словарями**: Удаление стоп-слов и нормализация оставшихся токенов (приведение к нижнему регистру, стемминг).
3.  **Формирование вектора**: Сборка уникальных лексем в объект `tsvector` с сохранением позиций.

### Типы индексов для FTS

| Тип индекса | Особенности | Когда использовать |
| :--- | :--- | :--- |
| **GIN** | Высокая скорость поиска, но медленное обновление. Поддерживает `fastupdate` для ускорения вставок. | Стандарт для большинства задач FTS. |
| **GiST** | Компактный, быстрее обновляется, но поиск медленнее и может быть «нечетким» (lossy). Поддерживает KNN-поиск. | Когда важна скорость вставки и экономия места на диске. |
| **RUM** | Стороннее расширение. Хранит позиции лексем и дополнительные метаданные (например, метки времени). | Когда нужно быстрое ранжирование по релевантности и сложный фразовый поиск на гигантских данных. |

### Конфигурации поиска
PostgreSQL использует конфигурации (например, `russian`, `english`) для связи парсеров и словарей.
- Просмотр доступных: `\dF` в psql.
- Просмотр маппингов (какой тип токена каким словарем обрабатывается): `\dFp`.
- Конфигурация по умолчанию: параметр `default_text_search_config`.

## Практические сценарии

### 1. Отладка и анализ (ts_debug)
Инструмент для проверки того, как именно текст разбивается на токены и какие словари их обрабатывают.

```sql
SELECT * FROM ts_debug('russian', 'Базы данных — это круто!');
-- Выведет: тип токена (alias), описание, слово, словари, лексему.
-- Если лексема NULL — слово является стоп-словом.
```

### 2. Создание векторов с весами (Weights)
Для повышения релевантности можно назначать веса разным частям документа: `A` (самый высокий), `B`, `C`, `D` (по умолчанию).

```sql
SELECT setweight(to_tsvector('russian', title), 'A') || 
       setweight(to_tsvector('russian', body), 'B') 
AS doc_vector
FROM articles;
```

### 3. Хранимые колонки и триггеры
Для производительности вектор должен быть индексирован.

**Вариант 1: GENERATED колонки (PostgreSQL 12+)** — Рекомендуемый способ.
```sql
CREATE TABLE articles (
    id SERIAL PRIMARY KEY,
    title TEXT,
    body TEXT,
    fts_vector tsvector GENERATED ALWAYS AS (
        setweight(to_tsvector('russian', coalesce(title, '')), 'A') || 
        setweight(to_tsvector('russian', coalesce(body, '')), 'B')
    ) STORED
);
CREATE INDEX idx_articles_fts ON articles USING gin(fts_vector);
```

**Вариант 2: Триггеры (для сложных правил или старых версий)**
```sql
CREATE FUNCTION articles_fts_trigger() RETURNS trigger AS $$
begin
  new.fts_vector := 
     setweight(to_tsvector('russian', coalesce(new.title,'')), 'A') ||
     setweight(to_tsvector('russian', coalesce(new.body,'')), 'B');
  return new;
end
$$ LANGUAGE plpgsql;

CREATE TRIGGER tsvectorupdate BEFORE INSERT OR UPDATE
ON articles FOR EACH ROW EXECUTE FUNCTION articles_fts_trigger();
```

### 4. Расширенный поиск (websearch_to_tsquery)
Функция поддерживает синтаксис Google-поиска (`"фраза"`, `-исключение`).

```sql
SELECT title 
FROM articles 
WHERE fts_vector @@ websearch_to_tsquery('russian', '"база данных" -oracle');
```

### 5. Фразовый поиск и расстояние
Оператор `<->` означает последовательность. `<N>` задает максимальное расстояние.

```sql
-- "база" сразу перед "данных"
SELECT to_tsquery('russian', 'база <-> данных');

-- "база" в пределах 2 слов от "данных"
SELECT to_tsquery('russian', 'база <2> данных');
```

### 6. Поиск без акцентов и ё/е (unaccent)
Расширение `unaccent` позволяет игнорировать диакритические знаки.

```sql
CREATE EXTENSION unaccent;
-- Создание кастомной конфигурации на базе russian
CREATE TEXT SEARCH CONFIGURATION russian_unaccent (COPY = russian);
ALTER TEXT SEARCH CONFIGURATION russian_unaccent 
    ALTER MAPPING FOR hword, hword_asciipart, hword_part, word 
    WITH unaccent, russian_stem;
```

### 7. Подключение словарей Hunspell (Качественная морфология)
Для более точного поиска (в отличие от стемминга) можно использовать Hunspell-словари.
1. Разместите файлы `.aff` и `.dict` в `$SHAREDIR/tsearch_data/`.
2. Создайте словарь в БД:
```sql
CREATE TEXT SEARCH DICTIONARY ru_hunspell (
    TEMPLATE = ispell,
    DictFile = ru_ru,
    AffFile = ru_ru,
    StopWords = russian
);
```

### 8. Поиск по триграммам (pg_trgm)
Эффективен для поиска с опечатками или нечеткого совпадения строк.
- **Использование**: `WHERE name % 'опечатка'` (оператор сходства).
- **Индекс**: `CREATE INDEX ON table USING gin(name gin_trgm_ops);`.

### 9. Ранжирование с нормализацией
Функция `ts_rank` поддерживает флаги нормализации для учета длины документа.

| Флаг | Описание |
| :--- | :--- |
| **0** (Default) | Игнорирует длину документа. |
| **1** | Делит ранг на `log(длина документа)`. |
| **2** | Делит ранг на длину документа. |
| **4** | Делит ранг на среднее расстояние между словами (только для `ts_rank_cd`). |

```sql
SELECT 
    title, 
    ts_headline('russian', body, query, 'StartSel=<b>, StopSel=</b>') as snippet
FROM articles, websearch_to_tsquery('russian', 'индексы') query
WHERE fts_vector @@ query
ORDER BY ts_rank_cd(fts_vector, query, 1) DESC; -- Нормализация по log(длины)
```

### 10. Поиск внутри JSONB
PostgreSQL позволяет индексировать значения внутри `jsonb`.
```sql
-- Индексация текстовых значений в JSON
CREATE INDEX idx_json_fts ON articles USING gin(to_tsvector('russian', data));
```
Для сложных запросов используйте расширение **`jsquery`**.

## Оптимизация производительности

### Тюнинг GIN индекса
- **`fastupdate = on`**: Включает `pending list`, группируя изменения в памяти перед записью в индекс.
- **`gin_pending_list_limit`**: Увеличение лимита (например, до 4-16 MB) ускоряет массовые вставки.
- **`work_mem`**: Влияет на скорость сортировки лексем при поиске и построении индекса.

### Очистка и обслуживание
- **VACUUM**: Регулярная очистка критична для GIN индексов, так как они могут сильно раздуваться при частых обновлениях.
- **Словари в памяти**: При первой загрузке словари кэшируются. На высоконагруженных системах следите за потреблением RAM бэкенд-процессами.

## Диагностика и Troubleshooting

- **Проблема "Мусора"**: Если в `tsvector` попадают слишком длинные строки (логи, дампы), индекс становится неэффективным. Ограничивайте маппинги токенов в конфигурации.
- **Проблема Coalesce**: При индексации нескольких колонок всегда используйте `coalesce(col, '')`. Один `NULL` в конкатенации превратит весь вектор в `NULL`.

## Сравнение PostgreSQL FTS vs Elasticsearch

| Характеристика | PostgreSQL (FTS) | Elasticsearch |
| :--- | :--- | :--- |
| **Сложность** | Низкая (интегрировано в БД) | Высокая (отдельная инфраструктура) |
| **Консистентность** | ACID (строгая, мгновенная) | Eventual Consistency (задержка индексации) |
| **Масштабирование** | Вертикальное (до ~20 млн документов) | Горизонтальное (миллиарды документов) |
| **Возможности** | Базовый полнотекст, триграммы | Fuzzy, аналитика, автодополнение, NLP |

## Золотые правила (DevOps/SRE)

1. **STORED над триггерами**: Всегда предпочитайте `GENERATED ALWAYS AS ... STORED`, это проще в поддержке и быстрее работает.
2. **Изоляция конфигурации**: Создавайте свои конфигурации (`CREATE TEXT SEARCH CONFIGURATION`), чтобы избежать влияния системных обновлений.
3. **REINDEX при обновлении**: Если вы обновили файлы словарей на диске, обязательно выполните `REINDEX` для всех зависимых индексов.
4. **Мониторинг лага**: Если используется `fastupdate`, следите за временем выполнения запросов — большой `pending list` может замедлять поиск.
