# pgcrypto: Криптография в PostgreSQL

## Определения

**pgcrypto** — доверенное расширение PostgreSQL, предоставляющее набор криптографических функций (хеширование, шифрование, генерация случайных данных) непосредственно в SQL.

*   **Data-at-rest encryption:** Шифрование данных в состоянии покоя (на диске, в бэкапах).
*   **HMAC (Keyed-Hash Message Authentication Code):** Код аутентификации сообщений, использующий хеш-функцию и секретный ключ.
*   **Соль (Salt):** Случайные данные, добавляемые к паролю перед хешированием для защиты от перебора по словарям и радужным таблицам.
*   **Вектор инициализации (IV):** Случайное число, используемое для обеспечения уникальности шифротекста при использовании одного и того же ключа.

## Установка и безопасность

Для обеспечения принципа наименьших привилегий рекомендуется устанавливать расширение в отдельную схему.

### Алгоритм установки

1.  Создание схемы и установка:
    ```sql
    CREATE SCHEMA crypto;
    CREATE EXTENSION pgcrypto SCHEMA crypto;
    ```
2.  Ограничение доступа (по умолчанию права есть у `PUBLIC`):
    ```sql
    -- Отозвать права у всех
    REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA crypto FROM PUBLIC;
    
    -- Выдать права конкретной роли приложения
    GRANT EXECUTE ON FUNCTION crypto.encrypt(bytea, bytea, text) TO app_user;
    GRANT EXECUTE ON FUNCTION crypto.decrypt(bytea, bytea, text) TO app_user;
    ```

## Хеширование данных

Предназначено для проверки целостности и подлинности.

*   **`digest(data, type)`:** Вычисляет хеш (отпечаток) данных.
    *   *Алгоритмы:* `sha256`, `sha512` (рекомендуются); `md5`, `sha1` (устарели).
    *   *Пример:* `SELECT crypto.digest('data', 'sha256');`
*   **`hmac(data, key, type)`:** Хеш с использованием секретного ключа. Подтверждает не только целостность, но и авторство данных.

**Внимание:** Не используйте `digest()` для хранения паролей, так как он не применяет соль.

## Шифрование данных

### Симметричное шифрование (AES)
Использует один ключ для зашифровки и расшифровки. Рекомендуемый стандарт — **AES-256**.

*   **Функции:** `encrypt()`, `decrypt()`, `encrypt_iv()`, `decrypt_iv()`.
*   **Режимы:**
    *   **CBC (Cipher Block Chaining):** Рекомендуемый. Использует IV для исключения паттернов в данных.
    *   **ECB (Electronic Codebook):** Небезопасен, не рекомендуется (одинаковые блоки данных дают одинаковый шифротекст).
*   **Дополнение (Padding):** Используется `PKCS#7` для приведения длины данных к размеру блока.

### Асимметричное шифрование (PGP)
Использует пару ключей (публичный/приватный). Совместимо с протоколом OpenPGP.

*   `pgp_pub_encrypt()` / `pgp_pub_decrypt()`: Шифрование на публичном ключе, расшифровка на приватном.
*   `dearmor()`: Преобразование ключей из текстового формата (ASCII-armored) в `bytea`.

**Ограничение:** pgcrypto поддерживает только шифрование PGP, но не создание/проверку цифровых подписей.

## Хранение паролей

Для паролей используются специализированные функции, реализующие алгоритм **bcrypt**.

1.  **Создание хеша:**
    ```sql
    -- gen_salt('bf', 10): алгоритм blowfish, фактор трудоемкости 10
    INSERT INTO users (username, pass_hash) 
    VALUES ('admin', crypto.crypt('password', crypto.gen_salt('bf', 10)));
    ```
2.  **Проверка при входе:**
    ```sql
    SELECT (pass_hash = crypto.crypt('entered_password', pass_hash)) AS is_valid
    FROM users WHERE username = 'admin';
    ```

## Управление ключами

Безопасность pgcrypto полностью зависит от хранения ключей вне базы данных.

**Стратегии хранения:**
1.  **KMS (Key Management Service):** Использование HashiCorp Vault или облачных сервисов (AWS/GCP KMS) — самый надежный способ.
2.  **Переменные окружения:** Ключ передается приложению при запуске и используется в параметрах SQL-запросов.
3.  **Конфигурационные файлы:** Файлы с правами доступа `0600` на сервере приложения.

**Категорически запрещено** хранить ключи в открытом виде в той же базе данных, где лежат зашифрованные данные.

## Генерация случайных данных

*   **`gen_random_bytes(count)`:** Криптографически стойкие байты (макс. 1024 за вызов).
*   **`gen_random_uuid()`:** Создание UUID версии 4.

## Практические сценарии

### 1. Шифрование конфиденциальных столбцов
Для хранения зашифрованных данных используйте тип `bytea`.

**Вставка данных (AES-256-CBC):**
```sql
INSERT INTO users (username, api_key)
VALUES ('dev_user', crypto.encrypt(
    convert_to('my_secret_api_key_123', 'utf8'), -- Текст в байты
    'my_kms_key_string',                         -- Ключ из внешнего сервиса
    'aes-cbc'
));
```

**Чтение и расшифровка:**
```sql
SELECT username, 
       convert_from(crypto.decrypt(api_key, 'my_kms_key_string', 'aes-cbc'), 'utf8') AS decrypted_key
FROM users
WHERE username = 'dev_user';
```

### 2. Контроль подлинности (HMAC-аудит)
HMAC позволяет создать «аудиторский след», подтверждающий, что данные не были изменены несанкционированно.

```sql
-- Хранение данных с подписью
INSERT INTO audit_logs (log_data, signature)
VALUES ('{"action": "delete", "user": "admin"}', 
        encode(crypto.hmac('{"action": "delete", "user": "admin"}', 'audit_secret', 'sha256'), 'hex'));

-- Проверка валидности
SELECT *, 
       (encode(crypto.hmac(log_data, 'audit_secret', 'sha256'), 'hex') = signature) AS is_authentic
FROM audit_logs;
```

### 3. Использование PGP для внешнего обмена
Безопасная загрузка данных, зашифрованных внешним партнером.

```sql
INSERT INTO partner_imports (raw_data)
VALUES (crypto.pgp_pub_decrypt(crypto.dearmor(:'pgp_message'), crypto.dearmor(:'private_key_bin')));
```

## Производительность и индексирование

Криптографические операции создают значительную нагрузку на CPU. Перед внедрением в production обязательно проведение нагрузочного тестирования.

### Проблема поиска
Качественное шифрование (с использованием случайного IV) является **недетерминированным**: один и тот же текст каждый раз дает разный шифротекст. Это делает стандартные индексы (B-Tree) бесполезными для поиска.

**Способы решения:**
1.  **Хеширование для точного поиска:** Храните рядом с зашифрованной колонкой хеш (`SHA-256`) от открытого текста и стройте индекс по нему. Позволяет выполнять поиск по точному совпадению (`=`), но не по диапазону или части строки.
2.  **Детерминированное шифрование (не рекомендуется):** Использование режима `ECB` или фиксированного IV. Это небезопасно, так как раскрывает паттерны данных.
3.  **Клиентская фильтрация:** Выгрузка данных и расшифровка в памяти приложения. Эффективно только для малых выборок.

**Золотое правило:** Избегайте шифрования полей, по которым требуется частый поиск.

## Сравнение методов защиты

| Метод | Уровень защиты | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **pgcrypto** (Column-level) | Средний/Высокий | Гранулярность, соответствие PCI DSS/GDPR. | Нагрузка на CPU, сложность индексации. |
| **Application-level** | Максимальный | Защита от скомпрометированного админа БД. | Сложная логика в коде, невозможность поиска в БД. |
| **TDE** (Filesystem-level) | Базовый | Прозрачность для приложения, нулевое Bloat. | Не защищает от SQL-инъекций или админа БД. |
| **Tokenization** | Экстремальный | Полная изоляция данных (Vaulting). | Зависимость от внешней системы, сетевые задержки. |

## Ограничения и риски

*   **Управление ключами:** Главная уязвимость. Хранение ключа рядом с данными обесценивает шифрование. Потеря ключа означает безвозвратную потерю данных.
*   **Encrypted Backups:** Данные в бэкапах и на репликах остаются зашифрованными.
*   **SQL-инъекции:** pgcrypto не защищает от кражи данных, если злоумышленник может выполнить дешифровку через приложение, имеющее доступ к ключам.

## Лучшие практики (Чек-лист)
- [ ] Использовать только **AES-256-CBC**, **SHA-256/512**, **bcrypt**.
- [ ] Ключи хранить в **KMS** (HashiCorp Vault и др.).
- [ ] Применять **принцип наименьших привилегий** для схемы `crypto`.
- [ ] Включить **аудит** всех вызовов функций дешифрования.
- [ ] Не шифровать поля, по которым нужен поиск или индексация.
