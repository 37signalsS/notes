# Борьба с блокировками в PostgreSQL: Управление параллелизмом

При работе с высоконагруженными системами на PostgreSQL одной из главных задач становится эффективное управление блокировками для достижения высокой параллельности (concurrency). Неправильная работа с блокировками может приводить к замедлению работы приложения, взаимоблокировкам (`deadlocks`) и общей деградации производительности.

## 1. Типы блокировок и уровни изоляции

### Типы блокировок
PostgreSQL использует различные уровни блокировок:
- **Блокировки уровня таблицы:** Захватывают всю таблицу целиком.
- **Блокировки уровня строки:** Захватывают отдельные строки. Это основной механизм для обеспечения параллельной работы с данными. Явная пессимистическая блокировка строки выполняется с помощью `SELECT ... FOR UPDATE` или `SELECT ... FOR SHARE`.

### Уровни изоляции транзакций
PostgreSQL поддерживает три из четырех стандартных уровней изоляции:
1.  **Read Committed (По умолчанию):** Транзакция видит только те данные, которые были зафиксированы (committed) до ее начала. Это предотвращает чтение "грязных" данных, но не решает проблемы "неповторяющегося чтения" (`non-repeatable read`) и "фантомного чтения" (`phantom read`).
2.  **Repeatable Read:** Гарантирует, что при повторном чтении в рамках одной транзакции данные останутся теми же, какими они были на момент начала транзакции. Этот уровень предотвращает "неповторяющееся чтение", но "фантомы" все еще возможны.
3.  **Serializable:** Самый строгий уровень, который гарантирует, что одновременное выполнение набора транзакций эквивалентно их некоторому последовательному выполнению. Этот уровень предотвращает все виды аномалий, включая "фантомы".

> PostgreSQL не поддерживает уровень `Read Uncommitted`.

### Механизм MVCC (Multi-Version Concurrency Control)
В основе уровней изоляции `Read Committed` и `Repeatable Read` лежит механизм MVCC. Вместо того чтобы блокировать данные при чтении, PostgreSQL создает "снимки" (snapshots) данных для каждой транзакции. При изменении или удалении строки создается ее новая версия, в то время как старые версии могут оставаться доступными для транзакций, которые начались до их изменения. Это позволяет операциям чтения не блокировать операции записи, и наоборот.

## 2. Проблема взаимоблокировок (Deadlocks)

Deadlock возникает, когда две (или более) транзакции блокируют друг друга, ожидая освобождения ресурсов, захваченных другой стороной.

**Пример классического дедлока:**
1.  Транзакция А блокирует строку 1.
2.  Транзакция Б блокирует строку 2.
3.  Транзакция А пытается заблокировать строку 2, но ждет, пока ее освободит транзакция Б.
4.  Транзакция Б пытается заблокировать строку 1, но ждет, пока ее освободит транзакция А.

PostgreSQL автоматически обнаруживает такие ситуации и прерывает одну из транзакций, откатывая ее с ошибкой.

### Способы предотвращения дедлоков:
- **Единый порядок блокировок:** Всегда захватывать ресурсы (строки, таблицы) в одном и том же порядке во всех транзакциях.
- **Короткие транзакции:** Чем меньше время жизни транзакции, тем ниже вероятность возникновения конфликта.
- **Использование `SELECT ... FOR UPDATE SKIP LOCKED`:** Для сценариев очередей задач, где не важен порядок обработки, эта конструкция позволяет захватить только те строки, которые не заблокированы в данный момент.
- **Таймауты:** Настройка `lock_timeout` может помочь избежать долгого ожидания блокировок.

## 3. Стратегии оптимизации и лучшие практики

### 3.1. Используйте короткие транзакции

Это один из самых важных принципов. Длинная транзакция удерживает блокировки на протяжении длительного времени, что увеличивает время ожидания для других транзакций и повышает риск дедлоков.

**Антипаттерн:** Длинная транзакция с бизнес-логикой и внешними вызовами.
```java
@Transactional
public void processOrder() {
    // 1. Блокируем запись в БД (начало транзакции)
    Order order = orderRepository.findByIdForUpdate(1L);

    // 2. Долгая бизнес-логика
    // 3. Вызов внешнего сервиса (например, платежного шлюза) - ОЧЕНЬ ПЛОХО!
    paymentGateway.charge(order.getAmount());

    // 4. Обновление статуса
    order.setStatus("PAID");
    orderRepository.save(order);
    // 5. Конец транзакции, блокировка снимается (может пройти несколько секунд)
}
```

**Правильный подход:** Разделение логики.
1.  Прочитать данные вне транзакции.
2.  Выполнить все внешние вызовы и долгую логику.
3.  Начать короткую транзакцию только для выполнения атомарной операции записи в БД.

### 3.2. Оптимистичные блокировки

Вместо пессимистичной блокировки (`FOR UPDATE`), которая физически блокирует строку, можно использовать оптимистичный подход.

- **Принцип:** Конфликты разрешаются в момент фиксации транзакции. Вместо блокировки используется колонка с версией (`version`).
- **Как работает:**
  1. При чтении строки приложение запоминает ее версию.
  2. При выполнении `UPDATE` в условие `WHERE` добавляется проверка `version = <прочитанная_версия>`.
  3. Если за время работы другая транзакция успела изменить строку (и увеличить ее версию), условие `WHERE` не будет выполнено, и `UPDATE` не затронет ни одной строки.
  4. Приложение проверяет количество измененных строк. Если оно равно 0, значит, произошел конфликт, и транзакцию нужно либо откатить и сообщить об ошибке пользователю, либо повторить (retry).

**Когда использовать:** Идеально подходит для сценариев с низкой вероятностью конфликтов (когда операций чтения значительно больше, чем записей). Например, редактирование профиля пользователя.
**Когда не использовать:** Не подходит для сценариев с высокой конкуренцией на запись (например, обновление общего счетчика), так как приведет к большому количеству ошибок и повторных попыток.

### 3.3. Паттерн "Очередь задач" с `SKIP LOCKED`

Для реализации очереди задач, где несколько воркеров разбирают задачи из одной таблицы, `SKIP LOCKED` является чрезвычайно эффективным решением.

```sql
DELETE FROM tasks
WHERE id = (
  SELECT id
  FROM tasks
  WHERE status = 'PENDING'
  ORDER BY priority DESC
  LIMIT 1
  FOR UPDATE SKIP LOCKED
)
RETURNING *;
```
- **Как это работает:**
  - `FOR UPDATE` пытается захватить блокировку на выбранную строку.
  - `SKIP LOCKED` говорит PostgreSQL не ждать, если строка уже заблокирована другой транзакцией, а просто пропустить ее и перейти к следующей.
  - Таким образом, каждый воркер гарантированно получит свою уникальную, свободную задачу без ожидания и риска дедлоков.

### 3.4. Разделение "горячих" данных

Если у вас есть одна строка, которая обновляется очень часто (например, глобальный счетчик), это создает "горячую точку" (hot spot) и узкое место.

**Решение:** Разделите (шардируйте) счетчик на несколько. Например, вместо одного счетчика создайте 10, и при инкременте выбирайте случайный из них. При чтении итогового значения просто суммируйте значения всех 10 счетчиков. Это распределяет нагрузку на запись по нескольким строкам.

### 3.5. Архитектурные паттерны
- **Event Sourcing:** Вместо изменения (`UPDATE`) состояния, записывайте события (`INSERT`) об изменениях. Текущее состояние вычисляется на основе всех событий. `INSERT`'ы, как правило, вызывают меньше конфликтов, чем `UPDATE`'ы.
- **Вынос состояния во внешние системы:** Для счетчиков, сессий и других часто изменяемых данных можно использовать более подходящие инструменты, такие как **Redis**, который предоставляет атомарные операции инкремента.
- **Компенсирующие транзакции (Saga):** В распределенных системах вместо одной длинной двухфазной транзакции используется цепочка коротких локальных транзакций. Для отката в случае сбоя выполняется последовательность "компенсирующих" транзакций.

## 4. Мониторинг блокировок

Для анализа текущей ситуации с блокировками в PostgreSQL существуют системные представления:
- **`pg_stat_activity`:** Показывает все активные сессии, их текущие запросы и состояние ожидания (`wait_event`). Позволяет увидеть, какие запросы заблокированы и кем.
- **`pg_locks`:** Предоставляет детальную информацию о всех активных блокировках в системе.
