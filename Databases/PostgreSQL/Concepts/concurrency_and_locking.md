# Конкурентность и блокировки в PostgreSQL

## Определения

- **MVCC (Multi-Version Concurrency Control)**: Механизм управления параллельным доступом, при котором для каждого изменения строки создается ее новая версия, а не блокируется существующая. Это позволяет операциям чтения не блокировать операции записи, и наоборот.
- **Снимок данных (Snapshot)**: Консистентное представление данных в оперативной памяти на определенный момент времени. Каждая транзакция работает со своим снимком.
- **Уровень изоляции транзакций (Transaction Isolation Level)**: Степень, в которой одна транзакция изолирована от изменений, производимых другими параллельными транзакциями.
- **Аномалии чтения**:
  - **Грязное чтение (Dirty Read)**: Чтение данных, измененных другой транзакцией, которая еще не была зафиксирована.
  - **Неповторяющееся чтение (Non-repeatable Read)**: При повторном чтении одних и тех же данных в рамках одной транзакции они оказываются измененными другой зафиксированной транзакцией.
  - **Фантомное чтение (Phantom Read)**: При повторном выполнении запроса с фильтрацией в рамках одной транзакции набор возвращаемых строк меняется из-за вставок других транзакций.

## Базовые концепции

### Механизм MVCC

MVCC в PostgreSQL работает по принципу версионности:

- **Изоляция**: Транзакция видит состояние базы на момент создания своего снимка.
- **Коммит**: При фиксации (`COMMIT`) новые версии строк становятся видимыми для последующих транзакций.
- **Очистка**: Старые ("мертвые") версии строк не удаляются немедленно, они сохраняются до тех пор, пока не будут очищены процессом `VACUUM`.
- **Эффект раздувания (Bloat)**: Интенсивное обновление данных приводит к накоплению мертвых строк, что увеличивает размер таблиц и замедляет индексы.

**Преимущество:** Читатели никогда не блокируют писателей, а писатели — читателей.

### Уровни изоляции транзакций

PostgreSQL поддерживает три уровня изоляции из стандарта SQL (уровень `Read Uncommitted` не поддерживается и работает как `Read Committed`).

1. **Read Committed (по умолчанию)**:
    - Видит только зафиксированные данные.
    - Снимок создается для каждого отдельного запроса внутри транзакции.
    - Возможны неповторяющееся и фантомное чтение.
2. **Repeatable Read**:
    - Снимок создается один раз при первом запросе в транзакции.
    - Гарантирует стабильность данных при повторном чтении.
    - При конфликте обновления (две транзакции меняют одну строку) вторая транзакция завершится ошибкой сериализации.
3. **Serializable**:
    - Самый строгий уровень. Гарантирует результат, эквивалентный последовательному выполнению транзакций.
    - Использует предикатные блокировки для отслеживания зависимостей между транзакциями.

### Типы блокировок

#### Разделяемая блокировка (Share Lock)

Допускает одновременное удержание несколькими транзакциями. Используется для чтения. Несовместима с эксклюзивными блокировками. Пример: `SELECT ... FOR SHARE`.

#### Эксклюзивная блокировка (Exclusive Lock)

Допускает удержание только одной транзакцией. Используется для изменения данных. Блокирует любые другие попытки захвата блокировки на этот же объект. Пример: `SELECT ... FOR UPDATE`.

#### Строгая блокировка (ACCESS EXCLUSIVE)

Самый высокий уровень блокировки. Накладывается операциями `ALTER TABLE`, `DROP TABLE`, `VACUUM FULL`. Блокирует все операции, включая `SELECT`.

## Практические сценарии

### Предотвращение каскадных блокировок

Операция `ALTER TABLE` может парализовать работу приложения:

1. `ALTER TABLE` ждет завершения долгой транзакции чтения.
2. Все новые `SELECT` встают в очередь за `ALTER TABLE`.
3. Система перестает отвечать.

**Решение:**

- Устанавливать `lock_timeout` перед выполнением DDL.
- Проверять наличие долгих транзакций перед миграциями.
- Выполнять миграции в периоды минимальной нагрузки.

### Мониторинг блокировок

Для поиска блокирующих и заблокированных процессов используется системное представление `pg_stat_activity` и `pg_locks`.

```sql
SELECT 
    a.pid AS blocked_pid,
    a.usename AS blocked_user,
    a.query AS blocked_query,
    b.pid AS blocking_pid,
    b.query AS blocking_query
FROM pg_stat_activity a
JOIN pg_locks l1 ON a.pid = l1.pid
JOIN pg_locks l2 ON l1.relation = l2.relation AND l1.locktype = l2.locktype
JOIN pg_stat_activity b ON l2.pid = b.pid
WHERE NOT l1.granted AND l2.granted;
```

### Обработка очередей с SKIP LOCKED

Для реализации распределенной очереди задач без конфликтов блокировки строк:

```sql
-- Воркер берет задачу, которую еще никто не заблокировал
SELECT id FROM tasks 
WHERE status = 'NEW' 
ORDER BY created_at 
LIMIT 1 
FOR UPDATE SKIP LOCKED;
```

### Взаимоблокировки (Deadlocks)

Ситуация, когда транзакции циклически ждут ресурсы друг друга. PostgreSQL автоматически обнаруживает дедлок и прерывает одну из транзакций.

**Способы предотвращения:**

- **Единый порядок**: Всегда обновляйте записи в одинаковом порядке (например, по возрастанию ID).
- **Минимизация транзакций**: Держите транзакции максимально короткими.
- **Изоляция логики**: Не делайте внешние запросы (API, файлы) внутри транзакции БД.
