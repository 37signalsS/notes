# Конкурентность и блокировки в PostgreSQL

## Определения

- **MVCC (Multi-Version Concurrency Control)** — механизм управления конкурентным доступом, при котором для каждого изменения строки создается её новая версия. Это позволяет читающим транзакциям работать с «замороженным» снимком данных, не блокируя пишущие транзакции, и наоборот.
- **Уровень изоляции (Isolation Level)** — параметр транзакции, определяющий степень строгости правил видимости изменений, внесенных параллельными транзакциями.
- **Снимок данных (Snapshot)** — структура данных, содержащая информацию о состоянии активных транзакций в момент начала запроса или всей транзакции. Определяет, какие версии строк (tuples) являются видимыми.
- **Взаимоблокировка (Deadlock)** — тупиковая ситуация, при которой две и более транзакции ожидают освобождения ресурсов, удерживаемых друг другом в циклической зависимости.
- **Рекомендательные блокировки (Advisory Locks)** — механизм прикладных блокировок, управляемый пользователем. Не привязан к строкам таблиц и используется для координации логики приложения (например, предотвращение одновременного запуска фоновых задач).
- **Очередь блокировок (Lock Queue)** — механизм управления доступом к ресурсу (таблице). Блокировки выстраиваются в очередь. Если запрос в начале очереди требует эксклюзивного доступа (например, `ALTER TABLE`), он заблокирует все последующие запросы, включая простые `SELECT`.
- **SSI (Serializable Snapshot Isolation)** — реализация уровня Serializable в PostgreSQL, основанная на отслеживании зависимостей между транзакциями для обнаружения циклов аномалий (например, Write Skew) без жестких блокировок чтения.

## Базовые концепции

### Внутреннее устройство MVCC
PostgreSQL хранит версии строк непосредственно в страницах данных (heap). Каждая версия строки (tuple) содержит служебный заголовок с полями:
- **XMIN**: Идентификатор транзакции (XID), которая создала данную версию строки.
- **XMAX**: Идентификатор транзакции, которая удалила или обновила строку (создав новую версию). Если строка актуальна, `XMAX` равен 0.
- **CID (Command ID)**: Порядковый номер команды внутри транзакции для обеспечения видимости собственных изменений.
- **CTID**: Указатель на физическое местоположение версии строки (номер страницы и смещение). При обновлении `CTID` старой версии указывает на новую.
- **Infomask**: Набор бит, определяющий статус транзакций (зафиксирована, отменена) без обращения к `CLOG` (Commit Log).

**Механизм видимости:** Транзакция видит версию строки, если `XMIN` зафиксирован (committed) до момента создания снимка, а `XMAX` либо равен 0, либо указывает на транзакцию, которая еще не была зафиксирована на момент снимка.

### Уровни изоляции транзакций в PostgreSQL

Реализация уровней изоляции в PostgreSQL более строгая, чем того требует стандарт ANSI SQL.

| Уровень | Особенности PostgreSQL | Решаемые аномалии |
| :--- | :--- | :--- |
| **Read Committed** | Снимок создается для **каждого оператора** (statement) внутри транзакции. Самый популярный уровень. | Грязное чтение (Dirty Read). |
| **Repeatable Read** | Снимок создается один раз в **начале транзакции**. В PostgreSQL на этом уровне **невозможны фантомные чтения**, что выше требований стандарта. | Неповторяющееся чтение, Фантомы, Потерянные обновления. |
| **Serializable** | Использует предикатные блокировки (SIREAD) для обнаружения аномалий сериализации. При обнаружении конфликта транзакция откатывается с ошибкой `40001`. | Все аномалии параллелизма, включая **Write Skew**. |

**Важно:** Уровень `Read Uncommitted` в PostgreSQL работает как `Read Committed`, так как архитектура MVCC исключает возможность чтения грязных (незафиксированных) данных в принципе.

## Иерархия блокировок

### Блокировки таблиц (Table-Level Locks)
PostgreSQL использует 8 уровней блокировок таблиц. Основное правило: блокировки одного уровня могут быть совместимы между собой, но конфликтовать с уровнями выше.

| Режим | Типичные команды | Конфликтует с |
| :--- | :--- | :--- |
| **ACCESS SHARE** | `SELECT` | ACCESS EXCLUSIVE |
| **ROW SHARE** | `SELECT FOR SHARE/UPDATE` | EXCLUSIVE, ACCESS EXCLUSIVE |
| **ROW EXCLUSIVE** | `INSERT`, `UPDATE`, `DELETE` | SHARE, SHARE ROW EXCL, EXCL, ACCESS EXCL |
| **SHARE UPDATE EXCL** | `VACUUM` (без Full), `ANALYZE`, `CREATE INDEX CONCURRENTLY` | SHARE UPDATE EXCL и выше |
| **SHARE** | `CREATE INDEX` (обычный) | ROW EXCLUSIVE и выше |
| **SHARE ROW EXCL** | `CREATE TRIGGER`, некоторые формы `ALTER TABLE` | ROW EXCLUSIVE и выше |
| **EXCLUSIVE** | Блокирует запись, разрешает только чтение | ROW SHARE и выше |
| **ACCESS EXCLUSIVE** | `ALTER TABLE`, `DROP`, `TRUNCATE`, `VACUUM FULL` | Со всеми (даже `SELECT`) |

### Блокировки строк (Row-Level Locks)
Блокировки строк не хранятся в памяти (shared memory), а записываются непосредственно в заголовок строки (`infomask`). Это позволяет PostgreSQL удерживать миллионы блокировок строк без риска исчерпания памяти.

- **Multixacts (Multi-Transaction IDs)**: Если строку заблокировали несколько транзакций (например, через `FOR SHARE`), PostgreSQL создает специальный `MultiXID`. Чрезмерное количество `MultiXID` может привести к нагрузке на диск и риску **MultiXID Wraparound**. Подробный механизм очистки описан в **[Внутреннем устройстве VACUUM](./vacuum_internals.md#3-multixacts-и-multixid-wraparound)**.

### Подтранзакции (Subtransactions)
Использование `SAVEPOINT` или исключений в PL/pgSQL создает подтранзакции. 
**Внимание:** Большое количество активных подтранзакций (более 64) приводит к переполнению кеша блокировок (Subtransaction Cache), после чего каждая проверка видимости начинает требовать обращения к диску, что вызывает резкую деградацию производительности всего кластера.

## Практические сценарии

### Высокопроизводительные очереди (SKIP LOCKED)
Позволяет воркерам выбирать задачи, которые еще не захвачены другими процессами, исключая ожидание на блокировках.
```sql
BEGIN;
SELECT id FROM jobs 
WHERE status = 'pending' 
FOR UPDATE SKIP LOCKED 
LIMIT 1;
-- Выполнение работы...
DELETE FROM jobs WHERE id = :id;
COMMIT;
```

### Координация задач (Advisory Locks)
Прикладные блокировки для управления логикой. Бывают сессионными (до конца подключения) и транзакционными (до `COMMIT`).
```sql
-- Транзакционная блокировка: освободится при COMMIT/ROLLBACK
SELECT pg_advisory_xact_lock(1001);

-- Сессионная попытка: вернет false, если занято
SELECT pg_try_advisory_lock(1001);
```

### Борьба с "Idle in transaction"
Транзакции, которые открыты и «молчат», удерживают `XMIN`, препятствуя `VACUUM` удалять мертвые строки. Это главная причина Bloat.
**Решение:** Настройка `idle_in_transaction_session_timeout` (например, 30s) для автоматического обрыва таких сессий.

### Диагностика через Wait Events
Начиная с PG 9.6, представление `pg_stat_activity` содержит колонки `wait_event_type` и `wait_event`. Позволяет понять, какого именно ресурса ждет процесс.
- `Lock`: Ожидание тяжелой блокировки (таблица/строка).
- `LWLock` (Lightweight Lock): Ожидание доступа к структурам в памяти. 
    - `WALWriteLock`: Запись в WAL.
    - `CLOGControlLock`: Доступ к Commit Log (SLRU). Возникает при экстремально высоком TPS.
    - `BufferContentLock`: Конкуренция за конкретную страницу в Shared Buffers.
- `IO`: Ожидание чтения/записи на диск (например, `DataFileRead`).

Подробный разбор критических событий и способов их устранения см. в **[Шпаргалке по Wait Events](../Operations/observability.md#шпаргалка-по-критическим-wait-events)**.

### Диагностика очереди блокировок
Запрос для поиска PID, который блокирует остальные процессы:
```sql
SELECT 
    blocked_activity.pid AS blocked_pid,
    blocking_activity.pid AS blocking_pid,
    blocked_activity.query AS blocked_query,
    blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks AS blocked_locks
JOIN pg_catalog.pg_stat_activity AS blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks AS blocking_locks 
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.DATABASE IS NOT DISTINCT FROM blocked_locks.DATABASE
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity AS blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.GRANTED;
```

## Поиск и устранение неисправностей

| Проблема | Диагностика | Решение |
| :--- | :--- | :--- |
| **Зависание SELECT** | Проверка `pg_locks` на наличие `AccessExclusiveLock`. | Поиск миграций или `VACUUM FULL`, удерживающих таблицу. |
| **Рост Bloat при Autovacuum ON** | Поиск долгоживущих транзакций в `pg_stat_activity`. | Завершение сессий (kill) или настройка таймаутов. |
| **Частые Deadlocks** | Анализ логов сервера PostgreSQL. | Изменение порядка обновления таблиц в коде приложения. |
| **Всплески CPU при блокировках** | Анализ `LWLock` в Wait Events. | Проверка нагрузки на WAL или переполнение кеша подтранзакций. |

## Дополнительная информация

### Рекомендации
- **lock_timeout**: Всегда устанавливайте `lock_timeout` в сессиях, выполняющих DDL-миграции, чтобы не блокировать очередь запросов к базе.
- **Минимальный охват**: Держите транзакции максимально короткими. Не выполняйте внешние HTTP-запросы или тяжелые вычисления внутри транзакций БД.
- **Индексация внешних ключей**: Отсутствие индекса на Foreign Key может приводить к избыточным блокировкам строк в родительской таблице при изменении дочерней.
