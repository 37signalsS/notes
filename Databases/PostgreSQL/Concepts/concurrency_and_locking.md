# Конкурентность и блокировки в PostgreSQL

**Актуально для:** PostgreSQL 13–18

## Определения

- **MVCC (Multi-Version Concurrency Control)** — механизм управления конкурентным доступом, при котором каждое изменение строки создаёт её новую версию. Читающие транзакции работают со «замороженным» снимком данных, не блокируя пишущие, и наоборот.
- **Уровень изоляции (Isolation Level)** — параметр транзакции, определяющий степень строгости правил видимости изменений, внесённых параллельными транзакциями. По умолчанию — `read committed` (`default_transaction_isolation`).
- **Снимок данных (Snapshot)** — структура с информацией о состоянии активных транзакций в момент начала запроса или транзакции. Определяет, какие версии строк (tuples) видимы.
- **Предикатная блокировка (Predicate Lock, `SIReadLock`)** — внутренний маркер SSI, фиксирующий, какие данные прочитала Serializable-транзакция. Не блокирует другие транзакции и не может стать причиной взаимоблокировки — служит только для обнаружения аномалий сериализации.
- **Взаимоблокировка (Deadlock)** — тупиковая ситуация, при которой две и более транзакции ожидают ресурсов, удерживаемых друг другом в циклической зависимости.
- **Рекомендательные блокировки (Advisory Locks)** — прикладные блокировки, управляемые пользователем. Не привязаны к строкам таблиц и используются для координации логики приложения (например, предотвращение одновременного запуска фоновых задач).
- **Очередь блокировок (Lock Queue)** — механизм управления доступом к ресурсу (таблице). Блокировки выстраиваются в очередь. Если запрос в начале очереди требует эксклюзивного доступа (например, `ALTER TABLE`), он заблокирует все последующие запросы, включая простые `SELECT`.
- **SSI (Serializable Snapshot Isolation)** — реализация уровня Serializable в PostgreSQL, основанная на отслеживании зависимостей между транзакциями для обнаружения циклов аномалий (например, Write Skew) без жёстких блокировок чтения.
- **Fastpath-блокировки** — блокировки, захваченные в быстром пути (per-backend), минуя общую таблицу менеджера блокировок. Снижают конкуренцию при большом количестве коротких транзакций; видны в `pg_locks` с `fastpath = true`.
- **Конфликт репликации (Hot Standby Conflict)** — ситуация, когда применение WAL-записи на реплике несовместимо с запросами, выполняемыми на ней в режиме чтения; реплика вынуждена отменить запрос или задержать применение WAL.

## Базовые концепции

### Внутреннее устройство MVCC

PostgreSQL хранит версии строк непосредственно в страницах данных (heap). Каждая версия строки (tuple) содержит служебный заголовок с полями:
- **XMIN**: Идентификатор транзакции (XID), которая создала данную версию строки.
- **XMAX**: Идентификатор транзакции, которая удалила или обновила строку (создав новую версию). Если строка актуальна, `XMAX` равен 0.
- **CID (Command ID)**: Порядковый номер команды внутри транзакции для обеспечения видимости собственных изменений.
- **CTID**: Указатель на физическое местоположение версии строки (номер страницы и смещение). При обновлении `CTID` старой версии указывает на новую.
- **Infomask**: Набор бит (hint bits), кэширующий статус транзакций (зафиксирована, отменена), чтобы не обращаться к SLRU-журналу коммитов при каждой проверке видимости.

**Механизм видимости:** Транзакция видит версию строки, если `XMIN` зафиксирован (committed) до момента создания снимка, а `XMAX` либо равен 0, либо указывает на транзакцию, ещё не зафиксированную на момент снимка.

### Уровни изоляции транзакций в PostgreSQL

Стандарт SQL определяет четыре запрещённых феномена: грязное чтение, неповторяющееся чтение, фантомное чтение и аномалия сериализации. Реализация уровней изоляции в PostgreSQL более строгая, чем требует стандарт ANSI SQL:

| Уровень | Грязное чтение | Неповторяющееся чтение | Фантомы | Аномалия сериализации |
| :--- | :--- | :--- | :--- | :--- |
| **Read Uncommitted** | возможно, но не в PG | возможно | возможно | возможно |
| **Read Committed** (дефолт) | невозможно | возможно | возможно | возможно |
| **Repeatable Read** | невозможно | невозможно | невозможно в PG | возможно |
| **Serializable** | невозможно | невозможно | невозможно | невозможно |

**Read Committed** — снимок создаётся для **каждого оператора** внутри транзакции. `UPDATE`/`DELETE`/`SELECT FOR UPDATE`, нашедшие строку, изменённую concurrent-транзакцией, дожидаются её коммита и затем **переоценивают условие `WHERE` на обновлённой версии строки** (если обновлённая строка уже не подходит под условие, она пропускается). Это даёт высокую пропускную способность, но команда со сложными условиями поиска может видеть несогласованный снимок: эффекты concurrent-обновлений на тех же строках видны, а на других строках — нет.

**Repeatable Read** — снимок создаётся один раз в **начале транзакции** (на первом неконтрольном операторе). В PostgreSQL на этом уровне **невозможны фантомные чтения**, что выше требований стандарта. Уровень реализован как Snapshot Isolation: он предотвращает все феномены таблицы, кроме аномалий сериализации. Если транзакция пытается изменить или заблокировать строку, изменённую другой транзакцией после начала своей, она откатывается с ошибкой `could not serialize access due to concurrent update` — приложение должно повторить всю транзакцию целиком. Повтора требуют только пишущие транзакции: read-only транзакции конфликтов не имеют.

**Serializable** — работает как Repeatable Read, плюс отслеживает зависимости «чтение→запись» между concurrent-транзакциями через предикатные блокировки (см. раздел SSI). При обнаружении аномалии одна из транзакций откатывается с ошибкой `could not serialize access due to read/write dependencies among transactions` (SQLSTATE `40001`).

**Важно:**
- Уровень `Read Uncommitted` в PostgreSQL работает как `Read Committed`, так как архитектура MVCC исключает возможность чтения грязных (незафиксированных) данных в принципе. Внутри реализовано только три различных уровня.
- Изменения последовательностей (`nextval`, `serial`-колонки) не являются транзакционными: они видны всем немедленно и не откатываются.
- Установка уровня: `SET TRANSACTION ISOLATION LEVEL ...` (внутри транзакции) или `default_transaction_isolation` в конфигурации.
- **Serializable недоступен на hot standby** — попытка его установить в режиме восстановления вызывает ошибку.

### Иерархия блокировок

#### Блокировки таблиц (Table-Level Locks)

PostgreSQL использует 8 режимов блокировок таблиц. Захватить явно можно командой `LOCK TABLE ... IN <mode> MODE`; без указания режима `LOCK TABLE` берёт `ACCESS EXCLUSIVE`. Блокировка удерживается до конца транзакции, но освобождается немедленно при откате к SAVEPOINT и при выходе из блока `EXCEPTION` в PL/pgSQL.

| Режим | Типичные команды | Конфликтует с |
| :--- | :--- | :--- |
| **ACCESS SHARE** | `SELECT` | ACCESS EXCLUSIVE |
| **ROW SHARE** | `SELECT FOR UPDATE / NO KEY UPDATE / SHARE / KEY SHARE` | EXCLUSIVE, ACCESS EXCLUSIVE |
| **ROW EXCLUSIVE** | `INSERT`, `UPDATE`, `DELETE`, `MERGE` | SHARE, SHARE ROW EXCL, EXCL, ACCESS EXCL |
| **SHARE UPDATE EXCL** | `VACUUM` (без Full), `ANALYZE`, `CREATE INDEX CONCURRENTLY`, `CREATE STATISTICS`, `COMMENT ON`, `REINDEX CONCURRENTLY`, некоторые формы `ALTER INDEX`/`ALTER TABLE` | SHARE UPDATE EXCL и выше |
| **SHARE** | `CREATE INDEX` (обычный), `REINDEX` (обычный — блокирует запись, не чтение; ACCESS EXCLUSIVE — на самом индексе) | ROW EXCLUSIVE и выше |
| **SHARE ROW EXCL** | `CREATE TRIGGER`, некоторые формы `ALTER TABLE` | ROW EXCLUSIVE и выше (self-exclusive: только одна сессия) |
| **EXCLUSIVE** | `REFRESH MATERIALIZED VIEW CONCURRENTLY` | ROW SHARE и выше (только чтение параллельно) |
| **ACCESS EXCLUSIVE** | `ALTER TABLE`, `DROP`, `TRUNCATE`, `VACUUM FULL`, `CLUSTER`, `REFRESH MATERIALIZED VIEW` | Со всеми (даже `SELECT`) |

**Ключевое правило:** только `ACCESS EXCLUSIVE` блокирует обычный `SELECT` (без `FOR UPDATE/SHARE`).

#### Блокировки строк (Row-Level Locks)

Четыре режима, задаваемые в блокирующей клаузе `SELECT`:

| Запрашиваемый режим | Текущий `FOR KEY SHARE` | `FOR SHARE` | `FOR NO KEY UPDATE` | `FOR UPDATE` |
| :--- | :--- | :--- | :--- | :--- |
| **FOR KEY SHARE** | — | — | — | конфликт |
| **FOR SHARE** | — | — | конфликт | конфликт |
| **FOR NO KEY UPDATE** | — | конфликт | конфликт | конфликт |
| **FOR UPDATE** | конфликт | конфликт | конфликт | конфликт |

- `FOR UPDATE` — самый сильный; блокирует всех конкурентов. Его же берёт `DELETE` и `UPDATE`, изменяющий колонки с уникальным индексом, пригодным для внешнего ключа.
- `FOR NO KEY UPDATE` — обычный `UPDATE`, не трогающий ключевые колонки; не блокирует `FOR KEY SHARE`.
- `FOR SHARE` — разделяемый; блокирует запись, но не другие разделяемые блокировки.
- `FOR KEY SHARE` — самый слабый; берётся операциями с внешними ключами (проверка ссылочной целостности на родительской таблице). Именно поэтому отсутствие индекса на FK-колонке приводит к избыточным блокировкам строк в родительской таблице.

Блокировки строк не хранятся в shared memory, а записываются непосредственно в заголовок строки (`infomask`). PostgreSQL не хранит в памяти информацию о заблокированных строках, поэтому **количество одновременно заблокированных строк не ограничено**; побочный эффект — блокирование строки может вызвать запись на диск (`SELECT FOR UPDATE` модифицирует заголовок строки).

- **Multixacts (Multi-Transaction IDs)**: Если строку заблокировали несколько транзакций (например, через `FOR SHARE`), PostgreSQL создаёт специальный `MultiXID`. Чрезмерное количество `MultiXID` может привести к нагрузке на диск и риску **MultiXID Wraparound**. Подробный механизм очистки описан в **[Внутреннем устройстве VACUUM](./vacuum_internals.md#3-multixacts-и-multixid-wraparound)**.

#### Блокировки страниц (Page-Level Locks)

На уровне страниц буферного пула используются разделяемые/исключающие блокировки для контроля чтения/записи страниц. Они освобождаются сразу после получения или изменения строки и обычному приложению не видны.

#### Рекомендательные блокировки (Advisory Locks)

Прикладные блокировки с определяемым пользователем смыслом. Система не контролирует их использование — за корректность отвечает приложение. Бывают двух уровней:

- **Сессионные** (`pg_advisory_lock`, `pg_try_advisory_lock`) — держатся до явного освобождения (`pg_advisory_unlock`, `pg_advisory_unlock_all`) или завершения сессии. **Не подчиняются транзакционной семантике**: откат транзакции не освобождает блокировку, а освобождение действует даже если транзакция позже упадёт. Блокировка реентерабельна: каждый запрос блокировки требует соответствующего запроса освобождения.
- **Транзакционные** (`pg_advisory_xact_lock`, `pg_try_advisory_xact_lock`) — освобождаются автоматически в конце транзакции, явного освобождения нет.

Ключ — либо один `bigint`, либо пара `int` (`pg_advisory_lock(key1, key2)`). Сессионные и транзакционные запросы на один ключ блокируют друг друга; повторный запрос той же сессии всегда успешен. В `pg_locks` блокировки видны как `locktype = 'advisory'`: для одноключевой формы старшая половина ключа — в `classid`, младшая — в `objid`, `objsubid = 1`; для двухключевой `classid = key1`, `objid = key2`, `objsubid = 2`. Advisory locks локальны для базы данных.

И обычные, и рекомендательные блокировки хранятся в общем пуле памяти, размер которого определяется `max_locks_per_transaction` и `max_connections`. Предел — обычно десятки-сотни тысяч блокировок; его исчерпание приводит к ошибке `out of shared memory`. Advisory locks быстрее флага в таблице, не создают bloat и автоматически очищаются сервером в конце сессии.

**Ловушка с `LIMIT`:** порядок вычисления выражений не гарантирует, что `LIMIT` применится до вызова функции блокировки — `SELECT pg_advisory_lock(id) FROM foo WHERE id > 12345 LIMIT 100;` может захватить больше блокировок, чем ожидалось (они останутся «висеть» до конца сессии). Безопасная форма — подзапрос:
```sql
SELECT pg_advisory_lock(q.id) FROM
  (SELECT id FROM foo WHERE id > 12345 LIMIT 100) q;  -- ok
```

#### Подтранзакции (Subtransactions)

Использование `SAVEPOINT` или блоков `EXCEPTION` в PL/pgSQL создаёт подтранзакции. Идентификаторы подтранзакций (sub-XID) кэшируются per-backend; транзакция с более чем 64 подтранзакциями считается «длинноживущей» с точки зрения снапшотов:

- **Hot standby:** наличие write-транзакции с более чем 64 подтранзакциями **задерживает начало приёма read-only подключений** на реплике до завершения самой длинной write-транзакции (это задокументированное ограничение hot standby).
- Подтранзакции имеют накладные расходы; глубокое вложение в горячих циклах (тысячи SAVEPOINT'ов) следует избегать.

### Serializable Snapshot Isolation (SSI)

SSI отслеживает, какие данные прочитала каждая Serializable-транзакция, с помощью предикатных блокировок. Ключевые свойства:

- Предикатные блокировки **никого не блокируют** и не могут привести к взаимоблокировке — они только фиксируют зависимости для обнаружения аномалий.
- Видны в `pg_locks` с `mode = 'SIReadLock'`.
- Размер таблицы предикатных блокировок ограничен: `max_pred_locks_per_transaction` (дефолт 64), `max_pred_locks_per_relation` (дефолт -2, т.е. `max_pred_locks_per_transaction/2`), `max_pred_locks_per_page` (дефолт 2). При нехватке памяти мелкие блокировки (tuple/page) объединяются в покрывающие всю таблицу — это повышает частоту ошибок сериализации; лечение — рост указанных параметров (требуется перезапуск).
- `SERIALIZABLE READ ONLY DEFERRABLE` — единственный случай, когда Serializable блокирует, а Repeatable Read нет: транзакция ждёт снимка, гарантированно свободного от проблем, после чего не нуждается в предикатных блокировках.
- Read-only Serializable-транзакции часто вообще не берут предикатных блокировок.

Оптимизация Serializable-транзакций (по документации): объявлять `READ ONLY`, где возможно; контролировать число соединений; не включать в транзакцию лишнее; не оставлять соединения `idle in transaction`; убирать явные `LOCK`/`FOR UPDATE`, которые SSI уже защищает; поощрять index-сканы (seq scan всегда требует relation-level предикатной блокировки) через `random_page_cost`/`cpu_tuple_cost`.

### Взаимоблокировки: обнаружение и профилактика

PostgreSQL автоматически обнаруживает deadlocks и прерывает одну из транзакций (какая именно — непредсказуемо, на это нельзя полагаться). Механика:

- Ожидающий блокировку процесс ждёт `deadlock_timeout` (дефолт **1s**), и только затем запускает относительно дорогую проверку цикла в графе ожиданий. Значение должно в идеале превышать типичное время транзакции; на нагруженных серверах его поднимают, а при отладке блокировок — понижают.
- Без обнаружения deadlock ожидающий ждёт **бесконечно** — поэтому нельзя держать транзакции открытыми долго (например, в ожидании ввода пользователя).
- Deadlock может возникнуть и на row-level блокировках без какого-либо явного `LOCK` (две транзакции обновляют одни и те же строки в разном порядке).
- `log_lock_waits = on` (дефолт **off** в PG 13–18; в PG 19 изменён на **on**) логирует ожидание блокировки, длившееся дольше `deadlock_timeout`, с указанием блокирующего процесса и SQL-оператора — основной инструмент диагностики конкуренции за блокировки.
- Счётчик `pg_stat_database.deadlocks` — метрика для мониторинга и алертинга.

Показательный фрагмент лога (иллюстративный):
```
LOG:  process 4231 deadlock detected
DETAIL:  Process holding the lock: 4231. Wait queue: 4232.
STATEMENT:  UPDATE accounts SET balance = balance - 100.00 WHERE acctnum = 22222;
```

**Профилактика (по документации):** единый порядок захвата объектов во всём приложении; первый захват объекта — в самом строгом из нужных режимов; короткие транзакции; обработка на лету — повтор прерванных транзакций.

## Практические сценарии

**Требования:** `psql` с двумя сессиями к одной базе; для просмотра чужих сессий в `pg_stat_activity` (непривилегированный пользователь видит полностью только свои сессии, в строках чужих большинство колонок NULL) требуется роль `pg_read_all_stats` или суперпользователь; `pg_terminate_backend` — права суперпользователя (или владельца сессии).

### Высокопроизводительные очереди (SKIP LOCKED)

`SKIP LOCKED` (доступен с PostgreSQL 9.5) пропускает уже заблокированные строки вместо ожидания или ошибки (`NOWAIT` — ошибка). Это повышает параллелизм выборки, но **не реализует exactly-once** и не заменяет идемпотентность, lease/visibility timeout или компенсацию внешних эффектов: `SKIP LOCKED` даёт непоследовательное представление данных и годится только для очередеподобных нагрузок.

Особенности (по документации): `NOWAIT`/`SKIP LOCKED` применяются только к row-level блокировкам — табличный `ROW SHARE` лок берётся обычным образом (для table-level без ожидания — `LOCK TABLE ... NOWAIT`); при `LIMIT` блокирование прекращается, как только набрано достаточно строк, но строки, пропущенные `OFFSET`, всё равно блокируются.

```sql
BEGIN;
SELECT id FROM jobs
WHERE status = 'pending'
ORDER BY id
FOR UPDATE SKIP LOCKED
LIMIT 1;
-- Выполнение работы...
DELETE FROM jobs WHERE id = :id;
COMMIT;
```

### Координация задач (Advisory Locks)

```sql
-- Транзакционная блокировка: освободится при COMMIT/ROLLBACK
SELECT pg_advisory_xact_lock(1001);

-- Сессионная попытка: вернет false, если занято
SELECT pg_try_advisory_lock(1001);
-- ...работа...
SELECT pg_advisory_unlock(1001);       -- явное освобождение
SELECT pg_advisory_unlock_all();       -- все сессионные блокировки сессии
```

Выбор уровня: для коротких критических секций удобны транзакционные блокировки (автоосвобождение, безопасны при откате); сессионные — для долгоживущих «мастер-локов» (например, единственный воркер рассылки), но требуют явного освобождения и **опасны при транзакционном пулинге** (PgBouncer `transaction`): блокировка привязана к серверному соединению, а не к клиентской сессии — детали и режимы пулинга в **[Настройке PgBouncer](../Operations/pgbouncer_setup.md)**.

### Борьба с "Idle in transaction"

Транзакции, которые открыты и «молчат», удерживают `XMIN`, препятствуя `VACUUM` удалять мёртвые строки. Это главная причина Bloat. Даже без значимых блокировок открытая транзакция мешает уборке недавно-умерших строк, видных только ей.

Одна из самых коварных причин состояния **Idle in transaction** — «долгоживущие» транзакции в бизнес-джобах. Типичный антипаттерн: приложение открывает транзакцию, выполняет первый `SELECT`, затем начинает тяжёлую бизнес-логику (вызовы внешних API, обработка данных, очереди сообщений), и только после неё выполняет следующий `SELECT` и в конце — `COMMIT`. Всё это время на задействованных таблицах висит `AccessShareLock`, и любая попытка `ALTER TABLE` застревает на нём.

**Диагностика** (возраст транзакции и её `xmin`-горизонт):
```sql
SELECT pid, usename, application_name, state,
       now() - xact_start AS xact_age,
       now() - query_start AS query_age,
       backend_xmin
FROM pg_stat_activity
WHERE state IN ('idle in transaction', 'idle in transaction (aborted)')
ORDER BY xact_age DESC NULLS LAST;
-- → pid | usename | application_name |        state         | xact_age | query_age | backend_xmin
-- →  4231 | app     | billing-job      | idle in transaction  | 00:14:32 | 00:00:01  | 74821
```

**Решение:**
1. **Минимизируйте транзакцию:** Закрывайте транзакцию (`COMMIT`) сразу после каждого запроса. Лучше сделать 100 отдельных `SELECT`-ов только тогда, когда они нужны, и не держать транзакцию в состоянии `idle in transaction`, удерживая `AccessShareLock`.
2. **`idle_in_transaction_session_timeout`:** Настройка автоматического обрыва сессий в состоянии `idle in transaction` (дефолт 0 — отключено; например, 30s–5min). Сначала почините старые запросы, которые создают это состояние. Полное руководство по управлению соединениями — в **[Управление соединениями PostgreSQL](../Operations/connection_management.md)**. В PostgreSQL 17 добавлен смежный `transaction_timeout` — лимит общей длительности транзакции (не затрагивает prepared transactions; если он меньше или равен `idle_in_transaction_session_timeout` либо `statement_timeout`, более долгий таймаут игнорируется).

```sql
-- В postgresql.conf или ALTER SYSTEM
ALTER SYSTEM SET idle_in_transaction_session_timeout = '30s';
SELECT pg_reload_conf();
```

### Сценарий: Каскад блокировок при миграции (Lock Queue Cascade)

Этот сценарий иллюстрирует, как одна долгая транзакция приводит к каскадному зависанию всей базы данных при запуске миграции.

**Ситуация:** CD-пайплайн запускает миграцию — обычный `ALTER TABLE`, который должен пройти за считанную секунду. Но он зависает, и приходит алерт: прод перестал отвечать на запросы.

**Механизм:** Каждый `SELECT` создаёт `AccessShareLock` на задействованные таблицы. Это самый нестрогий лок — он не конфликтует с другими запросами и локами. Единственный лок, который блокирует `SELECT`, это `AccessExclusiveLock`, создаваемый при `ALTER TABLE`, `DROP`, `TRUNCATE` и т.д.

**Пример:** Долгий `SELECT` (60 секунд) держит `AccessShareLock`. Затем прилетает `ALTER TABLE`, который запрашивает `AccessExclusiveLock`, встает в очередь за предыдущей транзакцией и ждет ее завершения. Все последующие запросы к этим таблицам также встают в очередь за миграцией.

```
10:00:00 — Большой SELECT с кучей JOIN-ов на 60 секунд
           AccessShareLock взят

10:00:10 — ALTER TABLE запускается (нужен AccessExclusiveLock)
           Встал в очередь, ждет окончания SELECT

10:00:11 — Обычный SELECT от приложения
           Встал в очереди ЗА миграцией

10:00:13 — SELECT, INSERT, SELECT, UPDATE...
           Все в очереди!

10:01:00 — Первый SELECT закончился
           ALTER TABLE начал выполняться (5 секунд)

10:01:05 — Миграция завершилась
           Очередь разблокировалась
```

**Особенно опасен idle-in-transaction:** если в момент миграции работает фоновая джоба, которая долго держит открытой транзакцию с `AccessShareLock`, миграция не просто ждет — она становится самой блокирующей, и весь последующий трафик сваливается в очередь. Если таблица популярная — прод ляжет надолго.

**Профилактика на уровне миграций:** Запускайте DDL через `PGOPTIONS="-c lock_timeout=5s"`. Если миграция не получает блокировку за 5 секунд, она упадет с ошибкой, а очередь не нарастит. `lock_timeout` (дефолт 0 — отключен) ограничивает каждую отдельную попытку захвата блокировки — явную (`LOCK TABLE`, `SELECT FOR UPDATE` без `NOWAIT`) и неявную; ставить его в `postgresql.conf` не рекомендуется, так как он повлияет на все сессии.

```bash
# CD-пайплайн
PGOPTIONS="-c lock_timeout=5s" psql -h $DB_HOST -U $DB_USER $DB_NAME \
  -c "ALTER TABLE users ADD COLUMN bio TEXT;"
```

**Перенос read-запросов на реплику:** Долгие аналитические `SELECT`-ы с кучей JOIN-ов можно перенести на read-реплику. Это устраняет конкуренцию за `AccessShareLock` на мастере, где DDL выполняется. Однако учитывайте задержку репликации (replication lag) — для критичных транзакций чтение с реплики недопустимо.

### Конфликты на реплике (Hot Standby Conflicts)

На реплике WAL применять обязаны, поэтому конфликты разрешаются в ущерб запросам реплики:

- `ACCESS EXCLUSIVE` на мастере (явный `LOCK` и DDL: `DROP`, `TRUNCATE`, `ALTER TABLE` и др.) конфликтует с обращениями к таблице в запросах реплики.
- Запись VACUUM-очистки конфликтует со снапшотами репликационных транзакций (видимые им мёртвые строки) и со страницами, читаемыми запросами.
- `DROP TABLESPACE` / `DROP DATABASE` на мастере конфликтует с временными файлами / сессиями на реплике (сессии при `DROP DATABASE` принудительно завершаются).

Параметры разрешения (на реплике): `max_standby_streaming_delay` / `max_standby_archive_delay` задают максимальную задержку применения WAL (отсчитывается от момента получения WAL на реплике). Если конфликтующий запрос не завершается за это время, он отменяется (обычно ошибкой отмены, повторяемой сразу в новой транзакции); если конфликт из-за блокировки, удерживаемой idle-транзакцией, — завершается вся сессия. Для HA-реплик ставят короткие задержки; для реплик с долгими аналитическими запросами — большие или `-1` (ждать вечно, эффект как у `statement_timeout` для других сессий).

`hot_standby_feedback = on` на реплике предотвращает удаление мастером недавно-умерших строк, нужных реплике — конфликты очистки исчезают, но на мастере растёт bloat; при частых подключениях/отключениях реплик дополнительно поднимают `max_standby_archive_delay`.

**Диагностика на реплике:** представление `pg_stat_database_conflicts` показывает число отмен и причины (`confl_lock`, `confl_snapshot`, `confl_bufferpin`, `confl_tablespace`, `confl_database`); `log_recovery_conflict_waits = on` логирует ожидание разрешения конфликта дольше `deadlock_timeout`. В `pg_locks` реплики виртуальная транзакция startup-процесса владеет всеми `AccessExclusiveLock`, применяемыми реплеем.

```sql
-- На реплике: статистика отмен запросов из-за конфликтов
SELECT * FROM pg_stat_database_conflicts WHERE datname = current_database();
-- → datname | confl_tablespace | confl_database | confl_lock | confl_snapshot | confl_bufferpin
-- → mydb    |                0 |              0 |         12 |             34 |             0
```

### Диагностика через Wait Events

Начиная с PG 9.6, представление `pg_stat_activity` содержит колонки `wait_event_type` и `wait_event`. Позволяет понять, какого именно ресурса ждет процесс. Типы событий: `Activity`, `BufferPin`, `Client`, `Extension`, `IO`, `IPC`, `Lock`, `LWLock`, `Timeout`.

- `Lock` (тяжёлая блокировка): события `relation`, `page`, `tuple`, `transactionid` (ожидание завершения другой транзакции — типичное ожидание row-level блокировки), `advisory`, `object`, `extend`, `frozenid`, `virtualxid`, `spectoken`, `userlock`.
- `LWLock` (доступ к структурам в памяти):
    - `BufferMapping`: конкуренция за поиск буфера в буферном пуле; `BufferContent`: конкуренция за конкретную страницу в Shared Buffers.
    - `LockManager` / `LockFastPath`: конкуренция за менеджер тяжёлых блокировок / быстрый путь — признак чрезмерной конкуренции за табличные блокировки при высоком TPS.
    - `MultiXactOffsetSLRU` / `MultiXactMemberSLRU`, `MultiXactGen`: давление multixactов.
    - `CommitTsSLRU` / `CommitTsBuffer` (в версиях ≤17 — `CLOG*`): доступ к SLRU-журналу статусов коммитов. Возникает при экстремально высоком TPS.
    - `NotifyQueue`, `NotifySLRU`: конкуренция за очередь `LISTEN`/`NOTIFY`.
- `IO`: Ожидание чтения/записи на диск (например, `DataFileRead`).

Подробный разбор критических событий и способов их устранения см. в **[Шпаргалке по Wait Events](../Operations/observability.md#шпаргалка-по-критическим-wait-events)**.

### Диагностика очереди блокировок

**Рекомендуемый способ (с PG 9.6):** функция `pg_blocking_pids(pid)` возвращает массив PID сессий, блокирующих данную — как «жёстких» (удерживают конфликтующий лок), так и «мягких» (стоят впереди в очереди на конфликтующий лок). Для параллельных запросов возвращаются видимые клиенту PID лидеров групп, поэтому дубликаты возможны. Документация рекомендует её, а не self-join `pg_locks`: ручной join должен сам кодировать матрицу конфликтов и не видит порядка в очереди ожидания.

```sql
SELECT pid, usename, application_name, state, wait_event, wait_event_type,
       pg_blocking_pids(pid) AS blocked_by
FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
-- →  pid | usename | application_name | state  | wait_event | wait_event_type | blocked_by
-- → 4232 | app     | order-api        | active | transactionid | Lock        | {4231}
```

Расширенный вариант с деталями блокировок (`pg_locks` содержит одну строку на комбинацию «объект × режим × процесс»; `granted = false` — ожидаемая блокировка, `waitstart` — начало ожидания, `fastpath = true` — быстрый путь):
```sql
SELECT blocked_activity.pid AS blocked_pid,
       blocking_activity.pid AS blocking_pid,
       blocked_locks.mode AS blocked_lock_mode,
       blocking_locks.mode AS blocking_lock_mode,
       blocked_activity.query AS blocked_query,
       blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks AS blocked_locks
JOIN pg_catalog.pg_stat_activity AS blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks AS blocking_locks
    ON blocking_locks.locktype = blocked_locks.locktype
    AND blocking_locks.DATABASE IS NOT DISTINCT FROM blocked_locks.DATABASE
    AND blocking_locks.relation IS NOT DISTINCT FROM blocked_locks.relation
    AND blocking_locks.pid != blocked_locks.pid
JOIN pg_catalog.pg_stat_activity AS blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.GRANTED;
```

Особенности `pg_locks`, важные для диагностики:
- View **глобальный** (весь кластер); join `relation` → `pg_class.oid` корректен только для текущей базы.
- Row-level блокировки хранятся на диске и в view обычно не видны: ожидающий строки процесс виден как ожидающий `transactionid` держащего её транзакции.
- Процесс может ожидать **не более одной** блокировки одновременно.
- Подготовленные транзакции (`pg_prepared_xacts`) продолжают удерживать захваченные блокировки до завершения — источник «бесхозных» очередей.
- Частый опрос `pg_locks` ненадолго блокирует менеджер блокировок — не превращайте его в высокочастотный мониторинг.
- Статистика кэшируется до конца транзакции: для свежих данных в интерактивном анализе используйте `pg_stat_clear_snapshot()`.

## Поиск и устранение неисправностей

| Проблема | Диагностика | Решение |
| :--- | :--- | :--- |
| **Зависание SELECT** | `pg_blocking_pids(pid)`; `pg_locks` на наличие ожидаемого `AccessExclusiveLock`. | Поиск миграций, `VACUUM FULL`, `CLUSTER`, `REFRESH MATERIALIZED VIEW`, удерживающих таблицу. |
| **Каскад блокировок при миграции** | `ALTER TABLE` висит в очереди, а все последующие запросы тоже висят (см. **[сценарий каскада блокировок](#сценарий-каскад-блокировок-при-миграции-lock-queue-cascade)**). | Убедитесь, что `lock_timeout` установлен для DDL-сессий. Завершите долгоживущие транзакции (`idle in transaction`) через `pg_terminate_backend`. |
| **Рост Bloat при Autovacuum ON** | Долгоживущие транзакции и их `backend_xmin` в `pg_stat_activity`. | Завершение сессий (kill) или настройка `idle_in_transaction_session_timeout`. |
| **Частые Deadlocks** | `pg_stat_database.deadlocks`, логи (`deadlock detected`), `log_lock_waits = on`. | Единый порядок обновления таблиц/строк в коде приложения; повтор прерванных транзакций. |
| **Ошибка `40001` / `could not serialize access`** | Повторяющиеся откаты на RR/Serializable. | Повторить всю транзакцию целиком; сократить длительность транзакций; для Serializable — поднять `max_pred_locks_per_transaction` (если мелкие предикатные блокировки сворачиваются в relation-level), поощрять index-сканы. |
| **Запросы на реплике отменяются** | `pg_stat_database_conflicts` на реплике; `log_recovery_conflict_waits`. | Настроить `max_standby_streaming_delay`; включить `hot_standby_feedback` (ценой bloat на мастере); переносить долгие запросы со свежих реплик. |
| **`out of shared memory` при захвате блокировок** | Утечка сессионных advisory locks (`pg_locks`, `locktype = 'advisory'`); много открытых prepared transactions. | Освободить `pg_advisory_unlock_all()` / завершить сессии; поднять `max_locks_per_transaction` (требуется перезапуск, и на репликах значение должно быть ≥ мастера). |
| **Всплески CPU при блокировках** | Анализ `LWLock` в Wait Events (`BufferMapping`, `BufferContent`, `LockManager`, `MultiXact*SLRU`). | Снижение конкуренции за буферный пул (индексы, batching), снижение TPS на одну таблицу, проверка давления multixactов. |
| **Подтранзакции задерживают подключения на реплике** | Длинная write-транзакция с >64 подтранзакциями на мастере (`pg_stat_activity`). | Разбить транзакцию / уменьшить число SAVEPOINT'ов; после её завершения read-only подключения возобновятся. |

## Лучшие практики

- **`lock_timeout`**: Всегда устанавливайте `lock_timeout` в сессиях, выполняющих DDL-миграции, чтобы не блокировать очередь запросов к базе (через `PGOPTIONS` или `SET LOCAL`).
- **Минимальный охват:** Держите транзакции максимально короткими. Не выполняйте внешние HTTP-запросы или тяжелые вычисления внутри транзакций БД.
- **Индексация внешних ключей:** Отсутствие индекса на FK-колонке приводит к избыточным блокировкам строк в родительской таблице при изменении дочерней (`FOR KEY SHARE` превращается в более тяжёлые ожидания).
- **Единый порядок захватов:** Все конкурентные пути кода должны захватывать объекты (таблицы, строки, advisory-ключи) в одном порядке; первый захват — в самом строгом нужном режиме.
- **Повтор вместо паники:** Приложения на RR/Serializable и вообще в конкурентной среде должны уметь повторять транзакцию при `40001` и deadlock-ошибках (с экспоненциальной задержкой).
- **Таймауты на всех уровнях:** `statement_timeout` для прикладных сессий, `idle_in_transaction_session_timeout` против зависших транзакций, `lock_timeout` для DDL; ни один из них по умолчанию не включён (0).
- **Мониторинг:** алерт на рост `pg_stat_database.deadlocks`; `log_lock_waits = on` в проде (в PG 19 включён по умолчанию); периодический опрос `pg_blocking_pids`-запроса из предыдущего раздела.
- **Advisory keys:** проектируйте пространство ключей осознанно (пара `int32` удобнее для неймспейсов: `pg_advisory_lock(app_id, resource_id)`); сессионные блокировки — только с явным освобождением.

### Очистка и откат изменений

```sql
-- Прервать ожидающий запрос (текущий оператор), но оставить сессию
SELECT pg_cancel_backend(4232);
-- Завершить сессию целиком (освобождает все её блокировки)
SELECT pg_terminate_backend(4232);
-- Освободить все сессионные advisory-блокировки текущей сессии
SELECT pg_advisory_unlock_all();
```

Для экспериментов с `LOCK TABLE`/advisory locks: `ROLLBACK` освобождает табличные и транзакционные блокировки (но **не** сессионные advisory), `DISCARD ALL` сбрасывает состояние сессии. После тестов с `ALTER SYSTEM` — верните параметр и `SELECT pg_reload_conf()`.
