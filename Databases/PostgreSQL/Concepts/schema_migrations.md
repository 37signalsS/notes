# Миграция схем баз данных

### Определения

* **Миграция схемы:** Упорядоченный, версионируемый процесс изменения структуры базы данных (например, добавление таблиц или колонок).
* **Откат миграции (Rollback):** Процесс отмены примененных изменений для возврата схемы к предыдущему состоянию.

### Основные концепции

#### Подходы к управлению схемой

* **Императивный подход:** Схема изменяется с помощью последовательности SQL-скриптов (миграций), каждый из которых описывает конкретное изменение (`ALTER TABLE ...`). Этим подходом пользуются традиционные инструменты, такие как Flyway и Liquibase.
* **Декларативный подход:** Описывается **желаемое конечное состояние** схемы, а инструмент сам определяет, какие изменения необходимо внести для его достижения. Это ключевая особенность современных инструментов, таких как Atlas и SchemaHero.

#### Стратегии безопасного отката

1. **Обратные миграции (Reversible Migrations):**
    * **Подход:** Для каждой "прямой" миграции (`up`) пишется "обратная" (`down`), которая логически отменяет ее изменения (например, `CREATE TABLE` ↔ `DROP TABLE`). Это самый надежный способ для production-сред.
    * **Проблема:** Ручное написание `down`-миграций трудоемко и подвержено ошибкам, поэтому современные инструменты автоматизируют этот процесс.

2. **Snapshots и PITR (для не-production сред):**
    * **Снимки томов (Volume Snapshots):** Создание снимка диска (PVC) перед миграцией в тестовой среде.
    * **Point-in-Time Recovery (PITR):** Восстановление базы на момент времени до начала миграции с помощью [архивирования WAL-журналов](./backup_and_recovery.md).

### Инструменты и практические сценарии

#### Обзор инструментов

* **Традиционные (императивные):**
  * **Flyway:** Популярен в Java-экосистеме. Управляет SQL-скриптами.
  * **Liquibase:** Более мощный, чем Flyway. Поддерживает изменения в форматах SQL, XML, YAML, JSON.
* **Современные (декларативные):**
  * **Bytebase:** Инструмент с веб-интерфейсом в стиле "Git для баз данных".
  * **SchemaHero:** Kubernetes-оператор для декларативного управления схемами.
  * **Atlas:** Мощный open-source инструмент, поддерживающий оба подхода.

#### Пример рабочего процесса с Atlas

**Atlas** — современный языково-независимый инструмент для автоматизации управления миграциями.

##### Декларативный режим (Schema-as-Code)

1. **Инспекция схемы:** Существующая схема БД сохраняется в виде HCL-файла.

    ```bash
    # Сохранить схему текущей базы в файл schema.hcl
    atlas schema inspect -u "postgres://user:pass@host:5432/dbname?sslmode=disable" > schema.hcl
    ```

2. **Применение изменений:** Atlas сравнивает `schema.hcl` с реальной базой, автоматически генерирует SQL и применяет его, предварительно проверив на временной БД в Docker.

    ```bash
    atlas schema apply -u "postgres://..." --to "file://schema.hcl" --dev-url "docker://postgres/15"
    ```

##### Версионируемый режим (управление файлами миграций)

Этот режим похож на Flyway, но с автоматической генерацией SQL.

1. **Генерация файла миграции:** Atlas генерирует SQL-файл на основе разницы между желаемым и текущим состоянием схемы.

    ```bash
    # Создать SQL-файл для новой миграции
    atlas migrate diff add_title_column --dir "file://migrations" --dev-url "docker://postgres/15" --to "file://schema.hcl"
    ```

2. **Применение миграции:**

    ```bash
    atlas migrate apply -u "postgres://..." --dir "file://migrations"
    ```

3. **Автоматический откат (Rollback):** Atlas умеет автоматически применять обратные миграции.

    ```bash
    # Откатить последнюю примененную миграцию
    atlas migrate apply -u "postgres://..." --dir "file://migrations" --revert 1
    ```

##### Kubernetes Operator

Atlas предоставляет **оператор для Kubernetes**, что позволяет реализовать GitOps-подход: схема БД (`schema.hcl`) хранится в Git, а оператор автоматически применяет изменения к базе данных при обновлении Custom Resource `AtlasSchema`.

### Дополнительная информация

#### Интеграция с CI/CD

Инструменты миграции полностью интегрируются в CI/CD пайплайны:

1. **CI (на Pull Request):** Автоматически запускается проверка (`--dry-run`) и генерация миграции.
2. **CD (при мерже в main):** Сгенерированные миграции последовательно применяются к `staging` и `production` окружениям.
