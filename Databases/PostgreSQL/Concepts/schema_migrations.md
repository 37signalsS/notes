# Миграции схем в PostgreSQL

## Определения

- **Транзакционный DDL** — возможность выполнения команд изменения структуры (Data Definition Language) внутри транзакции. В PostgreSQL почти все DDL-команды (кроме создания индексов конкурентно) атомарны.
- **Блокировка таблицы (Table Lock)** — механизм предотвращения конфликтов при изменении схемы. Большинство DDL-операций требуют `ACCESS EXCLUSIVE`, блокируя даже чтение из таблицы.
- **Идемпотентность** — свойство миграции, позволяющее запускать её повторно без ошибок и изменения конечного состояния (например, через `IF NOT EXISTS`).
- **Zero Downtime Migration** — стратегия изменения схемы без остановки приложения и блокировки пользовательских запросов.

## Базовые концепции

### Транзакционность и исключения
PostgreSQL поддерживает транзакционный DDL, что позволяет откатить изменения схемы при ошибке. Однако существуют команды, которые **запрещено** выполнять внутри транзакции:
- `CREATE INDEX CONCURRENTLY`
- `REINDEX CONCURRENTLY`
- `VACUUM`
- `ALTER TYPE ... ADD VALUE` (в версиях до PostgreSQL 12)

### Иерархия блокировок
При выполнении миграций важно понимать тип захватываемой блокировки. 
- **ACCESS EXCLUSIVE**: Блокирует чтение и запись. Захватывается при `ALTER TABLE`, `DROP TABLE`, `TRUNCATE`.
- **SHARE UPDATE EXCLUSIVE**: Не блокирует чтение и запись. Захватывается при `CREATE INDEX CONCURRENTLY`, `ANALYZE`, `ALTER TABLE ... VALIDATE CONSTRAINT`.

Подробности в разделе **[Блокировки в PostgreSQL](./concurrency_and_locking.md)**.

## Практические сценарии

### Безопасное управление таймаутами
Чтобы миграция не «подвесила» всю базу, ожидая блокировки, необходимо всегда устанавливать таймауты в сессии миграции:

```sql
-- Ожидать блокировку не более 5 секунд
SET lock_timeout = '5s';
-- Прервать выполнение, если сама миграция длится более 30 секунд
SET statement_timeout = '30s';

ALTER TABLE orders ADD COLUMN status TEXT;
```

### Создание индексов без простоев (Zero Downtime)
Использование флага `CONCURRENTLY` позволяет строить индекс, не блокируя запись в таблицу.

```sql
-- Важно: нельзя запускать внутри транзакции (BEGIN/COMMIT)
CREATE INDEX CONCURRENTLY idx_users_email ON users(email);
```

### Безопасное добавление NOT NULL
На больших таблицах `ALTER TABLE ... SET NOT NULL` вызывает полный скан таблицы под `ACCESS EXCLUSIVE`. Безопасный путь (PostgreSQL 12+):

1. Добавить `CHECK` ограничение как `NOT VALID` (быстро, короткая блокировка).
2. Выполнить `VALIDATE CONSTRAINT` (длительный скан, но **без блокировки записи**).
3. Установить `SET NOT NULL` (мгновенно, так как база использует проверенный `CHECK` ограничение).

```sql
ALTER TABLE orders ADD CONSTRAINT orders_amount_not_null 
CHECK (amount IS NOT NULL) NOT VALID;

ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_not_null;

ALTER TABLE orders ALTER COLUMN amount SET NOT NULL;
```

### Изменение типа данных без перезаписи
Многие изменения типов (например, `INT` -> `BIGINT` или увеличение длины `VARCHAR`) в старых версиях приводили к полной перезаписи таблицы. В современных версиях это оптимизировано, но для гарантированного отсутствия простоев при сложных изменениях используется паттерн **[Expand-Contract](../../Concepts/migrations/expand_contract.md)**:
1. Создание новой колонки с нужным типом.
2. Триггер на синхронизацию данных из старой в новую.
3. Фоновый перенос (backfill) исторических данных батчами.
4. Переключение приложения на новую колонку.
5. Удаление старой колонки.

### Инструменты миграций

| Инструмент | Преимущества для PostgreSQL |
| :--- | :--- |
| **Atlas** | Декларативный подход, встроенный линтинг на опасные операции (предупреждает о блокировках). |
| **Flyway** | Надежная поддержка транзакционного DDL, простота использования SQL-скриптов. |
| **Liquibase** | Поддержка сложных сценариев через XML/YAML, управление расширениями. |
| **Sqitch** | Не использует номера версий (теги), отлично подходит для сложных ветвлений. |
