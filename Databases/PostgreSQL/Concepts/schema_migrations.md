# Миграция схем баз данных

## Определения

*   **Миграция схемы:** Упорядоченный, версионируемый процесс изменения структуры базы данных (например, добавление таблиц или колонок).
*   **Откат миграции (Rollback):** Процесс отмены примененных изменений для возврата схемы к предыдущему состоянию.

## Основные концепции

### Подходы к управлению схемой

*   **Императивный подход:** Схема изменяется с помощью последовательности SQL-скриптов (миграций), каждый из которых описывает конкретное изменение (`ALTER TABLE ...`, `CREATE TABLE ...`). Большинство традиционных инструментов, таких как Flyway и Liquibase, используют этот подход.
*   **Декларативный подход:** Описывается **желаемое конечное состояние** схемы, а инструмент сам определяет, какие изменения необходимо внести для его достижения. Это ключевая особенность современных инструментов, таких как Atlas и SchemaHero.

### Стратегии безопасного отката

1.  **Обратные миграции (Reversible Migrations):**
    *   **Подход:** Для каждой "прямой" миграции (`up`) пишется "обратная" (`down`), которая логически отменяет ее изменения (например, `CREATE TABLE` ↔ `DROP TABLE`). Это самый надежный способ для production-сред, так как он не затрагивает данные, появившиеся после миграции.
    *   **Проблема:** Ручное написание `down`-миграций трудоемко и подвержено ошибкам. Современные инструменты автоматизируют этот процесс.

2.  **Snapshots и PITR (для не-production сред):**
    *   **Снимки томов (Volume Snapshots):** Перед применением миграции в тестовой среде делается снимок диска (PVC). В случае неудачи том восстанавливается из снимка.
    *   **Point-in-Time Recovery (PITR):** Восстановление базы на момент времени до начала миграции с помощью [архивирования WAL-журналов](./backup_and_recovery.md). Медленный, но надежный метод для тестовых окружений.

## Инструменты и практические сценарии

### Обзор инструментов

*   **Традиционные (императивные):**
    *   **Flyway:** Популярен в Java-экосистеме. Управляет SQL-скриптами, отслеживая их выполнение в специальной таблице.
    *   **Liquibase:** Более мощный, чем Flyway. Поддерживает изменения в форматах SQL, XML, YAML, JSON.
*   **Современные (декларативные):**
    *   **Bytebase:** Инструмент с веб-интерфейсом в стиле "Git для баз данных", ориентированный на совместную работу.
    *   **SchemaHero:** Kubernetes-оператор для декларативного управления схемами через YAML-манифесты.
    *   **Atlas:** Мощный open-source инструмент, поддерживающий как декларативный, так и версионируемый подходы.

### Пример рабочего процесса с Atlas

**Atlas** — современный языково-независимый инструмент, который автоматизирует управление миграциями.

#### Декларативный режим (Schema-as-Code)

Этот режим реализует концепцию "Инфраструктура как код" для баз данных.

1.  **Инспекция схемы:** Существующая схема БД "изучается" и сохраняется в виде декларативного HCL-файла.
    ```bash
    # Подключиться к базе и сохранить ее схему в файл schema.hcl
    atlas schema inspect -u "postgres://user:pass@host:5432/dbname?sslmode=disable" > schema.hcl
    ```

2.  **Декларативное изменение:** Разработчик редактирует файл `schema.hcl`, описывая желаемое состояние (например, добавляя новую колонку).

3.  **Применение изменений:** Atlas сравнивает `schema.hcl` с реальной базой, автоматически генерирует SQL и применяет его.
    ```bash
    # Применить изменения, симулировав их во временной БД в Docker
    atlas schema apply -u "postgres://..." --to "file://schema.hcl" --dev-url "docker://postgres/15"
    ```
    *   `--dev-url`: Ключевая особенность. Atlas использует временную БД для безопасной проверки миграции перед ее применением.

#### Версионируемый режим (управление файлами миграций)

Этот режим похож на Flyway, но с автоматической генерацией SQL.

1.  **Генерация файла миграции:** Atlas сравнивает желаемое состояние схемы (из HCL-файла) с текущим и генерирует SQL-файл миграции.
    ```bash
    # Создать SQL-файл для новой миграции с именем 'add_title_column'
    atlas migrate diff add_title_column --dir "file://migrations" --dev-url "docker://postgres/15" --to "file://schema.hcl"
    ```

2.  **Применение миграции:**
    ```bash
    atlas migrate apply -u "postgres://..." --dir "file://migrations"
    ```

#### Автоматический откат миграций (Rollback)

Atlas умеет **автоматически генерировать и применять обратные миграции**.
```bash
# Откатить последнюю примененную миграцию
atlas migrate apply -u "postgres://..." --dir "file://migrations" --revert 1
```

#### Kubernetes Operator

Atlas предоставляет **оператор для Kubernetes**, что позволяет реализовать GitOps-подход:
1.  Схема БД (`schema.hcl`) хранится в Git.
2.  При изменении схемы CI/CD-пайплайн обновляет Custom Resource `AtlasSchema` в Kubernetes.
3.  Оператор отслеживает этот ресурс и автоматически применяет изменения к базе данных.

## Дополнительная информация

### Интеграция с CI/CD

Инструменты миграции полностью интегрируются в CI/CD пайплайны:
1.  **CI (на Pull Request):** Автоматически запускается `atlas migrate diff` для генерации миграции и `atlas schema apply --dry-run` (или аналоги) для проверки корректности SQL.
2.  **CD (при мерже в main):** Сгенерированные миграции последовательно применяются к `staging` и `production` окружениям. При использовании Kubernetes-оператора этот шаг сводится к обновлению CR в Git.
