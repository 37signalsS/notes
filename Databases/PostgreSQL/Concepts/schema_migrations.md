# Миграции схем в PostgreSQL

## Определения

- **Транзакционный DDL** — возможность выполнения команд изменения структуры (Data Definition Language) внутри транзакции. В PostgreSQL почти все DDL-команды (кроме создания индексов конкурентно) атомарны и могут быть откачены.
- **Блокировка таблицы (Table Lock)** — механизм предотвращения конфликтов. Большинство DDL-операций требуют `ACCESS EXCLUSIVE`, блокируя даже чтение (`SELECT`).
- **Идемпотентность** — свойство миграции, позволяющее запускать её повторно без ошибок (использование `IF NOT EXISTS`, `IF EXISTS`).
- **Zero Downtime Migration** — стратегия изменения схемы без остановки приложения и длительных блокировок.
- **Online Schema Change** — выполнение миграции на «живой» базе данных без эксклюзивной блокировки всей таблицы на время операции.

## Базовые концепции

### Транзакционность и ограничения
PostgreSQL — одна из немногих СУБД с полноценной поддержкой транзакционного DDL. Это гарантирует, что при сбое в середине сложной миграции база не останется в промежуточном состоянии.

**Исключения (команды вне транзакций):**
- `CREATE INDEX CONCURRENTLY` / `DROP INDEX CONCURRENTLY`.
- `REINDEX CONCURRENTLY`.
- `VACUUM`.
- `ALTER TYPE ... ADD VALUE` (в версиях до PostgreSQL 12 выполнение внутри транзакции было ограничено).

### Управление блокировками
Даже быстрый `ALTER TABLE` может вызвать простой, если он ждет завершения долгого `SELECT`. Очередь блокировок в PostgreSQL работает по принципу FIFO: эксклюзивная блокировка в очереди заблокирует все последующие `SELECT`.

**Правило безопасности:** всегда устанавливайте `lock_timeout` в сессии миграции.
```sql
SET lock_timeout = '5s';
-- Если блокировка не получена за 5 секунд, миграция упадет, не создав очередь
ALTER TABLE users ADD COLUMN bio TEXT;
```

## Практические сценарии

### Добавление колонок (PostgreSQL 11+)
Начиная с версии 11, добавление колонки с дефолтным значением (`DEFAULT`) больше не требует перезаписи всей таблицы и выполняется мгновенно.

```sql
-- Выполняется мгновенно даже на миллиардах строк
ALTER TABLE orders ADD COLUMN internal_comment TEXT DEFAULT 'none';
```

### Безопасное управление ограничениями (Constraints)
Добавление `NOT NULL` или `FOREIGN KEY` на большие таблицы под `ACCESS EXCLUSIVE` вызывает полный скан таблицы, блокируя работу.

**Безопасный путь для NOT NULL (PG 12+):**
1. Создать `CHECK` ограничение с флагом `NOT VALID`.
2. Выполнить `VALIDATE CONSTRAINT` (длительный скан без эксклюзивной блокировки).
3. Установить `SET NOT NULL` (мгновенно, так как база опирается на проверенный `CHECK`).

```sql
ALTER TABLE orders ADD CONSTRAINT orders_amount_not_null 
CHECK (amount IS NOT NULL) NOT VALID;

ALTER TABLE orders VALIDATE CONSTRAINT orders_amount_not_null;

ALTER TABLE orders ALTER COLUMN amount SET NOT NULL;
```

**Безопасный путь для Foreign Key:**
Аналогично: `ADD CONSTRAINT ... FOREIGN KEY ... NOT VALID`, затем `VALIDATE CONSTRAINT`.

### Работа с индексами
Стандартный `CREATE INDEX` блокирует запись в таблицу.

- **Построение:** используйте `CONCURRENTLY`. Это требует двух проходов по таблице и запрещено внутри транзакций.
- **Перестроение:** используйте `REINDEX INDEX CONCURRENTLY`. Полезно для устранения раздувания (Bloat) индекса без блокировки таблицы.
- **Инвалидация:** если построение `CONCURRENTLY` прервалось, индекс остается в состоянии `INVALID`. Его нужно удалить и создать заново.

### Идентичность и последовательности (Identity Columns)
В новых версиях (PG 10+) рекомендуется использовать `GENERATED AS IDENTITY` вместо `SERIAL`.
- `SERIAL` — это макрос, создающий отдельный объект `SEQUENCE`.
- `IDENTITY` — стандарт SQL, лучше интегрированный с правами доступа и упрощающий копирование схем.

### Миграции и логическая репликация
Встроенная логическая репликация в PostgreSQL **не реплицирует DDL**.
- При миграции схемы изменения должны быть применены сначала на подписчике (Subscriber), затем на издателе (Publisher).
- При несовпадении схем репликация может остановиться с ошибкой.

### Обслуживание после миграции
После массового изменения данных или структуры (например, добавление колонки с заполнением) рекомендуется выполнить `ANALYZE` для обновления статистики планировщика.

```sql
-- Обновление статистики без блокировки таблицы
ANALYZE VERBOSE users;
```

## Дополнительная информация

### Инструменты и линтинг
- **Strong Migrations**: Руководство и линтер (для Ruby, Go, Python), который проверяет миграции на наличие опасных операций (например, переименование колонок или добавление индексов без `CONCURRENTLY`).
- **Atlas / Flyway / Liquibase**: Позволяют автоматизировать процесс применения скриптов с контролем версий.

### Рекомендации
- Никогда не смешивайте DDL (изменение структуры) и DML (изменение данных) в одной миграции, если это не требуется логикой.
- Используйте паттерн **[Expand-Contract](../../Concepts/migrations/expand_contract.md)** для сложных переименований или смены типов данных.
- Проверяйте планы запросов после миграций, если изменилась кардинальность данных.
