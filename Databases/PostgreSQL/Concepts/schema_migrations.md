# Управление схемами и версионирование баз данных PostgreSQL

Управление изменениями в схеме базы данных (добавление таблиц, колонок, индексов) — одна из самых критически важных и "болезненных" задач в DevOps-цикле. Если управление состоянием самого кластера (реплики, бэкапы, пользователи) решается операторами, то эволюция схемы требует отдельных подходов и инструментов. Эффективные стратегии версионирования обеспечивают предсказуемость, возможность отката и полную интеграцию с CI/CD.

## Ключевые концепции

*   **Миграция схем:** Процесс применения изменений к структуре базы данных.
*   **Откат изменений (Rollback):</b> Возможность вернуть схему базы данных к предыдущему состоянию. Это самый сложный аспект, так как большинство инструментов хорошо умеют "накатывать" последнюю версию (`update-to-latest`), но не предлагают надежного механизма отката, особенно в бесплатных версиях.
*   **Декларативное управление:** Описание желаемого состояния схемы в конфигурационных файлах, а не через последовательность императивных SQL-скриптов. Это идеал, к которому стремятся в рамках парадигмы "Инфраструктура как код".

## Стратегии обеспечения безопасности миграций

### 1. Обратные миграции (Reversible Migrations)

Для production-сред самый надежный способ — это не восстановление из бэкапа (которое приведет к потере данных, появившихся после бэкапа), а выполнение **"обратной" миграции**, которая отменяет изменения, внесенные "прямой". Главная проблема в том, что многие инструменты не генерируют их автоматически, требуя от разработчиков написания и поддержки двух наборов скриптов (`up` и `down`), что усложняет процесс.

### 2. Snapshots и Point-in-Time Recovery (PITR) для тестовых сред

Для не-production окружений, где потеря данных не критична, можно использовать более простые стратегии отката.
*   **Снимки томов (Volume Snapshots):** Перед применением миграции в тестовой среде делается снимок диска (PersistentVolumeClaim). В случае неудачи кластер можно мгновенно "откатить", восстановив его из этого снимка.
*   **Point-in-Time Recovery (PITR):** С помощью непрерывного архивирования WAL-журналов, как описано в [стратегиях резервного копирования](./backup_and_recovery.md), можно восстановить базу на любой момент времени. В CI/CD пайплайне это можно автоматизировать: в случае сбоя миграции система может взять временную метку последнего успешного коммита в Git и запустить восстановление на этот момент.

## Инструменты для управления миграциями схем

Существует множество инструментов, часто привязанных к языкам программирования и фреймворкам (например, миграции в Django ORM, Hibernate, Doctrine). Однако для построения универсального, языково-независимого процесса лучше подходят самостоятельные утилиты.

Среди традиционных инструментов можно выделить **Liquibase** и **Flyway**. Они популярны, но часто считаются тяжеловесными и не всегда удобны в cloud-native окружениях.

Более современные инструменты фокусируются на декларативном подходе и тесной интеграции с Kubernetes.

### 1. Bytebase
*   **Описание:** Инструмент с веб-интерфейсом, позиционируемый как "Git для баз данных". Позволяет визуально управлять схемами, ролями и данными.
*   **Особенности:** Веб-интерфейс, поддержка множества СУБД, API для интеграции.
*   **Ограничения:** Продвинутый функционал (включая сложные сценарии отката) доступен в платных версиях.

### 2. SchemaHero
*   **Описание:** Инструмент, ориентированный на декларативное управление схемами через YAML-файлы в духе GitOps.
*   **Особенности:** Интеграция с Kubernetes через собственный оператор, который отслеживает изменения в YAML-манифестах и применяет их к базе.
*   **Ограничения:** Как и у многих, полноценный rollback может быть ограничен.

### 3. Atlas: Современный декларативный подход

**Atlas** — мощный и гибкий open-source инструмент, который быстро набирает популярность. Он является языково-независимым и поддерживает несколько режимов работы.

#### Декларативный режим (Schema Mode)

Этот режим идеально подходит для концепции "Инфраструктура как код".
1.  **Инспекция схемы:** Текущая схема БД "изучается" и сохраняется в виде декларативного HCL-файла (`.hcl` - HashiCorp Configuration Language).
    ```bash
    # Подключаемся к живой базе и сохраняем ее схему в файл
    atlas schema inspect -u "postgres://user:pass@host:5432/dbname?sslmode=disable" > schema.hcl
    ```
2.  **Декларативное изменение:** Разработчик редактирует файл `schema.hcl`, описывая желаемое состояние (например, добавляя новую таблицу или колонку).
3.  **Применение изменений:** Atlas сравнивает желаемое состояние из файла с реальным состоянием БД и автоматически генерирует и применяет необходимый SQL.
    ```bash
    # Применяем изменения из файла schema.hcl к базе данных
    atlas schema apply -u "postgres://..." --to-file schema.hcl --dev-url "docker://postgres/15"
    ```
    - `--dev-url "docker://postgres/15"`: Ключевая особенность. Atlas запускает временный Docker-контейнер с PostgreSQL, чтобы проверить и симулировать миграцию перед применением к реальной базе.

#### Версионируемый режим (Migration Mode)

Этот режим больше похож на традиционные инструменты, но с мощными возможностями автогенерации.
1.  **Генерация файла миграции:** Atlas сравнивает желаемое состояние схемы (из файла `.hcl`) с текущим состоянием (которое он хранит в специальной таблице `atlas_schema_revisions`) и генерирует SQL-файл миграции.
    ```bash
    # Создать новую миграцию с именем 'add_users_table'
    atlas migrate diff add_users_table --dir "file://migrations" --dev-url "docker://postgres/15" --to "file://schema.hcl"
    ```
    В результате в директории `migrations` появится SQL-файл, содержащий `CREATE TABLE ...`.
2.  **Применение миграции:**
    ```bash
    atlas migrate apply -u "postgres://..." --dir "file://migrations"
    ```

#### Откат миграций (Rollback)

Это одна из сильнейших сторон Atlas. Он умеет **автоматически генерировать обратные миграции**. Когда вы генерируете `diff`, Atlas создает не только `up` (вперед) миграцию, но и неявно понимает, как ее откатить. Для отката достаточно выполнить `apply` с указанием количества шагов назад.

```bash
# Откатить последнюю примененную миграцию
atlas migrate apply -u "postgres://..." --dir "file://migrations" --revert 1
```

#### Kubernetes Operator

Atlas имеет собственный **оператор для Kubernetes**. Это выводит GitOps-подход на новый уровень:
1.  Декларативное описание схемы (`schema.hcl` или SQL) хранится в Git.
2.  В кластере Kubernetes создается Custom Resource `AtlasSchema`.
3.  Оператор Atlas отслеживает этот ресурс. При изменении схемы в Git, CI/CD-пайплайн обновляет `AtlasSchema` в кластере.
4.  Оператор "видит" изменение и автоматически применяет его к целевой базе данных.

Таким образом, вся цепочка управления схемой становится полностью автоматизированной и декларативной.

#### Лицензирование

Atlas является open-source проектом. Его основные функции, включая CLI, генерацию миграций и оператор Kubernetes, бесплатны для использования. Платная версия (Atlas Cloud) предлагает дополнительные возможности, такие как веб-интерфейс для визуализации схемы, совместной работы и аудита.

### Сравнение с Liquibase/Flyway

Atlas представляет собой более современную и гибкую альтернативу, особенно в контексте Kubernetes. В отличие от них, Atlas не только управляет SQL-скриптами, но и может **автоматически генерировать** их на основе декларативного описания схемы, а также **генерировать обратные миграции**, что значительно упрощает процесс. Глубокая интеграция с Kubernetes через оператор делает его идеальным выбором для cloud-native окружений.

## Интеграция с CI/CD

Инструменты, такие как Atlas, легко интегрируются в CI/CD пайплайны:
1.  **На стадии CI (Pull Request):** Автоматически запускается `atlas migrate diff` для генерации миграции. Можно также запустить `atlas schema apply --dry-run`, чтобы увидеть, какой SQL будет сгенерирован, и проверить его на ошибки.
2.  **На стадии CD (Merge в main):** Сгенерированные и проверенные миграции применяются к целевой базе данных (staging/production) командой `atlas migrate apply`. При использовании оператора достаточно обновить Custom Resource в Git.
