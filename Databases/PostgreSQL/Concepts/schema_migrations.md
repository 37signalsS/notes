# Управление схемами и версионирование баз данных

Управление изменениями в схеме базы данных — одна из самых критически важных задач в DevOps-цикле. Эффективные стратегии версионирования обеспечивают предсказуемость, возможность отката и полную интеграцию с CI/CD.

## 1. Определения

*   **Миграция схем:** Процесс применения изменений к структуре базы данных.
*   **Откат изменений (Rollback):</b> Возможность вернуть схему базы данных к предыдущему состоянию. Это самый сложный аспект, так как большинство инструментов хорошо умеют "накатывать" последнюю версию (`update-to-latest`), но не предлагают надежного механизма отката, особенно в бесплатных версиях.
*   **Декларативное управление:** Описание желаемого состояния схемы в конфигурационных файлах, а не через последовательность императивных SQL-скриптов. Это идеал, к которому стремятся в рамках парадигмы "Инфраструктура как код".

## 2. Основные концепции

В современной разработке изменения схемы БД должны проходить тот же жизненный цикл, что и код приложения: через систему контроля версий (Git), Pull Request'ы и автоматизированные пайплайны.

Ключевая проблема — обеспечить безопасное и, по возможности, автоматическое применение этих изменений на разные окружения (dev, staging, production) и, что еще важнее, иметь надежный план отката в случае сбоя.

## 3. Практические сценарии и инструменты

### 3.1. Стратегии безопасного отката

1.  **Обратные миграции (Reversible Migrations):**
    *   **Подход:** Для каждой "прямой" миграции (`up`) пишется "обратная" (`down`), которая отменяет ее изменения. Это самый надежный способ для production-сред, так как он не затрагивает данные, появившиеся после миграции.
    *   **Проблема:** Многие инструменты не генерируют `down`-миграции автоматически, что усложняет разработку.

2.  **Snapshots и PITR для не-production сред:**
    *   **Снимки томов (Volume Snapshots):** Перед применением миграции в тестовой среде делается снимок диска (PVC). В случае неудачи кластер можно мгновенно "откатить".
    *   **Point-in-Time Recovery (PITR):** Восстановление базы на момент времени до начала миграции с помощью [архивирования WAL-журналов](./backup_and_recovery.md).

### 3.2. Инструменты для управления миграциями

Существует множество инструментов, от привязанных к фреймворкам (Django migrations, Hibernate) до языково-независимых.

*   **Традиционные:** **Liquibase** и **Flyway** — популярные, но часто считаются тяжеловесными для cloud-native окружений.
*   **Современные (декларативные):**
    *   **Bytebase:** Инструмент с веб-интерфейсом, "Git для баз данных".
    *   **SchemaHero:** Kubernetes-оператор для декларативного управления схемами через YAML.
    *   **Atlas:** Мощный open-source инструмент с поддержкой декларативного и версионируемого подходов.

### 3.3. Пример рабочего процесса с Atlas

**Atlas** — языково-независимый инструмент, который может автоматически инспектировать схему, генерировать миграции и их откат.

Рассмотрим полный цикл внесения изменений в схему с помощью декларативного режима Atlas.

**1. Инспекция существующей схемы**

Предположим, у нас есть база данных с несколькими таблицами. Первым шагом мы "изучаем" её состояние и сохраняем в декларативный HCL-файл.

```bash
# Подключаемся к живой базе и сохраняем ее схему в файл
atlas schema inspect -u "postgres://user:pass@host:5432/dbname?sslmode=disable" > schema.hcl
```
В результате будет сгенерирован файл `schema.hcl`, описывающий все таблицы, колонки, индексы и другие объекты.

**2. Декларативное изменение схемы**

Далее мы редактируем полученный HCL-файл, чтобы описать желаемое состояние. Например, добавим новую колонку `title` в таблицу `orders`.

```hcl
// ... содержимое файла schema.hcl ...

table "orders" {
  schema = schema.public
  column "id" {
    null = false
    type = serial
  }
  column "amount" {
    null = false
    type = integer
  }
  // Добавляем новую колонку
  column "title" {
    null = false // Умышленно делаем ошибку для примера
    type = varchar(128)
  }
  primary_key {
    columns = [column.id]
  }
}

// ... остальное ...
```

**3. Применение изменений**

Теперь мы просим Atlas применить наши изменения. Atlas сам сравнит `schema.hcl` с реальной базой и сгенерирует нужный SQL.

```bash
atlas schema apply -u "postgres://..." --to "file://schema.hcl" --dev-url "docker://postgres/15"
```
*   `--dev-url "docker://postgres/15"`: Ключевая особенность. Atlas запускает временный Docker-контейнер с PostgreSQL для безопасной симуляции миграции и генерации SQL-кода перед его применением к реальной базе.

Atlas покажет план миграции:
```sql
-- Planned Changes:
-- Add column "title" to table "orders"
ALTER TABLE "public"."orders" ADD COLUMN "title" character varying(128) NOT NULL;
```

**4. Обработка ошибки и успешное применение**

При попытке применить этот план к таблице, где уже есть данные, PostgreSQL вернет ошибку, так как нельзя добавить колонку `NOT NULL` с default-значением `NULL`.

Atlas перехватит эту ошибку. Чтобы исправить, мы изменяем `schema.hcl`, сделав колонку nullable:
```hcl
  column "title" {
    null = true // Исправлено
    type = varchar(128)
  }
```

Запускаем команду `atlas schema apply` еще раз. Теперь миграция успешно применится.

Этот пример демонстрирует мощь декларативного подхода: мы описываем *что* хотим получить, а Atlas берет на себя генерацию SQL и безопасное применение изменений.

#### Декларативный режим (Schema Mode)

Этот режим идеально подходит для концепции "Инфраструктура как код".
1.  **Инспекция схемы:** Текущая схема БД "изучается" и сохраняется в виде декларативного HCL-файла (`.hcl` - HashiCorp Configuration Language).
    ```bash
    # Подключаемся к живой базе и сохраняем ее схему в файл
    atlas schema inspect -u "postgres://user:pass@host:5432/dbname?sslmode=disable" > schema.hcl
    ```
2.  **Декларативное изменение:** Разработчик редактирует файл `schema.hcl`, описывая желаемое состояние (например, добавляя новую таблицу или колонку).
3.  **Применение изменений:** Atlas сравнивает желаемое состояние из файла с реальным состоянием БД и автоматически генерирует и применяет необходимый SQL.
    ```bash
    # Применяем изменения из файла schema.hcl к базе данных
    atlas schema apply -u "postgres://..." --to-file schema.hcl --dev-url "docker://postgres/15"
    ```
    - `--dev-url "docker://postgres/15"`: Ключевая особенность. Atlas запускает временный Docker-контейнер с PostgreSQL, чтобы проверить и симулировать миграцию перед применением к реальной базе.

#### Версионируемый режим (Migration Mode)

Этот режим больше похож на традиционные инструменты, но с мощными возможностями автогенерации.
1.  **Генерация файла миграции:** Atlas сравнивает желаемое состояние схемы (из файла `.hcl`) с текущим состоянием (которое он хранит в специальной таблице `atlas_schema_revisions`) и генерирует SQL-файл миграции.
    ```bash
    # Создать новую миграцию с именем 'add_users_table'
    atlas migrate diff add_users_table --dir "file://migrations" --dev-url "docker://postgres/15" --to "file://schema.hcl"
    ```
    В результате в директории `migrations` появится SQL-файл, содержащий `CREATE TABLE ...`.
2.  **Применение миграции:**
    ```bash
    atlas migrate apply -u "postgres://..." --dir "file://migrations"
    ```

#### Откат миграций (Rollback)

Это одна из сильнейших сторон Atlas. Он умеет **автоматически генерировать обратные миграции**. Когда вы генерируете `diff`, Atlas создает не только `up` (вперед) миграцию, но и неявно понимает, как ее откатить. Для отката достаточно выполнить `apply` с указанием количества шагов назад.

```bash
# Откатить последнюю примененную миграцию
atlas migrate apply -u "postgres://..." --dir "file://migrations" --revert 1
```

#### Kubernetes Operator

Atlas имеет собственный **оператор для Kubernetes**. Это выводит GitOps-подход на новый уровень:
1.  Декларативное описание схемы (`schema.hcl` или SQL) хранится в Git.
2.  В кластере Kubernetes создается Custom Resource `AtlasSchema`.
3.  Оператор Atlas отслеживает этот ресурс. При изменении схемы в Git, CI/CD-пайплайн обновляет `AtlasSchema` в кластере.
4.  Оператор "видит" изменение и автоматически применяет его к целевой базе данных.

Таким образом, вся цепочка управления схемой становится полностью автоматизированной и декларативной.


## 4. Продвинутые детали: Интеграция с CI/CD

Инструменты, подобные Atlas, полностью интегрируются в CI/CD пайплайны:
1.  **CI (на Pull Request):** Автоматически запускается `atlas migrate diff` для генерации миграции и `atlas schema apply --dry-run` для проверки корректности SQL.
2.  **CD (при мерже в main):** Сгенерированные миграции применяются к `staging`, а после успешного тестирования — к `production`. При использовании **Kubernetes Operator** от Atlas, достаточно просто обновить Custom Resource в Git, и оператор сам применит изменения к базе данных.
