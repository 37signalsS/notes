# Архитектура PostgreSQL

## Определения

- **Экземпляр (Instance)**: Совокупность запущенных процессов PostgreSQL (`postmaster` и дочерние) и выделенной области оперативной памяти. Экземпляр управляет доступом к данным.
- **Кластер баз данных (Database Cluster)**: Набор баз данных, управляемый одним экземпляром и хранящийся в едином каталоге на диске (**PGDATA**).
- **Страница (Page)**: Минимальная единица хранения данных (по умолчанию 8 КБ). Все операции ввода-вывода происходят на уровне страниц.
- **Backend-процесс (postgres)**: Процесс, создаваемый для обслуживания конкретного клиентского подключения.

## Базовые концепции

### Процессная модель

PostgreSQL использует многопроцессную архитектуру (**Process-based**), что обеспечивает изоляцию соединений: крах одного процесса не приводит к падению всей СУБД.

1. **Postmaster (Supervisor)**: Главный процесс. Слушает порт, выполняет аутентификацию, порождает Backend-процессы и управляет восстановлением после сбоев.
2. **Служебные фоновые процессы (Background Processes)**:
   - **Checkpointer**: Выполняет контрольные точки (Checkpoints), сбрасывая "грязные" страницы из памяти на диск для сокращения времени восстановления.
   - **Background Writer (bgwriter)**: Асинхронно записывает страницы на диск, поддерживая наличие свободных буферов в памяти.
   - **WAL Writer**: Сбрасывает записи из WAL-буферов на диск для обеспечения **ACID**.
   - **Autovacuum Launcher**: Координирует работу процессов очистки (**Autovacuum Workers**) для удаления мертвых версий строк.
   - **Logger (syslogger)**: Собирает сообщения об ошибках и записывает их в файлы логов.
   - **Archiver**: Копирует заполненные сегменты WAL в архивное хранилище (используется для PITR и репликации).
   - **Logical Replication Launcher**: Управляет процессами логической репликации.
   - **Stats Collector** (до версии 15): Собирал статистику. В PostgreSQL 15+ заменен на механизм хранения статистики в общей памяти (**Shared Memory Stats**), что повысило производительность.

### Структуры памяти

#### Общая память (Shared Memory)
Доступна всем процессам экземпляра.
- **Shared Buffers**: Кэш страниц данных и индексов. Размер определяется параметром `shared_buffers`.
- **WAL Buffers**: Память для временного хранения записей журнала предзаписи перед записью на диск.
- **Caches (Syscache/Relcache)**: Кэши системного каталога и информации о таблицах, ускоряющие парсинг и планирование.

#### Локальная память процесса
Выделяется индивидуально для каждого Backend-процесса.
- **Work Mem**: Память для сортировок (`ORDER BY`, `DISTINCT`) и соединений (`JOIN`). Лимит задается параметром `work_mem` на одну операцию (один запрос может потреблять несколько таких блоков).
- **Maintenance Work Mem**: Ресурс для административных задач (`VACUUM`, `REINDEX`, `CREATE INDEX`).
- **Temp Buffers**: Используются для хранения временных таблиц в рамках сессии.

### Физическая структура хранения

Данные в **PGDATA** организованы иерархически:
1. **base/**: Содержит подкаталоги для каждой базы данных (имя каталога совпадает с OID базы).
2. **global/**: Хранит общие таблицы кластера (пользователи, роли, базы данных).
3. **pg_wal/**: Журналы предзаписи (WAL).
4. **pg_xact/**: Статусы транзакций (Commit Log).

**Служебные файлы таблиц:**
- **FSM (Free Space Map)**: Карта свободного места, помогает быстро найти страницу для вставки новой строки.
- **VM (Visibility Map)**: Карта видимости, используется для ускорения **Index Only Scan** и оптимизации работы `VACUUM`.

## Практические сценарии

### Жизненный цикл SQL-запроса

Процесс обработки запроса Backend-процессом:

1. **Парсинг (Parsing)**: Проверка синтаксиса и создание дерева разбора.
2. **Анализ и переписывание (Analysis & Rewriting)**: Проверка прав доступа и применение правил (Rules) для представлений (Views).
3. **Планирование (Planning)**: Поиск оптимального пути выполнения на основе стоимостной модели (**Cost-based Optimizer**) и статистики.
4. **Выполнение (Execution)**: Пошаговое исполнение плана с использованием методов доступа к данным.

### Оптимизация соединений

Поскольку модель "процесс на каждое соединение" потребляет много ресурсов, для масштабирования систем с тысячами клиентов используются внешние менеджеры очередей (Connection Poolers):
- **PgBouncer**: Легковесный, работает на уровне протокола PostgreSQL.
- **Odyssey**: Более сложный, с расширенными возможностями маршрутизации.
