# Архитектура PostgreSQL

## Определения

- **Экземпляр (Instance)**: Совокупность запущенных процессов PostgreSQL (`postmaster` и дочерние) и выделенной области оперативной памяти. Экземпляр управляет кластером баз данных.
- **Кластер баз данных (Database Cluster)**: Коллекция баз данных, управляемая одним экземпляром PostgreSQL и хранящаяся в едином каталоге на диске (`PGDATA`).
- **Страница (Page)**: Минимальная единица хранения и обмена данными между диском и оперативной памятью (по умолчанию 8 КБ).
- **Backend-процесс (postgres)**: Индивидуальный процесс, создаваемый для обслуживания одного клиентского подключения.

## Базовые концепции

### Процессная модель

PostgreSQL использует многопроцессную архитектуру, где каждый клиент обслуживается отдельным процессом ОС, что обеспечивает высокую изоляцию.

1. **Postmaster (Supervisor)**: Главный процесс, который прослушивает входящие соединения, порождает новые backend-процессы и координирует работу служебных процессов.
2. **Служебные фоновые процессы (Background Processes)**:
   - **Checkpointer**: Сбрасывает измененные ("грязные") страницы из памяти в файлы данных на диске во время контрольных точек (чекпоинтов).
   - **Background Writer (bgwriter)**: Асинхронно записывает часть измененных страниц на диск, чтобы освободить место в буферах и сгладить нагрузку на I/O.
   - **WAL Writer**: Сбрасывает записи из WAL-буфера на диск, обеспечивая долговечность транзакций.
   - **Autovacuum Launcher**: Запускает рабочие процессы для очистки "мертвых" строк и предотвращения раздувания (Bloat) таблиц.
   - **Stats Collector**: Собирает статистику об использовании таблиц, индексов и запросов.

### Структуры памяти

Память в PostgreSQL разделена на общую (Shared) и локальную для каждого процесса.

- **Общая память (Shared Memory)**:
  - **Shared Buffers (Буферный кэш)**: Самая важная часть памяти, где кэшируются страницы данных и индексов.
  - **WAL Buffers**: Временное хранилище записей журнала предзаписи перед их сбросом на диск.
- **Локальная память процесса**:
  - **Work Mem**: Память для операций сортировки и хэширования в рамках одного запроса.
  - **Maintenance Work Mem**: Память для административных задач (`VACUUM`, `CREATE INDEX`).

## Практические сценарии

### Жизненный цикл SQL-запроса

Прохождение запроса через backend-процесс:

1. **Парсинг (Parsing)**: Проверка синтаксиса и построение дерева разбора.
2. **Анализ и переписывание (Analysis & Rewriting)**: Проверка существования таблиц, прав доступа и применение правил (`Rules`).
3. **Планирование (Planning/Optimization)**: Оптимизатор на основе собранной статистики генерирует несколько планов выполнения и выбирает самый дешевый (наименее затратный по ресурсам).
4. **Выполнение (Execution)**: Исполнитель пошагово выполняет выбранный план и возвращает результат клиенту.

### Использование пула соединений

Поскольку создание процесса ОС на каждое подключение — дорогая операция, в высоконагруженных системах критически важно использовать пул соединений (Connection Pooler), такой как **PgBouncer** или **Odyssey**. Пул соединений позволяет:

- Снизить потребление памяти.
- Сократить время на установку соединения.
- Эффективно управлять сотнями и тысячами клиентских сессий при ограниченном количестве backend-процессов БД.
