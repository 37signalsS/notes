# Архитектура PostgreSQL

### Определения

*   **Сервер/Экземпляр (Server/Instance):** Процесс PostgreSQL (`postmaster` и его дочерние процессы), управляющий данными и принимающий клиентские подключения (по умолчанию на порту `5432` TCP).
*   **Кластер баз данных (Database Cluster):** В терминологии PostgreSQL это не кластер высокой доступности, а **набор баз данных**, управляемых одним экземпляром сервера.
*   **База данных (Database):** Именованный набор объектов SQL, хранящий данные. Один экземпляр PostgreSQL может управлять несколькими базами данных.
*   **Журнал WAL (Write-Ahead Log):** Фундаментальный механизм обеспечения долговечности (Durability) и целостности данных. Все изменения сначала записываются в WAL, находящийся на диске, и только затем применяются к файлам данных. Это основа для транзакционности, репликации и восстановления. Подробно концепция описана в SSoT-документе **[Журнал предзаписи (WAL)](../../Concepts/write_ahead_log.md)**.
*   **Индексы:** Вспомогательные структуры данных, которые позволяют ускорять поиск и сортировку, обеспечивая быстрый доступ к строкам таблицы.

### Основные концепции

#### Клиент-серверная архитектура и процессы

PostgreSQL использует многопроцессную модель:
*   **Postmaster:** Основной "управляющий" процесс, который запускается при старте сервера. Он отвечает за инициализацию, восстановление после сбоев, прослушивание входящих соединений и запуск фоновых процессов.
*   **Backend Process (postgres):** При подключении нового клиента `postmaster` создает для него отдельный дочерний процесс. Этот процесс обрабатывает все запросы от своего клиента, полностью изолируя его от других.
*   **Фоновые процессы (Background Processes):** Специализированные процессы, выполняющие служебные задачи. Ключевые из них:
    *   `Checkpointer`: Периодически записывает "грязные" (измененные) страницы данных из общей памяти на диск.
    *   `Background Writer (bgwriter)`: Помогает `checkpointer`, асинхронно записывая небольшие порции "грязных" страниц, чтобы снизить пиковую нагрузку на I/O во время чекпоинта.
    *   `Autovacuum Launcher`: Запускает процессы очистки таблиц от "мертвых" строк.
    *   `WAL Writer`: Сбрасывает записи WAL из буферов на диск.

#### Хранение данных и кэширование

*   **Страницы (Pages/Blocks):** Данные на диске хранятся в файлах, которые логически разделены на блоки фиксированного размера (обычно 8 КБ). Страница — минимальная единица дискового I/O.
*   **Буферный кэш (Shared Buffers):** Область общей памяти (RAM), выделяемая PostgreSQL для кэширования страниц данных и индексов. Это позволяет избежать медленных дисковых операций при частых обращениях к одним и тем же данным.
*   **Кэш операционной системы:** ОС также кэширует файловые операции, создавая дополнительный уровень кэширования между PostgreSQL и диском.

#### Пул соединений (Connection Pool)

Создание нового backend-процесса для каждого подключения является ресурсоемкой операцией. Для оптимизации в высоконагруженных системах используется **пул соединений** (например, PgBouncer). Это внешняя программа-прослойка, которая держит готовые соединения с PostgreSQL и выдает их клиентам по мере необходимости, ставя новые запросы в очередь.

### Практические сценарии

#### Выполнение запроса (Query Lifecycle)

Жизненный цикл SQL-запроса состоит из нескольких этапов:

1.  **Парсинг (Parsing):** Текстовый запрос преобразуется во внутреннюю древовидную структуру (parse tree). Проверяется синтаксис.
2.  **Анализ и переписывание (Analysis & Rewriting):** Система проверяет семантику (существование таблиц, колонок), разрешения и переписывает запрос, если он использует представления (VIEW) или правила (rules).
3.  **Планирование (Planning):** Планировщик запросов (Query Planner) генерирует несколько возможных планов выполнения запроса. На основе статистики о данных (`pg_statistic`) он выбирает наиболее "дешевый" (оптимальный) план, решая, какие индексы использовать, в каком порядке соединять таблицы и т.д.
4.  **Выполнение (Execution):** Исполнитель (Executor) выполняет выбранный план и возвращает результат клиенту.
