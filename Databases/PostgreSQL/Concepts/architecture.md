# Архитектура PostgreSQL

## Определения

- **Экземпляр (Instance)**: Совокупность запущенных процессов PostgreSQL (`postmaster` и дочерние) и выделенной области оперативной памяти. Экземпляр управляет доступом к данным и обеспечивает жизненный цикл СУБД.
- **Кластер баз данных (Database Cluster)**: Набор баз данных, управляемый одним экземпляром и хранящийся в едином корневом каталоге на диске (**PGDATA**).
- **Страница (Page)**: Минимальная единица хранения и обмена данными (по умолчанию 8 КБ). Все операции ввода-вывода (I/O) происходят на уровне страниц.
- **Backend-процесс (postgres)**: Индивидуальный процесс, создаваемый для обслуживания каждого клиентского подключения (модель process-per-connection).
- **TOAST (The Oversized-Attribute Storage Technique)**: Механизм хранения «широких» строк. Если данные строки не помещаются в страницу (обычно > 2 КБ), они сжимаются и/или выносятся во внетабличное хранилище.

## Базовые концепции

### Процессная модель

PostgreSQL использует многопроцессную архитектуру (**Process-based**), что обеспечивает изоляцию соединений: крах одного процесса не приводит к падению всей СУБД.

1. **Postmaster (Supervisor)**: Главный процесс. Слушает порт, выполняет аутентификацию, порождает Backend-процессы и координирует восстановление после сбоев.
2. **Служебные фоновые процессы (Background Processes)**:
   - **Checkpointer**: Выполняет контрольные точки (Checkpoints), сбрасывая «грязные» страницы из памяти на диск.
   - **Background Writer (bgwriter)**: Асинхронно записывает страницы на диск, поддерживая наличие свободных буферов в памяти.
   - **WAL Writer**: Сбрасывает записи из WAL-буферов на диск для обеспечения **ACID**.
   - **Autovacuum Launcher/Workers**: Очищают таблицы от «мертвых» версий строк. В **PG 17** работа с памятью оптимизирована через **TidStore** (потребляет до 20 раз меньше RAM).
   - **Walsummarizer (PG 17)**: Отслеживает измененные блоки для поддержки нативных инкрементальных бэкапов.
   - **Logger (syslogger)**: Собирает сообщения об ошибках и записывает их в файлы логов.
   - **Archiver**: Копирует сегменты WAL в архивное хранилище (используется для PITR и репликации).
   - **Shared Memory Stats (PG 16)**: Вся статистика теперь хранится в разделяемой памяти, отдельный процесс `Stats Collector` упразднен.

### Структуры памяти

#### Общая память (Shared Memory)
- **Shared Buffers**: Кэш страниц данных и индексов. Использует алгоритм **Clock Sweep** для определения страниц на вытеснение.
- **WAL Buffers**: Память для временного хранения журнальных записей.
- **Caches (Syscache/Relcache)**: Кэши системного каталога для ускорения парсинга.

#### Локальная память процесса
- **Work Mem**: Память для сортировок (`ORDER BY`) и соединений (`JOIN`).
- **Maintenance Work Mem**: Ресурс для `VACUUM`, `CREATE INDEX`. В **PG 17** лимит 1 ГБ для TID при вакууме снят.

### Физическая структура хранения (PGDATA)

Данные в **PGDATA** организованы иерархически. Пример структуры:
```bash
$ ls -F $PGDATA
base/               # Подкаталоги баз данных (идентификация по OID)
global/             # Общие таблицы (роли, БД)
pg_wal/             # Журналы предзаписи (WAL)
pg_xact/            # Статусы транзакций (Commit Log)
postgresql.conf     # Основной файл конфигурации
```

**Служебные файлы таблиц:**
- **FSM (Free Space Map)**: Помогает быстро найти свободное место в страницах для вставки (`INSERT`).
- **VM (Visibility Map)**: Ускоряет `VACUUM` и Index-Only Scan, помечая страницы, где все строки видимы всем транзакциям.

### Стратегии сортировки и хранения
PostgreSQL использует стратегию **пост-сортировки** (Post-sorting), что отличает его от баз с пред-сортировкой (MongoDB).

- **Признак пост-сортировки**: Наличие механизма **Vacuum**. СУБД не сортирует данные заранее, а помечает версии как мертвые при обновлениях (MVCC), требуя последующей очистки.

## Практические сценарии

### 1. Расчет параметров памяти (Sizing)

- **shared_buffers**: Рекомендуется устанавливать на уровне **25%** от общей RAM. 
  - *Пример:* Для сервера с 64 ГБ RAM → `shared_buffers = 16GB`.
- **work_mem**: Выделяется на каждую операцию. Расчет: `(Total RAM - shared_buffers) / (max_connections * 3)`.
  - *Пример:* Для 100 соединений при 64 ГБ RAM → `(64 - 16) / 300 ≈ 160MB`.

### 2. Жизненный цикл запроса и EXPLAIN

1. **Parser**: Разбор синтаксиса.
2. **Analyzer**: Применение правил и View.
3. **Planner**: Поиск оптимального пути.
4. **Executor**: Выполнение.

Для анализа плана используется `EXPLAIN ANALYZE`:
```sql
EXPLAIN (ANALYZE, BUFFERS) 
SELECT * FROM users WHERE id = 10;
-- → Index Scan using users_pkey on users (cost=0.29..8.31 rows=1 width=150)
-- → Buffers: shared hit=3
```

### 3. Анализ размера TOAST
Посмотреть размер TOAST-данных для конкретной таблицы:
```sql
SELECT relname AS table_name, 
       pg_size_pretty(pg_relation_size(reltoastrelid)) AS toast_size
FROM pg_class
WHERE relname = 'my_large_table';
```

### 4. Оптимизация соединений
Модель "процесс на соединение" дорога. Используйте пулеры:
- **PgBouncer**: Минимальный overhead, работа на уровне транзакций.
- **Odyssey**: Расширенная маршрутизация и многопоточность.
