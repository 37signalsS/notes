# Восстановление при повреждении данных (Corruption Recovery)

В данном документе рассматриваются методы диагностики, локализации и устранения физических и логических повреждений в структурах данных PostgreSQL.

## Определения

**Повреждение данных (Data Corruption)** — состояние, при котором физическое содержимое страниц базы данных на диске не соответствует ожидаемому формату или логическим правилам СУБД.

*   **Страница (Page):** Блок данных фиксированного размера (по умолчанию 8 КБ), базовая единица ввода-вывода и хранения в PostgreSQL.
*   **Контрольная сумма (Checksum):** Хеш-значение, вычисляемое для каждой страницы при записи на диск. Позволяет обнаружить искажение данных, возникшее на уровне ОС, ФС или оборудования.
*   **Bit rot (Тихая порча данных):** Самопроизвольное изменение битов на носителе информации, которое может годами оставаться незамеченным без регулярной проверки контрольных сумм.
*   **Partial Page Write (Разрыв страницы):** Ситуация, когда сбой питания происходит во время записи страницы, в результате чего на диске оказывается смесь старых и новых данных (лечится параметром `full_page_writes`).
*   **Логическое повреждение:** Нарушение связей между структурами (например, индекс ссылается на несуществующую строку в таблице), при этом физический формат страниц корректен.
*   **Повреждение CLOG (Commit Log):** Повреждение файлов в директории `pg_xact`, отвечающих за хранение статуса транзакций (зафиксирована/отменена). Часто приводит к невозможности чтения таблиц.

## Инструменты диагностики

### 1. amcheck (Логическая проверка)
Встроенное расширение для глубокой проверки целостности B-Tree индексов и их соответствия данным в таблицах (heap).

*   **Предпосылки:** Установка через `CREATE EXTENSION amcheck;`.
*   **Возможности:** Проверка связей "родитель-потомок", порядка ключей и наличия всех индексированных строк в таблице.

```sql
-- 1. Проверка конкретного индекса на базовую целостность
SELECT bt_index_parent_check('idx_users_id', true);

-- 2. Глубокая проверка всех индексов таблицы с верификацией соответствия куче (PG 14+)
-- Параметр heapallindexed = true проверяет, что КАЖДАЯ строка таблицы есть в индексе
SELECT bt_index_check(c.oid, true, true)
FROM pg_class c
JOIN pg_index i ON c.oid = i.indexrelid
WHERE i.indrelid = 'public.orders'::regclass;
```

### 2. pageinspect (Низкоуровневый анализ)
Позволяет читать содержимое страниц напрямую через SQL-запросы, минуя стандартные механизмы доступа.

```sql
CREATE EXTENSION pageinspect;

-- Просмотр заголовка страницы (Block 42 таблицы 'logs')
SELECT * FROM page_header(get_raw_page('logs', 42));

-- Детальный просмотр строк (items) на битой странице
-- Помогает определить xmin/xmax и понять, какие данные еще можно спасти
SELECT lp, t_ctid, t_xmin, t_xmax, t_infomask, t_data 
FROM heap_page_items(get_raw_page('logs', 42));
```

### 3. pg_checksums (Утилита командной строки)
Позволяет проверять, включать или отключать контрольные суммы в существующем кластере.

*   **Онлайн-проверка (PG 12+):** Можно запускать на работающем кластере для мониторинга (только чтение).
*   **Включение:** Требует полной остановки кластера.

```bash
# Проверка всего кластера на наличие ошибок контрольных сумм (без остановки)
pg_checksums --check --progress -D /var/lib/postgresql/data

# Включение контрольных сумм (требует остановки БД)
pg_ctl stop -D /var/lib/postgresql/data
pg_checksums --enable -D /var/lib/postgresql/data
pg_ctl start -D /var/lib/postgresql/data
```

### 4. pg_filedump
Внешняя утилита для анализа файлов PostgreSQL вне контекста запущенной СУБД. Позволяет декодировать блоки данных, даже если база не запускается.

```bash
# Форматированный вывод содержимого файла сегмента
pg_filedump -D /var/lib/postgresql/data -f base/16384/16385
```

## Сценарии восстановления

### 1. Физическое повреждение (Checksum Failure)
Симптом: Ошибка в логах `invalid page in block ... checksum verification failed`.

**Алгоритм действий:**
1.  **Локализация:** Определите имя таблицы по OID файла в сообщении об ошибке.
    ```sql
    SELECT relname FROM pg_class WHERE relfilenode = <filenode_из_логов>;
    ```
2.  **Анализ ОС:** Проверьте `dmesg`, `smartctl` и логи RAID-контроллера. Физические ошибки БД часто являются следствием деградации железа.
3.  **Экстренное извлечение:**
    ```sql
    -- Разрешить чтение страниц с неверными суммами (может вернуть мусор!)
    SET ignore_checksum_failure = on;
    -- Выгрузить данные в файл
    COPY (SELECT * FROM damaged_table) TO '/tmp/dump.csv';
    ```
4.  **Восстановление:**
    - Если поврежден индекс: `REINDEX TABLE damaged_table;`.
    - Если повреждена таблица: Создайте новую таблицу, залейте данные из CSV и пересоздайте связи.

### 2. Повреждение CLOG (pg_xact)
Симптом: Ошибки типа `could not access status of transaction` или `could not read from file "pg_xact/..."`.

**Решение:**
Если бэкапа нет, можно попытаться создать пустой файл CLOG нужного размера, заполненный нулями (это пометит все транзакции в этом диапазоне как "незавершенные/отмененные").
*Внимание: Это крайняя мера, приводящая к логической несогласованности.*

```bash
# Создание пустого сегмента CLOG (256 КБ)
dd if=/dev/zero of=/var/lib/postgresql/data/pg_xact/0XXX0000 bs=256k count=1
chown postgres:postgres /var/lib/postgresql/data/pg_xact/0XXX0000
chmod 600 /var/lib/postgresql/data/pg_xact/0XXX0000
```

### 3. Сброс WAL через pg_resetwal
Используется только если база не стартует из-за поврежденных журналов транзакций, а PITR невозможен.

**Важные флаги:**
- `-f` (force): Принудительное выполнение.
- `-o <next_oid>`: Установка следующего OID (если повреждены системные каталоги).
- `-x <next_xid>`: Установка следующего Transaction ID.

**Последовательность действий:**
1. Попытайтесь запустить `pg_resetwal -n` (dry run) для оценки изменений.
2. Выполните сброс: `pg_resetwal -f /var/lib/postgresql/data`.
3. Сразу после старта сделайте полный логический дамп (`pg_dumpall`).
4. **Удалите старый кластер и создайте новый** из дампа. Сброс WAL оставляет базу в неопределенном состоянии.

## Практические сценарии

### Сценарий: Профилактическое сканирование (Scrubbing)
Для предотвращения "тихой порчи" данных рекомендуется ежемесячно проверять контрольные суммы и индексы.

**Шаги:**
1. Запуск `pg_checksums --check`.
2. Запуск `amcheck` для всех таблиц:
```sql
DO $$
DECLARE
    r RECORD;
BEGIN
    FOR r IN SELECT indexrelid FROM pg_index i 
             JOIN pg_opclass o ON i.indclass[0] = o.oid 
             WHERE o.opcname = 'btree_ops' LOOP
        PERFORM bt_index_check(r.indexrelid, true);
    END LOOP;
END $$;
```

### Сценарий: Вырезание одной битой страницы
Если повреждена одна страница и `VACUUM` падает при её обработке, можно обнулить её через `dd`, чтобы PostgreSQL считал её пустой.

1. Найдите путь к файлу через `pg_relation_filepath('table_name')`.
2. Обнулите блок (например, блок 10, размер 8192):
```bash
dd if=/dev/zero of=<path_to_file> bs=8192 seek=10 count=1 conv=notrunc
```

## Стратегии предотвращения

1.  **data_checksums = on**: Фундаментальное требование. Включайте при `initdb`.
2.  **full_page_writes = on**: Защищает от разрыва страниц при сбоях питания. Выключать запрещено.
3.  **Изоляция WAL**: Выносите директорию `pg_wal` на отдельный физический диск или RAID 1.
4.  **ZFS/Btrfs**: Используйте файловые системы с самовосстановлением и контрольными суммами на уровне блоков.
5.  **Мониторинг логов:** Настройте оповещения на ключевые слова `checksum verification failed`, `PANIC`, `FATAL`.

## Поиск и устранение неисправностей

| Симптом | Вероятная причина | Первоочередное действие |
| :--- | :--- | :--- |
| `checksum verification failed` | Физический сбой I/O | Проверка `dmesg`, `ignore_checksum_failure = on` для спасения данных. |
| `could not read block ... from file` | Файл на диске меньше, чем ожидает БД | Проверка свободного места, восстановление из бэкапа. |
| `tuple concurrently updated` в пустом месте | Коррупция индекса | `REINDEX TABLE`. |
| `invalid xlog record at ...` | Повреждение WAL | `pg_resetwal` или восстановление из архива WAL. |
