# Внутреннее устройство VACUUM

## Определения

**VACUUM** — основной механизм PostgreSQL для управления пространством и предотвращения раздувания (Bloat), обусловленного архитектурой MVCC.

*   **Dead Tuple (Мертвый кортеж)** — старая версия строки, которая больше не видна ни одной активной транзакции. Физически остается в блоке до очистки.
*   **Line Pointer (Указатель строки / ItemID)** — 4-байтовый идентификатор в заголовке страницы, указывающий на начало кортежа. Имеет состояния: `LP_NORMAL` (живой), `LP_REDIRECT` (HOT-цепочка), `LP_DEAD` (ожидает очистки), `LP_UNUSED` (свободен).
*   **HOT (Heap Only Tuple) Updates** — оптимизация, позволяющая обновлять строку без создания новых записей в индексах, если новая версия помещается на ту же страницу. Создает цепочку `LP_REDIRECT`.
*   **Transaction ID (XID) Wraparound** — критическое состояние, при котором 32-битный счетчик транзакций переполняется. Требует обязательной очистки (**Freezing**) старых строк.
*   **TidStore (PG 17)** — высокоэффективная структура данных в оперативной памяти (на базе Radix-дерева) для хранения идентификаторов мертвых строк (TID). Потребляет в 20 раз меньше RAM, чем старый подход на основе массивов.
*   **Visibility Map (VM)** — битовая карта (файл с суффиксом `_vm`), отслеживающая состояние страниц. Содержит 2 бита на страницу: `all-visible` (все строки видны всем) и `all-frozen` (все строки заморожены).

## Внутренние структуры

### Visibility Map (VM)
Основная цель — **Index-Only Scans** и оптимизация сканирования кучи.
- Если страница `all-visible`, VACUUM может пропустить её при обычном сканировании.
- Если страница `all-frozen`, VACUUM пропустит её даже при агрессивной очистке (Anti-wraparound).
- Бит `all-visible` сбрасывается при любой модификации страницы (INSERT/UPDATE/DELETE).

### Free Space Map (FSM)
Файл с суффиксом `_fsm`, хранящий информацию о свободном месте.
- Структура: многоуровневое дерево (обычно 3 уровня), где каждый узел хранит максимальное количество свободного места в своих потомках.
- Позволяет планировщику мгновенно находить страницу с достаточным местом для новой строки, не сканируя кучу.
- Обновляется в конце фазы удаления из кучи.

### TidStore (PG 17+)
Заменяет старый механизм, ограниченный `maintenance_work_mem`.
- Использует динамически расширяемую память, позволяя хранить миллиарды TID.
- Позволяет избежать многократных проходов по индексам (Index Vacuum) при нехватке памяти.
- Интегрирован с механизмом **Parallel VACUUM**.

## Алгоритм работы (Phases)

Процесс очистки выполняется воркером `autovacuum` или командой `VACUUM` и проходит через следующие фазы:

### 1. Сканирование кучи (Heap Scan)
Воркер последовательно читает страницы таблицы.
- **HOT Pruning**: Перед основным сканированием выполняется «мини-очистка» внутри страницы. Если есть цепочки HOT, мертвые версии удаляются, а Line Pointer переводится в состояние `LP_UNUSED`. Это не требует Index Vacuum.
- Если страница помечена в **Visibility Map** как `all-visible`, она пропускается (если не выполняется агрессивная очистка).
- Идентифицируются мертвые кортежи, их TID сохраняются в **TidStore**.
- Генерируются записи в **WAL** для каждой модифицированной страницы.

### 2. Очистка индексов (Index Vacuum)
Если в TidStore накоплены мертвые TID, VACUUM переходит к индексам.
- Каждый индекс сканируется полностью. Записи, указывающие на собранные TID, удаляются.
- С PG 17 благодаря TidStore количество проходов по индексам сводится к минимуму (в идеале — один).
- Если индексов много, эта фаза становится самой долгой и нагруженной по I/O.

### 3. Удаление из кучи (Heap Vacuum)
Воркер возвращается к страницам кучи.
- Физически удаляет мертвые кортежи, ID которых были вычищены из индексов.
- Освободившееся место помечается в **Free Space Map (FSM)**.
- Устанавливаются биты в **Visibility Map**, если страница стала `all-visible`.

### 4. Заморозка (Freezing)
Если возраст страницы превышает `vacuum_freeze_min_age`, VACUUM помечает строки как "замороженные" (XID = 2).
- С PG 14+ этот процесс стал более ленивым: заморозка объединяется с обычным сканированием.
- При достижении `autovacuum_freeze_max_age` запускается **Aggressive VACUUM**, который игнорирует Visibility Map и сканирует все страницы.

### 5. Обрезка хвоста (Truncate)
Если последние страницы файла таблицы стали полностью пустыми, VACUUM пытается вернуть их ОС.
- Требует кратковременной блокировки `AccessExclusiveLock`. Если блокировку получить не удается, фаза пропускается.

## Механизмы Autovacuum

PostgreSQL использует **Cost-based Vacuuming**, чтобы очистка не «съела» все ресурсы диска.
- **vacuum_cost_limit**: Общий лимит «стоимости» для всех воркеров.
- **vacuum_cost_delay**: Пауза после достижения лимита (обычно 2-10ms).
- **Начисление стоимости**: 
  - Чтение страницы из `shared_buffers` = 1.
  - Чтение страницы с диска = 10.
  - Грязная (измененная) страница = 20.

## Практические сценарии

### 1. Оценка уровня Bloat (без расширений)
Приблизительная оценка того, сколько места можно освободить:
```sql
SELECT
  schemaname, relname,
  pg_size_pretty(pg_relation_size(relid)) AS total_size,
  CASE WHEN n_dead_tup > 0 
    THEN (n_dead_tup * 100 / (n_live_tup + n_dead_tup))::numeric(5,2) 
    ELSE 0 
  END AS dead_tup_pct
FROM pg_stat_all_tables
WHERE n_live_tup > 0
ORDER BY n_dead_tup DESC;
```

### 2. Тюнинг для Write-heavy таблиц
Для таблиц с миллионами обновлений в час:
```sql
ALTER TABLE large_orders SET (
  autovacuum_vacuum_scale_factor = 0.01,
  autovacuum_analyze_scale_factor = 0.005,
  autovacuum_vacuum_cost_limit = 1000
);
```

### 3. Действия при угрозе XID Wraparound
Если в логах ошибка: `database is not accepting commands to avoid wraparound data loss in database "mydb"`:
1. Переведите БД в **Single User Mode**: `postgres --single -D /path/to/data mydb`.
2. Выполните: `VACUUM FREEZE;`.
3. Режим Single User не запускает фоновые процессы и дает VACUUM максимум ресурсов.

## Поиск и устранение неисправностей

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **VACUUM не удаляет мертвые строки** | Долгая транзакция в состоянии `idle in transaction`. | Проверьте `pg_stat_activity`, завершите старую сессию. |
| **VACUUM работает вечно** | Слишком низкий `vacuum_cost_limit` или высокая нагрузка на диск. | Увеличьте лимит стоимости или используйте `Parallel VACUUM`. |
| **Рост Bloat на реплике** | Параметр `hot_standby_feedback` выключен на реплике. | Включите `hot_standby_feedback = on`, чтобы Standby сообщал Primary о своих транзакциях. |
| **Блокировки при очистке** | Фаза Truncate конфликтует с быстрыми запросами. | Установите `vacuum_truncate = off`, если таблица огромная, а удаление хвоста не критично. |


## Мониторинг и диагностика

### Отслеживание прогресса
Начиная с PG 9.6, текущее состояние можно видеть в реальном времени:
```sql
SELECT relname, phase, heap_blks_scanned, heap_blks_total, index_vacuum_count 
FROM pg_stat_progress_vacuum;
```

### Настройка для высоконагруженных систем
- **autovacuum_vacuum_scale_factor**: Снижайте до 0.01 для таблиц > 100 ГБ, чтобы очистка запускалась чаще и была короче.
- **maintenance_work_mem**: Увеличивайте (до 1-2 ГБ), чтобы TidStore вмещал больше ID за один проход индексов (уменьшает количество фаз Index Vacuum). В PG 17+ лимит на память для TID значительно расширен.
