# Индексы в PostgreSQL

## Определения

- **MVCC (Multi-Version Concurrency Control)**: Архитектура PostgreSQL, при которой изменения данных (`UPDATE`/`DELETE`) создают новые версии строк. Это приводит к накоплению "мертвых строк" (dead tuples) и раздуванию (**Bloat**) индексов.
- **Bloat (Раздувание)**: Избыточное дисковое пространство, занимаемое индексом или таблицей из-за накопления старых версий строк, которые еще не были очищены процессом VACUUM.
- **HOT (Heap Only Tuples)**: Оптимизация, позволяющая обновлять строки без обновления индексов, если новая версия строки помещается на ту же страницу данных и индексируемые столбцы не изменились.
- **Операторный класс (Operator Class)**: Набор правил, определяющих, как индекс должен обрабатывать конкретные типы данных и операторы (например, `text_pattern_ops` для корректной работы `LIKE` в не-C локалях).
- **TID (Tuple Identifier)**: Физический адрес строки (номер страницы и индекс внутри страницы), на который ссылается запись в индексе.

## Базовые концепции

### Специализированные типы индексов

Помимо стандартных B-Tree (см. **[Общие концепции](../../Concepts/indexes.md)**), PostgreSQL предоставляет:

- **GIN (Generalized Inverted Index)**: Обобщенный инвертированный индекс. Оптимизирован для составных типов данных (`jsonb`, массивы) и полнотекстового поиска. Очень быстрый поиск, но медленная запись.
- **GiST (Generalized Search Tree)**: Инфраструктура для реализации произвольных стратегий индексирования. Эффективен для геоданных (PostGIS), векторов, диапазонов и полнотекстового поиска. Поддерживает поиск по близости (KNN, оператор `<->`).
- **SP-GiST (Space-Partitioned GiST)**: Для несбалансированных структур данных (префиксные деревья, квадродеревья), где пространство может быть рекурсивно разделено на непересекающиеся области.
- **BRIN (Block Range Index)**: Индекс по диапазонам блоков. Хранит только min/max значения для группы страниц. Идеален для огромных таблиц, данные в которых физически упорядочены (логи, временные ряды). Начиная с PostgreSQL 14, поддерживает фильтры Блума и многодиапазонные значения.
- **Bloom**: Индекс на основе фильтров Блума (через расширение `bloom`). Позволяет эффективно фильтровать данные по любому количеству столбцов, но дает только вероятностный результат (требует перепроверки в куче).
- **Hash**: Предназначен только для сравнения на равенство. Начиная с PostgreSQL 10, Hash-индексы защищены WAL и поддерживают репликацию.

### Особенности реализации

- **B-Tree Deduplication**: Начиная с PostgreSQL 13, B-Tree индексы автоматически дедуплицируют повторяющиеся ключи, что значительно уменьшает их размер (особенно для столбцов с низкой кардинальностью).
- **Индексы и локали**: Стандартный B-Tree в локалях, отличных от `C` или `POSIX`, может не использовать индекс для `LIKE 'abc%'`. Для решения используются классы `text_pattern_ops`, `varchar_pattern_ops` или `bpchar_pattern_ops`.

## Практические сценарии

### 1. Выбор типа индекса

1. **`jsonb`, массивы, полнотекстовый поиск** → GIN
2. **Геоданные, векторы ([pgvector](../pgvector.md)), KNN поиск** → GiST
3. **Огромные упорядоченные таблицы (логи, архивы)** → BRIN
4. **Стандартные типы и операции (`=`, `<`, `>`, `BETWEEN`, `SORT`)** → B-Tree
5. **Равенство в уникальных столбцах (при нехватке места под B-Tree)** → Hash

### 2. Специальные техники

**Функциональные индексы (Expression Indexes):**
Позволяют индексировать результат вычисления.

```sql
-- Поиск по email без учета регистра
CREATE INDEX idx_users_lower_email ON users (lower(email));
```

**Частичные индексы (Partial Indexes):**
Индексируют только часть таблицы, подходящую под условие.

```sql
-- Индекс только для активных пользователей (экономит место)
CREATE INDEX idx_active_users ON users (id) WHERE is_active IS TRUE;
```

**Покрывающие индексы (Covering Indexes):**
Используют ключевое слово `INCLUDE` для добавления неключевых столбцов в индекс, что позволяет выполнять **Index Only Scan**.

```sql
CREATE INDEX idx_orders_status ON orders (status) INCLUDE (id, created_at);
```

### 3. Мониторинг и удаление неиспользуемых индексов

Неиспользуемые индексы замедляют запись и потребляют ресурсы. Проверка через `pg_stat_user_indexes`:

```sql
SELECT
    indexrelname AS index_name,
    relname AS table_name,
    idx_scan,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM
    pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;
```

## Дополнительная информация

### Обслуживание и устранение раздувания (Bloat)

- **REINDEX CONCURRENTLY**: Перестраивает индекс без блокировки таблицы на чтение и запись (доступно с PostgreSQL 12).
- **pg_repack**: Стороннее расширение для устранения раздувания таблиц и индексов онлайн (эффективнее `VACUUM FULL`, так как не блокирует таблицу).
- **Fillfactor**: Параметр (по умолчанию 90 для индексов), определяющий процент заполнения страниц. Уменьшение `fillfactor` может помочь снизить частоту раздувания при интенсивных `UPDATE`, оставляя место для новых версий строк (HOT).

### Золотые правила

- **Индексируйте внешние ключи (Foreign Keys)**: PostgreSQL не делает этого автоматически; отсутствие индексов на FK приводит к медленным JOIN и блокировкам при DELETE.
- **Остерегайтесь избыточности**: 5–10 индексов — разумный предел для OLTP. Каждый индекс замедляет вставку и обновление данных.
- **Проверяйте выполнение**: Всегда используйте `EXPLAIN (ANALYZE, BUFFERS)` для подтверждения того, что индекс действительно используется и эффективен.
