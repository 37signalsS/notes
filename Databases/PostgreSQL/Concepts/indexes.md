# Индексы в PostgreSQL

**Актуально для:** PostgreSQL 15–18

## Определения

- **MVCC (Multi-Version Concurrency Control)**: Архитектура PostgreSQL, при которой изменения данных (`UPDATE`/`DELETE`) создают новые версии строк. Это приводит к накоплению "мертвых строк" (dead tuples) и раздуванию (**Bloat**) индексов.
- **TID (Tuple Identifier) / CTID**: Физический адрес строки в таблице (номер блока и смещение внутри блока). Индексы связывают значения ключей с соответствующими CTID. При обновлении строки (без HOT) создается новый CTID, что требует обновления всех индексов таблицы.
- **Bloat (Раздувание)**: Избыточное дисковое пространство, занимаемое индексом или таблицей из-за накопления старых версий строк, которые еще не были очищены процессом VACUUM.
- **HOT (Heap Only Tuples)**: Оптимизация, позволяющая обновлять строки без обновления индексов, если новая версия строки помещается на ту же страницу данных и индексируемые столбцы не изменились. Начиная с PostgreSQL 16, индексы BRIN больше не блокируют HOT-обновления.
- **Visibility Map (Карта видимости)**: Битовая карта, отслеживающая, все ли строки на странице данных (в куче) видимы для всех активных транзакций. Если страница помечена как "полностью видимая", PostgreSQL может пропустить чтение кучи при **Index-Only Scan**.
- **Index-Only Scan**: Режим выполнения запроса, при котором данные извлекаются напрямую из индекса без обращения к основной таблице (куче). Эффективность напрямую зависит от актуальности Visibility Map.
- **Operator Class (Класс операторов)**: Определяет, как конкретный тип данных будет обрабатываться конкретным типом индекса (набор функций сравнения и стратегий поиска). Позволяет расширять возможности индексации для пользовательских типов.
- **Leaf Page (Листовая страница)**: Самый нижний уровень B-Tree, содержащий пары `(значение, CTID)`.
- **Internal Page (Внутренняя страница)**: Узлы дерева выше листового уровня, содержащие ссылки на дочерние страницы и границы диапазонов значений для навигации.
- **Cardinality (Кардинальность)**: Количество уникальных значений в столбце. Высокая кардинальность (например, ID) делает индекс более эффективным.
- **Selectivity (Селективность)**: Отношение количества строк, подходящих под условие, к общему количеству строк. Чем меньше селективность (ближе к 0), тем вероятнее использование индекса планировщиком.
- **NULLS NOT DISTINCT**: Опция уникального индекса (доступна с PostgreSQL 15), позволяющая трактовать все значения `NULL` как идентичные, тем самым запрещая вставку более одного `NULL` в индексируемый столбец.
- **Tablespace**: Область хранения на диске, куда PostgreSQL размещает файлы индексов. Позволяет SRE распределять горячие индексы по SSD, а холодные — по HDD или архивным хранилищам.
- **Page Split (Разделение страницы)**: Процесс деления переполненной страницы индекса на две при вставке данных выше `fillfactor`. Приводит к фрагментации и дополнительным случайным записям на диск.
- **Fillfactor (Фактор заполнения)**: Параметр, определяющий процент заполнения страниц индекса при создании или перестроении. Оставленное свободное место позволяет выполнять вставки без немедленного разделения страниц.

## Базовые концепции

### Основные типы индексов

PostgreSQL предоставляет широкий набор специализированных структур данных:

- **B-Tree**: Стандартный тип индекса (по умолчанию). Эффективен для операций сравнения (`=`, `<`, `>`, `<=`, `>=`), `BETWEEN`, `IN`, `IS NULL` и сортировки.
    - **PG 15+**: Ускорена сортировка данных (в 2-5 раз).
    - **PG 17+**: Значительная оптимизация для запросов с длинными списками `IN (...)` или `= ANY(...)` — поиск выполняется за один проход дерева.
    - **PG 18+**: Поддержка нативного **Asynchronous I/O (AIO)** ускоряет построение индексов (`CREATE INDEX`) и их обслуживание процессом `VACUUM`, особенно на высокопроизводительных NVMe-дисках. Появилась поддержка **Skip Scan** для составных B-Tree индексов, что позволяет использовать индекс в случаях, когда на ранние столбцы нет условий на равенство.
- **GIN (Generalized Inverted Index)**: Инвертированный индекс для составных типов (`jsonb`, массивы, полнотекстовый поиск). Быстрый поиск, но медленная вставка (можно ускорить через параметр `fastupdate`). С PG 16 улучшена оценка стоимости сканирования планировщиком.
- **GiST (Generalized Search Tree)**: Универсальное дерево для сложных структур (геоданные PostGIS, диапазоны, векторы). Поддерживает поиск ближайших соседей (KNN, оператор `<->`). С PG 17 поддерживает инкрементальную сортировку.
- **SP-GiST (Space-Partitioned GiST)**: Для несбалансированных данных (префиксные деревья, квадродеревья). Оптимален, когда пространство можно разделить на непересекающиеся области.
- **BRIN (Block Range Index)**: Хранит min/max значения для диапазонов блоков страниц. Занимает минимум места. Идеален для логов и временных рядов, упорядоченных физически.
    - **PG 14+**: Поддержка фильтров Блума и многодиапазонных значений.
    - **PG 16+**: Совместимость с HOT-обновлениями.
    - **PG 17+**: Поддержка параллельного построения индекса (`CREATE INDEX`).
- **Hash**: Предназначен только для сравнения на равенство (`=`). Начиная с PG 10, защищен WAL и пригоден для репликации. Занимает меньше места, чем B-Tree для длинных ключей.
- **Bloom**: На основе фильтров Блума (через расширение `bloom`). Позволяет фильтровать по любому количеству столбцов с вероятностным результатом.

### Особенности реализации

- **B-Tree Deduplication**: (PG 13+) Автоматическое сжатие повторяющихся ключей в B-Tree, что значительно уменьшает размер индексов на столбцах с низкой кардинальностью.
- **Индексы и локали**: В локалях, отличных от `C` или `POSIX`, обычный B-Tree может не использоваться для `LIKE 'abc%'`. Решение: классы операторов `text_pattern_ops`, `varchar_pattern_ops`.
- **SIMD Acceleration**: (PG 16+) Использование векторных инструкций процессора (x86, ARM) для ускорения поиска в индексах и обработки массивов.
- **btree_gist и btree_gin**: Расширения, позволяющие использовать стандартные B-Tree операторы в GiST и GIN индексах. Это критично для создания составных индексов, объединяющих сложные типы (например, `geometry` и `int`).

### Архитектура хранения и фрагментация

Индексы хранятся в страницах фиксированного размера (обычно 8 КБ). При вставке данных, если страница заполнена выше `fillfactor`, PostgreSQL выполняет **Page Split**:
1. Выделяется новая страница.
2. Около половины записей перемещается на новую страницу.
3. Обновляется родительская страница.

**Результат:** фрагментация индекса, дополнительные случайные записи на диск, рост времени чтения.

**Снижение splits:**
- Устанавливайте `fillfactor` ниже 100 для таблиц с частыми `UPDATE`/`DELETE` (например, 70–80), чтобы новые версии строк помещались на той же странице и могли использовать HOT.
- `fillfactor` индекса управляет запасом внутри страниц индекса и сам по себе не создает резерв в heap-страницах.
- Выполняйте `CLUSTER` или `REINDEX` после массовых изменений данных.

## Практические сценарии

### Предварительные требования

1. **Версия PostgreSQL**: Рекомендуется 15+ для использования `NULLS NOT DISTINCT` и оптимизаций B-Tree. Для PG 17 доступна ускоренная очистка памяти VACUUM. Для PG 18 доступен AIO (`io_method` = `worker` по умолчанию) и Skip Scan.
2. **Права доступа**: Требуются права владельца таблицы или роль `pg_maintain` (PG 17+) для создания индексов и выполнения `REINDEX`.
3. **Наличие расширений**:
    - `btree_gist` / `btree_gin` — для создания составных индексов с B-Tree и GiST/GIN типами.
    - `pgstattuple` (включает `pgstatindex`) — для глубокого анализа структуры индекса и уровня Bloat.
    - `pg_repack` — для онлайн-дефрагментации таблиц и индексов без блокировок (альтернатива `REINDEX CONCURRENTLY` для очень больших таблиц).

### 1. Выбор типа индекса

- **Точный поиск и диапазоны (INT, TEXT, DATE)** → B-Tree
- **JSONB, массивы, поиск подстрок** → GIN
- **Геометрия, IP-диапазоны, KNN** → GiST
- **Огромные архивы (сотни ГБ/ТБ), упорядоченные по времени** → BRIN
- **Уникальные ключи с запретом дублей NULL** → B-Tree + `NULLS NOT DISTINCT`

### 2. Специальные техники

**Индексирование виртуальных генерируемых столбцов (PG 18+):**
В PostgreSQL 18 появились виртуальные генерируемые столбцы, которые не занимают места на диске. Однако на них можно создавать индексы, что позволяет эффективно искать по вычисляемым значениям без дублирования данных в таблице.

**Функциональные индексы (Expression Indexes):**
Индексируют результат функции, например `lower(email)`. Важно: запрос должен использовать ту же функцию для срабатывания индекса.

**Частичные индексы (Partial Indexes):**
`CREATE INDEX ... WHERE (status = 'active')`. Экономят место и ускоряют работу с подмножеством данных.

**Покрывающие индексы (Covering Indexes):**
Использование `INCLUDE (col1, col2)` добавляет столбцы в "листья" B-Tree. Это позволяет выполнять **Index Only Scan**, если Visibility Map подтверждает актуальность данных в куче.

### 3. Многоколоночные индексы (Composite Indexes)

- **Правило префикса**: Индекс по `(A, B, C)` эффективен для фильтров `(A)`, `(A, B)` и `(A, B, C)`. Он практически бесполезен для фильтра только по `(B)` или `(C)` (кроме случая Index Only Scan).
- **Порядок столбцов**: Первыми должны идти столбцы, используемые в условиях на равенство (`=`), затем — столбцы для диапазонов (`>`, `<`) и сортировки.

### 4. Создание индексов без блокировок

Обычный `CREATE INDEX` блокирует таблицу на запись. Для живых систем используйте:

```sql
-- Медленнее, требует двух проходов, но не блокирует запись
CREATE INDEX CONCURRENTLY idx_user_id ON users (user_id);
```
*Примечание: Если создание прервется, останется "битый" индекс (INVALID). Его нужно удалить и запустить заново. В PostgreSQL 18+ благодаря AIO фаза сканирования при CONCURRENTLY построении выполняется значительно быстрее.*

**Для очень больших таблиц (> 1 ТБ):**
Стандартный `CREATE INDEX CONCURRENTLY` может занимать дни. Рассмотрите `pg_repack` для реорганизации с минимальной блокировкой:

```bash
pg_repack -t orders --index idx_orders_optim
```

### 5. Tablespace для управления дисками

Для SRE важно контролировать расположение индексов на разных типах дисков:

```sql
-- Создание tablespace на SSD для горячих индексов
CREATE TABLESPACE fast_ssp LOCATION '/mnt/ssd/pg_tablespace';

-- Создание индекса в конкретном tablespace
CREATE INDEX idx_orders_user_id ON orders (user_id) TABLESPACE fast_ssp;
```

**Рекомендации:**
- Горячие индексы (часто используемые B-Tree на FK) → SSD/NVMe
- Холодные индексы (BRIN на логах, архивные данные) → HDD
- После переноса индекса в другой tablespace обновите права доступа и проверьте пути в резервных скриптах.

### 6. Анализ работы индексов через EXPLAIN

Для понимания эффективности используйте `EXPLAIN (ANALYZE, BUFFERS)`:

- **Index Scan**: Прямое чтение из индекса и кучи. Хорошо для малого количества строк.
- **Index Only Scan**: Чтение только из индекса (куча не трогается). Идеально для производительности.
- **Bitmap Index Scan**: Сначала строится битовая карта подходящих страниц в памяти, затем читаются данные из кучи (`Bitmap Heap Scan`). Эффективно, когда строк много и они разбросаны по таблице.

**На что смотреть:**
- `Buffers: shared hit`: Данные взяты из кэша (хорошо).
- `Buffers: shared read`: Данные считаны с диска (медленно).
- `Index Cond`: Условие, по которому сработал индекс.
- `Filter`: Условие, которое пришлось проверять перебором после индекса (плохо, если строк много).

**AIO в PostgreSQL 18+:** Для мониторинга асинхронного I/O используйте `pg_aios` и `pg_stat_activity` (ищите `io worker` в `backend_type`). Параметр `io_method` в `postgresql.conf` управляет режимом AIO (`worker` по умолчанию, `io_uring` на Linux для максимальной производительности — требует сборки с `--with-liburing` и ядра 5.6+, `sync` для отката к поведению PG 17). Подробно: [Асинхронный ввод-вывод](../Operations/async_io.md).

### 7. Пошаговый пример оптимизации

**Задача:** Ускорить поиск активных заказов конкретного пользователя за последний месяц, отсортированных по цене.

1. **Исходный запрос:**
    ```sql
    SELECT id, price FROM orders 
    WHERE user_id = 123 AND status = 'active' AND created_at > now() - interval '1 month'
    ORDER BY price DESC;
    ```
2. **Анализ:** Нужен составной индекс.
3. **Выбор порядка:** `user_id` (равенство) → `status` (равенство) → `created_at` (диапазон) → `price` (сортировка).
4. **Создание покрывающего индекса:**
    ```sql
    CREATE INDEX CONCURRENTLY idx_orders_optim 
    ON orders (user_id, status, created_at, price DESC)
    INCLUDE (id); -- Для Index Only Scan
    ```

### 8. Проверка здоровья индексов

**Поиск инвалидных индексов:**
```sql
SELECT relname, indexrelname 
FROM pg_stat_user_indexes 
JOIN pg_index ON pg_index.indexrelid = pg_stat_user_indexes.indexrelid
WHERE NOT indisvalid;
```

**Оценка уровня Bloat (требует `pgstatindex` из `pgstattuple`):**
```sql
SELECT * FROM pgstatindex('idx_user_id');
-- Смотрите на параметр avg_leaf_density. Если < 50-60%, нужен REINDEX.
```

**Автоматизированная проверка для SRE (объединенный запрос):**
```sql
SELECT
    i.relname AS index_name,
    t.relname AS table_name,
    pg_size_pretty(pg_relation_size(i.indexrelid)) AS index_size,
    s.idx_scan AS scans,
    s.last_idx_scan,
    i.indisvalid AS is_valid,
    i.indisready AS is_ready
FROM
    pg_stat_user_indexes s
    JOIN pg_index i ON i.indexrelid = s.indexrelid
    JOIN pg_class t ON t.oid = s.relid
WHERE
    t.relkind = 'r'
    AND (i.indisvalid = false OR s.idx_scan = 0 OR pg_relation_size(i.indexrelid) > 1073741824)
ORDER BY pg_relation_size(i.indexrelid) DESC;
```

## Типичные проблемы и пограничные случаи

- **Корреляция данных**: Если физический порядок строк (`CLUSTER`) совпадает с порядком индекса, `Index Scan` будет значительно быстрее.
- **Индексы на выражениях**: Если индекс создан на `lower(email)`, запрос `WHERE email = '...'` его **не использует**. Нужно использовать ту же функцию в запросе.
- **Data Type Mismatch**: Если столбец `bigint`, а в запросе передается строка `'123'`, индекс может не сработать из-за неявного приведения типов.
- **Over-indexing**: Избыточные индексы замедляют `INSERT` и увеличивают время бэкапа. Всегда удаляйте дубликаты (например, `(a)` избыточен при наличии `(a, b)`).
- **Seq Scan при низкой селективности**: Если запрос выбирает более 20-30% строк таблицы, оптимизатор может решить, что полное сканирование быстрее, чем использование индекса и последующие переходы к диску за данными.
- **Неявный COMMIT**: `CREATE INDEX CONCURRENTLY` и `VACUUM` нельзя выполнить внутри транзакции. Они вызывают неявный COMMIT, что важно учитывать при миграциях.

## Мониторинг и обслуживание

### Поиск и удаление неиспользуемых индексов

Начиная с **PostgreSQL 16**, поле `last_idx_scan` в `pg_stat_user_indexes` показывает точное время последнего использования индекса.

```sql
SELECT
    indexrelname AS index_name,
    relname AS table_name,
    idx_scan,
    last_idx_scan,
    pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM
    pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'
ORDER BY pg_relation_size(indexrelid) DESC;
```

### Ключевые метрики для мониторинга

| Метрика | Зачем следить | Порог алерта |
| :--- | :--- | :--- |
| **Размер индекса** | Оценка места на диске и RAM для Buffer Pool | Рост > 30% за неделю без роста данных |
| **Плотность листьев (`avg_leaf_density`)** | Оценка bloat | < 60% для B-Tree |
| **Сканирования (`idx_scan`)** | Поиск неиспользуемых индексов | `idx_scan = 0` в течение 7+ дней (кроме PK) |
| **Время последнего сканирования** | Поиск "мертвых" индексов | > 7 дней (PostgreSQL 16+) |
| **Page Splits** | Дисковые узкие места | Рост фрагментации > 30% |

### Борьба с Bloat (Раздуванием)

- **REINDEX CONCURRENTLY**: Пересоздание индекса в фоновом режиме без блокировок (с PG 12).
- **pg_repack**: Онлайн-дефрагментация таблиц и индексов. Для таблиц > 100 GB часто предпочтительнее `REINDEX CONCURRENTLY`, так как не требует эксклюзивной блокировки на финальной фазе.
- **Fillfactor**: Для heap-таблиц с частыми `UPDATE` снижайте `fillfactor` самой таблицы (например, до 70–80), чтобы новые версии строк помещались на той же странице и могли использовать HOT. `fillfactor` индекса управляет запасом внутри страниц индекса и сам по себе не создает резерв в heap-страницах.
- **Vacuum TIDStore**: (PG 17+) Новая структура управления памятью в VACUUM потребляет в 20 раз меньше RAM, ускоряя очистку индексов на огромных таблицах.

## Влияние на репликацию и бэкапы

### Влияние на репликацию

Каждое изменение индекса генерирует WAL. На активных системах массовое обслуживание индексов может вызвать **Replica Lag**:
- **Физическая репликация:** WAL от `REINDEX`/`CLUSTER` может измеряться гигабайтами. Резкий рост WAL забивает сеть или disk queue на реплике.
- **Логическая репликация:** изменения DDL и массовые перестроения передаются как DDL/CAPI, что может привести к таймаутам.

**Рекомендации:**
- Выполняйте обслуживание последовательно, а не параллельно на всех таблицах.
- Увеличьте `wal_keep_size` перед массовым обслуживанием.
- Контролируйте задержку реплики через `pg_stat_replication`.

### Влияние на бэкапы и восстановление

- **Размер бэкапа:** Index Bloat напрямую увеличивает размер физических бэкапов (`pg_basebackup`).
- **Время восстановления (RTO):** При восстановлении СУБД должна прочитать и применить все индексные страницы. Чем больше bloat, тем дольше старт.
- **Влияние на PITR:** В WAL содержится информация об изменениях индексов. Чем больше обслуживание, тем больше WAL для архивации.

**Рекомендации:**
- Включайте в планирование бэкапов проверку размера индексов (`pg_relation_size`).
- Убедитесь, что диск для WAL выдерживает пиковую нагрузку во время обслуживания.

## Золотые правила

1. **Индексируйте Foreign Keys**: Отсутствие индекса на FK приводит к последовательному сканированию дочерней таблицы при удалении записи в родительской.
2. **Избегайте избыточности**: Каждый индекс замедляет `INSERT`/`UPDATE`. Проверяйте перекрывающиеся индексы (например, `(A)` не нужен, если есть `(A, B)`).
3. **Анализируйте план**: Всегда используйте `EXPLAIN (ANALYZE, BUFFERS)` для проверки эффективности. Обращайте внимание на `Index Scan` vs `Bitmap Index Scan`.
4. **Используйте CONCURRENTLY для production**: Никогда не блокируйте запись на горячих таблицах в рабочее время.
5. **Следите за bloat**: Регулярно проверяйте `avg_leaf_density` через `pgstatindex`. При < 50-60% планируйте `REINDEX` или `pg_repack`.
