# Индексы в PostgreSQL

## Определения

- **MVCC (Multi-Version Concurrency Control)**: Архитектура PostgreSQL, при которой изменения данных (`UPDATE`/`DELETE`) создают новые версии строк. Это приводит к появлению "мертвых строк" (dead tuples) и раздуванию (**Bloat**) индексов.
- **Bloat (Раздувание)**: Избыточное дисковое пространство, занимаемое индексом или таблицей из-за накопления старых версий строк, которые еще не были очищены процессом VACUUM.
- **Операторный класс (Operator Class)**: Набор правил, определяющих, как индекс должен обрабатывать конкретные типы данных и операторы (например, `text_pattern_ops` для ускорения `LIKE`).

## Базовые концепции

### Специализированные типы индексов

Помимо стандартных B-Tree и Hash (см. **[Общие концепции](../../Concepts/indexes.md)**), PostgreSQL предоставляет:

- **GIN (Generalized Inverted Index)**: Обобщенный инвертированный индекс. Оптимизирован для составных типов данных (`jsonb`, массивы) и полнотекстового поиска. Быстрый поиск, но медленная запись.
- **GiST (Generalized Search Tree)**: Эффективен для геоданных (PostGIS), векторов, диапазонов и полнотекстового поиска. Быстрее GIN при записи, поддерживает поиск по близости (KNN).
- **SP-GiST**: Для несбалансированных структур данных (например, префиксные деревья или непересекающиеся геоданные).
- **BRIN (Block Range Index)**: Для очень больших таблиц, данные в которых физически упорядочены (логи, временные ряды). Хранит только min/max для блоков страниц, что делает его крайне компактным.

### Особенности реализации стандартных индексов

- **B-Tree и локали**: По умолчанию B-Tree может не использовать индекс для `LIKE 'abc%'`, если локаль отлична от `C`. Для исправления используются классы `text_pattern_ops`.
- **Hash-индексы**: Начиная с PostgreSQL 10, полностью поддерживают WAL-логирование и безопасны для использования в репликации.

## Практические сценарии

### 1. Выбор типа индекса

1. **`jsonb`, массивы, полнотекстовый поиск** → GIN
2. **Геоданные, векторы ([pgvector](../pgvector.md)), поиск по близости** → GiST
3. **Огромные упорядоченные таблицы (логи)** → BRIN
4. **Стандартные операции (`=`, `<`, `>`, `BETWEEN`)** → B-Tree

### 2. Специальные техники

**Функциональные индексы (индексы на выражения):**
Позволяют индексировать результат выполнения функции.

```sql
-- Ускорение поиска по email без учета регистра
CREATE INDEX idx_users_lower_email ON users (lower(email));
```

**Покрывающие индексы (ключевое слово INCLUDE):**
Добавляют дополнительные поля в листовые узлы индекса. Это позволяет использовать **Index Only Scan**, так как все нужные данные есть в индексе.

```sql
CREATE INDEX idx_orders_status ON orders (status) INCLUDE (id, created_at);
```

**Индексы для поиска по шаблону (Pattern Ops):**
Необходимы для работы `LIKE` при специфических локалях.

```sql
CREATE INDEX idx_users_name_pattern ON users (name text_pattern_ops);
```

### 3. Поиск и удаление неиспользуемых индексов

Неиспользуемые индексы замедляют `INSERT/UPDATE` и занимают место. Мониторинг через `pg_stat_user_indexes`.

```sql
SELECT
    indexrelname AS index_name,
    relname AS table_name,
    idx_scan
FROM
    pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey';
```

## Дополнительная информация

### Золотые правила обслуживания

- **Лимит 5–10 индексов на таблицу**: Избыток индексов критически замедляет запись из-за MVCC.
- **Мониторинг раздувания (Bloat)**: Индексы на часто обновляемых колонках требуют периодического перестроения.
- **Безопасное перестроение**: Используйте `REINDEX CONCURRENTLY`, чтобы не блокировать таблицу на чтение и запись.
