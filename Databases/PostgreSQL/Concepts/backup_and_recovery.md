# Резервное копирование и восстановление в PostgreSQL

## Определения

- **PITR (Point-in-Time Recovery)** — технология восстановления базы данных на произвольный момент времени в прошлом путем наката журналов транзакций (**WAL**) на базовую физическую копию.
- **RPO (Recovery Point Objective)** — целевая точка восстановления; объем данных, который допустимо потерять (например, «не более 5 минут данных»).
- **RTO (Recovery Time Objective)** — целевое время восстановления; допустимая длительность простоя системы.
- **Логический бэкап** — выгрузка данных в виде SQL-запросов или структурированного архива (утилита `pg_dump`).
- **Физический бэкап** — побайтовая копия файлов данных и журналов транзакций (утилита `pg_basebackup`).
- **Инкрементальный бэкап** — копия только тех блоков данных, которые изменились с момента последнего бэкапа (встроено в PostgreSQL 17+).
- **Дифференциальный бэкап** — копия всех изменений с момента последнего **полного** бэкапа (в PG реализуется через внешние инструменты, такие как pgBackRest).

## Базовые концепции

### Логический vs Физический бэкап

| Характеристика | Логический (`pg_dump`) | Физический (`pg_basebackup`) |
| :--- | :--- | :--- |
| **Скорость создания** | Медленно (чтение через SQL) | Быстро (прямое копирование файлов) |
| **Скорость восстановления** | Очень медленно (выполнение SQL) | Быстро (копирование файлов + WAL) |
| **Гранулярность** | Таблицы, схемы, базы | Только весь кластер (инстанс) |
| **Версионность** | Можно восстановить на другую версию | Только та же мажорная версия |
| **PITR** | Не поддерживается | Основа для PITR |

### Механизм WAL и архивация
Для реализации PITR необходимо хранить не только базовый бэкап, но и все изменения (Write Ahead Log), произошедшие после него.
1.  **archive_mode**: Включение режима архивации журналов.
2.  **archive_command**: Команда для отправки заполненных WAL-сегментов в безопасное хранилище (S3, отдельный сервер). Рекомендуется использовать отказоустойчивые обертки (например, `pgbackrest archive-push`).

### Инкрементальное резервное копирование (PostgreSQL 17+)
В PostgreSQL 17 представлена нативная поддержка инкрементальных бэкапов.
- **Принцип**: Сервер отслеживает измененные блоки данных и передает только их.
- **Манифест**: Каждый бэкап создает `backup_manifest`, который необходим для выполнения последующего инкрементального бэкапа.
- **Эффективность**: Значительно снижает нагрузку на сеть и дисковую систему для больших БД.

## Практические сценарии

### 1. Логическое резервное копирование (`pg_dump` и `pg_dumpall`)
Идеально для частичного восстановления или миграции между версиями.

#### pg_dump
Используется для создания копии **одной конкретной** базы данных.
*   **Базовый синтаксис:** `pg_dump -U <user> -d <db_name> > backup.sql`
*   **Ключевые флаги:**
    *   `-h`, `--host`: Хост сервера.
    *   `-p`, `--port`: Порт подключения.
    *   `-U`, `--username`: Пользователь для подключения.
    *   `-W`, `--password`: Принудительный запрос пароля.
    *   `-t`, `--table`: Выгрузка только конкретной таблицы.
    *   `-s`, `--schema-only`: Выгрузка только схемы (DDL) без данных.
    *   `-a`, `--data-only`: Выгрузка только данных без схемы.
    *   `-F`, `--format`: Формат вывода: `p` (plain SQL), `c` (custom archive), `t` (tar), `d` (directory).
    *   `-j`, `--jobs`: Количество параллельных потоков (только для формата `directory`). Ускоряет бэкап больших баз.

#### pg_dumpall
Резервное копирование **всего кластера**, включая глобальные объекты (роли, табличные пространства).
*   **Синтаксис:** `pg_dumpall > full_cluster.sql`
*   **Сжатие:** `pg_dumpall | gzip > cluster_backup.sql.gz`

### 2. Физическое резервное копирование (`pg_basebackup`)
Бинарная копия инстанса, основа для репликации и PITR.

*   **Базовый синтаксис:** `pg_basebackup -h <host> -D /path/to/backup -P -X stream`
*   **Ключевые флаги:**
    *   `-D`, `--pgdata`: Директория для сохранения данных.
    *   `-F`, `--format`: `p` (plain) или `t` (tar).
    *   `-z`, `--gzip`: Сжатие (только для tar).
    *   `-R`, `--write-recovery-conf`: Создание файла `standby.signal` (автоматическая настройка реплики).
    *   `-X`, `--wal-method`: Способ включения WAL: `f` (fetch — в конце) или `s` (stream — параллельно).
    *   `-C`, `--create-slot`: (PG 10+) Создать слот репликации перед бэкапом, чтобы WAL не удалились.
    *   `-S`, `--slot`: Имя слота репликации.

### 3. Нативный инкрементальный бэкап (PG 17+)
1.  **Создание полного бэкапа с манифестом:**
    ```bash
    pg_basebackup -D /backups/full --backup-manifest-only
    ```
2.  **Создание инкрементального бэкапа:**
    ```bash
    pg_basebackup -D /backups/inc1 --incremental=/backups/full/backup_manifest
    ```

### 4. Проверка целостности (pg_verifybackup)
Утилита (с PG 13) для проверки физических бэкапов без их разворачивания.
```bash
pg_verifybackup /path/to/backup_directory
```
*Проверяет наличие всех файлов и соответствие контрольных сумм в манифесте.*

### 5. Восстановление данных (`pg_restore` и `psql`)
*   **SQL-скрипт:** `psql -d <db_name> -f backup.sql`
*   **Архив (custom/directory):** `pg_restore -d <db_name> backup_file.dump`
    *   `-C`, `--create`: Создать БД перед восстановлением.
    *   `-j`, `--jobs`: Параллельное восстановление (ускоряет процесс).
    *   `-v`, `--verbose`: Подробный вывод.

### 6. Восстановление на точку времени (PITR)
Алгоритм при аварии (например, ошибочный `DROP TABLE`):
1.  Остановить сервер и очистить `PGDATA`.
2.  Восстановить файлы из последнего физического бэкапа.
3.  Создать пустой файл `recovery.signal` в корне `PGDATA`.
4.  Настроить `postgresql.conf`:
    ```sql
    restore_command = 'cp /mnt/archived_wals/%f %p'
    recovery_target_time = '2026-07-18 10:00:00 MSK'
    recovery_target_action = 'promote'
    ```
5.  Запустить сервер. Он «проиграет» логи до указанной точки.

### 7. Резервное копирование в Kubernetes
Рекомендуется использовать **CloudNativePG Operator**:
- **Декларативность**: Бэкапы описываются через YAML-ресурсы `Backup`.
- **S3 Native**: Встроенная поддержка AWS S3, Google Cloud Storage, Azure Blob.
- **Scheduled Backups**: Настройка расписания через Cron.

## Безопасность и хранение

### Безопасность бэкапов
- **Права доступа**: Используйте роли `pg_read_all_settings` и `pg_backup_control` вместо суперпользователя.
- **Шифрование**: Рекомендуется шифровать бэкапы перед отправкой в хранилище (GPG или средства S3).
- **Изоляция**: Храните бэкапы в географически удаленном регионе или другом облачном аккаунте.

### Политики удержания (Retention)
- **Стратегия 3-2-1**: 3 копии, на 2 разных носителях, 1 копия — вне площадки (off-site).
- **Жизненный цикл**:
    - Полные бэкапы: Хранить 30 дней.
    - WAL-архивы: Должны покрывать период самого старого полного бэкапа, необходимого для PITR.

## Инструментарий (Enterprise-решения)
*   **pgBackRest**: Золотой стандарт. Инкрементальные/дифференциальные бэкапы, параллелизм, S3.
*   **WAL-G**: Высокопроизводительный инструмент для облачных сред.
