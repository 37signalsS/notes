# Резервное копирование и восстановление в PostgreSQL

## Определения

- **PITR (Point-in-Time Recovery)** — технология восстановления базы данных на произвольный момент времени в прошлом путем «проигрывания» журналов транзакций (**WAL**) поверх базовой физической копии (Base Backup).
- **RPO (Recovery Point Objective)** — целевая точка восстановления; максимально допустимый объем потери данных в случае сбоя (например, «не более 5 минут транзакций»).
- **RTO (Recovery Time Objective)** — целевое время восстановления; допустимая длительность простоя системы с момента сбоя до возврата в рабочее состояние.
- **Логический бэкап** — выгрузка структуры и данных в виде SQL-запросов (plain text) или проприетарного сжатого архива (утилита `pg_dump`).
- **Физический бэкап** — побайтовая копия файлов данных (блоков), конфигураций и журналов транзакций всего кластера БД (утилита `pg_basebackup`).
- **Инкрементальный бэкап** — копия только тех блоков данных, которые изменились с момента создания предыдущего бэкапа (встроено в PostgreSQL 17+ через WAL-summarization).
- **Asynchronous I/O (AIO) (PG 18+)** — нативная поддержка асинхронного ввода-вывода, которая значительно снижает нагрузку на дисковую подсистему при выполнении `Sequential Scan` во время бэкапов и ускоряет запись в WAL-архив.
- **Дифференциальный бэкап** — копия всех изменений с момента последнего **полного** бэкапа (реализуется внешними инструментами, такими как `pgBackRest`).
- **Таймлайн (Timeline ID)** — идентификатор ветки развития БД. Создается при каждом выполнении PITR или продвижении (promote) реплики, предотвращая перезапись WAL из разных сессий восстановления.
- **Манифест бэкапа (backup_manifest)** — файл в формате JSON, содержащий метаданные о бэкапе: список всех файлов, их размеры, контрольные суммы и LSN начала/конца бэкапа. Критически важен для инкрементальных копий и валидации.

## Базовые концепции

### Сравнение методов резервного копирования

| Характеристика | Логический (`pg_dump`) | Физический (`pg_basebackup`) |
| :--- | :--- | :--- |
| **Скорость создания** | Низкая (полное сканирование таблиц) | Высокая (AIO в PG 18 ускоряет процесс) |
| **Скорость восстановления** | Очень низкая (INSERT + построение индексов) | Высокая (копирование файлов + накат WAL) |
| **Гранулярность** | Высокая (таблица, схема, база) | Низкая (только весь инстанс) |
| **Версионность** | Между мажорными версиями и архитектурами | Только та же мажорная версия и ОС |
| **Влияние на нагрузку** | Высокое (блокировки DDL, нагрузка на CPU) | Умеренное (AIO минимизирует блокировки IO) |
| **Поддержка PITR** | Отсутствует | Фундаментальная основа |

### Журналы транзакций (WAL) и архивация
Механизм **Write Ahead Log** обеспечивает атомарность и долговечность (ACID). Для восстановления на момент времени необходимо сохранять не только базовую копию, но и непрерывный поток WAL-сегментов.

1.  **archive_mode**: Должен быть `on` для включения процесса архивации.
2.  **wal_level**: Для PITR и репликации требуется уровень `replica` (по умолчанию в 10+) или `logical`.
3.  **archive_command**: Внешняя команда или скрипт для перемещения заполненного сегмента (16 МБ) в хранилище. 
    *Пример:* `archive_command = 'test ! -f /mnt/server/archivedir/%f && cp %p /mnt/server/archivedir/%f'`
4.  **archive_timeout**: Принудительное переключение сегмента через N секунд, если база простаивает (снижает потенциальный RPO).

### Инкрементальное копирование в PostgreSQL 17
В версии 17 реализована нативная поддержка инкрементальных бэкапов через процесс **WAL summarization**.
- **Принцип работы**: Фоновый процесс `summarizer` анализирует WAL и создает компактные файлы-сводки, в которых указано, какие блоки данных изменились.
- **Параметр**: `summarize_wal = on`.
- **Восстановление**: Инкрементальные цепочки объединяются с помощью утилиты `pg_combinebackup` в новую полную копию.

### Переключение таймлайнов
При выполнении PITR PostgreSQL переключается на новый таймлайн (например, с 1 на 2). Это позволяет:
- Избежать конфликтов имен WAL-файлов.
- Проследить историю восстановлений.
- Выполнить восстановление «из будущего» по отношению к предыдущей точке восстановления, если это необходимо.

## Практические сценарии

### 1. Логическое резервное копирование (`pg_dump`)
Оптимально для миграций, частичного восстановления или небольших БД (< 100 ГБ).

#### Предпосылки
- Установленная версия клиента (`pg_dump`) должна быть не ниже мажорной версии сервера.
- Роль с правами `pg_read_all_data` (введена в PG 14) или владелец схем.

#### pg_dump
*   **Параллельный экспорт (Directory format):**
    ```bash
    pg_dump -h localhost -U backup_user -d mydb -F d -j 4 -f /backups/mydb_dump_dir
    ```
*   **Ключевые флаги:**
    *   `-F d`: Формат каталога (обязателен для параллелизма).
    *   `-j 4`: Использование 4 рабочих потоков.
    *   `--no-owner`: Не сохранять информацию о владельцах (полезно при миграции на другой инстанс).
    *   `--no-privileges`: Не экспортировать права доступа (GRANT/REVOKE).

#### pg_dumpall
Резервное копирование **всего кластера**, включая роли и табличные пространства.
*   **Экспорт только глобальных объектов:** `pg_dumpall -g > globals.sql`

---

### 2. Физическое резервное копирование (`pg_basebackup`)
Бинарная копия инстанса, необходимая для репликации и PITR.

#### Предпосылки
- `wal_level` установлен в `replica` или выше.
- Роль с правом `REPLICATION` или `SUPERUSER`.
- Доступ в `pg_hba.conf` для типа подключения `replication`.

#### Базовое использование
```bash
pg_basebackup -h 10.0.0.1 -U replicator -D /var/lib/postgresql/backup -P -X stream --checkpoint=fast
```
*   **`--checkpoint=fast`**: Форсирует немедленный чекпоинт для быстрого начала бэкапа.
*   **`-X stream`**: WAL-сегменты передаются параллельно через отдельное соединение.
*   **`-R`**: Автоматически создает `standby.signal` и `postgresql.auto.conf` для настройки реплики.

---

### 3. Инкрементальный бэкап и сборка (PostgreSQL 17+)
1.  **Создание цепочки:**
    ```bash
    # 1. Полный бэкап
    pg_basebackup -D /backups/full --backup-manifest-only
    # 2. Инкрементальный бэкап на основе манифеста
    pg_basebackup -D /backups/inc1 --incremental=/backups/full/backup_manifest
    ```
2.  **Сборка (восстановление):**
    ```bash
    pg_combinebackup /backups/full /backups/inc1 -o /var/lib/postgresql/data_restored
    ```

---

### 4. Восстановление на точку времени (PITR)
Алгоритм действий при критическом сбое (например, `DROP TABLE` в 14:05:00):

#### Подготовка (на стороне живого сервера)
Рекомендуется создавать «точки отката» перед опасными операциями:
```sql
SELECT pg_create_restore_point('before_migration');
```

#### Процедура восстановления
1.  **Остановка сервиса:** `sudo systemctl stop postgresql`
2.  **Очистка данных:** `rm -rf /var/lib/postgresql/data/*` (сохраните логи и конфиги!).
3.  **Развертывание бэкапа:** скопируйте файлы из последней физической копии.
4.  **Файл сигнала:** создайте пустой файл `recovery.signal` в корне `PGDATA`.
5.  **Настройка цели (`postgresql.auto.conf` или `postgresql.conf`):**
    ```ini
    restore_command = 'cp /mnt/wal_archive/%f %p'
    recovery_target_time = '2026-08-17 14:04:00 MSK'
    recovery_target_action = 'promote' # Открыть базу после достижения цели
    # Или по имени точки: recovery_target_name = 'before_migration'
    ```
6.  **Запуск:** `sudo systemctl start postgresql`. Следите за логом восстановления.

---

### 5. Проверка целостности и валидация
1.  **pg_verifybackup**: Проверка манифеста и контрольных сумм блоков.
    ```bash
    pg_verifybackup -m /path/to/backup/backup_manifest /path/to/backup
    ```
2.  **Тестовое восстановление:** единственная 100% гарантия. Рекомендуется выполнять раз в месяц в изолированном окружении.

## Поиск и устранение неисправностей

| Ошибка | Возможная причина | Решение |
| :--- | :--- | :--- |
| `permission denied for relation ...` | У бэкап-пользователя нет прав SELECT. | Выдайте `pg_read_all_data` или проверьте права на схему. |
| `WAL segment ... has already been removed` | Слишком медленный бэкап или малый `max_wal_size`. | Используйте слоты репликации (`--create-slot`) при `pg_basebackup`. |
| `archive_command failed with exit code 1` | Проблема с доступом к хранилищу (S3/NFS). | Проверьте монтирование диска и права записи для пользователя `postgres`. |
| `recovery_target_time is not reached` | Нужный WAL отсутствует в архиве. | Проверьте `archive_command` и наличие всех файлов в `wal_archive`. |
| `checksum verification failed` | Физическое повреждение данных на диске. | См. руководство по **[Corruption Recovery](./corruption_recovery.md)**. |

## Сложные сценарии и ограничения
...
- **Повреждение данных (Corruption):** В случае фатальных ошибок контрольных сумм или невозможности старта из-за битых WAL, требуются низкоуровневые инструменты типа `pageinspect` и `pg_resetwal`. См. **[Восстановление при повреждении данных](./corruption_recovery.md)**.

- **Bloat (раздувание):** Долгие `pg_dump` удерживают транзакцию, что мешает `VACUUM` очищать старые версии строк. Рекомендуется запускать дампы в часы минимальной нагрузки.
- **Расширения (Extensions):** При логическом восстановлении убедитесь, что бинарные файлы расширений (например, PostGIS) установлены на целевом сервере.
- **Large Objects (LO):** При использовании `pg_dump` убедитесь, что не используются флаги, исключающие блобы, если они важны. Помните об "orphan" объектах, которые увеличивают размер бэкапа. Детальное руководство по обслуживанию см. в **[Large Objects (LO): Администрирование и очистка](./large_objects.md)**.

## Безопасность и управление доступом

### Создание выделенного пользователя для бэкапов
```sql
-- Для логических бэкапов (PG 14+)
CREATE USER backup_user WITH PASSWORD 'password';
GRANT CONNECT ON DATABASE mydb TO backup_user;
GRANT USAGE ON SCHEMA public TO backup_user;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO backup_user;
ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO backup_user;
GRANT pg_read_all_data TO backup_user;

-- Для физических бэкапов
CREATE USER replicator WITH REPLICATION PASSWORD 'password';
```

### Политики удержания (Retention)
- **Стратегия 3-2-1**: 3 копии, на 2 разных носителях, 1 копия — вне площадки (off-site).
- **Жизненный цикл**:
    - Полные бэкапы: Хранить 30 дней.
    - WAL-архивы: Должны покрывать период самого старого полного бэкапа, необходимого для PITR.

## Инструментарий (Enterprise-решения)
*   **pgBackRest**: «Золотой стандарт» для крупных инсталляций. Поддерживает инкрементальные/дифференциальные бэкапы, многопоточность, дельта-восстановление и нативную работу с S3/GCS/Azure.
*   **WAL-G**: Высокопроизводительный инструмент от Yandex (преемник WAL-E), написанный на Go. Оптимизирован для максимально быстрой архивации и восстановления в облачных средах.
*   **Barman (Backup and Recovery Manager)** — решение от 2ndQuadrant (EDB), предоставляющее удобный интерфейс для управления бэкапами множества серверов.

*Подробные примеры настройки инструментов автоматизации см. в разделе **[Автоматизация бэкапов](../Operations/backup_automation.md)**.*
