# Резервное копирование и восстановление в PostgreSQL

## Определения

- **Point-in-Time Recovery (PITR)**: Технология восстановления базы данных на произвольный момент времени. Реализуется путем применения журналов транзакций (**[WAL](../../Concepts/write_ahead_log.md)**) к базовой физической копии.
- **MVCC (Multi-Version Concurrency Control)**: Архитектура PostgreSQL, позволяющая делать логические бэкапы (`pg_dump`) без блокировки таблиц на запись.
- **Отстающая реплика (Lagging Replica)**: Реплика, которая намеренно применяет изменения с задержкой, создавая окно времени для быстрого восстановления после человеческих ошибок (например, `DROP TABLE`).

## Базовые концепции

Общие стратегии (логические/физические, полные/инкрементальные) и метрики надежности (RPO/RTO) описаны в **[Стратегиях резервного копирования](../../Concepts/backups.md)** и **[Метриках SRE](../../../Concepts/sre_concepts_main.md)**.

### Специфика PostgreSQL

PostgreSQL предоставляет два основных способа создания резервных копий:

1. **Логический бэкап (`pg_dump`, `pg_dumpall`)**:
   - Формирует набор SQL-команд или архив в собственном формате.
   - Позволяет восстанавливать отдельные таблицы или переносить данные между разными мажорными версиями СУБД.
   - Медленнее физического бэкапа при создании и восстановлении на больших объемах.

2. **Физический бэкап (`pg_basebackup`)**:
   - Создает полную бинарную копию файлов данных кластера.
   - Требует идентичности мажорных версий PostgreSQL и архитектуры ОС для восстановления.
   - Является необходимой основой для настройки **PITR**.

### Инкрементальные бэкапы

Встроенные инструменты PostgreSQL не поддерживают инкрементальные бэкапы «из коробки». Для их реализации используются внешние утилиты (**pgBackRest**, **WAL-G**, **Barman**):

- **pgBackRest** — параллельный бэкап, сжатие, дедупликация, нативная интеграция с S3, полноценный PITR. Самый популярный инструмент для PostgreSQL.
- **Barman** — решение от EnterpriseDB, поддерживает remote backup, WAL streaming, retention policy.
- **WAL-G** — лёгкий инструмент с S3/GCS/Azure-native бэкендом, часто используется для отправки WAL в облачное хранилище.

## Практические сценарии

### 1. Логическое резервное копирование

**Дамп одной базы данных в формате `custom`:**
Рекомендуется использовать формат `-F c`, так как он сжат и поддерживает параллельное восстановление.

```bash
pg_dump -U postgres -d your_db -F c -f your_db.dump
```

**Восстановление из дампа (`pg_restore`):**
Параллельное восстановление в 4 потока:

```bash
pg_restore -U postgres -d target_db -j 4 your_db.dump
```

**Глобальные объекты:**
`pg_dump` не сохраняет роли и табличные пространства. Для них используется `pg_dumpall`:

```bash
pg_dumpall -U postgres -g > globals.sql
```

### 2. Физическое резервное копирование (`pg_basebackup`)

Создание базовой копии работающего сервера:

```bash
pg_basebackup -h master_host -U replicator -D /path/to/backup -F p -Xs -P -R
```

- `-Xs`: Включает необходимые WAL-файлы в бэкап.
- `-R`: Автоматически создает конфигурацию для запуска реплики.

### 3. Настройка восстановления на точку времени (PITR)

**Превентивная настройка:**
В `postgresql.conf` необходимо включить архивирование журналов:

```ini
wal_level = replica
archive_mode = on
archive_command = 'test ! -f /mnt/server/archivedir/%f && cp %p /mnt/server/archivedir/%f'
```

**Архивация WAL в S3 (через `archive_command`):**

```ini
archive_command = 'aws s3 cp %p s3://bucket/pg-wal/%f'
```

Для длительного хранения S3 с versioning защищает от случайного удаления WAL-файла. Альтернативы: `pgBackRest` (нативная S3-интеграция), `WAL-G`.

**Процесс восстановления:**

1. Остановить PostgreSQL.
2. Восстановить файлы из базового бэкапа (`pg_basebackup`) в пустой каталог данных.
3. Создать сигнальный файл восстановления: `touch $PGDATA/recovery.signal`.
4. В `postgresql.conf` указать параметры восстановления:

```ini
restore_command = 'cp /mnt/server/archivedir/%f %p'
recovery_target_time = '2026-02-02 18:14:00' # Целевое время
recovery_target_action = 'promote'          # Сделать мастером после восстановления
```

1. Запустить PostgreSQL.

### 4. Почему бэкап нужен при наличии репликации

Репликация (физическая и логическая) копирует все изменения с мастера — включая ошибочный `DROP TABLE`, логическую порчу данных и ошибки приложения. Реплика будет так же повреждена, как и мастер.

Бэкап решает три задачи, с которыми репликация не справляется:

1. **Защита от логических ошибок** — удалённые или испорченные данные восстанавливаются из бэкапа, а не из реплики, где они тоже испорчены.
2. **Долгосрочное хранение** — retention 90+ дней для аудита, compliance и расследования инцидентов.
3. **Restore на отдельный сервер** — анализ данных, отчёты, тестирование миграций без нагрузки на продакшен.

**Итог:** репликация = HA; бэкап = защита от логических ошибок + long-term retention.

### 5. Стратегия отстающей реплики

Для мгновенного «отката» без развертывания полных бэкапов настраивается реплика с задержкой:

```ini
# Настройка на стороне реплики
recovery_min_apply_delay = '4h'
```

Если на мастере случайно удалили данные, у администратора есть 4 часа, чтобы остановить реплику и извлечь данные до момента удаления.

### 6. Лучшие практики

| Компонент | Рекомендация |
|-----------|-------------|
| **Base backup** | Физический (`pg_basebackup` или pgBackRest) ежедневно |
| **WAL archiving** | Непрерывный, в S3 (versioning включён) или аналог |
| **Retention** | Минимум 90 дней для compliance |
| **Тест restore** | Ежеквартально — полное восстановление на отдельный сервер |
| **Restore-сервер** | Отдельный инстанс для периодического теста restore; он же — для аналитики без нагрузки на продакшен |
