# Резервное копирование и восстановление в PostgreSQL

## Определения

- **PITR (Point-in-Time Recovery)** — технология восстановления базы данных на произвольный момент времени в прошлом путем наката журналов транзакций (**WAL**) на базовую физическую копию.
- **RPO (Recovery Point Objective)** — целевая точка восстановления; объем данных, который допустимо потерять (например, «не более 5 минут данных»).
- **RTO (Recovery Time Objective)** — целевое время восстановления; допустимая длительность простоя системы.
- **Логический бэкап** — выгрузка данных в виде SQL-запросов или структурированного архива (утилита `pg_dump`).
- **Физический бэкап** — побайтовая копия файлов данных и журналов транзакций (утилита `pg_basebackup`).
- **Инкрементальный бэкап** — копия только тех блоков данных, которые изменились с момента последнего полного или инкрементального бэкапа (встроено в PostgreSQL 17+).

## Базовые концепции

### Логический vs Физический бэкап

| Характеристика | Логический (`pg_dump`) | Физический (`pg_basebackup`) |
| :--- | :--- | :--- |
| **Скорость создания** | Медленно (чтение через SQL) | Быстро (прямое копирование файлов) |
| **Скорость восстановления** | Очень медленно (выполнение SQL) | Быстро (копирование файлов + WAL) |
| **Гранулярность** | Таблицы, схемы, базы | Только весь кластер (инстанс) |
| **Версионность** | Можно восстановить на другую версию | Только та же мажорная версия |
| **PITR** | Не поддерживается | Основа для PITR |

### Механизм WAL и архивация
Для реализации PITR необходимо хранить не только базовый бэкап, но и все изменения (Write Ahead Log), произошедшие после него.
1.  **archive_mode**: Включение режима архивации журналов.
2.  **archive_command**: Команда для отправки заполненных WAL-сегментов в безопасное хранилище (S3, отдельный сервер).

### Инкрементальное резервное копирование (PostgreSQL 17+)
Начиная с версии 17, PostgreSQL поддерживает нативные инкрементальные бэкапы. Это значительно снижает нагрузку на сеть и дисковую систему, так как передаются только измененные блоки данных.

## Практические сценарии

### 1. Логическое резервное копирование (`pg_dump`)
Рекомендуется использовать формат `custom` (`-F c`), так как он сжат и позволяет параллельное восстановление.

```bash
# Бэкап одной базы данных
pg_dump -U postgres -d mydb -F c -f mydb.dump

# Восстановление в 4 потока (ускоряет процесс)
pg_restore -U postgres -d mydb -j 4 mydb.dump
```

### 2. Физическое резервное копирование (`pg_basebackup`)
Используется для создания базовой копии для реплик или PITR.

```bash
pg_basebackup -h master_host -D /var/lib/postgresql/backup -Fp -Xs -P -R
```
- `-Xs`: Включает необходимые WAL в бэкап.
- `-R`: Создает файл `standby.signal` для автоматического запуска в режиме реплики.

### 3. Профессиональные инструменты (pgBackRest)
**pgBackRest** — стандарт де-факто для крупных инсталляций. Поддерживает:
- Параллельное сжатие и передачу.
- Дельта-восстановление (перезапись только изменившихся файлов).
- Нативную интеграцию с S3/GCS/Azure.
- Управление временем хранения (Retention).

**Пример конфигурации архивации:**
```ini
# postgresql.conf
archive_command = 'pgbackrest --stanza=db_main archive-push %p'
```

### 4. Восстановление на точку времени (PITR)
Пример сценария: восстановление на состояние за 5 минут до ошибочного `DROP TABLE`.

1.  Остановить сервер и очистить каталог данных (`PGDATA`).
2.  Восстановить файлы из последнего полного бэкапа.
3.  Создать файл `recovery.signal` в корне `PGDATA`.
4.  Настроить параметры в `postgresql.conf` (или через `ALTER SYSTEM`):
    ```sql
    restore_command = 'cp /mnt/archived_wals/%f %p'
    recovery_target_time = '2026-07-18 10:00:00 MSK'
    recovery_target_action = 'promote'
    ```
5.  Запустить сервер. PostgreSQL применит WAL-логи до указанной метки и станет доступным для записи.

### 5. Резервное копирование в Kubernetes
Использование оператора **CloudNativePG** (рекомендуется):
- Автоматическое управление расписанием бэкапов.
- Нативная отправка в S3 (AWS, MinIO).
- Декларативное описание PITR через объект `Backup`.
