# PostgreSQL Backup and Recovery

## Definitions

* **RTO (Recovery Time Objective) и RPO (Recovery Point Objective):** Ключевые метрики, определяющие требования к процессу восстановления. Подробно рассмотрены в **[SRE Concepts: SLA, SLO, SLI](../../../Concepts/sre_concepts_main.md)**.
* **Point-in-Time Recovery (PITR):** Технология восстановления базы данных на произвольный момент времени. Реализуется путем применения журналов транзакций ([WAL](../../../Concepts/write_ahead_log.md)) к базовой резервной копии. Позволяет восстановить состояние БД за секунду до совершения фатальной ошибки (например, `DROP TABLE`).
* **MVCC (Multi-Version Concurrency Control):** Механизм управления параллельным доступом в PostgreSQL. Каждая транзакция работает со «снимком» данных, что позволяет `pg_dump` создавать консистентные логические бэкапы, не блокируя операции в базе.

## Basic Concepts

Фундаментальные подходы к резервному копированию (логическое/физическое, горячее/холодное), а также классификация по объему данных (полное, дифференциальное, инкрементальное) описаны в **[Database Backup Strategies](../../../Concepts/backups.md)**.

**Специфика PostgreSQL:**

* **Логическое резервное копирование (`pg_dump`, `pg_dumpall`):** Всегда полное.
* **Физическое резервное копирование (`pg_basebackup`):** Всегда полное.
* **Инкрементальные и дифференциальные бэкапы:** Встроенные инструменты отсутствуют. Функциональность реализуется сторонними утилитами (pgBackRest, WAL-G), анализирующими WAL-файлы.

## Practical Scenarios

### Logical Backup and Restore

#### `pg_dump`: Дамп одной базы данных

* **Рекомендуемый формат `custom` (`-F c`):** Сжатый, позволяет параллельное и выборочное восстановление.

    ```bash
    pg_dump -U postgres -d your_db -F c -Z 9 -f /path/to/your_db.dump
    ```

* **Дамп в виде SQL-скрипта:**

    ```bash
    pg_dump -U postgres -d your_db | gzip > /path/to/your_db.sql.gz
    ```

* **Дамп только схемы (`-s`) или только данных (`-a`):**

    ```bash
    pg_dump -s -d your_db > schema.sql
    pg_dump -a -d your_db > data.sql
    ```

#### `pg_restore`: Восстановление из архива `pg_dump`

* **Восстановление из SQL-скрипта (через `psql`):**

    ```bash
    gunzip -c /path/to/your_db.sql.gz | psql -U postgres -d your_db
    ```

* **Параллельное восстановление из custom-формата (`-j`):**

    ```bash
    pg_restore -U postgres -d your_db -j 4 /path/to/your_db.dump
    ```

#### `pg_dumpall`: Дамп всего кластера

Используется для копирования **глобальных объектов** (ролей, табличных пространств), которые `pg_dump` игнорирует.

* **Дамп только глобальных объектов:**

    ```bash
    pg_dumpall -g -U postgres > globals.sql
    ```

* **Полный дамп кластера:**

    ```bash
    pg_dumpall -U postgres > full_cluster.sql
    ```

### Physical Backup

#### `pg_basebackup`: Создание базовой копии

Создает полную бинарную копию кластера, подключаясь к серверу как реплика.

* **Команда:**

    ```bash
    pg_basebackup -h master_host -U replicator_user -D /path/to/backup_dir -F p -Xs -P -R
    ```

  * `-D`: Целевой каталог.
  * `-F p`: Формат `plain` (обычные файлы, готовые к запуску).
  * `-Xs`: Включить в бэкап WAL-файлы, сгенерированные во время копирования.
  * `-P`: Показывать прогресс.
  * `-R`: Создать файлы конфигурации для запуска реплики из бэкапа.

* **Восстановление:**
    1. Разместить файлы из каталога бэкапа в пустой `PGDATA` директории нового сервера.
    2. Запустить PostgreSQL. Он автоматически войдет в режим восстановления.

> **Важно:** Для полноценного **PITR** одного `pg_basebackup` недостаточно. Необходимо настроить непрерывное **архивирование WAL-сегментов** с помощью `archive_mode` и `archive_command`.

### Point-in-Time Recovery (PITR)

Сценарий описывает ручное восстановление на состояние до сбоя.

**Шаг 1: Настройка архивирования WAL (превентивно)**

1. **Создать каталог для архивов:**

    ```bash
    mkdir /path/to/wal_archive && chown postgres:postgres /path/to/wal_archive
    ```

2. **Настроить `postgresql.conf`:**

    ```ini
    wal_level = replica      # Уровень журналирования для репликации и архивирования
    archive_mode = on        # Включить режим архивирования
    archive_command = 'cp %p /path/to/wal_archive/%f' # Команда копирования WAL-сегмента
    ```

3. **Перезагрузить PostgreSQL** для применения настроек.

**Шаг 2: Создание базового бэкапа**

Регулярно создавайте свежие базовые бэкапы с помощью `pg_basebackup`.

```bash
pg_basebackup -h master_host -U postgres -D /path/to/base_backup -F p -Xs -P
```

**Шаг 3: Процесс восстановления (после сбоя)**

Задача: восстановить состояние на `18:14`, если сбой произошел в `18:15`.

1. **Остановить сервис:** `systemctl stop postgresql`.
2. **Очистить каталог данных:**
    * Сделайте резервную копию старого каталога `PGDATA`.
    * `mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main_old`
    * `mkdir /var/lib/postgresql/16/main && chown postgres:postgres /var/lib/postgresql/16/main && chmod 700 /var/lib/postgresql/16/main`
3. **Восстановить базовый бэкап:**
    `cp -a /path/to/base_backup/* /var/lib/postgresql/16/main/`
4. **Настроить восстановление:**
    * Создайте "сигнальный" файл: `touch /var/lib/postgresql/16/main/recovery.signal`.
    * Добавьте в `postgresql.conf`:

        ```ini
        # Команда для получения WAL-файлов из архива
        restore_command = 'cp /path/to/wal_archive/%f %p'

        # Целевая точка восстановления
        recovery_target_time = '2026-02-02 18:14:00' 
        # Завершить восстановление и начать работу в обычном режиме
        recovery_target_action = 'promote' 
        ```

5. **Запустить сервис:** `systemctl start postgresql`.
    Сервер запустится в режиме восстановления, применит WAL-файлы до указанной точки времени и станет primary-сервером.
6. **Проверить состояние:** `SELECT pg_is_in_recovery();` должен вернуть `false`.

### Lagging Replica Strategy

* **Проблема:** Случайное выполнение деструктивной команды на мастер-сервере (например, `DROP TABLE`), которая практически мгновенно реплицируется на все "горячие" реплики, делая восстановление через `failover` бесполезным. Восстановление из бэкапа (PITR) может занять слишком много времени.

* **Решение:** Создать специальную "отстающую" реплику, которая намеренно применяет WAL-файлы с задержкой (например, на несколько часов). Это создает "окно времени" для быстрого реагирования на человеческие ошибки.

* **Реализация:** На сервере-реплике в файле `postgresql.conf` (или в `recovery.conf` для старых версий) устанавливается параметр:

    ```ini
    # Задержка в 3 часа
    recovery_min_apply_delay = '3h'
    ```

* **Процесс восстановления:**
    1. При возникновении инцидента на мастере, немедленно останавливается процесс применения WAL на отстающей реплике.
    2. Реплика повышается до мастера, ее состояние "замораживается" на моменте времени до инцидента.
    3. Данные с "новой" мастер-базы используются для восстановления основной инфраструктуры.

* **Преимущества:** Значительно более низкие RTO (время восстановления) по сравнению с полным восстановлением из бэкапа.
* **Недостатки:** Требует дополнительного сервера и приводит к потере данных, записанных за время задержки.

> **Связанные концепции:** Отстающая реплика — это элемент стратегии высокой доступности. Подробнее об автоматическом failover см. **[Высокая доступность](./high_availability.md)**.

### COPY for Fast Table Export/Import

Оптимально для очень больших таблиц.

* **Экспорт в CSV:**
    `COPY your_table TO '/path/to/backup.csv' WITH (FORMAT CSV, HEADER);`
* **Импорт из CSV:**
    `COPY your_table FROM '/path/to/backup.csv' WITH (FORMAT CSV, HEADER);`
