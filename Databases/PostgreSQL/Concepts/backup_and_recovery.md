# Стратегии резервного копирования PostgreSQL

## 1. Определения

1.  **Правило "3-2-1" резервирования данных:**
    *   Иметь не менее **трех** экземпляров данных.
    *   Хранить копии не менее чем на **двух** различных носителях.
    *   Хранить не менее **одной** копии данных за пределами офиса (на удаленной площадке).
2.  **RTO (Recovery Time Objective):** Целевое время восстановления — время, требуемое на восстановление резервной копии.
3.  **RPO (Recovery Point Objective):** Целевая точка восстановления — точка во времени, на которую должны быть восстановлены данные (например, до 24 часов с момента сбоя).
4.  **Уровни резервного копирования:**
    *   **Полное (Full):** Копируется весь набор данных. Для восстановления требуется только эта копия.
    *   **Дифференциальное (Differential):** Копируются только изменения с момента последнего полного резервного копирования. Для восстановления требуется последняя полная и последняя дифференциальная копии.
    *   **Инкрементальное (Incremental):** Копируются только изменения с момента последнего *любого* бэкапа.
5.  **Point-in-Time Recovery (PITR):** Восстановление на определенный момент времени, которое достигается путем применения [журналов предзаписи (WAL)](../../../Concepts/write_ahead_log.md) к базовой резервной копии.

## 2. Основные концепции

PostgreSQL, как и многие другие СУБД, реализует два фундаментальных подхода к резервному копированию, подробно описанных в [общей концепции бэкапов](../../../Databases/Concepts/backups.md):

*   **[Логическое резервное копирование](../../../Databases/Concepts/backups.md#горячий-логический-бэкап):** Создает копию данных в виде исполняемого SQL-скрипта. Этот метод гибок и не зависит от версии или архитектуры, но может быть медленным для больших баз данных.
*   **[Физическое резервное копирование](../../../Databases/Concepts/backups.md#горячий-физический-бэкап):** Создает побайтовую копию файлов базы данных. Этот метод значительно быстрее, но менее гибок и привязан к версии и архитектуре СУБД.

Основным преимуществом физического бэкапа в PostgreSQL является возможность **восстановления на определенный момент времени (PITR)**.

## 3. Практические сценарии: Инструменты и команды

### 3.1. Логическое резервное копирование

#### Утилита `pg_dump`

`pg_dump` — утилита для создания "логических" резервных копий базы данных. Она выгружает объекты (схемы, таблицы, данные) в виде SQL-команд или в архивные форматы, которые можно переносить между разными версиями PostgreSQL (как правило, на более новую) и серверными архитектурами.

*   **Консистентность данных (MVCC):** `pg_dump` делает снимок состояния базы данных на момент своего запуска. Благодаря механизму [MVCC (Multi-Version Concurrency Control)](https://www.postgresql.org/docs/current/mvcc.html), дамп будет консистентным, даже если во время его создания другие транзакции изменяют данные.

##### Форматы вывода:

*   **Plain (текстовый SQL-скрипт):**
    ```bash
    pg_dump -U postgres -d your_database | gzip > /path/to/your_database_backup.sql.gz
    ```
*   **Custom (специальный сжатый формат):**
    ```bash
    pg_dump -U postgres -d your_database -F c -Z 9 -f /path/to/your_database_backup.dump
    ```
    -   `-F c`: Указывает формат `custom`. **Рекомендуемый формат**, так как позволяет выборочно восстанавливать объекты и поддерживает параллельное восстановление.
*   **Directory (каталог с файлами для каждого объекта):**
    ```bash
    pg_dump -U postgres -d your_database -j 4 -F d -f /path/to/your_database_backup_dir
    ```
    -   `-j 4`: Количество параллельных потоков. Обязательно требует формат `directory`.

##### Сценарии использования:

*   **Только схема или только данные:**
    - Флаги `-s` (`--schema-only`) и `-a` (`--data-only`) позволяют выгружать только структуру базы данных или только данные. Это полезно для миграций или для подготовки "чистой" схемы.
    ```bash
    pg_dump -s -d your_database > schema_only.sql
    pg_dump -a -d your_database > data_only.sql
    ```
*   **Резервное копирование отдельных таблиц (`-t` table / `-T` exclude table):**
    ```bash
    pg_dump -d your_database -t public.users > users_backup.sql
    ```

*   **Дамп схемы без данных для "тяжёлых" таблиц:**
    ```bash
    pg_dump -d your_database --exclude-table-data='*.log_table' > dump_with_empty_logs.sql
    ```

*   **Перенос данных между окружениями:**
    - Использование флагов `--no-owner` и `--no-privileges` позволяет избежать ошибок, если на целевом сервере нет тех же ролей или прав.
    ```bash
    pg_dump -d your_database --no-owner --no-privileges > portable_backup.sql
    ```

*   **Создание консистентного снимка для репликации:**
    - Флаг `--create-snapshot` используется в продвинутых сценариях, таких как [миграция без простоя](../Operations/zero_downtime_migration.md), для создания синхронизированного с WAL снимка, который можно использовать для запуска репликации.

#### Утилита `pg_restore` (восстановление из архивов)

Восстанавливает базу данных из архивов, созданных `pg_dump` (форматы `custom`, `tar`, `directory`).

*   **Восстановление из SQL-скрипта (через `psql`):**
    ```bash
    # Для несжатого файла
    psql -U postgres -d your_database -f /path/to/your_database_backup.sql
    # Для сжатого файла
    gunzip -c /path/to/your_database_backup.sql.gz | psql -U postgres -d your_database
    ```
*   **Параллельное восстановление из архива:**
    ```bash
    # Последовательное восстановление
    pg_restore -U postgres -d your_database /path/to/your_database_backup.dump
    # Параллельное восстановление (только для форматов custom и directory)
    pg_restore -U postgres -d your_database -j 4 /path/to/your_database_backup_dir
    ```

#### Утилита `pg_dumpall` (дамп всего кластера)

Создает полную копию всего кластера PostgreSQL, включая глобальные объекты (роли, табличные пространства), которые `pg_dump` пропускает.

*   **Полный дамп кластера:** `pg_dumpall -U postgres > /path/to/full_cluster_backup.sql`
*   **Только глобальные объекты:** `pg_dumpall -g -U postgres > globals.sql`

#### Команда `COPY` (для отдельных таблиц)

Используется для быстрого экспорта/импорта данных одной таблицы в формате CSV/бинарном.

*   **Экспорт:** `COPY your_table TO '/path/to/backup.csv' WITH (FORMAT CSV, HEADER);`
*   **Импорт:** `COPY your_table FROM '/path/to/backup.csv' WITH (FORMAT CSV, HEADER);`

### 3.2. Физическое резервное копирование

Физический бэкап работает на уровне файлов файловой системы, копируя файлы данных и журналы предзаписи (WAL).

*   **Преимущества:** Позволяет выполнять PITR и значительно быстрее для больших баз данных.
*   **Недостатки:** Негибкий, можно восстановить только весь кластер целиком на совместимой архитектуре.

#### Виды физического резервирования:

1.  **Холодный бэкап:**
    *   Выполняется, когда база данных полностью остановлена.
    *   Требуется скопировать только файлы данных (`PGDATA`).
    *   Если сервер был остановлен некорректно, дополнительно требуются WAL-сегменты.
2.  **Горячий бэкап:**
    *   Выполняется на работающем экземпляре базы данных.
    *   Требуется скопировать как файлы данных, так и все WAL-сегменты, сгенерированные во время копирования.
    *   Необходимо контролировать, чтобы сервер сохранял WAL-файлы на время копирования основных данных.

### Инструменты и команды:

#### Утилита `pg_basebackup`

Создает полную бинарную копию кластера, подключаясь к серверу по протоколу репликации.

*   **Создание базовой резервной копии:**
    ```bash
    pg_basebackup -h localhost -U postgres -D /path/to/backup_dir -F p -Xs -P -R
    ```
    -   `h`, `p`, `U`: Параметры подключения к серверу.
    -   `D /path/to/backup_directory`: Целевой каталог для бэкапа.
    -   `F p`: Указывает формат `plain` (обычный, не сжатый).
    -   `Xs`: Включает WAL-файлы в бэкап.
    -   `P`: Показывает прогресс.
    -   `R`: Создает файл `standby.signal` и `postgresql.auto.conf` (или `recovery.conf` для старых версий) для настройки восстановления/реплики.
*   **Восстановление:**
    1.  Развернуть созданную автономную копию в новый (или пустой) каталог данных.
    2.  Запустить PostgreSQL. Он автоматически начнет процесс восстановления, используя WAL-файлы, если они были включены в бэкап или доступны из WAL-архива.
    
    **Важно:** Для восстановления на определенный момент времени может потребоваться настроить WAL-архивирование (`archive_mode`, `archive_command`) на мастере.
