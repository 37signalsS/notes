# Стратегии резервного копирования PostgreSQL

### Определения

*   **Правило "3-2-1":** Классическая мнемоника для стратегии бэкапов: **3** копии данных на **2** разных носителях, **1** из которых находится на удаленной площадке.
*   **RTO (Recovery Time Objective) и RPO (Recovery Point Objective):** Ключевые метрики, определяющие требования к процессу восстановления. Подробно рассмотрены в основной заметке о концепциях SRE: **[Концепции SRE: SLA, SLO, SLI и метрики надежности](../../../Concepts/SRE/sre_concepts_main.md)**.
*   **Point-in-Time Recovery (PITR):** Восстановление на определенный момент времени. Технология, которая позволяет восстановить базу данных в состояние на любую произвольную точку во времени между двумя полными бэкапами. Реализуется путем "накатывания" журналов транзакций ([WAL](../../../Concepts/write_ahead_log.md)) на базовую резервную копию.
*   **MVCC (Multi-Version Concurrency Control):** Механизм управления параллельным доступом, используемый в PostgreSQL. Каждая транзакция работает со "снимком" данных, что позволяет `pg_dump` создавать консистентные бэкапы, не блокируя другие операции в базе.

### Основные концепции

В PostgreSQL, как и в большинстве СУБД, существует два фундаментальных подхода к резервному копированию. Подробно они описаны в [общей концепции бэкапов](../../../Databases/Concepts/backups.md).

#### Логическое vs. Физическое резервное копирование

*   **Логическое резервное копирование:**
    *   **Суть:** Сохранение данных в виде набора SQL-команд (`INSERT`, `CREATE TABLE` и т.д.).
    *   **Инструмент:** `pg_dump`, `pg_dumpall`.
    *   **Преимущества:** Гибкость (можно восстановить отдельные таблицы), независимость от версии и архитектуры ОС/PostgreSQL.
    *   **Недостатки:** Медленнее для больших объемов, не поддерживает PITR.

*   **Физическое резервное копирование:**
    *   **Суть:** Побайтовое копирование файлов базы данных.
    *   **Инструмент:** `pg_basebackup`, сторонние утилиты (pgBackRest, WAL-G).
    *   **Преимущества:** Значительно быстрее для больших баз, **позволяет выполнять PITR**.
    *   **Недостатки:** Менее гибкое (обычно восстанавливается весь кластер), привязано к мажорной версии PostgreSQL и архитектуре ОС.

#### Холодное vs. Горячее резервное копирование

*   **Холодный бэкап (Cold Backup):** Выполняется при полностью остановленной базе данных. Самый простой и надежный способ, но требует простоя.
*   **Горячий бэкап (Hot Backup):** Выполняется на работающей базе данных без прерывания обслуживания. Это стандарт для production-систем. Все описанные ниже инструменты (`pg_dump`, `pg_basebackup`) создают именно горячие бэкапы.

### Практические сценарии

#### 1. Логическое резервное копирование и восстановление

##### `pg_dump`: Дамп одной базы данных

*   **Рекомендуемый формат `custom` (-F c):** Сжатый, позволяет параллельное восстановление и выборочное восстановление объектов.
    ```bash
    pg_dump -U postgres -d your_db -F c -Z 9 -f /path/to/your_db.dump
    ```
*   **Текстовый SQL-скрипт:**
    ```bash
    pg_dump -U postgres -d your_db | gzip > /path/to/your_db.sql.gz
    ```
*   **Дамп только схемы (`-s`) или только данных (`-a`):**
    ```bash
    pg_dump -s -d your_db > schema.sql
    pg_dump -a -d your_db > data.sql
    ```
*   **Дамп с исключением данных некоторых таблиц:**
    ```bash
    pg_dump -d your_db --exclude-table-data='*.log_table' > dump.sql
    ```
*   **Дамп отдельных таблиц (`-t`):**
    ```bash
    pg_dump -d your_db -t public.users -t public.orders > tables.sql
    ```

##### `pg_restore`: Восстановление из архива `pg_dump`

*   **Восстановление из SQL-скрипта (через `psql`):**
    ```bash
    gunzip -c /path/to/your_db.sql.gz | psql -U postgres -d your_db
    ```
*   **Параллельное восстановление из custom-формата (`-j`):**
    ```bash
    pg_restore -U postgres -d your_db -j 4 /path/to/your_db.dump
    ```

##### `pg_dumpall`: Дамп всего кластера

Используется для копирования **глобальных объектов** (ролей, табличных пространств), которые `pg_dump` игнорирует.

*   **Дамп только глобальных объектов:**
    ```bash
    pg_dumpall -g -U postgres > globals.sql
    ```
*   **Полный дамп всего кластера (всех БД и глобальных объектов):**
    ```bash
    pg_dumpall -U postgres > full_cluster.sql
    ```

##### `COPY`: Быстрый экспорт/импорт одной таблицы

Оптимально для очень больших таблиц.

*   **Экспорт в CSV:**
    `COPY your_table TO '/path/to/backup.csv' WITH (FORMAT CSV, HEADER);`
*   **Импорт из CSV:**
    `COPY your_table FROM '/path/to/backup.csv' WITH (FORMAT CSV, HEADER);`

#### 2. Физическое резервное копирование и восстановление

##### `pg_basebackup`: Создание базового бэкапа

Создает полную бинарную копию кластера, подключаясь к серверу как реплика.

*   **Создание базовой копии с WAL-файлами:**
    ```bash
    pg_basebackup -h master_host -U replicator_user -D /path/to/backup_dir -F p -Xs -P -R
    ```
    *   `-D`: Целевой каталог.
    *   `-F p`: Формат `plain` (обычные файлы, готовые к запуску).
    *   `-Xs`: Включить в бэкап WAL-файлы, сгенерированные во время копирования (stream).
    *   `-P`: Показывать прогресс.
    *   `-R`: Создать файлы конфигурации для реплики (`standby.signal` и `postgresql.auto.conf`), что упрощает запуск standby-сервера из бэкапа.

*   **Восстановление:**
    1.  Разместить файлы из каталога бэкапа в пустой `PGDATA` директории нового сервера.
    2.  Запустить PostgreSQL. Он автоматически войдет в режим восстановления и применит WAL-файлы, находящиеся в `pg_wal`.

> **Важно:** Для полноценного **PITR** простого `pg_basebackup` недостаточно. Необходимо настроить непрерывное **архивирование WAL-сегментов** с помощью `archive_mode` и `archive_command` в `postgresql.conf`. Это позволит восстановить базу на любую точку времени, используя базовый бэкап и нужные сегменты из архива.

### 3. Восстановление на определенный момент времени (PITR): Пошаговый сценарий

Этот сценарий описывает процесс ручного восстановления базы данных на определенную точку во времени (например, до момента выполнения ошибочной транзакции).

#### Шаг 1: Настройка архивирования WAL (превентивная мера)

Эта настройка должна быть выполнена на рабочем сервере *до* возникновения сбоя.

1.  **Создать каталог для архивов WAL:**
    ```bash
    mkdir /path/to/wal_archive
    chown postgres:postgres /path_to/wal_archive
    ```
2.  **Настроить `postgresql.conf`:**
    ```ini
    # Уровень журналирования, достаточный для репликации и архивирования
    wal_level = replica 

    # Включаем режим архивирования
    archive_mode = on

    # Команда для копирования сегмента WAL в архив
    # %p - путь к файлу WAL, %f - имя файла
    archive_command = 'cp %p /path/to/wal_archive/%f'
    ```
3.  **Перезагрузить PostgreSQL** для применения настроек.

#### Шаг 2: Создание базового бэкапа

Регулярно создавайте свежие базовые бэкапы с помощью `pg_basebackup`.

```bash
pg_basebackup -h master_host -U postgres -D /path/to/base_backup -F p -Xs -P
```

#### Шаг 3: Процесс восстановления (после сбоя)

Предположим, в `18:15` произошла ошибочная операция, и нам нужно восстановиться на состояние `18:14`.

1.  **Остановить сервер PostgreSQL:**
    ```bash
    systemctl stop postgresql
    ```
2.  **Очистить каталог данных:**
    Переименуйте или удалите старый каталог `PGDATA` (например, `/var/lib/postgresql/16/main`). Перед удалением рекомендуется сделать его резервную копию.
    ```bash
    # Резервное копирование на всякий случай
    mv /var/lib/postgresql/16/main /var/lib/postgresql/16/main_old
    mkdir /var/lib/postgresql/16/main
    chown postgres:postgres /var/lib/postgresql/16/main
    chmod 700 /var/lib/postgresql/16/main
    ```
3.  **Восстановить базовый бэкап:**
    Скопируйте содержимое базового бэкапа в пустой каталог `PGDATA`.
    ```bash
    cp -a /path/to/base_backup/* /var/lib/postgresql/16/main/
    ```
4.  **Настроить восстановление:**
    В каталоге `PGDATA` создайте файл `recovery.signal`. Затем в `postgresql.conf` (или `postgresql.auto.conf`) добавьте команды для восстановления.
    ```bash
    touch /var/lib/postgresql/16/main/recovery.signal
    ```
    Добавьте в `postgresql.conf`:
    ```ini
    # Команда для получения WAL-файлов из архива
    restore_command = 'cp /path/to/wal_archive/%f %p'

    # Указание целевой точки восстановления
    recovery_target_time = '2026-01-05 18:14:00' 
    recovery_target_action = 'promote' # После достижения цели, завершить восстановление и начать работать в обычном режиме
    ```
    *   Вместо `recovery_target_time` можно использовать `recovery_target_xid` (ID транзакции) или `recovery_target_lsn` (позиция в WAL).
    *   `recovery_target_action = 'promote'` (начиная с v12) автоматически завершает режим восстановления. В старых версиях использовался `pause`.

5.  **Запустить сервер PostgreSQL:**
    ```bash
    systemctl start postgresql
    ```
    Сервер запустится в режиме восстановления. Он будет последовательно читать WAL-файлы из архива и применять их до тех пор, пока не достигнет указанной точки `recovery_target_time`. После этого он завершит режим восстановления (файл `recovery.signal` будет переименован в `recovery.done`) и начнет работать как обычный primary-сервер.

6.  **Проверить состояние:** Убедитесь, что база данных восстановилась на нужный момент и готова к работе.
    ```sql
    -- Запрос должен вернуть false
    SELECT pg_is_in_recovery(); 
    ```
