# Резервное копирование и восстановление в PostgreSQL

**Актуально для:** PostgreSQL 13–18

## Определения

- **PITR (Point-in-Time Recovery)** — технология восстановления базы данных на произвольный момент времени в прошлом путём «проигрывания» журналов транзакций (**WAL**) поверх базовой физической копии (Base Backup).
- **RPO (Recovery Point Objective)** — целевая точка восстановления; максимально допустимый объём потери данных в случае сбоя (например, «не более 5 минут транзакций»).
- **RTO (Recovery Time Objective)** — целевое время восстановления; допустимая длительность простоя системы с момента сбоя до возврата в рабочее состояние.
- **Base Backup (базовый бэкап)** — побайтовая копия файлов данных всего кластера, снятую с работающего сервера (`pg_basebackup` или низкоуровневый API). Основа для PITR и для развёртывания реплик.
- **Логический бэкап** — выгрузка структуры и данных в виде SQL-запросов (plain text) или проприетарного сжатого архива (утилита `pg_dump`).
- **Физический бэкап** — побайтовая копия файлов данных (блоков), конфигураций и журналов транзакций всего кластера БД (утилита `pg_basebackup`).
- **WAL-сегмент** — единица архивации WAL; по умолчанию 16 МБ (задаётся при `initdb` через `wal_segment_size`).
- **Инкрементальный бэкап** — копия только тех блоков данных, которые изменились с момента предыдущего бэкапа (встроено в PostgreSQL 17+ через WAL-summarization).
- **Дифференциальный бэкап** — копия всех изменений с момента последнего **полного** бэкапа (реализуется внешними инструментами, такими как `pgBackRest`).
- **Asynchronous I/O (AIO) (PG 18+)** — нативная подсистема асинхронного ввода-вывода (`io_method = worker | io_uring | sync`). Позволяет бэкендам ставить в очередь несколько запросов на чтение одновременно, что ускоряет sequential scan, bitmap heap scan, VACUUM и ANALYZE. Не влияет на `archive_command` (внешний процесс) и не ускоряет само копирование файлов в `pg_basebackup`. Мониторинг: представление `pg_aios`.
- **Таймлайн (Timeline ID)** — идентификатор ветки развития БД. Создаётся при каждом выполнении PITR или продвижении (promote) реплики, предотвращая перезапись WAL из разных сессий восстановления.
- **Манифест бэкапа (backup_manifest)** — файл в формате JSON со списком всех файлов бэкапа (размеры, время модификации, опциональные контрольные суммы), идентификатором таймлайна и диапазонами WAL, необходимых для восстановления. Критически важен для инкрементальных копий и валидации через `pg_verifybackup`. Создаётся `pg_basebackup` по умолчанию (с PG 13).

## Базовые концепции

### Сравнение методов резервного копирования

| Характеристика | Логический (`pg_dump`) | Физический (`pg_basebackup`) |
| :--- | :--- | :--- |
| **Скорость создания** | Низкая (полное сканирование таблиц) | Высокая (побайтовое копирование файлов) |
| **Скорость восстановления** | Очень низкая (COPY/INSERT + построение индексов) | Высокая (копирование файлов + накат WAL) |
| **Гранулярность** | Высокая (таблица, схема, база) | Низкая (только весь кластер) |
| **Версионность** | Между мажорными версиями и архитектурами (клиент `pg_dump` должен быть не ниже мажорной версии сервера) | Только та же мажорная версия и архитектура ОС |
| **Влияние на нагрузку** | Умеренное: `pg_dump` **не блокирует** других пользователей (чтение и запись), но держит снапшот транзакции, мешая `VACUUM` очищать мёртвые строки | Умеренное (чтение файлов; лимит через `-r`) |
| **Поддержка PITR** | Отсутствует | Фундаментальная основа |

> Официальная документация (с PG 18) прямо указывает: `pg_dump` **как правило не является правильным выбором для регулярных бэкапов production-БД** — используйте физические бэкапы с непрерывной архивацией WAL (глава «Backup and Restore»).

#### Форматы логического бэкапа (`pg_dump`)

PostgreSQL поддерживает несколько форматов выгрузки, каждый из которых имеет свою нишу:

| Формат | Флаг | Описание | Восстановление | Когда использовать |
| :--- | :--- | :--- | :--- | :--- |
| **Plain** | `-F p` | Текстовый SQL-дамп. | `psql < dump.sql` | Миграции, version control, чтение человеком. |
| **Custom** | `-F c` | Проприетарный архив, сжат по умолчанию (gzip, умеренный уровень). Поддерживает параллельную загрузку и выборку отдельных объектов. | `pg_restore -j 4 db.dump` | **Production default**. Большие БД (>50 ГБ), частичное восстановление. |
| **Tar** | `-F t` | Архив в формате tar. **Сжатие не поддерживается вообще** (ни в какой версии). Порядок табличных данных при restore менять нельзя; параллельный restore (`-j`) не поддерживается — только custom и directory. | `pg_restore db.tar` | Совместимость со старыми инструментами; ручная обработка стандартными средствами Unix. |
| **Directory** | `-F d` | Каталог файлов (TOC + по файлу на таблицу/блоб). Единственный формат с параллельным **экспортом**; сжат по умолчанию. | `pg_restore -j 8 dir/` | Очень большие БД (>500 ГБ), максимальный параллелизм. |

**Компрессия (PG 15+):**
- `--compress=method:level` (или `-Z level`), где `method` ∈ `gzip`, `lz4`, `zstd`, `none`. Например, `--compress=zstd:3`. ZSTD/lz4 появились в **PG 15** (не 17).
- `custom` и `directory` сжаты по умолчанию; `--compress=0`/`none` отключает.
- `plain` по умолчанию не сжимается; ненулевой уровень сжимает весь вывод целиком.

**Параллелизм:**
- Формат `directory` (`-F d`) обязателен для параллельного **экспорта** (`-j N`); требует synchronized snapshots (PG 9.2+ primary, 10+ standby).
- Формат `custom` (`-F c`) поддерживает параллельный **импорт** через `pg_restore -j N`, но экспорт всегда однопоточный.

**Примеры:**
```bash
# Custom + ZSTD + параллельный restore (4 потока)
pg_dump -h localhost -U backup_user -d mydb -F c --compress=zstd:3 -f /backups/mydb.dump
pg_restore -h localhost -U postgres -d mydb_restored -j 4 /backups/mydb.dump

# Directory + максимальный параллелизм (export и import)
pg_dump -h localhost -U backup_user -d mydb -F d -j 8 --compress=zstd:1 -f /backups/mydb_dir
pg_restore -h localhost -U postgres -d mydb_restored -j 8 /backups/mydb_dir

# Plain для миграций и audit
pg_dump -h localhost -U backup_user -d mydb -F p > /backups/mydb_20260817.sql
```

**Важно:** `pg_dump` не поддерживает PITR. Он создаёт снапшот на момент начала выполнения дампа. Долгий `pg_dump` удерживает транзакцию, что мешает `VACUUM` очищать старые версии строк (Bloat). Запускайте дампы в часы минимальной нагрузки и читайте stderr — предупреждения (права, исключённые объекты) печатаются туда.

#### Почему восстановление из дампа замедляется с ростом БД

Дамп под капотом — не «копия базы», а набор инструкций по сборке базы заново: схема, `COPY`/`INSERT`, затем `CREATE INDEX`. При восстановлении данные сначала наливаются с нуля из SQL, и только потом начинается создание индексов. На большой базе построение индексов занимает значительное время и потребляет много ресурсов CPU и диска. Поэтому время восстановления растёт вместе с размером БД, и для продукта это превращается в долгий простой. Параллельный `pg_restore -j N` ускоряет процесс, но не устраняет саму природу проблемы.

Компенсирующие плюсы логического дампа: возможность восстановить отдельные таблицы, развернуть данные в другую базу внутри того же инстанса (дамп не привязан к файловому layout кластера) и читаемость plain-формата (`pg_dump -F p`) обычным просмотром/грепом.

### Журналы транзакций (WAL) и архивация

Механизм **Write Ahead Log** обеспечивает атомарность и долговечность (ACID). Для восстановления на момент времени необходимо сохранять не только базовую копию, но и непрерывный поток WAL-сегментов.

1. **archive_mode**: `on` для включения процесса архивации (значение `always` дополнительно архивирует на standby).
2. **wal_level**: для PITR и репликации требуется `replica` (по умолчанию в 10+) или `logical`.
3. **archive_command**: команда или скрипт для копирования заполненного сегмента в хранилище.
   *Пример:* `archive_command = 'test ! -f /mnt/wal_archive/%f && cp %p /mnt/wal_archive/%f'`
4. **archive_library** (PG 15+): альтернатива `archive_command` — архивация через загружаемый модуль (без порождения внешнего процесса на каждый сегмент).
5. **archive_timeout**: принудительное переключение на новый сегмент, если с последнего переключения прошло N секунд **и была любая активность** (включая чекпоинт). Default `0` (выключено). Сегменты, закрытые досрочно, всё равно занимают полные 16 МБ — слишком короткое значение раздувает архив; значения порядка минуты обычно разумны. Это нижняя граница RPO, а не гарантия.

**Альтернатива `archive_command` — `pg_receivewal`:** утилита (с PG 10) стримит WAL в реальном времени через протокол репликации в локальный каталог, не дожидаясь заполнения сегмента, поэтому `archive_timeout` с ней не нужен. Полученный каталог можно использовать напрямую как `archive_location` при восстановлении.

**Мониторинг:** здоровье архивации видно в `pg_stat_archiver` (запрос — в разделе «Лучшие практики»).

### Инкрементальное копирование в PostgreSQL 17

В версии 17 реализована нативная поддержка инкрементальных бэкапов через процесс **WAL summarization**.

- **Принцип работы**: фоновый процесс summarizer анализирует WAL и создаёт компактные файлы-сводки в `pg_wal/summaries`, в которых указано, какие блоки данных изменились. Сервер при инкрементальном бэкапе заменяет изменённые relation-файлы компактными файлами с изменёнными блоками.
- **Параметры**: `summarize_wal = on` (default **off**; только `postgresql.conf`, релоад; нельзя стартовать с `summarize_wal=on` при `wal_level=minimal`), `wal_summary_keep_time` (default 10 дней — сколько хранить старые сводки).
- **Создание**: `pg_basebackup --incremental=<путь_к_backup_manifest_предыдущего_бэкапа>`.
- **Восстановление**: цепочки объединяются `pg_combinebackup` в синтетический полный бэкап.
- **Ограничения**: инкрементальный бэкап невозможен при наличии дополнительных tablespace и при использовании `-X stream`; требует, чтобы сводки не были удалены и summarizer успел догнать; возможен только если replay начинается с более позднего чекпоинта, чем у предыдущего бэкапа; для heavily-modified БД выигрыш в размере небольшой. PostgreSQL не отслеживает, какие бэкапы ещё нужны цепочке, — базовые копии надо хранить вручную.
- **Инструмент**: `pg_walsummary` печатает содержимое файлов-сводок.

### Низкоуровневый API онлайн-бэкапа (PG 15+)

Для файлового копирования своими средствами (rsync и т. п.) предусмотрен неблокирующий (non-exclusive) API — можно несколько одновременных бэкапов:

1. `SELECT pg_backup_start('label');` → возвращает стартовый LSN (без `fast` — чекпоинт распределённый; `pg_backup_start('label', true)` — немедленный чекпоинт, всплеск I/O).
2. Скопировать файлы данных (например, `rsync`).
3. `SELECT * FROM pg_backup_stop();` → возвращает запись `(lsn, labelfile, spcmapfile)`; содержимое `labelfile` записать в файл `backup_label` в корне копии, `spcmapfile` — в `tablespace_map`. `pg_backup_stop` по умолчанию ждёт архивации последнего WAL.

Функции доступны суперпривилегии по умолчанию; `EXECUTE` можно выдать другой роли. Имена `pg_start_backup()`/`pg_stop_backup()` — до PG 15.

### Переключение таймлайнов

При выполнении PITR PostgreSQL переключается на новый таймлайн (например, с 1 на 2). Это позволяет:
- Избежать конфликтов имен WAL-файлов.
- Проследить историю восстановлений.
- Выполнить восстановление «из будущего» по отношению к предыдущей точке восстановления, если это необходимо (для сложных повторных восстановлений — параметр `recovery_target_timeline`).

## Практические сценарии

### 1. Логическое резервное копирование (`pg_dump`, `pg_dumpall`)

Оптимально для миграций, частичного восстановления или небольших БД (< 100 ГБ).

#### Предпосылки
- Версия клиента (`pg_dump`) должна быть не ниже мажорной версии сервера (более новый клиент может дампить старый сервер, не наоборот).
- Роль с правом `pg_read_all_data` (введена в PG 14) или владелец схем.
- `pg_dump` выгружает **одну** базу; для ролей и табличных пространств нужен `pg_dumpall`.

#### Ключевые флаги
* `-F p|c|d|t`: формат вывода.
* `-j N`: параллелизм (только `-F d`).
* `--no-owner` / `--no-privileges`: не сохранять владельцев / права (полезно при миграции на другой инстанс).
* `--blobs`: включить Large Objects при выборке `-t` (иначе LO теряются).
* `--no-unlogged-table-data`: не выгружать данные UNLOGGED-таблиц (их данные всё равно не replay'ятся из WAL; при дампе со standby они исключаются всегда).

#### pg_dumpall — весь кластер
Резервное копирование **всего кластера**, включая роли и табличные пространства (глобальные объекты `pg_dump` не сохраняет). Требует суперпривилегий для полного дампа:
```bash
pg_dumpall -U postgres > /backups/cluster_full.sql   # все БД + глобальные объекты
pg_dumpall -U postgres -g > /backups/globals.sql     # только роли + tablespaces
pg_dumpall -U postgres -r > /backups/roles.sql       # только роли
# → SQL-скрипт; восстановление: psql -U postgres -f globals.sql
```

### 2. Физическое резервное копирование (`pg_basebackup`)

Бинарная копия инстанса, необходимая для репликации и PITR.

#### Предпосылки
- `wal_level` установлен в `replica` или выше.
- Роль с правом `REPLICATION` или `SUPERUSER`.
- Доступ в `pg_hba.conf` для типа подключения `replication` (иначе — `FATAL: no pg_hba.conf entry for replication connection`).
- `max_wal_senders` оставляет хотя бы одно слот свободным для бэкапа.

#### Базовое использование
```bash
pg_basebackup -h 10.0.0.1 -U replicator -D /backups/full -P -X stream -c fast -l nightly-full
# → прогресс-бар (благодаря -P); каталог /backups/full с полной копией кластера
#   и backup_manifest (создаётся по умолчанию, с PG 13)
```
* **`--checkpoint=fast`** (`-c fast`): форсирует немедленный чекпоинт для быстрого начала бэкапа (всплеск I/O; `spread` — по умолчанию, плавный).
* **`-X stream`**: WAL-сегменты передаются параллельно через отдельное соединение (бэкап самодостаточен).
* **`-R`**: автоматически создаёт `standby.signal` и `postgresql.auto.conf` для настройки реплики.
* **`-S name` / `-C`**: использовать / создать слот репликации (защищает WAL от удаления во время долгого бэкапа).
* **`-r 100M`** (`--max-rate`): лимит скорости передачи (32 kB/s – 1024 MB/s), снижает влияние на прод.
* **`-T olddir=newdir`**: перенаправить tablespace в другое место при восстановлении.
* **`-F t`**: tar-формат (тогда `pg_verifybackup` не сможет проверить WAL без `-n`).

### 3. Инкрементальная цепочка (PostgreSQL 17+)

```bash
# 0. Разово на кластере: summarize_wal = on в postgresql.conf (default off) + релоад
# 1. Полный бэкап (манифест создаётся автоматически)
pg_basebackup -h 10.0.0.1 -U replicator -D /backups/full
# 2. Инкрементальный бэкап на основе манифеста полного
pg_basebackup -h 10.0.0.1 -U replicator -D /backups/inc1 \
  --incremental=/backups/full/backup_manifest
# 3. Сборка синтетического полного бэкапа (oldest → newest)
pg_combinebackup /backups/full /backups/inc1 -o /backups/combined
# → каталог /backups/combined — обычный полный бэкап, пригодный для restore
```
`pg_combinebackup` проверяет, что бэкапы образуют корректную цепочку, но **не** целостность каждого файла — для этого прогоняйте `pg_verifybackup` по каждому элементу цепочки. Синтетический полный бэкап сам может служить базой для следующих инкрементов.

### 4. Восстановление на точку времени (PITR)

Алгоритм действий при критическом сбое (например, `DROP TABLE` в 14:05:00):

#### Иллюстрация RPO

Сценарий: полный физический бэкап снимается раз в сутки (последний — в 01:00), WAL архивируется непрерывно. В 10:45 инсайдер с доступом на прод уничтожил таблицу. Восстановление выполняется на `recovery_target_time = '10:44'`: накатывается суточный бэкап и WAL-сегменты до нужной секунды. Потеря данных — около минуты транзакций (10:44–10:45), тогда как при стратегии «дамп раз в сутки» пришлось бы откатиться на ночной дамп и потерять ~10 часов. Даунтайм на восстановление при этом не зависит от частоты дампов и определяется скоростью развертывания файлов и наката WAL.

#### Подготовка (на стороне живого сервера)
Рекомендуется создавать «точки отката» перед опасными операциями:
```sql
SELECT pg_create_restore_point('before_migration');
-- → имя точки доступно как recovery_target_name при восстановлении
```

#### Процедура восстановления
1. **Остановка сервиса:** `sudo systemctl stop postgresql`
2. **Очистка данных:** `rm -rf /var/lib/postgresql/data/*` (предварительно сохраните логи и конфиги; убедитесь, что бэкап скопирован в безопасное место).
3. **Развертывание бэкапа:** скопируйте файлы из последней физической копии; при наличии — проверьте её сначала: `pg_verifybackup /backups/full`.
4. **Файл сигнала:** создайте пустой файл `recovery.signal` в корне `PGDATA`.
5. **Настройка цели (`postgresql.auto.conf` или `postgresql.conf`):**
    ```ini
    restore_command = 'cp /mnt/wal_archive/%f %p'
    recovery_target_time = '2026-08-17 14:04:00 MSK'
    recovery_target_inclusive = off   # остановиться ДО транзакций ровно в 14:04:00
    recovery_target_action = 'promote' # Открыть базу после достижения цели
    # Альтернативные цели: recovery_target_name = 'before_migration'
    # (или recovery_target_lsn / recovery_target_xid — по LSN или ID транзакции)
    ```
    `recovery_target_action`: `promote` (завершить и открыть), `pause` (default — пауза для проверки точки, продолжение через `pg_wal_replay_resume()`), `shutdown` (остановить сервер на точке; `recovery.signal` при этом остаётся и следующий старт снова завершится shutdown).
6. **Запуск:** `sudo systemctl start postgresql`. В логе при успехе: `LOG: database system is ready to accept connections`; перед этим — записи о проигрывании WAL. После завершения восстановления сервер **автоматически удаляет `recovery.signal`** и переключается на новый таймлайн.

#### Детальный сценарий PITR: откат после `DROP TABLE`

**Ситуация:** в 14:05:00 было выполнено `DROP TABLE payments;`. Бэкапы: полный физический бэкап в 01:00, WAL-архив непрерывный.

**Шаг 1. Определение целевого времени**
```bash
# Время удаления — в серверном логе (нужен log_statement = 'ddl' или аудит, см. pgaudit)
grep -n "DROP TABLE" /var/log/postgresql/postgresql-16-main.log
# → 2026-08-17 14:05:02 MSK [1234] LOG:  statement: DROP TABLE payments;
```

**Шаг 2. Остановка и очистка**
```bash
sudo systemctl stop postgresql
sudo su - postgres
rm -rf /var/lib/postgresql/data/*
```

**Шаг 3. Развертывание базового бэкапа**
```bash
# Если бэкап в tar-архиве
tar -xzf /backups/full_base_backup.tar.gz -C /var/lib/postgresql/data

# Или из pgBackRest
pgbackrest restore --stanza=main --delta
```

**Шаг 4. Настройка восстановления**
```ini
# postgresql.auto.conf
restore_command = 'cp /mnt/wal_archive/%f %p'
recovery_target_time = '2026-08-17 14:04:59'
recovery_target_action = 'promote'
```

**Шаг 5. Запуск и валидация**
```bash
sudo systemctl start postgresql
# Проверить лог: tail -f /var/log/postgresql/postgresql-16-main.log
# Должно быть: "database system is ready to accept connections"

# Проверить таблицу
psql -c "SELECT count(*) FROM payments;"
```

**Шаг 6. Экспорт и повторный запуск**
```bash
# Сделать снимок восстановленной базы для аудита
pg_dump -Fc mydb > /backups/mydb_before_incident.dump

# Переключиться на новую базу
sudo systemctl stop postgresql
rm -rf /var/lib/postgresql/data/*
# Развернуть заново уже без recovery_target_time
```

#### Восстановление отдельной таблицы из PITR

PostgreSQL не поддерживает восстановление отдельной таблицы из PITR напрямую. Алгоритм:
1. Восстановить базовый бэкап в отдельную директорию (`/var/lib/postgresql/data_pitr`).
2. Настроить `postgresql.conf` с другим `port = 5433` и `data_directory = '/var/lib/postgresql/data_pitr'`.
3. Запустить временный инстанс на порту 5433 (расширения, нужные для дампа таблицы, должны быть установлены).
4. Выполнить `pg_dump -t payments payments_db > payments.sql`.
5. Остановить временный инстанс, применить дамп в основной базе.

```bash
# Временный инстанс
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /var/lib/postgresql/data_pitr -o "-p 5433" start
pg_dump -h localhost -p 5433 -U postgres -t payments mydb > /tmp/payments.sql
sudo -u postgres /usr/lib/postgresql/16/bin/pg_ctl -D /var/lib/postgresql/data_pitr stop
psql -h localhost -U postgres mydb -f /tmp/payments.sql
```

### 5. Отложенная реплика как страховка от логических ошибок

`recovery_min_apply_delay` задерживает применение **коммит-записей** на standby на фиксированный интервал — окно для отката после `DROP TABLE`/`DELETE` без обращения к архиву:
```ini
# postgresql.auto.conf на реплике
recovery_min_apply_delay = '5min'
```
Нюансы: задержка применяется только к записям коммитов (остальной WAL replay'ится сразу); работает при `hot_standby = on`; promote немедленно применяет весь отложенный WAL; при совместном использовании `hot_standby_feedback` задерживается тоже — риск bloat на первичном; требуется синхронизация часов (задержка считается между временем коммита на первичном и текущим временем на standby).

## Диагностика и устранение неисправностей

| Ошибка | Возможная причина | Решение |
| :--- | :--- | :--- |
| `permission denied for relation ...` | У бэкап-пользователя нет прав SELECT. | Выдайте `pg_read_all_data` или проверьте права на схему. |
| `FATAL: no pg_hba.conf entry for replication connection` | Нет строки `host replication ...` в `pg_hba.conf` или у роли нет атрибута `REPLICATION`. | Добавьте запись и перечитайте конфиг (`pg_reload_conf()`). |
| `WAL segment ... has already been removed` | Слишком медленный бэкап или малый `max_wal_size`. | Используйте слоты репликации (`--create-slot`) при `pg_basebackup`; увеличьте `wal_keep_size` / `max_slot_wal_keep_size`. |
| `archive_command failed with exit code 1` | Проблема с доступом к хранилищу (NFS/локальный диск), права, нехватка места. | Проверьте монтирование, права записи для пользователя `postgres`, место; посмотрите `pg_stat_archiver.failed_count` и `last_failed_wal`. |
| `recovery target ... not reached` (fatal) | Нужный WAL отсутствует в архиве — архивация прерывалась. | Проверьте `archive_command`, наличие всех файлов в `wal_archive`, `pg_stat_archiver`. |
| `checksum verification failed` (`pg_verifybackup`) | Повреждение файлов бэкапа или диска. | См. руководство по **[Corruption Recovery](./corruption_recovery.md)**; помните, что page-level чексуммы требуют `data_checksums` (с PG 18 включены по умолчанию при `initdb`). |
| `pg_dump: error: directory "..." exists but is not empty` | Формат `-F d` требует несуществующий или пустой каталог. | Укажите новый путь или очистите каталог. |
| Инкрементальный бэкап завершается ошибкой | Сводки удалены (`wal_summary_keep_time`), summarizer не успел, есть доп. tablespace или используется `-X stream`. | Увеличьте `wal_summary_keep_time`, проверьте `summarize_wal = on`, уберите tablespace/`-X stream`. |
| `pg_combinebackup` не собирает цепочку | Указаны не все промежуточные бэкапы (порядок oldest → newest) или удалён базовый. | Передайте полную цепочку; не удаляйте базовые копии инкрементов. |
| Восстановление дампа занимает часы | Нет параллелизма при `pg_restore` или `maintenance_work_mem` слишком мал. | Используйте `-j 8`, увеличьте `maintenance_work_mem` до 2–4 ГБ. |
| Bloat после долгого `pg_dump` | Дамп удерживает снапшот транзакции, `VACUUM` не чистит строки. | Запускайте в часы минимума нагрузки. (`--no-synchronized-snapshots` — **не** лечение: это обход для серверов < 9.2, требующий отсутствия concurrent-записей.) |
| Large Objects потеряны | Использован флаг `-t` без `--blobs`. | Всегда добавляйте `--blobs` при выборочном бэкапе. |
| PITR не стартует повторно | `recovery_target_action = shutdown` оставляет `recovery.signal`; при успешном `promote` файл удаляется автоматически. | Для `shutdown`-режима настройте новый target перед следующим стартом; `recovery.signal` руками не удаляйте. |
| `WARNING: WAL archiving is not enabled` от `pg_backup_stop()` | Бэкап сделан без `archive_mode = on` — он не самодостаточен для PITR. | Скопируйте все WAL-сегменты вручную или включите архивацию. |

## Лучшие практики

### Проверка целостности и валидация бэкапов

Бэкап, который не проверен, — это не бэкап, а ложное чувство безопасности.

1. **pg_verifybackup (физические бэкапы)** — проверяет список файлов, размеры и контрольные суммы из манифеста, а также наличие и читаемость нужного для восстановления WAL:
    ```bash
    pg_verifybackup /backups/full
    # → код возврата 0 при успехе; детали проблем — в stderr
    pg_verifybackup -s /backups/full      # только файлы и размеры, без чтения данных (быстро)
    pg_verifybackup -n /backups/full_tar  # tar-формат: WAL не парсится (поддерживается только plain)
    # Опции: -m/--manifest-path, -P/--progress, -q/--quiet, -e/--exit-on-error, -i/--ignore
    ```
2. **Тестовое восстановление (Smoke Test)** — единственная 100% гарантия. Восстанавливайте бэкап в изолированном окружении раз в месяц:
    - для логических бэкапов: `pg_restore -l dump.dump | head` (содержимое TOC), `--schema-only`/`--data-only` в тестовую базу;
    - для физических: проверьте, что кластер стартует и `SELECT 1` работает;
    - для PITR: восстановите базовый бэкап в отдельный каталог, настройте `restore_command` на WAL-архив и проверьте достижение `recovery_target_time` (алгоритм — в **[Проверка целостности бэкапов](../../Concepts/backup_validation.md)**).
3. **Анонимизация данных:** при восстановлении бэкапов в среды разработки (Staging/Dev) необходимо удалять или маскировать персональные данные (PII). Подробное руководство: **[Анонимизация и маскирование в PostgreSQL](../Operations/anonymization.md)**.
4. **Аудит размеров:**
    ```bash
    ls -lah /backups/*.dump
    # → если вчера было 50GB, а сегодня 5GB — Alarm: возможна потеря данных
    ```
5. **Проверка WAL-архива:**
    ```bash
    ls /mnt/wal_archive/ | wc -l   # количество файлов в архиве
    pg_controldata /var/lib/postgresql/data | grep -E "Latest checkpoint|TimeLineID"
    # → актуальный LSN последнего чекпоинта и идентификатор таймлайна кластера
    ```
6. **Автоматизация проверок:**
    ```bash
    #!/bin/bash
    # /usr/local/bin/verify_backup.sh
    set -e
    BACKUP_DIR="/backups/full"
    pg_verifybackup "$BACKUP_DIR"   # → код 0 при успехе
    echo "OK: backup verified"
    # при ошибке — алерт в мониторинг (mail / Dead Man's Snitch)
    ```

### Мониторинг архивации WAL

```sql
SELECT archived_count, failed_count,
       last_archived_wal, last_archived_time,
       last_failed_wal, last_failed_time
FROM pg_stat_archiver;
-- → archived_count | 1204
--   failed_count   | 0
--   last_archived_wal | 00000001000000000000002A
--   ...
SELECT pg_stat_reset_shared('archiver');  -- сброс счётчиков (суперпользователь)
```
Алерт: `failed_count > 0` или `last_archived_time` застыл. Подробности — в **[Наблюдаемость PostgreSQL](../Operations/observability.md)**.

### Пользователь бэкапа и права
```sql
-- Для логических бэкапов (PG 14+)
CREATE ROLE backup_user LOGIN PASSWORD 'password';
GRANT pg_read_all_data TO backup_user;

-- Для физических бэкапов
CREATE ROLE replicator LOGIN REPLICATION PASSWORD 'password';
-- pg_hba.conf: host replication replicator 10.0.0.0/24 scram-sha-256
```
`pg_backup_start()`/`pg_backup_stop()` и `pg_create_restore_point()` доступны суперпривилегии по умолчанию; `EXECUTE` можно выдать отдельной роли.

### Политики удержания (Retention)
- **Стратегия 3-2-1**: 3 копии, на 2 разных носителях, 1 копия — вне площадки (off-site).
- **Жизненный цикл**:
    - Полные бэкапы: хранить 30 дней.
    - WAL-архивы: должны покрывать период самого старого полного бэкапа, необходимого для PITR.
    - Инкрементальные цепочки: хранить все базовые копии, от которых зависят инкременты (PostgreSQL не отслеживает зависимости).

### Рекомендации по производительности

- **Сжатие:** используйте `--compress=zstd:3` (баланс скорости/размера). Для сети: сжимайте на лету (`pg_dump | gzip > file`).
- **Параллелизм:** `-j 4` для дампов > 50 ГБ. Не ставьте больше ядер CPU, иначе дамп начнёт thrashing.
- **Сеть:** для удаленного бэкапа используйте pipe + ssh:
  ```bash
  pg_dump -h localhost -U backup_user mydb | gzip | ssh backup@storage "cat > /backups/mydb.sql.gz"
  ```
- **IO:** запускайте бэкапы на реплике, а не на мастере (нужны `hot_standby = on` и защита WAL — слот или `wal_keep_size`). Ограничивайте скорость `pg_basebackup -r 100M`; запускайте один `pg_basebackup` за раз — параллельные копии конфликтуют за ресурсы.

### Ограничения и пограничные случаи

- **Повреждение данных (Corruption):** при фатальных ошибках контрольных сумм или невозможности старта из-за битых WAL требуются низкоуровневые инструменты `pageinspect` и `pg_resetwal`. См. **[Восстановление при повреждении данных](./corruption_recovery.md)**.
- **Bloat (раздувание):** долгие `pg_dump` удерживают транзакцию, что мешает `VACUUM` очищать старые версии строк.
- **Расширения (Extensions):** при логическом восстановлении убедитесь, что бинарные файлы расширений (например, PostGIS) установлены на целевом сервере.
- **Large Objects (LO):** помните об «orphan» объектах, которые увеличивают размер бэкапа. Детальное руководство: **[Large Objects (LO): Администрирование и очистка](./large_objects.md)**.
- **UNLOGGED-таблицы:** данные никогда не replay'ятся из WAL — после любого crash они пусты; не рассчитывайте на них в плане восстановления.

## Инструментарий

* **pgBackRest**: «золотой стандарт» для крупных инсталляций. Инкрементальные/дифференциальные бэкапы, многопоточность, дельта-восстановление, ретеншен, сжатие и шифрование.
* **WAL-G**: высокопроизводительный инструмент на Go (преемник WAL-E), быстрая архивация и восстановление, page-level инкрементальность.
* **Barman (Backup and Recovery Manager)**: решение от 2ndQuadrant (EDB) — централизованный интерфейс для управления бэкапами множества серверов.
* **pg_receivewal**: встроенная утилита для стриминга WAL в реальном времени (альтернатива `archive_command`).

*Подробные примеры настройки, скрипты, cron и ротация см. в разделе **[Автоматизация бэкапов](../Operations/backup_automation.md)**.*

## Вопросы на собеседованиях

1. **В чем разница между логическим и физическим бэкапом PostgreSQL?**
    - Логический (`pg_dump`): SQL-дамп, медленное восстановление, переносимость между версиями, нет PITR, не блокирует пользователей.
    - Физический (`pg_basebackup`): побайтовая копия, быстрое восстановление, только та же мажорная версия и ОС, основа для PITR.

2. **Что такое PITR и как он работает?**
    - Восстановление на произвольный момент времени через комбинацию полного бэкапа + WAL-архив. WAL содержит все изменения, поэтому можно «проиграть» журнал до нужной секунды (`restore_command` + `recovery_target_*` + `recovery.signal`).

3. **Почему `pg_dump` не подходит для PITR?**
    - `pg_dump` создаёт снапшот на момент начала. Он не содержит журнала изменений. PITR требует непрерывного потока WAL-сегментов. Официальная документация прямо не рекомендует `pg_dump` для регулярных production-бэкапов.

4. **Что такое Timeline ID и зачем он нужен?**
    - Идентификатор ветки восстановления. При каждом PITR создаётся новый таймлайн, чтобы избежать конфликтов WAL-файлов и позволить откат к предыдущей точке восстановления.

5. **Как настроить WAL-архивацию?**
    - `archive_mode = on`, `wal_level = replica`, `archive_command = 'test ! -f /archive/%f && cp %p /archive/%f'`, опционально `archive_timeout` порядка минуты (короткие значения раздувают архив: досрочно закрытые сегменты всё равно занимают 16 МБ).

6. **В чем разница между `pg_dump` и `pg_basebackup`?**
    - `pg_dump`: логический, одна база, поддерживает `-F c/d/t/p`, нет PITR, переносимость версий.
    - `pg_basebackup`: физический, весь кластер, бинарные файлы, основа для репликации и PITR.

7. **Что такое incremental backup в PostgreSQL 17+?**
    - Нативная поддержка через WAL summarization: `summarize_wal = on` (default off), сводки в `pg_wal/summaries`, `pg_basebackup --incremental=<manifest>` создаёт дельта-бэкап, собирается через `pg_combinebackup`. Невозможен с доп. tablespace и `-X stream`.

8. **Как восстановить отдельную таблицу после PITR?**
    - Восстановить кластер в отдельную директорию, запустить на другом порту, сделать `pg_dump -t table`, импортировать в основной кластер.

9. **Что проверять при failing WAL archiving?**
    - `pg_stat_archiver` (`failed_count`, `last_failed_wal`), `archive_command` в логах, права на директорию, место на диске, сетевая доступность до хранилища.

10. **Какой формат `pg_dump` выбрать для production?**
    - `-F c` (custom) — универсальный, сжатый по умолчанию, поддерживает частичный restore и параллельный импорт.
    - `-F d` (directory) — для очень больших БД и максимального параллелизма экспорта/импорта.
    - `-F p` (plain) — только для миграций и audit. Tar (`-F t`) не сжимается вообще.

11. **Как проверить, что бэкап пригоден к восстановлению?**
    - `pg_verifybackup <backupdir>` для физических (чексуммы манифеста + наличие нужного WAL), `pg_restore -l` для логических, и регулярное тестовое восстановление в изолированном окружении — единственная 100% гарантия.

12. **Как защититься от логических ошибок (DROP TABLE) помимо PITR?**
    - Отложенная реплика (`recovery_min_apply_delay`), именованные restore points перед опасными операциями, короткий RPO через частую архивацию WAL, аудит DDL (`log_statement = 'ddl'` или pgaudit).
