# Типы репликации в PostgreSQL

## 1. Определения

*   **Физическая репликация (Physical Replication):** Метод, при котором изменения передаются с мастера на реплику на уровне файлов данных (побайтово). Реплика является точной копией мастера. В PostgreSQL этот механизм называется **Streaming Replication**.
*   **Логическая репликация (Logical Replication):** Метод, при котором реплицируются изменения на уровне объектов базы данных (строки, таблицы). Работает по принципу "поставщик-подписчик" (Publisher-Subscriber).

## 2. Основные концепции

Репликация в PostgreSQL решает стандартный набор задач: **высокая доступность**, **отказоустойчивость**, **балансировка нагрузки на чтение** и другие. Подробно общие цели, типы (синхронная/асинхронная) и топологии репликации описаны в [основной заметке о концепциях репликации](../../../Databases/Concepts/replication.md).

Ключевое различие подходов в PostgreSQL:
*   **Физическая репликация** реплицирует *весь кластер* целиком, привязана к мажорной версии и архитектуре, но очень быстра и проста в настройке.
*   **Логическая репликация** позволяет *выборочно* реплицировать таблицы или базы данных, даже между разными мажорными версиями PostgreSQL, но требует более тщательной настройки.

## 3. Практические сценарии: Виды репликации в PostgreSQL

### 3.1. Физическая репликация (Streaming Replication)

Это наиболее распространенный вид репликации, при котором WAL-записи передаются с ведущего сервера (master) на ведомый (replica/standby) в реальном времени. Реплика "догоняет" мастер, применяя эти WAL-записи.

При физической репликации записи [журнала предзаписи (WAL)](../../../Concepts/write_ahead_log.md) передаются с основного сервера (мастера) на реплики и применяются к ним.

*   **Особенности:**
    *   Реплицируется весь кластер целиком, выборочная репликация невозможна.
    *   Мастер и реплика должны иметь одну и ту же основную версию PostgreSQL и совместимые архитектуры.
    *   Реплика по умолчанию доступна только для чтения (`Hot Standby`).
*   **Использование:**
    *   Горячий резерв (Hot Standby) для высокой доступности.
    *   Балансировка нагрузки на чтение.
    *   Создание [бэкапов с реплик](./backup_and_recovery.md), чтобы не нагружать мастер.
    *   Каскадная и отложенная репликация.
*   **Процессы-участники:**
    *   `wal_sender` (на мастере): Отправляет WAL-сегменты на реплики.
    *   `wal_receiver` (на реплике): Принимает WAL-сегменты от мастера.
    *   `startup` (на реплике): Применяет полученные WAL-сегменты.

### 3.2. Логическая репликация (Publisher-Subscriber)

Логическая репликация передает изменения отдельных таблиц, а не целые WAL-сегменты.

*   **Особенности:**
    *   Выборочная репликация таблиц или баз данных.
    *   Возможна репликация между разными основными версиями PostgreSQL.
    *   Требуется `wal_level = logical` на публикующем сервере.
*   **Компоненты:**
    1.  **Публикующий сервер (Publisher):** Создает `PUBLICATION` для таблиц, изменения в которых нужно отправить.
    2.  **Подписчик (Subscriber):** Создает `SUBSCRIPTION` для получения и применения изменений.
*   **Создание (упрощенно):**
    1.  На мастере: `CREATE PUBLICATION my_publication FOR TABLE users, products;`
    2.  На подписчике: `CREATE SUBSCRIPTION my_subscription CONNECTION '...' PUBLICATION my_publication;`
*   **Использование:**
    *   Консолидация данных из нескольких источников.
    *   Обновление основной версии сервера с минимальным простоем.
    *   Выборочная репликация данных между разными окружениями.

## 4. Продвинутые детали

### Промоутинг реплики до мастера (`PROMOTE`)

При необходимости (например, при сбое мастера) физическую реплику можно вручную повысить до состояния мастера командой `pg_ctl promote`.
*   **Плановое переключение (Switchover):** Управляемая процедура для проведения технических работ.
*   **Аварийное переключение (Failover):** Экстренная мера при внезапном отказе основного сервера. Может сопровождаться потерей данных, которые не успели реплицироваться.

### Слот репликации (Replication Slot)
Механизм, гарантирующий, что ведущий сервер не удалит WAL-записи, пока реплика не подтвердит их получение. Это критически важно для предотвращения отставания реплики и потери данных, если реплика временно отключается.

### Проблема "Split-Brain"

Если после аварийного переключения старый мастер снова станет доступным и будет работать независимо, возникнет ситуация, когда оба сервера считают себя мастерами. Это приводит к рассинхронизации данных. Для предотвращения этого используются автоматизированные системы управления кластером.

### Автоматический failover
Важно отметить, что PostgreSQL не имеет встроенного автоматического failover для потоковой репликации. Для этого используются внешние инструменты, такие как Patroni, которые управляют кластером и процессами повышения статуса реплики до мастера.

> Подробнее о решениях, таких как Patroni, см. в заметке [Концепции высокой доступности](./high_availability.md).
