# Типы репликации PostgreSQL

Репликация в PostgreSQL — это процесс синхронизации данных между несколькими экземплярами базы данных. Она решает задачи высокой доступности (High Availability), отказоустойчивости (Failover) и масштабирования нагрузки (Scale-out).

## Для чего нужна репликация?

1.  **Высокая доступность и отказоустойчивость:** В отличие от бэкапа, который требует времени на развертывание, реплика позволяет быстро восстановить работоспособность системы при сбое основного сервера.
2.  **Балансировка нагрузки на чтение (Read Scaling):** Можно распределить запросы на чтение между основным сервером (мастером) и репликами, снижая нагрузку на мастер.
3.  **Создание отчетов:** Выполнение ресурсоемких отчетов на репликах позволяет не нагружать основной производственный сервер.
4.  **Горизонтальное масштабирование:** Позволяет распределять данные и нагрузку на несколько серверов, что особенно актуально при исчерпании физических ресурсов одного сервера.

## Виды репликации

1.  **Физическая репликация:** Описание изменений на уровне файлов. Это побайтовая копия данных.
2.  **Логическая репликация:** Описание изменений данных в терминах строк и таблиц. Работает на более высоком уровне, чем файлы.

## Физическая репликация (Streaming Replication)

При физической репликации записи журнала предзаписи (WAL - Write-Ahead Log) передаются с основного сервера (мастера) на реплики и применяются к ним. Это однонаправленный поток данных: от мастера к реплике.

### Особенности:
*   **Реплицируется весь кластер целиком:** Реплика является точной побайтовой копией мастера. Выборочная репликация отдельных баз данных или таблиц невозможна.
*   **Требования к совместимости:** Мастер и реплика должны иметь одну и ту же основную версию PostgreSQL и полностью совместимые архитектуры/платформы.
*   **Реплика доступна только для чтения (Read-Only):** По умолчанию, на реплику можно отправлять только запросы на чтение (`SELECT`).

### Использование физической репликации:
*   **Горячий резерв (Hot Standby):** Реплика готова принять нагрузку в случае сбоя мастера.
*   **Балансировка нагрузки на чтение:** Передача части запросов на чтение на реплики.
*   **Создание бэкапов с реплик:** Чтобы не нагружать мастер, [стратегии резервного копирования](./backup_and_recovery.md) (особенно физического, например `pg_basebackup`) рекомендуется применять именно к репликам.
*   **Каскадная репликация:** Реплика может быть мастером для других реплик.
*   **Отложенная репликация (Delayed Replication):** Репликация с задержкой, полезная для восстановления после случайного удаления/изменения данных на мастере.

### Процессы, участвующие в физической репликации:
*   **`wal_sender` (на мастере):** Процесс, который отправляет WAL-сегменты на реплики.
*   **`wal_receiver` (на реплике):** Процесс, который принимает WAL-сегменты от мастера.
*   **`startup` (на реплике):** Процесс, который применяет полученные WAL-сегменты к файлам данных реплики, непрерывно восстанавливая её.

### Ограничения на реплике (по умолчанию):
*   **Запрещены операции изменения данных:** `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`.
*   **Запрещены операции DDL:** `CREATE`, `ALTER`, `DROP` любых объектов базы данных.
*   **Запрещены команды сопровождения:** `VACUUM`, `ANALYZE`, `REINDEX`.
*   **Не срабатывают триггеры и пользовательские блокировки.**

### Промоутинг реплики до мастера (`PROMOTE`)
При необходимости (например, при сбое мастера) реплику можно вручную повысить до состояния мастера.

```bash
pg_ctl -D /path/to/replica/data promote
```
*   **Причины промоутинга:** Процесс повышения реплики до мастера может быть инициирован по двум основным причинам:
    *   **Плановое переключение (Switchover):** Это штатная, управляемая процедура, которая выполняется для проведения технических работ на мастере (например, обновление ОС или оборудования). Процесс включает в себя последовательную остановку трафика, обеспечение полной синхронизации реплики, её "продвижение" до мастера и перенаправление трафика на новый мастер.
    *   **Аварийное переключение (Failover):** Это экстренная мера, которая принимается при внезапном отказе основного сервера. Цель — как можно быстрее восстановить работоспособность сервиса. В отличие от Switchover, Failover может сопровождаться потерей данных, которые были зафиксированы на старом мастере, но не успели реплицироваться.
*   **Проблема "Split-Brain":** Если после промоутинга старый мастер снова станет доступным и будет работать независимо, возникнет ситуация, когда оба сервера считают себя мастерами. Это приводит к рассинхронизации данных. Для предотвращения этого используются автоматизированные системы управления кластером, такие как Patroni. Подробнее об этом — в заметке [Концепции высокой доступности](./high_availability.md).

## Логическая репликация (Logical Replication)

Логическая репликация передает изменения строк отдельных таблиц, а не целые WAL-сегменты. Она работает по принципу "поставщик-подписчик" (Publisher-Subscriber).

### Особенности:
*   **Выборочная репликация:** Можно реплицировать отдельные таблицы, схемы или базы данных.
*   **Двунаправленная репликация:** Позволяет организовать поток данных в обе стороны, что делает возможным реализацию Master-Master конфигураций (хотя это требует внимательной работы с конфликтами).
*   **Совместимость:** Не требует бинарной совместимости. Возможна репликация между разными основными версиями PostgreSQL.
*   **Требуется `wal_level = logical`:** Параметр `wal_level` на публикующем сервере должен быть установлен в `logical`.

### Компоненты:
1.  **Публикующий сервер (Publisher):**
    *   Создает *публикацию* (`PUBLICATION`), которая определяет, какие таблицы будут реплицироваться.
    *   Выдает изменения данных в порядке их фиксации (только `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` с версии PG 11+).
    *   Начальная синхронизация данных возможна.
    *   Применение изменений происходит без разбора и планирования SQL-запросов, что снижает нагрузку.
2.  **Подписчик (Subscriber):**
    *   Создает *подписку* (`SUBSCRIPTION`) на публикацию с публикующего сервера.
    *   Получает и применяет изменения.
    *   Таблицы-приемники на стороне подписчика должны быть созданы вручную и иметь совместимую схему.
    *   Возможны конфликты с локальными данными подписчика.

### Создание логической репликации:

1.  **На публикующем сервере (Master):**
    *   Установить `wal_level = logical` и перезапустить сервер.
    *   Создать публикацию:
        ```sql
        CREATE PUBLICATION my_publication FOR TABLE users, products;
        -- или для всех таблиц
        -- CREATE PUBLICATION my_publication FOR ALL TABLES;
        ```
    *   Создать пользователя для репликации (с правами `REPLICATION`).

2.  **На подписчике (Replica):**
    *   Создать таблицы с соответствующими схемами.
    *   Создать подписку:
        ```sql
        CREATE SUBSCRIPTION my_subscription CONNECTION 'host=master_ip port=5432 user=replication_user password=your_password dbname=your_db' PUBLICATION my_publication WITH (copy_data = true);
        ```
        -   `copy_data = true`: Выполняет начальную синхронизацию данных.

### Для чего нужна логическая репликация:
*   **Консолидация данных:** Объединение данных из нескольких источников в одну центральную базу.
*   **Общие справочники:** Поддержание актуальности справочной информации на разных серверах.
*   **Обновление основной версии сервера:** Позволяет мигрировать данные между версиями PostgreSQL с минимальным простоем.
*   **Выборочная репликация:** Репликация только необходимых данных, а не всего кластера.

### Конфликты:
*   При логической репликации могут возникать конфликты, если одни и те же строки изменяются как на публикующем сервере, так и на подписчике.
*   PostgreSQL автоматически обнаруживает конфликты (например, по уникальным индексам). Информацию о конфликтах можно найти в логах подписчика.
