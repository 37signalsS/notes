# Репликация в PostgreSQL

## Определения

- **Физическая репликация (Physical Replication)**: Побайтовая передача данных с основного сервера на подчиненный. В PostgreSQL реализуется через механизм **Streaming Replication**. Реплика является точной бинарной копией основного сервера.
- **Логическая репликация (Logical Replication)**: Передача изменений на уровне отдельных строк или таблиц по принципу «поставщик — подписчик» (Publisher-Subscriber).
- **Слот репликации (Replication Slot)**: Механизм на основном сервере, гарантирующий, что записи WAL не будут удалены до тех пор, пока они не будут успешно переданы на реплику. Предотвращает поломку репликации при длительных сбоях связи.

## Базовые концепции

### Потоковая репликация (Streaming Replication)

Основной тип физической репликации в PostgreSQL. Записи **[журнала предзаписи (WAL)](../../Concepts/write_ahead_log.md)** передаются с основного сервера (Master) на ведомый (Standby) в реальном времени.

#### Режимы работы Standby-сервера

1. **Warm Standby**: Сервер находится в режиме восстановления, принимает WAL, но **не разрешает подключения** пользователей. Используется как «холодный» резерв.
2. **Hot Standby**: Сервер применяет изменения и **разрешает подключения на чтение** (ReadOnly). Активируется параметром `hot_standby = on`.

- **Особенности**:
  - Реплицируется весь кластер целиком (все базы данных).
  - Версии PostgreSQL и архитектура ОС на серверах должны быть идентичны (мажорная версия).
- **Процессы**:
  - `wal_sender` (на мастере): Читает WAL и отправляет их по сети.
  - `wal_receiver` (на реплике): Принимает данные и записывает их.
  - `startup` (на реплике): Процесс восстановления, применяющий записи WAL к файлам данных.

### Логическая репликация (Publisher-Subscriber)

Позволяет передавать изменения выборочно (только определенные таблицы). Требует установки `wal_level = logical`.

- **Плюсы**:
  - Возможность репликации между разными мажорными версиями PostgreSQL.
  - Возможность объединять данные из нескольких источников в одну БД (Multi-source).
- **Ограничения**:
  - Изменения схемы (DDL) не реплицируются автоматически.
  - Не реплицируются состояния последовательностей (`sequences`).
  - Требуется наличие первичного ключа (`PRIMARY KEY`) или `REPLICA IDENTITY` для идентификации изменяемых строк.

### Уровни синхронизации (Synchronous Commit)

Параметр `synchronous_commit` определяет, насколько надежно подтверждается транзакция при использовании синхронных реплик.

| Значение | Описание | Уровень надежности |
| :--- | :--- | :--- |
| `remote_apply` | Мастер ждет, пока транзакция будет **применена** на реплике | Максимальный (данные видны в SELECT на реплике) |
| `on` (default) | Мастер ждет записи транзакции в WAL на **диск** реплики | Высокий (защита от сбоя питания мастера) |
| `remote_write` | Мастер ждет получения WAL в **кэш ОС** реплики | Средний (защита от падения процесса БД) |
| `local` | Мастер подтверждает запись только в свой локальный WAL | Низкий (репликация фактически асинхронная) |
| `off` | Полностью асинхронная фиксация | Минимальный (риск потери данных при сбое мастера) |

## Практические сценарии

### Настройка потоковой репликации (Physical)

**Шаг 1: Настройка основного сервера (Master)**

1. Создать пользователя с правами репликации:

   ```sql
   CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'password';
   ```

2. Разрешить подключение в `pg_hba.conf`:

   ```conf
   host replication replicator <ip_реплики>/32 md5
   ```

3. Установить в `postgresql.conf`: `wal_level = replica`.

**Шаг 2: Настройка реплики (Standby)**

1. Снять базовую копию данных (Base Backup):

   ```bash
   pg_basebackup -h <ip_мастера> -U replicator -D /var/lib/postgresql/data -Fp -Xs -R
   ```

   Флаг `-R` автоматически создаст файл `standby.signal` и настроит параметры подключения.

### Настройка логической репликации

1. **На стороне публикации (Publisher)**:

   ```sql
   CREATE PUBLICATION my_pub FOR TABLE users, orders;
   ```

2. **На стороне подписки (Subscriber)**:

   ```sql
   CREATE SUBSCRIPTION my_sub CONNECTION 'host=... user=... dbname=...' PUBLICATION my_pub;
   ```

### Ручное переключение (Manual Failover)

Если основной сервер вышел из строя, реплику можно «повысить» до мастера командой:

```bash
pg_ctl promote
```

Для автоматизации этого процесса в production рекомендуется использовать **[Patroni](./high_availability.md#patroni)**.
