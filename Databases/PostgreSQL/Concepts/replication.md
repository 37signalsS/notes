# Репликация в PostgreSQL

## 1. Определения

* **Физическая репликация (Physical Replication):** Побайтовая передача данных с мастера на реплику. В PostgreSQL реализуется через механизм **Streaming Replication**. Реплика является точной бинарной копией мастера.
* **Логическая репликация (Logical Replication):** Репликация изменений на уровне объектов БД (строки, таблицы) по принципу "поставщик-подписчик" (Publisher-Subscriber).
* **Слот репликации (Replication Slot):** Механизм, гарантирующий, что мастер не удалит WAL-записи, пока реплика не подтвердит их получение. Предотвращает отставание реплики при временных сбоях связи.

## 2. Основные концепции

Общие цели, типы (синхронная/асинхронная) и топологии репликации описаны в [основной заметке о концепциях репликации](../../../Databases/Concepts/replication.md).

### 2.1. Физическая репликация (Streaming Replication)

Наиболее распространенный тип репликации в PostgreSQL. Записи [журнала предзаписи (WAL)](../../Concepts/write_ahead_log.md) передаются с ведущего сервера (master) на ведомый (replica/standby) и применяются к нему.

* **Особенности:**
  * Реплицируется весь кластер целиком, выборочная репликация невозможна.
  * Мастер и реплика должны иметь одну и ту же мажорную версию PostgreSQL и совместимую архитектуру.
  * Реплика по умолчанию доступна только для чтения (`Hot Standby`).
* **Процессы-участники:**
  * `wal_sender` (на мастере): Отправляет WAL-сегменты.
  * `wal_receiver` (на реплике): Принимает WAL-сегменты.
  * `startup` (на реплике): Применяет полученные WAL-сегменты.

### 2.2. Логическая репликация (Publisher-Subscriber)

Передает не целые WAL-сегменты, а логические изменения отдельных таблиц.

* **Особенности:**
  * Позволяет выборочно реплицировать таблицы или базы данных.
  * Возможна репликация между разными мажорными версиями PostgreSQL.
  * Требует `wal_level = logical` на сервере-публикаторе.
* **Ограничения:**
  * Изменения схемы (DDL) не реплицируются автоматически.
  * Состояния последовательностей (sequences) не реплицируются.
  * Рассинхронизация схем может привести к остановке репликации (например, при нарушении уникального ключа на подписчике).

### 2.3. Уровни синхронности (`synchronous_commit`)

Этот параметр определяет компромисс между надежностью и задержкой транзакции при синхронной репликации.

* `remote_apply` (самый надежный): Мастер ждет, пока транзакция будет **применена** на реплике и станет видимой для запросов.
* `on` (по умолчанию): Мастер ждет, пока транзакция будет **записана** в WAL на диск реплики.
* `remote_write`: Мастер ждет, пока реплика **получит** WAL в кэш ОС.
* `local`: Мастер подтверждает транзакцию после записи в свой WAL, не дожидаясь реплики.
* `off`: Полностью асинхронная фиксация. Максимальная производительность, но самый высокий риск потери данных.

## 3. Практические сценарии

### 3.1. Настройка Streaming Replication (упрощенно)

**Шаг 1: Настройка мастера**

1. Создать пользователя для репликации:

    ```sql
    CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'your_password';
    ```

2. Добавить запись в `pg_hba.conf`:

    ```conf
    # Разрешить подключение пользователя-репликатора с IP-адреса реплики
    host  replication  replicator  <ip_адрес_реплики>/32  md5
    ```

3. Настроить `postgresql.conf`:

    ```ini
    wal_level = replica
    max_wal_senders = 5
    ```

4. Перезапустить PostgreSQL на мастере.

**Шаг 2: Настройка реплики**

1. Остановить PostgreSQL на сервере реплики.
2. Создать базовую копию с мастера (удалит все в `PGDATA` реплики!):

    ```bash
    # Убедитесь, что каталог PGDATA пуст
    pg_basebackup -h <ip_адрес_мастера> -U replicator -D $PGDATA -Fp -Xs -R
    ```

    * `-R` создаст файл `standby.signal` и запишет строку подключения в `postgresql.auto.conf`.
3. Запустить PostgreSQL на реплике.

### 3.2. Настройка логической репликации

**Шаг 1: На мастере (Publisher)**

1. Установить `wal_level = logical` в `postgresql.conf` и перезапустить сервер.
2. Создать публикацию для одной или нескольких таблиц:

    ```sql
    CREATE PUBLICATION my_publication FOR TABLE users, products;
    ```

**Шаг 2: На подписчике (Subscriber)**

1. Убедиться, что таблицы `users` и `products` существуют (обычно пустые).
2. Создать подписку:

    ```sql
    CREATE SUBSCRIPTION my_subscription 
    CONNECTION 'host=... dbname=... user=... password=...' 
    PUBLICATION my_publication;
    ```

### 3.3. Ручное переключение (Failover)

При сбое мастера физическую реплику можно вручную "повысить" до нового мастера.

1. **На сервере реплики** выполнить команду:

    ```bash
    pg_ctl promote
    ```

2. Реплика завершит режим восстановления и станет полноценным мастером, доступным для записи.

## 4. Дополнительные сведения

### Проблема "Split-Brain"

Если после аварийного переключения старый мастер снова станет доступным, возникнет ситуация, когда оба сервера считают себя мастерами. Это приводит к рассинхронизации данных. Для предотвращения этого используются внешние системы управления кластером.

### Автоматический Failover

PostgreSQL не имеет встроенного автоматического failover. Эта задача решается с помощью внешних инструментов, таких как **Patroni**, которые управляют состоянием кластера, обеспечивают кворум и автоматически повышают реплику при сбое мастера.

> Подробнее о решениях, таких как Patroni, см. в заметке [Концепции высокой доступности](./high_availability.md).
