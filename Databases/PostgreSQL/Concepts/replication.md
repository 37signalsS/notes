# Репликация в PostgreSQL

## Определения

- **Физическая репликация (Physical Replication)**: Побайтовая передача данных с основного сервера на подчиненный. В PostgreSQL реализуется через механизм **Streaming Replication**. Реплика является точной бинарной копией основного сервера.
- **Логическая репликация (Logical Replication)**: Передача изменений на уровне отдельных строк или таблиц по принципу «поставщик — подписчик» (Publisher-Subscriber).
- **Слот репликации (Replication Slot)**: Механизм на основном сервере, гарантирующий, что записи WAL не будут удалены до тех пор, пока они не будут успешно переданы на реплику. Предотвращает поломку репликации при длительных сбоях связи.

## Базовые концепции

Общие цели, типы (синхронная/асинхронная) и топологии репликации описаны в **[Репликация баз данных](../../Concepts/replication.md)**. Проблема **Split-Brain** подробно рассмотрена в разделе **[механизмы Failover](../../Concepts/replication.md#проблема-split-brain-и-решение-через-кворум)**.

### Потоковая репликация (Streaming Replication)

Основной тип физической репликации в PostgreSQL. Записи **[журнала предзаписи (WAL)](../../Concepts/write_ahead_log.md)** передаются с основного сервера (Master/Primary) на ведомый (Standby/Replica) в реальном времени.

Если реплика отстает от мастера (Replication Lag), пользователи могут читать устаревшие данные, а в случае аварийного переключения (Failover) возможна потеря транзакций, которые еще не были применены на реплике.

#### Режимы работы Standby-сервера

1. **Warm Standby**: Сервер находится в режиме восстановления, принимает WAL, но **не разрешает подключения** пользователей. Используется как «холодный» резерв.
2. **Hot Standby**: Сервер применяет изменения и **разрешает подключения на чтение** (ReadOnly). Активируется параметром `hot_standby = on`.

- **Особенности**:
  - Реплицируется весь кластер целиком (все базы данных).
  - Версии PostgreSQL и архитектура ОС на серверах должны быть идентичны (мажорная версия).
- **Процессы**:
  - `wal_sender` (на мастере): Читает WAL и отправляет их по сети.
  - `wal_receiver` (на реплике): Принимает данные и записывает их.
  - `startup` (на реплике): Процесс восстановления, применяющий записи WAL к файлам данных.

### Логическая репликация (Publisher-Subscriber)

Позволяет передавать изменения выборочно (только определенные таблицы). Требует установки `wal_level = logical`. WAL-декодер преобразует изменения в row-level stream (INSERT/UPDATE/DELETE для выбранных таблиц).

- **Плюсы**:
  - Возможность репликации между разными мажорными версиями PostgreSQL (полезна при zero-downtime обновлении).
  - Возможность объединять данные из нескольких источников в одну БД (Multi-source).
  - Bi-directional репликация (multi-master): возможно, но сложно из-за конфликтов — требуется ручное разрешение на уровне приложения.
- **Ограничения**:
  - Изменения схемы (DDL) не реплицируются автоматически.
  - Не реплицируются состояния последовательностей (`sequences`).
  - Требуется наличие первичного ключа (`PRIMARY KEY`) или `REPLICA IDENTITY` для идентификации изменяемых строк.

### Каскадная репликация

Как физическая, так и логическая репликация поддерживает цепочку: реплика может быть источником для следующей реплики, снижая нагрузку на primary.

```conf
# На реплике (в primary_conninfo указывается вышестоящий узел — не обязательно primary)
primary_conninfo = 'host=upstream-replica port=5432 user=replicator'
```

Каскадная топология полезна при большом количестве реплик или распределении по DC: одна реплика в регионе получает WAL от primary, остальные — от неё.

### Уровни синхронизации (Synchronous Commit)

Параметр `synchronous_commit` определяет, насколько надежно подтверждается транзакция при использовании синхронных реплик.

| Значение | Описание | Уровень надежности |
| :--- | :--- | :--- |
| `remote_apply` | Мастер ждет, пока транзакция будет **применена** на реплике | Максимальный (данные видны в SELECT на реплике) |
| `on` (default) | Мастер ждет записи транзакции в WAL на **диск** реплики | Высокий (защита от сбоя питания мастера) |
| `remote_write` | Мастер ждет получения WAL в **кэш ОС** реплики | Средний (защита от падения процесса БД) |
| `local` | Мастер подтверждает запись только в свой локальный WAL | Низкий (репликация фактически асинхронная) |
| `off` | Полностью асинхронная фиксация | Минимальный (риск потери данных при сбое мастера) |

## Практические сценарии

### Сценарий 1: Настройка потоковой репликации (Physical)

**Шаг 1: Настройка основного сервера (Primary)**

1. В `postgresql.conf` установить параметры для поддержки репликации:

   ```conf
   wal_level = replica       # Базовый уровень для стриминговой репликации
   max_wal_senders = 5       # Максимальное количество одновременных подключений реплик
   wal_keep_size = 256MB     # Объем старых WAL, которые мастер хранит для реплик (PostgreSQL 13+)
   ```

2. Создать пользователя с правами репликации:

   ```sql
   CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'strongpassword';
   # → CREATE ROLE
   ```

3. Разрешить подключение в `pg_hba.conf`:

   ```conf
   host replication replicator <replica_ip>/32 md5
   ```

**Шаг 2: Настройка реплики (Replica)**

1. Удалить текущие данные (если есть) и снять базовую копию с мастера:

   ```bash
   pg_basebackup -h <primary_ip> -U replicator -D /var/lib/postgresql/data -P -Xs -R
   # → 31234/31234 kB (100%), 1/1 tablespace
   ```

   - `-R` — автоматически создает файл `standby.signal` и прописывает параметры подключения (`primary_conninfo`) в `postgresql.auto.conf`.

2. Запустить PostgreSQL на реплике. Она автоматически перейдет в режим Standby и начнет получать WAL от мастера.

### Сценарий 2: Настройка логической репликации

1. **На стороне публикации (Publisher)**:

   ```sql
   CREATE PUBLICATION my_pub FOR TABLE users, orders;
   # → CREATE PUBLICATION
   ```

2. **На стороне подписки (Subscriber)**:

   ```sql
   CREATE SUBSCRIPTION my_sub CONNECTION 'host=... user=... dbname=...' PUBLICATION my_pub;
   # → CREATE SUBSCRIPTION
   ```

### Сценарий 3: Мониторинг состояния и отставания (Lag)

**На основном сервере (Primary):**
Проверка активных подключений реплик и расчет отставания в байтах.

```sql
SELECT 
    client_addr, 
    state, 
    sent_lsn, 
    write_lsn, 
    flush_lsn, 
    replay_lsn,
    (sent_lsn - replay_lsn) AS replication_lag_bytes
FROM pg_stat_replication;
# → 192.168.1.10 | streaming | 0/3000060 | 0/3000060 | 0/3000060 | 0/3000060 | 0
```

**На реплике (Replica):**

1. Проверка режима работы (должно быть `t` для реплики):

   ```sql
   SELECT pg_is_in_recovery();
   # → t
   ```

2. Проверка задержки применения последней транзакции в секундах:

   ```sql
   SELECT now() - pg_last_xact_replay_timestamp() AS replication_delay;
   # → 00:00:01.123
   ```

### Сценарий 4: Ручное переключение (Manual Failover)

Если основной сервер вышел из строя, реплику можно «повысить» до мастера командой:

```bash
pg_ctl promote
# → server promoting
```

Для автоматизации этого процесса в production рекомендуется использовать **[Patroni](./high_availability.md#patroni)**.
