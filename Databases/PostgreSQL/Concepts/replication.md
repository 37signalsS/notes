# Репликация в PostgreSQL

## Определения

- **Репликация** — процесс дублирования данных, при котором информация с основного сервера (Master/Primary) автоматически копируется на один или несколько вспомогательных серверов (Replica/Standby).
- **Физическая репликация (Physical Replication)**: Побайтовая передача данных. Реализуется через механизм **Streaming Replication**. Реплика является точной бинарной копией основного сервера.
- **Логическая репликация (Logical Replication)**: Передача изменений на уровне отдельных строк или таблиц по принципу «издатель — подписчик» (Publisher-Subscriber).
- **WAL (Write-Ahead Log)**: Журнал предзаписи транзакций. Все изменения сначала фиксируются в WAL, а затем применяются к файлам данных. WAL является фундаментом для всех видов репликации в PostgreSQL.

## Цели репликации

1.  **Повышение отказоустойчивости (High Availability)**: При выходе из строя основного сервера одна из реплик может быть повышена до мастера, обеспечивая непрерывность работы.
2.  **Повышение производительности (Read Scaling)**: Распределение нагрузки путем направления запросов на чтение (SELECT) на реплики, освобождая мастер для операций записи.
3.  **Географическое распределение**: Размещение данных ближе к пользователям для снижения сетевых задержек.

## Базовые концепции

### Потоковая репликация (Streaming Replication)

Основной тип физической репликации, при котором WAL-записи передаются в реальном времени.

**Режимы синхронизации:**

| Режим | Описание | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **Асинхронная** | Мастер подтверждает транзакцию сразу после локальной записи, не дожидаясь реплик. | Максимальная производительность; мастер не зависит от состояния реплик. | Риск потери последних данных при внезапном сбое мастера (если они не успели уйти в сеть). |
| **Синхронная** | Мастер ждет подтверждения записи в WAL хотя бы на одной реплике перед фиксацией транзакции. | Гарантированная сохранность данных; реплика всегда актуальна. | Снижение производительности из-за задержек сети; простой мастера при отказе всех синхронных реплик. |

**Особенности:**
- Реплицируется весь экземпляр БД целиком.
- Требуется идентичная мажорная версия PostgreSQL и архитектура ОС.
- **Hot Standby**: Позволяет использовать реплику для выполнения запросов на чтение.

### Логическая репликация

Работает по модели **Публикация (Publication)** — **Подписка (Subscription)**. Оперирует логическими записями в таблицах (INSERT/UPDATE/DELETE).

**Ключевые возможности:**
- Выборочная репликация (только нужные таблицы или части таблиц через фильтры `WHERE`).
- Работа между разными версиями PostgreSQL, разными ОС и архитектурами.
- Позволяет объединять данные из нескольких источников в одну БД.

**Ограничения:**
- Не реплицируются изменения структуры (DDL: `CREATE TABLE`, `ALTER`). Их нужно применять на всех узлах вручную.
- Не реплицируются последовательности (`sequences`), крупные объекты (`large objects`), представления (`views`).
- Требуется наличие первичного ключа (`PRIMARY KEY`) или уникального индекса для корректной идентификации строк при обновлениях.

## Уровни синхронизации (synchronous_commit)

### Уровни синхронизации (synchronous_commit)

Параметр управляет балансом между производительностью и гарантией сохранности данных.

| Значение | Описание | Риск |
| :--- | :--- | :--- |
| `remote_apply` | Ждет записи в WAL и **применения** данных на реплике. | Самый медленный, гарантирует актуальность чтения с реплики. |
| `on` (default) | Ждет записи в WAL на **диск** реплики. | Оптимальный баланс для HA. |
| `remote_write` | Ждет получения WAL в **память** (кэш ОС) реплики. | Данные могут быть потеряны при сбое по питанию на реплике. |
| `local` | Подтверждает запись только в локальный WAL. | Репликация фактически асинхронная. |

## Практические сценарии

### 1. Настройка потоковой репликации (физической)

**На стороне Primary:**
1. Настроить `postgresql.conf`:
   ```conf
   wal_level = replica
   max_wal_senders = 10
   wal_keep_size = 1GB  -- Вместо устаревшего wal_keep_segments
   ```
2. Создать пользователя: `CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'pass';`
3. Добавить в `pg_hba.conf`: `host replication replicator <replica_ip>/32 scram-sha-256`

**На стороне Standby:**
1. Снять базовую копию:
   ```bash
   pg_basebackup -h <primary_ip> -U replicator -D /var/lib/postgresql/data -P -R -Xs --slot=replica_1
   ```
   Флаг `-R` создаст `standby.signal` и `postgresql.auto.conf` с параметрами подключения.

### 2. Настройка логической репликации с фильтрацией

**На стороне Издателя (Publisher):**
```sql
-- Публикация только определенных столбцов и строк
CREATE PUBLICATION sales_pub FOR TABLE orders (id, amount, status) WHERE (status = 'completed');
```

**На стороне Подписчика (Subscriber):**
```sql
CREATE SUBSCRIPTION sales_sub CONNECTION 'host=... dbname=...' PUBLICATION sales_pub;
```

### 3. Мониторинг и диагностика

**Проверка отставания (Lag):**
На Primary через представление `pg_stat_replication`:
```sql
SELECT client_addr, state, 
       pg_wal_lsn_diff(sent_lsn, write_lsn) AS write_lag,
       pg_wal_lsn_diff(sent_lsn, flush_lsn) AS flush_lag,
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS replay_lag
FROM pg_stat_replication;
```

**Проверка статуса восстановления:**
На Standby: `SELECT pg_is_in_recovery(), pg_last_wal_receive_lsn(), pg_last_wal_replay_lsn();`

## Дополнительная информация

### Управление отказоустойчивостью

Стандартный PostgreSQL не выполняет автоматическое переключение при сбое мастера. Для этих целей используются внешние инструменты:
- **Patroni**: Лидер в области управления отказоустойчивыми кластерами PostgreSQL. Подробнее: **[High Availability](./high_availability.md)**.
- **repmgr**: Популярная утилита для ручного и автоматического управления репликацией.
