# Наблюдаемость PostgreSQL (Full-Stack Observability)

## Определения

**Наблюдаемость (Observability)** для базы данных — это способность понимать внутреннее состояние PostgreSQL на основе внешних данных: метрик, логов, трассировок и событий ожидания.

**Ключевые понятия:**

- **Full-Stack Observability** — подход, объединяющий данные БД с контекстом приложения (trace_id) для сквозной диагностики.
- **4 столпа Observability** — логи, метрики, трассировки и профилирование. Подробнее — [Определения Observability](../../../Concepts/Observability_and_Monitoring/observability_definitions.md).

## Основные концепции

### Проблема мониторинга PostgreSQL

Традиционный мониторинг ресурсов (CPU, RAM) часто не дает ответа на вопрос "почему база тормозит?". Система может деградировать при низком потреблении ресурсов из-за блокировок, неоптимальных планов запросов или нехватки памяти в `shared_buffers`.

**Ключевая идея:** переход от "мониторинга состояния" к "анализу производительности" через связывание активности приложения с внутренними процессами БД с помощью сквозного идентификатора трассировки (`trace_id`).

### Ключевые области анализа

1. **События ожидания (Wait Events):** Информация из `pg_stat_activity` о том, чего именно ждет процесс (IO, Lock, CPU). Позволяет отличить проблемы диска от конкуренции за блокировки. Подробный разбор типов — [Диагностика дисковых узких мест](../../db_disk_bottleneck_troubleshooting.md#шаг-3-анализ-событий-ожидания-wait-events).
2. **Активные соединения и транзакции:** Мониторинг состояний сессий (`active`, `idle`, `idle in transaction`). Особое внимание — транзакциям, открытым дольше нескольких минут, которые могут мешать `VACUUM`.
3. **Дисковый I/O и Buffer Cache:** Анализ чтений и записей. Отличие "хитов" кэша (`shared_buffers`) от физических чтений. Важно отслеживать `track_io_timing` для понимания латентности диска.
4. **Блокировки (Locks):** Обнаружение длительных блокировок таблиц и строк. Корреляция между `pg_stat_activity` и `pg_locks`.
5. **Отставание репликации:** Критичный показатель для отказоустойчивых кластеров (High Availability). Отслеживается через `pg_stat_replication`.
6. **Прогресс длительных операций:** Использование семейства представлений `pg_stat_progress_*` для отслеживания `VACUUM`, `CREATE INDEX`, `ANALYZE` и `COPY`.
7. **Фоновые процессы (SRE-метрики):** Мониторинг `bgwriter` и `checkpoints` (`pg_stat_bgwriter`) для оценки нагрузки на диск при сбросе "грязных" страниц.
8. **Журналы (Logs):** Сбор медленных запросов (`log_min_duration_statement`), ошибок и информации о контрольных точках.

## Практические сценарии

### Конфигурация для глубокой наблюдаемости

Для того чтобы PostgreSQL отдавал максимум полезных данных, необходимо изменить значения по умолчанию в `postgresql.conf`:

```ini
# --- Сбор статистики ---
# Включает сбор статистики времени ввода-вывода (накладные расходы минимальны на совр. ОС)
track_io_timing = on
# Включает сбор статистики по вызовам функций (PL/pgSQL)
track_functions = all
# Позволяет связывать pg_stat_activity и pg_stat_statements (PG 14+)
compute_query_id = on

# --- Логирование ---
# Логировать запросы дольше 250мс (настроить под нагрузку)
log_min_duration_statement = 250ms
# Логировать информацию о выполнении контрольных точек (checkpoints)
log_checkpoints = on
# Логировать блокировки, если ожидание превысило deadlock_timeout
log_lock_waits = on
# Префикс лога для удобного парсинга (включает имя приложения и пользователя)
log_line_prefix = '%m [%p] %u@%d [%a] '
# Логировать временные файлы (помогает найти нехватку work_mem)
log_temp_files = 0
```

### Архитектура сквозной наблюдаемости

1. **Уровень приложения:**
   - Инструментируется OpenTelemetry SDK.
   - Добавляет `trace_id` в SQL-запросы через **sqlcommenter** (стандарт OTel для БД).
   - Передает контекст трассировки в заголовках к СУБД (через расширения).

2. **Уровень базы данных (PostgreSQL):**
   - **Логи:** `trace_id` из комментариев извлекается и записывается в логи (через настройку `log_line_prefix`).
   - **Трассировка:** Расширение `pg_tracing` (или аналоги) создает спаны для фаз `parsing`, `planning` и `execution`.
   - **Метрики:** **[postgres_exporter](../../Prometheus/Exporters/other_exporters.md#1-базы-данных-databases)** собирает данные из представлений `pg_stat_*`.

3. **Агент-коллектор (Grafana Alloy / OpenTelemetry Collector):**
   - Собирает метрики, парсит логи (извлекая `traceid`), принимает трейсы.
   - Проводит корреляцию данных перед отправкой в хранилище.

4. **Визуализация (Grafana):**
   - Позволяет из графика метрики (всплеск Latency) перейти к логам этого периода, а оттуда — к конкретному трейсу запроса.

### Корреляция через sqlcommenter

**sqlcommenter** добавляет метаданные в SQL-комментарии, которые видны в `pg_stat_activity` и логах:

```sql
-- Пример запроса с метаданными OpenTelemetry
SELECT * FROM orders 
WHERE id = 123 
/*application='web-api',traceparent='00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01'*/;
```

Для интеграции с логами рекомендуется настроить `log_line_prefix` в `postgresql.conf`:
`log_line_prefix = '%m [%p] %u@%d [%a] '` (параметр `%a` выводит имя приложения, которое может содержать метаданные).

### Расширения и инструменты для анализа

| Инструмент | Назначение |
| :--- | :--- |
| `pg_stat_statements` | **Must-have**. Статистика всех запросов: время выполнения, I/O, кол-во строк. Позволяет выявить "самые тяжелые" запросы за период. |
| `auto_explain` | Автоматически логирует планы выполнения (`EXPLAIN`) для медленных запросов. Незаменим для post-mortem анализа без ручного запуска запроса. |
| `pg_stat_kcache` | Дополняет `pg_stat_statements` статистикой использования CPU и дискового I/O на уровне ядра ОС (через `getrusage`). |
| `pg_wait_sampling` | (Расширение) Позволяет собирать историю событий ожидания (wait events) в виде профиля, а не только мгновенный снимок из `pg_stat_activity`. |
| `pg_profile` / `pg_probackup` | Генерация детальных отчетов о состоянии БД (аналог Oracle AWR) для анализа трендов производительности. |
| **Native Query ID** | Встроено в PG 14+. Позволяет связывать данные `pg_stat_activity` (текущий запрос) и `pg_stat_statements` (агрегированная история). |
| **eBPF (advanced)** | Использование инструментов вроде `bcc` или `bpftrace` для анализа задержек на уровне системных вызовов без нагрузки на БД. |

Подробнее об использовании `pg_stat_statements` — [Оптимизация производительности](./performance_tuning.md).

## Дополнительная информация

### Выбор инструментов

Для построения современной платформы наблюдаемости рекомендуется связка:
- **Метрики:** Prometheus / VictoriaMetrics.
- **Логи:** Grafana Loki (с извлечением меток из логов PG).
- **Трейсы:** Grafana Tempo.
- **Коллектор:** Grafana Alloy (поддерживает нативный сбор метрик и логов PostgreSQL).
