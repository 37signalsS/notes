# Наблюдаемость PostgreSQL (Full-Stack Observability)

## Определения

**Наблюдаемость (Observability)** для базы данных — это способность понимать внутреннее состояние PostgreSQL на основе внешних данных: метрик, логов, трассировок и событий ожидания.

**Ключевые понятия:**

- **Full-Stack Observability** — подход, объединяющий данные БД с контекстом приложения (trace_id) для сквозной диагностики.
- **4 столпа Observability** — логи, метрики, трассировки и профилирование. Подробнее — [Определения Observability](../../../Concepts/Observability_and_Monitoring/observability_definitions.md).

## Основные концепции

### Проблема мониторинга PostgreSQL

Традиционный мониторинг ресурсов (CPU, RAM) часто не дает ответа на вопрос "почему база тормозит?". Система может деградировать при низком потреблении ресурсов из-за блокировок, неоптимальных планов запросов или нехватки памяти в `shared_buffers`.

**Ключевая идея:** переход от "мониторинга состояния" к "анализу производительности" через связывание активности приложения с внутренними процессами БД с помощью сквозного идентификатора трассировки (`trace_id`).

### Ключевые области анализа

1. **События ожидания (Wait Events):** Информация из `pg_stat_activity` о том, чего именно ждет процесс (IO, Lock, CPU). Это самый быстрый способ найти "узкое место".
2. **Активные соединения:** Мониторинг состояний сессий (`active`, `idle`, `idle in transaction`). Решение проблем с "брошенными" транзакциями.
3. **Дисковый I/O:** Анализ чтений и записей. Отличие "хитов" кэша (`shared_buffers`) от физических чтений с диска.
4. **Блокировки (Locks):** Обнаружение длительных блокировок таблиц и строк, вызывающих простои приложения.
5. **Отставание репликации:** Критичный показатель для отказоустойчивых кластеров (High Availability).
6. **Журналы (Logs):** Сбор медленных запросов (`log_min_duration_statement`) и ошибок.

## Практические сценарии

### Архитектура сквозной наблюдаемости

1. **Уровень приложения:**
   - Инструментируется OpenTelemetry SDK.
   - Добавляет `trace_id` в SQL-запросы через **sqlcommenter** (стандарт OTel для БД).
   - Передает контекст трассировки в заголовках к СУБД (через расширения).

2. **Уровень базы данных (PostgreSQL):**
   - **Логи:** `trace_id` из комментариев извлекается и записывается в логи (через настройку `log_line_prefix`).
   - **Трассировка:** Расширение `pg_tracing` (или аналоги) создает спаны для фаз `parsing`, `planning` и `execution`.
   - **Метрики:** `postgres_exporter` собирает данные из представлений `pg_stat_*`.

3. **Агент-коллектор (Grafana Alloy / OpenTelemetry Collector):**
   - Собирает метрики, парсит логи (извлекая `traceid`), принимает трейсы.
   - Проводит корреляцию данных перед отправкой в хранилище.

4. **Визуализация (Grafana):**
   - Позволяет из графика метрики (всплеск Latency) перейти к логам этого периода, а оттуда — к конкретному трейсу запроса.

### Корреляция через sqlcommenter

**sqlcommenter** добавляет метаданные в SQL-комментарии, которые видны в `pg_stat_activity` и логах:

```sql
-- Пример запроса с метаданными OpenTelemetry
SELECT * FROM orders 
WHERE id = 123 
/*application='web-api',traceparent='00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01'*/;
```

Для интеграции с логами рекомендуется настроить `log_line_prefix` в `postgresql.conf`:
`log_line_prefix = '%m [%p] %u@%d [%a] '` (параметр `%a` выводит имя приложения, которое может содержать метаданные).

### Расширения и инструменты для анализа

| Инструмент | Назначение |
| :--- | :--- |
| `pg_stat_statements` | Золотой стандарт. Статистика выполнения всех запросов (время, кол-во строк, I/O). |
| `pg_stat_kcache` | Статистика использования CPU и дискового I/O на уровне ядра ОС для каждого запроса. |
| `pg_profile` / `pg_probackup` | Генерация детальных отчетов о состоянии БД (аналог Oracle AWR). |
| **Native Query ID** | Встроено в PG 14+. Позволяет связывать данные `pg_stat_activity` и `pg_stat_statements`. |
| **eBPF (advanced)** | Использование инструментов вроде `bcc` или `bpftrace` для анализа задержек на уровне системных вызовов без нагрузки на БД. |

Подробнее об использовании — [Оптимизация производительности](./performance_tuning.md).

## Дополнительная информация

### Выбор инструментов

Для построения современной платформы наблюдаемости рекомендуется связка:
- **Метрики:** Prometheus / VictoriaMetrics.
- **Логи:** Grafana Loki (с извлечением меток из логов PG).
- **Трейсы:** Grafana Tempo.
- **Коллектор:** Grafana Alloy (поддерживает нативный сбор метрик и логов PostgreSQL).
