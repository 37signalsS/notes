# Наблюдаемость PostgreSQL (Сквозной мониторинг)

## Определения

**Наблюдаемость (Observability)** для базы данных — это способность понимать внутреннее состояние PostgreSQL на основе внешних данных: метрик, логов, трассировок и событий ожидания.

**Ключевые понятия:**

- **Сквозная наблюдаемость (Full-Stack Observability)** — подход, объединяющий данные БД с контекстом приложения (`trace_id`) для сквозной диагностики.
- **4 столпа Observability** — логи, метрики, трассировки и профилирование. Подробнее — [Определения Observability](../../../Concepts/Observability_and_Monitoring/observability_definitions.md).

## Предпосылки

Для реализации полной наблюдаемости требуется:

1.  **Версия PostgreSQL:** 14 и выше (для поддержки `compute_query_id` и встроенных треков).
2.  **Роли и права:** Создание технического пользователя для мониторинга с ролью `pg_monitor`.
    ```sql
    CREATE USER monitoring_user WITH PASSWORD 'password';
    GRANT pg_monitor TO monitoring_user;
    ```
3.  **Расширения:** Обязательная установка `pg_stat_statements` в `shared_preload_libraries`.
4.  **Сетевой доступ:** Открытый порт (по умолчанию 5432) для коллектора или экспортера.

## Основные концепции

### Проблема мониторинга PostgreSQL

Традиционный мониторинг ресурсов (CPU, RAM) часто не дает ответа на вопрос "почему база тормозит?". Система может деградировать при низком потреблении ресурсов из-за блокировок, неоптимальных планов запросов или нехватки памяти в `shared_buffers`.

**Ключевая идея:** переход от "мониторинга состояния" к "анализу производительности" через связывание активности приложения с внутренними процессами БД с помощью сквозного идентификатора трассировки (`trace_id`).

### Ключевые области анализа

1.  **События ожидания (Wait Events):** Информация из `pg_stat_activity` о том, чего именно ждет процесс (IO, Lock, CPU). Позволяет отличить проблемы диска от конкуренции за блокировки. **Важно:** события разделяются на типы: `LWLock` (внутренние защелки), `Lock` (блокировки объектов), `IO` (чтение/запись). Подробный разбор типов и практические рекомендации — [Шпаргалка по Wait Events](#шпаргалка-по-критическим-wait-events).
2.  **Активные соединения и транзакции:** Мониторинг состояний сессий (`active`, `idle`, `idle in transaction`). Особое внимание — транзакциям, открытым дольше нескольких минут, которые могут мешать `VACUUM` и вызывать раздувание (bloat) таблиц.
3.  **Дисковый ввод-вывод (I/O) и Buffer Cache:** Анализ чтений и записей. Отличие "хитов" кэша (`shared_buffers`) от физических чтений. Включение `track_io_timing` позволяет измерять время, затраченное на каждый запрос к диску, что критично для диагностики деградации хранилища.
4.  **Блокировки (Locks):** Обнаружение длительных блокировок таблиц и строк. Корреляция между `pg_stat_activity` (кто ждет) и `pg_locks` (кто держит).
5.  **Отставание репликации (Replication Lag):** Критичный показатель для отказоустойчивых кластеров (High Availability). Отслеживается через `pg_stat_replication` (на Primary) и `pg_last_xact_replay_timestamp()` (на Standby).
6.  **Прогресс длительных операций:** Использование семейства представлений `pg_stat_progress_*` для отслеживания `VACUUM`, `CREATE INDEX`, `ANALYZE` и `COPY`. Позволяет оценить оставшееся время выполнения тяжелых административных задач.
7.  **Фоновые процессы (SRE-метрики):** Мониторинг `bgwriter` и `checkpoints` (`pg_stat_bgwriter`) для оценки нагрузки на диск при сбросе "грязных" страниц. Помогает настроить `max_wal_size` и `checkpoint_timeout`.
8.  **Журналы (Logs):** Сбор медленных запросов (`log_min_duration_statement`), ошибок, информации о контрольных точках и временных файлах. 
    - **Безопасность логов:** Перед сбором логов убедитесь, что в них не попадают PII-данные. Для маскирования чувствительной информации на уровне БД используйте **[Анонимизацию и маскирование](./anonymization.md)**.

### Базовые метрики здоровья (минимальный дашборд)

До внедрения глубокой наблюдаемости (wait events, трассировка) полезен минимальный набор метрик, отвечающих на вопрос «работает ли база и не собирается ли деградировать»:

| Метрика | Источник | Тревожные признаки |
| :--- | :--- | :--- |
| **Доступность** | `SELECT 1`, `pg_up` экспортера | Недоступность инстанса |
| **Число соединений** | `pg_stat_activity` | Приближение к `max_connections`; рост доли `idle`-сессий |
| **Самая долгая транзакция** | `pg_stat_activity` | Транзакции часами; долгие `idle in transaction` |
| **Блокировки** | `pg_locks` + `pg_stat_activity` | Растущая очередь ожидающих, взаимные блокировки |
| **Отставание репликации и слоты** | `pg_stat_replication`, `pg_replication_slots` | Рост lag; неактивный слот, удерживающий WAL |

```sql
-- Самые долгие активные транзакции (включая idle in transaction)
SELECT now() - xact_start AS xact_duration, pid, usename, state, left(query, 80) AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start
LIMIT 5;

-- Количество запросов, ожидающих блокировку
SELECT count(*) FROM pg_locks WHERE NOT granted;
```

Практический кейс ценности метрики «самая долгая транзакция»: процесс логической репликации открыл транзакцию и не коммитил её, ожидая недоступный внешний ресурс (сетевые таймауты). Слот репликации не продвигался, WAL начал накапливаться вплоть до заполнения диска. Мониторинг долгих транзакций и статуса слотов (`pg_replication_slots.wal_status`, `active`) обнаруживает такую ситуацию заранее. Подробнее: [Репликация](../Concepts/replication.md), [Настройка PgBouncer](./pgbouncer_setup.md).

### Шпаргалка по критическим Wait Events

Данная шпаргалка помогает быстро интерпретировать события, занимающие верхние строчки в `pg_stat_activity` или `pg_wait_sampling`.

| Wait Event | Тип | Описание | Причины и решение |
| :--- | :--- | :--- | :--- |
| **DataFileRead** | `IO` | Чтение страниц данных с диска в Shared Buffers. | **Причина:** Промах кэша (Buffer Cache Miss). Запрос требует данных, которых нет в RAM. <br> **Решение:** Проверить индексы (избегать `Seq Scan`), увеличить `shared_buffers`, оптимизировать запрос для уменьшения объема выборки. |
| **WALWriteLock** | `LWLock` | Ожидание освобождения WAL-буферов для записи на диск. | **Причина:** Чрезмерно высокая частота мелких транзакций или низкая скорость диска, где лежит `pg_wal`. <br> **Решение:** Использовать групповые коммиты (batching), увеличить `wal_buffers` (до 64-128MB), перенести WAL на быстрые NVMe-диски. |
| **RelationExtension** (Extend) | `LWLock` | Ожидание расширения файла таблицы или индекса новыми блоками. | **Причина:** Массовая параллельная вставка в одну таблицу. Несколько процессов борются за право расширить файл. <br> **Решение:** Проверить нагрузку на `INSERT`, рассмотреть партиционирование таблицы, проверить Latency диска (медленное выделение места ОС). |
| **DataFileExtend** | `IO` | Ожидание физического расширения файла на уровне ОС. | **Причина:** Файловая система медленно выделяет новые блоки. <br> **Решение:** Проверить настройки ФС (XFS/Ext4 с `noatime`), убедиться, что диск не перегружен фоновыми задачами. |
| **Lock: tuple** | `Lock` | Ожидание блокировки конкретной строки. | **Причина:** Конкуренция за обновление одной и той же строки. <br> **Решение:** Пересмотреть логику приложения, избегать "горячих" строк, использовать `SKIP LOCKED` для очередей. |

## Практические сценарии

### Конфигурация для глубокой наблюдаемости

Для того чтобы PostgreSQL отдавал максимум полезных данных, необходимо изменить значения по умолчанию в `postgresql.conf`:

```ini
# --- Сбор статистики ---
# Включает сбор статистики времени ввода-вывода (накладные расходы минимальны на совр. ОС)
track_io_timing = on
# Включает сбор статистики по вызовам функций (PL/pgSQL)
track_functions = all
# Позволяет связывать pg_stat_activity и pg_stat_statements (PG 14+)
compute_query_id = on

# --- Логирование ---
# Логировать запросы дольше 250мс (настроить под нагрузку)
log_min_duration_statement = 250ms
# Логировать информацию о выполнении контрольных точек (checkpoints)
log_checkpoints = on
# Логировать блокировки, если ожидание превысило deadlock_timeout
log_lock_waits = on
# Префикс лога для удобного парсинга (включает имя приложения и пользователя)
log_line_prefix = '%m [%p] %u@%d [%a] '
# Логировать временные файлы (помогает найти нехватку work_mem)
log_temp_files = 0
```

### Корреляция через sqlcommenter и OpenTelemetry

**sqlcommenter** — это библиотека, которая автоматически внедряет метаданные (trace_id, span_id, имя контроллера) в SQL-запросы в виде комментариев.

**Шаги настройки:**

1.  **Инструментация приложения:**
    - Для Python (Django/SQLAlchemy), Java (Spring Boot), Go (GORM) установите соответствующий пакет `sqlcommenter`.
    - Убедитесь, что `traceparent` передается в комментариях.
2.  **Настройка PostgreSQL:**
    - В `postgresql.conf` установите `log_line_prefix`, включающий `%a` (application_name).
    - Для расширенного анализа используйте расширение `pg_tracing`.

```sql
-- Пример запроса, генерируемого приложением
SELECT * FROM users 
WHERE id = 42 
/*application='billing-service',traceparent='00-84b5-01',controller='UserController'*/;
```

**Преимущество:** В `pg_stat_activity` и `pg_stat_statements` колонка `query` теперь содержит комментарий, позволяя найти конкретный трейс, вызвавший нагрузку.

### Расширенная трассировка с pg_tracing

Расширение `pg_tracing` позволяет PostgreSQL выступать в роли "участника" распределенной трассировки, создавая собственные спаны.

1.  **Установка:** Добавьте `pg_tracing` в `shared_preload_libraries`.
2.  **Возможности:**
    - Создает спаны для этапов: `Parse`, `Plan`, `Rewrite`, `Execute`.
    - Позволяет видеть, сколько времени заняло планирование относительно выполнения.
    - Автоматически коррелирует спаны БД со спанами приложения через `traceparent` из комментариев.

### Расширения и инструменты для анализа

| Инструмент | Назначение | Особенности |
| :--- | :--- | :--- |
| `pg_stat_statements` | Статистика всех запросов. | **Must-have**. Золотой стандарт для поиска "тяжелых" запросов. |
| `pg_stat_monitor` | Современная альтернатива `pg_stat_statements`. | Поддержка **Buckets** (статистика по временным интервалам) и гистограмм. |
| `auto_explain` | Логирование планов медленных запросов. | Помогает понять, почему запрос тормозит (например, Index Scan vs Seq Scan). |
| `pg_stat_kcache` | Статистика ресурсов ОС. | Показывает потребление CPU (user/system) и чтение из дискового кэша ОС. |
| `pg_wait_sampling` | История событий ожидания. | Позволяет строить профили нагрузки (Flame Graphs) по событиям ожидания. |

### Сбор метрик через OpenTelemetry Collector

Для сбора метрик без использования `postgres_exporter` можно использовать встроенный ресивер в OTel Collector.

**Пример конфигурации `otel-collector.yaml`:**

```yaml
receivers:
  postgresql:
    endpoint: "postgres:5432"
    transport: tcp
    username: "${env:POSTGRES_USER}"
    password: "${env:POSTGRES_PASSWORD}"
    databases:
      - "main_db"
    collection_interval: 10s
    tls:
      insecure: true

exporters:
  prometheus:
    endpoint: "0.0.0.0:8889"

service:
  pipelines:
    metrics:
      receivers: [postgresql]
      processors: [batch]
      exporters: [prometheus]
```

**Преимущество:** Уменьшение количества компонентов (не нужен отдельный экспортер) и нативная интеграция в OTel-пайплайн.

## Валидация и проверка

После настройки выполните следующие шаги для проверки корректности сбора данных:

1.  **Проверка работы pg_stat_statements:**
    ```sql
    SELECT query, calls, total_exec_time 
    FROM pg_stat_statements 
    ORDER BY total_exec_time DESC LIMIT 5;
    ```
    *Ожидаемый результат:* список запросов с ненулевыми значениями времени.

2.  **Проверка попадания метаданных (sqlcommenter) в БД:**
    Запустите запрос с комментарием и проверьте его наличие в активных сессиях:
    ```sql
    SELECT pid, query 
    FROM pg_stat_activity 
    WHERE query LIKE '%traceparent%';
    ```

3.  **Проверка логов:**
    Убедитесь, что в лог-файлах присутствуют записи с `trace_id` и `application_name`.

## Устранение неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Пустой query_id в pg_stat_activity** | `compute_query_id` выключен или PG < 14. | Установите `compute_query_id = on` в `postgresql.conf`. |
| **Комментарии sqlcommenter обрезаются** | Слишком длинные запросы или настройки драйвера. | Проверьте параметр `track_activity_query_size` (увеличьте до 2048+). |
| **Высокий CPU при мониторинге** | Слишком высокая частота `pg_wait_sampling` или `track_functions = all`. | Уменьшите частоту сэмплирования или установите `track_functions = pl`. |
| **pg_stat_statements не показывает данные** | Расширение не создано в конкретной базе. | Выполните `CREATE EXTENSION pg_stat_statements;` в каждой БД. |
