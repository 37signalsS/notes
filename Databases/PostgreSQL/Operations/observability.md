# Full-Stack Observability для PostgreSQL

## Определения

* **[Наблюдаемость (Observability)](../../../Concepts/Observability_and_Monitoring/observability_overview.md):** Способность системы отвечать на вопросы о своем внутреннем состоянии на основе анализа производимых ею внешних данных (метрики, логи, трассировки).
* **Метрики (Metrics):** Агрегированная числовая информация о состоянии системы (например, количество запросов в секунду).
* **Логи (Logs):** Записи о конкретных событиях в определенный момент времени (например, медленный запрос).
* **Трассировки (Traces):** Набор связанных "спанов" (spans), отслеживающий полный путь одного запроса через все компоненты распределенной системы.

## Основные концепции

Проблемы с производительностью БД часто неочевидны. Стандартные метрики (CPU, память) могут быть в норме, но система деградирует из-за неоптимальных запросов или блокировок. Чтобы точно ответить на вопрос **"почему система тормозит?"**, необходимо связать активность на уровне приложения с поведением внутри базы данных.

Ключевая идея — прокинуть сквозной **контекст трассировки (`trace_id`)** от клиентского запроса через все микросервисы вплоть до конкретного SQL-запроса. Это позволяет увидеть SQL-операцию как часть общей картины, а не как изолированное событие.

### Ключевые области мониторинга PostgreSQL

1. **Активные соединения:** Резкий рост числа соединений к лимиту `max_connections` — признак проблемы в приложении или нехватки ресурсов. Для защиты используется пулер соединений (например, PgBouncer).
2. **Дисковый ввод-вывод (I/O):** Высокие значения IOPS могут указывать на нехватку RAM (`shared_buffers`), неэффективные запросы (full scan) или медленные диски.
3. **Отставание репликации (Replication Lag):** Критически важная метрика для HA-кластеров. Рост отставания увеличивает риск потери данных при аварийном переключении.
4. **Блокировки (Locks):** Большое количество и длительное удержание блокировок, особенно на уровне таблиц, — прямой путь к деградации производительности всей системы.
5. **Состояние резервных копий:** Возраст последней успешной резервной копии. Сбой в процессе бэкапирования часто остается незамеченным до тех пор, пока не становится слишком поздно.

## Практический сценарий: Архитектура современного стека

1. **Приложение:** Инструментируется с помощью **OpenTelemetry SDK**. При выполнении запросов к БД автоматически добавляется SQL-комментарий **`sqlcommenter`** с `trace_id`.
2. **PostgreSQL:**
    * Принимает запрос с комментарием, `trace_id` попадает в логи.
    * Расширение **`pg_tracing`** (если установлено) создает детализированные спаны для стадий выполнения SQL и отправляет их в коллектор.
    * `postgres_exporter` собирает метрики из системных представлений (`pg_stat_*`).
3. **[Grafana Alloy](../../Grafana/grafana_alloy_overview.md) (Агент-коллектор):**
    * Принимает трейсы от приложения и `pg_tracing`.
    * Собирает метрики с `postgres_exporter`.
    * Читает лог-файлы, парсит их и извлекает `trace_id`.
    * Отправляет все три типа данных в бэкенды Grafana.
4. **Бэкенд (Grafana Stack):**
    * **[Tempo](../../Tempo/tempo_overview.md):** Хранит трейсы.
    * **[Loki](../../Loki/loki_overview.md):** Хранит логи.
    * **[Mimir](../../Mimir/mimir_overview.md) или Prometheus:** Хранит метрики.
5. **Grafana (Визуализация):** Предоставляет единый интерфейс для корреляции всех сигналов: от метрик к трейсам, от трейсов к логам.

## Дополнительные сведения: Инструменты и расширения

### Инструменты для сбора метрик и логов

* **`pg_stat_statements`** / **`pg_stat_monitor`:** Предоставляют агрегированные метрики по запросам. `pg_stat_monitor` является более продвинутой версией, собирающей больше статистики и планы запросов.
* **`auto_explain`:** Автоматически логирует планы выполнения медленных запросов.

> Подробнее об их использовании: [Оптимизация производительности PostgreSQL](./performance_tuning.md#мониторинг-и-диагностика).

### `sqlcommenter`

Это не расширение, а **конвенция и набор библиотек** для добавления метаданных в SQL-комментарии.

* **Принцип:** `SELECT ...` -> `SELECT ... /*application='backend',traceparent='...'*/;`
* **Польза:** Позволяет фильтровать `slow query log` в контексте конкретного сервиса и связывать SQL-запросы с трассировками.
* **Реализация:** Существуют библиотеки для популярных ORM (SQLAlchemy, GORM и др.), которые делают это автоматически.
  * См. [Примеры для OpenTelemetry](../../OpenTelemetry/opentelemetry_overview.md#практический-пример-инструментация-запросов-к-postgresql).

### `pg_tracing` (экспериментальный)

* **Функционал:**
  * Создает спаны для фаз выполнения запроса (parsing, planning, execution).
  * Читает `traceparent` из `sqlcommenter` и связывает свои спаны с родительской трассой.
  * Напрямую экспортирует спаны по протоколу OTLP в коллектор.
* **Статус:** Считается экспериментальным, но активно развивается. Может требовать сборки PostgreSQL из исходного кода.
