# Full-Stack Observability для PostgreSQL

## 1. Определения

*   **[Наблюдаемость (Observability)](../../../Concepts/Observability_and_Monitoring/observability_overview.md):** Способность системы отвечать на вопросы о своем внутреннем состоянии на основе анализа внешних данных, которые она производит (метрики, логи, трассировки).
*   **Метрики (Metrics):** Агрегированная числовая информация о состоянии системы (например, количество запросов в секунду, cache hit rate).
*   **Логи (Logs):** Записи о конкретных событиях, произошедших в системе в определенный момент времени (например, ошибка или медленный запрос).
*   **Трассировки (Traces):** Набор связанных "спанов" (spans), который позволяет отследить полный путь выполнения одного запроса через все компоненты распределенной системы.

## 2. Основные концепции

Проблемы с производительностью БД часто неочевидны. Стандартные метрики (CPU, память) могут быть в норме, но система деградирует из-за неоптимальных запросов или блокировок. Чтобы точно ответить на вопрос **"почему система тормозит?"**, необходимо связать активность на уровне приложения с поведением внутри базы данных.

Ключевая идея — прокинуть сквозной **контекст трассировки (`trace_id`)** от клиентского запроса через все микросервисы вплоть до конкретного SQL-запроса. Это позволяет увидеть SQL-операцию как часть общей картины, а не как изолированное событие.

Связкой между трейсами, логами и метриками служат общие метаданные (лейблы), главным из которых является `trace_id`.

### Ключевые области мониторинга ("Золотые сигналы")

Помимо стандартных системных метрик (CPU, RAM, Disk), для базы данных критически важны свои "золотые сигналы", которые напрямую отражают ее состояние:

1.  **Активные соединения:** В конфиге PostgreSQL есть параметр `max_connections`. Каждое соединение — это отдельный процесс, который потребляет память. Резкий рост числа соединений к `max_connections` — признак проблемы в приложении или нехватки ресурсов. Если приложение откроет слишком много соединений, база данных ответит фатальной ошибкой, и сервис для пользователей ляжет. Для защиты базы от перегрузки соединениями используется пулер соединений, например, **PgBouncer**, который держит очередь и не даёт перегрузить базу.
2.  **Дисковый ввод-вывод (I/O):** Высокие значения IOPS (количество операций ввода-вывода в секунду) и пропускная способность, а также очереди на диск могут указывать на нехватку RAM (`shared_buffers`), неэффективные запросы (full scan вместо index scan) или медленные диски. Если I/O упрется в потолок (например, лимит облачного провайдера), база начнёт сильно тормозить, даже если CPU будет свободен.
3.  **Отставание репликации (Replication Lag):** Критически важная метрика для HA-кластеров. Рост отставания означает, что реплики получают устаревшие данные (пользователи, читающие с реплик, видят старые данные), и увеличивается риск потери данных при аварийном переключении (если мастер умрёт, данные, на которые отстала реплика, исчезнут навсегда).
4.  **Блокировки (Locks):** База данных — это система, в которой одна транзакция блокирует строку при обновлении, и остальные ждут. Большое количество и длительное удержание блокировок, особенно на табличном уровне, — прямой путь к деградации производительности. Если график количества блокировок резко пошёл вверх, это значит, что какое-то приложение "завесило" таблицу, и для пользователей все висит.
5.  **Состояние резервных копий:** Необходимо отслеживать возраст последней успешной резервной копии. Сбой в процессе бэкапирования часто остается незамеченным до тех пор, пока не становится слишком поздно. Если процесс отправки WAL-логов в хранилище сломался, а никто за этим не следит, то при падении базы восстанавливаться будет нечего. Поэтому важно ставить алерты на возраст последнего успешного архивирования.

## 3. Практический сценарий: Архитектура современного стека

Типичный стек для Full-Stack Observability выглядит следующим образом:

1.  **Приложение:** Инструментируется с помощью **OpenTelemetry SDK**. При выполнении запросов к БД автоматически добавляется SQL-комментарий **`sqlcommenter`** с `trace_id`.
2.  **PostgreSQL:**
    *   Принимает запрос с комментарием. `trace_id` попадает в логи.
    *   Расширение **`pg_tracing`** (если установлено) "читает" `traceparent` из комментария, создает детализированные дочерние спаны для стадий выполнения SQL и отправляет их в коллектор.
    *   `postgres_exporter` собирает метрики из системных представлений (`pg_stat_*`).
3.  **[Grafana Alloy](../../Grafana/grafana_alloy_overview.md) (Агент-коллектор):**
    *   Принимает трейсы от приложения и `pg_tracing`.
    *   Скрейпит метрики с `postgres_exporter`.
    *   Читает лог-файлы, парсит их и извлекает `trace_id` из комментариев.
    *   Отправляет все три типа данных в бэкенды Grafana Stack.
4.  **Grafana Stack (Бэкенд):**
    *   **[Tempo](../../Tempo/tempo_overview.md):** Хранит трейсы.
    *   **[Loki](../../Loki/loki_overview.md):** Хранит логи.
    *   **[Mimir](../../Mimir/mimir_overview.md) или Prometheus:** Хранит метрики.
5.  **Grafana (Визуализация):** Предоставляет единый интерфейс, где можно увидеть метрики, найти аномалию, перейти к трейсам, увидеть медленный спан с SQL-запросом и тут же посмотреть все логи, связанные с этим трейсом.

## 4. Продвинутые детали: Инструменты и расширения

### Инструменты для сбора метрик и логов

- **`pg_stat_statements`** / **`pg_stat_monitor`:** Предоставляют агрегированные метрики по запросам (время выполнения, количество вызовов). `pg_stat_monitor` является более продвинутой версией, собирающей больше статистики и планы запросов.
- **`auto_explain`:** Автоматически логирует планы выполнения медленных запросов.

> Подробнее об их использовании: [Оптимизация производительности PostgreSQL](./performance_tuning.md#мониторинг-и-диагностика).

### `sqlcommenter`
Это не расширение, а **конвенция и набор библиотек** для добавления метаданных в SQL-комментарии.
*   **Принцип:** `SELECT * FROM users;` -> `SELECT * FROM users /*application='backend',controller='users',traceparent='...'*/;`
*   **Польза:**
    1.  Позволяет фильтровать `slow query log` в контексте конкретного сервиса или эндпоинта.
    2.  `traceparent` используется `pg_tracing` для создания сквозной трассировки.
*   **Реализация:** Существуют библиотеки для популярных ORM и драйверов (SQLAlchemy, Psycopg, GORM и др.), которые делают это автоматически.
    *   См. [Примеры для OpenTelemetry](../../OpenTelemetry/opentelemetry_overview.md#практический-пример-инструментация-запросов-к-postgresql).

### `pg_tracing` (экспериментальный)

*   **Функционал:**
    *   Создает спаны для различных фаз выполнения запроса (parsing, planning, execution).
    *   Читает `traceparent` из `sqlcommenter` и связывает свои спаны с родительской трассой.
    *   Напрямую экспортирует спаны по протоколу OTLP в коллектор, что намного эффективнее парсинга логов.
*   **Статус:** Считается экспериментальным, но активно развивается. Может требовать сборки PostgreSQL из исходного кода.
