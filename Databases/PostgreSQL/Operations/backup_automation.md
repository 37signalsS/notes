# Автоматизация резервного копирования PostgreSQL

## Определения

**Автоматизация бэкапов** — системный процесс создания, сжатия, шифрования, транспортировки и верификации резервных копий без участия оператора. В PostgreSQL автоматизация реализуется на двух уровнях:

- **Логический уровень:** Генерация SQL-дампов или структурированных архивов (`pg_dump`). Подходит для малых БД (< 100 ГБ), выборочного восстановления и миграций между версиями.
- **Физический уровень:** Прямое копирование файлов данных и архивация журналов транзакций (WAL) с помощью специализированных инструментов (`pgBackRest`, `WAL-G`, `Barman`). Поддерживает инкрементальные копии и восстановление на момент времени (PITR).

**Жизненный цикл бэкапа (Automation Lifecycle):**
1. **Триггер:** Запуск по расписанию (Cron, Systemd Timer) или событию.
2. **Выполнение:** Создание консистентной копии.
3. **Обработка:** Сжатие и опциональное шифрование.
4. **Транспортировка:** Отправка в удаленное хранилище (S3, Off-site).
5. **Верификация:** Проверка целостности и пробное восстановление.
6. **Ротация (Retention):** Удаление устаревших копий согласно политике хранения.
7. **Оповещение:** Отправка статуса выполнения в систему мониторинга.

## Предпосылки

Для корректной работы автоматизации необходимо подготовить окружение:

1.  **Выделенная роль:** Рекомендуется использовать роль с минимально необходимыми правами.
    - Для `pg_dump`: `pg_read_all_data` (PG 14+).
    - Для физических бэкапов: `pg_monitor` и права на чтение файлов данных в ОС.
    - См. подробнее: **[Управление ролями и правами доступа (RBAC)](./role_management.md)**.
2.  **Аутентификация:** Использование файла `~/.pgpass` для исключения передачи пароля в командной строке.
    ```text
    # формат: hostname:port:database:username:password
    db.example.com:5432:*:backup_user:super_secret_password
    ```
    *Права на файл должны быть `0600`.*
3.  **Хранилище:** Выделенное место на диске, NFS-монтирование или доступ к S3-совместимому объектному хранилищу.
4.  **Сетевой доступ:** Разрешение подключений в `pg_hba.conf` для пользователя бэкапа.

## Основные концепции

### Выбор стратегии автоматизации

| Инструмент | Уровень | Хранилище | Особенности |
| :--- | :--- | :--- | :--- |
| **Shell + Cron** | Логический | Локальный диск / NFS | Простота, подходит для небольших изолированных инстансов. |
| **pgBackRest** | Физический | S3, Azure, GCS, Local | **Золотой стандарт**. Параллелизм, инкрементальные/дифференциальные бэкапы, дельта-восстановление. |
| **WAL-G** | Физический | S3-совместимые | Высокая скорость, оптимизация под облачные хранилища, интеграция с Kubernetes. |
| **Barman** | Физический | Диск / S3 | Централизованный менеджер для управления множеством серверов БД. |

### Архитектура автоматизации

1. **Планировщик (Scheduler):** `Cron` или `Systemd Timers` на стороне сервера БД или отдельного хоста управления.
2. **Исполнитель (Runner):** Агент или скрипт, вызывающий утилиты копирования.
3. **Хранилище (Storage):** Разделение на "горячее" (локальное для быстрого отката) и "холодное" (удаленное для DR).
4. **Мониторинг:** Внешний сервис, проверяющий свежесть бэкапа (Dead Man's Snitch).

## Практические сценарии

### Сценарий 1: Логический бэкап с шифрованием и ротацией

Подходит для небольших баз, где важна простота восстановления одной таблицы.

**Скрипт `/usr/local/bin/pg_backup_logical.sh`:**
```bash
#!/bin/bash
set -e

# Конфигурация
DB_NAME="production_db"
BACKUP_DIR="/mnt/backups/postgres/logical"
KEEP_DAYS=14
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="${BACKUP_DIR}/${DB_NAME}_${TIMESTAMP}.dump.gpg"

# Создание директории, если её нет
mkdir -p "$BACKUP_DIR"

# Выполнение дампа -> Сжатие -> Шифрование (GPG)
pg_dump -Fc "$DB_NAME" | \
gpg --encrypt --recipient "backup-key@example.com" -o "$BACKUP_FILE"

# Удаление старых бэкапов
find "$BACKUP_DIR" -type f -name "*.gpg" -mtime +"$KEEP_DAYS" -delete

echo "Backup completed: $BACKUP_FILE"
# → результат: файл production_db_20260817_150000.dump.gpg создан и зашифрован
```

### Сценарий 2: Физическая автоматизация через pgBackRest

Рекомендуется для Production-сред любого масштаба.

**Конфигурация `/etc/pgbackrest/pgbackrest.conf`:**
```ini
[global]
repo1-path=/var/lib/pgbackrest
repo1-retention-full=2          # Хранить 2 полных бэкапа
repo1-bundle=y                 # Группировка малых файлов
process-max=4                  # Параллелизм (4 ядра)
log-level-console=info

[main]
pg1-path=/var/lib/postgresql/16/main
```

**Автоматизация через Systemd Timer (`/etc/systemd/system/pgbackrest-backup.timer`):**
```ini
[Unit]
Description=Daily pgBackRest Full Backup

[Timer]
OnCalendar=daily
Persistent=true

[Install]
WantedBy=timers.target
```

**Команда для выполнения инкрементального бэкапа:**
```bash
# pgBackRest сам выберет тип (full/incr/diff) на основе расписания и наличия полной копии
pgbackrest backup --stanza=main --type=incr
```

### Сценарий 3: Облачная архивация WAL через WAL-G

Обеспечивает минимальный RPO за счет непрерывной отправки журналов транзакций в S3.

**Настройка `postgresql.conf`:**
```conf
archive_mode = on
archive_command = 'wal-g wal-push %p'
archive_timeout = 60
```

**Автоматизация полного бэкапа (Cron):**
```bash
# Выполнять полную копию каждое воскресенье в 02:00
0 2 * * 0 root wal-g backup-push /var/lib/postgresql/16/main
```

**Верификация бэкапов в S3:**
```bash
wal-g backup-list
# → результат: список доступных копий с датами и именами
```

### Сценарий 4: Централизованное управление через Barman

Используется, если нужно управлять десятками серверов с одного узла.

**Конфигурация сервера в Barman (`/etc/barman.d/db-server.conf`):**
```ini
[db-server]
description = "Main Production DB"
conninfo = host=10.0.0.5 user=barman dbname=postgres
backup_method = postgres
archiver = on
retention_policy = RECOVERY WINDOW OF 4 WEEKS
```

**Команда запуска бэкапа:**
```bash
barman backup db-server
```

## Валидация и мониторинг

### Верификация целостности (pg_verifybackup)

Начиная с PostgreSQL 13, можно проверить физический бэкап на наличие повреждений без его полного восстановления.

```bash
# Проверка манифеста и контрольных сумм файлов
pg_verifybackup /var/lib/pgbackrest/backup/main/latest
```

### Автоматическое тестовое восстановление

Лучшая практика — автоматический разворот последнего бэкапа на изолированном инстансе (Stage/Test) раз в неделю.
- **Скрипт:** Автоматизирует создание VM/контейнера, восстановление через `pgbackrest restore` и запуск простого `SELECT 1`.
- **Результат:** Гарантия того, что бэкап не просто "лежит на диске", но и работоспособен.

### Мониторинг бэкапов

Необходимо отслеживать следующие метрики через Prometheus или Zabbix:
1.  **Time since last backup:** Время с момента последней успешной копии.
2.  **Backup size trend:** Резкое уменьшение размера бэкапа может сигнализировать об удалении данных.
3.  **WAL archiving status:** Очередь непереданных WAL-файлов (каталог `pg_wal/archive_status`).
4.  **Exit code:** Код завершения скриптов автоматизации.

См. подробнее: **[Наблюдаемость PostgreSQL](./observability.md)**.

## Поиск и устранение неисправностей

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **pg_dump: Access Denied** | Недостаточно прав у роли. | Выдайте `pg_read_all_data` или проверьте `pg_hba.conf`. |
| **Backup fails: No space left** | Не настроена ротация (retention). | Уменьшите глубину хранения или увеличьте хранилище. |
| **Archive command failed** | Проблемы с сетью до S3 или неверные ключи. | Проверьте `wal-g` логи и доступность эндпоинта. |
| **Exclusive lock timeout** | Бэкап конфликтует с DDL (например, `TRUNCATE`). | Запускайте бэкап в часы минимальной нагрузки; используйте `pgBackRest` (он менее чувствителен к блокировкам). |

## Дополнительная информация

### Рекомендации (Best Practices)

- **Правило 3-2-1:** 3 копии данных, в 2 разных форматах, 1 копия — off-site (в другом регионе/облаке).
- **Immutable Backups:** Использование S3 Object Lock для защиты бэкапов от удаления вредоносным ПО (Ransomware).
- **Шифрование:** Всегда шифруйте бэкапы перед отправкой в публичные облака.
