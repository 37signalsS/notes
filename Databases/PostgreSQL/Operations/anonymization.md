# Анонимизация и маскирование PII-данных в PostgreSQL

Практическое руководство по защите персональных данных (Personally Identifiable Information — PII) с использованием специализированных расширений и встроенных механизмов PostgreSQL. Общие концепции защиты описаны в руководстве **[Безопасность бэкапов](../../Concepts/backup_security.md)**.

## Определения

**Анонимизация (Anonymization)** — необратимый процесс изменения данных, при котором идентификация личности становится невозможной. Анонимизированные данные не подпадают под действие GDPR.

**Псевдонимизация (Pseudonymization)** — замена идентификаторов на искусственные значения (псевдонимы). Процесс обратим при наличии дополнительной информации (таблицы соответствия).

**Динамическое маскирование (Dynamic Masking)** — скрытие данных «на лету» в момент выполнения запроса в зависимости от роли пользователя. Исходные данные на диске остаются неизменными.

**Статическая анонимизация (Static Anonymization)** — перезапись реальных данных в базе или дампе фиктивными значениями. Обычно применяется при подготовке Staging/Dev сред из Production бэкапов.

---

## Основной инструмент: `postgresql-anonymizer`

`postgresql-anonymizer` (также известный как `pg_anon`) — наиболее зрелое расширение для декларативного маскирования в PostgreSQL.

### 1. Установка и активация
Расширение должно быть загружено в оперативную память сервера.

```bash
# Добавьте в postgresql.conf
shared_preload_libraries = 'anon'

# Выполните в базе данных
CREATE EXTENSION IF NOT EXISTS anon CASCADE;
SELECT anon.init();
```

### 2. Принцип декларативного маскирования
Вместо изменения запросов, вы описываете правила маскирования прямо в схеме БД с помощью комментариев (Security Labels).

```sql
-- Маскирование email: оставляем домен, скрываем имя
SECURITY LABEL FOR anon ON COLUMN users.email
IS 'MASKED WITH FUNCTION anon.partial(email,2,''*****'',2)';

-- Маскирование телефона: замена на случайный номер
SECURITY LABEL FOR anon ON COLUMN users.phone
IS 'MASKED WITH FUNCTION anon.random_phone()';

-- Маскирование имени: замена на случайное имя из встроенного словаря
SECURITY LABEL FOR anon ON COLUMN users.first_name
IS 'MASKED WITH FUNCTION anon.fake_first_name()';
```

## Практические сценарии

### Сценарий 1: Динамическое маскирование (Dynamic Masking)
Идеально для предоставления доступа аналитикам или службе поддержки к Production-базе без риска утечки PII.

1. **Активация для конкретной БД:**
   ```sql
   SELECT anon.start_dynamic_masking();
   ```
2. **Создание роли с ограниченным доступом:**
   ```sql
   CREATE ROLE analyst LOGIN PASSWORD 'password';
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO analyst;
   
   -- Разрешаем роли видеть маскированные данные
   SECURITY LABEL FOR anon ON ROLE analyst IS 'MASKED';
   ```
3. **Результат:** При выполнении `SELECT * FROM users` роль `analyst` увидит `*****@gmail.com` вместо реальных адресов, в то время как суперпользователь будет видеть оригинальные данные.

### Сценарий 2: Анонимный дамп (Anonymous Dump)
Создание бэкапа для разработчиков, в котором PII уже заменены на фиктивные данные.

```bash
# Использование утилиты pg_dump с фильтрацией через расширение
pg_dump -h localhost -U postgres my_db \
  --schema-only > schema.sql

pg_dump_anon -h localhost -U postgres my_db > anonymous_data.sql
```
*Примечание: `pg_dump_anon` гарантирует, что PII никогда не покинут оперативную память сервера в открытом виде.*

### Сценарий 3: Статическое маскирование "на месте"
Применяется на Dev-сервере после восстановления свежего бэкапа из Production.

```sql
-- Применяет все описанные SECURITY LABEL правила к данным на диске
SELECT anon.anonymize_database();
```
**Внимание:** Это необратимая операция. Никогда не запускайте её в Production-среде.

## Доступные функции маскирования

| Тип данных | Функция | Результат |
| :--- | :--- | :--- |
| **Email** | `anon.partial(e,2,'**',2)` | `jo**oe@domain.com` |
| **Числа** | `anon.random_int_between(10,100)` | Случайное число в диапазоне |
| **Даты** | `anon.noise(dob, '10 years')` | Случайное смещение даты на +/- 10 лет |
| **Текст** | `anon.fake_last_name()` | "Ivanov" -> "Smith" (из словаря) |
| **IBAN/Card** | `anon.partial_card(num)` | `4242 **** **** 4242` |
| **Хеширование** | `anon.hash(id, 'salt')` | Детерминированный псевдоним |

---

## Рекомендации (Best Practices)

1. **Принцип минимизации:** Маскируйте всё, что не требуется для разработки. Лучше замаскировать лишнее, чем оставить PII.
2. **Детерминизм:** Если для тестов важно сохранять связи между таблицами (например, один и тот же `user_id` в разных таблицах), используйте функции на основе хеширования с солью (`anon.hash`).
3. **Производительность:** Динамическое маскирование добавляет накладные расходы на выполнение запросов. Для тяжелой аналитики предпочтительнее использовать статические анонимизированные реплики.
4. **Безопасность расширения:** Ограничивайте права на выполнение функций `anon.*` только администраторам безопасности.

## Диагностика

**Проверка активных правил маскирования:**
```sql
SELECT * FROM anon.pg_masking_rules;
```

**Отключение маскирования для отладки (только Superuser):**
```sql
SELECT anon.stop_dynamic_masking();
```
