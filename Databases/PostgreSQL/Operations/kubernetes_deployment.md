# PostgreSQL в Kubernetes с помощью оператора CloudNativePG

## 1. Определения

* **[Kubernetes Operator](../../../Kubernetes/Concepts/kubernetes_operators.md):** "Виртуальный администратор" внутри кластера. Это контроллер, который расширяет API Kubernetes для автоматизации управления жизненным циклом сложных stateful-приложений, таких как PostgreSQL.
* **[Custom Resource Definition (CRD)](../../../Kubernetes/Concepts/kubernetes_operators.md#custom-resource-definitions-crd):** Механизм для создания собственных типов ресурсов в Kubernetes. Оператор определяет CRD (например, `kind: Cluster`), чтобы пользователи могли декларативно описывать желаемое состояние приложения.
* **[GitOps](../../../../GitOps/GitOps_overview.md)**: Подход к управлению инфраструктурой и приложениями. Вся конфигурация (в виде YAML-манифестов) хранится в Git, а автоматизированные агенты (например, [ArgoCD](../../../../GitOps/ArgoCD.md) + оператор БД) приводят состояние кластера в соответствие с репозиторием.

## 2. Основные концепции

### Stateful vs Stateless в Kubernetes и роль операторов

Базы данных по своей природе являются **stateful** (состояний) приложениями. Это означает, что они хранят постоянное состояние (данные), которое должно сохраняться даже при перезапуске или перемещении приложения. В Kubernetes для stateful-приложений стандартный примитив **`Deployment` непригоден**, так как он не гарантирует порядка запуска, уникальности сетевых идентификаторов и сохранения данных.

Для развертывания stateful-приложений, включая базы данных, в Kubernetes используется **`StatefulSet`**. Он обеспечивает:

* Стабильные, уникальные сетевые идентификаторы.
* Упорядоченное развертывание и масштабирование.
* Сохранение данных через `PersistentVolumeClaim`.

Однако `StatefulSet` сам по себе "тупой". Он не умеет выполнять задачи, специфичные для базы данных, такие как:

* Настройка репликации и управление ею.
* Автоматический failover при сбое мастера.
* Создание и восстановление резервных копий.
* Обновление версии базы данных без простоя.

Эти задачи автоматизирует **[Kubernetes Operator](../../../Kubernetes/Concepts/kubernetes_operators.md)**. Оператор — это специализированный контроллер, который расширяет API Kubernetes и инкапсулирует операционные знания администратора базы данных. Он работает в цикле сверки (reconciliation loop): постоянно сравнивает желаемое состояние (описанное в CRD) с текущим и выполняет необходимые действия для устранения расхождений.

Важные аспекты, которые оператор решает для баз данных в Kubernetes:

* **Эфемерность подов:** Поды в Kubernetes являются смертными (ephemeral). Оператор гарантирует, что даже при переезде пода на другую ноду данные не будут утеряны, используя `PersistentVolume` и механизмы восстановления.
* **Производительность:** Хотя в контейнере сложнее добиться прямого доступа к памяти и тонкого тюнинга ядра ОС, операторы помогают настроить ресурсы, а `PersistentVolume` обеспечивают необходимый I/O.
* **OOM Killer:** Оператор настраивает параметры контейнеров таким образом, чтобы минимизировать риск нежелательного завершения процесса базы данных со стороны OOM Killer.
* **On-premise vs Managed Service:** В случае on-premise решения и использования своего оборудования операторы являются лучшим выбором для управления базами данных в Kubernetes. Если же ваш кластер Kubernetes развернут в облаке, часто предпочтительнее использовать управляемые сервисы баз данных (Managed Database Service) от облачного провайдера, чтобы снять с себя нагрузку по администрированию.

### Зачем нужен оператор?

При ручном развертывании PostgreSQL в Kubernetes администратору необходимо самостоятельно управлять `StatefulSet`, `PVC`, `Service`, настраивать репликацию, обрабатывать сбои, организовывать бэкапы. Оператор автоматизирует все эти задачи.

### Когда выбирать Kubernetes для баз данных (а когда нет)

Решение о размещении базы данных в Kubernetes или на традиционных виртуальных машинах (ВМ) зависит от профиля нагрузки и экспертизы команды.

#### Сценарии, где выигрывает Kubernetes

1. **"Фабрика" баз данных:** Если у вас сотни микросервисов, и каждому нужна своя небольшая изолированная база данных. С помощью оператора можно создавать и удалять экземпляры БД за секунды, управляя ими как единым целым. Администрировать сотни ВМ было бы намного сложнее и дороже.
2. **Динамические окружения:** Для создания временных баз данных под каждую ветку разработки, для прогона тестов в CI/CD или для демонстрации функционала. Kubernetes позволяет делать это быстро и с минимальными затратами.
3. **Унификация и стандартизация:** Если вся ваша инфраструктура уже построена на Kubernetes, размещение в нем баз данных позволяет использовать единые подходы к мониторингу, логированию, безопасности и управлению конфигурациями (GitOps).

#### Сценарии, где лучше выбрать виртуальные машины

1. **Очень большие и высоконагруженные базы данных:** "Слоны" размером в несколько терабайт с высокими требованиями к дисковому вводу-выводу (IOPS) могут быть сложны в управлении в Kubernetes. Перемещение пода с такой базой на другую ноду — медленный и рискованный процесс.
2. **Предсказуемость производительности:** На ВМ проще гарантировать эксклюзивный доступ к ресурсам (CPU, I/O) и избежать проблемы "шумных соседей". Тонкий тюнинг ядра ОС также проще выполнить на выделенной ВМ.
3. **Экспертиза команды:** Если ваша команда имеет глубокую экспертизу в автоматизации ВМ (например, с помощью Ansible), но недостаточно опыта в Kubernetes, миграция баз данных в контейнеры может принести больше проблем, чем пользы.

**Гибридный подход** часто является оптимальным решением: критически важные, большие "ядра" данных размещаются на надежных ВМ, а многочисленные вспомогательные и тестовые базы — в Kubernetes.

## 3. Практические сценарии с CloudNativePG

CloudNativePG управляет кластером PostgreSQL, автоматически создавая и настраивая все необходимые ресурсы Kubernetes: [StatefulSet](../../../Kubernetes/Base/statefulset.md), `Services`, `Pods`, `PVC`, `Secrets` и др.

### 3.1. Ключевые возможности

* **Автоматический Failover:** При сбое ведущего узла (primary) оператор автоматически выполняет переключение, реализуя на практике [концепции высокой доступности](../Concepts/high_availability.md).
* **Масштабирование:** Изменение количества реплик или размеров дисков выполняется изменением одного поля в YAML-файле кластера.
* **Резервное копирование и PITR:** Встроенная интеграция с `barman` для создания резервных копий в object storage (S3-совместимые хранилища) и восстановления на определенный момент времени (Point-in-Time Recovery). Поддерживаются также бэкапы через снимки томов (`Volume Snapshots`).
* **Мониторинг:** Автоматический экспорт метрик в формате Prometheus.
* **Обновления:** Управляемые обновления версии PostgreSQL с минимальным простоем.
* **Connection Pooling:** Встроенная поддержка `PgBouncer` через отдельный CRD `Pooler`.
* **Декларативное управление:** Пользователи, базы данных и роли могут быть описаны прямо в манифесте кластера.

### 3.2. Практическое использование

#### 3.2.1. Установка оператора

Оператор устанавливается в кластер с помощью одного манифеста, который регистрирует все необходимые CRD и запускает сам контроллер.

```bash
# Установка последней версии (пример для 1.23.0)
kubectl apply -f https://raw.githubusercontent.com/cloudnative-pg/cloudnative-pg/release-1.23/releases/cnpg-1.23.0.yaml
```

После установки в кластере появится пространство имен `cnpg-system` с работающим контроллером.

#### 3.2.2. Создание кластера

Кластер описывается с помощью ресурса `Cluster`.

**Пример `cluster-example.yaml`:**

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: cluster-example
spec:
  instances: 3
  
  storage:
    size: "1Gi"
    storageClass: "standard-rwx" # Укажите ваш storage class

  # Включение мониторинга для Prometheus Operator
  monitoring:
    enablePodMonitor: true

  # Настройки начальной инициализации
  bootstrap:
    initdb:
      database: app
      owner: app

  # Стратегия обновления primary-узла
  # 'unsupervised' доверяет Kubernetes, 'switchover' делает это управляемо
  primaryUpdateStrategy: unsupervised 
```

После применения этого манифеста (`kubectl apply -f cluster-example.yaml`) оператор создаст:

* `StatefulSet` с 3 подами PostgreSQL.
* `PersistentVolumeClaim` для каждого пода.
* Несколько `Service` для доступа к кластеру.

#### 3.2.3. Сервисы (Services) для доступа

Оператор автоматически создает три сервиса для разных сценариев доступа:

* `<cluster-name>-rw` (read-write): Всегда указывает на **единственный ведущий узел (primary)**. Используется для операций записи.
* `<cluster-name>-ro` (read-only): Указывает на **все реплики (standby)**. Используется для масштабирования нагрузки на чтение.
* `<cluster-name>-r` (read): Указывает на **все узлы кластера** (и primary, и standby).

#### 3.2.4. Плагин `kubectl cnpg`

Для удобного управления кластером существует плагин `kubectl cnpg`.

* **Просмотр статуса:**

    ```bash
    kubectl cnpg status cluster-example
    ```

    Команда показывает текущий primary, список реплик, их задержку и общее состояние кластера.

* **Подключение через `psql`:**

    ```bash
    # Подключиться к primary
    kubectl cnpg psql cluster-example

    # Подключиться к одной из реплик
    kubectl cnpg psql cluster-example --replica
    ```

* **Другие полезные команды:**
  * `kubectl cnpg hibernate cluster-example`: "Усыпляет" кластер (останавливает поды, сохраняя диски).
  * `kubectl cnpg fence <pod-name>`: Изолирует узел от кластера для обслуживания.
  * `kubectl cnpg promote <pod-name>`: Вручную повышает реплику до primary.
  * `kubectl cnpg destroy <cluster-name>`: Корректно удаляет кластер и все связанные ресурсы.

#### 3.2.5. Автоматический Failover в действии

Если вручную удалить под, на котором работает primary:

```bash
kubectl delete pod cluster-example-1
```

Оператор обнаружит это, повысит одну из оставшихся реплик (например, `cluster-example-2`) до нового primary, а Kubernetes автоматически пересоздаст удаленный под, который затем подключится к кластеру уже в качестве реплики. Сервис `<cluster-name>-rw` будет автоматически перенаправлен на новый primary, обеспечивая непрерывность операций записи.

### 3.3. Резервное копирование и восстановление

CloudNativePG использует `barman` для управления бэкапами, автоматизируя многие [стратегии резервного копирования](../Concepts/backup_and_recovery.md), включая создание базовых копий и восстановление на момент времени (Point-in-Time Recovery). Необходимо настроить `backup` секцию в спецификации кластера.

#### 3.3.1. Резервное копирование в Object Storage (S3)

**Пример конфигурации:**

```yaml
spec:
  # ...
  backup:
    barmanObjectStore:
      destinationPath: "s3://your-bucket/path-to-backups/"
      endpointURL: "https://s3.your-provider.com"
      s3Credentials:
        accessKeyId:
          name: my-s3-credentials
          key: ACCESS_KEY_ID
        secretAccessKey:
          name: my-s3-credentials
          key: ACCESS_SECRET_KEY
```

После этого можно создавать бэкапы вручную или настроить автоматическое резервное копирование по расписанию с помощью ресурса `ScheduledBackup`.

* **Создание бэкапа вручную:**

    ```bash
    kubectl cnpg backup cluster-example --method barmanObjectStore
    ```

#### 3.3.2. Резервное копирование через Volume Snapshots

Если ваш Storage Class поддерживает CSI Volume Snapshots, это более быстрый способ создания бэкапов.

**Пример конфигурации:**

```yaml
spec:
  # ...
  backup:
    volumeSnapshot:
      className: <your-volume-snapshot-class>
```

* **Создание бэкапа вручную:**

    ```bash
    kubectl cnpg backup cluster-example --method volumeSnapshot
    ```

#### 3.3.3. Восстановление (Recovery)

Восстановление происходит при создании нового кластера, где в секции `bootstrap` указывается источник.

**Пример восстановления из бэкапа:**

```yaml
apiVersion: postgresql.cnpg.io/v1
kind: Cluster
metadata:
  name: cluster-restored
spec:
  instances: 3
  # ... (storage, etc) ...

  bootstrap:
    recovery:
      source: "cluster-example" # Имя кластера, с которого был снят бэкап
```

CloudNativePG найдет последний доступный бэкап от `cluster-example` и использует его для инициализации нового кластера. Для Point-in-Time Recovery (PITR) можно дополнительно указать `recovery_target`.

## 4. Дополнительная информация

### 4.1. Мониторинг

CloudNativePG "из коробки" интегрируется с Prometheus. Если в манифесте указать `monitoring: { enablePodMonitor: true }`, оператор создаст ресурс `PodMonitor`, который будет автоматически обнаружен Prometheus Operator'ом для сбора сотен метрик о состоянии PostgreSQL.
