# Обновление PostgreSQL между мажорными версиями (pg_upgrade)

**Актуально для:** PostgreSQL 14–18 (PG 19 beta — изменения помечены «PG 19»); pg_upgrade поддерживает апгрейд с 9.2+; режимы `--clone`/`--swap`/`--copy-file-range` — PG 17+, `--no-statistics`/`--set-char-signedness` — PG 18+

## Определения

*   **pg_upgrade** (ранее `pg_migrator`) — утилита обновления кластера PostgreSQL до более новой мажорной версии без dump/restore: создаёт новые системные каталоги и переиспользует файлы пользовательских данных (внутренний формат данных редко меняется между мажорными версиями). Не нужна для минорных обновлений (12.7 → 12.8).
*   **In-place upgrade** — апгрейд на том же хосте с переиспользованием `PGDATA` (в отличие от логической репликации на новый кластер — см. [Миграцию без простоя](./zero_downtime_migration.md)).
*   **Режим переноса данных** — способ переноса файлов данных: `--copy` (по умолчанию), `--link` (hard links), `--clone` (reflinks, PG 17+), `--copy-file-range` (PG 17+), `--swap` (PG 17+, самый быстрый при множестве отношений).
*   **`pg_upgrade --check`** — режим только проверок совместимости кластеров; данные не меняет, можно запускать при работающем старом сервере (порты при этом должны различаться); pg_upgrade «очерчивает» ручные правки, необходимые после апгрейда.
*   **`pg_upgrade_output.d`** — каталог с рабочими файлами апгрейда (дампы схем, скрипты пересборки) в каталоге нового кластера; каждый запуск создаёт подкаталог с меткой времени ISO 8601 (`%Y%m%dT%H%M%S`); удаляется автоматически при успехе, сохраняется при сбое для отладки.
*   **Analyze-in-stages** — двухфазная регенерация статистики после апгрейда: сначала минимальная (`vacuumdb --all --analyze-in-stages --missing-stats-only`), затем полная (`vacuumdb --all --analyze-only`).

## Базовые концепции

### Как работает pg_upgrade

1.  Проверяет бинарную совместимость кластеров через `pg_controldata` (разрядность, compile-time настройки, размеры блока и WAL-сегмента, `data_checksums`, максимальные длины и пр.).
2.  Запускает короткоживущие postmaster-процессы старого и нового кластеров на служебном порту (по умолчанию **50432**; при самом апгрейде оба кластера могут использовать один порт, так как не работают одновременно).
3.  Дампит и восстанавливает только системные каталоги (`pg_catalog`), пользовательские файлы данных переиспользует; locale и кодировку старого `template0` копирует в новый.
4.  Генерирует post-upgrade скрипты для объектов, требующих пересборки (например, индексы, чьи правила сортировки изменились).

pg_upgrade требует права на запись в текущий каталог (в нём по умолчанию создаются unix-сокеты postmasters; при слишком длинном пути — `--socketdir`). Внешние модули должны быть бинарно совместимы — это **не проверяется** pg_upgrade.

### Когда применим, а когда нет

| Условие | Применимость |
| :--- | :--- |
| Та же архитектура ОС и разрядность | Обязательно (проверяется `pg_controldata`) |
| Совпадение `data_checksums` на обоих кластерах | Обязательно (иначе — `... does not match`) |
| Совпадение размеров блока, WAL-блока и WAL-сегмента, максимальных длин | Обязательно (`pg_controldata ... are invalid or do not match`) |
| Расширения установлены как `.so` в новом кластере | Обязательно (схемы `CREATE EXTENSION` не дампить — они перенесутся) |
| Меняется внутренний формат хранения | pg_upgrade **неприменим** (сообщество старается этого избегать) |
| Нужен нулевой простой | Не pg_upgrade — [логическая репликация](./zero_downtime_migration.md) |

**Важно:** апгрейд выполняет произвольный код от имени суперпользователей старого кластера — убедитесь, что старые суперпользователи доверенные.

### Выбор режима переноса данных

| Режим | Скорость | Диск | Старый кластер после старта нового | Условия |
| :--- | :--- | :--- | :--- | :--- |
| `--copy` (дефолт) | Медленно | 2× | Цел | — |
| `--link` | Быстро | ~1× | **Небезопасен** (общие файлы) | Оба `PGDATA` на одной файловой системе (tablespace и `pg_wal` — на других) |
| `--clone` (PG 17+) | Быстро | ~1× | Цел | Оба `PGDATA` на одной файловой системе; Btrfs/XFS (создан с поддержкой reflink) на Linux 4.5+, APFS (macOS) |
| `--copy-file-range` (PG 17+) | Средне | ~1× | Цел | Linux, FreeBSD; на некоторых ФС разделяет физические блоки (как `--clone`), на других — оптимизированное копирование |
| `--swap` (PG 17+) | Быстро (много отношений) | ~1× | **Разрушен** после начала переноса | Оба `PGDATA` на одной файловой системе; рекомендуется `--sync-method=fsync` |

`--jobs=N` (начальная точка — число ядер; при `≥2` включается параллельная обработка баз и tablespace).

### Опции и переменные

| Опция | Назначение |
| :--- | :--- |
| `-b/--old-bindir`, `-B/--new-bindir` | Каталоги бинарников старого/нового кластера (`--new-bindir` по умолчанию — каталог самого `pg_upgrade`; запускать всегда из **нового** каталога) |
| `-d/--old-datadir`, `-D/--new-datadir` | Каталоги данных (`PGDATA`) |
| `-c/--check` | Только проверки, данные не меняет |
| `-j/--jobs=N` | Параллелизм (базы и tablespace) |
| `-k/--link`, `--clone`, `--copy-file-range`, `--copy`, `--swap` | Режим переноса данных (таблица выше) |
| `--no-statistics` (PG 18+) | Не переносить статистику оптимизатора |
| `--sync-method=fsync\|syncfs` | Метод сброса на диск: `fsync` (дефолт) или `syncfs` (Linux: целые файловые системы, caveats — см. `recovery_init_sync_method`); без эффекта с `--no-sync` |
| `-N/--no-sync` | Не ждать сброса файлов на диск — быстрее, но crash ОС может повредить каталог; **только для тестов** |
| `-o/--old-options`, `-O/--new-options` | Опции, передаваемые напрямую postgres старого/нового кластера (можно повторять) |
| `-p/--old-port`, `-P/--new-port`, `-U/--username` | Порты кластеров и пользователь установки |
| `-r/--retain` | Сохранять SQL и логи даже при успешном апгрейде |
| `-s/--socketdir=dir` | Каталог для unix-сокетов postmaster (по умолчанию — текущий каталог; должен быть недоступен другим пользователям) |
| `-v/--verbose`, `-V/--version`, `-?/--help` | Подробное логирование, версия, справка |
| `--set-char-signedness=signed\|unsigned` (PG 18+) | Явно задать signedness `char` нового кластера (см. пограничные случаи) |

Переменные окружения: `PGBINOLD`/`PGBINNEW`, `PGDATAOLD`/`PGDATANEW`, `PGPORTOLD`/`PGPORTNEW`, `PGSOCKETDIR`, `PGUSER`.

### Статистика оптимизатора

*   **PG 18:** `pg_upgrade` переносит основную статистику оптимизатора; флаг `--no-statistics` отключает перенос. Не переносятся: `CREATE STATISTICS`, статистика расширений, cumulative statistics.
*   **PG 19 (beta):** в списке непереносимых остались статистика расширений и cumulative statistics — расширенная статистика (`CREATE STATISTICS`) переносится; отдельно в 19 появились `pg_dump --statistics`, `pg_restore_extended_stats()`, `pg_clear_extended_stats()`.
*   **PG 15–17:** статистика **не переносится** — обязательна регенерация после апгрейда.
*   **PG 19 (beta):** `vacuumdb --analyze-only` / `--analyze-in-stages` без целевых БД обрабатывают и партиционированные таблицы (ранее пропускали).

## Практические сценарии

### Сценарий: In-place апгрейд 17 → 18 (bare metal / VM)

#### Шаг 0. Подготовка (до окна обслуживания)

1.  Прочитать release notes всех промежуточных версий — несовместимости устраняются **до** апгрейда.
2.  Сделать бэкап (`pg_basebackup` + WAL-архив) — [стратегия](../Concepts/backup_and_recovery.md).
3.  Установить новые бинарники (PGDG: `dnf install postgresql18-server`, см. [Установку на RHEL](./installation_rhel.md)).
4.  Проверить версии расширений: они должны быть доступны для **обеих** мажорных версий; `pg_upgrade` сообщит о доступных обновлениях и создаст скрипты.
5.  **Потренироваться на клоне** (схема-only копия с тестовыми данными; безопасный приём для link-режима — см. лучшие практики).

#### Шаг 1. Инициализировать новый кластер

```bash
/usr/pgsql-18/bin/initdb -D /var/lib/pgsql/18/data --data-checksums
# → совпадение --data-checksums со старым кластером обязательно
```

Не запускать новый кластер. Скопировать кастомные FTS-файлы (словари, синонимы, thesaurus) из старого кластера.

#### Шаг 2. Проверить совместимость

```bash
sudo -u postgres /usr/pgsql-18/bin/pg_upgrade \
  --old-bindir=/usr/pgsql-17/bin --new-bindir=/usr/pgsql-18/bin \
  --old-datadir=/var/lib/pgsql/17/data --new-datadir=/var/lib/pgsql/18/data \
  --check
# → Performing Consistency Checks
# → *Clusters are compatible*
```

`--check` можно запускать при работающем старом сервере (порты должны различаться). Для link/clone/copy-file-range/swap-режимов добавьте соответствующий флаг к `--check` — включатся режим-специфичные проверки.

#### Шаг 3. Остановить оба сервера

```bash
sudo systemctl stop postgresql-17
sudo systemctl stop postgresql-18
```

Standby-реплики и log-shipping должны быть **запущены** при остановке Primary, чтобы получить все изменения.

#### Шаг 4. Запустить апгрейд

```bash
sudo -u postgres /usr/pgsql-18/bin/pg_upgrade \
  --old-bindir=/usr/pgsql-17/bin --new-bindir=/usr/pgsql-18/bin \
  --old-datadir=/var/lib/pgsql/17/data --new-datadir=/var/lib/pgsql/18/data \
  --clone --jobs=8
# → Performing Upgrade
# → Upgrade Complete
# → Some statistics are not transferred by pg_upgrade.
# → Once you start the new server, consider running these two commands:
# →     /usr/pgsql-18/bin/vacuumdb --all --analyze-in-stages --missing-stats-only
# →     /usr/pgsql-18/bin/vacuumdb --all --analyze-only
# → Running this script will delete the old cluster's data files:
# →     ./delete_old_cluster.sh
```

*   `--clone` — reflink-копирование (быстро, старый кластер остаётся целым); `--link` — hard links (быстро, но старый кластер после старта нового небезопасен).
*   Аутентификация между кластерами: временно `peer` в `pg_hba.conf` или `~/.pgpass`.
*   Во время апгрейда никто не должен обращаться к кластерам.

#### Шаг 5. Стартовать новый кластер и восстановить конфигурацию

```bash
sudo systemctl start postgresql-18
sudo -u postgres psql -c "SELECT version();"
# → PostgreSQL 18.x ...
```

Вернуть оригинальные настройки `pg_hba.conf`, `postgresql.conf` (и включаемых им файлов), `postgresql.auto.conf` — initdb создал чистые конфиги, pg_upgrade их не переносит.

#### Шаг 6. Регенерация статистики

```bash
PGOPTIONS='-c vacuum_cost_delay=0' vacuumdb --all --analyze-in-stages --missing-stats-only --jobs=8
PGOPTIONS='-c vacuum_cost_delay=0' vacuumdb --all --analyze-only --jobs=8
```

Первый проход быстро создаёт минимальную статистику для отношений без неё (позволяет открыть доступ), второй — полную. `PGOPTIONS` обходит `vacuum_cost_delay`, ускоряя генерацию; `--jobs` параллелит по базам.

#### Шаг 7. Post-upgrade скрипты

Если `pg_upgrade` сообщил о необходимости пересборки объектов, он сгенерировал скрипты — выполнить каждый:

```bash
psql --username=postgres --file=script.sql postgres
```

Скрипты можно выполнять в любом порядке и удалять после выполнения. **Осторожно:** таблицы из rebuild-скриптов небезопасно читать до завершения скрипта (неправильные результаты или плохая производительность); таблицы, не упомянутые в скриптах, доступны сразу.

#### Шаг 8. Удалить старый кластер

```bash
# Скрипт delete_old_cluster.sh (сгенерирован pg_upgrade) — после проверки работы нового кластера
./delete_old_cluster.sh
```

Автоудаление невозможно, если в старом `PGDATA` есть пользовательские tablespace (или каталог нового кластера лежит внутри старого) — тогда pg_upgrade сообщает, что старый кластер нужно удалять вручную. Можно также удалить старые каталоги установки (`bin`, `share`).

### Сценарий: Апгрейд standby-реплик через rsync (только с `--link`)

После апгрейда Primary (новые standby-каталоги должны отсутствовать или быть пустыми; бинарники и `.so` расширений установлены; конфиги старых standby сохранены):

```bash
# На Primary, из каталога выше обоих PGDATA, для каждого standby:
rsync --archive --delete --hard-links --size-only --no-inc-recursive \
  /var/lib/pgsql/17/data /var/lib/pgsql/18/data standby.example.com:/var/lib/pgsql
```

*   Перед этим убедитесь, что standby догнали Primary: `pg_controldata` на Primary и standby должен показывать одинаковый «Latest checkpoint location»; `wal_level` на новом Primary не должен быть `minimal`.
*   Бэкап через `pg_backup_start()`/`pg_backup_stop()` не нужен — standby синхронизированы с Primary.
*   Для каждого tablespace — аналогичный rsync его каталога; если `pg_wal` вынесен за пределы `PGDATA` — rsync и его.
*   Проверить план команды можно через `rsync --dry-run`.
*   rsync обязательно запускается на Primary хотя бы для одного standby; далее можно догонять другие standby с уже апгрейжденного (но не стартовавшего) standby.
*   rsync копирует и файлы временных/unlogged-таблиц, которых на standby нет — это нормально.

Затем сконфигурировать репликацию на standby и стартовать. Если Primary старше 17.0 — слоты на Primary не копируются, **все** слоты старого standby нужно пересоздать вручную; для Primary 17+ копируются только логические слоты Primary, остальные слоты старого standby всё равно пересоздаются вручную. Альтернатива без rsync — пересоздать standby через `pg_basebackup` (медленнее, но надёжнее).

### Сценарий: Откат к старому кластеру (reverting)

| Режим апгрейда | Состояние старого кластера | Откат |
| :--- | :--- | :--- |
| `--check` | Не изменён | Перезапустить старый кластер |
| `--copy` / `--clone` / `--copy-file-range` | Не изменён | Перезапустить старый кластер |
| `--link`, апгрейд прерван до начала linking | Не изменён | Перезапустить |
| `--link`, новый кластер **не стартовал** | Цел, кроме `.old`-суффикса на `$PGDATA/global/pg_control` | Убрать суффикс `.old`, перезапустить |
| `--link`, новый кластер **стартовал** | Небезопасен (общие файлы изменены) | Только восстановление из бэкапа |
| `--swap` до отчёта «unsafe to start» | Не изменён | Перезапустить |
| `--swap` после отчёта «unsafe to start» | Разрушен | Только восстановление из бэкапа |

**Вывод для production:** при `--link`/`--swap` откат возможен только до старта нового кластера — поэтому в K8s-операторах (Zalando/CloudNativePG) откат после `pg_upgrade` невозможен и апгрейд сначала тестируют на клоне.

## Устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `old cluster uses data checksums but the new one does not` (и обратно) | Разный `--data-checksums` при initdb; апгрейд во время включения/выключения checksums | Инициализировать оба кластера с `--data-checksums`; дождаться завершения смены checksums |
| `old and new pg_controldata ... are invalid or do not match` | Размеры блока, WAL-блока, WAL-сегмента, max identifier lengths и пр. | `initdb` нового кластера с параметрами, совпадающими со старым |
| `The source cluster contains prepared transactions` | Незавершённые 2PC-транзакции | `COMMIT PREPARED` / `ROLLBACK PREPARED` для всех |
| `All non-template0 databases must allow connections` | `datallowconn = false` у пользовательской БД | Временно разрешить подключение (`template0` наоборот должен с `datallowconn = false`) |
| `database user "..." is not the install user` | pg_upgrade запущен не от владельца `PGDATA` | Запускать от пользователя, владеющего обоими `PGDATA` |
| Ошибка при восстановлении схемы на расширении | `.so` расширения не установлены в новом кластере | Установить пакеты расширений для новой версии (не `CREATE EXTENSION` — схема перенесётся) |
| Апгрейд падает на восстановлении схемы | Проблемный contrib-модуль | Откатиться, удалить модуль из старого кластера, установить после апгрейда (если не хранит пользовательские данные), повторить |
| `encodings that are no longer supported` (PG 19: MULE_INTERNAL) | БД в удалённой кодировке | `pg_dumpall` + restore в UTF8 |
| `gist_inet_ops` / `gist_cidr_ops` (PG 19) | Поломанные opclasses btree_gist | Пересоздать такие индексы на встроенном GiST `inet_ops` **до** апгрейда |
| Имена БД/ролей/tablespace с CR/LF (PG 19) | В 19 такие имена запрещены | Переименовать объекты до апгрейда |
| `non-default tablespace ... in PGDATA` (до PG 19) | Каталоги tablespace внутри старого `PGDATA` | Апгрейд на PG 19 (поддерживается) или вынести tablespace за пределы `PGDATA` |
| `pg_upgrade не поддерживает типы reg*` | Колонки `regcollation`, `regconfig`, `regdictionary`, `regnamespace`, `regoper`, `regoperator`, `regproc`, `regprocedure` | Убрать такие колонки (`regclass`, `regrole`, `regtype` поддерживаются всегда; `regdatabase` — PG 19+) |
| Не создаются сокеты / путь слишком длинный | Unix-сокеты по умолчанию в текущем каталоге | `--socketdir=/tmp` (каталог недоступен другим пользователям) |
| Всё медленнее после апгрейда | Статистика не перенесена/устарела | Сценарий 12 [runbook](./troubleshooting_runbook.md#сценарий-12-после-апгрейда-всё-работает-медленнее) |

## Лучшие практики

1.  **Тест на клоне обязателен** — схема-only копия + dummy-данные + `pg_upgrade` (docs: «For deployment testing, create a schema-only copy of the old cluster, insert dummy data, and upgrade that»).
2.  **Все приготовления — до остановки Primary**: initdb, установка расширений, `--check`, ручные `CHECKPOINT` (ускоряют `pg_ctl stop -m fast`).
3.  **`--clone` вместо `--link`** где поддерживается — старый кластер остаётся целым, откат проще.
4.  **`--jobs`** — параллелизм по числу ядер.
5.  **Расширения с особым порядком обновления** (PostGIS, Citus) — обновлять до/после `pg_upgrade` по инструкции расширения; бинарники расширений должны соответствовать новой мажорной версии.
6.  **После апгрейда — новый basebackup** для standby и проверка эталонных планов запросов.
7.  **Версии бинарников** — запускать `pg_upgrade` из **нового** каталога, не старого.
8.  **Безопасное тестирование link-режима**: rsync-копия старого кластера при работающем сервере → останов → `rsync --checksum` (гранулярность mtime 1 с) → апгрейд копии в `--link`. Файловые снапшоты/COW-копии тоже допустимы, но должны создаваться одновременно или при остановленном сервере.
9.  **Автоматизация**: кластеры с одинаковой схемой требуют одинаковых post-upgrade шагов (скрипты зависят от схемы, а не от данных) — playbook можно подготовить один раз и применять к ферме кластеров.
10. **Windows**: вход с административной учётной записью, каталоги в кавычках.

## Пограничные случаи

*   **`--set-char-signedness` (PG 18)**: с PG 18 кластер хранит свой signedness `char`; при апгрейде с 17 и ниже новый кластер наследует signedness платформы сборки (x86 — `signed`, ARM — `unsigned`). При миграции на другую платформу: апгрейд делать на **исходной** платформе без флага, затем мигрировать данные; если данные уже перенесены — указать signedness исходной платформы и не модифицировать файлы данных до `pg_upgrade`.
*   **Locale**: initdb нового кластера можно выполнять с любым locale — pg_upgrade копирует locale/кодировку старого `template0` в новый; но libc/ICU-locale старого кластера должны быть доступны на новой ОС. При смене версии ICU — `ALTER DATABASE ... REFRESH COLLATION VERSION` после апгрейда.
*   **`--no-sync`**: возвращает управление до сброса файлов на диск — только для тестов, на production не использовать.
*   **`--sync-method=syncfs`** (Linux): синхронизирует целые файловые системы; caveats — см. `recovery_init_sync_method`; с `--swap` используйте `fsync` (дефолт).
*   **Логическая репликация**: апгрейд кластеров с логической репликацией через pg_upgrade — отдельная процедура (не покрыта этой инструкцией; см. [миграцию без простоя](./zero_downtime_migration.md)).
*   **`pg_upgrade_output.d`**: при успехе удаляется автоматически; при сбое — источник дампов и логов для отладки; `--retain` сохраняет SQL и логи даже при успехе.
*   **PG 19 (beta)**: быстрее копируются метаданные large objects; поддерживаются нестандартные tablespace внутри `PGDATA` (ранее — ошибка); `vacuumdb --analyze-only`/`--analyze-in-stages` обрабатывают партиционированные таблицы.
