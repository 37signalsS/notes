# Миграция PostgreSQL через логический бэкап

Метод «холодной» миграции данных, основанный на экспорте структуры и содержимого базы данных в виде SQL-скриптов или архивов. Является стандартом для перехода между мажорными версиями СУБД (например, с 12 на 18) или при смене облачного провайдера. Подходит для баз данных малого и среднего объема, где допустимо временное прекращение записи.

## Определения

*   **Логическая миграция** — перенос данных путем выгрузки объектов БД в промежуточный формат и их последующего импорта. В отличие от физической миграции, позволяет менять мажорную версию СУБД, архитектуру ОС (например, x86 на ARM) и настройки табличных пространств.
*   **Холодная миграция (Cold Migration)** — процесс, требующий остановки записи в базу на исходном сервере для обеспечения консистентности снимка данных.
*   **Ингибирование VACUUM** — эффект, при котором долгая транзакция `pg_dump` препятствует очистке "мертвых" строк. На нагруженных системах это может привести к росту (bloat) объема таблиц на Source-сервере.
*   **Формат каталога (Directory Format, `-F d`)** — наиболее эффективный формат `pg_dump`, позволяющий выполнять экспорт и импорт в несколько параллельных потоков, что значительно сокращает время миграции.
*   **pg_dump / pg_restore** — базовый инструментарий. `pg_dump` работает с одной БД, `pg_dumpall` используется для выгрузки всего кластера или его глобальных объектов.

## Базовые концепции

### Правила совместимости версий (2026)

Для успешной миграции необходимо соблюдать иерархию инструментов:
1.  **Версия клиента (`pg_dump`)** должна быть ≥ мажорной версии исходного сервера.
2.  **Версия целевого сервера** должна быть ≥ мажорной версии исходного сервера.
3.  **Рекомендация:** Используйте утилиты `pg_dump` и `pg_restore` версии 18 (текущий стандарт), так как они наиболее эффективно работают с новыми алгоритмами сжатия и параллельности.

### Выбор формата экспорта

| Формат | Флаг | Параллельность | Сжатие (2026) | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **Plain Text** | `-F p` | Нет | Внешнее (`zstd/gzip`) | Небольшие БД, ручная правка SQL. |
| **Custom** | `-F c` | Только импорт | Встроенное (ZSTD/LZ4) | Стандарт для одной БД. Гибкий выбор объектов. |
| **Directory** | `-F d` | **Экспорт и импорт** | Встроенное (ZSTD) | **Рекомендуется** для больших БД (> 50 ГБ). |

**Технический нюанс:** Флаг параллельности `-j` в `pg_dump` требует обязательного использования формата `Directory`. Начиная с PostgreSQL 17+, поддерживается нативное сжатие **ZSTD** через флаг `--compress=zstd`.

### Этапы миграции

1.  **Подготовка:** Проверка дискового пространства (нужно минимум 1.5x от объема данных для дампа и временных файлов).
2.  **Блокировка записи:** Остановка приложений или перевод БД в режим `read-only` для обеспечения консистентности:
    ```sql
    ALTER DATABASE name SET default_transaction_read_only = on;
    -- Для сброса текущих сессий:
    SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'name' AND pid <> pg_backend_pid();
    ```
3.  **Экспорт глобальных объектов:** Выгрузка ролей и табличных пространств через `pg_dumpall --globals-only` (флаг `-g`).
4.  **Экспорт данных:** Создание дампа базы. Используйте `--blobs` (по умолчанию включено) для переноса Large Objects.
5.  **Импорт:** Развертывание данных на целевом сервере. Рекомендуется увеличить `maintenance_work_mem` до 2-4 ГБ для ускорения создания индексов.
6.  **Пост-миграция:** Сбор статистики (`ANALYZE`), проверка целостности объектов и последовательностей.

## Практические сценарии

### Сценарий 1: Быстрая параллельная миграция (Directory Format)

Наиболее эффективный способ для баз данных среднего размера с использованием сжатия ZSTD (PG 17+).

#### Шаг 1: Экспорт на исходном сервере
```bash
# Используем 4 потока и ZSTD сжатие для скорости
pg_dump -h source_host -U postgres -d my_db -F d -j 4 --compress=zstd:1 -f /path/to/dump_dir
```

#### Шаг 2: Перенос данных
```bash
rsync -avz --progress /path/to/dump_dir/ user@target_host:/tmp/dump_dir/
```

#### Шаг 3: Импорт на целевом сервере
Предварительно создайте базу данных на новом сервере.
```bash
pg_restore -h localhost -U postgres -d my_db -j 8 /tmp/dump_dir
```

### Сценарий 2: Миграция через сетевой поток (Streaming Migration)

Если на исходном сервере недостаточно места для дампа, можно передавать данные напрямую через сетевой канал (pipe).

```bash
# Миграция «на лету» без промежуточного файла
pg_dump -h source_host -U postgres -C -F c my_db | \
  pg_restore -h target_host -U postgres -d postgres -j 4
```
*Примечание: Флаг `-C` (create database) создаст базу на целевом сервере автоматически.*

### Сценарий 3: Миграция в облако (RDS / Cloud SQL)

В облачных средах часто нет прав суперпользователя, поэтому требуются флаги подавления владельцев.

```bash
# Экспорт с подавлением владельцев и прав
pg_dump -h source_host -U postgres -d my_db -F c \
  --no-owner --no-privileges -f my_db.dump

# Импорт под администратором облачной БД
pg_restore -h cloud_host -U cloud_user -d my_db my_db.dump
```

### Сценарий 4: Перенос ролей и прав (Globals)

Логический дамп отдельной БД не содержит пользователей. Их нужно перенести отдельно.

```bash
# Выгрузка только ролей и табличных пространств
pg_dumpall -h source_host -U postgres -g > globals.sql

# Импорт на новом сервере
psql -h target_host -U postgres -f globals.sql
```

## Устранение неполадок (Troubleshooting)

| Ошибка | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `ERROR: role "..." does not exist` | Глобальные объекты не перенесены. | Выполните Сценарий 4 перед импортом. |
| Медленное восстановление индексов | Низкий `maintenance_work_mem`. | `SET maintenance_work_mem = '2GB';` перед импортом. |
| `Permission denied` на Large Objects | Недостаточно прав у пользователя. | Убедитесь, что пользователь имеет права `SELECT` на все таблицы и `--blobs` включен. |
| `UTF-8` ошибки сортировки | Разница в версиях ICU или libc. | Проверьте `LC_COLLATE` на обоих серверах. Может потребоваться `REINDEX`. |

## Пограничные случаи и ограничения

### Крупные объекты (Large Objects / Blobs)
При селективном дампе отдельных таблиц (флаг `-t`) блобы **не выгружаются** по умолчанию. Добавляйте `--blobs` явно.

**Важно:** Механизм Large Objects требует особого администрирования (очистка "сиротских" объектов через `vacuumlo`). Подробности см. в **[Large Objects (LO): Администрирование и очистка](../Concepts/large_objects.md)**.

### Триггеры и внешние ключи
Чтобы избежать ошибок при вставке данных в произвольном порядке, `pg_restore` управляет порядком автоматически. Если используется `psql` для Plain Text, рекомендуется:
```sql
SET session_replication_role = 'replica'; -- Отключает триггеры и FK
-- ... импорт данных ...
SET session_replication_role = 'origin';
```

## Дополнительная информация

### Чек-лист верификации после миграции

После завершения импорта ОБЯЗАТЕЛЬНО выполните следующие действия:
1.  **Сбор статистики:** Выполните `ANALYZE;` или воспользуйтесь утилитой `vacuumdb -j 4 -z -d my_db` для ускорения.
2.  **Заморозка XID:** При переезде на новую мажорную версию выполните `VACUUM FREEZE;` для предотвращения Transaction ID Wraparound.
3.  **Проверка объектов:** Сравните количество объектов.
    ```sql
    SELECT relkind, count(*) FROM pg_class GROUP BY relkind;
    -- r = tables, i = indexes, v = views, S = sequences
    ```
4.  **Валидация индексов:** Убедитесь, что нет `INVALID` индексов.
5.  **Проверка последовательностей:** Убедитесь, что `last_value` соответствует максимальным ID.
6.  **Проверка кодировок:** Убедитесь, что `LC_COLLATE` и `LC_CTYPE` совпадают с исходными.
