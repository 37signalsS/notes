# Миграция PostgreSQL с помощью логического бэкапа (pg_dump/pg_dumpall)

Этот документ описывает "холодный" способ миграции всей СУБД PostgreSQL или отдельных баз данных с одного сервера на другой с использованием утилит `pg_dump`, `pg_dumpall` и `psql`. Этот метод подразумевает временную остановку работы с базой данных (downtime).

## 1. Определения

*   **Логический бэкап (Logical Backup):** Процесс создания копии объектов базы данных (таблиц, схем, пользователей, ролей) в виде набора SQL-команд или архивного файла, который можно восстановить на другом сервере. В отличие от физического бэкапа, он не зависит от архитектуры ОС и версии PostgreSQL (в определенных пределах).
*   **pg_dump:** Утилита для создания логического бэкапа **одной** базы данных PostgreSQL.
*   **pg_dumpall:** Утилита для создания логического бэкапа **всех** баз данных в кластере PostgreSQL, включая глобальные объекты, такие как пользователи (роли) и табличные пространства.
*   **psql:** Интерактивный терминал для работы с PostgreSQL, который также используется для восстановления данных из SQL-дампа.

## 2. Основные концепции

Процесс миграции состоит из трех основных этапов:

1.  **Создание дампа (Dump):** На исходном сервере (Source) создается файл, содержащий SQL-команды для воссоздания структуры и данных.
    *   `pg_dumpall` используется для полного переноса всего кластера, включая всех пользователей и их права. Это предпочтительный вариант для миграции всего сервера.
    *   `pg_dump` используется, если нужно перенести только одну конкретную базу данных.
2.  **Перенос файла дампа:** Файл бэкапа копируется с исходного сервера на целевой (Target).
3.  **Восстановление (Restore):** На целевом сервере с помощью `psql` выполняется файл дампа, что приводит к созданию баз данных, таблиц, пользователей и наполнению их данными.

Этот метод прост и надежен, но требует остановки записи в базу данных на время создания дампа, чтобы обеспечить консистентность данных.

## 3. Практический сценарий: Миграция всего кластера

Этот сценарий описывает перенос всех баз данных, пользователей и прав с одного сервера на другой.

### Шаг 1: Создание полного дампа на исходном сервере (Source)

1.  Подключитесь к серверу и переключитесь на системного пользователя `postgres`.
    ```bash
    sudo -iu postgres
    ```
2.  Создайте полный дамп всего кластера PostgreSQL с помощью `pg_dumpall`. Дамп будет сохранен в домашней директории пользователя `postgres` (`/var/lib/postgresql/`).
    ```bash
    pg_dumpall > all_db_backup.sql
    ```
    *Эта команда создает текстовый файл `all_db_backup.sql`, содержащий все необходимые SQL-инструкции.*

### Шаг 2: Перенос файла дампа на целевой сервер (Target)

1.  Используйте утилиту `scp` или `rsync` для копирования файла дампа с исходного сервера на целевой.
    ```bash
    # Команда выполняется на исходном сервере
    scp /var/lib/postgresql/all_db_backup.sql user@target_server_ip:/path/to/destination/
    ```
    *Замените `user`, `target_server_ip` и `/path/to/destination/` на реальные данные.*

### Шаг 3: Восстановление дампа на целевом сервере (Target)

1.  Убедитесь, что на целевом сервере установлен PostgreSQL. Версия должна быть не ниже, чем на исходном сервере.
2.  Переместите файл дампа в доступное для пользователя `postgres` место, например, `/tmp`.
3.  Подключитесь к серверу и переключитесь на системного пользователя `postgres`.
    ```bash
    sudo -iu postgres
    ```
4.  Восстановите данные из дампа с помощью `psql`. Ключ `-f` указывает на файл, из которого нужно выполнить команды.
    ```bash
    psql -f /path/to/destination/all_db_backup.sql
    ```
    *`psql` последовательно выполнит все команды из файла, воссоздавая пользователей, базы данных, схемы, таблицы и заливая данные.*

### Шаг 4: Проверка

1.  После завершения восстановления проверьте, что все объекты были успешно перенесены.
    ```bash
    # Зайти в psql
    psql
    
    # Показать список баз данных
    \l
    
    # Подключиться к перенесенной базе
    \c my_database
    
    # Показать таблицы
    \dt
    
    # Проверить наличие данных в таблице
    SELECT * FROM my_table LIMIT 10;
    ```
2.  Проверьте, что приложение может подключиться к новой базе данных с учетными данными перенесенных пользователей.

## 4. Дополнительная информация

*   **Версии PostgreSQL:** Миграция с помощью `pg_dump`/`pg_dumpall` обычно безболезненно проходит при обновлении на более новую мажорную версию PostgreSQL (например, с 12 на 14). Обратная миграция (с новой версии на старую) не поддерживается.
*   **Форматы дампа:** `pg_dump` поддерживает альтернативные архивные форматы (ключ `-F c` для custom format), которые являются сжатыми и позволяют выборочно восстанавливать объекты. Для восстановления таких форматов используется утилита `pg_restore`. `pg_dumpall` выводит только текстовый дамп.
*   **Безопасность:** Дамп `pg_dumpall` содержит команды для создания пользователей с их захешированными паролями. Не передавайте файлы дампа по незащищенным каналам.
