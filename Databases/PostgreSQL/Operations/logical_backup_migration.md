# Миграция PostgreSQL через логический бэкап

Метод «холодной» миграции данных, основанный на экспорте структуры и содержимого базы данных в виде SQL-скриптов или архивов. Требует временной остановки записи на исходном сервере для обеспечения консистентности.

## Определения

**Логическая миграция** — процесс переноса данных между серверами путем выгрузки объектов БД в промежуточный формат и их последующего импорта на целевой сервер.

**Исходный сервер (Source)** — сервер, с которого переносятся данные.

**Целевой сервер (Target)** — новый сервер, на который выполняется миграция.

Инструменты `pg_dump`, `pg_dumpall` и `pg_restore` подробно описаны в разделе **[Резервное копирование и восстановление](../Concepts/backup_and_recovery.md)**.

## Основные концепции

### Этапы процесса

1. **Подготовка:** Оптимизация сетевых параметров, настройка доступов и проверка свободного места на Target.
2. **Остановка записи:** Перевод приложения в режим обслуживания (Downtime) для предотвращения расхождения данных.
3. **Экспорт (Dump):** Создание снимка данных на Source.
4. **Перенос:** Копирование файлов на Target через `scp`, `rsync` или S3.
5. **Импорт (Restore):** Развертывание данных на новом сервере.
6. **Верификация:** Проверка целостности данных и актуальности статистики.

### Требования и ограничения

- **Версии СУБД:** Мажорная версия Target должна быть равна или выше версии Source. Обратная миграция (с более новой версии на старую) через логический бэкап официально не поддерживается.
- **Простой (Downtime):** Запись должна быть остановлена на все время экспорта и импорта. Для баз данных объемом более 100 ГБ рекомендуется рассмотреть **[Миграцию без простоя](./zero_downtime_migration.md)**.
- **Ресурсы:** Процесс восстановления (Restore) создает высокую нагрузку на CPU и диск.

## Практические сценарии

### Сценарий 1: Перенос всего кластера (всех баз данных)

Используется, когда необходимо перенести все данные, включая глобальные объекты (роли, табличные пространства).

#### Шаг 1: Экспорт на Source

```bash
# Переключение на пользователя postgres
sudo -iu postgres

# Создание сжатого дампа всего кластера
pg_dumpall | gzip > all_databases.sql.gz
```

#### Шаг 2: Перенос на Target

```bash
scp all_databases.sql.gz user@target-host:/tmp/
```

#### Шаг 3: Импорт на Target

```bash
# Распаковка и импорт через psql
gunzip -c /tmp/all_databases.sql.gz | sudo -u postgres psql -f -
```

### Сценарий 2: Перенос отдельной базы данных (рекомендуемый)

Формат `custom` (`-F c`) позволяет использовать многопоточное восстановление, что значительно ускоряет миграцию.

#### Шаг 1: Экспорт на Source

```bash
pg_dump -U postgres -d my_app_db -F c -Z 9 -f my_app_db.dump
```

#### Шаг 2: Импорт на Target

```bash
# Создание базы данных (если она не создана)
createdb -U postgres my_app_db

# Восстановление в 4 потока
pg_restore -U postgres -d my_app_db -j 4 my_app_db.dump
```

### Шаг 4: Действия после миграции

После завершения импорта необходимо обновить статистику для корректной работы планировщика:

```sql
ANALYZE;
```

Информацию о настройке производительности после миграции см. в **[Performance Tuning](./performance_tuning.md)**.

## Дополнительная информация

### Безопасность

Дампы содержат чувствительные данные и хеши паролей ролей. При передаче через открытые сети обязательно используйте шифрованные каналы (SSH) и удаляйте временные файлы после завершения работ.
