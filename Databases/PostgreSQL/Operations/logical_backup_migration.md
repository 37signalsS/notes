# Миграция PostgreSQL через логический бэкап

Метод «холодной» миграции: экспорт базы в SQL-скрипт или архив `pg_dump` и импорт на целевом сервере через `psql` / `pg_restore`. Применяется для перехода между мажорными версиями СУБД, смены архитектуры ОС (x86 → ARM), изменения расположения табличных пространств и переноса отдельных баз. Требует окна обслуживания: время простоя равно времени выгрузки + переноса + загрузки.

**Актуально для:** PostgreSQL 14–18 (текущий stable — 18, релиз 2025-09-25; zstd/lz4-сжатие дампа — с PG 15, опции `--statistics` — с PG 18)

## Определения

*   **Логическая миграция** — перенос данных через промежуточный логический формат (SQL или архив). В отличие от физической, позволяет менять мажорную версию и архитектуру ОС и не привязана к файловому layout кластера.
*   **Холодная миграция (Cold Migration)** — миграция с остановкой записи на исходном сервере. Важно: сама консистентность снапшота обеспечивается MVCC — `pg_dump` «makes consistent exports even if the database is being used concurrently» и не блокирует ни читателей, ни писателей. Остановка записи нужна не для консистентности снапшота, а чтобы после выгрузки на источнике не осталось изменений, которых нет в целевой базе (расхождение данных).
*   **Ингибирование VACUUM** — долгая транзакция `pg_dump` удерживает snapshot, мешая `VACUUM` очищать мёртвые строки; на нагруженных системах это приводит к росту bloat на источнике. Запускайте дампы в часы минимальной нагрузки.
*   **TOC (Table of Contents)** — машинно-читаемый реестр объектов в архивных форматах; основа для выборочного восстановления (`pg_restore -l` / `-L`).
*   **Synchronized snapshots** — механизм (PG 9.2+ primary, 10+ standby), гарантирующий, что несколько соединений параллельного дампа видят один и тот же снапшот данных.
*   **pg_dump / pg_restore / pg_dumpall** — `pg_dump` выгружает одну базу, `pg_dumpall` — весь кластер или глобальные объекты (роли, табличные пространства), `pg_restore` восстанавливает архивные форматы.

## Базовые концепции

### Когда применять, а когда нет

*   **Применять:** БД малого и среднего объёма (до ~100–500 ГБ); смена мажорной версии; смена архитектуры; изменение layout табличных пространств; перенос одной базы из кластера; восстановление отдельной базы/таблицы.
*   **Не применять:** регулярные бэкапы production — документация (с PG 18) прямо указывает, что `pg_dump` «generally not the right choice for taking regular backups of production databases» — используйте физические бэкапы с архивацией WAL (см. **[Резервное копирование и восстановление](../Concepts/backup_and_recovery.md)**).
*   **Большие БД с ограниченным простоем** — `pg_upgrade` или логическая репликация: см. **[Миграция без простоя](./zero_downtime_migration.md)** (там же — сравнение методов).
*   **PITR** логическим бэкапом не поддерживается — только физические бэкапы + WAL.

### Совместимость версий

1.  **Клиент (`pg_dump`) должен быть ≥ мажорной версии исходного сервера.** `pg_dump` откажется дампить сервер новее своей мажорной версии («refuse to even try, rather than risk making an invalid dump»); серверы до 9.2 включительно поддерживаются.
2.  **Дамп загружается в серверы новее версии `pg_dump`.** Загрузка в сервер *старше* версии `pg_dump` не гарантирована даже для дампа, снятого с этого сервера — может потребоваться ручная правка SQL.
3.  **Для кросс-версий используйте `--quote-all-identifiers`** — предотвращает проблемы из-за разных списков зарезервированных слов в разных мажорных версиях (рекомендация документации).
4.  **Рекомендация:** используйте свежие утилиты (18) — они поддерживают все текущие алгоритмы сжатия и параллелизм, но если дамп должен загрузиться в конкретный старый сервер, сверяйтесь с п. 2.

### Форматы, сжатие и параллелизм

| Формат | Флаг | Параллельный экспорт (`-j`) | Параллельный импорт (`pg_restore -j`) | Сжатие по умолчанию | Применение |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Plain** | `-F p` | Нет | Не применим (`psql`) | Нет (внешнее: `gzip/zstd`) | Миграции, version control, чтение человеком |
| **Custom** | `-F c` | Нет (экспорт однопоточный) | Да | **gzip** умеренного уровня | Стандарт для одной БД; выборочное восстановление |
| **Directory** | `-F d` | **Да** (единственный формат) | Да | **gzip** | Рекомендуется для больших БД (> 50 ГБ) |
| **Tar** | `-F t` | Нет | **Нет** (только custom и directory) | Не поддерживается вообще | Совместимость со старыми инструментами; ручная обработка Unix-средствами |

**Параллелизм:**

*   `-j N` в `pg_dump` возможен **только** с directory-форматом: открывается `N + 1` соединений (лидер + N воркеров) — убедитесь, что `max_connections` это позволяет. Параллельный дамп требует synchronized snapshots; при запросе эксклюзивной блокировки на таблицу третьим клиентом дамп прерывается (воркер детектирует конфликт через `NOWAIT`).
*   `pg_restore -j N` работает **только** с custom и directory форматами, **только** с обычным файлом или каталогом (не pipe/stdout), и **не совместим** с `--single-transaction`. Оптимальный старт — число ядер сервера.
*   **Сжатие (PG 15+):** `--compress=method[:level]`, где `method` ∈ `gzip`, `lz4`, `zstd`, `none`; для plain-формата ненулевой уровень сжимает весь вывод целиком. Zstd/lz4 добавлены в **PG 15** (не 17).

### Что переносится, а что нет

*   **Переносится:** схема, данные (`COPY`), значения последовательностей (`setval` — в отличие от логической репликации, где последовательности не реплицируются), Large Objects (по умолчанию, кроме `-t`/`--schema-only`/`--statistics-only`/`--no-data`), комментарии, политики RLS, расширения.
*   **Не переносится в дампе одной БД:** роли, табличные пространства, глобальные привилегии — только через `pg_dumpall -g` (Сценарий 4).
*   **Статистика оптимизатора** не переносится по умолчанию — после восстановления планировщик работает вслепую до первого `ANALYZE`. С PG 18 доступно `pg_dump --statistics` / `pg_restore --statistics-only` (подробности — **[Статистика после восстановления](../Concepts/planner_internals.md#5-статистика-после-восстановления-и-обновления-кластера)**), но даже с ней рекомендуется `ANALYZE`: `CREATE STATISTICS`, кастомная статистика расширений и кумулятивная статистика в дамп не включаются.
*   **Подписки** сохраняются с `connect = false` — после восстановления их нужно активировать вручную.

## Предварительные требования

1.  **Версии:** `pg_dump` ≥ мажорная версия источника; целевой сервер ≥ версии источника (п. «Совместимость версий»).
2.  **Дисковое пространство:** эвристика — ~1–1.5× от размера БД под дамп и временные файлы; точный размер зависит от сжатия. Для directory-формата каталог должен **не существовать** — `pg_dump` создаёт его сам.
3.  **Права:** для полного дампа — `SELECT` на всех таблицах и `USAGE` на схемах; для `pg_dumpall -g` — как правило, суперпользователь (пароли ролей читаются из `pg_authid`); для выполнения скрипта `pg_dumpall` нужны права на создание ролей и баз. При политиках, запрещающих прямой вход суперпользователя, — флаг `--role=rolename` (`SET ROLE` после подключения).
4.  **Сеть:** маршрутизация между серверами (firewall rules / VPN / peering), SSH-туннель для передачи дампа; `~/.pgpass` для неинтерактивной аутентификации (`pg_dumpall` запрашивает пароль для каждой базы).
5.  **Окно обслуживания:** согласованное время простоя; план отката (источник не изменяется в процессе, поэтому откат = возврат приложения на источник).

## Практические сценарии

### Сценарий 1: Параллельная миграция (Directory Format)

Наиболее эффективный способ для БД среднего и большого размера.

#### Шаг 1: Экспорт на исходном сервере

```bash
# 4 потока, ZSTD уровня 1 (скорость важнее коэффициента); по умолчанию — gzip
pg_dump -h source_host -U postgres -d my_db -F d -j 4 --compress=zstd:1 -f /path/to/dump_dir
# → каталог dump_dir с TOC и файлами данных
```

#### Шаг 2: Перенос данных

```bash
# -a без -z: дамп уже сжат, повторное сжатие на transfer — пустая трата CPU
rsync -a --progress /path/to/dump_dir/ user@target_host:/tmp/dump_dir/
```

#### Шаг 3: Импорт на целевом сервере

```bash
# Целевая БД создаётся заранее из template0 (см. ниже)
createdb -T template0 -h target_host -U postgres my_db
pg_restore -h target_host -U postgres -d my_db -j 8 /tmp/dump_dir
# → данные загружены; предупреждения и ошибки — в stderr
```

### Сценарий 2: Миграция через сетевой поток (без промежуточного файла)

Когда на исходном сервере недостаточно места для дампа. **Ограничения:** параллельный импорт из pipe невозможен (вход должен быть обычным файлом или каталогом), поэтому `-j` здесь не используется; `-C` передаётся `pg_restore`, а не `pg_dump` (для архивных форматов `pg_dump -C` игнорируется).

```bash
# Дамп сжимается на лету и разворачивается на целевом сервере
pg_dump -h source_host -U postgres -F c --compress=zstd:1 my_db | \
  pg_restore -h target_host -U postgres -d postgres -C
# → БД my_db создана на целевом сервере и заполнена (-C: -d postgres используется
#   только для выдачи CREATE DATABASE, данные восстанавливаются в my_db)
```

Если нужен параллельный импорт — сохраните дамп в файл/каталог и восстановите оттуда (Сценарий 1).

### Сценарий 3: Миграция без прав суперпользователя

Для сред, где целевой пользователь не суперпользователь (ограниченные окружения, shared-инстансы, контейнеры). **Флаги `-O`/`-x` для архивных форматов задаются при `pg_restore`, а не при `pg_dump`** — в `pg_dump` они игнорируются для архивов.

```bash
# Экспорт обычным архивом
pg_dump -h source_host -U postgres -d my_db -F c -f my_db.dump

# Импорт: владение и ACL не восстанавливаются, всё создаётся от имени целевого пользователя
pg_restore -h target_host -U app_user -d my_db -O -x my_db.dump
```

Для plain-формата те же флаги задаются при `pg_dump` (`-O -x`), так как там нет `pg_restore`. Альтернатива — `--use-set-session-authorization` (стандартный SQL, но восстановление требует суперпользователя).

### Сценарий 4: Перенос ролей и глобальных объектов

Дамп отдельной БД не содержит пользователей и табличных пространств.

```bash
# Только роли и табличные пространства (пароли включены из pg_authid)
pg_dumpall -h source_host -U postgres -g > globals.sql

# Импорт на новом сервере; "role already exists" для bootstrap-суперпользователя
# — безвредная ошибка, её следует игнорировать
psql -X -h target_host -U postgres -d postgres -f globals.sql
```

*   `--roles-only` / `--tablespaces-only` — выгрузить только роли или только табличные пространства.
*   `--no-role-passwords` — не выгружать пароли (чтение из представления `pg_roles` вместо `pg_authid`; полезно при политиках, ограничивающих доступ к `pg_authid`).
*   Каталоги табличных пространств должны существовать на целевом сервере **до** восстановления, иначе создание баз в нестандартных locations завершится ошибкой.

### Сценарий 5: Другие табличные пространства и чистая целевая БД

```bash
# Опустить команды выбора табличных пространств (всё создаётся в default tablespace)
pg_restore -h target_host -U postgres -d my_db --no-tablespaces my_db.dump

# Создать по-настоящему пустую БД: template1 может содержать локальные дополнения,
# которые дадут ошибки дублирования объектов
CREATE DATABASE my_db WITH TEMPLATE template0;
```

### Тюнинг восстановления

Перед импортом (одна сессия `psql` или `SET` в скрипте):

```sql
SET maintenance_work_mem = '4GB';      -- ускоряет CREATE INDEX
SET synchronous_commit = off;          -- безопасно при миграции (однократная загрузка)
```

В `postgresql.conf` целевого сервера на время восстановления: `max_wal_size = '10GB'`, `checkpoint_timeout = '30min'` — меньше чекпоинтов при массовой загрузке. Верните значения после миграции. Альтернатива `-1` (всё одной транзакцией) — `--transaction-size=N` (несколько тысяч объектов): почти та же скорость при ограниченном потреблении таблицы блокировок.

## Валидация

После импорта обязательно:

1.  **Код возврата:** запускайте `pg_restore -e` (exit on error; по умолчанию ошибки накапливаются и только считаются в конце) и проверяйте `$?`.
2.  **Сбор статистики:** `ANALYZE my_db;` или `vacuumdb -j 4 -z -d my_db` (`-z` включает freeze). Без статистики планировщик работает вслепую (см. **[planner_internals.md](../Concepts/planner_internals.md)**).
3.  **Счётчики объектов** (сравните источник и цель):
    ```sql
    SELECT relkind, count(*) FROM pg_class
    WHERE relnamespace NOT IN ('pg_catalog'::regnamespace, 'information_schema'::regnamespace)
    GROUP BY relkind;
    -- → r = tables, i = indexes, v = views, S = sequences, p = partitioned tables
    ```
4.  **Индексы:** нет `INVALID` индексов (`SELECT indexrelid::regclass, indisvalid FROM pg_index WHERE NOT indisvalid;`).
5.  **Последовательности:** значения перенесены в дампе (`setval`), но проверьте:
    ```sql
    SELECT last_value FROM my_table_id_seq;   -- не продвигает последовательность
    -- → должно быть >= max(id) из my_table
    ```
6.  **Локаль:** `SELECT datcollate, datctype, datlocprovider FROM pg_database WHERE datname = 'my_db';` — должна совпадать с источником, иначе порядок сортировки текстовых индексов может различаться. PG 15+: проверка версии collation через `pg_database_collation_actual_version()` и `ALTER DATABASE ... REFRESH`.
7.  **Структурная целостность** (опционально, большие БД): `amcheck` — см. **[Восстановление после повреждений](../Concepts/corruption_recovery.md)**.

## Устранение неполадок (Troubleshooting)

| Ошибка | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `ERROR: role "..." does not exist` | Глобальные объекты не перенесены | Выполните Сценарий 4 перед импортом |
| Медленное восстановление индексов | Низкий `maintenance_work_mem` | `SET maintenance_work_mem = '4GB';` перед импортом |
| `permission denied` на Large Objects | Недостаточно прав у пользователя дампа | Пользователь дампа должен иметь `SELECT` на все таблицы; LO включены по умолчанию (кроме `-t`) |
| Ошибки сортировки / дубликаты в уникальных индексах | Разные версии libc/ICU или `LC_COLLATE` | Сверьте `datcollate`/`datctype`; PG 15+ — `pg_database_collation_actual_version()` + `ALTER DATABASE ... REFRESH`; может потребоваться `REINDEX` |
| `pg_dump: error: server version: ...; pg_dump version: ...` | Сервер новее `pg_dump` | Обновите клиентские утилиты до версии ≥ мажорной версии сервера |
| Дамп «сломан» после restore в более старый сервер | Дамп версии N не гарантированно загружается в сервер < N | Используйте `pg_dump` версии, совместимой с самой старой целью, и `--quote-all-identifiers` |
| Параллельный дамп прерывается | Третий клиент запросил эксклюзивную блокировку на таблицу | Повторите в окно без DDL; `--lock-wait-timeout` ограничит ожидание блокировок |
| `row security` ошибка при дампе | Таблица с RLS, пользователь не может обходить политики | По умолчанию `pg_dump` ставит `row_security = off` и это ошибка при недостатке прав; либо дайте `bypassrls`, либо `--enable-row-security` (требует `--inserts`) |
| Дублирование объектов при restore | Целевая БД создана из `template1` с локальными дополнениями | Создавайте БД из `template0` |
| Ошибки при restore `pg_dumpall` | «role already exists» для bootstrap-суперпользователя | Безвредно — игнорируйте; `--clean --if-exists` минимизирует шум |

## Пограничные случаи и ограничения

### Крупные объекты (Large Objects / Blobs)

При селективном дампе (`-t`, `-n`, `--schema-only`, `--statistics-only`, `--no-data`) блобы **не выгружаются** — добавляйте `--blobs` явно. `pg_restore` не умеет восстанавливать LO выборочно: либо все, либо none (через `-L`/`-t`). Подробности — **[Large Objects (LO): Администрирование и очистка](../Concepts/large_objects.md)** (включая очистку «сиротских» объектов через `vacuumlo`).

### Триггеры и внешние ключи

`pg_restore` восстанавливает объекты в порядке зависимостей, а `pg_dump` формирует ограничения отдельно от данных — поэтому в архивных форматах отключать триггеры обычно не нужно. Для plain-формата через `psql` или при restore data-only:

```sql
SET session_replication_role = 'replica'; -- отключает триггеры и FK; требует суперпользователя
-- ... импорт данных ...
SET session_replication_role = 'origin';
```

Опция `--disable-triggers` (только для data-only восстановления) требует суперпользователя (`-S`). **Внимание:** при прерывании restore с `--disable-triggers` системные каталоги могут остаться в некорректном состоянии.

### Расширения

Конфигурационные таблицы расширений сохраняются только если расширение вызвало `pg_extension_config_dump()` — иначе `pg_dump` не выгрузит их содержимое. См. **[Полезные расширения](../Concepts/extensions_utility.md)**. При restore в БД с уже загруженными данными расширения (например, PostGIS) — `pg_restore --no-data-for-failed-tables`.

### Read-Only источник и standby

`pg_dump` можно запускать на standby-сервере (synchronized snapshots поддерживаются с PG 10 на standby) — мастер не нагружается. Данные UNLOGGED-таблиц и последовательностей при дампе со standby **исключаются всегда** (и по флагу `--no-unlogged-table-data`).

### Партиционированные таблицы

Если ключ партиционирования — `text` с разными collation на источнике и цели, строки могут разложиться по другим партициям: `--load-via-partition-root` заставляет `COPY` адресовать строки корню иерархии (партиция определяется при загрузке).

### Согласованность снапшота

Для копии под отчёты, где дамп должен быть согласован с сериальным выполнением транзакций (батч-обработка), — `pg_dump --serializable-deferrable`: дамп дождётся точки без аномалий (старт может задержаться на неопределённое время). `--snapshot=<name>` — синхронизация дампа со слотом логической репликации или параллельной сессией.

### Переносимость формата данных

`--inserts` / `--column-inserts` / `--rows-per-insert` вместо `COPY` — медленнее, но устойчивы к частичным ошибкам и пригодны для загрузки в не-PostgreSQL СУБД (`--column-inserts` безопасен при смене порядка столбцов).

### Безопасность дампа

Восстановление дампа — это выполнение произвольного кода от имени суперпользователей источника. Для дампов из недоверенных источников инспектируйте содержимое до restore: `pg_restore -l my_db.dump` (или `pg_restore --file - my_db.dump > dump.sql` для не-plain форматов), затем `psql -X -f dump.sql` с `-X` (без `~/.psqlrc`).

## Лучшие практики

*   **Окно и нагрузка:** дампы — в часы минимальной нагрузки (ингибирование VACUUM); читайте stderr — предупреждения (права, исключённые объекты) печатаются туда.
*   **Строгость:** `pg_restore -e` для немедленного стопа на ошибке; `-1` (all-or-nothing) для критичных загрузок, где это практично; `--strict-names` в `pg_dump` ловит опечатки в шаблонах `-t`/`-n`.
*   **Разделение этапов:** `--section=pre-data|data|post-data` позволяет применить схему заранее, а данные — в окне обслуживания; то же для restore.
*   **План отката:** источник в процессе не модифицируется (запись остановлена), поэтому при неудаче на цели — возврат приложения на источник и повторная попытка.
*   **Cleanup после миграции:** удалите файлы дампа с обеих сторон; отключите read-only (`ALTER DATABASE name SET default_transaction_read_only = off;` — учтите, что `ALTER DATABASE ... SET` не влияет на уже установленные сессии: существующие соединения нужно завершить через `pg_terminate_backend(pid)` или дождаться их закрытия); верните `maintenance_work_mem`/`max_wal_size` к рабочим значениям.
*   **Тестирование:** перед продакшн-миграцией отработайте полный цикл на копии и замерьте время каждого этапа — время простоя линейно зависит от размера БД и скорости диска/сети.
