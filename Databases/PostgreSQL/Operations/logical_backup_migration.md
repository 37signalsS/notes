# Миграция PostgreSQL через логический бэкап

Метод «холодной» миграции данных, основанный на экспорте структуры и содержимого базы данных в виде SQL-скриптов или архивов. Подходит для баз данных малого и среднего объема, где допустимо временное прекращение записи.

## Определения

* **Логическая миграция** — перенос данных путем выгрузки объектов БД в промежуточный формат и их последующего импорта. В отличие от физической миграции, позволяет менять мажорную версию СУБД, архитектуру ОС и настройки табличных пространств.
* **Холодная миграция (Cold Migration)** — процесс, требующий остановки записи в базу на исходном сервере для обеспечения консистентности снимка данных.
* **Формат каталога (Directory Format, `-F d`)** — наиболее эффективный формат `pg_dump`, позволяющий выполнять экспорт и импорт в несколько параллельных потоков, что значительно сокращает время миграции.

## Базовые концепции

### Правила совместимости версий

Для успешной миграции необходимо соблюдать иерархию версий инструментов:
1. **Версия клиента (`pg_dump`)** должна быть ≥ мажорной версии исходного сервера.
2. **Версия целевого сервера** должна быть ≥ мажорной версии исходного сервера.
3. Рекомендуется использовать утилиты `pg_dump` и `pg_restore` той же версии, что и целевой сервер.

### Выбор формата экспорта

| Формат | Флаг | Параллельность | Сжатие | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **Plain Text** | `-F p` | Нет | Внешнее (`gzip`) | Небольшие БД, ручная правка SQL. |
| **Custom** | `-F c` | Только импорт | Встроенное | Стандарт для одной БД. Гибкий выбор объектов при импорте. |
| **Directory** | `-F d` | **Экспорт и импорт** | Встроенное | **Рекомендуется** для больших БД (> 50 ГБ). Поддерживает `-j`. |

**Технический нюанс:** Флаг параллельности `-j` в `pg_dump` требует обязательного использования формата `Directory`. В `pg_restore` параллельный импорт доступен для форматов `Custom` и `Directory`.

### Этапы миграции

1. **Подготовка:** Проверка дискового пространства (нужно минимум 1.5x от объема данных для дампа и временных файлов).
2. **Блокировка записи:** Остановка приложений или перевод БД в режим `read-only` (`ALTER DATABASE name SET default_transaction_read_only = on;`).
3. **Экспорт глобальных объектов:** Выгрузка ролей и табличных пространств через `pg_dumpall --globals-only`.
4. **Экспорт данных:** Создание дампа баз данных. Используйте `--blobs` (по умолчанию включено) для переноса Large Objects.
5. **Импорт:** Развертывание данных на целевом сервере.
6. **Пост-миграция:** Сбор статистики (`ANALYZE`), проверка индексов и последовательностей.

## Практические сценарии

### Сценарий 1: Быстрая параллельная миграция (Directory Format)

Наиболее эффективный способ для баз данных среднего размера.

#### Шаг 1: Экспорт на исходном сервере
Использование `-j` позволяет задействовать несколько ядер CPU для чтения таблиц.
```bash
pg_dump -h source_host -U postgres -d my_db -F d -j 4 -f /path/to/dump_dir
```

#### Шаг 2: Перенос данных
```bash
rsync -avz /path/to/dump_dir/ user@target_host:/tmp/dump_dir/
```

#### Шаг 3: Импорт на целевом сервере
Предварительно создайте базу данных на новом сервере.
```bash
pg_restore -h localhost -U postgres -d my_db -j 8 /tmp/dump_dir
```

### Сценарий 2: Миграция через сетевой поток (Streaming Migration)

Если на исходном сервере недостаточно места для дампа, можно передавать данные напрямую через сетевой канал (pipe).

```bash
# Миграция «на лету» без промежуточного файла
pg_dump -h source_host -U postgres -C -F c my_db | \
  pg_restore -h target_host -U postgres -d postgres -j 4
```
*Примечание: Флаг `-C` (create database) создаст базу на целевом сервере автоматически.*

### Сценарий 3: Миграция в облако (RDS / Cloud SQL)

В облачных средах часто нет прав суперпользователя, поэтому требуются дополнительные флаги.

```bash
# Экспорт с подавлением владельцев и прав
pg_dump -h source_host -U postgres -d my_db -F c \
  --no-owner --no-privileges -f my_db.dump

# Импорт
pg_restore -h cloud_host -U cloud_user -d my_db my_db.dump
```

### Сценарий 4: Перенос ролей и прав (Globals)

Логический дамп отдельной БД не содержит пользователей. Их нужно перенести отдельно.

```bash
# Выгрузка только ролей и табличных пространств
pg_dumpall -h source_host -U postgres -g > globals.sql

# Импорт на новом сервере
psql -h target_host -U postgres -f globals.sql
```

## Дополнительная информация

### Чек-лист верификации после миграции

После завершения импорта ОБЯЗАТЕЛЬНО выполните следующие действия:
1. **Сбор статистики:** Выполните `ANALYZE;` или воспользуйтесь утилитой `vacuumdb -j 4 -z -d my_db` для ускорения.
2. **Заморозка XID:** Если миграция выполнялась на новую мажорную версию, рекомендуется выполнить `VACUUM FREEZE;` для предотвращения Transaction ID Wraparound в будущем.
3. **Проверка объектов:** Сравните количество таблиц, индексов и триггеров.
   ```sql
   SELECT relkind, count(*) FROM pg_class GROUP BY relkind;
   -- r = tables, i = indexes, v = views
   ```
4. **Проверка последовательностей:** Убедитесь, что `last_value` соответствует максимальным ID. При необходимости используйте скрипты для массового `setval`.
5. **Проверка кодировок:** Убедитесь, что `LC_COLLATE` и `LC_CTYPE` совпадают с исходными.
