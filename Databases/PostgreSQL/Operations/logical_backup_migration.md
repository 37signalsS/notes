# Миграция PostgreSQL с помощью логического бэкапа

Метод "холодной" миграции PostgreSQL через логический бэкап с использованием `pg_dump`/`pg_dumpall`. Требует остановки записи в БД на время миграции.

## Определения

**Логический бэкап** — SQL-дамп объектов БД (таблиц, схем, данных), который можно восстановить на другом сервере. Не зависит от архитектуры и версии PostgreSQL.

**`pg_dumpall`** — инструмент для дампа всего кластера, включая глобальные объекты (роли, табличные пространства).

**`pg_dump`** — инструмент для дампа одной базы данных.

**`psql`** — клиент PostgreSQL для восстановления данных из SQL-дампа.

## Основные концепции

### Этапы миграции

1. **Создание дампа (Dump):** Экспорт структуры и данных в SQL-файл на исходном сервере (Source).
2. **Перенос файла:** Копирование дампа на целевой сервер (Target) через `scp`/`rsync`.
3. **Восстановление (Restore):** Выполнение SQL-файла через `psql` на целевом сервере.

### Требования и ограничения

- **Downtime:** Запись в БД должна быть остановлена на время создания дампа для обеспечения консистентности.
- **Версии PostgreSQL:** Целевая версия должна быть не ниже исходной. Обратная миграция не поддерживается.
- **Время простоя:** Зависит от размера БД и скорости диска/сети. Для БД >100 ГБ рекомендуется [миграция без простоя](./zero_downtime_migration.md).

### Выбор инструмента

| Инструмент | Сценарий | Формат | Восстановление |
| :--- | :--- | :--- | :--- |
| `pg_dumpall` | Миграция всего кластера | Текстовый SQL | `psql -f file.sql` |
| `pg_dump -F c` | Миграция одной БД | Сжатый бинарный | `pg_restore -j N` |

Подробнее об инструментах и их параметрах — **[Резервное копирование и восстановление](../Concepts/backup_and_recovery.md#logical-backup-and-restore)**.

## Практические сценарии

### Миграция всего кластера

#### Шаг 1: Создание дампа на Source

```bash
# Переключение на пользователя postgres
sudo -iu postgres

# Создание полного дампа кластера
pg_dumpall > all_db_backup.sql
```

> **Примечание:** Для сжатия дампа используйте `gzip`: `pg_dumpall | gzip > all_db_backup.sql.gz`

#### Шаг 2: Перенос файла на Target

```bash
# Копирование на целевой сервер
scp all_db_backup.sql user@target_server_ip:/path/to/destination/
```

#### Шаг 3: Восстановление на Target

```bash
# Проверка версии PostgreSQL (должна быть >= исходной)
postgres --version

# Восстановление из дампа
sudo -iu postgres
psql -f /path/to/destination/all_db_backup.sql
```

#### Шаг 4: Проверка

```bash
# Подключение к psql
sudo -iu postgres psql

# Проверка списка БД
\l

# Проверка таблиц в конкретной БД
\c my_database
\dt
```

### Миграция отдельной базы данных

Для миграции одной БД используйте `pg_dump` с форматом `custom` для ускорения восстановления:

```bash
# Создание дампа на Source
pg_dump -U postgres -d mydb -F c -Z 9 -f mydb.dump

# Восстановление на Target (параллельное, -j 4)
pg_restore -U postgres -d mydb -j 4 mydb.dump
```

## Дополнительная информация

**Безопасность:** Дамп содержит хеши паролей пользователей. Используйте защищённые каналы передачи (SCP, rsync over SSH).

**Альтернативы:** Для миграции без простоя используйте [логическую репликацию](./zero_downtime_migration.md).
