# Миграция PostgreSQL с помощью логического бэкапа (pg_dump/pg_dumpall)

Этот документ описывает **"холодный"** способ миграции PostgreSQL, который подразумевает временную остановку работы с базой данных (downtime).

## Определения

* **Логический бэкап:** Копия объектов базы данных (таблиц, схем, ролей) в виде набора SQL-команд, который можно восстановить на другом сервере. Не зависит от архитектуры и версии СУБД (в определенных пределах).
* **`pg_dumpall`:** Основной инструмент для данной миграции, создающий дамп **всего** кластера, включая глобальные объекты (роли, табличные пространства).
* **`pg_dump`:** Инструмент для миграции **одной** конкретной базы данных.
* **`psql`:** Стандартный клиент PostgreSQL, используемый для восстановления данных из SQL-дампа.

## Основные концепции

Процесс миграции состоит из трех этапов:

1. **Создание дампа (Dump):** На исходном сервере (Source) создается SQL-файл, содержащий команды для воссоздания структуры и данных.
2. **Перенос файла дампа:** Файл бэкапа копируется с исходного сервера на целевой (Target).
3. **Восстановление (Restore):** На целевом сервере с помощью `psql` выполняется файл дампа для развертывания данных.

Этот метод прост и надежен, но требует остановки записи в базу данных на время создания дампа для обеспечения консистентности.

## Практический сценарий: Миграция всего кластера

### Шаг 1: Создание дампа на исходном сервере (Source)

1. Подключитесь к серверу и переключитесь на системного пользователя `postgres`.

    ```bash
    sudo -iu postgres
    ```

2. Создайте полный дамп всего кластера с помощью `pg_dumpall`.

    ```bash
    pg_dumpall > all_db_backup.sql
    ```

    *Эта команда создает текстовый файл `all_db_backup.sql` со всеми необходимыми SQL-инструкциями.*

### Шаг 2: Перенос файла дампа на целевой сервер (Target)

Используйте `scp` или `rsync` для копирования файла дампа.

```bash
# Команда выполняется на исходном сервере
scp /var/lib/postgresql/all_db_backup.sql user@target_server_ip:/path/to/destination/
```

### Шаг 3: Восстановление дампа на целевом сервере (Target)

1. Убедитесь, что на целевом сервере установлен PostgreSQL версии не ниже, чем на исходном.
2. От имени пользователя `postgres` выполните восстановление из файла.

    ```bash
    sudo -iu postgres
    psql -f /path/to/destination/all_db_backup.sql
    ```

    *`psql` последовательно выполнит все команды из файла, воссоздавая пользователей, базы данных и их содержимое.*

### Шаг 4: Проверка

1. После завершения убедитесь, что все объекты были успешно перенесены.

    ```bash
    # Зайти в psql
    sudo -iu postgres psql
    
    # Показать список баз данных
    \l
    
    # Подключиться к перенесенной базе и проверить таблицы
    \c my_database
    \dt
    ```

2. Проверьте, что приложение может подключиться к новой базе данных с учетными данными перенесенных пользователей.

## Дополнительная информация

* **Детальное описание инструментов:** Более подробно об инструментах `pg_dump`, `pg_dumpall` и их параметрах см. **[Резервное копирование и восстановление](../Concepts/backup_and_recovery.md)**.
* **Альтернативный метод:** Если требуется миграция без простоя, используйте подход, описанный в документе **[Миграция PostgreSQL без простоя (Zero-Downtime)](./zero_downtime_migration.md)**.
* **Версии PostgreSQL:** Данный метод хорошо подходит для обновления на более новую мажорную версию (например, с 12 на 14). Обратная миграция (с новой версии на старую) не поддерживается.
* **Форматы дампа:** `pg_dump` поддерживает сжатые форматы (ключ `-F c`), которые восстанавливаются с помощью `pg_restore`. `pg_dumpall` выводит только текстовый дамп.
* **Безопасность:** Дамп `pg_dumpall` содержит хеши паролей пользователей. Не передавайте файлы дампа по незащищенным каналам.
