# Миграция PostgreSQL без простоя (Zero-Downtime)

## 1. Определения

**Миграция без простоя (Zero-Downtime Migration)** — это процесс переноса работающей (production) базы данных на новый сервер или в облако без остановки обслуживания, либо с минимально возможным окном простоя, незаметным для большинства пользователей.

## 2. Основные концепции

Ключевой технологией для такой миграции в PostgreSQL является **[логическая репликация](../Concepts/replication.md)**.

Процесс основан на том, чтобы развернуть новую базу данных, сделать полную копию данных со старой, а затем "догнать" все изменения, произошедшие во время копирования, с помощью потоковой передачи изменений. Переключение на новую базу происходит в самом конце и занимает минимальное время.

## 3. Практические сценарии: Пошаговая стратегия

### Шаг 1: Подготовка

1.  **Развернуть новый сервер (Target):** Установите и настройте новый экземпляр PostgreSQL, который станет заменой старому. Убедитесь, что версии совместимы, а конфигурация (`postgresql.conf`) оптимизирована под новую среду.
2.  **Настроить старый сервер (Source):** На текущем, работающем сервере необходимо включить логическую репликацию.
    *   В `postgresql.conf` установите `wal_level = logical`.
    *   **Примените настройку перезагрузкой сервера.** Это единственное действие, требующее кратковременного планового простоя, и его лучше провести заранее, в окно обслуживания.
3.  **Создать пользователя для репликации:** На старом сервере создайте роль с атрибутом `REPLICATION`.

### Шаг 2: Начальная загрузка данных

Пока приложение продолжает работать со старой базой данных, необходимо сделать ее полный снимок и загрузить его на новый сервер.

1.  **Создайте логический дамп:** Используйте [`pg_dump`](../Concepts/backup_and_recovery.md#pg_dump-дамп-одной-базы-данных) для создания дампа схемы и данных.
    ```bash
    # Сначала дамп только схемы
    pg_dump -h <source_host> -U <user> -d <db_name> --schema-only > schema.sql
    
    # Затем дамп только данных
    pg_dump -h <source_host> -U <user> -d <db_name> --data-only > data.sql
    ```
    *Разделение на схему и данные дает больше контроля над процессом.*

2.  **Зафиксируйте позицию в WAL:** В момент создания дампа необходимо зафиксировать его позицию в журнале транзакций (LSN - Log Sequence Number). `pg_dump` с опцией `--snapshot` делает это в рамках одной транзакции. Имя снапшота понадобится для старта репликации ровно с этого момента.
    ```bash
    # Создание дампа внутри транзакции с экпортом снапшота
    pg_dump --snapshot=<snapshot_name> ...
    ```

3.  **Восстановите дамп на новом сервере:**
    ```bash
    psql -h <target_host> -U <user> -d <db_name> -f schema.sql
    psql -h <target_host> -U <user> -d <db_name> -f data.sql
    ```

### Шаг 3: Настройка логической репликации

Теперь нужно настроить поток изменений, которые произошли на старом сервере *после* того, как был сделан дамп.

1.  **Создать публикацию (Publication) на старом сервере:** Публикация определяет, изменения каких таблиц будут реплицироваться.
    ```sql
    -- На старом сервере (Source)
    CREATE PUBLICATION migration_pub FOR ALL TABLES;
    ```
    *Для миграции обычно реплицируют все таблицы, но можно указать и конкретный список.*

2.  **Создать подписку (Subscription) на новом сервере:** Подписка подключается к публикации и начинает получать изменения.
    ```sql
    -- На новом сервере (Target)
    CREATE SUBSCRIPTION migration_sub 
    CONNECTION 'host=<source_host> user=<repl_user> password=<pass> dbname=<db_name>' 
    PUBLICATION migration_pub
    WITH (copy_data = false);
    ```
    *   `copy_data = false` — **критически важно!** Мы уже скопировали данные вручную. Эта опция говорит подписчику не делать начальную копию, а просто начать применять поступающие изменения.
    *   При создании подписки необходимо указать, что она должна стартовать не с текущего момента, а с LSN, сохраненного на Шаге 2.

### Шаг 4: Синхронизация и мониторинг

Новый сервер начнет получать и применять изменения из WAL старого сервера. Этот процесс называется "catch-up".

*   **Мониторинг задержки репликации (Replication Lag):** Необходимо постоянно отслеживать, насколько новый сервер отстает от старого.
    ```sql
    -- На старом сервере
    SELECT sent_lsn FROM pg_stat_replication WHERE application_name = 'migration_sub';
    
    -- На новом сервере
    SELECT received_lsn, latest_end_lsn FROM pg_stat_subscription;
    ```
    Ваша цель — дождаться, когда задержка станет минимальной (в идеале, близкой к нулю).

### Шаг 5: Переключение (Switchover)

Это самый ответственный и единственный этап, который затрагивает работу приложения. Его нужно проводить максимально быстро.

1.  **Кратковременная остановка записей:** Переведите приложение в режим "только чтение" или полностью остановите трафик, который генерирует запись (`INSERT`, `UPDATE`, `DELETE`) в старую базу данных. Это обеспечивает консистентность данных. Чтение может продолжаться.
2.  **Финальная синхронизация:** Дождитесь, пока последние изменения будут полностью реплицированы на новый сервер (задержка репликации станет равна нулю).
3.  **Перенаправление трафика:** Измените конфигурацию вашего приложения так, чтобы оно теперь указывало на **новый** сервер базы данных.
4.  **Возобновление работы:** Включите полный трафик на приложение. Теперь все новые запросы на запись и чтение будут идти в новую базу данных.
5.  **Проверка:** Убедитесь, что приложение корректно работает с новой базой данных.

### Шаг 6: Завершение и очистка

После того как вы убедились, что новая система работает стабильно:
1.  **Удалите подписку** на новом сервере.
2.  **Удалите публикацию и слот репликации** на старом сервере.
3.  Через некоторое время старый сервер можно вывести из эксплуатации.
