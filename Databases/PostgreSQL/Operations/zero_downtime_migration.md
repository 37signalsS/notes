# Миграция PostgreSQL без простоя (Zero-Downtime)

## Определения

* **Миграция без простоя (Zero-Downtime Migration)** — процесс переноса базы данных с минимизацией времени недоступности. Простой ограничивается только временем переключения (Cutover) трафика в приложении, что обычно занимает от нескольких секунд до минуты.
* **Логическая репликация (Logical Replication)** — механизм передачи изменений на уровне отдельных строк, основанный на декодировании WAL. Позволяет передавать данные между разными мажорными версиями PostgreSQL (например, с 12 на 17) и разными аппаратными платформами.
* **Публикация (Publication)** — объект на исходном сервере (Source), определяющий набор таблиц и последовательностей для репликации.
* **Подписка (Subscription)** — объект на целевом сервере (Target), определяющий соединение с публикацией и способ получения данных.
* **REPLICA IDENTITY** — параметр таблицы, определяющий, какая информация будет записываться в WAL при UPDATE/DELETE. По умолчанию это первичный ключ (Primary Key).

## Базовые концепции

### Стратегия миграции

Процесс строится на модели «издатель — подписчик» и состоит из трех фаз:
1. **Начальная синхронизация (Snapshot):** копирование текущего состояния данных.
2. **Догоняющая репликация (Catch-up):** применение накопленных изменений за время копирования.
3. **Переключение (Cutover):** остановка записи на Source и финальный перенос остатка данных.

### Чек-лист подготовки (Mandatory)

Перед началом миграции **обязательно** проверьте следующие пункты:
1. **Первичные ключи:** Каждая таблица для репликации UPDATE/DELETE должна иметь Primary Key. Если его нет, используйте `ALTER TABLE name REPLICA IDENTITY FULL` (создает дополнительную нагрузку на CPU/IO).
2. **Триггеры:** По умолчанию триггеры не срабатывают на Target. Если они нужны (например, для аудита), включите их через `ALTER TABLE name ENABLE REPLICA TRIGGER name`.
3. **Типы данных:** Логическая репликация не поддерживает специфические типы (например, `lo` — large objects). Большие поля `bytea`/`text` могут вызвать значительные задержки.
4. **Место на диске:** На Source должен быть запас места для WAL, так как в случае сбоя Target или медленной сети WAL-логи будут накапливаться бесконечно до удаления слота репликации.

### Ключевые возможности современных версий

* **PostgreSQL 16:** поддержка параллельного применения изменений (`streaming = 'parallel'`), что значительно ускоряет миграцию высоконагруженных таблиц. Добавлена возможность репликации со Standby-серверов.
* **PostgreSQL 17:** нативная поддержка репликации последовательностей (Sequences). Ранее последовательности требовали ручной синхронизации при переключении.
* **Обработка конфликтов (PG 15+):** параметр `on_error` позволяет настраивать поведение подписки при возникновении ошибок (например, пропуск конфликтующих строк).

## Практические сценарии

### Сценарий: Миграция БД на новую мажорную версию

#### Шаг 1: Подготовка серверов

1. **Настройка Source (`postgresql.conf`):**
   ```ini
   wal_level = logical
   max_replication_slots = 10
   max_wal_senders = 10
   ```
   *Требуется перезапуск.*

2. **Создание пользователя (PG 15+):**
   Рекомендуется использовать роль `pg_create_subscription` или `pg_maintain` вместо суперпользователя.
   ```sql
   CREATE ROLE migration_user WITH REPLICATION LOGIN PASSWORD 'strong_password';
   GRANT SELECT ON ALL TABLES IN SCHEMA public TO migration_user;
   -- Для PG 17+ (последовательности)
   GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO migration_user;
   ```

#### Шаг 2: Начальный перенос схемы

Логическая репликация не переносит DDL. Схему нужно перенести заранее.
```bash
pg_dump -h source_host -U postgres -s dbname > schema.sql
psql -h target_host -U postgres -d dbname -f schema.sql
```

#### Шаг 3: Создание публикации и подписки

1. **На Source:**
   ```sql
   -- Для PG 17+ (включая последовательности)
   CREATE PUBLICATION migration_pub FOR ALL TABLES, ALL SEQUENCES;
   -- Для версий < 17
   CREATE PUBLICATION migration_pub FOR ALL TABLES;
   ```

2. **На Target:**
   ```sql
   CREATE SUBSCRIPTION migration_sub
   CONNECTION 'host=source_host user=migration_user password=strong_password dbname=dbname'
   PUBLICATION migration_pub
   WITH (copy_data = true, streaming = 'parallel');
   ```

#### Шаг 4: Мониторинг и оптимизация

Проверка отставания (Lag):
```sql
-- На Source
SELECT application_name, sent_lsn, replay_lsn, 
       pg_wal_lsn_diff(sent_lsn, replay_lsn) AS lag_bytes
FROM pg_stat_replication;
```

Если миграция идет медленно, увеличьте `max_logical_replication_workers` на целевом сервере.

#### Шаг 5: Переключение (Cutover)

1. **Остановить приложение** (или перевести в режим read-only).
2. **Проверить лаг:** он должен стать 0.
3. **Для версий < 17:** синхронизировать последовательности вручную.
   ```sql
   -- На Source: генерация setval
   SELECT 'SELECT setval(' || quote_literal(quote_ident(s.relname)) || ', ' || nextval(s.relname) || ');'
   FROM pg_class s WHERE s.relkind = 'S';
   ```
4. **Удалить подписку и публикацию:**
   ```sql
   DROP SUBSCRIPTION migration_sub; -- На Target
   DROP PUBLICATION migration_pub;  -- На Source
   ```
5. **Запустить приложение** на новом сервере.

### Сценарий: Стратегия отката (Rollback)

В случае критических проблем после переключения, вам может потребоваться вернуться на старый сервер, не теряя новых данных, записанных на Target.

1. **Подготовка реверса:** Сразу после переключения на Target, создайте на нем публикацию:
   ```sql
   CREATE PUBLICATION rollback_pub FOR ALL TABLES;
   ```
2. **Подписка на Source:** На исходном сервере создайте подписку на Target (убедившись, что данные на Source не менялись):
   ```sql
   CREATE SUBSCRIPTION rollback_sub 
   CONNECTION 'host=target_host user=migration_user ...' 
   PUBLICATION rollback_pub WITH (copy_data = false); -- Только новые данные
   ```
3. **Откат:** Если нужен возврат, остановите приложение, проверьте лаг `rollback_sub`, удалите подписки и переключите трафик обратно на Source.

### Сценарий: Валидация данных после миграции

Для подтверждения успешности переноса выполните следующие проверки:
1. **Сравнение количества строк:**
   ```sql
   SELECT count(*) FROM table_name;
   ```
2. **Проверка контрольных сумм (Sample Checksum):**
   ```sql
   SELECT sum(hashtext(t.*::text)) FROM (SELECT * FROM table_name LIMIT 1000) t;
   ```
3. **Проверка индексов и ограничений:** Убедитесь, что все Foreign Keys и Check Constraints находятся в статусе `VALID`.

## Дополнительная информация

### Оптимизация больших таблиц

Если в БД есть таблицы > 1TB:
* **Секционирование (Partitioning):** Разделите таблицу на секции. Логическая репликация в современных версиях позволяет реплицировать секционированные таблицы целиком или по отдельным секциям.
* **Индексы:** Создавайте тяжелые GIN/GiST индексы на Target **после** завершения начальной фазы `copy_data`, чтобы не замедлять процесс вставки.

### Производительность и тюнинг

* **Параллельная копия:** в PG 16+ начальная загрузка (`copy_data`) может выполняться параллельно для разных таблиц, если настроено достаточное количество `max_sync_workers_per_subscription`.
* **Слоты репликации:** всегда проверяйте наличие активного слота на Source (`pg_replication_slots`). Неактивный слот приведет к бесконечному росту WAL и переполнению диска.

### Ограничения и типичные ошибки

* **REPLICA IDENTITY:** Если таблица не имеет первичного ключа и не настроена как `FULL`, операции `UPDATE` и `DELETE` будут игнорироваться репликацией.
* **Конфликты данных:** Если на Target-сервере уже есть данные, перекрывающиеся с Source, подписка остановится с ошибкой `duplicate key value`.
* **Переполнение диска WAL:** Если подписка остановлена (например, из-за ошибки схемы), слот репликации на Source будет удерживать WAL-файлы. Мониторьте `pg_replication_slots.active`.
* **DDL:** любые изменения структуры (ALTER TABLE) на Source не передаются. При несовпадении схемы репликация остановится.
* **Индексы:** на Target-сервере индексы должны быть созданы до начала `copy_data` для уникальных проверок, но их наличие может замедлить начальную вставку. Оптимально: создать PK/Unique до начала, остальные индексы — после.
