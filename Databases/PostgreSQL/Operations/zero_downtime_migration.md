# Миграция PostgreSQL без простоя (Zero-Downtime)

## Определения

*   **Миграция без простоя (Zero-Downtime Migration)** — процесс переноса базы данных с минимизацией времени недоступности. Простой ограничивается только временем переключения (Cutover) трафика в приложении, что обычно занимает от нескольких секунд до минуты.
*   **Логическая репликация (Logical Replication)** — механизм передачи изменений на уровне отдельных строк, основанный на декодировании WAL в поток логических сообщений. Позволяет передавать данные между разными мажорными версиями PostgreSQL (например, с 12 на 18) и разными аппаратными платформами.
*   **LSN (Log Sequence Number)** — уникальный идентификатор (64-битное целое число), указывающий на позицию записи в журнале транзакций (WAL). Используется для отслеживания прогресса репликации.
*   **Слот репликации (Replication Slot)** — автоматизированный механизм на сервере-источнике, гарантирующий, что WAL-файлы не будут удалены до тех пор, пока они не будут успешно переданы всем подписчикам.
*   **Публикация (Publication)** — объект на исходном сервере (Source), определяющий набор таблиц и последовательностей для репликации.
*   **Подписка (Subscription)** — объект на целевом сервере (Target), определяющий соединение с публикацией и способ получения данных.
*   **REPLICA IDENTITY** — параметр таблицы, определяющий, какая информация будет записываться в WAL при UPDATE/DELETE. По умолчанию это первичный ключ (Primary Key).

## Базовые концепции

### Почему логическая репликация?

Для миграции между версиями существует два основных пути:
1.  **Физическая миграция (`pg_upgrade`):** Быстро, но требует полной остановки БД (Downtime).
2.  **Логическая миграция:** Позволяет держать оба сервера (старый и новый) синхронизированными в реальном времени, выполняя переключение только после полной готовности целевого сервера.

### Архитектура процесса

Процесс строится по модели «издатель — подписчик» (Publisher-Subscriber):
1.  **Начальная синхронизация (Snapshot):** Подписчик создает снапшот данных и копирует текущее состояние всех выбранных таблиц.
2.  **Накатка логов (Catch-up):** После копирования снапшота подписчик начинает применять изменения, произошедшие во время копирования, используя поток логического декодирования.
3.  **Синхронное состояние:** Когда лаг (Lag) становится минимальным, система готова к переключению.

### Чек-лист подготовки (Mandatory)

Перед началом миграции **обязательно** проверьте следующие пункты:
1.  **Первичные ключи:** Каждая таблица для репликации UPDATE/DELETE должна иметь Primary Key. Если его нет, используйте `ALTER TABLE name REPLICA IDENTITY FULL` (внимание: значительно увеличивает объем WAL и нагрузку на CPU).
2.  **Триггеры:** По умолчанию триггеры не срабатывают на Target. Если они нужны (например, для аудита), включите их через `ALTER TABLE name ENABLE REPLICA TRIGGER name`.
3.  **Типы данных:** Логическая репликация не поддерживает специфические типы (например, `lo` — large objects). Большие поля `bytea`/`text` могут вызвать значительные задержки.
4.  **Место на диске:** На Source должен быть запас места для WAL. Если Target отключится, слот репликации будет удерживать WAL-файлы до заполнения диска.
5.  **Конкуренция за VACUUM:** Логическая репликация может препятствовать очистке старых версий строк на Source, если транзакция копирования данных длится долго.

### Ключевые возможности современных версий

*   **PostgreSQL 16:** поддержка параллельного применения изменений (`streaming = 'parallel'`), что значительно ускоряет миграцию высоконагруженных таблиц. Добавлена возможность репликации со Standby-серверов.
*   **PostgreSQL 17:** нативная поддержка репликации последовательностей (Sequences). Ранее последовательности требовали ручной синхронизации при переключении.
*   **PostgreSQL 18:** логическое декодирование теперь использует преимущества **Asynchronous I/O (AIO)**. Это значительно снижает нагрузку на CPU/IO при чтении WAL на исходном сервере и ускоряет передачу изменений для высоконагруженных систем. Также улучшена стабильность репликации при обработке очень длинных транзакций.

## Практические сценарии

### Сценарий: Миграция БД на PostgreSQL 18 (2026 Standard)

#### Шаг 1: Подготовка исходного сервера (Source)

1.  **Настройка `postgresql.conf`:**
    ```ini
    wal_level = logical
    max_replication_slots = 10
    max_wal_senders = 10
    # Рекомендуется для стабильности длинных транзакций в 2026 году
    logical_decoding_work_mem = 128MB 
    ```
    *Требуется перезапуск.*

2.  **Создание пользователя миграции:**
    ```sql
    CREATE ROLE migration_user WITH REPLICATION LOGIN PASSWORD 'strong_password';
    GRANT SELECT ON ALL TABLES IN SCHEMA public TO migration_user;
    -- Для PG 17+ (последовательности)
    GRANT SELECT ON ALL SEQUENCES IN SCHEMA public TO migration_user;
    ```

#### Шаг 2: Перенос схемы и подготовка Target

Логическая репликация не переносит DDL. Схему нужно перенести заранее.
```bash
# Экспорт схемы без данных
pg_dump -h source_host -U postgres -s dbname > schema.sql
# Импорт на целевой сервер
psql -h target_host -U postgres -d dbname -f schema.sql
```
*Важно: На Target создайте только PK и Unique индексы перед началом. Тяжелые индексы (GIN/GiST) лучше создавать ПОСЛЕ начальной синхронизации.*

#### Шаг 3: Создание публикации и подписки

1.  **На Source (Создание публикации):**
    ```sql
    -- Для PG 17+ (включая последовательности)
    CREATE PUBLICATION migration_pub FOR ALL TABLES, ALL SEQUENCES;
    ```

2.  **На Target (Создание подписки):**
    ```sql
    CREATE SUBSCRIPTION migration_sub
    CONNECTION 'host=source_host user=migration_user password=strong_password dbname=dbname'
    PUBLICATION migration_pub
    WITH (
        copy_data = true, 
        streaming = 'parallel', -- PG 16+
        run_as_owner = true      -- PG 18+ для безопасности
    );
    ```

#### Шаг 4: Мониторинг и тюнинг

Проверка лага репликации:
```sql
-- На Source: смотрим сколько байт осталось передать
SELECT application_name, 
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn)) AS diff_from_current,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, replay_lsn)) AS replication_lag
FROM pg_stat_replication;
```

Если `replication_lag` растет, увеличьте `max_logical_replication_workers` на Target.

#### Шаг 5: Переключение (Cutover)

1.  **Остановка записи:** Переведите приложение в режим обслуживания или `READ ONLY` на Source.
2.  **Финальная проверка:** Убедитесь, что `replication_lag` равен 0.
3.  **Удаление связей:**
    ```sql
    DROP SUBSCRIPTION migration_sub; -- На Target
    DROP PUBLICATION migration_pub;  -- На Source
    ```
4.  **Смена точки входа:** Обновите DNS или конфиги приложения на адрес `target_host`.

### Сценарий: Обработка изменений DDL во время миграции

Логическая репликация останавливается при несовпадении схем. Если DDL необходим во время миграции, следуйте принципу **Expand-Contract**:
1.  Примените DDL на **Target** (Subscriber).
2.  Примените DDL на **Source** (Publisher).
3.  Репликация продолжит работу, так как Target готов принимать новые поля.

## Устранение неполадок (Troubleshooting)

| Проблема | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `duplicate key value violates unique constraint` | На Target уже были данные. | Очистите таблицы на Target: `TRUNCATE TABLE name CASCADE`. |
| `logical replication target relation ... is missing some replicated columns` | Схемы Source и Target различаются. | Выполните `ALTER TABLE` на Target, чтобы добавить недостающие колонки. |
| Бесконечный рост WAL на Source | Слот репликации неактивен (`active = f`). | Проверьте логи Target на наличие ошибок. Если миграция заброшена — удалите слот: `SELECT pg_drop_replication_slot('name')`. |
| `ERROR: replication slot ... is active for PID ...` | Другая подписка уже использует этот слот. | Используйте уникальные имена для каждой подписки. |
| Огромный лаг на больших таблицах | Отсутствие параллелизма или медленные индексы. | Используйте `streaming = 'parallel'` (PG 16+) и отключите лишние индексы на время `copy_data`. |

## Пограничные случаи и ограничения

### Таблицы без первичных ключей
Если вы используете `REPLICA IDENTITY FULL`:
*   Каждый `UPDATE` или `DELETE` выполняет последовательное сканирование (Sequential Scan) таблицы на Target для поиска нужной строки.
*   На больших таблицах это приведет к катастрофическому росту лага. 
*   **Рекомендация:** Добавьте хотя бы `UNIQUE` индекс.

### Большие объекты (Large Objects)
Тип данных `lo` (и функции `lo_create`, `lo_export`) не реплицируются. 
*   **Решение:** Перейдите на использование `bytea` или мигрируйте такие таблицы через `pg_dump/pg_restore` с коротким простоем.

### Ошибки типа "Replica lag due to bloat"
Если на Source идет массивная очистка (`VACUUM FULL`) или пересоздание индексов, это генерирует огромный поток WAL, который может "забить" канал логической репликации.

### Бесшовная миграция с ВМ в Kubernetes

Типичный сценарий: PostgreSQL работает на виртуальной машине (bare-metal или ВМ в облаке), и требуется перенести его в Kubernetes без простоя.

**Потенциальные подводные камни:**
1.  **Сетевые задержки:** Между ВМ и кластером Kubernetes может быть высокий latency, что увеличит лаг репликации.
2.  **Firewall/Security Groups:** Необходимо разрешить трафик между ВМ и кластером K8s на порту PostgreSQL (5432) и порту репликации.
3.  **Разные версии PostgreSQL:** Логическая репликация поддерживает миграцию между разными мажорными версиями, но требует тщательного тестирования.
4.  **Размер базы:** На больших БД (>500 ГБ) начальная синхронизация (`copy_data`) может занять часы.
5.  **DNS/Service Discovery:** После переключения приложений на новый кластер в K8s необходимо обновить DNS-записи или конфигурации.

**Порядок действий (Step-by-Step):**

1.  **Подготовка целевого кластера в K8s:**
    - Рвернуть PostgreSQL через оператор (CNPG, Zalando) или Patroni.
    - Убедиться, что `wal_level = logical` на Source.

2.  **Настройка сетевой связности:**
    - Создать туннель или разрешить трафик между ВМ и кластером K8s.
    - Проверить доступность: `psql -h <k8s-service> -U migration_user -d dbname`.

3.  **Создание логической репликации:**
    - На Source (ВМ): `CREATE PUBLICATION migration_pub FOR ALL TABLES, ALL SEQUENCES;`
    - На Target (K8s): `CREATE SUBSCRIPTION ... CONNECTION 'host=vm-host ...' PUBLICATION migration_pub;`

4.  **Мониторинга лага:**
    - Контролировать `replication_lag` до достижения минимального значения.

5.  **Переключение (Cutover):**
    - Остановить запись на Source (перевести приложение в READ ONLY или maintenance mode).
    - Дождаться обнуления лага.
    - Удалить подписку и публикацию.
    - Обновить DNS/конфигурации приложений на адрес сервиса K8s.
    - Возобновить запись.

**Схема переключения ролей:**
- Исходный мастер (ВМ) → Реплика → Новый мастер (в K8s)
- На момент переключения бывшая реплика в K8s становится Primary.
- Старая ВМ может оставаться как резервная реплика или быть выведена из эксплуатации.

**Важно:** После переключения необходимо:
- Проверить целостность данных (контрольные суммы).
- Убедиться, что последовательности (sequences) синхронизированы (PG 17+ делает это автоматически).
- Настроить бэкапы нового кластера (S3, WAL-G).
- Обновить DNS TTL заранее (за 24 часа до миграции).

## Дополнительная информация

### Валидация данных после миграции

Для подтверждения успешности переноса выполните следующие проверки:
1.  **Сравнение количества строк:** `SELECT count(*) FROM table_name;`
2.  **Проверка контрольных сумм (Sample Checksum):**
    ```sql
    SELECT sum(hashtext(t.*::text)) FROM (SELECT * FROM table_name ORDER BY id LIMIT 1000) t;
    ```
3.  **Проверка последовательностей:** Убедитесь, что `nextval` на Target больше, чем на Source.
