# Миграция PostgreSQL без простоя (Zero-Downtime)

## Определения

**Миграция без простоя (Zero-Downtime Migration)** — процесс переноса базы данных на новый сервер или в другую инфраструктуру с минимизацией времени недоступности приложения (обычно до секунд, необходимых на переключение трафика).

**Логическая репликация (Logical Replication)** — механизм передачи изменений данных на уровне отдельных строк, основанный на декодировании журнала предзаписи (WAL). В отличие от физической репликации, позволяет передавать данные между разными мажорными версиями PostgreSQL и разными архитектурами ОС. Подробнее — **[Репликация в PostgreSQL](../Concepts/replication.md#логическая-репликация-publisher-subscriber)**.

## Основные концепции

### Механизм работы

Стратегия миграции без простоя базируется на использовании логической репликации по модели «издатель — подписчик» (Publisher — Subscriber):

1. **Начальная синхронизация:** структура базы данных (схема) и существующие данные переносятся на новый сервер.
2. **Потоковая передача изменений:** все новые изменения (INSERT, UPDATE, DELETE), происходящие на исходном сервере во время переноса данных, фиксируются в слоте репликации и передаются на целевой сервер.
3. **Переключение (Cutover):** когда целевой сервер «догоняет» исходный по времени (лаг репликации близок к нулю), приложение переключается на работу с новой базой данных.

### Преимущества подхода

- **Минимальный простой:** время недоступности ограничено только временем переключения конфигурации приложения.
- **Обновление версий:** возможность миграции с более старой версии (например, PostgreSQL 12) на более новую (например, PostgreSQL 16).
- **Проверка данных:** возможность проверить целостность и производительность на новом сервере до окончательного переключения.

## Практические сценарии

### Сценарий: Миграция базы данных между серверами

#### Шаг 1: Подготовка окружения

1. **Настроить Source (Исходный сервер):**
    В `postgresql.conf` необходимо установить уровень логирования для логической репликации:

    ```ini
    wal_level = logical
    ```

    *Примечание: изменение параметра требует перезапуска сервера.*

2. **Создать пользователя для репликации:**

    ```sql
    CREATE ROLE migration_user WITH REPLICATION LOGIN PASSWORD 'strong_password';
    GRANT SELECT ON ALL TABLES IN SCHEMA public TO migration_user;
    ```

3. **Разрешить подключения в `pg_hba.conf`:**

    ```conf
    host  all  migration_user  <IP_целевого_сервера>/32  scram-sha-256
    ```

#### Шаг 2: Начальный перенос данных (Baseline)

Для обеспечения консистентности данных между дампом и началом репликации рекомендуется использовать механизм снимков (snapshots).

1. **Создать публикацию на Source:**

    ```sql
    CREATE PUBLICATION migration_pub FOR ALL TABLES;
    ```

2. **Перенос схемы (без данных):**

    ```bash
    pg_dump -h source_host -U postgres -s dbname > schema.sql
    psql -h target_host -U postgres -d dbname -f schema.sql
    ```

3. **Синхронизация данных:**
    Для больших баз данных эффективнее использовать `pg_dump` с ключом `--snapshot` (требует активной транзакции для получения идентификатора снимка) или встроенный механизм логической репликации `copy_data = true` при создании подписки.

#### Шаг 3: Настройка подписки на Target (Целевой сервер)

На новом сервере создается подписка, которая начнет забирать изменения с момента создания.

```sql
CREATE SUBSCRIPTION migration_sub
CONNECTION 'host=source_host user=migration_user password=strong_password dbname=dbname'
PUBLICATION migration_pub
WITH (copy_data = true);
```

*Параметр `copy_data = true` заставит PostgreSQL автоматически скопировать текущие данные всех таблиц, входящих в публикацию, перед началом репликации изменений.*

#### Шаг 4: Мониторинг синхронизации

Необходимо отслеживать лаг репликации. Когда значения LSN на мастере и реплике практически сравняются, можно планировать переключение.

```sql
-- На Source: проверка статуса репликации
SELECT application_name, state, sent_lsn, write_lsn, flush_lsn, replay_lsn
FROM pg_stat_replication;

-- На Target: проверка статуса подписки
SELECT subname, latest_end_lsn, last_msg_send_time, last_msg_receipt_time
FROM pg_stat_subscription;
```

#### Шаг 5: Переключение (Cutover)

1. **Остановить запись в БД:** перевести приложение в режим Maintenance или изменить настройки балансировщика, чтобы запретить запись на Source.
2. **Дождаться финальной синхронизации:** убедиться, что лаг репликации равен нулю.
3. **Обновить последовательности (Sequences):** логическая репликация не передает текущие значения последовательностей. Их нужно обновить вручную (см. Дополнительная информация).
4. **Переключить приложение:** обновить строки подключения (Connection Strings) в приложении на новый сервер.
5. **Удалить репликацию:**

    ```sql
    -- На Target
    DROP SUBSCRIPTION migration_sub;
    -- На Source
    DROP PUBLICATION migration_pub;
    ```

## Дополнительная информация

### Ограничения и нюансы

- **DDL-команды:** логическая репликация не передает изменения структуры таблиц (ALTER TABLE, CREATE INDEX). Если во время миграции схема изменится, репликация может остановиться с ошибкой.
- **Индексы и ограничения:** на Target-сервере должны быть созданы все необходимые индексы для производительности и уникальные ключи для работы репликации.
- **Триггеры:** по умолчанию триггеры не срабатывают на подписчике. Если логика приложения требует работы триггеров на целевом сервере, используйте `ALTER TABLE ... ENABLE ALWAYS TRIGGER ...`.

### Синхронизация последовательностей (Sequences)

После завершения репликации данных и перед запуском приложения на новом сервере необходимо актуализировать значения всех последовательностей:

```sql
-- Скрипт для генерации команд обновления на Source
SELECT 'SELECT setval(' || quote_literal(quote_ident(s.relname)) || ', ' || nextval(s.relname) || ');'
FROM pg_class s
WHERE s.relkind = 'S';
```

Выполните полученные команды `setval` на целевом сервере.

### Инструменты автоматизации

В сложных сценариях или облачных средах рекомендуется использовать специализированные инструменты:

- **`pglogical`** — расширение для более гибкого управления логической репликацией.
- **AWS Database Migration Service (DMS)** — для миграции в облако AWS.
- **Yandex Data Transfer** — для миграции внутри или в облако Yandex Cloud.
