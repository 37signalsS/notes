# Отказоустойчивый кластер PostgreSQL (Patroni, etcd, HAProxy)

## Определения

**Patroni** — шаблон (Python-приложение) для управления высокодоступными кластерами PostgreSQL. Обеспечивает автоматический failover, управление конфигурацией и мониторинг состояния инстансов.

**etcd** — распределенное отказоустойчивое хранилище типа "ключ-значение". Используется Patroni как **DCS (Distributed Configuration Store)** для хранения состояния кластера и выбора лидера (Leader Election).

**Watchdog** — механизм защиты («сторожевой таймер»), принудительно перезагружающий ОС в случае зависания Patroni или потери связи с DCS, чтобы исключить возникновение Split Brain.

**Failover** — автоматический процесс переключения ролей в кластере при выходе из строя мастера.

**Switchover** — плановый перенос роли мастера на один из резервных узлов (например, для обслуживания железа или обновления ядра ОС).

## Архитектура стека

Типовая схема включает 3 узла базы данных для обеспечения кворума в DCS.

```
      [ Клиент / Приложение ]
               |
        [ VIP / DNS Name ]
               |
      [ HAProxy + Keepalived ] (2-3 ноды)
               |
    -----------------------
    |          |          |
[ Узел 1 ] [ Узел 2 ] [ Узел 3 ]
| Patroni| | Patroni| | Patroni|
| Postgre| | Postgre| | Postgre|
|Watchdog| |Watchdog| |Watchdog|
    \          |          /
     \--- [ etcd кластер ] ---/
```

### Роли компонентов

1.  **PostgreSQL:** Непосредственно хранение и обработка данных. Работает в режиме `Primary` (чтение/запись) или `Replica` (только чтение, асинхронная или синхронная репликация).
2.  **Patroni:**
    -   Запускает и управляет процессом PostgreSQL.
    -   Удерживает **Leader Lock** в etcd через периодические Heartbeats (обычно каждые 10 секунд).
    -   Взаимодействует с ядром через `/dev/watchdog` для обеспечения безопасности на уровне ОС.
    -   Предоставляет REST API для проверок состояния (например, `/master`, `/replica`).
3.  **etcd:**
    -   Хранит конфигурацию кластера и текущую позицию WAL каждого узла.
    -   Служит механизмом блокировок (Locks) для предотвращения ситуации "Split Brain".
    -   Обеспечивает консистентность состояния кластера через алгоритм Raft.
4.  **HAProxy:**
    -   Опрашивает REST API Patroni на каждом узле.
    -   Узел, вернувший HTTP 200 на эндпоинт `/master` (или `/primary` в новых версиях), помечается как `UP` в пуле для записи.
    -   Узлы, вернувшие 200 на `/replica`, могут использоваться для балансировки запросов на чтение.

## Механизмы защиты: Watchdog и Fencing

Критически важно предотвратить ситуацию, когда два узла одновременно считают себя мастерами (Split Brain).

1.  **Watchdog (Software/Hardware):** Patroni периодически "кормит" собаку (сбрасывает таймер `/dev/watchdog`). Если Patroni зависнет, таймер истечет, и Watchdog вызовет немедленную перезагрузку (Kernel Panic / Reboot), освобождая лидерский ключ.
2.  **Fencing:** Если узел теряет связь с etcd, Patroni немедленно переводит PostgreSQL в режим `read-only` или выключает его, если настроен параметр `master_start_timeout`.

## Механизм Failover

1.  **Сбой мастера:** Мастер (Узел 1) падает или теряет сетевую связность.
2.  **Истечение TTL:** Leader Key в etcd имеет ограниченное время жизни (TTL). Поскольку Patroni на Узле 1 не может его обновить, ключ удаляется.
3.  **Выборы:** Patroni на репликах (Узел 2 и 3) замечают отсутствие мастера и начинают процесс выбора. Узел с наиболее актуальными данными захватывает новый Leader Key.
4.  **Смена роли:** Выбранная реплика (например, Узел 2) переходит в режим `Master`.
5.  **Переключение трафика:** HAProxy при очередной проверке видит, что Узел 1 недоступен, а Узел 2 теперь отвечает на запрос `/master`. Трафик мгновенно перенаправляется на Узел 2.

## Обеспечение отказоустойчивости балансировщика

Сам HAProxy может стать единой точкой отказа. Методы защиты:

-   **Keepalived (VRRP):** Несколько нод HAProxy разделяют один **Virtual IP (VIP)**. При падении активной ноды VIP переезжает на резервную.
-   **DNS Round Robin:** За одним DNS-именем закреплено несколько IP-адресов балансировщиков. Клиент (или библиотека подключения) пробует их по очереди.
-   **Headless Service (в Kubernetes):** Если приложение в K8s, оно может обращаться к HAProxy через сервис.

## Практические сценарии

### Настройка Health Check в HAProxy

Пример конфигурации для проверки мастера через Patroni:

```haproxy
listen postgres_master
    bind *:5432
    option httpchk GET /master
    http-check expect status 200
    default-server inter 2s fall 3 rise 2
    server pg_node_1 192.168.1.10:5432 check port 8008
    server pg_node_2 192.168.1.11:5432 check port 8008
    server pg_node_3 192.168.1.12:5432 check port 8008
```
*Здесь порт 8008 — стандартный порт API Patroni.*

### Сценарий 1: Настройка синхронной репликации (Zero Data Loss)

Если бизнес-требования запрещают потерю даже одной транзакции, в Patroni настраивается синхронный режим:

```yaml
# В конфигурации patroni.yml или через edit-config
postgresql:
  parameters:
    synchronous_commit: "on"
  use_pg_rewind: true
  synchronous_mode: true
  synchronous_node_count: 1 # Минимум одна реплика должна подтвердить запись
```
*Внимание: Если ни одна реплика не доступна, мастер перестанет принимать запись до восстановления связности.*

### Сценарий 2: Обслуживание кластера (Maintenance Mode)

Для проведения технических работ на мастере без инициирования автоматического failover используется режим паузы:

```bash
# Перевод кластера в режим обслуживания (пауза)
patronictl pause <cluster_name>

# Теперь можно останавливать PostgreSQL или Patroni вручную
sudo systemctl stop patroni

# После завершения работ верните кластер в штатный режим
patronictl resume <cluster_name>
```

### Критерии выбора: Кубернетес vs ВМ

| Фактор | PostgreSQL в Kubernetes | PostgreSQL на ВМ |
| :--- | :--- | :--- |
| **Управление** | Через операторы (Zalando, CloudNativePG). | Ручное или через Ansible (Patroni). |
| **Автоматизация** | Встроена в оператор (самоисцеление, бэкапы). | Требует настройки внешних инструментов. |
| **Команда** | Подходит для продуктовых команд (DevOps-style). | Предпочтительно при наличии выделенного отдела DBA. |
| **Сложность** | Высокая (требует глубокого знания K8s Networking/Storage). | Средняя (классический стек). |
