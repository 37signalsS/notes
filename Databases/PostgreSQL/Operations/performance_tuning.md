# Оптимизация производительности PostgreSQL

## Определения

* **MVCC (Multi-Version Concurrency Control):** Механизм, используемый в PostgreSQL, при котором для обеспечения параллельного доступа создаются разные версии строк. При операции `UPDATE` или `DELETE` старая версия строки не удаляется физически, а лишь помечается как неактуальная ("мертвая").
* **Раздувание таблиц (Bloat):** Процесс, при котором файл таблицы на диске содержит много "мертвого" пространства (dead tuples) и занимает больше места, чем необходимо. Это следствие работы MVCC.
* **`VACUUM`:** Служебный процесс, который освобождает место от "мертвых" кортежей для повторного использования новыми строками. `autovacuum` — это фоновый процесс, который выполняет эту операцию автоматически.
* **План выполнения (`EXPLAIN`):** Последовательность операций (сканирование таблиц, соединения, сортировки), которую PostgreSQL планирует выполнить для запроса. `EXPLAIN ANALYZE` дополнительно **выполняет** запрос и показывает реальное время и стоимость каждого шага.
* **Коэффициент попадания в кэш (cache hit rate):** Ключевой показатель производительности, который показывает, какая доля запрошенных данных была найдена в кэше PostgreSQL (`shared_buffers`), а не прочитана с диска.
* **Индекс:** Структура данных, которая обеспечивает быстрый доступ к строкам таблицы. Правильное использование индексов — ключевой аспект оптимизации запросов.

## Основные концепции

### `VACUUM` и раздувание таблиц (Bloat)

PostgreSQL использует модель MVCC (Multi-Version Concurrency Control). При операции `UPDATE` или `DELETE` старая версия строки не удаляется физически, а лишь помечается как неактуальная ("мертвая" или `dead tuple`). `UPDATE` по своей сути является атомарной комбинацией `INSERT` (новой версии строки) и `DELETE` (пометки старой версии). Со временем это приводит к "раздуванию" (bloat) таблиц и индексов, когда файл таблицы на диске содержит много мусора и занимает больше места, чем необходимо.

Процесс `VACUUM` освобождает это место для повторного использования новыми строками. **Автовакуум (Autovacuum)** — это фоновый процесс, критически важный для поддержания производительности и эффективности PostgreSQL. Он отвечает за:

* Сбор статистики по таблицам для планировщика запросов (`ANALYZE`).
* Очистку "мертвых" строк (`dead tuples`).
* Предотвращение зацикливания счетчиков транзакций (transaction ID wraparound).

### Индексы

Помимо стандартного **B-Tree**, PostgreSQL предлагает несколько специализированных типов индексов для конкретных задач:

* **GIN (Generalized Inverted Index):** Эффективен для поиска внутри "составных" значений. Основные сценарии:
  * Полнотекстовый поиск.
  * Поиск элементов в массивах (`array`).
  * Поиск ключей и пар "ключ-значение" в `jsonb`.

* **GiST (Generalized Search Tree):** Обобщенное дерево поиска, которое позволяет реализовывать сложные типы индексов для нестандартных данных.
  * Основной пример — **геопространственные данные** (широта/долгота) с расширением `PostGIS`.

* **BRIN (Block Range Index):** Очень компактный индекс, который хранит только минимальное и максимальное значение для большого диапазона блоков на диске.
  * Идеален для очень больших таблиц, где данные физически упорядочены (например, таблицы с временными рядами, где `created_at` монотонно возрастает).

> **Основная теория:** Подробное описание концепций, базовых типов (B-Tree, Hash), составных индексов и проблем избыточного индексирования находится в основной заметке: **[Индексы в базах данных](../../Concepts/indexes.md)**.

### Анализ планов запросов (`EXPLAIN ANALYZE`)

`EXPLAIN` — основной инструмент для понимания того, как PostgreSQL собирается выполнять запрос.

**Что показывает `EXPLAIN`:**

* **План выполнения:** Последовательность операций (сканирование таблиц, соединения, сортировки).
* **Типы сканирования:**
  * `Sequential Scan (Seq Scan)`: Полное сканирование таблицы. Эффективно для маленьких таблиц или когда нужно прочитать большую часть таблицы.
  * `Index Scan`: Поиск по индексу. Эффективно для выборки небольшого количества строк.
  * `Bitmap Index/Heap Scan`: Комбинированный метод, эффективный для нескольких условий в `WHERE`.
* **Типы соединений (`JOIN`):**
  * `Nested Loop Join`: Для каждой строки из первой таблицы ищет совпадения во второй.
  * `Hash Join`: Строит хеш-таблицу для одной из таблиц в памяти. Эффективен для больших таблиц при соединении по равенству.
  * `Merge Join`: Сначала сортирует обе таблицы по ключу соединения, а затем "сливает" их.
* **Стоимость (`cost`):** Оценка планировщиком затрат на выполнение операции. Состоит из стоимости начала (`startup cost`) и общей стоимости (`total cost`).

### Аппаратное обеспечение и настройка ОС

* **CPU**: Для OLTP-нагрузок (много коротких транзакций) важна высокая тактовая частота. Для OLAP-нагрузок (сложные аналитические запросы) — большее количество ядер для параллелизации вычислений.
* **RAM**: Чем больше, тем лучше. Достаточный объем памяти позволяет держать "горячие" данные в кэше, минимизируя медленные дисковые операции.
* **Диски**: Использование SSD (NVMe) вместо HDD является стандартом для высоконагруженных систем. Рекомендуется разносить данные, WAL (Write-Ahead Log) и индексы на разные физические диски для распределения нагрузки ввода-вывода.
* **Настройки Linux**:
  * **`swappiness`**: Для серверов баз данных рекомендуется устанавливать низкое значение (например, `1` или `5`).
  * **`transparent_hugepage`**: Эту функцию рекомендуется отключать (`never`).
  * **`atime`**: Рекомендуется отключать с помощью опции `noatime` в `fstab`.

### Настройка параметров сервера

Ключевые параметры в `postgresql.conf`, влияющие на производительность:

* **`shared_buffers`:** Основной кэш PostgreSQL для страниц данных и индексов. Рекомендуемое значение — 25% от доступной оперативной памяти (RAM) для выделенного сервера.
* **`work_mem`:** Объем памяти, выделяемый для внутренних операций сортировки, хеширования, `GROUP BY`. Этот объем выделяется на каждую операцию, поэтому слишком большое значение может быстро исчерпать RAM.
* **`maintenance_work_mem`:** Память для служебных операций, таких как `VACUUM`, `CREATE INDEX`, `ALTER TABLE`.
* **`effective_cache_size`:** Подсказка для планировщика о том, сколько памяти доступно для кэширования данных операционной системой. Помогает точнее оценивать стоимость `Index Scan`. Рекомендуемое значение — 50-75% от RAM.

### Мониторинг и диагностика: основные инструменты

* **`pg_stat_activity`**: Показывает все активные процессы (сессии), подключенные к серверу. Это основной инструмент для ответа на вопрос "что сейчас происходит в базе?".
  * `state`: Статус процесса. Особое внимание стоит уделить `active` и `idle in transaction`.
  * `wait_event_type` / `wait_event`: Показывает, чего ожидает процесс (например, `IO`, `Lock`).
* **`pg_stat_statements`**: Мощное расширение (требует добавления в `shared_preload_libraries`), которое отслеживает статистику выполнения всех запросов в системе. Позволяет найти наиболее "дорогие" запросы.
* **`auto_explain`**: Встроенный инструмент для автоматического логирования планов выполнения медленных запросов.
* **`pg_stat_monitor`**: Более продвинутая альтернатива `pg_stat_statements`, которая собирает планы выполнения и предоставляет более детальную разбивку по метрикам.

## Практические сценарии

### Сценарий 1: Общий анализ производительности ("Что-то тормозит")

#### 1. Начните с основ

* **Человеческий фактор и недавние изменения:** Проанализируйте недавние коммиты и изменения в коде.
* **Окружение и соседи:** Убедитесь, что рядом с PostgreSQL не запущены другие ресурсоемкие процессы.

#### 2. Анализ на уровне ОС

* **Основные утилиты:** `top` / `htop`, `iostat`, `df`, `free` / `vmstat`.
* **Проверка OOM Killer:** `dmesg | grep oom-killer`.

#### 3. Анализ на уровне базы данных

* **Что происходит прямо сейчас (`pg_stat_activity`):**
  * Ищите запросы с `state = 'active'`, которые выполняются очень долго.
  * Особое внимание уделяйте состоянию `idle in transaction`.

  ```sql
  -- Найти запросы, выполняющиеся дольше 5 минут
  SELECT pid, age(clock_timestamp(), query_start), usename, query
  FROM pg_stat_activity
  WHERE state = 'active' AND (clock_timestamp() - query_start) > interval '5 minutes';
  ```

* **Какие запросы самые "дорогие" (`pg_stat_statements`):**

  ```sql
  -- Включить расширение (если еще не включено)
  CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
  
  -- Топ-10 запросов по общему времени выполнения
  SELECT total_exec_time, calls, mean_exec_time, query
  FROM pg_stat_statements
  ORDER BY total_exec_time DESC
  LIMIT 10;
  ```

#### 4. Принудительное завершение запросов

```sql
-- "Мягко" завершить запрос (рекомендуется)
SELECT pg_cancel_backend(PID);

-- "Жестко" завершить сессию (если pg_cancel_backend не помогает)
SELECT pg_terminate_backend(PID);
```

### Сценарий 2: Глубокий анализ и оптимизация медленного запроса

#### 1. Изучение плана выполнения с `EXPLAIN ANALYZE`

> **Важно:** `EXPLAIN ANALYZE` **выполняет** запрос. Используйте его с осторожностью с `INSERT`, `UPDATE` или `DELETE`.

* **Чтение плана:** "Изнутри наружу" и "снизу вверх".
* **Поиск проблемных операций:**
  * `Sequential Scan (Seq Scan)` на больших таблицах — главный кандидат на отсутствие индекса.
  * Неверные оценки количества строк (`rows`) — признак устаревшей статистики.

#### 2. Оптимизация и проверка

* **Добавить или изменить индекс:** Наиболее частое решение.
* **Переписать запрос:** Упростить, разбить на части.
* **Предварительная агрегация:** Создать материализованные представления.
* **Собрать статистику:** `ANALYZE table_name;`
* **Изменить конфигурацию для сессии:** `SET work_mem = '32MB';`

После внесения изменений **обязательно** повторно выполните `EXPLAIN ANALYZE`.

### Сценарий 3: Настройка и проактивный мониторинг

#### Управление конфигурацией

* Используйте `ALTER SYSTEM` для изменения параметров в `postgresql.auto.conf`.

  ```sql
  ALTER SYSTEM SET work_mem = '16MB';
  SELECT pg_reload_conf(); -- Применить конфигурацию без перезапуска
  ```

* **Совет:** Параметр `maintenance_work_mem` можно временно увеличить для текущей сессии: `SET maintenance_work_mem = '1GB';`.

#### Мониторинг эффективности кэша

**Целевой показатель:** > 99%.

```sql
SELECT
    (sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read))) * 100 AS cache_hit_rate
FROM
    pg_statio_user_tables;
```

#### Мониторинг Autovacuum и "мертвых" кортежей

```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

#### Автоматический анализ медленных запросов (`auto_explain`)

Настройка в `postgresql.conf`:

```ini
# Загружаем модуль
shared_preload_libraries = 'pg_stat_statements, auto_explain'

# Включаем логирование планов для запросов, выполняющихся дольше 250 мс
auto_explain.log_min_duration = '250ms'

# Чтобы не перегружать систему, можно логировать только часть медленных запросов
auto_explain.log_sample_rate = 0.5 # 50%
```

#### Поиск неиспользуемых индексов

Ненужные индексы замедляют запись и занимают место.

> Запрос для поиска неиспользуемых индексов и детальное описание проблемы доступны в основной заметке **[здесь](../../Concepts/indexes.md#поиск-и-удаление-неиспользуемых-индексов)**.

## Дополнительная информация

### Прямое влияние на планировщик

В редких случаях можно временно повлиять на поведение планировщика. Это опасный инструмент для отладки.

```sql
-- Отключить сканирование по индексу
SET enable_indexscan = off;
-- Вернуть настройку по умолчанию
RESET enable_indexscan;
```

### Другие техники

* **CTE (Common Table Expressions):** Использование `WITH ... AS (...)` может улучшить читаемость запроса.
* **Вынос WAL на отдельный диск:** Снижает дисковую нагрузку.
* **Оптимизация типов данных:** Используйте наиболее подходящие и компактные типы.

### Инструменты и расширения

* **Визуализация планов запросов:**
  * **[explain.depesz.com](https://explain.depesz.com/)**: Скопируйте в него вывод `EXPLAIN ANALYZE`.
* **Калькуляторы для первоначальной настройки:**
  * **PGTune**, **PGConfig.org** (дают лишь отправную точку).
* **Расширения для профилирования:**
  * **`pg_profile`**: Генерирует подробные отчеты о производительности, аналогичные AWR в Oracle.
* **JIT-компиляция:** Начиная с PostgreSQL 16, статистика по работе JIT (Just-In-Time) видна в выводе `EXPLAIN ANALYZE`.

### Связь с Full-Stack Observability

Чтобы понять, какая бизнес-операция в приложении привела к медленному SQL-запросу, необходима сквозная трассировка.

* Для получения полной картины ознакомьтесь с заметкой **[Full-Stack Observability для PostgreSQL](./observability.md)**.
* Ключевой технологией для этого является расширение **pg_tracing**.
