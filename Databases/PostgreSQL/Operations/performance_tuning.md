# Оптимизация производительности PostgreSQL

### 1. Начните с основ (Keep It Simple)

- **Человеческий фактор и недавние изменения:**
  - Проанализируйте недавние коммиты и изменения в коде приложения. Часто проблемы с производительностью появляются после развертывания нового кода с неоптимальными запросами.
  - Используйте систему контроля версий (например, Git) для всех изменений, связанных с базой данных, включая миграции схем и изменения в конфигурации.

- **Окружение и соседи:**
  - Убедитесь, что рядом с PostgreSQL на том же сервере не запущены другие ресурсоемкие процессы, которые могут "воровать" CPU, RAM или дисковый I/O. Базы данных, как правило, требуют выделенных ресурсов.

### 2. Анализ на уровне ОС

Проблемы с производительностью БД часто коренятся в ограничениях на уровне операционной системы. 70-80% тюнинга PostgreSQL — это тюнинг Linux.

- **Основные утилиты для мониторинга:**
  - `top` / `htop` / `atop`: Мониторинг использования CPU и RAM в реальном времени. Обратите внимание на равномерность загрузки ядер и на процессы, потребляющие больше всего ресурсов.
  - `iostat`: Анализ нагрузки на дисковую подсистему (операции чтения/записи, время ожидания).
  - `df`: Проверка свободного места на дисках.
  - `free` / `vmstat`: Проверка использования оперативной памяти и swap.

- **Проверка OOM Killer:** Проверьте системные логи (`dmesg`), чтобы убедиться, что `oom-killer` (Out-of-Memory Killer) не убивал процесс PostgreSQL.

### 3. Анализ на уровне базы данных

- **`pg_stat_activity`**: Первый шаг для ответа на вопрос "что происходит в базе прямо сейчас?".
  - Ищите запросы с `state = 'active'`, которые выполняются очень долго.
  - Особое внимание уделяйте состоянию `idle in transaction`. Такие сессии удерживают блокировки и мешают работе `VACUUM`. Их необходимо отслеживать и завершать.

- **`pg_stat_statements`**: Используйте это расширение для поиска самых "дорогих" запросов в системе по совокупным показателям.
  - **Топ запросов по общему времени выполнения (`total_exec_time`):** Запросы, которые в сумме создают наибольшую нагрузку.
  - **Топ запросов по среднему времени выполнения (`mean_exec_time`):** Отдельные медленные запросы.
  - **Топ запросов по количеству вызовов (`calls`):** Очень частые, но, возможно, быстрые запросы, которые в сумме могут создавать нагрузку.

### 4. Глубокий анализ конкретного запроса

После того как медленный запрос найден, используйте `EXPLAIN ANALYZE` для детального изучения его плана выполнения.

- **Чтение плана:** План выполнения читается "изнутри наружу" и "снизу вверх". Начинайте анализ с самых вложенных операций с наибольшей стоимостью (`cost`) и реальным временем выполнения (`actual time`).
- **Поиск проблемных операций:**
  - `Sequential Scan (Seq Scan)` на больших таблицах — главный кандидат на оптимизацию. Возможно, отсутствует необходимый индекс.
  - Неверные оценки количества строк (`rows`): если планировщик сильно ошибается в оценке количества строк (например, `rows=1` при реальном `rows=100000`), это может указывать на устаревшую статистику. Выполните `ANALYZE my_table;`.
  - Неоптимальные типы `JOIN`.

### 5. Оптимизация и проверка

На основе анализа плана вы можете применить одну из стратегий оптимизации:

- **Добавить или изменить индекс:** Наиболее частое решение.
- **Переписать запрос:** Упростить, разбить на части, использовать другие конструкции.
- **Предварительная агрегация:** Создать материализованные представления или сводные таблицы для тяжелых аналитических запросов.
- **Изменить конфигурацию PostgreSQL:** Например, увеличить `work_mem` для конкретной сессии, если в плане есть дорогостоящие дисковые сортировки.
- **Собрать статистику:** `ANALYZE table_name;`

После внесения изменений **обязательно** повторно выполните `EXPLAIN ANALYZE`, чтобы убедиться, что план действительно улучшился.

Производительность PostgreSQL зависит от множества факторов: от схемы данных и написания запросов до конфигурации сервера и аппаратного обеспечения.

## Аппаратное обеспечение и настройка ОС

### Аппаратное обеспечение

-   **CPU**: Для OLTP-нагрузок (много коротких транзакций) важна высокая тактовая частота. Для OLAP-нагрузок (сложные аналитические запросы) — большее количество ядер для параллелизации вычислений.
-   **RAM**: Чем больше, тем лучше. Достаточный объем памяти позволяет держать "горячие" данные в кэше, минимизируя медленные дисковые операции.
-   **Диски**: Использование SSD (NVMe) вместо HDD является стандартом для высоконагруженных систем. Рекомендуется разносить данные, WAL (Write-Ahead Log) и индексы на разные физические диски для распределения нагрузки ввода-вывода.

### Настройки Linux

До 70-80% тюнинга PostgreSQL сводится к правильной настройке операционной системы.

-   **`swappiness`**: Определяет, насколько "агрессивно" система будет использовать swap-файл. Для серверов баз данных рекомендуется устанавливать низкое значение (например, `1` или `5`), чтобы система использовала swap только при крайней необходимости.
    ```bash
    # Установка значения swappiness
    sysctl -w vm.swappiness=5
    ```
-   **`transparent_hugepage`**: Эту функцию рекомендуется отключать (`never`), так как она может приводить к деградации производительности на некоторых рабочих нагрузках СУБД.
-   **`atime`**: Время последнего доступа к файлу. Обновление этой информации создает дополнительную нагрузку на дисковую подсистему. Рекомендуется отключать с помощью опции `noatime` в `fstab`.

## Анализ планов запросов (`EXPLAIN ANALYZE`)

`EXPLAIN` — основной инструмент для понимания того, как PostgreSQL собирается выполнять запрос. `EXPLAIN ANALYZE` дополнительно выполняет запрос и показывает реальное время выполнения каждого шага.

> **Важно:** Поскольку `EXPLAIN ANALYZE` **выполняет** запрос, используйте его с осторожностью с операторами `INSERT`, `UPDATE` или `DELETE`. Выполнение `EXPLAIN ANALYZE` на DML-запросе изменит ваши данные. Если вы запустите его повторно на том же запросе, результат и план могут быть совершенно другими, так как данные уже были изменены первым запуском.

**Что показывает `EXPLAIN`:**
- **План выполнения:** Последовательность операций (сканирование таблиц, соединения, сортировки).
- **Типы сканирования:**
    - `Sequential Scan (Seq Scan)`: Полное сканирование таблицы. Эффективно для маленьких таблиц или когда нужно прочитать большую часть таблицы.
    - `Index Scan`: Поиск по индексу. Эффективно для выборки небольшого количества строк.
    - `Bitmap Index/Heap Scan`: Комбинированный метод, эффективный для нескольких условий в `WHERE`.
- **Типы соединений (`JOIN`):**
    - `Nested Loop Join`: Для каждой строки из первой таблицы ищет совпадения во второй.
    - `Hash Join`: Строит хеш-таблицу для одной из таблиц в памяти. Эффективен для больших таблиц при соединении по равенству.
    - `Merge Join`: Сначала сортирует обе таблицы по ключу соединения, а затем "сливает" их.
- **Стоимость (`cost`):** Оценка планировщиком затрат на выполнение операции. Состоит из стоимости начала (`startup cost`) и общей стоимости (`total cost`).

Начиная с PostgreSQL 16, активно используется **JIT-компиляция (Just-In-Time)**, которая может компилировать часто выполняемые запросы в нативный код для ускорения их выполнения. Статистику по работе JIT можно увидеть в выводе `EXPLAIN ANALYZE`.

### Прямое влияние на планировщик

В редких случаях, когда планировщик выбирает неоптимальный план, и вы уверены, что другой подход будет лучше, можно временно повлиять на его поведение в рамках текущей сессии. Это делается с помощью команд `SET`.

```sql
-- Отключить сканирование по индексу, чтобы "заставить" планировщик использовать Seq Scan
SET enable_indexscan = off;

-- Вернуть настройку по умолчанию
RESET enable_indexscan;
```

Это мощный, но опасный инструмент, который следует использовать только для отладки и в исключительных ситуациях, так как вы берете на себя работу, которую обычно выполняет оптимизатор.

## Индексы

Правильное использование индексов — ключевой аспект оптимизации запросов.

> **Основная теория:** Подробное описание концепций, базовых типов (B-Tree, Hash), составных индексов и проблем избыточного индексирования находится в основной заметке: **[Индексы в базах данных](../../Concepts/indexes.md)**.

### Специализированные типы индексов в PostgreSQL

Помимо стандартного **B-Tree**, PostgreSQL предлагает несколько специализированных типов индексов для конкретных задач:

- **GIN (Generalized Inverted Index):** Эффективен для поиска внутри "составных" значений. Основные сценарии:
  - Полнотекстовый поиск.
  - Поиск элементов в массивах (`array`).
  - Поиск ключей и пар "ключ-значение" в `jsonb`.

- **GiST (Generalized Search Tree):** Обобщенное дерево поиска, которое позволяет реализовывать сложные типы индексов для нестандартных данных.
  - Основной пример — **геопространственные данные** (широта/долгота) с расширением `PostGIS`.

- **BRIN (Block Range Index):** Очень компактный индекс, который хранит только минимальное и максимальное значение для большого диапазона блоков на диске.
  - Идеален для очень больших таблиц, где данные физически упорядочены (например, таблицы с временными рядами, где `created_at` монотонно возрастает).

### Поиск неиспользуемых индексов

Ненужные индексы замедляют запись и занимают место. Их следует периодически находить и удалять.
> Запрос для поиска неиспользуемых индексов и детальное описание проблемы доступны в основной заметке **[здесь](../../Concepts/indexes.md#поиск-и-удаление-неиспользуемых-индексов)**.

## Настройка параметров сервера

Ключевые параметры в `postgresql.conf`, влияющие на производительность:

- **`shared_buffers`:** Основной кэш PostgreSQL для страниц данных и индексов. Рекомендуемое значение — 25% от доступной оперативной памяти (RAM) для выделенного сервера.
- **`work_mem`:** Объем памяти, выделяемый для внутренних операций сортировки, хеширования, `GROUP BY`. Этот объем выделяется на каждую операцию, поэтому слишком большое значение может быстро исчерпать RAM при большом количестве одновременных запросов.
- **`maintenance_work_mem`:** Память для служебных операций, таких как `VACUUM`, `CREATE INDEX`, `ALTER TABLE`. Можно устанавливать значительно выше, чем `work_mem`. **Совет:** этот параметр можно временно увеличить для текущей сессии перед выполнением тяжелой операции: `SET maintenance_work_mem = '1GB';`.
- **`effective_cache_size`:** Подсказка для планировщика о том, сколько памяти доступно для кэширования данных операционной системой. Помогает планировщику точнее оценивать стоимость `Index Scan`. Рекомендуемое значение — 50-75% от RAM.

### Управление конфигурацией и инструменты

-   **Файлы конфигурации**:
    -   `postgresql.conf`: Основной конфигурационный файл. Редактировать его напрямую не рекомендуется, так как это усложняет автоматизацию и контроль версий.
    -   `postgresql.auto.conf`: Этот файл имеет более высокий приоритет и управляется автоматически. Изменения в него вносятся с помощью команды `ALTER SYSTEM`.
-   **`ALTER SYSTEM`**: Это предпочтительный способ изменения параметров конфигурации. Команда безопасно записывает изменения в `postgresql.auto.conf`, которые применяются после перезагрузки конфигурации (`pg_reload_conf()`) или сервера.
    ```sql
    ALTER SYSTEM SET work_mem = '16MB';
    ```
-   **Инструменты для тюнинга**: Для первоначальной настройки можно использовать онлайн-калькуляторы, которые предлагают базовые значения параметров на основе характеристик вашего сервера.
    -   **PGTune**
    -   **PGConfig.org**

    **Важно:** Эти инструменты дают лишь отправную точку. Оптимальные значения всегда зависят от конкретной рабочей нагрузки и требуют дальнейшего мониторинга и корректировки.

## Мониторинг эффективности кэша

Один из ключевых показателей производительности — это **коэффициент попадания в кэш (cache hit rate)**. Он показывает, какая доля запрошенных данных была найдена в кэше PostgreSQL (`shared_buffers`), а не прочитана с диска.

**Целевой показатель:** > 99% для баз данных с устоявшимся набором "горячих" данных.

Получить текущее значение можно с помощью следующего запроса:

```sql
SELECT
    'cache hit rate' AS metric,
    (sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read))) * 100 AS value
FROM
    pg_statio_user_tables;
```

Низкий показатель может свидетельствовать о недостаточном размере `shared_buffers` или о запросах, которые постоянно обращаются к "холодным" данным.

## `VACUUM` и раздувание таблиц (Bloat)

**Автовакуум (Autovacuum)** — это фоновый процесс, критически важный для поддержания производительности и эффективности PostgreSQL. Он отвечает за:
*   Сбор статистики по таблицам для планировщика запросов.
*   Очистку "мертвых" строк (`dead tuples`), оставшихся после `UPDATE` или `DELETE` операций (что является следствием механизма многоверсионности MVCC).
*   Предотвращение зацикливания счетчиков транзакций (transaction ID wraparound).

Автовакуум должен быть всегда включен и правильно настроен.

PostgreSQL использует модель MVCC (Multi-Version Concurrency Control). При операции `UPDATE` или `DELETE` старая версия строки не удаляется физически, а лишь помечается как неактуальная ("мертвая" или `dead tuple`). `UPDATE` по своей сути является атомарной комбинацией `INSERT` (новой версии строки) и `DELETE` (пометки старой версии). Со временем это приводит к "раздуванию" (bloat) таблиц и индексов, когда файл таблицы на диске содержит много мусора и занимает больше места, чем необходимо.

Процесс `VACUUM` освобождает это место для повторного использования новыми строками. `autovacuum` — фоновый процесс, который автоматически выполняет `VACUUM` и `ANALYZE` (сбор статистики для планировщика). Агрессивность `autovacuum` можно настраивать.

Отслеживать количество "мертвых" кортежей можно с помощью `pg_stat_user_tables`:
```sql
SELECT relname, n_live_tup, n_dead_tup, last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables
ORDER BY n_dead_tup DESC;
```

## Мониторинг и диагностика

### Ключевые системные представления

-   **`pg_stat_activity`**: Показывает все активные процессы (сессии), подключенные к серверу. Это основной инструмент для ответа на вопрос "что сейчас происходит в базе?".
    -   `state`: Статус процесса. Особое внимание стоит уделить `active` (выполняет запрос) и `idle in transaction` ("зависшая" транзакция, которая удерживает блокировки).
    -   `wait_event_type` / `wait_event`: Показывает, чего ожидает процесс (например, `IO`, `Lock`).
    -   **Поиск и завершение "тяжелых" запросов**:
        ```sql
        -- Найти запросы, выполняющиеся дольше 5 минут
        SELECT pid, age(clock_timestamp(), query_start), usename, query
        FROM pg_stat_activity
        WHERE state = 'active' AND (clock_timestamp() - query_start) > interval '5 minutes';
        
        -- "Мягко" завершить запрос (рекомендуется)
        SELECT pg_cancel_backend(PID);
        
        -- "Жестко" завершить сессию (используется, если pg_cancel_backend не помогает)
        SELECT pg_terminate_backend(PID);
        ```

-   **`pg_stat_statements`**: Мощное расширение (требует добавления в `shared_preload_libraries`), которое отслеживает статистику выполнения всех запросов в системе. Позволяет найти наиболее "дорогие" запросы по совокупному времени выполнения, количеству вызовов, объему I/O.
    ```sql
    -- Включить расширение
    CREATE EXTENSION pg_stat_statements;
    
    -- Топ-10 запросов по общему времени выполнения
    SELECT total_exec_time, calls, mean_exec_time, query
    FROM pg_stat_statements
    ORDER BY total_exec_time DESC
    LIMIT 10;
    ```

-   **`pg_stat_monitor`**: Это более продвинутая альтернатива `pg_stat_statements`. `pg_stat_monitor` собирает не только статистику, но и **планы выполнения запросов**, а также предоставляет более детальную разбивку по метрикам и может агрегировать статистику в разрезе времени (например, по минутам или часам). Это делает его очень мощным инструментом для глубокого анализа производительности.

### Автоматический анализ медленных запросов (`auto_explain`)

Расширение **`auto_explain`** — это встроенный инструмент для автоматического логирования планов выполнения медленных запросов. Вместо того чтобы вручную запускать `EXPLAIN` на запросах, которые вы *подозреваете* в медленной работе, `auto_explain` делает это за вас для реально выполняющихся запросов.

**Настройка в `postgresql.conf`:**
```ini
# Загружаем модуль
shared_preload_libraries = 'pg_stat_statements, auto_explain'

# Включаем логирование планов для запросов, выполняющихся дольше 250 мс
auto_explain.log_min_duration = '250ms'

# Чтобы не перегружать систему, можно логировать только часть медленных запросов
auto_explain.log_sample_rate = 0.5 # 50% от всех запросов, превысивших порог
```
Планы выполнения будут записываться в стандартный лог PostgreSQL. Эти логи можно собирать с помощью [Grafana Alloy](../../Grafana/grafana_alloy_overview.md) или Promtail и анализировать в [Loki](../../Loki/loki_overview.md), что позволяет централизованно отслеживать появление медленных запросов в системе.

### Визуализация планов запросов

Чтение текстового вывода `EXPLAIN` может быть затруднительным. Веб-инструменты помогают визуализировать план в виде дерева, подсвечивая самые "дорогие" узлы.

-   **[explain.depesz.com](https://explain.depesz.com/)**: Популярный бесплатный инструмент. Просто скопируйте в него вывод `EXPLAIN ANALYZE`.

### Расширения для профилирования

-   **`pg_profile`**: Расширение, которое периодически собирает статистику и генерирует подробные отчеты о производительности, аналогичные AWR (Automatic Workload Repository) в Oracle.

### Связь с Full-Stack Observability

Описанные выше инструменты (`pg_stat_activity`, `pg_stat_statements`, `auto_explain`) предоставляют мощные средства для анализа производительности **на уровне базы данных**. Однако в современных распределенных системах этого недостаточно. Чтобы понять, какая именно бизнес-операция в приложении привела к появлению медленного SQL-запроса, необходимо связать телеметрию приложения с телеметрией базы данных.

Этот подход называется **Full-Stack Observability**. Он достигается с помощью сквозной трассировки, где контекст трассировки (`trace_id`) из приложения передается вплоть до SQL-запроса.

-   Для получения полной картины ознакомьтесь с заметкой **[Full-Stack Observability для PostgreSQL](./observability.md)**.
-   Ключевой технологией для реализации сквозной трассировки на уровне PostgreSQL является расширение **pg_tracing**.

## Другие техники

- **CTE (Common Table Expressions):** Использование конструкции `WITH ... AS (...)` может улучшить читаемость запроса. В некоторых случаях PostgreSQL материализует результат CTE, что может как ускорить (если результат используется многократно), так и замедлить запрос. CTE также являются основным способом для написания **рекурсивных запросов** (например, для обхода иерархических структур).
- **Вынос WAL на отдельный диск:** Размещение журнала предзаписи (Write-Ahead Log) на отдельном физическом диске может снизить дисковую нагрузку на основной массив.
- **Оптимизация типов данных:** Используйте наиболее подходящие и компактные типы данных (`integer` вместо `bigint`, если возможно; `jsonb` вместо `json` для более быстрого доступа к элементам).
