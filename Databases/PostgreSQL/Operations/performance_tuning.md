# Оптимизация производительности PostgreSQL

## Определения

**MVCC (Multi-Version Concurrency Control)** — механизм управления параллельным доступом, при котором для каждого изменения строки создается новая версия. Подробности — **[Concurrency and Locking](../Concepts/concurrency_and_locking.md)**.

**Bloat** — раздувание таблиц из-за накопления "мёртвых" кортежей (dead tuples) — прямое следствие работы MVCC.

**VACUUM** — процесс очистки "мёртвых" кортежей для повторного использования пространства. `autovacuum` — фоновый процесс автоматической очистки.

**План выполнения (Execution Plan)** — последовательность операций (сканирование, соединения, сортировка), которую PostgreSQL планирует выполнить для запроса. `EXPLAIN ANALYZE` выполняет запрос и показывает реальное время каждого шага.

**Cache hit rate** — доля запрошенных данных, найденных в кэше (`shared_buffers`), а не прочитанных с диска. Целевой показатель для горячих данных: >99%.

**Индекс** — структура данных для ускорения доступа к строкам таблицы. См. **[Индексы в PostgreSQL](../Concepts/indexes.md)**.

## Основные концепции

### MVCC и VACUUM

PostgreSQL использует MVCC: при `UPDATE` или `DELETE` старая версия строки помечается как "мёртвая" (dead tuple). Со временем это приводит к раздуванию (bloat) таблиц и индексов.

**Autovacuum** критически важен для:

- Очистки dead tuples (предотвращение раздувания).
- Сбора статистики для планировщика (`ANALYZE`).
- Предотвращения зацикливания ID транзакций (transaction ID wraparound).

Механизмы блокировок и работы MVCC детально описаны в **[Concurrency and Locking](../Concepts/concurrency_and_locking.md)**.

### Типы сканирования

| Тип | Описание | Когда возникает |
| :--- | :--- | :--- |
| **Seq Scan** | Последовательное чтение таблицы. | Нет индекса или чтение всей таблицы быстрее. |
| **Index Scan** | Поиск по индексу с переходом к строке таблицы. | Данные найдены через индекс, высокая селективность. |
| **Index Only Scan** | Чтение только индекса без обращения к таблице. | Все запрашиваемые колонки входят в индекс. |
| **Bitmap Scan** | Комбинирование нескольких индексов через битовую карту. | Фильтрация по нескольким колонкам с разными индексами. |

**Index Only Scan** является самым производительным. **Bitmap Scan** эффективнее последовательного чтения при сложной фильтрации.

### Почему PostgreSQL не использует индекс

Планировщик выбирает план с минимальной стоимостью (cost). Основные причины отказа от индекса:

#### 1. Низкая селективность

Если условию удовлетворяет более 5–10% строк, последовательное чтение (`Seq Scan`) обычно выгоднее из-за меньшего объема операций ввода-вывода.

```sql
-- Таблица 10 млн строк, 33% со status = 'new' -> Seq Scan
EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'new';
```

**Решение:** Секционирование (партиционирование), частичные индексы (`WHERE status = 'active'`).

#### 2. Устаревшая статистика

Планировщик опирается на данные `pg_statistic`, собираемые `ANALYZE`. Если статистика неактуальна, планировщик может выбрать неэффективный путь.

**Признаки:** Сильное расхождение между `rows` (оценка) и `actual rows` (реальность) в плане.

**Решение:**

```sql
-- Ручной сбор статистики
ANALYZE table_name;

-- Тюнинг autovacuum для часто меняющихся таблиц
ALTER TABLE orders SET (autovacuum_analyze_scale_factor = 0.05);
```

#### 3. Использование функций в условии

Индекс на колонку не работает, если к ней применена функция в блоке `WHERE`.

```sql
-- Seq Scan (индекс на 'name' не используется)
SELECT * FROM users WHERE lower(name) = 'john';

-- Решение: Индекс на выражение
CREATE INDEX idx_users_lower_name ON users (lower(name));
```

#### 4. Неявное преобразование типов

Если тип данных в условии не совпадает с типом колонки (например, поиск строки в числовом поле), PostgreSQL может переключиться на `Seq Scan`.

### Анализ планов запросов

Для анализа используется команда `EXPLAIN (ANALYZE, BUFFERS)`. Флаг `BUFFERS` показывает работу с кэшем.

**Ключевые показатели:**

- **Cost**: Условная стоимость (startup .. total).
- **Rows**: Ожидаемое количество строк.
- **Actual time**: Реальное время выполнения (только с `ANALYZE`).
- **Buffers**: `Shared hit` (из RAM), `read` (с диска).

### Настройка параметров системы

Базовые параметры конфигурации `postgresql.conf`:

| Параметр | Назначение | Рекомендация |
| :--- | :--- | :--- |
| `shared_buffers` | Кэш страниц данных и индексов. | ~25% от всей RAM. |
| `work_mem` | Память для сортировок и соединений. | 4–16MB (на каждую операцию). |
| `maintenance_work_mem` | Память для `VACUUM` и `CREATE INDEX`. | 512MB–2GB. |
| `effective_cache_size` | Оценка кэша ОС планировщиком. | 50–75% от всей RAM. |

Подробное описание архитектуры памяти — **[Архитектура PostgreSQL](../Concepts/architecture.md#структуры-памяти)**.

## Практические сценарии

### Сценарий 1: Общий анализ производительности

#### 1. Диагностика на уровне ОС

Используйте системные утилиты для выявления узких мест:

- CPU/Memory: `top`, `htop`, `vmstat`.
- Disk I/O: `iostat -xz 1`.
- Ошибки: `dmesg | grep -i oom`.

#### 2. Анализ активности БД

**Поиск долгих запросов:**

```sql
SELECT pid, now() - query_start AS duration, query, state
FROM pg_stat_activity
WHERE state != 'idle' AND now() - query_start > interval '5 minutes';
```

**Анализ самых "дорогих" запросов (pg_stat_statements):**

```sql
SELECT query, calls, total_exec_time, mean_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC LIMIT 10;
```

### Сценарий 2: Оптимизация медленного запроса

1. **Получение плана:** Выполните `EXPLAIN (ANALYZE, BUFFERS) query`.
   - *Предупреждение:* `ANALYZE` выполняет запрос. Будьте осторожны с операциями изменения данных.
2. **Проверка селективности:** Если индекс не используется, проверьте количество возвращаемых строк.
3. **Проверка статистики:** Сравните оценки планировщика с реальными данными. При необходимости выполните `ANALYZE`.
4. **Корректировка индексов:** Проверьте наличие покрывающих (`INCLUDE`) или частичных индексов.
5. **Локальный тюнинг:** При необходимости увеличьте `work_mem` для текущей сессии: `SET work_mem = '64MB';`.

### Сценарий 3: Борьба с раздуванием (Bloat)

Если `autovacuum` не справляется, и таблица сильно раздута:

1. **Проверка уровня раздувания:** Используйте расширение `pgstattuple`.
2. **Пересоздание без блокировок:** Используйте `pg_repack` (требует установки расширения) вместо `VACUUM FULL`, чтобы избежать эксклюзивной блокировки таблицы.

### Сценарий 4: Экспресс-диагностика под нагрузкой

PostgreSQL тормозит — чек-лист мер без замены СУБД. Каждый пункт ведёт к детальному описанию в SSoT.

**1. Найти медленные запросы**
- `EXPLAIN ANALYZE` — план выполнения проблемного запроса. Сравнить `rows` (оценка) и `actual rows` (реальность) для выявления устаревшей статистики. Подробнее — [Сценарий 2](#сценарий-2-оптимизация-медленного-запроса).
- `pg_stat_statements` — топ запросов по `total_exec_time`. Подробнее — [Сценарий 1](#сценарий-1-общий-анализ-производительности).

**2. Индексы на WHERE / JOIN**
- Добавить индексы на колонки, используемые в фильтрации и соединениях.
- Проверить неиспользуемые индексы (`pg_stat_user_indexes WHERE idx_scan = 0`) — они замедляют запись.
- Подробнее — [Индексы в PostgreSQL](../Concepts/indexes.md).

**3. Read replicas — вынести read-only трафик**
- Направить SELECT-запросы на hot standby реплики. Мастер обслуживает только writes.
- **Архитектура:** приложение → HAProxy (проверка `/primary` / `/replica` через API Patroni) → PgBouncer (transaction mode) → PostgreSQL. Подробнее — [Read/Write Split](../Concepts/high_availability.md#балансировка-и-разделение-трафика-readwrite-split), [Read Scaling](../Concepts/scaling.md#масштабирование-чтения-read-scaling-через-реплики).
- Репликация асинхронная — допускается секундный лаг для нетребовательных к свежести запросов.

**4. Connection pooling**
- PgBouncer в **transaction mode** — пул держит постоянные соединения с PG, клиенты занимают их только на время транзакции, а не сессии. Это снижает число одновременных подключений и нагрузку от форков postmaster.
- Подробнее — [Архитектура PostgreSQL](../Concepts/architecture.md#использование-пула-соединений).

**5. Кэшировать hot read запросы через Redis**
- Разместить Redis перед PostgreSQL для часто запрашиваемых, редко меняющихся данных (справочники, сессии, кэш API-ответов).
- **Схема:** приложение → Redis (TTL) → PostgreSQL (прогрев кэша при cache miss).
- Это снижает число SELECT-запросов к PG и read load на диски. Подробнее — [Redis overview](../../../Databases/redis_overview.md).

**6. Партиционирование больших таблиц**
- Разделить large tables по дате (RANGE) — PostgreSQL выполняет **query pruning** (исключение нерелевантных партиций из плана).
- Особенно эффективно для таблиц с фильтрацией по дате и удалением устаревших партиций (DROP вместо DELETE). Подробнее — [Декларативное партиционирование](../Concepts/scaling.md#декларативное-партиционирование).

**7. VACUUM ANALYZE**
- Устаревшая статистика → планировщик выбирает неэффективные планы (Seq Scan вместо Index Scan).
- `ANALYZE table` обновляет статистику. Autovacuum должен успевать обрабатывать часто меняющиеся таблицы. Подробнее — [MVCC и VACUUM](#mvcc-и-vacuum), [Concurrency and Locking](../Concepts/concurrency_and_locking.md).

**8. Тюнинг shared_buffers и work_mem**
- `shared_buffers` = ~25% RAM — кэш страниц данных и индексов.
- `work_mem` = 4–16 MB на операцию (сортировка, hash join) — при множестве одновременных сортировок увеличение может привести к OOM.
- Подробнее — [Настройка параметров системы](#настройка-параметров-системы).
