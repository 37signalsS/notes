# Оптимизация производительности PostgreSQL

## Определения

**Многоверсионность (MVCC, Multi-Version Concurrency Control)** — механизм управления параллельным доступом, при котором для каждого изменения строки создается новая версия. Подробности — [Управление параллелизмом и блокировки](../Concepts/concurrency_and_locking.md).

**Раздувание (Bloat)** — накопление "мертвых" кортежей (dead tuples) в таблицах и индексах, приводящее к неэффективному использованию диска и замедлению запросов.

**Очистка (VACUUM)** — процесс удаления "мертвых" кортежей. `autovacuum` — фоновый процесс автоматической очистки и сбора статистики для планировщика.

**План выполнения (Execution Plan)** — последовательность операций, которую планировщик выбирает для выполнения SQL-запроса. `EXPLAIN ANALYZE` выполняет запрос и показывает реальное время каждого шага.

**Коэффициент попадания в кэш (Cache hit rate)** — доля данных, найденных в `shared_buffers` без обращения к диску. Целевой показатель для "горячих" данных: >99%.

## Основные концепции

### Работа MVCC и влияние на производительность

PostgreSQL использует MVCC: при `UPDATE` старая версия строки помечается как удаленная, а новая вставляется. Это избавляет от блокировок при чтении, но создает нагрузку на диск и требует регулярной очистки (`VACUUM`).

**Задачи Autovacuum:**
- Предотвращение Bloat (освобождение места).
- Актуализация статистики (`ANALYZE`) для выбора правильных планов.
- Предотвращение Transaction ID Wraparound (критическая остановка БД).

### Методы доступа к данным (Scans)

| Тип | Описание | Применение |
| :--- | :--- | :--- |
| **Seq Scan** | Последовательное чтение всей таблицы. | Маленькие таблицы или выборка >15% данных. |
| **Index Scan** | Поиск в индексе + переход к строке таблицы. | Точечные запросы, высокая селективность. |
| **Index Only Scan** | Чтение данных напрямую из индекса. | Самый быстрый. Все колонки в индексе. |
| **Bitmap Scan** | Карта страниц по индексу + чтение страниц. | Сложные фильтры, средняя селективность. |

### Причины игнорирования индексов

1. **Низкая селективность:** если условие возвращает слишком много строк, планировщик выберет `Seq Scan`.
2. **Устаревшая статистика:** без актуальных данных `ANALYZE` планировщик ошибается в оценке количества строк.
3. **Функции в условии:** `WHERE upper(name) = 'ADMIN'` не использует индекс на `name`. *Решение: индекс по выражению.*
4. **Неявное приведение типов:** сравнение разных типов данных заставляет БД выполнять преобразование для каждой строки.
5. **Тюнинг стоимости чтения:** если `random_page_cost` слишком велик (по умолчанию 4.0), планировщик будет избегать индексов даже на SSD. *Решение: снизить до 1.1 для SSD.*

### Анализ планов запросов

Команда `EXPLAIN (ANALYZE, BUFFERS)` — основной инструмент диагностики.

**На что смотреть:**
- **Actual time:** общее время выполнения шага.
- **Rows (Estimation vs Actual):** если разница велика — статистика устарела.
- **Buffers (Shared Hit/Read):** если много `Read`, значит данные читаются с диска, не помещаясь в `shared_buffers`.

## Практические сценарии

### Сценарий 1: Базовый тюнинг параметров (postgresql.conf)

| Параметр | Рекомендация | Комментарий |
| :--- | :--- | :--- |
| `shared_buffers` | 25% от всей RAM | Основной кэш страниц. |
| `work_mem` | 4MB - 64MB | Память на одну операцию (сортировка/хэш). |
| `maintenance_work_mem` | 512MB - 2GB | Память для VACUUM и создания индексов. |
| `effective_cache_size` | 75% от всей RAM | Оценка кэша ОС для планировщика. |
| `random_page_cost` | 1.1 (SSD) / 4.0 (HDD) | Стоимость случайного чтения. |
| `max_parallel_workers` | Кол-во ядер CPU | Лимит на параллельное выполнение. |

### Сценарий 2: Оптимизация тяжелых запросов

1. **Поиск:** расширение **`pg_stat_statements`** является основным инструментом для анализа активности:
    - Собирает статистику по всем выполненным запросам (частота, суммарное время, среднее время).
    - Позволяет выследить запросы, наиболее сильно нагружающие систему, для их последующей оптимизации.
2. **Анализ:** `EXPLAIN (ANALYZE, BUFFERS)` для проблемного запроса.
3. **Индексация:** добавление пропущенных индексов (включая `INCLUDE` индексы для Index Only Scan).
4. **Статистика:** если планировщик ошибается на коррелирующих колонках (например, город и регион), используйте `CREATE STATISTICS`.
5. **JIT:** для длинных аналитических запросов JIT полезен, для коротких OLTP его лучше отключить (`jit = off`).

### Сценарий 3: Борьба с раздуванием (Bloat)

Если `autovacuum` не справляется (например, при массовых ночных апдейтах):
1. **Мониторинг:** использование `pgstattuple` для оценки процента "мертвых" строк.
2. **Тюнинг:** снижение `autovacuum_vacuum_scale_factor` до 0.01 для больших таблиц.
3. **Обслуживание:** использование расширения **`pg_repack`**. Оно позволяет пересоздать таблицу и индексы онлайн, удаляя мертвые строки и дефрагментируя данные без эксклюзивной блокировки (в отличие от `VACUUM FULL`).
    - **Алгоритм работы:**
        1.  Создается временная «чистая» таблица-копия и индексы к ней.
        2.  Все актуальные данные копируются в новую таблицу.
        3.  Специальный триггер отслеживает и накапливает изменения в оригинальной таблице.
        4.  Накопленные изменения «догоняются» в новую таблицу.
        5.  Происходит быстрая подмена имен таблиц в системном каталоге.
        6.  Старый файл с «раздутыми» данными удаляется.
    - **Результат:** уменьшение размера данных на диске и ускорение доступа без простоя для приложения.

### Инструменты продвинутой оптимизации
*   **auto_explain:** автоматически логирует планы выполнения медленных запросов без необходимости ручного запуска `EXPLAIN`.
*   **hypopg:** позволяет создавать "гипотетические" индексы, которые не занимают места на диске. Это помогает оценить, выберет ли планировщик индекс, до его реального создания.
*   **pg_hint_plan:** позволяет вручную управлять планом выполнения запроса, если планировщик ошибается и стандартные методы (статистика, индексы) не помогают.

### Сценарий 4: Чек-лист экспресс-диагностики (SRE)

Когда база "тормозит" прямо сейчас:

**1. Инфраструктурный слой (ОС)**
- Проверить `htop`. Искать процессы со 100% CPU.
- Проверить `iostat -xz 1`. Если `%util` > 80% — дисковая подсистема перегружена.
- Проверить `dmesg` на предмет работы OOM-killer.

**2. Слой СУБД (Активность)**
- Найти долгие запросы:
  ```sql
  SELECT pid, now() - query_start as duration, query 
  FROM pg_stat_activity 
  WHERE state != 'idle' AND now() - query_start > interval '10s';
  ```
- Проверить блокировки (`pg_locks` + `pg_stat_activity`).
- Изучить топ по `pg_stat_statements`.

**3. Быстрые меры (Mitigation)**
- **Terminate:** принудительно завершить "зависшие" сессии через `pg_terminate_backend(pid)`.
- **Analyze:** если план запроса явно плохой — выполнить `ANALYZE` для затронутых таблиц.
- **Index:** если не хватает очевидного индекса — создать его с флагом `CONCURRENTLY`.
- **Scaling:** если нагрузка на чтение велика — переключить часть трафика на Read Replicas.
