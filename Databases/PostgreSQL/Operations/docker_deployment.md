# Развертывание PostgreSQL в Docker

## Определения

*   **Образ (Image):** Шаблон файловой системы и параметров запуска. Например, `postgres:16.3`. Является неизменяемым.
*   **Контейнер (Container):** Работающий экземпляр образа. Является изолированным процессом со своей собственной сетью и файловой системой.
*   **Том (Volume):** Специальная директория для постоянного хранения данных, которая "переживает" удаление контейнера. Управляется Docker.
*   **Сеть (Network):** Виртуальная сеть, позволяющая контейнерам коммуницировать друг с другом и с внешним миром.

## Основные концепции

### Сохранение данных (Volumes)

**Критически важно:** Данные внутри контейнера эфемерны. При `docker rm` (удалении контейнера) все данные теряются. При `docker stop/start` данные сохраняются, но этот подход не для production. Для надежного хранения используйте **тома (volumes)**.

Том создается и монтируется в директорию `/var/lib/postgresql/data` внутри контейнера. Теперь данные переживут удаление контейнера.

```bash
# Пример монтирования тома
-v pg-data:/var/lib/postgresql/data 
```

### Сеть и доступ к базе данных

По умолчанию Docker использует сеть `bridge`. Для изоляции и удобства обращения по именам лучше создавать пользовательские сети. Контейнеры в одной сети могут обращаться друг к другу по именам.

Для внешнего доступа к базе данных порт `5432` контейнера необходимо "пробросить" на хост-машину.

### Инициализация базы данных скриптами

Официальный образ PostgreSQL позволяет автоматически выполнять SQL и shell-скрипты при первом запуске контейнера. Для этого их нужно поместить в директорию `/docker-entrypoint-initdb.d`. Скрипты (`.sh`, `.sql`) будут выполнены в алфавитном порядке. Это отличный способ для создания пользователей, баз данных, схем и т.д.

### Безопасность

#### Доверенные и минимальные образы
Используйте только официальные образы (`postgres`) или образы из доверенного внутреннего registry. Образы из неизвестных источников могут содержать уязвимости или вредоносный код.

**Рекомендации:**
*   **Минимальные образы:** Отдавайте предпочтение минимальным образам (например, на базе Alpine), чтобы уменьшить поверхность атаки, так как они содержат меньше предустановленных пакетов и утилит.
*   **Закрепление версий:** Всегда используйте конкретные теги версий (например, `postgres:16.3`) вместо `latest`, чтобы обеспечить воспроизводимость и избежать неожиданных обновлений с потенциальными уязвимостями.

#### Ограничение сетевого доступа
Порты базы данных **никогда не должны быть напрямую доступны из интернета**. Доступ к PostgreSQL должен осуществляться через:
*   **Внутреннюю сеть Docker:** Для взаимодействия между сервисами в Docker Compose.
*   **Прокси/Балансировщик:** Например, PgBouncer, который может выступать в роли шлюза.
*   **Фаервол:** Ограничивайте доступ только с доверенных IP-адресов или подсетей.
*   **VPN/SSH-туннели:** Для административного доступа.

При использовании `docker-compose.yml` тщательно контролируйте секцию `ports`, пробрасывая только необходимые порты и только для внутренних нужд, если это возможно.

#### `pg_hba.conf`: Аутентификация `trust` и другие настройки

По умолчанию официальный образ использует метод аутентификации `trust` для всех подключений. Это означает, что **любой может подключиться к базе данных без пароля**. Для production это необходимо исправить, смонтировав в контейнер собственный файл `pg_hba.conf` с более строгими правилами (`md5` или `scram-sha-256`).

#### Запуск от имени непривилегированного пользователя (Non-root)
По умолчанию многие образы Docker запускают процессы от имени пользователя `root` внутри контейнера. Это может быть небезопасно. 
*   **Рекомендации:** Используйте образы, которые по умолчанию запускаются от имени непривилегированного пользователя. Официальный образ `postgres` уже следует этому правилу.

#### Управление конфигурацией
Конфигурационные файлы, содержащие чувствительные данные или специфические настройки, следует монтировать в контейнер как тома (`-v`) или использовать Docker Secrets/Config, а не встраивать их непосредственно в образ.

## Практические сценарии

### Сценарий 1: Запуск и управление standalone-сервером

Хотя команда `docker run` автоматически загрузит образ, если его нет локально, хорошей практикой является предварительная загрузка с помощью `docker pull`.
```bash
docker pull postgres:16.3
```

Команда для запуска контейнера, включающая имя, сеть, пароль, том для данных и проброс порта:
```bash
# 1. Создаем сеть
docker network create pg-net

# 2. Запускаем контейнер
docker run --name pg-server \
  --network pg-net \
  -e POSTGRES_PASSWORD=mysecretpassword \
  -p 5432:5432 \
  -v pg-data:/var/lib/postgresql/data \
  -v ./my_pg_hba.conf:/var/lib/postgresql/data/pg_hba.conf \
  -v ./init-scripts:/docker-entrypoint-initdb.d \
  -d postgres:16.3
```
*   `--name pg-server`: Задает имя контейнера для удобства обращения.
*   `--network pg-net`: Подключает контейнер к созданной сети.
*   `-e POSTGRES_PASSWORD=...`: Устанавливает переменную окружения для пароля.
*   `-p 5432:5432`: Пробрасывает порт с хоста в контейнер.
*   `-v pg-data:/...`: Монтирует том для хранения данных.
*   `-v ./my_pg_hba.conf:/...`: Монтирует кастомный файл конфигурации безопасности.
*   `-v ./init-scripts:/...`: Монтирует директорию со скриптами инициализации.
*   `-d`: Запускает контейнер в фоновом режиме (detached).

### Сценарий 2: Подключение и администрирование

**Подключение через `docker exec`**:
```bash
# 1. Запустить интерактивную сессию psql от имени пользователя postgres
docker exec -it pg-server psql -U postgres

# 2. Или сначала запустить shell в контейнере, а затем psql
docker exec -it pg-server bash
# > su - postgres
# > psql
```

**Использование временного клиент-контейнера (удобный паттерн)**:
```bash
# Запускаем временный контейнер, который подключится к pg-server по сети pg-net
# --rm - автоматически удалит контейнер после выхода
docker run --rm -it --network=pg-net postgres:16.3 psql -h pg-server -U postgres
```

**Инспекция контейнера**:
```bash
# Показывает всю информацию о контейнере, включая IP-адрес в сети Docker
docker inspect pg-server
```

### Сценарий 3: Развертывание стека с Docker Compose

Для управления многоконтейнерными приложениями используйте `docker-compose.yml`.

**Пример `docker-compose.yml` для приложения и базы данных:**
```yaml
version: '3.8'

services:
  db:
    image: postgres:16.3
    restart: always
    networks:
      - app-net
    environment:
      - POSTGRES_USER=myuser
      - POSTGRES_PASSWORD=mysecretpassword
      - POSTGRES_DB=myapp
    ports:
      - "5432:5432" # В production-среде рекомендуется не пробрасывать порт напрямую.
    volumes:
      - db-data:/var/lib/postgresql/data
      - ./init-scripts:/docker-entrypoint-initdb.d # монтируем init-скрипты
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U myuser -d myapp"]
      interval: 10s
      timeout: 5s
      retries: 5

  app:
    build: .
    networks:
      - app-net
    ports:
      - "8080:80"
    depends_on:
      db:
        condition: service_healthy
    environment:
      - DATABASE_URL=postgresql://myuser:mysecretpassword@db:5432/myapp

volumes:
  db-data:

networks:
  app-net:
    driver: bridge
```
**Важные аспекты межсервисного взаимодействия:**
*   **Имена сервисов как DNS-имена:** В рамках одной Docker-сети сервисы могут обращаться друг к другу по их именам (`db` для базы данных).
*   **Внутренние и внешние порты:** При обращении из одного сервиса к другому внутри той же сети всегда используйте внутренний порт контейнера (`db:5432`).
*   **`healthcheck` и `depends_on`:** `healthcheck` позволяет Docker'у проверять, готов ли PostgreSQL принимать соединения. `depends_on` с условием `service_healthy` гарантирует, что сервис `app` запустится только после этого.

## Дополнительная информация

### Расширение стека инструментами мониторинга и управления

Для полноценного мониторинга и управления можно добавить в `docker-compose.yml` сервисы Prometheus, Grafana, PgAdmin и PgBouncer.

**Пример `docker-compose.monitoring.yml`:**
```yaml
# ... services, volumes, networks ...
  pg_exporter:
    image: prometheuscommunity/postgres-exporter:v0.15.0
    restart: always
    environment:
      DATA_SOURCE_NAME: "postgresql://myuser:mysecretpassword@postgres:5432/myapp?sslmode=disable"
    networks:
      - monitor-net
    depends_on:
      - postgres

  prometheus:
    image: prom/prometheus:v2.51.2
    # ...
    ports: ["9090:9090"]

  grafana:
    image: grafana/grafana:10.4.2
    # ...
    ports: ["3000:3000"]
```

**Пример `docker-compose.tools.yml`:**
```yaml
# ... services, volumes, networks ...
  pgbouncer:
    image: edoburu/pgbouncer:1.22.1
    restart: always
    environment:
      DB_HOST: postgres
      # ...
    ports: ["6432:6432"]
    depends_on:
      - postgres

  pgadmin:
    image: dpage/pgadmin4:8.5
    restart: always
    environment:
      PGADMIN_DEFAULT_EMAIL: admin@example.com
      # ...
    ports: ["8080:80"]
    depends_on:
      - postgres
```
Для этих примеров также потребуются файлы конфигурации для `prometheus.yml` и `grafana/provisioning/`.
