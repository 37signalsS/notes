# Производительность запросов и индексы в SQLite

**Актуально для:** SQLite 3.45+ (отдельные возможности указаны с версиями)

## Определения

*   **EXPLAIN QUERY PLAN** — префикс, заставляющий SQLite вывести план выполнения запроса без его фактического выполнения. Показывает, какие сканирования и индексы будут использованы.
*   **Query Planner (планировщик)** — компонент SQLite, выбирающий стратегию выполнения запроса на основе оценки стоимости (cost-based). Использует статистику из `sqlite_stat1`.
*   **Covering index (покрывающий индекс)** — индекс, содержащий все колонки, нужные запросу. Запрос читает только индекс, без обращения к таблице.
*   **Partial index (частичный индекс)** — индекс, построенный только по строкам, удовлетворяющим условию `WHERE` (SQLite 3.8.0+).
*   **WITHOUT ROWID table** — таблица, где первичный ключ является rowid, а данные хранятся в порядке PK (SQLite 3.8.2+).
*   **ANALYZE** — команда, собирающая статистику распределения значений в индексах в таблицу `sqlite_stat1`.
*   **PRAGMA optimize** — автоматический аналог ANALYZE: запускает анализ только для таблиц, где он даст выигрыш (SQLite 3.18.0+; рекомендуемый способ с 3.46.0).
*   **Expression index** — индекс на выражении (например, `upper(name)`), позволяющий планировщику использовать индекс для запросов с функциями.

## Базовые концепции

### Как работает планировщик

SQLite использует cost-based планировщик. Для каждого запроса он оценивает стоимость различных стратегий (полное сканирование, поиск по индексу, поиск по rowid) и выбирает наименьшую. Оценки основаны на:

*   Статистике из `sqlite_stat1` (если есть — после ANALYZE)
*   Структуре индексов (порядок колонок)
*   Условиях WHERE (равенства, диапазоны)

Без статистики планировщик работает по эвристикам и может выбрать неоптимальный план на больших таблицах.

### Структура индекса

Индекс SQLite — B-tree, где ключ состоит из колонок индекса + rowid таблицы (для обычных таблиц). Порядок колонок в индексе критичен: индекс `idx(a, b)` обслуживает запросы по `a`, по `(a, b)`, но не по `b` в одиночку (правило левого префикса).

**Покрывающий индекс**: если в запросе участвуют только колонки индекса, SQLite читает только индекс — в плане это `USING COVERING INDEX`. Это самый быстрый вариант, так как исключает обращение к таблице.

**Частичный индекс**: `CREATE INDEX idx ON t(a) WHERE active = 1;` — индекс содержит только активные строки. Меньше размер, быстрее запись. Планировщик использует его, когда условие запроса гарантирует `active = 1`.

**WITHOUT ROWID**: `CREATE TABLE t(a, b, PRIMARY KEY(a, b)) WITHOUT ROWID;` — данные хранятся в порядке PK. Эффективно для таблиц, где основной доступ — по составному PK; вторичные индексы содержат PK вместо rowid.

### Когда индекс НЕ используется

*   Функция на индексированной колонке: `WHERE upper(name) = 'X'` (решение — expression index)
*   Неявное приведение типов: колонка TEXT, запрос с числом (или наоборот)
*   `LIKE` с ведущим wildcard: `LIKE '%x'` (но `LIKE 'x%'` использует индекс)
*   Арифметика над колонкой: `WHERE col + 1 = 5`
*   Условия `NOT`, `OR` по разным колонкам (часто)
*   Низкая селективность: планировщик считает полное сканирование дешевле
*   Несовпадение COLLATE между колонкой и выражением

## Практические сценарии

### 1. Чтение плана запроса

```sql
EXPLAIN QUERY PLAN SELECT * FROM events WHERE host = 'web-01';
```

```
QUERY PLAN
`--SEARCH events USING INDEX idx_events_host (host=?)
```

Ключевые маркеры в выводе:

| Маркер | Значение |
| :--- | :--- |
| `SCAN t` | Полное сканирование таблицы — потенциальная проблема на больших таблицах |
| `SEARCH t USING INDEX idx (col=?)` | Поиск по индексу |
| `SEARCH t USING COVERING INDEX idx (...)` | Покрывающий индекс — оптимально |
| `SEARCH t USING INTEGER PRIMARY KEY (rowid=?)` | Прямой доступ по rowid — самый быстрый |
| `SEARCH t USING AUTOMATIC PARTIAL COVERING INDEX` | Временный индекс, созданный на время запроса — сигнал, что нужен постоянный индекс |

В CLI можно включить автоматический вывод планов:

```bash
sqlite3 data.db ".eqp on" "SELECT * FROM events WHERE host='web-01';"
# → QUERY PLAN
#   `--SEARCH events USING INDEX idx_events_host (host=?)
```

### 2. Экспериментальный подбор индексов (.expert)

```bash
# .expert анализирует набор запросов и предлагает индексы
sqlite3 data.db ".expert" "SELECT * FROM events WHERE host='web-01' AND ts > 1700000000;"
```

Команда помечена EXPERIMENTAL, но полезна для первичной оценки.

### 3. Сбор статистики (ANALYZE / PRAGMA optimize)

```sql
-- Полный анализ (может быть долгим на больших БД)
ANALYZE;

-- Рекомендуемый способ (с 3.46.0): анализ только где выгоден
PRAGMA optimize;

-- Ограничить глубину анализа для ускорения (3.32.0+)
PRAGMA analysis_limit = 1000;

-- Посмотреть собранную статистику
SELECT * FROM sqlite_stat1;
-- → events|idx_events_host|1000000 rows, 50 distinct values
```

`PRAGMA optimize` безопасно запускать по расписанию (cron): он сам решает, нужна ли переоценка.

### 4. Инспекция индексов

```sql
-- Индексы таблицы (unique, origin, partial)
PRAGMA index_list('events');

-- Колонки индекса
PRAGMA index_info('idx_events_host');

-- Расширенная информация (включая auxiliary-колонки, DESC, collation)
PRAGMA index_xinfo('idx_events_host');
```

### 5. Анализ занимаемого места (dbstat)

```sql
-- Размер по таблицам и индексам
SELECT name, sum(pgsize) AS bytes
FROM dbstat GROUP BY name ORDER BY 2 DESC;

-- Эффективность упаковки страниц таблицы (ближе к 100% — лучше)
SELECT sum(pgsize - unused) * 100.0 / sum(pgsize) AS efficiency
FROM dbstat WHERE name = 'events';

-- Средний fan-out (чем выше, тем меньше глубина B-tree)
SELECT avg(ncell) FROM dbstat WHERE name = 'events' AND pagetype = 'internal';
```

Требуется сборка с `SQLITE_ENABLE_DBSTAT_VTAB` (проверить: `PRAGMA compile_options;`). В CLI есть обёртка: `sqlite3 data.db ".dbstat"`.

## Операции и команды

| Задача | Команда |
| :--- | :--- |
| План запроса | `EXPLAIN QUERY PLAN SELECT ...;` |
| План в CLI (авто) | `sqlite3 db ".eqp on" "SELECT ...;"` |
| Подбор индексов | `sqlite3 db ".expert" "SELECT ...;"` |
| Сбор статистики | `ANALYZE;` / `PRAGMA optimize;` |
| Лимит анализа | `PRAGMA analysis_limit = 1000;` |
| Статистика | `SELECT * FROM sqlite_stat1;` |
| Индексы таблицы | `PRAGMA index_list('table');` |
| Колонки индекса | `PRAGMA index_info('idx');` / `PRAGMA index_xinfo('idx');` |
| Размеры по объектам | `SELECT name, sum(pgsize) FROM dbstat GROUP BY name;` |
| Размеры в CLI | `sqlite3 db ".dbstat"` |

## Устранение неполадок

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `SCAN` в плане на большой таблице | Нет индекса по условию | Создать индекс; проверить порядок колонок |
| `AUTOMATIC INDEX` в плане | Индекса нет, SQLite построил временный | Создать постоянный индекс |
| Индекс есть, но планировщик игнорирует | Низкая селективность / устаревшая статистика | `PRAGMA optimize`; partial/covering index |
| Функция в WHERE обходит индекс | Функция на колонке | Expression index: `CREATE INDEX i ON t(upper(name));` |
| `LIKE '%x'` медленный | Ведущий wildcard | FTS5 или перестроить запрос |
| План не изменился после ANALYZE | Статистика не пересобрана | `PRAGMA optimize;` повторно |

## Рекомендации SRE

*   Запускайте `PRAGMA optimize;` по расписанию (например, ежедневно в cron) — это дешевле и безопаснее полного `ANALYZE`.
*   Проверяйте планы (`EXPLAIN QUERY PLAN`) после изменений схемы и после роста таблиц в разы.
*   Для запросов с функциями над колонками используйте expression index.
*   Для высоконагруженных read-запросов проектируйте покрывающие индексы.
*   `.eqp on` в CLI — быстрый способ проверить план в процессе отладки.
