# SQLite для SRE: WAL, Конкурентность и Эксплуатация

## Определения

*   **WAL (Write-Ahead Logging):** Режим журналирования, при котором изменения записываются в отдельный файл `-wal`, что позволяет читателям не блокировать писателей (и наоборот).
*   **Checkpoint (Чекпоинт):** Процесс переноса изменений из WAL-файла в основной файл базы данных (`.db`).
*   **Busy Timeout:** Таймаут ожидания освобождения БД при блокировке другим процессом.
*   **Journal Mode:** Режим журналирования, определяющий механизм обеспечения отказоустойчивости (DELETE, WAL, TRUNCATE, PERSIST, MEMORY, OFF).
*   **WAL-reset bug:** Дефект в SQLite 3.7.0–3.51.2, обнаруженный 2026-03-03, способный привести к повреждению базы данных при определенных условиях. Исправлен в версии 3.51.3 и бэкпортирован в 3.44.6 и 3.50.7.
*   **VACUUM:** Операция перестроения файла БД для удаления пустот и дефрагментации.
*   **Auto-vacuum:** Механизм автоматического освобождения места после удаления данных (не включен по умолчанию).

## Базовые концепции

### Режимы журналирования: сравнение для SRE

SQLite поддерживает шесть режимов журналирования, каждый из которых имеет свою нишу эксплуатации:

| Режим | Блокировка при записи | Надежность | Производительность | Использование |
| :--- | :--- | :--- | :--- | :--- |
| **DELETE** | Эксклюзивная блокировка на всю транзакцию | Высокая | Низкая | Отдельные приложения, низкая конкуренция |
| **WAL** | Shared lock для читателей, Reserved для писателей | Высокая | Высокая | **Стандарт для SRE**: Edge, контейнеры, многопроцессные приложения |
| **TRUNCATE** | Аналогично DELETE | Высокая | Средняя | Файловые системы, где удаление файла затратно |
| **PERSIST** | Аналогично DELETE | Высокая | Средняя | Высоконагруженные записи, где важен minimize churn |
| **MEMORY** | Аналогично DELETE | Нет (только для RAM) | Максимальная | Временные кэши, тесты |
| **OFF** | Нет | Нет | Максимальная | Отключено; риск повреждения при аварийном завершении |

### Архитектура WAL: файлы и блокировки

В режиме WAL SQLite создает два вспомогательных файла:

1.  **`-wal` (Write-Ahead Log):** Аппендикс-лог всех изменений с момента последнего чекпоинта.
2.  **`-shm` (Shared Memory):** Индекс WAL для координации доступа между процессами (может отсутствовать при `EXCLUSIVE` locking mode).

WAL использует более гранулярную блокировку по сравнению с rollback-журналом:
- Читатели получают `SHARED` lock, не мешая другим читателям.
- Писатель получает `RESERVED` lock, позволяя читателям продолжать работу.
- Только при смене режимов или подключении/отключении требуется `EXCLUSIVE` lock.

### Механизм чекпоинта

Чекпоинт переносит страницы из WAL в основной файл и усекает WAL. Существует три стратегии:

1.  **PASSIVE:** Выполняется только если нет конфликтующих блокировок. Может завершиться раньше, чем весь WAL будет перенесен.
2.  **FULL:** Блокирует Writers до завершения чекпоинта. Гарантирует полное слияние WAL.
3.  **TRUNCATE:** Как FULL, но дополнительно усекает WAL до нуля (эффективно для контроля размера файла).

По умолчанию SQLite выполняет автоматический чекпоинт каждые ~1000 страниц (около 4–8 МБ при page_size=4096/8192).

### Synchronous modes и их влияние на надежность

| Режим | Описание | Риск при сбое питания |
| :--- | :--- | :--- |
| **FULL (2)** | Гарантирует запись на физическую поверхность диска перед продолжением. Нет риска повреждения. | Нет |
| **NORMAL (1)** | Синхронизирует только в критические моменты (чекпоинт, завершение транзакции). Безопасен в WAL режиме на современных ФС. | Минимальный в WAL; есть в DELETE на старых ext3 |
| **OFF (0)** | Нет синхронизации. Максимальная скорость, но риск потери последних транзакций при сбое. | Высокий |

## Практические сценарии

### 1. Включение WAL и базовая настройка (Production Bootstrap)

WAL-режим является персистентным: после включения база автоматически остается в WAL при перезапуске. Настройки `synchronous` и `busy_timeout` требуют применения на каждое соединение.

```sql
-- Включение WAL (выполняется один раз на базу)
PRAGMA journal_mode = WAL;
-- → wal

-- Базовая конфигурация для продакшена
PRAGMA synchronous = NORMAL;       -- Баланс скорость/надежность
PRAGMA busy_timeout = 5000;        -- 5 секунд ожидания блокировки
PRAGMA journal_size_limit = 67108864; -- Ограничение WAL до 64 МБ
```

### 2. Настройка для высоконагруженных сред

При интенсивной записи (> 1000 транзакций/сек) или наличии долгих чтений, блокирующих чекпоинт:

```sql
-- Принудительный контроль частоты чекпоинтов
PRAGMA wal_autocheckpoint = 1000; -- Страниц (по умолчанию 1000)
-- Или полный отказ от авточекпоинта (только вручную)
PRAGMA wal_autocheckpoint = 0;

-- Периодический принудительный чекпоинт (например, в cron)
-- Используйте TRUNCATE для усечения WAL после слияния
PRAGMA wal_checkpoint(TRUNCATE);

-- Инкрементальный VACUUM для контроля размера без полной блокировки
PRAGMA auto_vacuum = INCREMENTAL;
PRAGMA incremental_vacuum(1000); -- Освободить до 1000 страниц
```

### 3. Валидация и health-check

Интегрируйте проверки целостности SQLite в процедуры оркестрации контейнеров:

```bash
# Быстрая проверка (проверяет только структуру, не целостность данных)
sqlite3 /var/lib/app/data.db "PRAGMA quick_check;"
# → ok

# Полная проверка (влияет на производительность, требует эксклюзивной блокировки)
sqlite3 /var/lib/app/data.db "PRAGMA integrity_check;"
# → ok

# Проверка на предмет зависших транзакций и необходимости VACUUM
sqlite3 /var/lib/app/data.db "
  SELECT 
    page_count * page_size AS db_size_bytes,
    freelist_count * page_size AS free_bytes,
    (freelist_count * 100.0 / page_count) AS fragmentation_pct
  FROM pragma_page_count(), pragma_freelist_count(), pragma_page_size();
"
```

### 4. Стратегии резервного копирования

#### А) Горячий бэкап через CLI (Online Backup API)

Безопасное копирование без остановки приложения. SQLite гарантирует консистентность снимка на уровне байтов.

```bash
# Полный бэкап с прогрессом
sqlite3 /var/lib/app/data.db ".backup '/backups/data_$(date +%F_%H%M).db'"

# Проверка результата
sqlite3 /backups/data_2026-09-30.db "PRAGMA integrity_check;"
```

#### Б) Атомарный снапшот через VACUUM INTO

Создает компактную (без пустот) копию. Подходит для миграций и ленивых бэкапов.

```sql
VACUUM INTO '/backups/compact_snapshot.db';
```

#### В) Логический дамп в SQL

Для миграции на другие СУБД или долгосрочного архивирования:

```bash
# Полный дамп схемы и данных
sqlite3 /var/lib/app/data.db .dump > /backups/dump_$(date +%F).sql

# Только схема
sqlite3 /var/lib/app/data.db .schema > /backups/schema.sql

# Только данные конкретной таблицы
sqlite3 /var/lib/app/data.db ".dump --data-only events" > /backups/events.sql
```

#### Г) Бэкап в контейнерной среде

При работе с Docker/Kubernetes важно учитывать, что копирование файла `.db` без остановки подов может привести к неконсистентности, если приложение выполняет запись.

```bash
# Временная остановка пода для полного копирования (надежно)
kubectl rollout pause deployment/app
cp /data/app.db /backups/app.db
kubectl rollout resume deployment/app

# Или использование Online Backup API через sqlite3 CLI
kubectl exec -it app-pod -- sqlite3 /data/app.db ".backup '/tmp/backup.db'"
kubectl cp app-pod:/tmp/backup.db ./backup.db
```

### 5. Восстановление и репликация

#### Восстановление из бэкапа

```bash
# Восстановление из полного бэкапа
sqlite3 /var/lib/app/data_restored.db ".restore '/backups/data_2026-09-30.db'"

# Применение лог-файла после бэкапа (Point-in-Time Recovery через WAL)
# Копируем основной файл, затем применяем WAL-чанки
cp /backups/base.db /var/lib/app/data.db
# WAL автоматически сольется при первом подключении
```

#### Локальная репликация через WAL shipping

Для Disaster Recovery между двумя хостами копируйте основной файл и WAL **только при остановленных писателях**: rsync живого WAL-файла может захватить недописанные фреймы, а WAL сбрасывается и переиспользуется — копия не будет соответствовать базовому файлу:

```bash
# На primary: остановить запись (приложение или сервис)
# Копируем основной файл И WAL вместе
rsync -az /var/lib/app/data.db /var/lib/app/data.db-wal backup@dr-host:/var/backups/

# На DR-хосте при переключении:
# 1. Остановить primary (гарантия, что WAL не меняется)
# 2. Синхронизировать базовый файл и WAL
# 3. Подключиться к базе — WAL автоматически применится
```

Для непрерывной репликации без остановки писателей используйте Online Backup API (`.backup`) или Litestream — см. [Экосистему SQLite](./sqlite_ecosystem.md).

### 6. Мониторинг и метрики

#### Метрики для Prometheus / node_exporter

```bash
# Размер БД и фрагментация
DB_SIZE=$(stat -c%s /var/lib/app/data.db)
WAL_SIZE=$(stat -c%s /var/lib/app/data.db-wal 2>/dev/null || echo 0)
FREELIST=$(sqlite3 /var/lib/app/data.db "SELECT freelist_count FROM pragma_freelist_count();")

# Экспорт в node_exporter textfile collector
cat <<EOF > /var/lib/node_exporter/textfile_collector/sqlite.prom
# HELP sqlite_db_size_bytes Размер файла базы данных
# TYPE sqlite_db_size_bytes gauge
sqlite_db_size_bytes $DB_SIZE
# HELP sqlite_wal_size_bytes Размер WAL-файла
# TYPE sqlite_wal_size_bytes gauge
sqlite_wal_size_bytes $WAL_SIZE
# HELP sqlite_freelist_pages Количество свободных страниц (фрагментация)
# TYPE sqlite_freelist_pages gauge
sqlite_freelist_pages $FREELIST
EOF
```

#### Пороговые значения для алертов

| Метрика | Предупреждение | Критический уровень | Действие |
| :--- | :--- | :--- | :--- |
| `sqlite_wal_size_bytes` | > 128 МБ | > 512 МБ | Проверить долгие транзакции чтения; выполнить `wal_checkpoint(TRUNCATE)` |
| `sqlite_freelist_pages` | > 10% от общего числа страниц | > 30% | Выполнить `VACUUM` или `incremental_vacuum` |
| `integrity_check` | Любое значение кроме `ok` | Любое значение кроме `ok` | Восстановление из бэкапа; проверка диска |

## Операции и команды

### Справочник PRAGMA

| Параметр | Значения / Диапазон | Назначение | Примечание SRE |
| :--- | :--- | :--- | :--- |
| `journal_mode` | DELETE / WAL / TRUNCATE / PERSIST / MEMORY / OFF | Режим журналирования | **WAL — обязателен** для многопроцессных сред |
| `synchronous` | 0(OFF) / 1(NORMAL) / 2(FULL) | Синхронизация на диск | NORMAL безопасен в WAL; FULL для максимальной надежности |
| `busy_timeout` | 0–60000 мс | Ожидание разблокировки | Установите 5000+ для конкурентных сред |
| `journal_size_limit` | байты | Максимальный размер WAL | 64–256 МБ для предотвращения неконтролируемого роста |
| `wal_autocheckpoint` | страницы | Частота авточекпоинта | 1000 (по умолчанию); 0 для полного ручного управления |
| `auto_vacuum` | 0(NONE) / 1(FULL) / 2(INCREMENTAL) | Автоочистка после DELETE | INCREMENTAL позволяет контролировать нагрузку |
| `page_size` | 512–65536 байт | Размер страницы БД | 4096 или 8192 для современных SSD |
| `max_page_count` | страницы | Лимит размера БД | По умолчанию ~281 ТБ; ограничен файловой системой |
| `cache_size` | страницы | Кэш страниц в памяти | -2000..-200000 (отрицательное = Kib) для контроля потребления RAM |
| `mmap_size` | байты | Размер memory-mapped файла | 0 для отключения; полезно для больших Read-only дампов |
| `locking_mode` | NORMAL / EXCLUSIVE | Режим блокировок файла | EXCLUSIVE убирает `-shm` файл, но требует единственного процесса |

### CLI команды для эксплуатации

```bash
# Проверка режима журналирования
sqlite3 data.db "PRAGMA journal_mode;"
# → wal

# Проверка параметров синхронизации и таймаута
sqlite3 data.db "PRAGMA synchronous; PRAGMA busy_timeout;"

# Анализ фрагментации
sqlite3 data.db "
  SELECT 
    page_count AS total_pages,
    freelist_count AS free_pages,
    (freelist_count * 100.0 / page_count) AS fragmentation_pct,
    page_count * page_size / 1024 / 1024 AS size_mb
  FROM pragma_page_count(), pragma_freelist_count(), pragma_page_size();
"

# Принудительный чекпоинт с усечением WAL
sqlite3 data.db "PRAGMA wal_checkpoint(TRUNCATE);"

# Процессы, держащие файл БД
lsof | grep data.db

# Индексы таблицы и их колонки
sqlite3 data.db "PRAGMA index_list('events');"
sqlite3 data.db "PRAGMA index_info('idx_events_host');"

# Проверка целостности (быстрая)
sqlite3 data.db "PRAGMA quick_check;"

# Проверка целостности (полная)
sqlite3 data.db "PRAGMA integrity_check;"
```

## Устранение неполадок

| Проблема | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `Error: database is locked` | Превышен `busy_timeout` или зависшая транзакция. Множественные writers без WAL. | Увеличьте `busy_timeout` до 5000–10000 мс. Проверьте зомби-процессы. Переведите на WAL если еще не done. |
| WAL-файл > размера БД | Длительное чтение блокирует авточекпоинт. Отсутствие `journal_size_limit`. | Увеличьте `busy_timeout` на чтение. Выполните `wal_checkpoint(TRUNCATE)`. Настройте `journal_size_limit`. |
| `disk I/O error` | Проблемы с правами, нехватка места, неисправность диска. | Проверьте `df -h` и `dmesg`. Убедитесь, что у пользователя приложения есть права на запись в директорию (нужен `+w` на папку для временных файлов). |
| `file is encrypted or is not a database` | Попытка открыть WAL-базу старым SQLite (< 3.22.0) или повреждение заголовка. | Обновите SQLite. Проверьте `integrity_check`. Восстановите из бэкапа. |
| Повреждение после сбоя питания | WAL-reset bug (версии 3.7.0–3.51.2), отключение синхронизации, сбой ФС. | Обновите до 3.51.3+. Проверьте `integrity_check`. Восстановите из бэкапа. |
| Низкая производительность записи | Отсутствие WAL, `synchronous=FULL`, отсутствие индексов, фрагментация. | Включите WAL. Установите `synchronous=NORMAL`. Выполните `ANALYZE` и `VACUUM`. |
| Высокое потребление RAM | Большой `cache_size`, memory-mapped region (`mmap_size`). | Уменьшите `cache_size` до разумного предела (например, 2000 страниц = 16 МБ при page_size=8192). |

### Диагностические сценарии

#### Проверка на предмет WAL-reset bug

```bash
# Определите версию SQLite
sqlite3 --version
# → 3.51.3  (или выше — уязвимости нет)

# Если версия ниже 3.51.3 и выше 3.7.0 — проверьте базу
sqlite3 data.db "PRAGMA integrity_check;"
# При подозрении на повреждение — восстановите из бэкапа
```

#### Анализ процессов, блокирующих базу

```bash
# Процессы, открывшие файл БД
lsof +L1 | grep data.db

# Зомби-транзакции в WAL
sqlite3 data.db "
  SELECT * FROM sqlite_master WHERE type='table';
  -- Проверьте долгие запросы в приложении
"

# Мониторинг размера WAL в реальном времени
watch -n 1 'stat -c%s data.db-wal 2>/dev/null || echo 0'
```

## Рекомендации SRE

### 1. Файловые системы и хранилища

*   **Никогда не используйте сетевые диски** (NFS, SMB, CIFS) для SQLite в WAL-режиме. Некорректная реализация файловых блокировок на сетевых ФС приведет к повреждению базы. Используйте только локальные тома (Local SSD, NVMe).
*   Для контейнеров используйте `emptyDir` с `medium: Memory` для временных баз или `hostPath` / `PersistentVolume` с `ReadWriteOnce` для персистентных.
*   Проверяйте, что файловая система поддерживает `fallocate` и корректные `fcntl` блокировки (ext4, XFS, Btrfs — да; NFS — нет).

### 2. Контейнеризация и оркестрация

*   В Kubernetes/Docker используйте `ReadWriteOnce` PersistentVolumeClaim. `ReadWriteMany` несовместим с WAL.
*   Никогда не запускайте несколько реплик пода с общей SQLite-БД. Для HA используйте внешнюю СУБД (PostgreSQL/MySQL).
*   Включите `PRAGMA integrity_check` в liveness/readiness probe контейнера.
*   При обновлении подов (rolling update) убедитесь, что старый под корректно закрыл соединения перед удалением volume.

### 3. Checkpoint и VACUUM в продакшене

*   При интенсивной записи настройте принудительные чекпоинты: `PRAGMA wal_checkpoint(PASSIVE)` каждые N минут или через `TRUNCATE` при достижении порога размера.
*   `VACUUM` блокирует базу на время выполнения. Используйте его в периоды низкой нагрузки или примените `incremental_vacuum` для онлайновой очистки.
*   Мониторьте фрагментацию (`freelist_count`). При росте выше 15% запланируйте обслуживание.

### 4. Конфигурация приложения

*   Устанавливайте `busy_timeout` на каждое соединение сразу после открытия.
*   `journal_mode=WAL` персистентен: достаточно выполнить его один раз через CLI для всей базы.
*   Используйте короткие транзакции. WAL неэффективен для транзакций > 100 МБ; для пакетных загрузок используйте промежуточные чекпоинты.
*   Включите `foreign_keys` если схема использует внешние ключи (отключены по производительности соображениям):

```sql
PRAGMA foreign_keys = ON;
```

### 5. Резервное копирование

*   Планируйте бэкапы по RPO/RTO: для критичных данных — ежедневные полные + почасовые инкрементальные через WAL shipping.
*   Регулярно проверяйте восстановление из бэкапа (`restore` + `integrity_check`).
*   Храните бэкапы на отдельном физическом носителе или хосте, отличном от источника.
*   Шифруйте бэкапы, если содержатся персональные данные.

### 6. Безопасность и целостность

*   Используйте `PRAGMA secure_delete = ON` для overwrite удаленных данных (полезно на SSD, где TRIM не стирает данные мгновенно).
*   Ограничьте права на файлы БД: `0600` для файла, `0700` для директории.
*   Никогда не открывайте БД из ненадежных директорий с правами записи для группы/other.
