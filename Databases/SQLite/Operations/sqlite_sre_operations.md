# SQLite для SRE: WAL, Конкурентность и Бэкапы

## Определения

*   **WAL (Write-Ahead Logging):** Режим журналирования, при котором изменения записываются в отдельный файл `-wal`, что позволяет читателям не блокировать писателей (и наоборот).
*   **Checkpoint (Чекпоинт):** Процесс переноса изменений из WAL-файла в основной файл базы данных (`.db`).
*   **Busy Timeout:** Таймаут ожидания освобождения БД при блокировке другим процессом.
*   **Litestream:** Утилита для потоковой репликации SQLite во внешние хранилища (S3) в реальном времени.

## Базовые концепции

### Режим WAL: Почему это стандарт для SRE

По умолчанию SQLite использует режим `DELETE` (откат через journal-файл), который блокирует всю базу для чтения при записи. В режиме WAL ситуация меняется:

1.  **Параллелизм:** Читатели могут работать одновременно с писателем.
2.  **Производительность:** Запись в WAL происходит последовательно (Append-only), что значительно быстрее случайной записи в основной файл.
3.  **Риски:** WAL-файл может бесконтрольно расти, если чекпоинты блокируются длительными транзакциями чтения.

## Практические сценарии

### 1. Включение и настройка WAL
Для современных Edge-сервисов этот режим обязателен.

```sql
-- Включение режима (выполняется один раз на БД)
PRAGMA journal_mode = WAL;

-- Настройка синхронизации для баланса скорость/надежность
-- NORMAL — быстрее, безопасно в WAL режиме; FULL — медленнее.
PRAGMA synchronous = NORMAL;

-- Установка ожидания блокировки (предотвращает ошибки "database is locked")
PRAGMA busy_timeout = 5000; -- 5 секунд
```

### 2. Мониторинг и управление лимитами
SQLite имеет встроенные ограничения, которые важно знать при масштабировании Edge-узлов.

*   **Max Database Size:** По умолчанию ~281 ТБ (ограничено файловой системой).
*   **Page Size:** Рекомендуется 4096 или 8192 байт для современных SSD.
```sql
-- Проверка текущих параметров
PRAGMA page_size;
PRAGMA max_page_count;
```

### 3. Стратегии резервного копирования

#### А) Онлайн бэкап через CLI
Безопасное копирование без остановки приложения (SQLite гарантирует консистентность снимка).
```bash
sqlite3 source.db ".backup 'backup.db'"
```

#### Б) Использование VACUUM INTO (Atomic Snapshot)
Позволяет создать упакованную (без пустот) копию базы.
```sql
VACUUM INTO '/mnt/backups/snapshot_$(date +%F).db';
```

#### В) Litestream (Disaster Recovery в S3)
SRE-стандарт для репликации SQLite. Litestream запускается как sidecar-процесс и отправляет каждый чанк WAL в S3.

**Пример конфига `litestream.yml`:**
```yaml
dbs:
  - path: /var/lib/myapp/data.db
    replicas:
      - url: s3://my-bucket/db-backups
        access-key-id: ${AWS_ACCESS_KEY_ID}
        secret-access-key: ${AWS_SECRET_ACCESS_KEY}
```
*Восстановление:* `litestream restore -o /data/recovered.db s3://my-bucket/db-backups`

## Рекомендации SRE

1.  **Контейнеризация:** Никогда не используйте сетевые диски (NFS, SMB) для SQLite в режиме WAL — это гарантированно приведет к повреждению БД из-за некорректной реализации файловых блокировок. Используйте только локальные тома (Local SSD/NVMe).
2.  **Чекпоинты:** Если ваше приложение делает много записей, настройте принудительные чекпоинты (`PRAGMA wal_checkpoint(PASSIVE)`), чтобы `-wal` файл не занял всё место на диске.
3.  **Corruption Check:** Включайте `PRAGMA integrity_check` в процедуры health-check контейнера.

## Устранение неполадок (Troubleshooting)

| Проблема | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `Error: database is locked` | Превышен `busy_timeout` или зависшая транзакция. | Увеличьте `busy_timeout` до 5-10с. Проверьте наличие зомби-процессов, удерживающих файл. |
| WAL-файл весит больше самой БД | Длительное чтение блокирует автоматический чекпоинт. | Завершите долгие сессии чтения. Выполните `VACUUM`. |
| `disk I/O error` | Проблемы с правами доступа или нехватка места. | Проверьте `df -h` и права пользователя на директорию (SQLite нужны права на запись в папку для создания временных файлов). |
