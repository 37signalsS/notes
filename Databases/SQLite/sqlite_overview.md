# SQLite: Обзор и применение в SRE и Edge-вычислениях

## Определения

*   **SQLite** — компактная, встраиваемая, полнофункциональная реляционная СУБД. В отличие от клиент-серверных СУБД (PostgreSQL, MySQL), SQLite не является отдельным процессом; это библиотека, которая работает внутри приложения и хранит всю базу данных в одном кроссплатформенном файле на диске.
*   **Zero-Configuration:** Не требует установки, настройки сервера или управления пользователями.
*   **Serverless:** Приложение напрямую читает и пишет файлы базы данных.
*   **Single-file format:** Вся БД (схемы, индексы, данные) упакована в один файл.
*   **WAL (Write-Ahead Logging):** Режим журналирования, при котором изменения записываются в отдельный файл `-wal`, что позволяет читателям не блокировать писателей.
*   **Checkpoint (Чекпоинт):** Процесс переноса изменений из WAL-файла в основной файл базы данных (`.db`).
*   **VFS (Virtual File System):** Абстрактный слой для работы с хранилищем, позволяющий SQLite работать над разными типами накопителей и зашифрованных разделов.
*   **Journal Mode:** Режим журналирования, определяющий механизм обеспечения отказоустойчивости (DELETE, WAL, TRUNCATE, PERSIST, MEMORY, OFF).
*   **ACID:** Гарантии транзакционности — атомарность, согласованность, изоляция, долговечность.
*   **WAL-reset bug:** Дефект в SQLite 3.7.0–3.51.2, обнаруженный 2026-03-03, способный привести к повреждению базы данных при определенных условиях. Исправлен в версии 3.51.3 и бэкпортирован в 3.44.6 и 3.50.7.

## Базовые концепции

### Архитектура и надежность

SQLite хранит всю базу данных в одном файле, что радикально упрощает бэкапы, перенос и версионирование по сравнению с клиент-серверными СУБД. Несмотря на простоту, SQLite обеспечивает полноценные ACID-транзакции: все изменения внутри одной транзакции либо применяются полностью, либо откатываются, даже при сбое питания, падении ОС или аварийном завершении процесса. Это подтверждается собственным тестовым набором SQLite, моделирующим сбои.

**VFS (Virtual File System)** — абстрактный слой между ядром СУБД и операционной системой, который инкапсулирует работу с файлами, блокировками и синхронизацией. Благодаря VFS SQLite может работать над локальными дисками, зашифрованными разделами (LUKS, BitLocker, FileVault) и специализированными хранилищами, при этом сохраняя одинаковое поведение на уровне транзакций.

**Manifest Typing:** Динамическая типизация в SQLite — тип значения привязан к самому значению, а не к колонке. Это упрощает работу с гибкими схемами данных, но требует аккуратности при интеграции со строго типизированными системами.

### Журналирование и WAL

По умолчанию SQLite использует **rollback journal** (`journal_mode=DELETE`): при записи создается временный файл журнала, а финальный COMMIT происходит путем его удаления. Этот подход обеспечивает надежность, но ограничивает concurrence: писатель получает эксклюзивную блокировку, блокируя всех читателей.

**WAL-режим** (доступен начиная с SQLite 3.7.0, 2010-07-21) инвертирует эту модель: изменения сначала аппендикс-записываются в отдельный файл `-wal`, а основной файл `.db` обновляется асинхронно во время чекпоинта. Это дает несколько критичных для SRE преимуществ:

*   **Читатели не блокируют писателей:** несколько процессов могут одновременно читать данные, пока писатель аппендиксит в WAL.
*   **Писатели не блокируют читателей:** чтение продолжает работать из неизменного основного файла, пока чекпоинт не переместит изменения.
*   **Более последовательный I/O:** записи идут в конец WAL-файла, что minimizes случайных seeks и повышает throughput на HDD/SSD.
*   **Меньше `fsync()`:** WAL использует fewer операций синхронизации по сравнению с rollback journal, что снижает риск проблем на системах с некорректной реализацией `fsync()`.

**Архитектура WAL-файлов:**

1.  **`-wal` (Write-Ahead Log):** Аппендикс-лог всех изменений с момента последнего чекпоинта.
2.  **`-shm` (Shared Memory):** Индекс WAL для координации доступа между процессами. При `EXCLUSIVE` locking mode файл `-shm` может отсутствовать, так как единственный процесс не нуждается в shared memory.

**Ограничения WAL-режима:**

*   Все процессы, работающие с базой, должны находиться на **одном хосте**. WAL использует shared memory (`-shm`), который недоступен между разными машинами. WAL **не работает по сетевой файловой системе** (NFS, SMB, CIFS).
*   Размер страницы (`page_size`) нельзя изменить после перехода в WAL-режим. Для изменения page_size необходимо предварительно выйти в DELETE/TRUNCATE/PERSIST режим.
*   Старые версии SQLite (< 3.22.0) не могут открывать WAL-базы в read-only режиме и сообщают ошибку `file is encrypted or is not a database`.

### Синхронизация и надежность

Параметр `synchronous` определяет, насколько агрессивно SQLite сбрасывает данные на физическую поверхность диска:

| Режим | Описание | Риск при сбое питания в WAL |
| :--- | :--- | :--- |
| **FULL (2)** | Гарантирует запись на диск перед продолжением. Нет риска повреждения. | Нет |
| **NORMAL (1)** | Синхронизирует в критические моменты (чекпоинт, завершение транзакции). Безопасен в WAL на современных ФС. | Минимальный: возможна потеря последних транзакций, но база остается целостной |
| **OFF (0)** | Нет синхронизации. Максимальная скорость, но риск потери данных. | Высокий |

Для большинства SRE-сценариев в WAL-режиме рекомендуется `synchronous=NORMAL`: это обеспечивает баланс между производительностью и целостностью данных. `synchronous=FULL` требуется только для максимальной надежности в критичных системах.

### Режимы журналирования (сводный обзор)

SQLite поддерживает шесть режимов журналирования. Выбор режима — компромисс между concurrence, производительностью и надежностью:

| Режим | Блокировка при записи | Надежность | Производительность | Использование |
| :--- | :--- | :--- | :--- | :--- |
| **DELETE** | Эксклюзивная блокировка на всю транзакцию | Высокая | Низкая | Отдельные приложения, низкая конкуренция |
| **WAL** | Shared lock для читателей, Reserved для писателей | Высокая | Высокая | **Стандарт для SRE**: Edge, контейнеры, многопроцессные приложения |
| **TRUNCATE** | Аналогично DELETE | Высокая | Средняя | Файловые системы, где удаление файла затратно |
| **PERSIST** | Аналогично DELETE | Высокая | Средняя | Высоконагруженные записи, где важен minimize churn |
| **MEMORY** | Аналогично DELETE | Нет (только для RAM) | Максимальная | Временные кэши, тесты |
| **OFF** | Нет | Нет | Максимальная | Отключено; риск повреждения при аварийном завершении |

### Ограничения и масштабирование

SQLite был изначально спроектирован без искусственных ограничений, но имеет физические пределы, определяемые аппаратными и файловыми системами:

*   **Максимальный размер БД:** ~281 терабайт при максимальном размере страницы 65536 байт. При дефолтном page_size=4096 максимальный размер составляет ~17.5 терабайт. На практике лимитирует файловая система.
*   **Количество строк:** теоретический максимум 2^64 (~1.8·10^19), на практике достигает ~2·10^13 строк при минимальном размере данных и заполненной БД на 281 ТБ.
*   **Колонок в таблице:** по умолчанию 2000, максимум 32767 при перекомпиляции. Практически хорошо нормализованная схема редко превышает 100 колонок.
*   **Конкуренция:** в WAL-режиме **один писатель** в любой момент времени. Для сценариев с высокой интенсивностью записи (>1000 транзакций/сек) или множеством concurrent writers стоит оценить, подходит ли SQLite, или требуется клиент-серверная СУБД.
*   **Сеть:** WAL не работает по NFS/SMB. Для распределенных сценариев требуется локальное хранилище на каждом узле.

SQLite не рекомендуется для баз данных больше 1 ТБ, высококонкурентных write-сценариев с десятками одновременных писателей, или когда требуется централизованное управление доступом (RBAC).

### Место SQLite в современной инфраструктуре (2026)

Несмотря на простоту, SQLite стал критически важным инструментом для SRE и Platform-инженеров:

1.  **Configuration Storage:** Используется как надежное хранилище настроек (Grafana, K3s через Kine, Podman, системные сервисы). В этом сценарии SQLite заменяет фрагментированные конфигурационные файлы и обеспечивает атомарные обновления.
2.  **Local-First приложения:** Обеспечивает работу приложения без интернета с последующей синхронизацией. Актуально для мобильных и десктопных приложений, работающих в периметрах с ненадежной связью.
3.  **Edge-вычисления и IoT:** Идеален для устройств с ограниченными ресурсами, где запуск тяжелого сервера БД невозможен. Шлюзы, датчики, промышленные контроллеры.
4.  **Эфемерные среды:** Идеален для CI/CD пайплайнов, где нужно мгновенно создать и уничтожить БД. Отсутствие серверного процесса и нулевая настройка ускоряют spin-up тестовых сред.
5.  **Встроенные системы и аппаратные устройства:** Автомобильные системы, медицинское оборудование, сетевые апплайнсы — везде, где требуется надежное хранение данных без отдельного процесса.

## Практические сценарии

### 1. Production bootstrap checklist

Перед переводом базы в production выполните минимальный набор проверок:

```bash
# Проверка целостности существующей базы
sqlite3 app.db "PRAGMA integrity_check;"
# → ok

# Включение WAL (персистентно для всей базы)
sqlite3 app.db "PRAGMA journal_mode=WAL;"
# → wal

# Базовая конфигурация для продакшена
sqlite3 app.db "PRAGMA busy_timeout=5000;"
sqlite3 app.db "PRAGMA synchronous=NORMAL;"
sqlite3 app.db "PRAGMA journal_size_limit=67108864;"
```

Важно: `journal_mode=WAL` является персистентным — после включения база автоматически остается в WAL при перезапуске. Настройки `synchronous` и `busy_timeout` требуют применения на каждое соединение.

### 2. Валидация и health-check

Интегрируйте проверки целостности SQLite в процедуры оркестрации контейнеров и мониторинга:

```bash
# Быстрая проверка (проверяет только структуру, не целостность данных)
sqlite3 /var/lib/app/data.db "PRAGMA quick_check;"
# → ok

# Полная проверка (требует эксклюзивной блокировки, влияет на производительность)
sqlite3 /var/lib/app/data.db "PRAGMA integrity_check;"
# → ok

# Проверка фрагментации и размера
sqlite3 /var/lib/app/data.db "
  SELECT 
    page_count * page_size AS db_size_bytes,
    freelist_count * page_size AS free_bytes,
    (freelist_count * 100.0 / page_count) AS fragmentation_pct
  FROM pragma_page_count(), pragma_freelist_count(), pragma_page_size();
"
```

Для глубокого погружения в эксплуатацию WAL, конкурентность, бэкапы и устранение неполадок см. **[SQLite для SRE: WAL, Конкурентность и Бэкапы](./Operations/sqlite_sre_operations.md)**.

### 3. Резервное копирование (философия single-file)

Однофайловый формат SQLite упрощает стратегии резервного копирования, но требует понимания гарантий consistency:

**Горячий бэкап (Online Backup API):** Безопасное копирование без остановки приложения. SQLite гарантирует консистентность снимка на уровне байтов.

```bash
sqlite3 /var/lib/app/data.db ".backup '/backups/data_$(date +%F_%H%M).db'"
```

**Атомарный снапшот через VACUUM INTO:** Создает компактную (без пустот) копию. Подходит для миграций и ленивых бэкапов.

```sql
VACUUM INTO '/backups/compact_snapshot.db';
```

**Логический дамп в SQL:** Для миграции на другие СУБД или долгосрочного архивирования:

```bash
sqlite3 /var/lib/app/data.db .dump > /backups/dump_$(date +%F).sql
```

В контейнерной среде (Docker/Kubernetes) копирование файла `.db` без остановки подов может привести к неконсистентности, если приложение выполняет запись. Используйте Online Backup API через `kubectl exec` или временную остановку пода.

### 4. Восстановление

```bash
# Восстановление из полного бэкапа
sqlite3 /var/lib/app/data_restored.db ".restore '/backups/data_2026-09-30.db'"

# Применение WAL после сбоя
# При первом подключении к базе WAL автоматически применится (merge)
cp /backups/base.db /var/lib/app/data.db
```

### 5. Мониторинг и метрики

Ключевые метрики для наблюдения за SQLite в production:

*   **Размер WAL-файла:** рост выше 128 МБ указывает на долгие транзакции чтения, блокирующие чекпоинт, или отсутствие `journal_size_limit`.
*   **Фрагментация:** доля свободных страниц (`freelist_count`) выше 15% — сигнал к планированию `VACUUM`.
*   **Целостность:** регулярный `integrity_check` должен возвращать `ok`. Любое другое значение — немедленная эскалация.

Пример экспорта метрик в Prometheus textfile collector:

```bash
DB_SIZE=$(stat -c%s /var/lib/app/data.db)
WAL_SIZE=$(stat -c%s /var/lib/app/data.db-wal 2>/dev/null || echo 0)
FREELIST=$(sqlite3 /var/lib/app/data.db "SELECT freelist_count FROM pragma_freelist_count();")

cat <<EOF > /var/lib/node_exporter/textfile_collector/sqlite.prom
# HELP sqlite_db_size_bytes Размер файла базы данных
# TYPE sqlite_db_size_bytes gauge
sqlite_db_size_bytes $DB_SIZE
# HELP sqlite_wal_size_bytes Размер WAL-файла
# TYPE sqlite_wal_size_bytes gauge
sqlite_wal_size_bytes $WAL_SIZE
# HELP sqlite_freelist_pages Количество свободных страниц (фрагментация)
# TYPE sqlite_freelist_pages gauge
sqlite_freelist_pages $FREELIST
EOF
```

## Операции и команды

### CLI команды для эксплуатации

```bash
# Проверка режима журналирования
sqlite3 data.db "PRAGMA journal_mode;"
# → wal

# Проверка параметров синхронизации и таймаута
sqlite3 data.db "PRAGMA synchronous; PRAGMA busy_timeout;"

# Анализ фрагментации
sqlite3 data.db "
  SELECT 
    page_count AS total_pages,
    freelist_count AS free_pages,
    (freelist_count * 100.0 / page_count) AS fragmentation_pct,
    page_count * page_size / 1024 / 1024 AS size_mb
  FROM pragma_page_count(), pragma_freelist_count(), pragma_page_size();
"

# Принудительный чекпоинт с усечением WAL
sqlite3 data.db "PRAGMA wal_checkpoint(TRUNCATE);"

# Проверка целостности (быстрая)
sqlite3 data.db "PRAGMA quick_check;"

# Проверка целостности (полная)
sqlite3 data.db "PRAGMA integrity_check;"

# Список процессов, держащих файл
lsof | grep data.db
```

Полный справочник PRAGMA-параметров, стратегий checkpoint/VACUUM и расширенных сценариев см. в **[SQLite для SRE: WAL, Конкурентность и Бэкапы](./Operations/sqlite_sre_operations.md)**.

## Устранение неполадок

| Проблема | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `Error: database is locked` | Превышен `busy_timeout` или зависшая транзакция. Множественные writers без WAL. | Увеличьте `busy_timeout` до 5000–10000 мс. Проверьте зомби-процессы. Переведите на WAL если еще не done. |
| WAL-файл > размера БД | Длительное чтение блокирует авточекпоинт. Отсутствие `journal_size_limit`. | Увеличьте `busy_timeout` на чтение. Выполните `wal_checkpoint(TRUNCATE)`. Настройте `journal_size_limit`. |
| `disk I/O error` | Проблемы с правами, нехватка места, неисправность диска. | Проверьте `df -h` и `dmesg`. Убедитесь, что у пользователя приложения есть права на запись в директорию (нужен `+w` на папку для временных файлов). |
| `file is encrypted or is not a database` | Попытка открыть WAL-базу старым SQLite (< 3.22.0) или повреждение заголовка. | Обновите SQLite. Проверьте `integrity_check`. Восстановите из бэкапа. |
| Повреждение после сбоя питания | WAL-reset bug (версии 3.7.0–3.51.2), отключение синхронизации, сбой ФС. | Обновите до 3.51.3+. Проверьте `integrity_check`. Восстановите из бэкапа. |
| Низкая производительность записи | Отсутствие WAL, `synchronous=FULL`, отсутствие индексов, фрагментация. | Включите WAL. Установите `synchronous=NORMAL`. Выполните `ANALYZE` и `VACUUM`. |
| Высокое потребление RAM | Большой `cache_size`, memory-mapped region (`mmap_size`). | Уменьшите `cache_size` до разумного предела (например, 2000 страниц = 16 МБ при page_size=8192). |

### Диагностические сценарии

#### Проверка на предмет WAL-reset bug

```bash
# Определите версию SQLite
sqlite3 --version
# → 3.53.4  (или выше — уязвимости нет)

# Если версия ниже 3.51.3 и выше 3.7.0 — проверьте базу
sqlite3 data.db "PRAGMA integrity_check;"
# При подозрении на повреждение — восстановите из бэкапа
```

#### Анализ процессов, блокирующих базу

```bash
# Процессы, открывшие файл БД
lsof +L1 | grep data.db

# Зомби-транзакции в WAL
sqlite3 data.db "
  SELECT * FROM sqlite_master WHERE type='table';
  -- Проверьте долгие запросы в приложении
"

# Мониторинг размера WAL в реальном времени
watch -n 1 'stat -c%s data.db-wal 2>/dev/null || echo 0'
```

## Рекомендации SRE

### 1. Файловые системы и хранилища

*   **Никогда не используйте сетевые диски** (NFS, SMB, CIFS) для SQLite в WAL-режиме. Некорректная реализация файловых блокировок на сетевых ФС приведет к повреждению базы. Используйте только локальные тома (Local SSD, NVMe).
*   Для контейнеров используйте `emptyDir` с `medium: Memory` для временных баз или `hostPath` / `PersistentVolume` с `ReadWriteOnce` для персистентных.
*   Проверяйте, что файловая система поддерживает `fallocate` и корректные `fcntl` блокировки (ext4, XFS, Btrfs — да; NFS — нет).

### 2. Контейнеризация и оркестрация

*   В Kubernetes/Docker используйте `ReadWriteOnce` PersistentVolumeClaim. `ReadWriteMany` несовместим с WAL.
*   Никогда не запускайте несколько реплик пода с общей SQLite-БД. Для HA используйте внешнюю СУБД (PostgreSQL/MySQL).
*   Включите `PRAGMA integrity_check` в liveness/readiness probe контейнера.
*   При обновлении подов (rolling update) убедитесь, что старый под корректно закрыл соединения перед удалением volume.

### 3. Checkpoint и VACUUM в продакшене

*   При интенсивной записи настройте принудительные чекпоинты: `PRAGMA wal_checkpoint(PASSIVE)` каждые N минут или через `TRUNCATE` при достижении порога размера.
*   `VACUUM` блокирует базу на время выполнения. Используйте его в периоды низкой нагрузки или примените `incremental_vacuum` для онлайновой очистки.
*   Мониторьте фрагментацию (`freelist_count`). При росте выше 15% запланируйте обслуживание.

### 4. Конфигурация приложения

*   Устанавливайте `busy_timeout` на каждое соединение сразу после открытия.
*   `journal_mode=WAL` персистентен: достаточно выполнить его один раз через CLI для всей базы.
*   Используйте короткие транзакции. WAL неэффективен для транзакций > 100 МБ; для пакетных загрузок используйте промежуточные чекпоинты.
*   Включите `foreign_keys` если схема использует внешние ключи (отключены по производительности соображениям):

```sql
PRAGMA foreign_keys = ON;
```

### 5. Резервное копирование

*   Планируйте бэкапы по RPO/RTO: для критичных данных — ежедневные полные + почасовые инкрементальные.
*   Регулярно проверяйте восстановление из бэкапа (`restore` + `integrity_check`).
*   Храните бэкапы на отдельном физическом носителе или хосте, отличном от источника.
*   Шифруйте бэкапы, если содержатся персональные данные.

### 6. Безопасность и целостность

*   Используйте `PRAGMA secure_delete = ON` для overwrite удаленных данных (полезно на SSD, где TRIM не стирает данные мгновенно).
*   Ограничьте права на файлы БД: `0600` для файла, `0700` для директории.
*   Никогда не открывайте БД из ненадежных директорий с правами записи для группы/other.
*   Для шифрования данных на уровне диска используйте LUKS/dm-crypt, BitLocker или FileVault. SQLite не имеет встроенного TDE, но прозрачно работает поверх зашифрованных разделов.
