# Redis vs Memcached

## Определения

**Redis** и **Memcached** — это высокопроизводительные in-memory системы кеширования, предназначенные для снижения нагрузки на основные базы данных и ускорения приложений.

**Текущие версии:**

- Redis 8.6 (февраль 2026)
- Memcached 1.6.41 (март 2026)

Несмотря на общую цель, они основаны на разных архитектурных решениях, что делает их подходящими для разных сценариев.

## Основные концепции

### Сравнение характеристик

| Аспект | Redis | Memcached |
| :--- | :--- | :--- |
| **Модель данных** | Сложные структуры данных (хэши, списки, множества) с атомарными операциями на сервере | Простые пары «ключ-значение», значение — непрозрачный blob. Сериализация на клиенте |
| **Управление памятью** | Гибкий аллокатор (`jemalloc`), политики вытеснения (`LRU`, `LFU` и др.) | `Slab allocator` с классами размеров. Менее гибкий, но предсказуемый. Только `LRU` по slab-классам |
| **Персистентность** | Поддерживается (RDB-снапшоты и AOF-журнал). Может использоваться как основная БД | Отсутствует. Данные теряются при перезагрузке. Только кеш |
| **Масштабирование** | Встроенные средства: репликация (`master-slave`), высокая доступность (`Sentinel`), шардирование (`Cluster`) | На стороне клиента через согласованное хеширование. Серверы не знают друг о друге |
| **Многопоточность** | Однопоточный цикл обработки команд, мультиплексирование I/O. Потоки для фоновых задач (v6+) | Многопоточный. Эффективно утилизирует многоядерные CPU для параллельных `get`/`set` |
| **Функциональность** | Транзакции, `Pub/Sub`, Lua-скрипты, геоданные, потоки | Базовые операции (`get`, `set`, `delete`) и `CAS` (Check-And-Set) для атомарных обновлений |
| **Размер значения** | До 512 МБ | До 1 МБ |
| **Ключ** | До 512 МБ | До 250 байт |

### Архитектурные различия

**Redis:**

- Единый поток для выполнения команд обеспечивает атомарность операций
- Поддержка сложных структур данных уменьшает сетевой трафик
- Персистентность позволяет использовать как основную БД
- Встроенные механизмы высокой доступности и шардирования

**Memcached:**

- Многопоточность обеспечивает лучшую утилизацию многоядерных CPU
- Простота архитектуры означает меньшие накладные расходы
- Только кеширование — данные не сохраняются после перезапуска
- Шардирование реализуется на стороне клиента

## Практические сценарии

### Когда выбирать Memcached

Memcached — идеальный выбор для **простого и быстрого кеширования**.

**Подходящие задачи:**

- Снижение нагрузки на БД через кеширование строк, результатов запросов, HTML-фрагментов
- Максимальная производительность на операциях `get`/`set`
- Эффективное использование многоядерных процессоров
- Простота развертывания и эксплуатации

**Пример:** В системе много одинаковых тяжелых SQL-запросов. Результат каждого запроса сериализуется и помещается в Memcached. Следующий запрос с теми же параметрами мгновенно получает данные из кеша.

### Когда выбирать Redis

Redis подходит для **сложных сценариев**, выходящих за рамки простого кеширования.

**Подходящие задачи:**

- Атомарные операции над структурами данных (добавить элемент в список, увеличить счетчик)
- Надёжность через персистентность данных
- Очереди задач и потоковая обработка
- Аналитика в реальном времени
- Распределённые блокировки
- Pub/Sub для обмена сообщениями

**Пример:** Реализация ленты новостей. Лента пользователя хранится в `Sorted Set`, где `score` — временная метка. Новые посты добавляются атомарно, получение последних N постов — быстрая операция.

### Пример: профиль пользователя

**В Redis:**

```bash
# Профиль хранится как хэш
HSET user:123 name "Alex" age "30" posts "5"

# Атомарное обновление одного поля
HINCRBY user:123 posts 1

# Получение одного поля
HGET user:123 name
```

**В Memcached:**

```bash
# Профиль хранится как сериализованная строка (JSON)
# Для обновления нужно:
# 1. Получить всю строку
# 2. Десериализовать
# 3. Изменить поле
# 4. Записать обратно с CAS для избежания гонки данных
```

### Таблица выбора

| Требование | Redis | Memcached |
| :--- | :--- | :--- |
| Простое кеширование строк | ✅ | ✅ Лучше |
| Сложные структуры данных | ✅ Лучше | ❌ |
| Персистентность | ✅ | ❌ |
| Очереди задач | ✅ | ❌ |
| Pub/Sub | ✅ | ❌ |
| Геоданные | ✅ | ❌ |
| Многопоточность | ⚠️ Частично | ✅ Лучше |
| Простота эксплуатации | ✅ | ✅ Лучше |
| Распределённые блокировки | ✅ | ⚠️ Через CAS |

## Дополнительная информация

### Производительность

Обе системы обеспечивают субмиллисекундную задержку:

- **Redis:** ~1 мкс для простых операций, однопоточная архитектура обеспечивает предсказуемость
- **Memcached:** ~0.5 мкс для `get`/`set`, многопоточность лучше для высоконагруженных систем

### Экосистема клиентов

Обе системы имеют клиенты для всех популярных языков программирования:

- **Redis:** Официальные клиенты для Python, Java, Node.js, Go, Ruby, PHP
- **Memcached:** Клиенты для Python, Java, Node.js, Go, Ruby, PHP

### Мониторинг

- **Redis:** `INFO` команда, Redis Sentinel, Redis Enterprise Flare
- **Memcached:** `stats` команда, интеграция с Prometheus через exporters
