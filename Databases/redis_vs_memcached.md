# Redis против Memcached: архитектурное сравнение систем кеширования 2026

## Определения

**Redis (Remote Dictionary Server)** и **Memcached** — это ведущие высокопроизводительные системы кеширования в оперативной памяти (In-memory). Они предназначены для снижения нагрузки на основные базы данных, ускорения работы приложений и управления состоянием в распределенных системах. В 2026 году разрыв между ними определяется не только производительностью, но и функциональной широтой: Redis стал полноценной мультимодальной платформой данных, в то время как Memcached остается эталоном специализированного, эффективного кеширования.

**Текущие версии (актуально на 2026 год):**
- **Redis 8.x:** Эволюционировал в мультимодальную платформу (AI-кэш, JSON, Векторный поиск, Redis Flex).
- **Memcached 1.6.x+:** Сохраняет фокус на экстремальной производительности, внедряя продвинутые мета-команды, проксирование (mcp) и поддержку SSD (Extstore).

**Лицензирование и экосистема:**
- **Redis:** Использует тройную лицензию (**AGPLv3**, RSALv2, SSPLv1). Возврат к AGPLv3 вернул Redis статус Open Source (OSI-approved), что упростило корпоративное использование.
- **Valkey:** Основной открытый форк Redis (лицензия BSD), поддерживаемый Linux Foundation. Считается стандартом для облачных провайдеров (AWS, GCP).
- **Memcached:** Полностью открыт (**лицензия BSD**), являясь эталоном стабильности и отсутствия лицензионных рисков.

## Основные концепции

### Сравнение технических характеристик

| Аспект | Redis 8.x | Memcached 1.6+ |
| :--- | :--- | :--- |
| **Архитектура потоков** | Reactor (один поток для команд) + Threaded I/O. | **Полная многопоточность** (Symmetric Multi-Processing). |
| **Модель данных** | Сложные структуры (JSON, Векторы, Хэши, Стримы). | Простые пары «ключ-значение» (Blob). |
| **Протокол** | RESP3 (текстовый/бинарный), конвейеризация. | Text/Binary и **Meta-команды** (высокая эффективность). |
| **Управление памятью** | Аллокатор `jemalloc`, аппроксимированный LRU/LFU. | **Slab allocator**. Segmented LRU (SLRU). |
| **Персистентность** | RDB, **Multi-part AOF**, Redis Flex. | Отсутствует (кроме сброса на SSD через **Extstore**). |
| **Масштабирование** | Sentinel (HA), Cluster (Server-side шардирование). | Client-side или через **Proxy (mcp)** на Lua. |
| **Размер значения** | До 512 МБ. | До 1 МБ (настраивается до гигабайтов). |
| **Безопасность** | **ACL v2**, TLS 1.3, LDAP/Entra ID. | TLS, SASL, Meta-auth. |

### Глубокий анализ архитектурных различий

#### Модель выполнения: Reactor vs SMP
- **Redis (Reactor Pattern):** Выполняет все команды последовательно в основном потоке. Это гарантирует атомарность без использования блокировок (mutex), что критично для работы со сложными структурами. Многопоточность в v8.x используется для сетевого I/O, фоновой очистки (Lazy Free) и векторного поиска, не нарушая однопоточность ядра.
- **Memcached (SMP):** Спроектирован как полностью многопоточное приложение. Каждый поток обрабатывает свои соединения, конкурируя за доступ к хеш-таблице через гранулярные блокировки. Это позволяет Memcached линейно масштабироваться с ростом количества ядер CPU на одном узле.

#### Управление памятью: Динамика vs Слабы
- **Redis (jemalloc):** Выделяет память по требованию. Это обеспечивает гибкость при хранении объектов разных размеров, но может привести к внешней фрагментации. Требует активного использования модуля `activedefrag`.
- **Memcached (Slab Allocation):** Делит память на страницы и чанки фиксированных размеров (Slabs). Это исключает внешнюю фрагментацию, но может приводить к внутренней неэффективности, если размер объекта значительно меньше размера чанка.

#### Алгоритмы вытеснения данных
- **Redis:** Использует аппроксимированный LRU/LFU на основе сэмплирования. Это экономит память на хранении ссылок, но менее точно при резких изменениях профиля нагрузки.
- **Memcached (SLRU):** Сегментированный LRU разделяет кэш на HOT, WARM и COLD зоны. Это защищает "горячие" данные от вытеснения при массовых разовых обращениях к другим ключам.

## Практические сценарии

### Когда выбирать Memcached
- **Экстремальные нагрузки на чтение:** Системы с миллионами RPS на простых ключах-значениях.
- **Огромные объемы кэша (ТБ+):** Использование **Extstore** позволяет хранить терабайты данных на SSD/NVMe, используя RAM только для метаданных, что радикально дешевле.
- **Сверхнизкие задержки:** Минимальная обработка на стороне сервера без накладных расходов на парсинг сложных структур.
- **Проксирование трафика:** Когда требуется сложная балансировка и маршрутизация кэша через **mcp (Lua)**.

### Когда выбирать Redis
- **AI и векторный поиск:** Хранение эмбеддингов и поиск по сходству (Vector Search).
- **Сложная бизнес-логика:** Атомарные манипуляции с частями объекта (например, инкремент поля в JSON).
- **Очереди и стриминг:** Использование Streams для построения надежных шин сообщений с группами потребителей.
- **Состояние сессий:** Где важна персистентность (RDB/AOF) и высокая доступность через Sentinel/Cluster.

### Матрица выбора решения

| Требование | Redis 8.x | Memcached 1.6+ |
| :--- | :--- | :--- |
| Простое кеширование строк | Да | **Предпочтительно (SLRU)** |
| Масштабирование на терабайты (SSD) | Сложно | **Да (Extstore)** |
| Векторный поиск / AI / LLM | **Да (Нативно)** | Нет |
| Документы JSON | **Да (Нативно)** | Нет |
| Сохранение на диск (Persistence) | **Да (Надежно)** | Частично (Extstore) |
| Очереди задач / Streams | **Да** | Нет |
| Многопоточная утилизация CPU | Высокая (I/O) | **Экстремальная** |

## Безопасность

**Redis:** Предлагает зрелую модель **ACL v2**, позволяющую ограничивать доступ к конкретным ключам и категориям команд. Поддерживает аутентификацию через внешние системы (LDAP, AD). TLS 1.3 обеспечивает шифрование трафика.

**Memcached:** Традиционно ориентирован на доверенные внутренние сети. Поддерживает TLS и SASL. **Критически важно:** UDP порт 11211 является вектором для усиления DDoS, поэтому UDP должен быть отключен (`-U 0`) в любой незащищенной среде.

## Облачные форки и Valkey

В 2026 году значительную долю рынка занимает **Valkey** — форк Redis под эгидой Linux Foundation.
- **Совместимость:** 100% совместим с протоколом RESP.
- **Преимущество:** Полностью открытая лицензия BSD, отсутствие вендор-лока.
- **Облака:** Является стандартом де-факто для AWS ElastiCache и GCP Cloud Memorystore после изменения политики лицензирования Redis в 2024 году.

## Диагностика и устранение неисправностей

### Типичные проблемы Redis
1.  **Блокировка потока (Latency Spikes):** Вызвана тяжелыми командами (KEYS, SMEMBERS на огромных сетах). 
    *   *Решение:* Переход на `SCAN`, разделение больших коллекций.
2.  **Фрагментация памяти:** `mem_fragmentation_ratio > 1.5`. 
    *   *Решение:* Включение `activedefrag yes` в конфиге.

### Типичные проблемы Memcached
1.  **Slab Calcification:** Дисбаланс страниц между slab-классами.
    *   *Решение:* Запуск с опциями `slab_reassign` и `slab_automove`.
2.  **Низкий Hit Rate:** Часто вызван недостатком памяти или "вымыванием" кэша.
    *   *Решение:* Увеличение `-m` или настройка **Extstore**.

## Лучшие практики (Best Practices) 2026

1.  **Мониторинг:** Ключевые метрики — `Hit Rate`, `Evictions`, `Latency`. В Redis дополнительно отслеживайте `Ops/sec` и `Blocked clients`.
2.  **Разделение инстансов:** Не используйте один Redis для кэша (где допустимо вытеснение) и для критической БД/очередей.
3.  **Сетевой тюнинг:** На Linux-серверах увеличивайте `net.core.somaxconn` до 65535 и отключайте Transparent Huge Pages (THP) для Redis.
4.  **Аварийное восстановление:** Для Redis всегда настраивайте Sentinel или Cluster для автоматического failover.

## Дополнительная информация

### Производительность и TCO
Хотя Redis 8.x сократил разрыв в производительности, Memcached остается более эффективным с точки зрения стоимости владения (TCO) при хранении гигантских объемов кэша благодаря **Extstore**. Redis, в свою очередь, экономит ресурсы на уровне приложения за счет атомарных операций, избавляя от циклов "read-modify-write".
