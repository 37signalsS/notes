# Redis vs Memcached

### Определения

**Redis** и **Memcached** — это высокопроизводительные in-memory системы кеширования, предназначенные для снижения нагрузки на основные базы данных и ускорения приложений.

Несмотря на общую цель, они основаны на разных архитектурных решениях, что делает их подходящими для разных сценариев. Этот документ сравнивает их ключевые различия.

---

### Основные концепции

| Аспект | Redis | Memcached |
| :--- | :--- | :--- |
| **Модель данных** | Сложные структуры данных (хэши, списки, множества) с атомарными операциями на сервере. | Простые пары «ключ-значение», где значение — непрозрачный блок данных (blob). Сериализация на клиенте. |
| **Управление памятью**| Гибкий аллокатор (`jemalloc`), политики вытеснения (`LRU`, `LFU` и др.). | `Slab allocator` с классами размеров. Менее гибкий, но предсказуемый. Только `LRU` по `slab-классам`. |
| **Персистентность**| Поддерживается (RDB-снапшоты и AOF-журнал). Может использоваться как основная БД. | Отсутствует. Данные теряются при перезагрузке. Только кеш. |
| **Масштабирование** | Встроенные средства: репликация (`master-slave`), высокая доступность (`Sentinel`), шардирование (`Cluster`). | На стороне клиента через согласованное хеширование. Серверы не знают друг о друге. |
| **Многопоточность** | Однопоточный цикл обработки команд (до v6), мультиплексирование I/O. Потоки для фоновых задач. | Многопоточный. Эффективно утилизирует многоядерные CPU для параллельных `get`/`set` операций. |
| **Функциональность**| Транзакции, `Pub/Sub`, Lua-скрипты, геоданные, потоки. | Базовые операции (`get`, `set`, `delete`) и `CAS` (Check-And-Set) для атомарных обновлений. |

---

### Практические сценарии

#### Когда выбирать Memcached?

Memcached — идеальный выбор для **простого и быстрого кеширования**.

- **Задача:** Снизить нагрузку на БД, кешируя строки, результаты запросов или отрендеренные фрагменты HTML.
- **Требования:** Максимальная производительность на простых операциях `get`/`set`, эффективное использование многоядерных процессоров, простота развертывания.
- **Пример:** В системе много одинаковых тяжелых SQL-запросов. Результат каждого запроса сериализуется и помещается в Memcached. Следующий запрос с теми же параметрами мгновенно получает данные из кеша.

#### Когда выбирать Redis?

Redis подходит для **сложных сценариев**, выходящих за рамки простого кеширования.

- **Задача:** Нужны не просто строки, а сложные структуры данных, или требуется дополнительная функциональность.
- **Требования:** Атомарные операции над структурами (например, добавить элемент в список или увеличить счетчик), надежность (персистентность), очереди задач, аналитика в реальном времени.
- **Пример:** Реализация ленты новостей. Лента пользователя хранится в `Sorted Set`, где `score` — временная метка. Новые посты добавляются атомарно, а получение последних N постов — быстрая операция.

**Пример: профиль пользователя**

- **В Redis:** Профиль хранится как хэш (`HASH`). Можно атомарно обновить одно поле (например, `HINCRBY user:123 posts 1`), не читая и не перезаписывая весь объект.
- **В Memcached:** Профиль хранится как сериализованная строка (JSON). Для обновления одного поля нужно получить всю строку, десериализовать, изменить поле и записать обратно, используя `CAS` для избежания гонки данных.
