# ClickHouse — Производительность и оптимизация

## Тюнинг производительности

Глубокая оптимизация ClickHouse требует настройки как системных параметров, так и способов хранения данных на уровне колонок.

### Конфигурация и лимиты (settings.xml / users.xml)

Настройки разделены на серверные (`config.d/*.xml`) и пользовательские сессии (`users.d/*.xml`).

- **Управление памятью:**
  - `max_memory_usage`: Максимальный объем RAM для одного запроса на одном сервере. Рекомендуется ~50–70% от общей RAM.
  - `max_bytes_before_external_group_by`: Порог, после которого промежуточные данные агрегации сбрасываются на диск. Критично для предотвращения OOM.
- **Таймауты и приоритеты:**
  - `max_execution_time`: Ограничение времени выполнения запроса (защита от "вечных" запросов).
  - `priority`: Приоритет выполнения (ниже число — выше приоритет). Позволяет разделять нагрузку от BI-дашбордов и фоновых ETL-задач.
- **Ресурсы CPU:**
  - `max_threads`: Количество потоков для одного запроса. По умолчанию равно количеству ядер, но для конкурентных сред может быть снижено.

### Сжатие и кодеки (Compression Codecs)

ClickHouse позволяет задавать кодеки для каждой колонки индивидуально, что критично для баланса между скоростью чтения и объемом хранения.

| Кодек | Описание | Рекомендации по применению |
| :--- | :--- | :--- |
| **LZ4** | Стандартный кодек, сверхбыстрая декомпрессия. | По умолчанию для всех типов. Идеален для горячих данных. |
| **ZSTD(level)** | Высокая степень сжатия, выше нагрузка на CPU. | Для исторических (холодных) данных. Уровни 1–3 — баланс, 10+ — архив. |
| **Delta(N)** | Сохраняет разницу между соседними значениями. | Для монотонно растущих чисел (ID, временные метки). Эффективен вместе с LZ4/ZSTD. |
| **DoubleDelta** | Разница разниц (вторая производная). | Идеально для временных рядов (Time-series) с регулярным шагом. |
| **Gorilla** | Алгоритм сжатия чисел с плавающей точкой (FCM). | Для `Float32/Float64` (метрики, показания датчиков). |
| **T64** | Транспонирование 64-битных чисел. | Для разреженных данных, где много нулевых битов. |

**Техническое обоснование:** Декомпрессия данных в ClickHouse обычно происходит быстрее, чем чтение с диска. Поэтому использование сильного сжатия (ZSTD) для I/O-bound запросов может парадоксальным образом ускорить выполнение за счет снижения объема передаваемых данных.

## Оптимизация на уровне запросов и индексов

### Механизм PREWHERE

`PREWHERE` — это специфическая для ClickHouse оптимизация, позволяющая радикально снизить объем читаемых данных.

- **Логика работы:** В классическом `WHERE` ClickHouse читает *все* колонки, указанные в `SELECT` и `WHERE`, для всех гранул, которые не были отсечены разреженным индексом. В `PREWHERE` ClickHouse сначала считывает *только* те колонки, которые участвуют в условии фильтрации. Затем он отфильтровывает ненужные строки и считывает остальные запрошенные колонки *только* для тех строк, которые прошли фильтр.
- **Pushdown:** В большинстве случаев ClickHouse автоматически переносит простые фильтры из `WHERE` в `PREWHERE`, но для сложных выражений или специфических условий может потребоваться ручное указание ключевого слова `PREWHERE`.

### Индексы пропуска данных (Data Skipping Indices)

Вторичные индексы, которые хранят агрегированную информацию о блоках гранул.

- **Принцип действия:** ClickHouse разбивает колонку на блоки (размер задается через `GRANULARITY`). Для каждого блока вычисляется индекс (min/max, bloom filter и др.). При запросе ClickHouse сначала проверяет индекс и, если блок гарантированно не содержит нужных данных, полностью пропускает его чтение.
- **Типы индексов:**
  - `minmax`: Хранит границы значений. Полезен для временных меток, не входящих в основной ключ.
  - `set(N)`: Хранит набор уникальных значений (до N штук). Полезен для колонок с низкой мощностью (например, `status_id`).
  - `bloom_filter([false_positive])`: Позволяет быстро проверить отсутствие значения. Идеален для идентификаторов (UUID, ID), которые редко встречаются.

**Пример использования:**
```sql
CREATE TABLE access_logs (
    event_time DateTime,
    user_id UUID,
    url String,
    INDEX idx_url url TYPE bloom_filter(0.01) GRANULARITY 4
) ENGINE = MergeTree() ORDER BY event_time;
```

## Предварительная агрегация и материализация

### Материализованные представления (Materialized Views)

Работают как "триггеры" на вставку данных. При поступлении пачки данных в исходную таблицу, ClickHouse выполняет запрос, описанный в MV, и записывает результат в целевую таблицу.

- **Преимущество:** Аналитические отчеты строятся мгновенно, так как данные уже предварительно агрегированы.
- **Ограничение:** MV видит только новые вставляемые данные; изменения существующих данных через мутации (`UPDATE/DELETE`) или слияния (`Merge`) не отражаются в MV автоматически.

### Проекции (Projections)

Это "скрытые" копии данных внутри основной таблицы, которые могут иметь другой порядок сортировки или быть предварительно агрегированными.

- **Автоматическая маршрутизация:** В отличие от MV, пользователю не нужно знать о существовании проекции. ClickHouse при выполнении запроса сам проверяет, какая проекция позволит выполнить его быстрее, и прозрачно перенаправляет запрос.
- **Синхронность:** Проекции всегда консистентны с основными данными и обновляются при каждом слиянии (merge) частей.

## Механизмы JOIN

В ClickHouse реализация `JOIN` существенно отличается от традиционных СУБД, так как основной упор сделан на скорость обработки данных в памяти.

### Алгоритмы выполнения JOIN

ClickHouse выбирает алгоритм на основе настроек и объема данных (параметр `join_algorithm`):

- **Hash Join:** Правая таблица полностью считывается в хэш-таблицу в оперативной памяти. Затем левая таблица сканируется построчно для поиска совпадений.
    - *Плюсы:* Самый быстрый метод.
    - *Минусы:* Требует много RAM. Если правая таблица не помещается в память, запрос упадет.
- **Direct Join (Dictionaries):** Ультимативный способ оптимизации соединения со справочниками. Если правая таблица является `Dictionary` (словарем), ClickHouse выполняет прямой поиск по ключу в RAM без построения промежуточных хэш-таблиц для каждого запроса.
- **Merge Join:** Обе таблицы сортируются по ключу соединения и объединяются слиянием. Используется, когда данные не влезают в RAM.
- **Grace Hash Join:** Гибридный метод, разбивающий данные на корзины, которые по очереди обрабатываются в памяти или сбрасываются на диск.

### Специфические настройки ClickHouse

- **`join_use_nulls`:** По умолчанию (0) ClickHouse заполняет несовпавшие строки значениями по умолчанию для типа (0, пустая строка). Установка в 1 включает стандартное поведение SQL (заполнение `NULL`).
- **`max_rows_in_join` / `max_bytes_in_join`:** Лимиты на объем правой таблицы. 
- **`distributed_product_mode`:** Определяет поведение распределенного JOIN (deny, local, global).

**Рекомендация:** Всегда старайтесь помещать меньшую таблицу справа в `JOIN` и активно используйте **Словари** для статических справочников.

## Уровни хранения (TTL и Tiered Storage)

Позволяет оптимизировать стоимость хранения без потери производительности на "горячих" данных.

- **TTL (Time To Live):** автоматическое удаление данных или их перемещение на другой диск/в S3 по истечении времени.
  - `ALTER TABLE t MODIFY TTL date + INTERVAL 1 MONTH DELETE;`
  - `ALTER TABLE t MODIFY TTL date + INTERVAL 1 WEEK TO VOLUME 'cold';`
- **Tiered Storage:** прозрачное объединение SSD (hot) и HDD/S3 (cold) в рамках одной таблицы. ClickHouse сам управляет размещением данных на основе политик хранения.
