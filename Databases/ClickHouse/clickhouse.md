# ClickHouse

## Определения

**ClickHouse** — это колоночная (столбцовая) система управления базами данных (СУБД) для онлайн-обработки аналитических запросов (OLAP — Online Analytical Processing), изначально разработанная в Яндексе для сервиса Яндекс.Метрика.

**Текущая версия:** ClickHouse 26.7 (июль 2026, Stable).

**Сравнение OLAP и OLTP:** ClickHouse относится к классу OLAP-систем, в отличие от транзакционных систем (OLTP — Online Transactional Processing), таких как PostgreSQL.

| Характеристика | OLTP (PostgreSQL) | OLAP (ClickHouse) |
| :--- | :--- | :--- |
| **Назначение** | Транзакции (заказы, профили) | Аналитика (отчёты, агрегации) |
| **Структура хранения** | Строковая | Колоночная |
| **Операции** | Частые вставки/обновления/удаления | Массовые вставки, редкие изменения |
| **Данные** | Нормализованные | Денормализованные |
| **Масштабирование** | Вертикальное / репликация чтения | Горизонтальное (MPP, шардирование) |
| **Гарантии** | ACID | BASE (скорость важнее согласованности) |

## Основные концепции

ClickHouse спроектирован для работы с огромными объемами данных (терабайты и петабайты), обеспечивая выполнение аналитических запросов по миллиардам записей за доли секунды.

### Ключевые особенности

- **Колоночное хранение:** данные хранятся по столбцам. Это обеспечивает высокую степень сжатия и ускоряет агрегацию, так как с диска считываются только необходимые для запроса столбцы.
- **Производительность:** выполнение запросов происходит в 100–1000 раз быстрее строковых СУБД на больших массивах данных.
- **Архитектура MPP (Massively Parallel Processing):** массивно-параллельная обработка данных по принципу Shared-Nothing («без разделяемых ресурсов») — каждый узел независим.
- **Горизонтальное масштабирование:** механизмы репликации и шардирования настраиваются на уровне отдельных таблиц.
- **Параллельные реплики (Parallel Replicas, v24.2+):** возможность использовать ресурсы нескольких реплик одновременно для выполнения одного запроса, что кратно увеличивает скорость обработки данных.
- **SQL-подобный язык:** используется диалект SQL с расширенными функциями для аналитики (массивы, кортежи, лямбда-функции).
- **Отсутствие блокировок:** параллельная обработка упрощена за счет отсутствия блокировок на уровне строк или таблиц.
- **QueryRunner (v26.7+):** движок для асинхронного выполнения запросов, батчинга генерируемых запросов и бенчмаркинга.

### Архитектура хранения: семейство MergeTree

Основой хранения данных является семейство движков `MergeTree`. Основные параметры таблицы:

- **Движок (ENGINE):** определяет способ хранения и обработки (например, `MergeTree`, `ReplicatedMergeTree`).
- **Ключ сортировки (ORDER BY):** задает физический порядок данных на диске. Это критический фактор производительности.
- **Ключ партиционирования (PARTITION BY):** разделяет данные на логические части (партиции) для ускорения обслуживания и удаления старых данных.
- **Проекции (Projections):** позволяют хранить данные в нескольких порядках сортировки одновременно для ускорения разных типов запросов (аналог материализованных представлений внутри таблицы).

**Партиция (part):** минимальная единица хранения. При каждой вставке создаются новые части, которые затем объединяются в фоне.

**Рекомендации по вставке данных:**

- Использовать пакетную загрузку (от 100 000 строк).
- **Асинхронные вставки (Async Inserts):** при невозможности батчинга на стороне приложения следует включить `async_insert = 1`. ClickHouse сам соберет мелкие вставки в батчи.
- Избегать частых вставок мелкими порциями без включенного `async_insert`.

**Мутации:** механизм изменения (`UPDATE`) или удаления (`DELETE`) данных, выполняемый асинхронно путем полной перезаписи затронутых частей данных.

### Репликация и шардирование

**Репликация** обеспечивает отказоустойчивость:

- Координация через **ClickHouse Keeper** (рекомендуется) или Apache ZooKeeper.
- Используются движки семейства `ReplicatedMergeTree`.
- Поддержка Multi-Master: запись возможна в любую реплику.
- Данные копируются между узлами асинхронно.

**Шардирование** обеспечивает горизонтальное масштабирование производительности:

- Используется движок `Distributed`, работающий как «прокси» над локальными таблицами.
- **Ключ шардирования:** определяет распределение данных по узлам. Ошибки в выборе ключа приводят к перекосу данных (data skew).
- **Стратегии распределения:**
  - По хешу ключа (например, `cityHash64(user_id)`) для равномерности.
  - По бизнес-ключу для локализации связанных данных на одном узле.
  - Репликация справочников (полные копии небольших таблиц на каждом узле).

Подробная теория распределенных систем: **[Шардирование и MPP](../Concepts/sharding.md)**.

## Практические сценарии

### Когда переходить на ClickHouse

**Сигналы о том, что PostgreSQL не справляется:**

1. **Медленные агрегаты:** запросы `COUNT`, `SUM`, `GROUP BY` на таблицах более 10–50 млн строк занимают десятки секунд.
2. **Нагрузка от аналитики:** тяжелые отчетные запросы замедляют работу продуктового трафика.
3. **Проблемы с объемами:** таблицы превышают 1–10 ТБ, и вертикальное масштабирование становится нецелесообразным.
4. **Медленные материализованные представления:** обновление данных в PostgreSQL происходит дольше, чем интервал их актуальности.

**Правило 80/20:** если 20% запросов (аналитических) потребляют 80% ресурсов процессора — пора выделять аналитику в отдельную СУБД.

### Когда НЕ использовать ClickHouse

- Требуется полная поддержка транзакций (ACID).
- Объем данных менее 1 ТБ (PostgreSQL обычно справляется).
- Требуются частые точечные обновления или удаления данных.
- В запросах преобладают выборки всех полей строки (`SELECT *`).

### Примеры настройки

**Создание локальной таблицы:**

```sql
CREATE TABLE events (
    event_id UInt64,
    user_id UInt64,
    event_date Date,
    payload String
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_date)
ORDER BY (event_date, user_id);
```

**Создание распределенной таблицы (Distributed):**

```sql
CREATE TABLE events_all AS events
ENGINE = Distributed(cluster_name, default, events, rand());
```

**Работа с JSON (v24.8+):**
ClickHouse автоматически выводит схему и оптимизирует хранение JSON-объектов.

```sql
CREATE TABLE logs (
    timestamp DateTime,
    data JSON
) ENGINE = MergeTree() ORDER BY timestamp;

-- Запрос по вложенному полю
SELECT data.user.id, count() FROM logs GROUP BY data.user.id;
```

### Интеграция с Kafka (ETL-конвейер)

Паттерн реализации:

1. **Таблица Kafka:** интерфейс для чтения из топика (движки `Kafka` или `Kafka2`).
2. **Целевая таблица:** физическое хранилище на диске (`MergeTree`).
3. **Материализованное представление:** триггер, который перекладывает данные из Kafka в целевую таблицу в реальном времени.

**Kafka2 (v26.7+):** новый экспериментальный движок с поддержкой Exactly-once семантики и хранением оффсетов в ClickHouse Keeper.

Детальное руководство: **[Интеграция ClickHouse и Kafka](./clickhouse_kafka_integration.md)**.

## Безопасность и управление доступом

ClickHouse поддерживает современную модель управления доступом на основе ролей (RBAC).

- **Аутентификация:** поддержка паролей (SHA256, Double SHA1), LDAP, Kerberos, SSL-сертификатов.
- **RBAC (Role-Based Access Control):**
  - Создание пользователей: `CREATE USER name IDENTIFIED WITH password BY 'pwd'`.
  - Роли: `CREATE ROLE analyst; GRANT SELECT ON db.* TO analyst;`.
  - Row-Level Security (RLS): фильтрация строк на основе атрибутов пользователя.
- **Именованные коллекции (Named Collections):** безопасный способ хранения параметров подключения (хосты, пароли) к внешним системам (S3, Kafka, PostgreSQL) в конфигурационных файлах вместо SQL-запросов.
- **Квоты (Quotas):** ограничение ресурсов (CPU, RAM, количество запросов) на интервал времени (час, день) для предотвращения "тяжелых" запросов, блокирующих систему.
- **Настройки S3 (v26.7+):** по умолчанию доступ к S3 требует явной конфигурации учетных данных для повышения безопасности.

## Резервное копирование и восстановление

Хотя ClickHouse устойчив к сбоям благодаря репликации, бэкапы необходимы для защиты от логических ошибок или катастрофических сбоев.

- **clickhouse-backup:** стандартный инструмент сообщества для создания снимков (snapshots) и их выгрузки в S3, GCS или Azure.
- **Нативные бэкапы (v22.6+):** команды `BACKUP TABLE ... TO S3(...)` и `RESTORE TABLE ... FROM S3(...)`.
- **Снапшоты файловой системы:** если данные хранятся на EBS/ZFS, можно использовать снимки томов (требуется `FREEZE` таблиц).
- **Синхронизация через `remote`:** использование функции `remote()` для копирования данных между кластерами.

## Мониторинг и диагностика

Эффективная эксплуатация ClickHouse требует глубокого понимания внутренних процессов.

- **Системные таблицы:**
  - `system.query_log`: история всех выполненных запросов (метрики выполнения, использование памяти).
  - `system.parts`: информация о частях данных (размер, сжатие, количество строк).
  - `system.merges`: текущие процессы объединения данных в фоне.
- **Метрики:** встроенный Prometheus экспортер (настраивается в `config.xml`).
- **Трассировка:** поддержка OpenTelemetry для отслеживания пути запроса между узлами кластера.

## Уровни хранения (TTL и Tiered Storage)

Позволяет оптимизировать стоимость хранения без потери производительности на "горячих" данных.

- **TTL (Time To Live):** автоматическое удаление данных или их перемещение на другой диск/в S3 по истечении времени.
  - `ALTER TABLE t MODIFY TTL date + INTERVAL 1 MONTH DELETE;`
  - `ALTER TABLE t MODIFY TTL date + INTERVAL 1 WEEK TO VOLUME 'cold';`
- **Tiered Storage:** прозрачное объединение SSD (hot) и HDD/S3 (cold) в рамках одной таблицы. ClickHouse сам управляет размещением данных.

## Интеграция с BI-системами

ClickHouse является стандартным бэкендом для многих современных систем визуализации данных благодаря сверхвысокой скорости выполнения аналитических запросов.

- **Apache Superset:** нативная поддержка, рекомендуется использовать SQLAlchemy-коннектор.
- **Grafana:** через официальный плагин ClickHouse Data Source. Идеально для построения дашбордов по логам и метрикам.
- **Metabase / Redash:** поддержка через плагины сообщества.
- **Tabix:** встроенный в ClickHouse легковесный open-source веб-интерфейс для SQL-запросов.

## Дополнительная информация

### Типы данных

- **Числовые:** `Int8`–`Int256`, `UInt8`–`UInt256`, `Float64`, `Decimal`.
- **Дата и время:** `Date`, `DateTime`, `DateTime64`.
- **Сложные:** `Array(T)`, `Tuple(...)`, `Map(K, V)`.
- **Специализированные:** `IPv4`, `IPv6`, `UUID`.
- **JSON:** новый структурированный тип (v24.8+) для эффективного хранения полуструктурированных данных с автоматическим выводом схемы.

### Интеграция и экосистема

- **PostgreSQL:** использование движков `PostgreSQL` или `clickhouse_fdw`. Детально: **[Интеграция PostgreSQL и ClickHouse](../PostgreSQL/Integrations/clickhouse.md)**.
- **Kafka:** потоковая обработка данных в реальном времени. Детально: **[Интеграция ClickHouse и Kafka](./clickhouse_kafka_integration.md)**.
- **S3:** объектные хранилища и многоуровневое хранение. Детально: **[Интеграция ClickHouse и S3](./clickhouse_s3_integration.md)**.
- **Материализованные представления (Materialized Views):** в ClickHouse работают как триггеры на вставку данных.
- **ClickHouse Keeper:** замена ZooKeeper, написанная на C++ и интегрированная в ClickHouse.

### Требования к ресурсам


| Ресурс | Минимум | Рекомендуется |
| :--- | :--- | :--- |
| **Процессор (CPU)** | 16 ядер | 32+ ядер |

### Сравнение с другими системами

- **[Greenplum](../greenplum.md):** лучше для сложнейших соединений (JOIN) множества таблиц.
- **[TimescaleDB](../timescaledb.md):** предпочтительнее для временных рядов при небольших объемах данных в рамках PostgreSQL.
- **Elasticsearch:** лучше для полнотекстового поиска, но хуже для числовой аналитики.
