# ClickHouse — Вопросы на собеседовании

**Актуально для:** ClickHouse 26.9.x (Stable) / 26.8.x (LTS)

## Определения

**OLAP (Online Analytical Processing)** — класс систем для аналитической обработки: агрегации по большим объёмам данных.

**LSM-tree (Log-Structured Merge-Tree)** — структура данных, лежащая в основе MergeTree: записи сначала попадают в память, затем сбрасываются на диск и периодически сливаются (merge).

**Sparse index** — разреженный индекс: хранит значения ключа только для первой строки каждой гранулы (не для каждой строки, как B-Tree).

**Granule** — минимальный блок данных (по умолчанию 8192 строк), который ClickHouse читает с диска.

**Part** — независимый каталог на диске с данными одной таблицы; результат одной вставки или merge.

**Mutation** — асинхронная операция изменения данных (`UPDATE`, `DELETE`), перезаписывающая целые части.

## Основные концепции

### Архитектура

**Q: Почему ClickHouse быстр для аналитики?**
- Колоночное хранение: читаются только нужные колонки.
- Векторное выполнение: обработка блоками с SIMD.
- Разреженный индекс: отсечение гранул без B-Tree.
- Сжатие: данные одного типа сжимаются лучше.

**Q: Чем ClickHouse отличается от PostgreSQL?**
- ClickHouse — колоночная OLAP; PostgreSQL — строковая OLTP.
- ClickHouse не имеет ACID-транзакций, но быстрее в 1000 раз на агрегатах.
- ClickHouse хранит индекс на уровне гранул, а не на уровне строк.

**Q: Что такое MergeTree?**
- Семейство движков на основе LSM-дерева: вставки создают части, фоновые процессы сливают их.
- Данные физически отсортированы по `ORDER BY`.

**Q: Что такое гранула?**
- Минимальный блок чтения (8192 строк по умолчанию). Все индексы пропуска данных работают на уровне гранул.

### Индексы

**Q: Чем разреженный индекс ClickHouse отличается от B-Tree?**
- B-Tree хранит ссылку на каждую строку; разреженный индекс — только первое значение ключа каждой гранулы. Экономит RAM и диск, но требует сортировки данных.

**Q: Что такое Data Skipping Indices?**
- Вторичные индексы (minmax, set, bloom_filter, text), хранящие агрегированную информацию о блоках гранул. Позволяют пропускать чтение блоков.

**Q: Когда использовать bloom_filter?**
- Для колонок с высокой кардинальностью (UUID, ID), когда нужно проверить отсутствие значения.

### Движки

**Q: Чем ReplacingMergeTree отличается от MergeTree?**
- ReplacingMergeTree удаляет дубликаты по ключу сортировки **только при merge**. Дедупликация не гарантирована в момент чтения — для гарантии нужен `FINAL` (дорого) или `argMax`.

**Q: Что такое CollapsingMergeTree?**
- Движок для обновления состояний без мутаций: пары строк с `Sign = 1` (состояние) и `Sign = -1` (отмена) аннигилируются при merge.

**Q: Что такое VersionedCollapsingMergeTree?**
- Расширение CollapsingMergeTree с полем `version`: допускает вставку в произвольном порядке (версия определяет актуальность).

**Q: Когда НЕ использовать ClickHouse?**
- Частые UPDATE/DELETE по одной строке, транзакции, точечные запросы по ID, высококонкурентная OLTP-нагрузка.

### Репликация и кластер

**Q: Как работает репликация в ClickHouse?**
- `ReplicatedMergeTree`: данные передаются напрямую между узлами (HTTP/Native TCP), метаданные (логи, список частей) — через Keeper/ZooKeeper.

**Q: Что такое insert_quorum?**
- Синхронная запись: запрос возвращается только после подтверждения от N реплик. RPO = 0, но растёт латентность вставки.

**Q: Что такое Distributed-таблица?**
- Виртуальная таблица, проксирующая запросы на локальные таблицы каждого шарда. Не хранит данные.

**Q: Что такое ClickHouse Keeper?**
- Нативный сервис координации (аналог ZooKeeper) на алгоритме Raft.

### Производительность

**Q: Что такое PREWHERE?**
- Фильтр, применяемый до чтения основных колонок: сначала читаются только колонки условия, отфильтровываются строки, затем дочитываются остальные колонки.

**Q: Что такое External Aggregation?**
- Сброс промежуточных хэш-таблиц GROUP BY на диск при нехватке RAM. Падение производительности в 10–50 раз.

**Q: Как оптимизировать ORDER BY?**
- Первая колонка — фильтр по времени или полю с высокой селективностью; далее — колонки с высокой кардинальностью; избегать низкой кардинальности в начале.

**Q: Что такое TTL в ClickHouse?**
- Time To Live: автоматическое удаление (`DELETE`), перемещение (`TO DISK`/`TO VOLUME`) или агрегация (`GROUP BY`) данных по истечении времени.

## Практические сценарии

### Задача: дедупликация событий

**Решение:** `ReplacingMergeTree(version)` + `argMax` в запросе (вместо `FINAL`):

```sql
CREATE TABLE events (
    event_id UInt64,
    version UInt64,
    payload String
) ENGINE = ReplacingMergeTree(version)
ORDER BY event_id;

-- Гарантированная дедупликация без FINAL
SELECT event_id, argMax(payload, version)
FROM events
GROUP BY event_id;
```

### Задача: обновление состояния без мутаций

**Решение:** `CollapsingMergeTree(sign)`:

```sql
CREATE TABLE user_state (
    user_id UInt64,
    name String,
    sign Int8
) ENGINE = CollapsingMergeTree(sign)
ORDER BY user_id;

-- Вставка нового состояния
INSERT INTO user_state VALUES (1, 'Alice', 1);
-- Отмена старого состояния
INSERT INTO user_state VALUES (1, 'Alice', -1);
-- Новое состояние
INSERT INTO user_state VALUES (1, 'Alice Smith', 1);

-- Чтение актуального состояния
SELECT user_id, name, sum(sign) AS s
FROM user_state
GROUP BY user_id, name
HAVING s > 0;
```

### Задача: быстрое удаление старых данных

**Решение:** `PARTITION BY` + `DROP PARTITION`:

```sql
CREATE TABLE logs (
    event_time DateTime,
    message String
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(event_time)
ORDER BY event_time;

-- Мгновенное удаление за месяц
ALTER TABLE logs DROP PARTITION '202601';
```

## Устранение неисправностей

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `Too many parts` | Мелкие вставки | Батчинг, `async_insert` |
| `Memory limit exceeded` | Большой GROUP BY/JOIN | `PREWHERE`, External Aggregation |
| Медленный `SELECT count()` | Нет оптимизации | `count()` оптимизирован; проверить `FINAL` |
| `FINAL` медленный | Дедупликация на лету | Использовать `argMax` вместо `FINAL` |
| Реплика отстаёт | Сеть/диск | `system.replicas`, `absolute_delay` |

## Лучшие практики

1. **ORDER BY** — самое важное решение; проектировать под паттерн запросов.
2. **PREWHERE** — для тяжёлых фильтров.
3. **Батчинг вставок** — 10k–100k строк.
4. **LowCardinality** — для строк с малым числом уникальных значений.
5. **Словари** — для JOIN со справочниками.
6. **TTL** — для автоматического управления жизненным циклом данных.
7. **Мониторинг** — `system.merges`, `system.parts`, `system.query_log`.
