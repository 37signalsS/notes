# ClickHouse — Архитектура и внутреннее устройство

**Актуально для:** ClickHouse 26.9.x (Stable) / 26.8.x (LTS)

Общие термины (ClickHouse, OLAP, MPP, Shared-Nothing) и обзор возможностей — в **[Обзоре ClickHouse](./clickhouse.md)**. Этот файл описывает внутреннее устройство: как хранятся данные, как устроены индексы и как выполняется запрос.

## Определения

**MergeTree** — семейство движков таблиц, являющееся фундаментом хранения данных; основано на LSM-дереве с фоновым слиянием мелких частей в крупные.

**LSM-дерево (Log-Structured Merge-Tree)** — структура данных, оптимизированная для записей: новые данные сбрасываются на диск в неизменяемые части (parts), которые периодически сливаются (merge) в фоновом режиме.

**Гранула (Granule)** — минимальный блок данных, читаемый ClickHouse с диска. Размер задается параметром `index_granularity` (по умолчанию 8192 строк). Все индексы пропуска данных работают на уровне гранул.

**Часть (Part)** — неизменяемый каталог на диске с данными одной таблицы. ClickHouse выполняет запросы параллельно по частям. Формат части — `Wide` (каждая колонка в отдельном файле) или `Compact` (все колонки в одном файле) — определяется при записи по порогам `min_bytes_for_wide_part` и `min_rows_for_wide_part`.

**Разреженный индекс (Sparse Index)** — индекс, хранящий значения ключа только для первой строки каждой гранулы. В отличие от B-Tree (PostgreSQL), который хранит ссылку на каждую строку, разреженный индекс ClickHouse позволяет быстро отсекать ненужные диапазоны данных.

**External Aggregation** — механизм, при котором промежуточные результаты агрегации (хэш-таблицы) не помещаются в RAM и сбрасываются на диск, что приводит к падению производительности в 10–50 раз.

**Мутация (Mutation)** — операция изменения данных в ClickHouse (`UPDATE`, `DELETE`, `MATERIALIZE`), которая перезаписывает целые части (parts) и выполняется асинхронно.

**Data Skipping Index** — вторичный индекс (например, `bloom_filter`, `minmax`, `set`), ускоряющий отсечение данных на уровне гранул.

**Проекция (Projection)** — скрытая копия данных внутри таблицы с другим порядком сортировки или предварительной агрегацией, выбираемая оптимизатором автоматически.

**ClickHouse Keeper** — нативный сервис координации (Raft-консенсус), совместимый с протоколом ZooKeeper, используемый для метаданных репликации и DDL-очередей.

**Векторное выполнение (Vectorized Execution)** — обработка данных блоками (пачками) вместо построчной. Позволяет эффективно использовать SIMD-инструкции процессора (SSE 4.2, AVX, AVX2, AVX-512) и кэши L1/L2/L3.

## Базовые концепции

### Колоночное хранение

В отличие от традиционных строковых СУБД (PostgreSQL, MySQL), ClickHouse хранит значения каждой колонки в отдельном файле (формат `Wide`).

- **Преимущество I/O:** С диска считываются только те колонки, которые явно указаны в запросе. Если в таблице 100 колонок, а запрос использует 2, объем чтения сокращается в 50 раз.
- **Эффективное сжатие:** Данные одного типа, расположенные последовательно, сжимаются значительно лучше. Например, последовательность идентификаторов или меток времени сжимается в 10–100 раз эффективнее, чем разнородные строки.
- **Кодеки сжатия:** для каждой колонки можно задать кодек (`LZ4`, `ZSTD(N)`, `Delta`, `DoubleDelta`, `Gorilla`, `T64`). **С 26.9 сжатие по умолчанию изменено с LZ4 на ZSTD(3):** для данных колонок `MergeTree` оно стало размерно-зависимым — `LZ4` для частей меньше 100 МБ и `ZSTD(3)` для частей от 100 МБ; сетевое взаимодействие (client/server, server/server) перешло на `ZSTD(3)`. Откат — через настройку `compatibility` или явный `CODEC(LZ4)` на колонке.
- **Декомпрессия обычно быстрее чтения с диска:** сильное сжатие (ZSTD) для I/O-bound запросов может парадоксально ускорить выполнение за счёт снижения объёма передаваемых данных.

Выбор кодеков и примеры — в **[Производительности](./clickhouse-performance.md#сжатие-и-кодеки)**.

### Векторное выполнение (SIMD)

ClickHouse обрабатывает данные не построчно, а блоками (векторами).

- **SIMD (Single Instruction, Multiple Data):** специализированные инструкции процессора (SSE 4.2, AVX, AVX2, AVX-512) выполняют одну операцию над множеством элементов данных за один такт.
- **Кэш-эффективность:** блочная обработка позволяет данным оставаться в кэшах L1/L2/L3 максимально долго, минимизируя обращения к медленной оперативной памяти.

**Требования к CPU (по документации ClickHouse):**

- Официальные бинарные сборки требуют **SSE 4.2** на x86_64 — это единственное жёсткое требование. На CPU без SSE 4.2, а также на AArch64 и PowerPC64LE ClickHouse можно запустить только сборкой из исходников.
- Docker-образ amd64 требует уровень **x86-64-v3** (AVX2, BMI1, BMI2, F16C, FMA, LZCNT, MOVBE, XSAVE) — поддерживается практически всеми x86 CPU начиная с 2015 года.
- **AVX-512 не является обязательным:** ClickHouse использует доступные SIMD-инструкции по возможности; при их отсутствии векторное выполнение не отключается целиком, а работает на доступном уровне.

```bash
grep -q sse4_2 /proc/cpuinfo && echo "SSE 4.2 supported" || echo "SSE 4.2 not supported"
# → SSE 4.2 supported
```

### Параллелизм и масштабирование

- **Внутриузловой параллелизм:** один запрос может задействовать все доступные ядра процессора (настройка `max_threads`, по умолчанию равна числу ядер).
- **Parallel Replicas:** один запрос распределяется по нескольким репликам одного шарда — каждая реплика читает свой диапазон гранул, координатор собирает агрегируемые состояния и формирует ответ. В OSS доступны с 23.3 (экспериментально), в beta с 24.12 (настройки `parallel_replicas_mode`, `enable_parallel_replicas`); также доступны в ClickHouse Cloud. Ограничения: не работает с `FINAL`, проекции не используются, сложные запросы (CTE, подзапросы, JOIN) могут деградировать. Настройки и кейсы — в **[Высокой конкурентности](./clickhouse-high-concurrency.md#parallel-replicas)**.
- **Ограничение конкурентности:** `max_concurrent_queries`, приоритеты запросов (`priority`) и пользовательские профили — механизмы очереди и приоритизации, защищающие критические пайплайны от тяжёлых аналитических задач. Детали — в **[Производительности](./clickhouse-performance.md#параметры-серверного-конфига-configxml)** и **[Высокой конкурентности](./clickhouse-high-concurrency.md)**.

### Связь архитектуры с оборудованием и ОС

Проектные решения ClickHouse напрямую зависят от характеристик hardware:

- **CPU и SIMD:** см. выше — SSE 4.2 — минимум для официальных сборок; AVX2/AVX-512 ускоряют, но не обязательны.
- **RAM и External Aggregation:** ClickHouse выполняет агрегации и JOIN в оперативной памяти. Недостаток RAM ведёт к External Aggregation — сбросу хэш-таблиц на диск с падением производительности в 10–50 раз, либо к ошибке `MEMORY_LIMIT_EXCEEDED` (Code 241) при превышении `max_memory_usage`.
- **Диски и MergeTree:** движок постоянно выполняет фоновые слияния (merges). HDD с высокой задержкой блокируют процессы записи и ведут к ошибке `Too many parts` (Code 252). Требуются SSD/NVMe.
- **Лимиты ОС:** `nofile` не менее 262144 — ClickHouse хранит каждую колонку в отдельном файле, и при большом числе таблиц стандартных 1024–4096 быстро исчерпывается.

Рецепты настройки ОС (планировщик диска, THP, sysctl, systemd) — в **[Эксплуатации](./clickhouse-operations.md#подготовка-ос-linux-tuning)** и **[Файловой системе и хранении](./clickhouse-filesystem-storage.md)**.

## Архитектура хранения: семейство MergeTree

Движки семейства `MergeTree` являются фундаментом хранения в ClickHouse. Их работа основана на принципах LSM-деревьев (Log-Structured Merge-Tree).

### Основные параметры таблицы

1.  **ORDER BY (Ключ сортировки):** Определяет физический порядок данных на диске. Это самый важный параметр. Данные в файлах колонок отсортированы именно по этому ключу.
2.  **PRIMARY KEY (Первичный ключ):** Используется для построения разреженного индекса. По умолчанию совпадает с `ORDER BY`. В ClickHouse первичный ключ не гарантирует уникальность, а служит только для ускорения поиска.
3.  **PARTITION BY (Ключ партиционирования):** Разделяет таблицу на крупные логические блоки (партиции), обычно по времени (месяц, день). Позволяет мгновенно удалять старые данные (`DROP PARTITION`) и ускоряет запросы, отсекая ненужные партиции.
4.  **SAMPLE BY:** Позволяет выполнять запросы на подмножестве данных (сэмплирование) для мгновенного получения приблизительных результатов.

### Параметры, влияющие на поведение MergeTree

Ключевые настройки движка (задаются в `SETTINGS` таблицы, через `ALTER TABLE ... MODIFY SETTING` или в секции `<merge_tree>` файла `config.xml`; актуальные значения видны в `system.merge_tree_settings`):

| Параметр | По умолчанию | Влияние на архитектуру |
| :--- | :--- | :--- |
| `index_granularity` | 8192 | Размер гранулы в строках. Меньше — точнее отсечение разреженным индексом, но больше индекс в RAM. Для неравномерно распределённых данных работает адаптивная гранулярность (`index_granularity_bytes`). |
| `merge_with_ttl_timeout` | 14400 (4 часа) | Минимальный интервал между TTL-мержами (DELETE/TO DISK). TTL применяется не мгновенно, а при слиянии. |
| `merge_max_block_size` | 8192 | Максимальный блок строк при слиянии; влияет на потребление RAM при merge. |
| `number_of_free_entries_in_pool_to_lower_max_size_of_merge` | 8 | Порог свободных слотов в фоновом пуле для адаптивного снижения размера слияний при высокой нагрузке. |
| `max_partitions_per_insert_block` | 100 | Сессионная настройка (не настройка MergeTree): лимит партиций в одном INSERT-блоке; при превышении — предупреждение или ошибка (управляется `throw_on_max_partitions_per_insert_block`). Защита от ошибочного дробления данных на мелкие партиции. |

Полный справочник настроек производительности — в **[Производительности](./clickhouse-performance.md)**.

### Анатомия данных на диске

Каждая вставка (INSERT) создаёт новую **часть данных (Part)**. Внутри директории части находятся:
- **`[column].bin`:** Сжатые данные конкретной колонки.
- **`[column].mrk`:** Файлы засечек (marks), связывающие индекс со смещениями в `.bin` файле.
- **`primary.idx`:** Разреженный индекс, содержащий значения первичного ключа для каждой гранулы.
- **`count.txt`:** Общее количество строк в части.
- **`checksums.txt`:** Контрольные суммы всех файлов части (проверка целостности при репликации и бэкапах).

**Гранула (Granule):** Минимальный набор строк (по умолчанию 8192), для которого создается запись в индексе. ClickHouse читает данные только целыми гранулами.

**Формат части (Wide/Compact):** при записи части размером от 10 МБ (OSS-сборки; в Cloud-сборках порог 1 ГБ) или более `min_rows_for_wide_part` строк используется формат `Wide` — каждая колонка в отдельном файле, что ускоряет чтение подмножества колонок. Менее крупные части (типично мелкие INSERTы) записываются как `Compact` — все колонки в одном файле.

### Процесс слияния (Merge)

Фоновые процессы ClickHouse постоянно объединяют мелкие части в более крупные.
- В процессе слияния данные пересортировываются.
- Выполняются специфические функции движков (дедупликация в `ReplacingMergeTree`, агрегация в `AggregatingMergeTree`).
- Удаляются строки, помеченные на удаление (мутации), и применяются TTL-правила.
- **Алгоритмы слияния:** `Horizontal` (все колонки сливаются вместе) и `Vertical` (колонки сливаются отдельно — экономит RAM на широких таблицах). Тип и алгоритм текущего слияния видны в `system.merges` (колонки `merge_type`, `merge_algorithm`).

### Специализированные движки

| Движок | Логика работы | Основной кейс |
| :--- | :--- | :--- |
| **ReplacingMergeTree** | Оставляет последнюю версию строки по ключу сортировки **только при merge**. | Хранение состояний, дедупликация событий. |
| **SummingMergeTree** | Суммирует числовые колонки с одинаковым ключом. | Предварительная агрегация метрик. |
| **AggregatingMergeTree** | Объединяет промежуточные состояния агрегатных функций. | Инкрементальные материализованные представления. |
| **CollapsingMergeTree** | Аннигилирует пары строк с флагом `Sign` (1/-1). | Обновление состояний без мутаций. |
| **VersionedCollapsingMergeTree** | Как `CollapsingMergeTree`, но с полем `version`: допускает вставку в произвольном порядке. | Обновление состояний при неупорядоченной вставке. |

**Важная семантика ReplacingMergeTree:** дедупликация происходит **только в процессе слияния (merge)**, а не при чтении. Это значит:
- Сразу после вставки дубликаты могут присутствовать в результатах `SELECT`.
- Для гарантированной дедупликации используйте `FINAL` (дорого — пересоздаёт merge на лету) или `argMax()`/`argMin()` в запросе.
- Дедупликация не гарантируется в рамках одной части — только при слиянии частей.

**VersionedCollapsingMergeTree(sign, version):**
- `sign` (`Int8`): `1` — состояние, `-1` — отмена.
- `version` (`UInt*`, `Date`, `DateTime`): монотонно растущая версия строки.
- В отличие от `CollapsingMergeTree`, допускает вставку в произвольном порядке: версия определяет актуальность.
- Паттерн запроса:
  ```sql
  SELECT UserID, sum(PageViews * Sign) AS views, Version
  FROM user_activity
  GROUP BY UserID, Version
  HAVING sum(Sign) > 0;
  ```

### Производственные настройки MergeTree

Настройки, критичные для стабильности записи при высокой нагрузке (задаются в `config.xml` в секции `<merge_tree>`, в `SETTINGS` таблицы или через `ALTER TABLE ... MODIFY SETTING`):

| Настройка | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `parts_to_delay_insert` | 1000 | При превышении числа активных частей в партиции — искусственная задержка вставки (бэкпрессур). |
| `parts_to_throw_insert` | 3000 | При превышении — отклонять вставку с ошибкой `Too many parts` (Code 252). |
| `max_parts_in_total` | 100000 | Максимальное суммарное число частей во всех партициях таблицы. |
| `max_delay_to_insert` | 1 (сек) | Максимальная задержка вставки при бэкпрессуре. |
| `min_delay_to_insert_ms` | 10 | Минимальная задержка вставки при бэкпрессуре. |
| `max_avg_part_size_for_too_many_parts` | 1 GB | Проверка `parts_to_*` активна, только если средний размер части не превышает порог. |

**Формула задержки (с 23.1):**
```
allowed_parts_over_threshold = parts_to_throw_insert - parts_to_delay_insert
parts_over_threshold = parts_count_in_partition - parts_to_delay_insert + 1
delay_milliseconds = max(min_delay_to_insert_ms, (max_delay_to_insert * 1000) * parts_over_threshold / allowed_parts_over_threshold)
```

**Мониторинг:**
```sql
-- Число частей на партицию (должно быть << parts_to_delay_insert)
SELECT database, table, partition, count() AS parts
FROM system.parts
WHERE active
GROUP BY database, table, partition
ORDER BY parts DESC;

-- Текущие значения настроек
SELECT name, value FROM system.merge_tree_settings
WHERE name IN ('parts_to_delay_insert', 'parts_to_throw_insert', 'max_parts_in_total');
```

### Выбор движка для SRE-сценариев

| Сценарий | Рекомендуемый движок | Обоснование |
| :--- | :--- | :--- |
| Иммутабельные события (логи, метрики) | `MergeTree` | Максимальная скорость вставки, простое обслуживание. |
| События с возможными дубликатами | `ReplacingMergeTree` | Дедупликация на уровне движка без внешних ETL. |
| Предагрегированные метрики | `SummingMergeTree` или `AggregatingMergeTree` | Автоматическая агрегация при слиянии, снижение нагрузки на запросы. |
| Изменяемые сущности (состояния) | `CollapsingMergeTree` | Без мутаций, но требует строгой логики `Sign`. |
| Частые UPDATE/DELETE | **Не ClickHouse** | MergeTree не оптимизирован для этого; используйте реляционную СУБД. |

## Внутреннее устройство индексации

ClickHouse использует многоуровневую систему индексов для минимизации объема сканирования.

### Разреженный индекс (Sparse Index)

В отличие от B-Tree (PostgreSQL), который хранит ссылку на каждую строку, разреженный индекс ClickHouse хранит значения ключа только для первой строки каждой гранулы.

**Алгоритм поиска:**
1. Бинарный поиск по `primary.idx` в RAM для нахождения диапазонов гранул, которые могут содержать данные.
2. Чтение соответствующих `.mrk` файлов для получения смещений в сжатых файлах данных.
3. Чтение и декомпрессия только выбранных гранул из `.bin` файлов.

### Вторичные индексы (Data Skipping Indices)

Позволяют дополнительно ускорять фильтрацию по колонкам, не входящим в PRIMARY KEY:

| Тип индекса | Использование | Ограничение |
| :--- | :--- | :--- |
| `minmax` | Диапазонные фильтры по числу/дате | Только минимум/максимум на гранулу. |
| `set` | Точные фильтры по низкой кардинальности | Размер индекса растет с количеством значений. |
| `bloom_filter` | Проверка наличия значения при высокой кардинальности | Вероятность ложноположительных срабатываний. |
| `ngrambf_v1` | Поиск по подстрокам | Только для строк; **deprecated с 26.2** — для полнотекстового поиска предпочтительнее встроенный text-индекс (inverted index). |

**Пример DDL:**
```sql
CREATE TABLE logs_skip_idx (
    timestamp DateTime,
    service_name String,
    status LowCardinality(String),
    message String
) ENGINE = MergeTree()
ORDER BY (timestamp, service_name)
INDEX idx_status (status) TYPE minmax;
```

Миграция с `ngrambf_v1`/`tokenbf_v1` на text-индекс, токенизаторы и функции `hasToken`/`hasPhrase` — в **[Полнотекстовом поиске](./clickhouse-full-text-search.md)**.

### Проекции (Projections)

Позволяют хранить данные одной таблицы в нескольких порядках сортировки или с разной агрегацией одновременно.
- Автоматически обновляются при вставке и слиянии.
- Оптимизатор сам выбирает наиболее подходящую проекцию для запроса.
- Аналог материализованного представления, но "внутри" таблицы и прозрачно для пользователя.

**Важно SRE:** Проекции увеличивают объем хранимых данных и нагрузку на фоновые слияния. Используйте их для таблиц с выраженными разными паттернами доступа, но не создавайте проекции "на всякий случай".

## Жизненный цикл запроса

### Этапы обработки

1.  **Парсинг и анализ:** SQL-запрос превращается в AST (Abstract Syntax Tree). Проверяются права, существование таблиц и типов. **С 26.9 единственный путь анализа запросов — Query Analyzer** (по умолчанию с 24.3; в 26.9 старый анализатор и настройка `enable_analyzer` удалены, отключить analyzer нельзя).
2.  **Оптимизация:**
    - Упрощение выражений.
    - Перенос фильтров из `WHERE` в `PREWHERE` (чтение только столбцов фильтра перед чтением остальных данных).
    - Выбор проекций или индексов.
3.  **Построение Pipeline:** Создание плана параллельного выполнения, учитывающего количество ядер и шардов.
4.  **Выполнение (Execution):** Параллельное чтение гранул, фильтрация, агрегация в оперативной памяти с использованием SIMD.

План выполнения можно inspectировать до запуска (`EXPLAIN PLAN`, `EXPLAIN PIPELINE`, `EXPLAIN ANALYZE`, `EXPLAIN ESTIMATE`) — синтаксис и разбор вывода в **[Производительности](./clickhouse-performance.md#explain-и-анализ-плана)**.

### Распределенное выполнение

Для `Distributed` таблиц:
- **Initiator:** Принимает запрос, разбивает его на подзапросы для каждого шарда.
- **Worker:** Выполняет локальный запрос над своим `MergeTree`, выполняет частичную агрегацию.
- **Initiator:** Собирает ответы от всех Worker-ов, выполняет финальную агрегацию и сортировку, возвращает результат.

Репликация, шардирование, `insert_quorum`, ClickHouse Keeper и настройки `Distributed`-таблиц — в **[Кластерном управлении](./clickhouse-cluster.md)**.

## Практические сценарии

### Проектирование ключа ORDER BY

Оптимальный порядок колонок в `ORDER BY` определяется паттерном запросов — первой должна стоять колонка, по которой чаще всего отсекают данные:

**Сценарий A — запросы фильтруют по времени** (типично для логов и метрик): `ORDER BY (timestamp, service_name)`. Диапазон по времени отсекается разреженным индексом, внутри диапазона данные упорядочены по сервису.

**Сценарий B — запросы фильтруют только по сервису** (агрегации по сервисам за весь период): `ORDER BY (service_name, timestamp)`. `service_name` имеет меньшую мощность (cardinality), гранулы конкретного сервиса лежат рядом, и индекс отсекает все остальные сервисы.

**Антипаттерн:** `ORDER BY (timestamp, service_name)` при частых запросах `WHERE service_name = 'x'` без условия по времени — ClickHouse придётся сканировать всю таблицу, так как `service_name` находится на втором месте и данные перемешаны по времени.

### Использование PREWHERE для тяжелых запросов

ClickHouse автоматически переносит простые фильтры из `WHERE` в `PREWHERE`, но для сложных выражений полезно указать его вручную. Механика: сначала читается только колонка условия (например, `severity`), гранулы без совпадений отбрасываются, тяжелые колонки (`message`, `stacktrace`) дочитываются только для выживших строк. Теория, механика pushdown и примеры — в **[Производительности](./clickhouse-performance.md#prewhere)**.

### Мониторинг здоровья слияний

Фоновые слияния — критически важный архитектурный процесс. Их зависание ведет к фрагментации и `Too many parts`.

```sql
-- Активные слияния (is_mutation = 0 — только merges, без мутаций)
SELECT database, table, elapsed, progress, num_parts, bytes_read_uncompressed, memory_usage
FROM system.merges
WHERE is_mutation = 0;
```

### Диагностика фрагментации

```sql
-- Количество частей на таблицу
SELECT database, table, count() as parts, sum(bytes_on_disk)/1024/1024 as mb
FROM system.parts
WHERE active = 1
GROUP BY database, table
ORDER BY parts DESC
LIMIT 10;
```

## Troubleshooting

Архитектурные корни типичных сбоев; подробные runbook-процедуры — в **[Эксплуатации](./clickhouse-operations.md#устранение-неисправностей)**.

| Проблема | Архитектурная причина | Решение |
| :--- | :--- | :--- |
| **Too many parts (Code 252)** | Мелкие частые INSERTы опережают фоновые слияния; превышены `parts_to_delay_insert`/`parts_to_throw_insert` в партиции. | Батчинг 10 000–100 000 строк, `async_insert = 1`, укрупнение партиций; проверка `system.parts`. |
| **External Aggregation (падение скорости в 10–50 раз)** | Хэш-таблицы GROUP BY/JOIN не помещаются в `max_memory_usage` и сбрасываются на диск. | Увеличить RAM, поднять `max_bytes_before_external_group_by`, добавить `PREWHERE`, сократить выборку. |
| **MEMORY_LIMIT_EXCEEDED (Code 241)** | Запрос превысил лимит памяти до перехода на диск. | `PREWHERE`, сужение выборки колонок, увеличение `max_memory_usage` для профиля пользователя. |
| **Merge backlog, рост числа частей** | Не хватает I/O диска на слияния, либо слияния остановлены (`SYSTEM STOP MERGES`). | `iostat -xz 1` для диска, `SYSTEM START MERGES`, мониторинг `system.merges`. |
| **Мутация зависла** | Мутации переписывают целые части и конкурируют за I/O с merges. | `system.mutations`, разбить операцию на партии, `SYSTEM STOP MERGES` как крайняя мера. |

## Лучшие практики

1. **ORDER BY под паттерн запросов** — первая колонка — самая частая в фильтрах; изменение ключа сортировки (`MODIFY ORDER BY`) требует перестроения всех данных.
2. **Батчинг вставок** — 10 000–100 000 строк за раз; мелкие вставки создают фрагментацию и нагружают фоновые слияния.
3. **Мутации — не для частых обновлений** — `UPDATE`/`DELETE` переписывают целые части; для изменяемых состояний используйте `CollapsingMergeTree`/`ReplacingMergeTree` или реляционную СУБД.
4. **TTL вместо ручной очистки** — автоматизирует удаление, перемещение и перекомпрессию старых данных.
5. **Мониторинг фоновых процессов** — `system.merges`, `system.mutations`, `system.parts` в Prometheus/Grafana.
