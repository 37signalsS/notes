# Резервное копирование и восстановление в SQL Server

Специфичные для Microsoft SQL Server инструменты, модели восстановления и подходы. Общие теоретические основы (логические и физические бэкапы, правило 3-2-1, метрики RPO/RTO) описаны в разделе **[Стратегии резервного копирования баз данных](../Concepts/backups.md)**.

## Определения

- **Модель восстановления (Recovery Model)** — свойство базы данных, управляющее процессом регистрации транзакций в журнале, необходимостью резервного копирования журнала и доступными операциями восстановления.
- **Журнал транзакций (Transaction Log)** — файл с расширением `.ldf`, обеспечивающий атомарность, согласованность, изоляцию и долговечность (ACID). Содержит записи о всех изменениях данных.
- **RPO (Recovery Point Objective)** — максимально допустимый объем потери данных, измеряемый во времени.
- **RTO (Recovery Time Objective)** — максимально допустимое время простоя сервиса до момента восстановления.
- **Point-in-Time Recovery (PITR)** — процесс возврата базы данных в состояние на произвольную метку времени. Доступно только в моделях Full и Bulk-Logged.
- **Tail-Log Backup (Бэкап хвоста журнала)** — резервная копия журнала транзакций, создаваемая перед началом восстановления для фиксации последних изменений, которые еще не были забэкаплены, даже если база данных повреждена.
- **LSN (Log Sequence Number)** — уникальный идентификатор записи в журнале транзакций, используемый SQL Server для синхронизации и последовательного восстановления.
- **VLF (Virtual Log File)** — внутренняя логическая сегментация журнала транзакций. Чрезмерное количество VLF замедляет операции бэкапа и восстановления.
- **Checkpoint (Контрольная точка)** — процесс записи «грязных» страниц из буферного пула на диск, что сокращает время восстановления после сбоя.
- **ADR (Accelerated Database Recovery)** — технология (SQL 2019+), использующая версионирование строк для мгновенного отката транзакций и быстрого восстановления после сбоя.
- **ZSTD (Zstandard)** — алгоритм сжатия (SQL 2025+), обеспечивающий высокую степень компрессии при низкой нагрузке на CPU.
- **Неизменяемый бэкап (Immutable Backup)** — резервная копия, защищенная от удаления или модификации на уровне хранилища (WORM).

## Основные концепции

### Архитектурные основы
Работа бэкапов в SQL Server тесно связана с механизмом **Write-Ahead Logging (WAL)**: изменения сначала фиксируются в журнале транзакций (`.ldf`), а затем записываются в файлы данных (`.mdf`/`.ndf`).

- **Механизм очистки журнала:** в модели `SIMPLE` журнал очищается автоматически при Checkpoint. В моделях `FULL`/`BULK_LOGGED` журнал очищается только после выполнения `BACKUP LOG`. Если лог не бэкапится, файл `.ldf` будет расти до заполнения диска.
- **Цепочка LSN:** каждый бэкап журнала содержит диапазон LSN. Для успешного PITR необходимо наличие непрерывной цепочки всех бэкапов журналов с момента последнего полного бэкапа.
- **Влияние VLF:** если журнал транзакций часто прирастал маленькими порциями, создается избыток VLF. Это приводит к долгому старту базы и замедлению восстановления («Long Recovery Time»). Оптимальное количество VLF — до нескольких сотен.

### Модели восстановления
Настройка выполняется командой: `ALTER DATABASE [DB_NAME] SET RECOVERY [FULL|SIMPLE|BULK_LOGGED]`.

| Модель | PITR | Протоколирование | Очистка лога | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **Simple** | Нет | Минимальное | Авто (Checkpoint) | Test, Dev, Read-only базы |
| **Full** | Да | Полное | После `BACKUP LOG` | Production, Critical Data |
| **Bulk-Logged** | Частично | Оптимизированное | После `BACKUP LOG` | Массовая загрузка данных |

### Типы резервных копий

| Тип | T-SQL пример | Описание |
| :--- | :--- | :--- |
| **Полный (Full)** | `BACKUP DATABASE [DB] TO DISK = '...' WITH COMPRESSION, CHECKSUM` | Копия всех данных + активная часть лога. Точка отсчета для всей цепочки. |
| **Дифференциальный** | `BACKUP DATABASE [DB] TO DISK = '...' WITH DIFFERENTIAL` | Изменения с последнего Full. Накапливается со временем. Ускоряет восстановление. |
| **Журнал (Log)** | `BACKUP LOG [DB] TO DISK = '...'` | Только записи лога. Требуется для PITR. Очищает (truncated) лог. |
| **Только копия (Copy-only)** | `BACKUP DATABASE [DB] TO DISK = '...' WITH COPY_ONLY` | Независимый бэкап, не влияющий на цепочку дифференциальных копий и LSN. |
| **Снапшот (Snapshot)** | `BACKUP DATABASE [DB] TO DISK = '...' WITH SNAPSHOT` | (SQL 2022+) Аппаратный снимок через T-SQL, интегрированный с СХД. |

## Новые возможности (2022–2025)

### SQL Server 2025
- **Бэкапы на вторичных репликах:** полноценная поддержка Full/Differential бэкапов на Secondary репликах Always On Availability Groups. Это позволяет полностью снять I/O нагрузку с первичного узла.
- **Поддержка Managed Identity:** нативная аутентификация через Azure Managed Identity для `BACKUP TO URL`, исключающая хранение секретов (SAS-токенов) в базе данных.
- **ZSTD Сжатие:** новый стандарт компрессии (алгоритм Zstandard), обеспечивающий более высокую плотность упаковки при значительно меньшей нагрузке на CPU по сравнению со стандартным MS_GZIP.

### SQL Server 2022
- **S3-совместимое хранилище:** нативная поддержка записи бэкапов в любые S3-хранилища (AWS S3, MinIO, Pure Storage и др.).
  ```sql
  BACKUP DATABASE [DB] TO URL = 's3://my-bucket/DB.bak'
  WITH CREDENTIAL = 'S3_Access_Credential', COMPRESSION, STATS = 10;
  ```
- **T-SQL Snapshot Backup:** возможность инициировать заморозку I/O и создание аппаратных снимков диска через стандартные команды T-SQL.

## Практические сценарии

### Алгоритм восстановления на момент времени (PITR)
Последовательность действий для восстановления базы в модели **Full** на конкретную дату:

1. **Создание бэкапа хвоста лога (Tail-Log):** фиксирует изменения, произошедшие после последнего бэкапа лога.
   ```sql
   BACKUP LOG [DB] TO DISK = 'C:\Backup\DB_tail.trn' WITH NORECOVERY;
   ```
2. **Восстановление полной копии:** база остается в состоянии `RESTORING`.
   ```sql
   RESTORE DATABASE [DB] FROM DISK = 'C:\Backup\DB.bak' WITH NORECOVERY, REPLACE;
   ```
3. **Восстановление дифференциальной копии:** (если она есть и сокращает цепочку логов).
   ```sql
   RESTORE DATABASE [DB] FROM DISK = 'C:\Backup\DB.diff' WITH NORECOVERY;
   ```
4. **Накат журналов транзакций:** последовательно восстанавливаем логи до нужной точки.
   ```sql
   RESTORE LOG [DB] FROM DISK = 'C:\Backup\DB_log1.trn' WITH NORECOVERY;
   -- Последний лог с указанием времени
   RESTORE LOG [DB] FROM DISK = 'C:\Backup\DB_tail.trn' WITH NORECOVERY, STOPAT = '2026-08-17 12:00:00';
   ```
5. **Завершение восстановления:** перевод базы в ONLINE.
   ```sql
   RESTORE DATABASE [DB] WITH RECOVERY;
   ```

### Валидация бэкапов без фактического восстановления
Обязательный этап проверки целостности файлов перед использованием:
```sql
-- 1. Просмотр метаданных (имя БД, версия, дата)
RESTORE HEADERONLY FROM DISK = 'C:\Backup\DB.bak';

-- 2. Список файлов данных и логов внутри архива
RESTORE FILELISTONLY FROM DISK = 'C:\Backup\DB.bak';

-- 3. Проверка контрольных сумм и структуры (без записи на диск)
RESTORE VERIFYONLY FROM DISK = 'C:\Backup\DB.bak';
```

### Решение типичных проблем
- **Ошибка "Log for database is full":**
  - *Причина:* Журнал транзакций переполнился, так как бэкапы лога не выполняются.
  - *Решение:* Создать бэкап лога или временно переключить базу в `SIMPLE`, если история изменений не важна.
- **Ошибка "LSN mismatch / Chain broken":**
  - *Причина:* Нарушена непрерывность логов (например, кто-то сделал бэкап без `COPY_ONLY` вручную).
  - *Решение:* Сделать новый Full бэкап и восстанавливаться из него.
- **Долгое восстановление (Slow Recovery):**
  - *Причина:* Огромное количество VLF (сотни тысяч). SQL Server вынужден инициализировать их при старте.
  - *Решение:* Выполнить `SHRINK` журнала и `GROW` его фиксированными большими порциями (например, по 8ГБ).

## Автоматизация и инструменты

- **Ola Hallengren's Maintenance Solution:** общепринятый стандарт скриптов для DBA. Позволяет одной командой настроить бэкапы всех баз с ротацией и проверкой.
- **dbatools (PowerShell):** модуль для DevOps-инженеров. Позволяет восстановить всю цепочку бэкапов одной командой `Restore-DbaDatabase`.
- **SQL Server Agent:** встроенный планировщик для запуска T-SQL и PowerShell скриптов по расписанию.

## Безопасность и отказоустойчивость

- **Шифрование бэкапов:** рекомендуется использовать `WITH ENCRYPTION` (AES-256). Сертификат и мастер-ключ должны храниться отдельно.
- **Правило 3-2-1 для SQL Server:**
  - 1 копия: Быстрый локальный диск.
  - 2 копия: Сетевая папка (SMB/NFS).
  - 3 копия: Удаленное объектное хранилище (S3/Azure Blob) с политикой Immutable.
- **Привилегии:** служба SQL Server должна иметь права `Write` на целевую папку, а учетная запись администратора — `db_backupoperator`.
