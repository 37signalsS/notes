# Резервное копирование и восстановление в SQL Server

Специфичные для Microsoft SQL Server инструменты, модели восстановления и подходы. Общие теоретические основы (логические/физические бэкапы, правило 3-2-1, RPO/RTO) — в **[Стратегии резервного копирования баз данных](../Concepts/backups.md)**.

## Определения

- **Модель восстановления (Recovery Model)** — свойство базы данных (не сервера), которое управляет процессом регистрации транзакций, определяет необходимость резервного копирования журнала транзакций и доступные типы операций восстановления.
- **Журнал транзакций (Transaction Log)** — файл с расширением `.ldf`, основа транзакционности и восстановления. Все операции модификации данных (INSERT, UPDATE, DELETE) сначала записываются в журнал транзакций, после чего асинхронно фиксируются на диске. Обеспечивает возможность отката транзакций, восстановления после сбоев и построения цепочек бэкапов.
- **RPO (Recovery Point Objective)** — целевая точка восстановления: сколько данных допустимо потерять. Измеряется во времени (минуты, часы).
- **RTO (Recovery Time Objective)** — целевое время восстановления: насколько быстро сервис должен подняться после аварии.
- **Point-in-Time Recovery (PITR)** — восстановление на произвольный момент времени. Требует наличия бэкапов журнала транзакций.
- **Minimally Logged Operations** — операции с минимальным логированием (массовая вставка через BULK INSERT, SELECT INTO, rebuild индексов при определённых условиях). Логируются не полностью, что ограничивает возможности PITR.

## Модели восстановления

Модель восстановления настраивается **для каждой базы отдельно**. На одном экземпляре SQL Server разные базы могут использовать разные модели в зависимости от требований бизнеса и характера нагрузки.

### Simple

Модель по умолчанию при создании базы данных.

**Характеристики:**

- Журнал транзакций очищается автоматически после завершения каждой транзакции и контрольной точки (checkpoint). Файл `.ldf` переиспользуется внутри выделенного пространства.
- **Не поддерживает** бэкапы журнала транзакций. Доступны только FULL и DIFF.
- Восстановление возможно только на момент последнего FULL или последнего FULL + DIFF. PITR невозможен.
- Минимальные требования к сопровождению: достаточно периодически делать FULL/DIFF по расписанию.

**Сценарии применения:**

- Тестовые и dev-среды, где потеря данных некритична.
- Хранилища данных (DWH) с регулярной загрузкой (например, ежедневный патч из production). Если база упадёт в середине дня, восстановление на начало дня приемлемо.
- Служебные базы без пользовательских данных.
- Ситуации, когда нет выделенного DBA и важна простота.

**Ограничения:**

- При активной записи лог может не успевать очищаться, если транзакции слишком долгие или не завершаются (например, забытый `BEGIN TRAN` без `COMMIT`).
- Не подходит для production-систем с требованиями минимальных потерь данных.

### Full

Основная модель для production-систем.

**Характеристики:**

- Журнал транзакций **не очищается автоматически**. Он сокращается (truncates) только после выполнения `BACKUP LOG`.
- Поддерживает все типы бэкапов: FULL, DIFF, LOG.
- Обеспечивает PITR — восстановление на любой момент времени, для которого есть бэкап лога.
- Требует регулярного `BACKUP LOG`: без него лог будет расти, пока не заполнит выделенное пространство или весь диск.

**Поведение журнала транзакций:**

В Full-модели лог не переиспользуется до тех пор, пока не будет выполнен `BACKUP LOG`. Завершённые транзакции остаются в логе. После бэкапа лога SQL Server помечает завершённые транзакции как освобождённые и может переиспользовать это пространство.

Если `BACKUP LOG` не выполняется:
- При ограниченном размере лога — лог переполнится, все операции записи начнут завершаться с ошибкой.
- При неограниченном росте — лог займёт весь диск.

**Сценарии применения:**

- Production-базы приложений (OLTP, CRM, интернет-магазины).
- Системы с минимально допустимыми потерями данных (RPO 5–15 минут и менее).
- Требует компетентной команды: минимум два человека, способных заменить друг друга.

**Требования к сопровождению:**

- Настройка расписания бэкапов (FULL, DIFF, LOG).
- Мониторинг размера журнала транзакций.
- Регулярное тестовое восстановление.

### Bulk-Logged

Специализированная модель для массовых операций с минимальным логированием.

**Характеристики:**

- По поведению близка к Full: журнал не очищается без `BACKUP LOG`, поддерживаются FULL, DIFF и LOG бэкапы.
- Оптимизирована для minimally logged operations: BULK INSERT, SELECT INTO, rebuild индексов, массовый импорт из CSV.
- При наличии minimally logged операций в интервале бэкапа лога **PITR невозможен** в рамках этого интервала. Восстановление возможно только на начало или конец бэкапа лога.

**Сценарии применения:**

- Краткосрочное переключение перед массовой загрузкой данных (наполнение DWH, интеграция данных из внешних источников).
- Плановое обслуживание: rebuild индексов в maintenance-окно.
- Обязательно возвращать модель обратно на Full после завершения операции.

**Типичный workflow:**

1. База работает в Full-модели.
2. Перед массовой загрузкой переключение на Bulk-Logged.
3. Выполнение массовых операций.
4. Возврат на Full-модель.
5. Немедленный `BACKUP LOG` для фиксации цепочки.

## Типы бэкапов в SQL Server

Три типа бэкапов дополняют друг друга и формируют цепочку восстановления.

| Тип | Описание | Частота |
| :-- | :------- | :------ |
| **FULL** (полный) | Полный снимок базы данных на момент выполнения. Основа любого сценария восстановления. | Раз в сутки (типично); для малых баз — чаще; для очень больших — раз в неделю |
| **DIFF** (дифференциальный) | Все изменения с момента последнего FULL. Выполняется быстрее FULL, сокращает время восстановления. | Раз в несколько часов или ежедневно |
| **LOG** (журнал транзакций) | Все изменения из transaction log за период с момента последнего LOG-бэкапа. Обеспечивает PITR и минимальный RPO. | Раз в 1–15 минут в зависимости от RPO |

### Цепочка восстановления

Стандартная последовательность:

```
FULL (ежедневно) → DIFF (каждые 4–6 часов) → LOG (каждые 5–15 минут)
```

**Влияние на метрики:**

- **RTO:** дифференциальные бэкапы сокращают время восстановления, уменьшая количество LOG-бэкапов для накатывания.
- **RPO:** частота LOG-бэкапов определяет минимальную потерю данных. Раз в 5 минут → RPO ≤ 5 минут; раз в минуту → RPO ≤ 1 минута.

**Производительность LOG-бэкапов:**

Частота бэкапов лога (раз в минуту vs раз в 15 минут) не влияет существенно на производительность. При высокой частоте режутся маленькие кусочки лога, каждый выполняется быстро. При низкой частоте один бэкап больше, но выполняется реже. Общее количество записанных данных сопоставимо. Основная разница — в количестве файлов, которое не является проблемой при автоматизации восстановления.

### Нативные и файловые бэкапы

**Нативные бэкапы** — выполняются средствами SQL Server (`BACKUP DATABASE`, `BACKUP LOG`). Стандартный подход для администрируемых систем.

**Файловые бэкапы** (через VSS, снапшоты ОС) — копирование файлов на уровне файловой системы. Применяется при отсутствии выделенного DBA, когда системный администратор делает снапшоты всего сервера. Имеет свои плюсы и минусы; подходит для небольших баз без выделенного штата.

## Стратегии бэкапов: практические примеры

### Production-система (OLTP, CRM, интернет-магазин)

```
FULL:      ежедневно (раз в 24 часа)
DIFF:      каждые 4–6 часов
LOG:       каждые 5–15 минут (или раз в минуту при строгом RPO)
```

**Результат:** максимальная защита данных, минимальный RPO, восстановление на любую точку времени.

### Хранилище данных (DWH)

```
FULL + DIFF: по расписанию загрузок (например, после nightly ETL)
LOG:         не требуется
Модель:      Simple
```

**Обоснование:** данные загруются регулярно (например, раз в ночь). При потере базы в середине дня восстановление на начало дня из production-бэкапа приемлемо.

### Тестовая / dev-среда

```
FULL:      периодически (раз в неделю или реже)
Модель:    Simple
```

**Обоснование:** данные можно пересоздать или наполнить заново.

### Массовая загрузка данных

```
До загрузки:    Full-модель (обычный режим)
Перед загрузкой: переключение на Bulk-Logged
Загрузка:       BULK INSERT / массовый импорт
После загрузки: возврат на Full-модель
Сразу после:   BACKUP LOG для фиксации цепочки
```

## Типичные ошибки и потеря данных

Потеря данных на практике происходит **не из-за сбоев SQL Server или оборудования**, а из-за некорректной настройки системы резервного копирования и расхождения ожиданий с реальностью.

### Ошибка 1: Full-модель без бэкапов лога

**Проблема:** база переведена в Full-модель, но `BACKUP LOG` не настроен.

**Последствия:**
- Журнал транзакций растёт до заполнения диска.
- PITR невозможен — преимущества Full-модели не используются.
- В худшем случае — полная остановка базы при переполнении лога.

**Решение:** настроить план обслуживания (Maintenance Plan) или использовать готовые скрипты (например, Ola Hallengren) для регулярного `BACKUP LOG`.

### Ошибка 2: Выбор Simple из-за «раздувающегося» лога

**Проблема:** лог растёт в Full-модели, и для «решения» базу переводят в Simple.

**Последствия:**
- Потеря возможности PITR.
- Simple не гарантирует очистку лога, если есть долгие или незавершённые транзакции.
- Бизнес ожидает минимальных потерь, но технически это невозможно.

**Решение:** диагностировать причину роста лога:
- Переписать код для сокращения длительности транзакций.
- Настроить мониторинг и kill-сессий для «забытых» транзакций.
- Настроить систему retry для падающих бэкапов лога.
- Остаться в Full-модели и устранить корневую проблему.

### Ошибка 3: Уверенность в бэкапах без проверки

**Проблема:** бэкапы регулярно создаются, но никогда не тестируются.

**Последствия:**
- Непроверенный бэкап = отсутствие бэкапа. Файлы могут быть повреждены, записаны в недоступное место, цепочка может быть нарушена.
- Проблемы обнаруживаются только в момент аварии, когда времени на разбирательства нет.

**Решение:**
- Регулярное тестовое восстановление (автоматическое или ручное).
- Проверка, что бэкапы разворачиваются и укладываются в целевой RTO.
- Написание и документирование плана восстановления (runbook) с конкретными командами.

### Ошибка 4: Хранение бэкапов на том же диске, что и база

**Проблема:** бэкапы записываются на тот же диск/сервер, где находится production-база.

**Последствия:**
- Отказ диска → потеря и базы, и бэкапов.
- Вирус-шифровальщик → шифрование и базы, и бэкапов.

**Решение:**
- Хранить бэкапы как минимум на отдельном диске, предпочтительно — на отдельном сервере.
- Использовать объектные хранилища (S3) или облачные решения.
- Шифровать все бэкапы для защиты от несанкционированного доступа.

## Безопасность бэкапов

- **Шифрование:** все бэкапы должны храниться в зашифрованном виде. Бэкап содержит чувствительные данные, которые при развёртывании на другом сервере становятся доступны.
- **Контроль доступа:** ограничить доступ к файлам бэкапов только тем, кому это необходимо для восстановления.
- **Иммутабельность:** по возможности использовать хранилища с блокировкой изменений (WORM, Object Lock) для защиты от шифровальщиков.

## План восстановления (Runbook)

Обязательные элементы documented recovery plan:

1. **Остановка сервера** (при необходимости).
2. **Последовательность восстановления:** FULL → DIFF (последний) → LOG (все до целевой точки).
3. **Конкретные команды** с параметрами для каждой базы.
4. **Проверка целостности** после восстановления.
5. **Переключение приложения** на восстановленную базу.

План должен быть задокументирован (Confluence, блокнот, скрипт) и **протестирован**. Без тестирования план равнозначен отсутствию бэкапов.
