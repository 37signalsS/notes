# Резервное копирование и восстановление в SQL Server

Специфичные для Microsoft SQL Server инструменты, модели восстановления и подходы. Общие теоретические основы (логические и физические бэкапы, правило 3-2-1, метрики RPO/RTO) описаны в разделе **[Стратегии резервного копирования баз данных](../Concepts/backups.md)**.

## Определения

- **Модель восстановления (Recovery Model)** — свойство базы данных, управляющее процессом регистрации транзакций в журнале, необходимостью резервного копирования журнала и доступными операциями восстановления.
- **Журнал транзакций (Transaction Log)** — файл с расширением `.ldf`, обеспечивающий атомарность, согласованность, изоляцию и долговечность (ACID). Содержит записи о всех изменениях данных.
- **RPO (Recovery Point Objective)** — максимально допустимый объем потери данных, измеряемый во времени.
- **RTO (Recovery Time Objective)** — максимально допустимое время простоя сервиса до момента восстановления.
- **Point-in-Time Recovery (PITR)** — процесс возврата базы данных в состояние на произвольную метку времени. Доступно только в моделях Full и Bulk-Logged.
- **Tail-Log Backup (Бэкап хвоста журнала)** — резервная копия журнала транзакций, создаваемая перед началом восстановления для фиксации последних изменений, которые еще не были забэкаплены, даже если база данных повреждена.
- **LSN (Log Sequence Number)** — уникальный идентификатор записи в журнале транзакций, используемый SQL Server для синхронизации и последовательного восстановления.
- **Минимально логируемые операции (Minimally Logged Operations)** — операции (например, `BULK INSERT`, `SELECT INTO`), при которых в журнал записывается только информация о выделении страниц, а не сами данные.

## Основные концепции

### Модели восстановления

Модель восстановления настраивается индивидуально для каждой базы данных командой `ALTER DATABASE [DB_NAME] SET RECOVERY [FULL|SIMPLE|BULK_LOGGED]`.

#### Simple (Простая)

- **Особенности:** журнал транзакций автоматически очищается (truncated) после прохождения контрольной точки (checkpoint).
- **Бэкапы:** не поддерживает резервное копирование журнала. Доступны только полные (Full) и дифференциальные (Differential) копии.
- **Восстановление:** PITR невозможен. Восстановление только до момента создания последнего бэкапа.
- **Применение:** тестовые среды, DWH с регулярной перезагрузкой, системные базы (кроме `model` и `msdb`).

#### Full (Полная)

- **Особенности:** записи в журнале сохраняются до тех пор, пока не будет выполнен `BACKUP LOG`.
- **Бэкапы:** поддерживает все типы копий.
- **Восстановление:** обеспечивает PITR на любой момент времени (при наличии непрерывной цепочки логов).
- **Применение:** критически важные системы (Production). Требует мониторинга размера `.ldf`.

#### Bulk-Logged (С неполным протоколированием)

- **Особенности:** массовые операции используют минимальное логирование, что снижает нагрузку на диск и экономит место в логе.
- **Восстановление:** PITR невозможен в интервале, содержащем минимально логируемые операции.
- **Применение:** временное переключение для ускорения массовой загрузки данных или обслуживания индексов.

### Типы резервных копий и T-SQL

| Тип | T-SQL пример | Описание |
| :--- | :--- | :--- |
| **Полный (Full)** | `BACKUP DATABASE [DB] TO DISK = 'C:\Backup\DB.bak' WITH COMPRESSION, CHECKSUM` | Снимок всех данных и части лога для консистентности. База для всех остальных типов. |
| **Дифференциальный** | `BACKUP DATABASE [DB] TO DISK = 'C:\Backup\DB.diff' WITH DIFFERENTIAL, COMPRESSION` | Изменения с момента последнего Full бэкапа. Экономит время при восстановлении. |
| **Журнал (Log)** | `BACKUP LOG [DB] TO DISK = 'C:\Backup\DB.trn' WITH COMPRESSION` | Записи из журнала транзакций. Необходим для PITR. Очищает лог (truncate). |
| **Только копия (Copy-only)** | `BACKUP DATABASE [DB] TO DISK = 'C:\Backup\DB.bak' WITH COPY_ONLY` | Не нарушает цепочку дифференциальных бэкапов и LSN. Полезен для разовых задач. |

### Опции повышения надежности

- **COMPRESSION:** значительно уменьшает размер файла и ускоряет процесс за счет меньшего объема I/O, но увеличивает нагрузку на CPU.
- **CHECKSUM:** проверяет целостность страниц при чтении и записывает контрольную сумму в бэкап. Рекомендуется использовать всегда.
- **STATS = 10:** выводит прогресс выполнения каждые 10%.
- **VERIFYONLY:** команда `RESTORE VERIFYONLY FROM DISK = '...'` проверяет, что файл бэкапа читаем и его контрольные суммы верны, не выполняя само восстановление.

## Практические сценарии

### Алгоритм восстановления (Restore Sequence)

Для восстановления базы на момент времени в модели **Full** необходимо следовать строгой последовательности:

1. **Tail-Log Backup:** если база доступна, забэкапить «хвост» лога.
   ```sql
   BACKUP LOG [DB] TO DISK = 'C:\Backup\DB_tail.trn' WITH NORECOVERY;
   ```
2. **Restore Full:** восстановить последний полный бэкап.
   ```sql
   RESTORE DATABASE [DB] FROM DISK = 'C:\Backup\DB.bak' WITH NORECOVERY, REPLACE;
   ```
3. **Restore Differential:** восстановить последний дифференциальный бэкап (если есть).
   ```sql
   RESTORE DATABASE [DB] FROM DISK = 'C:\Backup\DB.diff' WITH NORECOVERY;
   ```
4. **Restore Logs:** последовательно восстановить все логи, созданные после дифференциального бэкапа.
   ```sql
   RESTORE LOG [DB] FROM DISK = 'C:\Backup\DB_1.trn' WITH NORECOVERY;
   RESTORE LOG [DB] FROM DISK = 'C:\Backup\DB_2.trn' WITH NORECOVERY;
   ```
5. **Final Recovery:** перевести базу в онлайн.
   ```sql
   RESTORE DATABASE [DB] WITH RECOVERY;
   ```

*Примечание: опция `WITH NORECOVERY` оставляет базу в состоянии `RESTORING`, позволяя накатывать последующие логи.*

### Массовая загрузка данных

Алгоритм для оптимизации производительности:

1. Переключить в **Bulk-Logged**: `ALTER DATABASE [DB] SET RECOVERY BULK_LOGGED;`.
2. Выполнить вставку данных (`BULK INSERT` или `bcp`).
3. Вернуть в **Full**: `ALTER DATABASE [DB] SET RECOVERY FULL;`.
4. **Обязательно** выполнить `BACKUP LOG`, так как после Bulk-операций PITR ограничен.

### Типичные ошибки администрирования

- **Переполнение диска логом:** в Full-модели лог растет до тех пор, пока не будет сделан `BACKUP LOG`. Простое удаление файла `.ldf` или `SHRINK` без бэкапа — плохая практика, нарушающая цепочку восстановления.
- **Хранение бэкапов на том же физическом диске:** классическое нарушение правила 3-2-1.
- **Отсутствие проверки (RESTORE VERIFYONLY):** бэкап, который нельзя прочитать, бесполезен.
- **Забытый NORECOVERY:** если при восстановлении цепочки логов забыть `NORECOVERY` на промежуточном этапе, базу придется восстанавливать заново с самого начала.

## Дополнительная информация

### Инструменты автоматизации

- **Ola Hallengren SQL Server Maintenance Solution:** де-факто стандарт индустрии. Набор хранимых процедур для бэкапов, `DBCC CHECKDB` и обслуживания индексов. Гибкая настройка через параметры.
- **dbatools (PowerShell):** незаменимый модуль для миграций и автоматизации. Позволяет восстановить всю цепочку бэкапов одной командой `Restore-DbaDatabase`.
- **Maintenance Plans:** встроенный GUI-инструмент в SSMS. Подходит для очень простых задач, но менее гибок, чем скрипты Олы Халленгрена.

### Безопасность

- **Шифрование (Backup Encryption):** доступно начиная с SQL Server 2014. Требует наличия сертификата или асимметричного ключа. Защищает данные от несанкционированного восстановления на другом сервере.
- **Изоляция:** бэкапы должны храниться на отдельном защищенном сетевом ресурсе (SMB/S3) with ограниченным доступом.
