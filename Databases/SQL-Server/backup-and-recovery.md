# Резервное копирование и восстановление в SQL Server

Специфичные для Microsoft SQL Server инструменты, модели восстановления и подходы. Общие теоретические основы (логические и физические бэкапы, правило 3-2-1, метрики RPO/RTO) описаны в разделе **[Стратегии резервного копирования баз данных](../Concepts/backups.md)**.

## Определения

- **Модель восстановления (Recovery Model)** — свойство базы данных, управляющее процессом регистрации транзакций в журнале, необходимостью резервного копирования журнала и доступными операциями восстановления.
- **Журнал транзакций (Transaction Log)** — файл с расширением `.ldf`, обеспечивающий атомарность, согласованность, изоляцию и долговечность (ACID). Содержит записи о всех изменениях данных.
- **RPO (Recovery Point Objective, целевая точка восстановления)** — максимально допустимый объем потери данных, измеряемый во времени.
- **RTO (Recovery Time Objective, целевое время восстановления)** — максимально допустимое время простоя сервиса до момента восстановления.
- **Point-in-Time Recovery (PITR, восстановление на момент времени)** — процесс возврата базы данных в состояние на произвольную метку времени.
- **Минимально логируемые операции (Minimally Logged Operations)** — операции (например, `BULK INSERT`, `SELECT INTO`), при которых в журнал записывается только информация о выделении страниц, а не сами данные.

## Основные концепции

### Модели восстановления

Модель восстановления настраивается индивидуально для каждой базы данных.

#### Simple (Простая)

- **Особенности:** журнал транзакций автоматически очищается (truncated) после завершения транзакции и прохождения контрольной точки (checkpoint).
- **Бэкапы:** не поддерживает резервное копирование журнала транзакций. Доступны только полные (Full) и дифференциальные (Differential) копии.
- **Восстановление:** PITR невозможен. Восстановление только до момента создания последнего бэкапа.
- **Применение:** тестовые среды, хранилища данных (DWH) с регулярной перезагрузкой, служебные базы.

#### Full (Полная)

- **Особенности:** записи в журнале транзакций сохраняются до тех пор, пока не будет выполнено резервное копирование журнала (`BACKUP LOG`).
- **Бэкапы:** поддерживает все типы копий (Full, Differential, Transaction Log).
- **Восстановление:** обеспечивает PITR.
- **Применение:** критически важные системы (Production), где недопустима потеря данных. Требует регулярного мониторинга размера файла лога.

#### Bulk-Logged (С неполным протоколированием)

- **Особенности:** промежуточный вариант между Simple и Full. Массовые операции (индексы, вставки) используют минимальное логирование.
- **Бэкапы:** поддерживаются все типы.
- **Восстановление:** PITR невозможен в интервале, содержащем минимально логируемые операции.
- **Применение:** временное переключение для ускорения массовой загрузки данных или обслуживания индексов.

### Типы резервных копий

| Тип | Английское название | Описание |
| :--- | :--- | :--- |
| **Полный** | Full Backup | Снимок всех данных и части лога для обеспечения консистентности. |
| **Дифференциальный** | Differential Backup | Содержит изменения с момента последнего полного бэкапа. |
| **Журнал транзакций** | Transaction Log Backup | Содержит записи из журнала транзакций. Необходим для PITR в Full-модели. |

## Практические сценарии

### Стратегии бэкапа для различных типов систем

**1. Критически важная система (OLTP):**

- Модель восстановления: **Full**.
- Расписание: Full раз в сутки, Differential каждые 4–6 часов, Transaction Log каждые 5–15 минут.
- Результат: RPO до 5–15 минут, возможность восстановления на любой момент времени.

**2. Хранилище данных (DWH):**

- Модель восстановления: **Simple**.
- Расписание: Full после завершения ночной загрузки (ETL).
- Результат: простота обслуживания, восстановление на начало дня.

**3. Среды разработки (Dev/Test):**

- Модель восстановления: **Simple**.
- Расписание: по необходимости (например, раз в неделю).

### Массовая загрузка данных

Алгоритм действий для ускорения импорта данных:

1. Переключить базу в модель **Bulk-Logged**.
2. Выполнить массовую вставку (`BULK INSERT`).
3. Вернуть базу в модель **Full**.
4. Сразу выполнить **BACKUP LOG**, чтобы зафиксировать изменения и продолжить цепочку логов.

### Типичные ошибки администрирования

- **Full-модель без бэкапов лога:** приводит к бесконечному росту файла `.ldf` до заполнения диска.
- **Хранение бэкапов на том же физическом диске:** при отказе диска теряются и данные, и копии для восстановления.
- **Отсутствие тестирования:** бэкап считается существующим только после успешного пробного восстановления.

## Дополнительная информация

### Инструменты автоматизации

- **Maintenance Plans:** встроенный графический инструмент SQL Server Management Studio (SSMS) для базовых задач.
- **Ola Hallengren SQL Server Maintenance Solution:** признанный стандарт в сообществе — набор скриптов для бэкапов, проверки целостности и обслуживания индексов.
- **PowerShell (dbatools):** мощный модуль для автоматизации задач восстановления и миграции.

### Безопасность бэкапов

- **Шифрование:** рекомендуется шифровать бэкапы на уровне SQL Server для защиты данных при краже носителя.
- **Валидация:** использование опции `WITH CHECKSUM` при создании копии и регулярная проверка целостности базы через `DBCC CHECKDB`.
