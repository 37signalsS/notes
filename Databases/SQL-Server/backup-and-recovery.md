# Резервное копирование и восстановление в SQL Server

Специфичные для Microsoft SQL Server инструменты, модели восстановления и подходы. Общие теоретические основы (логические и физические бэкапы, правило 3-2-1, метрики RPO/RTO) описаны в разделе **[Стратегии резервного копирования баз данных](../Concepts/backups.md)**.

## Определения

- **Модель восстановления (Recovery Model)** — свойство базы данных, управляющее процессом регистрации транзакций в журнале, необходимостью резервного копирования журнала и доступными операциями восстановления.
- **Журнал транзакций (Transaction Log)** — файл с расширением `.ldf`, обеспечивающий атомарность, согласованность, изоляцию и долговечность (ACID). Содержит записи о всех изменениях данных.
- **RPO (Recovery Point Objective)** — максимально допустимый объем потери данных, измеряемый во времени.
- **RTO (Recovery Time Objective)** — максимально допустимое время простоя сервиса до момента восстановления.
- **Point-in-Time Recovery (PITR)** — процесс возврата базы данных в состояние на произвольную метку времени. Доступно только в моделях Full и Bulk-Logged.
- **Tail-Log Backup (Бэкап хвоста журнала)** — резервная копия журнала транзакций, создаваемая перед началом восстановления для фиксации последних изменений, которые еще не были забэкаплены, даже если база данных повреждена.
- **LSN (Log Sequence Number)** — уникальный идентификатор записи в журнале транзакций, используемый SQL Server для синхронизации и последовательного восстановления.
- **ADR (Accelerated Database Recovery)** — технология (SQL 2019+), использующая версионирование строк для мгновенного отката транзакций и быстрого восстановления после сбоя, независимо от объема незавершенных транзакций.
- **ZSTD (Zstandard)** — алгоритм сжатия (SQL 2025+), обеспечивающий более высокую степень компрессии и меньшую нагрузку на CPU по сравнению со стандартным MS_GZIP.
- **Неизменяемый бэкап (Immutable Backup)** — резервная копия, защищенная от удаления или модификации на уровне хранилища (WORM), критически важная для защиты от программ-вымогателей (Ransomware).

## Модели восстановления

Модель восстановления настраивается индивидуально для каждой базы данных командой `ALTER DATABASE [DB_NAME] SET RECOVERY [FULL|SIMPLE|BULK_LOGGED]`.

### Simple (Простая)
- **Особенности:** журнал транзакций автоматически очищается (truncated) после прохождения контрольной точки (checkpoint).
- **Бэкапы:** не поддерживает резервное копирование журнала. Доступны только полные (Full) и дифференциальные (Differential) копии.
- **Восстановление:** PITR невозможен. Восстановление только до момента создания последнего бэкапа.
- **Применение:** тестовые среды, DWH с регулярной перезагрузкой, системные базы (кроме `model` и `msdb`).

### Full (Полная)
- **Особенности:** записи в журнале сохраняются до тех пор, пока не будет выполнен `BACKUP LOG`.
- **Бэкапы:** поддерживает все типы копий.
- **Восстановление:** обеспечивает PITR на любой момент времени (при наличии непрерывной цепочки логов).
- **Применение:** критически важные системы (Production). Требует мониторинга размера `.ldf`.

### Bulk-Logged (С неполным протоколированием)
- **Особенности:** массовые операции используют минимальное логирование (`BULK INSERT`, `SELECT INTO`, обслуживание индексов).
- **Восстановление:** PITR невозможен в интервале, содержащем минимально логируемые операции.
- **Применение:** временное переключение для ускорения массовой загрузки данных.

## Типы резервных копий и T-SQL

| Тип | T-SQL пример | Описание |
| :--- | :--- | :--- |
| **Полный (Full)** | `BACKUP DATABASE [DB] TO DISK = '...' WITH COMPRESSION, CHECKSUM` | Снимок всех данных и части лога. База для всех остальных типов. |
| **Дифференциальный** | `BACKUP DATABASE [DB] TO DISK = '...' WITH DIFFERENTIAL, COMPRESSION` | Изменения с момента последнего Full бэкапа. |
| **Журнал (Log)** | `BACKUP LOG [DB] TO DISK = '...' WITH COMPRESSION` | Записи из журнала транзакций. Необходим для PITR. Очищает лог. |
| **Только копия (Copy-only)** | `BACKUP DATABASE [DB] TO DISK = '...' WITH COPY_ONLY` | Не нарушает цепочку дифференциальных бэкапов и LSN. |
| **Снапшот (Snapshot)** | `BACKUP DATABASE [DB] TO DISK = '...' WITH SNAPSHOT` | (SQL 2022+) Выполнение бэкапа на уровне дисковой системы через T-SQL. |

### Опции повышения надежности и скорости
- **COMPRESSION / ALGORITHM = ZSTD:** (SQL 2025+) Сжатие данных. ZSTD рекомендуется для снижения I/O и нагрузки на CPU.
- **CHECKSUM:** проверяет целостность страниц при чтении и записывает контрольную сумму в бэкап.
- **MAXTRANSFERSIZE / BUFFERCOUNT:** параметры для тюнинга производительности при записи на быстрые хранилища (NVMe, S3).
- **ENCRYPTION:** шифрование бэкапа. Требует наличия сертификата.
  ```sql
  BACKUP DATABASE [DB] TO DISK = 'C:\Backup\DB_enc.bak'
  WITH ENCRYPTION (ALGORITHM = AES_256, SERVER CERTIFICATE = MyBackupCert);
  ```

## Новые возможности (2022–2025)

### SQL Server 2025
- **Бэкапы на вторичных репликах (Always On):** теперь поддерживаются не только `COPY_ONLY`, но и полноценные Full/Differential бэкапы на вторичных репликах (GA). Это позволяет полностью снять нагрузку I/O с первичного сервера.
- **Поддержка Managed Identity:** нативная аутентификация через управляемые удостоверения Azure для `BACKUP TO URL`, исключающая хранение SAS-токенов в БД.
- **Интеграция с Immutable Storage:** поддержка флага неизменяемости для Azure Blob Storage, защищающая бэкапы от ransomware.

### SQL Server 2022
- **S3-совместимое хранилище:** нативная поддержка бэкапа в любые S3-хранилища (AWS, MinIO, Pure Storage).
  ```sql
  BACKUP DATABASE [DB] TO URL = 's3://my-bucket/DB.bak'
  WITH CREDENTIAL = 'S3_Access_Credential', COMPRESSION, STATS = 10;
  ```
- **T-SQL Snapshot Backup:** возможность инициировать аппаратные снимки через стандартный интерфейс SQL Server.

## Практические сценарии

### Алгоритм восстановления (Restore Sequence)
Для восстановления базы на момент времени (PITR) в модели **Full**:

1. **Tail-Log Backup:** фиксация последних изменений.
   ```sql
   BACKUP LOG [DB] TO DISK = 'C:\Backup\DB_tail.trn' WITH NORECOVERY;
   ```
2. **Restore Full:** восстановление базового снимка.
   ```sql
   RESTORE DATABASE [DB] FROM DISK = 'C:\Backup\DB.bak' WITH NORECOVERY, REPLACE;
   ```
3. **Restore Differential:** накат последних изменений (если есть).
   ```sql
   RESTORE DATABASE [DB] FROM DISK = 'C:\Backup\DB.diff' WITH NORECOVERY;
   ```
4. **Restore Logs:** последовательный накат всех логов до нужной точки.
   ```sql
   RESTORE LOG [DB] FROM DISK = 'C:\Backup\DB_1.trn' WITH NORECOVERY, STOPAT = '2026-08-03 14:00:00';
   ```
5. **Final Recovery:** перевод базы в ONLINE.
   ```sql
   RESTORE DATABASE [DB] WITH RECOVERY;
   ```

### Посекционное восстановление (Piecemeal Restore)
Для очень больших БД (VLDB) можно восстанавливать отдельные файловые группы (Filegroups), чтобы быстрее запустить критические части системы.
```sql
RESTORE DATABASE [DB] FILEGROUP = 'PRIMARY' FROM DISK = '...' WITH PARTIAL, NORECOVERY;
-- База будет доступна, но файлы в других группах будут в состоянии OFFLINE/RECOVERY_PENDING
```

## Автоматизация и инструменты

### Ola Hallengren's Maintenance Solution
Золотой стандарт обслуживания SQL Server.
- **DatabaseBackup:** процедура для создания бэкапов с автоматической очисткой старых копий и проверкой целостности.
- **Пример вызова:** `EXEC DatabaseBackup @Databases = 'USER_DATABASES', @Directory = '\\NAS\Backup', @BackupType = 'FULL', @Verify = 'Y', @Compress = 'Y'`.

### dbatools (PowerShell)
Мощнейший инструмент для DevOps и DBA.
- **Восстановление всей цепочки:** `Restore-DbaDatabase -SqlInstance 'MyServer' -Path 'C:\Backups' -DatabaseName 'NewDB'`.
- **Миграция:** `Backup-DbaDatabase -SqlInstance 'Source' | Restore-DbaDatabase -SqlInstance 'Target'`.

## Безопасность и отказоустойчивость

- **Валидация:** использование `RESTORE VERIFYONLY` и регулярный запуск `DBCC CHECKDB` на восстановленных копиях.
- **Разделение прав:** SQL Server сервис должен иметь минимальные NTFS/SMB права на запись в папку бэкапов.
- **Шифрование TDE:** при использовании Transparent Data Encryption (TDE) бэкапы шифруются автоматически. Важно экспортировать и хранить сертификат TDE отдельно, иначе бэкап будет невозможно восстановить.
- **3-2-1 для SQL Server:**
  - 1 копия: Локальный диск (для быстрого RTO).
  - 2 копия: Сетевое хранилище (NAS/SMB).
  - 3 копия: Облако/Объектное хранилище (S3/Azure Blob) с политикой Immutable.
