# Аудит в MariaDB: server_audit plugin

**Актуально для:** MariaDB 10.0+ / 10.5+ / 11.x / 12.x

## Определения

**Аудит (Audit)** — процесс фиксации событий безопасности в защищённом журнале с возможностью последующего расследования инцидентов, соответствия регуляторным требованиям и выявления подозрительной активности.

**server_audit plugin** — встроенный плагин MariaDB, поставляемый в стандартных пакетах (Community Edition) и фиксирующий подключения, выполнение запросов и доступ к таблицам. В отличие от MySQL, где аудит доступен только в Enterprise Edition, в MariaDB `server_audit` входит в базовую дистрибуцию бесплатно.

**Событие аудита (Audit Event)** — атомарное действие, подлежащее логированию: `CONNECT`, `QUERY`, `TABLE`, `QUERY_DDL`, `QUERY_DML`, `QUERY_DCL`, `QUERY_DML_NO_SELECT`.

**Синхронное логирование** — режим, при котором каждая запись аудита пишется на диск немедленно. Обеспечивает гарантию сохранения записи, но увеличивает латентность транзакций.

**Асинхронное логирование** — режим с буферизацией записей в оперативной памяти перед записью на диск. В MariaDB доступен с версии 12.1 через `server_audit_file_buffer_size` и `server_audit_sync_log_file`.

**server_audit_incl_users** — фильтр, при котором аудит ведётся только для указанных пользователей. Имеет приоритет над `server_audit_excl_users`.

**server_audit_excl_users** — фильтр, исключающий технических пользователей из логирования QUERY/TABLE событий. CONNECT-события для исключённых пользователей всё равно записываются.

**Табличное событие (TABLE event)** — уникальная возможность MariaDB, при которой логируется доступ к конкретным таблицам без записи полного текста запроса. Позволяет отслеживать доступ через представления, хранимые процедуры и триггеры, снижая риск утечки чувствительных данных через логи.

**Ротация логов (Log Rotation)** — автоматическое архивирование и ограничение размера аудит-файлов через `server_audit_file_rotate_size` и `server_audit_file_rotations`.

## Базовые концепции

### Архитектура server_audit

Плагин `server_audit` внедряется в ядро MariaDB и перехватывает события на уровне сервера до их выполнения. Это отличается от внешних аудиторов, которые работают поверх триггеров или репликации.

Ключевые свойства:
1. **Встроенность:** Поставляется в стандартных пакетах MariaDB как shared library (`server_audit.so` / `server_audit.dll`). Не требует отдельной установки.
2. **Блокировка выгрузки:** Опция `server_audit = FORCE_PLUS_PERMANENT` предотвращает отключение плагина пользователем с привилегией `SUPER`.
3. **Синхронность по умолчанию:** В версиях до 12.1 запись синхронна на каждое событие, что создаёт I/O-нагрузку. В 12.1+ появилась буферизация.
4. **Гибкая фильтрация:** По событиям (CONNECT/QUERY/TABLE и их вариации) и по пользователям (`incl_users`/`excl_users`).
5. **Вывод в FILE или SYSLOG:** Поддержка ротации файлов или отправка в системный логгер для интеграции с SIEM.

### Типы событий аудита

| Тип события | Описание | Введён в версии плагина |
| :--- | :--- | :--- |
| `CONNECT` | Подключения, отключения и неудачные попытки входа с кодом ошибки | Любая |
| `QUERY` | Полный текст всех запросов, включая неудачные из-за синтаксиса или недостатка прав | Любая |
| `TABLE` | Таблицы, к которым произошёл доступ (чтение/запись), с указанием типа операции. Уникальная особенность MariaDB | Любая |
| `QUERY_DDL` | Только DDL-запросы: `CREATE`, `ALTER`, `DROP`, `RENAME`, `TRUNCATE`. Исключения: `RENAME USER` не логируется, `CREATE/DROP USER/PROCEDURE/FUNCTION` логируются | >= 1.2.0 |
| `QUERY_DML` | Только DML-запросы: `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, `CALL`, `LOAD DATA/XML`, `HANDLER` | >= 1.2.0 |
| `QUERY_DCL` | Только DCL-запросы: `CREATE USER`, `DROP USER`, `RENAME USER`, `GRANT`, `REVOKE`, `SET PASSWORD` | >= 1.3.0 |
| `QUERY_DML_NO_SELECT` | DML без `SELECT` — позволяет отслеживать изменения данных без логирования всех чтений | >= 1.4.4 |

> **Важно:** Использование `QUERY_DDL` и `QUERY_DML` совместно не равно использованию `QUERY`, так как остальные типы запросов (например, административные команды) не покрываются.

### Механизм фильтрации пользователей

- `server_audit_excl_users` исключает пользователей из логирования QUERY/TABLE событий.
- **CONNECT-события всегда логируются** для всех пользователей, независимо от этих переменных.
- Если пользователь указан в обоих списках (`incl` и `excl`), действует `server_audit_incl_users` — его действия логируются.
- Фильтрация происходит по **имени пользователя**, а не по комбинации `username@hostname`. В логе, однако, записывается полный хост.

### Уникальность MariaDB: TABLE event

В MySQL нет аналога TABLE event. В MariaDB это единственный способ зафиксировать доступ к таблицам через представления, хранимые процедуры, функции и триггеры без разбора текста запроса. Например, вызов `SELECT * FROM secret_view` в логе QUERY покажет только `secret_view`, а TABLE event дополнительно зафиксирует доступ к базовым таблицам.

### Жизненный цикл аудита

1. **Установка плагина:** `INSTALL SONAME 'server_audit';` или через `plugin_load_add`.
2. **Блокировка:** `server_audit = FORCE_PLUS_PERMANENT` в `my.cnf`.
3. **Конфигурация:** Выбор событий, пользователей, вывода.
4. **Включение:** `server_audit_logging = ON`.
5. **Верификация:** `SHOW VARIABLES LIKE 'server_audit%'` и проверка `information_schema.PLUGINS`.
6. **Эксплуатация:** Мониторинг размера логов, ротация, интеграция с SIEM.
7. **Расследование:** Поиск по логам через `grep`, `mysqlbinlog` или SIEM-платформу.

### Взаимодействие с бинарными логами

Аудит и бинарное логирование дополняют друг друга:
- **Аудит:** фиксирует **кто** и **что** сделал на уровне SQL.
- **Бинарные логи:** фиксируют **изменения данных** в формате WAL. Позволяют восстановить состояние данных до/после инцидента (PITR).

Для полной картины инцидента используйте оба механизма. Подробнее: **[Бинарное логирование](binary-logging.md)**.

## Предварительные требования

- **Версия MariaDB:** 10.0+ (базовый plugin), 10.5+ для production-ready конфигураций, 12.1+ для асинхронного логирования.
- **Дисковое пространство:** Для FILE-режима выделите отдельный раздел/точку монтирования для логов. Рекомендуемый объём: не менее 20% от размера `datadir` в высоконагруженных системах.
- **Сеть:** При SYSLOG-режиме обеспечьте доступность syslog-демона на `localhost` или доверенного удалённого сервера по защищённому каналу.
- **Привилегии:** Для установки плагина требуется `SUPER` или `SYSTEM_VARIABLES_ADMIN`. Для изменения переменных аудита — `SUPER`.
- **Сервер syslog:** Настройте `rsyslog`/`syslog-ng` с буферизацией и защищённой передачей (TLS) на удалённый SIEM. Это инфраструктурная задача, выходящая за рамки этого документа.

## Установка и включение плагина

### Метод 1: Автозагрузка через my.cnf (рекомендуется)

```ini
[mariadb]
# Загрузка плагина при старте сервера
plugin_load_add = server_audit

# Блокировка выгрузки и удаления плагина (защита от компрометации)
server_audit = FORCE_PLUS_PERMANENT

# Включение логирования
server_audit_logging = ON

# События для логирования
server_audit_events = CONNECT,QUERY,TABLE,QUERY_DDL
```

После изменения `my.cnf` перезагрузите MariaDB:
```bash
sudo systemctl restart mariadb
```

### Метод 2: Динамическая установка без перезагрузки

```sql
-- Установка плагина в рантайме
INSTALL SONAME 'server_audit';

-- Проверка статуса
SHOW PLUGINS LIKE 'server_audit';
-- → server_audit | ACTIVE

-- Блокировка выгрузки (также требуется в my.cnf для постоянства)
SET GLOBAL server_audit = 'FORCE_PLUS_PERMANENT';
```

> **Примечание:** Динамическая установка теряется после перезагрузки. Добавьте `plugin_load_add = server_audit` в `my.cnf` для персистентности.

## Конфигурация параметров

### События аудита

```ini
[mariadb]
# Минимальный набор для комплаенса: входы + DDL + доступ к таблицам
server_audit_events = CONNECT,QUERY,TABLE,QUERY_DDL

# Альтернативные варианты:
# server_audit_events = CONNECT,TABLE,QUERY_DDL,QUERY_DML
# server_audit_events = CONNECT,TABLE,QUERY_DCL
```

**Рекомендации по выбору событий:**
- **Dev/Staging:** `CONNECT,QUERY,TABLE` — полная видимость для отладки.
- **Production (комплаенс):** `CONNECT,TABLE,QUERY_DDL,QUERY_DCL` — покрытие критических изменений без логирования всего DML.
- **High-Performance:** `CONNECT,TABLE,QUERY_DDL` — исключите QUERY для снижения нагрузки и риска утечки данных через логи.

### Вывод логов

```ini
[mariadb]
# === FILE: запись в локальный файл ===
server_audit_output_type = FILE
server_audit_file_path = /var/log/mysql/audit.log
server_audit_file_rotate_size = 1G
server_audit_file_rotations = 30

# === SYSLOG: отправка в системный логгер ===
server_audit_output_type = SYSLOG
server_audit_syslog_ident = mariadb-audit
server_audit_syslog_facility = LOG_LOCAL6
server_audit_syslog_priority = LOG_INFO
server_audit_timestamp_format = '%Y%m%d %H:%i:%s'
```

**Файл vs Syslog:**
- **FILE:** Простота настройки, но логи доступны только на хосте СУБД. Риск удаления или подделки при компрометации сервера.
- **SYSLOG:** Централизованный сбор в SIEM (Splunk, ELK, Graylog), защита от изменения на хосте. Требует доверенного канала к syslog-серверу.

### Фильтрация пользователей

```ini
[mariadb]
# Исключить технических пользователей для снижения шума
server_audit_excl_users = 'monitor,repl_user,maxscale,backup'

# ИЛИ: вести аудит только для привилегированных пользователей
# server_audit_incl_users = 'admin,root,app_admin'
```

> **Важно:** `server_audit_incl_users` имеет приоритет над `server_audit_excl_users`. Если пользователь в обоих списках — он логируется. CONNECT-события исключаемым пользователям всё равно записываются.

### Асинхронное логирование (MariaDB 12.1+)

```ini
[mariadb]
# Буфер в памяти перед записью на диск (размер в байтах, выравнивание до 8192)
server_audit_file_buffer_size = 65536

# Принудительная запись буфера на диск (требует SUPER)
# SET GLOBAL server_audit_sync_log_file=1;
```

Буфер позволяет снизить I/O-нагрузку. Размер `0` (по умолчанию) означает синхронную запись. Чем больше буфер, тем выше риск потери записей при аварийном отключении питания.

### Ограничение длины запроса

```ini
[mariadb]
# Максимальная длина запроса в аудит-логе (байты)
server_audit_query_log_limit = 1024
```

По умолчанию длинные запросы усекаются. Увеличьте значение, если требуется полный текст для расследований.

## Верификация работы аудита

```sql
-- 1. Проверка, что плагин загружен и активен
SELECT PLUGIN_NAME, PLUGIN_STATUS, PLUGIN_TYPE
FROM information_schema.PLUGINS
WHERE PLUGIN_NAME = 'server_audit';
-- → server_audit | ACTIVE | AUDIT

-- 2. Проверка текущих настроек
SHOW GLOBAL VARIABLES LIKE 'server_audit%';
-- → server_audit_logging = ON
-- → server_audit_events = CONNECT,QUERY,TABLE,QUERY_DDL
-- → server_audit_output_type = SYSLOG
-- → server_audit_excl_users = monitor,repl_user,maxscale,backup

-- 3. Проверка содержимого аудит-лога (FILE-режим)
-- Внимание: файл server_audit.log по умолчанию создаётся в datadir!
SHOW VARIABLES LIKE 'datadir';
-- → /var/lib/mysql/
-- Проверьте наличие /var/lib/mysql/server_audit.log

-- 4. Проверка syslog (если используется SYSLOG)
-- Путь зависит от дистрибутива:
sudo journalctl -u rsyslog -f
sudo tail -f /var/log/syslog | grep mariadb-audit

-- 5. Тестовый запрос для проверки логирования
-- Подключитесь под тестовым пользователем и выполните:
CREATE DATABASE audit_test;
-- В логе должна появиться запись с QUERY_DDL и TABLE event

-- 6. Принудительная ротация файла
SET GLOBAL server_audit_file_rotate_now = ON;
```

## SRE-рекомендации по эксплуатации

1. **Производительность:** Логирование `QUERY` может снизить пропускную способность записи на 10-15%. В высоконагруженных системах рассмотрите логирование только `TABLE` и `QUERY_DDL` для контроля доступа к данным при меньших затратах ресурсов. С версии 12.1 используйте асинхронный режим.
2. **Хранение логов:** Никогда не храните аудит-логи в `datadir`. Выделите отдельный раздел (`/var/log/mysql/`) или используйте SYSLOG с удалённым сервером. Это защищает логи при компрометации файловой системы БД.
3. **Мониторинг:** Настройте алерты в Zabbix/Prometheus на изменение переменной `server_audit_logging`. Если аудит выключен — это критический инцидент ИБ.
4. **Права доступа:** Установите `600` на аудит-логи и директорию. Владелец — `mysql:mysql`. Никогда не делайте логи доступными для пользовательских процессов.
5. **Ротация:** Настройте `server_audit_file_rotate_size = 1G` и `server_audit_file_rotations = 30`. Для FILE-режима дополнительно настройте `logrotate` или используйте встроенную ротацию.
6. **Асинхронность:** В MariaDB 12.1+ используйте `server_audit_file_buffer_size = 65536` для снижения синхронных I/O. Для критичных систем настройте `server_audit_sync_log_file = ON` при расследовании инцидентов.
7. **Кэш запросов:** При включённом query cache `TABLE` события не генерируются для кэшированных результатов. Отключите `query_cache_type` в production.
8. **Интеграция с SIEM:** Настройте `rsyslog` или `syslog-ng` с отправкой по TLS на центральный лог-сервер. Используйте `server_audit_syslog_ident` для фильтрации записей MariaDB среди других логов.

## Целостность и защита логов

Аудит-логи — доказательная база инцидента. Если их можно молча изменить или удалить, аудит теряет смысл.

### Защита от модификации (tamper-evidence)

**Уровни защиты:**

| Уровень | Механизм | Эффект |
| :--- | :--- | :--- |
| Локальный файл | права `600`, владелец `mysql:mysql`, отдельный раздел | защита от случайного изменения |
| Хеширование | периодический `sha256sum` логов, хеши в git/Vault | обнаружение модификации |
| Внешний хост | SYSLOG → SIEM по TLS | логи недоступны злоумышленнику на хосте СУБД |
| WORM/immutable | WORM-хранилище, Object Lock | невозможность удаления/изменения |

**Хеширование логов (пример cron-задачи):**

```bash
# /etc/cron.hourly/mysql-audit-hash
#!/bin/bash
# Хеширование аудит-лога и фиксация хеша
sha256sum /var/log/mysql/audit.log >> /var/log/mysql/audit.log.sha256
# Хеши отправляются в git-репозиторий или Vault — вне хоста СУБД
```

**Проверка целостности:**

```bash
# Проверка, что лог не изменялся с момента последнего хеша
sha256sum -c /var/log/mysql/audit.log.sha256
# → /var/log/mysql/audit.log: OK
```

**Важно:** при компрометации хоста злоумышленник может пересчитать хеши. Поэтому хеши хранятся вне хоста СУБД (git, Vault, SIEM), а основной канал — SYSLOG на удалённый сервер.

### General Query Log и Slow Query Log — безопасность

`general_log` и `slow_query_log` записывают текст запросов, включая параметры и чувствительные данные. Это отдельная поверхность утечки.

**Риски:**
- `general_log` записывает **все** запросы — пароли в `CREATE USER ... IDENTIFIED BY`, ПДн в `SELECT`/`INSERT`.
- Логи по умолчанию пишутся в `datadir` — доступны пользователю `mysql` и при компрометации СУБД.
- `log_output = TABLE` (mysql.general_log) — доступен через SQL, что упрощает эксфильтрацию.

**Рекомендации:**

```ini
[mariadb]
# general_log — только для расследований, не в production
general_log = OFF

# slow_query_log — включать осознанно
slow_query_log = ON
long_query_time = 10
log_slow_rate_limit = 100

# Логи — на отдельный раздел, не в datadir
slow_query_log_file = /var/log/mysql/slow.log

# Не логировать административные команды в slow log
log_slow_admin_statements = OFF
log_slow_slave_statements = OFF
```

**Проверка:**

```sql
SHOW VARIABLES LIKE 'general_log%';
SHOW VARIABLES LIKE 'slow_query_log%';
-- → general_log = OFF
-- → slow_query_log_file = /var/log/mysql/slow.log
```

**Очистка чувствительных данных:** если `general_log` включался для расследования — после завершения удалите лог (`shred -u`), а не просто отключите переменную.

### Синхронизация времени (NTP) для корреляции

Аудит-логи нескольких узлов (Galera, репликация, SIEM) корректны только при синхронизированных часах. Рассинхрон делает реконструкцию инцидента невозможной.

**Настройка chrony:**

```bash
# Установка
sudo apt install chrony   # Debian/Ubuntu
sudo yum install chrony   # RHEL/CentOS

# Конфигурация /etc/chrony/chrony.conf
pool ntp.example.com iburst
allow 10.0.5.0/24
```

**Проверка:**

```bash
chronyc tracking
# → Reference ID    : ...
# → Leap status     : Normal

chronyc sources -v
# → ^* ntp.example.com  ...
```

**Требования:**
- Все узлы кластера и SIEM синхронизированы с одним NTP-пулом.
- Дрейф (drift) мониторится; алерт при отклонении > 1 секунды.
- Для forensic: фиксируйте часовой пояс (`timedatectl`) — временные метки в логах локальны.

Подробнее об инцидентах и postmortem: [Устранение неполадок](troubleshooting.md).

## Troubleshooting

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Аудит-лог пустой | Плагин не загружен или `server_audit_logging = OFF` | Проверьте `SHOW PLUGINS` и `SHOW VARIABLES LIKE 'server_audit%'` |
| Логи не попадают в SIEM | Неправильный `syslog_facility` или фаервол блокирует 514/6514 порт | Проверьте `sudo journalctl -u rsyslog`, настройте доставку в SIEM |
| Нет записей о TABLE доступе | Включен query cache или запросы идут через кэш | Отключите `query_cache_type` или используйте `QUERY` вместо `TABLE` |
| Высокая латентность INSERT/UPDATE | Синхронное логирование QUERY на медленном диске | Переключитесь на `TABLE` + `QUERY_DDL`, включите асинхронный режим (12.1+), используйте NVMe для логов |
| `Access denied` при установке плагина | Недостаточно привилегий | Выполните от имени root или пользователя с `SUPER` |
| Потеря логов после перезагрузки | `plugin_load_add` отсутствует в my.cnf | Добавьте параметр в конфигурационный файл |
| Файл логов растёт без ограничения | Не настроена ротация или `server_audit_file_rotations = 0` | Настройте `server_audit_file_rotate_size` и `server_audit_file_rotations` |
| Дублирование записей в syslog | Несколько экземпляров MariaDB с одинаковым `server_audit_syslog_ident` | Уникализируйте `server_audit_syslog_ident` на каждом инстансе |

## Лучшие практики

1. **Принудительная блокировка плагина.** Используйте `FORCE_PLUS_PERMANENT` в production. Отключение аудита должно требовать физического доступа к серверу.
2. **Минимальный набор событий.** В production не используйте `QUERY` без необходимости. `TABLE` + `QUERY_DDL` + `CONNECT` покрывают большинство требований комплаенса при минимальном риске утечки данных через логи.
3. **SYSLOG вместо FILE.** Централизуйте логи. Локальные файлы можно удалить или подделать при компрометации хоста.
4. **Отдельный раздел для логов.** Выделите `/var/log/mysql/` на отдельный диск/partition. Настройте мониторинг свободного места (алерт на < 20%).
5. **Исключите технических пользователей.** Добавьте `monitor`, `repl_user`, `maxscale`, `backup` в `excl_users`. Их действия бесполезны для расследований и засоряют логи.
6. **Аудит RBAC-изменений.** Обязательно включите `QUERY_DCL` или полный `QUERY`, чтобы фиксировать `GRANT`/`REVOKE`/`CREATE USER`. Это требуется для соответствия регуляторным требованиям.
7. **Ротация и долговременное хранение.** Храните аудит-логи не менее 1 года, из них не менее 3 месяцев немедленно доступно для анализа (PCI DSS Req 10.7). Для долгосрочного хранения используйте SIEM с immutability или WORM-хранилище.
8. **Тестирование отключения.** Периодически проверяйте, что попытка `UNINSTALL PLUGIN server_audit` возвращает ошибку. Это validates конфигурацию.
9. **Версионирование конфигурации.** Храните `my.cnf` в системе управления конфигурациями. Изменения `server_audit_*` параметров должны проходить через Change Management.
10. **Сопряжение с бинарными логами.** Для полного forensic используйте `audit.log` (кто что сделал) + `mariadb-bin.log` (что изменилось в данных). По времени коррелируйте события между двумя источниками.

## Ограничения

- **Утечка через QUERY:** Логирование `QUERY` записывает полный текст запроса, включая параметры. Если в запросе есть чувствительные данные, они попадут в лог в открытом виде. Используйте `TABLE` event вместо `QUERY` для снижения этого риска.
- **Синхронность (до 12.1):** Каждая запись аудита вызывает fsync. При высокой нагрузке это становится узким местом. Решение: асинхронный режим в 12.1+ или ограничение событий.
- **Query cache:** При включённом query cache `TABLE` события не генерируются для кэшированных результатов. В production query cache должен быть отключен.
- **Фильтрация по username:** Плагин фильтрует по имени пользователя, а не по `username@hostname`. Пользователь `admin` с разных хостов будет логироваться одинаково.
- **CONNECT всегда логируется:** Невозможно исключить `admin@localhost` из CONNECT-логов через `excl_users`. Если требуется скрыть источник подключения, используйте отдельный технический аккаунт.
- **Размер логов:** При отсутствии ротации лог может заполнить диск и вызвать отказ СУБД. Всегда настраивайте `server_audit_file_rotate_size` и мониторинг свободного места.
- **Версионность параметров:** Некоторые параметры (`server_audit_file_buffer_size`, `server_audit_sync_log_file`) доступны только в MariaDB 12.1+. При даунгрейте конфигурация может потерять смысл.
- **Репликация:** Аудит-логи не реплицируются автоматически. Каждый узел Galera/реплики ведёт свой собственный аудит. Для единого журнала используйте SYSLOG с удалённым сервером.
