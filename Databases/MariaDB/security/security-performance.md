# Производительность security-фич MariaDB

**Актуально для:** MariaDB 10.11 LTS / 11.4 LTS / 11.8 LTS / 12.3 LTS

## Определения

**Оверхед безопасности** — дополнительные затраты CPU, I/O и задержки, вносимые механизмами защиты (TLS, аудит, TDE, шифрование binlog). Оверхед неизбежен, но измерим и управляем.

**AES-NI** — набор инструкций процессора для аппаратного ускорения AES. Наличие AES-NI снижает оверхед шифрования в разы. Проверка: `grep -o aes /proc/cpuinfo | head -1`.

**Handshake amortization** — эффект, при котором стоимость TLS-handshake распределяется по длительному соединению; для коротких соединений оверхед TLS существенно выше.

**Audit overhead** — нагрузка от записи событий аудита; сильно зависит от набора событий (`QUERY` дороже `CONNECT`).

**Throughput vs latency** — security-фичи обычно влияют на пропускную способность (throughput) сильнее, чем на задержку (latency) одного запроса.

## Основные концепции

### Сводная таблица оверхеда

| Механизм | CPU | I/O | Задержка | Комментарий |
| :--- | :--- | :--- | :--- | :--- |
| TLS 1.2/1.3 | ~1–5% | нет | +1 RTT на handshake | с AES-NI; без AES-NI до 10–20% |
| TDE (InnoDB) | ~3–7% | нет | минимальная | с AES-NI; без AES-NI 10–20%; зашифрованные данные не сжимаются |
| Шифрование binlog | ~1–3% | нет | минимальная | AES-CTR |
| `server_audit` (CONNECT, TABLE) | ~1–5% | запись логов | минимальная | зависит от частоты событий |
| `server_audit` (QUERY) | ~5–15% | запись логов | заметная | логирование каждого запроса — дорого; на write-интенсивных нагрузках может быть выше |
| `general_log` (FILE) | ~5–20% | запись каждого запроса | заметная | логирует ВСЕ запросы — тот же класс оверхеда, что `server_audit` (QUERY) |
| `slow_query_log` | <1–3% | запись медленных запросов | минимальная | только запросы дольше `long_query_time` |
| `validate_password` | <1% | нет | минимальная | только при установке пароля |
| `require_secure_transport` | нет | нет | нет | сам по себе не добавляет нагрузку |

**Важно:** приведённые значения — ориентировочные диапазоны из документации и практики. Реальный оверхед зависит от нагрузки, оборудования и конфигурации; измеряйте на staging до включения в production.

### Почему измерение обязательно

Оверхед security-фич нелинеен: TLS почти бесплатен для длительных соединений с AES-NI, но заметен для пулов коротких соединений; аудит `QUERY` может удвоить нагрузку на запись-интенсивных нагрузках. Единственный корректный подход — замер на репрезентативной нагрузке.

### Методология замера

1. Зафиксируйте baseline (без security-фич) на репрезентативной нагрузке (sysbench, собственный трафик). Прогрейвайте минимум 1–2 минуты перед замером — кэши и buffer pool влияют на результат.
2. Включайте одну фичу за раз, замеряйте throughput (tps) и p95/p99 latency. Длительность замера — минимум 60–120 секунд, иначе короткие выбросы искажают статистику.
3. Сравнивайте с baseline; фиксируйте результаты. CPU процесса контролируйте отдельно: `pidstat -p $(pgrep -x mariadbd) 1 10` (sysstat).
4. Повторите для комбинаций (TLS + аудит + TDE).
5. Снимайте промежуточную статистику: `--report-interval=10` выдаёт tps и p95 каждые 10 секунд — видно, деградирует ли нагрузка со временем (характерно при росте логов и ротации).

## Предварительные требования

- **sysbench ≥ 1.0** со сценариями `oltp_read_write`/`oltp_read_only` (поддерживает `--mysql-ssl`, `--report-interval`, `--percentile`; 95-й перцентиль считается по умолчанию).
- **Staging-копия** с репрезентативным объёмом данных и конкурентностью, близкой к production; замер на пустой базе не отражает оверхед I/O.
- **sysstat** (`pidstat`, `iostat`) для замера CPU процесса `mariadbd` и I/O-wait во время включённых фич.
- Возможность изменять `my.cnf` и перезапускать сервис `mariadb` (часть фич — только при старте).
- Включайте фичи по одной (см. «Методология замера»).

## Практические сценарии

### Сценарий 1: Замер baseline и оверхеда TLS

```bash
# Baseline (TLS выключен); --threads — конкурентность production, p95 — по умолчанию
sysbench oltp_read_write --table-size=1000000 --threads=16 --time=120 \
  --report-interval=10 --mysql-host=10.0.5.20 \
  --mysql-user=bench --mysql-password=... run
# → transactions: 24000 per 120s (200 tps); 95th percentile: 45.20

# С включённым TLS (require_secure_transport = ON)
sysbench oltp_read_write --table-size=1000000 --threads=16 --time=120 \
  --report-interval=10 --mysql-ssl=on --mysql-host=10.0.5.20 \
  --mysql-user=bench --mysql-password=... run
# → transactions: 23600 per 120s (197 tps); 95th percentile: 46.10 — оверхед ~1.7%
```

### Сценарий 2: Оценка оверхеда аудита

```sql
-- Включение только CONNECT и TABLE (дешевле, чем QUERY)
SET GLOBAL server_audit_events = 'CONNECT,TABLE';
SET GLOBAL server_audit_logging = ON;

-- Замер нагрузки (см. сценарий 1)
-- Сравнение с baseline: фиксируйте delta throughput
```

### Сценарий 3: Проверка AES-NI

```bash
grep -o aes /proc/cpuinfo | head -1
# → aes (поддерживается — оверхед шифрования минимален)

# Если пусто — процессор без AES-NI; оверхед TDE/TLS может достигать 10–20%
```

### Сценарий 4: Снижение оверхеда аудита

```ini
[mariadb]
# Логировать только подключения и доступ к таблицам, не каждый запрос
server_audit_events = CONNECT, TABLE

# Исключить шумовых пользователей: один список через запятую
# (синтаксис и пользователи — как в audit.md)
server_audit_excl_users = monitor,repl_user,backup
```

> `server_audit_excl_users` не влияет на CONNECT-события — они логируются всегда; экономия идёт за счёт QUERY/TABLE-событий.

## Проверка и валидация

### Критерии приемлемого оверхеда

| Фича | Допустимый оверхед (ориентир) | Действие при превышении |
| :--- | :--- | :--- |
| TLS | < 5% | проверить AES-NI, использовать TLS 1.3, session resumption |
| TDE | < 7% | проверить AES-NI, `innodb_encryption_threads` |
| Аудит (CONNECT, TABLE) | < 5% | исключить сервисных пользователей |
| Аудит (QUERY) | < 15% | пересмотреть набор событий |

### Контроль после включения

```bash
# Сравнение throughput до/после
# → зафиксируйте результаты sysbench в отчёте (tps и 95th percentile)

# CPU процесса (с 10.5 демон — mariadbd, не mysqld)
top -bn1 | grep -E 'mariadbd|mysqld'
# → %CPU в пределах baseline + допустимый оверхед

# Точнее — усреднённый CPU за интервал (sysstat)
pidstat -p $(pgrep -x mariadbd) 1 10 | tail -1

# I/O при включённом аудите/логах: рост %util и await
iostat -x 1 5

# Проверка, что настройки применились
mariadb -e "SHOW GLOBAL VARIABLES LIKE 'server_audit%';"
# → server_audit_events = CONNECT,TABLE
# → server_audit_excl_users = monitor,repl_user,backup

# Рост аудит-лога за интервал (оценка I/O-футпринта; путь — из server_audit_file_path)
du -sh <путь>/server_audit.log; sleep 60; du -sh <путь>/server_audit.log
```

## Устранение неполадок

### Резкое падение throughput после включения аудита

**Причина:** включено логирование `QUERY` на запись-интенсивной нагрузке.

**Решение:**
1. `SET GLOBAL server_audit_events = 'CONNECT,TABLE';`
2. Исключите сервисных пользователей через `server_audit_excl_users`.
3. Перезамерьте нагрузку.

### Высокий CPU после включения TDE

**Причина:** процессор без AES-NI или фоновое шифрование существующих таблиц.

**Решение:**
1. Проверьте AES-NI: `grep -o aes /proc/cpuinfo | head -1`
2. Фоновое шифрование завершится самостоятельно; мониторьте `information_schema.INNODB_TABLESPACES_ENCRYPTION`.
3. Увеличьте `innodb_encryption_threads`. Подробнее: [TDE](tde.md).

### Аудит-лог заполнил диск / вырос I/O wait

**Причина:** включено `QUERY`-логирование при высокой нагрузке и без ротации (`server_audit_file_rotations = 0` — лог никогда не ротируется; по умолчанию — 9 файлов).

**Диагностика:**
```bash
# Свободное место и размер логов
df -h /var/log/mysql
# Путь к аудит-логу и его рост в реальном времени
mariadb -Nse "SHOW GLOBAL VARIABLES LIKE 'server_audit_file_path'"
watch -n5 'ls -lh <путь>/server_audit.log'
```

**Решение:**
1. Снизьте набор событий: `SET GLOBAL server_audit_events = 'CONNECT,TABLE';`
2. Настройте ротацию: `server_audit_file_rotate_size`, `server_audit_file_rotations` (подробнее — [Аудит](audit.md)).
3. Вынесите логи на отдельный раздел или отправляйте в syslog (`server_audit_output_type = SYSLOG`).
4. Добавьте алерт на свободное место (< 20%).

## Лучшие практики

1. **Включайте по одной фиче.** Так вы измерите вклад каждой, а не получите непонятную деградацию.
2. **AES-NI обязателен для production.** Без аппаратного ускорения шифрование дорого.
3. **Аудит избирателен.** `QUERY`-логирование — только для расследований, не для постоянной работы.
4. **TLS 1.3 дешевле.** Меньше round-trips при handshake; используйте, если клиенты поддерживают.
5. **Замеряйте на репрезентативной нагрузке.** Синтетические бенчмарки (sysbench) — ориентир, но production-трафик лучше.
6. **Пулите соединения при TLS.** Handshake доминирует в оверхеде для коротких соединений; пул приложения снижает его до уровня долгоживущих сессий.

## Граничные случаи

- **Пулы коротких соединений vs TLS.** Оверхед TLS концентрируется на handshake: приложение без пула (новое подключение на каждую операцию) теряет гораздо больше, чем долгоживущие соединения. Замер без пула завышает оверхед TLS относительно production.
- **TDE: первичное шифрование — переходный период.** При включении `innodb_encrypt_tables` существующие таблицы шифруются фоновыми потоками (`innodb_encryption_threads`) — CPU/I/O выше steady-state, пока шифрование не завершится. Ротация ключей (`innodb_encryption_rotate_key_age`) тоже порождает постоянную фоновую нагрузку и может повышать CPU.
- **Синхронный аудит до 12.1.** Каждая запись аудита вызывает fsync — при высокой частоте событий это узкое место по задержке. В 12.1+ буферизация (`server_audit_file_buffer_size`, `server_audit_sync_log_file`) снижает задержку ценой задержки доставки событий в лог.
- **`excl_users` не отключает CONNECT.** Плагин всегда логирует CONNECT/отключения для всех пользователей — исключение сервисных аккаунтов экономит только на QUERY/TABLE-событиях.
- **Query cache ломает TABLE-события.** При включённом query cache TABLE-события не генерируются для кэшированных результатов (query cache в production должен быть отключён — deprecated).
- **1 поток sysbench не репрезентативен.** `--threads` должен соответствовать production-конкурентности; на одном потоке фиксированные затраты (handshake, парсинг) видны сильнее, чем на насыщенной нагрузке.
- **Имя процесса в мониторинге.** С 10.5 демон — `mariadbd` (`mysqld` — symlink); правила `top`/`pgrep`/алерты, написанные под `mysqld`, не находят процесс.

## Дополнительная информация

### Ограничения

- Числа в таблице оверхеда — диапазоны, а не гарантии; официальных бенчмарков MariaDB для всех фич не существует, единственный достоверный замер — на вашей нагрузке.
- Оверхед `server_audit` сильно зависит от частоты событий; для OLTP с миллионами запросов `QUERY`-логирование неприемлемо и может давать деградацию выше 15% (вплоть до удвоения нагрузки на запись).
- Значения TDE согласованы с [TDE](tde.md); механика ротации ключей и фонового шифрования описана там.
