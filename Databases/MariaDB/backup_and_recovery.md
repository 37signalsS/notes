# Резервное копирование и восстановление в MariaDB

Специфичные для MariaDB инструменты и стратегии. Общие теоретические основы (логические/физические, горячие/холодные бэкапы) — в **[Стратегии резервного копирования баз данных](../Concepts/backups.md)**.

## Определения

**`mariadb-dump`** — стандартная утилита для создания **логических** резервных копий (SQL-дампов). Оптимальна для баз данных малого и среднего объема, где критична гибкость восстановления отдельных таблиц.

**`mariadb-backup`** (ранее `mariabackup`) — инструмент для создания "горячих" **физических** бэкапов. Позволяет копировать файлы данных без остановки сервера. Является форком Percona XtraBackup, полностью адаптированным под архитектуру MariaDB (включая MyRocks и Aria).

**`mydumper` / `myloader`** — сторонний набор утилит для многопоточного логического бэкапа и восстановления. Значительно превосходит `mariadb-dump` по скорости на больших объемах данных.

## Основные концепции

### Новое в 12.3 LTS: Бинарные логи в InnoDB

В версии MariaDB 12.3 введена возможность хранения бинарных логов непосредственно внутри движка InnoDB (`binlog_storage_engine=innodb`). Это в корне меняет подход к надежности и восстановлению:
- **Атомарность:** Транзакции в данных и бинарном логе фиксируются атомарно (исключается рассинхронизация).
- **Новый формат:** Бинарные логи имеют расширение `.ibb` и используют структуру страниц InnoDB.
- **GTID-ориентированность:** В новом формате позиционирование по смещению (offset) не поддерживается; используется только **GTID**.
- **Интеграция в бэкап:** `mariadb-backup` автоматически включает консистентные `.ibb` файлы в состав физического бэкапа.

### Инкрементальные бэкапы

`mariadb-backup` поддерживает инкрементальное копирование, при котором сохраняются только измененные страницы данных с момента последнего полного или инкрементального бэкапа. Это существенно экономит место и время выполнения.

## Практические сценарии

### Сценарий 1: Логический бэкап (mariadb-dump)

```bash
# Создание дампа всех баз данных с поддержкой транзакций
mariadb-dump -u admin -p --all-databases --single-transaction --quick > full_dump.sql

# Восстановление
mariadb -u admin -p < full_dump.sql
```

### Сценарий 2: Физический бэкап (mariadb-backup)

Процесс разделен на три фазы: создание, подготовка (prepare) и восстановление.

1. **Создание копии:**
   ```bash
   mariadb-backup --backup --target-dir=/data/backups/base_backup --user=backup_user --password=pass
   ```

2. **Подготовка (Применение redo log для консистентности):**
   ```bash
   mariadb-backup --prepare --target-dir=/data/backups/base_backup
   ```

3. **Восстановление (На остановленном сервере):**
   ```bash
   systemctl stop mariadb
   rm -rf /var/lib/mysql/*
   mariadb-backup --copy-back --target-dir=/data/backups/base_backup
   chown -R mysql:mysql /var/lib/mysql
   systemctl start mariadb
   ```

### Сценарий 3: Point-in-Time Recovery (PITR) в MariaDB 12.3+

Восстановление состояния на конкретный момент времени с использованием новых `.ibb` логов.

1. **Определите стартовый GTID** из файла `mariadb_backup_binlog_info` в директории бэкапа.
2. **Восстановите базовый физический бэкап** (см. Сценарий 2).
3. **Примените инкрементальные изменения** через `mariadb-binlog`:

```bash
# Применение всех изменений от момента бэкапа до целевого времени
mariadb-binlog --start-gtid="0-1-1234" \
               --stop-datetime="2026-07-17 15:30:00" \
               /var/lib/mysql/binlog-*.ibb | mariadb -u root -p
```

## Дополнительная информация

### Особенности для Galera Cluster

- Для узлов Galera, являющихся источниками репликации для обычных слейвов, рекомендуется сохранять `binlog_storage_engine=FILE`, так как формат `.ibb` пока имеет ограничения в мульти-мастер конфигурациях.
- `mariadb-backup` используется кластером для SST (State Snapshot Transfer) при вводе новых узлов.

### Рекомендации по безопасности

- Всегда используйте флаг `--mask-passwords` при запуске утилит в скриптах.
- Для `mariadb-backup` создавайте отдельного пользователя с минимально необходимыми привилегиями (`RELOAD`, `PROCESS`, `LOCK TABLES`, `BINLOG MONITOR`).
