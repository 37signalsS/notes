# Резервное копирование и восстановление в MariaDB

Специфичные для MariaDB инструменты и стратегии обеспечения сохранности данных. Общие теоретические основы (RPO/RTO, типы бэкапов) описаны в руководстве **[Стратегии резервного копирования баз данных](../Concepts/backups.md)**.

## Определения

**`mariadb-backup`** — основной инструмент для создания «горячих» **физических** бэкапов. Является форком Percona XtraBackup, полностью оптимизированным под архитектуру MariaDB, включая поддержку движков MyRocks, Aria и новых атомарных бинарных логов InnoDB.

**`mariadb-dump`** — стандартная утилита для создания **логических** резервных копий (SQL-дампов). Подходит для небольших БД, миграций между мажорными версиями или когда требуется перенос данных между разными форками MySQL.

**Point-in-Time Recovery (PITR)** — процесс восстановления базы данных до точно определенного момента времени в прошлом путем наката бинарных логов (WAL) на предварительно восстановленный полный физический бэкап.

**SST (State Snapshot Transfer)** — процесс полной синхронизации данных нового узла Galera Cluster с существующим донором. `mariadb-backup` является методом SST по умолчанию (рекомендуемым) для минимизации блокировок.

## Основные концепции

### Архитектурные особенности MariaDB 12.3 LTS

Версия 12.3 LTS привносит критические изменения в механизмы логирования, влияющие на стратегию бэкапов:

1.  **Атомарные бинарные логи (Binlog-in-InnoDB):**
    - При включенном `binlog_storage_engine=innodb` события бинарного лога хранятся внутри табличного пространства InnoDB.
    - **Преимущество:** Исключает рассинхронизацию между данными и логом при сбоях (Crash Consistency) и устраняет накладные расходы на XA-транзакции при записи лога.
2.  **GTID-Only PITR:**
    - В современных инсталляциях (12.x+) восстановление на точку времени рекомендуется выполнять исключительно через **GTID** (Global Transaction ID). Старый метод позиционирования по имени файла и смещению (File:Offset) признается менее надежным в кластерных средах.

### Сравнение методов бэкапа

| Характеристика | Physical (mariadb-backup) | Logical (mydumper/dump) |
| :--- | :--- | :--- |
| **Скорость создания** | Высокая (копирование страниц) | Низкая (SELECT + генерация SQL) |
| **Скорость восстановления** | Очень высокая (копирование + накат логов) | Очень низкая (INSERT + построение индексов) |
| **Размер бэкапа** | Большой (равен объему данных на диске) | Малый (текстовое сжатие) |
| **Блокировки** | Минимальные (не блокирует чтение/запись) | Зависят от флагов (могут блокировать DDL) |
| **Версионность** | Только та же мажорная версия | Можно восстанавливать на другие версии |

## Практические сценарии

### Сценарий 1: Физический инкрементальный бэкап (mariadb-backup)

Используется для минимизации RTO в Production-средах.

**Prerequisites:** Пользователь с правами `RELOAD, PROCESS, LOCK TABLES, REPLICATION CLIENT`.

**1. Создание полного (Full) бэкапа:**
```bash
mariadb-backup --backup \
    --target-dir=/data/backups/full_$(date +%F) \
    --user=backup_admin --password=secret_pass
# → result: В каталоге создается копия файлов .ibd, .ibb и логов транзакций.
```

**2. Создание инкрементального бэкапа:**
```bash
mariadb-backup --backup \
    --target-dir=/data/backups/inc_$(date +%F) \
    --incremental-basedir=/data/backups/full_2026-08-17
# → result: Копируются только страницы, измененные с момента базового бэкапа.
```

**3. Подготовка к восстановлению (Prepare):**
Критический этап — накат логов транзакций на файлы данных.
```bash
# А) Подготовка базового бэкапа (не завершаем транзакции!)
mariadb-backup --prepare --apply-log-only --target-dir=/data/backups/full_base

# Б) Накат инкремента
mariadb-backup --prepare --apply-log-only --target-dir=/data/backups/full_base \
               --incremental-dir=/data/backups/inc_delta

# В) Финальный Prepare (завершаем незавершенные транзакции)
mariadb-backup --prepare --target-dir=/data/backups/full_base
```

### Сценарий 2: Многопоточный логический бэкап (mydumper)

Рекомендуется для БД объемом от 50 ГБ, где стандартный `mariadb-dump` становится узким местом.

**Prerequisites:** Установленный пакет `mydumper`.

```bash
# Бэкап в 8 потоков с компрессией Zstd
mydumper --user=root --threads=8 --compress --compress-algo=zstd \
         --long-query-guard=60 \
         --outputdir=/data/backups/logical_$(date +%F)

# Восстановление через myloader
myloader --user=root --directory=/data/backups/logical_2026-08-17 --threads=8
```

### Сценарий 3: Point-in-Time Recovery через GTID

Восстановление данных после случайного `DROP TABLE` в 14:30.

**1. Восстанавливаем последний физический бэкап (см. Сценарий 1).**

**2. Извлекаем данные из бинарных логов с момента бэкапа до ошибки:**
```bash
# Ищем GTID события удаления в логах
mariadb-binlog --start-datetime="2026-08-17 00:00:00" \
               --stop-datetime="2026-08-17 14:30:00" \
               --base64-output=DECODE-ROWS -v \
               /var/lib/mysql/binlog.000010 > recovery_pitr.sql

# Накатываем логи на восстановленную базу
mariadb -u root < recovery_pitr.sql
```

## Диагностика и устранение неисправностей

### Типичные ошибки mariadb-backup
-   **Error: `Redo log size mismatch`:**
    - **Причина:** Попытка выполнить `--prepare` на версии сервера, отличной от той, где создавался бэкап.
    - **Решение:** Используйте бинарный файл `mariadb-backup` той же версии, что и сервер-источник.
-   **Error: `Can't connect to local server`:**
    - **Решение:** Проверьте путь к сокету в `my.cnf` или передайте его явно через `--socket=/run/mysqld/mysqld.sock`.

### Валидация бэкапов (Best Practices)
1.  **Автоматизированный Prepare:** Сразу после создания бэкапа выполняйте фазу `--prepare` на отдельном сервере/контейнере.
2.  **Проверка контрольных сумм:** Утилита выполняет проверку страниц автоматически, но для логических дампов рекомендуется использовать `sha256sum`.
3.  **Удаленное хранение:** Никогда не храните бэкапы на том же диске, где лежат данные БД. Используйте S3 или удаленные NFS-шары.
