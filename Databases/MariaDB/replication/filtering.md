# Фильтрация репликации MariaDB: Настройка и риски

**Актуально для:** MariaDB 11.4 LTS / 12.3 LTS

## Определения

*   **Фильтрация репликации (Replication Filtering)** — механизмы ограничения набора данных (баз данных или таблиц), которые реплика будет применять из бинарного лога источника.
*   **Фильтры включения (Include Filters)** — параметры, определяющие, какие данные реплицировать (`replicate-do-db`, `replicate-do-table`, `replicate-wild-do-table`).
*   **Фильтры исключения (Exclude Filters)** — параметры, определяющие, какие данные НЕ реплицировать (`replicate-ignore-db`, `replicate-ignore-table`, `replicate-wild-ignore-table`).
*   **`replicate-do-db`** — фильтр включения на уровне базы данных: реплицировать только указанные базы.
*   **`replicate-ignore-db`** — фильтр исключения на уровне базы данных: реплицировать всё, кроме указанных баз.
*   **`replicate-wild-do-table`** — фильтр включения с поддержкой масок (wildcards) на уровне таблиц.
*   **`replicate-wild-ignore-table`** — фильтр исключения с поддержкой масок на уровне таблиц.
*   **`replicate-rewrite-db`** — параметр для переименования базы данных при репликации (полезно при миграции или отличиях в именах БД между источником и репликой). Начиная с MariaDB 10.11 доступен как динамическая системная переменная.
*   **`CHANGE REPLICATION FILTER`** — SQL-команда (MariaDB 10.5+ / MySQL 5.7+) для динамического изменения фильтров репликации без перезапуска сервера. Эффект теряется при перезапуске; для постоянного применения требуется обновление `my.cnf`.
*   **Динамические фильтры (Dynamic Replication Filters)** — с MariaDB 5.5.22/10.x параметры фильтрации доступны как системные переменные (`replicate_do_db`, `replicate_ignore_db`, `replicate_wild_do_table` и др.), что позволяет изменять их через `SET GLOBAL` без перезагрузки. С MariaDB 11.2.0 параметры уровня binlog (`binlog_do_db`, `binlog_ignore_db`) также стали системными переменными.
*   **Консистентность (Consistency)** — состояние данных, при котором все связи и зависимости между объектами соблюдены.
*   **`replicate_do_table`** — фильтр включения на уровне таблиц (системная переменная с MariaDB 10.x, динамическая). Имеет более высокий приоритет, чем wildcard-фильтры.

## Базовые концепции

### Уровни фильтрации

Фильтрация может выполняться на двух уровнях:

1.  **На Источнике (`binlog-do-db` / `binlog-ignore-db`):** События вообще не записываются в бинарный лог. **Не рекомендуется**, так как это делает невозможным полное восстановление из логов (Point-in-Time Recovery) и создает риски при смене источника.
2.  **На Реплике (`replicate-*`):** Все события передаются реплике, но SQL-поток игнорирует ненужные. Это **стандартный и безопасный подход**.

### Полный список параметров фильтрации

**Фильтры на уровне базы данных (DB-level):**

| Параметр | Описание | Приоритет |
| :--- | :--- | :--- |
| `replicate-do-db` | Реплицировать только указанные БД | Высокий |
| `replicate-ignore-db` | Игнорировать указанные БД | Высокий |

**Фильтры на уровне таблиц (Table-level):**

| Параметр | Описание | Приоритет |
| :--- | :--- | :--- |
| `replicate-do-table` | Реплицировать только указанные таблицы | Средний |
| `replicate-ignore-table` | Игнорировать указанные таблицы | Средний |
| `replicate-wild-do-table` | Реплицировать таблицы по маске | Низкий |
| `replicate-wild-ignore-table` | Игнорировать таблицы по маске | Низкий |

**Другие параметры:**

| Параметр | Описание |
| :--- | :--- |
| `replicate-rewrite-db` | Переименование БД при репликации |
| `replicate-do-db` (в multiple) | Несколько фильтров задаются многократным указанием параметра |

### Приоритеты фильтров

MariaDB обрабатывает фильтры в следующем порядке:

1.  **Binlog-level filters (Источник):** Если `binlog-do-db` задан, проверяется он. Если нет — проверяется `binlog-ignore-db`.
2.  **DB-level filters (Реплика):** Если `replicate-do-db` задан, проверяется он. Если нет — проверяется `replicate-ignore-db`.
3.  **Table-level filters (Реплика):** Порядок проверки:
    1.  `replicate-do-table`
    2.  `replicate-ignore-table`
    3.  `replicate-wild-do-table`
    4.  `replicate-wild-ignore-table`

**Важно:** Если `replicate-do-db` задан, фильтры таблиц (`replicate-do-table`, `replicate-ignore-table`) **не проверяются** для БД, не входящих в `replicate-do-db`.

### Динамические системные переменные и CHANGE REPLICATION FILTER

С MariaDB 11.2.0 параметры фильтрации стали доступны не только в `my.cnf`, но и как динамические системные переменные. Это позволяет изменять фильтры без перезапуска сервера:

```sql
-- Просмотр текущих значений фильтров
SHOW VARIABLES LIKE 'replicate_%';
SHOW VARIABLES LIKE 'binlog_%';

-- Изменение фильтров динамически
SET GLOBAL replicate_do_db = 'app_data,analytics';
SET GLOBAL replicate_wild_ignore_table = 'logs_db.temp_%';
```

Для постоянного применения изменений после перезапуска параметры также должны быть заданы в `my.cnf`.

MariaDB также поддерживает команду `CHANGE REPLICATION FILTER` (совместима с MySQL 5.7+):

```sql
CHANGE REPLICATION FILTER
    REPLICATE_DO_DB = (db1, db2),
    REPLICATE_IGNORE_TABLE = (logs_db.temp_%),
    REPLICATE_REWRITE_DB = (old_db -> new_db)
    FOR CHANNEL 'channel_name';  -- для multi-source репликации
```

> **Примечание:** Фильтры, установленные через `CHANGE REPLICATION FILTER` или `SET GLOBAL`, теряются при перезапуске сервера. Для постоянной конфигурации используйте `my.cnf`.

### Deprecation: binlog-do-db и binlog-ignore-db

Параметры `binlog-do-db` и `binlog-ignore-db` (фильтрация на уровне источника) **устарели в MariaDB 11.7** и будут удалены в будущих версиях. Они не рекомендуются по следующим причинам:

1. **Создают "дыры" в бинарном логе** — события не записываются, что делает невозможным Point-in-Time Recovery для отфильтрованных данных.
2. **Совместимость с сменой источника** — при promotion реплики в источник отфильтрованные события отсутствуют в её binlog.
3. **Современные альтернативы** — фильтрация на реплике (`replicate-*`) обеспечивает тот же результат без потерь для бэкапов.

С MariaDB 11.2.0 эти параметры также доступны как системные переменные, но их использование всё равно не рекомендуется.

### Механика работы фильтров

В MariaDB поведение фильтров зависит от формата бинарного лога:

*   **Statement-based (SBR):** Проверяется текущая база данных сессии (`USE dbname`). Если запрос затрагивает таблицы в других БД (cross-db query), фильтр может сработать некорректно.
*   **Row-based (RBR):** Проверяется база данных, к которой принадлежит изменяемая строка. Это **наиболее надежный** вариант для фильтрации.
*   **Mixed:** Автоматический выбор между SBR и RBR. Для детерминированных запросов используется SBR, что может привести к проблемам с фильтрацией.

**Пример проблемы с SBR:**
```sql
-- На источнике:
USE db1;
UPDATE db1.table1 t1 JOIN db2.table2 t2 ON t1.id = t2.id SET t1.val = 1;

-- Если replicate-do-db = db1, запрос может быть проигнорирован,
-- потому что текущая БД сессии - db1, но обновляется также db2
```

### Влияние фильтров на GTID-репликацию

При использовании GTID (Global Transaction ID) фильтрация работает следующим образом:

*   **GTID присваивается на источнике** до применения фильтров.
*   **Фильтры применяются на реплике** при воспроизведении транзакции.
*   **Проблема:** Если транзакция затрагивает несколько БД и фильтр исключает одну из них, GTID все равно будет записан в `gtid_slave_pos`, но данные не будут применены. Это может привести к "дырам" в последовательности GTID.

**Рекомендация:** При использовании GTID и фильтров тщательно проверяйте консистентность данных после изменений конфигурации.

### Фильтрация в Galera Cluster

При использовании фильтров в Galera Cluster необходимо учитывать особенности:

*   **Поддерживаются:** `replicate-do-db`, `replicate-ignore-db` для DDL и DML (InnoDB и MyISAM).
*   **Не поддерживаются:** `binlog-do-db`, `binlog-ignore-db`, `replicate-wild-do-db`, `replicate-wild-ignore-db`.
*   **Риски:** Использование фильтров может создать расхождения данных между узлами кластера и прервать репликацию (см. MDEV-421, MDEV-6229).

## Предварительные требования

### Программные требования

*   **MariaDB Server** — версия 11.4 LTS или 12.3 LTS (рекомендуется). Минимальная версия для GTID: MariaDB 10.0+; для динамических фильтров: MariaDB 10.5+; для системных переменных уровня binlog: MariaDB 11.2.0+.
*   **Формат бинарного лога:** `binlog_format = ROW` обязателен для предсказуемой фильтрации. SBR и Mixed ненадежны при кросс-базовых запросах.
*   **Уникальные `server_id`** — каждому узлу требуется уникальный идентификатор.
*   **GTID** — рекомендуется включить (`gtid_domain_id`, `gtid_strict_mode = ON`). С MariaDB 10.10 GTID включен по умолчанию для новых инсталляций.

### Безопасность

*   Создайте отдельного пользователя для репликации с привилегией `REPLICATION SLAVE`.
*   Ограничьте доступ по подсети или IP (`repl_user@192.168.1.%`).
*   Настройте SSL/TLS для шифрования репликационного трафика (`require_secure_transport = ON`).

### Проверка совместимости

*   Убедитесь, что версия источника не старше версии реплики.
*   Проверьте, что на реплике достаточно дискового пространства для целевых наборов данных.
*   При использовании `replicate-rewrite-db` убедитесь, что целевая БД существует на реплике и имеет совместимую схему.

## Практические сценарии

### Сценарий 1: Репликация только одной БД

Часто используется для аналитических реплик или выделенных микросервисов.

В конфигурации `/etc/mysql/mariadb.conf.d/tuning.cnf`:
```ini
[mariadb]
# Реплицировать только базу данных app_data
replicate-do-db = app_data
```

### Сценарий 2: Исключение системных или временных таблиц

```ini
[mariadb]
# Игнорировать базу с логами и временную таблицу
replicate-ignore-db    = logs_db
replicate-ignore-table = stats_db.temp_calculations
```

### Сценарий 3: Сложная конфигурация с масками

Для репликации нескольких баз с общим префиксом:
```ini
[mariadb]
# Реплицировать все базы, начинающиеся с sales_
replicate-wild-do-table = sales_%

# Исключить временные таблицы
replicate-wild-ignore-table = %.temp_%
```

### Сценарий 4: Переименование БД при репликации

Полезно при миграции или отличиях в именах БД:

В `my.cnf`:
```ini
[mariadb]
# На источнике БД называется old_app, на реплике - new_app
replicate-rewrite-db = old_app -> new_app
```

Или динамически (MariaDB 10.11+):
```sql
SET GLOBAL replicate_rewrite_db = 'old_app -> new_app';
```

> **Примечание:** `replicate-rewrite-db` работает только для событий, где БД указана явно или является текущей по умолчанию. Квалифицированные имена таблиц (`db.table`) в cross-db запросах могут не перезаписываться корректно.

### Сценарий 5: Комбинирование фильтров (рекомендуемый подход)

```ini
[mariadb]
# Используем только replicate-wild-do-table для максимальной предсказуемости
replicate-wild-do-table = app_data.%
replicate-wild-do-table = analytics.%

# Исключаем specific таблицы
replicate-ignore-table = app_data.temp_logs
```

### Сценарий 6: Динамическое изменение фильтров (без перезапуска)

Для временных изменений или blue/green deployments:

```sql
-- Остановите репликацию
STOP REPLICA;

-- Измените фильтры
SET GLOBAL replicate_wild_do_table = 'app_data.%,analytics.%';
SET GLOBAL replicate_ignore_table = 'app_data.temp_logs';

-- Запустите репликацию
START REPLICA;
```

Или через `CHANGE REPLICATION FILTER` (MariaDB 10.5+):

```sql
CHANGE REPLICATION FILTER
    REPLICATE_WILD_DO_TABLE = ('app_data.%', 'analytics.%'),
    REPLICATE_IGNORE_TABLE = ('app_data.temp_logs')
    FOR CHANNEL 'default';
```

### Сценарий 7: Multi-source репликация с фильтрацией по каналам

При подключении к нескольким источникам можно задавать фильтры отдельно для каждого канала:

```ini
[mariadb]
# Глобальные фильтры (применяются ко всем каналам)
replicate-wild-do-table = shared.%

# Канальные фильтры задаются через SQL
```

```sql
-- Для канала channel_1
CHANGE REPLICATION FILTER
    REPLICATE_DO_DB = ('db1')
    FOR CHANNEL 'channel_1';

-- Для канала channel_2
CHANGE REPLICATION FILTER
    REPLICATE_DO_DB = ('db2')
    FOR CHANNEL 'channel_2';
```

### Риски и влияние на производительность

1.  **Риск нарушения консистентности:** Если вы используете `replicate-do-db = db1`, но ваш запрос выполняет `UPDATE db1.table1 t1 JOIN db2.table2 t2 ON ...`, репликация может сломаться или проигнорировать запрос, если `db2` не входит в фильтр.
2.  **Нагрузка на сеть:** Фильтрация на реплике не снижает сетевой трафик — реплика все равно скачивает полный бинарный лог. Она лишь экономит ресурсы диска и CPU при применении (SQL Thread).
3.  **Сложность отладки:** Ошибки репликации при использовании фильтров часто связаны с тем, что "незаметно" пропущенный запрос на источнике привел к отсутствию данных на реплике через неделю.
4.  **Влияние на DDL:** Фильтры применяются и к DDL-операциям (CREATE TABLE, ALTER TABLE). Если таблица создается на источнике, но не реплицируется из-за фильтра, на реплике она не появится.

### Валидация фильтрации

После изменения фильтров выполните проверку:

```sql
-- На реплике: убедитесь, что потоки репликации активны
SHOW REPLICA STATUS\G

-- Ожидаемые значения:
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source: 0

-- Проверка активных фильтров (современный синтаксис)
SHOW VARIABLES LIKE 'replicate_%';
SHOW VARIABLES LIKE 'binlog_%';

-- Проверка GTID-позиции (источник vs реплика)
SELECT @@gtid_binlog_pos AS source_gtid;
SELECT @@gtid_slave_pos AS replica_gtid;

-- Для multi-source репликации: проверка по каналам
SHOW REPLICA STATUS FOR CHANNEL 'channel_name'\G
```

### Мониторинг влияния фильтров

```sql
-- Performance Schema: время применения транзакций
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- Проверка пропущенных событий (если есть расхождения)
SHOW REPLICA STATUS\G
-- Ищите поля Last_IO_Error, Last_SQL_Error
```

## Рекомендации SRE

1.  **Всегда используйте `binlog_format = ROW`** при использовании фильтров. Это единственный способ гарантировать, что фильтрация сработает на основе реально изменяемых данных, а не на основе заголовка `USE`.
2.  **Предпочитайте `replicate-wild-do-table`** вместо `replicate-do-db`. Параметры с `wild` поддерживают маски (например, `sales_%`) и работают более предсказуемо для кросс-базовых запросов.
    ```ini
    replicate-wild-do-table = app_data.%
    ```
3.  **Минимизируйте фильтры.** В современной инфраструктуре дешевле хранить лишние данные, чем тратить время инженера на распутывание ошибок консистентности, вызванных сложной логикой фильтрации.
4.  **Избегайте смешивания `replicate-do-db` и `replicate-wild-do-table`.** Это может привести к непредсказуемому поведению. Используйте либо один тип фильтра, либо тщательно тестируйте комбинацию.
5.  **Не используйте одновременно `replicate-do-db` и `replicate-ignore-db`.** Приоритеты могут привести к путанице. Используйте либо включение, либо исключение.
6.  **Для динамического изменения фильтров используйте `SET GLOBAL` или `CHANGE REPLICATION FILTER`** (MariaDB 10.5+), а не перезапуск сервиса. Фильтры, измененные динамически, теряются при перезапуске — дублируйте их в `my.cnf`.
7.  **Не используйте `binlog-do-db`/`binlog-ignore-db`** на источнике в новых развертываниях. Они устарели в MariaDB 11.7+ и создают риски для PITR и смены источника.
8.  **Взаимодействие с GTID:** При использовании фильтров включите `gtid_strict_mode = ON`. Это предотвратит дублирование транзакций при ручных исправлениях на реплике.
9.  **Crash-safe Replication:** Убедитесь, что `relay_log_recovery = ON` и `relay_log_info_repository = TABLE`. При сбое питания реплика корректно восстановит позицию и продолжит работу с учетом фильтров.
10. **Мониторинг:** Регулярно проверяйте `SHOW REPLICA STATUS` и метрики `performance_schema.replication_applier_status_by_worker` на предмет роста лага после изменения фильтров.

### Тестирование фильтрации

Перед применением фильтров в продакшене:

1.  **Проверьте логи репликации:**
    ```bash
    # На реплике
    tail -f /var/log/mysql/error.log | grep -i "replication"
    ```

2.  **Включите отладку (временно):**
    ```sql
    SET GLOBAL log_slave_updates = 1;
    SET GLOBAL general_log = 1;
    ```

3.  **Создайте тестовые данные на источнике:**
    ```sql
    -- В БД, которая должна реплицироваться
    USE app_data;
    INSERT INTO test_table (val) VALUES ('should replicate');

    -- В БД, которая НЕ должна реплицироваться
    USE logs_db;
    INSERT INTO test_table (val) VALUES ('should NOT replicate');
    ```

4.  **Проверьте на реплике:**
    ```sql
    SELECT * FROM app_data.test_table; -- Должна быть строка
    SELECT * FROM logs_db.test_table; -- Таблица не должна существовать
    ```

5.  **Проверьте GTID-позицию:**
    ```sql
    -- На источнике
    SELECT @@gtid_binlog_pos;

    -- На реплике
    SELECT @@gtid_slave_pos;
    ```

### Типовые ограничения и Edge Cases

1.  **Хранимые процедуры и триггеры:** Фильтры применяются к событиям, а не к результатам выполнения хранимых процедур. Если процедура на источнике изменяет таблицы в нескольких БД, фильтр на уровне таблиц корректно обработает каждое событие в RBR, но может дать сбой в SBR.
2.  **Multi-source репликация:** Для каналов (`FOR CHANNEL`) можно задавать отдельные фильтры. Глобальные фильтры применяются ко всем каналам; канальные переопределяют глобальные для своего канала.
3.  **Несоответствие версий:** На источнике MariaDB 12.3 с новым binlog-движком InnoDB (`binlog_storage_engine=innodb`) фильтрация работает так же, как и с файловым binlog. При репликации с MySQL на MariaDB убедитесь в совместимости формата binlog.
4.  **DDL и временные таблицы:** DDL-события реплицируются независимо от фильтров на данные (DML). Если таблица создается через `CREATE TABLE`, но не реплицируется из-за фильтра, на реплике она не появится, и последующие DML для неё вызовут ошибку.
5.  **Смена `binlog_format`:** Переключение с SBR на RBR требует перезапуска репликации или сброса позиции. GTID-репликация чувствительна к формату binlog на источнике.
6.  **`replicate-rewrite-db` limitations:** Переименование работает только для событий, где БД указана явно или является текущей по умолчанию. Квалифицированные имена таблиц (`db.table`) в cross-db запросах могут не перезаписываться корректно.

## Troubleshooting

### Типовые ошибки и решения

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `Error 1062: Duplicate entry` | Фильтр пропустил транзакцию, которая уже есть на реплике | Проверьте консистентность данных; рассмотрите полную пересинхронизацию |
| `Error 1032: Can't find record` | Запись удалена на источнике, но не реплицировалась на реплику | Восстановите запись на реплике или используйте `slave_skip_errors = 1032` (рискованно) |
| `Table doesn't exist` | DDL-операция не реплицировалась из-за фильтра | Создайте таблицу вручную на реплике или скорректируйте фильтры |
| `Replication lag increases` | Фильтры замедляют обработку SQL Thread | Оптимизируйте фильтры; рассмотрите параллельную репликацию |
| `Error 1192: Server is not configured as slave` | Попытка изменить фильтры во время running репликации без `STOP REPLICA` | Используйте `STOP REPLICA; SET GLOBAL ...; START REPLICA;` или `CHANGE REPLICATION FILTER` |

### Диагностика проблем с фильтрами

1.  **Проверьте текущие фильтры:**
    ```sql
    SHOW REPLICA STATUS\G
    -- Ищите поля Replicate_Do_DB, Replicate_Ignore_DB, Replicate_Do_Table и т.д.

    -- Или как системные переменные
    SHOW VARIABLES LIKE 'replicate_%';
    SHOW VARIABLES LIKE 'binlog_%';
    ```

2.  **Анализ бинарного лога на источнике:**
    ```bash
    mariadb-binlog --base64-output=DECODE-ROWS -v /var/log/mysql/mariadb-bin.000001 | less
    -- Проверьте, записываются ли нужные события
    ```

3.  **Анализ relay log на реплике:**
    ```bash
    mariadb-binlog --base64-output=DECODE-ROWS -v /var/log/mysql/relay-bin.000001 | less
    -- Проверьте, какие события получены, но не применены
    ```

4.  **Проверка GTID и позиции:**
    ```sql
    -- На источнике
    SELECT @@gtid_binlog_pos;

    -- На реплике
    SELECT @@gtid_slave_pos;

    -- Сравните позиции; расхождение указывает на пропущенные события
    ```

5.  **Диагностика консистентности:**
    ```bash
    # Percona Toolkit: сравнение данных источник vs реплика
    pt-table-checksum --databases=app_data h=source_ip,u=repl_user,p=password
    ```

### Восстановление после некорректной фильтрации

Если данные на реплике отличаются из-за некорректных фильтров:

1.  **Остановите репликацию:**
    ```sql
    STOP REPLICA;
    ```

2.  **Пересинхронизируйте данные:**
    ```bash
    # На источнике
    mariadb-dump --all-databases --user=repl_user --password --single-transaction > full_dump.sql

    # На реплике
    mariadb -u root -p < full_dump.sql
    ```

3.  **Настройте фильтры заново** и запустите репликацию:
    ```sql
    CHANGE REPLICATION SOURCE TO
        SOURCE_HOST='source_ip',
        SOURCE_USER='repl_user',
        SOURCE_PASSWORD='password',
        SOURCE_USE_GTID=slave_pos;
    START REPLICA;
    ```

4.  **Валидация:**
    ```sql
    SHOW REPLICA STATUS\G
    -- Replica_IO_Running: Yes
    -- Replica_SQL_Running: Yes
    -- Seconds_Behind_Source: 0
    ```
