# Отложенная репликация MariaDB (Delayed Replication)

**Актуально для:** MariaDB 10.5+ / 11.4 LTS / 12.3 LTS

## Определения

*   **Отложенная репликация (Delayed Replication)** — режим, при котором реплика применяет транзакции с задержкой относительно источника. Задержка задаётся параметром `SOURCE_DELAY` (MariaDB 10.5+, современный синтаксис) / `MASTER_DELAY` (устаревший синтаксис `CHANGE MASTER TO`).
*   **`SOURCE_DELAY`** — количество секунд задержки. Диапазон: 0..2147483647 (~68 лет). По умолчанию 0 (без задержки).
*   **`SQL_Delay`** — поле `SHOW REPLICA STATUS`: значение задержки в секундах (то, что задано в `SOURCE_DELAY`).
*   **`SQL_Remaining_Delay`** — поле `SHOW REPLICA STATUS`: сколько секунд задержки осталось до применения текущего события. `NULL`, если реплика не в состоянии ожидания задержки.
*   **Rollback-точка** — отложенная реплика как точка восстановления: если ошибка обнаружена в течение окна задержки, реплика ещё не применила ошибочную транзакцию.

## Базовые концепции

### Как работает отложенная репликация

Реплика получает события от источника в обычном режиме (I/O-поток работает без задержки, relay log заполняется как обычно). Задержка накладывается только на SQL-поток: перед применением события SQL-поток ожидает, пока не пройдёт `SOURCE_DELAY` секунд с момента фиксации транзакции на источнике.

Поведение `Seconds_Behind_Source` на отложенной реплике:
* Если реплика догнала источник по получению, но ждёт задержку — значение близко к `SOURCE_DELAY`.
* Если реплика отстаёт по получению — значение больше `SOURCE_DELAY`.

### Сценарии применения

*   **Защита от человеческих ошибок**: случайное `DROP TABLE`, `DELETE` без WHERE, ошибочный `UPDATE`. Если ошибка замечена в течение задержки (например, 1 час), отложенная реплика ещё не применила эти транзакции — можно остановить её и использовать как точку восстановления.
*   **Аудит/анализ «как было»**: возможность посмотреть состояние данных на момент времени в прошлом.
*   **Защита от логических ошибок приложения**: ошибки, которые не ловятся на уровне СУБД.

### Ограничения

*   **Не заменяет бэкапы**: отложенная реплика защищает только в пределах окна задержки. Ошибка, обнаруженная позже — уже применена.
*   **При failover отложенная реплика теряет данные** за время отставания от источника. Отложенную реплику нельзя использовать как кандидата для автоматического промоушена без сброса задержки.
*   **Окно задержки должно превышать время обнаружения ошибки человеком**. Если ошибка обнаруживается за 2 часа — задержка должна быть > 2 часов.
*   **Relay log растёт** на всю величину задержки — закладывайте место на диске с запасом.

## Практические сценарии

### Сценарий 1: Настройка отложенной реплики (30 минут)

```sql
-- На реплике (репликация должна быть остановлена для изменения задержки)
STOP REPLICA;

-- Современный синтаксис (MariaDB 10.5+)
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST='192.168.1.10',
    SOURCE_USER='repl_user',
    SOURCE_PASSWORD='password',
    SOURCE_USE_GTID=slave_pos,
    SOURCE_DELAY=1800;  -- 30 минут

-- Устаревший синтаксис (до 10.5)
-- CHANGE MASTER TO MASTER_DELAY=1800;

START REPLICA;
```

### Сценарий 2: Мониторинг отложенной реплики

```sql
SHOW REPLICA STATUS\G
-- Ключевые поля:
-- SQL_Delay: 1800              (заданная задержка)
-- SQL_Remaining_Delay: 1245    (осталось секунд до применения текущего события)
-- Seconds_Behind_Source: 1800  (лаг включает задержку)
-- Slave_SQL_Running_State: Waiting until SOURCE_DELAY seconds after master executed event
```

### Сценарий 3: Откат ошибочного изменения через отложенную реплику

```sql
-- 1. Немедленно остановите репликацию, чтобы не применить ошибочную транзакцию
STOP REPLICA;

-- 2. Определите GTID последней корректной транзакции
SELECT @@gtid_slave_pos;

-- 3. Восстановите данные из отложенной реплики (она отстаёт на задержку)
--    Вариант A: промоутите отложенную реплику в источник (после сброса задержки)
CHANGE REPLICATION SOURCE TO SOURCE_DELAY=0;
START REPLICA;
-- Дождитесь применения всех транзакций до момента ошибки, затем остановите

--    Вариант B: выгрузите нужные данные с отложенной реплики
mariadb-dump --single-transaction --databases app_db > recovery_dump.sql
-- И восстановьте на источнике

-- 4. Увеличьте окно задержки, если ошибка была обнаружена позже окна
CHANGE REPLICATION SOURCE TO SOURCE_DELAY=7200;  -- 2 часа
```

### Сценарий 4: Отключение задержки

```sql
STOP REPLICA;
CHANGE REPLICATION SOURCE TO SOURCE_DELAY=0;
START REPLICA;
-- Или через устаревший синтаксис: CHANGE MASTER TO MASTER_DELAY=0;
```

### Сценарий 5: Multi-source с разной задержкой

```sql
-- Для каждого канала задержка настраивается отдельно
STOP REPLICA FOR CHANNEL 'marketing_db';
CHANGE REPLICATION SOURCE TO SOURCE_DELAY=3600 FOR CHANNEL 'marketing_db';
START REPLICA FOR CHANNEL 'marketing_db';
```

## Валидация

```sql
-- Проверка, что задержка активна
SHOW REPLICA STATUS\G
-- SQL_Delay: 1800
-- Slave_SQL_Running_State: Waiting until SOURCE_DELAY seconds after master executed event

-- Проверка через Performance Schema
SELECT * FROM performance_schema.replication_applier_configuration;
-- DESIRED_DELAY: 1800

SELECT * FROM performance_schema.replication_applier_status;
-- REMAINING_DELAY: секунды до применения
```

## Типовые ошибки

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `SQL_Delay: 0` после настройки | Задержка задана без остановки реплики | `STOP REPLICA;` → `CHANGE REPLICATION SOURCE TO SOURCE_DELAY=N;` → `START REPLICA;` |
| `Seconds_Behind_Source` растёт бесконечно | Реальный лаг + задержка; или I/O-поток остановлен | Проверьте `Replica_IO_Running`; задержка добавляется к реальному лагу |
| Ошибка обнаружена после окна задержки | Окно задержки меньше времени обнаружения | Увеличьте `SOURCE_DELAY`; не полагайтесь только на delayed replica — используйте бэкапы |
| Relay log занял весь диск | Длительная задержка + высокая нагрузка | Увеличьте диск; настройте `relay_log_space_limit` |

## Best Practices

1.  **Задержка 30–60 минут** — типичный выбор для защиты от логических ошибок. Зависит от SLA и времени реакции команды.
2.  **Не используйте отложенную реплику для failover** без сброса `SOURCE_DELAY=0` и полного догона.
3.  **Мониторьте `SQL_Remaining_Delay`** — это прямой индикатор того, что реплика в состоянии задержки.
4.  **Закладывайте дисковое пространство** под relay log с учётом задержки: `размер binlog в час × SOURCE_DELAY / 3600`.
5.  **Отложенная реплика не заменяет PITR** — для восстановления за пределами окна задержки используйте бэкапы + binlog.
