# Диагностика и Troubleshooting репликации MariaDB

## Определения

*   **Replication Lag (Лаг репликации)** — временная задержка между фиксацией транзакции на источнике и её применением на реплике.
*   **`Seconds_Behind_Master`** — классический показатель лага, вычисляемый как разница между временем текущего события в SQL Thread и временем его записи на источнике.
*   **Parallel Replication (Параллельная репликация)** — механизм MariaDB, позволяющий использовать несколько SQL-потоков для одновременного применения транзакций.

## Базовые концепции

### Почему `Seconds_Behind_Master` может быть неточным?

Этот показатель часто вводит в заблуждение в следующих случаях:
1.  **Длительная транзакция:** Если запрос выполняется 3600 секунд, то в течение всего часа счетчик будет показывать 0, а по завершении — мгновенно прыгнет до 3600.
2.  **Параллельная репликация:** При использовании `slave_parallel_threads > 1` транзакции могут применяться не в строгом порядке записи. MariaDB вычисляет лаг на основе "самой старой" активной транзакции, что может приводить к ложным скачкам метрики.
3.  **Разрыв сети:** Если I/O Thread остановлен, значение будет `NULL` или 0, что не означает отсутствие лага.

### Параллельная репликация в MariaDB

В отличие от MySQL, MariaDB имеет уникальные режимы параллелизма (`slave_parallel_mode`):
*   **`optimistic` (Рекомендуемый):** Реплика пытается выполнять транзакции параллельно, предполагая отсутствие конфликтов. Если конфликт обнаружен, транзакция откатывается и выполняется последовательно.
*   **`conservative`:** Параллелизм используется только если источник явно указал группы транзакций, которые можно выполнять одновременно (Group Commit).
*   **`aggressive`:** Максимальный параллелизм, игнорирующий даже некоторые потенциальные конфликты (требует осторожности).

## Практические сценарии

### Сценарий 1: Устранение критического лага

Если лаг растет, выполните следующие действия:

1.  **Проверьте состояние дисков и CPU:** Репликация часто упирается в I/O (особенно при SBR).
2.  **Включите параллельную репликацию:**
    ```sql
    STOP SLAVE;
    SET GLOBAL slave_parallel_threads = 8; -- По количеству ядер или больше
    SET GLOBAL slave_parallel_mode = 'optimistic';
    START SLAVE;
    ```
3.  **Анализ тяжелых запросов:** Используйте `SHOW PROCESSLIST` на реплике. Если SQL Thread висит на `System lock` или `Waiting for table metadata lock`, ищите блокирующий SELECT-запрос в приложении.

### Сценарий 2: Пропуск ошибок (Skip Error)

Если репликация остановилась из-за ошибки (например, удаление уже отсутствующей строки), и вы уверены, что это безопасно:

**Для GTID-репликации (правильный способ):**
Вам нужно "перешагнуть" через битый GTID, записав пустую транзакцию на реплике.
```sql
-- Узнаем текущий gtid_slave_pos
SELECT @@gtid_slave_pos;
-- Переключаем позицию вручную (прибавляем 1 к последовательности или используем следующую)
SET GLOBAL gtid_slave_pos = '0-1-12346';
START SLAVE;
```

**Грубый способ (не рекомендуется для GTID):**
```sql
SET GLOBAL sql_slave_skip_counter = 1;
START SLAVE;
```

## Глубокая диагностика (SRE Toolset)

1.  **Анализ Relay Log:** Если вы не понимаете, что за запрос ломает репликацию:
    ```bash
    mariadb-binlog --base64-output=DECODE-ROWS -v /var/log/mysql/relay-bin.000001 | less
    ```
2.  **Проверка консистентности:** Используйте `pt-table-checksum` из Percona Toolkit. Он безопасно сравнивает данные между источником и репликой, вычисляя хеш-суммы.

## Типовые ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `Error 1062: Duplicate entry` | На реплику записали данные вручную. | Удалите строку на реплике или пропустите транзакцию. |
| `Error 1032: Can't find record` | На источнике удалили/обновили строку, которой нет на реплике. | Восстановите строку на реплике или используйте `slave_skip_errors = 1032` (рискованно). |
| `Relay log read failure` | Повреждение файла Relay Log на диске. | `STOP SLAVE; RESET SLAVE; START SLAVE;` — реплика перекачает логи заново. |
