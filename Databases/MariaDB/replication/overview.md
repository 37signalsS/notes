# Репликация MariaDB: Обзор и стандартные топологии

**Актуально для:** MariaDB 11.4 LTS / 12.3 LTS

## Определения

*   **Репликация (Replication)** — процесс автоматического копирования данных с одного сервера базы данных (**Источник / Source**) на один или несколько других серверов (**Реплика / Replica**). Обеспечивает высокую доступность, балансировку нагрузки на чтение и Disaster Recovery.
*   **Источник (Source)** — основной узел, принимающий операции записи. Ранее в терминологии MySQL/MariaDB назывался *Master*.
*   **Реплика (Replica)** — подчиненный узел, воспроизводящий изменения с источника. Ранее назывался *Slave*.
*   **Бинарный лог (Binlog)** — журнал на источнике, содержащий все изменения данных (транзакции, DDL-операции). Является основой асинхронной репликации.
*   **Relay Log** — локальный журнал на реплике, куда копируются события из бинарного лога источника перед их применением к данным реплики.
*   **GTID (Global Transaction ID)** — уникальный идентификатор транзакции, позволяющий отслеживать её состояние во всем кластере репликации. Формат MariaDB: `domain-id-server-id:sequence`.
*   **Полусинхронная репликация (Semi-synchronous Replication)** — режим, при котором источник ожидает подтверждения от хотя бы одной реплики о записи транзакции в её Relay Log перед фиксацией на источнике.
*   **Crash-safe Replication** — механизм восстановления реплики после аварийного завершения, гарантирующий консистентность данных благодаря восстановлению из Relay Log.
*   **Replication Lag (Лаг репликации)** — временная задержка между фиксацией транзакции на источнике и её применением на реплике. Измеряется в секундах (`Seconds_Behind_Source`) или в позиции GTID. Критичен для кластеров: лаг > 60 секунд требует вмешательства.
*   **`SHOW REPLICA STATUS`** — современный эквивалент `SHOW SLAVE STATUS` (поддерживается в MariaDB 10.5+). Возвращает состояние потоков репликации, позицию GTID и ошибки. В новом выводе поля именуются как `Replica_IO_Running`, `Replica_SQL_Running`, `Seconds_Behind_Source`.
*   **`binlog_gtid_index`** — системная переменная (MariaDB 11.4+, default ON), создающая индекс GTID в каждом файле бинарного лога. Ускоряет поиск стартовой позиции для новой реплики при переподключении, исключая полное сканирование binlog.
*   **`slave_domain_parallel_threads`** — количество рабочих потоков на домен GTID при out-of-order параллельной репликации (MariaDB 11.7+). Позволяет разным доменам репликации использовать отдельные пулы потоков.
*   **Minimal Mode** — режим параллельной репликации (`slave_parallel_mode = minimal`), при котором только шаг фиксации транзакции выполняется параллельно, а все остальные операции применяются последовательно. Полезен для минимизации конфликтов при высокой нагрузке.

## Базовые концепции

### Типы репликации по формату лога

MariaDB поддерживает три формата бинарного лога, определяющих способ записи событий:

| Формат | Описание | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **Statement-based (SBR)** | Записываются SQL-запросы (Statements) | Экономия места в логе; логи читаемы | Нестабильность при использовании `NOW()`, `RAND()`, UDF |
| **Row-based (RBR)** | Записываются изменения конкретных строк | Гарантирует идентичность данных; безопасен для фильтрации | Увеличенный размер лога при массовых UPDATE |
| **Mixed** | Автоматический выбор SBR/RBR | Баланс между размером и надежностью | Сложность предсказания поведения |

**Рекомендация:** Используйте `binlog_format = ROW` для максимальной надежности и совместимости с фильтрацией репликации.

### Классическая репликация (Source-Replica)

В MariaDB используется асинхронная репликация по умолчанию. Источник записывает изменения в **Бинарный лог (Binlog)**, а реплика считывает эти записи через сетевое соединение.

**Потоки репликации (Threads):**
1.  **Binlog Dump Thread (на Источнике):** Отправляет содержимое бинарного лога реплике.
2.  **I/O Thread (на Реплике):** Принимает данные от источника и записывает их в локальный **Relay Log**.
3.  **SQL Thread (на Реплике):** Вычитывает данные из Relay Log и применяет их к базе данных.

### Полусинхронная репликация (rpl_semi_sync)

В отличие от асинхронной, полусинхронная репликация обеспечивает более высокую сохранность данных (RPO близко к 0).

*   **Принцип работы:** Источник блокирует сессию клиента до тех пор, пока хотя бы одна реплика не подтвердит получение транзакции. Если реплики недоступны, источник через таймаут переходит в асинхронный режим.
*   **Плагины:** Реализуется через `semisync_master.so` и `semisync_slave.so`.
*   **Режимы (`rpl_semi_sync_master_wait_point`):**
    *   `AFTER_SYNC` (рекомендуемый): Источник записывает транзакцию в движок и binlog, затем ждет ACK. Только после этого транзакция становится видимой для других сессий. Гарантирует отсутствие "phantom reads".
    *   `AFTER_COMMIT` (по умолчанию): Транзакция фиксируется в движке до получения ACK. Это может привести к ситуации, когда другие клиенты увидят данные, которые еще не ушли на реплику.

### Мульти-сорс репликация (Multi-source Replication)

MariaDB позволяет одной реплике подключаться к нескольким источникам одновременно. Это полезно для агрегации данных из разных шардов или филиалов в одно хранилище (Data Warehouse).

*   **Каналы (Channels):** Каждое соединение с источником идентифицируется уникальным именем канала.
*   **Ограничение:** Все источники должны иметь уникальные `server_id`.

### Параллельная репликация

Для уменьшения лага репликации MariaDB поддерживает параллельное применение транзакций на реплике:

*   **`slave_parallel_threads`** — количество параллельных SQL-потоков (рекомендуется: количество ядер CPU). Alias: `slave_parallel_workers`.
*   **`slave_parallel_mode`** — режим параллелизма:
    *   `optimistic` (рекомендуемый, с MariaDB 10.5+): Пытается выполнять транзакции параллельно, предполагая отсутствие конфликтов. При обнаружении конфликта откатывает и выполняет последовательно. По умолчанию с MariaDB 10.5.1+.
    *   `conservative`: Параллелизм только для явно указанных групп транзакций (Group Commit).
    *   `aggressive`: Максимальный параллелизм с игнорированием некоторых конфликтов (требует осторожности; несовместим с триггерами Conflict Detection and Resolution в MariaDB Enterprise Server 12.3+).
    *   `minimal`: Только шаг фиксации транзакции выполняется параллельно, все остальные операции — последовательно. Полезен для минимизации конфликтов при высокой нагрузке.
*   **`slave_domain_parallel_threads`** — количество потоков на домен GTID при out-of-order параллельной репликации (MariaDB 11.7+). Позволяет разным доменам репликации использовать отдельные пулы потоков.
*   **Out-of-order Parallel Replication:** При использовании разных `gtid_domain_id` транзакции из разных доменов могут применяться параллельно в произвольном порядке. Текущая позиция реплики становится многомерной: каждый домен может находиться на своей позиции в binlog источника.

### Crash-safe Replication

Механизм восстановления реплики после аварийного завершения процесса или сбоя питания:

*   **`relay_log_recovery = ON`** — автоматическое восстановление Relay Log при старте реплики.
*   **`relay_log_info_repository = TABLE`** — хранение информации о позиции репликации в таблице вместо файла (более надежно при сбоях).
*   **`sync_relay_log = 1`** — синхронизация Relay Log на диск после каждой записи (снижает производительность, но повышает надежность).

## Предварительные требования (Prerequisites)

### Аппаратные и сетевые требования

| Компонент | Минимальный | Рекомендуемый |
| :--- | :--- | :--- |
| **CPU** | 2 ядра | 4+ ядер |
| **RAM** | 4 ГБ | 16+ ГБ (зависит от рабочего набора данных) |
| **Диск** | 50 ГБ SSD | NVMe SSD (минимум 100 ГБ) |
| **Сеть** | 100 Мбит/с | 1 Гбит/с с задержкой < 1 мс (в пределах одного дата-центра) |

### Программные требования

- **MariaDB Server** — версия 11.4 LTS или 12.3 LTS (рекомендуется); минимальная версия для GTID: MariaDB 10.0+; для параллельной репликации: MariaDB 10.5+.
- **Уникальные `server_id`** — каждому узлу в топологии репликации требуется уникальный целочисленный идентификатор (от 1 до 2^32-1).
- **Сетевая связность** — порт `3306` должен быть доступен между источником и репликой. Проверка: `telnet source_ip 3306` или `mysql -h source_ip -u repl_user -p -e "SELECT 1"`.
- **Достаточное дисковое пространство** — на источнике для бинарных логов, на реплике для relay log и данных.

### Безопасность

- Создайте отдельного пользователя репликации с минимально необходимыми привилегиями:
  ```sql
  CREATE USER 'repl_user'@'192.168.1.%' IDENTIFIED BY 'StrongPassword123';
  GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'192.168.1.%';
  FLUSH PRIVILEGES;
  ```
- Используйте конкретную подсеть или IP вместо `%`.
- Настройте SSL/TLS для шифрования репликационного трафика (`require_secure_transport = ON`, `ssl_cert`, `ssl_key`).

## Практические сценарии

### Выбор между Galera и Standard Replication

| Характеристика | Galera Cluster | Source-Replica |
| :--- | :--- | :--- |
| **Синхронность** | Синхронная (Multi-master) | Асинхронная / Полусинхронная |
| **Целостность (RPO)** | 0 (гарантировано) | > 0 (асинхронная) / ~0 (полусинхронная) |
| **Масштабирование записи** | Ограничено (все узлы пишут) | Только один узел (Source) |
| **Сложность** | Высокая | Низкая/Средняя |
| **Автоматический failover** | Да | Требует настройки (MaxScale) |

### Рекомендации SRE по настройке

1.  **Использование GTID:** Всегда включайте GTID. Начиная с MariaDB 10.10, GTID используется по умолчанию для новых реплик; для более старых версий явно задайте `gtid_domain_id` и `gtid_strict_mode = ON`. Это упрощает смену источника и автоматическое восстановление репликации.
2.  **Crash-safe Replication:** Убедитесь, что `relay_log_recovery = ON` и `relay_log_info_repository = TABLE`, чтобы реплика могла корректно восстановиться после сбоя питания.
3.  **Мониторинг лага:** Не полагайтесь только на `Seconds_Behind_Source`. Для высоконагруженных систем используйте `pt-heartbeat` или встроенные метрики MariaDB по задержке применения GTID, а также `performance_schema.replication_applier_status_by_worker`.
4.  **Безопасность:** Всегда используйте `read_only = 1` на репликах для предотвращения случайной записи данных. Создавайте отдельного пользователя репликации с привилегией `REPLICATION SLAVE` и ограничением по подсети.
5.  **Сетевые оптимизации:** Убедитесь, что соединение между источником и репликой стабильное с минимальной задержкой. Для удаленных реплик рассмотрите использование сжатия (`slave_compressed_protocol = ON`) и настройку TCP-таймаутов (`slave_net_timeout`, `net_read_timeout`, `net_write_timeout`).
6.  **Индексация GTID:** В MariaDB 11.4+ параметр `binlog_gtid_index = ON` (по умолчанию) ускоряет поиск позиции для новой реплики при переподключении.

### Базовая конфигурация Source-Replica (GTID)

**На Источнике** (`/etc/mysql/mariadb.conf.d/50-server.cnf`):
```ini
[mariadb]
server_id               = 1
log_bin                 = /var/log/mysql/mariadb-bin
binlog_format           = ROW
gtid_domain_id          = 1
sync_binlog             = 1
innodb_flush_log_at_trx_commit = 1
binlog_gtid_index       = ON
```

**На Реплике** (`/etc/mysql/mariadb.conf.d/50-server.cnf`):
```ini
[mariadb]
server_id               = 2
log_bin                 = /var/log/mysql/mariadb-bin
relay_log               = /var/log/mysql/relay-bin
read_only               = 1
gtid_domain_id          = 1
relay_log_recovery      = ON
relay_log_info_repository = TABLE
slave_parallel_threads  = 8
slave_parallel_mode     = 'optimistic'
binlog_gtid_index       = ON
```

### Валидация конфигурации

После применения настроек и запуска репликации выполните проверку:

```sql
-- На реплике: убедитесь, что потоки запущены
SHOW REPLICA STATUS\G

-- Ожидаемые значения:
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source: 0
-- Source_Server_Id: совпадает с server_id источника

-- Проверка GTID-позиции (источник vs реплика)
SELECT @@gtid_binlog_pos AS source_gtid;
SELECT @@gtid_slave_pos AS replica_gtid;

-- Проверка Crash-safe Replication
SHOW VARIABLES LIKE 'relay_log_recovery';
SHOW VARIABLES LIKE 'relay_log_info_repository';
SHOW VARIABLES LIKE 'sync_relay_log';

-- Проверка полусинхронности (на источнике)
SHOW STATUS LIKE 'Rpl_semi_sync_master_clients';
SHOW STATUS LIKE 'Rpl_semi_sync_master_status';
```

### Мониторинг репликации

**Основные метрики для мониторинга:**
```sql
-- Современный эквивалент SHOW SLAVE STATUS (MariaDB 10.5+)
SHOW REPLICA STATUS\G

-- Ключевые поля для мониторинга:
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source: 0
-- Last_IO_Error: (пусто)
-- Last_SQL_Error: (пусто)

-- Для совместимости также доступен:
SHOW SLAVE STATUS\G

-- Проверка полусинхронности (на источнике)
SHOW STATUS LIKE 'Rpl_semi_sync_master_clients';
-- Должно быть > 0

-- Мониторинг GTID Lag
-- Сравните gtid_binlog_pos (источник) и gtid_slave_pos (реплика)
SELECT @@gtid_binlog_pos;
SELECT @@gtid_slave_pos;

-- Performance Schema: состояние потоков репликации
SELECT * FROM performance_schema.replication_connection_status;
SELECT * FROM performance_schema.replication_applier_status_by_worker;
SELECT * FROM performance_schema.replication_applier_status_by_coordinator;

-- sys schema: удобные представления для быстрой диагностики
SELECT * FROM sys.replication_connection_status;
SELECT * FROM sys.replication_applier_status;
```

**Автоматический мониторинг с помощью pt-heartbeat:**
```bash
# На источнике (запускается как демон)
pt-heartbeat --update --database heartbeat --create-table --daemonize

# На реплике (проверка лага)
pt-heartbeat --monitor --database heartbeat --master-server-id=1
```

## Failover стратегии

### Ручной Failover

1.  Убедитесь, что выбранный кандидат (реплика) имеет наименьший лаг (`Seconds_Behind_Source` или GTID-позиция).
2.  Остановите запись на старом источнике (если возможно).
3.  Дождитесь применения всех транзакций на новом источнике.
4.  Выполните на новом источнике:
    ```sql
    STOP REPLICA;
    RESET REPLICA ALL;
    SET GLOBAL read_only = 0;
    ```
5.  Обновите конфигурацию приложения для подключения к новому источнику.
6.  На остальных репликах переключите источник (современный синтаксис):
    ```sql
    CHANGE REPLICATION SOURCE TO
        SOURCE_HOST='new_source_ip',
        SOURCE_USER='repl_user',
        SOURCE_PASSWORD='password',
        SOURCE_USE_GTID=slave_pos;
    START REPLICA;
    ```
    Альтернативный синтаксис (обратная совместимость):
    ```sql
    CHANGE MASTER TO
        MASTER_HOST='new_source_ip',
        MASTER_USER='repl_user',
        MASTER_PASSWORD='password',
        MASTER_USE_GTID=slave_pos;
    START SLAVE;
    ```

### Автоматический Failover с MaxScale

MaxScale предоставляет автоматическое обнаружение и переключение при сбое источника:

*   **Monitor Module:** Отслеживает состояние всех узлов репликации.
*   **Read/Write Splitting:** Автоматически маршрутизирует запросы на чтение к репликам, а на запись — к источнику.
*   **Failover:** Автоматически промотирует реплику в источник при обнаружении сбоя.

## Типовые ограничения репликации

1.  **Чтение с задержкой:** Реплики всегда отстают от источника (даже при полусинхронной репликации).
2.  **Односторонняя запись:** Запись разрешена только на источнике (для стандартной репликации).
3.  **Неподдерживаемые операции:**
    *   `LOAD DATA INFILE` (может работать некорректно с SBR).
    *   Управление пользователями и привилегиями (требует отдельной синхронизации).
    *   Временные таблицы (при определенных условиях).
4.  **Сетевые зависимости:** Репликация требует стабильного сетевого соединения между узлами.

### Типовые сценарии и ограничения (Edge Cases)

1.  **Большие транзакции:** Одиночные транзакции > 1 ГБ могут вызывать лаг и таймауты на реплике. Разбивайте на мелкие батчи или увеличьте `slave_net_timeout` и `max_allowed_packet`.
2.  **Часовые пояса и локаль:** Разные часовые пояса на источнике и реплике влияют на функции `NOW()`, `CURTIME()`, `UNIX_TIMESTAMP()`. Используйте UTC на всех узлах (`default_time_zone = '+00:00'`) или функцию `CONVERT_TZ()`. Подробно — [Часовые пояса](../time_zones.md).
3.  **Кодировки и сравнения:** Разные параметры `character_set_server` и `collation_server` на источниках и репликах приводят к некорректной сортировке и несоответствию индексов. Должны совпадать на всех узлах.
4.  **DDL на реплике:** Изменения схемы на реплике вручную (`ALTER TABLE`) прерывают репликацию при применении того же DDL с источника. Используйте `pt-online-schema-change` или `gh-ost` для безопасных изменений.
5.  **Временные таблицы:** Временные таблицы (`TEMPORARY TABLE`) созданные в рамках транзакции, реплицируются только внутри этой транзакции. После фиксации они становятся невидимыми для других сессий и не реплицируются на другие узлы.
6.  **Потоковые форматы binlog:** Изменение `binlog_format` на лету (`STATEMENT` → `ROW`) требует перезапуска репликации или сброса позиции. GTID-репликация чувствительна к формату binlog на источнике.
7.  **Несоответствие версий:** Источник должен быть такой же или более новой версии, чем реплика. При репликации с MySQL на MariaDB убедитесь в совместимости формата binlog и GTID.
8.  **Ротация бинарных логов:** Убедитесь, что `expire_logs_days` (или `binlog_expire_logs_seconds`) достаточно велик, чтобы реплики успели получить все события до их удаления. Для PITR используйте отдельный механизм бэкапов binlog.
