# TimescaleDB

## Определения

**TimescaleDB** — это расширение (extension) для СУБД (Система управления базами данных) PostgreSQL, которое превращает ее в полноценную базу данных временных рядов (TSDB — Time-Series Database). Оно оптимизировано для хранения и анализа данных, привязанных ко времени, сохраняя при этом все возможности реляционной базы данных.

**Текущая версия:** TimescaleDB 2.17+ (2026) с полной поддержкой PostgreSQL 17 и 18.

**Временные ряды (Time-Series Data):** данные, которые последовательно изменяются во времени.
**Особенности временных рядов:**
*   **Метка времени:** Каждая запись имеет обязательное поле времени.
*   **Append-only:** Данные преимущественно добавляются, старые записи не меняются (только удаляются целиком).
*   **Групповой анализ:** Записи редко рассматриваются по отдельности, важен анализ окон или периодов.

## Основные концепции

### TimescaleDB vs PostgreSQL
Несмотря на то, что данные можно хранить в обычном PostgreSQL, TimescaleDB дает существенные преимущества:
*   **Скорость вставки (INSERT):** Ванильный PostgreSQL может вставлять миллиард строк около 40 часов, тогда как TimescaleDB справляется за **3 часа** на том же железе.
*   **Оптимизация запросов:** Специализированная система улучшения запросов (до 14 000 параметров) для работы с временными зависимостями.
*   **Удаление данных:** До 2000 раз более быстрое удаление старых данных за счет манипуляций с чанками.

### Архитектура: гипертаблицы и чанки

**Гипертаблица (Hypertable)** — это абстракция над множеством обычных таблиц PostgreSQL, называемых **чанками (chunks)**. Для пользователя гипертаблица выглядит как единая большая таблица, но внутри она разбита на части.

**Чанк (Chunk)** — внутренняя дочерняя таблица, в которой физически хранятся данные за определённый промежуток времени. TimescaleDB гарантирует, что каждый чанк оптимально помещается в оперативную память для быстрой индексации.

**Ключевые преимущества:**
- **Высокая скорость вставки:** за счет работы с небольшими индексами активных чанков в памяти.
- **Автоматическое партиционирование:** создание новых чанков происходит прозрачно для пользователя.
- **Экосистема PostgreSQL:** поддержка всех стандартных индексов, триггеров и расширений (напр., PostGIS).

### Непрерывные агрегаты в реальном времени

**Непрерывные агрегаты (Continuous Aggregates)** — это материализованные представления, которые обновляются инкрементально. Современные версии TimescaleDB поддерживают **Real-time Aggregation**, объединяя предрассчитанные данные на диске с самыми свежими данными, которые еще не были агрегированы.

```sql
-- Создание непрерывного агрегата с поддержкой реального времени
CREATE MATERIALIZED VIEW hourly_metrics
WITH (timescaledb.continuous) AS
SELECT
    time_bucket('1 hour', time) AS bucket,
    device_id,
    AVG(cpu_usage) AS avg_cpu
FROM device_metrics
GROUP BY bucket, device_id;
```

### Колоночное сжатие

TimescaleDB использует колоночный формат для старых данных, что позволяет экономить до 90% дискового пространства и значительно ускорять аналитические запросы.

### Многоуровневое хранение (Tiered Storage)

Функция **Tiered Storage** позволяет автоматически перемещать старые, редко используемые чанки из быстрого локального хранилища (SSD) в объектное хранилище (например, AWS S3) в рамках единой гипертаблицы. Это позволяет хранить петабайты данных по низкой стоимости, оставляя их доступными для SQL-запросов.

### Аналитический инструментарий (Hyperfunctions)

**Timescale Toolkit** предоставляет набор **Hyperfunctions** — специализированных SQL-функций для сложной аналитики:
- `approx_percentile`: вычисление процентилей с высокой точностью на огромных объемах.
- `stats_agg`: расчет статистических агрегатов (среднее, отклонение) в один проход.
- `time_bucket_ng`: улучшенная группировка по времени с учетом часовых поясов.

## Практические сценарии

### Установка и настройка

**Установка в Debian/Ubuntu (PostgreSQL 17):**

```bash
# Добавление репозитория и установка
sudo add-apt-repository ppa:timescale/timescaledb-ppa
sudo apt update
sudo apt install timescaledb-2-postgresql-17

# Настройка производительности
sudo timescaledb-tune --quiet --yes

# Активация расширения в БД
psql -d my_database -c "CREATE EXTENSION IF NOT EXISTS timescaledb;"
```

### Создание гипертаблицы и политик

```sql
-- 1. Создание гипертаблицы
SELECT create_hypertable('device_metrics', 'time');

-- 2. Настройка сжатия (через 7 дней)
ALTER TABLE device_metrics SET (
    timescaledb.compress,
    timescaledb.compress_segmentby = 'device_id'
);
SELECT add_compression_policy('device_metrics', INTERVAL '7 days');

-- 3. Настройка политики удаления (через 2 года)
SELECT add_retention_policy('device_metrics', INTERVAL '2 years');
```

## Дополнительная информация

### Сравнение с альтернативами

| Система | Тип решения | Ключевая особенность |
| :--- | :--- | :--- |
| **TimescaleDB** | Реляционная TSDB | Полный SQL, ACID, JOIN с обычными таблицами. |
| **[ClickHouse](./ClickHouse/clickhouse.md)** | OLAP СУБД | Максимальная скорость агрегации на петабайтах. |
| **InfluxDB** | NoSQL TSDB | Собственный язык (Flux/InfluxQL), гибкая схема. |
| **[VictoriaMetrics](../VictoriaMetrics/overview.md)** | TSDB для метрик | Высокая плотность, совместимость с Prometheus. |
| **[Prometheus](../Prometheus/overview.md)** | Мониторинг | Pull-модель, специализированный язык PromQL. |

### Ограничения и особенности

- **Шардирование:** поддержка Multi-node (распределенных гипертаблиц) была значительно пересмотрена в последних версиях; основной фокус смещен на производительность одиночного узла и облачные решения.
- **Изменение схемы:** некоторые операции `ALTER TABLE` над сжатыми данными требуют их предварительной декомпрессии.
