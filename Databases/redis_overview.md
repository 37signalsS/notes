# Redis — обзор и практическое руководство

Высокопроизводительное хранилище данных в оперативной памяти (In-memory), используемое как база данных, кэш, брокер сообщений и очередь задач. Теоретические основы кэширования описаны в разделе **[Кэширование: обзор](../Concepts/Caching/caching_overview.md)**.

## Определения

**Redis (Remote Dictionary Server)** — это NoSQL СУБД типа «ключ-значение» с открытым исходным кодом. Благодаря работе целиком в RAM, Redis обеспечивает экстремально низкие задержки (микросекунды) и высокую пропускную способность (миллионы запросов в секунду на узел).

**Текущая версия:** Redis 8.x (2026).

**Лицензионные изменения (2024-2026):** 
*   Начиная с версии 7.4 (2024), Redis перешел с лицензии BSD на проприетарные лицензии (RSALv2 и SSPLv1). Это привело к появлению полностью открытых форков под эгидой Linux Foundation, таких как **Valkey** и **Redict**.
*   В версиях 8.x (2025-2026) Redis ввел **тройную лицензию** (AGPLv3, RSALv2 и SSPLv1), вернув продукту статус Open Source (OSI-approved через AGPLv3).

Отличительная черта Redis — поддержка разнообразных структур данных с атомарными операциями на стороне сервера.

## Основные концепции

### Модель данных

Redis — хранилище типа «ключ-значение» с богатым набором структур. В версии 8.x возможности «Redis Stack» (JSON, Search, TimeSeries, Vector) полностью интегрированы в ядро.

| Структура | Описание | Размер | Применение |
| :--- | :--- | :--- | :--- |
| **Strings** | Текстовые или бинарные данные | До 512 МБ | Кэш страниц, сессии, счетчики. |
| **Lists** | Упорядоченные коллекции по порядку вставки | 2^32 - 1 | Простые очереди, логи последних событий. |
| **Sets** | Неупорядоченные уникальные строки | 2^32 - 1 | Теги, уникальные посетители, пересечения. |
| **Hashes** | Карты (map) полей и значений | 2^32 - 1 | Объекты пользователей, конфигурации. |
| **Sorted Sets** | Множества с числовым score | 2^32 - 1 | Лидерборды, индексы с приоритетом. |
| **Bitmaps** | Битовые массивы | 512 МБ | Аналитика посещаемости (Daily Active Users). |
| **HyperLogLog** | Подсчет уникальных (приблизительно) | ~12 КБ | Cardinality на больших данных. |
| **Geospatial** | Координаты (широта/долгота) | 2^32 - 1 | Поиск точек в радиусе, дистанции. |
| **Streams** | Логи событий с группами потребителей | 2^64 - 1 | Шина событий, очереди с ACK. |
| **JSON** (v8+) | Нативная поддержка документов | Сложные объекты | Документо-ориентированное хранение. |
| **Vector Set** | Векторы для AI/LLM | Поиск KNN | RAG-системы, поиск сходства. |
| **Array** (v8+) | Индексированные массивы | 2^64 - 1 | Высокопроизводительные временные ряды. |

**Внутренние оптимизации памяти:**
- `listpack` (заменил `ziplist`) — компактное хранение небольших коллекций в одном блоке памяти.
- `intset` — оптимизация для множеств, состоящих только из целых чисел.
- `quicklist` — связный список из `listpack` блоков для списков.

Все операции над структурами данных атомарны.

### Управление памятью

Redis использует аллокатор `jemalloc` с объектными обертками. При достижении лимита `maxmemory` вступает в силу политика вытеснения.

**Политики вытеснения (`maxmemory-policy`):**

| Политика | Описание |
| :--- | :--- |
| `noeviction` | Не вытеснять, возвращать ошибку при записи. Безопасно для роли БД. |
| `allkeys-lru` | (Рекомендуется) Удаляет наименее давно использованные ключи. |
| `allkeys-lfu` | Удаляет наименее часто используемые ключи. |
| `allkeys-random` | Удаляет случайные ключи. |
| `volatile-lru` | Вытеснять LRU только среди ключей с установленным TTL. |
| `volatile-lfu` | Вытеснять LFU только среди ключей с установленным TTL. |
| `volatile-random` | Вытеснять случайные ключи только с TTL. |
| `volatile-ttl` | Вытеснять ключи с наименьшим оставшимся TTL. |

### TTL и старение данных

Redis хранит TTL для каждого ключа с миллисекундной точностью:
1. **Пассивное истечение:** Ключ удаляется при попытке обращения, если TTL истек.
2. **Активное истечение:** Фоновый процесс выборочно проверяет ключи (настройка `hz`, по умолчанию 10 раз в сек).

### Механизмы персистентности (Persistence)

1.  **RDB (Snapshotting):** Создание снапшотов всей БД. Компактно, быстрое восстановление, но риск потери данных между снапшотами.
2.  **AOF (Append-Only File):** Журналирование каждой операции записи. В v7.0+ используется **Multi-part AOF**, где данные разделяются на базовый файл и инкрементальные обновления.
3.  **Redis Flex (v8+):** Новый движок оптимизации фоновых задач, значительно снижающий пиковые задержки (Tail Latency) во время снапшотов за счет интеллектуального планирования I/O.

### Программируемость: Lua и Функции

1.  **Lua-скрипты:** Позволяют выполнять группу команд атомарно.
2.  **Redis Functions (v7+):** Эволюция скриптов. Функции являются частью БД (персистентны), поддерживают версионность и избавляют клиента от необходимости повторной загрузки логики.

### Безопасность и контроль доступа

В версии 8.x используется система **ACL v2**:
- **ACL Dryrun:** Команда `ACL DRYRUN <user> <command>` для проверки прав без выполнения.
- **Интеграция:** Поддержка **TLS 1.3**, интеграция с **LDAP/Active Directory** и **Entra ID RBAC**.
- **Безопасность по умолчанию:** Обязательный пароль (`requirepass`) и привязка к интерфейсам.

### Архитектура выполнения и потоковая модель

- **Threaded I/O (v6+):** Основной поток выполняет команды, вспомогательные потоки обрабатывают чтение/запись в сетевые сокеты.
- **Enhanced Multi-threading (v8+):** Расширенная многопоточность для фоновых задач (lazy free, active defrag) и векторного поиска, обеспечивающая до **2x прироста производительности** при сохранении атомарности основного ядра.

### Масштабирование и высокая доступность

- **Replication:** Асинхронная master-slave репликация.
- **Sentinel:** Мониторинг мастер-нод и реплик, автоматический failover.
- **Redis Cluster:** Шардирование по 16384 хэш-слотам. Горизонтальное масштабирование записи. В v8.x улучшена стабильность перебалансировки слотов без простоя.

**Пороги для шардирования Redis (2026):**
- **Размер датасета:** ~1 ТБ — при приближении к этому объему данных необходимо шардирование.
- **Пропускная способность:** ~100 000–200 000 операций в секунду — топовый кластер начинает деградировать при этих нагрузках.
- **Latency:** Если требуется гарантировать время ответа < 0.5 мс, необходимо размещать данные на отдельных физических инстансах (шардирование или выделенный кластер).

**Практический вывод:** Современные оптимизированные инстансы поддерживают до 1 ТБ оперативной памяти. Для большинства систем можно реализовать простой «тупой» кэш (весь датасет в RAM), что проще в разработке и поддержке, чем сложный partial-кэш с динамической инвалидацией. Бутылочным горлышком при кэшировании обычно является пропускная способность (операции в секунду), а не объем оперативной памяти.

### Очереди задач
Построение очередей на базе **List** или **Streams**:
- **LPUSH / RPUSH / BLPOP:** Блокирующие операции для асинхронной обработки.
- **Streams (XADD/XREAD):** Модель с группами потребителей, подтверждением (ACK) и сохранением истории.

## Практические сценарии

### Счетчики и аналитика
```bash
# Атомарное увеличение на 1
INCR page_views:article:123
# Увеличение на N
INCRBY page_views:article:123 10
# Увеличение дробного числа
INCRBYFLOAT rating:product:789 0.5
```

### Сессии пользователей
```bash
# Создание сессии с TTL 30 минут (1800 сек)
SETEX session:abc123 1800 "{\"user_id\":123,\"role\":\"admin\"}"
# Проверка и продление
EXISTS session:abc123
EXPIRE session:abc123 1800
```

### Распределённые блокировки (Redlock)
```bash
# Захватить блокировку на 30 сек (NX - только если нет ключа)
SET lock:resource:123 "client_id_uuid" NX EX 30
```
*Освобождение (через Lua для атомарности):*
```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

### Pub/Sub и Streams
```bash
# Публикация
PUBLISH channel:news "Breaking news!"
# Подписка
SUBSCRIBE channel:news

# Streams: добавление записи
XADD orders_stream * user_id 100 action "purchase"
```

### Геоданные
```bash
# Добавление координат
GEOADD cities 13.4050 52.5200 "Berlin"
GEOADD cities 2.3522 48.8566 "Paris"
# Поиск в радиусе 500 км от Берлина
GEORADIUS cities 13.4050 52.5200 500 km
# Расстояние между городами
GEODIST cities "Berlin" "Paris" km
```

### Векторный поиск (v8+)
```bash
# Поиск топ-5 похожих векторов (KNN)
FT.SEARCH idx "*=>[KNN 5 @vec $query_vec]" PARAMS 2 query_vec "\x00..." DIALECT 2
```

## Установка и настройка (Ubuntu 24.04/26.04)

### Шаг 1: Инсталляция
```bash
sudo apt update && sudo apt install redis-server
sudo systemctl enable --now redis-server
```

### Шаг 2: Тюнинг ядра Linux (Критично для Prod)
```bash
# 1. Отключение Transparent Huge Pages (вызывает задержки при снапшотах)
echo never | sudo tee /sys/kernel/mm/transparent_hugepage/enabled

# 2. Увеличение лимита соединений
sudo sysctl -w net.core.somaxconn=65535

# 3. Разрешение overcommit памяти (избегание ошибок при форке процесса RDB)
echo "vm.overcommit_memory = 1" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p
```

### Шаг 3: Базовая конфигурация (`/etc/redis/redis.conf`)
```conf
# Привязка и безопасность
bind 127.0.0.1 ::1
requirepass secure_password_2026

# Настройка памяти
maxmemory 4gb
maxmemory-policy allkeys-lru

# Персистентность
save 900 1
save 300 10
appendonly yes
appendfsync everysec

# Дефрагментация
activedefrag yes
```

## Диагностика и устранение неисправностей

### Инструменты диагностики
```bash
# Мониторинг команд в реальном времени (Внимание: снижает FPS!)
redis-cli monitor

# Поиск «тяжелых» ключей (Big Keys)
redis-cli --bigkeys

# Статистика задержек
redis-cli --latency

# Сканирование ключей по шаблону (безопасно для Prod в отличие от KEYS *)
redis-cli --scan --pattern "user:*"
```

### Типичные проблемы (Troubleshooting)

1.  **OOM (Out of Memory):**
    *   *Симптом:* Ошибка `OOM command not allowed`.
    *   *Действие:* Проверьте `INFO memory`. Изучите `mem_fragmentation_ratio` (если > 1.5, включите `activedefrag`). Проверьте, не занимают ли Big Keys всю память.
2.  **Latency Spikes (Всплески задержек):**
    *   *Причина:* Тяжелые команды (KEYS, SMEMBERS) или THP в ядре.
    *   *Решение:* Используйте `SCAN`. Отключите THP. Проверьте `slowlog get 10`.
3.  **Replication Lag:**
    *   *Диагностика:* `redis-cli info replication`.
    *   *Решение:* Проверьте пропускную способность сети и параметр `repl-backlog-size`.
