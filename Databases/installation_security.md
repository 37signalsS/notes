# Безопасная установка и закалка СУБД

## Определения

**Закалка (Hardening)** — процесс настройки СУБД (Система управления базами данных) и операционной среды для минимизации поверхности атаки и устранения стандартных уязвимостей.

**Принцип наименьших привилегий (Principle of Least Privilege, PoLP)** — концепция безопасности, согласно которой пользователю или приложению предоставляются только те права, которые минимально необходимы для выполнения их задач.

**Эшелонированная защита (Defense in Depth)** — стратегия использования нескольких уровней мер безопасности для защиты данных на уровне сети, ОС (Операционная система) и самой базы данных.

## Основные концепции

Первичная установка большинства СУБД по умолчанию ориентирована на простоту развертывания, а не на безопасность. Базовая "закалка" включает:

1. **Изоляция сети:** ограничение доступа к портам СУБД (напр., 5432, 3306, 27017) только для доверенных IP (Internet Protocol).
2. **Управление доступом:** удаление анонимных пользователей и ограничение удаленного входа для суперпользователей (root/postgres).
3. **Шифрование:** использование TLS (Transport Layer Security) для защиты данных при передаче и SCRAM для защиты паролей.
4. **Минимизация функций:** отключение неиспользуемых плагинов, расширений и функций ОС (например, `xp_cmdshell` в SQL Server).

## Практические сценарии

### MySQL и MariaDB: Использование скриптов защиты

В современных версиях (MySQL 8.4 LTS, MariaDB 12.3 LTS) утилиты защиты являются обязательным шагом после установки.

**Запуск:**
```bash
# Для MariaDB
sudo mariadb-secure-installation

# Для MySQL
sudo mysql_secure_installation
```

**Ключевые настройки:**
- **VALIDATE PASSWORD:** в MySQL 8.x рекомендуется включить компонент для проверки сложности паролей.
- **unix_socket:** в MariaDB 11.x+ для локального root по умолчанию используется `unix_socket`, что избавляет от необходимости хранить пароль root в файлах (вход только через `sudo`).
- **Блокировка root:** запрет удаленного подключения (`Disallow root login remotely`) обязателен для всех сред.

### PostgreSQL: Безопасность на уровне хоста и ролей

PostgreSQL (версии 15–17) требует ручной настройки файлов конфигурации.

**Аутентификация в `pg_hba.conf`:**
Используйте `scram-sha-256` вместо `md5` или `password`.
```conf
# TYPE  DATABASE        USER            ADDRESS                 METHOD
local   all             postgres                                peer
host    all             all             127.0.0.1/32            scram-sha-256
host    all             all             192.168.1.0/24          scram-sha-256
```

**Безопасность ролей (SQL):**
```sql
-- Создание пользователя с ограниченными правами
CREATE USER app_user WITH PASSWORD 'Strong_Password_123';

-- Запрет публичного доступа к схеме (актуально для PG < 15)
REVOKE ALL ON SCHEMA public FROM PUBLIC;

-- Предоставление прав только на конкретную БД
GRANT CONNECT ON DATABASE my_db TO app_user;
```

### MongoDB: Авторизация и сетевая привязка

По умолчанию MongoDB 7.x/8.x слушает только `localhost`, но авторизация может быть выключена.

**Настройка в `mongod.conf`:**
```yaml
net:
  port: 27017
  bindIp: 127.0.0.1  # Привязка только к локальному интерфейсу

security:
  authorization: enabled  # Обязательно для включения RBAC
```

**Создание администратора (до включения авторизации):**
```javascript
use admin
db.createUser({
  user: "admin",
  pwd: passwordPrompt(), // безопасный ввод
  roles: [ { role: "userAdminAnyDatabase", db: "admin" }, "readWriteAnyDatabase" ]
})
```

### Системная закалка (OS Level)

База данных защищена ровно настолько, насколько защищена ОС, на которой она запущена.

1. **Файрвол (UFW/Firewalld):**
   ```bash
   # Разрешить доступ к Postgres только с бэкенд-сервера
   sudo ufw allow from 10.0.5.10 to any port 5432 proto tcp
   ```
2. **AppArmor / SELinux:** убедитесь, что профили для СУБД находятся в режиме `enforce`. Это предотвратит чтение СУБД произвольных файлов на диске даже при наличии уязвимости (напр., SQL Injection).
3. **Лимиты ресурсов (`sysctl` / `limits.conf`):** ограничение использования памяти и количества процессов защищает от атак типа DoS (Denial of Service).

## Дополнительная информация

### Контроль и аудит

- **Логирование:** включите логирование неудачных попыток входа и DDL-запросов (изменение схемы).
- **pgAudit:** для PostgreSQL рекомендуется использовать расширение `pgaudit` для детального отслеживания действий администраторов.
- **MariaDB Audit Plugin:** встроенное решение для мониторинга активности в MariaDB.

### Управление секретами

Никогда не храните пароли СУБД в конфигурационных файлах приложений или переменных окружения в открытом виде. Используйте:
- **HashiCorp Vault:** для динамических секретов с коротким временем жизни.
- **AWS/Yandex Cloud Secrets Manager:** нативные облачные решения.
