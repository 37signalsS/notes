# Citus: распределенный PostgreSQL

**Актуально для:** Citus 14.x, PostgreSQL 18

---

## Определения

**Citus** — расширение для СУБД PostgreSQL, которое превращает ее в распределенную базу данных с архитектурой **Shared-Nothing**. Citus позволяет горизонтально масштабировать PostgreSQL (scale-out), распределяя данные и запросы по кластеру из нескольких серверов.

**Ключевая цель** — масштабирование PostgreSQL «наружу» (scale-out) для обработки больших объемов данных (десятки и сотни терабайт) и высоких нагрузок на запись, которые не может выдержать один сервер. При этом сохраняется полная совместимость с экосистемой PostgreSQL: типы данных, функции, инструменты и коннекторы.

- **Coordinator (Координатор):** Основной узел, точка входа для приложений. Хранит метаданные о расположении шардов и управляет планированием распределенных запросов. Начиная с Citus 12.0, координатор может сам хранить данные (шарды), что позволяет плавно переходить от одного узла к кластеру.
- **Worker Hosts (Воркеры):** Рабочие узлы, хранящие шарды и выполняющие фрагменты запросов. Воркеры могут взаимодействовать друг с другом напрямую для выполнения сложных JOIN'ов.
- **Shard (Шард):** Фрагмент распределенной таблицы. Citus разбивает таблицу на множество шардов (по умолчанию 32), которые равномерно распределяются по воркерам. Физически шард — это обычная таблица PostgreSQL на воркере с именем вида `table_name_102001`.
- **Distribution Column (Ключ дистрибуции):** Колонка, на основе которой строки распределяются по шардам. Строки с одинаковым значением попадают на один шард.
- **Colocation (Совместное размещение):** Гарантирует, что строки из разных таблиц с одинаковым значением ключа дистрибуции попадут на один и тот же физический узел.
- **Schema-based Sharding (Шардирование по схемам):** Отдельная схема на каждый тенант, введено в Citus 12.0. Полезно для микросервисов с гетерогенными схемами.
- **MX Mode (Multi-Node eXecution, с Citus 11.0):** Режим, при котором приложения могут подключаться к любому воркеру, а не только к координатору.

## Основные концепции

### Архитектура кластера

Citus использует архитектуру **Shared-Nothing**, где каждый узел (координатор и воркеры) обладает собственным процессором, памятью и дисковым хранилищем.

- **Coordinator:** Принимает SQL-запросы, анализирует метаданные распределения и либо перенаправляет запрос на конкретный воркер (Fast Path), либо разбивает его на параллельные подзадачи (Distributed Planner).
- **Workers:** Выполняют фрагменты запросов на локальных шардах и возвращают результаты координатору.
- **Shards:** Физически реализуются как стандартные таблицы PostgreSQL на воркерах. Citus управляет ими через системные таблицы метаданных, которые реплицируются на все узлы.

### Планирование и выполнение запросов

Citus использует два типа планировщиков:

1.  **Fast Path / Router Planner:**
    -   Используется, если в запросе (SELECT, UPDATE, DELETE) указан ключ дистрибуции в условии `WHERE`.
    -   Координатор мгновенно перенаправляет запрос на конкретный воркер, содержащий нужный шард.
    -   Минимальные задержки, сравнимые с одиночным инстансом PostgreSQL.
2.  **Distributed Planner:**
    -   Используется для сложных запросов, агрегаций и JOIN'ов, затрагивающих множество шардов.
    -   Разбивает запрос на «фрагменты задач» (task fragments), которые выполняются параллельно на воркерах.
    -   **Adaptive Executor:** Динамически управляет количеством соединений с воркерами. Для массовых запросов использует агрессивное параллельное выполнение.

### Типы таблиц

Citus расширяет стандартную модель данных тремя типами распределения:

1.  **Распределенные таблицы (Distributed Tables):**
    -   Большие таблицы, шардированные по ключу дистрибуции (distribution column).
    -   Создание: `SELECT create_distributed_table('table_name', 'distribution_column');`
    -   Пример: таблицы фактов, событий, заказов.
    -   **Schema-based sharding (Citus 12.0+):** При создании распределенной таблицы с опцией `distribution='append'` и параметром `create_default_table = false` можно использовать отдельные схемы для тенантов.

2.  **Таблицы-справочники (Reference Tables):**
    -   Небольшие таблицы, которые реплицируются на каждый узел кластера (включая координатор).
    -   Позволяют выполнять локальные JOIN'ы с распределенными таблицами на любом воркере.
    -   Создание: `SELECT create_reference_table('table_name');`
    -   Пример: справочники стран, категорий товаров.

3.  **Локальные таблицы (Local Tables):**
    -   Стандартные таблицы PostgreSQL на координаторе. Используются для служебных данных или небольших справочников, не требующих репликации на воркеры.

### Колоночное хранение (Columnar Storage)

Citus поддерживает нативный колоночный формат хранения (Columnar):
- **Сжатие:** до 3-10 раз по сравнению с классическим форматом Heap.
- **Производительность:** пропуск чтения ненужных колонок ускоряет OLAP-запросы в разы.
- **Virtual Generated Columns (PostgreSQL 18):** Поддержка виртуальных генерируемых колонок на распределенных таблицах, что позволяет вычислять значения при чтении без затрат на хранение.

```sql
-- Таблица с колоночным хранением
CREATE TABLE archive_events (
    id bigserial,
    event_time timestamptz,
    data jsonb
) USING columnar;
```

### Совместное размещение (Colocation)

**Colocation** гарантирует, что строки из разных таблиц с одинаковым значением ключа дистрибуции попадут на один и тот же физический узел:
- Позволяет выполнять высокопроизводительные JOIN'ы без перемещения данных между узлами (reshuffling).
- Обеспечивает работу `FOREIGN KEY` между распределенными таблицами.
- Таблицы автоматически объединяются в **colocation groups**, если они имеют одинаковый тип данных ключа дистрибуции и количество шардов.

### Транзакционность и целостность

- **Распределенные транзакции:** Citus поддерживает атомарность (ACID) для запросов, затрагивающих несколько шардов, используя двухфазный коммит (2PC).
- **Уникальные индексы:** Должны включать ключ дистрибуции для обеспечения локальной проверки на уровне шарда.
- **Temporal Constraints (PostgreSQL 18):** Поддержка временных ограничений в распределенном режиме для аудита данных и версионирования.
- **Ограничения NOT ENFORCED:** PostgreSQL 18 расширяет синтаксис ограничений, что требует корректной поддержки на уровне координатора и воркеров.

## Предварительные требования (Prerequisites)

### Аппаратное обеспечение

- **Сеть:** Для горизонтального масштабирования критична задержка (Latency) и пропускная способность. Рекомендуется **10 Gbps+** между координатором и воркерами. Задержка между узлами должна быть < 1 ms.
- **Диски:** Для аналитических нагрузок рекомендуется NVMe. Для OLTP — SSD с высокой выносливостью (DWPD ≥ 1). Выносите `pg_wal` на отдельный физический диск или RAID 1.
- **Память:** Минимум 16 GB RAM на воркер для OLTP; для OLAP — от 64 GB, чтобы умещать индексы в `shared_buffers`.
- **CPU:** Минимум 4 ядра на воркер; для аналитических нагрузок — от 8 ядер.

### Программное обеспечение

- **ОС:** Linux (RHEL 9+/Ubuntu 22.04+). Поддержка systemd обязательна.
- **PostgreSQL:** Версия 18.x для Citus 14.x.
- **Пакет:** `postgresql-18-citus-14.x` (версия может отличаться в зависимости от дистрибутива).

### Сетевая инфраструктура

- Открытые порты: **5432** (PostgreSQL) между всеми узлами кластера.
- Разрешение прямых соединений в обе стороны: координатор → воркеры, воркеры → координатор.
- DNS или статические IP-адреса для всех узлов.
- Отключение `transparent_huge_pages` (THP) на всех узлах для снижения задержек.

```bash
# Проверка transparent_huge_pages
cat /sys/kernel/mm/transparent_hugepage/enabled
# Должно быть: [never]
```

### Системные лимиты

```bash
# Рекомендуемые значения в /etc/security/limits.conf
postgres  soft  nofile  65536
postgres  hard  nofile  65536

# sysctl.conf
fs.file-max = 2097152
net.core.somaxconn = 4096
net.ipv4.tcp_syncookies = 0
vm.overcommit_memory = 0
```

## Установка и настройка

### Шаг 1: Установка расширения

На каждом узле (координатор и воркеры) установите пакет Citus:

```bash
# Для Ubuntu/Debian
curl https://install.citusdata.com/community/deb.sh | sudo bash
sudo apt-get install -y postgresql-18-citus-14.2

# Для RHEL/CentOS
sudo yum install -y https://install.citusdata.com/community/rpm.sh
sudo yum install -y postgresql-18-citus-14.2
```

### Шаг 2: Настройка PostgreSQL

В файле `postgresql.conf` на всех узлах добавьте Citus в предварительную загрузку библиотек:

```ini
# postgresql.conf
shared_preload_libraries = 'citus'
```

**Критические параметры для multi-node кластера:**

```ini
# Максимальное количество подготовленных транзакций (2PC)
# Должно быть >= max_connections на каждом воркере
max_prepared_transactions = 200

# Максимальное количество слотов репликации
max_replication_slots = 10

# Максимальное количество сендеров WAL
max_wal_senders = 10

# Размер WAL для репликации (1 GB минимум)
wal_keep_size = 1GB

# Уровень WAL для репликации
wal_level = replica
```

Перезапустите PostgreSQL:
```bash
sudo systemctl restart postgresql
```

### Шаг 3: Инициализация кластера

На **координаторе** выполните настройку узлов:

```sql
-- Регистрация координатора
SELECT citus_set_coordinator_host('coordinator-host', 5432);

-- Добавление воркеров
SELECT citus_add_node('worker-1', 5432);
SELECT citus_add_node('worker-2', 5432);

-- Проверка статуса
SELECT * FROM citus_get_active_worker_nodes();
```

### Шаг 4: Валидация установки

```sql
-- Проверка версии расширения
SELECT citus_version();

-- Проверка активных узлов
SELECT * FROM citus_get_active_worker_nodes();

-- Проверка статуса воркеров
SELECT * FROM citus_nodes;

-- Тестовое создание распределенной таблицы
CREATE TABLE test_dist (id bigserial, tenant_id int, data text);
SELECT create_distributed_table('test_dist', 'tenant_id');

-- Очистка тестовых данных
DROP TABLE test_dist;
```

### Шаг 5: Безопасность

#### pg_hba.conf

Для multi-node кластера настройте аутентификацию:

```ini
# Разрешить replication и md5/scram для всех узлов
host  all             all             10.0.0.0/24            scram-sha-256
host  all             all             10.0.0.0/24            md5

# Для репликации (если используется)
host  replication     replicator      10.0.0.0/24            scram-sha-256
```

#### Шифрование трафика

Используйте SSL для шифрования трафика между координатором и воркерами:

```ini
# postgresql.conf на всех узлах
ssl = on
ssl_cert_file = '/etc/postgresql/ssl/server.crt'
ssl_key_file = '/etc/postgresql/ssl/server.key'
ssl_ca_file = '/etc/postgresql/ssl/ca.crt'
```

```bash
# Проверка SSL-подключения
openssl s_client -connect coordinator-host:5432 -CAfile /etc/postgresql/ssl/ca.crt
```

#### Сетевая изоляция

По умолчанию используйте `deny-all` сетевые политики и явно разрешайте только необходимые соединения между узлами кластера.

## Резервное копирование и восстановление

Поскольку Citus — это расширение PostgreSQL, общая теория бэкапов описана в **[Бэкап и восстановление PostgreSQL](./PostgreSQL/Concepts/backup_and_recovery.md)**. Ниже — особенности распределенного кластера.

### Стратегия бэкапов

Для production кластера требуется:
1.  **Логический бэкап:** Периодический дамп всех данных с помощью `pg_dump` или `pg_dumpall` на координаторе.
2.  **Физический бэкап:** Копия каждого воркера отдельно (PgBaseBackup или файловый снимок).
3.  **Архивация WAL:** На каждом узле для поддержки PITR.

### Логическое резервное копирование

**Важно:** `pg_dump` выполняется только на координаторе и автоматически выгружает данные со всех воркеров.

```bash
# Полный дамп всей базы (с координатора)
pg_dump -h coordinator-host -U backup_user -d citus -F c \
  --compress=zstd:3 -f /backups/citus_full.dump
```

Для бэкапа глобальных объектов (роли, табличные пространства):
```bash
pg_dumpall -h coordinator-host -U backup_user -g > /backups/citus_globals.sql
```

### Физическое резервное копирование

Каждый воркер и координатор должны бэкапироваться независимо:

```bash
# На каждом узле (в т.ч. координатор)
pg_basebackup -h localhost -U replicator \
  -D /var/lib/postgresql/backups/base \
  -P -X stream --checkpoint=fast
```

### Восстановление после сбоя

1.  **Остановите кластер** на всех узлах.
2.  **Восстановите координатор** из бэкапа, накатите WAL до нужной точки.
3.  **Восстановите каждого воркера** отдельно из его бэкапа.
4.  **Проверьте согласованность LSN:** На координаторе выполните:
    ```sql
    SELECT * FROM citus_get_active_worker_nodes();
    ```
5.  **Перерегистрируйте воркеры** (если их адреса изменились):
    ```sql
    SELECT citus_remove_node('old-worker-host', 5432);
    SELECT citus_add_node('new-worker-host', 5432);
    ```

### Валидация бэкапов

Раз в квартал выполняйте восстановление на тестовом кластере:
- Проверяйте, что все таблицы и шарды восстановлены.
- Проверяйте контрольные суммы данных (если включены `data_checksums`).
- Запускайте `ANALYZE` на восстановленных таблицах.

## Высокая доступность (High Availability)

Citus не включает встроенную репликацию воркеров. HA обеспечивается на уровне каждого отдельного PostgreSQL-инстанса (координатора и воркеров) с использованием стандартных инструментов.

### HA с Patroni (рекомендуется)

**Patroni 3.0+** имеет первоклассную поддержку Citus 10.0 и выше. Каждый узел кластера (координатор и воркеры) управляется своим Patroni-инстансом.

**Особенности:**
- При падении координатора Patroni автоматически promotes его реплику.
- После failover координатора может потребоваться обновление метаданных:
  ```sql
  SELECT citus_set_coordinator_host('new-coordinator-host', 5432);
  ```
- Начиная с Citus 11.2, улучшена поддержка плавного переключения (switchover) в Patroni.

### HA без Patroni (ручной)

Можно использовать **repmgr** или классическую streaming replication с ручным failover, но это требует поддержки runbook'ов для каждого сценария.

### Ключевые метрики HA

| Метрика | Запрос | Назначение |
| :--- | :--- | :--- |
| **Replication Lag** | `SELECT * FROM pg_stat_replication;` | Задержка между мастером и репликой |
| **WAL Send Queue** | `pg_size_pretty(pg_wal_lsn_diff(...))` | Объем данных, ожидающих отправки |
| **pg_prepared_xacts** | `SELECT * FROM pg_prepared_xacts;` | Подвисшие распределенные транзакции |

## Мониторинг и observability

### Citus-specific представления

```sql
-- Активные распределенные запросы
SELECT * FROM citus_dist_stat_activity;

-- Состояние узлов
SELECT * FROM citus_nodes;

-- Расположение шардов
SELECT * FROM citus_shards;

-- Статистика по размерам таблиц (включая шарды)
SELECT * FROM citus_table_size('table_name');

-- Размер отношения на воркерах
SELECT * FROM citus_relation_size('table_name');
```

### Мониторинг ребалансировки

```sql
-- Запуск ребалансировки
SELECT citus_rebalance_start();

-- Мониторинг процесса
SELECT * FROM citus_rebalance_status();

-- Отмена ребалансировки
SELECT citus_rebalance_cancel();
```

### Мониторинг данных skew

```sql
-- Распределение шардов по воркерам
SELECT logicalrelid, count(*) 
FROM citus_shards 
GROUP BY logicalrelid;
```

### Интеграция с Prometheus

Используйте стандартный **postgres_exporter** на каждом узле. Ключевые дополнительные метрики:
- `citus_shard_count` — количество шардов на воркере.
- `citus_active_queries` — активные распределенные запросы.
- Размер шардов (`pg_relation_size` для шардных таблиц).

### Алерты

| Алерт | Порог | Действие |
| :--- | :--- | :--- |
| **Data Skew** | Разница утилизации CPU/Disk между воркерами > 30% | Пересмотр ключа дистрибуции, ручная миграция шардов |
| **Connection Exhaustion** | `citus_dist_stat_activity` > 80% от `max_connections` | Масштабирование пула PgBouncer, добавление воркеров |
| **Rebalance Stuck** | `citus_rebalance_status` в состоянии 'running' > 1h | Проверка блокировок, отмена и повтор |
| **Prepared Xacts** | Количество > 0 в течение > 5 мин | Анализ проблемных транзакций, ручная очистка |
| **Replication Lag** | > 10 сек на любом воркере | Проверка дисков и сети на реплике |

## Обслуживание и эксплуатация

### Vacuuming

В распределенной среде `VACUUM` выполняется на каждом воркере отдельно. Citus предоставляет функцию для запуска на всем кластере:

```sql
SELECT run_command_on_all_shards('VACUUM ANALYZE table_name');
```

**Важно:** Начиная с PostgreSQL 17, используйте `VACUUM ONLY parent` для партиционированных таблиц, чтобы избежать автоматической обработки детей.

### Ребалансировка (Online Rebalancing)

При добавлении новых узлов данные перемещаются без блокировок:

```sql
-- Перераспределение шардов на новые узлы
SELECT citus_rebalance_start();

-- Мониторинг процесса
SELECT * FROM citus_rebalance_status();

-- Отмена ребалансировки
SELECT citus_rebalance_cancel();
```

**Рекомендации:**
- Выполняйте ребалансировку в периоды низкой нагрузки.
- Для больших таблиц используйте параметры chunk size.
- Мониторьте `citus_shards` во время процесса.

### Инкрементальные бэкапы (PG 17+)

На каждом узле настройте нативные инкрементальные бэкапы:
```bash
pg_basebackup -D /path/to/backup --incremental=/path/to/full_backup_manifest
```

## Практические сценарии

### SaaS и мультитенантность (Multi-tenancy)

Основной сценарий для Citus. Данные сотен тысяч клиентов (тенантов) распределяются по кластеру.

**Настройка:**
1.  Выберите `tenant_id` как ключ дистрибуции для всех таблиц.
2.  Используйте `create_distributed_table`.
3.  Все запросы должны включать `tenant_id` для работы через **Router Planner**.

```sql
-- Распределение таблицы по tenant_id
SELECT create_distributed_table('orders', 'tenant_id');

-- Запрос, который пойдет на один воркер
SELECT * FROM orders WHERE tenant_id = 500 AND id = 12345;
```

**Index Skip-Scan (PostgreSQL 18):** Позволяет эффективно использовать составные индексы вида `(tenant_id, created_at)`, даже если в запросе не указан `tenant_id`.

### Аналитика в реальном времени

Citus позволяет выполнять агрегации (SUM, AVG, COUNT) параллельно на всех узлах.

- **Fast Ingest:** Поддержка `COPY` и `INSERT` с масштабируемой пропускной способностью. Координатор распараллеливает вставку данных напрямую на воркеры.
- **AIO Support (PostgreSQL 18):** Использование асинхронного I/O из ядра PostgreSQL 18 ускоряет сканирование шардов и фоновые процессы (VACUUM).

### Микросервисы (Schema-based sharding)

Citus 12.0+ поддерживает шардирование по схемам:
- Отдельная схема на каждый микросервис или тенанта.
- Простое подключение через `SET search_path`.
- Меньшая плотность тенантов на узел по сравнению с row-based шардированием.

## Производительность и тюнинг

### Connection Pooling

Обязательное использование **PgBouncer** в режиме транзакций для координатора. Подробнее: **[Настройка PgBouncer для PostgreSQL](./PostgreSQL/Operations/pgbouncer_setup.md)**.

### Управление соединениями координатора

Для координатора настройте PgBouncer в режиме транзакций. Размер пула:
```ini
default_pool_size = 50
max_client_conn = 10000
reserve_pool_size = 5
```

### Производительность 2PC

Двухфазный коммит (2PC) требует минимум 3 синхронных записи в WAL (prepare на воркерах, запись решения на координаторе, commit на воркерах), что увеличивает Latency в 2-4 раза.

**Рекомендации:**
- Избегайте тяжелых распределенных транзакций, затрагивающих много шардов.
- Локализуйте логику на воркерах через функции (UDF).
- Для массовых загрузок данных используйте `synchronous_commit = off` на координаторе (с пониманием риска потери данных при сбое).

### UUIDv7 для первичных ключей

Для первичных ключей в распределенных таблицах используйте `uuidv7()`. Это обеспечивает временную сортировку и снижает фрагментацию индексов при вставке.

## Отладка и устранение неисправностей

### Полезные представления

- `citus_dist_stat_activity`: Активные распределенные запросы.
- `citus_nodes`: Информация о состоянии узлов в кластере.
- `citus_shards`: Список всех шардов и их расположение.
- `pg_prepared_xacts`: Подвисшие распределенные транзакции.
- `pg_stat_activity`: Обычные активные сессии на координаторе.

### Типичные проблемы

1.  **Connection Exhaustion:**
    -   *Причина:* Каждый распределенный запрос может открывать несколько соединений с воркерами.
    -   *Решение:* Использование PgBouncer в режиме транзакций.
2.  **Data Skew (Перекос данных):**
    -   *Причина:* Неудачный выбор ключа дистрибуции, из-за чего один воркер перегружен.
    -   *Решение:* Изучение распределения данных через `citus_shards` и выбор более равномерного ключа (например, UUID).
3.  **Distributed Deadlocks:**
    -   *Причина:* Взаимная блокировка ресурсов на разных воркерах.
    -   *Решение:* Citus имеет встроенный детектор распределенных дедлоков, но рекомендуется избегать тяжелых транзакций, затрагивающих много шардов одновременно.
4.  **Подвисшие распределенные транзакции:**
    -   *Причина:* Координатор упал между фазами 2PC.
    -   *Решение:* Мониторинг `pg_prepared_xacts` и ручная очистка (или автоматика Citus).
5.  **Reshuffling на больших таблицах:**
    -   *Причина:* Сложные JOIN'ы несопоставленных (non-colocated) таблиц.
    -   *Решение:* Использование Reference Tables или денормализация данных.

---

## Ограничения

- **Reshuffling:** Запросы без ключа дистрибуции или сложные JOIN'ы несопоставленных таблиц могут вызывать перемещение данных по сети, что резко снижает производительность.
- **Stored Procedures:** Распределенные процедуры требуют проектирования с учетом сетевых задержек; логика должна быть максимально локализована на воркерах через функции.
- **Глобальные ограничения:** Ограничения NOT NULL, CHECK и FOREIGN KEY поддерживаются только между colocated таблицами.
- **Агрегатные функции:** Некоторые агрегатные функции (например, `array_agg`) могут быть медленными при распределенных данных.

---

## Рекомендации (Best Practices)

- **Используйте uuidv7:** Для первичных ключей в распределенных таблицах.
- **Connection Pooling:** Обязательное использование PgBouncer в режиме транзакций для координатора.
- **Выбирайте ключ дистрибуции тщательно:** Он должен присутствовать в большинстве тяжелых запросов и обеспечивать равномерное распределение.
- **Создавайте reference таблицы** для часто используемых справочных данных.
- **Анализ планов:** Всегда проверяйте `EXPLAIN (VERBOSE)` для распределенных запросов.
- **Мониторинг Skew:** Настройте алерты на отклонение утилизации ресурсов между воркерами более чем на 20-30%.
- **Тестирование отката:** Всегда имейте план возврата к старой схеме шардирования при неудачном решардинге.
- **Резервное копирование:** Настраивайте отдельные бэкапы для каждого воркера и координатора.
- **Изоляция (Cell-based Architecture):** Проектируйте шарды как независимые «ячейки». Сбой в одной ячейке не должен затрагивать работу других.
