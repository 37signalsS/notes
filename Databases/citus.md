# Citus

## Определения

**Citus** — это расширение (extension) для СУБД (Система управления базами данных) PostgreSQL, которое превращает ее в распределенную базу данных. Он позволяет горизонтально масштабировать PostgreSQL, распределяя данные и запросы по кластеру из нескольких серверов.

Ключевая цель — **масштабирование PostgreSQL «наружу» (scale-out)** для обработки больших объемов данных и высоких нагрузок, которые не может выдержать один сервер.

**Текущая версия:** Citus 14.0 (февраль 2026) с поддержкой PostgreSQL 18.

## Основные концепции

### Архитектура

- **Координатор (Coordinator):** один узел, который является точкой входа для приложений. Он хранит метаданные обо всех шардах и управляет распределенным выполнением запросов.
- **Воркеры (Workers):** несколько рабочих узлов, которые хранят фактические данные (шарды) и выполняют фрагменты запросов, полученные от координатора.

### Типы таблиц

Citus расширяет стандартную модель данных PostgreSQL двумя новыми типами таблиц:

1. **Распределенные таблицы (Distributed Tables):**
    - Это большие таблицы, которые разбиваются на **шарды (shards)** и распределяются по воркер-узлам.
    - Разбиение происходит на основе **ключа дистрибуции (distribution key)**. Строки с одинаковым значением ключа дистрибуции всегда попадают на один и тот же шард.
    - Для создания используется функция `create_distributed_table()`.

2. **Таблицы-справочники (Reference Tables):**
    - Это небольшие таблицы (справочники, таблицы измерений), которые **полностью реплицируются на каждый воркер-узел**.
    - Это позволяет эффективно выполнять операцию `JOIN` между распределенными таблицами и таблицами-справочниками локально на каждом воркере, без необходимости передавать данные по сети.
    - Для создания используется функция `create_reference_table()`.

### Работа с индексами и ограничениями

В распределенной среде Citus накладывает специфические требования на индексы и константы целостности:

- **Создание индексов:** индексы создаются на координаторе и автоматически распространяются на все шарды на воркер-узлах.
- **Уникальные индексы:** должны обязательно включать ключ дистрибуции. Это необходимо для того, чтобы проверка уникальности могла быть выполнена локально на одном шарде без межсетевого взаимодействия.
- **Внешние ключи (Foreign Keys):** работают только между таблицами с одинаковым ключом дистрибуции (механизм сопоставления или colocation) или при связи распределенной таблицы с таблицей-справочником.

### Процесс выполнения запроса

Когда приложение отправляет SQL (Structured Query Language) запрос на узел-координатор, происходит следующее:

1. Координатор анализирует запрос.
2. Определяет, какие шарды на каких воркерах необходимо задействовать.
3. Отправляет соответствующие подзапросы на воркеры для параллельного выполнения.
4. Собирает результаты от воркеров и возвращает их клиенту.

## Практические сценарии

- **Мультитенантные приложения:** каждого клиента (tenant) можно изолировать по `tenant_id`, который и будет ключом дистрибуции. Все данные одного клиента будут лежать на одном шарде.
- **Аналитика в реальном времени:** быстрая обработка аналитических запросов над большими объемами данных за счет параллельного выполнения.
- **Хранилища данных (DWH — Data Warehouse):** построение масштабируемых хранилищ на базе PostgreSQL.

## Дополнительная информация

### Преимущества

- **Горизонтальное масштабирование:** позволяет преодолеть ограничения одного сервера PostgreSQL, распределяя данные и нагрузку.
- **Параллельное выполнение запросов:** сложные запросы могут выполняться параллельно на нескольких узлах, что значительно сокращает время их выполнения.
- **Совместимость с PostgreSQL:** сохраняет полную совместимость с экосистемой (типы данных, функции, инструменты), что является преимуществом перед обособленными распределенными БД.

### Ограничения и особенности

- **Сложность ре-шардирования:** перераспределение данных между узлами (re-balancing) — тяжелая операция, требующая планирования ресурсов.
- **Транзакции:** хотя Citus поддерживает распределенные транзакции, их интенсивное использование может влиять на производительность.
