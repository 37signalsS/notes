# Citus: распределенный PostgreSQL

Специфичное для PostgreSQL расширение для горизонтального масштабирования. Общие теоретические основы распределенных систем описаны в разделе **[Шардирование в базах данных](./Concepts/sharding.md)**.

## Определения

**Citus** — это расширение (extension) для СУБД PostgreSQL, которое превращает ее в распределенную базу данных. Citus позволяет горизонтально масштабировать PostgreSQL, распределяя данные и запросы по кластеру из нескольких серверов.

Ключевая цель — **масштабирование PostgreSQL «наружу» (scale-out)** для обработки больших объемов данных (десятки и сотни терабайт) и высоких нагрузок на запись, которые не может выдержать один сервер.

**Текущее состояние (2026):** Citus 14.x является стандартом для распределенных OLTP и Real-time OLAP систем на базе **PostgreSQL 18**. Решение полностью поддерживает нативные фичи PG18, такие как асинхронный ввод-вывод (AIO) и Index Skip-Scan.

## Основные концепции

### Архитектура кластера

- **Координатор (Coordinator):** основной узел, точка входа для приложений. Хранит метаданные о расположении шардов и управляет планированием распределенных запросов. Начиная с Citus 12.0, координатор может сам хранить данные (шарды), что позволяет плавно переходить от одного узла к кластеру.
- **Воркеры (Worker Hosts):** рабочие узлы, хранящие шарды и выполняющие фрагменты запросов. Воркеры могут взаимодействовать друг с другом напрямую для выполнения сложных JOIN'ов.
- **Шарды (Shards):** фрагменты распределенной таблицы. Citus разбивает таблицу на множество шардов (по умолчанию 32), которые равномерно распределяются по воркерам.

### Типы таблиц

Citus расширяет стандартную модель данных тремя типами распределения:

1.  **Распределенные таблицы (Distributed Tables):**
    *   Большие таблицы, шардированные по **ключу дистрибуции** (distribution column).
    *   Создание: `SELECT create_distributed_table('table_name', 'distribution_column');`
    *   *Пример:* таблицы фактов, событий, заказов.

2.  **Таблицы-справочники (Reference Tables):**
    *   Небольшие таблицы, которые реплицируются на каждый узел кластера (включая координатор).
    *   Позволяют выполнять локальные JOIN'ы с распределенными таблицами на любом воркере.
    *   Создание: `SELECT create_reference_table('table_name');`
    *   *Пример:* справочники стран, категорий товаров.

3.  **Локальные таблицы (Local Tables):**
    *   Стандартные таблицы PostgreSQL на координаторе. Не требуют масштабирования.

### Колоночное хранение (Columnar Storage)

Citus поддерживает нативный колоночный формат хранения (Columnar), что критично для аналитических нагрузок:
- **Сжатие:** до 3-10 раз по сравнению с классическим форматом Heap.
- **Производительность:** пропуск чтения ненужных колонок ускоряет OLAP-запросы в разы.
- **Новое в 2026:** Поддержка **Virtual Generated Columns** (виртуальных генерируемых колонок) на распределенных таблицах.

```sql
-- Таблица с колоночным хранением
CREATE TABLE archive_events (...) USING columnar;
```

### Совместное размещение (Colocation)

**Colocation** гарантирует, что строки из разных таблиц с одинаковым значением ключа дистрибуции попадут на один и тот же физический узел.
- Позволяет выполнять высокопроизводительные JOIN'ы без перемещения данных между узлами (reshuffling).
- Обеспечивает работу `FOREIGN KEY` между распределенными таблицами.

### Транзакционность и целостность

- **Распределенные транзакции:** Citus поддерживает атомарность (ACID) для запросов, затрагивающих несколько шардов, используя двухфазный коммит (2PC).
- **Уникальные индексы:** должны включать ключ дистрибуции для обеспечения локальной проверки на уровне шарда.
- **PostgreSQL 18 Integration:** Поддержка **Temporal Constraints** (временных ограничений) в распределенном режиме для аудита данных.

## Практические сценарии

### SaaS и мультитенантность (Multi-tenancy)

Основной сценарий для Citus. Данные сотен тысяч клиентов (тенантов) распределяются по кластеру.
- **Изоляция:** использование `tenant_id` как ключа дистрибуции.
- **Index Skip-Scan (PG18):** Позволяет эффективно использовать составные индексы (где `tenant_id` на первом месте), даже если в запросе не указан идентификатор клиента.
- **Schema-based Sharding:** Новый паттерн для микросервисов, позволяющий распределять целые схемы по узлам.

### Аналитика в реальном времени

Citus позволяет выполнять агрегации (SUM, AVG, COUNT) параллельно на всех узлах.
- **Fast Ingest:** поддержка `COPY` и `INSERT` с масштабируемой пропускной способностью.
- **AIO Support:** Использование асинхронного I/O из ядра PostgreSQL 18 ускоряет сканирование шардов и фоновые процессы (VACUUM).

### Высокая доступность (HA) и эксплуатация

В 2026 году стандартным подходом является использование операторов Kubernetes:
1.  **CloudNativePG (CNPG):** Де-факто стандарт. Управляет каждым узлом Citus (координатором и воркерами) как отдельным отказоустойчивым инстансом с поддержкой инкрементальных бэкапов.
2.  **Patroni:** используется в bare-metal или VM инсталляциях для автоматического failover.

### Ребалансировка (Online Rebalancing)

При расширении кластера данные перемещаются в фоне без блокировок:
```sql
-- Перераспределение шардов на новые узлы
SELECT citus_rebalance_start();
-- Мониторинг через новые системные представления 2026 года
SELECT * FROM citus_nodes;
```

### Рекомендации (Best Practices 2026)

- **Используйте uuidv7:** Для первичных ключей в распределенных таблицах используйте `uuidv7()`. Это обеспечивает временную сортировку и снижает фрагментацию индексов при вставке.
- **Connection Pooling:** Обязательное использование **PgBouncer** (или встроенного пулера в CNPG) в режиме транзакций для координатора.
- **Инкрементальные бэкапы:** Настройте нативные инкрементальные бэкапы (фича PG17+) для всех узлов кластера.

### Ограничения

- **Reshuffling:** запросы без ключа дистрибуции или сложные JOIN'ы несопоставленных (non-colocated) таблиц могут вызывать перемещение данных по сети.
- **Stored Procedures:** Распределенные процедуры требуют проектирования с учетом сетевых задержек.
