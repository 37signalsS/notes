# MongoDB: Репликация

## Определения

**Репликация в MongoDB** — это механизм копирования данных с одного узла на другие для обеспечения отказоустойчивости, избыточности и масштабирования чтения. Основной структурной единицей является **Replica Set**.

*   **Replica Set (Набор реплик):** Группа инстансов `mongod`, хранящих идентичный набор данных.
*   **Primary (Лидер):** Единственный узел, принимающий операции записи. Все изменения фиксируются в Oplog.
*   **Secondary (Вторичный):** Узлы, копирующие Oplog лидера и применяющие изменения локально. Могут участвовать в выборах.
*   **Arbiter (Арбитр):** Узел, который не хранит данные и не может стать Primary. Его единственная задача — участие в голосовании для обеспечения кворума.
*   **Oplog (Operations Log):** Специальная capped-коллекция, хранящая историю всех изменений данных. Является фундаментом логической репликации.
*   **Quorum (Кворум):** Большинство голосующих узлов (`N/2 + 1`), необходимых для выбора Primary и подтверждения записей уровня `majority`.

## Базовые концепции

### Механизмы работы
Репликация в MongoDB основана на **логическом копировании** операций через Oplog. Узлы обмениваются **Heartbeats** (пульсом) каждые 2 секунды. Если Primary недоступен более 10 секунд (по умолчанию), инициируются выборы.

### Типы вторичных узлов (Special Members)
1.  **Priority 0:** Узел не может стать Primary. Используется для резервных копий или в удаленных ЦОД.
2.  **Hidden (Скрытый):** Узел не виден клиентам и не может стать Primary. Идеален для аналитики или создания бэкапов через `mongodump`.
3.  **Delayed (Задержанный):** Узел реплицирует данные с фиксированной задержкой (например, 1 час). Защищает от человеческих ошибок (случайное удаление данных). *Всегда имеет Priority 0.*

### Write Concern (Гарантия записи)
Определяет условия, при которых запись считается успешной для приложения.

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| **`w`** | `majority` (default) | Подтверждение, когда большинство голосующих узлов записали данные в Oplog. |
| **`w: 1`** | `1` | Подтверждение только от Primary. Риск потери при откате (Rollback). |
| **`j`** (journal) | `true` | Дожидаться записи в Journal на диске (гарантия устойчивости к сбою питания). |

### Read Concern (Уровень изоляции)
| Уровень | Гарантия |
| :--- | :--- |
| **`local`** | Возвращает последние данные с узла без гарантии их выживания при сплит-брейне. |
| **`majority`** | Гарантирует, что прочитанные данные уже подтверждены большинством и не будут откачены. |
| **`snapshot`** | Используется в многодокументных транзакциях для обеспечения согласованности снимка. |

## Практические сценарии

### 1. Развертывание Replica Set (v8.0+)
Инициализация кластера из трех узлов через `mongosh`:

```javascript
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "mongo-1:27017", priority: 2 }, // Предпочтительный лидер
    { _id: 1, host: "mongo-2:27017", priority: 1 },
    { _id: 2, host: "mongo-3:27017", arbiterOnly: true } // Арбитр для кворума
  ]
})
```

### 2. Добавление скрытого узла для аналитики
```javascript
rs.add({
  host: "mongo-analytics:27017",
  priority: 0,
  hidden: true
})
```

### 3. Мониторинг состояния
```javascript
rs.status() // Подробный отчет о лаге, статусе узлов и выборах
rs.printSecondaryReplicationInfo() // Краткая сводка по задержкам (Replica Lag)
```

## Устранение неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **`NotPrimaryNoSecondaryOk`** | Клиент пытается писать на Secondary или нет лидера. | Проверить `rs.status()`. Убедиться, что клиент использует правильную строку подключения с `replicaSet=...`. |
| **Высокий Replica Lag** | Нехватка пропускной способности сети или ресурсов CPU/Disk на Secondary. | Проверить мониторинг ресурсов. Увеличить `oplogSize`, чтобы избежать переполнения до завершения синхронизации. |
| **Бесконечные выборы** | Нестабильная сеть (Flapping) или отсутствие кворума. | Проверить доступность узлов. Убедиться, что количество голосующих узлов нечетное. |
| **Rollback (Откат)** | Primary упал, не успев реплицировать данные, подтвержденные с `w: 1`. | Использовать `w: "majority"`. Файлы отката сохраняются в `data/rollback/`, их нужно анализировать вручную. |

## Лучшие практики (Best Practices 2026)

*   **Используйте `majority`:** В MongoDB 8.0 это значение по умолчанию, не снижайте его без крайней необходимости.
*   **Следите за Oplog Window:** Размер Oplog должен позволять Secondary находиться в офлайне (например, для обслуживания) не менее 24 часов.
*   **Гео-распределение:** Размещайте узлы в разных зонах доступности. Используйте `priority` для контроля, какой регион должен быть основным.
*   **Минимальное количество:** Для полноценной работы всегда используйте минимум 3 узла данных. Арбитры — это крайняя мера для экономии ресурсов.
