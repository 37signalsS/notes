# MongoDB: Моделирование данных и валидация

**Актуально для:** MongoDB 8.0.x

---

## Определения

**Моделирование данных в MongoDB** — это процесс проектирования структуры документов и связей между ними, ориентированный на **шаблоны доступа приложения** (Application Access Patterns). В отличие от реляционных БД, где нормализация является стандартом, в MongoDB первичной целью является **локальность данных** (Data Locality) для минимизации количества операций ввода-вывода.

*   **Dynamic Schema (Гибкая схема):** Возможность хранения документов с разными наборами полей в одной коллекции.
*   **Локальность данных:** Объединение связанных данных в одном документе для исключения дорогостоящих JOIN-операций.
*   **JSON Schema Validation:** Механизм принудительного соблюдения структуры данных на уровне СУБД для обеспечения целостности без потери гибкости.
*   **BSON Document Limit:** Максимальный размер одного документа — **16 МБ**. Превышение лимита приводит к ошибке записи и требует перехода на модель ссылок или GridFS.
*   **Write Amplification:** При денормализации каждое обновление вложенного документа требует перезаписи всего родительского документа, что увеличивает нагрузку на диск и WiredTiger Cache.
*   **Schema Drift:** Непреднамеренное отклонение реальной структуры документов от задуманной схемы во время развития приложения.

## Архитектура и основные принципы

### Почему документная модель

MongoDB оптимизирована для сценариев, где приложение читает связанные данные единым запросом. В реляционных БД нормализация уменьшает дублирование, но увеличивает количество JOIN-ов. В MongoDB инженерный выбор смещается в сторону **Locality over Normalization**.

### Влияние модели данных на производительность (SRE)

*   **Cache Pressure:** Большие вложенные документы (>8 КБ) увеличивают объем WiredTiger Cache, необходимый для хранения Working Set. При превышении `cacheSizeGB` происходит Cache Eviction и рост latency.
*   **Write Path:** При обновлении поля внутри вложенного документа MongoDB перезаписывает весь BSON-документ. Это называется **Whole-Document Rewrite**. Для Write-heavy нагрузок глубокое вложение может стать узким местом.
*   **Read Path:** Вложенные данные читаются за один disk seek. Ссылки требуют минимум двух seek (основной документ + `$lookup` или второй запрос).
*   **Backup/Restore Impact:** Денормализованные данные создают крупные BSON-блоки. Логический бэкап (`mongodump`) на больших вложенных документах работает медленнее и создает более объемные файлы, чем на нормализованной структуре.

### Ограничения формата BSON

| Параметр | Значение | Следствие для SRE |
| :--- | :--- | :--- |
| Максимальный размер документа | 16 МБ | Мониторить `Object.bsonsize()` для коллекций с массивами. |
| Максимальная глубина вложенности | 100 уровней | На практике не превышать 3-5 уровней. |
| Максимальный размер поля-массива | 16 МБ | Бесконечные массивы (логи, события) выносить в отдельную коллекцию. |
| Имя поля | Не может содержать `$` или `.` | Валидировать на уровне приложения или через JSON Schema. |

## Паттерны моделирования

### 1. Вложенность vs. Ссылки (Embedding vs. Referencing)

Решение о способе связи данных — ключевой этап проектирования.

| Метод | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Вложенность (Embedding)** | Связанные данные хранятся внутри родительского документа как подобъекты или массивы. | Связи «1-к-1» или «1-ко-многим», где дочерние данные всегда читаются вместе с родительскими. |
| **Ссылки (Referencing)** | Хранение `ObjectId` (или другого ключа) связанного документа из другой коллекции. | Связи «многие-ко-многим», данные часто меняются независимо, или риск превышения лимита 16 МБ. |

**Золотое правило:** *Моделируйте данные так, чтобы один запрос к БД возвращал все необходимые приложению данные для текущего экрана/функции.*

### 2. Продвинутые паттерны моделирования

*   **Extended Reference Pattern (Расширенная ссылка):** Вместо простого `ObjectId`, мы копируем (денормализуем) несколько полей, которые нужны чаще всего (например, имя пользователя в документе заказа), чтобы избежать `$lookup`.
*   **Attribute Pattern (Атрибуты):** Использование массива объектов `{ k: "attr_name", v: "value" }` для поиска по множеству разнородных характеристик (например, параметры товаров: цвет, размер, мощность). Позволяет создать один индекс по `k` и `v`.
*   **Outlier Pattern (Исключения):** Если у 99% документов массив связанных данных мал, а у 1% огромен (например, подписчики инфлюенсеров), "лишние" данные выносятся в отдельную коллекцию, а в основном документе ставится флаг `has_more`.
*   **Schema Versioning Pattern (Версионирование):** Добавление поля `schema_version` в каждый документ. Позволяет приложению поддерживать старые и новые структуры одновременно, проводя миграцию данных "лениво" при обновлении документов.
*   **Computed Pattern (Вычисляемые данные):** Хранение результатов частых агрегаций (сумма заказа, количество комментариев) непосредственно в документе, обновляя их при записи.

### 3. Миграция схемы в масштабе (Schema Migration at Scale)

Изменение схемы на больших коллекциях (миллионы/миллиарды документов) требует специального подхода, чтобы избежать простоя и блокировок. Общая теория миграций: **[Миграции баз данных](../Concepts/migrations/migration_basics.md)**, **[Expand-Contract](../Concepts/migrations/expand_contract.md)**.

**Стратегия Expand-Contract (двухфазная миграция):**

```
Фаза 1: EXPAND (расширение)
├─ Добавить новое поле/коллекцию (не удаляя старое)
├─ Приложение пишет в оба места (dual-write) или только в новое
└─ Мигрировать исторические данные фоновым процессом

Фаза 2: CONTRACT (сжатие)
├─ Приложение переключается на новую схему
├─ Удалить старое поле/коллекцию
└─ Очистить миграционный код
```

**Фоновая миграция данных (без простоя):**
```javascript
// Миграция поля: вложенное → верхний уровень (пакетами)
const batchSize = 1000;
let migrated = 0;

while (true) {
  const batch = db.users.find({
    "profile.email": { $exists: true },
    "email": { $exists: false }  // ещё не мигрированы
  }).limit(batchSize);

  if (batch.hasNext() === false) break;

  const ops = [];
  for (const doc of batch) {
    ops.push({
      updateOne: {
        filter: { _id: doc._id },
        update: {
          $set: { email: doc.profile.email },
          $unset: { "profile.email": "" }
        }
      }
    });
  }
  db.users.bulkWrite(ops, { ordered: false });
  migrated += ops.length;
  print(`Migrated ${migrated} documents`);
}
```

**Миграция через агрегационный пайплайн (MongoDB 4.2+):**
```javascript
// Сложное преобразование на стороне сервера (без выгрузки в приложение)
db.users.updateMany(
  { "legacy_data": { $exists: true } },
  [
    { $set: {
        new_field: "$legacy_data.value",
        created_at: { $toDate: "$legacy_data.timestamp" }
    }},
    { $unset: "legacy_data" }
  ]
);
```

**Best Practices для миграции в масштабе:**
1.  **Пакетами (batch):** `updateMany`/`bulkWrite` по 1000–10000 документов, чтобы не блокировать кластер.
2.  **`ordered: false`:** продолжать при ошибках (дубликаты, конфликты).
3.  **Индекс на фильтре миграции:** создайте индекс по полю, используемому в `$match` миграции.
4.  **Мониторинг:** `db.currentOp()` во время миграции; следите за replication lag.
5.  **Maintenance window:** для очень больших миграций (TB) — в окно обслуживания.
6.  **Schema Versioning:** добавьте `schema_version` в документ до миграции (см. паттерн выше).
7.  **Тестирование:** сначала на копии данных (тестовый кластер).
8.  **Откат:** сохраните старое поле до подтверждения успешной миграции (Expand-Contract).

**Онлайн-миграция между кластерами:** см. **[Импорт/экспорт](./mongodb-import-export.md)** (mongodump/mongorestore, Change Streams).

### 4. Миграция с MapReduce на Aggregation

**MapReduce устарел.** Начиная с MongoDB 5.0, MapReduce deprecated; в 8.0 он по-прежнему доступен, но **не рекомендуется** к использованию. Замена — Aggregation Pipeline, который:
*   Быстрее (нативный C++ код, оптимизатор планов).
*   Поддерживает индексы (`$match`, `$sort` early).
*   Поддерживает `allowDiskUse` для больших наборов.
*   Поддерживает `out`/`merge` для записи результатов.

**Сравнение:**

| Аспект | MapReduce | Aggregation |
| :--- | :--- | :--- |
| Производительность | Медленнее (JS-движок) | Быстрее (нативный) |
| Индексы | Не использует | Использует (`$match`, `$sort`) |
| Сложность | Гибкий (произвольный JS) | Ограничен операторами |
| Статус | Deprecated (5.0+) | Рекомендуемый |
| `out`/`merge` | `out` | `$out`/`$merge` |

**Миграция MapReduce → Aggregation:**

```javascript
// === MapReduce (старый подход, deprecated) ===
db.orders.mapReduce(
  function() { emit(this.customer_id, this.amount); },
  function(key, values) { return Array.sum(values); },
  { out: "customer_totals_mr" }
)

// === Aggregation (новый подход) ===
db.orders.aggregate([
  { $group: { _id: "$customer_id", total: { $sum: "$amount" } } },
  { $out: "customer_totals" }  // или $merge для инкрементального обновления
])
```

**Типичные преобразования:**

| MapReduce | Aggregation |
| :--- | :--- |
| `emit(key, value)` | `$group: { _id: key, ... }` |
| `reduce(key, values)` | `$group` с аккумуляторами (`$sum`, `$avg`, `$push`) |
| `finalize(key, value)` | `$project` / `$addFields` после `$group` |
| `query: {...}` | `$match` (первая стадия) |
| `sort: {...}` | `$sort` |
| `limit: N` | `$limit` |
| `out: "collection"` | `$out: "collection"` |
| — | `$merge` (инкрементальный, обновляет существующие) |

**`$merge` vs `$out`:**
*   `$out` — заменяет всю коллекцию (атомарно).
*   `$merge` — инкрементально обновляет/вставляет (для регулярных отчётов).

**Когда MapReduce всё ещё нужен:** только для кастомной логики, невозможной в Aggregation (редкие случаи). В остальных случаях — Aggregation.

См. также: **[Агрегация](./mongodb-aggregation.md)** — полный справочник по пайплайну.

## Валидация схем (JSON Schema)

С версии 3.6 MongoDB поддерживает валидацию на базе стандарта **JSON Schema (Draft 4)**.

### Уровни валидации

1.  **`strict`** (по умолчанию): Проверяются все операции вставки и обновления.
2.  **`moderate`**: Проверяются вставки и обновления только тех документов, которые уже соответствовали схеме (позволяет постепенно очищать "грязные" данные).

### MongoDB 8.0: Улучшенная диагностика

В версии 8.0 значительно улучшена отладка валидации. При ошибке сервер возвращает детальный объект `errInfo`, который точно указывает на нарушенное правило (например, `minimum`, `maxLength` или несоответствие `pattern`).

### Создание коллекции с валидацией

```javascript
db.createCollection("products", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "price", "category", "sku"],
      properties: {
        name: { bsonType: "string", minLength: 3 },
        price: { bsonType: "decimal", minimum: 0 },
        sku: {
          bsonType: "string",
          pattern: "^[A-Z]{3}-[0-9]{5}$",
          description: "Формат: ABC-12345"
        },
        category: { enum: ["electronics", "home", "garden"] },
        tags: {
          bsonType: "array",
          items: { bsonType: "string" }
        }
      }
    }
  },
  validationAction: "error"
})
```

**Валидация:**
```javascript
// Проверка активных правил валидации
db.getCollectionInfos({ name: "products" })
// # → ищем поле "options" → "validator"

// Проверка успешного создания
db.products.insertOne({ name: "Widget", price: 10.0, category: "electronics", sku: "ABC-12345", tags: ["new"] })
// # → acknowledged: true

// Проверка отклонения невалидного документа
db.products.insertOne({ name: "AB", price: -1, category: "electronics", sku: "ABC-12345" })
// # → MongoError: Document failed validation
```

### Полиморфные коллекции

Если в одной коллекции хранятся разные типы документов (например, `orders` и `returns`), можно использовать `$or` в валидаторе:

```javascript
db.createCollection("events", {
  validator: {
    $or: [
      { $jsonSchema: { required: ["order_id", "items"], properties: { order_id: { bsonType: "string" } } } },
      { $jsonSchema: { required: ["return_id", "reason"], properties: { return_id: { bsonType: "string" } } } }
    ]
  }
})
```

**Валидация:**
```javascript
db.events.insertOne({ order_id: "ORD-001", items: [{ sku: "ABC-12345", qty: 2 }] })
// # → acknowledged: true

db.events.insertOne({ return_id: "RET-001", reason: "damaged" })
// # → acknowledged: true
```

## Практические сценарии

### 1. Эволюция схемы (Schema Migration)

MongoDB не требует предварительного описания схемы, но в production это становится проблемой. Рекомендуемый подход — версионирование с миграцией "ленивым" потоком.

```javascript
// Шаг 1: Добавляем schema_version
db.products.updateMany(
  { schema_version: { $exists: false } },
  [{ $set: { schema_version: 1 } }]
)
// # → acknowledged: true, modifiedCount: N

// Шаг 2: Проверяем распределение версий
db.products.aggregate([
  { $group: { _id: "$schema_version", count: { $sum: 1 } } }
])
// # → [{ _id: 1, count: 1500 }, { _id: null, count: 50 }]

// Шаг 3: Миграция документов версии 1 → 2
db.products.updateMany(
  { schema_version: 1 },
  [
    { $set: { "pricing.currency": "USD", schema_version: 2 } },
    { $unset: "legacy_price" }
  ]
)
// # → acknowledged: true, modifiedCount: 1500
```

### 2. Контроль размера документа

```javascript
// Проверка размера конкретного документа
db.users.findOne({ _id: ObjectId("...") })
Object.bsonsize(db.users.findOne({ _id: ObjectId("...") }))
// # → 4096 (размер в байтах)

// Поиск документов, приближающихся к 16 МБ
db.collection.find({ $where: "Object.bsonsize(this) > 14000000" }).count()
// # → количество документов >14 МБ
```

### 3. Очистка неиспользуемых вложенных данных

```javascript
// Удаление устаревшего поля у всех документов
db.users.updateMany(
  { "old_field": { $exists: true } },
  { $unset: { "old_field": "" } }
)
// # → acknowledged: true, modifiedCount: N
```

## Операции и команды

### Мониторинг здоровья схемы

```javascript
// Статистика по типам полей в коллекции
db.collection.aggregate([
  { $project: { fields: { $objectToArray: "$$ROOT" } } },
  { $unwind: "$fields" },
  { $group: { _id: "$fields.k", count: { $sum: 1 } } }
])
// # → распределение полей по документам

// Поиск документов с неожиданными полями (Schema Drift)
db.collection.find({ $nor: [{ name: { $exists: true } }, { title: { $exists: true } }] }).limit(10)
// # → документы, у которых нет ни name, ни title
```

### Валидация изменений без применения

```javascript
// Предпросмотр результата валидации (MongoDB 8.0+)
db.runCommand({
  validate: "collection",
  full: true
})
// # → документ с ошибками валидации и их описанием
```

## Ограничения и Edge Cases

*   **Unbound Arrays (Бесконечные массивы):** Избегайте вложенных массивов, которые могут расти бесконечно (например, логи в документе пользователя). Это приведет к деградации производительности и достижению лимита 16 МБ. *Решение: Выносите в отдельную коллекцию.*
*   **Deep Embedding (Глубокая вложенность):** Максимальный уровень вложенности BSON — 100 уровней, но на практике рекомендуется не превышать 3-5 уровней для сохранения читаемости и производительности индексов.
*   **Write Penalty (Штраф при записи):** Валидация и денормализация замедляют запись. Если приложение ориентировано на Write-heavy нагрузку, упрощайте схему и переносите валидацию на уровень приложения.
*   **Transaction Overhead:** Транзакции в MongoDB не решают проблему плохого моделирования. Использование транзакций для атомарности при обновлении двух коллекций вместо Embedding — временное решение, которое увеличивает latency и риск блокировок.
*   **Index Intersection:** Сложные вложенные объекты требуют много индексов. Если количество индексов приближается к 64, пересмотрите модель.

## Устранение неполадок

| Проблема | Возможная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **`Document failed validation`** | Поле не соответствует типу или отсутствует обязательное поле. | `db.getCollectionInfos({ name: "collection" })`, `errInfo` | Проверить конкретное правило в `errInfo`. Исправить тип или добавить поле. |
| **Медленный $lookup** | Отсутствие индексов на полях связи или большой вложенный документ. | `explain("executionStats")` | Создать индекс на внешнем ключе. Рассмотреть Extended Reference Pattern. |
| **Размер документа > 16MB** | Чрезмерное использование Embedding для больших данных. | `Object.bsonsize(db.coll.findOne())` | Перейти на Referencing или GridFS. |
| **Schema Drift** | Отсутствие валидации или приложение пишет поля, не описанные в схеме. | `db.collection.aggregate([ { $project: { keys: { $objectToArray: "$$ROOT" } } }, { $unwind: "$keys" }, { $group: { _id: "$keys.k" } } ])` | Добавить JSON Schema валидатор. |
| **Высокий WiredTiger Dirty Cache** | Частые обновления больших вложенных документов. | `db.serverStatus().wiredTiger.cache` | Уменьшить размер документа или снизить частоту обновлений. |
| **Таймаут транзакций** | Моделирование требует обновления многих документов. | `db.currentOp()` | Пересмотреть модель: вынести данные в один документ или использовать Bulk Write. |

## Лучшие практики (SRE)

1.  **Data Locality > Normalization:** Встраивайте данные, которые читаются вместе. Это уменьшает количество запросов и повышает cache hit ratio.
2.  **Validation в Production — по умолчанию:** JSON Schema валидация не влияет критично на производительность, но предотвращает Schema Drift. Начинайте с `strict`, переключайтесь на `moderate` только при миграции.
3.  **Schema Versioning — обязателен:** Даже в NoSQL храните `schema_version`. Это упрощает откат и постановку фичей под флагами.
4.  **Ограничьте размер документа до 1 МБ:** 16 МБ — технический лимит, но практический порог для комфортной работы — **1-2 МБ**. Большие документы замедляют сетевую передачу и увеличивают время сериализации.
5.  **Избегайте Whole-Document Rewrite для больших документов:** Если часто обновляется одно поле внутри большого вложенного документа — вынесите это поле на верхний уровень или в отдельную коллекцию.
6.  **Используйте Partial Index вместо Sparse:** В индексах, связанных с валидацией, `partialFilterExpression` дает более предсказуемый план запроса.
7.  **Планируйте миграции через `updateMany` с пайплайном:** Агрегационные пайплайны в `updateMany` (MongoDB 4.2+) позволяют делать сложные преобразования на стороне сервера без выгрузки данных в приложение.
8.  **Мониторьте Schema Drift:** Периодически (раз в неделю) проверяйте, нет ли в коллекции документов с неожиданными полями. Это признак отсутствия валидации.
