# MongoDB: Моделирование данных и валидация

## Определения

**Моделирование данных в MongoDB** — это процесс проектирования структуры документов и связей между ними, ориентированный на **шаблоны доступа приложения** (Application Access Patterns). В отличие от реляционных БД, где нормализация является стандартом, в MongoDB первичной целью является **локальность данных** (Data Locality) для минимизации количества операций ввода-вывода.

*   **Dynamic Schema (Гибкая схема):** Возможность хранения документов с разными наборами полей в одной коллекции.
*   **Локальность данных:** Объединение связанных данных в одном документе для исключения дорогостоящих JOIN-операций.
*   **JSON Schema Validation:** Механизм принудительного соблюдения структуры данных на уровне СУБД для обеспечения целостности без потери гибкости.

## Базовые концепции моделирования

### 1. Вложенность vs. Ссылки (Embedding vs. Referencing)

Решение о способе связи данных — ключевой этап проектирования.

| Метод | Описание | Когда использовать |
| :--- | :--- | :--- |
| **Вложенность (Embedding)** | Связанные данные хранятся внутри родительского документа как подобъекты или массивы. | Связи «1-к-1» или «1-ко-многим», где дочерние данные всегда читаются вместе с родительскими. |
| **Ссылки (Referencing)** | Хранение `ObjectId` (или другого ключа) связанного документа из другой коллекции. | Связи «многие-ко-многим», данные часто меняются независимо, или риск превышения лимита 16 МБ. |

**Золотое правило:** *Моделируйте данные так, чтобы один запрос к БД возвращал все необходимые приложению данные для текущего экрана/функции.*

### 2. Продвинутые паттерны моделирования

*   **Extended Reference Pattern (Расширенная ссылка):** Вместо простого `ObjectId`, мы копируем (денормализуем) несколько полей, которые нужны чаще всего (например, имя пользователя в документе заказа), чтобы избежать `$lookup`.
*   **Attribute Pattern (Атрибуты):** Использование массива объектов `{ k: "attr_name", v: "value" }` для поиска по множеству разнородных характеристик (например, параметры товаров: цвет, размер, мощность). Позволяет создать один индекс по `k` и `v`.
*   **Outlier Pattern (Исключения):** Если у 99% документов массив связанных данных мал, а у 1% огромен (например, подписчики инфлюенсеров), "лишние" данные выносятся в отдельную коллекцию, а в основном документе ставится флаг `has_more`.
*   **Schema Versioning Pattern (Версионирование):** Добавление поля `schema_version` в каждый документ. Позволяет приложению поддерживать старые и новые структуры одновременно, проводя миграцию данных "лениво" при обновлении документов.
*   **Computed Pattern (Вычисляемые данные):** Хранение результатов частых агрегаций (сумма заказа, количество комментариев) непосредственно в документе, обновляя их при записи.

## Валидация схем (JSON Schema)

С версии 3.6 MongoDB поддерживает валидацию на базе стандарта **JSON Schema (Draft 4)**.

### MongoDB 8.0: Улучшенная диагностика
В версии 8.0 значительно улучшена отладка валидации. При ошибке сервер возвращает детальный объект `errInfo`, который точно указывает на нарушенное правило (например, `minimum`, `maxLength` или несоответствие `pattern`).

### Уровни валидации

1.  **`strict`** (по умолчанию): Проверяются все операции вставки и обновления.
2.  **`moderate`**: Проверяются вставки и обновления только тех документов, которые уже соответствовали схеме (позволяет постепенно очищать "грязные" данные).

## Практические сценарии

### 1. Создание коллекции с комплексной валидацией
Пример для коллекции `products` с использованием типов BSON и регулярных выражений:

```javascript
db.createCollection("products", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["name", "price", "category", "sku"],
      properties: {
        name: { bsonType: "string", minLength: 3 },
        price: { bsonType: "decimal", minimum: 0 },
        sku: { 
          bsonType: "string", 
          pattern: "^[A-Z]{3}-[0-9]{5}$",
          description: "Формат: ABC-12345"
        },
        category: { enum: ["electronics", "home", "garden"] },
        tags: {
          bsonType: "array",
          items: { bsonType: "string" }
        }
      }
    }
  },
  validationAction: "error"
})
```

### 2. Реализация Polymorphic Schema
Если в одной коллекции хранятся разные типы документов (например, `orders` и `returns`), можно использовать `$or` в валидаторе:

```javascript
validator: {
  $or: [
    { $jsonSchema: { required: ["order_id", "items"] } },
    { $jsonSchema: { required: ["return_id", "reason"] } }
  ]
}
```

## Ограничения и Edge Cases

*   **Unbound Arrays (Бесконечные массивы):** Избегайте вложенных массивов, которые могут расти бесконечно (например, логи в документе пользователя). Это приведет к деградации производительности и достижению лимита 16 МБ. *Решение: Выносите в отдельную коллекцию.*
*   **Deep Embedding (Глубокая вложенность):** Максимальный уровень вложенности BSON — 100 уровней, но на практике рекомендуется не превышать 3-5 уровней для сохранения читаемости и производительности индексов.
*   **Write Penalty (Штраф при записи):** Валидация и денормализация замедляют запись. Если приложение ориентировано на Write-heavy нагрузку, упрощайте схему и переносите валидацию на уровень приложения.

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **`Document failed validation`** | Поле не соответствует типу или отсутствует обязательное поле. | В MongoDB 8.0+ проверьте поле `errInfo` в ответе сервера. Оно покажет конкретный `operatorName`. |
| **Медленный $lookup** | Отсутствие индексов на полях связи. | Создайте индекс на внешнем ключе в дочерней коллекции и на `_id` в родительской. |
| **Размер документа > 16MB** | Чрезмерное использование Embedding для больших данных. | Проверьте размер через `Object.bsonsize(db.coll.findOne())`. Используйте Referencing или GridFS. |
