# MongoDB: Шардирование

## Определения

**Шардирование (Sharding)** — это метод горизонтального масштабирования (Scale-Out), при котором данные распределяются по нескольким физическим узлам или Replica Sets, называемым **шардами**. В отличие от репликации, шардирование позволяет увеличивать не только отказоустойчивость, но и общую пропускную способность записи и объем хранимых данных.

*   **Shard (Шард):** Узел, содержащий часть данных кластера. В Production-средах каждый шард обязан быть Replica Set.
*   **Config Servers:** Специальная Replica Set, хранящая метаданные кластера (информацию о распределении чанков по шардам).
*   **Mongos (Маршрутизатор):** Прокси-слой, который принимает запросы от приложения, определяет местоположение данных через Config Servers и направляет запрос на нужный шард.
*   **Chunk (Чанк):** Непрерывный диапазон данных внутри коллекции, распределяемый по шардам. Размер по умолчанию в версии 8.0 — 128 МБ.
*   **Balancer (Балансировщик):** Фоновый процесс, который перемещает чанки между шардами для обеспечения равномерного распределения данных.

Подробная теория общих принципов: **[Шардирование в БД](../Concepts/sharding.md)**.

## Архитектура и механизмы

### Маршрутизация запросов
1.  **Targeted Query (Целевой запрос):** Содержит ключ шардирования. `mongos` направляет его на один конкретный шард. Самый эффективный метод.
2.  **Scatter-Gather (Широковещательный):** Не содержит ключа шардирования. `mongos` опрашивает все шарды и собирает результат. Крайне неэффективно для больших кластеров.

### Выбор ключа шардирования (Shard Key)
Выбор ключа — необратимая (до версии 5.0) или дорогостоящая операция. Критерии:
*   **Кардинальность:** Количество уникальных значений ключа должно быть высоким. Поле `boolean` — плохой выбор.
*   **Частота (Frequency):** Значения ключа должны быть распределены равномерно. Если 90% запросов идут по одному значению, возникнет "горячий шард".
*   **Направление роста:** Монотонно растущие ключи (например, `ObjectId` или `Timestamp`) при Ranged-шардировании создают нагрузку только на последний шард. Используйте **Hashed Sharding** для таких случаев.

## Продвинутые возможности v8.0+

### Resharding (Живой решардинг)
С версии 5.0+ MongoDB позволяет изменить ключ шардирования коллекции без остановки приложения. Процесс создает временную индексацию, копирует данные в новом порядке и переключает маршрутизацию. Требует двойного объема дискового пространства на время операции.

### Refining Shard Key (Уточнение ключа)
Позволяет добавить новые поля к существующему ключу шардирования для увеличения его кардинальности без полной перезаписи данных.

### Zone Sharding (Зонирование)
Позволяет привязывать диапазоны ключа шардирования к конкретным шардам.
*   **Tiered Storage:** "Горячие" данные на шардах с NVMe, "холодные" на дешевых HDD.
*   **Geospatial:** Данные европейских пользователей хранятся на шардах в Европе (соответствие GDPR).

## Практические сценарии

### 1. Включение шардирования и распределение коллекции
```javascript
// Подключение к mongos
// 1. Включение шардирования для БД
sh.enableSharding("shop_db")

// 2. Шардирование коллекции по хешированному ключу (для равномерной записи)
sh.shardCollection("shop_db.orders", { _id: "hashed" })

// 3. Шардирование по диапазону (для эффективных выборок по времени)
sh.shardCollection("shop_db.logs", { timestamp: 1 })
```

### 2. Управление балансировщиком
```javascript
sh.stopBalancer() // Остановка для проведения ТО
sh.startBalancer()
sh.getBalancerStatus() // Проверка активности перемещения чанков
```

## Устранение неполадок

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Jumbo Chunks** | Диапазон ключа содержит слишком много документов с одним значением, чанк нельзя разбить. | Уточнить ключ шардирования (`refineCollectionShardKey`), добавив поле с высокой кардинальностью. |
| **Balancer Lock** | Балансировщик завис или не может переместить чанки из-за долгой фиксации. | Проверить `db.locks.find()` в базе `config`. Проверить Replica Lag на шардах. |
| **Hot Shard (Перекос)** | Неудачный выбор ключа шардирования. | Выполнить `reshardCollection` с новым, более сбалансированным ключом. |
| **Высокий Latency на Mongos** | Большое количество Scatter-Gather запросов. | Оптимизировать индексы и убедиться, что приложение всегда передает Shard Key в фильтрах запроса. |

## Лучшие практики (Best Practices 2026)

*   **Всегда используйте Replica Set для шардов.** Одиночные инстансы запрещены в Production.
*   **Shard Key во всех запросах:** Убедитесь, что `find`, `update` и `delete` содержат ключ шардирования, чтобы `mongos` мог выполнить Targeted Query.
*   **Мониторинг Config Servers:** Их доступность критична для работы всего кластера.
*   **Hashed vs Ranged:** Используйте Hashed для равномерности, Ranged — только если вам жизненно необходимы Range-запросы по этому ключу.
