# Решардинг в MongoDB (Live Resharding)

**Актуально для:** MongoDB 5.0+ (Live Resharding), MongoDB 8.0+ (forceRedistribution, numSamplesPerChunk, Time Series resharding 8.0.10)

---

## Определения

*   **Решардинг (Resharding)** — процесс изменения ключа шардирования (shard key) для существующей коллекции без остановки записи (Live Resharding). Доступен с MongoDB 5.0; в 8.0 процесс оптимизирован и работает до 50 раз быстрее за счёт чтения данных в natural order.
*   **Donor Shard (Донор)** — шард, который отдает данные в процессе решардинга. После завершения процесса Донор удаляет старую версию коллекции.
*   **Recipient Shard (Приёмник)** — шард, который принимает данные согласно новому ключу шардирования. Создаёт временную пустую шардированную коллекцию-копию для записи новых данных.
*   **Resharding Coordinator (Координатор)** — Config Server Primary, управляющий всеми фазами процесса решардинга.
*   **Oplog Fetcher** — механизм, копирующий изменения, произошедшие в процессе миграции данных, для обеспечения консистентности.
*   **Index Phase (Фаза индексов)** — этап, на котором каждый Recipient Shard создаёт необходимые индексы, включая индекс для нового ключа шардирования.
*   **Commit Phase (Фаза фиксации)** — финальная фаза, когда Координатор дожидается строгой консистентности всех шардов и выполняет rename временной коллекции в основную.
*   **`forceRedistribution`** — опция (MongoDB 8.0+), позволяющая выполнять решардинг на тот же ключ шардирования для перераспределения данных между шардами (например, после добавления нового шарда).

## Базовые концепции

### Зачем нужен решардинг?

1.  **Неудачный выбор ключа:** Низкая кардинальность или монотонно растущий ключ (например, `createdAt` для не Time-series данных), приводящий к Hot Shard.
2.  **Изменение паттернов нагрузки:** Запросы чаще используют поле, которое не входит в текущий ключ шардирования (Scatter-Gather вместо Targeted Query).
3.  **Добавление новых шардов (MongoDB 8.0):** После добавления шарда в кластер можно использовать `forceRedistribution` для быстрого перераспределения данных без смены ключа. Решардинг пишет на все шарды параллельно, что значительно быстрее поштучных миграций чанков.
4.  **Зонирование (MongoDB 8.0):** Перемещение данных между зонами без изменения ключа шардирования (например, для соблюдения GDPR или Tiered Storage).

### Процесс решардинга — архитектура

В процессе решардинга каждый шард может быть:

*   **Donor (Донор)** — хранит текущие данные коллекции и отдаёт их Recipient'ам.
*   **Recipient (Приёмник)** — создаёт временную коллекцию и записывает в неё данные согласно новому ключу.
*   **Both (Донор и Приёмник одновременно)** — шард может быть одновременно Донором и Приёмником, если часть данных остаётся на нём, а часть перераспределяется.
*   **Neither** — шард не участвует в процессе.

Config Server Primary всегда выступает Координатором решардинга.

### Ограничения (MongoDB 8.0)

*   **Дисковое пространство:** Требуется минимум **1.2x** дополнительного места от размера коллекции на каждом шарде для временных индексов и данных.
*   **Производительность:** Процесс создаёт значительную нагрузку на I/O и CPU.
*   **Минимальная длительность:** Операция занимает минимум **5 минут** (даже для малых коллекций).
*   **Блокировка записи:** Записи блокируются максимум на **2 секунды** в финальной фазе (когда оценка оставшегося времени < 2 секунд).
*   **Одна коллекция:** Одновременно можно решардить только одну коллекцию.
*   **Retryable Writes:** Записи, начатые до или во время решардинга, могут быть повторены в течение **5 минут** после завершения. После 5 минут повторные попытки могут завершиться ошибкой `IncompleteTransactionHistory`.
*   **Неподдерживаемые команды:** Во время решардинга не поддерживаются: `moveCollection`, `renameCollection`, `drop`, `createIndex`, `dropIndex`.
*   **Queryable Encryption:** Коллекции с queryable encryption **не поддерживаются**.
*   **Atlas Search:** Индексы Atlas Search становятся недоступны после завершения. Требуется ручная пересборка.
*   **Уникальные индексы:** Если на коллекции заданы уникальные индексы, новый ключ шардирования должен удовлетворять их ограничениям.
*   **Дубликаты `_id`:** Решардинг завершается ошибкой при наличии дубликатов `_id`. Решение: скопировать данные в новые документы и удалить дубликаты.
*   **`numInitialChunks`:** По умолчанию 90; максимум 8192 на шард. При hashed ключе настройка игнорируется.
*   **`numSamplesPerChunk` (MongoDB 8.0.20+):** Количество документов для семплирования на чанк (по умолчанию 10).

### Предусловия (Prerequisites)

Перед запуском решардинга **обязательно** убедитесь:

1.  **Версия MongoDB:** 5.0+ (рекомендуется 8.0 для 최대 производительности).
2.  **Oplog Window:** Минимум **24 часа**. Рассчитайте необходимый размер:
    ```
    Размер Oplog >= (объём изменений за 24ч) + (объём данных коллекции + индексов)
    ```
    Если Oplog переполнится во время фазы Cloning — решардинг завершится ошибкой.
3.  **Дисковое пространство:** Минимум **1.2x** от суммарного размера коллекции + индексов на каждом участвующем шарде.
4.  **I/O:** Загрузка диска должна быть **ниже 50%** до начала операции.
5.  **CPU:** Загрузка процессора должна быть **ниже 80%** до начала операции.
6.  **Балансировщик (Balancer):** Должен быть **отключён** перед запуском решардинга.
7.  **Индексы:** Создавать индексы во время решардинга **запрещено** — они могут молча упасть. Не запускайте решардинг, если уже идёт сборка индекса.
8.  **Запросы приложения:** На время решардинга приложение должно передавать **оба ключа** (текущий и новый) во всех запросах к решардируемой коллекции. После завершения старый ключ можно удалить из запросов.

## Фазы процесса решардинга

### Фаза 1 — Initialization (Инициализация)

Координатор (Config Server Primary) вычисляет новое распределение данных (chunks) и подготавливает метаданные. Каждый Recipient Shard создаёт временную пустую шардированную коллекцию с теми же опциями, что и исходная. На этом этапе **индексы не создаются** (кроме `_id`).

### Фаза 2 — Clone (Клонирование)

Каждый Recipient Shard копирует документы с Доноров согласно новому ключу шардирования. Коллекция **доступна для чтения и записи** на протяжении всего этапа. Если объём данных большой, эта фаза занимает основное время.

### Фаза 3 — Index (Индексация)

Каждый Recipient Shard создаёт **все необходимые индексы**, включая индекс для нового ключа шардирования (если он ещё не существует). Это включает копирование всех существующих индексов коллекции.

### Фаза 4 — Apply and Catch-up (Применение и догоняющее копирование)

Recipient Shards применяют oplog-записи, написанные на Донорах после завершения клонирования. Этот этап обеспечивает консистентность данных. Когда оценка оставшегося времени падает ниже 2 секунд, **Донор блокирует запись** на исходной коллекции.

> Можно вручную ускорить завершение через `commitReshardCollection` / `sh.commitReshardCollection()`, если текущая оценка времени блокировки приемлема.

### Фаза 5 — Commit (Фиксация)

Координатор дожидается строгой консистентности всех шардов и выполняет:
1.  Rename временных коллекций в основные (на каждом шарде).
2.  Удаление старых коллекций на Донорах.
3.  Обновление метаданных кластера.

> После начала Commit Phase отмена через `abortReshardCollection` **невозможна**.

## Предварительная подготовка

### Шаг 0: Отключение балансировщика

Балансировщик должен быть отключён до запуска решардинга:

```javascript
// Подключение к mongos
sh.stopBalancer()

// Проверка статуса
sh.getBalancerState() // → false
```

> Балансировщик необходимо включить обратно после завершения решардинга.

## Практические сценарии

### Сценарий 1: Смена ключа шардирования

**Задача:** Сменить ключ с `{ "oldKey": 1 }` на `{ "newKey": 1, "oldKey": 1 }`.

#### Шаг 1: Проверка условий

```javascript
// Подключение к mongos
sh.status() // Убедиться, что коллекция шардирована и балансировщик отключён

// Проверка/создание индекса по новому ключу
// (в MongoDB 8.0 индекс создаётся автоматически, но рекомендуется создать заранее)
db.myCollection.createIndex({ newKey: 1, oldKey: 1 })
// → { "ok" : 1 }
```

#### Шаг 2: Запуск решардинга

```javascript
sh.reshardCollection(
  "myDatabase.myCollection",
  { newKey: 1, oldKey: 1 }
)
// → { "ok" : 1, "timeMillis" : <мс> }
```

Или через `db.adminCommand`:

```javascript
db.adminCommand({
  reshardCollection: "myDatabase.myCollection",
  key: { newKey: 1, oldKey: 1 }
})
// → { "ok" : 1 }
```

#### Шаг 3: Мониторинг прогресса

```javascript
// Способ 1: Общий статус шардирования
sh.status()

// Способ 2: Детали текущей операции решардинга
db.getSiblingDB("admin").aggregate([
  { $currentOp: { allUsers: true, localOps: false } },
  {
    $match: {
      type: "op",
      "originatingCommand.reshardCollection": "myDatabase.myCollection"
    }
  }
])
```

Пример вывода `$currentOp`:

```json
{
  "desc": "Resharding",
  "type": "op",
  "originatingCommand": {
    "reshardCollection": "myDatabase.myCollection",
    "key": { "newKey": 1, "oldKey": 1 }
  },
  "remainingOperationTimeEstimatedSecs": NumberLong(342),
  "totalOperationTimeElapsedSecs": NumberLong(158),
  "steps": "clone"
}
```

*Ключевые поля:*
*   `remainingOperationTimeEstimatedSecs` — примерное время до завершения (секунды).
*   `totalOperationTimeElapsedSecs` — прошедшее время (секунды).
*   `steps` — текущая фаза (`clone`, `index`, `apply`, `commit`).

#### Шаг 4: Включение балансировщика

```javascript
sh.startBalancer()
// → { "ok" : 1 }
```

#### Шаг 5: Обновление запросов приложения

После завершения решардинга обновите код приложения — удалите старый ключ шардирования из запросов:

```javascript
// Во время решардинга (оба ключа):
db.myCollection.find({ newKey: 123, oldKey: 456 })

// После завершения (только новый ключ):
db.myCollection.find({ newKey: 123 })
```

### Сценарий 2: Перераспределение данных на том же ключе (MongoDB 8.0+)

**Задача:** После добавления нового шарда в кластер перераспределить данные коллекции `shop_db.orders` по всем шардам.

```javascript
// Через sh.reshardCollection
sh.reshardCollection(
  "shop_db.orders",
  { _id: "hashed" },
  { forceRedistribution: true }
)
// → { "ok" : 1 }

// Или через db.adminCommand
db.adminCommand({
  reshardCollection: "shop_db.orders",
  key: { _id: "hashed" },
  forceRedistribution: true
})
// → { "ok" : 1 }
```

> `forceRedistribution: true` заставляет MongoDB запустить решардинг даже если ключ не изменился. Данные будут записаны на все шарды параллельно, что значительно быстрее последовательных миграций чанков.

---

### Сценарий 3: Решардинг с зонами (Zones)

**Задача:** Переместить данные `accounts.sales` в новые зоны `zone04` и `zone05` без изменения ключа шардирования.

```javascript
db.adminCommand({
  reshardCollection: "accounts.sales",
  key: { region_id: "hashed" },
  forceRedistribution: true,
  zones: [
    {
      zone: "zone04",
      min: { region_id: MinKey() },
      max: { region_id: 10 }
    },
    {
      zone: "zone05",
      min: { region_id: 10 },
      max: { region_id: MaxKey() }
    }
  ]
})
// → { "ok" : 1 }
```

---

### Сценарий 4: Отмена решардинга

Если решардинг вызывает проблемы с производительностью или обнаружены ошибки:

```javascript
// Отмена ДО начала Commit Phase
sh.abortReshardCollection("myDatabase.myCollection")
// → { "ok" : 1 }

// Или через db.adminCommand
db.adminCommand({
  abortReshardCollection: "myDatabase.myCollection"
})
```

> Отмена **невозможна** после начала Commit Phase (когда данные переключены). В этом случае дождитесь завершения.

## Справочник команд (Operations Reference)

| Команда / Действие | Описание |
| :--- | :--- |
| `sh.reshardCollection()` | Запуск решардинга с новым ключом шардирования. |
| `db.adminCommand({ reshardCollection: ... })` | Альтернативный способ запуска решардинга через adminCommand. |
| `sh.abortReshardCollection()` | Отмена решардинга (до начала Commit Phase). |
| `db.adminCommand({ abortReshardCollection: ... })` | Альтернативный способ отмены через adminCommand. |
| `sh.commitReshardCollection()` | Принудительное ускорение завершения решардинга (когда осталось < 2 сек). |
| `sh.getReshardCollectionStatus()` | Получение детального статуса текущей операции решардинга. |
| `$currentOp` (admin DB) | Мониторинг фазы, оставшегося времени и прогресса решардинга. |
| `sh.stopBalancer()` | Отключение балансировщика перед решардингом. |
| `sh.startBalancer()` | Включение балансировщика после завершения решардинга. |
| `sh.getBalancerState()` | Проверка состояния балансировщика. |
| `rs.printSecondaryReplicationInfo()` | Проверка задержки репликации на Secondary перед запуском. |
| `db.getReplicationInfo()` | Проверка размера и временного покрытия Oplog. |
| `db.serverStatus().wiredTiger.cache` | Проверка использования WiredTiger cache. |
| `replSetResizeOplog` | Увеличение размера Oplog при необходимости. |
| `sh.splitAt()` | Ручное разделение чанка (presplitting перед массовой загрузкой). |
| `sh.status()` | Проверка общего статуса шардированного кластера. |

## Лучшие практики (Best Practices)

### Подготовка к решардингу

1.  **Оценка Oplog:** Убедитесь, что размер Oplog достаточен для хранения всех изменений за время фазы Clone. Формула расчёта:
    ```
    Необходимый Oplog >= (объём изменений коллекции за 24ч) + (суммарный размер коллекции + индексов)
    ```
    Если Oplog переполнится — решардинг упадёт с ошибкой.

2.  **Мониторинг ресурсов перед запуском:**
    *   `Disk I/O Utilization` — должно быть **ниже 50%**.
    *   `CPU Load` — должно быть **ниже 80%**.
    *   `WiredTiger Tickets` — отслеживайте доступность тикетов для записи.
    *   Если задержки приложения растут во время решардинга — используйте `abortReshardCollection()`.

3.  **Отключение балансировщика:** Обязательно перед запуском решардинга. Включите обратно после завершения.

4.  **Выбор времени:** Запускайте операцию в периоды минимальной нагрузки. Учитывайте, что минимальная длительность — 5 минут.

5.  **Обновление приложения:** Подготовьте код приложения к передаче обоих ключей шардирования во всех запросах к коллекции.

6.  **Capacity Planning:** Перед решардингом оцените рост данных. Если коллекция будет превышать 1.2x текущего размера в течение 6 месяцев — рассмотрите добавление шардов с `forceRedistribution` вместо смены ключа.

### Во время решардинга

1.  **Мониторинг прогресса:** Используйте `$currentOp` pipeline для отслеживания фазы и оставшегося времени.
2.  **Нагрузка на диск:** Мониторьте I/O — фаза Clone создаёт значительную нагрузку на чтение.
3.  **Логи:** Следите за логами mongos и шардов на наличие предупреждений.
4.  **Не создавайте индексы** во время решардинга — они могут молча упасть.

### После решардинга

1.  **Включите балансировщик:** `sh.startBalancer()`.
2.  **Обновите приложение:** Удалите старый ключ шардирования из запросов.
3.  **Пересоберите Atlas Search** (если используется).
4.  **Проверьте распределение данных:** `sh.status()` — убедитесь, что чанки равномерно распределены.

### Runbook и реагирование

1.  **Документируйте процедуры:** Для каждого сценария (resharding, abort, fallback) должен быть пошаговый runbook. Храните его в Wiki или Git.
2.  **On-call rotation:** Дежурный инженер должен иметь доступ ко всем компонентам кластера и знать процедуры escalation.
3.  **План отката:** Перед `reshardCollection` всегда имейте план возврата к старой схеме (дамп коллекции или `forceRedistribution: false`).
4.  **Постмортем:** После каждого инцидента с решардингом проводите анализ с фиксацией причин и мер по предотвращению рецидива.

### Мониторинг и алертинг

1.  **Алерты на Oplog Window:** Порог — `< 12 часов` для production. Критический — `< 2 часов`.
2.  **Алерты на Replication Lag:** Порог — `> 10s` для Secondary. Критический — `> 30s`.
3.  **Алерты на дисковое пространство:** Порог — `> 80%` использования. Критический — `> 90%`.
4.  **Алерты на Critical Section:** Если решардинг завис в Critical Section дольше 5 минут — требуется вмешательство.
5.  **Мониторинг `$currentOp`:** Настройте дашборд с отображением текущих операций решардинга, фазы и оставшегося времени.

## Устранение неполадок (Troubleshooting)

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `Resharding aborted: Insufficient space` | Недостаточно места на диске (требуется минимум 1.2x от размера коллекции). | Увеличьте дисковые лимиты или очистите неиспользуемые данные/индексы. |
| `Stuck in Critical Section` | Слишком много активных транзакций блокируют финальную фазу. | Увеличьте `reshardingCriticalSectionTimeoutMillis` (опасно для latency) или снизьте нагрузку. |
| `Index build failed` | Ошибка создания индекса для нового ключа. | Убедитесь, что новый ключ не нарушает ограничения уникальности (если они заданы). |
| `Oplog overflow` / `Oplog window too small` | Oplog не вместил все изменения за фазу Clone. | Увеличьте размер Oplog (`replSetResizeOplog`) и перезапустите решардинг. |
| `Duplicate _id values` | Документы с одинаковыми `_id` не позволяют выполнить миграцию чанков. | Найдите и удалите дубликаты: `db.collection.aggregate([{$group:{_id:"$_id", count:{$sum:1}}}], {allowDiskUse:true})`. |
| `IncompleteTransactionHistory` (Retryable Writes) | Попытка повторной записи через >5 минут после завершения решардинга. | Повторите операцию вручную — она не будет автоматически перезапущена. |
| `Resharding aborted: index build` | Попытка запуска решардинга во время уже идущей сборки индекса. | Дождитесь завершения сборки индекса перед запуском решардинга. |
| `Balancer interference` | Балансировщик пытается мигрировать чанки во время решардинга. | Убедитесь, что `sh.stopBalancer()` выполнен до запуска. Проверьте `sh.getBalancerState()`. |
| `Config Server unavailable` | Config Server Primary недоступен во время решардинга. | Операция приостанавливается. Восстановите Config Server. Если требуется — выполните failover Config Server Replica Set. |
| `Network partition` | Разрыв связи между mongos и шардами или между шардами. | Решардинг приостанавливается. После восстановления сети операция продолжается автоматически. |
| `WiredTiger cache overflow` | Фаза Clone создаёт больше данных, чем помещается в кэш. | Уменьшите `storage.wiredTiger.engineConfig.cacheSizeGB` или увеличьте RAM. Мониторьте `db.serverStatus().wiredTiger.cache`. |
| `Secondary lag spike` | Secondary не успевает за Primary из-за повышенной нагрузки при решардинге. | Проверьте `rs.printSecondaryReplicationInfo()`. Увеличьте `oplogSize` или снизьте нагрузку на Primary. |
| `Chunk migration conflicts` | Несколько миграций чанков конфликтуют во время `forceRedistribution`. | Нормальное поведение. Балансировщик/решардинг повторит попытку. Убедитесь, что `maxChunkSize` не слишком мал (по умолчанию 128 МБ). |
| `Rollback after interrupted resharding` | Решардинг прерван (сбой питания, kill -9) во время Commit Phase. | MongoDB автоматически откатывает изменения. Данные остаются на старом ключе. Перезапустите решардинг. |
| `Resharding aborted: transaction conflict` | Долгая транзакция блокирует Critical Section дольше `transactionLifetimeLimitSeconds`. | Завершите долгие транзакции через `db.currentOp()` и `db.killOp()`. Увеличьте лимит времени транзакции. |
| Высокая задержка (latency) во время решардинга | Фаза Clone/Create Index нагружает диск и CPU. | Снизьте нагрузку на приложение; при необходимости отмените решардинг (`abortReshardCollection`). |
| Atlas Search индекс недоступен после решардинга | Ожидаемое поведение — индекс не переносится автоматически. | Пересоберите Atlas Search индекс вручную после завершения. |

## Граничные случаи и ограничения (Edge Cases)

- **Очень большие коллекции (>1 ТБ):** Решардинг может занимать часы. Убедитесь, что Oplog Window покрывает всю фазу Clone + Index. Рассмотрите разделение на несколько операций или использование `forceRedistribution` с более агрессивной конфигурацией чанков.
- **Высокая нагрузка на запись:** При постоянной высокой нагрузке Oplog может переполниться быстрее, чем ожидается. Мониторьте `db.getReplicationInfo()` во время операции. Если Oplog Window < 2 часов — отмените решардинг и увеличьте Oplog.
- **Сетевые разрывы между Config Server и шардами:** Если Config Server Primary становится недоступен во время решардинга, операция приостанавливается. После восстановления Config Server решардинг продолжается автоматически. Если Config Server не восстанавливается — требуется ручное вмешательство.
- **Активные транзакции:** Долгие-running транзакции (> 2 секунд) могут блокировать финальную фазу (Critical Section). Мониторьте `currentOp` на наличие активных транзакций. Увеличьте `transactionLifetimeLimitSeconds` или завершите транзакции перед запуском.
- **Сложный составной ключ:** Если новый ключ включает поле с низкой кардинальностью, MongoDB может создать слишком много мелких чанков. Используйте суффиксное поле с высокой кардинальностью или hashed префикс.
- **Зоны + forceRedistribution:** При использовании `zones` с `forceRedistribution: true` убедитесь, что зоны уже настроены на шардах (`addShardToZone`). Иначе данные могут распределиться некорректно.
- **Отставание Secondary:** Фаза Clone создаёт повышенную нагрузку на Primary. Secondary могут отстать, если `secondaryDelaySecs` настроен или диск медленный. Проверьте `rs.printSecondaryReplicationInfo()` перед запуском.
- **Откат после прерывания питания:** Если процесс решардинга прерван на этапе Commit Phase (например, сбой Config Server), MongoDB автоматически откатывает изменения при восстановлении. Данные остаются на старом ключе.
