# MongoDB: Change Streams (Потоки изменений)

## Определения

**Change Streams** — это механизм реального времени, позволяющий приложениям подписываться на изменения данных в коллекции, базе данных или во всем кластере. Он является современным и безопасным интерфейсом к **Oplog** (Operations Log) и служит фундаментом для построения событийно-ориентированных архитектур (EDA).

*   **CDC (Change Data Capture):** Процесс захвата изменений для синхронизации с другими системами (Elasticsearch, Kafka, аналитические хранилища).
*   **Resume Token:** Уникальный идентификатор позиции в потоке изменений. Позволяет приложению возобновить чтение ровно с того места, где оно остановилось, без потери событий.
*   **Oplog:** Первоисточник данных для Change Streams. Если событие вытеснено из Oplog по времени или размеру, поток не сможет его прочитать.

## Архитектура и механизмы

### 1. Уровни подписки
*   **Collection:** `db.collection.watch()` — наиболее частый сценарий (конкретная сущность).
*   **Database:** `db.watch()` — отслеживание всех изменений в рамках одной БД.
*   **Cluster:** `Mongo().watch()` — глобальное отслеживание (требует прав `clusterAdmin`).

### 2. Отказоустойчивость (Resumability)
Каждое событие содержит поле `_id`, которое является **Resume Token**.
*   **Механизм:** Приложение должно сохранять последний полученный токен в надежное хранилище.
*   **Возобновление:** При перезапуске приложение передает `resumeAfter: <token>` в опциях `watch()`.

### 3. Pre/Post Images (Снимки состояния)
С версии 6.0 MongoDB позволяет получать состояние документа до и после изменения:
*   **`fullDocument: "updateLookup"`:** Возвращает актуальную версию документа на момент обработки события (может отличаться от версии в момент изменения).
*   **`fullDocumentBeforeChange: "required"`:** Возвращает документ в том виде, в котором он был *до* обновления (требует включения `changeStreamPreAndPostImages` на коллекции).

## Особенности версии 8.0+

*   **`$changeStreamSplitLargeEvent`:** Новая стадия агрегации, позволяющая обрабатывать изменения, которые сами по себе или вместе с метаданными превышают лимит BSON в 16 МБ. Событие разбивается на фрагменты, которые приложение может собрать воедино.
*   **Оптимизированная фильтрация:** В версии 8.0 фильтры агрегации (`$match`) применяются максимально близко к чтению Oplog. Это значительно снижает нагрузку на CPU и уменьшает задержку (latency) в крупных кластерах.

## Типы событий (Operation Types)

| Тип | Описание |
| :--- | :--- |
| **`insert`** | Создание нового документа. |
| **`update`** | Изменение полей существующего документа. |
| **`replace`** | Полная замена документа. |
| **`delete`** | Удаление документа. |
| **`drop`** | Удаление всей коллекции. |
| **`invalidate`** | Событие, закрывающее поток (например, при удалении БД). |

## Практические сценарии

### 1. Реализация надежного потребителя (Node.js)
Пример с сохранением позиции и обработкой ошибок:

```javascript
async function watchOrders(collection, lastTokenStore) {
  const pipeline = [
    { $match: { "operationType": "insert", "fullDocument.status": "paid" } }
  ];

  let resumeToken = await lastTokenStore.get();
  const changeStream = collection.watch(pipeline, { 
    resumeAfter: resumeToken,
    fullDocument: "whenAvailable" 
  });

  changeStream.on("change", async (event) => {
    try {
      await processOrder(event.fullDocument);
      // Сохраняем токен ПОСЛЕ успешной обработки
      await lastTokenStore.save(event._id);
    } catch (err) {
      console.error("Ошибка обработки:", err);
      // Логика остановки или повтора
    }
  });

  changeStream.on("error", (err) => {
    console.error("Критическая ошибка потока:", err);
    // Пересоздание потока с последним сохраненным токеном
  });
}
```

### 2. Включение снимков состояния для коллекции
```javascript
db.runCommand({
  collMod: "orders",
  changeStreamPreAndPostImages: { enabled: true }
})
```

## Устранение неполадок

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| **`ChangeStreamHistoryLost`** | Resume Token старше, чем самая ранняя запись в Oplog. | Увеличить размер Oplog (`oplogSizeMB`). Выполнить полную синхронизацию данных и начать с нового токена. |
| **Высокая задержка событий** | Огромный поток записей или тяжелые фильтры. | В v8.0 использовать простейшие `$match`. Убедиться, что на Primary достаточно ресурсов CPU. |
| **Поток закрывается (`invalidate`)** | Коллекция или БД были удалены. | Пересоздать коллекцию и запустить новый поток `watch()`. |
| **События не приходят** | Чтение со вторичных реплик с большим лагом. | Проверить `rs.status()` и Replica Lag. |

## Лучшие практики

1.  **Фильтруйте на сервере:** Передавайте `pipeline` прямо в `watch()`, чтобы не перегружать сеть ненужными событиями.
2.  **Минимизируйте метаданные:** Если вам не нужны полные документы (`fullDocument`), не запрашивайте их — это экономит ресурсы WiredTiger.
3.  **Мониторинг Oplog:** Всегда держите окно Oplog не менее 24 часов, чтобы иметь запас времени на исправление ошибок в приложении-потребителе.
4.  **Idempotency:** Обработка событий в приложении должна быть идемпотентной, так как в распределенных системах возможна повторная доставка одного и того же события.
