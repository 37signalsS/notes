# MongoDB: Индексы

**Актуально для:** MongoDB 8.0.x

---

## Определения

**Индекс в MongoDB** — специализированная структура данных на основе **B-tree**, содержащая упорядоченную копию значений индексируемых полей. Позволяет СУБД находить документы без полного сканирования коллекции (**COLLSCAN**), что критично для производительности при больших объемах данных.

- **Структура:** Ключи хранятся в отсортированном порядке, что обеспечивает эффективный поиск по диапазону (Range queries) и сортировку.
- **Производительность:** Индексы ускоряют чтение, но увеличивают нагрузку на запись (Write Amplification) и занимают место в RAM и на диске.
- **Хранение:** В WiredTiger каждый индекс — отдельный B-tree файл в директории данных. При создании индекса происходит чтение всей коллекции и запись B-tree, что дает резкий всплесс I/O.
- **MongoDB 8.0+:** Улучшены сообщения `explain()` и автоматическая оптимизация планов выполнения.

Подробная теория общих принципов: **[Индексы баз данных](../Concepts/indexes.md)**.

## Базовые концепции

### Типы индексов

1.  **Single Field Index (Одиночный):** Индекс по одному полю. Включает автоматический уникальный индекс по полю `_id`.
2.  **Compound Index (Составной):** Индекс по нескольким полям. Порядок полей критичен.
    - **Правило ESR (Equality, Sort, Range):**
      - **Equality:** Поля с точным совпадением (`=`) — первыми.
      - **Sort:** Поля, по которым выполняется сортировка, — вторыми.
      - **Range:** Поля с диапазонами (`>`, `<`, `$in`, `$ne`) — последними.
3.  **Multikey Index (Мультиключевой):** Индексация массивов. MongoDB создает запись в индексе для каждого элемента массива.
4.  **Hashed Index (Хешированный):** Хранит хеш значения поля. Используется для равномерного распределения данных при шардировании. Не поддерживает поиск по диапазону.
5.  **Wildcard Index (Шаблонный):** Индексирует все поля объекта или массива. Полезен для динамических схем.
6.  **Functional (Expression) Index:** Индексация результата вычисления. Доступен с версии 4.4+.
7.  **Geospatial & Text:** Специализированные индексы для поиска по координатам (`2dsphere`) и полнотекстового поиска (`text`).

### Свойства индексов

- **Unique (Уникальный):** Гарантирует отсутствие дубликатов значений ключа.
- **Partial (Частичный):** Индексирует только документы, соответствующие фильтру (`partialFilterExpression`). Экономит место и ускоряет запись.
- **Sparse (Разреженный):** Содержит записи только для документов, где индексируемое поле существует.
- **TTL (Time-To-Live):** Автоматически удаляет документы по истечении времени (поле должно быть типа `Date`).
- **Hidden (Скрытый):** Индекс существует и обновляется, но не используется оптимизатором запросов. Позволяет тестировать удаление индекса без риска обрушить производительность.
- **Collation:** Сортировка и сравнение строк в соответствии с языковыми правилами. Используется для case-insensitive поиска.

### Особенности хранения и поведения

- **Write Amplification:** Каждая вставка/обновление требует обновления всех связанных B-tree индексов.
- **Cache Pressure:** Индексы хранятся в WiredTiger Cache. Чем больше индексов, тем меньше места для данных, тем чаще происходит Cache Eviction и чем выше latency.
- **Index Intersection:** MongoDB может использовать пересечение нескольких индексов, но один хорошо подобранный составной индекс всегда эффективнее.
- **Размер индекса:** Должен помещаться в RAM для максимальной производительности. При превышении происходит page fault и резкий рост latency.

## Подготовка окружения (Prerequisites)

Для безопасного создания индексов в промышленной среде:

1.  **Пространство на диске:** Свободное место должно быть не менее **2x** от размера индексируемой коллекции (данные + индекс + временные файлы).
2.  **WiredTiger Cache:** Не ограничивайте `cacheSizeGB` слишком агрессивно во время построения индекса. По умолчанию cache = 50% RAM.
3.  **IOPS:** Индексные построения вызывают последовательное чтение всей коллекции и случайную запись B-tree. Убедитесь, что диск имеет запас по пропускной способности.
4.  **Replica Set:** В кластере используйте `commitQuorum` для контроля, сколько узлов подтвердят создание индекса.

## Практические сценарии

### 1. Создание индексов

С версии 4.2 все индексы строятся в **фоновом режиме** (non-blocking). В Replica Set процесс координируется через `commitQuorum`.

```javascript
// Составной индекс с правилом ESR
db.orders.createIndex(
  { customer_id: 1, order_date: -1, status: 1 },
  { name: "idx_cust_date_status" }
)

// Частичный индекс
db.users.createIndex(
  { email: 1 },
  { partialFilterExpression: { email: { $exists: true } } }
)

// TTL индекс (автоудаление через 30 дней)
db.sessions.createIndex(
  { createdAt: 1 },
  { expireAfterSeconds: 2592000 }
)

// Collation для case-insensitive поиска
db.users.createIndex(
  { name: 1 },
  { collation: { locale: "en", strength: 2 } }
)
```

**Валидация:**
```javascript
db.orders.getIndexes() // # → список всех индексов с опциями
db.currentOp({ "command.createIndexes": { $exists: true } }) // # → активные построения
```

### 2. Анализ через explain()

Метод `explain()` — основной инструмент профилирования. В версии 8.0 сообщения стали более детализированными.

```javascript
db.collection.find({ age: { $gt: 25 } }).sort({ name: 1 }).explain("executionStats")
```

**Ключевые стадии (Stages):**
- **COLLSCAN:** Полное сканирование (индекс не использован).
- **IXSCAN:** Сканирование ключей индекса (цель — максимально точная выборка).
- **FETCH:** Получение документов с диска/кэша по ключам из индекса.
- **SORT:** Сортировка в памяти (если индекс не покрывает сортировку). Признак неэффективности при больших объемах.
- **PROJECTION_COVERED:** Index Only Scan (данные взяты только из индекса, стадия FETCH отсутствует).

**Валидация результата:**
```javascript
// Проверка покрытия индекса
db.collection.find({ indexed_field: "value" }, { indexed_field: 1 }).explain("executionStats")
// # → ищем "stage": "PROJECTION_COVERED", totalDocsExamined: 0
```

### 3. Оптимизация через $indexStats

Проверка востребованности индексов:

```javascript
db.collection.aggregate([ { $indexStats: {} } ])
// Анализируйте поле 'accesses.ops' — если оно 0, индекс можно скрыть или удалить.
```

**Валидация:**
```javascript
// Документ с нулевой активностью
db.collection.aggregate([ { $indexStats: {} }, { $match: { "accesses.ops": 0 } } ])
// # → список неиспользуемых индексов
```

### 4. Скрытие и удаление индексов

Безопасный способ проверить, нужен ли индекс:

```javascript
db.collection.hideIndex("idx_name")
// Если производительность упала — unhideIndex("idx_name").
// Если всё в порядке в течение суток — dropIndex("idx_name").
```

**Валидация:**
```javascript
db.collection.getIndexes() // # → проверка статуса индекса ("hidden": true/false)
```

### 5. Индексация для шардирования

Для равномерного распределения записей по чанкам используйте хешированный ключ:

```javascript
db.collection.createIndex({ _id: "hashed" })
```

**Важно:** В шардированном кластере Unique индекс должен включать полный ключ шардирования.

### 6. Text Index (полнотекстовый поиск)

Text index поддерживает полнотекстовый поиск по строковым полям с лингвистическим стеммингом (удаление окончаний) и стоп-словами.

```javascript
// Создание text-индекса (одно поле)
db.articles.createIndex({ content: "text" }, { name: "idx_content_text" })

// Составной text-индекс (несколько полей, веса)
db.articles.createIndex(
  { title: "text", content: "text" },
  { name: "idx_title_content_text", weights: { title: 10, content: 5 } }
)

// Поиск
db.articles.find({ $text: { $search: "mongodb performance" } })

// Поиск с релевантностью (score)
db.articles.find(
  { $text: { $search: "mongodb performance" } },
  { score: { $meta: "textScore" } }
).sort({ score: { $meta: "textScore" } })

// Поиск фразы (точное совпадение)
db.articles.find({ $text: { $search: "\"queryable encryption\"" } })

// Исключение слова
db.articles.find({ $text: { $search: "mongodb -encryption" } })
```

**Особенности:**
*   **Один text-индекс на коллекцию** — нельзя создать два text-индекса.
*   **Язык:** по умолчанию `english`. Укажите `default_language` при создании или `language` в документе.
*   **Стемминг:** `running`, `runs`, `ran` → `run`. Для русского используйте `default_language: "russian"`.
*   **Стоп-слова:** `the`, `a`, `is` игнорируются.
*   **Case-insensitive:** поиск нечувствителен к регистру.
*   **Не поддерживает:** регулярные выражения, частичные совпадения (только целые слова).

**Валидация:**
```javascript
db.articles.getIndexes() // # → наличие text-индекса
db.articles.find({ $text: { $search: "test" } }).explain("executionStats")
// # → "stage": "TEXT" — индекс используется
```

**Ограничения:**
*   Text index не поддерживается в sharded cluster как shard key.
*   Для сложного полнотекстового поиска (фасеты, автодополнение) используйте Atlas Search (Lucene) или Elasticsearch.

### 7. Geospatial Index (2dsphere)

`2dsphere` индекс поддерживает геопространственные запросы на сфере (Земля): near, within, intersects. Используйте для координат (GeoJSON).

```javascript
// Создание 2dsphere-индекса
db.places.createIndex({ location: "2dsphere" }, { name: "idx_location_2dsphere" })

// Вставка GeoJSON-точки
db.places.insertOne({
  name: "Office",
  location: { type: "Point", coordinates: [37.6173, 55.7558] } // [longitude, latitude]
})

// Поиск рядом (near) — в радиусе 1000 м
db.places.find({
  location: {
    $near: {
      $geometry: { type: "Point", coordinates: [37.6173, 55.7558] },
      $maxDistance: 1000 // метры
    }
  }
})

// Поиск внутри полигона
db.places.find({
  location: {
    $geoWithin: {
      $geometry: {
        type: "Polygon",
        coordinates: [[
          [37.5, 55.7], [37.7, 55.7], [37.7, 55.8], [37.5, 55.8], [37.5, 55.7]
        ]]
      }
    }
  }
})

// Пересечение с геометрией
db.places.find({
  location: {
    $geoIntersects: {
      $geometry: { type: "LineString", coordinates: [[37.5, 55.7], [37.7, 55.8]] }
    }
  }
})
```

**GeoJSON типы:** `Point`, `LineString`, `Polygon`, `MultiPoint`, `MultiLineString`, `MultiPolygon`, `GeometryCollection`.

**Важно:**
*   **Порядок координат:** `[longitude, latitude]` (не `[lat, lng]`!). Долгота первая.
*   **Единицы `$maxDistance`:** метры для `2dsphere` (радианы для legacy `2d`).
*   **`$near` требует индекс** — без `2dsphere` индекса `$near` не работает.
*   **`$geoWithin` и `$geoIntersects`** работают без индекса, но с индексом значительно быстрее.

**Валидация:**
```javascript
db.places.getIndexes() // # → наличие 2dsphere-индекса
db.places.find({ location: { $near: { $geometry: {...}, $maxDistance: 1000 } } })
  .explain("executionStats")
// # → "stage": "GEO_NEAR" — индекс используется
```

**Legacy `2d` индекс:** плоский (планарный) индекс для простых координат. Используйте `2dsphere` для реальных геоданных (сфера Земли).

**Применение SRE:** геолокация пользователей, поиск ближайших серверов/дата-центров, геозоны для compliance (данные в определённом регионе).

## Ограничения и Edge Cases

- **Лимит индексов:** Максимум 64 индекса на одну коллекцию.
- **Размер ключа:** Индексация очень длинных строк потребляет избыточное количество RAM и увеличивает время записи.
- **Resource Usage:** Построение индекса на больших коллекциях может вызвать резкий рост I/O и потребления WiredTiger Cache. В кластерах рекомендуется Rolling Index Build.
- **Sharding Unique Constraint:** Unique индекс в шардированной коллекции должен включать поле шардирования (shard key), иначе MongoDB отклонит создание.
- **Background Build:** В MongoDB 4.2+ построение индекса не блокирует чтение/запись, но на время построения могут появляться реплики, отстающие от Primary.

---

## Лучшие практики (SRE)

1.  **Следите за WiredTiger Cache Evictions:** Рост `wiredTiger.cache.evictions` указывает на недостаток RAM для данных и индексов.
2.  **Регулярно аудит индексы:** Используйте `$indexStats` раз в неделю для выявления неиспользуемых индексов.
3.  **Rolling Index Build в Production:** Для больших коллекций (>100GB) создавайте индексы по одному на узел Replica Set, чтобы избежать пиковой нагрузки.
4.  **Используйте Partial вместо Sparse:** `partialFilterExpression` дает больше контроля и работает предсказуемее.
5.  **Коллиции только при необходимости:** `collation` добавляет накладные расходы. Если достаточно строгого сравнения — не используйте.
6.  **Создавайте индексы до залива данных:** При больших объемах (`mongorestore`, `mongoimport`) сначала восстановите данные, затем создавайте индексы. Это быстрее, чем инкрементальное обновление индексов при каждой вставке.
7.  **Фиксируйте FCV после обновления:** После Rolling Upgrade установите `setFeatureCompatibilityVersion`, чтобы новые фичи индексов заработали на всех узлах.

## Устранение неполадок

| Проблема | Возможная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Slow Index Build** | Нехватка RAM или высокая нагрузка на диск | `db.currentOp()`, `iostat` | Увеличить `cacheSizeGB` или понизить приоритет построения. |
| **COLLSCAN при наличии индекса** | Несоответствие типа данных или пропущенное поле в ESR | `explain("executionStats")` | Убедиться, что типы в запросе и индексе совпадают (String vs Int). |
| **Index build failed** | Недостаточно места в `/tmp` или на диске данных | `df -h`, логи mongod | Убедиться, что свободного места > 2x от размера коллекции. |
| **Высокий WiredTiger Dirty Cache** | Чрезмерное количество индексов при интенсивной записи | `db.serverStatus().wiredTiger.cache` | Удалить неиспользуемые или дублирующие индексы. |
| **Unique constraint violation** | Дубликат при создании unique индекса на существующих данных | `db.collection.aggregate([ { $group: { _id: "$field", count: { $sum: 1 } } }, { $match: { count: { $gt: 1 } } } ])` | Очистить дубликаты перед созданием индекса. |
| **Index not used** | Неправильный ESR порядок или опечатка в поле | `explain("executionStats")` | Проверить порядок полей в запросе и индексе. |

## Диагностика медленных запросов (Slow Queries)

### 1. Уровни профилирования

- **Уровень 0:** Профилирование выключено.
- **Уровень 1:** Логирование запросов, превышающих `slowms` (по умолчанию 100мс).
- **Уровень 2:** Логирование **всех** запросов (только для отладки!).

```javascript
db.setProfilingLevel(1, { slowms: 50 }); // логировать всё, что дольше 50мс
```

### 2. Анализ системной коллекции `system.profile`

```javascript
// Топ-5 самых медленных запросов
db.system.profile.find().sort({ millis: -1 }).limit(5).pretty()

// Поиск запросов с COLLSCAN
db.system.profile.find({ planSummary: "COLLSCAN" }).pretty()
```

### 3. Использование explain(executionStats)

```javascript
db.collection.find({ user_id: 123 }).explain("executionStats")
```

**На что смотреть SRE:**
- `nReturned`: сколько документов вернул запрос.
- `totalKeysExamined`: сколько записей в индексе просмотрено.
- `totalDocsExamined`: сколько документов прочитано с диска/кэша.
- **Идеальное соотношение:** `nReturned == totalKeysExamined` и `totalDocsExamined == 0` (запрос покрыт индексом).
