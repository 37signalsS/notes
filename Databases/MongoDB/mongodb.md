# MongoDB

## 1. Определения

**MongoDB** – это документо-ориентированная NoSQL СУБД. В отличие от реляционных баз данных, которые используют таблицы и строки, MongoDB хранит данные в гибких, JSON-подобных документах. Модель данных и основанный на ней API позволяют быстро разрабатывать приложения и итерировать их.

- **Документ:** Основная единица данных, аналог строки в реляционной БД. Представляет собой BSON-структуру (Binary JSON).
- **Коллекция:** Группа документов, аналог таблицы. Не имеет строгой схемы.

## 2. Основные концепции

### Модель данных

- **Гибкая схема:** Документы в одной коллекции могут иметь разную структуру. Это упрощает эволюцию схемы данных по мере развития приложения.
- **Вложенные документы и массивы:** Позволяют моделировать сложные иерархические отношения в одном документе, избегая необходимости в `JOIN`'ах.

### Высокая доступность: Набор реплик (Replica Set)

**Replica Set** — это группа процессов `mongod`, которые поддерживают идентичные наборы данных, обеспечивая отказоустойчивость и повышая доступность данных.

- **Primary (первичный узел):** Принимает все операции записи. В реплика-сете только один primary.
- **Secondary (вторичные узлы):** Асинхронно реплицируют `oplog` (журнал операций) с primary. Могут обслуживать запросы на чтение.
- **Arbiter (арбитр):** Опциональный участник, который голосует на выборах, но не хранит данные.
- **Выборы (Elections):** Автоматический процесс, при котором secondary-узлы выбирают новый primary, если старый становится недоступным.

### Горизонтальное масштабирование: Шардирование (Sharding)

**Шардирование** — это метод распределения данных по нескольким серверам (шардам) для обеспечения горизонтальной масштабируемости.

- **Shard (Шард):** Независимый replica set, хранящий часть данных.
- **Query Router (`mongos`):** Маршрутизатор запросов, к которому подключаются приложения. Он направляет операции чтения и записи на нужные шарды.
- **Config Servers:** Replica set, хранящий метаданные о распределении данных по шардам.
- **Shard Key (Ключ шардирования):** Поле в документе, которое определяет, на каком шарде будут храниться данные. **Выбор ключа критически важен** для производительности.

### Особенности эксплуатации

Несмотря на гибкость, при эксплуатации MongoDB стоит учитывать следующие моменты:

- **Потребление ресурсов:** MongoDB может активно потреблять оперативную память и дисковое пространство, часто "жрёт" их как не в себя.
- **Сложность администрирования:** Управление кластером (Replica Set, Sharding) может быть гораздо сложнее по сравнению с традиционными реляционными СУБД, такими как PostgreSQL.

## 3. Практические сценарии

- **Быстрая разработка (Rapid Prototyping):** Гибкая схема позволяет быстро вносить изменения в модель данных.
- **Контент-менеджмент:** Хранение разнородного контента, пользовательских профилей, комментариев.
- **Большие данные и IoT:** Масштабируемость позволяет обрабатывать большие объемы данных от множества источников.
- **Каталоги продуктов:** Вложенные документы идеально подходят для хранения товаров с различными атрибутами.

## 4. Дополнительная информация
