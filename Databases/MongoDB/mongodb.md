# Обзор MongoDB

## Определения

**MongoDB** — высокопроизводительная документо-ориентированная NoSQL СУБД с открытым исходным кодом. Относится к семейству **Document Stores**. В контексте теоремы CAP классифицируется как **CP** (Consistency/Partition Tolerance), однако при определенных настройках `readPreference` может обеспечивать высокую доступность (AP).

- **Версия:** Актуальная стабильная ветка в 2026 году — **8.0+**. Основные изменения включают улучшенное сжатие, расширенную поддержку временных рядов (Time-series) и полную интеграцию с `mongosh`. Устаревшая оболочка `mongo` полностью удалена.
- **BSON (Binary JSON):** Бинарный формат хранения, расширяющий JSON поддержкой типов `ObjectId`, `Date`, `BinData`, `Decimal128`. BSON спроектирован для эффективного сканирования: поля в документе имеют префиксы с их длиной и типом, что позволяет пропускать ненужные данные при чтении.
- **Документ:** Основная единица записи. Максимальный размер — **16 МБ**. Ограничение введено для предотвращения чрезмерного использования RAM и обеспечения предсказуемой задержки при сетевых операциях. Для работы с более крупными файлами используется спецификация **GridFS**.
- **Коллекция:** Группировка документов. Не требует жесткой схемы (Dynamic Schema), что позволяет документам в одной коллекции иметь разный набор полей.

### Системные требования и подготовка (Prerequisites)

Для обеспечения стабильности и производительности MongoDB 8.0+ на Linux-системах обязательны следующие настройки:
1.  **Файловая система:** Рекомендуется только **XFS**. WiredTiger использует `fsync` и разреженные файлы, что на XFS работает эффективнее, чем на `ext4`.
2.  **Transparent Huge Pages (THP):** Должны быть **отключены**. MongoDB выделяет память небольшими порциями, и использование 2МБ страниц вместо 4КБ приводит к фрагментации и деградации производительности.
3.  **Лимиты (ulimits):**
    - `nofile` (количество открытых файлов): не менее 64 000.
    - `nproc` (количество процессов): не менее 64 000.
4.  **Swap:** Рекомендуется иметь небольшой swap, но настроить `vm.swappiness = 1`, чтобы избежать вытеснения горячих данных WiredTiger из RAM.
5.  **Архитектура:** Требуется поддержка набора инструкций **AVX** (для версий 5.0+).

## Базовые концепции

### Модель данных

- **Вложенность (Embedding):** Хранение связанных данных внутри одного документа. Рекомендуется для связей «один-к-одному» и «один-ко-многим», если данные часто читаются вместе. Это обеспечивает атомарность обновления всей записи за одну операцию.
- **Ссылки (Referencing):** Хранение `_id` другого документа. Используется для предотвращения превышения лимита 16 МБ или для связей «многие-ко-многим». В MongoDB 8.0+ операции `$lookup` (JOIN) значительно оптимизированы, но все равно требуют индексов на обеих сторонах.

### Механизмы хранения (WiredTiger)

Основной движок с версии 3.2. Работает по принципу **MVCC** (Multi-Version Concurrency Control).

- **WiredTiger Cache:** По умолчанию занимает **50% доступной RAM минус 1 ГБ**. В контейнерах (Docker/K8s) необходимо явно ограничивать кэш через параметр `storage.wiredTiger.engineConfig.cacheSizeGB`, иначе MongoDB может попытаться занять больше памяти, чем выделено лимитом cgroups, что приведет к OOM Kill.
- **Чекпоинты (Checkpoints):** Каждые 60 секунд (по умолчанию) WiredTiger сбрасывает все грязные страницы из кэша на диск. Это создает периодическую нагрузку на I/O.
- **Журналирование (Journaling):** Запись операций в журнал (WAL) перед фиксацией в файлах данных. Гарантирует восстановление данных после внезапного сбоя. Журнал сбрасывается на диск каждые 100 мс (или при каждом `writeConcern: majority`).
- **Сжатие:** Алгоритм `snappy` (баланс CPU/Ratio) по умолчанию. `zstd` рекомендуется для архивных данных.

### Индексы

Подробная теория: **[Индексы баз данных](../Concepts/indexes.md)**.

- **_id Index:** Уникальный индекс, создаваемый автоматически.
- **Compound Index:** Индекс по нескольким полям. Правило **ESR** (Equality, Sort, Range): сначала поля точного совпадения, затем сортировка, затем диапазоны.
- **Partial/Sparse Indexes:** Индексация только части документов (например, где поле существует или равно определенному значению), что экономит место и ускоряет запись.
- **Covered Queries:** Запросы, которые удовлетворяются полностью данными из индекса, не обращаясь к самому документу (самый быстрый тип чтения).
- **TTL Index:** Автоматическое удаление документов. Не гарантирует мгновенного удаления (фоновый поток работает раз в минуту).

### Агрегация (Aggregation Framework)

Мощный инструмент обработки данных, работающий по принципу конвейера (Pipeline).

**Продвинутые стадии и возможности:**
- **`$facet`:** Позволяет выполнять несколько конвейеров параллельно над одним набором данных (удобно для фильтров и пагинации за один запрос).
- **`$merge` / `$out`:** Сохранение результатов агрегации в другую коллекцию (нативно в БД, без перекачки данных на клиент).
- **`$lookup` (Inner/Outer Join):** Позволяет объединять данные. Для производительности внешнее поле (`foreignField`) обязано быть проиндексировано.
- **`$indexStats`:** Анализ использования индексов в реальном времени.

### Репликация (Replica Set)

Обеспечивает высокую доступность и отказоустойчивость. Подробная теория: **[Репликация](../Concepts/replication.md)**.

- **Election:** При сбое Primary новый лидер выбирается за считанные секунды. Рекомендуется нечетное количество узлов (минимум 3).
- **Read Preference:** Позволяет читать со вторичных узлов (`secondary`, `secondaryPreferred`), что полезно для аналитики, но может отдавать устаревшие данные (Stale Reads).
- **Write Concern (`w`):** `w: "majority"` является стандартом для защиты от потери данных при перевыборах.

### Шардирование (Sharding)

Горизонтальное масштабирование через распределение данных по разделам (chunks). Подробная теория: **[Шардирование](../Concepts/sharding.md)**.

- **Refined Shard Key:** В новых версиях можно изменять ключ шардирования путем добавления суффикса, что облегчает миграцию данных при росте.
- **Hashed Sharding:** Равномерное распределение, но не поддерживает эффективные запросы по диапазонам.
- **Ranged Sharding:** Оптимально для запросов по диапазонам (например, по дате), но требует аккуратного выбора ключа во избежание "горячих шардов" (hot shards).

### Транзакции (ACID)

Поддержка многодокументных транзакций в Replica Set (4.0+) и Sharded Cluster (4.2+).
- Гарантируют атомарность для набора операций в разных коллекциях или базах.
- Используют Snapshot Isolation.

### Безопасность

- **RBAC:** Ролевая модель (роли `read`, `readWrite`, `dbAdmin`, `root`).
- **Аутентификация:** SCRAM-SHA-256 (стандарт), x.509, LDAP.
- **TLS/SSL:** Обязательно для защиты трафика между узлами и клиентами.
- **Encryption at Rest:** Шифрование данных на диске (Enterprise).

## Практические сценарии

### Типовая конфигурация (`mongod.conf`)

Пример оптимизированного конфигурационного файла для продакшн-среды:

```yaml
storage:
  dbPath: /var/lib/mongodb
  journal:
    enabled: true
  wiredTiger:
    engineConfig:
      # Лимитируем кэш (важно для контейнеров)
      cacheSizeGB: 2 
      directoryForIndexes: true # Разделение данных и индексов для I/O оптимизации
    collectionConfig:
      blockCompressor: snappy

systemLog:
  destination: file
  logAppend: true
  path: /var/log/mongodb/mongod.log
  logRotate: reopen

net:
  port: 27017
  bindIp: 127.0.0.1,10.0.0.5 # Ограничиваем доступ только нужными интерфейсами
  tls:
    mode: requireTLS
    certificateKeyFile: /etc/ssl/mongodb.pem

security:
  authorization: enabled # Обязательно для продакшена
  keyFile: /var/lib/mongodb/keyfile # Для аутентификации между узлами реплики

replication:
  replSetName: rs0
```

### Базовое администрирование (`mongosh`)

Основные команды для инициализации кластера и управления доступом:

1. **Инициализация Replica Set:**
```javascript
// Выполняется на одном узле после запуска
rs.initiate({
  _id: "rs0",
  members: [
    { _id: 0, host: "mongo-1:27017" },
    { _id: 1, host: "mongo-2:27017" },
    { _id: 2, host: "mongo-3:27017" }
  ]
})
```

2. **Создание администратора:**
```javascript
use admin
db.createUser({
  user: "admin",
  pwd: passwordPrompt(), // Безопасный ввод пароля
  roles: [ { role: "root", db: "admin" } ]
})
```

### Мониторинг и диагностика

Для глубокого анализа состояния системы используются встроенные утилиты и команды:

- **`mongostat`:** Мониторинг в реальном времени (ops/sec, locks, mem, dirty cache).
- **`mongotop`:** Анализ времени, затрачиваемого на чтение/запись в разрезе коллекций.
- **Анализ плана запроса (`explain`):**
```javascript
db.collection.find({ status: "active" }).explain("executionStats")
```
*Ключевые показатели:* `nReturned` (сколько найдено) должен быть близок к `totalKeysExamined` (сколько индексов просмотрено). Если `totalDocsExamined` > 0 при наличии индекса — это признак неоптимального запроса.

- **Профилирование:**
```javascript
db.setProfilingLevel(1, { slowms: 100 }) // Логировать запросы медленнее 100мс в system.profile
```

### Резервное копирование и восстановление

1. **Логическое копирование (`mongodump` / `mongorestore`):**
   - Плюсы: Гибкость (можно восстановить одну коллекцию), компактность.
   - Минусы: Высокая нагрузка на CPU/RAM при дампе, не гарантирует мгновенной согласованности без флага `--oplog`.
2. **Физическое копирование (Снапшоты):**
   - Самый быстрый способ для больших БД.
   - Обязательно использование XFS и `db.fsyncLock()` (или механизмов LVM/EBS snapshots) для обеспечения консистентности на уровне файлов WiredTiger.

### Решение проблем (Troubleshooting)

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **OOM Kill** | Не ограничен WiredTiger Cache. | Установите `cacheSizeGB` в `mongod.conf`. |
| **Высокий I/O Wait** | Частые чекпоинты или нехватка RAM. | Проверьте `dirty cache` в `mongostat`. Увеличьте RAM или используйте более быстрые диски. |
| **Replica Rollback** | Узел Primary упал до репликации данных. | Используйте `w: "majority"` для предотвращения откатов. |
| **Slow Startup** | Восстановление после сбоя без журнала. | Убедитесь, что `journaling` включен. Проверьте права на `dbPath`. |

### Антипаттерны и "Белые пятна"
- **Толстые документы (Fat Documents):** Хранение огромных массивов внутри одного документа приводит к деградации производительности при частичных обновлениях.
- **Глубокая вложенность:** Затрудняет написание запросов и использование индексов.
- **Отсутствие индексов:** Приводит к полному сканированию коллекции (**COLLSCAN**), что парализует БД при больших объемах данных.
- **Заупотребление транзакциями:** Транзакции в MongoDB имеют накладные расходы. Если вам нужны транзакции для каждого запроса — возможно, вам нужна реляционная БД.
