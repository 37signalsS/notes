# MongoDB: Администрирование и обслуживание

## Определения

**Администрирование MongoDB** — это комплекс мер по обеспечению высокой доступности, производительности и сохранности данных кластера.

*   **FCV (Feature Compatibility Version):** Флаг, определяющий набор доступных функций версии. Даже после обновления бинарных файлов до v8.0, новые функции не будут активны, пока FCV не переключен.
*   **PITR (Point-in-Time Recovery):** Возможность восстановления состояния БД на любой конкретный момент времени (секунду) в прошлом.
*   **Working Set (Рабочий набор):** Объем данных и индексов, к которым приложение обращается наиболее часто. В идеале должен целиком помещаться в WiredTiger Cache.
*   **Oplog Window:** Временной интервал, за который хранятся операции в Oplog. Определяет, как долго Secondary может находиться в офлайне без необходимости полной пересинхронизации.

## Конфигурация и мониторинг

### 1. Управление конфигурацией (`mongod.conf`)
Основные блоки настроек в формате YAML:
*   **`storage`:** Пути к данным, настройки WiredTiger Cache и сжатия.
*   **`net`:** Порты, привязка IP, настройки TLS.
*   **`replication`:** Имя Replica Set.
*   **`security`:** Авторизация и `keyFile`.

### 2. Инструменты диагностики
*   **`db.serverStatus()`:** Показывает текущую нагрузку, состояние памяти, кэша и соединений.
*   **`db.currentOp()`:** Список всех выполняющихся операций в реальном времени. Позволяет найти и "убить" (`db.killOp()`) тяжелые запросы.
*   **`mongostat`:** Утилита для мониторинга в реальном времени (аналог `top` для MongoDB).
*   **`mongotop`:** Анализ времени I/O в разрезе коллекций.

## Резервное копирование и восстановление

### Стратегии бэкапа
1.  **Логический (`mongodump` / `mongorestore`):**
    *   *Плюсы:* Компактность, возможность восстановления отдельных коллекций.
    *   *Минусы:* Медленно на больших объемах (ТБ).
    *   *Команда:* `mongodump --uri="mongodb://..." --oplog --out=/backup/` (опция `--oplog` обязательна для консистентности).
2.  **Физический (Snapshots):**
    *   *Плюсы:* Мгновенное создание, быстрое восстановление.
    *   *Минусы:* Требует поддержки на уровне ФС (LVM, ZFS, AWS EBS) и блокировки БД через `db.fsyncLock()`.
3.  **PITR (Percona Backup for MongoDB):** Рекомендуемое open-source решение для непрерывного бэкапа Oplog и восстановления на момент времени.

## Обслуживание и обновление (Upgrades)

### Процедура Rolling Upgrade (8.0+)
Для минимизации простоя кластер обновляется по одному узлу:
1.  **Обновление Secondary:** Остановить `mongod`, обновить пакеты, запустить. Дождаться статуса `SECONDARY`.
2.  **Ротация Primary:** Выполнить на текущем лидере `rs.stepDown()`. Он станет Secondary, а один из обновленных узлов — Primary.
3.  **Обновление старого Primary:** Повторить шаг 1 для последнего узла.
4.  **Финализация (FCV):** После проверки стабильности всех узлов:
    ```javascript
    db.adminCommand({ setFeatureCompatibilityVersion: "8.0" })
    ```

## Устранение неполадок

| Проблема | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **OOM Kill** | Кэш + соединения > RAM. | `dmesg`, `mongostat` | Ограничить `cacheSizeGB` и `maxIncomingConnections`. |
| **Высокий I/O Wait** | Частые чекпоинты. | `iostat`, `mongotop` | Использовать NVMe, разнести индексы и данные на разные диски. |
| **Replica Lag** | Медленная сеть или диск на Secondary. | `rs.printSecondaryReplicationInfo()` | Проверить пропускную способность, увеличить `oplogSize`. |
| **`Connection reset`** | Лимит дескрипторов. | `ulimit -n` в системе. | Установить `ulimit -n 64000` в systemd юните. |
| **Stale Config** | Ошибка метаданных в шардах. | Логи `mongos`. | Обычно исправляется автоматически при повторе (Retry). |

## Лучшие практики (SRE)

1.  **Версионность:** Фиксируйте версии пакетов в ОС (`apt-mark hold`), чтобы избежать случайных обновлений.
2.  **Динамический Oplog:** Начиная с v4.4, изменяйте размер Oplog без перезагрузки:
    ```javascript
    db.adminCommand({ replSetResizeOplog: 1, size: 50000 }) // Размер в МБ
    ```
3.  **Мониторинг Oplog Window:** Держите окно не менее 48 часов. Если оно падает до 1-2 часов — это критический риск потери данных.
4.  **Разделение прав:** Используйте `keyFile` только для внутренней связи, а для администрирования — выделенных пользователей с RBAC.
