# Стратегии отката в базах данных

## Определения

**Откат (Rollback)** — операция возврата базы данных или её части в предыдущее стабильное состояние при обнаружении ошибок, сбоев или неудачных изменений.

**Точка восстановления (Restore Point)** — именованная метка или снимок состояния, к которому можно вернуться. Позволяет минимизировать время восстановления и предотвратить потерю данных при проведении рискованных операций.

**Отстающая реплика (Delayed Standby)** — сервер-реплика, на котором применение изменений из журнала транзакций намеренно задержано на фиксированное время (например, 4 часа). Позволяет быстро «откатиться» при человеческой ошибке (например, `DROP TABLE`) без обращения к бэкапам.

## Основные концепции

Выбор стратегии отката зависит от критичности данных и требуемых метрик **RTO/RPO**.

### Уровни и механизмы отката

Выбор стратегии отката зависит от критичности данных и требуемых метрик **RTO/RPO**.

| Уровень | Механизм | RTO | Особенности |
| :--- | :--- | :--- | :--- |
| **Транзакция** | `SAVEPOINT`, `ROLLBACK` | Секунды | Позволяет отменить часть операций внутри текущей сессии до завершения (`COMMIT`). |
| **База данных** | **PITR**, **Flashback** | Минуты/Часы | Восстановление на произвольный момент времени через накат WAL/Redo-логов поверх бэкапа. |
| **Инфраструктура** | Снапшоты (**ZFS**, **LVM**, Облако) | Минуты | Мгновенный откат тома. Для консистентности требуется `fsync` или Copy-on-Write механизмы на уровне СХД. |
| **Приложение** | Feature Flags, **Down-миграции** | Секунды | Возврат логики или структуры схемы. Требует обратной совместимости кода (см. **[Expand-Contract](./migrations/expand_contract.md)**). |

### Продвинутые техники

- **Flashback (Oracle/PostgreSQL):** Позволяет «отматывать» состояние объектов БД назад без полного восстановления из бэкапа. Реализуется через чтение сегментов отката (**Undo Log**) или использование расширений (напр. `pg_dirtyread`).
- **Delayed Standby (Отстающая реплика):** Сервер, на котором применение WAL намеренно задержано (например, на 6 часов). При фатальной ошибке на мастере (напр. `DROP TABLE`), администратор останавливает репликацию на этом узле и извлекает данные до момента аварии.
- **Copy-on-Write (CoW):** Технология снимков на уровне файловой системы (ZFS/Btrfs). Позволяет мгновенно создавать «клоны» базы данных для тестирования изменений или быстрого отката всей файловой системы без перемещения данных.

## Практические сценарии

### Использование транзакционных точек (SAVEPOINT)

Применяется для частичного отката изменений в рамках одной сложной транзакции.

```sql
BEGIN;
UPDATE inventory SET count = count - 1 WHERE item_id = 101;

SAVEPOINT part_order_saved;

-- Рискованная операция обновления статистики
UPDATE analytics SET total_orders = total_orders + 1;

-- При ошибке в аналитике откатываемся к SAVEPOINT
ROLLBACK TO SAVEPOINT part_order_saved;

-- Основное изменение (inventory) сохраняется
COMMIT;
```
### Именованные точки восстановления (PostgreSQL)

Создание метки перед выполнением ручных правок или миграций данных.

```sql
-- 1. Создание точки восстановления на мастере
SELECT pg_create_restore_point('pre_upgrade_task_404');

-- 2. В случае необходимости отката, перезапуск сервера с параметром:
-- recovery_target_name = 'pre_upgrade_task_404'
```

### Откат миграций (Down-скрипты)

При использовании паттерна **Expand-Contract**, откат выполняется через `down`-скрипты, которые удаляют триггеры синхронизации и новые объекты. См. подробнее в **[Стратегиях отката миграций](./migrations/rollback_strategies.md)**.

## Мониторинг и SRE-метрики
### Откат через клонирование снапшота (ZFS)

Применяется для быстрого восстановления огромных БД при неудачных мажорных обновлениях.

1. **Перед обновлением:** Создание снимка тома данных.
2. **При сбое:** Остановка СУБД, откат тома к снимку (`zfs rollback`), запуск СУБД. Время простоя не зависит от размера БД.

## Мониторинг и SRE-метрики

Успешность стратегии отката оценивается по следующим критериям:

- **Верификация целостности:** После отката необходимо запустить автоматические тесты (Smoke tests) для проверки консистентности данных и работоспособности приложения.
- **Контроль RTO:** Время от обнаружения ошибки до полного восстановления сервиса не должно превышать SLA.
- **Контроль RPO:** Объем потерянных данных при откате (например, транзакции между точкой отката и текущим моментом) должен быть задокументирован.
