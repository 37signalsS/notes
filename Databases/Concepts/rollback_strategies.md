# Стратегии отката в базах данных

**Актуально для:** PostgreSQL 18, MySQL 8.4 LTS, MariaDB 12.x, SQL Server 2022, MongoDB 8.0

## Определения

**Откат (Rollback)** — операция возврата базы данных или её части в предыдущее стабильное состояние. Различают:
- **Soft Rollback:** Отмена незафиксированных изменений текущей транзакции в оперативной памяти с помощью **Undo Log**.
- **Hard Rollback:** Восстановление всей БД или тома данных из физической копии (бэкап, снапшот) при катастрофических сбоях.

**Undo Log (Журнал отката)** — структура данных, хранящая информацию о том, как отменить изменения, внесенные активными транзакциями. Необходим для обеспечения атомарности (Atomicity) и многоверсионности (MVCC).

**Точка восстановления (Restore Point)** — именованная метка или снимок состояния, к которому можно вернуться. Позволяет минимизировать время восстановления и предотвратить потерю данных при проведении рискованных операций.

**Отстающая реплика (Delayed Standby)** — сервер-реплика, на котором применение изменений из журнала транзакций намеренно задержано на фиксированное время (например, 4 часа). Позволяет быстро «откатиться» при человеческой ошибке (например, `DROP TABLE`) без обращения к бэкапам.

## Основные концепции

Выбор стратегии отката зависит от критичности данных и требуемых метрик **RTO/RPO**.

| Уровень | Механизм | RTO | Особенности |
| :--- | :--- | :--- | :--- |
| **Транзакция** | `SAVEPOINT`, `ROLLBACK` | Секунды | Отмена операций внутри сессии через Undo Log до завершения (`COMMIT`). |
| **База данных** | **PITR**, **Flashback** | Минуты/Часы | Восстановление на произвольный момент времени через накат WAL/Redo-логов поверх бэкапа. |
| **Инфраструктура** | Снапшоты (**ZFS**, **LVM**) | Минуты | Мгновенный откат тома. Для консистентности требуется `fsync` или Copy-on-Write механизмы. |
| **Приложение** | Feature Flags, **Down-миграции** | Секунды | Возврат логики или структуры схемы. Требует обратной совместимости кода (см. **[Expand-Contract](./migrations/expand_contract.md)**). |

### Почему rollback работает: связь с ACID и WAL

Гарантия отката проистекает из двух фундаментальных свойств СУБД:

- **Atomicity (Атомарность)** — транзакция либо применяется полностью, либо не применяется вовсе. При сбое в любой точке СУБД откатывает все изменения транзакции через **Undo Log** (MVCC) или повторяет записи из WAL до последнего чекпоинта (ARIES: Redo) и затем откатывает незавершенные транзакции (Undo).
- **Durability (Долговечность)** — обеспечивается через **[WAL](./write_ahead_log.md)**. Изменения сначала фиксируются в журнале на диск (`fsync`), и только потом попадают в файлы данных. Если при откате страницы данных содержат изменения незавершенной транзакции, СУБД игнорирует их (LSN-механика) или откатывает через CLR (Compensation Log Records).

**Связь уровней отката и ACID:**

| Уровень отката | ACID-свойство | Механизм |
| :--- | :--- | :--- |
| **Транзакция** | Atomicity | Undo Log / MVCC visibility |
| **База данных (PITR)** | Durability + Atomicity | WAL + Redo/Undo (ARIES) |
| **Инфраструктура** | Durability | Снапшот тома + Crash Recovery |

### Продвинутые техники

- **Undo Log и MVCC:** При выполнении `ROLLBACK` транзакции СУБД использует **Undo Log** для восстановления старых значений строк в обратном хронологическом порядке. Этот же журнал позволяет другим транзакциям читать согласованное состояние данных (Snapshot isolation), пока текущая транзакция еще не завершена.
- **Delayed Standby (Отстающая реплика):** При совершении критической ошибки на мастере (например, `UPDATE` без `WHERE`), SRE должен немедленно:
    1.  Остановить репликацию на отстающей реплике (команда `STOP REPLICA` или `STOP SLAVE`).
    2.  Определить точный момент (timestamp или LSN) до совершения ошибки.
    3.  Восстановить реплику до этой точки.
    4.  Сделать дамп нужных данных и перенести их на мастер.
- **Инфраструктурные снапшоты (Copy-on-Write):** Файловые системы и менеджеры томов (ZFS, LVM) позволяют создавать мгновенные снимки томов.
    - **Crash Consistency:** Снапшот, сделанный без остановки БД, эквивалентен состоянию после "выдергивания шнура". СУБД восстановится при запуске через Redo Log.
    - **Заморозка (Quiescing):** Для идеального отката рекомендуется выполнить `fsync` или `FLUSH TABLES WITH READ LOCK`, сделать снапшот и разблокировать БД. Это гарантирует **Application-consistent** состояние.

## Предварительные требования

- **Архивация WAL/Binlog включена:** Для PITR требуется непрерывная архивация журналов транзакций (`archive_mode = on`, `binlog`).
- **Тестирование восстановления:** Бэкапы и PITR должны регулярно тестироваться на изолированном сервере.
- **Доступ к хранилищу ключей/логов:** Для отката через PITR или снапшоты требуется доступ к тому же хранилищу бэкапов и архивов.
- **План DR:** KEK/Master Key и процедуры восстановления должны быть задокументированы и доступны на площадке катастрофического восстановления.
- **Синхронизация времени:** NTP должна быть настроена на всех узлах. Некорректные временные метки ломают PITR и сортировку бинарных логов.
- **Разделение дисков data и WAL:** WAL/redo log должен находиться на выделенном устройстве, отдельно от файлов данных. Это исключает конкуренцию за IOPS и упрощает диагностику. Для NVMe — отдельный раздел или LUN; для HDD — отдельный физический диск или RAID 10.
- **Завершение зависших транзакций:** Настройте `idle_in_transaction_session_timeout` (PostgreSQL) и `wait_timeout` (MySQL) для автоматического завершения сессий, которые мешают чекпоинтам и WAL-архивации.
- **Шифрование и контроль доступа:** Для PITR требуется доступ к тому же ключевому материалу (KEK/Master Key), что и для шифрования бэкапов. Храните ключи отдельно от серверов БД (HSM, Vault, offline storage).
- **Документация runbook:** Для каждого типа отката (транзакционный, PITR, снапшот, pg_rewind) должен быть актуальный runbook с командами и точками проверки.

## Практические сценарии

### Использование транзакционных точек (SAVEPOINT)

Применяется для частичного отката изменений в рамках одной сложной транзакции.

```sql
BEGIN;
UPDATE inventory SET count = count - 1 WHERE item_id = 101;

SAVEPOINT part_order_saved;

-- Рискованная операция обновления статистики
UPDATE analytics SET total_orders = total_orders + 1;

-- При ошибке в аналитике откатываемся к SAVEPOINT
ROLLBACK TO SAVEPOINT part_order_saved;

-- Основное изменение (inventory) сохраняется
COMMIT;
```

#### Валидация

```sql
-- Проверка активных точек сохранения в текущей сессии (PostgreSQL)
SELECT * FROM pg_savepoint;

-- Проверка статуса транзакции
SELECT txid_current();
```

#### Очистка / Откат

```sql
-- Освобождение SAVEPOINT (без отката)
RELEASE SAVEPOINT part_order_saved;

-- Полный откат транзакции
ROLLBACK;
```

### Именованные точки восстановления (PostgreSQL)

Создание метки перед выполнением ручных правок или миграций данных.

```sql
-- 1. Создание точки восстановления на мастере
SELECT pg_create_restore_point('pre_upgrade_task_404');

-- 2. В случае необходимости отката, перезапуск сервера с параметром:
-- recovery_target_name = 'pre_upgrade_task_404'
```

#### Валидация

```sql
-- Проверка, что точка восстановления создана
SELECT * FROM pg_create_restore_point('test_validation_point');

-- Просмотр текущей позиции WAL для ручного PITR
SELECT pg_current_wal_lsn();
```

#### Очистка / Откат

```sql
-- Удаление старых WAL-сегментов после успешного бэкапа
SELECT pg_catalog.pg_switch_wal();
CHECKPOINT;
```

### PITR: Восстановление на произвольный момент времени (PostgreSQL)

PITR — основной механизм отката всей БД к состоянию на определенную секунду в прошлом.

#### Шаг 1: Подготовка (до сбоя)

```bash
# Включение архивации WAL в postgresql.conf
archive_mode = on
archive_command = 'test ! -f /var/lib/postgresql/wal_archive/%f && cp %p /var/lib/postgresql/wal_archive/%f'
wal_level = replica
```

**Альтернатива:** Для автоматизации используйте **[pgBackRest](../PostgreSQL/Operations/backup_automation.md)** или **WAL-G** — они управляют архивацией, ретенцией и проверяют целостность без ручных скриптов.

#### Шаг 2: Восстановление после сбоя

```bash
# 1. Остановка PostgreSQL
sudo systemctl stop postgresql@18-main

# 2. Восстановление последнего полного бэкапа
sudo -u postgres pg_basebackup -D /var/lib/postgresql/18/main/data -X fetch -P

# 3. Настройка recovery.conf (PostgreSQL 12+)
cat <<EOF | sudo -u postgres tee /var/lib/postgresql/18/main/data/postgresql.auto.conf
restore_command = 'cp /var/lib/postgresql/wal_archive/%f %p'
recovery_target_time = '2026-10-01 14:30:00'
recovery_target_action = 'promote'
EOF

# 4. Запуск
sudo systemctl start postgresql@18-main
```

#### Валидация

```sql
-- Проверка времени восстановления
SELECT pg_is_wal_replay_paused();
SELECT now() - pg_postmaster_start_time();

-- Проверка целостности
SELECT count(*) FROM pg_tables;
ANALYZE;
```

#### Очистка / Откат

```sql
-- Если восстановление неудачно — повторный PITR к более ранней точке
-- После успешного восстановления — отключение standby режима
ALTER SYSTEM SET restore_command = '';
SELECT pg_reload_conf();
```

### PITR: Восстановление по бинарным логам (MySQL)

В MySQL PITR реализуется через комбинацию полного бэкапа и бинарных логов.

#### Шаг 1: Подготовка (до сбоя)

```ini
# /etc/mysql/my.cnf
[mysqld]
server-id = 1
log_bin = /var/lib/mysql/binlog/mysql-bin
binlog_expire_logs_seconds = 604800
binlog_format = ROW
sync_binlog = 1
```

**GTID (рекомендуется):** Включите GTID для точного позиционирования при PITR. В MariaDB 10.8+ и MySQL 8.0+ предпочитайте `--start-position=GTID` вместо File:Offset. В MariaDB 11.4+ включите `binlog_gtid_index = ON` для ускорения поиска. Подробнее о GTID-ориентированном PITR см. в **[Резервном копировании MariaDB](../MariaDB/backup_and_recovery.md)**.

#### Шаг 2: Восстановление после сбоя

```bash
# 1. Восстановление полного бэкапа
mysql -u root -p < backup_full_2026-10-01.sql

# 2. Применение бинарных логов до момента ошибки
mysqlbinlog --stop-datetime="2026-10-01 14:30:00" /var/lib/mysql/binlog/mysql-bin.000123 \
  | mysql -u root -p
```

#### Валидация

```sql
-- Проверка позиции бинарного лога
SHOW MASTER STATUS;
SHOW BINARY LOGS;

-- Проверка времени восстановления
SELECT NOW();
```

#### Очистка / Откат

```bash
# Очистка примененных binlog файлов
PURGE BINARY LOGS BEFORE NOW();
```

### Откат через клонирование снапшота (ZFS / LVM)

Применяется для быстрого восстановления огромных БД при неудачных мажорных обновлениях (Major Upgrades).

**Сценарий (LVM):**
1. **Подготовка:** Создание снимка логического тома: `lvcreate -s -n pre_upgrade_snap -L 50G /dev/vg0/db_data`.
2. **Обновление:** Выполнение `apt upgrade` или миграции данных.
3. **Сбой:** Если база не запускается или данные повреждены.
4. **Откат:** Остановка сервиса, возврат к снимку: `lvconvert --merge /dev/vg0/pre_upgrade_snap`, запуск сервиса. Время простоя — минуты, вне зависимости от терабайтов данных.

#### Валидация

```bash
# Проверка статуса тома
lvs /dev/vg0/pre_upgrade_snap

# Проверка целостности после отката
sudo -u postgres pg_checksums -D /var/lib/postgresql/18/main/data
```

#### Очистка / Откат

```bash
# Удаление снапшота после успешного отката
lvremove /dev/vg0/pre_upgrade_snap
```

### Работа с отстающей репликой (Delayed Standby)

Используется для спасения данных при человеческой ошибке (например, `DROP TABLE`).

```bash
# 1. На реплике: немедленная остановка применения логов
mysql -e "STOP REPLICA;"

# 2. Поиск в логах мастера LSN/позиции ПЕРЕД ошибкой
# 3. Перемотка реплики до нужной точки (Point-in-Time)
# 4. Экспорт таблицы
mysqldump db_name lost_table > recovery.sql

# 5. Импорт данных на основной мастер
```

#### Валидация

```sql
-- Проверка задержки репликации
SHOW SLAVE STATUS\G

-- Проверка, что реплика остановлена
SELECT @@global.super_read_only;
```

#### Очистка / Откат

```bash
# Возобновление репликации после успешного восстановления
mysql -e "START REPLICA;"
```

## Восстановление с использованием pg_rewind (PostgreSQL)

`pg_rewind` — инструмент для быстрого возврата Primary-ноды к состоянию standby-ноды после отказа.

**Предпосылки:**
- Оба кластера работают на одной и той же major версии PostgreSQL.
- На старой Primary включен `wal_level = replica` и есть достаточный объем WAL для перемотки.
- Целевой кластер (будущий standby) остановлен перед запуском `pg_rewind`.

```bash
# 1. На старой Primary (которая станет новой standby):
sudo -u postgres pg_rewind --target-pgdata=/var/lib/postgresql/18/main/data \
  --source-server="host=replica.internal port=5432 user=postgres"

# 2. Настройка recovery.conf на старой Primary
cat <<EOF | sudo -u postgres tee /var/lib/postgresql/18/main/data/postgresql.auto.conf
primary_conninfo = 'host=replica.internal port=5432 user=postgres'
EOF

# 3. Запуск
sudo systemctl start postgresql@18-main
```

**Edge case:** Если `pg_rewind` завершается с ошибкой «source server must be shut down» — убедитесь, что целевой кластер остановлен. Если ошибка «could not open file» — проверьте права доступа к целевому каталогу `pg_wal`.

## Мониторинг и SRE-метрики

### Ключевые метрики

**Статус архивации WAL:**
```sql
-- PostgreSQL: проверка статуса архивации
SELECT * FROM pg_stat_archiver;
-- → archived_count, failed_count, last_archived_wal

-- MySQL: проверка binlog позиции
SHOW MASTER STATUS;
SHOW SLAVE STATUS\G
```

**Статус SAVEPOINT и транзакций:**
```sql
-- PostgreSQL: проверка активных транзакций
SELECT * FROM pg_stat_activity WHERE state = 'active';

-- MySQL: проверка активных транзакций InnoDB
SELECT * FROM information_schema.INNODB_TRX;
```

### Алерты и пороговые значения

| Метрика | Порог | Действие |
| :--- | :--- | :--- |
| `failed_count` (pg_stat_archiver) | > 0 | Критический алерт: WAL-архивация сломана, PITR невозможен |
| `last_archived_wal` | Старее 1 цикла бэкапа | Критический алерт: данные не архивируются |
| Задержка репликации | > 1 час (Delayed Standby) | Предупреждение: окно отката сужается |
| `Seconds_Behind_Master` | > задержка | Критический алерт: реплика отстает |
| Состояние LUKS тома | Не активен | Критический алерт: зашифрованный том не смонтирован |

### Rollback Confidence и Drift

- **Rollback Confidence (Уверенность в откате):** Процент случаев, когда процедура отката успешно прошла тестирование в staging-среде. Метрика показывает надежность процесса восстановления.
- **Rollback Drift (Дрейф отката):** Объем данных или количество транзакций, накопленных между точкой отката и моментом аварии. Помогает оценить реальный ущерб бизнесу.
- **Контроль RTO/RPO:** Реальное время простоя и объем потерянных данных не должны превышать установленные в SLA лимиты.

### Автоматизация

**Systemd-сервис для проверки готовности к откату:**
```ini
# /etc/systemd/system/db-rollback-readiness.service
[Unit]
Description=Check database rollback readiness
After=mysql.service

[Service]
Type=oneshot
ExecStart=/usr/local/bin/check-db-rollback.sh
```

**Скрипт проверки (`/usr/local/bin/check-db-rollback.sh`):**
```bash
#!/bin/bash
# Проверка готовности к PITR
if [ "$(psql -U postgres -t -c 'SELECT count(*) FROM pg_stat_archiver WHERE failed_count > 0' 2>/dev/null)" -gt 0 ]; then
    echo "CRITICAL: WAL archiving is failing, PITR is not possible"
    exit 1
fi

# Проверка задержки репликации
if [ "$(mysql -u root -p"${MYSQL_ROOT_PASSWORD}" -e "SHOW SLAVE STATUS\G" 2>/dev/null | grep Seconds_Behind_Master | awk '{print $2}')" -gt 3600 ]; then
    echo "WARNING: Replication delay exceeds 1 hour, rollback window is shrinking"
    exit 1
fi

echo "OK: Rollback readiness confirmed"
```

## Лучшие практики

1. **Всегда имейте план отката.** Перед любым изменением схемы или данных документируйте шаги отката и тестируйте их на staging.
2. **Тестируйте PITR регулярно.** Минимум раз в квартал выполняйте полное восстановление из бэкапа + WAL на изолированном сервере.
3. **Используйте Delayed Standby для защиты от человеческой ошибки.** Окно задержки 4–24 часа — разумный компромисс между RPO и RTO.
4. **Архивируйте WAL/Binlog не менее 72 часов.** Для PITR требуется архив за период, превышающий максимальное окно обнаружения ошибки.
5. **Ведите реестр точек восстановления.** Для каждой рискованной операции создавайте именованную точку (`pg_create_restore_point`) и фиксируйте её в changelog.
6. **Не полагайтесь только на откат миграций.** Down-скрипты не восстанавливают удаленные данные (`DROP`). Комбинация: бэкап + PITR + откат миграций.
7. **Тестируйте pg_rewind и аварийный failover.** В кластере с репликами регулярно проверяйте, что `pg_rewind` работает корректно.
8. **Мониторьте failed_count архивации.** Неработающая WAL-архивация делает PITR невозможным. Настройте алерт на `pg_stat_archiver.failed_count > 0`.
9. **Автоматизируйте PITR через pgBackRest / WAL-G.** Ручная настройка `archive_command` подвержена ошибкам. Используйте инструменты с встроенной проверкой и ретеншеном.
10. **Используйте GTID вместо File:Offset в MySQL/MariaDB.** GTID устойчив к ротации бинарных логов и упрощает автоматизацию восстановления.
11. **Разделяйте WAL и данные на разных дисках.** Для high-load систем это обязательно. WAL — последовательная запись, данные — случайная. Разделение позволяет использовать разные профили производительности для каждой нагрузки.
12. **Тестируйте откат на актуальном дампе продакшена.** Процедура деплоя должна всегда включать цикл: `Migrate Up -> Verify -> Migrate Down -> Verify` на staging.

## Типичные ошибки и troubleshooting

### 1. PITR не работает: `pg_stat_archiver` показывает ошибки

**Причина:** `archive_command` завершился с ошибкой, диск переполнен, или недоступен целевой каталог.

**Диагностика:**
```sql
SELECT * FROM pg_stat_archiver;
-- Проверьте failed_count, last_failed_wal, last_failed_time
```

**Решение:**
1. Проверьте место на диске: `df -h /var/lib/postgresql/wal_archive`.
2. Проверьте права доступа к каталогу архивации.
3. После исправления: `SELECT pg_catalog.pg_switch_wal();` для принудительной архивации.

### 2. MySQL: `mysqlbinlog` выводит ошибки формата

**Причина:** Бинарный лог поврежден или использовался режим `STATEMENT`/`MIXED` с небезопасными операциями.

**Решение:**
- Используйте `ROW` формат для всех таблиц (рекомендуется по умолчанию).
- Восстанавливайтесь до последнего валидного `GTID` или позиции.

### 3. LVM-снапшот не мержится: том занят

**Причина:** Снапшот был создан с недостаточным размером и переполнился (Cow-переполнение).

**Диагностика:**
```bash
lvs /dev/vg0/pre_upgrade_snap
# Проверьте поле "Allocation" и "Snap%"
```

**Решение:**
- Если снапшот переполнен — данные повреждены. Восстанавливайтесь из полного бэкапа.
- Для будущих снапшотов выделяйте место под все изменения за время жизни снапшота (обычно 10-20% от исходного тома).

### 4. Delayed Standby не защитил от `DROP TABLE`

**Причина:** Ошибка была обнаружена после истечения окна задержки, или реплика была остановлена слишком поздно.

**Решение:**
1. Немедленно остановите репликацию (`STOP REPLICA`).
2. Определите точный LSN/GTID до ошибки.
3. Восстановите реплику до этой точки.
4. Увеличьте окно задержки или добавьте вторую отстающую реплику с большей задержкой.

### 5. pg_rewind завершается с ошибкой «target server must be shut down»

**Причина:** Целевой кластер (который будет демотирован до standby) не остановлен перед `pg_rewind`.

**Решение:**
```bash
# Остановка кластера перед rewinding
sudo systemctl stop postgresql@18-main
sudo -u postgres pg_rewind --target-pgdata=/var/lib/postgresql/18/main/data \
  --source-server="host=replica.internal port=5432 user=postgres"
```

### 6. Бэкап не расшифровывается после потери ключа

**Причина:** KEK/Master Key был утерян (файл keyring удалён, доступ к HSM утерян, пароль Vault забыт).

**Решение:**
- Восстановите keyring файл из резервной копии (если она была сделана).
- Восстановите доступ к HSM/KMS.
- Если KEK не восстановим — данные утеряны безвозвратно.

**Профилактика:**
- Храните резервные копии ключей в отдельном хранилище (не на том же сервере).
- Регулярно тестируйте восстановление.
- Используйте автоматическую ротацию ключей в KMS.

### 7. PITR останавливается: WAL-сегмент поврежден или утерян

**Причина:** Диск с архивом WAL вышел из строя, сегмент поврежден (битые сектора), или `archive_command` не выполнялся в течение всего окна отката.

**Диагностика:**
```sql
-- PostgreSQL: проверка последнего архивированного WAL
SELECT * FROM pg_stat_archiver;
-- Проверка, что pg_wal не пустой и нет ошибок
SELECT count(*) FROM pg_ls_waldir() WHERE failed = true;
```

**Решение:**
1. Если архив неполный — найдите последний валидный WAL-сегмент и выполните PITR до него.
2. Если WAL поврежден — используйте последнюю известную хорошую точку (бэкап + WAL до повреждения).
3. Настройте RAID с проверкой четности (RAID 6) или ZFS с checksumming для защиты от битых секторов.
4. Настройте `archive_command` с ретраями и мониторингом ошибок.

### 8. pg_rewind не работает при разных major версиях

**Причина:** `pg_rewind` работает только между кластерами одной major версии (например, 18 на 18). При апгрейде с 16 на 18 сначала выполните `pg_upgrade` или восстановите из бэкапа.

**Решение:**
- Используйте логическую репликацию или `pg_dump`/`pg_restore` для миграции между major версиями.
- Для развертывания нового кластера на новой версии используйте PITR на новый каталог, а не `pg_rewind`.

## SRE/DevOps: мониторинг, автоматизация и соответствие

### Ключевые метрики для мониторинга

**Статус транзакций и откатов:**
```sql
-- PostgreSQL: соотношение commit/rollback
SELECT sum(xact_commit) as commits, sum(xact_rollback) as rollbacks,
       round(sum(xact_rollback)::numeric / NULLIF(sum(xact_commit) + sum(xact_rollback), 0) * 100, 2) as rollback_rate
FROM pg_stat_database;

-- MySQL: InnoDB транзакции
SHOW ENGINE INNODB STATUS\G
```

**Поддержка AES-NI (если используется LUKS):**
```bash
# Быстрая проверка
grep -o "aes" /proc/cpuinfo | head -n 1
# → aes (если поддерживается)

# Бенчмарк производительности шифрования
cryptsetup benchmark
# → Algorithm | Key | Encryption | Decryption
# → aes-xts    256b      1.5 GB/s         1.5 GB/s
```

### SLO и автоматизация отката

**Rollback Readiness SLI:**
- **Определение:** Процент успешных тестовых восстановлений за квартал.
- **Цель (SLO):** 100% успешных тестов PITR и восстановления из снапшотов за квартал.
- **Алерт:** Если последний тестовый откат завершился ошибкой или был более 30 дней назад.

**Chaos Engineering:**
- Регулярно (раз в квартал) выполняйте учения по откату на staging: имитируйте `DROP TABLE`, сбой диска, обрыв репликации.
- Замеряйте реальное RTO и RPO, сравнивайте с SLA.
- Используйте результаты для актуализации runbook и тренировки дежурных команд.

### Compliance и аудит

Для соответствия PCI DSS, GDPR, HIPAA:

1. **Реестр точек восстановления:** ведите реестр всех созданных точек восстановления с указанием:
   - Имя точки и время создания
   - Связанная операция (майорное обновление, миграция)
   - Дата и результат тестирования восстановления

2. **Аудит операций отката:** логируйте все операции `ROLLBACK`, `pg_create_restore_point`, остановку репликации. Отправляйте логи в SIEM.

3. **Политика тестирования восстановления:**
   - PITR тестируется минимум раз в квартал
   - Восстановление из снапшотов — раз в квартал
   - Тестирование `pg_rewind` — раз в квартал
