# Шардирование

## Определения

**Шардирование (Sharding)** — метод горизонтального масштабирования базы данных, при котором данные разделяются на независимые части (шарды), размещаемые на разных физических серверах. Каждый шард является полноценной и независимой базой данных, содержащей подмножество общего набора данных.

- **Шард (Shard):** Узел или экземпляр базы данных, хранящий определенный сегмент данных.
- **Ключ шардирования (Shard Key):** Атрибут (поле), на основе которого принимается решение о распределении записи между шардами.
- **Маршрутизатор (Query Router):** Компонент системы, направляющий запросы приложения на нужный шард на основе ключа шардирования.

## Базовые концепции

### Шардирование vs. Партиционирование

| Характеристика | Партиционирование (Partitioning) | Шардирование (Sharding) |
| :--- | :--- | :--- |
| **Локация** | Внутри одного сервера/инстанса | На разных серверах/узлах |
| **Цель** | Упорядочивание данных, ускорение обслуживания | Масштабирование записи и объема данных |
| **Ресурсы** | Ограничены мощностью одного сервера | Растут линейно с добавлением узлов |
| **Сложность** | Поддерживается СУБД нативно (Local) | Требует внешней или встроенной оркестрации |

### Методы распределения данных

1. **Диапазонное (Range-based):** Данные распределяются по диапазонам ключа (например, `id` от 1 до 1 000 000 — шард 1, от 1 000 001 до 2 000 000 — шард 2).
   - *Плюс:* Эффективно для запросов по диапазону.
   - *Минус:* Проблема "горячих точек" (Hotspots) при неравномерной нагрузке.
2. **Хеширование (Hash-based):** Шард определяется как `hash(key) % N`.
   - *Плюс:* Равномерное распределение нагрузки.
   - *Минус:* Сложность изменения количества шардов (требует полного перераспределения данных).
3. **Согласованное хеширование (Consistent Hashing):** Улучшенный метод хеширования, минимизирующий объем переносимых данных при добавлении или удалении шардов. Используется в распределенных системах типа Cassandra или DynamoDB.
4. **Справочное (Directory-based):** Наличие отдельной таблицы или сервиса (Lookup table), где хранится соответствие ключа и конкретного шарда.

### Архитектура массивно-параллельной обработки (MPP)

**MPP (Massively Parallel Processing)** — архитектура, в которой запрос разбивается на части и выполняется одновременно на множестве независимых узлов (Shared-Nothing).

- **Координатор (Master/Coordinator):** Принимает запрос от клиента, строит план выполнения и распределяет задачи по сегментам.
- **Сегменты (Segments/Workers):** Хранят данные и выполняют вычисления.
- **Interconnect:** Высокоскоростная сеть для обмена данными между сегментами в процессе выполнения запроса (например, при операциях `JOIN`).

## Практические сценарии

### Выбор ключа шардирования

Правильный выбор ключа критичен для производительности системы. Примеры:
- **Пользовательские данные:** `user_id` — хороший выбор, если большинство запросов связаны с конкретным пользователем.
- **Временные ряды (Logs):** Шардирование по `timestamp` создаст "горячую точку" на последнем шарде. Лучше использовать комбинацию `tenant_id + hash(timestamp)`.

### Популярные реализации и инструменты

- **PostgreSQL:**
  - **Citus:** Расширение, превращающее Postgres в распределенную БД. Подробнее: **[Citus](../citus.md)**.
  - **Foreign Data Wrappers (FDW):** Базовый механизм для доступа к внешним таблицам.
- **MySQL:**
  - **Vitess:** Мощная система шардирования, используемая в YouTube и Slack.
  - **ProxySQL:** Умный прокси для маршрутизации запросов.
- **NoSQL:**
  - **MongoDB:** Нативная поддержка через Mongos и Shard Keys. Подробнее: **[MongoDB: Шардирование](../MongoDB/mongodb.md#шардирование-sharding)**.
  - **ClickHouse:** Движок `Distributed` для работы с кластером. Подробнее: **[ClickHouse: Шардирование](../ClickHouse/clickhouse.md#репликация-и-шардирование)**.

## Дополнительная информация

### Проблемы и эксплуатационные риски

1. **Кросс-шард запросы (Cross-shard joins):** Операции `JOIN` между таблицами на разных шардах крайне медленны. Решение — денормализация данных или репликация справочных таблиц (Reference tables) на все шарды.
2. **Распределенные транзакции:** Гарантировать **[ACID](./acid.md)** между узлами сложно. Часто используется двухфазный коммит (**2PC**) или переход к модели **BASE** (Eventual Consistency).
3. **Ре-шардирование (Re-sharding):** Процесс добавления шардов в работающую систему. Требует миграции огромных объемов данных и может вызвать деградацию производительности.
4. **Сложность обслуживания:** Резервное копирование, восстановление и миграции схемы (DDL) должны выполняться согласованно на всех узлах кластера.
