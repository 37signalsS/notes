## Шардирование (Sharding)

**Шардирование** (от англ. *shard* — осколок), или **горизонтальное партиционирование**, — это процесс разделения одной большой логической базы данных или таблицы на множество мелких, независимых и более управляемых частей, называемых **шардами**. Каждый шард может быть размещен на отдельном физическом сервере.

Это ключевая техника **горизонтального масштабирования (scaling out)**, в отличие от **вертикального масштабирования (scaling up)**, которое подразумевает увеличение мощности одного сервера (CPU, RAM).

> **Шардирование vs [Репликация](./replication.md):**
> - **[Репликация](./replication.md)** — это *копирование* одних и тех же данных на несколько серверов для отказоустойчивости и распределения нагрузки на чтение.
> - **Шардирование** — это *разделение* разных данных по разным серверам для распределения нагрузки на запись и для хранения огромных объемов данных.
> В реальных системах эти два подхода часто используются вместе: каждый шард дополнительно реплицируется.

---

### Зачем нужно шардирование?

Представьте, что у вас есть одна огромная таблица `payments` с миллиардами записей. Один сервер перестает справляться:

-   **Производительность записи:** Дисковая подсистема перегружена, вставка новых данных замедляется.
-   **Производительность чтения:** Индексы становятся огромными, и даже простые запросы занимают много времени.
-   **Объем данных:** Данные просто не помещаются на один сервер.

Вертикальное масштабирование (покупка более мощного сервера) — это дорого и имеет свои пределы. Шардирование решает эту проблему, распределяя данные и нагрузку по множеству менее мощных и более дешевых серверов.

---

### Ключевые компоненты

1.  **Шард (Shard):** Отдельная база данных, которая хранит часть общих данных.
2.  **Ключ шардирования (Shard Key):** Один или несколько столбцов в таблице, на основе значения которых система решает, на какой шард поместить данные. **Выбор правильного ключа — самое важное решение при шардировании.**
3.  **Роутер запросов (Query Router):** Приложение или прокси-сервер, который принимает запросы от клиента, анализирует их (на основе ключа шардирования) и направляет на нужный шард или шарды.

---

### Практический пример: Шардирование пользователей

**Сценарий:** Мы создаем социальную сеть с потенциально миллионами пользователей. Основная таблица — `users`.

**Проблема:** Таблица `users` растет, и один сервер не справляется с нагрузкой по чтению и записи профилей пользователей.

**Решение:** Шардировать таблицу `users` по 4 серверам (4 шарда).

#### Шаг 1: Выбор ключа шардирования

Идеальный ключ шардирования должен:
-   Присутствовать во всех запросах.
-   Равномерно распределять данные.

Столбец `user_id` отлично подходит на эту роль. Он уникален для каждого пользователя.

#### Шаг 2: Выбор логики распределения

Мы будем использовать простую хэш-функцию. Логика будет такой: `shard_id = user_id % 4`.

-   `user_id = 1` -> `1 % 4 = 1` -> **Shard 1**
-   `user_id = 2` -> `2 % 4 = 2` -> **Shard 2**
-   `user_id = 3` -> `3 % 4 = 3` -> **Shard 3**
-   `user_id = 4` -> `4 % 4 = 0` -> **Shard 0**
-   `user_id = 5` -> `5 % 4 = 1` -> **Shard 1**

**Визуализация:**

```
                               +----------------------+
                               | Роутер запросов      |
                               | (Query Router)       |
                               +-----------+----------+
                                           |
+------------------------------------------+------------------------------------------+
|                                          |                                          |
| shard_id = user_id % 4                   |                                          |
|                                          |                                          |
v                                          v                                          v
+----------+                             +----------+                             +----------+
| Shard 0  |                             | Shard 1  |                             | Shard N  |
|----------|                             |----------|                             |----------|
| user_id: |                             | user_id: |                             | user_id: |
| 4, 8, 12 |                             | 1, 5, 9  |                             | ...      |
+----------+                             +----------+                             +----------+

```

#### Шаг 3: Работа с данными

-   **Запись нового пользователя:** Когда регистрируется новый пользователь с `user_id = 123`, приложение (или роутер) вычисляет `123 % 4 = 3`. Запрос `INSERT` отправляется напрямую на **Shard 3**.

-   **Чтение профиля пользователя:** Когда нужно найти пользователя с `user_id = 123`, роутер снова вычисляет `123 % 4 = 3` и отправляет запрос `SELECT * FROM users WHERE user_id = 123` напрямую на **Shard 3**. Запрос не затрагивает остальные шарды, что делает его очень быстрым.

### Плюсы и минусы шардирования

**Плюсы:**
-   **Масштабируемость:** Можно добавлять новые серверы (шарды) по мере роста данных и нагрузки.
-   **Производительность:** Запросы обрабатываются параллельно на разных серверах, и каждый шард работает с меньшим объемом данных.
-   **Повышение доступности:** Сбой одного шарда влияет только на часть данных, а не на всю систему (остальные шарды остаются доступны).

**Минусы:**
-   **Сложность архитектуры:** Логика приложения усложняется, так как нужно знать, на какой шард отправлять запрос.
-   **Сложность запросов:** Запросы, которые затрагивают несколько шардов (например, посчитать всех пользователей), становятся очень сложными и медленными. Их нужно отправлять на все шарды и затем агрегировать результат.
-   **Ре-шардирование:** Добавление нового шарда в работающую систему — сложная и рискованная операция, требующая перераспределения данных.
-   **"Горячие точки" (Hotspots):** При неправильном выборе ключа шардирования один шард может получать непропорционально много нагрузки.
