# Шардирование

## Определения

**Шардирование (Sharding)** — метод горизонтального масштабирования (Scale-Out), при котором набор данных разбивается на части (шарды), распределяемые между независимыми узлами. Каждый шард является полноценным инстансом базы данных, хранящим только подмножество общего объема данных.

- **Шард (Shard):** Независимый узел (сервер или кластер репликации), содержащий часть данных системы.
- **Ключ шардирования (Shard Key):** Атрибут (поле), значение которого определяет, на какой шард попадет конкретная запись.
- **Масштабирование (Scaling):**
    - **Вертикальное (Scale-Up):** Увеличение ресурсов одного сервера (CPU, RAM). Имеет физический предел и высокую стоимость.
    - **Горизонтальное (Scale-Out):** Добавление новых серверов в систему. Шардирование — основной способ реализации Scale-Out для записи.
- **Глобальный вторичный индекс (GSI):** Индекс, который позволяет эффективно искать данные по полям, отличным от ключа шардирования, охватывая все шарды кластера.

## Основные концепции

### Шардирование vs. Партиционирование

| Характеристика | Партиционирование (Partitioning) | Шардирование (Sharding) |
| :--- | :--- | :--- |
| **Локация** | Внутри одного сервера/инстанса | На разных серверах/узлах |
| **Цель** | Упорядочивание данных, ускорение обслуживания | Масштабирование записи и объема данных |
| **Ресурсы** | Ограничены мощностью одного сервера | Растут линейно с добавлением узлов |
| **Сложность** | Поддерживается СУБД нативно (Local) | Требует внешней или встроенной оркестрации |

### Методы распределения данных

1. **Диапазонное (Range-based):** Данные делятся по диапазонам ключа (например, `A-M` — Шард 1, `N-Z` — Шард 2).
   - *Плюс:* Эффективно для поиска по диапазону.
   - *Минус:* Возникновение "горячих точек" (Hotspots) при неравномерном распределении ключей.
2. **Хеширование (Hash-based):** Шард определяется как `hash(key) % N`.
   - *Плюс:* Равномерное распределение нагрузки.
   - *Минус:* Добавление нового узла требует пересчета всех хешей и массовой миграции данных.
3. **Согласованное хеширование (Consistent Hashing):** Узлы и ключи располагаются на "кольце". При добавлении узла перемещается только малая часть данных. Используется в NoSQL (Cassandra, DynamoDB).
4. **Хэш-слоты (Hash Slots):** Логическое деление на фиксированное число слотов (например, 16384 в Redis Cluster). Слоты распределяются между физическими узлами, что упрощает масштабирование.

### Архитектурные уровни шардирования

- **На уровне приложения:** Приложение само решает, к какому инстансу БД обращаться. Дает полный контроль, но усложняет код и управление соединениями.
- **Прокси-слой:** Использование промежуточного слоя (Vitess, ProxySQL), который берет на себя маршрутизацию запросов. Прозрачно для приложения.
- **Нативное (Database-native):** СУБД сама управляет распределением данных (MongoDB, ClickHouse, Citus). Максимальное удобство, но риск vendor lock-in.

### Архитектура MPP (Massively Parallel Processing)

Применяется в аналитических БД (Greenplum, ClickHouse). Запрос разбивается на подзапросы, которые выполняются параллельно на всех узлах (Shared-Nothing), после чего координатор собирает результат.

## Практические сценарии

### Выбор ключа шардирования

Ключ должен обеспечивать равномерное распределение и минимизировать кросс-шард запросы.
- **SaaS приложения:** `tenant_id` (клиент) — идеальный ключ, так как данные разных клиентов обычно не пересекаются.
- **Социальные сети:** `user_id` — позволяет держать все посты и профиль пользователя на одном узле.
- **Логи (Time-series):** Шардирование только по `timestamp` приведет к тому, что все новые записи будут идти только в один (последний) шард. Рекомендуется составной ключ: `hash(service_id) + timestamp`.

### Популярные инструменты

- **PostgreSQL:**
  - **[Citus](../citus.md):** Превращает Postgres в распределенную БД через расширение.
  - **[Greenplum](../greenplum.md):** MPP-решение для Big Data на базе Postgres.
- **MySQL:**
  - **Vitess:** Оркестрация шардирования (используется в YouTube, Slack).
  - **ProxySQL:** Маршрутизатор с поддержкой Read/Write splitting и шардирования.
- **NoSQL:**
  - **[MongoDB](../MongoDB/mongodb.md):** Нативная поддержка через Mongos.
  - **[ClickHouse](../ClickHouse/clickhouse.md):** Движок `Distributed` для параллельных запросов.

## Дополнительная информация

### Вызовы и ограничения

1. **Кросс-шард JOIN:** Объединение таблиц, шардированных по разным ключам, требует пересылки огромных объемов данных между узлами. 
   - *Решение:* Репликация справочных таблиц (Reference tables) на все шарды.
2. **Горячий шард (Hot Shard):** Ситуация, когда из-за неудачного выбора ключа шардирования вся нагрузка ложится на один узел (например, если аккаунты всех знаменитостей попали на один шард). Необходимо выбирать ключ так, чтобы нагрузка распределялась равномерно.
3. **Распределенные транзакции:** Обеспечение **[ACID](./acid.md)** требует использования протоколов типа **2PC (Two-Phase Commit)**, что сильно снижает производительность. Альтернатива — переход к модели **BASE** и паттерну Saga.
4. **Ре-шардирование (Resharding):** Изменение количества шардов — тяжелая операция. Современные системы стремятся минимизировать простой (Online resharding).
    > **Важное правило:** Используйте шардирование как можно позже. Это мощный, но крайне сложный инструмент. После разделения данных на шарды восстановить их обратно в единую базу будет практически невозможно.
4. **Отказоустойчивость:** Каждый шард сам по себе должен быть отказоустойчивым (обычно через репликацию). Выход из строя одного шарда без реплики означает потерю части данных всей системы.
