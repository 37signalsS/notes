# CAP-теорема и PACELC

**Актуально для:** PostgreSQL 16 / MySQL 8.0 / MariaDB 11 / etcd 3.5 / Consul 1.18 / MongoDB 8.0 / Cassandra 5.x / ScyllaDB 2026.x / CockroachDB 23.x / Redis Cluster 7.2

## Определения

**CAP-теорема (теорема Брюэра)** — фундаментальный принцип проектирования распределенных систем, утверждающий, что при возникновении сетевого разделения (partition) распределенная система может обеспечить только две из трех характеристик: Согласованность, Доступность или Устойчивость к разделению. Поскольку в распределенных средах разделение сети неизбежно, выбор всегда сводится к компромиссу между **Согласованностью (C)** и **Доступностью (A)**.

- **Согласованность (Consistency):** Гарантия того, что каждый запрос на чтение возвращает самый свежий результат записи или ошибку. В контексте CAP это эквивалентно **Linearizability** (линеаризуемости) — система ведет себя так, будто существует только одна копия данных, и все операции выполняются атомарно.
- **Доступность (Availability):** Гарантия того, что каждый запрос (чтение или запись) к работающему узлу завершается успешным ответом (не ошибкой) в разумное время, даже если данные могут быть не самыми свежими.
- **Устойчивость к разделению (Partition Tolerance):** Способность системы продолжать функционирование при потере произвольного количества сообщений или разрыве связи между узлами.
- **PACELC:** Расширенная теорема, описывающая компромиссы системы не только во время сбоя (P), но и в штатном режиме (E — Else).
- **Линеаризуемость:** Свойство системы, при котором результат любой последовательности операций совпадает с результатом их выполнения в некотором последовательном порядке, причем порядок операций для каждого отдельного клиента сохраняется.

## Архитектура и принцип работы

### Механизмы CP-систем (Согласованность + Устойчивость)

**Протоколы консенсуса (Raft / Paxos):**
1. **Лидерство (Leader Lease):** Узел-лидер управляется через lease/TTL в распределенном хранилище координации (etcd/Consul). Лидер обязан регулярно обновлять TTL; при истечении срока — происходит добровольный step-down.
2. **Журнал replicated state machine (Raft Log):** Каждая запись проходит через AppendEntries → репликация на большинство (N/2+1) → фиксация (commit). Пока majority не подтвердило, запись не видна клиентам.
3. **Fencing (STONITH):** При потере кворума minority-сторона принудительно останавливает сервис (SIGSTOP / IPMI / fence_agent). Это предотвращает Split-brain.
4. **Стоимость:** Каждая запись требует минимум одного сетевого раунд-трипа до majority. При географическом распределении (регионы A и B на 100мс) минимальная задержка записи — 100мс + обрат.

### Механизмы AP-систем (Доступность + Устойчивость)

**Gossip-протоколы:**
1. **Peer-to-peer:** Нет центрального координатора. Каждый узел периодически обменивается состоянием с случайными соседями (интервал: 1-5 сек).
2. **Eventual Convergence:** Без guarantee времени сходимости. При высокой нагрузке или partition время неконсистентности может достигать минут.
3. **Vector Clocks / Version Vectors:** Каждая запись маркируется парой (node_id, counter). При слиянии версий (read repair / anti-entropy) конфликты разрешаются на основе логических часов.
4. **CRDT (Conflict-free Replicated Data Types):** Структуры данных, которые гарантируют сходимость без координации (G-Set, PN-Counter, OR-Set). Используются в ScyllaDB, Redis Enterprise.

### Модель кворума: математика операций

Условие $R + W > N$ обеспечивает **Quorum Consistency**:
- **W > N/2:** Запись подтверждается большинством, защита от потери данных при одновременном отказе minority.
- **R > N/2:** Чтение гарантированно пересекается с записью (обещают majority).
- **R + W > N:** Пересечение множеств чтения и записи не пусто — читатель обязательно увидит последнюю запись.

**Пример:** N=5, W=3, R=3. Запись фиксируется на 3 узлах. Чтение опрашивает 3 узлов. Хотя бы один узел общий — данные согласованы.

**Edge Cases модели:**
- **N четное:** При N=4 и разделении 2+2 кворум не формируется ни одной стороной. Используйте только нечетное N.
- **W=N:** Синхронная запись на все узлы. Потеря одного узла = недоступность. Не рекомендуется для HA.
- **W=1, R=1:** Асинхронная запись + чтение. Максимальная скорость, но $R+W = 2 \le N$ при N≥2 — классический AP, риск потери данных при падении Primary.

## Основные концепции

### Фундаментальный выбор: CP vs AP

Сетевые задержки и сбои (**P**) — это данность. Следовательно, архитектор распределенной системы обязан выбрать стратегию поведения при аварии:

1.  **CP (Consistency + Partition Tolerance):**
    *   **Приоритет:** Целостность данных.
    *   **Поведение:** Если узел теряет связь с кворумом (большинством), он прекращает обслуживание запросов, чтобы избежать **Split-brain** (рассинхронизации). Система становится недоступной до восстановления связи.
    *   **Механизмы:** Протоколы консенсуса (**Raft**, **Paxos**).
2.  **AP (Availability + Partition Tolerance):**
    *   **Приоритет:** Доступность сервиса.
    *   **Поведение:** Узлы продолжают отвечать на запросы даже в изоляции. Это неизбежно приводит к тому, что разные узлы хранят разные версии данных.
    *   **Механизмы:** **Gossip-протоколы**, **Vector Clocks**, **Conflict-free Replicated Data Types (CRDT)**.

### Математика кворума (Quorum)

Для управления балансом между C и A используется модель кворума:
$$R + W > N$$
Где:
- **N** — общее количество реплик.
- **W** — количество узлов для подтверждения записи.
- **R** — количество узлов для подтверждения чтения.

**Сценарии:**
- **Строгая согласованность:** $W > N/2$ и $R + W > N$. Чтение всегда видит последнюю запись.
- **Eventual Consistency (Согласованность в конечном счете):** $R + W \le N$. Позволяет читать устаревшие данные, но увеличивает пропускную способность.

### Теорема PACELC: Штатный режим

CAP не учитывает задержки (latency) в нормальном состоянии системы. **PACELC** закрывает этот пробел:
`If P (Partition) then (A or C) else (L or C)`
- Если есть разделение (**P**), выбираем между Доступностью (**A**) и Согласованностью (**C**).
- В штатном режиме (**E**lse), выбираем между Задержкой (**L**atency) и Согласованностью (**C**).

**Пример (Cassandra):** Типичная PA/EL система. При сбое доступна (AP), в норме оптимизирована под минимальную задержку (L), жертвуя строгой согласованностью (C) ради скорости.

## Практические сценарии

### Классификация систем по PACELC

| СУБД / Инструмент | PACELC-класс | Описание механизмов |
| :--- | :--- | :--- |
| **etcd / Consul** | **PC/EC** | Используют Raft. Строгая согласованность всегда. Жертвуют доступностью при потере кворума. |
| **MongoDB** | **PC/EL** | При `writeConcern: majority` — CP. В штатном режиме чтение с вторичных реплик дает Eventual Consistency, однако использование **Causal Consistency** (в рамках сессии) обеспечивает монотонное чтение и чтение собственных записей без потери производительности. |
| **Cassandra** | **PA/EL** | Оптимизирована для записи. Разрешение конфликтов через Last Write Wins (LWW). Высокая доступность за счет Gossip. |
| **ScyllaDB** | **PA/EL** | Совместима с Cassandra CQL. Та же модель: Gossip + LWW + tunable consistency. |
| **CockroachDB / Spanner** | **PC/EC** | NewSQL. Распределенные транзакции. Spanner использует TrueTime (атомные часы) для минимизации задержек при EC. |

### Настройка уровней согласованности (Примеры)

**1. Apache Cassandra / ScyllaDB (CQL):**
Подробное руководство по эксплуатации: **[Cassandra и ScyllaDB: Deep Dive](../cassandra_scylladb_guide.md)**. Обзор архитектуры: **[Архитектура Cassandra vs ScyllaDB](../cassandra-scylladb/architecture.md)**.
```sql
-- Установка кворума для текущей сессии (CP-поведение)
CONSISTENCY QUORUM;
SELECT * FROM users WHERE id = 1;

-- Максимальная скорость, минимальная гарантия (AP-поведение)
CONSISTENCY ONE;
```

**2. MongoDB (Node.js Driver):**
```javascript
// Гарантия CP: запись подтверждена большинством, чтение из большинства
const collection = db.collection('data');
await collection.insertOne({ item: 'test' }, { writeConcern: { w: 'majority' } });
const result = await collection.findOne({ item: 'test' }, { readConcern: { level: 'majority' } });
```

### Валидация конфигурации кворума

**1. Проверка кворума в etcd:**
```bash
# Статус кластера etcd
etcdctl endpoint health --cluster
etcdctl endpoint status --write-out=table

# Проверка leader
etcdctl endpoint status | grep -E "Leader|Member"
```

**2. Проверка кворума в MongoDB:**
```javascript
// Проверка состояния Replica Set
rs.status();

// Проверка writeConcern
db.getSiblingDB("admin").runCommand({ getCmdLineOpts: 1 });
```

**3. Проверка gossip-статуса в Cassandra:**
```bash
# Проверка статуса узлов
nodetool status

# Проверка gossip info
nodetool describecluster
```

## Поиск и устранение неисправностей (Troubleshooting)

### Проблема Split-Brain (Раскол мозга)
Возникает, когда два сегмента сети считают себя "главными" и принимают записи.
- **Диагностика:** Резкий рост ошибок репликации, расхождение контрольных сумм на узлах, наличие нескольких "Leader" в логах (для CP).
- **Предотвращение:** Использование нечетного количества узлов ($2n+1$) и строгого кворума.
- **Разрешение в AP:** Механизмы слияния (Merge) на основе меток времени или бизнес-логики.

### Проблема "Stale Reads" (Устаревшее чтение)
Клиент видит старые данные в AP-системе.
- **Причина:** Нарушение условия $R + W > N$ или высокая нагрузка, замедляющая репликацию.
- **Мониторинг:** Метрики `replication_lag` (в секундах или байтах).
- **Решение:** Увеличение уровня согласованности запроса (Read Repair) или привязка клиента к одной реплике (Sticky Sessions).

## Лучшие практики

1.  **Начинайте с CP:** Если бизнес-логика не терпит расхождений (финансы, инвентарь, платежи), выбирайте CP. Проще обработать ошибку "Сервис временно недоступен", чем восстанавливать поврежденные данные после Split-brain.
2.  **AP для UI и аналитики:** Если задержка в 100мс важнее, чем актуальность данных на ту же долю секунды (лента новостей, счетчик лайков), выбирайте AP.
3.  **Нечетное количество узлов:** Всегда используйте 3, 5 или 7 узлов для систем с консенсусом, чтобы минимизировать риск потери кворума.
4.  **TrueTime / NTP:** Для систем, полагающихся на время (LWW), критически важна синхронизация часов. Используйте `chrony` с мониторингом `offset`.
5.  **Мониторинг кворума:** Настройте алерты на `wsrep_cluster_size` (MariaDB/Galera), `rs.status().members` (MongoDB), `raft_status` (etcd). Падение ниже majority — инцидент.
6.  **Sticky Sessions с осторожностью:** Используйте привязку к Primary только для read-heavy AP-сценариев с writeConcern=majority. При потере лидера sticky-сессия становится источником ошибок.
7.  **Изоляция сети:** Выносите heartbeat/репликацию в отдельные VLAN. Это снижает риск partition из-за congested LAN.
8.  **Chaos Engineering:** Периодически тестируйте Split-Brain с помощью `tc` (Linux traffic control) или AWS Chaos Monkey. Проверяйте, что minority сторона действительно переходит в read-only.

## Ограничения и крайние случаи (Edge Cases)

- **CAP при N=1:** Для одного узла теорема формально тривиальна — P невозможно. Однако на практике даже single-node может столкнуться с сетевой изоляцией от клиентов (network partition между сервером и приложением).
- **Even-numbered clusters:** Кластер из 2 или 4 узлов без arbiter/observer не может обеспечить кворум при падении одного узла. Используйте нечетное число или добавьте голосующего без данных (Arbiter в MongoDB).
- **Latency-driven partitions:** При высокой RTT (>200мс между дата-центрами) лидер Raft теряет лизию из-за задержки heartbeat. Решение: geo-fencing + increased election timeout.
- **Sticky Sessions и AP:** Привязка клиента к одной реплике (`readPreference: primary`) в AP-системе не защищает от stale reads при failover, если writeConcern < majority.
- **Split-Brain при нечетном кворуме:** Даже при 3 узлах возможен transient primary, если minority сторона не поддерживает quorum read. В Raft только majority сторона может принимать решения.
- **CRDT и размер metadata:** Vector clocks и CRDT требуют хранения истории конфликтов. Для high-throughput систем (100K+ writes/sec) размер metadata может привести к OOM.
- **TrueTime и необходимость GPS:** Spanner требует GPS-приемников на каждом узле с отклонением <1мс. Отсутствие GPS = невозможность гарантировать EC без задержки.

## Дополнительная информация

### "C" в ACID vs "C" в CAP
Это разные понятия, часто вызывающие путаницу:
- **ACID Consistency:** Переход базы из одного валидного состояния в другое (соблюдение правил `UNIQUE`, `FOREIGN KEY`, `CHECK`).
- **CAP Consistency:** Атомарность операций в распределенной среде (все видят одно и то же одновременно).
