# CAP-теорема (Теорема Брюэра)

## Определения

**CAP-теорема** — это фундаментальный принцип в теории распределенных систем, который утверждает, что любая распределенная система хранения данных может одновременно обеспечивать не более **двух** из трех следующих гарантий:

1. **Согласованность данных (Consistency):** Все узлы кластера видят одни и те же данные в одно и то же время. Любое чтение возвращает самый последний записанный результат.
    * **Примечание:** Это сильная согласованность (strong consistency), которую следует отличать от согласованности в транзакциях **[ACID](./acid.md)**.
2. **Доступность (Availability):** Каждый запрос к системе получает корректный (не ошибочный) ответ, даже если он не содержит самые последние данные.
3. **Устойчивость к разделению (Partition Tolerance):** Система продолжает функционировать в случае возникновения разрыва сетевой связи (partition) между узлами.

## Основные концепции

### Компромисс между согласованностью и доступностью

В распределенной системе, где узлы общаются по сети, сетевые сбои неизбежны. Поэтому на практике **устойчивость к разделению (P) является обязательным свойством** любой распределенной СУБД.

Поскольку от свойства (P) отказаться нельзя, реальный выбор при проектировании сводится к компромиссу между согласованностью (C) и доступностью (A). Ключевым механизмом реализации этого выбора является **[репликация](./replication.md)**.

* **Выбор в пользу согласованности (CP-система):** При сетевом разделении система выбирает согласованность, жертвуя доступностью. Узлы, которые не могут синхронизироваться, перестают отвечать на запросы во избежание рассинхронизации данных.
* **Выбор в пользу доступности (AP-система):** При сетевом разделении система выбирает доступность, жертвуя сильной согласованностью. Узлы продолжают отвечать на запросы, даже если возвращаемые данные устарели.

### Доказательство теоремы

Рассмотрим систему из двух узлов (`Node 1` и `Node 2`), содержащих идентичные данные (`value = 10`).

**Сценарий:**

1. **Сетевой разрыв (P):** Связь между узлами потеряна.
2. **Запрос на запись:** Клиент отправляет на `Node 1` команду `UPDATE value = 20`.

В этот момент узел `Node 1` оказывается перед выбором:

* **Вариант 1: Согласованность (C) ценой доступности (A)**
    Чтобы гарантировать идентичность данных на обоих узлах, `Node 1` должен дождаться подтверждения от `Node 2`. Так как сеть разорвана, `Node 1` вынужден отказать клиенту в выполнении запроса. Система становится **недоступной** для записи. Это поведение **CP-системы**.

* **Вариант 2: Доступность (A) ценой согласованности (C)**
    `Node 1` принимает запрос, обновляет значение локально (`value = 20`) и отвечает клиенту "OK". В этот момент данные на `Node 1` (`value = 20`) и `Node 2` (`value = 10`) расходятся. Система остается доступной, но жертвует сильной согласованностью. Это поведение **AP-системы**.

Этот пример наглядно показывает, что при возникновении сетевого разделения невозможно одновременно удовлетворить требования и согласованности, и доступности.

## Практические сценарии

### CP-системы (Consistency + Partition Tolerance)

В случае сетевого разделения система отдает приоритет **согласованности**.

* **Поведение:** Узел, потерявший связь с кластером, блокирует операции записи (и часто чтения), пока связь не восстановится. Как правило, используется **синхронная репликация**.
* **Примеры СУБД:** MongoDB, Redis, HBase.
* **Сценарии:** Финансовые транзакции, биллинговые системы, системы управления конфигурациями (etcd, Consul).

### AP-системы (Availability + Partition Tolerance)

В случае сетевого разделения система отдает приоритет **доступности**.

* **Поведение:** Все узлы продолжают обрабатывать запросы, даже будучи изолированными. Система стремится к **согласованности в конечном счете (Eventual Consistency)** — состоянию, в котором данные на всех узлах станут идентичными через некоторое время после восстановления связи.
* **Механизм:** Обычно используется **асинхронная репликация**. Master-узел подтверждает запись сразу после локального завершения, не дожидаясь реплик.

**Схема асинхронной репликации:**

```text
  Клиент                    Master                      Replica
    | -- 1. WRITE ---------> |                           |
    | <------- 2. OK -------- |                           |
    |                        | -- 3. REPLICATE ------> |
    |                        |                           |
... задержка репликации (replication lag) ...
    |                        | <------ 4. ACK ---------- |
```

* **Примеры СУБД:** Apache Cassandra, CouchDB, DynamoDB.
* **Сценарии:** Социальные сети (ленты новостей, лайки), системы сбора метрик, IoT-платформы.

### Особенности реляционных СУБД (MySQL, PostgreSQL)

Одиночный экземпляр классической РСУБД формально является **CA-системой** (Consistency + Availability), так как не является распределенной системой и не сталкивается с проблемой (P) внутри себя.

В кластерных конфигурациях (Galera Cluster, Patroni) такие системы обычно настраиваются как **CP**, обеспечивая строгую согласованность через кворумы и синхронную репликацию. Если кластер теряет кворум, он блокирует запись для защиты целостности данных.
