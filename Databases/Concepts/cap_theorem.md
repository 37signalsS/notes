# CAP-теорема и PACELC

## Определения

**CAP-теорема (теорема Брюэра)** — фундаментальный принцип проектирования распределенных систем, который утверждает, что при сетевом разделении (partition) система может обеспечить только одну из двух гарантий: **Согласованность** или **Доступность**.

- **Согласованность (Consistency):** Каждый запрос на чтение возвращает самый свежий результат записи или ошибку. В распределенных системах это означает **Linearizability** (линеаризуемость) — систему, которая ведет себя как одна копия данных.
    - *Важно:* Не путать с Consistency в **[ACID](./acid.md)** (соблюдение инвариантов).
- **Доступность (Availability):** Каждый запрос (чтение или запись) к рабочему узлу завершается успешно и без ошибок, даже если данные не являются самыми свежими.
- **Устойчивость к разделению (Partition Tolerance):** Способность системы продолжать работу при потере связи между узлами или задержках пакетов.
- **PACELC:** Расширение CAP, описывающее поведение системы не только при сбоях (P), но и в штатном режиме (E).
- **Кворум (Quorum):** Минимальное количество узлов, которые должны подтвердить операцию для её успешного завершения.

## Основные концепции

### Компромисс CP vs AP

В распределенной системе сетевые сбои (**P**) неизбежны. Выбор стоит между поведением системы *во время аварии*:

- **CP (Consistency + Partition Tolerance):** Система выбирает согласованность. Если узел не может подтвердить актуальность данных (потерял связь с большинством), он возвращает ошибку. Система становится недоступной до восстановления связи.
    - *Механизмы:* Алгоритмы консенсуса (**Raft**, **Paxos**).
- **AP (Availability + Partition Tolerance):** Система выбирает доступность. Узлы отвечают на запросы, даже если они изолированы. Это приводит к конфликтам данных и требует механизмов разрешения (например, Last Write Wins).
    - *Механизмы:* **Gossip-протоколы**, **Vector Clocks**.

### Математика кворума

Для обеспечения согласованности в распределенных системах используется формула кворума:
$$R + W > N$$
Где:
- **N** — общее количество реплик.
- **W** — количество узлов, подтверждающих запись.
- **R** — количество узлов, участвующих в чтении.

Если условие выполняется, чтение гарантированно пересекается с записью, и клиент видит актуальные данные. Если $R + W \le N$, система работает в режиме **Eventual Consistency** (согласованность в конечном счете).

### Теорема PACELC: работа в штатном режиме

CAP описывает только поведение при сбое. **PACELC** добавляет выбор в нормальном состоянии:
**P** (Partition) ? (**A** vs **C**) : (**L** vs **C**)
- Если есть разделение (**P**), выбираем между Доступностью (**A**) и Согласованностью (**C**).
- Иначе (**E**lse), выбираем между Задержкой (**L**atency) и Согласованностью (**C**).

Это объясняет, почему системы типа **PA/EL** (Cassandra) популярны: они доступны при сбоях и очень быстры в норме, жертвуя строгой согласованностью.

## Практические сценарии

### Классификация систем по PACELC

| СУБД | Тип (P/E) | Особенности |
| :--- | :--- | :--- |
| **etcd / Consul** | **PC/EC** | Строгий Raft. Всегда согласованны, но медленнее на запись. |
| **MongoDB** | **PC/EL** | По умолчанию CP при сбое. В норме можно читать с реплик (L). |
| **Cassandra** | **PA/EL** | AP при сбое. В норме оптимизирована под минимальную задержку. |
| **DynamoDB** | **PA/EL** | Высокая доступность и скорость. Eventual Consistency по умолчанию. |
| **Spanner** | **PC/EC*** | NewSQL. Использует TrueTime (атомные часы) для обеспечения внешней согласованности при высокой доступности. |

### Настройка уровней согласованности

Многие системы позволяют менять тип на лету через параметры запроса:
- **Cassandra:** `CONSISTENCY QUORUM` (делает систему CP) vs `CONSISTENCY ONE` (делает систему AP).
- **MongoDB:** `readConcern: majority` и `writeConcern: majority` обеспечивают поведение CP.

## Дополнительная информация

### Harvest и Yield

Альтернативный взгляд на CAP (авторы Fox и Brewer):
- **Yield:** Процент запросов, завершившихся успешно (аналог Availability).
- **Harvest:** Полнота ответа (например, поиск по 90% данных вместо 100%).
В некоторых системах (поиск, аналитика) выгоднее вернуть частичный результат быстро (высокий Yield, низкий Harvest), чем ждать все узлы.
