# CAP-теорема (Теорема Брюэра)

## 1. Определения

**CAP-теорема** — это фундаментальный принцип в теории распределенных систем, который утверждает, что любая распределенная система хранения данных может одновременно обеспечивать не более **двух** из трех следующих гарантий:

1.  **Consistency (Согласованность данных):** Все узлы кластера видят одни и те же данные в одно и то же время. Любое чтение возвращает самый последний записанный результат.
    > **Важно:** Это сильная согласованность (strong consistency), отличающаяся от согласованности в транзакциях [ACID](./acid.md).
2.  **Availability (Доступность):** Каждый запрос к системе получает корректный (не ошибочный) ответ, даже если он не содержит самые последние данные.
3.  **Partition Tolerance (Устойчивость к разделению):** Система продолжает функционировать в случае возникновения разрыва сетевой связи (partition) между узлами.

## 2. Основные концепции

### Компромисс C vs. A

В распределенной системе, где узлы общаются по сети, сбои считаются неизбежными. Поэтому на практике **устойчивость к разделению (P) не является опцией, а является обязательным свойством** любой серьезной распределенной СУБД.

Поскольку от (P) отказаться нельзя, реальный выбор при проектировании сводится к компромиссу между согласованностью (C) и доступностью (A). Ключевым механизмом, который реализует этот выбор на практике, является **[репликация](./replication.md)**.

- **Выбор C (CP-система):** В случае сетевого разделения система выбирает согласованность, жертвуя доступностью. Узлы, которые не могут синхронизироваться, перестают отвечать на запросы, чтобы избежать рассинхронизации данных.
- **Выбор A (AP-система):** В случае сетевого разделения система выбирает доступность, жертвуя сильной согласованностью. Узлы продолжают отвечать на запросы, даже если возвращают устаревшие данные.

## 3. Практические сценарии: CP vs AP системы

### CP-системы (Consistency + Partition Tolerance)
В случае сетевого разделения система выбирает **согласованность**.

- **Поведение:** Чтобы избежать рассинхронизации, узел, который не может связаться с другими, становится недоступным для записи (а иногда и для чтения), пока связь не восстановится. Используется **синхронная репликация**.
- **Примеры СУБД:** MongoDB, Redis, HBase.
- **Сценарии:** Финансовые системы, биллинг — везде, где целостность данных является абсолютным приоритетом.

### AP-системы (Availability + Partition Tolerance)
В случае сетевого разделения система выбирает **доступность**.

> Отсутствие согласованности данных не влияет на работу узлов.

**Схема процесса (асинхронная репликация):**
```text
  Клиент                    Master                      Replica
    | -- 1. WRITE ---------> |                           |
    | <------- 2. OK -------- |                           |
    |                        | -- 3. REPLICATE ------> |
    |                        |                           |
... через некоторое время (replication lag) ...
    |                        | <------ 4. ACK ---------- |
```

*   **Поведение:** Все узлы продолжают принимать запросы на чтение и запись. Данные могут быть временно рассинхронизированы между разделами сети. После восстановления связи система стремится к **"согласованности в конечном счете" (eventual consistency)**, синхронизируя данные в фоновом режиме.
*   **Примеры СУБД:** Apache Cassandra, CouchDB, ScyllaDB, DynamoDB.
*   **Сценарии:** Социальные сети, системы аналитики, IoT-платформы — там, где временное отображение устаревших данных менее критично, чем отказ в обслуживании.

### А что же MySQL?

Классический **одиночный экземпляр MySQL** является **CA-системой** (Consistency + Availability). Он не обладает устойчивостью к разделению по своей природе, так как не является изначально распределенной системой.

Однако в кластерных конфигурациях (например, MySQL Cluster, Percona XtraDB Cluster, Galera Cluster) MySQL пытается балансировать между гарантиями. В зависимости от конфигурации и типа кластера, он может склоняться к CP или AP поведению, но чаще всего стремится к сильной согласованности (CP), жертвуя доступностью в случае серьезных сетевых сбоев в кластере.

## 4. Продвинутые детали: Доказательство теоремы

Рассмотрим гипотетическую систему, которая пытается быть одновременно C, A и P.

**Сценарий:**
1.  **Состояние:** Два узла, `Node 1` и `Node 2`, содержат одинаковые данные (`value = 10`).
2.  **Разрыв сети (P):** Узлы больше не могут общаться друг с другом.
3.  **Запрос:** Клиент отправляет на `Node 1` команду на изменение данных (`UPDATE table SET value = 20`).

Теперь у `Node 1` есть выбор, который доказывает теорему:

-   **Выбрать Согласованность (C) -> пожертвовать Доступностью (A):**
    Чтобы гарантировать, что данные останутся одинаковыми (`value = 20` на обоих узлах), `Node 1` должен реплицировать изменение на `Node 2`. Но сеть разорвана. Чтобы не нарушить согласованность, `Node 1` **обязан отказать в выполнении запроса**. В этот момент система становится **недоступной** для записи. Это поведение **CP-системы**.

-   **Выбрать Доступность (A) -> пожертвовать Согласованностью (C):**
    Чтобы оставаться доступным, `Node 1` принимает запрос и изменяет данные у себя локально (`value = 20`). Он немедленно отправляет клиенту ответ "OK". В этот момент данные на `Node 1` (`value = 20`) и `Node 2` (`value = 10`) становятся **несогласованными**. Система остается доступной, но жертвует сильной согласованностью. Это поведение **AP-системы**.

Таким образом, невозможно одновременно удовлетворить все три требования. При возникновении сетевого разделения (P) система вынуждена выбирать между согласованностью (C) и доступностью (A).
