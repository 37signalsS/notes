# Ключевые концепции производительности баз данных

**Актуально для:** PostgreSQL 18, PostgreSQL 17, PostgreSQL 16, MySQL 8.4 LTS, MySQL 8.0, MariaDB 11.x, SQLite 3.45+, Linux 6.x

## Определения

**Производительность базы данных** — комплексная характеристика, отражающая способность системы обрабатывать запросы с заданной скоростью (Latency) и в заданном объеме (Throughput) при эффективном использовании ресурсов (CPU, RAM, I/O).

**Время отклика (Latency)** — суммарное время выполнения запроса.
- **Service Time:** время непосредственной обработки запроса процессором или диском.
- **Wait Time:** время нахождения запроса в очередях (на CPU, на ввод-вывод, ожидание блокировок).
- **Перцентили (P95, P99):** критически важные метрики для выявления «длинного хвоста» задержек, которые игнорируются средним арифметическим.

**Пропускная способность (Throughput)** — количество операций (транзакций, запросов), выполняемых системой за единицу времени. Измеряется в **TPS** (Transactions Per Second) или **QPS** (Queries Per Second).

**IOPS (Input/Output Operations Per Second)** — количество операций ввода-вывода в секунду.
- **Random IOPS:** критичны для OLTP-нагрузок (поиск по индексам).
- **Sequential Throughput:** критичен для OLAP-нагрузок (сканирование таблиц, бэкапы).

**Параллелизм (Concurrency)** — количество запросов, одновременно находящихся в обработке. Согласно **Закону Литтла**: `Concurrency = Throughput × Latency`.

**Утилизация (Utilization)** — процент времени, в течение которого ресурс был занят.
**Насыщение (Saturation)** — мера «очереди» к ресурсу. Если утилизация 100%, каждое новое поступление увеличивает очередь и Latency экспоненциально.

## Основные концепции

### Фундаментальные законы

1.  **Закон Литтла:** позволяет рассчитать необходимый уровень параллелизма (например, размер Connection Pool).
    - **Формула:** `Concurrency = Throughput × Latency`.
    - **Практическое применение:** если СУБД выдерживает 100 TPS при средней задержке 50 мс, то в среднем в системе находится 5 одновременных запросов. Если приложение открывает 50 соединений, 45 из них простаивают впустую, потребляя память.
2.  **Универсальный закон масштабируемости (USL):** учитывает не только закон Амдала (ограничение последовательными участками), но и затраты на взаимодействие (Coherency). Помогает понять, почему при добавлении ядер производительность БД может начать *падать* из-за конкуренции за общие структуры данных.
    - **Формула:** `C(p) = p / (1 + σ × (p - 1) + κ × p × (p - 1))`, где `σ` — коэффициент contention, `κ` — коэффициент coherency.
    - **Практическое применение:** при планировании апгрейда железа постройте scalability curve и определите точку насыщения. USL показывает, что добавление ядер бесконечно не работает: asymptote = `1/σ`.

### Иерархия памяти и задержек

Скорость доступа к данным определяет производительность:
- **L1/L2/L3 Кэш:** наносекунды. БД стремится держать горячие структуры данных (индексные узлы) максимально близко к CPU.
- **RAM (Buffer Pool):** десятки наносекунд. Основная рабочая область БД.
    - **Huge Pages:** использование страниц памяти по 2МБ вместо 4КБ снижает нагрузку на **TLB** и экономит до 10-15% CPU на операциях с памятью.
    - **NUMA:** в многопроцессорных системах важно, чтобы процесс БД работал с «локальной» памятью, иначе задержки доступа растут непредсказуемо.
    - **Persistent Memory (NVDIMM):** для PostgreSQL 16+ поддерживается как табличное пространство. Задержка доступа близка к RAM, но данные сохраняются при отключении питания. Используется для WAL или часто обновляемых таблиц.
- **Хранилище (NVMe/SSD/HDD):** от сотен микросекунд до десятков миллисекунд. Главное узкое место большинства СУБД.
    - **NVMe:** последовательная пропускная способность до 7 ГБ/с, случайное чтение 4K — до 1M IOPS. Для production СУБД рекомендуется минимально 2 диска NVMe в RAID 1 (данные) + отдельный NVMe для WAL.
    - **SATA SSD:** последовательная пропускная способность до 550 МБ/с, случайное чтение 4K — до 100K IOPS. Допустимо для небольших инстансов.
    - **HDD:** последовательная пропускная способность до 250 МБ/с, случайное чтение 4K — до 200 IOPS. Используется только для архивов и бэкапов.

### Управление соединениями (Connection Management)

Создание сессии — тяжелая операция (fork процесса в Postgres или создание потока в MySQL + авторизация).
- **Connection Storm:** ситуация, когда сотни приложений одновременно пытаются подключиться, вызывая лавинообразный рост нагрузки на CPU и задержек.
- **Решение:** Внешние пулеры (PgBouncer, Odyssey) или встроенные механизмы переиспользования соединений.

### Компромисс ACID: Durability vs Performance

Соблюдение **[ACID](./acid.md)** требует записи на диск (`fsync`) при каждом `COMMIT`.
- **Проблема:** `fsync` крайне медленный.
- **Решение:** **[Write-Ahead Logging (WAL)](./write_ahead_log.md)**. БД сначала пишет изменения в последовательный лог (Sequential Write), а затем асинхронно обновляет файлы данных. Это превращает случайную запись в быструю последовательную.
- **Group Commit:** объединение нескольких транзакций для одного вызова `fsync`.

### Управление конкурентностью и блокировками

1.  **MVCC (Multi-Version Concurrency Control):** позволяет читающим процессам не блокировать пишущие (и наоборот). Каждая транзакция видит «снимок» данных на момент своего начала.
2.  **Блокировки (Locks):** высокоуровневые объекты для защиты логики (строки, таблицы).
3.  **Защелки (Latches):** низкоуровневые примитивы синхронизации в памяти (например, для защиты страницы в Buffer Pool). Конкуренция за защелки (Latch Contention) — частая причина деградации на многоядерных системах.
4.  **Deadlock (Взаимная блокировка):** когда две транзакции ожидают ресурсы друг друга. СУБД автоматически детектирует и откатывает одну из транзакций. Приложения должны быть готовы к повтору (`Serialization Error` в PostgreSQL, `ER_LOCK_DEADLOCK` в MySQL).
5.  **Lock Wait Timeout:** если транзакция ждет блокировку дольше порога, СУБД прерывает её. В PostgreSQL — параметр `lock_timeout`, в MySQL — `innodb_lock_wait_timeout` (строковые блокировки) и `lock_wait_timeout` (метаданные; по умолчанию 1 год, см. [metadata_locking.md](./metadata_locking.md)).

### Чекпоинты (Checkpoints)

Чекпоинт — процесс сброса грязных страниц из RAM на диск. Неправильная настройка вызывает всплески Latency.
- **Проблема:** слишком частые чекпоинты создают пиковые нагрузки на диск.
- **PostgreSQL:** `checkpoint_timeout` (рекомендуется 15 мин), `max_wal_size` (рекомендуется 4-8 ГБ), `checkpoint_completion_target` (0.9 для распределения записи во времени).
- **MySQL/InnoDB:** `innodb_flush_log_at_trx_commit = 1` (полная durability) vs `= 2` (групповая запись, риск потери 1 секунды данных при сбое). `sync_binlog` регулирует частоту сброса binlog.

### Оптимизация запросов

**Cost-based Optimizer (CBO)** оценивает стоимость различных планов выполнения.
- **Статистика:** точность CBO напрямую зависит от свежести статистики распределения значений в столбцах.
- **План-кэширование:** повторное использование планов для идентичных запросов экономит CPU.

## Методология оптимизации (USE Method)

Для эффективной диагностики используйте метод **USE (Utilization, Saturation, Errors)** для каждого ресурса:

| Ресурс | Утилизация (Utilization) | Насыщение (Saturation) | Ошибки (Errors) |
| :--- | :--- | :--- | :--- |
| **CPU** | % загрузки ядер | Длина очереди (Load Average) | Перегрев, троттлинг |
| **RAM** | Свободная память, Кэш | Инсивность Swap, OOM | Ошибки ECC |
| **Disk** | % времени занятости | Длина очереди (avgqu-sz) | Тайм-ауты, битые блоки |
| **Network** | Полоса пропускания | Переполнения буферов | Потери пакетов (retrans) |

### SLO и SLI для производительности СУБД

| SLI (Service Level Indicator) | Целевое значение (SLO) | Измерение |
| :--- | :--- | :--- |
| **P99 Latency** (SELECT по PK) | < 5 мс | `pg_stat_statements.mean_exec_time` (P99) или `performance_schema` |
| **P99 Latency** (сложный JOIN) | < 100 мс | `pg_stat_statements` / `sys.analysis` |
| **TPS (Throughput)** | Базовый уровень не падает ниже 80% при пике | `pg_stat_database` или `information_schema.global_status` |
| **Cache Hit Ratio** | > 99% для OLTP | `blks_hit / (blks_hit + blks_read)` в PostgreSQL |
| **Connection Utilization** | < 70% от пула | `pg_stat_activity` / `SHOW STATUS LIKE 'Threads_connected'` |
| **Deadlock Frequency** | < 1 в час | Логи СУБД (`deadlock detected`) |
| **Autovacuum lag** | `n_dead_tup` < 10K на таблицу | `pg_stat_user_tables` |
| **Replication Lag** | < 1 сек для синхронной реплики | `pg_stat_replication` / `SHOW SLAVE STATUS` |

## Практические сценарии и настройка

### Оптимизация дискового ввода-вывода

#### Сценарий 1: Устранение Double Buffering (PostgreSQL)
Postgres хранит данные в `shared_buffers`, но также полагается на `Page Cache` ОС.
- **Проблема:** одни и те же данные дублируются в RAM, уменьшая эффективный объем кэша.
- **Настройка:** установите `shared_buffers` в 25% от RAM, остальное оставьте под кэш ОС. Для Linux настройте `vm.swappiness = 1` и `vm.dirty_background_ratio = 5-10`, чтобы ОС агрессивнее сбрасывала грязные страницы на диск.

#### Сценарий 2: Прямой ввод-вывод (MySQL/InnoDB)
InnoDB эффективнее управляет кэшем самостоятельно.
- **Настройка:** используйте `innodb_flush_method = O_DIRECT`. Это заставляет БД обходить системный кэш, предотвращая двойное кэширование и снижая нагрузку на CPU ОС.

### Настройка Huge Pages (Linux)
Для СУБД с большим Buffer Pool (десятки ГБ) настройка Huge Pages обязательна.

**Шаги реализации:**
1. Проверить поддержку: `grep Huge /proc/meminfo`.
2. Рассчитать количество страниц (размер Buffer Pool / 2МБ).
3. Зарезервировать страницы: `sysctl -w vm.nr_hugepages=XXXX`.
4. Включить в БД: `huge_pages = try` (PostgreSQL) или `large-pages` (MySQL).

### Устранение Bloat (MVCC)
Накопление старых версий строк из-за долгих транзакций или редкой очистки.
- **Симптомы:** размер таблицы растет, хотя количество данных — нет; Index Scan становится медленным.
- **Решение:** мониторинг `n_dead_tup` в Postgres. Настройка агрессивного `autovacuum` для часто обновляемых таблиц.

## Мониторинг и диагностика

### Инструментарий ОС

- **`iostat -xz 1`:** детальная статистика дисков (ищите рост `%util` и `await`).
- **`vmstat 1`:** общая картина системы (очереди CPU `r`, контекстные переключения `cs`).
- **`perf top`:** поиск функций ядра или БД, потребляющих больше всего CPU.

### Профилирование БД

- **PostgreSQL:** расширение `pg_stat_statements` (обязательно для поиска "Top SQL").
- **MySQL:** `Performance Schema` и `Slow Query Log`.
- **Explain Analyze:** единственный способ понять, *почему* запрос медленный в реальности (сравнение планируемой и реальной стоимости).

### Верификация производительности диска (fio)
Перед развертыванием БД проверьте, соответствуют ли диски заявленным характеристикам.

```bash
# Тест случайного чтения (имитация работы с индексами)
fio --name=randread --ioengine=libaio --iodepth=64 --rw=randread --bs=4k --direct=1 --size=4G --numjobs=4 --runtime=60 --group_reporting
```

## Устранение неисправностей (Troubleshooting)

### Методология диагностики (RED Method для запросов)

Параллельно с USE для ресурсов применяйте RED к потоку запросов:
- **Rate (R):** TPS/QPS на запрос.
- **Errors (E):** процент ошибок (сбой подключения, таймаут, deadlock).
- **Duration (D):** P50/P95/P99 Latency.

Если Rate упал, а Errors и Duration выросли — проблема в ресурсах (примените USE). Если Rate вырос, а Duration остался прежним — это нормальная масштабируемость.

### Паттерны неисправностей

| Паттерн | Возможная причина | Первый шаг диагностики |
| :--- | :--- | :--- |
| **Низкий CPU, высокий Latency, БД «жива»** | Исчерпание пула подключений | `SELECT count(*) FROM pg_stat_activity` — проверить занятость пула |
| **Высокий CPU, низкий Throughput** | Плохой план (Missing Index), Context Switching | `EXPLAIN ANALYZE` запроса, `pidstat` |
| **Низкий CPU, высокий Latency** | Блокировки, медленный Диск, Сеть | Проверка `pg_stat_activity` (wait_event) |
| **Всплески Latency каждые N минут** | Сброс грязных страниц (Checkpointing) | Анализ логов БД на предмет `checkpoints occur too frequently` |
| **Деградация после добавления RAM** | Неверная настройка Huge Pages или NUMA | `numastat`, проверка `vm.nr_hugepages` |
| **Снижение Cache Hit Ratio** | Слишком маленький `shared_buffers` или запрос вытесняет горячие данные | `pg_statio_*` / `SHOW ENGINE INNODB STATUS` |
| **Частые чекпоинты** | `checkpoint_timeout` слишком мал или `max_wal_size` превышен | Анализ логов: `checkpoints occur too frequently` |
| **Latch Contention** | Многопоточный доступ к одному индексу или буферу | `perf top`, `pg_stat_activity` (wait_event = `LWLock`) |
| **Ошибки ECC Memory** | Сбой аппаратной памяти | `dmesg | grep -i ECC`, проверка `edac` модуля |

### Планирование пропускной способности (Capacity Planning)

Прежде чем менять железо, определите текущую утилизацию и прогноз роста.

**Шаги:**
1.  **Соберите baseline:** запустите `pgbench` или `sysbench` в течение 24-48 часов под реальную нагрузку. Зафиксируйте P95/P99 Latency, TPS, IOPS.
2.  **Определите утилизацию:** если CPU > 70% в пике или Disk Queue > 2 — вы близки к насыщению.
3.  **Прогноз роста:** если данные растут на 50% в год, а TPS растет пропорционально — через год система окажется на пределе.
4.  **Моделирование USL:** постройте scalability curve. Определите, при какой нагрузке Latency начнет расти экспоненциально.
5.  **План апгрейда:** определите RTO (Recovery Time Objective). Если RTO = 4 часа, вам нужен горячий standby, а не просто бэкап.

### Operational Runbook: Анализ производительности

Используйте этот чек-лист при деградации производительности:

1.  **Быстрая проверка (5 минут):**
    - `top`/`htop`: какой процесс грузит CPU?
    - `iostat -xz 1`: какой диск перегружен?
    - `vmstat 1`: есть ли swap, высокий `wa`?
    - `pg_stat_activity`: нет ли зависших транзакций?

2.  **Диагностика (30 минут):**
    - `pg_stat_statements`: топ-5 самых медленных запросов.
    - `EXPLAIN ANALYZE` на проблемный запрос.
    - `pg_locks` / `SHOW ENGINE INNODB STATUS`: нет ли дедлоков?
    - Проверка `shared_buffers` hit ratio.

3.  **Корректировка (1-2 часа):**
    - Добавьте недостающий индекс.
    - Увеличьте `work_mem` для сортировок.
    - Увеличьте `shared_buffers` при низком cache hit ratio.

4.  **Валидация:**
    - Запустите нагрузочный тест и сравните с baseline.
    - Настройте алерт на повтор проблемы.

### Исчерпание пула подключений (Connection Pool Exhaustion)

Приложение держит к базе не отдельное соединение на каждый запрос, а заранее открытый набор — пул. Пул конечен, и если все подключения заняты, следующий запрос не идёт в базу вообще, а встаёт в очередь за свободным. При этом снаружи всё выглядит как просто медленная база, хотя сама база при этом может работать вполне штатно.

Увидев исчерпанный пул, первым делом хочется его увеличить. Иногда это действительно помогает, но часто это сделает ситуацию ещё хуже: каждое подключение к базе стоит ей памяти и процессорного времени, а число одновременных запросов, которые она реально способна тянуть, ограничено её ядрами и дисками. Расширив пул, вы не увеличиваете пропускную способность базы — вы просто переносите очередь: до этого запросы ждали снаружи, а теперь ждут внутри базы и мешают друг другу.

**Диагностика:**

```sql
-- PostgreSQL: количество активных и ожидающих соединений
SELECT count(*) AS total,
       count(*) FILTER (WHERE state = 'active') AS active,
       count(*) FILTER (WHERE wait_event IS NOT NULL) AS waiting
FROM pg_stat_activity;

-- MySQL: текущие соединения и лимит
SHOW STATUS LIKE 'Threads_connected';
SHOW VARIABLES LIKE 'max_connections';
```

**Решение:** не увеличивайте пул, пока не убедитесь, что запросы быстро завершаются. Сначала оптимизируйте медленные запросы и найдите застрявшие транзакции. Первая очередь в базе — это не проблема пула, а проблема запросов.

Подробнее о пулах соединений: [Connection Pooling](../../Networking/Concepts/connection_pooling.md).

## Лучшие практики

1.  **Индексируйте с умом:** лишние индексы замедляют вставку и увеличивают Bloat. Используйте `UNIQUE` и `NOT NULL` там, где возможно — это улучшает статистику и планы запросов.
2.  **Используйте Connection Pooling:** никогда не подключайтесь к БД напрямую из PHP/Python скриптов без прослойки. Для веб-приложений используйте PgBouncer в режиме transaction pooling.
3.  **Следите за типами данных:** использование `UUID` (случайных строк) в качестве первичных ключей убивает производительность B-Tree индексов из-за фрагментации. Для суррогатных ключей используйте `BIGSERIAL` / `BIGINT AUTO_INCREMENT`.
4.  **Автоматизируйте статистику:** убедитесь, что задачи `ANALYZE` работают регулярно. `default_statistics_target` повышает точность планов для сложных распределений.
5.  **Настройте `shared_buffers` под нагрузку:** 25% RAM — стартовая точка для mixed workload. Для read-heavy (OLAP) увеличьте до 40% и проверьте, что hit ratio > 99%.
6.  **Разделите данные и WAL на разные диски:** исключите конкуренцию за IOPS между последовательной записью WAL и случайной записью данных.
7.  **Настройте агрессивный `autovacuum` для часто обновляемых таблиц:** `autovacuum_vacuum_scale_factor = 0.01` (1%) и `autovacuum_vacuum_threshold = 50` для таблиц с высокой частотой обновлений.
8.  **Используйте покрывающие индексы (Covering Indexes):** если запрос полностью удовлетворяется индексом (Index Only Scan), СУБД не обращается к таблице. Это в 10-100 раз быстрее.
9.  **Ограничьте размеры транзакций:** транзакции дольше 5 минут мешают VACUUM и ротации WAL. Разбивайте массовые операции на батчи.
10. **Настройте мониторинг USE-метрик:** алертируйте на Load Average > 2 × vCPU, Disk Queue > 2, Cache Hit Ratio < 99%, Deadlocks > 1/час.
11. **Тестируйте изменения на staging:** перед применением `ALTER TABLE` или изменения конфигурации на production, проверьте на копии данных с реальной нагрузкой.
12. **Используйте Prepared Statements:** они снижают overhead на планирование и защищают от SQL-инъекций. В PostgreSQL — `PREPARE`, в MySQL — бинарные протоколы с prepared statements.
13. **Управляйте версиями запросов:** при изменении логики запроса не переиспользуйте старые планы. В PostgreSQL 12+ используйте `plan_cache_mode = force_custom_plan` для параметризованных запросов с неравномерными распределениями.
14. **Мониторинг NUMA:** на многосокетных серверах убедитесь, что процесс БД привязан к локальной памяти. В Linux используйте `numactl --cpunodebind=0 --membind=0` или настройку `numa_node` в systemd.
