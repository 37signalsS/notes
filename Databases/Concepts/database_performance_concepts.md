# Ключевые концепции производительности баз данных

## Определения

**Производительность базы данных** — комплексная характеристика, отражающая способность системы обрабатывать запросы с заданной скоростью (Latency) и в заданном объеме (Throughput) при эффективном использовании ресурсов (CPU, RAM, I/O).

**Время отклика (Latency)** — временной интервал между отправкой запроса и получением ответа. Важно анализировать не только среднее значение, но и процентили (P95, P99) для выявления "хвостов" задержек.

**Пропускная способность (Throughput)** — количество операций (транзакций, запросов), выполняемых системой за единицу времени (TPS, RPS, QPS).

**IOPS (Input/Output Operations Per Second)** — количество операций ввода-вывода в секунду. Критичная метрика для дисковой подсистемы, особенно при случайном доступе.

**Параллелизм (Concurrency)** — количество одновременно обрабатываемых запросов. Согласно **Закону Литтла**: `Concurrency = Throughput × Latency`.

**Утилизация (Utilization)** — степень загрузки ресурса (в процентах). При приближении утилизации к 100% задержки растут экспоненциально (теория очередей).

## Основные концепции

### Иерархия памяти и задержек

Производительность БД напрямую зависит от того, где находятся данные. Разница в скорости доступа между слоями составляет порядки:
- **L1/L2/L3 Кэш процессора:** наносекунды.
- **Оперативная память (RAM):** десятки наносекунд. Важна поддержка **Huge Pages** для снижения накладных расходов на TLB (Translation Lookaside Buffer).
- **NUMA (Non-Uniform Memory Access):** В многопроцессорных системах доступ к "своей" памяти быстрее. Неправильная настройка NUMA приводит к внезапным скачкам Latency.
- **NVMe SSD:** сотни микросекунд. Обладают высокой степенью параллелизма.
- **HDD:** десятки миллисекунд. Медленный случайный доступ из-за движения головок.

### Управление соединениями (Connection Management)

Создание нового соединения — дорогая операция (TCP handshake + Auth + выделение памяти в БД).
- **Проблема:** "Шторм соединений" (Connection Storm) может обрушить БД.
- **Решение:** Использование **Connection Pool** (HikariCP на стороне приложения, PgBouncer/Odyssey на стороне БД). Это позволяет переиспользовать существующие сессии.

### Компромисс между надежностью и скоростью

Соблюдение свойства **Durability** в **[ACID](./acid.md)** требует подтверждения записи на физический диск через системный вызов `fsync`.

- **Проблема:** `fsync` — блокирующая и медленная операция. Она ограничивает частоту фиксации транзакций.
- **Решение:** Использование **[журнала предзаписи (WAL)](./write_ahead_log.md)** позволяет превратить случайную запись данных в последовательную запись лога, что значительно быстрее.

### Управление блокировками (Locking)

Для обеспечения целостности СУБД используют механизмы синхронизации:
- **Locks (Блокировки):** Высокоуровневые объекты (транзакционные). Защищают данные (строки, таблицы).
- **Latches (Защелки):** Легковесные низкоуровневые объекты. Защищают структуры данных в памяти (страницы в Buffer Pool).
- **Lock Contention:** Ситуация, когда множество процессов ждут одну блокировку, что приводит к деградации производительности.

### Планы выполнения (Execution Plans)

СУБД строит план выполнения с помощью Оптимизатора.
- **Cost-based Optimizer (CBO):** Выбирает путь исполнения на основе статистики. Важно поддерживать статистику в актуальном состоянии (`ANALYZE`).
- **План-кэширование (Plan Caching):** Сохранение готовых планов для повторяющихся запросов с целью экономии CPU на этапе парсинга и оптимизации.
- **Методы доступа:** `Index Scan` vs `Sequential Scan`.

## Практические сценарии

### Оптимизация дискового ввода-вывода

#### Сценарий 1: Облачные диски и IOPS Burst

В облачных средах диски часто имеют лимиты IOPS.
- **Credits/Burst:** Возможность кратковременного превышения базовой скорости. При исчерпании "кредитов" производительность резко падает.
- **Решение:** Мониторинг метрик `BurstBalance`. Использование Provisioned IOPS для критических нагрузок.

#### Сценарий 2: Direct I/O vs OS Cache

- **PostgreSQL:** Полагается на системный кэш страниц (**Page Cache**). Возможна проблема двойного кэширования (Double Buffering). Требуется настройка `shared_buffers` (обычно 25% RAM).
- **MySQL (InnoDB):** Сама управляет кэшем через `innodb_buffer_pool_size` (до 80% RAM), часто используя Direct I/O для минимизации влияния ОС.

### Многоверсионность (MVCC) и Bloat

- **Проблема:** При `UPDATE` старая версия строки остается на диске. Накопление "мертвых" строк (**Bloat**) замедляет чтение.
- **Решение:** Регулярная очистка (`VACUUM` в Postgres, автоматическая очистка в InnoDB).

### Узкие места CPU и переключение контекста

При слишком большом количестве активных соединений (`Max Connections`) процессор тратит больше времени на переключение между задачами (**Context Switching**), чем на саму работу.
- **SRE-заметка:** Если `Load Average` значительно выше числа ядер, а CPU утилизация не 100%, скорее всего, система страдает от конкуренции за ресурсы или блокировок.

## Настройка и мониторинг

### Ключевые метрики (Золотые сигналы)

1. **Latency:** Время выполнения запросов (по типам: Read/Write).
2. **Throughput:** Количество транзакций в секунду (TPS).
3. **Errors:** Процент неуспешных запросов (Deadlocks, Timeouts).
4. **Saturation:** Длина очередей, Disk Queue Length, CPU Wait.

### Инструментарий

- **`iostat` / `iotop`:** Диагностика нагрузки на уровне ОС.
- **`pg_stat_statements` / `Slow Query Log`:** Поиск тяжелых запросов.
- **`fio`:** Синтетические тесты дисков.
- **`perf` / `ebpf`:** Глубокий анализ системных вызовов и задержек ядра Linux.
