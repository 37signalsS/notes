# Ключевые концепции производительности баз данных

## Определения

**Производительность базы данных** — комплексная характеристика, отражающая способность системы обрабатывать запросы с заданной скоростью (Latency) и в заданном объеме (Throughput) при эффективном использовании ресурсов (CPU, RAM, I/O).

**Время отклика (Latency)** — временной интервал между отправкой запроса и получением ответа. Важно анализировать не только среднее значение, но и процентили (P95, P99) для выявления "хвостов" задержек.

**Пропускная способность (Throughput)** — количество операций (транзакций, запросов), выполняемых системой за единицу времени (TPS, RPS, QPS).

**IOPS (Input/Output Operations Per Second)** — количество операций ввода-вывода в секунду. Критичная метрика для дисковой подсистемы, особенно при случайном доступе.

## Основные концепции

### Иерархия памяти и задержек

Производительность БД напрямую зависит от того, где находятся данные. Разница в скорости доступа между слоями составляет порядки:
- **L1/L2/L3 Кэш процессора:** наносекунды.
- **Оперативная память (RAM):** десятки наносекунд.
- **NVMe SSD:** сотни микросекунд. Обладают высокой степенью параллелизма.
- **SATA SSD:** единицы миллисекунд.
- **HDD:** десятки миллисекунд. Медленный случайный доступ из-за движения головок.

### Компромисс между надежностью и скоростью

Соблюдение свойства **Durability** в **[ACID](./acid.md)** требует подтверждения записи на физический диск через системный вызов `fsync`.

- **Проблема:** `fsync` — блокирующая и медленная операция. Она ограничивает частоту фиксации транзакций.
- **Решение:** Использование **[журнала предзаписи (WAL)](./write_ahead_log.md)** позволяет превратить случайную запись данных в последовательную запись лога, что значительно быстрее.

### Планы выполнения (Execution Plans)

СУБД не просто выполняет SQL-запрос, а строит план его выполнения с помощью Оптимизатора.
- **Cost-based Optimizer (CBO):** Выбирает путь исполнения на основе статистики (размер таблиц, распределение значений).
- **Методы доступа:** `Index Scan` (быстро для выборок) vs `Sequential Scan` (быстро для чтения всей таблицы).
- **Анализ:** Команда `EXPLAIN ANALYZE` позволяет увидеть, почему запрос работает медленно.

## Практические сценарии

### Оптимизация дискового ввода-вывода

#### Сценарий 1: Облачные диски и IOPS Burst

В облачных средах (AWS, GCP, Azure) диски часто имеют лимиты IOPS.
- **Credits/Burst:** Возможность кратковременного превышения базовой скорости. При исчерпании "кредитов" производительность резко падает.
- **Решение:** Мониторинг метрик `BurstBalance`. Для высоконагруженных БД использовать диски с гарантированным (provisioned) IOPS.

#### Сценарий 2: Прямая запись (Direct I/O) vs OS Cache

Некоторые СУБД (например, Oracle) предпочитают работать с диском напрямую, минуя кэш ОС, чтобы избежать двойного кэширования (Double Buffering). Другие (PostgreSQL) полагаются на системный кэш страниц (Page Cache).
- **SRE-заметка:** При настройке памяти БД важно оставлять достаточно RAM для кэша ОС.

### Влияние многоверсионности (MVCC)

Большинство современных СУБД используют MVCC для обеспечения изоляции.
- **Bloat (раздувание):** Устаревшие версии строк занимают место в файлах данных до тех пор, пока не будут вычищены (`VACUUM` в Postgres).
- **Влияние:** Накопление мусора замедляет сканирование таблиц и индексов.

## Настройка и мониторинг

### Ключевые параметры СУБД

- **Buffer Pool:** Область памяти для кэширования страниц данных (`shared_buffers` в Postgres, `innodb_buffer_pool_size` в MySQL).
- **WAL Buffers:** Кэш для записей лога перед сбросом на диск.
- **Max Connections:** Ограничение числа соединений. Избыток соединений ведет к конкуренции за CPU и блокировкам (Lock Contention).

### Инструментарий

- **`iostat` / `iotop`:** Диагностика нагрузки на уровне ОС. См. **[Диагностика дискового узкого места](../../db_disk_bottleneck_troubleshooting.md)**.
- **`pg_stat_statements` / `Slow Query Log`:** Поиск тяжелых запросов внутри СУБД.
- **`fio`:** Синтетические тесты производительности дисков перед деплоем БД.
