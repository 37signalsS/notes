# Database CI/CD: Автоматизация миграций и GitOps для БД

**Актуально для:** PostgreSQL 11+, MySQL 8.0.12+, MariaDB 10.3+

## Определения

- **Database CI/CD** — комплексная практика автоматизации жизненного цикла изменений схемы и данных базы данных, полностью интегрированная в общий конвейер поставки программного обеспечения (CI/CD).
- **GitOps для БД (Database-as-Code)** — подход, при котором эталонное состояние базы данных описывается декларативно в системе контроля версий (Git). Инструменты автоматизации (Atlas, Bytebase) непрерывно синхронизируют это состояние с реальными инстансами.
- **Дрейф схемы (Migration Drift)** — критическое расхождение между фактическим состоянием схемы в БД и тем, что зафиксировано в коде миграций.
- **Детекция дрейфа (Drift Detection)** — автоматизированный процесс проверки, выявляющий ручные или несанкционированные изменения схемы, сделанные в обход стандартного пайплайна.
- **Статический анализ SQL (SQL Linting)** — автоматизированная проверка скриптов миграции на наличие синтаксических ошибок, опасных (блокирующих) операций или нарушения корпоративных стандартов до их применения.
- **Zero-downtime Migration** — изменение структуры или данных БД, не требующее остановки приложения и обеспечивающее полную совместимость со старыми (N) и новыми (N+1) версиями кода.
- **Эфемерная БД (Ephemeral Database)** — временный экземпляр СУБД (обычно в Docker/Testcontainers), создаваемый "на лету" в пайплайне для безопасного тестирования миграций.
- **Императивный подход (Change-based)** — парадигма, при которой фокус на последовательности переходов: разработчик вручную пишет скрипты (`V1__init.sql`, `V2__add_column.sql`), а инструмент (Flyway, Liquibase) применяет их линейно. Инструмент хранит контрольные суммы и историю применённых версий в `flyway_schema_history` или `DATABASECHANGELOG`.
- **Декларативный подход (State-based)** — парадигма, при которой фокус на конечном состоянии: разработчик описывает целевую схему (HCL, SQL, YAML), а инструмент (Atlas) сам вычисляет план `ALTER` команд. Подходит для SRE-команд, где схема меняется часто и распределена между несколькими сервисами.
- **Fix-Forward (Ролл-вперёд)** — стратегия исправления ошибок миграции путём создания новой компенсирующей миграции (`V(N+1)__fix.sql`) вместо отката. Сохраняет линейную историю и исключает риск потери данных при `undo` на Production.

## Основные концепции

### Жизненный цикл Database CI/CD

Database CI/CD базируется на принципе «Shift Left»: любые потенциальные проблемы со схемой должны обнаруживаться на этапе разработки или Code Review, а не во время деплоя на Production.

Полный цикл автоматизации включает 6 ключевых этапов:

1.  **Lint (Shift Left):** Статический анализ SQL через `sqlfluff`, `squawk` или `atlas lint`. Обнаруживает блокирующие операции (`DROP`, `ALTER` без `CONCURRENTLY`).
2.  **Эфемерное тестирование (Dry-run):** Применение миграций на временной БД (Testcontainers / Docker Compose). **Зачем:** Проверка корректности SQL-скриптов в реальной среде, выявление конфликтов имен и типов.
3.  **Контроль дрейфа (Drift Check):** Сравнение текущего состояния целевой БД с мастер-веткой перед применением изменений. **Зачем:** Гарантия того, что база находится в ожидаемом состоянии.
4.  **DBA Review (опционально):** Ручное подтверждение для критичных изменений (таблицы > 10 ГБ, `DROP COLUMN`, переименование). **Зачем:** Снижение Blast Radius для миграций с высоким риском.
5.  **Применение (Deployment):** Выполнение миграций (Flyway, Liquibase, Atlas) через Kubernetes Jobs или CLI-агенты. Рекомендуется выполнять *до* деплоя приложения (Pre-deployment).
6.  **Верификация:** Автоматическая проверка целостности схемы, наличия индексов и актуальности статистики после завершения деплоя. Промоутинг миграций через окружения: `dev → staging → prod` с gate-проверками на каждом этапе.

### Предпосылки и подготовка

Перед запуском миграции в Production выполните стандартный чек-лист. Детальный разбор параметров сессии, проверки индексов и оценки объёма данных см. в **[Безопасные массовые операции](../safe_large_scale_data_modification.md#pre-flight-проверки)**.

Кросс-функциональные проверки:
- **Резервная копия:** Актуальность и восстанавливаемость. Для PostgreSQL выполните `pg_basebackup` или snapshot storage; для MySQL — `xtrabackup --backup`. Проверьте целостность через `pg_checksum` / `XtraBackup --prepare`.
- **Лаг репликации:** Должен быть ниже порога алертинга (обычно < 30с для Streaming Replication / < 10с для синхронной репликации). Если лаг близок к `wal_keep_size` — отложите миграцию.
- **Connection Pool:** Пулы приложения (PgBouncer/ProxySQL) должны иметь запас ёмкости на время миграции. При `ACCESS EXCLUSIVE` пул опустошается, пока DDL не завершится, и новые запросы приложения получают отказы.
- **Активные транзакции:** Должны отсутствовать долгоживущие транзакции в статусе `idle in transaction`. Они удерживают `AccessShareLock` и могут превратить кратковременную DDL-блокировку в каскадный deadlock.

Change Management и Runbook:
- **Change Advisory Board (CAB):** Миграции, затрагивающие таблицы > 10 ГБ или содержащие `DROP/RENAME`, требуют утверждения. Документируйте окно деплоя, критерии отката и контакты on-call.
- **Maintenance Window:** Для миграций с ожидаемым простем > 30с согласуйте окно с бизнесом. Для zero-downtime — фиксируйте время cutover в runbook.
- **Runbook:** Для каждой миграции подготовьте документ с пошаговой инструкцией, командами проверки, критериями успешного завершения и планом отката с триггерами.

## Продвинутые паттерны (Advanced Patterns)

### 1. Zero-downtime в распределенных системах

В высоконагруженных системах с множеством реплик и регионов простого применения миграций недостаточно.

- **Версионирование схемы (Schema Versioning):** Приложение поддерживает работу с двумя версиями схемы одновременно через слой доступа к данным (DAL) или Feature Flags.
- **Blue-Green Database Deployment:** Поднятие нового инстанса БД с новой схемой, настройка логической репликации с текущего мастера и переключение трафика после синхронизации.
- **Traffic Shadowing:** Проверка производительности новой схемы путем дублирования («отзеркаливания») реальных запросов на тестовую БД в режиме Read-only.
*Подробные шаги описаны в [Архитектурных сценариях миграции](scenarios.md).*

### 2. Автоматический аудит SQL (SQL Lint) в CI

Линтинг позволяет программно запретить опасные операции.
- **Squawk (PostgreSQL):** Специализированный линтер, выявляющий `ALTER TABLE` без `CONCURRENTLY`, добавление `NOT NULL` без `DEFAULT` и другие блокирующие операции.
- **Atlas Lint:** Анализирует план миграции, используя `dev-url` (эфемерную БД), и предупреждает о разрушительных изменениях (например, `DROP COLUMN`).
- **sqlfluff:** Кроссплатформенный линтер с поддержкой PostgreSQL, MySQL, Snowflake. Интегрируется в pre-commit hooks и CI пайплайны.

### 3. Предотвращение блокировок таблиц (Table Locks Prevention)

| Операция | Риск | Безопасная альтернатива |
| :--- | :--- | :--- |
| `ADD COLUMN` | Блокировка всей таблицы на запись | Postgres 11+: мгновенно. Старые версии: `DEFAULT NULL` → заполнение батчами. |
| `CREATE INDEX` | Полная блокировка `WRITE` операций | `CREATE INDEX CONCURRENTLY` (Postgres) / `ALGORITHM=INPLACE` (MySQL). |
| `ADD FOREIGN KEY` | Долгая проверка всех строк таблицы | `ADD CONSTRAINT ... NOT VALID` → `VALIDATE CONSTRAINT` вторым шагом. |
| `DROP COLUMN` | Поломка кода старой версии (N-1) | Сначала скрыть колонку в коде/DAL, удалять только в следующей итерации CI. |
| `ALTER TYPE` | Полная перезапись таблицы | Использование паттерна Expand-Contract с триггерами синхронизации. |

## Глубокое погружение: Flyway и Liquibase (Императивный подход)

Императивные инструменты фокусируются на последовательности изменений (Change-based).

### Практические руководства
Для детального изучения настройки, CI/CD пайплайнов и стратегий отката используйте специализированные руководства:
*   **[Flyway: Практическое руководство по эксплуатации](./tools/flyway_practical_guide.md)** — SQL-first подход, версионирование и работа с Undo-скриптами.
*   **[Liquibase: Практическое руководство по эксплуатации](./tools/liquibase_practical_guide.md)** — Enterprise-стандарт с поддержкой YAML/XML и мощными механизмами откатов.

### Интеграция в пайплайн (CLI)

Рекомендуется упаковывать скрипты миграций в Docker-образ и запускать его как **Kubernetes Job** с аннотациями Helm Hooks (`pre-upgrade`).

**Типовой запуск Flyway в CI/CD:**
```bash
# 1. Проверка текущего состояния (информационно)
flyway info -url=$DB_URL -user=$DB_USER -password=$DB_PASS

# 2. Валидация контрольных сумм (предотвращение изменения уже примененных файлов)
flyway validate -url=$DB_URL

# 3. Применение новых миграций
flyway migrate -url=$DB_URL
```

### Обработка откатов и ошибок

1.  **Fix-Forward (Рекомендуется):** Вместо отката создается новая миграция `V(N+1)`, которая исправляет ошибку или возвращает логику. Это сохраняет чистую линейную историю.
2.  **Flyway Undo (Teams/Enterprise):** Использование скриптов `U__filename.sql`. В CI требует ручного подтверждения; автоматический запуск Undo на Production крайне опасен.
3.  **Liquibase Rollback:** Использует теги `<rollback>` в XML/YAML. Команда `liquibase rollback --tag=release-1.0` возвращает БД к указанной метке.
4.  **Транзакционный DDL:** В PostgreSQL почти все DDL-команды атомарны. При сбое миграции база автоматически откатывается к состоянию `V(N-1)`.

### Проверка дрейфа схемы в императивном подходе

Flyway не видит ручных изменений в БД.
- **Решение:** Дополнить пайплайн шагом `liquibase diff` или `atlas schema inspect` для сравнения Production с "золотым" образом схемы в Git.

## Современный GitOps: Atlas и Bytebase (Декларативный подход)

Фокус на желаемом конечном состоянии схемы (State-based).

### Atlas (Schema-as-Code)

Atlas позволяет описывать схему на HCL или SQL и автоматически вычислять план перехода от текущего состояния к желаемому.

**GitOps Workflow в GitHub Actions:**
```yaml
name: Atlas CI/CD
on:
  pull_request:
    paths: ['migrations/**']
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ariga/setup-atlas@v0
      - name: Run Atlas Lint
        uses: ariga/atlas-action/migrate/lint@v1
        with:
          dir: 'file://migrations'
          dev-url: 'docker://postgres/15/dev' # Эфемерная БД для анализа
```
**Преимущество:** Использование `dev-url` позволяет Atlas прогнать миграции в Docker, сравнить результат с желаемым состоянием и выдать детальный отчет о безопасности (например, предупредить о неявном `DROP`).

### Bytebase (Database DevOps Portal)

Платформа с UI, превращающая управление БД в процесс, аналогичный GitLab/GitHub Flow.

**GitOps Workflow (GitLab CI):**
1.  **SQL Review:** При создании Merge Request Bytebase через API проверяет SQL на соответствие политикам (SQL Review Policy).
2.  **Rollout:** После слияния в `main` создается Issue на деплой. Возможна настройка ручного подтверждения (Approval) от DBA.
3.  **Multi-tenant Rollout:** Одновременное применение изменений к сотням шардов/баз с визуальным контролем прогресса.
4.  **Drift Detection:** Bytebase периодически опрашивает БД и подсвечивает расхождения в UI в реальном времени.

## Обработка дрейфа схемы (Drift Management)

Дрейф — главный риск для автоматизации, приводящий к сбоям миграций из-за неожиданного состояния объектов.

| Метод обнаружения | Инструмент | Описание |
| :--- | :--- | :--- |
| **Validate (Checksum)** | Flyway | Проверяет, не изменились ли *тексты* уже примененных миграций. |
| **Snapshot Diff** | Liquibase / Atlas | Сравнивает структуру реальной БД с сохраненным слепком (JSON/SQL). |
| **Full Inspection** | Bytebase | Постоянный мониторинг всех объектов БД и автоматическое создание алертов при расхождении с репозиторием. |
| **Schema Diff в CI** | `atlas schema diff` / `liquibase diff` | П comparaет текущее состояние production с "золотым" образом в Git при каждом пуше в `main`. |

**Стратегия исправления:**
1.  **Reconcile (Согласование):** Создать миграцию, которая отменяет ручные изменения или фиксирует их в коде.
2.  **Baseline (Точка отсчета):** Если ручное изменение легитимно, обновить метаданные инструмента (например, `flyway baseline`), чтобы синхронизировать историю.

## Интеграция со стратегиями деплоя

- **Rolling Update:** Требует обратной совместимости схемы (паттерн Expand-Contract); старые поды должны работать с новой схемой.
- **Blue/Green:** Миграции применяются к Green-инстансу до cutover; откат сводится к переключению трафика обратно на Blue.
- **Canary:** Миграция применяется к production перед canary-деплоем; мониторинг latency/errors на миграцию.
- **Feature Flags:** Связывание миграций с флагами позволяет постепенно включать новую логику после применения DDL.

## Ветвление и миграции

- **Trunk-Based Development:** Высокая частота merge → требуется timestamp-based versioning (`YYYYMMDDHHMMSS`); приоритет — roll-forward.
- **Git Flow:** Долгоживущие ветки → требуется sequential versioning (`V1`, `V2`); возможен tag-based rollback на release-ветках.

## Мультитенантность и мульти-БД

- **resource_group (GitLab CI):** Последовательное выполнение миграций для shared-database, предотвращает параллельные блокировки.
- **Matrix builds (GitHub Actions):** Параллельные миграции для независимых баз данных (per-tenant shards).
- **Ordering:** Миграции с FK между базами должны выполняться через `needs` / `dependencies`.

## Практические сценарии

### Сценарий 1: Интеграция Atlas Lint в CI (Shift Left)

#### Предпосылки
- Репозиторий с миграциями.
- Доступ CI-раннера к Docker.

#### Пошаговая инструкция
1. Настроить шаг линтинга в пайплайне (см. пример YAML выше).
2. Подключить `dev-url` (база той же версии, что и Production).

#### Валидация
- При добавлении опасной миграции (например, `TRUNCATE TABLE`) пайплайн должен упасть с детальным описанием риска.
- Atlas выдаёт список разрушительных операций и их severity (LOW/MEDIUM/HIGH).

#### Устранение неисправностей
- **Ошибка `dev-url`:** Проверьте доступность Docker-демона. **Решение:** Использовать `services` в GitLab CI или `docker-runner` в GitHub Actions.

### Сценарий 2: Деплой через Kubernetes Job (Pre-upgrade)

#### Предпосылки
- Образ приложения содержит CLI миграций и скрипты.
- Настроен RBAC для создания Jobs в K8s.

#### Пошаговая инструкция
1. Использовать Helm Chart с `pre-upgrade` хуком.
2. Настроить `backoffLimit` для предотвращения бесконечных перезапусков при ошибках SQL.

#### Валидация
- Проверка статуса Job: `kubectl get pods -l job-name=...`. Статус должен быть `Completed`.
- Helm upgrade продолжится только после успешного завершения Job.

#### Устранение неисправностей
- **Job висит (CrashLoopBackOff):** Ошибка в SQL или таймаут подключения. **Решение:** Проверить логи пода и сетевую связность до БД.

### Сценарий 3: Approval Gate и Change Management

#### Предпосылки
- Требуется DBA approval для production-миграций.
- Интеграция с Change Management (CAB).

#### GitLab CI: manual approval
```yaml
approve_prod_migration:
  stage: deploy
  script:
    - echo "Waiting for DBA approval..."
  when: manual
  allow_failure: false
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

migrate_prod:
  stage: deploy
  script:
    - flyway -url=$PROD_DB_URL migrate
  when: manual
  needs:
    - approve_prod_migration
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

#### GitHub Actions: environment protection rule
```yaml
migrate-prod:
  needs: validate
  runs-on: self-hosted
  environment:
    name: production
    url: https://app.example.com
  steps:
    - uses: actions/checkout@v4
    - uses: liquibase/setup-liquibase@v1
    - run: liquibase --changeLogFile=db/changelog/master.xml update
```

#### Валидация
- Миграция не начинается до ручного подтверждения.
- DBA получает уведомление в чат/email через CI-платформу.

### Сценарий 4: Тестирование миграций в CI/CD (Testcontainers)

#### Предпосылки
- Требуется гарантия, что миграции не ломают приложение.
- Требуется проверка обратной совместимости.

#### Паттерн: Testcontainers + Flyway
```yaml
test_migrations:
  stage: test
  image: golang:1.23
  services:
    - postgres:15
  script:
    - go test -v -run TestMigrations ./db/
```

#### Дополнительные проверки
- **Idempotency test:** Двойной запуск миграций на той же БД не вызывает ошибок.
- **Rollback test:** `down`-скрипт выполняется без потерь данных на staging-дампе.
- **Drift detection test:** Сравнение `atlas schema inspect` production с Git-версией.

#### Валидация
- Миграции применяются к чистой БД.
- Приложение стартует с новой схемой.
- Откат миграции не ломает приложение.

### Сценарий 5: Автоматизированный бэкап в CI/CD пайплайне

#### Предпосылки
- Наличие свободного места в хранилище бэкапов.
- Настроенные утилиты `pg_dump` / `pg_restore` в окружении раннера.

#### Bash-скрипт для CI
```bash
#!/bin/bash
# Запуск в составе CI Job перед деплоем схемы
BACKUP_FILE="/tmp/pre_mig_$(date +%s).sql"

echo "Creating safety backup..."
pg_dump -Fc -h $DB_HOST -U $DB_USER $DB_NAME > $BACKUP_FILE

echo "Starting migration..."
if ! flyway migrate; then
  echo "CRITICAL: Migration failed, initiating automated rollback..."
  pg_restore -c -h $DB_HOST -U $DB_USER -d $DB_NAME $BACKUP_FILE
  exit 1
fi
```

#### Валидация
- Бэкап создаётся перед каждой миграцией.
- При падении миграции пайплайн автоматически восстанавливает состояние.

### Сценарий 6: Сравнение инструментов миграций

## Пограничные случаи и ограничения

- **Большие таблицы (> 10 ГБ):** `ALTER TABLE` без `CONCURRENTLY`/`INPLACE` блокирует таблицу на минуты и более. Используйте shadow migration, pt-online-schema-change (MySQL) или `pg_repack` (PostgreSQL).
- **Необратимые миграции:** Некоторые изменения (`DROP COLUMN`, `DROP TABLE`) не имеют автоматического обратного пути. Требуется explicit down-скрипт или бэкап.
- **Транзакционный DDL (ограничения):** PostgreSQL поддерживает transactional DDL почти полностью. MySQL/MariaDB: `ALTER TABLE` не транзакционен — при сбое на середине миграции база остаётся в частично изменённом состоянии. Планируйте manual recovery.
- **Distributed transactions:** Миграции в sharded БД требуют оркестрации через координатор (например, миграции с FK между базами должны выполняться через `needs` / `dependencies`).
- **Rollback complexity:** Откат кода без отката схемы ломает приложение. Используйте Expand/Contract.
- **Drift detection:** В production схема может отличаться от Git. Настройте nightly drift detection.
- **Lock contention:** Долгие миграции создают lock на таблицу. Используйте batched updates и low-traffic windows.
- **Cross-platform compatibility:** Миграции, написанные для PostgreSQL, могут не работать на MySQL. Используйте инструменты с multi-DB поддержкой (Liquibase) или изолируйте SQL.
- **CI/CD platform lock-in:** Миграции, завязанные на vendor-specific фичи (GitLab `resource_group`, GitHub `environment`), усложняют миграцию между платформами. Предпочитайте стандартные паттерны.
- **Maintenance windows:** Некоторые миграции требуют planned downtime. Интегрируйте maintenance_mode в pipeline.
- **DBA bottleneck:** Ручное ревью каждой миграции создаёт очередь. Автоматизируйте lint и drift detection, оставляя ручное approval только для критичных изменений.

## Устранение неисправностей

### Ошибка "Checksum mismatch" (Flyway)
- **Причина:** Файл миграции был изменён после применения.
- **Решение:** Верните исходный текст файла или выполните `flyway repair` (только для Dev/Test).

### Lock Timeout
- **Причина:** Таблица занята долгим процессом (бэкап, тяжелый отчёт).
- **Решение:** Завершите блокирующую сессию (`SELECT pg_terminate_backend(pid);`) или повторите запуск в окно минимальной нагрузки.

### Миграция "зависла" (long-running DDL)
- **Диагностика:** `pg_stat_activity` показывает активную миграцию; `pg_stat_progress_*` показывает прогресс.
- **Решение:** Дождитесь завершения или откатитесь через `pg_cancel_backend` + restore from backup.

### Индекс стал INVALID (PostgreSQL)
- **Причина:** Сбой во время `CREATE INDEX CONCURRENTLY`.
- **Решение:** `DROP INDEX CONCURRENTLY` и повторный запуск.

### Раздувание таблицы (Bloat) после миграции
- **Причина:** Слишком частые апдейты без пауз при батчинге.
- **Решение:** Увеличьте `pg_sleep` между батчами; проверьте настройки автовакуума.

### Падение пайплайна на drift detection
- **Причина:** Производственная БД была изменена вручную.
- **Решение:** Создайте reconcile-миграцию, фиксирующую ручные изменения, или обновите baseline (`flyway baseline`).

### Откат миграции ломает приложение
- **Причина:** Не соблюдён паттерн Expand-Contract: старая версия кода несовместима с новой схемой.
- **Решение:** Используйте Fix-Forward (новая миграция) вместо отката; переделайте архитектуру на Expand-Contract.

## Рекомендации SRE по Database CI/CD

- **Защитные таймауты:** Всегда устанавливайте `lock_timeout` (2-5 сек) для сессии миграции. Пайплайн должен упасть, если не смог получить блокировку, а не "подвесить" всю БД.
- **Запрет `flyway clean`:** Эта команда должна быть аппаратно или программно запрещена для всех сред, кроме локальной разработки.
- **Принцип минимизации привилегий:** CI-пользователь не должен иметь прав `OWNER` или `SUPERUSER`. Достаточно прав на DDL в целевой схеме.
- **Dry-run для DBA:** Всегда генерируйте SQL-артефакт изменений (`liquibase update-sql` или `atlas migrate diff --dry-run`) и прикладывайте его к Merge Request для ручного ревью.
- **Идемпотентность:** Все миграции должны быть безопасно запускаемыми многократно (`CREATE IF NOT EXISTS`, `DROP IF EXISTS`).
- **Timestamp-based versioning:** Используйте `YYYYMMDDHHMMSS` вместо порядковых номеров (`V1`, `V2`) для предотвращения коллизий при merge.
- **Pipeline isolation:** Миграции должны быть отдельным stage/job; не смешивайте с деплоем приложения.
- **Multi-environment consistency:** Применяйте миграции в одном порядке: `dev → staging → prod`. Никогда не применяйте миграцию напрямую в prod, пропуская staging.
- **Мониторинг:** Настройте алерты на `FailedMigration` и `LongRunningMigration`. См. **[Мониторинг миграций](monitoring.md)**.
- **SLO/SLI:** Оценивайте каждую миграцию по потенциальному риску нарушения Service Level Objectives. Для сервисов с SLA 99,9% и выше допустимый простой при миграции — минуты, а не часы.
