# Database CI/CD: Автоматизация миграций и GitOps для БД

## Определения

- **Database CI/CD** — процесс автоматизации жизненного цикла изменений схемы и данных БД, интегрированный в общий конвейера поставки ПО.
- **GitOps для БД (Database-as-Code)** — подход, при котором состояние базы данных описывается декларативно в системе контроля версий (Git), а инструменты автоматизации (Atlas, Bytebase) синхронизируют это состояние с реальной БД.
- **Migration Drift (Дрейф схемы)** — расхождение между фактическим состоянием схемы в БД и тем, что описано в коде/миграциях.
- **Drift Detection** — автоматизированная проверка пайплайном наличия ручных или несанкционированных изменений схемы в обход CI/CD.
- **Static Analysis (SQL Linting)** — проверка скриптов миграции на наличие опасных (блокирующих) операций или нарушение корпоративных стандартов до их применения.
- **Zero-downtime Migration** — изменение структуры БД, не требующее остановки приложения и обеспечивающее совместимость со старыми и новыми версиями кода.

## Жизненный цикл Database CI/CD

Полный цикл автоматизации включает 5 ключевых этапов:

1.  **Валидация (Linting):** Проверка синтаксиса и аудит безопасности (Atlas Lint, Squawk) на блокирующие операции (`DROP`, `ALTER` без `CONCURRENTLY`).
2.  **Эфемерное тестирование (Dry-run):** Применение миграций на временной БД (Docker/Testcontainers) для проверки корректности SQL-скриптов.
3.  **Контроль дрейфа (Drift Check):** Сравнение текущего состояния Production с мастер-веткой перед применением новых изменений.
4.  **Применение (Deployment):** Выполнение миграций (Flyway, Liquibase, Atlas) через Kubernetes Jobs или CLI-агенты перед развертыванием новой версии приложения.
5.  **Верификация:** Автоматическая проверка целостности схемы и планов выполнения запросов после деплоя.

## Продвинутые паттерны (Advanced Patterns)

### 1. Zero-downtime в распределенных системах

В сложных системах с множеством реплик и регионов простого Expand-Contract недостаточно. Детальные технические шаги описаны в **[Архитектурных сценариях миграции](scenarios.md#практические-сценарии-архитектурные-переходы)**.

- **Версионирование схемы (Schema Versioning):** Приложение поддерживает работу с двумя версиями схемы одновременно через DAL или Feature Flags.
- **Blue-Green Database Deployment:** Создание инстанса с новой схемой и настройка логической репликации для синхронизации перед переключением трафика.
- **Traffic Shadowing:** Проверка производительности новой схемы путем дублирования реальных запросов на тестовую БД (Read-only).

### 2. Автоматический аудит SQL (SQL Lint) в CI

Линтинг позволяет отсекать опасные операции до их попадания в Production.
- **Squawk (PostgreSQL):** Выявляет `ALTER TABLE` без `CONCURRENTLY`, добавление `NOT NULL` без `DEFAULT` и другие блокирующие операции.
- **Atlas Lint:** Анализирует план миграции и предупреждает о разрушительных изменениях (например, `DROP COLUMN`).

### 3. Предотвращение блокировок таблиц (Table Locks Prevention)

| Операция | Риск | Безопасная альтернатива |
| :--- | :--- | :--- |
| `ADD COLUMN` | Блокировка всей таблицы | Postgres 11+: просто добавлять. Старые: `DEFAULT NULL` → `UPDATE` батчами. |
| `CREATE INDEX` | Полная блокировка записи | `CREATE INDEX CONCURRENTLY` (Postgres) / `ONLINE` (MySQL). |
| `ADD FOREIGN KEY` | Долгая проверка строк | `ADD CONSTRAINT ... NOT VALID` → `VALIDATE CONSTRAINT` отдельно. |
| `DROP COLUMN` | Поломка кода N-1 | Сначала скрыть в коде, затем удалять в следующей итерации CI. |

## Глубокое погружение: Flyway и Liquibase (Императивный подход)

Императивные инструменты фокусируются на последовательности изменений (Change-based).

### Интеграция в пайплайн (CLI)

Для Flyway и Liquibase рекомендуется упаковывать скрипты в Docker-образ и запускать его как **Kubernetes Job** с аннотациями Helm Hooks (`pre-upgrade`).

**Типовой запуск Flyway в CI:**
```bash
# Проверка текущего состояния
flyway info -url=$DB_URL -user=$DB_USER -password=$DB_PASS

# Валидация контрольных сумм примененных миграций
flyway validate -url=$DB_URL

# Применение новых миграций
flyway migrate -url=$DB_URL
```

### Обработка откатов и ошибок

Откаты в БД — это всегда риск потери данных.

1.  **Fix-Forward (Рекомендуется):** Создание новой миграции `V(N+1)` для исправления или отката логики `VN`. Сохраняет линейную историю.
2.  **Flyway Undo (Teams/Enterprise):** Использование скриптов `U__filename.sql`. В CI требует осторожности: автоматический откат запрещен для Prod.
3.  **Liquibase Rollback:** Использует теги `<rollback>` в XML/YAML. Команда `liquibase rollback --tag=release-1.0` возвращает БД к метке.
4.  **Транзакционный DDL:** В PostgreSQL миграция выполняется в транзакции. При ошибке происходит автоматический откат к состоянию `V(N-1)`.

### Проверка дрейфа схемы

Flyway сам по себе не видит изменений, сделанных вручную.
- **Решение:** Использовать Liquibase `diff` или Atlas `schema inspect` в CI для сравнения Production с эталоном из Git. Пайплайн должен падать при обнаружении расхождений.

## Современный GitOps: Atlas и Bytebase (Декларативный подход)

Фокус на конечном состоянии схемы (State-based).

### Atlas (Schema-as-Code)

Atlas позволяет описывать схему на HCL или SQL и автоматически генерировать план перехода.

**GitOps Workflow в GitHub Actions:**
```yaml
name: Atlas CI/CD
on:
  pull_request:
    paths: ['migrations/**']
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: ariga/setup-atlas@v0
      - name: Run Atlas Lint
        uses: ariga/atlas-action/migrate/lint@v1
        with:
          dir: 'file://migrations'
          dev-url: 'docker://postgres/15/dev' # Эфемерная БД для анализа
```
**Преимущество:** `dev-url` позволяет Atlas прогнать миграции в Docker, сравнить результат с желаемым состоянием и выдать детальный отчет о безопасности.

### Bytebase (Database DevOps Portal)

Bytebase — это платформа с UI, которая превращает управление БД в процесс, похожий на GitLab/GitHub.

**GitOps Workflow (GitLab CI):**
1.  **SQL Review:** При создании Merge Request, Bytebase через API проверяет SQL на соответствие правилам (SQL Review Policy).
2.  **Rollout:** После слияния в `main`, Bytebase создает Issue на деплой с возможностью ручного подтверждения (Approval) от DBA.
3.  **Multi-tenant Rollout:** Применение изменений к сотням шардов одновременно с контролем прогресса.
4.  **Drift Detection:** Bytebase каждые 10 минут опрашивает БД и подсвечивает расхождения в UI.

## Обработка дрейфа схемы (Drift Management)

Дрейф — главный враг автоматизации.

| Метод обнаружения | Инструмент | Описание |
| :--- | :--- | :--- |
| **Validate (Checksum)** | Flyway | Проверяет, не изменились ли *файлы* уже примененных миграций. |
| **Snapshot Diff** | Liquibase / Atlas | Сравнивает структуру реальной БД с сохраненным снимком (JSON/SQL). |
| **Full Inspection** | Bytebase | Постоянный мониторинг всех объектов БД и сравнение с репозиторием. |

**Стратегия исправления:**
1.  **Reconcile:** Создать миграцию, которая устраняет ручные изменения.
2.  **Baseline:** Если изменение легитимно, обновить историю инструмента (Flyway Baseline) для синхронизации "точки отсчета".

## Рекомендации SRE по Database CI/CD

- **Защитные таймауты в CI:** Всегда устанавливайте `lock_timeout` (2-5 сек) для миграционного пользователя. Если блокировка не получена, пайплайн должен упасть, а не блокировать приложение.
- **Никогда не используйте `flyway clean` в CI:** Это приведет к полному удалению данных.
- **Изоляция пайплайна:** Права CI-пользователя только на DDL/DML, но не на управление ролями или параметрами сервера.
- **Dry-run для DBA:** Всегда генерируйте SQL-артефакт (`liquibase update-sql` или `atlas migrate diff --dry-run`) для ревью в Merge Request.
- **Мониторинг:** Алерты на `FailedMigration` и `LongRunningMigration`. См. **[Мониторинг миграций](monitoring.md)**.
