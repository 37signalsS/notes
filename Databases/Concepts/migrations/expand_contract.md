# Обратно-совместимые миграции: Принцип Expand-Contract

## Определения

**Expand-Contract (также известный как Expand-Migrate-Contract или Parallel Change)** — это паттерн внесения структурных изменений в базу данных, который обеспечивает полную обратную совместимость между схемой БД и кодом приложения. Метод позволяет проводить релизы без простоя (Zero-downtime) и безопасно откатывать версию приложения без отката схемы БД.

## Основные концепции

Суть паттерна заключается в замене одного «разрушающего» изменения (Breaking Change) на серию безопасных этапов.

### Фазы процесса

1. **Расширение (Expand):** в БД добавляются новые элементы (колонки, таблицы), но старые сохраняются. Система начинает поддерживать обе структуры одновременно.
2. **Миграция (Migrate/Sync):** данные переносятся из старых структур в новые. На этом этапе настраивается синхронизация для поддержания консистентности.
3. **Сокращение (Contract):** после подтверждения стабильности нового кода и завершения переноса данных, старые (устаревшие) элементы удаляются.

### Способы синхронизации

- **Триггеры в БД:** обеспечивают мгновенную синхронизацию на уровне СУБД. Надежно, но создает дополнительную нагрузку на I/O.
- **Двойная запись (Double Writing):** приложение пишет данные одновременно в старую и новую колонки. Позволяет избежать логики в БД, но усложняет код приложения.
- **Представления (Views):** при переименовании сущностей можно использовать `VIEW` с именем старой таблицы, указывающее на новую. Это делает миграцию прозрачной для кода.

## Практические сценарии

### Сценарий 1: Разделение или переименование полей (PostgreSQL)

Задача: разделить колонку `name` на `first_name` и `last_name` без остановки сервиса.

**Шаг 1: Expand (Расширение)**
```sql
-- Добавляем новые колонки как NULLABLE
ALTER TABLE users ADD COLUMN first_name VARCHAR(100);
ALTER TABLE users ADD COLUMN last_name VARCHAR(100);

-- Настройка синхронизации (Триггер)
CREATE OR REPLACE FUNCTION sync_user_names() RETURNS TRIGGER AS $$
BEGIN
    IF (TG_OP = 'INSERT' OR TG_OP = 'UPDATE') THEN
        -- Если обновлено старое поле — заполняем новые
        IF NEW.name IS DISTINCT FROM OLD.name THEN
            NEW.first_name := SPLIT_PART(NEW.name, ' ', 1);
            NEW.last_name := SPLIT_PART(NEW.name, ' ', 2);
        END IF;
    END IF;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_names BEFORE INSERT OR UPDATE ON users
FOR EACH ROW EXECUTE FUNCTION sync_user_names();
```

**Шаг 2: Migrate (Перенос исторических данных)**
Выполняется батчами (см. **[Типовые сценарии миграций](scenarios.md)**) во избежание блокировок.

**Шаг 3: Переключение кода приложения**
Деплой новой версии ПО, которая использует только `first_name` и `last_name`. Старая колонка `name` всё еще обновляется триггером на случай отката приложения.

**Шаг 4: Contract (Сокращение)**
```sql
-- Удаляем триггер после успешного периода работы нового кода
DROP TRIGGER trg_sync_names ON users;
ALTER TABLE users DROP COLUMN name;

-- Добавляем NOT NULL ограничения безопасно
ALTER TABLE users ADD CONSTRAINT first_name_not_null 
    CHECK (first_name IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT first_name_not_null;
```

### Сценарий 2: Rolling Update в Kubernetes

При использовании `RollingUpdate` в кластере одновременно работают поды версий `N` (старая) и `N+1` (новая). Схема БД должна удовлетворять обеим.

1. **Job до деплоя:** запускает `Expand` миграцию.
2. **Rolling Update:** новые поды пишут в новые поля, старые — в старые. Синхронизация в БД (триггер) склеивает состояние.
3. **Следующий релиз:** когда версия `N` полностью вытеснена, запускается `Contract` миграция.

## Дополнительная информация

### Сравнение инструментов

| Инструмент | Подход | Рекомендация |
|:---|:---|:---|
| **Flyway / Liquibase** | Императивный | Enterprise-стандарт, поддержка Java/Kotlin экосистемы. |
| **Atlas / Prisma** | Декларативный | Удобно для быстрой итерации, автогенерация миграций. |
| **gh-ost / pt-osc** | Online Schema Change | Для терабайтных таблиц в MySQL. |

### Рекомендации и риски

- **Производительность:** триггеры увеличивают время выполнения каждого `INSERT/UPDATE`. Для высоконагруженных систем предпочтительнее синхронизация на уровне приложения.
- **Целостность:** при использовании двойной записи в приложении есть риск «состояния гонки» (race condition).
- **Мониторинг:** во время фазы `Migrate` обязательно отслеживайте лаг репликации и нагрузку на дисковую систему. Подробнее в **[Мониторинг миграций](monitoring.md)**.
