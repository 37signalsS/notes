# Обратно-совместимые миграции: Принцип Expand-Contract

**Актуально для:** PostgreSQL 11+, MySQL 8.0.12+, MariaDB 10.3+

## Определения

- **Expand-Contract (Расширение-Сокращение)** — это паттерн внесения структурных изменений в базу данных, также известный как **Parallel Change** или **Parallel Schema Evolution**. Он обеспечивает полную обратную совместимость между схемой БД и кодом приложения на всех этапах деплоя.
- **Обратная совместимость (Backward Compatibility):** состояние, при котором старая версия кода (N) продолжает корректно функционировать с новой схемой базы данных (N+1). Это критично для предотвращения ошибок 5xx при Rolling Update.
- **Zero-downtime Deployment:** процесс обновления системы без прекращения обслуживания пользователей. Паттерн Expand-Contract является фундаментом этого процесса на уровне данных.
- **Разрушающее изменение (Breaking Change):** изменение схемы (например, удаление колонки или смена типа), которое немедленно ломает код, ожидающий старую структуру.
- **Fix-Forward:** стратегия исправления миграций через накат новой миграции поверх проблемной, вместо физического отката изменений.
- **Согласованность (Consistency):** состояние, при котором данные в старых и новых структурах идентичны на протяжении всего цикла Expand-Contract.

## Основные концепции

Паттерн разделяет одно атомарное разрушающее изменение на последовательность безопасных, неразрушающих этапов, распределенных во времени. Это позволяет приложению плавно "перетечь" из старого состояния в новое.

### Три фазы процесса

1.  **Расширение (Expand):**
    - **Суть:** В базу данных добавляются новые элементы (колонки, таблицы, индексы).
    - **Состояние:** Существующая структура остается нетронутой. Код версии N игнорирует новинки, код N+1 начинает их использовать.
    - **Зачем:** БД становится "суперсетом", поддерживающим обе версии логики одновременно.
2.  **Миграция данных и кода (Migrate):**
    - **Суть:** Перенос данных из старых структур в новые и переключение логики приложения.
    - **Действия:** Приложение версии N+1 пишет в новые структуры. Настраивается синхронизация (триггеры или Dual Write) для поддержки консистентности.
    - **Зачем:** Обеспечение возможности безопасного отката (Rollback) приложения к версии N без потери новых данных.
3.  **Сокращение (Contract):**
    - **Суть:** Удаление старых, ставших ненужными элементов схемы.
    - **Действия:** Удаляются триггеры синхронизации, старые колонки и таблицы. Применяются финальные ограничения (например, `NOT NULL` на новую колонку).
    - **Зачем:** Очистка технического долга в БД и завершение перехода к целевой архитектуре.

### Методы синхронизации данных

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Триггеры в БД** | Автоматическая синхронизация «на лету» средствами СУБД. | Гарантированная атомарность, прозрачность для приложения. | Доп. нагрузка на диск (I/O), сложность отладки логики внутри БД. |
| **Двойная запись (Dual Write)** | Код приложения пишет в две структуры за одну операцию. | Весь контроль в коде, легче тестировать бизнес-логику. | Риск "состояния гонки" (Race Condition), усложнение кода приложения. |
| **Shadow Read / Write** | Запись в оба источника, чтение из старого; сравнение результатов. | Самый безопасный метод проверки новой схемы на реальном трафике. | Требует развитой системы Feature Flags и мониторинга расхождений. |
| **Представления (Views)** | Использование View для инкапсуляции изменений имен или структур. | Полная прозрачность при переименованиях (Alias). | Ограничения при обновлении данных через сложные вьюхи в некоторых СУБД. |

## Предпосылки и подготовка

Перед запуском миграции в Production выполните стандартный чек-лист.

- **Резервная копия:** Актуальность и восстанавливаемость. Для PostgreSQL выполните `pg_basebackup` или snapshot storage; для MySQL — `xtrabackup --backup`. Проверьте целостность через `pg_checksum` / `XtraBackup --prepare`.
- **Лаг репликации:** Должен быть ниже порога алертинга (обычно < 30с для Streaming Replication / < 10с для синхронной репликации). Если лаг близок к `wal_keep_size` — отложите миграцию.
- **Connection Pool:** Пулы приложения (PgBouncer/ProxySQL) должны иметь запас ёмкости на время миграции. При `ACCESS EXCLUSIVE` пул опустошается, пока DDL не завершится, и новые запросы приложения получают отказы.
- **Активные транзакции:** Должны отсутствовать долгоживущие транзакции в статусе `idle in transaction`. Они удерживают `AccessShareLock` и могут превратить кратковременную DDL-блокировку в каскадный deadlock.
- **Change Advisory Board (CAB):** Миграции, затрагивающие таблицы > 10 ГБ или содержащие `DROP/RENAME`, требуют утверждения. Документируйте окно деплоя, критерии отката и контакты on-call.
- **Maintenance Window:** Для миграций с ожидаемым простем > 30с согласуйте окно с бизнесом. Для zero-downtime — фиксируйте время cutover в runbook.
- **Runbook:** Для каждой миграции подготовьте документ с пошаговой инструкцией, командами проверки, критериями успешного завершения и планом отката с триггерами.

## Практические сценарии

### Сценарий 1: Изменение типа колонки или переименование (PostgreSQL)

Задача: изменить тип колонки `user_id` с `INT` на `BIGINT` в нагруженной таблице.

#### Предпосылки
- Таблица с миллионами строк, требующая доступности 24/7.
- Установленный `lock_timeout` для всех DDL-команд.
- Актуальный бэкап и лаг репликации < 30с.

#### Пошаговая инструкция

**Этап 1: Expand**
Добавляем новую колонку и настраиваем синхронизацию новых записей.
```sql
-- 1. Добавляем новую колонку (NULLABLE, чтобы не блокировать таблицу)
ALTER TABLE logs ADD COLUMN user_id_new BIGINT;

-- 2. Создаем функцию синхронизации
CREATE OR REPLACE FUNCTION sync_user_id() RETURNS TRIGGER AS $$
BEGIN
    NEW.user_id_new := NEW.user_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 3. Создаем триггер
CREATE TRIGGER trg_sync_user_id BEFORE INSERT OR UPDATE ON logs
FOR EACH ROW EXECUTE FUNCTION sync_user_id();
```

**Этап 2: Migrate**
Перенос исторических данных батчами (см. **[Типовые сценарии миграций](scenarios.md)**).
```sql
-- Выполняется в фоне до полного заполнения
UPDATE logs SET user_id_new = user_id WHERE user_id_new IS NULL;
```

**Этап 3: Switch & Contract**
После успешного деплоя кода, использующего `user_id_new`, и проверки консистентности:
```sql
-- 1. Удаляем триггер
DROP TRIGGER trg_sync_user_id ON logs;
-- 2. Удаляем старую колонку
ALTER TABLE logs DROP COLUMN user_id;
-- 3. Переименовываем новую в целевое имя
ALTER TABLE logs RENAME COLUMN user_id_new TO user_id;
```

#### Валидация
- `SELECT count(*) FROM logs WHERE user_id_new IS DISTINCT FROM user_id;` должен вернуть 0 перед фазой Contract.
- Проверка блокировок: отсутствие `waiting` процессов в `pg_stat_activity`.
- Проверка репликации: `pg_stat_replication` показывает `state = streaming` без задержек.

#### Устранение неисправностей
- **Нагрузка на I/O:** Если триггер замедляет запись, увеличьте паузу между батчами `UPDATE` или перейдите на Dual Write с очередями.
- **Восстание блокировок:** Долгий `SELECT` в другом сеансе удерживает `AccessShareLock`. Завершите блокирующий процесс через `pg_terminate_backend(pid)`.

---

### Сценарий 2: Добавление внешнего ключа (Foreign Key) без простоя

#### Теория
Обычный `ALTER TABLE ... ADD FOREIGN KEY` блокирует таблицу `ACCESS EXCLUSIVE` для полной проверки всех строк. Это вызывает простой.

#### Пошаговая инструкция
1. **Expand:** Добавить FK с флагом `NOT VALID`.
    ```sql
    ALTER TABLE orders ADD CONSTRAINT fk_user 
    FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;
    ```
    *Результат:* Новые данные проверяются мгновенно, старые — нет. Блокировка минимальна.
2. **Migrate:** Проверка данных в фоне.
3. **Contract:** Валидация ограничения.
    ```sql
    ALTER TABLE orders VALIDATE CONSTRAINT fk_user;
    ```
    *Результат:* Сканирование таблицы без блокировки записи.

#### Валидация
- Проверка статуса в системном каталоге: `convalidated = true` в `pg_constraint` (PostgreSQL).
- Для MySQL 8.0.12+ проверка статуса через `information_schema.table_constraints`.

---

### Сценарий 3: Масштабирование в Kubernetes (Rolling Update)

#### Пошаговая инструкция
1. **Pre-deployment Job:** Выполняет фазу **Expand** (DDL).
2. **Rolling Update:** 
   - Поды V(N) читают/пишут в старую колонку.
   - Поды V(N+1) пишут в обе (или через триггер) и читают из новой.
3. **Post-deployment Job:** После того как 100% подов перешли на V(N+1), выполняется фаза **Contract**.

#### Валидация
- Smoke-тест на 5% трафика перед полным cutover.
- Проверка метрик Pod'ов: отсутствие 5xx ошибок.

---

### Сценарий 4: Переименование колонки без простоя (MySQL / MariaDB)

#### Теория
`RENAME COLUMN` или `CHANGE` в MySQL 8.0.12+ с флагом `ALGORITHM=INPLACE, LOCK=NONE` выполняется мгновенно, но требует проверки совместимости приложения.

#### Пошаговая инструкция
1. **Expand:** Добавить новую колонку с целевым именем.
    ```sql
    ALTER TABLE users ADD COLUMN login VARCHAR(255) DEFAULT NULL, ALGORITHM=INPLACE, LOCK=NONE;
    ```
2. **Migrate:** Скопировать данные и настроить триггер или Dual Write.
3. **Contract:** Удалить старую колонку.

```sql
ALTER TABLE users DROP COLUMN user_name, ALGORITHM=INPLACE, LOCK=NONE;
```

## Пограничные случаи и ограничения

- **Секционированные таблицы:** Большинство DDL-операций в PostgreSQL 11+ выполняется на уровне секций без полной блокировки. Однако `ATTACH PARTITION` требует `ACCESS EXCLUSIVE` на дочерней таблице. Для MySQL используйте `ALGORITHM=INPLACE, LOCK=NONE` на отдельных секциях.
- **Внешние ключи (Foreign Keys):** Добавление FK с `NOT VALID` не блокирует чтение, но `VALIDATE CONSTRAINT` acquires `SHARE UPDATE EXCLUSIVE` на таблицу. На очень больших таблицах (> 100M строк) валидация может занимать часы.
- **Триггеры:** Триггеры `BEFORE/AFTER` замедляют записи из-за дополнительных операций ввода-вывода. При массовой миграции данных, если бизнес-логика позволяет, отключайте триггеры.
- **Огромные таблицы (> 1 ТБ):** Для таблиц терабайтного класса стандартные средства могут занимать дни. Рассмотрите `pg_repack` (PostgreSQL) или `gh-ost`/`pt-online-schema-change` (MySQL).
- **Миграция на реплике:** Выполняйте DDL сначала на standby (PostgreSQL поддерживает логическую репликацию с standby), затем promote и cutover.
- **Транзакционный DDL в MySQL/MariaDB:** DDL вызывает неявный коммит. Невозможно откатить миграцию из нескольких команд средствами СУБД. Используйте бэкапы или Fix-Forward.
- **Влияние на SLO:** Для сервисов с SLA 99,9% и выше допустимый простой при миграции — минуты. Zero-downtime обязателен.

## Устранение неисправностей

- **Очередь блокировок:** `lock_timeout` сработал. **Решение:** Завершите блокирующий сеанс через `pg_terminate_backend(pid)` или `KILL` в MySQL. Повторите запуск в период минимальной нагрузки.
- **Потеря данных при откате:** Фаза Contract выполнена (старая колонка удалена), а приложение откатили к версии N. **Решение:** Используйте Fix-Forward (новая миграция) вместо отката.
- **Триггер замедляет запись:** **Решение:** Увеличьте паузу между батчами или перейдите на Dual Write.
- **Индекс стал INVALID:** Сбой во время создания. **Решение:** `DROP INDEX CONCURRENTLY` и повторный запуск.
- **Раздувание таблицы (Bloat):** Слишком частые апдейты без пауз. **Решение:** Увеличить паузу между батчами и проверить настройки автовакуума.
- **Дрейф схемы:** Схема в Production отличается от Git. **Решение:** Используйте drift detection в CI/CD перед деплоем.
- **Replication Lag:** Рост лага во время миграции. **Решение:** Уменьшите размер батчей, проверьте нагрузку на master.

## Рекомендации

- **Таймауты блокировок:** Всегда устанавливайте `lock_timeout` (2-5 сек). Даже фаза Expand может вызвать очередь блокировок, если БД занята долгим `SELECT`.
- **Версионирование:** Предпочитайте формат `YYYYMMDDHHMMSS` (таймстамп) простым порядковым номерам.
- **Изоляция прав:** CI-пользователь не должен иметь прав `OWNER` на всю базу. Используйте минимально необходимые привилегии для DDL.
- **Отказ от `SELECT *`:** Приложение **обязано** явно перечислять колонки. Это позволяет безопасно добавлять новые поля в фазе `Expand` без ошибок маппинга.
- **Синхронизация в обоих направлениях:** Обеспечьте Dual Write или триггеры, чтобы данные, записанные новым кодом, были доступны старому при откате.
- **Мониторинг:** Ключевые метрики — `Replication Lag` и `CPU Load` при работе триггеров.
- **Очистка:** После завершения миграции удалите временные таблицы, триггеры синхронизации и проверьте, что autovacuum восстановил нормальный режим работы.
- **SRE/SLI:** Оцените влияние миграции на SLO. Для критичных сервисов используйте canary-подход: применяйте миграцию к подмножеству реплик, затем к 5% master-трафика.
