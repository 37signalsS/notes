# Обратно-совместимые миграции: Принцип Expand-Contract

## Определения

- **Expand-Contract (Расширение-Сокращение)** — это паттерн внесения структурных изменений в базу данных, также известный как **Parallel Change** или **Parallel Schema Evolution**. Он обеспечивает полную обратную совместимость между схемой БД и кодом приложения на всех этапах деплоя.
- **Обратная совместимость (Backward Compatibility):** состояние, при котором старая версия кода (N) продолжает корректно функционировать с новой схемой базы данных (N+1). Это критично для предотвращения ошибок 5xx при Rolling Update.
- **Zero-downtime Deployment:** процесс обновления системы без прекращения обслуживания пользователей. Паттерн Expand-Contract является фундаментом этого процесса на уровне данных.
- **Разрушающее изменение (Breaking Change):** изменение схемы (например, удаление колонки или смена типа), которое немедленно ломает код, ожидающий старую структуру.

## Основные концепции

Паттерн разделяет одно атомарное разрушающее изменение на последовательность безопасных, неразрушающих этапов, распределенных во времени. Это позволяет приложению плавно "перетечь" из старого состояния в новое.

### Три фазы процесса

1.  **Расширение (Expand):**
    - **Суть:** В базу данных добавляются новые элементы (колонки, таблицы, индексы).
    - **Состояние:** Существующая структура остается нетронутой. Код версии N игнорирует новинки, код N+1 начинает их использовать.
    - **Зачем:** БД становится "суперсетом", поддерживающим обе версии логики одновременно.
2.  **Миграция данных и кода (Migrate):**
    - **Суть:** Перенос данных из старых структур в новые и переключение логики приложения.
    - **Действия:** Приложение версии N+1 пишет в новые структуры. Настраивается синхронизация (триггеры или Dual Write) для поддержки консистентности.
    - **Зачем:** Обеспечение возможности безопасного отката (Rollback) приложения к версии N без потери новых данных.
3.  **Сокращение (Contract):**
    - **Суть:** Удаление старых, ставших ненужными элементов схемы.
    - **Действия:** Удаляются триггеры синхронизации, старые колонки и таблицы. Применяются финальные ограничения (например, `NOT NULL` на новую колонку).
    - **Зачем:** Очистка технического долга в БД и завершение перехода к целевой архитектуре.

### Методы синхронизации данных

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Триггеры в БД** | Автоматическая синхронизация «на лету» средствами СУБД. | Гарантированная атомарность, прозрачность для приложения. | Доп. нагрузка на диск (I/O), сложность отладки логики внутри БД. |
| **Двойная запись (Dual Write)** | Код приложения пишет в две структуры за одну операцию. | Весь контроль в коде, легче тестировать бизнес-логику. | Риск "состояния гонки" (Race Condition), усложнение кода приложения. |
| **Shadow Read / Write** | Запись в оба источника, чтение из старого; сравнение результатов. | Самый безопасный метод проверки новой схемы на реальном трафике. | Требует развитой системы Feature Flags и мониторинга расхождений. |
| **Представления (Views)** | Использование View для инкапсуляции изменений имен или структур. | Полная прозрачность при переименованиях (Alias). | Ограничения при обновлении данных через сложные вьюхи в некоторых СУБД. |

## Практические сценарии

### Сценарий 1: Изменение типа колонки или переименование (PostgreSQL)

Задача: изменить тип колонки `user_id` с `INT` на `BIGINT` в нагруженной таблице.

#### Предпосылки
- Таблица с миллионами строк, требующая доступности 24/7.
- Установленный `lock_timeout` для всех DDL-команд.

#### Пошаговая инструкция

**Этап 1: Expand**
Добавляем новую колонку и настраиваем синхронизацию новых записей.
```sql
-- 1. Добавляем новую колонку (NULLABLE, чтобы не блокировать таблицу)
ALTER TABLE logs ADD COLUMN user_id_new BIGINT;

-- 2. Создаем функцию синхронизации
CREATE OR REPLACE FUNCTION sync_user_id() RETURNS TRIGGER AS $$
BEGIN
    NEW.user_id_new := NEW.user_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- 3. Создаем триггер
CREATE TRIGGER trg_sync_user_id BEFORE INSERT OR UPDATE ON logs
FOR EACH ROW EXECUTE FUNCTION sync_user_id();
```

**Этап 2: Migrate**
Перенос исторических данных батчами (см. **[Типовые сценарии миграций](scenarios.md)**).
```sql
-- Выполняется в фоне до полного заполнения
UPDATE logs SET user_id_new = user_id WHERE user_id_new IS NULL;
```

**Этап 3: Switch & Contract**
После успешного деплоя кода, использующего `user_id_new`, и проверки консистентности:
```sql
-- 1. Удаляем триггер
DROP TRIGGER trg_sync_user_id ON logs;
-- 2. Удаляем старую колонку
ALTER TABLE logs DROP COLUMN user_id;
-- 3. Переименовываем новую в целевое имя
ALTER TABLE logs RENAME COLUMN user_id_new TO user_id;
```

#### Валидация
- `SELECT count(*) FROM logs WHERE user_id_new IS DISTINCT FROM user_id;` должен вернуть 0 перед фазой Contract.

#### Устранение неисправностей
- **Нагрузка на I/O:** Если триггер замедляет запись, увеличьте паузу между батчами `UPDATE` или перейдите на Dual Write с очередями.

### Сценарий 2: Добавление внешнего ключа (Foreign Key) без простоя

#### Теория
Обычный `ALTER TABLE ... ADD FOREIGN KEY` блокирует таблицу `ACCESS EXCLUSIVE` для полной проверки всех строк. Это вызывает простой.

#### Пошаговая инструкция
1. **Expand:** Добавить FK с флагом `NOT VALID`.
    ```sql
    ALTER TABLE orders ADD CONSTRAINT fk_user 
    FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;
    ```
    *Результат:* Новые данные проверяются мгновенно, старые — нет. Блокировка минимальна.
2. **Migrate:** Проверка данных в фоне.
3. **Contract:** Валидация ограничения.
    ```sql
    ALTER TABLE orders VALIDATE CONSTRAINT fk_user;
    ```
    *Результат:* Сканирование таблицы без блокировки записи.

#### Валидация
- Проверка статуса в системном каталоге: `convalidated = true` в `pg_constraint`.

---

### Сценарий 3: Масштабирование в Kubernetes (Rolling Update)

#### Пошаговая инструкция
1. **Pre-deployment Job:** Выполняет фазу **Expand** (DDL).
2. **Rolling Update:** 
   - Поды V(N) читают/пишут в старую колонку.
   - Поды V(N+1) пишут в обе (или через триггер) и читают из новой.
3. **Post-deployment Job:** После того как 100% подов перешли на V(N+1), выполняется фаза **Contract**.

## Дополнительная информация

### Рекомендации и риски

- **Таймауты блокировок:** Всегда устанавливайте `lock_timeout` (2-5 сек). Даже фаза Expand может вызвать очередь блокировок, если БД занята долгим `SELECT`.
- **Риск "Потери данных при откате":** Если вы уже выполнили фазу **Contract** (удалили старую колонку), а затем откатили приложение к версии N — оно упадет. Не спешите с фазой Contract до полной стабилизации релиза.
- **Мониторинг:** Ключевые метрики — `Replication Lag` и `CPU Load` при работе триггеров.
