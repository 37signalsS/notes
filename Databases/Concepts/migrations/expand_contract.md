# Обратно-совместимые миграции: Принцип Expand-Contract

## Определения

- **Expand-Contract (Расширение-Сокращение)** — это паттерн внесения структурных изменений в базу данных, также известный как **Parallel Change**, который обеспечивает полную обратную совместимость между схемой БД и кодом приложения.
- **Обратная совместимость (Backward Compatibility):** состояние, при котором старая версия кода (N) корректно работает с новой схемой базы данных (N+1).
- **Zero-downtime Deployment:** процесс развертывания новой версии ПО без прекращения обслуживания пользователей, требующий применения паттерна Expand-Contract для изменений БД.

## Основные концепции

Паттерн разбивает одно атомарное разрушающее изменение (Breaking Change) на последовательность безопасных фаз, разделенных во времени.

### Три фазы процесса

1.  **Расширение (Expand):**
    - В базу данных добавляются новые элементы (колонки, таблицы, индексы).
    - Существующая структура остается нетронутой.
    - БД находится в "переходном" состоянии, поддерживая как старую, так и новую логику.
2.  **Миграция данных и кода (Migrate):**
    - Данные переносятся из старых структур в новые (обычно батчами).
    - Приложение переключается на чтение и запись в новые структуры.
    - Настраивается временная синхронизация для поддержки возможности отката приложения.
3.  **Сокращение (Contract):**
    - После подтверждения стабильности нового кода старые элементы схемы удаляются.
    - Удаляются временные механизмы синхронизации (триггеры, двойная запись).
    - Применяются окончательные ограничения (`NOT NULL`, `UNIQUE`).

### Методы синхронизации данных

| Метод | Описание | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Триггеры в БД** | Автоматическая синхронизация на уровне СУБД. | Гарантированная консистентность, прозрачность для кода. | Доп. нагрузка на I/O, сложность отладки логики в БД. |
| **Двойная запись (Dual Write)** | Приложение пишет данные в обе структуры одновременно. | Легко контролировать из кода, нет логики в БД. | Риск "состояния гонки" (race condition), усложнение кода. |
| **Shadow Read / Write** | Чтение из старого, запись в оба; сравнение результатов в фоне. | Безопасная проверка новой схемы перед переключением. | Требует развитой системы мониторинга и флагов фич. |
| **Представления (Views)** | Подмена таблицы представлением с тем же именем. | Полная прозрачность для приложения при переименованиях. | Может влиять на производительность сложных запросов. |

## Практические сценарии

### Сценарий 1: Изменение типа колонки или переименование (PostgreSQL)

Задача: изменить тип колонки `user_id` с `INT` на `BIGINT` в таблице с миллионами строк.

**Фаза 1: Expand**
```sql
-- Добавляем новую колонку
ALTER TABLE logs ADD COLUMN user_id_new BIGINT;

-- Создаем триггер для синхронизации новых записей
CREATE OR REPLACE FUNCTION sync_user_id() RETURNS TRIGGER AS $$
BEGIN
    NEW.user_id_new := NEW.user_id;
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_sync_user_id BEFORE INSERT OR UPDATE ON logs
FOR EACH ROW EXECUTE FUNCTION sync_user_id();
```

**Фаза 2: Migrate**
Перенос существующих данных порциями (см. **[Типовые сценарии миграций](scenarios.md)**):
```sql
UPDATE logs SET user_id_new = user_id WHERE user_id_new IS NULL;
```

**Фаза 3: Contract**
После деплоя кода, использующего `user_id_new`:
```sql
DROP TRIGGER trg_sync_user_id ON logs;
ALTER TABLE logs DROP COLUMN user_id;
ALTER TABLE logs RENAME COLUMN user_id_new TO user_id;
```

### Сценарий 2: Добавление внешнего ключа (Foreign Key)

Прямое добавление FK на большую таблицу вызывает блокировку всей таблицы для проверки существующих связей.

1.  **Expand:** Добавить FK с флагом `NOT VALID` (PostgreSQL).
    ```sql
    ALTER TABLE orders ADD CONSTRAINT fk_user 
    FOREIGN KEY (user_id) REFERENCES users(id) NOT VALID;
    ```
    *Результат:* Новые данные проверяются, старые — нет. Таблица не блокируется.
2.  **Migrate:** Проверка целостности данных в фоне.
3.  **Contract:** Валидация ограничения.
    ```sql
    ALTER TABLE orders VALIDATE CONSTRAINT fk_user;
    ```

### Сценарий 3: Развертывание в Kubernetes (Rolling Update)

Во время Rolling Update в кластере одновременно работают поды версий `N` и `N+1`.

1.  **Pre-stop Hook / Init Container:** Выполняет фазу `Expand`.
2.  **Приложение:** Версия `N` продолжает работать со старыми полями, версия `N+1` начинает работать с новыми (и, возможно, старыми через Dual Write).
3.  **Post-deployment Job:** Когда все поды обновлены до `N+1`, запускается фаза `Contract`.

## Дополнительная информация

### Рекомендации и риски

- **Таймауты блокировок:** Всегда устанавливайте `lock_timeout` в сессии перед выполнением DDL фаз Expand/Contract.
- **Риск "Потери данных при откате":** Если фаза `Contract` уже выполнена, откат приложения к версии `N` станет невозможным без восстановления данных из бэкапа или обратной миграции.
- **Производительность:** При использовании триггеров на таблицах с высокой частотой `UPDATE/INSERT` мониторьте `CPU Load` и `I/O Wait`.
