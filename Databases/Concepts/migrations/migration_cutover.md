# Cutover и Zero-Downtime миграции

**Актуально для:** PostgreSQL 11+, MySQL 8.0.12+, MariaDB 10.3+

## Определения

- **Cutover (переключение)** — финальный момент перехода от старой схемы/логики к новой в zero-downtime миграции. Включает прекращение записи в старые структуры, синхронизацию отложенных данных и активацию новой логики приложения.
- **Zero-Downtime Migration** — миграция схемы или данных, выполняемая без заметного простоя сервиса для пользователей. Достигается за счёт двусторонней совместимости (backward/forward compatibility) между кодом и схемой БД.
- **Dual-Write (двойная запись)** — стратегия, при которой приложение одновременно записывает данные в старую и новую структуру (или колонку/таблицу) в течение переходного периода. Используется для поддержания консистентности без потери данных при возможном откате.
- **Backfill (дозаполнение)** — перенос исторических данных из старых структур в новые (batching, с контролем нагрузки). Выполняется до cutover, как правило, фоновыми батчами.
- **Drain (опорожнение очередей)** — ожидание завершения обработки всех активных запросов/событий (в т.ч. из очередей/воркеров) перед финальным переключением, чтобы исключить потерю «в полёте».
- **Read-Path Compatibility** — способность старого кода корректно читать данные из новой схемы, а нового — из старой (ключевое условие rolling deploy).
- **Feature Flag (Feature Toggle)** — переключатель, позволяющий мгновенно активировать/деактивировать использование новой схемы/логики без повторного деплоя. Незаменим для безопасного cutover и быстрого отката по коду.

## Теоретический блок

### Zero-downtime и совместимость

Zero-downtime миграции опираются на принцип **двусторонней совместимости**:
1. **Старая версия кода (N)** должна корректно работать с новой схемой БД (N+1) — backward compatibility.
2. **Новая версия кода (N+1)** должна корректно работать со старой схемой БД (N) — forward compatibility.

Это позволяет выполнять rolling update (постепенная замена инстансов приложения) без остановки трафика. Паттерн **Expand-Contract** ([expand_contract.md](expand_contract.md)) реализует эту совместимость через поэтапное расширение схемы, миграцию данных, переключение (cutover) и сокращение.

### Модель cutover

Типовой переходный период при zero-downtime:

1. **Expand** — добавляем новые структуры, настраиваем синхронизацию (триггеры или Dual-Write). Старый код их игнорирует.
2. **Backfill** — батчами переносим исторические данные в новые структуры, обеспечивая консистентность (с проверками `IS NULL`/ключей).
3. **Verification (pre-cutover)** — проверяем полноту/консистентность (count/diff по ключам), лаг репликации, метрики нагрузки, блокировки.
4. **Drain + Freeze Window (cutover window)** — останавливаем или дренируем фоновые обработчики, писатели (где возможно), дожидаемся завершения активных транзакций. Применяем feature flag переключения.
5. **Cutover (atomic switch)** — атомарное переключение чтения/записи на новую схему (обычно через конфиг/feature flag, реже — `RENAME TABLE`).
6. **Post-cutover validation** — smoke-тесты, алерты, мониторинг ошибок/латентности (Golden Signals). Фиксируем успешность.
7. **Contract** — удаляем временные механизмы (триггеры, старые колонки), завершаем миграцию.

### Dual-Write: когда обязателен

Dual-Write обязателен, когда:
- Старый код продолжает писать в старую структуру, новый — в новую, и **нельзя остановить всю запись** на время переключения.
- Нужна **двусторонняя совместимость на случай отката** (код N может читать/корректно работать, если переключим обратно) — особенно при наличии данных, созданных новой версией.
- Приложение пишет в БД напрямую (не через очередь с replay).

**Риски Dual-Write:** race conditions, частичная успешность записи, усложнение кода. Альтернатива — триггеры БД (атомарны внутри транзакции), либо запись только в новую структуру + backfill + read-through/view.

### Backfill: безопасное дозаполнение

Ключевые принципы безопасного backfill:
- **Идемпотентность**: `UPDATE ... WHERE target IS NULL AND source IS NOT NULL`, проверка по PK/уникальному ключу.
- **Batching (порциями)**: фиксированный размер батча (например, 500–5000 строк), пауза между батчами для снижения нагрузки.
- **Throttling**: ограничение скорости (строк/сек), адаптация под CPU/IO/replication lag.
- **Rate limiting**: избегать всплесков, особенно в пиковые часы.
- **Circuit breaker**: при росте ошибок/лага — приостановить backfill, алертить.
- **Только неблокирующие операции** там, где критичен трафик (Postgres: `UPDATE` мелкими транзакциями, избегать долгих эксклюзивных блоков; MySQL: учитывать копирование/lock waits).

## Практический блок

### 1. Чек-лист Cutover (Production-ready)

Перед cutover обязательно проверить:

| Пункт | Что проверить | Критерий успеха |
|---|---|---|
| **Pre-checks** | Резервная копия (восстанавливаемость), lag репликации, активные долгие транзакции (`idle in transaction`), свободное место на диске | Бэкап протестирован/актуален, replication lag < целевого (обычно < 30с), долгих транзакций нет |
| **Консистентность** | Backfill завершён, расхождения между старым/новым (count, checksum по ключам) | `SELECT COUNT(*)`/diff = 0 по проверяемым критериям. Критичные инварианты выполнены |
| **Нагрузка** | CPU/IO, locks/waits, replication lag стабильны | Без растущего тренда, в пределах целевых значений |
| **Дренаж (drain)** | Фоновые воркеры/cron/jobs, очереди (Kafka/RabbitMQ), активные веб-сессии с записью | Очереди опустошены/остановлены, новые записи перенаправлены, активные write-транзакции завершены |
| **Окно cutover** | Согласовано (maintenance window), команды on-call в готовности, runbook утверждён | Коммуникация согласована, все знают ответственных |
| **Feature flags** | Флаги готовы, можно мгновенно откатить (kill-switch) | Переключение протестировано на staging (в т.ч. откат) |
| **Мониторинг** | Дашборды, алерты включены, трейсинг доступен | Ошибки/latency/RPS отслеживаются в реальном времени |
| **Rollback план** | Работоспособен, протестирован, критерии принятия решения определены | Decision criteria зафиксированы (когда откатывать, когда fix-forward) |

### 2. Пошаговый план Cutover (общий шаблон)

1. **Зафиксировать тайминг** (start/end cutover window). Уведомить команду/бизнес.
2. **Enable read-only/ограничение записи** (опционально) — уменьшает гонки в момент переключения. Альтернатива — drain без полной блокировки.
3. **Drain очередей/воркеров** — дождаться завершения in-flight обработчиков, не принимая новые write-задачи.
4. **Дождаться завершения backfill** + финальная сверка консистентности (быстрый diff по ключам).
5. **Проверить replication lag** — должен быть ~0 (или минимальный, стабилен).
6. **Переключить feature flag** (код N+1 активирует использование новой схемы). Предпочтительно атомарное переключение (env/config/remote flag).
7. **Разрешить запись/включить трафик** на новую логику.
8. **Post-cutover smoke tests** (критичные бизнес-пути). Мониторинг 5–15 минут в усиленном режиме.
9. **Фиксация статуса** (success/rollback), коммуникация команде.
10. **При успехе** — запустить Contract-фазу ([expand_contract.md](expand_contract.md)), удалить временные механизмы.

### 3. Backfill с batching + throttling (практика)

**PostgreSQL (без длительных блоков):**

`UPDATE` в PostgreSQL не поддерживает `LIMIT`, поэтому батч выделяется подзапросом/CTE по первичному ключу. `COMMIT` внутри `DO`-блока доступен начиная с PostgreSQL 11 и работает только при запуске блока вне явной транзакции (без обрамляющих `BEGIN`/`COMMIT`).

```sql
-- Батч backfill с паузой, идемпотентно (PostgreSQL 11+)
DO $$
DECLARE
  batch_size INT := 2000;
  affected INT;
BEGIN
  LOOP
    WITH batch AS (
      SELECT t.id FROM target t
      WHERE t.new_col IS NULL
      ORDER BY t.id
      LIMIT batch_size
      FOR UPDATE SKIP LOCKED -- пропускаем строки, заблокированные другими транзакциями
    )
    UPDATE target t
    SET new_col = s.old_col
    FROM source s
    WHERE t.id = s.id
      AND t.new_col IS NULL
      AND t.id IN (SELECT id FROM batch);
    GET DIAGNOSTICS affected = ROW_COUNT;
    EXIT WHEN affected = 0;
    COMMIT; -- фиксация батча: освобождение блокировок и WAL
    PERFORM pg_sleep(0.2); -- throttle 200мс
    RAISE NOTICE 'Backfilled % rows', affected;
  END LOOP;
END $$;
```

**MySQL (мелкие транзакции, контроль нагрузки):**

В MySQL `LIMIT` допустим только в одиночном `UPDATE`; в многотабличном синтаксисе (`UPDATE ... JOIN`) `ORDER BY` и `LIMIT` использовать нельзя. Выборка батча выполняется через двойную вложенность подзапроса — внешняя производная таблица обходит ошибку `1093 (ER_UPDATE_TABLE_USED)`. Итерацию и адаптивные паузы реализует внешний скрипт (Python/Go), проверяющий `ROW_COUNT()`.

```sql
-- Одна итерация батчинга; повторять, пока затронуто > 0 строк
UPDATE target t
INNER JOIN source s ON t.id = s.id
SET t.new_col = s.old_col
WHERE t.new_col IS NULL
  AND t.id IN (
    SELECT * FROM (
      SELECT id FROM target
      WHERE new_col IS NULL
      ORDER BY id
      LIMIT 2000
    ) AS batch
  );
-- → затронуто до 2000 строк (на последнем батче — меньше)
```

**Валидация консистентности перед cutover** (должна вернуть 0 расхождений):

```sql
-- PostgreSQL: IS DISTINCT FROM корректно сравнивает и NULL
SELECT count(*) FROM target t
JOIN source s ON t.id = s.id
WHERE t.new_col IS DISTINCT FROM s.old_col;
-- → 0

-- MySQL: null-safe сравнение через оператор <=>
SELECT count(*) FROM target t
JOIN source s ON t.id = s.id
WHERE NOT (t.new_col <=> s.old_col);
-- → 0
```

**Рекомендации по throttling:**
- Начинать консервативно (паузы 100–500мс), увеличивать/уменьшать по метрикам (replication lag, DB load, lock waits).
- Адаптивный throttle: замедляться при росте `replication lag` > порога, ускоряться при стабильной нагрузке.
- Никогда не гнаться за максимальной скоростью в пиковые часы — приоритет надёжности.

### 4. Dual-Write: шаблон и предосторожности

**Рекомендуемая последовательность внедрения Dual-Write (безопасная):**
1. **Expand** — добавить целевую структуру.
2. **Включить Dual-Write** (писать в обе структуры, читать из старой). Код должен писать атомарно в рамках бизнес-транзакции там, где возможно.
3. **Backfill** исторических данных (идемпотентно).
4. **Verify** консистентность (reconciliation) — сверка, алерты при расхождениях.
5. **Switch reads** (новый код читает из новой структуры) — через feature flag.
6. **Cutover writes** — переключить writes на новую (или оставить dual-write коротко для страховки).
7. **Disable Dual-Write** после стабильности (убрать дублирующую запись).
8. **Contract** — удалить старую структуру.

**Предосторожности:** избегать гонок (использовать версионирование/updated_at, триггеры предпочтительнее для строгой атомарности внутри БД-транзакции). Логировать расхождения при reconciliation (мониторить drift).

## Устранение неисправностей

Разбор типовых проблем батчинга (зависший батч, bloat, `lock_timeout`, истощение connection pool) см. в **[Мониторинг миграций](monitoring.md)** и **[Безопасные массовые операции](../safe_large_scale_data_modification.md)**. Ниже — сбои, специфичные именно для фазы cutover:

| Паттерн | Возможная причина | Диагностика и решение |
| :--- | :--- | :--- |
| **Расхождение dual-write на момент cutover** | Гонка между записью приложения и синхронизирующим триггером; частичная успешность записи | Запрос сверки (`IS DISTINCT FROM` / `<=>`) показывает расхождения > 0. **Решение:** отложить cutover, дозаполнить расхождения, найти источник гонки (порядок операций в коде), повторить сверку |
| **Drain не завершается** | Воркер/consumer завис, очередь не опустевает, in-flight транзакции долгие | `pg_stat_activity` (PostgreSQL) / `SHOW PROCESSLIST` (MySQL), `consumer_lag` в Kafka/RabbitMQ. **Решение:** не переключать, пока очередь не опустеет; принудительный дренаж с таймаутом; при необходимости — ручная достройка событий |
| **Рост replication lag в момент переключения** | Слишком крупный финальный батч, отсутствие индекса на фильтрующей колонке | Уменьшить `batch_size`, проверить `EXPLAIN ANALYZE`, дождаться лага ≈ 0 перед переключением флага |
| **Откат кода после переключения записи на новую схему** | Старый код (N) не видит данные, записанные новым кодом в новую структуру — «логический разрыв» | **Решение:** обратная синхронизация (триггер new→old) или Fix-Forward. Kill-switch флаг должен быть протестирован с учётом направления записи; см. **[Стратегии отката](rollback_strategies.md)** |
| **`RENAME TABLE` зависает (MySQL/MariaDB)** | Активные транзакции удерживают metadata lock на таблице | `SHOW PROCESSLIST` / `sys.schema_table_lock_waits`; завершить блокирующий поток (`KILL <thread_id>`) или повторить в окно минимальной нагрузки |
| **Переключение «по кускам» вместо атомарного** | Многотабличное `RENAME` разбито на отдельные инструкции | В MySQL `RENAME TABLE a TO b, c TO d` атомарен — выполняйте все переименования одним оператором. В PostgreSQL — оборачивать в одну транзакцию (транзакционный DDL) |
| **Backfill повторно обрабатывает строки** | Неидемпотентное условие выборки (нет `WHERE target IS NULL` или проверки по PK) | Добавить идемпотентное условие и сортировку по PK; повторный запуск не должен менять результат |
| **Данные «старее» перезаписывают «новее» при dual-write** | Clock skew: часы инстансов приложения расходятся, версионирование по `updated_at` ненадёжно | Версировать средствами БД (триггер, системный столбец `xmin`) или сравнивать версии в одной транзакции |
| **Триггеры/артефакты остались после неудачного cutover** | Фаза Contract не выполнена при прерывании миграции | `SELECT tgname FROM pg_trigger WHERE tgrelid = 'target'::regclass;` (PostgreSQL) / `SHOW TRIGGERS LIKE 'target';` (MySQL). Удалить синхронизирующие триггеры, если запись уже переключена |

## Пограничные случаи и ограничения

- **Несколько писателей (multi-writer):** если в БД пишут несколько сервисов напрямую, Dual-Write обязателен во всех писателях, а `RENAME`-подход неприменим — переключение только через конфиг/флаги.
- **Невозможность полного дренажа** (24/7 фоновые задачи): короткое окно переключения + Dual-Write + финальный reconciliation; либо «пауза» запросов на уровне прокси (pgBouncer/ProxySQL) — см. **[Типовые сценарии миграций](scenarios.md)**.
- **Атомарность переключения зависит от СУБД:** PostgreSQL поддерживает транзакционный DDL — переключение схемы можно выполнить в одной транзакции с откатом при ошибке. MySQL/MariaDB: многотабличный `RENAME TABLE` атомарен, но DDL вызывает неявный коммит — откат средствами СУБД невозможен, только Fix-Forward или бэкап.
- **Таблицы > 1 ТБ:** стандартный backfill занимает дни — используйте `gh-ost`/`pt-online-schema-change` (подробности: [Online Schema Change в MySQL](../../MySQL/Operations/online-schema-change.md), [Online Schema Change в MariaDB](../../MariaDB/online_schema_change.md)).
- **Миграция между СУБД** (например, MySQL → PostgreSQL): cutover через CDC — останов записи в source, drain очереди, переключение; см. сценарий CDC в **[Типовых сценариях миграций](scenarios.md)**.
- **Секционированные таблицы:** cutover можно выполнять по секциям, снижая окно риска; переключение родительской таблицы — последним шагом.

## Лучшие практики

- **Kill-switch проверяется на staging с реальными объёмами**, включая сценарий «флаг выключен после записи в новую схему» — иначе откат превращается в потерю данных.
- **Критерии cutover/rollback фиксируются до старта** в runbook: пороги ошибок, рост latency p95/p99, replication lag, потеря консистентности.
- **Post-cutover наблюдение 5–15 минут в усиленном режиме** (Golden Signals), затем — плавное снижение частоты алертов.
- **Очистка (cleanup) после стабилизации:** удалить feature flags и мёртвый код, синхронизирующие триггеры, старые колонки (фаза Contract), выполнить `ANALYZE` для обновления статистики, проверить, что autovacuum восстановил нормальный режим (bloat после массовых DML — см. **[Безопасные массовые операции](../safe_large_scale_data_modification.md)**).
- **Предпочтение — feature-flag driven cutover + fix-forward** вместо принудительного отката БД при некритичных проблемах.
