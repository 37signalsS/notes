# Стратегии отката миграций баз данных

## Определения

**Откат миграции (Rollback)** — процедура возврата схемы и данных базы данных к состоянию, предшествовавшему выполнению изменений. Цель — восстановление работоспособности системы при обнаружении критических ошибок или деградации производительности после деплоя.

**Down-миграция (Undo)** — скрипт, содержащий SQL-команды, обратные действиям в основной миграции (например, `DROP COLUMN` для отмены `ADD COLUMN`).

**Логическая консистентность при откате** — состояние, при котором данные, записанные новым кодом приложения в новую схему, корректно обрабатываются или сохраняются при возврате к старой схеме.

## Основные концепции

Откат миграции в production-среде — это рискованная операция, требующая предварительного планирования.

### Уровни стратегий отката

1. **Сценарный (Down-скрипты):**
   - Самый быстрый способ.
   - Подходит для простых DDL операций.
   - *Риск:* Потеря данных при `DROP TABLE/COLUMN`. Часто `down`-скрипт для удаления данных является «фиктивным» (невозможно восстановить удаленное без бэкапа).

2. **Инфраструктурный (Снапшоты и Точки восстановления):**
   - Использование `pg_create_restore_point` (PostgreSQL) или снапшотов хранилища.
   - Гарантирует 100% восстановление состояния.
   - *Риск:* Высокий RTO (время восстановления) для больших БД и потеря данных, записанных между миграцией и моментом обнаружения ошибки.

3. **Логический (Feature Flags):**
   - Самый безопасный метод.
   - Приложение поддерживает обе версии схемы (см. **[Expand-Contract](expand_contract.md)**).
   - Откат сводится к выключению флага в коде, база данных не затрагивается.

### Проблема «Логического разрыва»

Если после миграции (Expand) код версии `N+1` записал данные в новые поля, а затем потребовался откат к коду версии `N`, данные в новых полях могут стать недоступными для старого кода. Без настроенной синхронизации (триггеров) этот «разрыв» может привести к потере бизнес-данных.

## Практические сценарии

### Сценарий 1: Именованные точки восстановления (PostgreSQL)

Рекомендуется для сложных миграций данных (DML), которые трудно отменить скриптом.

```sql
-- 1. Перед запуском миграции создаем точку восстановления
SELECT pg_create_restore_point('before_migration_v42');

-- 2. Выполняем миграцию
-- ...

-- 3. В случае критического сбоя, выполняем восстановление (PITR) 
-- до указанной точки в recovery.conf / postgresql.auto.conf:
-- recovery_target_name = 'before_migration_v42'
```
*Подробнее о технике PITR см. в **[Общих стратегиях отката](../rollback_strategies.md)**.*

### Сценарий 2: Откат через Drop-триггеры (Down-миграция)

При использовании паттерна Expand-Contract, откат сводится к удалению триггеров синхронизации и новых колонок.

```sql
-- U20260718__add_user_bio.sql (UNDO)
BEGIN;
  -- Удаляем триггер, который синхронизировал данные
  DROP TRIGGER IF EXISTS trg_sync_bio ON users;
  DROP FUNCTION IF EXISTS sync_bio_func();
  
  -- Удаляем новую колонку (ВНИМАНИЕ: данные будут потеряны)
  ALTER TABLE users DROP COLUMN bio;
COMMIT;
```

### Сценарий 3: Автоматизированный «горячий» бэкап

Для БД среднего размера (<100 ГБ) в пайплайне CI/CD.

```bash
#!/bin/bash
# Запуск в составе CI Job
BACKUP_FILE="/tmp/pre_mig_$(date +%s).sql"

# Сделать быстрый бэкап структуры и метаданных
pg_dump -Fc -s -h $DB_HOST $DB_NAME > $BACKUP_FILE

# Попытка миграции
if ! flyway migrate; then
  echo "Migration failed, rolling back schema..."
  pg_restore -c -h $DB_HOST -d $DB_NAME $BACKUP_FILE
  exit 1
fi
```

## Дополнительная информация

### Рекомендации SRE

- **Избегайте автоматических откатов схемы:** В production-среде откат схемы должен быть осознанным решением администратора БД, так как он почти всегда ведет к потере данных.
- **Двусторонняя совместимость:** Стремитесь к тому, чтобы код версии `N` мог работать со схемой версии `N+1`. Это делает откат кода тривиальным и не требующим отката БД.
- **Проверка Down-скриптов:** На staging-среде процедура деплоя должна включать тест: `Migrate Up -> Verify -> Migrate Down -> Verify`.
