# Стратегии отката миграций баз данных

## Определения

**Откат миграции (Rollback)** — процедура возврата схемы и данных базы данных к состоянию, предшествовавшему выполнению изменений. Цель — восстановление работоспособности системы при обнаружении критических ошибок или деградации производительности после деплоя.

**Down-миграция (Undo)** — скрипт, содержащий SQL-команды, обратные действиям в основной миграции (например, `DROP COLUMN` для отмены `ADD COLUMN`).

**Roll-forward (Компенсирующая миграция)** — стратегия исправления ошибок путем наката новой миграции поверх проблемной (например, `V5` исправляет ошибку в `V4`), вместо удаления изменений. Считается предпочтительной для сохранения данных в высоконагруженных системах.

**Транзакционный DDL (Transactional DDL)** — способность СУБД выполнять изменения схемы (CREATE, ALTER, DROP) внутри транзакции. При сбое транзакции изменения схемы откатываются автоматически.

**Логическая консистентность при откате** — состояние, при котором данные, записанные новым кодом приложения в новую схему, корректно обрабатываются или сохраняются при возврате к старой схеме.

## Основные концепции

Откат миграции в production-среде — это рискованная операция, требующая предварительного планирования. Основная сложность заключается в том, что база данных — это состояние (State), в то время как код приложения обычно не имеет состояния (Stateless).

### Поддержка транзакционного DDL

Выбор стратегии отката критически зависит от возможностей используемой СУБД:

| СУБД | Поддержка транзакционного DDL | Комментарий |
| :--- | :--- | :--- |
| **PostgreSQL** | Полная | Почти все операции (кроме CREATE INDEX CONCURRENTLY) транзакционны. |
| **MySQL / MariaDB** | Отсутствует | DDL-команды вызывают неявный коммит (`Implicit Commit`). Частичный откат невозможен. |
| **Oracle** | Ограниченная | Требует специальных блоков, но большинство DDL фиксируются немедленно. |
| **SQL Server** | Полная | Поддерживает DDL внутри `BEGIN TRANSACTION`. |

### Откат (Roll-back) vs Накат вперед (Roll-forward)

В 2026 году индустриальный стандарт сместился в сторону Roll-forward для stateful-изменений:

1.  **Roll-back (Откат):**
    *   **Применение:** Быстрое исправление логических ошибок в коде приложения.
    *   **Риск:** Высокая вероятность потери данных, если миграция была деструктивной (DROP).
    *   **Условие:** Требует обратной совместимости (старый код должен работать с новой схемой).

2.  **Roll-forward (Накат вперед):**
    *   **Применение:** Исправление ошибок в структуре данных без возврата к старой версии схемы.
    *   **Преимущество:** Сохранение «таймлайна» изменений и минимизация рисков при отсутствии транзакционного DDL.

### Уровни стратегий отката

1. **Сценарный (Down-скрипты):**
   - Самый быстрый способ.
   - Подходит для простых DDL операций.
   - *Риск:* Потеря данных при `DROP TABLE/COLUMN`. Часто `down`-скрипт для удаления данных является «фиктивным» (невозможно восстановить удаленное без бэкапа).

2. **Инфраструктурный (Снапшоты и Точки восстановления):**
   - Использование `pg_create_restore_point` (PostgreSQL) или снапшотов хранилища.
   - Гарантирует 100% восстановление состояния.
   - *Риск:* Высокий RTO (время восстановления) для больших БД и потеря данных, записанных между миграцией и моментом обнаружения ошибки.

3. **Логический (Feature Flags):**
   - Самый безопасный метод.
   - Приложение поддерживает обе версии схемы (см. **[Expand-Contract](expand_contract.md)**).
   - Откат сводится к выключению флага в коде, база данных не затрагивается.

### Проблема «Логического разрыва»

Если после миграции (Expand) код версии `N+1` записал данные в новые поля, а затем потребовался откат к коду версии `N`, данные в новых полях могут стать недоступными для старого кода. Без настроенной синхронизации (триггеров) этот «разрыв» может привести к потере бизнес-данных. Рекомендуется использовать паттерн **[Expand-Contract](expand_contract.md)** для обеспечения двусторонней совместимости.

## Практические сценарии

### Сценарий 1: Именованные точки восстановления (PostgreSQL)

Рекомендуется для сложных миграций данных (DML), которые трудно отменить скриптом.

```sql
-- 1. Перед запуском миграции создаем точку восстановления
SELECT pg_create_restore_point('before_migration_v42');

-- 2. Выполняем миграцию
-- ...

-- 3. В случае критического сбоя, выполняем восстановление (PITR) 
-- до указанной точки в recovery.conf / postgresql.auto.conf:
-- recovery_target_name = 'before_migration_v42'
```
*Подробнее о технике PITR см. в **[Общих стратегиях отката](../rollback_strategies.md)**.*

### Сценарий 2: Откат через Drop-триггеры (Down-миграция)

При использовании паттерна Expand-Contract, откат сводится к удалению триггеров синхронизации и новых объектов.

```sql
-- U20260718__add_user_bio.sql (UNDO)
BEGIN;
  -- 1. Удаляем триггер, который синхронизировал данные между старой и новой колонками
  DROP TRIGGER IF EXISTS trg_sync_bio ON users;
  DROP FUNCTION IF EXISTS sync_bio_func();
  
  -- 2. Удаляем новую колонку (ВНИМАНИЕ: данные будут потеряны)
  -- Выполнять только после того, как код приложения перестал использовать это поле.
  ALTER TABLE users DROP COLUMN bio;
COMMIT;
```

### Сценарий 3: Автоматизированный бэкап в CI/CD

Для БД среднего размера в пайплайне CI/CD перед применением миграции.

```bash
#!/bin/bash
# Запуск в составе CI Job
BACKUP_FILE="/tmp/pre_mig_$(date +%s).sql"

# ВАЖНО: Выбор типа бэкапа
# -s (schema-only) - быстро, только структура. Безопасно для DDL.
# Без -s - полный бэкап. Обязателен, если миграция содержит UPDATE/DELETE.
pg_dump -Fc -h $DB_HOST $DB_NAME > $BACKUP_FILE

# Попытка миграции
if ! flyway migrate; then
  echo "Migration failed, rolling back..."
  # -c (clean) удаляет объекты перед восстановлением
  pg_restore -c -h $DB_HOST -d $DB_NAME $BACKUP_FILE
  exit 1
fi
```

### Сценарий 4: Roll-forward (Компенсирующая миграция)

Применяется, когда откат (Rollback) невозможен или слишком рискован из-за накопленных данных.

1.  **Проблема:** Миграция `V10` добавила колонку с ошибкой в типе данных, и в нее уже записаны тысячи строк.
2.  **Решение:** Создаем миграцию `V11`, которая исправляет тип данных `V10`, сохраняя текущую информацию.
3.  **Преимущество:** Отсутствие простоя и риска удаления данных, которые были записаны в интервале между `V10` и `V11`.

## Связь с моделями ветвления и CI/CD

Выбор стратегии отката базы данных тесно связан с используемой моделью ветвления Git:

*   **Trunk-Based Development и GitHub Flow:**
    *   **Приоритет:** **Roll-forward**. В условиях непрерывной доставки (CD) и высокой частоты релизов классический откат схемы (Rollback) часто нецелесообразен, так как он блокирует конвейер.
    *   **Метод:** Ошибка исправляется «ходом вперед» — быстрым созданием нового Hotfix-PR в основной ветке, который исправляет проблему в структуре данных.
*   **Git Flow и GitLab Flow:**
    *   **Приоритет:** **Roll-back** или **Инфраструктурный откат**. Поскольку релиз является запланированным событием, часто есть время на использование Down-скриптов или восстановление из снапшотов/точек восстановления, созданных непосредственно перед релизом.

## Дополнительная информация

### Чек-лист SRE перед откатом

- [ ] **Оценка потери данных:** Сколько записей будет удалено при выполнении `DROP`? Есть ли возможность их сохранить?
- [ ] **Состояние приложения:** Откачен ли код приложения (App Revert) до версии, совместимой со старой схемой?
- [ ] **Лаг репликации:** Не приведет ли массовый откат (например, удаление большой таблицы) к остановке репликации или переполнению WAL/бинлогов?
- [ ] **Тестирование на суррогате:** Выполнялся ли `Migrate Down` на актуальном дампе продакшена в Staging-среде?

### Рекомендации по безопасности

- **Избегайте автоматических откатов схемы:** В production-среде откат схемы должен быть осознанным решением администратора БД, так как он почти всегда ведет к потере данных.
- **Двусторонняя совместимость:** Стремитесь к тому, чтобы код версии `N` мог работать со схемой версии `N+1`. Это делает откат кода тривиальным и не требующим отката БД.
- **Проверка Down-скриптов:** На staging-среде процедура деплоя должна включать тест: `Migrate Up -> Verify -> Migrate Down -> Verify`.
- **Использование dry-run:** Всегда проверяйте SQL-команды отката вручную через `EXPLAIN` или инструменты вроде `migration-lint`.
