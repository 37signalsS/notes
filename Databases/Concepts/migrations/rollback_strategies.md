# Стратегии отката миграций баз данных

## Определения

- **Откат миграции (Rollback)** — комплексная процедура возврата схемы и данных базы данных к состоянию, предшествовавшему выполнению изменений. Применяется при обнаружении критических ошибок, нарушении консистентности или деградации производительности после деплоя.
- **Down-миграция (Undo)** — скрипт (SQL или код), содержащий команды, логически обратные действиям в основной (Up) миграции (например, `DROP COLUMN` для отмены `ADD COLUMN`).
- **Roll-forward (Компенсирующая миграция / Fix-Forward)** — стратегия исправления ошибок путем наката новой миграции поверх проблемной (например, `V5` исправляет ошибку в `V4`), вместо физического удаления изменений. Это предпочтительный метод для высоконагруженных Production-систем.
- **Транзакционный DDL (Transactional DDL)** — способность СУБД выполнять команды изменения структуры (CREATE, ALTER, DROP) внутри транзакционного блока. Гарантирует атомарность: при ошибке миграции БД автоматически возвращается к исходному состоянию без ручного вмешательства.
- **Логическая консистентность при откате** — состояние, при котором данные, записанные новым кодом приложения (версии N+1) в новую схему, корректно обрабатываются или сохраняются при вынужденном возврате к старой схеме и старому коду (версии N).

## Основные концепции

Откат миграции в production-среде — это рискованная операция, требующая предварительного планирования. Основная сложность заключается в том, что база данных — это состояние (State), в то время как код приложения обычно не имеет состояния (Stateless).

### Поддержка транзакционного DDL в современных СУБД

Выбор стратегии отката критически зависит от возможностей используемой СУБД:

| СУБД | Транзакционный DDL | Особенности и комментарии |
| :--- | :--- | :--- |
| **PostgreSQL** | Полная | Почти все операции транзакционны. **Исключение:** `CREATE/DROP INDEX CONCURRENTLY`. |
| **MySQL / MariaDB** | Отсутствует | DDL-команды вызывают неявный коммит (`Implicit Commit`). Частичный откат миграции из нескольких команд невозможен. |
| **Oracle** | Ограниченная | Большинство DDL фиксируются немедленно. Требует использования процедурных блоков для имитации транзакционности. |
| **SQL Server** | Полная | Поддерживает DDL внутри `BEGIN TRANSACTION`. |

### Откат (Roll-back) vs Накат вперед (Roll-forward)

В современной SRE-практике (актуально на 2026 год) стандартом является Roll-forward для stateful-изменений:

1.  **Roll-back (Классический откат):**
    *   **Применение:** Быстрое исправление ошибок в коде приложения или простых опечаток в DDL.
    *   **Риск:** Высокая вероятность необратимой потери данных, если миграция была деструктивной (`DROP TABLE`, `ALTER TYPE`).
    *   **Условие:** Требует обратной совместимости (старый код должен "уметь" работать с новой схемой).

2.  **Roll-forward (Fix-Forward):**
    *   **Применение:** Исправление ошибок в структуре данных без возврата к старой версии схемы.
    *   **Преимущество:** Сохранение «таймлайна» изменений. Минимизация рисков при отсутствии транзакционного DDL в СУБД.

### Уровни стратегий отката

1. **Сценарный (Down-скрипты):**
   - **Суть:** SQL-скрипты отката (Undo). Самый быстрый способ для простых DDL.
   - **Риск:** Потеря данных при `DROP`. Часто `down`-скрипт является «фиктивным» (невозможно восстановить удаленные данные без бэкапа).
2. **Инфраструктурный (Снапшоты и Точки восстановления):**
   - **Суть:** Использование `pg_create_restore_point` (PostgreSQL), снапшотов хранилища (ZFS/LVM) или PITR.
   - **Плюс:** Гарантирует 100% восстановление состояния на момент времени.
   - **Риск:** Высокий RTO (время восстановления) для больших БД и потенциальная потеря данных, записанных между миграцией и моментом обнаружения ошибки.
3. **Логический (Feature Flags и Feature Toggles):**
   - **Суть:** Приложение поддерживает обе версии схемы через паттерн **[Expand-Contract](expand_contract.md)**.
   - **Плюс:** Откат сводится к мгновенному переключению флага в коде, база данных при этом не затрагивается физически.

### Проблема «Логического разрыва»

Если после миграции (фаза Expand) код версии `N+1` записал данные в новые поля, а затем потребовался откат к коду версии `N`, данные в новых полях могут стать недоступными для старого кода. Без настроенной синхронизации (триггеров) этот «разрыв» приводит к потере бизнес-данных. Рекомендуется использовать паттерн **[Expand-Contract](expand_contract.md)** для обеспечения двусторонней совместимости (Dual Write / Triggers).

## Практические сценарии

### Сценарий 1: Именованные точки восстановления (PostgreSQL)

Рекомендуется для сложных миграций данных (DML), которые трудно или невозможно безопасно отменить скриптом.

#### Предпосылки
- БД работает в режиме архивации WAL (`wal_level = replica` или выше).
- Наличие прав `SUPERUSER`.

#### Пошаговая инструкция
1. **Создание точки:** Выполнить непосредственно перед запуском миграции (например, через CI/CD джобу).
   ```sql
   -- На мастере
   SELECT pg_create_restore_point('before_migration_v2026_08_17');
   ```
2. **Выполнение миграции:** С помощью Flyway, Liquibase или Atlas.
3. **Восстановление (PITR):** В случае критического сбоя выполнить восстановление до указанной точки. Для PostgreSQL 12+ в `postgresql.auto.conf` или через параметры запуска:
   ```conf
   recovery_target_name = 'before_migration_v2026_08_17'
   ```
   *Подробнее о технике PITR см. в **[Общих стратегиях отката](../rollback_strategies.md)**.*

#### Валидация
- Проверка логов СУБД: сообщение `recovery stopping at restore point "..."`.

### Сценарий 2: Откат через Drop-триггеры (Down-миграция)

Применяется в рамках паттерна **Expand-Contract** для удаления временных механизмов синхронизации.

#### Предпосылки
- Миграция выполнялась с использованием триггеров для обеспечения обратной совместимости.

#### Пошаговая инструкция
При необходимости отката миграции, которая добавила новую колонку `bio` с триггером синхронизации:

```sql
-- U20260718__add_user_bio.sql (UNDO)
BEGIN;
  -- 1. Удаляем триггер, который синхронизировал данные
  DROP TRIGGER IF EXISTS trg_sync_bio ON users;
  DROP FUNCTION IF EXISTS sync_bio_func();
  
  -- 2. Удаляем новую колонку (ВНИМАНИЕ: накопленные за время релиза данные будут потеряны)
  -- Выполнять только если бизнес-риск потери этих данных ниже риска работы с багом.
  ALTER TABLE users DROP COLUMN IF EXISTS bio;
COMMIT;
```

#### Валидация
- `SELECT * FROM information_schema.triggers WHERE trigger_name = 'trg_sync_bio';` (должен вернуть 0 строк).

### Сценарий 3: Автоматизированный бэкап в CI/CD пайплайне

Подходит для БД среднего размера (< 100 ГБ), где время создания и восстановления из дампа приемлемо для SLA.

#### Предпосылки
- Наличие свободного места в хранилище бэкапов.
- Настроенные утилиты `pg_dump` / `pg_restore` в окружении раннера.

#### Пошаговая инструкция (Bash-скрипт для CI)
```bash
#!/bin/bash
# Запуск в составе CI Job перед деплоем схемы
BACKUP_FILE="/tmp/pre_mig_$(date +%s).sql"

echo "Creating safety backup..."
# -s (schema-only) - быстро, безопасно для DDL. Без -s - полный бэкап (нужен для DML).
pg_dump -Fc -h $DB_HOST -U $DB_USER $DB_NAME > $BACKUP_FILE

echo "Starting migration..."
if ! flyway migrate; then
  echo "CRITICAL: Migration failed, initiating automated rollback..."
  # -c (clean) удаляет объекты перед восстановлением
  pg_restore -c -h $DB_HOST -U $DB_USER -d $DB_NAME $BACKUP_FILE
  exit 1
fi
```

#### Устранение неисправностей
- **Ошибка `Insufficient space`:** Очистите старые дампы перед запуском миграции.

### Сценарий 4: Roll-forward (Компенсирующая миграция)

Используется, когда откат (Rollback) невозможен или слишком рискован из-за объема накопленных "новых" данных.

#### Пошаговая инструкция
1. **Проблема:** Миграция `V10` добавила колонку с неверным ограничением (например, `CHECK (price > 100)` вместо `CHECK (price > 0)`), и в нее уже записаны тысячи строк.
2. **Решение:** Вместо `DROP COLUMN` создаем миграцию `V11`, которая исправляет констрейнт.
   ```sql
   -- V11__fix_price_constraint.sql
   ALTER TABLE orders DROP CONSTRAINT chk_price_limit;
   ALTER TABLE orders ADD CONSTRAINT chk_price_positive CHECK (price > 0);
   ```
3. **Преимущество:** Сохранение данных, отсутствие простоя, чистая история миграций.

## Связь со стратегиями ветвления и CI/CD

Выбор стратегии отката базы данных тесно связан с используемой моделью разработки:

- **Trunk-Based Development (GitHub Flow):**
    - **Приоритет:** **Roll-forward**. Высокая частота релизов требует быстрого исправления ошибок «ходом вперед» новыми коммитами в `main`, чтобы не блокировать конвейер доставки.
- **Git Flow (GitLab Flow):**
    - **Приоритет:** **Roll-back** или **Инфраструктурный откат**. Релизы более редкие и плановые, часто есть временное окно на использование Down-скриптов или восстановление из снапшотов.

## Дополнительная информация

### SRE Чек-лист перед выполнением отката

- [ ] **Оценка потери данных:** Какой объем записей, созданных новым кодом, будет безвозвратно удален при выполнении `DROP`?
- [ ] **Состояние приложения:** Откачен ли код приложения (App Revert) до версии N, совместимой со старой схемой?
- [ ] **Лаг репликации:** Не приведет ли массовый откат (например, удаление большой таблицы) к остановке репликации или переполнению WAL/бинлогов?
- [ ] **Тестирование на суррогате:** Проверялся ли скрипт `Undo` на актуальном дампе продакшена в Staging-среде?

### Рекомендации по безопасности

- **Запрет автоматических откатов схемы:** В Production откат БД должен быть осознанным решением администратора/SRE, а не автоматическим действием CI/CD.
- **Двусторонняя совместимость:** Стремитесь к тому, чтобы код версии `N` корректно работал со схемой `N+1`. Это делает откат приложения тривиальным и безопасным.
- **Проверка Down-скриптов:** На Staging-среде процедура деплоя должна всегда включать цикл: `Migrate Up -> Verify -> Migrate Down -> Verify`.
- **Использование dry-run:** Всегда проверяйте SQL-команды отката вручную через `EXPLAIN` или `atlas migrate diff --dry-run`.
