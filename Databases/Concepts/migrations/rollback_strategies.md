# Стратегии отката миграций баз данных

## Определения

**Откат миграции (Rollback)** — это процедура возврата схемы и данных базы данных к состоянию, которое предшествовало выполнению конкретной миграции или группы миграций. Откат необходим в случае обнаружения критических ошибок, проблем с производительностью или несовместимости с кодом приложения после релиза.

## Основные концепции

### Подходы к откату

1. **Скриптовый откат (Down-миграции):** создание парного файла для каждой миграции, который выполняет обратное действие (например, `DROP COLUMN` для миграции `ADD COLUMN`).
2. **Восстановление из бэкапа (Restore):** полная замена текущего состояния БД снимком данных, сделанным до начала миграций.
3. **Логический откат (Feature Flags):** использование переключателей в коде приложения для возврата к старой логике работы с данными без изменения самой схемы БД.

### Когда откат невозможен или опасен

- **Потеря данных:** при удалении колонки (`DROP COLUMN`) данные в ней теряются безвозвратно, если не был сделан бэкап.
- **Размер данных:** на терабайтных таблицах откат через восстановление из бэкапа может занять часы, что недопустимо для production-систем.
- **Разрыв целостности:** если после миграции приложение успело записать новые данные, простой откат схемы может привести к потере этих записей.

## Практические сценарии

### Сценарий 1: Использование Down-миграций

Подход популярен в инструментах вроде Flyway или Liquibase.

```sql
-- V2__add_phone_column.sql (Миграция UP)
ALTER TABLE users ADD COLUMN phone VARCHAR(20);

-- U2__add_phone_column.sql (Миграция DOWN/Rollback)
ALTER TABLE users DROP COLUMN phone;
```

### Сценарий 2: Автоматизированный бэкап перед миграцией

Скрипт для создания моментального снимка перед запуском инструмента миграций.

```bash
#!/bin/bash
# backup_before_migration.sh

# 1. Создание бэкапа
BACKUP_NAME="pre_migration_$(date +%Y%m%d_%H%M%S).sql"
pg_dump -h $DB_HOST -U $DB_USER $DB_NAME > $BACKUP_NAME

# 2. Попытка выполнить миграцию
flyway migrate

# 3. Проверка результата и автоматический откат при сбое
if [ $? -ne 0 ]; then
    echo "Ошибка миграции. Начинаю восстановление..."
    psql -h $DB_HOST -U $DB_USER $DB_NAME < $BACKUP_NAME
    echo "Восстановление завершено."
    exit 1
fi
```

### Сценарий 3: Переключение логики через Feature Flags

Позволяет мгновенно «откатиться» на уровне кода, не затрагивая базу данных.

```python
# Пример использования флага в приложении
if feature_flags.is_enabled('new_user_schema'):
    # Использование новой структуры (например, после миграции)
    user = UserV2.query.get(user_id)
else:
    # Использование старой структуры (безопасный путь)
    user = User.query.get(user_id)

# В случае проблем: просто выключаем флаг в панели управления
```

## Дополнительная информация

### Рекомендации

- **Тестирование отката:** всегда проверяйте выполнение `down`-скриптов на staging-окружении перед деплоем.
- **Точки восстановления:** при выполнении сложных миграций в PostgreSQL используйте именованные точки восстановления (`pg_create_restore_point`).
- **Expand-Contract:** для минимизации необходимости в «горячем» откате используйте стратегию обратно-совместимых миграций — **[Принцип Expand-Contract](expand_contract.md)**.
