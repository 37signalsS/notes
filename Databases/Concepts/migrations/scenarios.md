# Типовые сценарии миграций

## Определения

- **Миграционные сценарии** — это проверенные последовательности операций по изменению схемы (DDL) или состава данных (DML) базы данных, адаптированные под конкретные требования доступности (uptime) и объемы данных.
- **Схема-миграция (Schema Migration)** — изменение структуры таблиц, индексов, представлений или ограничений.
- **Дата-миграция (Data Migration)** — преобразование, перенос или очистка самих данных внутри существующей или новой структуры.
- **Online Schema Change (OSC)** — процесс изменения схемы таблицы без её блокировки на чтение и запись, обычно реализуемый через создание теневой копии.

## Основные концепции

- **Zero-downtime (без простоя):** архитектурный подход, позволяющий обновлять БД без остановки приложения. Достигается за счет обеспечения совместимости версии приложения $N$ со схемой $N+1$ и наоборот.
- **Пакетная обработка (Batching):** разделение одной крупной операции на множество мелких транзакций. Это предотвращает:
    - Длительные эксклюзивные блокировки.
    - Переполнение журналов транзакций (WAL в PostgreSQL, Redo Log в Oracle).
    - Раздувание лага репликации.
- **Принцип «Expand-Contract»:** трехфазный процесс (расширение -> миграция -> сужение), минимизирующий риски при деплое.
- **Теневые таблицы (Shadow Tables):** создание копии таблицы с новой структурой, синхронизация данных через триггеры или чтение бинарных логов, и финальная подмена (swap) оригинальной таблицы.

## Практические сценарии

### Сценарий 1: Добавление колонки без простоя (Zero-downtime Add Column)

Используется для добавления новых полей, в том числе обязательных (`NOT NULL`).

**Современные СУБД (оптимизированный DDL):**
- **PostgreSQL 11+:** Добавление колонки с `DEFAULT` выполняется мгновенно (изменение только в системном каталоге).
- **MySQL 8.0.12+:** Поддержка `ALGORITHM=INSTANT` для большинства операций добавления колонок.

```sql
-- PostgreSQL 11+ / MySQL 8.0.29+
ALTER TABLE users ADD COLUMN phone_verified BOOLEAN DEFAULT false NOT NULL;
```

**Универсальный безопасный подход (для сложных случаев и старых версий):**
1. **Expand:** Добавление колонки как `NULLABLE` без ограничений.
2. **Migrate:** Заполнение данных батчами (см. Сценарий 2).
3. **Constraint:** Добавление `NOT NULL` или `CHECK` ограничений безопасным способом.

```sql
-- PostgreSQL: Безопасное добавление NOT NULL
ALTER TABLE orders ADD CONSTRAINT tracking_number_not_null 
    CHECK (tracking_number IS NOT NULL) NOT VALID;
-- Проверка существующих данных в фоновом режиме (без блокировки записи)
ALTER TABLE orders VALIDATE CONSTRAINT tracking_number_not_null;
```

### Сценарий 2: Пакетная миграция данных (Batch Data Migration)

Применяется при обновлении миллионов строк для изменения формата данных или заполнения новых колонок.

**Реализация на уровне SQL (PostgreSQL):**
```sql
DO $$
DECLARE
    row_count INT;
    batch_size INT := 5000;
BEGIN
    LOOP
        UPDATE users 
        SET full_name = first_name || ' ' || last_name
        WHERE id IN (
            SELECT id FROM users 
            WHERE full_name IS NULL 
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED
        );
        
        GET DIAGNOSTICS row_count = ROW_COUNT;
        EXIT WHEN row_count = 0;
        
        COMMIT; -- Фиксация батча и освобождение ресурсов
        PERFORM pg_sleep(0.1); -- Пауза для автовакуума и репликации
    END LOOP;
END $$;
```

### Сценарий 3: Создание индексов без блокировок (Concurrent Indexing)

Создание стандартного индекса блокирует `WRITE` операции до завершения сканирования таблицы.

**PostgreSQL:**
```sql
-- Выполняется вне транзакционного блока
CREATE INDEX CONCURRENTLY idx_users_email_active 
ON users(email) 
WHERE is_active = true;
```

**MySQL (Online DDL):**
```sql
ALTER TABLE users ADD INDEX idx_email (email), ALGORITHM=INPLACE, LOCK=NONE;
```

### Сценарий 4: Изменение типа колонки (Change Data Type)

Например, переход с `INT` на `BIGINT` при исчерпании диапазона ID. Прямой `ALTER TABLE ... TYPE` обычно вызывает полную перезапись таблицы и блокировку.

**Последовательность действий:**
1. Создать новую колонку с целевым типом (`new_id BIGINT`).
2. Настроить триггер для дублирования записей из старой колонки в новую.
3. Мигрировать существующие данные батчами.
4. Переключить код приложения на использование новой колонки.
5. Удалить старую колонку и триггер (Contract).

### Сценарий 5: Использование инструментов Online Schema Change (OSC)

Когда стандартные средства СУБД недостаточно эффективны для таблиц размером в терабайты.

**Популярные инструменты:**
- **gh-ost (GitHub):** Работает через чтение бинарных логов (binlog), не использует триггеры, что снижает нагрузку на БД.
- **pt-online-schema-change (Percona):** Использует триггеры для синхронизации данных.

**Пример команды gh-ost:**
```bash
gh-ost \
  --user=\"gh-ost\" --password=\"pass\" --host=\"db-host\" \
  --database=\"prod_db\" --table=\"large_table\" \
  --alter=\"ADD COLUMN bio TEXT\" \
  --allow-on-master --execute
```

### Сценарий 6: Процесс отката (Rollback Procedure)

Технические детали реализации откатов описаны в **[Стратегии отката (Rollback)](rollback_strategies.md)**.

1. **Приостановка (Pause):** Остановка текущего деплоя приложения.
2. **Анализ:** Проверка состояния через `flyway info` или `liquibase history`.
3. **Откат кода:** Возврат к версии $N$, которая должна быть совместима с текущей схемой $N+1$ (благодаря Expand-Contract).
4. **Решение по БД:** 
    - Если данные не повреждены — оставить схему как есть (безопаснее всего).
    - Если необходим откат схемы — выполнить `down`-скрипты, учитывая риск потери данных в новых колонках.

## Дополнительная информация

### Рекомендации

- **Таймауты блокировок:** Всегда устанавливайте `lock_timeout` перед выполнением DDL в PostgreSQL, чтобы не выстроить очередь из заблокированных запросов.
- **Проверка FK:** Добавление внешних ключей (Foreign Keys) на большие таблицы следует делать через `NOT VALID` с последующей валидацией.
- **Мониторинг:** Ключевые метрики при миграции — `Replication Lag`, `CPU Load`, `I/O Wait` и `Deadlocks`.
