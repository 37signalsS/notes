# Типовые сценарии миграций

## Определения

**Миграционные сценарии** — это проверенные последовательности операций по изменению схемы или состава данных базы данных, адаптированные под конкретные требования доступности (uptime) и объемы данных.

## Основные концепции

- **Zero-downtime:** подход, позволяющий обновлять схему базы данных без остановки приложения. Достигается за счет обеспечения совместимости старого кода с новой схемой и наоборот.
- **Пакетная обработка (Batching):** разделение одной крупной операции на множество мелких транзакций для предотвращения длительных блокировок и переполнения журналов транзакций.
- **Целостность при откате:** планирование процедуры возврата в исходное состояние до начала выполнения миграции.

## Практические сценарии

### Сценарий 1: Развертывание без простоя (Zero-downtime deployment)

Используется для добавления новых обязательных полей без остановки сервиса. Подробнее о паттерне расширения и сужения схемы см. **[Принцип Expand-Contract](expand_contract.md)**.

```sql
-- Шаг 1: Добавление nullable колонки
-- Операция выполняется мгновенно и не блокирует чтение/запись
ALTER TABLE orders ADD COLUMN tracking_number VARCHAR(100);

-- Шаг 2: Деплой кода, который учитывает возможность отсутствия значения
# if order.tracking_number:
#     show_tracking(order.tracking_number)

-- Шаг 3: Установка значения по умолчанию (опционально)
ALTER TABLE orders ALTER COLUMN tracking_number SET DEFAULT 'PENDING';

-- Шаг 4: Наполнение данными и установка NOT NULL
-- UPDATE выполняется небольшими порциями, если таблица велика
UPDATE orders SET tracking_number = 'PENDING' WHERE tracking_number IS NULL;
ALTER TABLE orders ALTER COLUMN tracking_number SET NOT NULL;

-- Шаг 5: Деплой кода, который ожидает обязательное наличие значения
# show_tracking(order.tracking_number)
```

### Сценарий 2: Миграция данных в больших таблицах

Применяется для изменения данных в таблицах с миллионами строк. Позволяет избежать блокировок всей таблицы и раздувания WAL. Подробнее о массовых операциях см. **[Безопасные массовые операции](./../safe_large_scale_data_modification.md)**.

```python
# batch_migration.py
# Миграция по батчам (пакетам)

BATCH_SIZE = 1000
last_id = 0

while True:
    with db.transaction():
        # Выборка строк с использованием SKIP LOCKED для параллельной обработки
        rows = db.execute(f"""
            SELECT id FROM large_table 
            WHERE id > {last_id} 
            ORDER BY id 
            LIMIT {BATCH_SIZE}
            FOR UPDATE SKIP LOCKED
        """)
        
        if not rows:
            break
            
        for row in rows:
            migrate_row(row.id)
            last_id = row.id
    
    # Пауза между батчами для "дыхания" базы данных
    time.sleep(0.1)
```

### Сценарий 3: Процесс отката (Rollback)

Алгоритм действий при неудачном выполнении миграции в production-среде. Технические детали реализации откатов описаны в **[Стратегии отката (Rollback)](rollback_strategies.md)**.

```bash
# 1. Приостановка развертывания новой версии кода
kubectl rollout pause deployment/myapp

# 2. Анализ состояния миграций инструментами (например, Flyway)
flyway info

# 3. Выполнение отката схемы (если поддерживается инструментом)
flyway undo

# 4. В критических случаях — восстановление из пре-релизного бэкапа
pg_restore -h $DB_HOST -U $DB_USER -d $DB_NAME backup_pre_migration.sql

# 5. Возврат кода к стабильной версии
git revert HEAD
kubectl rollout resume deployment/myapp
```

## Дополнительная информация

### Рекомендации

- **Тестирование отката:** процедура Rollback должна быть протестирована на staging-среде так же тщательно, как и сама миграция.
- **Мониторинг:** во время выполнения сценариев необходимо следить за лагом репликации и нагрузкой на I/O.
- **Бэкап:** создание бэкапа перед миграцией является обязательным шагом, независимо от сложности сценария.
