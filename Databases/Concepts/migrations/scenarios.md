# Типовые сценарии миграций

## Определения

**Миграционные сценарии** — это проверенные последовательности операций по изменению схемы или состава данных базы данных, адаптированные под конкретные требования доступности (uptime) и объемы данных.

## Основные концепции

- **Zero-downtime (без простоя):** подход, позволяющий обновлять схему базы данных без остановки приложения. Достигается за счет обеспечения совместимости старого кода с новой схемой и наоборот.
- **Пакетная обработка (Batching):** разделение одной крупной операции на множество мелких транзакций для предотвращения длительных блокировок и переполнения журналов транзакций (WAL).
- **Теневые таблицы (Shadow Tables):** использование сторонних инструментов для создания копии таблицы с новой схемой и постепенной синхронизации данных (например, gh-ost, pt-online-schema-change).
- **Целостность при откате:** планирование процедуры возврата в исходное состояние до начала выполнения миграции.

## Практические сценарии

### Сценарий 1: Развертывание без простоя (Zero-downtime deployment)

Используется для добавления новых обязательных полей. Подробнее о паттерне расширения и сужения схемы см. **[Принцип Expand-Contract](expand_contract.md)**.

**Современный подход (PostgreSQL 11+):**
Добавление колонки с `DEFAULT` и `NOT NULL` теперь является операцией только над метаданными и выполняется мгновенно.
```sql
ALTER TABLE orders ADD COLUMN tracking_number VARCHAR(100) DEFAULT 'PENDING' NOT NULL;
```

**Универсальный безопасный подход (для всех версий и сложной логики):**
```sql
-- Шаг 1: Добавление nullable колонки
ALTER TABLE orders ADD COLUMN tracking_number VARCHAR(100);

-- Шаг 2: Деплой кода, который учитывает возможность отсутствия значения
-- (Приложение пишет в старую и новую колонки, если это переименование, 
-- или просто умеет обрабатывать NULL)

-- Шаг 3: Установка значения по умолчанию и заполнение данных батчами
ALTER TABLE orders ALTER COLUMN tracking_number SET DEFAULT 'PENDING';
-- UPDATE выполняется небольшими порциями (см. Сценарий 2)
UPDATE orders SET tracking_number = 'PENDING' WHERE tracking_number IS NULL;

-- Шаг 4: Безопасная установка NOT NULL (PostgreSQL)
-- Вместо прямой установки, которая блокирует таблицу для сканирования:
ALTER TABLE orders ADD CONSTRAINT tracking_number_not_null 
    CHECK (tracking_number IS NOT NULL) NOT VALID;
-- Проверка существующий данных без блокировки DML
ALTER TABLE orders VALIDATE CONSTRAINT tracking_number_not_null;
```

### Сценарий 2: Миграция данных в больших таблицах

Применяется для изменения данных в таблицах с миллионами строк. Позволяет избежать блокировок всей таблицы и раздувания WAL. Подробнее о массовых операциях см. **[Безопасные массовые операции](./../safe_large_scale_data_modification.md)**.

```python
# batch_migration.py
# Миграция по батчам (пакетам) с использованием первичного ключа

BATCH_SIZE = 1000
last_id = 0

while True:
    # Использование транзакции только для одного батча
    with db.transaction():
        # Выборка строго по индексу для исключения Seq Scan
        rows = db.execute(f"""
            SELECT id FROM large_table 
            WHERE id > {last_id} 
            ORDER BY id 
            LIMIT {BATCH_SIZE}
            FOR UPDATE SKIP LOCKED
        """)
        
        if not rows:
            break
            
        for row in rows:
            migrate_row(row.id)
            last_id = row.id
    
    # Пауза («throttle») для очистки WAL и работы автовакуума
    time.sleep(0.1)
```

### Сценарий 3: Процесс отката (Rollback)

Технические детали реализации откатов описаны в **[Стратегии отката (Rollback)](rollback_strategies.md)**.

```bash
# 1. Приостановка развертывания новой версии кода
kubectl rollout pause deployment/myapp

# 2. Анализ состояния миграций инструментами (например, Flyway)
flyway info

# 3. Выполнение отката схемы (если поддерживается инструментом)
flyway undo

# 4. В критических случаях — восстановление из пре-релизного бэкапа
# ВНИМАНИЕ: ведет к потере данных, записанных после начала миграции
pg_restore -h $DB_HOST -U $DB_USER -d $DB_NAME backup_pre_migration.sql

# 5. Возврат кода к стабильной версии
git revert HEAD
kubectl rollout resume deployment/myapp
```

## Дополнительная информация

### Рекомендации

- **Тестирование отката:** процедура Rollback должна быть протестирована на staging-среде так же тщательно, как и сама миграция.
- **Мониторинг:** во время выполнения сценариев необходимо следить за лагом репликации (`pg_replication_slots`) и нагрузкой на I/O.
- **Бэкап:** создание бэкапа перед миграцией является обязательным шагом. Для огромных БД используйте снапшоты хранилища (LVM/ZFS/EBS).
