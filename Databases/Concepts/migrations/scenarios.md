# Типовые сценарии миграций

## Определения

- **Миграционные сценарии** — это проверенные последовательности операций по изменению схемы (DDL) или состава данных (DML) базы данных, адаптированные под конкретные требования доступности (uptime) и объемы данных.
- **Схема-миграция (Schema Migration)** — изменение структуры таблиц, индексов, представлений или ограничений. Требует осторожности из-за потенциальных блокировок системного каталога.
- **Дата-миграция (Data Migration)** — преобразование, перенос или очистка самих данных. Основной вызов — выполнение на «горячих» данных без деградации производительности.
- **Online Schema Change (OSC)** — процесс изменения схемы таблицы без её длительной блокировки на чтение и запись. Реализуется через создание теневой копии, синхронизацию изменений и атомарную подмену имен.
- **Транзакционный DDL** — способность СУБД (например, PostgreSQL) оборачивать изменения структуры в транзакцию, обеспечивая атомарность: либо вся миграция применилась, либо произошел полный откат при ошибке.

## Основные концепции

- **Zero-downtime (без простоя):** Архитектурный подход, при котором БД обновляется без остановки приложения. **Зачем:** Для критически важных систем, где простой измеряется стоимостью недополученной прибыли или нарушением SLA. Требует двусторонней совместимости кода и схемы.
- **Пакетная обработка (Batching):** Разделение одной крупной DML-операции на множество мелких транзакций. **Зачем:** 
    - Предотвращение накопления огромных объемов WAL/Redo логов.
    - Снижение вероятности и длительности эксклюзивных блокировок строк.
    - Предотвращение критического роста лага репликации.
- **Принцип «Expand-Contract»:** Трехфазный процесс (расширение -> миграция -> сужение). **Зачем:** Гарантирует, что старая версия приложения сможет работать с новой схемой, что критично для Rolling Updates и Blue-Green деплоев.
- **Теневые таблицы (Shadow Tables):** Создание копии таблицы с целевой структурой. **Зачем:** Позволяет выполнять тяжелые операции (например, перестроение индексов или изменение типов) в фоне, не мешая основному трафику.
- **Миграционный прокси:** Слой (ProxySQL, pgBouncer), управляющий соединениями. **Зачем:** Позволяет «поставить на паузу» запросы приложения на время финального переключения (cutover), исключая ошибки `Connection Refused`.

## Практические сценарии: Операции DDL/DML

### Сценарий 1: Добавление колонки без простоя (Zero-downtime Add Column)

Используется для добавления новых полей, включая обязательные (`NOT NULL`).

#### Предпосылки
- **СУБД:** PostgreSQL 11+ или MySQL 8.0.12+.
- **Настройки:** Установлен `lock_timeout` для предотвращения очередей блокировок.

#### Теория
В современных СУБД добавление колонки с `DEFAULT` — это операция только на уровне метаданных (системного каталога). Данные в существующих строках не переписываются физически до их следующего обновления, что делает DDL мгновенным.

#### Пошаговая инструкция
1. **Установка таймаута:** Ограничить время ожидания блокировки `ACCESS EXCLUSIVE`.
2. **Выполнение DDL:** Добавление колонки с дефолтным значением.

```sql
-- PostgreSQL
SET lock_timeout = '2s';
ALTER TABLE users ADD COLUMN phone_verified BOOLEAN DEFAULT false NOT NULL;
```

#### Валидация
- Проверка структуры: `\d users` (PostgreSQL) или `DESCRIBE users;` (MySQL).
- Проверка блокировок: Отсутствие `waiting` процессов в `pg_stat_activity`.

#### Устранение неисправностей
- **Ошибка lock_timeout:** Если таблица занята долгим запросом, миграция упадет. **Решение:** Повторить запуск в период минимальной нагрузки или вручную завершить блокирующий процесс.

### Сценарий 2: Пакетная миграция данных (Batch Data Migration)

Применяется для обновления миллионов строк (например, заполнение новой колонки данными на основе старых).

#### Предпосылки
- Наличие индекса по колонке, используемой для фильтрации (обычно PK или дата).
- Мониторинг лага репликации.

#### Пошаговая инструкция
Использование цикла с фиксацией транзакции после каждого батча.

```sql
DO $$
DECLARE
    row_count INT;
    batch_size INT := 5000;
BEGIN
    LOOP
        -- Обновление батча с использованием SKIP LOCKED для избежания конфликтов
        UPDATE users 
        SET full_name = first_name || ' ' || last_name
        WHERE id IN (
            SELECT id FROM users 
            WHERE full_name IS NULL 
            ORDER BY id
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED
        );
        
        GET DIAGNOSTICS row_count = ROW_COUNT;
        EXIT WHEN row_count = 0;
        
        COMMIT; -- Фиксация и освобождение ресурсов (включая WAL)
        PERFORM pg_sleep(0.05); -- Пауза для реплик и Autovacuum
    END LOOP;
END $$;
```

#### Валидация
- `SELECT COUNT(*) FROM users WHERE full_name IS NULL;` должен вернуть 0.
- Контроль `pg_stat_replication` на предмет роста лага.

#### Устранение неисправностей
- **Раздувание таблицы (Bloat):** Слишком частые апдейты без пауз. **Решение:** Увеличить `pg_sleep` и проверить настройки автовакуума.

### Сценарий 3: Создание индексов без блокировок (Concurrent Indexing)

#### Предпосылки
- **PostgreSQL:** Выполняется **вне** транзакционного блока (нельзя использовать `BEGIN`/`COMMIT`).
- **MySQL:** Использование `ALGORITHM=INPLACE`.

#### Теория
Обычный `CREATE INDEX` блокирует `WRITE` операции. Конкурентное создание проходит в два прохода по таблице, позволяя писать данные во время процесса, но занимает больше времени и ресурсов.

#### Пошаговая инструкция
```sql
-- PostgreSQL
CREATE INDEX CONCURRENTLY idx_users_email_active ON users(email) WHERE is_active = true;

-- MySQL
ALTER TABLE users ADD INDEX idx_email (email), ALGORITHM=INPLACE, LOCK=NONE;
```

#### Валидация
- PostgreSQL: `SELECT * FROM pg_class c JOIN pg_index i ON c.oid = i.indrelid WHERE c.relname = 'users' AND i.indisvalid = false;` (не должно быть невалидных индексов).

#### Устранение неисправностей
- **Индекс стал INVALID (PostgreSQL):** Сбой во время создания (например, нарушение уникальности). **Решение:** `DROP INDEX CONCURRENTLY` и повторный запуск.

### Сценарий 4: Изменение типа колонки через триггеры

Например, переход с `INT` на `BIGINT`.

#### Пошаговая инструкция (Expand-Contract)
1. **Expand:** Создать новую колонку `id_new BIGINT` с `NULLABLE`.
2. **Sync:** Создать триггер, который при `INSERT`/`UPDATE` в старую колонку пишет и в новую.
3. **Migrate:** Заполнить `id_new` для старых строк батчами (как в сценарии 2).
4. **Validation:** Проверить идентичность данных.
5. **Switch:** В приложении переключиться на новую колонку.
6. **Contract:** Удалить триггер и старую колонку.

### Сценарий 5: Online Schema Change (gh-ost / pt-osc)

Для таблиц > 500 ГБ, где стандартные средства СУБД вызывают слишком долгие блокировки метаданных.

#### Инструменты
- **gh-ost:** Рекомендуется для MySQL. Работает через binlog, не нагружает БД триггерами.
- **pt-online-schema-change:** Классика для MySQL, использует триггеры.

#### Пример (gh-ost)
```bash
gh-ost \
  --user="gh-ost_user" --password="password" --host="db-master" \
  --database="prod" --table="orders" \
  --alter="MODIFY COLUMN order_payload JSON" \
  --allow-on-master --execute
```

## Практические сценарии: Архитектурные переходы

### Сценарий 6: Blue-Green Deployment базы данных

#### Теория
Используется при обновлении мажорной версии (например, Postgres 14 -> 16) или переезде в другое облако. Основан на логической репликации.

#### Пошаговая инструкция
1. Поднять инстанс Green с новой версией.
2. Перенести схему (DDL) без данных.
3. Настроить логическую репликацию с Blue на Green.
4. Дождаться синхронизации.
5. **Cutover:** Приложение переключается на Green.

#### Валидация
- Сверка контрольных сумм или `COUNT` по ключевым таблицам.

### Сценарий 7: Миграция через CDC (Debezium + Kafka)

#### Теория
Change Data Capture позволяет мигрировать данные между разными СУБД (например, Oracle -> PostgreSQL) с трансформацией «на лету».

#### Техстек
- **Source:** Oracle/MySQL/Postgres.
- **Transport:** Kafka + Kafka Connect (Debezium).
- **Sink:** Целевая БД.

## Процесс отката (Rollback Procedure)

Любая миграция должна иметь план отката.

1. **Технический откат (Down-скрипт):** Только если данные не были удалены (`DROP`).
2. **Функциональный откат:** Возврат приложения на старую версию кода. Благодаря **Expand-Contract**, старый код совместим с новой схемой.
3. **Восстановление из бэкапа:** Крайняя мера при повреждении данных.

## Дополнительная информация

### Рекомендации
- **Lock Management:** Всегда используйте `lock_timeout`. Длительное ожидание DDL-блокировки блокирует *все* последующие запросы к таблице, даже простые `SELECT`.
- **Foreign Keys:** Добавляйте FK с `NOT VALID`, а затем запускайте `VALIDATE CONSTRAINT` в отдельной транзакции. Это исключает блокировку таблицы на время проверки существующих данных.
- **Мониторинг:** Следите за `Replication Lag` и `Disk I/O` во время батчинга.
