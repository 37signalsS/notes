# Типовые сценарии миграций

**Актуально для:** PostgreSQL 11+, MySQL 8.0.12+, MariaDB 10.3+

## Определения

- **Миграционные сценарии** — это проверенные последовательности операций по изменению схемы (DDL) или состава данных (DML) базы данных, адаптированные под конкретные требования доступности (uptime) и объемы данных.
- **Схема-миграция (Schema Migration)** — изменение структуры таблиц, индексов, представлений или ограничений. Требует осторожности из-за потенциальных блокировок системного каталога.
- **Дата-миграция (Data Migration)** — преобразование, перенос или очистка самих данных. Основной вызов — выполнение на «горячих» данных без деградации производительности.
- **Online Schema Change (OSC)** — процесс изменения схемы таблицы без её длительной блокировки на чтение и запись. Реализуется через создание теневой копии, синхронизацию изменений и атомарную подмену имен.
- **Транзакционный DDL** — способность СУБД (например, PostgreSQL) оборачивать изменения структуры в транзакцию, обеспечивая атомарность: либо вся миграция применилась, либо произошел полный откат при ошибке.

## Основные концепции

- **Zero-downtime (без простоя):** Архитектурный подход, при котором БД обновляется без остановки приложения. **Зачем:** Для критически важных систем, где простой измеряется стоимостью недополученной прибыли или нарушением SLA. Требует двусторонней совместимости кода и схемы.
- **Пакетная обработка (Batching):** Разделение одной крупной DML-операции на множество мелких транзакций. **Зачем:** 
    - Предотвращение накопления огромных объемов WAL/Redo логов.
    - Снижение вероятности и длительности эксклюзивных блокировок строк.
    - Предотвращение критического роста лага репликации.
- **Принцип «Expand-Contract»:** Трехфазный процесс (расширение -> миграция -> сужение). **Зачем:** Гарантирует, что старая версия приложения сможет работать с новой схемой, что критично для Rolling Updates и Blue-Green деплоев.
- **Теневые таблицы (Shadow Tables):** Создание копии таблицы с целевой структурой. **Зачем:** Позволяет выполнять тяжелые операции (например, перестроение индексов или изменение типов) в фоне, не мешая основному трафику.
- **Миграционный прокси:** Слой (ProxySQL, pgBouncer), управляющий соединениями. **Зачем:** Позволяет «поставить на паузу» запросы приложения на время финального переключения (cutover), исключая ошибки `Connection Refused`.
- **SRE Golden Signals в миграциях:** Четыре ключевых метрики, определяющих здоровье процесса:
  1. **Ошибки (Errors):** Количество неудачных попыток применения изменений.
  2. **Длительность (Latency):** Время выполнения шагов или батчей.
  3. **Насыщенность (Saturation):** Влияние миграции на CPU, I/O, память.
  4. **Блокировки (Traffic/Concurrency):** Количество запросов, ожидающих освобождения ресурсов, захваченных миграцией.
- **Влияние на SLO/SLA:** Каждая миграция оценивается по потенциальному риску нарушения Service Level Objectives. Для сервисов с SLA 99,9% и выше допустимый простой при миграции — минуты, а не часы.

## Предпосылки и подготовка

### Предполётная проверка (Pre-flight Check)

Перед выполнением любой миграции в Production выполните стандартный чек-лист. Детальный разбор параметров сессии, проверки индексов и оценки объёма данных см. в **[Безопасные массовые операции](../safe_large_scale_data_modification.md#pre-flight-проверки)**.

Кросс-функциональные проверки:
- **Резервная копия:** Актуальность и восстанавливаемость. Для PostgreSQL выполните `pg_basebackup` или snapshot storage; для MySQL — `xtrabackup --backup`. Проверьте целостность через `pg_checksum` / `XtraBackup --prepare`.
- **Лаг репликации:** Должен быть ниже порога алертинга (обычно < 30с для Streaming Replication / < 10с для синхронной репликации). Если лаг близок к `wal_keep_size` — отложите миграцию.
- **Connection Pool:** Пулы приложения (PgBouncer/ProxySQL) должны иметь запас ёмкости на время миграции. При `ACCESS EXCLUSIVE` пул опустошается, пока DDL не завершится, и новые запросы приложения получают отказы.
- **Активные транзакции:** Должны отсутствовать долгоживущие транзакции в статусе `idle in transaction`. Они удерживают `AccessShareLock` и могут превратить кратковременную DDL-блокировку в каскадный deadlock.

### Change Management и Runbook

- **Change Advisory Board (CAB):** Миграции, затрагивающие таблицы > 10 ГБ или содержащие `DROP/RENAME`, требуют утверждения. Документируйте окно деплоя, критерии отката и контакты on-call.
- **Maintenance Window:** Для миграций с ожидаемым простем > 30с согласуйте окно с бизнесом. Для zero-downtime — фиксируйте время cutover в runbook.
- **Runbook:** Для каждой миграции подготовьте документ с пошаговой инструкцией, командами проверки, критериями успешного завершения и планом отката с триггерами.

## Практические сценарии: Операции DDL/DML

### Сценарий 1: Добавление колонки без простоя (Zero-downtime Add Column)

Используется для добавления новых полей, включая обязательные (`NOT NULL`).

#### Предпосылки
- **СУБД:** PostgreSQL 11+ или MySQL 8.0.12+.
- **Настройки:** Установлен `lock_timeout` для предотвращения очередей блокировок.

#### Теория
В современных СУБД добавление колонки с `DEFAULT` — это операция только на уровне метаданных (системного каталога). Данные в существующих строках не переписываются физически до их следующего обновления, что делает DDL мгновенным.

#### Пошаговая инструкция
1. **Установка таймаута:** Ограничить время ожидания блокировки `ACCESS EXCLUSIVE`.
2. **Выполнение DDL:** Добавление колонки с дефолтным значением.

```sql
-- PostgreSQL
SET lock_timeout = '2s';
ALTER TABLE users ADD COLUMN phone_verified BOOLEAN DEFAULT false NOT NULL;

-- MySQL
ALTER TABLE users ADD COLUMN phone_verified BOOLEAN DEFAULT false NOT NULL, ALGORITHM=INPLACE, LOCK=NONE;
```

#### Валидация
- Проверка структуры: `\d users` (PostgreSQL) или `DESCRIBE users;` (MySQL).
- Проверка блокировок: Отсутствие `waiting` процессов в `pg_stat_activity`.

#### Устранение неисправностей
- **Ошибка lock_timeout:** Если таблица занята долгим запросом, миграция упадет. **Решение:** Повторить запуск в период минимальной нагрузки или вручную завершить блокирующий процесс.

---

### Сценарий 2: Пакетная миграция данных (Batch Data Migration)

Применяется для обновления миллионов строк (например, заполнение новой колонки данными на основе старых).

#### Предпосылки
- Наличие индекса по колонке, используемой для фильтрации (обычно PK или дата).
- Мониторинг лага репликации.

#### Пошаговая инструкция
Использование цикла с фиксацией транзакции после каждого батча.

```sql
DO $$
DECLARE
    row_count INT;
    batch_size INT := 5000;
BEGIN
    LOOP
        -- Обновление батча с использованием SKIP LOCKED для избежания конфликтов
        UPDATE users 
        SET full_name = first_name || ' ' || last_name
        WHERE id IN (
            SELECT id FROM users 
            WHERE full_name IS NULL 
            ORDER BY id
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED
        );
        
        GET DIAGNOSTICS row_count = ROW_COUNT;
        EXIT WHEN row_count = 0;
        
        COMMIT; -- Фиксация и освобождение ресурсов (включая WAL)
        PERFORM pg_sleep(0.05); -- Пауза для реплик и Autovacuum
    END LOOP;
END $$;
```

#### Валидация
- `SELECT COUNT(*) FROM users WHERE full_name IS NULL;` должен вернуть 0.
- Контроль `pg_stat_replication` на предмет роста лага.

#### Устранение неисправностей
- **Раздувание таблицы (Bloat):** Слишком частые апдейты без пауз. **Решение:** Увеличить `pg_sleep` и проверить настройки автовакуума.

### Сценарий 3: Создание индексов без блокировок (Concurrent Indexing)

#### Предпосылки
- **PostgreSQL:** Выполняется **вне** транзакционного блока (нельзя использовать `BEGIN`/`COMMIT`).
- **MySQL:** Использование `ALGORITHM=INPLACE`.

#### Теория
Обычный `CREATE INDEX` блокирует `WRITE` операции. Конкурентное создание проходит в два прохода по таблице, позволяя писать данные во время процесса, но занимает больше времени и ресурсов.

#### Пошаговая инструкция
```sql
-- PostgreSQL
CREATE INDEX CONCURRENTLY idx_users_email_active ON users(email) WHERE is_active = true;

-- MySQL
ALTER TABLE users ADD INDEX idx_email (email), ALGORITHM=INPLACE, LOCK=NONE;
```

#### Валидация
- PostgreSQL: `SELECT * FROM pg_class c JOIN pg_index i ON c.oid = i.indrelid WHERE c.relname = 'users' AND i.indisvalid = false;` (не должно быть невалидных индексов).

#### Устранение неисправностей
- **Индекс стал INVALID (PostgreSQL):** Сбой во время создания (например, нарушение уникальности). **Решение:** `DROP INDEX CONCURRENTLY` и повторный запуск.

---

### Сценарий 4: Изменение типа колонки через триггеры

Например, переход с `INT` на `BIGINT`.

#### Предпосылки
- Таблица с миллионами строк, требующая доступности 24/7.
- Установленный `lock_timeout` для всех DDL-команд.

#### Пошаговая инструкция (Expand-Contract)
1. **Expand:** Создать новую колонку `id_new BIGINT` с `NULLABLE`.
2. **Sync:** Создать триггер, который при `INSERT`/`UPDATE` в старую колонку пишет и в новую.
3. **Migrate:** Заполнить `id_new` для старых строк батчами (как в сценарии 2).
4. **Validation:** Проверить идентичность данных.
5. **Switch:** В приложении переключиться на новую колонку.
6. **Contract:** Удалить триггер и старую колонку.

#### Валидация
- Проверка триггера: `SELECT tgname FROM pg_trigger WHERE tgrelid = 'users'::regclass;` (PostgreSQL) или `SHOW TRIGGERS LIKE 'users';` (MySQL).
- Проверка данных: `SELECT COUNT(*) FROM users WHERE id_new IS NULL;` — должно быть 0.
- Сравнение: `SELECT id, id_new FROM users WHERE id != id_new LIMIT 10;` — все строки должны совпадать.

### Сценарий 5: Online Schema Change (gh-ost / pt-osc)

Для таблиц > 500 ГБ, где стандартные средства СУБД вызывают слишком долгие блокировки метаданных.

#### Инструменты
- **gh-ost:** Рекомендуется для MySQL. Работает через binlog, не нагружает БД триггерами.
- **pt-online-schema-change:** Классика для MySQL, использует триггеры.

#### Пример (gh-ost)
```bash
gh-ost \
  --user="gh-ost_user" --password="password" --host="db-master" \
  --database="prod" --table="orders" \
  --alter="MODIFY COLUMN order_payload JSON" \
  --allow-on-master --execute
```

#### Валидация
- Проверка статуса: лог gh-ost показывает `progress` и `eta`.
- Проверка репликации: `Seconds_Behind_Master` должен оставаться 0.
- После cutover: `DESCRIBE orders;` (MySQL) — структура соответствует ожидаемой.

## Практические сценарии: Архитектурные переходы

### Сценарий 6: Blue-Green Deployment базы данных

#### Теория
Используется при обновлении мажорной версии (например, Postgres 14 -> 16) или переезде в другое окружение. Основан на логической репликации.

#### Пошаговая инструкция
1. Поднять инстанс Green с новой версией.
2. Перенести схему (DDL) без данных.
3. Настроить логическую репликацию с Blue на Green.
4. Дождаться синхронизации.
5. **Cutover:** Приложение переключается на Green.

#### Валидация
- Сверка контрольных сумм или `COUNT` по ключевым таблицам.
- Проверка `pg_stat_replication` — `state` = `streaming` (PostgreSQL) или `Seconds_Behind_Master = 0` (MySQL).

---

### Сценарий 7: Миграция через CDC (Debezium + Kafka)

#### Теория
Change Data Capture позволяет мигрировать данные между разными СУБД (например, Oracle -> PostgreSQL) с трансформацией «на лету». Основан на чтении transaction logs (WAL/Binlog) без нагрузки на source-базу.

#### Техстек
- **Source:** Oracle/MySQL/Postgres.
- **Transport:** Kafka + Kafka Connect (Debezium).
- **Sink:** Целевая БД.

#### Пошаговая инструкция
1. **Подготовка инфраструктуры:** Развернуть Kafka cluster (минимум 3 брокера для redundancy) и Kafka Connect в distributed mode.
2. **Настройка Source Connector:** Запустить Debezium connector на source-СУБД с первичной загрузкой (snapshot) и последующей репликацией изменений.
3. **Настройка Sink Connector:** Настроить целевой connector с идемпотентной записью (upsert) и преобразованием типов данных между СУБД.
4. **Верификация данных:** Сравнить `COUNT(*)` и контрольные суммы на source и sink. Для сложных преобразований используйте Spark или dbt для точного сравнения.
5. **Cutover:** Остановить запись в source (maintenance window или dual-write), дождаться draining Kafka queue, переключить приложение на целевую БД.
6. **Обратный мониторинг:** После cutover следите за `consumer_lag` и ошибками в `connect.log`.

#### Валидация
- **Kafka:** `kafka-consumer-groups.sh --describe --group <sink-group>` — lag должен быть 0.
- **Sink DB:** `SELECT COUNT(*) FROM target_table;` совпадает с source.
- **Приложение:** Smoke-тесты на 5% трафика перед полным cutover.

## Пограничные случаи и ограничения

- **Секционированные таблицы:** Большинство DDL-операций в PostgreSQL 11+ выполняется на уровне секций без полной блокировки. Однако `ATTACH PARTITION` требует `ACCESS EXCLUSIVE` на дочерней таблице. Для MySQL используйте `ALGORITHM=INPLACE, LOCK=NONE` на отдельных секциях.
- **Внешние ключи (Foreign Keys):** Добавление FK с `NOT VALID` не блокирует чтение, но `VALIDATE CONSTRAINT` acquires `SHARE UPDATE EXCLUSIVE` на таблицу. На очень больших таблицах (> 100M строк) валидация может занимать часы. Для миграций данных рассмотрите отключение FK через `SET session_replication_role = 'replica'` (PostgreSQL) или `ALTER TABLE ... DISABLE KEYS` (MySQL).
- **Триггеры:** Триггеры `BEFORE/AFTER` замедляют батчинги из-за дополнительных операций ввода-вывода. При массовой миграции данных, если бизнес-логика позволяет, отключайте триггеры.
- **Огромные таблицы (> 1 ТБ):** Для таблиц терабайтного класса стандартные `CREATE INDEX CONCURRENTLY` могут занимать дни. Рассмотрите `pg_repack` (PostgreSQL) или `pt-online-schema-change`/`gh-ost` (MySQL) для реорганизации с минимальной блокировкой.
- **Миграция на реплике:** Выполняйте DDL сначала на standby (PostgreSQL поддерживает логическую репликацию с standby), затем promote и cutover. Это исключает нагрузку на production master.
- **Миграция данных между инстансами:** Используйте `--no-owner` и `--no-privileges` для миграции между окружениями с разными UID/GID. Валидируйте контрольные суммы после восстановления.

## Процесс отката (Rollback Procedure)

Любая миграция должна иметь план отката. Согласно SRE-практике, откат — это не авария, а запланированная операция.

### Триггеры отката (Rollback Triggers)

Определите явные критерии, при которых миграция останавливается и запускается откат:
- **Replication Lag:** > 60 секунд в течение 5 минут.
- **Ошибки приложения:** Рост 5xx ошибок > 1% от общего трафика.
- **Ресурсы СУБД:** `Disk I/O` wait > 80%, `CPU` > 90% на master-ноде.
- **Блокировки:** `pg_stat_activity` показывает > 10 процессов в статусе `waiting`.

### Уровни отката

1. **Технический откат (Down-миграция / Undo):** Только если данные не были удалены (`DROP`). Идемпотентный скрипт откатывает DDL к предыдущему состоянию.
2. **Функциональный откат (Rollback / Roll-forward):** 
   - Возврат приложения на старую версию кода (Rollback). Благодаря паттерну **Expand-Contract**, старый код совместим с новой схемой.
   - Или применение компенсирующей миграции (Roll-forward), если данные уже были записаны в новые структуры. Подробнее см. **[Стратегии отката (Rollback)](rollback_strategies.md)**.
3. **Восстановление из бэкапа (PITR):** Крайняя мера при повреждении данных или необходимости отката на момент времени до начала миграции. Требует протестированного RPO/RTO.

## Дополнительная информация

### Рекомендации
- **Lock Management:** Всегда используйте `lock_timeout`. Длительное ожидание DDL-блокировки блокирует *все* последующие запросы к таблице, даже простые `SELECT`. Для PostgreSQL также установите `statement_timeout` как страховку.
- **Foreign Keys:** Добавляйте FK с `NOT VALID`, а затем запускайте `VALIDATE CONSTRAINT` в отдельной транзакции. Это исключает блокировку таблицы на время проверки существующих данных.
- **Мониторинг:** Следите за `Replication Lag` и `Disk I/O` во время батчинга. Настройте алерты на `pg_stat_activity` с `wait_event_type = 'Lock'`.
- **Батчинг:** Для таблиц > 1M строк используйте батчи размером 1 000–10 000 строк в зависимости от индексации. Слишком большой батч вызывает WAL-раздувание; слишком малый — overhead на коммиты.
- **Валидация:** Всегда проверяйте идентичность данных после миграции: `COUNT(*)`, контрольные суммы ключевых колонок, smoke-тесты приложения на 5% трафика перед полным cutover.
- **Очистка:** После завершения миграции удалите временные таблицы, триггеры синхронизации и бэкап-копии. Проверьте, что autovacuum восстановил нормальный режим работы.
- **SRE/SLI:** Оцените влияние миграции на SLO. Для критичных сервисов (порядка нескольких 9s доступности) используйте canary-подход: применяйте миграцию к подмножеству реплик, затем к 5% master-трафика, и только потом полностью.
