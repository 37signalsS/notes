# Миграции баз данных: Основы

**Актуально для:** PostgreSQL 11+, MySQL 8.0.12+, MariaDB 10.3+

## Определения

- **Миграция базы данных (Database Migration)** — управляемый процесс изменения структуры (схемы) или состава данных СУБД, обеспечивающий их соответствие текущим требованиям приложения. Позволяет версионировать состояние БД аналогично исходному коду.
- **Схема базы данных (Schema)** — логическое описание структуры данных, включающее таблицы, колонки, типы данных, индексы, внешние ключи (FK), триггеры и представления.
- **Идемпотентность (Idempotency)** — свойство операции, гарантирующее, что её многократное выполнение приводит к тому же результату, что и однократное, без возникновения ошибок или дублирования данных (например, использование `IF NOT EXISTS`). См. подробнее: **[Идемпотентность](../../../../Concepts/idempotency.md)**.
- **Дрейф схемы (Schema Drift)** — расхождение между эталонным описанием структуры в репозитории и фактическим состоянием базы данных в конкретном окружении (Production/Staging). Основная причина "падающих" миграций.
- **Базовое состояние (Baseline)** — моментальный снимок (Snapshot) существующей схемы БД, принимаемый за точку отсчета для начала использования инструментов миграций в уже работающем проекте.
- **Транзакционный DDL (Transactional DDL)** — способность СУБД выполнять команды изменения структуры (CREATE, ALTER) внутри транзакции, обеспечивая атомарность: при сбое вся миграция откатывается целиком.
- **Таблица истории миграций (Schema History Table)** — служебная таблица в БД (например, `flyway_schema_history`, `DATABASECHANGELOG`), где инструмент хранит контрольные суммы, статус применения и время выполнения каждой миграции.
- **Контрольная сумма миграции (Checksum)** — хэш содержимого файла миграции, вычисляемый инструментом. Служит для обнаружения несанкционированных изменений в уже применённых миграциях.
- **Pre-flight проверка (Pre-flight Check)** — набор валидаций состояния СУБД, репликации и окружения, выполняемых перед применением миграции в Production.

## Основные концепции

Миграции реализуют принцип **Schema-as-Code**, позволяя автоматизировать развертывание баз данных и гарантировать идентичность структуры на всех этапах (Dev → Test → Prod).

### Подходы к управлению миграциями

В современной практике выделяют две основные парадигмы:

1.  **Императивный подход (Change-based / Migration-based):**
    - **Суть:** Фокус на *процессе перехода* из состояния A в состояние B. Разработчик вручную пишет последовательные скрипты (`V1__init.sql`, `V2__add_index.sql`).
    - **Механизм:** Инструмент (например, Flyway) хранит таблицу метаданных (например, `flyway_schema_history`) в самой БД. При запуске он сравнивает файлы в коде с записями в таблице и применяет только новые.
    - **Преимущество:** Полный контроль над SQL-командами; предсказуемость выполнения; явный аудит каждого изменения.
2.  **Декларативный подход (State-based):**
    - **Суть:** Фокус на *конечном состоянии*. Разработчик описывает целевую схему (HCL, YAML или сущности ORM), а инструмент сам вычисляет необходимые изменения.
    - **Механизм:** Инструмент (например, Atlas) сравнивает текущую БД с декларативным файлом и генерирует оптимальный план `ALTER` команд "на лету".
    - **Преимущество:** Упрощает работу со сложными схемами; исключает конфликты номеров миграций в больших командах; подходит для частых изменений.

### Классификация изменений

- **Структурные (DDL):** операции над объектами (`CREATE TABLE`, `DROP COLUMN`, `RENAME`). Требуют осторожности из-за блокировок.
- **Трансформационные (DML):** изменение самих данных (`UPDATE`, `DELETE`, миграция данных в новые колонки). Часто выполняются батчами.
- **Сидовые (Seed):** наполнение справочников и настроек по умолчанию, необходимых для работы приложения.

### Поведение СУБД при миграциях

| СУБД | Транзакционный DDL | Особенности |
| :--- | :--- | :--- |
| **PostgreSQL** | Да (почти полностью) | `CREATE INDEX CONCURRENTLY` и `VACUUM` нельзя выполнить внутри транзакции. |
| **MySQL / MariaDB** | Ограниченно (с 8.0) | `ALTER TABLE` вызывает неявный COMMIT. При сбое база остаётся в частично изменённом состоянии. |
| **SQLite** | Да | Подходит только для embedded-сценариев; не для Production. |

### Идемпотентность миграций

Идемпотентность — обязательное требование для миграций, выполняемых в CI/CD:

1.  **Использование `IF NOT EXISTS` / `IF NOT EXISTS`:** Для создания объектов.
    ```sql
    ALTER TABLE users ADD COLUMN IF NOT EXISTS email VARCHAR(255);
    CREATE INDEX IF NOT EXISTS idx_users_email ON users(email);
    ```
2.  **Оборачивание в DO-блок (PostgreSQL):** Для сложной логики с проверкой существования.
    ```sql
    DO $$
    BEGIN
        IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'chk_min_price') THEN
            ALTER TABLE products ADD CONSTRAINT chk_min_price CHECK (price >= 0.01);
        END IF;
    END $$;
    ```
3.  **Проверка в Liquibase/Flyway:** Инструменты предоставляют встроенные механизмы (`preConditions` в Liquibase, `repeatable` в Flyway).
4.  **Обработка NULL:** При заполнении данных используйте `WHERE ... IS NULL`, чтобы избежать дублирования.

## Практические сценарии

### Сценарий 1: Выбор стратегии и инструментария

Перед началом работы необходимо определить стек технологий на основе требований проекта.

#### Предварительные требования
- Выбрана СУБД (PostgreSQL, MySQL, MariaDB).
- Определена потребность в Zero-downtime (нужно ли обновлять БД без остановки трафика).

#### Сравнение инструментов

| Инструмент | Парадигма | Рекомендация |
| :--- | :--- | :--- |
| **Flyway** | Императивный | JVM-проекты (Java/Kotlin); проекты, где важен строгий аудит каждого SQL-запроса. |
| **Atlas** | Декларативный | SRE-ориентированные команды; сложные инфраструктуры; Schema-as-Code. |
| **Liquibase** | Императивный | Крупные Enterprise-системы с необходимостью абстракции (поддержка XML/JSON форматов). |
| **Bytebase** | Декларативный | Команды, требующие GUI для управления жизненным циклом и GitOps для БД. |
| **Alembic** | Императивный | Python-экосистема (интеграция со SQLAlchemy). |

#### Валидация выбора
- **Миграции на PostgreSQL:** Flyway, Atlas, Alembic.
- **Миграции на MySQL/MariaDB:** Flyway, Liquibase, Atlas.
- **Enterprise с XML/YAML абстракцией:** Liquibase.
- **Python-стек:** Alembic.
- **Требуется GUI и approval-процессы:** Bytebase.

### Сценарий 2: Создание идемпотентной миграции (Императивный стиль)

Задача: добавить колонку `email` и индекс по ней в таблице `users`.

#### Пошаговая инструкция
1.  **Создание файла:** Используйте таймстамп для именования (предотвращает коллизии при слиянии веток).
2.  **Написание SQL:** Обеспечьте безопасный повторный запуск.

```sql
-- V20260817120000__add_email_to_users.sql

-- 1. Добавление колонки с проверкой существования
-- Для PostgreSQL 11+ добавление DEFAULT выполняется мгновенно
ALTER TABLE users ADD COLUMN IF NOT EXISTS email VARCHAR(255) DEFAULT NULL;

-- 2. Миграция данных (DML)
-- Рекомендуется выполнять небольшими порциями (Batching) в больших таблицах
UPDATE users SET email = username || '@internal.corp' WHERE email IS NULL;

-- 3. Создание индекса
-- В PostgreSQL используйте CONCURRENTLY для избежания блокировки таблицы на запись
-- ВАЖНО: CREATE INDEX CONCURRENTLY нельзя выполнять внутри транзакции
CREATE INDEX IF NOT EXISTS idx_users_email ON users(email);
```

#### Валидация
- Проверьте статус миграций через CLI инструмента:
  ```bash
  flyway info
  # Ожидаемый результат: состояние миграции 'Success'
  ```
- Проверьте структуру БД: `\d users` (в psql).
- Проверьте контрольные суммы: `flyway validate` (должен вернуть `Success`).
- Проверьте размер индекса: `SELECT pg_size_pretty(pg_relation_size('idx_users_email'));`.

#### Устранение неисправностей
- **Ошибка "Checksum mismatch":** Файл миграции был изменен после применения. **Решение:** Верните исходный текст файла или выполните `flyway repair` (только для Dev/Test).
- **Lock Timeout:** Миграция не может получить блокировку. **Решение:** Найдите блокирующий процесс через `pg_stat_activity` и завершите его или повторите запуск в окно минимальной нагрузки.
- **Индекс не строится:** `CREATE INDEX CONCURRENTLY` требует отдельной транзакции. Убедитесь, что миграция не обёрнута в `BEGIN/COMMIT` (в Flyway Community каждая миграция — отдельная транзакция).

### Сценарий 3: Декларативное управление схемой (Atlas)

Задача: добавить колонку `phone` в таблицу `users` через декларативный описание.

#### Пошаговая инструкция
1.  **Создание схемемы-описания (HCL):**
    ```hcl
    schema "public" {
      table "users" {
        column "id" { type = "serial" primary_key = true }
        column "username" { type = "varchar(255)" unique = true }
        column "email" { type = "varchar(255)" }
        column "phone" { type = "varchar(50)" nullable = true }
      }
      index "idx_users_phone" { columns = ["phone"] unique = false }
    }
    ```
2.  **Проверка плана (Dry-run):**
    ```bash
    atlas schema apply --env local --auto-approve
    # Atlas сравнит текущую БД с описанием и выведет план ALTER
    ```
3.  **Применение:** После ручного или автоматического подтверждения план применяется.

#### Валидация
- Atlas сравнивает схему после применения с желаемой и сообщает `Schema is up to date`.
- Проверьте контрольные суммы: `SELECT * FROM atlas_schema_history;`.

## Предпосылки и подготовка

Перед запуском миграции в Production выполните стандартный чек-лист.

- **Резервная копия:** Актуальность и восстанавливаемость. Для PostgreSQL выполните `pg_basebackup` или snapshot storage; для MySQL — `xtrabackup --backup`. Проверьте целостность через `pg_checksum` / `XtraBackup --prepare`.
- **Лаг репликации:** Должен быть ниже порога алертинга (обычно < 30с для Streaming Replication / < 10с для синхронной репликации). Если лаг близок к `wal_keep_size` — отложите миграцию.
- **Connection Pool:** Пулы приложения (PgBouncer/ProxySQL) должны иметь запас ёмкости на время миграции. При `ACCESS EXCLUSIVE` пул опустошается, пока DDL не завершится, и новые запросы приложения получают отказы.
- **Активные транзакции:** Должны отсутствовать долгоживущие транзакции в статусе `idle in transaction`. Они удерживают `AccessShareLock` и могут превратить кратковременную DDL-блокировку в каскадный deadlock.
- **Change Advisory Board (CAB):** Миграции, затрагивающие таблицы > 10 ГБ или содержащие `DROP/RENAME`, требуют утверждения. Документируйте окно деплоя, критерии отката и контакты on-call.
- **Maintenance Window:** Для миграций с ожидаемым простоем > 30с согласуйте окно с бизнесом. Для zero-downtime — фиксируйте время cutover в runbook.
- **Runbook:** Для каждой миграции подготовьте документ с пошаговой инструкцией, командами проверки, критериями успешного завершения и планом отката с триггерами.

## Дополнительная информация

### Жизненный цикл миграции в CI/CD

Автоматизация — единственный способ избежать человеческого фактора при обновлении БД.

1.  **Линтинг (Lint):** Статический анализ SQL (например, через `squawk` или `atlas lint`) на наличие опасных операций (блокирующий `DROP`).
2.  **Эфемерное тестирование (Dry-run):** Автоматический запуск миграций на временной базе в Docker.
3.  **Проверка дрейфа (Drift Detection):** Сравнение текущего Production с эталоном перед деплоем.
4.  **Применение (Apply):** Выполнение через Kubernetes Job или специализированный CD-агент с ограниченными правами.

### Жизненный цикл миграции в SRE-подходе

1.  **Pre-flight:** Проверка бэкапов, лага репликации, connection pool, активных транзакций.
2.  **Baseline:** Фиксация метрик CPU, IOPS, лаг репликации, количества соединений до начала миграции.
3.  **Deploy:** Применение через CI/CD или вручную с ограниченными правами.
4.  **Observability:** Сбор метрик SRE Golden Signals во время миграции.
5.  **Post-flight:** Сравнение с baseline. Отклонение > 20% — останов деплоя.
6.  **Cleanup:** Удаление временных объектов, проверка автовакуума.

### Рекомендации

- **Разделяйте DDL и DML:** Тяжелые `UPDATE` запросы не должны блокировать применение структурных изменений.
- **Transactional DDL:** PostgreSQL почти полностью поддерживает. MySQL/MariaDB: при сбое миграции на середине база остаётся в частично изменённом состоянии. Планируйте ручное восстановление или Fix-Forward.
- **Versioning:** Предпочитайте формат `YYYYMMDDHHMMSS` (таймстамп) простым порядковым номерам `V1`, `V2`.
- **Изоляция прав:** CI-пользователь не должен иметь прав `OWNER` на всю базу. Используйте минимально необходимые привилегии для DDL.
- **Дрейф схемы:** Используйте drift detection в CI/CD перед деплоем. При обнаружении дрейфа — создайте reconcile-миграцию или обновите baseline.
- **Connection Pool:** Увеличьте размер пула на время миграции или приостановите запросы через ProxySQL/pgBouncer.
- **SLO/SLI:** Оцените влияние миграции на SLO. Для критичных сервисов используйте canary-подход: применяйте миграцию к подмножеству реплик, затем к 5% master-трафика.

### Пограничные случаи и ограничения

- **Секционированные таблицы:** Большинство DDL-операций в PostgreSQL 11+ выполняется на уровне секций без полной блокировки. Однако `ATTACH PARTITION` требует `ACCESS EXCLUSIVE` на дочерней таблице.
- **Огромные таблицы (> 1 ТБ):** Для таблиц терабайтного класса стандартные средства могут занимать дни. Рассмотрите `pg_repack` (PostgreSQL) или `gh-ost`/`pt-online-schema-change` (MySQL).
- **Внешние ключи (Foreign Keys):** Добавление FK с `NOT VALID` не блокирует чтение, но `VALIDATE CONSTRAINT` acquires `SHARE UPDATE EXCLUSIVE` на таблицу. На очень больших таблицах (> 100M строк) валидация может занимать часы.
- **Транзакционный DDL в MySQL/MariaDB:** DDL вызывает неявный коммит. Невозможно откатить миграцию из нескольких команд средствами СУБД. Используйте бэкапы или Fix-Forward.
- **CREATE INDEX CONCURRENTLY (PostgreSQL):** Нельзя выполнить внутри транзакции. Убедитесь, что инструмент миграций не оборачивает его в BEGIN/COMMIT.
- **Влияние на SLO:** Для сервисов с SLA 99,9% и выше допустимый простой при миграции — минуты. Zero-downtime обязателен.

### Устранение неисправностей

- **Ошибка "Checksum mismatch":** Файл миграции был изменен после применения. **Решение:** Верните исходный текст файла или выполните `flyway repair` (только для Dev/Test).
- **Lock Timeout:** Миграция не может получить блокировку. **Решение:** Найдите блокирующий процесс через `pg_stat_activity` / `SHOW PROCESSLIST` и завершите его или повторите запуск в окно минимальной нагрузки.
- **Дрейф схемы:** Схема в Production отличается от Git. **Решение:** Используйте drift detection в CI/CD перед деплоем.
- **Потеря данных при откате:** Фаза Contract выполнена (старая колонка удалена), а приложение откатили к версии N. **Решение:** Используйте Fix-Forward (новая миграция) вместо отката.
- **Раздувание таблицы (Bloat):** Слишком частые апдейты без пауз. **Решение:** Увеличить паузу между батчами и проверить настройки автовакуума.
- **Replication Lag:** Рост лага во время миграции. **Решение:** Уменьшите размер батчей, проверьте нагрузку на master.
