# Миграции баз данных: Основы

## Определения

- **Миграция базы данных (Database Migration)** — это управляемый процесс изменения схемы базы данных (структуры таблиц, индексов, связей) или трансформации самих данных для обеспечения соответствия БД требованиям приложения.
- **Схема базы данных (Schema)** — логическая структура данных, определяющая таблицы, поля, типы данных, индексы и ограничения (Constraints).
- **Идемпотентность (Idempotency)** — свойство, позволяющее запускать миграцию многократно без возникновения ошибок и дублирования данных. См. **[Идемпотентность](../../../Concepts/idempotency.md)**.
- **Дрейф схемы (Schema Drift)** — нежелательное состояние, при котором фактическая структура БД в окружении (Production/Staging) отличается от эталонной структуры, описанной в системе контроля версий.
- **Базовое состояние (Baseline)** — зафиксированная точка отсчета схемы БД, от которой начинают применяться все последующие миграции.

## Основные концепции

Миграции обеспечивают воспроизводимость окружений и позволяют версионировать структуру данных аналогично исходному коду (Schema-as-Code).

### Подходы к управлению миграциями

Существует две основные парадигмы управления изменениями в БД:

1. **Императивный подход (Change-based):**
   - **Суть:** Фокус на самом процессе изменения.
   - **Метод:** Разработчик пишет последовательность SQL-скриптов или программного кода (`V1`, `V2`, `V3`).
   - **Инструменты:** Flyway, Liquibase, dbmate.
   - **Особенности:** Инструмент хранит таблицу истории миграций в самой БД и применяет только те скрипты, которых там нет. Поддерживает полный контроль над SQL.

2. **Декларативный подход (State-based):**
   - **Суть:** Фокус на конечном (желаемом) состоянии.
   - **Метод:** Разработчик описывает схему (например, в HCL или YAML), а инструмент вычисляет разницу (diff) между текущей БД и целевым описанием, автоматически генерируя план миграции.
   - **Инструменты:** Atlas, Prisma, Bytebase.
   - **Особенности:** Упрощает управление сложными схемами, но требует доверия к движку генерации DDL.

### Типы миграций

- **Схемные (Structural/DDL):** операции по изменению структуры. Создание таблиц, добавление колонок, изменение индексов. Подробнее см. **[DDL и DML: Категории SQL-команд](../DDL_vs_DML.md)**.
- **Миграции данных (Data/DML):** операции по трансформации самих данных. Заполнение новых полей, перенос данных между таблицами, нормализация.
- **Сидовые (Seed):** наполнение БД начальными данными (справочники, настройки по умолчанию).

### Транзакционность и риски

Важнейшим аспектом миграций является поддержка **Transactional DDL**:
- **PostgreSQL:** Позволяет выполнять большинство DDL-операций внутри транзакции. При ошибке миграции БД откатывается к состоянию до её запуска.
- **MySQL:** Не поддерживает транзакционный DDL. Любая DDL-команда вызывает неявный коммит (Implicit Commit), что делает частичный откат миграции невозможным.

## Практические сценарии

### Выбор инструментария (2026)

| Инструмент | Парадигма | Рекомендация |
| :--- | :--- | :--- |
| **Flyway** | Императивный | Проекты на Java/Kotlin или там, где нужен строгий контроль SQL. |
| **Atlas** | Декларативный | Современный SRE-подход, Schema-as-Code, мощный линтинг. |
| **Liquibase** | Императивный | Сложные Enterprise-проекты с необходимостью абстракции от конкретной СУБД. |
| **Bytebase** | Декларативный | Визуальное управление миграциями для команд, "GitOps для БД". |
| **Alembic** | Императивный | Python-экосистема (SQLAlchemy). |

### Пример императивной миграции (SQL)

Использование таймстампов в названии предотвращает конфликты при слиянии веток.

```sql
-- V20260718120530__add_email_to_users.sql
-- 1. Расширение схемы
ALTER TABLE users ADD COLUMN email VARCHAR(255);

-- 2. Миграция данных (DML)
UPDATE users SET email = username || '@example.com' WHERE email IS NULL;

-- 3. Добавление индекса (если Postgres, лучше CONCURRENTLY вне транзакции)
CREATE INDEX idx_users_email ON users(email);
```

### Жизненный цикл миграции в CI/CD

1. **Lint:** Статический анализ SQL на наличие опасных операций (например, блокирующий `DROP`).
2. **Dry-run:** Тестовый запуск миграций на временной эфемерной БД (Docker/Testcontainers).
3. **Drift Detection:** Проверка текущего состояния Production на соответствие мастер-ветке.
4. **Apply:** Выполнение миграции через Kubernetes Job перед развертыванием новой версии приложения.

## Дополнительная информация

### Рекомендации

- **Разделяйте DDL и DML:** Для надежности рекомендуется разделять структурные изменения и тяжелые преобразования данных в разные файлы миграций.
- **Идемпотентность:** Всегда проектируйте миграции так, чтобы их повторный запуск (в случае сбоя сети или инструмента) не приводил к потере данных.
- **Versioning:** Предпочитайте семантические таймстампы (`YYYYMMDDHHMMSS`) простым порядковым номерам.
