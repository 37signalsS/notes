# Миграции баз данных: Основы

## Определения

**Миграция базы данных (Database Migration)** — это управляемый процесс изменения схемы базы данных (структуры таблиц, индексов, связей) или трансформации данных с целью приведения БД в соответствие с актуальными требованиями приложения.

**Схема базы данных (Schema)** — логическая структура данных, описывающая таблицы, поля, типы данных и ограничения (Constraints).

**Идемпотентность (Idempotency)** — свойство миграции, позволяющее запускать её многократно без изменения конечного результата и возникновения ошибок (например, использование `CREATE TABLE IF NOT EXISTS`).

## Основные концепции

Миграции позволяют версионировать структуру БД так же, как и исходный код приложения, обеспечивая воспроизводимость окружений.

### Подходы к управлению миграциями

Существует две основные парадигмы управления изменениями:

1. **Императивный подход (Change-based):**
   - Фокус на **изменении**.
   - Описывается последовательность SQL-скриптов (`V1`, `V2`, `V3`).
   - Инструмент (Flyway, Liquibase) хранит таблицу метаданных и применяет только новые скрипты.
   - Плюсы: полный контроль над SQL, предсказуемость.

2. **Декларативный подход (State-based):**
   - Фокус на **конечном состоянии**.
   - Описывается желаемая схема (например, в HCL или YAML), а инструмент (Atlas, Prisma) сам генерирует необходимые команды для приведения текущей БД к целевому виду.
   - Плюсы: автоматизация сложных диффов, Schema-as-Code.

### Типы миграций

- **Схемные (Structural):** создание/изменение таблиц, индексов, представлений. Используют операции **[DDL (Data Definition Language)](../DDL_vs_DML.md)**.
- **Миграции данных (Data):** обновление, перенос или очистка записей. Используют операции **[DML (Data Definition Language)](../DDL_vs_DML.md)**.
- **Сидовые (Seed):** наполнение справочников и базовых настроек системы.

### Жизненный цикл миграции

1. **Разработка:** написание скрипта или описание состояния.
2. **Локальное тестирование:** применение на временной БД.
3. **Валидация (CI):** проверка синтаксиса и безопасности (линтеры).
4. **Применение (Deployment):** выполнение на целевом окружении до деплоя кода.

## Практические сценарии

### Выбор инструментария

| Инструмент | Подход | Экосистема | Ключевая особенность |
| :--- | :--- | :--- | :--- |
| **Flyway** | Императивный | Любая (Java-based) | Простота, SQL-скрипты как основной формат. |
| **Liquibase** | Императивный | Любая (Java-based) | Поддержка XML/YAML для абстракции от СУБД. |
| **Atlas** | Декларативный | Любая (Go-based) | Мощный движок диффов, поддержка GitOps. |
| **Alembic** | Императивный | Python | Глубокая интеграция с SQLAlchemy. |
| **Prisma** | Декларативный | Node.js / TS | Автогенерация типов и схемы из одного файла. |
| **Django** | Декларативный | Python | Встроенная магия ORM, автоматическое отслеживание изменений моделей. |

### Пример императивной миграции (SQL)

```sql
-- V20260718__add_user_roles.sql
-- Расширение схемы согласно паттерну Expand-Contract
ALTER TABLE users ADD COLUMN role_id INTEGER;

-- Миграция данных (Data Migration)
UPDATE users SET role_id = 1 WHERE is_admin = true;
UPDATE users SET role_id = 2 WHERE is_admin = false;
```

### Пример декларативного описания (Atlas HCL)

```hcl
table "users" {
  schema = schema.public
  column "id" {
    type = int
  }
  column "email" {
    type = varchar(255)
  }
  index "idx_email" {
    columns = [column.email]
    unique  = true
  }
}
```

## Дополнительная информация

### Рекомендации

- **Транзакционность:** если СУБД поддерживает транзакционный DDL (например, PostgreSQL), всегда выполняйте миграции в транзакциях.
- **Версионирование:** используйте временные метки (Timestamp) вместо простых чисел (`V1`, `V2`) для избежания конфликтов при мерже веток.
- **Безопасность:** никогда не храните учетные данные в файлах миграций.
