# Лучшие практики миграций баз данных

## Определения

**Лучшие практики миграций** — это стандартизированный набор правил и инженерных подходов, обеспечивающих предсказуемость, безопасность и автоматизируемость процесса изменения схемы и данных СУБД.

**Атомарность миграции** — принцип, согласно которому один файл миграции должен содержать минимально возможное логически законченное изменение. Это упрощает отладку и минимизирует риски при частичном откате.

**Таймаут блокировки (Lock Timeout)** — параметр сессии, ограничивающий время ожидания получения блокировки на таблицу. Критически важен для предотвращения очередей запросов в production.

## Основные концепции

### Именование и упорядочивание

Для обеспечения детерминированного порядка выполнения и исключения конфликтов в командной разработке:
- **Timestamp-based:** использование `YYYYMMDDHHMMSS` в префиксе (например, `20260718120000_add_user_index.sql`). Рекомендуется для Git-потоков с множеством параллельных веток.
- **Semantic naming:** имя файла должно кратко отражать суть изменений (избегайте `migration_1.sql`).

### Принципы безопасности

1. **Идемпотентность:** миграция должна успешно завершаться, даже если она уже была частично или полностью применена. Использование `IF NOT EXISTS` для таблиц/индексов и защитных блоков `DO` для колонок.
2. **Управление таймаутами:** при выполнении миграции в высоконагруженных системах необходимо принудительно ограничивать время ожидания блокировки, чтобы не «подвесить» все входящие запросы к таблице.
3. **Атомарные транзакции:** группировка изменений в блоки `BEGIN...COMMIT`.
   *   *Примечание:* в PostgreSQL такие команды как `CREATE INDEX CONCURRENTLY` запрещены внутри транзакций.

### Линтинг и статический анализ

Использование инструментов автоматической проверки SQL (например, `sqlfluff`, `atlas lint`) для:
- Запрета «опасных» команд (`DROP`, `TRUNCATE`).
- Проверки наличия индексов для новых внешних ключей.
- Контроля стилистики и именования.

## Практические сценарии

### Сценарий 1: Настройка защитных таймаутов (PostgreSQL)

Обязательная практика для предотвращения каскадных сбоев из-за ожидания блокировок (`Lock Wait`).

```sql
-- Установка таймаутов на уровне сессии перед выполнением DDL
SET lock_timeout = '5s';      -- Ждать блокировку не более 5 секунд
SET statement_timeout = '10s'; -- Выполнять сам запрос не более 10 секунд

-- Теперь выполнение миграции безопасно
ALTER TABLE orders ADD COLUMN internal_note TEXT;
```

### Сценарий 2: Идемпотентное управление схемой

Пример создания структуры, устойчивой к повторному запуску.

```sql
-- 1. Создание таблицы
CREATE TABLE IF NOT EXISTS projects (
    id SERIAL PRIMARY KEY,
    title VARCHAR(255) NOT NULL
);

-- 2. Безопасное добавление колонки (PostgreSQL)
DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM information_schema.columns 
                   WHERE table_name='projects' AND column_name='status') THEN
        ALTER TABLE projects ADD COLUMN status VARCHAR(50) DEFAULT 'draft';
    END IF;
END $$;
```

### Сценарий 3: Разделение DDL и DML

Разделение изменения структуры и обновления данных повышает стабильность.

**Файл 1: `2026071801_add_column.sql` (DDL)**
```sql
ALTER TABLE users ADD COLUMN is_active BOOLEAN DEFAULT true;
```

**Файл 2: `2026071802_migrate_data.sql` (DML)**
```sql
-- Обновление данных батчами (см. Типовые сценарии миграций)
UPDATE users SET is_active = true WHERE created_at > '2026-01-01';
```

## Дополнительная информация

### Рекомендации

- **Small & Atomic:** один файл — одно изменение. Не смешивайте создание таблицы и обновление данных в другом модуле.
- **Lock Monitoring:** во время выполнения миграции на проде мониторьте `pg_stat_activity` на предмет заблокированных процессов.
- **No `SELECT *`:** убедитесь, что код приложения не использует `SELECT *`, так как добавление колонки в фазе `Expand` может нарушить ожидаемую структуру кортежа.
