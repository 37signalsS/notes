# Лучшие практики миграций баз данных

## Определения

- **Лучшие практики миграций** — это набор инженерных стандартов, обеспечивающих предсказуемость, безопасность и автоматизируемость изменений схемы (DDL) и данных (DML) СУБД.
- **Атомарность миграции** — принцип, согласно которому один файл миграции должен содержать минимально возможное логически законченное изменение.
- **Таймаут блокировки (Lock Timeout)** — параметр сессии, ограничивающий время ожидания получения эксклюзивной блокировки на объект БД.
- **Schema Drift (Дрейф схемы)** — расхождение между фактической структурой БД и её описанием в системе контроля версий.

## Основные концепции

### Стратегии именования и версионирования

Для обеспечения детерминированного порядка выполнения, особенно в условиях параллельной командной разработки, используются следующие подходы:

- **Использование таймстампов:** Вместо порядковых номеров (`V1`, `V2`) используйте префикс `YYYYMMDDHHMMSS` (например, `20260718120530_add_user_index.sql`). Это предотвращает конфликты при слиянии нескольких веток с новыми миграциями.
- **Семантическое именование:** Название должно отражать суть (например, `add_index_to_orders_user_id`), а не быть техническим идентификатором.

### Принципы безопасности в высоконагруженных системах

1. **Идемпотентность:** Миграция должна успешно завершаться, даже если она уже была частично применена. Это критично при сетевых сбоях инструментов миграции.
    - Используйте `IF NOT EXISTS` для таблиц и индексов.
    - Используйте защитные блоки `DO` (PostgreSQL) для проверки существования колонок или ограничений.
2. **Управление таймаутами (Lock & Statement):** Никогда не запускайте DDL на Production без установленных лимитов. Длительное ожидание блокировки может выстроить очередь из обычных запросов приложения, что приведет к отказу в обслуживании (DoS).
3. **Транзакционный DDL:** Всегда группируйте изменения в блоки `BEGIN...COMMIT`, если СУБД это поддерживает (PostgreSQL).
    - **Внимание:** В MySQL любая DDL-команда вызывает неявный коммит текущей транзакции.

### Линтинг и статический анализ (Database CI)

Автоматизация проверок в пайплайнах позволяет отсекать опасные операции до их попадания в Production.
- **Atlas Lint:** Проверка на дрейф схемы и опасные диффы.
- **Squawk (PostgreSQL):** Специализированный линтер, выявляющий блокирующие операции (например, добавление колонки с `NOT NULL` без `DEFAULT` в старых версиях).
- **sqlfluff:** Контроль стиля SQL и синтаксических ошибок.

## Практические сценарии

### Сценарий 1: Установка защитных таймаутов (Multi-DB)

**PostgreSQL:**
```sql
-- Установка на уровне сессии перед выполнением миграции
SET lock_timeout = '5s';        -- Время ожидания блокировки
SET statement_timeout = '30s';   -- Общее время выполнения запроса
ALTER TABLE users ADD COLUMN phone_number VARCHAR(20);
```

**MySQL:**
```sql
-- Установка таймаута ожидания блокировки метаданных (MDL)
SET SESSION lock_wait_timeout = 5;
ALTER TABLE users ADD COLUMN phone_number VARCHAR(20);
```

### Сценарий 2: Идемпотентное добавление ограничения (Check Constraint)

Безопасное добавление логической проверки в PostgreSQL без блокировки таблицы на чтение.

```sql
DO $$
BEGIN
    -- 1. Добавляем ограничение как NOT VALID (проверка только для новых данных)
    IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'check_positive_price') THEN
        ALTER TABLE products ADD CONSTRAINT check_positive_price 
        CHECK (price > 0) NOT VALID;
    END IF;
END $$;

-- 2. Валидация существующих данных (вне транзакции, не блокирует запись)
ALTER TABLE products VALIDATE CONSTRAINT check_positive_price;
```

### Сценарий 3: Разрешение конфликтов в Git (Parallel Development)

При слиянии веток с пересекающимися таймстампами или логическими зависимостями:
1. **Baseline check:** Инструменты типа Flyway или Atlas должны проверять контрольные суммы (checksums) применимых файлов.
2. **Rebase policy:** Требуйте перебазирования (rebase) ветки с БД-изменениями на актуальный `main`, чтобы разработчик проверил совместимость своей миграции с новыми изменениями коллег.

### Сценарий 4: Верификация после миграции (Sanity Checks)

Автоматизированная проверка здоровья системы сразу после применения изменений:
- Проверка лага репликации (`pg_replication_lag`).
- Проверка наличия невалидных индексов (`SELECT * FROM pg_class WHERE relkind = 'i' AND relhasindex = false`).
- Простая выборка из обновленной таблицы для подтверждения доступности данных.

## Дополнительная информация

### Рекомендации

- **Small & Atomic:** Один файл — одно логическое изменение. Не смешивайте создание таблиц с обновлением данных в нерелевантных модулях.
- **No `SELECT *` в приложении:** Это критическое требование для работы по паттерну **[Expand-Contract](expand_contract.md)**. Приложение должно явно перечислять колонки, чтобы добавление новой не вызвало ошибок в маппинге данных.
- **Review Workflow:** Все миграции должны проходить обязательное ревью DBA или Senior-инженеров, обладающих пониманием блокировок конкретной СУБД.
