# Лучшие практики миграций баз данных

## Определения

**Лучшие практики миграций** — это набор правил и подходов, направленных на обеспечение надежности, воспроизводимости и безопасности процесса изменения схемы и данных базы данных.

**Идемпотентность миграции** — свойство, при котором повторное выполнение одной и той же миграции не приводит к ошибкам или нежелательным изменениям состояния системы, если она уже находится в целевом состоянии.

**Транзакционность миграции** — применение изменений в рамках единой транзакции БД, гарантирующее атомарность операции («все или ничего»).

## Основные концепции

### Именование и версионирование

Использование строгих правил именования файлов предотвращает конфликты и гарантирует правильный порядок выполнения.

**Популярные форматы:**

- **Версионный (Flyway):** `V<Номер>__<Описание>.sql` (например, `V1__create_users.sql`).
- **На основе временной метки:** `YYYYMMDDHHMMSS_<Описание>.sql` (например, `20240101120000_add_phone.sql`). Позволяет избежать коллизий номеров при параллельной разработке в разных ветках.

### Идемпотентность

Миграция должна быть написана так, чтобы ее повторный запуск (например, после сбоя или в CI/CD) не приводил к ошибкам. Это достигается использованием защитных конструкций (`IF NOT EXISTS`, `IF EXISTS`).

### Транзакционность

Все изменения в рамках одного файла миграции должны выполняться в единой транзакции. Если одна команда завершится сбоем, база данных должна автоматически вернуться в исходное состояние. Важно учитывать, что не все СУБД поддерживают транзакционный DDL (PostgreSQL поддерживает, MySQL — нет).

## Практические сценарии

### Сценарий 1: Реализация идемпотентности в SQL

Использование защитных условий позволяет безопасно перезапускать миграции.

```sql
-- Проверка существования таблицы перед созданием
CREATE TABLE IF NOT EXISTS users (
    id SERIAL PRIMARY KEY,
    username VARCHAR(50) NOT NULL
);

-- Добавление колонки с проверкой в PostgreSQL
DO $$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM information_schema.columns 
                   WHERE table_name='users' AND column_name='phone') THEN
        ALTER TABLE users ADD COLUMN phone VARCHAR(20);
    END IF;
END $$;
```

### Сценарий 2: Применение транзакций

Оборачивание миграции в блок `BEGIN ... COMMIT`.

```sql
-- PostgreSQL: транзакционная миграция
BEGIN;

-- 1. Добавление колонки
ALTER TABLE users ADD COLUMN phone VARCHAR(20);

-- 2. Обновление существующих данных
UPDATE users SET phone = 'N/A' WHERE phone IS NULL;

-- 3. Установка ограничения NOT NULL
ALTER TABLE users ALTER COLUMN phone SET NOT NULL;

COMMIT;
```

*Примечание: в PostgreSQL некоторые операции (например, `CREATE INDEX CONCURRENTLY`) нельзя выполнять внутри транзакции.*

## Дополнительная информация

### Рекомендации

- **Разделение DDL и DML:** по возможности разделяйте изменения структуры (DDL) и изменения данных (DML) в разные файлы миграций для упрощения отладки и отката.
- **Откат:** для каждой миграции (`up`) должна быть предусмотрена процедура отката (`down`), если это технически возможно и оправдано.
- **Тестирование:** всегда проверяйте миграции на копии реальных данных (staging) перед применением в production.
