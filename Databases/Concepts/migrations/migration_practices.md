# Лучшие практики миграций баз данных

## Определения

- **Лучшие практики миграций** — это набор инженерных стандартов и паттернов, направленных на минимизацию рисков при изменении схемы (DDL) или данных (DML) СУБД, обеспечивающих высокую доступность системы и предсказуемость релизов.
- **Атомарность миграции** — принцип проектирования, при котором один файл миграции содержит ровно одно логически завершенное и минимально возможное изменение. Это упрощает отладку и откат.
- **Таймаут блокировки (Lock Timeout)** — критический параметр сессии, определяющий максимальное время ожидания получения эксклюзивной блокировки. Предотвращает образование очередей запросов, способных вызвать отказ приложения (DoS).
- **Идемпотентность** — свойство скрипта миграции, позволяющее запускать его неограниченное количество раз без изменения состояния системы после первого успешного выполнения и без генерации ошибок.
- **Дрейф схемы (Schema Drift)** — несанкционированное расхождение между фактической структурой БД и её эталонным описанием в системе контроля версий.

## Основные концепции

### Стратегии именования и версионирования

Для обеспечения детерминированного порядка выполнения и исключения конфликтов в распределенных командах используются следующие подходы:

1.  **Таймстампы (Timestamp-based):** Использование префикса `YYYYMMDDHHMMSS` (например, `V20260817120000__add_user_id.sql`). В отличие от простых порядковых номеров (`V1`, `V2`), таймстампы практически исключают коллизии при слиянии нескольких Feature-веток.
2.  **Семантическое описание:** Название должно четко отражать суть изменений (например, `rename_email_to_login`), что критично для аудита и быстрого понимания структуры изменений без чтения SQL-кода.

### Безопасность в высоконагруженных системах (SRE Standard)

- **Управление таймаутами:** Применение DDL на Production без `lock_timeout` запрещено. Длительное ожидание `AccessExclusiveLock` блокирует все последующие запросы к таблице, включая простые `SELECT`.
- **Разделение DDL и DML:** Рекомендуется разделять структурные изменения и массовые обновления данных в разные файлы. Это позволяет СУБД эффективно управлять транзакциями и ресурсами (например, Autovacuum в Postgres).
- **Отказ от `SELECT *`:** Приложение **обязано** явно перечислять колонки. Это позволяет безопасно добавлять новые поля в фазе `Expand` паттерна **[Expand-Contract](expand_contract.md)** без ошибок маппинга в коде.

### Автоматизация и контроль (Database CI)

Интеграция проверок в пайплайны — единственный способ гарантировать соблюдение стандартов:
- **Линтинг (Squawk, Atlas Lint):** Автоматическое выявление блокирующих операций до их попадания в мастер-ветку.
- **Dry-run (Тестирование на эфемерных БД):** Проверка SQL на синтаксические ошибки и конфликты объектов в реальной среде (Docker).

## Практические сценарии

### Сценарий 1: Безопасное выполнение DDL с таймаутами

Установка защитных барьеров для предотвращения деградации производительности БД.

#### Предпосылки
- Наличие прав на изменение параметров сессии.
- Понимание текущей нагрузки на целевую таблицу.

#### Пошаговая инструкция (PostgreSQL)
1. **Установка лимитов:** Ограничить время ожидания и общее время выполнения.
2. **Выполнение миграции:** Применение изменений в рамках установленных границ.

```sql
-- Установка на уровне сессии
SET lock_timeout = '2s';        -- Ждать блокировку не более 2 секунд
SET statement_timeout = '30s';   -- Прекратить запрос, если он идет дольше 30 секунд

-- Добавление колонки
ALTER TABLE orders ADD COLUMN IF NOT EXISTS internal_comment TEXT;
```

#### Валидация
- Проверка структуры: `\d orders`.
- Проверка логов: Отсутствие сообщений об очереди блокировок.

#### Устранение неисправностей
- **Ошибка `canceling statement due to lock timeout`:** Таблица занята долгими процессами (например, бэкапом или тяжелым отчетом). **Решение:** Повторить запуск в период низкой активности или вручную завершить блокирующую сессию.

### Сценарий 2: Идемпотентное управление ограничениями

Добавление логических проверок (`CHECK`) или внешних ключей (`FK`) без блокировки записи в таблицу.

#### Пошаговая инструкция (PostgreSQL)
1. **Expand:** Добавить ограничение с флагом `NOT VALID`. Это проверит только новые строки.
2. **Migrate:** Проверить существующие данные в фоновом режиме.

```sql
DO $$
BEGIN
    -- Проверка на существование перед добавлением
    IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'chk_min_price') THEN
        ALTER TABLE products ADD CONSTRAINT chk_min_price 
        CHECK (price >= 0.01) NOT VALID;
    END IF;
END $$;

-- Валидация (выполняется вне транзакции, не блокирует запись)
ALTER TABLE products VALIDATE CONSTRAINT chk_min_price;
```

#### Валидация
- `SELECT convalidated FROM pg_constraint WHERE conname = 'chk_min_price';` должен вернуть `true`.

### Сценарий 3: Разрешение конфликтов в Git (Parallel Development)

#### Пошаговая инструкция
1. **Rebase Policy:** Всегда делайте `git rebase main` перед мерджем ветки с миграциями.
2. **Baseline Validation:** Инструмент (Flyway/Atlas) должен проверить контрольные суммы. Если коллега изменил существующую миграцию — пайплайн обязан упасть.

---

### Сценарий 4: Верификация после миграции (Sanity Checks)

#### Пошаговая инструкция
Сразу после применения миграции выполните автоматизированные проверки:
1. **Индексы:** Проверить наличие `INVALID` индексов в PostgreSQL.
   ```sql
   SELECT relname FROM pg_class c JOIN pg_index i ON c.oid = i.indrelid 
   WHERE i.indisvalid = false;
   ```
2. **Статистика:** Выполнить `ANALYZE` для обновленных таблиц, чтобы планировщик запросов использовал актуальные данные.

## Дополнительная информация

### Рекомендации

- **DBA Review:** Все миграции, затрагивающие таблицы размером > 10 ГБ или содержащие `DROP/RENAME`, требуют ручного ревью Senior инженером.
- **Изоляция прав:** CI-пользователь не должен иметь прав `OWNER` на всю базу. Используйте минимально необходимые привилегии для DDL.
- **Версионирование в коде:** Используйте инструменты типа `Atlas` для декларативного описания схемы, если проект предполагает частые и сложные изменения.
