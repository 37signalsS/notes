# Лучшие практики миграций баз данных

**Актуально для:** PostgreSQL 11+, MySQL 8.0.12+, MariaDB 10.3+

## Определения

- **Лучшие практики миграций** — это набор инженерных стандартов и паттернов, направленных на минимизацию рисков при изменении схемы (DDL) или данных (DML) СУБД, обеспечивающих высокую доступность системы и предсказуемость релизов.
- **Атомарность миграции** — принцип проектирования, при котором один файл миграции содержит ровно одно логически завершенное и минимально возможное изменение. Это упрощает отладку и откат.
- **Таймаут блокировки (Lock Timeout)** — критический параметр сессии, определяющий максимальное время ожидания получения эксклюзивной блокировки. Предотвращает образование очередей запросов, способных вызвать отказ приложения (DoS).
- **Идемпотентность** — свойство скрипта миграции, позволяющее запускать его неограниченное количество раз без изменения состояния системы после первого успешного выполнения и без генерации ошибок.
- **Дрейф схемы (Schema Drift)** — несанкционированное расхождение между фактической структурой БД и её эталонным описанием в системе контроля версий.
- **Quality Gate (Качество деплоя)** — автоматизированная проверка в CI/CD, блокирующая продвижение миграции при обнаружении опасных паттернов (например, блокирующих `ALTER` без `CONCURRENTLY`).
- **Change Advisory Board (CAB)** — группа, ответственная за оценку рисков миграций, согласование окон обслуживания и утверждение планов изменений в Production.
- **Baseline (Базовое состояние)** — моментальный снимок существующей схемы БД, принимаемый за точку отсчета для начала использования инструментов миграций в уже работающем проекте.
- **Schema History Table (Таблица истории миграций)** — служебная таблица в БД (например, `flyway_schema_history`, `DATABASECHANGELOG`), где инструмент хранит контрольные суммы, статус применения и время выполнения каждой миграции.
- **Checksum (Контрольная сумма миграции)** — хэш содержимого файла миграции, вычисляемый инструментом. Служит для обнаружения несанкционированных изменений в уже применённых миграциях.

## Основные концепции

### Стратегии именования и версионирования

Для обеспечения детерминированного порядка выполнения и исключения конфликтов в распределенных командах используются следующие подходы:

1.  **Таймстампы (Timestamp-based):** Использование префикса `YYYYMMDDHHMMSS` (например, `V20260817120000__add_user_id.sql`). В отличие от простых порядковых номеров (`V1`, `V2`), таймстампы практически исключают коллизии при слиянии нескольких Feature-веток.
2.  **Семантическое описание:** Название должно четко отражать суть изменений (например, `rename_email_to_login`), что критично для аудита и быстрого понимания структуры изменений без чтения SQL-кода.

#### Антипаттерны именования
- **Порядковые номера без таймстампов:** `V1__init.sql`, `V2__add.sql` — приводят к конфликтам при параллельной разработке в ветках.
- **Неинформативные имена:** `V20260817120000__fix.sql` — не позволяют понять суть изменения без чтения кода.
- **Смешение стилей:** Использование таймстампов в одних ветках и порядковых номеров в других нарушает детерминизм.

### Безопасность в высоконагруженных системах (SRE Standard)

- **Управление таймаутами:** Применение DDL на Production без `lock_timeout` запрещено. Длительное ожидание `AccessExclusiveLock` блокирует все последующие запросы к таблице, включая простые `SELECT`.
- **Разделение DDL и DML:** Рекомендуется разделять структурные изменения и массовые обновления данных в разные файлы. Это позволяет СУБД эффективно управлять транзакциями и ресурсами (например, Autovacuum в Postgres).
- **Отказ от `SELECT *`:** Приложение **обязано** явно перечислять колонки. Это позволяет безопасно добавлять новые поля в фазе `Expand` паттерна **[Обратно-совместимые миграции (Expand-Contract)](expand_contract.md)** без ошибок маппинга в коде.

### Транзакционное управление

Применение транзакций к миграциям требует понимания особенностей СУБД:

- **PostgreSQL:** Почти все DDL-команды атомарны. При сбое миграции база автоматически откатывается к состоянию `V(N-1)`. Исключение: `CREATE INDEX CONCURRENTLY` и `VACUUM` нельзя выполнить внутри транзакции.
- **MySQL / MariaDB:** DDL вызывает неявный COMMIT. При сбое миграции на середине база остаётся в частично изменённом состоянии. Невозможно откатить миграцию из нескольких команд средствами СУБД. Используйте бэкапы или Fix-Forward.
- **SQLite:** Полностью транзакционный, но подходит только для embedded-сценариев.

### Обработка ошибок и повторные попытки

- **Retry Policy:** Для идемпотентных миграций (добавление колонки, создание индекса) автоматически повторяйте запуск при `lock_timeout` или `deadlock`. Используйте экспоненциальную задержку (1с, 2с, 4с) между попытками.
- **Non-idempotent миграции:** Для DML-операций (заполнение данных) используйте пакетную обработку с контрольными точками (`COMMIT` после каждого батча). При сбое повторный запуск продолжает с последней контрольной точки.
- **Failure Isolation:** Одна неудавшаяся миграция не должна блокировать очередь. Используйте отдельные сессии/транзакции для каждой миграции.

### Change Management и CAB

Миграции, затрагивающие таблицы > 10 ГБ или содержащие `DROP/RENAME`, требуют утверждения Change Advisory Board (CAB). Документируйте:
- Окно деплоя и ожидаемое время простоя.
- Критерии отката и триггеры для его запуска.
- Контакты on-call инженеров.

### Изоляция прав и безопасность

- **Principle of Least Privilege:** CI-пользователь не должен иметь прав `OWNER` на всю базу. Используйте минимально необходимые привилегии для DDL.
  ```sql
  -- PostgreSQL: создание роли с минимальными правами
  CREATE ROLE ci_migration WITH LOGIN;
  GRANT CREATE ON SCHEMA public TO ci_migration;
  GRANT USAGE, SELECT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO ci_migration;
  GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO ci_migration;
  ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT USAGE, SELECT ON SEQUENCES TO ci_migration;
  ```
- **Изоляция окружений:** Пользователь для CI не должен совпадать с пользователем для Production. Используйте отдельные учетные записи с разными политиками доступа.
- **Аудит:** Включайте `application_name` в соединениях для идентификации миграционных сессий в логах.

### Особенности СУБД

| СУБД | Транзакционный DDL | Блокировки при ADD COLUMN | Онлайн-индексы | Онлайн-FK |
| :--- | :--- | :--- | :--- | :--- |
| **PostgreSQL** | Да (почти полностью) | Мгновенно (с 11+) | `CREATE INDEX CONCURRENTLY` | `NOT VALID` + `VALIDATE CONSTRAINT` |
| **MySQL 8.0.12+** | Нет (неявный COMMIT) | `ALGORITHM=INPLACE, LOCK=NONE` | `ALGORITHM=INPLACE` | `ALGORITHM=INPLACE, LOCK=NONE` |
| **MariaDB 10.3+** | Нет (неявный COMMIT) | `ALGORITHM=INPLACE, LOCK=NONE` | `ALGORITHM=INPLACE` | `ALGORITHM=INPLACE, LOCK=NONE` |

## Предпосылки и подготовка

Перед запуском миграции в Production выполните стандартный чек-лист.

- **Резервная копия:** Актуальность и восстанавливаемость. Для PostgreSQL выполните `pg_basebackup` или snapshot storage; для MySQL — `xtrabackup --backup`. Проверьте целостность через `pg_checksum` / `XtraBackup --prepare`.
- **Лаг репликации:** Должен быть ниже порога алертинга (обычно < 30с для Streaming Replication / < 10с для синхронной репликации). Если лаг близок к `wal_keep_size` — отложите миграцию.
- **Connection Pool:** Пулы приложения (PgBouncer/ProxySQL) должны иметь запас ёмкости на время миграции. При `ACCESS EXCLUSIVE` пул опустошается, пока DDL не завершится, и новые запросы приложения получают отказы.
- **Активные транзакции:** Должны отсутствовать долгоживущие транзакции в статусе `idle in transaction`. Они удерживают `AccessShareLock` и могут превратить кратковременную DDL-блокировку в каскадный deadlock.
- **Change Advisory Board (CAB):** Миграции, затрагивающие таблицы > 10 ГБ или содержащие `DROP/RENAME`, требуют утверждения. Документируйте окно деплоя, критерии отката и контакты on-call.
- **Maintenance Window:** Для миграций с ожидаемым простем > 30с согласуйте окно с бизнесом. Для zero-downtime — фиксируйте время cutover в runbook.
- **Runbook:** Для каждой миграции подготовьте документ с пошаговой инструкцией, командами проверки, критериями успешного завершения и планом отката с триггерами.

## Практические сценарии

### Сценарий 1: Безопасное выполнение DDL с таймаутами

Установка защитных барьеров для предотвращения деградации производительности БД.

#### Предпосылки
- Наличие прав на изменение параметров сессии.
- Понимание текущей нагрузки на целевую таблицу.

#### Пошаговая инструкция (PostgreSQL)
1. **Установка лимитов:** Ограничить время ожидания и общее время выполнения.
2. **Выполнение миграции:** Применение изменений в рамках установленных границ.

```sql
-- Установка на уровне сессии
SET lock_timeout = '2s';        -- Ждать блокировку не более 2 секунд
SET statement_timeout = '30s';   -- Прекратить запрос, если он идет дольше 30 секунд

-- Добавление колонки
ALTER TABLE orders ADD COLUMN IF NOT EXISTS internal_comment TEXT;
```

#### Валидация
- Проверка структуры: `\d orders`.
- Проверка логов: Отсутствие сообщений об очереди блокировок.

#### Устранение неисправностей
- **Ошибка `canceling statement due to lock timeout`:** Таблица занята долгими процессами (например, бэкапом или тяжелым отчетом). **Решение:** Повторить запуск в период низкой активности или вручную завершить блокирующую сессию.

---

### Сценарий 2: Идемпотентное управление ограничениями

Добавление логических проверок (`CHECK`) или внешних ключей (`FK`) без блокировки записи в таблицу.

#### Пошаговая инструкция (PostgreSQL)
1. **Expand:** Добавить ограничение с флагом `NOT VALID`. Это проверит только новые строки.
2. **Migrate:** Проверить существующие данные в фоновом режиме.

```sql
DO $$
BEGIN
    -- Проверка на существование перед добавлением
    IF NOT EXISTS (SELECT 1 FROM pg_constraint WHERE conname = 'chk_min_price') THEN
        ALTER TABLE products ADD CONSTRAINT chk_min_price 
        CHECK (price >= 0.01) NOT VALID;
    END IF;
END $$;

-- Валидация (выполняется вне транзакции, не блокирует запись)
ALTER TABLE products VALIDATE CONSTRAINT chk_min_price;
```

#### Валидация
- `SELECT convalidated FROM pg_constraint WHERE conname = 'chk_min_price';` должен вернуть `true`.

---

### Сценарий 3: Разрешение конфликтов в Git (Parallel Development)

#### Пошаговая инструкция
1. **Rebase Policy:** Всегда делайте `git rebase main` перед мерджем ветки с миграциями.
2. **Baseline Validation:** Инструмент (Flyway/Atlas) должен проверить контрольные суммы. Если коллега изменил существующую миграцию — пайплайн обязан упасть.

---

### Сценарий 4: Верификация после миграции (Sanity Checks)

#### Пошаговая инструкция
Сразу после применения миграции выполните автоматизированные проверки:
1. **Индексы:** Проверить наличие `INVALID` индексов в PostgreSQL.
    ```sql
    SELECT relname FROM pg_class c JOIN pg_index i ON c.oid = i.indrelid 
    WHERE i.indisvalid = false;
    ```
2. **Статистика:** Выполнить `ANALYZE` для обновленных таблиц, чтобы планировщик запросов использовал актуальные данные.

---

### Сценарий 5: Качество миграций в CI/CD (Quality Gates)

Интеграция проверок в пайплайн — единственный способ гарантировать соблюдение стандартов.

#### Пошаговая инструкция
1. **Линтинг (Lint):** Автоматический статический анализ SQL на наличие опасных операций.
    ```bash
    # Пример: Squawk для PostgreSQL
    squawk --version 1.0 --transactions migrations/
    ```
2. **Dry-run (Эфемерное тестирование):** Применение миграций на временной базе в Docker.
    ```bash
    # Flyway: проверка на clean/test БД
    flyway -url=jdbc:postgresql://localhost:5432/test_db migrate
    ```
3. **Drift Detection:** Сравнение текущего состояния с мастер-веткой перед деплоем.
    ```bash
    # Atlas: сравнение Production с Git
    atlas schema inspect -u "postgres://user:pass@prod:5432/db" > current.hcl
    atlas schema diff --from "file://schema.hcl" --to "file://current.hcl"
    ```
4. **DBA Review Gate:** Для критичных изменений (таблицы > 10 ГБ, `DROP COLUMN`) — ручное подтверждение.

#### Валидация
- Пайплайн падает при обнаружении блокирующих операций.
- Drift detection возвращает пустой diff.
- Все изменения покрыты тестами.

---

### Сценарий 6: Обработка ошибок и повторные попытки

#### Пошаговая инструкция
1. **Идемпотентные миграции:** Автоматически повторяйте запуск при `lock_timeout` или `deadlock`.
2. **Пакетная обработка:** Для DML-операций используйте батчи с контрольными точками.
3. **Failure Isolation:** Одна неудавшаяся миграция не должна блокировать очередь.

```sql
-- Пример: пакетное заполнение с контрольными точками
DO $$
DECLARE
    row_count INT;
    batch_size INT := 5000;
BEGIN
    LOOP
        UPDATE users 
        SET full_name = first_name || ' ' || last_name
        WHERE id IN (
            SELECT id FROM users 
            WHERE full_name IS NULL 
            ORDER BY id
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED
        );
        
        GET DIAGNOSTICS row_count = ROW_COUNT;
        EXIT WHEN row_count = 0;
        
        COMMIT;
        PERFORM pg_sleep(0.05);
    END LOOP;
END $$;
```

#### Валидация
- `SELECT COUNT(*) FROM users WHERE full_name IS NULL;` должен вернуть 0.
- Контроль `pg_stat_replication` на предмет роста лага.

## Устранение неисправностей

- **Ошибка `Checksum mismatch`:** Файл миграции был изменен после применения. **Решение:** Верните исходный текст файла или выполните `flyway repair` (только для Dev/Test).
- **Lock Timeout:** Миграция не может получить блокировку. **Решение:** Найдите блокирующий процесс через `pg_stat_activity` / `SHOW PROCESSLIST` и завершите его или повторите запуск в окно минимальной нагрузки.
- **Дрейф схемы:** Схема в Production отличается от Git. **Решение:** Используйте drift detection в CI/CD перед деплоем.
- **Потеря данных при откате:** Фаза Contract выполнена (старая колонка удалена), а приложение откатили к версии N. **Решение:** Используйте Fix-Forward (новая миграция) вместо отката.
- **Раздувание таблицы (Bloat):** Слишком частые апдейты без пауз. **Решение:** Увеличить паузу между батчами и проверить настройки автовакуума.
- **Replication Lag:** Рост лага во время миграции. **Решение:** Уменьшите размер батчей, проверьте нагрузку на master.
- **Очередь блокировок:** `lock_timeout` сработал. **Решение:** Завершите блокирующий сеанс через `pg_terminate_backend(pid)` или `KILL` в MySQL. Повторите запуск в период минимальной нагрузки.

## Лучшие практики

### Именование и версионирование
- **Таймстампы:** Предпочитайте формат `YYYYMMDDHHMMSS` простым порядковым номерам. Таймстампы исключают коллизии при параллельной разработке.
- **Семантика:** Название должно отражать суть изменения (`add_email_to_users`), а не только номер версии.
- **Один файл — одно изменение:** Не объединяйте несколько несвязанных DDL-операций в один файл. Это усложняет откат и аудит.

### Транзакции и идемпотентность
- **Используйте `IF NOT EXISTS`:** Для создания объектов, допускающих повторный запуск.
    ```sql
    ALTER TABLE users ADD COLUMN IF NOT EXISTS email VARCHAR(255);
    CREATE INDEX IF NOT EXISTS idx_users_email ON users(email);
    ```
- **Оборачивайте сложную логику в DO-блок (PostgreSQL):** Для проверок с условной логикой.
- **Тестируйте повторный запуск:** Убедитесь, что миграция не падает при повторном выполнении.

### Безопасность и изоляция
- **Изоляция прав:** CI-пользователь не должен иметь прав `OWNER` на всю базу. Используйте минимально необходимые привилегии для DDL.
- **Отдельные учетные записи:** Пользователь для CI не должен совпадать с пользователем для Production.
- **Аудит:** Включайте `application_name` в соединениях для идентификации миграционных сессий в логах.

### Мониторинг и наблюдаемость
- **Baseline метрики:** Перед миграцией сохраните baseline (CPU, IOPS, лаг, соединения). Отклонение > 20% — останов деплоя.
- **SRE Golden Signals:** Мониторьте Ошибки, Длительность, Насыщенность, Блокировки.
- **Алертинг:** Настройте алерты на `lock_timeout`, `replication_lag > 30s`, `idle in transaction > 30s`.

### Обработка ошибок
- **Fix-Forward вместо отката:** Вместо отката создайте новую компенсирующую миграцию.
- **Retry Policy:** Для идемпотентных миграций используйте автоматические повторные попытки с экспоненциальной задержкой.
- **Failure Isolation:** Одна неудавшаяся миграция не должна блокировать очередь.

### Очистка (Cleanup)
- **Временные объекты:** Удалите временные таблицы, триггеры синхронизации после завершения миграции.
- **Индексы:** Проверьте, что все `CREATE INDEX CONCURRENTLY` завершились успешно (нет `INVALID` индексов).
- **Статистика:** Выполните `ANALYZE` для обновленных таблиц.
- **Автовакуум:** Проверьте, что autovacuum восстановил нормальный режим работы после массовых DML.
- **Бэкапы:** Удалите временные бэкапы, созданные для отката.

## Дополнительная информация

### Рекомендации

- **DBA Review:** Все миграции, затрагивающие таблицы размером > 10 ГБ или содержащие `DROP/RENAME`, требуют ручного ревью Senior инженером.
- **Изоляция прав:** CI-пользователь не должен иметь прав `OWNER` на всю базу. Используйте минимально необходимые привилегии для DDL.
- **Версионирование в коде:** Используйте инструменты типа `Atlas` для декларативного описания схемы, если проект предполагает частые и сложные изменения.
- **Quality Gates:** Интегрируйте линтинг и drift detection в CI/CD. Блокируйте деплой при обнаружении опасных паттернов.
- **Change Management:** Для критичных миграций используйте CAB, Maintenance Window и Runbook.
- **SRE/SLI:** Оцените влияние миграции на SLO. Для критичных сервисов используйте canary-подход: применяйте миграцию к подмножеству реплик, затем к 5% master-трафика.
