# Безопасные массовые операции с данными

## Определения

**Массовые операции с данными** — это запросы `UPDATE` (обновление) или `DELETE` (удаление), затрагивающие значительный объем строк (от десятков тысяч до миллиардов) в рамках одной или нескольких транзакций. Их выполнение требует особого подхода для исключения деградации производительности и нарушения доступности СУБД (Системы Управления Базами Данных).

Перед выполнением любых массовых операций необходимо создать **[резервную копию](./backups.md)** данных.

## Основные концепции

Прямое выполнение массовых операций в одной транзакции создает пиковую нагрузку на ресурсы и может привести к каскадным сбоям.

### Основные риски

- **Длительные блокировки:** захват эксклюзивных блокировок на строки или таблицы препятствует работе других транзакций.
- **Раздувание журналов:** массовая запись в **WAL (Write-Ahead Log)** или **Binlog** может привести к переполнению диска и критическому лагу репликации.
- **Нагрузка на I/O (Input/Output):** интенсивная перезапись данных и обновление индексов создают очередь на дисковой подсистеме.
- **Обслуживание индексов:** каждая измененная строка требует обновления всех связанных индексов, что замедляет операцию в разы.
- **Очистка MVCC (Multi-Version Concurrency Control):** в PostgreSQL массовые операции порождают большое количество «мертвых» строк (dead tuples), что приводит к раздуванию (bloat) таблиц.

### Влияние ограничений и триггеров

- **Foreign Keys (Внешние ключи):** проверка ссылочной целостности для каждой строки создает дополнительную нагрузку на чтение связанных таблиц.
- **Triggers (Триггеры):** выполнение логики триггеров на каждой строке может замедлить операцию на порядки и вызвать побочные эффекты.

## Практические сценарии

### 1. Порционное выполнение (Batching)

Разделение одной крупной операции на множество мелких транзакций (батчей).

- **Суть:** обработка по 1000–5000 строк за итерацию.
- **Реализация:** использование циклов в приложении или хранимых процедурах с обязательным `COMMIT` после каждого пакета.
- **Троттлинг (Throttling):** добавление пауз (`sleep`) между батчами для снижения нагрузки на диск и предоставления времени процессам очистки (например, Autovacuum).

```sql
-- Пример порционного удаления для PostgreSQL с использованием ctid
DO $$
DECLARE
    rows_affected BIGINT;
BEGIN
    LOOP
        DELETE FROM your_table
        WHERE ctid IN (
            SELECT ctid FROM your_table
            WHERE status = 'obsolete'
            LIMIT 5000
        );
        
        GET DIAGNOSTICS rows_affected = ROW_COUNT;
        EXIT WHEN rows_affected = 0;

        COMMIT;
        PERFORM pg_sleep(0.5); -- Пауза для снижения нагрузки
    END LOOP;
END $$;
```

### 2. Пересоздание таблицы (Swap Table)

Метод эффективен при необходимости модификации более 30–50% данных в таблице.

- **Шаги:**
    1. Создание новой таблицы со структурой оригинала: `CREATE TABLE new_table (LIKE old_table INCLUDING ALL)`.
    2. Вставка нужных данных: `INSERT INTO new_table SELECT * FROM old_table WHERE <условие>`.
    3. Создание индексов и ограничений на новой таблице (лучше делать *после* вставки данных для ускорения).
    4. Атомарное переименование: `BEGIN; ALTER TABLE old_table RENAME TO old_table_backup; ALTER TABLE new_table RENAME TO old_table; COMMIT;`.
    5. Удаление старой таблицы после проверки.

### 3. Использование специализированных инструментов

Для минимизации влияния на production-окружение рекомендуется использовать проверенные утилиты:
- **pt-archiver (Percona Toolkit):** для безопасного удаления или архивации строк в MySQL.
- **gh-ost** или **pt-online-schema-change:** если массовое изменение данных требует изменения структуры таблицы.

## Дополнительная информация

### Мониторинг и обслуживание

Во время и после проведения операций необходимо контролировать:
- **Replication Lag:** задержка репликации не должна расти бесконтрольно.
- **Disk Space:** свободное место для журналов (WAL/Binlog).
- **Bloat (Раздувание):** после завершения в PostgreSQL часто требуется запуск `ANALYZE` и, в некоторых случаях, `VACUUM`.

### Постобработка

Обязательно выполните обновление статистики после массовых изменений, чтобы оптимизатор запросов строил корректные планы:
- PostgreSQL: `ANALYZE table_name;`
- MySQL: `OPTIMIZE TABLE table_name;` (учитывайте блокировки) или `ANALYZE TABLE table_name;`
