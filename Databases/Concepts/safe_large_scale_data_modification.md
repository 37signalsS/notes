# Безопасные массовые операции с данными

## Определения

**Массовые операции с данными** — это запросы `UPDATE` (обновление) или `DELETE` (удаление), затрагивающие значительный объем строк (от десятков тысяч до миллиардов) в рамках одной или нескольких транзакций. Их выполнение требует особого подхода для исключения деградации производительности и нарушения доступности СУБД (Системы Управления Базами Данных).

Перед выполнением любых массовых операций необходимо создать **[резервную копию](./backups.md)** данных.

## Основные концепции

Прямое выполнение массовых операций в одной транзакции создает пиковую нагрузку на ресурсы и может привести к каскадным сбоям.

### Основные риски

- **Длительные блокировки:** захват эксклюзивных блокировок на строки (`RowExclusiveLock`) или страницы препятствует работе других транзакций. В MySQL (InnoDB) при отсутствии подходящего индекса запрос может заблокировать всю таблицу через `Next-Key Locks`.
- **Раздувание журналов:** массовая запись в **[WAL](./write_ahead_log.md)** или **Binlog** может привести к переполнению диска, превышению квот в облаке и критическому лагу репликации.
- **Деградация индексов:** массовые `UPDATE/DELETE` вызывают фрагментацию B-Tree индексов. Каждая измененная строка требует обновления всех индексов, что увеличивает количество случайных операций ввода-вывода (Random I/O).
- **Очистка MVCC:** в PostgreSQL массовые операции порождают большое количество "мертвых" строк (dead tuples). Если скорость их появления выше скорости работы `autovacuum`, наступает раздувание (bloat) таблиц и индексов, что замедляет все последующие запросы.

### Стратегии работы с индексами и триггерами

При модификации более 10–20% таблицы стандартные механизмы становятся узким местом:

- **Отключение индексов:** в ряде СУБД (например, SQL Server или Oracle) индексы можно перевести в состояние `UNUSABLE` или `DISABLED`, а после загрузки пересоздать их целиком (Sequential I/O). В PostgreSQL и MySQL рекомендуется удалять вторичные индексы и создавать их заново после завершения операции.
- **Невидимые индексы (Invisible Indexes):** в MySQL/Oracle можно сделать индекс невидимым для оптимизатора, чтобы снизить нагрузку на планирование, но он все равно будет обновляться при записи.
- **Отключение триггеров:** если бизнес-логика позволяет, триггеры и Foreign Keys временно отключаются (`SET session_replication_role = 'replica'` в Postgres) для радикального ускорения вставки/обновления.

## Практические сценарии

### 1. Порционное выполнение (Batching)

Разделение одной крупной операции на множество мелких транзакций (батчей).

- **Throttling (Дросселирование):** паузы (`sleep`) между батчами позволяют процессам очистки успевать за изменениями и предотвращают критический лаг репликации.

#### Пример для MySQL (удаление по первичному ключу)
```sql
-- Удаление порциями по 5000 строк с паузой
SET @rows = 1;
WHILE @rows > 0 DO
    DELETE FROM your_table 
    WHERE status = 'obsolete' 
    LIMIT 5000;
    
    SET @rows = ROW_COUNT();
    DO SLEEP(0.1); -- Даем репликам "догнать" мастера
END WHILE;
```

#### Пример для PostgreSQL (с использованием ctid)
```sql
-- Пример порционного удаления для PostgreSQL с использованием ctid
DO $$
DECLARE
    rows_affected BIGINT;
BEGIN
    LOOP
        DELETE FROM your_table
        WHERE ctid IN (
            SELECT ctid FROM your_table
            WHERE status = 'obsolete'
            LIMIT 5000
        );
        
        GET DIAGNOSTICS rows_affected = ROW_COUNT;
        EXIT WHEN rows_affected = 0;

        COMMIT;
        PERFORM pg_sleep(0.5); -- Пауза для снижения нагрузки на I/O
    END LOOP;
END $$;
```

### 2. Пересоздание таблицы (Swap Table / Shadow Table)

Метод эффективен при необходимости модификации более 30–50% данных в таблице.

- **Шаги:**
    1. Создание новой таблицы со структурой оригинала: `CREATE TABLE new_table (LIKE old_table INCLUDING ALL)`.
    2. Вставка нужных данных: `INSERT INTO new_table SELECT * FROM old_table WHERE <условие>`.
    3. Создание индексов и ограничений на новой таблице (лучше делать *после* вставки данных для ускорения).
    4. Атомарное переименование: `BEGIN; ALTER TABLE old_table RENAME TO old_table_backup; ALTER TABLE new_table RENAME TO old_table; COMMIT;`.
    5. Удаление старой таблицы после проверки.

### 3. Использование специализированных инструментов

Для минимизации влияния на production-окружение рекомендуется использовать проверенные утилиты:
- **pt-archiver (Percona Toolkit):** золотой стандарт для безопасного удаления или архивации строк в MySQL.
- **gh-ost** или **pt-online-schema-change:** если массовое изменение данных требует изменения структуры таблицы (Online Schema Change).

## Дополнительная информация

### Мониторинг и SRE-метрики

При проведении массовых операций необходимо отслеживать:

1.  **Replication Lag (seconds):** если лаг растет — увеличивайте паузу между батчами или уменьшайте размер батча.
2.  **WAL/Binlog Generation Rate (bytes/sec):** скорость записи логов не должна приводить к переполнению диска.
3.  **Active Sessions / Lock Wait:** количество процессов, ожидающих блокировки от вашего сервисного запроса.
4.  **Autovacuum/Purge Workers Activity:** активны ли процессы очистки и справляются ли они с объемом "мусора".
5.  **Disk I/O Latency:** деградация времени отклика диска может аффектить все запросы в СУБД.

### Постобработка

Обязательно выполните обновление статистики после массовых изменений, чтобы оптимизатор запросов строил корректные планы:
- PostgreSQL: `ANALYZE table_name;`
- MySQL: `ANALYZE TABLE table_name;` (обновляет индексы). При сильном раздувании может потребоваться `OPTIMIZE TABLE`, но учитывайте, что это блокирующая операция.
