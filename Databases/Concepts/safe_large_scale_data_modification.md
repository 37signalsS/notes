# Безопасные массовые операции с данными

**Актуально для:** PostgreSQL 18/17/16, MySQL 8.4 LTS/8.0, MariaDB 11.x, Percona Toolkit 3.x, gh-ost 1.x, Linux 6.x

## Определения

**Массовые операции с данными** — это запросы `UPDATE` (обновление) или `DELETE` (удаление), затрагивающие значительный объем строк (от десятков тысяч до миллиардов) в рамках одной или нескольких транзакций. Их выполнение требует особого подхода для исключения деградации производительности и нарушения доступности СУБД (Системы Управления Базами Данных).

Перед выполнением любых массовых операций необходимо создать **[резервную копию](./backups.md)** данных.

## Основные концепции

Прямое выполнение массовых операций в одной транзакции создает пиковую нагрузку на ресурсы и может привести к каскадным сбоям.

### Основные риски

- **Длительные блокировки:** захват эксклюзивных блокировок на строки (`RowExclusiveLock`) или страницы препятствует работе других транзакций. В MySQL (InnoDB) при отсутствии подходящего индекса запрос может заблокировать всю таблицу через `Next-Key Locks`.
- **Раздувание журналов и Write Amplification:** 
    - Массовая запись в **[WAL](./write_ahead_log.md)** (PostgreSQL) или **Binlog** (MySQL) может привести к переполнению диска и критическому лагу репликации.
    - **Write Amplification:** Каждое обновление строки требует обновления всех связанных индексов. Если в таблице 10 индексов, один `UPDATE` порождает 11 записей на диске.
- **Очистка MVCC и Bloat:**
    - В PostgreSQL массовые операции порождают "мертвые" строки (dead tuples). Если скорость их появления выше скорости работы `autovacuum`, наступает раздувание (bloat), что замедляет `Sequential Scan` и увеличивает размер бэкапов.
    - **HOT (Heap-Only Tuple):** Если обновляемые поля не входят в индексы и на странице данных есть свободное место, Postgres может выполнить HOT-обновление, не затрагивая индексы, что радикально снижает нагрузку на I/O.

### Стратегии работы с индексами и параметрами хранения

При модификации более 10–20% таблицы стандартные механизмы становятся узким местом:

- **Управление Fillfactor (PostgreSQL):** Снижение `fillfactor` (например, до 70-80) для таблицы оставляет свободное место на каждой странице данных. Это повышает вероятность выполнения **HOT-updates** при массовых изменениях, исключая необходимость обновления индексов.
- **Отключение индексов:** В ряде СУБД (например, SQL Server или Oracle) индексы можно перевести в состояние `UNUSABLE` или `DISABLED`, а после загрузки пересоздать их целиком (Sequential I/O). В PostgreSQL и MySQL рекомендуется удалять вторичные индексы и создавать их заново (CREATE INDEX CONCURRENTLY) после завершения операции.
- **Невидимые индексы (Invisible Indexes):** В MySQL/Oracle можно сделать индекс невидимым для оптимизатора, чтобы снизить нагрузку на планирование, но он все равно будет обновляться при записи.
- **Отключение триггеров:** Если бизнес-логика позволяет, триггеры и Foreign Keys временно отключаются (`SET session_replication_role = 'replica'` в Postgres) для радикального ускорения процессов.

## Архитектура и жизненный цикл операции

Массовая модификация данных проходит через несколько фаз, каждая из которых создает нагрузку на разные подсистемы СУБД:

1.  **Планирование (Planning):** Построение плана запроса. При отсутствии подходящего индекса СУБД может выбрать Sequential Scan, что приводит к полному сканированию таблицы и захвату всех строк под блокировки.
2.  **Выполнение (Execution):** Чтение строк, применение изменений, запись в WAL/Binlog. На этой фазе пиковая нагрузка на I/O и CPU.
3.  **Фиксация (Commit):** Запись WAL на диск (`fsync`), снятие блокировок. При больших транзакциях это может занять секунды, блокируя другие операции.
4.  **Очистка (Cleanup):** `autovacuum` удаляет мертвые строки. Если операция массовая, autovacuum не успевает, и наступает bloat.

**Почему батчинг работает:** Разделение операции на батчи фиксирует изменения частями, что позволяет:
- Снимать блокировки после каждого батча, уменьшая окно конфликтов.
- Позволить `autovacuum` обработать мертвые строки между батчами.
- Контролировать генерацию WAL, не переполняя диск и не сбрасывая кэш репликации.

## Практические сценарии

### 1. Порционное выполнение (Batching)

Разделение одной крупной операции на множество мелких транзакций (батчей).

- **Адаптивное дросселирование (Throttling):** Вместо фиксированного времени ожидания, SRE-практика предполагает проверку состояния системы (например, **Replication Lag**) перед запуском следующего батча. Это позволяет выполнять операцию максимально быстро, когда система свободна, и замедляться в моменты пиковой нагрузки.

#### Пример для MySQL (удаление порциями с проверкой лага)
```sql
-- Псевдокод логики с адаптивным ожиданием
SET @rows = 1;
WHILE @rows > 0 DO
    -- 1. Удаление батча
    DELETE FROM your_table 
    WHERE status = 'obsolete' 
    LIMIT 5000;
    
    SET @rows = ROW_COUNT();
    
    -- 2. Адаптивная пауза: ждем, пока лаг репликации не снизится
    -- В реальности реализуется внешним скриптом (Python/Go) или хранимой процедурой, 
    -- опрашивающей Seconds_Behind_Master.
    DO SLEEP(0.1); 
END WHILE;
```

#### Пример для PostgreSQL (интенсивное удаление по PK)
Использование `ctid` (физический адрес строки) эффективно для разовых операций, но для повторяющихся процессов лучше использовать первичный ключ (PK).

```sql
DO $$
DECLARE
    batch_size INT := 5000;
    rows_deleted INT;
BEGIN
    LOOP
        -- Удаление по индексу первичного ключа
        DELETE FROM your_table
        WHERE id IN (
            SELECT id FROM your_table
            WHERE status = 'obsolete'
            LIMIT batch_size
            FOR UPDATE SKIP LOCKED -- Пропускаем уже заблокированные строки
        );
        
        GET DIAGNOSTICS rows_deleted = ROW_COUNT;
        EXIT WHEN rows_deleted = 0;

        COMMIT; -- Фиксация батча для освобождения блокировок и WAL
        
        -- SRE-заметка: мониторинг pg_stat_replication
        PERFORM pg_sleep(0.5); 
    END LOOP;
END $$;
```

### 2. Пересоздание таблицы (Swap Table / Shadow Table)

Метод эффективен при необходимости модификации более 30–50% данных в таблице.

- **Шаги:**
    1. Создание новой таблицы со структурой оригинала: `CREATE TABLE new_table (LIKE old_table INCLUDING ALL)`.
    2. Вставка нужных данных: `INSERT INTO new_table SELECT * FROM old_table WHERE <условие>`.
    3. Создание индексов и ограничений на новой таблице (лучше делать *после* вставки данных для ускорения).
    4. Атомарное переименование: `BEGIN; ALTER TABLE old_table RENAME TO old_table_backup; ALTER TABLE new_table RENAME TO old_table; COMMIT;`.
    5. Удаление старой таблицы после проверки.

### 3. Использование специализированных инструментов

Для минимизации влияния на production-окружение рекомендуется использовать проверенные утилиты:
- **pt-archiver (Percona Toolkit):** Золотой стандарт для безопасного удаления или архивации строк в MySQL. Позволяет переносить данные во внешние файлы или другие таблицы маленькими чанками с автоматическим контролем лага репликации.
- **gh-ost:** Инструмент для Online Schema Change в MySQL. В отличие от аналогов на триггерах, gh-ost читает **Binary Log**, что существенно снижает нагрузку на мастер-сервер и предотвращает блокировки при массовых изменениях.

## Pre-flight проверки

Перед запуском массовой операции выполните проверки, чтобы минимизировать риск сбоев:

1.  **Резервное копирование:** Создайте полную резервную копию таблицы или базы (см. **[Резервное копирование](./backups.md)**). Для очень больших таблиц достаточно бэкапа за определенный временной срез (PITR).
2.  **Проверка индексов:** Убедитесь, что условие отбора (`WHERE`) покрыто индексом. Отсутствие индекса приводит к Sequential Scan и блокировке всей таблицы.
3.  **Оценка объема:** `SELECT count(*) FROM your_table WHERE <условие>` — определите точное количество строк для расчета длительности операции.
4.  **Проверка репликации:** Убедитесь, что реплика не отстает (`Seconds_Behind_Master = 0` в MySQL, `pg_stat_replication` в PostgreSQL).
5.  **Настройка параметров сессии:**
    - PostgreSQL: `SET LOCAL lock_timeout = '5s'; SET LOCAL statement_timeout = '30s';`
    - MySQL: `SET SESSION innodb_lock_wait_timeout = 5;`
6.  **Тестовый запуск:** Выполните операцию на копии production в staging-окружении с реальными объемами данных.

## Восстановление после сбоев (Recovery)

### Откат батча

Если батч застрял или вызвал деградацию:

- **PostgreSQL:** Откройте новую сессию и выполните `ROLLBACK;` для отката текущей транзакции. Если сессия потеряна — проверьте `pg_stat_activity` на предмет `idle in transaction` и завершите сессию.
- **MySQL:** Отправьте `KILL <thread_id>` для соединения, выполняющего долгий запрос. InnoDB откатит незавершенную транзакцию.

### Восстановление после прерывания Swap Table

Если операция Swap Table была прервана после создания `new_table` но до переименования:

1.  Удалите незавершенную `new_table`: `DROP TABLE new_table;`
2.  Удалите бэкап: `DROP TABLE old_table_backup;` (после проверки, что `old_table` доступна и корректна).

### Проверка консистентности после массовой операции

- **PostgreSQL:** `SELECT count(*) FROM your_table;` + `SELECT count(*) FROM your_table_backup;` — суммы должны совпадать.
- **MySQL:** `CHECKSUM TABLE your_table;` до и после операции.

## Дополнительная информация

### Тюнинг Autovacuum при массовых операциях (PostgreSQL)

Если планируется масштабное обновление данных, стандартные настройки `autovacuum` могут не справляться. Рекомендуется временно изменить параметры для целевой таблицы:

```sql
ALTER TABLE your_table SET (
  autovacuum_vacuum_scale_factor = 0.01,  -- Запускать очистку при 1% мертвых строк
  autovacuum_vacuum_cost_limit = 1000,    -- Разрешить процессу потреблять больше ресурсов
  autovacuum_vacuum_cost_delay = 10       -- Уменьшить задержку между циклами
);
```

### Мониторинг и SRE-метрики

При проведении массовых операций необходимо отслеживать:

1.  **Replication Lag (seconds):** Если лаг растет — увеличивайте паузу между батчами.
2.  **WAL/Binlog Generation Rate (bytes/sec):** Пиковая скорость генерации логов может забить канал репликации или переполнить диск.
3.  **Bloat Ratio:** Процент "мусора" в таблице (используйте `pgstattuple` для Postgres).
4.  **CPU / IOPS Throttling:** Массовые операции могут исчерпывать лимиты ввода-вывода и загрузку CPU, что сказывается на всех запросах в СУБД.
5.  **Disk I/O Latency:** Деградация времени отклика диска может аффектить все запросы в СУБД.

### Постобработка

Обязательно выполните обновление статистики после массовых изменений, чтобы оптимизатор запросов строил корректные планы:
- PostgreSQL: `ANALYZE table_name;`
- MySQL: `ANALYZE TABLE table_name;` (обновляет индексы). При сильном раздувании может потребоваться `OPTIMIZE TABLE`, но учитывайте, что это блокирующая операция.

## Ключевые метрики и пороги (SLO)

| Метрика | Пресет (SLO) | Диагностика |
| :--- | :--- | :--- |
| **Batch Duration** | P95 < 30 сек | Время выполнения одного батча. Рост означает недостаточное количество ресурсов или отсутствие индекса. |
| **Replication Lag** | < 5 сек | `Seconds_Behind_Master` (MySQL) или `pg_stat_replication` (PostgreSQL). При превышении — увеличивайте паузу между батчами. |
| **Prepared Transactions** | 0 | Зависшие prepared-транзакции в PostgreSQL (`pg_prepared_xacts`) блокируют ресурсы. |
| **Bloat Ratio** | < 20% | Процент мертвых строк (используйте `pgstattuple` в PostgreSQL). |
| **Dead Tuples Growth** | < 100K/мин | Скорость накопления мертвых строк. Если `autovacuum` не успевает — настройте агрессивнее. |
| **WAL/Binlog Lag** | < 1 сек | Размер отставания репликации по логам. |

## Troubleshooting

### Паттерны неисправностей

| Паттерн | Возможная причина | Первый шаг диагностики |
| :--- | :--- | :--- |
| **Зависший батч (idle in transaction)** | Блокировка строки другим процессом | `SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction';` |
| **Рост репликационного лага** | Слишком большой батч или отсутствие индекса | Уменьшите `batch_size`; проверьте `EXPLAIN ANALYZE` запроса |
| **Раздувание таблицы (bloat)** | `autovacuum` не справляется с нагрузкой | Включите агрессивный `autovacuum` (см. раздел ниже) или запустите `VACUUM` вручную |
| **Ошибка `lock_timeout`** | Конфликт с другими транзакциями | Увеличьте `lock_timeout` или используйте `SKIP LOCKED` для пропуска заблокированных строк |
| **Завершение соединения (критерий `statement_timeout`)** | Батч выполняется дольше установленного таймаута | Увеличьте `statement_timeout` для сессии или разбейте батч на меньшие части |

### Operational Runbook: Анализ массовой операции

1.  **Быстрая проверка (5 минут):**
    - `SELECT count(*) FROM pg_stat_activity WHERE state = 'active';` — нет ли зависших транзакций?
    - `SELECT * FROM pg_prepared_xacts;` — нет ли зависших prepared-транзакций?
    - `SHOW SLAVE STATUS` / `pg_stat_replication` — каков текущий лаг репликации?

2.  **Диагностика (30 минут):**
    - `EXPLAIN ANALYZE` на проблемный запрос — есть ли Sequential Scan?
    - `SELECT * FROM pg_locks WHERE granted = false;` — нет ли дедлоков?
    - Проверка `n_dead_tup` в `pg_stat_user_tables` — насколько быстро растет bloat?

3.  **Корректировка (1-2 часа):**
    - Уменьшение `batch_size` и увеличение паузы между батчами.
    - Принудительный `ROLLBACK` зависших транзакций (с подтверждением, что они не активны).
    - Включение агрессивного `autovacuum` для целевой таблицы.

4.  **Валидация:**
    - Запуск тестового батча и проверка репликационного лага.
    - Сравнение `count(*)` до и после операции.
    - Настройка алертов на `replication_lag > 10s` и `prepared_transactions_count > 0`.

## Лучшие практики

1.  **Используйте батчинг по умолчанию:** Даже для таблиц на 1 млн строк выполняйте операции порциями по 5–10K строк. Это снижает риск блокировок и дает СУБД возможность "дышать" между батчами.
2.  **Ограничьте время жизни транзакции:** Длительные транзакции блокируют `VACUUM` и репликацию. Настройте `statement_timeout` и `lock_timeout` на уровне сессии.
3.  **Контролируйте лаг репликации:** Никогда не запускайте следующий батч, пока реплика не догнала мастера. Это предотвращает каскадный рост лага и потерю данных при отказе мастера.
4.  **Используйте `SKIP LOCKED` для параллельной обработки:** В PostgreSQL `FOR UPDATE SKIP LOCKED` позволяет нескольким воркерам обрабатывать разные порции данных одновременно, не блокируя друг друга.
5.  **Отключайте индексы перед загрузкой:** При пересоздании таблицы (Swap Table) создавайте индексы *после* вставки данных. Это ускоряет загрузку в разы.
6.  **Настраивайте `fillfactor` для часто обновляемых таблиц:** Значение 70–80% оставляет место для HOT-updates и уменьшает фрагментацию.
7.  **Мониторинг `pg_stat_progress_vacuum`:** В PostgreSQL 14+ используйте этот view для отслеживания прогресса `VACUUM` во время массовых операций. Это позволяет оценить, успевает ли autovacuum.
8.  **Тестируйте отказы:** Регулярно прерывайте массовую операцию в staging (kill -9, падение сети) и проверяйте, что база остается консистентной.
9.  **Используйте `pg_repack` для устранения bloat:** Если после массовой операции таблица сильно раздулась, `pg_repack` пересоздает таблицу онлайн, без блокировок `ACCESS EXCLUSIVE`.
10. **Документируйте процедуру:** Для каждой массовой операции создайте пошаговый runbook с командами проверки, точками отката и контактами ответственных.

## Особые случаи и ограничения (Edge Cases)

1.  **Одновременная модификация и чтение:** Если приложение читает таблицу во время массового `UPDATE`, могут появиться аномалии (dirty reads в зависимости от уровня изоляции). Используйте snapshot isolation или планируйте операцию в окно низкой нагрузки.
2.  **Очередь удаленных строк (Delete Queue):** В MySQL InnoDB при массовом `DELETE` строки помечаются как удаленные, но физически не удаляются до purge. Это может привести к росту ibdata1. Мониторьте `Innodb_purge_trx_id_age`.
3.  **Влияние на реплики:** На репликах массовые операции выполняются последовательно. Если мастер применяет батчи быстро, а реплика медленная, реплика отстает. Настройте `slave_parallel_workers` в MySQL или `max_parallel_workers_per_gather` в PostgreSQL.
4.  **Ограничение `max_prepared_transactions` (PostgreSQL):** Если в процессе массовой операции используется 2PC, убедитесь, что `max_prepared_transactions > 0` (по умолчанию 0). Рекомендуемое значение: `max_connections * количество_участников`.
5.  **Взаимодействие с триггерами и Foreign Keys:** Временное отключение триггеров (`SET session_replication_role = 'replica'`) ускоряет операцию, но Foreign Keys остаются активными. Полностью отключите проверку внешних ключей только если уверены в консистентности данных.
6.  **Очень большие транзакции (> 10M строк):** Даже батчинг не поможет, если каждая транзакция слишком велика. Рассмотрите пересоздание таблицы (Swap Table) или использование специализированных инструментов (`pt-archiver`, `pg_repack`).
