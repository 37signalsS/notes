# Стратегии резервного копирования баз данных

## Определения

- **Резервное копирование (Backup)** — процесс создания копии данных для их восстановления в случае сбоя, повреждения или потери.
- **RPO (Recovery Point Objective)** — целевая точка восстановления; максимально допустимый объем потери данных, выраженный во времени (например, "не более 15 минут данных").
- **RTO (Recovery Time Objective)** — целевое время восстановления; максимальное допустимое время простоя сервиса до его возврата в рабочее состояние.
- **Окно резервного копирования (Backup Window)** — отведенный период времени, в течение которого выполнение бэкапа минимально влияет на производительность продуктивной системы.
- **Аварийное восстановление (Disaster Recovery, DR)** — комплекс мер и процедур по восстановлению ИТ-инфраструктуры после катастрофических событий.
- **PITR (Point-in-Time Recovery)** — технология восстановления базы данных на произвольный момент времени в прошлом, реализуемая через комбинацию полного бэкапа и журналов транзакций.

## Основные концепции

### Правило "3-2-1-1-0"

Современная эволюция классического правила для обеспечения максимальной надежности:
- **3** копии данных (оригинал + 2 бэкапа).
- **2** разных типа носителей (например, диск и облако).
- **1** копия на удаленной площадке (offsite).
- **1** копия в офлайне или **иммутабельном** хранилище (WORM, S3 Object Lock) для защиты от Ransomware.
- **0** ошибок при автоматической проверке восстановления.

### Репликация — это не бэкап

Важно разделять эти понятия:
- **[Репликация](./replication.md)** обеспечивает **отказоустойчивость** (High Availability). Она защищает от отказа железа, но мгновенно тиражирует логические ошибки (например, `DELETE` без `WHERE`) на все узлы.
- **Бэкап** обеспечивает **сохранность данных** во времени. Это единственный способ откатиться к состоянию "до ошибки пользователя или сбоя приложения".

### Уровни консистентности

1. **Неконсистентный (Dirty):** Копирование файлов на лету. Почти гарантированно приводит к повреждению базы при восстановлении.
2. **Согласованный на уровне диска (Crash-consistent):** Копия эквивалентна состоянию диска после внезапного выключения. СУБД восстановится через механизм **[Crash Recovery](./rollback_strategies.md)**, используя логи. Достигается через снапшоты (LVM, EBS).
3. **Согласованный на уровне приложения (Application-consistent):** Перед бэкапом БД сбрасывает буферы (`fsync`) и приостанавливает запись (quiesce). Гарантирует целостность всех транзакций на момент снимка.

### Валидация: "Бэкап Шрёдингера"

Бэкап считается существующим только в том случае, если процедура восстановления из него успешно протестирована.
- **Автоматическое восстановление:** Регулярный запуск пайплайнов, которые разворачивают базу из бэкапа на тестовом инстансе.
- **Проверка целостности:** Запуск `DBCC CHECKDB` (SQL Server) или `amcheck` (Postgres) на восстановленной копии.
- **Мониторинг свежести:** Оповещения, если самый свежий успешный бэкап старше установленного порога (например, 24 часа).

## Типы резервных копий

| Тип | Что копируется | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **Полный (Full)** | Все данные целиком | Простое восстановление | Долго, большой объем, нагрузка на IO |
| **Инкрементальный** | Изменения с последнего бэкапа | Минимум места, быстро | Долгое восстановление (нужна вся цепочка) |
| **Дифференциальный** | Изменения с последнего *полного* | Быстрее восстановление, чем у инкремента | Объем растет до следующего Full |
| **Synthetic Full** | Сборка Full из Incr на стороне хранилища | Снимает нагрузку с БД, быстрое восстановление | Требует поддержки со стороны ПО (pgBackRest, Veeam) |

## Практические сценарии

### 1. Логический бэкап (SQL Dump)
Данные в виде текста (`INSERT`, `CREATE`).
- **Инструменты:** `pg_dump`, `mysqldump`, `mydumper`.
- **Когда использовать:** Малые БД (< 100 ГБ), миграции между версиями, выгрузка конкретных схем/таблиц.
- **Белое пятно:** Огромные текстовые дампы сложно восстанавливать параллельно. Рекомендуется использовать формат `directory` в `pg_dump` для многопоточности.

### 2. Физический бэкап (Binary)
Копирование бинарных файлов данных.
- **Инструменты:** `pg_basebackup`, `wal-g`, `pgBackRest`, `Percona XtraBackup`.
- **Когда использовать:** Большие нагруженные системы, где RTO критичен. Восстановление физического бэкапа происходит со скоростью дисковой подсистемы.
- **PITR:** Физический бэкап + архивирование **[WAL](./write_ahead_log.md)** позволяет восстановиться на любую секунду.

### 3. Снапшоты и Cloud Native
Снимки на уровне СХД или облачного провайдера.
- **Инструменты:** AWS EBS Snapshots, GCP Snapshots, Azure Backup.
- **Kubernetes:** Использование **[Velero](../ToolsUtilities/velero-overview.md)** для бэкапа томов (`PV`) и метаданных через CSI-драйверы.
- **Преимущество:** Снапшот создается мгновенно (Copy-on-Write), не нагружая CPU сервера БД.

### 4. Retention Policy (Политика хранения)
Автоматизация жизненного цикла бэкапов:
- **G-F-S (Grandfather-Father-Son):** Схема ротации (ежемесячные, еженедельные, ежедневные).
- **Lifecycle в S3:** Автоматический перенос старых бэкапов в дешевые холодные хранилища (Glacier, Cold Archive) и их удаление по истечении срока (например, через 3 года).

## Дополнительная информация

При проектировании стратегии бэкапа всегда исходите из стоимости простоя бизнеса. Если 1 час простоя стоит $10,000, вложения в высокоскоростное восстановление (физические бэкапы + быстрые диски) оправданы.
