# Журнал предзаписи (Write-Ahead Log, WAL)

## Определения

**Журнал предзаписи (Write-Ahead Log, WAL)** — фундаментальный механизм обеспечения отказоустойчивости СУБД. Суть метода заключается в том, что любые изменения данных сначала фиксируются в специальном лог-файле на диске, и только после подтверждения записи в лог они могут быть внесены в основные файлы данных. Это гарантирует свойство **Durability** (долговечность) модели **[ACID](./acid.md)**.

**LSN (Log Sequence Number)** — уникальный возрастающий идентификатор (обычно 64-битный), указывающий на смещение конкретной записи в потоке WAL. LSN критически важен для обеспечения **идемпотентности**: при восстановлении СУБД сравнивает LSN записи в WAL с LSN на странице данных. Если LSN страницы >= LSN записи, значит, изменение уже применится и его нужно пропустить.

**Dirty Page (Грязная страница)** — страница данных в оперативной памяти (Buffer Pool), содержимое которой было изменено, но еще не синхронизировано с основным файлом данных на диске.

**Чекпоинт (Checkpoint)** — процесс синхронизации, при котором измененные данные («грязные страницы») из оперативной памяти принудительно сбрасываются в основные файлы БД, а WAL помечается как выполненный до этой точки.

## Основные концепции

### Зачем нужен WAL

1. **Производительность (Sequential I/O):** Основные файлы БД разбросаны по диску (Random I/O), что медленно для HDD и создает нагрузку на контроллеры SSD. WAL записывается последовательно, что максимально использует пропускную способность дисковой подсистемы.
2. **Надежность (Crash Recovery):** При сбое питания данные в оперативной памяти теряются. После перезапуска СУБД читает WAL с точки последнего чекпоинта и «доигрывает» (Redo) подтвержденные транзакции.
3. **Репликация:** WAL служит источником данных для передачи изменений на реплики. Это эффективнее, чем передача самих страниц данных.

### Типы логирования

СУБД различаются по тому, что именно они записывают в журнал:

1.  **Физическое логирование:** Записываются изменения на уровне байтов (например, "в файле X на смещении Y заменить байты A на B").
    - *Плюс:* Высокая надежность и простота восстановления.
    - *Минус:* Огромный объем логов при незначительных изменениях.
2.  **Логическое логирование:** Записываются SQL-команды (`INSERT`, `UPDATE`).
    - *Плюс:* Минимальный объем данных.
    - *Минус:* Трудно обеспечить консистентность при восстановлении (например, если в запросе был `NOW()`).
3.  **Физиологическое логирование (Physiological):** Стандарт современных СУБД (PostgreSQL, InnoDB). Записываются изменения внутри конкретной страницы (page), но в логическом формате (например, "вставить строку в слот N страницы M").
    - *Плюс:* Баланс между объемом данных и надежностью. Обеспечивает физическую целостность страниц.

### Ключевые механизмы

- **Group Commit:** Оптимизация, объединяющая несколько транзакций для записи на диск одним вызовом `fsync`. Это снижает количество операций ввода-вывода (IOPS).
- **Защита от повреждения страниц (Torn Page Protection):**
    - **Full Page Writes (PostgreSQL):** Первая запись страницы после чекпоинта копируется в WAL целиком. Если запись страницы данных прервется сбоем, её можно восстановить из WAL.
    - **Write Amplification:** Использование Full Page Writes приводит к значительному увеличению объема записи (**Write Amplification**), особенно при частых чекпоинтах или малом размере страниц.
    - **Doublewrite Buffer (MySQL/InnoDB):** Страницы сначала пишутся в непрерывную область диска (doublewrite buffer), а затем в основные файлы.
- **Логическое декодирование (Logical Decoding):** Процесс извлечения изменений данных из WAL в независимом от СУБД формате. Используется для **[CDC (Change Data Capture)](../../Concepts/Caching/caching_patterns.md#архитектура-инвалидации-через-cdc-debezium--kafka)**.
- **Fsync vs Fdatasync:** 
    - `fsync()` гарантирует физический сброс данных и метаданных файла (размер, время доступа) на диск.
    - `fdatasync()` сбрасывает только данные, что может быть быстрее, если метаданные не критичны для целостности (часто используется в etcd).

## Практические сценарии

### Жизненный цикл транзакции

1. **Изменение:** Пользователь выполняет `UPDATE`. СУБД меняет страницу в `Buffer Pool` (RAM) и помечает её как грязную.
2. **Генерация WAL:** В буфер WAL записывается информация об изменении с новым LSN.
3. **Фиксация (Commit):** При выполнении `COMMIT` записи из буфера WAL сбрасываются на диск (`fsync`). Пользователь получает подтверждение только после этого.
4. **Фоновая запись:** Процессы (например, Background Writer в PostgreSQL) постепенно переносят изменения из RAM в файлы данных.
5. **Контрольная точка:** СУБД фиксирует успешный сброс всех данных до определенного LSN. Старые сегменты WAL могут быть удалены или заархивированы.

### Восстановление после сбоя (Алгоритм ARIES)

Большинство современных СУБД используют элементы алгоритма **ARIES** (Algorithm for Recovery and Isolation Exploiting Semantics):

1. **Анализ (Analysis):** Определение точки последнего чекпоинта, выявление "грязных" страниц и активных транзакций на момент сбоя.
2. **Повтор (Redo):** Воспроизведение всех операций из WAL с момента чекпоинта (**History repeating**). Восстанавливается состояние Buffer Pool на момент сбоя, включая незавершенные транзакции.
3. **Откат (Undo):** Отмена операций всех транзакций, которые не были зафиксированы (`COMMIT`) до момента сбоя.
    - **CLR (Compensation Log Records):** Во время отката СУБД записывает в WAL специальные записи CLR. Если система снова упадет во время восстановления, CLR помогут не откатывать уже откатанные изменения повторно, делая процесс восстановления предсказуемым.

## Особенности реализаций

- **PostgreSQL:** Использует сегменты по 16 Мб. Параметр `wal_level` определяет объем информации в логах (minimal, replica, logical). Архивы WAL критически важны для **PITR (Point-In-Time Recovery)**.
- **MySQL (InnoDB):** Использует **Redo Log** (физиологический уровень) для надежности и **Binlog** (логический уровень) для репликации. В MySQL 8.0.30+ введен параметр `innodb_redo_log_capacity`, заменяющий старые настройки размера файлов (`innodb_log_file_size`, `innodb_log_files_in_group`).
- **MariaDB (InnoDB):** Тот же механизм, но `innodb_redo_log_capacity` **не существует**. Лог круговой, единственный файл `ib_logfile0`; его размер задаёт `innodb_log_file_size` (по умолчанию 96 МБ, динамический с MariaDB 10.9), а параметр `innodb_log_files_in_group` отсутствует. Подробности — в [InnoDB: долговечность и настройка записи](../MariaDB/innodb_durability_tuning.md).

### InnoDB: применение redo и идемпотентность

InnoDB реализует physiological logging: в redo пишутся изменения **внутри конкретной страницы**, а не байтовые диапазоны. Каждая заredo-содержимое страницы несёт LSN, и каждая страница данных хранит LSN последнего применённого к ней изменения. При восстановлении InnoDB применяет запись только если LSN записи больше LSN страницы, поэтому повторное применение одной и той же записи невозможно — это и есть механизм идемпотентности, описанный в разделе «Определения».

Отсюда следуют два практических следствия, специфичных для InnoDB:

- **Объём redo определяется объёмом изменений в страницах, а не логической величиной изменений.** Массовый `UPDATE` без индекса по индексу переписывает множество страниц целиком и генерирует redo непропорционально объёму данных. Это источник быстрого роста `ib_logfile0` и учащённых чекпоинтов.
- **Checkpoint age ограничен самой старой активной транзакцией.** Долгая транзакция удерживает LSN, до которого purge и сброс страниц не могут продвинуться, поэтому лог заполняется и page flushing начинает отставать. Это аналог проблемы bloat в PostgreSQL, но проявляется через чекпоинты InnoDB, а не через vacuum.

В отличие от PostgreSQL, где целостность страниц при частичной записи обеспечивается Full Page Writes, InnoDB использует doublewrite buffer, а начиная с MariaDB 10.8.3 кэш файловой системы для redo log по умолчанию отключён, чтобы запись шла в обход кэша ОС.
- **etcd (Raft):** В распределенных системах WAL используется для фиксации предложений (proposals) в протоколе Raft перед их применением к конечному автомату (State Machine).
- **Oracle:** Механизм называется **Redo Log**.

## Практическая эксплуатация и Troubleshooting

### Проблема WAL Bloat (Раздувание журналов)

Ситуация, когда СУБД не может удалить старые сегменты WAL, что приводит к переполнению диска. 
**Основные причины:**
1. **Зависшие Replication Slots (PostgreSQL):** Если реплика отключилась, но слот остался активным, Master будет хранить все WAL с момента отключения, чтобы реплика могла "догнать" его позже.
2. **Долгие транзакции (`idle in transaction`):** Чекпоинт не может быть полностью завершен дальше LSN начала самой старой активной транзакции.
3. **Сбой `archive_command`:** Если WAL не удается отправить в архив (например, локальное хранилище или NFS-сервер недоступен), база будет копить сегменты локально до исчерпания места.

### Зависшие репликационные слоты (PostgreSQL)

**Симптомы:** Диск на мастере заполняется, `pg_wal` растет, несмотря на наличие резервных копий. В `pg_stat_replication` видно отключенную реплику, но слот остался.

**Причины:** Реплика была отключена, но `pg_replication_slots` не был удален. PostgreSQL сохраняет все WAL-сегменты с момента отключения, чтобы реплика могла "догнать" состояние.

**Решение:**
1. Проверьте активные слоты: `SELECT * FROM pg_replication_slots;`
2. Если реплика больше не нужна — удалите слот: `SELECT pg_drop_replication_slot('slot_name');`
3. Для ограничения роста используйте `max_slot_wal_keep_size` (PostgreSQL 13+).

**Профилактика:**
- Настройте мониторинг размера `pg_wal` и количества inactive слотов.
- Используйте `max_slot_wal_keep_size` для ограничения объема хранимого WAL.

### Долгие транзакции и чекпоинты

**Симптомы:** Чекпоинт не завершается, WAL накапливается, время восстановления при сбое растет.

**Причины:** Самая старая активная транзакция (`idle in transaction`) удерживает LSN, до которого чекпоинт не может очистить WAL. Это также мешает vacuum и вызывает bloat.

**Решение:**
1. Найдите зависшие транзакции: `SELECT * FROM pg_stat_activity WHERE state = 'idle in transaction' ORDER BY xact_start;`
2. Завершите их: `SELECT pg_terminate_backend(pid);`
3. Настройте `idle_in_transaction_session_timeout` для автоматического завершения.

### Медленный WAL Replay при восстановлении

**Симптомы:** После сбоя сервер БД долго не выходит в readonly/primary режим, startup process грузит CPU.

**Причины:** Большой объем WAL накапливается между чекпоинтами (`max_wal_size` слишком велик), или дисковая подсистема не справляется с последовательным чтением.

**Решение:**
1. Настройте `max_wal_size` с запасом по времени восстановления (RTO). Например, если WAL генерируется 100 МБ/мин, а диск читает 200 МБ/мин, то `max_wal_size` не должен превышать 2 часа записи.
2. Разместите WAL на выделенном быстром устройстве (NVMe), отдельно от данных.
3. Используйте `restore_command` с локальным кэшем, чтобы не читать WAL с удаленного архива при каждом запуске.

### Ошибки архивации WAL

**Симптомы:** Файлы WAL не появляются в целевом каталоге, `pg_stat_archiver` показывает ошибки.

**Причины:** Неправильные права доступа, нехватка места на диске архива, сбой сетевой файловой системы.

**Решение:**
1. Проверьте статус архиватора: `SELECT * FROM pg_stat_archiver;`
2. Протестируйте `archive_command` вручную: `sudo -u postgres /usr/bin/pg_archivecleanup /var/lib/pgsql/wal_archive %r`
3. Настройте алерт на ошибки архивации. Используйте `archive_retry_interval` для автоматических повторов.

### Инспекция содержимого WAL

Иногда SRE требуется понять, какие именно данные или таблицы генерируют аномальный объем WAL.

**PostgreSQL (pg_waldump):**
```bash
# Просмотр статистики по типам операций в конкретном сегменте
pg_waldump --stats=record 000000010000000000000001

# Поиск записей, относящихся к конкретной таблице (по её relfilenode)
pg_waldump 000000010000000000000001 | grep "rel 16384"
```

**MySQL (mysqlbinlog):**
```bash
# Декодирование бинарного лога для анализа SQL-запросов
mysqlbinlog --base64-output=DECODE-ROWS -v binlog.000001
```

## Настройка и мониторинг (SRE-заметки)

### Параметры производительности

- **`max_wal_size` / `checkpoint_timeout`:** Увеличение этих значений снижает нагрузку на диск за счет более редких чекпоинтов, но увеличивает время восстановления при сбое. Это классический баланс между **RTO** (скорость восстановления) и **Performance** (производительность записи).
- **`wal_compression`:** Сжатие записей Full Page Writes экономит место и IOPS, но потребляет ресурсы CPU. Рекомендуется для High-Load систем с мощными процессорами.
- **Синхронность:** Отключение `synchronous_commit` (PostgreSQL) или установка `innodb_flush_log_at_trx_commit = 2` (MySQL) дает огромный прирост скорости, но допускает потерю данных за последние секунды при крахе ОС.

### Метрики для мониторинга

- **WAL Write Lag:** Время ожидания записи в WAL (показывает проблемы с производительностью диска).
- **WAL Generation Rate:** Объем генерируемого WAL в секунду (помогает планировать емкость диска и сети для репликации).
- **Checkpoint Distance:** Разрыв в байтах между текущим LSN записи и LSN последнего чекпоинта.
- **`etcd_disk_wal_fsync_duration_seconds`:** В etcd это критическая метрика. Задержка > 10 мс обычно приводит к нестабильности кластера.

## Лучшие практики

1. **Размещайте WAL на выделенном устройстве.** Отделите последовательный WAL от случайной записи данных. На NVMe/SDD выделите отдельный раздел или LUN для WAL — это исключает конкуренцию за IOPS и упрощает диагностику.
2. **Настраивайте `archive_command` с ретраями и мониторингом.** Без архивации WAL нет PITR. Используйте `archive_retry_interval` (PostgreSQL) и алерты на ошибки `pg_stat_archiver`. Целевое хранилище — локальный диск или SFTP-сервер с RAID.
3. **Ограничьте размер WAL через `max_wal_size`.** Слишком большой `max_wal_size` увеличивает RTO при сбое. Слишком малый — создает лишнюю нагрузку от частых чекпоинтов. Подбирайте значение исходя из скорости генерации WAL и производительности диска.
4. **Удаляйте неиспользуемые репликационные слоты.** Inactive слоты — частая причина WAL Bloat. Автоматически удаляйте слоты после отключения реплики или используйте `max_slot_wal_keep_size`.
5. **Используйте `hot_standby_feedback` на репликах.** Если на реплике выполняются долгие запросы, включите этот параметр, чтобы мастер не удалял версии строк, нужные реплике. Это предотвращает задержки репликации из-за vacuum на мастере.
6. **Тестируйте восстановление из WAL.** Раз в квартал выполняйте PITR на изолированном сервере: восстановите снапшот + примените WAL-сегменты. Убедитесь, что `archive_command` работает и `restore_command` читает архив корректно.
7. **Мониторьте WAL Generation Rate.** Это ключевая метрика для планирования емкости диска и пропускной способности сети для репликации. Внезатный рост WAL часто указывает на аномальную нагрузку (например, массовое обновление без индекса).
8. **Используйте `wal_log_hints` если нужно.** При использовании `hot_standby_feedback` и REPEATABLE READ на репликах включите этот параметр, чтобы мастер сохранял в WAL достаточно информации для vacuum на репликах.
9. **Не отключайте Full Page Writes без необходимости.** Настройка `full_page_writes = off` экономит место и IOPS, но при сбое питания страница данных может быть восстановлена только из WAL, а не из данных на диске. Используйте только с батарейным RAID-контроллером (BBU).
10. **Разделяйте WAL и данные на разных дисках.** Для high-load систем это обязательно. WAL — последовательная запись, данные — случайная. Разделение позволяет использовать разные профили производительности для каждой нагрузки.

## Особые случаи и ограничения

### WAL на SSD vs HDD

- **SSD/NVMe:** Рекомендуется для production. Последовательная запись WAL полностью использует пропускную способность. Главное ограничение — износ от записи. Современные SSD выдерживают десятки ПБ/записей, но для extremely write-heavy нагрузок мониторьте TBW (Total Bytes Written).
- **HDD:** Приемлемо для development или low-load систем. Убедитесь, что `hdparm -B 255` (отключение энергосбережения) и `noatime` включены. Ожидайте задержку `fsync` 5–15 мс против < 1 мс на NVMe.

### Коррупция WAL

Если WAL-сегмент поврежден (битые сектора, сбой записи), recovery прервется с ошибкой `could not locate a valid checkpoint record`. В этом случае:
1. Не удаляйте поврежденные сегменты сразу — они могут содержать валидные записи.
2. Попробуйте восстановить из последнего известного хорошего сегмента: `pg_rewind` или восстановление из base backup + WAL до повреждения.
3. Для предотвращения используйте RAID с проверкой четности (RAID 6) или ZFS с checksumming.

### WAL и Containers

При запуске PostgreSQL в контейнере (Docker/Kubernetes) WAL должен храниться на persistent volume (PV). Никогда не размещайте `pg_wal` на `emptyDir` — при перезапуске пода данные будут утеряны. В Kubernetes используйте `volumeClaimTemplate` с StorageClass на SSD/NVMe.
