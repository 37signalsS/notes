**Актуально для:** Общая теория репликации (PostgreSQL 16+, MySQL 8.0 / MariaDB 11, MongoDB 8.0, etcd 3.5, 2024–2026)

# Репликация баз данных

## Определения

**Репликация** — процесс создания и поддержания идентичных копий (реплик) данных на нескольких независимых серверах. Фундаментальный механизм обеспечения высокой доступности (High Availability, HA), масштабируемости нагрузки на чтение и катастрофоустойчивости инфраструктуры.

- **Primary (Источник / Мастер):** Узел, принимающий операции записи и передающий изменения на другие узлы кластера.
- **Replica (Реплика / Ведомый):** Узел, воспроизводящий изменения с Primary. В стандартных конфигурациях используется только для чтения.
- **Кворум (Quorum):** Минимальное количество узлов, чье подтверждение необходимо для фиксации транзакции или выбора нового лидера. Рассчитывается как $(N/2) + 1$. Детали см. в **[CAP-теорема](./cap_theorem.md)**.
- **Failover (Переключение при сбое):** Автоматический или ручной процесс передачи функций отказавшего Primary одной из реплик.
- **Promotion (Повышение):** Процедура смены роли узла с Replica на Primary.
- **Switchover:** Плановое переключение ролей между Primary и Replica (например, для обслуживания железа), минимизирующее простой.
- **Delayed Replica (Отложенная репликация):** Реплика, на которую изменения поступают с заданной задержкой (например, 30 минут). Используется как защита от логических ошибок на Primary (`DROP TABLE`, ошибочный `UPDATE`).
- **Replication Slot (Слот репликации):** Механизм на PostgreSQL, гарантирующий, что WAL не будет удален до передачи на реплику. В MySQL аналогом служит гарантия retention binlog для активных реплик.
- **Сток (Replication Lag / Отставание):** Разница во времени или позиции лога между Primary и Replica. Измеряется в секундах (`Seconds_Behind_Source`, `pg_stat_replication`) или байтах/сегментах WAL.

> **Примечание по терминологии:** Традиционные названия **Master** и **Slave** считаются устаревшими. В современной индустрии (Postgres, MySQL 8+, Kubernetes) стандартом являются термины **Primary/Replica** или **Source/Replica**.

В то время как репликация *копирует* данные, другой метод масштабирования, **[шардирование](./sharding.md)**, *разделяет* их по разным серверам.

## Предварительные требования

### Инфраструктура

| Компонент | Требование | Обоснование |
| :--- | :--- | :--- |
| **Сеть** | TCP-связность между всеми узлами. Для PostgreSQL — порт 5432; MySQL — 3306. RTT между ДЦ < 10 мс для синхронной репликации. | Сетевые задержки напрямую влияют на лаг и производительность записи. |
| **Диск** | Отдельные физические устройства для данных, WAL/binlog и бэкапов. NVMe SSD для высоконагруженных инстансов. | Конкуренция за I/O между записью данных и репликацией снижает пропускную способность. |
| **NTP/Chrony** | Расхождение часов < 10 мс между всеми узлами. | Критично для LWW-конфликтов, логической репликации, меток в бинарных логах. |
| **ОС** | Linux 5.4+ (стабильность ABI для `pg_basebackup`/`io_uring`). Лимиты файлов (`ulimit -n` ≥ 65536), `fs.file-max` ≥ 1000000. | Недостаточные лимиты приводят к отказу подключений репликации. |
| **RAM** | Достаточно для Buffer Pool + процессы репликации. На реплике Memory = ~70% от размера рабочего набора данных. | Нехватка RAM вызывает swap, что катастрофически увеличивает лаг репликации. |

### Идентификация и аутентификация

- **PostgreSQL:** Выделенная роль с атрибутом `REPLICATION`. Рекомендуется `scram-sha-256`.
- **MySQL:** Уникальный `server_id` (1-4294967295), `server_uuid` (автогенерируется в `auto.cnf`), пользователь с грантом `REPLICATION SLAVE` и `REPLICATION CLIENT`.
- **Общее:** Все узлы должны иметь разрешенные хосты в файрволе/security groups. Канал репликации должен быть зашифрован TLS при передаче через недоверенные сегменты.

## Основные концепции

### Механизм передачи: Физическая vs Логическая

Выбор подхода определяет производительность и гибкость системы.

1.  **Физическая репликация (Binary / Streaming):**
    *   **Механизм:** Передаются изменения на уровне блоков данных или дисковых страниц (побайтовая копия).
    *   **Основа:** **[Журнал предзаписи (WAL)](./write_ahead_log.md)**.
    *   **Плюсы:** Максимальная производительность (низкая нагрузка на CPU), гарантированная идентичность на байтовом уровне, поддержка всех типов данных и индексов "из коробки".
    *   **Минусы:** Требует одинаковых версий СУБД, ОС и архитектуры процессора; нельзя реплицировать только часть базы (только весь инстанс).

2.  **Логическая репликация:**
    *   **Механизм:** Передаются высокоуровневые изменения данных (строк или SQL-запросов).
    *   **Форматы логической записи:**
        *   **STATEMENT (SBR):** Передаются исходные SQL-запросы (`INSERT`, `UPDATE`). *Риск:* Недетерминированные функции (`NOW()`, `RAND()`, `UUID()`) могут дать разный результат на мастере и реплике.
        *   **ROW (RBR):** Передаются фактические изменения конкретных строк. Безопасно, но увеличивает объем трафика и логов.
        *   **MIXED:** СУБД автоматически переключается между форматами для оптимизации.
    *   **Плюсы:** Репликация отдельных таблиц, передача данных между разными версиями СУБД/ОС, возможность записи в реплику (в спец. сценариях).
    *   **Минусы:** Выше нагрузка на CPU (парсинг и выполнение запросов на реплике), сложности с репликацией структуры (DDL).

### Репликация на основе консенсуса (Paxos/Raft)

Современный стандарт для распределенных систем (**[etcd](../../etcd/raft_consensus.md)**, CockroachDB, TiDB, MongoDB Replica Set, MySQL Group Replication).

- **Принцип:** Для фиксации изменения не требуется подтверждение от *всех* реплик. Достаточно подтверждения от **большинства (кворума)** узлов.
- **Преимущества:** Устойчивость к сбоям меньшинства узлов без остановки записи, автоматические выборы лидера, отсутствие проблемы Split-brain.
- **Применение:** Системы, где надежность и согласованность критичнее максимальной пропускной способности.

### Роль журнала WAL

Основой любого надежного механизма репликации является **[Журнал предзаписи (Write-Ahead Log, WAL)](./write_ahead_log.md)**. Все изменения сначала фиксируются в этом журнале на Primary, а затем передаются на реплики для последовательного воспроизведения.

### Отложенная репликация (Delayed Replication)

Режим, при котором реплика применяет изменения с задержкой, задаваемой в секундах.

| СУБД | Параметр | Пример |
| :--- | :--- | :--- |
| **PostgreSQL** | `recovery_min_apply_delay` | `recovery_min_apply_delay = 30min` |
| **MySQL** | `SOURCE_DELAY` | `CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 1800;` |

**Применение:** Защита от логических ошибок. Если `DROP TABLE` выполнен на Primary, delayed replica позволяет откатиться до момента до ошибки, если ошибка обнаружена в течение окна задержки.

**Важно:** При failover delayed replica теряет данные за время отставания от источника. Окно задержки должно превышать время обнаружения ошибки человеком.

### Репликация — это не бэкап

- **Репликация** обеспечивает **высокую доступность** и защищает от сбоев оборудования.
- **[Резервное копирование](./backups.md)** защищает от **логических ошибок** и человеческого фактора.
- *Пример:* Команда `DROP TABLE`, выполненная на Primary, будет немедленно воспроизведена на всех репликах. Только бэкап позволит вернуть данные.

### Основные цели репликации

1.  **Высокая доступность (HA):** Мгновенное переключение на реплику при сбое мастера.
2.  **Масштабирование чтения (Read Scaling):** Распределение SELECT-запросов между репликами.
3.  **Географическое распределение:** Размещение данных ближе к пользователям для уменьшения Latency.
4.  **Миграция без простоя (Zero-Downtime):** Перенос данных на новую инфраструктуру с минимальным окном обслуживания.
5.  **Снятие нагрузки (Offloading):** Выполнение бэкапов и тяжелой аналитики на реплике без влияния на Primary.

### Типы репликации и CAP-теорема

Выбор типа репликации — это поиск компромисса в рамках **[CAP-теоремы](./cap_theorem.md)**.

1.  **Асинхронная репликация (AP):**
    *   Транзакция считается завершенной сразу после записи в локальный WAL на Primary. Данные уходят на реплики в фоновом режиме.
    *   **Плюсы:** Минимальная задержка на запись, независимость мастера от состояния реплик.
    *   **Минусы:** Риск потери данных (RPO > 0) при внезапном сбое Primary.

2.  **Синхронная репликация (CP):**
    *   Транзакция не фиксируется, пока Primary не получит подтверждение от всех (или большинства) реплик о записи данных.
    *   **Плюсы:** Гарантия Zero Data Loss. Строгая согласованность (Strong Consistency).
    *   **Минусы:** Запись блокируется при недоступности хотя бы одной реплики или медленной сети.

3.  **Полусинхронная репликация (Semi-synchronous):**
    *   Primary ждет подтверждения хотя бы от одной реплики о получении данных (записи в Relay Log).
    *   **Особенность:** Часто используется механизм "отката" в асинхронный режим при превышении таймаута ожидания реплик.

### Отставание репликации (Replication Lag)

**Replication Lag** — задержка между фиксацией данных на Primary и их доступностью на реплике.

- **Причины лага:**
    *   **Сетевые задержки:** Узкий канал или огромные расстояния.
    *   **Ресурсный дефицит:** Нехватка CPU/IOPS на реплике.
    *   **Длительные транзакции:** Реплика ждет завершения всей транзакции на мастере перед её применением (особенно в логической репликации).
    *   **Блокировки:** Тяжелые аналитические отчеты на реплике блокируют применение изменений.
    *   **Однопоточность:** На мастере запись идет в N потоков, а реплика применяет их последовательно.
    *   **Слоты репликации:** На PostgreSQL неактивный слот "удерживает" WAL, что может привести к переполнению диска и остановке Primary.

- **Последствия:**
    *   **Stale Reads (Грязное чтение):** Пользователь не видит свои изменения сразу после записи.

- **Как бороться:**
    1.  **Eventual Consistency:** Принять, что данные появятся на реплике через доли секунды.
    2.  **Read-after-write:** Форсировать чтение критичных запросов (например, профиль пользователя сразу после редактирования) из **Primary** БД.
    3.  **Параллельная репликация:** В MySQL включить Multi-Threaded Slave (MTS); в PostgreSQL использовать несколько реплик для распределения нагрузки.
    4.  **Мониторинг:** Настроить алерты на лаг > 30 секунд ( read-heavy ) или > 10 секунд ( OLTP ).

### Проблема Split-Brain и кворум

**Split-Brain** (расщепление мозга) — критическая ошибка, когда в кластере появляются два активных Primary, что ведет к необратимой порче данных.

**Сценарий возникновения:**
1.  Разрыв связи между сегментами сети.
2.  Реплика в изолированном сегменте решает, что Primary упал, и повышает себя до Primary.
3.  Оба узла начинают принимать запись независимо.
4.  Данные расходятся.

**Механизмы решения:**
- **Кворум:** Решение о повышении принимается только большинством голосов `(N/2)+1`.
- **STONITH / Fencing:** ("Shoot The Other Node In The Head") — принудительное выключение изолированного узла через IPMI/PDU или блокировка его доступа к общему хранилищу.

## Практические сценарии

### Топологии репликации

1.  **Primary-Replica (1 -> N):** Стандарт для масштабирования чтения.
2.  **Каскадная (Cascading):** `Primary -> Replica A -> Replica B`. Снижает сетевую нагрузку на Primary.
3.  **Multi-Primary (Master-Master):** Два или более узла принимают запись.
    *   *Минусы:* Чрезвычайная сложность разрешения конфликтов. Рекомендуется избегать активной записи на оба узла одновременно.
4.  **Multi-Source:** Одна реплика собирает данные из нескольких независимых Primary. Полезно для аналитики и ETL.
5.  **Кольцевая (Ring):** Узлы соединены по кругу. Хрупкая схема: сбой одного узла разрывает весь цикл репликации.

### Шифрование канала репликации

Репликация передает все данные между узлами. Если канал не зашифрован, злоумышленник с доступом к сети может перехватывать или подделывать данные.

| СУБД | Метод | Пример конфигурации |
| :--- | :--- | :--- |
| **PostgreSQL** | `sslmode=verify-full` в `postgresql.conf` / `primary_conninfo` | `primary_conninfo = 'host=<ip> user=replicator password=... sslmode=verify-full sslrootcert=/etc/ssl/ca.crt'` |
| **MySQL** | `SOURCE_SSL=1` / `REQUIRE SSL` | `CHANGE REPLICATION SOURCE TO SOURCE_SSL=1, SOURCE_SSL_CA='/etc/ssl/ca.pem';` |
| **etcd** | TLS peer-to-peer | `--peer-trusted-ca-file=ca.crt --peer-cert-file=peer.crt --peer-key-file=peer.key` |

### Балансировка нагрузки для чтения

Приложения с преобладанием чтения должны распределять запросы между репликами. Ручное управление через DNS или список хостов в конфиге приложения ненадежно.

**Рекомендуемые инструменты:**

| Инструмент | СУБД | Особенности |
| :--- | :--- | :--- |
| **ProxySQL** | MySQL / MariaDB | Встроенная балансировка, кэширование запросов, автоматическое определение мертвых реплик. |
| **HAProxy** | PostgreSQL / MySQL | L4/L7 балансировщик. Требует health-check скриптов для проверки состояния репликации. |
| **PgBouncer** | PostgreSQL | Connection pooler с режимом `transaction` или `session`. Не балансирует нагрузку сам, но используется в связке с HAProxy. |
| **PgCat** | PostgreSQL | Современный connection pooler и балансировщик с поддержкой Multi-Primary и чтения с реплик. |

**Health-check пример для HAProxy + PostgreSQL:**
```bash
#!/bin/bash
# /usr/local/bin/pg_is_primary.sh
PGPASSWORD='password' psql -U replicator -h "$1" -p 5432 -c "SELECT pg_is_in_recovery();" 2>/dev/null | grep -q f && exit 0 || exit 1
```
В `haproxy.cfg`:
```
backend pg_read
    option pgsql-check user replicator
    server primary 10.0.0.1:5432 check
    server replica1 10.0.0.2:5432 check
    server replica2 10.0.0.3:5432 check
```

### Connection Pooling и репликация

Каждое соединение к БД потребляет память (~10 МБ RAM на бэкенд). При большом числе приложений, направляющих запросы на реплики, пул соединений критически важен.

| Инструмент | Режим | Примечание |
| :--- | :--- | :--- |
| **PgBouncer** | `transaction` | Рекомендуется для веб-приложений. Соединение возвращается в пул после COMMIT/ROLLBACK. |
| **PgBouncer** | `session` | Соединение держится на всю сессию клиента. Менее эффективно, но совместимо с prepared statements и advisory locks. |
| **ProxySQL** | Встроенный пул | Автоматически создает и переиспользует соединения к MySQL-репликам. |

**Важно:** При использовании PgBouncer в режиме `transaction` не допускайте транзакций длительностью > `wait_timeout` (по умолчанию 600 сек), иначе соединение будет разорвано посередине транзакции.

### Мониторинг и диагностика

Ключевые метрики для отслеживания:

| Метрика | PostgreSQL | MySQL | Алерт |
| :--- | :--- | :--- | :--- |
| **Lag (время)** | `pg_last_xact_replay_timestamp()` | `Seconds_Behind_Source` | > 30 сек |
| **Lag (WAL)** | `pg_wal_lsn_diff(sent_lsn, replay_lsn)` | ` Relay_Log_Space` / GTID-разница | Рост > 1 ГБ/час |
| **Статус потоков** | `pg_stat_replication` | `SHOW REPLICA STATUS` | `Replica_IO_Running: No` |
| **Слоты репликации** | `pg_replication_slots` | N/A (retention binlog) | `active = false` > 1 час |
| **Ошибки DDL** | Логи Apply | `Last_SQL_Error` | Любая не-пустая ошибка |

**Примеры команд мониторинга:**

**PostgreSQL — проверка отставания:**
```sql
SELECT client_addr, state, sync_state,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), sent_lsn)) AS send_lag,
       pg_size_pretty(pg_wal_lsn_diff(sent_lsn, write_lsn)) AS write_lag,
       pg_size_pretty(pg_wal_lsn_diff(write_lsn, flush_lsn)) AS flush_lag,
       pg_size_pretty(pg_wal_lsn_diff(flush_lsn, replay_lsn)) AS replay_lag
FROM pg_stat_replication;
```

**PostgreSQL — статус на Standby:**
```sql
SELECT pg_is_in_recovery() AS is_replica,
       pg_last_wal_receive_lsn() AS last_received,
       pg_last_wal_replay_lsn() AS last_replayed,
       now() - pg_last_xact_replay_timestamp() AS last_apply_delay;
```

**MySQL — проверка здоровья:**
```sql
SHOW REPLICA STATUS\G
-- Ключевые поля:
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source: 0
-- Last_Error_Number: 0

-- GTID-консистентность:
SELECT GTID_SUBSET(@@GLOBAL.gtid_executed, @@GLOBAL.gtid_purged) AS is_consistent;
-- Должно возвращать 1
```

### Разрешение конфликтов (в Multi-Primary)

- **Last Write Wins (LWW):** Побеждает версия с более поздним Timestamp (требует синхронизации времени через NTP/Chrony).
- **Vector Clocks (Векторные часы):** Позволяют отследить причинно-следственную связь событий.
- **CRDT (Conflict-free Replicated Data Types):** Специальные типы данных, гарантирующие схождение к одному результату без конфликтов.

### Сценарий: Миграция БД (2 ТБ) без простоя

1.  **Синхронизация:** Снятие бэкапа и восстановление на целевом сервере.
2.  **Настройка Catch-up:** Подключение нового сервера как реплики к текущему Primary.
3.  **Догонка:** Ожидание минимального лага.
4.  **Switchover:**
    *   Перевод старого Primary в Read-only.
    *   Ожидание применения последних транзакций на реплике.
    *   Повышение реплики до Primary.
    *   Переключение трафика приложения.

**MySQL:**
```bash
# Проверка целостности данных (Percona Toolkit)
pt-table-checksum --replicate=percona.checksums h=primary

# Синхронизация при расхождениях
pt-table-sync --replicate=percona.checksums h=primary h=replica1
```

### Управление слотовми репликации (PostgreSQL)

```sql
-- Просмотр всех слотов
SELECT slot_name, slot_type, active, restart_lsn, confirmed_flush_lsn
FROM pg_replication_slots;

-- Удаление неактивного слота (риск: потеря реплики при её повторном подключении)
SELECT pg_drop_replication_slot('stale_slot_name');

-- Ограничение размера WAL на мастере (предотвращение переполнения)
ALTER SYSTEM SET wal_keep_size = '4GB';
```

### Отложенная репликация (Delayed Replication)

**PostgreSQL (16+):**
```conf
# standby.signal или postgresql.auto.conf
recovery_min_apply_delay = 30min
```

**MySQL:**
```sql
CHANGE REPLICATION SOURCE TO SOURCE_DELAY = 1800;
START REPLICA;
```

### Failover и Switchover

**Ручной Switchover (PostgreSQL с Patroni):**
```bash
# Плановое переключение с сохранением данных
patronictl switchover mycluster --leader primary1 --candidate replica2
```

**Ручной Failover (MySQL):**
```sql
-- На реплике: остановка потоков
STOP REPLICA;

-- Сброс бинарного лога (новая позиция)
RESET MASTER;

-- Подключение приложения к новой Primary
```

## Поиск и устранение неисправностей

### Типичные ошибки и диагностика

| Категория | Симптом | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Сетевое соединение** | `Replica_IO_Running: Connecting` (MySQL) / `streaming` неактивен (PG) | `telnet <primary> 5432`, `tcpdump`, проверка security groups | Восстановление маршрута, открытие портов, проверка TLS-сертификатов |
| **Применение данных** | `Replica_SQL_Running: No` | `SHOW REPLICA STATUS\G` / `pg_stat_replication` | Дубликаты (1062), отсутствие записей (1032), ошибки прав доступа |
| **WAL Bloat** | Диск на Primary заполняется | `du -sh pg_wal/` (PG), `SHOW BINARY LOGS` (MySQL) | Удаление неактивных слотов (PG), очистка старых binlog (MySQL) |
| **Однопоточность** | Лаг растет под нагрузкой | `SHOW STATUS LIKE 'Slave_open_temp_tables'` (MySQL), `pg_stat_activity` (PG) | Включение MTS (MySQL), добавление реплик (PG) |
| **Split-Brain** | Два активных Primary | Проверка `pg_is_in_recovery()` на всех узлах | Принудительное выключение minority (STONITH), восстановление из бэкапа |
| **GTID-конфликты** | Ошибка 1236, 1782 (MySQL) | `SHOW GLOBAL STATUS LIKE 'gtid_%'` | Пересоздание реплики из чистого бэкапа, очистка `gtid_executed` |
| **Конфликты логической репликации** | `duplicate key value violates unique constraint` | Проверка `pg_stat_user_tables` | Запрет записи на подписчик, настройка `SKIP` (PG 15+) |

### Граничные случаи

1.  **Зависшие Replication Slots (PostgreSQL):** Если реплика отключена, но слот остался активным, Master хранит все WAL с момента отключения.
    *   *Диагностика:* `SELECT * FROM pg_replication_slots WHERE active = false;`
    *   *Решение:* Удалить слот `SELECT pg_drop_replication_slot('slot_name');` или увеличить `wal_keep_size`.

2.  **Смешанный режим GTID и Non-GTID (MySQL):** При миграции на GTID допускается временное смешанное состояние, но в steady-state должна работать либо чистая GTID-топология, либо классическая File:Pos.

3.  **Конфликты AUTO_INCREMENT в Multi-Primary:** Требуется настройка смещений (`offset`) и шага (`increment`), чтобы ID не пересекались.

4.  **Гонки записи:** Без блокировок на уровне приложения одновременное изменение одной строки на разных узлах ведет к потере данных.

5.  **Ограничение `Seconds_Behind_Source` (MySQL):** Показатель неточен при сетевых разрывах или выполнении очень длинных транзакций. Для точного мониторинга используйте Performance Schema.

6.  **Утечка replication slot при долгой миграции:** При отключенном потребителе логической репликации на Primary накапливается WAL.
    *   *Мониторинг:* `pg_stat_replication_slots` / `ReplicationLag` в ClickHouse.
    *   *Решение:* удалить неиспользуемый slot или увеличить `wal_keep_size` / binlog retention.

## Лучшие практики

### Проектирование и развертывание

1.  **Используйте Primary/Replica вместо Master/Slave** в конфигурациях и документации.
2.  **Идентификация:** Всегда настраивайте `server_id` и `server_uuid` явно в MySQL. В PostgreSQL используйте уникальные имена для слотов репликации.
3.  **Формат binlog:** Используйте `ROW` повсеместно в MySQL. `STATEMENT` допустим только в изолированных read-only сценариях без репликации.
4.  **Crash-Safe репликация:** В MySQL 8.0 параметры `master_info_repository` и `relay_log_info_repository` установлены в `TABLE` по умолчанию. Не меняйте их на `FILE`.
5.  **Синхронизация времени:** Настройте chrony или systemd-timesyncd на всех узлах. Расхождение > 100 мс ломает мониторинг лага и LWW-конфликты.

### Эксплуатация и мониторинг

1.  **Мониторинг:** Интегрируйте метрики репликации в систему мониторинга (Prometheus + Grafana / Zabbix). Установите алерты на рост лага > 30 секунд.
2.  **Резервное копирование:** Снимайте бэкапы с реплик, а не с источника. Используйте физические бэкапы (XtraBackup, pg_basebackup) для больших инсталляций.
3.  **Upgrade:** При обновлении версии СУБД обновляйте сначала реплики, затем Primary. Это позволяет мгновенно откатиться при проблемах.
4.  **Документация:** Ведите актуальную схему топологии репликации. Документируйте процедуры ручного failover и воссоздания реплики.

### Безопасность

1.  **Аутентификация:** Используйте отдельного пользователя репликации с минимальными правами. Никогда не используйте `root` для репликации.
2.  **Шифрование в transit:** Включайте TLS на канале репликации. Для production используйте сертификаты, подписанные внутренним CA.
3.  **Изоляция:** Реплика должна работать в режиме `read_only = ON` (или `super_read_only = ON`), чтобы предотвратить случайную запись данных.

### Капасити-планирование

1.  **Резерв по дискам:** Оставляйте запас 30-50% на диске Primary для роста WAL при долгих транзакциях или остановке реплик.
2.  **Сеть:** Проектируйте пропускную способность канала с запасом 2x от пиковой нагрузки репликации. Синхронная репликация требует низкой и стабильной задержки.
3.  **Ресурсы на реплике:** Нагружающая аналитика на реплике может конкурировать с потоком репликации за CPU/IOPS. Для тяжелых отчетов используйте выделенные реплики-сегменты.

## Дополнительная информация

### Программные причины сбоев в Multi-Primary

1.  **Конфликты `AUTO_INCREMENT`:** Требуется настройка смещений (`offset`) и шага (`increment`), чтобы ID не пересекались.
2.  **Недетерминированные запросы:** Функции типа `NOW()`, `UUID()` требуют использования формата `ROW` для логической репликации.
3.  **DDL-операции:** Изменения схемы могут вызвать рассинхрон или долгие блокировки.
4.  **Гонки записи:** Без блокировок на уровне приложения одновременное изменение одной строки на разных узлах ведет к потере данных.
