# Репликация баз данных

## Определения

**Репликация** — это процесс создания и поддержания идентичных копий (реплик) базы данных на нескольких серверах. Это ключевой механизм для обеспечения отказоустойчивости и масштабируемости.

В то время как репликация *копирует* данные, другой метод масштабирования, **[шардирование](./sharding.md)**, *разделяет* их по разным серверам.

## Основные концепции

Основой механизма репликации является [Журнал предзаписи (Write-Ahead Log, WAL)](./write_ahead_log.md). Все изменения данных сначала записываются в этот журнал на Master-сервере, а затем эти записи передаются на реплики для повторения операций.

### Репликация — это не бэкап

- **Репликация** обеспечивает **высокую доступность** и защищает от сбоев оборудования.
- **[Резервное копирование](./backups.md)** защищает от **логических ошибок**, таких как случайное удаление данных (`DROP TABLE`).

Команда `DROP TABLE`, выполненная на master-сервере, будет немедленно воспроизведена на всех репликах, что приведет к полной потере данных в кластере. Только независимый бэкап может спасти от таких ситуаций.

### Основные цели репликации

- **Высокая доступность (High Availability):** Если основной (master) сервер выходит из строя, один из ведомых (slave) серверов может взять на себя его роль, минимизируя время простоя.
- **Масштабирование нагрузки на чтение (Read Scaling):** Запросы на чтение можно распределить между несколькими репликами, что снижает нагрузку на основной сервер и увеличивает общую производительность.
- **Резервное копирование:** Реплики можно использовать для создания [резервных копий](./backups.md) без остановки или замедления работы основного сервера.
- **Географическое распределение:** Размещение реплик ближе к пользователям в разных регионах может значительно уменьшить задержку при чтении данных.

### Типы репликации: Синхронная vs. Асинхронная

Выбор между синхронной и асинхронной репликацией напрямую влияет на компромисс между согласованностью (Consistency) и доступностью (Availability) в [CAP-теореме](./cap_theorem.md). Это вечный компромисс между скоростью и надёжностью.

#### Синхронная репликация

При синхронной репликации транзакция на master-сервере не считается завершенной до тех пор, пока все изменения не будут успешно применены на всех репликах.
Это обеспечивает **максимальную надежность ценой скорости**.

**Схема процесса:**

```text
  Клиент                    Master                      Replica
    | -- 1. WRITE ---------> |                           |
    |                        | -- 2. REPLICATE --------> |
    |                        |                           | -- 3. OK
    |                        | <-------- 4. ACK --------- |
    | <------- 5. OK -------- |                           |
```

- **Процесс:**
    1. Клиент отправляет запрос на запись на master-узел.
    2. Master-узел записывает данные локально (в WAL).
    3. Master-узел пересылает изменения на все реплики.
    4. Каждая реплика подтверждает успешное применение изменений.
    5. Только после получения всех подтверждений master-узел сообщает клиенту об успешном завершении транзакции.

- **Плюсы:**
  - **Сильная согласованность (Strong Consistency):** Гарантируется, что все реплики всегда содержат идентичные данные. Потеря данных при сбое мастера исключена.
  - **Высочайшая надёжность:** Данные гарантированно находятся на нескольких серверах.
- **Минусы:**
  - **Высокая задержка:** Запись замедляется до скорости самой медленной реплики, так как мастер ждет подтверждения.
  - **Низкая доступность:** Если хотя бы одна реплика недоступна или имеет проблемы с сетью, запись на master-узел блокируется, что может привести к "зависанию" всего кластера.
- **Связь с CAP:** Этот подход характерен для **CP** (Consistency + Partition Tolerance) систем. Используется там, где потеря транзакций недопустима (например, в банках или биллинговых системах), часто с тремя и более серверами.

#### Асинхронная репликация

При асинхронной репликации транзакция на master-сервере считается завершенной сразу после локальной записи (в WAL). Передача данных на реплики происходит в фоновом режиме с некоторой задержкой (`replication lag`).
Это обеспечивает **максимальную скорость ценой потенциального риска потери данных**.

- **Плюсы:**
  - **Низкая задержка:** Запись на master-узел происходит очень быстро, так как он сразу отвечает клиенту "ОК".
  - **Высокая доступность:** Недоступность реплик не влияет на возможность записи на master-узел.
- **Минусы:**
  - **Возможна потеря данных:** Если master-узел выйдет из строя до того, как данные будут переданы на реплики, эти данные будут потеряны навсегда. Реплика про них не успеет узнать.
  - **Согласованность в конечном счете (Eventual Consistency):** Чтение с реплики может вернуть устаревшие данные.
- **Связь с CAP:** Этот подход характерен для **AP** (Availability + Partition Tolerance) систем. Подходит для систем, где риск потери одной записи приемлем ради высокой скорости (социальные сети, мессенджеры, блоги).

### Проблема Split-Brain и решение через кворум

**Split-Brain** (расщепление мозга) — это критическая ошибка в распределенных системах, которая возникает в топологиях Master-Slave и Master-Master при неправильно настроенном автоматическом переключении (failover).

**Сценарий возникновения:**

1. **Разрыв связи:** Канал связи между Master и Slave (или между двумя Master-узлами) обрывается.
2. **Неправильное решение о сбое:** Slave-узел, не видя Master-сервер, решает, что тот вышел из строя. Автоматизированная система (или администратор) повышает Slave до роли нового Master-сервера.
3. **Появление двух Master-узлов:** В этот момент в кластере существуют два активных Master-сервера, которые не знают друг о друге. Старый Master (который на самом деле не падал, а был лишь изолирован) и новый, бывший Slave.
4. **Рассинхронизация данных:** Оба узла начинают принимать запросы на запись, и их данные необратимо расходятся.
5. **Сложное восстановление:** После восстановления связи выясняется, что в системе существуют две конфликтующие версии правды. Сведение этих данных в единое целое — сложная и часто ручная задача.

Для решения проблемы Split-Brain используются **кворумные системы**. Идея заключается в том, что для выполнения операций записи или выбора мастера кластер должен иметь **большинство** голосов (`(N / 2) + 1`).

- **Принцип работы:** Если из-за разрыва сети часть кластера оказывается в меньшинстве (не имеет кворума), она автоматически переходит в режим "только для чтения" или блокирует запись. Это гарантирует, что в любой момент времени только один сегмент кластера может изменять данные, предотвращая Split-Brain. Это яркий пример выбора **согласованности (C) в ущерб доступности (A)** в [CAP-теореме](./cap_theorem.md).

## Практические сценарии: Топологии репликации

### Master-Slave (Ведущий-ведомый)

Самая распространенная топология. Есть один главный узел (Master), который принимает все запросы на запись. Данные с него реплицируются на один или несколько ведомых узлов (Slaves), которые обычно обрабатывают запросы на чтение.

- **Плюсы:** Простота настройки и понимания.
- **Минусы:** Master является единой точкой отказа для операций записи.

**Вариации:**

1. **Один Master, много Slave (1 -> N)**
    Это стандартный способ масштабирования чтения.

    ```text
             +-----> [SLAVE 1]
    [MASTER] --+-----> [SLAVE 2]
             +-----> [SLAVE N]
    ```

2. **Цепочечная репликация (Chained Replication)**
    Slave-узел выступает мастером для следующего slave-узла.

    ```text
    [MASTER] --> [SLAVE 1] --> [SLAVE 2] --> ...
    ```

    - **Преимущество:** Снижает нагрузку на основной master-узел, так как ему нужно отправлять бинарный лог только одному получателю (Slave 1).
    - **Недостаток:** Увеличивается общая задержка репликации. Данные дойдут до `SLAVE 2` позже, чем до `SLAVE 1`.

### Master-Master (Ведущий-ведущий)

В этой топологии два или более узла являются ведущими и могут принимать запросы на запись. Изменения, сделанные на одном мастере, реплицируются на другой.

- **Плюсы:** Повышенная отказоустойчивость для операций записи.
- **Минусы:** Данная топология значительно сложнее в настройке и эксплуатации. Она сопряжена с высоким риском **конфликтов записи** и **тихой порчи данных** при некорректной конфигурации. Детальный разбор потенциальных проблем находится в разделе `Дополнительная информация`.

## Дополнительная информация

### Программные причины сбоев и конфликтов в Master-Master

Помимо сетевых проблем (split-brain), существует ряд чисто программных причин, по которым Master-Master репликация может легко выйти из строя или привести к порче данных.

1. **Конфликты `AUTO_INCREMENT`**
    - **Проблема:** Это самая частая причина сбоя. Оба мастера считают, что они имеют право выдать следующий ID для новой записи. Если они одновременно вставляют строки, они могут сгенерировать **один и тот же ID**. Когда изменение от первого мастера прилетит на второй, репликация остановится с ошибкой нарушения уникальности первичного ключа.
    - **Решение:** Настроить серверы так, чтобы они не могли генерировать пересекающиеся ID. В MySQL для этого используются переменные `auto_increment_increment` (шаг) и `auto_increment_offset` (смещение). Например, для двух мастеров:
        - *Мастер 1:* `auto_increment_increment = 2`, `auto_increment_offset = 1` (генерирует ID: 1, 3, 5, ...)
        - *Мастер 2:* `auto_increment_increment = 2`, `auto_increment_offset = 2` (генерирует ID: 2, 4, 6, ...)

2. **Недетерминированные запросы**
    - **Проблема:** Запросы, использующие функции, результат которых может отличаться в зависимости от времени или сервера (`UUID()`, `NOW()`, `RAND()`). Например, запрос `INSERT ... VALUES (UUID())` на каждом мастере сгенерирует *разные* UUID. Это не остановит репликацию, но приведет к **тихой порче данных** — данные в одной и той же строке на разных мастерах будут отличаться.
    - **Решение:** Использовать **строчный формат бинарного лога (`binlog_format = ROW`)**. В этом режиме в лог пишется не сам запрос, а уже измененная строка (конечный результат). Таким образом, на второй мастер прилетит уже готовая строка с правильным UUID, а не функция, которую нужно выполнить заново.

3. **Операции изменения схемы (DDL)**
    - **Проблема:** Команды `ALTER TABLE`, `DROP TABLE` и другие DDL-операции не являются атомарными в контексте репликации и могут вызвать хаос. Одновременное применение разных `ALTER` на разных мастерах почти гарантированно приведет к сбою.
    - **Решение:** Проводить миграции схемы через специальные утилиты (`pt-online-schema-change`, `gh-ost`) и по строгому регламенту, исключающему одновременные изменения.

4. **Гонки "прочитал-изменил-записал"**
    - **Проблема:** Если логика приложения не использует блокировки, одновременное изменение одних и тех же данных на разных мастерах приведет к потере обновлений.
    - **Решение:** Использовать пессимистические блокировки (`SELECT ... FOR UPDATE`) или атомарные SQL-операции (`UPDATE table SET balance = balance - 10`).
