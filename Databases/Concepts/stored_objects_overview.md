# Хранимые объекты в БД: Процедуры, Функции, Триггеры и События

**Актуально для:** PostgreSQL 18/17/16, MariaDB 11.4/10.11, MySQL 8.4 LTS, Linux 6.x

## Определения

*   **Хранимый объект (Stored Object)** — программный код (логика), который сохраняется внутри базы данных и выполняется сервером СУБД. Объект компилируется (или парсится) при создании и хранится в системном каталоге, что позволяет повторно использовать его без передачи текста запроса по сети.
*   **Хранимая процедура (Stored Procedure)** — набор SQL-инструкций и управляющих конструкций, который может выполнять произвольную логику, не возвращая значения (хотя может выводить параметры). Поддерживает управление транзакциями (`COMMIT/ROLLBACK`) и имеет собственный контекст выполнения.
*   **Функция (Function)** — объект, который **обязательно возвращает значение** (скалярное, строку или таблицу). Может использоваться в выражениях `SELECT`, `WHERE`, `JOIN`. В большинстве СУБД не может управлять транзакциями (делать `COMMIT/ROLLBACK` внутри тела).
*   **Триггер (Trigger)** — процедура, которая **автоматически** запускается при наступлении определённого события на таблице или представлении (`INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, а в некоторых СУБД — DDL-события). Работает в контексте транзакции вызвавшего её оператора.
*   **Событие (Event / Cron Job)** — запланированная задача, выполняемая сервером БД по расписанию (аналог `cron`). Позволяет запускать процедуры или SQL-блоки в фоне, без подключения клиента.

### Сравнительная таблица

| Критерий | Хранимая процедура | Функция | Триггер | Событие |
|---|---|---|---|---|
| Возвращает значение | Нет (только OUTPUT-параметры) | Да (обязательно) | Нет | Нет |
| Управление транзакциями | Да (`COMMIT`/`ROLLBACK`) | Обычно нет | В контексте родительской транзакции | Да (своя транзакция) |
| Вызывается из SQL | `CALL` / `EXEC` | В выражениях `SELECT` | Автоматически | По расписанию |
| Привязка к таблице | Нет | Нет | Да | Нет |
| Типичное применение | Пакетная обработка, ETL, администрирование | Вычисления, валидация, вспомогательные запросы | Аудит, целостность, репликация на уровне БД | Ротация логов, очистка, агрегация |

## Базовые концепции

### Зачем использовать хранимую логику?

1.  **Снижение сетевого трафика:** Вместо пересылки больших объёмов данных приложению для обработки, логика выполняется максимально близко к данным. Один `CALL` заменяет десятки запросов.
2.  **Безопасность:** Можно запретить прямой доступ к таблицам, разрешив только выполнение процедур (инкапсуляция). Пользователь не знает структуру таблиц и не может модифицировать данные напрямую. Подробнее: [Безопасность хранимых объектов](./stored_objects/security.md).
3.  **Консистентность:** Триггеры гарантируют выполнение правил целостности **независимо** от того, какое приложение изменяет данные — будь то веб-интерфейс, CLI-утилита или миграционный скрипт.
4.  **Переиспользование:** Логика, оформленная как хранимый объект, доступна всем клиентам (приложениям, отчётам, ETL-процессам) без дублирования кода.
5.  **Производительность (в некоторых сценариях):** Предкомпилированный план выполнения хранимой процедуры может быть эффективнее ad-hoc-запросов, особенно в MariaDB/MySQL, где отсутствует prepared statement cache для сложных пакетов.

### Модель выполнения

**Контекст выполнения (Execution Context):**

Каждый хранимый объект выполняется в собственном контексте, который включает:
- **Переменные:** Локальные переменные, параметры входа/выхода.
- **Обработка ошибок:** Блоки `EXCEPTION` (PL/pgSQL), `DECLARE ... HANDLER` (MySQL/MariaDB).
- **Последовательность инструкций:** Пошаговое выполнение SQL и управляющего кода.
- **Доступ к данным:** Через SQL-запросы внутри тела объекта.

**Консистентность чтения (Read Consistency):**

- В PostgreSQL каждая функция/процедура выполняется в **snapshot** транзакции. Если транзакция изменила данные до вызова функции, функция видит эти изменения.
- В MariaDB/MySQL (InnoDB) используется **MVCC**: функция видит данные на момент начала транзакции, в которой она вызвана.

**Уровень изоляции:**

Хранимые объекты выполняются на уровне изоляции **родительской транзакции**. Если транзакция неявная (autocommit), каждый SQL-оператор внутри объекта — отдельная транзакция.

### Механизм кэширования планов

При первом вызове хранимого объекта СУБД парсит и компилирует его, создавая план выполнения. Этот план кэшируется:
- **PostgreSQL:** План кэшируется в памяти процесса на время жизни сессии (prepared statements) или на время жизни объекта (для простых функций SQL).
- **MariaDB/MySQL:** План кэшируется в **query cache** (deprecated в 8.0) или через **prepared statements**. Хранимые процедуры используют **stored procedure cache**.
- **При изменении объекта** (`ALTER`, `CREATE OR REPLACE`) кэш инвалидируется и план пересоздаётся при следующем вызове.

### SRE-риски и недостатки

*   **Скрытая нагрузка:** Логика в БД потребляет CPU и RAM сервера базы данных, который сложнее масштабировать горизонтально, чем уровень приложения. Тяжёлые вычисления в триггерах могут замедлить все операции записи.
*   **Сложность отладки:** Инструменты отладки внутри БД значительно слабее современных IDE. Нет нормального step-through, conditional breakpoints, inspection переменных в реальном времени.
*   **Проблемы с CI/CD:** Хранимый код сложнее версионировать, тестировать (Unit-тесты) и деплоить без простоя. Требуются специализированные инструменты миграций (Flyway, Liquibase, Atlas).
*   **Блокировки:** Неоптимизированные триггеры могут вызывать длительные блокировки строк, парализуя запись. Особенно `BEFORE UPDATE` триггеры, которые выполняют дополнительные SELECT/INSERT.
*   **Версионирование и откат:** Откат изменений в хранимых объектах сложнее, чем в приложенческом коде — требуется отдельная миграция.
*   **Debug в production:** Логирование и трассировка в production-среде ограничены соображениями производительности и безопасности.

## Детализация по типам объектов

### Хранимые процедуры

**Назначение:** Пакетная обработка данных, администрирование БД, ETL-процессы, сложные бизнес-операции, требующие управления транзакциями.

**Характеристики:**
- Не возвращают значение напрямую (в PostgreSQL `PROCEDURE` поддерживает `COMMIT/ROLLBACK` внутри тела, а `FUNCTION` — нет).
- Могут принимать входные и выходные параметры.
- Вызываются через `CALL procedure_name(args)` (PostgreSQL 11+, MariaDB 10.3+) или `EXEC procedure_name(args)` (SQL Server).
- Могут содержать управляющие конструкции: циклы, условия, обработку ошибок.

**Управление транзакциями:**
- `PROCEDURE` в PostgreSQL может выполнять `COMMIT` и `ROLLBACK` внутри тела — это ключевое отличие от `FUNCTION`.
- Это позволяет разбивать долгие операции на части, делая промежуточные данные видимыми другим сессиям.
- В MariaDB/MySQL `PROCEDURE` также поддерживает `COMMIT`/`ROLLBACK`.

**Пример (PostgreSQL):**

```sql
-- Процедура для пакетного обновления статусов заказов
CREATE OR REPLACE PROCEDURE update_order_statuses(
    p_batch_size INT DEFAULT 1000
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_updated INT;
BEGIN
    LOOP
        UPDATE orders
        SET status = 'processed'
        WHERE id IN (
            SELECT id FROM orders
            WHERE status = 'pending'
            LIMIT p_batch_size
        );

        GET DIAGNOSTICS v_updated = ROW_COUNT;
        EXIT WHEN v_updated = 0;

        COMMIT;  -- Промежуточный коммит: данные видны другим сессиям
        RAISE NOTICE 'Обновлено % заказов', v_updated;
    END LOOP;
END;
$$;

-- Вызов
CALL update_order_statuses(500);
-- → NOTICE: Обновлено 500 заказов
-- → NOTICE: Обновлено 500 заказов
-- → NOTICE: Обновлено 237 заказов
```

### Функции

**Назначение:** Вычисления, валидация данных, вспомогательные запросы, использование в SQL-выражениях.

**Характеристики:**
- **Обязательно** возвращают значение (`RETURNS` в PostgreSQL, `RETURNS` в MariaDB).
- Могут быть **скалярными** (возвращают одно значение) или **табличными** (возвращают набор строк).
- Используются в `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`.
- В PostgreSQL могут быть написаны на `PL/pgSQL`, `SQL`, `PL/Python`, `PL/V8` и др.
- В MariaDB/MySQL — на `SQL`, `C` (плагины), `Lua` (MariaDB).

**Волатильность (PostgreSQL):**

PostgreSQL позволяет указать **volatility category** для оптимизации:
- `IMMUTABLE` — одинаковый результат при одинаковых аргументах (например, `sqrt(4)`). Кэшируется планировщиком.
- `STABLE` — одинаковый результат в пределах одного запроса (например, `current_date`). Не пересчитывается при вызове в цикле.
- `VOLATILE` (по умолчанию) — результат может меняться между вызовами (например, `random()`, `now()`). Не кэшируется.

### Триггеры

**Назначение:** Обеспечение целостности данных на уровне БД, аудит изменений, автоматическое обновление производных данных, репликация на уровне БД.

**Характеристики:**
- Привязаны к конкретной **таблице** или **представлению**.
- Срабатывают **автоматически** при `INSERT`, `UPDATE`, `DELETE` (и `TRUNCATE` в PostgreSQL).
- Работают в контексте транзакции вызвавшего её оператора.
- Могут быть **BEFORE** (до изменения) или **AFTER** (после изменения).
- В PostgreSQL также поддерживаются **INSTEAD OF** (для представлений) и **CONSTRAINT** триггеры (для проверки `FOREIGN KEY`).

**Типы триггеров по времени:**

| Тип | Назначение | Транзакция видна? | Типичное использование |
|---|---|---|---|
| `BEFORE INSERT` | Модифицировать данные до вставки | Нет (ещё не вставлены) | Заполнение значений по умолчанию, валидация |
| `BEFORE UPDATE` | Модифицировать данные до обновления | Да (старые данные видны) | Защита от изменения критичных полей, аудит |
| `BEFORE DELETE` | Действия перед удалением | Да | Архивирование перед удалением, каскадная логика |
| `AFTER INSERT` | Действия после вставки | Да | Обновление агрегатов, логирование |
| `AFTER UPDATE` | Действия после обновления | Да | Синхронизация производных данных |
| `AFTER DELETE` | Действия после удаления | Да | Очистка связанных данных, логирование |
| `INSTEAD OF` | Заменяет операцию (PostgreSQL) | Зависит от логики | Обновление представлений |
| `CONSTRAINT` | Проверка ограничений (PostgreSQL) | Да | Сложные проверки `FOREIGN KEY` |

**Триггерная функция vs триггер (PostgreSQL):**

В PostgreSQL триггер и функция — это **разные объекты**:
1. **Функция** определяет **что** делать (логику).
2. **Триггер** определяет **когда** и **на каком событии** вызывать функцию.

Одна функция может использоваться несколькими триггерами на разных таблицах.

```sql
-- 1. Функция-обработчик (логика)
CREATE OR REPLACE FUNCTION audit_changes()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit_log (table_name, operation, new_data, changed_at)
        VALUES (TG_TABLE_NAME, 'INSERT', row_to_json(NEW), NOW());
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit_log (table_name, operation, old_data, new_data, changed_at)
        VALUES (TG_TABLE_NAME, 'UPDATE', row_to_json(OLD), row_to_json(NEW), NOW());
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit_log (table_name, operation, old_data, changed_at)
        VALUES (TG_TABLE_NAME, 'DELETE', row_to_json(OLD), NOW());
        RETURN OLD;
    END IF;
END;
$$;

-- 2. Триггер (привязка к событию)
CREATE TRIGGER trg_orders_audit
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW
EXECUTE FUNCTION audit_changes();
```

**Контекстные переменные (PostgreSQL):**

| Переменная | Описание |
|---|---|
| `NEW` | Новая строка (для INSERT/UPDATE) |
| `OLD` | Старая строка (для UPDATE/DELETE) |
| `TG_OP` | Операция: `'INSERT'`, `'UPDATE'`, `'DELETE'`, `'TRUNCATE'` |
| `TG_TABLE_NAME` | Имя таблицы |
| `TG_TABLE_SCHEMA` | Имя схемы |
| `TG_WHEN` | `'BEFORE'` или `'AFTER'` |
| `TG_LEVEL` | `'ROW'` или `'STATEMENT'` |
| `TG_ARGV[]` | Аргументы, переданные в триггер |

### События (Event Scheduler)

**Назначение:** Фоновые задачи по расписанию: ротация логов, очистка временных данных, агрегация, отправка отчётов.

**Характеристики:**
- Выполняются **без подключения клиента** — сервер БД сам запускает задачу.
- Поддерживают выражения `AT` (одноразово) и `EVERY` (периодически).
- В MariaDB/MySQL встроен **Event Scheduler** (аналог `cron`).
- В PostgreSQL нет встроенного планировщика — используют `pg_cron`, `pgagent` или внешние планировщики.

## Сравнение возможностей по СУБД

| Особенность | PostgreSQL | MariaDB/MySQL | SQL Server |
|---|---|---|---|
| `COMMIT` внутри процедуры | Да (PROCEDURE) | Да | Да |
| Триггер на представлении | `INSTEAD OF` | Нет | `INSTEAD OF` |
| Триггер на DDL | Да (event triggers) | Нет | DDL триггеры |
| Вложенность триггеров | Ограничена `max_stack_depth` | Ограничена | Ограничена |
| Пакетная обработка | `FOR UPDATE SKIP LOCKED` | `LIMIT` в подзапросе | `TOP ... WITH (ROWLOCK)` |
| Динамический SQL | `EXECUTE` (PL/pgSQL) | Prepared statements | `sp_executesql` |
| Табличные функции | `RETURNS SETOF` / `RETURNS TABLE` | `RETURNS TABLE` | Table-valued functions |
| Триггеры на `TRUNCATE` | Да | Нет | Да |
| Возврат `NULL` из `BEFORE DELETE` | Ошибка | Ошибка | Ошибка |

## Рекомендации SRE по эксплуатации

1.  **Логирование:** Используйте встроенные механизмы (`RAISE NOTICE/LOG` в Postgres, таблицу логов в MariaDB) для отслеживания хода выполнения тяжёлых процедур. Не используйте `RAISE EXCEPTION` для логирования — это прерывает выполнение.
2.  **Таймауты:** Всегда устанавливайте локальные таймауты внутри процедур, чтобы избежать «зависания» сессий. В PostgreSQL: `statement_timeout` на уровне сессии; в MariaDB: `max_statement_time`; в MySQL: `max_execution_time` — но помните, что оба последних параметра не действуют на операторы внутри хранимых объектов (см. пункт 5 в разделе [Особые случаи и ограничения](#особые-случаи-и-ограничения-edge-cases)).
3.  **Версионирование:** Храните исходный код всех объектов в Git. Используйте инструменты миграций (Flyway, Liquibase, Atlas) для их развёртывания. Никогда не изменяйте объекты вручную в production.
4.  **Мониторинг:** Отслеживайте время выполнения процедур через системные представления. Подробнее: [Мониторинг хранимых объектов](./stored_objects/monitoring.md).
5.  **Тестирование:** Тестируйте хранимые объекты отдельно от приложения. Используйте `pg_prove` (PostgreSQL) или `MySQL Test Runner` (MariaDB/MySQL) для unit-тестов.
6.  **Именование:** Используйте консистентные префиксы: `fn_` для функций, `sp_` или `proc_` для процедур, `trg_` для триггеров, `evt_` для событий.
7.  **Не трогайте данные напрямую:** Если данные изменены некорректно, не используйте триггер для "исправления" — это может привести к рекурсии. Исправляйте данные через `UPDATE` с фильтрацией.

## Ключевые метрики и пороги (SLO)

| Метрика | Пресет (SLO) | Диагностика |
| :--- | :--- | :--- |
| **Procedure Duration (avg)** | P95 < 500 мс | Среднее время выполнения процедуры. Рост указывает на неоптимизированный SQL или отсутствие индекса. |
| **Procedure Calls/sec** | Без скачков > 2x baseline | Внезапный рост вызовов может указывать на циклическую рекурсию или проблему в приложении. |
| **Trigger Overhead** | < 5% от общей задержки INSERT/UPDATE | Доля времени, затрачиваемая на триггеры. Если выше — оптимизируйте триггерный код. |
| **Replication Lag** | < 5 сек | Наличие тяжёлых триггеров замедляет фиксацию транзакций, что влияет на лаг репликации. |
| **Lock Wait Time** | P95 < 100 мс | Время ожидания блокировки внутри триггера. Высокие значения указывают на дедлоки или конкуренцию. |
| **Event Scheduler Lag** | 0 отставших событий | Количество событий, которые не запустились по расписанию. Проверяйте `LAST_EXECUTED` в `information_schema.EVENTS` (в MariaDB — `last_executed` в `mysql.event`); значение `NULL` означает, что событие ещё ни разу не выполнялось, а `LAST_EXECUTED` фиксирует момент **старта**, а не завершения. |

## Operational Runbook: Анализ проблем с хранимыми объектами

1.  **Быстрая проверка (5 минут):**
    - `SELECT count(*) FROM pg_stat_activity WHERE state = 'active';` — нет ли зависших процедур?
    - `SELECT * FROM pg_locks WHERE granted = false;` — нет ли дедлоков?
    - `SHOW PROCESSLIST` / `SELECT * FROM information_schema.processlist;` — какие запросы выполняются?

2.  **Диагностика (30 минут):**
    - `SELECT * FROM pg_stat_user_functions ORDER BY total_time DESC LIMIT 10;` — какие функции самые тяжёлые?
    - `SELECT * FROM performance_schema.events_statements_summary_by_program ORDER BY avg_timer_wait DESC LIMIT 10;` — MariaDB/MySQL аналоги.
    - Проверка `n_live_tup` и `n_dead_tup` в `pg_stat_user_tables` — не вызывает ли триггер раздувание таблиц?
    - `SHOW SLAVE STATUS` / `pg_stat_replication` — каков текущий лаг репликации?

3.  **Корректировка (1-2 часа):**
    - `ALTER FUNCTION ... SET statement_timeout = '30s';` — ограничение времени выполнения.
    - `DROP TRIGGER ...;` — отключение проблемного триггера с последующим исправлением.
    - `ALTER EVENT ... DISABLE;` — отключение проблемного события.
    - Принудительный `ROLLBACK` зависших транзакций (с подтверждением, что они не активны).

4.  **Валидация:**
    - Запуск тестового вызова процедуры и проверка времени выполнения.
    - Сравнение `count(*)` до и после операции триггера.
    - Настройка алертов на `procedure_duration_p95 > 500ms` и `replication_lag > 10s`.

## Управление версиями и расписанием

Два аспекта эксплуатации, которые не относятся к синтаксису объекта, но ломают
эксплуатацию чаще всего: **как объект попадает на сервер** и **как задание
запускается по расписанию**.

### Версионированный rollout

Хранимый объект — исполняемый код, который меняется независимо от схемы, поэтому
его диффы не видны ни в миграциях схемы, ни в сравнении таблиц. Практический
приём — хранить тело объекта как текст в Git и применять идемпотентно:

```sql
-- PostgreSQL: тело — единственный источник истины, применение безопасно повторять
CREATE OR REPLACE FUNCTION app.get_customer_stats(p_customer_id INTEGER)
RETURNS NUMERIC AS $fn$
    SELECT COALESCE(SUM(total_spent), 0) FROM orders
    WHERE customer_id = p_customer_id;
$fn$ LANGUAGE sql STABLE;

-- MariaDB: замена тела с сохранением прав
CREATE OR REPLACE FUNCTION get_customer_stats(p_customer_id INT)
RETURNS DECIMAL(12,2) DETERMINISTIC READS SQL DATA
RETURN (SELECT COALESCE(SUM(total_spent), 0) FROM orders WHERE customer_id = p_customer_id);

-- MySQL: шага замены тела нет — только пересоздание
DROP PROCEDURE IF EXISTS sp_customer_stats;
CREATE PROCEDURE sp_customer_stats(IN p_customer_id INT)
BEGIN
    DECLARE v_total DECIMAL(12,2);
    SELECT COALESCE(SUM(total_spent), 0) INTO v_total
    FROM orders WHERE customer_id = p_customer_id;
    SELECT v_total;
END;
```

Ключевое различие, из которого следует вся стратегия деплоя: `CREATE OR
REPLACE` есть в PostgreSQL и MariaDB, но **не работает в MySQL**, где любая
замена тела — это `DROP` + `CREATE`, то есть объект на короткое время исчезает,
а его привилегии снимаются. Планируйте окно недоступности и пересоздание
привилегий явно. Полный разбор, включая `pg_get_functiondef`, сравнение с
`information_schema.ROUTINES`, версионирование через `pg_extension` и
спецслучай `CREATE OR REPLACE FUNCTION` с `SET`-опциями, — в
[Управление изменениями](stored_objects/change_management.md).

### Дрейф расписания

Расписание — такой же частьчно независимый объект, как и тело функции, и оно
деградирует незаметно:

- `cron.schedule` в `pg_cron` **пересоздаёт** задание: если передать то же
  `jobname` повторно, будет создан **дубль**, а не обновление. Планируйте
  `cron.unschedule(...)`, затем `cron.schedule(...)` в одной паре шагов.
- Переменные `cron.*` хранятся в обычных таблицах схемы `cron`, а не в
  системном каталоге, — они переживают `pg_dump --schema-only`, но теряются при
  пересоздании экземпляра, если схема не перенесена. Для планирования резервного
  копирования см. [maintenance_automation.md](../PostgreSQL/Operations/maintenance_automation.md).
- У события `ON COMPLETION DROP` (значение по умолчанию для события без явного
  `ON COMPLETION`) удаляет объект после однократного выполнения. Событие
  пропадёт из `information_schema.EVENTS`, и это будет выглядеть как «задание
  потерялось», хотя оно просто отработало. Для одноразовых работ это удобно, но
  для наблюдаемости лучше `ON COMPLETION PRESERVE`.

## Восстановление после сбоев (Recovery)

### Откат изменений хранимых объектов

Если хранимый объект вызвал деградацию или некорректные данные:

- **PostgreSQL:** Используйте `CREATE OR REPLACE FUNCTION` или `CREATE OR REPLACE PROCEDURE` для быстрого отката на предыдущую версию. Если объект был удалён — восстановите из Git. Для триггеров: `DROP TRIGGER ...; CREATE TRIGGER ...;`.
- **MariaDB:** `CREATE OR REPLACE PROCEDURE`/`FUNCTION` меняет тело и параметры, сохраняя права и владельца. Полную замену сигнатуры делайте через `DROP` + `CREATE`.
- **MySQL:** операции `ALTER PROCEDURE`/`ALTER FUNCTION` не меняют тело и параметры — только перечислимые атрибуты. Замена кода требует `DROP` + `CREATE`. Для событий: `DROP EVENT ...; CREATE EVENT ...;`.
- **Важно про привилегии при пересоздании:** удаление routine снимает специфичные привилегии (`EXECUTE`, `ALTER ROUTINE`, `GRANT OPTION`), и `CREATE` их не восстанавливает. При `automatic_sp_privileges = ON` их автоматически получает только создатель routine. Подробнее — в [Управление изменениями](stored_objects/change_management.md).

### Восстановление после рекурсии триггеров

Если триггер вызвал бесконечную рекурсию:

1.  **PostgreSQL:** Завершите сессию, выполнившую триггер: `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'active' AND query LIKE '%триггер_name%';`. Затем отключите триггер: `DROP TRIGGER trg_name ON table_name;`.
2.  **MariaDB/MySQL:** `KILL <thread_id>; DROP TRIGGER trg_name;`.

### Проверка консистентности после массовой операции

- **PostgreSQL:** `SELECT count(*) FROM audit_log WHERE changed_at > now() - interval '1 hour';` — проверка активности аудита.
- **MySQL:** `CHECKSUM TABLE audit_log;` до и после операции.

## Лучшие практики

1.  **Используйте имённые схемы для хранимых объектов:** В PostgreSQL создавайте отдельную схему (`CREATE SCHEMA stored_procs;`) для процедур, функций и триггеров. Это упрощает резервное копирование и управление привилегиями.
2.  **Ограничьте время жизни транзакции в триггерах:** Длительные триггеры блокируют запись и репликацию. Настройте `statement_timeout` и `lock_timeout` на уровне сессии.
3.  **Избегайте `SECURITY DEFINER` без необходимости:** Используйте `SECURITY DEFINER` только когда объект должен иметь повышенные привилегии. По умолчанию используйте `SECURITY INVOKER`.
4.  **Тестируйте отказы в staging:** Регулярно прерывайте процедуры/триггеры в staging (kill -9, падение сети) и проверяйте, что база остается консистентной.
5.  **Документируйте зависимости:** Для каждого триггера указывайте, на каких таблицах он находится и какие объекты вызывает. Это упрощает отладку и impacto анализа при изменениях.
6.  **Выбирайте планировщик по модели безопасности, а не «по удобству»:** `pg_cron` выполняет задания внутри сервера, отдельным рабочим процессом — сессия пользователя не участвует и ничего не блокирует. Цена — установка расширения и запуск от суперпользователя. Внешний планировщик (`cron` + `psql`) сессию тоже не занимает, зато требует хранения учётных данных в `.pgpass`/`.my.cnf` и не переживает переезд инсталляции. Если суперпользователь недоступен, внешний планировщик — единственный вариант, а не компромисс.
7.  **Настройка `event_scheduler` в MariaDB/MySQL:** задавайте `event_scheduler = ON` в `my.cnf` явно и не полагайтесь на дефолт, потому что **дефолты у движков различаются**: в MySQL 8.0 значение по умолчанию — `ON`, в MariaDB — `OFF`. Ошибки и историю выполнений смотрите в `SHOW EVENTS` и `information_schema.EVENTS`. Значение `DISABLED` задаётся только при старте сервера и не меняется на лету — в отличие от `OFF`, который управляется через `SET GLOBAL`.
8.  **Мониторинг `pg_stat_progress_vacuum`:** в PostgreSQL используйте этот view для отслеживания прогресса `VACUUM` во время массовых операций, вызванных триггерами.
9.  **Используйте `pg_repack` для устранения bloat:** Если триггер вызывает активное раздувание таблицы, `pg_repack` пересоздает таблицу онлайн, без блокировок `ACCESS EXCLUSIVE`.
10. **Версионирование через Git:** Для каждого хранимого объекта храните скрипт создания и миграции в Git. Это позволяет быстро откатить изменения и отслеживать историю.

## Особые случаи и ограничения (Edge Cases)

1.  **Бесконечная рекурсия триггеров:** Если триггер на таблице A вызывает `INSERT` в таблицу B, на которой есть триггер, вызывающий `INSERT` в таблицу A — возникает бесконечный цикл. Ограничьте глубину рекурсии или используйте флаги (`SET session_replication_role = 'replica'`) для отключения триггеров во время миграций.
2.  **Вложенность вызовов:** В PostgreSQL глубина вложенности ограничена `max_stack_depth` (по умолчанию 2 MB). При превышении возникает ошибка `stack depth limit exceeded`. Увеличьте параметр или рефакторите код.
3.  **Влияние на реплики:** поведение триггеров на реплике зависит от формата репликации, и это редко совпадает с ожиданиями. В MySQL при statement-based репликации триггеры, отработавшие на источнике, **выполняются и на реплике**; при row-based (`binlog_format=ROW`, значение по умолчанию) триггеры на реплике **не выполняются вовсе** — реплика применяет уже готовые изменения строк, порождённые триггером на источнике. Причина — иначе изменения применились бы дважды. Если триггеры должны работать на обеих сторонах, нужен statement-based формат, хотя бы для тех запросов, где это важно. Отставание реплики при этом лечится настройкой числа applier-потоков: `replica_parallel_workers` в MySQL (`slave_parallel_workers` объявлен устаревшим начиная с 8.0.26; по умолчанию 4 с 8.0.27) и `max_parallel_workers` / `max_parallel_apply_workers` в PostgreSQL.
4.  **Взаимодействие с Foreign Keys:** `SET session_replication_role = 'replica'` подавляет триггеры и правила, настроенные на поведение реплики, **и одновременно отключает проверку внешних ключей** — constraint-триггеры FK являются внутренними и тоже не срабатывают. Это делает операцию намного быстрее, но снимает защиту от ссылочной несогласованности. Включайте режим только на время загрузки и только если данные уже проверены; не забывайте вернуть `session_replication_role = 'origin'` в той же транзакции.
5.  **Очень большие события:** в MariaDB/MySQL **штатного ограничения длительности выполнения события нет**, и это регулярно всплывает в конфигурациях. `max_execution_time` в MySQL применяется только к read-only `SELECT` и, по документации, **игнорируется для `SELECT` внутри stored programs** — событие является stored program, поэтому ограничение на него не действует. В MariaDB `max_statement_time` действует на все типы запросов, но с тем же исключением: он **не распространяется на операторы внутри stored procedures**. Практический вывод: длительность события ограничивайте сами — проверяйте `LAST_EXECUTED` против ожидаемого времени старта, убивайте зависшие события по `PROCESSLIST.ID` или выносите задание во внешний планировщик (`cron` + `mysql`/`psql` CLI), где таймаут задаётся на стороне вызывающего процесса. Подробнее — в [Мониторинг](stored_objects/monitoring.md).
6.  **Ограничение `max_prepared_transactions` (PostgreSQL):** Если в процессе массовой операции используется 2PC, убедитесь, что `max_prepared_transactions > 0` (по умолчанию 0). Рекомендуемое значение: `max_connections * количество_участников`.
7.  **Влияние на WAL/Binlog:** Каждый вызов хранимого объекта генерирует WAL/Binlog. При частых вызовах это может переполнить диск и замедлить репликацию. Мониторьте размер WAL-файлов.
8.  **Объекты, «работающие только на primary»:** в PostgreSQL функция с признаком `VOLATILE` может быть вызвана на standby (только чтение), но любой её `INSERT`/`UPDATE` там отвергнут: соединения в hot standby строго read-only, писать нельзя даже во временные таблицы. Разделяйте read-only и write-версии объекта либо метите read-only вариант как `STABLE`. См. [Troubleshooting](stored_objects/troubleshooting.md).

## Дополнительная информация

### Тюнинг параметров для хранимых объектов

**PostgreSQL:**

```sql
-- Включение сбора статистики по функциям
ALTER SYSTEM SET track_functions = 'all';  -- 'none', 'pl', 'all'

-- Ограничение времени выполнения функции
ALTER FUNCTION fn_calculate_discount(INTEGER)
  SET statement_timeout = '30s';

-- ВАЖНО: SET-клаузу нельзя вешать на процедуру, которая внутри тела
-- делает COMMIT/ROLLBACK, — такая процедура просто перестанет управлять
-- транзакциями. Для неё таймаут задаётся внутри тела:
--   SET LOCAL statement_timeout = '30s';
```

**MariaDB/MySQL:**

```sql
-- Включение event scheduler
SET GLOBAL event_scheduler = ON;
-- Или в my.cnf:
-- [mysqld]
-- event_scheduler = ON

-- Сохранение объекта события в information_schema после выполнения
-- (ON COMPLETION PRESERVE; по умолчанию для одноразового события — DROP)
ALTER EVENT evt_cleanup_logs
  ON COMPLETION PRESERVE
  ENABLE;
```

Обратите внимание: `ON COMPLETION PRESERVE` — это про сохранение определения
события после выполнения, а **не** про ограничение времени выполнения. Штатного
таймаута длительности события в MariaDB/MySQL нет — см. пункт 5 в разделе
[Особые случаи и ограничения](#особые-случаи-и-ограничения-edge-cases).

### Мониторинг и SRE-метрики

При эксплуатации хранимых объектов необходимо отслеживать:

1.  **Procedure Duration (avg):** Среднее и P95 время выполнения процедур. Рост указывает на неоптимизированный SQL.
2.  **Procedure Calls/sec:** Количество вызовов в секунду. Резкий рост может указывать на рекурсию.
3.  **Trigger Overhead:** Доля времени, затрачиваемая на триггеры. Если > 5% — оптимизируйте триггерный код.
4.  **Replication Lag:** Триггеры замедляют фиксацию транзакций, что влияет на лаг репликации.
5.  **Lock Wait Time:** Время ожидания блокировки внутри триггера. Высокие значения указывают на дедлоки.
6.  **Event Scheduler Lag:** Количество отставших событий. Проверяйте `LAST_EXECUTED` в `information_schema.EVENTS` (в MariaDB — `last_executed` в `mysql.event`).

### Постобработка

После изменения хранимых объектов:

- **PostgreSQL:** `ANALYZE;` для обновления статистики после массовых изменений через процедуры.
- **MySQL:** `ANALYZE TABLE table_name;` (обновляет индексы).
