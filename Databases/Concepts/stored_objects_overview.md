# Хранимые объекты в БД: Процедуры, Функции, Триггеры и События

## Определения

*   **Хранимый объект (Stored Object)** — программный код (логика), который сохраняется внутри базы данных и выполняется сервером СУБД. Объект компилируется (или парсится) при создании и хранится в системном каталоге, что позволяет повторно использовать его без передачи текста запроса по сети.
*   **Хранимая процедура (Stored Procedure)** — набор SQL-инструкций и управляющих конструкций, который может выполнять произвольную логику, не возвращая значения (хотя может выводить параметры). Поддерживает управление транзакциями (`COMMIT/ROLLBACK`) и имеет собственный контекст выполнения.
*   **Функция (Function)** — объект, который **обязательно возвращает значение** (скалярное, строку или таблицу). Может использоваться в выражениях `SELECT`, `WHERE`, `JOIN`. В большинстве СУБД не может управлять транзакциями (делать `COMMIT/ROLLBACK` внутри тела).
*   **Триггер (Trigger)** — процедура, которая **автоматически** запускается при наступлении определённого события на таблице или представлении (`INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, а в некоторых СУБД — DDL-события). Работает в контексте транзакции вызвавшего её оператора.
*   **Событие (Event / Cron Job)** — запланированная задача, выполняемая сервером БД по расписанию (аналог `cron`). Позволяет запускать процедуры или SQL-блоки в фоне, без подключения клиента.

### Сравнительная таблица

| Критерий | Хранимая процедура | Функция | Триггер | Событие |
|---|---|---|---|---|
| Возвращает значение | Нет (только OUTPUT-параметры) | Да (обязательно) | Нет | Нет |
| Управление транзакциями | Да (`COMMIT`/`ROLLBACK`) | Обычно нет | В контексте родительской транзакции | Да (своя транзакция) |
| Вызывается из SQL | `CALL` / `EXEC` | В выражениях `SELECT` | Автоматически | По расписанию |
| Привязка к таблице | Нет | Нет | Да | Нет |
| Типичное применение | Пакетная обработка, ETL, администрирование | Вычисления, валидация, вспомогательные запросы | Аудит, целостность, репликация на уровне БД | Ротация логов, очистка, агрегация |

## Базовые концепции

### Зачем использовать хранимую логику?

1.  **Снижение сетевого трафика:** Вместо пересылки больших объёмов данных приложению для обработки, логика выполняется максимально близко к данным. Один `CALL` заменяет десятки запросов.
2.  **Безопасность:** Можно запретить прямой доступ к таблицам, разрешив только выполнение процедур (инкапсуляция). Пользователь не знает структуру таблиц и не может модифицировать данные напрямую. Подробнее: [Безопасность хранимых объектов](./stored_objects/security.md).
3.  **Консистентность:** Триггеры гарантируют выполнение правил целостности **независимо** от того, какое приложение изменяет данные — будь то веб-интерфейс, CLI-утилита или миграционный скрипт.
4.  **Переиспользование:** Логика, оформленная как хранимый объект, доступна всем клиентам (приложениям, отчётам, ETL-процессам) без дублирования кода.
5.  **Производительность (в некоторых сценариях):** Предкомпилированный план выполнения хранимой процедуры может быть эффективнее ad-hoc-запросов, особенно в MariaDB/MySQL, где отсутствует prepared statement cache для сложных пакетов.

### Модель выполнения

**Контекст выполнения (Execution Context):**

Каждый хранимый объект выполняется в собственном контексте, который включает:
- **Переменные:** Локальные переменные, параметры входа/выхода.
- **Обработка ошибок:** Блоки `EXCEPTION` (PL/pgSQL), `DECLARE ... HANDLER` (MySQL/MariaDB).
- **Последовательность инструкций:** Пошаговое выполнение SQL и управляющего кода.
- **Доступ к данным:** Через SQL-запросы внутри тела объекта.

**Консистентность чтения (Read Consistency):**

- В PostgreSQL каждая функция/процедура выполняется в **snapshot**那一刻的 транзакции. Если транзакция изменила данные до вызова функции, функция видит эти изменения.
- В MariaDB/MySQL (InnoDB) используется **MVCC**: функция видит данные на момент начала транзакции, в которой она вызвана.

**Уровень изоляции:**

Хранимые объекты выполняются на уровне изоляции **родительской транзакции**. Если транзакция неявная (autocommit), каждый SQL-оператор внутри объекта — отдельная транзакция.

### Механизм кэширования планов

При первом вызове хранимого объекта СУБД парсит и компилирует его, создавая план выполнения. Этот план кэшируется:
- **PostgreSQL:** План кэшируется в памяти процесса на время жизни сессии (prepared statements) или на время жизни объекта (для простых функций SQL).
- **MariaDB/MySQL:** План кэшируется в **query cache** (deprecated в 8.0) или через **prepared statements**. Хранимые процедуры используют **stored procedure cache**.
- **При изменении объекта** (`ALTER`, `CREATE OR REPLACE`) кэш инвалидируется и план пересоздаётся при следующем вызове.

### SRE-риски и недостатки

*   **Скрытая нагрузка:** Логика в БД потребляет CPU и RAM сервера базы данных, который сложнее масштабировать горизонтально, чем уровень приложения. Тяжёлые вычисления в триггерах могут замедлить все операции записи.
*   **Сложность отладки:** Инструменты отладки внутри БД значительно слабее современных IDE. Нет нормального step-through, conditional breakpoints, inspection переменных в реальном времени.
*   **Проблемы с CI/CD:** Хранимый код сложнее версионировать, тестировать (Unit-тесты) и деплоить без простоя. Требуются специализированные инструменты миграций (Flyway, Liquibase, Atlas).
*   **Блокировки:** Неоптимизированные триггеры могут вызывать длительные блокировки строк, парализуя запись. Особенно `BEFORE UPDATE` триггеры, которые выполняют дополнительные SELECT/INSERT.
*   **Версионирование и откат:** Откат изменений в хранимых объектах сложнее, чем в приложенческом коде — требуется отдельная миграция.
*   **Debug в production:** Логирование и трассировка в production-среде ограничены соображениями производительности и безопасности.

## Детализация по типам объектов

### Хранимые процедуры

**Назначение:** Пакетная обработка данных, администрирование БД, ETL-процессы, сложные бизнес-операции, требующие управления транзакциями.

**Характеристики:**
- Не возвращают значение напрямую (в PostgreSQL `PROCEDURE` поддерживает `COMMIT/ROLLBACK` внутри тела, а `FUNCTION` — нет).
- Могут принимать входные и выходные параметры.
- Вызываются через `CALL procedure_name(args)` (PostgreSQL 11+, MariaDB 10.3+) или `EXEC procedure_name(args)` (SQL Server).
- Могут содержать управляющие конструкции: циклы, условия, обработку ошибок.

**Управление транзакциями:**
- `PROCEDURE` в PostgreSQL может выполнять `COMMIT` и `ROLLBACK` внутри тела — это ключевое отличие от `FUNCTION`.
- Это позволяет разбивать долгие операции на части, делая промежуточные данные видимыми другим сессиям.
- В MariaDB/MySQL `PROCEDURE` также поддерживает `COMMIT`/`ROLLBACK`.

**Пример (PostgreSQL):**

```sql
-- Процедура для пакетного обновления статусов заказов
CREATE OR REPLACE PROCEDURE update_order_statuses(
    p_batch_size INT DEFAULT 1000
)
LANGUAGE plpgsql
AS $$
DECLARE
    v_updated INT;
BEGIN
    LOOP
        UPDATE orders
        SET status = 'processed'
        WHERE id IN (
            SELECT id FROM orders
            WHERE status = 'pending'
            LIMIT p_batch_size
        );

        GET DIAGNOSTICS v_updated = ROW_COUNT;
        EXIT WHEN v_updated = 0;

        COMMIT;  -- Промежуточный коммит: данные видны другим сессиям
        RAISE NOTICE 'Обновлено % заказов', v_updated;
    END LOOP;
END;
$$;

-- Вызов
CALL update_order_statuses(500);
-- → NOTICE: Обновлено 500 заказов
-- → NOTICE: Обновлено 500 заказов
-- → NOTICE: Обновлено 237 заказов
```

### Функции

**Назначение:** Вычисления, валидация данных, вспомогательные запросы, использование в SQL-выражениях.

**Характеристики:**
- **Обязательно** возвращают значение (`RETURNS` в PostgreSQL, `RETURNS` в MariaDB).
- Могут быть **скалярными** (возвращают одно значение) или **табличными** (возвращают набор строк).
- Используются в `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `ORDER BY`.
- В PostgreSQL могут быть написаны на `PL/pgSQL`, `SQL`, `PL/Python`, `PL/V8` и др.
- В MariaDB/MySQL — на `SQL`, `C` (плагины), `Lua` (MariaDB).

**Волатильность (PostgreSQL):**

PostgreSQL позволяет указать **volatility category** для оптимизации:
- `IMMUTABLE` — одинаковый результат при одинаковых аргументах (например, `sqrt(4)`). Кэшируется планировщиком.
- `STABLE` — одинаковый результат в пределах одного запроса (например, `current_date`). Не пересчитывается при вызове в цикле.
- `VOLATILE` (по умолчанию) — результат может меняться между вызовами (например, `random()`, `now()`). Не кэшируется.

### Триггеры

**Назначение:** Обеспечение целостности данных на уровне БД, аудит изменений, автоматическое обновление производных данных, репликация на уровне БД.

**Характеристики:**
- Привязаны к конкретной **таблице** или **представлению**.
- Срабатывают **автоматически** при `INSERT`, `UPDATE`, `DELETE` (и `TRUNCATE` в PostgreSQL).
- Работают в контексте транзакции вызвавшего её оператора.
- Могут быть **BEFORE** (до изменения) или **AFTER** (после изменения).
- В PostgreSQL также поддерживаются **INSTEAD OF** (для представлений) и **CONSTRAINT** триггеры (для проверки `FOREIGN KEY`).

**Типы триггеров по时机:**

| Тип | Назначение | Транзакция видна? | Типичное использование |
|---|---|---|---|
| `BEFORE INSERT` | Модифицировать данные до вставки | Нет (ещё не вставлены) | Заполнение значений по умолчанию, валидация |
| `BEFORE UPDATE` | Модифицировать данные до обновления | Да (старые данные видны) | Защита от изменения критичных полей, аудит |
| `BEFORE DELETE` | Действия перед удалением | Да | Архивирование перед удалением, каскадная логика |
| `AFTER INSERT` | Действия после вставки | Да | Обновление агрегатов, логирование |
| `AFTER UPDATE` | Действия после обновления | Да | Синхронизация производных данных |
| `AFTER DELETE` | Действия после удаления | Да | Очистка связанных данных, логирование |
| `INSTEAD OF` | Заменяет операцию (PostgreSQL) | Зависит от логики | Обновление представлений |
| `CONSTRAINT` | Проверка ограничений (PostgreSQL) | Да | Сложные проверки `FOREIGN KEY` |

**Триггерная функция vs триггер (PostgreSQL):**

В PostgreSQL триггер и функция — это **разные объекты**:
1. **Функция** определяет **что** делать (логику).
2. **Триггер** определяет **когда** и **на каком событии** вызывать функцию.

Одна функция может использоваться несколькими триггерами на разных таблицах.

```sql
-- 1. Функция-обработчик (логика)
CREATE OR REPLACE FUNCTION audit_changes()
RETURNS TRIGGER
LANGUAGE plpgsql
AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        INSERT INTO audit_log (table_name, operation, new_data, changed_at)
        VALUES (TG_TABLE_NAME, 'INSERT', row_to_json(NEW), NOW());
        RETURN NEW;
    ELSIF TG_OP = 'UPDATE' THEN
        INSERT INTO audit_log (table_name, operation, old_data, new_data, changed_at)
        VALUES (TG_TABLE_NAME, 'UPDATE', row_to_json(OLD), row_to_json(NEW), NOW());
        RETURN NEW;
    ELSIF TG_OP = 'DELETE' THEN
        INSERT INTO audit_log (table_name, operation, old_data, changed_at)
        VALUES (TG_TABLE_NAME, 'DELETE', row_to_json(OLD), NOW());
        RETURN OLD;
    END IF;
END;
$$;

-- 2. Триггер (привязка к событию)
CREATE TRIGGER trg_orders_audit
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH ROW
EXECUTE FUNCTION audit_changes();
```

**Контекстные переменные (PostgreSQL):**

| Переменная | Описание |
|---|---|
| `NEW` | Новая строка (для INSERT/UPDATE) |
| `OLD` | Старая строка (для UPDATE/DELETE) |
| `TG_OP` | Операция: `'INSERT'`, `'UPDATE'`, `'DELETE'`, `'TRUNCATE'` |
| `TG_TABLE_NAME` | Имя таблицы |
| `TG_TABLE_SCHEMA` | Имя схемы |
| `TG_WHEN` | `'BEFORE'` или `'AFTER'` |
| `TG_LEVEL` | `'ROW'` или `'STATEMENT'` |
| `TG_ARGV[]` | Аргументы, переданные в триггер |

### События (Event Scheduler)

**Назначение:** Фоновые задачи по расписанию: ротация логов, очистка временных данных, агрегация, отправка отчётов.

**Характеристики:**
- Выполняются **без подключения клиента** — сервер БД сам запускает задачу.
- Поддерживают выражения `AT` (одноразово) и `EVERY` (периодически).
- В MariaDB/MySQL встроен **Event Scheduler** (аналог `cron`).
- В PostgreSQL нет встроенного планировщика — используют `pg_cron`, `pgagent` или внешние планировщики.

## Сравнение возможностей по СУБД

| Особенность | PostgreSQL | MariaDB/MySQL | SQL Server |
|---|---|---|---|
| `COMMIT` внутри процедуры | Да (PROCEDURE) | Да | Да |
| Триггер на представлении | `INSTEAD OF` | Нет | `INSTEAD OF` |
| Триггер на DDL | Да (event triggers) | Нет | DDL триггеры |
| Вложенность триггеров | Ограничена `max_stack_depth` | Ограничена | Ограничена |
| Пакетная обработка | `FOR UPDATE SKIP LOCKED` | `LIMIT` в подзапросе | `TOP ... WITH (ROWLOCK)` |
| Динамический SQL | `EXECUTE` (PL/pgSQL) | Prepared statements | `sp_executesql` |
| Табличные функции | `RETURNS SETOF` / `RETURNS TABLE` | `RETURNS TABLE` | Table-valued functions |
| Триггеры на `TRUNCATE` | Да | Нет | Да |
| Возврат `NULL` из `BEFORE DELETE` | Ошибка | Ошибка | Ошибка |

## Рекомендации SRE по эксплуатации

1.  **Логирование:** Используйте встроенные механизмы (`RAISE NOTICE/LOG` в Postgres, таблицу логов в MariaDB) для отслеживания хода выполнения тяжёлых процедур. Не используйте `RAISE EXCEPTION` для логирования — это прерывает выполнение.
2.  **Таймауты:** Всегда устанавливайте локальные таймауты внутри процедур, чтобы избежать "зависания" сессий. В PostgreSQL: `statement_timeout` на уровне сессии; в MariaDB: `max_execution_time`.
3.  **Версионирование:** Храните исходный код всех объектов в Git. Используйте инструменты миграций (Flyway, Liquibase, Atlas) для их развёртывания. Никогда не изменяйте объекты вручную в production.
4.  **Мониторинг:** Отслеживайте время выполнения процедур через системные представления. Подробнее: [Мониторинг хранимых объектов](./stored_objects/monitoring.md).
5.  **Тестирование:** Тестируйте хранимые объекты отдельно от приложения. Используйте `pg_prove` (PostgreSQL) или `MySQL Test Runner` (MariaDB/MySQL) для unit-тестов.
6.  **Именование:** Используйте консистентные префиксы: `fn_` для функций, `sp_` или `proc_` для процедур, `trg_` для триггеров, `evt_` для событий.
7.  **Не трогайте данные напрямую:** Если данные изменены некорректно, не используйте триггер для "исправления" — это может привести к рекурсии. Исправляйте данные через `UPDATE` с фильтрацией.
