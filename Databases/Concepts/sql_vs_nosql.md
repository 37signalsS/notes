# Сравнение SQL и NoSQL

## Определения

- **SQL (Structured Query Language)** — язык структурированных запросов. Реляционные базы данных хранят данные в строго структурированном виде (таблицы, строки, колонки).
  - **Примеры:** MySQL, PostgreSQL, Microsoft SQL Server, Oracle.

- **NoSQL (Not Only SQL)** — "не только SQL". Нереляционные базы данных предлагают более гибкие модели хранения данных.
  - **Примеры:** MongoDB, Cassandra, Redis, CouchDB, Neo4j.

## Основные концепции

Ключевое архитектурное различие между SQL и NoSQL системами в распределенной среде объясняется через **[CAP-теорему (Consistency, Availability, Partition tolerance)](./cap_theorem.md)**. Теорема утверждает, что распределенная система может гарантировать только два из трех свойств: **Согласованность (C)**, **Доступность (A)** и **Устойчивость к разделению (P)**.

- **Традиционные SQL-системы (в кластере):** Чаще всего являются **CP-системами**. Они выбирают **согласованность** данных в ущерб доступности. В случае сбоя сети система скорее откажет в запросе, чем вернет некорректные данные. Это делает их идеальными для финансовых и транзакционных систем, где целостность данных имеет высший приоритет.

- **Классические NoSQL-системы:** Чаще всего являются **AP-системами**. Они выбирают **доступность** в ущерб строгой согласованности. Система всегда будет отвечать на запросы, даже если данные могут быть временно устаревшими. Это подходит для больших систем, таких как социальные сети или аналитика, где простой в обслуживании более критичен, чем мгновенная согласованность.

### Сравнительная таблица

| Критерий | SQL (Реляционные) | NoSQL (Нереляционные) |
| :--- | :--- | :--- |
| **Модель данных** | Таблицы со строками и колонками. Связи через внешние ключи (JOINs). | Разнообразные: Документы (JSON/BSON), Ключ-значение, Колоночные, Графовые. Часто избегают JOIN'ов. |
| **Схема** | **Строгая (schema-on-write):** структура данных определяется заранее. | **Гибкая (schema-on-read):** документы в одной коллекции могут иметь разную структуру. |
| **Масштабируемость** | **Вертикальное (Vertical Scaling):** Увеличение мощности одного сервера (CPU, RAM). | **Горизонтальное (Horizontal Scaling):** Распределение нагрузки на множество серверов (шардинг). |
| **Язык запросов** | **SQL** — стандартизированный и мощный язык для сложных запросов. | У каждой СУБД свой язык или API. Запросы часто менее гибкие, чем в SQL. |
| **Согласованность** | **ACID-транзакции:** Гарантируют надежность и строгую согласованность. См. **[ACID](./acid.md)**. | **BASE-модель (Basically Available, Soft state, Eventual consistency):** Приоритет доступности над согласованностью. |

## Практические сценарии

### Когда выбирать SQL?

1. **Требуется строгая целостность данных:** Финансовые приложения, банковские системы, биллинг, где каждая транзакция критична и требует ACID-гарантий.
2. **Сложные взаимосвязи данных:** Системы, где данные сильно связаны между собой, и требуется выполнение сложных JOIN-операций (например, ERP-системы, системы управления запасами).
3. **Структурированные данные:** Когда структура данных четко определена, редко меняется и соответствует реляционной модели.
4. **Нужны сложные запросы и отчетность:** Аналитические системы, где требуется выполнение комплексных агрегаций, фильтраций и генерация отчетов.

### Когда выбирать NoSQL?

1. **Большие объемы данных и высокая скорость записи/чтения:** Приложения, требующие экстремальной производительности и горизонтального масштабирования (логи, метрики, сессии).
2. **Гибкая структура данных:** Проекты, где схема данных не определена заранее или часто эволюционирует (социальные сети, IoT, профили пользователей).
3. **Быстрая разработка:** Когда скорость вывода нового функционала важнее строгой консистентности (MVP, прототипирование).
4. **Высокая доступность:** Системы, которые не могут позволить себе простои (онлайн-игры, стриминговые сервисы).
5. **Специфические модели данных:**
    - **Документоориентированные (MongoDB):** Для хранения сложных объектов с разным набором атрибутов.
    - **Ключ-значение (Redis, Memcached):** Для сверхбыстрого доступа к данным (кэширование, сессии).
    - **Колоночные (ClickHouse, Cassandra):** Для Big Data аналитики и хранения логов.
    - **Графовые (Neo4j):** Для анализа связей (социальные графы, рекомендации).

## Дополнительная информация

Выбор между SQL и NoSQL редко бывает исключительным. Современная архитектура часто использует гибридный подход (**полиглотная персистентность**), где разные типы данных хранятся в наиболее подходящих для них системах.

**Пример гибридной архитектуры:**

- **PostgreSQL** — критически важные данные (пользователи, транзакции) с **ACID (Atomicity, Consistency, Isolation, Durability)** гарантиями.
- **Redis** — кэширование "горячих" данных и сессий.
- **ClickHouse** — аналитика логов и метрик.
