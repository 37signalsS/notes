# SQL vs. NoSQL: Ключевые различия

## Определения

- **SQL (Реляционные базы данных):** Хранят данные в строго структурированном виде (таблицы, строки, колонки). Языком взаимодействия является SQL (Structured Query Language).
  - **Примеры:** MySQL, PostgreSQL, Microsoft SQL Server, Oracle.

- **NoSQL (Нереляционные базы данных):** Предлагают более гибкие модели хранения данных. Название "NoSQL" означает "Not Only SQL" (не только SQL).
  - **Примеры:** MongoDB, Cassandra, Redis, CouchDB, Neo4j.

## Основные понятия

Ключевое архитектурное различие между SQL и NoSQL системами в распределенной среде объясняется через **[CAP-теорему](./cap_theorem.md)**. Теорема утверждает, что распределенная система может гарантировать только два из трех свойств: **Согласованность (C)**, **Доступность (A)** и **Устойчивость к разделению (P)**.

- **Традиционные SQL-системы (в кластере):** Чаще всего являются **CP-системами**. Они выбирают **согласованность** данных в ущерб доступности. В случае сбоя сети система скорее откажет в запросу, чем вернет некорректные данные. Это делает их идеальными для финансовых и транзакционных систем, где целостность данных имеет высший приоритет.

- **Классические NoSQL-системы:** Чаще всего являются **AP-системами**. Они выбирают **доступность** в ущерб строгой согласованности. Система всегда будет отвечать на запросы, даже если данные могут быть временно устаревшими. Это подходит для больших систем, таких как социальные сети или аналитика, где простой в обслуживании более критичен, чем мгновенная согласованность.

### Сравнительная таблица

| Критерий                  | SQL (Реляционные)                                                              | NoSQL (Нереляционные)                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| **Модель данных**         | Таблицы со строками и колонками. Связи через внешние ключи (JOINs).             | Разнообразные: Документы (JSON/BSON), Ключ-значение, Колоночные, Графовые. Часто избегают JOIN'ов.                |
| **Схема**                 | **Строгая (schema-on-write):** структура данных определяется заранее. | **Гибкая (schema-on-read):** документы в одной коллекции могут иметь разную структуру.                             |
| **Масштабируемость**      | **Вертикальное (Vertical Scaling):** Увеличение мощности одного сервера (CPU, RAM). | **Горизонтальное (Horizontal Scaling):** Распределение нагрузки на множество серверов (шардинг).                  |
| **Язык запросов**         | **SQL** — стандартизированный и мощный язык для сложных запросов.                | У каждой СУБД свой язык или API. Запросы часто менее гибкие, чем в SQL.                                          |
| **Согласованность** | **ACID-транзакции:** Гарантируют надежность и строгую согласованность. См. **[ACID](./acid.md)**. | **BASE-модель (Basically Available, Soft state, Eventual consistency):** Приоритет доступности над согласованностью. |
| **Примеры**               | PostgreSQL, MySQL, Oracle                                                      | MongoDB (документы), Redis (ключ-значение), Cassandra (колонки), Neo4j (граф).                                      |

## Практические сценарии

### Когда выбирать SQL?

1. **Требуется строгая целостность данных:** Финансовые приложения, банковские системы, биллинг, где каждая транзакция критична и требует ACID-гарантий.
2. **Сложные взаимосвязи данных:** Системы, где данные сильно связаны между собой, и требуется выполнение сложных JOIN-операций (например, ERP-системы, системы управления запасами).
3. **Структурированные данные:** Когда структура данных четко определена, редко меняется и соответствует реляционной модели.
4. **Нужны сложные запросы и отчетность:** Аналитические системы, где требуется выполнение комплексных агрегаций, фильтраций и генерация отчетов.

### Когда выбирать NoSQL?

1. **Большие объемы данных и высокая скорость записи/чтения:** Приложения, требующие экстремальной производительности и горизонтального масштабирования, например, для хранения логов, метрик, пользовательских сессий.
2. **Гибкая или постоянно меняющаяся структура данных:** Проекты, где схема данных не определена заранее или часто эволюционирует (например, новые функции в социальных сетях, IoT-устройства с разнообразными датчиками, профили пользователей).
3. **Быстрая разработка и частые изменения в продукте:** Когда скорость вывода нового функционала на рынок важнее строгой консистентности (например, MVP, прототипирование).
4. **Высокая доступность и устойчивость к отказам:** Системы, которые не могут позволить себе простои даже при частичном выходе из строя узлов (например, онлайн-игры, стриминговые сервисы, социальные сети).
5. **Специфические модели данных:**
    - **Документоориентированные (MongoDB):** Для хранения сложных объектов, таких как пользовательские профили или каталоги товаров, где у разных товаров могут быть разные наборы атрибутов (например, у утюга — мощность, а у футболки — размер и цвет).
    - **Ключ-значение (Redis, Memcached, DynamoDB):** Для сверхбыстрого доступа к данным (часто хранятся in-memory). Идеально для кэширования, хранения сессий, конфигураций или счетчиков (например, лайков). Важно помнить, что данные в таких системах часто хранятся в оперативной памяти и могут быть утеряны при перезагрузке, если не настроена персистентность.
    - **Колоночные (ClickHouse, Cassandra, HBase):** Для Big Data аналитики, хранения логов и событий (например, действий пользователей за несколько лет). Позволяют выполнять агрегирующие запросы по миллиардам записей за доли секунды.
    - **Графовые (Neo4j):** Для задач, связанных с анализом связей (социальные графы, системы рекомендаций).

## Дополнительная информация: Полиглотная персистентность

Выбор между SQL и NoSQL редко бывает черно-белым. **Правильная современная архитектура — это почти всегда гибрид**, где разные типы данных хранятся в наиболее подходящих для них системах. Не стоит использовать один инструмент для всех задач ("не забивать гвозди микроскопом").

**Пример зрелой архитектуры:**

- **PostgreSQL** хранит основные, критически важные данные (пользователи, заказы, транзакции).
- **Redis** используется для кэширования "горячих" данных, сессий и быстрых счетчиков.
- **ClickHouse** анализирует историю действий, логов и метрик.
