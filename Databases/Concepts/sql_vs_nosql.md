# Сравнение SQL, NoSQL и NewSQL

## Определения

- **SQL (Relational Databases)** — системы, основанные на реляционной модели данных и использующие язык запросов SQL. Данные хранятся в строго структурированных таблицах с заранее определенными связями.
  - **Примеры:** PostgreSQL, MySQL, MariaDB, MS SQL Server.
- **NoSQL (Non-relational Databases)** — "Not Only SQL". Системы, использующие гибкие модели данных (документы, графы, ключ-значение) для решения задач высокой доступности и горизонтального масштабирования.
  - **Примеры:** MongoDB (документы), Redis (кэш), Cassandra (колонки), Neo4j (графы).
- **NewSQL (Distributed SQL)** — современное поколение СУБД, которые сочетают в себе горизонтальную масштабируемость NoSQL и гарантии ACID традиционных SQL-систем.
  - **Примеры:** CockroachDB, YugabyteDB, TiDB, Google Spanner.

## Основные концепции

### Сравнительная характеристика

| Критерий | SQL (Традиционные) | NoSQL | NewSQL (Distributed SQL) |
| :--- | :--- | :--- | :--- |
| **Модель данных** | Таблицы (строгая структура) | Гибкая (JSON, Blob, Graph) | Таблицы (строгая структура) |
| **Транзакции** | Строгие ACID | Часто BASE (Eventual) | Строгие ACID |
| **Масштабирование** | Преимущественно вертикальное | Горизонтальное (шардинг) | Горизонтальное (автоматическое) |
| **Join-операции** | Оптимизированы и мощны | Сложны или не поддерживаются | Поддерживаются (распределенные) |
| **Схема** | Schema-on-write | Schema-on-read (гибкая) | Schema-on-write |

### Распределенные системы: CAP и PACELC

Традиционное понимание через **[CAP-теорему](./cap_theorem.md)** (выбор между Consistency и Availability при наличии Partition tolerance) дополняется теоремой **PACELC**:

- **P (Partition):** Если есть разделение сети, выбираем между **A (Availability)** и **C (Consistency)**.
- **E (Else):** В нормальном состоянии (нет разделения) выбираем между **L (Latency)** и **C (Consistency)**.

Это объясняет, почему некоторые NoSQL системы (например, Cassandra) могут быть настроены либо на быстрый ответ с риском устаревших данных, либо на медленный ответ с гарантией свежести.

### Проблема "Schema-less" в NoSQL

Термин "бессхемность" является упрощением. В реальности NoSQL системы используют **Schema-on-read**. Ответственность за структуру данных переносится с БД на уровень приложения. Это дает скорость на старте, но может привести к проблемам с качеством данных при разрастании проекта.

## Практические сценарии

### Когда выбирать SQL (Relational)?
1. **Транзакционные системы:** Финансы, биллинг, бухгалтерия (требуется ACID).
2. **Сложные аналитические отчеты:** Где нужно объединять десятки таблиц через сложные JOIN.
3. **Стабильная структура:** Когда данные хорошо ложатся в таблицы и схема меняется редко.

### Когда выбирать NoSQL?
1. **Высокая скорость записи:** Сбор логов, метрик, IoT-данных.
2. **Кэширование и сессии:** Redis/Memcached для сверхбыстрого доступа.
3. **Неструктурированные данные:** Хранение каталогов товаров с разными атрибутами или профилей пользователей соцсетей.
4. **Графовые задачи:** Рекомендательные системы, анализ связей и мошенничества.

### Когда выбирать NewSQL?
1. **Глобально распределенные приложения:** Когда нужны ACID-транзакции в кластере, разнесенном по разным дата-центрам.
2. **Масштабирование SQL без боли:** Когда PostgreSQL перестал справляться по нагрузке, а переписывать все на NoSQL слишком дорого.
3. **Облачные архитектуры (Cloud-native):** Использование преимуществ эластичности облака для баз данных.

## Дополнительная информация

### Полиглотная персистентность (Polyglot Persistence)

Современный стандарт проектирования — использование нескольких типов БД в одном приложении под разные задачи.

**Пример архитектуры интернет-магазина:**
- **PostgreSQL:** Заказы, пользователи, транзакции (ACID).
- **Elasticsearch:** Поиск по каталогу товаров.
- **MongoDB:** Детальные характеристики товаров (разные атрибуты).
- **Redis:** Корзина покупок, кэш страниц, сессии.
