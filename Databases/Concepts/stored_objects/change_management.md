# Управление изменениями хранимых объектов

**Актуально для:** PostgreSQL 17/18, MariaDB 10.11/11.4, MySQL 8.4 LTS

## Определения

**Rollout** — процесс доведения новой версии объекта до production с контролируемым риском и возможностью отката на каждом шаге.

**Additive change (расширяющее изменение)** — изменение, которое добавляет новый объект или новый вызов, не ломая существующий: старые вызовы продолжают работать.

**Breaking change (ломающее изменение)** — изменение сигнатуры, имени или поведения, после которого существующий код перестаёт работать.

**Expand/contract** — двухфазная схема безопасного изменения: сначала добавить новое рядом со старым (expand), затем перевести вызовы и удалить старое (contract). Между фазами система работает с обеими версиями.

**Дрейф расписания (schedule drift)** — расхождение между определениями запланированных заданий в разных средах: расписание, команда или активность отличаются от ожидаемого эталона.

**Версионированный объект** — объект, в чьём имени или комментарии зафиксирована версия (`fn_calculate_discount_v2`), чтобы старый и новый варианты существовали одновременно.

**Окно недоступности** — интервал, в течение которого объект отсутствует или недоступен для вызова; в MySQL при `DROP` + `CREATE` тела он ненулевой.

**Тихий сброс привилегий** — потеря всех явно выданных на объект привилегий при его удалении, незаметная со стороны кода.

## Основные концепции

### Почему routine менять сложнее, чем таблицу

Таблицу можно менять так, что старое и новое существуют одновременно, и переключение идёт постепенно. С объектом-функцией так работают не все платформы, и именно здесь рождаются инциденты. Три различия, которые определяют процедуру:

| Свойство | PostgreSQL | MariaDB | MySQL |
|---|---|---|---|
| Атомарная замена тела | `CREATE OR REPLACE` | `CREATE OR REPLACE` | невозможна, только `DROP` + `CREATE` |
| Смена сигнатуры | новый объект | новый объект | новый объект |
| Реакция на неверную подпись при изменении тела | отказ, объект не тронут | отказ | объект уже удалён |
| Привилегии при замене тела | сохраняются | сохраняются | **теряются** |

Строка «реакция на неверную подпись» — ключевая. В MySQL последовательность `DROP PROCEDURE p; CREATE PROCEDURE p ...` неатомарна: если `CREATE` падает из-за синтаксической ошибки в теле, процедура уже удалена и восстановления нет. Это не теоретическая проблема — такой сценарий зафиксирован как давний запрос на доработку в трекере ошибок MySQL, где описаны реальные остановки обслуживания из-за связки `DROP` + `CREATE`.

Отсюда базовое правило: **процедура в MySQL изменяется только через создание нового объекта и переключение вызовов**, а не через удаление рабочего.

### PostgreSQL: сигнатура неизменна — это и защита, и ограничение

`CREATE OR REPLACE` заменяет тело атомарно: в момент выполнения старое тело либо целиком доступно, либо целиком заменено. Но типы и число аргументов, а также имя, изменить нельзя — попытка приводит к созданию нового отдельного объекта.

Практические следствия:

- Изменение логики при неизменной сигнатуре — безопасная операция, атомарная, привилегии сохраняются.
- Изменение сигнатуры — всегда новый объект, и все существующие вызовы сразу перестают разрешаться. Переход на новую сигнатуру требует смены имени.
- Перед `CREATE OR REPLACE` с изменением результата полезно снять текущее определение: если синтаксис не проходит проверку, команда откатывается и ничего не меняется. Но гарантировать успех можно только прогоном на staging.

```sql
-- Зафиксировать эталонное определение до изменения
SELECT pg_get_functiondef('app.calculate_discount(int, numeric)'::regprocedure);
-- → CREATE OR REPLACE FUNCTION app.calculate_discount(p_id integer, p_rate numeric)
-- →  RETURNS numeric
-- → ...

-- Атомарная замена тела при неизменной сигнатуре
CREATE OR REPLACE FUNCTION app.calculate_discount(p_id INT, p_rate NUMERIC)
RETURNS NUMERIC AS $$
BEGIN
  RETURN round(p_rate * (1 - COALESCE(app.get_customer_discount(p_id), 0)), 2);
END;
$$ LANGUAGE plpgsql;
```

Тело заменено — а как быть с атрибутами, которые `CREATE OR REPLACE` не меняет? Здесь PostgreSQL даёт то, чего нет в MySQL: оператор `ALTER ROUTINE`, единый для функций и процедур.

```sql
-- Изменить волатильность (влияет на решения оптимизатора)
ALTER ROUTINE app.calculate_discount(int, numeric) IMMUTABLE;

-- Изменить владельца
ALTER ROUTINE app.calculate_discount(int, numeric) OWNER TO app_owner;

-- Задать безопасность выполнения
ALTER ROUTINE app.calculate_discount(int, numeric) SECURITY DEFINER;

-- Задать search_path на уровне объекта, а не в теле
ALTER ROUTINE app.calculate_discount(int, numeric) SET search_path = pg_catalog, app;

-- Ограничить время выполнения объекта
ALTER ROUTINE app.calculate_discount(int, numeric) SET statement_timeout = '30s';

-- Переименовать объект
ALTER ROUTINE app.calculate_discount(int, numeric) RENAME TO app.calc_discount;

-- Вернуть настройку к значению по умолчанию сессии
ALTER ROUTINE app.calculate_discount(int, numeric) RESET statement_timeout;
```

Ключевое отличие от MariaDB и MySQL: в PostgreSQL оператор **единый для функций и процедур**, тогда как `ALTER PROCEDURE` и `ALTER FUNCTION` в MariaDB — разные операторы. И `ALTER ROUTINE` меняет то, чего не меняет `CREATE OR REPLACE`, — атрибуты, владельца и имя, сохраняя определение.

Оговорка по `SET`-клаузе: она несовместима с `COMMIT`/`ROLLBACK` внутри тела. Процедура, которая сама управляет транзакциями, не может быть ограничена через `ALTER ROUTINE ... SET` — там нужен `SET LOCAL` в самом теле. Подробнее: [Безопасность хранимых объектов](security.md).

### MariaDB: атомарная замена есть

В MariaDB тело меняется через `CREATE OR REPLACE PROCEDURE` / `CREATE OR REPLACE FUNCTION` — это штатный рекомендуемый способ, указанный в документации по `ALTER PROCEDURE`. MariaDB отличается от MySQL именно здесь: замена тела атомарна, привилегии не теряются, окна недоступности нет.

`ALTER PROCEDURE` в MariaDB меняет только характеристики — `SQL SECURITY DEFINER|INVOKER`, `CONTAINS SQL`/`READS SQL DATA`/`MODIFIES SQL DATA`, `COMMENT`. Ни параметры, ни тело — никогда.

### MySQL: только `DROP` + `CREATE`, и это ломает привилегии

Документация `ALTER PROCEDURE` в MySQL формулирует это однозначно: параметры и тело изменить нельзя, «чтобы внести такие изменения, вы должны удалить и заново создать процедуру». `CREATE OR REPLACE` для routines в MySQL нет.

Два последствия, которые обычно недооценивают.

**Первое — потеря привилегий.** Удаление объекта снимает с него все специфичные привилегии. При этом `automatic_sp_privileges` (по умолчанию включён) при создании автоматически выдаёт `EXECUTE` и `ALTER ROUTINE` только создателю. То есть все `GRANT EXECUTE ON PROCEDURE ... TO app_user`, выданные вручную, после `DROP` исчезают, а `CREATE` их не возвращает. Приложение получит `ERROR 1142 (42000): EXECUTE command denied` в момент вызова — то есть после успешного, на вид, деплоя.

```sql
-- До замены тела: снять полный список привилегий, которые нужно восстановить
SHOW GRANTS FOR 'app_user'@'%';
-- → GRANT USAGE ON *.* TO `app_user`@`%`
-- → GRANT EXECUTE ON PROCEDURE `mydb`.`proc_place_order` TO `app_user`@`%`

-- Замена тела
DROP PROCEDURE proc_place_order;
CREATE PROCEDURE proc_place_order(...) /* новое тело */;

-- Привилегии автоматически не восстановятся — выдать заново
GRANT EXECUTE ON PROCEDURE mydb.proc_place_order TO 'app_user'@'%';
```

**Второе — окно недоступности.** Между `DROP` и `CREATE` объект не существует. Вызов в это окно даёт `ERROR 1305 (42000): PROCEDURE mydb.proc_place_order does not exist`. Документация MariaDB отдельно отмечает, что её `DROP` действует немедленно, но уже выполняющиеся потоки продолжают работу — то есть оборван будет именно новый вызов, а не текущий.

В MySQL DDL не транзакционно, поэтому откатить пару `DROP` + `CREATE` нельзя. Единственная защита — не создавать окно: новое имя, переключение, удаление старого.

```sql
-- 1. Новое тело живёт под своим именем — production продолжает работать
CREATE PROCEDURE proc_place_order_v2(IN p_customer INT)
BEGIN
  INSERT INTO orders (customer_id, created_at) VALUES (p_customer, NOW());
END;

-- 2. Переключение вызовов: приложение должно обращаться к proc_place_order_v2.
--    ALTER PROCEDURE здесь не поможет — он не переименовывает объекты.

-- 3. Старый объект удаляется отдельным шагом после того, как вызовов не осталось
DROP PROCEDURE proc_place_order;
```

Порядок «создать → переключить → удалить» обязателен и требует, чтобы приложение умело менять имя вызываемого объекта. Если не умеет — применяйте expand/contract на уровне таблицы или обёртки.

### MariaDB/MySQL: деплой функции на сервере с бинарным логом

На сервере с включённым бинарным логом (репликация, point-in-time recovery) действуют дополнительные ограничения, из-за которых `CREATE FUNCTION` падает уже на этапе деплоя — то есть задолго до первого вызова.

**Первое ограничение — характеристики функции.** Чтобы `CREATE FUNCTION` был принят, в определении должна быть явно указана хотя бы одна из трёх характеристик: `DETERMINISTIC`, `NO SQL` или `READS SQL DATA`. Ни одна из них не подразумевается по умолчанию: без явного указания характеристика доступа к данным считается `CONTAINS SQL`, а детерминированность — `NOT DETERMINISTIC`. Отсутствие любой из трёх даёт отказ на этапе `CREATE`:

```
ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL,
or READS SQL DATA in its declaration and binary logging is enabled
(you *might* want to use the less safe log_bin_trust_function_creators variable)
```

Причина ограничения в том, что реплика применяет бинарный лог с полными правами. Если функция недетерминирована (содержит `NOW()`, `RAND()`, `UUID()`), то на источнике и на реплике она даст разный результат, а ложь при восстановлении из бэкапа. Проверить честность объявления движок не может — MySQL прямо полагается на «честность» автора: объявленная `DETERMINISTIC` функция не проверяется на отсутствие недетерминированных операций.

**Второе ограничение — привилегия.** Создание и изменение функции при включённом бинарном логе требует дополнительно `SET_ANY_DEFINER` (в документации MySQL 8.4 этот термин вытеснил прежнюю формулировку про `SUPER`) к обычной `CREATE ROUTINE` или `ALTER ROUTINE`. Без неё:

```
ERROR 1419 (HY000): You do not have the SUPER privilege and
binary logging is enabled (you *might* want to use the less safe
log_bin_trust_function_creators variable)
```

Существенное различие между движками: MariaDB указывает, что ограничения действуют при `binlog_format = STATEMENT`, тогда как MySQL формулирует их как следствие самого факта включённого бинарного лога.

**Третье ограничение — самый недооценённый момент.** Ограничения на `DETERMINISTIC` распространяются только на `FUNCTION` и `TRIGGER`. Процедуры и события Event Scheduler под них не подпадают, и их вызовы пишутся в бинарный лог на уровне отдельных выполненных внутри операторов, а не одним вызовом. Практическое следствие для архитектуры: **логику, которая пишет данные, следует оформлять как процедуру, а не как функцию**. Функция, изменяющая данные, формально не может честно объявить ни одну из трёх требуемых характеристик — пришлось бы солгать в объявлении. Дополнительно функция перед выполнением берёт табличные блокировки на свои таблицы, тогда как процедура этого не делает, — то есть пишущая функция ещё и сериализует конкурентный доступ.

```sql
-- Проверить, действуют ли ограничения на текущем сервере
SHOW VARIABLES LIKE 'log_bin';
-- → log_bin | /var/lib/mysql/binlog.000001

SHOW VARIABLES LIKE 'binlog_format';
-- → binlog_format | ROW

SHOW VARIABLES LIKE 'log_bin_trust_function_creators';
-- → log_bin_trust_function_creators | 0
```

`log_bin_trust_function_creators` снимает оба ограничения: функцию может создать любой пользователь с `CREATE ROUTINE`, и характеристики указывать не обязательно. Цена — отказ от защиты, поэтому переменная объявлена устаревшей начиная с MySQL 8.0.34 и будет удалена. В MariaDB переменная остаётся штатным инструментом; в [RBAC MariaDB](../../MariaDB/security/rbac.md) она разобрана как мера контроля создания хранимых объектов.

**Проектирование деплоя под эти ограничения:**

1. Всё, что пишет данные, оформляйте как `PROCEDURE` — ограничения тогда не применяются вовсе.
2. Если функция неизбежна, объявляйте ей честную характеристику (`NO SQL` или `READS SQL DATA`), даже если она читает данные.
3. Не поднимайте `log_bin_trust_function_creators` как средство обхода запрета: это снимает защиту целиком, а не решает задачу правильной архитектурой.
4. Триггеры под ограничение подпадают, но `DETERMINISTIC` у них нет вовсе — они считаются всегда детерминированными. Это делает опасными недетерминированные вызовы внутри триггера, например `UUID()`, который на реплике не реплицируется.

**Почему падение выглядит как случайное.** Ограничение действует на сервере с бинарным логом и не действует на сервере без него. Поэтому один и тот же скрипт деплоя штатно проходит на staging без репликации и падает на production — причём на `CREATE`, а не на первом вызове, поэтому функциональный тест на staging этого не обнаруживает.

### Переключение вызовов, когда сменить имя нельзя

Если приложение жёстко зашито на имя, единственная безопасная схема для MySQL — временная обёртка, но она сама по себе риск: старое тело приходится хранить. Практический компромисс: держать `proc_name` как тонкую обёртку, которая делегирует версионированной процедуре, и менять только тело обёртки — а это снова `DROP` + `CREATE`.

Поэтому **для MySQL правильный ответ — долгоживущая схема версионирования**: `proc_name_v1` / `proc_name_v2` плюс переключение на стороне приложения или в слое доступа. Либо принять окно недоступности и делать его в maintenance window с проверкой вызовов перед удалением. Оба подхода рабочие, выбор — между простотой эксплуатации и нулевым простоем.

### Расписания: два независимых механизма с разными свойствами

**pg_cron (PostgreSQL).** Задания лежат в обычной таблице `cron.job` (`jobid`, `schedule`, `command`, `nodename`, `nodeport`, `database`, `username`) в схеме `cron`, а изменения в ней инвалидируют кэш заданий триггером. Ключевые эксплуатационные свойства:

- выполняется **не более одного экземпляра конкретного задания одновременно**; следующий запуск той же задачи ставится в очередь;
- число параллельных запусков ограничено `cron.max_running_jobs` (по умолчанию 32) и общим числом background workers — `max_worker_processes` по умолчанию 8, поэтому реальный параллелизм упирается в workers, а не в `max_running_jobs`;
- задания **не выполняются, пока сервер в hot standby**, и автоматически стартуют после promotion;
- на таблице включён RLS с политикой по `username = current_user`, поэтому пользователь видит только свои задания;
- записи в `cron.job_run_details` **не очищаются автоматически**; удалять их вправе пользователь, создавший задание.

Следствие для изменений: pg_cron даёт очередь, но не идемпотентность. Если задание упало на середине и вызывается повторно, без защиты от повторного применения часть операций выполнится дважды. Механизм идемпотентности — отдельная тема (см. [Идемпотентность](../../../Concepts/idempotency.md)).

**Event Scheduler (MySQL/MariaDB).** Состояние задано глобальной переменной `event_scheduler`, и здесь есть ловушка, ломающая «деплой включил событие, а оно не работает»:

| Значение | Поведение | Изменение во время работы |
|---|---|---|
| `ON` | Поток планировщика работает, события выполняются | `SET GLOBAL` в `ON`/`OFF` |
| `OFF` | Поток не работает, события не выполняются | `SET GLOBAL` в `ON`/`OFF` |
| `DISABLED` | Планировщик неработоспособен | **невозможно** — только при старте сервера |

Значение по умолчанию **различается между движками**: в MySQL 8.0+ это `ON`, а в MariaDB — `OFF`. Поэтому в конфигурационном файле задавайте `event_scheduler = ON` явно: одинаково настроенный конфиг даст разное поведение на MySQL и MariaDB.

Значение `DISABLED` задаётся только при старте: параметром командной строки `--event-scheduler=DISABLED` или строкой `event_scheduler=DISABLED` в конфигурационном файле. Если планировщик выставлен в `DISABLED` при старте, изменить значение во время работы нельзя — потребуется рестарт. Это ключевое отличие от `OFF`, который выглядит почти так же, но управляется на лету.

Переменная только глобальная: попытка `SET @@event_scheduler = OFF` даёт `ERROR 1229 (HY000): Variable 'event_scheduler' is a GLOBAL variable and should be set with SET GLOBAL`. У `ON` и `OFF` есть числовые эквиваленты `1` и `0`, у `DISABLED` — нет.

### Дрейф расписания: почему он опасен и как его ловить

Дрейф расписаний коварнее дрейфа данных: расписание выглядит корректно, задание включено, а `command` в проде отличается от staging — и задача молча делает не то. Причины типичные: ручной `ALTER EVENT` или `UPDATE cron.job` мимо пайплайна, разные тексты заданий в шаблонах инфраструктуры, забытый `ALTER EVENT ... DISABLE` после инцидента.

Проверка в PostgreSQL:

```sql
-- Эталон расписаний: поднять из репозитория и сравнить
SELECT jobid, schedule, command, database, username, active
FROM cron.job
WHERE username = current_user
ORDER BY jobid;
-- → jobid | schedule  | command                        | database | username | active
-- →    1 | '5 * * * *'| SELECT app.rebuild_stats();    | mydb     | app      | t
-- →    2 | 0 3 * * 0  | SELECT app.purge_audit();      | mydb     | app      | t
```

Проверка в MySQL:

```sql
SELECT EVENT_SCHEMA, EVENT_NAME, STATUS, INTERVAL_VALUE, INTERVAL_FIELD,
       ON_COMPLETION, LAST_EXECUTED, LAST_ALTERED, EVENT_DEFINITION
FROM information_schema.EVENTS
WHERE STATUS NOT IN ('REPLICA_SIDE_DISABLED', 'SLAVESIDE_DISABLED')
ORDER BY EVENT_SCHEMA, EVENT_NAME;
-- → mydb | nightly_purge | ENABLED | 1 | DAY | PRESERVE | 2026-10-04 03:00:00 | 2026-09-30 11:14:02 | NULL
```

Обратите внимание на `EVENT_DEFINITION`: для повторяющихся событий, заданных через `EVERY`, это поле `NULL`, а `LAST_EXECUTED` отражает момент **старта** последнего выполнения, а не завершения. Поэтому «свежий» `LAST_EXECUTED` при долгой задаче не означает, что она отработала успешно.

### Репликация: `REPLICA_SIDE_DISABLED` как источник тихих потерь расписания

Отдельная и легко пропускаемая категория дрейфа. При репликации события в MySQL на реплике статус принудительно выставляется в `REPLICA_SIDE_DISABLED` — независимо от того, какой статус был указан при создании или изменении. Значение означает: событие пришло с источника репликации, но на реплике не выполняется.

> **Про имя значения.** В MySQL 8.4 это `REPLICA_SIDE_DISABLED`; прежнее написание `SLAVESIDE_DISABLED` объявлено устаревшим и готовится к удалению. MariaDB использует собственное написание. Если ваш аудит-скрипт сравнивает `STATUS` со строкой, сравнивайте с обоими вариантами — на старых инсталляциях вернётся legacy-имя, и запрос с одним лишь новым именем молча покажет «все события в порядке».

Два следствия:

1. **Проверять надо не только `STATUS = 'ENABLED'`**, но и наличие `REPLICA_SIDE_DISABLED` (или `SLAVESIDE_DISABLED` на старых версиях) — иначе события «потеряются» без ошибок при переключении.
2. **При promotion реплики в источник события надо включать вручную.** Каждое такое событие требует `ALTER EVENT ... ENABLE`. Документация рекомендует конкретный порядок: сначала выставить `event_scheduler = OFF`, затем выполнить `ALTER EVENT` для всех событий, затем перезапустить сервер, и только после этого включить планировщик обратно. Если позже сервер снова понижается до реплики, все события, включённые вручную, требуется отключить вручную же — автоматического возврата к `REPLICA_SIDE_DISABLED` для них не будет.

Для PostgreSQL аналог — `hot standby`: задания не выполняются и стартуют автоматически после promotion, но их `command` может указывать на схему, которой на standby ещё нет.

### Откат

Откат меняется по природе операции, и понимать это необходимо до деплоя, а не во время инцидента.

| Ситуация | Откат |
|---|---|
| PostgreSQL, изменено тело при той же сигнатуре | `CREATE OR REPLACE` с прежним определением — атомарно и мгновенно |
| PostgreSQL, добавлен новый объект | `DROP` нового объекта |
| PostgreSQL, удалён объект | Восстановление из дампа; удаление необратимо, если не осталось зависимых копий |
| MariaDB, изменено тело | `CREATE OR REPLACE` с прежним определением |
| MariaDB, удалён объект | `CREATE OR REPLACE` воссоздаёт из сохранённого текста — но **владелец становится тем, кто выполнил операцию**, а не исходным владельцем |
| MySQL, объект в процессе замены | `CREATE` прежнего тела немедленно; отката `DROP` не существует |
| Расписание | Пересоздание задания с прежним `schedule`/`command` |

Практический вывод: **текст каждого объекта должен лежать в репозитории**. Без этого откат в MySQL превращается в импровизацию по памяти, а удаление объекта в PostgreSQL — в операцию без возврата.

Проверить, что определение в репозитории соответствует базе, можно так:

```sql
-- PostgreSQL: сверка определения с эталоном
SELECT pg_get_functiondef('app.calculate_discount(int, numeric)'::regprocedure);
-- MariaDB/MySQL: SHOW CREATE PROCEDURE mydb.proc_place_order\G
```

### Классификация изменений: выбор процедуры rollout

Определения выше задают тип изменения; таблица ниже связывает тип с процедурой, окном и откатом. Решение принимается до написания скрипта, а не во время инцидента.

| Тип изменения | Процедура | Окно недоступности | Откат |
|---|---|---|---|
| Новый объект (additive) | `CREATE` под своим именем | нет | `DROP` нового объекта |
| Тело, сигнатура неизменна (PostgreSQL, MariaDB) | `CREATE OR REPLACE` | нет (атомарно) | `CREATE OR REPLACE` прежним телом из репозитория |
| Тело (MySQL) | версионированное имя → переключение вызовов → удаление старого | нет, но вызовы меняются | возврат вызовов на старое имя; тело — из репозитория |
| Смена сигнатуры | expand/contract: новый объект → переключение вызовов → contract | нет | возврат вызовов на старую версию до завершения contract |
| Характеристики (`ALTER ROUTINE` / `ALTER PROCEDURE`) | отдельный оператор, тело не меняется | нет | обратный `ALTER` |
| Привилегии объекта | `GRANT` / `REVOKE` | нет | обратный `GRANT` / `REVOKE` |
| Расписание | `ALTER EVENT` / `UPDATE cron.job` + сверка с эталоном | нет | восстановить прежние `schedule`/`command` |
| Удаление объекта | impact-анализ зависимостей → contract | зависит от зависимостей | PostgreSQL — из дампа; MariaDB/MySQL — из репозитория |

Критерий разделения additive/breaking — не размер изменения, а разрыв вызовов: если хоть один существующий вызов перестаёт разрешаться, изменение ломающее и требует expand/contract. Критичные объекты (пути записи, оплаты, отчётности) согласуются по процедуре change management — окно деплоя, критерии отката, контакты on-call — по тем же правилам, что и миграции таблиц (см. **[Expand-Contract](../migrations/expand_contract.md)** и **[Стратегии отката](../migrations/rollback_strategies.md)**).

### Обнаружение изменений вне пайплайна

Дрейф расписания возникает, когда изменение вносится мимо пайплайна — ручным `ALTER EVENT` или `UPDATE cron.job`. Механизмы обнаружения таких изменений различаются по движкам.

**MariaDB/MySQL — каталог и бинарный лог.** Таблица `information_schema.ROUTINES` хранит `CREATED`, `LAST_ALTERED` (при отсутствии изменений совпадает с `CREATED`), `DEFINER`, `SQL_DATA_ACCESS` и `ROUTINE_COMMENT`. Расхождение `LAST_ALTERED` с историей деплоев — признак ручной правки. DDL-операторы над routines и событиями (`CREATE`/`ALTER`/`DROP` `PROCEDURE`/`FUNCTION`/`EVENT`) сервер всегда записывает в бинарный лог в statement-формате, даже при `binlog_format = ROW`, — поэтому ретроспективно изменения ищутся через `mysqlbinlog`:

```sql
-- Кто и когда менял объекты схемы
SELECT ROUTINE_NAME, ROUTINE_TYPE, CREATED, LAST_ALTERED, DEFINER, SQL_DATA_ACCESS
FROM information_schema.ROUTINES
WHERE ROUTINE_SCHEMA = 'mydb'
ORDER BY LAST_ALTERED DESC;
-- → proc_place_order | PROCEDURE | 2026-09-28 11:02:41 | 2026-10-03 04:17:09 | `dba`@`localhost` | CONTAINS SQL
```

```bash
# Все операторы над stored objects с начала файла
mysqlbinlog binlog.000007 | grep -E '(CREATE|ALTER|DROP) (PROCEDURE|FUNCTION|EVENT)'
```

**PostgreSQL — event trigger на `ddl_command_end`.** Событийный триггер фиксирует DDL в аудит-таблицу: запись атомарна с самим изменением (триггер срабатывает до коммита транзакции) и откатывается вместе с ним; при ошибке DDL триггер не срабатывает вовсе. Полный механизм, примеры и ограничения (включая требование суперпользователя для `CREATE EVENT TRIGGER` по умолчанию) — в **[Event Triggers в PostgreSQL](../../PostgreSQL/Concepts/event_triggers.md)**. Для задачи change management важно отфильтровать триггер тегами команд над routines, иначе аудит-таблица заполняется всеми DDL базы:

```sql
-- Функция audit_ddl() — из примера по ссылке выше
CREATE EVENT TRIGGER audit_routine_ddl
ON ddl_command_end
WHEN tag IN ('CREATE FUNCTION', 'ALTER FUNCTION', 'DROP FUNCTION',
             'CREATE PROCEDURE', 'ALTER PROCEDURE', 'DROP PROCEDURE')
EXECUTE FUNCTION audit_ddl();
```

Сверка с эталоном из репозитория остаётся обязательным шагом: каталог фиксирует *факт* изменения, но не его *ожидаемость* — сравнение `LAST_ALTERED`, `cron.job` и `information_schema.EVENTS` с эталоном описано в разделе «Дрейф расписания» выше.

## Практические сценарии

#### Предпосылки

Перед любым сценарием проверьте:

- **Привилегии:** `CREATE ROUTINE` и `ALTER ROUTINE` для создания и изменения, `EXECUTE` для проверки вызовов, `GRANT OPTION` на восстанавливаемые права — для возврата привилегий после пересоздания объекта (сценарий 2). В MySQL при включённом бинарном логе для функций дополнительно требуется `SET_ANY_DEFINER` (см. раздел про деплой функции на сервере с бинарным логом).
- **Среды:** staging должен работать с включённым бинарным логом — иначе деплой пройдёт там и упадёт на production (`ERROR 1418`/`ERROR 1419`).
- **Репозиторий:** текст каждого объекта и список его привилегий зафиксированы до начала работ — без этого откат в MySQL невозможен.
- **Эталон для сверки:** актуальные определения (`pg_get_functiondef` / `SHOW CREATE`) и расписания (`cron.job` / `information_schema.EVENTS`) текущей среды.

### Сценарий 1: Изменение функции в PostgreSQL с expand/contract

Требуется изменить логику и при этом добавить обязательный параметр. Простое `CREATE OR REPLACE` невозможно — смена сигнатуры создаст новый объект и сломает все вызовы.

```sql
-- Фаза 1. EXPAND: новая функция живёт рядом со старой
CREATE FUNCTION app.calculate_discount_v2(p_id INT, p_rate NUMERIC, p_region TEXT)
RETURNS NUMERIC AS $$
BEGIN
  RETURN round(p_rate * (1 - COALESCE(app.get_customer_discount(p_id, p_region), 0)), 2);
END;
$$ LANGUAGE plpgsql;
-- → CREATE FUNCTION

-- Фаза 2. Проверка под нагрузкой на staging, затем переключение вызовов приложения
SELECT app.calculate_discount_v2(1, 10.00, 'EU');
-- → 9.50

-- Фаза 3. CONTRACT: только после того, как вызовов к v1 не осталось
DROP FUNCTION app.calculate_discount(INT, NUMERIC);
```

Между фазами 1 и 3 обе версии доступны. Время между ними — это период, в течение которого живут обе реализации; он должен быть конечным, и его надо отслеживать, иначе мёртвые версии накапливаются.

### Сценарий 2: Изменение процедуры в MySQL без простоя

Главная проблема — потеря привилегий. Порядок ниже сохраняет работоспособность приложения на каждом шаге.

```sql
-- 1. Зафиксировать привилегии ДО удаления
SELECT GRANTEE, PRIVILEGE_TYPE, TABLE_SCHEMA, SPECIFIC_NAME
FROM information_schema.ROUTINE_PRIVILEGES
WHERE SPECIFIC_SCHEMA = 'mydb' AND SPECIFIC_NAME = 'proc_place_order';
-- → GRANTEE         | PRIVILEGE_TYPE | TABLE_SCHEMA | SPECIFIC_NAME
-- → app_user@%      | EXECUTE        | mydb         | proc_place_order
-- → reporting@%     | EXECUTE        | mydb         | proc_place_order

-- 2. Проверить новое тело без риска: синтаксис проверяется только на CREATE,
--    поэтому сначала создаём под временным именем
CREATE PROCEDURE proc_place_order__new(IN p_customer INT)
BEGIN
  INSERT INTO orders (customer_id, created_at) VALUES (p_customer, NOW());
END;
-- → CREATE PROCEDURE (синтаксис подтверждён)

-- 3. Переключить вызовы на proc_place_order__new и дождаться обнуления вызовов
--    старого имени в журналах

-- 4. Удалить старое имя и переименовать новое в рабочее
DROP PROCEDURE proc_place_order;
RENAME PROCEDURE proc_place_order__new TO proc_place_order;

-- 5. Восстановить привилегии — шаг, который забывают чаще всего
GRANT EXECUTE ON PROCEDURE mydb.proc_place_order TO 'app_user'@'%';
GRANT EXECUTE ON PROCEDURE mydb.proc_place_order TO 'reporting'@'%';
-- → 2 rows affected

-- 6. Проверка: вызов от имени каждого получателя привилегий
--    SELECT app_user.proc_place_order(1);  (в MySQL нужно проверять через
--    соединение с этим пользователем, а не через DEFINER)
```

Замена шагов 4 и 5 важна: сначала привилегии, потом любые вызовы. Пропуск шага 5 даёт работающий объект, которым не может никто.

Оговорка про `DEFINER`: `SQL SECURITY DEFINER` исполняет тело с правами `DEFINER`, поэтому проверка вызовом из сессии `app_user` может пройти и без `EXECUTE` — проверять надо и обычным вызовом с правами `INVOKER`.

### Сценарий 3: Перенос расписания между средами

Расписание хранится в БД, а не в коде приложения, поэтому при развёртывании новой среды его нужно создавать явно, иначе новая среда окажется без заданий.

```sql
-- PostgreSQL: снять определения из эталонной среды
SELECT jobid, schedule, command, database, username, active
FROM cron.job ORDER BY jobid;
-- → Перенести в скрипт миграции в виде вызовов:
--   SELECT cron.schedule('5 * * * *', 'SELECT app.rebuild_stats();');

-- PostgreSQL: изменить расписание существующего задания.
-- Прямой UPDATE допустим — триггер на cron.job инвалидирует кэш заданий.
UPDATE cron.job
   SET schedule = '*/10 * * * *'
 WHERE command LIKE '%rebuild_stats%';
-- → UPDATE 1
```

```sql
-- MySQL: перенести расписание
SHOW CREATE EVENT mydb.nightly_purge;
-- → CREATE DEFINER=`dba`@`localhost` EVENT `nightly_purge` ... DO CALL app.purge_audit()

-- В новой среде
CREATE EVENT mydb.nightly_purge
  ON SCHEDULE EVERY 1 DAY
  STARTS '2026-10-06 03:00:00'
  ON COMPLETION PRESERVE
  ENABLE
  COMMENT 'nightly audit purge'
  DO CALL app.purge_audit();
```

Ключевое решение — `ON COMPLETION PRESERVE` для одноразовых событий. Значение по умолчанию для однократного события — `NOT PRESERVE`, что приводит к автоматическому удалению события после выполнения; если это не задано явно, отчёт ошибочно посчитают потерянным.

Проверка переноса обязательна на целевой среде:

```sql
SELECT jobid, schedule, command, active FROM cron.job ORDER BY jobid;
-- → jobid | schedule   | command                     | active
-- →    1 | '*/10 * * * *' | SELECT app.rebuild_stats(); | t
```

```sql
SHOW VARIABLES LIKE 'event_scheduler';
-- → Variable_name  | Value
-- → event_scheduler | ON     (OFF или DISABLED — задания выполняться не будут)

SELECT EVENT_SCHEMA, EVENT_NAME, STATUS, LAST_EXECUTED
FROM information_schema.EVENTS WHERE EVENT_SCHEMA = 'mydb';
-- → mydb | nightly_purge | ENABLED | 2026-10-06 03:00:00
```

#### Что переносит `pg_dump`, а что нет

Для PostgreSQL `pg_dump` умеет выгружать stored objects сам, но покрытие неполное, и это нужно учитывать до переезда, а не после.

| Объект | Поведение `pg_dump` | Секция дампа |
|---|---|---|
| Функция, процедура | Выгружается как `CREATE FUNCTION` / `CREATE PROCEDURE` | `pre-data` |
| Тело `BEGIN ATOMIC` (SQL-standard) | Берётся из `pg_get_function_sqlbody(oid)` и выводится дословно | `pre-data` |
| Обычное строковое тело | Выводится как `AS 'имя_объектного_файла', 'исходный текст'`; при наличии кавычек или обратных слэшей текст оборачивается в dollar-quoting | `pre-data` |
| Триггер (`CREATE TRIGGER`) | Выгружается | **`post-data`** |
| **Event trigger** (`CREATE EVENT TRIGGER`) | Выгружается вместе с состоянием `DISABLE` / `ENABLE ALWAYS` / `ENABLE`, восстановленным из `pg_event_trigger.evtenabled` | **`post-data`** |
| `pg_cron.job` | Отдельного механизма нет: таблица принадлежит расширению `pg_cron` | требует включения расширения |

Два уточнения, которые видны в исходном коде `pg_dump` и влияют на планирование загрузки:

- **Секция функции не фиксирована.** Обычно это `pre-data`, но если при сортировке зависимостей создание функции пришлось отложить (`postponed_def`), она попадает в `post-data`. Это происходит при циклических или сложных зависимостях между объектами, поэтому «функции всегда в pre-data» — неверное предположение.
- **Триггеры и event triggers ставятся в `post-data` намеренно.** В `pg_dump_sort.c` сказано прямо: триггеры восстанавливаются после всех модификаций данных, чтобы не мешать их загрузке, а event triggers — предпоследними, чтобы не мешать созданию объектов любого рода. Практическое следствие: если ваш event trigger на `ddl_command_end` пишет в таблицу, которая ещё не создана, он сработает уже после её создания, а не наоборот.

Дамп с ключом `--data-only` пропускает все объекты из таблицы целиком — там остаются только данные таблиц. Обратная сторона: при загрузке полного дампа `pg_restore` в начале сессии выставляет `SET check_function_bodies = false;` (функция `_doSetFixedOutputState` в `pg_backup_archiver.c`), чтобы тела с прямыми ссылками на ещё не созданные объекты не падали на проверке. Это снимает ошибку, но не устраняет проблему: битые ссылки переносятся в целевую базу молча, поэтому после `pg_restore` их нужно искать самому.

Расписание `pg_cron` — единственный элемент, который **не** переносится автоматически как «функция». Таблица `cron.job` создаётся скриптом расширения, поэтому в дампе присутствует `CREATE EXTENSION pg_cron`, а не `CREATE TABLE cron.job`. Практические следствия:

- `CREATE EXTENSION pg_cron` на целевом кластере требует, чтобы библиотека уже была в `shared_preload_libraries`, иначе операция падает. Скрипт расширения дополнительно проверяет, что текущая база совпадает с `cron.database_name`: если не совпадает, он выбрасывает ошибку `can only create extension in database ...` — jobs must be scheduled from the database configured in `cron.database_name.
- Работы хранят в `cron.job` владельца (`username`), а таблица защищена RLS-политикой `cron_job_policy USING (username = current_user)`. Восстановленный набор заданий может оказаться неисполняемым, если он принадлежит роли, которой нет на целевой среде.
- Поэтому `cron.job` проверяют отдельно после `pg_restore`, а не доверяют дампу вслепую:

```sql
-- Что попало в дамп, а что нет
SELECT jobid, schedule, command, username, active FROM cron.job ORDER BY jobid;
-- → jobid | schedule     | command                    | username | active
-- →     1 | '*/10 * * * *' | SELECT app.rebuild_stats(); | app_svc  | t

-- Event triggers пришли в post-data — проверяем их наличие и состояние
SELECT evtname, evtevent, evtenabled FROM pg_event_trigger ORDER BY evtname;
-- → evtname          | evtevent      | evtenabled
-- → ddl_end_audit    | ddl_command_end | O
-- → (O = enabled origin, D = disabled, A = always)
```

Файлы и переменные, на которые опирается расписание, в дамп не попадают: `shared_preload_libraries` и `cron.database_name` задаются в конфигурации сервера, а не в каталоге. Их нужно переносить вместе с дампом отдельно — иначе задания восстановятся, но фоновая работа не запустится.

### Сценарий 4: Promotion реплики с событиями

Стандартная задача: standby или реплика становится новым источником. Пропуск шага с событиями даёт среду без заданий, причём без ошибок.

```sql
-- 1. До promotion: найти события, которые не выполняются на реплике
SELECT EVENT_SCHEMA, EVENT_NAME, ORIGINATOR
FROM information_schema.EVENTS
WHERE STATUS IN ('REPLICA_SIDE_DISABLED', 'SLAVESIDE_DISABLED');
-- → mydb | nightly_purge | 1     (ORIGINATOR — server_id источника)

-- 2. Выключить планировщик на время изменений
SET GLOBAL event_scheduler = OFF;
-- → Query OK
--    (SET @@event_scheduler = OFF даст ERROR 1229 (HY000): Variable is GLOBAL)

-- 3. Включить каждое событие вручную
ALTER EVENT mydb.nightly_purge ENABLE;
-- → Query OK

-- 4. Перезапустить сервер — как предписывает документация для этого случая

-- 5. Включить планировщик
SET GLOBAL event_scheduler = ON;
-- → Query OK

-- 6. Проверка
SELECT EVENT_SCHEMA, EVENT_NAME, STATUS FROM information_schema.EVENTS
WHERE STATUS NOT IN ('REPLICA_SIDE_DISABLED', 'SLAVESIDE_DISABLED');
-- → mydb | nightly_purge | ENABLED
```

Если сервер позже снова становится репликой, события, включённые шагом 3, надо отключить вручную — документированного автоматического возврата к `REPLICA_SIDE_DISABLED` для них нет.

### Сценарий 5: Откат неудачного деплоя процедуры в MySQL

Ситуация: после `DROP` + `CREATE` обнаружена ошибка в логике. Откат — это не `DROP` нового объекта, а создание прежнего тела заново.

```sql
-- Источник истины — репозиторий, а не память инженера
-- Шаг 1: развернуть прежнее определение из репозитория
DROP PROCEDURE proc_place_order;
CREATE PROCEDURE proc_place_order(IN p_customer INT)
BEGIN
  INSERT INTO orders (customer_id, created_at) VALUES (p_customer, NOW());
  -- прежняя, проверенная логика
END;
-- → CREATE PROCEDURE

-- Шаг 2: восстановить привилегии (см. сценарий 2, шаг 5)
GRANT EXECUTE ON PROCEDURE mydb.proc_place_order TO 'app_user'@'%';

-- Шаг 3: проверить исполняемость от имени приложения
-- → ERROR 1142 (42000): EXECUTE command denied означает пропущенный GRANT
```

Потеря объекта между шагами — не гипотетическая: если процесс упал на `CREATE` с синтаксической ошибкой, объекта нет вообще, и откат состоит только в повторном `CREATE` из репозитория. Проверка синтаксиса до удаления (через создание под временным именем) существенно сокращает этот путь.

## Устранение неполадок

### Процедура исчезла после деплоя, в логах ошибка `does not exist`

**Симптомы:** `ERROR 1305 (42000): PROCEDURE mydb.proc_place_order does not exist` при вызове из приложения.

**Причины, проверяемые по порядку:**
1. Скрипт деплоя упал на `CREATE` после успешного `DROP` — синтаксическая ошибка в теле, и объект удалён безвозвратно.
2. В `CREATE` попал `DELIMITER`-artefact: клиент `mysql` разбивает тело по `;`, если `DELIMITER` не переключён, и отправляет обрезанный текст.
3. `CREATE` выполнен от пользователя, у которого нет привилегий на целевую схему, и ошибка была воспринята как успех пайплайна.

**Диагностика:**

```sql
SHOW PROCEDURE STATUS WHERE Db = 'mydb' AND Name = 'proc_place_order';
-- → (0 rows) — объекта действительно нет
```

**Решение:** развернуть определение из репозитория и восстановить привилегии. Профилактика — валидировать синтаксис созданием под временным именем до удаления рабочего объекта.

### `EXECUTE command denied` сразу после успешного деплоя

**Симптомы:** объект существует, `SHOW CREATE` возвращает определение, вызов падает с `ERROR 1142 (42000): EXECUTE command denied`.

**Причина:** потеря привилегий при `DROP`. Удаление снимает все специфичные объекту привилегии, а `automatic_sp_privileges` при создании выдаёт `EXECUTE` и `ALTER ROUTINE` только создателю.

**Диагностика:**

```sql
SELECT GRANTEE, PRIVILEGE_TYPE FROM information_schema.ROUTINE_PRIVILEGES
WHERE SPECIFIC_SCHEMA = 'mydb' AND SPECIFIC_NAME = 'proc_place_order';
-- → пусто либо только строка создателя — нужные GRANT потеряны
```

**Решение:** восстановить привилегию по списку, снятому до деплоя. Если список не снят, восстановить из `SHOW GRANTS` каждого пользователя. Отдельная проверка: если процедура объявлена с `SQL SECURITY DEFINER`, вызов от имени приложения может пройти за счёт прав `DEFINER` — проверяйте соединением с правами `INVOKER`.

### `CREATE FUNCTION` падает с `ERROR 1418` (MySQL)

**Симптомы:** деплой падает на `CREATE FUNCTION`:
```
ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL,
or READS SQL DATA in its declaration and binary logging is enabled
```

**Причина:** на сервере с бинарным логом функция обязана явно объявить одну из трёх характеристик — `DETERMINISTIC`, `NO SQL`, `READS SQL DATA`. Ни одна не подразумевается по умолчанию, поэтому функция без них не проходит проверку при создании.

**Диагностика:**

```sql
SHOW VARIABLES LIKE 'log_bin';
-- → log_bin | /var/lib/mysql/binlog.000001   (непусто — ограничение действует)

SHOW VARIABLES LIKE 'log_bin_trust_function_creators';
-- → log_bin_trust_function_creators | 0      (защита включена)
```

**Решение по приоритету:**

1. **Если функция пишет данные** — перепишите её как `PROCEDURE`. Ограничение на `DETERMINISTIC` к процедурам не относится, и это единственное решение, не ослабляющее защиту. Плюс процедура не берёт табличных блокировок на свои таблицы.
2. **Если функция только читает** — добавьте `READS SQL DATA` (или `NO SQL`, если не обращается к таблицам). Это честное объявление, а не обход.
3. `SET GLOBAL log_bin_trust_function_creators = 1` снимает требование, но отключает защиту целиком и в MySQL объявлена устаревшей с 8.0.34. Не используйте как штатное решение.

**Профилактика:** проверяйте деплой на среде с включённым бинарным логом — иначе расхождение между staging и production вы обнаружите только в момент деплоя.

### `CREATE FUNCTION` падает с `ERROR 1419` (MySQL)

**Симптомы:** `ERROR 1419 (HY000): You do not have the SUPER privilege and binary logging is enabled`.

**Причина:** при включённом бинарном логе создание и изменение функции требует `SET_ANY_DEFINER` дополнительно к `CREATE ROUTINE`/`ALTER ROUTINE`. Проверяется на этапе `CREATE`.

**Решение:** выдать привилегию пользователю, выполняющему деплой, либо перейти на процедуру, для которой это ограничение не действует. Практика разграничения привилегий: [RBAC MariaDB](../../MariaDB/security/rbac.md), [Привилегии для репликации MariaDB](../../MariaDB/replication/replication_privileges.md).

### События `ENABLED`, но не выполняются

**Симптомы:** `STATUS = 'ENABLED'`, `LAST_EXECUTED` не обновляется.

**Проверяйте по порядку:**

```sql
-- 1. Глобальный переключатель планировщика
SHOW VARIABLES LIKE 'event_scheduler';
-- → OFF     — задачи не выполняются, состояние меняется через SET GLOBAL
-- → DISABLED — менять во время работы нельзя, нужен рестарт сервера

-- 2. Планировщик виден как процесс?
SHOW PROCESSLIST;
-- → отсутствие потока планировщика согласуется с OFF/DISABLED
```

`DISABLED` — самая частая причина «неожиданно перестало работать»: значение задано в конфигурационном файле, поэтому «включение планировщика» через `SET GLOBAL` не работает, и нужен рестарт без этой строки.

### Задания pg_cron не выполняются после переключения на standby

**Симптомы:** после promotion или рестарта в логах нет ни одного запуска, `cron.job` заполнен корректными активными заданиями.

**Причины:**
1. Планировщик ещё находится в `hot standby` — задания в этом состоянии не выполняются и стартуют автоматически после promotion. Проверьте фактическое состояние сервера, а не предполагайте его.
2. Не хватает background workers: `cron.max_running_jobs` по умолчанию 32, но параллельные запуски упираются в `max_worker_processes`, по умолчанию 8.
3. `command` задания указывает на схему или функцию, которой нет на новом сервере.

**Диагностика:**

```sql
SHOW max_worker_processes;          -- → 8
SELECT count(*) FROM cron.job WHERE active;  -- → 5
SELECT * FROM cron.job_run_details ORDER BY start_time DESC LIMIT 5;
-- → пусто — задания не доходят до запуска, проблема в конфигурации,
--   а не в теле команд
```

### Расписание в prod не совпадает со staging

**Симптомы:** одинаковое развёртывание, разные задания; на prod задание выполняется с другой командой или не выполняется вовсе.

**Диагностика:**

```sql
-- PostgreSQL
SELECT jobid, schedule, command, active FROM cron.job ORDER BY jobid;

-- MySQL
SELECT EVENT_SCHEMA, EVENT_NAME, STATUS, INTERVAL_VALUE, INTERVAL_FIELD,
       LAST_ALTERED, EVENT_DEFINITION
FROM information_schema.EVENTS ORDER BY EVENT_SCHEMA, EVENT_NAME;
```

Сравнивайте `command`/`EVENT_DEFINITION` и `LAST_ALTERED` с эталоном. Расхождение `LAST_ALTERED` при отсутствии изменений в пайплайне означает ручную правку в среде.

**Решение:** расписание переносится декларативно, а не вручную; сравнение с эталоном — обязательный шаг проверки перед переключением трафика.

## Лучшие практики

1. **Держите текст всех объектов в репозитории.** Единственная гарантированная возможность отката — сохранённое определение. Без него откат в MySQL не существует.
2. **В MySQL никогда не меняйте тело через `DROP` + `CREATE` на рабочем имени.** Создавайте новое имя, переключайте вызовы, удаляйте старое отдельным шагом.
3. **Снимайте список привилегий перед любым удалением объекта в MySQL/MariaDB.** Удаление снимает все привилегии, и `CREATE` их не восстанавливает.
4. **В PostgreSQL и MariaDB используйте `CREATE OR REPLACE` для изменений логики.** Обе операции атомарны и сохраняют привилегии.
5. **Смену сигнатуры проводите по expand/contract.** Новый объект с новым именем, переключение вызовов, удаление старого в отдельном шаге.
6. **Проверяйте расписание как конфигурацию.** Сравнение `cron.job` и `information_schema.EVENTS` с эталоном — обязательный шаг перед переключением трафика.
7. **Проверяйте `event_scheduler` явно, а не по умолчанию.** `OFF` лечится через `SET GLOBAL`, `DISABLED` требует рестарта — и различить их, не посмотрев переменную, невозможно.
8. **Ищите `REPLICA_SIDE_DISABLED` перед promotion реплики.** События на реплике не выполняются, а после promotion требуют ручного `ALTER EVENT ... ENABLE`.
9. **Сопоставляйте `interval`-задачи с идемпотентными телами.** Ни pg_cron, ни Event Scheduler не гарантируют, что повторный запуск не продублирует работу.
10. **Не рассчитывайте на автоматическую очистку истории выполнения.** Записи `cron.job_run_details` накапливаются; удалять их нужно отдельной задачей.
11. **Проверяйте деплой на среде с включённым бинарным логом.** На сервере без него ограничения на характеристики функции не действуют, поэтому staging без репликации пропускает код, который упадёт на production с `ERROR 1418` или `ERROR 1419`.
12. **Оформляйте пишущую логику как процедуру, а не как функцию.** Ограничения на `DETERMINISTIC` к процедурам не относятся, а функция ещё и берёт табличные блокировки на свои таблицы.
