# Индексы в базах данных

## Определения

- **Индекс (Index)**: Специальная структура данных, которая ускоряет поиск в таблице, работая как предметный указатель в книге. Вместо полного сканирования таблицы (`Full Table Scan`) СУБД использует индекс для быстрого нахождения местоположения нужных строк.
- **B-Tree (B-дерево)**: Стандартный тип индекса в большинстве реляционных СУБД (PostgreSQL, MySQL, Oracle). Это сбалансированная древовидная структура, хранящая данные в отсортированном виде. Идеален для операций сравнения в широком диапазоне: `=`, `>`, `<`, `BETWEEN`, префиксного поиска.
- **Hash-индекс (Hash Index)**: Индекс, хранящий хеш-коды значений столбца. Идеален только для операций точного равенства (`=`). Бесполезен для запросов по диапазону, так как хеши не сохраняют порядок.
- **Составной индекс (Composite Index)**: Один индекс, построенный на нескольких столбцах. Используется для ускорения запросов, фильтрующих данные по этим столбцам одновременно.

## Базовые концепции

### Принцип работы

Индекс содержит упорядоченный набор значений из индексируемых столбцов и прямые указатели на физическое расположение строк в таблице. Вместо последовательного просмотра каждой записи СУБД быстро находит нужные ключи в компактной и отсортированной структуре индекса и немедленно получает доступ к строкам.

### Порядок столбцов в составном индексе

Порядок столбцов критически важен. В B-Tree индексах поиск идет слева направо. Индекс `(last_name, city)` будет эффективно использоваться для поиска по `last_name` или по паре `last_name` и `city`. Однако он будет практически бесполезен для запроса, который фильтрует данные только по `city`.

### Специализированные индексы

Каждая СУБД предоставляет свои типы индексов для конкретных задач (например, полнотекстовый поиск, геоданные, массивы).

## Практические сценарии

### 1. Ускорение запросов на чтение

Это основная задача индексов. Они значительно сокращают время выполнения запросов:

- с фильтрацией (`WHERE`)
- с сортировкой (`ORDER BY`)
- с соединениями (`JOIN` по индексированным столбцам)

### 2. Обеспечение уникальности данных

Уникальный индекс (`UNIQUE`) гарантирует отсутствие дубликатов в столбце или группе столбцов. Это быстрее и надежнее, чем проверка на уровне приложения.

### 3. Поддержка целостности данных

СУБД неявно создает уникальные индексы для реализации первичных ключей (`PRIMARY KEY`). Внешние ключи (`FOREIGN KEY`) также часто требуют наличия индексов на связанных столбцах для быстрой проверки целостности при удалении или обновлении родительских записей.

### 4. Специальные техники индексации

**Функциональные индексы (индексы на выражения):**
Создаются на результат функции, а не на колонку. Решают проблему, когда в `WHERE` используется функция поверх колонки (например, приведение к нижнему регистру).

**Покрывающие индексы:**
Индексы, которые содержат все столбцы, необходимые для выполнения запроса. Позволяют СУБД получить данные исключительно из индекса без обращения к основной таблице (Index Only Scan).

### 5. Поиск и удаление неиспользуемых индексов

Неиспользуемые индексы приносят только вред: они замедляют запись и занимают место. Их необходимо регулярно находить и удалять, используя системные представления и статистику конкретной СУБД.

## Дополнительная информация

### Компромисс: Чтение vs. Запись

Индексы — это компромисс между скоростью чтения и скоростью записи.

- **Накладные расходы при записи**: Каждая операция `INSERT`, `UPDATE` или `DELETE` в таблицу требует обновления связанных с ней индексов. Это увеличивает объем дисковых операций.
- **Проблема низкой кардинальности**: Индекс на столбце с небольшим количеством уникальных значений (например, `boolean` или `пол`) практически бесполезен. СУБД почти всегда предпочтет полное сканирование таблицы.
- **Затраты на хранение**: Индексы занимают дополнительное дисковое пространство.
- **Затраты на обслуживание**: При интенсивной записи структура индексов может фрагментироваться, что требует периодической перестройки.

### Составные индексы vs отдельные

- **Составной индекс:** Оптимален под конкретный запрос. Порядок колонок критичен.
- **Несколько отдельных:** СУБД могут комбинировать несколько индексов (например, Bitmap Index Scan), но правильно спроектированный составной индекс обычно эффективнее для конкретного запроса.
