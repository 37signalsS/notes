# Индексы в базах данных

## Определения

- **Индекс (Index)**: Специальная структура данных, которая ускоряет поиск строк в таблице, работая аналогично предметному указателю в конце книги. Если вам нужно слово «митохондрии», вы не листаете всю книгу, а смотрите в указателе номера страниц (1, 100, 125) и переходите сразу к ним. Вместо полного сканирования таблицы (**Full Table Scan**) СУБД обращается к индексу для получения прямых ссылок на физическое расположение данных.
- **Селективность (Selectivity)**: Отношение количества уникальных значений к общему количеству строк. Высокая селективность (например, UUID) делает индекс эффективным.
- **Кардинальность (Cardinality)**: Количество уникальных значений в столбце.
- **Кластеризованный индекс (Clustered Index)**: Индекс, определяющий физический порядок хранения строк в таблице. Сама таблица и есть индекс (Index-Organized Table). В таблице может быть только один кластеризованный индекс (обычно по первичному ключу).
- **Некластеризованный индекс (Non-Clustered Index)**: Структура, хранящая ключи и указатели на строки в основной таблице (Heap).
- **Раздувание индекса (Index Bloat)**: Увеличение физического размера индекса из-за накопления неиспользуемого пространства (результат интенсивных `UPDATE` и `DELETE`), что снижает производительность.

## Основные концепции

### Правила использования индексов
1.  **Не гадайте, что индексировать.** Сначала определите медленные запросы (Slow Queries) через логи СУБД, а затем добавляйте индексы для соответствующих столбцов.
2.  **Обслуживание стоит дорого.** Каждая новая запись в таблицу требует обновления всех её индексов. Слишком много индексов замедлят запись. Большинство реальных таблиц имеют от 3 до 5 индексов.
3.  **Индексируйте то, что ищут.** Столбцы, по которым часто идет фильтрация (`WHERE`), сортировка (`ORDER BY`) или объединение (`JOIN`), — главные кандидаты. В приложении для фото это: ID автора (поиск по профилю) и время загрузки (сортировка ленты).

### Архитектура B-Tree (B-дерево)

Наиболее распространенный тип индекса. Хранит данные в сбалансированном дереве в отсортированном виде.
- **Root node**: Корень дерева.
- **Branch nodes**: Промежуточные уровни для навигации.
- **Leaf nodes**: Листья, содержащие сами значения ключей и указатели на строки (**TID/RID**).
Позволяет выполнять поиск, вставку и удаление за логарифмическое время $O(\log n)$.

### Типы доступа к данным (Scans)

Оптимизатор СУБД выбирает метод доступа на основе статистики:
1.  **Sequential Scan (Full Table Scan)**: Последовательное чтение всей таблицы. Эффективно для маленьких таблиц или если запрос выбирает более 15–20% данных.
2.  **Index Scan**: Сначала поиск в индексе, затем переход к основной таблице (Heap) для получения остальных столбцов.
3.  **Index Only Scan**: Все запрашиваемые столбцы есть в индексе. СУБД не обращается к таблице вообще, что дает максимальную производительность.
4.  **Bitmap Index Scan**: Комбинированный метод. Сначала создается битовая карта подходящих строк в памяти (на основе одного или нескольких индексов), затем происходит чтение только нужных блоков таблицы.

### Составные индексы (Composite Indexes)

При создании индекса по нескольким столбцам (`col1, col2, col3`) критически важен их порядок (**Правило левого префикса**):
- Индекс работает эффективно, если в `WHERE` указан первый столбец или последовательность начиная с первого.
- Поиск по `col2` без `col1` не позволит использовать индекс (за редким исключением *Index Skip Scan* в некоторых СУБД).

## Практические сценарии

### 1. Покрывающие индексы (Covering Indexes)

Использование предложения `INCLUDE` (в Postgres/SQL Server) позволяет добавить дополнительные данные в листья индекса, не делая их частью ключа. Это форсирует **Index Only Scan**.

```sql
CREATE INDEX idx_orders_customer ON orders (customer_id) INCLUDE (order_date, total_amount);
```

### 2. Частичные индексы (Partial Indexes)

Позволяют индексировать только подмножество данных. Экономят место и ускоряют работу с "горячими" данными.

```sql
-- Индекс только по активным пользователям
CREATE INDEX idx_active_users ON users (last_login) WHERE active IS TRUE;
```

### 3. Индексы на выражения (Functional Indexes)

Ускоряют запросы, использующие трансформацию данных в условии поиска.

```sql
-- Поиск без учета регистра
CREATE INDEX idx_users_lower_email ON users (LOWER(email));
```

### 4. Ускорение JOIN и Foreign Keys

Индексация внешних ключей обязательна для предотвращения **Sequential Scan** при каждом соединении таблиц, что особенно критично в глубоких иерархиях данных.

## Дополнительная информация

### Обслуживание и мониторинг

- **Фактор заполнения (Fillfactor)**: Параметр, оставляющий свободное место в узлах индекса для будущих вставок. Снижает частоту разделения страниц (page split), но увеличивает размер.
- **REINDEX / REORGANIZE**: Процедура перестроения индекса для устранения фрагментации и Bloat.
- **Статистика**: Индексы эффективны только при наличии актуальной статистики. СУБД должна знать распределение значений, чтобы решить, использовать индекс или нет.

### Накладные расходы

- **Write Overhead**: Каждый индекс замедляет операции записи. Удаляйте неиспользуемые индексы (Unused Indexes).
- **Memory Pressure**: Индексы должны помещаться в кэш (RAM), иначе производительность упадет до скорости диска.
