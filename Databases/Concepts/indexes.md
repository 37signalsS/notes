# Индексы в базах данных

## Определения

- **Индекс (Index)**: Специальная структура данных, которая ускоряет поиск в таблице, работая как предметный указатель в книге. Вместо полного сканирования таблицы (`Full Table Scan`) СУБД использует индекс для быстрого нахождения местоположения нужных строк.

- **B-Tree (B-дерево)**: Стандартный тип индекса в большинстве реляционных СУБД (PostgreSQL, MySQL). Это сбалансированная древовидная структура, хранящая данные в отсортированном виде. Идеален для операций сравнения в широком диапазоне: `=`, `>`, `<`, `BETWEEN`, `LIKE 'prefix%'`.

- **Hash-индекс (Hash Index)**: Индекс, хранящий хеш-коды значений столбца. Идеален только для операций точного равенства (`=`). Как правило, быстрее B-Tree для поиска по точному значению, но бесполезен для запросов по диапазону, так как хеши не сохраняют порядок.

- **Составной индекс (Composite Index)**: Один индекс, построенный на нескольких столбцах. Используется для ускорения запросов, фильтрующих данные по этим столбцам одновременно.

## Основные концепции

### Принцип работы

Индекс содержит упорядоченный набор значений из индексируемых столбцов и прямые указатели на физическое расположение строк в таблице. Вместо последовательного просмотра каждой записи СУБД быстро находит нужные ключи в компактной и отсортированной структуре индекса и немедленно получает доступ к строкам.

### Порядок столбцов в составном индексе

Порядок столбцов в определении `CREATE INDEX` критически важен. Индекс `(last_name, city)` будет эффективно использоваться для поиска по `last_name` или по паре `last_name` и `city`. Однако он будет практически бесполезен для запроса, который фильтрует данные только по `city`.

### Специализированные индексы

Помимо стандартных B-Tree и Hash, существуют и другие типы индексов для особых задач, например:

- **GIN/GiST**: Для сложных типов данных в PostgreSQL (геопространственные данные, полнотекстовый поиск, `jsonb`).
- **BRIN**: Для очень больших, физически упорядоченных таблиц в PostgreSQL.

## Практические сценарии

### 1. Ускорение запросов на чтение

Это основная задача индексов. Они значительно сокращают время выполнения запросов:

- с фильтрацией (`WHERE`)
- с сортировкой (`ORDER BY`)
- с соединениями (`JOIN` по индексированным столбцам)

### 2. Обеспечение уникальности данных

Уникальный индекс (`UNIQUE`) гарантирует отсутствие дубликатов в столбце или группе столбцов. Это быстрее и надежнее, чем проверка на уровне приложения.

### 3. Поддержка целостности данных

СУБД неявно создает уникальные индексы для реализации первичных ключей (`PRIMARY KEY`). Внешние ключи (`FOREIGN KEY`) также требуют наличия индексов на связанных столбцах для быстрой проверки целостности.

### 4. Поиск и удаление неиспользуемых индексов

Неиспользуемые индексы приносят только вред: они замедляют запись и занимают место. Их необходимо регулярно находить и удалять. В PostgreSQL для этого можно использовать представление `pg_stat_user_indexes`.

**Пример запроса для PostgreSQL:**

```sql
SELECT
    indexrelname AS index_name,
    relname AS table_name,
    idx_scan
FROM
    pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'; -- Исключаем первичные ключи
```

## Дополнительная информация

### Компромисс: Чтение vs. Запись

Индексы — это компромисс между скоростью чтения и скоростью записи.

- **Накладные расходы при записи**: Каждая операция `INSERT`, `UPDATE` или `DELETE` в таблицу требует обновления *всех* связанных с ней индексов. Это увеличивает объем дисковых операций и время блокировок.
- **Проблема низкой кардинальности**: Индекс на столбце с небольшим количеством уникальных значений (например, `boolean` или `пол`) практически бесполезен. СУБД почти всегда предпочтет полное сканирование таблицы, так как выборка по такому индексу неэффективна.
- **Затраты на хранение**: Индексы занимают дополнительное дисковое пространство, иногда превышающее объем самих данных.
- **Затраты на обслуживание**: При интенсивной записи структура индексов может деградировать (фрагментироваться), что требует периодической перестройки (`REINDEX`) — ресурсоемкой операции.
