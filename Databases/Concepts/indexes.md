# Индексы в базах данных

## Определения

- **Индекс (Index)**: Специальная структура данных, которая ускоряет поиск в таблице, работая как предметный указатель в книге. Вместо полного сканирования таблицы (`Full Table Scan`) СУБД использует индекс для быстрого нахождения местоположения нужных строк.

- **B-Tree (B-дерево)**: Стандартный тип индекса в большинстве реляционных СУБД (PostgreSQL, MySQL). Это сбалансированная древовидная структура, хранящая данные в отсортированном виде. Идеален для операций сравнения в широком диапазоне: `=`, `>`, `<`, `BETWEEN`, `LIKE 'prefix%'`.

- **Hash-индекс (Hash Index)**: Индекс, хранящий хеш-коды значений столбца. Идеален только для операций точного равенства (`=`). Как правило, быстрее B-Tree для поиска по точному значению, но бесполезен для запросов по диапазону, так как хеши не сохраняют порядок.

- **Составной индекс (Composite Index)**: Один индекс, построенный на нескольких столбцах. Используется для ускорения запросов, фильтрующих данные по этим столбцам одновременно.

Индексы являются ключевым элементом оптимизации производительности. Подробнее о концепциях производительности см. в разделе: **[Ключевые концепции производительности баз данных](./database_performance_concepts.md)**.

## Основные концепции

### Принцип работы

Индекс содержит упорядоченный набор значений из индексируемых столбцов и прямые указатели на физическое расположение строк в таблице. Вместо последовательного просмотра каждой записи СУБД быстро находит нужные ключи в компактной и отсортированной структуре индекса и немедленно получает доступ к строкам.

### Порядок столбцов в составном индексе

Порядок столбцов в определении `CREATE INDEX` критически важен. Индекс `(last_name, city)` будет эффективно использоваться для поиска по `last_name` или по паре `last_name` и `city`. Однако он будет практически бесполезен для запроса, который фильтрует данные только по `city`.

### Специализированные индексы PostgreSQL

Помимо стандартных B-Tree и Hash, PostgreSQL поддерживает расширенный набор типов индексов для особых задач:

- **GIN (Generalized Inverted Index)**: Обобщённый инвертированный индекс. Оптимизирован для составных/сложных типов данных — `jsonb`, массивы, полнотекстовый поиск. Максимальная скорость поиска, но медленнее при записи и занимает больше места. Не применим к простым скалярным типам (числа, строки) без преобразования.
- **GiST (Generalized Search Tree)**: Обобщённое поисковое дерево. Эффективен для геоданных (PostGIS), векторов (AI/ML), диапазонов, полнотекстового поиска. Быстрее GIN при записи, компактнее по размеру, но медленнее при поиске. Поддерживает специфичные операторы (векторное расстояние, геометрические операции).
- **SP-GiST**: Расширение GiST с разбиением пространства. Работает с несбалансированными структурами — префиксные и камерные деревья, многомерные пространства.
- **BRIN (Block Range Index)**: Для очень больших таблиц с физически упорядоченными данными (временные ряды, лог событий). Хранит min/max для каждого блока страниц. Крайне компактный — помещается в кэш. Требует естественного порядка данных (например, монотонное возрастание `created_at`). Бесполезен для хаотичных данных. Аналог разреженных индексов в ClickHouse.
- **Hash**: Только для операций точного равенства (`=`). Не поддерживает диапазоны и `ORDER BY`. Быстрее B-Tree для точного поиска, но бесполезен при низкой селективности (например, колонка `status` с 3 значениями).

**Сравнение GIN vs GiST:**

| Критерий | GIN | GiST |
| :--- | :--- | :--- |
| Скорость поиска | Максимальная | Средняя |
| Скорость записи | Медленнее | Быстрее |
| Размер индекса | Больше | Компактнее |
| Полнотекстовый поиск | Оптимизирован | Поддерживается |
| Геоданные/векторы | Не поддерживает | Основной кейс |

Подробнее — **[Оптимизация производительности PostgreSQL](../PostgreSQL/Operations/performance_tuning.md)**.

## Практические сценарии

### 1. Ускорение запросов на чтение

Это основная задача индексов. Они значительно сокращают время выполнения запросов:

- с фильтрацией (`WHERE`)
- с сортировкой (`ORDER BY`)
- с соединениями (`JOIN` по индексированным столбцам)

### 2. Обеспечение уникальности данных

Уникальный индекс (`UNIQUE`) гарантирует отсутствие дубликатов в столбце или группе столбцов. Это быстрее и надежнее, чем проверка на уровне приложения.

### 3. Поддержка целостности данных

СУБД неявно создает уникальные индексы для реализации первичных ключей (`PRIMARY KEY`). Внешние ключи (`FOREIGN KEY`) также требуют наличия индексов на связанных столбцах для быстрой проверки целостности.

### 4. Алгоритм выбора типа индекса

1. **Только `=` без сортировки** → Hash (если высокая селективность)
2. **`=`, диапазоны, `ORDER BY`, `LIKE 'prefix%'`** → B-Tree (универсальный выбор)
3. **`jsonb`, массивы, полнотекстовый поиск** → GIN
4. **Геоданные, векторы, диапазоны, специфичные операторы** → GiST
5. **Большие упорядоченные таблицы (временные ряды)** → BRIN
6. **Остальные случаи** → B-Tree

### 5. Специальные техники индексации

**Функциональные индексы (индексы на выражения):** Создаются на результат функции, а не на колонку. Решают проблему, когда в `WHERE` используется функция поверх колонки.

```sql
-- Запрос с функцией — обычный индекс не применится
SELECT * FROM users WHERE lower(email) = 'john@example.com';

-- Решение: функциональный индекс
CREATE INDEX idx_users_lower_email ON users (lower(email));
```

**Покрывающие индексы (INCLUDE):** Поля в `INCLUDE` не индексируются, но хранятся в индексе. Позволяют получить данные без обращения к таблице (Index Only Scan).

```sql
-- Поля id и created_at не индексируются, но доступны для выборки
CREATE INDEX idx_orders_status ON orders (status) INCLUDE (id, created_at);

-- Запрос использует Index Only Scan
SELECT id, created_at FROM orders WHERE status = 'new';
```

**Pattern Ops для LIKE с суффиксом:** B-Tree работает с `LIKE 'prefix%'`, но не с `LIKE '%suffix'`. Для гарантированного применения индекса используются операторные классы:

```sql
-- Для типа text
CREATE INDEX idx_users_name_pattern ON users (name text_pattern_ops);

-- Для типа varchar
CREATE INDEX idx_users_name_pattern ON users (name varchar_pattern_ops);
```

> **Важно:** Локаль (collation) может препятствовать применению B-Tree индекса для `LIKE`. Pattern Ops решает эту проблему.

### 6. Поиск и удаление неиспользуемых индексов

Неиспользуемые индексы приносят только вред: они замедляют запись и занимают место. Их необходимо регулярно находить и удалять. В PostgreSQL для этого можно использовать представление `pg_stat_user_indexes`.

**Пример запроса для PostgreSQL:**

```sql
SELECT
    indexrelname AS index_name,
    relname AS table_name,
    idx_scan
FROM
    pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'; -- Исключаем первичные ключи
```

## Дополнительная информация

### Компромисс: Чтение vs. Запись

Индексы — это компромисс между скоростью чтения и скоростью записи.

- **Накладные расходы при записи**: Каждая операция `INSERT`, `UPDATE` или `DELETE` в таблицу требует обновления *всех* связанных с ней индексов. Это увеличивает объем дисковых операций и время блокировок.
- **Проблема низкой кардинальности**: Индекс на столбце с небольшим количеством уникальных значений (например, `boolean` или `пол`) практически бесполезен. СУБД почти всегда предпочтет полное сканирование таблицы, так как выборка по такому индексу неэффективна.
- **Затраты на хранение**: Индексы занимают дополнительное дисковое пространство, иногда превышающее объем самих данных.
- **Затраты на обслуживание**: При интенсивной записи структура индексов может деградировать (фрагментироваться), что требует периодической перестройки (`REINDEX`) — ресурсоемкой операции.

### Золотые правила управления индексами

- **Лимит 5-10 индексов на таблицу:** Больше индексов замедляют `UPDATE/INSERT` в разы (10-20 индексов → снижение производительности записи в 10+ раз).
- **Мониторинг неиспользуемых:** Еженедельная проверка статистики использования (`pg_stat_user_indexes`). Индексы с `idx_scan = 0` — кандидаты на удаление.
- **Осторожно с часто обновляемыми полями:** Индексы на колонках с частыми `UPDATE` — антипаттерн (раздувание из-за MVCC).
- **Мониторинг раздувания:** Регулярная проверка размера индексов. Для B-Tree на больших таблицах индекс может занимать 20-30 ГБ — не помещается в кэш.

### Составные индексы vs отдельные

- **Составной индекс:** Оптимален под конкретный запрос. Порядок колонок критичен — сравнение слева направо.
- **Несколько отдельных:** Могут комбинироваться через Bitmap Index Scan, но составной обычно эффективнее.
- **Решение:** Отталкиваться от запросов, анализировать `EXPLAIN ANALYZE`.
