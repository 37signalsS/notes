# Индексы

## 1. Определения

**Индекс** — это специальная структура данных, связанная с таблицей базы данных, предназначенная для ускорения операций поиска и извлечения данных. Индексы работают по принципу предметного указателя в книге или каталога в библиотеке.

## 2. Основные концепции

Индекс содержит упорядоченный набор значений из одного или нескольких столбцов таблицы и указатели на физическое расположение соответствующих строк данных. Это позволяет СУБД быстро находить нужные строки без полного сканирования всей таблицы.

*   **Как это работает:** Вместо того чтобы просматривать каждую запись в таблице (как если бы вы искали книгу на неоорганизованной полке), СУБД обращается к индексу (как к каталогу), который быстро указывает на точное местоположение искомых данных.
*   **Аналогия:** Представьте библиотечный каталог, где каждой книге соответствует карточка с ее названием, автором и указанием, на какой полке она находится. Чтобы найти книгу, вы пролистываете каталог (индекс), находите нужную карточку, а затем идете прямо к нужной полке (к данным), не просматривая все книги в библиотеке.

## 3. Практические сценарии использования

Индексы наиболее эффективны в следующих случаях:

*   **Ускорение запросов `SELECT`**: Значительно сокращают время выполнения запросов, использующих фильтрацию (`WHERE`), сортировку (`ORDER BY`) и соединения (`JOIN`) по индексированным столбцам.
*   **Уникальность данных**: Могут обеспечивать уникальность значений в столбце (например, уникальный индекс для email-адресов).
*   **Обеспечение целостности данных**: Используются для первичных и внешних ключей.

**Пример создания индекса (SQL):**
```sql
CREATE INDEX idx_users_lastname ON users (last_name);
```

## 4. Расширенные детали: Проблемы при избыточном количестве индексов

Наличие большого количества индексов может привести к проблемам производительности и увеличению накладных расходов:

*   **Накладные затраты при записи данных**: Каждая операция записи в таблицу также требует обновления всех связанных индексов. Это увеличивает объем операций записи в журнал транзакций (например, для таблицы с девятью некластеризованными индексами потребуется 10 операций записи — одна для таблицы и по одной для каждого индекса). Эти затраты особенно критичны внутри транзакций, где требуется поддержание актуального состояния индексов. Внетранзакционные затраты на чтение данных могут быть решены за счет масштабирования оборудования, тогда как затраты на запись и фиксацию изменений сократить сложнее.

*   **Накладные затраты на обслуживание индексов**: При интенсивной записи данных физическая структура индексов может стать неэффективной из-за появления "пропусков" (фрагментации). Это требует периодической дефрагментации или перестроения индексов, что снижает производительность СУБД во время этих операций.

*   **Влияние индексов на размер базы**: Индексы занимают дисковое пространство. Для средних OLTP баз данных объем индексов часто превышает объем самих данных, что может быть значительным для баз размером 150-200 ГБ и более.

*   **Затраты на создание и поддержание актуальной статистики**: Статистика базы данных, используемая оптимизатором запросов, должна регулярно обновляться при интенсивных операциях вставки и обновления. Это потребляет вычислительные ресурсы. Неактуальная статистика может привести к неоптимальным планам выполнения запросов и снижению производительности системы. Часто обновление статистики происходит в непиковые часы.

**Важно**: Индексы — это мощный инструмент для улучшения производительности чтения данных, и без них СУБД были бы малоэффективны. Однако, **плохи индексы, которые не используются**, так как они создают накладные расходы без предоставления какой-либо пользы.
