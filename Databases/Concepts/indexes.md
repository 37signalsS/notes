# Индексы в базах данных

## Определения

- **Индекс (Index)**: Специальная структура данных, которая ускоряет поиск строк в таблице, работая аналогично предметному указателю в книге. Вместо полного сканирования таблицы (**Full Table Scan**) СУБД обращается к индексу для получения прямых ссылок на нужные данные.
- **Селективность (Selectivity)**: Отношение количества уникальных значений к общему количеству строк. Чем выше селективность, тем эффективнее будет работать индекс.
- **Кардинальность (Cardinality)**: Количество уникальных значений в столбце. Столбцы с низкой кардинальностью (например, "пол" или "статус") обычно плохо подходят для индексации.
- **B-Tree (B-дерево)**: Наиболее распространенный тип индекса. Хранит данные в сбалансированном дереве в отсортированном виде, что позволяет эффективно выполнять поиск по равенству и диапазону (`=`, `<`, `>`, `BETWEEN`).
- **Инвертированный индекс (Inverted Index)**: Структура, сопоставляющая фрагменты данных (например, слова или элементы массива) со списком документов, в которых они встречаются. Основа для полнотекстового поиска.

## Базовые концепции

### Принцип работы

Индекс хранит значения одного или нескольких столбцов и указатель (**TID/ROWID**) на физическое расположение соответствующей строки на диске. При выполнении запроса СУБД сначала ищет значение в индексе, а затем выполняет **Index Scan** (переход к таблице за данными) или **Index Only Scan** (если все нужные данные уже есть в индексе).

### Порядок столбцов в составном индексе

В составных индексах (`INDEX (col1, col2)`) порядок критически важен. Индекс может использоваться эффективно, только если в условии `WHERE` указан самый левый префикс столбцов.
- Поиск по `col1` — **эффективно**.
- Поиск по `col1` и `col2` — **эффективно**.
- Поиск только по `col2` — **индекс не используется** (или используется крайне неэффективно).

### Типы индексов

1.  **B-Tree**: Универсальный выбор для большинства задач.
2.  **Hash**: Только для сравнения на равенство (`=`). Быстрее B-Tree, но не поддерживает диапазоны и сортировку.
3.  **Partial Index (Частичный индекс)**: Индекс, построенный только на части строк таблицы, соответствующих условию (например, `WHERE active = true`). Экономит место и ускоряет запись.
4.  **Functional Index (Индекс на выражение)**: Строится на результате функции (например, `LOWER(email)`). Позволяет использовать индекс при поиске без учета регистра.
5.  **Bitmap Index**: Эффективен для столбцов с низкой кардинальностью в хранилищах данных (OLAP), но плохо подходит для частых обновлений (OLTP).

## Практические сценарии

### 1. Покрывающие индексы (Covering Indexes)

Если индекс содержит все столбцы, запрашиваемые в `SELECT`, СУБД выполняет **Index Only Scan**. Это исключает дорогостоящую операцию обращения к основной таблице (Heap/Data files).
В современных СУБД для этого часто используется предложение `INCLUDE`.

```sql
CREATE INDEX idx_user_login ON users (email) INCLUDE (username, last_login);
```

### 2. Ускорение соединений (JOIN)

Индексы обязательны для внешних ключей (**Foreign Keys**). При выполнении `JOIN` СУБД использует индексы для быстрого сопоставления строк из разных таблиц. Без них сложность операции возрастает до квадратичной.

### 3. Сортировка и группировка

Поскольку B-Tree хранит данные в отсортированном виде, СУБД может использовать индекс для выполнения `ORDER BY` и `GROUP BY` без дополнительных затрат на сортировку в памяти (**Filesort**).

## Дополнительная информация

### Компромисс: Чтение vs. Запись

Индексы не бесплатны. Основные накладные расходы:
- **Замедление записи**: Каждый `INSERT`, `UPDATE` или `DELETE` требует обновления всех затронутых индексов.
- **Дисковое пространство**: Индексы часто занимают столько же места, сколько сама таблица, а иногда и больше.
- **Фрагментация**: При интенсивных обновлениях структура индекса становится менее плотной (появляются "дыры"), что требует периодического обслуживания (**REINDEX** или **VACUUM FULL** в зависимости от СУБД).

### Когда индекс вреден
- На маленьких таблицах (проще прочитать всю таблицу в память).
- На столбцах с очень низкой селективностью.
- При массовой вставке данных (часто выгоднее удалить индексы перед загрузкой и пересоздать их после).
