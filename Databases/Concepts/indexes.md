# Индексы в базах данных

## Определения

**Индекс** — это специальная структура данных, связанная с таблицей, предназначенная для ускорения операций поиска и извлечения данных. Индексы работают по принципу предметного указателя в книге: вместо полного сканирования таблицы СУБД использует индекс для быстрого нахождения местоположения нужных строк.

## Основные концепции

Индекс содержит упорядоченный набор значений из одного или нескольких столбцов и указатели на физическое расположение соответствующих строк.

*   **Как это работает:** Вместо того чтобы последовательно просматривать каждую запись в таблице (`Full Table Scan`), СУБД обращается к компактной и упорядоченной структуре индекса, которая быстро указывает на точное местоположение искомых данных.
*   **Аналогия:** Библиотечный каталог, где каждой книге соответствует карточка с указанием, на какой полке она находится. Чтобы найти книгу, вы используете каталог (индекс), а не просматриваете все книги подряд.

## Практические сценарии

### Основные случаи использования

Индексы наиболее эффективны в следующих случаях:

*   **Ускорение запросов `SELECT`**: Значительно сокращают время выполнения запросов с фильтрацией (`WHERE`), сортировкой (`ORDER BY`) и соединениями (`JOIN`) по индексированным столбцам.
*   **Обеспечение уникальности данных**: Уникальный индекс (например, для `email`) гарантирует отсутствие дубликатов в столбце.
*   **Поддержка целостности данных**: Неявно используются для реализации первичных (`PRIMARY KEY`) и внешних (`FOREIGN KEY`) ключей.

### Основные типы индексов

Хотя существуют различные типы, большинство баз данных поддерживают следующие базовые виды:

- **B-Tree (B-дерево):** Индекс по умолчанию в большинстве реляционных СУБД (включая PostgreSQL, MySQL, Oracle). Это сбалансированная древовидная структура, которая хранит данные отсортированными.
  - **Идеален для:** Операций сравнения в широком диапазоне: `=`, `>`, `<`, `BETWEEN`, `LIKE 'prefix%'`.
- **Hash-индекс:** Хранит хеш-коды значений столбца.
  - **Идеален для:** Только для операций точного равенства (`=`). Обычно компактнее и быстрее, чем B-Tree, для поиска по точному значению (например, ID).
  - **Ограничение:** Бесполезен для запросов по диапазону (`<`, `>`), так как хеш-коды не сохраняют порядка.

> Существуют и другие, более специализированные типы индексов, такие как **GIN** (для поиска в массивах и `jsonb`), **GiST** (для геопространственных данных) или **BRIN** (для очень больших, физически упорядоченных таблиц).

### Составные (Composite) индексы

Если запросы часто фильтруют данные по нескольким столбцам одновременно, имеет смысл создать один составной индекс вместо нескольких отдельных.

**Пример:**
```sql
-- Если часто выполняется запрос:
-- SELECT * FROM users WHERE last_name = 'Иванов' AND city = 'Москва';

-- Эффективнее создать один составной индекс:
CREATE INDEX idx_users_lastname_city ON users(last_name, city);
```
**Порядок столбцов в составном индексе критически важен.** СУБД может эффективно использовать такой индекс, если в условии `WHERE` используется первый столбец индекса, либо первые несколько столбцов в том же порядке.

## Дополнительная информация

### Проблемы и накладные расходы

Индексы — это компромисс между скоростью чтения и скоростью записи.

*   **Накладные расходы при записи (`INSERT`, `UPDATE`, `DELETE`):** Каждая операция записи в таблицу требует обновления *всех* связанных с ней индексов. Это кратно увеличивает объем дисковых операций и время блокировки.
*   **Низкая кардинальность:** Индекс на поле с небольшим количеством уникальных значений (например, `boolean` или пол) практически бесполезен, так как планировщик запросов почти всегда предпочтет полное сканирование таблицы.
*   **Увеличение размера базы данных:** Индексы занимают значительное дисковое пространство, иногда превышающее объем самих данных.
*   **Накладные расходы на обслуживание:** При интенсивной записи структура индексов может деградировать (фрагментироваться), что требует периодической перестройки (`REINDEX`) — ресурсоемкой операции.

### Поиск и удаление неиспользуемых индексов

**Неиспользуемые индексы приносят только вред:** они замедляют операции записи и занимают место, не давая никакой пользы для чтения. Их необходимо регулярно находить и удалять.

В PostgreSQL для поиска неиспользуемых индексов можно использовать системное представление `pg_stat_user_indexes`. Нулевое значение `idx_scan` говорит о том, что индекс ни разу не использовался с момента сбора последней статистики.

**Пример запроса для PostgreSQL:**
```sql
SELECT
    indexrelname AS index_name,
    relname AS table_name,
    idx_scan
FROM
    pg_stat_user_indexes
WHERE idx_scan = 0
  AND indexrelname NOT LIKE '%_pkey'; -- Исключаем первичные ключи
```
