# Индексы в базах данных

## Определения

- **Индекс (Index)** — специализированная структура данных, организованная для ускорения поиска строк в таблице. Работает по принципу предметного указателя: вместо полного сканирования таблицы (**Full Table Scan**) СУБД обращается к индексу для получения прямых ссылок на физическое расположение данных (адреса блоков или ключи кластеризации).
- **Селективность (Selectivity)** — отношение количества уникальных значений к общему количеству строк в таблице. Высокая селективность (близкая к 1.0, например, UUID) делает индекс максимально эффективным.
- **Кардинальность (Cardinality)** — абсолютное количество уникальных значений в столбце. Помогает оптимизатору оценить полезность индекса.
- **Страница / Блок (Page / Block)** — минимальная единица обмена данными между диском и оперативной памятью (Buffer Pool). Индексы хранятся и считываются постранично.
- **Куча (Heap)** — способ организации таблицы, при котором строки хранятся без определенного порядка. Некластеризованные индексы обычно указывают на записи в Heap через идентификатор строки (RID/TID).
- **Кластеризованный индекс (Clustered Index)** — структура, определяющая физический порядок хранения самих данных в таблице. Таблица является "индексно-организованной" (Index-Organized Table). Для таблицы возможен только один такой индекс.
- **Некластеризованный индекс (Non-Clustered Index)** — отдельная от данных структура, содержащая ключи и указатели на строки в основной таблице или на ключ кластеризованного индекса.
- **Раздувание индекса (Index Bloat)** — накопление неиспользуемого (пустого) пространства внутри страниц индекса из-за частых операций `UPDATE` и `DELETE`. Приводит к росту размера индекса и замедлению поиска.
- **Фактор заполнения (Fillfactor)** — параметр, определяющий процент заполнения страниц индекса при его создании или перестроении. Оставленное свободное место позволяет выполнять вставки без немедленного разделения страниц (Page Split).
- **Разделение страниц (Page Split)** — процесс деления переполненной страницы индекса на две. Приводит к фрагментации и дополнительным случайным записям на диск. Управляется параметром `fillfactor`.
- **Tablespace** — область хранения на диске, куда СУБД размещает файлы индексов. Позволяет SRE распределять горячие индексы по SSD, а холодные — по HDD или архивным хранилищам.

## Основные концепции

### Типы структур индексов

1.  **B-Tree (B-дерево):**
    *   Универсальный сбалансированный тип индекса. Данные хранятся в отсортированном виде.
    *   **Архитектура:** Корень (Root) → Ветви (Branches) → Листья (Leaves). Листья связаны двунаправленным списком для эффективного сканирования диапазонов.
    *   **Применение:** Операции сравнения (`=`, `<`, `>`, `<=`, `>=`), `BETWEEN`, `IN`, `IS NULL`, `ORDER BY`.
    *   **Сложность:** Поиск, вставка и удаление выполняются за $O(\log n)$.

2.  **Hash Index (Хеш-индекс):**
    *   Использует хеш-таблицу для хранения ключей.
    *   **Применение:** Только сравнение на точное равенство (`=`). Не поддерживает поиск диапазонов и сортировку.
    *   **Плюсы:** Чрезвычайно быстрый поиск при точных совпадениях.

3.  **Bitmap Index (Битовый индекс):**
    *   Хранит битовые маски для каждого уникального значения столбца.
    *   **Применение:** Столбцы с очень низкой кардинальностью (например, "Пол", "Статус заказа"). Эффективен в аналитических системах (OLAP) при комбинировании нескольких условий через `AND`/`OR`.
    *   **Минусы:** Плохо переносит частые обновления (блокировка всей битовой карты).

4.  **LSM-tree (Log-Structured Merge-tree):**
    *   Оптимизирован для систем с интенсивной записью. Изменения сначала накапливаются в памяти (MemTable), а затем сбрасываются на диск в виде упорядоченных файлов (SSTables).
    *   **Применение:** NoSQL базы (Cassandra, RocksDB), современные аналитические СУБД (ClickHouse).

### Принципы эффективного индексирования

1.  **Цена обслуживания:** Каждый индекс ускоряет чтение, но замедляет запись (`INSERT`, `UPDATE`, `DELETE`), так как СУБД должна обновлять индексные структуры транзакционно.
2.  **Индексация внешних ключей (Foreign Keys):** Практически всегда обязательна. Отсутствие индекса на FK приводит к полному сканированию подчиненной таблицы при проверке ограничений целостности или операциях `JOIN`.
3.  **Порядок в составных индексах (Composite Indexes):**
    *   Действует **правило левого префикса**. Индекс по `(A, B, C)` поможет при поиске по `(A)`, `(A, B)` или `(A, B, C)`, но будет бесполезен при поиске только по `(B)` или `(C)`.
    *   Наиболее селективные столбцы (с наибольшим количеством уникальных значений) обычно ставятся первыми.
4.  **Селективность и оптимизатор:** Если запрос выбирает более 20-30% строк таблицы, оптимизатор может решить, что **Sequential Scan** (полное сканирование) быстрее, чем использование индекса и последующие переходы к диску за данными.

### Архитектура хранения и фрагментация

Индексы хранятся в страницах фиксированного размера (обычно 8–16 КБ). При вставке данных, если страница заполнена выше `fillfactor`, СУБД выполняет **Page Split**:
1.  Выделяется новая страница.
2.  Около половины записей перемещается на новую страницу.
3.  Обновляется родительская страница.

**Результат:** фрагментация индекса, дополнительные случайные записи на диск, рост времени чтения.

**Снижение splits:**
-   Устанавливайте `fillfactor` ниже 100 для таблиц с частыми `UPDATE`/`DELETE` (например, 70–90).
-   Выполняйте `CLUSTER` или `REINDEX` после массовых изменений данных.

### Кластеризованные индексы в различных СУБД

Поведение кластеризованного индекса зависит от движка и определяет физический порядок строк:

| СУБД / Движок | Кластеризованный индекс | Особенности |
| :--- | :--- | :--- |
| **PostgreSQL** | `CLUSTER tbl USING idx_name;` | Перестраивает таблицу по индексу, но не поддерживает автоматическое поддержание порядка. |
| **MySQL InnoDB** | `PRIMARY KEY` | Первичный ключ всегда кластеризован. Вторичные индексы содержат PK как указатель. |
| **SQL Server** | `CLUSTERED` | Один на таблицу. Управление фрагментацией через `ALTER INDEX ... REBUILD`. |
| **Oracle** | `INDEX ORGANIZED TABLE (IOT)` | Данные хранятся в структуре индекса. Дополнительные индексы содержат `ROWID`. |
| **ClickHouse** | `ORDER BY` | Данные сортируются на диске по первичному ключу, но это не кластеризованный индекс в классическом понимании. |

### Tablespace и файловые группы

Распределение индексов по разным физическим устройствам позволяет снизить конкуренцию за I/O:
-   **PostgreSQL:** `CREATE INDEX ... TABLESPACE fast_ssp;`
-   **Oracle:** `CREATE INDEX ... TABLESPACE users;`
-   **SQL Server:** `CREATE INDEX ... ON filegroup_ssd;`

**Внимание:** После переноса индекса в другой tablespace обновите права доступа и проверьте пути в резервных скриптах.

## Практические сценарии

### 1. Покрывающие индексы (Covering Indexes)
Метод, при котором индекс содержит все столбцы, необходимые для выполнения запроса. СУБД выполняет **Index Only Scan**, не обращаясь к основной таблице.
*   **Реализация:** Предложение `INCLUDE` позволяет добавить неключевые столбцы в листья индекса. Доступно с PostgreSQL 11+, SQL Server 2005+, Oracle 12c+.
```sql
CREATE INDEX idx_orders_customer ON orders (customer_id) INCLUDE (order_date, total_amount);
```

### 2. Частичные индексы (Partial Indexes)
Индексирование только части строк, соответствующих условию. Это экономит место и ускоряет работу с актуальными данными.
```sql
-- Индекс только для активных пользователей (исключаем архивных)
CREATE INDEX idx_active_users_email ON users (email) WHERE status = 'active';
```

### 3. Функциональные индексы (Functional Indexes)
Индексация результата выражения или функции. Позволяет использовать индекс даже при трансформации данных в `WHERE`.
```sql
-- Поиск без учета регистра
CREATE INDEX idx_users_lower_email ON users (LOWER(email));
-- Запрос, использующий этот индекс:
-- SELECT * FROM users WHERE LOWER(email) = 'user@example.com';
```

### 4. Оптимизация пагинации (Seek Method)
Использование индексов для глубокой пагинации вместо `OFFSET`.
*   **Проблема:** `LIMIT 10 OFFSET 1000000` заставляет СУБД прочитать и отбросить миллион строк.
*   **Решение:** Использовать последнее значение индекса из предыдущей страницы.
```sql
SELECT * FROM messages WHERE id > :last_id ORDER BY id LIMIT 20;
```

## Операции и обслуживание

### 1. Создание индексов без блокировок

Для таблиц под нагрузкой обычный `CREATE INDEX` может заблокировать запись на длительное время. Используйте онлайн-построение:

| СУБД | Команда | Примечание |
| :--- | :--- | :--- |
| **PostgreSQL** | `CREATE INDEX CONCURRENTLY idx_name ON tbl (col);` | При аварийном прерывании индекс остаётся `INVALID` — удалите и повторите. |
| **MySQL 5.6+ (InnoDB)** | `ALTER TABLE tbl ADD INDEX idx_name (col), ALGORITHM=INPLACE, LOCK=NONE;` | По умолчанию `ALGORITHM=INPLACE` для InnoDB secondary индексов. |
| **SQL Server** | `CREATE INDEX idx_name ON tbl (col) WITH (ONLINE = ON);` | Требует Enterprise Edition. |
| **Oracle 12c+** | `CREATE INDEX idx_name ON tbl (col) ONLINE;` | Включено в Standard/Enterprise без доплат. |

### 2. Перестроение и дефрагментация

| СУБД | Команда | Что делает |
| :--- | :--- | :--- |
| **PostgreSQL** | `REINDEX INDEX idx_name;` | Пересоздает индекс. Начиная с PG 12, доступно `REINDEX CONCURRENTLY`. |
| **MySQL** | `OPTIMIZE TABLE tbl;` | Перестраивает таблицу и все её индексы. |
| **SQL Server** | `ALTER INDEX idx_name ON tbl REBUILD;` | Онлайн/офлайн перестроение с `FILLFACTOR`, `SORT_IN_TEMPDB`. |
| **Oracle** | `ALTER INDEX idx_name REBUILD;` | Поддерживает `PARALLEL` для больших объектов. |

### 3. Обновление статистик

Оптимизатор использует статистику по столбцам для выбора плана. Устаревшая статистика — частая причина игнорирования индексов:

| СУБД | Команда |
| :--- | :--- |
| **PostgreSQL** | `ANALYZE tbl;` |
| **MySQL** | `ANALYZE TABLE tbl;` |
| **SQL Server** | `UPDATE STATISTICS tbl WITH FULLSCAN;` |
| **Oracle** | `EXEC DBMS_STATS.GATHER_TABLE_STATS('schema', 'tbl');` |

Запускайте `ANALYZE` после массовых изменений или перестроения индексов.

### 4. Мониторинг здоровья индексов

Ключевые метрики для алертов:

| Метрика | Зачем следить | Порог алерта |
| :--- | :--- | :--- |
| **Размер индекса** | Оценка места на диске и RAM для Buffer Pool | Рост > 30% за неделю без роста данных |
| **Плотность листьев** | Оценка bloat | < 60% для B-Tree |
| **Сканирования (`idx_scan`)** | Поиск неиспользуемых индексов | `idx_scan = 0` в течение 7+ дней (кроме PK) |
| **Время последнего сканирования** | Поиск "мертвых" индексов | > 7 дней (PostgreSQL 16+) |
| **Page Splits** | Дисковые узкие места | Рост фрагментации > 30% |

**Примеры запросов:**

```sql
-- PostgreSQL: размер и использование индексов
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE relname = 'orders';

-- MySQL: статистика индексов (performance_schema)
SELECT OBJECT_SCHEMA, OBJECT_NAME, INDEX_NAME, COUNT_FETCH, COUNT_READ
FROM performance_schema.table_io_waits_summary_by_index_usage
WHERE OBJECT_SCHEMA = 'app';
```

### 5. Планирование обслуживания

Для high-load систем обслуживание индексов — часть Change Management:
-   **Окно обслуживания:** низкотрафиковые часы для `REINDEX`/`OPTIMIZE`.
-   **Онлайн-режим:** предпочитайте `CONCURRENTLY`/`ONLINE`/`INPLACE`.
-   **Шаблон для больших таблиц:** на таблицах >100 GB перестраивайте индексы по одному, чтобы не забить I/O.
-   **Валидация:** после обслуживания проверьте `EXPLAIN` и убедитесь, что оптимизатор использует перестроенные индексы.

## Влияние на репликацию и резервное копирование

### Влияние на репликацию

Каждое изменение индекса генерирует WAL (или эквивалент логической репликации). На активных системах массовое обслуживание индексов может вызвать **Replica Lag**:
-   **Физическая репликация:** WAL от `REINDEX`/`CLUSTER` может измеряться гигабайтами. Резкий рост WAL забивает сеть или disk queue на реплике.
-   **Логическая репликация:** изменения DDL и массовые перестроения передаются как DDL/CAPI, что может привести к таймаутам.

**Рекомендации:**
-   Выполняйте обслуживание последовательно, а не параллельно на всех таблицах.
-   Увеличьте `wal_keep_size` (PostgreSQL) или `binlog_cache_size` (MySQL) перед массовым обслуживанием.
-   Контролируйте задержку реплики через `pg_stat_replication` (PostgreSQL) или `SHOW REPLICA STATUS` (MySQL).

### Влияние на бэкапы и восстановление

-   **Размер бэкапа:** Index Bloat напрямую увеличивает размер физических бэкапов (`pg_basebackup`, `mysqldump --single-transaction` с индексами в файлах данных).
-   **Время восстановления (RTO):** При восстановлении СУБД должна прочитать и применить все индексные страницы. Чем больше bloat, тем дольше старт.
-   **Влияние на PITR:** В WAL содержится информация об изменениях индексов. Чем больше обслуживание, тем больше WAL для архивации.

**Рекомендации:**
-   Включайте в планирование бэкапов проверку размера индексов (`pg_relation_size`).
-   Убедитесь, что диск/объектное хранилище для WAL выдерживает пиковую нагрузку во время обслуживания.

## Поиск и устранение неисправностей (Troubleshooting)

### Неявное приведение типов (Implicit Type Casting)
Самая частая причина игнорирования индекса. Если столбец `phone` имеет тип `VARCHAR`, а в запросе передается число `WHERE phone = 12345`, СУБД применит функцию приведения к столбцу, что сделает индекс бесполезным.
*   **Решение:** Всегда передавать параметры в типе данных столбца.

### Невалидные индексы после аварийного прерывания

Индексы, созданные `CONCURRENTLY` (PostgreSQL) или `ONLINE` (Oracle/SQL Server), могут остаться в состоянии `INVALID`/`UNUSABLE`, если процесс был убит.
*   **Диагностика:** `pg_index.indisvalid = false` (PostgreSQL), `STATUS = UNUSABLE` (Oracle).
*   **Решение:** Удалите и пересоздайте индекс в офлайн-режиме или повторите онлайн-построение.

### Неиспользуемые индексы
Индексы, которые не помогают запросам, но потребляют ресурсы при записи и занимают место.
*   **Диагностика:** Использование системных представлений статистики (например, `pg_stat_user_indexes` в Postgres или `sys.dm_db_index_usage_stats` в SQL Server).

### Раздувание и фрагментация
При интенсивном удалении данных страницы индекса становятся полупустыми.
*   **Симптомы:** Рост размера индекса без роста объема данных, замедление запросов.
*   **Решение:** Регулярное обслуживание через `REINDEX` (Postgres), `OPTIMIZE TABLE` (MySQL) или `ALTER INDEX REBUILD` (SQL Server).

## Лучшие практики

1.  **Имена индексов:** Используйте понятные префиксы, например `idx_` (обычный), `uniq_` (уникальный), `fk_` (внешний ключ).
2.  **Анализ перед внедрением:** Всегда проверяйте план запроса с помощью `EXPLAIN` или `EXPLAIN ANALYZE` на репрезентативных данных.
3.  **Не индексируйте всё:** Начинайте с первичных ключей, внешних ключей и столбцов, используемых в наиболее частых и тяжелых запросах.
4.  **Удаляйте избыточность:** Если есть индекс по `(A, B)`, индекс по `(A)` является избыточным и должен быть удален.
5.  **Учитывайте влияние на WAL и репликацию:** Каждое изменение индекса генерирует WAL. На активных системах массовое обслуживание может вызвать **Replica Lag**. Распределяйте `REINDEX`/`OPTIMIZE` во времени.
6.  **Следите за fillfactor:** Для таблиц с частыми обновлениями снижайте `fillfactor` до 70–80%. Это уменьшает количество Page Splits.
7.  **Избегайте глобальных индексов на секционированных таблицах, если СУБД не поддерживает их эффективно:** В PostgreSQL (до v18) глобальные индексы отсутствуют. В Oracle/SQL Server глобальные индексы требуют перестроения при каждой операции `SPLIT PARTITION`.
8.  **Индексируйте столбцы фильтров логической репликации:** Если реплика настроена с фильтром по столбцу, индекс на этот столбец ускоряет применение изменений на реплике.
