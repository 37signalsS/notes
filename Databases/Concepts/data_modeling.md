**Актуально для:** PostgreSQL 16–18 / MySQL 8.0 / MariaDB 12–13 (12.3 LTS) / MongoDB 8.0–9.0 / Cassandra 5.x (2024–2026)

# Проектирование схемы БД: нормализация и моделирование данных

## Определения

**Проектирование схемы (Data Modeling)** — процесс определения структуры данных: какие сущности существуют, как они связаны, какие атрибуты хранит каждая сущность и какие ключи их идентифицируют. Результат — схема БД, которая одновременно гарантирует целостность данных и обеспечивает производительность типовых запросов.

**Нормализация (Normalization)** — процесс организации данных в реляционной БД, при котором каждая таблица содержит данные об одном типе сущности, а каждое значение зависит от ключа, целиком от ключа и ни от чего другого (правило Кодда). Цель — устранение аномалий вставки, обновления и удаления.

**Денормализация (Denormalization)** — сознательное нарушение нормальных форм ради производительности чтения: дублирование данных, объединение таблиц, вычисляемые колонки. Применяется там, где стоимость `JOIN` превышает стоимость поддержки избыточности.

**Сущность (Entity)** — объект реального мира, о котором хранятся данные (пользователь, заказ, товар). В схеме — таблица.

**Связь (Relationship)** — зависимость между сущностями. Типы по кардинальности: `1:1`, `1:N`, `M:N`.

**Ключи:**
- **Natural Key** — ключ из бизнес-данных (email, ИНН, артикул). Проблема: может измениться.
- **Surrogate Key** — суррогатный ключ, не имеющий бизнесного смысла (`serial`, `identity`, UUID). Генерация — в **[Генерация идентификаторов](./id_generation.md)**.
- **Candidate Key** — минимальный набор колонок, однозначно идентифицирующий строку.
- **Primary Key** — выбранный candidate key.
- **Foreign Key** — ссылка на PK другой таблицы, обеспечивает ссылочную целостность.

**Grain (Зерно)** — уровень детализации строки в таблице. Один из ключевых вопросов моделирования: «что означает одна строка?». См. также **[Моделирование хранилища данных](./dwh_modeling.md)**.

**ER-модель (Entity-Relationship)** — диаграммная нотация моделирования: сущности (прямоугольники), атрибуты (эллипсы), связи (ромбы с кардинальностью).

## Основные концепции

### Нормальные формы

Нормальные формы — последовательность всё более строгих правил. Каждая следующая форма предполагает выполнение предыдущих.

**1NF (First Normal Form):**
- Значения в каждой ячейке атомарны (неделимы).
- Нет повторяющихся групп и массивов в одной ячейке.
- Есть первичный ключ.
- *Нарушение:* колонка `phones` со списком номеров через запятую — нельзя индексировать и фильтровать по отдельному номеру.

**2NF (Second Normal Form):**
- 1NF + каждый неключевой атрибут полностью зависит от **всего** составного ключа, а не от его части.
- *Нарушение:* таблица `order_items(order_id, product_id, product_name, quantity)` — `product_name` зависит только от `product_id` (части ключа), а не от пары. Аномалия: при смене названия товара нужно обновить все строки заказов.

**3NF (Third Normal Form):**
- 2NF + каждый неключевой атрибут зависит от ключа **напрямую**, а не через другой неключевой атрибут (нет транзитивных зависимостей).
- *Нарушение:* `users(user_id, city, city_zip)` — `city_zip` зависит от `city`, а `city` — от ключа. Решение: отдельная таблица `cities(city, city_zip)`.

**BCNF (Boyce-Codd Normal Form):**
- 3NF + каждый детерминант (левая часть функциональной зависимости) является кандидатным ключом.
- *Нарушение:* таблица `enrollments(student, course, teacher)` с правилом «курс ведёт один преподаватель»: `course → teacher`, но `course` не является ключом. BCNF требует вынести `courses(course, teacher)`.

**4NF / 5NF:** устраняют многозначные зависимости (4NF) и зависимости соединения (5NF). Встречаются редко; для эксплуатации критичны первые три формы и BCNF.

### Аномалии, которые устраняет нормализация

| Аномалия | Суть | Пример (ненормализованная таблица заказов) |
| :--- | :--- | :--- |
| **Вставки** | Нельзя вставить строку без заполнения всех колонок | Нельзя добавить новый товар без заказа |
| **Обновления** | Одно значение хранится в N местах | Смена адреса клиента требует правки всех его заказов |
| **Удаления** | Удаление строки теряет несвязанные данные | Удаление последнего заказа теряет данные клиента |

### Денормализация: когда и почему

Нормализация — не самоцель. Денормализация оправдана, когда:

1. **Read-heavy нагрузка:** `JOIN` 5+ таблиц в горячем запросе дороже, чем поддержка избыточности.
2. **Аналитика (OLAP):** звездообразные схемы намеренно денормализованы — см. **[Моделирование хранилища данных](./dwh_modeling.md)**.
3. **Вычисляемые агрегаты:** счётчики (`comment_count`), итоговые суммы — обновляются триггером или приложением.
4. **NoSQL-модели:** embedding в MongoDB, широкие строки в Cassandra — принцип «locality over normalization». Теория — в **[Сравнение SQL и NoSQL](./sql_vs_nosql.md)**, примеры — в **[Моделирование MongoDB](../MongoDB/mongodb-modeling.md)** и **[Обзор Cassandra](../cassandra-scylladb/overview.md)**.

**Цена денормализации:** необходимость поддерживать консистентность избыточных копей (триггеры, приложение, CDC — см. **[CDC](./cdc_architectural_patterns.md)**), риск рассинхрона.

### Методология проектирования

1. **Собрать требования:** какие данные хранить, какие запросы выполняются (не только CRUD, но и отчёты, поиск, фильтры).
2. **Выделить сущности и связи:** ER-диаграмма с кардинальностью.
3. **Определить ключи:** surrogate PK для каждой таблицы (генерация — **[id_generation.md](./id_generation.md)**), FK для связей.
4. **Нормализовать до 3NF/BCNF:** устранить аномалии.
5. **Проверить против access patterns:** для каждого топ-20 запроса — `EXPLAIN`. Если план показывает seq scan или лишний JOIN — точечная денормализация или индекс (см. **[Индексы](./indexes.md)**).
6. **Задокументировать решения:** почему таблица денормализована, какая аномалия допускается.

### Кардинальность связей

| Тип | Реализация | Пример |
| :--- | :--- | :--- |
| **1:1** | FK в одной из таблиц с `UNIQUE` | `users` ↔ `user_profiles` (редко используемые поля) |
| **1:N** | FK в таблице «многие» | `orders.user_id → users.id` |
| **M:N** | Junction table с составным PK | `order_items` связывает `orders` и `products` |

Junction table для M:N должна иметь составной PK `(order_id, product_id)`. Он индексирует обращения по `order_id` (первый столбец) и по паре; для запросов только по `product_id` нужен второй индекс на `(product_id)` — как в Сценарии 1 (`idx_order_items_product`). Исключение: InnoDB хранит PK-колонки в конце каждого вторичного индекса, поэтому там индекс `(product_id)` фактически покрывает и `(product_id, order_id)`; в PostgreSQL такого расширения нет.

### Моделирование мультиарендности (multi-tenancy)

| Модель | Суть | Цена эксплуатации |
| :--- | :--- | :--- |
| **Shared table + `tenant_id`** | Все арендаторы в одних таблицах, колонка `tenant_id` в каждой | Один пул соединений; предикат по `tenant_id` в каждом запросе (или RLS); индексы — с `tenant_id` первым |
| **Schema per tenant** | Схема на арендатора в одной БД | Миграции — на каждую схему; управление `search_path` |
| **Database per tenant** | БД на арендатора | Пул соединений × N; бэкап, восстановление и миграции — по каждой БД |

PostgreSQL: общие таблицы защищаются Row-Level Security (с 9.5): политика фильтрует строки по контексту арендатора (`current_setting('app.tenant_id', true)`), включается `ALTER TABLE ... ENABLE ROW LEVEL SECURITY`. Владелец таблицы по умолчанию не подпадает под политики — `FORCE ROW LEVEL SECURITY` применяет их принудительно. Проверки целостности (PK/UNIQUE/FK) всегда обходят RLS: это защищает данные, но отклик ограничения может выдавать существование чужих строк — учитывать при проектировании.

### Выбор типа для перечислений

| Вариант | Плюсы | Минусы |
| :--- | :--- | :--- |
| `CHECK (col IN (...))` | Легко расширить в миграции (новое или заменённое ограничение) | Список — часть определения таблицы; нет единого типа |
| `ENUM` (PostgreSQL) | Тип БД, компактное хранение, порядок значений | Добавление значения — `ALTER TYPE ... ADD VALUE`: в PostgreSQL <12 нельзя внутри транзакции; в 12+ можно, но новое значение нельзя использовать до коммита текущей транзакции; сравнения с новым значением иногда медленнее |
| Справочная таблица + FK | Значения — данные: меняются без DDL, есть атрибуты и история | `JOIN` при каждом обращении; сложнее дефолт и валидация на уровне БД |

MySQL/MariaDB: добавление значения `ENUM` **в конец** списка — INPLACE (в 8.0.12+ может быть INSTANT), без копирования таблицы, пока не меняется размер хранения; вставка **в середину** — перенумерация существующих значений, требует COPY (полная копия таблицы, DML блокируется).

### Жизненный цикл строки: метки времени и удаление

- **Аудит-колонки:** `created_at timestamptz NOT NULL DEFAULT now()` и `updated_at` (триггером или приложением). `timestamptz`, а не `timestamp` — иначе время интерпретируется в локальной зоне сервера, и реплики в других зонах расходятся.
- **Soft delete:** `deleted_at timestamptz` вместо физического `DELETE` — сохраняется история, FK-ссылки не теряются. Цена: все запросы фильтруют `WHERE deleted_at IS NULL`, а `UNIQUE` блокирует повторное создание «удалённой» строки (в PostgreSQL/SQLite — частичный индекс `CREATE INDEX ... WHERE deleted_at IS NULL`).

## Практические сценарии

#### Предпосылки

- **Версии СУБД** — по scope-линии выше; поведение `ENUM` и RLS версионно-зависимо (см. разделы «Выбор типа для перечислений» и «Моделирование мультиарендности»).
- **Права:** `CREATE`/`ALTER` в целевой схеме (или роль владельца) для применения миграций; `SELECT` и право на `EXPLAIN` для проверки планов.
- **Среда:** staging-копия с репрезентативным объёмом данных — на пустой таблице `EXPLAIN ANALYZE` не покажет `Seq Scan`.

### Сценарий 1: Схема интернет-магазина (3NF)

```sql
-- Сущности
CREATE TABLE users (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email        text NOT NULL UNIQUE,
    created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE products (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    sku          text NOT NULL UNIQUE,   -- natural key, но PK surrogate
    name         text NOT NULL,
    price_cents  integer NOT NULL CHECK (price_cents >= 0)
);

-- Заказы: связь 1:N с users (FK в таблице «многие»)
CREATE TABLE orders (
    id           bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    user_id      bigint NOT NULL REFERENCES users(id),
    status       text NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now()
);

-- Junction table для M:N (заказ ↔ товар)
CREATE TABLE order_items (
    order_id     bigint NOT NULL REFERENCES orders(id) ON DELETE CASCADE,
    product_id   bigint NOT NULL REFERENCES products(id),
    quantity     integer NOT NULL CHECK (quantity > 0),
    price_cents  integer NOT NULL,  -- цена на момент заказа (историческая точность)
    PRIMARY KEY (order_id, product_id)
);

-- Индексы для access patterns (см. indexes.md)
CREATE INDEX idx_orders_user ON orders (user_id, created_at DESC);
CREATE INDEX idx_order_items_product ON order_items (product_id);
```

**Почему `price_cents` дублируется в `order_items`:** это не нарушение 3NF, а осознанная денормализация — цена товара меняется, а сумма заказа должна оставаться исторически точной.

### Сценарий 2: Точечная денормализация счётчика

```sql
-- Горячий запрос: «сколько комментариев у поста» без COUNT(*) по миллионам строк
ALTER TABLE posts ADD COLUMN comment_count integer NOT NULL DEFAULT 0;

-- Поддержка консистентности на уровне БД (триггером) или приложением.
-- Для высоконагруженных систем — инкремент в той же транзакции:
UPDATE posts SET comment_count = comment_count + 1 WHERE id = :post_id;
```

**Альтернатива без денормализации:** материализованное представление с периодическим `REFRESH` — см. **[Материализованные представления](./materialized_views.md)**.

### Сценарий 3: Антипаттерн EAV (Entity-Attribute-Value)

```sql
-- Антипаттерн: «универсальная» таблица атрибутов
CREATE TABLE entity_attributes (
    entity_id   bigint,
    attribute   text,   -- 'color', 'size', 'weight'
    value       text
);
```

**Проблемы:** невозможно задать типы колонок, `CHECK`-ограничения, FK; запросы превращаются в самосоединения; индексы неэффективны. Применяется только для редких, полиморфных атрибутов (см. `jsonb` в PostgreSQL — **[JSON-поддержка](../PostgreSQL/Concepts/json_support.md)**).

## Операции и команды

### Проверка схемы перед релизом

```bash
# 1. Структурная валидация миграций в CI (см. migrations/database-ci-cd.md)
# 2. Проверка плана каждого топового запроса
psql -c "EXPLAIN (ANALYZE, BUFFERS) SELECT ... " | grep -E "Seq Scan|Nested Loop"
# → при Seq Scan на большой таблице — проверить индексы и нормализацию

# 3. Поиск таблиц без PK (нарушение 1NF на практике)
psql -c "SELECT schemaname, tablename FROM pg_tables
WHERE schemaname='public' AND tablename NOT IN
(SELECT tablename FROM pg_indexes WHERE indexname LIKE '%pkey%');"

# 4. То же для MySQL/MariaDB (BASE TABLE без PRIMARY KEY)
mysql -N -e "SELECT table_schema, table_name FROM information_schema.tables
WHERE table_schema NOT IN ('mysql','sys','performance_schema','information_schema')
AND table_type='BASE TABLE'
AND (table_schema, table_name) NOT IN
(SELECT table_schema, table_name FROM information_schema.table_constraints
WHERE constraint_type='PRIMARY KEY');"
```

### Рефакторинг существующей схемы

1. Выделить транзитивную зависимость в отдельную таблицу (`CREATE TABLE cities ...`).
2. Заполнить её уникальными значениями (`INSERT INTO cities SELECT DISTINCT ...`).
3. Добавить FK и `NOT NULL`.
4. Удалить лишние колонки.
5. Всё — в рамках миграции с expand/contract: **[Expand/Contract](./migrations/expand_contract.md)**; откат изменений — **[Стратегии отката](./migrations/rollback_strategies.md)**.

## Поиск и устранение неисправностей

### Проблема: «Пере-normalization» — запросы с 10+ JOIN

**Симптомы:** план запроса показывает десятки `Nested Loop`, latency растёт, `EXPLAIN` показывает `Planning Time` сопоставимый с `Execution Time`.

**Причина:** схема нормализована «в лоб» без учёта access patterns.

**Решение:**
1. Собрать топ-20 запросов из `pg_stat_statements` / slow query log.
2. Для каждого — `EXPLAIN ANALYZE`.
3. Точечная денормализация или материализованное представление для read-only части.

### Проблема: аномалии обновления в денормализованных данных

**Симптомы:** `comment_count` не совпадает с `SELECT count(*) FROM comments`; отчёты расходятся.

**Причина:** инкремент/декремент выполняется вне транзакции с основной операцией, или приложение обновляет копию в другом месте.

**Решение:**
1. Обновление избыточного значения — в той же транзакции, что и основная операция.
2. Периодическая сверка (reconciliation job) с исправлением расхождений.
3. Для критичных агрегатов — материализованное представление или CDC-конвейер (**[CDC](./cdc_architectural_patterns.md)**).

### Проблема: полиморфные ассоциации

**Симптомы:** таблица `comments(entity_type, entity_id)` — FK невозможен, каскадное удаление не работает, запросы по одной сущности требуют фильтра по `entity_type`.

**Решение:** отдельные junction-таблицы для каждого типа сущности или `jsonb`/отдельные колонки.

### Проблема: отсутствие ограничений на junction table

**Симптомы:** дублирующиеся связи (`order_id, product_id` повторяется), orphan-строки после удаления родителя.

**Решение:** составной PK на junction table + `ON DELETE CASCADE`/`RESTRICT` на FK.

## Лучшие практики

1. **Начинайте с 3NF, денормализуйте по измеренным причинам.** Денормализация без метрик — оптимизация вслепую.
2. **Surrogate PK для каждой таблицы** — natural key может измениться; генерация — **[id_generation.md](./id_generation.md)**.
3. **Составной PK на M:N таблицах** — бесплатно даёт индекс для стороны-лидера; для обратных запросов — второй индекс на вторую колонку (в InnoDB он неявно расширяется PK-колонками).
4. **Историческая точность:** копируйте цену/статус в строку факта (как `price_cents` в `order_items`), а не ссылайтесь на текущие значения.
5. **Ограничения в БД, а не в приложении:** `CHECK`, `NOT NULL`, `UNIQUE`, FK — последняя линия обороны от грязных данных.
6. **Документируйте отклонения от 3NF:** комментарий в миграции — почему денормализовано и как поддерживается консистентность.
7. **Проверяйте планы до релиза:** `EXPLAIN (ANALYZE, BUFFERS)` на репрезентативных данных — часть CI (**[Database CI/CD](./migrations/database-ci-cd.md)**).
