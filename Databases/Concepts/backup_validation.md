# Проверка целостности и тестовое восстановление резервных копий

## Определения

**Проверка целостности (Integrity Check)** — процесс подтверждения того, что данные резервной копии не повреждены на физическом или логическом уровне и могут быть использованы для восстановления.

**Тестовое восстановление (Test Restore)** — регулярный процесс развертывания резервной копии в изолированной среде для подтверждения работоспособности стратегии восстановления и замера метрик RTO/RPO.

**RTO (Recovery Time Objective)** — целевое время восстановления; допустимый период простоя сервиса.

**RPO (Recovery Point Objective)** — целевая точка восстановления; допустимый объем потери данных в случае сбоя.

**Маскирование данных (Data Masking)** — процесс замены чувствительной информации (персональные данные, секреты) на реалистичные, но фиктивные данные при восстановлении в тестовые или аналитические среды.

## Основные концепции

Наличие успешно созданного архива не гарантирует возможность восстановления. Данные могут быть повреждены из-за деградации носителей (bit rot), ошибок в ПО бэкапа или сетевых сбоев.

### Проблема "Bit rot" (Тихая порча данных)

**Bit rot** — постепенная деградация физического носителя (воздействие космических лучей, деградация магнитных слоев или утечка заряда в SSD), приводящая к изменению отдельных бит данных без немедленного отказа диска. Бэкап, созданный с поврежденного носителя, будет бесполезен, если СУБД не обнаружит ошибку при чтении.

- **Механизмы защиты и Scrubbing:**
    - **Скраббинг (Scrubbing):** Процесс фонового перечитывания всех блоков данных и проверки их контрольных сумм.
    - **ZFS / Ceph:** Эти системы выполняют проверку целостности «на лету» (End-to-End Checksums). При обнаружении ошибки во время Scrubbing система автоматически восстанавливает поврежденный блок из зеркала или четности (Self-healing).
    - **Инструменты бэкапа:** Restic и Borg хранят хеши каждого чанка данных и проверяют их при операциях `check` или `scrub`.
    - **Облачные хранилища:** S3 гарантирует высокую надежность, но для исключения ошибок при передаче необходимо обязательно вычислять и проверять `Content-MD5` или `Checksum-SHA256` на стороне клиента.

### Уровни валидации

Проверка должна выполняться на нескольких уровнях для обеспечения полной уверенности:

1. **Физический (Checksum):** Проверка хеш-сумм файлов/блоков. Подтверждает, что данные в хранилище идентичны исходным.
2. **Логический (DB Integrity):** Проверка структуры СУБД (заголовки страниц, листы B-Tree индексов, системные каталоги). Подтверждает отсутствие повреждений внутри страниц данных.
    - **Инструменты:** `amcheck` (PostgreSQL) для поиска повреждений в индексах, `DBCC CHECKDB` (SQL Server).
3. **Дрейф схемы (Schema Drift):** Сравнение структуры восстановленной базы с эталонной (из Git или Production). Помогает выявить ситуации, когда бэкап был сделан в момент некорректной миграции.
4. **Функциональный (Smoke Test):** Запуск приложения поверх восстановленной БД и выполнение набора бизнес-запросов (например, "количество заказов за вчера").

### Маскирование данных (Data Masking)

При восстановлении бэкапов в среды разработки (Dev/Staging) критически важно удалять или подменять персональные данные (PII).

- **Продвинутые методы:**
    - **FPE (Format-Preserving Encryption):** Шифрование, сохраняющее формат данных (например, номер карты остается номером карты, но становится невалидным для оплаты). Это позволяет тестировать логику валидации без изменения кода приложения.
    - **Детерминированное маскирование:** Один и тот же входной ID всегда заменяется на один и тот же фиктивный ID, что сохраняет ссылочную целостность между связанными таблицами.
- **Архитектурный компромисс:**
    - **On-the-fly (на лету):** Данные маскируются в процессе выгрузки (дампа). Плюс: PII никогда не попадает на диск Dev-сервера. Минус: Нагрузка на Production БД при выгрузке.
    - **Static (после восстановления):** Полный бэкап восстанавливается в защищенную Sandbox-среду, маскируется скриптами, и только потом переносится в Dev.

## Практические сценарии

### Автоматизированный Smoke-тест (Bash)

После восстановления в Sandbox необходимо убедиться, что база готова к работе:

```bash
# 1. Проверка готовности СУБД принимать соединения
until pg_isready -h localhost -p 5432; do
  echo "Waiting for database..."
  sleep 2
done

# 2. Выполнение базовых ассертов (бизнес-проверка)
RECORD_COUNT=$(psql -t -c "SELECT count(*) FROM users WHERE created_at > now() - interval '24 hours'")
if [ "$RECORD_COUNT" -eq 0 ]; then
  echo "VALIDATION FAILED: No new users found in backup"
  exit 1
fi
```

### Sandbox Restore в Kubernetes (изолированные среды)

Использование эфемерных сред позволяет проводить валидацию без закупки постоянного оборудования:

1. **Namespace isolation:** Создание отдельного Namespace для каждой проверки.
2. **PVC Cloning:** Использование возможностей CSI-драйверов для мгновенного клонирования томов из бэкапа (если используется Storage-level backup).
3. **NetworkPolicies:** Полная блокировка внешнего трафика из Sandbox, чтобы тестовая база случайно не отправила реальные уведомления пользователям (защита от "Double Send").

### Встроенные инструменты СУБД

**PostgreSQL (pg_verifybackup):**
Инструмент для проверки физических бэкапов, созданных через `pg_basebackup`.

```bash
# Проверка манифеста и целостности всех файлов архива
pg_verifybackup /path/to/backup_directory
```

**MySQL (XtraBackup):**
Этап `prepare` является фактической проверкой: если Redo Log не удается применить к данным, бэкап считается поврежденным.

```bash
xtrabackup --prepare --target-dir=/data/backups/latest
```

## Мониторинг и метрики (SRE)

Валидация бэкапов должна быть прозрачной для систем мониторинга.

**Ключевые метрики (Prometheus):**
- `backup_last_validation_timestamp_seconds`: Время последней успешной проверки.
- `backup_validation_status`: Бинарный статус (1 - успех, 0 - провал).
- `backup_restore_duration_seconds`: Реальное время восстановления (для контроля RTO).
- `backup_integrity_errors_total`: Счетчик обнаруженных поврежденных блоков (Bit rot).
- `backup_schema_drift_detected`: Флаг обнаружения расхождения схем (1/0).

**Пример алерта (Alertmanager):**
```yaml
- alert: BackupValidationMissing
  expr: time() - backup_last_validation_timestamp_seconds > 86400 * 7
  labels:
    severity: warning
  annotations:
    summary: "Тестовое восстановление бэкапа не проводилось более недели"
```
