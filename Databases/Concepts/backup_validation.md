# Проверка целостности и тестовое восстановление резервных копий

## Определения

**Проверка целостности (Integrity Check)** — процесс подтверждения того, что данные резервной копии не повреждены на физическом или логическом уровне и могут быть использованы для восстановления.

**Тестовое восстановление (Test Restore)** — регулярный процесс развертывания резервной копии в изолированной среде для подтверждения работоспособности стратегии восстановления и замера метрик RTO/RPO.

**RTO (Recovery Time Objective)** — целевое время восстановления; допустимый период простоя сервиса.

**RPO (Recovery Point Objective)** — целевая точка восстановления; допустимый объем потери данных в случае сбоя.

**Маскирование данных (Data Masking)** — процесс замены чувствительной информации (персональные данные, секреты) на реалистичные, но фиктивные данные при восстановлении в тестовые или аналитические среды.

## Основные концепции

Наличие успешно созданного архива не гарантирует возможность восстановления. Данные могут быть повреждены из-за деградации носителей (bit rot), ошибок в ПО бэкапа или сетевых сбоев. Проверка должна выполняться на трех уровнях:

1. **Битовый уровень:** Проверка контрольных сумм (checksum) и метаданных файлов. Подтверждает, что данные в хранилище идентичны тем, что были отправлены.
2. **Логический уровень:** Проверка внутренней структуры данных СУБД (таблицы, индексы, системные каталоги). Подтверждает, что СУБД сможет открыть файлы без ошибок.
3. **Прикладной уровень (Smoke-тест):** Запуск приложения поверх восстановленных данных и выполнение базовых операций. Подтверждает целостность бизнес-логики.

### Уровни проверки

| Тип проверки | Объект | Частота (рек.) | Инструмент |
| :--- | :--- | :--- | :--- |
| **Верификация архива** | Хеш-суммы файлов | Ежедневно | `sha256sum`, `restic check` |
| **Логическая валидация** | Индексы, страницы БД | Еженедельно | `pg_verifybackup`, `DBCC CHECKDB` |
| **Тестовый Restore** | Весь сервис + приложение | Ежемесячно | CI/CD пайплайны, Ansible |
| **PITR-валидация** | Реплей логов (WAL/binlog) | Ежеквартально | `wal-g`, `pgBackRest` |

## Практические сценарии

### Проверка в Kubernetes (Velero)

Velero поддерживает автоматическую валидацию через хуки и интеграцию с `Restic`/`Kopia`.

```bash
# Проверка статуса последней операции бэкапа и его доступности
velero backup describe my-backup --details

# Проверка целостности данных в репозитории (Restic)
velero restic repo get
```

### Автоматизация через CI/CD (Sandbox Restore)

Использование пайплайнов (GitLab CI, GitHub Actions) для автоматического восстановления на временные инстансы:

1. **Trigger:** Завершение ночного бэкапа.
2. **Provision:** Создание временной ВМ или контейнера.
3. **Restore:** Развертывание данных из бэкапа.
4. **Anonymization:** Запуск скриптов маскирования данных.
5. **Validation:** Выполнение набора SQL-запросов или API-тестов.
6. **Report:** Отправка метрики времени восстановления в Prometheus/Grafana.
7. **Cleanup:** Удаление временных ресурсов.

### Встроенные инструменты СУБД

**PostgreSQL (pg_verifybackup):**
Инструмент для проверки физических бэкапов, созданных через `pg_basebackup`.

```bash
# Проверка манифеста и целостности файлов
pg_verifybackup /path/to/backup_directory
```

**MySQL (XtraBackup):**
Этап `prepare` является фактической проверкой целостности: если Redo Log не удается применить, бэкап поврежден.

```bash
xtrabackup --prepare --target-dir=/data/backups/latest
```

## Мониторинг и метрики (SRE)

Валидация бэкапов должна быть прозрачной для систем мониторинга.

**Ключевые метрики (Prometheus):**
- `backup_last_validation_timestamp_seconds`: Время последней успешной проверки.
- `backup_validation_status`: Бинарный статус (1 - успех, 0 - провал).
- `backup_restore_duration_seconds`: Реальное время восстановления (для контроля RTO).
- `backup_integrity_errors_total`: Счетчик обнаруженных поврежденных блоков.

**Пример алерта (Alertmanager):**
```yaml
- alert: BackupValidationMissing
  expr: time() - backup_last_validation_timestamp_seconds > 86400 * 7
  labels:
    severity: warning
  annotations:
    summary: "Тестовое восстановление бэкапа не проводилось более недели"
```
