# Проверка целостности и тестовое восстановление резервных копий

## Определения

- **Проверка целостности (Integrity Check):** Процесс подтверждения того, что данные резервной копии не повреждены, не изменены и могут быть успешно восстановлены.
- **Тестовое восстановление (Test Restore):** Процесс восстановления резервной копии в изолированной среде для проверки ее пригодности к использованию и соответствия целевым показателям восстановления (RTO/RPO).
- **RTO (Recovery Time Objective):** Целевое время восстановления — максимальное допустимое время простоя после сбоя.
- **RPO (Recovery Point Objective):** Целевая точка восстановления — максимально допустимый объем потери данных, выраженный во времени.
- **PITR (Point-in-Time Recovery):** Восстановление на произвольную точку во времени.

## Основные концепции

Проверка целостности и регулярное тестовое восстановление — обязательные практики эксплуатации систем резервного копирования. Архив может успешно создаваться и реплицироваться, но быть нечитаемым, частично повреждённым или непригодным для восстановления целевого сервиса. Целью является обнаружение битовой порчи, нарушений структуры, рассинхронизации метаданных и несовпадения версий/конфигураций, а также подтверждение того, что восстановление укладывается в целевые показатели по времени и объёму данных.

См. также: **[Стратегии резервного копирования](./backups.md)** для понимания типов бэкапов и **[Шифрование и сжатие](./backup_security.md)** для методов защиты данных.

Целостность рассматривается на нескольких уровнях: битовая (хеш-суммы и сравнение блоков), логическая (структура каталогов/БД), прикладная (сервис после восстановления корректно стартует и обрабатывает запросы). Тестовое восстановление имитирует реальные аварийные сценарии: от выборочной проверки файлов до развертывания изолированного окружения с реплеем транзакций и зависимостей.

### Техники контроля целостности

- **Контрольные суммы и манифесты:** Генерируются на источнике, проверяются на целевом хранилище с учётом порядка и набора файлов.

    ```bash
    find /backup/daily -type f -print0 | sort -z | xargs -0 sha256sum > manifest.sha256
    sha256sum -c manifest.sha256
    ```

- **Встроенные проверки репозитория бэкапа:** Многие специализированные инструменты для резервного копирования имеют встроенные функции проверки.
  - **PostgreSQL:**

        ```bash
        pg_basebackup --pgdata=/tmp/restore --write-recovery-conf --checksum-verification
        pg_verifybackup /tmp/restore
        ```

  - **MySQL/MariaDB (Percona XtraBackup):**

        ```bash
        xtrabackup --prepare --target-dir=/backups/2025-10-01
        ```
- **Проверка читаемости архивов и метаданных без полного извлечения.**
- **Консистентность баз данных на уровне движка.**
- **Сверка инвентаря:** Сопоставление каталога резервных копий с ожидаемыми наборами, сроками ретенции, тегами окружений.

## Практические сценарии

### Тестовое восстановление: уровни и сценарии

| Вид проверки | Что подтверждает | Пример инструмента |
| :----------- | :-------------- | :----------------- |
| Файловая выборка | Читаемость и корректные права | tar/borg extract (dry-run) |
| Частичное восстановление | Восстановление каталога/таблицы | restic restore --include; pg_restore --table |
| Полный сервис | Старт приложения и зависимостей | docker-compose/K8s namespace |
| Точечное во времени | Реплей журналов до целевой метки | WAL/binlog PITR |
| Репозиторий | Отсутствие порчи, дедупликация | restic/borg check |

### Сценарий 1: Проверка репозитория restic

```bash
# Проверка целостности всех пакетов в репозитории
restic -r s3:s3.example.com/backup check

# Проверка с чтением всех данных (медленнее, но надёжнее)
restic -r s3:s3.example.com/check --check-unused

# Тестовое восстановление случайного снапшота
restic -r s3:s3.example.com/backup restore latest --target /tmp/restore-test
```

### Сценарий 2: Проверка репозитория borgbackup

```bash
# Проверка целостности репозитория
borg check /path/to/repo

# Проверка конкретного архива
borg check /path/to/repo::archive-name

# Тестовое извлечение (dry-run)
borg extract --dry-run /path/to/repo::archive-name
```

### Сценарий 3: PostgreSQL — PITR с wal-g

```bash
# Проверка целостности WAL-архива
wal-g wal-fetch 000000010000000000000001 /tmp/test_wal

# Восстановление на точку во времени
wal-g backup-fetch /var/lib/postgresql/data LATEST
# Или на конкретную метку времени
wal-g backup-fetch /var/lib/postgresql/data "2025-03-25T10:00:00"
```

### Сценарий 4: PostgreSQL — pgBackRest verify

```bash
# Проверка целостности бэкапа
pgbackrest --stanza=main check

# Информация о доступных бэкапах
pgbackrest --stanza=main info

# Тестовое восстановление в отдельную директорию
pgbackrest --stanza=main --delta --pg1-path=/tmp/restore restore
```

### Сценарий 5: MySQL — проверка бэкапа Percona XtraBackup

```bash
# Подготовка бэкапа (применение логов)
xtrabackup --prepare --target-dir=/backups/2025-10-01

# Проверка возможности запуска (dry-run)
mysqld --datadir=/tmp/restore-test --skip-networking --dry-run
```

### Автоматизация и критерии приемки

- **Регулярность:** Самопроверка репозитория ежедневно; выборочное восстановление еженедельно; полнотекстовое восстановление критических систем по календарю.
- **Покрытие:** Ротация сценариев по сервисам и типам данных; в отчёт включать процент усреднённого чтения блобов.
- **Метрики:** Длительность восстановления, пропускная способность хранилища, ошибки целостности, соответствие таймбоксам.
- **Изоляция:** Восстановление в отдельные неймспейсы/ВМ, с маскированием секретов и отключёнными внешними интеграциями.
- **Трассируемость:** Протокол выполнения, версии инструментов, контрольные суммы до/после, артефакты логов для аудита.
