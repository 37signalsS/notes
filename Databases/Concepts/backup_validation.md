# Проверка целостности и тестовое восстановление резервных копий

## Определения

**Проверка целостности (Integrity Check)** — процесс подтверждения того, что данные резервной копии не повреждены на физическом или логическом уровне и могут быть использованы для восстановления.

**Тестовое восстановление (Test Restore)** — регулярный процесс развертывания резервной копии в изолированной среде для подтверждения работоспособности стратегии восстановления и замера метрик RTO/RPO.

**RTO (Recovery Time Objective)** — целевое время восстановления; допустимый период простоя сервиса.

**RPO (Recovery Point Objective)** — целевая точка восстановления; допустимый объем потери данных в случае сбоя.

**Маскирование данных (Data Masking)** — процесс замены чувствительной информации (персональные данные, секреты) на реалистичные, но фиктивные данные при восстановлении в тестовые или аналитические среды.

## Предварительные требования

Перед проведением валидации убедитесь, что инфраструктура и доступы настроены:

1. **Изолированная среда (Sandbox):** Отдельный сервер, виртуальная машина или namespace/Kubernetes-cluster, где восстановленная база не сможет повлиять на production. Доступ из sandbox к внешним сервисам должен быть заблокирован NetworkPolicy или firewall-правилами.
2. **Достаточное место на диске:** Объем должен покрывать размер самого большого бэкапа + временные файлы восстановления + WAL-архив для PITR. Рекомендуемый запас — 2x от размера бэкапа.
3. **Версии инструментов:** Клиентские утилиты (`pg_restore`, `xtrabackup`, `mysqlcheck`) должны быть той же мажорной версии, что и сервер, с которого был создан бэкап. Для PostgreSQL: `pg_dump` версии не ниже сервера.
4. **Доступы:** Роль с правами на чтение всего кластера (`pg_read_all_data` в PostgreSQL 14+, `SELECT` на все таблицы в MySQL) и возможность запуска инстанса на порту, не конфликтующем с production.
5. **Мониторинг:** Возможность замерить время восстановления (RTO) и проверить целостность данных после восстановления.
6. **Скрипты smoke-тестов:** Набор бизнес-запросов, который можно выполнить автоматически после восстановления для проверки корректности данных.

## Основные концепции

Наличие успешно созданного архива не гарантирует возможность восстановления. Данные могут быть повреждены из-за деградации носителей (bit rot), ошибок в ПО бэкапа или сетевых сбоев.

### Проблема "Bit rot" (Тихая порча данных)

**Bit rot** — постепенная деградация физического носителя (воздействие космических лучей, деградация магнитных слоев или утечка заряда в SSD), приводящая к изменению отдельных бит данных без немедленного отказа диска. Бэкап, созданный с поврежденного носителя, будет бесполезен, если СУБД не обнаружит ошибку при чтении.

- **Механизмы защиты и Scrubbing:**
    - **Скраббинг (Scrubbing):** Процесс фонового перечитывания всех блоков данных и проверки их контрольных сумм.
    - **ZFS / Ceph:** Эти системы выполняют проверку целостности «на лету» (End-to-End Checksums). При обнаружении ошибки во время Scrubbing система автоматически восстанавливает поврежденный блок из зеркала или четности (Self-healing).
    - **Инструменты бэкапа:** Restic и Borg хранят хеши каждого чанка данных и проверяют их при операциях `check` или `scrub`.
    - **Сетевые хранилища (NFS/SMB):** При передаче по сети необходимо вычислять и проверять контрольные суммы (`Content-MD5` или `Checksum-SHA256`) на стороне клиента. Это исключает ошибки при передаче и подтверждает целостность файла.

### Уровни валидации

Проверка должна выполняться на нескольких уровнях для обеспечения полной уверенности:

1. **Физический (Checksum):** Проверка хеш-сумм файлов/блоков. Подтверждает, что данные в хранилище идентичны исходным.
2. **Логический (DB Integrity):** Проверка структуры СУБД (заголовки страниц, листы B-Tree индексов, системные каталоги). Подтверждает отсутствие повреждений внутри страниц данных.
    - **Инструменты:** `amcheck` (PostgreSQL) для поиска повреждений в индексах, `DBCC CHECKDB` (SQL Server).
3. **Дрейф схемы (Schema Drift):** Сравнение структуры восстановленной базы с эталонной (из Git или Production). Помогает выявить ситуации, когда бэкап был сделан в момент некорректной миграции.
4. **Функциональный (Smoke Test):** Запуск приложения поверх восстановленной БД и выполнение набора бизнес-запросов (например, "количество заказов за вчера").

### Маскирование данных (Data Masking)

При восстановлении бэкапов в среды разработки (Dev/Staging) критически важно удалять или подменять персональные данные (PII).

- **Продвинутые методы:**
    - **FPE (Format-Preserving Encryption):** Шифрование, сохраняющее формат данных (например, номер карты остается номером карты, но становится невалидным для оплаты). Это позволяет тестировать логику валидации без изменения кода приложения.
    - **Детерминированное маскирование:** Один и тот же входной ID всегда заменяется на один и тот же фиктивный ID, что сохраняет ссылочную целостность между связанными таблицами.
- **Архитектурный компромисс:**
    - **On-the-fly (на лету):** Данные маскируются в процессе выгрузки (дампа). Плюс: PII никогда не попадает на диск Dev-сервера. Минус: Нагрузка на Production БД при выгрузке.
    - **Static (после восстановления):** Полный бэкап восстанавливается в защищенную Sandbox-среду, маскируется скриптами, и только потом переносится в Dev.
- **Практика:** Детальные инструкции по реализации для конкретных СУБД:
    - **[Анонимизация и маскирование в PostgreSQL](../PostgreSQL/Operations/anonymization.md)**
    - **[Динамическое маскирование в MariaDB (MaxScale)](../MariaDB/MaxScale/maxscale_overview.md)**

## Практические сценарии

### Автоматизированный Smoke-тест (Bash)

После восстановления в Sandbox необходимо убедиться, что база готова к работе:

```bash
# 1. Проверка готовности СУБД принимать соединения
until pg_isready -h localhost -p 5432; do
  echo "Waiting for database..."
  sleep 2
done

# 2. Выполнение базовых ассертов (бизнес-проверка)
RECORD_COUNT=$(psql -t -c "SELECT count(*) FROM users WHERE created_at > now() - interval '24 hours'")
if [ "$RECORD_COUNT" -eq 0 ]; then
  echo "VALIDATION FAILED: No new users found in backup"
  exit 1
fi
```

### Sandbox Restore в Kubernetes (изолированные среды)

Использование эфемерных сред позволяет проводить валидацию без закупки постоянного оборудования:

1. **Namespace isolation:** Создание отдельного Namespace для каждой проверки.
2. **PVC Cloning:** Использование возможностей CSI-драйверов для мгновенного клонирования томов из бэкапа (если используется Storage-level backup).
3. **NetworkPolicies:** Полная блокировка внешнего трафика из Sandbox, чтобы тестовая база случайно не отправила реальные уведомления пользователям (защита от "Double Send").

### Встроенные инструменты СУБД

**PostgreSQL (pg_verifybackup):**
Инструмент для проверки физических бэкапов, созданных через `pg_basebackup`.

```bash
# Проверка манифеста и целостности всех файлов архива
pg_verifybackup /path/to/backup_directory
```

**MySQL (XtraBackup):**
Этап `prepare` является фактической проверкой: если Redo Log не удается применить к данным, бэкап считается поврежденным.

```bash
xtrabackup --prepare --target-dir=/data/backups/latest
```

## Диагностика и устранение неисправностей

### Ошибка целостности при проверке бэкапа

**Симптомы:** `pg_verifybackup` завершается с ошибкой `backup integrity: FAILED`, `xtrabackup --prepare` не может применить Redo Log.

**Причины:** Повреждение носителя (bit rot), сбой сети при передаче, ошибка ПО бэкапа.

**Решение:**
1. Проверьте контрольные суммы исходных файлов на production: `sha256sum /var/lib/postgresql/data/base/...`
2. Проверьте файлы бэкапа на целостность: `pg_verifybackup /backup/pg_basebackup_2026-09-30`
3. Если файл поврежден — повторите бэкап с другого носителя. Если используется ZFS/Ceph — проверьте scrubbing.
4. Для XtraBackup: убедитесь, что `xtrabackup --prepare` завершается успешно перед удалением исходных файлов.

### Недостаточное место для тестового восстановления

**Симптомы:** Восстановление прерывается с ошибкой `No space left on device` на середине процесса.

**Причины:** Недостаточный запас места на диске sandbox-сервера.

**Решение:**
1. Подготовьте отдельный раздел/LUN размером не менее 2x от самого большого ожидаемого бэкапа.
2. Для PITR учитывайте дополнительный объем WAL-архива, который необходимо применить.
3. Используйте `df -h` перед началом восстановления. Минимальный порог для алерта — 20% свободного места.

### Долгое восстановление (RTO превышает SLA)

**Симптомы:** Тестовое восстановление занимает часы вместо допустимых минут.

**Причины:** Отсутствие параллелизма, недостаток `maintenance_work_mem`, медленный диск, восстановление на врачебном диске (HDD вместо NVMe).

**Решение:**
1. Используйте параллельное восстановление: `pg_restore -j 8`, `xtrabackup --copy-back` с параллельными потоками.
2. Увеличьте `maintenance_work_mem` до 2–4 GB на время восстановления.
3. Разместите WAL и данные на NVMe. Для PITR разместите `restore_command` на том же быстром диске, что и PGDATA.
4. Замерьте RTO регулярно — раз в квартал. Ведите историю изменений RTO при обновлении оборудования.

### Дрейф схемы (Schema Drift)

**Симптомы:** После восстановления приложение падает с ошибкой `column does not exist` или `relation does not exist`.

**Причины:** Бэкап был создан в момент, когда миграция схемы была выполнена на production, но не попала в репозиторий миграций (Flyway/Liquibase).

**Решение:**
1. Сравните схему восстановленной базы с эталонной из Git: `pg_dump --schema-only mydb_restored > restored.sql && diff -u expected.sql restored.sql`
2. Автоматизируйте проверку дрейфа схемы как часть smoke-теста.
3. Храните миграции в версионном контроле и применяйте их через конвейер CI/CD.

### Бэкап не проходит smoke-тест

**Симптомы:** Восстановление завершается успешно, но бизнес-запросы возвращают некорректные данные (нулевые значения, отсутствуют свежие записи).

**Причины:** Бэкап создан в момент неконсистентного состояния (например, DDL во время дампа), повреждение данных при передаче, устаревший бэкап.

**Решение:**
1. Выполните детерминированные проверки: `SELECT count(*) FROM users WHERE created_at > now() - interval '24 hours'` — результат должен совпадать с production.
2. Проверьте ссылочную целостность: `SELECT count(*) FROM orders o JOIN users u ON o.user_id = u.id WHERE u.id IS NULL;` — должно быть 0.
3. Проверьте временные метки: `SELECT max(created_at) FROM orders;` — дата не должна быть старше момента создания бэкапа.
4. Если smoke-тест падает — не удаляйте исходный бэкап немедленно. Повторите восстановление на другом сервере для исключения проблем с инфраструктурой.

### Ошибка маскирования данных (Data Masking)

**Симптомы:** После восстановления в Dev/Staging обнаруживаются реальные персональные данные (PII).

**Причины:** Маскирование не применялось, применялось с ошибками (например, `UPDATE` затронул не все строки), или маскирование выполнялось на production.

**Решение:**
1. Примените маскирование строго на sandbox-сервере после восстановления, но перед предоставлением доступа разработчикам.
2. Используйте детерминированное маскирование для сохранения ссылочной целостности: один и тот же ID всегда заменяется на один фиктивный ID.
3. Проверьте результат маскирования: `SELECT count(*) FROM users WHERE email LIKE '%@example.com';` — все адреса должны быть фиктивными.
4. Никогда не выполняйте маскирование на production. Это риск утечки данных и блокировок таблиц.

## Мониторинг и метрики (SRE)

Валидация бэкапов должна быть прозрачной для систем мониторинга.

**Ключевые метрики (Prometheus):**
- `backup_last_validation_timestamp_seconds`: Время последней успешной проверки.
- `backup_validation_status`: Бинарный статус (1 - успех, 0 - провал).
- `backup_restore_duration_seconds`: Реальное время восстановления (для контроля RTO).
- `backup_integrity_errors_total`: Счетчик обнаруженных поврежденных блоков (Bit rot).
- `backup_schema_drift_detected`: Флаг обнаружения расхождения схем (1/0).

**Пример алерта (Alertmanager):**
```yaml
- alert: BackupValidationMissing
  expr: time() - backup_last_validation_timestamp_seconds > 86400 * 7
  labels:
    severity: warning
  annotations:
    summary: "Тестовое восстановление бэкапа не проводилось более недели"
```

## Лучшие практики

1. **Автоматизируйте валидацию.** Никаких ручных проверок. Валидация должна запускаться по расписанию (cron, Kubernetes CronJob) и отправлять статус в мониторинг. Минимальная частота — раз в неделю для полных бэкапов, раз в день для критичных баз.
2. **Тестируйте на изолированном оборудовании.** Восстанавливайте бэкап на сервер, который не выполняет production-нагрузку. Это исключает влияние на продакшен и предотвращает случайную отправку уведомлений реальным пользователям.
3. **Валидируйте все уровни:** файловый checksum, логическую целостность СУБД (`pg_verifybackup`, `DBCC CHECKDB`), функциональный smoke-тест. Только комбинация трех уровней дает уверенность.
4. **Замеряйте реальный RTO.** Раз в квартал проводите учения по полному восстановлению на изолированном железе. Замерьте время от момента сбоя до возврата сервиса в работу. Сравните с заявленным SLO.
5. **Проверяйте PITR-готовность.** Самый частый источник ошибок — неработающая WAL-архивация. Проверяйте `pg_stat_archiver` (PostgreSQL) или `SHOW MASTER STATUS` (MySQL) после каждого создания бэкапа.
6. **Маскируйте данные до предоставления доступа.** Восстановите бэкап в sandbox → примените маскирование → только потом выдайте доступ разработчикам. Никогда не восстанавливайте production-бэкап напрямую в Dev-среду без маскирования.
7. **Храните скрипты валидации рядом с кодом.** Smoke-тесты, скрипты проверки целостности и runbook должны жить в том же репозитории, что и код приложения. Это упрощает поддержку при изменении схемы.
8. **Используйте Dead Man's Switch.** Настраивайте алерты не на "ошибку валидации", а на "отсутствие успешной валидации более N дней". Если скрипт упал и не отправляет метрики — алерт сработает.
9. **Не удаляйте исходный бэкап сразу после успешной валидации.** Храните последний удачный бэкап минимум один retention-период. Валидация может пройти, но восстановленное состояние может оказаться битым в редком сценарии.
10. **Проверяйте шифрование.** Если бэкап зашифрован — убедитесь, что KEK/ключевой файл доступен и процедура расшифровки работает. Раз в квартал выполняйте восстановление из зашифрованного бэкапа на isolated сервер.

## Особые случаи и ограничения

### Валидация PITR (Point-in-Time Recovery)

PITR сложнее валидировать, чем полный бэкап, потому что требует применить цепочку WAL-сегментов.

**Алгоритм проверки:**
1. Восстановите базовый бэкап в отдельный каталог.
2. Настройте `restore_command` на чтение из WAL-архива.
3. Запустите временный инстанс и убедитесь, что он доходит до `database system is ready to accept connections`.
4. Выполните детерминированный запрос: `SELECT max(created_at) FROM orders;` — временная метка должна совпадать с целевым моментом восстановления.
5. Убедитесь, что `pg_stat_archiver.last_archived_wal` обновляется и `failed_count = 0`.

### Валидация зашифрованных бэкапов

Зашифрованный бэкап может быть целостным, но ключ расшифровки может быть утерян.

**Проверки:**
1. Попробуйте расшифровать небольшой файл из бэкапа вручную: `gpg --decrypt backup.tar.zst.enc | gzip -t`
2. Убедитесь, что KEK/мастер-ключ доступен и хранится в отдельном хранилище от самого бэкапа.
3. Проверьте, что версия шифрования поддерживается целевой СУБД/инструментом (например, AES-GCM требует 96-битный Nonce).

### Валидация больших баз данных (> 1 ТБ)

Для больших баз полное восстановление на каждый тест экономически нецелесообразно.

**Оптимизации:**
1. Используйте дельта-восстановление: `pgBackRest --delta restore` — восстанавливает только измененные файлы поверх существующего каталога.
2. Валидируйте не всю базу, а критичные таблицы: `pg_restore -l dump.dump | grep -E 'TABLE|INDEX' | head -20`
3. Для логических бэкапов проверяйте количество строк в ключевых таблицах: `SELECT count(*) FROM users;` — сравните с production.
4. Используйте параллельное восстановление: `pg_restore -j 16` (не превышайте количество ядер CPU).

### Валидация после сбоя бэкапа (прерванное создание)

Если `pg_basebackup` или `xtrabackup` был прерван (сеть, нехватка места), полученный файл может быть неполным, но без явных ошибок.

**Проверки:**
1. Всегда проверяйте статус после создания: `pgBackRest info` должен показывать `status = OK`.
2. Для `pg_basebackup` проверяйте наличие `backup_manifest` и сравнивайте количество файлов с эталоном.
3. Никогда не удаляйте предыдущий валидный бэкап до подтверждения, что новый бэкап прошел все проверки.

### Ограничения логических бэкапов

- **Нет PITR:** Логические дампы (`pg_dump`, `mysqldump`) не содержат журналов транзакций. Валидация ограничивается проверкой содержимого дампа и восстановлением на момент создания.
- **Долгое восстановление:** Время восстановления растет пропорционально размеру БД. Для баз > 100 GB предпочитайте физические бэкапы.
- **Согласованность:** Логический дамп может содержать неконсистентное состояние, если во время дампа выполнялись DDL-операции. Используйте `--single-transaction` (MySQL) или дамп на readonly-реплике (PostgreSQL).

### Валидация в контейнерах (Docker/Kubernetes)

При восстановлении в контейнере убедитесь, что:
1. Persistent Volume (PV) достаточно размера для бэкапа + данных.
2. `emptyDir` не используется для `pg_wal` или файлов данных — при перезапуске пода данные будут утеряны.
3. В Kubernetes используйте `volumeClaimTemplate` с StorageClass на SSD/NVMe для временного PVC.
