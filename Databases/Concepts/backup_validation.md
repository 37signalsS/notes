# Проверка целостности и тестовое восстановление резервных копий

## Определения

- **Проверка целостности (Integrity Check)** — процесс подтверждения того, что данные резервной копии не повреждены, не изменены и могут быть успешно восстановлены.
- **Тестовое восстановление (Test Restore)** — процесс восстановления резервной копии в изолированной среде для проверки её пригодности к использованию и соответствия целевым показателям восстановления (RTO/RPO).
- **RTO (Recovery Time Objective)** — целевое время восстановления; максимальное допустимое время простоя после сбоя.
- **RPO (Recovery Point Objective)** — целевая точка восстановления; максимально допустимый объём потери данных, выраженный во времени.
- **PITR (Point-in-Time Recovery)** — технология восстановления данных на произвольный момент времени в прошлом.

## Основные концепции

Проверка целостности и регулярное тестовое восстановление являются критическими процессами в жизненном цикле управления данными. Наличие успешно созданного архива не гарантирует возможность восстановления сервиса: данные могут быть повреждены на уровне блоков (bit rot), иметь нарушенную логическую структуру или быть несовместимыми с текущей версией СУБД/приложения.

Целостность данных оценивается на трёх уровнях:

1. **Битовый уровень:** проверка хеш-сумм и отсутствие повреждений на физическом носителе.
2. **Логический уровень:** проверка структуры каталогов, таблиц и индексов базы данных (например, через `CHECKBLOCKS`).
3. **Прикладной уровень:** подтверждение работоспособности сервиса после восстановления (успешный старт процессов, прохождение smoke-тестов).

Для понимания общей архитектуры систем резервного копирования см. **[Стратегии резервного копирования](./backups.md)**, а для методов защиты данных — **[Шифрование и сжатие](./backup_security.md)**.

### Уровни тестового восстановления

| Вид проверки | Что подтверждает | Пример инструмента |
| :----------- | :-------------- | :----------------- |
| Файловая выборка | Читаемость файлов и корректность прав доступа | tar, borg extract (dry-run) |
| Частичное восстановление | Возможность извлечения конкретного каталога или таблицы | restic restore --include, pg_restore --table |
| Полный сервис | Успешный запуск приложения со всеми зависимостями | docker-compose, K8s namespace |
| Точечное восстановление | Корректный реплей журналов (WAL/binlog) до целевой метки | PITR механизмы (WAL-G, binlog) |
| Целостность репозитория | Отсутствие порчи данных внутри дедуплицированного хранилища | restic check, borg check |

## Практические сценарии

### Техники контроля целостности

Генерация и проверка контрольных сумм с использованием манифестов (универсальный метод):

```bash
# Создание манифеста
find /backup/daily -type f -print0 | sort -z | xargs -0 sha256sum > manifest.sha256

# Проверка по манифесту
sha256sum -c manifest.sha256
```

### Встроенные инструменты СУБД

**PostgreSQL:**

```bash
# Проверка целостности физического бэкапа
pg_verifybackup /path/to/backup

# Проверка в процессе создания (checksum verification)
pg_basebackup --pgdata=/tmp/restore --write-recovery-conf --checksum-verification
```

**MySQL / MariaDB (Percona XtraBackup):**

```bash
# Применение логов для подготовки к восстановлению (фактическая проверка консистентности)
xtrabackup --prepare --target-dir=/backups/2025-10-01
```

### Проверка специализированных репозиториев

**Restic:**

```bash
# Полная проверка структуры репозитория
restic -r s3:s3.example.com/backup check

# Глубокая проверка с чтением всех данных (рекомендуется проводить реже из-за нагрузки на сеть/IO)
restic -r s3:s3.example.com/backup check --read-data
```

**BorgBackup:**

```bash
# Проверка целостности индексов и сегментов данных
borg check /path/to/repo

# Эмуляция извлечения (dry-run)
borg extract --dry-run /path/to/repo::archive_name
```

### Проверка PITR (восстановление на точку во времени)

**WAL-G (PostgreSQL):**

```bash
# Проверка доступности WAL-сегментов и извлечение базового бэкапа
wal-g backup-fetch /var/lib/postgresql/data "2025-03-25T10:00:00"
```

**pgBackRest:**

```bash
# Проверка консистентности файлов внутри бэкапа
pgbackrest --stanza=main --delta --pg1-path=/tmp/restore restore
```

### Автоматизация и критерии приемки

Для обеспечения надежности системы восстановления необходимо внедрить следующие практики:

- **Регулярность:** автоматическая самопроверка репозиториев (ежедневно), выборочное восстановление (еженедельно), полномасштабное учение по восстановлению (ежеквартально).
- **Изоляция:** проведение тестов в выделенных окружениях (sandbox) с маскированием чувствительных данных.
- **Метрики:** фиксация реального времени восстановления и сравнение его с целевым RTO.
- **Трассируемость:** сохранение логов процесса восстановления и отчётов о проверке контрольных сумм для аудита.
