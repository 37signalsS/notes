# ACID: Свойства транзакций

## Определения

**ACID** — это набор из четырех ключевых свойств (Atomicity, Consistency, Isolation, Durability), гарантирующих надежность обработки данных и целостность базы данных при выполнении транзакций.

**Транзакция** — логическая единица работы с базой данных, состоящая из одной или нескольких операций (чтение, запись, удаление), которая должна быть выполнена либо целиком, либо не выполнена вовсе.

## Основные концепции

### Свойства ACID

- **Atomicity (Атомарность):** Принцип "все или ничего". Транзакция фиксируется (**commit**) только если все её операции выполнены успешно. Если хотя бы одна операция дает сбой, вся транзакция откатывается (**rollback**), и база возвращается в состояние до начала транзакции. Подробнее: **[Атомарные операции](../../Concepts/atomic_operations.md)**.
- **Consistency (Согласованность):** Гарантирует, что транзакция переводит базу данных из одного допустимого (валидного) состояния в другое. База данных должна соблюдать все определенные правила: целостность типов, ограничения (constraints), триггеры и связи между таблицами (Foreign Keys).
- **Isolation (Изолированность):** Обеспечивает независимость параллельно выполняемых транзакций. Результат работы нескольких транзакций должен быть таким же, как если бы они выполнялись последовательно.
- **Durability (Долговечность):** Гарантирует, что изменения, внесенные зафиксированной транзакцией, сохранятся даже в случае системного сбоя (отключение питания, крах процесса). Реализуется через запись данных на энергонезависимый носитель и использование **[журнала предзаписи (WAL)](./write_ahead_log.md)**.

### Уровни изоляции и аномалии

Идеальная изоляция (Serializable) требует больших ресурсов. Для баланса производительности и надежности стандарт SQL определяет уровни изоляции, предотвращающие различные аномалии.

#### Аномалии чтения (Феномены)
1. **Грязное чтение (Dirty Read):** Транзакция видит незафиксированные изменения другой транзакции.
2. **Неповторяющееся чтение (Non-repeatable Read):** Повторное чтение тех же данных в рамках одной транзакции дает другой результат, так как другая транзакция успела их изменить и зафиксировать.
3. **Фантомное чтение (Phantom Read):** Повторный запрос с тем же условием возвращает другой набор строк (появились новые или исчезли старые), так как другая транзакция добавила/удалила записи.

#### Аномалии записи
- **Dirty Write (Грязная запись):** Транзакция перезаписывает значение, которое уже было изменено другой, еще не зафиксированной транзакцией. Почти все СУБД предотвращают это на всех уровнях.
- **Lost Update (Потерянное обновление):** Две транзакции одновременно читают значение, изменяют его и записывают обратно. Вторая транзакция затирает изменения первой, не учитывая их.
- **Write Skew (Аномалия записи):** Две транзакции читают данные, на основе которых принимают решение об обновлении разных объектов. По отдельности транзакции корректны, но вместе нарушают инвариант (например, два врача одновременно уходят с дежурства, хотя минимум один должен остаться).

| Уровень изоляции | Грязное чтение | Неповторяющееся чтение | Фантомное чтение | Lost Update |
| :--- | :---: | :---: | :---: | :---: |
| **Read Uncommitted** | Допустимо | Допустимо | Допустимо | Допустимо |
| **Read Committed** | Предотвращено | Допустимо | Допустимо | Допустимо |
| **Repeatable Read** | Предотвращено | Предотвращено | Допустимо | Предотвращено* |
| **Serializable** | Предотвращено | Предотвращено | Предотвращено | Предотвращено |

*\* В ряде СУБД (например, PostgreSQL) Repeatable Read реализован через Snapshot Isolation и предотвращает Lost Update.*

#### Snapshot Isolation (Изоляция снимков)
Современный уровень изоляции, при котором транзакция видит "снимок" данных на момент своего начала. Читающие транзакции никогда не блокируют пишущие. SI предотвращает большинство аномалий, кроме **Write Skew**.

### Механизмы реализации

Для обеспечения свойств ACID современные СУБД используют следующие подходы:

- **Блокировки (Locking):**
  - **2PL (Two-Phase Locking):** Протокол двухфазной блокировки. Сначала транзакция только набирает блокировки (фаза роста), затем только освобождает (фаза сжатия). Гарантирует Serializable.
- **MVCC (Multi-Version Concurrency Control):** Позволяет транзакциям работать с разными версиями одних и тех же данных. Читающие транзакции не блокируют пишущие, и наоборот. Основа для Read Committed и Snapshot Isolation.
- **Write-Ahead Logging (WAL):** Все изменения сначала записываются в последовательный журнал на диске, и только потом применяются к основным файлам данных. Гарантирует **Durability**.
- **Shadow Paging:** Метод, при котором изменения вносятся в копии страниц данных. Атомарное переключение указателя на новые страницы обеспечивает **Atomicity**.

## Практические сценарии

### Пример: Банковский перевод
Перевод 1000 рублей со счета А на счет Б.

```sql
BEGIN TRANSACTION;
UPDATE accounts SET balance = balance - 1000 WHERE id = 'A';
UPDATE accounts SET balance = balance + 1000 WHERE id = 'B';
COMMIT;
```

Как свойства ACID защищают эту операцию:
- **Атомарность:** Если сервер упадет после списания с А, но до зачисления на Б, после перезапуска СУБД откатит списание. Деньги не пропадут "в никуда".
- **Согласованность:** Если в БД есть ограничение `CHECK (balance >= 0)`, и на счету А всего 500 рублей, транзакция завершится ошибкой на первом шаге, не нарушив правила бизнеса.
- **Изолированность:** Внешний наблюдатель не увидит момента, когда 1000 рублей уже ушли с А, но еще не пришли на Б.
- **Долговечность:** После подтверждения `COMMIT` изменения сохранятся даже при полном отказе оборудования.

### Распределенные транзакции
В распределенных системах ACID реализовать сложнее из-за сетевых сбоев.
- **2PC (Two-Phase Commit):** Протокол двухфазной фиксации, обеспечивающий атомарность между разными узлами.
- **Saga Pattern:** Используется в микросервисах как альтернатива ACID, обеспечивая итоговую согласованность (Eventual Consistency) через компенсирующие транзакции.

## Дополнительная информация

Важно различать **Consistency** в ACID и в CAP-теореме:
- В ACID это **целостность** (соблюдение инвариантов системы).
- В CAP это **согласованность** (одинаковость данных на всех узлах в один момент времени).

Многие NoSQL-системы используют модель **BASE** (Basically Available, Soft state, Eventual consistency), где строгая согласованность приносится в жертву ради высокой доступности и горизонтального масштабирования. См. также: **[SQL vs NoSQL (ACID vs BASE)](./sql_vs_nosql.md)**.
