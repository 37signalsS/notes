# ACID: Свойства транзакций

## Определения

**ACID** — это аббревиатура из четырех ключевых свойств (Atomicity, Consistency, Isolation, Durability), гарантирующих надежность обработки данных и целостность базы данных при выполнении транзакций. Эти принципы являются золотым стандартом для реляционных СУБД (RDBMS) и критически важны для систем, где потеря или искажение данных недопустимы (финансы, инвентаризация, медицина).

**Транзакция** — логическая единица работы с базой данных, состоящая из одной или нескольких операций (чтение, запись, удаление), которая переводит систему из одного согласованного состояния в другое. Она должна быть выполнена либо целиком, либо не выполнена вовсе.

## Основные концепции

### Детальный разбор свойств ACID

#### Atomicity (Атомарность)
Принцип "все или ничего". Транзакция фиксируется (**commit**) только если все её операции выполнены успешно. Если хотя бы одна операция дает сбой, вся транзакция откатывается (**rollback**), и база возвращается в состояние, в котором она была до начала транзакции. 
- **Механизм:** Реализуется через Undo-логи (в MVCC) или Shadow Paging.

#### Consistency (Согласованность)
Гарантирует, что транзакция переводит базу данных из одного валидного состояния в другое. 
Важно различать два уровня согласованности:
1.  **Физическая согласованность:** Целостность внутренних структур данных (B-деревья, страницы памяти), отсутствие битых ссылок на уровне движка БД.
2.  **Логическая (Бизнес-) согласованность:** Соблюдение правил, определенных схемой данных:
    *   **Constraints (Ограничения):** `NOT NULL`, `UNIQUE`, `CHECK`.
    *   **Foreign Keys:** Ссылочная целостность.
    *   **Triggers:** Автоматические проверки.
*Примечание: БД гарантирует соблюдение ограничений, но за логику приложения (например, чтобы сумма всех счетов была константой) отвечает разработчик.*

#### Isolation (Изолированность)
Обеспечивает независимость параллельно выполняемых транзакций. Результат работы нескольких транзакций должен быть таким же, как если бы они выполнялись строго последовательно. Идеальная изоляция требует огромных ресурсов, поэтому СУБД предлагают различные уровни компромисса между скоростью и надежностью.

#### Durability (Долговечность)
Гарантирует, что изменения, внесенные зафиксированной транзакцией, сохранятся даже в случае системного сбоя (отключение питания, крах ОС). 
- **Write Penalty:** Каждая запись требует подтверждения от дисковой подсистемы (`fsync`). 
- **Механизм:** Изменения сначала попадают в **[журнал предзаписи (WAL)](./write_ahead_log.md)**, который сбрасывается на диск перед тем, как транзакция будет считаться завершенной.

### Уровни изоляции и аномалии

Стандарт SQL-92 определяет уровни изоляции через аномалии чтения, которые они предотвращают.

#### Аномалии чтения (Феномены)
1.  **Грязное чтение (Dirty Read):** Транзакция читает данные, измененные другой транзакцией, которая еще не зафиксировала. Если та транзакция откатится, данные окажутся ложными.
2.  **Неповторяющееся чтение (Non-repeatable Read):** При повторном чтении одной и той же строки внутри транзакции данные оказываются изменены (другая транзакция обновила и зафиксировала их).
3.  **Фантомное чтение (Phantom Read):** Повторный запрос с тем же условием `WHERE` возвращает другой набор строк (появились новые или исчезли старые), так как другая транзакция выполнила `INSERT` или `DELETE`.
4.  **Read Skew (Перекос чтения):** Аномалия в Snapshot Isolation. Транзакция видит рассогласованное состояние данных, если она читает связанные объекты, которые были обновлены двумя разными транзакциями.

#### Аномалии записи
- **Lost Update (Потерянное обновление):** Классическая проблема `Read-Modify-Write`. Две транзакции одновременно читают значение, изменяют его локально и записывают обратно. Последняя запись просто затирает первую.
- **Write Skew (Аномалия записи):** Возникает, когда две транзакции читают один и тот же набор данных, но обновляют *разные* объекты, нарушая общий инвариант.
    *   *Пример:* Два врача на дежурстве. Правило: минимум один должен остаться. Оба одновременно решают уйти, проверяют `SELECT count(*) FROM doctors WHERE status = 'on-duty'`, видят "2", и оба переводят свой статус в 'off-duty'. В итоге — 0 врачей.

#### Таблица уровней изоляции

| Уровень изоляции | Dirty Read | Non-repeatable Read | Phantom Read | Lost Update |
| :--- | :---: | :---: | :---: | :---: |
| **Read Uncommitted** | Допустимо | Допустимо | Допустимо | Предотвращено* |
| **Read Committed** | Предотвращено | Допустимо | Допустимо | Предотвращено* |
| **Repeatable Read** | Предотвращено | Предотвращено | Допустимо | Допустимо |
| **Serializable** | Предотвращено | Предотвращено | Предотвращено | Предотвращено |

*\* Большинство современных СУБД предотвращают Dirty Write на любом уровне.*

### Механизмы реализации транзакционности

1.  **Блокировки (Locking):**
    *   **Пессимистичная:** СУБД блокирует данные сразу при чтении/записи, чтобы никто другой не мог их изменить.
    *   **Оптимистичная (OCC):** Транзакция выполняется без блокировок, но в момент `COMMIT` проверяется, не изменил ли кто-то данные. Если конфликт найден — откат. Эффективно при малом количестве конфликтов.
    *   **2PL (Two-Phase Locking):** Гарантирует Serializable через фазы накопления и освобождения блокировок.

2.  **MVCC (Multi-Version Concurrency Control):**
    Основной механизм в PostgreSQL, Oracle, MySQL (InnoDB). Каждая транзакция работает с "версией" данных. Читающие не блокируют пишущих, и наоборот.
    *   **Snapshot Isolation (SI):** Транзакция видит снимок базы на момент начала. Позволяет избежать большинства аномалий при высокой производительности, но подвержена **Write Skew**.

3.  **Дедлоки (Deadlocks):**
    Ситуация, когда две транзакции ждут блокировок друг друга. СУБД автоматически обнаруживает дедлоки и принудительно прерывает (откатывает) одну из транзакций.

## Практические сценарии

### Кейс 1: Банковский перевод (Атомарность + Консистентность)
```sql
BEGIN;
UPDATE accounts SET balance = balance - 1000 WHERE id = 'User_A';
-- Если здесь произойдет сбой (например, нарушение ограничения balance >= 0),
-- БД автоматически откатит списание.
UPDATE accounts SET balance = balance + 1000 WHERE id = 'User_B';
COMMIT;
```
Если на счете А недостаточно средств, сработает `CHECK constraint`, транзакция упадет, и деньги не исчезнут.

### Кейс 2: Бронирование билетов (Lost Update)
При низком уровне изоляции (`Read Committed`) два пользователя могут купить последний билет.
**Решение:** 
- Использование `SELECT ... FOR UPDATE` (пессимистичная блокировка).
- Или уровень `Repeatable Read` / `Serializable`.

## Рекомендации для DevOps и SRE

### Валидация Durability (Долговечности)
Гарантия сохранности данных зависит не только от СУБД, но и от оборудования:
1.  **Тестирование fsync:** Используйте утилиты типа `fio` или `pg_test_fsync` для измерения скорости сброса логов на диск.
2.  **RAID и кэширование:** Если RAID-контроллер использует кэш на запись без батарейки (BBU/Flash), при сбое питания данные в кэше будут потеряны, несмотря на подтвержденный `COMMIT`.
    *   *Best Practice:* Использовать `Write-Through` кэширование, если нет BBU.
3.  **Барьеры ФС:** Убедитесь, что файловая система примонтирована с поддержкой барьеров (для ext4 это `barrier=1` по умолчанию), иначе порядок записи WAL может быть нарушен.

### Мониторинг транзакций
- **Long-running transactions:** Затянувшиеся транзакции в MVCC мешают очистке старых версий строк (Bloat), что ведет к деградации производительности.
- **Lock Contention:** Высокое количество блокировок указывает на плохую архитектуру запросов или слишком высокий уровень изоляции.
## Лучшие практики

### Выбор уровня изоляции

Уровень изоляции — это всегда компромисс между консистентностью и производительностью:

- **Read Committed (по умолчанию в PostgreSQL, Oracle, SQL Server):** Достаточен для большинства OLTP-сценариев. Минимизирует блокировки и позволяет достичь высокой пропускной способности.
- **Repeatable Read (по умолчанию в MySQL/InnoDB, PostgreSQL):** Гарантирует, что повторное чтение строки в рамках транзакции вернет те же данные. Подходит для отчетов, где важна стабильность снапшота, но может привести к большему количеству откатов при обновлениях.
- **Serializable:** Только для критичных сценариев, где нельзя допустить никаких аномалий (например, финансовые проводки). Нагрузка на СУБД максимальна, производительность падает в разы из-за механизмов предотвращения фантомов (predicate locking или Serializable Snapshot Isolation с проверкой сериализуемости).

### Управление транзакциями

- **Минимизируйте время транзакции:** Чем дольше транзакция активна, тем дольше удерживаются блокировки (в Locking-механизмах) или версии строк (в MVCC), что ведет к Bloat и деградации производительности.
- **Избегайте операций I/O внутри транзакций:** Вызовы внешних сервисов, `pg_sleep()`, ожидание ввода пользователя внутри активной транзакции — распространенная причина долгих транзакций и дедлоков.
- **Используйте идемпотентные операции:** В分布式 системах или при нестабильных сетях идемпотентность позволяет безопасно повторять `COMMIT` при таймаутах, не опасаясь двойного списания.
- **SELECT ... FOR UPDATE vs Advisory Locks:** Для явной блокировки строк используйте пессимистичные блокировки (`SELECT ... FOR UPDATE`), а не прикладные флаги в таблице — это снижает риск гонок.

### Баланс Durability и производительности

| Параметр | Значение | Эффект |
| :--- | :--- | :--- |
| `synchronous_commit = on` (PostgreSQL) | Ждет fsync WAL на диск | Максимальная надежность, максимальная задержка |
| `synchronous_commit = remote_write` | Ждет записи в WAL standby | Высокая надежность, умеренная задержка |
| `innodb_flush_log_at_trx_commit = 1` (MySQL) | fsync на каждом COMMIT | Максимальная надежность |
| `innodb_flush_log_at_trx_commit = 2` | fsync раз в секунду | Может потерять до 1 секунды данных при крахе |
| `sync_binlog = 1` (MySQL) | fsync binlog при каждой транзакции | Гарантирует репликацию, но снижает производительность |

> **Важно:** Любое ослабление синхронности (`synchronous_commit = off`, `innodb_flush_log_at_trx_commit = 0`) допускает потерю данных при аварийном выключении. Используйте такие режимы только для неключевых данных (логи, кэши, аналитика).

### Мониторинг транзакций (SRE)

- **Длительные транзакции (Long-running transactions):** В PostgreSQL мониторьте `state = 'idle in transaction'` в `pg_stat_activity`. В MySQL проверяйте `TIME` в `information_schema.INNODB_TRX`. Длительные транзакции блокируют очистку MVCC (Vacuum), вызывая рост таблиц и деградацию производительности.
- **Lock Timeouts:** Настройте `lock_timeout` и `idle_in_transaction_session_timeout` (PostgreSQL) для предотвращения зависших сессий. В MySQL используйте `innodb_lock_wait_timeout`.
- **Откаты (Rollbacks):** Мониторьте соотношение `rollback` к `commit`. Высокий процент откатов указывает на ошибки приложения, нехватку блокировок или дедлоки.
- **Deadlock Detected:** В логах СУБД должны быть алерты на дедлоки. В PostgreSQL включите `log_lock_waits = on` для отслеживания ожиданий блокировок.

## Устранение неисправностей (Troubleshooting)

### Проблема: Потеря данных при сбое питания

**Симптомы:** После аварийного выключения сервера некоторые зафиксированные транзакции (`COMMIT`) отсутствуют в базе.

**Причины:**
1. **Отключен fsync:** Параметр `synchronous_commit` выключен или `innodb_flush_log_at_trx_commit` установлен в `0`/`2`.
2. **Кэш RAID-контроллера без батарейки (BBU):** Данные в кэше были потеряны до записи на диск.
3. **Файловая система без барьеров (barriers):** Порядок записи WAL нарушен, и при восстановлении изменения не были применены.

**Решение:**
1. Убедитесь, что `fsync` работает корректно: для PostgreSQL выполните `SELECT pg_test_fsync();` — измерьте задержку.
2. Проверьте параметры монтирования ФС: для ext4/XFS должны быть включены barriers (`barrier=1` по умолчанию).
3. Если RAID-контроллер не имеет BBU, используйте режим `Write-Through` или откажитесь от RAID в пользу файловых систем с журналированием (ZFS, Btrfs) и регулярными снапшотами.

### Проблема: Грязное чтение (Dirty Read)

**Симптомы:** Приложение видит данные, которые были изменены, но не зафиксированы другой транзакцией. При откате второй транзакции данные в приложении оказываются неверными.

**Причина:** Уровень изоляции `Read Uncommitted` или неявное чтение незафиксированных данных через `NOLOCK` (SQL Server) или `READ UNCOMMITTED` (PostgreSQL).

**Решение:**
1. Установите минимальный уровень `Read Committed`.
2. В прикладном коде избегайте чтения данных, которые могут быть изменены незавершенными транзакциями, без явного указания уровня изоляции.

### Проблема: Неповторяющееся чтение (Non-repeatable Read)

**Симптомы:** В рамках одной транзакции два `SELECT` по одной и той же строке возвращают разные значения.

**Причина:** Уровень изоляции `Read Committed`. Другая транзакция обновила и зафиксировала строку между двумя чтениями.

**Решение:**
1. Для сценариев, где важна стабильность снапшота (например, генерация отчета), используйте `Repeatable Read` или `SERIALIZABLE`.
2. В PostgreSQL можно использовать курсоры с hold (`DECLARE CURSOR WITH HOLD`) или явные блокировки (`SELECT ... FOR SHARE`).

### Проблема: Фантомное чтение (Phantom Read)

**Симптомы:** Повторный `SELECT` с `WHERE` возвращает разное количество строк.

**Причина:** Уровень изоляции `Read Committed` или `Repeatable Read` (в зависимости от СУБД). Другая транзакция выполнила `INSERT` или `DELETE`, удовлетворяющий условию.

**Решение:**
1. Используйте `SERIALIZABLE` для строгой сериализуемости.
2. В PostgreSQL `Repeatable Read` предотвращает фантомы через **Serializable Snapshot Isolation (SSI)** — при обнаружении риска аномалии транзакция автоматически откатывается с ошибкой serialization failure.
3. В приложении реализуйте повторную логику (retry) для обработки ошибок сериализации.

### Проблема: Потерянное обновление (Lost Update)

**Симптомы:** Два пользователя одновременно редактируют одну запись. Изменения одного пользователя перезаписываются изменениями другого без предупреждения.

**Причина:** Классическая гонка **Read-Modify-Write** на уровне `Read Committed` или `Repeatable Read` без явных блокировок.

**Решение:**
1. **Пессимистичная блокировка:** `SELECT ... FOR UPDATE` (или `FOR SHARE`) — блокирует строку до конца транзакции.
2. **Оптимистичная блокировка:** Добавьте колонку `version INT` или `updated_at TIMESTAMP`. В `UPDATE` добавьте условие `WHERE version = :old_version`. Если `row_count = 0` — данные были изменены, примените retry-логику.
3. **Уровень Serializable:** В PostgreSQL `SERIALIZABLE` автоматически откатывает конфликтующие транзакции.

### Проблема: Дедлоки (Deadlocks)

**Симптомы:** Транзакция зависает и завершается ошибкой `deadlock detected` или `Deadlock found when trying to get lock`.

**Причина:** Циклическая зависимость блокировок: Транзакция А ждет ресурс, заблокированный Б, а Б ждет ресурс А.

**Решение:**
1. **Единый порядок доступа:** Всегда обращайтесь к таблицам в одном и том же порядке (например, сначала `orders`, затем `order_items`).
2. **Минимизируйте время удержания блокировок:** Выполняйте вычисления и I/O вне транзакции, а в транзакции оставьте только изменения данных.
3. **Таймауты:** Установите `lock_timeout` для предотвращения бесконечного ожидания.
4. **Мониторинг:** В PostgreSQL включите `log_lock_waits = on` и отслеживайте `pg_stat_database.deadlocks`.

### Проблема: MVCC Bloat (Раздувание таблиц)

**Симптомы:** Таблицы растут в размерах несмотря на `DELETE` и `UPDATE`. Производительность падает, запросы сканируют все больше "мертвых" строк.

**Причина:** Длинные транзакции или зависшие сессии (`idle in transaction`) не дают завершиться очистке (VACUUM в PostgreSQL, Purge в InnoDB). Старые версии строк не могут быть удалены, потому что они могут быть нужны для незавершенных транзакций (snapshot visibility).

**Решение:**
1. **Укоротите транзакции:** Выполняйте коммит как можно раньше.
2. **Закрывайте соединения:** Убедитесь, что приложение не оставляет открытые транзакции в пуле соединений.
3. **VACUUM (PostgreSQL):** Настройте `autovacuum` для агрессивной очистки горячих таблиц. Для ручной очистки: `VACUUM (VERBOSE) table_name;` и при необходимости `VACUUM FULL` (требрует блокировку).
4. **В MySQL (InnoDB):** `innodb_purge_threads` определяет количество потоков очистки. Убедитесь, что `innodb_max_purge_lag` не слишком велик, чтобы purge не отставал.

### Проблема: Durability при отказе диска

**Симптомы:** После сбоя диска часть данных не восстанавливается, даже если WAL на месте.

**Причины:**
1. **Одиночный диск без резервирования:** WAL и данные на одном физическом диске. При отказе диска теряется и то, и другое.
2. **Отсутствие резервного копирования WAL:** Архивация WAL (`archive_command` в PostgreSQL) не настроена или не работает.
3. **Коррупция WAL:** Аварийное выключение во время записи сегмента WAL.

**Решение:**
1. **Резервируйте WAL отдельно:** Используйте RAID 10 для данных и WAL, либо размещайте WAL на отдельном физическом диске.
2. **Настройте PITR:** В PostgreSQL настройте непрерывное архивирование WAL (`archive_mode = on`, `archive_command`). Это позволяет восстановиться на любой момент времени.
3. **Мониторинг:** Отслеживайте ошибки в `pg_stat_archiver` (PostgreSQL) и статус `archive_command`. Если архив не работает, база будет копить WAL локально и может остановиться при заполнении диска.

### Проблема: Транзакционный таймаут и откаты

**Симптомы:** Приложение получает ошибки `canceling statement due to statement timeout` или `transaction timeout`.

**Причины:**
1. **Слишком долгие запросы:** Отсутствуют индексы, causing sequential scans на больших таблицах.
2. **Блокировки:** Транзакция ждет освобождения ресурса, удерживаемого другой транзакцией.
3. **Сетевые задержки:** В распределенных транзакциях (2PC) таймаут может быть вызван задержкой между узлами.

**Решение:**
1. Настройте `statement_timeout` (PostgreSQL) или `max_execution_time` (MySQL) для предотвращения зависших запросов.
2. Используйте EXPLAIN ANALYZE для диагностики медленных запросов.
3. В распределенных системах увеличьте таймауты 2PC с учетом сетевых задержек между дата-центрами.

## Крайние случаи и сценарии сбоев

### Сбой питания во время COMMIT

**Сценарий:** Сервер отключился после того, как WAL записан на диск (`fsync` успешен), но данные страниц еще не сброшены в файлы данных.

**Результат:** После перезапуска СУБД восстанавливает данные из WAL (Redo phase алгоритма ARIES). Транзакция считается зафиксированной, так как Durability гарантируется через WAL. Данные из WAL применяются к страницам данных. **Данные не теряются.**

### Падение СУБД во время ROLLBACK

**Сценарий:** Транзакция откатывается, но сервер падает до завершения отката.

**Результат:** При восстановлении СУБД повторяет операции отката (Undo phase алгоритма ARIES), читая CLR (Compensation Log Records) из WAL. Транзакция не будет частично применена.

### Отказ диска с WAL

**Сценарий:** Диск, на котором хранится WAL, вышел из строя.

**Результат:** Если WAL утерян, а данных нет — восстановление невозможно (RPO = время с последнего бэкапа). Поэтому WAL всегда должен быть на отказоустойчивом хранилище (RAID, репликация).

### Сетевое разделение в распределенных транзакциях (2PC)

**Сценарий:** Координатор отправил `PREPARE` всем участникам и получил подтверждения, но перед отправкой `COMMIT` loses connection.

**Результат:** Участники находятся в состоянии **In-doubt** (prepared). Они не могут ни зафиксировать, ни откатить транзакцию без решения координатора. Это требует ручного вмешательства или механизмов автоматического разрешения (например, **Heuristic Commit/Abort** в некоторых СУБД).

### Длинная транзакция в MVCC

**Сценарий:** Транзакция открыта на несколько часов (например, из-за забытого `COMMIT` в интерактивном psql).

**Результат:**
1. **Bloat:** Удаленные строки физически не удаляются, потому что их старые версии нужны для этой транзакции.
2. **VACUUM блокируется:** PostgreSQL не может удалить строки, измененные после LSN начала этой транзакции.
3. **Wrap-around:** При достижении 2 млрд транзакций база может остановиться для предотвращения переполнения MXID.

**Решение:** Автоматический `idle_in_transaction_session_timeout` (PostgreSQL) или обнаружение долгих транзакций через мониторинг `pg_stat_activity`.

## Валидация ACID-свойств (SRE-чеклист)

### Атомарность (Atomicity)

```bash
# PostgreSQL: Проверка, что транзакция откатывается при ошибке
psql -c "
BEGIN;
INSERT INTO accounts (id, balance) VALUES (1, 1000);
INSERT INTO accounts (id, balance) VALUES (1, 2000); -- нарушение UNIQUE
-- Транзакция автоматически откатится
SELECT * FROM accounts WHERE id = 1;
";
```

### Согласованность (Consistency)

```bash
# PostgreSQL: Проверка CHECK constraint
psql -c "
BEGIN;
INSERT INTO accounts (id, balance) VALUES (2, -100); -- нарушение CHECK (balance >= 0)
-- Должна быть ошибка: new row for relation violates check constraint
ROLLBACK;
";

# MySQL: Аналогично
mysql -e "
START TRANSACTION;
INSERT INTO accounts (id, balance) VALUES (2, -100);
-- ERROR: Check constraint violated
ROLLBACK;
";
```

### Изоляция (Isolation)

Для тестирования изоляции используйте две параллельные сессии:

```bash
# Сессия 1
psql -c "
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM accounts WHERE id = 1;
-- Должна увидеть начальное значение, даже если Сессия 2 обновит строку
";

# Сессия 2
psql -c "
BEGIN;
UPDATE accounts SET balance = balance + 100 WHERE id = 1;
COMMIT;
";
```

### Долговечность (Durability)

```bash
# PostgreSQL: Проверка времени fsync WAL
pg_test_fsync
# Ожидаемый результат: время записи 4KB блока < 10-20 мс на SSD

# Проверка, что COMMIT блокируется до fsync
psql -c "
BEGIN;
INSERT INTO accounts (id, balance) VALUES (3, 500);
COMMIT;
-- Если fsync включен, COMMIT не вернется, пока данные не будут на диске
";

# MySQL: Проверка innodb_flush_log_at_trx_commit
mysql -e "SHOW VARIABLES LIKE 'innodb_flush_log_at_trx_commit';"
# 1 = максимальная надежность
```

### ACID vs BASE

В распределенных системах часто невозможно обеспечить ACID из-за сетевых задержек и теоремы CAP.
