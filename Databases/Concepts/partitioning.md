# Секционирование данных (Partitioning)

## Определения

**Секционирование (Partitioning)** -- метод логического разделения одной большой таблицы на несколько более мелких физических сегментов (секций), которые СУБД воспринимает как единый объект. Секционирование выполняется по горизонтальному принципу (разделение строк). Каждая секция хранит подмножество данных согласно определённым границам, а сама секционированная таблица остаётся "виртуальной" -- она не имеет собственного хранилища, данные живут в дочерних таблицах-секциях.

**Partition Key (Ключ секционирования)** -- колонка или набор колонок, по значению которых СУБД определяет, в какую именно секцию должна быть записана строка. При вставке новой строки СУБД вычисляет значение ключа и маршрутизирует запись в соответствующую секцию. Если значение ключа обновляется так, что строка перестаёт соответствовать границам текущей секции, СУБД перемещает её в другую секцию автоматически.

**Partition Pruning (Исключение секций)** -- оптимизация, при которой планировщик запросов анализирует WHERE-условие и обращается только к тем секциям, которые содержат потенциально подходящие данные, игнорируя остальные. Это значительно снижает нагрузку на I/O. Различают два вида pruning:

- **Plan-time pruning** -- выполняется на этапе планирования запроса, когда значения ключа известны заранее (литералы в WHERE). Секции, не попадающие в диапазон, полностью исключаются из плана выполнения.
- **Run-time pruning** -- выполняется во время выполнения запроса, когда значение ключа определяется динамически (параметры подготовленных выражений, результаты подзапросов, значения из JOIN). Менее эффективен, но всё равно исключает лишние секции.

**Default Partition (Секция по умолчанию)** -- специальная секция, которая принимает все строки, не попадающие ни в одну из определённых секций. Предотвращает ошибки при вставке данных за пределы заданных диапазонов. Использование default-секции рекомендуется как защитный механизм, но не как основная стратегия хранения данных.

**Sub-partitioning (Подсекционирование)** -- секционирование уже секционированной таблицы, то есть когда каждая секция верхнего уровня дополнительно разделяется на подсекции. Увеличивает количество секций и сложность управления, поэтому применяется только при необходимости двумерного разделения (например, по времени и по региону одновременно).

## Основные концепции

### Типы секционирования

1.  **RANGE (Диапазоны):**
    *   Строки распределяются на основе принадлежности ключа к определённому диапазону значений.
    *   Границы диапазонов: нижняя граница включительная (`FROM`), верхняя -- исключающая (`TO`). Например, секция `FOR VALUES FROM ('2025-01-01') TO ('2025-02-01')` принимает все даты с 1 января по 31 января включительно, но не 1 февраля.
    *   *Применение:* Самый популярный тип. Идеально подходит для работы с временными рядами (логи, транзакции), где данные секционируются по месяцам или годам.
    *   *Особенность:* Требуется специальная обработка для данных за пределами последнего диапазона -- либо создаётся `MAXVALUE`-секция (MySQL), либо используется `DEFAULT` (PostgreSQL).

2.  **LIST (Списки):**
    *   Распределение на основе фиксированного списка значений (например, по регионам или статусам).
    *   Каждая секция определяет явный перечень допустимых значений ключа через `VALUES IN (...)`.
    *   *Применение:* Когда данные имеют дискретную категориальную природу (регион, тип транзакции, статус заказа).

3.  **HASH (Хэш):**
    *   СУБД вычисляет хэш-функцию от ключа и распределяет данные равномерно между заданным количеством секций по формуле `hash(key) % N`.
    *   Равномерное распределение достигается за счёт математических свойств хэш-функции, что исключает "горячие" секции.
    *   *Применение:* Для равномерного распределения нагрузки на I/O, когда нет явного критерия для диапазонов (например, распределение данных по тенантам в мульти-tenant системе).
    *   *Ограничение:* Запросы без указания ключа секционирования вынуждены сканировать все секции.

4.  **KEY (Ключ):**
    *   Вариант HASH, где СУБД сама выбирает хэш-функцию (обычно MD5 или внутренний алгоритм на основе первичного ключа).
    *   В MySQL поддерживает колонки типа DATE, TIME, DATETIME без необходимости ручного преобразования в целое число.
    *   *Применение:* Когда нужна равномерная хэш-раскладка, но не хочется определять собственную хэш-функцию.

### Когда секционировать, а когда не стоит

Секционирование -- это не универсальное средство. Оно даёт значительные преимущества при определённых условиях, но увеличивает сложность системы в других.

**Секционирование оправдано, когда:**

- Таблица превышает объём физической памяти сервера (десятки и сотни ГБ).
- Существует чёткий паттерн удаления данных по времени (TTL, ретеншн-политика) -- секционирование позволяет удалять целые секции мгновенно вместо тяжёлых `DELETE`.
- Запросы стабильно фильтруют данные по одной колонке (90%+ запросов содержат WHERE по ключу секционирования).
- Нужна возможность размещать данные на разных уровнях хранения (hot/cold, NVMe/HDD/S3).

**Секционирование НЕ нужно, когда:**

- Таблица помещается в оперативную память -- индексы и VACUUM дадут больший эффект при меньшей сложности.
- Нет естественного ключа для секционирования -- произвольный выбор ключа приведёт к полному сканированию всех секций.
- Запросы не фильтруют данные по ключу секционирования -- секционирование замедлит планирование без выигрыша в выполнении.
- Количество уникальных значений ключа слишком велико (millions) -- число секций будет чрезмерным.
- Таблица является целевой для внешних ключей (FK) -- в некоторых СУБД это ограничивает или запрещает секционирование.

**Правило принятия решения:** Посмотрите на 20 наиболее частых запросов к таблице. Если колонка, присутствующая в 90%+ WHERE-условий, является хорошим кандидатом на ключ секционирования -- секционирование будет эффективным. Если такой колонки нет, индексы и оптимизация запросов дадут лучший результат.

### Преимущества секционирования

*   **Maintenance (Обслуживание):** Мгновенное удаление старых данных через `DROP PARTITION` / `DETACH PARTITION` вместо тяжелых `DELETE` (которые генерируют много логов и фрагментируют таблицу). Один `DROP` секции выполняется за миллисекунды независимо от объёма данных в секции.
*   **Производительность:** Ускорение запросов за счет Partition Pruning -- планировщик обращается только к релевантным секциям, пропуская остальные.
*   **Масштабируемость I/O:** Возможность размещать секции на разных физических дисках или уровнях хранения (Tiered Storage). Секции с "горячими" данными на быстрых NVMe, архивные -- на дешёвых HDD или S3.
*   **Локальность индексов:** Индексы строятся для каждой секции отдельно, что делает их меньше и позволяет чаще помещаться в RAM. Меньшие индексы = лучший cache hit ratio.
*   **Упрощение VACUUM (PostgreSQL):** `VACUUM` работает в рамках отдельной секции, что снижает длительность блокировок и упрощает контроль за процессом очистки.
*   **Partition-wise Join/Aggregate (PG 12+):** При соединении двух таблиц, секционированных по одинаковому ключу, планировщик может выполнять join/aggregation параллельно по соответствующим секциям, снижая потребление памяти и ускоряя аналитические запросы.

### Ограничения и риски

*   **Первичные ключи:** В большинстве СУБД (MySQL, PostgreSQL) ключ секционирования **обязан** входить в состав первичного ключа (Primary Key) и всех уникальных индексов. Это ключевое ограничение проектирования: если вам нужен глобально уникальный `id` без привязки ко времени/категории, секционирование потребует составного ключа `(id, partition_key)`.
*   **Сложность запросов:** Если запрос не содержит ключа секционирования, СУБД будет вынуждена сканировать все секции (Full Table Scan), что может быть медленнее, чем на обычной несекционированной таблице из-за накладных расходов на планирование.
*   **Глобальные ограничения:** Сложности с обеспечением уникальности данных вне ключа секционирования. Уникальные индексы (без включения ключа секционирования) не могут гарантировать уникальность между разными секциями.
*   **Число секций:** Слишком малое число секций не даёт эффекта от секционирования. Слишком большое число (тысячи) увеличивает время планирования запросов и потребление памяти -- каждый план запроса должен учитывать метаданные каждой секции, к которой он обращается.
*   **Стоимость миграции:** Переход на секционирование существующей большой таблицы -- нетривиальная операция, которая может потребовать downtime или сложных схем с триггерами/дублирующей записью.
*   **Ограничения СУБД:** Не все storage engine поддерживают секционирование (в MySQL -- только InnoDB/NDB). Внешние ключи (FK) могут быть ограничены или запрещены на секционированных таблицах.

## Практические сценарии

### PostgreSQL: Создание секционированной таблицы (RANGE)

```sql
-- Создание родительской таблицы с секционированием по дате
CREATE TABLE events (
    id         bigserial,
    user_id    bigint NOT NULL,
    event_type text NOT NULL,
    payload    jsonb,
    created_at timestamptz NOT NULL DEFAULT now(),
    PRIMARY KEY (id, created_at)  -- ключ секционирования ОБЯЗАН входить в PK
) PARTITION BY RANGE (created_at);

-- Создание секций (каждая -- отдельная физическая таблица)
CREATE TABLE events_2025_01 PARTITION OF events
    FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');

CREATE TABLE events_2025_02 PARTITION OF events
    FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');

-- Секция по умолчанию (ловит всё, что не попало в другие)
CREATE TABLE events_default PARTITION OF events DEFAULT;

-- Индекс на родителе автоматически создаётся на всех секциях (PG 11+)
CREATE INDEX ON events (created_at, user_id);
```

**Важно:** Верхняя граница (`TO`) исключающая. Значение `2025-02-01 00:00:00` попадёт в `events_2025_02`, а не в `events_2025_01`.

### PostgreSQL: Создание секционированной таблицы (HASH)

```sql
-- Равномерное распределение по 8 секциям по user_id
CREATE TABLE user_events (
    user_id    bigint NOT NULL,
    event_type text NOT NULL,
    created_at timestamptz NOT NULL
) PARTITION BY HASH (user_id);

CREATE TABLE user_events_p0 PARTITION OF user_events
    FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE user_events_p1 PARTITION OF user_events
    FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ... (p2 -- p7 аналогично)
CREATE TABLE user_events_p7 PARTITION OF user_events
    FOR VALUES WITH (MODULUS 8, REMAINDER 7);
```

### PostgreSQL: Каталог секций и их границ

```sql
-- Просмотр всех секций таблицы
SELECT
    child.relname AS partition_name,
    pg_get_expr(child.relpartbound, child.oid) AS partition_bounds
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child ON pg_inherits.inhrelid = child.oid
WHERE parent.relname = 'events'
ORDER BY child.relname;

-- Результат:
--  partition_name  |      partition_bounds
-- -----------------+-------------------------------
--  events_2025_01  | FOR VALUES FROM ('2025-01-01') TO ('2025-02-01')
--  events_2025_02  | FOR VALUES FROM ('2025-02-01') TO ('2025-03-01')
--  events_default  | DEFAULT
```

### PostgreSQL: Жизненный цикл данных (TTL / Rolling Window)

Сценарий: Хранение логов за 12 месяцев. Ежемесячная ротация.

```sql
-- 1. Создание новой секции (в начале месяца)
CREATE TABLE events_2026_09 PARTITION OF events
    FOR VALUES FROM ('2026-09-01') TO ('2026-10-01');

-- 2. Отсоединение старой секции (без блокировки родителя, PG 14+)
ALTER TABLE events DETACH PARTITION events_2025_08 CONCURRENTLY;

-- 3. Удаление отсоединённой секции (мгновенно, без VACUUM)
DROP TABLE events_2025_08;
```

`DETACH PARTITION ... CONCURRENTLY` (PostgreSQL 14+) не берёт `ACCESS EXCLUSIVE` lock на родительской таблице -- безопасно выполнять в рабочее время.

### PostgreSQL: Автоматизация с pg_partman

```sql
-- Установка расширения
CREATE EXTENSION pg_partman SCHEMA partman;

-- Создание родительской секционированной таблицы
-- (таблица должна уже существовать и быть секционированной)

-- Автоматическое создание секций
SELECT partman.create_parent(
    p_parent_table => 'public.events',
    p_control      => 'created_at',
    p_interval     => '1 month',
    p_premake      -- сколько будущих секций создавать заранее
);

-- Настройка ретеншна (автоудаление старше 12 месяцев)
UPDATE partman.part_config
SET retention           = '12 months',
    retention_keep_table = false,
    automatic_maintenance = 'on'
WHERE parent_table = 'public.events';

-- Планировщик через pg_cron (ежедневно в полночь)
SELECT cron.schedule(
    'partition-maintenance',
    '0 0 * * *',
    'SELECT partman.run_maintenance_proc()'
);
```

### MySQL: RANGE-секционирование по годам

```sql
CREATE TABLE sales (
    id INT NOT NULL,
    sale_date DATE NOT NULL,
    amount DECIMAL(10,2),
    PRIMARY KEY (id, sale_date)
) PARTITION BY RANGE (YEAR(sale_date)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p_max  VALUES LESS THAN MAXVALUE  -- заглушка для новых данных
);
```

### MySQL: Обслуживание партиций

```sql
-- Удаление старых данных (мгновенно)
ALTER TABLE sales DROP PARTITION p2024;

-- Добавление новой секции (требует REORGANIZE из-за MAXVALUE)
ALTER TABLE sales REORGANIZE PARTITION p_max INTO (
    PARTITION p2026 VALUES LESS THAN (2027),
    PARTITION p_max  VALUES LESS THAN MAXVALUE
);

-- Очистка данных в секции (без удаления самой секции)
ALTER TABLE sales TRUNCATE PARTITION p2025;

-- Обслуживание: пересборка, анализ, проверка
ALTER TABLE sales REBUILD PARTITION p2025, p2026;
ALTER TABLE sales ANALYZE PARTITION p2025;
ALTER TABLE sales CHECK PARTITION p2025;
```

### MySQL: Коалесцентное секционирование (HASH/KEY)

```sql
-- Уменьшение числа HASH-секций с 6 до 4
-- Данные из последних 2 секций автоматически перераспределяются
ALTER TABLE t2 COALESCE PARTITION 2;

-- Увеличение числа секций
ALTER TABLE t2 ADD PARTITION PARTITIONS 4;
```

### Изоляция горячих данных (Tiered Storage)

Сценарий: Активные заказы текущего года хранятся на NVMe, а архивные данные прошлых лет -- на дешёвых HDD или в облачном хранилище (S3). Секционирование позволяет физически разместить секции на разных дисках или таблиценных пространствах (tablespace), а затем выполнять `ATTACH` / `DETACH` для миграции данных между уровнями.

## Проверка и валидация

### Проверка Partition Pruning

Всегда проверяйте, что pruning действительно работает. Отсутствие pruning означает, что секционирование замедляет, а не ускоряет запросы.

```sql
-- PostgreSQL: анализ плана запроса
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT count(*), event_type
FROM events
WHERE created_at BETWEEN '2025-06-01' AND '2025-06-30'
GROUP BY event_type;

-- Хорошо: в плане будет "Partitions selected: 1 out of 18"
-- Плохо: все секции в плане = pruning не работает
```

**Частая ошибка, убивающая pruning:**

```sql
-- НЕПРАВИЛЬНО: функция на колонке блокирует pruning
WHERE created_at::date = '2025-06-01'

-- ПРАВИЛЬНО: сравнение с литералом того же типа
WHERE created_at >= '2025-06-01' AND created_at < '2025-06-02'
```

Неявные приведения типов и функции над ключом секционирования (в левой части WHERE) не позволяют планировщику использовать границы секций. Всегда пишите предикаты напрямую к колонке и проверяйте план через `EXPLAIN ANALYZE`.

### Мониторинг состояния секций

```sql
-- PostgreSQL: размер каждой секции
SELECT
    child.relname AS partition_name,
    pg_size_pretty(pg_total_relation_size(child.oid)) AS total_size
FROM pg_inherits
JOIN pg_class parent ON pg_inherits.inhparent = parent.oid
JOIN pg_class child ON pg_inherits.inhrelid = child.oid
WHERE parent.relname = 'events'
ORDER BY pg_total_relation_size(child.oid) DESC;

-- PostgreSQL: статистика по секциям
SELECT
    schemaname, relname,
    n_live_tup, n_dead_tup,
    last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE relname LIKE 'events_%';
```

## Типичные ошибки и их решение

### 1. Запрос сканирует все секции

**Причина:** WHERE-условие не содержит ключ секционирования, или ключ используется с функцией/приведением типа.

**Решение:** Переписать запрос так, чтобы ключ секционирования присутствовал в WHERE без функций. Проверить через `EXPLAIN (ANALYZE, BUFFERS)`, что в плане видно pruning.

### 2. Ошибка при вставке данных "no partition of relation ... found"

**Причина:** Значение ключа не попадает ни в одну существующую секцию (нет покрытия для данного диапазона).

**Решение:** Создать секцию для нового диапазона или добавить `DEFAULT`-секцию (PostgreSQL) / `MAXVALUE`-секцию (MySQL).

### 3. Ошибка уникальности при секционировании

**Причина:** Попытка создать уникальный индекс без включения ключа секционирования. Каждая секция гарантирует уникальность только внутри себя.

**Решение:** Включить ключ секционирования во все уникальные ограничения и первичные ключи.

### 4. Длительное планирование запросов

**Причина:** Слишком много секций (тысячи), планировщик тратит время на обработку метаданных каждой.

**Решение:** Уменьшить число секций. Для PostgreSQL рекомендуется до нескольких сотен секций на таблицу. Использовать более крупные интервалы (месяцы вместо дней) или `HASH` вместо `RANGE`.

### 5. ATTACH PARTITION блокирует таблицу

**Причина:** `ATTACH PARTITION` берёт `ACCESS EXCLUSIVE` lock на родителе (до PostgreSQL 14).

**Решение:** В PostgreSQL 14+ использовать `DETACH PARTITION ... CONCURRENTLY`. При `ATTACH` -- планировать операцию в окно обслуживания или использовать триггер-схему с двойной записью.

## Best Practices

### Выбор ключа секционирования

- Проанализируйте `WHERE`-условия наиболее частых запросов. Колонка, присутствующая в 90%+ запросов -- лучший кандидат.
- Для временных рядов: ключ по дате/времени (RANGE).
- Для мульти-tenant систем: ключ по tenant_id (HASH или LIST).
- Избегайте ключей с высокой кардинальностью (millions уникальных значений) для LIST/RANGE -- число секций станет чрезмерным.

### Число секций

- **RANGE/LIST:** Планируйте с запасом. Для ежемесячной ротации -- 12-24 секции (1-2 года данных + будущие + default).
- **HASH:** Начинайте с 8-16 секций. Увеличивайте при необходимости через `ADD PARTITION`.
- **Максимум:** Несколько тысяч. Свыше -- резкое tăng времени планирования (PostgreSQL 12+ значительно улучшил производительность, но лимит остаётся).

### Автоматизация

- **PostgreSQL:** Используйте `pg_partman` для автоматического создания и удаления секций. Ручное управление при масштабе чревато ошибками.
- **MySQL:** Используйте `EVENT SCHEDULER` или внешний планировщик (cron) для `ALTER TABLE ADD PARTITION` / `DROP PARTITION`.
- Всегда создавайте будущие секции заранее (`premake` в pg_partman) -- это исключит ошибки при вставке данных в новый период.

### Запросы

- Пишите WHERE-условия напрямую к ключу секционирования без функций и приведений типов.
- Всегда проверяйте план запроса через `EXPLAIN (ANALYZE, BUFFERS)` после создания/изменения секционирования.
- Настройте `enable_partition_pruning = on` (включён по умолчанию в современных версиях PostgreSQL).
- Для аналитических запросов на больших объёмах рассмотрите `enable_partitionwise_join = on` и `enable_partitionwise_aggregate = on` (выключены по умолчанию -- увеличивают потребление памяти).

### Обслуживание

- Регулярно выполняйте `ANALYZE` по секциям для обновления статистики.
- В PostgreSQL: `VACUUM` работает эффективнее на секционированных таблицах -- он обрабатывает каждую секцию отдельно.
- В MySQL: `REBUILD PARTITION` и `ANALYZE PARTITION` для дефрагментации и обновления статистики.
- Мониторьте `n_dead_tup` в `pg_stat_user_tables` для каждой секции отдельно.

## Дополнительная информация

### Эволюция поддержки в PostgreSQL

| Версия | Изменение |
|--------|-----------|
| PG 10 | Декларативное секционирование (RANGE, LIST) |
| PG 11 | HASH-секционирование, FK к секционированным таблицам |
| PG 12 | Улучшения pruning, partition-wise join |
| PG 13 | Логическая репликация для секционированных таблиц |
| PG 14 | `DETACH PARTITION ... CONCURRENTLY` (без блокировки) |
| PG 15 | `MERGE` на секционированных таблицах |
| PG 17 | Ускоренная очистка памяти VACUUM, поддержка `IDENTITY`-колонок |
| PG 18 | Ускоренное планирование для большого числа секций, улучшенный partition-wise join, `NOT VALID` FK |
