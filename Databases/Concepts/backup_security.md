# Шифрование и сжатие резервных копий

## Определения

- **Шифрование резервных копий** — процесс преобразования данных резервной копии в зашифрованный формат для защиты конфиденциальности и целостности.
- **Сжатие резервных копий** — процесс уменьшения размера данных резервной копии для экономии места хранения и ускорения передачи.
- **AEAD (Authenticated Encryption with Associated Data)** — режимы шифрования, которые одновременно обеспечивают конфиденциальность, целостность и аутентификацию зашифрованных данных.
- **Дедупликация** — процесс удаления избыточных копий повторяющихся данных для сокращения объема хранения.

## Основные концепции

Надежные резервные копии должны быть одновременно компактными и конфиденциальными. Сжатие снижает объем хранения и ускоряет передачу, а шифрование защищает данные в покое и при транспортировке. Неправильный порядок операций, неудачный выбор алгоритмов или слабое управление ключами могут привести к необратимым потерям или утечкам данных.

Подробности об общей архитектуре бэкапов см. в **[Стратегиях резервного копирования](./backups.md)**, а методы верификации — в **[Проверке целостности](./backup_validation.md)**.

### Базовые принципы

- **Порядок операций:** всегда сначала упаковка и сжатие, затем шифрование. Зашифрованный поток данных имеет высокую энтропию и практически не поддается сжатию. Использование упаковщиков (например, tar) также позволяет скрыть структуру и имена файлов внутри архива.
- **Аутентифицированное шифрование:** рекомендуется использовать режимы AEAD (AES-256-GCM, ChaCha20-Poly1305) для одновременного обеспечения конфиденциальности и целостности. Отдельные механизмы HMAC поверх шифротекста оправданы только при отсутствии поддержки AEAD.
- **Исключения из сжатия:** данные в уже сжатых форматах (jpg, mp4, zip, parquet, pdf) практически не сжимаются повторно; их следует исключать из этапа компрессии для экономии ресурсов CPU.
- **Дедупликация и шифрование:** блочная дедупликация эффективна только в том случае, если она выполняется до шифрования. Специализированные инструменты (Borg, Restic) выполняют нарезку на блоки (chunking), компрессию и только затем шифрование в рамках собственного формата. При использовании связки `tar + openssl` межбэкапная дедупликация становится невозможной.
- **Производительность:** на системах с медленной дисковой подсистемой сжатие экономит I/O за счет нагрузки на CPU. При дефиците процессорного времени следует выбирать быстрые алгоритмы (LZ4, Zstd на низких уровнях) и использовать многопоточность.

### Алгоритмы сжатия

| Алгоритм | Скорость | Степень сжатия | Потоковость | Примечания |
| :------- | :------- | :------------- | :---------- | :--------- |
| gzip | Высокая | Средняя | Да | Универсальный стандарт |
| bzip2 | Низкая | Выше gzip | Ограниченно | Устаревает, вытесняется Zstd |
| xz | Низкая | Высокая | Многопоточно | Оптимален для долгосрочных архивов |
| zstd | Очень высокая | От ср. до высокой | Отличная | Рекомендуемый выбор для бэкапов |

Оптимальным выбором часто является **Zstd**: уровни 3–8 для регулярных копий и уровни 12–19 для долгосрочного хранения.

### Управление ключами и целостностью

- **Типы ключей:** симметричное шифрование (быстрее и проще в автоматизации) или асимметричное (публичный ключ для шифрования, приватный — для восстановления; упрощает безопасное распространение).
- **Хранение и ротация:** ключи должны храниться отдельно от данных резервных копий. Рекомендуется использовать KMS (Key Management Service) или HSM (Hardware Security Module) для автоматизации ротации и контроля доступа.
- **Деривация паролей:** при использовании паролей необходимо применять функции формирования ключа (PBKDF2, Argon2) с солью и достаточным количеством итераций.
- **Контроль целостности:** использование AEAD является стандартом де-факто. Дополнительно следует сохранять манифест с контрольными суммами (SHA-256) и размерами файлов для обнаружения повреждений на ранних этапах.

## Практические сценарии

### Сценарий 1: Сжатие данных с использованием Zstd

```bash
# Создание сжатого архива (уровень 3)
tar --use-compress-program='zstd -3' -cf backup.tar.zst /var/lib/postgresql/data

# Распаковка архива
tar --use-compress-program='zstd -d' -xf backup.tar.zst -C /restore/path
```

### Сценарий 2: Асимметричное шифрование с использованием GPG

```bash
# Шифрование на публичный ключ получателя
gpg --encrypt --recipient backup@company.com --trust-model always backup.tar.zst

# Расшифровка с использованием приватного ключа
gpg --decrypt backup.tar.zst.gpg > backup.tar.zst
```

### Сценарий 3: Симметричное шифрование с OpenSSL

```bash
# Шифрование с использованием PBKDF2 (AES-256-CBC)
openssl enc -aes-256-cbc -salt -pbkdf2 -in backup.tar.zst -out backup.tar.zst.enc

# Расшифровка
openssl enc -aes-256-cbc -d -pbkdf2 -in backup.tar.zst.enc -out backup.tar.zst
```

### Сценарий 4: Конвейерная обработка (сжатие + шифрование)

```bash
# Полный цикл: упаковка -> сжатие -> шифрование
tar -cf - /var/lib/postgresql/data | zstd -3 | gpg --encrypt --recipient backup@company.com --trust-model always > backup.tar.zst.gpg

# Обратный цикл: расшифровка -> декомпрессия -> распаковка
gpg --decrypt backup.tar.zst.gpg | zstd -d | tar -xf - -C /restore/path
```

### Сценарий 5: Генерация манифеста целостности

```bash
# Создание манифеста SHA-256 для всех файлов в директории
find /backup/daily -type f -print0 | sort -z | xargs -0 sha256sum > manifest.sha256

# Проверка целостности по манифесту
sha256sum -c manifest.sha256
```

## Дополнительная информация

- **Специализированные инструменты:** [BorgBackup](https://www.borgbackup.org/), [Restic](https://restic.net/), [WAL-G](https://github.com/wal-g/wal-g) — утилиты с встроенной дедупликацией, сжатием и шифрованием.
- **Управление ключами (KMS):** AWS KMS, HashiCorp Vault, Google Cloud KMS для централизованной ротации ключей.
- **Защита от удаления (Immutability):** использование S3 Object Lock или WORM-хранилищ для защиты от вирусов-шифровальщиков (ransomware).
