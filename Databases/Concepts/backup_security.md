# Безопасность и сжатие резервных копий

## Определения

- **Шифрование в покое (At Rest)** — защита данных бэкапа на носителе (диск, лента, облако) от несанкционированного доступа при краже носителя или компрометации хранилища.
- **Шифрование при передаче (In Transit)** — защита данных в процессе их копирования с сервера на сервер или в облако.
- **Иммутабельность (Immutability / WORM)** — свойство данных, при котором они не могут быть изменены или удалены в течение заданного периода времени (защита от Ransomware).
- **KMS (Key Management Service)** — централизованная система управления криптографическими ключами, обеспечивающая их безопасное хранение, ротацию и контроль доступа.
- **AEAD (Authenticated Encryption with Associated Data)** — режимы шифрования (например, AES-GCM), обеспечивающие одновременно конфиденциальность и проверку целостности данных.
- **Zstd (Zstandard)** — современный алгоритм сжатия, обеспечивающий высокую скорость и степень компрессии, де-факто стандарт для SRE-инструментов.

## Основные концепции

Безопасность резервных копий строится на принципе **"Бэкап — это последний рубеж"**. Если основная система скомпрометирована (например, злоумышленник получил права администратора), он попытается первым делом удалить или зашифровать бэкапы.

Для понимания общей архитектуры см. **[Стратегии резервного копирования](./backups.md)**, а методы проверки — в **[Проверке целостности](./backup_validation.md)**.

### Правило 3-2-1-1-0

Современная эволюция классического правила 3-2-1:
- **3** копии данных.
- **2** разных носителя.
- **1** копия вне площадки (offsite).
- **1** копия **иммутабельная** или **в автономном режиме** (air-gapped/offline).
- **0** ошибок после проверки восстановления.

### Защита от Ransomware (Вирусов-шифровальщиков)

Основная угроза — удаление бэкапов через скомпрометированные API-ключи облака или учетные записи админов.
- **S3 Object Lock:** запрещает удаление файлов даже владельцу аккаунта до истечения срока (режим `COMPLIANCE`) или разрешает удаление только с особыми правами (`GOVERNANCE`).
- **Разделение прав (IAM):** сервер бэкапов должен иметь права только на запись (`PutObject`), но не на удаление (`DeleteObject`).
- **Air-gap:** физическое или логическое отключение хранилища от сети вне окон резервного копирования.

### Порядок операций и алгоритмы

1. **Сжатие -> Шифрование:** Шифрование всегда идет последним. Зашифрованные данные имеют максимальную энтропию и не сжимаются.
2. **Дедупликация:** Выполняется до шифрования или специализированными инструментами (Borg, Restic), которые умеют дедуплицировать внутри зашифрованного репозитория.

| Алгоритм | Назначение | Особенности |
| :--- | :--- | :--- |
| **Zstd** | Универсальный выбор | Настраиваемый баланс скорость/сжатие. Рекомендуется для бэкапов. |
| **LZ4** | Максимальная скорость | Используется, когда пропускная способность сети выше скорости записи на диск. |
| **AES-256-GCM** | Шифрование | Аппаратное ускорение (AES-NI), встроенная проверка целостности (AEAD). |

### Управление ключами

- **Passphrase-based:** ключ выводится из пароля (требует PBKDF2/Argon2). Подходит для простых скриптов.
- **KMS (Cloud/Vault):** ключи не покидают защищенный периметр. БД-сервер запрашивает шифрование данных через API KMS.
- **Асимметричное шифрование:** бэкап шифруется публичным ключом (безопасно хранить на сервере), а расшифровка возможна только приватным ключом (хранится в защищенном месте/офлайн).

## Практические сценарии

### Сценарий 1: Эффективное сжатие с Zstd

```bash
# Многопоточное сжатие (уровень 3 — баланс)
tar -cf - /data/db | zstd -T0 -3 -o backup.tar.zst

# Максимальное сжатие для долгосрочного архива (уровень 19)
zstd -19 --ultra backup.tar -o backup_ultra.tar.zst
```

### Сценарий 2: Шифрование через OpenSSL (PBKDF2)

```bash
# Шифрование с защитой от перебора (Modern OpenSSL)
openssl enc -aes-256-gcm -salt -pbkdf2 -iter 100000 -in backup.tar.zst -out backup.tar.zst.enc

# Расшифровка
openssl enc -aes-256-gcm -d -pbkdf2 -iter 100000 -in backup.tar.zst.enc -out backup.tar.zst
```

### Сценарий 3: Асимметричное шифрование с GPG (Public Key)

```bash
# Шифрование на сервере без хранения приватного ключа
gpg --encrypt --recipient "admin@company.com" --trust-model always backup.tar.zst

# Расшифровка (только на машине администратора)
gpg --decrypt backup.tar.zst.gpg > backup.tar.zst
```

### Сценарий 4: Облачная безопасность (AWS S3 + KMS)

```bash
# Загрузка с шифрованием на стороне сервера через KMS
aws s3 cp backup.tar.zst s3://my-backups/ --sse aws:kms --sse-kms-key-id <key-id>

# Включение Object Lock (Immutability) на 30 дней
aws s3api put-object-lock-configuration --bucket my-backups --object-lock-configuration '{ "ObjectLockEnabled": "Enabled", "Rule": { "DefaultRetention": { "Mode": "COMPLIANCE", "Days": 30 }}}'
```

### Сценарий 5: Современные SRE-инструменты

**Restic (S3 + Шифрование + Дедупликация):**
```bash
# Инициализация репозитория (пароль задается через RESTIC_PASSWORD)
restic -r s3:s3.amazonaws.com/bucket init

# Создание бэкапа (шифрование и дедупликация встроены)
restic -r s3:s3.amazonaws.com/bucket backup /var/lib/postgresql/data
```
