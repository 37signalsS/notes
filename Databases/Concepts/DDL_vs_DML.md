# DDL, DML, DQL, DCL и TCL: Категории SQL-команд

**Актуально для:** SQL-92 / PostgreSQL 16 / MySQL 8.0 / MariaDB 11 / Oracle 21c / SQL Server 2022

## Определения

Язык SQL (Structured Query Language) подразделяется на несколько функциональных категорий в зависимости от объекта воздействия: структура базы данных, содержимое таблиц или права доступа.

- **DDL (Data Definition Language)** — язык определения данных. Команды этой категории изменяют **структуру** (схему) базы данных и её объекты (таблицы, индексы, представления, схемы).
    - Примеры: `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME`.
- **DML (Data Manipulation Language)** — язык манипулирования данными. Используется для **изменения содержимого** таблиц (строк).
    - Примеры: `INSERT`, `UPDATE`, `DELETE`, `MERGE`.
- **DQL (Data Query Language)** — язык запросов данных. Часто рассматривается как подмножество DML, но выделяется в отдельную категорию для операций **чтения** и выборки.
    - Примеры: `SELECT`.
- **DCL (Data Control Language)** — язык управления данными. Операции для настройки **прав доступа** и обеспечения безопасности на уровне объектов СУБД.
    - Примеры: `GRANT`, `REVOKE`, `DENY`.
- **TCL (Transaction Control Language)** — язык управления транзакциями. Позволяет управлять **логическими единицами работы**, обеспечивая соблюдение свойств ACID.
    - Примеры: `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `SET TRANSACTION`.

## Архитектура и принцип работы

### Жизненный цикл команд

**DML/DQL:**
1. Парсинг → оптимизация → выполнение.
2. Изменения записываются в WAL/Binlog и буферы данных.
3. При `COMMIT` происходит `fsync` WAL (если включен), после чего транзакция считается зафиксированной.
4. При `ROLLBACK` изменения откатываются через Undo-логи.

**DDL:**
1. Парсинг → проверка прав → получение MDL-блокировки (Metadata Lock).
2. Обновление системных каталогов (pg_class/pg_attribute в PostgreSQL, data dictionary в MySQL).
3. **Наиболее критично:** в MySQL/MariaDB DDL вызывает **неявный COMMIT** до и после выполнения. В PostgreSQL большинство DDL выполняется внутри транзакции, но `CREATE INDEX CONCURRENTLY` и `VACUUM` — исключения.
4. В Oracle DDL выполняет два неявных COMMIT: перед операцией и после неё.

### Блокировки и их влияние

| Тип операции | Блокировка | Влияние на приложение |
| :--- | :--- | :--- |
| `SELECT` (DQL) | Shared Lock / Snapshot | Минимальное |
| `INSERT/UPDATE/DELETE` (DML) | Row-level / Next-Key | Локализованное |
| `ALTER TABLE` (DDL) | MDL (Metadata Lock) | Полная остановка таблицы |
| `CREATE/DROP INDEX` | Schema-level / Table-level | Зависит от алгоритма |

**Важно для SRE:** MDL-блокировка в MySQL/MariaDB является приоритетной. Даже быстрый `SELECT`, начавшийся перед `ALTER TABLE`, будет ждать завершения DDL, блокируя пул соединений приложения.

## Основные концепции

### Транзакционность и неявный коммит

Реакция СУБД на выполнение команд разных категорий внутри транзакции (`BEGIN ... END`) существенно различается и зависит от архитектуры конкретного движка.

| Категория | Транзакционность | Возможность отката (Rollback) |
| :--- | :--- | :--- |
| **DML / DQL** | Всегда транзакционны | Да, до фиксации (COMMIT) |
| **DDL** | Зависит от СУБД | Часто вызывают неявный COMMIT |
| **DCL / TCL** | Системные операции | Обычно необратимы или имеют специфичный жизненный цикл |

**Особенности Transactional DDL:**
- **PostgreSQL:** Поддерживает почти все DDL-команды внутри транзакции. Если `ALTER TABLE` завершился ошибкой, вся транзакция откатывается, и структура таблицы остается прежней. *Исключения:* `CREATE INDEX CONCURRENTLY` и `VACUUM`.
- **MySQL / MariaDB:** **Не поддерживает**. Любая DDL-команда вызывает **неявный коммит** (Implicit Commit) текущей открытой транзакции. Откатить изменения схемы невозможно.
- **Oracle:** DDL-команды выполняют два неявных коммита — непосредственно перед выполнением команды и сразу после него.

### Блокировки метаданных (Metadata Locks, MDL)

Выполнение DDL-операций на высоконагруженных системах сопряжено с риском полной остановки сервиса из-за блокировок метаданных.

1.  **MDL (Metadata Lock):** При выполнении `ALTER TABLE` СУБД должна гарантировать, что ни одна другая транзакция не использует таблицу.
2.  **Очередь блокировок:** Если в системе выполняется долгий `SELECT`, `ALTER TABLE` будет ждать его завершения. Все последующие запросы к этой таблице (даже быстрые `SELECT`) встанут в очередь *после* `ALTER`, что приведет к исчерпанию пула соединений приложения.
3.  **Безопасный подход (OSC):** Инструменты **Online Schema Change** (например, `gh-ost` или `pt-online-schema-change`) создают временную таблицу, копируют данные в фоновом режиме и подменяют оригинальную таблицу в конце процесса через атомарный `RENAME`.

## Практические сценарии

### Сравнение способов удаления данных (DELETE vs TRUNCATE vs DROP)

Выбор команды зависит от требуемой скорости и необходимости сохранения структуры.

| Характеристика | DELETE (DML) | TRUNCATE (DDL) | DROP (DDL) |
| :--- | :--- | :--- | :--- |
| **Объект воздействия** | Отдельные строки | Все строки таблицы | Вся таблица (структура и данные) |
| **Условие WHERE** | Поддерживается | Не поддерживается | Не поддерживается |
| **Скорость** | Низкая (удаление построчно) | Высокая (манипуляция с метаданными) | Мгновенная |
| **Лог транзакций** | Большой объем (каждая строка) | Минимальный объем | Минимальный объем |
| **Счетчики (Serial/Identity)** | Не сбрасываются | Сбрасываются (`RESTART IDENTITY`) | Удаляются вместе с объектом |
| **Блокировки** | Построчные (Row-level) | На уровне таблицы (Exclusive) | На уровне таблицы (Exclusive) |

### Атомарная синхронизация: MERGE и UPSERT

Для предотвращения ошибок "дубликат ключа" при вставке данных используются продвинутые DML-команды:
- **MERGE (SQL Standard):** Универсальная команда, позволяющая описать условия для `UPDATE` (если запись найдена) и `INSERT` (если записи нет) в одном запросе.
- **UPSERT (PostgreSQL/SQLite):** Синтаксис `INSERT ... ON CONFLICT (key) DO UPDATE ...`. Позволяет эффективно обрабатывать коллизии без явной проверки существования записи со стороны приложения.

### Управление доступом (DCL) и безопасность

Команды DCL являются фундаментом ролевой модели доступа (RBAC):
- **GRANT:** Предоставление прав (например, `GRANT SELECT, INSERT ON orders TO web_app;`).
- **REVOKE:** Отзыв ранее выданных прав.
- **Безопасность:** Рекомендуется всегда использовать принцип наименьших привилегий (POLP), ограничивая DML-права для прикладных пользователей и полностью запрещая им DDL в Production-среде.

### Управление транзакциями (TCL) в сложных сценариях

Команды TCL обеспечивают логическую целостность при выполнении множества связанных DML-операций:
- **SAVEPOINT:** Создание промежуточной точки внутри транзакции. Позволяет выполнить частичный откат (`ROLLBACK TO SAVEPOINT`), не прерывая всю транзакцию.
- **SET TRANSACTION ISOLATION LEVEL:** Определение уровня изоляции (Read Committed, Serializable), что критично для предотвращения аномалий (грязное чтение, фантомные записи).

### Zero-Downtime миграции (Expand-Contract)

Классический паттерн для изменения схемы без остановки сервиса:

1.  **Expand:** Добавление новой колонки/таблицы (DDL). Приложение продолжает писать в старую и новую структуру.
2.  **Migrate:** Перенос существующих данных в новую структуру (DML). Выполняется батчами.
3.  **Switch:** Изменение приложения для использования только новой структуры.
4.  **Contract:** Удаление старой колонки/таблицы (DDL) после деплоя новой версии приложения.

**Важно:** Этап Contract должен откладываться минимум на несколько недель, чтобы откатить приложение без потери данных.

### Валидация изменений

```bash
# PostgreSQL: Проверка, что DDL не блокирует таблицу дольше ожидания
psql -c "SET lock_timeout = '5s'; ALTER TABLE users ADD COLUMN IF NOT EXISTS email TEXT;"

# MySQL: Проверка типа DDL (ONLINE/INSTANT)
SHOW CREATE TABLE users;
```

## Устранение неисправностей (Troubleshooting)

### Ошибка 1: DDL заблокирована indefinitely из-за MDL

**Симптом:** `ALTER TABLE` зависает, приложение получает `Lock wait timeout exceeded`.
**Причина:** Долгая транзакция удерживает MDL-блокировку.
**Диагностика:**
```sql
-- PostgreSQL
SELECT * FROM pg_locks WHERE relation = 'users'::regclass;
SELECT pid, now() - pg_stat_activity.query_start AS duration, query
FROM pg_stat_activity WHERE state = 'active' AND query LIKE '%users%';

-- MySQL
SHOW PROCESSLIST;
SELECT * FROM information_schema.INNODB_LOCK_WAITS;
```
**Решение:** Завершите блокирующую сессию (`SELECT pg_terminate_backend(pid)` или `KILL <thread_id>`). Для предотвращения используйте `lock_timeout`.

### Ошибка 2: Неявный COMMIT снял защиту транзакции

**Симптом:** Данные изменились в БД после `ROLLBACK`, хотя DDL-команда была внутри транзакции.
**Причина:** MySQL/MariaDB автоматически выполняет COMMIT перед любой DDL-командой.
**Решение:** В MySQL нельзя откатить DDL. Используйте PostgreSQL для транзакционного DDL или инструменты OSC (`gh-ost`, `pt-online-schema-change`).

### Ошибка 3: DML-запрос блокирует таблицу целиком

**Симптом:** `UPDATE` без индекса по `WHERE` блокирует все строки таблицы.
**Причина:** InnoDB использует Next-Key Locking при отсутствии подходящего индекса.
**Решение:** Добавьте индекс перед массовым обновлением. Используйте `EXPLAIN` для проверки плана запроса.

### Ошибка 4: Отставание репликации после массового DML

**Симптом:** `Seconds_Behind_Master` растет до тысяч секунд после большого `DELETE`.
**Причина:** Массовое изменение создает огромный Binlog/WAL, который реплика не может обработать в реальном времени.
**Решение:** Выполняйте массовый DML батчами с контролем лага репликации (см. [safe_large_scale_data_modification.md](../safe_large_scale_data_modification.md)).

## Best Practices

1.  **Тестируйте DDL на staging:** Никогда не применяйте `ALTER TABLE` в Production без предварительного теста на копии Production. Особенно критично для MySQL, где DDL вызывает неявный COMMIT и необратима.
2.  **Используйте Online Schema Change:** Для больших таблиц применяйте `gh-ost` или `pt-online-schema-change` вместо прямого `ALTER TABLE`. Это позволяет избежать MDL-блокировок и долгих простоев.
3.  **Разделяйте DDL и DML:** В рамках одного деплоя сначала применяйте структурные изменения (DDL), затем миграцию данных (DML), затем обновление приложения. Это упрощает откат.
4.  **Идемпотентность:** Все DDL-скрипты должны быть идемпотентными (`IF NOT EXISTS`, `IF EXISTS`). Это позволяет безопасно перезапускать миграции после сбоя.
5.  **Бэкап перед DDL:** Создавайте бэкап перед любой деструктивной операцией (`DROP COLUMN`, `TRUNCATE`). В PostgreSQL используйте `pg_dump --schema-only`, в MySQL `mysqldump --no-data`.
6.  **Мониторинг MDL:** Включите мониторинг блокировок метаданных. В PostgreSQL отслеживайте `pg_locks`, в MySQL `performance_schema.metadata_locks`.
7.  **Ограничьте права приложения:** Прикладной пользователь должен иметь только `SELECT/INSERT/UPDATE/DELETE` на нужные таблицы. Права `ALTER` и `DROP` оставляйте только для CI/CD-сервиса.
8.  **Используйте maintenance windows:** Для тяжелых DDL (`ADD COLUMN DEFAULT`, `MODIFY COLUMN`) планируйте окно обслуживания с низкой нагрузкой.

## Ограничения и крайние случаи (Edge Cases)

- **DDL внутри хранимых процедур (PostgreSQL):** Обычные функции PostgreSQL запрещают DDL. Используйте `dblink` или event triggers для динамических изменений схемы.
- **Transactional DDL исключения:** Даже в PostgreSQL `CREATE INDEX CONCURRENTLY` и `VACUUM` нельзя выполнить внутри транзакции. Они вызывают неявный COMMIT.
- **TRUNCATE vs DELETE в репликации:** `TRUNCATE` в логической репликации MySQL может не реплицироваться корректно. Используйте `DELETE` для гарантии доставки изменения на реплики.
- **Implicit Commit в MySQL:** Любая DDL-команда (`ALTER`, `CREATE`, `DROP`, `RENAME`, `TRUNCATE`) вызывает неявный COMMIT. Это означает, что вы не можете откатить миграцию, если она упала на середине.
- **Блокировка при чтении metadata:** В MySQL даже `SELECT` на таблицу, для которой выполняется `ALTER TABLE`, будет ждать завершения DDL из-за MDL. Это может привести к каскадному таймауту в пуле соединений.
