# DDL, DML, DQL, DCL и TCL: Категории SQL-команд

## Определения

Язык SQL разделен на несколько функциональных категорий в зависимости от того, на что направлены операции: на структуру, на данные или на управление доступом.

- **DDL (Data Definition Language)** — язык определения данных. Операции, изменяющие **структуру** базы данных (объекты: таблицы, индексы, схемы, представления).
  - Примеры: `CREATE`, `ALTER`, `DROP`, `TRUNCATE`, `RENAME`, `COMMENT`.
- **DML (Data Manipulation Language)** — язык манипулирования данными. Операции для **изменения содержимого** таблиц.
  - Примеры: `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CALL`.
- **DQL (Data Query Language)** — язык запросов данных. Часто выделяется из DML как отдельная категория для операций **чтения**.
  - Примеры: `SELECT`.
- **DCL (Data Control Language)** — язык управления данными. Операции для управления **правами доступа** и безопасностью.
  - Примеры: `GRANT`, `REVOKE`.
- **TCL (Transaction Control Language)** — язык управления транзакциями. Операции для управления **логическими единицами работы** и обеспечения ACID.
  - Примеры: `COMMIT`, `ROLLBACK`, `SAVEPOINT`, `SET TRANSACTION`.

## Основные концепции

### Транзакционность и неявный коммит

Поведение команд при выполнении внутри транзакции (`BEGIN ... END`) радикально различается в зависимости от категории и конкретной СУБД.

| Категория | Транзакционность | Возможность отката (Rollback) |
| :--- | :--- | :--- |
| **DML / DQL** | Всегда транзакционны | Да, до фиксации (COMMIT) |
| **DDL** | Зависит от СУБД | Часто вызывают неявный COMMIT |
| **DCL** | Обычно авто-коммит | Зависит от реализации СУБД |

**Транзакционный DDL (Transactional DDL):**
- **PostgreSQL:** Поддерживает почти все DDL-команды внутри транзакции. Исключение: `CREATE INDEX CONCURRENTLY` и `VACUUM`.
- **MySQL:** **Не поддерживает**. Любая DDL-команда вызывает **неявный коммит** (Implicit Commit) текущей транзакции. Откатить `ALTER TABLE` невозможно.
- **Oracle:** DDL-команды вызывают два неявных коммита (до и после выполнения).

### Блокировки и Online Schema Changes (OSC)

Выполнение DDL-команд на нагруженных таблицах сопряжено с рисками:
- **Метаданные (Metadata Locks, MDL):** Даже быстрый `ALTER TABLE` может "встать в очередь" за долгим `SELECT`, блокируя все последующие запросы к таблице.
- **Эксклюзивные блокировки:** Традиционный DDL блокирует таблицу на запись (и иногда на чтение).

**Методы безопасного изменения (OSC):**
1. **Нативные средства:** `CREATE INDEX CONCURRENTLY` (Postgres), `ALGORITHM=INPLACE` (MySQL).
2. **Внешние инструменты:** `pt-online-schema-change` (Percona), `gh-ost` (GitHub). Они создают теневую таблицу, копируют данные и переключают имена через `RENAME`.

## Практические сценарии

### Сравнение способов удаления данных

| Характеристика | DELETE (DML) | TRUNCATE (DDL) | DROP (DDL) |
| :--- | :--- | :--- | :--- |
| **Объект** | Отдельные строки | Все строки таблицы | Вся таблица (объект) |
| **Условие WHERE** | Поддерживается | Нет | Нет |
| **Скорость** | Медленно (лог на строку) | Очень быстро (Metadata) | Мгновенно |
| **Лог транзакций** | Огромный объем (UNDO/REDO) | Минимальный | Минимальный |
| **Сброс счетчиков** | Нет | Да (Serial/Identity) | — |
| **Внешние ключи** | Проверяет каждую строку | Часто запрещен, если есть FK | Удаляет, если `CASCADE` |
| **Освобождение места** | Нет (только пометка) | Да (сброс High Water Mark) | Да |

### Продвинутый DML: MERGE и UPSERT
Операция `MERGE` (SQL Standard) или `INSERT ... ON CONFLICT` (Postgres/UPSERT) объединяет логику `INSERT` и `UPDATE`. Это позволяет атомарно синхронизировать данные, избегая ошибок "запись уже существует".

## Дополнительная информация

### Рекомендации по работе с DDL/DML

1. **Идемпотентность миграций:** Используйте `IF EXISTS` и `IF NOT EXISTS` в DDL-скриптах, чтобы повторный запуск не вызывал ошибок.
2. **Разделение миграций:** Никогда не смешивайте DDL (создание колонки) и DML (заполнение этой колонки данными) в одной транзакции, если СУБД не поддерживает Transactional DDL.
3. **Контроль блокировок:** Перед выполнением DDL на Production всегда устанавливайте `lock_timeout`, чтобы миграция не "подвесила" все приложение при ожидании блокировки.
