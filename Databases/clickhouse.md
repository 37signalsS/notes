# ClickHouse

ClickHouse — это колоночная (столбцовая) система управления базами данных (СУБД), изначально разработанная в Яндексе для аналитических задач (OLAP).

## Ключевые особенности

- **Колоночное хранение:** Данные хранятся по столбцам, а не по строкам. Это обеспечивает более эффективное сжатие и значительно ускоряет выполнение агрегирующих запросов, так как с диска читаются только необходимые столбцы.
- **Высокая производительность:** Оптимизирована для аналитических запросов (OLAP) и показывает высокую скорость выполнения сложных агрегаций и отчетов.
- **Горизонтальное масштабирование:** Поддерживает шардирование и репликацию "из коробки", что позволяет строить высокодоступные и производительные кластеры. В отличие от многих других систем, репликация и шардирование в ClickHouse настраиваются на уровне таблиц, а не всего сервера.
- **SQL-подобный язык запросов:** Использует диалект SQL, который включает расширения для аналитических функций.
- **Поддержка протокола PostgreSQL:** Может быть настроена для взаимодействия через протокол PostgreSQL, что позволяет использовать стандартные драйверы и инструменты для подключения.
- **Оптимизация памяти:** Эффективно управляет памятью для достижения максимальной производительности запросов.

## Масштабирование: Репликация и Шардирование

ClickHouse позволяет гибко комбинировать репликацию и шардирование для построения распределенных хранилищ данных.

### Кластеры

Логика распределения данных по серверам определяется **кластерами**, которые настраиваются в конфигурационном файле сервера. Кластер — это именованная группа серверов (шардов), каждый из которых может содержать одну или несколько реплик.

Пример конфигурации кластера с 2 шарами и 2 репликами на каждом:
```xml
<remote_servers>
    <my_cluster>
        <shard>
            <internal_replication>true</internal_replication>
            <replica>
                <host>host1.example.com</host>
                <port>9000</port>
            </replica>
            <replica>
                <host>host2.example.com</host>
                <port>9000</port>
            </replica>
        </shard>
        <shard>
            <internal_replication>true</internal_replication>
            <replica>
                <host>host3.example.com</host>
                <port>9000</port>
            </replica>
            <replica>
                <host>host4.example.com</host>
                <port>9000</port>
            </replica>
        </shard>
    </my_cluster>
</remote_servers>
```

### Репликация

Репликация в ClickHouse обеспечивает **отказоустойчивость и высокую доступность** данных.

-   **Механизм:** Для управления репликацией требуется **Apache ZooKeeper** или его аналог **ClickHouse Keeper**. Они хранят метаданные о репликах, отслеживают их состояние и координируют процессы.
-   **Движки:** Для создания реплицируемых таблиц используются движки семейства `ReplicatedMergeTree`.
-   **Принцип работы:** Данные реплицируются на уровне отдельных таблиц. При вставке данных в одну из реплик, информация о новой порции данных записывается в ZooKeeper. Остальные реплики "видят" эту запись, проверяют, есть ли у них такая порция данных, и если нет — скачивают её у другой реплики.
-   **Multi-Master репликация:** Вставлять данные можно в любую реплику, что упрощает архитектуру приложений.

```sql
-- Создание реплицируемой таблицы
CREATE TABLE orders_replicated (
    order_id UInt64,
    order_date Date
) ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/orders', '{replica}')
PARTITION BY toYYYYMM(order_date)
ORDER BY order_date;
```
> `{shard}` и `{replica}` — это макросы, которые заменяются на конкретные значения из конфигурации сервера.

### Шардирование

Шардирование используется для **горизонтального масштабирования** — распределения данных и нагрузки на запись и чтение по разным серверам (шардам).

-   **Механизм:** Шардирование реализуется с помощью движка **`Distributed`**.
-   **Архитектура:**
    1.  На каждом шарде кластера создается **локальная таблица** (например, на движке `ReplicatedMergeTree` для обеспечения отказоустойчивости).
    2.  Поверх всех локальных таблиц создается одна **распределенная таблица** с движком `Distributed`.
-   **Принцип работы:**
    -   Распределенная таблица сама по себе **не хранит данные**. Она является "прокси" или "представлением" над локальными таблицами.
    -   При **вставке** данных в `Distributed` таблицу, она распределяет строки по шардам на основе **ключа шардирования**.
    -   При **чтении** из `Distributed` таблицы, она отправляет запрос на все шарды, собирает результаты и отдает их пользователю.

```sql
-- Создание распределенной таблицы поверх локальных
CREATE TABLE orders_distributed AS orders_replicated
ENGINE = Distributed(my_cluster, default, orders_replicated, rand());
```
> `my_cluster` — имя кластера из конфигурации, `rand()` — ключ шардирования (в данном случае, случайное распределение).

- **Справочники:** Для эффективных `JOIN`'ов в распределенной среде, небольшие таблицы-справочники часто делают **полностью реплицированными** на всех шардах кластера.

## Хранение данных

Основой хранения в ClickHouse является семейство движков `MergeTree`.

При создании таблицы необходимо указать:
- **Движок (Engine):** Например, `MergeTree`.
- **Ключ сортировки (`ORDER BY`):** Определяет физический порядок хранения данных на диске. Это критически важно для производительности, так как данные, отсортированные по определенному ключу, считываются быстрее.
- **Ключ партиционирования (`PARTITION BY`):** Позволяет разбивать данные на более мелкие части (партиции) на основе ключа, например, по месяцам.

```sql
CREATE TABLE orders (
    order_id UInt64,
    customer_id UInt64,
    order_date Date,
    total_amount Float64
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(order_date)
ORDER BY (order_date, order_id);
```

## Преимущества для аналитики

- **Скорость:** Запросы, требующие агрегации по большим объемам данных (например, `COUNT`, `SUM`, `AVG`), выполняются значительно быстрее по сравнению с традиционными строковыми СУБД.
- **Оконные функции:** Отлично работает с оконными функциями, позволяя выполнять сложные аналитические вычисления, например, расчет скользящего среднего.
- **Денормализация:** Часто используется с денормализованными данными. Вместо сложных `JOIN`'ов создается одна "широкая" таблица, содержащая все необходимые поля, что еще больше ускоряет запросы.

## Интеграция с PostgreSQL

ClickHouse часто используется в гибридной связке с PostgreSQL:

- **PostgreSQL:** Используется как основная база данных для транзакционной нагрузки (OLTP), где важна целостность данных и быстрые операции вставки/обновления/удаления.
- **ClickHouse:** Выступает в роли аналитического фронтенда. Данные из PostgreSQL периодически или в реальном времени переливаются в ClickHouse для выполнения быстрых аналитических запросов.

Подробнее о вариантах интеграции см. в заметке [Интеграция PostgreSQL и ClickHouse](./PostgreSQL/postgresql_high_load_and_scaling.md).
