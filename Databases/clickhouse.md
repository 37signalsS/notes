# ClickHouse

## Определения

**ClickHouse** — это колоночная (столбцовая) система управления базами данных (СУБД) для онлайн-обработки аналитических запросов (OLAP), изначально разработанная в Яндексе для Яндекс.Метрики.

**OLAP vs OLTP:** ClickHouse относится к классу OLAP-систем (Online Analytical Processing), в отличие от OLTP-систем (Online Transactional Processing), таких как PostgreSQL. Ключевые различия:

| Характеристика | OLTP (PostgreSQL) | OLAP (ClickHouse) |
| :--- | :--- | :--- |
| **Назначение** | Транзакции (создание заказа, обновление профиля) | Аналитика (отчёты, агрегации) |
| **Структура хранения** | Строковая | Колоночная |
| **Операции** | Частые INSERT/UPDATE/DELETE | Массовые INSERT, редкие UPDATE/DELETE |
| **Данные** | Нормализованные | Денормализованные |
| **Масштабирование** | Вертикальное / репликация чтения | Горизонтальное (MPP, шардирование) |
| **Гарантии** | ACID | BASE (скорость важнее согласованности) |

## Основные концепции

ClickHouse предназначен для работы с огромными объемами данных (терабайты и петабайты), позволяя выполнять аналитические запросы по миллиардам записей за доли секунды. Однако за такую производительность приходится платить высоким потреблением процессорных ресурсов и отсутствием полной поддержки ACID.

### Ключевые особенности

- **Колоночное хранение:** Данные хранятся по столбцам, а не по строкам. Это обеспечивает более эффективное сжатие (до 10–13 раз) и значительно ускоряет выполнение агрегирующих запросов, так как с диска читаются только необходимые столбцы.
- **Высокая производительность:** Оптимизирована для аналитических запросов (OLAP) и показывает высокую скорость выполнения сложных агрегаций и отчетов. Выполняет запросы в 100–1000 раз быстрее строковых СУБД на больших объёмах данных.
- **Горизонтальное масштабирование:** Поддерживает шардирование и репликацию "из коробки", что позволяет строить высокодоступные и производительные кластеры. В отличие от многих других систем, репликация и шардирование в ClickHouse настраиваются на уровне таблиц, а не всего сервера.
- **SQL-подобный язык запросов:** Использует диалект SQL, который включает расширения для аналитических функций.
- **Оптимизация памяти:** Эффективно управляет памятью для достижения максимальной производительности запросов.
- **Высокое потребление CPU:** Запросы с тяжелыми вычислениями могут полностью утилизировать все доступные ядра процессора. Это является платой за высокую скорость обработки.
- **Отсутствие блокировок:** В ClickHouse нет блокировок строк/таблиц, что упрощает параллельную обработку, но требует осторожности при мутациях.

### Хранение данных: Движки `MergeTree`

Основой хранения в ClickHouse является семейство движков `MergeTree`. При создании таблицы необходимо указать:

- **Движок (`ENGINE`):** Например, `MergeTree`.
- **Ключ сортировки (`ORDER BY`):** Определяет физический порядок хранения данных на диске. Это критически важно для производительности.
- **Ключ партиционирования (`PARTITION BY`):** Позволяет разбивать данные на более мелкие части (партиции) по ключу, например, по месяцам.

**Партиция (part)** — это минимальная единица хранения данных в ClickHouse. При каждой вставке создаётся одна или несколько новых партиций. Частые маленькие вставки (например, по одной строке) приводят к появлению множества мелких партиций, что снижает производительность. Рекомендуется:
- Пакетная загрузка: от 100 000 до 1 000 000 строк за одну вставку
- Частота вставок: не чаще одного раза в секунду для одной таблицы

**Мутации** — механизм изменения или удаления данных в ClickHouse. В отличие от традиционных СУБД, мутации выполняются асинхронно и тяжёлые: при UPDATE/DELETE ClickHouse вычитывает партицию, применяет изменения и записывает её заново. Злоупотребление мутациями может привести к зависанию очередей и перерасходу ресурсов.

### MPP-архитектура (Massively Parallel Processing)

ClickHouse использует **MPP-архитектуру** — массивно-параллельную обработку данных. Ключевые принципы:

- **Распределение данных и вычислений:** Данные и вычислительные мощности распределены по множеству узлов (нод). Каждый узел обрабатывает свою часть данных независимо и параллельно.
- **Принцип Shared-Nothing:** Каждая нода независима — у неё свои диски, память и процессор. Сбой одной ноды не влияет на другие.
- **Скорость выполнения запроса:** Определяется скоростью **самой медленной** ноды в кластере. Все ноды должны завершить обработку, прежде чем результат будет возвращён.
- **Масштабирование:** Горизонтальное — добавление новых нод увеличивает и объём хранилища, и вычислительную мощность.

**Сравнение с PostgreSQL:**
- PostgreSQL (ванильный): один мастер (запись + чтение) + реплики (только чтение). Узкое горлышко на запись.
- ClickHouse: любая нода может быть мастером для любого куска данных. Распределённая запись на все ноды.

### Масштабирование: Репликация и Шардирование

- **Репликация:** Обеспечивает **отказоустойчивость**. Для управления используется **Apache ZooKeeper** или его аналог **ClickHouse Keeper**. Репликация настраивается на уровне таблиц с помощью движков семейства `ReplicatedMergeTree`. Поддерживается Multi-Master репликация, позволяющая записывать данные в любую реплику.

  **Принцип работы репликации:**
  1. Вставка данных происходит на одну из нод (мастер для этой партиции).
  2. Метаданные о новой партиции отправляются в ZooKeeper/ClickHouse Keeper.
  3. Keeper уведомляет остальные реплики о новых данных.
  4. Реплики самостоятельно загружают данные с мастер-ноды.
  5. Репликация асинхронная — возможна временная несогласованность.

- **Шардирование:** Обеспечивает **горизонтальное масштабирование** производительности. Данные распределяются по серверам (шардам) с помощью движка `Distributed`, который является "прокси" над локальными таблицами на каждом шарде.

  **Ключ шардирования:** Критически важный параметр. Неправильный выбор приводит к перекосу данных (data skew) и "горячим точкам" (hotspots).
  
  **Стратегии распределения:**
  - **По хешу ключа:** `rand()`, `cityHash64(user_id)` — равномерное распределение.
  - **По бизнес-ключу:** `order_id`, `user_id` — группировка связанных данных на одном шарде.
  - **Round-robin:** равномерное распределение без учёта ключа.
  - **Репликация справочников:** небольшие таблицы-справочники дублируются на все ноды для эффективных JOIN.

  **Важно:** Ре-шардирование (добавление нового шарда) в ClickHouse **не автоматизировано**. Требуется ручное перераспределение данных.

## Практические сценарии

### Когда переходить на ClickHouse

**Признаки того, что PostgreSQL не справляется с аналитической нагрузкой:**

1. **Медленные аналитические запросы:**
   - Запросы с `GROUP BY`, `COUNT`, `SUM` на таблицах от 10 млн строк выполняются десятки секунд
   - Дашборды в BI загружаются дольше 5–10 секунд
   - Индексы перестают помогать, даже на репликах для чтения

2. **Высокая задержка из-за аналитики:**
   - Тяжёлые SELECT-запросы повышают latency для обычных пользователей
   - Аналитика мешает продуктовому трафику (записи данных)
   - Приходится запускать аналитику ночью, чтобы не мешать дневной нагрузке

3. **Проблемы с материализованными представлениями:**
   - Обновление материализованных представлений занимает минуты
   - Представления блокируют запросы во время обновления
   - Данные устаревают быстрее, чем успевает обновиться представление

4. **Масштабирование не решает проблему:**
   - Горизонтальное масштабирование через Citus сложно и дорого
   - Добавление реплик не помогает при высокой нагрузке на запись
   - Вертикальное масштабирование упирается в экономические/физические пределы

5. **Объём данных:**
   - Таблицы превысили 1–10 ТБ
   - Объём данных растёт быстрее, чем возможности масштабирования PostgreSQL

**Правило 80/20:** Если 20% аналитических запросов потребляют более 80% суммарного времени CPU — это чёткий сигнал к рассмотрению специализированного OLAP-хранилища.

### Когда НЕ нужно мигрировать на ClickHouse

- **Транзакционные нагрузки:** ClickHouse не поддерживает ACID. Не храните транзакционные данные в ClickHouse.
- **Мало данных:** До 1 ТБ данных — PostgreSQL справится при правильной индексации и партиционировании.
- **Простая аналитика:** 2–3 стандартных отчёта без сложных агрегатов — можно ускорить материализованными представлениями.
- **Маленькая команда:** Нет ресурсов на поддержку двух СУБД и изучение ClickHouse.
- **Частые UPDATE/DELETE:** ClickHouse не предназначен для частых изменений данных.
- **Модный тренд:** Не выбирайте ClickHouse только потому, что он популярный.

### Создание локальной таблицы

```sql
CREATE TABLE orders (
    order_id UInt64,
    customer_id UInt64,
    order_date Date,
    total_amount Float64
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(order_date)
ORDER BY (order_date, order_id);
```

### Репликация таблицы

Для создания реплицируемой таблицы используется движок `ReplicatedMergeTree`.

```sql
-- {shard} и {replica} — это макросы, которые заменяются на значения из конфигурации сервера.
CREATE TABLE orders_replicated (
    order_id UInt64,
    order_date Date
) ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/orders', '{replica}')
PARTITION BY toYYYYMM(order_date)
ORDER BY order_date;
```

### Шардирование с помощью `Distributed` таблиц

1. **Конфигурация кластера:** В конфигурационном файле сервера определяется кластер — именованная группа шардов, каждый из которых может содержать реплики.

    ```xml
    <remote_servers>
        <my_cluster>
            <shard>
                <internal_replication>true</internal_replication>
                <replica>
                    <host>host1.example.com</host>
                    <port>9000</port>
                </replica>
                ...
            </shard>
            ...
        </my_cluster>
    </remote_servers>
    ```

2. **Создание распределенной таблицы:** Поверх локальных таблиц на всех шардах создается `Distributed` таблица.

    ```sql
    -- my_cluster — имя кластера из конфигурации
    -- rand() — ключ шардирования (здесь — случайное распределение)
    CREATE TABLE orders_distributed AS orders_replicated
    ENGINE = Distributed(my_cluster, default, orders_replicated, rand());
    ```

    - При **вставке** данных `Distributed` таблица распределяет их по шардам.
    - При **чтении** она отправляет запрос на все шарды и агрегирует результат.

### Применение в аналитике

- **Скорость:** Быстрое выполнение `COUNT`, `SUM`, `AVG` по большим объемам данных.
- **Оконные функции:** Возможность выполнять сложные вычисления, например, расчет скользящего среднего.
- **Денормализация:** Для максимальной производительности часто используется денормализация данных в одну "широкую" таблицу, чтобы избежать `JOIN`'ов.

## Дополнительная информация

### Типы данных

ClickHouse поддерживает богатую систему типов данных:

- **Числовые:** `UInt8`–`UInt256`, `Int8`–`Int256`, `Float32`, `Float64`, `Decimal`
- **Строковые:** `String`, `FixedString(N)`
- **Дата и время:** `Date`, `DateTime`, `DateTime64`
- **Сложные:** `Array(T)`, `Tuple(T1, T2, ...)`, `Map(Key, Value)`, `Nested`
- **Специализированные:** `UUID`, `IPv4`, `IPv6`, `JSON` (экспериментальный)

**Особенности:**
- `String` вместо `TEXT`/`VARCHAR` как в PostgreSQL
- `FixedString(N)` для строк фиксированной длины
- `Nested` — для вложенных структур данных (массивы структур)
- Поддержка массивов и JSON позволяет хранить сложные структуры без нормализации

### Особенности и "капризы" ClickHouse

**Несогласованность данных:**
- ClickHouse следует принципам **BASE** (Basically Available, Soft state, Eventual consistency), а не ACID
- CTE (Common Table Expressions) могут возвращать разное количество строк при многократном обращении в одном запросе
- Данные в репликах могут временно расходиться (асинхронная репликация)

**Отсутствие транзакций:**
- Нет блокировок строк/таблиц
- INSERT не гарантирует атомарность при сбоях
- SELECT во время INSERT видит данные по мере их поступления

**Материализованные представления:**
- **Обычные:** Trigger-based — реагируют только на INSERT в исходную таблицу. Данные хранятся в отдельной таблице.
- **Refreshable:** Обновляются по расписанию (не чаще раза в минуту). Аналог материализованных представлений PostgreSQL.

**Интеграция с Kafka:**
- Движок `Kafka` создаёт "окно" в топик Kafka
- Данные можно переливать в основную таблицу через материализованное представление
- Поддерживает форматы: `JSONEachRow`, `CSV`, `Avro`, `Parquet`, `Protobuf` и др.

### Требования к оборудованию

ClickHouse требователен к ресурсам. Рекомендуемая конфигурация ноды:

- **CPU:** 32+ ядра (важно количество ядер, а не тактовая частота)
- **RAM:** 512+ ГБ (ClickHouse активно использует память)
- **Диски:** NVMe SSD от 8 ТБ (скорость дисков критична)
- **Сеть:** 10+ Гбит/с для кластера

**Масштабирование:** Предпочтительно множество небольших нод вместо нескольких мощных.

### Сравнение с другими системами

| Система | Тип | Назначение |
| :--- | :--- | :--- |
| **PostgreSQL** | OLTP (строковая) | Транзакции, операционные данные |
| **ClickHouse** | OLAP (колоночная) | Аналитика, отчёты, Big Data |
| **Greenplum** | OLAP (MPP на PostgreSQL) | Аналитика, DWH (дороже, сложнее) |
| **Hadoop/HDFS** | Хранилище (Data Lake) | Сырые данные, batch-обработка |

**ClickHouse vs Hadoop:**
- Hadoop — это "озеро данных" (storage), ClickHouse — вычислительная система (compute)
- ClickHouse в 10–100 раз быстрее для интерактивной аналитики
- Интеграция: данные из Hadoop (Parquet) загружаются в ClickHouse для анализа

### Интеграция с PostgreSQL

ClickHouse часто используется в гибридной связке с PostgreSQL, где PostgreSQL выполняет роль OLTP-системы, а ClickHouse — аналитического фронтенда. Данные периодически или в реальном времени переносятся из PostgreSQL в ClickHouse.

Подробнее о вариантах интеграции см. в заметке **[Интеграция PostgreSQL и ClickHouse](./PostgreSQL/Integrations/clickhouse.md)**.
