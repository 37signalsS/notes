# ClickHouse

## Определения

**ClickHouse** — это колоночная (столбцовая) система управления базами данных (СУБД) для онлайн-обработки аналитических запросов (OLAP), изначально разработанная в Яндексе для Яндекс.Метрики.

**Текущая версия:** ClickHouse 26.2 (март 2026).

**OLAP vs OLTP:** ClickHouse относится к классу OLAP-систем (Online Analytical Processing), в отличие от OLTP-систем (Online Transactional Processing), таких как PostgreSQL. Ключевые различия:

| Характеристика | OLTP (PostgreSQL) | OLAP (ClickHouse) |
| :--- | :--- | :--- |
| **Назначение** | Транзакции (создание заказа, обновление профиля) | Аналитика (отчёты, агрегации) |
| **Структура хранения** | Строковая | Колоночная |
| **Операции** | Частые INSERT/UPDATE/DELETE | Массовые INSERT, редкие UPDATE/DELETE |
| **Данные** | Нормализованные | Денормализованные |
| **Масштабирование** | Вертикальное / репликация чтения | Горизонтальное (MPP, шардирование) |
| **Гарантии** | ACID | BASE (скорость важнее согласованности) |

## Основные концепции

ClickHouse предназначен для работы с огромными объемами данных (терабайты и петабайты), позволяя выполнять аналитические запросы по миллиардам записей за доли секунды.

### Ключевые особенности

- **Колоночное хранение:** Данные хранятся по столбцам, а не по строкам. Это обеспечивает эффективное сжатие (до 10–13 раз) и ускоряет выполнение агрегирующих запросов, так как с диска читаются только необходимые столбцы.
- **Высокая производительность:** Выполняет запросы в 100–1000 раз быстрее строковых СУБД на больших объёмах данных.
- **MPP-архитектура:** Массивно-параллельная обработка данных с принципом **Shared-Nothing** — каждая нода независима (свои диски, память, процессор). Скорость запроса определяется скоростью самой медленной ноды.
- **Горизонтальное масштабирование:** Репликация и шардирование настраиваются на уровне таблиц.
- **SQL-подобный язык запросов:** Диалект SQL с расширениями для аналитических функций.
- **Отсутствие блокировок:** Нет блокировок строк/таблиц, что упрощает параллельную обработку.

### Архитектура хранения: Движки `MergeTree`

Основой хранения является семейство движков `MergeTree`. При создании таблицы указываются:

- **Движок (`ENGINE`):** Например, `MergeTree`, `ReplicatedMergeTree`.
- **Ключ сортировки (`ORDER BY`):** Определяет физический порядок хранения данных на диске. Критически важен для производительности.
- **Ключ партиционирования (`PARTITION BY`):** Разбивает данные на партиции по ключу (например, по месяцам).

**Партиция (part)** — минимальная единица хранения. При каждой вставке создаются новые партиции. Частые маленькие вставки приводят к множеству мелких партиций, что снижает производительность.

**Рекомендации по вставке:**
- Пакетная загрузка: от 100 000 до 1 000 000 строк за одну вставку
- Частота вставок: не чаще одного раза в секунду для одной таблицы

**Мутации** — механизм изменения или удаления данных. Выполняются асинхронно: при UPDATE/DELETE ClickHouse вычитывает партицию, применяет изменения и записывает её заново. Злоупотребление мутациями приводит к зависанию очередей.

### Репликация и шардирование

**Репликация** обеспечивает отказоустойчивость:

- Управляется через **Apache ZooKeeper** или **ClickHouse Keeper**.
- Движки семейства `ReplicatedMergeTree` настраиваются на уровне таблиц.
- **Multi-Master репликация:** запись в любую реплику.
- **Принцип работы:**
  1. Вставка данных на одну из нод.
  2. Метаданные о новой партиции отправляются в Keeper.
  3. Keeper уведомляет остальные реплики.
  4. Реплики самостоятельно загружают данные с мастер-ноды.
  5. Репликация асинхронная — возможна временная несогласованность.

**Шардирование** обеспечивает горизонтальное масштабирование производительности:

- Движок `Distributed` — "прокси" над локальными таблицами на каждом шарде.
- **Ключ шардирования** критически важен. Неправильный выбор приводит к перекосу данных (data skew) и "горячим точкам" (hotspots).
- **Стратегии распределения:**
  - По хешу ключа: `rand()`, `cityHash64(user_id)` — равномерное распределение.
  - По бизнес-ключу: `order_id`, `user_id` — группировка связанных данных на одном шарде.
  - Round-robin: равномерное распределение без учёта ключа.
  - Репликация справочников: небольшие таблицы дублируются на все ноды для эффективных JOIN.
- **Ре-шардирование** не автоматизировано — требуется ручное перераспределение данных.

Подробнее об общей теории шардирования и MPP-архитектуры: **[Шардирование](./Concepts/sharding.md)**.

## Практические сценарии

### Когда переходить на ClickHouse

**Признаки того, что PostgreSQL не справляется с аналитической нагрузкой:**

1. **Медленные аналитические запросы:**
   - Запросы с `GROUP BY`, `COUNT`, `SUM` на таблицах от 10 млн строк выполняются десятки секунд
   - Дашборды в BI загружаются дольше 5–10 секунд
   - Индексы перестают помогать, даже на репликах для чтения

2. **Высокая задержка из-за аналитики:**
   - Тяжёлые SELECT-запросы повышают latency для обычных пользователей
   - Аналитика мешает продуктовому трафику
   - Приходится запускать аналитику ночью

3. **Проблемы с материализованными представлениями:**
   - Обновление занимает минуты, представления блокируют запросы
   - Данные устаревают быстрее, чем обновляются представления

4. **Масштабирование не решает проблему:**
   - Горизонтальное масштабирование через Citus сложно и дорого
   - Добавление реплик не помогает при высокой нагрузке на запись

5. **Объём данных:**
   - Таблицы превысили 1–10 ТБ
   - Объём данных растёт быстрее возможностей масштабирования PostgreSQL

**Правило 80/20:** Если 20% аналитических запросов потребляют более 80% суммарного времени CPU — сигнал к рассмотрению OLAP-хранилища.

### Когда НЕ нужно мигрировать на ClickHouse

- **Транзакционные нагрузки:** ClickHouse не поддерживает ACID
- **Мало данных:** До 1 ТБ — PostgreSQL справится при правильной индексации
- **Простая аналитика:** 2–3 стандартных отчёта — можно ускорить материализованными представлениями
- **Маленькая команда:** Нет ресурсов на поддержку двух СУБД
- **Частые UPDATE/DELETE:** ClickHouse не предназначен для частых изменений данных

### Примеры SQL-запросов

**Создание локальной таблицы:**
```sql
CREATE TABLE orders (
    order_id UInt64,
    customer_id UInt64,
    order_date Date,
    total_amount Float64
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(order_date)
ORDER BY (order_date, order_id);
```

**Создание реплицируемой таблицы:**
```sql
CREATE TABLE orders_replicated (
    order_id UInt64,
    order_date Date
) ENGINE = ReplicatedMergeTree('/clickhouse/tables/{shard}/orders', '{replica}')
PARTITION BY toYYYYMM(order_date)
ORDER BY order_date;
```

**Создание распределённой таблицы:**
```sql
CREATE TABLE orders_distributed AS orders_replicated
ENGINE = Distributed(my_cluster, default, orders_replicated, rand());
```

**Конфигурация кластера (XML):**
```xml
<remote_servers>
    <my_cluster>
        <shard>
            <internal_replication>true</internal_replication>
            <replica>
                <host>host1.example.com</host>
                <port>9000</port>
            </replica>
        </shard>
    </my_cluster>
</remote_servers>
```

**Аналитический запрос:**
```sql
SELECT
    toDate(order_date) AS date,
    count() AS orders_count,
    sum(total_amount) AS revenue
FROM orders_distributed
GROUP BY date
ORDER BY date DESC;
```

## Дополнительная информация

### Типы данных

- **Числовые:** `UInt8`–`UInt256`, `Int8`–`Int256`, `Float32`, `Float64`, `Decimal`
- **Строковые:** `String`, `FixedString(N)`
- **Дата и время:** `Date`, `DateTime`, `DateTime64`
- **Сложные:** `Array(T)`, `Tuple(T1, T2, ...)`, `Map(Key, Value)`, `Nested`
- **Специализированные:** `UUID`, `IPv4`, `IPv6`, `JSON` (экспериментальный)

### Особенности ClickHouse

**Несогласованность данных:**
- Следует принципам **BASE**, а не ACID
- CTE могут возвращать разное количество строк в одном запросе
- Данные в репликах могут временно расходиться

**Отсутствие транзакций:**
- Нет блокировок строк/таблиц
- INSERT не гарантирует атомарность при сбоях

**Материализованные представления:**
- **Trigger-based:** Реагируют только на INSERT, данные хранятся в отдельной таблице
- **Refreshable:** Обновляются по расписанию (минимальный интервал — 1 минута)

**Интеграция с Kafka:**
- Движок `Kafka` создаёт "окно" в топик
- Поддерживает форматы: `JSONEachRow`, `CSV`, `Avro`, `Parquet`, `Protobuf`

### Требования к оборудованию

| Ресурс | Минимум | Рекомендуется |
| :--- | :--- | :--- |
| **CPU** | 16 ядер | 32+ ядра |
| **RAM** | 128 ГБ | 512+ ГБ |
| **Диски** | SSD 4 ТБ | NVMe SSD от 8 ТБ |
| **Сеть** | 1 Гбит/с | 10+ Гбит/с |

**Принцип масштабирования:** Предпочтительно множество небольших нод вместо нескольких мощных.

### Сравнение с другими системами

| Система | Тип | Назначение |
| :--- | :--- | :--- |
| **[PostgreSQL](./PostgreSQL/overview.md)** | OLTP (строковая) | Транзакции, операционные данные |
| **ClickHouse** | OLAP (колоночная) | Аналитика, отчёты, Big Data |
| **[Greenplum](./greenplum.md)** | OLAP (MPP на PostgreSQL) | Аналитика, DWH |
| **Hadoop/HDFS** | Хранилище (Data Lake) | Сырые данные, batch-обработка |

**ClickHouse vs Hadoop:**
- Hadoop — "озеро данных" (storage), ClickHouse — вычислительная система (compute)
- ClickHouse в 10–100 раз быстрее для интерактивной аналитики
