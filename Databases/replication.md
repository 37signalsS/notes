## Репликация баз данных

**Репликация** — это процесс создания и поддержания копий (реплик) базы данных на нескольких серверах. Это ключевой механизм для обеспечения отказоустойчивости и масштабируемости.

В то время как репликация *копирует* данные, другой метод масштабирования, **[шардирование](./sharding.md)**, *разделяет* их по разным серверам.

### Основные цели репликации

- **Высокая доступность (High Availability):** Если основной (master) сервер выходит из строя, один из ведомых (slave) серверов может взять на себя его роль, минимизируя время простоя.
- **Масштабирование нагрузки на чтение (Read Scaling):** Запросы на чтение можно распределить между несколькими репликами, что снижает нагрузку на основной сервер и увеличивает общую производительность.
- **Резервное копирование:** Реплики можно использовать для создания [резервных копий](./database_backups.md) без остановки или замедления работы основного сервера.
- **Географическое распределение:** Размещение реплик ближе к пользователям в разных регионах может значительно уменьшить задержку при чтении данных.

### Типы репликации по механизму передачи данных

Выбор между синхронной и асинхронной репликацией напрямую влияет на компромисс между согласованностью (Consistency) и доступностью (Availability) в CAP-теореме.

#### Синхронная репликация

При синхронной репликации транзакция на master-сервере не считается завершенной до тех пор, пока все изменения не будут успешно применены на всех репликах. 

**Схема процесса:**
```text
  Клиент                    Master                      Replica
    | -- 1. WRITE ---------> |                           |
    |                        | -- 2. REPLICATE --------> |
    |                        |                           | -- 3. OK
    |                        | <-------- 4. ACK --------- |
    | <------- 5. OK -------- |                           |
```

*   **Процесс:**
    1.  Клиент отправляет запрос на запись на master-узел.
    2.  Master-узел записывает данные локально.
    3.  Master-узел пересылает изменения на все реплики.
    4.  Каждая реплика подтверждает успешное применение изменений.
    5.  Только после получения всех подтверждений master-узел сообщает клиенту об успешном завершении транзакции.

*   **Плюсы:**
    *   **Сильная согласованность (Strong Consistency):** Гарантируется, что все реплики всегда содержат идентичные данные. Потеря данных при сбое мастера исключена.
*   **Минусы:**
    *   **Высокая задержка:** Общая задержка на запись равна сумме задержек на всех репликах.
    *   **Низкая доступность:** Если хотя бы одна реплика не доступна, запись на master-узел блокируется.

*   **Связь с CAP:** Этот подход характерен для **CP** (Consistency + Partition Tolerance) или **CA** (Consistency + Availability) систем.

#### Асинхронная репликация

При асинхронной репликации транзакция на master-сервере считается завершенной сразу после локальной записи. Передача данных на реплики происходит в фоновом режиме с некоторой задержкой (replication lag).

*   **Процесс:**
    1.  Клиент отправляет запрос на запись на master-узел.
    2.  Master-узел записывает данные локально и сразу же подтверждает успешное завершение транзакции клиенту.
    3.  Master-узел асинхронно, без ожидания, отправляет изменения на реплики.

*   **Плюсы:**
    *   **Низкая задержка:** Запись на master-узел происходит очень быстро.
    *   **Высокая доступность:** Недоступность реплик не влияет на возможность записи на master-узел.
*   **Минусы:**
    *   **Возможна потеря данных:** Если master-узел выйдет из строя до того, как данные будут переданы на реплики, эти данные будут потеряны.
    *   **Согласованность в конечном счете (Eventual Consistency):** Существует задержка репликации, из-за которой чтение с реплики может вернуть устаревшие данные.

*   **Связь с CAP:** Этот подход характерен для **AP** (Availability + Partition Tolerance) систем.

### Основные топологии репликации

#### Master-Slave (Ведущий-ведомый)

Самая распространенная топология. Есть один главный узел (Master), который принимает все запросы на запись. Данные с него реплицируются на один или несколько ведомых узлов (Slaves), которые обычно обрабатывают запросы на чтение.

*   **Плюсы:** Простота настройки и понимания.
*   **Минусы:** Master является единой точкой отказа для операций записи.

**Пример: MySQL Master-Slave**

Это классическая реализация данной топологии.

**Схема потоков данных:**
```text
  [Клиент] -- WRITE --> [MASTER] -- REPLICATE --> [SLAVE]
     ^                     |                      |
     |                     |                      |
     '----- READ ----------'                      '-- READ
```

*   **Запись (Write):** Всегда идет только в Master.
*   **Чтение (Read):** Может идти как с Master (гарантированно свежие данные), так и со Slave (для масштабирования нагрузки, но с возможной задержкой репликации).

**Нюанс с "CA-системой":**
Хотя на схеме такая система помечена как CA, это является упрощением.
*   Сам по себе **Master-узел является CA-системой**: он согласован (Consistency) и доступен (Availability), но не устойчив к разделению (нет Partition Tolerance, т.к. он один).
*   Вся система **Master + Slave с асинхронной репликацией** по факту является **AP-системой**, так как чтение со Slave может возвращать устаревшие данные в угоду доступности. Сильной согласованности в целом по кластеру нет.

> Подробный внутренний механизм этого процесса описан в заметке **[Обзор MySQL](./mysql_overview.md)**.

**Вариации топологии Master-Slave**

1.  **Один Master, много Slave (1 -> N)**
    Это стандартный способ масштабирования чтения. Master реплицирует данные на несколько (N) ведомых узлов.
    ```text
             +-----> [SLAVE 1]
    [MASTER] --+-----> [SLAVE 2]
             +-----> [SLAVE N]
    ```

2.  **Цепочечная репликация (Chained Replication)**
    В этой конфигурации slave-узел сам выступает мастером для следующего slave-узла.
    ```text
    [MASTER] --> [SLAVE 1] --> [SLAVE 2] --> ...
    ```
    *   **Преимущество:** Снижает нагрузку на основной master-узел, так как ему нужно отправлять бинарный лог только одному получателю (Slave 1).
    *   **Недостаток:** Увеличивается общая задержка репликации. Данные дойдут до `SLAVE 2` позже, чем до `SLAVE 1`.

#### Master-Master (Ведущий-ведущий)

В этой топологии два или более узла являются ведущими и могут принимать запросы на запись. Изменения, сделанные на одном мастере, реплицируются на другой.

*   **Плюсы:** Повышенная отказоустойчивость для операций записи.
*   **Минусы:** Сложность в настройке и, что более важно, высокий риск возникновения **конфликтов записи** (когда одни и те же данные изменяются одновременно на разных мастерах). Требуются сложные механизмы разрешения конфликтов.

### Программные причины сбоев в Master-Master

Помимо сетевых проблем (split-brain), существует ряд чисто программных причин, по которым Master-Master репликация может легко выйти из строя.

1.  **Конфликты `AUTO_INCREMENT`**
    -   **Проблема:** Это самая частая причина сбоя. Оба мастера считают, что они имеют право выдать следующий ID для новой записи. Если они одновременно вставляют строки, они могут сгенерировать **один и тот же ID**. Когда изменение от первого мастера прилетит на второй, репликация остановится с ошибкой нарушения уникальности первичного ключа.
    -   **Решение:** Настроить серверы так, чтобы они не могли генерировать пересекающиеся ID. В MySQL для этого используются переменные `auto_increment_increment` (шаг) и `auto_increment_offset` (смещение). Например, для двух мастеров:
        -   *Мастер 1:* `auto_increment_increment = 2`, `auto_increment_offset = 1` (генерирует ID: 1, 3, 5, ...)
        -   *Мастер 2:* `auto_increment_increment = 2`, `auto_increment_offset = 2` (генерирует ID: 2, 4, 6, ...)

2.  **Недетерминированные запросы**
    -   **Проблема:** Запросы, использующие функции, результат которых может отличаться в зависимости от времени или сервера (`UUID()`, `NOW()`, `RAND()`). Например, запрос `INSERT ... VALUES (UUID())` на каждом мастере сгенерирует *разные* UUID. Это не остановит репликацию, но приведет к **тихой порче данных** — данные в одной и той же строке на разных мастерах будут отличаться.
    -   **Решение:** Использовать **строчный формат бинарного лога (`binlog_format = ROW`)**. В этом режиме в лог пишется не сам запрос, а уже измененная строка (конечный результат). Таким образом, на второй мастер прилетит уже готовая строка с правильным UUID, а не функция, которую нужно выполнить заново.

3.  **Операции изменения схемы (DDL)**
    -   **Проблема:** Команды `ALTER TABLE`, `DROP TABLE` и другие DDL-операции не являются атомарными в контексте репликации и могут вызвать хаос. Одновременное применение разных `ALTER` на разных мастерах почти гарантированно приведет к сбою.
    -   **Решение:** Проводить миграции схемы через специальные утилиты (`pt-online-schema-change`, `gh-ost`) и по строгому регламенту, исключающему одновременные изменения.

4.  **Ошибки в логике приложения**
    -   **Проблема:** Классическая гонка "прочитал-изменил-записал". Приложение на первом мастере читает `balance = 100`. В этот же момент приложение на втором мастере читает то же значение. Оба отнимают 10 и записывают `balance = 90`. В итоге со счета списалось 20, а баланс уменьшился только на 10.
    -   **Решение:** Использовать пессимистические блокировки (`SELECT ... FOR UPDATE`) или перекладывать логику изменения на саму БД (`UPDATE table SET balance = balance - 10`), чтобы операция была атомарной.


**Пример: MySQL Master-Master**

**Схема потоков данных:**
```text
  [Клиент] --> WRITE/READ --> [MASTER 1] <-- REPLICATE --> [MASTER 2] <-- WRITE/READ <-- [Клиент]
```

*   **Поведение:** Любой из master-узлов может принимать как чтение, так и запись. Изменения с одного узла асинхронно реплицируются на другой.
*   **Связь с CAP:** Такая конфигурация является классической **AP-системой**. Она обеспечивает высокую доступность (Availability) для записи, так как выход из строя одного мастера не останавливает запись на втором. Однако это достигается ценой отказа от сильной согласованности (Consistency), так как возможны задержки репликации и, что еще опаснее, конфликты записи.

### Проблема Split-Brain в асинхронных топологиях

**Split-Brain** (расщепление мозга) — это критическая ошибка в распределенных системах, которая возникает в топологиях Master-Slave и Master-Master при неправильно настроенном автоматическом переключении (failover).

**Сценарий возникновения:**

1.  **Разрыв связи:** Канал связи между Master и Slave (или между двумя Master-узлами) обрывается.
2.  **Неправильное решение о сбое:** Slave-узел, не видя Master-сервер, решает, что тот вышел из строя. Автоматизированная система (или администратор) повышает Slave до роли нового Master-сервера.
3.  **Появление двух Master-узлов:** В этот момент в кластере существуют два активных Master-сервера, которые не знают друг о друге. Старый Master (который на самом деле не падал, а был лишь изолирован) и новый, бывший Slave.
4.  **Рассинхронизация данных:** Оба узла начинают принимать запросы на запись, и их данные необратимо расходятся. Клиенты, подключенные к разным мастерам, видят и изменяют разное состояние системы.
5.  **Сложное восстановление:** После восстановления связи выясняется, что в системе существуют две конфликтующие версии правды. Сведение этих данных в единое целое — сложная и часто ручная задача, ведущая к простоям и возможной потере данных.

Эта проблема является основной причиной, по которой автоматическое переключение в простых асинхронных системах репликации требует очень осторожного подхода.

### Кворум как решение проблемы Split-Brain

Для решения проблемы Split-Brain и обеспечения строгой согласованности (Consistency) используются **кворумные системы** (например, Percona XtraDB Cluster, Galera Cluster, или системы, использующие Zookeeper).

Идея кворума заключается в том, что для выполнения операций записи кластер должен иметь **большинство** голосов. Обычно каждый узел имеет один голос.

**Принцип работы на примере кластера из 3-х узлов:**

1.  **Нормальная работа:** В кластере 3 узла. Кворум (большинство) составляет `(3 / 2) + 1 = 2` узла. Пока 2 или 3 узла "видят" друг друга, кластер принимает запросы на запись.

2.  **Сбой одного узла:** Один узел выходит из строя. В сети остаются 2 узла. Они составляют большинство (кворум), и кластер продолжает работать в штатном режиме. Запись доступна.

3.  **Разрыв сети (Split):** Сеть разделяется так, что с одной стороны остается 1 узел, а с другой — 2 узла.
    *   **Сегмент с 2-мя узлами:** Этот сегмент имеет кворум (большинство). Он продолжает принимать запросы на чтение и запись. Он является "истинной" частью кластера.
    *   **Сегмент с 1-м узлом:** Этот узел понимает, что он в меньшинстве (не имеет кворума). Чтобы предотвратить Split-Brain, он автоматически переходит в режим "только для чтения" или полностью блокирует запись. Он не имеет права изменять состояние кластера.

4.  **Восстановление:**
    *   Когда узел, который отвалился, возвращается в строй, он видит, что его версия данных устарела. Он запрашивает у основного компонента кластера недостающие изменения и догоняет его, после чего полноценно присоединяется к работе.
    *   Если весь кластер теряет кворум (например, из 3-х узлов остаются работать только 1), то весь кластер **автоматически прекращает принимать запросы на запись**, чтобы гарантировать целостность данных. Это яркий пример выбора **согласованности (C) в ущерб доступности (A)** в [CAP-теореме](./cap_theorem.md).
