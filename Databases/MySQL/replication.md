# Репликация в MySQL

## Определения

**Репликация MySQL** — это процесс создания и поддержания идентичных копий (реплик) базы данных на нескольких серверах. Данные копируются с основного сервера, называемого **Master**, на один или несколько подчиненных серверов, называемых **Slave**.

- **Master Server (Ведущий)**: Источник данных, на котором происходят все операции записи. Изменения фиксируются в специальном журнале.
- **Slave Server (Ведомый)**: Копия Master-сервера, которая получает изменения от Master и применяет их к своей копии данных. Обычно используется для распределения нагрузки на чтение, резервного копирования или как "горячий" резерв.
- **Бинарный лог (Binary Log)**: Файл на Master-сервере, в который записываются все события, изменяющие данные (DML) или структуру базы данных (DDL). Является основой для репликации.
- **Журнал ретрансляции (Relay Log)**: Файл на Slave-сервере, в который I/O-поток записывает события, полученные из бинарного лога Master-сервера. SQL-поток читает события из этого журнала и выполняет их.

## Базовые концепции

### 1. Механизм Master-Slave репликации

Стандартная асинхронная master-slave репликация в MySQL работает на основе бинарного лога (`binary log`) и включает в себя три основных потока:

**Схема компонентов:**

```text
                                    +------------------------------------+
                                    |             Slave Server           |
                                    |                                    |
+----------------+                  |  +-------------+   +-------------+   |   +----------+
| Master Server  |                  |  |             |   |             |   |   |          |
|                | -- Binlog dump --> |  I/O Thread   |-->|  Relay Log  |--> | SQL Thread |-->| Database |
| +------------+ |                  |  |             |   |             |   |   |          |
| | Binary Log | |                  |  +-------------+   +-------------+   |   +----------+
| +------------+ |                  |                                    |
|       ^        |                  +------------------------------------+
|       |        |
| DML Commands   |
|       |        |
| +----------+   |
| | Database |   |
| +----------+   |
+----------------+
```

1. **Запись на Master:** Любые команды изменения данных (DML: `INSERT`, `UPDATE`, `DELETE`) на master-сервере записываются в специальный файл — **бинарный лог (Binary Log)**. Этот лог содержит все события, которые изменяют данные в базе.

2. **Подключение Slave:** Slave-сервер инициирует подключение к master-серверу. Для этого на slave-сервере запускается специальный поток — **I/O Thread**.

3. **Запрос данных:** `I/O Thread` на slave-сервере запрашивает у master-сервера содержимое его бинарного лога, начиная с последней сохраненной позиции.

4. **Отправка данных:** На master-сервере для каждого подключенного slave-сервера создается поток **Binlog Dump Thread**. Его задача — читать бинарный лог и отправлять его содержимое в `I/O Thread` slave-сервера.

5. **Запись в Relay Log:** `I/O Thread` на slave-сервере, получив данные от мастера, не применяет их сразу, а записывает их в свой собственный лог — **журнал ретрансляции (Relay Log)**. Этот журнал является точной копией бинарного лога мастера. Такой подход позволяет slave-серверу получить все изменения от мастера как можно быстрее, не задерживаясь на их выполнении.

6. **Применение данных:** На slave-сервере работает второй важный поток — **SQL Thread**. Он последовательно читает события из `Relay Log`, преобразует их в SQL-запросы и выполняет на своей копии базы данных. Именно на этом этапе происходит фактическое изменение данных на slave-сервере.

**Ключевые моменты:**

- **Разделение потоков:** Разделение на I/O- и SQL-потоки является ключевой оптимизацией. I/O-поток отвечает за быструю сетевую пересылку, а SQL-поток — за их применение. Это предотвращает отставание репликации (`replication lag`).
- **Отставание репликации (Replication Lag):** Задержка между записью на мастере и применением на слейве. Может возникать из-за медленной сети (влияет на I/O-поток) или высокой нагрузки на слейве (влияет на SQL-поток).

### 2. Форматы бинарного лога (binlog_format)

Параметр `binlog_format` определяет, *что именно* записывается в бинарный лог.

#### 1. `STATEMENT` (Statement-Based Replication - SBR)

- **Принцип:** В лог записываются сами SQL-запросы (`INSERT`, `UPDATE`, `DELETE`).
- **Проблема:** Ненадежен для **недетерминированных** функций, таких как `NOW()` или `UUID()`. Выполнение одного и того же запроса на мастере и слейве в разное время приведет к рассинхронизации данных.
- **Плюсы:** Минимальный размер логов.
- **Минусы:** Небезопасен для целостности данных. Не является режимом по умолчанию в современных версиях MySQL.

#### 2. `ROW` (Row-Based Replication - RBR)

- **Принцип:** В лог записывается не SQL-запрос, а бинарное представление **измененных строк** (до и после).
- **Надежность:** Формат полностью детерминирован. Он не выполняет функцию `NOW()` на слейве заново, а копирует строку с уже готовым значением. Это гарантирует побайтовое совпадение данных.
- **Плюсы:** Максимальная консистентность данных.
- **Минусы:** Большой размер логов при массовых операциях (`UPDATE` на миллион строк создаст гигабайтный лог), что увеличивает нагрузку на диск и сеть.

> **Примечание:** Начиная с MySQL 5.7.7, `ROW` является форматом по умолчанию, что подчеркивает приоритет надежности.

#### 3. `MIXED` (Mixed-Format Replication)

- **Принцип:** Гибридный режим. По умолчанию используется `STATEMENT`, но для "небезопасных" (недетерминированных) запросов MySQL автоматически переключается на `ROW`.
- **Плюсы:** Баланс между надежностью и размером логов.
- **Минусы:** Поведение не всегда предсказуемо и требует глубокого понимания, какой запрос будет считаться "безопасным".

## Практические сценарии

### Пошаговая настройка Master-Slave репликации

Теоретические основы репликации (синхронная, асинхронная, топологии) и CAP-теорема рассмотрены в основной заметке: **[Репликация баз данных](../Concepts/replication.md)**.

#### Шаг 1: Настройка Master-сервера

1. **Редактирование конфигурации (`my.cnf`)**

    В файле конфигурации (обычно `/etc/mysql/my.cnf` или `/etc/mysql/mysql.conf.d/mysqld.cnf`) в секции `[mysqld]` укажите:

    ```ini
    [mysqld]
    # Уникальный ID сервера в кластере (целое число > 0)
    server-id = 1 

    # Имя файла, активирующее ведение бинарного лога
    log_bin = /var/log/mysql/mysql-bin.log
    ```

    > После изменения конфигурации перезапустите сервис MySQL.

2. **Создание пользователя для репликации**

    Создайте на Master-сервере специального пользователя, от имени которого Slave будет подключаться.

    ```sql
    -- Для безопасности рекомендуется указать IP-адрес slave-сервера вместо '%'
    CREATE USER 'slave_user'@'%' IDENTIFIED BY '${REPLICATION_PASSWORD}';

    -- Выдача необходимых прав
    GRANT REPLICATION SLAVE ON *.* TO 'slave_user'@'%';

    FLUSH PRIVILEGES;
    ```

#### Шаг 2: Создание дампа и фиксация позиции на Master

Для инициализации реплики необходимо создать дамп текущих данных и зафиксировать позицию в бинарном логе на этот момент.

Используйте `mysqldump` с флагами, которые автоматически добавляют в дамп координаты для старта репликации:

```bash
# --single-transaction: создает консистентный дамп для InnoDB без блокировки таблиц.
# --master-data=2: добавляет в дамп закомментированную команду CHANGE MASTER TO.
# (Используйте --master-data=1, если не хотите, чтобы команда была закомментирована).
mysqldump -u root -p --all-databases --single-transaction --master-data=2 > master_dump.sql

# Для MyISAM требуется полная блокировка:
# mysqldump -u root -p --all-databases --lock-all-tables --master-data=2 > master_dump.sql
```

Флаг `--master-data=2` добавит в начало дампа строку с координатами для запуска репликации:

```sql
-- CHANGE MASTER TO MASTER_LOG_FILE='mysql-bin.000001', MASTER_LOG_POS=154;
```

#### Шаг 3: Настройка Slave-сервера

1. **Редактирование конфигурации (`my.cnf`)**

    На Slave-сервере также задайте уникальный `server-id`.

    ```ini
    [mysqld]
    # ID должен отличаться от ID master-сервера
    server-id = 2
    
    # (Опционально) Лог для отладки репликации
    relay-log = /var/log/mysql/mysql-relay-bin.log
    
    # (Опционально) Включает бинарный лог, если slave будет мастером для другого slave
    # (необходимо для каскадной репликации: Master -> Slave1 -> Slave2).
    # В MySQL 8+ опция log_slave_updates, отвечающая за это, включена по умолчанию.
    log_bin = /var/log/mysql/mysql-bin.log 
    ```

    > После изменения конфигурации перезапустите сервис MySQL.

#### Шаг 4: Восстановление данных и запуск репликации на Slave

1. **Загрузка дампа**

    Перенесите файл `master_dump.sql` на Slave-сервер и примените его:

    ```bash
    mysql -u root -p < master_dump.sql
    ```

2. **Подключение к Master и запуск**

    Выполните на Slave команду `CHANGE MASTER TO`, используя данные из дампа и дополнив их учетными данными.

    ```sql
    -- Раскомментируйте и дополните строку из файла master_dump.sql
    CHANGE MASTER TO
      MASTER_HOST='<ip_адрес_мастера>',
      MASTER_USER='slave_user',
      MASTER_PASSWORD='${REPLICATION_PASSWORD}',
      MASTER_LOG_FILE='mysql-bin.000001', -- из дампа
      MASTER_LOG_POS=154;                 -- из дампа

    START SLAVE;
    ```

3. **Проверка статуса**

    Проверьте статус репликации. Оба потока должны иметь статус `Yes`.

    ```sql
    SHOW SLAVE STATUS\G
    ```

    Ключевые поля:
    - `Slave_IO_Running: Yes` — I/O-поток успешно получает данные от Master.
    - `Slave_SQL_Running: Yes` — SQL-поток успешно применяет данные.
    - `Seconds_Behind_Master: 0` — Отставание от мастера отсутствует.

## Дополнительная информация

### 1. Управление и отладка

- **`SHOW SLAVE STATUS\G`**: Основная команда для диагностики на Slave. Показывает состояние потоков, ошибки, отставание (`Seconds_Behind_Master`).
- **`SHOW MASTER STATUS\G`**: Показывает текущую позицию в бинарном логе на Master-сервере.
- **`START SLAVE;` / `STOP SLAVE;`**: Запуск и остановка репликации на Slave.
- **Пропуск ошибочной транзакции**: Если репликация остановилась из-за ошибки (например, дубликат ключа), ее можно пропустить:

    ```sql
    STOP SLAVE;
    SET GLOBAL SQL_SLAVE_SKIP_COUNTER = 1;
    START SLAVE;
    ```

### 2. Особенности MySQL 8

- **Плагин аутентификации:** По умолчанию используется `caching_sha2_password` вместо `mysql_native_password`, что может вызвать проблемы совместимости со старыми клиентами. Варианты решения:
  1. **Создать пользователя со старым плагином:**

      ```sql
      CREATE USER 'slave_user'@'%' 
      IDENTIFIED WITH mysql_native_password BY '${REPLICATION_PASSWORD}';
      ```

  2. **Использовать безопасную передачу пароля по RSA:**
      В команде `CHANGE MASTER TO` на slave-сервере указать опцию запроса публичного ключа:

      ```sql
      CHANGE MASTER TO GET_MASTER_PUBLIC_KEY = 1;
      ```

  3. **(Менее безопасно) Вернуть старый плагин по умолчанию в `my.cnf` на мастере:**

      ```ini
      [mysqld]
      default-authentication-plugin=mysql_native_password
      ```

- **Цепочечная репликация:** Опция `log_slave_updates` (в старых версиях `log-slave-updates`) включена по умолчанию. Это значит, что slave записывает полученные от мастера изменения в свой бинарный лог, позволяя ему выступать мастером для других slave (M -> S1 -> S2). Раньше эту опцию нужно было включать явно.
