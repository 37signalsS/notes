# Бэкап MySQL снимками файловой системы

**Актуально для:** MySQL 8.0 / 8.4 на Linux (LVM, ZFS, Btrfs, XFS)

> **Статус:** снимки — **дополнение** к логическому или физическому бэкапу, а не его замена. Снимок на том же диске, что и исходные данные, не переживёт отказ диска.

## Определения

**Snapshot (снимок файловой системы)** — атомарная копия состояния блочного устройства или тома в момент времени, сделанная сервером за секунды при продолжающейся работе приложения. Механизм копирования на уровне блочного устройства (copy-on-write): до изменённых блоков на целевом носителе не пишется ничего.

**COW (copy-on-write)** — принцип, при котором запись в исходный том сначала перенаправляет изменённый блок в новую область, а оригинал сохраняется. Именно поэтому снимок мгновенен и почти не влияет на нагрузку — в отличие от `cp`.

**Crash-consistent snapshot** — снимок, согласованный на уровне отдельного тома, но не на уровне согласованности MySQL. InnoDB восстановит себя из собственного redo log при следующем старте, поэтому результат **пригоден к использованию**, если redo log цел.

**Application-consistent snapshot** — снимок, снятый в момент, когда приложение не пишет (остановленное приложение, read-only режим, файловая блокировка). Требует координации с приложением; кратковременная блокировка (`FLUSH TABLES WITH READ LOCK`) совместима с production-автоматизацией.

**QCOW2 / живой снимок VM** — снимок виртуальной машины на уровне гипервизора. Механизм тот же COW; отличие в масштабе и в том, что согласованность обеспечивается гостевой ОС.

## Основные концепции

### Почему снимок без координации всё равно работает

Ключевой факт, который снимает большинство вопросов: **файлы MySQL не обязаны быть согласованы в момент снятия снимка.**

При старте InnoDB выполняет crash recovery — читает свой redo log и применяет записи, не попавшие в файлы данных. Если снимок содержит согласованный набор файлов данных и соответствующий им redo log, то сервер восстановится до последней завершённой транзакции. Именно это делает снимок пригодным без остановки приложения.

Напротив, копирование файлов *по частям*, без снимка, даёт смешанный набор — часть страниц новая, часть старая. Такой набор не восстановится: redo log не сможет привести его к консистентному состоянию. Снимок атомарен, поэтому этой проблемы нет.

### Три требования к снимку MySQL

| Требование | Почему |
| :--- | :--- |
| **Снимок включает `datadir` целиком**, включая redo log и `ibdata1` | Частичный снимок (только `.ibd`) без соответствующего redo log не восстановится |
| **Все тома данных попадают в снимок** | Если `datadir` и binlog лежат на разных томах, снимки по очереди не атомарны — между ними успевают записаться данные. LVM не умеет атомарный снимок нескольких LV одной командой: либо один том под все файлы MySQL, либо FTWRL на время серии снимков (сценарий 4); ZFS снимает набор датасетов атомарно (`zfs snapshot -r`) |

Запись во время создания одного COW-снимка не вредит: снимок атомарен и отражает состояние тома на момент `lvcreate` / `zfs snapshot`. Атомарность — проблема только между несколькими томами.

### Snapshot и бинлог: объём данных для PITR

Снимок даёт точку входа, но не даёт возможности откатиться на произвольный момент. Для PITR снимок должен быть **сопоставлен** с архивом binlog: сохранять позицию в binlog (или `--source-data` у mysqldump) вместе со снимком. Оператор зависит от версии: `SHOW BINARY LOG STATUS` в MySQL 8.2+ и 8.4, `SHOW MASTER STATUS` в MySQL 5.7/8.0/8.1 (привилегия `REPLICATION CLIENT`).

```sql
SELECT @@server_uuid, @@hostname, NOW();
SHOW BINARY LOG STATUS;
-- MySQL 8.0: SHOW MASTER STATUS;
-- → File: binlog.000042   Position: 1540   Executed_Gtid_Set: ...
```

Позиция, записанная **после** создания снимка, не гарантирует точного соответствия: транзакции, совершённые в окне между снимком и записью позиции, в снимок не попали, но их события в binlog уже пройдены — при восстановлении это окно теряется. Для точного соответствия позиции моменту снимка — сценарий 4 (FTWRL) или **[XtraBackup](./xtrabackup.md)**.

Эта тройка идентифицирует снимок и даёт отправную точку для последующего применения binlog — процедура описана в **[Point-in-Time Recovery](./pitr.md)**.

### Три уровня консистентности: сравнение

| Метод | Консистентность | Влияние на нагрузку | Требования |
| :--- | :--- | :--- | :--- |
| Снимок без координации | Crash-consistent (InnoDB восстановится сам) | Минимальное | Снимок всех томов данных |
| Снимок + `FLUSH TABLES WITH READ LOCK` | Application-consistent | Кратковременная блокировка записи | Требуется привилегия `RELOAD` |
| Снимок + остановленное приложение | Application-consistent | Простой приложения | Окно обслуживания |

Для большинства задач достаточно первого уровня: InnoDB откатывает незакоммиченные транзакции при crash recovery. Второй уровень нужен, когда критична точная позиция binlog (PITR без потерянного окна) или в `datadir` есть таблицы нетранзакционных движков (MyISAM, MEMORY) — их изменения при восстановлении не откатываются.

## Практические сценарии

### Пререквизиты

- **Утилиты:** `lvm2` (LVM), `zfsutils-linux` (ZFS; пакет `zfs` в RHEL), `btrfs-progs` (Btrfs) — в зависимости от механизма.
- **Привилегии:** `root`/`sudo` для команд создания снимков; `REPLICATION CLIENT` для `SHOW BINARY LOG STATUS` / `SHOW MASTER STATUS`; `RELOAD` для `FLUSH TABLES WITH READ LOCK`.
- **Ресурсы:** для LVM — свободное место в VG под COW-область; для ZFS — место на приёмном пуле; отдельный носитель для копии снимка.

### Сценарий 1: LVM-снимок тома MySQL

Общая механика LVM (включение COW, `lvs`, `vgcfgbackup`) разобрана в **[LVM-снапшоты](../../../Linux/FileSystems/LVM/snapshots.md)**. Здесь — специфика MySQL.

```bash
# 1. Определяем LV с данными
lvs --options lv_name,lv_size,vg_name,lv_path | grep mysql
# → mysql-data  50.00g  vg0  /dev/vg0/mysql-data
```

```bash
# 2. Свободное место в VG должно превышать размер снимка (--size):
#    COW-область растёт вместе с записью в исходном томе
vgs vg0 --options vg_name,vg_size,vg_free
# → vg0  100.00g  50.00g
```

```bash
# 3. Снимок: 50 ГБ
lvcreate --snapshot --size 50G \
  --name mysql-data-snap-2026-10-03 \
  /dev/vg0/mysql-data
# →   Logical volume mysql-data-snap-2026-10-03 created.
```

```bash
# 4. Фиксируем метаданные для возможного PITR — ДО любых операций с приложением
#    MySQL 8.0: SHOW MASTER STATUS;  (привилегия REPLICATION CLIENT)
#    О позиции, снятой после создания снимка, — оговорка выше (потерянное окно)
mysql -N -B -e "SELECT @@server_uuid, NOW();" > /var/log/mysql/snap_2026-10-03.meta
mysql -N -B -e "SHOW BINARY LOG STATUS;" >> /var/log/mysql/snap_2026-10-03.meta
cat /var/log/mysql/snap_2026-10-03.meta
# → e71a47dc-61f8-11e9-a3cb-080027154b4d  2026-10-03 04:30:00
# → binlog.000042  1540  8e71a475-...
```

```bash
# 5. Монтируем снимок read-only
mkdir -p /mnt/mysql-snap
mount -o ro /dev/vg0/mysql-data-snap-2026-10-03 /mnt/mysql-snap
ls /mnt/mysql-snap
# → binlog.000042  ibdata1  #innodb_redo  mysql  performance_schema  sys
#   → Наличие ibdata1 и redo log обязательна: без них восстановление невозможно.
#   redo log: каталог #innodb_redo/ в MySQL 8.0.30+ / 8.4; файлы ib_logfile0, ib_logfile1 в 8.0.0–8.0.29
```

```bash
# 6. Только чтение: страховка от случайной записи в снимок
mount -o remount,ro /mnt/mysql-snap
# → (без вывода при успехе)

# 7. Копируем снимок на отдельный носитель — сам снимок не бэкап
rsync -aHAX --numeric-ids --delete \
  /mnt/mysql-snap/ /mnt/backup-nas/mysql/2026-10-03/
# → (без вывода при успехе)

# 8. Размонтируем и удаляем снимок — он занимает место в VG
umount /mnt/mysql-snap
lvremove /dev/vg0/mysql-data-snap-2026-10-03
# →   Logical volume "mysql-data-snap-2026-10-03" successfully removed.
```

> **Важно:** после шага 3 все новые блоки в исходном LV пишутся в COW-область. Место в VG расходуется пропорционально **изменениям** между снимком и удалением, а не размеру снимка. Долгий снимок на базе с интенсивной записью заполнит VG и уронит саму БД — это реальный инцидент, а не теоретический риск. Если `vg_free` мал, вместо снимка данных используйте XtraBackup.

### Сценарий 2: ZFS-снимок

```bash
# Пул для данных MySQL (предполагаем, что datadir размещён в zfs-пуле)
zfs list | grep mysql
# → tank/mysql-data  12.4G  37.6G  12.4G  /var/lib/mysql
#   колонки: NAME USED AVAIL REFER MOUNTPOINT
```

```bash
# Снимок — атомарный, рекурсивный по датасетам
zfs snapshot tank/mysql-data@2026-10-03
# → (без вывода при успехе)

zfs list -t snapshot | grep 2026-10-03
# → tank/mysql-data@2026-10-03   0B   -   12.4G   -
#   USED — место, занятое снимком с момента создания; REFER — данные на момент снимка
```

```bash
# Метаданные для PITR
mysql -N -B -e "SHOW BINARY LOG STATUS;" | tee /var/log/mysql/snap.meta
# → binlog.000042  1540  8e71a475-...
```

```bash
# Первичная копия — полный поток (инкрементальный -i требует,
# чтобы базовый снимок уже существовал на приёмной стороне)
zfs send tank/mysql-data@2026-10-03 | zfs recv tank/backup/mysql-data
# → (может занять значительное время; поток проверен контрольными суммами)

# Последующие копии — только изменения между снимками
zfs send -i tank/mysql-data@2026-10-03 tank/mysql-data@2026-10-04 \
  | zfs recv tank/backup/mysql-data
```

```bash
# Восстановление
zfs rollback tank/mysql-data@2026-10-03
# → если есть снимки новее целевого, откат откажется выполнять:
#   "more recent snapshots exist" — удалите их или добавьте -R

# Очистка: снимок-источник после копии на backup-пул
zfs destroy tank/mysql-data@2026-10-03
```

Преимущество ZFS — `zfs send`/`recv` передаёт данные по конвейеру с проверкой контрольной суммы, то есть копирование проверяется по ходу дела, а не постфактум.

### Сценарий 3: Btrfs-снимок подтома

```bash
# Данные MySQL размещены в отдельном подтоме
btrfs subvolume list / | grep mysql
# → ID 257 gen 1204 top level 5 path var/lib/mysql

# Read-only снимок подтома — атомарен при продолжающейся записи
sudo btrfs subvolume snapshot -r /var/lib/mysql /mnt/btrfs/snap-mysql-2026-10-03
# → Create a readonly snapshot '/mnt/btrfs/snap-mysql-2026-10-03'

# Метаданные для PITR — как в сценарии 1, шаг 4
# MySQL 8.0: SHOW MASTER STATUS;
mysql -N -B -e "SHOW BINARY LOG STATUS;" > /var/log/mysql/snap_2026-10-03.meta
```

```bash
# Копируем на отдельный носитель: send работает только с read-only снимком
sudo btrfs send /mnt/btrfs/snap-mysql-2026-10-03 | gzip \
  > /mnt/backup-nas/mysql-2026-10-03.snap.gz

# Очистка: снимок не нужен после копии
sudo btrfs subvolume delete /mnt/btrfs/snap-mysql-2026-10-03
# → Delete subvolume '/mnt/btrfs/snap-mysql-2026-10-03'
```

### Сценарий 4: Снимок с application-consistent гарантией (LVM)

Когда crash-consistent недостаточно — нужна точная позиция binlog для PITR и согласованность нетранзакционных таблиц (MyISAM, MEMORY):

```sql
-- Блокируем запись во всём инстансе (привилегия RELOAD)
FLUSH TABLES WITH READ LOCK;
-- → Блокировка удерживается этой сессией, пока соединение живо

-- Позиция binlog, снятая под блокировкой, точно соответствует моменту снимка
SHOW BINARY LOG STATUS;
-- MySQL 8.0: SHOW MASTER STATUS;
-- → File: binlog.000042   Position: 1540   Executed_Gtid_Set: ...
```

```bash
# Снимок делается, пока сессия с блокировкой жива.
# Держите терминал открытым до подтверждения завершения lvcreate.
lvcreate --snapshot --size 50G --name mysql-data-snap-consistent /dev/vg0/mysql-data
# →   Logical volume mysql-data-snap-consistent created.
```

```sql
UNLOCK TABLES;
-- → (разблокировка выполнена)
```

> **Критично:** `FLUSH TABLES WITH READ LOCK` держится на соединении. Если выполнить `lvcreate` из того же терминала, где открыт `mysql`, блокировка снимется при закрытии соединения до завершения снимка. Используйте **два** терминала, либо `mysql -e "FLUSH TABLES WITH READ LOCK; SELECT SLEEP(120);"` в фоне.

Сравнение механизмов блокировки приведено в **[Механизмы блокировки при бэкапе](./overview.md#механизмы-блокировки-при-бэкапе)**.

### Сценарий 5: Восстановление из снимка

```bash
# 1. Остановленный сервер
systemctl stop mysql
# → (без вывода при успехе)

# 2. Восстанавливаем LV из снимка (в команде — только снимок;
#    исходный том определяется автоматически)
lvconvert --merge /dev/vg0/mysql-data-snap-2026-10-03
# → слияние выполняется, только когда исходный LV не открыт
#   (mysql остановлен на шаге 1; иначе — ошибка "Can't merge over active LV")

# 3. Проверяем наличие критичных файлов ДО старта
ls -l /var/lib/mysql/ibdata1 && ls -ld /var/lib/mysql/#innodb_redo
# → -rw-r----- 1 mysql mysql 9437184 Oct  3 04:30 /var/lib/mysql/ibdata1
# → drwxr-x--- 2 mysql mysql    4096 Oct  3 04:30 /var/lib/mysql/#innodb_redo
# MySQL 8.0.0–8.0.29: вместо каталога #innodb_redo — файлы ib_logfile0, ib_logfile1.
# Отсутствие redo log означает, что снимок неполон.
```

```bash
# 4. Запуск — InnoDB выполнит crash recovery
systemctl start mysql
sleep 30
systemctl is-active mysql
# → active
```

```bash
# 5. Проверяем результат recovery
journalctl -u mysql -n 40 --no-pager | grep -i "innodb\|recovery"
# → записи InnoDB о crash recovery при старте (точный текст зависит от версии;
#   наличие записей recovery и успешный старт — признак корректного восстановления)
```

```sql
-- 6. Валидация данных
SELECT COUNT(*) FROM users;
-- → 152834
CHECK TABLE users, orders, sessions EXTENDED;
-- → ... status  OK

-- 7. Позиция binlog для продолжения PITR
SHOW BINARY LOG STATUS;
-- → binlog.000042  1540  (совпадает с метаданными снимка)
```

> **Замечание:** полноценное восстановление на резервный инстанс предпочтительнее проверки на продуктиве — проверочная среда исключает риск для данных.

### Сценарий 6: Ограничения и когда снимок — неправильный выбор

| Ограничение | Следствие | Что использовать вместо |
| :--- | :--- | :--- |
| Снимок локальный, на том же носителе | Отказ диска уничтожает и данные, и снимок | **[XtraBackup](./xtrabackup.md)** с копированием на удалённый носитель |
| Снимок не даёт PITR без архива binlog | Можно восстановиться только на момент снимка | Архив binlog + **[PITR](./pitr.md)** |
| Весь том данных копируется целиком | Объём в разы больше логического дампа при малой БД | **[mysqldump](./mysqldump.md)** |
| COW расходует место в VG при записи | Долгий снимок на загруженной БД может заполнить VG | XtraBackup, `--stream=tar` |
| Нет выборочного восстановления данных | Восстанавливается всё | Логический бэкап |
| Производительность после сброса снимка падает на время | COW-область сливается, потом удаляется | Плановое обслуживание |
| Не снимает согласованность с внешними системами | Файл на NFS и данные в БД могут разойтись | Координация на уровне приложения |

## Бест-практики

1. **Снимок дополняет бэкап, а не заменяет его.** Физический бэкап на удалённый носитель — обязательная основа; снимок сокращает RTO.
2. **Сохраняйте метаданные снимка рядом со снимком:** `server_uuid`, `SHOW BINARY LOG STATUS`, время. Без них PITR невозможен.
3. **Удаляйте снимок сразу после копирования.** COW-область растёт вместе с записью и может заполнить VG.
4. **Копируйте снимок на отдельный носитель.** Снимок на том же диске — не бэкап.
5. **Монтируйте снимок только read-only.** Защита от случайной записи в эталонные данные.
6. **Для PITR настраивайте архивирование binlog заранее** — см. **[Управление бинарным логом](../replication/binlog_management.md)**.
7. **Регулярно проверяйте снимок пробным восстановлением** — неразвёрнутый снимок через год может оказаться непригодным.
8. **Не снимайте снимок в момент пиковой нагрузки** без запаса свободного места: расход COW пропорционален интенсивности записи.
9. **Для больших баз предпочитайте XtraBackup с `--stream`** — он не требует снимка, не расходует место в VG/COW и копирует данные на удалённый носитель без простоя.
