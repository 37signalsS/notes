## Предпосылки и требования

### Версии MySQL и инструментов

| Инструмент | Минимальная версия MySQL | Актуальная версия инструмента | Примечания |
| :--- | :--- | :--- | :--- |
| `mysqldump` | 5.7+ | Входит в дистрибутив MySQL | Рекомендуется для БД < 100 ГБ |
| `mysqlpump` | 5.7+ (deprecated в 8.0.34) | **Удалён в MySQL 8.4** | Используйте MySQL Shell Dump вместо него |
| `mysqlsh` (MySQL Shell) | 5.7+ (для выгрузки), 5.7+ (для загрузки) | 9.7.x (актуальная) | Предпочтительный метод для MySQL 8.0+ |
| `Percona XtraBackup` | 5.7 (ветка 2.4), 8.0 (ветка 8.0) | 8.0.35-36 (июнь 2026) | Финальный релиз ветки 8.0 |
| `mysqlbinlog` | 5.7+ | Входит в дистрибутив MySQL | Обязателен для PITR |
| `MySQL Clone Plugin` | 8.0.17+ | Входит в сервер | Для физического клонирования (Seeding реплик) |

> **Важно:** MySQL 8.0 находится в режиме «Bug fixes only» и завершает поддержку (EOL) в апреле 2026. Рекомендуется переход на MySQL 8.4 LTS (поддержка до 2032). Для MySQL 8.4 и выше `mysqlpump` удалён — используйте MySQL Shell Dump.

### Включённый бинарный лог (обязательно для PITR)

Point-in-Time Recovery невозможен без включённого бинарного лога. Убедитесь, что в конфигурации MySQL задан параметр:

```ini
[mysqld]
server-id               = 1
log_bin                 = mysql-bin
binlog_format           = ROW          # Предпочтительный формат для минимального размера лога
binlog_expire_logs_seconds = 604800    # 7 дней — минимальный срок для восстановления
max_binlog_size         = 100M
sync_binlog             = 1            # Фиксация после каждой транзакции (максимальная надёжность)
gtid_mode               = ON           # Рекомендуется для MySQL 5.7+/8.0+
enforce_gtid_consistency = ON
```

> **Совет по `binlog_expire_logs_seconds`:** Значение зависит от RPO и размера логов. Для базы с высокой нагрузкой логи могут занимать несколько гигабайтов в день. Установите значение не менее `(RPO в секундах * размер лога за секунду)`, но рекомендуется минимум 3–7 дней для покрытия типичных сценариев восстановления.

Проверка текущих настроек:

```sql
SHOW VARIABLES LIKE 'log_bin';
-- → log_bin: ON

SHOW VARIABLES LIKE 'binlog_format';
-- → binlog_format: ROW

SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
-- → binlog_expire_logs_seconds: 604800

SHOW BINARY LOGS;
-- →mysql-bin.000001   154
-- →mysql-bin.000002   154
```

### Пользователь бэкапа (принцип наименьших привилегий)

Создайте отдельного пользователя для операций бэкапа. Минимальные права зависят от используемого инструмента:

```sql
-- Для mysqldump / mysqlpump / mysqlsh dump
CREATE USER 'backup_user'@'localhost' IDENTIFIED BY 'StrongPassword!2024';
GRANT SELECT, RELOAD, SHOW DATABASES, REPLICATION CLIENT,
      LOCK TABLES, SHOW VIEW, EVENT, TRIGGER
ON *.* TO 'backup_user'@'localhost';

-- Для XtraBackup (добавляется PROCESS)
GRANT PROCESS, RELOAD, LOCK TABLES, REPLICATION CLIENT, SELECT
ON *.* TO 'backup_user'@'localhost';

-- Для mysqlbinlog (чтение бинарных логов с реплики)
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'backup_user'@'%';
```

### Необходимые утилиты

```bash
# Проверка наличия инструментов
which mysqldump mysql mysqlsh xtrabackup mysqlbinlog
# → Все утилиты должны быть доступны в PATH

# Для XtraBackup (установка на Debian/Ubuntu)
sudo apt-get install percona-xtrabackup-80

# Для MySQL Shell (установка через MySQL APT/YUM repository или статический бинарник)
# См. https://dev.mysql.com/doc/mysql-shell/8.4/en/mysql-shell-install.html
```

## Определения

**`mysqldump`** — классическая утилита для создания логических бэкапов. Генерирует набор SQL-инструкций для воссоздания структуры и данных таблиц. Однопоточная, что делает её медленной на больших объемах данных (> 50–100 ГБ). Поддерживает режим `--single-transaction` для консистентного снимка InnoDB без блокировок.

**`mysqlpump`** — утилита для параллельного логического бэкапа, представленная в MySQL 5.7. Поддерживала многопоточность на уровне баз данных и таблиц. **Депрекейтнута в MySQL 8.0.34 и удалена в MySQL 8.4.** Для MySQL 8.0+ рекомендуется использовать MySQL Shell Dump. Основное ограничение: `--single-transaction` с параллельными потоками не гарантирует консистентность на уровне инстанса — каждый поток открывает транзакцию в разные моменты времени.

**`mysqlsh` (MySQL Shell) Dump & Load** — современная замена `mysqldump`. Поддерживает многопоточность, сжатие Zstandard и прямую выгрузку в облачные хранилища (S3/OCI). Является предпочтительным методом логического бэкапа для MySQL 8.0+. Функции `util.dumpInstance()`, `util.dumpSchemas()`, `util.dumpTables()` разделяют данные на чанки и загружают/выгружают в десятки потоков. Подробнее — в **[MySQL Shell Dump & Load](./mysql_shell_dump.md)**.

**`Percona XtraBackup`** — промышленный стандарт для создания «горячих» физических бэкапов. Позволяет копировать файлы данных InnoDB без остановки сервера и блокировок записи (для InnoDB). Полностью совместим с Percona Server и MySQL Community. Версия 8.0.35-36 (июнь 2026) — финальный релиз ветки 8.0. Подробнее — в **[Percona XtraBackup](./xtrabackup.md)**.

**`mysqlbinlog`** — утилита для чтения и обработки бинарных логов MySQL. Используется для анализа операций (аудит), а также как ключевой компонент PITR — применяет транзакции из бинарных логов к восстановленной БД. Поддерживает фильтрацию по времени, GTID, серверу и базе данных. Подробнее — в **[Point-in-Time Recovery](./pitr.md)**.

**`MySQL Clone Plugin`** — встроенный механизм MySQL 8.0.17+ для физического клонирования данных с одного сервера на другой (Seeding). Используется для быстрой инициализации реплик. Начиная с MySQL 8.0.35+, клонирование между патч-версиями в пределах одного LTS-series разрешено.

**Point-in-Time Recovery (PITR)** — восстановление состояния БД на конкретный момент времени с помощью полного физического или логического бэкапа и последующего применения бинарных логов через `mysqlbinlog`. Подробный сценарий — в **[PITR](./pitr.md)**.

## Основные концепции

### Сравнение методов бэкапа

| Характеристика | Physical (XtraBackup) | Logical (MySQL Shell) | Logical (mysqldump) |
| :--- | :--- | :--- | :--- |
| **Скорость создания** | Очень высокая (I/O) | Высокая (Parallel) | Низкая (Single-thread) |
| **Скорость восстановления** | Максимальная (Copy + Redo) | Средняя (Parallel INSERT) | Очень низкая (SQL Parser) |
| **Гранулярность** | Сложная (уровень таблиц) | Высокая (таблица/схема) | Высокая |
| **Блокировки** | Почти отсутствуют | Минимальные (`--consistent`) | Могут быть значительными |
| **Облако (S3)** | Через xbstream/pipe | Нативная поддержка | Через pipe |
| **Консистентность** | Crash-consistent + Redo Log | Application-consistent (`LOCK TABLES FOR BACKUP`) | Application-consistent (`--single-transaction` или `LOCK`) |
| **PITR** | Да (с бинарными логами) | Да (с бинарными логами) | Да (с бинарными логами) |

### Преимущества MySQL Shell Dump

В отличие от `mysqldump`, MySQL Shell (`util.dumpInstance`, `util.dumpSchemas`):
- Разделяет данные на чанки (chunks), позволяя выполнять импорт и экспорт в десятки потоков.
- Автоматически создает метаданные для быстрого восстановления.
- Поддерживает инкрементальный импорт и пропуск существующих данных.
- Поддерживает сжатие Zstandard (уровень настраивается) и LZ4.
- Нативная интеграция с облачными хранилищами (OCI Object Storage, S3 через совместимые API).
- Управление засечками (chunk boundaries) для гранулярного восстановления.

### Уровни консистентности бэкапов MySQL

1. **Неконсистентный (Dirty):** Простое копирование файлов данных (`/var/lib/mysql/`) без взаимодействия с сервером. Гарантированно приводит к повреждению данных — InnoDB redo/undo логи не зафиксированы, могли произойти partial writes.
2. **Crash-consistent (Физический):** Копия, эквивалентная состоянию после аварийного выключения питания. XtraBackup достигает этого через фоновое копирование страниц + Apply Log (`--prepare`). InnoDB Crash Recovery восстанавливает целостность при восстановлении.
3. **Application-consistent (Логический):** Перед выгрузкой сервер фиксирует состояние через `START TRANSACTION WITH CONSISTENT SNAPSHOT` (`--single-transaction`) или `LOCK TABLES FOR BACKUP` (MySQL Shell). Гарантирует, что все таблицы находятся в согласованном состоянии на момент начала выгрузки.

### Проблема консистентности при инкрементальном бэкапе XtraBackup

XtraBackup копирует страницы InnoDB непрерывно. Если между началом копирования данных и фиксацией redo log изменится одновременно и данные, и redo-запись для них, бэкап может оказаться неполным. XtraBackup решает это, записывая log sequence number (LSN) начальной страницы и проверяя его при `--prepare`. Если страница была изменена после начала копирования, `--prepare` обнаружит несоответствие LSN и завершится ошибкой.

### Клонирование через MySQL Clone Plugin

```bash
# На источнике (Primary): установка плагина
INSTALL PLUGIN clone SONAME 'mysql_clone.so';

# На источнике: создание пользователя для клонирования
CREATE USER 'clone_user'@'%' IDENTIFIED BY 'ClonePassword!2024';
GRANT CLONE_ADMIN ON *.* TO 'clone_user'@'%';

# На реплике (Replica): выполнение клонирования с источника
SET GLOBAL clone_valid_donor_list = 'primary_host:3306';
CLONE INSTANCE FROM 'clone_user'@'primary_host'
  IDENTIFIED BY 'ClonePassword!2024';
# → Клонирование выполнено. Сервер автоматически перезапустится.
```

> **Важно:** После клонирования сервер-получатель автоматически останавливается. Перезапустите его, и он будет готов к работе как полная копия источника. Версии MySQL должны совпадать по major.minor (с MySQL 8.0.35+ допускается различие в patch-версиях).

## Диагностика и устранение неисправностей

### Ошибки Percona XtraBackup

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`Error: redo log size mismatch`** | Подготовка бэкапа версией утилиты, несовместимой с версией сервера | Версии `xtrabackup` и `mysqld` должны совпадать. XtraBackup 8.0.35-xx для MySQL 8.0.x |
| **`Log sequence number (LSN) mismatch`** | Базовый бэкап для инкремента повреждён, перемещён или incomplete | Удалите инкремент и сделайте новый базовый бэкап |
| **`xtrabackup: Error: last checkpoint LSN is greater`** | Повреждение redo-лога | Проверьте целостность диска (`fsck`), сделайте новый полный бэкап |
| **`Found tables with row versions due to INSTANT ADD/DROP columns`** | Использование `INSTANT ADD/DROP COLUMN` в MySQL 8.0.12–8.0.28 | Обновите MySQL до 8.0.29+ или используйте XtraBackup 8.0.35-xx (имеет workaround) |
| **`xtrabackup: error: code=1` при `--copy-back`** | Неверные права на каталог данных или нехватка места | Проверьте `chown -R mysql:mysql /var/lib/mysql` и `df -h` |

### Ошибки MySQL Shell Dump/Load

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`Access denied for user`** | Недостаточно прав | Требуются: `SELECT, RELOAD, SHOW DATABASES, REPLICATION CLIENT, LOCK TABLES, EVENT, TRIGGER` |
| **`Consistency error`** | Зависшие транзакции блокируют `LOCK TABLES FOR BACKUP` | Проверьте `SHOW PROCESSLIST;` и завершите зависшие транзакции перед запуском дампа |
| **`Table already exists` при загрузке** | Таблица уже существует в целевой БД | Используйте `--ignoreExistingObjects: true` при загрузке |
| **`Unsupported feature in dump metadata`** | Дамп создан более новой версией MySQL Shell, чем та, что используется для загрузки | Обновите MySQL Shell на целевом сервере до версии не ниже, чем на источнике |

### Ошибки mysqldump

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`Lock wait timeout exceeded`** | Конфликт с активными транзакциями при `--lock-all-tables` | Используйте `--single-transaction` для InnoDB, или запускайте в часы минимальной нагрузки |
| **`Got error 2006: MySQL server has gone away`** | Слишком большой дамп превышает `max_allowed_packet` | Увеличьте `max_allowed_packet` на сервере и в команде: `--max_allowed_packet=1G` |
| **`Unknown table 'INFORMATION_SCHEMA.FILES'`** | Дамп создаётся со старой версией клиента | Обновите клиент `mysql` до версии сервера |

### Общие ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`No space left on device`** | Нехватка места для бэкапа | Используйте стриминг (`--stream=xbstream`) напрямую в удалённое хранилище, или сжатие (`--compress`) |
| **`mysqlbinlog: [ERROR] unknown variable`** | Конфликт опций конфигурации | Добавьте `--no-defaults` к команде `mysqlbinlog` |
| **Бэкап занимает больше места, чем исходные данные** | Не используется сжатие | Добавьте `--compress` (XtraBackup) или `compression: 'zstd'` (MySQL Shell) |
| **Восстановление занимает Hours** | Логический дамп SQL-based, однопоточное восстановление | Используйте MySQL Shell `util.loadDump()` с многопоточным импортом (`threads: 16`) |

## Бест-практики и стратегии

### Стратегии ротации и хранения

| Тип бэкапа | Частота | Срок хранения | Назначение |
| :--- | :--- | :--- | :--- |
| Полный физический (XtraBackup) | Ежедневно | 7–14 дней | Восстановление после сбоя диска/сервера |
| Инкрементальный (XtraBackup) | Ежедневно между полными | 3–7 дней | Минимальный RPO, быстрое восстановление |
| Логический дамп (MySQL Shell) | Ежедневно | 30 дней | Миграция между версиями, восстановление отдельных таблиц |
| Бинарные логи (mysqlbinlog) | Непрерывно (архивация) | 7–30 дней | PITR, аудит операций |

### Рекомендации по бэкапам

1. **Автоматизируйте:** Никаких ручных запусков. Используйте Cron или оркестраторы (Nomad, Kubernetes CronJobs). См. **[Автоматизация и верификация](./automation.md)**.
2. **Бэкапируйте конфиги MySQL:** Файл `my.cnf`, TLS-сертификаты, ключи шифрования (keyring). База без конфигурации может не запуститься.
3. **Разделение прав:** Пользователь бэкапа НЕ должен иметь `SUPER` или `ALL PRIVILEGES`. Используйте最小 привилегий из раздела «Предпосылки».
4. **Верификация восстановления:** Минимум раз в квартал проводите полное восстановление в изолированную среду и проверяйте целостность данных. См. **[Автоматизация и верификация](./automation.md#скрипт-верификации-бэкапа-smoke-test)**.
5. **Мониторинг:** Настраивайте алерты не на «ошибку бэкапа», а на «отсутствие успешного бэкапа за N часов». Используйте метрики `backup_last_success_timestamp` в Prometheus Pushgateway (см. **[Pushgateway](../../../Prometheus/pushgateway.md)**).
6. **Хранение offsite:** Копия бэкапа должна находиться на удалённой площадке (S3, другого ДЦ). Следуйте правилу 3-2-1-1-0 (см. **[Стратегии резервного копирования](../../Concepts/backups.md)**).
7. **Иммутабельность:** Для критичных данных храните бэкапы в иммутабельном хранилище (S3 Object Lock) для защиты от Ransomware (см. **[Безопасность бэкапов](../../Concepts/backup_security.md)**).

### Выбор инструмента по сценарию

| Сценарий | Рекомендуемый инструмент | Обоснование |
| :--- | :--- | :--- |
| Production backup (RTO < 1 ч) | [XtraBackup](./xtrabackup.md) + архивация binlog | Физическое копирование — максимальная скорость восстановления |
| Миграция между версиями MySQL | [MySQL Shell Dump/Load](./mysql_shell_dump.md) | Логический дамп гарантирует совместимость DDL между версиями |
| Восстановление отдельной таблицы | mysqldump / [MySQL Shell dumpTables](./mysql_shell_dump.md) | Гранулярность на уровне таблицы |
| Быстрое развёртывание реплики | MySQL Clone Plugin | Физическое клонирование за минуты, не требует остановки источника |
| PITR (откат на конкретную секунду) | Любой бэкап + [mysqlbinlog (PITR)](./pitr.md) | Бинарный лог — единственный способ отката на произвольный момент |
| Облачные среды (S3, OCI) | [MySQL Shell Dump/Load](./mysql_shell_dump.md) | Нативная интеграция с облачными хранилищами |
