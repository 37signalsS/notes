## Предварительные требования

### Версии MySQL и инструментов

| Компонент | Минимальная версия MySQL | Актуальная версия | Примечания |
| :--- | :--- | :--- | :--- |
| `mysqldump` | 5.7+ | Входит в дистрибутив | Для БД < 100 ГБ, одиночные таблицы |
| `mysqlpump` | 5.7+ | **Удалён в MySQL 8.4** | Депрекейтнут в 8.0.34; используйте MySQL Shell Dump |
| `mysqlsh` (MySQL Shell) | 5.7+ | 9.7.x | Предпочтительный логический метод для 8.0+ |
| `Percona XtraBackup` | 5.7 (ветка 2.4), 8.0 (ветка 8.0) | 8.0.35-36 (июнь 2026) | Финальный релиз ветки 8.0 |
| `mysqlbinlog` | 5.7+ | Входит в дистрибутив | Обязателен для PITR |
| `MySQL Clone Plugin` | 8.0.17+ | Входит в сервер | Физическое клонирование для seeding реплик |
| `mysqlbackup` (MySQL Enterprise Backup) | 8.0.17+ | MEB 8.0 | Проприетарный, только MySQL Enterprise Edition |
| `Redo Log Archiving` | 8.0.17+ | Встроено в сервер | Защита от потери redo при копировании, см. **[InnoDB Redo Log Archiving](./redo_log_archiving.md)** |
| `LVM` / `ZFS` / `Btrfs` | Зависит от ОС | — | Снимки файловой системы, см. **[Бэкап снимками ФС](./snapshot_backup.md)** |

> **Важно:** MySQL 8.0 завершает поддержку (EOL) в апреле 2026. Для новых систем используйте MySQL 8.4 LTS. Для MySQL 8.4 и выше `mysqlpump` удалён — используйте MySQL Shell Dump.

### Выбор инструмента бэкапа

| Инструмент | Тип | Лицензия | Когда выбирать | Ограничения |
| :--- | :--- | :--- | :--- | :--- |
| `mysqldump` | Логический | Входит в дистрибутив | БД < 100 ГБ, перенос между версиями и ОС, частичный дамп, полный контроль над SQL | Медленное восстановление, только InnoDB для консистентности |
| `mysqlsh` Dump & Load | Логический | Входит в дистрибутив | MySQL 8.0.21+, большие базы, нужен многопоточный дамп | Не переносит между мажорными версиями «как есть» |
| `XtraBackup` | Физический | GPL | Production, критичный RTO, базы от сотен ГБ | Не переносится между мажорными версиями; ветка 8.0 EOL в июне 2026 |
| `mysqlbackup` (MEB) | Физический | **Enterprise** | Подписка MySQL Enterprise, нужен проверенный вендорский SLA | Проприетарный, недоступен в community; ветка 8.0 привязана к MySQL 8.0 |
| `Percona XtraCluster` | Физический | Enterprise | Управляемый кластер с автоматическим failover | Enterprise-лицензия, заменяет ручную сборку из XtraBackup + Galera |
| `pt-backup` | Логический | GPL (Percona Toolkit) | Аналог `mysqldump` из Percona Toolkit | Ограниченный набор возможностей; проверяйте поддержку вашей версии |
| Снимок ФС | Физический | Зависит от ОС | Быстрое локальное копирование, RTO минуты | **Не бэкап без копирования на другой носитель**; не даёт PITR без binlog |
| MySQL Clone Plugin | Физический | Входит в сервер | Seeding реплик по локальному каналу | Только между серверами MySQL, не замена бэкапу |

> **Ограничения проприетарных инструментов:** `mysqlbackup` (MySQL Enterprise Backup) недоступен в community-версии и требует действующей Enterprise-лицензии. `pt-backup` распространяется свободно, но позиционируется как лёгкая замена `mysqldump`, а не как инструмент физического бэкапа. Перед выбором проверяйте совместимость с вашей версией MySQL — расхождение версий у этих инструментов приводит к ошибкам формата.

**Про `pt-backup`.** Утилита существует в Percona Toolkit и применяется для логических дампов. Функционально она ближе к `mysqldump`, чем к XtraBackup: не поддерживает инкрементальные копии, PITR и физическое восстановление страниц. Полный перечень её флагов следует сверять с документацией Percona Toolkit для установленной версии — набор опций между релизами менялся. Если задача — логический дамп в production, `mysqldump` или MySQL Shell покрывают её предсказуемее.

### Включённый бинарный лог (обязательно для PITR)

PITR невозможен без включённого binlog. Минимальная конфигурация:

```ini
[mysqld]
server-id               = 1
log_bin                 = mysql-bin
binlog_format           = ROW
binlog_expire_logs_seconds = 604800
max_binlog_size         = 100M
sync_binlog             = 1
gtid_mode               = ON
enforce_gtid_consistency = ON
```

Проверка:
```sql
SHOW VARIABLES LIKE 'log_bin';
-- → log_bin: ON

SHOW BINARY LOGS;
-- → mysql-bin.000001   154
```

> **Совет по `binlog_expire_logs_seconds`:** Устанавливайте значение с запасом под RPO. Для продакшена рекомендуем минимум 7 дней (604800 сек). При высокой нагрузке логи могут занимать несколько гигабайтов в день.

### Пользователь бэкапа (принцип наименьших привилегий)

```sql
-- Для чтения binlog с удалённого сервера или реплики
GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'backup_user'@'%';

-- Для XtraBackup
GRANT PROCESS, RELOAD, LOCK TABLES, REPLICATION CLIENT, SELECT ON *.* TO 'backup_user'@'localhost';

-- Для логических дампов
GRANT SELECT, RELOAD, SHOW DATABASES, REPLICATION CLIENT,
      LOCK TABLES, SHOW VIEW, EVENT, TRIGGER
    ON *.* TO 'backup_user'@'localhost';
```

> **Примечание об именах:** привилегия `REPLICATION SLAVE` сохраняет своё имя в 8.0/8.4/9.x — переименования затронули операторы, не привилегии: `SHOW SLAVE STATUS` → `SHOW REPLICA STATUS` — с MySQL 8.0.22; `SHOW MASTER STATUS` → `SHOW BINARY LOG STATUS` — с MySQL 8.2.0 (в 8.4 `SHOW MASTER STATUS` уже не поддерживается). В MySQL 5.7 доступны только старые имена операторов.

Привилегии, добавленные в MySQL 8.0 и обязательные для штатной автоматизации бэкапа:

```sql
-- LOCK INSTANCE FOR BACKUP / UNLOCK INSTANCE (MySQL 8.0+)
GRANT BACKUP_ADMIN ON *.* TO 'backup_user'@'localhost';

-- Архивирование InnoDB redo log (MySQL 8.0.17+)
GRANT INNODB_REDO_LOG_ARCHIVE ON *.* TO 'backup_user'@'localhost';
```

Требования к привилегиям `mysqldump` зависят от версии и набора флагов:

| Требование | Условие | Альтернатива |
| :--- | :--- | :--- |
| `PROCESS` | MySQL 8.0.21+, если не задан `--no-tablespaces` | Добавить `--no-tablespaces` — обычный случай |
| `RELOAD` или `FLUSH_TABLES` | MySQL 8.0.32+, при `--single-transaction` и одновременно `gtid_mode=ON` и `gtid_purged=ON\|AUTO` | Убрать `gtid_purged` или не использовать `--single-transaction` |
| `SELECT` | Всегда | — |
| `SHOW VIEW` | Для представлений | — |
| `TRIGGER` | Для триггеров | — |
| `LOCK TABLES` | Только если **не** используется `--single-transaction` | Всегда используйте `--single-transaction` для InnoDB |
| `SHOW MASTER STATUS` + `RELOAD` | Для `--source-data` (`--master-data` в 5.7) | Включённый `log_bin` обязателен |

### Инфраструктурные требования

- **NTP:** синхронизация времени на всех узлах кластера. Некорректные временные метки binlog делают PITR невозможным.
- **Диск:** отдельный раздел или том для binlog; место под 2–3 цикла ротации сверх активных логов.
- **Сеть:** стабильный канал для `mysqlbinlog --read-from-remote-server`, если используется удаленный архив.

## Определения

**Резервное копирование (Backup)** — процесс создания копии данных для восстановления после сбоя. В контексте MySQL делится на физическое (копирование файлов данных) и логическое (дамп SQL или специализированный формат).

**Восстановление (Restore)** — процесс возврата данных из резервной копии в рабочую базу.

**Восстановление на конкретный момент (Point-in-Time Recovery, PITR)** — восстановление состояния БД до точного момента в прошлом путем комбинации полного бэкапа и последовательного применения бинарных логов через `mysqlbinlog`. Подробный сценарий — в **[PITR](./pitr.md)**.

**Физический бэкап** — копирование файлов данных InnoDB на уровне страниц. Осуществляется `Percona XtraBackup`. Скорость создания и восстановления максимальна, но гранулярность ограничена (уровень таблиц). Подробнее — в **[Percona XtraBackup](./xtrabackup.md)**.

**Логический бэкап** — дамп данных в виде SQL-инструкций или специализированного формата (MySQL Shell). Осуществляется `mysqldump`, `mysqlpump` (deprecated), `mysqlsh`. Гранулярность высокая (таблица/схема/инстанс), скорость создания ниже. Подробнее — в **[MySQL Shell Dump & Load](./mysql_shell_dump.md)**.

**Уровни консистентности:**
- **Dirty:** простое копирование файлов без взаимодействия с сервером; гарантированно приводит к повреждению.
- **Crash-consistent:** эквивалентен состоянию после аварийного выключения питания; InnoDB выполняет crash recovery при старте.
- **Application-consistent:** сервер фиксирует согласованное состояние через `START TRANSACTION WITH CONSISTENT SNAPSHOT` или `LOCK INSTANCE FOR BACKUP`.

**RTO (Recovery Time Objective)** — максимально допустимое время простоя. Диктует выбор метода: физический бэкап даёт минимальный RTO, логический — выше.

**RPO (Recovery Point Objective)** — максимально допустимая потеря данных. Диктует частоту бэкапов и срок хранения binlog. Для PITR RPO определяется размером binlog и временем их архивации.

**Целевая точка восстановления (Recovery Target)** — конкретный момент времени или позиция в binlog, до которого необходимо откатить данные.

## Основные концепции

### Сравнение методов бэкапа

| Характеристика | Physical (XtraBackup) | Logical (MySQL Shell) | Logical (mysqldump) |
| :--- | :--- | :--- | :--- |
| **Скорость создания** | Очень высокая (потоковое I/O) | Высокая (Parallel) | Низкая (Single-thread) |
| **Скорость восстановления** | Максимальная (Copy + Redo) | Средняя (Parallel INSERT) | Очень низкая (SQL Parser) |
| **Гранулярность** | Уровень таблиц (с export) | Таблица/схема/инстанс | Таблица/схема/инстанс |
| **Блокировки** | Минимальные (InnoDB) | Минимальные (`LOCK INSTANCE FOR BACKUP`) | Могут быть значительными |
| **RTO** | Минимальный | Средний | Максимальный |
| **RPO** | Зависит от binlog | Зависит от binlog | Зависит от binlog |
| **PITR** | Да | Да | Да |
| **Совместимость версий** | Требует совпадения major.minor | Высокая (логический формат) | Высокая |

### Уровни консистентности бэкапов MySQL

1. **Неконсистентный (Dirty):** Простое копирование файлов данных (`/var/lib/mysql/`) без взаимодействия с сервером. Гарантированно приводит к повреждению — InnoDB redo/undo логи не зафиксированы, могли произойти partial writes.
2. **Crash-consistent (Физический):** XtraBackup копирует страницы InnoDB непрерывно, затем применяет redo log (`--prepare`). InnoDB Crash Recovery восстанавливает целостность при старте сервера.
3. **Application-consistent (Логический):** Перед выгрузкой сервер фиксирует состояние через `START TRANSACTION WITH CONSISTENT SNAPSHOT` (`--single-transaction`) или `LOCK INSTANCE FOR BACKUP` (MySQL Shell).

Снимок файловой системы без координации даёт уровень 2: набор файлов атомарен, и InnoDB восстановит себя из собственного redo log — см. **[Бэкап снимками ФС](./snapshot_backup.md)**.

### Механизмы блокировки при бэкапе

Три механизма регулярно путают, и разница между ними определяет, встанет ли продакшен во время бэкапа. Ключевой вопрос: **блокирует ли механизм обычную запись данных (DML)**.

| Механизм | Блокирует DML | Блокирует DDL | Что ещё блокирует | Привилегия | Где применяется |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `START TRANSACTION WITH CONSISTENT SNAPSHOT` | Нет | Нет | Ничего | Обычные права на чтение | `mysqldump --single-transaction` |
| `LOCK INSTANCE FOR BACKUP` | **Нет** | **Да** | `TRUNCATE`, `OPTIMIZE`, `REPAIR`, операции с файлами вне redo log, управление учётными записями | `BACKUP_ADMIN` (8.0+) | MySQL Shell `consistent: true`, `mysqlbackup`, `mysqlsh dumpInstance` |
| `FLUSH TABLES WITH READ LOCK` (GRL) | **Да — всё во всём инстансе** | **Да** | Всё, включая запись | `RELOAD` | Только `--master-data`/`--source-data` без `--single-transaction` |

Практические следствия:

- **`LOCK INSTANCE FOR BACKUP` — не GRL.** Приложение продолжает писать данные во время бэкапа; останавливается только изменение структуры и файлов. Поэтому окно блокировки минимально, а DML-нагрузка не страдает.
- **GRL останавливает продакшен полностью.** Это глобальная блокировка на уровне инстанса: любой `INSERT`, `UPDATE` или `DELETE` любой таблицы ждёт её снятия. Использовать только на короткое время и только когда иначе получить согласованный снимок невозможно.
- **Блокировка держится на соединении.** `FLUSH TABLES WITH READ LOCK` освобождается при закрытии сессии. Если выполнить бэкап в том же терминале, где открыт `mysql`, блокировка исчезнет раньше времени — классическая причина «неконсистентного бэкапа при вроде бы правильных командах».
- **`LOCK TABLES ... FOR BACKUP` не существует.** Это распространённая ошибка в самодельных скриптах: команда не является синтаксисом MySQL и завершается ошибкой. Корректные варианты — `LOCK INSTANCE FOR BACKUP` (8.0+) или GRL.

> **Выбор по сценарию:** почти всегда достаточно `START TRANSACTION WITH CONSISTENT SNAPSHOT` (логический дамп InnoDB) или ничего (XtraBackup, снимок ФС). `LOCK INSTANCE FOR BACKUP` нужен там, где утилита требует согласованности на уровне инстанса. GRL — крайний случай, и его применение в production стоит рассматривать как инцидент.

Подробно о требованиях привилегий для каждого флага — в таблице ниже и в **[Пользователь бэкапа](#пользователь-бэкапа-принцип-наименьших-привилегий)**.

### Архитектура PITR

PITR состоит из трех этапов:
1. Восстановить полный бэкап на целевом инстансе.
2. Определить начальную позицию в binlog (момент создания бэкапа).
3. Применить binlog-события от начальной позиции до целевого момента.

Для PITR требуется:
- Включенный `log_bin` на источнике до момента создания бэкапа.
- Доступ ко всем binlog-файлам за период от момента бэкапа до целевого момента.
- GTID включён (рекомендуется) для точного позиционирования и исключения транзакций.

### Проблема консистентности при инкрементальном бэкапе XtraBackup

XtraBackup копирует страницы InnoDB непрерывно. Если между началом копирования и фиксацией redo log изменится и данные, и redo-запись, бэкап может оказаться неполным. XtraBackup решает это, записывая LSN начальной страницы и проверяя его при `--prepare`. Несоответствие LSN приводит к ошибке.

### Клонирование через MySQL Clone Plugin

Физическое клонирование используется для быстрого seeding реплик:

```bash
# На источнике
INSTALL PLUGIN clone SONAME 'mysql_clone.so';
CREATE USER 'clone_user'@'%' IDENTIFIED BY 'ClonePassword!2024';
GRANT CLONE_ADMIN ON *.* TO 'clone_user'@'%';

# На реплике
SET GLOBAL clone_valid_donor_list = 'primary_host:3306';
CLONE INSTANCE FROM 'clone_user'@'primary_host'
  IDENTIFIED BY 'ClonePassword!2024';
```

> **Важно:** После клонирования сервер-получатель автоматически останавливается. Перезапустите его. Версии MySQL должны совпадать по major.minor (с 8.0.35+ допускается различие в patch).

## Практические сценарии

### Сценарий 1: Ежедневный Production бэкап

Стандартная стратегия: полный физический бэкап XtraBackup + непрерывная архивация binlog. Детали — в **[Percona XtraBackup](./xtrabackup.md)** и **[Автоматизация](./automation.md)**.

### Сценарий 2: Восстановление после сбоя диска/сервера

1. Восстановите последний полный бэкап через `xtrabackup --copy-back`.
2. Примените binlog до целевого момента через `mysqlbinlog`.
3. Запустите сервер и проведите smoke-тест. Подробный сценарий — в **[PITR](./pitr.md)**.

### Сценарий 3: Миграция между версиями MySQL

Используйте логический дамп MySQL Shell (`util.dumpInstance()`), который гарантирует совместимость DDL между версиями. Подробнее — в **[MySQL Shell Dump & Load](./mysql_shell_dump.md)**.

### Сценарий 4: Восстановление отдельной таблицы

- Из физического бэкапа: `xtrabackup --prepare --export` + `IMPORT TABLESPACE`.
- Из логического дампа: `mysqlsh util.dumpTables()` или фильтрация SQL-дампа.

### Сценарий 5: Быстрая инициализация реплики

Используйте `MySQL Clone Plugin` для физического клонирования данных за минуты. Подробнее — в **[Настройка репликации MySQL](../replication/setup_guide.md)**.

## Ограничения и особенности

1. **MySQL 8.0 EOL:** Завершает поддержку в апреле 2026. Для новых систем используйте 8.4 LTS.
2. **`mysqlpump` удалён в 8.4:** Используйте `mysqlsh util.dumpInstance()`.
3. **INSTANT ADD/DROP COLUMN:** В MySQL 8.0.12–8.0.28 может привести к ошибкам XtraBackup. Обновите MySQL до 8.0.29+ или используйте XtraBackup 8.0.35-xx.
4. **Совместимость XtraBackup:** Версии инструмента и сервера должны совпадать по major.minor.
5. **Шифрование binlog:** Если включен `binlog_encryption`, используйте `mysqlbinlog --read-from-remote-server` с `--keyring-path`.
6. **Смешанные форматы binlog:** В режиме `MIXED` PITR может восстановить только события, поддерживаемые целевым сервером. Рекомендуется `ROW`. Подробнее — в **[Форматах бинарного лога](../replication/binlog_formats.md)**.
7. **Длинные транзакции:** `--stop-datetime` может не отработать корректно. Используйте `--stop-position` для точного контроля.
8. **Сжатие binlog:** Если включен `binlog_transaction_compression`, `mysqlbinlog` декодирует автоматически (MySQL 8.0.20+).

## Диагностика и устранение неисправностей

### Ошибки Percona XtraBackup

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`Error: redo log size mismatch`** | Несовместимость версий xtrabackup и mysqld | Версии должны совпадать по major.minor |
| **`Log sequence number (LSN) mismatch`** | Базовый бэкап повреждён | Удалите инкремент и сделайте новый базовый бэкап |
| **`last checkpoint LSN is greater`** | Повреждение redo-лога | Проверьте целостность диска, сделайте новый полный бэкап |
| **`Found tables with row versions due to INSTANT ADD/DROP`** | MySQL 8.0.12–8.0.28 | Обновите MySQL или используйте XtraBackup 8.0.35-xx |
| **`code=1` при `--copy-back`** | Неверные права или нехватка места | Проверьте `chown` и `df -h` |

### Ошибки MySQL Shell Dump/Load

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`Access denied for user`** | Недостаточно прав | Требуются: `SELECT, RELOAD, SHOW DATABASES, REPLICATION CLIENT, LOCK TABLES, EVENT, TRIGGER` |
| **`Consistency error`** | Зависшие транзакции блокируют `LOCK INSTANCE FOR BACKUP` | Проверьте `SHOW PROCESSLIST` и завершите зависшие транзакции |
| **`Table already exists`** | Таблица существует в целевой БД | Используйте `ignoreExistingObjects: true` |
| **`Unsupported feature in dump metadata`** | Версия MySQL Shell целевого сервера ниже источника | Обновите MySQL Shell |

### Ошибки mysqldump

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`Lock wait timeout exceeded`** | Конфликт с активными транзакциями | Используйте `--single-transaction` для InnoDB |
| **`MySQL server has gone away`** | Слишком большой дамп превышает `max_allowed_packet` | Увеличьте `--max-allowed-packet=1G` (максимум 1 ГБ) |
| **`Unknown table 'INFORMATION_SCHEMA.FILES'`** | Старая версия клиента | Обновите клиент до версии сервера |

### Общие ошибки

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| **`No space left on device`** | Нехватка места | Используйте стриминг (`--stream=xbstream`) или сжатие |
| **`mysqlbinlog: [ERROR] unknown variable`** | Конфликт опций конфигурации | Добавьте `--no-defaults` к команде |
| **Бэкап больше исходных данных** | Не используется сжатие | Добавьте `--compress` (XtraBackup) или `compression: 'zstd'` (MySQL Shell) |
| **Восстановление занимает часы** | Логический однопоточный дамп | Используйте `util.loadDump()` с многопоточным импортом |

## Бест-практики и стратегии

### Стратегии ротации и хранения

| Тип бэкапа | Частота | Срок хранения | RTO | RPO |
| :--- | :--- | :--- | :--- | :--- |
| Полный физический (XtraBackup) | Ежедневно | 7–14 дней | Минимальный | Зависит от binlog |
| Инкрементальный (XtraBackup) | Ежедневно между полными | 3–7 дней | Средний | Минимальный |
| Логический дамп (MySQL Shell) | Ежедневно | 30 дней | Высокий | Зависит от binlog |
| Бинарные логи (mysqlbinlog) | Непрерывно (архивация) | 7–30 дней | — | Определяет RPO |

### Рекомендации по бэкапам

1. **Автоматизируйте:** Никаких ручных запусков. Используйте Cron или оркестраторы (Nomad, Kubernetes CronJobs). См. **[Автоматизация и верификация](./automation.md)**.
2. **Бэкапируйте конфиги MySQL:** Файл `my.cnf`, TLS-сертификаты, ключи шифрования (keyring). База без конфигурации может не запуститься.
3. **Разделение прав:** Пользователь бэкапа НЕ должен иметь `SUPER` или `ALL PRIVILEGES`. Используйте минимальные привилегии из раздела «Предварительные требования».
4. **Верификация восстановления:** Минимум раз в квартал проводите полное восстановление в изолированную среду. Документируйте RTO (среднее время восстановления) и RPO (максимально допустимая потеря данных).
5. **Мониторинг:** Настраивайте алерты не на «ошибку бэкапа», а на «отсутствие успешного бэкапа за N часов». Используйте метрики `backup_last_success_timestamp` в Prometheus Pushgateway.
6. **Хранение offsite:** Копия бэкапа должна находиться на удалённой площадке. Следуйте правилу 3-2-1-1-0 (см. **[Стратегии резервного копирования](../../Concepts/backups.md)**).
7. **Иммутабельность:** Для критичных данных храните бэкапы в иммутабельном хранилище для защиты от Ransomware (см. **[Безопасность бэкапов](../../Concepts/backup_security.md)**).
8. **Тестируйте PITR регулярно:** Проводите drills восстановления на изолированном инстансе не реже раза в квартал.
9. **Используйте отложенную репликацию (`SOURCE_DELAY`):** Для защиты от логических ошибок (DROP TABLE, ошибочный UPDATE) можно настроить реплику с задержкой 30–60 минут. Это позволяет откатиться без полного PITR, если ошибка обнаружена вовремя.
10. **Мониторинг места под binlog:** Настройте алерт при заполнении диска более чем на 80%. Используйте `du -sh /var/lib/mysql-binlog/`.

### Выбор инструмента по сценарию

| Сценарий | Рекомендуемый инструмент | Обоснование |
| :--- | :--- | :--- |
| Production backup (RTO < 1 ч) | [XtraBackup](./xtrabackup.md) + архивация binlog | Физическое копирование — максимальная скорость восстановления |
| Миграция между версиями MySQL | [MySQL Shell Dump/Load](./mysql_shell_dump.md) | Гарантирует совместимость DDL между версиями |
| Восстановление отдельной таблицы | [MySQL Shell dumpTables](./mysql_shell_dump.md) / XtraBackup export | Гранулярность на уровне таблицы |
| Быстрое развёртывание реплики | MySQL Clone Plugin | Физическое клонирование за минуты |
| PITR (откат на конкретную секунду) | Любой бэкап + [mysqlbinlog (PITR)](./pitr.md) | Бинарный лог — единственный способ точного отката |
