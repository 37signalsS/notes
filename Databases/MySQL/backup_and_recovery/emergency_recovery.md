# Аварийное восстановление MySQL (InnoDB)

**Актуально для:** MySQL 5.7 / 8.0 / 8.4

> **Статус:** процедура для инцидента, когда сервер не стартует или таблица недоступна. Материал носит аварийный характер: порядок шагов критичен, пропуск шага может уничтожить остатки данных.

## Определения

**Crash recovery** — автоматическое восстановление InnoDB при старте сервера после аварийного сбоя. Сервер читает redo log и применяет записи, не попавшие в файлы данных. Применение redo выполняется на этапе инициализации, до приёма соединений; обычно проходит прозрачно.

**`innodb_force_recovery`** — глобальная системная переменная (Scope: Global, Dynamic: No — задаётся только при старте сервера в конфиге, через `SET` не меняется). Значение `0` (по умолчанию) — штатный режим; `1`–`6` — аварийный. Значения кумулятивны: уровень `3` включает функциональность `1` и `2`.

**Системный tablespace (`ibdata1`)** — общее пространство InnoDB (tablespace с ID 0). В 5.7 в нём находятся data dictionary, undo log и doublewrite buffer; в 8.0 data dictionary вынесен в отдельный tablespace `mysql.ibd`, а undo — в отдельные undo tablespace. Не путать с файлами-таблицами `db_table.ibd`.

**Redo log corruption** — повреждение файлов redo log (`ib_logfile*` в 5.7, `#innodb_redo/` в 8.0.30+). Проявляется ошибкой вида `Plugin 'InnoDB' init function returned error` при старте.

**Dump из аварийного режима** — извлечение данных через `mysqldump` (или `SELECT ... INTO OUTFILE`) с сервера, запущенного с `innodb_force_recovery > 0`. Дамп содержит только то, что удалось прочитать; недоступные таблицы приводят к ошибкам вида `mysqldump: Error reading '...'`.

## Основные концепции

### Порядок действий: что можно и что нельзя

При аварии порядок шагов определяет, сохранится ли что-нибудь вообще.

| Шаг | Действие | Почему именно так |
| :--- | :--- | :--- |
| 1 | **Остановить запись.** Снять приложения с базы | Каждая запись на повреждённый инстанс может добить данные |
| 2 | **Снять копию всего каталога данных**, включая redo log и undo | Единственная возможность откатиться к исходному состоянию, если следующие шаги усугубят ситуацию |
| 3 | Диагностика: прочитать лог ошибок, определить масштаб | Без диагноза выбор уровня `innodb_force_recovery` — гадание |
| 4 | Поднимать `innodb_force_recovery` **минимальным** рабочим значением | Каждый уровень отключает подсистемы и увеличивает риск потери данных |
| 5 | Извлечь данные дампом | Цель аварийного режима — не починить, а **забрать** данные |
| 6 | Восстановить в чистый инстанс | Починенный на месте сервер редко становится надёжным |

> **Шаг 2 — критический.** Он выполняется **до** любых изменений конфигурации и запусков. Множество инцидентов усугубляются именно тем, что инженер меняет `my.cnf`, перезапускает сервер и только потом вспоминает про копию. Копия снимается холодно: если сервер не стартует, копируется файловая система целиком, а не «живая».

### Уровни `innodb_force_recovery` и их цена

Официальное предупреждение Oracle: значение `> 0` задаётся **только в аварийной ситуации**, чтобы поднять InnoDB и снять дамп; перед этим должна быть копия базы. Значения `≥ 4` могут **перманентно повредить файлы данных** — применять их на продакшн-инстансе следует только после успешной проверки на отдельной физической копии базы. Начинать всегда с `1` и повышать только по необходимости, по одному уровню.

| Уровень | Символ | Что отключено / делает | Последствия для данных |
| :--- | :--- | :--- | :--- |
| `1` | `SRV_FORCE_IGNORE_CORRUPT` | Сервер работает, даже обнаружив повреждённую страницу; `SELECT` перепрыгивает повреждённые индексные записи и страницы — помогает снять дамп | Данные не страдают |
| `2` | `SRV_FORCE_NO_BACKGROUND` | Не запускаются master thread и потоки purge — предотвращает падение во время purge | Данные не страдают |
| `3` | `SRV_FORCE_NO_TRX_UNDO` | После crash recovery **не выполняются откаты транзакций** | Незавершённые транзакции остаются в промежуточном состоянии — возможна частичная запись |
| `4` | `SRV_FORCE_NO_IBUF_MERGE` | Запрещены операции слияния insert buffer; не рассчитывается статистика таблиц | **Может перманентно повредить файлы данных.** Будьте готовы пересоздать все вторичные индексы. InnoDB переводится в read-only |
| `5` | `SRV_FORCE_NO_UNDO_LOG_SCAN` | При старте undo log не читаются: даже незавершённые транзакции считаются зафиксированными | **Может перманентно повредить файлы данных.** Read-only |
| `6` | `SRV_FORCE_NO_LOG_REDO` | Roll-forward по redo log не выполняется | **Может перманентно повредить файлы данных.** Страницы остаются в устаревшем состоянии, что вносит дополнительную коррупцию в B-деревья. Read-only |

Правила, которые следуют из документации:

1. **Дамп на уровнях ≤ 3 относительно безопасен** — потеря ограничена данными на повреждённых страницах («only some data on corrupt individual pages is lost»). Значение `≥ 4` считается опасным, `6` — радикальным.
2. **При любом значении `> 0` InnoDB блокирует `INSERT`/`UPDATE`/`DELETE`.** От уровня `4` InnoDB переводится в read-only mode. Исключение для записи нет — единственная «изменяющая» операция, разрешенная на уровнях ≤ 3, — `DROP`/`CREATE TABLE` (см. ниже).
3. **`DROP`/`CREATE TABLE` разрешены на уровнях ≤ 3; `DROP TABLE` разрешён до уровня 4 включительно и запрещён на 5–6.** Это используется для удаления таблицы, вызывающей бесконечный откат (сценарий 5).
4. **На высоких уровнях сложные запросы (`WHERE`, `ORDER BY`) могут падать** — возможны только простые `SELECT * FROM t`.

### Почему нельзя чинить на месте

`innodb_force_recovery` не является механизмом восстановления. Это режим, в котором InnoDB **отказывается от гарантий**, чтобы вы смогли прочитать данные. Возможные причины повреждения (сбойное хранилище, отказ питания, ошибка в драйвере, баг) остаются на месте, если продолжить работу на том же инстансе.

Практика: извлечь данные в чистый инстанс, восстановить туда бэкап, выяснить причину по логам и hardware health, а исходный инстанс оставить для анализа. Восстановленный сервер обязательно включать в план возврата на штатную эксплуатацию только после устранения первопричины.

### Различие 5.7 и 8.0 при работе с redo log

| | MySQL 5.7 | MySQL 8.0 |
| :--- | :--- | :--- |
| Файлы redo log | `ib_logfile0`, `ib_logfile1` в `datadir` | `#innodb_redo/` в `datadir` (настраиваемое размещение) |
| Размер | Фиксированный, оба файла, циклически | Динамический `innodb_redo_log_capacity` (с 8.0.30) |
| Применение redo при старте | Выполняется, если есть записи с момента последнего чекпойнта | То же |
| Пересоздание | Удалить `ib_logfile*` при **остановленном** сервере — при старте InnoDB пропускает применение redo и создаёт файлы заново | То же для `#innodb_redo/` (8.0.30+) |
| Предостережение | Удаление `ib_logfile*` на работающем сервере — потеря данных | `#innodb_redo` удаляется только при остановленном сервере |

> **Удаление redo log — мера последней инстанции.** Документация: «Removing redo logs to speed up recovery is not recommended, even if some data loss is acceptable. Removing redo logs should only be considered after a clean shutdown, with `innodb_fast_shutdown` set to `0` or `1`». InnoDB пропускает применение redo, только если файлы redo отсутствуют при старте — именно это и делает процедуру рабочей, и именно поэтому теряются все изменения, не попавшие в файлы данных.

> **Опасный совет, который часто дают неправильно:** «удалите ib_logfile и запустите сервер». Процедура рабочая, но она уничтожает redo log — то есть **все несохранённые на диск изменения теряются**, а неиспорченные данные остаются. Допустимо только когда потеря изменений приемлема и вы понимаете её цену. Первым всегда пробуйте `innodb_force_recovery = 1`.

## Практические сценарии

### Сценарий 1: Определение масштаба повреждения (до изменений)

**Предварительные условия:** root/sudo на хосте, свободное место ≥ 2× размер `datadir` (оригинал + forensic-копия), версии клиентских утилит (`mysqldump`, `mysqlcheck`) совпадают с версией сервера. Путь к логу ошибок зависит от дистрибутива: `/var/log/mysql/error.log` (Debian/Ubuntu), `/var/log/mysqld.log` (RHEL/CentOS), либо `journalctl` на systemd.

```bash
# 1. Лог ошибок — основной источник диагноза
tail -50 /var/log/mysql/error.log
# → [ERROR] [MY-012153] [InnoDB] Trying to access page number 875705389 in
#   space 7312, space name mydb/orders, which is outside the tablespace
#   bounds. Byte offset 0, len 16384, i/o type read. If you get this error
#   at mysqld startup, please check that your my.cnf matches the ibdata
#   files that you have in the MySQL server.
# → [ERROR] [MY-013183] [InnoDB] Assertion failure: fil0fil.cc:7192 thread ...
```

> **Перед глубоким анализом:** иногда видимая «коррупция страниц» — это повреждение файлового кэша ОС, а не данных на диске. Документация рекомендует сначала перезагрузить хост: это может устранить ошибки, которые выглядят как повреждение страниц. Если после перезагрузки сервер стартует — проверяйте данные, а не восстанавливайте.

```bash
# 2. Целостность файловой системы
fsck -n /dev/sdX
# → clean, exit 0
```

```bash
# 3. Состояние SMART — исключить аппаратную первопричину
smartctl -H /dev/sdX
# → SMART overall-health self-assessment test result: PASSED
# → Если FAILED — причина не в MySQL, чинить нужно хранилище
```

```bash
# 4. Холодная копия всего каталога данных (шаг 2 из таблицы выше)
systemctl stop mysql
cp -a /var/lib/mysql /var/lib/mysql.forensic.$(date +%F)
ls -ld /var/lib/mysql.forensic.*
# → drwxr-xr-x 27 mysql mysql 4096 Oct  3 04:20 /var/lib/mysql.forensic.2026-10-03
# Дальнейшие шаги выполняются ТОЛЬКО на копии, оригинал не трогать
```

### Сценарий 2: Подъём в аварийном режиме

```bash
# Работаем на копии, чтобы не рисковать оригиналом
mv /var/lib/mysql /var/lib/mysql.broken
cp -a /var/lib/mysql.forensic.2026-10-03 /var/lib/mysql
chown -R mysql:mysql /var/lib/mysql
```

```ini
# /etc/mysql/mysql.conf.d/emergency.cnf
[mysqld]
innodb_force_recovery = 1
skip-networking                    # только локальный доступ — никакого риска для приложений
```

```bash
systemctl start mysql
sleep 10
systemctl is-active mysql
# → active
```

```bash
# Ошибка на уровне 1 означает, что нужно поднимать уровень.
# Если сервер стартовал — уровень достаточный, повышать НЕЛЬЗЯ.
journalctl -u mysql -n 30 --no-pager
# → [ERROR] [MY-012153] [InnoDB] Trying to access page number ... outside the tablespace bounds
```

```bash
# Если не стартовал — поднимаем на 2, затем 3, и так далее.
# Каждый шаг: изменить, перезапустить, прочитать лог.
sed -i 's/innodb_force_recovery = 1/innodb_force_recovery = 2/' \
  /etc/mysql/mysql.conf.d/emergency.cnf
systemctl restart mysql && sleep 10
systemctl is-active mysql
# → active
```

```sql
-- Сервер работает ТОЛЬКО НА ЧТЕНИЕ (INSERT/UPDATE/DELETE запрещены
-- при любом innodb_force_recovery > 0)
SELECT @@innodb_force_recovery;
-- → 1
```

### Сценарий 3: Определение, какие таблицы читаются

```sql
-- Проверка читаемости каждой таблицы по одной.
-- Цель — понять масштаб потерь ДО начала извлечения.
SELECT COUNT(*) FROM users;
-- → 152834
SELECT COUNT(*) FROM orders;
-- → ERROR 1812 (HY000): Tablespace is missing for table 'orders'
--   (потерян файл orders.ibd)
-- → ERROR 1814 (HY000): Tablespace has been discarded for table 'orders'
--   (.ibd был discard'ed вручную)
```

> Тяжёлая коррупция страниц чаще всего проявляется не ошибкой SQL, а падением сервера: `mysqldump: Error 2013: Lost connection to MySQL server during query` и assertion failure в логе. Это тоже признак непригодности таблицы для дампа.

Практический подход — автоматизировать перебор, чтобы получить карту повреждений:

```bash
for t in $(mysql -N -B -e "SELECT TABLE_NAME FROM information_schema.TABLES
                            WHERE TABLE_SCHEMA='mydb' AND ENGINE='InnoDB';"); do
  if mysql -N -B -e "SELECT 1 FROM mydb.\`$t\` LIMIT 1;" >/dev/null 2>&1; then
    echo "OK      $t"
  else
    echo "CORRUPT $t"
  fi
done | tee /var/log/table_damage_map.txt
# → OK      users
# → OK      orders
# → CORRUPT sessions
# → CORRUPT audit_log
```

Эта карта — основной артефакт аварии: она определяет, что извлекаем, а что придётся поднимать из последнего бэкапа.

### Сценарий 4: Извлечение данных

```bash
# Извлекаем только читаемые таблицы — попытка прочитать повреждённую
# прерывает весь дамп, поэтому исключаем их явно
mysqldump --user=root \
  --single-transaction --no-tablespaces \
  --ignore-table=mydb.sessions \
  --ignore-table=mydb.audit_log \
  --databases mydb 2>/var/log/emergency_dump.err \
  | zstd -T0 -3 > /tmp/rescued_$(date +%F_%H%M).sql.zst
# → 0
```

Альтернатива явному перечислению — `--ignore-error` с кодами ошибок, которые означают лишь недоступность отдельных таблиц (подробно — в **[mysqldump](./mysqldump.md)**):

```bash
mysqldump --user=root --single-transaction --no-tablespaces \
  --ignore-error=1812,1814 --databases mydb 2>/var/log/emergency_dump.err
# Дамп продолжится мимо таблиц с потерянным tablespace.
# ВНИМАНИЕ: --ignore-error скрывает проблемы — всегда проверяйте stderr,
# иначе в дампе окажется меньше таблиц, чем ожидалось.
```

> **Важно:** `--single-transaction` в аварийном режиме применять можно — он лишь открывает транзакцию; никакой блокировки и никакой записи. Не добавляйте `--lock-tables`: на аварийном инстансе блокировка бесполезна и добавляет точку отказа.

```bash
# Проверка лога: что именно не удалось прочитать
cat /var/log/emergency_dump.err
# → mysqldump: Error reading 'CHARACTER SET' information:
#   Can't find file: 'mydb/sessions.ibd'
# → Значит таблица sessions исключена осознанно
```

> **Если коррупция в середине таблицы** — дамп обрывается на повреждённой странице. Документация: запрос с `ORDER BY primary_key DESC` может вычитать часть таблицы **после** повреждённого участка. Дампите два диапазона (прямой и обратный) и склеивайте — это выигрывает часть данных, которую не прочитал прямой проход.

```sql
-- Дамп аварийного сервера НЕ содержит stored routines и events,
-- если их не удалось прочитать — проверяем явно
SHOW PROCEDURE STATUS WHERE Db='mydb';
-- → (пусто — потеряны)
```

Полное описание дампа и его флагов — в **[mysqldump](./mysqldump.md)**.

### Сценарий 5: Бесконечный откат после неудачного импорта или ALTER

Симптом: сервер «завис» — откат большой незавершённой транзакции (провалившийся массовый `INSERT`, `ALTER TABLE`, `LOAD DATA`). Документация: откат может занять **в 3–4 раза больше времени, чем сама транзакция**, и его **нельзя отменить** — сервер будет недоступен часами.

```bash
# 1. Остановить mysqld (дайте ему уйти, если уходит; иначе kill)
systemctl stop mysql || pkill -TERM mysqld

# 2. Поднять с innodb_force_recovery = 3 — откат не выполняется,
#    незавершённая транзакция остаётся как есть
sed -i 's/^innodb_force_recovery.*/innodb_force_recovery = 3/' \
  /etc/mysql/mysql.conf.d/emergency.cnf
systemctl start mysql

# 3. Удалить таблицу, вызвавшую откат (DROP TABLE разрешён до уровня 4)
mysql -e "DROP TABLE mydb.huge_import_tmp;"

# 4. Остановить, снять аварийный режим, стартовать штатно
systemctl stop mysql
rm -f /etc/mysql/mysql.conf.d/emergency.cnf
systemctl start mysql
```

> Уровень `3` пропускает откат транзакций — значит, данные в других таблицах могут остаться в промежуточном состоянии. После подъёма сверьте счётчики и критичные таблицы с репликой/дампом. Если инцидент не про «зависший откат», а про повреждение — используйте сценарий 2 и начинайте с уровня `1`.

### Сценарий 6: Потерянный `.ibd` и сирота в data dictionary

Симптом: в логе при старте — `[Warning] InnoDB: Ignoring tablespace `mydb.t1` because it could not be opened`, а в SQL — `ERROR 1812/1814`. Причина: файл `t1.ibd` удалён (вручную или сбоем), а запись о таблице осталась в data dictionary.

Особенность механизма tablespace discovery: если redo log ссылается на отсутствующий `.ibd`, **старт отказывается**; в аварийном режиме (`innodb_force_recovery > 0`) отсутствующие `.ibd` игнорируются — сервер стартует.

```bash
# 1. Поднять в аварийном режиме (уровень 1..3), если сервер отказывается стартовать
#    из-за отсутствующих .ibd — см. сценарий 2

# 2. Убрать сироту из словаря — DROP TABLE чистит data dictionary
mysql -e "DROP TABLE mydb.t1;"
# → после этого ошибка "Tablespace is missing" исчезает

# 3. Восстановить таблицу из бэкапа (схема + данные) или из реплики
mysql mydb < /backups/t1_schema.sql
```

> Если файл `.ibd` не потерян, а лежит где-то ещё (перенесён, отсоединён LUN), правильный путь — вернуть его на место и перезапустить сервер, а не дропать таблицу. Дроп — только когда файла нет окончательно.

### Сценарий 7: Пересоздание повреждённых таблиц

Если повреждена таблица, но есть её содержимое в другом источнике (реплика, предыдущий дамп, binlog):

```bash
# 1. В чистом инстансе создаём таблицу заново
#    (в аварийном режиме DROP/CREATE разрешены на уровнях ≤ 3,
#     DROP TABLE — до 4 включительно)
mysql -e "DROP TABLE mydb.sessions;"

# 2. Восстанавливаем структуру из последнего дампа схем
mysql mydb < /backups/sessions_schema.sql

# 3. Доливаем данными из binlog с момента последнего бэкапа
#    (позиция берётся из --source-data дампа)
mysqlbinlog --start-position=154 /var/log/mysql/binlog.000042 \
  | mysql -u root
# → 0

# 4. Валидация
mysql -e "CHECK TABLE mydb.sessions;"
# → mydb.sessions  check  status  OK
```

> **Осторожно с шагом 3:** `mysqlbinlog` без фильтров проигрывает **все** события потока, не только относящиеся к восстанавливаемой таблице. Если остальные таблицы уже восстановлены из rescued-дампа, полное проигрывание двойит изменения. Для точечного восстановления одной таблицы проиграйте binlog на отдельном scratch-инстансе и скопируйте оттуда таблицу, либо фильтруйте события по позиции/времени.

### Сценарий 8: Пересоздание redo log как крайняя мера

Применяется, когда повреждён именно redo log, а файлы данных целы, **и потеря несохранённых изменений приемлема**.

```bash
# Если сервер ещё стартует — выполните ЧИСТУЮ остановку:
# полный сброс грязных страниц минимизирует потерю
mysql -e "SET GLOBAL innodb_fast_shutdown = 0;"
systemctl stop mysql
# Если сервер не стартует вовсе — остановка уже факта, переходите к rm.

# MySQL 8.0.30+: redo в отдельном каталоге
rm -rf /var/lib/mysql/#innodb_redo

# MySQL 5.7: два фиксированных файла
rm -f /var/lib/mysql/ib_logfile0 /var/lib/mysql/ib_logfile1

# Убираем аварийный режим
rm -f /etc/mysql/mysql.conf.d/emergency.cnf

systemctl start mysql
sleep 10
systemctl is-active mysql
# → active
```

```bash
journalctl -u mysql -n 20 --no-pager | grep -i "redo\|InnoDB"
# → InnoDB: Starting recovery after a crash
# → InnoDB: Recovery has completed
```

> **Цена решения:** удаление redo log означает, что все изменения, не записанные в файлы данных, теряются безвозвратно. Данные могут откатиться на состояние последнего чекпойнта — то есть потеря может измеряться минутами или часами активности. Это причина, по которой процедура идёт **после** снятия копии и **после** попыток с уровнями 1–3.

### Сценарий 9: Возврат в эксплуатацию

```bash
# 1. Убедиться, что аварийный режим снят
grep -r "innodb_force_recovery" /etc/mysql/ 2>/dev/null
# → (пусто)
grep -r "skip-networking" /etc/mysql/ 2>/dev/null
# → (пусто)
```

```bash
# 2. Проверка целостности InnoDB
#    EXTENDED для InnoDB игнорируется (применим только к MyISAM) —
#    plain CHECK TABLE делает полный проход по индексам
mysql -e "CHECK TABLE mydb.users, mydb.orders, mydb.sessions;"
# → ... status  OK
```

> **Кавеат `CHECK TABLE` на InnoDB:** при встрече с повреждённой страницей сервер **завершает работу**, чтобы не распространять повреждение. На подозрительных таблицах `CHECK TABLE` не запускайте — сначала `innochecksum` по файлам (ниже) или чтение из бэкапа.

```bash
# 3. Файловая проверка .ibd на forensic-копии (innochecksum не работает
#    с открытыми сервером файлами — копия идеальна для этого)
innochecksum --strict-check=innodb /var/lib/mysql.forensic.2026-10-03/mydb/*.ibd
# → (мismatch'и отсутствуют → вывод без ошибок)
# → при mismatch'ах: страница повреждена, восстанавливайте tablespace из бэкапа
```

```bash
# 4. Валидация rescued-дампа — восстановите его на отдельном инстансе
#    и сверьте число таблиц и строк с картой повреждений
zstd -dc /tmp/rescued_2026-10-03_0440.sql.zst | mysql -h scratch-host
mysql -h scratch-host -N -B -e "SELECT COUNT(*) FROM mydb.users;"
# → 152834   ← совпадает с сценарием 3: дамп полный
```

```bash
# 5. Первое полноценное тестовое восстановление из свежего бэкапа —
#    резервная копия текущего состояния, снятого после аварии
xtrabackup --backup --target-dir=/backups/post-incident-$(date +%F)
# → MySQL binlog position: filename 'binlog.000045', position '1540'
#    (та же позиция записана в файл xtrabackup_binlog_info в target-dir)
```

```bash
# 6. Очистка: forensic-копии занимают место (каждая = полный datadir)
du -sh /var/lib/mysql.forensic.* /var/lib/mysql.broken
rm -rf /var/lib/mysql.broken          # после закрытия инцидента и
rm -rf /var/lib/mysql.forensic.2026-10-03   # успешной валидации дампа
```

> **Важно:** восстановленный инстанс нельзя считать надёжным, пока не устранена причина. Если `smartctl` показал ошибки диска, `fsck` — повреждения, а `error.log` — ошибки записи, то повторное повреждение лишь вопрос времени. Признайте инцидент открытым до замены хранилища и успешного тестового восстановления.

## Устранение неполадок

| Симптом / ошибка | Причина | Действие |
| :--- | :--- | :--- |
| `Plugin 'InnoDB' init function returned error` при старте | повреждён redo log или системные страницы | шаги 1–4; `innodb_force_recovery` по уровням от 1 |
| `[ERROR] [MY-012153] [InnoDB] Trying to access page number ... outside the tablespace bounds` | повреждение tablespace; несоответствие `my.cnf` составу `ibdata*` | сверить конфигурацию с файлами; работать на forensic-копии |
| `[ERROR] [MY-013183] [InnoDB] Assertion failure` | внутренняя проверка InnoDB не прошла (часто следствие той же коррупции) | копия → дамп; assertion с repeat'ом — материал для баг-репорта |
| `InnoDB: Unable to lock ./ibdata1` | второй экземпляр `mysqld` уже держит файлы или не завершился | `pgrep -a mysqld`; дождаться полной остановки |
| Сервер отказывается стартовать, в логе ссылки на потерянные `*.ibd` | tablespace discovery: redo ссылается на отсутствующий файл | аварийный режим игнорирует отсутствующие `.ibd`; затем `DROP TABLE` (сценарий 6) |
| `ERROR 1812` / `ERROR 1814 (HY000): Tablespace is missing / has been discarded` | `.ibd` удалён или discard'ed, запись осталась в словаре | вернуть файл на место либо `DROP TABLE` + восстановление из бэкапа |
| `mysqldump: Error 2013: Lost connection ... during query` | сервер упал, читая повреждённую страницу | исключить таблицу (`--ignore-table`); попробовать `ORDER BY primary_key DESC` |
| Откат длится часами после краша | большая незавершённая транзакция (откат в 3–4 раза дольше самой транзакции) | сценарий 5: kill → `innodb_force_recovery=3` → `DROP TABLE` |
| `ERROR 1874 (HY000): Changes to undo tablespaces are not allowed in force_recovery mode` | DDL над undo tablespace в аварийном режиме | снять аварийный режим, выполнить штатно |
| `CHECK TABLE` падает сервер | InnoDB выходит, чтобы не распространять повреждение | не запускать `CHECK TABLE` на подозрительных таблицах; `innochecksum` на копии |
| `innochecksum: Unable to lock file` | сервер уже открыл этот tablespace | запускать `innochecksum` только на остановленном сервере или на копии |

## Бест-практиси

1. **Снимите холодную копию каталога данных до любых действий.** Это единственная точка невозврата; всё остальное можно повторить.
2. **Снимите приложения с базы** до начала работы. Запись на повреждённый инстанс усугубляет потери.
3. **Поднимайте `innodb_force_recovery` по одному уровню за раз,** начиная с 1. Никогда не начинайте с 4+. Уровни ≥ 4 предварительно тестируйте на отдельной физической копии базы.
4. **Никогда не пишите на сервер с `innodb_force_recovery > 0`.** `INSERT`/`UPDATE`/`DELETE` запрещены InnoDB при любом уровне; `DROP`/`CREATE TABLE` — только на уровнях ≤ 3, `DROP TABLE` — до 4 включительно, и только если это часть процедуры (сценарий 5).
5. **Отключите сеть** (`skip-networking`) на аварийном инстансе, чтобы исключить подключения приложений.
6. **Постройте карту повреждений** перебором таблиц и сохраните её как артефакт инцидента.
7. **Извлекайте дампом только читаемые таблицы** через `--ignore-table` (или `--ignore-error` с контролем stderr); иначе дамп прервётся на первой повреждённой.
8. **Проверьте rescued-дамп на отдельном инстансе** до объявления инцидента закрытым.
9. **Определите первопричину** (SMART, fsck, лог) до возврата в продакшен — иначе инцидент повторится.
10. **Не удаляйте redo log**, пока не снята копия, не оценён масштаб потери несохранённых изменений и не выполнен clean shutdown (`innodb_fast_shutdown=0`).
11. **Отключите аварийную конфигурацию** перед возвратом в эксплуатацию — иначе следующий сбой пройдёт в том же режиме.
12. **Удалите forensic-копии** после закрытия инцидента — каждая занимает столько же, сколько весь `datadir`.
