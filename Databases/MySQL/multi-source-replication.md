# MySQL: Репликация Multi-Source (Multi-Master)

## Определения

**Репликация Multi-Source** — это топология репликации в MySQL/MariaDB, при которой один slave-сервер может принимать данные от нескольких master-серверов одновременно. Это достигается созданием отдельных каналов репликации для каждого мастера.

**Репликация Multi-Master** — более общее понятие, описывающее конфигурацию, где несколько узлов в кластере могут принимать запросы на запись. Multi-Source является технологической основой для построения некоторых видов Multi-Master кластеров. В контексте асинхронной репликации, "активный" Multi-Master (где запись идет на все узлы) **крайне не рекомендуется** из-за риска конфликтов и рассинхронизации данных. Безопасной схемой является "пассивный" Multi-Master, где запись всегда идет только на один узел, а остальные находятся в режиме ожидания.

## Базовые концепции

### 1. Топология "Кольцо" или "Треугольник"

В отличие от классической схемы Master-Slave, Multi-Source позволяет строить более сложные топологии. Например, кольцевую репликацию, где каждый узел является мастером для следующего и слейвом для предыдущего (N1 -> N2 -> N3 -> N1). Это создает отказоустойчивую, но потенциально сложную в управлении систему.

```text
      +------------------+
      |      Node 1      |
      | (Master, Slave)  |
      +--------+---------+
               |
      Binlog   |   Binlog
     (to N2)   ^   (from N3)
               |
      +--------v---------+
      |      Node 2      |
      | (Master, Slave)  |
      +--------+---------+
               |
      Binlog   |   Binlog
     (to N3)   ^   (from N1)
               |
      +--------v---------+
      |      Node 3      |
      | (Master, Slave)  |
      +------------------+
```

### 2. Проблема конфликтов записи и GTID

При асинхронной репликации, если два разных клиента одновременно запишут данные в одну и ту же таблицу на разных узлах, возникнет конфликт, который стандартными средствами не разрешается. Это приведет к остановке репликации или, что хуже, к незаметной рассинхронизации данных.

Для предотвращения "зацикливания" одних и тех же транзакций в кольце используется **GTID (Global Transaction ID)**. Каждый сервер имеет уникальный `server-id`, и каждая транзакция помечается этим ID. Когда транзакция "возвращается" на породивший ее узел, он видит свой `server-id` и игнорирует ее, предотвращая бесконечный цикл. Дополнительно, опция `gtid_ignore_duplicates=ON` (в MariaDB) или `replicate_same_server_id=OFF` (в MySQL) помогает управлять этим поведением.

### 3. Отказоустойчивость с помощью плавающего IP (VIP)

Чтобы избежать конфликтов записи, используется подход с **единой точкой входа**. Все пишущие клиенты обращаются к одному **виртуальному IP-адресу (VIP)**, который в любой момент времени активен только на одном узле кластера.

- **Инструмент**: `keepalived`.
- **Принцип работы**: Демон `keepalived` на всех узлах "общаются" друг с другом. Тот узел, у которого наивысший приоритет (или который был выбран "мастером"), назначает себе VIP.
- **Отказоустойчивость**: Если текущий мастер с VIP-адресом становится недоступен (перестает отвечать на heart-beat пакеты или проваливает проверку здоровья сервиса), другой узел "захватывает" VIP-адрес на себя. Клиентские приложения кратковременно теряют соединение, но после переподключения по тому же IP-адресу попадают уже на новый активный узел.

### 4. Проблема Split-Brain и Кворум

- **Split-Brain**: Ситуация, когда из-за проблем с сетью кластер разделяется на несколько изолированных частей, и каждая часть считает себя основной (например, в каждой части поднимается свой VIP). Это приводит к катастрофической рассинхронизации данных.
- **Кворум**: Механизм защиты, который гласит, что узел может стать мастером, только если он "видит" большинство (50% + 1) других узлов кластера.
- **Ограничение**: `keepalived` "из коробки" не имеет встроенного механизма кворума. В конфигурации из двух узлов он бессилен против split-brain. Для надежной защиты в `keepalived` необходимо реализовывать логику кворума с помощью **внешних проверочных скриптов**, которые будут анализировать доступность соседей.

## Практические сценарии

### Настройка 3-узловой Multi-Source репликации (кольцо)

#### Шаг 1: Конфигурация `my.cnf`

На каждом из трех узлов в секции `[mysqld]` (или `[mariadb]`) нужно добавить/изменить параметры. Конфигурация должна быть идентичной, **кроме `server-id`**.

```ini
[mysqld]
# 1. Уникальный ID для каждого сервера
server-id = 1 # (на втором - 2, на третьем - 3)

# 2. Включение бинарного лога и использование GTID
log_bin             = /var/log/mysql/mysql-bin.log
gtid_domain_id      = 1 # (Одинаковый на всех узлах, если это один кластер)
enforce_gtid_consistency = ON
gtid_mode           = ON

# 3. Формат лога и предотвращение зацикливания
binlog_format       = ROW
# Для MariaDB:
gtid_ignore_duplicates = ON 
# Для MySQL:
# replicate_same_server_id = OFF (по умолчанию)
```

*После изменения перезапустите сервис MySQL/MariaDB на всех узлах.*

#### Шаг 2: Создание пользователя для репликации

На **одном из узлов** создайте пользователя, который будет использоваться для репликации. Благодаря репликации, он автоматически появится на других узлах.

```sql
CREATE USER 'repl_user'@'%' IDENTIFIED BY 'your_password';
GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'%';
FLUSH PRIVILEGES;
```

#### Шаг 3: Настройка каналов репликации

На каждом узле нужно настроить два канала репликации: от двух других "мастеров".

**На Узле 1 (server-id=1):**

```sql
-- Канал от Узла 2
CHANGE MASTER TO 
  MASTER_HOST='<ip_node_2>', 
  MASTER_USER='repl_user', 
  MASTER_PASSWORD='your_password', 
  MASTER_USE_GTID=slave_pos
FOR CHANNEL 'node2';

-- Канал от Узла 3
CHANGE MASTER TO 
  MASTER_HOST='<ip_node_3>', 
  MASTER_USER='repl_user', 
  MASTER_PASSWORD='your_password', 
  MASTER_USE_GTID=slave_pos
FOR CHANNEL 'node3';
```

**На Узле 2 (server-id=2):**

```sql
-- Настроить каналы от Узла 1 ('node1') и Узла 3 ('node3')
... FOR CHANNEL 'node1';
... FOR CHANNEL 'node3';
```

**На Узле 3 (server-id=3):**

```sql
-- Настроить каналы от Узла 1 ('node1') и Узла 2 ('node2')
... FOR CHANNEL 'node1';
... FOR CHANNEL 'node2';
```

#### Шаг 4: Запуск и проверка

На каждом узле запустите все настроенные каналы:

```sql
START SLAVE FOR CHANNEL 'nodeX';
START SLAVE FOR CHANNEL 'nodeY';
```

Проверка статуса для конкретного канала:

```sql
SHOW SLAVE 'nodeX' STATUS\G
```

Убедитесь, что `Slave_IO_Running: Yes` и `Slave_SQL_Running: Yes` для всех каналов на всех узлах.

### Настройка плавающего IP с помощью `keepalived`

#### Шаг 1: Установка `keepalived`

```bash
sudo apt install keepalived
```

#### Шаг 2: Конфигурация `keepalived.conf`

Создайте `/etc/keepalived/keepalived.conf`. Конфиг на всех узлах может быть почти идентичным, за исключением `priority` (у мастера он должен быть выше) и `state` (у мастера `MASTER`, у остальных `BACKUP`).

```conf
global_defs {
   router_id MYSQL_HA
}

# Скрипт для проверки, жив ли локальный сервис MySQL
vrrp_script chk_mysql {
    script "/usr/bin/killall -0 mysqld" # Простая проверка, что процесс существует
    interval 2
    fall 2
    rise 2
}

vrrp_instance VI_1 {
    state MASTER # На одном узле MASTER, на других BACKUP
    interface ens3 # Ваш сетевой интерфейс
    virtual_router_id 51 # Должен быть одинаковым на всех узлах
    priority 101 # У MASTER - выше (напр. 101), у BACKUP - ниже (напр. 100)
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111 # Простой пароль для группы
    }

    # VIP-адрес
    virtual_ipaddress {
        192.168.1.100/24
    }

    # Применение скрипта проверки
    track_script {
        chk_mysql
    }
}
```

#### Шаг 3: Запуск сервиса

```bash
sudo systemctl enable keepalived
sudo systemctl start keepalived
```

После запуска проверьте, что VIP-адрес (`192.168.1.100`) появился на узле с состоянием `MASTER` с помощью команды `ip addr`.

## Дополнительная информация

- **Отладка GTID**: Если репликация не запускается из-за расхождения позиций GTID, может потребоваться ручная синхронизация. Это делается путем остановки репликации (`STOP SLAVE`), установки нужной позиции с помощью `SET GLOBAL gtid_slave_pos = "..."`, и перезапуска.
- **Альтернативы**: Для построения надежных Multi-Master кластеров часто используют решения с **синхронной репликацией**, такие как **Galera Cluster** (Percona XtraDB Cluster, MariaDB Galera Cluster). Они решают проблему конфликтов на уровне протокола, но ценой более высоких задержек при записи.
- **[Стандартная репликация Master-Slave](./replication.md)**: Основа, которую полезно понимать перед настройкой более сложных топологий.
