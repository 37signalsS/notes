# Управление и отладка репликации в MySQL

## Определения

**Диагностика репликации** — комплекс мероприятий по мониторингу состояния потоков данных, анализу ошибок и измерению задержек (лага) между источником и репликами.

**Отставание репликации (Replication Lag)** — разрыв во времени между фиксацией транзакции на источнике и её применением на реплике. 

**MTS (Multi-Threaded Slave)** — механизм параллельного применения транзакций на реплике несколькими потоками (воркерами) для снижения лага.

**Crash-Safe Replication** — конфигурация репликации, гарантирующая сохранность позиции и консистентность метаданных после внезапной остановки сервера.

## Основные концепции

### Потоки репликации

Процесс обслуживается тремя основными потоками:

| Поток | Расположение | Задача |
| :--- | :--- | :--- |
| **I/O-поток (Receiver)** | Реплика | Подключается к источнику, запрашивает события binlog и записывает их в локальный **Relay Log**. |
| **SQL-поток (Applier)** | Реплика | Читает события из Relay Log и последовательно (или параллельно через MTS) применяет их к данным. |
| **Binlog Dump** | Источник | Читает бинарный лог и отправляет события подключенным репликам. |

### Проблема точности Seconds_Behind_Source

Показатель `Seconds_Behind_Source` (ранее `Seconds_Behind_Master`) часто вводит в заблуждение:
- **Как считается:** Разница между временной меткой транзакции, которая сейчас выполняется SQL-потоком, и текущим временем.
- **Когда врет:** 
  - Если I/O-поток остановлен, значение может быть `NULL` или `0`, хотя данных на реплике нет.
  - Если SQL-поток занят одной очень длинной транзакцией, лаг будет расти рывками.
  - При медленной сети I/O-поток не успевает скачивать логи, и лаг на уровне SQL-потока может быть `0`, хотя реплика фактически отстает от источника.
- **Решение:** 
  - Проверка `Performance Schema` (метрики задержки на уровне соединений).
  - Использование `pt-heartbeat` для записи реальных меток времени на источнике.
  - Настройка `SOURCE_HEARTBEAT_PERIOD` (в `CHANGE REPLICATION SOURCE TO`) для поддержания активности соединения.

## Практические сценарии

### 1. Управление репликацией (MySQL 8.0+)

```sql
-- Полный запуск и остановка
START REPLICA;
STOP REPLICA;

-- Управление конкретными потоками
START REPLICA IO_THREAD;  -- Только скачивание логов
START REPLICA SQL_THREAD; -- Только применение данных

-- Просмотр статуса (основной инструмент)
SHOW REPLICA STATUS\G
```

### 2. Типовые ошибки и их решение

#### Ошибка 1062 (Duplicate entry)
Данные уже существуют на реплике.
- **Причина:** Прямая запись на реплику (`read_only=OFF`) или рассинхронизация.
- **Решение:** 
  1. Найти конфликтующую строку по сообщению об ошибке.
  2. Удалить строку на реплике или пропустить транзакцию (через пустой GTID).

#### Ошибка 1032 (Can't find record)
Запись для обновления или удаления не найдена.
- **Причина:** Строка была удалена на реплике вручную.
- **Решение:** Вставить недостающую строку на реплику или пропустить транзакцию.

#### Пропуск транзакции (GTID режим)
```sql
STOP REPLICA;
-- Узнаем ID из поля Last_SQL_Error (например, 'uuid:N')
SET GTID_NEXT='3E11FA47-71CA-11E1-9E33-C80AA9429562:542';
BEGIN; COMMIT;
SET GTID_NEXT='AUTOMATIC';
START REPLICA;
```

#### Проблема "Replica_IO_Running: Connecting"
- **DNS:** Проверьте доступность по имени хоста.
- **Firewall:** Проверьте порт 3306 (`nc -zv source_ip 3306`).
- **UUID/ServerID:** Убедитесь, что `server_id` и `server_uuid` уникальны для всех узлов.
- **User/Pass:** Проверьте права пользователя `REPLICATION SLAVE`.

### 3. Отладка параллельной репликации (MTS)

Если SQL-поток не успевает (лаг растет), проверьте распределение нагрузки по воркерам:

```sql
-- Статус воркеров
SELECT CHANNEL_NAME, WORKER_ID, LAST_APPLIED_TRANSACTION, LAST_ERROR_NUMBER, LAST_ERROR_MESSAGE
FROM performance_schema.replication_applier_status_by_worker
WHERE SERVICE_STATE = 'ON';
```

**Оптимизация:**
- Если работает только один воркер — проверьте `replica_parallel_type`. Для MySQL 8.0 используйте `LOGICAL_CLOCK`.
- Увеличьте `replica_parallel_workers` (обычно 2-4 на каждое ядро CPU).
- Включите `replica_preserve_commit_order = ON` для сохранения порядка транзакций.

### 4. Проверка консистентности (Percona Toolkit)

Стандартные инструменты MySQL не умеют проверять идентичность данных. 

```bash
# 1. Проверка контрольных сумм (запускается на источнике)
# Параметр --replicate создает таблицу percona.checksums и пишет туда результаты
pt-table-checksum --replicate=percona.checksums --host=source_host --user=root

# 2. Поиск и исправление расхождений (запускается на реплике или источнике)
pt-table-sync --execute --replicate=percona.checksums h=source_host,u=root h=replica_host
```

## Дополнительная информация

### Глубокий мониторинг через Performance Schema

В MySQL 8.0 Performance Schema является SSoT для метрик репликации.

```sql
-- Задержка применения транзакций (Lag)
SELECT CHANNEL_NAME, 
       LAST_QUEUED_TRANSACTION_START_LOG_POS, 
       LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP - LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP AS lag_seconds
FROM performance_schema.replication_applier_status_by_coordinator;

-- Состояние I/O потока и сетевые задержки
SELECT * FROM performance_schema.replication_connection_status\G
```

### Рекомендации по Crash-Safety

Для предотвращения повреждения репликации при внезапном выключении (Hard Reboot):

1. **Репозитории в таблицах:** 
   ```ini
   master_info_repository = TABLE
   relay_log_info_repository = TABLE
   ```
2. **Восстановление Relay Log:**
   ```ini
   relay_log_recovery = ON
   ```
   *При запуске реплика удаляет старые Relay Logs и скачивает их заново с источника, основываясь на последней подтвержденной позиции в БД.*
3. **Синхронизация логов:**
   ```ini
   sync_binlog = 1
   innodb_flush_log_at_trx_commit = 1
   ```

### Очистка бинарных логов
Если диск переполнен бинлогами, никогда не удаляйте их через `rm`.
- Используйте: `PURGE BINARY LOGS TO 'mysql-bin.000123';`
- Или: `PURGE BINARY LOGS BEFORE '2024-05-01 00:00:00';`
- Настройте автоматическую очистку: `binlog_expire_logs_seconds = 604800` (7 дней).
