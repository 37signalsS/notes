# Управление и отладка репликации в MySQL

**Актуально для:** MySQL 5.1+ / 5.7 / 8.0+ / 8.4 LTS

## Определения

**Диагностика репликации** — комплекс мероприятий по мониторингу состояния потоков данных, анализу ошибок и измерению задержек (лага) между источником и репликами.

**Отставание репликации (Replication Lag)** — временной разрыв между моментом фиксации транзакции на источнике и моментом завершения её применения на реплике.

**MTS (Multi-Threaded Slave)** — механизм параллельного применения транзакций на реплике несколькими потоками (воркерами). Позволяет эффективно использовать многоядерные процессоры и преодолевать бутылочное горлышко однопоточной записи.

**Crash-Safe Replication** — конфигурация, при которой метаданные репликации (позиции в логах) хранятся в транзакционных InnoDB таблицах. Это гарантирует атомарность обновления данных и позиций, предотвращая расхождения после аварийного завершения работы сервера.

## Предварительные требования

### Версии MySQL

- **Минимальная версия:** Базовая репликация доступна с MySQL 3.23. MTS (Multi-Threaded Slave) — с MySQL 5.6, значительно улучшена в 5.7 и 8.0.
- **Рекомендуемые версии:** Для production используйте MySQL 8.0+ или 8.4 LTS. На этих версиях доступны современные команды (`START REPLICA` вместо `START SLAVE`), Performance Schema метрики и улучшенный MTS.
- **Совместимость источников и реплик:** Источник и реплика могут работать на разных минорных версиях в рамках одной major-версии. Миграция с 5.7 на 8.0 требует проверки формата binlog и GTID-совместимости.

### Привилегии

Для полного управления репликацией требуются следующие привилегии:

- **`REPLICATION SLAVE`** — на реплике, для подключения к источнику и чтения binlog.
- **`REPLICATION CLIENT`** — для выполнения `SHOW REPLICA STATUS`, `SHOW BINARY LOG STATUS` (в MySQL 5.7 и 8.0 — `SHOW MASTER STATUS`).
- **`SELECT` на `performance_schema`** — для диагностики лага и состояния воркеров.
- **`SUPER` или `SYSTEM_VARIABLES_ADMIN`** — для изменения `super_read_only` и других динамических системных переменных на лету (MySQL 8.0+). `relay_log_recovery` и `relay_log_space_limit` — не динамические: только `my.cnf` + рестарт (`relay_logs_crashsafe.md`).
- **`FILE`** — для использования `mysqlbinlog` на хосте, где хранятся binlog-файлы.

### Конфигурационные требования

- **Crash-Safe репозитории:** В MySQL 5.6/5.7 параметры `master_info_repository` и `relay_log_info_repository` по умолчанию равны `FILE` — установите `TABLE` явно в `my.cnf`. С MySQL 8.0 дефолт `TABLE` (deprecated с 8.0.23). Обе переменные **удалены в MySQL 8.3.0** — на 8.4 LTS настройка не требуется.
- **`relay_log_recovery = ON`** — обязательно для автоматического восстановления Relay Log после сбоя реплики.
- **Сеть:** Убедитесь, что порт 3306 открыт между источником и репликой. Для SSL-репликации требуется отдельный порт или настройка `require_secure_transport = ON`.
- **Дисковое пространство:** На реплике должно быть достаточно места для Relay Log (рекомендуется отдельный диск или LVM-том). Размер `relay_log_space_limit` должен превышать ожидаемый объем binlog за время возможного лага.

### Зависимости

- **Percona Toolkit:** Для проверки консистентности требуется установка `pt-table-checksum` и `pt-table-sync` на хосте с доступом к источнику.
- **Performance Schema:** В MySQL 8.0+ включена по умолчанию. На 5.7 может потребоваться `performance_schema = ON` в `my.cnf` для доступа к метрикам репликации.
- **NTP:** На источнике и реплике должен быть синхронизирован системный тайм. Постоянная разница часов сама по себе не ломает расчёт `Seconds_Behind_Source`, но корректировки NTP вносят clock skew и снижают его надёжность (детали — `./lag_monitoring.md`).

## Основные концепции

### Потоки репликации и их взаимодействие

В современной репликации (MySQL 8.0+) процесс обслуживается следующими ключевыми потоками:

| Поток | Узел | Задача |
| :--- | :--- | :--- |
| **I/O-поток (Receiver)** | Реплика | Подключается к источнику, запрашивает события через `COM_BINLOG_DUMP` и сохраняет их в локальный **Relay Log**. |
| **Binlog Dump** | Источник | Считывает события из бинарного лога по запросу реплики и отправляет их по сети. |
| **SQL-поток (Coordinator)** | Реплика | Читает Relay Log. В классическом режиме применяет транзакции сам. В MTS — распределяет транзакции между воркерами, следя за зависимостями. |
| **Worker Threads** | Реплика | (Только в MTS) Потоки, непосредственно выполняющие транзакции в базе данных. |

**Механизм переподключения:**

Параметры `SOURCE_RETRY_COUNT` и `SOURCE_CONNECT_RETRY` (устанавливаются в `CHANGE REPLICATION SOURCE TO`) определяют поведение I/O-потока при обрыве связи. Первый таймаут определяется системной переменной `replica_net_timeout` (60 секунд по умолчанию), после чего I/O-поток начинает повторные попытки с интервалом `SOURCE_CONNECT_RETRY`, но не более `SOURCE_RETRY_COUNT` раз. Значение `SOURCE_RETRY_COUNT = 0` означает бесконечные попытки.

> **Версии — значение по умолчанию для `SOURCE_RETRY_COUNT` изменилось:**

| Версия | `SOURCE_RETRY_COUNT` по умолчанию | Суммарное время попыток при `SOURCE_CONNECT_RETRY = 60` |
| :--- | :--- | :--- |
| MySQL 8.0 (и `MASTER_RETRY_COUNT`) | `86400` | 60 дней |
| MySQL 8.4 (`SOURCE_RETRY_COUNT`) | `10` | 10 минут |

`SOURCE_CONNECT_RETRY` по умолчанию равен 60 секунд во всех версиях.

Практическое следствие: **реплика, обновлённая с 8.0 до 8.4, начинает отказываться от реконнекта через 10 минут вместо 60 дней.** Если узел возвращается в строй позже (долгая переустановка, ожидание кворума, замороженный контейнер), реплика останется в состоянии `Replica_IO_Running: Connecting`, пока её не перезапустят вручную или пока сработает внешний оркестратор.

Практическая настройка для production — задать значения явно, а не полагаться на дефолт:

```sql
-- На реплике: не сдаваться 7 суток, переподключаясь каждые 10 секунд
CHANGE REPLICATION SOURCE TO
  SOURCE_RETRY_COUNT = 0,       -- бесконечные попытки
  SOURCE_CONNECT_RETRY = 10;
```

> **Версии — имена опций.** На MySQL до 8.0.23 опции назывались `MASTER_*` (`MASTER_RETRY_COUNT`, `MASTER_CONNECT_RETRY`, `MASTER_AUTO_POSITION`). С 8.0.23 доступны `SOURCE_*`; старые имена `CHANGE MASTER TO` объявлены deprecated. В MySQL 5.7 существуют только `MASTER_*`.

Текущие значения видны в Performance Schema — этот источник надёжнее, чем `SHOW REPLICA STATUS`, и не требует разбора вывода:

```sql
SELECT CHANNEL_NAME, SOURCE_HOST, SOURCE_CONNECT_RETRY, SOURCE_RETRY_COUNT
FROM performance_schema.replication_connection_configuration\G
```

### Проблема точности Seconds_Behind_Source

`Seconds_Behind_Source` — лишь *косвенный* индикатор лага. Полный разбор алгоритма расчёта, семантики `NULL`/`0`, ложных срабатываний и штатных альтернатив (Performance Schema, `pt-heartbeat`) — в [Мониторинг отставания репликации](./lag_monitoring.md).

## Практические сценарии

### 1. Управление репликацией (MySQL 8.0+)

```sql
-- Полный запуск и остановка всех потоков
START REPLICA;
STOP REPLICA;

-- Управление конкретными потоками (полезно при отладке I/O или SQL части)
START REPLICA IO_THREAD;  -- Начать только скачивание логов
STOP REPLICA SQL_THREAD;  -- Приостановить применение (например, для снятия бэкапа)

-- Просмотр детального статуса
SHOW REPLICA STATUS\G
```

### 2. Типовые ошибки и их решение

#### Ошибка 1062 (Duplicate entry) / 1022 (Can't write; duplicate key)
Данные уже существуют на реплике.
- **Причина:** Прямая запись на реплику (`read_only=OFF`), рассинхронизация после сбоя или некорректная фильтрация.
- **Решение:** 
  1. Найти конфликтующую строку: `SELECT * FROM table WHERE id = ...;`
  2. Если данные на реплике верны — удалите их или пропустите транзакцию.
  3. Включите `super_read_only = ON` для предотвращения рецидивов.

#### Ошибка 1032 (Can't find record)
Запись для обновления или удаления отсутствует на реплике.
- **Причина:** Ручное удаление данных на реплике или сбой консистентности.
- **Решение:** Вставьте недостающую строку вручную или пропустите транзакцию (если данные на источнике признаны неактуальными).

#### Ошибка SSL (Authentication failure)
`Replica_IO_Running: Connecting` с ошибкой `SSL connection error`.
- **Диагностика:** Проверьте `REQUIRE SSL` у пользователя репликации и наличие валидных сертификатов.
- **Решение:** `CHANGE REPLICATION SOURCE TO SOURCE_SSL = 1, SOURCE_SSL_CA = '...', ...;`

#### Дубликат UUID (Fatal error 1593)
`Fatal error: The slave I/O thread stops because source and slave have equal MySQL server UUIDs`.
- **Причина:** Реплика была создана физическим копированием (бэкапом) источника, включая файл `auto.cnf`.
- **Решение:** 
  1. Удалите файл `auto.cnf` в data-директории реплики.
  2. Перезапустите MySQL (новый UUID сгенерируется автоматически).

#### Переполнение Relay Log (Disk Full)
- **Симптом:** SQL-поток работает, но I/O-поток стоит с ошибкой записи.
- **Решение:** 
  - Проверьте параметр `relay_log_space_limit`. Если он установлен — увеличьте его или проверьте, почему SQL-поток не успевает удалять старые логи.
  - Никогда не удаляйте Relay Logs вручную! Используйте `STOP REPLICA; RESET REPLICA;` (внимание: это сбросит позицию, если не используется GTID).

#### Пропуск транзакции (GTID режим)
Никогда не используйте `sql_slave_skip_counter` (8.0.18+ — `sql_replica_skip_counter`) в режиме GTID: оператор отклоняется при `gtid_mode=ON`. Вместо этого вставьте "пустую" транзакцию:

```sql
STOP REPLICA;
-- 1. Определяем UUID:ID из Last_SQL_Error (при MTS — из APPLYING_TRANSACTION в performance_schema.replication_applier_status_by_worker)
-- 2. "Выполняем" пустую транзакцию с этим ID
SET GTID_NEXT='3E11FA47-71CA-11E1-9E33-C80AA9429562:542';
BEGIN; COMMIT;
-- 3. Возвращаем автоматический режим
SET GTID_NEXT='AUTOMATIC';
START REPLICA;
```

Если на реплике включён бинарный лог и она может стать источником в будущем, пустая транзакция попадёт в поток репликации — во избежание: `FLUSH LOGS; PURGE BINARY LOGS TO 'binlog.000146';`. Полная методика пропуска (включая без-GTID варианты) — **[Обработка ошибок SQL-потока](./replication_sql_errors.md)**.

### 3. Отладка параллельной репликации (MTS)

Если при наличии MTS лаг всё равно растет, проверьте, не упираетесь ли вы в **Commit Order**.

```sql
-- Проверка: сколько воркеров реально занято работой
SELECT * FROM performance_schema.replication_applier_status_by_worker 
WHERE SERVICE_STATE = 'ON';
```

**Оптимизация:**
- **replica_parallel_type:** Убедитесь, что установлено `LOGICAL_CLOCK`. Устаревший `DATABASE` параллелит только транзакции в разных БД.
- **replica_preserve_commit_order:** Включите (`ON`), чтобы транзакции фиксировались на реплике в том же порядке, что и на источнике. Это необходимо для консистентности, но может снижать параллелизм.
- **replica_checkpoint_group:** Увеличьте это значение, если координатор создает слишком много мелких чекпоинтов.

### 4. Проверка консистентности (Percona Toolkit)

Стандартные инструменты MySQL не могут гарантировать, что данные на источнике и реплике идентичны. Полная методика, опции и диагностика — **[Проверка консистентности репликации](./consistency_checks.md)**.

```bash
# 1. Проверка (Checksumming)
# Создает таблицу percona.checksums на источнике и сравнивает хеши блоков данных
pt-table-checksum --replicate=percona.checksums h=source_host,u=root

# 2. Исправление (Syncing)
# Применяет no-op REPLACE на источнике; изменения реплицируются на реплику
pt-table-sync --execute --replicate percona.checksums h=source_host,u=root
```

## Валидация

### Статус репликации: SHOW REPLICA STATUS

Ключевые поля для проверки здоровья репликации (MySQL 8.0+):

```sql
SHOW REPLICA STATUS\G
```

| Поле | Значение | Интерпретация |
| :--- | :--- | :--- |
| `Replica_IO_Running` | `Yes` | I/O-поток подключен к источнику и скачивает binlog. |
| `Replica_SQL_Running` | `Yes` | SQL-поток применяет транзакции из Relay Log. |
| `Seconds_Behind_Source` | `0` или `NULL` | `NULL` означает остановку потоков. `0` не гарантирует отсутствие лага (см. `./lag_monitoring.md`). |
| `Last_IO_Errno` / `Last_SQL_Errno` | `0` | Отсутствие ошибок. Любое ненулевое значение требует диагностики. Поле `Last_Error_Number` существует только в Performance Schema, в выводе `SHOW REPLICA STATUS` его нет. |
| `Last_SQL_Error` | пусто | Описание последней ошибки SQL-потока. |
| `Source_UUID` | UUID | Должен совпадать с `SELECT @@server_uuid;` на источнике. |
| `Auto_Position` | `1` | GTID-автопозиционирование активно. |
| `Retrieved_Gtid_Set` | GTID-набор | GTID, которые реплика уже получила от источника. |
| `Executed_Gtid_Set` | GTID-набор | GTID, которые реплика уже применила. |

### Точный мониторинг лага через Performance Schema

Запросы к `replication_applier_status_by_worker` (лаг по меткам коммита/применения), `replication_applier_status_by_coordinator`, `replication_connection_status` и `replication_applier_status` — в [Мониторинг отставания репликации](./lag_monitoring.md).

### Мониторинг через pt-heartbeat

Установка heartbeat-таблицы (`--create-table`), запуск `--update`/`--monitor`/`--check`, каскадные топологии (`--source-server-id`), интерпретация отрицательного лага и интеграция с `mysqld_exporter --collect.heartbeat` — в [Мониторинг отставания репликации](./lag_monitoring.md).

### Проверка сетевого подключения

```bash
# Проверка доступности порта 3306
nc -zv source_host 3306

# Проверка SSL-подключения (если используется)
openssl s_client -connect source_host:3306 --servername source_host
```

### Проверка консистентности данных

```bash
# Проверка (суммы пишутся в percona.checksums на источнике; dry-run — см. --explain)
pt-table-checksum --replicate=percona.checksums h=source_host,u=root

# Если найдены расхождения — синхронизация через источник (не на реплику напрямую)
pt-table-sync --execute --replicate percona.checksums h=source_host,u=root
```

Методика, безопасное применение и диагностика — **[Проверка консистентности репликации](./consistency_checks.md)**.

## Устранение неисправностей

### Сетевой таймаут / обрыв связи (I/O-поток в состоянии "Connecting")

- **Симптом:** `Replica_IO_Running: Connecting`, `Last_IO_Error: error reconnecting to source`.
- **Причины:** 
  - Брандмауэр блокирует порт 3306.
  - Источник недоступен (отключение, перегрузка).
  - Неверные учетные данные репликации.
  - SSL-сертификаты истекли или неверны.
- **Решение:**
  1. Проверьте сетевую доступность: `nc -zv source_host 3306`.
  2. Проверьте пользователя репликации: `SELECT user, host FROM mysql.user WHERE user = 'repl';`.
  3. Проверьте SSL: `SHOW REPLICA STATUS\G` — поле `Source_SSL` должно быть `Yes`.
  4. Если проблема intermittent — увеличьте `SOURCE_CONNECT_RETRY` и `SOURCE_RETRY_COUNT`.

### Повреждение Relay Log (аварийное завершение)

- **Симптом:** `Replica_SQL_Running: No`, `Last_SQL_Error: Relay log read failure: unexpected end of log file`.
- **Причина:** Реплика записала частичный Relay Log при аварийном выключении (power loss, OOM kill, `kill -9`).
- **Решение:**
  1. Остановите репликацию: `STOP REPLICA;`.
  2. Включите `relay_log_recovery = ON` в `my.cnf` (если еще не включено).
  3. Перезапустите MySQL: `systemctl restart mysql`.
  4. Реплика автоматически удалит поврежденные Relay Logs и скачает их заново.

### Недостаточно прав у пользователя репликации

- **Симптом:** `Replica_IO_Running: No`, `Last_IO_Error: '...' for user 'repl' (using password: YES)`.
- **Причина:** У пользователя репликации нет привилегии `REPLICATION SLAVE` или `REPLICATION CLIENT`.
- **Решение:**
  ```sql
  GRANT REPLICATION SLAVE, REPLICATION CLIENT ON *.* TO 'repl'@'replica_host';
  FLUSH PRIVILEGES;
  ```

### Несовпадение наборов символов (charset/collation)

- **Симптом:** `Replica_SQL_Running: No`, `Last_SQL_Error: 'Incorrect string value'` или `'Illegal mix of collations'`.
- **Причина:** Источник и реплика используют разные `character_set_server` или `collation_server`. Данные, записанные на источнике в одной кодировке, не могут быть прочитаны на реплике.
- **Решение:**
  1. Проверьте кодировки: `SHOW VARIABLES LIKE 'character_set%'; SHOW VARIABLES LIKE 'collation%';`.
  2. Установите одинаковые значения на источнике и реплике в `my.cnf`.
  3. Перезапустите MySQL на обеих сторонах.

### Длинные транзакции на источнике (зависание SQL потока)

- **Симптом:** `Seconds_Behind_Source` растет, хотя `Replica_SQL_Running: Yes`. На источнике активны транзакции длительностью > 30 минут.
- **Причина:** SQL-поток не может применить транзакцию, пока она не зафиксирована на источнике (должен быть strict ordering). I/O-поток успевает скачать binlog, но SQL-поток ждет.
- **Решение:**
  1. Включите `replica_preserve_commit_order = ON` (если еще не включено) для явного упорядочивания.
  2. Разделите длинные транзакции на более мелкие.
  3. Переключите MTS на writeset-зависимости: `binlog_transaction_dependency_tracking = WRITESET` (только для MySQL 5.7 — 8.2; переменная удалена в 8.4.0). Учтите, что длинная транзакция **не** распараллеливается: она целиком блокирует очередь координатора, и WRITESET от её ожидания не избавляет.

### Сбой после DDL на источнике

- **Симптом:** `Replica_SQL_Running: No` после выполнения `ALTER TABLE` на источнике.
- **Причина:** 
  - На реплике активны long-running queries, блокирующие DDL.
  - Разные версии MySQL на источнике и реплике (новый синтаксис DDL не поддерживается).
  - Недостаточно места на диске реплики для временных файлов ALTER TABLE.
- **Решение:**
  1. Проверьте `Last_SQL_Error` для точного кода ошибки.
  2. Убедитесь, что на реплике нет блокирующих сессий: `SHOW PROCESSLIST;`.
  3. Проверьте место на диске: `df -h`.
  4. При необходимости выполните `ALTER TABLE` на реплике вручную перед перезапуском репликации.

### Расхождение времени (time drift)

- **Симптом:** `Seconds_Behind_Source` скачет без видимой причины, `pt-heartbeat` показывает отрицательные значения.
- **Причина:** Системное время на реплике отстает или опережает время на источнике.
- **Решение:**
  1. Настройте NTP на обеих машинах: `systemctl enable --now chronyd` или `systemctl enable --now ntpd`.
  2. Проверьте синхронизацию: `chronyc tracking` или `ntpq -p`.
  3. После синхронизации перезапустите репликацию: `STOP REPLICA; START REPLICA;`.

### Повреждение бинарного лога на источнике

- **Симптом:** `Replica_IO_Running: No`, `Last_IO_Error: Error reading packet from source: ...`.
- **Причина:** Бинарный лог на источнике поврежден (сбой диска, некорректное завершение).
- **Решение:**
  1. На источнике проверьте целостность binlog: `mysqlbinlog --verify-binlog-checksum /var/lib/mysql/binlog.000001`.
  2. Если поврежден — восстановите из бэкапа или пропустите поврежденный фрагмент (если данные не критичны).
  3. На реплике выполните `STOP REPLICA; RESET REPLICA ALL;` и повторно настроите источник.

## Рекомендации

### Мониторинг и алертинг

1. **Ключевые метрики для мониторинга:**
   - `Replica_IO_Running = No` / `Replica_SQL_Running = No` — критично, немедленная реакция.
   - `Seconds_Behind_Source > 60` (или порог, зависящий от RPO) — предупреждение.
   - `Last_IO_Errno != 0` / `Last_SQL_Errno != 0` — ошибка репликации, требует вмешательства (в Performance Schema это `LAST_ERROR_NUMBER`).
   - `relay_log_space_usage` — заполнение диска Relay Log.
   - `binlog_space_usage` — заполнение диска binlog на источнике.

2. **Инструменты мониторинга:**
   - **Performance Schema** (MySQL 8.0+) — встроенный, не требует внешних агентов.
   - **pt-heartbeat** — точное измерение лага независимо от состояния потоков.
   - **Prometheus + MySQL Exporter** — сбор метрик и алертинг в production-средах.
   - **Percona Monitoring and Management (PMM)** — полноценный стек мониторинга для MySQL.

3. **Частота проверок:**
   - **Критичные сервисы:** проверка каждые 30 секунд через скрипт или мониторинговый агент.
   - **Обычные сервисы:** проверка каждые 5 минут.
   - **Консистентность данных:** еженедельно или после каждого крупного DDL.

### Жесткое обеспечение безопасности

1. **`super_read_only = ON`** — на всех репликах, кроме активного источника. Защищает от случайной записи.
2. **Пользователь репликации:** Используйте отдельного пользователя с минимальными привилегиями (`REPLICATION SLAVE`, `REPLICATION CLIENT`). Никогда не используйте `root`.
3. **SSL/TLS:** Для репликации через ненадежные сети включите `require_secure_transport = ON` и настройте сертификаты.
4. **Файрвол:** Разрешите порт 3306 только между источником и репликой. Запретите доступ извне.

### Процедурные рекомендации

1. **Перед любым DDL на источнике:**
   - Остановите репликацию на всех репликах: `STOP REPLICA;`.
   - Выполните DDL на источнике.
   - Проверьте, что DDL завершился: `SHOW PROCESSLIST;`.
   - Запустите репликацию: `START REPLICA;`.
   - Дождитесь `Seconds_Behind_Source = 0` и `SHOW REPLICA STATUS\G` без ошибок.

2. **Регулярная проверка консистентности:**
   - Настройте ежедневный/еженедельный запуск `pt-table-checksum`.
   - Интегрируйте результаты в систему алертинга.

3. **Бэкапы:**
   - Перед отладкой репликации (особенно перед `RESET REPLICA`) убедитесь, что имеете актуальный бэкап реплики.
   - Используйте `mysqldump --single-transaction` или `mydumper` для логически консистентных бэкапов без остановки сервиса.

4. **Изоляция рабочих нагрузок:**
   - Не запускайте аналитические запросы на реплике во время пиковой нагрузки на источник — это может вызвать lock wait и лаг.
   - Используйте отдельные реплики для чтения (read replicas) и для аналитики.

### Настройка MTS для production

1. **`replica_parallel_type = LOGICAL_CLOCK`** — единственный рекомендуемый режим. `DATABASE` параллелит только по базам данных, что редко дает benefit.
2. **`replica_parallel_workers`** — начните с 4, увеличивайте до числа ядер CPU на реплике, но не более 16. Слишком большое значение увеличивает overhead координатора.
3. **`replica_preserve_commit_order = ON`** — обязательно для консистентности, если приложение зависит от порядка записи.
4. **`replica_checkpoint_group`** — установите от 32 до 512 транзакций. Меньшее значение создает больше чекпоинтов, большее — увеличивает время восстановления после сбоя.

## Граничные случаи

### Failover и переключение (Switchover)

При плановом переключении ролей источник → реплика:
1. Остановите запись на старом источнике: `SET GLOBAL super_read_only = ON;`.
2. Дождитесь применения всех транзакций на реплике: `SHOW REPLICA STATUS\G` — `Seconds_Behind_Source = 0`.
3. На реплике (будущем источнике) включите запись: `SET GLOBAL super_read_only = OFF;`.
4. На старом источнике переключите на реплику: `CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION = 1; START REPLICA;`.
5. Обновите приложения, чтобы они подключались к новому источнику.

**Важно:** Если используется GTID, переключение упрощается — не требуется указывать позицию. Если нет GTID — запишите позицию на старом источнике (`SHOW BINARY LOG STATUS`, в MySQL 5.7 и 8.0 — `SHOW MASTER STATUS`) и укажите её на реплике.

### Сетевое разделение (Split Brain)

Если источник и реплика потеряли связь, но обе остались доступны для записи:
1. Как только связь восстановится, GTID-репликация автоматически определит расхождение и остановится.
2. Если GTID не используется — возможна неконсистентность данных. Определите, какие данные являются canonical, и выполните `RESET REPLICA ALL; CHANGE REPLICATION SOURCE TO ...` с указанием корректной позиции.

### Разница часовых поясов

`Seconds_Behind_Source` рассчитывается на основе системного времени реплики. Если на источнике и реплике разные часовые пояса:
- Показатель будет некорректным.
- GTID не зависит от часового пояса, поэтому GTID-репликация более устойчива к этой проблеме.
- **Решение:** Синхронизируйте время через NTP и установите `time_zone = 'UTC'` на всех серверах.

### Очень большие транзакции (> 1 ГБ)

- **Симптом:** Репликация "зависает" на одной транзакции, лаг растет до нескольких часов.
- **Причина:** В binlog записывается полное содержимое транзакции. На реплике SQL-поток должен применить всю транзакцию целиком перед фиксацией.
- **Решение:**
  1. Разбейте большие транзакции на батчи (по 10K–100K строк).
  2. Включите `binlog_transaction_compression = ON` для уменьшения объема.
  3. Увеличьте `net_read_timeout` и `net_write_timeout` на обеих сторонах.

### Изменение схемы (DDL) во время репликации

Если на источнике выполняется `ALTER TABLE` длительностью несколько часов:
1. На реплике SQL-поток будет ждать завершения DDL на источнике.
2. `Seconds_Behind_Source` будет расти пропорционально времени выполнения DDL.
3. **Решение:** Выполняйте DDL через `pt-online-schema-change` на источнике, чтобы минимизировать время блокировки.

### Репликация с própriыми (не-InnoDB) таблицами

MyISAM, MEMORY, CSV таблицы реплицируются в STATEMENT или MIXED режиме. В ROW режиме изменения MyISAM также записываются как row events, но:
- MyISAM не поддерживает транзакции — `ROLLBACK` не откатит изменения на реплике.
- Критерий Crash-Safe не распространяется на MyISAM.

**Решение:** Переведите все таблицы на InnoDB.

### Сброс репликации при отсутствии GTID

Если репликация настроена без GTID и требуется сбросить позицию:
1. На источнике выполните `SHOW BINARY LOG STATUS;` (в MySQL 5.7 и 8.0 — `SHOW MASTER STATUS;`; оператор удалён начиная с MySQL 8.4) — запишите `File` и `Position`.
2. На реплике: `STOP REPLICA; CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION = 0, SOURCE_LOG_FILE = 'binlog.000042', SOURCE_LOG_POS = 154; START REPLICA;`.
3. **Предупреждение:** Это неотъемлемо рискованная операция. Убедитесь, что позиция указывает на корректное событие, иначе данные будут неконсистентны.

## Очистка и откат

### Безопасный сброс репликации

```sql
-- Полный сброс (удаляет все метаданные репликации, Relay Logs и GTID-выполненные транзакции)
RESET REPLICA ALL;

-- Частичный сброс (сохраняет GTID, удаляет только Relay Log и метаданные)
RESET REPLICA;
```

**Когда использовать:**
- `RESET REPLICA ALL` — при полной переконфигурации репликации, изменении источника, переходе с GTID на не-GTID или наоборот.
- `RESET REPLICA` — при очистке Relay Log без смены источника (например, после ручного удаления файлов).

**Предупреждение:** `RESET REPLICA ALL` удаляет `gtid_executed` на реплике. Если реплика имеет собственные транзакции, они будут потеряны. Перед выполнением убедитесь, что реплика не содержит уникальных данных.

### Очистка Relay Log

```sql
-- Остановка репликации
STOP REPLICA;

-- Очистка всех Relay Log (сброс позиции!)
RESET REPLICA;

-- Запуск репликации (скачает свежий Relay Log с источника)
START REPLICA;
```

**Автоматическая очистка:**
- `relay_log_space_limit` — ограничивает общий размер Relay Log. При достижении лимита I/O-поток останавливается до освобождения места SQL-потоком.
- `relay_log_recovery = ON` — при запуске реплика автоматически удаляет неиспользуемые Relay Log.

### Восстановление после сбоя

1. **Проверка состояния:**
   ```sql
   SHOW REPLICA STATUS\G
   ```
   Убедитесь, что `Replica_IO_Running = Yes` и `Replica_SQL_Running = Yes`.

2. **Если SQL-поток остановлен с ошибкой:**
   ```sql
   -- Пропустить транзакцию (только если данные на источнике корректны, а на реплике — нет)
   STOP REPLICA;
   SET GLOBAL sql_slave_skip_counter = 1;
   START REPLICA;
   ```
   **В GTID-режиме:** Вместо `sql_slave_skip_counter` используйте пустую транзакцию (см. `### 2. Типовые ошибки и их решение`).

3. **Если I/O-поток остановлен с ошибкой:**
   ```sql
   STOP REPLICA IO_THREAD;
   START REPLICA IO_THREAD;
   ```
   Или полный перезапуск: `STOP REPLICA; START REPLICA;`.

### Откат конфигурации

Если изменения конфигурации (`my.cnf`) привели к нестабильной работе репликации:

1. Восстановите предыдущую версию `my.cnf` из резервной копии или VCS.
2. Перезапустите MySQL: `systemctl restart mysql`.
3. Проверьте статус: `SHOW REPLICA STATUS\G`.
4. Если репликация не стартует — проверьте ошибки в `error.log`.

### Удаление репликации

Если реплика больше не нужна:

1. Остановите репликацию: `STOP REPLICA;`.
2. Сбросьте метаданные: `RESET REPLICA ALL;`.
3. Удалите пользователя репликации на источнике:
   ```sql
   DROP USER IF EXISTS 'repl'@'replica_host';
   FLUSH PRIVILEGES;
   ```
4. На реплике удалите конфигурацию репликации из `my.cnf` (`server-id`, `relay-log`, `replica-*` параметры).
5. Перезапустите MySQL на реплике.

## Дополнительная информация

### Глубокий мониторинг через Performance Schema

В MySQL 8.0 Performance Schema является основным источником метрик репликации.

```sql
-- Задержка применения транзакций (Lag)
SELECT CHANNEL_NAME,
       WORKER_ID,
       TIMESTAMPDIFF(MICROSECOND,
                     LAST_APPLIED_TRANSACTION_ORIGINAL_COMMIT_TIMESTAMP,
                     LAST_APPLIED_TRANSACTION_END_APPLY_TIMESTAMP) / 1000000 AS lag_seconds
FROM performance_schema.replication_applier_status_by_worker
WHERE LAST_APPLIED_TRANSACTION IS NOT NULL;

-- Состояние I/O потока и сетевые задержки
SELECT * FROM performance_schema.replication_connection_status\G
```

### Рекомендации по Crash-Safety

Для предотвращения повреждения репликации при внезапном выключении (Hard Reboot):

1. **Репозитории в таблицах (MySQL 5.7 — 8.2):** 
   ```ini
   master_info_repository = TABLE
   relay_log_info_repository = TABLE
   ```
   Обе переменные **удалены в MySQL 8.3.0**; начиная с 8.4 метаданные репликации всегда хранятся в транзакционных таблицах.
2. **Восстановление Relay Log:**
   ```ini
   relay_log_recovery = ON
   ```
   *При запуске реплика удаляет старые Relay Logs и скачивает их заново с источника, основываясь на последней подтвержденной позиции в БД.*
3. **Синхронизация логов:**
   ```ini
   sync_binlog = 1
   innodb_flush_log_at_trx_commit = 1
   ```

## Связь с лагом

MTS напрямую влияет на **SQL-лаг** (применение), но не влияет на **IO-лаг**. Если `Read_Master_Log_Pos` сильно отстаёт от `Master_Log_Pos` на мастере — проблема в сети/I/O-потоке, а не в MTS. Детали — см. `lag_monitoring.md`.
