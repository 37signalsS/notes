# Управление и отладка репликации в MySQL

## Определения

**Диагностика репликации** — комплекс мероприятий по мониторингу состояния потоков данных, анализу ошибок и измерению задержек (лага) между источником и репликами.

**Отставание репликации (Replication Lag)** — разрыв во времени между фиксацией транзакции на источнике и её применением на реплике. 

**Crash-Safe Replication** — конфигурация репликации, гарантирующая сохранность позиции и консистентность метаданных после внезапной остановки сервера (например, при сбое питания).

## Основные концепции

### Потоки репликации

Процесс обслуживается тремя основными потоками:

| Поток | Расположение | Задача |
| :--- | :--- | :--- |
| **I/O-поток (Receiver)** | Реплика | Подключается к источнику, запрашивает события binlog и записывает их в локальный **Relay Log**. |
| **SQL-поток (Applier)** | Реплика | Читает события из Relay Log и последовательно применяет их к данным. |
| **Binlog Dump** | Источник | Читает бинарный лог и отправляет события подключенным репликам. |

### Проблема точности Seconds_Behind_Master

Показатель `Seconds_Behind_Master` часто вводит в заблуждение:
- **Как считается:** Разница между временем транзакции, которая *сейчас выполняется* SQL-потоком на реплике, и текущим временем на источнике (или временем последней транзакции на реплике).
- **Когда врет:** 
  - Если I/O-поток остановлен или сеть медленная, значение может быть `0`, хотя данных на реплике нет.
  - Если SQL-поток занят длительной транзакцией, лаг будет расти рывками.
  - При использовании Multi-Threaded Slave (MTS) расчет становится менее точным.
- **Решение:** Использовать внешние инструменты (например, `pt-heartbeat` из Percona Toolkit), которые записывают временную метку в таблицу на источнике каждую секунду.

## Практические сценарии

### Управление репликацией (MySQL 8.0+)

```sql
-- Полный запуск
START REPLICA;

-- Запуск только одного потока (удобно для отладки сети)
START REPLICA IO_THREAD;

-- Остановка для обслуживания
STOP REPLICA;

-- Просмотр статуса (основной инструмент)
SHOW REPLICA STATUS\G
```

### Пропуск ошибок репликации

Если данные на реплике разошлись и SQL-поток остановился с ошибкой:

#### Метод GTID (рекомендуемый)
Для пропуска транзакции нужно создать "пустую" транзакцию с тем же идентификатором:
```sql
STOP REPLICA;
SET GTID_NEXT='uuid:N'; -- ID из Last_SQL_Error
BEGIN; COMMIT;
SET GTID_NEXT='AUTOMATIC';
START REPLICA;
```

#### Метод по позициям (устаревший)
```sql
STOP REPLICA;
SET GLOBAL SQL_SLAVE_SKIP_COUNTER = 1;
START REPLICA;
```

### Проверка консистентности

Стандартные инструменты MySQL не гарантируют, что данные на реплике идентичны источнику. Рекомендуется использовать **Percona Toolkit**:

```bash
# Проверка контрольных сумм всех таблиц (выполняется на источнике)
pt-table-checksum --replicate=percona.checksums --host=source_host

# Синхронизация данных при обнаружении различий
pt-table-sync --execute --replicate=percona.checksums h=source_host,u=root h=replica_host
```

## Дополнительная информация

### Мониторинг через Performance Schema

В MySQL 8.0+ Performance Schema предоставляет гораздо больше данных, чем `SHOW REPLICA STATUS`.

```sql
-- Состояние каждого воркера параллельной репликации
SELECT CHANNEL_NAME, WORKER_ID, LAST_APPLIED_TRANSACTION, LAST_ERROR_NUMBER 
FROM performance_schema.replication_applier_status_by_worker;

-- Общий статус подключения
SELECT * FROM performance_schema.replication_connection_status;
```

### Рекомендации по стабильности

Для обеспечения **Crash-Safety** на реплике должны быть установлены следующие параметры:

```ini
[mysqld]
# Хранение метаданных в таблицах InnoDB (обязательно для 8.0)
relay_log_info_repository = TABLE
master_info_repository = TABLE

# Автоматическое восстановление логов после сбоя
relay_log_recovery = ON

# Синхронизация после каждой транзакции
sync_binlog = 1
innodb_flush_log_at_trx_commit = 1
```

### Диагностика сетевых проблем

Если `Replica_IO_Running: No`:
1. Проверьте `Last_IO_Error` в `SHOW REPLICA STATUS`.
2. Попробуйте ручное подключение с реплики: `mysql -h <source> -u <user> -p`.
3. Убедитесь, что `server_id` на источнике и реплике **разные**.
4. Проверьте `server_uuid` в файле `auto.cnf` (должны быть уникальными).
