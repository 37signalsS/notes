# Форматы бинарного лога в MySQL

**Актуально для:** MySQL 5.1+ / 5.7 / 8.0+ / 8.4 LTS

## Определения

**`binlog_format`** — системная переменная, определяющая способ записи изменений в бинарный лог. Выбор формата напрямую влияет на надежность репликации, объем генерируемого трафика и возможности восстановления.

**Бинарный лог (Binary Log)** — последовательность файлов, содержащих "события", которые описывают изменения данных (DML) и структуры (DDL). Используется для репликации и восстановления данных на точку времени (Point-in-Time Recovery).

**binlog_checksum** — механизм проверки целостности данных. MySQL добавляет контрольную сумму (обычно CRC32) к каждому событию лога, позволяя выявить повреждения при чтении или передаче по сети.

**Dependency Tracking** — механизм записи метаданных о зависимостях транзакций (`binlog_transaction_dependency_tracking`). Позволяет реплике понимать, какие транзакции выполнялись параллельно на источнике и могут быть применены параллельно (MTS).

## Предварительные требования

### Версии MySQL и совместимость

- **Минимальная версия:** Формат `STATEMENT` доступен с MySQL 3.23. Формат `ROW` — с MySQL 5.1. `MIXED` — с MySQL 5.1.
- **Рекомендуемые версии:** Для production используйте MySQL 8.0+ или 8.4 LTS. На этих версиях `ROW` является не только рекомендуемым, но и фактически обязательным форматом для корректной работы GTID и Group Replication.
- **Совместимость источников и реплик:** Источник и реплика могут работать с разными форматами binlog, но репликация будет использовать формат источника. Если реплика настроена на `STATEMENT`, а источник генерирует `ROW`-события, репликация не сработает.
- **Восстановление из бэкапа:** При использовании `mysqldump` с опцией `--set-gtid-purged=ON` убедитесь, что целевой сервер поддерживает формат binlog исходного сервера.

### Требования к конфигурации

- **GTID:** Для использования `binlog_format = ROW` с GTID требуется `enforce_gtid_consistency = ON`. Это запрещает недетерминированные операции, которые несовместимы с ROW.
- **InnoDB:** Формат `ROW` эффективен только с InnoDB. Для MyISAM он также работает, но обеспечивает только детерминизм безCrash safety.
- **Сеть:** При использовании `ROW` объем binlog может увеличиваться в 2-10 раз по сравнению с `STATEMENT`. Убедитесь, что канал репликации выдерживает нагрузку (пропускная способность, латентность).

### Зависимости и ограничения

- **Временные таблицы:** В `STATEMENT` и `MIXED` режимах временные таблицы реплицируются как DDL/DML. В `ROW` режиме изменения временных таблиц не записываются в binlog.
- **Хранимые процедуры и триггеры:** В `STATEMENT` режиме вызовы процедур реплицируются как отдельные события. В `ROW` — реплицируются только изменения данных, произведенные процедурой.
- **Недетерминированные функции:** В `STATEMENT` режиме функции `UUID()`, `RAND()`, `NOW()` (в отличие от `SYSDATE()`) вызываются на реплике и могут вернуть другое значение. В `ROW` — значение генерируется на источнике и записывается как константа.

## Основные концепции

### STATEMENT (SBR — Statement-Based Replication)

**Принцип:** В лог записываются исходные SQL-запросы в текстовом виде.

**Особенности и ограничения:**
- **Недетерминизм:** Главный риск SBR. Запросы, зависящие от контекста или случайных факторов, могут дать разный результат на реплике:
  - Функции: `UUID()`, `RAND()`, `USER()`, `FOUND_ROWS()`.
  - Временные метки: `SYSDATE()` (в отличие от `NOW()`, возвращает время выполнения, а не старта).
  - Порядок строк: `UPDATE` или `DELETE` с `LIMIT` без явного `ORDER BY` может затронуть разные строки из-за разницы в индексах или статистике.
- **Временные таблицы:** Реплицируются полностью. Если реплика упадет, временные таблицы исчезнут, и последующие запросы, использующие их, завершатся с ошибкой.
- **Уровни изоляции:** Для корректной работы требует `REPEATABLE READ`. При `READ COMMITTED` возможны ситуации, когда порядок записи в бинлог не совпадает с порядком фиксации данных, что ломает консистентность реплики.

**Плюсы:** Минимальный объем данных (особенно при массовых `UPDATE`); человекочитаемость.
**Минусы:** Высокий риск расхождения данных; несовместимость с Group Replication и GTID (в части временных таблиц).

### ROW (RBR — Row-Based Replication)

**Принцип:** В лог записываются фактические изменения каждой затронутой строки (состояние "до" и "после"). Это стандарт для современных инсталляций.

**Особенности:**
- **Детерминизм:** Гарантирует 100% идентичность данных. Если на источнике выполнился `UPDATE ... SET col = UUID()`, в лог попадет уже сгенерированная строка.
- **Group Replication:** Единственный поддерживаемый формат, так как механизмы сертификации транзакций требуют анализа измененных строк для обнаружения конфликтов.
- **JSON (Partial Updates):** В MySQL 8.0+ при изменении части большого JSON-документа записывается только `diff`, а не весь объект.
- **Уровни изоляции:** Позволяет безопасно использовать `READ COMMITTED`, что снижает количество блокировок в базе.

**Плюсы:** Максимальная надежность; поддержка Change Data Capture (CDC); эффективная работа с JSON.
**Минусы:** Взрывной рост объема логов при операциях типа `DELETE FROM huge_table`.

### MIXED (Mixed-Based Replication)

**Принцип:** MySQL использует SBR по умолчанию, но автоматически переключается на RBR для конкретного события, если запрос признается "небезопасным" для SBR.

**Условия переключения на ROW:**
1. Использование функций `UUID()`, `USER()`, `CURRENT_USER()`.
2. Обращение к временным таблицам внутри хранимых процедур.
3. Использование `LOAD_FILE()`.
4. Запросы к таблицам с `AUTO_INCREMENT` столбцами в сочетании с триггерами или функциями.
5. Использование `FOUND_ROWS()` или `ROW_COUNT()`.
6. Использование системных переменных (например, `@@hostname`).

## Оптимизация и расширенные возможности (MySQL 8.0+)

Выбор формата `ROW` требует настройки дополнительных параметров для баланса между объемом данных и информативностью.

### Сжатие и метаданные

1.  **binlog_transaction_compression = ON:** (MySQL 8.0.20+) Использует алгоритм **ZSTD** для сжатия целых групп транзакций перед записью в лог.
    - **Эффект:** Сокращение объема логов в 3-5 раз. Снижение нагрузки на дисковую подсистему (IOPS) и сетевой трафик.
    - **Цена:** Незначительное повышение нагрузки на CPU (зависит от интенсивности записи).
    - **Валидация:** Эффективность сжатия можно проверить в Performance Schema:
      ```sql
      SELECT * FROM performance_schema.binary_log_transaction_compression_stats;
      ```
2.  **binlog_row_metadata = FULL:** Включает в лог расширенные метаданные столбцов (имена, типы данных, кодировки).
    - **Зачем:** Это критично для систем захвата изменений (CDC), таких как **Debezium** или **Kafka Connect**. Без этого CDC-агенты вынуждены постоянно опрашивать словарь данных (`information_schema`) БД, что создает нагрузку и риски при DDL-изменениях.
    - **Рекомендация:** Для обычных реплик используйте `MINIMAL` (по умолчанию), для CDC — только `FULL`.
3.  **binlog_row_image:** Контролирует объем данных для каждой строки:
    - `FULL` (Default): Записываются все столбцы строки ("до" и "после"). Максимальная безопасность.
    - `MINIMAL`: Записываются только первичный ключ и измененные столбцы. Резко снижает объем логов при `UPDATE`.
    - **Ограничение:** Для CDC и некоторых типов репликации (на основе триггеров или внешних средств извлечения изменений) обязателен `FULL`.

### Эффективная работа с JSON

Для активации частичных обновлений (Partial Updates) JSON в формате `ROW`:
- `binlog_row_value_options = PARTIAL_JSON` (стандарт в MySQL 8+).
- Это позволяет записывать в бинлог только путь к измененному ключу и новое значение, вместо перезаписи всего JSON-документа объемом в несколько мегабайт.

## Практические сценарии

### 1. Поиск конкретной транзакции в ROW-логах

Так как формат `ROW` бинарный, для его анализа требуется утилита `mysqlbinlog` с продвинутыми флагами:

```bash
# --base64-output=DECODE-ROWS: преобразует бинарные строки в читаемый формат
# -v -v: добавляет комментарии с именами и типами столбцов (если включен metadata)
mysqlbinlog -v -v --base64-output=DECODE-ROWS \
  --start-datetime="2024-05-20 10:00:00" \
  --stop-datetime="2024-05-20 10:05:00" \
  /var/lib/mysql/binlog.000042 > debug_rows.sql
```

### 2. Извлечение изменений для конкретной таблицы

```bash
# Фильтрация по БД и поиск по названию таблицы в декодированном выводе
mysqlbinlog -v --base64-output=DECODE-ROWS --database=prod_db \
  /var/lib/mysql/binlog.000042 | grep -A 5 "INSERT INTO \`users\`"
```

### 3. Решение ошибки 3748 (temporary table в транзакции при GTID)

**Ситуация:** При `gtid_mode = ON` попытка создать или удалить temporary table внутри транзакции приводит к фатальной ошибке на реплике.
**Причина:** В SBR/MIXED такая конструкция невоспроизводима — временная таблица принадлежит только сессии-источнику. Детали в разделе [Устранение неисправностей](#ошибка-при-создании-временной-таблицы-в-транзакции-3748).
**Решение:** `binlog_format = ROW`. В RBR изменения во временных таблицах в бинарный лог не попадают.

## Устранение неисправностей

### Ошибка при создании временной таблицы в транзакции (3748)

- **Симптом:** `ERROR 3748 (HY000): Statement is not safe because it is not safe in statement-based replication when GTID is enabled: Can't create/drop temporary table in transaction.`
- **Причина:** `binlog_format` установлен в `STATEMENT` или `MIXED` (для этой конструкции), а `gtid_mode = ON`. Временная таблица существует только в сессии-источнике и не может быть воспроизведена на реплике идентично, поэтому MySQL отвергает такую конструкцию при statement-based репликации с GTID.
- **Решение:** Переключитесь на `binlog_format = ROW`:
  ```sql
  SET GLOBAL binlog_format = ROW;
  -- Или в my.cnf:
  binlog_format = ROW
  ```

### Взрывной рост binlog при массовых UPDATE

- **Симптом:** Диск, на котором хранятся binlog, заполняется мгновенно после запуска массового `UPDATE` или `DELETE`.
- **Причина:** В формате `ROW` каждое измененное строку записывается полностью. При `UPDATE users SET status = 1` на таблице с 10 млн строк в binlog попадут 10 млн записей.
- **Решение:**
  1. Временно увеличьте `binlog_expire_logs_seconds` или отключите binlog: `SET SESSION sql_log_bin = 0;` (требует `SUPER` privilege, не рекомендуется на источнике).
  2. Разбейте массовое изменение на батчи: `UPDATE ... WHERE id BETWEEN X AND Y LIMIT 1000`.
  3. Используйте `pt-online-schema-change` для больших изменений.

### Сбой репликации после изменения binlog_format

- **Симптом:** `Last_SQL_Error: ... Error 'You are not using binary logging'` или репликация останавливается с кодом ошибки.
- **Причина:** Изменение `binlog_format` на лету требует перезапуска репликации или сброса позиции. GTID-репликация чувствительна к формату binlog на источнике.
- **Решение:** 
  1. Остановите репликацию: `STOP REPLICA;`
  2. Измените `binlog_format` в `my.cnf` на источнике.
  3. Перезапустите MySQL на источнике.
  4. На реплике выполните `RESET REPLICA ALL;` и повторно настроите `CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION = 1`.

### Проблемы с CDC и отсутствием метаданных

- **Симптом:** CDC-агенты (Debezium, Kafka Connect) не могут определить структуру таблиц или выводят пустые значения для столбцов.
- **Причина:** `binlog_row_metadata = MINIMAL` (по умолчанию). В этом режиме в binlog записываются только типы данных, но не имена столбцов.
- **Решение:** Включите `binlog_row_metadata = FULL` на источнике.

### Высокое потребление CPU при сжатии ZSTD

- **Симптом:** `iostat` показывает высокую нагрузку на CPU после включения `binlog_transaction_compression = ON`.
- **Причина:** Сжатие ZSTD — CPU-интенсивная операция. На серверах с высокой интенсивностью записи (>10K TPS) это может стать узким местом.
- **Решение:** 
  1. Оцените Benefit: если сжатие сокращает объем binlog в 3-5 раз и освобождает IOPS, утилизация CPU может быть приемлемой.
  2. Для серверов с > 16 CPU cores увеличение нагрузки обычно не критично.
  3. Если CPU becomes bottleneck — отключите сжатие или перейдите на менее агрессивный алгоритм (в MySQL 8.0+ доступен только ZSTD).

## Рекомендации

### Выбор формата для Production

1. **`binlog_format = ROW`** — единственный рекомендуемый формат для всех современных систем. `STATEMENT` допустим только в изолированных legacy-средах без GTID и Group Replication.
2. **`binlog_checksum = CRC32`** — всегда включено по умолчанию в MySQL 8.0+. Для 5.7 установите явно. Это защищает от тихого повреждения данных при передаче по сети.
3. **`enforce_gtid_consistency = ON`** — обязательно для `ROW` + GTID. Запрещает недетерминированные операции, нарушающие атомарность.

### Настройка для высокой нагрузки

1. **`binlog_transaction_compression = ON`** — включайте для всех баз с интенсивной записью (> 1000 TPS). Экономия места и IOPS перевесит дополнительные CPU-затраты.
2. **`binlog_row_image = MINIMAL`** — допустимо только если реплика не используется для CDC и все таблицы имеют первичный ключ. Для CDC и Multi-Source — только `FULL`.
3. **`binlog_row_value_options = PARTIAL_JSON`** — обязательно, если в базе есть крупные JSON-документы, которые частично обновляются.
4. **`binlog_row_metadata = MINIMAL`** — для обычных реплик. Переключитесь на `FULL` только при подключении CDC-агентов.

### Управление хранилищем

1. **`binlog_expire_logs_seconds`** — настройте автоматическую очистку. Значение по умолчанию — `2592000` (30 суток). Для PITR выставляйте срок больше фактического окна восстановления плюс запас на репликацию: если окно 72 часа, задайте `259200` или больше.
2. **Отдельный диск для binlog:** На высоконагруженных серверах размещайте binlog на отдельном физическом устройстве от data directory. Это снижает contention между random I/O (InnoDB) и sequential I/O (binlog).
3. **Мониторинг размера:** Настройте алерт при заполнении диска, на котором хранятся binlog, более чем на 80%. Используйте `SHOW BINARY LOGS` для проверки.

## Граничные случаи

### Изменение binlog_format на лету

Изменение `binlog_format` через `SET GLOBAL` действует только для новых соединений. Существующие сессии продолжают использовать старое значение. После изменения:
1. Убедитесь, что все клиенты переподключились.
2. Проверьте `SHOW GLOBAL VARIABLES LIKE 'binlog_format'`.
3. На источнике перезапустите репликацию: `STOP REPLICA; START REPLICA;`.

### Использование STATEMENT в специфичных сценариях

`STATEMENT` формат может использоваться только если:
- Нет GTID и Group Replication.
- Все таблицы имеют только детерминированные операции.
- Нет временных таблиц внутри транзакций.
- Нет `UUID()`, `RAND()`, `SYSDATE()` и других недетерминированных функций.

**Важно:** Даже в этих условиях `STATEMENT` несовместим с `READ COMMITTED` уровнем изоляции. При переходе на `READ COMMITTED` необходимо переключиться на `ROW`.

### SBR с NOT NULL колонками и частичные обновления

В `STATEMENT` режиме `ALTER TABLE` с добавлением NOT NULL колонки без DEFAULT значения блокирует таблицу и может вызвать расхождение данных на реплике, если на источнике данные уже есть. В `ROW` режиме это работает корректно, так как фиксируется физическое изменение.

### Восстановление PITR при смешанных форматах

Если в рамках одного binlog файла встречаются события в разных форматах (что возможно только в MIXED режиме), PITR может восстановить только те события, которые поддерживаются целевым сервером. Рекомендуется единообразное использование `ROW`.

### Репликация между разными версиями MySQL

MySQL 5.7 может реплицировать с MySQL 8.0, но:
- `binlog_row_metadata` в 8.0+ может содержать расширенные метаданные, которые 5.7 не поймет.
- `binlog_transaction_compression` работает только если и источник, и реплика — MySQL 8.0.20+.
- GTID-формат идентичен, но `gtid_executed` в 8.0 может содержать транзакции, которые 5.7 не видит.

## Очистка и откат

### Очистка старых binlog файлов

```sql
-- Удаление binlog старше N секунд (рекомендуется 259200 = 72 часа)
PURGE BINARY LOGS BEFORE (NOW() - INTERVAL 259200 SECOND);

-- Удаление binlog старше конкретной даты
PURGE BINARY LOGS BEFORE '2024-05-20 10:00:00';

-- Проверка, какие файлы будут удалены
SHOW BINARY LOGS;
```

### Откат на STATEMENT формат (не рекомендуется)

Если по какой-то причине требуется вернуться на `STATEMENT`:
1. Остановите репликацию на всех репликах.
2. Убедитесь, что нет активных транзакций, использующих недетерминированные функции.
3. Измените `binlog_format = STATEMENT` в `my.cnf` на источнике.
4. Перезапустите MySQL.
5. На репликах выполните `RESET REPLICA ALL;` и повторно настроите источники.

**Предупреждение:** Это критически опасная операция для production. GTID, Group Replication и CDC-агенты перестанут работать корректно.

### Миграция с MIXED на ROW

```sql
-- 1. Остановка репликации
STOP REPLICA;

-- 2. Изменение формата на источнике (my.cnf)
-- binlog_format = ROW

-- 3. Перезапуск MySQL на источнике
-- systemctl restart mysql

-- 4. Проверка формата
SHOW GLOBAL VARIABLES LIKE 'binlog_format';

-- 5. Сброс и повторная настройка репликации на реплике
RESET REPLICA ALL;
CHANGE REPLICATION SOURCE TO SOURCE_AUTO_POSITION = 1;
START REPLICA;
```

## Дополнительная информация

### Сводная таблица сравнения

| Характеристика | STATEMENT (SBR) | ROW (RBR) | ROW + ZSTD |
| :--- | :--- | :--- | :--- |
| **Объем логов** | Минимальный | Высокий | Средний |
| **Надежность** | Низкая (Недетерминизм) | Максимальная | Максимальная |
| **Нагрузка на CPU** | Низкая | Средняя | Выше (сжатие) |
| **Параллельная репликация** | Плохо (сложные зависимости) | Отлично | Отлично |
| **Поддержка PITR** | Ограничена | Полная | Полная |

### Рекомендации для Production (MySQL 8.4 LTS)

1. **`binlog_format = ROW`** — промышленный стандарт. Использование `STATEMENT` допустимо только в изолированных legacy-системах без высоких требований к консистентности.
2. **`binlog_transaction_compression = ON`** — обязательно для баз с интенсивной записью.
3. **`binlog_checksum = CRC32`** — всегда включено для предотвращения повреждения данных (Corruption).
4. **`sync_binlog = 1`** — критично для предотвращения потери транзакций при сбое питания.

## Практический блок: выбор формата бинлога (компромиссы)

### Сравнение форматов

| Критерий | STATEMENT | ROW | MIXED |
| :--- | :--- | :--- | :--- |
| **Объём binlog** | Меньше (только SQL) | Больше (изменённые строки) | Промежуточный |
| **Нагрузка на сеть/диск** | Ниже | Выше (особенно массовые UPDATE/DELETE) | Зависит от кейсов |
| **Детерминизм** | Проблемный (недетерминированные функции: UUID(), RAND(), NOW() без точной синхронизации, LIMIT без ORDER BY) | Надёжный (реплицирует строки) | Компромисс |
| **Безопасность репликации** | Риск расхождений на недетерминированных запросах | Наиболее безопасен с точки зрения консистентности | Лучше STATEMENT, но не гарантирует |
| **Анализ/аудит binlog** | Удобен (видны SQL) | Менее удобен (пары Before/After Images) | Смешанный |
| **Влияние на лаг репликации** | Часто меньше объёма, но применение может зависеть от версии | Может увеличивать объём, но применение по строкам предсказуемее | Гибрид |
| **Совместимость/триггеры** | Ограничения при некоторых триггерах/функциях | Шире совместим | Зависит |

### Практические рекомендации выбора

| Сценарий | Рекомендуемый формат | Обоснование |
| :--- | :--- | :--- |
| **Default/Production (безопасность прежде всего)** | `ROW` | Минимальный риск расхождений данных, особенно на ROW-базированной репликации. Рекомендуется в MySQL 8.0+ как более предсказуемый. |
| **Большие аналитические массовые операции (объём критичен)** | `STATEMENT` | Меньший объём бинлога, но **только** если все запросы детерминированны. Требует тщательной проверки. |
| **Смешанные нагрузки (исторически)** | `MIXED` | Автоматически выбирает формат. В MySQL 8.0 поведение MIXED стало ближе к ROW для многих случаев; часто проще использовать `ROW`. |
| **Нужно удобство чтения binlog (debug/аудит SQL)** | `STATEMENT` | Проще анализировать. Для production-аудита часто используют инструменты, работающие с ROW. |

### Практические замечания

- **MySQL 8.0+:** `BINLOG_FORMAT` по-прежнему актуален, но при использовании некоторых фич (например, Group Replication) поведение может требовать `ROW`. Проверяйте требования конкретного решения.
- **Массовые операции (`DELETE/UPDATE` без LIMIT по большим таблицам):** ROW даёт много событий (строк) — увеличивает объём. Можно разбивать на батчи, снижая объём за раз и нагрузку на репликацию.
- **Недетерминизм:** если не можете исключить недетерминированные выражения — **не** используйте STATEMENT.
- **Тестирование:** перед сменой формата бинлога обязательно тестировать на реплике/non-prod с характерной нагрузкой (оценить объём бинлога, лаг).
