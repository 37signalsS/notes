# Форматы бинарного лога в MySQL

## Определения

**`binlog_format`** — системная переменная, определяющая способ записи изменений в бинарный лог. Выбор формата напрямую влияет на надежность репликации, объем генерируемого трафика и возможности восстановления.

**Бинарный лог (Binary Log)** — последовательность файлов, содержащих "события", которые описывают изменения данных (DML) и структуры (DDL). Используется для репликации и восстановления данных на точку времени (Point-in-Time Recovery).

**Избыточность лога (Log Verbosity)** — объем метаданных, включаемых в лог для обеспечения детерминизма или поддержки внешних систем (CDC).

## Основные концепции

### STATEMENT (SBR — Statement-Based Replication)

**Принцип:** В лог записываются исходные SQL-запросы в текстовом виде.

**Особенности и ограничения:**
- **Недетерминизм:** Использование функций `UUID()`, `RAND()`, `NOW()`, `SYSDATE()`, а также `UPDATE` или `DELETE` с `LIMIT` без явного `ORDER BY` может привести к расхождениям между источником и репликой.
- **Временные таблицы:** Реплицируются полностью, что требует синхронного состояния сессий на мастере и реплике.
- **Хранимые процедуры:** Реплицируется сам вызов процедуры. Если процедура содержит логику на основе текущего времени или случайных чисел, данные разойдутся.
- **Уровни изоляции:** Требует `REPEATABLE READ` для обеспечения консистентности.

**Плюсы:** Минимальный объем данных; легкость чтения лога.
**Минусы:** Высокий риск рассинхронизации; несовместимость с Group Replication.

### ROW (RBR — Row-Based Replication)

**Принцип:** В лог записываются фактические изменения каждой затронутой строки (состояние "до" и "после"). Это стандарт для MySQL 5.7+ и обязательное требование для 8.0+.

**Особенности:**
- **Детерминизм:** Гарантирует идентичность данных независимо от используемых функций (например, `UUID()` просто запишется как итоговая строка).
- **JSON (Partial Updates):** В MySQL 8.0+ при изменении части большого JSON-документа записывается только измененный фрагмент, а не весь объект.
- **Временные таблицы:** Не записываются в бинарный лог (за исключением `DROP`), так как изменения в них не аффектят постоянные данные через механизмы RBR.
- **Уровни изоляции:** Позволяет использовать `READ COMMITTED` для повышения производительности и уменьшения блокировок.

**Плюсы:** Максимальная надежность; поддержка Change Data Capture (CDC); эффективная работа с JSON.
**Минусы:** Большой объем логов при массовых операциях (например, `UPDATE` миллиона строк).

### MIXED (Mixed-Based Replication)

**Принцип:** MySQL использует `STATEMENT` по умолчанию, но автоматически переключается на `ROW`, если запрос признается "небезопасным" (например, содержит функции типа `UUID()`, обращение к временным таблицам или `User Defined Functions`).

## Оптимизация и расширенные возможности (MySQL 8.0+)

Выбор формата `ROW` требует настройки дополнительных параметров для баланса между объемом данных и информативностью.

### Сжатие и метаданные

1.  **binlog_transaction_compression = ON:** (MySQL 8.0.20+) Использует алгоритм **ZSTD** для сжатия событий в логе. Позволяет сократить объем логов в 3-5 раз, что критично при использовании `ROW`.
2.  **binlog_row_metadata = FULL:** Включает в лог метаданные столбцов (имена, типы). Это обязательно для систем захвата данных (CDC), таких как **Debezium**, чтобы они могли корректно интерпретировать изменения без обращения к словарю данных БД.
3.  **binlog_row_image:** Контролирует, сколько данных записывается для каждой строки:
    *   `FULL` (Default): Полные образы строк (до и после). Самый надежный режим.
    *   `MINIMAL`: Только измененные поля и первичный ключ. Существенно экономит место.
    *   `NOBLOB`: Аналог FULL, но без BLOB/TEXT полей, если они не менялись.

### Эффективная работа с JSON

Для активации частичных обновлений (Partial Updates) JSON в формате `ROW`:
- `binlog_row_value_options = PARTIAL_JSON` (включено по умолчанию в 8.0).
- `binlog_row_image` должен быть `FULL` или `NOBLOB`.

## Практические сценарии

### 1. Мониторинг и переключение формата

```sql
-- Просмотр текущих настроек
SELECT @@binlog_format, @@binlog_row_image, @@binlog_transaction_compression;

-- Динамическое переключение (для новых сессий)
SET GLOBAL binlog_format = 'ROW';
SET GLOBAL binlog_row_image = 'MINIMAL';
```

### 2. Чтение ROW-логов через mysqlbinlog

Так как формат `ROW` бинарный, для его анализа требуется утилита `mysqlbinlog` с декодированием:

```bash
# -v: декодирует события в SQL-запросы (в комментариях)
# --base64-output=DECODE-ROWS: скрывает огромные бинарные блоки строк
mysqlbinlog -v --base64-output=DECODE-ROWS /var/lib/mysql/binlog.000042
```

### 3. Настройка для CDC (Debezium / Kafka Connect)

Если база используется как источник событий для внешней системы:

```ini
[mysqld]
binlog_format = ROW
binlog_row_image = FULL
binlog_row_metadata = FULL
gtid_mode = ON
enforce_gtid_consistency = ON
```

## Дополнительная информация

### Сводная таблица сравнения

| Характеристика | STATEMENT | ROW | ROW + ZSTD |
| :--- | :--- | :--- | :--- |
| **Объем логов** | Минимальный | Высокий | Средний |
| **Надежность** | Низкая (Недетерминизм) | Максимальная | Максимальная |
| **Нагрузка на CPU** | Низкая | Средняя | Выше (за счет сжатия) |
| **Поддержка PITR** | Ограничена | Полная | Полная |

### Рекомендации для MySQL 8.4 LTS

Для современных высоконагруженных систем рекомендуется следующий "золотой стандарт":
1. `binlog_format = ROW` — без вариантов для 8.x.
2. `binlog_transaction_compression = ON` — для экономии IOPS и места.
3. `binlog_row_image = FULL` — для максимальной совместимости с инструментами восстановления.
