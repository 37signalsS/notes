# Форматы бинарного лога в MySQL

## Определения

**`binlog_format`** — параметр конфигурации MySQL, определяющий формат записи событий в бинарный лог. От выбранного формата зависит надежность репликации, размер логов, производительность и возможность использования определенных технологий (например, Group Replication).

**Бинарный лог (Binary Log)** — журнал всех событий, изменяющих данные (DML) или структуру базы данных (DDL). Является основой для репликации и восстановления данных на определенный момент времени (PITR).

## Основные концепции

### STATEMENT (SBR — Statement-Based Replication)

**Принцип:** В лог записываются исходные SQL-запросы (`INSERT`, `UPDATE`, `DELETE`).

**Особенности:**
- **Недетерминизм:** Самая большая проблема. Функции типа `NOW()`, `UUID()`, `RAND()` или использование `LIMIT` без `ORDER BY` могут привести к разным результатам на источнике и реплике.
- **Временные таблицы:** Реплицируются (записываются в лог), что требует осторожности при управлении сессиями.
- **Хранимые процедуры:** Реплицируется сам вызов процедуры, что накладывает ограничения на использование недетерминированного кода внутри них.

**Плюсы:** Минимальный размер логов и низкая нагрузка на сеть.
**Минусы:** Риск рассинхронизации данных, не поддерживается в современных топологиях (Group Replication).

### ROW (RBR — Row-Based Replication)

**Принцип:** В лог записываются фактические изменения строк (состояние до и после операции). Это формат по умолчанию, начиная с MySQL 5.7.

**Особенности:**
- **Детерминизм:** Гарантирует 100% идентичность данных, так как реплика просто применяет готовый результат.
- **JSON:** Позволяет выполнять частичное обновление JSON-документов (Partial Updates), что значительно быстрее пересылки всего документа.
- **Временные таблицы:** **Не записываются** в лог (кроме операций `DROP`), так как изменения данных в них не влияют на постоянные таблицы через RBR.

**Плюсы:** Максимальная надежность, поддержка всех современных функций MySQL.
**Минусы:** Большой объем логов при массовых обновлениях, сложность ручного чтения лога.

### MIXED (Mixed-Format Replication)

**Принцип:** Автоматическое переключение. По умолчанию используется `STATEMENT`, но если запрос признается недетерминированным (например, содержит `UUID()`), MySQL переключает запись этого события в формат `ROW`.

### Оптимизация формата ROW

Для смягчения "минусов" формата ROW в MySQL 8.0+ введены важные параметры:

1.  **binlog_row_image:** Контролирует объем данных, записываемых для каждой строки.
    *   `FULL` (по умолчанию): Записываются все столбцы строки.
    *   `MINIMAL`: Записываются только измененные столбцы и столбцы первичного ключа. Значительно уменьшает размер логов.
    *   `NOBLOB`: Как FULL, но исключает неизмененные BLOB/TEXT поля.
2.  **binlog_transaction_compression:** (MySQL 8.0.20+) Позволяет сжимать транзакции в бинарном логе с помощью алгоритма ZSTD. Это критично для ROW-формата, так как позволяет экономить до 60-90% места на диске и сетевого трафика.
3.  **binlog_row_metadata:** Позволяет включать метаданные (имена столбцов, типы данных) прямо в бинарный лог, что упрощает работу внешним инструментам захвата данных (CDC), таким как Debezium.

## Практические сценарии

### Проверка и изменение формата

```sql
-- Проверка текущего режима
SELECT @@global.binlog_format, @@session.binlog_format;

-- Изменение в рантайме (требует SYSTEM_VARIABLES_ADMIN или SUPER)
SET GLOBAL binlog_format = 'ROW';
```

### Декодирование ROW-событий

Поскольку формат `ROW` является бинарным, обычный просмотр через `cat` или `less` невозможен. Используйте утилиту `mysqlbinlog` с флагами расшифровки:

```bash
# -v (verbose): показывает реконструированные SQL-запросы в виде комментариев
# --base64-output=DECODE-ROWS: скрывает бинарные дампы строк
mysqlbinlog -v --base64-output=DECODE-ROWS /var/lib/mysql/binlog.000001
```

### Работа с JSON (Partial Updates)

Для эффективной работы с JSON в формате ROW убедитесь, что:
1. Используется MySQL 8.0+.
2. Параметр `binlog_row_value_options` установлен в `PARTIAL_JSON` (по умолчанию в 8.0+).
3. `binlog_row_image` установлен в `FULL` или `NOBLOB`.

## Дополнительная информация

### Рекомендации для MySQL 8.4 LTS

В современной архитектуре (особенно в облачных инсталляциях) рекомендуется следующая конфигурация:

```ini
[mysqld]
# Промышленный стандарт
binlog_format = ROW

# Экономия места без потери надежности
binlog_row_image = MINIMAL

# Сжатие для ROW логов (MySQL 8.0.20+)
binlog_transaction_compression = ON

# Для Group Replication и корректного failover
gtid_mode = ON
enforce_gtid_consistency = ON
```

### Сравнение производительности

| Формат | Нагрузка на CPU (Источник) | Нагрузка на Сеть | Надежность |
| :--- | :--- | :--- | :--- |
| **STATEMENT** | Низкая | Низкая | Низкая |
| **ROW** | Средняя (сериализация) | Высокая (без сжатия) | Максимальная |
| **ROW + ZSTD** | Выше (сжатие) | Низкая | Максимальная |
