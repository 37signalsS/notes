# Форматы бинарного лога (binlog_format)

## Definitions

**`binlog_format`** — параметр конфигурации MySQL, определяющий формат записи событий в [бинарный лог](./overview.md#бинарный-лог). От выбранного формата зависит надежность репликации, размер логов и производительность.

**Бинарный лог (Binary Log)** — журнал всех событий, изменяющих данные (DML) или структуру базы данных (DDL). Используется для репликации и восстановления данных.

## Basic Concepts

### 1. STATEMENT (Statement-Based Replication — SBR)

**Принцип:** В лог записываются исходные SQL-запросы (`INSERT`, `UPDATE`, `DELETE`, `DDL`).

**Проблема:** Ненадежен для **недетерминированных** функций:

- `NOW()`, `SYSDATE()` — время выполнения
- `UUID()`, `UUID_SHORT()` — уникальные идентификаторы
- `RAND()`, `USER()`, `CONNECTION_ID()` — контекст-зависимые значения
- `LOAD_FILE()`, `BENCHMARK()` — побочные эффекты

Выполнение одного и того же запроса на master и slave в разное время приведет к рассинхронизации данных.

**Плюсы:**

- Минимальный размер логов (записывается только текст запроса)
- Низкая нагрузка на диск и сеть

**Минусы:**

- Небезопасен для целостности данных при использовании недетерминированных функций
- Не является режимом по умолчанию в современных версиях MySQL (≥5.7.7)

### 2. ROW (Row-Based Replication — RBR)

**Принцип:** В лог записывается бинарное представление **измененных строк** (до и после), а не SQL-запрос.

**Надежность:** Формат полностью детерминирован. Функция `NOW()` не выполняется на slave заново — копируется строка с уже готовым значением. Гарантируется побайтовое совпадение данных.

**Плюсы:**

- Максимальная консистентность данных
- Безопасен для недетерминированных функций
- Формат по умолчанию начиная с MySQL 5.7.7

**Минусы:**

- Большой размер логов при массовых операциях (`UPDATE` на миллион строк создаст гигабайтный лог)
- Увеличенная нагрузка на диск и сеть
- Невозможность быстрого аудита (не видно, какой запрос вызвал изменение)

### 3. MIXED (Mixed-Format Replication)

**Принцип:** Гибридный режим. По умолчанию используется `STATEMENT`, но при обнаружении недетерминированных запросов MySQL автоматически переключается на `ROW`.

**Плюсы:**

- Баланс между надежностью и размером логов
- Автоматическая защита от рассинхронизации

**Минусы:**

- Поведение не всегда предсказуемо
- Требует глубокого понимания, какой запрос считается "безопасным"
- Сложнее отладка репликации

## Practical Scenarios

### Проверка текущего формата

```sql
-- Проверка текущего значения
SHOW VARIABLES LIKE 'binlog_format';

-- Или через переменную сессии/глобально
SELECT @@binlog_format;
SELECT @@GLOBAL.binlog_format;
SELECT @@SESSION.binlog_format;
```

### Изменение формата

```ini
# В конфигурационном файле (my.cnf / mysqld.cnf)
[mysqld]
binlog_format = ROW
```

```sql
-- Изменение на уровне сессии (требует привилегий)
SET SESSION binlog_format = STATEMENT;

-- Изменение глобально (действует до перезагрузки)
SET GLOBAL binlog_format = ROW;
```

> **Важно:** Изменение `binlog_format` не влияет на уже существующие бинарные логи. Новый формат применяется только к новым событиям.

### Рекомендации по выбору

| Сценарий | Рекомендуемый формат | Обоснование |
| :--- | :--- | :--- |
| Стандартная репликация | `ROW` | Гарантия консистентности |
| Высокая нагрузка на запись | `ROW` | Избегание конфликтов репликации |
| Ограниченный диск/сеть | `MIXED` | Баланс размера и надежности |
| Аудит запросов | `STATEMENT` | Видны исходные SQL-команды |
| Master-Master топология | `ROW` | Критично для [недетерминированных запросов](../../Concepts/replication.md#недетерминированные-запросы) |

### Примеры проблемных запросов в STATEMENT

```sql
-- Недетерминированные запросы (проблемы в SBR):
INSERT INTO logs VALUES (NOW(), UUID(), 'event');
UPDATE users SET last_login = NOW() WHERE id = 1;
INSERT INTO rand_table VALUES (RAND());

-- Безопасные запросы (корректны в SBR):
INSERT INTO users (id, name) VALUES (1, 'John');
UPDATE accounts SET balance = 100 WHERE id = 5;
```

## Additional Information

### Влияние на производительность

- **STATEMENT:** Минимальные накладные расходы, но риск рассинхронизации
- **ROW:** Дополнительные затраты на сериализацию строк, особенно для широких таблиц
- **MIXED:** Переключение между форматами добавляет небольшую задержку на анализ запроса

### Особенности в MySQL 8.0+

Начиная с MySQL 8.0, формат `ROW` является безальтернативной рекомендацией для всех продакшен-окружений. Формат `STATEMENT` считается устаревшим для репликации.

### Связь с GTID

При использовании [GTID](./gtid.md) рекомендуется формат `ROW`, так как он обеспечивает лучшую совместимость и предсказуемость при failover.

### Мониторинг размера binlog

```sql
-- Размер бинарных логов
SHOW BINARY LOGS;

-- Статистика по событиям в binlog
SHOW BINLOG EVENTS IN 'mysql-bin.000001' LIMIT 10;
```

Подробное управление и очистка — в [binlog_management.md](./binlog_management.md).
