# Форматы бинарного лога (binlog_format)

## Определения

**`binlog_format`** — параметр конфигурации MySQL, определяющий формат записи событий в бинарный лог. От выбранного формата зависит надежность репликации, размер логов и производительность.

**Бинарный лог (Binary Log)** — журнал всех событий, изменяющих данные: **DML (Data Manipulation Language — язык манипулирования данными)** или структуру базы данных: **DDL (Data Definition Language — язык определения данных)**. Используется для репликации и восстановления данных.

## Основные концепции

### 1. STATEMENT (Statement-Based Replication — SBR)

**Принцип:** В лог записываются исходные SQL-запросы (`INSERT`, `UPDATE`, `DELETE`, `DDL`).

**Проблема:** Ненадежен для **недетерминированных** функций, результат которых зависит от времени или контекста выполнения:

- `NOW()`, `SYSDATE()` — время выполнения.
- `UUID()`, `UUID_SHORT()` — уникальные идентификаторы.
- `RAND()`, `USER()`, `CONNECTION_ID()` — контекст-зависимые значения.
- `LOAD_FILE()`, `BENCHMARK()` — функции с побочными эффектами.

Выполнение одного и того же запроса на master и slave в разное время приведет к рассинхронизации данных.

**Плюсы:**

- Минимальный размер логов (записывается только текст запроса).
- Низкая нагрузка на дисковую подсистему и сеть.

**Минусы:**

- Небезопасен для целостности данных при использовании недетерминированных функций.
- Не является режимом по умолчанию в современных версиях MySQL (начиная с 5.7.7).

### 2. ROW (Row-Based Replication — RBR)

**Принцип:** В лог записывается бинарное представление **измененных строк** (состояние до и после изменения), а не исходный SQL-запрос.

**Надежность:** Формат полностью детерминирован. Например, функция `NOW()` не выполняется на slave заново — в лог копируется строка с уже вычисленным значением. Это гарантирует побайтовое совпадение данных в кластере.

**Плюсы:**

- Максимальная консистентность данных.
- Полная безопасность при использовании любых недетерминированных функций.
- Формат по умолчанию в современных версиях MySQL.

**Минусы:**

- Значительный рост объема логов при массовых операциях (например, `UPDATE` миллиона строк создаст соответствующее количество записей в логе).
- Увеличенная нагрузка на сеть и дисковый ввод-вывод.
- Сложность аудита (в логах не виден исходный SQL-запрос, вызвавший изменения).

### 3. MIXED (Mixed-Format Replication)

**Принцип:** Гибридный режим. По умолчанию используется `STATEMENT`, но при обнаружении запросов, которые могут привести к рассинхронизации (недетерминированных), MySQL автоматически переключается на `ROW` для записи этих конкретных событий.

**Плюсы:**

- Оптимальный баланс между надежностью и размером логов.
- Автоматическая защита от большинства проблем асинхронной репликации.

**Минусы:**

- Поведение системы менее предсказуемо по сравнению с чистыми режимами.
- Сложнее отлаживать проблемы репликации из-за смены форматов "на лету".

## Практические сценарии

### Проверка текущего формата

```sql
-- Проверка текущего значения параметра
SHOW VARIABLES LIKE 'binlog_format';
/* 
+---------------+-------+
| Variable_name | Value |
+---------------+-------+
| binlog_format | ROW   |
+---------------+-------+
*/

-- Проверка через системные переменные
SELECT @@GLOBAL.binlog_format;
-- -> ROW
```

### Изменение формата записи

Для постоянного изменения параметра необходимо отредактировать конфигурационный файл (`my.cnf` или `mysqld.cnf`):

```ini
[mysqld]
binlog_format = ROW
```

Изменение без перезагрузки (требует прав `SUPER` или `SYSTEM_VARIABLES_ADMIN`):

```sql
-- Изменение глобально (для новых подключений)
SET GLOBAL binlog_format = ROW;
-- -> Query OK, 0 rows affected

-- Изменение для текущей сессии
SET SESSION binlog_format = STATEMENT;
-- -> Query OK, 0 rows affected
```

> **Важно:** Изменение `binlog_format` применяется только к новым событиям. Формат записей в уже созданных файлах бинарного лога не меняется.

### Примеры проблемных запросов в STATEMENT

Ниже приведены примеры запросов, которые приведут к рассинхронизации данных при использовании формата `STATEMENT` (SBR):

```sql
-- Недетерминированные запросы:
INSERT INTO logs (dt, uid, msg) VALUES (NOW(), UUID(), 'event');
UPDATE users SET last_login = NOW() WHERE id = 1;
INSERT INTO random_data (val) VALUES (RAND());

-- Безопасные запросы:
INSERT INTO users (id, name) VALUES (10, 'Admin');
UPDATE accounts SET balance = balance - 100 WHERE id = 5;
```

## Дополнительная информация

### Влияние на производительность

- **STATEMENT:** Минимальное влияние на производительность, но высокий риск нарушения целостности данных на репликах.
- **ROW:** Требует дополнительных ресурсов CPU на сериализацию строк и существенно больше дискового пространства и пропускной способности сети.
- **MIXED:** Добавляет небольшую задержку на этапе анализа запроса оптимизатором для выбора формата записи.

### Рекомендации для MySQL 8.0+

В современных инфраструктурах формат **ROW** является промышленным стандартом. Использование **STATEMENT** не рекомендуется для продакшен-окружений из-за рисков рассинхронизации и ограничений при работе с новыми типами данных и функциями (например, JSON).

### Связь с GTID

При использовании **GTID (Global Transaction Identifier — глобальный идентификатор транзакции)** формат **ROW** обязателен для обеспечения корректной работы механизмов автоматического переключения мастера (failover).

### Просмотр событий в логе

```sql
-- Показать список файлов бинарного лога
SHOW BINARY LOGS;
/*
+------------------+-----------+-----------+
| Log_name         | File_size | Encrypted |
+------------------+-----------+-----------+
| mysql-bin.000001 |      1548 | No        |
+------------------+-----------+-----------+
*/

-- Просмотр содержимого конкретного лога
SHOW BINLOG EVENTS IN 'mysql-bin.000001' LIMIT 2;
```
