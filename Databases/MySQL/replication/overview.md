# Репликация MySQL: Обзор

**Актуально для:** MySQL 5.6+ / 8.0+ / 8.4 LTS

## Определения

**Репликация MySQL** — процесс автоматического копирования данных с основного сервера (**Источник / Source**) на один или несколько дополнительных серверов (**Реплика / Replica**). Это фундаментальный механизм для обеспечения отказоустойчивости, распределения нагрузки и защиты данных.

**Источник (Source)** — основной узел, принимающий операции записи (`INSERT`, `UPDATE`, `DELETE`). Все изменения фиксируются в бинарном логе (**Binary Log**). В устаревшей терминологии — **Master**.

**Реплика (Replica)** — узел-получатель, который считывает события из бинарного лога источника и применяет их к своей локальной копии данных. В устаревшей терминологии — **Slave**.

**Server UUID** — уникальный идентификатор каждого сервера в топологии (хранится в файле `auto.cnf`). Критически важен для работы GTID и предотвращения циклов в репликации.

**Heartbeat Mechanism** — механизм контроля активности соединения. Источник отправляет пакеты-сердцебиения реплике в периоды отсутствия данных, чтобы реплика знала, что соединение всё еще активно и источник не "завис".

## Основные концепции

### Назначение репликации

| Цель | Описание |
| :--- |  |
| **Высокая доступность (HA)** | Обеспечение непрерывности бизнеса. При сбое источника одна из реплик берет на себя его роль. Требует механизмов оркестрации (Orchestrator, MHA). |
| **Масштабирование чтения** | Снятие нагрузки с источника путем распределения запросов `SELECT` на реплики. Эффективно для систем с преобладанием чтения. |
| **Резервное копирование** | Минимизация влияния на продакшн. Бэкап снимается с реплики, что позволяет избежать блокировок и деградации производительности источника. |
| **Географическое распределение** | Снижение сетевых задержек (Latency) для конечных пользователей путем размещения реплик в разных дата-центрах или регионах. |
| **Изоляция нагрузки** | Выполнение тяжелых аналитических отчетов или миграций на выделенной реплике, не затрагивая OLTP-транзакции на мастере. |

### Типы репликации в MySQL

#### Асинхронная репликация (Standard)
Источник записывает транзакцию в бинарный лог и сразу подтверждает её выполнение клиенту. Передача данных на реплику происходит в фоновом режиме.
- **Принцип:** Fire-and-forget.
- **Риски:** Возможен лаг (Replication Lag) и потеря данных (RPO > 0) при аварии источника, если транзакции не успели передаться.

#### Полусинхронная репликация (Semisync)
Источник ожидает подтверждения от хотя бы одной реплики о том, что транзакция получена и записана в её Relay Log.
- **After-Sync (Lossless):** (MySQL 5.7+, рекомендуется) Источник сначала получает подтверждение от реплики, и только потом фиксирует транзакцию (Storage Engine Commit) и отвечает клиенту. Гарантирует отсутствие "фантомных данных" на мастере при сбое.
- **After-Commit (Legacy):** Источник фиксирует транзакцию локально, а затем ждет подтверждения. При сбое другие клиенты могли успеть увидеть данные на мастере, которых не окажется на реплике после Failover.

#### Групповая репликация (Group Replication)
Синхронная (на уровне сертификации) репликация, обеспечивающая консистентность во всей группе узлов. Использует протокол консенсуса Paxos.
- **Консистентность:** Транзакция фиксируется только после того, как большинство (Quorum) узлов группы подтвердили отсутствие конфликтов.
- **Отказоустойчивость:** Автоматическое обнаружение сбоев и перевыборы лидера (в Single-Primary режиме).
- **Ограничения:** Требует GTID, ROW-формат и наличие первичных ключей (Primary Keys) во всех таблицах.

Подробно о теории — в [Репликация баз данных](../../Concepts/replication.md).

### Ключевые компоненты и надежность

| Компонент | Описание |
| :--- | :--- |
| **Binary Log (Binlog)** | Логический журнал на источнике. Детали в [Форматы бинарного лога](./binlog_formats.md). |
| **Relay Log** | Буферный журнал на реплике для хранения событий перед применением. |
| **Crash-Safe Replication** | Механизм защиты от повреждения метаданных при сбое питания. Позиции хранятся в транзакционных InnoDB таблицах при `master_info_repository=TABLE` / `relay_log_info_repository=TABLE`: в MySQL 5.6/5.7 задаются явно (дефолт `FILE`), с 8.0 — по умолчанию, начиная с 8.4 настраиваются автоматически. |
| **Clone Plugin** | Физическое клонирование данных для сверхбыстрой инициализации новых узлов без необходимости ручного восстановления бэкапа. |

Подробное описание потоков и жизненного цикла события — в [Механизм работы репликации](./master_slave_mechanism.md).

## Предварительные требования

### Среда и инфраструктура

| Категория | Требование | Описание |
| :--- | :--- | :--- |
| **Сеть** | TCP/3306 | Доступ по сети между всеми узлами топологии. Проверьте файрволы, security groups и маршрутизацию. |
| **Время** | NTP / chrony | Синхронизация времени между всеми узлами обязательна. Расхождение во времени приводит к некорректным записям в бинарных логах и ошибкам мониторинга. |
| **Хранилище** | Выделенные диски | Рекомендуется размещать binlog, relay log и данные на отдельных физических устройствах для исключения contention. |
| **ОС** | Linux (RHEL/Debian) | Стандартные дистрибутивы с поддержкой systemd. Проверьте лимиты файлов (`ulimit -n`) и параметры ядра (`fs.file-max`). |
| **Ресурсы** | CPU/RAM | Для параллельной репликации (MTS) требуется достаточно ядер CPU. Нагрузка на реплику при применении может быть сопоставима с нагрузкой на источник. |
| **Идентификация** | `server_id` | Уникальное целое число (1-4294967295) на каждом узле топологии. |

### Требования к версиям и параметрам

- **Минимальная версия для GTID:** MySQL 5.6 (базовая), 5.7 (стабильная), 8.0+ (рекомендуемая).
- **Обязательный формат binlog:** `ROW` для GTID и Group Replication.
- **Crash-Safe:** В MySQL 8.0 параметры `master_info_repository` и `relay_log_info_repository` установлены в `TABLE` по умолчанию. Не меняйте их на `FILE`. Обе переменные **удалены в MySQL 8.3.0**.

## Валидация

### Проверка базового здоровья

```sql
-- Быстрый статус репликации (MySQL 8.0.22+)
SHOW REPLICA STATUS\G

-- Ключевые поля для проверки:
-- Replica_IO_Running: Yes
-- Replica_SQL_Running: Yes
-- Seconds_Behind_Source: 0
-- Last_Error_Number: 0
```

### Проверка GTID-консистентности

```sql
-- Убедиться, что все транзакции источника присутствуют на реплике
SELECT GTID_SUBSET(@@GLOBAL.gtid_executed, @@GLOBAL.gtid_purged) AS is_consistent;
-- Должно возвращать 1
```

### Проверка потоков Performance Schema

```sql
-- Состояние каналов репликации (Multi-Source)
SELECT CHANNEL_NAME, SERVICE_STATE, LAST_ERROR_NUMBER, LAST_ERROR_MESSAGE
FROM performance_schema.replication_connection_status;

-- Статус рабочих потоков MTS
SELECT WORKER_ID, THREAD_ID, LAST_APPLIED_TRANSACTION
FROM performance_schema.replication_applier_status_by_worker;
```

### Проверка шифрования

Состояние TLS/TLS-канала — это поле вывода `SHOW REPLICA STATUS`, а не колонка Performance Schema:

```sql
SHOW REPLICA STATUS\G
-- Source_SSL_Allowed: Yes  --> шифрование разрешено для канала
-- Source_SSL_Verify_Server_Cert: Yes --> сертификат источника проверяется
-- (в MySQL 5.7 и ранее те же поля называются Master_SSL_Allowed / Master_SSL_Verify_Server_Cert)
```

## Практические сценарии

### Мониторинг и диагностика

Для оперативной проверки состояния репликации используется стандартная команда (синтаксис MySQL 8.0.22+):

```sql
-- Просмотр статуса на реплике
SHOW REPLICA STATUS\G

-- Ключевые показатели здоровья:
-- Replica_IO_Running: Yes  --> Соединение с источником установлено, бинлоги читаются.
-- Replica_SQL_Running: Yes --> События успешно применяются к локальной БД.
-- Seconds_Behind_Source: 0  --> Ориентировочный лаг в секундах. 
-- Last_SQL_Error:           --> Сообщение о последней ошибке выполнения запроса.
```

**Ограничение `Seconds_Behind_Source`:** Этот показатель может быть неточным при сетевых разрывах или выполнении очень длинных транзакций. Для точного мониторинга в высоконагруженных системах используйте **Performance Schema**:

```sql
-- Проверка состояния потоков по каналам (для Multi-Source).
-- В replication_connection_status нет колонок с задержкой в секундах:
-- задержку считают по временным меткам воркеров (см. следующий запрос).
SELECT 
    CHANNEL_NAME, 
    SERVICE_STATE, 
    LAST_ERROR_NUMBER, 
    LAST_ERROR_MESSAGE 
FROM performance_schema.replication_connection_status;

-- Детальный статус рабочих потоков при параллельной репликации (MTS)
SELECT * FROM performance_schema.replication_applier_status_by_worker;
```

### Параллельная репликация (Multi-Threaded Slave, MTS)
MTS позволяет использовать несколько ядер CPU для применения транзакций. До 8.0.26 репликация по умолчанию однопоточна; с 8.0.27 MTS включён по умолчанию (4 воркера, `LOGICAL_CLOCK`). Полная методика — `parallel_replication_mts.md`.

**Настройка MTS:**
```ini
[mysqld]
# Число воркеров: начать с 4, повысить до числа ядер CPU реплики
replica_parallel_workers = 8

# Алгоритм распределения:
# DATABASE (устаревший) - параллелит только разные БД.
# LOGICAL_CLOCK (рекомендуется) - параллелит транзакции, которые выполнялись одновременно на источнике.
replica_parallel_type = LOGICAL_CLOCK

# Защита от повреждения метаданных при сбоях
relay_log_recovery = ON
```

### Отставание репликации (Replication Lag)
**Типовые причины и диагностика:**
1. **CPU/Disk Bound:** SQL-поток не успевает записывать данные. Решение: MTS, переход на SSD.
2. **Lock Wait:** Длительные блокировки от бэкапов или аналитических запросов на реплике. Решение: `SET GLOBAL replica_preserve_commit_order = ON`.
3. **Network Latency:** Большая задержка между ДЦ. Решение: Тюнинг TCP стека или переход на каскадную репликацию.

## Безопасность и фильтрация

### Рекомендации по безопасности
1. **Принцип минимальных прав:** Пользователь репликации должен иметь только грант `REPLICATION SLAVE`. Грант `REPLICATION CLIENT` полезен для мониторинга.
2. **Шифрование:** Всегда используйте TLS (`SOURCE_SSL=1`) при репликации через интернет или между недоверенными сегментами сети.
3. **Изоляция:** Реплика должна работать в режиме `read_only = ON` (или `super_read_only = ON` для полной защиты), чтобы предотвратить случайную запись данных, нарушающую консистентность.

### Фильтрация данных
Используйте параметры `replicate-do-db` или `replicate-ignore-db` с осторожностью:
- **Риск:** Фильтры на стороне реплики могут привести к ошибкам в GTID-репликации, так как транзакции всё равно регистрируются в наборе `gtid_executed`.
- **Альтернатива:** Фильтрация на стороне источника (`binlog-do-db`) крайне не рекомендуется, так как данные будут навсегда потеряны для всех потенциальных реплик и PITR-восстановления.

## Устранение неисправностей

Обзор типовых сценариев и точек диагностики. Для детальных пошаговых решений см. [Управление и отладка](./management_debug.md).

| Категория | Типичные симптомы | Первичная диагностика |
| :--- | :--- | :--- |
| **Сетевое соединение** | `Replica_IO_Running: Connecting` | Проверка портов, DNS, firewall, SSL-сертификатов. |
| **Применение данных** | `Replica_SQL_Running: No`, `Last_SQL_Error` | Дубликаты (1062), отсутствие записей (1032), ошибки прав доступа. |
| **GTID-конфликты** | Ошибка 1789 (очищены binlog на источнике), 1885 (реплика «обгоняет» источник), 1782 (`GTID_NEXT = 'ANONYMOUS'` при `gtid_mode = ON`) | Несоответствие `gtid_executed` и `gtid_purged`, `RESET BINARY LOGS AND GTIDS` (в 5.7/8.0 — `RESET MASTER`) на источнике, дубликаты UUID. Подробнее — [gtid.md — Устранение неисправностей](./gtid.md#устранение-неисправностей). |
| **Производительность** | Растущий `Seconds_Behind_Source` | CPU/Disk bound на реплике, длинные транзакции, нехватка `replica_parallel_workers`. |
| **Целостность метаданных** | Репликация не стартует после ребута | Проверка `relay_log_recovery`, Crash-Safe репозиториев. |

**Важно:** При переходе по ошибкам используйте Performance Schema для точного определения активного потока и состояния очередей. Для проверки консистентности данных на источнике и реплике применяйте `pt-table-checksum` из Percona Toolkit.

## Рекомендации

### Проектирование и развертывание
- **Версии:** Используйте одинаковые Major версии MySQL на источнике и реплике. Миграция через GTID упрощает cross-version сценарии, но тестируйте совместимость DDL перед продом.
- **Идентификация:** Всегда настраивайте `server_id` и `server_uuid` явно. Не оставляйте авто-генерацию в производственных кластерах.
- **Формат binlog:** Используйте `ROW` повсеместно. `STATEMENT` допустим только в изолированных read-only сценариях без репликации.
- **Crash-Safe:** Включите `relay_log_recovery = ON`. Хранение метаданных в таблицах (`master_info_repository=TABLE`, `relay_log_info_repository=TABLE`) — в MySQL 5.6/5.7 задаётся явно (дефолт `FILE`), с MySQL 8.0 — поведение по умолчанию; обе переменные **удалены в MySQL 8.3.0** и на 8.4 LTS не настраиваются.

### Эксплуатация и мониторинг
- **NTP:** Синхронизируйте время на всех узлах через chrony или systemd-timesyncd. Дрожание времени (clock skew) искажает временные метки binlog и ломает мониторинг лага.
- **Мультиплексор:** Для масштабирования чтения используйте ProxySQL или HAProxy вместо ручного балансирования на уровне приложения.
- **Резервное копирование:** Снимайте бэкапы с реплик, а не с источника. Используйте физические бэкапы (XtraBackup) для больших инсталляций и `mysqldump` для малых.
- **Мониторинг:** Интегрируйте метрики репликации (`Seconds_Behind_Source`, состояние потоков, GTID-лаги) в систему мониторинга (Prometheus + Grafana / Zabbix). Установите алерты на рост лага > 60 секунд.

### Безопасность
- **Аутентификация:** Используйте отдельного пользователя `repl_user` с минимальными правами (`REPLICATION SLAVE`, `REPLICATION CLIENT`). Никогда не используйте `root` для репликации.
- **Шифрование в transit:** Включайте `SOURCE_SSL=1` и `REQUIRE SSL` для пользователя репликации. Дляproduction используйте сертификаты, подписанные внутренним CA, а не самоподписанные.
- **Изоляция на уровне ОС:** Размещайте MySQL в контейнере или chroot с ограниченными правами. Отключайте ненужные плагины (`SELECT * FROM information_schema.plugins;`).

## Граничные случаи

### Смешанный режим GTID и Non-GTID
При миграции на GTID допускается временное смешанное состояние (`gtid_mode = ON_PERMISSIVE` / `OFF_PERMISSIVE`), но в steady-state должна работать либо чистая GTID-топология, либо классическая File:Pos. Смешанный режим запрещает автоматический Failover и усложняет диагностику.

### Частичные GTID-наборы при восстановлении
Если на реплике были выполнены дополнительные транзакции (например, через `super_read_only = OFF`), её `gtid_executed` будет содержать "лишние" GTID. При повторном подключении к источнику с `SOURCE_AUTO_POSITION = 1` источник увидит, что реплика запросила транзакции, которых нет в её наборе, и репликация остановится с ошибкой. Решение: пересоздание реплики из чистого бэкапа или ручная очистка `gtid_executed`.

### Delayed Replication с GTID
Используется для защиты от логических ошибок (`DROP TABLE`, ошибочный `UPDATE`). Настройка:
```sql
CHANGE REPLICATION SOURCE TO SOURCE_DELAY=1800;  -- 30 минут
```
Полная методика, откат ошибочных изменений и диагностика — **[Отложенная репликация](./delayed_replication.md)**. Окно задержки должна превышать время обнаружения ошибки человеком. При Failover задержанная реплика теряет данные за время отставания от источника.

### Повреждение `mysql.gtid_executed`
Таблица `mysql.gtid_executed` является критически важной. При её повреждении реплика потеряет историю примененных GTID и начнет повторно применять старые транзакции, что приведет к дубликатам (ошибка 1062). Для восстановления используйте `RESET BINARY LOGS AND GTIDS` (в MySQL 5.7 и 8.0 — `RESET MASTER`; оператор удалён начиная с MySQL 8.4) только если это источник без реплик, либо пересоздание реплики из бэкапа.

### Перестройка реплики с изменением данных
Если данные на реплике были изменены вручную, а затем включена GTID-репликация, возможны конфликты. Правильная процедура:
1. Остановить репликацию (`STOP REPLICA`).
2. Сделать полный дамп с источника (`mysqldump` / XtraBackup).
3. Очистить data-директорию реплики.
4. Восстановить дамп.
5. Настроить `SOURCE_AUTO_POSITION = 1` и запустить (`START REPLICA`).

### Мультисорсная репликация и GTID
Multi-Source репликация (MySQL 5.7+) позволяет одной реплике принимать потоки от нескольких источников через каналы (`CHANNEL`). Каждый канал имеет собственный `gtid_executed` набор. Управление:
```sql
-- Список каналов
SELECT CHANNEL_NAME, SERVICE_STATE FROM performance_schema.replication_connection_status;

-- Управление отдельным каналом
START REPLICA IO_THREAD FOR CHANNEL 'channel_source1';
```

## Дополнительная информация

### Топологии репликации
- Звезда, каскадная, кольцевая, multi-master (classic), ромбовидная (diamond) и multi-source — описание, требования, сценарии и устранение неисправностей — в [топологиях репликации](topologies.md) (SSoT).

### Гибридная топология: синхронный master-master + асинхронная отложенная реплика

Для сценариев, где требуется максимальная доступность в основном дата-центре и защита от полного выхода из строя площадки, используется комбинация:

- **Внутри основного дата-центра:** синхронная репликация (semisync/group replication) между двумя узлами. RPO ≈ 0 для локальных сбоев.
- **Вторичный дата-центр:** асинхронная репликация с задержкой (`SOURCE_DELAY = 1800` — 30 минут). Позволяет откатиться после логической ошибки (например, `DROP TABLE` или ошибочный `UPDATE`), если ошибка обнаружена в течение окна задержки.

**Важно:** задержка репликации защищает только от логических ошибок на источнике. При полном выходе из строя основного дата-центра возможна потеря данных за время, пока реплика не догонит источник. Для оценки риска используйте мониторинг `Seconds_Behind_Source` и размер окна задержки.
