# Репликация MySQL: Обзор

## Определения

**Репликация MySQL** — процесс автоматического копирования данных с одного сервера базы данных (Источника) на один или несколько других серверов (Реплик). Это фундаментальный механизм для обеспечения отказоустойчивости, распределения нагрузки и защиты данных.

**Источник (Source)** — основной узел, принимающий операции записи (`INSERT`, `UPDATE`, `DELETE`). Все изменения фиксируются в бинарном логе (**Binary Log**). В устаревшей терминологии — **Master**.

**Реплика (Replica)** — узел-получатель, который считывает события из бинарного лога источника и применяет их к своей локальной копии данных. В устаревшей терминологии — **Slave**.

**Server UUID** — уникальный идентификатор каждого сервера в топологии (хранится в файле `auto.cnf`). Критически важен для работы GTID и предотвращения циклов в репликации.

## Основные концепции

### Назначение репликации

| Цель | Описание |
| :--- | :--- |
| **Высокая доступность (HA)** | При выходе из строя источника одна из реплик может быть повышена до роли источника (Failover). |
| **Масштабирование чтения** | Запросы на чтение (`SELECT`) распределяются между репликами, снижая нагрузку на основной узел. |
| **Резервное копирование** | Создание бэкапов (например, через `mysqldump` или `Percona XtraBackup`) выполняется на реплике, не блокируя источник. |
| **Географическое распределение** | Размещение данных ближе к пользователям в разных регионах для снижения сетевых задержек. |
| **Аналитика и отчетность** | Выполнение тяжелых OLAP-запросов на выделенном узле, чтобы не аффектить производительность OLTP на мастере. |

### Типы репликации в MySQL

#### Асинхронная репликация (Стандарт)
Источник записывает транзакцию в бинарный лог и сразу подтверждает её клиенту, не дожидаясь доставки на реплику.
- **Плюсы:** Минимальное влияние на производительность записи.
- **Минусы:** Риск потери данных, если источник упал до того, как реплика успела забрать события.

#### Полусинхронная репликация (Semisync)
Источник ожидает подтверждения (ACK) хотя бы от одной реплики о том, что транзакция получена и записана в её Relay Log.
- **After-Sync (Lossless):** (MySQL 5.7+) Гарантирует, что данные не будут потеряны, так как транзакция фиксируется в хранилище источника только после получения ACK.
- **After-Commit (Legacy):** Фиксация происходит до получения ACK. В случае сбоя возможна ситуация "фантомного чтения" на мастере.

#### Групповая репликация (Group Replication)
Обеспечивает синхронное (или близкое к нему) взаимодействие на основе протокола Paxos. Является основой **MySQL InnoDB Cluster**.
- **Multi-Primary:** Запись возможна на любой узел группы.
- **Single-Primary:** Один узел записи, остальные — для чтения, автоматические выборы нового лидера.

Подробно о теории — в [Репликация баз данных](../../Concepts/replication.md#типы-репликации-синхронная-vs-асинхронная).

### Ключевые компоненты

| Компонент | Описание |
| :--- | :--- |
| **Binary Log (Binlog)** | Журнал на источнике, содержащий все изменения данных. Детали в [Форматы бинарного лога](./binlog_formats.md). |
| **Relay Log** | Локальный журнал на реплике, куда I/O-поток записывает события, полученные от источника, перед их применением. |
| **Metadata Repositories** | Файлы (`master.info`, `relay-log.info`) или таблицы (`mysql.slave_master_info`, `mysql.slave_relay_log_info`), хранящие текущую позицию репликации. |
| **Clone Plugin** | Механизм быстрого развертывания новых реплик через копирование физических файлов данных (доступен с 8.0.17). |

Подробное описание потоков и жизненного цикла события — в [Механизм работы репликации](./master_slave_mechanism.md).

## Режимы и форматы

### Форматы бинарного лога
1.  **ROW (Рекомендуемый):** Записывает состояние строк. Гарантирует консистентность, обязателен для современных функций.
2.  **STATEMENT:** Записывает SQL-запросы. Компактен, но вызывает проблемы с недетерминированными функциями (`UUID()`, `NOW()`).
3.  **MIXED:** Автоматический выбор формата в зависимости от типа операции.

Детали в [Форматы бинарного лога](./binlog_formats.md).

### Режимы идентификации
-   **Классический (File & Pos):** Позиционирование по имени файла и смещению в байтах. Требует ручного вмешательства при Failover.
-   **GTID (Global Transaction Identifier):** Каждая транзакция имеет глобальный ID. Репликация настраивается автоматически через `SOURCE_AUTO_POSITION = 1`.

Детали в [GTID-репликация](./gtid.md).

## Практические сценарии

### Мониторинг и диагностика
Для проверки состояния репликации (синтаксис MySQL 8.0.22+):

```sql
-- Просмотр статуса на реплике
SHOW REPLICA STATUS\G

-- Ключевые поля:
-- Replica_IO_Running: Yes  --> Реплика подключена к источнику
-- Replica_SQL_Running: Yes --> Реплика применяет данные
-- Seconds_Behind_Source: 0  --> Текущий лаг репликации
```

### Отставание репликации (Replication Lag)
**Основные причины:**
-   Тяжелые или длительные запросы на источнике.
-   Недостаточная производительность дисковой подсистемы на реплике.
-   Однопоточное применение данных (SQL Thread).

**Решение:** Использование параллельной репликации (**MTS — Multi-Threaded Slave**). Настройка `replica_parallel_workers > 0` и `replica_parallel_type = LOGICAL_CLOCK`.

## Безопасность репликации

1.  **Выделенный пользователь:** Всегда используйте отдельную учетную запись с минимальными правами (`REPLICATION SLAVE`).
2.  **Шифрование (SSL/TLS):** Включайте `REQUIRE SSL` для защиты трафика бинарных логов, особенно при репликации через публичные сети.
3.  **Фильтрация:** Используйте `replicate-do-db` или `replicate-ignore-db` с осторожностью, так как это может привести к нарушению консистентности при использовании GTID.

## Дополнительная информация

### Топологии репликации
-   **Source -> N Replicas:** Классическая "звезда".
-   **Chained (Cascading):** Source -> Replica 1 -> Replica 2. Помогает экономить сетевой трафик и ресурсы CPU на основном источнике.
-   **Multi-Source:** Одна реплика собирает данные из нескольких разных источников (шардов). Подробности в [Multi-Source репликация](./multi-source.md).
