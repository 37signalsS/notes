# Репликация MySQL: Обзор

## Определения

**Репликация MySQL** — процесс создания и поддержания идентичных копий данных на нескольких серверах. Это обеспечивает отказоустойчивость, масштабируемость и сохранность данных.

**Источник (Source)** — основной сервер, принимающий операции записи. Все изменения фиксируются в бинарном логе (**Binary Log**). В устаревшей терминологии — **Master**.

**Реплика (Replica)** — сервер-копия, который получает изменения от источника и применяет их к своим данным. В устаревшей терминологии — **Slave**.

## Основные концепции

### Назначение репликации

| Цель | Описание |
| :--- | :--- |
| Высокая доступность | При сбое источника одна из реплик может быть повышена до новой роли. |
| Масштабирование чтения | Запросы на чтение распределяются между несколькими репликами. |
| Резервное копирование | Бэкапы создаются на реплике, не нагружая основной источник. |
| Географическое распределение | Реплики размещаются ближе к конечным пользователям. |
| Отчетность и аналитика | Тяжелые аналитические запросы выполняются на выделенной реплике. |

### Типы репликации в MySQL

#### Асинхронная репликация (Стандарт)
Стандартный режим. Источник записывает транзакцию и сразу подтверждает её клиенту, не дожидаясь реплики.
- **Плюсы:** Максимальная производительность.
- **Минусы:** Риск потери данных при внезапном сбое источника (Replication Lag).

#### Полусинхронная репликация (Semisync)
Источник ждет подтверждения от хотя бы одной реплики о том, что транзакция получена и записана в Relay Log.
- **Плюсы:** Гарантирует наличие данных минимум на двух узлах.
- **Минусы:** Небольшая задержка на запись.

#### Групповая репликация (Group Replication)
Основана на протоколе Paxos (встроена в **InnoDB Cluster**). Обеспечивает синхронную (или близкую к ней) репликацию с автоматическим разрешением конфликтов и выбором лидера.
- **Режимы:** Single-Primary (один узел записи) или Multi-Primary (запись на все узлы).
- **Плюсы:** Высокая согласованность, автоматический Failover.

Подробно о теории — в [Репликация баз данных](../../Concepts/replication.md#типы-репликации-синхронная-vs-асинхронная).

### Ключевые компоненты

| Компонент | Описание |
| :--- | :--- |
| **Binary Log (Binlog)** | Журнал изменений на источнике. Основа всей репликации — [Форматы бинарного лога](./binlog_formats.md). |
| **Relay Log** | Временный журнал на реплике, куда записываются события, полученные от источника. |
| **Потоки (Threads)** | **Dump thread** (на источнике), **Receiver/IO thread** и **Applier/SQL thread** (на реплике) — [Механизм работы](./master_slave_mechanism.md). |
| **Clone Plugin** | Механизм быстрого создания реплик путем копирования физических данных (вместо логического дампа). Доступен с MySQL 8.0.17. |

### Форматы бинарного лога

1.  **ROW (Рекомендуемый):** Записывает фактические изменения строк. Самый надежный, используется по умолчанию с 5.7.
2.  **STATEMENT:** Записывает SQL-запросы. Компактный, но небезопасен для недетерминированных функций.
3.  **MIXED:** Автоматическое переключение между STATEMENT и ROW.

Подробно — в [Форматы бинарного лога](./binlog_formats.md).

### Режимы идентификации

-   **Классический (File & Pos):** Репликация по имени файла и позиции в логе. Сложна в управлении при Failover.
-   **GTID (Global Transaction Identifier):** Каждая транзакция имеет уникальный ID (`UUID:N`). Репликация настраивается через `SOURCE_AUTO_POSITION = 1`.

Подробно — в [GTID-репликация](./gtid.md).

## Практические сценарии

### Проверка состояния репликации (MySQL 8.0.22+)

```sql
-- Просмотр статуса на реплике
SHOW REPLICA STATUS\G
-- → Replica_IO_Running: Yes (поток чтения логов работает)
-- → Replica_SQL_Running: Yes (поток применения данных работает)
-- → Seconds_Behind_Source: 0 (отставание отсутствует)
```

### Проверка конфигурации Binlog и GTID

```sql
-- Формат лога
SELECT @@binlog_format;
-- → ROW

-- Статус GTID
SELECT @@gtid_mode;
-- → ON
```

### Диагностика типичных ошибок

```sql
-- Последние ошибки в выводе статуса
SHOW REPLICA STATUS\G
-- → Last_IO_Error: ...
-- → Last_SQL_Error: ...
```

Подробная диагностика — в [Управление и отладка репликации](./management_debug.md).

## Дополнительная информация

### Топологии репликации

1.  **Source → N Replicas:** Масштабирование чтения.
2.  **Цепочка (Chained):** Источник → Реплика 1 → Реплика 2. Снижает нагрузку на основной источник.
3.  **Multi-Source:** Одна реплика получает данные от нескольких независимых источников — [Multi-Source репликация](./multi-source.md).

Подробно о топологиях — в [Репликация баз данных](../../Concepts/replication.md#топологии-репликации).

### Версии MySQL и возможности

| Версия | Ключевые изменения |
| :--- | :--- |
| **5.6** | Появление GTID, репликация по базе данных. |
| **5.7** | ROW-формат по умолчанию, параллельная репликация (LOGICAL_CLOCK). |
| **8.0** | Group Replication (GA), Clone Plugin, переименование терминологии (Source/Replica). |
