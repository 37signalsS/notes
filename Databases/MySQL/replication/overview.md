# Репликация MySQL: Обзор

## Definitions

**Репликация MySQL** — процесс создания и поддержания идентичных копий (реплик) базы данных на нескольких серверах. Данные копируются с основного сервера (**Master**) на один или несколько подчиненных серверов (**Slave**).

**Master (Ведущий)** — сервер, на котором происходят все операции записи. Изменения фиксируются в бинарном логе.

**Slave (Ведомый)** — сервер-копия, который получает изменения от Master и применяет их к своей копии данных.

## Basic Concepts

### Назначение репликации

| Цель | Описание |
| :--- | :--- |
| Высокая доступность | При сбое Master один из Slave может взять его роль |
| Масштабирование чтения | Запросы на чтение распределяются между репликами |
| Резервное копирование | Бэкапы создаются на реплике без нагрузки на Master |
| Географическое распределение | Реплики размещаются ближе к пользователям |
| Тестирование | Тестовые запросы выполняются на реплике |

### Типы репликации в MySQL

#### Асинхронная репликация

Стандартный режим MySQL. Транзакция на Master считается завершенной сразу после локальной записи. Передача на Slave происходит в фоновом режиме.

- **Плюсы:** Минимальная задержка записи, высокая доступность
- **Минусы:** Возможна потеря данных при сбое Master, отставание реплики

Подробно о компромиссах синхронной и асинхронной репликации — в [Concepts/replication.md](../../Concepts/replication.md#синхронная-vs-асинхронная).

#### Полусинхронная репликация

Опциональный режим (плагин `semisync`). Master ждет подтверждения от хотя бы одного Slave перед подтверждением клиенту.

- **Плюсы:** Гарантия, что данные есть хотя бы на одной реплике
- **Минусы:** Увеличенная задержка записи

#### Улучшенная полусинхронная (MySQL 5.7+)

Режим `AFTER_COMMIT`. Master ждет подтверждения от Slave только на этапе коммита, что уменьшает задержку.

### Ключевые компоненты

| Компонент | Описание |
| :--- | :--- |
| **Бинарный лог (Binary Log)** | Журнал всех событий, изменяющих данные (DML/DDL). Основа репликации — [binlog_formats.md](./binlog_formats.md) |
| **Журнал ретрансляции (Relay Log)** | Копия binlog на Slave. I/O-поток записывает, SQL-поток читает — [master_slave_mechanism.md](./master_slave_mechanism.md) |
| **Потоки репликации** | Binlog Dump (Master), I/O Thread (Slave), SQL Thread (Slave) |

### Форматы бинарного лога

| Формат | Описание | Рекомендация |
| :--- | :--- | :--- |
| **STATEMENT** | Запись SQL-запросов | Устарел, небезопасен |
| **ROW** | Запись измененных строк | По умолчанию с MySQL 5.7.7 |
| **MIXED** | Гибрид STATEMENT и ROW | Для специфичных сценариев |

Подробно — в [binlog_formats.md](./binlog_formats.md).

### Режимы с GTID

**GTID (Global Transaction Identifier)** — уникальный идентификатор транзакции формата `UUID:N`. Упрощает failover и настройку репликации.

- **Классическая репликация:** По координатам binlog (`MASTER_LOG_FILE`, `MASTER_LOG_POS`)
- **GTID-репликация:** Автоматическое определение позиции (`MASTER_AUTO_POSITION = 1`)

Подробно — в [gtid.md](./gtid.md).

## Practical Scenarios

### Быстрая проверка статуса репликации

```sql
-- На Slave: проверка состояния
SHOW SLAVE STATUS\G

-- Ключевые поля:
--   Slave_IO_Running: Yes
--   Slave_SQL_Running: Yes
--   Seconds_Behind_Master: 0
```

### Проверка режима GTID

```sql
-- Проверка включенного GTID
SELECT @@GLOBAL.gtid_mode;

-- Проверка выполненных GTID
SELECT @@GLOBAL.gtid_executed;
```

### Проверка формата binlog

```sql
-- Текущий формат бинарного лога
SHOW VARIABLES LIKE 'binlog_format';
```

### Диагностика проблем

```sql
-- Проверка ошибок репликации
SHOW SLAVE STATUS\G | grep -E 'Last_IO_Error|Last_SQL_Error'

-- Проверка отставания
SHOW SLAVE STATUS\G | grep Seconds_Behind_Master
```

Подробная диагностика — в [management_debug.md](./management_debug.md).

## Additional Information

### Топологии репликации

#### Один Master, много Slave (1 → N)

Стандартная топология для масштабирования чтения.

```text
         +-----> [SLAVE 1]
[MASTER] --+-----> [SLAVE 2]
         +-----> [SLAVE N]
```

#### Цепочечная репликация

Slave выступает мастером для другого Slave.

```text
[MASTER] --> [SLAVE 1] --> [SLAVE 2] --> ...
```

#### Master-Master (кольцо)

Два Master-сервера реплицируются друг на друга. Требует осторожности из-за риска конфликтов.

```text
[MASTER 1] <--> [MASTER 2]
```

> **Рекомендация:** Избегайте активной записи на оба узла. Используйте Master-Master только для failover.

Подробно о топологиях — в [Concepts/replication.md](../../Concepts/replication.md#практические-сценарии-топологии-репликации).

### Версии MySQL и возможности

| Версия | Возможности репликации |
| :--- | :--- |
| 5.1 | Базовая асинхронная репликация |
| 5.5 | Полусинхронная репликация (плагин) |
| 5.6 | GTID, репликация по базе данных |
| 5.7 | Улучшенная параллельная репликация (LOGICAL_CLOCK) |
| 8.0 | WRITESET параллелизм, улучшенная производительность |

| Синхронная | Полусинхронная (плагин) | Встроенная |
| Параллелизм | `slave_parallel_workers` | `max_parallel_apply_workers` |
