# Репликация MySQL: Обзор

## Определения

**Репликация MySQL** — процесс создания и поддержания идентичных копий (реплик) базы данных на нескольких серверах. Данные копируются с основного сервера (**Master**) на один или несколько подчиненных серверов (**Slave**).

**Master (Ведущий)** — сервер, на котором происходят все операции записи. Изменения фиксируются в бинарном логе (Binary Log).

**Slave (Ведомый)** — сервер-копия, который получает изменения от Master и применяет их к своей копии данных. В современных версиях MySQL (8.0+) используется терминология **Source** (Источник) и **Replica** (Реплика).

## Основные концепции

### Назначение репликации

| Цель | Описание |
| :--- | :--- |
| Высокая доступность | При сбое Master один из Slave может взять его роль |
| Масштабирование чтения | Запросы на чтение распределяются между репликами |
| Резервное копирование | Бэкапы создаются на реплике без нагрузки на Master |
| Географическое распределение | Реплики размещаются ближе к пользователям |
| Тестирование | Тестовые запросы выполняются на реплике |

### Типы репликации в MySQL

#### Асинхронная репликация

Стандартный режим MySQL. Транзакция на Master считается завершенной сразу после локальной записи. Передача на Slave происходит в фоновом режиме.

- **Плюсы:** Минимальная задержка записи, высокая доступность.
- **Минусы:** Возможна потеря данных при сбое Master, отставание реплики (Replication Lag).

Подробно о компромиссах синхронной и асинхронной репликации — в [Репликация баз данных](../../Concepts/replication.md#синхронная-vs-асинхронная).

#### Полусинхронная репликация

Опциональный режим (плагин `semisync`). Master ждет подтверждения от хотя бы одного Slave о получении события перед подтверждением транзакции клиенту.

- **Плюсы:** Гарантия наличия данных хотя бы на одной реплике.
- **Минусы:** Увеличенная задержка записи.

#### Улучшенная полусинхронная (MySQL 5.7+)

Режим `AFTER_COMMIT`. Master ждет подтверждения от Slave только на этапе завершения транзакции (commit), что уменьшает задержку для клиента.

### Ключевые компоненты

| Компонент | Описание |
| :--- | :--- |
| **Бинарный лог (Binary Log)** | Журнал всех событий, изменяющих данные: DML (Data Manipulation Language) и DDL (Data Definition Language). Основа репликации — [Форматы бинарного лога](./binlog_formats.md) |
| **Журнал ретрансляции (Relay Log)** | Копия бинарного лога на стороне Slave. I/O (Input/Output) поток записывает данные, SQL поток их считывает — [Механизм Master-Slave](./master_slave_mechanism.md) |
| **Потоки репликации** | Binlog Dump (на Master), I/O Thread (на Slave), SQL Thread (на Slave) |

### Форматы бинарного лога

| Формат | Описание | Рекомендация |
| :--- | :--- | :--- |
| **STATEMENT** | Запись SQL (Structured Query Language) запросов | Устарел, небезопасен для некоторых функций |
| **ROW** | Запись измененных строк | По умолчанию с MySQL 5.7.7, самый надежный |
| **MIXED** | Гибрид STATEMENT и ROW | Переключается автоматически в зависимости от запроса |

Подробно — в [Форматы бинарного лога](./binlog_formats.md).

### Режимы с GTID

**GTID (Global Transaction Identifier)** — уникальный идентификатор транзакции формата `UUID:N` (UUID — Universally Unique Identifier). Упрощает процесс переключения мастера (failover) и настройку репликации.

- **Классическая репликация:** По координатам бинарного лога (`MASTER_LOG_FILE`, `MASTER_LOG_POS`).
- **GTID-репликация:** Автоматическое определение позиции (`MASTER_AUTO_POSITION = 1`).

Подробно — в [GTID-репликация](./gtid.md).

## Практические сценарии

### Быстрая проверка статуса репликации

```sql
-- На Slave: проверка состояния
SHOW SLAVE STATUS\G
-- -> Slave_IO_Running: Yes
-- -> Slave_SQL_Running: Yes
-- -> Seconds_Behind_Master: 0
```

### Проверка режима GTID

```sql
-- Проверка включенного GTID
SELECT @@GLOBAL.gtid_mode;
-- -> ON

-- Проверка выполненных GTID
SELECT @@GLOBAL.gtid_executed;
-- -> 3e11fa47-71ca-11e1-9e33-c80aa9429562:1-542
```

### Проверка формата binlog

```sql
-- Текущий формат бинарного лога
SHOW VARIABLES LIKE 'binlog_format';
-- -> ROW
```

### Диагностика проблем

```sql
-- Проверка ошибок репликации
SHOW SLAVE STATUS\G
-- -> Last_IO_Error: 
-- -> Last_SQL_Error: 

-- Проверка отставания репликации
SHOW SLAVE STATUS\G
-- -> Seconds_Behind_Master: 0
```

Подробная диагностика — в [Управление и отладка репликации](./management_debug.md).

## Дополнительная информация

### Топологии репликации

1. **Один Master, много Slave (1 → N):** Стандартная топология для масштабирования операций чтения.
2. **Цепочечная репликация:** Slave выступает мастером для другого Slave, снижая нагрузку на основной Master.
3. **Master-Master (кольцо):** Два сервера реплицируются друг на друга. Требует осторожности из-за риска конфликтов при записи на оба узла.

Подробно о топологиях — в [Репликация баз данных](../../Concepts/replication.md#топологии-репликации).

### Версии MySQL и возможности

| Версия | Возможности репликации |
| :--- | :--- |
| 5.1 | Базовая асинхронная репликация |
| 5.5 | Полусинхронная репликация (плагин) |
| 5.6 | GTID, репликация по базе данных |
| 5.7 | Улучшенная параллельная репликация (LOGICAL_CLOCK) |
| 8.0 | WRITESET параллелизм, улучшенная производительность |

### Сравнение с другими СУБД

| Характеристика | MySQL | PostgreSQL |
| :--- | :--- | :--- |
| Механизм | На базе бинарного лога | Потоковая передача WAL (Write Ahead Log) |
| Синхронная | Полусинхронная (плагин) | Встроенная синхронная репликация |
| Параллелизм | `slave_parallel_workers` | `max_parallel_apply_workers` |
