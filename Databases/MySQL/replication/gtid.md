# Репликация на основе GTID (Global Transaction Identifier)

## Определения

**GTID (Global Transaction Identifier)** — уникальный идентификатор транзакции, автоматически присваиваемый каждой транзакции при её выполнении на master-сервере. Он гарантирует однозначную идентификацию транзакции во всём кластере репликации.

**Формат GTID:** `source_id:transaction_id`

- `source_id` — UUID (Universally Unique Identifier, Универсальный уникальный идентификатор) сервера (например, `3E11FA47-71CA-11E1-9E33-C80AA9429562`).
- `transaction_id` — порядковый номер транзакции (например, `1-542`).

**GTID-репликация** — режим репликации, при котором slave-сервер отслеживает выполненные транзакции по их GTID, а не по физической позиции (файлу и смещению) в бинарном логе.

## Основные концепции

### Преимущества GTID перед классической репликацией

| Преимущество | Описание |
| :--- | :--- |
| Упрощённый Failover | При переключении master-сервера не нужно вручную искать имя файла и позицию в бинарном логе. |
| Автоматическое позиционирование | Slave самостоятельно определяет, какие транзакции из лога master-сервера уже были применены. |
| Гарантированная консистентность | Каждая транзакция выполняется в кластере ровно один раз, что предотвращает дублирование. |
| Идемпотентность | Повторная попытка применения транзакции с уже известным GTID автоматически игнорируется. |

### Принцип работы

1. Каждая транзакция на master-сервере получает уникальный GTID перед записью в бинарный лог.
2. Slave-сервер считывает транзакции, сохраняет полученные идентификаторы в системной таблице `mysql.gtid_executed`.
3. При восстановлении соединения или смене источника репликации slave сообщает master-серверу диапазон уже выполненных транзакций.
4. Master-сервер отправляет только те транзакции, GTID которых отсутствует в списке выполненных на slave.

### Требования и ограничения

- **Однородность режима:** Все серверы в топологии репликации должны использовать режим GTID одновременно.
- **Консистентность DDL (Data Definition Language):** Параметр `enforce_gtid_consistency = ON` обязателен и запрещает операции, которые могут привести к рассинхронизации (например, `CREATE TABLE ... SELECT`).
- **Транзакционные движки:** Рекомендуется использование InnoDB, так как изменения фиксируются в системных таблицах транзакционно.

## Практические сценарии

### 1. Включение GTID через конфигурацию

Добавьте следующие параметры в файл конфигурации (`my.cnf` или `mysqld.cnf`) на **всех** узлах кластера:

```ini
[mysqld]
# Включение режима GTID
gtid_mode = ON
# Обеспечение строгой консистентности транзакций
enforce_gtid_consistency = ON
# Обязательные параметры для работы GTID
log_bin = /var/log/mysql/mysql-bin.log
log_slave_updates = ON
server-id = 101
```

После изменения конфигурации требуется перезапуск службы MySQL:

```bash
sudo systemctl restart mysql
# -> (служба перезапущена без ошибок)
```

### 2. Настройка репликации с использованием GTID

Для активации автоматического позиционирования на slave-сервере используется параметр `MASTER_AUTO_POSITION = 1`.

```sql
-- Выполняется на Slave
CHANGE MASTER TO
  MASTER_HOST='192.168.1.10',
  MASTER_USER='repl_user',
  MASTER_PASSWORD='secure_password',
  MASTER_AUTO_POSITION = 1;
-- -> Query OK, 0 rows affected

START SLAVE;
-- -> Query OK, 0 rows affected
```

Проверка статуса репликации:

```sql
SHOW SLAVE STATUS\G
/*
             Slave_IO_Running: Yes
            Slave_SQL_Running: Yes
                Auto_Position: 1
           Retrieved_Gtid_Set: 3E11FA47...:1-100
            Executed_Gtid_Set: 3E11FA47...:1-100
*/
```

### 3. Пропуск проблемной транзакции

Если репликация остановилась из-за конкретной транзакции, в режиме GTID нельзя использовать `SET GLOBAL SQL_SLAVE_SKIP_COUNTER`. Вместо этого нужно "подделать" выполнение транзакции:

```sql
-- 1. Определяем проблемный GTID из SHOW SLAVE STATUS (поле Last_SQL_Error)
-- 2. "Выполняем" пустую транзакцию с этим GTID
STOP SLAVE;
SET GTID_NEXT='3E11FA47-71CA-11E1-9E33-C80AA9429562:542';
BEGIN; COMMIT;
SET GTID_NEXT='AUTOMATIC';
START SLAVE;
-- -> Query OK, 0 rows affected
```

### 4. Восстановление из дампа (gtid_purged)

При развертывании нового slave-сервера из бэкапа необходимо сообщить серверу, какие транзакции уже есть в данных, чтобы он не запрашивал их у мастера снова.

```sql
-- Очистка истории GTID и установка начальной точки
RESET MASTER;
SET GLOBAL gtid_purged = '3E11FA47-71CA-11E1-9E33-C80AA9429562:1-1000000';
-- -> Query OK, 0 rows affected
```

## Дополнительная информация

### Системные переменные и мониторинг

- `@@GLOBAL.gtid_executed`: Список всех транзакций, которые были применены на данном сервере.
- `@@GLOBAL.gtid_purged`: Набор транзакций, которые были выполнены, но чьи записи уже удалены из бинарных логов (например, в процессе ротации).
- `@@GLOBAL.gtid_mode`: Текущее состояние режима (`OFF`, `OFF_PERMISSIVE`, `ON_PERMISSIVE`, `ON`).

### Постепенная миграция (без простоя)

MySQL поддерживает динамическое включение GTID без одновременного перезапуска всех серверов через промежуточные состояния:

1. `OFF`: GTID выключен.
2. `OFF_PERMISSIVE`: Сервер генерирует анонимные транзакции, но принимает транзакции с GTID.
3. `ON_PERMISSIVE`: Сервер генерирует транзакции с GTID, но принимает анонимные.
4. `ON`: Полный режим GTID.
