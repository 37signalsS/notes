# Репликация на основе GTID (Global Transaction Identifier)

## Определения

**GTID (Global Transaction Identifier)** — уникальный идентификатор транзакции, автоматически присваиваемый каждой транзакции при её выполнении на источнике (source). Он гарантирует однозначную идентификацию транзакции во всём кластере репликации и остается неизменным при передаче по всей топологии.

**Формат GTID:** `source_id:transaction_id`
- `source_id` — `server_uuid` сервера, на котором была инициирована транзакция. Генерируется автоматически при первом запуске и хранится в файле `auto.cnf` в data-директории.
- `transaction_id` — порядковый номер транзакции (64-битное целое число), который инкрементируется для каждой новой транзакции на данном источнике.

**GTID Set (Набор GTID)** — группа идентификаторов, представляющая собой список UUID и диапазонов транзакций.
- Пример: `3E11FA47-71CA-11E1-9E33-C80AA9429562:1-140:150-200`.

**GTID-репликация** — режим репликации, при котором реплика отслеживает выполненные транзакции по их идентификаторам, а не по физическим координатам (имени файла и смещению) в бинарном логе.

## Основные концепции

### Преимущества GTID перед классической репликацией

| Преимущество | Описание |
| :--- | :--- |
| **Упрощённый Failover** | При смене мастера реплике достаточно указать новый хост. Позиция в логах определится автоматически, если нужные транзакции там есть. |
| **Автоматическое позиционирование** | Использование `SOURCE_AUTO_POSITION = 1` избавляет от ручного поиска координат `binlog_file/pos`. |
| **Гарантированная консистентность** | Каждая транзакция выполняется в кластере ровно один раз. Это предотвращает дублирование данных и облегчает восстановление. |
| **Идемпотентность** | Повторная попытка применения транзакции с уже известным GTID автоматически игнорируется сервером. |
| **Защита от циклов** | В кольцевой или multi-source репликации сервер автоматически игнорирует транзакции, которые он сам же и породил (на основе своего UUID). |

### Принцип работы

1. Каждая транзакция получает уникальный GTID перед записью в бинарный лог на мастере.
2. Реплика сохраняет информацию о выполненных GTID в системной таблице `mysql.gtid_executed` и в своих бинарных логах.
3. При восстановлении соединения (handshake) реплика сообщает источнику диапазон уже выполненных транзакций (`gtid_executed`).
4. Источник сканирует свои логи и отправляет только те транзакции, идентификаторы которых отсутствуют в списке реплики.

#### Таблица `mysql.gtid_executed`
Введена для повышения надежности и служит постоянным хранилищем выполненных GTID.
- **Назначение:** Позволяет серверу знать состояние GTID даже после удаления (пурджа) бинарных логов (`PURGE BINARY LOGS`).
- **Запись данных:** Данные в таблицу записываются при ротации логов, остановке сервера или транзакционно для каждого изменения (если бинарный лог на реплике выключен).
- **Сжатие (Compression):** Чтобы таблица не росла бесконечно, MySQL периодически выполняет сжатие диапазонов. Частота регулируется параметром `gtid_executed_compression_period`.

#### Механизм Simple Recovery
Параметр `binlog_gtid_simple_recovery = ON` (рекомендуется) ускоряет запуск сервера. Он заставляет MySQL сканировать только самый новый и самый старый бинарные логи для расчета `gtid_executed` и `gtid_purged`, вместо перебора всей цепочки файлов.

### Требования и ограничения

- **MySQL 5.6+:** Минимальная версия для базовой поддержки. Для полноценной работы в продакшене рекомендуется 5.7 или 8.0+.
- **ROW-формат:** Настоятельно рекомендуется для обеспечения консистентности (обязателен для Group Replication). Использование `STATEMENT` может привести к расхождениям.
- **Консистентность DDL:** Параметр `enforce_gtid_consistency = ON` запрещает операции, нарушающие атомарность GTID:
  - `CREATE TABLE ... SELECT` (в MySQL до 8.0.21).
  - `CREATE TEMPORARY TABLE` внутри транзакций.
  - Транзакции, затрагивающие как транзакционные (InnoDB), так и нетранзакционные (MyISAM) таблицы.
- **Однородность:** Все узлы в топологии должны использовать идентичный режим `gtid_mode`.
- **Фильтры репликации:** При использовании `replicate_do_db` или `replicate_ignore_db` отфильтрованные транзакции всё равно попадают в `gtid_executed` как **пустые транзакции**. Это необходимо, чтобы реплика "помнила" о факте их получения и не запрашивала их снова при переключении на другой источник.

## Практические сценарии

### 1. Включение режима GTID через конфигурацию

Добавьте следующие параметры в файл конфигурации (`my.cnf` или `mysqld.cnf`) на всех узлах:

```ini
[mysqld]
# Уникальный ID сервера (обязательно)
server-id = 101

# Включение режима GTID и строгой консистентности
gtid_mode = ON
enforce_gtid_consistency = ON

# Обязательные настройки для надежной репликации
log_bin = /var/log/mysql/mysql-bin.log
# Позволяет реплике записывать полученные изменения в свой binlog (нужно для каскадной репликации)
log_replica_updates = ON 
# Рекомендуемый формат бинлога
binlog_format = ROW

# Ускорение восстановления при запуске
binlog_gtid_simple_recovery = ON
```

После изменения конфигурации требуется перезапуск службы:
```bash
sudo systemctl restart mysql
# → Проверяем статус: SELECT @@GLOBAL.gtid_mode;
```

### 2. Динамическая миграция на GTID (без простоя)

Если серверы уже работают в классическом режиме, можно перейти на GTID без остановки записи, последовательно меняя `gtid_mode` на всех узлах:

1. `SET GLOBAL ENFORCE_GTID_CONSISTENCY = ON;`
2. `SET GLOBAL GTID_MODE = OFF_PERMISSIVE;` (сервер принимает любые транзакции).
3. `SET GLOBAL GTID_MODE = ON_PERMISSIVE;` (сервер начинает генерировать GTID).
4. Проверьте отсутствие анонимных транзакций: `SHOW STATUS LIKE 'ONGOING_ANONYMOUS_TRANSACTION_COUNT';` (должно быть 0).
5. `SET GLOBAL GTID_MODE = ON;` (полный режим).

### 3. Настройка репликации

Для активации автоматического позиционирования используется параметр `SOURCE_AUTO_POSITION = 1` (в версиях до 8.0.22 — `MASTER_AUTO_POSITION`).

```sql
-- Выполняется на Реплике
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.1.10',
  SOURCE_USER='repl_user',
  SOURCE_PASSWORD='secure_password',
  SOURCE_AUTO_POSITION = 1;
-- → Query OK, 0 rows affected

START REPLICA;
```

### 4. Пропуск проблемной транзакции

В режиме GTID нельзя использовать `SET GLOBAL SQL_SLAVE_SKIP_COUNTER`. Вместо этого нужно "подделать" выполнение транзакции, создав пустую запись с этим ID.

```sql
-- 1. Определяем проблемный GTID из SHOW REPLICA STATUS (поле Last_SQL_Error)
STOP REPLICA;
-- 2. "Выполняем" пустую транзакцию с нужным GTID
SET GTID_NEXT='3E11FA47-71CA-11E1-9E33-C80AA9429562:542';
BEGIN; COMMIT;
-- 3. Возвращаем автоматический режим и запускаем репликацию
SET GTID_NEXT='AUTOMATIC';
START REPLICA;
```

### 5. Восстановление из дампа и gtid_purged

При развертывании новой реплики из бэкапа необходимо сообщить серверу, какие транзакции уже есть в данных. Утилита `mysqldump` с флагом `--set-gtid-purged=ON` делает это автоматически.

**Ручное управление (MySQL 8.0+):**
```sql
-- Полная очистка состояния GTID (требует RESET MASTER)
RESET MASTER; 

-- Установка начального набора транзакций (перезаписывает gtid_purged)
SET GLOBAL gtid_purged = '3E11FA47-71CA-11E1-9E33-C80AA9429562:1-1000000';

-- Инкрементальное добавление новых транзакций (только MySQL 8.0+)
-- Знак '+' позволяет добавить набор к уже существующему gtid_purged
SET GLOBAL gtid_purged = '+4F22BC81-82DB-11E2-9F44-D90BB0530673:1-500';
```

## Дополнительная информация

### Системные переменные и мониторинг

- `@@GLOBAL.gtid_executed`: Набор всех транзакций, примененных на данном сервере (хранится в памяти + таблице `mysql.gtid_executed`).
- `@@GLOBAL.gtid_purged`: Набор транзакций, выполненных на сервере, но уже удаленных из бинарных логов (например, в процессе ротации).
- `Retrieved_Gtid_Set`: Набор GTID, полученных репликой от источника и сохраненных в Relay Log.
- `Executed_Gtid_Set`: Набор GTID, которые были фактически применены к данным на реплике.

**Мониторинг через Performance Schema (MySQL 8.0+):**
```sql
-- Проверка статуса потока применения (Applier)
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- Детальный статус соединения
SELECT * FROM performance_schema.replication_connection_status\G
```

### Использование mysqlbinlog

Для извлечения транзакций по их идентификаторам:
```bash
mysqlbinlog --include-gtids="uuid:1-100" /var/lib/mysql/binlog.000001 | mysql -u root -p
```

### Сравнение с MariaDB
Реализации GTID в MySQL и MariaDB **несовместимы**.
- MariaDB использует формат `domain_id-server_id-sequence_number`.
- Прямая GTID-репликация между MySQL 8.x и MariaDB 11+ невозможна без использования логического дампа.
