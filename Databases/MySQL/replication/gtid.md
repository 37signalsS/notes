# Репликация на основе GTID (Global Transaction Identifier)

## Определения

**GTID (Global Transaction Identifier)** — уникальный идентификатор транзакции, автоматически присваиваемый каждой транзакции при её выполнении на источнике (source). Он гарантирует однозначную идентификацию транзакции во всём кластере репликации.

**Формат GTID:** `source_id:transaction_id`
- `source_id` — `server_uuid` сервера, на котором была инициирована транзакция.
- `transaction_id` — порядковый номер транзакции (начинается с 1).

**GTID-репликация** — режим репликации, при котором реплика отслеживает выполненные транзакции по их идентификаторам, а не по физическим координатам (имени файла и смещению) в бинарном логе.

## Основные концепции

### Преимущества GTID перед классической репликацией

| Преимущество | Описание |
| :--- | :--- |
| Упрощённый Failover | При смене мастера реплике достаточно указать новый хост. Позиция в логах определится автоматически. |
| Автоматическое позиционирование | Использование `SOURCE_AUTO_POSITION = 1` избавляет от ручного поиска координат `binlog_file/pos`. |
| Гарантированная консистентность | Каждая транзакция выполняется в кластере ровно один раз, что предотвращает дублирование данных. |
| Идемпотентность | Повторная попытка применения транзакции с уже известным GTID автоматически игнорируется. |

### Принцип работы

1. Каждая транзакция получает уникальный GTID перед записью в бинарный лог на мастере.
2. Реплика сохраняет информацию о выполненных GTID в системной таблице `mysql.gtid_executed` и в своих бинарных логах.
3. При восстановлении соединения реплика сообщает источнику диапазон уже выполненных транзакций (`gtid_executed`).
4. Источник сканирует свои логи и отправляет только те транзакции, идентификаторы которых отсутствуют в списке реплики.

**Таблица `mysql.gtid_executed`:**
Введена для повышения надежности. Она позволяет серверу хранить состояние GTID даже после удаления (пурджа) бинарных логов. Данные в таблицу записываются при ротации логов, остановке сервера или транзакционно для каждого изменения (если бинарный лог на реплике выключен).

### Требования и ограничения

- **MySQL 5.6+:** Минимальная версия для базовой поддержки. Для полноценной работы в продакшене рекомендуется 5.7 или 8.0+.
- **ROW-формат:** Настоятельно рекомендуется для обеспечения консистентности (обязателен для Group Replication).
- **Консистентность DDL:** Параметр `enforce_gtid_consistency = ON` запрещает операции, нарушающие атомарность GTID (например, `CREATE TABLE ... SELECT`).
- **Однородность:** Все узлы в топологии должны использовать идентичный режим `gtid_mode`.

## Практические сценарии

### 1. Включение режима GTID через конфигурацию

Добавьте следующие параметры в файл конфигурации (`my.cnf` или `mysqld.cnf`) на всех узлах:

```ini
[mysqld]
# Включение режима GTID
gtid_mode = ON
# Обеспечение строгой консистентности транзакций
enforce_gtid_consistency = ON

# Обязательные и рекомендуемые параметры
log_bin = /var/log/mysql/mysql-bin.log
log_replica_updates = ON
server-id = 101
binlog_gtid_simple_recovery = ON
```

После изменения конфигурации требуется перезапуск службы:
```bash
sudo systemctl restart mysql
# → служба перезапущена, проверяем статус: SELECT @@GLOBAL.gtid_mode;
```

### 2. Настройка репликации с использованием GTID

Для активации автоматического позиционирования используется параметр `SOURCE_AUTO_POSITION = 1` (в версиях до 8.0.22 — `MASTER_AUTO_POSITION`).

```sql
-- Выполняется на Реплике
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.1.10',
  SOURCE_USER='repl_user',
  SOURCE_PASSWORD='secure_password',
  SOURCE_AUTO_POSITION = 1;
-- → Query OK, 0 rows affected

START REPLICA;
-- → Query OK, 0 rows affected
```

Проверка статуса:
```sql
SHOW REPLICA STATUS\G
/*
             Replica_IO_Running: Yes
            Replica_SQL_Running: Yes
                  Auto_Position: 1
             Retrieved_Gtid_Set: 3E11FA47...:1-100
              Executed_Gtid_Set: 3E11FA47...:1-100
*/
```

### 3. Пропуск проблемной транзакции

В режиме GTID нельзя использовать `SET GLOBAL SQL_SLAVE_SKIP_COUNTER`. Вместо этого нужно "подделать" выполнение транзакции, создав пустую запись с этим ID.

```sql
-- 1. Определяем проблемный GTID из SHOW REPLICA STATUS (поле Last_SQL_Error)
STOP REPLICA;
-- 2. "Выполняем" пустую транзакцию с нужным GTID
SET GTID_NEXT='3E11FA47-71CA-11E1-9E33-C80AA9429562:542';
BEGIN; COMMIT;
-- 3. Возвращаем автоматический режим и запускаем репликацию
SET GTID_NEXT='AUTOMATIC';
START REPLICA;
```

### 4. Восстановление из дампа и gtid_purged

При развертывании новой реплики из бэкапа необходимо сообщить серверу, какие транзакции уже есть в данных.

**В MySQL 8.0+ доступно инкрементальное добавление:**
```sql
-- Полная очистка состояния GTID
RESET MASTER; 

-- Установка начального набора транзакций (перезаписывает gtid_purged)
SET GLOBAL gtid_purged = '3E11FA47-71CA-11E1-9E33-C80AA9429562:1-1000000';

-- Добавление новых транзакций к существующему набору (только MySQL 8.0+)
SET GLOBAL gtid_purged = '+4F22BC81-82DB-11E2-9F44-D90BB0530673:1-500';
```

## Дополнительная информация

### Системные переменные и мониторинг

- `@@GLOBAL.gtid_executed`: Набор всех транзакций, примененных на данном сервере.
- `@@GLOBAL.gtid_purged`: Набор транзакций, выполненных на сервере, но уже удаленных из бинарных логов (например, в процессе ротации).
- `Retrieved_Gtid_Set`: Набор GTID, полученных репликой от источника и записанных в Relay Log.
- `Executed_Gtid_Set`: Набор GTID, фактически примененных к данным в базе.

### Постепенная миграция (без простоя)

MySQL поддерживает динамическое включение GTID через промежуточные состояния:
1. `OFF`: GTID выключен.
2. `OFF_PERMISSIVE`: Сервер генерирует анонимные транзакции, но принимает транзакции с GTID.
3. `ON_PERMISSIVE`: Сервер генерирует транзакции с GTID, но принимает анонимные.
4. `ON`: Полный режим GTID.

### Особенности работы с фильтрами

При использовании `replicate_do_db` или `replicate_ignore_db` отфильтрованные транзакции всё равно попадают в `gtid_executed` как пустые транзакции. Это необходимо для того, чтобы реплика "знала", что она видела эту транзакцию, и не запрашивала её повторно при переключении мастера.
