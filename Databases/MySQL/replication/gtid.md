# Репликация на основе GTID (Global Transaction Identifier)

## Определения

**GTID (Global Transaction Identifier)** — уникальный идентификатор транзакции, автоматически присваиваемый каждой транзакции при её выполнении на источнике (source). Он гарантирует однозначную идентификацию транзакции во всём кластере репликации и остается неизменным при передаче по всей топологии.

**Формат GTID:** `source_id:transaction_id`
- `source_id` — `server_uuid` сервера, на котором была инициирована транзакция. Генерируется автоматически при первом запуске и хранится в файле `auto.cnf` в data-директории.
- `transaction_id` — порядковый номер транзакции (64-битное целое число), который инкрементируется для каждой новой транзакции на данном источнике.

**GTID Set (Набор GTID)** — группа идентификаторов, представляющая собой список UUID и диапазонов транзакций.
- Пример: `3E11FA47-71CA-11E1-9E33-C80AA9429562:1-140:150-200`.

**GTID-состояния потоков:**
- **gtid_next** — сессионная переменная, определяющая GTID для следующей транзакции. Может принимать значения `AUTOMATIC` (сервер генерирует сам), `anonymous` (классическая транзакция) или конкретный `UUID:ID`.
- **gtid_owned** — список GTID, которые в данный момент "принадлежат" активным потокам (выполняются или записываются). Позволяет избежать одновременного выполнения одной транзакции разными потоками.
- **gtid_purged** — набор транзакций, которые были выполнены на сервере, но уже удалены из бинарных логов (пурдж). Это критически важный параметр для восстановления: сервер не может отправить транзакции из этого набора репликам, так как их физически нет в логах.

**GTID-репликация** — режим репликации, при котором реплика отслеживает выполненные транзакции по их идентификаторам, а не по физическим координатам (имени файла и смещению) в бинарном логе.

## Основные концепции

### Преимущества GTID перед классической репликацией

| Преимущество | Описание |
| :--- | :--- |
| **Упрощённый Failover** | При смене мастера реплике достаточно указать новый хост. Позиция в логах определится автоматически, если нужные транзакции там есть. |
| **Автоматическое позиционирование** | Использование `SOURCE_AUTO_POSITION = 1` избавляет от ручного поиска координат `binlog_file/pos`. |
| **Гарантированная консистентность** | Каждая транзакция выполняется в кластере ровно один раз. Это предотвращает дублирование данных и облегчает восстановление. |
| **Идемпотентность** | Повторная попытка применения транзакции с уже известным GTID автоматически игнорируется сервером. |
| **Защита от циклов** | В кольцевой или multi-source репликации сервер автоматически игнорирует транзакции, которые он сам же и породил (на основе своего UUID). |

### Принцип работы и жизненный цикл транзакции

1. **Генерация:** Когда клиент выполняет `COMMIT` на источнике, поток проверяет `gtid_next`. Если стоит `AUTOMATIC`, сервер выделяет следующий порядковый номер для своего `server_uuid`.
2. **Запись в Binlog:** Транзакция записывается в бинарный лог вместе с событием `Gtid_log_event`.
3. **Обновление состояния:** GTID добавляется в `gtid_executed` в памяти и записывается в таблицу `mysql.gtid_executed`.
4. **Передача:** Replica I/O Thread подключается к источнику, отправляя свой набор уже выполненных транзакций. Источник отправляет все транзакции, которых нет в наборе реплики.
5. **Применение:** Replica SQL Thread считывает GTID из Relay Log, устанавливает свою `gtid_next` в это значение и выполняет транзакцию. Если транзакция с таким GTID уже есть в `gtid_executed` реплики, она пропускается.

#### Таблица `mysql.gtid_executed`
Введена для повышения надежности и служит постоянным хранилищем выполненных GTID.
- **Назначение:** Позволяет серверу знать состояние GTID даже после удаления (пурджа) бинарных логов (`PURGE BINARY LOGS`).
- **Запись данных:**
  - Если `log_bin = ON`: Данные в таблицу записываются при ротации бинарного лога или остановке сервера. В промежутках актуальное состояние хранится только в бинарных логах.
  - Если `log_bin = OFF` (на реплике): GTID записывается в таблицу транзакционно вместе с изменениями данных. Это гарантирует, что реплика не потеряет позицию даже без собственного бинлога.
- **Сжатие (Compression):** Чтобы таблица не росла бесконечно (одна строка на каждый GTID), MySQL периодически выполняет сжатие, объединяя отдельные ID в диапазоны (например, `1, 2, 3` → `1-3`).
  - Процесс запускается фоновым потоком.
  - Частота регулируется `gtid_executed_compression_period` (количество транзакций между сжатиями).
  - Во время сжатия сервер выполняет транзакцию, обновляющую таблицу, что можно увидеть в логах как активность системного пользователя.

#### Механизм Simple Recovery
Параметр `binlog_gtid_simple_recovery = ON` (рекомендуется) ускоряет запуск сервера. Он заставляет MySQL сканировать только самый новый и самый старый бинарные логи для расчета `gtid_executed` и `gtid_purged`, вместо перебора всей цепочки файлов. Это критично, если накоплено большое количество файлов логов.

### Требования и ограничения

- **MySQL 5.6+:** Минимальная версия для базовой поддержки. Для полноценной работы в продакшене рекомендуется 5.7 или 8.0+.
- **ROW-формат:** Настоятельно рекомендуется для обеспечения консистентности (обязателен для Group Replication). Использование `STATEMENT` может привести к расхождениям.
- **Консистентность DDL:** Параметр `enforce_gtid_consistency = ON` запрещает операции, нарушающие атомарность GTID:
  - `CREATE TABLE ... SELECT`: До версии 8.0.21 этот запрос порождал два разных события (DDL и данные), что невозможно упаковать в один GTID. В 8.0.21+ это разрешено для InnoDB.
  - `CREATE TEMPORARY TABLE` внутри транзакций: Временные таблицы не записываются в `gtid_executed`, что может привести к проблемам при переключении на другой источник.
  - Транзакции, затрагивающие как транзакционные (InnoDB), так и нетранзакционные (MyISAM) таблицы.
- **XA Transactions:** В версиях до 8.0.29 существовали ограничения на использование XA-транзакций с GTID (возможные дубли или потери при сбоях).
- **Однородность:** Все узлы в топологии должны использовать идентичный режим `gtid_mode`.
- **Фильтры репликации:** При использовании `replicate_do_db` или `replicate_ignore_db` отфильтрованные транзакции всё равно попадают в `gtid_executed` как **пустые транзакции**. Это необходимо, чтобы реплика "помнила" о факте их получения и не запрашивала их снова при переключении на другой источник.

## Практические сценарии

### 1. Включение режима GTID через конфигурацию

Добавьте следующие параметры в файл конфигурации (`my.cnf` или `mysqld.cnf`) на всех узлах:

```ini
[mysqld]
# Уникальный ID сервера (обязательно)
server-id = 101

# Включение режима GTID и строгой консистентности
gtid_mode = ON
enforce_gtid_consistency = ON

# Обязательные настройки для надежной репликации
log_bin = /var/log/mysql/mysql-bin.log
# Позволяет реплике записывать полученные изменения в свой binlog (нужно для каскадной репликации)
log_replica_updates = ON 
# Рекомендуемый формат бинлога
binlog_format = ROW

# Ускорение восстановления при запуске
binlog_gtid_simple_recovery = ON
```

После изменения конфигурации требуется перезапуск службы:
```bash
sudo systemctl restart mysql
# → Проверяем статус: SELECT @@GLOBAL.gtid_mode;
```

### 2. Динамическая миграция на GTID (без простоя)

Если серверы уже работают в классическом режиме, можно перейти на GTID без остановки записи, последовательно меняя `gtid_mode` на всех узлах:

1. `SET GLOBAL ENFORCE_GTID_CONSISTENCY = ON;`
2. `SET GLOBAL GTID_MODE = OFF_PERMISSIVE;` (сервер принимает любые транзакции).
3. `SET GLOBAL GTID_MODE = ON_PERMISSIVE;` (сервер начинает генерировать GTID).
4. Проверьте отсутствие анонимных транзакций: `SHOW STATUS LIKE 'ONGOING_ANONYMOUS_TRANSACTION_COUNT';` (должно быть 0).
5. `SET GLOBAL GTID_MODE = ON;` (полный режим).

### 3. Настройка репликации

Для активации автоматического позиционирования используется параметр `SOURCE_AUTO_POSITION = 1` (в версиях до 8.0.22 — `MASTER_AUTO_POSITION`).

```sql
-- Выполняется на Реплике
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.1.10',
  SOURCE_USER='repl_user',
  SOURCE_PASSWORD='secure_password',
  SOURCE_AUTO_POSITION = 1;
-- → Query OK, 0 rows affected

START REPLICA;
```

### 4. Пропуск проблемной транзакции

В режиме GTID нельзя использовать `SET GLOBAL SQL_SLAVE_SKIP_COUNTER`. Вместо этого нужно "подделать" выполнение транзакции, создав пустую запись с этим ID.

```sql
-- 1. Определяем проблемный GTID из SHOW REPLICA STATUS (поле Last_SQL_Error)
STOP REPLICA;
-- 2. "Выполняем" пустую транзакцию с нужным GTID
SET GTID_NEXT='3E11FA47-71CA-11E1-9E33-C80AA9429562:542';
BEGIN; COMMIT;
-- 3. Возвращаем автоматический режим и запускаем репликацию
SET GTID_NEXT='AUTOMATIC';
START REPLICA;
```

### 5. Восстановление из дампа и gtid_purged

При развертывании новой реплики из бэкапа необходимо сообщить серверу, какие транзакции уже есть в данных. Утилита `mysqldump` с флагом `--set-gtid-purged=ON` делает это автоматически.

**Ручное управление (MySQL 8.0+):**
```sql
-- Полная очистка состояния GTID (требует RESET MASTER)
RESET MASTER; 

-- Установка начального набора транзакций (перезаписывает gtid_purged)
SET GLOBAL gtid_purged = '3E11FA47-71CA-11E1-9E33-C80AA9429562:1-1000000';

-- Инкрементальное добавление новых транзакций (только MySQL 8.0+)
-- Знак '+' позволяет добавить набор к уже существующему gtid_purged
SET GLOBAL gtid_purged = '+4F22BC81-82DB-11E2-9F44-D90BB0530673:1-500';
```

### 6. Устранение ошибки 1236 (Missing GTIDs on Source)

**Ситуация:** Реплика запрашивает транзакции, которые мастер уже удалил из своих бинарных логов (`PURGE BINARY LOGS`). В `SHOW REPLICA STATUS` видна ошибка:
`Got fatal error 1236 from master when reading data from binary log: 'The slave is connecting using CHANGE MASTER TO MASTER_AUTO_POSITION = 1, but the master has purged binary logs containing GTIDs that the slave requires.'`

**Причины:**
- Реплика была выключена слишком долго.
- На мастере слишком агрессивно настроен `binlog_expire_logs_seconds`.

**Решение (если данные можно синхронизировать вручную):**
1. Определить отсутствующий набор на мастере:
   ```sql
   -- На мастере: смотрим что осталось
   SELECT @@GLOBAL.gtid_purged;
   ```
2. Если `gtid_purged` мастера содержит транзакции, нужные реплике, значит данные в логах утеряны. Нужно либо пересоздать реплику из нового бэкапа, либо вручную добавить недостающие GTID как пустые транзакции (если уверены, что данные консистентны).

### 7. Автоматизация через Clone Plugin

При использовании `Clone Plugin` в MySQL 8.0+ состояние GTID передается автоматически.
1. При выполнении `CLONE INSTANCE FROM ...` реплика копирует все данные и `Executed_Gtid_Set`.
2. После перезапуска реплика уже знает свою позицию.
3. Достаточно выполнить `CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION = 1;` без указания координат.

## Дополнительная информация

### Продвинутый мониторинг и сравнение GTID

Для проверки рассинхронизации можно использовать функцию `GTID_SUBSET(subset, superset)`. Она возвращает 1, если первый набор является подмножеством второго.

```sql
-- Проверка: все ли транзакции, полученные из бинлогов (Retrieved), уже применены (Executed)
SELECT GTID_SUBSET(@@GLOBAL.Retrieved_Gtid_Set, @@GLOBAL.gtid_executed) AS is_synced;

-- Поиск "дырок" (gap) в транзакциях
-- Если набор gtid_executed выглядит как 1-10, 15-20, значит транзакции 11-14 еще не дошли или пропущены
SELECT @@GLOBAL.gtid_executed;
```

**Мониторинг через Performance Schema (MySQL 8.0+):**
```sql
-- Проверка статуса потока применения (Applier)
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- Детальный статус соединения и лаг по GTID
SELECT 
    CHANNEL_NAME, 
    LAST_QUEUED_TRANSACTION, 
    LAST_APPLIED_TRANSACTION 
FROM performance_schema.replication_applier_status_by_coordinator;
```

### Использование mysqlbinlog с GTID

**Извлечение конкретных транзакций:**
```bash
mysqlbinlog --include-gtids="3E11FA47-71CA-11E1-9E33-C80AA9429562:1-100" /var/lib/mysql/binlog.000001 > export.sql
```

**Пропуск (исключение) транзакций (полезно при PITR):**
```bash
# Восстановить всё, кроме проблемной транзакции :542
mysqlbinlog --exclude-gtids="3E11FA47-71CA-11E1-9E33-C80AA9429562:542" /var/lib/mysql/binlog.000001 | mysql -u root -p
```

### Предотвращение циклов в кольцевой репликации

В топологии A → B → C → A:
1. Сервер A порождает транзакцию `UUID_A:1`.
2. Она приходит на B, затем на C.
3. Когда она возвращается на A, сервер видит в заголовке `UUID_A` (свой собственный `server_uuid`).
4. Сервер A проверяет свой `gtid_executed` и видит, что `UUID_A:1` уже была выполнена.
5. Транзакция игнорируется, цикл разрывается автоматически без дополнительных настроек типа `replicate-same-server-id`.

### Сравнение с MariaDB
Реализации GTID в MySQL и MariaDB **несовместимы**.
- MariaDB использует формат `domain_id-server_id-sequence_number`.
- Прямая GTID-репликация между MySQL 8.x и MariaDB 11+ невозможна без использования логического дампа.
- MariaDB не требует `enforce_gtid_consistency = ON`.
