# Пошаговая настройка репликации MySQL

**Актуально для:** MySQL 5.6+ / 8.0+ / 8.4 LTS

## Определения

**Репликация MySQL** — процесс автоматической синхронизации данных между основным сервером (**Источник / Source**) и одним или несколькими подчиненными серверами (**Реплика / Replica**), обеспечивающий отказоустойчивость, масштабируемость чтения и защиту данных.

**Источник (Source)** — мастер-узел, генерирующий события бинарного лога при изменении данных.
**Реплика (Replica)** — узел-получатель, применяющий события из лога источника к своей локальной копии.

**GTID (Global Transaction Identifier)** — уникальный идентификатор транзакции в рамках всего кластера. Рекомендуемый стандарт для современных инсталляций, обеспечивающий автоматическое позиционирование и упрощенный Failover.

**Classic Replication** — метод репликации на основе физических координат бинарного лога (имя файла и смещение в байтах). Считается устаревшим и менее надежным.

## Основные концепции

### Предварительные требования и надежность

Перед настройкой репликации убедитесь, что инфраструктура соответствует требованиям производства (Production):

- **Сеть:** TCP-соединение по порту 3306 между Source и Replica, стабильная задержка < 10 мс в пределах дата-центра.
- **Время:** NTP или chrony настроен на всех узлах; максимальное расхождение < 100 мс.
- **Хранилище:** Выделенные диски для binlog и relay log, отдельно от data directory, чтобы избежать contention.
- **ОС:** Файловые дескрипторы (`ulimit -n`) не менее 65535; отключен transparent huge pages (THP) для InnoDB.

Для стабильной работы в промышленной среде (Production) также должны быть выполнены следующие параметры конфигурации:

| Категория | Параметр | Рекомендация | Описание |
| :--- | :--- | :--- | :--- |
| **Сеть** | Порт 3306 | Открыт (FW/SG) | Доступ по TCP между Source и Replica обязателен. |
| **Время** | NTP / chrony | Синхронизировано | Разница во времени между узлами приводит к ошибкам в логах и мониторинге лага. |
| **Идентификация** | `server_id` | Уникальный | Целое число (1-4294967295), должно быть разным на всех узлах топологии. |
| **Консистентность** | `binlog_format` | `ROW` | Гарантирует идентичность данных на источнике и реплике. Обязателен для GTID. |
| **Надежность** | `sync_binlog` | `1` | Гарантирует запись каждого события binlog на диск. Предотвращает потерю данных при сбое. |
| **Надежность** | `innodb_flush_log_at_trx_commit` | `1` | Гарантирует ACID-свойства транзакций InnoDB. |
| **Надежность** | `relay_log_recovery` | `ON` | Автоматическое восстановление позиции репликации после сбоя реплики. |

### Методы инициализации реплики (Seeding)

Выбор метода зависит от объема данных и требований к доступности источника:

1.  **MySQL Clone Plugin:**
    *   **Применение:** MySQL 8.0.17+, пустые реплики, быстрая сеть.
    *   **Механизм:** Прямое копирование физических файлов данных (Snapshot).
    *   **Преимущества:** Максимальная скорость, минимум ручных действий.
2.  **MySQL Shell (`util.dumpInstance`):**
    *   **Применение:** Большие БД (> 100 ГБ), гетерогенные среды, облака.
    *   **Механизм:** Параллельная логическая выгрузка в чанки.
    *   **Преимущества:** Высокая скорость загрузки через `util.loadDump`, сжатие.
3.  **Percona XtraBackup:**
    *   **Применение:** Высоконагруженные системы, требующие Hot Backup без блокировок.
    *   **Механизм:** Физическое копирование с учетом активных транзакций.
    *   **Преимущества:** Промышленный стандарт для крупных On-premise инсталляций.
4.  **mysqldump:**
    *   **Применение:** Малые базы данных, разовые миграции.
    *   **Механизм:** Создание SQL-скрипта со всеми данными.
    *   **Преимущества:** Простота, переносимость между версиями.

## Практические сценарии

### 1. Подготовка Источника (Source)

**Создание пользователя репликации:**
Используйте отдельную учетную запись с ограниченными правами. В современных версиях рекомендуется требовать SSL.

```sql
-- Создание пользователя (замените пароль на надежный)
CREATE USER 'repl_user'@'%' IDENTIFIED BY 'SecureReplicaPass!2024';
-- Выдача прав на чтение бинарного лога
GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'%';

-- Дополнительные права для инициализации через Clone Plugin
GRANT BACKUP_ADMIN ON *.* TO 'repl_user'@'%';

-- Требование SSL для безопасности (рекомендуется)
ALTER USER 'repl_user'@'%' REQUIRE SSL;
```

**Конфигурация `my.cnf` (секция `[mysqld]`):**
Добавьте или обновите следующие параметры на Источнике:

```ini
[mysqld]
# Идентификация узла
server_id = 101

# Включение GTID (обязательно для современных схем)
gtid_mode = ON
enforce_gtid_consistency = ON

# Бинарный лог
log_bin = /var/log/mysql/mysql-bin.log
binlog_format = ROW

# Параметры надежности (Durability)
sync_binlog = 1
innodb_flush_log_at_trx_commit = 1

# Управление местом: хранить логи 7 дней
binlog_expire_logs_seconds = 604800
```

После внесения изменений требуется перезапуск: `systemctl restart mysql`.

### 2. Настройка Реплики через Clone Plugin

Этот метод автоматически переносит данные и настраивает позицию GTID.

**Шаг 1: Активация плагина на обоих серверах**
```sql
INSTALL PLUGIN clone SONAME 'mysql_clone.so';
```

**Шаг 2: Запуск клонирования на Реплике**
Внимание: данные в data-директории реплики будут удалены и заменены данными с источника.

```sql
-- Указываем IP источника как доверенного донора
SET GLOBAL clone_valid_donor_list = '192.168.1.10:3306';

-- Запуск процесса
CLONE INSTANCE FROM 'repl_user'@'192.168.1.10':3306 IDENTIFIED BY 'SecureReplicaPass!2024';
-- → Сервер автоматически перезагрузится после завершения.
```

**Шаг 3: Активация репликации после клонирования**
```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.1.10',
  SOURCE_USER='repl_user',
  SOURCE_PASSWORD='SecureReplicaPass!2024',
  SOURCE_SSL=1,
  SOURCE_AUTO_POSITION = 1;

START REPLICA;
```

### 3. Настройка GTID-репликации (ручная)

Используется, если данные уже перенесены на реплику другим способом (например, через бэкап) и вам нужно только связать узлы.

**На Реплике:**
```sql
-- 1. Настройка параметров подключения
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.1.10',
  SOURCE_USER='repl_user',
  SOURCE_PASSWORD='SecureReplicaPass!2024',
  SOURCE_SSL=1,                -- Обязательно, если на источнике REQUIRE SSL
  SOURCE_AUTO_POSITION = 1;    -- Автоматический поиск позиции по GTID

-- 2. Запуск потоков репликации
START REPLICA;

-- 3. Проверка статуса
SHOW REPLICA STATUS\G
-- Ищите: Replica_IO_Running: Yes и Replica_SQL_Running: Yes
```

### 4. Классическая репликация (Legacy)

Используется только для старых версий (до 5.6) или при миграции с очень специфическими требованиями. **Не рекомендуется для новых систем.**

1.  **На Источнике:** Зафиксировать позицию (выполните `FLUSH TABLES WITH READ LOCK` или используйте `--source-data=2` в mysqldump; в MySQL 5.7 — `--master-data=2`).
    `SHOW BINARY LOG STATUS;` (в MySQL 5.7 и 8.0/8.1 — `SHOW MASTER STATUS;`) → Запомните `File` (`mysql-bin.000001`) и `Position` (`154`).
2.  **На Реплике:**
```sql
CHANGE REPLICATION SOURCE TO
  SOURCE_HOST='192.168.1.10',
  SOURCE_USER='repl_user',
  SOURCE_PASSWORD='SecureReplicaPass!2024',
  SOURCE_LOG_FILE='mysql-bin.000001',
  SOURCE_LOG_POS=154;

START REPLICA;
```

### 5. Использование фильтров репликации

Фильтры позволяют реплицировать только часть данных. Настраиваются на стороне **Реплики**.

**Рекомендация:** Используйте `wildcard`-параметры (`replicate-wild-*`), так как они корректно обрабатывают кросс-базовые запросы.

```ini
[mysqld]
# Реплицировать только конкретную БД и все её таблицы
replicate-wild-do-table = production_db.%

# Игнорировать временные или технические базы
replicate-ignore-db = tmp_test_db
replicate-ignore-db = staging_db
```

*Примечание: При использовании GTID отфильтрованные транзакции всё равно попадают в `gtid_executed` как пустые события для сохранения целостности цепочки.*

## Валидация

После того как репликация запущена и `Seconds_Behind_Source` равен 0, выполните следующие проверки для подтверждения корректности настройки:

### 1. Защита от случайной записи (Read Only)
Реплика должна быть доступна только для чтения, чтобы избежать рассинхронизации данных.

```sql
-- Обычный read_only позволяет пользователям с SUPER писать в БД
SET GLOBAL read_only = ON;

-- Рекомендуется super_read_only (MySQL 5.7+), блокирует запись даже для root
SET GLOBAL super_read_only = ON;
```

Добавьте эти параметры в `my.cnf` реплики для сохранения после перезагрузки:
```ini
[mysqld]
read_only = 1
super_read_only = 1
```

### 2. Проверка SSL-шифрования
Убедитесь, что трафик бинарных логов защищен.

```sql
-- SSL_ALLOWED / SSL_USED не являются колонками Performance Schema.
-- Состояние TLS-канала смотрите в выводе SHOW REPLICA STATUS.
SHOW REPLICA STATUS\G
-- Source_SSL_Allowed: Yes --> шифрование включено
```

### 3. Базовый мониторинг

```sql
-- Проверка наличия ошибок в потоках
SELECT CHANNEL_NAME, LAST_ERROR_NUMBER, LAST_ERROR_MESSAGE 
FROM performance_schema.replication_applier_status_by_worker 
WHERE LAST_ERROR_NUMBER > 0;

-- Проверка лага: поля Seconds_Behind_Source нет среди системных переменных,
-- это поле вывода SHOW REPLICA STATUS (в MySQL 5.7 и ранее — Seconds_Behind_Master)
SHOW REPLICA STATUS\G
```

## Устранение неисправностей

### Ошибка создания пользователя репликации

- **Симптом:** `Access denied for user 'repl_user'@'%'` при попытке подключения реплики.
- **Причина:** Несовпадение хоста, неправильный пароль или недостаточные права.
- **Решение:** Убедитесь, что пользователь создан с хостом, из которого подключается реплика (`'repl_user'@'replica_ip'`), и имеет права `REPLICATION SLAVE` и `BACKUP_ADMIN` (для Clone Plugin).

### Сетевое соединение недоступно

- **Симптом:** `Replica_IO_Running: Connecting`, `Last_IO_Error: error connecting to source`.
- **Причина:** Порт 3306 закрыт файрволом, маршрутизация недоступна или `server_id` дублируется.
- **Решение:** Проверьте доступность порта (`telnet source_ip 3306`), uniqueness `server_id` и отсутствие NAT между узлами.

### Ошибка инициализации Clone Plugin

- **Симптом:** `INSTALL PLUGIN clone SONAME 'mysql_clone.so'` возвращает ошибку.
- **Причина:** MySQL < 8.0.17, плагин уже установлен или отсутствует файл `mysql_clone.so`.
- **Решение:** Обновите MySQL до 8.0.17+ или используйте ручной seeding (XtraBackup / mysqldump). Убедитесь, что `plugin_load_add` не конфликтует.

### GTID-конфликт после восстановления из бэкапа

- **Симптом:** `Fatal error 1236` или `Last_SQL_Error: ... GTID sequence already executed`.
- **Причина:** На реплике уже присутствуют транзакции с GTID, конфликтующие с позицией источника.
- **Решение:** В режиме GTID выполните `RESET REPLICA ALL` на реплике перед повторной настройкой `CHANGE REPLICATION SOURCE TO ... SOURCE_AUTO_POSITION = 1`. Если данные на реплике важны — пересоздайте реплику из чистого бэкапа.

### Ошибка доступа к файлам данных

- **Симптом:** `Can't create/write to file ... (Errcode: 13 - Permission denied)`.
- **Причина:** MySQL не имеет прав на запись в data directory или relay log directory.
- **Решение:** Убедитесь, что ownership директорий принадлежит пользователю `mysql:mysql` и права `700` на data directory.

### SSL handshake failure

- **Симптом:** `Replica_IO_Running: Connecting`, `Last_IO_Error: SSL connection error`.
- **Причина:** Несовпадение версий TLS, отсутствие сертификатов или `REQUIRE SSL` не настроен на источнике.
- **Решение:** Проверьте цепочку сертификатов (`SOURCE_SSL_CA`, `SOURCE_SSL_CERT`, `SOURCE_SSL_KEY`) и версию TLS в `my.cnf` (`tls_version`).

## Рекомендации

### Процесс настройки

- **Отдельный пользователь:** Никогда не используйте `root` для репликации. Создавайте пользователя `repl_user` с минимальными правами (`REPLICATION SLAVE`, `BACKUP_ADMIN`).
- **Резервное копирование:** Перед первой настройкой создайте полный бэкап источника (XtraBackup или mysqldump). Это позволит быстро пересоздать реплику при ошибках.
- **Тестирование:** Настраивайте репликацию сначала на стенде с небольшим датасетом (< 10 ГБ), затем переносите конфигурацию в production.
- **Документация:** Записывайте `server_id`, топологию, версии MySQL и credentials репликации в isolated документации (не в репозитории кода).
- **Мониторинг:** Настройте алерты на `Replica_IO_Running = No`, `Replica_SQL_Running = No`, рост `Seconds_Behind_Source > 60` и ошибки в `replication_applier_status_by_worker`.

### Безопасность

- **Шифрование:** Включайте SSL/TLS на канале репликации (`SOURCE_SSL=1`, `REQUIRE SSL` у пользователя). Внутри дата-центра используйте шифрование на уровне ОС (dm-crypt) для файлов данных.
- **Файрвол:** Закройте порт 3306 файрволом (nftables/iptables/security groups) для всех IP, кроме подсети реплик и приложений.
- **Аутентификация:** Используйте `caching_sha2_password` (MySQL 8.0+) или `mysql_native_password` в зависимости от совместимости клиентов. Избегайте `auth_socket` для репликации.

### Производительность

- **Формат binlog:** Всегда используйте `binlog_format = ROW`. `STATEMENT` и `MIXED` несовместимы с GTID и опасны в production.
- **Durability:** В production устанавливайте `sync_binlog = 1` и `innodb_flush_log_at_trx_commit = 1`. Для аналитических реплик с допуском потери данных можно снизить до `2` / `2` для повышения throughput.
- **Параллелизм:** Начиная с MySQL 8.0, настройте `replica_parallel_type = LOGICAL_CLOCK` и `replica_parallel_workers` (начать с 4, повысить до числа ядер CPU реплики; методика — `parallel_replication_mts.md`).

## Граничные случаи

### Существующие данные на реплике

При использовании Clone Plugin или XtraBackup данные в data directory реплики будут удалены. Если реплика уже содержит данные, которые нужно сохранить — выполните логический дамп (`mysqldump` или `util.dumpInstance`) перед инициализацией.

### Переход с классической репликации на GTID

Если источник работает в режиме `gtid_mode = OFF`, переход на GTID требует:
1. Включить `enforce_gtid_consistency = WARN` и протестировать.
2. Перевести в `ON` после подтверждения отсутствия не-GTID-безопасных транзакций.
3. На реплике выполнить `RESET REPLICA ALL` и переконфигурировать с `SOURCE_AUTO_POSITION = 1`.

### Кросс-версионная репликация

MySQL поддерживает репликацию между разными минорными версиями (например, 8.0.35 → 8.0.36), но не между мажорными (5.7 → 8.0) в режиме GTID. Для миграции используйте логическую репликацию или обновляйте обе стороны одновременно.

### Очень большие датасеты (> 1 ТБ)

Для инициализации реплики с большим объемом данных используйте физический бэкап (XtraBackup) или Clone Plugin. Логический дамп (`mysqldump`) будет работать часы и создает долгий окно обслуживания.

### GTID-набор на реплике уже содержит транзакции

Если реплика ранее работала как источник или участвовала в chain-репликации, её `gtid_executed` может содержать транзакции, отсутствующие на новом источнике. Решение: `RESET REPLICA ALL` и пересоздание из чистого бэкапа.

## Очистка и откат

При необходимости удалить репликацию и вернуть узел в независимый standalone:

```sql
-- 1. Остановка потоков
STOP REPLICA;

-- 2. Полный сброс метаданных репликации (включая GTID)
RESET REPLICA ALL;

-- 3. Удаление пользователя репликации (на источнике)
DROP USER 'repl_user'@'%';
FLUSH PRIVILEGES;

-- 4. Удаление конфигурации из my.cnf реплики
-- Удалите строки: log_bin, binlog_format, gtid_mode, enforce_gtid_consistency
-- Удалите строки: read_only, super_read_only

-- 5. Перезапуск MySQL
systemctl restart mysql;

-- 6. Отключение read_only (если нужно разрешить запись)
SET GLOBAL read_only = OFF;
SET GLOBAL super_read_only = OFF;
```

## Дополнительная информация

### Безопасность и отказоустойчивость

*   **Crash-Safe Replication:** В MySQL 5.6/5.7 параметры `master_info_repository` и `relay_log_info_repository` по умолчанию равны `FILE` — задайте `TABLE` явно (позиция коммитится в транзакции InnoDB). С MySQL 8.0 дефолт `TABLE` (deprecated с 8.0.23). Обе переменные **удалены в MySQL 8.3.0** — на 8.4 LTS метаданные всегда хранятся в таблицах. Методика — `relay_logs_crashsafe.md`.
*   **Primary Keys:** Установите `sql_generate_invisible_primary_key = ON` (8.0.30+) или контролируйте наличие ПК. Репликация таблиц без PK крайне медленна.
*   **Параллельная репликация (MTS):** Для ускорения применения данных на реплике используйте:
    `replica_parallel_type = LOGICAL_CLOCK`
    `replica_parallel_workers = 8` (подберите под количество ядер).
