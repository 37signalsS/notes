# Multi-Source репликация в MySQL

## Определения

**Multi-Source репликация** — это топология, при которой один сервер-реплика (Replica) одновременно принимает и применяет изменения от нескольких независимых серверов-источников (Source).

**Канал репликации (Replication Channel)** — изолированный поток данных внутри реплики. Каждый канал имеет собственные настройки подключения, позиции в логах и набор потоков (I/O и SQL).

**Репозитории репликации (Replication Repositories)** — системные таблицы (`mysql.slave_master_info`, `mysql.slave_relay_log_info`), в которых хранятся метаданные каналов. В MySQL 8.0+ использование таблиц вместо файлов является обязательным.

## Основные концепции

### Механизм именованных каналов

В стандартной репликации используется один "безымянный" канал (Default Channel). Multi-Source расширяет эту логику, позволяя создавать множество именованных каналов.
- **Изоляция:** Сбой или остановка одного канала не влияет на работу остальных.
- **Параллелизм:** Каждый канал работает в своем темпе, используя собственные ресурсы.
- **Лимиты:** MySQL 8.0 поддерживает до 256 каналов репликации на один инстанс.

### Типовые сценарии использования

- **Консолидация данных:** Сбор данных из нескольких шардов на один сервер для построения общей аналитики или создания бэкапа всей системы.
- **Топология "Кольцо" (Ring):** Цепочка серверов N1 → N2 → N3 → N1, где каждый узел является и источником, и репликой.
- **Агрегация из разных сред:** Объединение данных из независимых приложений (например, биллинг и CRM) в единое хранилище (DWH).

### Особенности GTID в Multi-Source

Применение **GTID (Global Transaction Identifier)** в данной топологии является критически важным:
- **Предотвращение циклов:** Благодаря уникальным `server_uuid`, реплика автоматически игнорирует транзакции, которые она сама же и породила (важно для кольцевой репликации).
- **Консистентность:** Гарантирует, что транзакция с одного источника не будет применена дважды через разные пути.

### Параллельная репликация (MTS)

В Multi-Source нагрузка на реплику возрастает пропорционально количеству источников. Для поддержания производительности необходимо использовать **Multi-Threaded Slave (MTS)**:
- **replica_parallel_workers:** Определяет количество потоков применения данных. В Multi-Source настройка применяется к каждому каналу отдельно.
- **replica_parallel_type:** Рекомендуется значение `LOGICAL_CLOCK` для параллельного выполнения транзакций, не конфликтующих по зависимостям.
- **replica_preserve_commit_order:** Обеспечивает фиксацию транзакций в том же порядке, что и на источнике, что важно для предотвращения разрывов в GTID.

### Конфликты и ограничения

- **Конфликты данных:** Если разные источники изменяют одну и ту же строку в одной и той же таблице, репликация остановится с ошибкой. Multi-Source лучше всего работает, когда источники пишут в разные базы данных.
- **Производительность:** Нагрузка на диск (I/O) и CPU реплики суммируется от всех источников.
- **Асинхронность:** По умолчанию Multi-Source является асинхронной. Использование полусинхронного режима возможно, но усложняет архитектуру.

## Практические сценарии

### Настройка Multi-Source в MySQL 8.4 LTS

В современных версиях используется синтаксис `SOURCE` вместо `MASTER`.

#### Подготовка источников
На каждом сервере-источнике создается пользователь с правами репликации:
```sql
CREATE USER 'repl_user'@'%' IDENTIFIED BY 'StrongPassword123!';
GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'%';
```

#### Создание каналов на реплике
На сервере-реплике настройте подключения, указывая уникальное имя канала через `FOR CHANNEL`.

```sql
-- Настройка канала для Источника А
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '192.168.1.10',
    SOURCE_USER = 'repl_user',
    SOURCE_PASSWORD = 'StrongPassword123!',
    SOURCE_AUTO_POSITION = 1
FOR CHANNEL 'channel_alpha';

-- Настройка канала для Источника Б
CHANGE REPLICATION SOURCE TO
    SOURCE_HOST = '192.168.1.11',
    SOURCE_USER = 'repl_user',
    SOURCE_PASSWORD = 'StrongPassword123!',
    SOURCE_AUTO_POSITION = 1
FOR CHANNEL 'channel_beta';
```

#### Управление потоками репликации
Каналы можно запускать и останавливать независимо.

```sql
-- Запуск всех каналов
START REPLICA;

-- Запуск конкретного канала
START REPLICA FOR CHANNEL 'channel_alpha';

-- Полное удаление канала (требует остановки)
STOP REPLICA FOR CHANNEL 'channel_beta';
RESET REPLICA ALL FOR CHANNEL 'channel_beta';
```

#### Использование фильтров для каналов
Настройка фильтров позволяет реплицировать только нужные данные для каждого канала:

```sql
-- Ограничиваем канал channel_alpha только базой 'sales_db'
CHANGE REPLICATION FILTER REPLICATE_DO_DB = (sales_db) FOR CHANNEL 'channel_alpha';
```

### Обеспечение высокой доступности (Keepalived)

Для Multi-Source реплик часто применяются механизмы обеспечения доступности:
- **Keepalived:** Позволяет назначить Virtual IP (VIP) на группу реплик. Если основная реплика, собирающая данные, выходит из строя, VIP переходит на резервную.
- **Ограничение:** Keepalived не отслеживает состояние конкретных каналов репликации, а только доступность всего узла.

## Дополнительная информация

### Мониторинг каналов

Для анализа состояния каналов используются системные таблицы `Performance Schema`:

```sql
-- Общий статус всех каналов
SELECT CHANNEL_NAME, SERVICE_STATE, LAST_ERROR_NUMBER, LAST_ERROR_MESSAGE 
FROM performance_schema.replication_connection_status;

-- Мониторинг воркеров параллельной репликации
SELECT CHANNEL_NAME, WORKER_ID, LAST_APPLIED_TRANSACTION 
FROM performance_schema.replication_applier_status_by_worker;
```

### Рекомендации по конфигурации

Рекомендуемые параметры в `my.cnf` для стабильной работы Multi-Source:

```ini
[mysqld]
# Использование таблиц для хранения метаданных
relay_log_info_repository = TABLE
master_info_repository = TABLE

# Защита от случайной записи на реплику
super_read_only = ON

# Настройки GTID (обязательно)
gtid_mode = ON
enforce_gtid_consistency = ON
log_replica_updates = ON

# Автоматическое восстановление логов после сбоя
relay_log_recovery = ON

# Настройка параллельного применения (MTS)
replica_parallel_workers = 4
replica_parallel_type = LOGICAL_CLOCK
replica_preserve_commit_order = ON
```
