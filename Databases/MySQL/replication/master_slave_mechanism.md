# Механизм Master-Slave репликации

Стандартная асинхронная master-slave репликация в MySQL работает на основе бинарного лога (`binary log`) и включает в себя три основных потока:

## Схема компонентов

```text
                                    +------------------------------------+
                                    |             Slave Server           |
                                    |                                    |
+----------------+                  |  +-------------+   +-------------+   |   +----------+
| Master Server  |                  |  |             |   |             |   |   |          |
|                | -- Binlog dump --> |  I/O Thread   |-->|  Relay Log  |--> | SQL Thread |-->| Database |
| +------------+ |                  |  |             |   |             |   |   |          |
| | Binary Log | |                  |  +-------------+   +-------------+   |   +----------+
| +------------+ |                  |                                    |
|       ^        |                  +------------------------------------+
|       |        |
| DML Commands   |
|       |        |
| +----------+   |
| | Database |   |
| +----------+   |
+----------------+
```

## Этапы репликации

1. **Запись на Master:** Любые команды изменения данных (DML: `INSERT`, `UPDATE`, `DELETE`) на master-сервере записываются в специальный файл — **бинарный лог (Binary Log)**. Этот лог содержит все события, которые изменяют данные в базе.

2. **Подключение Slave:** Slave-сервер инициирует подключение к master-серверу. Для этого на slave-сервере запускается специальный поток — **I/O Thread**.

3. **Запрос данных:** `I/O Thread` на slave-сервере запрашивает у master-сервера содержимое его бинарного лога, начиная с последней сохраненной позиции.

4. **Отправка данных:** На master-сервере для каждого подключенного slave-сервера создается поток **Binlog Dump Thread**. Его задача — читать бинарный лог и отправлять его содержимое в `I/O Thread` slave-сервера.

5. **Запись в Relay Log:** `I/O Thread` на slave-сервере, получив данные от мастера, не применяет их сразу, а записывает их в свой собственный лог — **журнал ретрансляции (Relay Log)**. Этот журнал является точной копией бинарного лога мастера. Такой подход позволяет slave-серверу получить все изменения от мастера как можно быстрее, не задерживаясь на их выполнении.

6. **Применение данных:** На slave-сервере работает второй важный поток — **SQL Thread**. Он последовательно читает события из `Relay Log`, преобразует их в SQL-запросы и выполняет на своей копии базы данных. Именно на этом этапе происходит фактическое изменение данных на slave-сервере.

## Ключевые моменты

- **Разделение потоков:** Разделение на I/O- и SQL-потоки является ключевой оптимизацией. I/O-поток отвечает за быструю сетевую пересылку, а SQL-поток — за их применение. Это предотвращает отставание репликации (`replication lag`).

- **Отставание репликации (Replication Lag):** Задержка между записью на мастере и применением на слейве. Может возникать из-за медленной сети (влияет на I/O-поток) или высокой нагрузки на слейве (влияет на SQL-поток).
