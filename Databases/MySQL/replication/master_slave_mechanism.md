# Механизм репликации в MySQL

## Определения

**Репликация Source-Replica** — процесс автоматического копирования данных с основного сервера (**Источник/Source**) на один или несколько дополнительных серверов (**Реплика/Replica**).

**Потоки репликации (Replication Threads)** — системные процессы, обеспечивающие асинхронную или полусинхронную передачу данных.

**MTS (Multi-Threaded Slave)** — механизм параллельного применения транзакций на реплике.

**Relay Log (Журнал ретрансляции)** — промежуточный набор файлов на стороне реплики, играющий роль буфера между получением данных из сети и их записью в базу данных.

## Основные концепции

### Архитектура и жизненный цикл события

Репликация в MySQL работает на основе передачи событий бинарного лога. Весь путь транзакции можно разделить на 4 этапа:

1.  **Источник:** Изменение данных фиксируется в **Binary Log**.
2.  **Источник (Dump Thread):** При подключении реплики (команда `COM_BINLOG_DUMP` или `COM_BINLOG_DUMP_GTID`) источник создает выделенный поток. Он считывает события из лога и отправляет их в сеть.
3.  **Реплика (Receiver/IO Thread):** Подключается к источнику, принимает пакеты данных и записывает их "как есть" в локальный **Relay Log**.
4.  **Реплика (Applier/SQL Thread):** Читает события из Relay Log и выполняет их, изменяя данные в локальной БД.

### Типы потоков репликации

| Поток | Расположение | Описание |
| :--- | :--- | :--- |
| **Binlog Dump Thread** | Источник | Слушает запросы реплик. Если новых событий нет, поток засыпает. При появлении данных в binlog источник "будит" поток для отправки. |
| **Replica I/O Thread** | Реплика | Отвечает за сетевое взаимодействие. Поддерживает TCP-соединение, запрашивает данные с определенной позиции (позиция в файле или GTID). |
| **Replica SQL Thread** | Реплика | Отвечает за логику. В MTS-режиме этот поток выступает в роли **Координатора (Coordinator)**, который распределяет транзакции по **Воркерам (Workers)**. |

### Параллельная репликация (MTS) и отслеживание зависимостей

В MySQL 8.0 реплика может применять транзакции параллельно, если они не конфликтуют.
- **Coordinator:** SQL-поток, который считывает Relay Log и проверяет зависимости между транзакциями.
- **Workers:** Потоки, выполняющие сами транзакции. Их количество задается через `replica_parallel_workers`.

**Механизмы отслеживания (binlog_transaction_dependency_tracking):**
1.  **COMMIT_ORDER:** (Legacy) Транзакции, зафиксированные в одной группе на мастере, могут быть применены параллельно.
2.  **WRITESET:** (Рекомендуемый) Источник вычисляет хеши измененных строк. Если транзакции меняют разные строки, они помечаются как независимые и могут быть применены параллельно на реплике, даже если на мастере они фиксировались в разное время.

### Полусинхронная репликация (Semisync)

В стандартном механизме источник не ждет ответа от реплики. В полусинхронном режиме механизм дополняется этапом подтверждения (**ACK**):

**Типы ACK (rpl_semi_sync_master_wait_point):**
- **AFTER_SYNC (Lossless):** (Default) Источник сначала отправляет транзакцию на реплику, получает ACK и только потом делает `COMMIT` локально. Гарантирует, что данные на реплике есть *до* того, как они стали видны клиентам мастера.
- **AFTER_COMMIT (Legacy):** Источник сначала делает `COMMIT` локально, а потом ждет ACK от реплики. В случае сбоя возможна ситуация "фантомного чтения" (клиент увидел данные на мастере, но после сбоя их не оказалось ни на мастере, ни на реплике).

## Практические сценарии

### Настройка Crash-Safety механизма

Для того чтобы реплика не "развалилась" при внезапном выключении питания, механизм должен быть настроен на автоматическое восстановление:

```ini
[mysqld]
# Метаданные хранятся в InnoDB таблицах, а не в файлах
relay_log_info_repository = TABLE
master_info_repository = TABLE

# Игнорировать локальные файлы Relay Log после сбоя
# Реплика заново выкачает данные с источника по сохраненной позиции в таблицах
relay_log_recovery = ON

# Сбрасывать Relay Log на диск после каждой записи
sync_relay_log = 1
```

### Мониторинг воркеров (MTS) через Performance Schema

Для анализа производительности параллельной репликации используйте следующие запросы:

```sql
-- Состояние воркеров и ошибки на них
SELECT * FROM performance_schema.replication_applier_status_by_worker;

-- Статус координатора (очереди и задержки)
SELECT * FROM performance_schema.replication_applier_status_by_coordinator;
```

### Протокол Binlog Dump

При использовании GTID используется протокол `COM_BINLOG_DUMP_GTID`. 
**Преимущество:** Источнику передается не только позиция, но и `Executed_Gtid_Set` реплики. Источник сам вычисляет, какие транзакции нужно отправить, что исключает ошибки позиционирования.

## Дополнительная информация

### Изоляция через Relay Log

Использование Relay Log обеспечивает важную архитектурную развязку:
- **Скорость сети != Скорость диска:** Реплика может очень быстро скачать большой объем логов (например, во время ночного пакетного обновления) и медленно применять их в течение нескольких часов, не нагружая сеть постоянно.
- **Устойчивость:** Если источник выйдет из строя, на реплике в Relay Log останутся данные, которые она еще не успела применить, что позволяет выполнить более точное восстановление.
