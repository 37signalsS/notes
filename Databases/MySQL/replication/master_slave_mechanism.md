# Механизм Master-Slave репликации

## Определения

**Master-Slave репликация** — асинхронный механизм копирования данных с основного сервера (Master/Source) на один или несколько подчиненных серверов (Slave/Replica) в режиме реального времени.

**Потоки репликации** — три независимых процесса, обеспечивающих передачу и применение изменений: Binlog Dump Thread (на стороне Master), I/O Thread и SQL Thread (на стороне Slave).

**Relay Log (Журнал ретрансляции)** — промежуточный лог на Slave-сервере, содержащий копию бинарного лога (Binary Log) Master-сервера для последующего применения к данным.

## Основные концепции

### Архитектура потоков

```text
                                    +------------------------------------+
                                    |             Slave Server           |
                                    |                                    |
+----------------+                  |  +-------------+   +-------------+   |   +----------+
| Master Server  |                  |  |             |   |             |   |   |          |
|                | -- Binlog dump --> |  I/O Thread   |-->|  Relay Log  |--> | SQL Thread |-->| Database |
| +------------+ |                  |  |             |   |             |   |   |          |
| | Binary Log | |                  |  +-------------+   +-------------+   |   +----------+
| +------------+ |                  |                                    |
|       ^        |                  +------------------------------------+
|       |        |
| DML Commands   |
|       |        |
| +----------+   |
| | Database |   |
| +----------+   |
+----------------+
```

### Три потока репликации

| Поток | Сервер | Назначение |
| :--- | :--- | :--- |
| **Binlog Dump Thread** | Master | Считывает события из бинарного лога и отправляет их подключенным Slave-серверам. |
| **I/O Thread (Input/Output)** | Slave | Инициирует подключение к Master, получает события и записывает их в локальный Relay Log. |
| **SQL Thread** | Slave | Считывает данные из Relay Log и последовательно применяет транзакции к локальной Базе Данных (БД). |

### Детальное описание этапов

1. **Запись изменений:** Команды **DML (Data Manipulation Language — язык манипулирования данными)** и **DDL (Data Definition Language — язык определения данных)** фиксируются в бинарном логе на Master-сервере.
2. **Инициализация связи:** Slave-сервер запускает **I/O Thread**, который запрашивает у Master данные из бинарного лога, начиная с последней известной позиции.
3. **Передача данных:** На Master-сервере создается отдельный **Binlog Dump Thread** для каждого подключенного Slave. Он считывает записи из бинарного лога и отправляет их по сети.
4. **Буферизация (Relay Log):** I/O Thread на Slave-сервере принимает события и записывает их в **Relay Log**. Это позволяет разделить процессы получения и исполнения команд.
5. **Применение изменений:** **SQL Thread** на Slave-сервере читает Relay Log и выполняет содержащиеся в нем команды на локальной БД. При успешном выполнении файлы Relay Log автоматически удаляются (процесс `relay_log_purge`).

## Практические сценарии

### Проверка состояния потоков

Для диагностики используется команда `SHOW REPLICA STATUS` (в старых версиях — `SHOW SLAVE STATUS`).

```sql
-- Проверка статуса репликации
SHOW REPLICA STATUS\G
/*
             Replica_IO_Running: Yes
            Replica_SQL_Running: Yes
          Seconds_Behind_Master: 0
*/
```

### Диагностика остановки потоков

Если один из потоков имеет статус `No`, необходимо проверить соответствующее поле ошибки:

```sql
-- Ошибка I/O-потока (проблемы сети или аутентификации)
SHOW REPLICA STATUS\G
-- -> Last_IO_Error: error connecting to master...

-- Ошибка SQL-потока (конфликты данных или синтаксиса)
SHOW REPLICA STATUS\G
-- -> Last_SQL_Error: Error 'Duplicate entry...' on query...
```

### Управление потоками

В случае необходимости (например, для проведения технических работ) потоки можно останавливать и запускать независимо.

```sql
-- Полная остановка репликации
STOP REPLICA;
-- -> Query OK, 0 rows affected

-- Остановка только применения транзакций (чтение продолжается)
STOP REPLICA SQL_THREAD;
-- -> Query OK, 0 rows affected

-- Запуск всех потоков
START REPLICA;
-- -> Query OK, 0 rows affected
```

### Оптимизация: Параллельная репликация

Для ускорения работы SQL-потока на многоядерных системах (начиная с MySQL 5.7) можно включить многопоточное применение транзакций.

```ini
# Настройка в my.cnf (секция [mysqld])
# Количество рабочих потоков
slave_parallel_workers = 4
# Тип параллелизма: LOGICAL_CLOCK (позволяет выполнять транзакции из одного коммита одновременно)
slave_parallel_type = LOGICAL_CLOCK
```

## Дополнительная информация

### Роль Relay Log

Relay Log служит буфером безопасности. Он позволяет Slave-серверу быстро считать данные из бинарного лога Master (который может быть ротирован или удален) и применить их в своем темпе, не допуская потери событий при временных скачках нагрузки или сбоях сети.

### Сравнение с PostgreSQL

| Характеристика | MySQL | PostgreSQL |
| :--- | :--- | :--- |
| Основа передачи | Бинарный лог (Binlog) | Журнал транзакций (WAL) |
| Структура логов | Binlog + Relay Log | Streaming WAL |
| Потоки применения | SQL Thread (1 или несколько) | Startup Process (обычно 1) |
