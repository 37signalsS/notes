# Механизм Master-Slave репликации

## Definitions

**Master-Slave репликация** — асинхронный механизм копирования данных с основного сервера (Master) на подчиненные серверы (Slave) в реальном времени.

**Потоки репликации** — три независимых процесса, обеспечивающих передачу и применение изменений: Binlog Dump Thread (Master), I/O Thread (Slave), SQL Thread (Slave).

**Relay Log (Журнал ретрансляции)** — промежуточный лог на Slave-сервере, содержащий копию бинарного лога Master для последующего применения.

## Basic Concepts

### Архитектура потоков

```text
                                    +------------------------------------+
                                    |             Slave Server           |
                                    |                                    |
+----------------+                  |  +-------------+   +-------------+   |   +----------+
| Master Server  |                  |  |             |   |             |   |   |          |
|                | -- Binlog dump --> |  I/O Thread   |-->|  Relay Log  |--> | SQL Thread |-->| Database |
| +------------+ |                  |  |             |   |             |   |   |          |
| | Binary Log | |                  |  +-------------+   +-------------+   |   +----------+
| +------------+ |                  |                                    |
|       ^        |                  +------------------------------------+
|       |        |
| DML Commands   |
|       |        |
| +----------+   |
| | Database |   |
| +----------+   |
+----------------+
```

### Три потока репликации

| Поток | Сервер | Назначение |
| :--- | :--- | :--- |
| **Binlog Dump Thread** | Master | Читает события из binary log и отправляет подключенным Slave |
| **I/O Thread** | Slave | Подключается к Master, получает события и записывает в relay log |
| **SQL Thread** | Slave | Читает relay log и применяет события к локальной базе данных |

### Детальное описание потоков

#### 1. Binlog Dump Thread (на Master)

- Создается для каждого подключенного Slave-сервера
- Читает события из бинарного лога начиная с позиции, запрошенной Slave
- Отправляет события через сетевое соединение
- Приостанавливается, если Slave отстает (не читает данные)
- Завершается при отключении Slave

#### 2. I/O Thread (на Slave)

- Инициирует подключение к Master-серверу
- Запрашивает события начиная с последней известной позиции
- Получает события от Binlog Dump Thread
- Записывает события в Relay Log
- Обновляет файл `master.info` с координатами последнего прочитанного события
- Работает максимально быстро, минимизируя сетевую задержку

#### 3. SQL Thread (на Slave)

- Читает события из Relay Log последовательно
- Применяет события к локальной базе данных
- Удаляет обработанные Relay Log файлы (при включенном `relay_log_purge`)
- Может отставать от I/O Thread при высокой нагрузке на запись
- В MySQL 5.7+ может работать параллельно (несколько worker-потоков)

### Этапы репликации

1. **Запись на Master:** Команды DML (`INSERT`, `UPDATE`, `DELETE`) записываются в **бинарный лог (Binary Log)**.

2. **Подключение Slave:** Slave-сервер инициирует подключение к Master. Запускается **I/O Thread**.

3. **Запрос данных:** I/O Thread запрашивает у Master содержимое бинарного лога с последней сохраненной позиции.

4. **Отправка данных:** На Master создается **Binlog Dump Thread** для чтения и отправки событий.

5. **Запись в Relay Log:** I/O Thread записывает полученные события в **журнал ретрансляции (Relay Log)** — точную копию бинарного лога Master.

6. **Применение данных:** **SQL Thread** читает Relay Log, преобразует события в SQL-запросы и выполняет их на локальной базе.

## Practical Scenarios

### Проверка состояния потоков

```sql
-- Проверка статуса репликации
SHOW SLAVE STATUS\G

-- Ключевые поля:
--   Slave_IO_Running: Yes      -- I/O-поток работает
--   Slave_SQL_Running: Yes     -- SQL-поток работает
--   Seconds_Behind_Master: 0   -- Отставание отсутствует
```

### Диагностика проблем с потоками

**I/O Thread остановлен:**

```sql
SHOW SLAVE STATUS\G | grep Last_IO_Error
```

Возможные причины:

- Сетевая недоступность Master
- Неправильные учетные данные
- Master не имеет бинарного лога с запрошенной позиции

**SQL Thread остановлен:**

```sql
SHOW SLAVE STATUS\G | grep Last_SQL_Error
```

Возможные причины:

- Ошибка выполнения SQL (дубликат ключа, отсутствие таблицы)
- Конфликт данных между Master и Slave
- Недетерминированный запрос при STATEMENT-репликации

### Мониторинг отставания (Replication Lag)

```sql
-- Быстрая проверка отставания
SHOW SLAVE STATUS\G | grep Seconds_Behind_Master

-- Если Seconds_Behind_Master = NULL, проверьте потоки:
--   - SQL Thread может быть остановлен
--   - Нет событий для применения (проверьте Last_SQL_Error)
```

**Причины отставания:**

- **Медленная сеть:** I/O Thread не успевает получать события
- **Высокая нагрузка на Slave:** SQL Thread не успевает применять события
- **Блокировки:** SQL Thread ждет снятия блокировок на Slave
- **Однопоточное применение:** В старых версиях MySQL SQL Thread один

### Управление потоками

```sql
-- Остановка всех потоков репликации
STOP SLAVE;

-- Остановка только I/O-потока (чтение от Master)
STOP SLAVE IO_THREAD;

-- Остановка только SQL-потока (применение событий)
STOP SLAVE SQL_THREAD;

-- Запуск всех потоков
START SLAVE;

-- Запуск конкретного потока
START SLAVE IO_THREAD;
START SLAVE SQL_THREAD;
```

### Настройка параллельной репликации (MySQL 5.7+)

Для ускорения применения событий на Slave:

```ini
[mysqld]
# Количество worker-потоков для параллельного применения
slave_parallel_workers = 4

# Тип параллелизма: LOGICAL_CLOCK (рекомендуется)
slave_parallel_type = LOGICAL_CLOCK

# Размер очереди для worker-потоков
slave_pending_jobs_size_max = 1G
```

> **Важно:** Параллельная репликация эффективна при наличии независимых транзакций, которые могут выполняться одновременно.

## Additional Information

### Relay Log: детали

**Назначение:**

- Буфер между быстрой сетевой передачей и медленным применением
- Позволяет Slave продолжать работу при временной недоступности Master
- Дает возможность приостановить применение без остановки чтения

**Расположение:**

```ini
[mysqld]
relay-log = /var/log/mysql/mysql-relay-bin.log
relay-log-index = /var/log/mysql/mysql-relay-bin.index
```

**Автоматическая очистка:**

```ini
[mysqld]
relay_log_purge = ON  # По умолчанию в современных версиях
```

### Синхронизация и безопасность

**Потеря данных при сбое:**

- При аварийном отключении Master возможна потеря непримененных событий
- I/O Thread может не успеть прочитать последние события из binlog
- Relay Log защищает от кратковременных сбоев сети

**Консистентность:**

- При `binlog_format = ROW` гарантируется побайтовое совпадение данных
- При `binlog_format = STATEMENT` возможна рассинхронизация при недетерминированных запросах
- GTID обеспечивает дополнительную гарантию идемпотентности

### Эволюция механизма

| Версия MySQL | Улучшение |
| :--- | :--- |
| 5.1 | Базовая репликация (однопоточная) |
| 5.5 | Полусинхронная репликация (опционально) |
| 5.6 | GTID, улучшенная параллельная репликация (по базе данных) |
| 5.7 | LOGICAL_CLOCK параллелизм (по коммитам) |
| 8.0 | Улучшенная производительность, WRITESET параллелизм |

### Сравнение с PostgreSQL

| Характеристика | MySQL | PostgreSQL |
| :--- | :--- | :--- |
| Механизм | Binlog + Relay Log | WAL Streaming |
| Потоки | 3 (Binlog Dump, I/O, SQL) | WAL Sender + WAL Receiver |
| Применение | SQL Thread (однопоточное по умолчанию) | Startup Process (однопоточное) |
| Параллелизм | `slave_parallel_workers` | `max_parallel_apply_workers` (12+) |
