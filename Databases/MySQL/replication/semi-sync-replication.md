# Полусинхронная репликация MySQL (Semisynchronous Replication)

**Актуально для:** MySQL 8.0.26 / 8.4 LTS / 9.x Innovation

Начиная с MySQL 8.0.26 плагины полусинхронной репликации переименованы: термины
`master` и `slave` заменены на `source` и `replica` в именах плагинов, библиотек
и системных/статусных переменных. Старые имена остались устаревшими синонимами,
но в новых инсталляциях использовать следует новые.

Смежные темы: [Отслеживание лага репликации](./lag_monitoring.md),
[GTID](./gtid.md), [Переключение источника](./failover_switchover.md),
[Репликация — обзор](./overview.md).

## Определения

| Термин | Значение |
| :--- | :--- |
| Источник (source) | Сервер, принимающий записи и генерирующий binary log |
| Реплика (replica) | Сервер, применяющий события источника |
| Semi-sync | Режим, в котором источник блокируется на коммите до подтверждения от реплики |
| Acknowledgment | Подтверждение от реплики, что она получила события транзакции и сбросила их в relay log на диск |
| AFTER_SYNC | Точка ожидания: подтверждение получается после синхронизации binlog, **до** коммита в storage engine |
| AFTER_COMMIT | Точка ожидания: подтверждение получается **после** коммита в storage engine |
| Деградация в async | Автоматический переход источника в асинхронный режим по таймауту ожидания подтверждения |
| Канал по умолчанию | Канал с пустым именем `""`; единственный канал, с которым совместим semisync |

## Базовые концепции

### Как работает механизм

1. Реплика сообщает источнику о своей способности работать в полусинхронном
   режиме при подключении I/O (receiver) потока.
2. Если полусинхронный режим включён на источнике и подключён хотя бы один
   полусинхронный реплика, поток, выполняющий коммит транзакции на источнике,
   **блокируется** и ждёт, пока нужное число полусинхронных реплик подтвердит
   получение всех событий транзакции, либо пока не истечёт таймаут.
3. Реплика подтверждает получение событий транзакции только **после** того, как
   события записаны в её relay log и сброшены на диск.
4. Если таймаут наступил без подтверждения, источник откатывается в
   асинхронную репликацию. Когда хотя бы одна полусинхронная реплика догоняет
   источник, источник автоматически возвращается в полусинхронный режим.

Полусинхронный режим должен быть включён **на обеих сторонах**. Если он выключен
на источнике, либо включён на источнике, но ни на одной реплике, источник
использует асинхронную репликацию.

Заявления вне транзакционного контекста (то есть без `START TRANSACTION` и без
`SET autocommit = 0`) коммитятся неявно, и источник блокируется на каждом таком
заявлении точно так же, как на явных коммитах. Блокировка возникает и после
откатов, записываемых в binary log: когда откатывается транзакция, изменяющая
нетранзакционные таблицы, она всё равно записывается в binlog (изменения
нетранзакционных таблиц откатить нельзя), и источник ждёт подтверждения для
этой записи.

### Гарантия и её границы

Гарантия, которую даёт режим: **если источник аварийно завершился, все
закоммиченные им транзакции переданы как минимум одной реплике** (сохранены в
её relay log). При этом подтверждение не означает применения событий в таблицы
реплики — защита от потери данных при отказе источника, но не гарантия
актуальности чтения с реплики и не замена бэкапам.

> **Правило failover:** если источник аварийно завершился и выполняется
> переключение на реплику, вышедший из строя источник **не следует**
> переиспользовать как источник репликации — его нужно вывести из эксплуатации.
> На нём могут остаться транзакции, не подтверждённые ни одной репликой (не
> закоммиченные до переключения).

### Точки ожидания: AFTER_SYNC и AFTER_COMMIT

`rpl_semi_sync_source_wait_point` допускает два значения:

- **`AFTER_SYNC` (по умолчанию):** источник записывает транзакцию в свой
  binary log и передаёт реплике, синхронизирует binary log на диск, **затем**
  ждёт подтверждения получения, **после** чего коммитит транзакцию в storage
  engine и возвращает результат клиенту.
- **`AFTER_COMMIT`:** источник записывает транзакцию в binary log, синхронизирует
  его, **коммитит в storage engine**, и только затем ждёт подтверждения
  получения. После подтверждения возвращает результат клиенту.

Различия в поведении:

- **`AFTER_SYNC`:** все клиенты видят зафиксированную транзакцию одновременно
  — после подтверждения репликой и коммита в storage engine источника. При
  аварийном выходе источника и переключении на реплику потерь нет: реплика
  полностью актуальна.
- **`AFTER_COMMIT`:** между коммитом в storage engine и подтверждением репликой
  другие клиенты могут увидеть зафиксированную транзакцию раньше, чем клиент,
  её инициировавший. Если реплика не обработает транзакцию, при аварийном
  выходе источника и переключении такие клиенты могут потерять данные
  относительно того, что видели на источнике.

### Плагины: новая и старая ветки

| | Новая ветка | Старая ветка |
| :--- | :--- | :--- |
| Плагин источника | `rpl_semi_sync_source` | `rpl_semi_sync_master` |
| Плагин реплики | `rpl_semi_sync_replica` | `rpl_semi_sync_slave` |
| Библиотека источника | `semisync_source.so` | `semisync_master.so` |
| Библиотека реплики | `semisync_replica.so` | `semisync_slave.so` |
| Префикс переменных | `rpl_semi_sync_source_*` / `rpl_semi_sync_replica_*` | `rpl_semi_sync_master_*` / `rpl_semi_sync_slave_*` |
| Доступна с | MySQL 8.0.26 | раньше |

> **Ограничение, ломающее конфигурацию:** установить обе версии соответствующего
> плагина на одном инстансе **невозможно**. Если установлена новая версия
> `rpl_semi_sync_source`, то доступны новые переменные, а старые — **нет**, и наоборот.
> Проверять всегда фактический набор:

```sql
SHOW VARIABLES LIKE 'rpl_semi_sync%';
```

Суффикс библиотеки зависит от платформы (`.so` для Unix-подобных, `.dll` для
Windows). Файлы библиотек должны находиться в каталоге плагинов (`plugin_dir`).

### Требования и ограничения

- Динамическая загрузка плагинов: `SHOW VARIABLES LIKE 'have_dynamic_loading';`
  → `YES` (бинарные дистрибутивы поддерживают).
- Репликация **уже должна работать** — semisync не настраивается «с нуля».
- **Только канал по умолчанию.** Нельзя настраивать несколько каналов
  репликации: semisync совместим только с каналом по умолчанию (пустое имя
  `""`). Multi-source с именованными каналами semisync не поддерживает —
  см. [multi-source.md](multi-source.md).
- `INSTALL PLUGIN`, `SET GLOBAL`, `STOP REPLICA`, `START REPLICA` требуют
  привилегии `REPLICATION_SLAVE_ADMIN` (или deprecated `SUPER`).

### Ключевые системные переменные

Переменные доступны только при установленном соответствующем плагине. Все —
`Global`, динамические (`SET GLOBAL`).

**Источник:**

| Переменная | По умолчанию | Диапазон | Назначение |
| :--- | :--- | :--- | :--- |
| `rpl_semi_sync_source_enabled` | `OFF` | `ON`/`OFF` | Включение полусинхронного режима на источнике |
| `rpl_semi_sync_source_timeout` | `10000` | `0`–`4294967295` мс | Сколько источник ждёт подтверждения до отката в async |
| `rpl_semi_sync_source_trace_level` | `32` | `0`–`4294967295` | Битмаска уровня трассировки (см. ниже) |
| `rpl_semi_sync_source_wait_for_replica_count` | `1` | `1`–`65535` | Сколько подтверждений нужно на транзакцию |
| `rpl_semi_sync_source_wait_no_replica` | `ON` | `ON`/`OFF` | Ждать ли таймаут, если число реплик упало ниже `wait_for_replica_count` |
| `rpl_semi_sync_source_wait_point` | `AFTER_SYNC` | `AFTER_SYNC`, `AFTER_COMMIT` | Точка ожидания подтверждения |

**Реплика:**

| Переменная | По умолчанию | Диапазон | Назначение |
| :--- | :--- | :--- | :--- |
| `rpl_semi_sync_replica_enabled` | `OFF` | `ON`/`OFF` | Включение полусинхронного режима на реплике |
| `rpl_semi_sync_replica_trace_level` | `32` | `0`–`4294967295` | Битмаска уровня трассировки |

`rpl_semi_sync_source_wait_for_replica_count`: значение по умолчанию `1` означает,
что полусинхронная репликация продолжается после одного подтверждения;
производительность лучше при малых значениях. При значении `2` до истечения
таймаута должны подтвердить получение транзакции две реплики, иначе источник
откатывается в обычную репликацию. Поведение зависит также от
`rpl_semi_sync_source_wait_no_replica`: при `ON` (по умолчанию) источник
продолжает ждать до истечения таймаута, даже если число реплик упало ниже
`wait_for_replica_count`; при `OFF` — откатывается в async сразу, как только
число реплик стало недостаточным.

`rpl_semi_sync_source_trace_level` — битмаска: `1` = общий уровень (например,
сбои функций времени), `16` = детальный уровень, `32` = уровень ожиданий в сети,
`64` = уровень входа/выхода функций. Значения комбинируются (например, `48` =
`32`+`16`). Трассировка пишется в error log; `0` — без диагностики.

### Оптимизация при росте числа реплик

С ростом числа реплик contention на блокировках способен снижать производительность
как на источнике, так и на репликах:

```sql
-- Ограничивает колбэки
SET GLOBAL replication_sender_observe_commit_only = ON;

-- Использует разделяемые блокировки и устраняет ненужные захваты
SET GLOBAL replication_optimize_for_static_plugin_config = ON;
```

Обе переменные — `Global`, динамические, по умолчанию `OFF`; могут включаться до
или после установки плагина semisync и при работающей репликации. Источник
получает от них выигрыш, потому что использует те же механизмы блокировок, что и
реплики. **Ограничение на очистку:** пока переменная включена, плагин semisync
нельзя удалить (`UNINSTALL PLUGIN`) — сначала выключите переменную.

## Практические сценарии

### Сценарий 1. Развёртывание с нуля

```sql
-- На источнике: проверить динамическую загрузку и установить плагин
SHOW VARIABLES LIKE 'have_dynamic_loading';
-- → have_dynamic_loading | YES

INSTALL PLUGIN rpl_semi_sync_source SONAME 'semisync_source.so';
-- → Query OK, 0 rows affected

-- На реплике: своя библиотека, не source!
INSTALL PLUGIN rpl_semi_sync_replica SONAME 'semisync_replica.so';
-- → Query OK, 0 rows affected
```

Проверка установки плагина:

```sql
SELECT PLUGIN_NAME, PLUGIN_STATUS
FROM INFORMATION_SCHEMA.PLUGINS
WHERE PLUGIN_NAME LIKE '%semi%';
-- → rpl_semi_sync_source | ACTIVE
```

Включение режима:

```sql
-- На источнике
SET GLOBAL rpl_semi_sync_source_enabled = 1;
SET GLOBAL rpl_semi_sync_source_timeout = 10000;
SET GLOBAL rpl_semi_sync_source_wait_for_replica_count = 1;
SET GLOBAL rpl_semi_sync_source_wait_point = 'AFTER_SYNC';

-- На реплике
SET GLOBAL rpl_semi_sync_replica_enabled = 1;
-- При включении в runtime обязательно перезапустить I/O (receiver) поток,
-- иначе реплика не зарегистрируется как полусинхронная и продолжит работать
-- в асинхронном режиме:
STOP REPLICA IO_THREAD;
START REPLICA IO_THREAD;
```

Для постоянства настройки продублируйте в `my.cnf` — `SET GLOBAL` сбрасывается при
рестарте сервера:

```ini
[mysqld]
# на источнике
rpl_semi_sync_source_enabled=1
# на реплике
rpl_semi_sync_replica_enabled=1
```

Проверка режима с обеих сторон:

```sql
-- На источнике
SHOW STATUS LIKE 'Rpl_semi_sync%';
-- → Variable_name                     | Value
-- → Rpl_semi_sync_source_clients      |     2   ← подключено полусинхронных реплик
-- → Rpl_semi_sync_source_status       |     1   ← режим работает сейчас
-- → Rpl_semi_sync_source_no_tx        |     0   ← коммитов без подтверждения
-- → Rpl_semi_sync_source_yes_tx       | 184213  ← коммитов с подтверждением

-- На реплике
SHOW STATUS LIKE 'Rpl_semi_sync_replica_status';
-- → Rpl_semi_sync_replica_status = ON (плагин включён и I/O поток работает)
```

> **Ключевое различие для мониторинга:** из-за автоматической деградации в async
> значение `rpl_semi_sync_source_enabled = 1` **не означает**, что полусинхронная
> репликация работает в данный момент. Действующий режим показывает
> `Rpl_semi_sync_source_status`: `0`, если плагин выключен **или** источник откатился в
> асинхронный режим по таймауту подтверждения. Алертить нужно именно на эту переменную.

### Сценарий 2. Поведение при потере ответа от реплики

Если реплика не отвечает в течение `rpl_semi_sync_source_timeout`:

- **Деградация в асинхронный режим (async).** Источник переключается в обычную
  асинхронную репликацию. Новые транзакции фиксируются без ожидания подтверждения.
- **Возврат в semi-sync.** Когда подключённая полусинхронная реплика снова начнёт
  присылать подтверждения, источник автоматически вернётся в полусинхронный режим.
  Переключение автоматическое, ручного вмешательства не требуется.

При каждом таком переключении источник выставляет `Rpl_semi_sync_source_status`
соответствующим образом и увеличивает `Rpl_semi_sync_source_no_times` (счётчик
переключений источника в асинхронный режим), поэтому рост этого счётчика —
сигнал о нестабильности сети или реплик.

### Сценарий 3. Влияние на latency источника

- **Нормальная работа:** каждая транзакция ждёт подтверждения от реплики (RTT сети плюс
  время записи в relay log на реплике). Это увеличивает время коммита на источнике по
  сравнению с чистым async — как минимум на TCP/IP RTT.
- **Потеря подтверждений (таймаут):** транзакции, «упёршиеся» в таймаут, фиксируются с
  задержкой порядка `rpl_semi_sync_source_timeout`. После переключения в async latency
  источника снижается до уровня обычной асинхронной репликации.
- **Выбор таймаута:** `rpl_semi_sync_source_timeout` (в миллисекундах, по умолчанию
  `10000`) — компромисс между сохранением гарантий semi-sync и устойчивостью источника к
  временным сетевым проблемам. Слишком маленькое значение даёт частые деградации, слишком
  большое — источник дольше «зависает» при недоступности реплики.
- **Измерение цены ожидания:** `Rpl_semi_sync_source_tx_avg_wait_time` (среднее время
  ожидания транзакции, мкс) и `Rpl_semi_sync_source_tx_wait_time` (суммарное время, мкс)
  позволяют оценить накладные расходы режима в конкретной топологии.

### Сценарий 4. Когда теряется гарантия доставки

Гарантия зависит от точки ожидания (`AFTER_SYNC` или `AFTER_COMMIT`):

- Пока источник **ещё не получил** подтверждение и транзакция не закоммичена, потеря
  источника в этот момент может означать, что транзакция не дошла ни до одной реплики.
  После таймаута источник может её закоммитить в асинхронном режиме — возникает классический
  компромисс между durability и availability.
- **После деградации в async** гарантии semi-sync временно отсутствуют до возврата
  режима. Это ожидаемое поведение (fail-safe деградация).
- При `AFTER_COMMIT` клиенты могут увидеть транзакцию до того, как она гарантированно
  попала на реплику (см. раздел про точки ожидания).
- При failover после аварии источника упавший источник не переиспользуется (см.
  «Гарантия и её границы»).

### Сценарий 5. Оптимизация при росте числа реплик

С ростом числа реплик contention на блокировках способен снижать производительность как
на источнике, так и на репликах. Две системные переменные (описаны в разделе
«Оптимизация при росте числа реплик») снижают нагрузку:
`replication_sender_observe_commit_only` (ограничивает колбэки) и
`replication_optimize_for_static_plugin_config` (разделяемые блокировки). Помните
ограничение на удаление плагина, пока они включены.

## Валидация

Порядок проверки работоспособности после включения:

```sql
-- 1. Плагин установлен и активен (на обеих сторонах)
SHOW PLUGINS LIKE '%semi%';
-- → Name                | Status
-- → rpl_semi_sync_source | ACTIVE      (на источнике)
-- → rpl_semi_sync_replica | ACTIVE     (на реплике)

-- 2. Режим включён с обеих сторон
SHOW VARIABLES LIKE 'rpl_semi_sync_%enabled';
-- → rpl_semi_sync_source_enabled  | ON    (источник)
-- → rpl_semi_sync_replica_enabled | ON    (реплика)

-- 3. Фактический режим работы (источник)
SHOW STATUS LIKE 'Rpl_semi_sync_source_status';
-- → Rpl_semi_sync_source_status | 1

-- 4. Есть подключённые полусинхронные реплики (источник)
SHOW STATUS LIKE 'Rpl_semi_sync_source_clients';
-- → Rpl_semi_sync_source_clients | 1

-- 5. Реплика зарегистрирована как полусинхронная (реплика)
SHOW STATUS LIKE 'Rpl_semi_sync_replica_status';
-- → Rpl_semi_sync_replica_status | ON

-- 6. Подтверждения поступают: yes_tx растёт, no_tx = 0
SHOW STATUS LIKE 'Rpl_semi_sync_source_%tx';
-- → Rpl_semi_sync_source_no_tx  | 0
-- → Rpl_semi_sync_source_yes_tx | <растёт с числом коммитов>
```

Если `Rpl_semi_sync_source_clients = 0` при `enabled = 1` — реплика не зарегистрировалась:
проверьте `rpl_semi_sync_replica_enabled` на реплике и факт перезапуска I/O потока
(`STOP REPLICA IO_THREAD; START REPLICA IO_THREAD;`).

## Устранение неисправностей (Troubleshooting)

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| `rpl_semi_sync_source_enabled = 1`, но `Rpl_semi_sync_source_status = 0` | Источник откатился в async по таймауту | Проверить `Rpl_semi_sync_source_clients`; если 0 — нет подключённых полусинхронных реплик |
| `Rpl_semi_sync_source_clients = 0` при включённом режиме | На реплике не установлен или не включён `rpl_semi_sync_replica`, либо не перезапущен I/O поток после `SET GLOBAL` | Проверить `SHOW VARIABLES LIKE 'rpl_semi_sync%'` **на реплике**; выполнить `STOP REPLICA IO_THREAD; START REPLICA IO_THREAD;` |
| `ERROR 1126 (HY000): Can't open shared library ... errno: 22 libimf.so` | Не установлена библиотека `libimf` | Установить `libimf` (пакет Intel Math Library из MySQL Linux distribution) |
| Переменные `rpl_semi_sync_source_*` отсутствуют | Установлена старая ветка плагинов | Сверить с фактически установленным плагином (`SHOW PLUGINS`); обе версии на одном инстансе несовместимы |
| Частые переключения `Rpl_semi_sync_source_status`, растёт `no_times` | Нестабильная сеть или медленные реплики | Измерить RTT; пересмотреть `rpl_semi_sync_source_timeout` |
| Latency коммита выросла после включения semi-sync | Ожидание подтверждения в пределах RTT | Ожидаемо; посмотреть `Rpl_semi_sync_source_tx_avg_wait_time`; проверить, не завышен ли `wait_for_replica_count` |
| Резкое падение throughput | `wait_for_replica_count` выше 1 | Снизить до 1 либо добавить реплик; проверить `wait_no_replica` |
| Транзакции вне явных транзакций блокируются | Каждый оператор при `autocommit = 1` коммитится неявно и блокируется | Ожидаемое поведение; при необходимости упаковать операторы в явную транзакцию |
| `Rpl_semi_sync_source_no_tx` растёт | Растёт число коммитов без подтверждения | Проверить error log источника и состояние реплик |
| Нужна детальная диагностика работы плагина | — | Поднять `rpl_semi_sync_source_trace_level` / `rpl_semi_sync_replica_trace_level` (битмаска: 1, 16, 32, 64), диагностика пишется в error log |

## Лучшие практика

- **Мониторить `Rpl_semi_sync_source_status`, а не `rpl_semi_sync_source_enabled`.**
  Только первая переменная отражает фактический режим в данный момент.
- **Следить за `Rpl_semi_sync_source_clients`.** Ноль подключённых полусинхронных реплик
  означает, что режим не работает, несмотря на `enabled = 1`.
- **Отслеживать соотношение `Rpl_semi_sync_source_yes_tx` к
  `Rpl_semi_sync_source_no_tx` и счётчик `Rpl_semi_sync_source_no_times`.** Резкие
  частые переключения async ↔ semi-sync — сигнал о нестабильности сети или реплик.
- **Подбирать таймаут под фактический RTT.** Значение по умолчанию — `10000` мс;
  менять его следует только с обоснованием и с замером RTT.
- **Использовать `AFTER_SYNC` (значение по умолчанию).** Разница в том, какие данные
  успевают увидеть клиенты, — не техническая деталь: при `AFTER_SYNC` все клиенты
  видят транзакцию одновременно, при `AFTER_COMMIT` — нет.
- **Держать минимум одну полусинхронную реплику.** Конфигурация с одной
  полусинхронной репликой — распространённый практический вариант; при её потере
  деградация в async ожидаема.
- **Оптимизировать contention при масштабировании.** При нескольких репликах включать
  `replication_sender_observe_commit_only` и
  `replication_optimize_for_static_plugin_config`; перед `UNINSTALL PLUGIN` —
  выключить обе.
- **Помнить про цену гарантии:** semi-sync увеличивает время коммита как минимум на
  TCP/IP RTT до реплики плюс запись событий в её relay log; режим лучше всего работает
  для близких серверов в быстрых сетях.
- **Отключение режима:** выключите `rpl_semi_sync_source_enabled` /
  `rpl_semi_sync_replica_enabled`, при необходимости удалите плагины
  (`UNINSTALL PLUGIN rpl_semi_sync_source;` / `UNINSTALL PLUGIN rpl_semi_sync_replica;`)
  — только после выключения оптимизационных переменных.

## Дополнительная информация

### Граничные случаи и ограничения

- **Заявления вне транзакционного контекста** (без `START TRANSACTION` и без
  `SET autocommit = 0`) при `autocommit = 1` коммитятся неявно, и источник блокируется
  на каждом таком заявлении — так же, как на явных коммитах. То же верно для откатов
  транзакций с нетранзакционными таблицами: они записываются в binlog и тоже ждут
  подтверждения.
- **Обе версии плагина на одном инстансе несовместимы.** Это самая частая причина
  «пропавших» переменных при обновлении с 8.0.25 и ранее на 8.0.26+.
- **Автоматическая деградация в async делает `enabled` ненадёжным индикатором.**
  Это следствие заложенного в механизм поведения, а не ошибка конфигурации.
- **Полусинхронность не устраняет lag.** Она гарантирует доставку, а не свежесть: после
  деградации реплика может отставать. Отслеживание лага —
  [Отслеживание лага репликации](./lag_monitoring.md).
- **`Rpl_semi_sync_source_net_avg_wait_time` и `Rpl_semi_sync_source_net_wait_time`**
  всегда равны 0 и объявлены deprecated — для измерения ожиданий используйте
  `tx_avg_wait_time` / `tx_wait_time` и счётчик `tx_waits`.
- **`Rpl_semi_sync_source_wait_pos_backtraverse`** растёт, когда порядок, в котором
  транзакции начинают ждать ответа, отличается от порядка записи их событий в binlog —
  вспомогательный диагностический признак перестановки ожиданий.
