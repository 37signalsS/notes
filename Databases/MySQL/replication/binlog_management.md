# Управление бинарными и ретрансляционными логами в MySQL

## Определения

**Бинарный лог (Binary Log)** — журнал всех событий, изменяющих данные (DML) или структуру базы данных (DDL) на стороне источника. Необходим для репликации и восстановления данных на определенный момент времени (**Point-in-Time Recovery — PITR**).

**Ретрансляционный лог (Relay Log)** — временный журнал на стороне реплики, содержащий события, полученные от источника, но еще не примененные к локальным данным.

**Point-in-Time Recovery (PITR)** — процедура восстановления базы данных до конкретного момента в прошлом путем наката транзакций из бинарных логов поверх полного бэкапа.

## Основные концепции

### Жизненный цикл бинарных логов (Source)

MySQL 8.0+ предоставляет автоматизированные механизмы контроля объема журналов:

- **binlog_expire_logs_seconds:** Время хранения файлов (заменил `expire_logs_days`). Определяет момент автоматического удаления старых логов.
- **max_binlog_size:** Максимальный размер одного файла. По достижении лимита создается новый файл лога.
- **binlog_space_limit:** (MySQL 8.0.21+) Жесткий лимит на суммарный объем всех binlog-файлов. При переполнении старые файлы удаляются превентивно.

### Жизненный цикл ретрансляционных логов (Replica)

Настройка хранения Relay Log критична для стабильности реплики:

- **relay_log_purge = ON:** (По умолчанию) Автоматическое удаление файлов Relay Log сразу после их успешного применения SQL-потоком.
- **relay_log_space_limit:** Общий лимит места для Relay Log. Если место заканчивается, I/O-поток останавливается до тех пор, пока SQL-поток не освободит пространство. Полезно для защиты диска на реплике.
- **relay_log_recovery = ON:** Гарантирует целостность репликации после сбоя. При запуске реплика отбрасывает недополученные Relay Logs и скачивает их заново, основываясь на позиции в БД.

### Целостность и безопасность

- **binlog_checksum = CRC32:** (По умолчанию) Добавление контрольной суммы к каждому событию. Позволяет обнаружить повреждение данных при чтении или передаче.
- **sync_binlog = 1:** Сброс логов на диск после каждой транзакции. Гарантирует **Crash-Safety**.
- **binlog_encryption = ON:** (MySQL 8.0.14+) Шифрование логов на диске (требует Keyring plugin).
- **binlog_transaction_compression = ON:** (MySQL 8.0.20+) Сжатие транзакций по алгоритму ZSTD (экономия 60–90% места).

## Практические сценарии

### 1. Мониторинг и анализ логов

```sql
-- Просмотр списка бинарных логов
SHOW BINARY LOGS;

-- Просмотр состояния ретрансляционных логов на реплике
SHOW REPLICA STATUS\G
-- → Relay_Log_File, Relay_Log_Pos

-- Анализ эффективности сжатия (MySQL 8.0.20+)
SELECT * FROM performance_schema.binary_log_transaction_compression_stats\G
```

### 2. Ручное управление ротацией и очисткой

**Никогда не удаляйте файлы логов через команды операционной системы (`rm`).** Используйте SQL-команды для сохранения целостности метаданных.

```sql
-- Принудительное создание нового файла лога
FLUSH BINARY LOGS;

-- Удаление логов старше конкретной даты
PURGE BINARY LOGS BEFORE '2024-05-01 00:00:00';

-- Удаление логов до определенного файла
PURGE BINARY LOGS TO 'mysql-bin.000123';
```

### 3. Удаленное резервное копирование логов

Утилита `mysqlbinlog` позволяет скачивать логи с работающего сервера без остановки:

```bash
# Непрерывное скачивание логов с источника на сервер бэкапов
mysqlbinlog --read-from-remote-server \
            --host=source_db \
            --user=repl_user \
            --password \
            --raw \
            --stop-never \
            --result-file=/backup/binlogs/ mysql-bin.000001
```

### 4. Процедура Point-in-Time Recovery (PITR)

Алгоритм восстановления при аварии (например, ошибочный `DROP TABLE`):

1. **Определите точку остановки:** Найдите GTID или временную метку события непосредственно ПЕРЕД ошибкой.
2. **Восстановите последний полный бэкап** (например, через XtraBackup или mysqldump).
3. **Примените логи:**

```bash
# Вариант 1: По временной метке
mysqlbinlog --stop-datetime="2024-08-03 10:00:00" \
    /var/lib/mysql/binlog.000* | mysql -u root -p

# Вариант 2: По GTID (наиболее надежный)
mysqlbinlog --include-gtids="3E11FA47-71CA-11E1-9E33-C80AA9429562:1-541" \
    /var/lib/mysql/binlog.000* | mysql -u root -p
```

## Дополнительная информация

### Рекомендации по эксплуатации

- **Изоляция диска:** Храните бинарные логи на выделенном диске или разделе. Это предотвратит "падение" сервера из-за переполнения раздела с данными.
- **Relay Log Space:** На репликах с высокой нагрузкой всегда ограничивайте `relay_log_space_limit`, чтобы лаг репликации не привел к переполнению диска.
- **Архивация:** В критически важных системах настройте `mysqlbinlog --stop-never` на удаленный сервер для защиты логов в реальном времени.
