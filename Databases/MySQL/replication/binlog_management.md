# Управление бинарными логами (Binary Log) в MySQL

## Определения

**Бинарный лог (Binary Log)** — журнал всех событий, изменяющих данные (**DML** — Data Manipulation Language) или структуру базы данных (**DDL** — Data Definition Language). Подробнее: **[DDL vs DML](../../Concepts/DDL_vs_DML.md)**. Является основой для репликации и восстановления данных на определенный момент времени (Point-in-Time Recovery).

**Управление бинарными логами** — совокупность процессов мониторинга объема, настройки автоматической ротации и ручной очистки журналов для предотвращения переполнения дискового пространства и обеспечения стабильности системы.

## Основные концепции

### Проблема роста объема логов

В системах с высокой интенсивностью операций записи объем бинарных логов может многократно превышать размер самой базы данных.

**Пример:** При базе данных объемом 50 ГБ и нагрузке 1000 транзакций в секунду объем логов за неделю может составить несколько терабайт. Рекомендуется выделять под хранение логов отдельный дисковый раздел или иметь запас свободного места, значительно превышающий объем актуальных данных.

### Автоматическая ротация и очистка

MySQL обеспечивает автоматическое удаление старых файлов бинарного лога на основе времени хранения:

| Параметр | Описание | Примечание |
| :--- | :--- | :--- |
| `binlog_expire_logs_seconds` | Время хранения логов в секундах | Стандарт для MySQL 8.0+ (рекомендуется) |
| `expire_logs_days` | Время хранения логов в днях | Считается устаревшим (Deprecated) в MySQL 8.0 |
| `max_binlog_size` | Максимальный размер одного файла лога | По умолчанию 1 ГБ |

### Ручная очистка (PURGE)

Ручное удаление логов выполняется командой `PURGE BINARY LOGS`. Этот процесс требует обязательной предварительной проверки состояния реплик (Slaves), чтобы избежать удаления данных, которые еще не были переданы или применены на подчиненных серверах.

## Практические сценарии

### 1. Мониторинг состояния бинарных логов

Для оценки занимаемого места и текущей активности используются следующие запросы:

```sql
-- Список всех файлов лога и их индивидуальные размеры
SHOW BINARY LOGS;
/*
+------------------+-----------+-----------+
| Log_name         | File_size | Encrypted |
+------------------+-----------+-----------+
| mysql-bin.000001 | 107374182 | No        |
...
*/

-- Суммарный объем всех бинарных логов на диске
SELECT SUM(FILE_SIZE) / 1024 / 1024 / 1024 AS total_size_gb
FROM information_schema.FILES
WHERE FILE_TYPE LIKE 'BINARY LOG%';
-- -> 15.42
```

### 2. Настройка автоматического удаления

Рекомендуется настраивать параметры в файле `my.cnf` для сохранения настроек после перезагрузки.

```ini
[mysqld]
# Хранение логов в течение 7 дней (7 * 24 * 3600)
binlog_expire_logs_seconds = 604800
# Ротация файла при достижении 500 МБ
max_binlog_size = 500M
```

Применение настроек "на лету" (без перезагрузки):

```sql
SET GLOBAL binlog_expire_logs_seconds = 604800;
-- -> Query OK, 0 rows affected
```

### 3. Ручная очистка до определенного момента

Если необходимо срочно освободить место, используйте команду `PURGE`.

```sql
-- Удаление всех файлов, предшествующих указанному
PURGE BINARY LOGS TO 'mysql-bin.000015';
-- -> Query OK, 0 rows affected

-- Удаление логов старше 3 дней
PURGE BINARY LOGS BEFORE DATE_SUB(NOW(), INTERVAL 3 DAY);
-- -> Query OK, 0 rows affected
```

### 4. Безопасная очистка в топологии репликации

Перед выполнением `PURGE` на мастере необходимо убедиться, что реплики не используют эти логи.

```sql
-- Выполняется на Реплике (Slave)
SHOW REPLICA STATUS\G
-- -> Relay_Master_Log_File: mysql-bin.000020
```

*На мастере безопасно удалять логи только до `mysql-bin.000020` (не включая его).*

## Дополнительная информация

### Взаимосвязь с резервным копированием

Срок хранения бинарных логов (`binlog_expire_logs_seconds`) должен быть **не меньше** интервала между полными резервными копиями данных. Это необходимо для возможности восстановления системы на любой момент времени (PITR) между созданием бэкапов.

### Целостность данных

Параметр `binlog_checksum = CRC32` (включен по умолчанию в современных версиях) позволяет серверу обнаруживать повреждения записей в логах, что критично при использовании их для восстановления или репликации.
