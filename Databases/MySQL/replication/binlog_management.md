# Управление бинарными логами (binlog)

## Definitions

**Бинарный лог (Binary Log)** — журнал всех событий, изменяющих данные (DML) или структуру базы данных (DDL). Используется для репликации и восстановления данных.

**Управление binlog** — процессы мониторинга, ротации и очистки бинарных логов для предотвращения исчерпания дискового пространства.

## Basic Concepts

### Проблема размера binlog

В системах с высокой нагрузкой на запись binlog могут занимать значительно больше места, чем сама база данных.

> **Практический пример:** При объёме БД 40 ГБ и нагрузке ~1000 записей/сек, binlog за неделю могут занять 2–3 ТБ. Рекомендуется выделять под binlog минимум в 50–100 раз больше места относительно размера БД при активной записи.

### Автоматическая ротация

MySQL предоставляет два параметра для автоматической очистки старых бинарных логов:

| Параметр | Описание | Версия MySQL |
| :--- | :--- | :--- |
| `expire_logs_days` | Хранить binlog указанное количество дней | Все версии (устаревает) |
| `binlog_expire_logs_seconds` | Хранить binlog указанное количество секунд | MySQL 8.0+ (рекомендуется) |

> **Важно:** Начиная с MySQL 8.0, параметр `expire_logs_days` считается устаревшим. Рекомендуется использовать `binlog_expire_logs_seconds` для большей точности.

### Ручная очистка

Ручное удаление выполняется через команду `PURGE BINARY LOGS`. Требует осторожности — необходимо убедиться, что все slave-серверы уже применили удаляемые логи.

## Practical Scenarios

### Мониторинг размера binlog

```sql
-- Показать все binlog файлы и их размеры
SHOW BINARY LOGS;

-- Проверить текущую позицию и активный binlog
SHOW MASTER STATUS;

-- Размер всех binlog в сумме (для оценки занимаемого места)
SELECT SUM(FILE_SIZE) AS total_binlog_bytes
FROM information_schema.FILES
WHERE FILE_TYPE LIKE 'BINARY LOG%';
```

### Настройка автоматической ротации

```ini
# В конфигурационном файле (my.cnf / mysqld.cnf)
[mysqld]

# MySQL 8.0+ (рекомендуется)
binlog_expire_logs_seconds = 604800  # 7 дней

# Или устаревший способ (все версии)
expire_logs_days = 7

# Ограничение размера одного файла binlog
max_binlog_size = 100M
```

```sql
-- Изменение без перезагрузки (действует до рестарта)
SET GLOBAL binlog_expire_logs_seconds = 604800;
SET GLOBAL expire_logs_days = 7;
```

Подробная настройка параметров — в [configuration.md](../configuration.md#репликация).

### Ручная очистка binlog

```sql
-- Удалить все binlog до указанного файла (не включая)
PURGE BINARY LOGS TO 'mysql-bin.000010';

-- Удалить binlog старше указанной даты
PURGE BINARY LOGS BEFORE DATE_SUB(NOW(), INTERVAL 7 DAY);

-- Удалить binlog старше конкретного timestamp
PURGE BINARY LOGS BEFORE '2025-01-01 00:00:00';
```

### Безопасная очистка в топологии репликации

Перед очисткой убедитесь, что все slave-серверы уже применили удаляемые binlog:

```sql
-- На каждом slave проверить позицию
SHOW SLAVE STATUS\G

-- Найти поля:
--   Relay_Master_Log_File: mysql-bin.000015
--   Exec_Master_Log_Pos: 123456

-- На master удалять только логи ДО этой позиции
PURGE BINARY LOGS TO 'mysql-bin.000014';
```

> **Критично:** Если удалить binlog, который еще не применен на slave, репликация будет нарушена и потребует полной перенастройки.

### Диагностика проблем с местом

```sql
-- Проверить, сколько места занимают binlog
SHOW BINARY LOGS;

-- Проверить текущий размер активного binlog
SHOW MASTER STATUS;

-- Проверить настройки истечения логов
SHOW VARIABLES LIKE 'expire_logs%';
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
```

```bash
# На уровне ОС - проверить размер директории с binlog
du -sh /var/log/mysql/
ls -lh /var/log/mysql/mysql-bin.*
```

### Best Practices

| Задача | Решение |
| :--- | :--- |
| Предотвращение переполнения | Настроить `binlog_expire_logs_seconds` + мониторинг диска |
| Экономия места | Использовать [ROW-формат](./binlog_formats.md) + сжатие на уровне ОС |
| Быстрое восстановление | Хранить минимум 7 дней binlog + регулярные бэкапы |
| Безопасная очистка | Автоматизировать проверку позиции slave перед purge |

## Additional Information

### Влияние на производительность

- **Частая ротация:** Увеличивает нагрузку на файловую систему
- **Редкая ротация:** Требует больше дискового пространства
- **Оптимально:** 3-7 дней для продакшена с активными бэкапами

### Сжатие binlog

MySQL не поддерживает встроенное сжатие бинарных логов. Для экономии места можно использовать:

- Сжатие на уровне файловой системы (ZFS, Btrfs)
- Архивация старых логов внешними утилитами (gzip, zstd)
- Использование [ROW-формата](./binlog_formats.md) может уменьшить размер при определенных сценариях

### binlog_checksum

Параметр `binlog_checksum` добавляет контрольные суммы к событиям в binlog для обнаружения повреждений:

```ini
[mysqld]
binlog_checksum = CRC32  # Включено по умолчанию в MySQL 5.6+
```

Это не сжатие, а механизм целостности данных.

### Связь с бэкапами

Бинарные логики позволяют восстановить данные на момент времени (point-in-time recovery):

1. Восстановить последний полный бэкап
2. Применить binlog до нужного момента

Поэтому срок хранения binlog должен быть **не меньше интервала между полными бэкапами**.
