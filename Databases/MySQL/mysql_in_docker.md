## Запуск MySQL в Docker: Лучшие практики и производительность

Запуск баз данных, таких как MySQL, в контейнерах Docker — распространенная практика, которая предлагает гибкость и повторяемость окружения. Однако для эффективного использования необходимо понимать ключевые аспекты управления данными и производительности.

---

### Преимущества и недостатки

**Преимущества:**

1.  **Изоляция и повторяемость:** Гарантированный запуск одной и той же версии MySQL с одинаковой конфигурацией в любом окружении (разработка, тестирование, продакшн).
2.  **Быстрое развертывание:** Возможность поднять инстанс БД одной командой, что идеально для тестирования и CI/CD.
3.  **Параллельный запуск:** Легко запускать несколько версий или форков MySQL на одной машине, не опасаясь конфликтов.
4.  **Интеграция с экосистемой:** Легко встраивается в `docker-compose` для оркестрации всего приложения.

**Недостатки:**

1.  **Производительность:** Неправильная конфигурация, особенно сети, может привести к значительной деградации производительности.
2.  **Управление состоянием (Stateful):** Требует внимательного подхода к хранению данных, чтобы избежать их потери при удалении контейнера.

---

### Лучшие практики запуска

#### 1. Хранение данных: Использование Volumes

**Категорически запрещено** хранить данные базы данных внутри файловой системы контейнера. Для персистентности данных необходимо использовать **именованные тома (named volumes)**.

-   **Принцип:** Том монтируется в директорию, где MySQL хранит свои файлы (`/var/lib/mysql`). Данные, записанные в эту директорию внутри контейнера, на самом деле сохраняются в управляемую Docker директорию на хосте.
-   **Преимущество:** Том "переживает" удаление контейнера. Вы можете обновить образ MySQL, запустить новый контейнер и подключить к нему старый том сохранив все данные.

**Пример `docker run`:**

```bash
# 1. Создаем именованный том
docker volume create mysql-data

# 2. Запускаем контейнер, монтируя том
docker run -d --name mysql-db \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=my-secret-pw \
  -v mysql-data:/var/lib/mysql \
  mysql:8.4
```

> Подробнее о томах: **[Управление данными в Docker: Volumes](./../../Docker/docker_volumes.md)**.

#### 2. Конфигурация

Для передачи кастомной конфигурации (`my.cnf`) в контейнер используется монтирование файла или директории (`bind mount`).

```bash
# Пробрасываем свой my.cnf в контейнер
docker run -d --name mysql-db \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=my-secret-pw \
  -v mysql-data:/var/lib/mysql \
  -v ./my.cnf:/etc/mysql/conf.d/custom.cnf \
  mysql:8.4
```

#### 3. Инициализация

Официальные образы MySQL поддерживают механизм автоматической инициализации при первом запуске на пустом томе. Скрипты (`.sh`, `.sql`, `.sql.gz`), помещенные в директорию `/docker-entrypoint-initdb.d/`, будут выполнены по алфавиту.

```bash
# Запускаем контейнер, монтируя директорию со скриптами инициализации
docker run -d --name mysql-db \
  -p 3306:3306 \
  -e MYSQL_ROOT_PASSWORD=my-secret-pw \
  -v mysql-data:/var/lib/mysql \
  -v ./init-scripts:/docker-entrypoint-initdb.d \
  mysql:8.4
```

### Анализ производительности: Host vs Docker

Производительность MySQL в Docker напрямую зависит от двух факторов: **дискового I/O** и **сетевого режима**.

#### Дисковый I/O

При использовании `docker volume` для хранения данных, операции записи и чтения по сути напрямую транслируются в файловую систему хоста. Накладные расходы на этом уровне минимальны. **Основным узким местом, как и при нативной установке, остается производительность самого диска.**

#### Сетевой режим: `bridge` vs `host`

Это ключевой фактор, влияющий на производительность.

**1. Режим `bridge` (по умолчанию)**

-   **Как работает:** Docker создает виртуальный сетевой мост. Для проброса портов используется userspace-прокси `docker-proxy`, который перехватывает трафик на порту хоста и перенаправляет его в контейнер.
-   **Производительность:** Процесс `docker-proxy` потребляет значительные ресурсы CPU, особенно при большом количестве мелких и быстрых запросов.
-   **Результаты тестов (на примере `sysbench`):**
    -   На **read-only** нагрузках (точечные `SELECT`'ы), где производительность упирается в сеть и CPU, падение производительности может достигать **50% и более** по сравнению с нативной установкой. `docker-proxy` становится "бутылочным горлышком".
    -   На **read-write** нагрузках, где производительность начинает упираться в диск (синхронная запись в `binlog` и `InnoDB log`), разница сглаживается, но все равно составляет заметные **10-15%** в пользу нативной установки.

**2. Режим `host` (`--network host`)**

-   **Как работает:** Сетевая изоляция отключается. Контейнер использует сетевой стек хоста напрямую, без `docker-proxy`. Приложение в контейнере "слушает" порт непосредственно на сетевом интерфейсе хоста.
-   **Производительность:**
    -   **Практически идентична нативной установке.** Тесты показывают паритет или минимальную погрешность (в пределах 5%) как на read-only, так и на read-write нагрузках.
-   **Недостатки:**
    -   Теряется сетевая изоляция.
    -   Возможны конфликты портов, если на хосте уже что-то запущено.

> Подробнее о сетевых драйверах: **[Сетевые драйверы Docker](./../../Docker/docker_network.md)**.

### Выводы и рекомендации

1.  **Для максимальной производительности** в продакшене, если это возможно, используйте сетевой режим **`--network host`**. Это устраняет основной источник накладных расходов.

2.  Если требуется **сетевая изоляция** (режим `bridge`), будьте готовы к снижению производительности, особенно на нагрузках с высокой частотой запросов (high QPS).

3.  Всегда используйте **именованные тома (`volumes`)** для хранения данных. Это надежно и не оказывает существенного влияния на производительность дисковых операций.

4.  Для задач разработки и тестирования, где производительность не является критическим фактором, стандартный режим `bridge` является приемлемым и более удобным компромиссом.
