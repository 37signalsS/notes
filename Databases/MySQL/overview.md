## Обзор MySQL

### Механизм Master-Slave репликации

Стандартная асинхронная master-slave репликация в MySQL работает на основе бинарного лога (binary log) и включает в себя несколько ключевых компонентов и потоков.

**Схема компонентов:**

```
                                    +------------------------------------+
                                    |             Slave Server           |
                                    |                                    |
+----------------+                  |  +-------------+   +-------------+   |   +----------+
| Master Server  |                  |  |             |   |             |   |   |          |
|                | -- Binlog dump --> |  I/O Thread   |-->|  Relay Log  |--> | SQL Thread |-->| Database |
| +------------+ |                  |  |             |   |             |   |   |          |
| | Binary Log | |                  |  +-------------+   +-------------+   |   +----------+
| +------------+ |                  |                                    |
|       ^        |                  +------------------------------------+
|       |        |
| DML Commands   |
|       |        |
| +----------+   |
| | Database |   |
| +----------+   |
+----------------+

```

1.  **Запись на Master:** Любые команды изменения данных (DML: `INSERT`, `UPDATE`, `DELETE`) на master-сервере записываются в специальный файл — **бинарный лог (Binary Log)**. Этот лог содержит все события, которые изменяют данные в базе.

2.  **Подключение Slave:** Slave-сервер инициирует подключение к master-серверу. Для этого на slave-сервере запускается специальный поток — **I/O Thread**.

3.  **Запрос данных:** `I/O Thread` на slave-сервере запрашивает у master-сервера содержимое его бинарного лога, начиная с последней сохраненной позиции.

4.  **Отправка данных:** На master-сервере для каждого подключенного slave-сервера создается поток **Binlog Dump Thread**. Его задача — читать бинарный лог и отправлять его содержимое в `I/O Thread` slave-сервера.

5.  **Запись в Relay Log:** `I/O Thread` на slave-сервере, получив данные от мастера, не применяет их сразу, а записывает их в свой собственный лог — **журнал ретрансляции (Relay Log)**. Этот журнал является точной копией бинарного лога мастера. Такой подход позволяет slave-серверу получить все изменения от мастера как можно быстрее, не задерживаясь на их выполнении.

6.  **Применение данных:** На slave-сервере работает второй важный поток — **SQL Thread**. Он последовательно читает события из `Relay Log`, преобразует их в SQL-запросы и выполняет на своей копии базы данных. Именно на этом этапе происходит фактическое изменение данных на slave-сервере.

**Ключевые моменты:**

*   **Разделение потоков:** Разделение на `I/O Thread` и `SQL Thread` является важной оптимизацией. `I/O Thread` отвечает только за быструю сетевую пересылку данных, а `SQL Thread` — за их применение, которое может быть медленным. Если бы это был один поток, медленное применение запросов на slave-сервере замедлило бы и чтение данных с master-сервера, что привело бы к большому отставанию (lag).

*   **Отставание репликации (Replication Lag):** Задержка между записью на мастере и применением на слейве называется отставанием репликации. Оно может возникать из-за медленной сети (влияет на I/O Thread) или из-за высокой нагрузки и медленных запросов на слейве (влияет на SQL Thread).

### Форматы бинарного лога (binlog_format)

Ключевым аспектом репликации является то, *что именно* записывается в бинарный лог. За это отвечает параметр `binlog_format` в `my.cnf`, который имеет три основных значения.

#### 1. `STATEMENT` (Statement-Based Replication - SBR)

-   **Что пишет в лог:** Текстовое представление SQL-запросов, которые изменяют данные (`INSERT`, `UPDATE`, `DELETE`).
-   **Проблема:** Этот формат ненадежен, так как некоторые запросы являются **недетерминированными**. Например, запрос `INSERT INTO logs (ts) VALUES (NOW());` на мастере и на слейве запишет *разное* время, если будет выполнен в разное время. То же самое касается `UUID()`, `RAND()` и других подобных функций. Это приводит к рассинхронизации данных.
-   **Плюсы:** Бинарные логи занимают очень мало места.
-   **Минусы:** Небезопасно для целостности данных. В современных версиях MySQL не используется по умолчанию.

#### 2. `ROW` (Row-Based Replication - RBR)

-   **Что пишет в лог:** Не сам SQL-запрос, а бинарное представление **измененных строк**. Если `UPDATE` затронул 1000 строк, в лог будут записаны образы всех 1000 строк до и после изменения.
-   **Решение проблемы:** Этот формат является полностью детерминированным. Он не выполняет `NOW()` на слейве заново, а просто копирует строку с уже вычисленным на мастере значением. Это гарантирует побайтовое совпадение данных на мастере и слейве.
-   **Плюсы:** Максимальная надежность и консистентность данных.
-   **Минусы:** Размер бинарного лога может быть огромным. `UPDATE`, изменяющий миллион строк, сгенерирует лог размером в гигабайты, что создает нагрузку на сеть и диск.

> **Примечание:** Начиная с MySQL 5.7.7, `ROW` является форматом по умолчанию, что подчеркивает приоритет надежности над экономией места.

#### 3. `MIXED` (Mixed-Format Replication)

-   **Что пишет в лог:** Это гибридный режим, который пытается взять лучшее от двух предыдущих.
-   **Принцип работы:** По умолчанию используется `STATEMENT` как наиболее экономичный. Но MySQL анализирует каждый запрос, и если он определяет его как "небезопасный" (недетерминированный, например, содержащий `UUID()`), он автоматически переключается в режим `ROW` для этого конкретного запроса.
-   **Плюсы:** Хороший баланс между надежностью и размером логов.
-   **Минусы:** Поведение может быть не всегда предсказуемым, требует более глубокого понимания, какой запрос будет считаться "безопасным", а какой нет.

### Настройка Master-Slave репликации

#### 1. Настройка Master сервера

**Конфигурация MySQL (`my.cnf`)**

В конфигурационном файле MySQL (обычно `/etc/mysql/my.cnf` или `/etc/mysql/mysql.conf.d/mysqld.cnf`) в секции `[mysqld]` необходимо указать два ключевых параметра:

```ini
[mysqld]
# Уникальный идентификатор сервера в кластере репликации. Должен быть целым числом > 0.
server-id = 1 

# Имя файла бинарного лога. Включение этой опции активирует ведение бинарного лога.
log_bin = /var/log/mysql/mysql-bin.log
```
> **Примечание:** После изменения конфигурации необходимо перезапустить сервис MySQL.

**Создание пользователя для репликации**

В консоли MySQL на master-сервере нужно создать специального пользователя, от имени которого slave-сервер будет подключаться и запрашивать данные.

```sql
-- Создаем пользователя 'slave_user' с паролем. 
-- '%' означает, что пользователь может подключаться с любого хоста. 
-- Для безопасности лучше указать конкретный IP-адрес slave-сервера.
CREATE USER 'slave_user'@'%' IDENTIFIED BY '${REPLICATION_PASSWORD}';

-- Выдаем пользователю права на репликацию.
GRANT REPLICATION SLAVE ON *.* TO 'slave_user'@'%';

-- Применяем изменения.
FLUSH PRIVILEGES;
```

### Инициализация реплики с существующими данными

Просто включить репликацию на работающем мастере недостаточно. Бинарный лог содержит только *изменения* данных с момента его включения, но не *существующие* данные. Чтобы слейв был полной копией мастера, необходимо выполнить процесс инициализации.

**Основной принцип: "Снять дамп и запомнить позицию".**

Нужно создать полную резервную копию данных мастера (дамп) и в момент создания дампа зафиксировать точное место в бинарном логе. Затем этот дамп разворачивается на слейве, и репликация запускается именно с этой сохраненной позиции.

#### Пошаговый процесс

1.  **Подготовка Мастера:**
    -   Убедитесь, что на мастере включен `log_bin` в `my.cnf`. Если он был выключен, его нужно включить и **перезапустить** сервис MySQL.

2.  **Создание дампа и фиксация позиции на Мастере:**
    -   Используйте `mysqldump` со специальными флагами. Этот способ является предпочтительным, так как он автоматически блокирует таблицы на минимальное время и добавляет в дамп точные координаты для старта репликации.
    ```bash
    # Для таблиц InnoDB (самый частый случай)
    mysqldump -u root -p --all-databases --single-transaction --master-data=2 > master_dump.sql

    # Для таблиц MyISAM (требует полной блокировки)
    # mysqldump -u root -p --all-databases --lock-all-tables --master-data=2 > master_dump.sql
    ```
    -   Флаг `--master-data=2` (значение 2 означает, что команда будет закомментирована) добавит в начало файла `master_dump.sql` строку, похожую на эту:
        ```sql
        -- CHANGE MASTER TO MASTER_LOG_FILE='mysql-bin.000001', MASTER_LOG_POS=154;
        ```
    -   Это и есть та самая **сохраненная позиция**, с которой должен стартовать слейв.

3.  **Подготовка Слейва:**
    -   Перенесите файл `master_dump.sql` на слейв-сервер.
    -   Разверните дамп. Это приведет базу данных слейва в то же состояние, в котором был мастер на момент начала создания дампа.
    ```bash
    mysql -u root -p < master_dump.sql
    ```

4.  **Настройка и запуск Слейва:**
    -   Теперь на слейве нужно выполнить команду `CHANGE MASTER TO`, используя данные из дамп-файла.
    -   Раскомментируйте и выполните ту самую строку, которую `mysqldump` добавил в начало файла.
    ```sql
    CHANGE MASTER TO
      MASTER_HOST='ip_адрес_мастера',
      MASTER_USER='slave_user',
      MASTER_PASSWORD='пароль_пользователя_репликации',
      MASTER_LOG_FILE='mysql-bin.000001', -- Взято из дампа
      MASTER_LOG_POS=154;                 -- Взято из дампа
    ```
    -   Запустите процесс репликации:
    ```sql
    START SLAVE;
    ```
    -   Проверьте статус `SHOW SLAVE STATUS\G`. Слейв начнет запрашивать у мастера все изменения, которые произошли *после* позиции `154`, и применять их.


#### 2. Настройка Slave сервера

**Конфигурация MySQL (`my.cnf`)**

На slave-сервере также необходимо задать уникальный `server-id`.

```ini
[mysqld]
# ID должен отличаться от ID master-сервера.
server-id = 2
# (Опционально) Включает лог для отладки репликации.
relay-log = /var/log/mysql/mysql-relay-bin.log
# (Опционально) Включает бинарный лог, если slave будет мастером в цепочке.
log_bin = /var/log/mysql/mysql-bin.log
```

**Подключение к Master-серверу**

В консоли MySQL на slave-сервере выполняется команда `CHANGE MASTER TO`, которая указывает, к какому мастеру подключаться и с какими учетными данными.

```sql
-- Перед выполнением этой команды нужно получить актуальные данные с master-сервера.
-- На master-сервере выполните команду: SHOW MASTER STATUS;
-- Это покажет имя файла бинарного лога (File) и позицию (Position).

CHANGE MASTER TO
  MASTER_HOST='192.168.101.33',
  MASTER_USER='slave',
  MASTER_PASSWORD='${REPLICATION_PASSWORD}',
  MASTER_LOG_FILE='mysql-bin.xxxxxx', -- Имя файла из `SHOW MASTER STATUS`
  MASTER_LOG_POS=xxx;                 -- Позиция из `SHOW MASTER STATUS`

-- Запускаем процесс репликации
START SLAVE;

-- (Опционально) Проверить статус репликации
SHOW SLAVE STATUS\G
```
> `Slave_IO_Running` и `Slave_SQL_Running` должны быть в состоянии `Yes`.

**Пример последовательности команд на Slave**

```bash
# 1. Отредактировать конфигурационный файл, чтобы задать server-id
# vi /etc/mysql/mysql.conf.d/mysqld.cnf

# 2. Перезапустить сервис MySQL для применения изменений
root@host02:~# systemctl restart mysql.service

# 3. Подключиться к MySQL
root@host02:~# mysql

# 4. Выполнить команду для подключения к master-серверу
mysql> CHANGE MASTER TO 
         MASTER_HOST='192.168.101.33', 
         MASTER_USER='slave', 
         MASTER_PASSWORD='password', 
         MASTER_LOG_FILE='mysql-bin.000001', 
         MASTER_LOG_POS=690;

# 5. Запустить репликацию
mysql> START SLAVE;
```

### Особенности MySQL 8

- **Механизм аутентификации:** По умолчанию используется `caching_sha2_password` вместо старого `mysql_native_password`. Это требует поддержки со стороны клиентов. Если slave-сервер не может подключиться к master-серверу из-за этой особенности, есть несколько решений:

  - **1. Создать пользователя репликации со старым плагином аутентификации на master-сервере:**
    ```sql
    CREATE USER 'slave_user'@'%'
    IDENTIFIED WITH mysql_native_password BY '${REPLICATION_PASSWORD}';
    ```

  - **2. Использовать безопасную передачу пароля по RSA:**
    В команде `CHANGE MASTER TO` на slave-сервере указать опцию для запроса публичного ключа у master-сервера.
    ```sql
    CHANGE MASTER TO GET_MASTER_PUBLIC_KEY = 1;
    -- или указать путь к ключу напрямую
    -- CHANGE MASTER TO MASTER_PUBLIC_KEY_PATH = '/path/to/key.pem';
    ```

  - **3. (Менее безопасно) Глобально вернуть старый метод аутентификации на master-сервере:**
    В `my.cnf` добавить:
    ```ini
    [mysqld]
    default-authentication-plugin=mysql_native_password
    ```

- **Цепочечная репликация:** Опция `log-slave-updates` включена по умолчанию. Это означает, что slave-сервер будет записывать в свой бинарный лог изменения, полученные от master-сервера. Такое поведение необходимо для построения цепочечной репликации (Master -> Slave 1 -> Slave 2), где один slave является мастером для другого.

### Основные команды для начала работы

- **Подключение к серверу:**
  ```bash
  # Подключиться к локальному серверу от имени текущего пользователя
  mysql
  
  # Подключиться под определенным пользователем (потребуется ввод пароля)
  mysql -u <username> -p
  ```

- **Просмотр списка баз данных:**
  ```sql
  SHOW DATABASES;
  ```

- **Выбор базы данных для работы:**
  ```sql
  USE <database_name>;
  ```

- **Просмотр таблиц в текущей базе данных:**
  ```sql
  SHOW TABLES;
  ```

- **Выход из клиента:**
  ```sql
  EXIT;
  -- или
  QUIT;
  ```

### Пример конфигурационного файла

Ниже приведен пример более подробной конфигурации `my.cnf`.

```ini
[mysqld]

# -- Базовые настройки --
user                    = mysql
pid-file                = /var/run/mysqld/mysqld.pid
socket                  = /var/run/mysqld/mysqld.sock
port                    = 3306
datadir                 = /var/lib/mysql
# Адрес, на котором сервер принимает подключения. 0.0.0.0 - все доступные интерфейсы.
bind-address            = 0.0.0.0

# -- Настройки производительности --
key_buffer_size         = 16M
max_allowed_packet      = 64M
thread_stack            = 256K

# Режим восстановления таблиц MyISAM. BACKUP - создавать бекап поврежденной таблицы.
myisam-recover-options = BACKUP

# Максимальное количество одновременных подключений.
max_connections = 151

# Количество открытых таблиц, которые кэшируются. Увеличивайте, если много таблиц.
table_open_cache = 4000

# -- Логирование --

# Путь к логу ошибок.
log_error = /var/log/mysql/error.log

# Включение лога медленных запросов.
slow_query_log = 1

# Файл для лога медленных запросов.
slow_query_log_file = /var/log/mysql/mysql-slow.log

# Время в секундах, после которого запрос считается медленным.
long_query_time = 2

# Логировать запросы, которые не используют индексы.
log-queries-not-using-indexes

# -- Репликация --

# Уникальный ID сервера в топологии репликации.
server-id = 2

# Включение и указание пути к бинарному логу (обязательно для master и для slave, если он участвует в цепочке).
log_bin = /var/log/mysql/mysql-bin.log

# Время жизни бинарных логов в днях (здесь 30 дней). По истечении этого срока они будут автоматически удалены.
expire_logs_days = 30
# Для MySQL 8 рекомендуется использовать expire_logs_days вместо binlog_expire_logs_seconds
# binlog_expire_logs_seconds = 2592000 

# Максимальный размер одного файла бинарного лога.
max_binlog_size = 100M

# -- Фильтрация репликации (используйте осторожно) --

# Реплицировать только указанную базу данных.
# binlog_do_db = database_name

# Игнорировать указанную базу данных при репликации.
# binlog_ignore_db = database_name

```

### Резервное копирование (Backup)

Резервное копирование является критически важной частью администрирования MySQL. Существуют различные стратегии, каждая со своими плюсами и минусами, включая "холодные" и "горячие" бэкапы, а также логические и физические.

### phpMyAdmin: Веб-интерфейс для администрирования MySQL

**phpMyAdmin** — это бесплатный инструмент с открытым исходным кодом, написанный на PHP, предназначенный для администрирования баз данных MySQL (и MariaDB) через веб-интерфейс. Он предоставляет удобный способ управления базами данных, таблицами, полями, индексами, пользователями, разрешениями и т.д., без необходимости использования командной строки.

**Ключевые возможности:**
*   Управление базами данных и таблицами.
*   Выполнение SQL-запросов.
*   Управление пользователями и их привилегиями.
*   Импорт и экспорт данных.
*   Создание и изменение структуры таблиц.
*   Поиск по базе данных.
