# Транзакции и долговечность (durability) в MySQL

**Актуально для:** MySQL 8.4 LTS (проверено по MySQL 8.4 Reference Manual)

Транзакция в MySQL — это не «обёртка» над запросами, а объект с собственной
жизненным циклом: запись redo log, фиксация в бинарном логе, фиксация в
таблицах, освобождение блокировок. Понимание этой последовательности
объясняет большинство «необъяснимых» сценариев в продакшене: почему
`ROLLBACK` не отменяет `INSERT`, почему падение сервера «откатывает»
уже подтверждённую транзакцию, почему коммит одного клиента тормозит
тысячи других.

Общая теория ACID и уровней изоляции — в
**[ACID](../Concepts/acid.md)**; блокировки и уровни изоляции InnoDB — в
**[Блокировки и взаимоблокировки](./locking_and_deadlocks.md)**. Этот файл
описывает операционную механику MySQL: управление транзакциями, неявную
фиксацию, savepoint-ы, commit groups и параметры долговечности.

## Определения

| Термин | Значение |
| :--- | :--- |
| `autocommit` | Режим сессии (по умолчанию `1`): каждый оператор выполняется как отдельная транзакция. При `0` изменения накапливаются до явного `COMMIT`/`ROLLBACK` |
| Неявный commit (implicit commit) | Перечень операторов, которые неявно фиксируют текущую транзакцию до своего выполнения (DDL, `GRANT`, `LOCK TABLES` и др.). Транзакции в MySQL не вкладываются |
| Savepoint | Именованная точка внутри транзакции, к которой можно частично откатиться без завершения транзакции |
| Commit group | Группа транзакций, фиксируемых одним вызовом `fsync`; binlog синхронизируется «после каждых N commit groups» |
| `innodb_flush_log_at_trx_commit` | Параметр InnoDB: как часто redo log сбрасывается на диск относительно коммита транзакции (`0`/`1`/`2`) |
| `sync_binlog` | Параметр сервера: как часто бинарный лог синхронизируется с диском |
| Двухфазная фиксация (2PC) | Внутренний протокол InnoDB, обеспечивающий согласованность между redo log и бинарным логом через состояние *prepared* |
| Prepared transaction | Транзакция, прошедшая фару prepare, но ещё не зафиксированная в InnoDB; видна в `XA`/`PREPARED` состоянии |
| `binlog_error_action` | Что делать, если сервер не может записать/сбросить/синхронизировать бинарный лог: `ABORT_SERVER` (по умолчанию) или `IGNORE_ERROR` |

## Базовые концепции

### Управление транзакциями

По умолчанию `autocommit=1`, то есть каждый оператор атомарен «как если бы он
был окружён `START TRANSACTION` и `COMMIT`». Отменить его через `ROLLBACK`
нельзя; при ошибке выполнения оператор откатывается сам.

```sql
START TRANSACTION;
SELECT @A := SUM(salary) FROM table1 WHERE type = 1;
UPDATE table2 SET summary = @A WHERE type = 1;
COMMIT;
```

Ключевые особенности, важные для эксплуатации:

- **`START TRANSACTION` не меняет состояние `autocommit` сессии** — после
  `COMMIT`/`ROLLBACK` режим возвращается к прежнему.
- **Транзакции не вкладываются.** `START TRANSACTION` (и его синоним `BEGIN`)
  неявно фиксирует уже открытую транзакцию.
- **`START TRANSACTION` снимает блокировки `LOCK TABLES`**, как если бы
  выполнен был `UNLOCK TABLES`. Глобальная блокировка чтения
  (`FLUSH TABLES WITH READ LOCK`) при этом не снимается.
- **`WITH CONSISTENT SNAPSHOT`** даёт согласованное чтение только на уровне
  изоляции `REPEATABLE READ`; на остальных уровнях модификатор игнорируется с
  предупреждением.
- **`READ ONLY`** включает оптимизации InnoDB для транзакций, которые доказанно
  только читают. При включённом системном параметре `read_only` оператор
  `START TRANSACTION READ WRITE` требует привилегии `CONNECTION_ADMIN`
  (или устаревшей `SUPER`).
- **Внутри хранимых программ** (процедуры, функции, триггеры, события) парсер
  трактует `BEGIN` как начало блока `BEGIN ... END`. Для старта транзакции
  внутри такого объекта используется `START TRANSACTION`.
- **Блокировки при откате различаются по масштабу.** Полный `ROLLBACK`
  транзакции освобождает все её блокировки. Откат отдельного оператора внутри
  транзакции (например, ошибка дубликата ключа) сохраняет блокировки этого
  оператора — InnoDB хранит их в формате, не позволяющем отличить, какая
  блокировка была выставлена каким оператором.
- **В бинарный лог транзакция попадает одним куском при `COMMIT`.** Откатанные
  транзакции не логируются. Исключение: если в откатываемой транзакции были
  изменения нетранзакционных таблиц, вся транзакция логируется с
  `ROLLBACK` в конце, чтобы изменения были реплицированы.

### Неявный commit: полный перечень

Операторы ниже неявно завершают открытую транзакцию, «как если бы перед ними
выполнился `COMMIT`». Большинство из них вызывает неявный commit и **после**
выполнения — цель в том, чтобы каждый такой оператор обрабатывался в своей
собственной транзакции. Исключения — операторы управления транзакциями и
блокировками: для них неявный commit происходит только **до** выполнения.

**DDL (определение и изменение объектов):** `ALTER EVENT`, `ALTER FUNCTION`,
`ALTER PROCEDURE`, `ALTER SERVER`, `ALTER TABLE`, `ALTER TABLESPACE`,
`ALTER VIEW`, `CREATE DATABASE`, `CREATE EVENT`, `CREATE FUNCTION`,
`CREATE INDEX`, `CREATE PROCEDURE`, `CREATE ROLE`, `CREATE SERVER`,
`CREATE SPATIAL REFERENCE SYSTEM`, `CREATE TABLE`, `CREATE TABLESPACE`,
`CREATE TRIGGER`, `CREATE VIEW`, `DROP DATABASE`, `DROP EVENT`,
`DROP FUNCTION`, `DROP INDEX`, `DROP PROCEDURE`, `DROP ROLE`, `DROP SERVER`,
`DROP SPATIAL REFERENCE SYSTEM`, `DROP TABLE`, `DROP TABLESPACE`,
`DROP TRIGGER`, `DROP VIEW`, `INSTALL PLUGIN`, `RENAME TABLE`,
`TRUNCATE TABLE`, `UNINSTALL PLUGIN`.

**Операторы, работающие с таблицами схемы `mysql`:** `ALTER USER`,
`CREATE USER`, `DROP USER`, `GRANT`, `RENAME USER`, `REVOKE`, `SET PASSWORD`.

**Управление транзакциями и блокировками:** `BEGIN`, `LOCK TABLES`,
`SET autocommit = 1` (если значение не уже равно 1), `START TRANSACTION`,
`UNLOCK TABLES`. `UNLOCK TABLES` фиксирует транзакцию, только если таблицы
были заблокированы через `LOCK TABLES` для получения нетранзакционных
блокировок.

**Загрузка данных:** `LOAD DATA` — неявный commit только для таблиц NDB.

**Административные:** `ANALYZE TABLE`, `CACHE INDEX`, `CHECK TABLE`,
`FLUSH`, `LOAD INDEX INTO CACHE`, `OPTIMIZE TABLE`, `REPAIR TABLE`, `RESET`
(но не `RESET PERSIST`).

**Управление репликацией:** `START REPLICA`, `STOP REPLICA`, `RESET REPLICA`,
`CHANGE REPLICATION SOURCE TO`.

Тонкости, которые чаще всего приводят к инцидентам:

- `CREATE TABLE` и `DROP TABLE` **не** вызывают неявный commit, если
  используется ключевое слово `TEMPORARY`. Но оператор при этом всё равно не
  откатывается — то есть атомарность нарушается: если после
  `CREATE TEMPORARY TABLE` выполнить `ROLLBACK`, таблица останется.
- `CREATE TABLE ... SELECT` вызывает неявный commit **до и после** оператора
  при создании невременных таблиц.
- Неявный commit нельзя использовать внутри XA-транзакции в состоянии
  `ACTIVE`.
- Блок `BEGIN ... END` не вызывает неявный commit.

Практический вывод: DDL внутри пакетной обработки «ломает» атомарность
транзакции. Если транзакция содержит `ALTER TABLE`, весь накопленный до него
DML фиксируется до выполнения DDL, а откатить оставшееся нельзя.

### Savepoint

```sql
SAVEPOINT identifier;
ROLLBACK [WORK] TO [SAVEPOINT] identifier;
RELEASE SAVEPOINT identifier;
```

InnoDB поддерживает все три оператора. Поведение, важное для эксплуатации:

- **`ROLLBACK TO SAVEPOINT` не завершает транзакцию и не освобождает
  блокировки строк**, сохранённые в памяти после установки savepoint. Для
  только что вставленной строки информация о блокировке несётся в
  идентификаторе транзакции, записанном в строку, и освобождается через undo —
  отдельного снятия блокировки в памяти нет. Savepoint-ы, установленные позже
  указанного, удаляются.
- **Ошибка `ERROR 1305 (42000): SAVEPOINT identifier does not exist`**
  означает, что savepoint с таким именем отсутствует.
- **Все savepoint-ы текущей транзакции удаляются** при `COMMIT` или при
  `ROLLBACK`, не называющем savepoint.
- **`RELEASE SAVEPOINT` не вызывает ни commit, ни rollback**; удаление
  несуществующего savepoint — ошибка.
- **Вложенные уровни:** при вызове хранимой функции или срабатывании триггера
  создаётся новый уровень savepoint-ов. Savepoint-ы предыдущего уровня
  становятся недоступны (и потому не конфликтуют с одноимёнными на новом
  уровне); после завершения функции или триггера они освобождаются, а
  предыдущий уровень восстанавливается.

### Долговечность: что именно гарантирует каждый параметр

`innodb_flush_log_at_trx_commit` — параметр типа Enumeration, область Global,
динамический, по умолчанию `1`, допустимые значения `0`, `1`, `2`. Он
управляет балансом между строгим соответствием ACID и производительностью,
достигаемой перегруппировкой и пакетированием операций ввода-вывода при
фиксации.

- **`1`** — логи пишутся и сбрасываются на диск при каждом коммите
  транзакции. Значение по умолчанию, требуемое для полного соответствия ACID.
- **`0`** — логи пишутся и сбрасываются на диск раз в секунду. Транзакции, для
  которых логи ещё не сброшены, могут быть потеряны при сбое.
- **`2`** — логи пишутся при каждом коммите транзакции и сбрасываются на диск
  раз в секунду. Транзакции, для которых логи ещё не сброшены, могут быть
  потеряны при сбое.

Для значений `0` и `2` секундный сброс **не гарантирован на 100%**: он может
происходить чаще из-за DDL и других внутренних операций InnoDB, сбрасывающих
лог независимо от параметра, и реже — из-за особенностей планировщика. Если
логи сбрасываются раз в секунду, при сбое может быть потеряно до секунды
транзакций; если чаще или реже — соответственно меняется и окно потерь. Частоту
сброса задаёт `innodb_flush_log_at_timeout` (по умолчанию `1`, диапазон
`1 ... 2700`); при этом аварийный выход процесса `mysqld` может привести к
потере до `N` секунд транзакций.

Отдельно: **восстановление InnoDB после сбоя работает при любом значении
`innodb_flush_log_at_trx_commit`** — транзакции применяются целиком либо
стираются целиком. То есть параметр определяет именно окно потери, а не
возможность частично применённой транзакции.

`sync_binlog` — по умолчанию `1`, то есть бинарный лог синхронизируется с
диском при каждой записи. Меньшие значения синхронизируют лог «после каждых
N commit groups». Наиболее безопасное значение — `1` (по умолчанию), и оно же
самое медленное. Если `sync_binlog` не включён и упала ОС или машина (не
только процесс `mysqld`), последние записи бинарного лога могут быть потеряны.

Для схемы с InnoDB в репликации документация требует: при включённом
бинарном логировании `sync_binlog=1`, всегда `innodb_flush_log_at_trx_commit=1`.

Оговорка из документации, которую нельзя игнорировать: многие ОС и некоторые
дисковые контроллеры обманывают операцию сброса на диск — сообщают `mysqld`
об успешном сбросе, хотя он не выполнен. В этом случае долговечность не
гарантирована даже при рекомендованных настройках, а в худшем случае отключение
питания может повредить данные InnoDB. Практические меры: батарейная поддержка
кэша в контроллере или в самом диске либо отключение кэширования записи в
аппаратном кэше.

### Commit groups: почему коммит одного клиента не тормозит остальных

Записи бинарного лога не пишутся на диск по одной на каждую транзакцию:
сервер собирает фиксации в группы коммитов и синхронизирует лог «после
каждых N commit groups». Плата за batch-подход — одно `fsync` на группу
транзакций вместо одного на транзакцию.

Что из этого следует на практике:

- Чем выше параллелизм коммитов, тем выгоднее группировка: при 200 транзакциях
  в секунду и нескольких `fsync` в секунду задержка в бинлоге распределяется
  между ними.
- При одиночной последовательной нагрузке (`innodb_flush_log_at_trx_commit=1`,
  `sync_binlog=1`) каждая транзакция платит за `fsync`, и latency коммита
  определяется временем сброса на диск, а не загрузкой CPU.
- Снижение параметров ниже рекомендованных меняет не скорость, а окно
  потерь — это осознанный размен, который нельзя делать без понимания
  требований к RPO.

Внутренний механизм группировки (список сброса InnoDB и монотонность LSN) —
деталь реализации, а не документированный контракт; наблюдаемым и
документированным является поведение «синхронизация после каждых N commit
groups».

### Двухфазная фиксация между redo log и бинарным логом

Последовательность при коммите такова: InnoDB записывает подготовленные
транзакции в бинарный лог, синхронизирует его, затем фиксирует транзакцию в
InnoDB. Раньше сбой между этими шагами мог привести к расхождению: транзакция
откатывалась InnoDB при старте, но оставалась в бинарном логе. Решение —
поддержка двухфазной фиксации в XA-транзакциях, **в MySQL 8.4 она включена
всегда**.

Как это спасает при аварии (по описанию документации):

1. При старте сервер сканирует последний файл бинарного лога, собирает
   значения `xid` транзакций и вычисляет последнюю корректную позицию в логе.
2. Сервер указывает InnoDB завершить подготовленные транзакции, которые были
   успешно записаны в бинарный лог.
3. Бинарный лог усекается до последней корректной позиции.

В результате бинарный лог точно соответствует данным InnoDB, а реплика
остаётся синхронной, потому что не получает откатанный оператор.

Если при восстановлении выясняется, что бинарный лог короче, чем должен быть,
сервер печатает ошибку `The binary log file_name is shorter than its expected
size`: в нём отсутствует как минимум одна успешно зафиксированная транзакция
InnoDB. Такой лог непригоден — репликацию нужно перезапускать из свежего
снимка данных источника.

### Поведение при ошибке записи в бинарный лог

Если сервер не может записать, сбросить или синхронизировать бинарный лог,
его содержимое на источнике может стать несогласованным, и реплики могут
потерять синхронизацию с источником. За это отвечает `binlog_error_action`:

- **`ABORT_SERVER`** (по умолчанию) — остановить бинарное логирование и
  выключить сервер. Причина устраняется, затем recovery идёт как при
  аварийной остановке.
- **`IGNORE_ERROR`** — обеспечить обратную совместимость со старыми версиями:
  сервер завершает текущую транзакцию, логирует ошибку, прекращает бинарное
  логирование, но продолжает выполнять обновления. Для возобновления
  логирования нужно снова включить `log_bin`, что требует рестарта сервера.
  Применять, только если бинарный лог на этом инстансе не критичен: он не
  используется для репликации и PITR (например, только для аудита или
  отладки).

## Предварительные требования

- **MySQL 8.4 LTS** (файл основан на MySQL 8.4 Reference Manual). MySQL 8.0
  выходит из поддержки (EOL) в апреле 2026 — повышение до 8.4 безопасно для
  большинства топологий; миграционные нюансы — в
  **[Обслуживание и обновления MySQL](./maintenance-and-upgrades.md)**.
- **InnoDB** — единственный движок, где гарантии Durability действительны.
  MyISAM/MEMORY не участвуют в двухфазной фиксации и не поддерживают SAVEPOINT.
- **Бинарное логирование** (`log_bin = ON`) должно быть включено на
  источнике репликации — без него `sync_binlog` и `binlog_error_action`
  бессмысленны, а PITR невозможен.
- **Права:** на источнике — `SYSTEM_VARIABLES_ADMIN` (или устаревший `SUPER`)
  для динамических изменений параметров; на репликах — `REPLICATION CLIENT`
  для `SHOW MASTER STATUS`.
- **Оборудование:** для `innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`
  рекомендуется SSD с PLP (power-loss protection) или батарейный контроллер
  RAID; без них `fsync` может верать `0` в кэш, не дожидаясь записи на планки.
- **Тестирование изменений** — выполняйте на стенде с тем же `innodb_flush_method`
  и теми же дисками, что и production.

## Практические сценарии

### 1. Найти источник потери долговечности в конфигурации

```sql
SELECT @@GLOBAL.innodb_flush_log_at_trx_commit,
       @@GLOBAL.innodb_flush_log_at_timeout,
       @@GLOBAL.sync_binlog,
       @@GLOBAL.binlog_error_action,
       @@GLOBAL.read_only;
```

```text
# → innodb_flush_log_at_trx_commit | innodb_flush_log_at_timeout | sync_binlog | binlog_error_action | read_only
# → 1                              | 1                           | 1           | ABORT_SERVER        | 0
```

Ненулевой `read_only` на источнике меняет картину: такой инстанс сам не
принимает запись, а `START TRANSACTION READ WRITE` на нём требует
`CONNECTION_ADMIN`.

Параметры, действующие на источнике репликации, должны быть также
проверены на реплике, а не только на мастере:

```sql
-- На каждом узле: innodb_flush_log_at_trx_commit, sync_binlog
SHOW VARIABLES WHERE Variable_name IN
  ('innodb_flush_log_at_trx_commit', 'sync_binlog', 'binlog_error_action');
```

### 2. Матрица долговечности: что теряется при сбое

| `innodb_flush_log_at_trx_commit` | `sync_binlog` | Потеря при сбое ОС/питания | Потеря при сбое процесса `mysqld` | Применимость |
| :--- | :--- | :--- | :--- | :--- |
| `1` | `1` | Не теряются подтверждённые коммиты | Не теряются | Требование документации для репликации с InnoDB |
| `1` | `0` | До последних записей бинарного лога | Транзакции, чьи redo-записи уже на диске | Опасно: теряется то, что нужно для PITR и репликации |
| `2` | `1` | До одной секунды транзакций | Транзакции, чьи redo-записи уже на диске | Только для тестового стенда |
| `0` | `0` | До секунды транзакций и хвост бинарного лога | То же | Загрузка данных на новый инстанс, не для боевой базы |

Важная оговорка: параметры `innodb_flush_log_at_trx_commit=2` и `0` означают,
что **redo log** сбрасывается раз в секунду независимо от коммита. Если
подтверждённая клиенту транзакция не попала в этот сброс, она исчезает при
сбое питания — при работающем процессе `mysqld` и без всяких ошибок.

### 3. Найти и обезвредить длинную транзакцию

Длинная транзакция — источник сразу нескольких проблем: рост лага репликации,
рост `History list length` и недоступность purge (см.
**[Undo logs и purge](./undo_logs_and_purge.md)**), удержание блокировок.

```sql
SELECT trx_id,
       trx_state,
       trx_started,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_sec,
       trx_mysql_thread_id,
       trx_rows_locked,
       trx_rows_modified,
       LEFT(trx_query, 120) AS query
FROM information_schema.INNODB_TRX
ORDER BY trx_started;
```

```text
# → trx_id     | trx_state | trx_started           | age_sec | trx_mysql_thread_id | trx_rows_locked | trx_rows_modified | query
# → 1283741002 | RUNNING   | 2026-10-03 14:02:11.0 |     4210|               4821 |               0 |               0 | SELECT * FROM orders WHERE customer_id = 17
```

Отслеживание без polling — через Performance Schema:

```sql
SELECT t.PROCESSLIST_ID,
       t.PROCESSLIST_USER,
       t.PROCESSLIST_TIME,
       es.EVENT_NAME,
       es.SQL_TEXT
FROM performance_schema.threads t
LEFT JOIN performance_schema.events_statements_current es
  ON es.THREAD_ID = t.THREAD_ID
WHERE t.PROCESSLIST_ID IS NOT NULL
  AND t.PROCESSLIST_COMMAND = 'Sleep'
  AND t.PROCESSLIST_TIME > 600;
```

```text
# → PROCESSLIST_ID | PROCESSLIST_USER | PROCESSLIST_TIME | EVENT_NAME | SQL_TEXT
# →            4821 | app_writer      |             3900 | NULL       | NULL
```

Такой поток — «забытый» `SELECT` без коммита при выключенном `autocommit`.
Исправление:

```sql
KILL 4821;
```

Завершение длинной транзакции откатывает её изменения и освобождает все её
блокировки. Если это поток репликации, сначала убедитесь, что он не в
состоянии `Commit` — прерывание на поздней фазе коммита оставляет
prepared-транзакцию (см. ниже).

### 4. Частичный откат внутри транзакции

Пакетная обработка с обработкой ошибок по одной записи: savepoint позволяет
откатить только неудачную запись, не теряя весь пакет.

```sql
START TRANSACTION;

INSERT INTO orders (id, customer_id, total) VALUES (5001, 17, 199.00);
SAVEPOINT after_order;

INSERT INTO orders (id, customer_id, total) VALUES (5001, 17, 199.00); -- дубль ключа
-- → ERROR 1062 (23000): Duplicate entry '5001' for key 'orders.PRIMARY'

ROLLBACK TO SAVEPOINT after_order;  -- откат только второй вставки

INSERT INTO orders (id, customer_id, total) VALUES (5002, 17, 49.00);
COMMIT;
```

```text
# → после ROLLBACK TO SAVEPOINT: SELECT COUNT(*) FROM orders WHERE id IN (5001, 5002);
# → 1   (запись 5001 осталась, 5002 добавлена после отката дубля)
```

Что важно помнить при таком подходе:

- `ROLLBACK TO SAVEPOINT` **не освобождает** блокировки строк, взятые после
  savepoint. Пакет из миллиона строк с частыми savepoint-ами всё равно
  удерживает блокировки до `COMMIT`.
- `COMMIT` удаляет все savepoint-ы: повторный `ROLLBACK TO SAVEPOINT` после
  него вернёт `ERROR 1305`.
- Если в пакете встречается DDL, неявный commit разорвёт транзакцию вместе со
  всеми savepoint-ами — этого достаточно, чтобы потерять весь пакет.

### 5. Проверить неожиданный неявный commit

Типичный инцидент — падение приложения, которое «переписало» данные ранее,
чем весь пакет был обработан:

```sql
SELECT COUNT(*) AS rows_before FROM orders;
-- → 1000

START TRANSACTION;
UPDATE orders SET status = 'paid' WHERE id BETWEEN 1 AND 100;
ALTER TABLE orders ADD COLUMN paid_at DATETIME NULL;  -- неявный commit ДО и ПОСЛЕ
-- → ERROR 1146? нет: выполняется успешно, но транзакция уже зафиксирована

ROLLBACK;  -- откатывает только пустую транзакцию
-- → (пустой вывод — затронуто 0 строк)

SELECT COUNT(*) AS rows_after FROM orders WHERE status = 'paid';
-- → 100   (изменения зафиксировались, хотя приложение ожидало отката)
```

Вывод для эксплуатации: DDL выносить за пределы транзакции, а миграции
схемы выполнять отдельными шагами (см.
**[Онлайн-изменение схемы](./Operations/online-schema-change.md)**).

### 6. Обнаружить prepared-транзакцию после аварии

Если сервер упал между синхронизацией бинарного лога и фиксацией в InnoDB,
после старта может остаться подготовленная транзакция:

```bash
mysql -u root -p -e "SHOW ENGINE INNODB STATUS\G" | grep -A 12 "PREPARED XA"
```

```text
# → ---TRANSACTION 1283742000, ACTIVE 0 sec preparing
# → id 1283742000, os_thread_id 140289365317376, db 6, qs 0, last_query 0
# → XA transactions in prepared state: 1
```

Нормальное состояние после аварийного старта — ноль prepared-транзакций:
recovery доводит подготовленные транзакции, записанные в бинарный лог, и
усекает лог до корректной позиции. Транзакция в состоянии *preparing* в
стабильном работающем сервере — признак зависшего клиента в XA; её следует
завершать через `XA COMMIT`/`XA ROLLBACK` от того клиента, который её начал,
либо разбирать по `XA` из другого сеанса.

Согласованность данных и бинарного лога проверяется сверкой: на источнике и
реплике не должно быть расхождения ни в данных, ни в позиции.

### 7. Восстановление после потери синхронизации с бинарным логом

Ошибка `The binary log file_name is shorter than its expected size` означает,
что файл бинарного лога непригоден: в нём отсутствуют подтверждённые
транзакции. Порядок действий:

1. Не пытаться «починить» лог — он обрезан на уровне файловой системы
   синхронизации, доверять содержимому нельзя.
2. Сверить `Executed_Gtid_Set` источника и реплики (см.
   **[GTID: практические сценарии](./replication/gtid_practical.md)**).
3. Пересобрать реплику из свежего физического бэкапа (см.
   **[Резервное копирование и восстановление](./backup_and_recovery/overview.md)**),
   а не из старой копии: расхождение могло накапливаться до инцидента.
4. Устранить причину — обычно это обрыв синхронизации диска
   (контроллер кэша без батареи, виртуализация с общим хранилищем) — и только
   затем возвращать реплику в оборот.

### 8. Конфигурация долговечности для production

```ini
[mysqld]
# Гарантия ACID на источнике и на репликах
innodb_flush_log_at_trx_commit = 1
sync_binlog = 1

# По умолчанию: остановить сервер при ошибке записи бинарного лога
binlog_error_action = ABORT_SERVER

# Интервал сброса redo log, если осознанно ослабляем гарантии
# (на боевой базе не выставлять без пересмотра RPO)
# innodb_flush_log_at_timeout = 1
```

```bash
sudo -u mysql mysqld --validate-config
# → (пустой вывод при отсутствии ошибок)
```

Изменение во время работы сессии — только там, где параметр динамический:

```sql
SET GLOBAL innodb_flush_log_at_trx_commit = 1;
SET PERSIST innodb_flush_log_at_trx_commit = 1;
```

Проверка, что изменение пережило рестарт:

```sql
SELECT VARIABLE_VALUE FROM performance_schema.variables_info
WHERE VARIABLE_NAME = 'innodb_flush_log_at_trx_commit';
```

```text
# → VARIABLE_VALUE
# → 1
```

## Устранение неисправностей

| Симптом | Вероятная причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Потерянные транзакции при сбое питания | `innodb_flush_log_at_trx_commit` ∈ {0, 2} | `SELECT @@innodb_flush_log_at_trx_commit;` | Установить `1` на источнике репликации (см. сценарий 8) |
| Глобальная ошибка `ERROR 1213` (дедлок) внутри транзакции | Глобальная блокировка (GRL / `LOCK TABLES`) | `SHOW ENGINE INNODB STATUS\G` → секция `TRANSACTIONS` | Снять GRL (`FLUSH TABLES`, `UNLOCK TABLES`); дедлоки InnoDB разрешаются автоматически |
| `prepared transaction` после перезапуска | Сбой между sync binlog и commit в InnoDB | `SHOW ENGINE INNODB STATUS\G` → `PREPARED XA` | `XA COMMIT` от клиента, или `XA ROLLBACK` при потере xid |
| `ERROR 1305 (42000): SAVEPOINT ... does not exist` | Savepoint удалён предыдущим `RELEASE`/`ROLLBACK` | `SELECT * FROM information_schema.INNODB_TRX;` — savepoint-ы не видны | Проверить логику — движок не экспортирует savepoint-ы в `INNODB_TRX` |
| `ERROR 1062 (23000): Duplicate entry` в пакетной обработке | Автоинкрементный конфликт после `ROLLBACK TO SAVEPOINT` | `SELECT * FROM INFORMATION_SCHEMA.INNODB_TRX;` | `ROLLBACK TO SAVEPOINT` не освобождает автоинкремент — INSERT после него может вернуть тот же `id`; используйте `INSERT ... ON DUPLICATE KEY UPDATE` |
| `binlog_error_action = IGNORE_ERROR`, реплика отстаёт | Бинарный лог на источнике пропустил записи | `SHOW REPLICA STATUS\G` — `Last_Error`, `Seconds_Behind_Master` | Сменить на `ABORT_SERVER` (требует рестарта); пересоздать реплику из свежего бэкапа (сценарий 7) |
| «Откатанная» транзакция осталась в данных | DDL вызвал implicit commit до `ROLLBACK` | `SELECT * FROM orders WHERE status = 'paid';` после падения | Вынести DDL из транзакций; миграции — отдельными шагами (сценарий 5) |

Подробные сценарии восстановления — в сценарии 6 (prepared-транзакции
после аварии) и сценарии 7 (потеря синхронизации бинарного лога).

## Лучшие практики

- **`innodb_flush_log_at_trx_commit = 1` + `sync_binlog = 1`** — обязательный
  минимум для источника репликации. Любое ослабление (`0`/`2`) допускает
  потерю подтверждённых клиентом транзакций при сбое питания.
- **`binlog_error_action = ABORT_SERVER`** (по умолчанию в 8.4) — останавливает
  сервер при ошибке записи в binlog, предотвращая рассинхрон с репликами.
  `IGNORE_ERROR` применять только если бинарный лог не нужен для репликации и PITR.
- **`innodb_flush_log_at_timeout` не менять** от значения `1` на production.
  Увеличение до `2`+ экономит I/O за счёт batch-flush, но расширяет окно потерь.
- **Двухфазная фиксация (2PC) включена всегда в MySQL 8.4** — не пытайтесь
  отключить. Это гарантирует согласованность redo log и бинарного лога после
  аварки.
- **DDL за пределами транзакций.** `ALTER TABLE`/`CREATE TABLE ... SELECT`
  вызывают implicit commit и разрывают атомарность пакета (сценарий 5).
- **Ограничивайте длительные транзакции** (< 5–10 минут в production). Длинные
  транзакции растягивают `History list length`, блокируют purge и могут вызывать
  рост размера undo-логов (см. **[Undo logs и purge](./undo_logs_and_purge.md)**).
- **На репликах** добавляйте `read_only = 1` и `super_read_only = 1` — защита
  от случайных записей в случае ошибочного подключения приложения.
- **Диски:** используйте SSD с PLP или батарейный контроллер RAID. Без
  аппаратной защиты `fsync` может вернуть успех, не дожидаясь записи на планки.

### Очистка и откат

Изменения параметров `innodb_flush_log_at_trx_commit`, `sync_binlog` и `binlog_error_action` можно отменить без рестарта (они динамические):

```sql
-- Откат динамических изменений к исходным значениям
SET GLOBAL innodb_flush_log_at_trx_commit = 1;   -- или 2/0 для теста
SET GLOBAL sync_binlog = 1;
SET GLOBAL binlog_error_action = 'ABORT_SERVER';

-- Сделать изменения постоянными (в my.cnf):
SET PERSIST innodb_flush_log_at_trx_commit = 1;
SET PERSIST sync_binlog = 1;
```

Для проверки, что параметр пережил рестарт, используйте
`performance_schema.variables_info` (сценарий 8). Убедитесь, что
тестовые значения сброшены перед выключением сервера.

Изменение `log_bin` требует рестарта `mysqld`.
