# Внешние ключи (FOREIGN KEY) и ссылочная целостность в MySQL

**Актуально для:** MySQL 8.4 LTS (последний релиз 8.4.12, 2026-08-18; проверено по MySQL 8.4 Reference Manual)

> **Примечание по версии:** на дату правки (2026-10-10) последний релиз линейки 8.4 — 8.4.12. Следующий LTS — MySQL 9.7 (GA с апреля 2026); путь апгрейда: 8.4.x → 9.7.x, прыжки через LTS-линейку не поддерживаются.

`FOREIGN KEY` — механизм, который MySQL реализует **в движке InnoDB**, а не
в сервере. Это различие важнее, чем кажется: правила, ошибки, блокировки и
ограничения внешних ключей определяются движком таблицы, и смена движка
невозможна, пока ограничение существует.

Вопрос «использовать ли внешние ключи в продакшене» звучит на собеседованиях
почти всегда, и ответ на него следует из материала этого файла: ограничения
работают, но платят за себя на каждой вставке, на каждом DDL и при каждом
реплицировании. Ниже — что именно делает InnoDB, во что это обходится и как
с этим работают онлайн-миграции схемы.

Смежные темы: **[Индексация](./indexing.md)** — индексы на внешних ключах;
**[Блокировки и взаимоблокировки](./locking_and_deadlocks.md)** — как
контроль целостности взаимодействует с блокировками.

## Определения

| Термин | Значение |
| :--- | :--- |
| Родительская таблица (parent) | Таблица, содержащая значения, на которые ссылаются другие таблицы |
| Дочерняя таблица (child) | Таблица, в которой определено ограничение `FOREIGN KEY` |
| `REFERENTIAL ACTION` | Правило поведения при `UPDATE`/`DELETE` в родительской таблице: `RESTRICT`, `CASCADE`, `SET NULL`, `NO ACTION`, `SET DEFAULT` |
| `foreign_key_checks` | Системная переменная (Global, Session, динамическая): проверяются ли ограничения целостности |
| `innodb_native_foreign_keys` | Системная переменная (Global, не динамическая): где выполняется проверка внешнего ключа — внутри InnoDB (`ON`, по умолчанию) или на уровне SQL-сервера (`OFF`) |
| `enable_cascade_triggers` | Системная переменная (Session, динамическая, по умолчанию `OFF`, помечена на удаление): включает выполнение триггеров на дочерних строках при каскадных `CASCADE`/`SET NULL`-операциях, но только при `innodb_native_foreign_keys=OFF` |
| Self-referential FK | Ограничение, ссылающееся на ту же таблицу — иерархия сотрудников, дерево категорий |
| Shared read-only lock | Тип блокировки, который InnoDB берёт на связанные таблицы при проверке внешнего ключа |
| «Сироты» (orphans) | Строки в дочерней таблице, ссылающиеся на несуществующие строки в родительской — возможны при `foreign_key_checks=0` |

## Теоретический блок

### Синтаксис и правила именования

```sql
[CONSTRAINT [symbol]] FOREIGN KEY
    [index_name] (col_name, ...)
    REFERENCES tbl_name (col_name,...)
    [ON DELETE reference_option]
    [ON UPDATE reference_option]
```

- Значение `CONSTRAINT symbol` используется, если задано. Если `CONSTRAINT
  symbol` не определён, имя генерируется автоматически (в MySQL это
  `<table>_ibfk_N`).
- Имя `symbol` должно быть уникальным в пределах базы данных; повтор
  приводит к ошибке вида `ERROR 1005 (HY000): Can't create table 'test.fk1'
  (errno: 121)`.
- Если `CONSTRAINT symbol` не задан, движки InnoDB и NDB игнорируют
  `FOREIGN_KEY index_name`.
- Идентификаторы таблиц и колонок в клаузе `FOREIGN KEY ... REFERENCES`
  заключаются в обратные кавычки; при включённом режиме SQL `ANSI_QUOTES`
  допустимы двойные кавычки. Учитывается и настройка
  `lower_case_table_names`.

### Условия и ограничения

Внешние ключи подчиняются следующим условиям:

- **Обе таблицы должны использовать один и тот же движок, и ни одна из них не
  может быть временной таблицей.**
- Для создания ограничения требуется привилегия **`REFERENCES`** на родительскую
  таблицу.
- Соответствующие колонки должны иметь «похожие» типы данных: для типов с
  фиксированной точностью (`INTEGER`, `DECIMAL`) — одинаковые размер и знак;
  для строковых типов длина может различаться, но для небинарных
  (символьных) строк **набор символов и сравнение должны совпадать**.
- **Индексы обязательны с обеих сторон.** В ссылающейся таблице должен быть
  индекс, в котором колонки внешнего ключа перечислены первыми в том же
  порядке; если такого индекса нет, он создаётся автоматически. Такой индекс
  может быть молча удалён позже, если появится другой индекс, пригодный для
  контроля ограничения.
- Ссылка на **неуникальный** индекс или частичный индекс ранее была
  расширением InnoDB. Она и сейчас допускается для обратной совместимости, но
  **устарела** и требует явного включения переменной
  **`restrict_fk_on_non_standard_key`**; в referenced-таблице при этом всё
  равно должен быть индекс, где referenced-колонки идут первыми в том же
  порядке. Поддержка нестандартных ключей планируется к удалению — миграция с
  них обязательна.
- **Префиксы индексов на колонках внешнего ключа не поддерживаются.**
  Следствие: колонки `BLOB` и `TEXT` **нельзя** включить во внешний ключ,
  поскольку индексы по ним всегда требуют длину префикса.
- **InnoDB не поддерживает внешние ключи для таблиц с определённым
  пользователем секционированием** — это касается и родительской, и дочерней
  таблицы. Исключение: таблицы NDB, секционированные по `KEY` или `LINEAR KEY`
  (единственные типы секционирования, поддерживаемые NDB).
- Таблицу, участвующую в отношениях с внешним ключом, **нельзя перевести на
  другой движок**: сначала нужно удалить ограничения.
- Внешний ключ **не может ссылаться на виртуальную генерируемую колонку**.
- Ссылка на колонку внутри той же таблицы поддерживается (self-referential),
  но колонка не может ссылаться сама на себя.

Практический вывод: FK и partitioning несовместимы в InnoDB. Если таблица
секционирована по дате (типичный сценарий), внешние ключи на ней создать нельзя
— это само по себе часто решает спор «FK или партиционирование».

### Referential actions

| Действие | Поведение |
| :--- | :--- |
| `CASCADE` | При `DELETE`/`UPDATE` родителя автоматически удаляется/обновляется соответствующая строка в дочерней таблице. Поддерживаются и `ON DELETE CASCADE`, и `ON UPDATE CASCADE`. **Каскадные действия не активируют триггеры** |
| `SET NULL` | В дочерней таблице значения внешнего ключа устанавливаются в `NULL`. Колонки при этом не должны быть объявлены `NOT NULL` |
| `RESTRICT` | Операция отклоняется. Для InnoDB эквивалентен `NO ACTION` и отсутствующему `ON DELETE`/`ON UPDATE` |
| `NO ACTION` | Стандарт SQL. Для InnoDB эквивалентен `RESTRICT`; `DELETE`/`UPDATE` родителя отклоняется немедленно, если в referenced-таблице есть связанные значения. NDB поддерживает отложенную проверку |
| `SET DEFAULT` | Распознаётся парсером MySQL, но **InnoDB и NDB отклоняют** определения таблиц с `ON DELETE SET DEFAULT` или `ON UPDATE SET DEFAULT` |

Дополнительные ограничения:

- Между двумя таблицами не следует определять несколько `ON UPDATE CASCADE`,
  действующих на одну и ту же колонку.
- Если клауз `FOREIGN KEY` определён с обеих сторон отношения (таблицы
  одновременно родитель и дочерняя), то `ON UPDATE CASCADE` или
  `ON DELETE CASCADE`, заданные для одного клауза, должны быть заданы и для
  другого — иначе каскадные операции завершатся ошибкой.
- InnoDB выполняет каскадные операции обходом в глубину (depth-first) по
  записям индекса, соответствующего ограничению.
- Ограничение на хранимую генерируемую колонку не может использовать
  `CASCADE`, `SET NULL` или `SET DEFAULT` как `ON UPDATE`, и `SET NULL` или
  `SET DEFAULT` как `ON DELETE`. Для базовой колонки хранимой генерируемой
  колонки запрещены `CASCADE`, `SET NULL` и `SET DEFAULT` в обоих случаях.

Практический вывод: `SET DEFAULT` — ловушка. Синтаксис проходит через
парсер, ошибка возникает на `CREATE TABLE`/`ALTER TABLE`, а не на записи.

### Каскадные триггеры и `enable_cascade_triggers`

По умолчанию каскадные действия InnoDB **не активируют триггеры** на дочерней
таблице. Это поведение можно изменить, но оно связано с двумя важными
деталями:

- Переменная **`innodb_native_foreign_keys`** (по умолчанию `ON`) определяет,
  где выполняется проверка внешнего ключа: внутри InnoDB (нативно) или на
  уровне SQL-сервера. При `innodb_native_foreign_keys=ON` каскады обрабатываются
  движком, и триггеры на дочерних строках не срабатывают ни при каких
  настройках.
- Переменная **`enable_cascade_triggers`** (Session, динамическая, по
  умолчанию `OFF`) включает выполнение триггеров на дочерних строках при
  каскадных `CASCADE`/`SET NULL`-операциях, но **только когда
  `innodb_native_foreign_keys=OFF`**. При `innodb_native_foreign_keys=ON`
  присвоение `enable_cascade_triggers=ON` генерирует предупреждение и не
  влияет на поведение. При включении/выключении этой переменной всегда
  выводится предупреждение о её устаревшем статусе — она помечена на
  удаление в будущих релизах.

Когда `enable_cascade_triggers=ON` и триггеры срабатывают:

- `ON DELETE CASCADE` активирует `BEFORE DELETE` → удаление → `AFTER DELETE`.
- `ON UPDATE CASCADE`, `ON UPDATE SET NULL`, `ON DELETE SET NULL` активируют
  `BEFORE UPDATE` → обновление → `AFTER UPDATE`.
- Множественные триггеры одного события и времени выполняются в порядке их
  создания (или с помощью `trigger_order` `FOLLOWS`/`PRECEDES`).
- При мультиуровневом каскаде `BEFORE`-триггеры идут от родителя к потомкам,
  `AFTER` — в обратном порядке, от самого глубокого потомка к родителю.
- Если какой-либо триггер поднимает ошибку, вся операция (включая все уровни
  каскада) откатывается.
- `INSERT ... ON DUPLICATE KEY UPDATE`, вызывающий `ON UPDATE`-действие,
  активирует `UPDATE`-триггеры на затронутых дочерних строках. `REPLACE`,
  удаляющий родительскую строку, активирует `DELETE`-триггеры для дочерних
  строк, удалённых `ON DELETE CASCADE`; последующая вставка родительской строки
  не восстанавливает удалённые дочерние строки.

Практический вывод: в продакшене, где триггеры используются для аудита,
имейте в виду — каскадное удаление/обновление **не** запускает триггеры
по умолчанию. Проверяйте логи аудита на пропуски.

### Глубина каскада и пределы

InnoDB выполняет каскадные операции обходом в глубину (depth-first) по
записям индекса, соответствующего ограничению. Ограничения:

- Каскад может охватывать не более **15 уровней**. Превышение приводит к
  ошибке `ER_FK_DEPTH_EXCEEDED` — операция завершается неудачей, и все
  изменения, сделанные оператором, откатываются.
- При включённых триггерах (`enable_cascade_triggers=ON`) одна инструкция может
  создать несколько независимых цепочек каскада; collectively в них может
  участвовать не более **30 таблиц**. При превышении инструкция терпит
  неудачу и откатывает все изменения.
- Циклические ссылки внешних ключей: если сервер обнаруживает повторение
  той же связи, он прекращает следовать по ней; триггеры срабатывают по одному
  разу для каждой участвующей таблицы. Триггер, []). If the trigger attempts to re-enter the active cascade path, it causes an error.

Влияние на вывод метаданных: явный `ON DELETE NO ACTION` или
`ON UPDATE NO ACTION` не отображается в выводе `SHOW CREATE TABLE` и в дампах
`mysqldump`; эквивалентное нестандартное ключевое слово `RESTRICT`
отображается.

### Блокировки: плата за проверку целостности

MySQL расширяет metadata locks на все таблицы, связанные ограничением: это
предотвращает параллельные конфликтующие DML и DDL на связанных таблицах и
позволяет безопасно обновлять метаданные внешнего ключа при изменении
родительской таблицы. Это одно из немногих мест, где FK затрагивает сразу
блокировки метаданных (MDL) — механизм, который сам по себе является
отдельным источником инцидентов.

Дополнительно:

- Если таблица явно заблокирована через `LOCK TABLES`, все связанные внешним
  ключом таблицы открываются и блокируются неявно. **Для проверки внешнего
  ключа на связанных таблицах берётся разделяемая блокировка только на чтение
  (`LOCK TABLES READ`).** Для каскадных обновлений берётся разделяемое
  «бездействующее» блокирование записи (`LOCK TABLES WRITE`) на участвующих
  таблицах.

Отсюда следует механизм, из-за которого FK не любят в OLTP: вставка в
дочернюю таблицу требует доступа к родительской строке, то есть блокировки
родителя. При конкуренции за одну и ту же родительскую строку (заказ одного
клиента, дебет одного счёта) транзакции выстраиваются в очередь — там, где
без FK ограничение существовало бы только логическое, на уровне приложения.

### Проверки целостности и `foreign_key_checks`

`foreign_key_checks` включена по умолчанию. Переменная динамическая, имеет
области Global и Session; для NDB действует так же, как для InnoDB.

Когда проверку отключают:

- при удалении таблицы, на которую ссылается ограничение (пока проверка
  включена, такую таблицу удалить нельзя; при удалении таблицы её ограничения
  также удаляются);
- при загрузке таблиц в порядке, отличном от требуемого отношениями FK.
  `mysqldump` выдаёт корректные определения таблиц вместе с ограничениями
  для дочерних таблиц, и для упрощения перезагрузки **автоматически включает в
  дамп оператор отключения проверки внешних ключей** — это позволяет импортировать
  таблицы в любом порядке. Отключение проверки также ускоряет импорт;
- при операциях `LOAD DATA` — чтобы не проверять ограничения;
- при `ALTER TABLE` над таблицей, участвующей в отношениях с внешним ключом.

Что **не** делает отключение проверки:

- **Оно не запускает проверку при обратном включении.** Включение
  `foreign_key_checks` не вызывает сканирование данных таблицы: строки,
  добавленные при выключенной проверке, не проверяются на согласованность
  после её включения.
- Оно не позволяет создать ограничение, ссылающееся на несовпадающий тип
  колонки: `ALTER TABLE` вернёт ошибку `errno: 150`.
- Оно не позволяет удалить индекс, необходимый ограничению: сначала нужно
  удалить само ограничение.
- Оно не позволяет пересоздать ранее удалённую таблицу с некорректным
  определением: вернётся ошибка `1005` со ссылкой на `errno: 150`.

Дополнительные эффекты отключения: разрешается удалять базу, в которой есть
таблицы с внешними ключами, ссылающимися на таблицы вне этой базы, и таблицу с
внешними ключами, на которые ссылаются другие таблицы.

Отсюда правило эксплуатации: `SET foreign_key_checks=0` — это не «выключить
проверку», а «согласиться, что целостность теперь на вашей совести». Перед
повторным включением нужно искать «сирот» самостоятельно (сценарий 4).

### Диагностика ошибок внешнего ключа

При ошибке с InnoDB-таблицами (обычно `Error 150`) подробности последней
ошибки доступны в `SHOW ENGINE INNODB STATUS` — секция
`LATEST FOREIGN KEY ERROR` показывает транзакцию, индекс дочерней таблицы и
ближайшее совпадение в родительской.

Ошибки `ER_NO_REFERENCED_ROW_2` и `ER_ROW_IS_REFERENCED_2` раскрывают
информацию о родительских таблицах только если у пользователя есть табличные
привилегии на все родительские таблицы; иначе выводятся более обобщённые
`ER_NO_REFERENCED_ROW` и `ER_ROW_IS_REFERENCED`. Исключение: для хранимых
программ, исполняемых с привилегиями `DEFINER`, права оцениваются по
пользователю из клаузы `DEFINER`, а не по вызывающему — поэтому информация о
родительских таблицах снова может быть раскрыта.

### Мониторинг внешних ключей

Внешние ключи не имеют отдельного набора системных переменных, но их
поведение можно отслеживать косвенно:

- **`SHOW ENGINE INNODB STATUS`** — секции `LATEST FOREIGN KEY ERROR`
  (последняя ошибка) и `SEMAPHORES`/`TRANSACTIONS` (блокировки, связанные с
  проверкой FK). Подробнее о включении периодической записи в error log — в
  **[Мониторинг MySQL](./monitoring.md)** (`innodb_status_output`,
  `innodb_status_output_locks`).
- **`INFORMATION_SCHEMA.INNODB_FOREIGN` и `INNODB_FOREIGN_COLS`** — полный
  реестр ограничений с идентификаторами, родительскими/дочерними таблицами и
  колонками (см. сценарий 1). Подходит для автоматической инвентаризации и
  построения карты зависимостей схемы.
- **`INFORMATION_SCHEMA.INNODB_METRICS`** — счётчики движка InnoDB. Счётчики,
  связанные с внешними ключами, включаются через `SET GLOBAL
  innodb_monitor_enable = '<counter>'`. Набор модулей: `module_dml`
  (DML-операции, включая `dml_inserts`/`dml_deletes`/`dml_updates`), `module_lock`
  (блокировки), `module_metadata` (метаданные). Отдельного `module_foreign_key`
  не существует — FK-активность отражается в общих счётчиках DML и блокировок.
- **Системные переменные:** `foreign_key_checks` (Global/Session, динамическая)
  — текущее состояние проверки; `innodb_native_foreign_keys` (Global, не
  динамическая) — где выполняется проверка (InnoDB или SQL-сервер);
  `enable_cascade_triggers` (Session, динамическая) — триггеры при каскадах.
- **Счётчики сервера:** `Innodb_rows_deleted` — при SQL-слойном `DELETE CASCADE`
  увеличивается для каждой попытки рекурсивного удаления; если каскад
  превысил максимальную глубину и завершился ошибкой `ER_FK_DEPTH_EXCEEDED`,
  эти счётчики не откатываются. При нативной обработке InnoDB счётчик не
  увеличивается при этой ошибке.

Практический вывод: прямого алерта «FK-проверка отключена» нет. Контролируйте
`foreign_key_checks` вручную и проверяйте отсутствие сирот перед каждым
включением (сценарий 4).

### Ограничения при онлайн-изменении схемы

- **Добавление и удаление внешнего ключа в одном `ALTER TABLE` поддерживается
  для `ALTER TABLE ... ALGORITHM=INPLACE` и не поддерживается для
  `ALTER TABLE ... ALGORITHM=COPY`.** Это утверждение из документации;
  полная матрица поддержки (какой алгоритм и какая блокировка допустимы для
  каждой операции) приведена в официальной таблице «ALTER TABLE and Online
  DDL» — ссылка в разделе «Дополнительная информация».
- **`gh-ost` не поддерживает внешние ключи**: инструмент не работает с
  ограничениями FK, и это ограничение зафиксировано в его документации.
  Практическое следствие: таблицу с FK нельзя перевести на новую схему через
  `gh-ost` — нужен `pt-online-schema-change` либо онлайн-`ALTER` силами самого
  MySQL.
- `pt-online-schema-change` создаёт теневую таблицу и синхронизирует изменения
  через триггеры; ограничения FK при таком подходе требуют отдельной проверки
  на конкретной версии инструмента — официальная документация Percona Toolkit
  требует наличия первичного или уникального ключа (транзакции так или иначе
  не смогут удалять строки) и не описывает перенос FK как поддерживаемый сценарий.

Вывод для практики: **внешние ключи — аргумент против `gh-ost` в проекте,
где FK есть**. Выбор инструмента миграции определяется наличием ограничений,
а не только размером таблицы.

## Практический блок

### 1. Инвентаризация внешних ключей в базе

```sql
SELECT CONSTRAINT_NAME,
       TABLE_SCHEMA,
       TABLE_NAME,
       COLUMN_NAME,
       REFERENCED_TABLE_SCHEMA,
       REFERENCED_TABLE_NAME,
       REFERENCED_COLUMN_NAME
FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
WHERE REFERENCED_TABLE_SCHEMA IS NOT NULL
  AND TABLE_SCHEMA = 'shop'
ORDER BY TABLE_NAME, CONSTRAINT_NAME;
```

```text
# → CONSTRAINT_NAME | TABLE_SCHEMA | TABLE_NAME | COLUMN_NAME | REFERENCED_TABLE_SCHEMA | REFERENCED_TABLE_NAME | REFERENCED_COLUMN_NAME
# → orders_ibfk_1  | shop         | orders     | customer_id | shop                  | customers            | id
```

Детали именно для InnoDB:

```sql
SELECT ID, FOR_NAME, REF_NAME, N_COLS
FROM INFORMATION_SCHEMA.INNODB_FOREIGN;

SELECT ID, FOR_COL_NAME, REF_COL_NAME, POS
FROM INFORMATION_SCHEMA.INNODB_FOREIGN_COLS;
```

```text
# → ID               | FOR_NAME       | REF_NAME      | N_COLS
# → shop/orders_ibfk_1 | shop/orders  | shop/customers |      1
```

```text
# → ID               | FOR_COL_NAME | REF_COL_NAME | POS
# → shop/orders_ibfk_1 | customer_id | id            |   0
```

Проверка, что родительская колонка проиндексирована (иначе проверка каждой
вставки идёт через скан):

```sql
SELECT TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX, COLUMN_NAME
FROM INFORMATION_SCHEMA.STATISTICS
WHERE TABLE_SCHEMA = 'shop'
  AND TABLE_NAME IN ('customers', 'orders')
ORDER BY TABLE_NAME, INDEX_NAME, SEQ_IN_INDEX;
```

```text
# → TABLE_NAME | INDEX_NAME      | SEQ_IN_INDEX | COLUMN_NAME
# → customers  | PRIMARY         |            1 | id
# → orders     | orders_ibfk_1   |            1 | customer_id
```

### 2. Создание внешнего ключа на работающей системе

```sql
-- Родительский индекс должен существовать заранее
ALTER TABLE orders ADD INDEX idx_customer_id (customer_id);

-- Ограничение с явным именем: имя важно для последующего DROP
ALTER TABLE orders
  ADD CONSTRAINT fk_orders_customer
  FOREIGN KEY (customer_id) REFERENCES customers (id)
  ON DELETE RESTRICT;
```

```text
# → Query OK, 0 rows affected (0.42 sec)
```

Если ограничение создаётся в одном `ALTER TABLE` вместе с удалением другого
ограничения, официально поддерживается только `ALGORITHM=INPLACE`; вариант
`ALGORITHM=COPY` для такой комбинации не поддерживается. Как проверить, какой
алгоритм доступен для конкретного изменения — в
**[Онлайн-изменение схемы](./Operations/online-schema-change.md)** (сценарий
«определить, какой алгоритм доступен»).

Удаление:

```sql
-- Имя ограничения: SHOW CREATE TABLE, если задано неявное
ALTER TABLE orders DROP FOREIGN KEY fk_orders_customer;
```

### 3. Оценить стоимость ограничения до внедрения

Быстрая проверка, что FK действительно создаётся с блокировкой родителя:
одновременные сессии, вставляющие в дочернюю таблицу, должны блокироваться на
одной и той же родительской строке.

```sql
-- Сессия 1
START TRANSACTION;
INSERT INTO orders (id, customer_id, total) VALUES (9001, 17, 10.00);

-- Сессия 2 (в другой сессии) — вставка в тот же customer_id
START TRANSACTION;
INSERT INTO orders (id, customer_id, total) VALUES (9002, 17, 20.00);
-- → выполнение не завершается: ожидание блокировки

-- Сессия 1
COMMIT;

-- Сессия 2 — вставка завершается
COMMIT;
```

Наблюдаемое поведение — ожидание именно в момент фиксации второй транзакции —
и есть та плата, о которой идёт речь в разделе про блокировки. На
высококонкурентной записи одного клиента (одна корзина, один счёт) эти
очереди становятся источником лага.

### 4. Найти «сирот» перед повторным включением проверки

Включение `foreign_key_checks` не сканирует данные, поэтому «сироты»,
появившиеся при выключенной проверке, сохраняются молча. Их нужно искать
явно:

```sql
SELECT c.id, c.customer_id
FROM orders c
LEFT JOIN customers p ON p.id = c.customer_id
WHERE p.id IS NULL;
```

```text
# → id  | customer_id
# → 9003|        999
```

В общем виде по конкретному ограничению:

```sql
SELECT COUNT(*) AS orphans
FROM orders c
LEFT JOIN customers p ON p.id = c.customer_id
WHERE c.customer_id IS NOT NULL
  AND p.id IS NULL;
```

```text
# → orphans
# → 1
```

Порядок действий при найденных сиротах:

1. Восстановить недостающие родительские записи из бэкапа или создать
   заглушки — в зависимости от того, потеряны они или вставлены ошибочно.
2. Удалить строки-сироты, если они невалидны.
3. Убедиться, что других ограничений на этих таблицах нет проблем, затем
   вернуть `SET SESSION foreign_key_checks = 1`.
4. Доказать целостность сверкой с репликой (`pt-table-checksum`, см.
   **[Проверка согласованности репликации](./replication/consistency_checks.md)**).

### 5. Понять, почему ограничение не создалось

Типичные сообщения и причины:

```bash
mysql -u root -p -e "SHOW ENGINE INNODB STATUS\G" | grep -A 12 "LATEST FOREIGN KEY ERROR"
```

```text
# → LATEST FOREIGN KEY ERROR
# → 2026-10-03 15:02:11 Transaction:
# → TRANSACTION 7717, ACTIVE 0 sec inserting
# → Foreign key constraint fails for table `shop`.`orders`:
# → , CONSTRAINT `orders_ibfk_1` FOREIGN KEY (`customer_id`)
# →   REFERENCES `shop`.`customers` (`id`)
# → Trying to add in child table, in index par_ind tuple: ...
# → But in parent table `shop`.`customers`, in index PRIMARY,
# → the closest match we can find is record: ...
```

- `errno: 150` при `CREATE TABLE`/`ALTER TABLE` — условие не выполнено:
  родительская колонка не проиндексирована, типы не совпадают (разная длина
  `VARCHAR`, разный набор символов или сравнение), таблица секционирована,
  движки разные, либо включена попытка ссылаться на виртуальную колонку.
- `errno: 150` при вставке данных — нарушена ссылочная целостность: значения
  внешнего ключа нет в родительской таблице. Детали — в секции
  `LATEST FOREIGN KEY ERROR`.
- Ошибка про `BLOB`/`TEXT` в определении ограничения — для этих типов нужны
  индексы с префиксом, а префиксы индексов на колонках внешних ключей не
  поддерживаются.

### 6. Обходной путь для миграции большой таблицы с FK

```sql
-- Шаг 1. Проверить наличие ограничений до планирования миграции
SELECT COUNT(*) AS fk_count
FROM INFORMATION_SCHEMA.TABLE_CONSTRAINTS
WHERE CONSTRAINT_TYPE = 'FOREIGN KEY'
  AND TABLE_SCHEMA = 'shop'
  AND TABLE_NAME = 'orders';
# → fk_count
# → 2

-- Шаг 2. Временно снять ограничения на время массовой операции
SET FOREIGN_KEY_CHECKS = 0;
-- ... массовая операция ...
SET FOREIGN_KEY_CHECKS = 1;

-- Шаг 3. Обязательно найти сироты (см. сценарий 4) — включение
--         FOREIGN_KEY_CHECKS этого не делает
```

Каждая такая операция на продакшене требует обоснования: окно, в котором
целостность не проверяется, должно быть минимальным, а после него обязателен
поиск сирот. Если ограничения можно сохранить — сохраняйте их.

### 7. Проверить, не мешает ли FK онлайн-миграции

```bash
# Есть ли ограничения FK на таблице — от этого зависит выбор инструмента
mysql -u root -p -e "
  SELECT CONSTRAINT_NAME, REFERENCED_TABLE_NAME
  FROM INFORMATION_SCHEMA.KEY_COLUMN_USAGE
  WHERE TABLE_SCHEMA = 'shop' AND TABLE_NAME = 'orders'
    AND REFERENCED_TABLE_NAME IS NOT NULL;"
```

```text
# → CONSTRAINT_NAME | REFERENCED_TABLE_NAME
# → fk_orders_customer | customers
```

Если ограничения найдены, `gh-ost` для этой таблицы неприменим, и план
миграции должен строиться на `pt-online-schema-change` либо на онлайн-`ALTER`
(`ALGORITHM=INPLACE`), см.
**[Онлайн-изменение схемы](./Operations/online-schema-change.md)**.

## Лучшие практики

1. **Давайте имена ограничениям.** Имя `CONSTRAINT symbol` делает `DROP`
   предсказуемым и не требует поиска сгенерированного `orders_ibfk_N`. Имя
   уникально в пределах базы данных.
2. **Создавайте индекс на родительской колонке до добавления FK.** InnoDB
   создаёт индекс автоматически, но явное создание даёт понятное имя и
   контролируемый план.
3. **Выбирайте `RESTRICT` по умолчанию.** `ON DELETE RESTRICT` (или просто
   отсутствие клаузы, что эквивалентно `NO ACTION`) предотвращает случайное
   каскадное удаление. `CASCADE` — осознанное решение: оно не активирует
   триггеры по умолчанию, и это нужно проверять отдельно.
4. **Не используйте `SET DEFAULT`** — парсер принимает, InnoDB и NDB отклоняют
   определение таблицы.
5. **Согласуйте типы, наборы символов и сравнение.** Разная длина `VARCHAR`,
   разный `CHARSET` или `COLLATE` дают `errno: 150`.
6. **Не включайте `BLOB`/`TEXT` во внешний ключ** — префиксы индексов не
   поддерживаются.
7. **Планируйте миграции с учётом FK.** `gh-ost` не работает с внешними ключами;
   выбирайте `pt-online-schema-change` или онлайн-`ALTER`.
8. **При `SET foreign_key_checks=0` ищите сироты самостоятельно.** Включение
   проверки не сканирует данные. Используйте запрос из сценария 4.
9. **Тестируйте блокировки на высококонкурентных таблицах.** Вставка в
   дочернюю таблицу блокирует родительскую строку; если приложение часто
   пишет в одну и ту же родительскую запись, FK добавит лаг (сценарий 3).
10. **Проверяйте аудит-логи на пропуски.** Каскадные действия не активируют
    триггеры по умолчанию; если триггеры нужны — включайте
    `enable_cascade_triggers` осознанно и учитывайте, что он устаревает.

## Очистка и откат

- **Удаление ограничения:** `ALTER TABLE <child> DROP FOREIGN KEY <symbol>`.
  Имя ограничения — из `SHOW CREATE TABLE` или из `INFORMATION_SCHEMA`.
- **Откат миграции с отключённой проверкой:** если после операции обнаружены
  сироты, их нужно удалить или восстановить родительские записи из бэкапа
  (сценарий 4). Проверка согласованности с репликой через
  `pt-table-checksum` — в **[Проверка согласованности репликации](./replication/consistency_checks.md)**.
- **Удаление таблицы:** при включённой проверке удалить родительскую таблицу
  нельзя, пока на неё ссылаются внешние ключи. Сначала удалите ограничения в
  дочерних таблицах, либо отключите `foreign_key_checks=0`.
- **Смена движка таблицы:** возможна только после удаления всех внешних ключей,
  участвующих в отношениях с этой таблицей.
