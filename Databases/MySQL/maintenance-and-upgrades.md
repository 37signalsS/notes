# Обслуживание и обновления MySQL

**Актуально для:** MySQL 5.7 / 8.0 / 8.4 LTS

Обслуживание (maintenance) и обновления (upgrades) — две непрерывные фазы жизненного цикла эксплуатируемой СУБД. Обслуживание направлено на поддержание производительности, целостности и эффективного использования ресурсов (диск, память, CPU) на уже работающем инстансе. Обновления направлены на переход между версиями сервера для получения исправлений безопасности, новых возможностей и поддержки со стороны вендора. Обе фазы критичны для SRE-практики: невыполненное обслуживание ведёт к деградации производительности и раздуванию хранилища, а неконтролируемое обновление — к простою или повреждению данных.

## Определения

**OPTIMIZE TABLE** — команда для дефрагментации таблиц и индексов. Для движка InnoDB она сопоставляется с `ALTER TABLE ... FORCE` и пересоздаёт таблицу «с нуля», освобождая неиспользуемое пространство и обновляя статистику оптимизатора запросов (кардинальность индексов).

**ANALYZE TABLE** — команда обновления статистики таблицы (кардинальности индексов), используемой оптимизатором запросов для построения планов выполнения. Для InnoDB выполняет выборочное чтение (sampling) страниц индекса и не блокирует чтение/запись надолго.

**CHECK TABLE** — команда проверки логической и физической целостности структуры таблицы и индексов. Для InnoDB проверяет B-деревья индексов и связи; для MyISAM способна не только находить, но и исправлять повреждения.

**mysqlcheck** — консольная утилита командной строки, являющаяся обёрткой над `CHECK TABLE` / `REPAIR TABLE` / `ANALYZE TABLE` / `OPTIMIZE TABLE`. Позволяет обслуживать таблицы по имени базы/таблицы без прямого входа в SQL-клиент, а также пакетно обрабатывать все таблицы сервера.

**Фрагментация таблицы (Table Fragmentation / Fragmented Space)** — состояние, при котором физический объём файла таблицы превышает объём реально хранимых данных из-за «дыр» в страницах (pages) после массовых `DELETE` и `UPDATE`. Косвенно диагностируется по значению `Data_free` в выводе `SHOW TABLE STATUS`.

**InnoDB** — транзакционный Storage Engine (движок хранения) по умолчанию в MySQL 8.x. Использует кластерный индекс (данные лежат в первичном ключе B-дерева), журнал отката (undo log), буферный пул (buffer pool) и табличные пространства (tablespaces). Архитектура хранения InnoDB определяет поведение всех операций обслуживания.

**MySQL Shell (`mysqlsh`)** — продвинутый интерактивный клиент, поддерживающий выполнение команд на JavaScript, Python и SQL. Является стандартом для управления современными инстансами MySQL (8.0+), включая утилиты `util.checkForServerUpgrade()` и `util.dumpInstance()`.

**In-place Upgrade (Обновление на месте)** — метод обновления СУБД путём замены бинарных файлов сервера и выполнения процедур обновления на существующих файлах данных без их перемещения. Сохраняет пути хранения, права доступа и конфигурацию; применяется при переходе между совместимыми версиями (в т.ч. мажорными в рамках поддерживаемых путей).

**Logical Upgrade (Логическое обновление)** — метод обновления через полное логическое копирование данных: дамп (dump) исходной базы средствами `mysqldump` / MySQL Shell `/ util.dumpInstance()`, установку нового сервера и восстановление дампа. Не зависит от формата файлов данных, поэтому применим в ситуациях, когда In-place невозможен (смена ОС, архитектуры CPU, значительный разрыв версий).

**Patch / Minor Upgrade (Патч- или минорное обновление)** — переход внутри одной ветки (например, 8.4.0 → 8.4.3). Содержит исправления ошибок и уязвимостей без изменения формата данных; выполняется быстро и с минимальными рисками.

**Major Upgrade (Мажорное обновление)** — переход между ветками (например, 8.0 → 8.4 LTS). Требует тщательной проверки совместимости схем, функций, зарезервированных слов и параметров конфигурации, поскольку могут меняться формат системных таблиц, поведение оптимизатора и удаляться устаревшие возможности.

**Maintenance Window (Окно обслуживания)** — заранее запланированный интервал времени низкой нагрузки, в течение которого выполняются операции с потенциальным влиянием на доступность или производительность: `OPTIMIZE TABLE`, `ALTER TABLE`, обновление версии, замена оборудования.

**Rolling Upgrade (Поэтапное обновление)** — стратегия обновления кластера, при которой узлы обновляются последовательно, один за другим, с проверкой работоспособности после каждого шага. Позволяет минимизировать downtime и обеспечить мгновенный откат путём возврата к предыдущему узлу.

## Базовые концепции

### Зачем нужно обслуживание: жизненный цикл эксплуатируемой БД

Любая работающая база данных в процессе эксплуатации непрерывно меняет свою внутреннюю структуру:

1. **Запись и удаление данных** оставляют «дыры» в страницах (fragmentation). После `DELETE` страница помечается свободной, но физический файл не уменьшается — `Data_free` растёт, а эффективность последовательного чтения падает.
2. **Обновления (`UPDATE`)** в InnoDB часто физически удаляют старую версию строки (через undo/redo) и вставляют новую, что фрагментирует кластерный индекс.
3. **Статистика оптимизатора** устаревает по мере изменения распределения данных, из-за чего планировщик начинает выбирать неоптимальные планы (например, full scan вместо index lookup).
4. **Накопление служебных данных** — binary logs, undo tablespaces, временные файлы сортировки — постепенно занимает место на диске, если не очищается.

Регулярное обслуживание решает три задачи: (а) вернуть дисковое пространство ОС; (б) обновить статистику для корректных планов; (в) проверить целостность, чтобы обнаружить повреждение до аварии. Без него производительность деградирует нелинейно: небольшая фрагментация почти незаметна, но на таблицах в десятки—сотни ГБ она превращается в многократный рост I/O и времени запросов.

### Архитектура хранения InnoDB и природа фрагментации

Понимание физического хранения необходимо, чтобы правильно выбирать метод обслуживания:

- **Страницы (pages), 16 КБ** — атомарная единица хранения и I/O в InnoDB. Данные и индексы организованы в B-деревья поверх страниц.
- **Кластерный индекс** — строки таблицы физически упорядочены по первичному ключу внутри B-дерева. Вторичные индексы хранят значение PK для поиска строки. Поэтому дефрагментация по PK одновременно уплотняет и данные, и вторичные индексы.
- **Табличные пространства (tablespaces).** При `innodb_file_per_table = ON` (значение по умолчанию в 8.x) каждая таблица живёт в собственном файле `.ibd`. Освобождённое внутри него место возвращается операционной системе только при пересоздании таблицы (`OPTIMIZE TABLE`, `ALTER TABLE ... FORCE`) или усечении (truncate). При `innodb_file_per_table = OFF` все таблицы живут в общем `ibdata1`, который **никогда не уменьшается** — `OPTIMIZE TABLE` уплотнит данные внутри, но место ОС не вернёт. Это ключевое ограничение при планировании обслуживания.
- **Undo tablespaces** — хранят старые версии строк для MVCC и отката транзакций. Со временем раздуваются при долгих транзакциях; в 8.x могут быть усечены (`innodb_undo_log_truncate`).
- **Buffer pool** — кэш страниц в памяти. Тяжёлые операции обслуживания (пересоздание таблицы) интенсивно читают/пишут через buffer pool, вытесняя «горячие» страницы приложения — отсюда нагрузка на рабочие запросы.

**Вывод для практики:** дефрагментация имеет смысл только при реальном расхождении объёма данных и файла (`Data_free` > 20–30% от размера таблицы или после удаления > 20% строк). На небольших таблицах она бесполезна и лишь создаёт нагрузку.

### Статистика оптимизатора и её роль

Оптимизатор запросов MySQL строит план выполнения, опираясь на оценку количества строк (cardinality), проходящих через каждый шаг. Эта оценка берётся из **статистики индексов**, а не из реального пересчёта таблицы. InnoDB хранит статистику персистентно (`innodb_stats_persistent = ON` по умолчанию в 8.x) в системных таблицах `mysql.innodb_index_stats` / `mysql.innodb_table_stats`.

- Статистика **автоматически пересчитывается** при изменении ~10% строк таблицы (`innodb_stats_auto_recalc = ON`), но выборочно и асинхронно — после массовой нагрузки план может временно «плыть».
- Явный `ANALYZE TABLE` принудительно обновляет статистику. Это дешевле `OPTIMIZE TABLE` и часто решает проблему медленных запросов без пересоздания таблицы.
- Устаревшая статистика — частая причина регрессий после обновления версий и после массовых `DELETE`/`LOAD DATA`.

### Модель релизов MySQL и совместимость

С 2024 года Oracle использует две линии выпусков:

- **LTS (Long Term Support)** — стабильные версии (например, **8.4 LTS**). Поддержка до ~8 лет, пригодны для критических Production-систем. Рекомендуются по умолчанию.
- **Innovation** — быстрые релизы с новыми функциями (например, **9.x**). Каждая версия поддерживается только до выхода следующей (≈ раз в 3 месяца). Не для стабильного Production.

Ветка **8.0** завершает поддержку (EOL — октябрь 2026), поэтому основной сценарий обновления сегодня — переход **8.0 → 8.4 LTS**. Мажорные переходы между несовместимыми форматами системных таблиц требуют явной процедуры обновления метаданных при первом запуске нового сервера.

### Стратегии обновления: In-place против Logical

| Критерий | In-place Upgrade | Logical Upgrade |
| --- | --- | --- |
| Механизм | Замена бинарей + обновление словаря на месте | Дамп → новый сервер → восстановление |
| Время простоя | Минимально (зависит от размера словаря) | Долго (пропорционально объёму данных) |
| Смена ОС / архитектуры CPU | Невозможна | Возможна |
| Большие разрывы версий | Рискованно (8.0 → 9.x напрямую не рекомендуется) | Надёжно |
| Целостность файлов данных | Используются существующие | Полностью пересоздаются |

**Правило выбора:** для рутинного обновления 8.0 → 8.4 LTS на той же ОС используйте **In-place** (быстрее, проще откат по бэкапу). Для миграции между ОС, смены архитектуры (x86 → ARM) или при серьёзно повреждённых/очень старых данных — **Logical**.

> **Важно:** MySQL **не поддерживает понижение версии (downgrade)** между мажорными релизами. Единственный способ «отката» после обновления — восстановление из полного бэкапа, сделанного до операции. Это делает предварительный бэкап обязательным, а не рекомендательным шагом.

## Практические сценарии

### 1. Диагностика состояния таблиц и фрагментации

Прежде чем что-либо обслуживать, необходимо измерить реальный объём фрагментации. Нельзя опираться только на размер файла `.ibd` — файл всегда немного больше данных из-за служебных структур.

#### Предварительные условия (Prerequisites)
- Доступ к серверу с правами `PROCESS` и `SELECT` на целевые таблицы (для `SHOW TABLE STATUS`/`INFORMATION_SCHEMA`).
- Свободное место на диске: при любом пересоздании таблицы потребуется до 100% её текущего размера в свободном пространстве (под временную копию).
- Понимаем, что таблица использует `InnoDB` и `innodb_file_per_table = ON` (иначе возврат места ОС невозможен).

```sql
-- Размер данных, индексов и «свободного» места в таблице
SHOW TABLE STATUS IN my_database LIKE 'large_log_table'\G
-- → Data_length:   5242880000  (≈ 5 ГБ данные)
-- → Index_length:  1073741824  (≈ 1 ГБ индексы)
-- → Data_free:     3145728000  (≈ 3 ГБ «дыр» — 47% от файла)
```

```sql
-- Тот же показатель через INFORMATION_SCHEMA (удобно для выборки по порогу)
SELECT
    TABLE_NAME,
    ROUND(DATA_LENGTH / 1024 / 1024, 1) AS data_mb,
    ROUND(INDEX_LENGTH / 1024 / 1024, 1) AS index_mb,
    ROUND(DATA_FREE   / 1024 / 1024, 1) AS free_mb,
    ROUND(DATA_FREE / (DATA_LENGTH + INDEX_LENGTH) * 100, 1) AS free_pct
FROM INFORMATION_SCHEMA.TABLES
WHERE TABLE_SCHEMA = 'my_database'
  AND DATA_FREE > 100 * 1024 * 1024          -- только таблицы с > 100 МБ «дыр»
ORDER BY DATA_FREE DESC;
-- → строки тех таблиц, которые реально стоит дефрагментировать
```

**Как интерпретировать результат:**
- `free_pct` > 20–30% или удалено > 20% строк недавно → кандидат на `OPTIMIZE TABLE`.
- `Data_free` близок к 0, но запросы медленные → проблема в статистике, а не в фрагментации (см. сценарий 3).
- Для проверки гранулярной фрагментации индекса используйте `SHOW INDEX FROM table_name`, где `Cardinality` отражает оценку уникальности.

### 2. Дефрагментация таблиц (`OPTIMIZE TABLE`)

При интенсивных `DELETE` и `UPDATE` в InnoDB возникают пустоты в страницах данных (Fragmented Space). `OPTIMIZE TABLE` уплотняет данные и возвращает место ОС (при `innodb_file_per_table = ON`).

#### Как это работает
1. MySQL создаёт временную таблицу с новой схемой (физически новый `.ibd`).
2. Копирует данные из старой таблицы в новую. В MySQL < 5.6 таблица в это время доступна только для чтения; в версиях 5.6.17+ для InnoDB операция выполняется как онлайн DDL (`ALTER TABLE ... FORCE`, `ALGORITHM=INPLACE`), допуская параллельные `INSERT`/`UPDATE`/`DELETE`, но с повышенной нагрузкой на диск и buffer pool.
3. Удаляет старую таблицу и переименовывает новую, атомарно подменяя объект.
4. Обновляет статистику оптимизатора (эквивалент `ANALYZE TABLE`).

#### Когда применять
- После массового удаления строк (> 20% объёма).
- При значительном расхождении `Data_free` в выводе `SHOW TABLE STATUS`.
- При плановом обслуживании больших «логовых»/исторических таблиц в низком трафике.

#### Шаги выполнения (Step-by-Step)
```sql
-- 1. Проверка до операции (зафиксируйте размер)
SHOW TABLE STATUS IN my_database LIKE 'large_log_table'\G

-- 2. Сама дефрагментация
OPTIMIZE TABLE my_database.large_log_table;
-- → +----------------------------+----------+----------+-------------------------------------------------------------------+
-- → | Table                      | Op       | Msg_type | Msg_text                                                          |
-- → +----------------------------+----------+----------+-------------------------------------------------------------------+
-- → | my_database.large_log_table| optimize | note     | Table does not support optimize, doing recreate + analyze instead |
-- → | my_database.large_log_table| optimize | status   | OK                                                                |
-- → +----------------------------+----------+----------+-------------------------------------------------------------------+
-- Для InnoDB сообщение "Table does not support optimize, doing recreate + analyze instead" — НОРМА.
```

#### Альтернативы без длительных блокировок
Для таблиц, где допустимость онлайн-операции критична, используйте `ALTER TABLE ... ALGORITHM=INPLACE` (штатно, но блокирует метаданные на финальном rename) или внешний инструмент:

```bash
# pt-online-schema-change (Percona Toolkit) — создаёт теневую таблицу,
# копирует данные построчно и синхронизирует изменения через триггеры.
pt-online-schema-change \
  --alter "ENGINE=InnoDB" \
  --execute \
  h=127.0.0.1,P=3306,u=root,D=my_database,t=large_log_table
# → Copying rows: progress, затем swap таблиц без заметной блокировки приложения
```

#### Валидация (что проверить после)
```sql
SHOW TABLE STATUS IN my_database LIKE 'large_log_table'\G
-- → Data_free существенно уменьшился (близок к 0 или к штатному запасу)
-- → Data_length сопоставим с реальным объёмом строк
```
```bash
# На уровне ОС: файл .ibd должен уменьшиться
ls -lh /var/lib/mysql/my_database/large_log_table.ibd
# → до: 9.0G ; после: 6.2G
```

#### Устранение неполадок (Troubleshooting)
| Симптом / ошибка | Причина | Решение |
| --- | --- | --- |
| `ERROR 1114 (HY000): The table ... is full` | Не хватило места под временную копию | Освободите ≥ размера таблицы на томе `/var/lib/mysql` и повторите |
| Файл `.ibd` не уменьшился | `innodb_file_per_table = OFF` (общий `ibdata1`) | Возврат места ОС невозможен; уплотнение внутри всё равно полезно для I/O |
| Долгая блокировка на записи | Таблица > 100 ГБ, нет онлайн-инструмента | Используйте `pt-online-schema-change`; планируйте в окно обслуживания |
| Рост `Data_free` сразу после OPTIMIZE | Запущена авто-вставка/приложение пишет | Ожидаемо; повторная дефрагментация бессмысленна — устраните источник |

**SRE-предупреждение:** На огромных таблицах (> 100 ГБ) `OPTIMIZE TABLE` может вызвать долгую блокировку или исчерпание места на диске. Используйте `pt-online-schema-change` для безопасной дефрагментации без блокировок.

#### Best Practices и очистка
- Запускайте в окно низкого трафика; мониторьте `Threads_running` и latency в [мониторинге](./monitoring.md).
- После успеха нет «отката» на уровне таблицы — возврат к состоянию до обслуживания возможен только из бэкапа. Поэтому бэкап перед сценарием 2 опционален (сама операция безопасна), но бэкап всей БД обязателен перед обновлениями (сценарии 5–6).
- Не дефрагментируйте таблицы с `Data_free` < 20% — нагрузка не окупается.

### 3. Обновление статистики и проверка целостности

Частая причина «внезапно» медленных запросов — устаревшая статистика, а не фрагментация. `ANALYZE TABLE` решает её быстро, без пересоздания таблицы.

#### Предварительные условия
- Минимальные требования к диску (операция не создаёт полную копию таблицы).
- Допустим кратковременный shared-лок на таблицу (на InnoDB — очень короткий).

```sql
-- Обновление статистики одной таблицы
ANALYZE TABLE my_database.orders;
-- → +----------------------+---------+----------+----------+
-- → | Table                | Op      | Msg_type | Msg_text |
-- → +----------------------+---------+----------+----------+
-- → | my_database.orders   | analyze | status   | OK       |
-- → +----------------------+---------+----------+----------+
```

```sql
-- Проверка целостности таблицы (InnoDB — только диагностика)
CHECK TABLE my_database.orders;
-- → Msg_text: OK  → структура и индексы целы
```

#### Почему `CHECKSUM TABLE` не является проверкой целостности

`CHECKSUM TABLE` часто ошибочно ставят в один ряд с `CHECK TABLE`, но это разные вещи:

```sql
CHECKSUM TABLE my_database.orders;
-- → Table                 | Checksum
-- → my_database.orders    | 8213495717234984621
```

| | `CHECK TABLE` | `CHECKSUM TABLE` |
| :--- | :--- | :--- |
| Что делает | Проверяет корректность структуры, B-деревьев индексов и связей | Вычисляет контрольную сумму построчным чтением |
| Выявляет повреждение данных | Да (в пределах того, что InnoDB способен обнаружить) | Нет |
| Стоимость на InnoDB | Умеренная, `QUICK` пропускает проверку связей | **Полное чтение всей таблицы** |
| Регулярное применение | Да, из cron | **Нет** |

Ключевой факт: для InnoDB (и любого движка, кроме MyISAM) результат `CHECKSUM TABLE` —
это именно тот же построчный расчёт, что даёт `CHECK TABLE ... EXTENDED`. То есть
контрольная сумма для InnoDB **не является детектором повреждений**: она всегда
возвращает значение для успешно прочитанной таблицы и не сообщает о битых страницах.
Смысл `CHECKSUM` есть только для MyISAM, созданных с `CHECKSUM=1`, где он сравнивается
с сохранённым значением.

Практический вывод: для контроля целостности InnoDB использовать `CHECK TABLE`
(и `innochecksum` для офлайн-проверки файлов `.ibd`, см.
[Диагностический runbook](./troubleshooting-runbook.md)), а не `CHECKSUM TABLE`.
Регулярный прогон `CHECKSUM TABLE` по большим таблицам даст только лишнюю нагрузку на
ввод-вывод.

#### Пакетное обслуживание через mysqlcheck (без входа в SQL)
```bash
# Обновить статистику всех таблиц конкретной базы
mysqlcheck --analyze --databases my_database -u root -p
# → my_database.orders                             OK

# Проверить целостность всей БД
mysqlcheck --check --databases my_database -u root -p
# → my_database.orders                             OK

# Оптимизировать (дефрагментировать) все таблицы базы
mysqlcheck --optimize --databases my_database -u root -p
```

#### Валидация
```sql
-- Новая статистика отражается в системных таблицах
SELECT TABLE_NAME, STATS_PERSISTENT, LAST_UPDATE
FROM mysql.innodb_table_stats
WHERE DATABASE_NAME = 'my_database' AND TABLE_NAME = 'orders';
-- → LAST_UPDATE показывает время только что выполненного ANALYZE
```

#### Устранение неполадок
| Симптом | Причина | Решение |
| --- | --- | --- |
| `CHECK TABLE` возвращает `warning`/`error` | Повреждение индекса/страницы | Для InnoDB — восстановление из бэкапа; `REPAIR TABLE` для InnoDB не применим (только для MyISAM/Archive) |
| `ANALYZE TABLE` не меняет план запроса | Используется устаревший кэш планов / hints | Сбросьте планы (`FLUSH STATUS`) и перепроверьте `EXPLAIN`; см. [оптимизацию запросов](./Operations/explain_and_optimization.md) |
| Клиент жалуется на `LOCK` во время ANALYZE | Shared-лок на короткое время | Допустимо; для критичных таблиц планируйте в низкий трафик |

**Best Practices:** после массовых `DELETE`/`LOAD DATA`/переезда данных всегда выполняйте `ANALYZE TABLE` раньше, чем `OPTIMIZE TABLE` — статистика часто устраняет регрессию дешевле.

### 4. Секционирование (Partitioning) в MySQL

Секционирование — проактивный метод обслуживания: таблица делится на физические сегменты, и устаревшие данные удаляются мгновенно операцией `DROP PARTITION` (без полной пересборки таблицы). Реализация теоретических основ из **[Секционирования данных](../Concepts/partitioning.md)**.

#### Пример создания таблицы RANGE по годам
```sql
CREATE TABLE sales (
    id INT NOT NULL,
    sale_date DATE NOT NULL,
    amount DECIMAL(10,2)
)
PARTITION BY RANGE (YEAR(sale_date)) (
    PARTITION p2024 VALUES LESS THAN (2025),
    PARTITION p2025 VALUES LESS THAN (2026),
    PARTITION p_max VALUES LESS THAN MAXVALUE
);
```

#### Обслуживание партиций
```sql
-- Удаление старых данных (мгновенно, без полного сканирования/пересборки)
ALTER TABLE sales DROP PARTITION p2024;
-- → Query OK, 0 rows affected (0.02 sec)  -- освобождает место сразу

-- Добавление новой секции (если есть MAXVALUE, требуется REORGANIZE)
ALTER TABLE sales REORGANIZE PARTITION p_max INTO (
    PARTITION p2026 VALUES LESS THAN (2027),
    PARTITION p_max VALUES LESS THAN MAXVALUE
);
-- → перераспределяет только строки, попавшие в p_max, остальные не трогает
```

#### Валидация
```sql
-- Список партиций и количество строк в каждой
SELECT PARTITION_NAME, TABLE_ROWS, DATA_FREE
FROM INFORMATION_SCHEMA.PARTITIONS
WHERE TABLE_SCHEMA = 'my_database' AND TABLE_NAME = 'sales';
-- → по одной строке на партицию; DATA_FREE показывает фрагментацию внутри
```

#### Устранение неполадок и крайние случаи
- **`REORGANIZE PARTITION` перестраивает данные** выбранных партиций — на больших объёмах это долго; планируйте до заполнения `p_max`.
- **Partition Pruning** зависит от условия в `WHERE` по ключу секционирования. Если фильтра нет — читаются все партиции (эффект пропадает).
- **Нельзя секционировать таблицу «на лету» без пересоздания** — выбор стратегии делается на этапе проектирования; миграция существующей таблицы требует `ALTER TABLE ... PARTITION BY ...` (полная пересборка).

### 5. Процедура Major Upgrade (8.0 -> 8.4 LTS, In-place)

Переход на современные LTS-версии требует строгого соблюдения чеклиста. Стратегия — In-place (та же ОС, сохраняются файлы данных).

#### Предварительные условия
- **Полный свежий бэкап** (физический, через Percona XtraBackup/MySQL Shell dump) — единственный способ отката, т.к. downgrade не поддерживается. См. **[Резервное копирование и восстановление в MySQL](./backup_and_recovery/overview.md)**.
- Доступ root к серверу и к БД.
- Свободное место: под временные файлы словаря и логи — минимум 20% свободного пространства тома данных.
- Проверка, что реплики (replicas) обновляются вместе с источником (source); в репликации сначала обновляются реплики, затем источник (rolling upgrade).
- Окно обслуживания (для некластерных одиночных инстансов — простой обязателен на время остановки/запуска).

#### Шаг 1: Проверка совместимости (MySQL Shell)
Самый важный шаг. Утилита `util.checkForServerUpgrade()` проверяет базу на наличие устаревших типов данных, зарезервированных слов, конфликтов имён и несовместимостей целевой версии.

```bash
# Запуск из командной строки (подключение к живому инстансу)
mysqlsh --user root --password --execute "util.checkForServerUpgrade('root@localhost:3306')"
# → MySQL Shell 8.4 ...
# → 1) Issues reported by checkForServerUpgrade:
# →   ... [чек-лист совместимости] ...
# → Errors: 0  Warnings: 2
```

**На что обратить внимание в отчете:**
- **Removed features:** Параметры в `my.cnf`, которые больше не поддерживаются (например, `query_cache_size` — кэш запросов удалён в 8.0, но может остаться в конфиге 5.7→8.0).
- **Reserved keywords:** Колонки с именами, ставшими ключевыми словами в 8.4 (например, `RANK`, `ROW`, `SYSTEM`).
- **Circular dependencies:** В представлениях (Views) и stored routines.
- **Table/sysvar changes:** Изменения типов системных таблиц. Исправьте все `Errors` до продолжения; `Warnings` анализируйте индивидуально.

#### Шаг 2: Чистая остановка и бэкап
```bash
# Убедиться, что InnoDB завершит все операции слияния/сброса (fast shutdown = 0)
mysql -u root -p -e "SET GLOBAL innodb_fast_shutdown = 0;"

# Остановка сервиса
sudo systemctl stop mysql
# → вывод отсутствует при успешной остановке

# Подтверждение отсутствия процесса
sudo systemctl status mysql --no-pager | head -3
# → Active: inactive (dead)

# Бэкап (пример — физический через XtraBackup); детали в backup_and_recovery/overview.md
# xtrabackup --backup --target-dir=/backup/pre_upgrade_$(date +%F)
```

#### Шаг 3: Обновление бинарных файлов
Подключите новый репозиторий Oracle (8.4 LTS) и обновите пакеты. **Не запускайте сервер сразу** — сначала обновите конфиг.

```bash
# Пример для Ubuntu/Debian (через mysql-apt-config, выбран mysql-8.4-lts)
sudo apt update
sudo apt install -y mysql-server mysql-shell
# → обновляет mysqld, mysqlsh, клиенты; файлы данных НЕ трогаются

# Проверка установленной версии бинарника до запуска
mysqld --version
# → /usr/sbin/mysqld  Ver 8.4.x for Linux on x86_64 (MySQL Community Server - LTS)
```

> Перед запуском удалите/закомментируйте в `my.cnf` параметры, помеченные `checkForServerUpgrade` как `Removed` (например, `query_cache_size`, `query_cache_type`), иначе сервер не стартует.

#### Шаг 4: Автоматическое обновление данных
Начиная с версии 8.0.16, MySQL автоматически выполняет обновление системных таблиц (Data Dictionary, performance_schema, sys) при первом запуске после смены бинарников. Утилита `mysql_upgrade` считается устаревшей (deprecated) и в 9.0 удалена — больше не требуется.

```bash
# Запуск сервиса (он сам обновит словарь при старте)
sudo systemctl start mysql
# → вывод отсутствует при успешном старте

# В логе должны появиться строки об успешном обновлении словаря
sudo grep -i "upgrading" /var/log/mysql/error.log | tail -5
# → ... [Server] Upgrading the data dictionary ...
# → ... [Server] Server upgrade from '800xx' to '804xx' started ...
# → ... [Server] Server upgrade from '800xx' to '804xx' completed
```

#### Шаг 5: Валидация
```bash
# Версия работающего сервера
mysql -u root -p -e "SELECT VERSION();"
# → 8.4.x

# Все движки загружены, словарь обновлён
mysql -u root -p -e "SHOW ENGINES; SHOW TABLES FROM mysql;" | head
# → InnoDB поддержка YES/DEFAULT; системные таблицы присутствуют
```

Проверьте логи ошибок `/var/log/mysql/error.log` и убедитесь, что все движки загружены корректно, а в логе нет `ERROR`-строк после `Server upgrade ... completed`.

#### Устранение неполадок
| Симптом / ошибка | Причина | Решение |
| --- | --- | --- |
| Сервер не стартует, `unknown variable 'query_cache_size'` | Удалённый параметр в `my.cnf` | Закомментируйте/удалите параметр, повторите `systemctl start mysql` |
| `ERROR 1810 (HY000): ... table is full` при старте | Не хватило места под временные файлы словаря | Освободите место и перезапустите |
| `Server upgrade ... failed` в error.log | Несовместимая схема/остались Errors из `checkForServerUpgrade` | Остановите, восстановите бэкап, исправьте схему, повторите с шага 1 |
| Реплика отстаёт/рассинхронизирована | Обновление словаря тяжёлое | Обновляйте реплики до источника; для группы — rolling, один узел за раз |

#### Best Practices и откат
- **Порядок в репликации:** сначала все replicas, затем source (rolling upgrade), чтобы source всегда имел совместимую со старыми репликами версию формата binlog во время перехода.
- **Откат:** MySQL не поддерживает downgrade. Если обновление не удалось — остановите сервер и восстановите данные из бэкапа шага 2 (см. [backup_and_recovery](./backup_and_recovery/overview.md)).
- После успешного обновления пересоберите статистику нагруженных таблиц (`ANALYZE TABLE`), т.к. после обновления словаря планы могут измениться.

### 6. Логическое обновление (Logical) и патч/минор обновление

#### 6.1 Логическое обновление (смена ОС / архитектуры / большие разрывы версий)
Применяется, когда In-place невозможен (миграция x86 → ARM, Debian → RHEL, 5.7 → 8.4).

```bash
# 1. Дамп на ИСХОДНОМ сервере (MySQL Shell — параллельный, консистентный dump)
mysqlsh --user root --password --execute "util.dumpInstance('/backup/dump_8_0', {threads: 4})"
# → Acquiring global lock...  Dumping 123 tables...  Dump complete

# 2. Установка НОВОГО сервера 8.4 LTS (см. [Установка MySQL](./installation.md))
# 3. Загрузка дампа на НОВЫЙ сервер
mysqlsh --user root --password --execute "util.loadInstance('/backup/dump_8_0', {loadUsers: true})"
# → 100% complete; Schema и данные перенесены в новый формат
```

**Преимущество:** формат файлов данных не имеет значения — данные пересоздаются заново, исключая накопленную фрагментацию и повреждения. **Недостаток:** длительный простой пропорционально объёму.

#### 6.2 Патч / минорное обновление (8.4.0 -> 8.4.3)
Внутри одной ветки формат данных не меняется — операция дешёвая и низкорисковая (по сути In-place без обновления словаря).

```bash
# Предварительно — бэкап (хотя бы логический, на всякий случай)
# Затем обновление пакетов
sudo apt update && sudo apt install -y mysql-server
# → обновляет только бинарник; данные нетронуты
sudo systemctl restart mysql
mysql -e "SELECT VERSION();"   # → 8.4.3
```

#### Валидация (общая для всех стратегий)
```bash
mysql -u root -p -e "SELECT VERSION(); SHOW VARIABLES LIKE 'innodb_version';"
# → целевая версия; движок соответствует
mysqlcheck --check --all-databases -u root -p   # → все таблицы OK
```

#### Крайние случаи и ограничения
- **Прямой переход 8.0 → 9.x (Innovation) не рекомендуется** без промежуточной 8.4 LTS — разрыв функций велик; предпочтителен Logical-путь.
- **Обновление кластера InnoDB Cluster / Group Replication** — только по одному узлу (rolling), с выводом узла из группы (`group_replication` stop) и возвратом после валидации.
- **Docker-инстансы:** обновление делается сменой тега образа при сохранении volume `/var/lib/mysql` (см. [MySQL в Docker](./docker.md)), но бэкап volume обязателен до операции.

### 7. Тихие изменения поведения при переходе 5.7 → 8.0

Переход 5.7 → 8.0 меняет не только состав возможностей, но и значения по
умолчанию. Ниже — изменения, которые не выдают ошибку при старте, а проявляются
позже: неверные данные, отказы запросов или изменившаяся производительность.
Все значения ниже взяты из официальной таблицы изменённых умолчаний и списков
добавленных, устаревших и удалённых переменных для 8.0 и 8.4.

#### Ломает старт сервера

| Переменная или режим | Что произошло | Что делать |
| :--- | :--- | :--- |
| `NO_AUTO_CREATE_USER` в `sql_mode` | Удалён из `sql_mode` в 8.0.11 — `GRANT` больше не создаёт пользователей, и режим стал неактуальным. Официально: чтобы избежать сбоя старта на 8.0, удалите `NO_AUTO_CREATE_USER` из `sql_mode` в файлах опций | Убрать из `my.cnf` до обновления |
| `query_cache_size`, `query_cache_type`, `query_cache_limit`, `query_cache_min_res_unit`, `query_cache_wlock_invalidate` | Удалены в 8.0.3 | Удалить из `my.cnf` |
| `DB2`, `MAXDB`, `MSSQL`, `MYSQL323`, `MYSQL40`, `ORACLE`, `POSTGRESQL`, `NO_FIELD_OPTIONS`, `NO_KEY_OPTIONS`, `NO_TABLE_OPTIONS` в `sql_mode` | Удалены в 8.0.11, больше не могут быть присвоены `sql_mode` | Убрать из `sql_mode` |
| `secure_auth` | Удалена в 8.0.3 | Удалить из `my.cnf` |
| `show_compatibility_56` | Удалена в 8.0.1 | Удалить из `my.cnf` |
| `old_passwords` | Удалена в 8.0.11 | Удалить из `my.cnf` |
| `partition` / `skip-partition` | Удалены в 8.0.0 | Удалить из `my.cnf` |
| `sync_frm` | Удалена в 8.0.0 | Удалить из `my.cnf` |

Обратите внимание на последствия удаления `MAXDB`: его удаление означает, что
тип `TIMESTAMP` в `CREATE TABLE` и `ALTER TABLE` трактуется как `TIMESTAMP` и
больше не трактуется как `DATETIME`. Проверьте схему на неявные `TIMESTAMP` до
обновления.

#### Меняет значения по умолчанию

| Параметр | 5.7 | 8.0 и 8.4 | Риск |
| :--- | :--- | :--- | :--- |
| `explicit_defaults_for_timestamp` | `OFF` | `ON` | Колонки `TIMESTAMP` без явных `NULL`/`DEFAULT`/`ON UPDATE` больше не получают автоматически `NOT NULL`, а **первая** такая колонка больше не получает автоматически `DEFAULT CURRENT_TIMESTAMP` и `ON UPDATE CURRENT_TIMESTAMP` |
| `character_set_server` | `latin1` | `utf8mb4` | Смена набора символов по умолчанию для новых объектов |
| `collation_server` | `latin1_swedish_ci` | `utf8mb4_0900_ai_ci` | То же для сравнений |
| `max_allowed_packet` | `4194304` (4 MB) | `67108864` (64 MB) | Клиенты и утилиты с меньшими значениями будут отклонять крупные пакеты |
| `local_infile` | `ON` | `OFF` | `LOAD DATA LOCAL INFILE` перестаёт работать без явного включения |
| `event_scheduler` | `OFF` | `ON` | События Event Scheduler начинают выполняться после обновления — проверьте список событий заранее |
| `table_open_cache` | `2000` | `4000` | Изменение потребления памяти |
| `innodb_undo_tablespaces` | `0` | `2` | Появляются отдельные undo tablespace |
| `innodb_undo_log_truncate` | `OFF` | `ON` | Включается автоматическое усечение undo tablespace |
| `innodb_autoinc_lock_mode` | `1` | `2` | Меняется поведение блокировок вокруг `AUTO_INCREMENT` |
| `innodb_max_dirty_pages_pct` | `75` | `90` | Допускается больше грязных страниц в памяти |
| `innodb_flush_neighbors` | `1` | `0` | Сброс соседних страниц выключен |
| `log_bin` | `OFF` | `ON` | Бинарный лог включается по умолчанию |
| `server_id` | `0` | `1` | Узел получает идентификатор по умолчанию |
| `transaction-write-set-extraction` | `OFF` | `XXHASH64` | Write-set для параллельной репликации извлекается по умолчанию |
| `slave_pending_jobs_size_max` | 16 MB | 128 MB | Рост потребления памяти |
| `slave_rows_search_algorithms` | `INDEX_SCAN,TABLE_SCAN` | `INDEX_SCAN,HASH_SCAN` | Меняется алгоритм поиска строк на реплике |

**Важная поправка к распространённому мифу:** `ONLY_FULL_GROUP_BY` — не
изменение 5.7 → 8.0. Этот режим присутствует в списке `sql_mode` по умолчанию
начиная с MySQL 5.7.5. Единственное отличие дефолтного `sql_mode` 8.0 от 5.7 —
исчезновение `NO_AUTO_CREATE_USER`. Формулировка самого режима в 8.0 и 8.4
одинакова: отклоняются запросы, в которых список выбора, условие `HAVING` или
список `ORDER BY` ссылаются на неагрегированные колонки, не названные в
`GROUP BY` и не функционально от них зависящие.

#### Меняет поведение приложения

- **`default_authentication_plugin`**: `mysql_native_password` →
  `caching_sha2_password`. Изменение применяется **только к новым аккаунтам**,
  существующие не меняются. Проверьте, как клиенты подключаются без
  `--get-server-public-key`, иначе возможны ошибки аутентификации.
- **`utf8mb3` и псевдоним `utf8`**: псевдоним `utf8` для `utf8mb3` помечен как
  устаревший в 8.0; начиная с 8.0.28 `utf8mb3` отображается вместо `utf8` в
  `INFORMATION_SCHEMA` и выводе `SHOW`. В 8.4 статус тот же — устаревший, не
  удалённый. Проверьте вывод `SHOW CREATE TABLE` в приложении: ожидаемое имя
  набора символов изменилось.
- **Зарезервированные слова**: часть слов, не являвшихся зарезервированными в
  5.7, стали зарезервированными в 8.0. Официальная формулировка: идентификаторы,
  использовавшиеся как имена, становятся недопустимыми, и запросы следует
  исправлять quoting'ом. Ключевые примеры, помеченные в документации 8.0 как
  добавленные: `RANK`, `ROW_NUMBER`, `DENSE_RANK`, `OVER`, `WINDOW`, `RECURSIVE`,
  `GROUPING`, `GROUPS`, `LATERAL`, `SYSTEM`, `EMPTY`, `CUME_DIST`, `NTILE`,
  `FIRST_VALUE`, `INTERSECT`.
- **Квалификаторы `ASC`/`DESC` в `GROUP BY`** удалены начиная с 8.0.13:
  результаты сортировки могут отличаться.
- **Формат бинарного лога**: в 8.0 бинарный лог включён по умолчанию, а формат
  по умолчанию — `ROW`.
- **Предупреждение документации о режимах SQL и секционированных таблицах:**
  изменение режима SQL сервера после создания секционированной таблицы и вставки
  в неё данных может вызвать существенные изменения в поведении таких таблиц и
  привести к потере или повреждению данных. Если в базе есть партиционированные
  таблицы, фиксируйте `sql_mode` до обновления.

## Диагностика и устранение неисправностей

### Типичные симптомы и пороговые значения

| Симптом | Диагностическая команда | Пороговое значение / ожидаемый результат | Вероятная причина | Решение |
| --- | --- | --- | --- | --- |
| Рост `Data_free` > 20% | `SHOW TABLE STATUS` | `Data_free` / (`Data_length` + `Index_length`) > 20% | Массовые `DELETE`, фрагментация | `OPTIMIZE TABLE` или `pt-online-schema-change` |
| Рост `Innodb_row_lock_time_avg` > 50ms | `SHOW GLOBAL STATUS LIKE 'Innodb_row_lock_time_avg'` | > 50ms | Длинные транзакции, отсутствие индексов | Сократить транзакции, добавить индексы; см. [locking_and_deadlocks.md](./locking_and_deadlocks.md) |
| Медленные запросы после массовой загрузки | `ANALYZE TABLE` не меняет план | `EXPLAIN` показывает full scan | Устаревшая статистика | `ANALYZE TABLE` + `FLUSH STATUS` |
| Рост размера `.ibd` без изменений данных | `ls -lh *.ibd` vs `SELECT COUNT(*)` | Файл значительно больше данных | Внутренняя фрагментация, undo log | `OPTIMIZE TABLE` |
| Ошибка `ERROR 1114: Table is full` | `df -h /var/lib/mysql` | < 20% свободно на томе | Не хватило места под временную копию | Освободить место или использовать `pt-online-schema-change` |
| `Innodb_buffer_pool_wait_free` > 0 | `SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_wait_free'` | > 0 в течение 5 минут | Buffer Pool переполнен | Увеличить `innodb_buffer_pool_size` |
| `Server upgrade ... failed` в error.log | `grep -i upgrading /var/log/mysql/error.log` | Строка `failed` после `started` | Несовместимая схема, остались Errors из `checkForServerUpgrade` | Остановить, восстановить бэкап, исправить схему |
| Реплика отстаёт после обновления | `SHOW REPLICA STATUS` | `Seconds_Behind_Source` растёт | Обновление словаря тяжёлое | Обновлять реплики до источника, использовать rolling |

## Бест-практисы

1. **Держите транзакции короткими:** Чем дольше транзакция, тем выше вероятность конфликта. Цель: < 1 секунды для OLTP.
2. **Соблюдайте порядок:** Всегда обновляйте таблицы и строки в одном и том же порядке во всех частях приложения. Например, всегда `UPDATE orders SET ... WHERE id = X` перед `UPDATE order_items SET ... WHERE order_id = X`.
3. **Индексируйте поля фильтрации:** Если запрос `UPDATE/DELETE` не использует индекс, InnoDB заблокирует **все строки** таблицы (Next-Key Locks на весь диапазон).
4. **Используйте READ COMMITTED для очередей:** Если бизнес-логика позволяет, переход с `Repeatable Read` на `Read Committed` отключает Gap Locks, что значительно снижает количество дедлоков.
5. **Настройка таймаутов:**
    - `innodb_lock_wait_timeout`: Время ожидания блокировки строки (дефолт 50с, в высоконагруженных системах лучше снизить до 5–10с).
    - `lock_wait_timeout`: Время ожидания MDL (дефолт 1 год! Рекомендуется ограничить сессионно перед DDL).
    - `innodb_deadlock_detect`: ON по умолчанию. OFF только для низко-конкурентных окружений.
6. **Используйте `FOR UPDATE SKIP LOCKED`:** Для очередей задач позволяет пропускать заблокированные строки вместо ожидания.
7. **Включите `innodb_print_all_deadlocks` в production:** Это даст полную историю дедлоков в error log для постфактум анализа.
8. **Мониторьте `Innodb_row_lock_time_avg`:** Рост значения > 50ms сигнализирует о проблемах с блокировками. Настройте алерты.
9. **Используйте `pt-online-schema-change` для DDL:** Стандартный `ALTER TABLE` может блокировать таблицу на долгое время. Используйте Percona Toolkit для онлайн-изменений.
10. **Не смешивайте DDL и DML в одной транзакции:** DDL выполняет неявный COMMIT, что может привести к неожиданным блокировкам.

## Дополнительная информация

### Границы применимости и ограничения

1. **MDL и хранимые процедуры:** Внутри хранимых процедур MDL удерживается на все объекты, к которым происходит обращение, до завершения процедуры. Длительные процедуры могут блокировать DDL на своих таблицах.
2. **Информационная схема:** Запросы к `information_schema` могут удерживать кратковременные MDL. При высокой частоте таких запросов возможны каскадные задержки.
3. **Флаг `NOWAIT` и `SKIP LOCKED`:** `SELECT ... FOR UPDATE NOWAIT` немедленно возвращает ошибку, если блокировка недоступна. `SKIP LOCKED` пропускает заблокированные строки. Оба варианта доступны с MySQL 8.0.
4. **`innodb_lock_wait_timeout` vs `lock_wait_timeout`:** Первый относится к блокировкам строк InnoDB (Record/Gap/Next-Key), второй — к MDL. Значения таймаутов не связаны.
5. **Блокировки в replica-экземплярах:** На репликах SQL Thread выполняет транзакции последовательно, поэтому блокировки на репликах возникают реже, но при конфликте могут вызвать задержку репликации (`Seconds_Behind_Master` растет).
6. **Self-Deadlock:** При обновлении одной и той же строки в рамках одной транзакции InnoDB не обнаруживает дедлок, но запрос завершится ошибкой `ERROR 1213` при попытке повторного получения блокировки.
7. **FOREIGN KEY constraints:** При нарушении ограничения внешнего ключа InnoDB может приобретать блокировки на родительскую таблицу, что приводит к неожиданным контенциям.
