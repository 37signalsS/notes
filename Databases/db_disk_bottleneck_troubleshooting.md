# Диагностика дискового узкого места в базах данных

## Определения

**Дисковое узкое место (I/O bottleneck)** — состояние, при котором производительность базы данных ограничивается скоростью дисковой подсистемы. Процессор простаивает в ожидании завершения операций чтения/записи.

**I/O-bound нагрузка:** Тип нагрузки, при котором производительность системы упирается в скорость ввода-вывода, а не в вычислительную мощность CPU или объем памяти.

## Основные концепции

### Симптомы дискового瓶颈

- **Высокий `iowait`:** Процессор простаивает в ожидании диска (см. **[iowait и задержки](../Linux/Diagnostics/Performance/DiskIO/iowait_and_latency.md)**)
- **Медленные запросы:** Запросы, которые раньше выполнялись быстро, теперь работают медленно
- **Высокая утилизация диска:** `%util` близок к 100% в `iostat`
- **Большая очередь к диску:** `avgqu-sz > 1-2`

### Диагностический подход

Диагностика проводится на двух уровнях:

1. **Уровень ОС:** Какой процесс и насколько интенсивно использует диск
2. **Уровень БД:** Какие запросы создают наибольшую нагрузку на чтение/запись

Подробнее об инструментах:

- **[iostat](../Linux/Diagnostics/Filesystem/iostat.md)** — статистика по дискам
- **[iotop](../Linux/Diagnostics/Filesystem/iotop.md)** — I/O по процессам

## Практические сценарии

### Шаг 1: Определение процесса-виновника

Используйте `iotop` или `iostat` для определения процесса, создающего нагрузку на диск.

```bash
# Показывает I/O в реальном времени для каждого процесса
sudo iotop -o

# Статистика по дискам каждую секунду
# Обратите внимание на %util и await
iostat -xz 1
```

**Интерпретация:**

- Если основной потребитель I/O — процесс БД (`postgres`, `mysqld`), переходите к шагу 2
- Если другой процесс — оптимизируйте его или ограничьте приоритет I/O (`ionice`)

### Шаг 2: Анализ нагрузки внутри БД

#### PostgreSQL

Используйте расширение `pg_stat_statements` для поиска запросов с наибольшим чтением с диска:

```sql
SELECT
    (total_exec_time / 1000 / 60) AS total_minutes,
    (mean_exec_time) AS avg_ms,
    calls,
    query,
    shared_blks_read
FROM pg_stat_statements
ORDER BY shared_blks_read DESC
LIMIT 10;
```

**Основной виновник:** `Seq Scan` (последовательное сканирование) по большим таблицам.

Подробнее: **[Оптимизация производительности PostgreSQL](./PostgreSQL/Operations/performance_tuning.md)**.

#### MySQL

Используйте `Performance Schema`:

```sql
SELECT
    digest_text,
    SUM_TIMER_WAIT,
    COUNT_STAR
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

Проанализируйте медленные запросы с помощью `EXPLAIN`.

### Шаг 3: Быстрые решения

#### 1. Добавление индекса (самое эффективное)

Если запрос делает `Seq Scan` по большой таблице, добавьте индекс на столбцы из `WHERE`.

**PostgreSQL (безопасно для production):**

```sql
CREATE INDEX CONCURRENTLY my_table_my_column_idx 
ON my_table (my_column);
```

**MySQL:**

```sql
ALTER TABLE my_table ADD INDEX my_table_my_column_idx (my_column);
```

> **Важно:** В MySQL операция может вызвать блокировки в зависимости от версии и движка.

#### 2. Увеличение буферов БД (если есть свободная RAM)

Проверьте наличие свободной памяти: `free -h`

**PostgreSQL:** Увеличьте `shared_buffers` в `postgresql.conf` (обычно до 25% от RAM).

**MySQL:** Увеличьте `innodb_buffer_pool_size` в `my.cnf`.

#### 3. Временное ослабление гарантий записи (ОПАСНО)

Если проблема в нагрузке на запись, можно временно отключить синхронную запись.

**PostgreSQL:**

```sql
ALTER SYSTEM SET synchronous_commit = 'off';
```

> **Предупреждение:** При сбое питания возможна потеря последних транзакций. Используйте только как временную меру!

#### 4. Анализ `autovacuum` (PostgreSQL)

Если диск нагружают процессы автовакуума, это может указывать на "раздутые" (bloated) таблицы.

```sql
-- Посмотреть текущие процессы автовакуума
SELECT * FROM pg_stat_activity 
WHERE backend_type = 'autovacuum worker';
```

На время пиковой нагрузки можно настроить autovacuum менее агрессивно.

### Шаг 4: Особый случай — низкий iowait при высокой задержке

**Проблема:** `iowait` низкий, CPU свободен, но диск тормозит.

**Причина:** `iowait` показывает только время простоя CPU. Если процессы в очереди на диск, но CPU переключается на другие задачи, `iowait` остаётся низким.

**Диагностика:**

```bash
iostat -x 1
# Ключевые метрики:
# - await > 20 мс (HDD) или > 1 мс (SSD) — высокая задержка
# - avgqu-sz > 1-2 — растущая очередь
```

Подробнее: **[Низкий iowait при высокой задержке](../Linux/Diagnostics/Performance/DiskIO/iowait_and_latency.md)**.
