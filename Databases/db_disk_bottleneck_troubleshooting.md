# Быстрая диагностика и устранение дискового узкого места в БД

Это руководство описывает шаги по быстрой диагностике и решению проблемы, когда производительность базы данных упирается в дисковую подсистему (I/O-bound).

### Симптомы

* Высокое значение `iowait` в выводе `top` или `htop` (процессор простаивает в ожидании диска).
* Медленное выполнение запросов, которые раньше работали быстро.
* Высокая утилизация диска (`%util` близко к 100%) в `iostat`.
* Большая очередь к диску.

### Шаг 1: Чем занят диск?

Используйте `iotop` или `iostat` для определения, какой процесс и насколько интенсивно использует диск.

```bash
# Показывает I/O в реальном времени для каждого процесса
sudo iotop
```

```bash
# Показывает статистику по дискам каждую секунду. Обратите внимание на %util и await
iostat -xz 1
```

Если основной потребитель I/O — ваш процесс БД (`postgres`, `mysqld`), переходите к следующему шагу.

### Шаг 2: Анализ нагрузки внутри БД

Необходимо найти запросы, которые создают наибольшую нагрузку на чтение с диска.

#### PostgreSQL

Используйте расширение `pg_stat_statements`.

```sql
SELECT
    (total_exec_time / 1000 / 60) AS total_minutes,
    (mean_exec_time) AS avg_ms,
    calls,
    query,
    shared_blks_read
FROM pg_stat_statements
ORDER BY shared_blks_read DESC
LIMIT 10;
```

Этот запрос покажет топ-10 запросов, которые прочитали с диска наибольшее количество блоков (`shared_blks_read`).

#### MySQL

Используйте `Performance Schema`.

```sql
SELECT
    digest_text,
    SUM_TIMER_WAIT,
    COUNT_STAR
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 10;
```

Ищите запросы, которые тратят больше всего времени. Проанализируйте их с помощью `EXPLAIN`.

**Основной виновник, которого нужно искать — это `Seq Scan` (последовательное сканирование) по большим таблицам.**

### Шаг 3: Быстрые решения ("Прямо сейчас")

#### 1. Добавление индекса (Самое эффективное)

Если вы нашли запрос, который делает `Seq Scan` по большой таблице через `EXPLAIN`, добавление индекса на столбцы из `WHERE` — это самый быстрый способ решения проблемы.

**PostgreSQL (безопасно для Production):**

```sql
-- Не блокирует таблицу для чтений и записей
CREATE INDEX CONCURRENTLY my_table_my_column_idx ON my_table (my_column);
```

**MySQL:**

```sql
-- Может вызвать блокировки в зависимости от версии и движка
ALTER TABLE my_table ADD INDEX my_table_my_column_idx (my_column);
```

#### 2. Тюнинг конфигурации (если есть свободная RAM)

Увеличение буферов БД позволяет держать больше данных и индексов в оперативной памяти, что кардинально снижает нагрузку на диск.

* **Проверьте наличие свободной RAM:** `free -h`
* **PostgreSQL:** Увеличьте `shared_buffers` в `postgresql.conf` (обычно до 25% от общей RAM).
* **MySQL:** Увеличьте `innodb_buffer_pool_size` в `my.cnf`.

#### 3. Агрессивный тюнинг записи (ОПАСНО, но быстро)

Если проблема в нагрузке на запись, можно ослабить гарантии сохранности данных для пиковой производительности. **Используйте как временную меру!**

* **PostgreSQL:** `ALTER SYSTEM SET synchronous_commit = 'off';`
    Это убирает ожидание записи на диск перед подтверждением коммита. **При сбое питания возможна потеря последних транзакций.**

#### 4. Анализ `autovacuum` (PostgreSQL)

Если диск нагружают процессы автовакуума, это может быть признаком "раздутых" (bloated) таблиц. Вакуум необходим, но можно настроить его менее агрессивно на время пиковой нагрузки, если это мешает работе.

```sql
-- Посмотреть текущие процессы автовакуума
SELECT * FROM pg_stat_activity WHERE backend_type = 'autovacuum worker';
```

### Долгосрочные решения

* **Апгрейд дисков:** Переход на более быстрые SSD/NVMe.
* **Партиционирование:** Разделение больших таблиц на части.
* **Архивация:** Перенос старых, редко используемых данных.
* **Рефакторинг приложения:** Оптимизация логики работы с данными.
