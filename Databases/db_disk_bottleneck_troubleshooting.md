# Диагностика дисковых узких мест в базах данных

## Определения

**Дисковое узкое место (I/O bottleneck)** — состояние, при котором производительность базы данных (БД) ограничивается скоростью дисковой подсистемы. В этом состоянии вычислительные ресурсы процессора (CPU) простаивают, ожидая завершения операций чтения или записи данных.

**I/O-bound нагрузка** — тип нагрузки, при которой основным ограничивающим фактором является скорость ввода-вывода (чтение с диска или запись на него), а не вычислительная мощность процессора или объем оперативной памяти.

**События ожидания (Wait Events)** — метрики СУБД, показывающие, на каком именно этапе и какого ресурса ожидает процесс (например, чтение блока данных, запись в лог транзакций или ожидание освобождения буфера).

## Основные концепции

### Основные симптомы

1.  **Высокий показатель `iowait` (`%wa`):** процессор простаивает, ожидая ответа от диска.
2.  **Рост задержек (Latency):** увеличение времени выполнения запросов, которые ранее работали быстро.
3.  **Высокая утилизация диска (`%util`):** диск постоянно занят обработкой запросов (близко к 100% в выводе `iostat`).
4.  **Длинная очередь к диску (`avgqu-sz`):** большое количество запросов на ввод-вывод ожидает своей очереди на выполнение.
5.  **Наличие процессов в статусе `D` (Uninterruptible Sleep):** процессы, заблокированные на операциях ввода-вывода.

### Типы дисковой нагрузки в СУБД

В базах данных дисковая нагрузка обычно делится на следующие категории:

-   **Случайное чтение (Random Read):** возникает при поиске данных без подходящих индексов или при работе с «холодными» данными, не помещающимися в кэш.
-   **Последовательная запись (Sequential Write):** запись в журналы транзакций (WAL в PostgreSQL, Redo Log в MySQL). Является критической для производительности операций `INSERT/UPDATE/DELETE`.
-   **Случайная запись (Random Write):** сброс «грязных» страниц данных из оперативной памяти на диск (Checkpoints).
-   **Работа с временными файлами (Temp I/O):** возникает при нехватке оперативной памяти для сортировки (`ORDER BY`), группировки (`GROUP BY`) или хеш-соединений (`Hash Join`). Это часто «невидимый» источник нагрузки, не связанный с объемом самих данных.

Подробная теория задержек и механизмов ожидания процессора описана в разделе **[Низкий iowait при высокой задержке](../Linux/Diagnostics/Performance/DiskIO/iowait_and_latency.md)**.

## Практические сценарии

### Шаг 1: Определение процесса-виновника на уровне ОС

Первым шагом необходимо подтвердить, что именно процесс базы данных является основным потребителем дисковых ресурсов.

```bash
# Просмотр I/O в реальном времени по процессам
sudo iotop -o

# Расширенная статистика по дискам (обновление каждую секунду)
iostat -xz 1

# Детальный анализ задержек конкретных запросов ввода-вывода (требует bcc-tools)
sudo biosnoop
```

**Интерпретация результатов:**

- Если `await` (среднее время ожидания) превышает 10–20 мс для HDD или 1–2 мс для SSD — дисковая подсистема перегружена.
- Если основную нагрузку создают процессы `postgres` или `mysqld`, переходите к анализу внутри БД.
- В облачных средах (AWS, GCP, Azure) обязательно проверьте метрики IOPS Burst (например, `BurstBalance` в AWS CloudWatch). Исчерпание Burst-кредитов приводит к резкому падению производительности диска (throttling), даже если процесс БД не изменил свой профиль нагрузки.
- При использовании **eBPF** (инструменты `biosnoop`, `biolatency`): если поле `LAT` показывает высокие значения только для потоков базы данных, проблема может быть в неэффективной конфигурации планировщика или файловой системы.

### Шаг 2: Анализ нагрузки внутри базы данных

#### PostgreSQL

Для глубокого анализа I/O в PostgreSQL необходимо включить сбор статистики времени ввода-вывода (по умолчанию выключен из-за накладных расходов на системные вызовы времени).

```sql
-- Включение сбора статистики времени I/O (в postgresql.conf или динамически)
SET track_io_timing = on;

-- Поиск запросов с наибольшим временем чтения/записи (требует pg_stat_statements)
SELECT
    query,
    calls,
    total_exec_time / 1000 AS total_sec,
    blk_read_time / 1000 AS read_sec,
    blk_write_time / 1000 AS write_sec,
    temp_blks_read,
    temp_blks_written
FROM pg_stat_statements
ORDER BY (blk_read_time + blk_write_time) DESC
LIMIT 5;
```

**Интерпретация:**
- `blk_read_time` / `blk_write_time`: время, затраченное непосредственно на I/O. Если оно составляет >50% от `total_exec_time`, проблема в диске.
- `temp_blks_read/written`: если значения высоки, необходимо увеличить `work_mem`, чтобы сортировки проходили в памяти.

Для анализа текущих сессий и их ожиданий:
```sql
SELECT pid, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'IO';
-- → result: 1234 | active | IO | DataFileRead | SELECT * FROM large_table...
```

#### MySQL (InnoDB)

Используйте системное представление `sys` для быстрого поиска файлов и таблиц с наибольшей задержкой:

```sql
-- Топ файлов по задержке ввода-вывода
SELECT file, count_read, sum_timer_read, count_write, sum_timer_write
FROM sys.io_global_by_file_by_latency
LIMIT 5;

-- Статистика ожидания по таблицам
SELECT table_schema, table_name, count_read, sum_timer_read, count_write, sum_timer_write
FROM sys.schema_table_statistics_with_buffer
ORDER BY (sum_timer_read + sum_timer_write) DESC
LIMIT 5;
```

Проверьте статус InnoDB на наличие ожидающих операций:
```sql
SHOW ENGINE INNODB STATUS\G
-- Ищите раздел FILE I/O: "OS file reads 100, OS file writes 500, OS fsyncs 200"
-- И "Pending normal aio reads: 10, aio writes: 5"
```

### Шаг 3: Анализ событий ожидания (Wait Events)

Если база данных «вистит», необходимо понять, какого именно типа I/O она ожидает:

| СУБД | Тип ожидания | Описание | Что делать |
| :--- | :--- | :--- | :--- |
| **PostgreSQL** | `DataFileRead` | Чтение данных с диска. | Проверить индексы, увеличить `shared_buffers`. |
| **PostgreSQL** | `WALWrite` | Запись в лог транзакций. | Вынести WAL на отдельный быстрый диск (NVMe). |
| **PostgreSQL** | `BufFileWrite` | Запись во временные файлы. | Увеличить `work_mem`. |
| **MySQL** | `wait/io/file/innodb/data` | Чтение/запись страниц данных. | Оптимизировать запросы, проверить RAID/SSD. |
| **MySQL** | `wait/io/file/innodb/log` | Запись в Redo Log. | Проверить `innodb_flush_log_at_trx_commit`. |


### Шаг 3: Оперативные меры устранения

1. **Добавление индексов:** если запрос выполняет сканирование всей таблицы, создание индекса на столбцы в условии `WHERE` может радикально снизить дисковое чтение. В PostgreSQL используйте `CREATE INDEX CONCURRENTLY` для предотвращения блокировок.
2. **Увеличение буферного кэша:** если в системе есть свободная оперативная память, увеличение `shared_buffers` (PostgreSQL) или `innodb_buffer_pool_size` (MySQL) позволит БД хранить больше данных в RAM.
3. **Оптимизация журналов (WAL/Redo):** если нагрузка идет на запись, проверьте частоту контрольных точек (checkpoints). Слишком частые контрольные точки создают избыточную нагрузку на диск.
4. **Ослабление гарантий записи (в крайнем случае):** для временного ускорения массовой загрузки данных можно отключить синхронную фиксацию транзакций (`synchronous_commit = off` в PostgreSQL). **Внимание:** это создает риск потери последних данных при сбое питания.

### Тюнинг ядра Linux и файловых систем для БД

Правильная настройка ОС позволяет снизить вероятность возникновения «замираний» (I/O Stalls) при интенсивной записи.

1.  **Настройка Writeback (параметры `vm.dirty_*`):**
    *   `vm.dirty_background_ratio`: процент памяти, при достижении которого ядро начинает сбрасывать данные на диск в фоновом режиме. Для БД рекомендуется **5–10%**.
    *   `vm.dirty_ratio`: порог принудительного сброса. При его достижении все процессы блокируются до завершения записи. Рекомендуется **10–20%**.
    *   **Цель:** не допускать накопления огромного объема «грязных» страниц, сброс которых парализует систему.

2.  **Параметры монтирования ФС:**
    *   `noatime, nodiratime`: отключает обновление времени последнего доступа при чтении. Снижает количество операций записи.
    *   `barrier=0` (только для Ext4 с BBU/UPS): отключает барьеры записи. Значительно ускоряет запись, но **опасно** без резервного питания.

3.  **Планировщик ввода-вывода:**
    *   Для SSD/NVMe рекомендуется `none` или `mq-deadline`.
    *   Подробнее: **[Планировщики ввода-вывода](../Linux/Core/kernel/io_schedulers.md)**.

## Дополнительная информация

### Стратегии долгосрочного решения

- **Вертикальное масштабирование:** переход на более быстрые накопители (NVMe SSD) или диски с гарантированным (provisioned) IOPS в облаке.
- **Партиционирование:** разделение гигантских таблиц на части для уменьшения объема данных, сканируемых при одном запросе.
- **Репликация чтения:** вынос аналитических запросов на отдельные реплики для разгрузки основного мастера. См. [Репликация](./Concepts/replication.md).
- **Архивация:** перенос старых данных в холодные хранилища или другие СУБД (например, [ClickHouse](./ClickHouse/clickhouse.md)).
