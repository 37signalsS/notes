# Диагностика дисковых узких мест в базах данных

## Определения

**Дисковое узкое место (I/O Bottleneck)** — состояние, при котором производительность базы данных (БД) ограничивается скоростью дисковой подсистемы (пропускной способностью или временем отклика). В этом состоянии вычислительные ресурсы процессора (CPU) простаивают, ожидая завершения операций чтения или записи данных.

**I/O-bound нагрузка** — тип нагрузки, при которой основным ограничивающим фактором является скорость ввода-вывода (чтение с диска или запись на него), а не вычислительная мощность процессора или объем оперативной памяти.

**События ожидания (Wait Events)** — метрики СУБД, показывающие, на каком именно этапе и какого ресурса ожидает процесс (например, чтение блока данных, запись в лог транзакций или ожидание освобождения буфера).

**Direct I/O vs Buffered I/O:**
- **Buffered I/O (PostgreSQL):** СУБД использует системный кэш страниц (Page Cache). Это упрощает работу с ОС, но может приводить к "двойному буферированию" (Double Buffering) данных в RAM.
- **Direct I/O (MySQL/InnoDB):** СУБД обходит системный кэш (`O_DIRECT`), самостоятельно управляя буферами в оперативной памяти, что снижает накладные расходы на копирование данных и уменьшает задержки.

## Предварительные требования

Перед диагностикой дисковых узких мест убедитесь, что на сервере доступны
необходимые утилиты и привилегии.

**Привилегии:**
- **ОС-уровень:** `sudo` или root — для доступа к `iostat`, `iotop`, `bpftrace`,
  `procfs` (`/proc/pressure/io`, `/proc/<pid>/io`).
- **PostgreSQL:** любая роль с `pg_read_all_stats` (или `pg_monitor`); для
  `track_io_timing` требуется `pg_read_all_settings` или superuser.
- **MySQL:** `PROCESS` + `RELOAD` для `SHOW ENGINE INNODB STATUS\G`; просмотр
  `performance_schema` требует `SELECT` на нужные таблицы или root.

**Утилиты ОС (установить из пакетов):**

| Утилита | Пакет | Назначение |
| :--- | :--- | :--- |
| `iostat` | `sysstat` | Метрики дисков (`%util`, `await`, `avgqu-sz`) |
| `iotop` | `iotop` | Топ процессов по I/O в реальном времени |
| `biosnoop`, `biolatency` | `bcc-tools` или `bpftrace` | eBPF-трассировка задержек I/O |
| `df`, `lsblk`, `mount` | `coreutils`/`procps` | Свободное место, таблица разделов, опции монтирования |

**Настройка СУБД:**
```sql
-- PostgreSQL: включить сбор timing для I/O
-- → postgresql.conf: track_io_timing = on
-- либо динамически (будет сброшено при рестарте):
ALTER SYSTEM SET track_io_timing = on;
-- → Query OK, 1 row affected
SELECT pg_reload_config();
```

```sql
-- MySQL: включить performance_schema для sys-схемы
-- → my.cnf: performance_schema = ON (включено по умолчанию в 8.4)
-- Проверить доступность sys-схемы:
SELECT COUNT(*) FROM sys.io_global_by_file_by_latency;
-- → COUNT(*) = 10 (или аналогичное число файлов)
```

Если утилиты недоступны, используйте минимальный набор `df`, `iostat`
(из `sysstat`) и `SHOW ENGINE INNODB STATUS` — это покрывает 80% типовых
случаев.

## Основные концепции

### Основные симптомы

1.  **Высокий показатель `iowait` (`%wa`):** Процент времени, когда CPU простаивал при наличии активных запросов к диску.
2.  **Pressure Stall Information (PSI):** Современный механизм ядра Linux для оценки влияния диска на задержки приложений. Если `cat /proc/pressure/io` показывает `avg10 > 10.00`, система испытывает критическое давление I/O.
3.  **Рост задержек (Latency):** Увеличение времени выполнения запросов, которые ранее работали быстро.
4.  **Высокая утилизация диска (`%util`):** Диск постоянно занят обработкой запросов (близко к 100% в выводе `iostat`).
5.  **Длинная очередь к диску (`avgqu-sz`):** Большое количество запросов на ввод-вывод ожидает своей очереди на выполнение.
6.  **Наличие процессов в статусе `D` (Uninterruptible Sleep):** Процессы, заблокированные на операциях ввода-вывода.

### Типы дисковой нагрузки в СУБД

В базах данных дисковая нагрузка обычно делится на следующие категории:

-   **Случайное чтение (Random Read):** Возникает при поиске данных без подходящих индексов или при работе с «холодными» данными, не помещающимися в кэш. Критично для OLTP-нагрузок.
-   **Последовательная запись (Sequential Write):** Запись в журналы транзакций (WAL в PostgreSQL, Redo Log в MySQL). Является критической для производительности операций `INSERT/UPDATE/DELETE`.
-   **Случайная запись (Random Write):** Сброс «грязных» страниц данных из оперативной памяти на диск (процесс Checkpoint).
-   **Работа с временными файлами (Temp I/O / Spill to Disk):** Возникает при нехватке оперативной памяти для сортировки (`ORDER BY`), группировки (`GROUP BY`) или хеш-соединений (`Hash Join`). Это часто «невидимый» источник нагрузки, не связанный с объемом самих данных, а зависящий от сложности запросов.

Подробная теория задержек и механизмов ожидания процессора описана в разделе **[Низкий iowait при высокой задержке](../Linux/Diagnostics/Performance/DiskIO/iowait_and_latency.md)**.

## Практические сценарии

### Системный подход к диагностике (Infrastructure -> Application)

Если база данных начинает "тормозить", следуйте методике послойного анализа:

#### 1. Уровень Инфраструктуры: Свободное место и I/O
Первым делом исключите базовые системные ограничения.
- **Дисковое пространство**: Проверьте, не закончилось ли место на разделах с данными или логами.
  ```bash
  df -h
  ```
- **I/O Bottleneck**: Убедитесь, что диск справляется с нагрузкой. Высокий `%util` или `await` в `iostat` указывают на аппаратный предел.
  ```bash
  iostat -xz 1
  iotop -o # Поиск конкретного процесса-виновника
  ```

#### 2. Уровень СУБД: Медленные запросы (Slow Query Logs)
Если инфраструктура в норме, переходите к анализу логов самой базы данных.
- **Включение Slow Log**: Включите логирование запросов, превышающих определенный порог (например, 1 секунда).
- **Анализ логов**: Используйте инструменты типа `pt-query-digest` (для MySQL) или `pgbadger` (для PostgreSQL) для выявления самых тяжелых запросов.
- **MySQL:** полный разбор по шагам — **[Анализ медленных запросов](./MySQL/Operations/slow-query-analysis.md)**; разбор инцидентов по симптомам — **[Диагностический runbook MySQL](./MySQL/troubleshooting-runbook.md)**;
  если `iowait` сочетается с промахами buffer pool и временными таблицами — **[Движки MySQL: InnoDB](./MySQL/Operations/storage_engines_deep_dive.md)**.

#### 3. Уровень Запроса: Анализ плана (EXPLAIN)
Для конкретного медленного запроса необходимо понять, *как* база данных его выполняет.
- **EXPLAIN**: Используйте команду `EXPLAIN` (или `EXPLAIN ANALYZE` для получения реального времени выполнения).
- **На что смотреть**:
  - **Seq Scan / Full Table Scan**: База читает всю таблицу целиком. Требуется индекс.
  - **Temporary Files**: Базе не хватает памяти для сортировки, и она использует диск (см. `work_mem` в PG или `sort_buffer_size` в MySQL).
  - **Index Scan**: Правильно ли выбраны индексы для условий `JOIN` и `WHERE`.

### Шаг 1: Определение процесса-виновника на уровне ОС

Первым шагом необходимо подтвердить, что именно процесс базы данных является основным потребителем дисковых ресурсов.

```bash
# Просмотр I/O в реальном времени по процессам
sudo iotop -o

# Расширенная статистика по дискам (обновление каждую секунду)
iostat -xz 1

# Детальный анализ задержек конкретных запросов ввода-вывода (требует bcc-tools или bpftrace)
sudo biosnoop-bpfcc
sudo biolatency-bpfcc -D 1 10 # Гистограмма задержек
```

**Интерпретация результатов:**

  - Если `await` (среднее время ожидания) превышает 10–20 мс для HDD или 1–2 мс для SSD — дисковая подсистема перегружена.
  - Если основную нагрузку создают процессы `postgres` или `mysqld`, переходите к анализу внутри БД.
  - **eBPF трассировка:** Инструмент `biolatency` позволяет увидеть "хвостовые задержности" (Tail Latency), которые могут быть скрыты за средними значениями `iostat`.

### Шаг 2: Анализ нагрузки внутри базы данных

#### PostgreSQL

Для глубокого анализа I/O в PostgreSQL необходимо включить сбор статистики времени ввода-вывода.

```sql
-- Включение сбора статистики времени I/O (в postgresql.conf или динамически)
SET track_io_timing = on;

-- Поиск запросов с наибольшим временем чтения/записи (требует pg_stat_statements)
SELECT
    query,
    calls,
    total_exec_time / 1000 AS total_sec,
    blk_read_time / 1000 AS read_sec,
    blk_write_time / 1000 AS write_sec,
    temp_blks_read,
    temp_blks_written
FROM pg_stat_statements
ORDER BY (blk_read_time + blk_write_time) DESC
LIMIT 5;
```

**Интерпретация:**
- `blk_read_time` / `blk_write_time`: Время, затраченное непосредственно на I/O. Если оно составляет >50% от `total_exec_time`, проблема в диске.
- `temp_blks_read/written`: Если значения высоки, необходимо увеличить `work_mem`, чтобы сортировки и хеширование проходили в памяти.

Для анализа текущих сессий и их ожиданий:
```sql
SELECT pid, state, wait_event_type, wait_event, query
FROM pg_stat_activity
WHERE wait_event_type = 'IO';
-- → result: 1234 | active | IO | DataFileRead | SELECT * FROM large_table...
```

#### MySQL (InnoDB)

Используйте системное представление `sys` для быстрого поиска файлов и таблиц с наибольшей задержкой:

```sql
-- Топ файлов по задержке ввода-вывода
SELECT file, count_read, sum_timer_read, count_write, sum_timer_write
FROM sys.io_global_by_file_by_latency
LIMIT 5;
-- → result: /var/lib/mysql/ibdata1 | 5000 | 2500000000000 | 3000 | 1500000000000

-- Статистика ожидания по таблицам
SELECT table_schema, table_name, count_read, sum_timer_read, count_write, sum_timer_write
FROM sys.schema_table_statistics_with_buffer
ORDER BY (sum_timer_read + sum_timer_write) DESC
LIMIT 5;
-- → result: shop | orders | 4200 | 2000000000000 | 8100 | 4000000000000
```

Проверьте статус InnoDB на наличие ожидающих операций:
```sql
SHOW ENGINE INNODB STATUS\G
-- Ищите раздел FILE I/O: "OS file reads 100, OS file writes 500, OS fsyncs 200"
-- И "Pending normal aio reads: 10, aio writes: 5"
```

### Шаг 3: Анализ событий ожидания (Wait Events)

Если база данных «висит», необходимо понять, какого именно типа I/O она ожидает:

| СУБД | Тип ожидания | Описание | Что делать |
| :--- | :--- | :--- | :--- |
| **PostgreSQL** | `DataFileRead` | Чтение страниц данных с диска. | Проверить индексы, увеличить `shared_buffers`. |
| **PostgreSQL** | `WALWriteLock` | Запись в лог транзакций (WAL). | Использовать batching, вынести WAL на NVMe. |
| **PostgreSQL** | `RelationExtension` | Расширение файла таблицы. | Проверить конкуренцию при `INSERT`, партиционировать. |
| **PostgreSQL** | `BufFileWrite` | Запись во временные файлы. | Увеличить `work_mem`. |
| **PostgreSQL** | `CheckpointWrite` | Ожидание сброса грязных страниц. | Настроить `checkpoint_completion_target`. |
| **MySQL** | `wait/io/file/innodb/data` | Чтение/запись страниц данных. | Оптимизировать запросы, проверить RAID/SSD. |
| **MySQL** | `wait/io/file/innodb/log` | Запись в Redo Log. | Проверить `innodb_flush_log_at_trx_commit`. |

Подробная шпаргалка по событиям PostgreSQL — **[Wait Events Cheat Sheet](./PostgreSQL/Operations/observability.md#шпаргалка-по-критическим-wait-events)**.

### Шаг 4: Оперативные меры устранения

1. **Добавление индексов:** Если запрос выполняет сканирование всей таблицы (`Seq Scan`), создание индекса на столбцы в условии `WHERE` может радикально снизить дисковое чтение. В PostgreSQL используйте `CREATE INDEX CONCURRENTLY` для предотвращения блокировок.
2. **Увеличение буферного кэша:** Если в системе есть свободная оперативная память, увеличение `shared_buffers` (PostgreSQL) или `innodb_buffer_pool_size` (MySQL) позволит БД хранить больше данных в RAM, снижая `DataFileRead`.
3. **Оптимизация журналов (WAL/Redo):** Если нагрузка идет на запись, проверьте частоту контрольных точек (checkpoints). Слишком частые контрольные точки создают избыточную нагрузку. Увеличение `max_wal_size` в PG помогает растянуть этот процесс.
4. **Ослабление гарантий записи (в крайнем случае):** Для временного ускорения массовой загрузки данных можно отключить синхронную фиксацию транзакций (`synchronous_commit = off` в PostgreSQL или `innodb_flush_log_at_trx_commit = 2` в MySQL). **Внимание:** Это создает риск потери последних секунд данных при сбое питания.

### Тюнинг ядра Linux и файловых систем для БД

Правильная настройка ОС позволяет снизить вероятность возникновения «замираний» (I/O Stalls) при интенсивной записи.

1.  **Настройка Writeback (параметры `vm.dirty_*`):**
    *   `vm.dirty_background_ratio`: Процент памяти, при достижении которого ядро начинает сбрасывать данные на диск в фоновом режиме. Рекомендуется **5–10%**.
    *   `vm.dirty_ratio`: Порог принудительного сброса. При его достижении все процессы блокируются до завершения записи. Рекомендуется **10–20%**.
    *   **Для систем с большим объемом RAM** лучше использовать `vm.dirty_background_bytes` и `vm.dirty_bytes` (например, 256MB и 1GB соответственно), чтобы избежать накопления гигабайтов "грязных" страниц.

2.  **Параметры монтирования ФС:**
    *   `noatime, nodiratime`: Отключает обновление времени последнего доступа при чтении. Снижает количество мета-записей.
    *   `barrier=0` (Ext4): Отключает барьеры записи. **Опасно** без резервного питания (BBU/UPS), но значительно ускоряет запись.
    *   **XFS:** Рекомендуется для баз данных из-за лучшей параллельной обработки I/O. Используйте параметры `logbufs=8,logbsize=256k`.

3.  **Планировщик ввода-вывода:**
    *   Для SSD/NVMe рекомендуется `none` или `mq-deadline`.
    *   Подробнее: **[Планировщики ввода-вывода](../Linux/Core/kernel/io_schedulers.md)**.

## Устранение неисправностей (Troubleshooting)

### Симптом → причина → решение

| Симптом | Диагностика | Причина | Решение |
| :--- | :--- | :--- | :--- |
| `await` > 20 мс (HDD) / > 2 мс (SSD) постоянно | `iostat -xz 1` | Диск на пределе пропускной способности | SSD/NVMe, LVM striping, разнести WAL |
| `avgqu-sz` > 32 | `iostat -xz 1` | Очередь запросов растёт | Уменьшить конкуренцию, добавить диски |
| `%util` = 100% на одном диске, < 50% на другом | `iostat -xz 1` | «Горячий» диск в RAID-массиве | Перераспределить таблицы на файлы |
| Процессы в статусе `D` | `ps aux \| grep ' D'` | Синхронный `fsync()` блокирует | Отключить `barrier=0` (с BBU) или вынести на SSD |
| `vm.swappiness` активно используется | `vmstat 1`, `sar -B` | Нехватка RAM, swap-пэйджинг | Увеличить RAM или снизить `shared_buffers`/`innodb_buffer_pool` |
| `pg_stat_statements`: `blk_read_time` > 50% от `total_exec_time` | Запрос из Шага 2 | Промахи buffer pool → чтения с диска | Добавить индекс или увеличить `shared_buffers` |
| `innodb_buffer_pool_reads` > 1% от `innodb_buffer_pool_read_requests` | `SHOW GLOBAL STATUS` | Hit ratio < 99% → чтения с диска | Увеличить `innodb_buffer_pool_size` |
| `temp_blks_written` растёт | Шаг 2 PostgreSQL | Сортировка в памяти не помещается | Увеличить `work_mem` |
| `wal_keep_size` растёт на реплике | `pg_stat_replication` | Реплика отстаёт, WAL не высвобождается | Проверить I/O реплики через `iostat`, увеличить `max_wal_senders` |

### Требования к устранению

Если после устранения корневой причины (долгая транзакция, нехватка индексов)
метрики не стабилизируются через 5–10 минут — проблема в аппаратном узле.
Используйте **biolatency** для поиска tail latency:

```bash
sudo biolatency-bpfcc 1 10
# → result: [1-2]       : 50 (50% запросов быстро)
# → result: [10-20]     : 30 (30% в норме)
# → result: [100-1000]  : 15 (15% с задержкой > 100 мс — проблемный диск)
```

Если гистограмма показывает хвост за 50–100 мс — это аппаратный предел,
а не проблема запросов или конфигурации СУБД.

## Лучшие практики

**Диагностика — не разовая операция.** После каждого вмешательства:
1. Зафиксировать baseline (`iostat -xz 1 10`, `vmstat 1 10`) до изменений.
2. Применить изменение (индекс, `shared_buffers`, `work_mem`).
3. Сравнить `blk_read_time` / `blk_write_time` до и после — если I/O не
   упало, корень не в диске.

**Разделяйте WAL и данные.** Журнал транзакций (PostgreSQL `pg_wal`, MySQL
`redolog/ib_logfile`) выполняет **последовательную запись** — на нём
критична минимальная задержка. Данные выполняют **случайный доступ** — им
важна пропускная способность. Один диск для обоих создаёт конкуренцию.

**Контролируйте `innodb_flush_method` (MySQL).** В 8.4 значение `O_DIRECT`
(по умолчанию) избегает double buffering. Не используйте `O_DSYNC`, если
только WAL не вынесен на отдельный том с `fsync = on`.

**Отключайте `barrier=0` ТОЛЬКО с BBU/UPS.** Без резервного питания
отключение барьёров записи рискует потерей данных при сбое питания.

**Не держите `track_io_timing` включённым постоянно** на продакшене —
накладные расходы на `clock_gettime()` в некоторых конфигурациях могут
добавлять 1–3% CPU. Включайте на время диагностики, выключайте после.

**Используйте `iostat -xz` с интервалом 1s.** Сокращённая выборка
(например, `iostat -xz 5 3`) скрывает вспышки нагрузки короче 5 секунд.

### Очистка и откат

Все изменения параметров после диагностики должны быть отменены или
зафиксированы:

| Что изменено | Как откатить |
| :--- | :--- |
| `SET track_io_timing = on` (PostgreSQL, runtime) | `ALTER SYSTEM RESET track_io_timing;` + `SELECT pg_reload_config();` |
| `ALTER SYSTEM SET track_io_timing = on` | `ALTER SYSTEM RESET track_io_timing;` |
| `SET GLOBAL innodb_buffer_pool_size = ...` | `SET GLOBAL innodb_buffer_pool_size = <былое значение>;` |
| `SET GLOBAL innodb_io_capacity = ...` | `SET GLOBAL innodb_io_capacity = <былое значение>;` (default в 8.4 = 10000) |
| `sysctl -w vm.dirty_bytes=...` | `sysctl -w vm.dirty_bytes=0;` (сброс в default) |
| `mount -o remount,barrier=1 /data` | `mount -o remount,barrier=1 /data;` |
| `iostat -xz 1` в фоновом режиме | `Ctrl+C` или `kill <PID>` |

Изменения через `ALTER SYSTEM SET` или `sysctl -w` сохраняются в файле
конфигурации и **не сбрасываются при рестарте сервера**. Проверьте:

```sql
-- PostgreSQL: изменение через ALTER SYSTEM сохранилось в файле?
SELECT name, setting, source FROM pg_settings
WHERE name IN ('track_io_timing', 'shared_buffers', 'work_mem');
-- → result: track_io_timing | on | ALTER SYSTEM
```

```bash
# sysctl: изменение сохранилось в /etc/sysctl.d/?
sudo sysctl vm.dirty_ratio vm.dirty_background_ratio
# → vm.dirty_ratio = 20 (если изменялось — удалите из /etc/sysctl.d/)
```

## Дополнительная информация

### Стратегии долгосрочного решения

- **Вертикальное масштабирование:** Переход на более быстрые накопители (NVMe SSD) или диски с гарантированной черезпропускной способностью и минимальной задержкой.
- **Партиционирование:** Разделение гигантских таблиц на части для уменьшения объема данных, сканируемых при одном запросе.
- **Репликация чтения:** Вынос аналитических запросов на отдельные реплики для разгрузки основного мастера. См. **[Репликация](./Concepts/replication.md)**.
- **Архивация:** Перенос старых данных в холодные хранилища или специализированные СУБД для аналитики (например, **[ClickHouse](./ClickHouse/clickhouse.md)**).
- **Подготовка данных (Prewarming):** Использование модулей (например, `pg_prewarm`) для загрузки горячих данных в кэш после перезапуска.
