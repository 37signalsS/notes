# Neo4j: Графовая база данных — обзор

**Актуально для:** Neo4j 2026.09.x. Ветка LTS: Neo4j 5.26.x (поддержка ветки 5 — до июня 2028).

> **Лицензия:** Community Edition — GPLv3 (open source). Enterprise Edition — коммерческая лицензия. Infinigraph — отдельная подписка поверх Enterprise. Различия редакций определяют доступность кластеризации, онлайн-бэкапа, нескольких баз и части Security — см. [Редакции](#редакции-что-доступно-в-какой-редакции).

**Java:** требуется OpenJDK/ZuluJDK/Oracle JDK 21 (начиная с Neo4j 2025.01.0). Начиная с Neo4j 2025.10 поддерживается Java 25. Neo4j 5.26 LTS — последняя версия, работающая на Java SE 17.

## Определения

**Neo4j** — ведущая графовая СУБД с открытым исходным кодом, реализующая модель **LPG (Labeled Property Graph)**. В отличие от реляционных БД, Neo4j хранит данные в виде узлов (Nodes), связей (Relationships) и свойств (Properties), обеспечивая производительность $O(1)$ при обходе связей независимо от общего объема данных (Index-free adjacency).

**DBMS** — экземпляр Neo4j, способный управлять несколькими базами данных. Сама база (database) — контейнер хранения данных; граф — логическая структура внутри неё. Внутри любого экземпляра всегда присутствует служебная база `system` (пользователи, роли, метаданные), которая в Community Edition не удаляется.

**Cypher** — декларативный язык запросов к графам, использующий ASCII-art синтаксис для описания шаблонов (Patterns). С 2025 года язык версионируется отдельно от сервера: **Cypher 5** и **Cypher 25** — см. [Версии языка Cypher](#версии-языка-cypher-и-рантаймы).

**ACID** — Neo4j является полностью транзакционной СУБД, гарантирующей целостность данных даже при сложных графовых мутациях.

**Bolt** — бинарный протокол взаимодействия клиента и сервера Neo4j (порт 7687 по умолчанию). Используется всеми драйверами и `cypher-shell`. Протокол HTTP (порт 7474) существует в основном для Neo4j Browser и REST API, но в драйверах не используется.

**APOC (Awesome Procedures on Cypher)** — стандартная библиотека расширений Neo4j: сотни процедур и функций, покрывающих импорт/экспорт данных, графовые алгоритмы, рефакторинг и интеграции. Входит в поставку Neo4j — JAR лежит в `$NEO4J_HOME/labs`, но для загрузки его нужно перенести в `$NEO4J_HOME/plugins`. Версия APOC должна совпадать с версией Neo4j по году и месяцу (patch может отличаться).

## Модель данных

| Элемент | Правила |
| :--- | :--- |
| **Узел (node)** | Уникальный ID, ноль или более меток (labels), набор свойств, набор связей |
| **Метка (label)** | Именованное и индексируемое множество узлов. Узел может иметь ноль, одну или несколько меток |
| **Связь (relationship)** | Уникальный ID, **ровно один тип**, узел-источник, узел-цель, набор свойств |
| **Свойство (property)** | Пара ключ-значение на узле или на связи |

**Идентификаторы элементов.** Каждый узел и связь имеют `elementId` — строковый идентификатор, уникальный среди узлов и связей в пределах одной транзакции. Внутренние числовые ID **переиспользуются после удаления** узлов и связей, поэтому хранить их в приложении или в выгружаемых данных нельзя — они уедут на другой объект. Legacy-функции `id()` и `node(id)` объявлены устаревшими.

**Схема.** Схема в Neo4j открытая по умолчанию: узел может получить любую метку и любое свойство в любой момент. Целостность поддерживается индексами и ограничениями (constraints): уникальность свойства, существование свойства, тип свойства, ключ узла. Ограничения на существование свойства, тип свойства и ключи узлов — только в Enterprise Edition; базу с ними нельзя открыть в Community Edition.

**Что не поддерживается на уровне модели:** `NULL` в свойствах (отсутствующее свойство и `NULL` — разные вещи, значение `null` удаляет свойство), вложенные map/list как значения свойства не подходят для индексов, у связей не может быть нескольких типов, у узла не может быть родительско-дочерних иерархий «из коробки».

## Сравнение графовых моделей: LPG vs RDF

| Характеристика | LPG (Neo4j) | RDF (Jena, Neptune) |
| :--- | :--- | :--- |
| **Модель** | Узлы + Связи + Свойства на обоих | Тройки (Subject-Predicate-Object) |
| **Язык запросов** | Cypher | SPARQL |
| **Семантика** | Неявная (свойства на связях) | Онтологии (RDFS, OWL) |
| **Производительность** | Index-free adjacency, $O(1)$ на шаг | Зависит от индексов, JOIN-операции |
| **Сценарий** | Транзакционные графы, рекомендации | LOD, онтологии, знаниевые графы с инференцией |

**Neo4j не поддерживает RDF-модель из коробки**, но RDF-данные можно импортировать через APOC или специализированные коннекторы.

## Когда использовать графовую модель

**Подходит:** данные с высокой связностью (3+ уровня вложенности связей), частые обходы графа (BFS/DFS), поиск кратчайших путей, рекомендации, анализ графов.

**Не подходит:** bulk-аналитика (OLAP), временные ряды, простые CRUD без связей, данные с фиксированной схемой без отношений.

**Критерий выбора — форма запроса, а не объём данных.** Если типичный вопрос звучит как «покажи все пути от A до B за N переходов», «найди узлы, связанные с этими тремя более чем через два узла» или «кто сильнее всего влияет на этот сервис», графовая модель даёт качественно другой результат. Если вопрос сводится к фильтрации и агрегации столбцов, реляционная СУБД справится дешевле.

**Практический порог.** Стоимость входа в графовую модель — это изменение способа моделирования и эксплуатации: уходят JOIN, приходят индексы на свойствах-якорях, паттерны обхода и необходимость отслеживать количество `DbHits`. Если граф небольшой и обходы одноуровневые, выигрыш не окупает эти затраты.

## Типовые сценарии применения в инфраструктуре

Графовая модель естественна там, где сущности инфраструктуры определяются через отношения друг с другом, а не через набор столбцов.

| Сценарий | Что моделируется | Типовой запрос |
| :--- | :--- | :--- |
| **CMDB и учёт активов** | Сервисы, хосты, приложения, владельцы, стойки, VLAN-сети | Blast radius падения сервиса: все сущности, достижимые за N переходов |
| **Анализ зависимостей** | Кто от кого зависит — вызовы, очереди, тома, DNS | Все входящие и исходящие зависимости сервиса |
| **Сетевая топология** | Устройства, каналы, VLAN, маршруты, ACL | Путь L2/L3 между двумя хостами,Reachability с учётом правил фильтрации |
| **Инциденты и корреляция** | Алерты, события, деплойменты, изменения конфигурации | Какие алерты и изменения относятся к одному инциденту |
| **Rights и доступ** | Пользователи, роли, группы, ресурсы, разрешения | Все пути от пользователя до ресурса, где есть хотя бы один `ALLOW` |
| **Дерево зависимостей сборки** | Пакеты, модули, репозитории | Blast radius уязвимой версии пакета |

Главная операционная ценность — **blast radius**: заранее вычислить последствия отказа или изменения до того, как он произойдёт. В реляционной модели такой запрос требует рекурсивного CTE и растёт по времени линейно с числом уровней; в Neo4j стоимость определяется размером подграфа, а не всей базы.

## Сравнение с альтернативами

| Система | Модель | Сценарий | Отличие от Neo4j |
| :--- | :--- | :--- | :--- |
| **Neo4j** | LPG, Cypher | Транзакционные графы, рекомендации | Стандарт de facto для графовых БД |
| **Amazon Neptune** | RDF + Gremlin/SPARQL | Облачные графы с семантикой | Управляемый сервис, RDF-натурный |
| **ArangoDB** | Multi-model (граф+документы) | Гибкие схемы, AQL | Multi-model, но слабее в pure-graph |
| **TigerGraph** | LPG, GSQL | Масштабная графовая аналитика | Параллельный обход под аналитические запросы |
| **JanusGraph** | RDF + OLTP | Распределённые графы на JVM | Сложнее в настройке, зависит от бэкенда |

Выбор между ними определяется не самой графовой моделью, а тремя практическими критериями: требуется ли кластеризация и онлайн-бэкап (у JanusGraph и TigerGraph своя эксплуатационная сложность), нужна ли интеграция с RDF/онтологиями, и допустима ли зависимость от внешнего бэкенда хранения.

## Редакции: что доступно в какой редакции

| Возможность | CE | EE |
| :--- | :--- | :--- |
| GPLv3, ACID-транзакции, Cypher, Bolt, драйверы | Да | Да |
| Формат хранения | `aligned` | `block` (по умолчанию), `aligned` |
| Cypher runtime по умолчанию | `slotted` | `pipelined` (+ `parallel` для чтения) |
| Кластеризация, автономный failover | Нет | Да |
| Онлайн-бэкап и восстановление | Нет | Да |
| Несколько баз данных (кроме `system` и базы по умолчанию) | Нет | Да |
| Составные (composite) и шардированные базы | Нет | Да |
| Fine-grained RBAC, доступ по свойствам и подграфам, LDAP/AD, Kerberos | Нет | Да |
| Ограничения: существование свойства, тип свойства, ключ узла | Нет | Да |
| Полный импорт, инкрементальный импорт, store copy | Нет | Да |
| Эндпоинт метрик для Prometheus, Ops Manager | Нет | Да |
| Показ и прерывание выполняющихся запросов, высокопроизводительный кэш | Нет | Да |
| Bloom, GDS Enterprise, CDC | Нет | Да |

**Infinigraph** — специализированная редакция Enterprise с неограниченным горизонтальным масштабированием и автоматическим шардингом; распространяется по отдельной подписке.

**Что это значит на практике.** Community Edition — это полнофункциональная СУБД для одного инстанса: она не «урезанная», она **одноузловая**. В ней нет онлайн-бэкапа (только остановка сервиса и копирование файлов или `neo4j-admin database dump`), нет второстепенных пользователей с гранулярными правами и нет кластера. Если задача требует хотя бы одного из этих трёх свойств, EE — не «улучшение», а требование задачи.

**Community Edition не является бесплатной альтернативой EE для production.** Community собирается с runtime `slotted` (один поток на одно ядро) и форматом `aligned` с пределом $2^{35}$ узлов и связей, тогда как EE даёт `pipelined`, `parallel` для аналитических чтений и формат `block` с пределом $2^{48}$ узлов. Разница видна на тех же данных и том же железе.

## Версии и жизненный цикл релизов

**CalVer вместо SemVer.** Начиная с 2025.01.0 сервер версионируется как `YYYY.MM.Patch`. Патч инкрементируется внутри месяца, поэтому «текущая версия» меняется каждые несколько недель.

**Поддерживается только последний минорный релиз.** Для линеек 5.x и выше политика поддержки одна: актуальна только последняя минорная версия. Практический вывод: **не пинировать production на конкретный CalVer-релиз** — такой релиз выйдет из поддержки через один-два месяца после следующего.

| Линейка | Статус | Окончание поддержки |
| :--- | :--- | :--- |
| **5.26 LTS** | LTS, чекпоент для миграций | Июнь 2028 |
| **2026.09.x** | Текущий релиз | До выхода следующего |
| **4.4** | Legacy, вне поддержки | Ноябрь 2025 |

**Маршрут обновления.** 4.4 → 5.26 LTS → 2025.x/2026.x. Все обновления с версий старше 5.26 обязаны пройти через 5.26 LTS: это чекпоинт-версия. Перед обновлением с 5.26 LTS на любую версию 2025–2026 все базы Enterprise Edition должны быть переведены в формат `block` — иначе производительность после миграции будет ниже ожидаемой.

**Версии документации.** Operations Manual версионируется по версии сервера: `current` (2026.09), `5.26` (LTS), `4.4` (legacy). Переключатель версий находится в шапке документации; URL вида `/docs/operations-manual/current/` всегда указывает на последний релиз, что опасно при копировании команд из документации в продакшен-конфигурацию.

## Версии языка Cypher и рантаймы

**Cypher 5 и Cypher 25.** С Neo4j 2025.06 язык отделён от сервера и версионируется самостоятельно. Cypher 5 — замороженный набор семантики (совместим со всеми запросами, написанными для Neo4j 2025.05 и ранее), получает только исправления и оптимизации. Cypher 25 добавляет новый синтаксис и **изменения существующей семантики** (например, `IS [NOT] LABELED`, удаление возможности ссылаться на свойство другого элемента в том же `MERGE`).

Начиная с **Neo4j 2026.02** поставляемый `neo4j.conf` явно задаёт `db.query.default_language=CYPHER_25`, поэтому новые базы по умолчанию используют Cypher 25. Уже существующие базы сохраняют свой язык: значение фиксируется в момент создания базы, а не глобально. Это критично при миграции — один и тот же текст запроса может вести себя по-разному на старой и новой базе.

```cypher
// Явное переопределение версии языка для конкретного запроса
CYPHER 5 MATCH (n:Person) RETURN count(n);
// → выполняется на семантике Cypher 5 независимо от настройки базы
```

Уровень БД переопределяется через `CREATE DATABASE`/`ALTER DATABASE` и глобально — через `db.query.default_language` в `neo4j.conf`.

**Рантаймы.** Это разные механизмы исполнения плана, а не разные оптимизации одной программы:

| Рантайм | Редакция | Модель исполнения | Когда назначать принудительно |
| :--- | :--- | :--- | :--- |
| **`slotted`** | По умолчанию в CE | Iterator («Volcano»), построчная, один поток | Сравнение с EE, отладка плана в CE |
| **`pipelined`** | По умолчанию в EE | Пакетная (по 128 строк), операторы группируются в пайплайны | Транзакционная нагрузка — обычно лучший выбор |
| **`parallel`** | Только EE | Многопоточная, по всем ядрам сервера | Длинные аналитические **читающие** запросы |

```cypher
// Принудительный выбор рантайма — префикс перед запросом
EXPLAIN CYPHER runtime = slotted MATCH (a)-[:DEPENDS_ON]->(b) RETURN count(*);
// → Planner COST / Runtime SLOTTED / Runtime version 2026.09
```

`parallel` поддерживает только чтение и не работает, если в транзакции уже были изменения; вызов процедуры, не поддерживающей параллельное исполнение, не приводит к ошибке — запрос автоматически уходит на `pipelined`. Потоков workers регулируется параметром `server.cypher.parallel.worker_limit`: `0` — по одному на логический процессор, отрицательное значение `-n` — все минус `n`. Подбор рантайма вручную — последнее средство: сначала `PROFILE` и индексы.

## Форматы хранения

Формат хранения определяет, как элементы графа укладываются в файлы на диске, и вместе с ним — жёсткие лимиты на размер графа.

| Формат | Редакция | Статус | Лимит узлов / связей |
| :--- | :--- | :--- | :--- |
| **`block`** | EE+ | По умолчанию для новых баз (с 5.22) | $2^{48}$ узлов (~281 трлн), связи и свойства без верхней границы |
| **`aligned`** | CE и EE | По умолчанию в CE | $2^{35}$ узлов и связей (~34 млрд), $2^{16}$ типов связей |
| **`high_limit`** | EE | **Устарел в 5.23** | $2^{50}$ узлов и связей (~1 квадриллион) |
| **`standard`** | CE и EE | **Устарел в 5.23** | $2^{35}$ узлов и связей |

**Почему `block` — рекомендуемый формат.** Свойства хранятся в блоках вместе с узлами и связями, а не в отдельных записях с переходами по указателям. Меньше обращений к диску на один запрос, лучше локальность данных, эффективнее расход памяти.

**Проверка текущего формата:**

```cypher
SHOW DATABASES YIELD name, store;
// +----------------------------------+
// | name           | store           |
// +----------------------------------+
// | "neo4j"        | "block-block-1.1"  |
// | "system"       | "record-aligned-1.1" |
// +----------------------------------+
```

**Миграция формата** — операция офлайн, интенсивная по I/O: она переписывает все данные и меняет внутренние ID элементов. Требует места примерно на один размер базы (данные компактифицируются), пересоздаёт индексы при первом старте, а в кластере выполняется через backup/restore на одном сервере с последующим назначением его designated seeder. По документации: 100 ГБ база — от 10 минут в оптимальных условиях до более часа в худших, поэтому перед плановой миграцией обязателен прогон на копии.

**Критичный срок.** Поддержка `standard` и `high_limit` заканчивается вместе с LTS-релизом, запланированным на ноябрь 2026 (поддержка до ноября 2029). После выхода этого LTS-релиза `high_limit`-базы **не запустятся** — совместимого слоя не останется. Все базы в этом формате должны быть переведены в `block` до перехода на него.

## Порты и сетевые коннекторы

| Порт | Протокол | Назначение |
| :--- | :--- | :--- |
| 7687 | Bolt | Драйверы, `cypher-shell` — основной канал приложений |
| 7474 | HTTP | Neo4j Browser, REST API. Трафик не шифруется |
| 7473 | HTTPS | Neo4j Browser и REST API поверх TLS |
| 6362 | Backup | Приём онлайн-бэкапов (Enterprise) |
| 6000 | — | Транзакционный протокол кластера, discovery, клиент бэкапа (Enterprise) |
| 7000 | — | Raft-протокол кластера (Enterprise) |
| 7688 | Bolt Routing | Маршрутизация в кластере (Enterprise) |

Значения настраиваются через `server.bolt.*`, `server.http.*`, `server.https.*`. Параметр `advertised_address` задаёт адрес, который сервер объявляет клиентам, — он обязателен, если порты пробрасываются через reverse proxy или проброску портов, иначе драйвер получит неверный адрес и не сможет подключиться.

Коннекторы можно отключать по отдельности, а HTTP-коннектор в продакшене обычно выключают целиком: приложения ходят по Bolt, а открытый 7474 остаётся неиспользуемой точкой входа.

## Эксплуатационные антипаттерны

**Сверхузлы (hub nodes).** Узел с тысячами связей одного типа вырождается в бутылочное горлышко: каждый обход проходит через него, а последовательные связи хранятся в одном кластере store-файла. В `block`-формате для таких узлов предусмотрен dense store, но стоимость обхода всё равно растёт. Если узел становится хабом — пересмотрите модель: вероятно, это набор узлов, склеенных общим свойством.

**Забытые индексы.** Обход без индекса на стартовом узле сканирует все узлы с меткой. Главный симптом — `NodeByLabelScan` или `DirectedRelationshipTypeScan` в выводе `PROFILE` и `DbHits`, непропорциональный размеру результата.

**Длинные транзакции.** Транзакция, удерживающая блокировки на записи и растущую в памяти транзакционный журнал, приводит к contention и рост latency для всех. Импорт и массовые изменения выполняются пачками в `CALL { } IN TRANSACTIONS`, а не одной транзакцией на весь датасет.

**Недооценённый Page Cache.** Если рабочий набор базы не помещается в Page Cache, обход упирается в I/O и производительность падает на порядки при неизменной нагрузке. Это первое, что проверяется при жалобах на «медленные запросы» после переноса на новое железо.

**Граф вместо СУБД.** Если задача решается одним JOIN или фильтром, графовая СУБД добавляет стоимость эксплуатации (отдельный сервис на JVM, резервное копирование, мониторинг) без выигрыша в запросах.

**Ошибка привязки к внутреннему ID.** Экспорт `id()` в выгрузку и повторный импорт приводит к тихому переназначению связей после удаления объектов. Для внешних ссылок использовать только `elementId()` или собственные бизнес-ключи.
