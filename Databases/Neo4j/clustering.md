# Neo4j: Кластеризация и высокая доступность

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

> **Enterprise Edition.** Вся кластеризация Neo4j — функция Enterprise. В Community Edition есть только одиночный сервер.

> **Causal Clustering больше не существует.** Механизм Causal Clustering из ветки 4.x полностью заменён в Neo4j 5.0. Аппарат `neo4j-admin database cluster ...` (check, forget, reindex, safepoint) из 4.x отсутствует: администрирование кластера перенесено в Cypher-команды (`SHOW SERVERS`, `CREATE DATABASE`, `ENABLE SERVER`) и в процедуры префикса `dbms.cluster`. Миграция 4.4 → 5.x для кластера выполняется только пересборкой с нуля.

## Определения

Ключевое отличие кластера Neo4j 5+ от его предшественника: **серверы и базы данных разделены**. Сервер — это вычислительный и storage-ресурс без роли; роль принадлежит *копии базы данных*, размещённой на сервере.

**Server** — физическая машина, ВМ или контейнер с запущенным экземпляром Neo4j. Сервер может быть частью кластера, а может быть standalone. В Neo4j 5+ standalone — это просто кластер размера 1, отдельного режима работы не существует.

**Database** — контейнер хранения; копия базы может быть размещена на нескольких серверах.

**Primary** — копия базы, участвующая в обработке записей и имеющая право быть избранной лидером. Только primary участвует в формировании кворума при подтверждении записи.

**Leader** — один из primary выбранный Raft-протоколом в качестве писателя. Он принимает все write-транзакции, синхронно реплицирует их остальным primary и асинхронно — secondaries. Лидер выбирается автоматически и может меняться. Если кластер содержит несколько баз, у каждой базы **своя логически отдельная Raft group со своим лидером**, поэтому один сервер может быть leader'ом одной базы и follower'ом другой.

**Follower** — primary, который принимает и подтверждает синхронные записи от leader'а.

**Secondary** — копия базы, реплицируемая асинхронно (shipping транзакционных логов) методом опроса upstream-членов. Служит для масштабирования чтения; по умолчанию всегда read-only.

**Raft group** — группа серверов, участвующих в размещении конкретной базы в primary-режиме. Один сервер может состоять в нескольких Raft group.

**Raft log** — общий лог группы, содержащий и данные, и её операционное состояние.

**Topology** — конфигурация распределения копий базы по серверам: сколько primary и сколько secondary.

**modeConstraint** — ограничение сервера: `PRIMARY`, `SECONDARY` или `NONE` (без ограничений). Значение `NONE` позволяет разместить на сервере и primary, и secondary разных баз.

**Allocator** — компонент кластера, распределяющий базы по серверам с учётом topology-ограничений, `modeConstraint` и стратегии распределения.

**Reconciler** — внутренний компонент каждого сервера, который наблюдает *запрошенное* состояние в `system` и приводит локальный сервер к нему.

**Bookmark** — маркер, который клиент передаёт, чтобы гарантировать чтение собственных записей (causal consistency). Серверы, не обработавшие bookmark, не обслуживают такую транзакцию.

**Routing table** — таблица, выдаваемая сервером драйверу: какие серверы являются `writers`, `readers` и `routers` для конкретной базы.

**Seed** — дамп или полный бэкап, из которого создаётся база в кластере.

### Устаревшая терминология

Словарь Neo4j 4.x и соответствующие термины Neo4j 5+:

| Neo4j 4.x | Neo4j 5+ | Что изменилось по сути |
| :--- | :--- | :--- |
| Causal Cluster | Cluster | Другая архитектура: базы отделены от серверов, размещение автоматическое |
| Core server | Primary | Core был особым типом сервера; primary — роль *копии базы* |
| Read replica | Secondary | То же самое, но роль копии, а не тип сервера |
| Standalone | Кластер размера 1 | Отдельного режима нет, открываются дополнительные порты |
| `neo4j-admin database cluster ...` | Cypher-команды и `dbms.cluster.*` | CLI-подкоманды кластера удалены |

## Архитектура

### Как работает репликация

Запись проходит три стадии:

1. **Лидер принимает** write-транзакцию и реплицирует её follower-ам **синхронно** по протоколу Raft.
2. **Коммит** завершается только когда подтверждение получено от кворума primary (учитывая самого лидера). Это даёт и доступность записи, и долговечность: подтверждённое изменение есть минимум у большинства.
3. **Secondaries** получают изменения асинхронно, опрашивая выбранный upstream-член. Они **могют отставать**: только что закоммиченная транзакция может быть на secondary ещё не видна.

Отсюда следует правило: если чтение сразу после записи обязано видеть эту запись, нужна причинная согласованность (bookmark) — вторая копия без bookmark не ответит.

### Отказоустойчивость

Ключевое правило: запись подтверждается **большинством primary** в конкретной базе. Отсюда прямо следует, что primary нечётны в рабочей конфигурации — при чётном числе отказ на половину primary всё равно оставит базу без кворума.

Проверка «безопасно ли выключать этот primary» formulируется в терминах Raft, а не в терминах «сколько копий осталось»: primary считается безопасным для остановки, когда **большинство остальных primary** здоровы, догнали лидер и недавно слышали от него. Именно это даёт `/db/<database>/cluster/status`.

**Три primary** — базовый вариант: переживает отказ одного члена без потери записи и данных, а не-writer primary дают ёмкость чтения. **Пять primary** — переживает отказ любых двух. Границы заданы самим продуктом: `initial.dbms.default_primaries_count` допускает значения от 1 до 11, `initial.dbms.default_secondaries_count` — от 0 до 20.

Практический след: чем больше primary, тем больше сетевых раундов на каждую запись, поэтому primary не стоит наращивать «про запас» — добавляйте secondaries.

Остановка процесса Neo4j ради обновления бинарников или вывода сервера из эксплуатации **считается отказом**. Значит, чтобы обновляться без downtime, нужна избыточность.

Вторых копий жёсткого правила нет: их добавляют, пока не достигнут нужной производительности чтения.

### Типовые топологии

| Топология | Что даёт | Чего не даёт |
| :--- | :--- | :--- |
| 1 primary | Минимальная задержка записи | Никакой отказоустойчивости. Потеря копии = потеря данных |
| 3 primary | Отказ одного члена без потери записи и данных. Не-writer primary дают ёмкость чтения | После второго отказа запись невозможна, чтение ещё доступно на последнем члене |
| 5 primary | Отказ любых двух primary | Больше сетевых раундов на каждую запись |
| 1 primary + N secondary | Масштабирование чтения; чтение переживает потерю primary | Запись не отказоустойчива: потеря primary = потеря записи |
| 3 primary + N secondary | Отказ любой одной копии не влияет ни на запись, ни на чтение, ни на долговечность | При отказе всех secondary не-writer primary подхватывают чтение сами |

По умолчанию read-запросы **не** маршрутизируются на writer — он сосредоточен на записи и не тратит ресурсы на два типа взаимодействия. Управляется параметрами `dbms.routing.reads_on_primaries_enabled` и `dbms.routing.reads_on_writers_enabled`.

### Балансировка лидерств

Write-транзакции всегда идут на leader соответствующей базы, поэтому неравномерное распределение лидерств перекашивает нагрузку. Neo4j решает это автоматически, перенося лидерства так, чтобы они были распределены равномерно. Дополнительно лидерства автоматически переносятся **с** серверов, где базы помечены read-only через `server.databases.read_only`.

### База `system`

`system` хранит представление о кластере: какие серверы и базы существуют, где они размещены и как настроены. Она может быть в primary- или secondary-режиме, но её режим задаётся **не** через Cypher, а параметром `server.cluster.system_database_mode` в `neo4j.conf` до старта процесса. Значение по умолчанию — `PRIMARY`.

Рекомендации по размещению:

- Устойчивые, долгоживущие серверы — кандидаты на primary `system`.
- Эфемерные и часто меняемые — на secondary.
- Один primary `system` не даёт отказоустойчивости записи, поэтому в типовом развёртывании начинают с трёх.
- Первичных копий `system` не должно быть больше, чем у пользовательских баз: объём записи мал, поэтому лишние primary там не нужны.

### Порты кластера

| Порт | Параметр | Назначение |
| :--- | :--- | :--- |
| 6000 | `server.cluster.listen_address` / `server.cluster.advertised_address` | Transaction shipping и discovery. **Этим же портом можно подключиться клиенту бэкапа** — доступ следует ограничивать firewall'ом и SSL-политикой |
| 7000 | `server.cluster.raft.listen_address` / `server.cluster.raft.advertised_address` | Обмен Raft-сообщениями |
| 7688 | `server.routing.listen_address` / `server.routing.advertised_address` | Server-side routing |
| 7687 | `server.bolt.*` | Bolt — основной канал приложений |
| 6362 | — | Приём онлайн-бэкапов |

Полный список портов и правила их сетевой изоляции — в [обзоре](./overview.md#порты-и-сетевые-коннекторы) и [безопасности](./security.md).

## Практические сценарии

### Развёртывание кластера из трёх серверов

**Предпосылки:** Neo4j Enterprise Edition на всех серверах, одинаковая версия, открытые между серверами порты 6000 и 7000, адреса, резолвящиеся в DNS. Имена в примере: `server01.example.com`, `server02.example.com`, `server03.example.com`. Конфигурация идентична на всех трёх, кроме `server.default_advertised_address`.

```properties
# server01.example.com — server02 и server03 отличаются только этой строкой
server.default_listen_address=0.0.0.0
server.default_advertised_address=server01.example.com
dbms.cluster.endpoints=server01.example.com:6000,server02.example.com:6000,server03.example.com:6000
initial.dbms.default_primaries_count=3
```

Порядок старта не важен — серверы найдут друг друга при первом запуске.

**Проверка после старта.** Подключиться к любому экземпляру:

```cypher
SHOW SERVERS;
```

```text
+-----------------------------------------------------------------------------------------------------------+
| name                                   | address          | state     | health      | hosting             |
+-----------------------------------------------------------------------------------------------------------+
| "d6fbe54b-0c6a-4959-9bcb-dcbbe80262a4" | "server01:7687" | "Enabled" | "Available" | ["system", "neo4j"] |
| "e56b49ea-243f-11ed-861d-0242ac120002" | "server02:7687" | "Enabled" | "Available" | ["system", "neo4j"] |
| "73e9a990-0a97-4a09-91e9-622bf0b239a4" | "server03:7687" | "Enabled" | "Available" | ["system", "neo4j"] |
+-----------------------------------------------------------------------------------------------------------+
```

Подробности — `SHOW SERVERS YIELD *`; столбец `version` показывает, что все члены на одной версии (при разнице версий кластер не соберётся корректно).

Если разворачивается кластер всего из **двух** серверов, на всех них нужно явно выставить `dbms.cluster.minimum_initial_system_primaries_count=2` — иначе порог в 3 сервера не будет достигнут.

### Обнаружение серверов (discovery)

Новый член должен знать адреса хотя бы части существующих серверов. Способ задаётся параметром `dbms.cluster.discovery.resolver_type`.

| Значение | Как работает | Требования |
| :--- | :--- | :--- |
| `LIST` | Статический список в `dbms.cluster.endpoints` | Список устаревает при замене серверов на другие адреса |
| `DNS` | A-записи домена возвращают IP всех членов | Порт discovery должен быть одинаков на всех серверах |
| `SRV` | Одна SRV-запись возвращает адреса и порты | `dbms.cluster.endpoints` = одно доменное имя, порт `0` |
| `K8S` | List Service API по label selector | Service account с правом list services; `server.default_advertised_address` должен в точности совпадать с внутренним DNS-именем вида `<service>.<namespace>.svc.cluster.local` |

Дополнительные параметры для `K8S`: `dbms.kubernetes.label_selector` и `dbms.kubernetes.discovery.service_port_name`. При `K8S` значение `dbms.cluster.endpoints` игнорируется.

Для `LIST` адреса всех членов кластера, включая текущий сервер, перечисляются в `dbms.cluster.endpoints` на каждом сервере. В список **обязательно** входят все серверы, размещающие `system` в primary-режиме.

Отдельная тонкость: `dbms.cluster.discovery.resolver_type=LIST` с пустым `dbms.cluster.endpoints` трактуется как развёртывание standalone, и порог `dbms.cluster.minimum_initial_system_primaries_count` игнорируется.

Для IPv6 все адреса заключаются в квадратные скобки:

```properties
server.default_advertised_address=[2001:db8::1]
server.default_listen_address=[::]
dbms.cluster.endpoints=[2001:db8::1]:6000,[2001:db8::2]:6000,[2001:db8::3]:6000
```

### Переход с standalone на кластер

Механика — перенос дампа `system` на остальные серверы.

1. Остановить standalone-сервер.
2. Добавить в его `neo4j.conf` discovery-эндпоинты всех трёх серверов и `initial.dbms.default_primaries_count=3`.
3. Сделать дамп `system`:
   ```bash
   bin/neo4j-admin database dump system --to-path=/full/path/to/dumps/
   ```
4. Загрузить дамп на два новых сервера:
   ```bash
   bin/neo4j-admin database load --from-path=/full/path/to/dumps system
   ```
5. Запустить все серверы. Новые покажутся в состоянии `Free`:
   ```cypher
   SHOW SERVERS;
   ```
```text
| name                                   | address          | state   | health      | hosting             |
+-----------------------------------------------------------------------------------------------------------+
| "d6fbe54b-0c6a-4959-9bcb-dcbbe80262a4" | "server01:7687" | "Enabled"| "Available" | ["system", "neo4j"] |
| "e56b49ea-243f-11ed-861d-0242ac120002" | "server02:7687" | "Free"   | "Available" | ["system"]          |
| "73e9a990-0a97-4a09-91e9-622bf0b239a4" | "server03:7687" | "Free"   | "Available" | ["system"]          |
+-----------------------------------------------------------------------------------------------------------+
```
6. Включить новые серверы и расширить топологию баз:
   ```cypher
   ENABLE SERVER 'e56b49ea-243f-11ed-861d-0242ac120002';
   ALTER DATABASE neo4j SET TOPOLOGY 3 PRIMARIES;
   ```

### Создание базы с заданной топологией

```cypher
CREATE DATABASE foo TOPOLOGY 3 PRIMARIES 2 SECONDARIES
```

Команда сама размещает базу — вызывать `REALLOCATE DATABASES` после неё не нужно. Команда завершается ошибкой, если серверов недостаточно или их `modeConstraint` не позволяет собрать запрошенную топологию.

Если `TOPOLOGY` не указан, применяются `initial.dbms.default_primaries_count` и `initial.dbms.default_secondaries_count` — по умолчанию **1** и **0** соответственно. Поэтому в базовом кластере из трёх серверов без явного `TOPOLOGY` база создастся с одной primary; строка `initial.dbms.default_primaries_count=3` в примере выше существует именно ради этого. Явный `TOPOLOGY` переопределяет оба.

Изменить топологию существующей базы:

```cypher
ALTER DATABASE foo SET TOPOLOGY 2 PRIMARIES 1 SECONDARY
```

Возможные значения `currentStatus` в `SHOW DATABASES`: `online`, `offline`, `starting`, `stopping`, `store copying`, `initial`, `deallocating`, `dirty`, `quarantined`, `unknown`.

**Важное ограничение.** Автоматический переход к топологии с единственным primary невозможен — команда вернёт ошибку. Переход выполняется вручную: бэкап → `DROP DATABASE` → создание с новой топологией из этого бэкапа. Обратный переход (single primary → несколько primary) автоматический, но база на короткое время недоступна.

Значения по умолчанию для новых баз меняются на лету, а параметры `initial.*` в `neo4j.conf` этого не умеют. Процедура требует `Admin Only`:

```cypher
CALL dbms.setDefaultAllocationNumbers(3, 2, 0);
CALL dbms.showTopologyGraphConfig();
```

Третий аргумент — `propertyShardReplicas` — появился только в 2025.12 вместе с Cypher 25. В Cypher 5 процедура принимает два аргумента, и вызов с тремя завершится ошибкой.

### Приём консолидации: `WAIT`

Административные операции выполняются **асинхронно**. Команда сначала пишет запрошенное состояние в `system`, а каждый сервер применяет его своим reconciler'ом, когда becomes aware. Успешный ответ означает только, что запрос закоммичен в `system` — не то, что он выполнен везде.

```cypher
CREATE DATABASE foo WAIT
```

Ключевое слово `WAIT` заставляет оператор ждать, пока все серверы увидят транзакцию и их reconciler обработает её. Это **не гарантия успеха**: запрос запуска базы считается обработанным, даже если база упала в `dirty`.

Аргумент `WAIT n SECOND[S]` задаёт таймаут ожидания; `NOWAIT` — противоположное поведение.

Ошибка на части серверов не проваливает операцию целиком: база может работать, просто с меньшей отказоустойчивостью, чем планировалось.

### Планирование rolling upgrade

HTTP-эндпоинт статуса существует именно для этой задачи — он показывает, насколько безопасно выводить конкретный primary:

```bash
curl -s localhost:7474/db/neo4j/cluster/status | python3 -m json.tool
```

```text
{
 "lastAppliedRaftIndex":0,
 "votingMembers":["30edc1c4-519c-4030-8348-7cb7af44f591","80a7fb7b-c966-4ee7-88a9-35db8b4d68fe","f9301218-1fd4-4938-b9bb-a03453e1f779"],
 "memberId":"80a7fb7b-c966-4ee7-88a9-35db8b4d68fe",
 "leader":"30edc1c4-519c-4030-8348-7cb7af44f591",
 "millisSinceLastLeaderMessage":84545,
 "participatingInRaftGroup":true,
 "core":true,
 "isHealthy":true,
 "raftCommandsPerSecond":124
}
```

Параметры `leader`, `votingMembers` и `millisSinceLastLeaderMessage` относятся к Raft **конкретной базы**, поэтому у каждой базы свои значения.

Обратите внимание: Cypher-административные команды **нельзя выполнять во время rolling upgrade**.

## Управление серверами

### Жизненный цикл сервера

| Состояние | Значение | Дальнейшие действия |
| :--- | :--- | :--- |
| `Free` | Обнаружен discovery-сервисом, но не включён в кластер. Имя по умолчанию равно сгенерированному server ID. Базы размещаться не могут | `ENABLE SERVER` |
| `Enabled` | Полноценный член кластера, может принимать базы | `ALTER SERVER`, `DEALLOCATE ... FROM SERVERS` |
| `Cordoned` | Хостит текущие базы, но новые ему не назначаются. Применяется при разборе инцидентов | `ENABLE SERVER` для возврата |
| `Deallocating` | Убирает свои базы на другие серверы. Необратимый переход | Дождаться `Deallocated` |
| `Deallocated` | Кроме `system` ничего не хостит, можно удалять | `DROP SERVER` |
| `Dropped` | Удалён из кластера, но процесс ещё работает и виден другим членам | Остановить процесс |

При уменьшении числа размещений базы первыми снимаются размещения с cordoned-серверов.

Известная особенность: ранее deallocated сервер, который был выключен, при старте может на короткое время показать состояние `Deallocating` — затем он вернётся в `Deallocated` без вмешательства.

### Добавление сервера

На новом сервере настроить discovery, режим `system` и, при необходимости, значения по умолчанию для `ENABLE SERVER`:

```properties
server.default_listen_address=0.0.0.0
server.default_advertised_address=server07.example.com
dbms.cluster.discovery.resolver_type=LIST
dbms.cluster.endpoints=server01.example.com:6000,server02.example.com:6000,server03.example.com:6000,server04.example.com:6000,server05.example.com:6000,server06.example.com:6000,server07.example.com:6000
server.cluster.system_database_mode=PRIMARY
initial.server.tags=eu,eu-west
```

Режим `system` выбирается по назначению сервера: `PRIMARY` для долгоживущего сервера под транзакционную нагрузку, `SECONDARY` для аналитики и read-heavy задач.

После старта сервер появится в `Free`, и его нужно включить, взяв ID из вывода:

```cypher
SHOW SERVERS;
```

```cypher
ENABLE SERVER '25a7efc7-d063-44b8-bdee-f23357f89f01' OPTIONS
  {modeConstraint:'PRIMARY', allowedDatabases:['foo'], tags:['eu','eu-west']};
```

Опции `ENABLE SERVER` перекрывают значения `initial.server.*` при конфликте:

| Опция | Допустимые значения | Назначение |
| :--- | :--- | :--- |
| `modeConstraint` | `PRIMARY`, `SECONDARY`, `NONE` | В каких режимах серверу разрешено хостить базы |
| `allowedDatabases` | список имён, с 2025.12 — wildcard-паттерны | Какие базы разрешено хостить. Несовместимо с `deniedDatabases` |
| `deniedDatabases` | список имён, с 2025.12 — wildcard-паттерны | Какие базы запрещено хостить. Несовместимо с `allowedDatabases` |
| `tags` | список строк | Метки для политик балансировки и маршрутизации |

Пустой `allowedDatabases` означает, что разрешены все базы. Имена в обоих списках — паттерны длиной 1–63 символа из букв, цифр, точек, вопросительных знаков, звёздочек и дефисов (набор символов расширен в 2025.12). Упоминание базы по тегу **не** означает членства в группе: сервер с тегом `gb-london` не попадает в группу тега `gb`, если у него нет и `gb`.

Автоматическое включение свободных серверов:

```properties
initial.dbms.automatically_enable_free_servers=true
```

либо на лету:

```cypher
CALL dbms.cluster.setAutomaticallyEnableFreeServers(true);
```

Ограничения: `tags` не могут содержать дубликаты и запятые; `allowedDatabases`/`deniedDatabases` не влияют на композитные базы — те доступны везде. Теги, требующие символов вне Latin1 (китайский, арабский), задавайте через Cypher: `.conf`-файлы читаются в Latin1, либо выставляйте `NEO4J_CONFIG_FILE_CHARSET=utf8`. Имя `RENAME SERVER` должно быть уникальным; ID сервера при переименовании не меняется.

`ALTER SERVER` требует привилегии `SERVER MANAGEMENT`. Всегда сверяйте текущую конфигурацию через `SHOW SERVERS YIELD *` и переносите в `SET OPTIONS` те опции, которые не меняете, — они заменяются целиком, а не дополняются.

Изменение опций существующего сервера и переименование:

```cypher
ALTER SERVER 'server07' SET OPTIONS {modeConstraint:'PRIMARY', tags:['eu','eu-west']};
RENAME SERVER 'server07' TO 'eu-1';
```

### Удаление сервера из кластера

Порядок обязателен: сначала увести базы, потом удалять сервер.

```cypher
-- 1. Dry run — посмотреть, что переедет
DRYRUN DEALLOCATE DATABASES FROM SERVERS 'server07';

-- 2. Выполнить
DEALLOCATE DATABASES FROM SERVERS 'server07';

-- 3. После того как сервер дошёл до Deallocated
DROP SERVER 'server07';
```

`DROP SERVER` требует состояния `Deallocated`. Пока процесс Neo4j на удалённом сервере запущен, он остаётся видимым в состоянии `Dropped` и окончательно исчезает после остановки процесса. Вернуться в кластер после `DROP SERVER` сервер не может.

Чтобы то же железо снова вошло в кластер, нужно сбросить установку Neo4j — переустановкой или командой:

```bash
# Server process must be shut down first
bin/neo4j-admin server unbind
```

`unbind` сохраняет все store-файлы баз, но сервер при следующем старте считается **совершенно новым** с новым server ID — он не подхватит ни одну из прежних баз. Назначение аллокатора этому серверу гарантий не даёт, возможны осиротевшие store-файлы.

Ограничения `unbind`, которые важно знать заранее:

- Процесс Neo4j должен быть остановлен.
- Запуск на нескольких серверах сразу может привести к **потере кворума**.
- В 2025.x `unbind` **не умеет** превращать член кластера в standalone. Правильный путь — снять бэкапы, поднять standalone и восстановить базы из бэкапов.

Архивирование состояния кластера перед сбросом:

```bash
bin/neo4j-admin server unbind --archive-cluster-state=true --archive-path=/path/to/archive-folder
# → unbound_cluster_state.<YYYYMMDDHH24MM>.zip
```

## Размещение и балансировка баз

Включённый сервер не начинает хостить базы автоматически. Это происходит, только если создаются новые базы, меняется топология существующих, другой сервер переводится в `Deallocating`, либо выполняется явная перебалансировка.

### Deallocate — разгрузить конкретный сервер

Процедуры деаллоцируют базы, **не** переводя сервер в состояние `deallocating`. Обратимы — в отличие от `DEALLOCATE DATABASES FROM SERVERS`.

```cypher
CALL dbms.cluster.deallocateDatabaseFromServer("server01", "baz", true);   -- dry run
CALL dbms.cluster.deallocateDatabaseFromServer("server01", "baz");
CALL dbms.cluster.deallocateDatabaseFromServers(["server01","server02"], "baz", true);
CALL dbms.cluster.deallocateNumberOfDatabases("server01", 3, true);
```

### Reallocate — перебалансировать кластер

```cypher
CALL dbms.cluster.reallocateDatabase("baz", true);           -- dry run
CALL dbms.cluster.reallocateDatabase("baz");
CALL dbms.cluster.reallocateNumberOfDatabases(3, true);
```

Если кластер уже сбалансирован, процедура ничего не делает. На больших кластерах `REALLOCATE DATABASES` за один раз может переместить слишком много размещений и нагрузить кластер — безопаснее делать это порциями через `dbms.cluster.reallocateNumberOfDatabases` с небольшим числом, давая базам завершить переезд.

Предпросмотр cluster-level:

```cypher
DRYRUN REALLOCATE DATABASES;
```

```text
+----------------------------------------------------------------------------------------------------------------------------------------+
| database | fromServerName | fromServerId | toServerName | toServerId | mode |
+----------------------------------------------------------------------------------------------------------------------------------------+
| "bar" | "server-1" | "00000000-27e1-402b-be79-d28047a9418a" | "server-5" | "00000003-b76c-483f-b2ca-935a1a28f3db" | "primary" |
| "bar" | "server-3" | "00000001-7a21-4780-bb83-cee4726cb318" | "server-4" | "00000002-14b5-4d4c-ae62-56845797661a" | "primary" |
```

## Маршрутизация

### Клиентская маршрутизация

Работает через схему URI `neo4j://`. Драйвер при первом подключении получает routing table и обновляет её по TTL, который сообщает сервер, либо досрочно, если таблица выглядит устаревшей — например, запись была отклонена с ошибкой «not able to write», потому что роль writer'а уехала на другой сервер.

При схеме `bolt://` драйвер **не маршрутизирует** ничего и подключается напрямую к указанному хосту.

TTL таблицы маршрутизации задаётся параметром `dbms.routing_ttl`, значение по умолчанию — **5 минут** (минимум 1s).

### Параметры маршрутизации

| Параметр | По умолчанию | Назначение |
| :--- | :--- | :--- |
| `dbms.routing_ttl` | `5m` | Как долго клиент кэширует routing table |
| `dbms.routing.reads_on_primaries_enabled` | `true` | Включать ли non-writer primary в read-эндпоинты. Если secondaries нет, primary вернутся как read-эндпоинты в любом случае |
| `dbms.routing.reads_on_writers_enabled` | `false` | Включать ли writer в read-эндпоинты. Если других членов нет, writer вернётся в любом случае |
| `dbms.routing.enabled` | — | Server-side routing; требуется на каждом члене |
| `dbms.routing.default_router` | `CLIENT` | Стратегия для `neo4j://`. `SERVER` шортиртит клиентскую маршрутизацию и передаёт клиенту таблицу с одной записью, делая поведение члена похожим на standalone |
| `dbms.routing.client_side.enforce_for_domains` | — | Всегда использовать клиентскую маршрутизацию для перечисленных доменов, независимо от `default_router`. Список через запятую, поддерживает wildcards `*` |

Server-side routing включается отдельно на каждом члене: `dbms.routing.enabled=true`, плюс `server.routing.listen_address` и `server.routing.advertised_address`. При значении `default_router=CLIENT` (по умолчанию) клиентская маршрутизация используется всегда, а server-side routing выступает как fallback; чтобы опираться на него как на основной, нужен `default_router=SERVER`. Драйверы используют server-side routing только с `neo4j://`; HTTP API каждого члена получает эти настройки автоматически. Шифрование канала server-side routing задаётся SSL-политикой `cluster`.

### Политики маршрутизации

Политика фильтрует множество серверов для каждой категории. Синтаксис — набор правил, вычисляемых по порядку; правило, давшее непустой результат, становится итоговым:

```text
rule1; rule2; rule3
```

Каждое правило — цепочка фильтров, причём **каждое правило начинается с полного множества** доступных серверов:

```text
filter1 -> filter2 -> filter3
```

| Фильтр | Смысл |
| :--- | :--- |
| `tags(name1, name2, …)` | Проходят серверы с любым из указанных тегов. До 5.4 назывался `groups()` — работает, но устарел |
| `roles()` (с 2025.12) | Фильтр по роли копии: `writer` (primary-лидер), `follower` (остальные primary), `secondary` |
| `min(count)` | Разрешить прохождение минимальному числу серверов (или ни одному) — управление перегрузкой |
| `all()` | Неявный фильтр в начале каждого правила и неявный последний фильтр |
| `halt()` | Только как последний фильтр последнего правила — прекращает обработку остальных правил |

`tags(A,B)` — это OR-фильтр (объединение). AND-фильтр получается цепочкой `tags(A) -> tags(B)` (пересечение). Если ни одно правило не дало непустого результата, драйвер получает сигнал об ошибке.

```properties
# Только north1, и только если там есть минимум два сервера
dbms.routing.load_balancing.config.server_policies.north1_only=\
tags(north1)->min(2); halt();

# Предпочесть north1/north2, затем весь север, затем весь кластер
dbms.routing.load_balancing.config.server_policies.north_app1=\
tags(north1,north2)->min(2);\
tags(north);\
all();
```

Политики хранятся в свойстве `dbms.routing.load_balancing.config.server_policies.<policy-name>`. Имя чувствительно к регистру, допускает буквы, цифры и подчёркивание. `default` — зарезервированное имя политики по умолчанию, и её значение по умолчанию — `all()`.

**Два жёстких требования:**

1. Набор политик должен быть **идентичен на всех серверах** — это cluster-wide конфигурация, расхождение даёт непредсказуемое поведение.
2. Политики под активным именем нельзя удалять или переименовывать — это ломает приложения, которые их запрашивают. Менять содержимое под тем же именем можно и нужно.

Если драйвер запрашивает несуществующее имя политики, он не сможет работать с кластером. Драйвер без имени получает все доступные серверы.

Сам параметр `dbms.routing.load_balancing.plugin=server_policies` объявлен **устаревшим в 2025.05**.

### Встроенные политики (с 2025.12)

Настраиваются теми же двумя параметрами, что и политики пользователя:

| Политика | Поведение | Конфигурация |
| :--- | :--- | :--- |
| `builtin_default` | Предпочитает non-writer primary и secondaries; откатывается на writer | `reads_on_primaries_enabled=true`, `reads_on_writers_enabled=false` |
| `builtin_all` | Writer, non-writer primary и secondaries | `reads_on_primaries_enabled=true`, `reads_on_writers_enabled=true` |
| `builtin_add_writer` | Writer и secondaries; при отсутствии — тегированные secondaries, затем writer и non-writer primary | `reads_on_primaries_enabled=false`, `reads_on_writers_enabled=true` |
| `builtin_prefer_secondaries` | Secondaries, затем non-writer primary, затем writer | `reads_on_primaries_enabled=false` |

### Catch-up стратегии для secondary

Catch-up стратегии задают правила выбора upstream-члена, от которого secondary тянет транзакционные логи. Как только стратегия выбрала удовлетворительный upstream, он используется для **одной** синхронизации; для следующей процедура повторяется — так всегда выбирается наиболее предпочтительный доступный upstream.

## Мониторинг и диагностика

### SHOW SERVERS

По умолчанию пять столбцов: `name`, `address`, `state`, `health`, `hosting`. `SHOW SERVERS YIELD *` добавляет `serverId`, `httpAddress`, `httpsAddress`, `requestedHosting`, `tags`, `allowedDatabases`, `deniedDatabases`, `modeConstraint`, `version`.

Значения `health` — только `Available` и `Unavailable`. `Unavailable` не означает, что сервер не запущен: это лишь отсутствие успешного сетевого обмена с кластером.

Столбцы `hosting` и `requestedHosting` — это способ увидеть рассогласование: `requestedHosting` может содержать меньше баз, если сервер в процессе безопасной остановки одной копии, и больше, если запускает. Композитные базы в `requestedHosting` не отображаются, хотя в `hosting` присутствуют.

### SHOW DATABASES

Возвращает **одну строку на пару «база × сервер»**, а не одну строку на базу. Кластер из 4 серверов с 3 базами по 3 primary и 1 secondary даст 12 строк.

Базы, размещённые на офлайн-серверах, **тоже возвращаются**: для них `address` показывает `NULL`, `currentStatus` — `unknown`, а `statusMessage` — `Server is unavailable`. Поэтому «база исчезла из вывода» обычно означает не потерю данных, а потерю связи с её серверами — проверять нужно `SHOW SERVERS`.

Ключевые столбцы:

| Столбец | На что смотреть |
| :--- | :--- |
| `role` | `primary`, `secondary` или `unknown`. `unknown` — база офлайн на этом сервере по решению оператора или из-за ошибки |
| `writer` | `true` — тот узел, который принимает записи: leader в кластере либо сам сервер в standalone |
| `requestedStatus` / `currentStatus` | Расхождение означает незавершённый переход. `requestedStatus` бывает только `online` или `offline` |
| `statusMessage` | Текст ошибки перехода. Для баз на офлайн-серверах — `Server is unavailable` |
| `access` | `read-write` или `read-only` |

Для баз, размещённых на офлайн-серверах, `address` показывает `NULL`, `currentStatus` — `unknown`.

Фильтрация по имени:

```cypher
SHOW DATABASE foo;
```

### Проверка статуса репликации

```cypher
CALL dbms.cluster.statusCheck([]);
```

Процедура ставит в кластер фиктивную транзакцию и проверяет, что она реплицируется и применяется. Пустой список означает «все базы, размещённые на этом сервере»; процедура не выполняется для одиночных баз и secondaries.

Параметр `timeoutMilliseconds` по умолчанию — **1000 мс**.

| Столбец | Значение |
| :--- | :--- |
| `replicationSuccessful` | `TRUE`, если сервер реплицировал фиктивную транзакцию к большинству в пределах таймаута |
| `memberStatus` | `APPLYING` — реплицирует и применяет; `REPLICATING` — может участвовать в репликации, но не применять; `UNAVAILABLE` — слишком отстал или недостижим, отказоустойчивость не увеличивает |
| `recognisedLeader` / `recognisedLeaderTerm` | Воспринимаемый лидер и его term. **Если члены называют разных лидеров, доверять надо тому, у которого term выше** |
| `requester` | `TRUE` для сервера, на котором выполнена процедура |
| `error` | Сообщение об ошибке, если есть |

Проверку можно проводить и без Cypher:

```cypher
CALL dbms.cluster.statusCheck(["system"]);
```

Процедура возвращает **строку на каждый primary** каждой запрошенной базы — не по строке на базу. Процедура `Admin Only`.

**Ограничение проверки.** Она не реплицирует настоящую транзакцию, поэтому не гарантирует доступность на запись — помешать могут другие факторы write-path. Здоровая проверка обычно означает доступность на запись, но не эквивалентна ей.

### HTTP-эндпоинты статуса

| Эндпоинт | Назначение |
| :--- | :--- |
| `/db/<database>/cluster/writable` | 200 + `true` только на leader'е; иначе 404 + `false` |
| `/db/<database>/cluster/read-only` | 200 + `true` на follower и secondary; 404 + `false` на leader'е |
| `/db/<database>/cluster/available` | 200 + `true` на всех ролях |
| `/db/<database>/cluster/status` | JSON с детальным описанием роли экземпляра |
| `/dbms/cluster/status` | То же по всем базам сразу. Удобно для координации rolling upgrade |

Эндпоинты для базы, которая не размещена на данном сервере, возвращают `404`.

```bash
curl -v localhost:7474/db/neo4j/cluster/writable
# → HTTP/1.1 200 OK, тело: true
```

Если включена аутентификация, эндпоинты требуют учётных данных. Для балансировщиков и прокси, которые не умеют их передавать, существует `dbms.security.cluster_status_auth_enabled=false` — решение осознанное, доступ ограничивать сетью.

### Механизм выборов и частые перевыборы

Если follower какое-то время не слышит leader'а, он может инициировать выборы: становится кандидатом и просит голосовать остальных. Получив **большинство голосов**, он берёт на себя роль leader'а. Серверы не голосуют за кандидата, который отстаёт от них самих, поэтому в каждый момент у базы ровно один leader, и у него гарантированно самый свежий лог.

Выборы — нормальная часть работы кластера и сами по себе не являются проблемой. Тревожный признак — **частые** перевыборы, мешающие работе. Документация называет две типичные причины:

- проблемы окружения, например нестабильная сеть (flaky networking);
- перегрузка — параллельных запросов и транзакций больше, чем железо выдерживает.

## Бэкап, восстановление и seed в кластере

Общая теория резервного копирования и процедуры бэкапа — в [бэкапе и восстановлении](./backup_and_restore.md) и [общих концепциях](../Concepts/backups.md). Здесь — только то, что специфично для кластера.

Четыре способа восстановить базу в кластере: из URI, через выделенный seeder-сервер, процедурой `dbms.recreateDatabase` и командой `neo4j-admin database copy`. Различаются они тем, требуется ли предварительно останавливать или удалять исходную базу, и тем, что переносится вместе с данными.

| Способ | Исходная база | Пользователи и роли | Топология |
| :--- | :--- | :--- | :--- |
| Seed из URI | Должна быть удалена, иначе `CREATE OR REPLACE` | Входят в бэкап по умолчанию | Задаётся заново |
| Выделенный seeder | Не должна существовать ни на одном сервере | Удаляются вместе с базой при `DROP DATABASE` | Задаётся заново |
| `dbms.recreateDatabase` | Пересоздаёт существующую базу на месте | **Привилегии сохраняются** | Задаётся заново |
| `neo4j-admin database copy` | Можно не останавливать и не удалять | Не переносятся, пересоздаются руками | Задаётся при `CREATE DATABASE` |

`dbms.recreateDatabase` — единственный путь, который сохраняет ранее выданные права на базу: процедура пересоздаёт хранилище, не трогая каталог пользователей и ролей.

### Seed из URI

```cypher
CREATE DATABASE foo
TOPOLOGY 3 PRIMARIES 0 SECONDARIES
OPTIONS { seedURI: 'file:///backups/foo/' };
```

Значение по умолчанию `dbms.databases.seed_from_uri_providers` — только `CloudSeedProvider`, поэтому для локальных seed'ов `FileSeedProvider` нужно добавить в список явно:

```properties
dbms.databases.seed_from_uri_providers=FileSeedProvider,CloudSeedProvider
```

Доступные провайдеры и схемы URI: `FileSeedProvider` → `file`, `CloudSeedProvider` → `s3`, `azb`, `gs`, `ServerSeedProvider` → `server` (с 2026.04), `URLConnectionSeedProvider` → `ftp`, `http`, `https`. `S3SeedProvider` устарел и работает только в Cypher 5. Если один и тот же URI подходит нескольким провайдерам, используется первый в списке; пустой список полностью отключает seed из URI.

Особенности:

- Seed может быть полным бэкапом, дифференциальным бэкапом (тогда URI указывает на папку с цепочкой) или дампом существующей базы.
- При восстановлении задаётся topology, и она может **отличаться** от исходной. Нужное число primaries и secondaries должно укладываться в количество `Enabled`-серверов и их mode constraints; размещение происходит автоматически.
- Пользователи и роли в бэкап попадают по умолчанию, но это регулируется `--include-metadata` у `neo4j-admin database backup`; дампы (`neo4j-admin database dump`) содержат **только данные**, метаданные доступа придётся пересоздать руками.
- Если база не удалена перед восстановлением, используйте `CREATE OR REPLACE DATABASE` вместо `CREATE DATABASE`.

### Выделенный seeder

> **Только Cypher 5.** Опция `existingData` в Cypher 25 устарела и не имеет эффекта, а `existingDataSeedInstance` и `seedCredentials` в Cypher 25 **удалены**. В актуальных версиях используйте `seedURI` (см. выше) или `dbms.recreateDatabase`.

Подход короче, но капризнее: неизвестно заранее, как база распределится по серверам, и он полагается на то, что seed уже лежит на одном из них.

1. Восстановить базу на одном сервере:
   ```bash
   bin/neo4j-admin database restore --from-path=/path/to/foo-backup-dir foo
   ```
2. Узнать server ID этого сервера:
   ```cypher
   SHOW SERVERS YIELD serverId, name, address, state, health, hosting;
   ```
3. Создать базу в кластере, указав этот сервер источником (с 2025.06):
   ```cypher
   CREATE DATABASE foo
   TOPOLOGY 3 PRIMARIES 0 SECONDARIES
   OPTIONS {existingData: 'use', existingDataSeedServer: '8512c9b9-d9e8-48e6-b037-b15b0004ca18'};
   ```
4. Проверить:
   ```cypher
   SHOW DATABASE foo;
   ```
```text
| name | type | aliases | access | address | role | writer | requestedStatus | currentStatus | statusMessage | default | home | constituents |
+------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
| "foo" | "standard" | [] | "read-write" | "localhost:7687" | "primary" | FALSE | "online" | "online" | "" | FALSE | FALSE | [] |
| "foo" | "standard" | [] | "read-write" | "localhost:7688" | "primary" | FALSE | "online" | "online" | "" | FALSE | FALSE | [] |
| "foo" | "standard" | [] | "read-write" | "localhost:7689" | "primary" | TRUE | "online" | "online" | "" | FALSE | FALSE | [] |
+------------------------------------------------------------------------------------------------------------------------------------------------------------------------+
```
Обратите внимание: в выводе видно, что из трёх primary только один помечен `writer = TRUE` — остальные являются follower'ами этой базы. Для базы большого объёма команда выполняется долго.

Опция `existingDataSeedInstance` объявлена устаревшей в 5.26 — заменена на `existingDataSeedServer`. Опция `seedCredentials` также устарела.

### dbms.recreateDatabase

Самый чистый путь: сохраняет все выданные на базу привилегии и роли, `DROP DATABASE` вызывать не нужно, seed может быть локальным.

```cypher
CALL dbms.recreateDatabase("foo", {seedURI: "file:///backups/foo/"});

-- С изменением топологии
CALL dbms.recreateDatabase("foo", {seedURI: "file:///backups/foo/", primaries: 3, secondaries: 0});
```

Нужны привилегии `CREATE DATABASE` и `DROP DATABASE`. Процедура `dbms.cluster.recreateDatabase()` — предшественник, устарела с 2025.04 и заменена именно на `dbms.recreateDatabase()`.

### Бэкап в замороженной точке

Ключевая возможность, которой нет у standalone: приостановить репликацию secondaries, снять бэкап и получить консистентный снимок, соответствующий моменту остановки.

```cypher
CALL dbms.cluster.secondaryReplicationDisable("neo4j", true);   -- pause
CALL dbms.cluster.secondaryReplicationDisable("neo4j", false);  -- resume
```

Требования: процедура `Admin Only`, подключаться напрямую к серверу, размещающему базу в **secondary**-режиме, по `bolt://` или через HTTP API; процедура работает только для базы, которая на подключённом сервере находится в роли secondary. Возвращает текущее состояние репликации (`state`).

Бэкап с такой базы будет содержать только транзакции до момента паузы. Второй сценарий применения — заморозить secondary и отдавать аналитикам набор данных, который не изменится посреди анализа.

Процедура `dbms.cluster.readReplicaToggle()` — устаревший предшественник (deprecated в 5.6, удалена в Cypher 25).

## Отказоустойчивость и аварийное восстановление

### Как сбой ложится на базы

Серверы размещают разные базы, и потеря сервера бьёт по ним по-разному:

| Ситуация | Следствие | Стратегия |
| :--- | :--- | :--- |
| Потеряны все размещения | Размещений не осталось | Пересоздать из бэкапа |
| Потерян primary, secondary жив | Потеряно большинство primary, запись невозможна | Пересоздать, используя уцелевший secondary как seed — **бэкап не нужен**. Данные будут настолько свежими, насколько свеж был secondary |
| Потеряны два primary и secondary | То же, но seed выбирается из уцелевших копий | Пересоздать без бэкапа; состояние отражает самую свежую выжившую копию |
| Потерян один primary и два secondary | Запись доступна, деаллокация переедет сама | Пересоздание не требуется |
| Ничего не потеряно | — | Действий не требуется |

Обратите внимание: базы с одинаковой topology могут требовать разных действий — всё зависит от того, **какие именно** копии уцелели.

### Порядок восстановления

Официальное руководство разбивает DR на три шага, и порядок важен: пока `system` недоступна на запись, нельзя ни менять представление кластера, ни пересоздавать базы.

1. **Шаг 1 — сделать `system` доступной на запись.**
2. **Шаг 2 — сделать доступными серверы:** отметить потерянные недоступными, разгрузить их, поднять остановленные базы.
3. **Шаг 3 — сделать доступными базы:** пересоздать всё, что не write-available, и убедиться через `SHOW DATABASES`.

Потеря всех серверов кластера означает, что восстановить **текущий** кластер невозможно — нужно развернуть новый и восстановить базы в него.

### Шаг 1: восстановление `system`

Сначала проверка:

```cypher
CALL dbms.cluster.statusCheck(["system"]);
```

Проверка не работает для базы с единственным primary — там проверяют размещение и `currentStatus = online` через `SHOW DATABASES`.

Далее — создаётся новый `system` из самой свежей копии, найденной в кластере:

1. Остановить процессы на всех серверах — это downtime для всех баз до конца шага.
2. На каждом сервере сбросить состояние `system`:
   ```bash
   bin/neo4j-admin dbms unbind-system-db
   ```
3. Найти сервер с самым свежим `system`:
   ```bash
   bin/neo4j-admin database info system
   ```
   Сравнивать поле `lastCommittedTransaction` на всех серверах.
4. На самом свежем сервере снять дамп:
   ```bash
   bin/neo4j-admin database dump system --to-path=/path/to/dump
   ```
5. Добавить новые серверы **без ограничений** — иначе последующая деаллокация упирается в ограничения, даже когда серверов достаточно. Как альтернатива: сменить `server.cluster.system_database_mode` на secondary-размещениях на primary, определив нужное число через `dbms.cluster.minimum_initial_system_primaries_count`. Но без замены серверов есть риск перегрузки кластера при переносе баз.
6. Загрузить дамп на каждый сервер:
   ```bash
   bin/neo4j-admin database load system --from-path=/path/to/dump --overwrite-destination=true
   ```
7. Проверить discovery-параметры и запустить все процессы.

### Шаг 2: серверы

Потерянный сервер остаётся в представлении кластера со статусом `Unavailable` и продолжает числиться хостингом своих баз. Поэтому одного отсоединения мало — нужно сначала перенести размещения.

```cypher
SHOW SERVERS;
```
Целевое состояние: у всех серверов `health = Available` и `state = Enabled`.

```cypher
CALL dbms.cluster.cordonServer("unavailable-server-id");
```

Cordoning запрещает новые размещения на недоступный сервер. Дальше:

- размещения, которые не могут переехать сами, заставляют пересоздать базу;
- остальные переезжают при переводе сервера в `Deallocating`.

Базы, остановленные в `currentStatus = offline`, нужно **сначала запустить**, иначе деаллокация их не сможет снять, а `statusCheck` не сможет отличить «нужно пересоздать» от «нужно просто поднять»:

```cypher
START DATABASE stopped-db;
```

Базу, которая не поднялась, оставляют на пересоздание в шаге 3.

### Шаг 3: базы

После восстановления доступности `system` недоступные базы пересоздаются с использованием существующих серверов как seeder'ов, с принятием меньшей topology, чем хотелось бы. Устойчивость write-доступности проверяется той же `dbms.cluster.statusCheck`.

Пересоздание не завершится, если seed'ы расходятся. Эти сообщения в поле `statusMessage` означают, что нужен откат на бэкап:

- `Seeders <id1> and <id2> have different checksums for transaction <id>. All seeders must have the same checksum for the same append index.`
- `Seeders <id1> and <id2> have incompatible storeIds. All seeders must have compatible storeIds.`
- `No store found on any of the seeders <id1>, <id2>…`

Отдельно: базы в `currentStatus = quarantined` на доступном сервере пересоздаются **только** из бэкапа.

## Кросс-кластерная репликация баз (2026.08)

**CCDR (cross-cluster database replication)** — репликация базы из одного кластера в другой. База-источник называется upstream, реплицируемая — replica.

Два механизма: через сеть (прямое подключение между кластерами) и через бэкапы. Оба опрашивают источник и применяют изменения, как только те появляются.

```cypher
CREATE REPLICA DATABASE foo-replica
TOPOLOGY 3 PRIMARIES 2 SECONDARIES
OPTIONS {
  replicaConfig: {
    remote: "foo",
    addresses: ["server01.example.com:6000","server02.example.com:6000","server03.example.com:6000"]
  }
};
```

Свойства, которые нельзя игнорировать:

- **Требуется Cypher 25** — команда поддерживается только в нём.
- **Replica всегда read-only.** При этом у неё есть topology из primary и secondary, но **и те, и другие не принимают записи**.
- **Источником может быть только standard database.** Composite databases и sharded property databases (SPD) как источник не поддерживаются.
- **Реплицируются данные, а не доступ.** Пользователи и роли не копируются, а `system` реплицировать нельзя вовсе — RBAC настраивается на каждом кластере отдельно.
- Репликация идёт на уровне базы, а не уровне сервера.
- Начиная с 2026.08 на upstream **не требуется**, чтобы каждый сервер из `addresses` хостил эту базу. На более ранних версиях — требовался.

Комбинация с готовым seed:

```cypher
CREATE REPLICA DATABASE foo-replica
TOPOLOGY 3 PRIMARIES 1 SECONDARY
OPTIONS {
  seedURI: "file:///backups/foo/",
  replicaConfig: { remote: "foo", addresses: ["server01.example.com:6000"] }
};
```

Проверка:

```cypher
SHOW DATABASE foo-replica YIELD name, type, access, address, role, writer, options;
```
Столбец `type` будет `replica`, `access` — `read-only`.

### Промоция replica

Если upstream стал недоступен, replica поднимается promoted. **Промоция — операция односторонняя.**

```cypher
CALL dbms.promoteReplicaDatabase("foo-replica", {});
```

Сохранение текущей topology или её изменение задаётся вторым аргументом. Процедура требует Cypher 25 (введена в 2026.06). После промоции тип базы становится `standard` — проверять через `SHOW DATABASES`.

Промоция **необратима**: промотированная база больше не может быть присоединена обратно к исходному источнику. Чтобы возобновить репликацию, нужно создать новую replica.

## Аналитический кластер

Разделение транзакционной и аналитической нагрузки по разным серверам. На аналитических серверах выставляется `modeConstraint = SECONDARY`, чтобы они физически не могли участвовать в записи.

### С отказоустойчивостью

Пять серверов: три транзакционных и два аналитических. Все перечисляют в discovery **все** членов кластера, а аналитические дополнительно получают:

```properties
# server04.example.com — server05 отличается только этой строкой
server.default_listen_address=0.0.0.0
server.default_advertised_address=server04.example.com
dbms.cluster.endpoints=server01.example.com:6000,server02.example.com:6000,server03.example.com:6000,server04.example.com:6000,server05.example.com:6000
initial.server.mode_constraint=SECONDARY
server.cluster.system_database_mode=SECONDARY
```

Порядок старта не важен. После старта база создаётся с топологией, которая и разводит нагрузку по ролям:

```cypher
CREATE DATABASE bar TOPOLOGY 3 PRIMARIES 2 SECONDARIES
```

Транзакционные primary (3 штуки) обслуживают запись, secondaries (2 штуки) физически размещены на аналитических серверах и обслуживают чтение.

### Без отказоустойчивости

Если отказоустойчивость не в приоритете, допустим **один writer-сервер на весь DBMS**. Тогда серверов нужно меньше, но падение этого одного сервера или его процесса делает недоступными для записи все базы сразу.

Особенность конфигурации: writer-сервер перечисляет в discovery **только себя** — он не ищет остальных при старте, наоборот, остальные должны обнаружить его. Это и даёт кластер с единственным primary `system`:

```properties
# server01.example.com — writer, в списке только он сам
dbms.cluster.endpoints=server01.example.com:6000
```

Аналитические серверы, наоборот, перечисляют и writer'а, и себя, плюс получают те же ограничения, что и в варианте с отказоустойчивостью.

**Важное ограничение: библиотека GDS не поддерживает отказоустойчивость.** GDS следует разворачивать только на серверах, настроенных под аналитику, описанным выше. В варианте с одним writer'ом остальные серверы умеют только читать, а записывать результаты GDS обратно может лишь writer-сервер.

## Межкластеровое шифрование

По умолчанию внутрикластеровый обмен **не зашифрован**. Включение:

```properties
dbms.ssl.policy.cluster.enabled=true
dbms.ssl.policy.cluster.tls_versions=TLSv1.2
dbms.ssl.policy.cluster.ciphers=TLS_ECDHE_RSA_WITH_AES_256_CBC_SHA384
dbms.ssl.policy.cluster.client_auth=REQUIRE
```

`client_auth=REQUIRE` — значение по умолчанию, серверы обязаны аутентифицировать себя. Сертификат каждого сервера должен поддерживать **и** server, **и** client usage, потому что при соединении между серверами каждый использует свой сертификат для аутентификации в качестве клиента:

```bash
openssl x509 -in public.crt -noout -text
# → X509v3 Extended Key Usage: TLS Web Server Authentication, TLS Web Client Authentication
```

Строка `-----BEGIN RSA PRIVATE KEY-----` в начале файла означает старый формат PKCS #1, устаревший с Neo4j 5.0.

Никогда не используйте публичный CA или свой внутренний корневой CA для сертификатов кластера — любая подпись этим CA будет доверенной для входа в кластер. Используйте промежуточный CA, принадлежащий организации и используемый только для этого кластера. Отзыв — через CRL в каталоге `revoked`.

Полная конфигурация, структура каталогов и правила — в [безопасности](./security.md).

## Географическое распределение

### Три primary по трём ЦОД

Каждая primary-копия в своём ЦОД, минимум три ЦОД. Отказ одного ЦОД теряет одну primary — кластер продолжает работать без потери данных, но **платит межЦОД-задержкой на каждую запись**. Квереум не теряется, отказоустойчивость временно исчерпана. Восстановление: поднять новый primary в другом ЦОД или дождаться возврата.

### Все primary в одном ЦОД, secondaries в другом

Быстрая запись, потому что всё происходит в одном ЦОД. При отказе ЦОД с primary теряется доступность на запись, **но чтение через secondaries остаётся**. Восстановление доступности на запись: перевести secondaries `system` в primary (требует перезапуска процессов), затем пересоздать пользовательские базы, приняв уменьшенную topology, — восстановление идёт из существующих копий, а не из бэкапа.

### Пять primary для отказа любых двух

Чтобы пережить отказ любых двух произвольных серверов (или двух primary), базе нужно пять primary. Такая конфигурация допускает **временное** снятие одного primary с сохранением отказоустойчивости — например, при плановом перезапуске сервера.

Для много-ЦОД развёртывания пять primary распределяются по трём ЦОД в раскладке **`2P + 2P + 1P`**. Secondaries можно добавить сверху, например, для запуска задач бэкапа. С этой конфигурацией кластер переживает потерю **любого одного ЦОД**.

### Третий ЦОД только для `system`

Все primary пользовательских баз в одном ЦОД, все secondaries в другом, а в третьем — маленький сервер только с primary `system` (плюс primary `system` в первых двух). Чтобы на него не попадали пользовательские базы, задайте `allowedDatabases` с именем, которое никогда не будет использовано. Записи быстрые, а при отказе основного ЦОД `system` остаётся доступной на запись — что радикально упрощает восстановление пользовательских баз.

## Устранение неисправностей

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| `SHOW SERVERS` показывает `Free` | Сервер обнаружен, но не участвует | Сервер не включён | `ENABLE SERVER '<id>'`. Автоматически — `initial.dbms.automatically_enable_free_servers=true` |
| Сервер не появляется вообще | Нет строки в `SHOW SERVERS` | Discovery не находит кластер | Проверить `dbms.cluster.discovery.resolver_type` и `dbms.cluster.endpoints`. Для `LIST` убедиться, что перечислены **все** члены, включая текущий сервер |
| Кластер не собирается при старте | `system` не bootstraps | Не достигнут порог `dbms.cluster.minimum_initial_system_primaries_count` | Проверить, что достаточно серверов с `server.cluster.system_database_mode=PRIMARY`. Для кластера из 2 серверов выставить порог в 2 |
| `CREATE DATABASE` падает с ошибкой | Топология не собирается | Недостаточно серверов или их `modeConstraint` не позволяет | `SHOW SERVERS YIELD *` — смотреть `modeConstraint`. Расширить кластер или ослабить ограничения |
| `ALTER DATABASE SET TOPOLOGY 1 PRIMARY` | Ошибка | Автопереход к единственному primary невозможен | Бэкап → `DROP DATABASE` → `CREATE DATABASE` с новой topology из seed |
| Запись не принимается, кворум потерян | `WRITE` ошибки на всех primary | Слишком много primary офлайн | `CALL dbms.cluster.statusCheck([])` — смотреть `memberStatus` и `recognisedLeaderTerm` |
| В `SHOW DATABASES` `role = "unknown"`, `address = NULL` | Похоже на потерю базы | Хостивший её сервер офлайн: строка остаётся, но `statusMessage` = `Server is unavailable` | Проверить `SHOW SERVERS` — `state` и `health` этого сервера. Данные не потеряны, недоступно только размещение |
| `requestedStatus != currentStatus` надолго | База «застревает» в переходе | Reconciler не смог довести до цели | Ждать завершения перехода. `store copying` при копировании store-файлов между серверами — штатно |
| `currentStatus = "dirty"` | База не поднялась | Ошибка при старте базы | Разбирать логи. Повторный `START DATABASE` допустим, если причина устранена |
| Частые перевыборы лидера | Скачет `leader`, растут задержки | Нестабильная сеть или перегрузка | Проверить `millisSinceLastLeaderMessage` в `/db/<db>/cluster/status` и метрики нагрузки |
| `dbms.cluster.uncordonServer()` не работает | Процедура недоступна | Устарела в 5.23, **удалена в Cypher 25** | Использовать `ENABLE SERVER` |
| `dbms.cluster.readReplicaToggle()` не работает | Процедура недоступна | Устарела в 5.6, **удалена в Cypher 25** | Использовать `dbms.cluster.secondaryReplicationDisable()` |
| `dbms.cluster.recreateDatabase()` не работает | Процедура недоступна | Устарела с 2025.04 | Использовать `dbms.recreateDatabase()` |
| `dbms.cluster.routing.getRoutingTable()` не работает | Процедура устарела | Устарела в 5.21 | Использовать `dbms.routing.getRoutingTable()` |
| `existingDataSeedInstance` не работает | Опция не действует | В 5.26 устарела, а в **Cypher 25 удалена** вместе с `seedCredentials` | В Cypher 5 использовать `existingDataSeedServer`. В Cypher 25 — только `seedURI` или `dbms.recreateDatabase()` |
| `seedURI: 'file://...'` отклоняется | Ошибка создания базы | `FileSeedProvider` не в списке провайдеров | Добавить в `dbms.databases.seed_from_uri_providers` |
| Драйвер получает неверный адрес | `ServiceUnavailable` за базой | Неверный advertised address за reverse proxy или проброской портов | Проверить `server.default_advertised_address`; для IPv6 заключать в квадратные скобки |
| Все запросы идут на leader, secondaries простаивают | Реплики не нагружены | Writer включён в read-эндпоинты | `dbms.routing.reads_on_writers_enabled=false`; проверить `SHOW SERVERS` — `modeConstraint` аналитических серверов |
| Второй ЦОД нагружает запись | Рост задержки записи | Secondaries случайно попали в routing table как writers | Проверить `modeConstraint` и настройки `reads_on_primaries_enabled`/`reads_on_writers_enabled` |
| `DROP SERVER` отклоняется | Ошибка | Сервер ещё в `Enabled` или `Deallocating` | Сначала `DEALLOCATE DATABASES FROM SERVERS`, дождаться `Deallocated` |
| `unbind` оставил сервер без баз | Сервер вернулся как новый ID | `unbind` сохраняет store-файлы, но сбрасывает членство | Норма: сервер считается новым и базы не подхватывает. Для возврата данных — восстановление из бэкапа |
| После `unbind` на нескольких серверах кластер встал | Потеря кворума | Массовый сброс состояния | Восстановление по процедуре DR для `system` |

## Практические рекомендации

- **Начинайте с трёх primary.** Этого достаточно для обновлений без downtime и переживания отказа одного члена. Пятерка оправдана, только если отказ одного участника недопустим.
- **Не раздувайте число primary.** 11 — максимум, и каждый лишний участник добавляет сетевой раунд к каждой записи. Secondaries дешевле: они не участвуют в кворуме.
- **Разделяйте роли через `modeConstraint`.** Аналитические и транзакционные нагрузки на разных серверах избавляют от борьбы за ресурсы и от неожиданного попадания аналитики на writer.
- **Держите `system` на трёх primary.** Без этого не будет write-доступности `system`, а значит — и возможности чинить кластер.
- **Планируйте смены через `WAIT`.** Успешный ответ на `CREATE DATABASE` не означает, что база поднялась везде.
- **Используйте `DRYRUN` перед деаллокацией и реаллокацией.** Стоит посмотреть план до того, как масса баз поедет.
- **Не выводите сервер из кластера, не уведя с него базы.** `DEALLOCATE DATABASES FROM SERVERS` → дождаться `Deallocated` → `DROP SERVER`.
- **Не выполняйте Cypher-административные команды во время rolling upgrade.** Для координации используйте `/dbms/cluster/status`.
- **Задавайте одинаковый набор routing-политик на всех серверах.** Расхождение — источник трудно диагностируемых проблем маршрутизации.
- **Изолируйте кластерные порты (6000, 7000, 7688) от клиентской сети.** Транзакционный протокол допускает репликацию базы без аутентификации на уровне приложения, а клиент бэкапа может подключиться к порту 6000.
- **Включайте внутрикластеровое шифрование**, если кластер пересекает границы доверенной сети. Отдельный промежуточный CA для кластера, а не корневой.
- **Делайте бэкапы с secondary через `secondaryReplicationDisable`** — получается консистентный снимок без влияния на writer.
- **Сверяйте версию всех членов через `SHOW SERVERS YIELD *`** перед обновлением.
- **Проверяйте состояние кластера регулярно, а не по инциденту.** `SHOW SERVERS` + `dbms.cluster.statusCheck([])` — минимальный набор для ежедневного контроля.
