# Neo4j: Change Data Capture и интеграция с потоками

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

## Определения

| Термин | Значение |
| :--- | :--- |
| **CDC (Change Data Capture)** | Захват изменений данных (создание, обновление, удаление узлов и связей) в реальном времени для синхронизации с другими системами. |
| **Transaction log enrichment** | Обогащение записей transaction log дополнительной информацией; без него CDC не работает. |
| **`txLogEnrichment`** | Опция базы данных, задающая режим CDC: `OFF`, `DIFF`, `FULL`. |
| **DIFF** | В поток попадает разница между состояниями до и после: только удаления, обновления и добавления. |
| **FULL** | В поток попадает полная копия состояний до и после для каждого изменённого элемента. |
| **Boosted privileges** | Привилегии на выполнение процедур, работа в обход ограничений на данные. |
| **Change identifier** | Идентификатор изменения; определяет позицию в потоке. Локален для базы, к которой привязан. |
| **Debezium** | Фреймворк CDC, читающий журналы транзакций СУБД; для Neo4j коннектор находится в статусе incubating. |
| **Kafka Connector** | Коннектор Kafka Connect, читающий изменения Neo4j и (или) публикующий их в Kafka. |
| **Event selector** | Приложенческий фильтр во `db.cdc.query` по типу сущности, операции, свойствам или метаданным; не является границей безопасности. |
| **txCommitTime** | Метка времени фиксации транзакции, возвращаемая `db.cdc.current` начиная с Neo4j 2026.06 (Cypher 25). |

## Базовые понятия: откуда CDC берёт данные

Neo4j не читает сами store-файлы: изменения уже проходят через транзакционный слой и пишутся в transaction log. Но **журнал по умолчанию не содержит информации, пригодной для CDC** — в нём нет ни «до», ни «после». Чтобы поток появился, журнал нужно обогатить дополнительными сведениями.

Обогащение включается **на каждой базе отдельно** — это опция базы, а не настройка сервера. После включения база готова отвечать на CDC-запросы клиентских приложений.

> **Требования:** CDC доступен **только на Neo4j Enterprise Edition (или AuraDB Enterprise)**. Обогащение — опция базы, а не сервера, поэтому включается на каждой базе отдельно; на системной базе (`system`) CDC недоступен.

Три режима:

| Режим | Что попадает в поток | Когда выбирать |
| :--- | :--- | :--- |
| `OFF` | Ничего (значение по умолчанию) | CDC не нужен |
| `DIFF` | Разница между состояниями: удаления, обновления, добавления | Экономия места и трафика; потребителю достаточно дельты |
| `FULL` | Полная копия состояний до и после каждого изменённого элемента | Потребитель не умеет применять дельту или нужна сверка состояния |

**Переключение между `DIFF` и `FULL` немедленно меняет структуру захваченных изменений.** Приложение-потребитель обязно это пережить.

**Отключение разрывает непрерывность потока.** Идентификаторы, сгенерированные до отключения, больше не действительны, и после повторного включения они остаются невалидными: отключение и включение эквивалентны первому включению — памяти о предыдущих изменениях не остаётся.

### Что CDC не захватывает

CDC видит только то, что прошло через транзакционный слой. Данные, которые пишутся в store напрямую, поток обходят стороной:

| Способ загрузки | Попадает в CDC |
| :--- | :--- |
| Cypher `CREATE` / `MERGE` / `SET` / `DELETE` | Да |
| `LOAD CSV`, `apoc.load.json`, другие процедуры записи | Да |
| `neo4j-admin database import` (full и incremental) | **Нет** — пишет прямо в store |
| `neo4j-admin database load` | **Нет** — пишет прямо в store |

Практическое следствие: если начальная загрузка идёт через bulk import, потребитель CDC должен стартовать **после** неё, иначе он увидит поток, не соответствующий состоянию базы. Подробности — в [массовом импорте](./bulk_import.md).

### Когда CDC — неправильный инструмент

CDC не создаёт точную копию базы Neo4j: метаданные в поток не попадают — дата создания, создавший пользователь, внутренние ID. Если нужна точная копия, правильный путь — кластер или офлайн-копии через бэкап, см. [кластеризацию](./clustering.md) и [бэкап и восстановление](./backup_and_restore.md).

## Процедуры CDC и формат событий

После включения `txLogEnrichment` база отвечает на запросы клиентов через три процедуры. Все они работают с **change identifier** — позицией в потоке, которая является локальной для базы: идентификатор, сгенерированный в одной базе, не подходит для чтения в другой (см. [Восстановление из бэкапа](#восстановление-из-бэкапа-и-идентификаторы-изменений)).

### Процедуры

| Процедура | Назначение | Привилегии |
| :--- | :--- | :--- |
| `db.cdc.earliest()` | Идентификатор **самого раннего** доступного изменения | `ACCESS` на базу + обычный `EXECUTE` |
| `db.cdc.current()` | Идентификатор **последнего закоммиченного** изменения (exclusive) | `ACCESS` на базу + обычный `EXECUTE` |
| `db.cdc.query(from, selectors)` | События после заданного change identifier | `EXECUTE PROCEDURE db.cdc.query` + `EXECUTE BOOSTED PROCEDURE` (см. [Модель безопасности потока](#модель-безопасности-потока)) |

`db.cdc.current` возвращает `id`. **Начиная с Neo4j 2026.06 (Cypher 25)** дополнительно возвращается `txCommitTime` — метка времени последней закоммиченной транзакции:

```cypher
CALL db.cdc.current()
```

```plain
+-------------------------------------------------------------------+
| id                                                   | txCommitTime         |
+-------------------------------------------------------------------+
| "A3V16ZaLlUmnipHLFkWrlA0AAAAAAAAABAAAAAAAAAAA"        | "2026-09-08T14:11:02Z"|
+-------------------------------------------------------------------+
```

Возвращаемый `id` **exclusive**: изменения транзакции, на которую он указывает, в результат не входят. По умолчанию `from = ""` подменяется на `db.cdc.current`.

### Сигнатура `db.cdc.query`

```text
db.cdc.query(
    from = "" :: STRING?,                        (1)
    selectors = [] :: LIST? OF MAP?              (2)
) :: (
    id :: STRING?,                              (3)
    txId :: INTEGER?,                           (4)
    seq :: INTEGER?,                            (5)
    metadata :: MAP?,                           (6)
    event :: MAP?                               (7)
)
```

1. Change identifier, с которого читать (exclusively).
2. Необязательный список селекторов для фильтрации (см. ниже).
3. Уникальный change identifier конкретной записи — его можно передать в следующий `db.cdc.query`.
4. Номер транзакции; уникален в комбинации с `seq`. Идентификаторы транзакций **непрерывны**: системные и схемные транзакции не записываются в CDC и создают пробелы.
5. Порядковый номер изменений внутри одной транзакции.
6. Метаданные транзакции — одинаковы для всех событий одной транзакции.
7. Само событие изменения сущности (node или relationship); структура — в [Формате событий](#формат-событий).

### Селекторы (selectors)

Параметр `selectors` — это **приложенческий** фильтр на уровне потребителя: он не заменяет политику доступа (см. [Модель безопасности потока](#модель-безопасности-потока)) и не является границей безопасности. Он позволяет уменьшить объём доставляемых данных.

Селектор к любому типу сущности:

```json
{ "select": "e", "operation": "c", "changesTo": ["name", "title"] }
```

| Поле | Значения | Примечание |
| :--- | :--- | :--- |
| `select` | `"e"` (все), `"n"` (node), `"r"` (relationship) | Обязательно |
| `operation` | `"c"`, `"u"`, `"d"` | По умолчанию — все операции |
| `changesTo` | `["prop1", "prop2"]` | Только изменения, затрагивающие **все** перечисленные свойства |

Для узлов доступно дополнительно: `elementId`, `key` (только при key constraint), `labels`. Для relationship — `type`, `start`/`end` (вложенные node-селекторы без `operation`/`changesTo`). Все селекторы можно дополнить метафильтром: `authenticatedUser`, `executingUser`, `txMetadata` (только совпадающие ключи-значения).

Для выборки по `OR` (либо `name`, либо `surname`) используйте **два** селектора в списке:

```cypher
CALL db.cdc.query($prevId, [
  {select: "n", changesTo: ["name"]},
  {select: "n", changesTo: ["surname"]}
])
```

Для `AND` (оба свойства изменились в одной транзакции) — один селектор с обеими колонками в `changesTo`.

### Формат событий

CDC фиксирует **только реальные изменения**: если две операции на одной сущности нивелируют друг друга (например, `CREATE` с последующим `DELETE` того же узла), событие не попадает в поток. Порядок событий **не гарантирован** совпадать с порядком применения в транзакции — Neo4j упорядочивает их так: node creations → relationship creations → node label/properties updates → relationship properties updates → node deletions → relationship deletions.

**Событие узла** (node):

```json
{
  "id": "A7fjWXMK_0L6hztd4xhoy0oAAAAAAAAADAAAAAAAAAAA",
  "txId": 12,
  "seq": 0,
  "metadata": {
    "executingUser": "neo4j",
    "authenticatedUser": "neo4j",
    "captureMode": "FULL",
    "connectionClient": "127.0.0.1:51320",
    "serverId": "e605bd8f",
    "databaseId": "edec6ba8-e82f-4aac-ae41-2725f2357fdd",
    "connectionType": "bolt",
    "connectionServer": "127.0.0.1:51316",
    "txStartTime": "2026-09-08T14:10:58.429Z",
    "txCommitTime": "2026-09-08T14:10:58.526Z",
    "txMetadata": { "correlationId": "987654321" }
  },
  "event": {
    "elementId": "4:b7e35973-0aff-42fa-873b-5de31868cb4a:1",
    "keys": { "Person": [{ "ssn": "Y654321" }] },
    "eventType": "n",
    "state": {
      "before": null,
      "after": {
        "properties": { "name": "Stefano" },
        "labels": ["Person"]
      }
    },
    "operation": "c",
    "labels": []
  }
}
```

| Поле event | Описание |
| :--- | :--- |
| `eventType` | `"n"` — узел, `"r"` — связь |
| `operation` | `"c"` create, `"u"` update, `"d"` delete |
| `state.before` / `state.after` | Состояние до/после. `before = NULL` для create, `after = NULL` для delete. В режиме `DIFF` ограничено изменёнными свойствами/метками; для create/delete возвращено полное состояние независимо от режима |
| `labels` | Метки **до** изменения (для узлов) |
| `keys` | Бизнес-ключи (только при key constraints) |
| `elementId` | Stable ID сущности в пределах одной базы |

**Событие связи** (relationship) добавляет `start`/`end` (вложенные node-селекторы с `elementId`, `keys`, `labels`) и `type` (отношение типа, напр. `"ACTED_IN"`).

### Элемент IDs и бизнес-ключи

`elementId`, возвращаемый `db.cdc.query`, **не стабилен** при операциях, меняющих базу (см. [роль elementId и key properties](https://neo4j.com/docs/cdc/current/procedures/elementids-key-properties/)). Особенно это важно после восстановления из бэкапа: свежая база генерирует новые `elementId`. **Для идентификации сущностей в потребителе используйте бизнес-ключи** (определённые через `CREATE CONSTRAINT ... KEY`) и поле `keys` в событии, а не `elementId`.

### Восстановление из бэкапа и идентификаторы изменений

Restore из бэкапа заменяет базу новой (новый transaction log, новые `elementId`), поэтому старые change identifier перестают действовать. Чтобы не потерять согласованность потребителя:

1. Перевести базу в read-only.
2. Зафиксировать текущий режим CDC (`txLogEnrichment`).
3. Убедиться, что потребитель прогнал весь доступный поток (`db.cdc.current`).
4. Остановить потребителя.
5. Выполнить restore из бэкапа.
6. Перевести восстановленную базу в read-only.
7. Установить тот же режим CDC (`DIFF`/`FULL`) на восстановленной базе.
8. Запустить потребителя с `db.cdc.earliest()` — восстановленная база начинается с начала.
9. Включить запись.
10. Проверить, что события доставляются без дублей.

## Практические сценарии

### Минимальный рабочий пример

Самый простой способ увидеть CDC в действии — зафиксировать текущий `id`, создать узел и запросить изменения. Операции идут в **трёх разных транзакциях**:

Транзакция 1 — захват текущей позиции

```cypher
CALL db.cdc.current() YIELD id AS currentId
-- currentId = "BaQswf9NV0b7qicwDdh7vfwAAAAAAAAD83__________AAABjzfm4bM="
```

Транзакция 2 — изменение данных

```cypher
CREATE (:Person:Hero {name: 'Batman', color: 'black'})
```

Транзакция 3 — чтение потока с зафиксированного `id`

```cypher
WITH "BaQswf9NV0b7qicwDdh7vfwAAAAAAAAD83__________AAABjzfm4bM=" AS previousId
CALL db.cdc.query(previousId) YIELD event, metadata RETURN event, metadata
```

```plain
event → {"eventType":"n","operation":"c","state":{"before":null,"after":{"properties":{"name":"Batman","color":"black"},"labels":["Person","Hero"]}},...}
metadata.captureMode → "DIFF"
```

Метаданные позволяют отнести событие к конкретной транзакции (`txId`) и упорядочить (`seq`) изменения внутри неё.

### Включение CDC на новой базе

```cypher
CREATE DATABASE mydatabase IF NOT EXISTS OPTIONS {txLogEnrichment: "FULL"}
```

### Смена режима на существующей базе

```cypher
ALTER DATABASE mydatabase SET OPTION txLogEnrichment "DIFF"
```

### Проверка текущего режима

```cypher
SHOW DATABASES YIELD name, options
RETURN name, options;
```

```plain
+--------------------+------------------------------+
| name               | options                      |
+--------------------+------------------------------+
| "mydatabase"       | {"txLogEnrichment": "DIFF"}  |
| "system"           | {}                           |
+--------------------+------------------------------+
```

Опция видна не на каждой базе — у `system` её нет, и это нормально: CDC на системной базе не включается.

### Отключение

```cypher
-- Явно выключить
ALTER DATABASE mydatabase SET OPTION txLogEnrichment "OFF"
```

```cypher
-- Убрать опцию altogether
ALTER DATABASE mydatabase REMOVE OPTION txLogEnrichment
```

### Модель безопасности потока

CDC возвращает **все изменения в базе и не ограничен сущностями, к которым у пользователя есть доступ**. Это не дыра, а особенность: фильтрация на уровне прав доступа в потоке не предусмотрена. Отсюда требование — выдавать доступ по принципу наименьших привилегий.

Процедура `db.cdc.query` требует административных привилегий. Обычному пользователю её выдают явно:

```cypher
GRANT EXECUTE PROCEDURE db.cdc.query ON DBMS TO $role;
GRANT EXECUTE BOOSTED PROCEDURE db.cdc.query ON DBMS TO $role;
```

Без `BOOSTED` процедура работать не будет. Небустовые привилегии на выполнение обычно уже входят в роль `PUBLIC`, поэтому отдельно их выдавать не нужно. Дополнительно требуется доступ к самой базе:

```cypher
GRANT ACCESS ON DATABASE $database TO $role
```

Для `PUBLIC` доступ к базе по умолчанию обычно уже есть.

Процедуры `db.cdc.current` и `db.cdc.earliest` административных привилегий не требуют — достаточно доступа к базе и обычных привилегий на выполнение. Их роль — узнать границы доступного диапазона изменений, прежде чем читать поток.

Фильтрация по сущности через параметр `selectors` в `db.cdc.query` — это **приложенческий** фильтр: он сокращает объём событий, но не является границей безопасности и не заменяет политику доступа. Политика доступа к данным на уровне прав доступа в потоке **не предусмотрена** — отсюда требование выдавать доступ по принципу наименьших привилегий.

Полная картина разграничений — в [безопасности](./security.md).

### Место на диске

С включённым CDC в transaction log пишется больше данных, поэтому файлы журнала ротируются и удаляются чаще. При ограниченном месте на диске это приводит к его исчерпанию.

Планируйте прирост записи в transaction log:

| Режим | Планируемый прирост |
| :--- | :--- |
| `DIFF` | **50 %** |
| `FULL` | **75 %** |

Фактическое потребление зависит от приложения, модели данных и характеристик транзакций.

### Глубина истории и retention

Период, в который CDC может отдавать изменения, определяется retention журналов транзакций: как только записи удалены ротацией, поток для них недоступен.

Правило выбора: **retention ≥ допустимого простоя приложения-потребителя**, чтобы изменения не были удалены до того, как потребитель их обработает.

```properties
# neo4j.conf
db.tx_log.rotation.retention_policy=7 days 4G
```

У журнала транзакций три потребителя, и изменение retention затрагивает их все:

| Потребитель | Что пострадает |
| :--- | :--- |
| CDC | Сократится глубина доступной истории изменений |
| Дифференциальные бэкапы | Сократится окно, за которое возможен restore |
| Операции кластера | Может сократиться доступный журнал для операций кластера |

Полная настройка ротации и хранения журналов — в [обслуживании](./operations.md#ротация-и-хранение-журналов).

## Интеграция с Kafka

### Статус коннекторов

| Коннектор | Статус | Примечание |
| :--- | :--- | :--- |
| `neo4j-contrib/neo4j-streams` (Neo4j Kafka Connector 5.0) | **Архивирован** | Поддерживался только для критических багов и security-фиксов ветки 5.0.x; новых функций не получает |
| `neo4j/neo4j-kafka-connector` | Активен | Текущий официальный коннектор; документация — [neo4j.com/docs/kafka](https://neo4j.com/docs/kafka/) |
| `debezium/debezium-connector-neo4j` | Incubating | Инкубаторный коннектор Debezium CDC для Neo4j; не production-решение |

> **Статус:** ветка 5.0.x коннектора Neo4j Kafka более не развивается. Для новых развёртываний используйте репозиторий `neo4j/neo4j-kafka-connector`; существующие инсталляции 5.0.x стоит планировать на переезд.

### Что выбрать

| Задача | Инструмент |
| :--- | :--- |
| Синхронизация графа с другими системами через Kafka | `neo4j/neo4j-kafka-connector` |
| Собственный потребитель на Python/Java/Go | `db.cdc.query` напрямую из приложения |
| CDC из реляционной БД в Neo4j | Коннектор Debezium для источника + запись в Neo4j |
| Точная копия базы | Бэкап или кластер, не CDC |

Общие архитектурные паттерны CDC — доставка через Kafka Connect, SMT-трансформации, поисковая индексация — разобраны в [паттернах CDC](../Concepts/cdc_architectural_patterns.md) и не дублируются здесь.

### Направление синхронизации

| Направление | Механизм | На что обратить внимание |
| :--- | :--- | :--- |
| Relational → Neo4j | Debezium на стороне источника, запись в Neo4j | Идемпотентность записи: повтор доставки не должна плодить узлы — `MERGE`, а не `CREATE` |
| Neo4j → Relational | `neo4j-kafka-connector` либо `db.cdc.query` | Порядок событий и повторная доставка: нужна дедупликация по change identifier |
| Neo4j → Neo4j | Кластер или `neo4j-admin database copy` | CDC не переносит метаданные, поэтому для полной копии он не подходит |

## Устранение неполадок

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| CDC не возвращает изменения | Пустой результат | Опция не включена на этой базе | `SHOW DATABASES YIELD name, options`; включить `txLogEnrichment` |
| Запрос `db.cdc.query` отклонён | Ошибка прав | Не выданы EXECUTE или BOOSTED | Выдать обе привилегии и `GRANT ACCESS ON DATABASE` |
| Пользователь видит чужие изменения | Замечание по безопасности | Поток не фильтруется по правам — это ожидаемо | Сузить круг пользователей с доступом к `db.cdc.query`; не выдавать его приложениям, которым он не нужен |
| Диск заполнен, логи исчезают быстрее | Рост потребления transaction log | `FULL` или `DIFF` увеличивают объём записи | Расширить место под журналы либо перейти с `FULL` на `DIFF` |
| Потребитель отстаёт, нужная история обрезана | Ошибка при чтении старых изменений | Retention короче простоя потребителя | Увеличить `db.tx_log.rotation.retention_policy`, учитывая влияние на бэкапы и кластер |
| После переключения `DIFF` ↔ `FULL` ломается потребитель | Ошибка разбора событий | Структура событий изменилась | Сделать потребителя терпимым к обоим форматам; переключать при остановленном потребителе |
| После отключения и включения идентификаторы не работают | Ошибка чтения потока | Непрерывность потока разорвана | Ожидаемое поведение: сохранять свою позицию и перечитывать поток с новой границы |
| Данные, загруженные через import, не появились в потоке | Пропуски в событиях | Bulk import пишет в store мимо transaction log | Начать чтение потока после загрузки; при необходимости сверить состояние |
| После restore из бэкапа события дублируются или «пропадают» | Несоответствие состояния потребителя | Restore заменяет БД новой (новый transaction log); старые change identifier недействительны, elementId меняются | Остановить потребитель; после restore включить `txLogEnrichment` в режиме `DIFF`/`FULL`; стартовать с `db.cdc.earliest()`; идентифицировать сущности по бизнес-ключам, а не elementId |

## Лучшие практики

- **CDC — не механизм резервного копирования.** Метаданные не передаются; для точной копии используйте бэкап или кластер.
- **Выбирайте `DIFF`, пока потребитель умеет применять дельту.** Разница с `FULL` — 25 процентных пунктов записи в журнал.
- **Планируйте место под журналы сразу:** минимум 50 % при `DIFF` и 75 % при `FULL` сверх прежнего объёма.
- **Retention — общий ресурс с бэкапами и кластером.** Одно изменение влияет на три подсистемы.
- **Не выдавайте `db.cdc.query` приложениям, которым он не нужен:** поток возвращает все изменения базы без фильтрации по правам.
- **Используйте бизнес-ключи, а не elementId:** `elementId` нестабилен после restore/операций над хранилищем — идентифицируйте сущности по key constraints и полю `keys` в событии.
- **Для restore из бэкапа** следуйте процедуре из [Troubleshooting](#устранение-неполадок): остановить потребителя, восстановить, перевести CDC в режим `DIFF`/`FULL`, стартовать с `db.cdc.earliest()`.
- **Применяйте селекторы** (`selectors`) для сужения потока на уровне приложения — это сокращает трафик, но не заменяет политику доступа.
- **Не переключайте режим CDC на работающем потребителе** без его подготовки к смене формата.
- **Начальную загрузку делайте до старта потребителя**, если она идёт через bulk import: такие изменения в поток не попадают.
- **Делайте потребителя идемпотентным:** повторная доставка события — норма, а не аномалия.
