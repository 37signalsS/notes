# Neo4j: Антипаттерны моделирования графа

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

## Определения

| Термин | Значение |
| :--- | :--- |
| **Супернод (super node, хаб)** | Узел со степенью на порядки выше остальных: через него проходит большинство обходов. |
| **Degree (степень узла)** | Число связей конкретного узла; петли считаются дважды. |
| **Dense node (плотный узел)** | Узел с большим количеством связей одного типа; хранится в отдельном dense store. |
| **Гиперребро** | Связь между более чем двумя сущностями, разложенная на набор бинарных связей с потерей смысла. |
| **Материализованный путь** | Отношения, вложенные в другие отношения (`[:ROUTE*1..5]`) — способ хранить иерархию. |
| **Property** | Свойство узла или связи; у связи свойства есть, но у каждой связи ровно один тип. |
| **Мульти-лейбл** | Несколько меток на одном узле как способ «унаследовать» сущность. |
| **Inline-данные** | Большие массивы, списки или длинные строки, сохранённые в свойстве узла. |

## Базовые понятия: где ломается граф

Реляционная база деградирует линейно с ростом объёма данных. Граф деградирует по-другому: качество запроса определяется не объёмом графа, а **распределением степеней узлов**. Один узел с сотней тысячью связей превращает идеально избирательный обход в последовательное сканирование.

Три механизма Neo4j делают это явным:

1. **Index-free adjacency** — при обходе не нужен индекс, страницы соседей лежат рядом. Это и сила, и слабость: у hub-узла страницы соседей не укладываются в кэш.
2. **Dense store** — узел с большим количеством связей одного типа хранит их отдельно от обычных записей. Проблема отсюда не исчезает: страниц по-прежнему много, они по-прежнему не помещаются в page cache.
3. **Ровно один тип у связи** — это ограничение делает гиперребра принципиально непредставимыми нативно: связь «заказ ↔ три товара» нельзя выразить одной связью, и её неизбежно размазывают по трём бинарным связям.

Наличие `dense store` зависит от **формата хранилища** базы. В `block`-формате (по умолчанию в Enterprise Edition с Neo4j 5.22) переполнение связей одного узла уходит в отдельный dense store (`block.relationship.dense.db`), и плотность hub-узла растёт не так резко — однако **стоимость обхода всё равно растёт**, потому что страниц в нём всё равно становится много. В `aligned`-формате (по умолчанию в Community Edition) этой оптимизации нет — хабы тормозят сильнее. Формат проверить: `SHOW DATABASES YIELD name, store`. Подробности — в [Архитектура и хранение](./architecture.md#форматы-хранения) и [store formats](https://neo4j.com/docs/operations-manual/current/database-internals/store-formats/).

Симптомы, общие для большинства паттернов ниже:

| Симптом | На чём видно |
| :--- | :--- |
| Рост `page faults` | `PROFILE`, `neo4j_dbms_page_cache_hit_ratio` |
| Рост latency на обходах | `query.log`, метрики задержек |
| Деградация при `DETACH DELETE` | Contention и длинные транзакции на hub-узлах |
| Транзакция не влезает в память | `dbms.tx_state.max_off_heap_memory`, `SHOW TRANSACTIONS` |

## Практические сценарии

### Антипаттерн 1: супернод (хаб)

**Симптом.** Модель выглядит безобидно, пока через один узел не начинают ходить все: глобальный каталог, «все пользователи», корневой элемент иерархии, узел-агрегатор по метрикам.

```cypher
MATCH (n:Global)
RETURN n;
// → один узел, миллионы входящих связей
```

**Диагностика — поиск хабов по степени:**

```cypher
// Общая степень узла: больше 1000 связей
MATCH (n)
WHERE size((n)--()) > 1000
RETURN n, size((n)--()) AS degree
ORDER BY degree DESC
LIMIT 25;
```

```plain
+---------------------------------------+--------+
| n                                    | degree |
+---------------------------------------+--------+
| (:Catalog {name: "global"})          | 2841193|
| (:Metric {name: "requests_total"})   | 910442 |
| (:Org {name: "root"})                | 318    |
+---------------------------------------+--------+
```

```cypher
// Степень по конкретному типу связи — показывает, какой именно тип перегружен
MATCH (n:Metric {name: "requests_total"})
RETURN size((n)-[:HAS_SAMPLE]-()) AS samples;
```

**Лечение.** Вынести перегруженный атрибут из узла в собственный узел и разбить связь по времени или по сегменту — тогда у каждого сегмента своя степень, а запросы получают anchor point:

```cypher
// Было: 2.8 млн связей в одном узле
// Стало: узел на сегмент
MATCH (c:Catalog {name: "global"})-[:HAS_ITEM]->(i)
WITH i, i.segment AS segment
MERGE (s:Segment {catalog: "global", segment: segment})
MERGE (s)-[:HAS_ITEM]->(i);
```

### Антипаттерн 2: гиперребро

**Симптом.** Связь с более чем двумя участниками моделируется тройкой бинарных связей через искусственный узел-«тройку», который не имеет самостоятельного смысла.

```cypher
// Гиперребро, размазанное по бинарным связям
CREATE (a:Account)-[:PARTICIPANT]->(t:Transfer {id: 't-1'})-[:PARTICIPANT]->(b:Account);
```

**Диагностика.** Ищем узлы, которые встречаются только как посредники: у них нет собственных свойств, но есть ровно две входящие связи одного типа.

```cypher
// Узлы-посредники: участвуют в двух и более связях одного типа
MATCH (n)-[:PARTICIPANT]->()
WITH n, count(*) AS c
WHERE c >= 2
RETURN labels(n) AS labels, count(*) AS nodes
ORDER BY nodes DESC;
```

**Лечение.** Оставить узел, но сделать его настоящей сущностью с идентичностью и свойствами — тогда у него появятся собственные связи, и он перестанет быть транзитным мусором:

```cypher
// Гиперребро как полноценная сущность
CREATE (t:Transfer {id: 't-1', amount: 4200, currency: 'EUR'})
CREATE (a:Account)-[:DEBITED]->(t)-[:CREDITED]->(b:Account);
```

### Антипаттерн 3: один тип связи на каждую пару

**Симптом.** Вместо одного отношения с именем появляется зоопарк типов с одинаковой семантикой: `OWNS`, `HAS`, `CONTAINS`, `HOLDS` — все про одно и то же.

**Диагностика.** Считаем типы связей и смотрим на распределение:

```cypher
MATCH ()-[r]->()
RETURN type(r) AS relType, count(*) AS count
ORDER BY count DESC;
```

**Лечение.** Свести к одному типу и перенести семантику в свойства. Исключение — случаи, когда разные типы действительно имеют разную привилегию или разную обработку; тогда расхождение оправдано и должно быть осознанным.

### Антипаттерн 4: мульти-лейбл

**Симптом.** «Наследование» через метки: `:User`, `:Admin`, `:Active` на одном узле. Проблема не в хранении, а в запросах: фильтр по `:Admin` возвращает узлы без гарантии наличия общих свойств, а любая новая метка умножает число комбинаций в планировщике.

**Диагностика.** Смотрим распределение меток и пересечения:

```cypher
MATCH (n)
UNWIND labels(n) AS label
RETURN label, count(*) AS nodes
ORDER BY nodes DESC
LIMIT 20;
```

**Лечение.** Разделить роль и класс: класс — метка (`:User`), роль — свойство (`:User {role: 'admin'}`) либо отдельная узловая сущность прав. Смешивать нельзя: метка участвует в индексах и планировании, свойство — в фильтрах.

### Антипаттерн 5: inline-данные в свойстве

**Симптом.** В свойство узла пишутся большие списки или длинные строки: список связей, теги, полезная нагрузка события.

**Диагностика.** Проверяем распределение размеров значений:

```cypher
MATCH (n:Service)
RETURN n.name AS name, size(n.tags) AS tagCount, size(n.payload) AS payloadSize
ORDER BY payloadSize DESC
LIMIT 20;
```

**Лечение.** Данные, по которым нужен поиск или обход, — это узлы и связи. Данные, которые только читаются целиком, — остаются свойством. Граница простая: если по элементу нужен `MATCH`, это узел.

### Антипаттерн 6: неограниченная глубина обхода

**Симптом.** `MATCH (a)-[*]->(b)` без верхней границы в графе с циклами: количество путей растёт экспоненциально, запрос не завершается в разумное время.

**Лечение.** Всегда ограничивать глубину переменной длины и указывать направление:

```cypher
// Ограничено по глубине и по числу результатов
MATCH path = (root:Service {name: 'payment-api'})-[:DEPENDS_ON*1..4]->(dep)
RETURN DISTINCT dep.name AS name
LIMIT 100;
```

### Антипаттерн 7: реляционная нормализация «по привычке»

**Симптом.** Каждое свойство вынесено в узел-словарь, и всё общение идёт через связи: `(:User)-[:HAS_NAME]->(:PropertyValue)`. Формально нормализовано, фактически — лишние обходы там, где достаточно свойства.

**Диагностика.** Смотрим на запросы с высокой глубиной обхода при простых фильтрах:

```cypher
// Кто-нибудь ходит на глубину 3 ради значения одного свойства?
MATCH path = (a)-[*1..3]->(b)
WHERE length(path) >= 3
RETURN a, b, length(path) AS hops
LIMIT 10;
```

**Лечение.** Значения, которые нужны как фильтр и не имеют собственного жизненного цикла, — свойства. Сущности с жизненным циклом — узлы.

### Антипаттерн 8: связь как единственное место хранения данных

**Симптом.** Все свойства сущности висят на связи, у которой всего один тип и нет имени. Связь без типа и без семантики — это просто пара узлов; её свойства негде найти и нечем объяснить.

**Лечение.** Дать связи имя типа и перенести атрибуты на узел, если у сущности есть собственные свойства. Если атрибут принадлежит именно отношениям (например, `since`, `weight`), оставить его на связи — это правильное использование возможности.

### Материализованный путь как осознанное решение

Иерархии — источник глубоких обходов. Материализованный путь (вложенные связи) — стандартный ответ:

```cypher
CREATE (root:Category {name: 'root'})-[:PART_OF*1..5]->(leaf:Category {name: 'leaf'});
```

Обход дерева становится предсказуемым по стоимости, но запись требует пересчёта путей при изменении структуры. Это плата: выбирайте материализованный путь, когда запись редка, а чтение иерархии — постоянно.

## Устранение неполадок

| Проблема | Симптом | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| Рост `page faults` | Медленные обходы, низкий hit ratio | Поиск узлов со степенью > 1000 | Разбить хаб на сегменты или вынести в отдельные узлы |
| `DETACH DELETE` на узле висит | Долгая транзакция, contention | `SHOW TRANSACTIONS` по `elapsedTime` | Сначала разорвать связи пакетами, затем удалить узлы |
| Запрос возвращает миллионы строк | Упирается в память клиента | `RETURN` без `LIMIT` | `LIMIT` + пагинация курсором; агрегировать на стороне базы |
| Планировщик игнорирует индекс | `Index not used` в `EXPLAIN` | Строка «Когда НЕ создавать индекс» | Не создавать индекс на низкокардинальном или неиспользуемом свойстве |
| Граф разросся без пользы | Много меток, мало выгоды | Распределение меток и типов связей | Свести мульти-лейбл к свойствам, типы связей — к одному |
| Перестроение модели ломает приложение | Ошибки в проде после изменения формы | — | Expand → Contract, см. [миграции схемы](./schema_migrations.md) |

## Лучшие практики

- **Степень узла — метрика модели, а не деталь реализации.** Проверяйте распределение степеней так же, как размер таблицы.
- **Любой узел, через который проходит больше тысячи связей, — кандидат на разбиение.**
- **Индекс создавайте только там, где он используется как anchor point.** Фильтр по неиндексированному свойству на пути обхода не ускоряет ничего.
- **Гиперребро моделируйте узлом.** Это единственный способ сделать его адресуемым и надёжным.
- **Роль — свойство, класс — метка.** Метки участвуют в индексах и планировании; свойства — в фильтрах.
- **Атрибуты принадлежат узлу, атрибуты взаимодействия — связи.** Данные, по которым ищут, — узлы.
- **Ограничивайте глубину обхода всегда:** без верхней границы переменной длины запрос с циклами не имеет конечной стоимости.
- **Свойства-исключения для больших значений:** то, что читается целиком и почти не фильтруется, разумно оставить свойством.
- **Рефакторинг модели — это миграция схемы** с порядком expand → migrate → contract, а не правка на проде.
