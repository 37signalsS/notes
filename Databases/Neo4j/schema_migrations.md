# Neo4j: Миграции схемы и эволюция модели данных

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

## Определения

| Термин | Значение |
| :--- | :--- |
| **Миграция схемы** | Версионированное, повторяемое изменение структуры данных: создание или удаление индексов и ограничений, изменение состава меток и свойств. |
| **Рефакторинг** | Изменение данных, вызванное новой моделью: перенос свойства в узел, переименование, разбиение узла на два. |
| **Идемпотентность** | Повторный прогон миграции на уже применённой базе не меняет данные и не падает. |
| **Catalog (каталог)** | Набор известных миграций: применённые и ожидающие. |
| **Chain (цепочка)** | Упорядоченная история применённых миграций, по которой проверяется непротиворечивость. |
| **Baseline** | Зафиксированное состояние каталога, с которого начинается отсчёт новых миграций. |
| **Expand / Contract** | Схема выкатки в три шага: расширить → перенести данные → сузить. |
| **POPULATING** | Состояние индекса, в котором он уже создан, но ещё заполняется данными. |

## Базовые понятия: почему миграция графа устроена иначе

Neo4j schema-less по умолчанию: узел может получить любую метку и любое свойство в любой момент. Целостность обеспечивается индексами и ограничениями (constraints), а не объявлением структуры заранее. Отсюда следствие: **миграция графа — это в первую очередь миграция данных, а не только DDL.**

### Три класса изменений

| Класс | Пример | Как выполняется в проде |
| :--- | :--- | :--- |
| **DDL-подобные** | `CREATE INDEX`, `CREATE CONSTRAINT`, `DROP INDEX`, `DROP CONSTRAINT` | Обычная Cypher-команда; отдельно требуется дождаться `ONLINE`/`POPULATING` |
| **Данные** | Добавить метку, заполнить свойство, переименовать свойство | Транзакции, на больших графах — `CALL { } IN TRANSACTIONS` пакетами |
| **Структурные** | Узел → узел + узел, связь → узел-связь, выделение узла из hub | Expand/Contract, см. ниже |

Индексы и ограничения создаются **в отдельном кластере-транзакции**: команда возвращается сразу, а заполнение индекса идёт в фоне. Состояние видно в `SHOW INDEXES`:

```cypher
SHOW INDEXES YIELD name, type, labelsOrTypes, properties, state, population;
```

→ `state` содержит `ONLINE` (готов) или `POPULATING` (строится).

### Чего в Cypher нет, а в SQL привычно

В Cypher нет `ALTER TABLE ... DROP COLUMN` и нет оператора «удалить свойство у всех узлов». Удаление свойства — это обход графа с записью, то есть операция над миллионами строк:

```cypher
// Удаление свойства — обход с записью, а не DDL
MATCH (n:Legacy)
WHERE n.deprecatedField IS NOT NULL
WITH n LIMIT 10000
REMOVE n.deprecatedField
RETURN count(*) AS processed;
```

Поэтому «удалить колонку» в графе — это всегда две операции: сначала перестать писать поле (в коде приложения), затем вычистить его пакетами в фоне. Порядок нарушать нельзя: удаление поля из кода раньше, чем вычистка, безопасно; обратный порядок приводит к потере данных.

### Блокировки и что мешает миграции в проде

| Действие | Что происходит с конкурентной работой |
| :--- | :--- |
| `CREATE INDEX` / `CREATE CONSTRAINT` | Команда неблокирующая, но индекс в состоянии `POPULATING` отнимает ресурсы и создаёт нагрузку на запись |
| `DROP INDEX` / `DROP CONSTRAINT` | Привилезии `DROP INDEX` / `DROP CONSTRAINT`; падение производительности запросов, использовавших индекс, после удаления |
| `CALL { } IN TRANSACTIONS` без `LIMIT` | Длинная транзакция: растёт расход transaction memory, растёт `currentQuery` время |
| Массовое удаление через `DETACH DELETE` | На hub-узлах — contention и длинные транзакции; только пакетами |

Согласованную методику массовых изменений в общем виде даёт [безопасные массовые изменения данных](../Concepts/safe_large_scale_data_modification.md), а откат — [стратегии отката](../Concepts/rollback_strategies.md). Здесь только специфика графа.

## Практические сценарии

### SRE-подход к миграции: окно, риски, наблюдение

Миграция в проде — операция с RTO/RPO, а не просто команда. Перед запуском зафиксируйте:

| Параметр | Значение по умолчанию | Что проверить |
| :--- | :--- | :--- |
| **Окно обслуживания** | 02:00–04:00 | Низкая нагрузка, нет GDS-проекций, нет бэкапов |
| **RTO** | 30 мин | Время, за которое можно откатиться к бэкапу |
| **RPO** | 5 мин | Потери данных при откате |
| **Бэкап перед миграцией** | Обязателен | Онлайн-бэкап перед каждой структурной миграцией |
| **Наблюдение** | `query.log`, метрики, `SHOW INDEXES` | Проверять state индексов до, во время и после |

**Критические замечания по наблюдению:**
- `CREATE INDEX`/`CREATE CONSTRAINT` возвращается мгновенно, но индекс строится в фоне. Миграция не завершена, пока `SHOW INDEXES` не покажет `ONLINE` для всех новых индексов. Вызовите `CALL db.awaitIndexes(300)` после миграции, чтобы дождаться готовности.
- `CALL db.awaitIndexes()` работает в режиме `READ` и не поддерживается параллельным рантаймом — нельзя вызывать из контекста параллельного рантайма.
- Мониторьте `neo4j_dbms_page_cache_hit_ratio` и `neo4j_dbms_vm_gc_time_percent` во время миграции — резкое падение hit ratio означает, что индексное построение вытесняет данные из кэша.

### Мониторинг во время миграции

Наблюдение строится вокруг трёх вопросов: идёт ли построение индекса, не давит ли миграция на память, не блокирует ли она приложение.

| Метрика | Где взять | Порог | Что означает |
| :--- | :--- | :--- | :--- |
| `neo4j_dbms_page_cache_hit_ratio` | Prometheus | < 95 % | Индексное построение вытесняет данные из кэша; увеличьте page cache или снизьте нагрузку |
| `neo4j_dbms_vm_gc_time_percent` | Prometheus | > 10 % | Heap под давлением; тюнинг GC (см. [диагностику на уровне JVM](./jvm_diagnostics.md)) |
| `neo4j_dbms_tx_state_max_off_heap_memory` | `SHOW TRANSACTIONS`, метрики | Рост без остановки | Пакет миграции слишком велик; добавьте `LIMIT` и перезапустите |
| `neo4j_dbms_bolt_connections_running` | Prometheus | Пиковые значения | Подключение миграции учитывается в общем пуле; не превышайте `thread_pool_max_size` |
| `database.<db>.check_point.duration` | Prometheus | > 5 мин | Checkpoint под давлением миграции; увеличьте `db.checkpoint.interval.time` |
| `SHOW INDEXES` → `population` | Cypher | Рост > 10 % в минуту | Индекс строится нормально; стагнация — признак нехватки ресурсов |
| `SHOW TRANSACTIONS` | Cypher | Долгие `currentQuery` | Проверьте, не висит ли миграционная транзакция |

**Практический чек-лист перед запуском:**
1. Отключите автоматические бэкапы на время миграции (или перенесите в конец окна).
2. Остановите GDS-проекции — они конкурируют за heap и page cache.
3. Запустите онлайн-бэкап — это единственная точка отката.
4. Запустите миграцию и следите за метриками выше в реальном времени.
5. После завершения — `CALL db.awaitIndexes(300)` и проверка `SHOW INDEXES` → `ONLINE`.

### Порядок выкатки: expand → migrate → contract

Изменение «`User.email` → отдельный узел `:EmailAddress`» в три шага:

```cypher
// 1. EXPAND — создаём структуру и заполняем её новыми данными.
//    Старый код продолжает писать в user.email — он ещё нужен.

// 1a. Новая метка и индекс (populate идёт в фоне)
CREATE INDEX email_address_node IF NOT EXISTS
FOR (e:EmailAddress) ON (e.value);

// 1b. Новые записи идут в обе структуры
MATCH (u:User {id: $id})
MERGE (e:EmailAddress {value: u.email})
MERGE (u)-[:HAS_EMAIL]->(e);
```

```cypher
// 2. MIGRATE — переносим исторические данные пакетами.
//    Запускать в фоне, повторяемо, с ограничением размера пакета.
MATCH (u:User)
WHERE u.email IS NOT NULL AND NOT (u)-[:HAS_EMAIL]->()
WITH u LIMIT 5000
MERGE (e:EmailAddress {value: u.email})
MERGE (u)-[:HAS_EMAIL]->(e)
RETURN count(*) AS migrated;
```

```cypher
// 3. CONTRACT — перестаём читать старое поле, затем вычищаем его.
//    Сначала выключаем чтение в приложении, и только потом удаляем свойство.
MATCH (u:User)
WHERE u.email IS NOT NULL
WITH u LIMIT 10000
REMOVE u.email
RETURN count(*) AS cleaned;
```

Критерий готовности шага 2 — запрос не возвращает строк:

```cypher
MATCH (u:User)
WHERE u.email IS NOT NULL AND NOT (u)-[:HAS_EMAIL]->()
RETURN count(*) AS remaining;
// → remaining = 0
```

### Neo4j-Migrations: каталог миграций в самой базе

Единственный поддерживаемый сообществом инструмент для версионирования миграций графа — **Neo4j-Migrations** ([`michael-simons/neo4j-migrations`](https://github.com/michael-simons/neo4j-migrations)). Это проект Neo4j Labs, вдохновлённый FlywayDB; он работает поверх официального Java-драйвера, поддерживает релизы 2025 и 2026, а также 3.5, 4.1–4.4 и 5, включая Enterprise-возможности — multi-database и impersonation.

**Ключевая особенность: история применённых миграций хранится как подграф в самой базе.** Это значит, что отдельная таблица состояния не нужна, а состояние миграций видно тем же Cypher.

Установка CLI (нужен JDK 17+; для чисто Cypher-миграций есть нативные бинарники без JVM):

```bash
# Актуальная версия — на странице релизов; архитектурно-независимая сборка
curl -LO https://github.com/michael-simons/neo4j-migrations/releases/download/4.2.0/neo4j-migrations-4.2.0.zip
unzip neo4j-migrations-4.2.0.zip
cd neo4j-migrations-4.2.0
./bin/neo4j-migrations -V
# → Neo4j-Migrations 4.2.0
```

Создать проект миграций в текущем каталоге:

```bash
./bin/neo4j-migrations init
# → создаёт каталог со структурой скриптов и конфигурацией
```

Посмотреть, что применено, а что ожидает:

```bash
./bin/neo4j-migrations \
  -a bolt://localhost:7687 -u neo4j -p 'secret' \
  --location file:./migrations \
  info
```

```plain
neo4j@localhost:7687 (Neo4j/2026.09.0)
Database: neo4j
+---------+-------------------+-------+--------------+----+----------------+---------+-------------------------------+
| Version | Description       | Type  | Installed on | by | Execution time | State   | Source                        |
+---------+-------------------+-------+--------------+----+----------------+---------+-------------------------------+
| 001     | AddEmailNode      | CYPHER |              |    |                | PENDING | 001__AddEmailNode.cypher       |
| 002     | BackfillEmails    | CYPHER |              |    |                | PENDING | 002__BackfillEmails.cypher     |
+---------+-------------------+-------+--------------+----+----------------+---------+-------------------------------+
```

Применить ожидающие:

```bash
./bin/neo4j-migrations -a bolt://localhost:7687 -u neo4j -p 'secret' \
  --location file:./migrations \

# → применяет все PENDING по порядку
```

Полезные ключи CLI:

| Ключ | Назначение |
| :--- | :--- |
| `-a`, `--address` | Адрес подключения; поддерживаются схемы `bolt`, `bolt+routing`, `neo4j` |
| `-d`, `--database` | База для миграции (Neo4j EE 4.0+) |
| `--schema-database` | База, где хранится информация о миграциях (Neo4j EE 4.0+) |

| `--validate-on-migrate` | Сверка применённых миграций с локальными; включена по умолчанию |
| `--autocrlf` | Конвертация CRLF → LF при чтении ресурсных миграций |

Автодополнение в текущей оболочке:

```bash
source <(./bin/neo4j-migrations generate-completion)
```

### Идемпотентность миграций

Прогоняемый в проде скрипт должен быть безопасен при повторе. Встроенные идиоматические конструкции:

```cypher
CREATE INDEX person_email IF NOT EXISTS FOR (p:Person) ON (p.email);
CREATE CONSTRAINT person_id IF NOT EXISTS FOR (p:Person) REQUIRE p.id IS UNIQUE;
```

`IF NOT EXISTS` не скрывает расхождение с каталогом: если в базе есть индекс с другим определением, повторный запуск ничего не исправит. Проверяйте состояние явно:

```cypher
SHOW INDEXES YIELD name, labelsOrTypes, properties, state, population
WHERE name IN ['person_email', 'person_id']
RETURN name, labelsOrTypes, properties, state, population;
```

Для произвольных данных идемпотентность обеспечивает `MERGE`, а не `CREATE`:

```cypher
// Повторный запуск не создаёт дубликаты
MATCH (u:User {id: $id})
MERGE (e:EmailAddress {value: u.email})
MERGE (u)-[:HAS_EMAIL]->(e);
```

### Проверка перед выкаткой

Полный снимок схемы — то, что нужно хранить рядом с миграциями и сравнивать в CI:

```cypher
SHOW CONSTRAINTS YIELD name, type, labelsOrTypes, properties;
```

```cypher
SHOW INDEXES YIELD name, type, entityType, labelsOrTypes, properties, state;
```

Дождаться готовности индексов перед тем, как считать миграцию завершённой:

```cypher
-- Аргумент — целое число секунд ожидания
CALL db.awaitIndexes(300);
```

Процедура работает в режиме `READ` и не поддерживается параллельным рантаймом, поэтому её
нельзя вызвать из контекста параллельного рантайма.

### Валидация результата миграции

После применения миграции проверьте, что она завершилась корректно, до того как включить обратную нагрузку.

**Индексы:**
```cypher
SHOW INDEXES YIELD name, type, labelsOrTypes, properties, state, population
ORDER BY name;
```
- Ожидаемое состояние: `ONLINE` для всех новых индексов, `population` = 100 %.
- Если индекс в `POPULATING` — дождитесь или пересоздайте.

**Ограничения:**
```cypher
SHOW CONSTRAINTS YIELD name, type, labelsOrTypes, properties
ORDER BY name;
```
- Ожидаемое состояние: все новые ограничения присутствуют и активны.
- `Constraint validation failed` при создании — остановите миграцию, устраните дубликаты/null, перезапустите.

**Каталог миграций:**
```cypher
CALL dbms.migrations.list()
YIELD version, description, type, installedOn, executionTime, state
ORDER BY version;
```
- Ожидаемое состояние: все миграции в `APPLIED`, `executionTime` разумный, `state` не `FAILED`.
- `neo4j-migrations info` — альтернатива из CLI; показывает `PENDING`/`APPLIED`.

**Данные (для миграций с backfill):**
```cypher
MATCH (u:User)
WHERE u.email IS NOT NULL AND NOT (u)-[:HAS_EMAIL]->()
RETURN count(*) AS remaining;
// → remaining = 0
```
- Ненулевое значение — миграция не завершена; запустите шаг 2 (MIGRATE) повторно.

**Производительность:**
- Сравните latency и page cache hit ratio до и после миграции. Резкое падение hit ratio — индексное построение вытеснило данные; увеличьте page cache.
- `EXPLAIN` на типовых запросах — убедитесь, что используется новый индекс, а не `NodeFullScan`.

### Откат

Откат миграции графа — это новая миграция, а не откат релиза: восстановить данные до произвольного момента можно только бэкапом (см. [бэкап и восстановление](./backup_and_restore.md)). Практический порядок:

1. До миграции снять онлайн-бэкап базы — это и есть точка отката.
2. Писать в структуру, которую можно наполнить заново дешевле, чем откатывать.
3. Обратимую миграцию (создание индекса) откатывать `DROP INDEX IF EXISTS`.
4. Необратимую (удаление данных) готовить заранее: сначала `REMOVE` пакетами, потом — только после проверки.

### CI/CD и автоматизация проверки схемы

Снимок схемы перед каждым релизом — это контрольная точка для CI. Сравнивайте `SHOW INDEXES` и `SHOW CONSTRAINTS` в двух окружениях (staging и production) перед выкаткой:

```cypher
// Снимок для CI: индексы
SHOW INDEXES YIELD name, type, labelsOrTypes, properties, state
ORDER BY name;

// Снимок для CI: ограничения
SHOW CONSTRAINTS YIELD name, type, labelsOrTypes, properties
ORDER BY name;
```

**Что проверять в CI:**
1. **Сравнение схемы** — разница между staging и production перед деплоем. Если в production есть индекс, которого нет в staging, миграция может быть неидемпотентной.
2. **`validate-on-migrate`** — включена по умолчанию в Neo4j-Migrations; проверяет, что применённые миграции соответствуют локальным скриптам. При несоответствии команда падает до применения.
3. **Проверка `POPULATING`** — если индекс остаётся в `POPULATING` дольше окна обслуживания, миграция считается неудавшейся.
4. **Параллельный рантайм** — `CALL db.awaitIndexes()` не поддерживается в параллельном рантайме; если используется multi-database или composite databases, проверяйте каждый базу отдельно.

### Восстановление после сбоя во время миграции

Сценарий: миграция началась, но середина не завершилась (сервер упал, диск переполнился, таймаут). Порядок действий:

1. **Не пытайтесь «дописать» миграцию вручную.** Каталог миграций хранится в самой базе; ручные правки приводят к рассинхронизации (см. [Устранение неполадок](#устранение-неполадок)).
2. **Оцените состояние:** `SHOW INDEXES` — какие индексы `ONLINE`, какие `POPULATING`. `SHOW CONSTRAINTS` — какие ограничения применены.
3. **Остановите нагрузку** — миграция и рабочая нагрузка конкурируют за page cache и CPU.
4. **Восстановите из бэкапа** — если миграция необратима (удаление данных, изменение типа свойства). Онлайн-бэкап перед миграцией — единственная точка отката.
5. **Перезапустите Neo4j-Migrations с `--validate-on-migrate`** — инструмент повторно применит только PENDING миграции, пропуская уже применённые.
6. **Для `POPULATING` индексов:** дождитесь завершения или удалите и создайте заново. `DROP INDEX` на индексе в `POPULATING` безопасен; создание заново — медленнее, но предсказуемее.

**Важно:** Neo4j-Migrations не откатывает миграции автоматически. Откат — это новая миграция или восстановление из бэкапа (см. [Откат](#откат)).

### Очистка после миграции

После успешной миграции, перед возвратом приложения в нормальный режим:

1. **Проверьте, что все индексы `ONLINE`:**
   ```cypher
   SHOW INDEXES YIELD name, state
   WHERE state <> 'ONLINE'
   RETURN name, state;
   ```
2. **Очистите кэш планов и запросов**, чтобы следующие запросы строили планы на обновлённой схеме:
   ```cypher
   CALL db.clearQueryCaches();
   ```
3. **Проверьте, что `SHOW TRANSACTIONS` не показывает зависших транзакций** — миграционные сессии должны быть закрыты.
4. **Соберите артефакты:** снимок схемы (`SHOW INDEXES`, `SHOW CONSTRAINTS`), `query.log`, конфигурацию, метрики во время миграции. Архивируйте с версией Neo4j и описанием изменений.
5. **Сравните схему с репозиторием** — убедитесь, что фактическое состояние соответствует ожидаемому.
6. **Включите обратную нагрузку** постепенно и проконтролируйте первые минуты: latency, page cache hit ratio, GC.

### Особенности конфигураций и ограничения

| Ситуация | Ограничение / особенность | Что делать |
| :--- | :--- | :--- |
| **Community Edition** | Нет `multi-database`, нет `composite databases`, нет `--schema` в bulk import | Миграции схемы — только через Cypher; `SHOW INDEXES` по умолчанию показывает только текущую базу |
| **Multi-database / Composite databases** | Каталог миграций хранится в отдельной `schema database`; `CALL db.awaitIndexes()` не поддерживается в параллельном рантайме | Проверяйте каждую базу отдельно; `--schema-database` указывайте явно |
| **Кластер (Causal Clustering)** | `CREATE INDEX`/`CREATE CONSTRAINT` реплицируются; `POPULATING` идёт на каждом реплике | Ожидайте задержку репликации перед проверкой `ONLINE` на read-репликах |
| **Docker / контейнер** | Объём данных растёт при построении индексов; `POPULATING` требует места на диске | Mount Docker volume для `data` и `logs`; не запускайте миграцию при близком к заполнению диске |
| **Neo4j 4.x и ниже** | Нет `IF NOT EXISTS` для индексов (появилось в 5.x); `SHOW INDEXES` без `YIELD` даёт другой формат | Используйте `CALL db.schema.visualization()` для проверки; проверяйте существование перед созданием |
| **Параллельный рантайм** | `CALL db.awaitIndexes()` не поддерживается | Проверяйте `state` в `SHOW INDEXES` вручную с интервалами |
| **Neo4j 2025.02+** | `--schema` в bulk import поддерживается только для формата `block` (Enterprise Edition) | Для Community Edition или `standard`/`high_limit` форматов — создавайте индексы вручную после импорта |

### Начальная загрузка и схема

При массовой начальной загрузке индексы и ограничения можно создать в рамках самой загрузки — параметр `--schema` принимает файл с Cypher-командами. Поддерживается только в формате `block` (Enterprise Edition) начиная с Neo4j 2025.02; для остальных форматов индексы создаются вручную после импорта. Подробно — в [массовом импорте](./bulk_import.md).

## Устранение неполадок

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| `POPULATING` не завершается | `population` растёт медленно, индекс не `ONLINE` | Не хватает ресурсов: индекс заполняется в фоне и конкурирует с записью | Снизить нагрузку или перенести заполнение в окно низкой активности; не запускать массовую запись одновременно |
| План перестал использоваться после миграции | `Index not used` в `EXPLAIN` | Удалён индекс, на который опирался запрос, или появился более селективный | Сравнить план до и после; сбросить кэш планов `CALL db.clearQueryCaches()` |
| Каталог миграций рассинхронизирован | `validate-on-migrate` падает, chain разошёлся | Скрипт правили вручную в базе, либо разные версии каталога в разных окружениях | Вернуть окружения к единому каталогу; состояние чистится `neo4j-migrations clean` (удаляет данные о миграциях из выбранной schema database) |
| Constraint создаётся и сразу падает на данных | `Constraint validation failed` | Дубликаты или `null` в столбце, ужесточаемом ограничением | Найти и починить нарушения до создания ограничения, либо создавать в фоне и дочищать |
| Долгая транзакция после миграции | Растёт `db.tx_state.max_off_heap_memory`, «висят» `SHOW TRANSACTIONS` | Пакет слишком велик либо ограничение `LIMIT` отсутствует | Разбить на пакеты, добавить `LIMIT`, выполнять в `CALL { } IN TRANSACTIONS` |
| Удаление свойства идёт слишком долго | Запись транзакций растёт, клиенты жалуются на задержки | `REMOVE` на большой доле графа в одной транзакции | Пакетами, в фоне, с наблюдением за `neo4j_dbms_tx_state_max_off_heap_memory` |

## Лучшие практики

- **Expand → Contract — единственный безопасный порядок** для изменения формы данных. Обратный порядок ломает работающее приложение.
- **Индекс создавайте заранее, до того как запрос начнёт по нему ходить.** Пока индекс в `POPULATING`, он уже виден планировщику.
- **Пакет ограничивайте явно:** `LIMIT` внутри `CALL { } IN TRANSACTIONS` вместо hope-and-pray по памяти.
- **Состояние схемы — в репозиторий:** снимок `SHOW INDEXES` / `SHOW CONSTRAINTS` на каждом релизе, сравнение в CI.
- **Каталог миграций не редактируют после применения.** Нужна новая миграция; иначе цепочка расходится между окружениями.
- **Бэкап перед структурной миграцией** — обязателен, если миграция необратима.
- **Длинные backfill-миграции выносите из транзакции приложения** в отдельную процедуру с возможностью повторного запуска.
- **Не смешивайте миграции схемы и формата хранилища:** перевод базы в формат `block` — отдельная офлайн-операция, см. [миграцию формата хранилища](./backup_and_restore.md#миграция-формата-хранилища).
- **Миграция не завершена, пока все новые индексы не в состоянии `ONLINE`.** `SHOW INDEXES` проверяется до, во время и после; `CALL db.awaitIndexes()` — для ожидания готовности.
- **Окно обслуживания — не формальность:** не запускайте миграции одновременно с GDS-проекциями, бэкапами или пакетными задачами. Конкурирующая нагрузка искажает `POPULATING` и растягивает транзакции.
- **Не редактируйте Applied миграции вручную** — это разрывает цепочку и `validate-on-migrate` падает. Используйте `neo4j-migrations clean` только для сброса состояния на чистом стенде.
- **Для необратимых изменений — только бэкап, без автоматического отката.** Neo4j-Migrations не откатывает; откат — это новая миграция или восстановление из бэкапа.
