# Neo4j: Архитектура и хранение

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

## Определения

| Термин | Значение |
| :--- | :--- |
| **Store file** | Бинарный файл на диске, содержащий записи определённого типа (узлы, связи, свойства). |
| **Page cache** | Кэш в RAM, в котором хранятся страницы store-файлов и индексов для быстрого чтения. |
| **WAL (Write-Ahead Log)** | Транзакционный журнал, в котором фиксируются все изменения до записи в store-файлы. |
| **Checkpoint** | Момент в WAL, начиная с которого возможно восстановление после сбоя. |
| **Block format** | Формат хранения Enterprise Edition по умолчанию с 5.22; данные укладываются в 128-байтовые блоки. |
| **Aligned format** | Формат хранения по умолчанию в Community Edition; записи фиксированного размера со смещением. |
| **Token** | Элемент словаря: метка (label), тип связи (relationship type) или ключ свойства (property key). |
| **Dense node** | Узел с большим количеством связей одного типа; хранится в отдельном dense store. |
| **ID file** | Файл `.id`, содержащий список освобождённых ID для повторного использования. |
| **Native index** | B-tree индекс на свойствах узлов или связей, хранящийся в Lucene-файлах. |
| **Full-text index** | Lucene-индекс для полнотекстового поиска по свойствам. |
| **Vector index** | Индекс для поиска по векторным embedding (Enterprise). |

## Базовые понятия: процесс, служба, жизненный цикл

Neo4j работает как отдельный процесс JVM, управляемый через systemd. При старте процесс читает `neo4j.conf`, открывает служебную базу `system` и одну или несколько пользовательских баз. Движок последовательно инициализирует store-файлы, восстанавливает незавершённые транзакции из WAL и принимает подключения на Bolt (7687) и HTTP (7474).

**Жизненный цикл записи:**
1. Клиент отправляет Cypher через Bolt.
2. Планировщик строит план, движок получает блокировки на узлах/связях.
3. Изменения пишутся в transaction log (WAL) и в in-memory transaction state.
4. При `COMMIT` запись в WAL подтверждается, Transaction ID назначается.
5. Checkpoint периодически сбрасывает отложенные страницы из page cache в store-файлы.
6. После checkpoint старые transaction logs можно удалить.

## Index-free Adjacency (Смежность без индексов)

Ключевая особенность Neo4j. Каждый узел физически хранит указатели на свои входящие и исходящие связи. Это позволяет "проходить" по графу, не выполняя дорогостоящих операций поиска по индексам (Joins) на каждом шаге.

**Почему это важно:** В реляционной БД JOIN для N шагов обхода стоит $O(N \cdot \log K)$, где $K$ — размер таблицы. В Neo4j каждый шаг обхода стоит $O(1)$ независимо от размера графа.

## Транзакционный движок

Neo4j использует non-blocking reads и блокирующую запись:

- **Reads** — могут выполняться параллельно без блокировок (MVCC-подобный подход). Уровень изоляции по умолчанию — read-committed. Данные, прочитанные в рамках транзакции, не защищены от изменения другими транзакциями; non-repeatable reads возможны.
- **Writes** — атомарны в пределах одной транзакции; конкурентная запись управляется через Optimistic Locking. Блокировки захватываются автоматически на уровне узлов и связей. При конфликте транзакция записи перезапускается (retry).
- **Deadlock detection** — встроена в ядро управления транзакциями.

## Хранение на диске

### Store files

Данные хранятся в специализированных бинарных файлах (Store files):

- **Node Store:** Записи фиксированного размера для узлов.
- **Relationship Store:** Записи для связей, указывающие на начальный и конечный узлы, а также на следующую/предыдущую связь для обхода.
- **Property Store:** Хранение свойств (key-value пары). Мелкие свойства инлайнятся в основные store-файлы; большие выносятся в отдельные блоки.
- **String/Array Store:** Хранение длинных строк и массивов, не помещающихся инлайн.
- **Relationship Group Store:** Оптимизация для узлов с большим количеством связей одного типа (группировка связей в цепочки).

### Форматы хранения

Формат хранения определяет, как элементы графа укладываются в файлы на диске, и вместе с ним — жёсткие лимиты на размер графа.

| Формат | Редакция | Статус | Лимит узлов / связей |
| :--- | :--- | :--- | :--- |
| **`block`** | EE+ | По умолчанию для новых баз (с 5.22) | $2^{48}$ узлов (~281 трлн), связи и свойства без верхней границы |
| **`aligned`** | CE и EE | По умолчанию в CE | $2^{35}$ узлов и связей (~34 млрд), $2^{16}$ типов связей |
| **`high_limit`** | EE | **Устарел в 5.23** | $2^{50}$ узлов и связей (~1 квадриллион) |
| **`standard`** | CE и EE | **Устарел в 5.23** | $2^{35}$ узлов и связей |

**Почему `block` — рекомендуемый формат.** Свойства хранятся в блоках вместе с узлами и связями, а не в отдельных записях с переходами по указателям. Меньше обращений к диску на один запрос, лучше локальность данных, эффективнее расход памяти. В блок-формате данные укладываются в 128-байтовые блоки (`block.x1.db`); при превышении объёма данные перемещаются в dynamic store (`block.node.xd.db`, `block.relationship.xd.db`) или dense store (`block.relationship.dense.db` для hubs, `block.huge.db` для тысяч свойств).

**Проверка текущего формата:**

```cypher
SHOW DATABASES YIELD name, store;
// +----------------------------------+
// | name           | store           |
// +----------------------------------+
// | "neo4j"        | "block-block-1.1"  |
// | "system"       | "record-aligned-1.1" |
// +----------------------------------+
```

**Миграция формата** — операция офлайн, интенсивная по I/O: она переписывает все данные и меняет внутренние ID элементов. Требует места примерно на один размер базы, пересоздаёт индексы при первом старте. По документации: 100 ГБ база — от 10 минут в оптимальных условиях до более часа в худших.

**Критичный срок.** Поддержка `standard` и `high_limit` заканчивается вместе с LTS-релизом, запланированным на ноябрь 2026. После выхода этого LTS-релиза `high_limit`-базы **не запустятся**.

## Схема и индексы

Neo4j — schema-less по умолчанию: узел может получить любую метку и любое свойство в любой момент. Целостность обеспечивается индексами и ограничениями (constraints).

### Типы индексов

| Тип индекса | Назначение | Хранение |
| :--- | :--- | :--- |
| **Native (B-tree)** | Точечный поиск по свойству, диапазоны | Файлы Lucene в `schema/...` |
| **Composite** | Составной индекс по нескольким свойствам | Файлы Lucene |
| **Full-text** | Поиск по строковым свойствам | Lucene-индекс |
| **Vector** | Поиск по векторным embedding (EE) | Отдельный формат индекса |

Native индексы хранятся в директории `schema/` внутри каталога базы и обслуживаются через page cache, но их внутренняя структура — B-дерево Lucene, а не store-файлы графа. Это важно при планировании page cache: объём Lucene-индексов учитывается отдельно от объёма store-файлов.

### Ограничения (constraints)

| Тип ограничения | Редакция | Назначение |
| :--- | :--- | :--- |
| **UNIQUE** | CE, EE | Уникальность свойства |
| **EXISTS** | EE | Существование свойства |
| **TYPE** | EE | Тип свойства |
| **NODE KEY** | EE | Составной ключ узла |

Ограничения `EXISTS`, `TYPE` и `NODE KEY` — только в Enterprise Edition; базу с ними нельзя открыть в Community Edition.

## Память и page cache

Page cache — это область памяти, в которой хранятся страницы store-файлов и индексов для быстрого чтения. Page cache **не является частью JVM heap**. Данные графа и индексы читаются через page cache напрямую с диска, минуя JVM heap.

Размер page cache задаётся параметром `server.memory.pagecache.size` и должен покрывать рабочий набор store-файлов и Lucene-индексов. Формула планирования: `1.2 * (объём data + native indexes)`.

При недостатке page cache появляются page faults, и производительность обходов падает на порядки. Мониторинг: `page_cache_hit_ratio` (должен быть выше 0.98) и `page_cache_usage_ratio` (должен быть ниже 1.0).

## Восстановление (Crash Recovery)

Neo4j использует **WAL (Write-Ahead Log)** — все изменения сначала пишутся в транзакционный журнал, затем применяются к основным store-файлам. При старте движок replay'ит незавершённые транзакции из WAL.

Transaction log файлы содержат последовательность записей со всеми изменениями, сделанными в рамках каждой транзакции, включая данные, индексы и ограничения. По умолчанию логи хранятся в `<NEO4J_HOME>/data/transactions/<database-name>`, размер файла — 256 MiB, политика удержания — `2 days 2G`.

Checkpoint — это момент в WAL, начиная с которого возможно восстановление после сбоя. Процесс сбрасывает отложенные страницы из page cache в store-файлы, после чего старые transaction logs можно удалить.

## Пространство и дефрагментация

Store-файлы не сжимаются при удалении данных. Освобождённые записи помечаются как удалённые, их ID добавляются в `.id`-файлы и становятся доступными для повторного использования при создании новых записей. Это означает, что store-файлы могут стать sparse и фрагментированными, но производительское воздействие обычно минимально.

Для сокращения store-файлов используется `neo4j-admin database copy`, который создаёт дефрагментированную копию базы. В блок-формате начиная с 2026.01 большие значения свойств автоматически фрагментируются на несколько записей для гарантии повторного использования пространства.

## Операции и команды

### Просмотр store-файлов

```bash
# Общий объём store-файлов базы
du -sh /var/lib/neo4j/data/databases/neo4j/

# Размер transaction logs
du -sh /var/lib/neo4j/data/transactions/

# Список файлов store
ls -la /var/lib/neo4j/data/databases/neo4j/neostore.*
ls -la /var/lib/neo4j/data/databases/neo4j/block.*.db
```

### Проверка формата и информации

```cypher
-- Формат хранения баз
SHOW DATABASES YIELD name, store;

-- Размер базы и allocation
CALL dbms.listDatabases() YIELD name
RETURN name;
```

### Индексы

```cypher
-- Список индексов
SHOW INDEXES;

-- Размер индексов
SHOW INDEXES YIELD name, type, population, sizeBytes, readCount, writeCount;
```

### Управление WAL и checkpoint

```cypher
-- Принудительный checkpoint
CALL db.checkpoint();

-- Проверка настроек checkpoint
SHOW SETTINGS YIELD name, value WHERE name STARTS WITH 'db.checkpoint' RETURN name, value;
```

## Устранение неполадок

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| **Store files не помещаются в page cache** | Рост `page faults`, падение `hit_ratio` | `server.memory.pagecache.size` меньше рабочего набора | Увеличить page cache по формуле `1.2 * (данные + индексы)` |
| **Фрагментация store-файлов** | Размер базы растёт при удалении данных | Логическое удаление не возвращает место на диск | Выполнить `neo4j-admin database copy` для дефрагментации |
| **Ошибка формата при старте** | Сервер не стартует после обновления | `high_limit` формат на новом LTS | Перевести базу в `block` формат до обновления |
| **Рост WAL без pruning** | Диск заполняется `data/transactions` | Checkpoint не успевает за коммитами | Проверить `db.checkpoint.iops.limit`, интервалы checkpoint |
| **Dense node bottleneck** | Высокий latency на обходах через хаб | Узел с тысячами связей одного типа | Пересмотреть модель данных; в block format есть dense store, но проблема остаётся |
| **ID exhaustion** | Ошибка allocation при создании узлов | Превышен лимит ID для формата | Проверить формат базы; `aligned` ограничен $2^{35}$ |
| **Index corruption** | Ошибки при чтении индекса | Аварийное завершение, сбой диска | Пересоздать индекс: `DROP INDEX` → `CREATE INDEX` |

## Лучшие практики

- **Файловая система:** XFS предпочтительнее ext4 для больших баз: лучше работает с большими файлами и параллельными I/O. Монтирование с `noatime` снижает лишние записи. `nobarrier` опасен при отключённом write-back кэше на контроллере — только если есть батарейный кэш.
- **Разделение дисков:** transaction logs на отдельном устройстве — официальная рекомендация для максимальной производительности.
- **Мониторинг page cache:** отслеживайте `page_cache_hit_ratio` и `page_cache_usage_ratio`. `usage_ratio = 1.0` — прямой сигнал увеличить page cache, причём до того, как производительность упадёт.
- **Формат хранения:** для Enterprise Edition используйте `block` формат. Для Community Edition `aligned` — единственный доступный.
- **Не удаляйте `.id` файлы вручную:** store-файлы должны модифицироваться только движком Neo4j и инструментами `neo4j-admin`.
- **Планируйте миграцию формата как операцию с окном простоя:** 100 ГБ — от 10 минут до более часа; тестируйте на копии.
- **Векторные индексы в OS memory:** в Enterprise Edition векторные индексы загружаются в память ОС, а не в page cache. При наличии векторного поиска зарезервируйте для ОС дополнительную память.
- **Квотирование:** ограничьте место под `data/transactions` отдельной квотой — это защита от заполнения диска при сбое checkpoint.
