# Neo4j: Обновление версии и миграция

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

## Определения

| Термин | Значение |
| :--- | :--- |
| **CalVer** | Calendar Versioning, формат `YYYY.MM.PATCH`, принятый Neo4j с января 2025 года. |
| **SemVer** | Semantic Versioning `MAJOR.MINOR.PATCH`, использовавшийся в Neo4j 4 и 5. |
| **LTS** | Long-Term Support: релиз с трёхлетним окном поддержки, получающий критические исправления и security-обновления, но не новые функции. |
| **Breaking change** | Несовместимое изменение. В Neo4j такие изменения вносятся **только в релизе сразу после LTS**. |
| **LTS checkpoint** | Правило: при обновлении сервер обязан пройти через каждый LTS-релиз между текущей и целевой версией. |
| **Rolling upgrade** | Обновление кластера по одному серверу с сохранением доступности. |
| **Store format** | Формат store-файлов на диске; требует отдельной операции миграции. |
| **`db.query.default_language`** | Настройка версии Cypher по умолчанию для всего DBMS, для базы или на уровне запроса. |

## Базовые понятия: модель версионирования и что из неё следует

### Смена модели версионирования

С января 2025 года Neo4j использует календарную версию `YYYY.MM.PATCH` (`2025.01`, `2025.02` и так далее), а patch увеличивается для каждого релиза внутри месяца. Версии 4 и 5 использовали семантическую версию `MAJOR.MINOR.PATCH`, где MAJOR-версии архитектурно несовместимы с предыдущими.

CalVer может содержать четвёртый компонент — `LTS`. Новый LTS-релиз выходит примерно раз в **18–24 месяца** и получает **трёхлетнее окно поддержки**.

Актуальные статусы:

| Версия | Статус |
| :--- | :--- |
| Neo4j 2026.09 | Текущий релиз |
| Neo4j 5.26 | LTS, поддержка ветки 5 — до июня 2028 |
| Neo4j 4.4 | LTS, поддержка завершена 30 ноября 2025 |

### Окно breaking changes

Ключевое правило, из которого следует всё остальное: **несовместимые изменения вносятся только в релизе, непосредственно следующем за LTS.** Например, раздел breaking changes в документации описывает релиз 2025.01 — первый релиз после Neo4j 5.26 LTS.

Два следствия для планирования:

1. **Переход через LTS требует внимания.** В релизе сразу после LTS могут быть удалены устаревшие функции, изменены требования к ПО и значения конфигурации по умолчанию.
2. **Обновление идёт только через LTS-чекпоинты.** Если текущая версия и целевая разделены LTS-релизом, сервер обязан последовательно обновить до каждого LTS между ними — перепрыгнуть нельзя.

Конкретные удаления каждого релиза собраны в разделе [Breaking changes](https://neo4j.com/docs/operations-manual/current/breaking-changes/). Для примера, в релиз 2025.01, первом после 5.26 LTS, удалены discovery service v1, настройки `server.discovery.advertised_address` и `server.discovery.listen_address`, а параметры подключения `connect-randomly-to-server-group` и `connect-randomly-within-server-group` заменены на `connect-randomly-to-server-tags` и `connect-randomly-within-server-tags`.

### Версия Cypher отделена от версии сервера

Начиная с Neo4j 2025.06 язык Cypher развивается отдельно от сервера, и доступны две версии — Cypher 5 и Cypher 25. Выбор делается через `db.query.default_language` для всего DBMS, для отдельной базы или на уровне запроса.

Семантика зависит от выбранной версии:

| Умолчание | Что означает |
| :--- | :--- |
| Cypher 5 | Все запросы базы используют Cypher 5 **в том виде, в каком он был в релизе 2025.06**. Изменения после 2025.06 семантику не меняют |
| Cypher 25 | Запросы используют Cypher 25 в том виде, какой он есть в текущем релизе, включая изменения 2025.06, 2025.07, 2025.08 и далее |

Умолчание при обновлении и при новой установке:

| Сценарий | Существующие базы | Новые базы |
| :--- | :--- | :--- |
| Новая установка | — | Cypher 5 |
| Обновление | Cypher 5 | Cypher 5 |
| Обновление | Cypher 25 | Cypher 5 |

Практический смысл: **обновление сервера не меняет семантику запросов для баз с умолчанием Cypher 5.** Это делает обновление безопаснее, чем смена версии языка.

### Простои при обновлении

| Сценарий | Простой |
| :--- | :--- |
| Standalone | **Всегда требуется простой** |
| Кластер, переход 5.26 LTS → любой релиз 2025–2026 | Без простоя, поддерживается |
| Кластер, переход 4.4 → 5.26 | **Требуется простой**, плюс миграция баз со старого сервера на новый |

Сервер обновляется заменой бинарных файлов с последующим перезапуском — никакой отдельной процедуры «обновления на месте» для store-файлов это не подразумевает.

Порядок обновления кластера по одному серверу и требования к синхронизации ролей разобраны в [кластеризации](./clustering.md#планирование-rolling-upgrade).

### Формат хранилища

Обновление формата store — **необязательная** операция, если только целевая версия не удаляет поддержку вашего текущего формата. Между Neo4j 4.4 и любым релизом 2025–2026 изменений форматов хранилища нет.

Сама процедура миграции формата — офлайн, выполняется на каждом сервере отдельно и описана в [бэкапе и восстановлении](./backup_and_restore.md#миграция-формата-хранилища). Обновление версии сервера и миграция формата — **две независимые операции**, и их не следует совмещать в одном окне обслуживания без необходимости.

## Практические сценарии

### SRE-подход к обновлению: окно, RTO/RPO, наблюдение

Обновление версии — операция с RTO/RPO, как и любая миграция. Перед запуском зафиксируйте:

| Параметр | Значение по умолчанию | Что проверить |
| :--- | :--- | :--- |
| **Окно обслуживания** | 02:00–04:00 | Низкая нагрузка, нет бэкапов, нет GDS-проекций |
| **RTO** | 30 мин | Время, за которое можно откатиться к бэкапу или старой версии |
| **RPO** | 5 мин | Потери данных при откате (онлайн-бэкап перед обновлением) |
| **Наблюдение** | `query.log`, метрики, `SHOW DATABASES` | Проверять статусы баз до, во время и после |

**Критические замечания:**
- `CREATE INDEX`/`CREATE CONSTRAINT` возвращается мгновенно, но индекс строится в фоне. Обновление не завершено, пока `SHOW INDEXES` не покажет `ONLINE` для всех индексов.
- Standalone всегда требует простоя; кластер 5.26 LTS → 2025–2026 — без простоя.
- Миграция формата store — отдельная операция, она закрывает путь отката версии (см. [Откат](#откат)).

### Мониторинг во время обновления

Наблюдение строится вокруг трёх вопросов: стартует ли сервер, не изменились ли планы запросов, не сбилась ли производительность.

| Метрика | Где взять | Порог | Что означает |
| :--- | :--- | :--- | :--- |
| `neo4j_dbms_page_cache_hit_ratio` | Prometheus | < 95 % | Резкое падение — обновление вытеснило данные из кэша |
| `neo4j_dbms_vm_gc_time_percent` | Prometheus | > 10 % | Heap под давлением; см. [диагностику JVM](./jvm_diagnostics.md) |
| `neo4j_dbms_tx_state_max_off_heap_memory` | `SHOW TRANSACTIONS`, метрики | Рост без остановки | Длинная транзакция; проверьте, не висит ли сессия |
| `database.<db>.check_point.duration` | Prometheus | > 5 мин | Checkpoint под давлением; увеличьте `db.checkpoint.interval.time` |
| `SHOW DATABASES` → `currentStatus` | Cypher | `OFFLINE` | База не поднялась после обновления |
| `SHOW INDEXES` → `state` | Cypher | `POPULATING` | Индекс строится; дождитесь `ONLINE` |
| `SHOW CONSTRAINTS` → `state` | Cypher | Отсутствует | Ограничение не применилось; проверьте breaking changes |

**Чек-лист перед запуском:**
1. Отключите автоматические бэкапы на время обновления.
2. Остановите GDS-проекции — они конкурируют за heap и page cache.
3. Запустите онлайн-бэкап — единственная точка отката.
4. Запустите обновление и следите за метриками в реальном времени.
5. После старта — проверка `SHOW DATABASES`, `SHOW INDEXES`, `SHOW CONSTRAINTS`.

### Подготовка

Официальное руководство адресовано опытным администраторам и инженерам эксплуатации, обновляющим self-managed развёртывания, и рекомендует до изменений в production обязательно проверить на тестовом окружении:

- сам процесс обновления;
- совместимость с другими системами.

Практический список подготовки:

1. Онлайн-бэкап всех баз данных; проверить, что он читается, — см. [бэкап и восстановление](./backup_and_restore.md).
2. Зафиксировать текущие версии: сервер, драйверы, плагины, Java.
3. Проверить, не попадает ли целевая версия в окно breaking changes (релиз сразу после LTS) и не требует ли путь прохождения через промежуточный LTS.
4. Проверить Java: каждая версия сервера имеет свои требования. Neo4j 2025.01.0 и новее требует Java 21, начиная с 2025.10 поддерживается Java 25; Neo4j 5.26 LTS — последняя версия на Java SE 17.
5. Проверить драйверы: драйвер 6.x поддерживает серверы 4.4, 5 и релизов 2025–2026, но при обновлении сервера драйвер стоит обновить тоже.
6. Снять метрики до обновления — они будут базой сравнения.
7. Проверить, не используются ли удалённые настройки из [breaking changes](https://neo4j.com/docs/operations-manual/current/breaking-changes/).

### Обновление standalone

Простой обязателен:

```bash
# 1. Остановить сервис
sudo systemctl stop neo4j

# 2. Проверить конфигурацию новой версии до старта
sudo -u neo4j /var/lib/neo4j/bin/neo4j-admin server validate-config

# 3. Обновить пакет или заменить бинарные файлы
# 4. Запустить и дождаться готовности
sudo systemctl start neo4j
sudo systemctl status neo4j
```

```bash
# 5. Проверить состояние баз и индексов после старта
cypher-shell -u neo4j -p 'secret' "SHOW DATABASES YIELD name, currentStatus, access RETURN name, currentStatus, access"
```

### Обновление кластера

Обновление по одному серверу, с сохранением кворума:

```bash
# На каждом сервере по очереди, начиная с secondaries
sudo systemctl stop neo4j
# замена бинарных файлов
sudo systemctl start neo4j

# На leader — только после того, как все secondaries обновлены
```

На каждом шаге после старта проверяйте, что сервер вернулся в кластер и синхронизировался. Роли и порядок при переносе leader — в [кластеризации](./clustering.md#планирование-rolling-upgrade).

### В Kubernetes

Обновление выполняется через Helm с фиксацией тега образа; полная процедура — в [Kubernetes](./kubernetes_deployment.md#обновление-версии).

```yaml
image:
  customImage: neo4j:2026.09.0-enterprise
```

```bash
helm upgrade neo4j-standalone neo4j/neo4j -f values.yaml
```

### Восстановление после сбоя во время обновления

Сценарий: обновление началось, но не завершилось (сервер упал, диск переполнился, таймаут). Порядок действий:

1. **Не пытайтесь «дописать» обновление вручную.** Запускайте обновление заново — Neo4j не хранит состояние «обновления в процессе».
2. **Оцените состояние:** `SHOW DATABASES` — какие базы `ONLINE`, какие `OFFLINE`. `SHOW INDEXES` — какие индексы `ONLINE`, какие `POPULATING`. `SHOW CONSTRAINTS` — какие ограничения применены.
3. **Остановите нагрузку** — обновление и рабочая нагрузка конкурируют за page cache и CPU.
4. **Восстановите из бэкапа** — если обновление необратимо (удаление данных, изменение типа свойства). Онлайн-бэкап перед обновлением — единственная точка отката.
5. **Вернитесь к старой версии** — если формат store не мигрировал, это безопасно. Если формат мигрировал — только бэкап (см. [Откат](#откат)).
6. **Для `POPULATING` индексов:** дождитесь завершения или удалите и создайте заново. `DROP INDEX` на индексе в `POPULATING` безопасен; создание заново — медленнее, но предсказуемее.

**Важно:** обновление версии и миграция формата store — две независимые операции. Если формат уже мигрировал, откат версии возможен только через бэкап.

### Очистка после обновления

После успешного обновления, перед возвратом приложения в нормальный режим:

1. **Проверьте, что все базы `ONLINE`:**
   ```cypher
   SHOW DATABASES YIELD name, currentStatus
   WHERE currentStatus <> 'ONLINE'
   RETURN name, currentStatus;
   ```
2. **Проверьте, что все индексы `ONLINE`, а не `POPULATING`:**
   ```cypher
   SHOW INDEXES YIELD name, state
   WHERE state <> 'ONLINE'
   RETURN name, state;
   ```
3. **Очистите кэш планов и запросов**, чтобы следующие запросы строили планы на обновлённой схеме:
   ```cypher
   CALL db.clearQueryCaches();
   ```
4. **Проверьте, что `SHOW TRANSACTIONS` не показывает зависших транзакций** — сессии обновления должны быть закрыты.
5. **Соберите артефакты:** снимок схемы (`SHOW INDEXES`, `SHOW CONSTRAINTS`), `query.log`, конфигурацию, метрики во время обновления. Архивируйте с версией Neo4j и описанием изменений.
6. **Сравните схему с репозиторием** — убедитесь, что фактическое состояние соответствует ожидаемому.
7. **Включите обратную нагрузку** постепенно и проконтролируйте первые минуты: latency, page cache hit ratio, GC.
8. **Удалите устаревшие артефакты:** старые бинарные файлы, логи предыдущей версии, ненужные плагины.

### Критерии готовности обновления

Обновление считается завершённым, когда:

| Критерий | Проверка |
| :--- | :--- |
| Все базы `ONLINE` | `SHOW DATABASES` → `currentStatus = ONLINE` |
| Все индексы `ONLINE` | `SHOW INDEXES` → `state = ONLINE` |
| Все ограничения активны | `SHOW CONSTRAINTS` → все новые ограничения присутствуют |
| Планы запросов не изменились | `EXPLAIN` на типовых запросах — сравнение до/после |
| Производительность в норме | Метрики latency, page cache hit ratio, GC — в пределах базового уровня |
| Нет устаревших настроек | `neo4j.conf` — проверено против breaking changes целевой версии |
| Драйвер совместим | Версия драйвера поддерживает новую версию сервера |

### Проверка после обновления

```cypher
// Версии и статусы баз
SHOW DATABASES YIELD name, type, currentStatus, requestedStatus, default
RETURN name, type, currentStatus, requestedStatus, default;
```

```cypher
// Все индексы должны быть ONLINE, а не POPULATING
SHOW INDEXES YIELD name, state, population
RETURN name, state, population
ORDER BY state;
```

```cypher
// Планы на ключевых запросах не должны измениться
PROFILE
MATCH (p:Person {email: $email})-[:FRIENDS_WITH*1..2]->(f)
RETURN f.name AS name LIMIT 10;
```

Сравните метрики с зафиксированными до обновления: latency, page cache hit ratio, долю времени в GC, длительность checkpoint. Проверьте также, что удалённые настройки из breaking changes не остались в `neo4j.conf`.

### План отката

Перед запуском обновления зафиксируйте, в каком случае и каким способом откатываться:

| Ситуация | Способ отката | Условие |
| :--- | :--- | :--- |
| Сервер не стартует | Возврат к старым бинарным файлам и перезапуск | Формат store не мигрировал |
| Запросы стали падать | Возврат к старым бинарным файлам + смена `db.query.default_language` на Cypher 5 | Формат store не мигрировал |
| Производительность упала | Возврат к старой версии | Формат store не мигрировал |
| Кластер не собирает кворум | Восстановление из бэкапа | Формат store мигрировал или бэкап — единственная точка отката |
| Потеря данных | Восстановление из онлайн-бэкапа или PITR | Всегда |

**Ключевое правило:** формат store мигрируется вперёд надёжно, назад — нет. Миграция формата — отдельная операция, и её не следует совмещать с обновлением версии: она закрывает путь отката версии.

### Откат

| Что откатываем | Способ |
| :--- | :--- |
| Версию сервера | Возврат к прежним бинарным файлам и перезапуск; **только если формат store не был мигрирован** |
| Данные | Восстановление из онлайн-бэкапа или PITR |
| Формат store | Отдельная операция, обратный путь — миграция в предыдущий формат |

**Формат хранилища мигрируется вперёд надёжно, назад — нет.** Именно поэтому миграцию формата не стоит совмещать с обновлением версии: она закрывает путь отката.

## Устранение неполадок

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| Сервер не стартует после обновления | Падение на старте, ошибка в логе | Неизвестная или удалённая настройка | `neo4j-admin server validate-config` до старта; сверить с breaking changes |
| Кластер не собирает кворум | Часть серверов вышла | Обновлён leader раньше второстепенных | Возвращать порядок: сначала secondaries, затем leader |
| `Store format not supported` | Отказ запуска | Текущий формат удалён в целевой версии | Проверить матрицу форматов по версиям; мигрировать формат до обновления |
| Запросы стали падать после обновления | Ошибки синтаксиса или семантики | Базы с умолчанием Cypher 25 | Проверить `db.query.default_language`; временно вернуть Cypher 5 |
| Новая настройка не применяется | Поведение не изменилось | Значение изменилось по умолчанию в релизе после LTS | Сверяться с документацией целевой версии; зафиксировать значения явно |
| Драйвер несовместим с сервером | Ошибки соединения | Устаревшая версия драйвера | Обновить драйвер до версии, поддерживающей новый сервер |
| Требуется промежуточный LTS | Ошибка при попытке перехода | Путь пересекает LTS-релиз | Обновляться последовательно через каждый LTS-чекпоинт |
| Standalone без простоя | Невозможно согласовать окно | Standalone всегда требует простоя | Развернуть кластер либо заложить окно обслуживания |

## Лучшие практики

- **Готовьтесь на тестовом окружении:** и процесс обновления, и совместимость с другими системами — это прямое требование руководства.
- **Миграцию формата store делайте отдельным окном.** Она закрывает путь отката версии.
- **Не совмещайте обновление версии и смену версии Cypher.** Для баз с умолчанием Cypher 5 обновление сервера семантику запросов не меняет.
- **Проверяйте окно breaking changes:** релиз сразу после LTS — единственное место, где удаляются настройки.
- **Режим CDC проверяйте отдельно.** Если на базе включён CDC, обновление меняет версии сервера, а структура потока зависит от режима; сверьтесь с [CDC](./cdc_integration.md).
- **Фиксируйте метрики до и после** и сравнивайте их: одинаковые нагрузки дают сопоставимые цифры.
- **Держите бэкап, проверенный на чтение.** Бэкап, который не открывается, не является точкой отката.
- **Обновляйте драйверы вместе с сервером.** Драйвер 6.x поддерживает всю линейку, но новее сервер — новее драйвер.
- **В кластере обновляйте secondaries первыми.** Обновление leader последним сохраняет доступность.
- **Не выполняйте Cypher-административные команды во время rolling upgrade.** Для координации используйте `/dbms/cluster/status` (см. [кластеризацию](./clustering.md)).
- **Планируйте откат до запуска.** Формат store мигрируется вперёд, назад — нет; если формат уже мигрировал, откат — только через бэкап.
- **Окно обслуживания — не формальность:** не запускайте обновление одновременно с GDS-проекциями, бэкапами или пакетными задачами.
- **Проверяйте `SHOW INDEXES` после обновления.** Индекс в `POPULATING` — обновление не завершено.
