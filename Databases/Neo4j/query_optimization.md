# Neo4j: Оптимизация запросов

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

## Определения

| Термин | Значение |
| :--- | :--- |
| **Planner** | Компонент, выбирающий стратегию построения плана: `COST` (по умолчанию), `IDP`, `DP`. |
| **Runtime** | Механизм исполнения плана: `slotted`, `pipelined`, `parallel`. |
| **DbHits** | Обращения к engine в `PROFILE`; первичная метрика стоимости запроса. |
| **Page fault** | Промах page cache: страница store-файла не найдена в RAM, требуется чтение с диска. |
| **Anchor point** | Узел или связь, с которого начинается обход; должен быть найден через индекс. |
| **NodeByLabelScan** | План операции: полное сканирование всех узлов с меткой. Признак отсутствия индекса. |
| **Expand** | Операция обхода связей от узла; основная нагрузка в графовых запросах. |
| **Variable-length expansion** | Обход переменной длины `[:TYPE*min..max]`; может привести к combinatorial explosion. |
| **Query plan cache** | Кэш планов запросов; переиспользуется при повторном выполнении того же текста с теми же параметрами. |
| **Cypher 25** | Активная ветвь языка; добавляет синтаксис и изменяет семантику некоторых конструкций, влияя на оптимизацию. |

## Базовые понятия: как выполняется запрос

Запрос проходит три стадии: **планирование**, **компиляция**, **исполнение**.

1. **Планировщик (Planner)** выбирает стратегию. По умолчанию `COST` — строит несколько
   кандидатных планов и выбирает самый дешёвый по оценке. `IDP` — для запросов с большим
   количеством паттернов. `DP` — динамическое программирование, редко нужен принудительно.
2. **Компилятор** строит логический план, оптимизирует его и преобразует в физический.
3. **Рантайм (Runtime)** исполняет физический план. Выбор рантайма влияет на параллелизм
   и потребление памяти, но не на план himself.

**Ключевое правило:** индексы используются только для поиска **anchor points** — начальных
узлов обхода. Сами связи обходятся через Index-free adjacency и не используют индексы.

## Анализ планов: EXPLAIN и PROFILE

### Различие

| Команда | Что делает | Когда использовать |
| :--- | :--- | :--- |
| `EXPLAIN` | Показывает план без выполнения запроса | Проверка структуры плана, сравнение рантаймов |
| `PROFILE` | Запускает запрос, показывает реальные DbHits, время, page faults | Измерение на репрезентативных данных |

```cypher
// EXPLAIN — без запуска, только план
EXPLAIN
MATCH (p:Person {email: $email})-[:WORKS_AT]->(c:Company)
RETURN p.name, c.name;
```

```cypher
// PROFILE — реальное выполнение с метриками
PROFILE
MATCH (p:Person {email: $email})-[:WORKS_AT]->(c:Company)
RETURN p.name, c.name;
// → DbHits: 3 (или меньше с индексом)
```

### Что смотреть в выводе PROFILE

**Обязательные поля:**

| Поле | Значение |
| :--- | :--- |
| `DbHits` | Обращения к engine; основной показатель стоимости. Должен быть минимальным. |
| `Rows` | Количество строк, прошедших через операцию. РостRows между операциями — cartesian product или фильтрация. |
| `time` | Wall-clock время операции. |

**Диагностические операторы:**

| Оператор | Что означает | Действие |
| :--- | :--- | :--- |
| `NodeByLabelScan` | Полное сканирование узлов с меткой | Создать индекс на свойство из `MATCH` |
| `DirectedRelationshipTypeScan` | Сканирование всех связей типа | Проверить, есть ли индекс на стартовом узле |
| `Expand(All)` | Обход всех связей без фильтра | Указать тип связи `-[:TYPE]->` |
| `CartesianProduct` | Декартово произведение наборов | Добавить связь между паттернами или `WITH` для ограничения |
| `Sort` | Сортировка, не покрытая индексом | Добавить составной индекс или ограничить `LIMIT` до сортировки |

```cypher
// Признак проблемы: NodeByLabelScan в плане
PROFILE MATCH (p:Person {name: 'Alice'})-[:FRIENDS_WITH]->(f)
RETURN f.name;
// Если в плане есть NodeByLabelScan — индекса нет или он не используется
```

### Сравнение рантаймов

```cypher
// Сравнение slotted и pipelined на одном запросе
EXPLAIN CYPHER runtime=slotted MATCH (a)-[:DEPENDS_ON]->(b) RETURN count(*);
EXPLAIN CYPHER runtime=pipelined MATCH (a)-[:DEPENDS_ON]->(b) RETURN count(*);
// → Planner COST / Runtime SLOTTED / Runtime version 2026.09
```

`parallel` поддерживает только чтение и не работает, если в транзакции уже были изменения.
Подбор рантайма вручную — последнее средство: сначала индексы и параметризация.

## Стратегии индексирования

### Типы индексов и когда использовать

| Тип | Синтаксис создания | Когда использовать |
| :--- | :--- | :--- |
| **Range Index** (B-tree) | `CREATE INDEX FOR (n:Label) ON (n.prop)` | Точечный поиск, диапазоны, сортировка |
| **Composite Index** | `CREATE INDEX FOR (n:Label) ON (n.a, n.b)` | Фильтрация по нескольким свойствам одновременно |
| **Full-text Index** | `CREATE FULLTEXT INDEX … FOR (n:Label) ON EACH [n.prop]` | Нечёткий поиск по строкам (Lucene) |
| **Point Index** | `CREATE POINT INDEX FOR (n:Label) ON (n.coordinates)` | Пространственные запросы |
| **Token Index** | Автоматически на метках | Быстрый доступ ко всем узлам метки; не заменяет индекс на свойства |

```cypher
// Range Index — базовый поиск
CREATE INDEX person_email FOR (p:Person) ON (p.email);

// Composite — фильтрация по двум свойствам
CREATE INDEX person_name FOR (p:Person) ON (p.lastName, p.firstName);

// Full-text — поиск по строковым полям
CREATE FULLTEXT INDEX personSearch FOR (p:Person) ON EACH [p.name, p.bio];

// Point — пространственные запросы
CREATE POINT INDEX location_coords FOR (n:Location) ON (n.coordinates);

// Просмотр всех индексов
SHOW INDEXES YIELD name, type, state, population, sizeBytes, readCount, writeCount;

// Удаление
DROP INDEX person_email;
```

### Когда НЕ создавать индекс

- **Свойства, не используемые в anchor points.** Индекс на `p.age` не поможет, если все
  запросы начинаются с `MATCH (p:Person {email: $email})`.
- **Низкокардинальные свойства.** Индекс на булево поле с двумя значениями не даёт
  преимущества — planner предпочтёт полное сканирование.
- **Свойства с высокой частотой обновлений.** Каждая запись переиндексируется; для
  активно меняющихся полей избыточный индекс — это лишний I/O.
- **Связи вместо узлов.** Индексы создаются только на свойствах узлов или связей, но не на
  типах связей. Фильтрация по типу связи `-[:TYPE]->` выполняется без индекса.

### Полезные сведения

- **Индексы строятся фоново.** Создание индекса не блокирует запросы. Проверяйте состояние
  `state` в `SHOW INDEXES`: `ONLINE` — готов, `POPULATING` — строится.
- **Индексные подсказки.** Если planner выбирает неверный план, можно принудительно указать
  индекс, но это редко needed: обычно достаточно параметризации и актуальной статистики.

```cypher
// Принудительное использование индекса
MATCH (p:Person)
USING INDEX p:Person(email)
WHERE p.email = $email
RETURN p;
```

## Правила написания эффективных запросов

### 1. Метки и направление связей

```cypher
// Плохо: без метки — сканирование всех узлов
MATCH (n) RETURN n;

// Хорошо: метка ограничивает пространство поиска
MATCH (n:Person) RETURN n;

// Плохо: не указано направление — ищет в обе стороны
MATCH (a)-[:FRIENDS_WITH]-(b) RETURN a, b;

// Хорошо: направление известно — сокращает пространство поиска вдвое
MATCH (a)-[:FRIENDS_WITH]->(b) RETURN a, b;
```

### 2. Параметризация

Всегда используйте параметры вместо констант. Это позволяет переиспользовать планы:

```cypher
// Правильно: план переиспользуется для разных значений
MATCH (p:Person {email: $email})-[:WORKS_AT]->(c:Company)
RETURN p.name, c.name;

// Неправильно: каждый текст — отдельный план
MATCH (p:Person {email: 'alice@example.com'})-[:WORKS_AT]->(c:Company)
RETURN p.name, c.name;
```

### 3. Сначала фильтрация, потом обход

Используйте `WITH` для ограничения набора данных перед выполнением тяжелых `MATCH`:

```cypher
// Сначала фильтруем, потом обходим
MATCH (p:Person {active: true})
WITH p LIMIT 1000
MATCH (p)-[:WORKS_AT]->(c:Company)
RETURN p.name, c.name;
```

### 4. Ограничивайте переменную длину

Без ограничений `[:TYPE*]` — потенциальный обход всего графа:

```cypher
// Плохо: без ограничений — может обойти весь граф
MATCH (a)-[:FRIENDS_WITH*]->(b) RETURN a, b;

// Хорошо: ограничьте глубину
MATCH (a)-[:FRIENDS_WITH*1..3]->(b) RETURN a, b;

// Для проверки связности достаточно 1
MATCH (a)-[:FRIENDS_WITH*1..1]-(b) RETURN a, b;
```

### 5. Пакетная обработка

Импорт и массовые изменения выполняются пачками, а не одной транзакцией:

```cypher
// Пакетная запись через CALL { } IN TRANSACTIONS
MATCH (n:Person {status: 'pending'})
CALL {
  WITH n
  SET n.processed = true
} IN TRANSACTIONS OF 1000 ROWS
RETURN count(*) AS updated;
```

### 6. Агрегация и DISTINCT

Агрегация с `DISTINCT` на больших наборах — expensive. Используйте `WITH` для
предварительной дедупликации:

```cypher
// Плохо: DISTINCT на всём результате
MATCH (p:Person)-[:FRIENDS_WITH]->(f)
RETURN p.name, count(DISTINCT f) AS friends;

// Хорошо: предварительная дедупликация
MATCH (p:Person)-[:FRIENDS_WITH]->(f)
WITH p, f
LIMIT 10000
RETURN p.name, count(f) AS friends;
```

### 7. OPTIONAL MATCH

Каждый `OPTIONAL MATCH` может умножить количество строк. Используйте `LEFT JOIN`-эквивалент
только когда нужно, и ограничивайте левую часть:

```cypher
MATCH (p:Person {email: $email})
OPTIONAL MATCH (p)-[:FRIENDS_WITH]->(f)
RETURN p.name, collect(f.name) AS friends;
```

## Кэш планов запросов

Neo4j кэширует планы запросов. План переиспользуется, когда текст запроса и типы параметров
совпадают.

### Очистка кэша

```cypher
-- Сброс всех кэшированных планов
CALL db.clearQueryCaches();
```

### Что сбрасывает кэш

- Изменение схемы (создание/удаление индекса)
- Анализ статистики (`ANALYZE`)
- Изменение конфигурации, влияющей на план

```cypher
-- Принудительный пересбор плана после изменения индекса
CALL db.clearQueryCaches();
```

## Мониторинг производительности запросов

### query.log (Enterprise)

`query.log` — основной источник данных о стоимости запросов. Включите пороговое логирование,
чтобы не собирать все запросы:

```conf
# Логировать только запросы дольше 100ms
db.logs.query.enabled=INFO
db.logs.query.threshold=100ms
```

Запись в `query.log`:

```plain
2026-06-22 13:45:54.597+0000 INFO id:34 - transaction id:6 - 195 ms:
(planning: 185, waiting: 0) - 68 page hits, 0 page faults -
neo4j-javascript/6.0.1 client/127.0.0.1:53864 server/127.0.0.1:7687>
MATCH (n:Person {name:'Tom Hanks'})-[:ACTED_IN]->(n1:Movie)<-[:DIRECTED]-(n2:Person)
RETURN n1.title - {app: 'query', type: 'user-direct'}
```

**Как читать:**
- `planning: 185` близко к общему времени `195 ms` — план строится заново, пересмотрите
  параметризацию.
- `page faults: 0` — page cache покрывает запрос. Ненулевой `page faults` — увеличьте
  `server.memory.pagecache.size`.
- `waiting: 0` — нет contention по блокировкам.

### Метрики

| Метрика | Что показывает | Порог |
| :--- | :--- | :--- |
| `neo4j_dbms_page_cache_hit_ratio` | Доля попаданий в page cache | ниже 0.98 — page cache undersized |
| `neo4j_dbms_vm_gc_time_percent` | Доля времени в GC | резкий рост — запросы потребляют слишком много heap |
| `neo4j_database_<db>_check_point_duration` | Длительность checkpoint | приближается к интервалу — checkpoint не успевает |
| `neo4j_database_<db>_transaction_last_committed_tx_id` | Последний закоммиченный tx ID | должен расти линейно; плато — репликация остановилась |

Полный справочник метрик — в [мониторинге](./monitoring.md).

### Запросы для диагностики

```cypher
-- Текущие транзакции: сортировка по elapsedTime
SHOW TRANSACTIONS
YIELD transactionId, currentQuery, elapsedTime, status, currentQueryAllocatedBytes, pageFaults
ORDER BY elapsedTime DESC
LIMIT 10;

-- Память: потребление пулов
CALL dbms.listPools();

-- Проверка настроек
SHOW SETTINGS YIELD name, value WHERE name STARTS WITH 'db.checkpoint' RETURN name, value;
```

## Устранение неполадок

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| **Высокий DbHits** | `PROFILE` показывает тысячи DbHits | Нет индекса на anchor point | Создать индекс на свойство из `MATCH (n:Label {prop: $val})` |
| **NodeByLabelScan** | `PROFILE` показывает полное сканирование | Нет индекса или не используется anchor point | Добавить индекс или уточнить паттерн |
| **Page faults > 0** | В `PROFILE` или `query.log` есть page faults | Page cache меньше рабочего наета | Увеличить `server.memory.pagecache.size` по формуле `1.2 × (data + native indexes)` |
| **Cartesian product** | В плане оператор `CartesianProduct` | Отсутствует связь между паттернами | Добавить связь или `WITH` для ограничения |
| **Длинный planning** | `planning` близок к общему времени в `query.log` | План не кэшируется или пересобирается | Проверить параметризацию; `CALL db.clearQueryCaches()` после изменения схемы |
| **OutOfMemoryError** | Запрос падает, база жива | Транзакция превышает лимит heap | Снизить `dbms.memory.transaction.total.max`; разбить на батчи |
| **Combinatorial explosion** | Запрос зависает на `*` без ограничения | Переменная длина без `min..max` | Добавить ограничение глубины |
| **Ошибка `PropertyKeyNotFound`** | Запрос падает на несуществующем свойстве | Свойство удалено или опечатка | Проверить наличие свойства через `apoc.meta.*` или `CALL db.propertyKeys()` |
| **Timeout** | `TransactionTimeout` | Запрос не завершается за лимит | Увеличить `db.transaction.timeout` или оптимизировать запрос |
| **GDS/APOC медленнее Cypher** | Процедура работает дольше ручного запроса | Проекция/подготовка стоит дороже работы | Для небольших графов используйте прямой Cypher; см. [graph_data_science.md](./graph_data_science.md) |

## Разбор инцидента: от жалобы до исправления

Таблица выше даёт соответствие «симптом → причина». Ниже — сквозной порядок действий, когда
жалоба приходит из приложения («запрос отвалился по таймауту») и нужно дойти до конкретного
исправления. Порядок шагов важнее скорости: пропуск первого шага приводит к оптимизации
не того запроса.

**Шаг 1. Найти запрос в момент жалобы.** Пока пользователь ещё ждёт, снять картину по базе:

```cypher
SHOW TRANSACTIONS
YIELD transactionId, currentQuery, elapsedTime, status, currentQueryAllocatedBytes, pageFaults
ORDER BY elapsedTime DESC
LIMIT 10;
```

`elapsedTime` и `pageFaults` сразу делят все случаи на два класса:

| Что видно | Класс проблемы | Переходить к шагу |
| :--- | :--- | :--- |
| Большой `elapsedTime` при нулевых `pageFaults` | Запрос упирается в вычисления: план, объём промежуточных результатов, блокировки | Шаг 3 |
| Ненулевые `pageFaults` | Запрос упирается в ввод-вывод: данных больше, чем в кэше | Шаг 2 |

Если момент жалобы прошёл, работаем с журналом: `query.log` содержит и текст запроса, и
`planning`/`pagecache`/`pagehits` — разбор записи в [мониторинге](./monitoring.md#querylog-разбор-записи).

**Шаг 2. Проверить, это кэш или память.**

```cypher
SHOW TRANSACTIONS
YIELD transactionId, currentQuery, pageFaults, currentQueryPageHits
WHERE pageFaults > 0
RETURN transactionId, pageFaults, currentQueryPageHits, currentQuery
LIMIT 10;
```

- Ненулевые `pageFaults` при низком `neo4j_dbms_page_cache_hit_ratio` → дефицит памяти под кэш. Увеличить `server.memory.pagecache.size` по формуле `1.2 × (данные + индексы)`, а не оптимизировать запрос.
- `pageFaults` при высоком hit ratio → страницы запрашиваются правильно, но кэш мал для конкретного горячего подмножества. Ищите запрос с большим `currentQueryPageHits` — он и определяет рабочий набор.

**Шаг 3. Снять план именно того запроса.** Не «похожего», а того, что в `currentQuery`:

```cypher
PROFILE
MATCH (p:Person {email: $email})-[:FRIENDS_WITH*1..3]->(f:Person)
RETURN f.email AS email, f.name AS name;
```

Читать вывод в порядке, заданном разделом «Что смотреть в выводе PROFILE»:

| Что найдено | Значит | Шаг 4 |
| :--- | :--- | :--- |
| `NodeByLabelScan` или `NodeByElementIdScan` | Нет индекса на anchor point | 4a |
| `DbHits`, пропорциональный объёму строк | Нет индекса, идёт фильтрация по свойству | 4a |
| `CartesianProduct` | Два независимых паттерна без связи между ними | 4b |
| `Expand(All)` с большой `cardinality` на хабе | Обход через супернод | 4c |
| Долгий `planning` при малом времени исполнения | План не кэшируется | 4d |

**Шаг 4a. Нет индекса.** Создать индекс на свойство, по которому начинается `MATCH`, дождаться состояния `ONLINE`, пересобрать план:

```cypher
CREATE INDEX person_email IF NOT EXISTS FOR (p:Person) ON (p.email);
SHOW INDEXES YIELD name, state, population RETURN name, state, population;
```

```cypher
CALL db.awaitIndexes(300);
```

Индекс должен быть `ONLINE`, и только после этого `PROFILE` покажет реальный план. Если после создания индекса план не изменился — проверьте, не участвует ли свойство в часто обновляемом поле (см. «Когда НЕ создавать индекс»).

**Шаг 4b. Cartesian product.** Связать паттерны явной связью или ограничить промежуточный результат:

```cypher
MATCH (c:Company {id: $companyId})
MATCH (p:Person)-[:WORKS_AT]->(c)
RETURN p.name AS name;
```

**Шаг 4c. Обход через хаб.** Индекс тут не поможет — проблема в структуре данных. Разбор и варианты разбиения — в [антипаттернах моделирования](./data_modeling_antipatterns.md).

**Шаг 4d. План не кэшируется.** Проверьте параметризацию; после изменения схемы кэш планов сбрасывают:

```cypher
CALL db.clearQueryCaches();
```

**Шаг 5. Проверить, помогло ли.** Критерий проверки — не «стало быстрее», а конкретные цифры:

```cypher
PROFILE
MATCH (p:Person {email: $email}) RETURN p.id AS id;
```

Сравните с исходным снимком: `DbHits`, `pagehits`, `pagecache`, `time`. Затем сверьте метрики на той же нагрузке — `neo4j_dbms_page_cache_hit_ratio`, `neo4j_database_<db>_db_query_execution_latency_millis`.

**Шаг 6. Не помогло — расширять круг.** Если запрос оптимизирован, а таймауты остались, проблема вне запроса: нехватка ресурсов пула Bolt, GC, длинные транзакции. Диагностика по этим осям — в [оптимизации и мониторинге](./monitoring.md), разбор памяти процесса — в [диагностике на уровне JVM](./jvm_diagnostics.md).

Полезно завести метку транзакции: `tx.setMetaData({app: ..., type: ...})` кладёт в `query.log` имя
приложения, и поиск источника нагрузки становится точным. Это же рекомендовано в
[обслуживании](./operations.md#лучшие-практики).

## Cypher 25: изменения, влияющие на оптимизацию

Cypher 25 добавляет синтаксис и изменяет семантику некоторых конструкций. Это влияет на
поведение оптимизатора и стоимость запросов.

### Ключевые изменения

| Изменение | Влияние на оптимизацию |
| :--- | :--- |
| `IS [NOT] LABELED` | Позволяет фильтровать по метке без дополнительного `MATCH`; план упрощается |
| Правила `MERGE` | Изменены правила разрешения свойств в `MERGE`; проверяйте планы после миграции |
| `CALL { } IN TRANSACTIONS` | Стандартный способ пакетной обработки; `apoc.periodic.iterate` объявлен устаревшим |

```cypher
-- Cypher 25: фильтрация по метке без дополнительного MATCH
MATCH (n)
WHERE n IS Person AND n.age > 25
RETURN n;

-- Явное указание версии языка для отладки
CYPHER 5 MATCH (n:Person) RETURN count(n);
```

Глобальное значение задаётся через `db.query.default_language` в `neo4j.conf`. Уровень
языка фиксируется в момент создания базы — при миграции проверяйте планы на обеих версиях.

## Лучшие практики

- **Индексируйте anchor points.** Каждый `MATCH (n:Label {prop: $val})` должен иметь индекс
  на `prop`. Без индекса запрос сканирует все узлы с меткой.
- **Параметризуйте запросы.** Константы в тексте запроса создают новый план на каждое
  значение. Параметры `$name` переиспользуют план.
- **Указывайте тип связи.** `(a)-[:TYPE]->(b)` сокращает пространство поиска вдвое по
  сравнению с `(a)-[:TYPE]-(b)`.
- **Ограничивайте переменную длину.** Всегда указывайте `min..max`; без ограничений запрос
  может обойти весь граф.
- **Используйте `WITH` для ограничения набора.** Фильтрация и `LIMIT` перед обходом
  сокращают количество строк, проходящих через следующие операции.
- **Не пересоздавайте индексы часто.** Каждое создание — I/O-интенсивная операция на всю базу.
- **Проверяйте планы на репрезентативных объёмах.** Тестовые данные на 100 узлах не покажут
  проблем, которые появятся на миллионах.
- **Сравнивайте рантаймы через EXPLAIN, а не PROFILE.** `PROFILE` выполняет запрос; для
  сравнения планов достаточно `EXPLAIN`.
- **Мониторьте page cache через метрики.** `page_cache_hit_ratio` ниже 0.98 — сигнал
  увеличить page cache. `page_cache_usage_ratio = 1.0` — страница исчерпана.
- **Фиксируйте `neo4j.conf` в репозитории.** Конфигурация — часть состояния системы;
  воспроизводимость важнее удобства редактирования на месте.
- **Используйте транзакционные функции в драйверах.** Автоматические ретраи и управление
  сессиями — в драйверах 6.x; подробности — в [драйверах](./drivers.md).
