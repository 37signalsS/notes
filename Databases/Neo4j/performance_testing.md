# Neo4j: Нагрузочное тестирование

**Актуально для:** Neo4j 2026.09.x / 5.26.x LTS

## Определения

| Термин | Значение |
| :--- | :--- |
| **Benchmarking** | Измерение производительности в одинаковых условиях для сравнения конфигураций, версий или СУБД. |
| **Load testing** | Проверка поведения системы под нагрузкой, приближенной к продуктовой или превышающей её. |
| **Рабочий набор** | Объём данных, к которому система обращается; именно он должен помещаться в page cache. |
| **Page cache hit ratio** | Доля попаданий в кэш; ниже 98 % означает чтение с диска. |
| **Прогрев (warmup)** | Прогон нагрузки до начала измерения, чтобы JIT и кэш пришли в установившийся режим. |
| **`query.log`** | Журнал медленных запросов; источник данных о фактической нагрузке. |
| **PTLC** | Percentile of Time to Last Complete — метрика «время до последней полной обработки» в нагрузочных тестах. |

## Базовые понятия: где Neo4j ломает наивный тест

Методология нагрузочного тестирования общая и в базе уже изложена: [бенчмаркинг СУБД](../Concepts/benchmarking.md), [методология тестирования производительности](../../Testing/performance_testing_methodology.md), инструменты — [k6](../../Testing/k6_load_testing.md), [JMeter](../../Testing/jmeter_load_testing.md), [Gatling](../../Testing/gatling_load_testing.md), [Yandex Tank](../../Testing/yandex_tank_taurus.md), [HammerDB](../Concepts/hammerdb.md). Здесь — только специфика графовой базы, из-за которой результат с чужими инструментами получается неверным.

**Пять вещей, которые ломают тест Neo4j:**

| Фактор | Что делает | Как учесть |
| :--- | :--- | :--- |
| **Тёплый кэш** | Первый прогон измеряет диск, второй — память; разница кратна | Обязательный прогрев, оба состояния измерять отдельно и подписывать |
| **JIT** | Первые тысячи запросов исполняются интерпретированно | Прогрев до установившейся latency, замер после |
| **Заполнение индексов** | Индекс в `POPULATING` отнимает ресурсы и искажает картину | Проверить `state` в `SHOW INDEXES` до замера |
| **Checkpoint и WAL** | Сброс страниц и ротация журналов создают всплески задержек | Длительность замера — кратна нескольким циклам checkpoint |
| **Проекции GDS** | Графовые алгоритмы занимают heap и page cache, конкурируя с обычными запросами | Замер раздельно: с проекциями и без |

Отдельно про объём данных: если данные помещаются в память, тест измеряет работу с кэшем, а не поведение СУБД под нагрузкой ввода-вывода. Правила подготовки среды — в [бенчмаркинге СУБД](../Concepts/benchmarking.md).

### Что измерять

| Метрика | Где взять | Зачем |
| :--- | :--- | :--- |
| p95 / p99 latency запросов | `query.log`, гистограмма `database.<db>.db.query.execution.latency.millis` | Пользовательская боль |
| Page cache hit ratio | `neo4j_dbms_page_cache_hit_ratio` | Не читает ли база с диска вместо кэша |
| Доля времени в GC | `neo4j_dbms_vm_gc_time_percent` | Не вытесняют ли паузы сборщика мусора |
| Длительность checkpoint | `database.<db>.check_point.duration` | Не наезжает ли checkpoint на интервал |
| Page faults | `PROFILE`, `query.log` | Фактические обращения к диску |
| Размер transaction log, скорость роста | файлы журнала, метрики | Хватает ли места и успевает ли pruning |
| Число соединений Bolt | `neo4j_dbms_bolt_connections_running` | Не исчерпан ли worker-пул |

Пороговые значения метрик и настройка Prometheus — в [мониторинге](./monitoring.md).

## Подготовка среды

### Предварительные требования

| Параметр | Минимум | Рекомендация |
| :--- | :--- | :--- |
| **Neo4j** | 5.26 LTS / 2026.09.x | Enterprise Edition — `query.log`, метрики Prometheus, `CONTINUOUS` checkpoint |
| **Java** | OpenJDK 21 | Включён в пакет Neo4j |
| **RAM** | 16 ГБ | 32+ ГБ; сумма heap + page cache + минимум 1 ГБ на ОС |
| **Диск** | SSD (SATA) | NVMe Gen4+ для write-heavy нагрузок; отдельные устройства для `data` и `transactions` |
| **CPU** | 8 ядер | 16+ ядер, изолированных от нагрузчика |
| **Сеть** | 1 Гбит | 10 Гбит |
| **ОС** | Linux 4.x+ | Ubuntu 22.04/24.04 LTS или RHEL/Rocky 9+ |

**Изоляция нагрузчика.** Никогда не запускайте генератор нагрузки на том же хосте, где работает Neo4j: конкуренция за CPU, L3-кэш и page cache искажает результат. Минимальная допустимая конфигурация — отдельная ВМ на том же физическом сервере. Для строгой изоляции используйте `cset shield` (см. [бенчмаркинг СУБД](../Concepts/benchmarking.md#важность-изоляции)).

### Конфигурация Neo4j для тестирования

Перед каждым тестом зафиксируйте `neo4j.conf` — без этого сравнение прогонов не является измерением. Ниже — пример с комментариями к параметрам, влияющим на производительность:

```conf
# --- Память ---
# heap: фиксируйте initial = max, иначе Full GC при каждом расширении
server.memory.heap.initial_size=8G
server.memory.heap.max_size=8G

# page cache: 1.2 × (данные + нативные индексы) по memory-recommendation
server.memory.pagecache.size=16G

# --- Checkpoint ---
db.checkpoint=PERIODIC
db.checkpoint.interval.time=10m
db.checkpoint.interval.tx=50000
db.checkpoint.iops.limit=600

# --- Bolt thread pool ---
server.bolt.thread_pool_min_size=10
server.bolt.thread_pool_max_size=200

# --- Логи ---
# INFO с порогом вместо VERBOSE: те же ответы, в разы меньше объём
db.logs.query.enabled=INFO
db.logs.query.threshold=100ms
dbms.logs.query.time_logging_enabled=true

# --- Метрики ---
server.metrics.prometheus.enabled=true
server.metrics.prometheus.endpoint=localhost:2004
```

Конфигурацию храните в Git вместе с версией Neo4j и seed-данными — это единственный способ добиться воспроизводимости.

### Генерация тестовых данных

Тестовые данные должны быть **реалистичными**, а не просто огромными. Плохие данные искажают результат:

- **Распределение степеней (degree distribution).** В реальном графе большинство узлов имеют 1–3 связи, несколько — высокую степень (хабы). Случайное равномерное соединение даёт нормальное распределение, которое не отражает реальность и создаёт искусственные hot spots.
- **Рабочий набор.** Запросы должны обращаться к одному и тому же объёму данных, а не сканировать весь граф. Если вы тестируете `MATCH (p:Person)-[:KNOWS*1..2]->(f)`, рабочий набор — все `Person` и их связи в радиусе 2.
- **Индексы.** Поля, используемые в `WHERE`, должны быть проиндексированы. Иначе каждый запрос — `NodeFullScan`, и вы измеряете не СУБД, а скорость сканирования диска.
- **Размер данных vs page cache.** Для «тёплого» состояния рабочий набор должен помещаться в page cache. Для «холодного» состояния данные должны быть минимум в 2 раза больше page cache (см. [бенчмаркинг СУБД](../Concepts/benchmarking.md)).

Для генерации данных можно использовать:
- **APOC** — генераторы графа и `apoc.periodic.commit` (см. [APOC](./apoc.md))
- **`neo4j-admin database import`** — для начальной загрузки (см. [Массовый импорт](./bulk_import.md))
- **Скрипт на Python/Cypher** — генерация с заданным распределением степеней и свойств

## Практические сценарии

### Методология SRE: 4 этапа теста

Прогон в Neo4j строится по той же схеме, что и бенчмаркинг любых СУБД (см. [бенчмаркинг СУБД](../Concepts/benchmarking.md#методология-sre-4-этапа-тестирования)), но с учётом специфики графа. Каждый этап — отдельный замер, результаты которого фиксируются и сравниваются между прогонами.

**Этап 1: Baseline (Эталон).** Однопоточный тест для определения минимальной задержки в текущей конфигурации. Результат — нижняя граница latency, к которой система стремится при идеальных условиях. Запускайте через драйвер с `routing_=neo4j.RoutingControl.READ`, 1 соединение, 60 секунд.

**Этап 2: Ramp-up (Разгон).** Поэтапное увеличение параллельности: 1 → 4 → 8 → 16 → 32 → 64 соединения. На каждом шаге — по 2–3 минуты. Цель — найти точку перегиба: где latency начинает расти, а throughput перестаёт. Записывайте `p95`/`p99` и `neo4j_dbms_bolt_connections_running` на каждом шаге.

**Этап 3: Steady State (Стабильное состояние).** Удержание пиковой нагрузки в течение 15–30 минут. Минимальная длительность — 15 минут, чтобы активировались checkpoint и GC. Зафиксируйте конфигурацию, версию Neo4j и seed данных — без этого сравнение «было / стало» не является измерением.

**Этап 4: Analysis (Анализ).** Постройте график `Throughput` vs `Latency p95` по данным всех этапов. Ищите **Saturation Point** — точку, где throughput перестаёт расти, а latency растёт экспоненциально. Сравнивайте с предыдущими прогонами: регрессия больше 5% — повод для расследования.

### Порядок теста

1. Зафиксировать конфигурацию: `server.memory.heap.*`, `server.memory.pagecache.size`, размеры WAL и checkpoint, число ядер.
2. Подготовить данные по правилам из [бенчмаркинга](../Concepts/benchmarking.md), с запасом по объёму относительно page cache.
3. Проверить готовность схемы:

```cypher
SHOW INDEXES YIELD name, state, population
RETURN name, state, population
ORDER BY state;
```

4. Прогреть систему: повторить целевой запрос тысячи раз, не записывая результаты замера.
5. Провести замер с фиксированной длительностью, кратной нескольким циклам checkpoint.
6. Снять метрики до, во время и после; сопоставить с `query.log`.
7. Повторить для другой конфигурации в тех же условиях — иначе сравнение бессмысленно.

### Генерация нагрузки драйвером

Когда нужен именно сценарий приложения, а не абстрактный HTTP-поток, нагрузку проще поднимать драйвером. Скрипт ниже использует документированный высокоуровневый API `execute_query` и маршрутизацию на чтение:

```python
import time
import neo4j
from neo4j import GraphDatabase

URI = "neo4j://localhost:7687"
AUTH = ("neo4j", "password123")
ROUNDS = 1000
CONCURRENCY = 8

QUERY = (
    "MATCH (p:Person {email: $email})-[:FRIENDS_WITH*1..2]->(f) "
    "RETURN count(f) AS friends"
)

def run_round(driver, index):
    records, summary, _ = driver.execute_query(
        QUERY,
        email=f"user{index % 100}@example.com",
        routing_=neo4j.RoutingControl.READ,
    )
    return summary.result_available_after

with GraphDatabase.driver(URI, auth=AUTH, max_connection_pool_size=CONCURRENCY) as driver:
    driver.verify_connectivity()

    # Прогрев: первые итерации не измеряем
    for i in range(100):
        run_round(driver, i)

    latencies = []
    started = time.perf_counter()
    for i in range(ROUNDS):
        latencies.append(run_round(driver, i))
    elapsed = time.perf_counter() - started

latencies.sort()
p95 = latencies[int(len(latencies) * 0.95) - 1]
print(f"rounds={ROUNDS} elapsed={elapsed:.2f}s p95_result_available_after={p95}ms")
```

Значения `summary` доступны без дополнительных запросов; для распределения задержек по перцентилям опирайтесь на метрику `database.<db>.db.query.execution.latency.millis`, которая приходит готовой гистограммой.

### Чтение на конкретной базе и роли

В кластере распределение нагрузки определяется маршрутизацией: чтения уходят на secondaries, записи — на leader. Указывайте тип доступа явно, иначе результат зависит от того, куда драйвер решил пойти:

```python
# Чтение — на secondaries
records, summary, _ = driver.execute_query(
    "MATCH (p:Person {id: $id}) RETURN p.name AS name",
    id=42,
    routing_=neo4j.RoutingControl.READ,
)

# Запись — на leader
records, summary, _ = driver.execute_query(
    "MERGE (p:Person {id: $id}) SET p.seen = true",
    id=42,
    routing_=neo4j.RoutingControl.WRITE,
)
```

Правила маршрутизации, кэш routing table и таймауты — в [драйверах](./drivers.md) и [кластеризации](./clustering.md).

### Разбор результатов по `query.log`

`query.log` — источник фактической нагрузки, а не результатов синтетического теста:

```cypher
-- Запросы для диагностики на живой базе
CALL db.clearQueryCaches()
```

Формат `query.log` и разбор записи — в [мониторинге](./monitoring.md#querylog-разбор-записи). Включать подробный лог на время теста стоит осознанно: на нагруженной базе `VERBOSE` даёт огромный объём и сам становится нагрузкой.

### Проверка «а не кэш ли это»

Главный вопрос к результату Neo4j: кэш это или диск.

```cypher
SHOW TRANSACTIONS
YIELD transactionId, currentQuery, elapsedTime, pageFaults, currentQueryAllocatedBytes
RETURN transactionId, elapsedTime, pageFaults, currentQueryAllocatedBytes
ORDER BY elapsedTime DESC
LIMIT 10;
```

Ненулевые `pageFaults` при низком `neo4j_dbms_page_cache_hit_ratio` означают, что измеряется ввод-вывод. Дальше — либо расширить page cache по формуле `1.2 × (данные + индексы)`, либо уменьшить рабочий набор запросов. Разбор — в [оптимизации запросов](./query_optimization.md).

## Очистка после теста

После каждого тестового цикла выполните следующее, иначе результаты следующего прогона будут искажены:

1. **Остановите нагрузку** и дождитесь, пока все Bolt-соединения закроются (`neo4j_dbms_bolt_connections_running` → 0).
2. **Очистите кэш запросов и статистику**, чтобы следующий прогон начинался с чистого состояния:
   ```cypher
   CALL db.clearQueryCaches()
   ```
3. **Соберите артефакты:** `query.log`, CSV-метрики, логи Neo4j, конфигурацию (`SHOW SETTINGS`), снимки Prometheus. Архивируйте с указанием версии Neo4j, даты и описания конфигурации.
4. **Удалите тестовые данные**, если они не идемпотентны: `MATCH (n) DETACH DELETE n` или drop тестовой базы. Оставшиеся данные влияют на статистику и размер page cache.
5. **Проверьте, что диск не заполнился:** WAL и `query.log` растут под нагрузкой. При нехватке места Neo4j может перейти в оффлайн.
6. **Остановите фоновые процессы мониторинга**, если они запускались отдельно (syswatch, fio, etc.).

## Устранение неполадок

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| Первый прогон медленнее второго в разы | Разброс между итерациями | Тёплый кэш и JIT | Прогрев; измерять и подписывать оба состояния |
| Задержки скачут каждые N минут | Всплески в p99 | Checkpoint | Сверить период с `db.checkpoint.interval.time`; уменьшить размер пачки или частоту |
| p99 лучше p95 — метрика подозрительна | Аномалия | Гистограмма переполнена или сбрасывается | Проверить, не отбрасываются ли наблюдения в экспортере |
| Рост `neo4j_dbms_vm_gc_time_percent` | CPU под 100 % | Давление на heap | Тюнинг GC, см. [диагностику на уровне JVM](./jvm_diagnostics.md) |
| Загрузка упёрлась в worker-пул Bolt | Очередь соединений | Мало потоков или мал `thread_pool_min_size` | Пул потоков Bolt — в [мониторинге](./monitoring.md) |
| Тест не воспроизводится | Разные результаты на том же стенде | Не зафиксированы конфигурация и данные | Фиксировать версию, конфигурацию и seed данных |
| Тест прошёл, а в проде медленно | Разница | В тесте не учтены смежные нагрузки | Добавить в тест конкурирующую нагрузку: GDS-проекции, бэкапы |

## Лучшие практики

- **Прогревайте перед замером** и не смешивайте холодные и тёплые цифры в одном отчёте.
- **Измеряйте оба состояния кэша явно** — «после прогрева» и «на холодном кэше». Это разные характеристики системы.
- **Фиксируйте версию, конфигурацию и данные.** Без этого сравнение «было / стало» не является измерением.
- **Берите замер длительностью в несколько циклов checkpoint**, иначе вы не увидите влияние сброса страниц.
- **Проверяйте `state` индексов до замера** — `POPULATING` во время теста искажает всё.
- **Держите в тесте конкурирующую нагрузку**, если она есть в проде: аналитические проекции GDS, бэкапы, пакетные задачи.
- **Отделяйте p95 от p99.** В Neo4j разница между ними — это вклад checkpoint и GC, а не «шум».
- **Отделяйте результаты приложения от абстрактного HTTP-нагрузчика:** драйвер учитывает реальную семантику транзакций и маршрутизации.
- **Не запускайте нагрузчика на том же хосте, где Neo4j.** Конкуренция за CPU и page cache искажает результат. Используйте отдельную ВМ или `cset shield`.
- **Генерируйте реалистичные данные**, а не просто большие: учтите распределение степеней узлов, индексы в `WHERE` и размер рабочего набора.
- **Собирайте артефакты после каждого прогона:** `query.log`, метрики, конфигурацию, снимки Prometheus. Без артефактов воспроизводимость теряется.
- **Очищайте кэш и данные между прогонами**, иначе следующий прогон стартует в загрязнённом состоянии.
