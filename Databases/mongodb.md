# MongoDB

**MongoDB** – это документо-ориентированная NoSQL база данных. В отличие от реляционных баз данных (таких как MySQL или PostgreSQL), которые хранят данные в таблицах и строках, MongoDB хранит данные в гибких, JSON-подобных документах. Эта модель данных позволяет легко и быстро разрабатывать приложения, адаптируясь к изменяющимся требованиям.

Ключевые характеристики:

-   **Высокая производительность:** Обеспечивается за счет встроенного кэширования и оптимизированного доступа к данным.
-   **Высокая доступность:** Поддерживается через наборы реплик ([replication](./Concepts/replication.md)).
-   **Горизонтальное масштабирование:** Достигается с помощью [шардинга](./Concepts/sharding.md), что позволяет распределять данные по нескольким серверам.
-   **Гибкая схема данных:** Нет необходимости заранее определять структуру документов.

Данные хранятся в формате **BSON** (Binary JSON), который является бинарным представлением JSON-документов и поддерживает больше типов данных.

## Установка MongoDB Community Edition на Ubuntu

MongoDB использует свой репозиторий, поэтому сначала необходимо добавить его ключ в систему.

```bash
# Устанавливаем зависимости, если их нет
sudo apt-get install gnupg curl

# Импортируем ключ MongoDB
curl -fsSL https://www.mongodb.org/static/pgp/server-7.0.asc | \
   sudo gpg -o /usr/share/keyrings/mongodb-server-7.0.gpg --dearmor
```

Создайте файл `/etc/apt/sources.list.d/mongodb-org-7.0.list`, чтобы `apt` знал, откуда скачивать пакеты.

```bash
echo "deb [ arch=amd64,arm64 signed-by=/usr/share/keyrings/mongodb-server-7.0.gpg ] https://repo.mongodb.org/apt/ubuntu jammy/mongodb-org/7.0 multiverse" | sudo tee /etc/apt/sources.list.d/mongodb-org-7.0.list
```

Обновите список пакетов и установите мета-пакет `mongodb-org`, который включает в себя все необходимые компоненты (сервер, клиент, утилиты).
```bash
sudo apt-get update
sudo apt-get install -y mongodb-org
```

После установки служба `mongod` не запускается автоматически.

-   **Запустить службу:**
    ```bash
    sudo systemctl start mongod
    ```

-   **Подключиться к базе данных:**
    Используйте `mongosh` (новый shell, который устанавливается вместе с сервером).
    ```bash
    mongosh
    ```

## Кластеризация: Replica Set и Sharding

MongoDB обеспечивает высокую доступность и масштабируемость с помощью двух ключевых механизмов: наборов реплик и шардинга.

### Набор реплик (Replica Set)

Набор реплик — это группа процессов `mongod`, которые поддерживают один и тот же набор данных для обеспечения отказоустойчивости. Это основной способ достижения высокой доступности в MongoDB.

-   **Цель:** Отказоустойчивость и высокая доступность.
-   Подробнее об общей концепции см. в [Основной заметке о репликации](./Concepts/replication.md).

#### Компоненты Replica Set

-   **Primary (первичный):** Основной узел, который принимает все операции записи. В наборе реплик может быть только один первичный узел.
-   **Secondary (вторичный):** Узлы, которые асинхронно копируют данные с первичного узла. Они могут обслуживать запросы на чтение.
-   **Arbiter (арбитр):** Специальный легковесный узел, который не хранит данные и не может стать первичным. Его единственная задача — участвовать в голосовании при выборе нового первичного узла, когда в наборе реплик четное количество узлов с данными. Это помогает достичь кворума для выборов.

#### Механизм работы

1.  **Oplog (Журнал операций):** Все операции, изменяющие данные на первичном узле, записываются в специальную коллекцию с фиксированным размером — `oplog.rs`. Вторичные узлы постоянно следят за этим журналом и асинхронно применяют те же операции к своим наборам данных.
2.  **Heartbeats (Пульс):** Все члены набора реплик постоянно обмениваются сигналами (раз в две секунды по умолчанию), чтобы проверять доступность друг друга.

#### Выборы (Elections)

Если первичный узел становится недоступным (не отвечает на heartbeats в течение 10 секунд), оставшиеся узлы инициируют процесс выборов, чтобы выбрать новый первичный узел. Узел с самым свежим `oplog` и наивысшим приоритетом (если задан) побеждает в выборах.

#### Кворум и гарантии записи (Write Concern)

**Write Concern (`writeConcern`)** — это параметр, который определяет, какого уровня подтверждения должна дождаться операция записи, чтобы считаться успешной.
-   `w: 1`: Запись подтверждается после того, как она будет выполнена на первичном узле (поведение по умолчанию).
-   `w: "majority"`: Запись подтверждается после того, как она будет выполнена на большинстве узлов в наборе реплик, обладающих правом голоса. Это гарантирует, что данные не будут "откачены" даже в случае сбоя и выборов нового первичного узла.

### Шардирование (Sharding)

Шардирование — это метод горизонтального масштабирования, при котором большие наборы данных разделяются на части (шарды) и распределяются по нескольким серверам.

-   **Цель:** Горизонтальное масштабирование для обработки очень больших наборов данных и распределения нагрузки на запись.
-   Подробнее об общей концепции см. в [Основной заметке о шардировании](./Concepts/sharding.md).

#### Архитектура шардированного кластера

1.  **Shards (Шарды):** Каждый шард является независимым набором реплик (replica set), который хранит часть общих данных. Это обеспечивает как масштабируемость, так и отказоустойчивость.
2.  **Config Servers (Серверы конфигурации):** Это также набор реплик, который хранит метаданные кластера: информацию о том, какие данные на каком шарде находятся (маппинг), и другую конфигурацию.
3.  **Query Routers (`mongos`):** Легковесные процессы-маршрутизаторы. Приложение подключается не напрямую к шардам, а к `mongos`. `mongos` принимает запрос, обращается к серверам конфигурации, чтобы определить, на какой шард (или шарды) его направить, и возвращает результат приложению.

#### Ключ шардирования (Shard Key)

Это один или несколько полей в документе, значение которых используется для определения, на какой шард попадет этот документ. **Выбор правильного ключа шардирования является критически важным решением**, так как он определяет, насколько равномерно данные и нагрузка будут распределены по шардам.

#### Включение шардирования

Процесс состоит из двух основных шагов:

1.  Включить шардирование для базы данных:

    ```javascript
    sh.enableSharding("myDatabase")
    ```

2.  Шардировать коллекцию, указав ключ шардирования:

    ```javascript
    sh.shardCollection("myDatabase.myCollection", { "user_id": 1 })
    ```
    
После этого `mongos` начнет распределять документы коллекции `myCollection` по шардам на основе значения поля `user_id`.
