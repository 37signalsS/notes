## CAP-теорема (Теорема Брюэра)

**CAP-теорема**, также известная как **теорема Брюэра**, является фундаментальным принципом в теории распределенных систем. Она утверждает, что любая распределенная система хранения данных может одновременно обеспечивать не более двух из трех следующих гарантий:

1.  **Consistency (Согласованность данных)**
2.  **Availability (Доступность)**
3.  **Partition Tolerance (Устойчивость к разделению)**

В контексте баз данных, особенно распределенных, эта теорема определяет ключевые архитектурные компромиссы.

### Компоненты теоремы

#### Consistency (Согласованность)

Согласованность означает, что все клиенты (или узлы кластера) видят одни и те же данные в одно и то же время. При выполнении операции записи, она должна атомарно отразиться на всех узлах, прежде чем будет считаться успешной. Любое последующее чтение вернет именно этот, последний записанный результат.

> **Важно:** Это сильная согласованность (strong consistency), отличающаяся от согласованности в транзакциях ACID.

#### Availability (Доступность)

Доступность гарантирует, что каждый запрос к системе получает корректный (не ошибочный) ответ. Это не гарантирует, что ответ содержит самые последние обновленные данные, но система всегда остается работоспособной для чтения и записи.

#### Partition Tolerance (Устойчивость к разделению)

Устойчивость к разделению — это способность системы продолжать функционировать в случае возникновения разрыва сетевой связи (partition) между узлами. В распределенной системе, где узлы общаются по сети, сбои (потеря пакетов, задержки) считаются неизбежными. Поэтому на практике **устойчивость к разделению (P) не является опцией, а является обязательным свойством** любой серьезной распределенной СУБД.

### Компромиссы в реальных системах

Поскольку от устойчивости к разделению (P) отказаться нельзя, реальный выбор при проектировании распределенной БД сводится к компромиссу между согласованностью (C) и доступностью (A). Ключевым механизмом, который реализует этот выбор на практике, является **[репликация](./replication.md)**.

#### CP-системы (Consistency + Partition Tolerance)

В случае сетевого разделения система выбирает **согласованность**, жертвуя доступностью.

> Система будет недоступна до тех пор, пока не согласует данные.

**Схема процесса (синхронная репликация):**
```text
  Клиент                    Master                      Replica
    | -- 1. WRITE ---------> |                           |
    |                        | -- 2. REPLICATE --------> |
    |                        |                           | -- 3. OK
    |                        | <-------- 4. ACK --------- |
    | <------- 5. OK -------- |                           |
```

*   **Поведение:** Чтобы избежать рассинхронизации данных, узел, который не может связаться с другими узлами (например, с мастером), становится недоступным для записи или даже для чтения. Он отказывается отвечать на запросы, пока связь не восстановится и данные не будут синхронизированы.
*   **Примеры СУБД:** MongoDB, Redis, HBase.
*   **Сценарии:** Финансовые системы, банковские приложения, системы биллинга — везде, где целостность данных является абсолютным приоритетом.

#### AP-системы (Availability + Partition Tolerance)

В случае сетевого разделения система выбирает **доступность**, жертвуя сильной согласованностью.

> Отсутствие согласованности данных не влияет на работу узлов.

**Схема процесса (асинхронная репликация):**
```text
  Клиент                    Master                      Replica
    | -- 1. WRITE ---------> |                           |
    | <------- 2. OK -------- |                           |
    |                        | -- 3. REPLICATE ------> |
    |                        |                           |
... через некоторое время (replication lag) ...
    |                        | <------ 4. ACK ---------- |
```

*   **Поведение:** Все узлы продолжают принимать запросы на чтение и запись. Данные могут быть временно рассинхронизированы между разделами сети. После восстановления связи система стремится к **"согласованности в конечном счете" (eventual consistency)**, синхронизируя данные в фоновом режиме.
*   **Примеры СУБД:** Apache Cassandra, CouchDB, ScyllaDB, DynamoDB.
*   **Сценарии:** Социальные сети, системы аналитики, IoT-платформы — там, где временное отображение устаревших данных менее критично, чем отказ в обслуживании.

### А что же MySQL?

Классический **одиночный экземпляр MySQL** является **CA-системой** (Consistency + Availability). Он не обладает устойчивостью к разделению по своей природе, так как не является изначально распределенной системой.

Однако в кластерных конфигурациях (например, MySQL Cluster, Percona XtraDB Cluster, Galera Cluster) MySQL пытается балансировать между гарантиями. В зависимости от конфигурации и типа кластера, он может склоняться к CP или AP поведению, но чаще всего стремится к сильной согласованности (CP), жертвуя доступностью в случае серьезных сетевых сбоев в кластере.

### Иллюзия "CAP"-системы: анализ идеальных требований

Рассмотрим гипотетическую систему, описанную следующими требованиями:

1.  **Согласованность:** *"Данные во всех точках должны быть одинаковы в любой момент времени".*
2.  **Доступность:** *"Доступ к БД на всех точках 24/7"* и *"Любой запрос к БД должен завершаться корректным откликом".*
3.  **Устойчивость к разделению:** *"Этих точек СУБД должно быть несколько"* и *"Расщепление распределенной сети БД на независимые сегменты не ведет к некорректной работе".*

Эти требования описывают систему, которая одновременно является **C**, **A** и **P**. Согласно теореме CAP, такая система невозможна.

#### Почему это не работает? (Мысленный эксперимент)

Представим два узла базы данных, `Node 1` и `Node 2`, между которыми происходит разрыв сети (partition).

1.  **Начальное состояние:** Данные на обоих узлах одинаковы (например, `value = 10`).
2.  **Возникает разрыв сети (P):** Узлы больше не могут общаться друг с другом.
3.  **Приходит запрос на запись:** Клиент подключается к `Node 1` и отправляет команду на изменение данных (`UPDATE table SET value = 20`).

Теперь у системы есть выбор, который доказывает теорему:

-   **Выбрать Согласованность (C) и пожертвовать Доступностью (A):**
    Чтобы гарантировать, что данные останутся одинаковыми на всех узлах, `Node 1` должен реплицировать изменение на `Node 2`. Но сеть разорвана, и сделать это невозможно. Чтобы не нарушить согласованность, `Node 1` **обязан отказать в выполнении запроса на запись**. В этот момент система становится **недоступной** для записи. Это поведение **CP-системы**.

-   **Выбрать Доступность (A) и пожертвовать Согласованностью (C):**
    Чтобы оставаться доступной, `Node 1` принимает запрос и изменяет данные у себя локально (`value = 20`). Он немедленно отправляет клиенту ответ "OK". В этот момент данные на `Node 1` (`value = 20`) и `Node 2` (`value = 10`) становятся **несогласованными**. Система остается доступной, но жертвует сильной согласованностью. Это поведение **AP-системы**.

Таким образом, невозможно одновременно удовлетворить все три требования. При возникновении сетевого разделения (P) система вынуждена выбирать между согласованностью (C) и доступностью (A).
