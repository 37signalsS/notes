# Greenplum

## Определения

**Greenplum** — это массивно-параллельная (MPP, Massively Parallel Processing) СУБД, основанная на PostgreSQL. Она спроектирована как платформа для крупномасштабных хранилищ данных (DWH) и выполнения сложных аналитических запросов (OLAP).

**Текущая версия:** VMware Tanzu Greenplum 7.x (2025–2026).

Ключевая идея — **распараллеливание выполнения запросов** по десяткам и сотням серверов для обработки петабайтных объемов данных.

## Основные концепции

### Архитектура (Shared-Nothing MPP)

Greenplum использует архитектуру **"без разделяемых ресурсов" (shared-nothing)**, где каждый узел в кластере имеет собственные CPU, память и диски.

**Компоненты архитектуры:**

- **Мастер-хост (Master Host):** Точка входа для клиентов. Хранит метаданные (глобальный каталог), оптимизирует и координирует выполнение запросов. Пользовательские данные на мастере не хранятся.
- **Сегмент-хосты (Segment Hosts):** Рабочие узлы, на которых хранятся и обрабатываются данные. На каждом хосте работает один или несколько **сегментов** (экземпляров PostgreSQL), каждый из которых владеет частью общих данных.
- **Interconnect:** Сеть для обмена данными между сегментами во время выполнения запросов.

### Распределение данных

Greenplum комбинирует два уровня распределения данных:

1. **Дистрибуция (Distribution):** Строки таблиц распределяются (шардируются) по всем сегментам в кластере на основе **ключа дистрибуции**. Это обеспечивает параллельную обработку.

    **Стратегии распределения:**
    - `DISTRIBUTED BY (key)` — по ключу (хорошо для JOIN по этому ключу)
    - `DISTRIBUTED RANDOMLY` — случайное равномерное распределение
    - `DISTRIBUTED REPLICATED` — полные копии для небольших таблиц-справочников

2. **Партиционирование (Partitioning):** Внутри каждого сегмента таблицы могут быть дополнительно разделены на партиции (например, по датам), что ускоряет выборку данных и упрощает управление ими.

### MPP-архитектура: принципы работы

**MPP (Massively Parallel Processing)** — архитектура массивно-параллельной обработки данных.

**Принципы:**

1. **Shared-Nothing:** Каждый узел независим — свои CPU, память, диски. Сбой одной ноды не влияет на другие.
2. **Распределение вычислений:** Данные и вычисления распределены по всем узлам. Каждый узел обрабатывает только свою часть данных.
3. **Параллельное выполнение:** Запрос выполняется одновременно на всех узлах. Скорость определяется скоростью **самой медленной** ноды.

**Сравнение с традиционной архитектурой:**

| Характеристика | Традиционная (PostgreSQL) | MPP (Greenplum, ClickHouse) |
| :--- | :--- | :--- |
| **Архитектура** | Мастер + реплики | Множество независимых нод |
| **Запись** | Только мастер | Распределённая на все ноды |
| **Чтение** | Мастер + реплики | Параллельно со всех нод |
| **Масштабирование** | Вертикальное / репликация чтения | Горизонтальное (шардирование) |
| **Назначение** | OLTP (транзакции) | OLAP (аналитика) |

Подробнее об общей теории MPP и шардирования: **[Шардирование](./Concepts/sharding.md)**.

## Практические сценарии

### Когда использовать Greenplum

**Подходящие сценарии:**

- **Корпоративные хранилища данных (DWH):** Централизованный сбор и анализ данных со всей организации.
- **Business Intelligence (BI) и отчетность:** Построение витрин данных и выполнение тяжелых аналитических запросов для отчетов.
- **Анализ больших данных:** Исследовательский анализ, машинное обучение с Apache MADlib.
- **Сложные ETL-процессы:** Пакетная обработка больших объемов данных.

### Когда НЕ использовать Greenplum

- **Транзакционные нагрузки (OLTP):** Частые короткие INSERT/UPDATE/DELETE.
- **Запросы с низкой задержкой:** MPP-системы оптимизированы для пропускной способности, а не latency.
- **Малые объемы данных:** До 1 ТБ — PostgreSQL справится при правильной индексации.

### Пример создания таблицы

```sql
-- Распределённая таблица с партиционированием
CREATE TABLE sales (
    sale_id SERIAL,
    sale_date DATE,
    product_id INT,
    customer_id INT,
    amount NUMERIC(10,2)
)
DISTRIBUTED BY (sale_id)
PARTITION BY RANGE (sale_date)
(
    PARTITION p2023 START ('2023-01-01') END ('2024-01-01'),
    PARTITION p2024 START ('2024-01-01') END ('2025-01-01')
);

-- Таблица-справочник (реплицируется на все сегменты)
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name TEXT
) DISTRIBUTED REPLICATED;
```

### Загрузка данных

```bash
# Использование gpfdist для параллельной загрузки
gpfdist -d /data/load_files -p 8080 &

-- Вставка из внешнего источника
INSERT INTO sales_ext
SELECT * FROM gp_read_external_table('gpfdist://host:8080/*.csv');
```

## Дополнительная информация

### Сравнение с альтернативами

| Система | Тип | Назначение | Особенности |
| :--- | :--- | :--- | :--- |
| **[PostgreSQL](./PostgreSQL/overview.md)** | OLTP (строковая) | Транзакции, операционные данные | ACID, экосистема |
| **[ClickHouse](./clickhouse.md)** | OLAP (колоночная) | Аналитика, отчёты, Big Data | Высокая скорость, колоночное хранение |
| **Greenplum** | OLAP (MPP на PostgreSQL) | Аналитика, DWH | Совместимость с PostgreSQL, MADlib |
| **Hadoop/HDFS** | Хранилище (Data Lake) | Сырые данные, batch-обработка | Дешёвое хранение |

**Greenplum vs ClickHouse:**

- Greenplum требует отдельной инфраструктуры (не extension), дороже в эксплуатации.
- ClickHouse быстрее для интерактивной аналитики, но менее совместим с PostgreSQL.
- Greenplum поддерживает Apache MADlib для машинного обучения внутри БД.

### Экосистема

- **Apache MADlib:** Библиотека для машинного обучения внутри базы данных.
- **gpfdist:** Утилита для параллельной загрузки/выгрузки данных.
- **PXF (Platform Extension Framework):** Доступ к внешним источникам данных (Hadoop, S3, JDBC).
- **Greenplum Command Center:** Веб-интерфейс для мониторинга и управления кластером.

### Требования к оборудованию

**Рекомендации для production-кластера:**

| Компонент | Минимум | Рекомендуется |
| :--- | :--- | :--- |
| **CPU** | 8 ядер на сегмент | 16+ ядер на сегмент |
| **RAM** | 32 ГБ на сегмент | 64+ ГБ на сегмент |
| **Диски** | SSD | NVMe SSD |
| **Сеть** | 1 Гбит/с | 10+ Гбит/с (InfiniBand для больших кластеров) |

**Принцип масштабирования:** Предпочтительно множество небольших нод вместо нескольких мощных.

### Ограничения

- **Версия PostgreSQL:** Greenplum основан на PostgreSQL, но может отставать от последней версии.
- **UPDATE/DELETE:** Могут быть медленными из-за необходимости перераспределения данных.
- **Сложность эксплуатации:** Требует отдельной инфраструктуры и квалифицированной команды.
