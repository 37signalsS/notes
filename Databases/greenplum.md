# Greenplum: Массивно-параллельный PostgreSQL

Массивно-параллельная СУБД для аналитических хранилищ. Общая теория распределенных систем и MPP описана в разделе **[Шардирование и MPP](./Concepts/sharding.md)**.

## Определения

**Greenplum** — это СУБД с массивно-параллельной архитектурой (MPP — Massively Parallel Processing), построенная на базе PostgreSQL. Она предназначена для создания корпоративных хранилищ данных (DWH) и выполнения сверхсложных аналитических запросов (OLAP) на петабайтных объемах данных.

Ключевая идея — **разбиение запроса на множество параллельных задач**, которые выполняются одновременно на десятках или сотнях серверов.

**Текущее состояние (2026):** VMware Tanzu Greenplum 7.x является основным стандартом, базируясь на ядре **PostgreSQL 12**. Версия 7.x привнесла поддержку хранимых процедур, улучшенные CTE (Common Table Expressions), нативное партиционирование PostgreSQL, адаптированное под MPP, и значительно улучшенную производительность планировщика.

## Основные концепции

### Архитектура Shared-Nothing («Без разделяемых ресурсов»)

В отличие от систем с общими дисками, в Greenplum каждый узел обладает собственной памятью, CPU и дисковым пространством. Это устраняет единую точку конкуренции за ввод-вывод и позволяет линейно масштабировать производительность.

**Компоненты кластера:**

- **Координатор (Coordinator Host):** (ранее Master) «Мозг» кластера. Принимает SQL-запросы, строит план выполнения и распределяет его между сегментами. Хранит только метаданные (системный каталог).
- **Сегмент-хосты (Segment Hosts):** Серверы, выполняющие основную работу. На каждом хосте работают несколько **сегментов** (инстансов Postgres), каждый из которых владеет своей частью данных.
- **Interconnect:** Сетевой коммутационный слой. Обеспечивает передачу промежуточных результатов между сегментами. В 2026 году предпочтительно использование протокола **UDPI** (UDP с подтверждением доставки), оптимизированного для аналитических нагрузок с низкими задержками.

### Типы хранения и сжатие

Greenplum позволяет гибко настраивать формат хранения под конкретный тип нагрузки:

1.  **Heap Storage:** Классический строковый формат PostgreSQL. Лучший выбор для небольших таблиц (<100 MB), справочников с частыми `UPDATE/DELETE` или таблиц, требующих частых обновлений индексов.
2.  **Append-Optimized (AO):** Структура, оптимизированная для массовой загрузки (`COPY`, `INSERT`). Игнорирует накладные расходы на MVCC при дозаписи, что ускоряет вставку огромных массивов данных.
3.  **Column-Oriented (AOCO):** Колоночное хранение. Каждая колонка хранится в отдельном файле.
    - **Сжатие:** Поддержка алгоритмов **ZSTD** (высокий коэффициент), **LZ4** (высокая скорость) и **RLE** (Run-Length Encoding для повторяющихся значений).
    - **Эффективность:** Чтение только необходимых колонок радикально снижает I/O нагрузку в OLAP-запросах.

### Отказоустойчивость (High Availability)

- **Standby Coordinator:** Резервный узел для Координатора. В случае сбоя переключение может быть выполнено вручную или с помощью средств автоматизации.
- **Зеркалирование сегментов (Segment Mirroring):** Для каждого первичного сегмента (Primary) создается зеркальная копия (Mirror) на другом хосте. Данные синхронизируются в реальном времени.
- **FTS (Fault Tolerance Service):** Фоновый процесс на Координаторе, который постоянно опрашивает сегменты. Если Primary сегмент недоступен, FTS автоматически активирует Mirror.

### Оптимизатор GPORCA

**GPORCA** — это современный расширяемый планировщик запросов на основе стоимости, созданный специально для MPP.
- **Масштабируемость:** Эффективно обрабатывает запросы с сотнями JOIN'ов и сложными подзапросами.
- **Многоэтапное планирование:** Умеет строить планы с перемещением данных (Redistribution) и дублированием (Broadcast) для минимизации сетевого трафика.
- **Интеграция с PG12:** В GP7 оптимизатор полностью поддерживает новые типы JOIN'ов и оконные функции ядра PostgreSQL 12.

### Распределение данных (Distribution)

Greenplum комбинирует два уровня распределения данных:

1. **Дистрибуция (Distribution):** Строки таблиц шардируются по сегментам.
    - `DISTRIBUTED BY (key)` — по хешу колонки. Критично для локальных JOIN'ов по этому ключу.
    - `DISTRIBUTED RANDOMLY` — случайное равномерное распределение (Round-robin). Используется, если нет явного ключа дистрибуции.
    - `DISTRIBUTED REPLICATED` — копия таблицы на каждом сегменте. Идеально для небольших справочников.
2. **Партиционирование (Partitioning):** Логическое деление внутри каждого сегмента (например, по датам). Позволяет использовать **Partition Pruning** (исключение партиций) для ускорения выборок.

## Практические сценарии

### Области применения

- **Корпоративные хранилища данных (DWH):** Централизованный сбор и анализ данных всей организации.
- **Бизнес-аналитика (BI) и отчетность:** Построение витрин данных и выполнение тяжелых агрегирующих запросов.
- **Анализ больших данных (Big Data) и ML:** Исследовательский анализ и машинное обучение внутри БД с помощью Apache MADlib.
- **Сложные ETL/ELT процессы:** Пакетная обработка и преобразование огромных массивов данных (PXF, gpfdist).

### Антипаттерны

- **OLTP нагрузки:** Частые короткие операции записи/обновления отдельных строк.
- **Низкая задержка (Latency):** Система оптимизирована для пропускной способности (throughput), а не для мгновенного отклика одиночного запроса.
- **Малые данные:** При объемах <1 ТБ стандартный PostgreSQL обычно проще и быстрее.

### Установка и базовая настройка

#### Подготовка ОС (Bare Metal / VM)
Greenplum требует специфических настроек ядра:
```bash
# /etc/sysctl.conf
kernel.shmmax = 500000000
kernel.shmall = 4000000
net.ipv4.ip_local_port_range = 10000 65535
# Отключение Transparent Huge Pages (THP) обязательно
```

#### Инициализация кластера
Используется утилита `gpinitsystem` с конфигурационным файлом, описывающим топологию:
```bash
gpinitsystem -c gpinitsystem_config -h hostfile_segments
```

#### Развертывание в Kubernetes (2026)
Использование **Greenplum Operator** для автоматизации жизненного цикла:
```yaml
apiVersion: greenplum.pivotal.io/v1
kind: GreenplumCluster
metadata:
  name: gp-prod
spec:
  masterHostCount: 1
  segmentsHostCount: 4
  storageClassName: premium-rwo
```

### Примеры создания таблиц

```sql
-- Распределённая таблица с партиционированием и колоночным хранением (ZSTD сжатие)
CREATE TABLE sales (
    sale_id SERIAL,
    sale_date DATE,
    product_id INT,
    customer_id INT,
    amount NUMERIC(10,2)
)
WITH (appendonly=true, orientation=column, compresstype=zstd, compresslevel=3)
DISTRIBUTED BY (sale_id)
PARTITION BY RANGE (sale_date)
(
    PARTITION p2025 START ('2025-01-01') END ('2026-01-01'),
    PARTITION p2026 START ('2026-01-01') END ('2027-01-01')
);

-- Таблица-справочник (реплицируется на все сегменты для быстрых JOIN)
CREATE TABLE products (
    product_id INT PRIMARY KEY,
    product_name TEXT
) DISTRIBUTED REPLICATED;
```

### Параллельная загрузка данных

```bash
# Запуск gpfdist на сервере-источнике для параллельного чтения всеми сегментами
gpfdist -d /data/csv_files -p 8081 &

-- Создание внешней таблицы для доступа к данным
CREATE EXTERNAL TABLE ext_sales (LIKE sales)
LOCATION ('gpfdist://source-host:8081/*.csv')
FORMAT 'CSV' (HEADER);

-- Быстрая параллельная вставка
INSERT INTO sales SELECT * FROM ext_sales;
```

### Обслуживание и мониторинг

- **Управление ресурсами:** Использование **Resource Groups** на базе **cgroups v2** (в GP7) для изоляции нагрузки разных групп пользователей.
- **Ключевые утилиты:**
    - `gpstate -m`: Мониторинг состояния репликации сегментов.
    - `gpconfig`: Изменение параметров конфигурации (GUC) сразу на всем кластере.
    - `gpcheckcat`: Проверка целостности системного каталога (рекомендуется перед обновлениями).
- **VACUUM и ANALYZE:**
    - `VACUUM`: Для Heap-таблиц — освобождение места. Для AO-таблиц — упаковка блоков при превышении порога `gp_appendonly_compaction_threshold`.
    - `ANALYZE`: Критически важно для сбора статистики, на основе которой GPORCA строит планы.

## Дополнительная информация

### Сравнение аналитических решений

| Система | Архитектура | Основное назначение | JOIN'ы |
| :--- | :--- | :--- | :--- |
| **Greenplum** | MPP (Shared-Nothing) | Сложная аналитика, DWH | Отлично (Redistribution/Broadcast) |
| **[ClickHouse](./ClickHouse/clickhouse.md)** | Колоночная | Сверхбыстрые агрегаты, логи | Ограниченно (предпочтительны flat-tables) |
| **Snowflake** | Cloud MPP | Полностью управляемое DWH | Отлично |
| **[PostgreSQL](./PostgreSQL/overview.md)** | Single Node / Replication | OLTP, малые DWH | Локальные, высокая нагрузка при росте |

### Экосистема и инструменты

- **Apache MADlib:** Машинное обучение и статистика на SQL внутри БД.
- **PXF (Platform Extension Framework):** Доступ к S3, HDFS, Azure Blob напрямую.
- **gpbackup / gprestore:** Параллельное резервное копирование с поддержкой инкрементальных бэкапов.
- **Greenplum Command Center (GPCC):** Графический интерфейс мониторинга запросов и ресурсов.

### Требования к ресурсам (Рекомендации 2026)

| Компонент | Минимум | Рекомендуется для Prod |
| :--- | :--- | :--- |
| **CPU** | 8 ядер на сегмент-хост | 32+ ядер на сегмент-хост (высокая частота) |
| **RAM** | 32 ГБ на сегмент-хост | 128+ ГБ (из расчета ~8 ГБ на сегмент) |
| **Диски** | SSD (SATA/SAS) | NVMe SSD в RAID 10 |
| **Сеть** | 1 Гбит/с | 25/40/100 Гбит/с (Bonding / RoCE) |

### Ограничения и особенности

- **Версия PostgreSQL:** GP7 базируется на PG12. Некоторые расширения и синтаксис PG13+ могут быть недоступны.
- **Распределенные транзакции:** Протокол **2PC (Two-Phase Commit)** накладывает штраф на производительность массовых UPDATE/DELETE.
- **Data Skew (Перекос данных):** Неправильный ключ дистрибуции приводит к перегрузке одного сегмента, что замедляет весь кластер.
    - *Диагностика:* `SELECT gp_segment_id, count(*) FROM table GROUP BY 1;`
