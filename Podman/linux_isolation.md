# Изоляция в Podman

## Определения

**Изоляция Podman** — это комплексный механизм обеспечения безопасности, использующий примитивы ядра Linux для создания изолированных сред выполнения процессов. В отличие от Docker, Podman реализует модель **daemonless** и **rootless**, что вносит существенные изменения в способы применения пространств имен (namespaces) и контрольных групп (cgroups).

**OCI Runtime (Среда выполнения)** — низкоуровневая утилита (например, `crun` или `runc`), которая непосредственно взаимодействует с ядром для настройки изоляции. Podman по умолчанию использует **`crun`**, так как он написан на C, обладает меньшим потреблением памяти и лучшей поддержкой cgroups v2.

**conmon (Container Monitor)** — легковесная утилита, которая сопровождает жизненный цикл контейнера. Она отвечает за сбор логов, мониторинг процесса контейнера и удержание открытых дескрипторов после того, как CLI-процесс Podman завершится.

## Основные концепции

### Пространства имен (Namespaces) в Podman

Podman изолирует контейнеры с помощью следующих пространств имен:

- **User Namespace (Критично для Rootless):** Позволяет мапировать UID 0 (root) внутри контейнера на UID обычного пользователя на хосте. Это предотвращает "побег" из контейнера с правами суперпользователя.
- **Network Namespace:** Изолирует сетевой стек.
    - **Rootless:** Используется **`pasta`** (стандарт в Podman 5.0+, обеспечивает высокую производительность и прозрачную трансляцию портов) или `slirp4netns`.
    - **Rootful:** Используется **`Netavark`** и `Abridge` для настройки мостов и маршрутизации.
- **PID Namespace:** Изолирует дерево процессов. Контейнер видит только свои процессы, начиная с PID 1.
- **Mount Namespace:** Изолирует точки монтирования. Поддерживается `fuse-overlayfs` для реализации слоев в rootless-режиме без прав root.

### Контрольные группы (Cgroups v2)

Podman полностью оптимизирован для **Cgroup v2** (унифицированная иерархия). В отличие от Docker, который может управлять группами напрямую, Podman делегирует это **`systemd`** через `systemd --user` (в rootless) или системный `systemd`.

**Преимущества интеграции с systemd:**
- Совместное использование ресурсов контейнерами и системными сервисами без конфликтов.
- Использование `systemctl` для анализа потребления (через `systemd-cgtop`).
- Корректное распределение весов CPU и лимитов памяти на уровне сессии пользователя.

### Дополнительные уровни защиты

1. **SELinux:** Podman автоматически назначает уникальные MCS-метки контейнерам (например, `container_t`, `container_file_t`). Это предотвращает доступ одного контейнера к файлам другого, даже если оба запущены от одного UID.
2. **AppArmor:** Используется в дистрибутивах на базе Debian/Ubuntu для ограничения возможностей процессов через профили безопасности.
3. **Seccomp (Secure Computing Mode):** Фильтрация системных вызовов. По умолчанию Podman блокирует около 40 опасных вызовов (например, `mount`, `reboot`), разрешая только необходимые.
4. **Capabilities:** Linux-привилегии разбиты на мелкие части. Podman по умолчанию выдает минимальный набор (например, `NET_RAW` для ping), отключая опасные (`SYS_ADMIN`, `CHOWN` в некоторых режимах).

## Практические сценарии

### 1. Вход в пространство имен пользователя (troubleshooting)

Если в rootless-режиме возникают ошибки доступа к файлам на хосте (Permission Denied), используйте `podman unshare`. Эта команда запускает shell в том же User Namespace, в котором работают контейнеры.

```bash
# Проверка текущего маппинга UID
podman unshare cat /proc/self/uid_map
# → 0       1000          1    (Root в контейнере == UID 1000 на хосте)
# → 1     100000      65536    (Остальные UID)

# Исправление прав на директорию для контейнера
podman unshare chown -R 0:0 ./my-app-data
```

### 2. Смена среды выполнения (OCI Runtime)

Вы можете переключиться между `crun` (быстрее) и `runc` (стандарт de-facto) для проверки совместимости.

```bash
# Запуск с использованием runc
podman run --runtime /usr/bin/runc -it alpine sh

# Проверка текущего рантайма по умолчанию
podman info --format '{{.Runtime.Name}}'
# → crun
```

### 3. Настройка сетевой изоляции (Pasta vs slirp4netns)

В Podman 5.0+ рекомендуется использовать `pasta` для rootless-сетей из-за отсутствия накладных расходов на копирование пакетов.

```bash
# Явное использование pasta (по умолчанию в 5.0)
podman run --network=pasta nginx

# Ограничение видимости интерфейсов хоста внутри pasta
podman run --network=pasta:--no-map-gw nginx
```

### 4. Ограничение системных вызовов (Seccomp)

Если приложению нужен специфический системный вызов, заблокированный по умолчанию, можно добавить свой профиль или отключить фильтрацию.

```bash
# Запуск с кастомным профилем seccomp
podman run --security-opt seccomp=/path/to/my-profile.json my-app

# Отключение seccomp для отладки (небезопасно!)
podman run --security-opt seccomp=unconfined my-app
```

### Диагностика проблем изоляции

| Ошибка | Причина | Решение |
| :--- | :--- | :--- |
| `operation not permitted` | Заблокирован системный вызов или Capability | Проверьте `--cap-add` или `--security-opt seccomp=unconfined` |
| `permission denied` (на томах) | Ошибка маппинга UID или SELinux | Используйте `podman unshare` или добавьте `:Z` к монтированию |
| Контейнер не видит сеть | Проблема `slirp4netns` / `pasta` | Проверьте наличие `pasta` в системе (`podman info`) |

**Совет:** Для анализа всех активных пространств имен в системе используйте утилиту `lsns`. Для анализа cgroups — `systemd-cgtop`.
