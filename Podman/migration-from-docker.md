# Миграция с Docker на Podman

## Определения

**Миграция на Podman** — процесс перевода контейнеризированных приложений с Docker на Podman. Включает замену централизованного демона `dockerd` на бездемонную (**daemonless**) архитектуру, переход в безрутовый (**rootless**) режим и адаптацию конфигураций (Compose → Quadlet).

**API (Application Programming Interface)** — программный интерфейс для взаимодействия компонентов Podman с внешними инструментами.

**Quadlet** — инструмент Podman для нативной интеграции с **systemd**. Преобразует декларативные конфигурации контейнеров в системные юниты.

**Linger** — настройка **systemd**, позволяющая пользовательским процессам и контейнерам продолжать работу после завершения сессии пользователя (**SSH**).

## Основные концепции

### Преимущества миграции

1. **Безопасность**: Устранение единой точки отказа и вектора атаки в виде рутового демона. Контейнеры по умолчанию работают в режиме **rootless**.
2. **Надёжность**: Каждый контейнер является независимым процессом. Сбой одного компонента не влияет на работу остальных.
3. **Нативная интеграция**: Управление жизненным циклом через стандартные инструменты ОС — `systemctl` и `journalctl`.
4. **Эффективность**: Отсутствие постоянно запущенного демона снижает потребление ресурсов (**RAM**, **CPU**) в режиме ожидания.

Сравнение характеристик приведено в файле **[Podman vs Docker](./podman_vs_docker.md)**.

## Практические сценарии

### 1. Подготовка системы для rootless-режима

Для полноценной работы без прав root необходимо настроить порты и сессии.

#### Разрешение низких портов

По умолчанию порты < 1024 зарезервированы за root. Для использования порта 80 или 443:

```bash
echo "net.ipv4.ip_unprivileged_port_start=80" | sudo tee /etc/sysctl.d/90-unprivileged-ports.conf
sudo sysctl -p /etc/sysctl.d/90-unprivileged-ports.conf
# → net.ipv4.ip_unprivileged_port_start = 80
```

#### Включение Linger

Гарантирует работу контейнеров после выхода пользователя из системы:

```bash
sudo loginctl enable-linger $USER
# → Проверка: ls /var/lib/systemd/linger/$USER
```

### 2. Настройка совместимости API

Для работы инструментов, ожидающих Docker API (например, CI/CD агенты), необходимо активировать сокет Podman:

```bash
# Установка пакета (Debian/Ubuntu)
sudo apt install podman

# Включение пользовательского сокета
systemctl --user enable --now podman.socket
```

Путь к сокету: `/run/user/$(id -u)/podman/podman.sock`.

### 3. Работа с Docker Compose

Существующие файлы `docker-compose.yml` можно запускать двумя способами.

**Вариант А: podman-compose (Python-реализация)**

```bash
sudo apt install podman-compose
podman-compose up -d
```

**Вариант Б: Использование сокета и Docker Compose v2**

```bash
export DOCKER_HOST="unix://$XDG_RUNTIME_DIR/podman/podman.sock"
docker-compose up -d
```

Подробности в статье: **[Podman Compose](./podman-compose.md)**.

### 4. Переход на Quadlet (Рекомендуется)

Для постоянных сервисов рекомендуется конвертация Compose-файлов в юниты Quadlet.

**Ключевые моменты при миграции:**

- **Сети (Networks)**: Использование нативных сетей через `Network=name.network`.
- **Зависимости**: Описание порядка запуска через `Requires=` и `After=` в секции `[Unit]`.
- **Проверки здоровья**: Использование `Notify=healthy` для синхронизации готовности. Подробнее: **[Настройка через Quadlet и зависимости](./podman_healthchecks.md#настройка-через-quadlet-и-зависимости)**.
- **Права доступа**: При монтировании томов в rootless-режиме может потребоваться флаг `:U` для корректного маппинга владельца.

## Дополнительная информация

### Особенности и ограничения

- **Docker Socket**: Приложения, жестко привязанные к `/var/run/docker.sock`, требуют перенаправления на сокет Podman или использования переменной `DOCKER_HOST`.
- **Безопасность портов**: Если прямое открытие портов через `sysctl` нежелательно, рекомендуется использовать Reverse Proxy (Nginx, Angie).
