# Автообновление и откат в Podman

## Определения

**Podman Auto-Update** — встроенный механизм автоматического обновления контейнеров при появлении новых версий образов в удаленном реестре. В отличие от Docker, этот механизм не требует постоянно работающего демона-монитора, а опирается на стандартные таймеры и службы **systemd**.

**Policy (Политика обновления)** — настройка, определяющая источник проверки обновлений:
- **`registry`**: Сравнение локального дайджеста образа с актуальным дайджестом в удаленном реестре (Registry).
- **`local`**: Обновление на основе локально измененного образа с тем же тегом (например, после пересборки через Buildah).

**Rollback (Откат)** — автоматический возврат к предыдущей стабильной версии образа (по дайджесту), если новый контейнер не смог успешно запуститься или не прошел проверку здоровья (Healthcheck).

---

## Основные концепции

### Архитектура и компоненты

Механизм автообновления Podman глубоко интегрирован с операционной системой:

1. **`podman-auto-update.timer`**: Глобальный планировщик (системный или пользовательский), который периодически запускает процесс проверки.
2. **`podman-auto-update.service`**: Служба, выполняющая команду `podman auto-update`. Она сканирует все запущенные контейнеры на наличие метки `io.containers.autoupdate`.
3. **Метка `io.containers.autoupdate`**: Активирует механизм для конкретного контейнера.
4. **`sdnotify` / `Notify=healthy`**: Протоколы, позволяющие Podman понять, что новый контейнер успешно запустился и готов к работе.

### Жизненный цикл обновления

1. **Триггер**: Таймер срабатывает согласно расписанию.
2. **Инспекция**: Podman проверяет метаданные образов для контейнеров с активной политикой.
3. **Загрузка**: Если в реестре обнаружен новый дайджест, скачивается новый образ.
4. **Перезапуск**: systemd-юнит контейнера перезапускается. Podman создает новый контейнер на базе свежего образа.
5. **Верификация**: Если настроен Healthcheck, Podman ожидает статуса `healthy`.
6. **Откат**: Если в течение заданного времени контейнер стал `unhealthy` или упал, Podman перезапускает службу, принудительно указывая дайджест предыдущего (рабочего) образа.

## Практические сценарии

### 1. Настройка через Quadlet (Рекомендуемый способ)

Для реализации надежного обновления с откатом в Quadlet необходимо настроить проверку здоровья.

**Файл:** `~/.config/containers/systemd/webapp.container`

```ini
[Unit]
Description=My Secure Web Application
After=network-online.target

[Container]
Image=docker.io/library/nginx:latest
ContainerName=webapp
# Включение автообновления
AutoUpdate=registry
PublishPort=8080:80

# Настройка Healthcheck для обеспечения Rollback
HealthCmd=curl -f http://localhost/ || exit 1
HealthInterval=30s
HealthRetries=3

[Service]
# Позволяет systemd понимать состояние здоровья контейнера
Notify=healthy
Restart=on-failure

[Install]
WantedBy=default.target
```

### 2. Аутентификация в приватных реестрах

Команда `podman auto-update` работает в неинтерактивном режиме, поэтому ей необходим доступ к файлу авторизации.

```bash
# Выполнение логина (данные сохранятся в стандартный путь)
podman login registry.example.com

# Если используется кастомный путь к auth.json
podman auto-update --authfile /path/to/my/auth.json
```

Для системных служб файл обычно ищется в `/run/containers/0/auth.json` или `/var/lib/containers/sigstore/`.

### 3. Настройка расписания (systemd timer)

По умолчанию обновление происходит раз в сутки. Вы можете изменить это через override.

```bash
# Создание override для таймера (пользовательский режим)
systemctl --user edit podman-auto-update.timer
```

**Пример конфигурации (обновление каждые 4 часа):**
```ini
[Timer]
OnCalendar=
OnCalendar=00/4:00:00
RandomizedDelaySec=10m
```

### 4. Ручной запуск и отладка

Перед автоматизацией рекомендуется проверить работу механизма вручную.

```bash
# Проверка наличия обновлений без их применения
podman auto-update --dry-run

# Принудительное обновление всех помеченных контейнеров
podman auto-update

# Просмотр логов последнего обновления
journalctl --user -u podman-auto-update.service
```

## Нюансы и ограничения

- **Обновление Подов (Pods)**: При обновлении контейнера внутри пода, Podman может перезапустить весь под, если это необходимо для сохранения сетевого пространства имен.
- **Очистка образов**: Podman автоматически не удаляет старые образы после обновления. Рекомендуется настроить отдельный таймер для `podman image prune -f`.
- **Rootless специфика**: В безрутовом режиме таймер и служба должны быть включены для каждого пользователя отдельно (`systemctl --user`).
- **Зависимость от тегов**: Автообновление работает только если образ в реестре обновился, но сохранил тот же тег (например, `:latest` или `:stable`). Если вы используете уникальные теги для каждой версии (например, `:v1.2.3`), автообновление их не подхватит.

## Дополнительная информация

### Сравнение с Watchtower

| Характеристика | Watchtower (Docker) | Podman Auto-Update |
| :--- | :--- | :--- |
| **Механизм** | Отдельный контейнер-агент. | Интеграция с нативным планировщиком ОС. |
| **Безопасность** | Требует доступа к `docker.sock`. | Работает в рамках прав пользователя (Rootless). |
| **Откат (Rollback)** | Сложная настройка, часто нестабилен. | Нативный механизм через дайджесты образов. |
| **Ресурсы** | Постоянно потребляет RAM. | 0 МБ в режиме ожидания (timer-based). |
