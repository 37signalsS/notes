# Podman: Переменные окружения

> Актуально для: Podman 6.x

## Определения

**Переменные окружения (Environment Variables, ENV)** — динамические пары "ключ-значение", доступные процессам внутри контейнера. В Podman они являются основным механизмом конфигурации приложений без модификации их кода или образа.

**ARG (Build Arguments)** — переменные времени сборки. Они доступны только во время выполнения `podman build` и не сохраняются в метаданных запущенного контейнера, если не были явно переданы в `ENV`. Подробнее: **[Переменные в Containerfile](../Docker/Dockerfile/Instructions/environment_variables.md)**.

**Environment File (.env)** — текстовый файл, содержащий список переменных, который Podman может загрузить массово для настройки контейнера. Формат: построчный, `KEY=VALUE`, комментарии с `#`, пустые строки игнорируются.

**Прокси-переменные** — набор переменных окружения (`http_proxy`, `https_proxy`, `ftp_proxy`, `no_proxy` и их варианты в верхнем регистре), которые Podman по умолчанию пробрасывает из окружения процесса в контейнер (поведение `--http-proxy=true`).

## Основные концепции

### Способы передачи переменных

Podman предоставляет гибкие методы управления окружением в зависимости от сценария использования:

| Метод | Параметр | Описание |
| :--- | :--- | :--- |
| **CLI (Прямой)** | `-e KEY=VAL` | Задание значения непосредственно в команде `run`/`create`. |
| **CLI (Проброс)** | `-e HOST_VAR` | Передача переменной из окружения текущей оболочки (без знака `=`). |
| **CLI (Glob)** | `-e 'PREFIX*'` | Все переменные хоста с данным префиксом (работает только при передаче без `=`). |
| **Файл переменных** | `--env-file f.env` | Загрузка списка переменных из внешнего файла. |
| **Окружение хоста целиком** | `--env-host` | Импорт всего окружения процесса Podman в контейнер. |
| **Метаданные образа** | `ENV` | Значения, жестко заданные в Containerfile при сборке. |
| **Слияние с образом** | `--env-merge 'K=${K}-suffix'` | Подстановка значения по умолчанию из образа в шаблон `${VAR}`. |
| **Прокси** | `--http-proxy` | Проброс прокси-переменных хоста (включено по умолчанию). |
| **Динамическое (5.5+)** | `podman update --env / --unsetenv` | Изменение переменных у **созданного** контейнера без пересоздания. |
| **Удаление при запуске** | `--unsetenv` / `--unsetenv-all` | Убрать переменные до старта контейнера. |
| **Конфигурация engine** | `containers.conf` → `[containers] env=` | Базовые переменные для всех контейнеров. |

### Переменные по умолчанию

Podman добавляет к окружению контейнера несколько переменных, если они не заданы иначе:

| Переменная | Источник | Значение |
| :--- | :--- | :--- |
| `PATH` | встроенная по умолчанию | `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin` |
| `container` | встроенная | `podman` |
| `TERM` | добавляется при `-t`/`--tty` | из окружения хоста либо `xterm` |

Базовый слой задается в `containers.conf` (секция `[containers]`):

```ini
[containers]
env = ["TZ=Europe/Moscow"]
env_host = true
```

- `env` — переменные, передаваемые в контейнер; запись без `=` означает "взять значение из окружения хоста".
- `env_host = true` — эквивалент флага `--env-host`.
- Переменные из `containers.conf` применяются **только при создании** контейнера (`run`/`create`) и не влияют на последующие `podman exec`.
- Значения `containers.conf` являются самым низким слоем и перекрываются образом, файлами и флагами CLI.

### Иерархия приоритетов (Precedence)

Порядок применения переменных при совпадении имен (позднее в списке перекрывает более раннее):

1. **Контейнерный образ** — `ENV` из метаданных образа.
2. **`--http-proxy`** — прокси-переменные хоста (если `--http-proxy=true`, значение по умолчанию).
3. **`--env-host`** — окружение процесса Podman.
4. **`--env-file`** — при указании нескольких файлов последний имеет преимущество над предыдущими.
5. **`--env` / `-e`** — всегда имеет наивысший приоритет среди флагов CLI.

При нескольких значениях в одном `--env` приоритет также у последнего указанного.

Дополнительно:
- Значения `containers.conf` (`[containers] env=`) и встроенные (`PATH`, `container`) образуют самый нижний слой и перекрываются образом.
- **Отличие от Docker:** если `-e HOST_VAR` передан без значения, а переменной нет в окружении хоста, Docker завершится с ошибкой, а Podman **молча пропускает** такую переменную.
- Прокси-переменные, заданные для контейнера явно (`--env`, `ENV` в образе), перекрывают проброшенные через `--http-proxy`.

## Практические сценарии

### 1. Использование конфигурационных файлов (.env)

Рекомендуется для локальной разработки и разделения настроек сред (Dev/Prod).

**Файл `web.env`**:
```ini
# Конфигурация приложения
NODE_ENV=production
API_URL=http://api.internal:8080
LOG_LEVEL=info

# Переменная без значения — будет взята из окружения хоста
HOME_DIR

# Glob: импорт всех переменных хоста с префиксом CFG_
CFG_*
```

**Запуск**:
```bash
podman run -d --name web-server --env-file web.env nginx:alpine
```

**Особенности формата `--env-file`:**
- Строки с `#` в начале и пустые строки игнорируются; пробелы в начале строки отбрасываются.
- `KEY=VALUE` — явное значение; разделение по первому символу `=`.
- `KEY` — значение берется из окружения хоста (если переменная там не задана, она не добавляется).
- `KEY*` — импорт всех переменных хоста с данным префиксом.
- Несколько файлов указываются повтором флага: `--env-file a.env --env-file b.env` — файл `b.env` перекрывает `a.env` при совпадении имен.

### 2. Проброс переменных окружения хоста

**Одиночная переменная** (без знака `=` значение берется из оболочки):
```bash
export API_KEY=abc123
podman run --rm -e API_KEY alpine printenv API_KEY
# → abc123
```

**Группа переменных по префиксу (glob)**:
```bash
export CFG_DEBUG=true
export CFG_RETRIES=5
podman run --rm -e 'CFG_*' alpine env | grep CFG_
# → CFG_DEBUG=true
# → CFG_RETRIES=5
```
Glob-подстановка активна только когда переменная передана **без значения**: `-e 'CFG_*=b'` создаст переменную с буквальным именем `CFG_*=b`.

**Все окружение хоста** (`--env-host`):
```bash
podman run --rm --env-host alpine env
```
Важно: флаг недоступен для удаленного клиента Podman (включая macOS и Windows без WSL2).

**Прокси-переменные** (`--http-proxy`):
```bash
# По умолчанию прокси хоста уже пробрасываются; отключить:
podman run --http-proxy=false alpine env | grep -i proxy
```

### 3. Динамическое обновление (Podman 5.5+)

Версия 5.5 добавила возможность изменять окружение **созданного** контейнера без пересоздания (флаги `--env` и `--unsetenv`).

```bash
# Добавление или изменение переменной
podman update --env DEBUG=true my-running-app

# Удаление переменной
podman update --unsetenv DEBUG my-running-app
```

**Важно:** изменения окружения затрагивают **основной процесс контейнера только при его следующем старте**. Работающий процесс и запускаемые через `podman exec` команды продолжают видеть старое окружение. Немедленная проверка через `podman exec ... env` покажет прежние значения — корректно проверять так:

```bash
# Просмотр конфигурации контейнера (новое значение уже в конфигурации)
podman inspect my-running-app --format '{{range .Config.Env}}{{println .}}{{end}}'

# После перезапуска — проверка внутри контейнера
podman restart my-running-app
podman exec my-running-app env | grep DEBUG
# → DEBUG=true
```

*Примечание: приложение должно поддерживать перечитывание переменных (или горячую перезагрузку), иначе изменения вступят в силу только после рестарта процесса внутри контейнера.*

### 4. Переменные в Quadlet (systemd)

Quadlet позволяет декларативно описывать окружение и использовать спецификаторы systemd для динамического формирования путей.

**Файл `app.container`**:
```ini
[Container]
Image=localhost/api-server:latest

# Прямое задание (секция [Container], НЕ [Service])
Environment=APP_PORT=3000
Environment=DATA_DIR=/data/%u

# Загрузка из файла (относительно домашней папки пользователя)
EnvironmentFile=%h/.config/app/prod.env

# Импорт всего окружения хоста
EnvironmentHost=true

[Service]
# Автоматический рестарт при изменении конфига
Restart=on-failure
```

Соответствие ключей Quadlet и флагов CLI:

| Ключ Quadlet | Флаг CLI |
| :--- | :--- |
| `Environment=KEY=VAL` | `--env KEY=VAL` |
| `EnvironmentFile=/path` | `--env-file /path` |
| `EnvironmentHost=true` | `--env-host` |

**Спецификаторы systemd:** `%u` — имя пользователя, `%h` — путь к домашней директории, `%n` — имя юнита, `%t` — каталог времени выполнения. Они делают конфигурацию переносимой между пользователями.

**Нюансы Quadlet:**
- Переменные окружения контейнера задаются в секции `[Container]`; запись `Environment=` в секции `[Service]` настраивает окружение самого systemd-сервиса и в контейнер не попадает.
- Для путей, начинающихся с `%`, Quadlet не разрешает относительные пути автоматически: чтобы указать путь относительно юнита, добавьте `./`, например `EnvironmentFile=./%n/env`.
- Quadlet добавляет в сгенерированный сервис `Environment=PODMAN_SYSTEMD_UNIT=%n` — эта переменная доступна внутри контейнера и используется механизмом `podman auto-update` для перезапуска нужного юнита.

### 5. Безопасность: секреты vs переменные окружения

**Критическое правило:** Никогда не передавайте пароли, API-ключи или сертификаты через переменные окружения.

- **Риск**: Переменные видны в `podman inspect`, `ps`, а также в логах систем мониторинга и через `/proc/<pid>/environ` на хосте.
- **Решение**: Используйте нативный механизм секретов.

```bash
# Правильный подход (Secret)
podman secret create db_pass -
podman run --secret db_pass my-db-app

# Секрет как переменная окружения (type=env)
podman run --secret source=db_pass,type=env my-db-app
```

- Секреты с `type=env` с Podman 5.2 маскируются в выводе `podman inspect` как `*******`.
- Чувствительные значения не должны попадать в команды `run`/`create` и, как следствие, в историю оболочки — создавайте секреты из stdin, файлов или переменных окружения.
- Для конфигурации, не содержащей секретов, применяйте `--env-file` вместо длинных цепочек `-e` (меньше шансов случайно оставить значение в истории и проще ротация между средами).

Подробнее: **[Секреты Podman](./podman_secrets.md)**.

**Раскрытие переменных в командах:** для использования переменной внутри `CMD` или `ENTRYPOINT` всегда используйте shell-форму или явный вызов оболочки:

```dockerfile
# Верно (интерпретируется /bin/sh)
CMD ["sh", "-c", "echo $MY_VAR"]

# Ошибка (переменная не будет раскрыта)
CMD ["echo", "$MY_VAR"]
```

**Обновление Podman как мера безопасности:** CVE-2026-57231 (исправлена в 5.8.4) позволяла вредоносному образу с некорректными ENV-записями утечь переменные окружения хоста, в том числе через glob-оператор `*`. Поддерживайте актуальную версию Podman.

### 6. Диагностика и просмотр переменных

```bash
# Переменные внутри работающего контейнера
podman exec my-app env

# Значение одной переменной
podman exec my-app printenv NODE_ENV

# Переменные из конфигурации контейнера (без exec)
podman inspect my-app --format '{{range .Config.Env}}{{println .}}{{end}}'

# Переменные, заданные в образе по умолчанию
podman image inspect nginx --format '{{range .Config.Env}}{{println .}}{{end}}'
```

Для одноразовой команды можно расширить окружение прямо в `exec`:

```bash
podman exec -e NODE_ENV=test -e APP_LOG_LEVEL=debug my-app ./run-tests.sh
```

## Дополнительная информация

### Нюансы и ограничения

- Переменные из `containers.conf` и флагов `--env` фиксируются в конфигурации контейнера в момент создания; `podman exec` без явных `-e` использует окружение из конфигурации.
- `--env-host` и `--env-merge` неприменимы к удаленному клиенту Podman (`--env-host` явно задокументирован как недоступный).
- Переменные `PATH` и `container` задаются Podman только если не переопределены образом или флагами.
- `TERM` появляется в окружении только при запуске с `-t`/`--tty` (Docker задает `TERM` независимо от tty — отличие в поведении).
- Для миграции с Docker см. **[Миграция с Docker](./migration-from-docker.md)** — таблица соответствия `environment:`/`env_file:` → `Environment=`/`EnvironmentFile=`.
