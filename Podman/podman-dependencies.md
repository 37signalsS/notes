# Управление зависимостями и готовностью в Podman

## Определения

**Зависимости контейнеров** — это логические и временные связи между компонентами распределенного приложения, определяющие порядок их запуска, остановки и перезапуска (например, API-сервер требует предварительного запуска и готовности базы данных).

**Готовность сервиса (Readiness)** — состояние приложения внутри контейнера, при котором оно не только запущено как процесс, но и полностью инициализировано и готово к обработке входящих запросов.

**Notify=healthy** — специфический параметр Podman и Quadlet, который интегрирует механизмы **Healthcheck** контейнера с системой инициализации **systemd**. Он позволяет считать юнит "запущенным" (Active) только после прохождения проверки здоровья.

**sd_notify** — протокол уведомлений systemd, используемый для передачи сообщений о готовности от приложения к менеджеру системных служб.

## Основные концепции

### Архитектурный вызов: Бездемонность vs Очередность

В Docker центральный демон `dockerd` управляет всей цепочкой запуска. В Podman каждый контейнер — это независимый процесс. Это создает сложности при попытке реализовать классический `depends_on`:
1. **Отсутствие координатора**: Нет единого процесса, который бы ждал готовности одного контейнера перед запуском другого в CLI-режиме.
2. **Проблема "Race Condition"**: Запуск контейнера (`podman run`) считается успешным сразу после старта процесса, даже если приложение внутри будет инициализироваться еще 30 секунд.

### Решение: Делегирование в systemd

В экосистеме Podman управление сложными зависимостями делегируется **systemd**. Это дает ряд преимуществ:
- **Параллелизм**: systemd запускает независимые службы одновременно.
- **Декларативность**: Связи описываются через `Requires`, `Wants`, `After`, `BindsTo`.
- **Надежность**: Если база данных упадет, зависимое приложение может быть автоматически остановлено или перезапущено.

## Методы обеспечения связности (Connectivity)

Перед ожиданием готовности необходимо настроить сетевое взаимодействие.

### 1. Сетевое пространство имен Пода (Pod)
Все контейнеры внутри одного пода разделяют один сетевой стек.
- **Взаимодействие**: Только через `localhost` и порты.
- **Особенности**: DNS-имена контейнеров внутри пода не резолвятся, используйте `127.0.0.1`.

### 2. Пользовательские сети (User-defined networks)
Использование сетевого стека **Netavark** (для rootful) или **pasta/slirp4netns** (для rootless).
- **Взаимодействие**: По именам контейнеров через встроенный DNS (**Aardvark**).
- **Важно**: Сети `bridge` не обеспечивают автоматический DNS-резолвинг для имен, заданных через `--name`, если они не созданы вручную (`podman network create`).

## Практические сценарии

### 1. Реализация Readiness через Quadlet (Рекомендуется)

Это наиболее надежный способ имитации `depends_on` с проверкой состояния.

**База данных: `db.container`**
```ini
[Unit]
Description=Database Service

[Container]
Image=docker.io/library/postgres:16
Environment=POSTGRES_PASSWORD=secret
# Проверка готовности внутри образа
HealthCmd=pg_isready -U postgres
HealthInterval=5s
HealthRetries=3
# Сообщаем systemd, что мы готовы, только когда Healthcheck = healthy
Notify=healthy

[Service]
# Важно: Type=notify устанавливается Quadlet автоматически при Notify=healthy
Restart=on-failure

[Install]
WantedBy=multi-user.target
```

**Приложение: `app.container`**
```ini
[Unit]
Description=Application Service
# Логическая зависимость: app не запустится без db
Requires=db.service
# Временная зависимость: ждать завершения старта db
After=db.service
# Жесткая связь: если db упадет, app тоже остановится
BindsTo=db.service

[Container]
Image=docker.io/library/my-app:latest
Environment=DB_HOST=db.service
```

### 2. Ожидание через "Init-логику" в CLI

Если вы не используете systemd (например, в скриптах миграции), используйте циклы ожидания.

```bash
# Запуск БД
podman run -d --name db-server -e POSTGRES_PASSWORD=secret postgres

# Ожидание готовности порта перед запуском приложения
podman run --rm --network host alpine sh -c '
  until nc -z localhost 5432; do
    echo "Waiting for DB..."
    sleep 1
  done
  echo "DB is up!"'

# Запуск основного приложения
podman run -d --name web-app --link db-server:db my-web-app
```

### 3. Использование `depends_on` в Podman Compose

`podman-compose` (Python-версия) поддерживает `depends_on` с условиями готовности, имитируя поведение Docker Compose.

```yaml
services:
  db:
    image: postgres
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      retries: 5
  
  web:
    image: my-app
    depends_on:
      db:
        condition: service_healthy
```
*Примечание: При трансляции этого файла в Quadlet (через `podman-compose` или вручную) убедитесь, что используется `Notify=healthy`.*

## Диагностика и отладка

При возникновении проблем с запуском зависимых служб используйте следующие инструменты:

1. **Проверка состояния юнитов**:
   ```bash
   systemctl --user status db.service app.service
   ```
   Если `db.service` застрял в статусе `activating`, значит его Healthcheck не проходит или `Notify=healthy` не срабатывает.

2. **Анализ логов готовности**:
   ```bash
   # Просмотр событий Healthcheck в реальном времени
   podman events --filter event=health_status
   ```

3. **Инспекция статуса здоровья**:
   ```bash
   podman inspect --format '{{.State.Health.Status}}' db-container
   ```

## Дополнительная информация

### Сравнение методов управления

| Метод | Плюсы | Минусы |
| :--- | :--- | :--- |
| **systemd (Quadlet)** | Максимальная надежность, нативный откат, управление ресурсами. | Требует настройки юнит-файлов. |
| **Wait-скрипты** | Простота, не зависит от системы инициализации. | "Засорение" образов, отсутствие мониторинга после старта. |
| **Podman Compose** | Привычный синтаксис Docker Compose. | Дополнительная зависимость (Python), менее гибко чем Quadlet. |
