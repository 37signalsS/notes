# Podman: Архитектура без демона (Daemonless)

## Определения

**Daemonless Architecture** — модель управления контейнерами без центрального привилегированного демона. Каждая команда (`podman run`, `podman ps`) запускает отдельный процесс, который выполняет задачу и завершается. Жизненным циклом запущенных контейнеров управляют легковесные процессы-мониторы.

## Основные концепции

### Сравнение архитектур

| Аспект | Docker | Podman |
| :--- | :--- | :--- |
| **Модель** | Клиент-серверная (демон `dockerd`) | Fork/exec на контейнер |
| **Процессы** | Контейнеры — дочерние процессы демона | Контейнеры — независимые процессы |
| **Требования root** | Демон требует root | Rootless по умолчанию |
| **Накладные расходы** | 140-180 МБ (демон) | 0 МБ (нет демона) |
| **Интеграция с systemd** | Через внешние unit-файлы | Нативная генерация unit-файлов |

### Компоненты архитектуры Podman

Архитектура Podman следует философии UNIX: "делай одну вещь, и делай её хорошо".

1. **Модель `fork/exec`**:
    - Когда вы выполняете `podman run`, ваш терминал запускает процесс `podman`.
    - Этот процесс подготавливает все необходимое для запуска контейнера (слои образа, сетевые настройки).
    - Затем он порождает (`forks`) процесс-монитор `conmon`.
    - `conmon`, в свою очередь, вызывает OCI-совместимый рантайм (`runc` или `crun`) для создания контейнера.
    - После этого первоначальный процесс `podman` **завершает свою работу**. В системе остаются только `conmon` и сам контейнер.

2. **`conmon` — монитор контейнера**:
    - Это легковесный процесс на C, который запускается **для каждого контейнера индивидуально**.
    - **Задачи `conmon`**:
        - Мониторинг основного процесса контейнера и передача его `exit-code`.
        - Обработка `STDIN`, `STDOUT`, `STDERR` и ведение логов контейнера.
        - Обработка `TTY` (интерактивных терминалов).
        - Реагирование на сигналы, например, от `podman kill`.
    - Так как на каждый контейнер свой `conmon`, сбой одного не влияет на остальные.

3. **Интеграция с `systemd`**:
    - Поскольку контейнеры (через `conmon`) являются обычными дочерними процессами пользовательской сессии, они идеально вписываются в модель управления `systemd`.
    - Podman может автоматически генерировать `systemd unit`-файлы (`podman generate systemd`), что позволяет управлять контейнерами как стандартными системными службами (автозапуск, зависимости, перезапуск при сбое).

### Генерация systemd-юнитов для автозапуска

После перезагрузки системы процессы контейнеров не сохраняются. Для автоматического запуска контейнеров при старте системы используется интеграция с `systemd`.

**Процесс настройки:**

1. **Создание контейнера** (если еще не создан):

   ```bash
   podman run -d --name my_app -p 8080:80 nginx
   ```

2. **Генерация systemd-юнита**:

   ```bash
   # Создать файл сервиса в домашней директории
   podman generate systemd --name my_app --files --new
   ```

   Ключи:
   - `--name my_app`: Имя контейнера.
   - `--files`: Создать файл, а не выводить в stdout.
   - `--new`: Создавать новый контейнер при каждом запуске (удалять старый, если есть).

3. **Настройка systemd**:
   - Для пользовательских сервисов: скопируйте файл в `~/.config/systemd/user/`
   - Включите сервис:

     ```bash
     systemctl --user enable --now my_app.service
     ```

4. **Настройка Lingering**:
   - По умолчанию пользовательские сервисты systemd работают только при активной сессии пользователя.
   - Чтобы сервисы запускались после перезагрузки без логина, включите `lingering`:

     ```bash
     loginctl enable-linger $(whoami)
     ```

> **Примечание о привилегированных портах:** В rootless-режиме контейнеры не могут слушать на портах ниже 1024. Если приложение внутри контейнера должно быть доступно по порту 80, настройте проброс на уровне firewall или используйте порт > 1024 (например, `-p 8080:80`).

## Практические сценарии

### 1. Жизненный цикл `podman run`

```
[user@host]$ podman run -d nginx
    |
    +--> 1. Запускается процесс `podman`
    |
    +--> 2. `podman` порождает `conmon`
    |
    +--> 3. `conmon` вызывает `crun/runc` для создания контейнера (с namespaces/cgroups)
    |
    +--> 4. `runc` запускает `nginx` внутри контейнера
    |
    +--> 5. Процесс `podman` завершается. В системе остаются:
           - conmon (мониторит nginx)
           - nginx (работает в контейнере)
```

Проверить это можно командой `ps -ef --forest | grep -E 'podman|conmon|nginx'`. Процесса `podman` не будет в списке после запуска контейнера.

### 2. Преимущества Daemonless-архитектуры

- **Безопасность**:
  - Нет единого демона с `root`-привилегиями, который можно было бы скомпрометировать.
  - Архитектура идеально подходит для **[Rootless режима](./podman_rootless.md)**, где все процессы выполняются от имени непривилегированного пользователя.
- **Отказоустойчивость**: Сбой одного `conmon` или контейнера не затрагивает остальную систему. Нет "единой точки отказа".
- **Интеграция с ОС**: Контейнеры видны как обычные процессы в дереве `systemd` и могут управляться стандартными утилитами (`systemctl`, `journalctl`). Логи контейнеров по умолчанию отправляются в `journald`.

### 3. Эмуляция Docker API

Для совместимости с инструментами, ожидающими Docker API (например, `docker-compose`), Podman предоставляет сервис, который эмулирует `docker.sock`.

```bash
# Включить и запустить сокет для текущего пользователя
systemctl --user enable --now podman.socket

# Установить переменную окружения
export DOCKER_HOST=unix:///run/user/$(id -u)/podman/podman.sock

# Теперь инструменты, использующие Docker API, будут работать с Podman
docker-compose up -d
```

## Дополнительная информация

### Компоненты и версии

| Компонент | Версия | Назначение |
| :--- | :--- | :--- |
| **Podman** | 5.x | Управление контейнерами и подами |
| **conmon** | 2.1.x | Монитор контейнера (легковесный процесс на C) |
| **crun** | 1.x | OCI runtime (на C, быстрее runc) |
| **runc** | 1.2.x | OCI runtime (эталонная реализация, на Go) |
| **Netavark** | 1.x | Сетевой драйвер (заменяет CNI в Podman 4+) |
| **Aardvark-dns** | 1.x | DNS для контейнеров (заменяет dnsmasq) |

### Преимущества и недостатки daemonless-архитектуры

| Преимущества | Недостатки |
| :--- | :--- |
| Нет единой точки отказа | Нет централизованного управления |
| Экономия памяти (0 МБ idle) | Некоторые инструменты требуют Docker API |
| Лучшая изоляция процессов | Меньшая зрелость экосистемы |
| Нативная интеграция с systemd | Сложнее отладка распределённых процессов |
| Rootless по умолчанию | |
