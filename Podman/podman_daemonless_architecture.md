# Архитектура без демона: ключевые особенности Podman

Podman реализует контейнеры без постоянного фонового демона. Каждая команда запускается как краткоживущий процесс пользователя, который подготавливает окружение, создаёт или управляет контейнером и завершается, оставляя лёгкий монитор `conmon` следить за жизненным циклом. Такой подход снижает площадь атаки, упрощает изоляцию прав и интеграцию с пользовательским пространством.

## Компоненты и поток процессов

Podman опирается на стек OCI:

*   **libpod** — управление объектами (контейнеры, образы, pods).
*   **conmon** — отдельный процесс-наблюдатель на контейнер; пишет логи, ретранслирует stdio, фиксирует exit-код.
*   **OCI runtime** (`crun` по умолчанию, либо `runc`) — создание и запуск контейнеров через специфическую для Linux изоляцию.
*   **containers/storage** и **containers/image** — хранилище слоёв и транспорт образов.

> Основой изоляции в Podman, как и в других контейнерных системах на Linux, служат **`namespaces`** и **`cgroups`**. Подробнее об этих механизмах можно прочитать в документе **[Изоляция процессов в Linux: cgroups и namespaces](./Concepts/linux_isolation.md)**.

Пример отражения отсутствия демона:

```css
podman run -d --name web -p 8080:80 nginx
ps -ef | egrep 'podman|conmon|nginx'
# podman-процесс отсутствует после старта; остаются conmon и процессы в контейнере
```

## Rootless-режим как норма

Podman полноценно работает без привилегий суперпользователя: контейнер исполняется в user namespace, а UID/GID внутри сопоставляются поддиапазонам на хосте. Это минимизирует риск эскалации и упрощает запуск в мультипользовательских системах и CI-окружениях. При активном SELinux/AppArmor правила применяются и к rootless-контейнерам.

**Ключевые аспекты:**

*   Не требуется демон с правами root.
*   Сетевые стековые особенности: в rootless используется `slirp4netns` или `pasta` для проброса сети.
*   Ограниченные capability по умолчанию; при необходимости тонко настраиваются флаги `--cap-add`, `--security-opt`.

Проверка:

```bash
podman info | grep Rootless
cat /etc/subuid /etc/subgid  # сопоставления пользователей
```

## Совместимость с OCI и докер-экосистемой

Podman работает с OCI-образами и поддерживает знакомую CLI-семантику. Для сценариев, ожидающих Docker API, доступен сокет-совместимый сервис:

```bash
systemctl --user enable --now podman.socket
export DOCKER_HOST=unix:///run/user/1000/podman/podman.sock
# клиенты, использующие Docker API, смогут подключаться к Podman
```

Это позволяет использовать существующие инструменты, не меняя пайплайны.

## Pods как базовый примитив

Podman вводит `pods` — группы контейнеров, разделяющих набор неймспейсов и единый «infra»-контейнер. Это приближает модель к Kubernetes.

**Сравнение:**

| Характеристика | Podman Pod | Kubernetes Pod |
| :--- | :--- | :--- |
| **Инфраструктурный контейнер** | Да, «infra» | Да, pause |
| **Общие неймспейсы** | net, uts, ipc по умолчанию | net, uts, ipc по умолчанию |
| **Назначение** | Локальная группировка процессов | Оркестрация в кластере |

**Пример:**

```applescript
podman pod create --name app
podman run -d --pod app --name api ghcr.io/guzzle/api:latest
podman run -d --pod app --name sidecar busybox sleep 3600
```

## Сетевой стек: Netavark и DNS

Начиная с ветки 4.x, по умолчанию используется Netavark и Aardvark DNS для rootful-сетей: быстрее старт, предсказуемые правила NAT, корректная работа с pods и именами. В rootless-режиме применяется `slirp4netns`/`pasta`, что не требует прав суперпользователя и упрощает запуск в пользовательских сессиях.

Создание пользовательской сети:

```css
podman network create devnet
podman run -d --network devnet --name db postgres:16
```

## Интеграция с systemd и автозапуск

Поскольку демон отсутствует, автозапуск реализуется системными юнитами. Podman генерирует unit-файлы для контейнеров и pods:

```css
podman generate systemd --name web --new --files
systemctl --user enable --now container-web.service
```

Юниты корректно обрабатывают перезапуски, порядок зависимостей и логирование через `journald`.
