# Подман: Бездемонная (Daemonless) архитектура

## Определения

**Bezdemonnaya arhitektura (Daemonless Architecture)** — модель управления контейнерами, в которой отсутствует центральный фоновый процесс (демон) с привилегиями суперпользователя. В отличие от Docker, где клиент взаимодействует с демоном `dockerd`, в Podman каждая команда запускает отдельный независимый процесс.

**conmon (Container Monitor)** — легковесная утилита на языке C, выступающая в роли монитора жизненного цикла контейнера. Она отвечает за чтение логов, управление стандартными потоками ввода-вывода (**TTY**) и фиксацию кода завершения основного процесса контейнера.

**OCI (Open Container Initiative)** — открытый стандарт, определяющий форматы образов и спецификации сред выполнения контейнеров, обеспечивающий совместимость между различными инструментами (Podman, Docker, Kubernetes).

## Основные концепции

### Модель Fork/Exec

Podman использует стандартную Unix-модель **Fork/Exec** вместо клиент-серверной архитектуры. Это означает, что контейнеры являются прямыми потомками процесса, который их запустил (или передаются под управление `systemd`).

**Этапы запуска контейнера (`podman run`):**

1. Пользователь запускает команду `podman`.
2. Процесс `podman` порождает (fork) процесс-монитор `conmon`.
3. `conmon` вызывает низкоуровневую среду выполнения (**OCI Runtime**, например, `crun` или `runc`).
4. Среда выполнения настраивает пространства имен (**namespaces**) и группы контроля (**cgroups**), после чего запускает приложение.
5. Процесс `podman` завершается, а `conmon` остается в памяти до завершения работы контейнера.

### Компоненты системы

Архитектура Podman следует принципу модульности, где каждый компонент выполняет одну задачу:

| Компонент | Назначение |
| :--- | :--- |
| **Podman CLI** | Интерфейс для пользователя, управление образами и подами. |
| **conmon** | Мониторинг состояния контейнера и сбор логов. |
| **crun / runc** | Низкоуровневые среды выполнения (**OCI Runtime**). `crun` написан на C и является приоритетным для Podman. |
| **Netavark** | Современный сетевой стек для настройки интерфейсов и правил маршрутизации. |
| **Aardvark-dns** | Встроенный DNS-сервер для разрешения имен контейнеров внутри сетей. |

### Интеграция с systemd и Quadlet

Отсутствие демона позволяет операционной системе управлять контейнерами как обычными системными службами.

- **Quadlet**: Декларативный инструмент, преобразующий файлы описания контейнеров (например, `.container`) в нативные юниты **systemd**. Это рекомендуемый способ обеспечения автозапуска и управления зависимостями.
- **Логирование**: Поскольку контейнеры — это обычные процессы, их вывод напрямую перехватывается и сохраняется в **journald**, что упрощает централизованный сбор логов.

## Практические сценарии

### 1. Анализ дерева процессов

Для подтверждения отсутствия центрального демона можно исследовать иерархию процессов при запущенном контейнере:

```bash
# Запуск контейнера Nginx в фоновом режиме
podman run -d --name web-monitor nginx

# Просмотр дерева процессов (conmon является родителем для nginx)
ps -ef --forest | grep -E 'conmon|nginx'
# → 1000  1234  1  0  conmon --api-version ...
# → 1000  1235  1234  0  \_ nginx: master process ...
```

### 2. Использование Quadlet для автозапуска

Создание сервиса, который будет автоматически запускаться системой.

**Файл:** `/etc/containers/systemd/nginx-web.container`

```ini
[Unit]
Description=Nginx Web Server

[Container]
Image=docker.io/library/nginx:latest
PublishPort=8080:80

[Install]
WantedBy=multi-user.target
```

**Применение настроек:**

```bash
systemctl daemon-reload
systemctl start nginx-web.service
```

### 3. Эмуляция Docker API (Socket)

Если внешние инструменты (например, `docker-compose`) требуют наличия сокета, Podman может запустить службу эмуляции API:

```bash
# Включение сокета для текущего пользователя
systemctl --user enable --now podman.socket

# Проверка через переменную окружения
export DOCKER_HOST="unix://$XDG_RUNTIME_DIR/podman/podman.sock"
podman ps
```

## Дополнительная информация

### Преимущества бездемонной архитектуры

1. **Отказоустойчивость**: Сбой одного компонента (например, CLI) не влияет на работу уже запущенных контейнеров.
2. **Безопасность**: Устраняется необходимость в процессе, постоянно работающем с правами root. Это позволяет нативно реализовать **Rootless** режим.
3. **Ресурсы**: В режиме ожидания Podman потребляет 0 МБ оперативной памяти, так как нет постоянно работающего демона.
