# Podman: Бездемонная (Daemonless) архитектура

## Определения

**Бездемонная архитектура (Daemonless Architecture)** — модель управления контейнерами, исключающая наличие центрального фонового процесса (демона) с правами суперпользователя. В Podman каждая команда является независимым процессом, что устраняет единую точку отказа и повышает безопасность.

**Модель Fork/Exec** — классическая Unix-модель порождения процессов. В Podman контейнеры не являются "клиентами" демона, а становятся прямыми потомками процесса, который их запустил (или передаются под управление менеджера системных служб).

**conmon (Container Monitor)** — легковесная утилита на языке C, выступающая в роли монитора жизненного цикла контейнера. Она отвечает за сбор логов, удержание TTY и фиксацию кода завершения основного процесса. В современных версиях Podman также внедряется **conmon-rs** — высокопроизводительная реализация на Rust.

**OCI Runtime (Среда выполнения)** — низкоуровневая утилита (например, **crun** или **runc**), которая непосредственно взаимодействует с ядром Linux для настройки пространств имен (Namespaces) и контрольных групп (Cgroups).

## Основные концепции

### Жизненный цикл процесса (Цепочка запуска)
Когда пользователь выполняет команду `podman run`, запускается следующая цепочка событий:
1. **Podman CLI**: Считывает конфигурацию, проверяет наличие образа и подготавливает спецификацию OCI.
2. **conmon**: Podman порождает процесс `conmon`. Он становится "родителем" для контейнера и остается в памяти, даже если CLI-процесс завершится.
3. **OCI Runtime**: `conmon` вызывает среду выполнения (по умолчанию `crun`).
4. **Контейнер**: Рантайм настраивает изоляцию в ядре и запускает приложение. После старта рантайм завершается, оставляя `conmon` наблюдать за процессом.

### Модульные компоненты (Ecosystem)
Podman делегирует задачи специализированным инструментам, следуя философии Unix:
- **Сборка**: Выполняется через **Buildah**.
- **Инспекция и транспорт**: Выполняются через **Skopeo**.
- **Сеть**: Стек **Netavark** настраивает интерфейсы, а **Aardvark-dns** обеспечивает разрешение имен внутри сетей.
- **Хранилище метаданных**: В Podman 5.x осуществлен переход на **SQLite**, что обеспечивает транзакционную целостность и лучшую производительность по сравнению с BoltDB.

### Интеграция с systemd и Quadlet
Поскольку Podman не имеет собственного демона-планировщика, он использует **systemd** как нативный оркестратор для одиночных узлов.
- **Quadlet**: Технология, позволяющая описывать контейнеры в декларативных `.container` файлах. Systemd автоматически преобразует их в юниты при загрузке.
- **Преимущество**: Контейнеры получают все возможности системных служб: автоматический перезапуск, управление зависимостями, лимиты ресурсов и сбор логов в `journald`.

## Практические сценарии

### 1. Анализ дерева процессов
Вы можете убедиться в отсутствии демона, проследив иерархию процессов. В отличие от Docker, где родителем всегда является `dockerd`, здесь вы увидите `conmon`.

```bash
# Запуск контейнера в фоне
podman run -d --name web-test nginx:alpine

# Поиск монитора и процесса приложения
ps -ef --forest | grep -E 'conmon|nginx'
# → 1000  12345     1  0  conmon --api-version ...
# → 1000  12346 12345  0  \_ nginx: master process ...
```

### 2. Декларативное управление через Quadlet
Рекомендуемый способ запуска сервисов в продакшене.

**Файл:** `~/.config/containers/systemd/web.container`
```ini
[Unit]
Description=Nginx Production Service

[Container]
Image=docker.io/library/nginx:latest
PublishPort=80:80
AutoUpdate=registry

[Install]
WantedBy=default.target
```
После создания файла выполните `systemctl --user daemon-reload` и `systemctl --user start web.service`.

### 3. Эмуляция Docker API (Socket)
Для инструментов, которые не могут работать без сокета (например, Docker Desktop расширения или старые CI-агенты), Podman предоставляет службу API.

```bash
# Включение сокета (daemonless на бэкенде, но с API-прослойкой)
systemctl --user enable --now podman.socket

# Проверка работоспособности
export DOCKER_HOST="unix://$XDG_RUNTIME_DIR/podman/podman.sock"
docker info | grep "Runtime"
# → Runtime: crun
```

## Дополнительная информация

### Преимущества архитектуры
1. **Безопасность**: Нет процесса с правами root, постоянно слушающего сеть или сокет. Это минимизирует поверхность атаки.
2. **Изоляция сбоев**: Падение процесса Podman не приводит к остановке контейнеров.
3. **Обновления без простоя**: Вы можете обновлять сам пакет Podman на хосте, не перезапуская запущенные сервисы.
