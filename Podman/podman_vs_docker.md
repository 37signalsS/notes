# Podman vs Docker: Ключевые различия

Оба инструмента поддерживают стандарты [Open Container Initiative (OCI)](../Docker/docker_overview.md#open-container-initiative-oci-spec), что обеспечивает совместимость образов и сред выполнения. Однако их архитектура и философия безопасности кардинально различаются.

## Основные концепции: Сравнительный анализ

| Критерий | Docker | Podman |
| :--- | :--- | :--- |
| **Архитектура** | **Клиент-серверная (`daemon`)**: `docker` CLI отправляет команды демону `dockerd`, который управляет контейнерами. | **Без демона (`daemonless`)**: `podman` напрямую взаимодействует со средой выполнения, запуская контейнеры как дочерние процессы. |
| **Безопасность** | Изначально `root-centric`, но поддерживает `rootless` режим (требует настройки). Безопасность зависит от защиты демона. | `Rootless-first` дизайн. Контейнеры по умолчанию запускаются от имени обычного пользователя, используя **[user namespaces](../Docker/Concepts/linux_isolation.md#1-пространства-имён-namespaces)**. Работает "из коробки" без дополнительной настройки. |
| **Среда выполнения** | `containerd` + `runc` | `crun` (часто по умолчанию, быстрее) или `runc`. |
| **Интеграция с ОС** | Ограниченная. Для автозапуска контейнеров требуются [собственные systemd-юниты](../Docker/docker_systemd.md). | Глубокая. Команда `podman generate systemd` автоматически создает `unit`-файлы для управления контейнерами. |
| **Группы контейнеров** | `docker-compose` (официальный инструмент) | `podman-compose` (сторонняя утилита) или концепция **Pods** — групп контейнеров с общими ресурсами. |
| **Интеграция с K8s** | Отсутствует встроенная генерация манифестов. | `podman generate kube` / `podman play kube` для прямого взаимодействия с Kubernetes-манифестами. |
| **Сеть** | `libnetwork` | `Netavark` и `Aardvark-dns` (для rootful) или `slirp4netns` (для rootless). |
| **Философия** | "Monolith" — один инструмент с большим количеством функций. | **Unix-философия** — набор специализированных утилит (Podman, Buildah, Skopeo), каждая решает свою задачу. |

## Практические сценарии

### 1. Совместимость команд (CLI)

Для большинства базовых операций достаточно заменить `docker` на `podman`. Многие пользователи создают псевдоним `alias docker=podman` для полной прозрачности.

```bash
# Запуск контейнера
docker run -d --name web -p 8080:80 nginx
podman run -d --name web -p 8080:80 nginx

# Сборка образа
docker build -t app:1.0 .
podman build -t app:1.0 .

# Работа с реестром
docker login registry.example.com
podman login registry.example.com
```

### 2. Сценарии выбора

- **Podman** — идеальный выбор для:
  - Linux-серверов с фокусом на безопасность и интеграцию с `systemd`.
  - Многопользовательских сред, где изоляция пользователей критична (`rootless`).
  - Разработки и тестирования Kubernetes-приложений (`podman play kube`).

- **Docker** — остается сильным выбором для:
  - Устоявшихся CI/CD пайплайнов, сильно завязанных на `docker-compose`.
  - Кросс-платформенной разработки (Windows/macOS), где `Docker Desktop` предоставляет более зрелый UX.
  - Экосистем с большим количеством плагинов и инструментов, ориентированных на Docker API.

### 3. Rootless-режим: Подробнее

Одно из ключевых преимуществ Podman — это возможность запуска контейнеров без привилегий root.

**Как это работает в Docker:**
- Добавление пользователя в группу `docker` позволяет управлять контейнерами без `sudo`, но сами контейнеры по-прежнему работают от имени root (или указанного пользователя внутри образа).
- Для полноценной работы Docker без root (Rootless Docker) требуется специальная настройка.

**Как это работает в Podman:**
- Podman работает в режиме rootless "из коробки" без дополнительной настройки.
- Использует **User Namespaces** для изоляции: процессы внутри контейнера видят себя как root (UID 0), но в хостовой системе это непривилегированный пользователь.
- Это снижает риск компрометации системы через уязвимости в контейнере.

### 4. Привилегированные порты

При работе в rootless-режиме есть ограничение на использование привилегированных портов (ниже 1024).

- **Проблема:** Пользователь без root-прав не может слушать на портах 80, 443 и т.д.
- **Решение в Podman:**
  - Снаружи (на хосте) можно слушать только на портах > 1024 (например, `-p 8080:80`).
  - Для проброса портов < 1024 можно использовать firewall (firewalld) для перенаправления:
    ```bash
    firewall-cmd --add-forward-port=port=80:proto=tcp:toport=8080
    ```
  - Или использовать `pasta` (альтернативный сетевой стек для rootless).

### 5. Экосистема инструментов (Buildah, Skopeo)

В отличие от Docker (монолит), Podman следует Unix-философии, разделяя функционал на отдельные утилиты:

- **Podman**: Управление контейнерами (запуск, остановка, удаление).
- **Buildah**: Сборка образов. Позволяет создавать образы без демона, с использованием стандартных инструментов Linux.
- **Skopeo**: Управление реестрами. Копирование, синхронизация и инспекция образов без загрузки их на локальную машину.

> При установке модуля `container-tools` в RHEL-подобных системах все эти инструменты устанавливаются вместе.
