# Секреты в Podman

## Определения

**Podman Secrets** — встроенный механизм управления конфиденциальными данными (паролями, API-ключами, сертификатами, SSH-ключами), обеспечивающий их безопасную доставку в контейнеры. Ключевое свойство: секреты не сохраняются в истории слоев образа — они не попадают в результат `podman commit` и не включаются в архив, создаваемый `podman export`. От переменных окружения они отличаются тем, что значение не раскрывается напрямую (env-секреты маскируются в выводе `podman inspect` как `*******`).

**Secret driver (драйвер секретов)** — компонент хранения, определяющий, где и как хранится содержимое секрета на хосте. По умолчанию используется драйвер `file` (обычные файлы в незашифрованном виде); доступны также `pass` (GPG-шифрование) и `shell` (пользовательские скрипты).

**tmpfs mount** — технология, применявшаяся в ранних версиях Podman (3.x — начало 4.x) для доставки секретов: данные помещались во временную файловую систему в оперативной памяти контейнера. В актуальных версиях содержимое секрета копируется в локальное хранилище секретов хоста и монтируется в контейнер как файл только для чтения (подробнее — раздел «Доставка секрета в контейнер»). В любом случае секреты не записываются в слои образа, а при остановке или удалении контейнера их файлы исчезают вместе с ним.

**`/run/secrets/`** — стандартный каталог внутри контейнера, в который монтируются секреты типа `mount` (по умолчанию — в `/run/secrets/<имя_секрета>`).

## Основные концепции

### Механизм хранения и драйверы

По умолчанию Podman использует драйвер `file`, который сохраняет содержимое секрета в виде обычного файла (без шифрования «at rest») в хранилище контейнеров.

- **Путь хранения (Rootful)**: `/var/lib/containers/storage/secrets/`
- **Путь хранения (Rootless)**: `$HOME/.local/share/containers/storage/secrets/`

**Драйвер `pass`** хранит секрет в GPG-зашифрованном файле (требуется предварительно настроенная связка ключей GPG у пользователя):

```bash
podman secret create --driver=pass my_secret ./secret.txt
```

**Драйвер `shell`** управляет секретами через пользовательские скрипты. В `containers.conf` (`/etc/containers/containers.conf` или `~/.config/containers/containers.conf`) задается активный драйвер и пути к скриптам:

```ini
[secrets]
driver = "shell"

[secrets.opts]
list =
lookup =
store =
delete =
```

Скриптам передается переменная окружения `SECRET_ID` (кроме операции `list`), данные секрета передаются через stdin/stdout. Дополнительные параметры драйвера задаются флагом `--driver-opts key1=val1,key2=val2` при создании секрета.

**Критическое замечание по безопасности**: хотя секреты защищены внутри контейнера (файл монтируется только на чтение и не попадает в слои образа), на самом хосте драйвер `file` хранит их как обычные файлы без шифрования. Для защиты «at rest» необходимо шифрование диска (LUKS) либо использование драйвера `pass`/`shell`.

### Управление через CLI

| Операция | Команда | Описание |
| :--- | :--- | :--- |
| **Создать** | `podman secret create <имя> <файл>` | Создание из файла или `-` для stdin (`< 512 КБ`) |
| **Проверить наличие** | `podman secret exists <имя>` | Не выводит текст; код возврата `0`/`1` (Podman 4.7+) |
| **Список** | `podman secret ls` | Просмотр всех доступных секретов |
| **Инспекция** | `podman secret inspect <имя>` | Метаданные (дата создания, драйвер, ID); значение по умолчанию скрыто |
| **Показать значение** | `podman secret inspect --showsecret <имя>` | Вывод фактического значения (Podman 4.7+) |
| **Удаление** | `podman secret rm <имя>` | Удаление из хранилища хоста; безопасно для работающих контейнеров |

**Полезные флаги `podman secret create`:**
- `--driver`, `-d` — драйвер (`file` по умолчанию, `pass`, `shell`); `--driver-opts` — параметры драйвера.
- `--env` — читать значение из переменной окружения: `podman secret create --env my_secret MYSECRET` (Podman 4.9+).
- `--replace` — обновить уже существующий секрет с тем же именем (актуально для ротации; не изменяет значение в уже созданных контейнерах).
- `--ignore` — не возвращать ошибку, если секрет с таким именем уже существует; вернуть ID существующего (нельзя одновременно с `--replace`; Podman 5.8+).
- `--label`, `-l` — метаданные секрета (видимы в `ls`/`inspect`).

**Полезные флаги `podman secret ls` / `rm`:** `--filter` (фильтрация по имени/драйверу/меткам), `--format` (кастомизация вывода), `--all`, `-a` и `--ignore`, `-i` (у `rm`).

**Проверка на ротацию в скриптах:**

```bash
podman secret exists my_secret && echo "секрет существует"
# → секрет существует
```

### Доставка секрета в контейнер (`--secret`)

Секрет подключается флагом `--secret` (для `podman run` и `podman create`), синтаксис:

```text
--secret [source=]<секрет>[,opt=opt ...]
```

Поддерживаемые опции (актуальные версии Podman):

| Опция | Значение | Примечание |
| :--- | :--- | :--- |
| `type` | `mount` (по умолчанию) \| `env` | `mount` — секрет как файл; `env` — как переменная окружения |
| `target` | путь/имя | Для `mount`: путь в контейнере (по умолчанию `/run/secrets/<имя>`); для `env`: имя переменной (по умолчанию — имя секрета) |
| `uid` | число | Владелец файла; только для `mount`; по умолчанию `0` |
| `gid` | число | Группа файла; только для `mount`; по умолчанию `0` |
| `mode` | восьмеричное | Права файла; только для `mount`; по умолчанию `0444` |

**Особенности поведения:**
- Секреты **копируются и монтируются в контейнер в момент его создания**. `podman secret rm` безопасен для работающих контейнеров — после удаления (или удаления и повторного создания с тем же именем) контейнер продолжает видеть старое значение. Для смены значения в работающем контейнере его необходимо пересоздать (`podman rm -f` + `podman run`, либо `podman run --replace`).
- Для `type=mount` файл монтируется только для чтения; содержимое не попадает в слои образа и в `podman export`.
- Для `type=env` значение доступно как обычная переменная окружения, но в выводе `podman inspect` маскируется как `*******` (начиная с Podman 5.2).
- В `podman inspect` для mount-секретов выводится блок `Config.Secrets` с именами, ID и примененными `uid`/`gid`/`mode` — без содержимого.

### Сравнение механизмов доставки

| Характеристика | Переменные окружения | Монтирование файлов (Bind Mount) | Podman Secrets |
| :--- | :--- | :--- | :--- |
| **Видимость на хосте** | Высокая (`inspect`, `/proc/<pid>/environ`) | Видны в `mount` и `podman inspect` | Скрыты (`inspect` показывает только имена/ID) |
| **Видимость в контейнере** | Доступны всем процессам (`env`) | Постоянные файлы на диске | Файлы в `/run/secrets` только для чтения |
| **След в образе** | Могут попасть в слои | Нет | Нет |
| **Обновление** | Требует перезапуска | Требует перезапуска | Требует пересоздания контейнера (значение копируется при создании) |
| **Права доступа** | Не настраиваются | Наследуются от хоста | `uid`/`gid`/`mode` настраиваются (только `mount`) |

## Практические сценарии

### 1. Создание секрета и права доступа

При подключении секрета можно явно указать владельца и права доступа внутри контейнера.

```bash
# Создание секрета из строки (stdin)
echo "my-secure-token" | podman secret create api_token -

# Запуск с настройкой UID, GID и прав (mode) — только для type=mount
podman run -d \
  --name app-container \
  --secret api_token,target=/etc/api/token,uid=1000,gid=1000,mode=0400 \
  my-app-image
```

Значения по умолчанию: `uid=0`, `gid=0`, `mode=0444`. Современный эквивалент с явным указанием источника:

```bash
podman run --rm --secret source=api_token,type=mount,uid=1001,gid=1001,mode=440 \
  docker.io/library/alpine ls -l /run/secrets/api_token
```

### 2. Использование бинарных секретов

Podman поддерживает передачу бинарных данных (например, SSL-сертификатов или SSH-ключей).

```bash
# Создание секрета из бинарного файла
podman secret create ssl_cert ./server.crt

# Подключение в стандартный путь (/run/secrets/ssl_cert)
podman run --rm --secret ssl_cert alpine ls -l /run/secrets/
```

Лимит размера одного секрета — 512 КБ (для генерации секрета размером чуть меньше максимума через stdin можно использовать `openssl`).

### 3. Секреты как переменные окружения

Секрет можно доставить не файлом, а переменной окружения (`type=env`).

```bash
# Создание секрета из переменной окружения процесса
export MYSECRET="supersecret"
podman secret create --env my_secret MYSECRET

# Подключение как переменной окружения ENVSEC (внутри контейнера — printenv ENVSEC)
podman run --rm --secret my_secret,type=env,target=ENVSEC \
  docker.io/library/alpine printenv ENVSEC
```

**Важно:** несмотря на маскирование в `podman inspect`, значение env-секрета доступно всем процессам в контейнере через окружение — при выборе способа доставки стоит учитывать, что смонтировать файл с правами безопаснее, чем отдать секрет в окружение.

### 4. Ротация секретов

Ротация без остановки всего стека выполняется с флагом `--replace` (сохраняет имя и ID секрета); значение подхватывают вновь создаваемые контейнеры.

```bash
# Генерация криптографически стойкого секрета чуть меньше лимита 512000 байт и ротация
openssl rand -base64 378000 | podman secret create --replace my_secret -

# Для контейнеров, уже использующих секрет, требуется пересоздание
podman rm -f app-container
podman run -d --name app-container --secret api_token my-app-image
```

При автоматизации безопасно удалять секрет, который больше не нужен, не трогая работающие контейнеры:

```bash
podman secret rm my_secret --ignore
```

### 5. Секреты при сборке образов (podman build)

`podman build --secret` передает секрет в сборку, где он доступен только внутри инструкции `RUN --mount=type=secret` и не попадает в слои образа.

```bash
podman build --secret id=mysecret,src=./secret.txt -t my-app .
```

```dockerfile
FROM docker.io/library/alpine
RUN --mount=type=secret,id=mysecret cat /run/secrets/mysecret && \
    your-build-step
```

Значение секрета доступно в `/run/secrets/<id>` (переопределяется опциями `target`/`dst`). Секрет доступен только в той инструкции `RUN`, где указан `--mount`; изменение содержимого секрета не пересоздает слои, использующие его, без принудительного `--no-cache`.

### 6. Использование в Quadlet (systemd)

Quadlet позволяет декларативно описывать секреты для systemd-сервисов (поддержка ключа `Secret` появилась в Podman 4.7).

**Файл:** `~/.config/containers/systemd/db.container`

```ini
[Container]
Image=docker.io/library/postgres:16
Environment=POSTGRES_PASSWORD_FILE=/run/secrets/db_pass
# Подключение секрета как файла
Secret=db_pass
# Подключение с изменением пути
Secret=app_key,target=/app/certs/key.pem
# Подключение секрета как переменной окружения
Secret=api_token,type=env,target=API_TOKEN
```

## Дополнительная информация

### Нюансы и ограничения

- **Лимит размера**: максимальный размер одного секрета ограничен 512 КБ.
- **Rootless-специфика**: в rootless-режиме секреты одного пользователя невидимы для другого, так как хранятся в домашней директории пользователя (`$HOME/.local/share/containers/storage/secrets/`).
- **Права и не-root процессы**: по умолчанию файл монтируется с правами `0444` и владельцем `root`; для доступа непривилегированного процесса задавайте `uid`/`gid`/`mode` (поддерживается с Podman 3.2).
- **Удаление**: `podman secret rm` не удаляет секрет из уже запущенных контейнеров — значение копируется в контейнер при его создании; после `rm` контейнер продолжает работать со старым значением до пересоздания.
- **Смена значения**: `--replace` меняет значение для новых контейнеров, но не для существующих — для применения ротации необходимо пересоздание контейнера.
- **Маскирование**: значение env-секретов скрывается в `podman inspect` (начиная с Podman 5.2); в `podman secret inspect` значение по умолчанию скрыто и выводится только с `--showsecret`.
- **Драйвер `pass`**: `podman secret create --driver=pass ...` позволяет хранить секрет в GPG-зашифрованном виде (требуется настройка связки ключей GPG).
- **Реестры**: секреты можно использовать как пароли для `podman login` (вход в реестры), не записывая пароль в файлы конфигурации в открытом виде.

### Рекомендации по безопасности

1. **Минимальные права**: при необходимости ограничьте доступ по умолчанию, задав `mode` и `uid`/`gid` (например, `mode=0400`), чтобы секрет мог читать только основной процесс приложения. Помните, что значение не шифруется на хосте драйвером `file`.
2. **Очистка stdin**: при создании секретов используйте файлы, пайпы или `podman secret create --env`, чтобы значения не попадали в `~/.bash_history`.
3. **Паттерн `_FILE`**: многие официальные образы (Postgres, MariaDB) поддерживают переменные вида `DATABASE_PASSWORD_FILE`, указывающие на файл секрета в `/run/secrets/` — это идеально сочетается с `type=mount`.
4. **Ротация**: регулярно ротируйте секреты (`podman secret create --replace`), избегайте хранения секретов в слоях образа и в репозиториях исходного кода; секреты в CI/CD и при сборке передавайте только через `podman build --secret`.
