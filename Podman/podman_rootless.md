# Podman: Rootless режим

## Определения

**Rootless Containers** — контейнеры, весь жизненный цикл которых (от скачивания образа до запуска и удаления) управляется пользователем без прав `root`. Процесс внутри контейнера считает себя `root` (UID 0), но на хост-системе выполняется с правами обычного пользователя.

**User Namespace** — механизм ядра Linux, создающий виртуальную таблицу пользователей внутри контейнера, позволяя маппинг `root` контейнера на обычного пользователя хоста. Подробно: [Изоляция в Linux: Namespaces и Cgroups](../Docker/Concepts/linux_isolation.md).

## Базовые концепции

### Зачем нужен rootless-режим

| Проблема традиционных контейнеров | Решение Podman |
| :--- | :--- |
| Демон требует root | Нет демона, rootless по умолчанию |
| Побег из контейнера = root на хосте | Побег = права обычного пользователя |
| Сложная настройка rootless | Работает «из коробки» |
| Общая поверхность атаки | Изоляция на пользователя |

Архитектурные преимущества rootless-режима Podman объясняются в [Daemonless архитектуре](./podman_daemonless_architecture.md).

### Механизм работы

#### 1. User Namespaces — изоляция пользователей

Основной механизм, делающий rootless возможным. `User namespace` создаёт виртуальную таблицу пользователей и групп внутри контейнера:

- `root` (UID 0) внутри контейнера сопоставляется с реальным UID пользователя на хосте.
- Остальные UID внутри контейнера сопоставляются с диапазоном неиспользуемых UID на хосте.

#### 2. Маппинг идентификаторов: `/etc/subuid` и `/etc/subgid`

Для работы `user namespace` система должна знать, какой диапазон виртуальных UID/GID выделить пользователю:

- `/etc/subuid` — пулы UID для пользователей.
- `/etc/subgid` — пулы GID для пользователей.
- Пример записи: `myuser:100000:65536` — пользователю `myuser` выделен диапазон 65536 идентификаторов, начиная с 100000. UID 0 в контейнере мапится на реальный UID `myuser`, UID 1 → 100000, UID 2 → 100001 и т.д.

Вопросы маппинга UID/GID для файловых систем описаны в [Podman: Хранилище](./podman_volumes_and_storage.md#управление-правами-в-rootless-режиме-uidgid-mapping).

#### 3. Сетевое взаимодействие: slirp4netns, pasta, Netavark

Непривилегированный пользователь не может создавать сетевые интерфейсы или управлять `iptables` на хосте, поэтому Podman использует сетевые режимы в пространстве пользователя:

| Драйвер | Описание | Производительность | Когда использовать |
| :--- | :--- | :--- | :--- |
| **slirp4netns** | Виртуальный сетевой стек с NAT | Базовая | По умолчанию в Podman 3.x |
| **pasta** | Современная замена slirp4netns | На 30–50% быстрее | Podman 4+ (рекомендуется) |
| **Netavark** | Новый сетевой бэкенд Podman | Лучшая интеграция | Podman 4+ (по умолчанию, rootful) |

Изменения в Podman 4+:
- **Netavark** заменил CNI как сетевой бэкенд по умолчанию.
- **Aardvark-dns** заменил dnsmasq для DNS.
- **pasta** стала рекомендуемой заменой slirp4netns.

#### 4. Хранилище: fuse-overlayfs

Для управления слоями образов используется `fuse-overlayfs` — реализация `OverlayFS`, работающая в пространстве пользователя без прав `root`. Обычный `OverlayFS` требует привилегий для монтирования, поэтому в rootless-режиме применяется FUSE-вариант.

### Ограничения rootless-режима

| Ограничение | Причина | Решение |
| :--- | :--- | :--- |
| Порты < 1024 | Требуют привилегий `root` | Использовать порты > 1024 или reverse proxy (Nginx) |
| Производительность сети | NAT overhead в userspace | Использовать `pasta` (`--network=pasta`) |
| ICMP (`ping`) | Требует `CAP_NET_RAW` | `sysctl -w net.ipv4.ping_group_range="0 2147483647"` или `--cap-add=NET_RAW` |
| Прямой доступ к устройствам | Нет прав на `/dev/*` | Rootful режим или `--device` с осторожностью |

## Практические сценарии

### 1. Подготовка хоста

**Проверка `subuid`/`subgid`:**

```bash
# Проверить наличие записей
grep $USER /etc/subuid /etc/subgid

# Если записей нет, добавить (требуется root)
# sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 $USER
```

**Включение `linger` (опционально):**

Чтобы rootless-сервисы `systemd` запускались при загрузке системы, а не только при входе пользователя в сессию:

```bash
loginctl enable-linger $USER
```

### 2. Запуск контейнера и проброс портов

```bash
# Запуск Nginx и проброс порта 80 контейнера на порт 8080 хоста
podman run --rm -d --name web -p 8080:80 docker.io/library/nginx:alpine
```

Порт `8080` используется потому, что порты ниже 1024 (well-known ports) требуют привилегий `root`. В rootless-режиме доступны только порты > 1024. Для доступа через порт 80 настройте reverse proxy (Nginx) на хосте, перенаправляющий трафик с 80 на 8080.

### 3. Выбор сетевого драйвера

```bash
# Использовать pasta вместо slirp4netns (рекомендуется для производительности)
podman run --rm -d --network=pasta --name web -p 8080:80 nginx
```

### 4. Разрешение ping из контейнера

```bash
# Вариант 1: через sysctl на хосте
sysctl -w net.ipv4.ping_group_range="0 2147483647"

# Вариант 2: через capability контейнера
podman run --rm --cap-add=NET_RAW alpine ping -c 1 8.8.8.8
```

## Дополнительная информация

### Сравнение безопасности: rootless vs rootful

| Аспект | Rootless | Rootful |
| :--- | :--- | :--- |
| Права при побеге из контейнера | Обычный пользователь | Root на хосте |
| Доступ к устройствам | Ограничен | Полный |
| Сетевые возможности | Ограничены (NAT) | Полные |
| Порты < 1024 | Недоступны | Доступны |
| Производительность сети | Ниже (NAT overhead) | Нативная |
| Привилегированный режим (`--privileged`) | Недоступен | Доступен |
