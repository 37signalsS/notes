# Безрутовый (Rootless) режим в Podman

## Определения

**Безрутовый режим (Rootless mode)** — это архитектурная особенность Podman, позволяющая запускать контейнеры, управлять образами и настраивать сети от имени обычного непривилегированного пользователя. В этом режиме ни основной процесс Podman, ни процессы внутри контейнера не требуют прав `root` на хост-системе.

**User Namespace (Пространство имен пользователей)** — технология ядра Linux, которая мапирует (сопоставляет) идентификаторы пользователей внутри контейнера (например, UID 0 — root) на идентификаторы обычных пользователей на хосте. Это изолирует привилегии контейнера от привилегий хоста.

**subuid / subgid** — файлы конфигурации (`/etc/subuid`, `/etc/subgid`), определяющие диапазоны вспомогательных идентификаторов, которые пользователь может использовать для маппинга внутри своих контейнеров.

---

## Основные концепции

### Механизмы реализации

#### 1. Изоляция пользователей (User Namespaces)
В безрутовом режиме используется формула маппинга:
- **UID 0** в контейнере = **UID текущего пользователя** на хосте (например, 1000).
- **UID 1..65535** в контейнере = Диапазон из `/etc/subuid` (например, 100000..165535).

Это гарантирует, что если злоумышленник "вырвется" из контейнера, он получит права обычного пользователя, а не `root`.

#### 2. Сетевой стек: Pasta и Slirp4netns
Так как обычный пользователь не может создавать сетевые интерфейсы `veth`, Podman использует сетевые стеки в пространстве пользователя:
- **pasta** (по умолчанию в Podman 5.0+): Обеспечивает высокую производительность (близкую к нативной) и не требует трансляции адресов (NAT) для каждого пакета.
- **slirp4netns**: Классический драйвер, создающий виртуальный стек TCP/IP. Обладает более высокой задержкой и накладными расходами.

#### 3. Хранилище: fuse-overlayfs
Стандартный драйвер `overlay` в ядре Linux требует прав `root` для монтирования. В безрутовом режиме Podman использует **`fuse-overlayfs`**, который работает через FUSE (Filesystem in Userspace), позволяя обычному пользователю объединять слои образов.

### Управление через сокет и окружение

В безрутовом режиме сокет Podman (для работы с API или Docker-совместимыми инструментами) располагается в директории пользователя:
- **Путь:** `/run/user/$(id -u)/podman/podman.sock`
- **Переменная окружения:** `XDG_RUNTIME_DIR`. Если она не установлена, Podman не сможет создать сокет или найти временные файлы.

## Практические сценарии

### 1. Подготовка системы (ID Mapping)

Для работы безрутового режима пользователю должны быть выделены диапазоны ID.

```bash
# Проверка выделенных диапазонов
grep $USER /etc/subuid
# → user:100000:65536

# Если диапазоны отсутствуют, их можно добавить (от root)
# sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 $USER
```

### 2. Устранение проблем с правами доступа (podman unshare)

Если вы монтируете директорию хоста в контейнер и получаете `Permission Denied`, это часто связано с тем, что UID внутри контейнера не совпадает с владельцем на хосте.

```bash
# Вход в пространство имен пользователя для ручной настройки прав
podman unshare chown -R 1000:1000 ./data

# Проверка того, как система видит файлы внутри namespace
podman unshare ls -l ./data
```

### 3. Настройка Linger для автозапуска

По умолчанию пользовательские процессы (включая контейнеры и systemd-юниты) убиваются при выходе пользователя из системы. Чтобы они работали постоянно:

```bash
# Включить "задержку" (linger) для пользователя
sudo loginctl enable-linger $USER
```

### 4. Проброс привилегированных портов

Обычный пользователь не может занимать порты ниже 1024. Чтобы разрешить запуск, например, веб-сервера на порту 80:

```bash
# Вариант 1: Использовать порты выше 1024 (рекомендуется)
podman run -p 8080:80 nginx

# Вариант 2: Изменить настройки ядра (sysctl) на хосте
# sudo sysctl net.ipv4.ip_unprivileged_port_start=80
```

## Нюансы и ограничения

| Особенность | Описание |
| :--- | :--- |
| **Пути к данным** | Образы хранятся в `~/.local/share/containers/storage` вместо `/var/lib/containers`. |
| **Производительность** | `fuse-overlayfs` и `slirp4netns` вносят небольшие задержки по сравнению с root-режимом. Использование `pasta` нивелирует разницу в сети. |
| **Доступ к устройствам** | Прямой доступ к `/dev` ограничен. Может потребоваться ручное изменение прав на файлы устройств на хосте. |
| **Квоты ресурсов** | Ограничение ресурсов (CPU/RAM) требует настройки делегирования в Cgroups v2 для пользователя. |
