# Podman: Rootless режим

## Определения

**Rootless Containers** — контейнеры, весь жизненный цикл которых (от скачивания образа до запуска и удаления) управляется пользователем без прав `root`. Процесс внутри контейнера считает себя `root` (UID 0), но на хост-системе он выполняется с правами обычного пользователя.

**User Namespace** — механизм ядра Linux, который создает виртуальную таблицу пользователей внутри контейнера, позволяя маппинг `root` контейнера на обычного пользователя хоста.

## Основные концепции

### Почему rootless важен

| Проблема традиционных контейнеров | Решение Podman |
| :--- | :--- |
| Демон требует root | Нет демона, rootless по умолчанию |
| Побег из контейнера = root на хосте | Побег = права обычного пользователя |
| Сложная настройка rootless | Работает "из коробки" |
| Общая поверхность атаки | Изоляция на пользователя |

### Как это работает

#### 1. Изоляция пользователей: User Namespaces

Это основной механизм, делающий rootless возможным. `User namespace` позволяет создать "виртуальную" таблицу пользователей и групп внутри контейнера.

- `root` (UID 0) внутри контейнера сопоставляется с реальным UID вашего пользователя на хосте.
- Другие UID внутри контейнера сопоставляются с диапазоном неиспользуемых UID на хосте.

> Подробнее об этом механизме ядра: **[Изоляция в Linux: Namespaces и Cgroups](../Docker/Concepts/linux_isolation.md)**.

### 2. Маппинг идентификаторов: `/etc/subuid` и `/etc/subgid`

Чтобы `user namespace` работал, система должна знать, какой диапазон "виртуальных" UID/GID можно выделить конкретному пользователю.

- `/etc/subuid`: Определяет пулы UID для пользователей.
- `/etc/subgid`: Определяет пулы GID для пользователей.
- Пример записи: `myuser:100000:65536`. Это означает, что пользователю `myuser` выделен диапазон из 65536 идентификаторов, начиная с 100000. UID 0 в контейнере будет смаплен на реальный UID `myuser`, а UID 1 — на 100000, UID 2 — на 100001 и так далее.

### 3. Сетевое взаимодействие: slirp4netns, pasta и Netavark

Поскольку непривилегированный пользователь не может создавать сетевые интерфейсы или управлять `iptables` на хосте, Podman использует сетевые режимы, работающие в пространстве пользователя (`userspace`).

**Сетевые драйверы для rootless-режима:**

| Драйвер | Описание | Производительность | Когда использовать |
| :--- | :--- | :--- | :--- |
| **slirp4netns** | Виртуальный сетевой стек с NAT | Базовая | По умолчанию в Podman 3.x |
| **pasta** | Современная замена slirp4netns | На 30-50% быстрее | Podman 4+ (рекомендуется) |
| **Netavark** | Новый сетевой бэкенд Podman | Лучшая интеграция | Podman 4+ (по умолчанию) |

**Что изменилось в Podman 4+:**

- **Netavark** заменил CNI как сетевой бэкенд по умолчанию
- **Aardvark-dns** заменил dnsmasq для DNS
- **pasta** стала рекомендуемой заменой slirp4netns

### 4. Хранилище: fuse-overlayfs

Для управления слоями образов используется `fuse-overlayfs` — реализация `OverlayFS`, которая может работать в пространстве пользователя без прав `root`.

## Практические сценарии

### 1. Подготовка хоста

1. **Проверьте `subuid`/`subgid`**: Убедитесь, что для вашего пользователя созданы записи.

    ```bash
    # Проверить наличие записей
    grep $USER /etc/subuid /etc/subgid
    
    # Если их нет, добавьте (требуется root)
    # sudo usermod --add-subuids 100000-165535 --add-subgids 100000-165535 $USER
    ```

2. **Включите `linger` (опционально)**: Чтобы rootless-сервисы `systemd` запускались при загрузке системы, а не только при входе пользователя в сессию.

    ```bash
    loginctl enable-linger $USER
    ```

### 2. Запуск контейнера и проброс портов

```bash
# Запускаем Nginx и пробрасываем порт 80 контейнера на порт 8080 хоста
podman run --rm -d --name web -p 8080:80 docker.io/library/nginx:alpine
```

- **Почему порт `8080`?** Потому что порты ниже 1024 (well-known ports) требуют привилегий `root`. В rootless-режиме можно использовать только порты > 1024.

### 3. Ограничения и пути их обхода

- **Порты < 1024**: Недоступны для прямого биндинга.
  - **Решение**: Используйте порты > 1024 или настройте на хосте `reverse proxy` (например, Nginx), который будет перенаправлять трафик с порта 80 на ваш `8080`.
- **Производительность сети**: `slirp4netns` работает медленнее, чем нативные сетевые драйверы в `rootful` режиме.
  - **Решение**: Используйте `pasta` (`podman run --network=pasta`) для лучшей производительности или, если это допустимо, `rootful` режим.
- **ICMP (`ping`)**: По умолчанию `ping` из контейнера не работает, так как требует специальных прав.
  - **Решение**: Можно разрешить `ping` через `sysctl`, но чаще всего это не является проблемой для веб-приложений.

## Дополнительная информация

### Безопасность rootless-контейнеров

| Аспект | Rootless | Rootful |
| :--- | :--- | :--- |
| **Права при побеге** | Обычный пользователь | Root на хосте |
| **Доступ к устройствам** | Ограничен | Полный |
| **Сетевые возможности** | Ограничены (NAT) | Полные |
| **Порты < 1024** | Недоступны | Доступны |
| **Производительность сети** | Ниже (NAT overhead) | Нативная |

### Дополнительные ограничения и решения

| Ограничение | Решение |
| :--- | :--- |
| Порты < 1024 | Reverse proxy (Nginx) или firewall-cmd --add-forward-port |
| Производительность сети | Использовать `pasta` вместо `slirp4netns` |
| ICMP (ping) | `sysctl -w net.ipv4.ping_group_range="0 2147483647"` |
| Прямой доступ к устройствам | Rootful режим или `--device` с осторожностью |
