# Подман: Безрутовый (Rootless) режим

## Определения

**Rootless Containers** — контейнеры, весь жизненный цикл которых (от скачивания образа до запуска и удаления) управляется пользователем без прав `root`. Процесс внутри контейнера считает себя `root` (UID 0), но на хост-системе выполняется с правами обычного пользователя.

**User Namespace (Пространство имен пользователей)** — механизм ядра Linux, создающий виртуальную таблицу пользователей внутри контейнера, позволяя маппинг `root` контейнера на обычного пользователя хоста. Подробно: [Изоляция в Linux: Namespaces и Cgroups](../Docker/Concepts/linux_isolation.md).

**UID (User ID)** — уникальный идентификатор пользователя в Linux.

**GID (Group ID)** — уникальный идентификатор группы в Linux.

## Основные концепции

### Преимущества безрутового режима

| Проблема традиционных контейнеров | Решение Podman |
| :--- | :--- |
| Демон требует root | Нет демона, rootless по умолчанию |
| Побег из контейнера = root на хосте | Побег = права обычного пользователя |
| Сложная настройка rootless | Работает «из-под коробки» |
| Общая поверхность атаки | Изоляция на уровне пользователя |

Архитектурные преимущества объясняются в разделе **[Daemonless архитектура](./podman_daemonless_architecture.md)**.

### Механизмы реализации

#### 1. Пространства имен пользователей (User Namespaces)

Основной механизм, делающий rootless возможным. Он создаёт виртуальную таблицу пользователей и групп внутри контейнера:

- **UID 0 (root)** внутри контейнера сопоставляется с реальным UID текущего пользователя на хосте (например, 1000).
- Остальные идентификаторы внутри контейнера сопоставляются с диапазоном неиспользуемых UID на хосте из файла `/etc/subuid`.

#### 2. Маппинг идентификаторов: /etc/subuid и /etc/subgid

Для работы системы необходимо знать, какой диапазон виртуальных UID/GID выделить пользователю:

- **/etc/subuid** — пулы идентификаторов пользователей.
- **/etc/subgid** — пулы идентификаторов групп.
- **Пример записи:** `myuser:100000:65536`. Пользователю `myuser` выделен диапазон из 65536 идентификаторов, начиная со 100000. UID 0 в контейнере мапится на реальный UID пользователя, UID 1 → 100000, UID 2 → 100001 и т. д.

**Проверка маппинга (от имени пользователя):**

```bash
podman unshare cat /proc/self/uid_map
# → 0       1000          1  (UID 0 в контейнере -> UID 1000 на хосте)
# → 1     100000      65536  (UID 1 в контейнере -> UID 100000 на хосте)
```

Вопросы маппинга для файловых систем описаны в разделе **[Podman: Хранилище](./podman_volumes_and_storage.md#управление-правами-в-rootless-режиме-uidgid-mapping)**.

#### 3. Сетевой стек: slirp4netns, pasta, Netavark

Непривилегированный пользователь не может создавать сетевые интерфейсы или управлять правилами фильтрации трафика на хосте. Podman использует сетевые стеки в пространстве пользователя:

| Драйвер | Описание | Производительность | Примечание |
| :--- | :--- | :--- | :--- |
| **slirp4netns** | Виртуальный стек с **NAT (Network Address Translation)** | Базовая | Устаревающий стандарт |
| **pasta** | Современная замена slirp4netns | Высокая (на 30–50% быстрее) | Рекомендовано для Podman 4+ |
| **Netavark** | Новый сетевой бэкенд на Rust | Лучшая | По умолчанию для rootful |

#### 4. Файловая система: fuse-overlayfs

Для управления слоями образов используется **fuse-overlayfs** — реализация OverlayFS, работающая через **FUSE (Filesystem in Userspace)** без прав root. Это необходимо, так как стандартный механизм OverlayFS в ядре требует привилегий для монтирования.

### Ограничения безрутового режима

| Ограничение | Причина | Решение |
| :--- | :--- | :--- |
| Порты < 1024 | Требуют привилегий суперпользователя | Использовать порты > 1024 или reverse proxy |
| Производительность сети | Накладные расходы NAT в userspace | Использовать драйвер `pasta` |
| ICMP (Internet Control Message Protocol) | Требует **CAP_NET_RAW** | Настройка `ping_group_range` в sysctl |
| Доступ к устройствам | Ограничен правами на `/dev/*` | Использование флага `--device` |

## Практические сценарии

### 1. Подготовка хост-системы

**Проверка конфигурации идентификаторов:**

```bash
# Проверить наличие записей для текущего пользователя
grep $USER /etc/subuid /etc/subgid
# → q:100000:65536
# → q:100000:65536
```

**Включение Linger (постоянная работа):**

Чтобы rootless-сервисы systemd запускались при загрузке системы, а не только при входе пользователя:

```bash
loginctl enable-linger $USER
```

### 2. Запуск контейнера с пробросом портов

```bash
# Запуск Nginx на порту 8080 (вместо 80)
podman run --rm -d --name web -p 8080:80 docker.io/library/nginx:alpine
# → a1b2c3d4e5f6... (ID контейнера)

# Проверка доступности
curl -I http://localhost:8080
# → HTTP/1.1 200 OK
```

### 3. Настройка сетевого драйвера pasta

```bash
# Использование pasta для повышения производительности
podman run --rm -d --network=pasta --name fast-web -p 8081:80 nginx
# → b2c3d4e5f6g7...
```

### 4. Разрешение ICMP (ping) внутри контейнера

```bash
# Вариант: настройка на уровне ядра хоста
sudo sysctl -w net.ipv4.ping_group_range="0 2147483647"
# → net.ipv4.ping_group_range = 0 2147483647

# Проверка в контейнере
podman run --rm alpine ping -c 1 8.8.8.8
# → PING 8.8.8.8 (8.8.8.8): 56 data bytes
# → 64 bytes from 8.8.8.8: seq=0 ttl=116 time=15.241 ms
```

## Дополнительная информация

### Сравнение режимов безопасности

| Аспект | Rootless | Rootful |
| :--- | :--- | :--- |
| Права при «побеге» | Права обычного пользователя | Root на хосте (полный доступ) |
| Доступ к устройствам | Ограничен | Полный |
| Порты < 1024 | Недоступны напрямую | Доступны |
| Производительность | Небольшие задержки (NAT) | Нативная скорость |
