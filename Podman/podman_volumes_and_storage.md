# Podman: Хранилище и работа с файловой системой

## Определения

**Файловая система контейнера** — комбинация слоёв образа (read-only, через OverlayFS) и записываемого слоя контейнера (writable layer). Для персистентного хранения данных используются внешние монтирования.

Общие концепции томов, bind mounts и tmpfs описаны в основном руководстве: [Тома и персистентное хранение данных](../Docker/Docker_fs/docker_volumes.md). Данный документ фокусируется на **Podman-специфичных особенностях**.

### Bind Mount

Прямое монтирование каталога или файла с хостовой машины в контейнер.

```bash
# Монтирует текущий каталог ./data в /app/data внутри контейнера
podman run -it -v $(pwd)/data:/app/data alpine sh
```

### Named Volume

Хранилище, которым управляет Podman. Не привязано к конкретному пути на хосте явно.

```bash
# Создать именованный том
podman volume create mydata

# Подключить к контейнеру
podman run -it -v mydata:/app/data alpine sh
```

### tmpfs Mount

Временное хранилище в оперативной памяти.

```bash
podman run -it --tmpfs /tmp:rw,size=100M alpine sh
```

## Основные концепции

### Расположение хранилища

Расположение данных Podman зависит от режима запуска:

| Режим | Графы/образы | Тома (volumes) |
| :--- | :--- | :--- |
| **Rootless** | `~/.local/share/containers/storage` | `~/.local/share/containers/storage/volumes/` |
| **Root (sudo)** | `/var/lib/containers/storage` | `/var/lib/containers/storage/volumes/` |

> **Важно:** Не рекомендуется вручную изменять содержимое этих каталогов. Они управляются storage-драйвером (обычно `overlay`) и содержат слои образов, метаданные и lock-файлы. Для управления используйте команды `podman volume`.

### Управление томами через CLI

```bash
# Создать том
podman volume create mydata

# Список томов
podman volume ls

# Детальная информация
podman volume inspect mydata

# Удалить том (не должен использоваться контейнером)
podman volume rm mydata

# Удалить все неиспользуемые тома
podman volume prune

# Посмотреть использование дискового пространства
podman system df -v
```

### Анализ Named Volume

Команда `podman volume inspect mydata` возвращает детальную информацию:

```json
{
  "Name": "mydata",
  "Driver": "local",
  "Mountpoint": "/home/user/.local/share/containers/storage/volumes/mydata/_data",
  "CreatedAt": "...",
  "Labels": {},
  "Scope": "local",
  "Options": {},
  "MountCount": 0,
  "NeedsCopyUp": true,
  "NeedsChown": true,
  "LockNumber": 6
}
```

Ключевые Podman-специфичные параметры:

| Параметр | Описание |
| :--- | :--- |
| `MountCount` | Счётчик контейнеров, использующих том |
| `NeedsCopyUp` | Если `true`, содержимое из образа копируется в том при первом монтировании |
| `NeedsChown` | Если `true`, Podman меняет владельца файлов под UID rootless-контейнера |
| `Scope` | `local` — том находится на локальном хосте |
| `LockNumber` | Внутренний lock для предотвращения гонок при одновременном доступе |

## Практические сценарии

### Работа с SELinux

На системах с включенным SELinux (Fedora, RHEL, CentOS) простое монтирование bind mount может привести к ошибке `Permission denied`, даже если права доступа корректны.

**Проблема:** SELinux по умолчанию запрещает контейнерам доступ к произвольным каталогам на хосте. Контекст SELinux у каталога (например, `user_home_t`) не позволяет контейнеру (`container_t`) выполнять запись.

**Решение:** Использовать флаги `:z` или `:Z` при монтировании.

```bash
# :Z - Приватный доступ. Метка SELinux меняется, и только этот контейнер может получить доступ.
podman run --rm -it -v ~/selinux-test:/data:Z alpine sh

# :z - Общий доступ (Shared). Метка SELinux меняется, и несколько контейнеров могут получить доступ.
podman run --rm -it -v ~/selinux-test:/data:z alpine sh
```

Эти флаги заставляют Podman выполнить "relabel" — изменить тип контекста на `container_file_t`, разрешая доступ.

### Управление правами в Rootless-режиме (UID/GID Mapping)

**Проблема:** В rootless-режиме UID пользователя внутри контейнера (например, `root` с UID `0`) не соответствует UID пользователя на хосте. Он "маппится" в диапазон неиспользуемых UID. Механизм маппинга описан в [Rootless режиме](./podman_rootless.md#2-маппинг-идентификаторов-etcsubuid-и-etcsubgid). Если файл на хосте принадлежит `UID 1000`, а процесс в контейнере работает от имени `UID 10000`, возникнет ошибка `Permission denied`.

**Решение:** Использовать флаг `:U` (`chown`).

```bash
# :U заставляет Podman рекурсивно изменить владельца файлов на хосте
# под нужный UID/GID контейнера.
podman run --rm -v $(pwd)/demo:/data:U alpine sh -c "echo test >> /data/file.txt"
```

> **Примечание:** Флаги `:Z` и `:U` могут конфликтовать. Если требуется и то, и другое, рекомендуется сначала вручную изменить контекст SELinux на хосте:
> `chcon -R -t container_file_t /path/to/your/volume`

### Использование временного оверлея (Overlay Mount)

**Задача:** Разрешить контейнеру писать данные "поверх" bind mount, не изменяя исходные файлы на хосте. Все изменения должны исчезнуть после удаления контейнера.

**Решение:** Использовать флаг `:O`.

```bash
podman run --rm -it -v $(pwd)/data:/data:O alpine sh
```

**Как это работает:** Podman создает временный overlayfs. Исходный каталог (`lowerdir`) остается неизменным, а все операции записи попадают во временный слой (`upperdir`), который уничтожается вместе с контейнером. Ключ `:O` не меняет SELinux-контекст и не делает `chown`.

Проверка активности оверлея внутри контейнера:

```bash
mount | grep /data
# Должно быть: /data type overlay (rw, ...)
```

## Дополнительная информация

### Изоляция контейнеров через SELinux и MCS

При старте контейнера с SELinux ему присваивается уникальная метка MCS (Multi-Category Security).

`system_u:system_r:container_t:s0:c123,c456`

- `c123,c456` — это MCS-категории.
- Даже если у двух контейнеров общий тип `container_t`, SELinux не позволит им взаимодействовать друг с другом, если их MCS-категории не совпадают. Это обеспечивает строгую изоляцию между контейнерами на уровне ядра.
- Флаг `:z` создает общую метку, позволяя контейнерам с этой меткой взаимодействовать с volume. Флаг `:Z` создает уникальную метку для каждого контейнера.

> Подробнее о MCS: **[SELinux MCS](../Linux/Security/Mechanisms/SELinux.md)**.

### Сводная таблица флагов монтирования

| Флаг | Назначение | Когда использовать |
| :--- | :--- | :--- |
| `:z` | Relabel для общего доступа (несколько контейнеров) | Общие данные между контейнерами |
| `:Z` | Relabel для приватного доступа (один контейнер) | Приватные данные контейнера |
| `:U` | Автоматический chown под UID rootless-контейнера | Rootless-режим с bind mount |
| `:O` | Временный overlay (запись не влияет на хост) | Безопасное чтение с хоста без записи |
| `:ro` | Только чтение | Конфиги, которые не должны изменяться |

### Диагностика проблем

| Проблема | Причина | Решение |
| :--- | :--- | :--- |
| `Permission denied` при bind mount | SELinux блокирует доступ | Добавить флаг `:z` или `:Z` |
| `Permission denied` в rootless | Конфликт UID/GID | Добавить флаг `:U` |
| Конфликт `:Z` и `:U` | Оба меняют файлы на хосте | Вручную: `chcon -R -t container_file_t /path` |
| Том не удаляется | Используется контейнером | Остановить контейнер или `podman volume prune -f` |
| Данные не сохраняются | Запись в writable layer, не в volume | Использовать `-v` или `--mount` для персистентности |
