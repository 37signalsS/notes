# Grafana: Оповещения (Alerting)

## Определения

- **Правило оповещения (Alert Rule)**: Набор условий, применяемых к данным на панели дашборда. При выполнении условий генерируется оповещение.
- **Условие (Condition)**: Логическое выражение, которое оценивает метрику (например, `среднее значение > 80`). Является триггером для оповещения.
- **Канал уведомлений (Notification Channel)**: Настроенный получатель оповещений (например, Slack, Email, Webhook).
- **Состояния оповещений**:
  - **OK**: Условия не выполняются, система в норме.
  - **PENDING**: Условие выполнено, идет период ожидания перед переходом в `ALERTING`.
  - **ALERTING**: Оповещение активно, отправляются уведомления.

## Основные концепции

### Жизненный цикл оповещения

1. **Оценка**: Grafana периодически выполняет запросы, указанные в правиле оповещения.
2. **Срабатывание**: Если результат запроса соответствует условию, правило переходит в состояние `PENDING`, а затем в `ALERTING`.
3. **Уведомление**: Grafana отправляет детальную информацию о сработавшем правиле в один или несколько каналов уведомлений.

### Каналы уведомлений

- **Мессенджеры**: Slack, Telegram, Microsoft Teams.
- **Email**.
- **Системы управления инцидентами**: PagerDuty, Opsgenie.
- **Общие веб-хуки (Webhooks)**: Для интеграции с любыми другими системами.

### Визуализация в оповещениях (Image Renderer)

Ключевая особенность Grafana — возможность прикреплять к уведомлениям снимки графиков.

- **Компонент**: За эту функцию отвечает **Image Renderer**, который должен быть установлен и настроен. См. [[./Installation/grafana_helm_installation.md|установку Grafana через Helm]].
- **Преимущество**: Снимок показывает тренд и контекст метрики в момент срабатывания алерта, что значительно ускоряет анализ проблемы.
- **Особенности**: Для некоторых каналов (например, Slack) может потребоваться внешнее хранилище (S3) для изображений.

## Практические сценарии

### Сценарий 1: Настройка базового оповещения

1. **Создать канал уведомлений**:
    - Перейдите в **Alerting -> Notification channels -> Add channel**.
    - Выберите тип (например, Slack), укажите название и учетные данные (URL веб-хука).
    - Настройте опции: отправка изображений, напоминаний и сообщений о восстановлении.

2. **Создать правило оповещения**:
    - На панели дашборда перейдите на вкладку **Alert -> Create Alert**.
    - Задайте имя правила и частоту оценки.
    - Настройте условие (например, `WHEN avg() OF query(A, 5m, now) IS ABOVE 80`).
    - В разделе **Notifications** выберите созданный канал.

### Сценарий 2: Оповещения для многомерных данных (без переменных)

Алерты в Grafana **не поддерживают переменные** дашбордов. Чтобы настроить оповещение для метрики, которая имеет несколько измерений (например, `node_cpu_usage` для разных `hostname`), используйте следующий подход:

1. **Создайте отдельную панель для алертинга** (или целый дашборд) без использования переменных.
2. **Используйте обобщенный запрос**: В запросе не указывайте конкретное значение лейбла (например, `node_cpu_usage`, а не `node_cpu_usage{instance="$instance"}`). Grafana оценит правило для каждого временного ряда.
3. **Используйте лейблы в легенде**: Настройте легенду графика, чтобы она включала нужные идентификаторы (например, `{{instance}}` или `{{nodename}}`).
4. **Результат**: При срабатывании алерта Grafana укажет в уведомлении лейблы того ряда, который вызвал проблему, предоставляя полный контекст.

### Сценарий 3: Интеграция с системами эскалации

Для управления инцидентами Grafana интегрируется с **PagerDuty** или **Opsgenie**.

- **Разделение ответственности**: Grafana обнаруживает проблему и отправляет событие. Внешняя система управляет жизненным циклом инцидента: эскалацией, графиками дежурств, группировкой.
- **Пример эскалации**: Если дежурный инженер не реагирует на алерт в течение 5 минут, система автоматически передает его руководителю.

## Дополнительная информация

### Сравнение с Alertmanager и стратегия использования

| Критерий | Grafana Alerting | Prometheus Alertmanager |
| :--- | :--- | :--- |
| **Настройка** | **Визуальная**, на графиках. Интуитивно понятна для разработчиков. | **Конфигурация через YAML.** Требует знания синтаксиса, но обеспечивает гибкость. |
| **Сложность правил** | **Базовая.** Идеально для простых пороговых значений (`> 80%`). | **Продвинутая.** Поддерживает сложную логику, агрегацию, корреляцию и зависимости. |
| **Информативность** | **Высокая.** Прикрепляет **снимок графика**, показывая тренд и контекст. | **Низкая.** Отправляет "сухое" **текстовое сообщение** с лейблами и значениями. |
| **Обработка алертов** | **Ограниченная.** Базовая группировка. | **Мощная.** Дедупликация, группировка, "тишина" (silencing) и подавление (inhibition) алертов. |
| **Зависимости** | **Не понимает.** Сбой базового компонента может вызвать "лавину" алертов. | **Частично управляет** через inhibition rules, подавляя зависимые алерты. |
| **Поддержка переменных**| **Отсутствует.** | Неприменимо (работает с лейблами). |

### Рекомендуемая стратегия

1. **Использовать Grafana (≈70% случаев)**:
    - Для простых пороговых алертов (CPU, память, диск).
    - Когда важен визуальный контекст для быстрой оценки проблемы.
    - Для команд, которым нужен простой и наглядный инструмент.

2. **Использовать Alertmanager (≈30% случаев)**:
    - Для критически важных, сложных бизнес-алертов.
    - Когда требуется сложная логика маршрутизации, группировки или эскалации.
    - Для управления "лавиной" алертов при сбое ключевых компонентов инфраструктуры.

Эти системы **дополняют друг друга**: Alertmanager сообщает, *что* "все плохо", а Grafana присылает снимок, *как именно* "все плохо", что ускоряет решение проблемы.
