# Grafana: Оповещения (Unified Alerting)

## Определения

Алертинг в Grafana (Unified Alerting) — это централизованная система, которая отделена от дашбордов и работает поверх различных источников данных.

- **Правило (Alert rule)**: Набор запросов и выражений, условие с порогом, интервал оценки, длительность стабилизации (`for`), поведение при отсутствии данных (`NoData`) или ошибке (`Error`), а также набор меток (`labels`) и аннотаций (`annotations`).
- **Группа правил (Rule group)**: Логическое объединение правил с единым интервалом оценки, что помогает снизить "дрожание" и управлять связанными алертами как единым целым.
- **Контакт-пойнт (Contact point)**: Канал для отправки уведомлений (Email, Slack, Webhook, PagerDuty и т.д.). Настраивается один раз и переиспользуется в политиках.
- **Политика уведомлений (Notification policy)**: Дерево правил для маршрутизации оповещений на основе их меток. Определяет группировку (`group_by`), задержки (`group_wait`), интервалы повторов (`repeat_interval`).
- **Глушения (Silences) и Окна тишины (Mute timings)**: Механизмы для временного подавления уведомлений по селекторам меток или расписанию (например, на время плановых работ).
- **Шаблоны (Templates)**: Go-шаблоны для форматирования сообщений в уведомлениях с использованием переменных алерта.

### Состояния правил

- **Normal / OK**: Условие не выполняется, система в норме.
- **Pending**: Условие выполняется, но меньше, чем задано в параметре `for`.
- **Alerting**: Условие стабильно выполняется дольше времени `for`, отправляются уведомления.
- **NoData**: Запросы к источнику данных не вернули данных. Поведение настраивается (может быть `Alerting`, `NoData` или `OK`).
- **Error**: Ошибка при оценке правила. Поведение также настраивается.

## Основные концепции

### Жизненный цикл оповещения

1. **Оценка**: По расписанию Grafana выполняет запросы и выражения, определенные в правиле.
2. **Формирование событий**: Для многомерных метрик условие применяется к каждой серии отдельно, формируя множество алертов, различающихся метками.
3. **Маршрутизация**: События маршрутизируются к контакт-пойнтам с учётом политик, глушений и окон группировки.
4. **Группировка**: Результаты правил с одинаковыми метками (согласно `group_by` в политике) агрегируются для уменьшения "шумовых" уведомлений.
5. **Доставка**: Уведомления доставляются по маршрутам, соответствующим меткам события.

### Визуализация в оповещениях (Image Renderer)

Ключевая особенность Grafana — возможность прикреплять к уведомлениям снимки графиков.

- **Компонент**: За эту функцию отвечает **Image Renderer**, который должен быть установлен и настроен. См. [установку Grafana через Helm](./Installation/grafana_helm_installation.md).
- **Преимущество**: Снимок показывает тренд и контекст метрики в момент срабатывания алерта, что значительно ускоряет анализ проблемы.

## Практические сценарии

### Сценарий 1: Настройка оповещений через Provisioning

Это основной подход для реализации Infrastructure as Code.

#### Пример правила

```yaml
# provisioning/alerting/api-alerts.yaml
apiVersion: 1
groups:
  - orgId: 1
    name: api-alerts
    folder: Production
    interval: 1m
    rules:
      - uid: api_error_rate_high
        title: API error rate > 5%
        condition: B # Условие, которое триггерит алерт
        for: 5m
        noDataState: NoData
        execErrState: Error
        labels:
          service: api
          severity: critical
        annotations:
          summary: Высокая доля ошибок API
          runbook: Проверьте логи и зависимые сервисы
        data:
          - refId: A # Запрос PromQL
            datasourceUid: prometheus_ds_uid
            model:
              expr: 'sum(rate(http_requests_total{job="api",status=~"5.."}[5m])) / sum(rate(http_requests_total{job="api"}[5m])) * 100'
              instant: false
              format: time_series
          - refId: B # Выражение Threshold
            datasourceUid: __expr__
            model:
              type: threshold
              conditions:
                - evaluator: { type: gt, params: [5] }
                  query: { params: [A] }
```

#### Пример контакт-пойнтов и политик

```yaml
# provisioning/alerting/contact-points.yaml
apiVersion: 1

contactPoints:
  - orgId: 1
    name: team-devops-email
    receivers:
      - uid: team-devops-email-receiver
        type: email
        settings:
          addresses: devops@example.com

policies:
  - orgId: 1
    receiver: team-devops-email
    group_by: ["alertname", "service"]
    group_wait: 30s
    group_interval: 5m
    repeat_interval: 4h
    routes:
      - receiver: team-devops-email
        object_matchers:
          - ["severity", "=", "critical"]
```

### Сценарий 2: Интеграция с системами эскалации

Для управления инцидентами Grafana интегрируется с **PagerDuty** или **Opsgenie**.

- **Разделение ответственности**: Grafana обнаруживает проблему и отправляет событие. Внешняя система управляет жизненным циклом инцидента: эскалацией, графиками дежурств, группировкой.
- **Пример эскалации**: Если дежурный инженер не реагирует на алерт в течение 5 минут, система автоматически передает его руководителю.

## Дополнительная информация

### Практические нюансы

- Соотносите `for` с интервалом оценки: `for` не должен быть меньше 2–3 интервалов.
- Различайте `NoData` и `Error`: для метрик с редкими событиями полезно `NoData=OK`, а для критичных — `NoData=Alerting`.
- Применяйте метки для маршрутизации и дедупликации; аннотации используйте для контекста (симптом, предположение, следующий шаг).
- Для "шумных" метрик вводите пост-агрегации (`reduce`/`avg_over_time`) и окна группировки в политике.

### Сравнение с Alertmanager и стратегия использования

| Критерий | Grafana Alerting | Prometheus Alertmanager |
| :--- | :--- | :--- |
| **Настройка** | **Визуальная** или через YAML-файлы. Интуитивно понятна. | **Конфигурация через YAML.** Требует знания синтаксиса, но обеспечивает гибкость. |
| **Сложность правил** | **Средняя.** Поддерживает многомерные алерты, выражения. | **Продвинутая.** Поддерживает сложную логику, агрегацию, корреляцию и зависимости. |
| **Информативность** | **Высокая.** Прикрепляет **снимок графика**, показывая тренд и контекст. | **Низкая.** Отправляет "сухое" **текстовое сообщение** с лейблами и значениями. |
| **Обработка алертов** | **Продвинутая.** Группировка, глушение (`silencing`), политики маршрутизации. | **Мощная.** Дедупликация, группировка, глушение и подавление (`inhibition`) алертов. |
| **Зависимости** | **Не понимает.** Сбой базового компонента может вызвать "лавину" алертов. | **Частично управляет** через `inhibition rules`, подавляя зависимые алерты. |

### Рекомендуемая стратегия

1. **Использовать Grafana (≈80% случаев)**:
    - Для большинства пороговых алертов (CPU, память, диск, ошибки).
    - Когда важен визуальный контекст для быстрой оценки проблемы.
    - Для команд, которым нужен единый инструмент для визуализации и алертинга.

2. **Использовать Alertmanager (≈20% случаев)**:
    - Для критически важных, сложных бизнес-алертов.
    - Когда требуется сложная логика подавления зависимых алертов (`inhibition`).
    - Для управления "лавиной" алертов при сбое ключевых компонентов инфраструктуры.

Эти системы **дополняют друг друга**: Alertmanager сообщает, *что* "все плохо", а Grafana присылает снимок, *как именно* "все плохо", что ускоряет решение проблемы.
