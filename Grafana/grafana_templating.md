# Grafana: Шаблонизация

**Актуально для:** Grafana 13.2.x / 12.x (LTS)

## Определения

**Шаблонизация (Templating)** — механизм создания динамических дашбордов через переменные. Значения переменных подставляются в запросы к источникам данных, заголовки панелей, аннотации и ссылки, позволяя одному дашборду отображать данные для различных ресурсов (серверов, приложений, кластеров) без дублирования панелей.

**Цепочка зависимых переменных (Chaining)** — связывание переменных так, что значение одной вычисляется на основе выбранного значения другой (например, выбор `Datacenter` зависит от выбранного `Region`). Grafana обновляет зависимые переменные в порядке их объявления в списке `templating`.

**Multi-value** — опция переменной, разрешающая выбрать несколько значений одновременно. Результат подстановки — набор значений, который нужно использовать с оператором `=~` (regex-совпадение) или форматированием `:csv`/`:pipe`, иначе запрос вернёт ошибку.

**Include All option** — опция, добавляющая в выпадающий список пункт `All`. При выборе `All` по умолчанию подставляются все значения переменной (через `|` в regex-контексте), либо переопределяются через поле **Custom all value**.

**Повторение (Repeat)** — опция панели или ряда (Row), создающая копию визуализации для каждого значения multi-value переменной. Позволяет автоматически размножать панели для гомогенных ресурсов (хостов, инстансов) без ручного дублирования.

**Filter and Group by** (ранее *Ad hoc filters*; переименована в Grafana 13.1) — специальный тип переменной, автоматически добавляющий фильтры по меткам ко всем запросам дашборда к совместимому источнику данных, без необходимости явно прописывать переменную в каждом запросе. В Grafana 13.1 добавлена группировка (`Group by`) для Prometheus и Loki; в JSON-схеме дашборда по-прежнему используется `"kind": "AdhocVariable"`.

**Regex-фильтр (Query Options → Regex)** — регулярное выражение, отбирающее только нужные значения из результата запроса переменной либо извлекающее значение через группу захвата (например, `pod=.*` или `instance="([^"]*)"`). Опция **Apply regex to** определяет, к чему применяется выражение — к значению переменной (**Variable value**) или к отображаемому тексту (**Display text**).

**Switch** — тип переменной с двумя настраиваемыми значениями (включено/выключено), отображаемая как переключатель. Применяется для булевых условий в запросах, например `$debug_mode` в PromQL или `$show_errors` в LogQL.

**Интерполяция (Interpolation)** — подстановка текущего значения переменной в строку запроса, заголовка, ссылки или аннотации перед отправкой в источник данных. При интерполяции значение может экранироваться согласно синтаксису языка запроса; форматом подстановки можно управлять (см. [Синтаксис форматирования](#синтаксис-форматирования-variable-formatting)).

## Базовые концепции

### Преимущества шаблонизации

| Преимущество | Описание |
| :--- | :--- |
| **Переиспользование** | Один дашборд обслуживает множество однотипных ресурсов (кластеры, сервисы, хосты) |
| **Удобство навигации** | Быстрое переключение контекста через выпадающие списки в верхней части дашборда |
| **Автоматизация** | Динамическое создание рядов (**Rows**) и панелей (**Panels**) при появлении новых сущностей |
| **Условная отрисовка (13.x)** | Динамическое скрытие или отображение панелей, рядов и вкладок через правила **Show/hide** (по значению переменной, результату запроса или диапазону времени) |
| **Dashboard-as-Code** | Возможность декларативного описания переменных в JSON-модели дашборда (схема v1) и в ресурсах схемы v2 (`QueryVariableKind`, `CustomVariableKind`, …) |

### Типы переменных

| Тип | Назначение | Особенности |
| :--- | :--- | :--- |
| **Query** | Список значений, получаемый динамически из БД | Поддерживает `Regex` фильтрацию, `Multi-value` выбор и (12+) multi-property через JSON или source-specific запрос |
| **Custom** | Статический список значений | Задается вручную в формате CSV (`label : value` или `value`) либо JSON-массивом объектов для multi-property |
| **Multi-property (12+)** | Переменная-объект с набором свойств | Позволяет извлекать несколько свойств (`${var.id}`, `${var.name}`, `${var.ip}`) из одного значения; поддерживается типами `Custom` и `Query` (Infinity, PostgreSQL) |
| **Switch** | Переключатель из двух значений | Пары `true/false`, `1/0`, `yes/no` или произвольные; удобен для булевых условий в запросах |
| **Data source** | Переключение между источниками данных | Позволяет менять "бэкенд" дашборда (например, с Prod на Staging); фильтруется по типу плагина через `Instance name filter` |
| **Interval** | Динамический шаг времени | Используется в функциях `rate()`, `histogram_quantile()` и др.; поддерживает `auto` (step count, min interval) |
| **Filter and Group by** (13.1+) | Глобальные фильтры и группировка по меткам | Ранее *Ad hoc filters*; автоматически добавляются ко всем запросам дашборда, поддерживающим данные метки; в 13.1 добавлена группировка для Prometheus и Loki |
| **Text box** | Ручной ввод текста | Полезно для поиска по ID транзакции, комментарию или части имени |
| **Constant** | Скрытая константа | Фиксация значения для использования в нескольких панелях без отображения в UI; по умолчанию `skipUrlSync=true` |

### Глобальные переменные системы

Grafana предоставляет расширенный набор встроенных (global) переменных для управления контекстом. Они доступны во всех полях, где поддерживается интерполяция — в запросах, заголовках, ссылках и аннотациях:

| Переменная | Описание |
| :--- | :--- |
| **`$__interval`** | Оптимальный шаг агрегации, вычисляемый по формуле `(to - from) / resolution` — на основе диапазона времени и ширины графика (в пикселях) |
| **`$__interval_ms`** | То же, что `$__interval`, но число в миллисекундах (например, `20m` → `1200000`) |
| **`$__range`** | Длительность текущего диапазона дашборда (`to - from`, например `1h`); поддерживается Prometheus и Loki |
| **`$__range_s` / `$__range_ms`** | То же, что `$__range`, но в секундах / миллисекундах |
| **`$__from` / `$__to`** | Начало и конец временного интервала; по умолчанию в миллисекундах Unix Epoch (см. [форматирование дат](#форматирование-дат-во-встроенных-переменных)) |
| **`$__rate_interval`** | Рекомендуемый интервал для `rate()`/`increase()`, гарантирующий не менее четырёх scrape-точек в окне (Prometheus) |
| **`$__rate_interval_ms`** | То же, что `$__rate_interval`, но в миллисекундах |
| **`$__user`** | Объект пользователя (`${__user.id}`, `${__user.login}`, `${__user.email}`) |
| **`$__dashboard`** | Имя текущего дашборда |
| **`$__org`** | Идентификатор организации; `${__org.name}` — её имя |

### Синтаксис форматирования (Variable Formatting)

Переменные можно подставлять несколькими способами:

- `$varname` — краткий синтаксис; нельзя использовать в середине слова (`apps.frontend.$server.requests`).
- `${varname}` — для подстановки внутри выражения (в середине слова).
- `${varname:format}` — управление форматом подстановки.
- `[[varname]]` — устаревший синтаксис, использовать не следует (будет удалён в будущих релизах).

При интерполяции значение может автоматически экранироваться под язык источника (например, PromQL/InfluxDB — под регулярное выражение). Формат задаётся через `${var_name:format}` (при неверном формате применяется `glob`):

| Формат | Когда использовать | Пример результата (`v1`, `v2`) |
| :--- | :--- | :--- |
| **`:regex`** | PromQL, LogQL (внутри `=~`) | `(v1|v2)` |
| **`:glob`** | Graphite | `{v1,v2}` |
| **`:csv`** | SQL (фильтр `IN`), Python | `v1,v2` |
| **`:sqlstring`** | SQL (одинарные кавычки, `'` экранируется как `''`) | `'v1','v2'` |
| **`:singlequote`** | Одинарные кавычки, `'` экранируется как `\'` | `'v1','v2'` |
| **`:doublequote`** | JSON, HTTP/API-запросы (двойные кавычки) | `"v1","v2"` |
| **`:pipe`** | Регулярные выражения (альтернатива) | `v1|v2` |
| **`:percentencode`** | Передача в URL-ссылках | `v1%2Cv2` |
| **`:json`** | JSON-массив | `["v1","v2"]` |
| **`:lucene`** | Elasticsearch (Lucene-синтаксис) | `("v1" OR "v2")` |
| **`:queryparam`** | URL-параметры вида `var-name=...` | `var-servers=v1&var-servers=v2` |
| **`:text`** | Текстовая форма значения; для multi — через ` + ` | `v1 + v2` |
| **`:raw`** | Значение без преобразований источника | `v1,v2` |

> **Дополнительные форматы:** `:join:<delim>` — объединение multi-значений произвольным разделителем (по умолчанию `,`), например `${servers:join:&}` → `v1&v2`; `:customqueryparam:<name>:<prefix>` — настройка имени и префикса параметров; `:distributed` — формат OpenTSDB; `:date` — форматирование дат (`${__from:date:seconds}`, `${__from:date:YYYY-MM}`). `:raw` полезен, когда автоэкранирование мешает (например, спецсимволы ломают регулярное выражение).

### Общие параметры переменной

Независимо от типа, каждая переменная имеет набор настроек, влияющих на поведение и безопасность:

| Параметр | Назначение | Рекомендация |
| :--- | :--- | :--- |
| **Name** | Внутреннее имя переменной (без пробелов, регистрозависимо) | Используйте `snake_case` или `CamelCase`; не совпадайте с именами меток/полей БД |
| **Label** | Подпись в выпадающем списке | Человекочитаемое имя (`Region` вместо `region`) |
| **Description** | Подсказка (tooltip) рядом с переменной; поддерживает Markdown-ссылки | Кратко поясняйте назначение и ожидаемые значения |
| **Display / Hide** | Где отображается элемент управления | `Above dashboard` (по умолчанию); `Above dashboard, label hidden` (только без имени); `Controls menu` (в меню-гамбургере 13.x); `Hidden`. В JSON: `hide` = `0` / `1` / `2` (`dontHide`/`hideLabel`/`hideVariable` в схеме v1) |
| **Datasource (для Query)** | Источник, к которому идёт запрос переменной | Явно укажите datasource, иначе используется дефолтный дашборда |
| **Refresh** | Когда пересчитывать значения | `Never` / `On Dashboard Load` / `On Time Range Change` (см. ниже) |
| **Query Options → Sort** | Сортировка списка | `Alphabetical (asc)` — для удобства; `Disabled` — сохранить порядок из источника |
| **Query Options → Regex** | Фильтрация/извлечение значений из результата запроса | Отбирайте нужные сущности, снижая кардинальность; для извлечения используйте группу захвата |
| **Query Options → Apply regex to** | К чему применять regex | `Variable value` (по умолчанию) или `Display text` |
| **Static options** | Фиксированные значения в дополнение к запросу `Query` | Добавляйте для значений, которых нет в источнике (например, `All`/`None`) |
| **Multi-value** | Разрешить несколько значений | Включайте, когда пользователю нужен выбор "нескольких" |
| **Include All option** | Добавить пункт `All` | Включайте для агрегатов; при необходимости задайте **Custom all value** |
| **Allow custom values** | Разрешить ввод произвольных значений (только CSV-Custom) | Для гибких списков, где значение вводится вручную |
| **Custom all value** | Что подставлять при выборе `All` | Для PromQL — `.*` (через `=~`); для Loki — `.+`; по умолчанию `$__all` |
| **skipUrlSync** | Не синхронизировать значение переменной в URL | Включайте для чувствительных значений и «чистых» ссылок; у `Constant` включено по умолчанию |

### Расширенные глобальные переменные

Помимо перечисленных выше, Grafana предоставляет переменные для работы со временем и форматированием, полезные в запросах и заголовках:

| Переменная | Описание |
| :--- | :--- |
| **`$__timeFilter` / `$__timefilter`** | Готовое выражение фильтра по времени для SQL/InfluxDB (например, `time > now() - 7d`) — подставляется автоматически в соответствующих источниках |
| **`$__timezone`** | Текущая временная зона дашборда: `utc` или запись IANA (например, `Europe/Moscow`); при выборе *Browser Time* определяется по браузеру |
| **`$__url_time_range`** | Диапазон времени в виде URL-параметров (`from=...&to=...`), где значения — Unix-миллисекунды; предназначена для ссылок (Data Links, Panel Links), а не для редактора запросов |

> **Примечание:** устаревшая переменная `$__name` (для панели Singlestat) неактуальна — сама панель Singlestat удалена с Grafana 8.0.

#### Форматирование дат во встроенных переменных

Переменные `$__from` и `$__to` по умолчанию подставляются как Unix-миллисекунды, но их формат можно переопределить через `:date`. Для получения секунд вместо миллисекунд (например, в источниках, требующих секунды) используйте вариант `:date:seconds`, а не отдельную переменную:

| Синтаксис | Пример результата | Описание |
| :--- | :--- | :--- |
| `${__from}` | `1594671549254` | Unix-миллисекунды (по умолчанию) |
| `${__from:date}` | `2020-07-13T20:19:09.254Z` | ISO 8601/RFC 3339 |
| `${__from:date:iso}` | `2020-07-13T20:19:09.254Z` | ISO 8601/RFC 3339 |
| `${__from:date:seconds}` | `1594671549` | Unix-секунды |
| `${__from:date:YYYY-MM}` | `2020-07` | Произвольный формат moment.js (без `:`) в локальной зоне |

Синтаксис работает одинаково для `$__from` и `$__to`; его можно использовать и в URL-ссылках.

### JSON-модель переменной (Dashboard-as-Code)

Переменные хранятся в массиве `templating.list` JSON-модели дашборда. Это позволяет описывать их декларативно при провиженинге (см. [Провиженинг](./grafana_provisioning.md)):

```json
{
  "templating": {
    "list": [
      {
        "name": "Region",
        "type": "query",
        "label": "Region",
        "datasource": { "type": "prometheus", "uid": "prom-prod" },
        "definition": "label_values(node_info, region)",
        "query": { "query": "label_values(node_info, region)", "refId": "Region" },
        "refresh": 1,
        "sort": 1,
        "regex": "",
        "multi": false,
        "includeAll": true,
        "allValue": ".*",
        "hide": 0,
        "current": { "text": "All", "value": "$__all" }
      }
    ]
  }
}
```

Ключевые поля: `type` (`query`/`custom`/`datasource`/`interval`/`textbox`/`constant`/`adhoc`/`switch`), `refresh` (`1`=On Dashboard Load, `2`=On Time Range Change, `0`=Never), `multi`/`includeAll` (boolean), `allValue` (Custom all value), `hide` (`0`/`1`/`2`), `skipUrlSync` (boolean). Для зависимой переменной в `query.query` достаточно сослаться на `$Region` — Grafana подставит значение перед вычислением. Полное описание полей см. в [JSON-модели дашборда](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/view-dashboard-json-model/).

> **Схема v1 и v2.** Классическая модель хранит переменные в массиве `templating.list` (как в примере выше). Начиная с Grafana 13 (Dynamic Dashboards) дашборды автоматически мигрируют в **схему v2** при первой загрузке — это не меняет работу провиженинга через API/Terraform/Git Sync. В ресурсной (v2) модели переменные описываются типизированными видами: `QueryVariableKind`, `CustomVariableKind`, `SwitchVariableKind`, `DatasourceVariableKind`, `IntervalVariableKind`, `TextVariableKind`, `ConstantVariableKind`, `AdhocVariableKind`, `GroupByVariableKind` (см. [схему переменных](https://grafana.com/docs/grafana/latest/observability-as-code/schema-v2/variables-schema/)).

### Порядок обновления и разрешение зависимостей

Переменные вычисляются **в том порядке, в котором они перечислены в `templating.list`**. Следствия:

- Зависимая переменная должна стоять **после** той, на которую ссылается (иначе `$Region` ещё не будет готов при её вычислении).
- Режим `Refresh = On Time Range Change` заставляет переменную пересчитываться при смене диапазона времени — используйте только для действительно динамических списков (например, появление новых подов), чтобы не нагружать источник.
- Режим `On Dashboard Load` (и `Never` для констант) — для относительно статичных списков.
- При смене значения в UI Grafana пересчитывает все зависимые переменные и обновляет панели.

### Управление и инспекция переменных

В разделе **Dashboard options → Variables** доступны операции:

- **Reorder** — перетаскивание переменных меняет их порядок вычисления и позицию в списке. Тип отображения (`Above dashboard` / `Controls menu` / `Hidden`) можно менять перетаскиванием между секциями.
- **Duplicate variable** — быстрое создание зависимой переменной-копии (удобно для цепочек: скопировать родителя и дописать запрос).
- **Inspect variable** — просмотр зависимостей переменной (граф `depends on` / `used by`), текущего значения и итогового интерполированного результата — помогает отлаживать цепочки.
- **Apply to all panels** — массовое применение изменения переменной к панелям.

**Синхронизация с URL.** По умолчанию значения переменных синхронизируются в URL в виде `var-<name>=value` (например, `?var-Region=eu-west&var-Host=node1`), что позволяет открывать дашборд с готовым контекстом. Отключить это для конкретной переменной можно флагом `skipUrlSync=true` (полезно для скрытых и чувствительных значений). Подробнее — [Create dashboard URL variables](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/create-dashboard-url-variables/).

**Индексация multi-value (indexed variables).** Для переменной с несколькими значениями к элементу массива можно обратиться по индексу: `${query0.0}`, `${query0.1}` — первый, второй элемент и т.д. Это позволяет в разных панелях использовать позицию значения, а не само значение.

## Практические сценарии

### Предварительные требования

Перед выполнением сценариев убедитесь, что выполнены общие условия:

- **Grafana 12+** (для Multi-property переменных и Switch) / **Grafana 13+** (для Dynamic Dashboards, правил Show/hide и переименования Ad hoc → Filter and Group by). Проверьте версию: `curl -s $GRAFANA_URL/api/health | jq -r .version` → `13.x.x`.
- **Права редактора (Editor)** или выше на дашборде, либо токен Service Account с ролью `Dashboard Editor`/`Admin` для DaC/API.
- **Источник данных** настроен и доступен (Prometheus/Loki/PostgreSQL/…). Проверьте: `curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" $GRAFANA_URL/api/datasources` → список datasources с `uid`.
- **Метрики/данные присутствуют** в источнике (для Query-переменных). Проверьте в источнике запросом, возвращающим значения переменной.
- **Переменные окружения** (для примеров с API): `GRAFANA_URL` (например, `http://localhost:3000`), `GRAFANA_TOKEN` (SA-токен).

> Примечание: шаблонные переменные **не поддерживаются в запросах алертинга (Unified Alerting)** — правила оповещений вычисляются на стороне сервера без контекста дашборда. Для алертов используйте фиксированные селекторы или recording rules (см. [Дашборды](./grafana-dashboards.md)).

### Сценарий 1: Цепочки зависимых переменных (Chaining)

Этот сценарий позволяет реализовать иерархическую фильтрацию (например: Регион → ЦОД → Стойка → Хост).

1. **Базовая переменная `Region`**:
   ```promql
   label_values(node_info, region)
   ```

2. **Зависимая переменная `Datacenter`**:
   В запросе используется значение первой переменной:
   ```promql
   label_values(node_info{region="$Region"}, datacenter)
   ```

3. **Зависимая переменная `Host`**:
   Используется оператор `=~` для поддержки множественного выбора (`Multi-value`) в предыдущих звеньях:
   ```promql
   label_values(node_info{region=~"$Region", datacenter=~"$Datacenter"}, instance)
   ```

**Настройка обновления (Refresh)**:
- **On Dashboard Load**: Для статичных данных.
- **On Time Range Change**: Если состав хостов меняется часто (динамические окружения).

**Пошаговая настройка в UI:**
1. Откройте дашборд → ⋮ (шестерёнка) → **Variables** → **Add variable** → тип `Query`.
2. `Region`: `Name=Region`, `Query=label_values(node_info, region)`, `Refresh=On Dashboard Load`, `Include All option=on`, `Custom all value=.*`.
3. `Datacenter`: `Query=label_values(node_info{region="$Region"}, datacenter)` — важно, чтобы переменная стояла **ниже** `Region` в списке.
4. `Host`: `Query=label_values(node_info{region=~"$Region", datacenter=~"$Datacenter"}, instance)`, включите `Multi-value`.
5. В панелях используйте селекторы `instance=~"$Host"`.

**Ожидаемый результат:** при выборе `Region=eu-west` список `Datacenter` содержит только ЦОД этого региона; при `All` в `Region` — `Datacenter` тоже видит `All` (через `.*`/`$__all`).

**Валидация:**
- Проверьте порядок: `curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" "$GRAFANA_URL/api/datasources/proxy/uid/<dsUid>/api/v1/label/region/values"` → список регионов.
- В UI убедитесь, что смена `Region` пересобирает `Datacenter` и `Host` (индикатор загрузки списка).

**Типичные проблемы:**
- Список `Datacenter` пуст при выборе `All` в `Region` → причина: `Region` не использует `=~` в запросе `Datacenter`. Исправление: `region=~"$Region"`.
- `Host` не обновляется → причина: переменная стоит выше зависимости в списке `templating.list`. Перенесите ниже.
- Ошибка `bad_data` в PromQL → причина: `Multi-value` в `Host` с оператором `=`. Исправление: используйте `=~` или формат `${Host:pipe}`.

### Сценарий 2: Переменные Multi-property (12+)

Multi-property переменная сопоставляет одному логическому значению несколько свойств, специфичных для разных источников. Это избавляет от необходимости создавать отдельные переменные для каждого свойства.

Поддерживается типами `Custom` и `Query` (Infinity, PostgreSQL).

**Custom (JSON-массив):**

```json
[
  { "value": "1", "text": "Development", "aws": "dev", "azure": "development" },
  { "value": "2", "text": "Staging", "aws": "stag", "azure": "staging" },
  { "value": "3", "text": "Production", "aws": "prod", "azure": "production" }
]
```

**Query (PostgreSQL):** запрос `SELECT id, name, ip FROM servers` возвращает несколько колонок.

**Доступ к свойствам:** `${var.id}`, `${var.name}`, `${var.ip}`, `${var.azure}` — свойства можно вкладывать друг в друга и обращаться к вложенным через точку. В разных панелях можно использовать то свойство, которое ожидает конкретный источник.

### Сценарий 3: Использование `$__rate_interval` для точных графиков

При использовании стандартного `$__interval` в функции `rate()` на малых масштабах времени (например, просмотр за 5 минут) интервал может оказаться меньше частоты сбора метрик (scrape interval), что приведет к пустым графикам.

**Правильный подход в PromQL:**
```promql
sum(rate(http_requests_total{instance=~"$Host"}[$__rate_interval])) by (status)
```
`$__rate_interval` определяется как `max($__interval + Scrape interval, 4 × Scrape interval)` и гарантирует, что в окно расчета попадут как минимум четыре scrape-точки. Это делает графики стабильными при любом зуме и устраняет «дыры» от `$__interval`. Используйте `$__rate_interval` вместо фиксированного интервала.

### Сценарий 4: Динамическое скрытие панелей, рядов и вкладок (Show/hide rules)

В Grafana 13 (Dynamic Dashboards) видимостью элементов управляют правила **Show/hide rules**. Правила применяются к панелям, рядам и вкладкам и поддерживают три типа условий:

| Тип правила | Условие | Пример |
| :--- | :--- | :--- |
| **Query result** | Наличие/отсутствие данных у запроса | Скрыть панель при `No data` |
| **Template variable** | Значение переменной: `Equals`, `Not equals`, `Matches`, `Not matches` (regex) | Показать секцию только при `$datasource == Prometheus` |
| **Time range less than** | Диапазон времени дашборда короче заданного (от 5 минут до 5 лет) | Скрыть недельную панель, если диапазон меньше 7 дней |

**Пошагово:**
1. Создайте переменную: `Variables` → `Add variable` → `Custom`, `Name=show_advanced`, `Values=true,false`, `Display=Above dashboard`.
2. Откройте панель → `Panel options` → **Show / hide rules** → выберите **Show** или **Hide**.
3. **+ Add rule** → тип **Template variable** → переменная `show_advanced`, оператор `Equals`, значение `true`.
4. При нескольких правилах выберите **Match all** или **Match any** (логика `AND` / `OR`).
5. Сохраните дашборд.

**Валидация:** переключите `show_advanced` в `false` — панель скрывается; в `true` — появляется. В режиме редактирования скрытые панели помечаются значком.

> **Ограничение:** правила Show/hide доступны только для раскладки **Auto grid** (задаётся на уровне дашборда, ряда или вкладки). Наследование: элементы внутри скрытого ряда/вкладки также скрываются.

### Сценарий 5: Переключение источника данных (Datasource variable)

Позволяет одним дашбордом переключаться между окружениями (Prod/Staging) или бэкендами (Prometheus/Loki), не дублируя панели.

1. `Variables` → `Add variable` → тип `Datasource`.
2. `Name=ds`, `Label=Datasource`, `Type=Prometheus` (отфильровать только нужный тип) или оставить все.
3. В запросах панелей вместо жёстко заданного источника выберите `${ds}` (в редакторе панели — поле **Data source** → `${ds}`).
4. (Опционально) включите `Include All` — тогда `${ds}` не подставится напрямую; используйте `=~` или конкретный выбор.

**Пример запроса PromQL с datasource-переменной:**
```promql
sum(rate(http_requests_total{job=~"$job"}[$__rate_interval])) by (status)
```
Здесь источник выбран через `${ds}`, а фильтр — через обычную переменную `$job`.

**Валидация:** смена `ds` в выпадающем списке пересобирает все панели с этим источником. Проверьте, что оба datasource содержат одинаковые метрики/поля, иначе часть панелей вернёт `No data`.

**Типичная проблема:** ошибка `datasource ${ds} not found` → причина: переменная `Include All` включена и выбран `All`. Исправление: отключите `Include All` для datasource-переменной или используйте `=~`.

### Сценарий 6: Filter and Group by (ранее Ad hoc filters)

Автоматически добавляют фильтры ко всем запросам дашборда к совместимому источнику, без явной переменной в каждом запросе.

> **Переименование (13.1).** В Grafana 13.1 тип *Ad hoc filters* переименован в **Filter and Group by** и расширен группировкой для Prometheus и Loki. В JSON-схеме дашборда элемент по-прежнему называется `"kind": "AdhocVariable"`.

1. `Variables` → `Add variable` → тип **Filter and Group by** (в более старых версиях — `Ad hoc filters`).
2. `Name=filters`, `Datasource` — укажите целевой источник (например, Prometheus `prom-prod`).
3. Вверху дашборда появится блок фильтров: выберите метку (`namespace`), оператор (`=`, `=~`, `!=`) и значение (`prod`).
4. Все панели, чьи запросы идут к этому источнику, получат условие `namespace="prod"` автоматически.

**Группировка (13.1+):** для Prometheus/Loki доступна агрегация по выбранной метке — например, `sum by (namespace)` при группировке по `namespace`.

**Пример (Loki/LogQL):** фильтр `cluster=~"prod-.*"` добавится к каждому запросу как строковый фильтр `| json | cluster=~"prod-.*"`.

**Валидация:** добавьте фильтр `status="500"` — панели пересобираются только с этими значениями. Фильтры применяются только к запросам того же источника, что указан в переменной.

**Ограничение:** фильтры поддерживаются не всеми источниками (Prometheus, Loki, Elasticsearch, PostgreSQL и др.); для неподдерживаемых источников используйте обычные Query-переменные.

### Сценарий 7: Переменная Interval (ручной выбор шага агрегации)

Полезна, когда автоматический `$__interval` даёт слишком детальный или слишком укрупнённый шаг для конкретной панели.

1. `Variables` → `Add variable` → тип `Interval`.
2. `Name=myinterval`, `Values=30s,1m,5m,1h,1d` (через запятую; `auto` добавляется автоматически).
3. В запросе используйте `$myinterval` вместо `$__interval`:
```promql
sum(rate(http_requests_total{instance=~"$Host"}[$myinterval])) by (status)
```

**Валидация:** выбор `5m` в выпадающем списке укрупняет график (меньше точек). При `auto` Grafana выбирает шаг по разрешению и диапазону.

**Типичная проблема:** график «плывет»/странный — причина: диапазон меньше выбранного интервала. Исправление: добавьте `auto` и используйте его по умолчанию или уменьшите `Values`.

### Сценарий 8: Text box — поиск по ID/строке

Тип `Text box` даёт свободный ввод без выпадающего списка (поиск транзакции, части имени, trace-id).

1. `Variables` → `Add variable` → тип `Text box`.
2. `Name=trace_id`, `Label=Trace ID`, `Default value=` (пусто или пример `abc123`).
3. В запросе Loki:
```logql
{app="checkout"} | json | traceId=~"$trace_id"
```
При пустом значении условие сработает как «все» (если реализовано через опциональный фильтр), иначе отфильтрует по введённой подстроке.

**Безопасность:** экранируйте спецсимволы ввода. Для regex-источников используйте формат `${trace_id:regex}`, чтобы избежать `bad_data` при вводе `(`, `[` и т.п.

**Валидация:** введите `abc` — панель показывает только строки с `abc` в `traceId`. Очистка поля возвращает все строки (при корректной реализации фильтра).

### Сценарий 9: Кастомное значение «All» и регулярка

При `Include All option` по умолчанию Grafana подставляет `$__all` — токен, который в зависимости от контекста раскрывается в список всех значений. Для PromQL это часто нужно заменить на `.*`.

- Переменная `Host` (`Multi-value` + `Include All`), `Custom all value=.*`.
- В запросе: `instance=~"$Host"`. При выборе `All` подставляется `instance=~".*"` → все инстансы.
- Для Loki аналогично: `Custom all value=.+`.

**Почему `.*`, а не список:** для источников без встроенной поддержки `$__all` (например, старые версии PostgreSQL) явная регулярка надёжнее и избегает проблем с кавычками. Для Grafana-native datasource `Custom all value` можно оставить пустым (тогда используется `$__all`).

**Валидация:** выберите `All` → запрос выполняется без ошибок и возвращает агрегат по всем значениям. Проверьте `curl` к источнику с подставленным `.*`.

### Сценарий 10: Dashboard-as-Code — переменная в JSON-модели

Переменные удобно версионировать в Git вместе с дашбордом (см. [Провиженинг](./grafana_provisioning.md) и [Дашборды как код](./grafana-dashboards.md)).

Пример описания зависимой переменной `Datacenter` в `dashboard.json` (фрагмент `templating.list`):

```json
{
  "name": "Datacenter",
  "type": "query",
  "label": "Datacenter",
  "datasource": { "type": "prometheus", "uid": "prom-prod" },
  "query": { "query": "label_values(node_info{region=~\"$Region\"}, datacenter)", "refId": "Datacenter" },
  "refresh": 1,
  "sort": 1,
  "multi": true,
  "includeAll": true,
  "allValue": ".*",
  "hide": 0
}
```

**Пошагово (провиженинг через API):**
1. Подготовьте `dashboard.json` с нужным `templating.list`.
2. Загрузите дашборд (см. Сценарий HTTP API в [Дашборды](./grafana-dashboards.md)):
```bash
curl -X POST "$GRAFANA_URL/api/dashboards/db" \
  -H "Authorization: Bearer $GRAFANA_TOKEN" \
  -H "Content-Type: application/json" \
  -d @dashboard.json
# → {"status":"success","uid":"...","url":"..."}
```
3. Откройте дашборд в UI — переменные уже настроены и работают.

**Валидация:** после загрузки откройте Variables в дашборде — список совпадает с `templating.list`. Изменение JSON и повторная загрузка обновляет переменные (при `version`+1 в метаданных дашборда).

### Сценарий 11: Повторение панелей и рядов (Repeat)

Опция `Repeat` размножает панель, ряд или вкладку по каждому значению multi-value переменной. Это позволяет одним шаблоном обслуживать гомогенные ресурсы (по панели на диск, на узел, на namespace).

1. Создайте переменную `disk` (`Query`, `Multi-value` включён, например `label_values(node_disk_info, device)`).
2. Откройте панель → `Panel options` → **Repeat options**.
3. Выберите **Repeat by variable** = `$disk`.
4. Для кастомной раскладки выберите **Repeat direction**: `Horizontal` (панели в ряд, ширина подстраивается) или `Vertical` (колонка). Для `Horizontal` задайте **Max per row**.

**Пример запроса с неповторяющейся привязкой к текущему значению:** панель, повторяемая по `$disk`, получает собственный подставленный `$disk`, поэтому в её запросе используйте `device=~"$disk"`:

```promql
rate(node_disk_read_bytes_total{device=~"$disk"}[$__rate_interval])
```

**Валидация:** при выборе нескольких дисков появляется по панели на каждый; заголовок панели можно сделать динамическим (`Disk $disk`).

**Ограничения повторения:**
- Повторение работает только с multi-value переменными.
- Генерируемые копии нельзя редактировать по отдельности — изменения вносятся только в исходную панель.
- Изменения раскладки сгенерированных копий не сохраняются: при каждой загрузке дашборда они пересоздаются из исходной панели.
- Нельзя смешивать повторяемую панель с обычными на одном ряду при `Horizontal`.
- Вложенное повторение (ряд по `$cluster`, панель внутри — по `$node`) требует двух связанных переменных.
- Повторение не поддерживается в публичных дашбордах и имеет ограничения в Dynamic Dashboards (схема v2); для масштабирования предпочитайте программную генерацию (Grafonnet, Scenes SDK).

## Дополнительная информация

### Рекомендации (Best Practices)

1. **Оператор `=~` vs `=`**: Всегда используйте `=~ "$var"`, если для переменной включена опция **Multi-value** или **Include All**. Обычное равенство `=` вызовет ошибку при выборе более одного значения.
2. **Scrubbing (Очистка)**: Если в именах переменных или их значениях могут быть спецсимволы, используйте форматирование `:regex` или `:sqlstring`.
3. **Ограничение выборки**: Не создавайте переменные, возвращающие более 1000 значений (например, `ID` каждой транзакции). Это перегружает браузер и источник данных. Используйте `Text box` для поиска конкретных ID.
4. **Тип Refresh**: Используйте `Never` или `On Dashboard Load` для констант. `On Time Range Change` — только если данные действительно зависят от времени.
5. **Порядок переменных**: Размещайте переменные без зависимостей выше их «детей»; используйте `Duplicate variable` для создания зависимых переменных и не забывайте затем перетаскивать копию в нужную позицию.
6. **`All` для скрытой переменной**: если `Include All` включён, но `Display=Hidden`, по умолчанию выбирается только первое значение. Чтобы закрепить `All`, временно переключите Display на `Above dashboard`, выберите `All`, сохраните дашборд и верните `Hidden`.
7. **Документируйте связи**: в UI нет индикации зависимостей между переменными — задавайте логический порядок и понятные `Label`/`Description`.

### Типичные ошибки

- **Кардинальность**: Запрос `label_values({__name__=~".*"}, pod)` без фильтра по `job` или `namespace` может "уронить" Prometheus при большом количестве метрик.
- **Конфликт имен**: Называйте переменные с большой буквы или используйте префиксы (например, `var_Host`), чтобы не перепутать их с именами полей в SQL или метками в PromQL.
- **Отсутствие "All"**: Если опция `Include All` выключена, а пользователь хочет видеть агрегат по всем сущностям, дашборд может стать неудобным.
- **Большой `All` без `Custom all value`**: при пустом `Custom all value` для `All` подставляется полный список значений, что даёт длинный запрос и нагрузку на источник; задайте `.*`/`.+` или другой компактный селектор.

### Устранение неполадок

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| **No data** во всех панелях после выбора переменной | Несовпадение значения переменной с метками источника | Проверьте точное совпадение (`$Host` = `instance`); используйте `=~` для частичного совпадения |
| **`bad_data: ... unexpected token`** в PromQL | `Multi-value`/`All` с оператором `=` | Замените `=` на `=~` или примените формат `${var:pipe}`/`${var:csv}` |
| Список зависимой переменной пуст | Переменная стоит **выше** зависимости в `templating.list` | Перенесите зависимую переменную ниже в списке |
| `datasource ${ds} not found` | `Include All` включён для datasource-переменной | Отключите `Include All` или используйте `=~` в запросах |
| Регулярка в `Query Options → Regex` не фильтрует | Неправильный синтаксис / захват не той группы | Проверьте regex отдельно; для извлечения значения используйте группу захвата, например `pod="([^"]+)"` |
| Переменная не обновляется при смене времени | `Refresh = Never`/`On Dashboard Load` | Установите `On Time Range Change`, если список зависит от времени |
| Filter and Group by не применяется | Источник панели отличается от источника переменной | Назначьте переменной тот же datasource, что у панелей |
| `All` возвращает пустой результат | `Custom all value` не задан для non-native источника | Укажите `.*` (PromQL) / `.+` (Loki) в `Custom all value` |
| Высокая нагрузка на источник | Переменная возвращает тысячи значений | Ограничьте `Regex`-фильтром; используйте `Text box` для поиска конкретных ID |
| Скрытая переменная не подставляется | `Hide=2`/`Display=Hidden`, но имя не совпадает в запросе | Проверьте `Name` (регистрозависимо) и наличие `$` в запросе |
| Правило Show/hide не действует | Панель не в раскладке **Auto grid** | Переключите раскладку дашборда/ряда на `Auto grid`; правила доступны только в ней |
| В URL подставляется значение, которого не было | Переменная синхронизируется с URL и переопределена ссылкой | Включите `skipUrlSync=true` для переменной или уберите `var-<name>` из ссылки |
| `${var.prop}` не подставляется | Переменная не является multi-property | Для multi-property используйте JSON `Custom` или `Query` (PostgreSQL/Infinity) |

### Ограничения и особые случаи

- **Алертинг не поддерживает переменные:** правила Unified Alerting вычисляются сервером без контекста дашборда, поэтому `$Host`, `$Region` и прочие template-переменные в запросах алертов недопустимы. Используйте фиксированные селекторы или recording rules. Исключение — переменные в **аннотациях/сообщениях** алерта (там допустимы built-in, например `{{ $labels.instance }}` — это уже шаблоны сообщений, а не dashboard-переменные).
- **Цепочка зависимостей ограничена порядком:** Grafana не разрешает циклические зависимости; зависимая переменная должна быть ниже в списке.
- **Кардинальность:** переменные, возвращающие >1000 значений, перегружают UI и источник. Ограничивайте выборку `Regex` или переходите на `Text box`.
- **`Custom all value` и кавычки:** для SQL-источников при `All` используйте `:sqlstring` или задайте `Custom all value` как список с кавычками, иначе получите SQL-ошибку.
- **Скрытые переменные (`Hide=2`/`Display=Hidden`):** удобны для констант, но их нельзя изменить из UI — значение берётся из JSON/провиженинга (или из URL, если `skipUrlSync` не установлен).
- **Multi-property ограничена типами:** `${var.prop}` работает только для переменных `Custom` (JSON-массив) и `Query` с источниками Infinity и PostgreSQL; для прочих источников используйте отдельные переменные или `Regex`-группы захвата.
- **Схема v2 и Dynamic Dashboards:** в Grafana 13 дашборды автоматически мигрируют в схему v2; провиженинг через API/Terraform/Git Sync продолжает работать, но повторяющиеся панели имеют ограничения в v2 (для масштабирования предпочтительнее генерация через Grafonnet/Scenes SDK).
- **Legacy Angular:** старые дашборды на Angular могут использовать устаревший синтаксис переменных; при миграции на React проверьте совместимость (Angular отключена по умолчанию в Grafana 11 и полностью удалена в Grafana 12).
- **Переменные в заголовках/аннотациях:** поддерживаются (например, заголовок панели `Статус $Host`), но не во всех типах аннотаций.
- **Передача через URL:** значения переменных можно задать в ссылке (`?var-Region=eu-west&var-Host=node1`) — удобно для переходов извне и дашбордов верхнего уровня (см. раздел [Управление и инспекция переменных](#управление-и-инспекция-переменных)).

Подробная информация о синтаксисе переменных доступна в [документации Grafana](https://grafana.com/docs/grafana/latest/visualizations/dashboards/variables/).
