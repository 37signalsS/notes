# Grafana: Шаблонизация

## Определения

**Шаблонизация (Templating)** — механизм создания динамических дашбордов через переменные. Значения переменных подставляются в запросы к источникам данных, заголовки панелей, аннотации и ссылки, позволяя одному дашборду отображать данные для различных ресурсов (серверов, приложений, кластеров) без дублирования панелей.

**Связанные темы:**

- [Дашборды: определения и концепции](./grafana-dashboards.md)

## Базовые концепции

### Преимущества шаблонизации

| Преимущество | Описание |
| :--- | :--- |
| **Переиспользование** | Один дашборд обслуживает множество однотипных ресурсов (кластеры, сервисы, хосты) |
| **Удобство навигации** | Быстрое переключение контекста через выпадающие списки в верхней части дашборда |
| **Автоматизация** | Динамическое создание рядов (**Rows**) и панелей (**Panels**) при появлении новых сущностей |
| **Условная логика (v11+)**| Динамическое скрытие или отображение элементов интерфейса на основе логики переменных |
| **Dashboard-as-Code** | Возможность декларативного описания переменных в JSON-модели дашборда |

### Типы переменных

| Тип | Назначение | Особенности |
| :--- | :--- | :--- |
| **Query** | Список значений, получаемый динамически из БД | Поддерживает `Regex` фильтрацию и `Multi-value` выбор |
| **Multi-property (v12+)**| Переменная-объект с набором свойств | Позволяет извлекать несколько колонок (например, `ID`, `Name`, `IP`) из одного запроса |
| **Custom** | Статический список значений | Задается вручную в формате `label : value` или просто `value` |
| **Datasource** | Переключение между источниками данных | Позволяет менять "бэкенд" дашборда (например, с Prod на Staging) |
| **Interval** | Динамический шаг времени | Используется в функциях `rate()`, `histogram_quantile()` и др. |
| **Ad hoc filters** | Глобальные фильтры по меткам | Автоматически добавляются ко всем запросам дашборда, поддерживающим данные метки |
| **Text box** | Ручной ввод текста | Полезно для поиска по ID транзакции, комментарию или части имени |
| **Constant** | Скрытая константа | Фиксация значения для использования в нескольких панелях без отображения в UI |

### Глобальные переменные системы

Grafana 11/12 предоставляет расширенный набор встроенных переменных для управления контекстом:

| Переменная | Описание |
| :--- | :--- |
| **`$__interval`** | Оптимальный шаг агрегации, вычисляемый на основе разрешения экрана и диапазона времени |
| **`$__interval_ms`** | То же самое, что и `$__interval`, но в миллисекундах |
| **`$__range`** | Текущий временной диапазон (например, `1h`, `24h`) |
| **`$__from` / `$__to`** | Начало и конец временного интервала в миллисекундах (Unix Epoch) |
| **`$__rate_interval`** | Рекомендуемый интервал для `rate()`, предотвращающий "дыры" в графиках |
| **`$__user`** | Объект пользователя (`$__user.id`, `$__user.login`, `$__user.email`) |
| **`$__dashboard`** | Метаданные (`$__dashboard.name`, `$__dashboard.uid`) |
| **`$__org`** | Идентификатор организации (`$__org.id`, `$__org.name`) |

### Синтаксис форматирования (Variable Formatting)

Для корректной подстановки значений в запросы различных типов баз данных используется синтаксис `${var_name:format}`:

| Формат | Когда использовать | Пример результата (`v1`, `v2`) |
| :--- | :--- | :--- |
| **`:regex`** | PromQL, LogQL (внутри `=~`) | `(v1|v2)` |
| **`:glob`** | Graphite | `{v1,v2}` |
| **`:csv`** | SQL (фильтр `IN`), Python | `v1,v2` |
| **`:sqlstring`**| SQL (экранирование строк) | `'v1','v2'` |
| **`:doublequote`**| JSON, API запросы | `"v1","v2"` |
| **`:pipe`** | Регулярные выражения (альтернатива) | `v1|v2` |
| **`:percentencode`**| Передача в URL-ссылках | `v1%2Cv2` |
| **`:text`** | Отображение имени (Label) переменной | Выводит "Value 1" вместо "v1" |

## Практические сценарии

### Сценарий 1: Цепочки зависимых переменных (Chaining)

Этот сценарий позволяет реализовать иерархическую фильтрацию (например: Регион → ЦОД → Стойка → Хост).

1. **Базовая переменная `Region`**:
   ```promql
   label_values(node_info, region)
   ```

2. **Зависимая переменная `Datacenter`**:
   В запросе используется значение первой переменной:
   ```promql
   label_values(node_info{region="$Region"}, datacenter)
   ```

3. **Зависимая переменная `Host`**:
   Используется оператор `=~` для поддержки множественного выбора (`Multi-value`) в предыдущих звеньях:
   ```promql
   label_values(node_info{region=~"$Region", datacenter=~"$Datacenter"}, instance)
   ```

**Настройка обновления (Refresh)**:
- **On Dashboard Load**: Для статичных данных.
- **On Time Range Change**: Если состав хостов меняется часто (динамические окружения).

### Сценарий 2: Переменные Multi-property для SQL/Infinity (v12+)

Если источник данных возвращает несколько колонок, вы можете обращаться к ним через точку:
- Запрос: `SELECT id, name, ip FROM servers`
- Доступ: `${var.id}`, `${var.name}`, `${var.ip}`.
Это избавляет от необходимости создавать три отдельные переменные и выполнять три запроса к БД.

### Сценарий 3: Использование `$__rate_interval` для точных графиков

При использовании стандартного `$__interval` в функции `rate()` на малых масштабах времени (например, просмотр за 5 минут) интервал может оказаться меньше частоты сбора метрик (scrape interval), что приведет к пустым графикам.

**Правильный подход в PromQL:**
```promql
sum(rate(http_requests_total{instance=~"$Host"}[$__rate_interval])) by (status)
```
`$__rate_interval` гарантирует, что в окно расчета попадет как минимум две точки (Scrape Interval + Resolution), что делает графики стабильными при любом зуме.

### Сценарий 4: Динамическое скрытие панелей (Visibility)

В Grafana 11+ можно управлять видимостью панелей на основе значения переменной.
- Создайте переменную `show_advanced` (тип `Custom`, значения `true, false`).
- В настройках панели (раздел **Visibility**) укажите условие: `$show_advanced == 'true'`.
- Панель будет появляться только тогда, когда пользователь выберет соответствующий режим.

## Дополнительная информация

### Рекомендации (Best Practices)

1. **Оператор `=~` vs `=`**: Всегда используйте `=~ "$var"`, если для переменной включена опция **Multi-value** или **Include All**. Обычное равенство `=` вызовет ошибку при выборе более одного значения.
2. **Scrubbing (Очистка)**: Если в именах переменных или их значениях могут быть спецсимволы, используйте форматирование `:regex` или `:sqlstring`.
3. **Ограничение выборки**: Не создавайте переменные, возвращающие более 1000 значений (например, `ID` каждой транзакции). Это перегружает браузер и источник данных. Используйте `Text box` для поиска конкретных ID.
4. **Тип Refresh**: Используйте `Never` или `On Dashboard Load` для констант. `On Time Range Change` — только если данные действительно зависят от времени.

### Типичные ошибки

- **Кардинальность**: Запрос `label_values({__name__=~".*"}, pod)` без фильтра по `job` или `namespace` может "уронить" Prometheus при большом количестве метрик.
- **Конфликт имен**: Называйте переменные с большой буквы или используйте префиксы (например, `var_Host`), чтобы не перепутать их с именами полей в SQL или метками в PromQL.
- **Отсутствие "All"**: Если опция `Include All` выключена, а пользователь хочет видеть агрегат по всем сущностям, дашборд может стать неудобным.

Подробная информация о синтаксисе переменных доступна в [документации Grafana](https://grafana.com/docs/grafana/latest/dashboards/variables/).
