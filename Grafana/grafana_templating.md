# Grafana: Шаблонизация

## Определения

**Шаблонизация (Templating)** — механизм создания динамических дашбордов через переменные. Значения переменных подставляются в запросы к источникам данных, заголовки панелей, аннотации и ссылки, позволяя одному дашборду отображать данные для различных ресурсов (серверов, приложений, кластеров) без дублирования панелей.

**Цепочка зависимых переменных (Chaining)** — связывание переменных так, что значение одной вычисляется на основе выбранного значения другой (например, выбор `Datacenter` зависит от выбранного `Region`). Grafana обновляет зависимые переменные в порядке их объявления в списке `templating`.

**Multi-value** — опция переменной, разрешающая выбрать несколько значений одновременно. Результат подстановки — набор значений, который нужно использовать с оператором `=~` (regex-совпадение) или форматированием `:csv`/`:pipe`, иначе запрос вернёт ошибку.

**Include All option** — опция, добавляющая в выпадающий список пункт `All`. При выборе `All` по умолчанию подставляются все значения переменной (через `|` в regex-контексте), либо переопределяются через поле **Custom all value**.

**Повторение (Repeat)** — опция панели или ряда (Row), создающая копию визуализации для каждого значения multi-value переменной. Позволяет автоматически размножать панели для гомогенных ресурсов (хостов, инстансов) без ручного дублирования.

**Ad hoc filters** — специальный тип переменной, автоматически добавляющий фильтры по меткам ко всем запросам дашборда к совместимому источнику данных, без необходимости явно прописывать переменную в каждом запросе.

**Regex-фильтр (Query Options → Regex)** — регулярное выражение, отбирающее только нужные значения из результата запроса переменной (например, оставить только `pod=`.*`)`.

## Базовые концепции

### Преимущества шаблонизации

| Преимущество | Описание |
| :--- | :--- |
| **Переиспользование** | Один дашборд обслуживает множество однотипных ресурсов (кластеры, сервисы, хосты) |
| **Удобство навигации** | Быстрое переключение контекста через выпадающие списки в верхней части дашборда |
| **Автоматизация** | Динамическое создание рядов (**Rows**) и панелей (**Panels**) при появлении новых сущностей |
| **Условная логика (v11+)**| Динамическое скрытие или отображение элементов интерфейса на основе логики переменных |
| **Dashboard-as-Code** | Возможность декларативного описания переменных в JSON-модели дашборда |

### Типы переменных

| Тип | Назначение | Особенности |
| :--- | :--- | :--- |
| **Query** | Список значений, получаемый динамически из БД | Поддерживает `Regex` фильтрацию и `Multi-value` выбор |
| **Multi-property (v12+)**| Переменная-объект с набором свойств | Позволяет извлекать несколько колонок (например, `ID`, `Name`, `IP`) из одного запроса |
| **Custom** | Статический список значений | Задается вручную в формате `label : value` или просто `value` |
| **Datasource** | Переключение между источниками данных | Позволяет менять "бэкенд" дашборда (например, с Prod на Staging) |
| **Interval** | Динамический шаг времени | Используется в функциях `rate()`, `histogram_quantile()` и др. |
| **Ad hoc filters** | Глобальные фильтры по меткам | Автоматически добавляются ко всем запросам дашборда, поддерживающим данные метки |
| **Text box** | Ручной ввод текста | Полезно для поиска по ID транзакции, комментарию или части имени |
| **Constant** | Скрытая константа | Фиксация значения для использования в нескольких панелях без отображения в UI |

### Глобальные переменные системы

Grafana 11/12 предоставляет расширенный набор встроенных переменных для управления контекстом:

| Переменная | Описание |
| :--- | :--- |
| **`$__interval`** | Оптимальный шаг агрегации, вычисляемый на основе разрешения экрана и диапазона времени |
| **`$__interval_ms`** | То же самое, что и `$__interval`, но в миллисекундах |
| **`$__range`** | Текущий временной диапазон (например, `1h`, `24h`) |
| **`$__from` / `$__to`** | Начало и конец временного интервала в миллисекундах (Unix Epoch) |
| **`$__rate_interval`** | Рекомендуемый интервал для `rate()`, предотвращающий "дыры" в графиках |
| **`$__user`** | Объект пользователя (`$__user.id`, `$__user.login`, `$__user.email`) |
| **`$__dashboard`** | Метаданные (`$__dashboard.name`, `$__dashboard.uid`) |
| **`$__org`** | Идентификатор организации (`$__org.id`, `$__org.name`) |

### Синтаксис форматирования (Variable Formatting)

Для корректной подстановки значений в запросы различных типов баз данных используется синтаксис `${var_name:format}`:

| Формат | Когда использовать | Пример результата (`v1`, `v2`) |
| :--- | :--- | :--- |
| **`:regex`** | PromQL, LogQL (внутри `=~`) | `(v1|v2)` |
| **`:glob`** | Graphite | `{v1,v2}` |
| **`:csv`** | SQL (фильтр `IN`), Python | `v1,v2` |
| **`:sqlstring`**| SQL (экранирование строк) | `'v1','v2'` |
| **`:doublequote`**| JSON, API запросы | `"v1","v2"` |
| **`:pipe`** | Регулярные выражения (альтернатива) | `v1|v2` |
| **`:percentencode`**| Передача в URL-ссылках | `v1%2Cv2` |
| **`:text`** | Отображение имени (Label) переменной | Выводит "Value 1" вместо "v1" |

> **Дополнительные форматы (менее употребительные):** `:raw` — значение без преобразований; `:singlequote` — `'v1','v2'` (SQL-строки в одинарных кавычках); `:json` — массив JSON `["v1","v2"]`; `:lucene` — для Lucene-запросов; `:queryparam` — для подстановки в URL/параметры HTTP-источника; `:csv` с модификатором `${var:csv}` применяется в `IN (...)`. Форматы можно комбинировать: `${var:raw}` сохраняет спецсимволы как есть.

### Общие параметры переменной

Независимо от типа, каждая переменная имеет набор настроек, влияющих на поведение и безопасность:

| Параметр | Назначение | Рекомендация |
| :--- | :--- | :--- |
| **Name** | Внутреннее имя переменной (без пробелов, регистрозависимо) | Используйте `snake_case` или `CamelCase`; не совпадайте с именами меток/полей БД |
| **Label** | Подпись в выпадающем списке | Человекочитаемое имя (`Region` вместо `region`) |
| **Hide** | Скрытие элемента UI | `0` — показывать; `1` — показывать только метку (без выпадающего списка); `2` — скрыть полностью (для констант/скрытых переменных) |
| **Datasource (для Query)** | Источник, к которому идёт запрос переменной | Явно укажите datasource, иначе используется дефолтный дашборда |
| **Refresh** | Когда пересчитывать значения | `Never` / `On Dashboard Load` / `On Time Range Change` (см. ниже) |
| **Query Options → Sort** | Сортировка списка | `Alphabetical (asc)` — для удобства; `Disabled` — сохранить порядок из источника |
| **Query Options → Regex** | Фильтрация результатов запроса | Отбирайте только нужные сущности, снижая кардинальность |
| **Multi-value** | Разрешить несколько значений | Включайте, когда пользователю нужен выбор "нескольких" |
| **Include All option** | Добавить пункт `All` | Включайте для агрегатов; при необходимости задайте **Custom all value** |
| **Custom all value** | Что подставлять при выборе `All` | Для PromQL — `.*` (через `=~`); для Loki — `.+`; по умолчанию `$__all` |

### Расширенные глобальные переменные

Помимо перечисленных выше, Grafana предоставляет переменные для работы со временем и форматированием, полезные в запросах и заголовках:

| Переменная | Описание |
| :--- | :--- |
| **`$__timefilter`** | Готовое выражение фильтра по времени для SQL (`time BETWEEN ... AND ...`) — подставляется автоматически в SQL-источниках |
| **`$__timezone`** | Текущая временная зона дашборда (например, `Europe/Moscow`) |
| **`$__url_time_range`** | Временной диапазон в формате URL (`now-1h%20to%20now`) |
| **`$__lc` / `$__iso`** | Метки времени в форматах local/ISO, используются в заголовках и аннотациях |
| **`$__unixEpochFrom` / `$__unixEpochTo`** | Алиасы `$__from` / `$__to` в секундах (а не миллисекундах) — для источников, требующих секунды |

### JSON-модель переменной (Dashboard-as-Code)

Переменные хранятся в массиве `templating.list` JSON-модели дашборда. Это позволяет описывать их декларативно при провиженинге (см. [Провиженинг](./grafana_provisioning.md)):

```json
{
  "templating": {
    "list": [
      {
        "name": "Region",
        "type": "query",
        "label": "Region",
        "datasource": { "type": "prometheus", "uid": "prom-prod" },
        "definition": "label_values(node_info, region)",
        "query": { "query": "label_values(node_info, region)", "refId": "Region" },
        "refresh": 1,
        "sort": 1,
        "regex": "",
        "multi": false,
        "includeAll": true,
        "allValue": ".*",
        "hide": 0,
        "current": { "text": "All", "value": "$__all" }
      }
    ]
  }
}
```

Ключевые поля: `type` (`query`/`custom`/`datasource`/`interval`/`textbox`/`constant`/`adhoc`), `refresh` (`1`=On Dashboard Load, `2`=On Time Range Change, `0`=Never), `multi`/`includeAll` (boolean), `allValue` (Custom all value), `hide` (`0`/`1`/`2`). Для зависимой переменной в `query.query` достаточно сослаться на `$Region` — Grafana подставит значение перед вычислением.

### Порядок обновления и разрешение зависимостей

Переменные вычисляются **в том порядке, в котором они перечислены в `templating.list`**. Следствия:

- Зависимая переменная должна стоять **после** той, на которую ссылается (иначе `$Region` ещё не будет готов при её вычислении).
- Режим `Refresh = On Time Range Change` заставляет переменную пересчитываться при смене диапазона времени — используйте только для действительно динамических списков (например, появление новых подов), чтобы не нагружать источник.
- Режим `On Dashboard Load` (и `Never` для констант) — для относительно статичных списков.
- При смене значения в UI Grafana пересчитывает все зависимые переменные и обновляет панели.

## Практические сценарии

### Предварительные требования

Перед выполнением сценариев убедитесь, что выполнены общие условия:

- **Grafana 11+** (для условной видимости панелей) / **Grafana 12+** (для Multi-property переменных). Проверьте версию: `curl -s $GRAFANA_URL/api/health | jq -r .version` → `11.x.x` / `12.x.x`.
- **Права редактора (Editor)** или выше на дашборде, либо токен Service Account с ролью `Dashboard Editor`/`Admin` для DaC/API.
- **Источник данных** настроен и доступен (Prometheus/Loki/PostgreSQL/…). Проверьте: `curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" $GRAFANA_URL/api/datasources` → список datasources с `uid`.
- **Метрики/данные присутствуют** в источнике (для Query-переменных). Проверьте в источнике запросом, возвращающим значения переменной.
- **Переменные окружения** (для примеров с API): `GRAFANA_URL` (например, `http://localhost:3000`), `GRAFANA_TOKEN` (SA-токен).

> Примечание: шаблонные переменные **не поддерживаются в запросах алертинга (Unified Alerting)** — правила оповещений вычисляются на стороне сервера без контекста дашборда. Для алертов используйте фиксированные селекторы или recording rules (см. [Дашборды](./grafana-dashboards.md)).

### Сценарий 1: Цепочки зависимых переменных (Chaining)

Этот сценарий позволяет реализовать иерархическую фильтрацию (например: Регион → ЦОД → Стойка → Хост).

1. **Базовая переменная `Region`**:
   ```promql
   label_values(node_info, region)
   ```

2. **Зависимая переменная `Datacenter`**:
   В запросе используется значение первой переменной:
   ```promql
   label_values(node_info{region="$Region"}, datacenter)
   ```

3. **Зависимая переменная `Host`**:
   Используется оператор `=~` для поддержки множественного выбора (`Multi-value`) в предыдущих звеньях:
   ```promql
   label_values(node_info{region=~"$Region", datacenter=~"$Datacenter"}, instance)
   ```

**Настройка обновления (Refresh)**:
- **On Dashboard Load**: Для статичных данных.
- **On Time Range Change**: Если состав хостов меняется часто (динамические окружения).

**Пошаговая настройка в UI:**
1. Откройте дашборд → ⋮ (шестерёнка) → **Variables** → **Add variable** → тип `Query`.
2. `Region`: `Name=Region`, `Query=label_values(node_info, region)`, `Refresh=On Dashboard Load`, `Include All option=on`, `Custom all value=.*`.
3. `Datacenter`: `Query=label_values(node_info{region="$Region"}, datacenter)` — важно, чтобы переменная стояла **ниже** `Region` в списке.
4. `Host`: `Query=label_values(node_info{region=~"$Region", datacenter=~"$Datacenter"}, instance)`, включите `Multi-value`.
5. В панелях используйте селекторы `instance=~"$Host"`.

**Ожидаемый результат:** при выборе `Region=eu-west` список `Datacenter` содержит только ЦОД этого региона; при `All` в `Region` — `Datacenter` тоже видит `All` (через `.*`/`$__all`).

**Валидация:**
- Проверьте порядок: `curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" "$GRAFANA_URL/api/datasources/proxy/<dsId>/api/v1/label/region/values"` → список регионов.
- В UI убедитесь, что смена `Region` пересобирает `Datacenter` и `Host` (индикатор загрузки списка).

**Типичные проблемы:**
- Список `Datacenter` пуст при выборе `All` в `Region` → причина: `Region` не использует `=~` в запросе `Datacenter`. Исправление: `region=~"$Region"`.
- `Host` не обновляется → причина: переменная стоит выше зависимости в списке `templating.list`. Перенесите ниже.
- Ошибка `bad_data` в PromQL → причина: `Multi-value` в `Host` с оператором `=`. Исправление: используйте `=~` или формат `${Host:pipe}`.

### Сценарий 2: Переменные Multi-property для SQL/Infinity (v12+)

Если источник данных возвращает несколько колонок, вы можете обращаться к ним через точку:
- Запрос: `SELECT id, name, ip FROM servers`
- Доступ: `${var.id}`, `${var.name}`, `${var.ip}`.
Это избавляет от необходимости создавать три отдельные переменные и выполнять три запроса к БД.

### Сценарий 3: Использование `$__rate_interval` для точных графиков

При использовании стандартного `$__interval` в функции `rate()` на малых масштабах времени (например, просмотр за 5 минут) интервал может оказаться меньше частоты сбора метрик (scrape interval), что приведет к пустым графикам.

**Правильный подход в PromQL:**
```promql
sum(rate(http_requests_total{instance=~"$Host"}[$__rate_interval])) by (status)
```
`$__rate_interval` гарантирует, что в окно расчета попадет как минимум две точки (Scrape Interval + Resolution), что делает графики стабильными при любом зуме.

### Сценарий 4: Динамическое скрытие панелей (Visibility)

В Grafana 11+ можно управлять видимостью панелей на основе значения переменной.
- Создайте переменную `show_advanced` (тип `Custom`, значения `true, false`).
- В настройках панели (раздел **Visibility**) укажите условие: `$show_advanced == 'true'`.
- Панель будет появляться только тогда, когда пользователь выберет соответствующий режим.

**Пошагово:** `Variables` → `Add variable` → `Custom`, `Name=show_advanced`, `Values=true,false`, `Hide=0`. Откройте нужную панель → `Panel options` → `Visibility` → `Show this panel only when` → введите `$show_advanced == 'true'`. Можно комбинировать через `&&`/`||` (например, `$env == 'prod' && $show_advanced == 'true'`).

**Валидация:** переключите `show_advanced` в `false` — панель исчезает из дашборда; в `true` — появляется. Условие поддерживает сравнение строк в одинарных кавычках и чисел без кавычек.

### Сценарий 5: Переключение источника данных (Datasource variable)

Позволяет одним дашбордом переключаться между окружениями (Prod/Staging) или бэкендами (Prometheus/Loki), не дублируя панели.

1. `Variables` → `Add variable` → тип `Datasource`.
2. `Name=ds`, `Label=Datasource`, `Type=Prometheus` (отфильровать только нужный тип) или оставить все.
3. В запросах панелей вместо жёстко заданного источника выберите `${ds}` (в редакторе панели — поле **Data source** → `${ds}`).
4. (Опционально) включите `Include All` — тогда `${ds}` не подставится напрямую; используйте `=~` или конкретный выбор.

**Пример запроса PromQL с datasource-переменной:**
```promql
sum(rate(http_requests_total{job=~"$job"}[$__rate_interval])) by (status)
```
Здесь источник выбран через `${ds}`, а фильтр — через обычную переменную `$job`.

**Валидация:** смена `ds` в выпадающем списке пересобирает все панели с этим источником. Проверьте, что оба datasource содержат одинаковые метрики/поля, иначе часть панелей вернёт `No data`.

**Типичная проблема:** ошибка `datasource ${ds} not found` → причина: переменная `Include All` включена и выбран `All`. Исправление: отключите `Include All` для datasource-переменной или используйте `=~`.

### Сценарий 6: Ad hoc filters (глобальные фильтры по меткам)

Автоматически добавляют фильтры ко всем запросам дашборда к совместимому источнику, без явной переменной в каждом запросе.

1. `Variables` → `Add variable` → тип `Ad hoc filters`.
2. `Name=filters`, `Datasource` — укажите целевой источник (например, Prometheus `prom-prod`).
3. Вверху дашборда появится блок фильтров: выберите метку (`namespace`), оператор (`=`, `=~`, `!=`) и значение (`prod`).
4. Все панели, чьи запросы идут к этому источнику, получат условие `namespace="prod"` автоматически.

**Пример (Loki/LogQL):** ad hoc фильтр `cluster=~"prod-.*"` добавится к каждому запросу как строковый фильтр `| json | cluster=~"prod-.*"`.

**Валидация:** добавьте фильтр `status="500"` — панели пересобираются только с этими значениями. Фильтры применяются только к запросам того же источника, что указан в переменной.

**Ограничение:** ad hoc фильтры поддерживаются не всеми источниками (Prometheus, Loki, Elasticsearch, PostgreSQL и др.); для неподдерживаемых источников используйте обычные Query-переменные.

### Сценарий 7: Переменная Interval (ручной выбор шага агрегации)

Полезна, когда автоматический `$__interval` даёт слишком детальный или слишком укрупнённый шаг для конкретной панели.

1. `Variables` → `Add variable` → тип `Interval`.
2. `Name=myinterval`, `Values=30s,1m,5m,1h,1d` (через запятую; `auto` добавляется автоматически).
3. В запросе используйте `$myinterval` вместо `$__interval`:
```promql
sum(rate(http_requests_total{instance=~"$Host"}[$myinterval])) by (status)
```

**Валидация:** выбор `5m` в выпадающем списке укрупняет график (меньше точек). При `auto` Grafana выбирает шаг по разрешению и диапазону.

**Типичная проблема:** график «плывет»/странный — причина: диапазон меньше выбранного интервала. Исправление: добавьте `auto` и используйте его по умолчанию или уменьшите `Values`.

### Сценарий 8: Text box — поиск по ID/строке

Тип `Text box` даёт свободный ввод без выпадающего списка (поиск транзакции, части имени, trace-id).

1. `Variables` → `Add variable` → тип `Text box`.
2. `Name=trace_id`, `Label=Trace ID`, `Default value=` (пусто или пример `abc123`).
3. В запросе Loki:
```logql
{app="checkout"} | json | traceId=~"$trace_id"
```
При пустом значении условие сработает как «все» (если реализовано через опциональный фильтр), иначе отфильтрует по введённой подстроке.

**Безопасность:** экранируйте спецсимволы ввода. Для regex-источников используйте формат `${trace_id:regex}`, чтобы избежать `bad_data` при вводе `(`, `[` и т.п.

**Валидация:** введите `abc` — панель показывает только строки с `abc` в `traceId`. Очистка поля возвращает все строки (при корректной реализации фильтра).

### Сценарий 9: Кастомное значение «All» и регулярка

При `Include All option` по умолчанию Grafana подставляет `$__all` — токен, который в зависимости от контекста раскрывается в список всех значений. Для PromQL это часто нужно заменить на `.*`.

- Переменная `Host` (`Multi-value` + `Include All`), `Custom all value=.*`.
- В запросе: `instance=~"$Host"`. При выборе `All` подставляется `instance=~".*"` → все инстансы.
- Для Loki аналогично: `Custom all value=.+`.

**Почему `.*`, а не список:** для источников без原生 поддержки `$__all` (например, старые PostgreSQL) явная регулярка надёжнее и избегает проблем с кавычками. Для Grafana-native datasource `Custom all value` можно оставить пустым (тогда используется `$__all`).

**Валидация:** выберите `All` → запрос выполняется без ошибок и возвращает агрегат по всем значениям. Проверьте `curl` к источнику с подставленным `.*`.

### Сценарий 10: Dashboard-as-Code — переменная в JSON-модели

Переменные удобно версионировать в Git вместе с дашбордом (см. [Провиженинг](./grafana_provisioning.md) и [Дашборды как код](./grafana-dashboards.md)).

Пример описания зависимой переменной `Datacenter` в `dashboard.json` (фрагмент `templating.list`):

```json
{
  "name": "Datacenter",
  "type": "query",
  "label": "Datacenter",
  "datasource": { "type": "prometheus", "uid": "prom-prod" },
  "query": { "query": "label_values(node_info{region=~\"$Region\"}, datacenter)", "refId": "Datacenter" },
  "refresh": 1,
  "sort": 1,
  "multi": true,
  "includeAll": true,
  "allValue": ".*",
  "hide": 0
}
```

**Пошагово (провиженинг через API):**
1. Подготовьте `dashboard.json` с нужным `templating.list`.
2. Загрузите дашборд (см. Сценарий HTTP API в [Дашборды](./grafana-dashboards.md)):
```bash
curl -X POST "$GRAFANA_URL/api/dashboards/db" \
  -H "Authorization: Bearer $GRAFANA_TOKEN" \
  -H "Content-Type: application/json" \
  -d @dashboard.json
# → {"status":"success","uid":"...","url":"..."}
```
3. Откройте дашборд в UI — переменные уже настроены и работают.

**Валидация:** после загрузки откройте Variables в дашборде — список совпадает с `templating.list`. Изменение JSON и повторная загрузка обновляет переменные (при `version`+1 в метаданных дашборда).

## Дополнительная информация

### Рекомендации (Best Practices)

1. **Оператор `=~` vs `=`**: Всегда используйте `=~ "$var"`, если для переменной включена опция **Multi-value** или **Include All**. Обычное равенство `=` вызовет ошибку при выборе более одного значения.
2. **Scrubbing (Очистка)**: Если в именах переменных или их значениях могут быть спецсимволы, используйте форматирование `:regex` или `:sqlstring`.
3. **Ограничение выборки**: Не создавайте переменные, возвращающие более 1000 значений (например, `ID` каждой транзакции). Это перегружает браузер и источник данных. Используйте `Text box` для поиска конкретных ID.
4. **Тип Refresh**: Используйте `Never` или `On Dashboard Load` для констант. `On Time Range Change` — только если данные действительно зависят от времени.

### Типичные ошибки

- **Кардинальность**: Запрос `label_values({__name__=~".*"}, pod)` без фильтра по `job` или `namespace` может "уронить" Prometheus при большом количестве метрик.
- **Конфликт имен**: Называйте переменные с большой буквы или используйте префиксы (например, `var_Host`), чтобы не перепутать их с именами полей в SQL или метками в PromQL.
- **Отсутствие "All"**: Если опция `Include All` выключена, а пользователь хочет видеть агрегат по всем сущностям, дашборд может стать неудобным.

### Устранение неполадок

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| **No data** во всех панелях после выбора переменной | Несовпадение значения переменной с метками источника | Проверьте точное совпадение (`$Host` = `instance`); используйте `=~` для частичного совпадения |
| **`bad_data: ... unexpected token`** в PromQL | `Multi-value`/`All` с оператором `=` | Замените `=` на `=~` или примените формат `${var:pipe}`/`${var:csv}` |
| Список зависимой переменной пуст | Переменная стоит **выше** зависимости в `templating.list` | Перенесите зависимую переменную ниже в списке |
| `datasource ${ds} not found` | `Include All` включён для datasource-переменной | Отключите `Include All` или используйте `=~` в запросах |
| Регулярка в `Query Options → Regex` не фильтрует | Неправильный синтаксис / захват не той группы | Проверьте regex отдельно; для извлечения значения используйте группу захвата, например `pod="([^"]+)"` |
| Переменная не обновляется при смене времени | `Refresh = Never`/`On Dashboard Load` | Установите `On Time Range Change`, если список зависит от времени |
| Ad hoc фильтр не применяется | Источник панели отличается от источника переменной | Назначьте переменной тот же datasource, что у панелей |
| `All` возвращает пустой результат | `Custom all value` не задан для non-native источника | Укажите `.*` (PromQL) / `.+` (Loki) в `Custom all value` |
| Высокая нагрузка на источник | Переменная возвращает тысячи значений | Ограничьте `Regex`-фильтром; используйте `Text box` для поиска конкретных ID |
| Скрытая переменная не подставляется | `Hide=2`, но имя не совпадает в запросе | Проверьте `Name` (регистрозависимо) и наличие `$` в запросе |

### Ограничения и особые случаи

- **Алертинг не поддерживает переменные:** правила Unified Alerting вычисляются сервером без контекста дашборда, поэтому `$Host`, `$Region` и прочие template-переменные в запросах алертов недопустимы. Используйте фиксированные селекторы или recording rules. Исключение — переменные в **аннотациях/сообщениях** алерта (там допустимы built-in, например `{{ $labels.instance }}` — это уже шаблоны сообщений, а не dashboard-переменные).
- **Цепочка зависимостей ограничена порядком:** Grafana не разрешает циклические зависимости; зависимая переменная должна быть ниже в списке.
- **Кардинальность:** переменные, возвращающие >1000 значений, перегружают UI и источник. Ограничивайте выборку `Regex` или переходите на `Text box`.
- **`Custom all value` и кавычки:** для SQL-источников при `All` используйте `:sqlstring` или задайте `Custom all value` как список с кавычками, иначе получите SQL-ошибку.
- **Скрытые переменные (`Hide=2`):** удобны для констант, но их нельзя изменить из UI — значение берётся из JSON/провиженинга.
- **Legacy Angular:** старые дашборды на Angular могут использовать устаревший синтаксис переменных; при миграции на React проверьте совместимость (Angular EOL в Grafana 11).
- **Переменные в заголовках/аннотациях:** поддерживаются (например, заголовок панели `Статус $Host`), но не во всех типах аннотаций.
- **Передача через URL:** значения переменных можно задать в ссылке (`?var-Region=eu-west&var-Host=node1`) — удобно для переходов извне и дашбордов верхнего уровня.

Подробная информация о синтаксисе переменных доступна в [документации Grafana](https://grafana.com/docs/grafana/latest/dashboards/variables/).
