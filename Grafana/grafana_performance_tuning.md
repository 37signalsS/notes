# Производительность и тюнинг Grafana

**Актуально для:** Grafana 13.2.x (актуальная линия) / 12.4.x (LTS); 11.x — EOL (25 июня 2026). Облачные и ИИ-функции не рассматриваются; кэширование запросов к источникам — функция Grafana Enterprise/Cloud, это отмечено отдельно.

## Определения

- **Query and resource caching** — кэширование результатов запросов к источникам данных и resource-запросов (HTTP-запросы backend-плагинов) на стороне Grafana. Механизм доступен в **Grafana Enterprise и Grafana Cloud**; глобально включается в секции `[caching]`, TTL задаётся индивидуально для каждого источника данных.
- **`remote_cache`** — отдельный кэш временных данных, связанных с аутентификацией (токены). Не влияет на запросы дашбордов. Секция `[remote_cache]`.
- **`versions_to_keep`** — лимит хранимой истории версий дашбордов (на один дашборд, ключ `[dashboards] versions_to_keep`). Определяет размер таблицы `dashboard_version` и, как следствие, объём БД, скорость дампа и миграций.
- **`concurrent_query_limit`** — число запросов, выполняемых одновременно в панели со смешанными источниками данных. Секция `[query]`.
- **query timeout** — максимальное время ожидания ответа источника данных до таймаута. Ключ `[dataproxy] timeout` (по умолчанию `30` с).
- **Rendering (рендеринг)** — генерация изображения дашборда/панели для алертов, снимков и отчётов; выполняется внешним сервисом `grafana-image-renderer`.
- **pprof** — встроенный профайлер Go-рантайма. В Grafana включается флагом `-profile`, слушает отдельный адрес/порт (по умолчанию `localhost:6060`) и отдаёт эндпоинты `/debug/pprof/*`.
- **GOGC / GOMEMLIMIT** — переменные окружения Go-рантайма, управляющие частотой сборки мусора и «мягким» лимитом памяти процесса Grafana (не специфичны для Grafana).

## Базовые концепции

### Три группы факторов

Производительность Grafana определяется тремя группами факторов:

1. **Нагрузка на источники данных.** Тяжёлые дашборды с десятками панелей бьют запросами по Prometheus/Loki/БД. Кэширование запросов и оптимизация самих запросов — главный рычаг.
2. **Размер состояния в БД.** История версий дашбордов, аннотации и сессии раздувают БД; это замедляет миграции, бэкап и старт.
3. **Ресурсы процесса Grafana.** CPU/память для рендеринга панелей (особенно таблиц/heatmap с большими объёмами точек) и параллельной загрузки дашбордов.

### Независимые механизмы кэширования

Grafana использует несколько независимых кэшей, которые настраиваются разными секциями и не взаимозаменяемы (полный разбор — в [Обзор Grafana](grafana_overview.md), раздел «Кэширование»):

- **Query and resource caching** (`[caching]`) — кэш результатов запросов к backend-источникам. Enterprise/Cloud.
- **remote_cache** (`[remote_cache]`) — кэш токенов аутентификации; на дашборды не влияет.
- **Сессии пользователей** — всегда хранятся в основной БД и не выносятся в эти кэши.

### Интервал панели и вероятность попадания в кэш

Кэш запросов даёт выигрыш не всегда, а в зависимости от «интервала» панели. Интервал вычисляется как `диапазон времени / max data points`; он определяет, насколько близко запросы разных пользователей округляются к одному кэшированному диапазону:

- **широкие панели и короткие диапазоны времени** — запрашивают свежие данные чаще, попаданий в кэш меньше;
- **узкие панели и длинные диапазоны** — запрашивают реже, кэш обслуживает панель вплоть до `TTL` (обычно порядка интервала).

Практический вывод: увеличение **Max data points** панели повышает интервал и вероятность попадания в кэш; для дашбордов реального времени (`refresh = 5s`, свежие данные) кэш даёт мало выигрыша и добавляет задержку свежести.

### Куда уходит время, помимо запросов

Кроме запросов к источникам, время загрузки дашборда расходуется на: чтение состояния из БД (история версий, аннотации), рендеринг изображений (Chromium, если используются алерты со снимками/отчёты) и построение панелей в браузере (`maxDataPoints`).

## Практические сценарии

### Предварительные требования

- Доступ к `grafana.ini` (или переменным окружения `GF_*`) и права перезапуска Grafana.
- Метрики Grafana (`/metrics`) и логи доступны для оценки (см. [Диагностика и устранение неполадок](grafana_troubleshooting.md)).
- Для кэширования запросов — лицензия Grafana Enterprise или Grafana Cloud.
- Понимание паттерна чтения дашбордов (сколько зрителей, как часто меняются данные).

### Сценарий 1. Кэширование запросов к источникам (Grafana Enterprise/Cloud)

Глобальные настройки в `grafana.ini`:

```ini
[caching]
# Включить механизм кэширования (по умолчанию true)
enabled = true
# Бэкенд хранения: memory (по умолчанию), redis, memcached.
# В production рекомендуется redis/memcached — in-memory растёт вместе с памятью процесса
backend = redis
# TTL по умолчанию, когда он не задан в источнике (по умолчанию 1m)
ttl = 1m
# Жёсткий верхний предел TTL (по умолчанию 0s — без ограничения)
max_ttl = 10m
# Не кэшировать результат больше этого размера, МБ (по умолчанию 1)
max_value_mb = 10

[caching.redis]
url = redis://localhost:6379
prefix = grafana
```

Через переменные окружения:

```bash
export GF_CACHING_ENABLED=true
export GF_CACHING_BACKEND=redis
export GF_CACHING_TTL=1m
```

> `[caching] enabled = true` включает сам механизм, но **не** включает кэш ни для одного источника. Кэш включается отдельно для каждого источника данных.

**Включение для источника:** Connections → Data source → вкладка **Cache** → **Enable** → (опционально) свой TTL для запросов и resource-запросов.
**Переопределение для панели:** Edit panel → **Query options** → **Cache TTL** (в миллисекундах).
**Очистка кэша:** Cache → **Clear cache** (затрагивает все источники; для Memcached очищается всё хранилище).
**Обход кэша при отладке:** запрос с заголовком `X-Cache-Skip` не ищет результат в кэше.

Если после включения `[caching]` вкладка **Cache** в настройках источника отсутствует — значит, кэширование для этого типа источника не поддерживается.

### Сценарий 2. Размер БД: история версий дашбордов и интервал обновления

```ini
[dashboards]
# Сколько версий каждого дашборда хранить (по умолчанию 20, минимум 1)
versions_to_keep = 10
# Минимальный интервал автообновления дашборда (по умолчанию 5s; ограничивает и Explore)
min_refresh_interval = 30s
# Предзагрузка панелей при открытии дашборда (по умолчанию false — ленивая загрузка)
default_preload = false
```

`versions_to_keep` ограничивает объём таблицы `dashboard_version`; старые версии вытесняются по мере сохранения новых. Раздутая история напрямую замедляет апгрейд и бэкап (см. [Резервное копирование и восстановление](grafana_backup_restore.md) и [Обновление и миграция](grafana_upgrade_migration.md)).

Оценка объёма истории:

```bash
# PostgreSQL
psql -U grafana -c "SELECT count(*) FROM dashboard_version;"
# MySQL
mysql -u grafana -p -e "SELECT count(*) FROM grafana.dashboard_version;"
# → число строк; большое значение при малом числе дашбордов указывает на раздутую историю
```

`min_refresh_interval` не даёт пользователям выставить `refresh` ниже порога (частые автообновления — один из основных источников постоянной нагрузки на источники). `default_preload = false` сохраняет ленивую загрузку панелей, снижая одновременную нагрузку при открытии больших дашбордов.

### Сценарий 3. Параллелизм, таймауты и пул соединений к источникам

```ini
[query]
# Одновременно выполняемые запросы в панели со смешанными источниками
# (по умолчанию — число CPU)
concurrent_query_limit = 8

[dataproxy]
# Таймаут запроса к источнику, сек (по умолчанию 30)
timeout = 30
# Лимит соединений на хост, включая active/idle (0 — без лимита, по умолчанию 0)
max_conns_per_host = 0
# Максимум idle-соединений к источникам (по умолчанию 100)
max_idle_connections = 100
# Таймаут простоя соединения, сек (по умолчанию 90)
idle_conn_timeout_seconds = 90
# Лимит строк, обрабатываемых из SQL-источников (по умолчанию 1000000)
row_limit = 1000000
```

Особенности:

- `[dataproxy] timeout` применяется к core-источникам, использующим backend HTTP-клиент; для отдельных источников таймаут может задаваться в их настройках (см. [Источники данных](grafana_datasources.md)). Симптом превышения — `context deadline exceeded` на тяжёлых панелях.
- `concurrent_query_limit` ограничивает «взрыв» параллельных запросов при открытии панели со смешанными источниками; снижение значения уменьшает пиковую нагрузку на источники и процесс.
- `row_limit` защищает процесс Grafana от вычитывания гигантских результатов SQL-запросов.

> Раньше в примерах этой темы встречался ключ `[datasources] timeout` — такого ключа в Grafana нет. Таймаут запроса задаётся в `[dataproxy] timeout`.

```bash
# Проверка действующих значений
curl -s http://localhost:3000/metrics | grep -E "grafana_http_request_duration|process_resident_memory_bytes|go_goroutines"
```

### Сценарий 4. Пул соединений с базой данных Grafana

Число соединений процесса Grafana с собственной СУБД задаётся в `[database]`: `max_open_conn`, `max_idle_conn`, `conn_max_lifetime`. Это не пул к источникам данных из Сценария 3, а пул к базе состояния Grafana.

Настройка и правило расчёта `(replicas × max_open_conn) < 0.8 × max_connections СУБД` описаны в [Высокая доступность и отказоустойчивость](high_availability.md) — это SSoT по пулам соединений.

### Сценарий 5. Ресурсы процесса, сборка мусора и профайлер

Для Docker — лимиты в `docker-compose.yml`:

```yaml
services:
  grafana:
    image: grafana/grafana:13.2.3
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 2G
    environment:
      - GF_DATAPROXY_TIMEOUT=30
```

Для systemd — лимиты в unit-файле (`MemoryMax=`/`CPUQuota=` из `systemd.resource-control`).

Grafana — Go-приложение, поэтому память процесса регулируется также переменными Go-рантайма:

- `GOGC` — целевой процент роста кучи между сборками мусора (по умолчанию `100`); меньшее значение = чаще GC, ниже потребление памяти, выше CPU.
- `GOMEMLIMIT` — «мягкий» лимит памяти процесса (например, `GOMEMLIMIT=1800MiB` при лимите контейнера `2G`). Заставляет GC работать активнее при приближении к лимиту и предотвращает OOMKilled. Это настройка рантайма Go, а не Grafana, — применяйте с осторожностью и проверяйте под нагрузкой.

Проверка — метрики процесса в `/metrics` (`process_resident_memory_bytes`, `go_goroutines`, `go_gc_duration_seconds`).

Профайлер включается только временно для диагностики (узких мест CPU, утечек, блокировок):

```bash
# Включить профайлер. pprof слушает ОТДЕЛЬНЫЙ порт (по умолчанию 6060),
# адрес по умолчанию localhost; это не порт Grafana 3000
grafana server -profile -profile-addr=127.0.0.1 -profile-port=6060

# Те же настройки через переменные окружения
export GF_DIAGNOSTICS_PROFILING_ENABLED=true
export GF_DIAGNOSTICS_PROFILING_PORT=6060

# Снять CPU-профиль за 30 секунд
curl -s "http://localhost:6060/debug/pprof/profile?seconds=30" -o cpu.prof
# → файл cpu.prof для анализа: go tool pprof -http=:8081 cpu.prof

# Профили памяти и горутин
curl -s "http://localhost:6060/debug/pprof/heap"      -o heap.prof
curl -s "http://localhost:6060/debug/pprof/goroutine" -o goroutine.prof
```

Дополнительно: `-profile-block-rate` (доля событий блокировки горутин в профиле, по умолчанию `1`) и `-profile-mutex-rate` (доля событий конкуренции мьютексов, по умолчанию `0`); соответствующие env — `GF_DIAGNOSTICS_PROFILING_BLOCK_RATE`, `GF_DIAGNOSTICS_PROFILING_MUTEX_RATE`.

### Сценарий 6. Оптимизация дашбордов и запросов

- Уменьшите число панелей и интервал опроса (`refresh`) для широких дашбордов; при возможности поднимите `min_refresh_interval`.
- Используйте агрегации в источнике (PromQL `rate()`/`sum()`, LogQL `|=` фильтры как можно раньше), а не «вытягивайте сырьё» — см. [Оптимизация PromQL-запросов](../Prometheus/concepts/promql/optimization.md).
- Ограничьте `maxDataPoints` панелей (определение — в [Дашборды](grafana-dashboards.md)), чтобы не запрашивать и не рендерить лишние точки.
- Избегайте повторяющихся запросов: выносите общие запросы в повторяющиеся строки и переменные шаблонов.
- Отдавайте предпочтение источникам, которые кэшируют сами (Elasticsearch, Prometheus, Loki), — для них выигрыш от *query* caching Grafana невелик, но *resource* caching может помочь.

### Сценарий 7. Рендеринг изображений

Рендеринг выполняется внешним сервисом `grafana-image-renderer` (headless Chromium) и прожорлив по памяти — его выносят в отдельный процесс/под, чтобы не расходовать память основного процесса Grafana:

```ini
[rendering]
# Лимит одновременных запросов на рендеринг (по умолчанию 30)
concurrent_render_request_limit = 20
```

Развёртывание и тюнинг рендерера — в [Рендеринг изображений](grafana_image_rendering.md); таймауты отчётов и снимков — в [Отчёты](grafana_reporting.md).

## Дополнительная информация

### Рекомендации по эксплуатации

- Включайте query caching (Enterprise/Cloud) для дашбордов с большим числом зрителей и редко меняющимися данными; TTL начните с `1m`–`10m`. В production используйте бэкенд Redis/Memcached, а не in-memory.
- Держите `versions_to_keep` умеренным, чтобы БД не раздувалась, а миграции и бэкапы оставались быстрыми.
- Задайте `min_refresh_interval`, чтобы ограничить частые автообновления дашбордов.
- Подбирайте `concurrent_query_limit` и лимиты `[dataproxy]` так, чтобы панели со смешанными источниками не устраивали «шторм» запросов.
- Выделяйте Grafana 1–2 vCPU и 1–2 ГБ RAM на инстанс средней нагрузки; горизонтально масштабируйте в HA (см. [Высокая доступность и отказоустойчивость](high_availability.md)).
- Мониторьте метрики самой Grafana (`/metrics`) — это единственный способ увидеть регрессию до жалоб пользователей.
- Рендеринг изображений выносите во внешний `grafana-image-renderer` (отдельный сервис/под).

### Типичные ошибки и их решение

| Симптом | Причина | Решение |
| --- | --- | --- |
| Высокая нагрузка на Prometheus при массовом открытии дашборда | Кэш не включён для источника | Включить механизм `[caching]` и кэш на вкладке Cache источника (Enterprise/Cloud), подобрать TTL |
| Настройка `[datasources] timeout` не действует | Такого ключа нет | Задать таймаут в `[dataproxy] timeout` |
| Медленный бэкап/старт, огромная БД | Раздутая `dashboard_version` | Уменьшить `versions_to_keep`, ограничить частоту сохранений |
| `context deadline exceeded` при загрузке дашборда | Таймаут источника/слишком тяжёлый запрос | Увеличить `[dataproxy] timeout`, оптимизировать запрос |
| Панель тормозит, но БД отвечает быстро | Слишком много точек | Ограничить `maxDataPoints`, агрегировать в источнике |
| OOM Grafana | Рендеринг тяжёлых панелей в том же процессе | Вынести `grafana-image-renderer` отдельно, задать `GOMEMLIMIT` |
| `pprof` недоступен | Профайлер не включён либо слушает другой адрес | Запустить с `-profile`; порт `6060`, адрес по умолчанию `localhost` |

### Ограничения и особые случаи

- Query and resource caching доступно только в Grafana Enterprise и Grafana Cloud; в OSS механизма нет. Кэш работает не для всех источников — критерий — наличие вкладки **Cache** в настройках источника.
- Кэш малоэффективен для дашбордов реального времени (`refresh = 5s`, свежие данные) и заметно теряет пользу для источников с собственным кэшированием (Prometheus, Loki, Elasticsearch).
- In-memory бэкенд увеличивает footprint процесса Grafana; в production используйте Redis или Memcached.
- Профайлер (`/debug/pprof`) раскрывает внутреннюю статистику процесса — держите его выключенным в публичном контуре, привязывайте к `localhost` (`-profile-addr`).
- `GOGC`/`GOMEMLIMIT` — настройки Go-рантайма; их влияние зависит от нагрузки и версии рантайма, проверяйте эмпирически.
- Рендеринг изображений требует `grafana-image-renderer`; без него алерты со снимками и отчёты не содержат графиков.

### Очистка и откат изменений

- Перед изменением `grafana.ini` сохраните его копию.
- Откат кэша: `[caching] enabled = false` и перезапуск; либо очистка через вкладку **Clear cache** источника. При смене бэкенда (например, memory → redis) старый кэш не переносится.
- Профайлер отключается перезапуском Grafana без флага `-profile` (или снятием `GF_DIAGNOSTICS_PROFILING_ENABLED`).
- После понижения `versions_to_keep` освобождение места происходит по мере вытеснения старых версий; для немедленного сокращения БД см. [Резервное копирование и восстановление](grafana_backup_restore.md).
