# Производительность и тюнинг Grafana

Практическое руководство по настройке производительности self-hosted Grafana. Версии: 13.x актуальная, 12.x LTS, 11.x — EOL (июнь 2026). Облачные и ИИ-функции не рассматриваются.

## Определения

- **Dashboard query caching** — кэширование результатов запросов дашборда на стороне Grafana (появилось в 11.x), снижает нагрузку на источники данных при одновременном просмотре одного дашборда многими пользователями.
- **dashboard_versions_to_keep** — лимит хранимой истории версий дашбордов в БД; влияет на размер БД и скорость её дампа/восстановления.
- **concurrent_dashboard** — число дашбордов, загружаемых параллельно при старте/провиженинге.
- **query timeout** — максимальное время выполнения запроса к источнику данных до отмены.
- **Rendering (рендеринг)** — генерация изображения дашборда/панели для алертов, снимков и отчётов; выполняется внешним сервисом `grafana-image-renderer`.
- **--profile** — встроенный HTTP-профайлер Grafana для диагностики CPU/памяти/блокировок.

## Базовые концепции

Производительность Grafana определяется тремя группами факторов:

1. **Нагрузка на источники данных.** Тяжёлые дашборды с десятками панелей бьют запросами по Prometheus/Loki/БД. Кэширование запросов и оптимизация самих запросов — главный рычаг.
2. **Размер состояния в БД.** История версий дашбордов, аннотации и сессии раздувают БД; это замедляет миграции, бэкап и старт.
3. **Ресурсы процесса Grafana.** CPU/память для рендеринга панелей (особенно таблиц/heatmap с большими объёмами точек) и параллельной загрузки дашбордов.

Кэш запросов полезен преимущественно при «широком» чтении одного дашборда (много зрителей, редко меняющиеся данные). Для дашбордов реального времени кэш даёт меньше выигрыша и добавляет задержку свежести (`TTL`).

## Практические сценарии

### Предварительные требования

- Доступ к `grafana.ini` и (желательно) переменным окружения `GF_*`.
- Версия Grafana 11.x+ для dashboard query caching.
- Метрики Grafana (`/metrics`) и логи доступны для оценки (см. связанные темы по диагностике).
- Понимание паттерна чтения дашбордов (сколько зрителей, как часто данные меняются).

### Сценарий 1. Включение кэширования запросов дашборда (11.x+)

```ini
[unified_alerting]
# не связано напрямую, но в одном блоке часто правят таймауты

[caching]
# Включить кэш запросов дашборда
dashboard_cache_enabled = true
# TTL кэша в секундах (баланс между свежестью и нагрузкой)
dashboard_cache_ttl_seconds = 30
```

Через переменные окружения:

```bash
export GF_CACHING_DASHBOARD_CACHE_ENABLED=true
export GF_CACHING_DASHBOARD_CACHE_TTL_SECONDS=30
```

Проверка — в ответе запроса дашборда появляется заголовок `X-Grafana-Cache` (например, `HIT`/`MISS`), и нагрузка на источник данных падает при повторных открытиях:

```bash
curl -sI "https://grafana.example.internal/api/ds/query" -H "Authorization: Bearer $TOKEN" | grep -i "x-grafana-cache"
# → x-grafana-cache: HIT  (при повторном запросе в окне TTL)
```

### Сценарий 2. Ограничение истории версий дашбордов

```ini
[dashboards]
# Сколько версий хранить на дашборд (0 = без лимита; рекомендуется 10–20)
versions_to_keep = 20
```

Снижает объём БД и ускоряет бэкап/восстановление (см. связанные темы). Проверка объёма таблицы:

```bash
mysql -u grafana -p grafana -e "SELECT COUNT(*) FROM dashboard_version;"
# → число строк; при росте — уменьшить versions_to_keep и очистить старые
```

### Сценарий 3. Лимиты параллельной загрузки и таймауты

```ini
[server]
# Сколько дашбордов грузить параллельно при старте/провиженинге
concurrent_dashboard = 10

[datasources]
# Таймаут запроса к источнику данных (сек)
timeout = 30
```

Для источников с медленными БД увеличьте `timeout`, но контролируйте нагрузку. Проверка — Grafana стартует без `context deadline exceeded` на тяжёлых дашбордах.

### Сценарий 4. Выделение ресурсов процессу

Для Docker — лимиты в `docker-compose.yml`:

```yaml
services:
  grafana:
    image: grafana:13.2.3
    deploy:
      resources:
        limits:
          cpus: "2.0"
          memory: 2G
    environment:
      - GF_SERVER_CONCURRENT_DASHBOARD=10
```

Для systemd — через `MemoryLimit=`/`CPUQuota=` в unit-файле. Проверка — метрики процесса в Grafana `/metrics` (`process_resident_memory_bytes`, `go_goroutines`) стабильны под нагрузкой.

### Сценарий 5. Профилирование (диагностика утечек/тормозов)

```bash
# Включить профайлер (только временно, не в проде постоянно!)
GF_DIAGNOSTICS_PROFILING_ENABLED=true grafana-server
# или section [profiling] enabled = true

# Снять CPU-профиль
curl -s http://localhost:3000/debug/pprof/profile?seconds=30 -o cpu.prof
# → файл cpu.prof для анализа (go tool pprof cpu.prof)
```

Проверка: `go tool pprof cpu.prof` открывает интерактивный анализ; ищите неожиданные потребители CPU.

### Сценарий 6. Оптимизация дашбордов как запросов

- Уменьшите число панелей и интервал опроса (`refresh`) для широких дашбордов.
- Используйте агрегации в источнике (PromQL `rate()`/`sum()`, LogQL `|=` фильтры как можно раньше), а не «вытягивать сырьё».
- Ограничьте `maxDataPoints` панелей, чтобы не рендерить лишние точки.
- Избегайте повторяющихся запросов: выносите общие запросы в повторяющиеся строки/переменные.

## Дополнительная информация

### Рекомендации по эксплуатации

- Включайте dashboard query caching для дашбордов с большим числом зрителей и редко меняющимися данными; TTL 30–60 с — разумный старт.
- Держите `versions_to_keep` ограниченным (10–20), чтобы БД не раздувалась.
- Выделяйте Grafana 1–2 vCPU и 1–2 ГБ RAM на инстанс средней нагрузки; масштабируйте горизонтально в HA.
- Мониторьте метрики самой Grafana (`/metrics`) — это единственный способ увидеть регрессию до жалоб пользователей.
- Рендеринг изображений выносите во внешний `grafana-image-renderer` (отдельный сервис/под), чтобы не «съедал» память основного процесса (см. связанные темы).

### Типичные ошибки и их решение

| Симптом | Причина | Решение |
| --- | --- | --- |
| Высокая нагрузка на Prometheus при массовом открытии дашборда | Нет кэша запросов | Включить `dashboard_cache_enabled`, подобрать TTL |
| Медленный бэкап/старт, огромная БД | Раздутая `dashboard_version` | Уменьшить `versions_to_keep`, очистить старые версии |
| `context deadline exceeded` при загрузке дашборда | Таймаут источника/слишком тяжёлый запрос | Увеличить `timeout`, оптимизировать запрос |
| OOM Grafana | Рендеринг тяжёлых панелей в том же процессе | Вынести `grafana-image-renderer` отдельно |
| Дашборд «тормозит», но БД отвечает быстро | Слишком много точек/`maxDataPoints` | Ограничить `maxDataPoints`, агрегировать раньше |
| Профайлер недоступен | Не включён `[profiling]` | Включить временно, НЕ держать в проде постоянно |

### Ограничения и особые случаи

- Dashboard query caching появилось в 11.x; на 10.x и старее недоступно.
- Кэш бесполезен для дашбордов реального времени с `refresh=5s` и свежими данными — добавляет лишь задержку.
- Профайлер (`/debug/pprof`) раскрывает внутреннюю статистику — держите его выключенным в публичном контуре.
- Рендеринг изображений требует `grafana-image-renderer`; без него алерты/снимки не содержат графиков.

### Очистка и откат изменений

- После тюнинга сохраните предыдущий `grafana.ini`.
- Отключите профайлер сразу после диагностики (`[profiling] enabled = false`).
- Откат кэша: `dashboard_cache_enabled = false` и перезапуск; ранее закэшированные данные сбросятся.

### Актуальность и статус

Dashboard query caching и связанные параметры актуальны для 11.x/12.x/13.x. Параметры `concurrent_dashboard`, `versions_to_keep`, `timeout` стабильны на протяжении многих версий.
