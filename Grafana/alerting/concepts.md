# Обзор Grafana Alerting

**Grafana Alerting** — подсистема оповещений Grafana, построенная на модели Prometheus Alerting. Она позволяет создавать, оценивать и доставлять алерты из множества источников данных в едином интерфейсе, независимо от дашбордов. Актуальная версия (проверено для Grafana 12.x и 13.x, август 2026) опирается на так называемый **Unified Alerting** — современный движок, который пришёл на смену старой системе Dashboard Alerts.

> **Актуальность версий (2026):** Grafana 13.x — текущая стабильная ветка (Current), 12.x — поддержка безопасности (LTS), 11.x — EOL (июнь 2026). В Grafana 13.0+ доступен режим Single-Node Evaluation (SNE, public preview); он включается явно (`ha_single_node_evaluation = true`), по умолчанию отключён. Нативные inhibition rules доступны в beta.

> Почему это важно: в старой модели алерты были привязаны к панелям дашборда и не могли агрегировать данные из разных источников. Unified Alerting развязывает оценку правил и доставку уведомлений (модель «генератор алертов» + «получатель/Alertmanager»), что даёт масштабируемость, многомерные алерты, общие политики маршрутизации и HA-кластер.

## Определения

**Unified Alerting** — современная система оповещений Grafana (начиная с версии 9+), которая позволяет создавать, управлять и объединять алерты из множества источников данных в одном интерфейсе. В отличие от старой системы (Dashboard Alerts), Unified Alerting работает независимо от визуализации и поддерживает сложные многомерные алерты.

**Alert rule (Правило оповещения)** — декларативное описание того, что и при каком условии нужно проверять, с указанием интервала оценки, условий перехода в состояние `Alerting` и маршрута доставки.

**Alert instance (Экземпляр алерта)** — конкретная уникальная комбинация меток (`labels`), порождённая правилом при оценке. Один многомерный запрос может породить десятки экземпляров (по одному на каждый уникальный набор меток).

**Alertmanager** — компонент-получатель, который принимает сработавшие алерты, группирует их, применяет политики маршрутизации, тишины и подавления, а затем доставляет уведомления через контакт-пойнты.

**Contact point (Контакт-пойнт)** — описание канала доставки уведомления (Slack, Telegram, Email, Webhook и т.д.) и шаблона сообщения.

**Notification policy (Политика уведомлений)** — правило маршрутизации экземпляров алертов по меткам к контакт-пойнтам, включая группировку и тайминги.

## Базовые концепции

### Архитектура

Grafana Alerting построена на модели Prometheus, которая **развязывает оценку правил и обработку уведомлений**. Это ключевой архитектурный принцип: сбой или перегрузка одной части не блокирует другую, а масштабирование делается независимо. Система состоит из двух логических ролей и трёх исполняющих блоков внутри Grafana:

1.  **Генератор алертов (Alert generator / Evaluator):** оценивает правила и отправляет сработавшие/разрешённые (`firing`/`resolved`) алерты получателю. В Grafana роль генератора выполняет связка **Scheduler + Condition Evaluator**.
2.  **Получатель алертов (Alert receiver) — Alertmanager:** принимает алерты и отвечает за их маршрутизацию, группировку, дедупликацию и доставку.

Внутри Grafana генератор реализован тремя функциональными блоками:

1.  **Scheduler (Планировщик):** Отвечает за запуск запросов к источникам данных согласно расписанию групп правил. Каждое правило входит в *evaluation group* с фиксированным интервалом (например, `evaluate every 1m`). Scheduler гарантирует, что правила одной группы оцениваются синхронно — это важно для согласованности математических выражений, ссылающихся друг на друга.

    > **Интервал вычисления (`evaluation_interval`).** Глобальное значение по умолчанию задаётся в `grafana.ini` (`[unified_alerting] evaluation_interval`, по умолчанию 10s) и применяется ко всем группам правил, если не переопределено. В самой группе правил интервал задаётся явно (`evaluate every 1m` в UI или поле `interval` в YAML-провиженинге группы правил). Все правила внутри одной группы оцениваются с этим интервалом синхронно и стартуют выровненно по времени. Более короткий интервал повышает «свежесть» алертов, но увеличивает нагрузку на источники данных — подбирайте исходя из частоты поступления метрик и допустимой задержки обнаружения.
2.  **Condition Evaluator (Оценщик условий):** Применяет логику конвейера выражений (Expressions) к полученным данным для определения состояния алерта. Если условие истинно — алерт переходит в `Pending`, затем (после истечения `for`) в `Alerting`.
3.  **Alertmanager:** Встроенный компонент, отвечающий за приём активных алертов, их группировку, дедупликацию в HA-кластере и доставку через контакт-пойнты.

> **Важно про встроенный Alertmanager.** Grafana включает собственный Alertmanager, который **расширяет** Prometheus Alertmanager и по умолчанию называется «Grafana» в интерфейсе. Он обрабатывает только *Grafana-managed* алерты. Grafana также умеет пересылать алерты во внешние Alertmanager (например, Prometheus/Mimir Alertmanager), которые могут обрабатывать как Grafana-managed, так и data source-managed алерты.

### Высокая доступность (High Availability)

Grafana Alerting поддерживает полноценный HA-режим (актуально для Grafana 12.x/13.x). Подробное описание архитектуры HA, SNE, Gossip и требований к БД — в отдельном файле [Grafana: Высокая доступность](../high_availability.md).

*   **Single-Node Evaluation (SNE):** Начиная с Grafana 13.0, доступен режим SNE (public preview). При явном включении (`ha_single_node_evaluation = true`) только один узел (Primary, Position 0) выполняет оценку всех правил, остальные узлы получают результаты через Gossip-протокол. Это предотвращает дублирование вычислений и снижает нагрузку на источники данных. По умолчанию режим отключён: каждый узел оценивает правила самостоятельно (классический HA).

*   **Синхронизация:** Узлы кластера общаются через **Gossip-протокол (Memberlist)** на порту `9094` (TCP и UDP). Он используется для обнаружения узлов и согласования «владельца» (Leader) каждого правила. В режиме SNE (Grafana 13+) Leader — это Primary-узел (Position 0), который выполняет всю оценку.
*   **Дедупликация:** В режиме SNE оценка правил выполняется только на Primary, что исключает дублирование вычислений. В классическом HA-режиме (до 13.0) правило вычислялось на всех узлах, но только Leader отправлял результат в Alertmanager. Сам Alertmanager гарантирует доставку только одного уведомления благодаря внутренней дедупликации по fingerprint алерта.
*   **База данных:** Требуется внешняя БД (PostgreSQL или MySQL) для синхронизации состояний, конфигураций политик и истории. Без внешней БД каждый инстанс Grafana живёт «сам по себе» и HA невозможна.
*   **Конфигурационные снимки:** Для встроенного Grafana Alertmanager хранится до 100 версий конфигурации (per organization). Администратор может откатить неудачное изменение (version snapshot) или сравнить версии.

### Источники данных и типы управления алертами

Grafana Alerting поддерживает два типа управления алертами, которые определяют, **где** правило хранится и вычисляется:

1.  **Grafana-managed (GMA, рекомендуется):** Запросы выполняются сервером Grafana. Поддерживаются любые источники: SQL (PostgreSQL, MySQL), CloudWatch, Elasticsearch, а также Prometheus/Loki. Конвейер выражений (Expressions) доступен только для этого типа. Это основной и наиболее гибкий режим.
2.  **Data source-managed (DMA):** Правила хранятся и вычисляются непосредственно на стороне бэкенда источника данных, а Grafana лишь отображает и маршрутизирует результат.
    *   **Mimir:** Оптимизировано для крупномасштабных метрик; правила вычисляются в Mimir Ruler.
    *   **Loki:** Для алертинга на основе логов (LogQL); вычисляется в Loki Ruler.
    *   **Prometheus:** Классический вариант с использованием Ruler (включая Thanos, Cortex).

> **Следствие для маршрутизации.** Алерты, сенерированные внешними Ruler (data source-managed), попадают во внешний Alertmanager этого бэкенда. Чтобы Grafana-маршрутизация (политики уведомлений Grafana) обработала их, нужно либо настроить внешний Alertmanager как контакт-пойнт Grafana, либо включить для источника опцию «Receive Grafana-managed alerts» (это относится к Grafana-managed алертам, пересылаемым во внешний Alertmanager).

> **Важно (Grafana Cloud, 2026):** Предварительно настроенные Loki и Prometheus источники с data source-managed alerts **deprecated** и не могут быть созданы в новых стеках. Существующие стеки не затронуты. DMA-правила можно импортировать в GMA-правила через импорт-инструмент. В self-hosted Grafana оба типа по-прежнему доступны.

### Производительность и ограничения (Performance & Limits)

Grafana Alerting накладывает ограничения на количество правил и экземпляров алертов. Ключевые параметры:

*   **Лимит результатов оценки одного правила:** По умолчанию не ограничен (`-1`) в self-hosted Grafana; в Grafana Cloud — управляется Grafana Labs. Если запрос возвращает больше лимита, правило переходит в состояние `Error` с сообщением `query evaluation returned too many results`. Настройте через `[quota] alerting_rule_evaluation_results`.
*   **Лимит экземпляров алертов (Grafana Cloud):** Free — до 100 алертов на правило; Pro/Advanced — мягкий лимит 2000 правил, экземпляры не ограничены.
*   **Поддерживаемые версии Prometheus/Alertmanager:** последние две_minor_-версии. Старше — работать не гарантируется.
*   **Хранилище состояний:** Начиная с Grafana 13.2, тогл `alertingSaveStateCompressed` удалён — хранение состояния теперь всегда сжатое. При апгрейде убедитесь, что в старой uncompressed-формате данные не осталось.
*   **Параметры сохранения состояния:** `[unified_alerting]` — `state_periodic_save_interval` (по умолчанию 1m), `state_periodic_save_batch_size` (100), `state_periodic_save_jitter_enabled` (true). При большом числе экземпляров (например, 2000) записи распределяются по батчам в течение 51s.

### Конвейер выражений (Expressions)

Механизм трансформации данных для Grafana-managed алертов. Каждое выражение имеет идентификатор (`A`, `B`, `C`…), на который ссылаются последующие шаги. Типичный конвейер:

*   **Query (A):** Сырой запрос к источнику (PromQL, LogQL, SQL). Возвращает временные ряды.
*   **Reduce (B):** Агрегация временного ряда в одно число (например, `Mean`, `Max`, `Last`/`Last*`). Без Reduce многозначный ряд нельзя сравнить в Math.
*   **Resample (C):** Изменение временного окна/шага данных для сопоставления рядов из разных источников (приводит ряды к общей сетке времени).
*   **Math (D):** Математическое условие (например, `$B > 10`), результат которого определяет переход в состояние оповещения. Поддерживает операторы сравнения и логику (`$B > 90 && $B < 100`).
*   **Threshold (порог):** Упрощённая альтернатива Math — прямое сравнение с порогом (greater than, lower than, within range) без написания формулы.
*   **Classic condition (классическое условие):** Устаревающий, но ещё доступный режим для простых одиночных порогов; не рекомендуется для новых алертов, так как менее гибок, чем конвейер выражений.

Пример конвейера для «CPU > 90%»:

```text
A: query  = CPU utilization (возвращает ряд по каждому pod)
B: reduce = Last()  → число на каждый pod
C: math   = $B > 90 → булево: сработал ли алерт для pod
```

Каждый pod с `$B > 90` станет отдельным **экземпляром алерта** с уникальным набором меток.

### Метки и Аннотации (Labels & Annotations)

*   **Метки (Labels):** Используются для **идентификации** экземпляра алерта и **маршрутизации**. Примеры: `cluster`, `service`, `severity`, `instance`. Именно по меткам работают политики уведомлений, тишины и правила подавления. Изменение набора меток меняет идентичность алерта (считается новым экземпляром).
*   **Аннотации (Annotations):** Содержат **дополнительную информацию** для человека. Не влияют на маршрутизацию. Примеры: `summary`, `description`, `runbook_url`. Аннотации могут содержать динамические значения через шаблоны.

### Правила записи (Recording Rules)

В Grafana реализована нативная поддержка Recording Rules для любых источников данных.

*   **Назначение:** Предварительное вычисление сложных или тяжелых запросов и сохранение результата как новой метрики.
*   **Преимущества:** Ускорение загрузки дашбордов и снижение нагрузки на источники данных при частых проверках алертов.
*   **Хранение:** Результаты могут записываться обратно в Prometheus-совместимые хранилища (Mimir, Prometheus) через Remote Write API. Для Grafana-managed recording rules результат сохраняется в выбранном совместимом бэкенде, после чего им можно пользоваться как обычной метрикой.

### Группировка и тайминги уведомлений

Чтобы не «заспамить», Alertmanager объединяет похожие алерты и управляет частотой отправки через три интервала (настраиваются на политике уведомлений):

*   **`group_by`** — список меток, по которым алерты объединяются в одно уведомление (например, `['alertname', 'cluster']`).
*   **`group_wait`** — начальная задержка (по умолчанию `30s`) перед первой отправкой, чтобы накопить всплеск связанных алертов в одно сообщение.
*   **`group_interval`** — пауза (по умолчанию `5m`) между повторными отправками *новых* алертов в уже сгруппированном уведомлении.
*   **`repeat_interval`** — период (по умолчанию `4h`), с которым повторяется уведомление об уже сработавшем алерте, пока он не разрешится.

> **Пример поведения.** Алерт `CPUHigh` сработал на 5 pod'ах. Благодаря `group_wait=30s` и `group_by=['alertname','cluster']` пользователь получит **одно** сообщение со списком всех 5 pod'ов, а не 5 отдельных уведомлений.

### Политики уведомлений и дерево маршрутизации

Политики уведомлений определяют, куда отправится алерт, основываясь на его метках. Это **не плоский список, а дерево**:

*   Корень дерева — **Default notification policy** — совпадает со всеми алертами и гарантирует, что ни один алерт не будет потерян.
*   Каждая политика может иметь дочерние (child) и «братские» (sibling) политики.
*   **Наследование:** Дочерняя политика наследует от родителя `contact point`, `group_by` и тайминги, если не переопределит их явно. Это позволяет задать общий контакт-пойнт на уровне команды и переопределять лишь специфику на листьях.
*   **Matching:** Обход начинается с корня; если дочерняя политика совпадает по меткам, обход рекурсивно идёт вглубь. Обрабатывает самая глубокая совпавшая политика.
*   **Continue matching siblings:** опция на политике, позволяющая алерту матчиться также с «братьями» родителя (по умолчанию выключена — один алерт обрабатывается одной политикой).
*   **Множественные деревья (multiple notification policies):** опция разделения маршрутизации на независимые деревья для разных доменов (feature toggle `alertingMultiplePolicies`, public preview в Grafana 13+). Каждое дерево имеет собственные контакт-пойнты, политики и тишины — они не шерятся между собой.

**Механизм сопоставления (Label Matching):**
*   **`=` (Exact match):** Полное совпадение значения.
*   **`!=` (Not equal):** Исключение конкретного значения.
*   **`=~` (Regex match):** Сопоставление по регулярному выражению.
*   **`!~` (Regex not match):** Исключение по регулярному выражению.

Система использует дерево политик: если алерт не подошёл ни под одну дочернюю политику, используется дефолтная корневая политика.

**Особенности настройки таймингов:**
*   **`group_by: ['...']`** — специальное значение, отключает агрегацию (каждый алерт — отдельное уведомление). Используйте только при очень низком объёме алертов.
*   **`override_grouping` / `override_general_timings`** — в дочерней политике можно явно переопределить `group_by` и тайминги родителя, не наследуя их.
*   **`active_time_intervals`** — противоположный Mute Timing механизм: уведомления подавляются, **если** время НЕ попадает в интервал (алертит только в указанные окна). Mute Timing имеет приоритет над Active time interval при пересечении.

### Тишины (Silences)

**Silence** — точечное подавление уведомлений для алертов, совпадающих по меткам, на заданный период (с указанием автора и комментария). Тишина **не останавливает оценку правила** — алерт продолжает переходить в `Alerting`, просто уведомление не отправляется. Применяется для плановых работ или подавления известного шума во время инцидента. Создаётся через UI (Alerting > Silences) или provisioning.

### Периоды тишины и временные интервалы (Mute Timings & Time Intervals)

*   **Time Interval (временной интервал):** именованное расписание (дни недели, часы, временные зоны, даже отдельные даты). Сам по себе не глушит уведомления — это строительный блок.
*   **Mute Timing (период тишины):** правило, привязывающее Time Interval к политике уведомлений — в указанные окна уведомления не доставляются. Идеально для «тихих часов» ночью или нерабочего времени команды.

> Отличие от Silence: Mute Timing привязан к **времени** и политике, а Silence — к **конкретному набору меток** и сроку. Оба не останавливают вычисление правил.

### Правила подавления (Inhibition Rules)

Позволяют **подавлять уведомления зависимых алертов**, когда уже сработал вышестоящий (корневой) алерт. Пример: если `ClusterDown` активен, нет смысла слать десятки `NodeDown` — Inhibition скроет их. Работает по матчерам:

*   **Source matchers** — условие наличия «подавляющего» алерта (например, `severity=critical`, `alertname=ClusterDown`).
*   **Target matchers** — какие алерты подавляются (`alertname=NodeDown`).
*   **Equal labels** — метки, которые должны совпадать у источника и цели (например, `cluster`), чтобы подавление применилось в нужном контексте. Если `equal` не указан — подавляющий алерт с любыми метками подавляет все целевые.

> **Важно (Grafana 13+, beta):** Нативные inhibition rules доступны начиная с Grafana 13 через **Grafana App Platform API** (`notifications.alerting.grafana.app/v1beta1`, ресурс `inhibitionrules`). Выделенного UI для управления inhibition rules **нет по дизайну** — они предназначены в первую очередь для совместимости с импортируемыми конфигурациями Prometheus Alertmanager или Mimir. Правило привязывается к конкретному Alertmanager и подавляет только алерты, управляемые им. Подробные примеры и `curl` — в [Best practices](./best_practices.md). До Grafana 13 inhibition эмулировалось через сложные `Math`-выражения (неудобно).

### История состояний (State History)

Grafana записывает каждое изменение состояния экземпляра алерта (например, `Normal → Pending → Alerting → Resolved`). Это используется для страницы **History** и вью «State history» в правиле.

*   **Backend хранения:** по умолчанию — встроенное хранилище Annotation (доступно «из коробки» в Grafana Cloud и в последних OSS-версиях). Альтернативы — **Loki** или **Prometheus/Mimir** (через Remote Write). Настройка через `[unified_alerting.state_history]`: `enabled = true`, `backend = loki` (или `prometheus`), `loki_remote_url`.
*   **OSS/Enterprise нюанс:** чтобы видеть History в OSS/Enterprise, нужно настроить Loki как backend истории и включить feature toggle `alertingCentralAlertHistory`. Без этого страница истории недоступна.
*   **Отладка:** история показывает все переходы **независимо от тишин и mute timings** — это позволяет анализировать алерты, которые «сработали, но не уведомили».
*   **История уведомлений (Notification History, Grafana 13+):** отдельный функционал — запись каждой попытки доставки (firing/resolved, контакт-пойнт, статус доставки). Хранится в Loki через `[unified_alerting.notification_history]`. Доступно на вкладке **Notifications** страницы History и в правиле. Требует feature toggle `alertingNotificationHistory` (и производных: `alertingNotificationHistoryGlobal`, `alertingNotificationHistoryRuleViewer`).

### Шаблоны уведомлений (Templates)

Все контакт-пойнты поддерживают шаблонизацию через **Go Templates**, что позволяет настраивать текст сообщений динамически. Различают:

*   **Message templates:** многоразовые фрагменты, определяемые в разделе Notification templates, которые можно подключать к разным контакт-пойнтам.
*   **Custom templates:** inline-шаблоны внутри конкретного контакт-пойнта (например, тело Webhook-JSON или заголовок Telegram).

Шаблоны имеют доступ к объекту `{{ .CommonLabels }}`, `{{ .CommonAnnotations }}`, `{{ .Alerts }}`, `{{ .Status }}` и т.д. Ошибка в шаблоне может полностью сломать доставку уведомления (см. раздел Troubleshooting).

### Контакт-пойнты (Contact Points)

Каналы доставки уведомлений. Основные типы в Grafana 12.x/13.x:

*   **Slack / Discord / Microsoft Teams:** Вебхуки с поддержкой форматирования.
*   **Telegram:** Через официальное API ботов.
*   **Email:** С поддержкой вложенных графиков.
*   **PagerDuty / Opsgenie:** Интеграции для управления инцидентами и эскалациями.
*   **Webhook:** Универсальный способ передачи JSON-данных в сторонние системы.
*   **Kafka:** Для передачи событий алертинга в шины данных.
*   **Другие Alertmanager:** контакт-пойнт «Alertmanager» для пересылки алертов во внешний Alertmanager.

Все контакт-пойнты поддерживают шаблонизацию через **Go Templates**, что позволяет настраивать текст сообщений динамически.

### Рендеринг изображений (Image Renderer)

Функция включения скриншотов панелей в уведомления (Slack, Telegram, Email). Подробная настройка — в [Рендеринг изображений](../grafana_image_rendering.md).

*   **Статус:** Рендеринг выполняет внешний сервис `grafana-image-renderer` (на базе headless Chromium). Плагинный (встроенный) режим устарел и удалён в Grafana 13 — сервис разворачивается отдельно.
*   **Требования:** Запущенный сервис `grafana-image-renderer` (Docker-образ или бинарник с установленным Chromium), доступный Grafana по `[rendering] server_url`.
*   **Конфигурация:** В `grafana.ini` секция `[rendering]` (`server_url`, `callback_url`, `renderer_token`); включение картинок в уведомлениях — `[unified_alerting.screenshots] capture = true`.

### Состояния правил

| Состояние | Описание |
| :--- | :--- |
| **Normal / OK** | Условие не выполняется, система стабильна. |
| **Pending** | Условие выполнено, но не истекло время задержки `for`. |
| **Alerting** | Условие выполняется дольше `for`, уведомление отправлено. |
| **NoData** | Источник вернул пустой результат. Поведение настраиваемое (NoData → Alerting / NoData / OK). |
| **Error** | Техническая ошибка (таймаут, ошибка синтаксиса, сбой сети). |
| **Inactive** | Правило отключено (paused/disabled) либо не входит в текущий период оценки. |
| **Resolved (Recovered)** | Переход из `Alerting` обратно в `Normal`; генерирует уведомление о восстановлении. |

> Поведение при `NoData` и `Error` настраивается отдельно для каждого правила: можно трактовать их как сработку (полезно, чтобы заметить пропажу метрик), как норму или как «вне оценки». Дополнительные параметры: `no_data_state` и `exec_err_state` (в YAML-провиженинге).

### Жизненный цикл оповещения

1.  **Оценка:** Планировщик запускает конвейер запросов и выражений согласно интервалу группы.
2.  **Генерация экземпляров:** Создаются уникальные алерты для каждой комбинации меток.
3.  **Состояние Pending:** Если условие истинно, алерт ждёт подтверждения в течение периода `for`.
4.  **Сработка (Firing):** Переход в `Alerting` и отправка данных в Alertmanager.
5.  **Группировка:** Ожидание `group_wait` для объединения связанных событий.
6.  **Доставка:** Отправка сообщения в выбранный контакт-пойнт согласно политике уведомлений.
7.  **Разрешение (Resolved):** При возврате условия в норму алерт переходит в `Normal`, генерируется уведомление о восстановлении (если не подавлено).

> **`keep_firing_for` (Grafana 12.x/13.x):** параметр правила, удерживающий алерт в состоянии `Firing` в течение заданного времени даже после возврата метрики в норму. Предотвращает каскад `Resolved → Firing` при кратковременных улучшениях (recovery flapping). Наивается в UI в блоке rule settings или через YAML-провиженинг.

## Практические сценарии

> Ниже — концептуальный и UI-ориентированный сценарий. Полное описание Infrastructure as Code (YAML) вынесено в [Provisioning алертов](./provisioning.md). Цель этого раздела — дать пошаговый, воспроизводимый путь создания, проверки и отладки алерта.

### Предварительные требования

*   **Версия:** Grafana 12.x или 13.x (проверено август 2026).
*   **База данных:** для HA — внешняя PostgreSQL/MySQL; для одиночного инстанса достаточно встроенной (SQLite) с пониманием ограничений.
*   **Источник данных:** настроен и проверен (например, Prometheus/Mimir с метрикой `CPU`), пользователь Grafana имеет права `Alerting > Edit rules` (или `Admin`).
*   **Контакт-пойнт:** хотя бы один настроен (например, Slack/Telegram) и протестирован кнопкой **Test**.
*   **Сеть:** доступ Grafana к источнику данных; для HA — открытый порт `9094` между узлами.

### Сценарий 1. Создание Grafana-managed алерта через UI

1.  Откройте **Alerting → Alert rules → New alert rule**.
2.  В поле **Rule name** укажите осмысленное имя, например `CPUHigh-prod`.
3.  Выберите тип **Grafana-managed** (по умолчанию).
4.  Добавьте выражение **A (Query)** к нужному источнику:

    ```promql
    # A: средняя загрузка CPU по pod'ам кластера prod
    100 - (avg by (pod) (rate(node_cpu_seconds_total{mode="idle",cluster="prod"}[5m])) * 100)
    ```

5.  Добавьте **B (Reduce)** → тип `Last`, input `A`. Результат: число на каждый pod.
6.  Добавьте **C (Math)** → условие `$B > 90`. Только pod'ы с CPU > 90% дадут `true`.
7.  В секции **Evaluation** задайте группу (`cpu-rules`) и интервал `Evaluate every = 1m`.
8.  В поле **For** укажите `5m` — алерт перейдёт в `Alerting` только если условие держится 5 минут (снижает дребезг).
9.  В блоке **Configure no data and error handling** выберите, например: *No data → Alerting* (чтобы заметить пропажу метрик), *Error → Alerting*.
10. В блоке **Labels and annotations** добавьте:
    *   Labels: `severity = critical`, `team = ops`, `cluster = prod`.
    *   Annotations: `summary = "High CPU on {{ $labels.pod }}"`, `description = "CPU > 90% for 5m"`, `runbook_url = "https://wiki.example.com/cpu"`.
11. В **Notifications** выберите либо конкретный **Contact point**, либо **Notification policy** (рекомендуется — для гибкой маршрутизации).
12. Нажмите **Preview** (предпросмотр), чтобы убедиться, что запрос возвращает данные и условие корректно.
13. Нажмите **Save**.

**Результат:** правило появится в списке, пройдёт оценку и при выполнении условия отправит уведомление согласно политике.

### Сценарий 2. Маршрутизация через политику уведомлений

1.  Откройте **Alerting → Notification policies**.
2.  Создайте дочернюю политику от Default с матчером `team = ops`.
3.  Назначьте ей контакт-пойнт `#ops-alerts` и `group_by = [alertname, cluster]`.
4.  Установите `group_wait = 30s`, `group_interval = 5m`, `repeat_interval = 2h`.
5.  Сохраните. Теперь все алерты с меткой `team=ops` попадут в `#ops-alerts`, а `team=sre` — в дефолтный или свою политику.

### Проверка корректности (Validation)

*   **Список правил:** `Alerting → Alert rules` показывает состояние (`Normal`/`Pending`/`Alerting`) и время последней оценки.
*   **Предпросмотр:** кнопка **Preview** в редакторе правила показывает, сколько экземпляров алерта вернёт запрос и какое значение у каждого.
*   **State history:** `Alerting → History` (или «Show state history» внутри правила) — видны все переходы состояний, **включая те, что подавлены тишиной/мute**.
*   **Тест контакт-пойнта:** на странице Contact point нажмите **Test** — должно прийти тестовое сообщение с ожидаемым шаблоном.
*   **Тест уведомления:** во время `Alerting` проверьте канал (Slack/Telegram) и `Alerting → Silences/Notifications` (в Cloud/Enterprise — лог доставки).

### Устранение неполадок (Troubleshooting)

| Симптом | Вероятная причина | Решение |
| :--- | :--- | :--- |
| Алерт вечно `Pending` | `For` слишком велико, или данные поступают рывками | Уменьшите `for`; проверьте непрерывность данных в источнике |
| Состояние `NoData` | Запрос пуст / неверный селектор меток / не тот временной диапазон | Проверьте PromQL/LogQL в Explore; сверьте метки источника |
| Состояние `Error` | Ошибка синтаксиса, недоступность источника, нет прав | Смотрите лог Grafana (`logger=alerting`); проверьте доступность datasource |
| Уведомления не приходят | Неверная маршрутизация, активная тишина/mute timing, ошибка шаблона | Проверьте политику по меткам, Silences и Mute Timings, лог рендера шаблона |
| Дублирующиеся уведомления в HA | Несколько Grafana Alertmanager без внешней БД / дедуп не работает | Используйте внешнюю БД и встроенный Grafana Alertmanager (дедуп по fingerprint) |
| Скриншот не прикладывается | Не настроен/недоступен сервис `grafana-image-renderer` | Проверьте `[rendering] server_url` и `/healthz` сервиса; включите `[unified_alerting.screenshots] capture = true` |
| Ошибка доставки «template” | Некорректный Go-шаблон в contact point | Проверьте синтаксис шаблона, используйте `{{ .CommonLabels }}` аккуратно |
| Правило в `Error` из-за лимита результатов | Запрос возвращает больше `alerting_rule_evaluation_results` | Уменьшите кардинальность запроса или увеличьте лимит в `[quota]` |
| `query evaluation returned too many results` | Превышен лимит экземпляров (Grafana Cloud: 100 на правило Free) | Используйте `group_by`, Reduce, фильтрацию по меткам |
| История не доступна | Не настроен Loki backend или не включён `alertingCentralAlertHistory` | Настройте `[unified_alerting.state_history]` и включите тогл |
| DMA-правило не отображается | Источник не поддерживает reading rules / устаревшая версия Prometheus | Обновите бэкенд до поддерживаемой версии |

### Граничные случаи (Edge Cases)

*   **Дребезг (Flapping):** метрика колеблется у порога → каскад `Alerting`/`Resolved`. Лечится параметром `for`, сглаживанием запроса (`avg_over_time`) и inhibit-правилами.
*   **Взрыв экземпляров:** многомерный запрос без Reduce порождает сотни алертов → шум и нагрузка. Используйте `group_by`, осмысленный Reduce и не создавайте алерт на высокой кардинальности без необходимости.
*   **Temporal thresholds:** алерт, зависящий от времени суток, — реализуется через Mute Timings/Time Intervals, а не через логику самого правила.
*   **Временные зоны:** Mute Timings и Time Intervals учитывают указанную тайм-зону; несовпадение с локальным временем команды — частый источник «почему ночью пришло уведомление».
*   **Наследование в дереве политик:** дочерняя политика наследует контакт-пойнт и тайминги родителя — неочевидное поведение при каскадных политиках.
*   **Несколько Alertmanager:** каждый Alertmanager хранит **собственные** независимые ресурсы (contact points, policies, silences) — они не шерятся между собой.
*   **OSS/Enterprise History:** страница History требует настроенного Loki и тоггла `alertingCentralAlertHistory`; без этого переходы состояний не видны.
*   **SNE и классический HA:** в режиме SNE (Grafana 13+) оценка правил выполняется только на Primary-узле, что исключает дублирование вычислений. В классическом HA-режиме (до 13.0) правило вычислялось на всех узлах, но результат отправлял только Leader — при неправильной настройке Memberlist это могло приводить к дедупликационным сбоям.
*   **Лимит экземпляров (Grafana Cloud):** Free-план — до 100 экземпляров на правило; Pro/Advanced — мягкий лимит 2000 правил, экземпляры не ограничены. Превышение лимита ведёт в `Error`.
*   **Inhibition rules (Grafana 13+, beta):** привязаны к конкретному Alertmanager и управляются через App Platform API без выделенного UI. Неверно настроенное правило может молча подавить важные алерты.
*   **DMA-правила в Grafana Cloud (2026):** предварительно настроенные Loki/Prometheus источники с DMA deprecated; существующие стеки не затронуты. Импорт DMA → GMA доступен через импорт-инструмент.

### Лучшие практики и очистка (Best Practices & Cleanup)

*   Задавайте осмысленные `for` (обычно 3–10 мин) для снижения шума.
*   Группируйте по `alertname` + ключевым меткам (`cluster`, `service`), избегайте группировки по высококардинальным меткам (`pod`, `instance`).
*   Делайте метки стабильными: изменение набора меток = новый экземпляр алерта (сброс состояния).
*   Тестируйте контакт-пойнты кнопкой **Test** перед продакшеном.
*   Делайте бэкап конфигурации Alertmanager (export) перед массовыми изменениями; помните про лимит 100 версий истории.
*   **Очистка:** удаляйте временные Silences после инцидентов, регулярно пересматривайте Mute Timings и отключайте/удаляйте устаревшие правила, чтобы не накапливать «мёртвые» алерты.

Подробнее про проектирование и снижение шума — в [Best practices](./best_practices.md).
