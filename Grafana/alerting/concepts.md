# Обзор Grafana Alerting

## Определения

**Unified Alerting** — централизованная система оповещений Grafana, отделённая от дашбордов и работающая поверх различных источников данных (Prometheus, Loki, MySQL, PostgreSQL и др.).

## Базовые концепции

### Архитектура

Grafana Alerting состоит из трёх основных компонентов:
1.  **Scheduler (Планировщик)** — отвечает за периодическое выполнение запросов к источникам данных.
2.  **Condition Evaluator (Оценщик условий)** — применяет логику порога к результатам запросов.
3.  **Internal Alertmanager** — встроенный компонент (на базе Prometheus Alertmanager), который принимает алерты, группирует их, применяет политики маршрутизации и доставляет уведомления.

### Ключевые понятия

| Понятие | Описание |
| :--- | :--- |
| **Правило (Alert rule)** | Логика проверки: запрос, выражения (Reduce, Resample, Math), порог и метаданные. |
| **Экземпляр (Alert instance)** | Отдельный алерт, порождённый правилом для конкретного набора меток (мульти-размерность). |
| **Группа правил** | Объединение правил с общим интервалом оценки для оптимизации нагрузки. |
| **Контакт-пойнт** | Канал доставки (Email, Slack, Webhook, Telegram и др.). |
| **Политика уведомлений** | Правила маршрутизации алертов на основе меток (`group_by`, `repeat_interval`). |
| **Глушения (Silences)** | Временное подавление уведомлений по фильтру меток. |
| **Графики глушения (Mute Timings)** | Подавление уведомлений по расписанию (например, только в нерабочее время). |
| **Шаблоны** | Настраиваемые Go-шаблоны для оформления текстов уведомлений. |

### Типы правил

1.  **Grafana-managed rules** — оцениваются на стороне сервера Grafana. Поддерживают любые источники данных и сложные выражения (Math/Reduce).
2.  **Data source-managed rules** — правила, хранящиеся и оцениваемые на стороне источника (Prometheus, Loki, Mimir). Grafana служит только интерфейсом для их управления.
3.  **Recording rules** — правила для предварительного вычисления сложных запросов и сохранения результатов в виде новых метрик.

### Состояния правил

| Состояние | Описание | Когда переходит |
| :--- | :--- | :--- |
| **Normal / OK** | Условие не выполняется. | После срабатывания `for` без нарушений. |
| **Pending** | Условие выполняется, но время `for` ещё не истекло. | При первом нарушении порога. |
| **Alerting** | Условие выполняется дольше, чем задано в `for`. | После истечения `for`, уведомления отправляются. |
| **NoData** | Источник не вернул данных. | Настраивается: `Alerting`, `NoData` (по умолчанию), `OK`. |
| **Error** | Ошибка при выполнении запроса или оценки. | Настраивается: `Alerting`, `Error` (по умолчанию), `OK`. |

### Жизненный цикл оповещения

1.  **Оценка (Evaluation)** — Планировщик запускает запрос согласно интервалу группы.
2.  **Многомерная обработка** — Если запрос возвращает несколько временных рядов, для каждого создаётся свой **экземпляр оповещения**.
3.  **Переход состояния** — Правило переходит в `Pending`, а затем в `Alerting`, если проблема сохраняется в течение времени `for`.
4.  **Отправка в Alertmanager** — Активные алерты попадают во внутренний Alertmanager.
5.  **Группировка и Маршрутизация** — Alertmanager ждёт `group_wait`, собирает алерты с одинаковыми метками в одну группу и выбирает путь в дереве политик.
6.  **Доставка** — Сообщение отправляется в настроенные контакт-пойнты.

### Рендеринг изображений (Image Renderer)

**Image Renderer** — дополнительный сервис для включения скриншотов панелей в уведомления.

-   **Назначение:** Позволяет увидеть график метрики в Slack/Email без входа в Grafana.
-   **Реализация:** Отдельный плагин или контейнер `grafana-image-renderer` (на базе Headless Chromium).
-   **Требования:** Минимум 512MB RAM.

## Практические сценарии

### Пример: Создание правила (Error Rate)

**Запрос (PromQL):**
```promql
sum(rate(http_requests_total{job="api",status=~"5.."}[5m])) 
/ 
sum(rate(http_requests_total{job="api"}[5m])) * 100
```

**Настройки:**
| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| Интервал оценки | 1m | Частота проверки |
| `for` | 5m | Время задержки перед переходом в `Alerting` |
| `NoData` | OK | Игнорировать отсутствие данных |

**Метки и Аннотации:**
```yaml
labels:
  severity: critical
  team: backend
annotations:
  summary: "Высокая доля ошибок API: {{ $value | humanizePercentage }}"
  description: "Доля 5xx ошибок на {{ $labels.instance }} превышает 5%"
  runbook_url: "https://wiki.example.com/api-troubleshooting"
```

### Пример: Маршрутизация уведомлений

Логика: Критические алерты — в PagerDuty и Telegram, остальные — только в Slack.

```yaml
route:
  receiver: slack-default
  routes:
    - matchers:
        - severity = critical
      receiver: critical-notifications
      continue: true  # Продолжить поиск по другим веткам, если нужно
```

### Пример: График глушения (Mute Timing)

Запрет уведомлений для некритичных систем по выходным:

```yaml
mute_timings:
  - name: weekends-off
    time_intervals:
      - weekdays: ['saturday', 'sunday']
```
