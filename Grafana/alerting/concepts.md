# Обзор Grafana Alerting

## Определения

**Unified Alerting** — современная система оповещений Grafana (начиная с версии 9+), которая позволяет создавать, управлять и объединять алерты из множества источников данных в одном интерфейсе. В отличие от старой системы (Dashboard Alerts), Unified Alerting работает независимо от визуализации и поддерживает сложные многомерные алерты.

## Базовые концепции

### Архитектура

Система состоит из трех ключевых функциональных блоков:

1.  **Scheduler (Планировщик):** Отвечает за запуск запросов к источникам данных согласно расписанию групп правил.
2.  **Condition Evaluator (Оценщик условий):** Применяет логику конвейера выражений (Expressions) к полученным данным для определения состояния алерта.
3.  **Alertmanager:** Встроенный компонент, отвечающий за прием активных алертов, их группировку, дедупликацию в HA-кластере и доставку через контакт-пойнты.

### Высокая доступность (High Availability)

В 2025 году Grafana Alerting поддерживает полноценный HA-режим:
*   **Синхронизация:** Узлы кластера общаются через **Gossip-протокол (Memberlist)** на порту 9094.
*   **Дедупликация:** Несмотря на то, что каждое правило вычисляется на всех узлах, Alertmanager гарантирует отправку только одного уведомления.
*   **База данных:** Требуется внешняя БД (PostgreSQL или MySQL) для синхронизации состояний и конфигураций.

## Источники данных

Grafana Alerting поддерживает два типа управления алертами:

1.  **Grafana-managed:** Запросы выполняются сервером Grafana. Поддерживаются любые источники: SQL (PostgreSQL, MySQL), CloudWatch, Elasticsearch, а также Prometheus/Loki.
2.  **Data source-managed (Managed Rules):** Правила хранятся и вычисляются непосредственно на стороне бэкенда.
    *   **Mimir:** Оптимизировано для крупномасштабных метрик.
    *   **Loki:** Для алертинга на основе логов (LogQL).
    *   **Prometheus:** Классический вариант с использованием Ruler.

## Ключевые понятия

### Конвейер выражений (Expressions)

Механизм трансформации данных для Grafana-managed алертов:
*   **Query:** Сырой запрос к источнику.
*   **Reduce:** Агрегация временного ряда в одно число (например, среднее значение или последнее полученное).
*   **Resample:** Изменение временного окна данных для сопоставления рядов из разных источников.
*   **Math:** Математическое условие (например, `$B > 10`), результат которого определяет переход в состояние оповещения.

### Метки и Аннотации (Labels & Annotations)

*   **Метки (Labels):** Используются для **идентификации** экземпляра алерта и **маршрутизации**. Примеры: `cluster`, `service`, `severity`.
*   **Аннотации (Annotations):** Содержат **дополнительную информацию** для человека. Не влияют на маршрутизацию. Примеры: `summary`, `description`, `runbook_url`.

## Правила записи (Recording Rules)

В Grafana реализована нативная поддержка Recording Rules для любых источников данных.
*   **Назначение:** Предварительное вычисление сложных или тяжелых запросов и сохранение результата как новой метрики.
*   **Преимущества:** Ускорение загрузки дашбордов и снижение нагрузки на источники данных при частых проверках алертов.
*   **Хранение:** Результаты могут записываться обратно в Prometheus-совместимые хранилища (Mimir, Prometheus) через Remote Write API.

## Маршрутизация и Label Matching

Политики уведомлений определяют, куда отправится алерт, основываясь на его метках.

**Механизм сопоставления (Matching):**
*   **`=` (Exact match):** Полное совпадение значения.
*   **`!=` (Not equal):** Исключение конкретного значения.
*   **`=~` (Regex match):** Сопоставление по регулярному выражению.
*   **`!~` (Regex not match):** Исключение по регулярному выражению.

Система использует дерево политик: если алерт не подошел ни под одну дочернюю политику, используется дефолтная корневая политика.

## Контакт-пойнты (Contact Points)

Каналы доставки уведомлений. Основные типы в 2025 году:
*   **Slack / Discord / Microsoft Teams:** Вебхуки с поддержкой форматирования.
*   **Telegram:** Через официальное API ботов.
*   **Email:** С поддержкой вложенных графиков.
*   **PagerDuty / Opsgenie:** Интеграции для управления инцидентами и эскалациями.
*   **Webhook:** Универсальный способ передачи JSON-данных в сторонние системы.
*   **Kafka:** Для передачи событий алертинга в шины данных.

Все контакт-пойнты поддерживают шаблонизацию через **Go Templates**, что позволяет настраивать текст сообщений динамически.

## Рендеринг изображений (Image Renderer)

Функция включения скриншотов панелей в уведомления (Slack, Telegram, Email).
*   **Статус:** В актуальных версиях базовый функционал рендеринга встроен в ядро Grafana и не требует установки внешнего плагина.
*   **Требования:** Наличие установленных библиотек Chromium в системе (или использование Docker-образа с предустановленным Chromium).
*   **Конфигурация:** Включается в `grafana.ini` в секции `[screenshots]`.

## Состояния правил

| Состояние | Описание |
| :--- | :--- |
| **Normal / OK** | Условие не выполняется, система стабильна. |
| **Pending** | Условие выполнено, но не истекло время задержки `for`. |
| **Alerting** | Условие выполняется дольше `for`, уведомление отправлено. |
| **NoData** | Источник вернул пустой результат. Поведение настраиваемое. |
| **Error** | Техническая ошибка (таймаут, ошибка синтаксиса, сбой сети). |

## Жизненный цикл оповещения

1.  **Оценка:** Планировщик запускает конвейер запросов и выражений.
2.  **Генерация экземпляров:** Создаются уникальные алерты для каждой комбинации меток.
3.  **Состояние Pending:** Если условие истинно, алерт ждет подтверждения в течение периода `for`.
4.  **Сработка (Firing):** Переход в `Alerting` и отправка данных в Alertmanager.
5.  **Группировка:** Ожидание `group_wait` для объединения связанных событий.
6.  **Доставка:** Отправка сообщения в выбранный контакт-пойнт.
