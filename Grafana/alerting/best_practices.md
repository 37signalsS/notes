# Лучшие практики алертинга — Grafana Alerting

## Определения

**Лучшие практики (Best Practices) Grafana Alerting** — совокупность методологических и технических рекомендаций по проектированию системы оповещений, направленных на минимизацию ложных срабатываний, снижение уровня шума и обеспечение высокой скорости реакции (MTTR) при возникновении реальных инцидентов.

## Базовые концепции

### SRE Golden Signals и методологии

При проектировании правил оповещения необходимо классифицировать объекты мониторинга для выбора правильных метрик.

| Методология | Фокус | Метрики для алертинга |
| :--- | :--- | :--- |
| **RED** | Сервисы / API | **R**equests (всплески/падения), **E**rrors (доля 5xx > 1%), **D**uration (P99 latency). |
| **USE** | Ресурсы (CPU, RAM) | **U**tilization (загрузка %), **S**aturation (очереди, троттлинг), **E**rrors (ошибки драйверов/железа). |
| **Golden Signals** | Системный обзор | Latency, Traffic, Errors, Saturation. |

**Важное правило:** Никогда не настраивайте алерты на среднее значение (Average) для времени ответа. Используйте перцентиль P95 или P99, чтобы видеть проблемы реальных пользователей, а не "среднюю температуру по больнице".

### Принцип Actionable Alerts (Полезные действия)

Алерт считается полезным только в том случае, если он требует немедленного вмешательства инженера. Если на алерт можно "просто посмотреть" — это не алерт, а график на дашборде.

**Критерии качества:**
1.  **Наличие Runbook:** Каждое правило обязано иметь аннотацию `runbook_url` со ссылкой на конкретную инструкцию по устранению.
2.  **Dashboard Link:** Прямая ссылка на дашборд с отфильтрованным контекстом (используя переменные в URL).
3.  **Ясность:** Аннотация `summary` должна отвечать на вопросы: "Что случилось?", "На что это влияет?" и "Где искать проблему?".
4.  **Степень важности (Severity):**
    *   `critical`: Разбудить дежурного (PagerDuty, звонок).
    *   `warning`: Уведомить команду в Slack/Email для разбора в рабочее время.

## Борьба с шумом и дребезгом (Flapping)

**Flapping (дребезг)** — состояние, когда метрика колеблется около порогового значения, вызывая каскад уведомлений "Alerting" и "Resolved".

### Методы стабилизации в 2025 году:

1.  **Параметр `for`:** Время ожидания подтверждения проблемы. Рекомендуется устанавливать `for` не менее чем в 3-5 раз больше интервала оценки группы.
2.  **Параметр `keep_firing_for`:** Удерживает алерт в состоянии `Firing` в течение заданного времени даже после возвращения метрики в норму. Это предотвращает закрытие инцидента при кратковременных улучшениях.
3.  **Гистерезис (Порог выхода):** Использование разных порогов для входа в алерт и выхода из него (например, вход при CPU > 90%, выход при CPU < 80%). В Grafana реализуется через сложные выражения `Math`.
4.  **Группировка в Notification Policies:**
    *   `group_wait`: (30с - 1м) Дает системе время собрать алерты по одному инциденту в одну группу.
    *   `group_interval`: (5м) Время между повторными уведомлениями для одной группы.

## Стратегии подавления и маршрутизации

### Управление политиками уведомлений

*   **Иерархия маршрутизации:** Стройте дерево политик от общего к частному. Используйте `continue: true` только если один алерт действительно должен попасть в несколько независимых каналов (например, в лог-систему и в мессенджер).
*   **Mute Timings:** Обязательно настраивайте окна тишины для плановых работ и нерабочего времени для некритичных систем. Это предотвращает "усталость от алертов" (Alert Fatigue).
*   **Label Matching:** Используйте метку `service` или `team` как основной ключ маршрутизации. Метка `severity` должна определять приоритет доставки (Email vs PagerDuty).

### Сравнение: Grafana Alerting vs Prometheus Alertmanager

| Функция | Grafana Alerting | Prometheus Alertmanager |
| :--- | :--- | :--- |
| **Сильные стороны** | Визуализация снимков (Images), доступность данных из SQL/Loki/Cloud. | Подавление зависимостей (Inhibition), масштабируемость Mesh. |
| **Inhibition** | Реализуется через `Math` в выражениях (сложно). | Нативно через `inhibition_rules` (просто). |

**Рекомендация:** Для инфраструктурных алертов (Node Down, Disk Full) предпочитайте Alertmanager. Для бизнес-метрик и комплексных отчетов — Grafana.

## Жизненный цикл и гигиена (Alert Hygiene)

Система алертинга требует регулярного обслуживания, иначе она превращается в бесполезный шум.

1.  **Ежемесячный аудит:**
    *   Выявление "самых шумных" правил. Если алерт срабатывает > 10 раз в день и инцидент не подтверждается — порог неверен.
    *   Проверка актуальности ссылок на Runbook.
2.  **Тестирование:** Используйте функцию **Preview Queries** в интерфейсе при создании правила. Проверьте, как бы сработало правило на исторических данных за последние 24-48 часов.
3.  **Удаление неактивных:** Алерты, которые висят в Silenced больше месяца без плана работ, должны быть удалены.
