# Best Practices: Grafana Alerting

## Определения

**Best Practices Grafana Alerting** — рекомендуемые подходы к настройке правил оповещений, минимизирующие шум и обеспечивающие быструю реакцию на инциденты.

**Текущая версия (февраль 2026):** Grafana 12.x

## Базовые концепции

### Параметры правил алертинга

| Параметр | Рекомендация | Обоснование |
| :--- | :--- | :--- |
| **`for` и интервал оценки** | `for` ≥ 2–3 интервалов оценки | Фильтрация кратковременных аномалий, снижение ложных срабатываний |
| **`NoData`** | Для редких метрик: `NoData=OK`; для критичных: `NoData=Alerting` | Баланс между пропуском проблем и шумом |
| **`Error`** | `Error=Alerting` для критичных правил | Ошибка оценки = потенциальная проблема |
| **Метки (labels)** | Использовать для маршрутизации и дедупликации | Интеграция с политиками уведомлений |
| **Аннотации** | Включать: симптом, предположение, следующий шаг | Ускорение реакции инженера |

### Агрегация шумных метрик

Для метрик с высокой волатильностью используйте пост-агрегацию:

- `reduce()` — агрегация нескольких серий в одно значение
- `avg_over_time()` — усреднение за временное окно
- `max_over_time()` — максимум за окно (для пиковых нагрузок)

**Пример:**

```promql
avg_over_time(cpu_usage{job="app"}[5m]) > 80
```

### Сравнение: Grafana Alerting vs Prometheus Alertmanager

| Критерий | Grafana Alerting | Prometheus Alertmanager |
| :--- | :--- | :--- |
| **Настройка** | Визуальная + YAML | YAML |
| **Сложность правил** | Средняя (выражения, multi-dimension) | Продвинутая (агрегация, корреляция) |
| **Информативность** | Высокая (снимки графиков) | Низкая (текст) |
| **Обработка** | Группировка, глушение, политики | Дедупликация, группировка, inhibition |
| **Зависимости** | Не понимает | Inhibition rules для зависимых алертов |
| **Источники данных** | Множество (Prometheus, Loki, MySQL, etc.) | Только Prometheus-совместимые |

## Практические сценарии

### Рекомендуемая стратегия использования

| Сценарий | Решение |
| :--- | :--- |
| **80% случаев** | Grafana Alerting (пороговые алерты, визуальный контекст) |
| **20% случаев** | Alertmanager (сложные бизнес-алерты, inhibition rules) |

**Принцип:** Эти системы дополняют друг друга. Alertmanager сообщает *что* «все плохо», Grafana присылает снимок, *как именно* «все плохо».

### Типовые конфигурации

#### Для веб-приложений

```yaml
# Интервал оценки: 30s
# for: 1m30s (3 интервала)
# NoData: OK
# Error: Alerting
```

#### Для инфраструктурных метрик

```yaml
# Интервал оценки: 1m
# for: 5m
# NoData: Alerting (инфраструктура должна быть всегда доступна)
# Error: Alerting
```

#### Для бизнес-метрик

```yaml
# Интервал оценки: 5m
# for: 15m
# NoData: OK (бизнес-метрики могут быть непостоянны)
# Error: Warning
```

### Маршрутизация и дедупликация

**Метки для маршрутизации:**

- `severity` — критичность (`critical`, `warning`, `info`)
- `team` — ответственная команда
- `environment` — окружение (`prod`, `staging`, `dev`)
- `service` — имя сервиса

**Пример аннотаций:**

```
Summary: Высокое потребление CPU на {{ $labels.instance }}
Description: CPU usage > 80% в течение 5 минут
Assumption: Возможна утечка ресурсов или аномальная нагрузка
Action: Проверить топ процессов, сравнить с базовой линией
```
