# Лучшие практики Grafana Alerting

## Определения

**Лучшие практики (Best Practices) Grafana Alerting** — рекомендуемые подходы к настройке правил оповещений, минимизирующие уровень шума и обеспечивающие быструю реакцию инженеров на инциденты.

**Текущая версия (февраль 2026):** Grafana 12.x

## Базовые концепции

### Параметры правил алертинга

| Параметр | Рекомендация | Обоснование |
| :--- | :--- | :--- |
| **`for` и интервал оценки** | `for` ≥ 2–3 интервалов оценки | Фильтрация кратковременных аномалий, снижение ложных срабатываний |
| **`NoData`** | Для редких метрик: `NoData=OK`; для критичных: `NoData=Alerting` | Баланс между пропуском реальных проблем и информационным шумом |
| **`Error`** | `Error=Alerting` для критичных правил | Ошибка оценки запроса приравнивается к потенциальной проблеме |
| **Метки (Labels)** | Использовать для маршрутизации и дедупликации | Необходимы для интеграции с политиками уведомлений и группировки |
| **Аннотации** | Включать: симптом, предположение, инструкцию (Runbook) | Ускорение диагностики и локализации проблемы инженером |

### Агрегация шумных метрик

Для метрик с высокой волатильностью рекомендуется использовать функции агрегации во времени:

- `reduce()` — преобразование нескольких серий данных в единое значение.
- `avg_over_time()` — усреднение значений за определенное временное окно.
- `max_over_time()` — выделение максимального значения за окно (полезно для отслеживания пиковых нагрузок).

**Пример запроса:**

```promql
avg_over_time(cpu_usage{job="app"}[5m]) > 80
```

### Сравнение: Grafana Alerting vs Prometheus Alertmanager

| Критерий | Grafana Alerting | Prometheus Alertmanager |
| :--- | :--- | :--- |
| **Настройка** | Визуальный интерфейс (UI) + YAML | Только YAML-конфигурация |
| **Сложность правил** | Средняя (выражения, многомерные алерты) | Продвинутая (агрегация, сложная корреляция) |
| **Информативность** | Высокая (снимки графиков, визуальный контекст) | Низкая (преимущественно текстовые данные) |
| **Обработка** | Группировка, глушение (silences), политики | Дедупликация, группировка, подавление (inhibition) |
| **Зависимости** | Отсутствует встроенный механизм иерархии | Поддержка Inhibition rules для подавления каскадных алертов |
| **Источники данных** | Множество источников (Prometheus, Loki, MySQL и др.) | Только Prometheus-совместимые системы |

## Практические сценарии

### Стратегия выбора системы оповещений

| Сценарий | Рекомендуемое решение |
| :--- | :--- |
| **80% типовых случаев** | Grafana Alerting (пороговые алерты, требующие визуального контекста) |
| **20% сложных случаев** | Alertmanager (сложные бизнес-логики, подавление каскадных сбоев) |

**Принцип взаимодействия:** Эти системы дополняют друг друга. Alertmanager сигнализирует о факте сбоя в инфраструктуре, в то время как Grafana предоставляет наглядный снимок (snapshot) состояния системы в момент инцидента.

### Типовые конфигурации по категориям

#### Веб-приложения (API)

- **Интервал оценки:** 30s
- **Параметр `for`:** 1m30s (три интервала для фильтрации всплесков)
- **`NoData`:** OK
- **`Error`:** Alerting

#### Инфраструктурные метрики (CPU/RAM)

- **Интервал оценки:** 1m
- **Параметр `for`:** 5m (подтверждение устойчивого потребления)
- **`NoData`:** Alerting (инфраструктура должна отдавать метрики непрерывно)
- **`Error`:** Alerting

#### Бизнес-метрики (Заказы/Платежи)

- **Интервал оценки:** 5m
- **Параметр `for`:** 15m
- **`NoData`:** OK (бизнес-активность может иметь естественные паузы)
- **`Error`:** OK / Warning

### Маршрутизация и информативность

**Рекомендуемые метки для маршрутизации:**

- `severity` — критичность (`critical`, `warning`, `info`).
- `team` — ответственная команда (напр. `backend`, `frontend`, `devops`).
- `environment` — окружение (`prod`, `staging`, `dev`).
- `service` — наименование микросервиса.

**Пример наполнения аннотаций:**

- **Summary:** Высокое потребление CPU (Central Processing Unit) на {{ $labels.instance }}
- **Description:** Использование процессора превышает 80% в течение 5 минут.
- **Assumption:** Возможна утечка ресурсов или аномальный всплеск трафика.
- **Action:** Проверить список процессов через `top`, сверить нагрузку с графиками за прошлые сутки.
