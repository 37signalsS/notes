# Лучшие практики алертинга — Grafana Alerting

## Определения

**Лучшие практики (Best Practices) Grafana Alerting** — рекомендуемые подходы к проектированию, настройке и поддержке системы оповещений, направленные на максимизацию отношения "сигнал/шум" и минимизацию времени реакции (MTTR).

## Базовые концепции

### SRE Golden Signals в алертинге

При настройке алертов для сервисов рекомендуется опираться на методологию **RED** (для запросов) или **USE** (для ресурсов).

| Метрика | Принцип алертинга | Пример в Grafana |
| :--- | :--- | :--- |
| **Errors (Ошибки)** | Алертить на долю ошибок (%) от общего трафика, а не на абсолютное кол-во. | `Rate(5xx) / Rate(Total) > 0.05` |
| **Latency (Задержка)** | Использовать перцентили (P95, P99), а не среднее значение (Average). | `Histogram_quantile(0.95, ...)` |
| **Traffic (Трафик)** | Алертить на аномальные отклонения или достижение пределов пропускной способности. | Внезапное падение трафика до 0. |
| **Saturation (Насыщение)** | Алертить при приближении к 100% утилизации ресурсов (CPU, Disk IO, Thread Pools). | `Disk space > 90%` |

### Параметры правил алертинга

| Параметр | Рекомендация | Обоснование |
| :--- | :--- | :--- |
| **`for` и интервал** | `for` ≥ 3 × интервал оценки. | Исключение "мигающих" алертов (flapping) из-за кратковременных пиков. |
| **`NoData`** | Для критичных метрик: `Alerting`. Для редких: `OK`. | `Alerting` на NoData — это "алерт на мониторинг": сигнал, что агент сбора данных упал. |
| **`Error`** | Всегда `Alerting` для критичных путей. | Если запрос не может выполниться, мы считаем систему слепой и потенциально неисправной. |
| **Labels (Метки)** | Минимум: `severity`, `team`, `service`. | Основа для маршрутизации и автоматизации ответов. |
| **Annotations (Аннотации)** | Ссылки на Runbook и Dashboard. | Инженер не должен искать контекст вручную в 3 часа ночи. |

### Группировка и подавление шума

Для предотвращения "шторма алертов" используйте механизмы `Notification Policies`:

- **Group By:** Группируйте алерты по `alertname` и `cluster/env`. Десять упавших микросервисов в одном кластере должны прийти одним сообщением.
- **Group Wait:** Установите `30s-1m`, чтобы Grafana успела собрать все связанные алерты в один пакет.
- **Repeat Interval:** Для критичных алертов — `1h-3h`, для информационных — `24h`.

## Практические сценарии

### Сравнение: Grafana Alerting vs Prometheus Alertmanager

| Критерий | Grafana Alerting | Prometheus Alertmanager |
| :--- | :--- | :--- |
| **Источники данных** | Мульти-источники (SQL, Cloudwatch, Loki) | Только Prometheus-совместимые |
| **Визуализация** | Включает снимки графиков (snapshots) | Преимущественно текстовые уведомления |
| **Управление** | UI + Provisioning (YAML) | Только конфигурационные файлы (YAML) |
| **Иерархия** | Слабая поддержка Inhibition | Сильная (Inhibition rules — подавление зависимых алертов) |

**Рекомендация:** Используйте Grafana для алертов, требующих визуального подтверждения (бизнес-метрики, сложные запросы к разным БД). Используйте Prometheus Alertmanager для базовой инфраструктуры и сложных графов зависимостей.

### Стратегия управления "тишиной" (Silences)

- **Mute Timings:** Используйте для запланированных работ и нерабочего времени (если сервис не 24/7).
- **Temporary Silences:** Создавайте "тишину" в UI только при активном расследовании инцидента, чтобы не дублировать уведомления.
- **Expiry:** Всегда ставьте время истечения. "Вечная тишина" — признак забытого и бесполезного алерта.

### Жизненный цикл и аудит алертов

1.  **Принцип "Actionable":** Каждый алерт должен требовать действия. Если на алерт никто не реагирует — он должен быть удален или переведен в статус `info` (Dashboard only).
2.  **Регулярный аудит:** Раз в месяц проверяйте топ самых шумных алертов.
3.  **Тестирование:** Используйте `Preview context` в интерфейсе Grafana для проверки правила на исторических данных перед активацией.
