# Обзор Grafana Alloy

**Grafana Alloy** (ранее известный как Grafana Agent в режиме "Flow") — это новый флагманский агент для сбора телеметрии от Grafana Labs. Он построен на основе [OpenTelemetry Collector](../OpenTelemetry/opentelemetry_overview.md) и представляет собой единое, мощное и гибкое решение для сбора, обработки и отправки метрик, логов, трассировок и профилей.

Alloy является **официальным преемником** и в конечном итоге **полностью заменит** два предыдущих агента Grafana:
1.  **Grafana Agent (static mode):** Традиционный агент с конфигурацией в статическом YAML-формате. Его поддержка будет прекращена осенью 2025 года.
2.  **Promtail:** Агент, предназначенный исключительно для сбора логов и их отправки в Loki. Его поддержка будет прекращена весной 2026 года.

Grafana Alloy призван заменить их обоих, предоставив унифицированный, более мощный и масштабируемый подход к управлению потоками данных.

## Ключевые особенности

*   **Унифицированный сбор:** Собирает все основные типы телеметрических данных (metrics, logs, traces, profiles) с помощью одного агента.
*   **Компонентная модель:** Конфигурация описывается на языке River (диалект HCL от HashiCorp), который позволяет определять компоненты и выстраивать из них конвейер (pipeline) обработки данных. Это делает конфигурацию более читаемой, переиспользуемой и мощной по сравнению с плоским YAML.
*   **Совместимость с экосистемой:**
    *   **Prometheus:** Включает в себя встроенный код Prometheus для скрапинга метрик, что обеспечивает полную совместимость с конфигурациями Prometheus.
    *   **Loki:** Поддерживает все возможности Promtail по сбору логов, включая service discovery и обработку лейблов.
    *   **OpenTelemetry:** Являясь дистрибутивом OpenTelemetry Collector, Alloy полностью совместим с его компонентами (receivers, processors, exporters).
*   **Мощная обработка данных:** Позволяет трансформировать, фильтровать и обогащать данные прямо на агенте перед отправкой в бэкенд.
*   **Встроенный UI для отладки:** Поставляется с веб-интерфейсом, который позволяет в реальном времени инспектировать состояние компонентов, их взаимосвязи, проходящие через них данные, а также визуализировать пайплайны обработки данных и список пиров в кластере.
*   **Горизонтальное масштабирование:** Alloy спроектирован для работы в режиме кластера, поддерживая горизонтальное масштабирование в Kubernetes. Это позволяет динамически увеличивать мощности для обработки данных (например, при резком росте объема логов или метрик), значительно повышая отказоустойчивость и скорость обработки, что решает проблему "скачков" объема данных.

## Язык конфигурации River

Вместо традиционного YAML, Alloy использует язык **River**. Его синтаксис похож на Terraform (HCL). Конфигурация в River — это граф (pipeline) из компонентов, где выходы одного компонента служат входами для другого.

**Пример конфигурации River:**

```hcl
// 1. Обнаружение локальных лог-файлов
loki.source.file "local_logs" {
  targets = discovery.file.local_files.targets
}

// Используем service discovery для поиска файлов
discovery.file "local_files" {
  path_targets = [{
    __path__ = "/var/log/*.log",
  }]
}

// 2. Отправка логов в Loki
loki.write "to_loki_cloud" {
  endpoint {
    url = "https://loki-prod-us-central-0.grafana.net/loki/api/v1/push"
    // Аутентификация настраивается отдельно
  }
  // Внешние лейблы, которые добавятся ко всем логам
  external_labels = {
    source = "grafana-alloy",
  }
}

// 3. Установка связи: выход loki.source.file является входом для loki.write
loki.write.to_loki_cloud.receiver = loki.source.file.local_logs.receiver
```
В этом примере:
1.  `discovery.file` находит все файлы, соответствующие шаблону `/var/log/*.log`.
2.  `loki.source.file` начинает читать эти файлы.
3.  `loki.write` настраивает отправку данных в Loki.
4.  Последняя строка `loki.write.to_loki_cloud.receiver = loki.source.file.local_logs.receiver` явно определяет поток данных, соединяя "выход" компонента чтения логов с "входом" компонента отправки.

Такой подход делает поток данных очевидным и легко отлаживаемым.

## Миграция на Grafana Alloy

Grafana Labs предусмотрела инструменты для упрощения миграции со своих предыдущих агентов на Alloy. В сам бинарник Alloy встроены конвертеры, которые позволяют:

*   Конвертировать конфигурации **Promtail** в формат Alloy.
*   Конвертировать конфигурации **Grafana Agent** в формат Alloy.
*   Конвертировать конфигурации **Prometheus** (например, `scrape_configs`) в формат Alloy, позволяя Alloy взять на себя роль скрапера метрик.
*   Использовать Alloy в качестве замены **OpenTelemetry Collector**, так как он построен на его основе.

Это значительно упрощает переход на Alloy, позволяя переиспользовать существующие конфигурации и минимизировать ручную работу.

## Alloy vs. OpenTelemetry Collector

Хотя Alloy основан на OpenTelemetry Collector, между ними есть различия:
*   **Язык конфигурации:** Alloy использует River, в то время как стандартный OTel Collector использует YAML. River обеспечивает более явное определение потоков данных.
*   **Интеграция с Prometheus и Loki:** Alloy включает в себя специфичный код из Prometheus и Promtail, обеспечивая 100% совместимость с их форматами конфигурации, что не всегда гарантировано в стандартном OTel Collector.
*   **Фокус:** Alloy ориентирован в первую очередь на экосистему Grafana (Loki, Mimir, Tempo), хотя и может отправлять данные в любые другие OTel-совместимые бэкенды.

В целом, если вы строите свой стек наблюдаемости вокруг продуктов Grafana, **Grafana Alloy является предпочтительным выбором** для агента сбора данных.

## Преимущества и Ограничения Grafana Alloy

### Преимущества

*   **Унификация:** Единый агент для всех типов телеметрии (метрики, логи, трассировки, профили), что упрощает развертывание и управление стеком наблюдаемости.
*   **Масштабируемость:** Возможность горизонтального масштабирования и работы в кластере (особенно в Kubernetes) позволяет эффективно обрабатывать большие объемы данных и динамические нагрузки.
*   **Отказоустойчивость:** Кластерный режим работы повышает устойчивость к сбоям.
*   **Простота миграции:** Наличие встроенных конвертеров конфигураций с Promtail, Grafana Agent и Prometheus.
*   **Основа OpenTelemetry:** Полная совместимость с экосистемой OpenTelemetry, что обеспечивает стандартизацию и гибкость.
*   **Удобство для экосистемы Grafana:** Оптимизирован для работы с Loki, Mimir, Tempo и другими продуктами Grafana Stack.

### Ограничения

*   **Новизна продукта:** Как относительно новый продукт, Alloy может иметь менее зрелую документацию и меньшее сообщество по сравнению с более старыми решениями. Возможно появление изменений, требующих адаптации.
*   **Зависимость от Grafana Labs:** Развитие функционала полностью определяется командой Grafana Labs. Хотя продукт Open Source, возможность расширения пользовательскими плагинами ограничена, так как все компоненты встроены в единый бинарник. Это отличает его от решений с богатой экосистемой плагинов (например, Fluentd).
*   **Ограниченный список компонентов:** По сравнению с универсальными коллекторами типа FluentBit или Vector, список встроенных компонентов для сбора и отправки данных в Alloy пока менее обширен, хотя и растет.

## Пример: Full-Stack Observability для PostgreSQL с помощью Alloy

Этот пример демонстрирует, как Grafana Alloy может выступать в роли единого центра для сбора всех типов телеметрии (метрики, логи, трейсы) от PostgreSQL и связанных с ним приложений.

**Цель:**
1.  **Собирать метрики** с `postgres_exporter`.
2.  **Собирать трейсы** от приложения и от расширения `pg_tracing` через OTLP.
3.  **Собирать логи** из файла `postgresql.log`.
4.  **Обогащать логи**, извлекая из них `trace_id` для корреляции с трейсами.
5.  **Отправлять** данные в соответствующие бэкенды: Mimir/Prometheus (метрики), Loki (логи), Tempo (трейсы).

### Конфигурация Grafana Alloy (`alloy.conf`)

```hcl
// --- 1. СБОР ТРЕЙСОВ ---
// Приемник OTLP, который будет слушать трейсы от приложения и pg_tracing.
otelcol.receiver.otlp "traces_receiver" {
  grpc {}
  http {}

  // Выход этого приемника будет отправлен в экспортер Tempo.
  output {
    traces = [otelcol.exporter.otlp.traces_exporter.input]
  }
}

// Экспортер, отправляющий трейсы в Tempo.
otelcol.exporter.otlp "traces_exporter" {
  client {
    endpoint = "tempo:4317" // Адрес Tempo
    tls {
      insecure = true
    }
  }
}

// --- 2. СБОР ЛОГОВ ---
// Обнаружение лог-файла PostgreSQL.
discovery.file "log_files" {
  path_targets = [{
    __path__ = "/var/lib/postgresql/data/log/postgresql.log", // Путь к логу внутри контейнера
    "host"   = "postgresql",
    "job"    = "postgres-logs",
  }]
}

// Чтение лог-файла.
loki.source.file "read_logs" {
  targets = discovery.file.log_files.targets
  // Перенаправляем прочитанные логи на следующий этап обработки.
  forward_to = [loki.process.add_trace_id.receiver]
}

// Обработка логов: извлечение trace_id.
loki.process "add_trace_id" {
  // Этап 1: Ищем строки, содержащие комментарий sqlcommenter.
  stage.match {
    selector = `{job="postgres-logs"}`
    // Выбираем только те строки, где есть "traceparent".
    stages = [
      { pipeline_name = "extract_trace_id", expression = ".*traceparent.*" },
    ]
  }
  
  // Этап 2: С помощью регулярного выражения извлекаем trace_id.
  stage.regex {
    expression = ".*traceparent='00-(?P<trace_id>[a-f0-9]{32})-[a-f0-9]{16}-01'.*"
    source     = "log_line" // Псевдо-поле, куда помещается вся строка лога
  }
  
  // Этап 3: Устанавливаем извлеченное значение как внутренний лейбл traceID.
  // Grafana автоматически использует этот лейбл для связи логов и трейсов.
  stage.label_drop {
    values = {
      "trace_id" = `^(?P<value>.*)$`,
    }
    target_label = "traceID"
  }

  // Перенаправляем обработанные логи в Loki.
  forward_to = [loki.write.loki_writer.receiver]
}

// Экспортер логов в Loki.
loki.write "loki_writer" {
  endpoint {
    url = "http://loki:3100/loki/api/v1/push"
  }
}

// --- 3. СБОР МЕТРИК ---
// Скрапинг метрик с postgres_exporter.
prometheus.scrape "postgres_exporter_scrape" {
  targets = [{
    "__address__" = "postgres_exporter:9187",
    "job"         = "postgres-metrics",
  }]
  // Перенаправляем метрики в удаленное хранилище (Mimir/Prometheus).
  forward_to = [prometheus.remote_write.metrics_writer.receiver]
}

// Экспортер метрик в Mimir или Prometheus.
prometheus.remote_write "metrics_writer" {
  endpoint {
    url = "http://mimir:9009/api/v1/push"
  }
}
```

### Поток данных

1.  **Трейсы**: Приложение и `pg_tracing` отправляют спаны по протоколу OTLP. `otelcol.receiver.otlp` в Alloy принимает их и через `otelcol.exporter.otlp` пересылает в Tempo.
2.  **Логи**: `loki.source.file` читает лог PostgreSQL. `loki.process` анализирует строки, находит `traceparent` в `sqlcommenter`, извлекает `trace_id` и устанавливает его как специальный лейбл `traceID`. Затем `loki.write` отправляет обогащенные логи в Loki.
3.  **Метрики**: `prometheus.scrape` собирает метрики с эндпоинта `postgres_exporter` и через `prometheus.remote_write` отправляет их в Mimir/Prometheus.

Такая конфигурация позволяет в Grafana бесшовно переключаться между метриками, логами и трейсами, получая полную картину работы системы. Например, увидев медленный SQL-запрос в трейсе, можно в один клик перейти ко всем логам, связанным с этим запросом, благодаря общему `trace_id`.
