# Grafana: Дашборды

**Актуально для:** Grafana 13.2.x / 12.x (LTS)

> **См. также:** [Обзор Grafana](./grafana_overview.md) · [Шаблонизация](./grafana_templating.md) · [Провиженинг](./grafana_provisioning.md)

## Определения

- **Дашборд (Dashboard)**: Набор из одной или нескольких панелей для визуализации данных. Он является визуальной проекцией модели наблюдаемости системы и должен помогать отвечать на конкретные эксплуатационные вопросы: работает ли система сейчас, где узкое место, как поведение менялось во времени. Каждый дашборд является JSON-объектом, что позволяет его экспортировать, версионировать и развертывать автоматически.
- **Организация метрик**: Продуманные группировки, единообразное оформление панелей, использование переменных для фильтрации и лаконичные визуализации, которые исключают перегрузку деталей.
- **Панель (Panel)**: Базовый элемент дашборда для визуализации данных (например, график, таблица, датчик).
- **Переменная (Variable)**: Интерактивный элемент управления, позволяющий динамически изменять данные, отображаемые на панелях (например, выбирать сервер или `namespace` из списка).
- **Аннотация (Annotation)**: Маркер на графике, отмечающий событие (например, деплой или инцидент) для помощи в корреляции изменений метрик.
- **Плейлист (Playlist)**: Функция, позволяющая автоматически и циклично переключаться между несколькими дашбордами через заданный интервал, что удобно для NOC-экранов.
- **Снимок (Snapshot)**: Интерактивный, но статичный "слепок" дашборда с зафиксированными данными на определенный момент времени.
- **Библиотечная панель (Library Panel)**: Переиспользуемая панель, которую можно добавить на несколько дашбордов. Изменение в библиотечной панели автоматически применяется ко всем дашбордам, где она используется.
- **Публичный дашборд (Public Dashboard)**: Функция, позволяющая делиться дашбордом через публичную ссылку (только чтение) без необходимости создания учетных записей для конечных пользователей. Поддерживает кеширование на стороне Grafana.
- **Сервисный аккаунт (Service Account)**: Основной механизм аутентификации для автоматизации (API, CI/CD), заменивший устаревшие API-ключи. Позволяет гибко настраивать роли и сроки действия токенов.
- **Dynamic Dashboards**: Движок дашбордов нового поколения (GA в Grafana 13.0, включён по умолчанию), построенный на SDK **Grafana Scenes** и схеме **v2**. Поддерживает вложенность рядов и табов до трёх уровней, условную отрисовку (conditional rendering/show-hide), продвинутые раскладки (grid, auto-grid, rows, tabs) и программное управление состоянием. Понятие **Dashboard Scenes** (Grafana 11+) — движок в стадии развития; начиная с 13.x продуктовая реализация называется Dynamic Dashboards.
- **Ряд (Row)**: Группировка панелей, которую можно свернуть или развернуть. Позволяет организовать дашборд в логические секции и экономить ресурсы браузера: свёрнутые по умолчанию ряды могут не запрашивать данные до раскрытия.
- **Переопределение (Override)**: Правило уровня панели, которое изменяет отображение выборочных полей или серий, не затрагивая остальные (например, задать красный цвет и другие единицы измерения только для ряда `errors`).
- **Ссылка данных (Data Link)**: Гиперссылка на отдельной серии, поле таблицы или значении, ведущая на другой дашборд, конкретную панель или внешнюю систему, часто с динамической подстановкой переменных и временного диапазона.
- **UID дашборда**: Стабильный текстовый идентификатор (в отличие от внутреннего числового `id`), используемый в URL, ссылках и API. Позволяет предсказуемо ссылаться на дашборд между инстансами и при миграциях.
- **Папка (Folder)**: Контейнер для логической группировки дашбордов и централизованного назначения прав доступа. Имеет собственный `uid` и используется в provisioning/API для размещения дашбордов.

## Основные концепции

### JSON-модель как основа

Каждый дашборд в Grafana — это структурированный JSON-документ. Этот принцип обеспечивает:

- **Версионирование**: Автоматическое сохранение истории изменений, сравнение (diff) и откат.
- **Переносимость**: Легкий экспорт/импорт между инстансами.
- **Infrastructure as Code (IaC)**: Управление через Git и автоматический деплой (см. [Provisioning](./grafana_provisioning.md)).
- **Kubernetes Native**: В облачных средах дашборды часто доставляются через `ConfigMap` с использованием `sidecar`-контейнеров (например, в Rancher или Kube-Prometheus-Stack). Это позволяет хранить дашборды рядом с кодом приложения. В Grafana 13.x появился нативный [Git Sync](#дашборды-как-код-dashboard-as-code), который для многих случаев заменяет sidecar.

Начиная с Grafana 12.2 и особенно в 13.x дашборды существуют в **трёх JSON-моделях**:

- **Classic** — «плоский» JSON (описан ниже), формат по умолчанию до версии 12.2. По-прежнему используется для экспорта/импорта, файлового провиженинга и дашбордов из библиотеки grafana.com;
- **V1 Resource** — та же Classic-модель, обёрнутая в Kubernetes-style ресурс `kind: Dashboard`, `apiVersion: dashboard.grafana.app/v1` (`spec` содержит Classic-модель). Была форматом обмена по умолчанию с 12.2 по 13.0;
- **V2 Resource** — актуальная схема **v2** (`apiVersion: dashboard.grafana.app/v2`), на которой построены Dynamic Dashboards: табы, условная отрисовка, продвинутые раскладки, все элементы — Kubernetes-ресурсы.

Провиженинг и API принимают как Classic-обёртку (`{"dashboard": {...}, "overwrite": true}`), так и Kubernetes-представление (`{"kind": "Dashboard", "spec": {...}}`).

### Структура JSON-модели дашборда (Classic)

Классическая модель сериализуется в плоский JSON-объект верхнего уровня. Ключевые поля и их назначение:

```json
{
  "uid": "k8s-health",
  "title": "Kubernetes — Здоровье приложения",
  "tags": ["env:prod", "layer:backend"],
  "timezone": "browser",
  "schemaVersion": 41,
  "version": 12,
  "refresh": "1m",
  "time": { "from": "now-6h", "to": "now" },
  "templating": { "list": [ /* описание переменных */ ] },
  "annotations": { "list": [ /* описание аннотаций */ ] },
  "panels": [ /* массив панелей верхнего уровня и рядов */ ],
  "editable": true,
  "fiscalYearStartMonth": 0
}
```

| Поле | Назначение |
| :--- | :--- |
| `uid` | Стабильный идентификатор дашборда. Если не задан при импорте — генерируется. Используется в URL (`/d/<uid>/`), API и ссылках. |
| `title` | Отображаемое имя дашборда. |
| `tags` | Список тегов для поиска и фильтрации. |
| `schemaVersion` | Версия схемы Grafana. Внутренний параметр, определяет, как Grafana мигрирует структуру при загрузке. Не редактируется вручную; значение растёт с мажорными версиями (для v1-схемы в 13.x — 41–42, финальная для v1-API — 42). В схеме v2 структура дашборда иная (`spec`). |
| `version` | Счётчик сохранений дашборда. Автоматически увеличивается на 1 при каждом `Save`. Используется для optimistic concurrency при API-обновлениях (`overwrite: false` отклонит правку, если версия устарела). |
| `refresh` | Интервал автообновления дашборда (например, `30s`, `1m`, `5m`). |
| `time` | Диапазон по умолчанию (`from`/`to`), поддерживает относительные значения `now-6h` и абсолютные `2026-01-01T00:00:00Z`. |
| `templating.list` | Массив переменных дашборда. |
| `annotations.list` | Массив аннотаций (источников событий). |
| `panels` | Массив панелей и рядов (`type: "row"`). Вложенные панели ряда хранятся в поле `panels` самого ряда. |
| `editable` | Флаг, запрещающий/разрешающий редактирование через UI. При provisioning с `editable: false` дашборд становится read-only, что защищает его от расхождения с кодом в Git. |

Модель панели также является JSON-объектом. Минимально осмысленная панель содержит `type` (визуализация), `title`, `datasource`, `targets` (запросы) и `fieldConfig` (настройки отображения полей). Редактирование «сырого» JSON доступно через **Dashboard settings → JSON Model** и через API `api/dashboards/uid/<uid>`, что критично для IaC и программных правок.

### Уровни дашбордов (Onepager & Drill-down)

Для эффективной эксплуатации рекомендуется разделять дашборды по уровням абстракции, создавая иерархию переходов:

- **L1 — Onepager (Обзорный)**: Здоровье всей платформы или кластера на одном экране. Ключевые SLO и цветовые «светофоры» для дежурных. Должен помещаться на один экран без прокрутки.
- **L2 — Drill-down (Продуктовый/Сервисный)**: Полные RED-метрики конкретного микросервиса. Клик на индикатор в Onepager должен вести на этот уровень.
- **L3 — Resource (Диагностический)**: USE-метрики ресурсов, состояние JVM (GC, Hiccups), детализация дискового ввода-вывода и сети. Нужны для поиска первопричины.

### Компоненты дашборда

#### Панели (Panels)

Базовые элементы визуализации. В Grafana 12+ выбор панели диктуется не только эстетикой, но и типом данных.

| Тип панели | Назначение | Особенности |
| :--- | :--- | :--- |
| **Time series** | Временные ряды, тренды | Основная панель для большинства метрик |
| **Stat / Gauge** | Текущие значения, прогресс | Цветовые пороги (thresholds), компактность |
| **Table** | Структурированные списки | Трансформации данных, ссылки на другие дашборды |
| **State timeline** | Состояние статусов во времени | Идеально для аптайма и состояний подов |
| **Heatmap** | Распределение значений | Анализ задержек (latency buckets) |
| **Flame graph** | Профилирование (Phlare/Pyroscope) | Визуализация стеков вызовов CPU/Memory |
| **Canvas** | Интерактивные схемы | Визуализация топологии сети или физических объектов |
| **Datagrid** | Редактируемые данные (v12+) | Просмотр и редактирование данных непосредственно в Grafana |
| **Trends** | Анализ зависимостей | Сравнение данных без временной привязки |
| **Bar chart** | Категориальные сравнения | Альтернатива столбцам в Table; подходит для единичных значений по группам |
| **Pie chart / Donut** | Доли и распределения | Визуализация состава (например, запросы по кодам ответа) |
| **Node Graph** | Топология и зависимости | Граф связей сервисов (источник/цель), интегрируется с Tempo/Trace |
| **Traces** | Трейсы распределённых вызовов | Визуализация спанов из Tempo/Jaeger поверх временной шкалы |
| **Status history** | История изменения статусов | Похож на State timeline, но с агрегацией по временным «корзинам» |
| **Alert list** | Сводка активных алертов | Отображение сработавших оповещений прямо на дашборде |
| **Text** | Документация и контекст | Markdown/HTML описание, ссылки на Runbook и владельцев |

#### Библиотечные панели (Library Panels)

Решают проблему дублирования логики. Стандартные панели для типовых сервисов (например, Nginx или JVM) создаются один раз и подключаются к десяткам дашбордов. При обновлении PromQL-запроса в библиотеке изменения применяются повсеместно.

#### Переменные (Variables)

Обеспечивают динамичность и фильтрацию.
- **Типы**: `Query` (из источника), `Custom` (ручной список), `Datasource`, `Interval`.
- **Повторение (Repeating)**: Позволяют автоматически создавать строки или панели для каждого значения переменной (например, по одной панели на каждый диск сервера).
- **Взаимозависимость**: Изменение одной переменной (Cluster) может обновлять список другой (Node).

**Важно**: Переменные не работают в серверных оповещениях (Alerting), так как алерты должны иметь статичный контекст для вычисления. В запросах алертинга вместо переменных используются Recording Rules или фиксированные селекторы меток.

**Подстановка в запросы и форматы значений.** Переменная вставляется как `$var` или `${var}`. Доступны модификаторы формата:
- `${var}` — значение по умолчанию (обычно `regex`/строка для одиночного, многострочный список для multi-value).
- `${var:raw}` — «как есть», без кавычек/экранирования (нужно для именования в заголовках или `label_replace`).
- `${var:csv}` — значения через запятую (`a,b,c`), удобно для `in (${var:csv})`.
- `${var:doublequote}` — каждое значение в кавычках, разделитель `, ` (типично для PromQL `=~"^(a|b)$"`).
- `${var:pipe}` — значения через `|` (для regex-матчинга `=~"a|b"`).
- `${var:json}` — JSON-массив (для JSONPath/SQL).

Multi-value переменные (`Multi-value` в настройках) генерируют несколько серий/значений — например, `instance=~"${instance:pipe}"`.

**Повторение панелей и рядов (Repeating).** Опция `Repeat` на панели (или на ряду) заставляет Grafana создавать копию панели для каждого значения multi-value переменной. Полезно для гомогенных ресурсов (по панели на диск, узел или namespace). Нюансы:
- Повторение работает только с multi-value переменными.
- Вложенное повторение (ряд повторяется по `$cluster`, а панель внутри — по `$node`) требует двух связанных переменных.
- Повторяющиеся панели не поддерживаются в публичных дашбордах (Public Dashboards); в Dynamic Dashboards (схема v2) работают, но исторически имели ограничения (например, show/hide-правила применялись ко всем копиям сразу — исправлено в 12.x). Для сложных сценариев предпочтительна программная генерация через Scenes SDK.

#### Аннотации (Annotations)

Визуальные маркеры событий (деплои, перезагрузки, инциденты). Позволяют коррелировать всплески метрик с изменениями в системе. Источником могут быть как ручные отметки, так и автоматические запросы к Prometheus, Loki или API.

Типы аннотаций:
- **Built-in**: автоматические события Grafana (например, деплои при интеграции с CI/CD через Grafana Provisioning или Git Sync).
- **Grafana (annotation query)**: запрос к источнику данных, возвращающий временные метки событий (например, `ALERTS{alertstate="firing"}` из Prometheus или лог-строки об ошибках из Loki). Для PromQL-источников включите переключатель **Annotations & Alerts** в настройках запроса панели, чтобы он одновременно поставлял и данные, и аннотации.
- **Granular/Region**: помечают не точку, а диапазон (например, окно планового обслуживания).

#### Переопределения (Overrides) и настройка полей (Field config)

Поведение панели управляется `fieldConfig`:
- **Defaults** — базовые настройки для всех полей панели: `unit` (единицы, например `reqps`, `bytes`, `percent`), `decimals`, `min`/`max`, `thresholds` (цветовые пороги), `color` (схема окраски), `custom` (специфичные для типа панели опции).
- **Overrides** — выборочные правила, применяемые к подмножеству полей по матчеру:
  - `byName` — по точному имени серии/поля;
  - `byRegexp` — по регулярному выражению в имени;
  - `byType` — по типу данных (например, `number`);
  - `byFrameRef` — по ссылке на конкретный запрос.

Типичный пример: выделить красным только ряд `errors` поверх общих зелёных порогов.

```json
"fieldConfig": {
  "defaults": {
    "unit": "reqps",
    "thresholds": { "mode": "absolute", "steps": [
      { "color": "green", "value": null },
      { "color": "red", "value": 100 }
    ] }
  },
  "overrides": [
    {
      "matcher": { "id": "byName", "options": "errors" },
      "properties": [
        { "id": "color", "value": { "fixedColor": "red", "mode": "fixed" } },
        { "id": "custom.lineStyle", "value": { "dashLength": 0, "gapLength": 0, "type": "solid" } }
      ]
    }
  ]
}
```

Overrides применяются после трансформаций и поверх defaults, что позволяет, например, скрывать (`custom.hideFrom`), переименовывать или менять единицы измерения только для части серий без правки запроса.

#### Ссылки данных (Data Links)

Data Link привязывается к серии, полю таблицы или отдельному значению и открывает URL при клике. Поддерживаются встроенные переменные ссылки:
- `${__series.name}`, `${__field.name}` — имя серии/поля;
- `${__value.raw}`, `${__value.text}` — сырое/отформатированное значение;
- `${__url_time_range}` — текущий диапазон времени в формате URL;
- `${__from}`, `${__to}` — метки начала/конца диапазона (в мс);
- `${var}` — значения переменных дашборда.

Это позволяет, например, кликнув по серии `pod=web-1`, перейти на диагностический дашборд с подставленным `var-pod=web-1` и тем же временным окном. Data Links дополняют Data Correlations (см. ниже): Correlations автоматически предлагают переходы по общим лейблам, а Data Links задаются вручную на уровне панели.

### Трансформации и обработка данных

Практическое руководство с готовыми сценариями — в файле [Трансформации, Library Panels и режимы показа](./grafana_transformations_and_library_panels.md). Ниже — краткий обзор.

Трансформации (Transformations) позволяют изменять данные на стороне Grafana перед отрисовкой:
- **Join by field**: Объединение данных из разных источников (например, Prometheus и SQL).
- **Config from query results**: Динамическая настройка порогов панели на основе данных из другого запроса.
- **Filter by name/value**: Очистка графиков от ненужных рядов.
- **Reduce**: Агрегация каждого ряда до одного значения (min/max/mean/last) — основа для Stat/Gauge из временных рядов.
- **Group by / Aggregate**: Группировка по полю с агрегирующей функцией (аналог `GROUP BY` в SQL).
- **Outer join / Join by labels**: Соединение по общим лейблам/полям нескольких источников (Prometheus + SQL).
- **Labels to fields / Series to rows**: Поворот (pivot) данных — превращение лейблов в колонки таблицы или серий в строки.
- **Merge**: Объединение результатов нескольких запросов в одну таблицу по совпадающим полям.
- **Organize fields**: Переименование, перестановка и скрытие колонок.
- **Convert field type / Extract fields**: Смена типа (string↔number) и извлечение полей из JSON-строки.

Пример сценария «Join by field»: к метрикам нагрузки из Prometheus добавляется справочник имён сервисов из PostgreSQL по общему ключу `service_id`, и итоговая таблица обогащается человекочитаемыми названиями. Трансформации выполняются на стороне Grafana (в браузере при интерактивном просмотре или на backend при рендеринге/алертинге), поэтому тяжёлые преобразования больших наборов могут влиять на отзывчивость — предпочтительно агрегировать данные на уровне источника (Recording Rules).

### Производительность и масштабируемость

Для дашбордов с сотнями панелей или огромным количеством пользователей:
- **Query Caching**: Снижение нагрузки на БД (Prometheus, VictoriaMetrics) за счет кеширования результатов.
- **Streaming (Live)**: Получение данных в реальном времени через WebSockets для критических метрик.
- **Min Interval**: Предотвращение избыточной детализации (не запрашивать больше точек, чем пикселей).
- **Recording Rules**: Перенос тяжелых вычислений на сторону источника данных.

Конкретные рычаги производительности на уровне панели и дашборда:
- **Max data points (`maxDataPoints`)**: ограничивает количество точек, запрашиваемых у источника (по умолчанию — число пикселей ширины панели). Снижает нагрузку на источник и браузер.
- **Min interval (`min interval`)**: минимальный шаг агрегации (например, `1m`), запрещающий запрашивать суб-секундную детализацию для долгих диапазонов. Предотвращает «одна точка на пиксель» и избыточные запросы к TSDB.
- **Concurrent panel rendering**: Grafana рендерит панели параллельно; при сотнях панелей используйте свёрнутые ряды (`collapsed rows`), чтобы отложить запросы до раскрытия.
- **Query caching** (Grafana Enterprise/Cloud и провиженинг кеш-прокси): результат кешируется на N секунд, что критично для NOC-экранов с общим источником.
- **Лимиты источника**: настраивайте `timeout` и ограничения строк (например, Loki `maxLines`) во избежание зависаний отдельных панелей.
- **Dashboard preloading / Playlist kiosk**: для стеновых экранов отключайте ненужные панели и используйте `?kiosk` для минимизации DOM.
### Инструменты для анализа

- **Shared Crosshair**: Опция для синхронного отображения перекрестия на всех графиках дашборда, что помогает визуально сопоставлять данные в один момент времени.
- **Time Range Controls**: Мощные элементы управления для быстрого выбора временного диапазона. Фиксированные окна (`5m`, `1h`) нужны для сравнимости; относительные — для оперативного анализа. Используйте `override` для панелей, где требуется иная гранулярность.
- **Drilldown**: Настройка ссылок с передачей переменных (`dashboard links` и `panel links`) для перехода от обзорных к диагностическим дашбордам с сохранением контекста выбора.
- **Связи данных (Data Correlations)**: (Grafana 10+) Функция для автоматического связывания данных между разными источниками (например, переход от графика Prometheus к логам Loki по общему `label`). Позволяет определять правила корреляции на уровне дашборда или организации. Подробнее — [Корреляции и Exemplars](./grafana_correlation_exemplars.md).

### Управление временем и URL-параметры дашборда

Диапазон времени задаётся относительными выражениями (`now-6h` → `now`), фиксированными (`2026-01-01T00:00:00Z` → `2026-01-01T12:00:00Z`) или ключевыми словами (`now/d` — начало текущего дня). Для повторяемости отчётов используйте фиксированные окна; для оперативного мониторинга — относительные.

Дашборд можно открыть с предустановленным состоянием через URL-параметры (полезно для встраивания, рассылок и NOC-экранов):

| Параметр | Назначение | Пример |
| :--- | :--- | :--- |
| `?orgId=` | Переключение организации (при нескольких org) | `?orgId=2` |
| `&from=` / `&to=` | Диапазон времени в мс или относительный | `&from=now-24h&to=now` |
| `&var-<name>=` | Значение переменной дашборда | `&var-cluster=prod&var-namespace=default` |
| `&refresh=` | Интервал автообновления | `&refresh=30s` |
| `&kiosk` | Полноэкранный режим без сайдбара | `/d/<uid>?kiosk` |
| `&kiosk=tv` | Полноэкранный режим без верхней панели (для TV) | `/d/<uid>?kiosk=tv` |
| `&theme=` | Тема оформления | `&theme=light` |
| `&viewPanel=<id>` | Открыть только одну панель (fullscreen panel) | `&viewPanel=12` |

Пример ссылки для дежурного: `https://grafana.example.com/d/k8s-health?orgId=1&from=now-3h&to=now&var-cluster=prod&refresh=1m&kiosk`. Эти же параметры подставляются автоматически при копировании ссылки «Share → Link».

### Организация: папки, теги и доступ

- **Папки**: Структурируйте по доменам и критичности:
  - `00-Overview` — обзорные дашборды
  - `10-Platform` — инфраструктура
  - `20-Services` — сервисы по командам
  - `30-Diagnostics` — диагностические
- **Нейминг дашбордов**: Формат `SVC <Название> — <Метрика>`, например `SVC Checkout — Latency`.
- **Теги**: `env:prod`, `env:staging`, `team:payments`, `team:auth`, `layer:frontend`, `layer:backend`.
- **Доступ**: Ограничивайте редактирование обзорных панелей и фиксируйте их версии. Для массового распространения структуры применяйте [provisioning](./grafana_provisioning.md).
- **Публичные дашборды (Public Dashboards)**: Позволяют делиться данными через публичную ссылку без необходимости логина. Данные кешируются на стороне Grafana для защиты источника от перегрузки. Доступны настройки фильтрации по переменным.
- **Dynamic Dashboards (Grafana 13.x)**: движок нового поколения (на основе Scenes SDK) делает дашборды быстрее и управляемее программно: вложенность рядов/табов до трёх уровней, переменные и аннотации в боковой панели, условная отрисовка. В 13.x включён по умолчанию, существующие дашборды мигрируют в схему v2 автоматически.

**Папки и их роль в доступе.** Папка — не только группировка, но и единица назначения прав (Folder-based RBAC). Назначение прав на папку наследуется всеми дашбордами внутри, что упрощает управление для команд. Папка имеет собственный `uid`, используемый в API (`/api/folders/<uid>`) и provisioning (`folderUid`). Рекомендация: одна папка на команду/домен, права — через группы (Team sync с IdP) или сервисные аккаунты, а не индивидуально.

### Предварительные требования

- Работающий инстанс Grafana (рекомендуется версия **13.2.x**, LTS — **12.x**; большинство сценариев применимы с 10.x, помеченные отличия — для 11/12/13).
- Настроенный и доступный источник данных (Prometheus, Loki, Tempo, PostgreSQL и др.) с наличием метрик/логов. Проверка: **Connections → Data sources → `<name>` → Save & test** должен вернуть «Data source is working».
- Права `Editor` (создание/правка через UI) либо токен сервисного аккаунта с ролью `Admin`/`Editor` для операций через API.
- Для CLI-сценариев: установленные `curl`, `jq`, и переменные окружения:

  ```bash
  export GRAFANA_URL="http://localhost:3000"
  export GRAFANA_TOKEN="<SERVICE_ACCOUNT_TOKEN>"   # токен SA с правами Editor/Admin
  # → переменные готовы к использованию в последующих командах
  ```

### Сценарий 1: Создание дашборда с нуля

1. **Создайте дашборд**: Перейдите в **Dashboards -> New Dashboard**. В настройках (`Dashboard settings`) задайте имя и выберите папку для хранения.

2. **Добавьте панель (Graph)**: Нажмите **Add panel -> Add new panel**.
    - **Источник данных**: Выберите ваш источник (например, Prometheus).
    - **Запрос**: Напишите PromQL-запрос. Для отображения скорости роста счетчика используйте функцию `rate()`:

      ```promql
      # Потребление CPU в пользовательском режиме за последнюю минуту
      rate(node_cpu_seconds_total{mode="user"}[1m])
      ```

    - **Легенда**: Для читаемости настройте легенду, используя краткие, стабильные шаблоны. Например, `{{deployment}}` или `{{job}}/{{instance}}`.

3. **Добавьте вторую панель (Gauge)**: Нажмите **Add panel**.
    - **Визуализация**: Справа выберите тип **Gauge**.
    - **Запрос**: Добавьте запрос, возвращающий одно числовое значение:

      ```promql
      # Количество активных горутин
      go_goroutines{job="prometheus"}
      ```

4. **Сохраните дашборд**: Нажмите **Save** в правом верхнем углу.

   **Ожидаемый результат:** всплывающее уведомление «Dashboard saved», дашборд появляется в списке **Dashboards → Browse** и в поиске (Ctrl/Cmd+K) по имени. Версия (`version`) становится `1`.

   **Проверка (валидация):**
   - Откройте дашборд и убедитесь, что обе панели отрисовываются и содержат данные за выбранный диапазон.
   - Наведите курсор на график — появляется `tooltip` со значениями по временной шкале.
   - Для автоматизации проверьте наличие через API:

     ```bash
     curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
       "$GRAFANA_URL/api/search?query=<имя дашборда>&type=dash-db"
     # → [{"id":42,"uid":"<uid>","title":"<имя дашборда>","type":"dash-db","uri":"db/<uid>"}]
     ```

   **Типичные проблемы:**
   - Панель пустая («No data») → проверьте выбранный источник данных, диапазон времени (данные могут быть старше `from`) и наличие лейблов в запросе (`rate()` требует range-вектор `[1m]` и накопленный counter).
   - Ошибка «Data source not found» → источник переименован/удалён; выберите корректный в настройках панели.
   - Легенда дублируется → уточните шаблон `Legend` (например, `{{instance}}` вместо пустого).

### Сценарий 2: Использование переменных для динамических дашбордов

Использование переменных позволяет создавать масштабируемые дашборды и избегать дублирования панелей для каждого узла или кластера. Полное описание механизмов и примеры настройки зависимых переменных, подстановки в запросы и повторения панелей (repeating) представлены в разделе **[Шаблонизация (Templating)](./grafana_templating.md)**.

**Практический пример: зависимые переменные `cluster` → `node`.**

1. Откройте **Dashboard settings → Variables → New variable**.
2. Создайте переменную `cluster` (тип `Query`, источник Prometheus):
   - **Query:** `label_values(kube_node_info, cluster)` — возвращает список кластеров.
   - **Selection options:** включите `Multi-value` (опционально).
3. Создайте переменную `node`, зависящую от `cluster`:
   - **Query:** `label_values(kube_node_info{cluster="$cluster"}, node)`
   - Так как в запросе фигурирует `$cluster`, Grafana автоматически пересчитывает список `node` при смене `cluster` (механизм зависимостей работает по тексту запроса/значению `dependsOn`).
4. Используйте в панели:
   ```promql
   # Нагрузка CPU по выбранному узлу
   sum(rate(node_cpu_seconds_total{node=~"$node", mode="idle"}[5m])) by (node)
   ```
5. **Валидация:** при смене `cluster` в выпадающем списке сверху дашборда список `node` обновляется, а панели перестраиваются под выбранный узел (без ручного редактирования запросов).

**Важно:** порядок переменных в списке имеет значение — зависимая переменная должна стоять ниже той, от которой зависит. Для принудительного обновления при смене временного диапазона включите опцию **Refresh** = `On time range change`.

### Сценарий 3: Импорт готовых дашбордов

У Grafana есть огромная [библиотека готовых дашбордов](https://grafana.com/grafana/dashboards/).

1. **Найдите дашборд**: Например, **Node Exporter Full** (ID `1860`) для мониторинга хоста или **cAdvisor Exporter** (ID `14282`) для Docker-контейнеров.

2. **Импортируйте**:
    - Перейдите в **Dashboards -> New -> Import**.
    - Вставьте ID дашборда в поле "Import via grafana.com".
    - Нажмите **Load**.
    - В настройках выберите правильный источник данных (Prometheus) и нажмите **Import**.

   **Ожидаемый результат:** дашборд открывается, панели заполняются данными из выбранного источника. Имя дашборда появляется в поиске.

   **Валидация:** убедитесь, что на панелях нет значков предупреждения; откройте **Dashboard settings → Variables** — переменные импортированного дашборда должны ссылаться на ваш источник.

   **Типичные проблемы:**
   - «Data source `<name>` not found» → при импорте не был сопоставлен источник; повторите импорт и выберите свой Prometheus/Loki в выпадающих списках (или используйте templated datasource `${datasource}` в экспортированном JSON).
   - Пустые панели → в импортируемом дашборде могут использоваться лейблы/метрики, отсутствующие в вашей среде (например, `job="node"` против вашего `job="node-exporter"`). Адаптируйте запросы или переименуйте лейблы через `label_replace`.
   - Конфликт `uid` → если дашборд с таким `uid` уже есть, Grafana предложит перегенерировать uid; согласитесь, либо укажите свой `uid` в JSON перед импортом.

### Сценарий 4: Клонирование и модификация дашборда

Для безопасного создания копии дашборда (например, для переноса между средами или создания вариации):

1. Откройте дашборд, который хотите скопировать.
2. Нажмите **Share -> Export**.
3. Активируйте переключатель **"Export for sharing externally"**. Это очистит из JSON все уникальные ID, которые могут вызвать конфликт.
4. Скопируйте JSON.
5. Перейдите в **Dashboards -> New -> Import** и вставьте скопированный JSON. Grafana создаст новую, независимую копию.

   **Альтернатива через API (для автоматизации и переноса между инстансами):**

   ```bash
   # 1. Экспортируем исходный дашборд
   curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
     "$GRAFANA_URL/api/dashboards/uid/<source_uid>" > dash.json
   # → файл dash.json с полями dashboard{} и meta{}

   # 2. Очищаем служебные поля и задаём новый uid/папку, затем импортируем
   jq '{dashboard: (.dashboard | del(.id,.uid,.version) | .title="Копия — SVC Checkout"),
        folderUid: "staging", overwrite: true}' dash.json \
     | curl -s -X POST -H "Authorization: Bearer $GRAFANA_TOKEN" \
         -H "Content-Type: application/json" -d @- "$GRAFANA_URL/api/dashboards/db"
   # → {"status":"success","uid":"<новый_uid>","version":1,"slug":"kopiya-svc-checkout"}
   ```

   **Типичные проблемы:**
   - Сохранились старые ссылки/переменные → при ручном копировании через UI JSON может содержать `uid` исходника; используйте переключатель «Export for sharing externally» или удаляйте `uid` перед импортом, иначе Grafana обновит оригинал вместо создания копии.
   - Ошибка `412 Precondition failed` при API-импорте → конфликт версий (`version` устарела); установите `overwrite: true` или актуальную `version`.

### Сценарий 5: Создание плейлистов для NOC

1. Перейдите в **Dashboards -> Playlists** и нажмите **New playlist**.
2. Задайте имя и интервал переключения (например, `1m`).
3. Добавьте в плейлист существующие дашборды.
4. Сохраните и запустите плейлист в режиме **TV** или **Kiosk** для полноэкранного отображения без лишних элементов интерфейса.

   **Kiosk-ссылка для NOC-экрана** (открывается сразу в полноэкранном режиме, без сайдбара/топбара):

   ```bash
   # Получаем slug/id плейлиста
   curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" "$GRAFANA_URL/api/playlists"
   # → [{"id":3,"name":"NOC — Platform","interval":"1m","uid":"<playlist_uid>"}]

   # Открыть плейлист в kiosk-режиме (в браузере/киоске)
   echo "$GRAFANA_URL/playlists/<playlist_uid>?kiosk"
   ```

   **Типичные проблемы:**
   - Плейлист пустой → в него не добавлены дашборды (шаг 3) или у пользователя/токена нет прав `dashboards:read` на соответствующие папки.
   - Дашборд «прыгает»/не переключается → проверьте интервал (он задаётся на уровне плейлиста, а не дашборда) и что дашборд доступен в текущей организации.
   - Для автозапуска на TV используйте флаг браузера `--kiosk`/`--app` и URL с `?kiosk`, либо Grafana Kiosk-утилиту.

### Сценарий 6: Дашборд здоровья приложения в Kubernetes

Этот сценарий описывает создание дашборда для оценки здоровья приложения, запущенного в Kubernetes. Дашборд предназначен для дежурного инженера и должен позволять быстро оценить состояние сервиса.

**Предварительные требования:** в кластере развёрнуты `kube-state-metrics` (метрики объектов K8s: deployments, pods, containers) и `cAdvisor`/`kubelet` (метрики контейнеров `container_*`). Без них запросы вернут пустоту. Проверка наличия метрик:

```bash
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/datasources/proxy/uid/<prom_uid>/api/v1/query?query=kube_deployment_status_replicas_available" \
  | jq '.data.result | length'
# → число > 0 означает, что метрика доступна
```

**Валидация дашборда:** после сборки переключитесь по переменным `namespace` → `deployment` → `pod` → `container` и убедитесь, что каждая панель заполняется; статус-таймлайн подов показывает цветовые состояния; Stat-панель реплик отображает «5/5 available» без красных порогов при здоровом состоянии.

**Типичные проблемы:**
- Панели пусты → экспортеры не в том `namespace`, либо метрики собираются в другом источнике (проверьте селектор `namespace="$namespace"` и сам источник данных).
- «OOMKilled» не считается → метрика `kube_pod_container_status_last_terminated_reason` появляется только в момент завершения; для истории используйте логи/`kube_pod_container_status_restarts_total`.
- Ошибки в LogQL панели → убедитесь, что Loki собирает логи подов (Promtail/Alloy), иначе панель покажет «No labels»; замените на панель `Logs` с источником Loki.

#### Базовые метрики состояния

**Количество контейнеров в поде:**
Панель показывает соотношение работающих контейнеров к общему количеству:

```promql
# Доступные реплики / Желаемые реплики
kube_deployment_status_replicas_available{deployment="<deployment_name>", namespace="<namespace>"}
/
kube_deployment_status_replicas{deployment="<deployment_name>", namespace="<namespace>"}
```

**Визуализация:** Stat или Gauge с пороговыми значениями (Зеленый: 100%, Желтый: 50-99%, Красный: <50%).

**Статусы подов и контейнеров:**
Панель для отслеживания состояний подов:

```promql
# Поды по статусам
count by (phase) (kube_pod_status_phase{namespace="<namespace>", phase=~"Running|Pending|Failed|Unknown|Succeeded"})
```

**Детализация по причинам завершения контейнеров:**

```promql
# OOM Killed контейнеры
count(kube_pod_container_status_last_terminated_reason{reason="OOMKilled", namespace="<namespace>"})

# Error статусы
count(kube_pod_container_status_last_terminated_reason{reason="Error", namespace="<namespace>"})

# Completed статусы (штатно завершённые)
count(kube_pod_container_status_terminated_reason{reason="Completed", namespace="<namespace>"})
```

**Визуализация:** Table или State Timeline с группировкой по причинам (`reason`).

#### Инфраструктурные метрики

**CPU (Total Seconds):**

```promql
# Потребление CPU контейнером
rate(container_cpu_usage_seconds_total{namespace="<namespace>", container="<container_name>"}[5m])
```

**Визуализация:** Time series с пороговыми значениями на основе `limits`.

**Память:**

```promql
# Использование памяти контейнером
container_memory_usage_bytes{namespace="<namespace>", container="<container_name>"}

# Процент использования от limits
container_memory_usage_bytes{namespace="<namespace>", container="<container_name>"}
/
kube_pod_container_resource_limits{resource="memory", namespace="<namespace>", container="<container_name>"}
* 100
```

**Визуализация:** Time series + Gauge с порогом 80-90%.

#### Метрики деплойментов

**Реплики и доступность:**

```promql
# Желаемые vs Доступные реплики
kube_deployment_status_replicas{deployment="<deployment_name>"}
kube_deployment_status_replicas_available{deployment="<deployment_name>"}
kube_deployment_status_replicas_unavailable{deployment="<deployment_name>"}
```

**Визуализация:** Stat с сравнением (например, `5/5 available`).

**Ошибки конфигурации (ConfigMap/Secret не найдены или не смонтированы):**

```promql
# Контейнер в состоянии Waiting с причиной CreateContainerConfigError
# — прямой признак проблем с монтированием ConfigMap/Secret или образом
count(kube_pod_container_status_waiting_reason{reason="CreateContainerConfigError", namespace="<namespace>"})
```

> Метрики `kube_configmap_info` и `kube_secret_info` всегда имеют значение `1` (наличие ресурса),
> поэтому `== 0` на них ничего не вернёт — для детекции проблем монтирования используйте запрос выше
> или панель по причинам `kube_pod_container_status_waiting_reason` целиком (`CreateContainerConfigError`,
> `ImagePullBackOff`, `CrashLoopBackOff`).

#### Логи (опционально)

При наличии Loki можно добавить панель с последними логами:

```logql
{namespace="<namespace>", pod=~"<pod_name>.*"} |~ "ERROR|Exception|Fatal" | line_format "{{.pod}}: {{.line}}"
```

**Визуализация:** Logs panel с фильтром по уровню ошибок.

#### Рекомендуемая структура дашборда

| Row | Панели | Тип визуализации |
| :--- | :--- | :--- |
| **Status Overview** | Доступность реплик, Статусы подов | Stat, State Timeline |
| **Container Health** | OOM Killed, Error, Completed | Table, Bar chart |
| **Resources** | CPU, Memory usage | Time series, Gauge |
| **Deployment Metrics** | Реплики, ошибки монтирования ConfigMap/Secret | Stat, Table |
| **Logs** | Последние ошибки | Logs panel |

#### Переменные для динамической фильтрации

Создайте переменные для удобной навигации:

| Имя | Query | Описание |
| :--- | :--- | :--- |
| `namespace` | `label_values(kube_namespace_labels, namespace)` | Выбор namespace |
| `deployment` | `label_values(kube_deployment_labels{namespace="$namespace"}, deployment)` | Выбор деплоймента |
| `pod` | `label_values(kube_pod_labels{namespace="$namespace"}, pod)` | Выбор пода |
| `container` | `label_values(kube_pod_container_info{namespace="$namespace", pod="$pod"}, container)` | Выбор контейнера |

### Сценарий 7: Управление дашбордами через HTTP API

HTTP API Grafana позволяет полностью автоматизировать жизненный цикл дашбордов (поиск, экспорт, импорт, обновление, удаление) в CI/CD и скриптах миграции. Все вызовы требуют заголовок `Authorization: Bearer <GRAFANA_TOKEN>`, где токен — от сервисного аккаунта с ролью `Editor`/`Admin`.

**Поиск дашбордов:**

```bash
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/search?query=health&type=dash-db"
# → [{"id":42,"uid":"k8s-health","title":"Kubernetes — Здоровье","type":"dash-db","uri":"db/k8s-health", ...}]
```

**Экспорт дашборда в JSON:**

```bash
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/dashboards/uid/k8s-health" > k8s-health.json
# → файл k8s-health.json: {"dashboard":{...},"meta":{...}}
```

**Импорт/обновление дашборда.** Тело запроса — обёртка с обязательным полем `dashboard` и опциональными `folderUid`/`folderId` и `overwrite`:

```bash
jq '{dashboard: (.dashboard | del(.id,.version)),
      folderUid: "infra", overwrite: true}' k8s-health.json \
  | curl -s -X POST \
      -H "Authorization: Bearer $GRAFANA_TOKEN" \
      -H "Content-Type: application/json" -d @- \
      "$GRAFANA_URL/api/dashboards/db"
# → {"status":"success","uid":"k8s-health","version":13,"slug":"kubernetes-zdorovie"}
```

**Удаление дашборда:**

```bash
curl -s -X DELETE -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/dashboards/uid/k8s-health"
# → {"message":"Dashboard deleted"}
```

**Новое поколение API (`/apis/`, Grafana 12+).** С версии 12 появился Kubernetes-подобный слой `/apis/`, а с Grafana 13 legacy-путь `/api/` официально объявлен устаревшим (но остаётся полностью рабочим и не отключается). Для дашбордов используется группа `dashboard.grafana.app`, версия `v1` (для схемы v2 — `apiVersion: dashboard.grafana.app/v2`). Тело запроса — Kubernetes-style ресурс `kind: Dashboard`; `metadata.name` используется в URL, `uid` для этого не нужен.

```bash
# Список дашбордов в namespace
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/apis/dashboard.grafana.app/v1/namespaces/default/dashboards"
# → {"kind":"DashboardList","items":[{...}]}

# Получение дашборда по metadata.name
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/apis/dashboard.grafana.app/v1/namespaces/default/dashboards/k8s-health"
# → {"kind":"Dashboard","apiVersion":"dashboard.grafana.app/v1","metadata":{"name":"k8s-health",...}}

# Создание: POST   .../namespaces/<ns>/dashboards
# Обновление: PUT  .../namespaces/<ns>/dashboards/<name>
# Удаление:  DELETE .../namespaces/<ns>/dashboards/<name>
# Папка задаётся аннотацией metadata.annotations["grafana.app/folder"] = "<folderUid>"
```

При миграции скриптов учитывайте: legacy-endpoint `POST /api/dashboards/db` и новый `POST /apis/.../dashboards` имеют разный формат тела (`dashboard`-обёртка против `kind: Dashboard`).

**Типичные проблемы:**
- `401 Unauthorized` → токен неверен, истёк или у SA нет нужной роли; проверьте `curl .../api/user` для валидации токена.
- `412 Precondition failed` → `version` в JSON ниже текущей; поставьте `overwrite: true` (осторожно: перезапишет чужие правки) или обновите `version` из экспорта.
- Dashboard не появляется в нужной папке → не указан `folderUid`/`folderId`; без него дашборд попадает в General.

### Сценарий 8: Резервное копирование и восстановление всех дашбордов

Регулярный бэкап всех дашбордов организации в Git защищает от случайных удалений и упрощает миграцию между инстансами.

```bash
#!/usr/bin/env bash
# backup-dashboards.sh — выгрузка всех дашбордов в ./backups/<uid>.json
set -euo pipefail
export GRAFANA_URL="${GRAFANA_URL:-http://localhost:3000}"
export GRAFANA_TOKEN="${GRAFANA_TOKEN:?установите GRAFANA_TOKEN}"
mkdir -p backups

curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/search?type=dash-db" \
  | jq -r '.[].uid' \
  | while read -r uid; do
      curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
        "$GRAFANA_URL/api/dashboards/uid/$uid" > "backups/$uid.json"
      echo "saved backups/$uid.json"
    done
# → saved backups/k8s-health.json
# → saved backups/node-exporter.json
```

**Восстановление** — обратный проход по `backups/*.json` с импортом (см. Сценарий 7). Храните папку `backups/` в Git; при провиженинге из Git конфликтов не будет, если `editable: false` на стороне Grafana.

### Сценарий 9: Версионирование и откат изменений дашборда

Grafana хранит историю версий каждого дашборда (по умолчанию до 20 версий в OSS). Это позволяет откатиться после неудачной правки без внешнего Git.

**Просмотр истории версий (UI):** **Dashboard settings → Versions** — список с автором, временем и diff.

**Через API:**

```bash
# Список версий
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/dashboards/uid/k8s-health/versions"
# → [{"id":11,"version":11,"createdBy":"admin","createdAt":"2026-01-10T..."}, ...]

# Откат к версии 11 (создаёт новую версию поверх)
curl -s -X POST -H "Authorization: Bearer $GRAFANA_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"version": 11}' \
  "$GRAFANA_URL/api/dashboards/uid/k8s-health/restore"
# → {"status":"success","uid":"k8s-health","version":13}
```

**Валидация отката:** откройте дашборд и сравните ключевые панели/запросы с ожидаемым состоянием; версия в настройках увеличится, но содержимое совпадёт с выбранной.

### Устранение неполадок (Troubleshooting)

| Симптом | Вероятная причина | Диагностика и решение |
| :--- | :--- | :--- |
| Панель показывает «No data» | Нет данных в диапазоне, неверный источник или лейблы не совпадают | Проверьте `data source`, расширьте диапазон (`now-90d`), выполните запрос напрямую в источнике. Для PromQL убедитесь, что `rate()` применяется к counter с range-вектором `[5m]`. |
| «Data source not found» в панели | Источник удалён/переименован или uid изменился | Выберите корректный источник в настройках панели; при IaC используйте templated datasource `${datasource}`. |
| Дашборд не открывается по ссылке («Dashboard not found») | `uid` изменился или открыт в неверной организации | Используйте стабильный `uid`; добавьте `?orgId=<id>` если в инстансе несколько организаций. |
| Дашборд не загружается (ошибка парсинга) | Повреждён JSON (ручное редактирование) | Получите сырой JSON через `GET /api/dashboards/uid/<uid>` и проверьте синтаксис (`jq . dashboard.json`); при необходимости восстановите версию (см. Сценарий 9). |
| Зависимые переменные не обновляются | Неверный порядок переменных или нет зависимости в запросе | Убедитесь, что зависимая переменная стоит ниже родительской и ссылается на неё в `Query`; проверьте `Refresh`. |
| Очень медленная отрисовка | Слишком много панелей / точек / тяжёлые трансформации | Ограничьте `maxDataPoints` и `min interval`, сверните ряды, вынесите агрегации в Recording Rules, включите Query Caching. |
| «Panel plugin not found» | Плагин панели не установлен/отключен | Установите плагин (`grafana cli plugins install <plugin>`) или замените тип панели на встроенный. |
| «Template variables are not supported in alerts» | Попытка использовать `$var` в server-side alerting | Замените переменную на фиксированный селектор или Recording Rule; для dashboard-алертов (legacy) переменные допустимы, но не рекомендуются. |
| ConfigMap дашборда не применяется / > 1 МБ | Sidecar не видит метку или превышен лимит | Проверьте метку `grafana_dashboard: "1"` и `folder`/`provider` в sidecar; для больших дашбордов включите `sidecar.dashboards.GZIP: true` или храните в S3/Git Sync. |

Для глубокой диагностики используйте **Explore** с тем же запросом и источником — это изолирует проблему панели от проблемы данных. Логи Grafana (`grafana.log`, уровень `debug`) покажут ошибки рендеринга и запросов.

### Ограничения и особые случаи (Edge Cases)

- **Переменные в алертинге:** server-side Alerting (Unified Alerting) не поддерживает шаблонные переменные — контекст должен быть статичным. Используйте Recording Rules или фиксированные селекторы лейблов.
- **Публичные дашборды (Public Dashboards):** доступны только для чтения по ссылке; данные кешируются на стороне Grafana (задержка до минут), нельзя редактировать, ограничена работа переменных/аннотаций и повторяющихся панелей, а dashboard-to-dashboard ссылки могут не передавать контекст. Не публикуйте дашборды с чувствительными данными.
- **Снимки (Snapshots):** это статичный «слепок» данных на момент создания; ссылка может быть публичной — остерегайтесь утечки данных через экспорт внешнего снимка (external snapshot отправляет данные на grafana.com).
- **Библиотечные панели (Library Panels):** правка влияет на ВСЕ дашборды, где панель используется (риск массового изменения); повторяющиеся (repeating) панели нельзя превратить в library-панель напрямую.
- **Repeating panels:** не поддерживаются в публичных дашбордах и имеют ограничения в Dynamic Dashboards (схема v2); для масштабирования предпочитайте программную генерацию (Grafonnet/Scenes SDK).
- **Angular-панели (legacy):** поддержка AngularJS отключена по умолчанию в Grafana 11 и **полностью удалена в Grafana 12** (параметр `angular_support_enabled` больше не существует). Панели force-мигрируются на React-аналоги либо показывают ошибку `Panel plugin not found: <plugin>` — мигрируйте на React-плагины.
- **Миграция v1 → v2 (Dynamic Dashboards):** при открытии дашбордов в Grafana 13.x они автоматически конвертируются в схему v2; «откатить» миграцию на лету нельзя. Для возврата к Classic/V1 экспортируйте дашборд в нужной схеме и переимпортируйте. Провижининг-дашборды (file-based, Git Sync, API) продолжают работать в обеих схемах.
- **Размер дашборда:** GUI и ConfigMap ограничены (ConfigMap ≤ 1 МБ в Kubernetes); очень большие дашборды дробите на несколько или используйте GZIP/S3.
- **Версии схемы (schemaVersion):** при импорте в более старую Grafana дашборд, сохранённый в новой версии, может быть несовместим; проверяйте матрицу совместимости версий.

## Дополнительная информация

### Управление доступом и разрешения (RBAC)

Эффективное управление дашбордами в крупных организациях требует разграничения прав:
- **Уровни разрешений**: `Admin` (полный доступ), `Editor` (создание/правка), `Viewer` (только просмотр) — базовые роли Grafana. Кастомные роли с гранулярными экшенами (`dashboards:read`, `dashboards:write`, `folders:create`) доступны только в **Grafana Enterprise/Cloud** (см. [Fine-grained RBAC](grafana_rbac_fine_grained.md)).
- **Область действия (Scope)**: Разрешения можно настраивать на уровне всей организации, конкретной папки или отдельного дашборда. Более узкая область (дашборд) переопределяет более широкую (папку/организацию).
- **Service Accounts**: Используйте сервисные аккаунты для CI/CD и внешних интеграций вместо личных токенов сотрудников. **API-ключи полностью выведены из эксплуатации**: создание новых ключей недоступно с августа 2024, а в начале 2025 года (начиная с Grafana 11.6) оставшиеся ключи автоматически мигрированы в Service Accounts и эндпоинты `/api/auth/keys` удалены — используйте SA-токены.
- **Folder-based RBAC**: Рекомендуется группировать дашборды в папки по командам или проектам и назначать права на папку. Это упрощает наследование доступов.
- **Datasource permissions**: отдельно ограничивайте доступ к источникам данных (например, секретные логи Loki), чтобы Viewer дашборда не мог напрямую запрашивать источник вне дашборда.
- **Пример**: назначить команде `team-payments` роль `Editor` только на папку `20-Services/Payments` через UI (`Folder → Permissions`) или API `POST /api/access-control/folders/<uid>/users` — иначе правки будут возможны во всей организации.

## Проектирование дашбордов (Best Practices)

#### 1. Цель и аудитория

Дашборд бесполезен, если он не отвечает на конкретный вопрос. Определите аудиторию:
- **SRE/Инфраструктура**: Состояние ресурсов, SLO, бюджеты ошибок.
- **Разработчики**: Производительность сервиса (Latency, RPS, ошибки), бизнес-метрики (регистрации, оплаты).
- **Бизнес/Менеджмент**: Высокоуровневые KPI, доступность сервиса для пользователей.

#### 2. Иерархия и навигация

Используйте принцип "от общего к частному":
- **Overview** → **Service** → **Component** → **Detail**.
- **Drilldown**: Настраивайте ссылки (`Dashboard links`) для перехода между уровнями с сохранением временного диапазона и значений переменных.

#### 3. Стандартизация именования

Единая система упрощает поиск и поддержку:
- **Формат**: `[DOMAIN] — [SERVICE] — [METRIC]`, например `INFRA — Kubernetes — Node Resources`.
- **Консистентность**: Используйте одинаковые названия лейблов (`user_id` вместо `customer_id` в разных сервисах) для облегчения корреляции.

#### 4. Компоновка (Layout)

- **Верхняя треть**: Самые важные "светофоры" и SLO. Должны отвечать на вопрос "все ли в порядке?".
- **Связанные метрики**: Располагайте панели, требующие сравнения, рядом или одну под другой.
- **Сворачиваемые ряды (Rows)**: Группируйте второстепенные метрики в ряды, которые по умолчанию свернуты (`collapsed`), для экономии ресурсов браузера.

#### 5. Визуализация и цвет

- **Цветовое кодирование**: Красный — критическая ошибка, желтый — предупреждение, зеленый — норма.
- **Информативность**: Избегайте "новогодних елок". Используйте цвета осознанно, чтобы выделить аномалии, а не просто "раскрасить" дашборд.
- **Шкалы**: Для данных с разбросом в несколько порядков используйте логарифмическую шкалу.

#### 6. Контекст и документация

- **Описание (Text Panel)**: Добавьте Markdown-панель с описанием дашборда, ссылками на дежурный регламент (Runbook) и контактами владельцев.
- **Единицы измерения (Units)**: Всегда задавайте корректные `units` (bytes, ms, req/s). Grafana автоматически масштабирует их (например, превращая 1024 KB в 1 MB).

### Антипаттерны

1. **Перегруженность**: Дашборд с 50+ открытыми панелями. Это замедляет работу и рассеивает внимание.
2. **Отсутствие агрегации**: Отрисовка тысяч линий на одном графике. Используйте `sum()`, `avg()` или `topk()` в запросах.
3. **Игнорирование Latency**: Использование только среднего времени ответа вместо перцентилей (p95, p99). Среднее скрывает проблемы отдельных пользователей.
4. **Статичные пороги**: Использование фиксированных порогов там, где данные имеют сезонность (например, трафик ночью всегда ниже).
5. **Несогласованные интервалы**: Сравнение метрик, собранных с интервалом 15с и 5м, на одной панели без выравнивания.

### Дашборды как код (Dashboard-as-Code)

Для обеспечения надёжности и повторяемости дашборды должны управляться как код:
- **Provisioning**: Декларативное описание в YAML/JSON, загружаемое при старте или через API.
- **Git Sync (GA в Grafana 13.x)**: нативная двусторонняя синхронизация дашбордов и папок с Git-репозиторием (GitHub, GitLab, Bitbucket, Pure Git) без sidecar-контейнеров: правка в UI → коммит → PR, изменения из Git подтягиваются автоматически. Рекомендованный способ провиженинга дашбордов в 13.x (см. [Monitoring as Code](./monitoring_as_code.md)).
- **Шаблонизация**: Использование `Grizzly`, `Grafonnet` (Jsonnet) или `Terraform` для генерации JSON-моделей. Это исключает ручные ошибки при массовом обновлении панелей.
- **Версионирование в Git**: Позволяет проводить Code Review изменений и быстро откатываться при неудачных правках.

#### Подготовка дашборда к коммиту в Git

Перед коммитом JSON-модели дашборда в репозиторий:

1. **Удалите поле `id`** — оно присваивается Grafana при первом импорте и привязано к конкретному инстансу. Оставляя его, вы рискуете перезаписать существующий дашборд вместо создания нового.
2. **Замените жёстко заданные `uid` источников данных на переменную** — иначе дашборд будет работать только с одним источником, привязанным к конкретному `uid`. Добавьте переменную `datasource` типа `datasource`:

```json
{
  "templating": {
    "list": [
      {
        "name": "datasource",
        "type": "datasource",
        "query": "prometheus"
      }
    ]
  },
  "panels": [
    {
      "datasource": {"type": "prometheus", "uid": "${datasource}"}
    }
  ]
}
```

3. **Задайте стабильный `uid`** для самого дашборда — если он не задан, Grafana сгенерирует его случайно при каждом импорте.
4. **Убирайте локальные настройки доступа** (персональные time range, просмотр конкретного пользователя) — они не должны попадать в Git.

> **Структура папок** рекомендуется организовывать по доменам: `infrastructure/`, `application/`, `flux/` — при использовании `foldersFromFilesStructure` (см. [Провиженинг](./grafana_provisioning.md)) папки в Grafana создаются автоматически по структуре каталогов. В контексте kube-prometheus-stack см. также [практические сценарии](../../Prometheus/kubernetes/Kube_Prometheus_Stack_Helm/grafana_config.md).

### Аннотации и события

**Источники событий**:
- **CI/CD**: Отметки о деплоях.
- **Loki**: Ошибки из логов, выведенные как маркеры.
- **Prometheus/Alertmanager**: Состояние алертов на временной шкале.

Это превращает дашборд из простого графика в инструмент расследования (root cause analysis).

### Учёт обратной связи

Дашборд — это живой инструмент. Удаляйте неиспользуемые панели, объединяйте дубликаты и регулярно проверяйте актуальность запросов. Используйте встроенную аналитику (Usage Insights), чтобы понять, какие дашборды востребованы, а какие пора отправить в архив.
