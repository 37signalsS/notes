# Grafana: Дашборды

> **См. также:** [Обзор Grafana](./grafana_overview.md)

## Определения

- **Дашборд (Dashboard)**: Набор из одной или нескольких панелей для визуализации данных. Он является визуальной проекцией модели наблюдаемости системы и должен помогать отвечать на конкретные эксплуатационные вопросы: работает ли система сейчас, где узкое место, как поведение менялось во времени. Каждый дашборд является JSON-объектом, что позволяет его экспортировать, версионировать и развертывать автоматически.
- **Организация метрик**: Продуманные группировки, единообразное оформление панелей, использование переменных для фильтрации и лаконичные визуализации, которые исключают перегрузку деталей.
- **Панель (Panel)**: Базовый элемент дашборда для визуализации данных (например, график, таблица, датчик).
- **Переменная (Variable)**: Интерактивный элемент управления, позволяющий динамически изменять данные, отображаемые на панелях (например, выбирать сервер или `namespace` из списка).
- **Аннотация (Annotation)**: Маркер на графике, отмечающий событие (например, деплой или инцидент) для помощи в корреляции изменений метрик.
- **Плейлист (Playlist)**: Функция, позволяющая автоматически и циклично переключаться между несколькими дашбордами через заданный интервал, что удобно для NOC-экранов.
- **Снимок (Snapshot)**: Интерактивный, но статичный "слепок" дашборда с зафиксированными данными на определенный момент времени.
- **Библиотечная панель (Library Panel)**: Переиспользуемая панель, которую можно добавить на несколько дашбордов. Изменение в библиотечной панели автоматически применяется ко всем дашбордам, где она используется.
- **Публичный дашборд (Public Dashboard)**: Функция, позволяющая делиться дашбордом через публичную ссылку (только чтение) без необходимости создания учетных записей для конечных пользователей. Поддерживает кеширование на стороне Grafana.
- **Сервисный аккаунт (Service Account)**: Основной механизм аутентификации для автоматизации (API, CI/CD), заменивший устаревшие API-ключи. Позволяет гибко настраивать роли и сроки действия токенов.
- **Dashboard Scenes**: Новый движок отрисовки и управления состоянием дашбордов (Grafana 11+), обеспечивающий высокую производительность, стабильность и расширяемость.

## Основные концепции

### JSON-модель как основа

Каждый дашборд в Grafana — это структурированный JSON-документ. Этот принцип обеспечивает:

- **Версионирование**: Автоматическое сохранение истории изменений, сравнение (diff) и откат.
- **Переносимость**: Легкий экспорт/импорт между инстансами.
- **Infrastructure as Code (IaC)**: Управление через Git и автоматический деплой (см. [Provisioning](./grafana_provisioning.md)).
- **Kubernetes Native**: В облачных средах дашборды часто доставляются через `ConfigMap` с использованием `sidecar`-контейнеров (например, в Rancher или Kube-Prometheus-Stack). Это позволяет хранить дашборды рядом с кодом приложения.

### Уровни дашбордов (Onepager & Drill-down)

Для эффективной эксплуатации рекомендуется разделять дашборды по уровням абстракции, создавая иерархию переходов:

- **L1 — Onepager (Обзорный)**: Здоровье всей платформы или кластера на одном экране. Ключевые SLO и цветовые «светофоры» для дежурных. Должен помещаться на один экран без прокрутки.
- **L2 — Drill-down (Продуктовый/Сервисный)**: Полные RED-метрики конкретного микросервиса. Клик на индикатор в Onepager должен вести на этот уровень.
- **L3 — Resource (Диагностический)**: USE-метрики ресурсов, состояние JVM (GC, Hiccups), детализация дискового ввода-вывода и сети. Нужны для поиска первопричины.

### Компоненты дашборда

#### Панели (Panels)

Базовые элементы визуализации. В Grafana 12+ выбор панели диктуется не только эстетикой, но и типом данных.

| Тип панели | Назначение | Особенности |
| :--- | :--- | :--- |
| **Time series** | Временные ряды, тренды | Основная панель для большинства метрик |
| **Stat / Gauge** | Текущие значения, прогресс | Цветовые пороги (thresholds), компактность |
| **Table** | Структурированные списки | Трансформации данных, ссылки на другие дашборды |
| **State timeline** | Состояние статусов во времени | Идеально для аптайма и состояний подов |
| **Heatmap** | Распределение значений | Анализ задержек (latency buckets) |
| **Flame graph** | Профилирование (Phlare/Pyroscope) | Визуализация стеков вызовов CPU/Memory |
| **Canvas** | Интерактивные схемы | Визуализация топологии сети или физических объектов |
| **Datagrid** | Редактируемые данные (v12+) | Просмотр и редактирование данных непосредственно в Grafana |
| **Trends** | Анализ зависимостей | Сравнение данных без временной привязки |

#### Библиотечные панели (Library Panels)

Решают проблему дублирования логики. Стандартные панели для типовых сервисов (например, Nginx или JVM) создаются один раз и подключаются к десяткам дашбордов. При обновлении PromQL-запроса в библиотеке изменения применяются повсеместно.

#### Переменные (Variables)

Обеспечивают динамичность и фильтрацию.
- **Типы**: `Query` (из источника), `Custom` (ручной список), `Datasource`, `Interval`.
- **Повторение (Repeating)**: Позволяют автоматически создавать строки или панели для каждого значения переменной (например, по одной панели на каждый диск сервера).
- **Взаимозависимость**: Изменение одной переменной (Cluster) может обновлять список другой (Node).

**Важно**: Переменные не работают в серверных оповещениях (Alerting), так как алерты должны иметь статичный контекст для вычисления.

#### Аннотации (Annotations)

Визуальные маркеры событий (деплои, перезагрузки, инциденты). Позволяют коррелировать всплески метрик с изменениями в системе. Источником могут быть как ручные отметки, так и автоматические запросы к Prometheus, Loki или API.

### Трансформации и обработка данных

Трансформации (Transformations) позволяют изменять данные на стороне Grafana перед отрисовкой:
- **Join by field**: Объединение данных из разных источников (например, Prometheus и SQL).
- **Config from query results**: Динамическая настройка порогов панели на основе данных из другого запроса.
- **Filter by name/value**: Очистка графиков от ненужных рядов.

### Производительность и масштабируемость

Для дашбордов с сотнями панелей или огромным количеством пользователей:
- **Query Caching**: Снижение нагрузки на БД (Prometheus, VictoriaMetrics) за счет кеширования результатов.
- **Streaming (Live)**: Получение данных в реальном времени через WebSockets для критических метрик.
- **Min Interval**: Предотвращение избыточной детализации (не запрашивать больше точек, чем пикселей).
- **Recording Rules**: Перенос тяжелых вычислений на сторону источника данных.
### Инструменты для анализа

- **Shared Crosshair**: Опция для синхронного отображения перекрестия на всех графиках дашборда, что помогает визуально сопоставлять данные в один момент времени.
- **Time Range Controls**: Мощные элементы управления для быстрого выбора временного диапазона. Фиксированные окна (`5m`, `1h`) нужны для сравнимости; относительные — для оперативного анализа. Используйте `override` для панелей, где требуется иная гранулярность.
- **Drilldown**: Настройка ссылок с передачей переменных (`dashboard links` и `panel links`) для перехода от обзорных к диагностическим дашбордам с сохранением контекста выбора.
- **Связи данных (Data Correlations)**: (Grafana 10+) Функция для автоматического связывания данных между разными источниками (например, переход от графика Prometheus к логам Loki по общему `label`). Позволяет определять правила корреляции на уровне дашборда или организации.

### Организация: папки, теги и доступ

- **Папки**: Структурируйте по доменам и критичности:
  - `00-Overview` — обзорные дашборды
  - `10-Platform` — инфраструктура
  - `20-Services` — сервисы по командам
  - `30-Diagnostics` — диагностические
- **Нейминг дашбордов**: Формат `SVC <Название> — <Метрика>`, например `SVC Checkout — Latency`.
- **Теги**: `env:prod`, `env:staging`, `team:payments`, `team:auth`, `layer:frontend`, `layer:backend`.
- **Доступ**: Ограничивайте редактирование обзорных панелей и фиксируйте их версии. Для массового распространения структуры применяйте [provisioning](./grafana_provisioning.md).
- **Публичные дашборды (Public Dashboards)**: Позволяют делиться данными через публичную ссылку без необходимости логина. Данные кешируются на стороне Grafana для защиты источника от перегрузки. Доступны настройки фильтрации по переменным.
- **Архитектура Dashboard Scenes (Grafana 11+)**: Новая внутренняя архитектура, которая делает дашборды более стабильными, быстрыми и позволяет программно управлять их состоянием. Это закладывает основу для будущих интерактивных возможностей.

## Практические сценарии

### Сценарий 1: Создание дашборда с нуля

1. **Создайте дашборд**: Перейдите в **Dashboards -> New Dashboard**. В настройках (`Dashboard settings`) задайте имя и выберите папку для хранения.

2. **Добавьте панель (Graph)**: Нажмите **Add panel -> Add new panel**.
    - **Источник данных**: Выберите ваш источник (например, Prometheus).
    - **Запрос**: Напишите PromQL-запрос. Для отображения скорости роста счетчика используйте функцию `rate()`:

      ```promql
      # Потребление CPU в пользовательском режиме за последнюю минуту
      rate(node_cpu_seconds_total{mode="user"}[1m])
      ```

    - **Легенда**: Для читаемости настройте легенду, используя краткие, стабильные шаблоны. Например, `{{deployment}}` или `{{job}}/{{instance}}`.

3. **Добавьте вторую панель (Gauge)**: Нажмите **Add panel**.
    - **Визуализация**: Справа выберите тип **Gauge**.
    - **Запрос**: Добавьте запрос, возвращающий одно числовое значение:

      ```promql
      # Количество активных горутин
      go_goroutines{job="prometheus"}
      ```

4. **Сохраните дашборд**: Нажмите **Save** в правом верхнем углу.

### Сценарий 2: Использование переменных для динамических дашбордов

Использование переменных позволяет создавать масштабируемые дашборды и избегать дублирования панелей для каждого узла или кластера.
Полное описание механизмов и примеры настройки зависимых переменных, подстановки в запросы и повторения панелей (repeating) представлены в разделе **[Шаблонизация (Templating)](./grafana_templating.md)**.

### Сценарий 3: Импорт готовых дашбордов

У Grafana есть огромная [библиотека готовых дашбордов](https://grafana.com/grafana/dashboards/).

1. **Найдите дашборд**: Например, **Node Exporter Full** (ID `1860`) для мониторинга хоста или **cAdvisor Exporter** (ID `14282`) для Docker-контейнеров.

2. **Импортируйте**:
    - Перейдите в **Dashboards -> New -> Import**.
    - Вставьте ID дашборда в поле "Import via grafana.com".
    - Нажмите **Load**.
    - В настройках выберите правильный источник данных (Prometheus) и нажмите **Import**.

### Сценарий 4: Клонирование и модификация дашборда

Для безопасного создания копии дашборда (например, для переноса между средами или создания вариации):

1. Откройте дашборд, который хотите скопировать.
2. Нажмите **Share -> Export**.
3. Активируйте переключатель **"Export for sharing externally"**. Это очистит из JSON все уникальные ID, которые могут вызвать конфликт.
4. Скопируйте JSON.
5. Перейдите в **Dashboards -> New -> Import** и вставьте скопированный JSON. Grafana создаст новую, независимую копию.

### Сценарий 5: Создание плейлистов для NOC

1. Перейдите в **Dashboards -> Playlists** и нажмите **New playlist**.
2. Задайте имя и интервал переключения (например, `1m`).
3. Добавьте в плейлист существующие дашборды.
4. Сохраните и запустите плейлист в режиме **TV** или **Kiosk** для полноэкранного отображения без лишних элементов интерфейса.

### Сценарий 6: Дашборд здоровья приложения в Kubernetes

Этот сценарий описывает создание дашборда для оценки здоровья приложения, запущенного в Kubernetes. Дашборд предназначен для дежурного инженера и должен позволять быстро оценить состояние сервиса.

#### Базовые метрики состояния

**Количество контейнеров в поде:**
Панель показывает соотношение работающих контейнеров к общему количеству:

```promql
# Доступные реплики / Желаемые реплики
kube_deployment_status_replicas_available{deployment="<deployment_name>", namespace="<namespace>"}
/
kube_deployment_status_replicas{deployment="<deployment_name>", namespace="<namespace>"}
```

**Визуализация:** Stat или Gauge с пороговыми значениями (Зеленый: 100%, Желтый: 50-99%, Красный: <50%).

**Статусы подов и контейнеров:**
Панель для отслеживания состояний подов:

```promql
# Поды по статусам
count by (phase) (kube_pod_status_phase{namespace="<namespace>", phase=~"Running|Pending|Failed|Unknown|Succeeded"})
```

**Детализация по причинам завершения контейнеров:**

```promql
# OOM Killed контейнеры
count(kube_pod_container_status_last_terminated_reason{reason="OOMKilled", namespace="<namespace>"})

# Error статусы
count(kube_pod_container_status_last_terminated_reason{reason="Error", namespace="<namespace>"})

# Completed статусы
count(kube_pod_container_status_state_completed{namespace="<namespace>"} == 1)
```

**Визуализация:** Table или State Timeline с группировкой по причинам (`reason`).

#### Инфраструктурные метрики

**CPU (Total Seconds):**

```promql
# Потребление CPU контейнером
rate(container_cpu_usage_seconds_total{namespace="<namespace>", container="<container_name>"}[5m])
```

**Визуализация:** Time series с пороговыми значениями на основе `limits`.

**Память:**

```promql
# Использование памяти контейнером
container_memory_usage_bytes{namespace="<namespace>", container="<container_name>"}

# Процент использования от limits
container_memory_usage_bytes{namespace="<namespace>", container="<container_name>"}
/
kube_pod_container_resource_limits{resource="memory", namespace="<namespace>", container="<container_name>"}
* 100
```

**Визуализация:** Time series + Gauge с порогом 80-90%.

#### Метрики деплойментов

**Реплики и доступность:**

```promql
# Желаемые vs Доступные реплики
kube_deployment_status_replicas{deployment="<deployment_name>"}
kube_deployment_status_replicas_available{deployment="<deployment_name>"}
kube_deployment_status_replicas_unavailable{deployment="<deployment_name>"}
```

**Визуализация:** Stat с сравнением (например, `5/5 available`).

**Ошибки конфигурации:**

```promql
# ConfigMap не загружены
count(kube_configmap_info{namespace="<namespace>"} == 0)

# Secret не загружены
count(kube_secret_info{namespace="<namespace>"} == 0)
```

#### Логи (опционально)

При наличии Loki можно добавить панель с последними логами:

```logql
{namespace="<namespace>", pod=~"<pod_name>.*"} |~ "ERROR|Exception|Fatal" | line_format "{{.pod}}: {{.line}}"
```

**Визуализация:** Logs panel с фильтром по уровню ошибок.

#### Рекомендуемая структура дашборда

| Row | Панели | Тип визуализации |
| :--- | :--- | :--- |
| **Status Overview** | Доступность реплик, Статусы подов | Stat, State Timeline |
| **Container Health** | OOM Killed, Error, Completed | Table, Bar chart |
| **Resources** | CPU, Memory usage | Time series, Gauge |
| **Deployment Metrics** | Реплики, ConfigMap/Secret статусы | Stat, Table |
| **Logs** | Последние ошибки | Logs panel |

#### Переменные для динамической фильтрации

Создайте переменные для удобной навигации:

| Имя | Query | Описание |
| :--- | :--- | :--- |
| `namespace` | `label_values(kube_namespace_labels, namespace)` | Выбор namespace |
| `deployment` | `label_values(kube_deployment_labels{namespace="$namespace"}, deployment)` | Выбор деплоймента |
| `pod` | `label_values(kube_pod_labels{namespace="$namespace"}, pod)` | Выбор пода |
| `container` | `label_values(kube_pod_container_info{namespace="$namespace", pod="$pod"}, container)` | Выбор контейнера |

## Дополнительная информация

### Управление доступом и разрешения (RBAC)

Эффективное управление дашбордами в крупных организациях требует разграничения прав:
- **Уровни разрешений**: `Admin` (полный доступ), `Editor` (создание/правка), `Viewer` (только просмотр).
- **Область действия (Scope)**: Разрешения можно настраивать на уровне всей организации, конкретной папки или отдельного дашборда.
- **Service Accounts**: Используйте сервисные аккаунты для CI/CD и внешних интеграций вместо личных токенов сотрудников.
- **Folder-based RBAC**: Рекомендуется группировать дашборды в папки по командам или проектам и назначать права на папку. Это упрощает наследование доступов.

## Проектирование дашбордов (Best Practices)

#### 1. Цель и аудитория

Дашборд бесполезен, если он не отвечает на конкретный вопрос. Определите аудиторию:
- **SRE/Инфраструктура**: Состояние ресурсов, SLO, бюджеты ошибок.
- **Разработчики**: Производительность сервиса (Latency, RPS, ошибки), бизнес-метрики (регистрации, оплаты).
- **Бизнес/Менеджмент**: Высокоуровневые KPI, доступность сервиса для пользователей.

#### 2. Иерархия и навигация

Используйте принцип "от общего к частному":
- **Overview** → **Service** → **Component** → **Detail**.
- **Drilldown**: Настраивайте ссылки (`Dashboard links`) для перехода между уровнями с сохранением временного диапазона и значений переменных.

#### 3. Стандартизация именования

Единая система упрощает поиск и поддержку:
- **Формат**: `[DOMAIN] — [SERVICE] — [METRIC]`, например `INFRA — Kubernetes — Node Resources`.
- **Консистентность**: Используйте одинаковые названия лейблов (`user_id` вместо `customer_id` в разных сервисах) для облегчения корреляции.

#### 4. Компоновка (Layout)

- **Верхняя треть**: Самые важные "светофоры" и SLO. Должны отвечать на вопрос "все ли в порядке?".
- **Связанные метрики**: Располагайте панели, требующие сравнения, рядом или одну под другой.
- **Сворачиваемые ряды (Rows)**: Группируйте второстепенные метрики в ряды, которые по умолчанию свернуты (`collapsed`), для экономии ресурсов браузера.

#### 5. Визуализация и цвет

- **Цветовое кодирование**: Красный — критическая ошибка, желтый — предупреждение, зеленый — норма.
- **Информативность**: Избегайте "новогодних елок". Используйте цвета осознанно, чтобы выделить аномалии, а не просто "раскрасить" дашборд.
- **Шкалы**: Для данных с разбросом в несколько порядков используйте логарифмическую шкалу.

#### 6. Контекст и документация

- **Описание (Text Panel)**: Добавьте Markdown-панель с описанием дашборда, ссылками на дежурный регламент (Runbook) и контактами владельцев.
- **Единицы измерения (Units)**: Всегда задавайте корректные `units` (bytes, ms, req/s). Grafana автоматически масштабирует их (например, превращая 1024 KB в 1 MB).

### Антипаттерны

1. **Перегруженность**: Дашборд с 50+ открытыми панелями. Это замедляет работу и рассеивает внимание.
2. **Отсутствие агрегации**: Отрисовка тысяч линий на одном графике. Используйте `sum()`, `avg()` или `topk()` в запросах.
3. **Игнорирование Latency**: Использование только среднего времени ответа вместо перцентилей (p95, p99). Среднее скрывает проблемы отдельных пользователей.
4. **Статичные пороги**: Использование фиксированных порогов там, где данные имеют сезонность (например, трафик ночью всегда ниже).
5. **Несогласованные интервалы**: Сравнение метрик, собранных с интервалом 15с и 5м, на одной панели без выравнивания.

### Дашборды как код (Dashboard-as-Code)

Для обеспечения надежности и повторяемости дашборды должны управляться как код:
- **Provisioning**: Декларативное описание в YAML/JSON, загружаемое при старте или через API.
- **Шаблонизация**: Использование `Grizzly`, `Grafonnet` (Jsonnet) или `Terraform` для генерации JSON-моделей. Это исключает ручные ошибки при массовом обновлении панелей.
- **Версионирование в Git**: Позволяет проводить Code Review изменений и быстро откатываться при неудачных правках.

### Аннотации и события

**Источники событий**:
- **CI/CD**: Отметки о деплоях.
- **Loki**: Ошибки из логов, выведенные как маркеры.
- **Prometheus/Alertmanager**: Состояние алертов на временной шкале.

Это превращает дашборд из простого графика в инструмент расследования (root cause analysis).

### Учёт обратной связи

Дашборд — это живой инструмент. Удаляйте неиспользуемые панели, объединяйте дубликаты и регулярно проверяйте актуальность запросов. Используйте встроенную аналитику (Usage Insights), чтобы понять, какие дашборды востребованы, а какие пора отправить в архив.
