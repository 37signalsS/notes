# Grafana: Дашборды

> **См. также:** [Обзор Grafana](./grafana_overview.md)

## Определения

- **Дашборд (Dashboard)**: Набор из одной или нескольких панелей для визуализации данных. Он является визуальной проекцией модели наблюдаемости системы и должен помогать отвечать на конкретные эксплуатационные вопросы: работает ли система сейчас, где узкое место, как поведение менялось во времени. Каждый дашборд является JSON-объектом, что позволяет его экспортировать, версионировать и развертывать автоматически.
- **Организация метрик**: Продуманные группировки, единообразное оформление панелей, использование переменных для фильтрации и лаконичные визуализации, которые исключают перегрузку деталей.
- **Панель (Panel)**: Базовый элемент дашборда для визуализации данных (например, график, таблица, датчик).
- **Переменная (Variable)**: Интерактивный элемент управления, позволяющий динамически изменять данные, отображаемые на панелях (например, выбирать сервер или `namespace` из списка).
- **Аннотация (Annotation)**: Маркер на графике, отмечающий событие (например, деплой или инцидент) для помощи в корреляции изменений метрик.
- **Плейлист (Playlist)**: Функция, позволяющая автоматически и циклично переключаться между несколькими дашбордами через заданный интервал, что удобно для NOC-экранов.
- **Снимок (Snapshot)**: Интерактивный, но статичный "слепок" дашборда с зафиксированными данными на определенный момент времени.
- **Библиотечная панель (Library Panel)**: Переиспользуемая панель, которую можно добавить на несколько дашбордов. Изменение в библиотечной панели автоматически применяется ко всем дашбордам, где она используется.
- **Публичный дашборд (Public Dashboard)**: Функция, позволяющая делиться дашбордом с пользователями без учетной записи в Grafana (только чтение).
- **Сервисный аккаунт (Service Account)**: Современный механизм аутентификации для автоматизации работы с дашбордами через API, заменивший устаревшие API-ключи.

## Основные концепции

### JSON-модель как основа

Каждый дашборд в Grafana — это структурированный JSON-документ. Этот принцип лежит в основе всей работы с дашбордами и обеспечивает ключевые возможности:

- **Версионирование**: Grafana автоматически сохраняет историю изменений дашборда, позволяя сравнивать версии и откатываться к предыдущим.
- **Переносимость**: JSON-модель можно легко экспортировать и импортировать между разными экземплярами Grafana.
- **Автоматизация**: Дашбордами можно управлять как кодом, хранить их в Git и автоматически развертывать (см. [Provisioning](./grafana_provisioning.md)).
- **Взаимодействие с `ConfigMap` в Rancher**: В контексте `kube-prometheus-stack`, развернутого через Rancher, дашборды часто поставляются и управляются через Kubernetes `ConfigMap`. Пользователи могут создавать собственные `ConfigMap`, содержащие JSON-определение их дашбордов. Это позволяет декларативно определять дашборды в YAML-файлах и включать их в Git-репозитории. При таком подходе **Persistent Volume для самой Grafana часто не требуется**, поскольку данные о дашбордах "поставляются" из `ConfigMap`, а не хранятся в файловой системе пода Grafana. Это также упрощает масштабирование и восстановление Grafana.

### Уровни дашбордов

Практически полезно разделять дашборды по уровням:

- **Обзорные (Level 1)**: Общее состояние платформы и ключевые показатели (SLO) для дежурной команды (on-call).
- **Продуктовые (Level 2)**: Метрики конкретного сервиса в терминах бизнес- или пользовательских операций (RED-метрики).
- **Диагностические (Level 3)**: Низкоуровневые панели для глубокой отладки ресурсов (USE-метрики: CPU, память, GC, I/O, latency buckets).

### Компоненты дашборда

#### Панели (Panels)

Основной строительный блок, визуализирующий данные из запросов. Выбор типа панели подчинен задаче: тренд — линия, состояние — число или gauge, сравнительный анализ — таблица или столбцы.

| Тип панели | Когда использовать | Особенности |
| :--- | :--- | :--- |
| **Time series** | Тренды, сезонность, корреляции | Легенда, интервалы, downsampling |
| **Stat** | Единичное число, текущий статус | Цветовые пороги, компактизация |
| **Gauge / Bar gauge** | Прогресс к лимиту, насыщение | Верхние/нижние пороги, максимумы |
| **Table** | Срезы по экземплярам/эндпойнтам | Сортировка, цветовая индикация |
| **State timeline** | Состояние (статус) во времени | Дискретные состояния, история изменений |
| **Status history** | История изменения статусов | Компактная визуализация аптайма |
| **Heatmap** | Распределения, latency buckets | Логарифмическая шкала, палитра |
| **Flame graph** | Профилирование ресурсов | Визуализация стека вызовов CPU/Memory |
| **Trace view** | Распределенная трассировка | Анализ пути запроса (Tempo) |
| **Node graph** | Карты зависимостей и сервисов | Визуализация связей между узлами |
| **Canvas** | Визуализация инфраструктуры | Кастомные изображения, связи |
| **Logs** | Соотнесение логов с метриками | Временная синхронизация |
| **Trend** | Анализ тенденций без временной шкалы | Сравнение двух рядов данных |
| **Datagrid** | Работа с данными в виде таблиц | Редактирование и просмотр данных (v12+) |

#### Библиотечные панели (Library Panels)

Библиотечные панели решают проблему дублирования усилий. Если у вас есть стандартная панель для мониторинга здоровья микросервиса (RED-метрики), вы можете создать её один раз как библиотечную.
- **Централизованное управление**: Обновление логики запроса или визуализации в библиотеке обновляет её везде.
- **Стандартизация**: Гарантирует, что все команды используют одни и те же определения метрик.
- **Уменьшение ошибок**: Исключает опечатки в сложных PromQL-запросах при копировании панелей.

#### Переменные (Variables)

Обеспечивают интерактивность. Пользователь может выбирать значения из выпадающего списка, а панели, использующие эти переменные в запросах, мгновенно обновляются.

Распространенная схема использования:

- `datasource`-переменная для выбора источника.
- Списки значений из меток: приложения, окружения, кластера.
- Повторяющиеся ряды/панели по переменной `instance` или `pod`.

**Важное ограничение**: переменные не работают с [системой оповещений Grafana](./alerting/concepts.md).
Более подробную информацию и примеры использования переменных смотрите в разделе [Шаблонизация (Templating)](./grafana_templating.md).

#### Аннотации (Annotations)

Добавляют контекст на графики, отмечая важные события, что помогает в анализе инцидентов. События релизов, инцидентов и переключений фич следует включать как аннотации, чтобы соотносить изменения с метриками.

### Трансформации, агрегирование, единицы и пороги

- **Трансформации**: Операции `group by`, `join`, `merge`, `rename` и фильтрация строк помогают приводить разрозненные серии к компактным таблицам. "Шум" убирается преобразованием `Null value` и фильтрами по минимумам/максимумам. **Config from query results** позволяет динамически изменять пороги или цвета панели на основе данных из другого запроса.
- **Агрегирование**: Суммирование и перцентильные агрегаты используются там, где важен общий эффект или хвост распределения. Для сравнения экземпляров используется таблица без агрегации с сортировкой.
- **Единицы измерения**: Корректный выбор `units` (CPU cores, bytes, req/s, ms) повышает читаемость и уменьшает ошибки интерпретации.
- **Пороги**: Визуальные пороги в панелях должны соответствовать тем значениям, на которых построены правила оповещений, чтобы исключить расхождения.

### Производительность дашбордов

Высокопроизводительные дашборды критичны для быстрого реагирования.
- **Кеширование запросов (Query Caching)**: Настройка интервала кеширования на стороне источника данных снижает нагрузку на базу (Prometheus/ClickHouse) при одновременном просмотре дашборда многими пользователями.
- **Минимальный интервал (Min Interval)**: Установка `Min interval` в настройках запроса предотвращает избыточную детализацию, когда Grafana пытается отрисовать больше точек, чем пикселей на экране.
- **Количество панелей**: Старайтесь не превышать 20 панелей на одном дашборде. Используйте `Rows` (ряды) с функцией `collapsed` (свернуты по умолчанию), чтобы лениво подгружать данные только при необходимости.
- **Recording Rules (Prometheus)**: Для тяжелых запросов, агрегирующих тысячи рядов, создавайте `recording rules` на стороне Prometheus. Это позволит дашборду запрашивать уже вычисленный результат, сокращая время загрузки с секунд до миллисекунд.
- **Data Source Caching**: Использование плагина "Data Source Proxy Caching" для Grafana Open Source или встроенного кеширования в Enterprise.

### Инструменты для анализа

- **Shared Crosshair**: Опция для синхронного отображения перекрестия на всех графиках дашборда, что помогает визуально сопоставлять данные в один момент времени.
- **Time Range Controls**: Мощные элементы управления для быстрого выбора временного диапазона. Фиксированные окна (`5m`, `1h`) нужны для сравнимости; относительные — для оперативного анализа. Используйте `override` для панелей, где требуется иная гранулярность.
- **Drilldown**: Настройка ссылок с передачей переменных (`dashboard links` и `panel links`) для перехода от обзорных к диагностическим дашбордам с сохранением контекста выбора.
- **Связи данных (Data Correlations)**: (Grafana 10+) Функция для автоматического связывания данных между разными источниками (например, переход от графика Prometheus к логам Loki по общему `label`). Позволяет определять правила корреляции на уровне дашборда или организации.

### Организация: папки, теги и доступ

- **Папки**: Структурируйте по доменам и критичности:
  - `00-Overview` — обзорные дашборды
  - `10-Platform` — инфраструктура
  - `20-Services` — сервисы по командам
  - `30-Diagnostics` — диагностические
- **Нейминг дашбордов**: Формат `SVC <Название> — <Метрика>`, например `SVC Checkout — Latency`.
- **Теги**: `env:prod`, `env:staging`, `team:payments`, `team:auth`, `layer:frontend`, `layer:backend`.
- **Доступ**: Ограничивайте редактирование обзорных панелей и фиксируйте их версии. Для массового распространения структуры применяйте [provisioning](./grafana_provisioning.md).
- **Публичные дашборды (Public Dashboards)**: Позволяют делиться данными через публичную ссылку без необходимости логина. Данные кешируются на стороне Grafana для защиты источника от перегрузки. Доступны настройки фильтрации по переменным.
- **Архитектура Dashboard Scenes (Grafana 11+)**: Новая внутренняя архитектура, которая делает дашборды более стабильными, быстрыми и позволяет программно управлять их состоянием. Это закладывает основу для будущих интерактивных возможностей.

## Практические сценарии

### Сценарий 1: Создание дашборда с нуля

1. **Создайте дашборд**: Перейдите в **Dashboards -> New Dashboard**. В настройках (`Dashboard settings`) задайте имя и выберите папку для хранения.

2. **Добавьте панель (Graph)**: Нажмите **Add panel -> Add new panel**.
    - **Источник данных**: Выберите ваш источник (например, Prometheus).
    - **Запрос**: Напишите PromQL-запрос. Для отображения скорости роста счетчика используйте функцию `rate()`:

      ```promql
      # Потребление CPU в пользовательском режиме за последнюю минуту
      rate(node_cpu_seconds_total{mode="user"}[1m])
      ```

    - **Легенда**: Для читаемости настройте легенду, используя краткие, стабильные шаблоны. Например, `{{deployment}}` или `{{job}}/{{instance}}`.

3. **Добавьте вторую панель (Gauge)**: Нажмите **Add panel**.
    - **Визуализация**: Справа выберите тип **Gauge**.
    - **Запрос**: Добавьте запрос, возвращающий одно числовое значение:

      ```promql
      # Количество активных горутин
      go_goroutines{job="prometheus"}
      ```

4. **Сохраните дашборд**: Нажмите **Save** в правом верхнем углу.

### Сценарий 2: Использование переменных для динамических дашбордов

Использование переменных позволяет создавать масштабируемые дашборды и избегать дублирования панелей для каждого узла или кластера.
Полное описание механизмов и примеры настройки зависимых переменных, подстановки в запросы и повторения панелей (repeating) представлены в разделе **[Шаблонизация (Templating)](./grafana_templating.md)**.

### Сценарий 3: Импорт готовых дашбордов

У Grafana есть огромная [библиотека готовых дашбордов](https://grafana.com/grafana/dashboards/).

1. **Найдите дашборд**: Например, **Node Exporter Full** (ID `1860`) для мониторинга хоста или **cAdvisor Exporter** (ID `14282`) для Docker-контейнеров.

2. **Импортируйте**:
    - Перейдите в **Dashboards -> New -> Import**.
    - Вставьте ID дашборда в поле "Import via grafana.com".
    - Нажмите **Load**.
    - В настройках выберите правильный источник данных (Prometheus) и нажмите **Import**.

### Сценарий 4: Клонирование и модификация дашборда

Для безопасного создания копии дашборда (например, для переноса между средами или создания вариации):

1. Откройте дашборд, который хотите скопировать.
2. Нажмите **Share -> Export**.
3. Активируйте переключатель **"Export for sharing externally"**. Это очистит из JSON все уникальные ID, которые могут вызвать конфликт.
4. Скопируйте JSON.
5. Перейдите в **Dashboards -> New -> Import** и вставьте скопированный JSON. Grafana создаст новую, независимую копию.

### Сценарий 5: Создание плейлистов для NOC

1. Перейдите в **Dashboards -> Playlists** и нажмите **New playlist**.
2. Задайте имя и интервал переключения (например, `1m`).
3. Добавьте в плейлист существующие дашборды.
4. Сохраните и запустите плейлист в режиме **TV** или **Kiosk** для полноэкранного отображения без лишних элементов интерфейса.

### Сценарий 6: Дашборд здоровья приложения в Kubernetes

Этот сценарий описывает создание дашборда для оценки здоровья приложения, запущенного в Kubernetes. Дашборд предназначен для дежурного инженера и должен позволять быстро оценить состояние сервиса.

#### Базовые метрики состояния

**Количество контейнеров в поде:**
Панель показывает соотношение работающих контейнеров к общему количеству:

```promql
# Доступные реплики / Желаемые реплики
kube_deployment_status_replicas_available{deployment="<deployment_name>", namespace="<namespace>"}
/
kube_deployment_status_replicas{deployment="<deployment_name>", namespace="<namespace>"}
```

**Визуализация:** Stat или Gauge с пороговыми значениями (Зеленый: 100%, Желтый: 50-99%, Красный: <50%).

**Статусы подов и контейнеров:**
Панель для отслеживания состояний подов:

```promql
# Поды по статусам
count by (phase) (kube_pod_status_phase{namespace="<namespace>", phase=~"Running|Pending|Failed|Unknown|Succeeded"})
```

**Детализация по причинам завершения контейнеров:**

```promql
# OOM Killed контейнеры
count(kube_pod_container_status_last_terminated_reason{reason="OOMKilled", namespace="<namespace>"})

# Error статусы
count(kube_pod_container_status_last_terminated_reason{reason="Error", namespace="<namespace>"})

# Completed статусы
count(kube_pod_container_status_state_completed{namespace="<namespace>"} == 1)
```

**Визуализация:** Table или State Timeline с группировкой по причинам (`reason`).

#### Инфраструктурные метрики

**CPU (Total Seconds):**

```promql
# Потребление CPU контейнером
rate(container_cpu_usage_seconds_total{namespace="<namespace>", container="<container_name>"}[5m])
```

**Визуализация:** Time series с пороговыми значениями на основе `limits`.

**Память:**

```promql
# Использование памяти контейнером
container_memory_usage_bytes{namespace="<namespace>", container="<container_name>"}

# Процент использования от limits
container_memory_usage_bytes{namespace="<namespace>", container="<container_name>"}
/
kube_pod_container_resource_limits{resource="memory", namespace="<namespace>", container="<container_name>"}
* 100
```

**Визуализация:** Time series + Gauge с порогом 80-90%.

#### Метрики деплойментов

**Реплики и доступность:**

```promql
# Желаемые vs Доступные реплики
kube_deployment_status_replicas{deployment="<deployment_name>"}
kube_deployment_status_replicas_available{deployment="<deployment_name>"}
kube_deployment_status_replicas_unavailable{deployment="<deployment_name>"}
```

**Визуализация:** Stat с сравнением (например, `5/5 available`).

**Ошибки конфигурации:**

```promql
# ConfigMap не загружены
count(kube_configmap_info{namespace="<namespace>"} == 0)

# Secret не загружены
count(kube_secret_info{namespace="<namespace>"} == 0)
```

#### Логи (опционально)

При наличии Loki можно добавить панель с последними логами:

```logql
{namespace="<namespace>", pod=~"<pod_name>.*"} |~ "ERROR|Exception|Fatal" | line_format "{{.pod}}: {{.line}}"
```

**Визуализация:** Logs panel с фильтром по уровню ошибок.

#### Рекомендуемая структура дашборда

| Row | Панели | Тип визуализации |
| :--- | :--- | :--- |
| **Status Overview** | Доступность реплик, Статусы подов | Stat, State Timeline |
| **Container Health** | OOM Killed, Error, Completed | Table, Bar chart |
| **Resources** | CPU, Memory usage | Time series, Gauge |
| **Deployment Metrics** | Реплики, ConfigMap/Secret статусы | Stat, Table |
| **Logs** | Последние ошибки | Logs panel |

#### Переменные для динамической фильтрации

Создайте переменные для удобной навигации:

| Имя | Query | Описание |
| :--- | :--- | :--- |
| `namespace` | `label_values(kube_namespace_labels, namespace)` | Выбор namespace |
| `deployment` | `label_values(kube_deployment_labels{namespace="$namespace"}, deployment)` | Выбор деплоймента |
| `pod` | `label_values(kube_pod_labels{namespace="$namespace"}, pod)` | Выбор пода |
| `container` | `label_values(kube_pod_container_info{namespace="$namespace", pod="$pod"}, container)` | Выбор контейнера |

## Дополнительная информация

### Проектирование дашбордов (Best Practices)

#### 1. Цель и аудитория дашбордов

Дашборды строятся с конкретной целью — если на дашборд никто не заходит, он бесполезен. Целевая аудитория определяет содержание и уровень детализации:

- **SRE / Platform / Infrastructure-инженеры** — техническое состояние инфраструктуры и сервисов: количество запросов, ошибок, логов, потребление ресурсов. Основной фокус: надёжность, SLO, Error Budget.
- **Разработчики** — производительность своего сервиса (latency, RPS, ошибки), а также бизнес-метрики (количество авторизаций, регистраций и т.д.). Связка технических и бизнес-показателей позволяет быстро выявить проблемы после деплоя.
- **Бизнес-пользователи (Product, Marketing, Finance)** — продуктовые и финансовые показатели: количество регистраций, заказов, отправленных посылок, стоимость облачных ресурсов, эффективность рекламных кампаний.
- **Менеджмент** — SLO, Business KPIs, надёжность продукта.

Технические дашборды делятся на два типа:
- **Overview** — общее состояние системы: работает/не работает, есть ли инцидент. Должен сразу отвечать на вопрос «есть ли проблема прямо сейчас».
- **Детализированные** — просматриваются только при инциденте для глубокого анализа.

#### 2. Типология и иерархия дашбордов

Один дашборд — одна тема. Иерархия дашбордов строится по принципу «от общего к частному»:

- **Overview** → **Service Dashboard** → **Component Dashboard** → **Detail Dashboard**
- **Drilldown** — настройка ссылок с передачей переменных (`dashboard links`, `panel links`) для перехода между уровнями иерархии с сохранением контекста (временной интервал, выбранный сервис, статус).

Распределение по командам:
- Команда разработки — дашборд производительности своего сервиса (latency, ошибки).
- Команда DBA — операционные характеристики баз данных (сотни БД в Kubernetes).
- Команда платформы — инфраструктурные дашборды.

#### 3. Навигация и связность дашбордов

- **Ссылки между дашбордами** — drill-down ссылки позволяют кликнуть на точку на графике и перейти к связанному дашборду с сохранением временного интервала и переменных.
- **Теги** — единая система тегов (`env:prod`, `team:payments`, `layer:frontend`) для поиска и построения кросс-ссылок между дашбордами по тегу.
- **Dashboard Links** — добавление ссылок на связанные дашборды через настройки дашборда (по тегу или конкретной ссылке).

#### 4. Стандартизация именования

Единая система наименования критически важна:
- Стандартный формат дашбордов: `SVC <Название> — <Метрика>`.
- Единые названия метрик и лейблов во всех сервисах. Например, `user_id` и `customer_id` — это одно и то же, но разные названия делают невозможной корреляцию.
- Стандартные HTTP-статус-коды — сервис, который всегда отвечает 200, делает observability практически невозможной.
- Формат написания: один сервис использует `request_per_second`, другой `rps` — это сильно усложняет анализ.

#### 5. Компоновка дашборда (Layout)

- **Важные показатели — сверху.** Пользователь смотрит слева направо, сверху вниз. Самые критичные метрики (SLO, Error Budget, текущий статус) — в верхней части.
- **Связанные метрики — рядом.** Две панели, которые нужно коррелировать, должны находиться рядом визуально.
- **Прогрессивное раскрытие** — сначала общие показатели, затем детализация. Чем ниже, тем менее критичные метрики.

#### 6. Цвета и визуальное оформление

- **Цветовой код:** красный — проблема, жёлтый — стоит обратить внимание, зелёный — всё в порядке.
- **Color blindness:** не все различают цвета. Используйте не только цвет, но и форму, текст, символы.
- **Избегайте «новогодней ёлки»:** слишком много цветов на одном дашборде делает его нечитаемым.
- **Согласованность:** одинаковые цвета для одинаковых метрик на всех дашбордах.

#### 7. Шкалы и единицы измерения

- **Логарифмическая шкала** — когда метрики отличаются на порядки (например, 10 RPS и 10000 RPS на одном графике). Линейная шкала «сплющит» меньшие значения.
- **Единые единицы измерения** — наносекунды vs микросекунды vs миллисекунды, мегабайты (Mebibytes vs Megabytes), количество в секунду vs в минуту. Приводите к единой размерности.
- **Консистентная частота сбора** — метрики с разным интервалом сбора (15 секунд vs 5 минут) сложно коррелировать на одном графике.

#### 8. Контекст и документация

Каждый дашборд должен содержать контекстную информацию, особенно если им пользуется не только его создатель:

- Markdown-описание дашборда: что показывает, как использовать.
- Ссылки на команду-владельца, контакты (чат, тикетная система).
- Ссылки на документацию сервиса.
- Комментарии к сложным запросам.
- Отображение алертов и деплоев прямо на графиках.

#### 9. Аннотации и интеграция

- **Аннотации деплоев** — отметки о деплое на временной шкале. Позволяют сразу увидеть, что проблема началась после выката (например, CPU ушёл в потолок через 5 минут после деплоя).
- **Аннотации алертов** — отображение сработавших алертов на графике.
- **Интеграция с алертингом** — при срабатывании алерта ссылка на дашборд с нужным временным интервалом. Один клик — и видна проблема.
- **Grafana v11+:** аннотации через Graphite или Prometheus можно использовать для отображения любых событий (деплои из GitLab CI, переключения фич).
- **Источники аннотаций:** встроенные аннотации Grafana, Prometheus-запросы, Loki-запросы, API-вебхуки.

#### 10. Целевая аудитория и среда отображения

- **Размер экрана:** дашборд для ноутбука разработчика (MacBook Air, 13") отличается от дашборда для большого монитора в офисе или NOC-экрана.
- **NOC-экраны:** используйте плейлисты (Playlists) для автоматической смены дашбордов, полноэкранный режим (TV mode).
- **Dashboard-as-Code:** шаблоны дашбордов, автоматически создаваемые при развёртывании нового сервиса (через Provisioning или Grafanalib). Подход «бородатые дашборды» (fat dashboards) — антипаттерн, дашборды должны описываться кодом, но визуальная составляющая (Grafanalib, Jsonnet) используется ограниченно, в основном для базовых метрик (RED/USE).

#### 11. Методологии RED и USE

- **RED (Rate, Errors, Duration)** — для сервисов/приложений:
  - Rate — количество запросов в секунду.
  - Errors — количество/процент ошибочных запросов.
  - Duration — время ответа (latency, перцентили p50/p95/p99).
- **USE (Utilization, Saturation, Errors)** — для инфраструктурных ресурсов:
  - Utilization — процент использования (CPU, память).
  - Saturation — степень перегрузки (длина очереди, количество горутин).
  - Errors — количество ошибок ресурса.

RED + USE в связке позволяют отличить проблему сервиса от проблемы инфраструктуры: если трафик вырос, utilisation базы данных поднялся — корреляция сразу видна.

#### 12. Дополнительные показатели

- **Error Budget** — сколько ошибок допустимо до нарушения SLO. Визуализация «сжигания» бюджета ошибок.
- **Перцентили latency:** p50, p95, p99. Не забывайте про **максимальное значение (max)** — даже при отличном p99 может быть outlier со временем ответа 3 минуты.
- **Cardinality:** избегайте метрик с высокой кардинальностью (driver_id, user_id в лейблах). Это убивает производительность системы сбора метрик.

### Антипаттерны

1. **Перегрузка дашборда** — слишком много панелей, данных, цветов. Пользователь не понимает, куда смотреть.
2. **Бессистемное добавление метрик** — всё подряд на одном дашборде (geomaP + объём логов + HTTP-статусы + последние запросы). Невозможно коррелировать.
3. **Отсутствие контекста** — нет описания, нет контактов ответственных, нет ссылок на документацию.
4. **Несогласованные цвета** — в одном дашборде зелёный означает «ок», а на соседней панели — что-то другое. Christmas tree — «новогодняя ёлка» из десятков цветов.
5. **Разные временные диапазоны на соседних графиках** — один график показывает 16:00-08:00, другой 11:00-14:00. Невозможно коррелировать.
6. **Разная гранулярность метрик** — одна метрика в req/s, другая в req/min. Или latency в наносекундах на одном графике и в микросекундах на другом.
7. **Некорректный выбор визуализации** — gauge без шкалы и истории (непонятно, горячо сейчас или было горячо всю неделю). Только значение без временного ряда.
8. **Ошибки в запросах** — неправильно построенный PromQL-запрос (например, `rate` вместо `sum` для счётчика горутин) может годами показывать некорректные данные.
9. **Игнорирование детализации по инстансам** — усреднение всех подов может скрыть проблему: один под получает 100 RPS, остальные 10 RPS, но среднее показывает «всё хорошо».
10. **Скрытие ошибок за агрегацией** — если не показывать p99 и max latency, можно не заметить outliers с 3-минутным временем ответа.

### Дашборды как код (Dashboard-as-Code)

- **Provisioning:** управление дашбордами и источниками данных через YAML/JSON.
- **Grafanalib / Jsonnet:** используются для шаблонизации — если у вас есть платформенная команда, создающая boilerplate-сервисы, базовые дашборды (RED, USE, Golden Signals) должны создаваться автоматически при создании сервиса.
- **Ограничения:** визуальную составляющую сложно описывать в коде, поэтому для уникальных дашбордов часто используют ручное редактирование.

### Версионирование

1. **Git-репозиторий:**
   - Хранение JSON дашбордов
   - Code review изменений
   - Откат к предыдущим версиям

2. **CI/CD:**
   - Автоматическое развертывание
   - Валидация JSON
   - Тестирование на staging

3. **Встроенное версионирование Grafana:** автоматическое сохранение истории изменений. Сравнение версий в JSON-формате неудобно для восприятия (diff показывает большое количество строк даже при минимальных изменениях), но позволяет откатиться к предыдущей версии.

### Аннотации

**Источники аннотаций:**

1. **Grafana:** Встроенные аннотации
2. **Prometheus:** Запросы к метрикам
3. **Loki:** Запросы к логам
4. **API:** Вебхуки от внешних систем (например, GitLab CI)
5. **Graphite:** Push-метрики с событиями (деплои, переключения)

**Примеры использования:**

- Деплои: версия, автор, изменения
- Инциденты: начало, окончание, статус
- Переключения фич: включение/выключение

### Учёт обратной связи

Дашборды постоянно улучшаются — точно так же, как код. Не стоит ожидать, что написанный дашборд не нужно будет переписывать через 2 месяца. Собирайте обратную связь от пользователей:
- Если во время инцидента в дашборде было непонятно — нужно добавить комментарии, подписи, размерности.
- Если на дашборд никто не заходит — возможно, он никому не нужен (используйте аналитику использования в Grafana Enterprise).
