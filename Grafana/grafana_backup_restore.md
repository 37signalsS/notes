# Резервное копирование и восстановление Grafana

Практическое руководство по резервному копированию и восстановлению самоуправляемой Grafana. Версии: 13.x актуальная, 12.x LTS, 11.x — EOL (июнь 2026). Облачные функции не рассматриваются.

## Определения

- **База Grafana** — основное хранилище состояния: дашборды, папки, пользователи, организации, источники данных (без секретов в открытом виде), правила алертинга, аннотации, сессии, ключи/токены. Поддерживаются MySQL и PostgreSQL (SQLite — только для тестов, не для продакшена).
- **SQLite** — встроенная БД по умолчанию, один файл `grafana.db`. Допустима только для одиночного инстанса; одновременная запись из нескольких узлов не поддерживается.
- **Провиженинг (provisioning)** — декларативное описание дашбордов/источников/алертов в YAML/JSON, хранящееся вне БД (в репозитории). Это и есть «идеальная резервная копия» конфигурации.
- **Секреты источников данных** — пароли/токены, шифруемые в БД ключом `secret_key` (секция `[security]`); при восстановлении на другой `secret_key` не расшифровываются.
- **mysqldump / pg_dump** — штатные утилиты логического дампа соответствующей БД.
- **RPO (Recovery Point Objective)** — допустимый объём потерянных данных, выраженный во времени; для Grafana определяется частотой дампа БД.
- **RTO (Recovery Time Objective)** — целевое время восстановления сервиса после сбоя.

## Базовые концепции

Состояние Grafana делится на несколько частей, и стратегия резервного копирования для них разная.

### Что входит в состояние Grafana

| Часть | Где лежит | Изменчивость | Как бэкапить |
| :--- | :--- | :--- | :--- |
| Конфигурация `grafana.ini` | `/etc/grafana/grafana.ini` (deb/rpm) | Редко | Копия файла (и переопределения env/Helm values) |
| Провиженинг | `/etc/grafana/provisioning` | По коммитам | Git (основной источник правды) |
| Плагины | `/var/lib/grafana/plugins` | Редко | Архив каталога (если плагины не из каталога/образа) |
| База данных | MySQL / PostgreSQL / SQLite | Постоянно | Регулярный логический дамп |
| Секреты (`secret_key`) | `[security]` / `GF_SECURITY_SECRET_KEY` | Крайне редко | Хранить отдельно от дампа |
| Файловые сессии | `[paths] data` (только SQLite-режим) | Постоянно | Входит в дамп БД |

1. **Конфигурация (идемпотентна, предпочтительна в виде кода):**
   - `grafana.ini` — один файл, копируется «как есть».
   - Провиженинг-файлы (YAML) + JSON дашбордов — хранятся в Git, это основной источник правды для инфраструктуры.
2. **Данные в БД (изменчивы, требуют регулярного дампа):**
   - Пользователи, их пароли (хеши), организации, назначения ролей, runtime-дашборды (созданные вручную через UI без провиженинга), аннотации, история версий дашбордов, Alertmanager-конфигурация, сессии, API-токены.

> **Важно:** значения из `grafana.ini` могут переопределяться переменными окружения (`GF_*`), параметрами Helm chart или аргументами запуска. При таком развёртывании одной копии файла недостаточно — фиксируйте также `environment:` (Compose), `values.yaml` (Helm) или манифест с env (Kubernetes).

### Согласованность и secret_key

При восстановлении важно совпадение `secret_key` (иначе секреты источников данных не расшифруются) и версии Grafana (схема БД мигрирует только вперёд при запуске). Поэтому бэкап БД всегда сопровождается фиксацией версии.

Бэкап БД имеет смысл только вместе с согласованным набором конфигурации. Если БД откатывают на более ранний момент, чем провиженинг, дашборды и источники вернутся к состоянию провиженинг-файлов; если наоборот — runtime-изменения могут конфликтовать с декларативными. Снимайте дамп БД и снимок провиженинга в одном окне.

### Provisioned и runtime-дашборды

- **Provisioned-дашборды** восстанавливаются применением провиженинга и не требуют восстановления из БД.
- **Runtime-дашборды** (созданные в UI, если для них не включён провиженинг) живут только в БД и восстанавливаются исключительно из дампа.

Минимально достаточный бэкап продакшена: (а) дамп БД, (б) `grafana.ini` (с env-переопределениями), (в) каталог провиженинга, (г) `secret_key`. Провиженинг делает восстановление детерминированным и не требует восстановления дашбордов из БД.

### Взаимодействие с Git Sync (Grafana 13)

В Grafana 13.0 функция **Git Sync** (GA) делает Git источником правды для синхронизируемых папок с дашбордами. Для таких папок бэкап БД **не является** полным: незакоммиченные изменения и история версий живут в Git-репозитории. При использовании Git Sync считайте репозиторий первичным хранилищем, а дамп БД — копией остального состояния (пользователи, настройки, alerting). Подробнее — [Monitoring as Code](./monitoring_as_code.md).

## Практические сценарии

### Предварительные требования

- Доступ к серверу Grafana и к СУБД (MySQL/PostgreSQL), в которой лежит БД Grafana.
- Установленные `mysqldump` (для MySQL) или `pg_dump` (для PostgreSQL) той же мажорной версии, что и сервер БД.
- Остановка записи во время дампа не обязательна (используется согласованный снимок), но рекомендуется окно обслуживания для консистентности с провиженингом.
- Известны имя БД Grafana (`grafana`) и `secret_key` (из `grafana.ini` / `GF_SECURITY_SECRET_KEY`).
- Каталог для бэкапов вне узла Grafana и достаточное место под дамп (история версий дашбордов может занимать сотни МБ).
- Версия Grafana зафиксирована (`grafana server -v` или `/api/health`).

### Сценарий 1. Бэкап конфигурации, провиженинга и плагинов

```bash
# Конфиг
cp /etc/grafana/grafana.ini ./grafana.ini.bak

# Провиженинг (YAML + JSON дашбордов)
tar czf grafana-provisioning-$(date +%F).tgz -C /etc/grafana provisioning
# → сохранён декларативный вид дашбордов/источников/алертов

# Плагины (если установлены не из образа)
tar czf grafana-plugins-$(date +%F).tgz -C /var/lib/grafana plugins
# → сохранён каталог установленных плагинов
```

Проверка: `tar tzf grafana-provisioning-2026-08-24.tgz | head` выводит список файлов архива.

### Сценарий 2. Дамп базы MySQL

```bash
# Параметры подключения — из grafana.ini: [database] type/mysql/user/password
export GRAFANA_DB_PASSWORD='...'   # пароль не попадает в history/ps

mysqldump --single-transaction --default-character-set=utf8mb4 \
  -h 127.0.0.1 -u grafana -p"$GRAFANA_DB_PASSWORD" grafana \
  > grafana-db-$(date +%F).sql
# → файл grafana-db-2026-08-24.sql размером в десятки–сотни МБ
```

`--single-transaction` даёт согласованный снимок InnoDB без блокировки таблиц. `--default-character-set=utf8mb4` фиксирует кодировку, чтобы восстановление не исказило UTF-8 символы. Проверка:

```bash
grep -c "CREATE TABLE" grafana-db-2026-08-24.sql
# → число таблиц > 50 (dashboard, dashboard_version, user, data_source, ...) — дамп не пуст
```

> Для MySQL 8 с включённым GTID при импорте в другой инстанс добавьте `--set-gtid-purged=OFF` к `mysqldump`, иначе восстановление может завершиться ошибкой GTID.

### Сценарий 3. Дамп базы PostgreSQL

```bash
pg_dump -h 127.0.0.1 -U grafana -F c -b -v \
  -f grafana-db-$(date +%F).dump grafana
# → обычный формат (-F c), включает large objects (-b)
```

Проверка содержимого без восстановления:

```bash
pg_restore -l grafana-db-2026-08-24.dump | head
# → список объектов (таблицы, индексы) — дамп валиден
```

### Сценарий 4. Бэкап SQLite (одиночный инстанс / тесты)

SQLite хранит всё состояние в одном файле, поэтому его нельзя копировать «на горячую».

```bash
# Файл заблокирован, пока Grafana работает — останавливаем сервис
systemctl stop grafana-server
cp /var/lib/grafana/grafana.db /backup/grafana-$(date +%F).db
systemctl start grafana-server
# → консистентная копия grafana.db
```

Для тестового инстанса без остановки допустим `sqlite3 grafana.db ".backup /backup/grafana.db"` (онлайн-копия через SQLite backup API).

### Сценарий 5. Экспорт runtime-дашбордов через API

Если дашборды создавались вручную в UI, их нет в провиженинге — экспортируйте через API:

```bash
GRAFANA_URL=https://grafana.example.internal
GRAFANA_TOKEN=<service-account-token-with-dashboards:read>

# Получить все папки и дашборды
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/search?type=dash-db&limit=5000" > dashboards-list.json

# Выгрузить каждый дашборд в отдельный файл
for uid in $(jq -r '.[].uid' dashboards-list.json); do
  curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
    "$GRAFANA_URL/api/dashboards/uid/$uid" \
    | jq '.' > "dashboard-$uid.json"
done
# → набор dashboard-<uid>.json, пригодных для импорта обратно или конвертации в провиженинг
```

Проверка: `jq -e '.dashboard.title' dashboard-<uid>.json` возвращает название дашборда.

> В Grafana 13 маршруты `/api` считаются устаревшими в пользу `/apis`, но продолжают работать без изменений; новые `/apis`-эндпоинты могут не иметь полного соответствия. В примерах выше используются стабильные legacy-эндпоинты.

### Сценарий 6. Бэкап и восстановление Docker-тома

В Docker состояние (SQLite-БД, плагины, файловые сессии) лежит в томе `grafana_data`. Плагины в образе и провиженинг, смонтированный как bind-mount, в том не хранятся.

```bash
# 1) Остановить, упаковать том в архив
docker compose stop grafana
docker run --rm \
  -v monitoring-stack_grafana_data:/var/lib/grafana \
  -v /backup:/backup \
  alpine tar czf /backup/grafana-full-$(date +%F).tar.gz -C /var/lib/grafana .
docker compose start grafana

# 2) Восстановление: очистить том и распаковать архив
docker compose stop grafana
docker run --rm \
  -v monitoring-stack_grafana_data:/var/lib/grafana \
  -v /backup:/backup \
  alpine sh -c 'rm -rf /var/lib/grafana/* && tar xzf /backup/grafana-full-2026-08-24.tar.gz -C /var/lib/grafana'
docker compose start grafana
```

> Для внешней БД (MySQL/PostgreSQL в Compose) том Grafana содержит лишь кэш/сессии — основной бэкап делается дампом СУБД (Сценарии 2–3).

### Сценарий 7. Восстановление БД MySQL

```bash
# 1. Остановить Grafana, чтобы не писала в БД
systemctl stop grafana-server

# 2. Пересоздать пустую БД с той же кодировкой и залить дамп
mysql -h 127.0.0.1 -u grafana -p"$GRAFANA_DB_PASSWORD" \
  -e "DROP DATABASE IF EXISTS grafana; CREATE DATABASE grafana CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -h 127.0.0.1 -u grafana -p"$GRAFANA_DB_PASSWORD" grafana < grafana-db-2026-08-24.sql
# → импорт завершён без ошибок

# 3. Восстановить grafana.ini с ТЕМ ЖЕ secret_key
cp ./grafana.ini.bak /etc/grafana/grafana.ini

# 4. Запустить Grafana — она накатит недостающие миграции схемы
systemctl start grafana-server
```

### Сценарий 8. Восстановление БД PostgreSQL

```bash
systemctl stop grafana-server
dropdb   -h 127.0.0.1 -U grafana --if-exists grafana
createdb -h 127.0.0.1 -U grafana -E UTF8 grafana
pg_restore -h 127.0.0.1 -U grafana -d grafana --clean --if-exists -v grafana-db-2026-08-24.dump
systemctl start grafana-server
```

### Сценарий 9. Восстановление SQLite

```bash
systemctl stop grafana-server
cp /var/lib/grafana/grafana.db /var/lib/grafana/grafana.db.broken   # на всякий случай
cp /backup/grafana-2026-08-24.db /var/lib/grafana/grafana.db
chown grafana:grafana /var/lib/grafana/grafana.db
chmod 640 /var/lib/grafana/grafana.db
systemctl start grafana-server
```

### Сценарий 10. Восстановление доступа администратора

Если из дампа не восстановились пользователи или утерян пароль `admin`:

```bash
grafana cli --homepath /usr/share/grafana --config /etc/grafana/grafana.ini \
  admin reset-admin-password '<new-strong-password>'
# → Admin password changed successfully
```

> При внешней БД (MySQL/PostgreSQL) обязательно указывайте `--config` и `--homepath`. Без них `grafana cli` не видит параметры подключения и сбросит пароль в локальной SQLite (`/var/lib/grafana`), а не в рабочей БД.

### Сценарий 11. Проверка восстановления

```bash
curl -s https://grafana.example.internal/api/health
# → {"commit":"...","database":"ok","version":"13.2.x"}

# Проверить, что секреты источников данных расшифровались (совпал secret_key)
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/datasources/uid/<uid>/health" | jq
# → {"status":"OK","message":"..."}

# Убедиться, что дашборды на месте
curl -s -H "Authorization: Bearer $GRAFANA_TOKEN" \
  "$GRAFANA_URL/api/search?type=dash-db" | jq 'length'
# → число дашбордов совпадает с ожидаемым
```

## Дополнительная информация

### Рекомендации по эксплуатации

- Переводите дашборды в провиженинг (Git) — тогда БД хранит только пользователей и runtime-изменения, и восстановление детерминировано.
- Делайте дамп БД по расписанию (cron/systemd timer, nightly) и храните копии вне узла Grafana (удалённый хост). Для офсайт-копий используйте `scp`/`rsync` или шифрование на стороне утилиты.
- Фиксируйте версию Grafana рядом с дампом (`grafana server -v` или `/api/health`).
- Храните `secret_key` отдельно от дампа БД; при восстановлении на новый ключ пересоздайте секреты источников данных.
- Шифруйте дампы перед вывозом за пределы доверенного периметра: `gpg --symmetric --cipher-algo AES256 grafana-db-2026-08-24.sql`.
- Регулярно проводите **тренировочное восстановление** на отдельном стенде — непроверенный бэкап не считается бэкапом.
- Определите и документируйте RPO/RTO; частота дампа должна укладываться в RPO.
- Для SQLite (только тесты) достаточно скопировать файл `grafana.db` при остановленной службе или снять онлайн-копию через `sqlite3 ... ".backup"`.

### Типичные ошибки и их решение

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| После восстановления источники данных недоступны (ошибка auth) | Другой `secret_key` — секреты не расшифровываются | Восстановить прежний `secret_key` или пересохранить секреты источников |
| `database migration failed` при старте | Дамп от более новой версии Grafana (схема не откатывается) | Поднять Grafana той же/новее версии, что при дампе |
| Дамп огромный, долгий импорт | Раздутая история версий дашбордов | Снизить `versions_to_keep` в секции `[dashboards]` и пересоздать БД |
| `Access denied` при mysqldump | Нет прав на чтение всех таблиц | Дать пользователю `SELECT` на БД Grafana |
| Дашборды восстановились, но пользователи — нет | Дамп делали с `--no-data` или не из той БД | Проверить, что дамп включает таблицы `user`, `user_auth` |
| `grafana cli` сбрасывает пароль не в ту БД | Не указаны `--homepath`/`--config`, взята локальная SQLite | Указать `--config /etc/grafana/grafana.ini` (и `--homepath`) |
| Искажённые символы (кракозябры) в названиях после восстановления | Импорт в БД с кодировкой, отличной от дампа | Пересоздать БД с `utf8mb4`/`UTF8` и восстановить дамп с той же кодировкой |
| Восстановление упало с ошибкой GTID (MySQL 8) | Дамп содержит GTID-команды | Снимать дамп с `--set-gtid-purged=OFF` |

### Ограничения и особые случаи

- Миграция схемы БД выполняется Grafana только вперёд при старте; штатный откат версии БД невозможен — только из дампа нужной версии.
- Смена типа СУБД (MySQL ↔ PostgreSQL) не поддерживается «на лету» — нужен экспорт/импорт (дашборды/папки/источники) и пересоздание пользователей.
- Сессии и временные токены в БД теряют смысл после восстановления — пользователям нужно войти заново.
- История версий дашбордов (`dashboard_version`) может занимать большую часть объёма БД.
- При включённом Git Sync дашборды синхронизируемых папок определяются Git-репозиторием, а не БД: бэкап БД их не заменит.
- Секреты, добавленные через переменные окружения (`GF_*`) или внешний vault, не входят в дамп БД — их восстанавливают из системы, где они хранятся.

### Очистка и откат изменений

- Перед восстановлением всегда снимайте свежий дамп текущего (даже «сломанного») состояния — он может пригодиться.
- Откат: остановите Grafana, залейте предыдущий дамп, верните предыдущий `grafana.ini`, запустите.
- Для отката только дашбордов достаточно переприменить провиженинг или импортировать сохранённый `dashboard-<uid>.json` через UI/API.
- Удаляйте временные архивы и дампы с рабочими секретами сразу после вывоза в безопасное хранилище.

### Актуальность и статус

Процедура дампа/восстановления стабильна для MySQL/PostgreSQL на 11.x/12.x/13.x. Рекомендуемый подход — провиженинг как основной вид бэкапа конфигурации, дамп БД — как страховка состояния. В Grafana 13 добавьте к этому учёт Git Sync для синхронизируемых папок.
