# Управление пользователями и аутентификация в Grafana

В Grafana существует гибкая система для управления доступом, которая включает в себя роли пользователей, команды и организации. Также поддерживаются внешние провайдеры аутентификации, такие как GitHub, GitLab или LDAP.

## Иерархия доступа

### 1. Роли пользователей (User Roles)

Базово в Grafana предусмотрено три вида ролей для пользователей:

*   **Viewer**: Может только просматривать дашборды в режиме "read-only".
*   **Editor**: Может создавать и редактировать дашборды и источники данных, но не имеет доступа к административным настройкам.
*   **Admin**: Суперпользователь с полным доступом ко всем настройкам.

### 2. Команды (Teams)

Пользователей можно группировать в команды (`Teams`). Это позволяет выдавать разрешения на уровне команд, например, предоставить доступ к определенной папке с дашбордами или, наоборот, ограничить его.

С концептуальной точки зрения, команды в Grafana являются просто **метками (тегами)** для группировки пользователей. Они не создают физической изоляции данных.

### 3. Организации (Organizations)

Организация — это самая высокоуровневая сущность в иерархии доступа Grafana. Дашборды, папки и источники данных принадлежат конкретной организации. Это обеспечивает **полную физическую изоляцию** ресурсов между разными командами или проектами. Один пользователь может быть членом нескольких организаций и переключаться между ними.

## Практические примеры

### Создание пользователя и настройка прав

В Grafana существует два основных способа создания учетной записи пользователя:

1.  **Создание пользователя вручную (`New user`)**:

    *   Администратор переходит в раздел `Server Admin` -> `Users` и нажимает `New user`.
    *   В этом случае администратор **сам задает логин и пароль** для нового пользователя.
    *   Этот способ не позволяет отправить пользователю приглашение (инвайт).

2.  **Отправка приглашения (`Invite`)**:

    *   Администратор переходит в `Server Admin` -> `Users` и нажимает `Invite`.
    *   Пользователь получает по электронной почте ссылку-приглашение.
    *   При первом входе система попросит его **самостоятельно задать себе пароль**. После этого учетная запись становится активной.
    *   Этот способ является более предпочтительным с точки зрения безопасности.

> **Важно**: При настройке Grafana через Helm, убедитесь, что в `grafana.ini` в секции `[server]` (или в `values.yaml` Helm-чарта) правильно указан параметр `root_url` (например, `server.root_url` или через переменную окружения `GF_SERVER_ROOT_URL`). Если он не задан, ссылки в письмах-приглашениях будут генерироваться некорректно (например, с `localhost:3000`), что является частой ошибкой.

### Ограничение прав

*   Пользователь с ролью `Viewer` не видит кнопок редактирования и не может изменять панели на дашбордах.

### Работа с командами и правами доступа к папкам

1.  **Создание команды**:

    *   Перейдите в раздел `Configuration` -> `Teams`.
    *   Создайте команду (например, `FirstTeam`) и добавьте в нее пользователя.
    > **Примечание**: Добавить пользователя в команду можно только после того, как он примет приглашение.

2.  **Настройка прав для папок (Folders)**:

    *   Перейдите в `Dashboards` -> `Browse`.
    *   В настройках папки (`Permissions`) можно управлять доступом.
    *   Например, можно убрать права для роли `Viewer`, и пользователи с этой ролью не увидят папку.
    *   Можно также предоставить команде (`FirstTeam`) права на редактирование (`Editor`) дашбордов в определенной папке.

    Права доступа наследуются от папки к дашборду, но их можно переопределить на уровне отдельного дашборда.

## Сервисные аккаунты (Service Accounts)

Начиная с Grafana 9, появился новый, предпочтительный способ для автоматизации — **сервисные аккаунты**. Это специальные "пользователи", предназначенные исключительно для программного взаимодействия с Grafana API.

**Ключевые отличия от API-ключей пользователя:**

*   **Изоляция:** Сервисный аккаунт не привязан к реальному пользователю. Если сотрудник увольняется, его API-ключи перестают работать, а сервисный аккаунт — нет.
*   **Принадлежность к организации:** Сервисный аккаунт создается внутри конкретной организации и не может быть "глобальным".
*   **Отсутствие UI-доступа:** У сервисного аккаунта нет пароля, и под ним нельзя войти в веб-интерфейс Grafana.
*   **Токены:** Для сервисного аккаунта можно создать несколько токенов (аналогов API-ключей) с разным сроком действия, и их можно отзывать независимо друг от друга.

Создание сервисного аккаунта и токенов для него производится в разделе **Configuration -> Service Accounts**.

### Создание токена для сервисного аккаунта

1.  Перейдите в раздел **Configuration -> Service Accounts**.
2.  Выберите нужный сервисный аккаунт.
3.  Нажмите **Add new token**.
4.  Задайте имя токена, выберите роль и срок действия (или оставьте бессрочным).
5.  После создания токен будет показан **только один раз**. Его необходимо сразу же скопировать и сохранить в безопасном месте. Если токен был утерян, его нельзя восстановить; потребуется сгенерировать новый.

## API Ключи (API Keys)

> **Примечание:** Этот механизм считается устаревшим в пользу Сервисных аккаунтов, но все еще поддерживается.

API-ключи, привязанные к пользователю, являются традиционным способом для автоматизации взаимодействия с Grafana.

### Создание API-ключа

1.  Перейдите в раздел **Configuration -> API Keys**.
2.  Нажмите **New API key**.
3.  Задайте имя ключа, выберите роль (`Admin`, `Editor` или `Viewer`) и срок действия (`Time to live`).
4.  После создания ключ будет показан **только один раз**. Его необходимо сразу же скопировать и сохранить в безопасном месте (например, в системе управления секретами, как Ansible Vault или HashiCorp Vault).

API-ключ затем используется для аутентификации в Grafana API, обычно путем передачи его в HTTP-заголовке `Authorization: Bearer <key>`.

### Автоматизация через Grafana API

Хотя файловый провиженинг (см. [Провиженинг Grafana](./grafana_provisioning.md)) отлично подходит для дашбордов и источников данных, он не позволяет управлять пользователями, командами или организациями. Эти задачи можно автоматизировать с помощью Grafana API, используя скрипты.

Это позволяет реализовать "Security as Code", храня версионированные скрипты для настройки прав доступа в Git.

**Пример (используя `curl`):**

Следующий подход можно использовать в shell-скрипте для автоматического создания структуры организации:

1.  Создать сервисный аккаунт с правами администратора и сгенерировать для него токен.
2.  Используя этот токен, отправлять `curl`-запросы к эндпоинтам Grafana API для:
    *   Создания организаций (`/api/orgs`).
    *   Создания пользователей (`/api/admin/users`).
    *   Создания команд (`/api/teams`).
    *   Добавления пользователей в команды (`/api/teams/{team_id}/members`).

Такой скрипт можно встроить в CI/CD пайплайн для автоматического развертывания и настройки нового экземпляра Grafana.

## Интеграция с внешними провайдерами аутентификации (OAuth)

Grafana поддерживает интеграцию с OAuth-сервисами (GitHub, GitLab, Google и др.) и LDAP.

### Настройка аутентификации через GitHub

Для включения аутентификации через GitHub необходимо настроить `grafana.ini` (или `values.yaml` для Helm-чарта).

1.  **Создание OAuth App в GitHub**:

    *   Перейдите в `Settings` -> `Developer settings` -> `OAuth Apps` на GitHub.
    *   Создайте новое приложение.
    *   `Authorization callback URL` должен быть `http://<your-grafana-url>/login/github`.
    *   После создания вы получите `Client ID` и `Client Secret`.

2.  **Конфигурация Grafana**:

    В `values.yaml` для Helm-чарта Grafana добавьте или измените следующие секции:

    ```yaml
    grafana.ini:
      auth.github:
        enabled: true
        allow_sign_up: true
        scopes: user:email,read:org
        auth_url: https://github.com/login/oauth/authorize
        token_url: https://github.com/login/oauth/access_token
        api_url: https://api.github.com/user
        client_id: "${VAULT_KEY_CLIENT_ID}" # Замените на ваш Client ID или используйте !vault
        client_secret: "${VAULT_KEY_CLIENT_SECRET}" # Замените на ваш Client Secret или используйте !vault
        allowed_organizations: "your-github-org" # Например, devops.prodigy
        team_ids: "" # ID команды в GitHub, если нужно ограничить доступ
    ```

3.  **Применение конфигурации**:

    Обновите Helm-релиз:
    
    ```bash
    helm upgrade --atomic grafana grafana/grafana \
      -n monitoring \
      -f grafana-values-2.yaml
    ```

После обновления на странице входа в Grafana появится кнопка "Sign in with GitHub". Если в `allowed_organizations` указана организация, в которой пользователь не состоит, он получит ошибку доступа.
