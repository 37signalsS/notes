# Grafana: Управление пользователями и аутентификация

## Определения

**Управление пользователями и аутентификация** в Grafana — комплекс механизмов для идентификации субъектов (пользователей и сервисов) и разграничения их прав доступа к ресурсам платформы (дашбордам, источникам данных, настройкам).

**Текущая версия (март 2026):** Grafana 12.x

**Связанные темы:**

- [Обзор Grafana](./grafana_overview.md) — общая информация о платформе
- [Провиженинг](./grafana_provisioning.md) — автоматизация конфигурации
- [Алертинг](./alerting/concepts.md) — сервисные аккаунты для системы оповещений

## Базовые концепции

### Роли пользователей

Базовые права доступа определяются на уровне Организации:

| Роль | Права |
| :--- | :--- |
| **Viewer** | Просмотр дашбордов и панелей (только чтение) |
| **Editor** | Создание и редактирование дашбордов, папок и источников данных |
| **Admin** | Полный административный доступ к настройкам Организации и пользователям |

### Иерархия доступа и сущности

1. **Организации (Organizations)** — высший уровень изоляции. Дашборды, источники данных и пользователи в одной организации полностью отделены от других.
2. **Команды (Teams)** — логические группы пользователей. Позволяют централизованно управлять правами доступа к папкам и дашбордам для набора участников.
3. **Сервисные аккаунты (Service Accounts)** — учетные записи для программного взаимодействия через API (появились в Grafana 9). Не привязаны к конкретному человеку.
4. **API-ключи (API Keys)** — устаревающий способ аутентификации. Привязаны к пользователю и имеют меньше гибкости в управлении токенами.

### Сравнение: Сервисные аккаунты и API-ключи

| Характеристика | Сервисный аккаунт | API-ключ |
| :--- | :--- | :--- |
| **Владелец** | Организация | Пользователь |
| **Стабильность** | Не зависит от увольнения сотрудника | Перестает работать при удалении пользователя |
| **Токены** | Поддержка нескольких токенов с разным сроком действия | Один ключ на сущность |
| **Рекомендация** | Рекомендуется для всей новой автоматизации | Считается устаревшим (Legacy) |

### Внешняя аутентификация

Grafana поддерживает интеграцию с внешними провайдерами для реализации SSO (Single Sign-On):

| Провайдер | Тип | Назначение |
| :--- | :--- | :--- |
| **GitHub / GitLab** | OAuth | Аутентификация через учетные записи разработчиков |
| **Google** | OAuth | Использование корпоративных аккаунтов Google Workspace |
| **LDAP** | Directory | Интеграция с корпоративными каталогами (Active Directory, OpenLDAP) |
| **SAML / OIDC** | Enterprise | Корпоративные стандарты SSO (доступно в Grafana Enterprise) |

## Практические сценарии

### Сценарий 1: Настройка аутентификации через GitHub

Для включения входа через GitHub необходимо создать OAuth Application в настройках GitHub и обновить конфигурацию Grafana.

**Конфигурация в `grafana.ini` (или через Helm `values.yaml`):**

```ini
[auth.github]
enabled = true
allow_sign_up = true
scopes = user:email,read:org
client_id = ${GITHUB_CLIENT_ID}
client_secret = ${GITHUB_CLIENT_SECRET}
allowed_organizations = my-tech-org
```

> **Важно:** Убедитесь, что параметр `server.root_url` настроен корректно, иначе GitHub не сможет выполнить перенаправление (callback) после успешного входа.

### Сценарий 2: Создание пользователей и управление правами

1. **Ручное создание**: В разделе **Administration → Users** администратор может создать пользователя, задав ему логин и пароль.
2. **Приглашения**: Через кнопку **Invite** можно отправить ссылку на почту. Это безопаснее, так как пользователь сам устанавливает пароль.
3. **Права на папки**: В настройках папки (Permissions) можно добавить команду или роль и назначить уровень доступа (View, Edit, Admin), который будет унаследован всеми дашбордами внутри.

### Сценарий 3: Управление сервисными аккаунтами

1. Перейдите в **Administration → Users and access → Service accounts**.
2. Создайте аккаунт, выбрав нужную роль (например, Editor для CI/CD).
3. Внутри аккаунта нажмите **Add service account token**.
4. Скопируйте токен сразу — он будет показан только один раз.

### Сценарий 4: Автоматизация через Grafana API

Для массового создания команд или организаций используйте HTTP API.

**Пример создания команды через `curl`:**

```bash
curl -X POST -H "Authorization: Bearer <TOKEN>" \
     -H "Content-Type: application/json" \
     -d '{"name":"DevOps-Team", "email":"devops@example.com"}' \
     http://grafana.local/api/teams
```

## Дополнительная информация

### Лучшие практики (Best Practices)

- **Принцип минимальных привилегий**: Назначайте роль Viewer по умолчанию. Роль Admin должна быть только у ответственных за эксплуатацию.
- **Отказ от API-ключей**: Переводите существующую автоматизацию на сервисные аккаунты для повышения надежности.
- **Использование SSO**: Интеграция с внешним провайдером (LDAP или OAuth) избавляет от необходимости управлять паролями внутри Grafana и упрощает отзыв доступа при увольнении.
- **Секретный ключ**: При развертывании в режиме HA обязательно устанавливайте одинаковый `secret_key` в `grafana.ini` для всех экземпляров, чтобы сессии пользователей не сбрасывались при переключении между узлами.
