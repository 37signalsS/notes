# Grafana: Обзор

**Актуально для:** Grafana 13.2.x / 12.x (LTS)

## Определения

**Grafana** — универсальная open-source платформа для аналитики, мониторинга и интерактивной визуализации данных телеметрии (метрик, логов, трассировок, профилей).

**Ключевые характеристики:**
- **Stateless-архитектура:** Grafana не хранит собираемые данные (метрики/логи), а выступает интерфейсом для внешних источников.
- **Сетевое взаимодействие:** По умолчанию работает на порту `3000` (протокол HTTP/HTTPS).
- **Персистентность настроек:** Хранит собственные данные (пользователи, дашборды, сессии) во внутренней базе данных. По умолчанию используется **SQLite**, для высокодоступных (HA) инсталляций рекомендуются **PostgreSQL** или **MySQL**.
- **Управление расширениями:** Утилита `grafana cli` используется для установки плагинов и администрирования из командной строки. В Grafana 13.0 старые обёртки `grafana-cli` и `grafana-server` удалены (используются подкоманды `grafana cli` и `grafana server`).

**Текущий релиз (октябрь 2026):** Grafana 13.2.x.
- **Статус веток:** 13.x — актуальная стабильная ветка (Current), 12.x — поддержка безопасности (LTS), 11.x — EOL (июнь 2026).

### Основные понятия экосистемы

| Понятие | Определение |
| :--- | :--- |
| **Организация (Organization)** | Изолированный «тенант» внутри одного инстанса: свои пользователи, дашборды, источники данных и настройки. Один пользователь может состоять в нескольких организациях с разными ролями. |
| **Дашборд (Dashboard)** | Логический контейнер, объединяющий панели (визуализации), фильтры и аннотации для решения конкретной аналитической задачи. |
| **Панель (Panel)** | Отдельный визуальный блок внутри дашборда (график, таблица, карта, лог-стрим и т.д.), построенный на основе одного или нескольких запросов к источникам данных. |
| **Источник данных (Data Source)** | Подключение к внешней системе хранения телеметрии (Prometheus, Loki, Tempo, PostgreSQL, Elasticsearch и др.), откуда Grafana получает данные для панелей. |
| **Переменная (Variable / Template)** | Параметр, добавляющий интерактивность в дашборд. Позволяет динамически изменять запросы, диапазоны времени или отображаемые данные без редактирования каждой панели отдельно. См. [Шаблонизация](./grafana_templating.md). |
| **Оповещение (Alert)** | Правило, которое периодически оценивает выражение (запрос) и генерирует уведомление при нарушении заданного порогового значения. |
| **Аннотация (Annotation)** | Визуальный маркер на временной шкале дашборда, отмечающий события (деплои, инциденты, релизы) для контекстного анализа. |
| **Провиженинг (Provisioning)** | Подход Infrastructure as Code (IaC) для автоматизированного управления конфигурацией Grafana через YAML/JSON-файлы. См. [Провиженинг Grafana](./grafana_provisioning.md). |

### Grafana Stack (LGTM)

Комплексное решение для реализации [наблюдаемости (observability)](../Concepts/Observability_and_Monitoring/observability_definitions.md). Включает в себя:
- **Grafana** — уровень представления.
- **Mimir/Prometheus** — хранение метрик ([Mimir: Обзор](../Mimir/mimir_overview.md), [Prometheus: Обзор](../Prometheus/overview.md)).
- **Loki** — агрегация логов ([Loki: Обзор](../Loki/loki_overview.md)).
- **Tempo** — распределенные трассировки ([Grafana Tempo](../Tempo/index.md)).
- **Alloy** — унифицированный сборщик телеметрии (заменил Grafana Agent, см. [Grafana Alloy: Обзор](./grafana_alloy_overview.md)).

## Базовые концепции

### Архитектура и лицензирование

- **Технологический стек:** Бэкенд реализован на **Go**, фронтенд — на **TypeScript/React**.
- **Лицензия:** Распространяется под лицензией **AGPLv3** (основные компоненты, редакция OSS). Ряд функций — кэширование запросов, reporting, расширенное управление правами через UI, Usage Insights — доступны только в коммерческой редакции **Enterprise**.
- **Конфигурация:** Управление параметрами сервера осуществляется через файл `grafana.ini` (или `custom.ini`) либо переменные окружения (формат `GF_<SECTION>_<KEY>`).
- **Мультиарендность:** Один инстанс обслуживает несколько изолированных организаций; переключение контекста — заголовком `X-Grafana-Org-Id` или выбором в UI.
- **Схема дашбордов:** В Grafana 13.x по умолчанию используется новый движок **Dynamic Dashboards** и схема дашборда **v2**. Дашборды старой схемы (v1) мигрируют в v2 автоматически при открытии; определённые как код (provisioning, API, Git Sync) дашборды продолжают работать.

### Ключевые возможности Grafana 13.x

| Возможность | Описание |
| :--- | :--- |
| **Dynamic Dashboards (GA)** | Новый движок раскладки и редактирования дашбордов, включённый по умолчанию в 13.0. Поддерживает вложенность рядов и табов до трёх уровней, переменные и аннотации в боковой панели, drag-and-drop панелей. |
| **Git Sync (GA)** | Нативная двусторонняя синхронизация дашбордов и папок с Git-репозиториями (GitHub, GitLab, Bitbucket, Pure Git). Позволяет редактировать дашборды в UI с коммитом в Git и открытием PR без внешних sidecar-контейнеров. |
| **Unified Alerting** | Централизованное управление оповещениями для всех типов источников данных с поддержкой сложных цепочек уведомлений. См. [Обзор Grafana Alerting](./alerting/concepts.md). |
| **Grafana Advisor (GA)** | Инструмент автоматической проверки здоровья инстанса: регулярные проверки источников данных, плагинов и настроек SSO с рекомендациями по исправлению. |
| **Suggested Dashboards** | Автоматический подбор готовых дашбордов под подключённый источник данных с оценкой совместимости метрик (public preview в 13.x). |

### Персистентность и хранение данных

| Компонент | Тип данных | Решение по умолчанию | Решение для HA/Prod |
| :--- | :--- | :--- | :--- |
| **Configuration Store** | Дашборды, пользователи, алерты | SQLite3 | PostgreSQL 12+ / MySQL 8.0+ |
| **Session Storage** | Сессии активных пользователей | Файловая система (`[session] provider = file`) | Redis или внешняя СУБД через `[session] provider` |
| **Image Storage** | Скриншоты панелей для алертов | Локальный диск | S3-совместимое объектное хранилище (например, MinIO) |

Grafana официально поддерживает в качестве внешней БД **PostgreSQL 12+** и **MySQL 8.0+**; SQLite годится только для разработки и небольших инсталляций и не поддерживается в HA-кластере.

### Жизненный цикл запроса

Понимание пути данных критично для диагностики и оптимизации:

1. **Frontend (React/TypeScript):** Пользователь взаимодействует с UI, задавая переменные, временной диапазон и фильтры.
2. **Composition:** Grafana собирает финальный запрос, подставляя значения переменных в шаблоны выражений (PromQL, LogQL, SQL).
3. **Backend (Go):** Обрабатывает авторизацию, кэширование и маршрутизацию.
4. **Data Source:** Внешняя система выполняет запрос и возвращает результат.
5. **Rendering:** Фронтенд рендерит панель (рендеринг может выполняться на бэкенде — "Image Rendering" — для экспорта в PNG/PDF, см. [Рендеринг изображений](./grafana_image_rendering.md)).

### Безопасность и аутентификация

Grafana 13.x реализует многоуровневую модель безопасности:

- **RBAC (Role-Based Access Control):** Fine-grained access control (фиксированные и кастомные роли с гранулярными экшенами `dashboards:read`, `datasources:query`) доступен только в **Grafana Enterprise и Grafana Cloud**. В Grafana OSS присутствуют лишь базовые организационные роли (Viewer, Editor, Admin). Роли задаются через RBAC API, Terraform или provisioning. См. [Управление пользователями и аутентификация](./grafana_user_management_and_authentication.md) и [Fine-grained RBAC](./grafana_rbac_fine_grained.md).
- **Аутентификация:** Встроенная (локальная БД), OAuth 2.0/OIDC, LDAP, SAML, JWT. Провайдеры и способы интеграции — в [Управление пользователями и аутентификация](./grafana_user_management_and_authentication.md), [SSO: SAML, JWT](./grafana_sso_saml_jwt.md).
- **Авторизация запросов:** Каждый запрос к источнику данных проверяется на соответствие прав пользователя. Источники данных могут быть помечены как `editable: false` через провиженинг для защиты от случайного изменения.
- **Сеть:** Grafana не открывает входящие порты к источникам данных через брандмауэр — взаимодействие инициирует сам Grafana (проксирование или прямой доступ в зависимости от конфигурации). Практические меры — в [Безопасность и hardening](./grafana_security_hardening.md).

### Кэширование

Grafana использует несколько независимых механизмов кэширования; они настраиваются разными секциями `grafana.ini` и не взаимозаменяемы:

| Механизм | Назначение | Секция / параметры | Доступность |
| :--- | :--- | :--- | :--- |
| **Remote cache** | Кэш токенов аутентификации и других временных auth-данных | `[remote_cache]` (`type = database`, `redis`, `memcached`) | OSS |
| **Query and resource caching** | Кэш результатов запросов к источникам и resource-запросов (TTL задаётся на каждый источник отдельно) | `[caching]` (`backend = memory`, `redis`, `memcached`) | Enterprise / Cloud |

- **Remote cache** имеет смысл только при использовании внешней БД: при SQLite временные данные хранятся в самой базе.
- **Query caching** не включается «для всех сразу»: после активации механизма кэш включается отдельно на вкладке Cache каждого источника данных.
- **Сессии пользователей** хранятся отдельно от этих кэшей — см. раздел [Персистентность](#персистентность-и-хранение-данных).

### Архитектура оповещений (Unified Alerting)

Начиная с Grafana 8.0, система оповещений перешла на архитектуру **Unified Alerting**, состоящую из двух логических компонентов:
- **Evaluator (Генератор):** Периодически выполняет запросы к источникам данных и оценивает пороговые значения.
- **Notifier (Обработчик/Alertmanager):** Принимает сработавшие алерты, применяет политики группировки, маршрутизации и подавления, доставляет уведомления через контакт-пойнты (Email, Slack, Telegram, PagerDuty и т.д.).

В режиме HA в Grafana 13.x доступен **Single-Node Evaluation (SNE)** (public preview): при явном включении (`ha_single_node_evaluation = true`) только узел с позицией 0 (Primary) выполняет вычисления, остальные получают результаты через Gossip-протокол, что снижает нагрузку на источники данных. По умолчанию режим отключён — все инстансы вычисляют все правила. Подробнее — [Обзор Grafana Alerting](./alerting/concepts.md), [Лучшие практики Alerting](./alerting/best_practices.md), [Высокая доступность](./high_availability.md).

### HTTP API

Grafana предоставляет HTTP API двух поколений:

- **Legacy API (`/api/`)** — исторический REST-интерфейс (дашборды, папки, источники данных, пользователи, организации, RBAC). Grafana объявила его устаревшим (deprecated) в пользу нового поколения; часть эндпоинтов в `/apis` пока не имеет аналога.
- **Новое поколение (`/apis/`)** — Kubernetes-подобный слой со стандартной структурой и версионированием:
  `/apis/<GROUP>/<VERSION>/namespaces/<NAMESPACE>/<RESOURCE>[/<NAME>]`
  Версии следуют уровням стабильности: `v1alpha1` (alpha), `v1beta1` (beta), `v1` (GA, включена по умолчанию).

- **Аутентификация:** Bearer-токен сервисного аккаунта (API-ключи упразднены и перенесены в Service Accounts). См. [Управление пользователями и аутентификация](./grafana_user_management_and_authentication.md).
- **Контекст организации:** заголовок `X-Grafana-Org-Id` (работает у сессии/basic auth с членством в нескольких организациях; токен сервисного аккаунта привязан к своей организации).
- **Спецификация:** OpenAPI/Swagger доступны встроенным UI по адресу `/swagger-ui` (JSON-описание — `/swagger`); внешняя документация — на [grafana.com](https://grafana.com/docs/grafana/latest/developers/http_api/).

## Практические сценарии

Способы развёртывания Grafana (Docker Compose, Helm, standalone-пакет) с предварительными требованиями и валидацией описаны отдельно: [Установка через Docker Compose](./Installation/docker_compose_setup.md), [Установка через Helm](./Installation/grafana_helm_installation.md).

### Первоначальная настройка и первый дашборд

**Предварительные требования:**
- Вновь развернутый инстанс Grafana 13.x (Docker/Helm/Standalone).
- Доступ к источнику данных (например, Prometheus на `http://localhost:9090`).

**Шаги:**
1. **Вход под администратором:**
   ```bash
   # Получение пароля admin из логов (первый запуск)
   docker logs grafana 2>&1 | grep "password"
   # Или сброс пароля
   grafana cli admin reset-admin-password admin123
   ```
2. **Подключение источника данных:**
   - В `Connections → Data Sources` добавьте Prometheus.
   - URL: `http://prometheus:9090`
   - Access: `Server` (проксирование через Grafana).
   - Нажмите "Save & Test" → ожидаемый вывод: `Data source successfully connected`.

3. **Создание дашборда:**
   - `Create → Dashboard → Add visualization`.
   - Выберите источник данных Prometheus.
   - Введите запрос: `up` или `sum(rate(prometheus_http_requests_total[5m]))`.
   - Нажмите "Apply".

**Валидация:**
```bash
# Проверка здоровья инстанса (эндпоинт не требует аутентификации)
curl -s http://grafana:3000/api/health
# → {"commit":"...","database":"ok","version":"13.2.x"}

# Проверка наличия дашборда
curl -s -H "Authorization: Bearer <SA_TOKEN>" http://grafana:3000/api/search?query=My%20Dashboard
# → JSON с найденным дашбордом
```

**Очистка:** Удалите созданный дашборд через UI или API, если он был создан для тестирования.

### Диагностика инцидента через Unified View

1. **Обнаружение:** Unified Alerting присылает уведомление о росте 5xx-ошибок или аномалиях по метрикам (Mimir/Prometheus); состояние самого инстанса Grafana отслеживается по эндпоинту `/metrics`.
2. **Корреляция:** Использование **Data Links** для бесшовного перехода от графика (Mimir) к конкретным строкам логов (Loki) с тем же временным интервалом и метками. Механика — в [Корреляция и exemplars](./grafana_correlation_exemplars.md).
3. **Анализ:** В Grafana Explore строится LogQL-запрос для выявления паттерна ошибок в логах (Loki).
4. **Трассировка:** Переход к Tempo для визуализации пути проблемного запроса и поиска узкого места в микросервисной архитектуре.

**Практические примеры запросов:**

```promql
# Mimir: Найти метрики с ростом 5xx ошибок (rate за 5 минут)
sum by (status_code) (rate(http_requests_total{status_code=~"5.."}[5m]))
```

```logql
# Loki: Поиск ошибок 500 с контекстом (строки до и после)
{service="api-gateway"} |= "500" | json | line_format "{{.timestamp}} {{.message}}"
```

**Валидация:**
- Убедитесь, что Data Link между Mimir и Loki настроен с макросами `$__range` и `$__tags`.
- Проверьте, что Tempo имеет теги `traceID` в Loki или Mimir для корреляции.

**Очистка:** Удалите временные дашборды и переменные, созданные для диагностики, чтобы не загрязнять основное пространство.

### Декларативное управление через провиженинг

Вместо ручного создания через UI используйте YAML-файлы для автоматизации.

**Структура:**
```
/etc/grafana/provisioning/
├── datasources/prometheus.yaml
├── dashboards/provider.yaml
└── alerting/contactpoints.yaml
```

**Пример — автоматическое подключение Prometheus:**
```yaml
# /etc/grafana/provisioning/datasources/prometheus.yaml
apiVersion: 1
datasources:
  - name: Prometheus-Prod
    type: prometheus
    url: http://prometheus:9090
    access: proxy
    isDefault: true
    jsonData:
      timeInterval: "15s"
    editable: false
```

**Валидация:**
```bash
# Проверка, что источник данных создан
curl -s -H "Authorization: Bearer <SA_TOKEN>" \
  http://grafana:3000/api/datasources | jq '.[] | select(.name=="Prometheus-Prod")'

# Проверка логов Grafana на ошибки парсинга
docker logs grafana 2>&1 | grep -i provisioning
```

См. детали в [Провиженинг Grafana](./grafana_provisioning.md).

### GitOps и Dashboard-as-Code

Эксплуатация дашбордов, источников данных и алертов как кода (Git Sync, file-based provisioning, Terraform, Jsonnet/Grafonnet, Kubernetes sidecar) подробно разобрана в [Monitoring as Code](./monitoring_as_code.md). Ключевая особенность Grafana 13.x — нативный **Git Sync** (GA в 13.0): двусторонняя синхронизация дашбордов и папок с GitHub, GitLab, Bitbucket или любым Git-репозиторием (Pure Git) без внешних sidecar-контейнеров. При включённом Git Sync источником правды для синхронизируемых папок становится Git-репозиторий.

## Устранение неполадок (Troubleshooting)

Расширенное руководство по диагностике self-hosted Grafana (логи, профайлер, метрики) — в [Диагностика и устранение неполадок Grafana](./grafana_troubleshooting.md).

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Grafana не запускается** | База данных заблокирована или недоступна | Проверьте подключение к PostgreSQL/MySQL; убедитесь, что миграции завершены. |
| **5xx ошибки в UI** | Источник данных недоступен или медленный | Проверьте доступность источника данных через `curl`; увеличьте `queryTimeout` в настройках. |
| **Дашборды не отображаются** | Ошибка в JSON-конфигурации дашборда | Используйте `api/dashboards/uid/:uid` для получения сырых данных и проверьте синтаксис. |
| **Плагины не загружаются** | Неподписанный плагин или архитектурная несовместимость | Проверьте `allow_loading_unsigned_plugins` и архитектуру (amd64/arm64). |
| **Git Sync не работает** | Ошибки аутентификации или права доступа | Проверьте SSH-ключ/токен; убедитесь, что репозиторий доступен из сети Grafana. |
| **Алерты не срабатывают** | Неправильная конфигурация SNE в HA | Убедитесь, что `ha_single_node_evaluation = true` и `ha_peers` настроены корректно. |
| **Ошибка `secret_key` mismatch** | Разные `secret_key` на узлах HA | Установите идентичную длинную случайную строку на всех узлах. |
| **ConfigMap > 1 MB** | Большой дашборд или провайдер | Включите `sidecar.dashboards.GZIP: true` в Helm values или разбейте на несколько ConfigMap. |

## Рекомендации (Best Practices)

- **Версионирование:** Фиксируйте версии Grafana в Docker (`grafana/grafana:13.2.x`) и плагинов в `values.yaml` (Helm) или manifests (Kubernetes). Избегайте тегов `latest` в production.
- **Безопасность:**
  - Используйте Service Accounts (API-ключи упразднены и автоматически перенесены в сервисные аккаунты).
  - Включите RBAC и назначайте минимально необходимые права (принцип наименьших привилегий).
  - Храните `secret_key` во внешнем vault; для HA он должен быть идентичен на всех узлах.
  - Никогда не используйте `allow_loading_unsigned_plugins = true` в production.
- **Производительность:**
  - Для редакции Enterprise задействуйте query caching для тяжелых панелей.
  - Ограничьте временные диапазоны по умолчанию, чтобы предотвратить перегрузку источников данных.
  - Для HA используйте PostgreSQL 12+ и Redis Cluster; SQLite не поддерживается в кластере.
  - Подробнее — [Производительность и тюнинг](./grafana_performance_tuning.md).
- **Мониторинг:**
  - Экспортируйте метрики Grafana (`/metrics`) для мониторинга самого инстанса.
  - Используйте Grafana Advisor для регулярной проверки здоровья.
- **Очистка:**
  - Удаляйте неиспользуемые плагины, дашборды и источники данных.
  - Для аудита востребованности дашбордов используйте Usage Insights (в редакции Enterprise).

## Особые случаи (Edge Cases)

- **Air-gapped среды:** Grafana требует предварительной загрузки всех плагинов и образов. Используйте приватный registry и `GF_PLUGINS_PREINSTALL_SYNC` для автоматической установки. Для Kubernetes используйте Init Container для копирования плагинов в `emptyDir`.
- **Архитектурная несовместимость:** ARM64 (Apple Silicon, ARM-серверы) несовместима с плагинами, скомпилированными только для amd64. Используйте эмуляцию (`binfmt_misc`) или пересоберите плагин.
- **Конфликты версий плагинов:** При обновлении плагина через CLI старые версии не удаляются автоматически. Используйте `grafana cli plugins ls` для проверки.
- **Ограничение ConfigMap (1 МБ):** Kubernetes ограничивает размер ConfigMap. Для дашбордов >1 МБ используйте GZIP-сжатие sidecar'а или хранение в S3.
- **SQLite в HA:** SQLite не поддерживает одновременную запись из нескольких процессов. В HA-режиме используйте исключительно PostgreSQL или MySQL.
- **Время drift в HA:** Разница во времени между узлами >500 мс приводит к дребезгу алертов. Обязательно используйте NTP/Chrony.
