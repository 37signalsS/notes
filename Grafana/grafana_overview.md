# Grafana: Обзор

## Определения

**Grafana** — универсальная open-source платформа для аналитики, мониторинга и интерактивной визуализации данных телеметрии (метрик, логов, трассировок, профилей). 

**Ключевые характеристики:**
- **Stateless-архитектура:** Grafana не хранит собираемые данные (метрики/логи), а выступает интерфейсом для внешних источников.
- **Сетевое взаимодействие:** По умолчанию работает на порту `3000` (протокол HTTP/HTTPS).
- **Персистентность настроек:** Хранит собственные данные (пользователи, дашборды, сессии) во внутренней базе данных. По умолчанию используется **SQLite**, для высокодоступных (HA) инсталляций рекомендуются **PostgreSQL** или **MySQL**.
- **Управление расширениями:** Утилита `grafana-cli` используется для установки плагинов и администрирования из командной строки.

**Текущая версия (август 2026):** Grafana 13.1.x.
- **Статус веток:** 13.x — актуальная стабильная ветка (Current), 12.x — поддержка безопасности (LTS), 11.x — EOL (июнь 2026).

### Основные понятия экосистемы

| Понятие | Определение |
| :--- | :--- |
| **Дашборд (Dashboard)** | Логический контейнер, объединяющий панели (визуализации), фильтры и аннотации для решения конкретной аналитической задачи. |
| **Панель (Panel)** | Отдельный визуальный блок внутри дашборда (график, таблица, карта, лог-стрим и т.д.), построенный на основе одного или нескольких запросов к источникам данных. |
| **Источник данных (Data Source)** | Подключение к внешней системе хранения телеметрии (Prometheus, Loki, Tempo, PostgreSQL, Elasticsearch и др.), откуда Grafana получает данные для панелей. |
| **Переменная (Variable / Template)** | Параметр, добавляющий интерактивность в дашборд. Позволяет динамически изменять запросы, диапазоны времени или отображаемые данные без редактирования каждой панели отдельно. |
| **Оповещение (Alert)** | Правило, которое периодически оценивает выражение (запрос) и генерирует уведомление при нарушении заданного порогового значения. |
| **Аннотация (Annotation)** | Визуальный маркер на временной шкале дашборда, отмечающий события (деплои, инциденты, релизы) для контекстного анализа. |
| **Провиженинг (Provisioning)** | Подход Infrastructure as Code (IaC) для автоматизированного управления конфигурацией Grafana через YAML/JSON-файлы. См. [Провиженинг Grafana](./grafana_provisioning.md). |

### Grafana Stack (LGTM)

Комплексное решение для реализации [наблюдаемости (observability)](../Concepts/Observability_and_Monitoring/observability_definitions.md). Включает в себя:
- **Grafana** — уровень представления.
- **Mimir/Prometheus** — хранение метрик.
- **Loki** — агрегация логов.
- **Tempo** — распределенные трассировки.
- **Alloy** — унифицированный сборщик телеметрии (заменил Grafana Agent).

## Базовые концепции

### Архитектура и лицензирование

- **Технологический стек:** Бэкенд реализован на **Go**, фронтенд — на **TypeScript/React**.
- **Лицензия:** Распространяется под лицензией **AGPLv3** (основные компоненты).
- **Конфигурация:** Управление параметрами сервера осуществляется через файл `grafana.ini` или переменные окружения (формат `GF_<SECTION>_<KEY>`).

### Ключевые возможности Grafana 13.x

| Возможность | Описание |
| :--- | :--- |
| **Git Sync (GA)** | Нативная двусторонняя синхронизация с Git-репозиториями. Позволяет редактировать дашборды в UI с автоматическим коммитом в Git (и созданием PR) или подтягивать изменения из JSON-файлов репозитория. |
| **Grafana Assistant** | ИИ-ассистент, доступный для OSS-версий. Помогает в написании запросов (PromQL, LogQL, SQL) и анализе аномалий. |
| **Grafana Advisor** | Инструмент автоматической проверки здоровья сервера. Дает рекомендации по оптимизации производительности, настройке кэширования и очистке неиспользуемых ресурсов. |
| **Unified Alerting** | Централизованное управление оповещениями для всех типов источников данных с поддержкой сложных цепочек уведомлений. |
| **Suggested Dashboards** | Автоматическое построение панелей на основе анализа схемы данных (Data Discovery) подключенного источника. |

### Персистентность и хранение данных

| Компонент | Тип данных | Решение по умолчанию | Решение для HA/Prod |
| :--- | :--- | :--- | :--- |
| **Configuration Store** | Дашборды, пользователи, алерты | SQLite3 | PostgreSQL 15+ / MySQL 8+ |
| **Session Storage** | Сессии активных пользователей | Файловая система | Redis / Database |
| **Image Storage** | Скриншоты панелей для алертов | Локальный диск | S3 / Azure Blob / GCS |

### Жизненный цикл запроса

Понимание пути данных критично для диагностики и оптимизации:

1. **Frontend (React/TypeScript):** Пользователь взаимодействует с UI, задавая переменные, временной диапазон и фильтры.
2. **Composition:** Grafana собирает финальный запрос, подставляя значения переменных в шаблоны выражений (PromQL, LogQL, SQL).
3. **Backend (Go):** Обрабатывает авторизацию, кэширование и маршрутизацию.
4. **Data Source:** Внешняя система выполняет запрос и возвращает результат.
5. **Rendering:** Фронтенд рендерит панель (рендеринг может выполняться на бэкенде — "Image Rendering" — для экспорта в PNG/PDF).

### Безопасность и аутентификация

Grafana 13.x реализует многоуровневую модель безопасности:

- **RBAC (Role-Based Access Control):** Начиная с версии 11, расширенное управление доступом доступно в OSS. Поддерживаются базовые роли (Viewer, Editor, Admin) и кастомные роли с гранулярными экшенами (`dashboards:read`, `datasources:query`). См. [Управление пользователями и аутентификация](./grafana_user_management_and_authentication.md).
- **Аутентификация:** Встроенная (локальная БД), OAuth 2.0/OIDC, LDAP, SAML, Workload Identity Federation (GCP/AWS/Azure).
- **Авторизация запросов:** Каждый запрос к источнику данных проверяется на соответствие прав пользователя. Источники данных могут быть помечены как `editable: false` через провиженинг для защиты от случайного изменения.
- **Сеть:** Grafana не открывает входящие порты к источникам данных через брандмауэр — взаимодействие инициирует сам Grafana (проксирование или прямой доступ в зависимости от конфигурации).

### Кэширование

| Тип кэша | Назначение | Параметры |
| :--- | :--- | :--- |
| **Query Result Cache** | Кэширование результатов запросов к источникам данных | Настраивается через `[cache]` в `grafana.ini` или через Redis |
| **Dashboard Cache** | Кэширование структур дашбордов и панелей | Включен по умолчанию в памяти |
| **Resource Cache** | Кэширование статических ресурсов (изображения плагинов) | Файловая система или CDN |

### Архитектура оповещений (Unified Alerting)

Начиная с Grafana 8.0, система оповещений перешла на архитектуру **Unified Alerting**, состоящую из двух логических компонентов:
- **Evaluator (Генератор):** Периодически выполняет запросы к источникам данных и оценивает пороговые значения.
- **Notifier (Обработчик):** Принимает сработавшие алерты, применяет политики группировки и доставляет уведомления через контакт-пойнты (Email, Slack, PagerDuty и т.д.).

В режиме HA работает **Single-Node Evaluation (SNE)**: только узел с позицией 0 (Primary) выполняет вычисления, что снижает нагрузку на источники данных.

### HTTP API

Grafana предоставляет RESTful HTTP API для полного управления ресурсами:
- Базовый URL: `/api/`
- Аутентификация: Bearer-токен (Service Account) или API Key (Legacy).
- Версионирование: `Accept: application/json` заголовок для явного указания формата.
- Документация: доступна эндпоинтом `/api/swagger` или на [официальном сайте](https://grafana.com/docs/grafana/latest/developers/http_api/).

## Практические сценарии

### Первоначальная настройка и первый дашборд

**Предварительные требования:**
- Вновь развернутый инстанс Grafana 13.x (Docker/Helm/Standalone).
- Доступ к источнику данных (например, Prometheus на `http://localhost:9090`).

**Шаги:**
1. **Вход под администратором:**
   ```bash
   # Получение пароля admin из логов (первый запуск)
   docker logs grafana 2>&1 | grep "password"
   # Или сброс пароля
   grafana-cli admin reset-admin-password admin123
   ```
2. **Подключение источника данных:**
   - В `Connections → Data Sources` добавьте Prometheus.
   - URL: `http://prometheus:9090`
   - Access: `Server` (проксирование через Grafana).
   - Нажмите "Save & Test" → ожидаемый вывод: `Data source successfully connected`.

3. **Создание дашборда:**
   - `Create → Dashboard → Add visualization`.
   - Выберите источник данных Prometheus.
   - Введите запрос: `up` или `sum(rate(prometheus_http_requests_total[5m]))`.
   - Нажмите "Apply".

**Валидация:**
```bash
# Проверка доступности API
curl -s -o /dev/null -w "%{http_code}" http://admin:admin123@grafana:3000/api/health
# → 200

# Проверка наличия дашборда
curl -s -H "Authorization: Bearer <SA_TOKEN>" http://grafana:3000/api/search?query=My%20Dashboard
# → JSON с найденным дашбордом
```

**Очистка:** Удалите созданный дашборд через UI или API, если он был создан для тестирования.

### Реализация GitOps-процесса (Observability as Code)

С выходом Grafana 13.x нативная синхронизация вытесняет внешние инструменты (sidecar-контейнеры).

**Предварительные требования:**
- Grafana 13.x с включенной функцией Git Sync (GA).
- Git-репозиторий с дашбордами в формате JSON.
- SSH-ключ или GitHub App с правами на запись.

**Шаги:**
1. **Подключение репозитория:** В настройках Grafana указывается URL Git-репозитория (GitHub/GitLab) и метод аутентификации (SSH-ключ или GitHub App). Включается режим `Bidirectional` (двусторонний) или `Pull` (только чтение).
2. **Разработка:** Инженер создает дашборд в интерфейсе Grafana, настраивает панели и фильтры.
3. **Фиксация:** При нажатии "Save" Grafana предлагает создать коммит. Инженер вводит описание, и изменения улетают в Git.
4. **Синхронизация:** Другие инстансы Grafana (например, в разных регионах) автоматически подтягивают изменения из этого же репозитория.

**Валидация:**
```bash
# Проверка статуса Git Sync через API
curl -s -H "Authorization: Bearer <SA_TOKEN>" \
  http://grafana:3000/api/git/settings | jq .

# Ожидаемый результат: enabled=true, mode="bidirectional"

# Проверка последнего коммита
git -C /path/to/repo log --oneline -1
# → должен содержать описание изменения дашборда
```

**Очистка:** Отключите Git Sync в UI перед удалением репозитория, чтобы предотвратить автоматические коммиты от удаленного инстанса.

### Диагностика инцидента через Unified View

1. **Обнаружение:** Grafana Advisor сигнализирует о росте потребления памяти в самом инстансе Grafana или Unified Alerting присылает уведомление о росте 5xx ошибок в приложении.
2. **Корреляция:** Использование **Data Links** для бесшовного перехода от графика (Mimir) к конкретным строкам логов (Loki) с тем же временным интервалом и метками.
3. **Анализ:** Grafana Assistant помогает составить сложный LogQL-запрос для выявления паттерна ошибок в логах.
4. **Трассировка:** Переход к Tempo для визуализации пути проблемного запроса и поиска узкого места в микросервисной архитектуре.

**Практические примеры запросов:**

```promql
# Mimir: Найти метрики с ростом 5xx ошибок (rate за 5 минут)
sum by (status_code) (rate(http_requests_total{status_code=~"5.."}[5m]))
```

```logql
# Loki: Поиск ошибок 500 с контекстом (строки до и после)
{service="api-gateway"} |= "500" | json | line_format "{{.timestamp}} {{.message}}"
```

**Валидация:**
- Убедитесь, что Data Link между Mimir и Loki настроен с макросами `$__range` и `$__tags`.
- Проверьте, что Tempo имеет теги `traceID` в Loki или Mimir для корреляции.

**Очистка:** Удалите временные дашборды и переменные, созданные для диагностики, чтобы не загрязнять основное пространство.

### Декларативное управление через провиженинг

Вместо ручного создания через UI, используйте YAML-файлы для автоматизации.

**Структура:**
```
/etc/grafana/provisioning/
├── datasources/prometheus.yaml
├── dashboards/provider.yaml
└── alerting/contactpoints.yaml
```

**Пример — автоматическое подключение Prometheus:**
```yaml
# /etc/grafana/provisioning/datasources/prometheus.yaml
apiVersion: 1
datasources:
  - name: Prometheus-Prod
    type: prometheus
    url: http://prometheus:9090
    access: proxy
    isDefault: true
    jsonData:
      timeInterval: "15s"
    editable: false
```

**Валидация:**
```bash
# Проверка, что источник данных создан
curl -s -H "Authorization: Bearer <SA_TOKEN>" \
  http://grafana:3000/api/datasources | jq '.[] | select(.name=="Prometheus-Prod")'

# Проверка логов Grafana на ошибки парсинга
docker logs grafana 2>&1 | grep -i provisioning
```

См. детали в [Провиженинг Grafana](./grafana_provisioning.md).

### Рекомендации (Best Practices)

- **Версионирование:** Фиксируйте версии Grafana в Docker (`grafana/grafana:13.1.x`) и плагинов в `values.yaml` (Helm) или manifests (Kubernetes). Избегайте тегов `latest` в production.
- **Безопасность:**
  - Используйте Service Accounts вместо Legacy API Keys.
  - Включите RBAC и назначайте минимально необходимые права (принцип наименьших привилегий).
  - Храните `secret_key` во внешнем vault; для HA он должен быть идентичен на всех узлах.
  - Никогда не используйте `allow_loading_unsigned_plugins = true` в production.
- **Производительность:**
  - Используйте кэширование запросов для тяжелых панелей.
  - Ограничьте временные диапазоны по умолчанию, чтобы предотвратить перегрузку источников данных.
  - Для HA используйте PostgreSQL 15+ и Redis Cluster; SQLite не поддерживается в кластере.
- **Мониторинг:**
  - Экспортируйте метрики Grafana (`/metrics`) для мониторинга самого инстанса.
  - Используйте Grafana Advisor для регулярной проверки здоровья.
- **Очистка:**
  - Удаляйте неиспользуемые плагины, дашборды и источники данных.
  - Используйте Usage Insights для анализа востребованности дашбордов.

### Устранение неполадок (Troubleshooting)

| Проблема | Возможная причина | Решение |
| :--- | :--- | :--- |
| **Grafana не запускается** | База данных заблокирована или недоступна | Проверьте подключение к PostgreSQL/MySQL; убедитесь, что миграции завершены. |
| **5xx ошибки в UI** | Источник данных недоступен или медленный | Проверьте доступность источника данных через `curl`; увеличьте `queryTimeout` в настройках. |
| **Дашборды не отображаются** | Ошибка в JSON-конфигурации дашборда | Используйте `api/dashboards/uid/:uid` для получения сырых данных и проверьте синтаксис. |
| **Плагины не загружаются** | Неподписанный плагин или архитектурная несовместимость | Проверьте `allow_loading_unsigned_plugins` и архитектуру (amd64/arm64). |
| **Git Sync не работает** | Ошибки аутентификации или права доступа | Проверьте SSH-ключ/токен; убедитесь, что репозиторий доступен из сети Grafana. |
| **Алерты не срабатывают** | Неправильная конфигурация SNE в HA | Убедитесь, что `ha_single_node_evaluation = true` и `ha_peers` настроены корректно. |
| **Ошибка `secret_key` mismatch** | Разные `secret_key` на узлах HA | Установите идентичную длинную случайную строку на всех узлах. |
| **ConfigMap > 1 MB** | Большой дашборд или провайдер | Включите `sidecar.dashboards.GZIP: true` в Helm values или разбейте на несколько ConfigMap. |

### Особые случаи (Edge Cases)

- **Air-gapped среды:** Grafana требует предварительной загрузки всех плагинов и образов. Используйте приватный registry и `GF_INSTALL_PLUGINS` для автоматической установки. Для Kubernetes используйте Init Container для копирования плагинов в `emptyDir`.
- **Архитектурная несовместимость:** ARM64 (Apple Silicon, AWS Graviton) несовместима с плагинами, скомпилированными только для amd64. Используйте эмуляцию (`binfmt_misc`) или пересоберите плагин.
- **Конфликты версий плагинов:** При обновлении плагина через CLI старые версии не удаляются автоматически. Используйте `grafana-cli plugins ls` для проверки.
- **Ограничение ConfigMap (1 МБ):** Kubernetes ограничивает размер ConfigMap. Для дашбордов >1 МБ используйте GZIP-сжатие sidecar'а или хранение в S3.
- **SQLite в HA:** SQLite не поддерживает одновременную запись из нескольких процессов. В HA-режиме используйте исключительно PostgreSQL или MySQL.
- **Время drift в HA:** Разница во времени между узлами >500 мс приводит к дребезгу алертов. Обязательно используйте NTP/Chrony.
