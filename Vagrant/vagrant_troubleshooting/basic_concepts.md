# Vagrant Troubleshooting — Основные концепции

**Актуально для:** Vagrant 2.4.x

## Определения

**Рассинхронизация состояния (State Desync)** — ситуация, когда локальные метаданные Vagrant (директория `.vagrant/`) не соответствуют реальному состоянию виртуальной машины в гипервизоре. Основной индикатор — файл `.vagrant/machines/<name>/<provider>/id`, содержащий уникальный идентификатор ВМ у провайдера. При рассинхронизации Vagrant не может корректно управлять ВМ: команды `vagrant halt`, `vagrant destroy` или `vagrant ssh` завершаются ошибкой «Machine not found» или пытаются управлять несуществующей ВМ.

**Изоляция метаданных (`VAGRANT_DOTFILE_PATH`)** — механизм изменения пути к директории `.vagrant/`. Ошибки в этом параметре часто приводят к тому, что Vagrant «теряет» уже запущенные машины. В CI/CD и при параллельном запуске нескольких инстансов одного проекта изоляция метаданных предотвращает гонки за ресурсы и коллизии UUID.

**Коммуникатор (Communicator)** — программный мост, через который Vagrant отправляет команды внутрь ВМ. Основные типы: `ssh` (Linux/macOS) и `winrm` (Windows). Проблемы с коммуникатором блокируют этапы провижининга и монтирования папок. Vagrant выбирает коммуникатор автоматически на основе типа гостевой ОС, но это поведение можно переопределить через `config.communicator = "ssh"`.

**SSH-ключ Vagrant** — приватный ключ, используемый для управления ВМ. По умолчанию используется «небезопасный» ключ (`~/.vagrant.d/insecure_private_key`), который заменяется на уникальный при первом запуске. При рассинхронизации ключ может не обновиться, что приводит к `Permission denied (publickey)`.

**Глобальный реестр (`global-status`)** — база данных всех ВМ, известных Vagrant на хосте, хранящая связь между именем проекта, путем к `.vagrant/` и идентификатором ВМ у провайдера. Команда `vagrant global-status --prune` очищает записи о ВМ, удаленных вручную через гипервизор.

**Провижинер (Provisioner)** — плагин или встроенный модуль, отвечающий за конфигурацию гостевой ОС после запуска (shell, ansible, puppet, chef). Сбои на этапе провижининга не влияют на жизнеспособность ВМ, но оставляют её в неконфигурированном состоянии.

**Бок (Box)** — базовый шаблон ВМ, упакованный в специфический формат провайдера (`.box`). Содержит предустановленную ОС, пользователя `vagrant` и минимальный набор инструментов. Жестко привязан к провайдеру: `qcow2` для Libvirt/KVM, `vmdk`/`ovf` для VirtualBox, `vhd`/`vhdx` для Hyper-V.

## Основные концепции

### Архитектура управления состоянием

Vagrant хранит состояние проекта в двух независимых пространствах:

1. **Локальные метаданные (`.vagrant/`)** — привязаны к директории проекта. Содержат:
   - `machines/<name>/<provider>/id` — UUID ВМ у гипервизора
   - `machines/<name>/<provider>/private_key` — SSH-ключ для доступа
   - `machines/<name>/<provider>/action_*` — логи исполнения команд
   - Сгенерированные конфиги (например, `ssh_config`)

2. **Глобальный реестр (`~/.vagrant.d/data/machine-index/index`)** — отслеживает все ВМ на хосте. Позволяет находить ВМ по имени проекта даже если `.vagrant/` перемещена.

Разрыв между этими двумя пространствами составляет основную причину большинства проблем отсоединения состояния.

### Жизненный цикл команды и точки отказа

| Этап | Действие Vagrant | Типичные ошибки | Диагностика |
| :--- | :--- | :--- | :--- |
| **1. Валидация** | Проверка Ruby-синтаксиса Vagrantfile | `SyntaxError`, `NameError` | `vagrant validate` |
| **2. Загрузка** | Чтение конфигурации, загрузка плагинов | `Plugin error`, несовместимость Ruby | `VAGRANT_LOG=debug` |
| **3. Поиск образа** | Проверка `~/.vagrant.d/boxes/`, загрузка при отсутствии | `Box not found`, `SSL certificate problem` | `vagrant box list`, `VAGRANT_LOG=debug` |
| **4. Создание ВМ** | Взаимодействие с API провайдера | `VT-x not available`, `No space left`, конфликты сетей | Логи провайдера (libvirt: `virsh`, VirtualBox: `VBoxManage`) |
| **5. Загрузка ОС** | Запуск ВМ, ожидание готовности SSH | `Connection timeout`, `Permission denied` | `vagrant ssh-config`, `ssh -vvv` |
| **6. Провижининг** | Выполнение shell/ansible/puppet скриптов | Сбои скриптов, таймауты | `VAGRANT_LOG=debug`, логи провижинера |
| **7. Монтирование** | Создание общих папок (NFS, virtiofs, vboxsf) | `Mounting failed`, `Permission denied` | `mount` внутри ВМ, логи Vagrant |
| **8. Информирование** | Вывод итогового статуса, проброшенных портов | — | `vagrant port`, `vagrant status` |

### Взаимодействие с провайдером

Vagrant не является гипервизором — это оркестратор, который транслирует декларативные команды в imperative вызовы API провайдера. При troubleshooting важно понимать, на каком уровне произошел сбой:

- **Уровень Vagrant:** ошибки парсинга Vagrantfile, несовместимость плагинов, проблемы с сетевой конфигурацией.
- **Уровень провайдера:** ошибки гипервизора (Libvirt: `virsh`, VirtualBox: `VBoxManage`). Эти ошибки часто появляются в логах Vagrant как `ERROR`, но их истинная причина требует диагностики на стороне гипервизора.
- **Уровень гостевой ОС:** проблемы внутри ВМ (не запущен `sshd`, не настроен `cloud-init`, не установлены Guest Additions). Vagrant видит их как таймауты коммуникатора или ошибки монтирования.

## Основные источники проблем

1.  **Инфраструктурные:** Ошибки сетевых мостов, конфликты IP-адресов, нехватка дискового пространства или RAM на хосте, отключенные аппаратные возможности виртуализации (Intel VT-x / AMD-V) в BIOS/UEFI.
2.  **Синхронизация времени (Clock Drift):** Расхождение времени между хостом и гостем может приводить к ошибкам в работе SSL/TLS, Kerberos и баз данных. Особенно критично для InfluxDB, MongoDB, Ceph и систем, использующих сертификаты X.509 с коротким временем жизни.
3.  **Программные конфликты:** Несовместимость версий Vagrant и плагинов, отсутствие Guest Additions внутри образа, блокировки антивирусом или файрволом, конфликты между гипервизорами (например, VirtualBox + Hyper-V на Windows).
4.  **Прокси-серверы:** Отсутствие настроек `http_proxy` блокирует скачивание образов и установку плагинов (требуется плагин `vagrant-proxyconf`). В корпоративных сетях без настроенного прокси Vagrant не сможет даже проверить наличие обновлений.
5.  **Специфика Apple Silicon:** Использование x86 образов на архитектуре ARM64 без соответствующей эмуляции (см. [Vagrant на Apple Silicon](../vagrant_macos_apple_silicon.md)). Ограничения QEMU-эмуляции: производительность в 3–5 раз ниже нативной KVM, отсутствие гостевых ускорителей OpenGL.
6.  **Проблемы провайдера:** Несовместимость формата диска (например, попытка запуска `qcow2` образа в VirtualBox), отсутствие необходимого плагина, неверные параметры пулов хранилища.
7.  **Сетевая изоляция:** Конфликты с VPN (Tailscale, ZeroTier), Docker Networks, другими инстансами Vagrant, занимающими стандартную подсеть `192.168.121.0/24`.

## Диагностика и восстановление

### Проверка компонентов

Диагностические команды для быстрой оценки состояния окружения:

```bash
# Глобальный статус всех ВМ в системе
vagrant global-status
# → id   name   provider   state   directory
#   ---  ----   --------   -----   ---------
#   123  default libvirt   running /home/user/project

# Проверка установленных образов
vagrant box list
# → bento/ubuntu-24.04 (libvirt, 0)
#   generic/ubuntu2404  (virtualbox, 1)

# Проверка и обновление плагинов
vagrant plugin list
# → vagrant-libvirt (0.12.2, global)
#   vagrant-vbguest (0.11.0, global)

vagrant plugin update
# → Updating vagrant-libvirt to 0.13.0...
```

### Восстановление плагинов

Часто требуется после обновления версии Vagrant или Ruby в системе.

- **`vagrant plugin repair`** — попытка исправить зависимости gem без полной переустановки.
- **`vagrant plugin expunge --reinstall`** — полное удаление и повторная установка всех пользовательских плагинов (самый надёжный метод).
- Полный пошаговый сценарий с валидацией — в [Практических сценариях](./practical_scenarios.md#сценарий-18-плагины-и-зависимости).
- Предотвращение проблем со сбоем плагинов — в [профилактике](./additional_info.md#предотвращение-и-обслуживание).

### Гранулярное восстановление состояния

Пред праложением полного сброса попробуйте точечное восстановление:

```bash
# 1. Проверьте, существует ли ВМ в гипервизоре
virsh list --all          # Libvirt
# → Name   State   Autostart   Autostartable
#   my-vm  running  1           1

VBoxManage list vms       # VirtualBox
# → "my-vm" {12345678-abcd-...}

# 2. Если ВМ существует, но Vagrant её не видит — исправьте id в .vagrant/
echo "<provider_uuid>" > .vagrant/machines/default/libvirt/id

# 3. Если SSH-ключ рассинхронизирован — перегенерируйте
vagrant ssh-config
# → Host default
#   HostName 127.0.0.1
#   User vagrant
#   IdentityFile /path/.vagrant/machines/.../private_key

# 4. Изоляция проблемного провижининга
vagrant up --no-provision
# → Базовая ВМ запущена, коммуникатор работает
vagrant provision
# → Провинчен только provisioning step
```

## "Золотой молоток": полный сброс

**Требования (Prerequisites):** эта процедура удаляет все данные внутри ВМ. Перед её применением:
1. Остановите ВМ (`vagrant halt`), если они работают.
2. Сохраните важные данные через `vagrant ssh -c "sudo tar czf /vagrant/backup.tar.gz /path/to/data"` или `vagrant package`.
3. Убедитесь, что нет других активных проектов в директории (команда `rm -rf .vagrant` удаляет локальные метаданные текущего проекта).

**Валидация:** после выполнения всех шагов запустите `vagrant up` — ВМ должна успешно создаться и провижениться. Если ошибка сохраняется, проблема не в State Desync.

```bash
# 1. Принудительное удаление (даже если ВМ не видна Vagrant)
vagrant destroy -f
# → ==> default: Finding domain...
#     ==> default: Deleting domain...

# 2. Удаление локальных метаданных проекта
rm -rf .vagrant

# 3. Очистка глобального кэша состояний
vagrant global-status --prune
# → id   name   provider   state   directory
#   (пустой список после prune)
```

## Уровни логирования и переменные

Vagrant управляется через переменные окружения, позволяющие получить детальный отчёт о сбоях. Для производственной диагностики используйте `VAGRANT_LOG=debug` (самый подробный уровень) совместно с `VAGRANT_LOG_FILE` для записи лога в файл — это позволяет сохранять вывод для последующего анализа и передачи коллегам.

| Переменная | Значения | Описание |
| :--- | :--- | :--- |
| **`VAGRANT_LOG`** | `debug`, `info`, `warn`, `error` | Уровень детализации вывода в консоль. |
| **`VAGRANT_LOG_FILE`**| `/path/to/log.txt` | Запись лога в файл (рекомендуется для debug). |
| **`VAGRANT_DEFAULT_PROVIDER`** | `virtualbox`, `libvirt` | Принудительный выбор провайдера при отладке. |
| **`VAGRANT_NO_PARALLEL`** | `true` | Отключает параллельный запуск (полезно при дебаге гонок ресурсов). |
| **`VAGRANT_DOTFILE_PATH`** | `/custom/path/.vagrant` | Перенаправляет хранение метаданных (для CI/CD и параллельных запусков). |
| **`VAGRANT_NO_TTY`** | `1` | Отключает интерактивный режим (обязательно для CI/CD пайплайнов). |
| **`VAGRANT_HTTP_PROXY`** / **`VAGRANT_HTTPS_PROXY`** | `http://proxy:port` | Прокси для загрузки образов. Работает независимо от системных переменных. |
| **`VAGRANT_NO_PROXY`** | `localhost,127.0.0.1` | Список исключений из прокси. |
| **`VAGRANT_BOX_UPDATE_CHECK`** | `0` | Отключает автоматическую проверку обновлений box (полезно в CI для скорости). |

**Пример запуска с отладкой в файл:**
```bash
VAGRANT_LOG=debug VAGRANT_LOG_FILE=vagrant_debug.log vagrant up
# → Логи Vagrant, provisioning и SSH записываются в vagrant_debug.log
```

## Устранение неполадок

### Каталог типовых ошибок и паттерны

| Ошибка / Симптом | Вероятная причина | Первый шаг диагностики | Решение |
| :--- | :--- | :--- | :--- |
| `Machine not found` | State Desync: `.vagrant/` ссылается на несуществующую ВМ | `vagrant global-status` | `vagrant global-status --prune && vagrant up` или точечное обновление `id` файла |
| `Permission denied (publickey)` | Несоответствие ключей, сбой `cloud-init`, неверные права | `vagrant ssh-config`, `ssh -vvv` | Перезапуск ВМ, проверка `sshd` внутри гостя |
| `Box format mismatch` | Попытка запуска образа не для текущего провайдера | `vagrant box list` | Скачать box для нужного провайдера или указать `--provider` |
| `No space left on device` | Переполнение пула хранилища гипервизора или `~/.vagrant.d/` | `df -hT`, `virsh pool-info` | `vagrant box prune`, очистка пулов, расширение диска |
| `VT-x is not available` | Hyper-V / WSL2 / Memory Integrity захватили аппаратную виртуализацию (Windows) | `systeminfo` | Отключить Hyper-V или переключиться на `hyperv` провайдер |
| `Mounting shared folders failed` | Отсутствие Guest Additions, неправильные права, firewall | `vagrant reload`, `vagrant plugin install vagrant-vbguest` | Переключение на `virtiofs`/`nfs`/`rsync`, проверка `mount` внутри ВМ |
| `SSL certificate problem` | Корпоративный MITM-прокси, устаревший `ca-certificates` | `curl -v https://vagrantcloud.com` | Добавление корневого сертификата в цепочку, флаг `--insecure` как крайняя мера |
| `Plugin error` | Несовместимость версий Vagrant и плагинов, сбой зависимостей Ruby | `vagrant plugin list` | `vagrant plugin expunge --reinstall` |
| `Call to virNetworkCreate failed` | Конфликт подсетей с Docker/VPN/Vagrant | `virsh net-list --all` | Смена подсети в Vagrantfile на нестандартную (`10.0.0.0/24`) |
| `The provider 'X' is not supported` | Отсутствие провайдера или несовместимость архитектуры (Apple Silicon) | `uname -m` | Установка нужного плагина или переключение на `qemu`/`vmware_desktop` |

## Лучшие практики

### Рекомендации по анализу логов

При изучении `debug` лога ищите следующие паттерны:
- `DEBUG ssh`: проблемы с аутентификацией или таймауты подключения.
- `DEBUG interface`: ошибки создания сетевых мостов или захвата IP.
- `DEBUG guest`: ошибки определения типа ОС гостя.
- `DEBUG mount`: проблемы с монтированием общих папок (NFS, virtiofs).
- `DEBUG provisioner`: ошибки выполнения провижининга (ansible, shell, puppet).
- `ERROR`: критические сбои API провайдера (VirtualBox, Libvirt).
- `Plugin error`: несовместимость расширений с текущей версией ядра/Vagrant.
