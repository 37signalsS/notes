# Принципы работы систем обмена сообщениями

**Актуально для:** Apache Kafka 3.9 / 4.0 (KRaft), RabbitMQ 3.13 / 4.0

Системы обмена сообщениями (Message Queues, Message Brokers) представляют собой специализированное промежуточное программное обеспечение (Middleware), предназначенное для реализации асинхронного взаимодействия между компонентами распределенных систем. Основная задача таких систем — обеспечить надежную передачу данных (сообщений) от отправителя к получателю, минимизируя их прямую связность (decoupling) по времени, пространству и технологическому стеку.

---

## Определения

- **Очереди сообщений (Message Queues):** Механизм, обеспечивающий асинхронный обмен данными, где сообщения накапливаются в структуре данных брокера и хранятся до тех пор, пока не будут подтверждены или вытеснены по политике хранения.
- **Брокер сообщений (Message Broker):** Централизованный сервер или распределенный кластер узлов, ответственный за прием, маршрутизацию, персистентное хранение и доставку сообщений клиентам.
- **Продюсер (Producer / Publisher):** Процесс или компонент системы, инициирующий отправку сообщения в брокер.
- **Консьюмер (Consumer / Subscriber):** Процесс или компонент системы, подписанный на получение данных из брокера для их последующей обработки.
- **Сообщение (Message):** Атомарная единица передаваемой информации. Состоит из полезной нагрузки (Payload — тело данных в бинарном или текстовом формате) и метаданных (Headers — служебные заголовки, Key — ключ маршрутизации/партиционирования, Timestamp — временная метка).
- **Очередь (Queue):** Именованный буфер сообщений, в классических брокерах (RabbitMQ) работающий по модели FIFO, где каждое сообщение после подтверждения вычитывания удаляется из очереди.
- **Топик / Тема (Topic):** Логический именованный канал. В архитектуре распределенного журнала ([Apache Kafka](./kafka_overview.md)) представляет собой неизменяемый упорядоченный append-only лог, разделенный на партиции, где сообщения сохраняются независимо от факта их прочтения.
- **Подтверждение (Acknowledgement / Ack, Nack):** Сигнал от консьюмера брокеру об успешной (`ack`) или неуспешной (`nack` / `reject`) обработке сообщения.
- **Смещение (Offset):** Уникальный монотонно возрастающий целочисленный идентификатор записи в пределах одной партиции Kafka, фиксирующий текущую позицию консьюмера.
- **Партиция (Partition):** Минимальная физическая единица хранения и горизонтального масштабирования в Kafka, представляющая собой упорядоченный неизменяемый файл журнала.
- **ISR (In-Sync Replicas):** Множество реплик партиции, которые полностью синхронизированы с лидером и не отстают от него дольше заданного таймаута (`replica.lag.time.max.ms`). Подробнее: **[ISR и репликация](./kafka_isr_replication.md)**.
- **High Watermark (HW):** Офсет последнего сообщения в партиции, которое было успешно реплицировано на все активные узлы из списка ISR. Консьюмеры имеют доступ к чтению только до HW, что защищает от чтения незафиксированных данных.
- **Log End Offset (LEO):** Офсет следующей записи, которая будет записана в лог реплики (всегда больше или равен HW).
- **Consumer Group (Группа потребителей):** Пул параллельно работающих процессов-консьюмеров с общим `group.id`, совместно вычитывающих сообщения из одного топика. Каждая партиция назначается строго одному консьюмеру внутри группы.
- **Backpressure (Обратное давление):** Защитный механизм, при котором принимающая сторона (брокер или консьюмер) ограничивает скорость поступления входящих данных от источника, предотвращая исчерпание оперативной памяти и падение служб.
- **Dead Letter Queue (DLQ):** Очередь или топик для изолированного хранения сообщений, обработка которых завершилась критической ошибкой после исчерпания лимита повторных попыток.
- **Poison Pill (Ядовитое сообщение):** Сообщение, вызывающее необрабатываемое исключение (например, ошибку десериализации или деление на ноль) при каждой попытке обработки, способное заблокировать консьюмер.
- **Prefetch Count (QoS):** Ограничение максимального количества неподтвержденных сообщений, которые брокер может отправить консьюмеру в Push-модели до получения очередного `ack`.
- **Page Cache:** Дисковый кэш ядра Linux в невыделенной оперативной памяти хоста, используемый брокерами логов (Kafka) для мгновенной отдачи горячих данных без накладных расходов на кучу JVM. Подробнее: **[OS тюнинг для Apache Kafka](./kafka_os_tuning.md)**.
- **Zero-Copy (`sendfile(2)`):** Системный вызов Linux, передающий данные напрямую из Page Cache в сетевой сокет через дескрипторы DMA ядра, исключая промежуточное копирование в пространство пользователя.
- **Quorum Queue:** Отказоустойчивая реплицируемая очередь в RabbitMQ, построенная на базе консенсуса Raft, пришедшая на замену устаревшим классическим зеркалированным очередям (Mirrored Queues).
- **Share Group (KIP-932):** Механизм потребления в Kafka с семантикой очередей («Queues for Kafka»), позволяющий параллельным консьюмерам внутри одной группы разбирать отдельные сообщения из одной партиции с индивидуальным подтверждением.
- **Claim Check:** Шаблон проектирования, при котором тяжелые полезные нагрузки сохраняются во внешнем хранилище (например, локальном S3-совместимом MinIO), а через брокер передается только легковесное событие со ссылкой на объект.

## Базовые концепции и архитектура

### Синхронное против Асинхронного взаимодействия

Выбор модели взаимодействия определяет устойчивость системы к пиковым нагрузкам и сетевым сбоям:

1. **Синхронное (Request-Response, RPC / REST):**
   - **Механизм:** Клиент отправляет сетевой запрос и блокирует вызывающий поток в ожидании ответа сервиса.
   - **Применение:** Операции, требующие строго немедленного возврата результата пользователю (авторизация по паролю, синхронная валидация карточки).
   - **Архитектурные риски:** Каскадные отказы (Cascading Failures) — отказ или деградация производительности downstream-сервиса приводит к исчерпанию пула потоков вызывающего сервиса, вызывая отказ всей цепочки вызовов.

2. **Асинхронное (Event-Driven / Message-Driven):**
   - **Механизм:** Продюсер формирует событие, передает его брокеру и продолжает выполнение своей логики, не ожидая завершения обработки получателем.
   - **Применение:** Фоновые вычисления, финансовый клиринг, аудит, интеграция микросервисов, обработка телеметрии и логов.
   - **Преимущества:**
     - **Развязка по времени (Temporal Decoupling):** Отправитель и получатель могут функционировать независимо. Консьюмер может быть отключен для регламентных работ, а продюсер продолжит публиковать данные.
     - **Развязка по пространству (Spatial Decoupling):** Отправителю не требуется знать сетевые адреса, топологию и количество инстансов принимающей стороны.
   - **Подробнее:** [Событийно-ориентированная архитектура (EDA)](../Concepts/event-driven-architecture.md).

```
Синхронная модель (прямая связность, блокировка):
[Продюсер] ──REST Запрос──> [Блокировка потока] ──> [Консьюмер (упал)] ──> [Таймаут/Каскадный сбой]

Асинхронная модель (буферизация через брокер):
[Продюсер] ──Отправка──> [Брокер (Буфер)] ──Ack──> [Продюсер продолжает работу]
                              │
                              ▼ (сообщения сохранены)
                     [Консьюмер восстановился] ──Вычитка──> [Обработка]
```

### Архитектурные парадигмы: Smart Broker против Smart Client

В индустрии систем обмена сообщениями сформировались две фундаментальные модели:

| Параметр | Традиционные очереди (Smart Broker / Dumb Client) | Распределенный лог (Dumb Broker / Smart Client) |
| :--- | :--- | :--- |
| **Примеры** | RabbitMQ (классические и кворумные очереди), ActiveMQ | Apache Kafka, Redpanda |
| **Логика брокера** | Сложная: фильтрация, маршрутизация (Exchange, Routing Keys), трекинг каждого сообщения (`ack/nack`), поддержка очередей приоритетов. | Минимальная: append-only запись бинарных батчей на диск и отдача байтов через `sendfile(2)`. |
| **Логика клиента** | Минимальная: подключился к очереди, получил сообщение, отправил подтверждение. | Сложная: партиционирование по ключу, локальный батчинг, вычисление офсетов, координация ребалансировки consumer-групп. |
| **Жизненный цикл данных** | Сообщение уничтожается сразу после получения `ack` от консьюмера. | Данные хранятся неизменно до истечения срока удержания (`retention.ms` / `retention.bytes`) независимо от чтения. |
| **Повторное чтение** | Невозможно штатно (только через повторную публикацию в очередь). | Поддерживается в любой момент путем сдвига офсета назад (Replay). |
| **Поведение при накоплении** | Очереди рассчитаны на опустошение; рост миллионов сообщений ведет к деградации RAM/диска. | Производительность не зависит от объема накопленных исторических данных на диске. |

Подробное сопоставление см. в **[Сравнение архитектур RabbitMQ и Apache Kafka](./rabbitmq_vs_kafka.md)**.

### Модели передачи данных: Push против Pull

- **Push-модель (RabbitMQ, NATS Core):**
  - Брокер самостоятельно отправляет новые сообщения в открытый TCP-сокет консьюмера сразу по факту их появления.
  - *Преимущество:* Минимальная задержка доставки (субмиллисекунды).
  - *Риск для SRE:* Перегрузка консьюмера при резких всплесках трафика (Thundering Herd). Требует обязательного ограничения входящего потока через `prefetch_count` (QoS).
- **Pull-модель (Apache Kafka):**
  - Консьюмер циклически опрашивает брокер (`poll()`), запрашивая порцию данных.
  - *Преимущество:* Естественное обратное давление — консьюмер запрашивает ровно столько данных, сколько способен обработать в памяти (`max.poll.records`). Идеальная поддержка батчинга сообщений.
  - *Риск для SRE:* При отсутствии данных консьюмер может генерировать холостые запросы (минимизируется параметрами `fetch.min.bytes` и `fetch.max.wait.ms`).

### Топологии обмена сообщениями

- **Точка-точка (Point-to-Point):** Каждое сообщение доставляется строго одному консьюмеру. В RabbitMQ реализуется привязкой консьюмеров к одной очереди; в Kafka — всеми участниками одной Consumer Group.
- **Издатель-подписчик (Publish/Subscribe, Pub/Sub):** Сообщение тиражируется всем независимым потребителям. В RabbitMQ реализуется через Fanout Exchange; в Kafka — чтением одного топика несколькими независимыми Consumer Groups.
- **Конкурирующие потребители (Competing Consumers):** Пул идентичных воркеров разбирает задачи из общего источника. Брокер распределяет нагрузку между ними (по round-robin в очередях RabbitMQ или по партициям в Kafka).
- **Запрос-ответ (Request-Response over MQ):** Асинхронная имитация RPC через брокер. Сообщение продюсера содержит заголовок `reply-to` (имя временной очереди для ответа) и уникальный `correlation-id` для идентификации возвращаемого результата.
- **Fan-out:** Шаблон широковещательной рассылки, при котором сообщение дублируется во все привязанные очереди или подписчики без фильтрации.

## Системный уровень и взаимодействие с ОС (Linux Kernel & Storage)

Эксплуатация брокеров сообщений в on-premise инфраструктуре требует глубокого понимания взаимодействия брокеров с подсистемами ядра Linux.

### Модель ввода-вывода: Append-Only лог против случайного доступа

Традиционные реляционные СУБД и брокеры со сложными индексами используют B-Tree структуры, требующие случайных операций чтения-записи (Random I/O) с постоянной перезаписью страниц на диске.

Архитектура распределенного лога (Apache Kafka) основывается на **последовательной записи в конец файла (Sequential Append-Only I/O)**:
1. Скорость линейной записи на современные NVMe и даже классические HDD приближается к теоретическому пределу физической шины (сотни МБ/с на диск), минимизируя накладные расходы на позиционирование головок и дефрагментацию.
2. Сегмент лога закрывается при достижении размера `segment.bytes` (по умолчанию 1 ГБ) и становится доступным только для чтения, что исключает блокировки файлов между пишущими и читающими потоками.

### Page Cache ядра Linux и системный вызов Zero-Copy

Kafka делегирует управление кэшированием ядру Linux вместо выделения огромных областей памяти JVM Heap:

```
Схема передачи данных консьюмеру через Zero-Copy sendfile(2):

Классический путь (4 копирования, 4 переключения контекста):
[Диск] ──DMA──> [Page Cache] ──CPU──> [JVM Буфер] ──CPU──> [Буфер сокета] ──DMA──> [Сетевая карта]

Zero-Copy через sendfile(2) (0 копирований CPU, 2 переключения контекста):
[Диск] ──DMA──> [Page Cache] ────────────────DMA (дескрипторы)───────────────> [Сетевая карта]
```

- **Преимущества для системного администратора:**
  - JVM Heap брокера ограничивается 6–10 ГБ (только метаданные партиций и сетевые буферы NIO), полностью исключая многосекундные Stop-The-World паузы сборщика мусора (GC).
  - 70–80% RAM сервера отдается под дисковый Page Cache. «Горячие» сообщения читаются напрямую из оперативной памяти без единого физического обращения к диску.
  - При перезапуске службы Kafka Page Cache хоста не сбрасывается, благодаря чему брокер не требует длительного прогрева кэша после регламентного рестарта.

### Персистентность и сброс на диск: `fsync` против фоновой синхронизации

- В **RabbitMQ** сообщение считается сохраненным на диск (`durable`), когда брокер явно инициирует системный вызов `fsync(2)` перед возвратом подтверждения продюсеру. Это гарантирует сохранность данных при внезапном сбое питания одного узла, но накладывает ограничение на дисковый IOPS.
- В **Apache Kafka** по умолчанию параметры `flush.messages` и `flush.ms` отключены (`Long.MAX_VALUE`). Брокер доверяет запись системному вызову `write(2)` в Page Cache ядра Linux, а физический сброс грязных страниц (dirty pages) выполняет фоновый поток ядра Linux (`flush` / `kworker`). Отказоустойчивость достигается не за счет локального `fsync`, а за счет репликации в память и Page Cache нескольких независимых физических серверов в составе ISR!

## Кластеризация, консенсус и защита от Split-Brain

Обеспечение высокой доступности (HA) в распределенных брокерах опирается на алгоритмы кворумного консенсуса, гарантирующие согласованность состояния при падении узлов и сетевых разделениях (Network Partitions).

### Кворумные алгоритмы (KRaft и Quorum Queues)

- **Apache Kafka (KRaft):** Начиная с версии 3.3 (и безальтернативно в 4.0+) кластер работает под управлением протокола KRaft (Kafka Raft Metadata Mode) без внешнего ZooKeeper. Метаданные кластера хранятся в изолированном топике `@metadata`, управляемом пулом выделенных контроллеров.
- **RabbitMQ (Quorum Queues):** Репликация очередей построена на базе встроенной реализации Raft. Каждая кворумная очередь представляет собой отдельную группу консенсуса с выделенным Raft-лидером и последователями (Followers).

### Формула кворума и предотвращение Split-Brain

Кворум определяется как строгое большинство активных узлов кластера:
$$\text{Quorum} = \left\lfloor \frac{N}{2} \right\rfloor + 1$$
где $N$ — общее число сконфигурированных узлов-участников консенсуса.

| Размер кластера ($N$) | Необходимый кворум | Допустимое число отказавших узлов |
| :--- | :--- | :--- |
| 1 | 1 | 0 |
| 3 | 2 | 1 |
| 5 | 3 | 2 |
| 7 | 4 | 3 |

**Сценарий сетевой изоляции (Network Partition / Split-Brain):**
Если сетевой сбой разделяет кластер из 5 узлов на два изолированных сегмента: 3 узла в Сегменте А и 2 узла в Сегменте Б:
- Сегмент А ($3 \ge 3$) сохраняет кворум, выбирает лидера и продолжает обрабатывать операции записи.
- Сегмент Б ($2 < 3$) теряет кворум, переходит в режим ожидания или Read-Only и отвергает любые попытки записи.
- **Итог:** Рассогласование данных (Split-Brain) физически невозможно, так как большинство голосов может существовать только в одной половине сети.

### Выборы лидера: Clean против Unclean Leader Election

При падении лидера партиции в Kafka:
1. **Clean Leader Election:** Новым лидером назначается только узел из текущего списка `ISR`. Данные гарантированно не теряются.
2. **Unclean Leader Election (`unclean.leader.election.enable`):** Если все реплики из ISR вышли из строя, флаг разрешает назначить лидером отставшую реплику (Out-of-sync Replica).
   - *Последствия:* Восстановление доступности ценой безвозвратной потери всех сообщений, которые старый лидер успел зафиксировать, но не передал отставшей реплике.
   - *Стандарт SRE:* Для production-окружений флаг `unclean.leader.election.enable` должен быть строго равен `false`.

## Семантика доставки (Delivery Guarantees)

Гарантии доставки определяют обязательства брокера и клиентов по сохранности и уникальности передачи сообщений. Подробный разбор архитектурных аспектов см. в **[Гарантии доставки](./delivery_guarantees.md)**.

| Гарантия | Риск потери | Риск дубликатов | Нагрузка / Latency | Конфигурация продюсера |
| :--- | :--- | :--- | :--- | :--- |
| **At-most-once** | Да | Нет | Минимальная | `acks=0`, автокоммит офсетов до обработки. |
| **At-least-once** | Нет | Да | Умеренная | `acks=all`, `retries > 0`, ручной коммит после сохранения данных. |
| **Exactly-once** | Нет | Нет | Высокая | Идемпотентный продюсер + двухфазные транзакции Kafka (`transactional.id`). |

> **Критическое архитектурное ограничение Exactly-Once Processing (EOS):**
> Семантика «ровно один раз» гарантируется **исключительно внутри замкнутой экосистемы Kafka** (транзакционная передача между топиками одного кластера через `sendOffsetsToTransaction()`).
> Если консьюмер сохраняет данные во внешнюю базу данных (PostgreSQL, ClickHouse) или инициирует внешний сетевой вызов (REST API), семантика неизбежно откатывается к **At-least-once**. Гарантия полного отсутствия дубликатов в таких сценариях достигается **только идемпотентностью на стороне целевой системы**!

## Жизненный цикл сообщения (Flow)

```
1. Сериализация ──> 2. Партиционирование ──> 3. Батчинг (linger.ms) ──> 4. Отправка в TCP
   (Продюсер)          (Ключ/Round-Robin)       (Буфер продюсера)           (Socket Send)
                                                                                  │
┌────────────────────────────── Брокер Kafka ─────────────────────────────────────┘
│ 5. Запись в Page Cache лидера
│ 6. Репликация на Follower узлы (ISR)
│ 7. Продвижение High Watermark (HW) ──> 8. Возврат Ack продюсеру
└─────────────────────────────────────────────────┬───────────────────────────────
                                                  ▼
9. Fetch запрос консьюмера <── 10. Десериализация <── 11. Бизнес-логика <── 12. Commit Offset
```

1. **Сериализация:** Преобразование объекта данных в байтовый массив (Avro, Protobuf, JSON).
2. **Маршрутизация:** Вычисление целевой партиции на клиенте (`murmur2(key) % numPartitions` в Kafka) или обменника (Exchange в RabbitMQ).
3. **Батчинг:** Накопление сообщений в буфере продюсера до достижения размера пакета (`batch.size`) или таймаута (`linger.ms`).
4. **Сетевая передача:** Пересылка сжатого батча (LZ4 / ZSTD) через TCP-сокет брокеру.
5. **Фиксация в лидере:** Брокер записывает батч в Page Cache сегмента лога.
6. **Репликация:** Реплики-последователи (Followers) запрашивают данные у лидера и подтверждают получение.
7. **Коммит брокера:** Лидер сдвигает High Watermark (HW) после подтверждения от `min.insync.replicas` узлов.
8. **Подтверждение продюсеру:** Лидер возвращает ответ `ProduceResponse` продюсеру.
9. **Выборка консьюмером:** Консьюмер запрашивает данные (`poll()`), вычитывая записи до уровня HW.
10. **Обработка и коммит:** Консьюмер выполняет бизнес-логику и сохраняет смещение (`CommitOffset`).

## Механизмы управления потоком и Backpressure

Backpressure предотвращает отказ узлов при превышении скорости поступления сообщений над скоростью их обработки:

- **На стороне продюсера (Producer Backpressure):**
  - Буфер памяти продюсера (`buffer.memory`, по умолчанию 32 МБ).
  - При насыщении буфера вызов `send()` блокируется на время до `max.block.ms` (по умолчанию 60 сек). При превышении таймаута выбрасывается `TimeoutException` / `BufferExhaustedException`.
  - Ограничение запросов «в полете»: `max.in.flight.requests.per.connection` (рекомендуется $\le 5$ для сохранения порядка при включенной идемпотентности).
- **На стороне брокера (Broker Flow Control):**
  - В **RabbitMQ** при исчерпании доступной оперативной памяти выше порога `vm_memory_high_watermark` (по умолчанию 40% RAM) или свободного места на диске (`disk_free_limit`) брокер принудительно блокирует TCP-сокеты продюсеров (Connection Alarm), останавливая прием данных.
  - В **Kafka** используются квоты (Quotas): ограничение пропускной способности сети (`bytes/sec`) для клиента. При превышении брокер искусственно задерживает ответ клиенту (Client Throttling), не закрывая соединение.
- **На стороне консьюмера (Consumer Backpressure):**
  - В **RabbitMQ**: регулируется через `channel.basic_qos(prefetch_count=N)`. Брокер не отправляет новые сообщения, пока количество неподтвержденных сообщений консьюмера равно $N$.
  - В **Kafka**: консьюмер самостоятельно управляет объемом данных, считываемых за один вызов `poll()` параметром `max.poll.records`. Консьюмер может временно приостановить чтение отдельных партиций с помощью метода `pause()` и возобновить через `resume()`.

## Сериализация данных (SerDes) и Schema Registry

Формат сериализации определяет размер сетевых пакетов, нагрузку на CPU при парсинге и правила эволюции структур данных:

| Формат | Тип | Сжатие / Размер | Производительность CPU | Эволюция схемы | Необходимость внешнего сервиса |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **JSON** | Текстовый | Низкое (передает имена полей) | Низкая (парсинг строк) | Ручная, слабая типизация | Нет |
| **Protobuf** | Бинарный | Высокое (числовые теги) | Высокая | Строгая (forward/backward) | Опционально (генерация кода) |
| **Avro** | Бинарный | Максимальное (без метаданных) | Высокая | Автоматическая (через Registry) | Да, обязателен Schema Registry |

### Роль Schema Registry

Schema Registry — выделенный централизованный сервис для валидации и версионирования схем данных:
1. Продюсер регистрирует схему в реестре и получает ее уникальный 4-байтный идентификатор (`Schema ID`).
2. Сообщение передается в брокер в формате: `Magic Byte (0x00)` + `Schema ID (4 байта)` + `Сериализованные бинарные данные payload`.
3. Консьюмер извлекает `Schema ID` из первых 5 байт сообщения, запрашивает соответствующую схему из кэша или реестра и корректно десериализует полезную нагрузку.
4. **Преимущество:** Гарантируется обратная (Backward) и прямая (Forward) совместимость. Запрещается публикация сообщений, нарушающих контракт схемы.
5. Подробнее: **[Schema Registry в Apache Kafka](./kafka_schema_registry.md)**.

## Безопасность и Multi-tenancy

Защита инфраструктуры обмена сообщениями в корпоративном контуре строится на трех уровнях:

1. **Шифрование транспортного уровня (TLS / mTLS):**
   - Защита клиентского трафика (`client-to-broker`) и межузлового трафика кластера (`inter-broker`).
   - Использование взаимной TLS-аутентификации (mTLS), где клиент подтверждает подлинность своим клиентским сертификатом, выданным корпоративным удостоверяющим центром (PKI).
2. **Аутентификация (SASL):**
   - `SCRAM-SHA-256` / `SCRAM-SHA-512`: Хранение криптографических хэшей учетных записей в метаданных брокера. Рекомендуемый стандарт для закрытых инфраструктур без доменной интеграции.
   - `GSSAPI (Kerberos)`: Корпоративный стандарт для интеграции с Active Directory / FreeIPA.
   - `PLAIN`: Передача логина/пароля в открытом виде. Допустима **исключительно внутри шифрованного канала TLS**.
3. **Авторизация (ACLs):**
   - Разграничение прав доступа на уровне учетных записей (Principal) к ресурсам: Топикам, Consumer Groups, Транзакционным ID и операциям с кластером (`Read`, `Write`, `Describe`, `Alter`).
4. **Многопользовательская изоляция (Multi-tenancy):**
   - **Квоты пропускной способности (Client Quotas):** Ограничение полосы пропускания (`producer_byte_rate`, `consumer_byte_rate`) на пользователя (`user`) или `client-id`, предотвращающее исчерпание полосы пропускания одним неоптимальным приложением (Noisy Neighbor problem).
   - **Квоты CPU брокера (`request_percentage`):** Лимит процента времени пула обработчиков запросов (`KafkaRequestHandlerPool`), выделяемого конкретному клиенту.

## Паттерны устойчивости и обработки ошибок

### Retry с экспоненциальным откатом и случайным джиттером

При возникновении временных сетевых сбоев повторные запросы не должны производиться непрерывно, иначе это вызовет лавинообразную перегрузку брокера (Retry Storm):

```python
import time
import random
import logging

logger = logging.getLogger(__name__)

def produce_with_exponential_backoff(producer, topic, key, value, max_retries=5, base_delay=0.5, max_delay=10.0):
    """
    Отправка сообщения с экспоненциальным откатом и полным джиттером (Full Jitter).
    Формула задержки: sleep = uniform(0, min(max_delay, base_delay * 2^attempt))
    """
    for attempt in range(max_retries):
        try:
            future = producer.send(topic, key=key, value=value)
            record_metadata = future.get(timeout=10)
            logger.info("Сообщение успешно записано: partition=%d, offset=%d", 
                        record_metadata.partition, record_metadata.offset)
            return True
        except Exception as exc:
            if attempt == max_retries - 1:
                logger.error("Превышен лимит попыток отправки: %s", exc)
                raise
            
            calculated_delay = min(max_delay, base_delay * (2 ** attempt))
            jittered_delay = random.uniform(0, calculated_delay)
            logger.warning("Попытка %d не удалась (%s). Повтор через %.2f сек.", 
                           attempt + 1, exc, jittered_delay)
            time.sleep(jittered_delay)
    return False
```

### Circuit Breaker (Прерыватель цепи)

Паттерн предотвращает каскадные сбои при длительной недоступности брокера:
- **Состояние Closed (Закрыт):** Запросы отправляются штатно. Ошибки подсчитываются скользящим окном.
- **Состояние Open (Разомкнут):** При превышении порога ошибок (например, >50% отказов за 10 сек) отправка блокируется мгновенно. Приложение не тратит потоки и сокеты на попытки соединения, возвращая локальный fallback (например, сохранение во временный аварийный буфер на локальном SSD).
- **Состояние Half-Open (Полуразомкнут):** По истечении таймаута покоя отправляется одиночный пробный запрос. При успехе цепь замыкается; при ошибке — снова размыкается.

### Паттерн: Transactional Outbox

Решает проблему атомарного изменения состояния реляционной БД и публикации события в брокер без использования медленных двухфазных распределенных коммитов (2PC/XA):

```
Транзакция БД (Атомарно):
┌────────────────────────────────────────────────────────┐
│ 1. UPDATE orders SET status = 'PAID' WHERE id = 100;   │
│ 2. INSERT INTO outbox (aggregate_id, event, payload)   │
│    VALUES ('100', 'OrderPaid', '{"sum": 5000}');       │
└────────────────────────────────────────────────────────┘
                           │
                           ▼
          [Фоновый процесс Outbox Relay / Debezium CDC]
                           │
                           ▼
              [Публикация в брокер сообщений]
                           │
                           ▼
     [Удаление или пометка записи в таблице outbox]
```

- **Результат:** Гарантируется доставка события в брокер с семантикой **At-least-once**.
- Подробнее: **[Распределенные транзакции](../Databases/Concepts/distributed_transactions.md)**.

### Паттерн: Идемпотентный потребитель (Idempotent Consumer)

Обязательный паттерн для устранения дубликатов на стороне консьюмера при семантике At-least-once:

```python
import psycopg2

def process_incoming_order(cursor, message_id, payload):
    """
    Атомарная проверка уникальности сообщения и выполнение бизнес-логики в единой транзакции БД.
    """
    # 1. Попытка зафиксировать идентификатор сообщения в таблице дедупликации
    cursor.execute(
        """
        INSERT INTO processed_messages (message_id, processed_at)
        VALUES (%s, NOW())
        ON CONFLICT (message_id) DO NOTHING
        RETURNING message_id;
        """,
        (message_id,)
    )
    result = cursor.fetchone()
    
    if result is None:
        # Идентификатор уже присутствовал в БД — сообщение дубликат
        print(f"Дубликат обнаружен: message_id={message_id}. Обработка пропущена.")
        return False

    # 2. Выполнение целевой бизнес-логики
    cursor.execute(
        """
        UPDATE accounts 
        SET balance = balance - %s 
        WHERE account_id = %s;
        """,
        (payload['amount'], payload['account_id'])
    )
    return True
```

Подробнее: **[Идемпотентность](../Concepts/idempotency.md)**.

### Dead Letter Queue (DLQ) и регламент безопасного повторного воспроизведения (Replay)

При возникновении необрабатываемых ошибок (Poison Pill, повреждение формата полезной нагрузки):
1. Консьюмер перехватывает исключение десериализации/валидации.
2. Сообщение обогащается служебными заголовками: `x-original-topic`, `x-exception-message`, `x-failure-timestamp`, `x-retry-count`.
3. Сообщение отправляется в DLQ-топик (`orders.dlq` в Kafka или Dead Letter Exchange в RabbitMQ).
4. Основной консьюмер фиксирует смещение (`ack`) исходной партиции, чтобы разблокировать очередь и продолжить обработку здорового потока данных.
5. **Регламент DLQ Replay:**
   - После исправления бага в приложении или исправления данных запускается выделенная утилита-реплейер.
   - Реплейер читает данные из DLQ с ограничением скорости (Rate Limiting) и публикует их обратно в основной топик или направляет сразу в сервис обработки, чтобы не вызвать перегрузку основной базы данных.

## Мониторинг и наблюдаемость (Observability & SRE Metrics)

### Ключевые Golden Signals систем обмена сообщениями

1. **Consumer Lag (Отставание потребителя):** Абсолютная разница между последним смещением в партиции (`LOG-END-OFFSET`) и последним подтвержденным смещением группы (`CURRENT-OFFSET`). Самый критичный индикатор проблем деградации обработки.
2. **UnderReplicatedPartitions (Недореплицированные партиции):** Количество партиций, число синхронных реплик которых меньше заданного коэффициента репликации (`ReplicationFactor`). В нормальном состоянии должно быть строго равно `0`.
3. **RequestHandlerAvgIdlePercent:** Процент времени простоя пула обработчиков запросов брокера. Значение ниже `0.2` (20%) указывает на острую нехватку CPU или блокировку дискового ввода-вывода брокера.
4. **IsrShrinksPerSec / IsrExpandsPerSec:** Частота выпадения и возврата реплик в список ISR. Ненулевые постоянные значения сигнализируют о сетевой нестабильности, GC-паузах или задержках записи на диск.

### Примеры PromQL алертов для SRE

```yaml
groups:
  - name: message_queue_alerts
    rules:
      # Критическое отставание консьюмер-группы
      - alert: KafkaConsumerGroupLagCritical
        expr: sum by (consumergroup, topic) (kafka_consumergroup_lag) > 10000
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: "Критический лаг группы {{ $labels.consumergroup }} в топике {{ $labels.topic }}"
          description: "Текущее отставание превышает 10 000 сообщений более 5 минут."

      # Деградация репликации кластера
      - alert: KafkaUnderReplicatedPartitionsDetected
        expr: sum(kafka_server_replicamanager_underreplicatedpartitions) > 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "Обнаружены недореплицированные партиции в кластере Kafka"
          description: "UnderReplicatedPartitions > 0 в течение 2 минут. Риск потери отказоустойчивости."

      # RabbitMQ: Заполнение очередей сообщениями без консьюмеров
      - alert: RabbitMQQueueMessagesStuck
        expr: rabbitmq_queue_messages_ready > 5000 and rabbitmq_queue_consumers == 0
        for: 3m
        labels:
          severity: warning
        annotations:
          summary: "Очередь {{ $labels.queue }} накапливает сообщения при отсутствии консьюмеров"
          description: "В очереди {{ $labels.queue }} находится более 5000 сообщений, но активных потребителей 0."
```

### Матрица типовых эксплуатационных инцидентов

| Симптом инцидента | Вероятная причина | Метод диагностики | План устранения |
| :--- | :--- | :--- | :--- |
| **Лавинообразный рост Consumer Lag** | 1. Зависание потоков консьюмера на внешних I/O вызовах.<br>2. Резкий рост объема входящих сообщений.<br>3. Частые ребалансировки. | 1. Снять Thread Dump (`jstack <pid>`).<br>2. Проверить `kafka-consumer-groups.sh`.<br>3. Проверить логи на `CommitFailedException`. | 1. Увеличить число консьюмеров до числа партиций.<br>2. | **Диск заполнен (`log.dirs` full на брокере)** | Сегменты лога не удаляются вовремя; слишком высокое значение `log.retention.hours`. | Выполнить `df -h` в точках монтирования брокера. | 1. Добавить диски в JBOD конфигурацию. |

## Лучшие практики (Best Practices)

### Эксплуатационные стандарты DevOps и SRE

1. **Корректное завершение работы консьюмеров (Graceful Shutdown):**
   - Приложение-консьюмер обязано перехватывать системные сигналы `SIGTERM` и `SIGINT`.
   - При получении сигнала инициируется выход из цикла `poll()` (вызов `consumer.wakeup()`), завершается обработка текущего пакета сообщений, выполняется синхронный коммит офсетов (`commitSync()`) и закрытие сокета (`consumer.close()`).
   - Это предотвращает задержки ребалансировки и избавляет группу от ожидания истечения `session.timeout.ms`.

2. **Низкоуровневая настройка ядра Linux хостов:**
   - **`vm.swappiness = 1`:** Минимизация сброса анонимной памяти в раздел подкачки swap при сохранении активности файлового Page Cache.
   - **Отключение Transparent Huge Pages (THP):** Динамическое объединение страниц ядром вызывает микропаузы (latency spikes) и дефрагментацию памяти:
     ```bash
     echo never > /sys/kernel/mm/transparent_hugepage/enabled
     echo never > /sys/kernel/mm/transparent_hugepage/defrag
     ```
   - **Тюнинг фонового сброса dirty pages:**
     ```ini
     # /etc/sysctl.d/99-kafka.conf
     vm.dirty_background_ratio = 5
     vm.dirty_ratio = 10
     vm.max_map_count = 1048576
     ```
     Частый фоновый сброс небольших порций данных ядром предотвращает внезапные штормы дисковой активности (Flush Storms), блокирующие операции чтения брокера.

3. **Формула расчета емкости и сайзинга (Capacity Planning):**
   - **Сетевая пропускная способность брокера (Bandwidth):**
     $$\text{Inbound Bandwidth} = \text{Write Rate (МБ/с)} \times (1 + \text{RF} - 1) = \text{Write Rate} \times \text{RF}$$
     $$\text{Outbound Bandwidth} = \text{Write Rate} \times \text{Количество Consumer Groups} + \text{Репликационный трафик}$$
   - **Дисковое пространство хранения (Disk Storage):**
     $$\text{Storage} = \text{Write Rate (МБ/с)} \times 86400 \times \text{Retention (дней)} \times \text{RF} \times 1.25 \text{ (запас)}$$
   - **Оперативная память для Page Cache:**
     Для гарантированного отсутствия чтений с диска размер Page Cache на кластере должен вмещать объем сообщений, публикуемых за пиковое окно отставания консьюмеров (обычно 2–4 часа активной записи).

4. **Регламент безаварийного обслуживания узлов кластера (Rolling Maintenance):**
   - Перед остановкой брокера Kafka перевести лидерство контроллера на другой узел.
   - Использовать `controlled.shutdown.enable=true`, чтобы брокер перед остановкой плавно передал лидерство партиций другим узлам из ISR без просадки клиентского трафика.
   - Перезапускать брокеры строго последовательно: перед переходом к следующему узлу дождаться возвращения `UnderReplicatedPartitions` к значению `0`.

### Антипаттерны эксплуатации

- **Очередь как постоянная база данных:** Использование классических очередей RabbitMQ для многодневного хранения миллионов непрочитанных сообщений приводит к деградации структур памяти Erlang и падению производительности.
- **Публикация гигантских сообщений в теле payload:** Отправка файлов > 1–2 МБ напрямую в брокер забивает сетевые буферы и кэш страниц. Для тяжелых файлов необходимо применять паттерн **Claim Check** (хранение файла в локальном S3 MinIO, передача хэша/ссылки в очереди).
- **Игнорирование изоляции Consumer Groups:** Подключение разнородных бизнес-модулей под одним `group.id` приводит к непредсказуемой конкурентной обработке сообщений разными сервисами.
- **Слепое автосоздание топиков:** Включение `auto.create.topics.enable=true` приводит к хаотичному созданию топиков с 1 партицией и RF=1 при любой опечатке в коде продюсера.
