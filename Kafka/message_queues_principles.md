# Принципы работы очередей сообщений

## Определения

- **Очереди сообщений**: Механизм, обеспечивающий асинхронный обмен данными между независимыми компонентами системы (сервисами).
- **Продьюсер (Producer)**: Компонент, который формирует и отправляет сообщения.
- **Брокер (Broker)**: Центральный узел, который принимает, хранит, маршрутизирует и доставляет сообщения.
- **Консьюмер (Consumer)**: Компонент, который получает (читает) и обрабатывает сообщения.
- **Сообщение**: Атомарная единица данных, состоящая из полезной нагрузки (payload) и метаданных (например, ключ, заголовки, таймштамп).
- **Очередь/Тема (Queue/Topic)**: Логическое именованное место, где брокер накапливает сообщения для консьюмеров.
  - В **RabbitMQ** основной сущностью является очередь, а маршрутизация происходит через обменники (exchanges).
  - В **Kafka** — это [лог-тема (topic)](./kafka_overview.md), разделенная на партиции.
- **Подтверждение доставки (Acknowledgement / ack)**: Сигнал от консьюмера к брокеру о том, что сообщение было успешно получено и обработано.

## Основные концепции

### Синхронное vs Асинхронное взаимодействие

Выбор между брокером сообщений и прямым взаимодействием (REST, gRPC) зависит от характера задачи:

- **Синхронное (Request-Response):** Пользователь нажимает кнопку и ожидает немедленного результата (например, добавление товара в корзину). Здесь лучше подходят протоколы вроде HTTP/REST или gRPC.
- **Асинхронное (Fire-and-forget):** Сервис уведомляет о событии и продолжает работу, не дожидаясь ответа (например, отправка SMS или уведомления). Это идеальный сценарий для брокеров сообщений.

В реальных системах обычно сосуществуют оба подхода: синхронные вызовы для внешнего API и асинхронные — для внутренней фоновой обработки.

### Преимущества и недостатки брокеров

**Плюсы:**
- **Service Discovery:** Сервисам не нужно знать адреса (IP, порт) друг друга, достаточно знать адрес брокера.
- **Высокая доступность:** Брокер сохраняет сообщения, если получатель временно недоступен.
- **Масштабирование:** Легко распределять нагрузку между несколькими экземплярами одного сервиса.
- **Устойчивость к каскадным сбоям:** Система продолжает накапливать сообщения, даже если часть сервисов упала.

**Минусы:**
- **Задержка (Latency):** Передача через посредника всегда медленнее прямого вызова.
- **Сложность:** Появляется дополнительный критический узел, требующий мониторинга и администрирования.
- **Единая точка отказа:** Если брокер (не в кластере) падает, останавливается всё асинхронное взаимодействие.

### Поток обработки сообщения

Очереди сообщений развязывают скорость и режим работы сервисов, повышая общую устойчивость и масштабируемость системы.

Типичный жизненный цикл сообщения выглядит так:

1. **Продьюсер** сериализует данные и публикует их в определенную очередь или тему на брокере.
2. **Брокер** принимает сообщение, маршрутизирует его в соответствии с правилами и сохраняет (например, на диске).
3. **Консьюмер** подключается к брокеру, получает сообщение, выполняет его обработку.
4. После успешной обработки **консьюмер** отправляет брокеру подтверждение.
5. **Брокер**, получив подтверждение, помечает сообщение как потреблённое или удаляет его.

### Гарантии доставки

Существуют три основные семантики доставки сообщений, каждая со своими компромиссами между надежностью и производительностью. Детальное описание каждой гарантии, а также примеры их реализации в Kafka и RabbitMQ, находятся в специальном документе.

**[Гарантии доставки в очередях сообщений](./delivery_guarantees.md)** — подробное описание с примерами кода.

## Практические сценарии

### Обязанности и настройки компонентов

#### Продьюсер

- **Надёжность публикации**: Использование подтверждений от брокера (`publisher confirms` в RabbitMQ, `acks=all` в Kafka), настройка повторных попыток (retries) и стратегий отката (backing-off).
- **Производительность**: Применение батчинга (группировки сообщений), компрессии (сжатия) и асинхронной отправки.
- **Маршрутизация**: Выбор правильного ключа для партиционирования (в Kafka) или ключа маршрутизации (в RabbitMQ), использование заголовков для более сложных политик доставки.

#### Брокер

- **Долговечность (Durability)**: Настройка записи на диск (персистентность), репликации данных между узлами и кворума для подтверждения записи.
- **Порядок сообщений**: В большинстве систем порядок гарантируется только в рамках одной очереди или партиции. Глобальный порядок для всего потока, как правило, не обеспечивается.
- **Контроль нагрузки**: Использование квот, лимитов на размер очередей, `TTL (Time-To-Live)` для сообщений и специальных очередей для "ядовитых" сообщений (`DLQ (Dead-Letter Queue)`).
- **Масштабирование**: Шардирование очередей, [партиционирование](./partitioning_and_balancing.md) и балансировка нагрузки на группы потребителей.

#### Консьюмер

- **Модель получения сообщений**: Разные брокеры используют разные подходы к доставке сообщений, что влияет на архитектуру потребителей.
  - **Push**: Брокер сам "проталкивает" сообщения консьюмеру (типично для RabbitMQ).
  - **Pull**: Консьюмер сам запрашивает (читает) сообщения у брокера (типично для Kafka).
  - **Подробнее: [Сравнение RabbitMQ и Kafka: Push vs Pull](./rabbitmq_vs_kafka.md)**
- **Управление скоростью**: Настройка `prefetch` (ограничение количества неподтвержденных сообщений), реализация `backpressure` (обратное давление), запуск нескольких экземпляров консьюмеров для конкурентной обработки.
- **Идемпотентность**: Ключевое требование для систем с гарантией `at-least-once`. Обработчик должен быть устойчив к повторной обработке одного и того же сообщения без побочных эффектов.
- **Управление состоянием**: Ручное или автоматическое подтверждение сообщений, управление смещениями (offsets) в Kafka.

### Пример идемпотентной обработки

```python
# Псевдокод: ключ идемпотентности в заголовке/ключе сообщения
if not cache.exists(msg.id):
    result = handle(msg.payload)
    cache.put(msg.id, "done")
    persist(result)
# Повторная обработка этого сообщения не нарушит целостность данных
```

### Подбор параметров

Выбор конкретных настроек зависит от профиля нагрузки:

- Для систем, где важна **низкая латентность**, используются малые размеры батчей и ограничивается `prefetch`.
- Для обработки **пиковых нагрузок** применяется агрессивное батчирование и сжатие данных.
- **Гарантии доставки** усиливаются за счет дисковой персистентности, репликации и идемпотентных обработчиков на стороне консьюмеров.

### Форматы сериализации сообщений

Брокер не вникает в содержимое сообщения — тело — это набор байт. Выбор формата сериализации влияет на производительность, совместимость и удобство отладки.

| Формат | Тип | Особенности | Schema Registry |
|:-------|:----|:------------|:----------------|
| **JSON** | Текстовый | Прост, читаем, но избыточен (названия полей передаются в каждом сообщении). | Не требуется |
| **Protobuf / Thrift** | Бинарный | Вместо названий полей используются числовые идентификаторы (tags/IDs), что экономит место. Расширяем. | Рекомендуется |
| **Avro** | Бинарный | Не передаёт в данных даже идентификаторы полей. Только значения. | **Обязателен** |

**Рекомендация:** начинать с JSON — прост, читаем, поддерживается всеми языками. Переходить на бинарные форматы (Protobuf, Avro) только при объективной нехватке производительности или размера сообщения.

#### Бинарные форматы и Schema Registry

Бинарные форматы (Protobuf, Avro, Thrift) используют **IDL (Interface Definition Language)** для описания структуры данных. Эти файлы компилируются в классы для конкретного языка программирования.

- **Protobuf/Thrift:** В бинарный поток пишутся только значения и их ID. Это позволяет добавлять новые поля, не ломая старых клиентов (backward/forward compatibility).
- **Avro:** Идет ещё дальше — в поток пишутся только данные. Чтобы их прочитать, консьюмеру **необходимо** знать точно ту версию схемы, которую использовал отправитель.
- **Schema Registry:** Специальный сервис для хранения всех версий схем. Отправитель регистрирует схему, а получатель запрашивает её по идентификатору, переданному в заголовке или начале сообщения. Это критично для Avro, но полезно и для других форматов для централизованного управления контрактами.

### Термины и понятия

| Термин | Описание |
| :--- | :--- |
| **Backpressure** | Механизм обратного давления для контроля скорости обработки |
| **Prefetch** | Ограничение количества неподтверждённых сообщений у консьюмера |
| **Dead-Letter Queue (DLQ)** | Специальная очередь для сообщений, которые не удалось обработать |

| **Идемпотентность** | Свойство обработки: повторная обработка не меняет результат |
