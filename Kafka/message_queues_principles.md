# Принципы работы систем обмена сообщениями

Системы обмена сообщениями (Message Queues, Message Brokers) представляют собой специализированное промежуточное программное обеспечение (Middleware), предназначенное для реализации асинхронного взаимодействия между компонентами распределенных систем. Основная задача таких систем — обеспечить надежную передачу данных (сообщений) от отправителя к получателю, минимизируя их прямую связность (decoupling).

---

## Определения

- **Очереди сообщений (Message Queues):** Механизм, обеспечивающий асинхронный обмен данными, где сообщения хранятся до тех пор, пока не будут обработаны.
- **Брокер (Broker):** Центральный узел (сервер или кластер), ответственный за прием, временное хранение, маршрутизацию и доставку сообщений.
- **Продюсер (Producer / Publisher):** Компонент системы, инициирующий создание и отправку сообщения в брокер.
- **Консьюмер (Consumer / Subscriber):** Компонент, подписанный на получение данных из брокера для их последующей обработки.
- **Сообщение (Message):** Атомарная единица передаваемой информации. Состоит из полезной нагрузки (Payload — тело данных) и метаданных (Headers — заголовки, Key — ключ, Timestamp — временная метка).
- **Очередь (Queue):** В контексте RabbitMQ — именованный канал, работающий по принципу FIFO, где сообщения ожидают потребления.
- **Топик / Тема (Topic):** В контексте Kafka — [неизменяемый журнал (лог)](./kafka_overview.md), разделенный на партиции, предназначенный для хранения потока событий.
- **Подтверждение (Acknowledgement / Ack):** Сигнал от консьюмера брокеру о том, что сообщение успешно получено и обработано. На основе этого сигнала брокер может удалить сообщение или обновить офсет.
- **Смещение (Offset):** Уникальный последовательный идентификатор записи в пределах партиции. Консьюмеры используют офсет для отслеживания своей позиции чтения.
- **Партиция (Partition):** Минимальная единица параллелизма и хранения. В Kafka — упорядоченный неизменяемый журнал сообщений.
- **ISR (In-Sync Replicas):** Список реплик, полностью синхронизированных с лидером партиции. Подробнее: **[ISR и репликация](./kafka_isr_replication.md)**.
- **High Watermark (HW):** Офсет последнего сообщения, успешно реплицированного на все ISR. Консьюмеры читают только до HW.
- **Consumer Group:** Группа консьюмеров, совместно читающих данные из топиков. Kafka распределяет партиции между участниками.
- **Backpressure:** Механизм, при котором консьюмер ограничивает скорость продюсера, предотвращая перегрузку.
- **Dead Letter Queue (DLQ):** Очередь для сообщений, которые не удалось обработать после N попыток.
- **Schema Registry:** Централизованный сервис для хранения версий схем данных (Avro, Protobuf, JSON Schema).
- **Poison Pill:** Сообщение, которое невозможно обработать и которое приводит к падению консьюмера.

## Основные концепции

### Синхронное против Асинхронного взаимодействия

Выбор модели взаимодействия критически влияет на архитектуру системы:

1. **Синхронное (Request-Response):**
   - **Механизм:** Клиент отправляет запрос и блокируется в ожидании ответа (REST, gRPC).
   - **Применение:** Операции, требующие немедленного результата (например, проверка остатка на счете при совершении покупки).
   - **Риски:** Каскадные отказы — если целевой сервис недоступен, вызывающий сервис также может выйти из строя из-за накопления ожидающих потоков.

2. **Асинхронное (Event-Driven):**
   - **Механизм:** Продюсер отправляет сообщение брокеру и немедленно переходит к следующей задаче (Fire-and-forget).
   - **Применение:** Длительные фоновые задачи (генерация отчетов, отправка Email), уведомления, интеграция независимых систем.
   - **Преимущество:** Развязка по времени (Temporal Decoupling) — отправитель и получатель могут работать в разные моменты времени.
   - **Подробнее:** [Событийно-ориентированная архитектура (EDA)](../Concepts/event-driven-architecture.md).

В современных архитектурах эти подходы комбинируются: внешнее API работает синхронно, а внутренняя бизнес-логика и побочные эффекты (side effects) обрабатываются через очереди.

### Архитектурные модели: Push vs Pull

Разные брокеры реализуют разные модели доставки сообщений консьюмеру:

- **Push (RabbitMQ, NATS):** Брокер проталкивает сообщения консьюмеру по мере их поступления. Преимущество — низкая задержка. Риск — консьюмер может быть перегружен (backpressure решается на стороне брокера через prefetch/PFC).
- **Pull (Kafka):** Консьюмер сам запрашивает данные (polling). Преимущество — консьюмер контролирует скорость обработки и размер батча. Риск — при низкой нагрузке возможны лишние запросы (решается sticky-партиционером и linger.ms).

**Почему Kafka использует Pull:** модель Pull естественным образом поддерживает батчинг, позволяет консьюмеру обрабатывать данные со своей скоростью и восстанавливаться после сбоя, повторно читая с последнего закоммиченного офсета.

### Топологии обмена сообщениями

- **Точка-точка (Point-to-Point):** Одно сообщение доставляется строго одному консьюмеру (модель очередей). Используется для распределения задач.
- **Издатель-подписчик (Pub/Sub):** Одно сообщение транслируется всем заинтересованным подписчикам (модель топиков). Используется для уведомления систем об изменениях состояния.
- **Конкурирующие потребители (Competing Consumers):** Несколько экземпляров одного сервиса читают из одной очереди для параллельной обработки. Брокер балансирует нагрузку между ними.
- **Запрос-ответ через MQ (Request-Response over Messaging):** Реализуется через временные очереди ответов (заголовок `reply-to` и `correlation-id` для связки запроса с ответом).
- **Fan-out:** Шаблон, при котором сообщение копируется во все доступные очереди/подписчиков. В Kafka достигается автоматически за счет нескольких Consumer Groups на один топик.

### Преимущества и недостатки использования брокеров

**Преимущества:**
- **Service Discovery (Развязка по пространству):** Продюсеру не нужно знать IP-адреса и порты всех консьюмеров. Достаточно знать адрес брокера.
- **Высокая доступность (High Availability):** Брокер выступает буфером. Если консьюмер временно недоступен, сообщения накапливаются в очереди и будут обработаны после его восстановления.
- **Масштабирование (Load Balancing):** Возможность легко распределять нагрузку между множеством экземпляров одного сервиса-потребителя.
- **Устойчивость к каскадным сбоям:** Брокер изолирует сервисы друг от друга. Падение одного компонента не приводит к мгновенной остановке всей системы.
- **Backpressure (Управление нагрузкой):** Консьюмеры могут вычитывать данные с той скоростью, с которой они способны их обрабатывать, не будучи перегруженными продюсером.

**Недостатки:**
- **Увеличение задержки (Latency):** Дополнительный «прыжок» через сеть и обработка на брокере увеличивают время доставки сообщения.
- **Сложность эксплуатации:** Появляется новый критический компонент инфраструктуры, требующий мониторинга, резервного копирования и администрирования.
- **Единая точка отказа (SPOF):** Если кластер брокеров выйдет из строя, вся асинхронная коммуникация в системе остановится. Требуется использование кластерных решений (Quorum Queues, ISR).
- **Упорядочивание:** Глобальный порядок сообщений в распределенном брокере сложен и дорог. Обычно гарантируется порядок только внутри одной очереди или партиции.

### Семантика доставки (Delivery Guarantees)

Гарантии доставки — это набор обязательств, которые брокер и клиенты берут на себя для обеспечения сохранности и корректности передачи данных. Подробный разбор семантик At-most-once, At-least-once и Exactly-once: **[Гарантии доставки](./delivery_guarantees.md)**.

| Гарантия | Риск потери | Риск дубликатов | Нагрузка / Latency | Типичные сценарии |
| :--- | :--- | :--- | :--- | :--- |
| **At-most-once** | Да | Нет | Минимальная | Сбор метрик, UDP-подобные потоки телеметрии. |
| **At-least-once (default)** | Нет | Да | Средняя | Платежи, заказы (с дедупликацией в БД). |
| **Exactly-once** | Нет | Нет | Высокая | Финансовый клиринг, агрегация данных в реальном времени. |

**Важно:** Exactly-once гарантируется **только внутри экосистемы Kafka** (транзакции между топиками одного кластера). Если приложение пишет данные во внешнюю базу данных или вызывает внешний API, семантика откатывается к **At-least-once**, так как Kafka не может гарантировать атомарность внешнего действия и фиксации офсета.

### Жизненный цикл сообщения (Flow)

1. **Сериализация:** Продюсер переводит объект данных в байтовый формат.
2. **Публикация:** Продюсер отправляет байты брокеру, указывая цель (Exchange или Topic).
3. **Прием и маршрутизация:** Брокер подтверждает прием (Publisher Confirm) и помещает сообщение в соответствующие очереди/партиции.
4. **Хранение:** Сообщение сохраняется в памяти или на диске (Durability).
5. **Доставка / Получение:** Брокер проталкивает (Push) или консьюмер запрашивает (Pull) сообщение.
6. **Обработка:** Консьюмер десериализует данные и выполняет бизнес-логику.
7. **Подтверждение:** Консьюмер отправляет `ack`. Брокер помечает сообщение как обработанное.

### Механизмы Backpressure

Backpressure — состояние, при котором брокер или консьюмер ограничивают скорость продюсера, предотвращая переполнение:

- **Consumer-side:** В Kafka консьюмер читает данные только тогда, когда готов их обработать. Размер батча (`max.poll.records`) и интервал poll (`max.poll.interval.ms`) ограничивают объем данных в памяти.
- **Broker-side (RabbitMQ):** Используется `prefetch_count` (QoS) — брокер отправляет консьюмеру только N сообщений, не дожидаясь подтверждения.
- **Producer-side:** Таймауты и буферы продюсера ограничивают количество «в воздухе» сообщений (`max.in.flight.requests.per.connection`). При переполнении продюсер блокируется или выбрасывает исключение (`BufferExhaustedException`).

### Сериализация данных (SerDes)

Формат данных определяет скорость, размер сообщений и гибкость развития системы.

| Формат | Тип | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **JSON** | Текстовый | Читаемость, простота, универсальность. | Избыточность (ключи), медленный парсинг. |
| **Protobuf** | Бинарный | Высокая скорость, компактность, типизация. | Требует компиляции `.proto` файлов. |
| **Avro** | Бинарный | Минимальный размер, поддержка эволюции схем. | Сложность без Schema Registry. |
| **Thrift** | Бинарный | Высокая скорость, поддержка нескольких языков. | Меньше распространен в экосистеме Kafka. |

#### Schema Registry

Централизованный сервис для хранения версий схем данных.
- **Механизм:** Продюсер отправляет в Kafka только ID схемы, а само сообщение содержит только значения полей.
- **Преимущество:** Консьюмер скачивает схему по ID и десериализует данные. Это позволяет менять структуру сообщения (добавлять поля), не ломая старых потребителей.
- **Ограничение:** Без Schema Registry работа с Avro/Protobuf практически невозможна — отсутствует механизм определения формата на приеме.

### Безопасность

Безопасность канала передачи данных включает три слоя:

1. **Шифрование (SSL/TLS):** Защита трафика между клиентами и брокерами, а также между самими брокерами (inter-broker communication).
2. **Аутентификация (SASL):** Механизмы `PLAIN` (логин/пароль, только поверх TLS), `SCRAM-SHA-256/512`, `GSSAPI` (Kerberos), `OAUTHBEARER`.
3. **Авторизация (ACL):** Контроль доступа к ресурсам (топики, группы, кластер) на уровне операций (Read, Write, Describe).

## Практические сценарии

### Настройка и обязанности компонентов

#### Продюсер (Producer)

- **Надежность:** Настройка подтверждений (`acks=all`), использование транзакций или паттерна Transactional Outbox.
- **Оптимизация:** Батчинг (объединение сообщений в пакеты) и сжатие (Snappy, Gzip, Zstd) для снижения нагрузки на сеть.
- **Маршрутизация:** Выбор ключа партиционирования для обеспечения порядка (Kafka) или Routing Key для сложных топологий (RabbitMQ).
- **Идемпотентность:** Начиная с Kafka 3.0, `enable.idempotence=true` включен по умолчанию. В RabbitMQ для дедупликации используется `message_id` на стороне приложения.

**Предварительные требования:**
- JDK 17+ (для Kafka 4.x) или соответствующий клиентский драйвер.
- Доступ к брокеру (сеть, сертификаты TLS при необходимости).
- Установленный Schema Registry при работе с Avro/Protobuf.

**Пошаговая настройка продюсера Kafka (Java):**

```properties
# Идемпотентный продюсер (Kafka 3.0+): acks=all, retries=MAX, max.in.flight<=5
enable.idempotence=true

# Сжатие батчей (экономия сети и диска)
compression.type=lz4

# Накопление батча: ждать до 20 мс и собирать пакеты до 32 КБ
linger.ms=20
batch.size=32768

# Общий лимит на доставку (время отправки + все ретраи)
delivery.timeout.ms=120000

# Таймаут на запрос к брокеру
request.timeout.ms=30000

# Повторные попыты при временных ошибках
retries=2147483647
retry.backoff.ms=500
```

**Валидация конфигурации:**

```bash
# Запуск producer-perf-test для проверки acks=all
kafka-producer-perf-test.sh \
  --topic test-acks \
  --num-records 10000 \
  --record-size 1024 \
  --throughput 1000 \
  --producer-props acks=all bootstrap.servers=localhost:9092

# Проверка количества ошибок (должно быть 0)
# → 10000 records sent, 1000.000000 records/sec (0.98 MB/sec), 1.00 ms avg latency, 5.00 ms max latency, 0.00% error rate.
```

**Типичные ошибки продюсера:**

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `NOT_ENOUGH_REPLICAS` | ISR просело ниже `min.insync.replicas` | Проверить `kafka-topics.sh --describe`; восстановить брокер. Не снижать `min.insync.replicas`. |
| `TimeoutException` | Брокер не отвечает за `request.timeout.ms` | Проверить сеть, метрики брокера (`RequestHandlerAvgIdlePercent`). |
| `UNKNOWN_TOPIC_OR_PARTITION` | Метаданные топика еще не распространились | Подождать 30–60 секунд (метаданные кэшируются на клиенте). |
| `RecordTooLargeException` | Сообщение превышает `max.request.size` | Увеличить лимит или использовать паттерн Claim Check. |

#### Брокер (Broker)

- **Durability:** Настройка персистентности — запись на диск перед подтверждением приема.
- **Управление порядком:** Порядок гарантируется только внутри одной очереди или [партиции](./partitioning_and_balancing.md).
- **Error Handling:** Настройка **Dead Letter Queues (DLQ)** для изоляции сообщений, вызывающих ошибки (Poison Pills).
- **Retention:** Определение политики удаления данных по времени (TTL) или размеру.

**Предварительные требования:**
- Linux/macOS, JDK 17+ (Kafka 4.x), 8+ ГБ RAM, 100+ ГБ SSD.
- Настройка `vm.swappiness = 1`, отключение THP (Transparent Huge Pages).
- Для production: минимум 3 брокера, RF=3, `min.insync.replicas=2`.

**Пошаговая проверка работоспособности брокера:**

```bash
# 1. Проверка статуса сервиса
systemctl status kafka
# → Active: active (running) since ...

# 2. Проверка слушаемых портов
ss -tlnp | grep 9092
# → LISTEN 0 4096 *:9092 *:* users:(java,pid=1234,fd=123)

# 3. Проверка метрик контроллера
kafka-run-class kafka.tools.JmxTool \
  --object-name "kafka.controller:type=KafkaController,name=ActiveControllerCount" \
  --one-time true
# → ActiveControllerCount = 1

# 4. Проверка UnderReplicatedPartitions
kafka-run-class kafka.tools.JmxTool \
  --object-name "kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions" \
  --one-time true
# → UnderReplicatedPartitions = 0

# 5. Проверка ISR по топику
kafka-topics.sh --bootstrap-server localhost:9092 --topic orders --describe
# → Partition: 0 Leader: 1 Replicas: 1,2,3 Isr: 1,2,3
```

**Типичные ошибки брокера:**

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `UnderReplicatedPartitions > 0` | Медленные диски, сеть, упавший брокер | Проверить `iostat`, `ping`, `systemctl status kafka` на follower. |
| `LeaderNotAvailableException` | Контроллер не может назначить лидера | Проверить `ActiveControllerCount`, логи брокера. |
| `Disk full` | Retention не работает, переполнение `log.dirs` | Уменьшить `retention.bytes` или добавить диски. |
| `High RequestHandlerAvgIdlePercent < 0.1` | Брокер перегружен запросами | Увеличить `num.io.threads`, добавить брокеры. |

#### Консьюмер (Consumer)

- **Идемпотентность:** Обязательное условие при семантике At-least-once. Повторная обработка одного и того же сообщения не должна менять состояние системы дважды.
- **Prefetch / Batch size:** Настройка количества сообщений, загружаемых в память за один раз, для предотвращения переполнения RAM.
- **Retry Policy:** Реализация стратегий повтора (Retries) с экспоненциальным откатом (Exponential Backoff).
- **Обработка Poison Pills:** Битая десериализация одного сообщения не должна останавливать всю группу консьюмеров.

**Предварительные требования:**
- Совместимость версий клиента и брокера (или использование `inter.broker.protocol.version`).
- Настроенный `group.id`, корректно выбранный `auto.offset.reset` (earliest/latest/none).
- Идемпотентная обработка на стороне приложения.

**Пошаговая настройка консьюмера Kafka (Java):**

```properties
group.id=orders-processor

# Ручной коммит: офсет фиксируется ТОЛЬКО после успешной обработки.
enable.auto.commit=false

# Поведение при отсутствии закоммиченного офсета:
auto.offset.reset=earliest

# Видеть только закоммиченные данные (для EOS-продюсеров)
isolation.level=read_committed

# Инкрементальная ребалансировка без stop-the-world
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# Таймауты: запас на GC-паузы и сетевые проблемы
session.timeout.ms=45000

# Максимум времени между вызовами poll()
max.poll.interval.ms=300000

# Размер батча за один poll
max.poll.records=500

# Сетевые и fetch-параметры
fetch.min.bytes=1
fetch.max.wait.ms=500
max.partition.fetch.bytes=1048576
```

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| Консьюмер зависает на одном сообщении | Poison pill (битая десериализация) | Обернуть в try/catch, отправить в DLQ-топик. |
| Постоянные ребалансировки | `max.poll.interval.ms` слишком мал | Увеличить таймаут или уменьшить `max.poll.records`. |

### Паттерны обработки ошибок и устойчивости

#### Retry с экспоненциальным откатом (Exponential Backoff)

Повторные попытки при временных ошибках должны сопровождаться ростом задержки:

```python
import time
import random

def send_with_retry(message, max_retries=5, base_delay=1.0):
    for attempt in range(max_retries):
        try:
            producer.send(message)
            return True
        except TemporaryException as e:
            delay = base_delay * (2 ** attempt) + random.uniform(0, 1)
            time.sleep(delay)
    raise PermanentException("Failed after retries")
```

**Рекомендации:**
- Используйте `retry.backoff.ms` на стороне клиента (Kafka: 500 мс по умолчанию).
- Для RabbitMQ настройте параметры `x-delivery-limit` и `x-delivery-exchange`.
- Добавляйте джиттер (случайное отклонение) для предотвращения "штурма" брокера.

#### Circuit Breaker (Прерыватель цепи)

Защита от каскадных отказов при недоступности брокера:

- **Открытое состояние (Open):** После N последовательных ошибок запросы к брокеру не отправляются, а сразу возвращают fallback-результат.
- **Полуоткрытое (Half-Open):** Периодически отправляются пробные запросы для проверки восстановления.
- **Закрытое (Closed):** Нормальная работа, ошибки считаются.

**Инструменты:** Resilience4j, Polly (C#), Hystrix (устарел).

### Паттерн: Transactional Outbox

Используется для надежной отправки событий при изменении данных в БД.

1. **Запись:** В рамках одной транзакции БД обновляются бизнес-данные и записывается событие в служебную таблицу `outbox`.
2. **Передача (Relay):** Отдельный процесс (Relay) или CDC-инструмент (например, Debezium) читает таблицу `outbox` и публикует сообщения в брокер.
3. **Очистка:** После успешной отправки записи из `outbox` удаляются или помечаются как отправленные.

**Результат:** Гарантия **At-least-once** доставки события в брокер: если бизнес-данные сохранились, сообщение точно будет отправлено, но возможно дублирование (например, relay упал между публикацией и пометкой записи). Эффект «ровно один раз» достигается только добавлением дедупликации на приемнике. Подробное сравнение Relay против CDC и схема Inbox: [Распределенные транзакции](../Databases/Concepts/distributed_transactions.md), [Идемпотентность](../Concepts/idempotency.md).

### Паттерн: Идемпотентный потребитель (Idempotent Consumer)

Самый распространенный способ обработки дубликатов при семантике **At-least-once**.

1. Продюсер добавляет в сообщение уникальный `request_id`.
2. Потребитель перед обработкой проверяет наличие этого ID в базе данных (например, в таблице `processed_messages`).
3. Если ID найден — сообщение пропускается. Если нет — выполняется бизнес-логика и ID сохраняется в рамках одной транзакции.

### Обработка ошибок и DLQ (Dead Letter Queues)

Для предотвращения бесконечных циклов обработки «битых» сообщений (poison pills) используются очереди «мертвых писем».

- **Принцип:** Если сообщение не удалось обработать после N попыток, оно перемещается в специальную очередь (в RabbitMQ) или топик (в Kafka) для ручного анализа.
- **RabbitMQ:** Настраивается через `x-dead-letter-exchange`; счетчик доставок ограничивается `x-delivery-limit` (кворумные очереди).
- **Kafka:** Реализуется на стороне консьюмера (перенаправление сообщения в другой топик). Альтернатива DLQ — паттерн retry-топиков (`orders.retry.5m`, `orders.retry.30m`) с отложенным повтором; в Kafka Streams есть встроенный обработчик десериализации (`DeserializationExceptionHandler`), отправляющий битые записи в DLT-топик.
- **Важно:** Сообщение в DLQ — это не решение проблемы, а ее локализация. Настройте алертинг на глубину DLQ.

### Мониторинг и наблюдаемость (Observability)

Ключевые показатели здоровья систем обмена сообщениями:
- **Consumer Lag:** Разрыв между последним сообщением в брокере и позицией чтения консьюмера. Самый важный индикатор проблем производительности.
- **Throughput (Пропускная способность):** Количество сообщений в секунду на запись (Inbound) и чтение (Outbound).
- **Error Rate / DLQ Rate:** Частота попадания сообщений в очередь ошибок.
- **Resource Pressure:** Использование CPU, RAM (критично для RabbitMQ) и дискового пространства брокерами.
- **UnderReplicatedPartitions:** Количество партиций с неполной репликацией (должно быть 0).
- **ISR Shrink Rate:** Скорость сокращения синхронных реплик.

## Ограничения и краевые случаи (Edge Cases)

### Общие ограничения message queues

1. **Глобальный порядок сообщений:** В распределенном брокере глобальный порядок по топику отсутствует. Для упорядоченной обработки объекта используйте его идентификатор как ключ. Для сообщений без ключа порядок между объектами не гарантируется вовсе.
2. **Изменение числа партиций:** В Kafka изменение числа партиций ломает соответствие `hash(key) % N`. Увеличивайте число партиций до ожидаемого максимума заранее.
3. **Большие сообщения:** Лимит по умолчанию ~1 МБ (`message.max.bytes` у брокера, `max.request.size` у продюсера). Каноничное решение — паттерн Claim Check: данные в объектном хранилище, в событии только ссылка.
4. **Потеря сообщений при unclean leader election:** Если `unclean.leader.election.enable=true` и все ISR упали, новым лидером может стать отстающая реплика, что приведет к потере данных.
5. **Задержки при ребалансировке:** В классическом (eager) протоколе ребалансировка вызывает Stop-the-world паузу для всей группы. Используйте CooperativeStickyAssignor (KIP-429) или протокол KIP-848 (GA с Kafka 4.0).
6. **Ограничение параллелизма:** Количество активных консьюмеров в группе не может превышать количество партиций. «Лишние» консьюмеры простаивают.
7. **Транзакции и внешние системы:** Exactly-once гарантируется только внутри экосистемы Kafka. Для внешних систем требуется идемпотентность на стороне получателя.

### Ограничения RabbitMQ

1. **Vertically scalable:** Очереди по умолчанию размещаются на одном узле. Масштабирование происходит через federation/shadows или кластерные очереди (Quorum Queues).
2. **Memory pressure:** При переполнении RAM брокер блокирует продюсеров (flow control). Требуется careful capacity planning.
3. **Сложность troubleshooting:** При использовании federation или shovel routing debugging маршрутизации может быть нетривиальным.

### Ограничения Kafka

1. **Over-partitioning:** Каждая партиция требует ресурсов для репликации, метаданных и координации. Слишком большое количество партиций может замедлить работу контроллера.
2. **Долговечность против throughput:** Настройка `acks=all` + `min.insync.replicas=2` + RF=3 обеспечивает максимальную надежность, но снижает пропускную способность записи.
3. **Offset management:** Консьюмеры самостоятельно управляют офсетами. При неверной конфигурации `auto.offset.reset` возможна потеря или дублирование данных.
4. **Segment immutability:** Данные в партиции неизменяемы. Для обновления записи необходимо записать новую версию с тем же ключом (в компактных топиках).

## Безопасность и Multi-tenancy

### Безопасность

- **Шифрование (SSL/TLS):** Защита трафика между клиентами и брокерами, а также между самими брокерами (inter-broker communication). Возможна взаимная аутентификация сертификатами (mTLS).
- **Аутентификация (SASL):** Механизмы `PLAIN` (логин/пароль, только поверх TLS), `SCRAM-SHA-256/512` (хранение хэшей учетных данных в самом кластере), `GSSAPI` (Kerberos), `OAUTHBEARER` (интеграция с внешним OAuth/OIDC-провайдером).
- **Авторизация (ACL):** Контроль доступа к ресурсам (топики, группы, кластер, транзакционные ID) на уровне операций (Read, Write, Describe и др.). Включается параметром `authorizer.class.name`.

### Multi-tenancy (Многопользовательские среды)

- **Квоты (Quotas):** Ограничение пропускной способности (`network.quota.bytes.per.second.default`), скорости запросов (`request.quota.window.num`) и дискового пространства.
- **Разделение топиков по командам:** Использование префиксов `team-a-`, `team-b-` для логической изоляции.
- **Separate clusters:** Для strict isolation используются отдельные кластеры с разными ресурсами.

## Пример реализации идемпотентности (Код)

```python
# Псевдокод: Использование ключа дедупликации в БД
def process_message(msg):
    # msg.id - уникальный идентификатор (например, UUID транзакции)
    if database.exists(f"processed_msg:{msg.id}"):
        log.info(f"Дубликат обнаружен: {msg.id}. Пропускаем.")
        return

    try:
        with database.transaction():
            perform_business_logic(msg.payload)
            database.save(f"processed_msg:{msg.id}", status="done")
    except Exception as e:
        log.error(f"Ошибка обработки: {e}")
        raise # Позволит брокеру вернуть сообщение в очередь
```

### Глоссарий

| Термин | Описание |
| :--- | :--- |
| **Poison Pill** | Сообщение, которое невозможно обработать и которое приводит к падению консьюмера. |
| **Exponential Backoff** | Увеличение задержки между повторными попытками обработки сообщения. |
| **Fan-out** | Шаблон, при котором сообщение копируется во все доступные очереди/подписчиков. |
| **Backpressure** | Состояние, при котором брокер или консьюмер ограничивают скорость продюсера. |
| **Dead Letter Queue (DLQ)** | Очередь для сообщений, которые не удалось обработать после N попыток. |
| **Sticky Partitioner** | Стратегия партиционирования Kafka без ключа: продюсер наполняет батчи по одной партиции перед переключением. |
| **Unclean Leader Election** | Выбор лидера из реплик, не входящих в ISR. Может привести к потере данных. |
| **Zombie Instance** | Старый экземпляр приложения, который считает себя активным и пытается писать в брокер. |
| **Transactional Outbox** | Паттерн надежной отправки событий через таблицу outbox в той же транзакции, что и бизнес-данные. |
| **Claim Check** | Паттерн для больших сообщений: данные в объектном хранилище, в Kafka — только ссылка. |
| **Share Group (KIP-932)** | Группа консьюмеров с queue-семантикой поверх партиций (GA с Kafka 4.2). |
