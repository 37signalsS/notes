# Обзор Apache Kafka

**Apache Kafka** — распределённая стриминговая платформа для создания высокопроизводительных конвейеров (pipelines) данных, потоковой аналитики и интеграции систем. В отличие от традиционных систем обмена сообщениями, Kafka спроектирована как отказоустойчивый неизменяемый журнал (лог), обеспечивающий надёжность и возможность повторного чтения данных.

---

## Определения

- **Событие (Event):** Запись о произошедшем факте или действии, часто представленная в виде пары «ключ-значение» (key-value pair).
- **Стриминг событий (Event Streaming):** Непрерывный поток и обработка данных о событиях в реальном времени, обеспечивающая возможность немедленного анализа или реакции.
- **Брокер (Broker):** Сервер Kafka, хранящий данные и обслуживающий запросы продюсеров и консьюмеров. Кластер состоит из одного или нескольких брокеров. Брокеры работают в тесной связке, распределяя между собой нагрузку по хранению и обслуживанию партиций.
- **Топик (Topic):** Логическая категория или именованный поток записей, в который продюсеры записывают, а консьюмеры считывают данные. Топик можно представить как аналог таблицы в БД или папки в файловой системе.
- **Партиция (Partition):** Минимальная единица параллелизма и масштабирования. Топик делится на партиции — упорядоченные неизменяемые журналы сообщений. Каждая партиция является атомарной единицей, которую может обрабатывать один консьюмер в группе. Порядок сообщений гарантируется строго в пределах одной партиции.
- **Продюсер (Producer):** Клиентское приложение, отправляющее записи (сообщения) в топики Kafka. Продюсер определяет, в какую партицию отправить сообщение: на основе ключа, либо по липкой стратегии (Sticky Partitioner) для сообщений без ключа.
- **Консьюмер (Consumer):** Клиентское приложение, подписывающееся на топики и считывающее из них данные. Консьюмеры могут работать независимо или объединяться в группы.
- **Группа потребителей (Consumer Group):** Группа консьюмеров, совместно читающих данные из топиков. Kafka распределяет партиции топика между участниками группы, обеспечивая параллельную обработку и балансировку нагрузки.
- **Смещение (Offset):** Уникальный последовательный идентификатор (целое число) записи в пределах партиции. Консьюмеры используют офсет для отслеживания своей позиции чтения, что позволяет возобновлять работу после сбоев.
- **Запись (Record):** Атомарная единица данных в Kafka. Состоит из временной метки (timestamp), ключа (key), значения (value) и заголовков (headers). Ключ и значение передаются как байтовые массивы, формат сериализации определяется приложением.
- **Заголовки (Headers):** Набор произвольных пар «ключ-значение», передаваемых вместе с записью без изменения тела сообщения. Используются для трассировки (trace-id), идентификатора схемы и служебной маршрутизации.
- **Журнал (Log):** Упорядоченная append-only последовательность записей партиции. Записи видны консьюмерам в порядке добавления; физически журнал состоит из сегментов.
- **Репликация (Replication):** Механизм отказоустойчивости, при котором партиции копируются на несколько брокеров. Существует реплика-лидер (обрабатывает запросы) и реплики-последователи (пассивно копируют данные).
- **Синхронные реплики (ISR — In-Sync Replicas):** Список реплик (включая лидера), которые не отстают от лидера и полностью синхронизированы с ним. Новый лидер может быть выбран только из состава ISR.
- **High Watermark (HW):** Офсет последней записи, успешно реплицированной на все реплики из ISR. Консьюмеры видят записи только до этой отметки — это исключает чтение данных, которые могут быть потеряны при смене лидера. Подробнее: **[Партиционирование и балансировка](./partitioning_and_balancing.md)**.
- **Контроллер (Controller):** Узел кластера, отвечающий за метаданные (список брокеров, топиков, конфигураций) и назначение лидеров партиций. В режиме KRaft контроллеры образуют кворум по протоколу Raft.
- **Bootstrap-сервер:** Адрес одного или нескольких брокеров для первичного подключения клиента. По этому адресу клиент запрашивает полные метаданные кластера, после чего взаимодействует с нужными брокерами напрямую — адрес начального подключения не обязан быть лидером партиции.
- **Tombstone (Надгробие):** Запись со значением `null` в топике с политикой `compact`. Маркер удаления ключа: при компактификации все предыдущие значения этого ключа вычищаются.
- **KRaft (Kafka Raft):** Встроенный протокол консенсуса на базе Raft, заменивший зависимость от ZooKeeper. ZooKeeper был объявлен устаревшим (deprecated) в версии 3.5 (2023) и **полностью удалён из дистрибутива в версии 4.0 (март 2025)** — все кластеры линейки 4.x работают исключительно в режиме KRaft.
- **Сегмент (Segment):** Физический файл на диске брокера, в котором хранятся сообщения партиции. Удаление и компактификация данных происходят на уровне сегментов.

## Основные концепции

### История и предпосылки

Apache Kafka создана в **LinkedIn в 2011 году** (с 2012 года — проект Apache Software Foundation) для решения проблем синхронного взаимодействия сервисов: каскадных отказов и неконтролируемого обратного давления (backpressure). Классические очереди сообщений (RabbitMQ, IBM MQ, SQS) решали проблему жёсткой связанности, но оставались ограничены одной машиной — очередь масштабируется только **вертикально**.

**Проблемы классической архитектуры (на примере интернет-магазина):**
Представьте сервис оформления заказа (Checkout), который при поступлении нового заказа должен напрямую вызвать:
1.  **Email Service** — для подтверждения заказа.
2.  **Inventory Service** — для обновления склада.
3.  **Analytics Service** — для учета продаж.

Это создает две фундаментальные проблемы:
*   **Жесткая связанность (Tight Coupling):** Checkout должен "знать" обо всех сервисах-получателях. Добавление нового сервиса (например, программы лояльности) требует изменения кода Checkout.
*   **Синхронное ожидание (Blocking):** Если Email Service тормозит или упал, Checkout вынужден ждать ответа, что замедляет работу всей системы для пользователя.

**Решение с Kafka:** Checkout просто пишет событие `order_created` в Kafka и не заботится о том, кто и когда его прочитает. Продюсеры и консьюмеры полностью развязаны.

**Проблемы классической EDA (без централизованной шины):**
1. **Жесткая связанность (Tight Coupling):** Сервисы слишком зависят друг от друга. Изменение в одной системе (например, платежной) может сломать другую (заказы).
2. **Ограниченная масштабируемость:** Системы с прямым взаимодействием («точка-точка») плохо справляются с резкими всплесками трафика (например, Super Bowl в Twitter или Black Friday в e-commerce).
3. **Единая точка отказа (SPOF):** Падение одного критического компонента может вызвать «эффект домино», обрушив всю цепочку сервисов.
4. **Отсутствие персистентности:** Если события не сохраняются, риск потери критических данных (например, транзакции в банке) возрастает при сбоях доставки.
5. **Ограниченная функциональность:** Без продвинутых функций (аналитика в реальном времени, восстановление после ошибок) архитектура не раскрывает свой потенциал.

### Масштаб использования в индустрии

Показатели реальных внедрений демонстрируют пределы применимости технологии:

- **Netflix:** ~4 000 брокеров, более 50 кластеров, обрабатывающих ~1 триллион сообщений в день.
- **Pinterest:** ~4 триллиона сообщений в день, пиковая нагрузка ~50 ГБ/с, хранение экзобайтов данных в S3.
- **PayPal:** ~1 500 брокеров, более 85 кластеров, обеспечивающих 99.99% времени работы финансовых транзакций.
- **LinkedIn:** ~1 400 брокеров, ~1.4 триллиона сообщений в день.
- **Яндекс:** использует Kafka-совместимый брокер, ~150 ГБ/с, более 2 000 брокеров.
- **Ozon:** кластер из ~200 брокеров для обработки заказов и логистики.

### Модель «Издатель-подписчик» на основе журнала

В отличие от классических очередей, где сообщение удаляется после прочтения, Kafka сохраняет сообщения в течение настраиваемого периода. Консьюмеры не «забирают» сообщения, а читают их по указателю (офсету).

**Преимущества:**
1. **Множество консьюмеров** читают одни и те же данные независимо друг от друга (например, один поток данных идет в БД, другой — в систему мониторинга).
2. **Возврат назад во времени** — возможность повторно прочитать обработанные сообщения (например, после исправления бага в логике обработки).

**Анатомия записи (Record):**

| Поле | Назначение | Особенности |
| :--- | :--- | :--- |
| **Timestamp** | Время события | Тип `CreateTime` (ставит продюсер, по умолчанию) или `LogAppendTime` (ставит брокер при записи). |
| **Key** | Ключ партиционирования | Байтовый массив. Определяет партицию через хэш. `null` — сообщение без ключа. |
| **Value** | Полезная нагрузка | Байтовый массив произвольного формата (JSON, Avro, Protobuf). `null` означает tombstone в компактных топиках. |
| **Headers** | Служебные метаданные | Произвольные пары «ключ-значение»: trace-id, ID схемы, флаги ретраев. Не участвуют в партиционировании. |

### Партиционирование для масштабируемости

Топики разбиваются на партиции, распределяемые по разным брокерам. Партиция — это лог-файл, в который данные дописываются только в конец.

**Алгоритм выбора партиции (Partitioning):**
Продюсер может явно указать номер партиции, но обычно используется автоматическое распределение:
1. **Сообщение с ключом:** Берется ключ сообщения (байтовый массив), вычисляется хэш (по умолчанию используется MurmurHash2). Номер партиции = `hash(key) % total_partitions`. Это гарантирует, что сообщения с одинаковым ключом (например, ID одного заказа или пользователя) всегда попадут в одну партицию и будут обработаны в строгом порядке.
2. **Сообщение без ключа:** Вместо чистого Round-Robin используется **липкий партиционер (Sticky Partitioner, KIP-480)** — продюсер наполняет батчи по одной партиции, переключаясь на следующую после её заполнения. Это улучшает сжатие и снижает нагрузку на сеть за счет более крупных батчей. Начиная с Kafka 3.3 (KIP-794) эта логика унифицирована и учитывает совместимость с изменением числа партиций.

**Возможности:**
- **Горизонтальное масштабирование:** нагрузка распределяется по серверам, пропускная способность кластера растёт пропорционально числу брокеров и партиций.
- **Порядок сообщений:** гарантируется строго **в пределах одной партиции**.

**Подробнее:** **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — стратегии партиционирования, выбор количества партиций, data skew.

### Управление смещениями и группами потребителей

В Kafka консьюмеры сами отслеживают свою позицию (Offset). При использовании Consumer Groups офсеты могут храниться на стороне брокера.

**Механизм хранения:**
- Офсеты записываются в специальный служебный топик `__consumer_offsets` (компактный внутренний топик, по умолчанию 50 партиций; ключ записи — кортеж «группа + топик + партиция»).
- Консьюмер отправляет сообщение `commit offset` после обработки пачки данных.
- По умолчанию библиотека делает это автоматически каждые 5 секунд (auto-commit), но для обеспечения надежности (At-least-once) часто настраивают ручной коммит.

**Новый протокол групп (KIP-848):** Представлен в раннем доступе в Kafka 3.7 (2024), статус **Generally Available с версии 4.0** (март 2025). Логика назначения партиций перенесена на сторону брокера: координатор инкрементально раздает партиции без «Stop-the-world» пауз для всей группы. На сервере протокол активируется автоматически после финализации апгрейда; клиентские приложения подключаются к нему явным параметром `group.protocol=consumer`.

**Внешнее хранение офсетов:** Консьюмер может хранить offset самостоятельно (например, в той же БД, куда записывает результат обработки), обеспечивая атомарность операции. При старте он указывает брокеру, с какого смещения начинать чтение.

### Процесс перебалансировки (Rebalancing)

Когда в группе меняется состав участников (добавился новый консьюмер или упал существующий), запускается перебалансировка для перераспределения партиций.

**Этапы в классическом (eager) протоколе:**
1. **Остановка:** Kafka приостанавливает отправку новых сообщений всем участникам группы (Stop-the-world пауза).
2. **Координация:** Выбирается `Group Coordinator` (один из брокеров) и `Group Leader` (один из консьюмеров группы).
3. **Назначение:** Лидер группы распределяет партиции между консьюмерами согласно алгоритму (например, Round Robin или Sticky) и передает план координатору.
4. **Запуск:** Координатор рассылает новый план всем участникам, и они начинают чтение из назначенных партиций.

**Важно:** Перебалансировка в классическом протоколе — ресурсоемкая операция. Современные подходы устраняют её недостатки:
- **CooperativeStickyAssignor (KIP-429):** Инкрементальная перебалансировка — отзываются только перемещаемые партиции, остальные консьюмеры продолжают работу без остановки.
- **Статическое членство (Static Membership, KIP-345):** Параметр `group.instance.id` исключает ребалансировку при кратковременном перезапуске консьюмера (в пределах `session.timeout.ms`) — актуально для Kubernetes/Docker, где поды часто перезапускаются.
- **Протокол KIP-848 (GA с Kafka 4.0):** Назначением партиций управляет сам брокер инкрементально; клиентский лидер группы больше не строит план распределения, что убирает паузы даже для очень больших групп.

### Репликация и отказоустойчивость

Каждая партиция имеет несколько копий (реплик) на разных брокерах. Фактор репликации (Replication Factor) определяет количество этих копий.

- **Лидер и последователи (Leader & Followers):** Все операции записи и чтения по умолчанию идут через лидера. Последователи асинхронно копируют данные лидера.
- **Восстановление после сбоя:** При выходе лидера из строя Kafka (через контроллер) автоматически выбирает нового лидера из списка ISR.
- **Синхронные реплики (ISR):** Реплики, которые полностью догнали лидера. Параметр `min.insync.replicas` определяет минимальное количество ISR для подтверждения записи при `acks=all`. Если синхронных реплик меньше минимума, брокер отклоняет запись с ошибкой `NOT_ENOUGH_REPLICAS` — защита от потери данных ценой доступности записи.

**Подробнее:** **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — настройки RF и min.insync.replicas, сценарий failover.

### Механизмы ISR

ISR (In-Sync Replicas) — это не просто счётчик реплик, а динамический механизм, определяющий какие реплики могут стать лидером.

**Логика работы ISR:**
- Реплика остаётся в ISR, пока регулярно отправляет fetch-запросы лидеру (в пределах `replica.lag.time.max.ms`, по умолчанию 30 секунд)
- Если реплика не запрашивает данные дольше этого порога — она исключается из ISR (ISR shrink)
- Когда реплика догоняет лидер (LEO приближается к HW лидера) — она возвращается в ISR (ISR expand)

**Ключевой параметр:** `replica.lag.time.max.ms` — влияет на:
- Скорость обнаружения "мёртвых" реплик
- Доступность записи при `acks=all` (если ISR сокращается до 1, продюсер получает ошибку при `min.insync.replicas=2`)

**Диагностика ISR:**
```bash
# Проверка текущего состояния ISR по топику
kafka-topics.sh --bootstrap-server kafka:9092 --topic orders --describe

# Метрика UnderReplicatedPartitions (должна быть 0)
kafka-run-class kafka.tools.JmxTool \
  --object-name "kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions" \
  --one-time true
```

**Подробнее:** **[ISR и репликация](./kafka_isr_replication.md)** — полный разбор механизмов ISR, параметров репликации и unclean leader election.

### Архитектура KRaft

Режим работы без ZooKeeper, основанный на протоколе консенсуса Raft (KIP-500).

- **Хранение метаданных:** Состояние кластера (реестр брокеров, конфигурации топиков, ACL) хранится в самой Kafka — во внутреннем журнале `__cluster_metadata`, который сам является партицией с кворумной репликацией.
- **Контроллеры:** Вместо одиночного контроллера выбирается кворум (обычно 3 или 5 узлов). Каждый узел настраивается параметром `process.roles`: роль `controller`, роль `broker` или совмещенная (`broker,controller`) для малых сред.
- **Преимущества:** Масштабируемость до миллионов партиций, мгновенное восстановление контроллера (метаданные уже реплицированы Raft-журналом), упрощение эксплуатации (один бинарный файл, один тип узлов, одна модель безопасности).

**Актуальный статус:** ZooKeeper был объявлен устаревшим в версии 3.5 и полностью удалён в **Kafka 4.0 (март 2025)**. Существующие кластеры на ZooKeeper мигрируют на KRaft штатным инструментом миграции (production-ready с версии 3.6, KIP-866); поскольку версия 3.9 была последней с поддержкой ZooKeeper, обновление до 4.x выполняется через промежуточное обновление до 3.9. Брокеры 4.0 требуют JVM 17+ (поддержка Java 8 удалена). Новые возможности линейки 4.x выпускаются только для KRaft.

**Практика развертывания:** **[Развертывание в Docker (KRaft)](./kafka_docker_setup.md)**, **[Strimzi Operator для Kubernetes](./strimzi_kafka_operator.md)**, **[Развертывание с Ansible](./kafka_ansible_deployment.md)**.

### Высокая производительность

Kafka достигает экстремальной пропускной способности благодаря следующим механизмам:
1. **Последовательный ввод-вывод (Sequential I/O):** Дописывание данных в конец лога — самая быстрая операция для физических дисков.
2. **Page Cache ОС:** Kafka активно использует кэш оперативной памяти файловой системы. Продюсер пишет в RAM, а ядро ОС в фоновом режиме сбрасывает данные на диск. Именно поэтому под heap JVM выделяют лишь часть RAM — остальное оставляют под Page Cache.
3. **Zero-Copy:** С помощью системного вызова `sendfile` данные передаются из Page Cache напрямую в сетевую карту, минуя копирование в адресное пространство приложения.
4. **Батчинг и сжатие:** Сообщения группируются в батчи и сжимаются целиком (кодеки `lz4`, `zstd`, `snappy`, `gzip`). Сжатие батча эффективнее сжатия отдельных сообщений, а распаковка происходит только на стороне конечного консьюмера — брокер передает данные «как есть».

### Хранение и очистка данных (Retention)

Данные хранятся на диске в **сегментах (log segments)**.

#### Удаление по времени или размеру (`cleanup.policy=delete`)
Политика по умолчанию. Данные удаляются целыми сегментами.
1. **Закрытие сегмента:** Происходит при достижении `segment.bytes` (по умолчанию 1 ГБ) или `segment.ms` (по умолчанию 7 дней).
2. **Удаление:** Сегмент удаляется, когда время жизни **последнего** сообщения в нем превышает `retention.ms` или общий объем партиции превышает `retention.bytes`. Активный сегмент (в который идет запись) по времени не удаляется никогда — поэтому короткий `retention.ms` при большом `segment.ms` приводит к тому, что данные фактически живут дольше заявленного.

#### Компактификация логов (`cleanup.policy=compact`)
- **Принцип:** Сохранение только последнего значения для каждого ключа. Записи с `null`-значением (tombstone) удаляют предыдущие значения ключа, затем сами вычищаются по истечении `delete.retention.ms`.
- **Применение:** Хранение состояний, справочников, настроек конфигурации. Внутренние топики Kafka (`__consumer_offsets`, `__cluster_metadata`) используют именно компактификацию.
- **Ограничение:** Топик с политикой `compact` отклоняет записи с `null`-ключом (ошибка `InvalidRecordException`) — без ключа невозможно определить, какое значение считать последним.

#### Уровневое хранение (Tiered Storage)
Разделение хранения на «горячее» (локальные диски брокеров) и «холодное» (объектные хранилища типа S3). Реализовано по KIP-405: ранний доступ с версии 3.6, **GA с версии 3.9**. Реализация хранилища подключаемая (интерфейс RemoteStorageManager), что позволяет хранить огромные объемы данных без привязки к дисковому пространству брокеров: локально остаются только горячие сегменты и индексы.

### Экосистема: Connect, Streams и межкластерная репликация

Kafka — это не только брокер, но и развитая экосистема компонентов:
1. **Kafka Connect:** Фреймворк для интеграции с внешними системами (БД, S3, Elasticsearch) без написания кода. Работает в двух режимах: `standalone` (один воркер, для разработки) и `distributed` (кластер воркеров с автоматическим перераспределением коннекторов и REST API для управления, порт 8083 по умолчанию). Коннекторы двух типов: **Source** (читают внешнюю систему и пишут в Kafka, например Debezium для захвата изменений CDC) и **Sink** (читают Kafka и пишут во внешнюю систему). Single Message Transforms (SMT) позволяют делать простые преобразования (переименование полей, маршрутизация по топику) без кода.
2. **Kafka Streams:** Библиотека для обработки потоков данных в реальном времени (фильтрация, агрегация, Join, оконные вычисления). Работает внутри обычного Java/Kotlin приложения, не требуя отдельного кластера обработки. Состояние хранится в локальных state store (RocksDB) с резервным копированием в компактные топики changelog; поддерживает exactly-once обработку через транзакции.
3. **MirrorMaker 2:** Межкластерная репликация топиков и офсетов (геораспределение, disaster recovery, миграция между датацентрами). Построена на базе Kafka Connect, поддерживает циклическую репликацию с переименованием топиков (`source.topic` → `source.topic.replica`).

**Форматы данных:** Для эволюции схем без поломки консьюмеров используется Schema Registry (Avro, Protobuf, JSON Schema) — продюсер пишет в сообщение только ID схемы, консьюмер забирает схему из реестра. Подробнее о форматах сериализации: **[Принципы работы систем обмена сообщениями](./message_queues_principles.md)**.

### Квоты и управление ресурсами

Для обеспечения стабильности в многопользовательских средах (Multi-tenancy) Kafka поддерживает квоты:
- **Network Bandwidth Quotas:** Ограничение скорости чтения/записи в байтах в секунду для конкретного пользователя или клиента.
- **Request Rate Quotas:** Ограничение процента времени CPU, которое брокер тратит на обработку запросов от клиента.
- **Storage Quotas:** Ограничение объема дискового пространства, занимаемого пользователем.

### Безопасность

Безопасность кластера строится на трех слоях, настраиваемых отдельно для каждого listener:
- **Шифрование (SSL/TLS):** Защита трафика между клиентами и брокерами, а также между самими брокерами (inter-broker communication). Возможна взаимная аутентификация сертификатами (mTLS).
- **Аутентификация (SASL):** Механизмы `PLAIN` (логин/пароль, только поверх TLS), `SCRAM-SHA-256/512` (хранение хэшей учетных данных в самом кластере), `GSSAPI` (Kerberos), `OAUTHBEARER` (интеграция с внешним OAuth/OIDC-провайдером).
- **Авторизация (ACL):** Контроль доступа к ресурсам (топики, группы, кластер, транзакционные ID) на уровне операций (Read, Write, Describe и др.). Включается параметром `authorizer.class.name`; в режиме KRaft управление правами упрощено — метаданные авторизации хранятся в том же журнале, что и остальное состояние кластера.

## Практические сценарии

### Быстрый старт: одноброкерный кластер в KRaft

**Предварительные требования:** Linux/macOS, JDK 17+ (для Kafka 4.x), распакованный официальный дистрибутив Apache Kafka. Для полноценного локального стенда с UI вместо ручного запуска удобнее **[Docker Compose](./kafka_docker_setup.md)**; ниже — минимальный запуск из дистрибутива.

```bash
# 1. Сгенерировать уникальный ID кластера
KAFKA_CLUSTER_ID="$(bin/kafka-storage.sh random-uuid)"
# → пример вывода: 5L6g3nShT-eMCtK--X86sw

# 2. Отформатировать директорию хранилища (обязательный шаг для KRaft)
bin/kafka-storage.sh format --standalone -t "$KAFKA_CLUSTER_ID" -c config/kraft/server.properties
# → Formatting /tmp/kraft-combined-logs with metadata.version 4.0-IV0.

# 3. Запустить брокер (остановка — Ctrl+C)
bin/kafka-server-start.sh config/kraft/server.properties
# → ... [KafkaRaftServer nodeId=1] Kafka Server started (kafka.server.KafkaRaftServer)

# 4. Создать тестовый топик: 3 партиции, RF=1 (для одного брокера)
bin/kafka-topics.sh --bootstrap-server localhost:9092 --create --topic orders --partitions 3 --replication-factor 1
# → Created topic orders.

# 5. Отправить два сообщения (интерактивный режим; каждая строка — отдельное сообщение, выход Ctrl+C/Ctrl+D)
bin/kafka-console-producer.sh --bootstrap-server localhost:9092 --topic orders
>order-1
>order-2

# 6. Прочитать сообщения с начала журнала (второй терминал)
bin/kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic orders --from-beginning --max-messages 2
# → order-1
# → order-2
# → Processed a total of 2 input messages to 2 output message(s) in 42 ms.

# 7. Проверить раскладку партиций, лидера и ISR
bin/kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
# → Topic: orders	TopicId: ...	PartitionCount: 3	ReplicationFactor: 1	Configs: ...
# → Topic: orders	Partition: 0	Leader: 1	Replicas: 1	Isr: 1
```

**Валидация результата:** команды шагов 4–7 обязаны вернуть вывод, приведенный в комментариях. Если клиентская команда «висит» без ответа — брокер не слушает порт: проверьте параметры `listeners` и `advertised.listeners` в `config/kraft/server.properties` и лог запуска на ошибки.

**Примечания по версиям:** команды выше работают в Kafka 3.3+. Начиная с версии 4.0 пустое хранилище форматируется автоматически при первом старте (удобно для разработки; для production рекомендуется явное форматирование с сохранением ID кластера). Для продакшн-развертывания см. также **[CLI-инструменты Kafka](./kafka_cli_tools.md)** — полный справочник команд.

**Очистка окружения:** остановите брокер (Ctrl+C) и удалите директорию данных из параметра `log.dirs` (по умолчанию `/tmp/kraft-combined-logs`) — состояние кластера вернется к исходному.

### Сценарий 1: Такси-сервис (Uber/Lyft style)

Kafka выступает в роли «супермагистрали» для движения данных между мобильными приложениями клиентов, водителей и бэкэнд-сервисами.
1. **Бронирование:** Клиент создает событие заказа. Kafka передает его ближайшим водителям.
2. **Подтверждение:** Водитель принимает заказ. Событие обновляет статус клиента и уведомляет его.
3. **Телеметрия:** Во время поездки датчики IoT передают данные о маршруте, скорости и пробках в реальном времени для оптимизации пути и расчета стоимости.
4. **Завершение:** Финальное событие инициирует списание средств и обновление баланса водителя.

### Сценарий 2: Финансовый шлюз (Real-time Transaction Processing)

Все виды транзакций (карты, онлайн-банкинг, банкоматы) обрабатываются как поток событий.
1. **Transaction Topic:** Единый вход для всех операций.
2. **Compliance & Fraud:** Параллельные консьюмеры проверяют транзакцию на соответствие правилам и наличие признаков мошенничества.
3. **Account Update:** Если проверка пройдена, обновляется баланс аккаунта.
4. **Notifications:** Пользователь мгновенно получает push-уведомление о списании.

### Сценарий 3: Зарядные станции для электромобилей (EV Charging)

Использование датчиков IoT для мониторинга и биллинга.
1. **Station Status:** Реальное время — свободна станция или занята. Данные агрегируются в приложении пользователя для поиска зарядки.
2. **Charging Session:** Учет времени и объема потребленной энергии.
3. **Payment System:** После завершения зарядки данные уходят в биллинг для формирования счета.

### Гарантии доставки (acks)

Продюсер настраивает уровень надёжности через параметр `acks`. Подробное описание семантик At-most-once, At-least-once и Exactly-once — в **[Гарантии доставки](./delivery_guarantees.md)**.

| Значение | Описание | Риск потери | Производительность | Применение |
| :--- | :--- | :--- | :--- | :--- |
| `acks=0` | «Выстрелил и забыл». Продюсер не ждет ответа от брокера. | Высокий | Максимальная | Сбор некритичных метрик |
| `acks=1` | Подтверждение только от лидера. | Небольшой | Высокая | Большинство стандартных задач |
| `acks=all` | Подтверждение от лидера и всех ISR. | Минимальный | Низкая | Финансовые транзакции, аудит |

**Базовая надежная конфигурация продюсера (актуально для Kafka 3.0+):**

```properties
# Идемпотентный продюсер включен по умолчанию с версии 3.0 (KIP-679).
# Он автоматически задает: acks=all, retries=Integer.MAX_VALUE,
# max.in.flight.requests.per.connection<=5 — без риска нарушения порядка.
enable.idempotence=true

# Сжатие батчей целиком (экономия сети и диска на стороне брокера)
compression.type=lz4

# Накопление батча: ждать до 20 мс и собирать пакеты до 32 КБ
linger.ms=20
batch.size=32768

# Общий лимит на доставку сообщения (время отправки + все ретраи)
delivery.timeout.ms=120000
```

### Надежная конфигурация консьюмера

Для семантики At-least-once с идемпотентной обработкой (рекомендуемый промышленный стандарт):

```properties
group.id=orders-processor

# Ручной коммит: офсет фиксируется ТОЛЬКО после успешной обработки записи.
# Auto-commit здесь опасен: консьюмер может закоммитить еще необработанную пачку
# и потерять данные при падении до завершения обработки.
enable.auto.commit=false

# Поведение при отсутствии закоммиченного офсета (новая группа или утраченные данные):
# earliest — читать с начала журнала, latest — только новые сообщения.
auto.offset.reset=earliest

# Не видеть транзакционные записи, которые ещё не зафиксированы (для EOS-продюсеров)
isolation.level=read_committed

# Инкрементальная ребалансировка без stop-the-world (см. раздел Rebalancing)
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# Таймауты: запас на GC-паузы и сетевые проблемы, чтобы избежать ложных ребалансировок
session.timeout.ms=45000

# Максимум времени между вызовами poll() при долгой обработке;
# превышение = консьюмер считается умершим, запускается ребалансировка
max.poll.interval.ms=300000
max.poll.records=500
```

**Режимы коммита:** `commitSync()` — блокирует поток и гарантированно подтверждает офсет (надежнее, но медленнее); `commitAsync()` — не блокирует, но при сбое прогресс может быть потерян (консьюмер перечитает сообщения — безопасно при идемпотентной обработке). Типовая комбинация: `commitAsync()` в основном цикле плюс финальный `commitSync()` при закрытии консьюмера.

### Распределение нагрузки с помощью Consumer Groups

Kafka автоматически распределяет партиции между консьюмерами в одной группе.

**Ключевые правила:**
- Каждая партиция назначается строго одному консьюмеру в группе в конкретный момент времени.
- Один консьюмер может обрабатывать несколько партиций.
- Если консьюмеров больше, чем партиций — «лишние» будут простаивать (статус `IDLE`).
- **Рекомендация:** Количество активных консьюмеров в группе должно быть меньше или равно количеству партиций в топике.

### Батчинг и буферизация

Kafka выступает в роли «амортизатора» между источниками и системами хранения:
1. **Сглаживание пиков:** Продюсеры могут генерировать всплески событий. Kafka сохраняет их в журнале, не перегружая медленные системы (например, реляционные БД).
2. **Батчинг на запись:** Консьюмеры (например, для ClickHouse или Elasticsearch) считывают данные пачками. Запись одного большого батча в БД в десятки раз эффективнее, чем запись сообщений по одному.
3. **Надежность логов:** Использование Kafka как буфера для логов (через Vector или Logstash) гарантирует, что логи не потеряются при временном сбое в ELK-стеке.

### Мониторинг здоровья кластера

Главная операционная метрика — **Consumer Lag** (отставание консьюмера от конца журнала):

```bash
# Проверка лагов группы (самая частая диагностическая операция)
bin/kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group orders-processor
# → GROUP             TOPIC    PARTITION  CURRENT-OFFSET  LOG-END-OFFSET  LAG   CONSUMER-ID
# → orders-processor  orders   0          15234           15240           6     consumer-1-a3f...
# → orders-processor  orders   1          9811            9811            0     consumer-2-b7c...
```

**Ключевые метрики JMX/Prometheus:**

| Метрика | Здоровое значение | Интерпретация отклонения |
| :--- | :--- | :--- |
| `UnderReplicatedPartitions` | `0` | Реплики не успевают за лидером: проблема диска, сети или упавший брокер. |
| `ActiveControllerCount` | `1` на весь кластер | `0` — нет контроллера (паралич кластера); `>1` — расщепление управления. |
| `RequestHandlerAvgIdlePercent` | `> 0.3` | Низкая простая очередь потоков = брокер перегружен запросами. |
| Consumer Lag (на группу) | Стабильно около нуля | Рост — консьюмеры не успевают: масштабировать группу или оптимизировать обработку. |
| Disk usage (по `log.dirs`) | `< 80%` | Переполнение диска блокирует запись; проверить retention. |

Детальный список метрик и алертинг: **[Kafka для мониторинга](./kafka_for_monitoring.md)**.

### Типичные проблемы и диагностика

| Симптом | Вероятная причина | Диагностика и решение |
| :--- | :--- | :--- |
| **Растет Consumer Lag** | Консьюмер не успевает обрабатывать поток. | `kafka-consumer-groups.sh --describe` — найти лагающую партицию. Добавить консьюмеров (до числа партиций), ускорить обработку, вынести тяжелые операции в асинхронные воркеры. |
| **Частые ребалансировки** | Медленная обработка превышает `max.poll.interval.ms`, GC-паузы или нестабильная сеть выбивают консьюмеров из группы. | Логи консьюмера на предмет `Attempt to heartbeat failed`; увеличить `max.poll.interval.ms` и `session.timeout.ms`, уменьшить `max.poll.records`, включить статическое членство (`group.instance.id`). |
| **Ошибка продюсера `NOT_ENOUGH_REPLICAS`** | Число ISR упало ниже `min.insync.replicas` (например, упал брокер при RF=3 и `min.insync.replicas=2`). | Проверить ISR: `kafka-topics.sh --describe`. Восстановить брокер; не снижать `min.insync.replicas` — это защита от потери данных. |
| **`UnderReplicatedPartitions > 0` постоянно** | Медленный диск, деградация сети или отставание follower. | Сравнить метрики диска на лидере и follower; проверить пропускную способность репликации; при недавнем reassign — не снят ли throttle. |
| **Нарушение порядка при ретраях** | `retries > 0` с `enable.idempotence=false` и `max.in.flight > 1`: неудачная отправка повторяется позже, чем уходят следующие. | Включить идемпотентность (`enable.idempotence=true`) — она гарантирует порядок при ретраях. |
| **Диск заполнен, данные не удаляются** | Retention не работает: активный сегмент не закрывается (`segment.ms` велик), либо политика топика переопределена. | Проверить `cleanup.policy` топика и время создания старейших файлов в `log.dirs`. Уменьшить `segment.ms`/`segment.bytes`, чтобы сегменты закрывались чаще. |
| **Консьюмер падает на одном сообщении (poison pill)** | Сообщение не десериализуется, группа циклически падает и ребалансируется. | Обернуть десериализацию в try/catch и отправлять битые записи в отдельный топик (DLQ-паттерн) с исходными данными в headers. |
| **Продюсер получает `UNKNOWN_TOPIC_OR_PARTITION` после создания топика** | Метаданные о новом топике еще не распространились по кластеру. | Нормальное поведение: настроить retry/backoff у продюсера (`retry.backoff.ms`), повторить отправку. |

### Ограничения и краевые случаи

- **Порядок только внутри партиции:** глобального порядка по топику нет. Для упорядоченной обработки объекта используйте его идентификатор как ключ. Для сообщений без ключа порядок между объектами не гарантируется вовсе (sticky-партиционер выбирает партицию по своему усмотрению).
- **Изменение числа партиций ломает соответствие ключ → партиция:** `hash(key) % N` меняет результат при росте N, поэтому сообщения одного ключа временно попадают в разные партиции. Увеличивайте число партиций до ожидаемого максимума заранее.
- **Большие сообщения:** лимит по умолчанию ~1 МБ (`message.max.bytes` у брокера, `max.request.size` у продюсера, `fetch.max.bytes` у консьюмера). Увеличивать лимиты следует осторожно (растет память fetch-буферов); каноничное решение — паттерн Claim Check: данные в объектном хранилище, в событии только ссылка. Подробнее: **[ISR и репликация](./kafka_isr_replication.md)**.

#### Large Messages: настройка и паттерны

**Проблема:** Стандартный лимит 1 МБ на сообщение недостаточен для некоторых сценариев (изображения, документы, большие JSON).

**Уровни ограничений:**
| Уровень | Параметр | По умолчанию | Описание |
|---------|----------|--------------|----------|
| Producer | `max.request.size` | 1 МБ | Максимальный размер запроса на запись |
| Broker | `message.max.bytes` | 1 МБ | Максимальный размер сообщения на брокере |
| Consumer | `fetch.max.bytes` | 50 МБ | Максимальный размер fetch ответа |
| Consumer | `max.partition.fetch.bytes` | 1 МБ | Максимальный размер данных с партиции |

**Рекомендуемая конфигурация для больших сообщений (10 МБ):**
```properties
# Producer
max.request.size=10485760

# Broker (в server.properties)
message.max.bytes=10485760

# Consumer
fetch.max.bytes=10485760
max.partition.fetch.bytes=10485760
```

**Паттерн Claim Check (рекомендуется для сообщений > 10 МБ):**
```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│ Large File  │────▶│ Object      │────▶│ Kafka       │
│ (100 MB)    │     │ Storage     │     │ (reference) │
└─────────────┘     │ (S3, GCS)   │     └─────────────┘
                    └─────────────┘
```

**Когда увеличивать лимиты вместо Claim Check:**
- Сообщения 1-10 МБ и Claim Check невозможен
- Критична задержка (дополнительный сетевой ход к хранилищу недопустим)

**Риски увеличения лимитов:**
- Увеличение использования памяти на брокере (буферы fetch)
- Увеличение времени сжатия/распаковки
- Увеличение времени передачи по сети
- **Exactly-once ограничен экосистемой Kafka:** транзакции дают exactly-once при чтении внутри Kafka (read_committed) и в Kafka Streams. Сквозная гарантия до внешней системы (БД, S3) требует идемпотентной записи на стороне приемника. Разбор: **[Гарантии доставки](./delivery_guarantees.md)**.
- **Параллелизм группы ограничен числом партиций:** классическое ограничение для задач типа Competing Consumers. С версии **4.2 (2026) production-ready статус получили Share Groups (KIP-932, «Queues for Kafka»)**: очередь-семантика поверх партиций с посообщным подтверждением (`group.protocol=share`), где сообщения одной партиции могут распределяться между несколькими консьюмерами.
- **Over-partitioning:** каждая партиция стоит памяти (индексы), файловых дескрипторов и нагрузки на контроллер. Тысячи партиций на брокера увеличивают время восстановления после сбоя. Расчет баланса: **[Партиционирование и балансировка](./partitioning_and_balancing.md)**.
