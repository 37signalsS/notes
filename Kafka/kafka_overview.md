# Обзор Apache Kafka

**Актуально для:** Apache Kafka 3.9.x / 4.0.x (KRaft)

**Apache Kafka** — распределённая стриминговая платформа для построения высокопроизводительных конвейеров данных (data pipelines), потоковой обработки и асинхронной интеграции сервисов. В отличие от традиционных брокеров сообщений, Kafka спроектирована как горизонтально масштабируемый, отказоустойчивый и неизменяемый распределенный журнал (append-only log), гарантирующий долговременное хранение, высокую пропускную способность и возможность многократного повторного чтения событий.

---

## Определения

- **Событие (Event / Record):** Атомарная единица данных в Kafka, фиксирующая факт произошедшего действия. Состоит из ключа (key), значения (value), временной метки (timestamp) и служебных заголовков (headers). Ключ и значение хранятся как массивы байт (`byte[]`).
- **Стриминг событий (Event Streaming):** Непрерывная публикация, сохранение и обработка потоков событий в реальном времени.
- **Брокер (Broker):** Экземпляр серверного процесса Kafka, отвечающий за прием, хранение и выдачу сообщений клиентам. Кластер состоит из одного или нескольких брокеров, распределяющих между собой нагрузку по хранению партиций.
- **Топик (Topic):** Именованный логический поток сообщений, в который продюсеры записывают, а консьюмеры считывают данные. Топик не навязывает схему записям: брокер хранит полезную нагрузку как произвольные байтовые массивы без валидации бизнес-формата.
- **Партиция (Partition):** Базовая единица параллелизма и физического шардирования топика. Представляет собой строго упорядоченный, неизменяемый журнал записей на диске. Порядок сообщений гарантируется строго в пределах одной партиции.
- **Смещение (Offset):** Уникальный монотонно возрастающий целочисленный идентификатор записи в пределах конкретной партиции. Используется консьюмерами для отслеживания текущей позиции чтения.
- **Log End Offset (LEO):** Офсет следующей записи, которая будет добавлена в локальный лог брокера (позиция последней физически записанной репликой строки).
- **High Watermark (HW):** Наивысший офсет записи, успешно реплицированной на все активные синхронные реплики (ISR). Консьюмеры могут читать сообщения только до значения High Watermark, что предотвращает чтение данных, которые могут быть утрачены при смене лидера партиции.
- **Consumer Lag:** Разница между последним записанным офсетом в партиции (LEO) и последним зафиксированным смещением (committed offset) группы консьюмеров. Главная метрика отставания обработки.
- **Продюсер (Producer):** Клиентское приложение, публикующее записи в топики Kafka. Определяет целевую партицию по ключу сообщения или с помощью алгоритма Sticky Partitioner.
- **Консьюмер (Consumer):** Клиентское приложение, подписывающееся на топики и считывающее записи по смещениям.
- **Группа потребителей (Consumer Group):** Множество процессов-консьюмеров с общим `group.id`, совместно читающих один или несколько топиков. Каждая партиция назначается строго одному консьюмеру группы в конкретный момент времени.
- **Репликация (Replication):** Механизм отказоустойчивости, дублирующий партиции между независимыми брокерами. Каждая партиция имеет одну реплику-лидера (Leader) и несколько реплик-последователей (Followers).
- **Синхронные реплики (ISR — In-Sync Replicas):** Список реплик партиции (включая лидера), которые не отстают от лидера дольше интервала `replica.lag.time.max.ms`. Новый лидер выбирается только из состава ISR.
- **KRaft (Kafka Raft Metadata Mode):** Встроенный протокол распределенного консенсуса на базе Raft, полностью заменивший внешнюю зависимость от Apache ZooKeeper. Метаданные кластера хранятся во внутреннем изолированном журнале `@metadata`. ZooKeeper объявлен устаревшим в 3.5 и полностью удален из дистрибутива в Kafka 4.0.
- **Контроллер (Controller):** Узел кластера, входящий в кворум KRaft и управляющий метаданными (регистрация брокеров, создание топиков, назначение лидеров партиций).
- **Purgatory (Чистилище):** Внутрипамяточная структура брокера на базе многоуровневых колес таймеров (Hierarchical Timing Wheels), предназначенная для асинхронного удержания отложенных запросов (delayed produce/fetch) без блокировки рабочих потоков ввода-вывода.
- **Log Cleaner:** Фоновый поток брокера, выполняющий очистку и слияние устаревших сегментов журнала в топиках с политикой `cleanup.policy=compact`.
- **Сегмент (Log Segment):** Физический файл на файловой системе брокера (`.log` и вспомогательные индексы `.index`, `.timeindex`), на которые нарезается журнал партиции. Ротация и удаление данных происходят на уровне сегментов.
- **Tombstone (Надгробие):** Запись с ненулевым ключом и значением `null`, отправляемая в топик с политикой `compact` для явного удаления ключа при следующей компактификации.
- **Bootstrap-сервер:** Первоначальный адрес подключения клиента, используемый исключительно для запроса топологии и метаданных кластера (`MetadataRequest`), после чего клиент взаимодействует с лидерами партиций напрямую.

## Архитектура и основные концепции

### История и предпосылки

Apache Kafka создана в LinkedIn в 2011 году (с 2012 года — проект верхнего уровня Apache Software Foundation) для решения проблем масштабирования традиционных шин сообщений и брокеров очередей (RabbitMQ, ActiveMQ, IBM MQ) в условиях экстремальных нагрузок.

**Ограничения классических очередей при высоких нагрузках:**
1. **Удаление после прочтения:** В классической очереди сообщение удаляется сразу после подтверждения (ack). Это делает невозможным независимое чтение одного и того же потока событий десятками разных сервисов без создания копий очередей (fan-out exchange).
2. **Отсутствие воспроизводимости (Replay):** Невозможно «отмотать» чтение назад после исправления бага в сервисе или для пересчета исторической аналитики.
3. **Вертикальное масштабирование:** Традиционные очереди хранят сообщения в сложных структурах данных в оперативной памяти (деревья, списки индексов). При накоплении миллионов невычитанных сообщений производительность деградирует из-за вытеснения страниц на диск.
4. **Жесткая связанность (Tight Coupling):** Прямые синхронные вызовы между сервисами (REST, gRPC) приводят к каскадным сбоям и неконтролируемому обратному давлению (backpressure).

**Архитектурное решение Kafka:** Замена изменяемых очередей неизменяемым распределенным журналом упреждающей записи (append-only log). Продюсеры только дописывают данные в конец файла, а консьюмеры независимо перемещают свои указатели смещений (offsets).

```
                      ┌─────────────────────────────────────────┐
                      │             Apache Kafka                │
                      │ ┌─────────────────────────────────────┐ │
┌───────────┐         │ │              Топик                  │ │         ┌─────────────┐
│ Продюсер  ├─────────┼─┼─► [0] [1] [2] [3] [4] [5] [6] [7]... │ ┼────────►│ Консьюмер 1 │
│  (Write)  │         │ └─────────────────────────────────────┘ │ (Read)  │ (Offset: 7) │
└───────────┘         │                                         │         └─────────────┘
                      │                                         │         ┌─────────────┐
                      │                                         │         │ Консьюмер 2 │
                      │                                         │ ┼──────►│ (Offset: 3) │
                      └─────────────────────────────────────────┘ (Replay)└─────────────┘
```

### Критерии выбора Kafka

| Сценарий | Рекомендуемое решение | Причина |
| :--- | :--- | :--- |
| Простая очередь задач для фоновых воркеров, маршрутизация по шаблонам (Routing Key), Dead Letter Exchange на уровне брокера | RabbitMQ / Redis | Минимальный операционный оверхед, встроенная сложная маршрутизация, низкие требования к инфраструктуре |
| Поток событий для множества независимых потребителей (Pub/Sub), хранение истории, воспроизводимость (Replay), миллионы сообщений/сек | **Apache Kafka** | Append-only log, неизменяемость, масштабирование через партиционирование, независимые офсеты |
| Change Data Capture (CDC из PostgreSQL/MySQL через Debezium) | **Apache Kafka** | Гарантия строгого порядка изменений строк по первичному ключу внутри партиции |
| Хранение логов и трейсов перед загрузкой в ClickHouse / Elasticsearch / OpenSearch | **Apache Kafka** | Буферизация всплесков трафика (backpressure buffer), батчинг на стороне консьюмеров |

### Фундаментальное отличие от классических очередей

| Аспект | Классическая очередь (RabbitMQ / JMS) | Apache Kafka (Log-centric) |
| :--- | :--- | :--- |
| **Модель хранения** | Сообщение уничтожается после подтверждения (`ack`) | Сообщения сохраняются на диске в пределах настроенного retention |
| **Позиция чтения** | Управляется брокером (указатель головы очереди) | Управляется клиентом через числовой офсет (`offset`) |
| **Множественные получатели** | Требуется дублирование сообщений в разные очереди | Все консьюмер-группы читают один и тот же неизменяемый журнал |
| **Повторное чтение (Replay)** | Невозможно | Произвольный сброс смещения (`seek to offset/timestamp`) |
| **Порядок доставки** | Глобальный в очереди, но нарушается при nack/reject | Строгий порядок гарантирован **в пределах партиции** |
| **Масштабирование чтения** | Конкурирующие консьюмеры читают из одной очереди | Параллелизм жестко ограничен числом партиций топика |

### Масштаб использования в индустрии

Показатели промышленных on-premise и bare-metal инсталляций:
- **LinkedIn:** свыше 1 400 брокеров, более 1.4 триллиона сообщений в сутки, средняя задержка доставки < 5 мс.
- **Netflix:** более 4 000 брокеров в десятках кластеров, транзитный поток более 1 триллиона событий в день.
- **Крупные финансовые организации и банки:** ядра процессинга транзакций, аудит-логирование, антифрод в реальном времени с гарантиями `acks=all` и нулевой потерей данных.

**Производительность современного узла на bare-metal (Linux, NVMe, 10/25GbE):**
- Пропускная способность на запись: от 200 до 800 МБ/с на брокер (до 1 000 000 msg/sec).
- Сетевая задержка доставки (End-to-End Latency): 3–8 мс при включенном батчинге и fsync через Page Cache.
- Лимит партиций: до 10 000–15 000 активных партиций на брокер в режиме KRaft без деградации кворума.

### Архитектура KRaft (Kafka Raft)

Режим KRaft (Kafka Raft Metadata Mode, KIP-500) заменил внешнюю координацию через ZooKeeper. Состояние кластера хранится в специальном служебном топике `@metadata` (однопартиционный лог с кворумной репликацией Raft).

```
┌───────────────────────────────────────────────────────────────────┐
│                      KRaft Controller Quorum                      │
│                                                                   │
│  ┌───────────────────┐  Raft Consensus  ┌───────────────────┐     │
│  │   Controller 1    │◄────────────────►│   Controller 2    │     │
│  │   (Active Leader) │                  │    (Follower)     │     │
│  └─────────┬─────────┘                  └─────────┬─────────┘     │
│            │                                      │               │
│            └───────────────────┬──────────────────┘               │
│                                │ Raft Replication                 │
│                                ▼                                  │
│                     ┌───────────────────┐                         │
│                     │   Controller 3    │                         │
│                     │    (Follower)     │                         │
│                     └───────────────────┘                         │
└───────────────────────────────────┬───────────────────────────────┘
                                    │ Metadata Updates
                                    ▼
┌───────────────────────────────────────────────────────────────────┐
│                           Brokers Pool                            │
│                                                                   │
│  ┌───────────────────┐  ┌───────────────────┐  ┌────────────────┐ │
│  │   Broker ID=101   │  │   Broker ID=102   │  │  Broker ID=103 │ │
│  │ (User Partitions) │  │ (User Partitions) │  │(User Partitions│ │
│  └───────────────────┘  └───────────────────┘  └────────────────┘ │
└───────────────────────────────────────────────────────────────────┘
```

**Ключевые преимущества KRaft:**
1. **Устранение внешнего SPOF и рассогласования метаданных:** Отсутствует рассинхронизация между состоянием брокеров и ZooKeeper. Метаданные реплицируются тем же движком, что и сообщения.
2. **Быстрое восстановление после сбоя:** Контроллеры держат метаданные в памяти и обновляют их через журнал Raft. При падении активного лидера выборы нового лидера кворума занимают десятки миллисекунд (в ZooKeeper перезагрузка дерева метаданных занимала минуты).
3. **Поддержка миллионов партиций:** Кластер масштабируется до сотен тысяч и миллионов партиций благодаря локальному чтению метаданных каждым брокером.
4. **Упрощение эксплуатации:** Единый бинарный файл, единые порты, единая модель аутентификации и ACL, администрируемые через стандартные утилиты Kafka.

> **Статус версий:** ZooKeeper объявлен устаревшим в Apache Kafka 3.5 (2023) и **полностью удален в релизе 4.0**. Кластеры линейки 4.x работают исключительно на базе KRaft. Требуется OpenJDK 17 LTS или 21 LTS (поддержка Java 8 и 11 удалена).

### Потоковая модель брокера и жизненный цикл запроса

Обработка сетевого ввода-вывода в брокере построена на шаблоне Reactor (Java NIO) и пулах специализированных потоков, разделяющих сетевой обмен и работу с дисковой подсистемой:

```
[TCP Клиент] ──SYN──► [Acceptor Thread] (1 на порт)
                             │
                             ▼ Round-Robin
                      [Network Threads] (num.network.threads)
                             │  (Чтение фрейма, десериализация)
                             ▼
                      [RequestQueue] (queued.max.requests, блокирующая очередь)
                             │
                             ▼ Dequeue
                      [I/O Threads] (num.io.threads)
                             │  (Бизнес-логика, запись в Page Cache)
                             ├──────────────────────────┐
                             ▼ (Завершенные запросы)    ▼ (Отложенные запросы)
                      [ResponseQueue]             [Purgatory]
                             │                          │ (acks=all кворум /
                             ▼                          ▼  fetch.min.bytes)
                      [Network Threads] ◄───────────────┘
                             │
                             ▼ (sendfile / Zero-Copy)
[TCP Клиент] ◄───────────────┘
```

1. **Acceptor Thread:** Один поток на каждый сетевой listener. Принимает входящие TCP-соединения (`accept`) и регистрирует их в сетевых процессорах.
2. **Network Processors (`num.network.threads`):** Неблокирующие потоки Java NIO. Читают входящие байты из сокетов, парсят заголовки и помещают готовые запросы в общую очередь `RequestQueue`.
3. **Request Handler Pool (`num.io.threads`):** Рабочие потоки обработки. Забирают запросы из очереди, выполняют валидацию, обращаются к локальным логам через системный вызов `write()` (в Page Cache ядра Linux) и генерируют ответы.
4. **Purgatory:** Если запросу требуется ожидание внешнего события (например, `acks=all` ждет подтверждения от реплик-последователей, а `FetchRequest` ждет накопления байт), он помещается в Purgatory без блокировки потоков `num.io.threads`.
5. **Response Queue & Отправка:** Ответ возвращается в очередь соответствующего сетевого процессора, который отправляет его клиенту. Чтение данных из сегментов для консьюмеров использует Zero-Copy.

Подробнее о расчете и метриках очередей: **[Thread Model брокера](./kafka_broker_thread_model.md)**.

### Высокая производительность и подсистема ввода-вывода

Феноменальная скорость работы Kafka достигается за счет синергии архитектуры приложения и механизмов ядра Linux:

1. **Последовательный ввод-вывод (Sequential I/O):** Дозапись в конец неизменяемого лога выполняется со скоростью физической шины диска (для NVMe/SSD — гигабайты в секунду), полностью исключая случайные позиционирования головок и перестроения индексов.
2. **Делегирование кэширования ядру Linux (Page Cache):** Kafka не дублирует данные сообщений в куче JVM. Брокер выделяет под Java Heap лишь 6–10 ГБ (для хранения метаданных, кэша соединений и Purgatory), а 70–80% оперативной памяти сервера оставляет операционной системе под файловый Page Cache. Запись выполняется в память через системный вызов `write()`, а фоновый сброс страниц на накопитель выполняет ядро Linux (`flusher threads`).
3. **Zero-Copy (`sendfile`):** При чтении данных консьюмером байты передаются из Page Cache напрямую в сетевой сокет через системный вызов `sendfile(2)`, минуя копирование в адресное пространство пользователя JVM и экономя такты процессора.
4. **Батчинг и сквозное сжатие:** Продюсер собирает сообщения в батчи (`batch.size`, `linger.ms`) и сжимает их целиком (кодеки `lz4`, `zstd`, `snappy`). Брокер записывает сжатый батч на диск «как есть», не распаковывая его. Декомпрессия выполняется только на стороне конечного консьюмера.

Низкоуровневые параметры ядра и памяти: **[OS тюнинг для Apache Kafka](./kafka_os_tuning.md)**.

### Партиционирование для масштабируемости

Топик состоит из одной или нескольких независимых партиций. Партиция — неделимая единица параллелизма:
- **Сообщение с ключом:** Хэш ключа вычисляется по алгоритму `MurmurHash2`:
  $$\text{Partition} = \operatorname{abs}(\operatorname{MurmurHash2}(\text{key})) \pmod{\text{TotalPartitions}}$$
  Все события с одинаковым ключом гарантированно направляются в одну и ту же партицию, что обеспечивает строгий порядок их обработки.
- **Сообщение без ключа (`key = null`):** Начиная с KIP-480 и KIP-794 используется **Sticky Partitioner**: продюсер наполняет батч для одной партиции, а после его отправки переключается на следующую. Это максимизирует плотность сжатия и снижает сетевые задержки по сравнению со старым циклическим Round-Robin.

Расчет количества партиций и борьба с перекосами: **[Партиционирование и балансировка](./partitioning_and_balancing.md)**.

### Управление смещениями и группами потребителей (Consumer Groups)

Группа консьюмеров (`Consumer Group`) обеспечивает масштабируемое параллельное чтение топиков:

```
                      Топик: orders (4 партиции)
          ┌─────────────┬─────────────┬─────────────┬─────────────┐
          │ Партиция 0  │ Партиция 1  │ Партиция 2  │ Партиция 3  │
          └──────┬──────┴──────┬──────┴──────┬──────┴──────┬──────┘
                 │             │             │             │
                 ▼             ▼             │             │
          ┌─────────────┐┌─────────────┐     │             │
          │ Консьюмер 1 ││ Консьюмер 2 │     └──────┬──────┘
          └─────────────┘└─────────────┘            │
                 ▲             ▲                    ▼
                 │             │             ┌─────────────┐
                 │             │             │ Консьюмер 3 │
                 │             │             └─────────────┘
                 └─────────────┴────────────────────┘
                  Consumer Group: "orders-workers"
```

**Правила распределения:**
1. Каждая партиция назначается строго одному консьюмеру внутри конкретной группы.
2. Один консьюмер может обрабатывать несколько партиций одновременно.
3. Если консьюмеров больше, чем партиций топика, «лишние» консьюмеры переходят в состояние ожидания (`IDLE`).
4. Независимые группы (`group.id = "billing"`, `group.id = "analytics"`) читают один и тот же топик параллельно, храня собственные офсеты.

**Хранение смещений:** Офсеты сохраняются во внутреннем компактном топике `__consumer_offsets` (по умолчанию 50 партиций). Ключ записи — кортеж `[Group, Topic, Partition]`, значение — текущий подтвержденный офсет и метаданные коммита.

**Эволюция протоколов групп:**
- **Классический протокол (Client-driven):** Консьюмер-лидер группы получает список участников от брокера (Group Coordinator), локально вычисляет распределение партиций по выбранной стратегии (Range, RoundRobin, CooperativeSticky) и возвращает план координатору.
- **Новый протокол групп (KIP-848, Generally Available с Kafka 4.0):** Логика назначения перенесена на сторону брокера-координатора. Устраняются тяжелые Stop-the-world паузы, ребалансировка становится инкрементальной и прозрачной. Включается на клиентах параметром `group.protocol=consumer`.
- **Share Groups (KIP-932, доступно с Kafka 4.2):** Семантика очередей («Queues for Kafka») с подтверждением доставки отдельных сообщений (`ack/nack`) нескольким параллельным консьюмерам из одной партиции без привязки партиция-к-воркеру.

### Процесс перебалансировки (Rebalancing)

Перебалансировка запускается при изменении состава группы: падении воркера, добавлении нового инстанса, перезапуске пода или изменении числа партиций.

**Стратегии ребалансировки:**
1. **Eager Rebalance (устаревшая):** При любой смене состава все участники группы останавливают потребление, отзывают все назначенные партиции и переподключаются заново (Stop-the-world пауза). Приводит к скачкам Consumer Lag.
2. **Cooperative Sticky Rebalance (рекомендуемая в 3.x/4.x):** Инкрементальное переназначение (`org.apache.kafka.clients.consumer.CooperativeStickyAssignor`). Отзываются только те партиции, которые физически перемещаются на другой узел. Остальные консьюмеры продолжают непрерывную обработку.
3. **Статическое членство (Static Membership, KIP-345):** Консьюмеру задается уникальный идентификатор `group.instance.id`. При плановом перезапуске процесса (в пределах `session.timeout.ms`) брокер не запускает ребалансировку, сохраняя партиции за данным инстансом. Критически важно для Kubernetes и контейнерных сред.

### Репликация, отказоустойчивость и ISR

Отказоустойчивость обеспечивается репликацией партиций по формуле кворумного согласования:
- **Лидер (Leader):** Обрабатывает все клиентские операции записи и чтения.
- **Последователи (Followers):** Фоновые потоки `num.replica.fetchers` копируют байты из лога лидера.
- **Механизм ISR (In-Sync Replicas):** Реплика считается синхронной, если время с ее последнего успешного `FetchRequest` не превышает `replica.lag.time.max.ms` (по умолчанию 30 000 мс). Если узел отстает из-за деградации диска или сети, он исключается из ISR (ISR shrink). При восстановлении темпа узел возвращается в ISR (ISR expand).
- **Критический параметр `min.insync.replicas`:** Минимальное количество синхронных реплик (включая лидера), подтвердивших запись при `acks=all`. Если в живых осталось меньше ISR, чем `min.insync.replicas`, брокер отклоняет запросы продюсеров с ошибкой `NOT_ENOUGH_REPLICAS`, предотвращая запись данных под угрозой их последующей утраты.

Детальный разбор failover и репликации: **[ISR и репликация](./kafka_isr_replication.md)**.

### Гарантии доставки и семантика подтверждений (acks)

Продюсер настраивает баланс надежности и производительности параметром `acks`:

| Уровень `acks` | Описание механизма | Риск потери данных | Производительность | Применение |
| :--- | :--- | :--- | :--- | :--- |
| `acks=0` | Продюсер отправляет пакет по TCP и не ждет подтверждения от брокера | Высокий (при сетевом сбое или аварии брокера данные теряются) | Максимальная | Некритичные метрики, телеметрия, дебаг-логи |
| `acks=1` | Подтверждение возвращается после локальной записи в Page Cache лидера | Умеренный (при падении лидера до синхронизации репликами) | Высокая | Стандартные фоновые события, допускающие потерю |
| `acks=all` (`-1`) | Подтверждение возвращается только после синхронизации всеми узлами из ISR | Нулевой (при `min.insync.replicas=2` и RF=3) | Оптимальная для enterprise | Финансовые платежи, биллинг, заказы, аудит |

**Идемпотентный продюсер (`enable.idempotence=true`):** Включен по умолчанию с версии 3.0 (KIP-679). Брокер присваивает продюсеру Producer ID (PID), а каждому сообщению — монотонный порядковый номер Sequence Number. При повторной отправке из-за сетевого сбоя брокер фиксирует дубликат и отбрасывает его без дублирования в логе.

Подробный разбор семантик At-most-once, At-least-once и Exactly-once: **[Гарантии доставки](./delivery_guarantees.md)**.

### Хранение и очистка данных (Retention и сегменты)

Каждая партиция разбивается на сегменты: файл данных `.log` (по умолчанию до 1 ГБ согласно `segment.bytes`) и разреженные индексы `.index` (смещение $\to$ физическая позиция в файле) и `.timeindex` (временная метка $\to$ смещение).

**Политики очистки (`cleanup.policy`):**
1. **Удаление (`delete`, по умолчанию):** Сегменты удаляются целиком, когда время последнего сообщения превышает `retention.ms` (по умолчанию 7 дней) или общий размер партиции превышает `retention.bytes`. Активный сегмент, в который в текущий момент идет запись, не удаляется никогда.
2. **Компактификация (`compact`):** Сохранение только самого свежего значения для каждого уникального ключа. Применяется для топиков состояний (state stores), конфигурационных реестров и внутреннего топика `__consumer_offsets`. Для удаления ключа продюсер пишет tombstone (значение `null`).
3. **Комбинированная (`compact,delete`):** Лог компактифицируется по ключам, но также удаляет сегменты по таймауту.
4. **Уровневое хранение (Tiered Storage, KIP-405, GA с Kafka 3.9):** Разделение хранения на горячий локальный уровень (NVMe/SSD брокера для оперативной дозаписи и свежих консьюмеров) и холодный уровень (on-premise объектное хранилище MinIO/Ceph по интерфейсу S3 через RemoteStorageManager). Позволяет хранить терабайты истории без масштабирования дисков брокеров.

### Экосистема: Connect, Streams и MirrorMaker 2

1. **Kafka Connect:** Распределенный runtime для интеграции Kafka с внешними системами без прикладного кода:
   - **Source Connectors:** Захват данных из СУБД (Debezium CDC для PostgreSQL/MySQL), очередей или файловых хранилищ в топики.
   - **Sink Connectors:** Выгрузка данных из топиков в ClickHouse, Elasticsearch, PostgreSQL, S3/MinIO.
   - Работает в распределенном режиме (`distributed mode`), автоматически распределяя задачи (Tasks) между воркерами.
2. **Kafka Streams:** Java/Kotlin клиентская библиотека для потоковой обработки внутри микросервиса. Поддерживает фильтрацию, агрегации, оконные функции, Join нескольких потоков и локальные хранилища состояния на базе RocksDB с автоматическим бэкапом в топики changelog.
3. **MirrorMaker 2:** Инструмент межкластерной репликации и аварийного восстановления (Disaster Recovery). Обеспечивает асинхронную репликацию топиков, трансляцию офсетов консьюмеров и синхронизацию ACL между территориально распределенными дата-центрами.

### Безопасность и квоты

**Слои безопасности брокера:**
- **Шифрование транспортного уровня (TLS/SSL):** Защита межузлового трафика репликации и подключений клиентов, поддержка взаимной аутентификации по сертификатам (mTLS).
- **Аутентификация (SASL):** Механизмы `SCRAM-SHA-256` и `SCRAM-SHA-512` (хранение учетных записей внутри метаданных кластера), `GSSAPI` (Kerberos), `OAUTHBEARER` (токены JWT/OIDC) и `PLAIN` (только внутри TLS-туннеля).
- **Авторизация (ACL):** Разграничение прав на операции (`Read`, `Write`, `Create`, `Alter`, `Describe`) для ресурсов (`Topic`, `Group`, `Cluster`, `TransactionalId`). В KRaft метаданные авторизации реплицируются через журнал `@metadata`.

**Квотирование ресурсов (Quotas):**
- **Сетевые квоты:** Ограничение пропускной способности на запись и чтение в байтах в секунду на пользователя (`user`) или ID клиента (`client-id`).
- **Квоты CPU:** Ограничение процента утилизации потоков обработки брокера (`request_percentage`).

### Быстрый старт: одноброкерный кластер в KRaft

Локальный стенд на базе официального бинарного дистрибутива Apache Kafka (для демонстрации и отладки).

**Предварительные требования:**
- Linux (Ubuntu 22.04 / 24.04, Debian 12, RHEL 9 / Rocky Linux 9).
- Установленный OpenJDK 17 LTS или 21 LTS (`java -version`).
- Распакованный дистрибутив Apache Kafka в `/opt/kafka`.

```bash

# → Cluster ID: 5L6g3nShT-eMCtK--X86sw

# 2. Форматирование каталога хранения метаданных и логов
/opt/kafka/bin/kafka-storage.sh format \
  --cluster-id "$KAFKA_CLUSTER_ID" \
  --config /opt/kafka/config/kraft/server.properties
# → Formatting /tmp/kraft-combined-logs with metadata.version 4.0-IV0.

# 3. Запуск брокера в фоновом режиме
/opt/kafka/bin/kafka-server-start.sh -daemon /opt/kafka/config/kraft/server.properties

# 4. Проверка запуска процесса и открытых сетевых портов
ss -tulpn | grep 9092

  --partitions 3 --replication-factor 1

# 6. Отправка тестовых сообщений через консольный продюсер

  --topic events.orders \
  --from-beginning \
  --property "print.key=true" \

# → order_102 -> paid
# → Processed a total of 2 messages.

# → 	Topic: events.orders	Partition: 2	Leader: 1	Replicas: 1	Isr: 1
```

Эталонный конфигурационный файл для узла совмещенной роли (`broker,controller`) в трехнодовом production-кластере на базе KRaft для Linux bare-metal / VM:

```properties

process.roles=broker,controller

# Уникальный числовой ID данного узла

# Список всех контроллеров, образующих кворум Raft: node_id@host:controller_port

############################# Сетевые интерфейсы #############################
# Слушатели сокетов на локальной машине
listeners=PLAINTEXT://kafka-node1.corp:9092,CONTROLLER://kafka-node1.corp:9093

advertised.listeners=PLAINTEXT://kafka-node1.corp:9092

controller.listener.names=CONTROLLER
inter.broker.listener.name=PLAINTEXT
listener.security.protocol.map=CONTROLLER:PLAINTEXT,PLAINTEXT:PLAINTEXT,SSL:SSL,SASL_PLAINTEXT:SASL_PLAINTEXT

num.network.threads=8

############################# Хранилище логов #############################
# Директории монтирования дисков для хранения данных (JBOD через запятую)
log.dirs=/var/lib/kafka/data-disk1,/var/lib/kafka/data-disk2

num.partitions=6

# Потоки восстановления сегментов при аварийном старте и плановом сбросе

############################# Политики хранения (Retention) #############################
# Хранение сообщений по времени: 7 суток (168 часов)
log.retention.hours=168

# Максимальный размер одного сегмента: 1 ГБ
log.segment.bytes=1073741824

# Интервал проверки устаревших сегментов для удаления фоновым чистильщиком
log.retention.check.interval.ms=300000

# Политика удаления сегментов по умолчанию
log.cleanup.policy=delete

############################# Надежность и Graceful Shutdown #############################
# Запрет автоматического создания топиков (строгий production стандарт)
auto.create.topics.enable=false

# Запрет выборов несинхронизированного лидера (гарантия нулевой потери данных)
unclean.leader.election.enable=false

# Разрешение штатной миграции лидерства партиций при остановке брокера
controlled.shutdown.enable=true
controlled.shutdown.max.retries=3
controlled.shutdown.retry.backoff.ms=5000

# Таймаут выбывания реплики из ISR при отсутствии fetch-запросов
replica.lag.time.max.ms=30000
```

### Надежная конфигурация продюсера

Конфигурация продюсера, обеспечивающая семантику At-least-once без дубликатов сообщений и без риска нарушения порядка при ретраях:

```properties
# Список bootstrap-брокеров кластера
bootstrap.servers=kafka-node1.corp:9092,kafka-node2.corp:9092,kafka-node3.corp:9092

# Сериализаторы ключа и значения в массив байт
key.serializer=org.apache.kafka.common.serialization.StringSerializer
value.serializer=org.apache.kafka.common.serialization.ByteArraySerializer

# Включение идемпотентности продюсера (гарантирует acks=all, retries=MAX, max.in.flight<=5)
enable.idempotence=true
acks=all

# Максимальное количество неподтвержденных запросов на одно TCP-соединение
# При enable.idempotence=true значение до 5 сохраняет строгий порядок записей
max.in.flight.requests.per.connection=5

# Настройки батчинга: искусственная задержка до 20 мс для укрупнения пакетов
linger.ms=20
batch.size=65536

# Сквозное сжатие батчей алгоритмом LZ4 (минимальный оверхед на CPU при хорошем сжатии)
compression.type=lz4

# Общий таймаут доставки записи (время в очереди продюсера + все сетевые попытки ретраев)
delivery.timeout.ms=120000
request.timeout.ms=30000

# Объем буфера памяти продюсера для накопления сообщений (64 МБ)
buffer.memory=67108864
```

### Надежная конфигурация консьюмера

Конфигурация консьюмера для гарантированной обработки без потерь с ручной фиксацией смещений и инкрементальной ребалансировкой:

```properties
# Подключение к кластеру
bootstrap.servers=kafka-node1.corp:9092,kafka-node2.corp:9092,kafka-node3.corp:9092

# Идентификатор группы потребителей
group.id=billing-transactions-processor

# Статическое членство для предотвращения ребалансировок при рестартах подов
group.instance.id=billing-worker-node-01

# Десериализаторы
key.deserializer=org.apache.kafka.common.serialization.StringDeserializer
value.deserializer=org.apache.kafka.common.serialization.ByteArrayDeserializer

# Отключение автоматического коммита смещений: офсет фиксируется ТОЛЬКО после транзакции в БД
enable.auto.commit=false

# Действие при отсутствии сохраненного офсета (новая группа): читать журнал с самого начала
auto.offset.reset=earliest

# Чтение только зафиксированных транзакционных сообщений (изоляция от незавершенных EOS батчей)
isolation.level=read_committed

# Инкрементальная кооперативная стратегия ребалансировки без полной остановки группы
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# Таймауты жизнедеятельности воркера
session.timeout.ms=45000
heartbeat.interval.ms=15000

# Максимальное время между вызовами poll() для обработки пачки записей
# Если обработка 500 записей длится дольше — консьюмер считается зависшим
max.poll.interval.ms=300000
max.poll.records=500
```

### Настройка передачи больших сообщений (Large Messages)

По умолчанию Kafka оптимизирована для записей размером до 1 МБ (`message.max.bytes=1048576`).

**Настройка лимитов для сообщений до 10 МБ:**
```properties
# 1. На брокере (server.properties)
message.max.bytes=10485760

# 2. На продюсере (producer.properties)
max.request.size=10485760

# 3. На консьюмере (consumer.properties)
fetch.max.bytes=52428800
max.partition.fetch.bytes=10485760
```

**Архитектурный паттерн Claim Check (для объектов > 10 МБ):**
Передача файлов размером в десятки и сотни мегабайт напрямую через брокер перегружает память сетевых буферов и кэш ядра. Каноническое решение — разделение полезной нагрузки и события:

```
┌──────────────┐      1. Загрузка файла      ┌──────────────────────────────┐
│   Продюсер   ├────────────────────────────►│ On-Premise Объектное S3     │
│              │                             │ Хранилище (MinIO / Ceph RGW) │
└──────┬───────┘                             └──────────────┬───────────────┘
       │ 2. Событие с URL и метаданными                     │
       ▼                                                    │
┌──────────────┐                                            │ 4. Скачивание
│    Kafka     │                                            │    файла
│ (Топик логов)│                                            │    по ссылке
└──────┬───────┘                                            │
       │ 3. Вычитка метаданных                              │
       ▼                                                    ▼
┌──────────────┐                                     ┌──────────────┐
│  Консьюмер   │◄────────────────────────────────────┤  Консьюмер   │
│              │                                     │              │
└──────────────┘                                     └──────────────┘
```

### Бизнес-сценарии применения

1. **Сервис вызова такси и шеринга (Такси / Каршеринг):**
   - **Ingestion:** Прием сотен тысяч телеметрических точек от GPS-трекеров автомобилей в секунду в топик `telemetry.raw`.
   - **Processing:** Потоковая фильтрация и гео-индексация. Сообщения с ключом `driver_id` гарантируют хронологический порядок координат одного водителя.
   - **Fan-out:** Параллельная передача одного потока в сервис расчета стоимости поездки, сервис антифрода и долгосрочную аналитическую БД.
2. **Финансовый платежный шлюз (Банковский процессинг):**
   - Топик `payments.incoming` работает с параметрами `acks=all`, `min.insync.replicas=2`, `enable.idempotence=true`.
   - Ключ сообщения — `account_id` или `card_token`, что гарантирует строгую последовательность списаний и зачислений без гонок состояний.
   - Микросервис балансов фиксирует офсет только после подтверждения коммита в реляционной базе данных.
3. **Мониторинг промышленного оборудования (IoT Telemetry):**
   - Тысячи датчиков на промышленных объектах передают параметры давления, температуры и вибрации.
   - Kafka выступает буфером обратного давления: при всплесках трафика или задержках сервисов записи данные надежно накапливаются в журнале на дисках брокеров без отбрасывания пакетов.

## Рекомендации (Best Practices)

### Инфраструктура и оборудование (Bare-metal / VM)

1. **Оперативная память (RAM):**
   - Выделяйте процессу Kafka JVM Heap в объеме **6–10 ГБ** с сборщиком мусора G1GC.
   - Оставшиеся **60–80% физической RAM** хоста должны быть свободны от других процессов и полностью отданы операционной системе под **Page Cache ядра Linux**.
2. **Дисковая подсистема:**
   - Используйте накопители NVMe или корпоративные SSD.
   - **Kafka предпочитает JBOD аппаратному RAID:** указывайте несколько независимых точек монтирования через запятую в `log.dirs` (`log.dirs=/disk1/kafka,/disk2/kafka`). Kafka самостоятельно изолирует сбой одного диска, не останавливая работу с остальными.
   - Файловая система: строго **XFS** с опциями монтирования `noatime,nodiratime`.
3. **Сетевая инфраструктура:**
   - Выделяйте сетевые интерфейсы не менее **10 GbE** (оптимально 25 GbE с LACP-бондингом).
   - Разделяйте сетевые потоки: клиентский трафик и трафик межброкерной репликации/кворума контроллеров желательно изолировать на уровне VLAN.

### Системный тюнинг ядра Linux (OS Level)

Обязательные параметры `/etc/sysctl.d/99-kafka.conf`:
- **`vm.dirty_background_ratio = 5`** и **`vm.dirty_ratio = 10`**: Агрессивный фоновый сброс грязных страниц ядром Linux предотвращает блокирующие паузы ввода-вывода (I/O flush storms).
- **`vm.swappiness = 1`**: Запрет выгрузки страниц памяти Kafka в swap при наличии свободного Page Cache.
- **`vm.max_map_count = 1048576`**: Обеспечивает запас областей отображения памяти для тысяч сегментных индексов через `mmap`.
- **`fs.file-max = 1000000`** и `LimitNOFILE=1000000`: Защита от исчерпания файловых дескрипторов для сетевых сокетов и файлов логов.

Детальные инструкции: **[OS тюнинг для Apache Kafka](./kafka_os_tuning.md)**.

### Проектирование топиков и партиций

1. **Фактор репликации (RF):** Для production-топиков строго **`replication.factor = 3`**.
2. **Кворум подтверждения записи:** Строго **`min.insync.replicas = 2`** при `acks = all`. Это гарантирует отсутствие потерь данных даже при одновременном плановом выводе одного брокера и аварии другого.
3. **Запрет автосоздания:** Всегда выставляйте **`auto.create.topics.enable = false`**. Создание топиков должно происходить через системы автоматизации (GitOps / Terraform / Ansible / Strimzi) с контролируемым числом партиций.
4. **Предотвращение Over-Partitioning:** Не создавайте более 1 000–2 000 партиций на один физический брокер без обоснованной необходимости. Лимит на кластер — до 100 000–200 000 партиций.

### Эксплуатация и регламенты SRE

1. **Регламент планового перезапуска (Rolling Restart):**
   - **Шаг 1:** Проверить статус метаданных: `/opt/kafka/bin/kafka-metadata-quorum.sh describe --status`.
   - **Шаг 2:** Перезапускать контроллеры по одному. После рестарта каждого контроллера дожидаться полного выравнивания `MaxFollowerLag = 0`.
   - **Шаг 3:** Перезапускать брокеры по одному.
   - **Шаг 4:** Перед остановкой следующего брокера **обязательно** дождаться, пока метрика `UnderReplicatedPartitions` вернется в строгое значение `0`.
2. **Штатный Graceful Shutdown:**
   - Убедитесь, что в конфигурации включен `controlled.shutdown.enable = true`.
   - В юнитах systemd обязательно задавайте `TimeoutStopSec = 180` (или более), чтобы процесс успел передать лидерство партиций соседям и записать маркер `clean-shutdown-marker`, исключая долгий этап Log Recovery при следующем старте.
3. **Приоритеты мониторинга и алертинга:**
   - `UnderReplicatedPartitions > 0` (Severity: P1 / Critical).
   - `OfflinePartitionsCount > 0` (Severity: P0 / Blocker).
   - `ActiveControllerCount != 1` (Severity: P0 / Blocker).
   - `RequestHandlerAvgIdlePercent < 0.2` (Severity: P2 / Warning — голодание потоков обработки).
   - Рост Consumer Lag выше установленного бизнес-порога SLA (Severity: P2).
