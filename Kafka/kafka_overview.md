# Обзор Apache Kafka

**Apache Kafka** — распределённая стриминговая платформа для создания высокопроизводительных pipeline данных, потоковой аналитики и интеграции систем. В отличие от традиционных систем обмена сообщениями, Kafka работает как отказоустойчивый неизменяемый журнал (лог), обеспечивая надёжность и возможность повторного чтения данных.

**Основные источники:**

- **[Гарантии доставки](./delivery_guarantees.md)** — at-most-once, at-least-once, exactly-once
- **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — стратегии партиционирования, ребалансировка
- **[Принципы очередей сообщений](./message_queues_principles.md)** — общие концепции брокеров сообщений

## Определения

- **Продюсер (Producer):** Клиентское приложение, отправляющее записи в топик Kafka.
- **Консьюмер (Consumer):** Клиентское приложение, подписывающееся на топики и считывающее записи.
- **Брокер (Broker):** Сервер Kafka, хранящий данные и обслуживающий запросы продюсеров/консьюмеров. Кластер состоит из одного или нескольких брокеров.
- **Топик (Topic):** Логическая категория (именованный поток записей), в который продюсеры пишут, а консьюмеры читают данные.
- **Партиция (Partition):** Минимальная единица параллелизма. Топик делится на партиции — упорядоченные неизменяемые журналы сообщений. Порядок гарантируется только в пределах одной партиции.
- **Офсет (Offset):** Уникальный последовательный идентификатор записи в пределах партиции. Консьюмеры используют офсет для отслеживания позиции чтения.
- **Репликация (Replication):** Механизм отказоустойчивости: партиции копируются на несколько брокеров. Реплики-лидеры принимают запись/чтение, реплики-последователи пассивно копируют данные.
- **Consumer Group:** Группа консьюмеров, совместно читающих данные из топиков. Kafka распределяет партиции между участниками группы для параллелизма.

**См. также:** **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — подробные определения ISR, min.insync.replicas, rebalancing.

## Основные концепции

### Модель «Издатель-подписчик» на основе журнала

В отличие от классических очередей, где сообщение удаляется после прочтения, Kafka сохраняет сообщения в течение настраиваемого периода. Консьюмеры не «забирают» сообщения, а читают их по указателю (офсету).

**Преимущества:**

1. **Множество консьюмеров** читают одни данные независимо друг от друга.
2. **Возврат назад во времени** — повторное чтение обработанных сообщений (например, после сбоя логики).

### Партиционирование для масштабируемости

Топики разбиваются на партиции, распределяемые по разным брокерам.

**Возможности:**

- **Горизонтальное масштабирование:** нагрузка распределяется по серверам, скорость растёт пропорционально количеству брокеров.
- **Порядок сообщений:** гарантируется строго **в пределах одной партиции**.

**См. также:** **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — стратегии partitioner, выбор количества партиций.

### Отказоустойчивость через репликацию

Каждая партиция имеет несколько копий (реплик) на разных брокерах.

- **Лидер и последователи (Leader & Followers):** Запись/чтение идут через лидера. Последователи асинхронно копируют данные.
- **Восстановление после сбоя:** При выходе лидера из строя Kafka автоматически выбирает нового лидера из синхронизированных последователей.
- **In-Sync Replicas (ISR):** Список реплик (включая лидера), не отстающих от лидера. Новый лидер выбирается только из ISR.

**См. также:** **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — настройки RF, min.insync.replicas.

### Высокая производительность

Kafka достигает высокой пропускной способности благодаря:

1. **Последовательная запись/чтение (Sequential I/O):** Дописывание в конец лога — самая быстрая операция для дисков.
2. **Page Cache ОС:** Kafka использует кэш файловой системы. Продюсер пишет в RAM, ядро Linux в фоне сбрасывает на диск.
3. **Zero-Copy:** Системный вызов `sendfile` передаёт данные с диска напрямую в сетевую карту, минуя копирование в пространство приложения (снижает нагрузку на CPU).

### Хранение и удаление данных

Данные хранятся на диске в **сегментах** (`segments`).

#### Удаление на основе времени или размера (`cleanup.policy=delete`)

Политика по умолчанию. Данные удаляются целыми сегментами.

1. **Закрытие сегмента:** Активный сегмент закрывается (становится read-only) при:
   - Достижении максимального размера (`segment.bytes`, по умолчанию 1 ГБ).
   - Истечении максимального времени с момента создания (`segment.ms`, по умолчанию 7 дней).
2. **Удаление сегмента:** Kafka удаляет сегмент целиком, когда время жизни **последнего** сообщения превышает политику хранения (`retention.ms` или `retention.bytes`).

**Важно:** Сообщения могут храниться дольше `retention.ms`. Например, при `retention.ms=7 дней` сегмент удалится, только когда timestamp **последнего** сообщения станет старше 7 дней.

#### Компактификация (`cleanup.policy=compact`)

Режим для хранения последнего актуального значения по ключу.

- **Принцип:** Kafka периодически сканирует лог, удаляя старые сообщения с тем же ключом.
- **Гарантия:** Для каждого ключа сохраняется как минимум одно последнее значение.
- **Применение:** Состояния, конфигурации, справочники.

#### Смешанная политика (`cleanup.policy=compact,delete`)

Комбинация подходов: хранится последнее значение для ключа, но ключ удаляется, если не обновлялся дольше `retention.ms`. Полезно для неактуальных сущностей.

**Важно:** В Kafka нельзя удалить конкретное сообщение по офсету (кроме компактифицируемых топиков).

### Батчинг и буферизация

Kafka часто используется как промежуточный слой между источниками данных и базами данных:

1. **Сглаживание пиков нагрузки:** Продюсеры могут генерировать огромное количество событий в секунду. Kafka принимает их и хранит в журнале.
2. **Батчинг (Batching):** Консьюмеры считывают данные не по одному сообщению, а пачками (батчами). Многие БД (ClickHouse, Elasticsearch) работают значительно быстрее, когда данные записываются большими блоками.
3. **Надежность логов:** Агенты сбора логов отправляют данные в Kafka, что гарантирует их сохранность даже при временной недоступности системы хранения логов (ELK/Loki).

## Практические сценарии

### Гарантии доставки (`acks`)

Продюсер настраивает уровень надёжности через параметр `acks`. Подробное описание с примерами кода — в **[Гарантии доставки](./delivery_guarantees.md)**.

| Значение | Описание | Риск потери | Производительность | Применение |
| :--- | :--- | :--- | :--- | :--- |
| `acks=0` | «Выстрелил и забыл», без ожидания ответа | Да | Максимальная | Некритичные метрики |
| `acks=1` | Подтверждение от лидера (по умолчанию) | Небольшой | Высокая | Большинство сценариев |
| `acks=all` | Подтверждение от лидера и всех ISR | Нет | Низкая | Критичные данные (транзакции, аудит) |

### Распределение нагрузки с помощью Consumer Groups

При запуске нескольких консьюмеров с одинаковым `group.id` Kafka автоматически распределяет партиции между ними.

**Правила:**

- Каждая партиция назначается только одному консьюмеру в группе.
- Если консьюмеров меньше, чем партиций — некоторым достанется несколько партиций.
- Если консьюмеров столько же, сколько партиций — идеальный баланс (по одной партиции).
- Если консьюмеров больше — «лишние» будут простаивать (`IDLE`).

**Правило:** Количество активных консьюмеров в группе ≤ количества партиций в топике.

Разные consumer group независимы: каждая получает полную копию всех сообщений из топика.

**См. также:** **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — стратегии ребалансировки (CooperativeStickyAssignor).

### Сохранение порядка с помощью ключей

Для строгой последовательной обработки связанных сообщений (например, события одного пользователя) используется **ключ** (например, `user_id`). Kafka вычисляет хэш ключа и определяет номер партиции.

**Гарантия:** Все сообщения с одинаковым ключом попадают в одну партицию и обрабатываются последовательно.

**См. также:** **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — стратегии partitioner (key-based, round-robin, sticky).
