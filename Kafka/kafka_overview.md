# Обзор Apache Kafka

Apache Kafka — это распределённая стриминговая платформа, которая используется для создания высокопроизводительных конвейеров данных, потоковой аналитики, интеграции данных и для критически важных приложений. В отличие от традиционных систем обмена сообщениями, Kafka работает как отказоустойчивый, неизменяемый журнал (лог), что обеспечивает надёжность и возможность повторного чтения данных.

## Определения

* **Продюсер (Producer):** Клиентское приложение, которое отправляет (публикует) записи в топик Kafka.
* **Консьюмер (Consumer):** Клиентское приложение, которое подписывается на топики и считывает из них записи.
* **Брокер (Broker):** Сервер Kafka, который хранит данные и обслуживает запросы от продюсеров и консьюмеров. Кластер Kafka состоит из одного или нескольких брокеров.
* **Топик (Topic):** Логическая категория или именованный поток записей, в который продюсеры пишут данные и из которого консьюмеры их читают.
* **Партиция (Partition)::** Минимальная единица параллелизма в Kafka. Топик делится на одну или несколько партиций. Каждая партиция представляет собой упорядоченный, неизменяемый журнал сообщений, куда последовательно дописываются данные.
* **Офсет (Offset):** Уникальный последовательный идентификатор, который Kafka присваивает каждой записи в пределах одной партиции. Консьюмеры используют офсет для отслеживания своей позиции чтения.
* **Репликация (Replication):** Механизм отказоустойчивости, при котором партиции копируются на несколько брокеров. Существуют реплики-лидеры (принимают запись и чтение) и реплики-последователи (пассивно копируют данные).
* **Consumer Group:** Группа консьюмеров, которые совместно читают данные из одного или нескольких топиков. Kafka распределяет партиции топика между участниками группы, что позволяет распараллелить обработку.

## Основные концепции

### Модель "Издатель-подписчик" на основе журнала

В отличие от классических очередей, где сообщение удаляется после прочтения, Kafka сохраняет сообщения в течение настраиваемого периода. Консьюмеры не "забирают" сообщения, а читают их, используя указатель (офсет). Это позволяет:

1. **Множеству консьюмеров** читать одни и те же данные независимо друг от друга.
2. **Вернуться назад во времени** и повторно прочитать уже обработанные сообщения, если это необходимо (например, после сбоя в логике обработки).

### Партиционирование для масштабируемости

Для обработки огромных потоков данных топики разбиваются на партиции, которые могут быть распределены по разным брокерам в кластере. Это позволяет:

* **Горизонтально масштабировать запись и чтение:** Нагрузка распределяется по нескольким серверам. Скорость обработки растёт пропорционально количеству брокеров.
* **Гарантировать порядок сообщений:** Kafka гарантирует строгий порядок доставки сообщений **только в пределах одной партиции**.

### Отказоустойчивость через репликацию

Каждая партиция может иметь несколько копий (реплик) на разных брокерах.

* **Лидер и последователи (Leader & Followers):** Все операции записи и чтения для партиции проходят через одну реплику — **лидера**. Остальные реплики — **последователи** (followers) — асинхронно копируют данные с лидера.
* **Восстановление после сбоя:** Если брокер-лидер выходит из строя, Kafka автоматически выбирает нового лидера из числа синхронизированных последователей. Этот процесс обеспечивает высокую доступность без потери данных.
* **In-Sync Replicas (ISR):** Список реплик (включая лидера), которые не сильно отстали от лидера. Новый лидер может быть выбран только из этого списка, что гарантирует консистентность данных.

### Высокая производительность

Kafka достигает высокой пропускной способности благодаря нескольким механизмам:

1. **Последовательная запись/чтение (Sequential I/O):** Kafka дописывает данные в конец лога, что для жёстких дисков является самой быстрой операцией.
2. **Использование Page Cache ОС:** Kafka активно использует кэш файловой системы операционной системы. Продюсер пишет данные в кэш (RAM), а ядро Linux в фоне сбрасывает их на диск.
3. **Zero-Copy:** При чтении данных консьюмером Kafka использует системный вызов `sendfile`, который позволяет передавать данные с диска напрямую в сетевую карту, минуя копирование в пространство приложения. Это значительно снижает нагрузку на CPU.

## Практические сценарии

### Гарантии доставки (`acks`)

Продюсер может настраивать уровень надёжности при отправке сообщений с помощью параметра `acks`:

* `acks=0`: **"Выстрелил и забыл"**. Продюсер не ждёт ответа от брокера. Максимальная производительность, но есть риск потери сообщений. Подходит для некритичных данных (например, метрики).
* `acks=1` (по умолчанию): **Подтверждение от лидера**. Продюсер ждёт подтверждения только от лидера партиции. Существует небольшой риск потери данных, если лидер упадёт сразу после подтверждения, но до того, как последователи скопируют данные.
* `acks=all` (или `-1`): **Подтверждение от всех реплик**. Продюсер ждёт подтверждения от лидера и всех синхронизированных реплик (ISR). Это самый надёжный режим, исключающий потерю данных, но он самый медленный. Обязателен для финансовых транзакций и других критичных систем.

### Распределение нагрузки с помощью Consumer Groups

Если запустить несколько экземпляров сервиса-консьюмера с одинаковым `group.id`, Kafka автоматически распределит партиции топика между ними.

* Если консьюмеров меньше, чем партиций, некоторым консьюмерам достанется несколько партиций.
* Если консьюмеров столько же, сколько партиций, каждый будет обрабатывать одну партицию (идеальный баланс).
* Если консьюмеров больше, чем партиций, "лишние" консьюмеры будут простаивать (`IDLE`), так как одну партицию в рамках одной группы может читать только один консьюмер.

**Правило:** Количество активных читающих инстансов сервиса ограничено количеством партиций в топике.

### Сохранение порядка с помощью ключей

Чтобы связанные сообщения (например, все события одного пользователя) обрабатывались строго последовательно, их нужно помещать в одну и ту же партицию. Для этого при отправке сообщения продюсер указывает **ключ** (например, `user_id`). Kafka вычисляет хэш от ключа и на его основе определяет номер партиции. Таким образом, все сообщения с одинаковым ключом гарантированно попадут в одну партицию.
