# Kafka для мониторинга

## Определения

**Kafka для мониторинга** — паттерн использования Apache Kafka в качестве отказоустойчивого распределённого буфера в системах Observability для агрегации логов, метрик и трассировок перед обработкой и хранением.

**Ключевая цель:** предотвращение потери данных при пиковых нагрузках и временной недоступности систем хранения.

## Основные концепции

### Роль Kafka в системах мониторинга

**Kafka** играет критически важную роль отказоустойчивого буфера в высоконагруженных системах мониторинга и Observability. Она используется для агрегации всех типов данных: логов, метрик и трассировок, перед их последующей обработкой и хранением.

### Риски прямой отправки данных

Прямая отправка данных от агентов (например, Vector, FluentBit) в системы хранения (например, Elasticsearch, Loki, ClickHouse) без промежуточного буфера создает следующие риски:

* **Потеря данных:** Если система хранения недоступна или перегружена, агенты не смогут отправить данные, что приведет к их безвозвратной потере.
* **Деградация производительности:** Агенты, вынужденные ожидать ответа от медленной или перегруженной системы хранения, могут потреблять больше системных ресурсов (CPU, память) на источнике, что негативно сказывается на работе основных приложений.
* **Блокировка агентов:** Переполнение внутренних буферов агентов приводит к остановке сбора новых данных.

### Архитектурный паттерн: Producer → Kafka → Consumer → Storage

```
[Агенты/Продюсеры] → [Kafka (топики)] → [Консьюмеры] → [Хранилища]
     (Fluent Bit)    (буферизация)     (Vector/Logstash) (Elasticsearch/Loki)
```

**Принцип работы:**
1. **Агенты (продюсеры)** отправляют данные в топики Kafka — быстрая операция записи без блокировки
2. **Kafka** надёжно хранит данные на диске, принимая пиковые нагрузки
3. **Консьюмеры** вычитывают данные в комфортном темпе, адаптируясь к производительности хранилища
4. **Хранилища** получают данные без перегрузки

**Преимущества:**
- **Асинхронность:** сбор данных отделён от их сохранения
- **Back-pressure:** проблема противодавления решена на уровне архитектуры
- **Гарантия доставки:** ни один лог не будет потерян из-за временных проблем с хранилищем

## Практические сценарии

### Сценарий: Предотвращение потери логов при пиковых нагрузках

**Проблема:** В архитектуре, где легковесный агент (например, Fluent Bit) отправляет логи напрямую в систему хранения (например, Elasticsearch), возникает риск потери данных. У Fluent Bit есть собственный небольшой буфер для временного хранения логов перед отправкой. Если Elasticsearch перегружен или временно недоступен, он не может принимать данные так же быстро, как их отправляет агент. В результате внутренний буфер Fluent Bit переполняется, и новые логи начинают отбрасываться.

**Решение:** Внедрение Kafka в качестве промежуточного асинхронного буфера между агентом и хранилищем.

1. **Fluent Bit (Продюсер)**: Агент настраивается на отправку всех логов в топик Kafka. Запись в Kafka — это очень быстрая операция, которая практически никогда не блокирует отправителя.
2. **Kafka (Буфер)**: Принимает на себя весь поток логов, даже во время пиковых нагрузок. Данные надежно хранятся в топиках на диске, ожидая обработки.
3. **Vector/Logstash (Консьюмер)**: Отдельный сервис (или группа сервисов) вычитывает данные из Kafka в комфортном для себя и для конечного хранилища темпе.
4. **Elasticsearch (Хранилище)**: Принимает обработанные данные от консьюмера.

Эта архитектура "отвязывает" процесс сбора логов от процесса их сохранения, эффективно решая проблему противодавления (back-pressure) и гарантируя, что ни один лог не будет потерян из-за временных проблем с производительностью или доступностью системы хранения.

**См. также:** **[Полный пайплайн: Fluent Bit → Kafka → Vector → OpenSearch](../ELK_Stack/Tutorials/fluentbit_kafka_vector_opensearch_pipeline.md)** — практическое руководство по развёртыванию.

### KRaft vs. ZooKeeper: Современный стандарт для Kafka

Исторически кластеры Kafka зависели от внешнего сервиса координации — **Apache ZooKeeper**, который управлял метаданными кластера (конфигурации топиков, ACL, состояние брокеров).

**Недостатки ZooKeeper:**

1. **Дополнительная точка отказа:** Необходимость развертывания, мониторинга и обслуживания отдельной распределенной системы.
2. **Проблемы с производительностью:** Потенциальное узкое место при высоких нагрузках или большом количестве топиков/партиций.
3. **Сложность эксплуатации:** Управление двумя сложными распределенными системами одновременно (Kafka и ZooKeeper).
4. **Медленный запуск:** Длительное время восстановления после рестарта кластера из-за необходимости вычитывания всех метаданных контроллером Kafka из ZooKeeper.

Современные версии Kafka (начиная с 3.3) поддерживают режим **KRaft** (Kafka Raft), который устраняет зависимость от ZooKeeper.

**Преимущества KRaft:**

1. **Упрощение архитектуры:** Отсутствие отдельного кластера ZooKeeper снижает сложность развертывания и управления.
2. **Повышенная производительность:** Метаданные хранятся непосредственно в Kafka, что ускоряет доступ к ним и процесс ребалансировки.
3. **Улучшенная масштабируемость:** KRaft позволяет эффективно управлять значительно большим количеством партиций.
4. **Быстрое восстановление:** Отсутствие внешней зависимости ускоряет восстановление кластера после сбоев.

> **Рекомендация:** Для любых новых инсталляций Kafka, особенно в средах с высокими требованиями к надежности и производительности, следует использовать исключительно режим **KRaft**, отказываясь от ZooKeeper.

### Рекомендации по настройке для мониторинга

**Репликация и надёжность:**
- **Replication Factor:** не менее **3** для критически важных топиков в продуктивной среде
- **min.insync.replicas:** `RF - 1` (обычно 2) для гарантии записи в несколько реплик
- **Гарантии доставки:** выбираются в зависимости от типа данных — подробности в **[Гарантии доставки](./delivery_guarantees.md)**

**Партиционирование:**
- Количество партиций определяет максимальный параллелизм чтения (число консьюмеров в группе)
- Для увеличения пропускной способности пропорционально увеличивайте количество партиций и консьюмеров
- Заранее планируйте количество партиций — изменить без пересоздания топика нельзя
