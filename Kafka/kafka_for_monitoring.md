# Использование Apache Kafka в системах мониторинга и наблюдаемости

**Kafka для мониторинга** — это архитектурный паттерн, при котором Apache Kafka выступает в роли распределенного персистентного буфера между источниками телеметрии (метрики, логи, трассировки) и системами их обработки и хранения. Этот подход является стандартом для высоконагруженных систем (High Load), обеспечивая надежность и масштабируемость observability-пайплайнов.

---

## Определения

- **Очередь-буфер (Buffering):** Механизм временного хранения данных в Kafka для изоляции систем-источников от систем-приемников. Позволяет сглаживать пики нагрузки.
- **Обратное давление (Back-pressure):** Состояние, при котором система-приемник не успевает обрабатывать входящий поток данных. В Kafka консьюмеры сами контролируют скорость чтения, предотвращая перегрузку хранилищ.
- **Consumer Lag (Лаг консьюмера):** Разница между последним записанным офсетом в партиции и последним прочитанным офсетом консьюмера. Ключевая метрика здоровья observability-пайплайна.
- **Декаплинг (Decoupling):** Архитектурное разделение процессов генерации телеметрии и её индексации. Изменения или сбои в хранилище (например, Elasticsearch) не влияют на работу агентов сбора данных на серверах приложений.
- **Fan-out (Множественные потребители):** Возможность Kafka транслировать один поток телеметрии сразу в несколько систем (например, логи одновременно идут в OpenSearch для поиска и в S3 для долгосрочного аудита).

## Основные концепции

### Роль Kafka в архитектуре наблюдаемости

Kafka выполняет роль «амортизатора» и «распределителя» данных. В современных системах наблюдаемости (Observability) она занимает центральное место между уровнем сбора (Edge) и уровнем хранения (Storage).

**Ключевые преимущества:**
1. **Персистентность:** В отличие от буферов в оперативной памяти агентов, Kafka записывает данные на диск. При перезагрузке агента или сбое сети данные не теряются.
2. **Асинхронность:** Приложения отправляют телеметрию в Kafka за миллисекунды и продолжают работу, не дожидаясь медленной индексации в БД.
3. **Сжатие данных:** Использование алгоритмов сжатия (Snappy, LZ4, Zstd) на стороне продюсера позволяет экономить до 80% сетевого трафика и места на дисках брокеров.

### Риски прямой отправки телеметрии

Прямая отправка (например, `Fluent Bit → OpenSearch`) допустима только в малых системах. В High Load возникают следующие проблемы:
- **Потеря данных:** При недоступности БД агенты (Fluent Bit, Vector) начинают переполнять свои ограниченные буферы в RAM и в итоге отбрасывают новые события (drop logs).
- **Блокировка ресурсов:** Агенты тратят CPU и память на попытки переотправки данных (retries) в недоступную систему, что может привести к деградации самого приложения на хосте.
- **Отсутствие гибкости:** Если нужно добавить вторую систему анализа, придется перенастраивать все агенты на всех хостах.

### Эффективность через батчинг и сжатие

Для мониторинга критически важна оптимизация ресурсов:
- **Батчинг (Batching):** Продюсеры объединяют мелкие события логов в пакеты. Это уменьшает количество сетевых запросов и накладные расходы на заголовки протоколов.
- **Типы сжатия:**
    - `Snappy`: Баланс между скоростью и сжатием. Идеально для логов.
    - `Zstd`: Самая высокая степень сжатия при умеренной нагрузке на CPU. Рекомендуется для больших объемов телеметрии.

## Практические сценарии

### Сценарий 1: Обработка всплесков логов (Log Spikes)

**Проблема:** Ошибка в коде вызывает бесконечный цикл записи лога. Поток данных вырастает с 10 МБ/с до 500 МБ/с. Хранилище (Loki/Elasticsearch) «ложится» под нагрузкой.

**Решение с Kafka:**
1. **Агент (Fluent Bit/Vector):** Отправляет пиковый поток в Kafka. Для Kafka запись 500 МБ/с на кластер из 3-5 нод является штатной нагрузкой.
2. **Kafka:** Хранит эти логи в партициях.
3. **Консьюмер (Vector/Logstash):** Видит рост лага (Consumer Lag), но продолжает вычитывать данные со скоростью, которую может выдержать хранилище (например, 50 МБ/с).
4. **Итог:** Хранилище стабильно, логи не потеряны, они доиндексируются позже, когда пик пройдет.

### Сценарий 2: Отказоустойчивый конвейер с OpenTelemetry

Современный стандарт — использование **OpenTelemetry (OTel)**.
`Приложение → OTel Collector (Agent) → Kafka → OTel Collector (Gateway) → ClickHouse / Tempo / Prometheus`.

**Преимущества:**
- OTel Collector умеет работать с Kafka как в роли продюсера (`kafka exporter`), так и консьюмера (`kafka receiver`).
- Поддержка единого формата данных (OTLP) упрощает интеграцию.

### Сценарий 3: Мониторинг самой Kafka

Система, которая буферизует мониторинг, сама должна быть под наблюдением.
1. **Ключевые метрики (Prometheus):**
    - `kafka_consumergroup_lag`: Самая важная метрика. Рост лага означает, что консьюмеры не справляются или хранилище тормозит.
    - `kafka_server_replica_under_replicated_partitions_count`: Сигнализирует о проблемах с репликацией и риске потери данных.
    - `kafka_controller_active_controller_count`: Должен быть равен 1.
2. **Инструменты:**
    - **Kafka Exporter:** Собирает метрики лагов по группам потребителей.
    - **JMX Exporter:** Собирает внутренние метрики JVM и брокера.

## Дополнительная информация

### Рекомендуемые настройки топиков для телеметрии

| Тип данных | Retention (срок хранения) | Replication Factor | Сжатие |
| :--- | :--- | :--- | :--- |
| **Логи приложений** | 3–7 дней | 3 | `lz4` или `snappy` |
| **Аудит-логи** | 14–30 дней | 3 | `zstd`, `acks=all` |
| **Метрики** | 1 день | 2 | `zstd` |
| **Трассировки (Traces)** | 12–24 часа | 2 | `snappy` |
