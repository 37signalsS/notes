# Kafka для мониторинга

## Определения

**Kafka для мониторинга** — паттерн использования Apache Kafka в качестве отказоустойчивого распределённого буфера в системах Observability (наблюдаемости) для агрегации логов, метрик и трассировок перед обработкой и хранением.

**Ключевая цель:** предотвращение потери данных при пиковых нагрузках и временной недоступности систем хранения.

**См. также:**

- **[Обзор Apache Kafka](./kafka_overview.md)** — базовые концепции (продюсер, консьюмер, топики)
- **[Гарантии доставки](./delivery_guarantees.md)** — семантика доставки сообщений
- **[Партиционирование и балансировка](./partitioning_and_balancing.md)** — масштабирование

## Основные концепции

### Роль Kafka в системах наблюдаемости

**Kafka** выступает в роли промежуточного слоя между источниками телеметрии и системами анализа. Она позволяет сглаживать «всплески» трафика и гарантирует, что данные будут доставлены в хранилище даже при его кратковременном отключении.

### Риски прямой отправки телеметрии

Прямая отправка данных от агентов (Vector, Fluent Bit) в системы хранения (Elasticsearch, Loki, ClickHouse) создает следующие риски:

- **Потеря данных:** при недоступности хранилища агенты могут потерять накопленные данные после переполнения локального буфера.
- **Деградация производительности:** ожидание ответа от медленного хранилища увеличивает потребление ресурсов **CPU (Central Processing Unit)** и памяти на узлах с приложениями.
- **Блокировка агентов:** переполнение внутренних очередей агента останавливает сбор новых метрик и логов.

### Архитектурный паттерн: Продюсер → Kafka → Консьюмер → Хранилище

```
[Агенты/Продюсеры] → [Kafka (топики)] → [Консьюмеры] → [Хранилища]
     (Fluent Bit)    (буферизация)     (Vector/Logstash) (Elasticsearch/Loki)
```

**Принцип работы:**

1. **Агенты (продюсеры)** записывают данные в топики Kafka — это быстрая неблокирующая операция.
2. **Kafka** сохраняет данные на диск, обеспечивая персистентность.
3. **Консьюмеры** (потребители) вычитывают данные со скоростью, которую может обеспечить целевое хранилище.
4. **Хранилища** индексируют данные без риска перегрузки.

### Преимущества буферизации

- **Асинхронность:** процесс сбора данных полностью отделён от процесса их индексации.
- **Back-pressure (обратное давление):** механизм контроля скорости, реализованный на уровне архитектуры.
- **Масштабируемость:** возможность независимого масштабирования слоёв сбора и обработки.

## Практические сценарии

### Предотвращение потери логов при пиковых нагрузках

**Проблема:** Приложение генерирует аномальный объем логов (например, при ошибке в цикле). Elasticsearch не успевает их индексировать, Fluent Bit переполняет свой буфер и начинает отбрасывать новые записи.

**Решение:**

1. **Fluent Bit** настраивается на отправку в Kafka.
2. **Kafka** принимает пиковый поток, записывая его в партиции.
3. **Vector** (в роли консьюмера) вычитывает логи из Kafka и плавно передает их в Elasticsearch.

**См. также:** **[Пайплайн Fluent Bit → Kafka → Vector → OpenSearch](../ELK_Stack/Tutorials/fluentbit_kafka_vector_opensearch_pipeline.md)**.

### Переход на KRaft (Kafka Raft)

Современный стандарт (начиная с версии 3.3) — использование режима **KRaft (Kafka Raft)**, который заменяет зависимость от **ZooKeeper**.

**Преимущества KRaft перед ZooKeeper:**

- **Упрощение:** отсутствие необходимости управлять отдельным кластером координации.
- **Производительность:** метаданные (конфигурации топиков, **ACL (Access Control List)**, состояние брокеров) хранятся внутри самой Kafka.
- **Скорость:** значительно более быстрое восстановление контроллера после сбоев.

### Рекомендации по настройке для мониторинга

**Надёжность:**

- **Replication Factor (фактор репликации):** не менее **3** для продуктивных сред.
- **min.insync.replicas:** обычно устанавливается в значение `2` (при RF=3) для подтверждения записи в большинство реплик.

**Масштабирование:**

- Количество партиций должно соответствовать планируемому количеству консьюмеров для параллельной обработки.
- Использование **acks=all** рекомендуется для критичных данных (например, аудит-логи).
