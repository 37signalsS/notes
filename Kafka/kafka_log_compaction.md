# Log Compaction и сегменты хранения в Apache Kafka

**Актуально для:** Apache Kafka 3.8.x / 3.9.x / 4.0.x (KRaft)

**Log Compaction (Компактификация логов)** — это фоновый механизм управления хранилищем Apache Kafka, гарантирующий, что для каждого уникального ключа сообщения внутри партиции сохраняется как минимум его последнее известное значение (latest state). В отличие от стандартной политики удаления по времени (`cleanup.policy=delete`), компактификация позволяет использовать Kafka в качестве персистентного журнала изменений состояний (Changelog / Key-Value Store) для задач Change Data Capture (CDC), реестров схем (Schema Registry), кэшей микросервисов и восстановления состояния Kafka Streams (RocksDB).

---

## Определения

- **Log Segment (Сегмент журнала):** Физический файл данных на диске хоста брокера (`.log`) фиксированного размера (`log.segment.bytes`, по умолчанию 1 ГБ) или времени жизни (`segment.ms`), сопровождаемый индексными файлами.
- **Active Segment (Активный сегмент):** Единственный сегмент партиции, открытый в текущий момент на запись новых сообщений. **Никогда не подвергается очистке или компактификации**, пока не будет закрыт (rolled).
- **Log Cleaner:** Пул фоновых системных потоков брокера (`log.cleaner.threads`), выполняющих уплотнение неактивных сегментов в топиках с политикой `cleanup.policy=compact`.
- **Cleaner Point (Точка очистки):** Граница смещения (offset) в партиции, разделяющая лог на две части: уже очищенную (Clean/Tail) и ожидающую компактификации (Dirty/Head).
- **Tail (Clean Log):** Очищенная часть журнала. Содержит только уникальные ключи (каждый ключ встречается строго один раз с максимальным смещением на момент последней очистки).
- **Head (Dirty Log):** «Грязная» часть журнала, накопившаяся после предыдущего цикла очистки. Может содержать дублирующиеся ключи с новыми версиями данных.
- **Tombstone («Надгробный маркер»):** Специальная запись об удалении сущности, содержащая ключ и пустое значение полезной нагрузки (`value = null`).
- **`delete.retention.ms`:** Время гарантированного удержания tombstone-маркера в очищенном логе (по умолчанию 24 часа). Предотвращает удаление маркера до того, как все потребители успеют его вычитать.
- **`min.cleanable.dirty.ratio`:** Коэффициент загрязненности лога (по умолчанию `0.5` или 50%), по достижении которого поток Log Cleaner инициирует процедуру уплотнения сегментов партиции.
- **SkimpyOffsetMap:** Внутренняя хэш-таблица брокера, размещаемая в off-heap памяти (`log.cleaner.dedupe.buffer.size`), используемая потоком очистки для запоминания соответствия `Hash(Key) -> LatestOffset` при сканировании «грязного» сегмента.
- **Sparse Index (Разреженный индекс):** Индекс смещений (`.index`) и временных меток (`.timeindex`), индексирующий не каждое отдельное сообщение, а позиции через интервалы байт (`index.interval.bytes`, по умолчанию 4 КБ).

## Архитектура и основные концепции

### Структура партиции на файловой системе

Каждая партиция топика представляет собой каталог в одном из путей `log.dirs` брокера:

```
/var/lib/kafka/data/orders-0/
├── 00000000000000000000.log                 # Сегмент с сообщениями (Clean)
├── 00000000000000000000.index               # Индекс: логический offset -> физическая позиция в .log
├── 00000000000000000000.timeindex           # Индекс: timestamp -> логический offset
├── 00000000000001048576.log                 # Активный сегмент (Active, Head)
├── 00000000000001048576.index
├── 00000000000001048576.timeindex
├── leader-epoch-checkpoint                  # Контрольная точка соответствия Leader Epoch и начальных смещений
└── partition.metadata                       # UUID топика
```

### Как работает бинарный поиск по разреженному индексу (Sparse Index)

Когда консьюмер запрашивает чтение сообщения со смещением `Offset = 10050`:
1. Брокер определяет подходящий файл сегмента по базовому смещению в имени файла.
2. Вместо сканирования гигабайтного `.log` файла брокер открывает отображенный в оперативную память (`mmap`) индекс `.index`.
3. По индексу выполняется бинарный поиск $O(\log N)$ для нахождения наибольшего проиндексированного смещения, которое $\le 10050$ (например, смещение `10048`, находящееся на физической позиции `4194304` байт).
4. Процесс переходит на позицию `4194304` в `.log` файле и последовательно считывает несколько записей до смещения `10050`. Чтение выполняется мгновенно из системного кэша страниц Linux (Page Cache).

```
.index (mmap в памяти)                      .log (на диске / в Page Cache)
┌──────────────────────┬─────────────┐     ┌────────────────────────────────────────────────────────┐
│ Логический Offset    │ Байт в файле │     │ ... [Offset 10048] [Offset 10049] [Offset 10050] ...   │
├──────────────────────┼─────────────┤     └────────────────────────────────────────────────────────┘
│ 10000                │ 0           │                                              ▲
│ 10024                │ 2097152     │                                              │
│ 10048                │ 4194304     │ ──► Прямой переход на байт 4194304 и скан ───┘
└──────────────────────┴─────────────┘
```

### Архитектура и этапы работы Log Cleaner

Лог с политикой `cleanup.policy=compact` разделен на три логические зоны:

```
┌───────────────────────────────────────┬───────────────────────────────────┬─────────────────────┐
│              TAIL (CLEAN)             │            HEAD (DIRTY)           │   ACTIVE SEGMENT    │
│  Сегменты прошли компактификацию.     │  Неактивные закрытые сегменты.    │  Сегмент открыт     │
│  Только последние версии ключей.      │  Содержат дубликаты ключей.       │  на запись.         │
│  (Уплотненные сегменты)               │  (Ожидают уплотнения)             │  НЕ ТРОГАЕТСЯ!      │
└───────────────────────────────────────┴───────────────────────────────────┴─────────────────────┘
0                                       Cleaner Point                       Log End Offset (LEO)
```

#### Этап 1: Проверка условий запуска (Dirty Ratio)
Поток Log Cleaner периодически проверяет все партиции кластера. Вычисляется коэффициент загрязнения:
$$\text{DirtyRatio} = \frac{\text{Bytes(Dirty)}}{\text{Bytes(Clean)} + \text{Bytes(Dirty)}}$$
Если $\text{DirtyRatio} \ge \text{min.cleanable.dirty.ratio}$ (по умолчанию `0.5`), партиция ставится в очередь на очистку.

Дополнительные барьеры:
- `min.compaction.lag.ms` (по умолчанию `0`): минимальное время, которое должно пройти с момента записи сообщения до того, как оно станет доступно для очистки. Позволяет консьюмерам гарантированно прочитать промежуточные обновления.
- `max.compaction.lag.ms` (по умолчанию $\infty$): принудительный запуск компакции даже при низком Dirty Ratio, если сообщения лежат дольше заданного интервала.

#### Этап 2: Построение карты ключей (First Pass)
Поток считывает заголовки сообщений из «грязных» сегментов (Head) и заполняет структуру `SkimpyOffsetMap` в ОЗУ:
- Ключ хэшируется (MD5/MurmurHash) для минимизации расхода памяти (24 байта на запись).
- В карту записывается наибольшее смещение: $\text{Hash}(K_1) \to \text{Offset}_{max}$.

#### Этап 3: Слияние и перезапись (Second Pass)
Поток последовательно перечитывает все неактивные сегменты (как Clean, так и Dirty):
1. Для каждого сообщения проверяется: равно ли его смещение смещению в карте для данного ключа?
2. Если смещение равно максимальному — сообщение сохраняется и копируется в новый уплотненный сегмент.
3. Если смещение меньше максимального — сообщение отбрасывается.
4. По завершении старые сегменты атомарно удаляются, а новые переименовываются.

### Механика Tombstone и ловушка воскрешения данных (Resurrection Bug)

В системах без удаления по времени полное удаление записи по ключу невозможно обычной перезаписью. Для этого используется **Tombstone** (запись с `value = null`).

#### Проблема опережающего удаления Tombstone
Если брокер удалит Tombstone сразу при первом проходе компактификации, медленный или временно упавший консьюмер столкнется со сбоем:
1. Консьюмер прочитал запись `(K1, V1, Offset=10)`.
2. Продюсер отправил маркер удаления: `(K1, null, Offset=50)`.
3. Консьюмер упал на плановое обслуживание на 36 часов.
4. Брокер очистил лог. Если маркер удаления удалился, в логе вообще не осталось записей про `K1`.
5. Консьюмер просыпается, считывает свои локальные данные или внешний кэш и считает, что ключ `K1` валиден, потому что он **никогда не увидел маркер удаления**.

```
[ Продюсер ] ──► (K1, null, offset=50) ──► [ Брокер Kafka ]
                                                    │
                                         delete.retention.ms = 24h
                                                    │
                         ┌──────────────────────────┴──────────────────────────┐
                         ▼                                                     ▼
         Консьюмер успел прочитать до 24h                     Консьюмер лежал 36h
           - Получил ключ K1 с value=null                       - Tombstone УДАЛЕН брокером
           - Удалил запись в своей БД / кэше                    - Консьюмер НЕ ЗНАЕТ об удалении
           - УСПЕХ                                              - ВОСКРЕШЕНИЕ ЗАПИСИ (БАГ!)
```

> [!WARNING]
> Параметр `delete.retention.ms` (по умолчанию 24 часа) определяет, сколько времени маркер tombstone должен сохраняться в логе после первой компактификации. **Он обязан быть строго больше максимального времени восстановления консьюмеров после аварий.**

### Комбинированная политика: `cleanup.policy=compact,delete`

В production часто требуется хранить только актуальные состояния записей по ключам, но одновременно гарантировать, что данные не будут лежать на диске вечно, если по ним давно не было активности (например, сессии пользователей).

Kafka поддерживает комбинацию политик:
```properties
cleanup.policy=compact,delete
retention.ms=604800000  # 7 дней
```
- Для записей моложе 7 дней выполняется дедупликация по ключам (Log Compaction).
- Сегменты, где все записи старше 7 дней, полностью удаляются с диска по Retention.

## Практические сценарии

### Сценарий 1: Настройка топика Change Data Capture (CDC) с Log Compaction

Создание и проверка параметров топика для хранения актуальных состояний учетных записей пользователей:

```bash
# 1. Создание топика с обязательной политикой compact и увеличенным временем удержания Tombstone
kafka-topics.sh --bootstrap-server localhost:9092 --create \
    --topic user-accounts-state \
    --partitions 6 \
    --replication-factor 3 \
    --config cleanup.policy=compact \
    --config min.cleanable.dirty.ratio=0.3 \
    --config delete.retention.ms=172800000 \
    --config segment.ms=86400000 \
    --config min.insync.replicas=2
# → Created topic user-accounts-state.

# 2. Проверка примененной конфигурации топика
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic user-accounts-state
# → Topic: user-accounts-state	PartitionCount: 6	ReplicationFactor: 3	Configs: cleanup.policy=compact,delete.retention.ms=172800000,min.cleanable.dirty.ratio=0.3,segment.ms=86400000,min.insync.replicas=2
```

```bash
# 1. Проверка структуры лога и поиск маркеров удаления (Tombstone)

```

### Сценарий 3: Настройка параметров Log Cleaner в `server.properties` брокера

При высокой интенсивности обновлений топиков дефолтный 1 поток Log Cleaner не справляется с очисткой, вызывая взрывной рост диска:

```properties
# Количество параллельных потоков уплотнения (рекомендуется 2-4 на мощных брокерах)
log.cleaner.threads=4

# Объем оперативной памяти на один поток под SkimpyOffsetMap (дедупликация)
# По умолчанию 128 МБ. При миллионах уникальных ключей увеличьте до 512 МБ
log.cleaner.dedupe.buffer.size=536870912

# Максимальная пропускная способность ввода-вывода потока очистки (IO Throttling)
# 50 МБ/с на поток, чтобы компактификация не создавала дисковых очередей для клиентов
log.cleaner.io.max.bytes.per.second=52428800

# Частота проверки логов на необходимость запуска очистки
log.cleaner.backoff.ms=15000

# Режим отказоустойчивости потоков (падение потока не должно ронять весь брокер)
log.cleaner.enable=true
```

Динамическое изменение лимита дискового ввода-вывода Log Cleaner в runtime:
```bash
kafka-configs.sh --bootstrap-server localhost:9092 --command-config admin.properties --alter \
    --entity-type brokers --entity-name 1 \
    --add-config log.cleaner.io.max.bytes.per.second=104857600
# → Completed updating config for broker 1.
```

## Диагностика и устранение неисправностей (Troubleshooting)

### Типичные сбои компактификации

| Проблема / Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Топик с `policy=compact` не уменьшается в размере, диск переполняется** | 1. Все данные пишутся в Active Segment (`segment.ms` слишком велик).<br>2. Dirty Ratio не достиг `min.cleanable.dirty.ratio`.<br>3. Умер поток `log-cleaner-thread`. | 1. `ls -la /data/kafka/<topic>-*`<br>2. Логи брокера: `Dead cleaner thread`<br>3. JMX: `max-dirty-percent` | 1. Уменьшить `segment.ms` до 24–48 часов.<br>2. Принудительно уменьшить `min.cleanable.dirty.ratio` до 0.2.<br>3. Перезапустить поток/брокер. |
| **`Buffer size too small for dedupe map`** | Слишком много уникальных ключей в dirty-сегментах, хэш-таблица не помещается в `dedupe.buffer.size` | Ошибка в `server.log`: `IllegalArgumentException` в `SkimpyOffsetMap` | Увеличить `log.cleaner.dedupe.buffer.size` в `server.properties` (например, с 128M до 512M). |
| **Дисковые очереди и задержки продюсеров во время очистки логов** | Log Cleaner утилизирует 100% дискового I/O, конкурируя с клиентскими запросами | `iostat -xz 1` (`%util > 95%`)<br>JMX: `RequestHandlerAvgIdlePercent < 0.2` | Ограничить скорость дискового I/O: `log.cleaner.io.max.bytes.per.second=30000000`. |
| **Консьюмер воскрешает удаленные сущности (Resurrection)** | Консьюмер простаивал дольше, чем `delete.retention.ms`, и пропустил Tombstone-маркер | Сверка времени простоя консьюмера со значением `delete.retention.ms` топика | Увеличить `delete.retention.ms` до 3–7 дней; выполнить холодную пересинхронизацию БД консьюмера. |
| **`CorruptRecordException` / Ошибка отображения индекса `Map failed`** | Сбой питания или аварийная остановка привела к повреждению `.index` файла | Логи брокера: `CorruptIndexException` или `IOException: Map failed` | Удалить поврежденные файлы `.index`/`.timeindex`; брокер автоматически перестроит их из `.log` при старте. |

## Рекомендации и Best Practices

1. **Никогда не используйте Log Compaction без ключей:** Если продюсер отправляет сообщения без ключа (`key = null`), Kafka помещает их в конец лога, но не может дедуплицировать. Лог будет расти бесконечно.
2. **Контролируйте `segment.ms` для медленных топиков:** Если топик со справочниками принимает всего 10 МБ в сутки, дефолтный сегмент в 1 ГБ будет наполняться 100 дней. Все это время сегмент считается активным и **не очищается**. Для справочников всегда выставляйте `segment.ms=86400000` (1 день).
3. **Рассчитывайте `delete.retention.ms` с запасом:** Всегда закладывайте в `delete.retention.ms` время на устранение аварий консьюмеров (минимум 48–72 часа для критичных интеграций).
4. **Не допускайте раздувания ключей:** Размер ключа напрямую влияет на плотность кэша и размер off-heap буфера дедупликации. Используйте компактные строковые или бинарные идентификаторы (UUID, числовые ID).
5. **Мониторьте метрику `DeadThreadCount`:** Настройте в Prometheus триггер на `kafka_log_cleaner_cleaner_thread_count < log_cleaner_threads`. Если один из потоков компактификации падает из-за поврежденной записи, остальные могут не справляться с нагрузкой.
