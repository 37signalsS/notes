# Эксплуатация сотен кластеров Kafka в Kubernetes: опыт MindBox

**Актуально для:** Apache Kafka 2.8 / 3.x / 4.x (KRaft), Strimzi 0.4x–1.2, Kubernetes 1.25+ (Strimzi 1.x требует 1.30+), KMinion 2.x (redpanda-data/kminion)

Материал интегрирован из доклада Дмитрия Баскакова (MindBox) «Kafka в K8s — это просто!». Расшифровка доклада хранится в корне базы знаний.

---

## Определения

- **Техпродукт** — внутренний SaaS-сервис для разработки, цель которого — упростить и ускорить разработку, снизив контекст. Это не чарт и не возможность развернуть Kafka, а цельное решение: полный опыт использования технологии.
- **Тир (tier)** — готовый профиль конфигурации кластера, выбираемый одной опцией (буквой); каждый тир под свой сценарий — от небольшого потока данных до огромного батча.
- **USI (User Satisfaction Index)** — индекс удовлетворённости пользователей: метрика, классифицирующая запросы к кластеру на три категории (удовлетворительные / приемлемые / неудовлетворительные) относительно порогового времени запроса.
- **KMinion** — Prometheus-экспортёр для Kafka от Redpanda (Go, MIT-лицензия), опрашивающий кластер по протоколу Kafka: consumer-group лаги, размеры log-dirs, информация о брокерах, а также end-to-end мониторинг — производит и консьюмит тестовые сообщения в собственном топике, измеряя roundtrip-латентность.
- **KHQ** — веб-UI для Kafka (проект KHQ, переименованный в AKHQ); в описанном случае используется в read-only режиме.
- **KRaft** — режим работы Kafka без ZooKeeper (KIP-500), кворум контроллеров на протоколе Raft.
- **NLB** — облачный Network Load Balancer; **Ingress-NLB** — реализация внешнего доступа к Kafka через Ingress поверх NLB.
- **NUMA (Non-Uniform Memory Access)** — архитектура многопроцессорных серверов, где у каждого процессора своя локальная память; доступ к локальной памяти быстрее, чем к памяти другого процессора.
- **MM1 / MM2** — MirrorMaker 1 (legacy) и MirrorMaker 2 (построен на базе Kafka Connect) — инструменты межкластерной репликации.
- **Chaos-тесты** — тесты, имитирующие отказы (убить брокер, контроллер, зону) для проверки надёжности кластера.

## Контекст: почему Kubernetes

MindBox — крупнейшая в России SaaS-платформа автоматизации маркетинга; система высоконагруженная, Kafka — одна из ключевых технологий. Инфраструктура гетерогенна: несколько облаков + собственные стойки в ЦОД.

- Рост компании ~30% в год → рост числа кластеров.
- Весна 2024: ~200 кластеров Kafka на ВМ (Terraform + Ansible). К 2025 году — ~300.
- Модель автономности: команды разработки сами создают и конфигурируют свои кластеры (иногда несколько кластеров на команду).

Боли при таком масштабе:

1. **Низкий DX:** создание кластера для разработчика — в среднем 3–4 дня; огромная инструкция, в которой нужно внимательно следить за шагами и глубоко погружаться в контекст ради правильных переменных; то же самое для масштабирования и ребалансировки — автоматизация есть, но разработчику приходится что-то вбивать вручную; разработчики постоянно обращаются в поддержку, и даже хорошая документация не спасает.
2. **Перегрузка SRE:** много автоматизации, но частичной и разрозненной; runbook'ы перегружены, инженеры SRE тонут в них; гетерогенность инфраструктуры (нюансы облаков и ЦОД) сильно усложняет работу.
3. **Надёжность:** автономные разработчики не являются экспертами по Kafka; нет полноценных механизмов self-healing (брокер упал → пойти анализировать причину → запустить ручной runbook); старые версии Kafka 2.8 с ZooKeeper. Весной 2024 года произошли два массовых инцидента, показавших, что дальше так работать нельзя.

Варианты выхода: улучшать автоматизацию на ВМ (написать свой оркестратор) или прыгнуть в Kubernetes. Пути в K8s: чарты/манифесты, community-оператор, свой оператор. Свой оператор сразу отброшен: займёт много сил и времени, и его потом нужно поддерживать.

## Выбор оператора

Сравнивались актуальные на момент выбора операторы:

| Оператор | Статус | Комментарий |
|---|---|---|
| **Koperator** (бывший Banzai Cloud Kafka Operator) | open source | заархивирован 26.03.2025 (Cisco, купившей Banzai Cloud в 2021); развитие продолжается в форке Adobe — [adobe/koperator](https://github.com/adobe/koperator) |
| **Banzai Cloud Kafka** | open source | проекты Banzai Cloud по Kafka заархивированы весной 2025 |
| **Strimzi** | open source, CNCF-проект | **выбран** |
| **Confluent for Kubernetes (CFK)** | коммерческий | понравился больше всех, но платный |

Обновление с момента доклада: с Strimzi 1.0 поддерживается только CRD API `v1` — `v1beta2` удалён из CRD. Актуальная версия на октябрь 2026 — Strimzi 1.2.0 (поддержка Kafka 4.2/4.3, Kubernetes 1.30–1.36).

Что закрывает Strimzi:

- **Day 1 Operations:** создание кластеров, нативное подключение экосистемных компонентов, все абстракции описываются CRD. Кластер описывается парой манифестов: версия Kafka, количество реплик, роли (controller/broker), размер хранилища — кластер готов.
- **Day 2 Operations:** масштабирование, апгрейды, балансировка, конфигурации — всё через CRD. Ребалансировка внутри Kafka — одна строка в аннотации (ресурс `KafkaRebalance`, Cruise Control), заменяет bash-скрипт на ~500 строк.
- **Observability:** метрики, логи, трейсы доступны из коробки.
- **Безопасность:** интеграции есть, базовую авторизацию можно накрутить.

Чего Strimzi НЕ закрывает (решалось отдельно, техпродуктом):

- **Конфигурация для разработчика:** в Strimzi своих «миллион абстракций», в которых нужно довольно хорошо разбираться.
- **Ограничения для разработки:** Strimzi не вводит ограничений, которые помогли бы ограничить разработку.
- **Self-healing от ошибок людей:** поды Kubernetes поднимаются при падении, но разработчики и SRE всё ещё могут уронить кластер — оператор с этим ничего не сделает.

## Техпродукт: архитектура решения

Под капотом: чарт + клиентская библиотека + набор инфраструктурных интеграций, которые сильно снижают контекст для разработки и дают определённые гарантии надёжности.

### Нейминг кластеров

Имя кластера живёт не только в контексте клиента — оно сразу появляется в Kubernetes, дашбордах, service discovery и ADP (если он есть). Паттерн MindBox максимально прост: **префикс + имя + окружение**. Автоматическое прорастание имён в DNS: в MindBox используется Consul, публикация происходит сама (с помощью consul-k8s), отдельно заводить DNS-записи разработчикам не нужно.

### KRaft вместо ZooKeeper

- Бенчмарки: KRaft побеждает ZooKeeper во всех операциях.
- Главный аргумент: в Kafka 4.0 (март 2025) ZooKeeper полностью удалён — KRaft стал единственным режимом работы. Даже если апгрейд не в планах — задумайтесь о KRaft.
- MindBox перешёл на KRaft при миграции.

### Внешний доступ к кластерам

Strimzi предоставляет три типа внешних listener'ов (в терминах доклада — «Port / NLB / Ingress»):

1. **`nodeport`** — не самый удобный.
2. **`loadbalancer`** (NLB) — использовали изначально.
3. **`ingress`** — сначала не поехали, но потом пришли к нему (чтобы сократить количество NLB в облаках).

### Размещение кластеров

- Отдельный Kubernetes-кластер под Kafka **не** создают — слишком жирно для их масштаба. Большинство кластеров живёт в **общем нодпуле** (сотни кафок в одном). Для супержирных кластеров автоматически создаются **отдельные нодпулы**.
- Нодпулы распределены по зонам — с надёжностью в них всё хорошо.
- В рамках одного кластера **контроллеры и брокеры полностью раскладываются по разным зонам и нодам** — брокер и контроллер не могут оказаться на одной ноде. Остальные компоненты кластера размещаются рандомно: их выход из строя кластер сильно не аффектит.
- Почему не отдельный K8s-кластер: масштаб не в тысячи кластеров; при совместном размещении микросервисы ходят к Kafka по внутренним адресам без лишних хопов (NLB), что быстрее.

### Экосистемные компоненты

Kafka Connect и любые другие экосистемные компоненты подключаются через чарт: одной строкой разработчик включает компонент, при необходимости указывает параметры — и всё работает.

### Конфигурация Kafka: тиры

Разработчикам часто хочется настраивать всё самим, но границу проводить нужно. Подход MindBox — отдельные готовые профили (**тиры**), указываемые одной строкой-буквой; каждый тир под свой сценарий (небольшой поток данных ↔ огромный батч). Разработчик может не использовать тир, выставив нужную опцию, — но тогда за свою надёжность его команда отвечает сама.

Пример выбора разработчика: тир + `storage size` для контроллера и брокера (количество данных в каждой кафке разное). Можно указать только тир — поднимется кластер с дефолтными значениями.

### Масштабирование

- **Upscale:** поменять одну букву на другую.
- **Downscale:** требует дополнительной операции — сначала ребалансировка: включить ребаланс → дождаться окончания → скейл вниз → выключить ребаланс. Цель — довести процесс до автоматизации, чтобы и эта операция пропала.

### Надёжность: когда Kafka работает нормально, а не кажется

Ответ — в метрике **USI (индекс удовлетворённости пользователей)**. Она классифицирует запросы на три категории: удовлетворительные (зелёная), приемлемые (жёлтая), неудовлетворительная (красная). Пороговое время запроса считается легко; метрика по описанию доклада: (удовлетворительные + приемлемые) / 2 / сумма всех запросов за пороговое время. Нюанс: классическая формула Apdex-подобных индексов — (удовлетворительные + приемлемые/2) / все запросы; арифметика из доклада отличается, поэтому при внедрении уточните формулу под свою систему алертов.

Ни Kafka, ни экспортёры такую метрику из коробки не отдают. Попробованы два инструмента:

1. **e2e-мониторинг от разработчиков Strimzi** (в расшифрове доклада — «стримзири»; точное название проекта не подтверждено): отправляет тестовое сообщение через кластер и измеряет время доставки сообщений, отдаёт метрики в формате Prometheus. После ~1,5 месяцев эксплуатации обнаружилось, что он регулярно «протекает» (утечки ресурсов).
2. **KMinion от Redpanda** — выбран. Умеет всё то же самое плюс дополнительные метрики (например, consumer groups). Чтобы метрики появились, нужно определить секцию `endToEnd` в конфиге:

```yaml
# Конфиг KMinion: end-to-end мониторинг кластера
# (путь к YAML-файлу задаётся переменной окружения CONFIG_FILEPATH)
minion:
  endToEnd:
    enabled: true
    probeInterval: 800ms           # как часто слать тестовые сообщения
    topicManagement:
      name: kminion-end-to-end     # топик для тестовых сообщений
      reconciliationInterval: 10m  # проверка конфига, числа партиций и назначений топика
      replicationFactor: 1         # 1 — алерт на падение брокера; 3 — алерт на незаписываемый кластер
      partitionsPerBroker: 1       # по одной партиции на брокер
    producer:
      ackSla: 5s                   # SLA подтверждения записи
      requiredAcks: all
    consumer:
      groupIdPrefix: kminion-end-to-end
      roundtripSla: 20s            # SLA roundtrip'а сообщения
      commitSla: 10s               # SLA коммита офсетов
```

Экспортируемые метрики: `kminion_end_to_end_roundtrip_latency_seconds`, `kminion_end_to_end_produce_latency_seconds`, `kminion_end_to_end_offset_commit_latency_seconds`, `kminion_end_to_end_messages_lost_total`, `kminion_end_to_end_messages_produced_failed_total`, `kminion_end_to_end_messages_produced_in_flight`, `kminion_end_to_end_messages_received_total` и другие (полный список — в документации KMinion).

В Grafana — полная детализация: сразу видно, почему USI начинает проседать (например, на одном из брокеров повысилась нагрузка → возможно, проблема на ноде или в зоне; дальше — инструменты мониторинга помогают раскрутить).

### Chaos-тесты

Надёжность нельзя проверить на бумаге: из коробки добавлены хаос-тесты — можно случайно убить брокер, контроллер или даже сделать имитацию отказа зоны. Это даёт уверенность, что кластеры Kafka выдержат реальные сбои.

### Взаимодействие разработчиков с кластерами

Раньше разработчики использовали разные инструменты — от kcat и клиентских библиотек до локальных консолей. Собраны три кейса:

1. **Просмотр настроек и чтение сообщений — KHQ.** Перепробовали разные варианты, остановились на KHQ: не совсем красивый, но работает. Разработчик авторизуется в read-only режиме, видит все кластера и сообщения в них. Фанфакт: в большинстве UI, которые пробовали (например, Kafbat UI / kafka-ui), при большом количестве кластеров начинает ломаться UI. Чтобы все кластера автоматически подсасывались в KHQ, написан свой микросервис: умеет смотреть в Consul и релоадить конфиг KHQ.
2. **Конфигурирование топиков в узких кейсах — runbooks в CI.** Их очень мало (например, поменять retention динамического топика: задать значения и прогнать runbook — быстро, просто, понятно). Малое количество — гарантия, что эта часть не превратится в хаос. Сервис runbook'ов в MindBox — Octopus, но такие же пайплайны можно напилить в любой другой CI: GitLab, Jenkins, TeamCity.
3. **Прямой доступ к Kafka с машины разработчика.** В очень редких кейсах разработчикам требуется прямой доступ к кластерам, а доступа к проду у них нет. Проблема: при первом коннекте к кластеру Kafka возвращает в метаинформации прямые адреса брокеров — просто так запроксировать это не получится. Решение — **Teleport**: разработчик в специальной секции включает доступ через Teleport, публикуются специально образом порты; запрашивая стандартным образом доступ к приложению, опубликованному в Teleport, разработчик получает сертификат, и порты пробрасываются на его машину.

### Ограничения

Strimzi помогает ограничивать throughput, но этого недостаточно. Поэтому ряд ограничений впилен на клиенте: создание топиков, количество партиций и т. п.

## Миграция с ВМ на Kubernetes

Схема миграции проста:

1. Старый кластер на ВМ продолжает работать.
2. Поднимается новый кластер в Kubernetes.
3. Поднимается второй MirrorMaker, натравливается на старый кластер, начинает реплицировать.
4. Разработчик убеждается, что репликация прошла.
5. Переключаются консьюмеры, убеждаются, что всё хорошо.
6. Переключаются продюсеры.
7. Старый кластер удаляется, MirrorMaker выключается.

Пару слов про MirrorMaker 2:

- Для одинаковых имён топиков нужно переопределить `replication policy class` (по умолчанию MM2 добавляет префикс при репликации) — используется `IdentityReplicationPolicy` (детали и конфигурация — в [Capacity Planning и DR](./kafka_capacity_dr.md)).
- Следите за размером сообщений: если в буфер размер сообщений не пролезает, часть сообщений потеряете.
- **MM2 не реплицирует топики, попадающие под внутренний паттерн (Kafka < 4.0).** В `ReplicationPolicy` есть метод `isInternalTopic`: топики, начинающиеся с `__` или `.`, а также топики с суффиксом `.internal` / `-internal`, считаются внутренними и не реплицируются — на Kafka 2.8/3.x это поведение нельзя переопределить конфигурацией, только своей реализацией `ReplicationPolicy` (KAFKA-17200). В **Kafka 4.0** (KIP-1074) поведение изменили: бизнес-топики с суффиксом `.internal`/`-internal` реплицируются по умолчанию (дефолтный exclude-паттерн стал `mm2.*internal, .*\.replica, __.*`), внутренними остаются только `__`- и `.`-префиксы и `mm2.*internal`. Инцидент MindBox произошёл на старом стеке (2.8/3.x). Решение MindBox — добавить **MirrorMaker 1**: он без проблем реплицирует любые топики (офсеты не синхронизирует, но у MindBox есть идемпотентность).

### Тип сжатия

Холиварная тема. Раньше в MindBox использовали разные типы сжатия на разных кластерах, и почему так — уже не знал никто: кто-то обосновывал выбор, кто-то говорил «так исторически сложилось», где-то скопипастили. Статьи и поисковики рекомендуют LZ4 и ZSTD, но архитекторы потребовали тесты. Результат: на их нагрузке **GZIP оказался лучше** — не в каком-то конкретном ресурсе, а суммарно в стоимости ресурсов: экономия ~200 тыс. ₽ в месяц. Вывод: всегда тестируйте в реальности, а не доверяйте статьям. (Для телеметрии в [файле по мониторингу Kafka](./kafka_for_monitoring.md) рекомендованы LZ4/Zstd — контекст другой: бизнес-потоки MindBox.)

## Инциденты и troubleshooting миграции

### Параметры, которые нельзя переопределить в Strimzi

Если захотите, например, уменьшить время ожидания неотвечающего брокера, столкнётесь с тем, что в Strimzi это переопределить нельзя — как и ряд других параметров. Если у вас есть специфика — проверьте перед миграцией, можете ли вы её переопределить через Strimzi.

### История загадочного топика

После миграции порядка 20–30 кластеров команда сообщила: новый кластер поднят, репликация включена, всё среплицировалось ровно кроме одного топика. Диагностика: MirrorMaker'ы в порядке (регулярные выражения корректны, стоит `.*`), настройки обоих кластеров в порядке (кластер обычный, переопределений нет). Причина — в коде MM2: метод, определяющий, подходит ли топик под внутренний паттерн MM2; если подходит — топик не реплицируется, и поведение не переопределяется. Решение — добавить MirrorMaker 1 (см. выше). На Kafka 4.0+ (KIP-1074) этот класс инцидентов в значительной степени исчез — бизнес-топики с суффиксами `.internal`/`-internal` реплицируются по умолчанию (см. оговорку о версиях выше).

### Рост latency после миграции

Симптом: latency запросов стабильно выше, чем было (при изначальных тестах не был большим, внимания не обращали; увидели при анализе миграции по разным кластерам).

- Как работал старый кластер: клиент напрямую ходил в брокеры, без прокси и NLB.
- Как работает в K8s: клиент → NLB → **рандомная нода** → нода, на которой находится брокер.

Причина лишнего хопа — `externalTrafficPolicy: Cluster` (значение по умолчанию у Service): трафик от NLB может прилететь на любую случайную ноду (сделано для лучшего распределения трафика по кластеру). Решение — выставить `externalTrafficPolicy: Local`: NLB будет слать трафик только на те ноды, где поды с брокерами, и лишний хоп исчезнет. Учитывайте, что эта же история может аффектить вас, если у вас есть security-группы. Теория и нюансы `externalTrafficPolicy` — в [типах Service Kubernetes](../Kubernetes/Networking/Service/service_overview.md).

### Метрики растут линейно, kafka-exporter падает

На некоторых кластерах очень много метрик; метрики вроде consumer group растут линейно. Причина: kafka-exporter падает. Решение — замена на KMinion, у которого эти метрики есть. При этом сбор метрик **разделён**: один KMinion собирает метрики, необходимые разработчикам, второй — считает SLO, чтобы, если KMinion со сбором метрик не выдержит, SLO не пострадали. Часть метрик также подрезана через конфигурацию (manifest).

### Случайное удаление кластера разработчиком

Кейс (прошло ~70% миграции): у команды несколько кластеров со схожими названиями, разработчик перепутал и поставил опцию удаления не у того кластера. Хорошая новость: удалился только кластер, PV остались — к такому были готовы.

Важно: обычным перенакатом кластера не отделаться — у нового кластера новые идентификаторы, и «магия» не произойдёт сама. Починка: вытащить идентификаторы нового кластера и подсунуть их в PVC (метаданные KRaft на дисках), после чего перезапустить поды — всё автоматически подцепится. Для этого есть автоматический runbook (кейс продуман заранее).

Для удаления Kafka в техпродукте две опции: удалить кластер и удалить данные в кластере. В этом кейсе разработчик не знал о второй опции, поэтому не удалил данные, и кластер удалось спасти.

## Облачные приключения

### Тестируйте в масштабе

Рекомендация: проводите тесты того, что хотите сделать, в масштабе ×1.5. При тестировании развёртки в облаке (десяток кластеров) всё было хорошо, никаких проблем не было, но на ~90% процесса миграции у облачного провайдера возник ряд проблем.

### Ingress-NLB и сертификаты

Чтобы сократить количество NLB, реализован внешний доступ через Ingress-NLB. Это не лучший доступ (появляется плюс абстракции на пути к кластеру), но если делать нечего — работает. Ключевой нюанс: нужны сертификаты, и Strimzi рекомендует passthrough (серты должны быть на брокерах). Четыре варианта:

1. **Дефолт Strimzi** — Strimzi сам рулит именем сертификата, но вы должны вытащить сертификат и подложить его клиентам. Плюсов много.
2. **Корпоративный сертификат** — указываете в секрете/конфигмапе, но занимаетесь обновлением сами.
3. **Свои сертификаты для брокеров** — загрузить свои серты для брокеров.
4. **Интеграция с cert-manager** — использовали, но минус: при автоматическом обновлении сертов происходит роллинг-апдейт по кластеру в случайное время, и управлять этим техокном в этом кейсе нельзя. Поэтому реализацию перепиливают на встроенный Strimzi-серт с опцией указания техокна — `maintenanceTimeWindows` в `Kafka` CR (`Kafka.spec.maintenanceTimeWindows`, список cron-выражений, интерпретируемых в UTC): Strimzi поймёт, когда обновить серты можно, и сделает роллинг в окно. Проверенные нюансы: окна применяются только к сертификатам, которые генерирует сам Strimzi, — на cert-manager-серты они не действуют (именно поэтому роллинг от cert-manager происходит в случайное время); окно должно быть не короче интервала реконсиляции оператора, иначе обновление может выйти за его границы.

Если очень хочется — можно и без passthrough: будет просто терминация TLS на ингрессе.

### Consul: публикация Ingress и флап

- DNS в Consul публикуется автоматически с помощью consul-k8s. Для Ingress'а захотели сделать то же, но в community-версии consul-k8s публикация Ingress в Consul не поддерживается — написали свою версию, которая умеет публиковать Ingress в Consul. Она получилась настолько хорошей, что думают вообще отказаться от consul-k8s.
- Жирный минус consul-k8s: если поды Consul убить или они перераспределятся, произойдёт дерегистрация и регистрация заново в Consul, из-за чего будет флап на микросервисах.

### NUMA на суперкрупных нодах

Проблемы провайдера заставили создать суперкрупные ноды — и это активировало NUMA. Простыми словами: у сервера несколько процессоров, у каждого своя память, локальный доступ к ней быстрее, чем к памяти другого процессора. Результат: CPU вырос примерно в 1.8 раза. Если планируете крутить Kafka на жирных нодах — тестируйте такую нагрузку заранее, чтобы не получить неожиданность; в целом лучше избегать такой ситуации. Про NUMA-оптимизацию в целом — в [методологии нагрузочного тестирования](../Testing/performance_testing_methodology.md) и [борьбе с tail latency](../Concepts/High_Availability/tail_latency_mitigation.md).

## Техпродукт как продукт

Важно помнить, что техпродукт — это продукт: в начале разработки об этом забыли, и пару раз обновления подламывали некоторые кластеры (клиентам это не сказалось). Чтобы улучшить опыт:

- написаны тесты: функциональные, нагрузочные и e2e;
- введены ограничения с помощью value schema для чарта;
- припилено регулярное обновление минорных версий (мажорные пока не обновляют автоматически);
- поверх всего — релизная политика: выкатить новый релиз без полноценного прохождения тестов нельзя.

## Результаты миграции

- **DX:** победил примерно на 95% — тикетов, связанных с Kafka, стало значительно реже, задач на улучшения осталось минимум; опрос разработчиков: новый экспириенс не поругали.
- **Надёжность:** массовых инцидентов на мигрированных кластерах не было. Кейс: разработчик набагал в коде, и его микросервис начал бесконечно создавать топики — на старой инфраструктуре он бы наверняка убил кластер, а здесь сработали лимиты: сервис отстрелился, деградация части функционала, но кластер и клиенты в корректном функционале не пострадали.
- **Стоимость:** Kafka в K8s не выросла по сравнению с Kafka на ВМ — примерно равны. При этом за год число кластеров выросло до ~300, а затраты значительно не увеличились. Не потому, что Kafka в K8s супердешёвая или требует меньше ресурсов: разработчик может просто привести свою конфигурацию к оптимальному значению и тратить меньше, и это стоит ему меньше времени, чем раньше.

**Что дальше:** переход на Kafka 4.x (4.0 вышла в марте 2025, актуальная линейка на октябрь 2026 — 4.3.x), честный autoscaling (Kafka сама добавляет или убавляет брокеров и меняет параметры в рамках своего тира), Tiered Storage.

## Контрольный вопрос из доклада (надёжность)

Условие: кластер Kafka, три брокера; `replication factor` топиков = 3, `min.insync.replicas` = 2, на клиенте `acks` = `all`. Один из брокеров становится недоступным. Что будет для продюсера?

Ответ (правильный — вариант 3): **продюсить сможем, но через какое-то время.** Почему: один брокер падает, часть реплик выходит из ISR; Kafka начинает пересчитывать, кто теперь лидер партиции. Так как на клиенте стоит `acks=all`, оно ждёт подтверждения от всех реплик — поэтому Kafka должна убрать недоступную реплику из ISR и пересчитать новый набор реплик, доступных для продюса. Этот пересчёт включает обновление метаинформации о партициях и репликах, которую контроллер отдаёт клиентам. Механизм исключения реплики из ISR (ISR Shrink, `AlterPartition` в KRaft) подробно разобран в [ISR и репликация](./kafka_isr_replication.md).

## Best Practices

1. **Тестируйте в масштабе ×1.5** то, что планируете делать в облаке, до миграции.
2. **Тестируйте сжатие на реальной нагрузке** — статьи рекомендуют LZ4/ZSTD, но на бизнес-потоках MindBox лучше оказался GZIP.
3. **Тестируйте NUMA-настройки** на жирных нодах заранее; в целом избегайте суперкрупных нод.
4. **Проверяйте переопределяемость параметров** в Strimzi до миграции (часть параметров переопределить нельзя).
5. **Разделяйте сбор метрик** (разработчики vs SLO) и подрезайте лишние метрики — kafka-exporter не выдерживает сотни кластеров и групп.
6. **Используйте e2e-мониторинг** (KMinion) для USI-подобной метрики и хаос-тесты для проверки надёжности.
7. **Ограничивайте разработчиков на клиенте** (создание топиков, количество партиций) — ограничений Strimzi недостаточно.
8. **Продумывайте восстановление после случайного удаления** кластера (PVC + идентификаторы кластера) заранее, автоматизируйте runbook'ом.
9. **Управляйте техокном** обновления сертификатов (`maintenanceTimeWindows`), а не полагайтесь на случайное время роллинга cert-manager.
10. **Релизная политика для техпродукта:** тесты (функциональные, нагрузочные, e2e), value schema, минорные обновления, релиз только после прохождения тестов.
11. **Учитывайте версию Kafka при репликации:** на Kafka < 4.0 MM2 не реплицирует топики с суффиксом `.internal`/`-internal` (только кастомная `ReplicationPolicy` или MM1); на Kafka 4.0+ (KIP-1074) такие топики реплицируются по умолчанию.
