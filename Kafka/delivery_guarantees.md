# Гарантии доставки и надежность данных

**Гарантии доставки** — это набор обязательств, которые брокер сообщений и клиентские библиотеки берут на себя для обеспечения сохранности и корректности передачи данных. Выбор конкретной гарантии всегда является компромиссом между надёжностью, пропускной способностью и сложностью реализации.

---

## Определения

- **At-most-once (не более одного раза):** Сообщение доставляется 0 или 1 раз. Брокер не гарантирует доставку, а консьюмер не подтверждает получение. Возможны потери данных, но дубликаты исключены.
- **At-least-once (не менее одного раза):** Сообщение гарантированно доставляется 1 или более раз. Потери исключены при условии доступности брокера, но возможны дубликаты из-за сетевых сбоев при отправке подтверждений. Требует идемпотентности на стороне потребителя.
- **Exactly-once (ровно один раз):** Каждое сообщение обрабатывается системой ровно один раз. Это не означает отсутствие повторных отправок, но гарантирует, что итоговое состояние системы будет таким, как если бы сообщение было получено и обработано строго единожды.
- **Идемпотентность (Idempotence):** Свойство операции, при котором её многократное выполнение дает тот же результат, что и однократное. Критически важно для семантики At-least-once. Глубокая теория и паттерны реализации: [Идемпотентность](../Concepts/idempotency.md).
- **Подтверждение (Acknowledgement / Ack):** Сигнал от получателя отправителю (или от брокера продюсеру) о том, что сообщение успешно принято и обработано.
- **Publisher Confirms:** Механизм RabbitMQ: брокер подтверждает продюсеру получение сообщения после его безопасной записи (на диск или репликацию в кворумную очередь).
- **Транзакционный ID (Transactional ID):** Уникальный стабильный идентификатор продюсера в Kafka, позволяющий брокеру идентифицировать конкретный экземпляр приложения и предотвращать «зомби-записи» от старых инстансов после рестарта.
- **Producer ID (PID) и Epoch:** Брокер назначает каждому идемпотентному продюсеру PID, а каждой новой сессии — возрастающий номер эпохи. Эпоха используется для фенсинга: записи от устаревшей эпохи отбрасываются.
- **Зомби-инстанс (Zombie Instance):** Старый экземпляр приложения, который считает себя активным и пытается писать в брокер (например, после временной заморозки JVM или сетевого разрыва).
- **Фенсинг (Fencing):** Механизм изоляции и блокировки зомби-инстансов через инкремент эпохи (epoch) транзакции.
- **`__transaction_state`:** Внутренний топик Kafka, хранящий состояние всех транзакций (координатор транзакций живет на брокере-лидере его партиции).
- **Last Stable Offset (LSO):** Граница в партиции, до которой транзакции завершены. Консьюмер с `isolation.level=read_committed` не видит данные за пределами LSO.
- **In-Flight Messages:** Количество сообщений, отправленных продюсером, на которые ещё не получено подтверждение от брокера.

## Основные концепции

### Сравнительный анализ семантик

Kafka поддерживает три основных уровня гарантий. Важно понимать, что **Exactly-once не является поведением по умолчанию**.

| Гарантия | Риск потери | Риск дубликатов | Нагрузка / Latency | Типичные сценарии |
| :--- | :--- | :--- | :--- | :--- |
| **At-most-once** | Да | Нет | Минимальная | Сбор метрик, UDP-подобные потоки телеметрии. |
| **At-least-once (default)** | Нет | Да | Средняя | Платежи, заказы (с дедупликацией в БД). |
| **Exactly-once** | Нет | Нет | Высокая | Финансовый клиринг, агрегация данных в реальном времени. |

**Особенности At-least-once (по умолчанию):**
Kafka гарантирует, что сообщение не будет потеряно, но оно может быть обработано более одного раза. 
- **Сценарий дублирования:** Консьюмер прочитал сообщение, успешно выполнил бизнес-логику (например, списал оплату), но упал **до того**, как успел зафиксировать (commit) смещение (offset) в Kafka. После перезапуска консьюмер увидит то же сообщение (так как в Kafka его офсет не обновился) и обработает его повторно.

**Важность идемпотентности консьюмеров:**
Поскольку дубликаты возможны, критически важно, чтобы логика обработки была **идемпотентной**. Если платежный сервис получает запрос на списание по заказу №101 второй раз, он должен проверить статус заказа в своей БД и не производить повторное списание. Каталог приемов (Inbox-паттерн, конечный автомат статусов, ложная идемпотентность): [Идемпотентность](../Concepts/idempotency.md).

### Гарантии определяются двумя сторонами: продюсер и консьюмер

Распространенная ошибка — думать о гарантиях только на стороне продюсера. Семантика складывается из поведения **обоих** концов канала:

**Сторона продюсера (Kafka):** уровень `acks`, идемпотентность, ретраи — см. ниже.

**Сторона консьюмера:** момент фиксации офсета решает, какая семантика получится фактически:

| Поведение консьюмера | Получившаяся семантика | Механика |
| :--- | :--- | :--- |
| `enable.auto.commit=true` | Непредсказуемая | Автокоммит срабатывает по таймеру: если он случился до конца обработки — потери (at-most-once); если приложение упало до следующего автокоммита — дубликаты (at-least-once) |
| Коммит офсета **до** обработки | At-most-once | После перезапуска сообщение уже «прочитано» и не доставится повторно |
| Коммит офсета **после** обработки (ручной) | At-least-once | Падение между обработкой и коммитом приводит к повторной доставке |
| Транзакционный цикл consume-produce | Exactly-once (внутри Kafka) | Офсет фиксируется атомарно с результатом обработки |

Дополнительный источник дубликатов: превышение `max.poll.interval.ms` вызывает ребалансировку посреди обработки — партиция уходит другому члену группы, а старый обработчик еще мог успеть записать результат. Держите интервал с запасом относительно времени обработки батча.

### Реализация надежности в RabbitMQ

RabbitMQ полагается на подтверждения на каждом этапе пути сообщения. Подробнее: **[Обзор RabbitMQ](../rabbitmq/overview.md)**.

1. **At-most-once:** Продюсер отправляет данные без ожидания подтверждения (publisher confirms выключены). Консьюмер использует `auto_ack=true` (сообщение удаляется из очереди сразу после отправки брокером в сокет).
2. **At-least-once:**
   - **Продюсер:** Использует **Publisher Confirms**. Брокер отправляет `ack` продюсеру только после того, как сообщение было записано на диск или реплицировано в кворумную очередь. Для защиты от потери при отсутствии маршрута добавляется флаг `mandatory` (сообщение вернется отправителю вместо тихого удаления).
   - **Консьюмер:** Использует ручные подтверждения (`basic.ack`). Сообщение остается в очереди, пока приложение не подтвердит успешную обработку. Незакрытый канал или разрыв соединения возвращают сообщение в очередь (requeue).
   - **Ограничитель повторов:** В кворумных очередях параметр `x-delivery-limit` ограничивает число доставок одного сообщения (по умолчанию 20), после чего оно уходит в Dead Letter Queue — защита от бесконечного requeue «отравленного» сообщения.
3. **Exactly-once:** Нативно не поддерживается брокером. Реализуется через:
   - **Дедупликацию:** Использование уникального ID сообщения и проверка его наличия в кэше/БД перед обработкой.
   - **Паттерн Transactional Outbox:** Совместная запись данных и события в одну БД (см. Практические сценарии).

### Реализация надежности в Kafka

Kafka предоставляет более глубокую интеграцию для обеспечения гарантий на уровне протокола.

#### Настройка продюсера (acks)
- `acks=0`: Продюсер не ждет ответа.
- `acks=1`: Продюсер ждет подтверждения только от лидера партиции.
- `acks=all` (или `-1`): Продюсер ждет подтверждения от всех реплик из списка ISR. Это самая надежная настройка.

> `acks=all` сам по себе недостаточен: без брокерного `min.insync.replicas >= 2` подтверждение лидера-одиночки формально проходит проверку. Связка RF=3 + `min.insync.replicas=2` + `acks=all` — стандартная формула durability; таблица настроек и failover-сценарий: [Партиционирование и балансировка](./partitioning_and_balancing.md).

#### Идемпотентный продюсер (Enable Idempotence)
Начиная с Kafka 3.0, параметр `enable.idempotence=true` включен по умолчанию (вместе с ним автоматически выставляются `acks=all`, `retries=Integer.MAX_VALUE` и `max.in.flight.requests.per.connection <= 5`).
- **Механизм:** Продюсеру присваивается Producer ID (PID), а каждому сообщению — порядковый номер (Sequence Number). Брокер игнорирует сообщения с номером, который уже был успешно записан, что исключает дубликаты при сетевых сбоях.
- **Границы действия:** Защита работает **в рамках одной сессии продюсера и одной партиции**: она устраняет дубликаты от собственных ретраев, но не спасает от повторной отправки после рестарта приложения и не дает атомарности между партициями.

#### Exactly-once Semantics (EOS)
Kafka обеспечивает EOS в сценариях «чтение-обработка-запись» (read-process-write).

**Важное ограничение:** Exactly-once гарантируется **только внутри экосистемы Kafka** (транзакции между топиками одного кластера). Если приложение пишет данные во внешнюю базу данных или вызывает внешний API, семантика откатывается к **At-least-once**, так как Kafka не может гарантировать атомарность внешнего действия и фиксации офсета. В таких случаях по-прежнему требуется идемпотентность на стороне получателя.

Также учтите: EOS **не дедуплицирует входящие данные**. Если продюсер выше по цепочке отправил одно и то же событие дважды как два разных сообщения, для Kafka это два независимых входа, и каждый будет обработан ровно один раз.

Механизмы EOS:
1. **Транзакции:** Группа записей в разные топики и коммит офсетов прочитанных сообщений объединяются в атомарную транзакцию.
2. **Zombie Fencing:** Использование `transactional.id` позволяет брокеру принудительно завершить транзакции старого экземпляра. Серверная сторона защиты усилена в KIP-890 («Transactions Server-Side Defense»): координатор отклоняет записи с устаревшей эпохой даже в краевых случаях частично закоммиченных транзакций.
3. **EOS v2 (KIP-447):** Современная реализация для приложений с ручным управлением (и Kafka Streams, где включается через `processing.guarantee=exactly_once_v2`). Офсет-коммит транзакционного продюсера несет метаданные группы консьюмеров (member/generation id): после ребалансировки попытка «зависшего» старого инстанса закоммитить транзакцию проваливает проверку поколения и фенсится. Исключения вида `ProducerFencedException` / `InvalidProducerEpochException` в этот момент — признак нормальной работы защиты, а не аварии.
4. **Isolation Level:** Консьюмеры должны использовать `isolation.level=read_committed`, чтобы видеть только те сообщения, транзакции по которым были успешно зафиксированы (читаются записи до LSO).

#### Требования к брокерам для EOS

Состояние транзакций хранится во внутреннем топике `__transaction_state`. Его durability настраивается брокерными параметрами со строгими значениями по умолчанию:

```properties
# Значения по умолчанию на брокере:
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2
transaction.max.timeout.ms=900000        # потолок для клиентского transaction.timeout.ms
```

Отсюда практическое следствие, часто ставящее разработчиков в тупик: **на dev-кластере из одного брокера транзакционный продюсер зависает на `initTransactions()`** — внутренний топик не создается, пока кластер меньше требуемого фактора репликации, и вызов упирается в таймаут `max.block.ms` (60 c). Для локальной разработки допустимо снизить оба параметра до 1 (см. Практические сценарии); в production так делать нельзя.

Клиентский `transaction.timeout.ms` (по умолчанию 60 c) задает максимальную длительность одной транзакции: координатор прерывает транзакции, живущие дольше. Он должен быть больше времени обработки батча и согласован с `delivery.timeout.ms`.

## Практические сценарии

### Паттерн: Transactional Outbox
Используется для надежной отправки событий при изменении данных в БД.

1. **Запись:** В рамках одной транзакции БД обновляются бизнес-данные и записывается событие в служебную таблицу `outbox`.
2. **Передача (Relay):** Отдельный процесс (Relay) или CDC-инструмент (например, Debezium) читает таблицу `outbox` и публикует сообщения в брокер.
3. **Очистка:** После успешной отправки записи из `outbox` удаляются или помечаются как отправленные.

**Результат:** Гарантия **At-least-once** доставки события в брокер: если бизнес-данные сохранились, сообщение точно будет отправлено, но возможно дублирование (например, relay упал между публикацией и пометкой записи). Эффект «ровно один раз» достигается только добавлением дедупликации на приемнике. Подробное сравнение Relay против CDC и схема Inbox: [Распределенные транзакции](../Databases/Concepts/distributed_transactions.md), [Идемпотентность](../Concepts/idempotency.md).

### Паттерн: Идемпотентный потребитель (Idempotent Consumer)
Самый распространенный способ обработки дубликатов при семантике **At-least-once**.
1. Продюсер добавляет в сообщение уникальный `request_id`.
2. Потребитель перед обработкой проверяет наличие этого ID в базе данных (например, в таблице `processed_messages`).
3. Если ID найден — сообщение пропускается. Если нет — выполняется бизнес-логика и ID сохраняется в рамках одной транзакции.

### Обработка ошибок и DLQ (Dead Letter Queues)
Для предотвращения бесконечных циклов обработки «битых» сообщений (poison pills) используются очереди «мертвых писем».
- **Принцип:** Если сообщение не удалось обработать после N попыток, оно перемещается в специальную очередь (в RabbitMQ) или топик (в Kafka) для ручного анализа.
- **RabbitMQ:** Настраивается через `x-dead-letter-exchange`; счетчик доставок ограничивается `x-delivery-limit` (кворумные очереди).
- **Kafka:** Реализуется на стороне консьюмера (перенаправление сообщения в другой топик). Альтернатива DLQ — паттерн retry-топиков (`orders.retry.5m`, `orders.retry.30m`) с отложенным повтором; в Kafka Streams есть встроенный обработчик десериализации (`DeserializationExceptionHandler`), отправляющий битые записи в DLT-топик.
- **Важно:** Сообщение в DLQ — это не решение проблемы, а ее локализация. Настройте алертинг на глубину DLQ.

### Сценарий: включение EOS на dev-кластере из одного брокера

Одноброкерный стенд из [Развертывания в Docker](./kafka_docker_setup.md) не примет транзакционный продюсер с настройками по умолчанию. Добавьте в конфигурацию брокера:

```properties
# ТОЛЬКО для локальной разработки! В production запрещено.
transaction.state.log.replication.factor=1
transaction.state.log.min.isr=1
offsets.topic.replication.factor=1
```

**Проверка работоспособности транзакций:**

```bash
docker exec -it kafka-broker kafka-transactions.sh list --bootstrap-server localhost:9092
# → TRANSACTIONAL-ID  PRODUCER-ID  LAST-TIMEOUT
#    (пустой список до первого транзакционного продюсера — это норма)
```

Полный справочник CLI: [CLI-инструменты Kafka](./kafka_cli_tools.md). Замер цены надежности (`acks=all` против `acks=1` через `kafka-producer-perf-test.sh`): там же, раздел Performance Test.

### Пример кода: Транзакционная обработка в Kafka (Python)

Канонический цикл consume-transform-produce на библиотеке `confluent-kafka`. Ключевой момент: в транзакцию отправляются **текущие позиции консьюмера** по всем назначенным партициям, а не watermark-границы.

```python
from confluent_kafka import Producer, Consumer, KafkaException

# --- Продюсер для Exactly-once ---
producer = Producer({
    'bootstrap.servers': 'localhost:9092',
    'transactional.id': 'order-processor-v1', # Уникальный и СТАБИЛЬНЫЙ ID для фенсинга
    'transaction.timeout.ms': 60000,          # > времени обработки батча
})

# --- Консьюмер ---
consumer = Consumer({
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'order-group',
    'enable.auto.commit': False,              # Только ручной коммит внутри транзакции!
    'isolation.level': 'read_committed'       # Видим только закоммиченные данные
})
consumer.subscribe(['orders-input'])

# Инициализация транзакций: регистрация transactional.id, фенсинг прошлых сессий
producer.init_transactions()

try:
    while True:
        msg = consumer.poll(1.0)
        if msg is None:
            continue
        if msg.error():
            raise KafkaException(msg.error())  # Фатальные ошибки не глушим

        producer.begin_transaction()
        try:
            # Бизнес-логика трансформации
            processed_data = transform_order(msg.value())

            # Отправка результата в выходной топик
            producer.produce('orders-output', value=processed_data)

            # Коммит позиций ВСЕХ назначенных партиций в рамках этой же транзакции.
            # Метаданные группы позволяют координатору фенсить инстансы
            # после ребалансировки (EOS v2, KIP-447).
            producer.send_offsets_to_transaction(
                consumer.position(consumer.assignment()),
                consumer.consumer_group_metadata()
            )

            producer.commit_transaction()
        except Exception as e:
            producer.abort_transaction()
            print(f"Ошибка обработки, транзакция откачена: {e}")
            # Оффеты не закоммичены — сообщения будут доставлены повторно
finally:
    consumer.close()
    producer.flush()
```

После `abort_transaction()` офсеты остаются незаккоммиченными — при следующем поллинге группа получит тот же батч заново (естественный retry на уровне семантики at-least-once внутри транзакционного цикла).

| Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `initTransactions()` виснет 60 c и падает по `max.block.ms` | Dev-кластер из 1–2 брокеров не может создать `__transaction_state` (дефолт RF=3, min.isr=2) | Для dev снизить `transaction.state.log.replication.factor=1` и `min.isr=1`; в production держать 3 брокера |
| `ProducerFencedException` / `InvalidProducerEpochException` после ребаланса | Нормальный фенсинг: старый инстанс пытался писать с устаревшей эпохой | Не «чинить»: убедиться, что новый владелец партиции обрабатывает поток; Streams восстанавливается сам |
| Дубликаты в выходном топике при включенном `exactly_once_v2` | EOS не дедуплицирует вход: апстрим отправил два разных сообщения | Чинить источник или добавить дедуп-шаг; EOS защищает только свой цикл обработки |
| Консьюмер видит «мусорные» незакоммиченные записи | Забыт `isolation.level=read_committed` (default `read_uncommitted`) | Явно задать уровень изоляции у всех читателей транзакционных топиков |
| `NOT_ENOUGH_REPLICAS` у продюсера с `acks=all` | ISR просело ниже `min.insync.replicas` | Диагностика и действия: [Обзор Apache Kafka](./kafka_overview.md), раздел Troubleshooting |
| Нарушение порядка сообщений при ретраях без идемпотентности | `retries > 0`, `max.in.flight > 1`, идемпотентность выключена | Не отключать `enable.idempotence` (или держать `max.in.flight=1` ценой throughput) |
| Потери при `enable.auto.commit=true` под нагрузкой | Автокоммит сработал до конца обработки батча | Ручной коммит после обработки; либо осознанно принять at-most-once |

### Глоссарий

| Термин | Описание |
| :--- | :--- |
| **ISR** | In-Sync Replicas. Реплики, полностью догнавшие лидера. |
| **DLQ** | Dead Letter Queue. Очередь для сообщений, которые не удалось обработать. |
| **Sequence Number** | Порядковый номер сообщения в батче продюсера для дедупликации на брокере. |
| **Transactional ID** | Идентификатор, обеспечивающий атомарность записей и фенсинг. |
| **PID** | Producer ID, выдается брокером идемпотентному продюсеру. |
| **Epoch** | Возрастающий номер сессии продюсера; инструмент фенсинга зомби. |
| **LSO** | Last Stable Offset — граница видимости для `read_committed` консьюмеров. |
