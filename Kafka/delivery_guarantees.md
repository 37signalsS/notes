# Гарантии доставки в системах обмена сообщениями

**Гарантии доставки** — это набор обязательств, которые брокер сообщений и клиентские библиотеки берут на себя для обеспечения сохранности и корректности передачи данных. Выбор конкретной гарантии всегда является компромиссом между надёжностью, пропускной способностью и сложностью реализации.

---

## Определения

- **At-most-once (не более одного раза):** Сообщение доставляется 0 или 1 раз. Брокер не гарантирует доставку, а консьюмер не подтверждает получение. Возможны потери данных, но дубликаты исключены.
- **At-least-once (не менее одного раза):** Сообщение гарантированно доставляется 1 или более раз. Потери исключены при условии доступности брокера, но возможны дубликаты из-за сетевых сбоев при отправке подтверждений. Требует идемпотентности на стороне потребителя.
- **Exactly-once (ровно один раз):** Каждое сообщение обрабатывается системой ровно один раз. Это не означает отсутствие повторных отправок, но гарантирует, что итоговое состояние системы будет таким, как если бы сообщение было получено и обработано строго единожды.
- **Идемпотентность (Idempotence):** Свойство операции, при котором её многократное выполнение дает тот же результат, что и однократное. Критически важно для семантики At-least-once.
- **Подтверждение (Acknowledgement / Ack):** Сигнал от получателя отправителю (или от брокера продюсеру) о том, что сообщение успешно принято и обработано.
- **Транзакционный ID (Transactional ID):** Уникальный идентификатор продюсера в Kafka, позволяющий брокеру идентифицировать конкретный экземпляр приложения и предотвращать «зомби-записи» от старых инстансов после рестарта.
- **In-Flight Messages:** Количество сообщений, отправленных продюсером, на которые ещё не получено подтверждение от брокера.

## Основные концепции

### Сравнительный анализ семантик

| Гарантия | Риск потери | Риск дубликатов | Нагрузка / Latency | Типичные сценарии |
| :--- | :--- | :--- | :--- | :--- |
| **At-most-once** | Да | Нет | Минимальная | Сбор метрик, UDP-подобные потоки телеметрии. |
| **At-least-once** | Нет | Да | Средняя | Платежи, заказы (с дедупликацией в БД). |
| **Exactly-once** | Нет | Нет | Высокая | Финансовый клиринг, агрегация данных в реальном времени. |

### Реализация надежности в RabbitMQ

RabbitMQ полагается на подтверждения на каждом этапе пути сообщения. Подробнее: **[Обзор RabbitMQ](../rabbitmq/overview.md)**.

1. **At-most-once:** Продюсер отправляет данные без ожидания подтверждения. Консьюмер использует `auto_ack=true` (сообщение удаляется из очереди сразу после отправки брокером в сокет).
2. **At-least-once:**
   - **Продюсер:** Использует **Publisher Confirms**. Брокер отправляет `ack` продюсеру только после того, как сообщение было записано на диск или реплицировано в кворумную очередь.
   - **Консьюмер:** Использует ручные подтверждения (`basic.ack`). Сообщение остается в очереди, пока приложение не подтвердит успешную обработку.
3. **Exactly-once:** Нативно не поддерживается брокером. Реализуется через:
   - **Дедупликацию:** Использование уникального ID сообщения и проверка его наличия в кэше/БД перед обработкой.
   - **Паттерн Transactional Outbox:** Запись сообщения в таблицу `outbox` той же БД, где лежат бизнес-данные, в рамках одной транзакции.

### Реализация надежности в Kafka

Kafka предоставляет более глубокую интеграцию для обеспечения гарантий на уровне протокола.

#### Настройка продюсера (acks)
- `acks=0`: Продюсер не ждет ответа.
- `acks=1`: Продюсер ждет подтверждения только от лидера партиции.
- `acks=all` (или `-1`): Продюсер ждет подтверждения от всех реплик из списка ISR. Это самая надежная настройка.

#### Идемпотентный продюсер (Enable Idempotence)
Начиная с Kafka 3.0, параметр `enable.idempotence=true` включен по умолчанию.
- **Механизм:** Продюсеру присваивается Producer ID (PID), а каждому сообщению — порядковый номер (Sequence Number). Брокер игнорирует сообщения с номером, который уже был успешно записан, что исключает дубликаты при сетевых сбоях (например, если `ack` потерялся, но данные записались).

#### Exactly-once Semantics (EOS)
Kafka обеспечивает EOS в сценариях «чтение-обработка-запись» (read-process-write).
1. **Транзакции:** Группа записей в разные топики и коммит офсетов прочитанных сообщений объединяются в атомарную транзакцию.
2. **Zombie Fencing:** Использование `transactional.id` позволяет брокеру принудительно завершить транзакции старого экземпляра продюсера (эпохи), если появился новый с тем же ID.
3. **Isolation Level:** Консьюмеры должны использовать `isolation.level=read_committed`, чтобы видеть только те сообщения, транзакции по которым были успешно зафиксированы.

## Практические сценарии

### Паттерн: Идемпотентный потребитель (Idempotent Consumer)

Самый распространенный способ обработки дубликатов при семантике **At-least-once**.
1. Продюсер добавляет в заголовок или тело сообщения уникальный `request_id`.
2. Потребитель перед обработкой проверяет наличие этого ID в базе данных (например, в таблице `processed_messages`).
3. Если ID найден — сообщение пропускается как дубликат. Если нет — выполняется бизнес-логика и ID сохраняется в рамках одной транзакции.

### Пример кода: Транзакционная обработка в Kafka (Python)

```python
from confluent_kafka import Producer, Consumer, KafkaError

# Настройка продюсера для Exactly-once
producer = Producer({
    'bootstrap.servers': 'localhost:9092',
    'transactional.id': 'order-processor-v1', # Уникальный ID для фенсинга
    'enable.idempotence': True,
    'acks': 'all'
})
producer.init_transactions()

# Настройка консьюмера
consumer = Consumer({
    'bootstrap.servers': 'localhost:9092',
    'group.id': 'order-group',
    'enable.auto.commit': False,
    'isolation.level': 'read_committed' # Видим только закоммиченные данные
})
consumer.subscribe(['orders-input'])

try:
    while True:
        msg = consumer.poll(1.0)
        if msg is None: continue
        if msg.error(): continue

        # Начало транзакции
        producer.begin_transaction()
        try:
            # Бизнес-логика трансформации
            processed_data = transform_order(msg.value())
            
            # Отправка результата в выходной топик
            producer.produce('orders-output', value=processed_data)
            
            # Коммит офсета в рамках этой же транзакции
            producer.send_offsets_to_transaction(
                consumer.get_watermark_offsets(msg.partition()),
                consumer.consumer_group_metadata()
            )
            
            # Фиксация всего батча действий
            producer.commit_transaction()
        except Exception as e:
            # Откат при любой ошибке
            producer.abort_transaction()
            print(f"Ошибка обработки, транзакция откачена: {e}")
finally:
    consumer.close()
```

### Настройка RabbitMQ для At-least-once (Quorum Queues)

Обеспечение надежности в RabbitMQ реализуется через использование **Quorum Queues**, включение **Publisher Confirms** на стороне продюсера и использование **Manual Acknowledgments** на стороне консьюмера.

Подробное описание настройки с примерами кода на Python приведено в основном разделе: **[Обзор RabbitMQ: Надежность и гарантии доставки](../rabbitmq/overview.md#надежность-и-гарантии-доставки)**.

### Глоссарий терминов

| Термин | Описание |
| :--- | :--- |
| **ISR (In-Sync Replicas)** | Реплики Kafka, которые не отстают от лидера и готовы стать новыми лидерами. |
| **DLQ (Dead Letter Queue)** | Очередь для «плохих» сообщений, которые не удалось обработать после N попыток. |
| **Zombie Instance** | Старый экземпляр приложения, который считает себя активным и пытается писать в брокер после сетевого разрыва. |
| **Fence (Фенсинг)** | Механизм изоляции и блокировки «зомби-инстансов» через инкремент эпохи (epoch). |
