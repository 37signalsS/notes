# Гарантии доставки и надежность данных

**Актуально для:** Apache Kafka 3.9 / 4.0 (KRaft), RabbitMQ 3.13 / 4.0

**Гарантии доставки** — это совокупность архитектурных и протокольных обязательств, которые брокер сообщений, операционная система хоста и клиентские библиотеки берут на себя для обеспечения сохранности, целостности и порядка передачи данных. В распределенных системах выбор конкретной семантики всегда представляет собой инженерный компромисс между абсолютной надежностью (durability), задержкой (latency), пропускной способностью (throughput) и эксплуатационной сложностью.

---

## Определения

- **At-most-once (не более одного раза):** Сообщение доставляется 0 или 1 раз. Брокер не гарантирует сохранность при сбое, а консьюмер подтверждает получение до обработки. Потери данных возможны, но дублирование полностью исключено.
- **At-least-once (не менее одного раза):** Сообщение гарантированно доставляется 1 или более раз. Потери исключены при условии доступности кворума брокеров, но возможны дубликаты из-за сетевых сбоев при передаче подтверждений (acknowledgements). Требует обеспечения идемпотентности на стороне потребителя.
- **Exactly-once (ровно один раз):** Каждое сообщение обрабатывается системой строго один раз. В распределенной среде это реализуется не отсутствием сетевых повторов, а тем, что итоговое состояние системы эквивалентно строго однократной обработке (дедупликация + атомарная фиксация состояния).
- **Идемпотентность (Idempotence):** Свойство операции давать идентичный результат при многократном повторении с теми же параметрами. Фундаментальный базис надежности распределенных систем: [Идемпотентность](../Concepts/idempotency.md).
- **Подтверждение (Acknowledgement / Ack):** Квитанция, передаваемая получателем отправителю (консьюмером брокеру или брокером продюсеру), подтверждающая прием, фиксацию на диске или репликацию батча сообщений.
- **Publisher Confirms:** Асинхронный протокольный механизм RabbitMQ: брокер возвращает продюсеру подтверждение (`ack`) только после надежной записи сообщения (на диск или репликации в кворум узлов Raft).
- **ISR (In-Sync Replicas):** Множество реплик партиции Kafka, которые не отстают от лидера более чем на интервал `replica.lag.time.max.ms` и полностью синхронизировали лог.
- **High Watermark (HW):** Наибольший офсет в партиции Kafka, который был успешно отреплицирован на все узлы из текущего списка ISR. Консьюмеры в стандартном режиме читают данные только до границы High Watermark.
- **Last Stable Offset (LSO):** Нижняя граница офсета в партиции Kafka, до которой завершены все начатые транзакции (закоммичены или откачены). Консьюмер с `isolation.level=read_committed` видит сообщения только до границы LSO.
- **Producer ID (PID) и Sequence Number:** Уникальный идентификатор сессии продюсера (PID) и монотонно возрастающий номер сообщения (Sequence Number) внутри партиции, используемые брокером для аппаратной дедупликации при включенной идемпотентности.
- **Producer Epoch:** Возрастающий счетчик поколения сессии продюсера; предотвращает коллизии и зомби-записи при перезапуске клиента или сетевой изоляции.
- **Transactional ID:** Стабильный строковый идентификатор транзакционного продюсера, сохраняющийся между перезапусками процесса и позволяющий координатору изолировать зомби-инстансы.
- **Зомби-инстанс (Zombie Instance):** Экземпляр продюсера или консьюмера, временно отделившийся из-за GC-паузы или сетевого сплита, который ошибочно считает себя активным и пытается совершать операции записи.
- **Фенсинг (Fencing):** Механизм изоляции и блокировки устаревших зомби-инстансов брокером через инкремент эпохи транзакции (`ProducerEpoch`) или поколения консьюмер-группы (`generation_id`).
- **`__transaction_state`:** Внутренний системный топик Kafka, в котором Transaction Coordinator сохраняет статус и журнал двухфазного коммита всех распределенных транзакций.
- **In-Flight Messages:** Максимальное количество батчей сообщений, отправленных клиентом в сетевой сокет, на которые еще не получен ответ от брокера.
- **Dead Letter Queue (DLQ / DLT):** Выделенная очередь в RabbitMQ или топик в Kafka, куда направляются сообщения, обработка которых завершилась неустранимой ошибкой после исчерпания лимита повторных попыток.
- **Poison Pill («отравленное сообщение»):** Некорректно сформированное сообщение, приводящее к фатальному сбою консьюмера при каждой попытке десериализации или обработки, вызывая бесконечный цикл ретраев.

## Основные концепции

### Сравнительный анализ семантик доставки

Гарантии доставки определяют поведение системы при возникновении сбоев сети, падении узлов кластера или аварии клиентского приложения.

| Гарантия | Риск потери | Риск дубликатов | Влияние на Throughput / Latency | Типичные сценарии использования |
| :--- | :--- | :--- | :--- | :--- |
| **At-most-once** | Да (при сбое) | Исключен | Минимальная задержка, максимальный throughput | Сбор высокочастотных метрик, телеметрия, логирование некритичных событий |
| **At-least-once (default)** | Исключен (при кворуме) | Да (при таймаутах/ретраях) | Сбалансированная нагрузка, средняя задержка | Заказы, учетные события, аудит, интеграция микросервисов с дедупликацией в БД |
| **Exactly-once** | Исключен | Исключен | Повышенная задержка (координация 2PC), снижение throughput | Биллинг, клиринг, транзакционные пайплайны потоковой обработки |

### Сквозная модель надежности: Продюсер — Брокер — Потребитель

Распространенное заблуждение — считать, что гарантия доставки обеспечивается исключительно настройками брокера. Итоговая надежность формируется согласованным взаимодействием всех звеньев сквозного тракта:

```
[ Продюсер ]  ----( Сеть / Ретраи )---->  [ Кластер Брокеров ]  ----( Опрос / Поллинг )---->  [ Консьюмер ]
 (acks, retries,                           (ISR, min.insync,                               (commit offset,
  idempotence)                              fsync/page cache)                               idempotent DB)
```

1. **Сегмент продюсера:** определяет, гарантирует ли отправляющая сторона прием сообщения кластером до перехода к следующей операции. Включает таймауты доставки, политику повторных отправок (`retries`) и ожидание квитанций (`acks`).
2. **Сегмент брокера:** определяет долговечность хранения принятого сообщения (durability). Зависит от фактора репликации (`replication.factor`), минимального числа синхронных копий (`min.insync.replicas`) и политики сброса страниц ОС на диск.
3. **Сегмент консьюмера:** момент фиксации позиции (offset commit в Kafka или `basic.ack` в RabbitMQ) решает, какая семантика возникнет фактически:

| Поведение консьюмера | Результирующая семантика | Физическая механика сбоя |
| :--- | :--- | :--- |
| `enable.auto.commit=true` | Непредсказуемая (смешанная) | Таймер автокоммита срабатывает в фоновом потоке: если коммит произошел до завершения вычислений — потеря данных при падении; если падение случилось до срабатывания таймера — дублирование |
| Коммит офсета **до** выполнения бизнес-логики | At-most-once | В случае аварии процесса при обработке сообщение уже помечено прочитанным в брокере и не будет прочитано повторно |
| Ручной коммит офсета **после** успешной обработки | At-least-once | Авария между сохранением результата в БД и отправкой коммита в брокер приведет к повторному чтению того же сообщения |
| Consume-Transform-Produce в единой транзакции | Exactly-once (внутри Kafka) | Офсеты входного топика фиксируются в `__consumer_offsets` атомарно с публикацией результата в выходной топик через транзакционный координатор |

### Уровень хранения и ОС: Page Cache, Fsync и Репликация

Архитектура надежности Kafka фундаментально отличается от традиционных реляционных СУБД:

- **Отсутствие fsync на каждое сообщение:** По умолчанию Kafka не вызывает системный вызов `fsync()` на каждую входящую запись (`log.flush.interval.messages=Long.MAX_VALUE`, `log.flush.interval.ms=Long.MAX_VALUE`). Запись производится в Page Cache ядра Linux, а сброс на диск делегируется фоновому механизму ядра `pdflush`/`flush`.
- **Durability через распределенную репликацию:** Долговечность данных в Kafka гарантируется не локальным диском одного сервера, а одновременным нахождением копии данных в оперативной памяти и Page Cache нескольких независимых физических серверов, входящих в кворум ISR.
- **Риск синхронного fsync:** Принудительное включение `log.flush.interval.messages=1` переводит операции записи в блокирующий синхронный ввод-вывод, что снижает пропускную способность кластера в 10–50 раз и создает колоссальную нагрузку на дисковую подсистему.
- **Выборы лидера без потерь:** Параметр брокера `unclean.leader.election.enable=false` жестко запрещает назначение лидером реплики, не входящей в ISR. Если все брокеры ISR недоступны, партиция переходит в режим недоступности для записи, предотвращая бесследную потерю уже подтвержденных данных. Подробный разбор механизма репликации: [Репликация и ISR в Kafka](./kafka_isr_replication.md).

### Механизм идемпотентного продюсера (Idempotent Producer)

Начиная с Apache Kafka 3.0, параметр `enable.idempotence=true` включен по умолчанию. Вместе с ним клиент автоматически выставляет `acks=all`, `retries=Integer.MAX_VALUE` и устанавливает безопасный лимит `max.in.flight.requests.per.connection <= 5`.

- **Принцип работы:**
  1. При инициализации продюсер запрашивает у брокера уникальный 64-битный идентификатор `Producer ID` (PID) через запрос `InitProducerId`.
  2. Для каждой целевой партиции продюсер ведет локальный счетчик `Sequence Number`, начиная с `0`, который инкрементируется с каждым батчем сообщений.
  3. Брокер кэширует последние 5 номеров последовательностей для каждого PID на уровне партиции в файле состояния `.snapshot`.
  4. Если брокер получает батч с `Sequence Number`, равным `LastSequence + 1`, он фиксирует запись и сдвигает указатель.
  5. Если брокер получает `Sequence Number <= LastSequence`, запрос расценивается как дубликат (результат сетевого ретрая при потере ack) и отклоняется без ошибки для продюсера (тихая дедупликация).
  6. Если получен номер `> LastSequence + 1`, брокер фиксирует разрыв лога и возвращает `OutOfOrderSequenceException`.
- **Границы применимости:** Идемпотентность работает **исключительно в рамках одной сессии продюсера и одной партиции**. После перезапуска приложения генерируется новый PID, и брокер не сможет дедуплицировать сообщения, повторно отправленные новым процессом.

### Семантика Exactly-Once (EOS v2, KIP-447, KIP-890)

Семантика Exactly-Once в Kafka гарантирует, что в цикле потоковой обработки «чтение — трансформация — запись» (read-process-write) все операции выполняются атомарно.

- **Transaction Coordinator и `__transaction_state`:**
  - На каждом брокере может функционировать координатор транзакций. Ответственным за конкретный `transactional.id` назначается лидер партиции внутреннего топика `__transaction_state`, определяемый хешированием: `Math.abs(transactional.id.hashCode()) % transaction.state.log.num.partitions`.
- **Протокол двухфазного коммита (2PC):**
  1. Продюсер регистрирует `transactional.id` у координатора, получая PID и инкрементируя `Producer Epoch`.
  2. Перед отправкой данных в партиции продюсер регистрирует их список у координатора (`AddPartitionsToTxnRequest`).
  3. Продюсер отправляет батчи сообщений в назначенные партиции данных.
  4. Продюсер передает смещения прочитанных сообщений координатору (`AddOffsetsToTxnRequest`), который фиксирует их во внутреннем топике `__consumer_offsets`.
  5. При вызове `commit_transaction()` координатор записывает маркер `PREPARE_COMMIT` в `__transaction_state`, затем параллельно рассылает служебные маркеры `COMMIT` во все задействованные партиции данных, после чего фиксирует статус `COMPLETE_COMMIT`.
- **Last Stable Offset (LSO) и Isolation Level:**
  - Консьюмеры с `isolation.level=read_committed` буферизуют сообщения и продвигают видимый офсет только до отметки LSO. Если в партиции открыта транзакция с офсета `100`, консьюмер не увидит сообщения с офсетами `101`, `102` и далее, пока транзакция `100` не будет завершена маркером `COMMIT` или `ABORT`. Сообщения прерванных (`ABORT`) транзакций отфильтровываются консьюмером на лету с использованием индексных файлов `.txnindex`.
- **EOS v2 (KIP-447) и серверная защита (KIP-890):**
  - В EOS v2 офсеты консьюмера передаются в транзакцию вместе с метаданными консьюмер-группы (`generation_id`, `member_id`). Если посреди обработки произошла ребалансировка, координатор отклоняет попытку коммита от старого участника.
  - KIP-890 предотвращает коллизии эпох при сбоях брокера, валидируя статус транзакции на стороне партиции данных до включения записей в локальный лог.
- **Критическое ограничение:** EOS действует **строго внутри границ кластера Kafka**. Если обработчик осуществляет запись во внешнюю СУБД, отправку HTTP-запроса или мутацию внешнего состояния, транзакционность Kafka не распространяется на внешнюю систему.

### Механизмы надежности и доставки в RabbitMQ

Архитектура очередей RabbitMQ опирается на индивидуальные или батчевые подтверждения прохождения сообщений через брокер. Архитектурный базис: **[Обзор RabbitMQ](../rabbitmq/overview.md)**, сравнение концепций: **[Сравнение RabbitMQ и Kafka](./rabbitmq_vs_kafka.md)**.

1. **At-most-once:**
   - Продюсер работает без включения режима подтверждений (`publisher confirms`).
   - Консьюмер подключается с параметром `auto_ack=true` (`no_ack=true`). Сообщение удаляется из оперативной памяти брокера в момент отправки в сокет TCP.
2. **At-least-once:**
   - **Продюсер:** Активирует протокольный режим `confirm_select`. Брокер возвращает `basic.ack` (или `basic.nack` при сбое) только после гарантированной записи сообщения на диск или репликации по протоколу Raft в кворум узлов. Флаг `mandatory=true` гарантирует возврат сообщения продюсеру (`basic.return`), если в брокере отсутствует подходящий маршрут (routing key).
   - **Консьюмер:** Использует ручные квитанции `basic.ack` только после успешного завершения обработки. При аварии воркера или разрыве соединения неотвеченные сообщения возвращаются брокером в голову очереди (`requeue`).
   - **Лимит попыток доставки:** Для кворумных очередей аргумент `x-delivery-limit` задает порог повторных доставок. При превышении счетчика брокер автоматически сбрасывает сообщение в сконфигурированный Dead Letter Exchange (`x-dead-letter-exchange`), предотвращая циклическое зацикливание.
3. **Exactly-once:**
   - Брокер не имеет нативной поддержки сквозных транзакций уровня Kafka EOS. Реализуется исключительно комбинацией протокола Publisher Confirms, дедупликации по бизнес-идентификатору (`message_id`) на стороне потребителя и паттерна Transactional Outbox.

## Практические сценарии и конфигурация

### Сценарий 1: Промышленная конфигурация Zero Data Loss (At-least-once)

Эталонная конфигурация для обеспечения максимальной долговечности (RPO=0) без риска потери сообщений при авариях отдельных узлов.

#### Конфигурация брокера (`server.properties`):

```properties
# Фактор репликации метаданных и системных топиков
offsets.topic.replication.factor=3
offsets.topic.num.partitions=50
transaction.state.log.replication.factor=3
transaction.state.log.min.isr=2

# Запрет несинхронных выборов лидера (предотвращает потерю закоммиченных данных)
unclean.leader.election.enable=false

# Дефолтный кворум синхронных реплик для топиков
min.insync.replicas=2
default.replication.factor=3
```

#### Конфигурация топика через CLI:

```bash
kafka-topics.sh --bootstrap-server localhost:9092 --create \
    --topic business-orders \
    --partitions 6 \
    --replication-factor 3 \
    --config min.insync.replicas=2
# → Created topic business-orders.
```

#### Конфигурация продюсера:

```properties
bootstrap.servers=kafka-node1:9092,kafka-node2:9092,kafka-node3:9092
acks=all
enable.idempotence=true
max.in.flight.requests.per.connection=5
retries=2147483647
delivery.timeout.ms=120000
request.timeout.ms=30000
retry.backoff.ms=100
```

#### Конфигурация консьюмера:

```properties
bootstrap.servers=kafka-node1:9092,kafka-node2:9092,kafka-node3:9092
group.id=order-processor-group
enable.auto.commit=false
auto.offset.reset=earliest
max.poll.interval.ms=300000
session.timeout.ms=45000
```

### Сценарий 2: Полноценный цикл Exactly-Once (EOS v2) в Python

Каноническая реализация цикла «чтение — трансформация — запись» с атомарным коммитом смещений консьюмер-группы с использованием библиотеки `confluent-kafka`.

```python
import sys
from confluent_kafka import Consumer, Producer, KafkaException, KafkaError

def run_transactional_pipeline():
    # 1. Инициализация транзакционного продюсера
    producer_conf = {
        'bootstrap.servers': 'localhost:9092',
        'transactional.id': 'order-transformer-prod-1',  # Стабильный ID для фенсинга зомби
        'enable.idempotence': True,
        'transaction.timeout.ms': 60000,                 # 60 секунд на транзакцию
    }
    producer = Producer(producer_conf)

    # 2. Инициализация консьюмера с ручным управлением смещениями
    consumer_conf = {
        'bootstrap.servers': 'localhost:9092',
        'group.id': 'order-transformer-group',
        'enable.auto.commit': False,                     # Автокоммит категорически запрещен
        'isolation.level': 'read_committed',             # Читаем только завершенные транзакции
        'auto.offset.reset': 'earliest'
    }
    consumer = Consumer(consumer_conf)
    consumer.subscribe(['orders-raw'])

    # Инициализация транзакций на брокере (регистрация PID и сброс прошлых сессий)
    producer.init_transactions()

    try:
        while True:
            # Чтение батча сообщений
            msg = consumer.poll(timeout=1.0)
            if msg is None:
                continue
            if msg.error():
                if msg.error().code() == KafkaError._PARTITION_EOF:
                    continue
                raise KafkaException(msg.error())

            # Начало распределенной транзакции
            producer.begin_transaction()
            try:
                # Трансформация данных (бизнес-логика)
                raw_payload = msg.value().decode('utf-8')
                transformed_payload = raw_payload.upper()

                # Публикация результата в целевой топик
                producer.produce(
                    topic='orders-processed',
                    key=msg.key(),
                    value=transformed_payload.encode('utf-8')
                )

                # Атомарная фиксация смещения входного топика в транзакции (EOS v2 / KIP-447)
                current_positions = consumer.position(consumer.assignment())
                group_metadata = consumer.consumer_group_metadata()
                producer.send_offsets_to_transaction(current_positions, group_metadata)

                # Фиксация транзакции: рассылка маркеров COMMIT во все топики
                producer.commit_transaction()
            except KafkaException as err:
                # При ошибке транзакция откатывается; сообщение будет перечитано
                producer.abort_transaction()
                sys.stderr.write(f"Транзакция прервана из-за ошибки брокера: {err}\n")
            except Exception as biz_err:
                producer.abort_transaction()
                sys.stderr.write(f"Ошибка бизнес-логики: {biz_err}\n")

    except KeyboardInterrupt:
        pass
    finally:
        consumer.close()
        producer.flush(timeout=5.0)

if __name__ == '__main__':
    run_transactional_pipeline()
```

### Сценарий 3: Запуск EOS на тестовом одноброкерном стенде

### Сценарий 4: Паттерн Transactional Outbox и Idempotent Consumer

Для исключения потерь данных при передаче информации из реляционной базы данных во внешние системы используется связка **Transactional Outbox** + **Idempotent Consumer**.

1. **Transactional Outbox на источнике:**
   - В транзакции БД атомарно сохраняется сущность (например, запись в таблице `orders`) и формируется событие в системной таблице `outbox_events`.
   - Фоновый процесс (Debezium CDC или специализированный Relay-воркер) вычитывает таблицу `outbox_events` и передает сообщения в Kafka с гарантией **At-least-once**.
2. **Idempotent Consumer на приемнике:**
   - Каждое сообщение содержит детерминированный бизнес-ключ `idempotency_key` (или UUID события).
   - При получении сообщения консьюмер выполняет в рамках единой локальной транзакции БД:
     ```sql
     INSERT INTO processed_messages (message_id, processed_at) VALUES ('msg-uuid-101', NOW());
     UPDATE user_balance SET balance = balance - 100 WHERE user_id = 42;
     ```
   - Если первичный ключ `message_id` уже существует в таблице, СУБД возвращает ошибку уникальности (`unique constraint violation`), транзакция откатывается, а сообщение пропускается как дубликат.

### Сценарий 5: Обработка Poison Pills и архитектура неблокирующих повторов (Non-Blocking Retry & DLT)

Если сообщение содержит поврежденный JSON или некорректную структуру данных, консьюмер не сможет его обработать. Без изолирующей обработки это приводит к циклическому сбою (crash loop) сервиса и блокировке консьюмер-группы.

```
[ Входной топик orders ] ---> [ Воркер консьюмера ] --(Ошибка десериализации)--> [ Ретраи: Retry Topic ]
                                        |                                                    |
                                        | (Превышен лимит)                                   | (Превышен лимит)
                                        v                                                    v
                             [ Dead Letter Topic (DLT): orders.DLT ] <-----------------------+
```

#### Проблема блокирующих повторов (Head-of-Line Blocking)
Частая ошибка реализации консьюмера — организация цикла повторных попыток со `Thread.sleep()` прямо внутри цикла обработки сообщения:
- **Блокировка партиции:** Пока поток спит и пытается повторить обработку одного сбойного сообщения, **все последующие здоровые сообщения в этой партиции простаивают**.
- **Шторм ребалансировок:** Суммарное время сна быстро превышает порог `max.poll.interval.ms` (по умолчанию 300 секунд). Координатор считает консьюмер мертвым, исключает его из группы и запускает ребалансировку. После перезапуска новый воркер снова берет то же битое сообщение, засыпает и падает по таймауту.

#### Архитектура неблокирующих повторных попыток (Non-Blocking Retry Pattern)

1. **Цепочка Retry-топиков:** Для временных инфраструктурных сбоев (недоступность сторонней БД) применяются промежуточные топики задержки (`orders.retry-10s`, `orders.retry-1m`), куда сообщение пересылается перед попаданием в DLT.
2. **Немедленный коммит в основном топике:** При обнаружении ошибки воркер публикует сбойное сообщение в топик первой задержки `orders.retry-10s` и **немедленно фиксирует смещение (commit offset)** в исходном топике `orders`. Основной конвейер продолжает непрерывную обработку здоровых сообщений.
3. **Dead Letter Topic (DLT):** Выделенный топик (например, `orders.DLT`), куда сбрасываются непрочитанные сообщения после исчерпания лимита повторных попыток с сохранением исчерпывающих заголовков:
   - `x-original-topic`: имя исходного топика.
   - `x-original-partition`: партиция исходного сообщения.
   - `x-original-offset`: смещение в исходном топике.
   - `x-exception-message`: краткое описание ошибки.
   - `x-exception-stacktrace`: стек-трейс ошибки.
   - `x-retry-count`: количество совершенных попыток.
   - `x-retry-timestamp`: время отправки в DLT.
4. **Изоляция Poison Pills (ошибки десериализации):** Если полезная нагрузка повреждена до вызова бизнес-логики (битый JSON или несовместимый Avro), стандартный десериализатор падает с `SerializationException` внутри метода `poll()`. Для изоляции таких сообщений используется обертка `ErrorHandlingDeserializer` (Spring Kafka) или кастомный перехватчик: битое сообщение не роняет JVM, а сразу упаковывается с заголовком об ошибке десериализации и перенаправляется напрямую в Dead Letter Topic (`orders.DLT`).
5. **Регламент DLQ Replay:** После устранения аварии во внешней системе сообщения из `orders.DLT` воспроизводятся обратно в `orders` выделенной утилитой с жестким ограничением скорости (Rate Limiting), чтобы не вызвать лавинообразную перегрузку базы данных.

## Устранение неполадок

### Зависшие транзакции (Hanging Transactions) и блокировка LSO

- **Симптом:** Консьюмеры с `isolation.level=read_committed` внезапно перестают вычитывать новые сообщения из топика, при этом консьюмеры с `read_uncommitted` читают поток без задержек. В мониторинге растет метрика задержки потребителя (consumer lag).
- **Причина:** Транзакционный продюсер выполнил запись сообщений, но не вызвал `commit_transaction()` или `abort_transaction()` (процесс продюсера завис на этапе GC-паузы, упал без завершения сессии, либо сетевая изоляция заблокировала связь с координатором). LSO остановился на офсете первой незавершенной транзакции.
- **Диагностика:**
  1. Выполните команду `kafka-transactions.sh --bootstrap-server localhost:9092 find-hanging`.
  2. Убедитесь, что `CurrentTransactionStartOffset` не сдвигается в течение времени, превышающего `transaction.timeout.ms`.
- **Решение:**
  1. Проверьте клиентскую настройку `transaction.timeout.ms` (по умолчанию 60 000 мс). Если она превышает `transaction.max.timeout.ms` на брокере (900 000 мс), брокер должен был автоматически прервать транзакцию по истечении серверного таймаута.
  2. Если таймаут еще не истек или координатор заблокирован, выполните принудительный сброс через `kafka-transactions.sh --bootstrap-server localhost:9092 abort --transactional-id <ID> --coordinator-epoch <epoch>`.

### Ошибки фенсинга: ProducerFencedException и InvalidProducerEpochException

- **Симптом:** При вызове методов транзакции клиентское приложение завершается с фатальным исключением `org.apache.kafka.common.errors.ProducerFencedException` или `InvalidProducerEpochException`.
- **Причина:** Координатор зафиксировал появление нового экземпляра продюсера с тем же самым `transactional.id` и более новой эпохой (`ProducerEpoch`), либо консьюмер в транзакции EOS v2 был исключен из группы в результате ребалансировки (`CommitFailedException`). Это штатный механизм защиты от зомби-инстансов.
- **Решение:**
  - Убедитесь, что каждый физический экземпляр распределенного приложения имеет **уникальный** `transactional.id` (например, `order-worker-${HOSTNAME}` или `order-worker-0`, `order-worker-1`), если они не работают в режиме взаимоисключающего резервирования (Active/Passive).
  - При возникновении `ProducerFencedException` процесс продюсера обязан немедленно прекратить работу (`close()`) и перезапуститься, так как его текущее состояние признано невалидным.

### Сбои репликации и NotEnoughReplicasException при acks=all

- **Симптом:** Продюсер получает ошибку `NotEnoughReplicasException` или `NotEnoughReplicasAfterAppendException`. Запись блокируется.
- **Причина:** Количество активных синхронных реплик в текущем списке ISR для партиции стало меньше значения `min.insync.replicas` (например, при RF=3 и `min.insync.replicas=2` упали два брокера, либо одна реплика отстала по сети).
- **Решение:**
  1. Проверьте недореплицированные партиции: `kafka-topics.sh --bootstrap-server localhost:9092 --describe --under-replicated-partitions`.
  2. Восстановите упавшие брокеры кластера.
  3. Категорически запрещено снижать `min.insync.replicas` на лету в production, если критична сохранность данных — это защитный барьер, предотвращающий тихую потерю данных при последующих авариях.

## Лучшие практики

### Ключевые SRE-метрики надежности (Prometheus / JMX)

Для построения надежных SLO/SLA мониторинга тракта передачи данных в Prometheus через JMX Exporter отслеживаются критические метрики:

#### Метрики брокера (Kafka Broker):
- **`kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions`:** Количество партиций, для которых число реплик в ISR меньше фактора репликации (`> 0` — критический алерт, риск деградации надежности).
- **`kafka.server:type=ReplicaManager,name=UnderMinIsrPartitionCount`:** Количество партиций, где ISR ниже `min.insync.replicas` (`> 0` означает полную блокировку записи продюсеров с `acks=all`).
- **`kafka.server:type=TransactionCoordinatorMetrics,name=TransactionsPerSec`:** Частота открываемых распределенных транзакций.
- **`kafka.server:type=TransactionCoordinatorMetrics,name=AbortTransactionsPerSec`:** Частота откатов транзакций (всплеск свидетельствует об ошибках воркеров или сетевых таймаутах).

#### Метрики продюсера (Kafka Producer):
- **`kafka.producer:type=producer-metrics,client-id={client-id},name=record-error-rate`:** Частота сообщений, завершившихся ошибкой отправки (`> 0` требует расследования).
- **`kafka.producer:type=producer-metrics,client-id={client-id},name=record-retry-rate`:** Частота повторных отправок сообщений клиентом при сетевых сбоях.

#### Метрики консьюмера (Kafka Consumer):
- **`kafka.consumer:type=consumer-fetch-manager-metrics,client-id={client-id},name=records-lag-max`:** Максимальное отставание консьюмера от лидера партиции.
- **Разрыв High Watermark и LSO:** Отслеживание расстояния между High Watermark и Last Stable Offset: рост разрыва сигнализирует о длительной или зависшей транзакции.

### Системный тюнинг ядра Linux для брокеров Kafka

Поскольку Kafka активно использует Page Cache операционной системы для организации высокопроизводительного ввода-вывода, настройки виртуальной памяти ядра Linux напрямую влияют на надежность и отсутствие «заиканий» брокера при записи. Детальный разбор: [Тюнинг ОС для Kafka](./kafka_os_tuning.md).

```ini
# /etc/sysctl.d/99-kafka-durability.conf

# Начинать сброс грязных страниц в фоне при достижении 5% свободной памяти
vm.dirty_background_ratio = 5

# Блокировать процессы записи для синхронного сброса только при достижении 10%
vm.dirty_ratio = 10

# Интервал пробуждения потоков сброса страниц (в сотых долях секунды: 500 = 5 секунд)
vm.dirty_writeback_centisecs = 500

# Максимальный возраст грязной страницы до обязательного сброса на диск (30 секунд)
vm.dirty_expire_centisecs = 3000

# Минимизация агрессивности сброса памяти в swap
vm.swappiness = 1
```

Применение параметров ядра:

```bash
sudo sysctl -p /etc/sysctl.d/99-kafka-durability.conf
# → vm.dirty_background_ratio = 5
# → vm.dirty_ratio = 10
# → vm.dirty_writeback_centisecs = 500
# → vm.dirty_expire_centisecs = 3000
# → vm.swappiness = 1
```

**Файловая система:**
- Рекомендуется файловая система **XFS**. Опции монтирования в `/etc/fstab`: `noatime,nodiratime,logbufs=8,logbsize=256k`. Отключение обновления времени доступа (`noatime`) устраняет паразитные дисковые операции метаданных при чтении сегментов.

### Чек-лист проверки гарантий надежности перед выводом в Production

- [ ] **Топология:** Кластер состоит минимум из 3 независимых физических серверов / гипервизоров в разных стойках питания/сети.
- [ ] **Репликация топиков:** Критичные бизнес-топики имеют `replication.factor=3` и `min.insync.replicas=2`.
- [ ] **Служебные топики:** Параметры `transaction.state.log.replication.factor=3`, `transaction.state.log.min.isr=2`, `offsets.topic.replication.factor=3` заданы в конфигурации брокеров.
- [ ] **Лидерство:** Флаг `unclean.leader.election.enable=false` установлен глобально.
- [ ] **Клиентский продюсер:** Включена идемпотентность `enable.idempotence=true`, `acks=all`, `max.in.flight.requests.per.connection <= 5`.
- [ ] **Клиентский консьюмер:** Отключен автокоммит (`enable.auto.commit=false`), коммит смещений выполняется только после успешной обработки или в транзакции.
- [ ] **Изоляция транзакций:** Если используется Transactional API, все консьюмеры результирующих топиков сконфигурированы с `isolation.level=read_committed`.
- [ ] **Мониторинг:** Настроены алерты на `UnderReplicatedPartitions > 0`, `UnderMinIsrPartitionCount > 0` и длительность зависших транзакций.
- [ ] **Изоляция сбоев:** Сконфигурирован Dead Letter Topic (DLT) и обработчики сериализации для предотвращения бесконечных crash loop воркеров.
