# Сравнение RabbitMQ и Kafka: Push vs Pull

Этот документ сравнивает ключевые архитектурные различия между RabbitMQ и Kafka. Для понимания общих принципов работы очередей, обратитесь к основному документу:

* **[Принципы работы очередей сообщений](./message_queues_principles.md)**

## Определения

* **Push-модель (проталкивание)**: Брокер активно отправляет (проталкивает) сообщения подписавшимся консьюмерам. Контроль скорости осуществляется на стороне брокера. *Основной представитель: RabbitMQ.*
* **Pull-модель (вытягивание)**: Консьюмеры самостоятельно запрашивают (вытягивают) сообщения у брокера. Контроль скорости и создание обратного давления (backpressure) естественным образом ложатся на сторону консьюмера. *Основной представитель: Kafka.*

## Основные концепции

### Модель доставки и контроль потока

#### RabbitMQ (Push)

* **Принцип**: Брокер отправляет сообщения консьюмерам и держит у каждого из них буфер неподтверждённых сообщений.
* **Контроль потока**: Основной механизм — `prefetch` (`basic.qos`). Этот параметр ограничивает количество сообщений, которые брокер может отправить консьюмеру без получения подтверждения (`ack`).
  * **Малое значение `prefetch`** идеально подходит для медленных или неоднородных задач, так как предотвращает переполнение памяти у консьюмера и неравномерное распределение нагрузки.
  * **Большое значение `prefetch`** может привести к перекосу в распределении задач и всплескам нагрузки на отдельные инстансы консьюмеров.

#### Kafka (Pull)

* **Принцип**: Брокер хранит сообщения в партициях, а консьюмеры циклично вызывают метод `poll()`, запрашивая новые данные.
* **Контроль потока**: Осуществляется самим консьюмером через параметры:
  * **Частота вызовов `poll()`**: Если обработка замедляется, консьюмер реже вызывает `poll()`, создавая естественное обратное давление.
  * **Размер батча**: Параметры `fetch.min.bytes`, `fetch.max.bytes` и `max.poll.records` позволяют контролировать, сколько данных забирать за один раз. Увеличение размера батча повышает пропускную способность за счет увеличения задержки.

### Сравнительная таблица моделей

| Аспект | RabbitMQ (Push) | Kafka (Pull) |
| :--- | :--- | :--- |
| **Транспорт/Протокол** | AMQP 0-9-1/1.0 | Собственный бинарный протокол поверх TCP/IP |
| **Модель данных** | Очереди, обменники (exchanges), биндинги | Темы (topics) как неизменяемый лог, партиции |
| **Доставка** | Push к потребителю | Pull с контролем темпа со стороны потребителя |
| **Порядок** | Внутри одной очереди, но может нарушаться при `requeue` | Строгий порядок внутри одной [партиции](./partitioning_and_balancing.md) |
| **Подтверждения** | `ack`/`nack`, `requeue`, DLQ. Подробнее: [Гарантии доставки](./delivery_guarantees.md) | Коммиты оффсетов, DLQ через топик. Подробнее: [Гарантии доставки](./delivery_guarantees.md) |
| **Масштабирование** | Шардинг очередей, кластеризация | [Партиционирование](./partitioning_and_balancing.md) тем + группы потребителей |
| **Контроль нагрузки** | `prefetch` и `ack` | Частота `poll()` и размер батча |
| **Пропускная способность**| Умеренная, зависит от сложности маршрутизации | Очень высокая за счёт батчинга и последовательного I/O |
| **Минимальная задержка**| Обычно ниже при обработке легковесных сообщений | Может быть выше из-за интервала опроса и батчинга |
| **Повторная обработка**| Неподтвержденные сообщения возвращаются в очередь (`requeue`) | Повторное чтение достигается через управление оффсетом |

## Практические сценарии

### Обмен сообщениями между микросервисами

И RabbitMQ, и Kafka хорошо справляются с этой задачей. Выбор зависит от требований:

* **Kafka** предпочтительнее при высоких нагрузках и когда важна возможность повторного чтения событий (например, для Event Sourcing).
* **RabbitMQ** может быть проще в настройке для более простых сценариев и обеспечивает меньшую задержку при обработке одиночных сообщений.

Перед выбором всегда рекомендуется проводить нагрузочное тестирование под конкретный паттерн использования.

### Маршрутизация сообщений

* **RabbitMQ**: Гибкая маршрутизация "из коробки" с помощью обменников (exchanges) и правил биндинга (по паттерну, по заголовкам). Не требует дополнительного кода, но работает только если продюсер добавил необходимые атрибуты в сообщение.
* **Kafka**: Отсутствует встроенная сложная маршрутизация. Для разделения потока требуется написать отдельное приложение-фильтр (например, с использованием Kafka Streams), которое будет читать из одного топика и перекладывать сообщения в другие на основе их содержимого.

### Распределение задач по воркерам

* **RabbitMQ**: Идеально подходит. Каждый воркер может забирать по одному сообщению. Если воркер занят или упал, сообщение может быть немедленно передано другому свободному. Обработка одного "проблемного" сообщения не блокирует остальные.
* **Kafka**: Менее гибко. Так как каждая партиция обрабатывается одним консьюмером в группе, обработка "проблемного" сообщения заблокирует всю партицию (Head-of-Line Blocking). Увеличение числа консьюмеров не поможет, если все партиции уже заняты. Эта проблема частично решается в новых версиях Kafka (KIP-932 Queues for Kafka).

### Сбор логов и поставка в аналитические платформы

* **Kafka**: Стандарт де-факто для этих задач благодаря следующим преимуществам:
  * **Высокая пропускная способность**: Способна выдерживать огромный поток логов от тысяч микросервисов.
  * **Горизонтальное масштабирование**: Легко масштабируется добавлением новых брокеров.
  * **Экосистема**: Существуют готовые фреймворки (`Kafka Connect`) и агенты (Logstash, Fluentd, Vector), которые упрощают сбор данных из различных источников (БД, приложения) и их загрузку в хранилища данных (ClickHouse, Hadoop, S3).
  * **Возможность перечитывания**: Данные можно загрузить в Kafka один раз, а затем многократно выгружать в разные аналитические системы для разных нужд.
* **RabbitMQ**: Может использоваться, но встречается значительно реже из-за меньшей пропускной способности и отсутствия развитой экосистемы для интеграции с платформами данных.

### Примеры кода

#### RabbitMQ: потребитель с управляемым потоком

```python
import pika

# Установка соединения
conn = pika.BlockingConnection(pika.ConnectionParameters('rabbit'))
ch = conn.channel()

# Ограничиваем "давление" на консьюмер: не более 20 неподтвержденных сообщений
ch.basic_qos(prefetch_count=20)
ch.queue_declare(queue='tasks', durable=True)

# Функция обработки сообщения
def handle(ch, method, props, body):
    process(body)  # Ваша логика
    # Подтверждаем успешную обработку
    ch.basic_ack(delivery_tag=method.delivery_tag)

# Подписываемся на очередь
ch.basic_consume(queue='tasks', on_message_callback=handle)
ch.start_consuming()
```

#### Kafka: потребитель с pull и батчингом

```python
from kafka import KafkaConsumer

# Создание консьюмера с ручным коммитом
consumer = KafkaConsumer(
    'events',
    bootstrap_servers=['kafka:9092'],
    enable_auto_commit=False,
    max_poll_records=500,        # Контроль размера батча
    fetch_min_bytes=1048576,     # Ждать, пока не наберется 1 МБ данных
)

while True:
    # Вытягиваем батч сообщений
    records = consumer.poll(timeout_ms=500)
    for tp, msgs in records.items():
        # Обрабатываем весь батч
        process_batch([m.value for m in msgs])
    # Коммитим оффсет после успешной обработки батча
    consumer.commit()
```

## Дополнительная информация

### Операционные аспекты

* **Пики нагрузки**: Kafka более устойчива к всплескам благодаря своей архитектуре на основе сегментированного лога и последовательных дисковых операций. RabbitMQ чувствителен к пикам, что требует аккуратной настройки `prefetch` и, возможно, горизонтального масштабирования.
* **Повторная обработка**: В RabbitMQ сообщение, которое не получило `ack`, может быть возвращено в начало очереди. В Kafka данные в логе неизменны, и повторная обработка реализуется через сброс оффсета консьюмера на более раннюю позицию.
