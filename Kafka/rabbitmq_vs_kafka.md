# RabbitMQ vs Kafka: сравнение архитектур

## Определения

**Push-модель (проталкивание)** — брокер активно отправляет сообщения подписавшимся консьюмерам. Контроль скорости осуществляется на стороне брокера. Основной представитель: **RabbitMQ**.

**Pull-модель (вытягивание)** — консьюмеры самостоятельно запрашивают сообщения у брокера. Контроль скорости и создание обратного давления (backpressure) ложатся на сторону консьюмера. Основной представитель: **Kafka**.

## Основные концепции

### Модель доставки и контроль потока

**RabbitMQ** спроектирован как **быстрый транспорт**. Его главная задача — как можно быстрее доставить сообщение от продюсера к консьюмеру и удалить его после подтверждения. Очереди в RabbitMQ лучше всего работают, когда они пустые.

**Kafka** спроектирован как **распределенный лог**. Это хранилище данных, которое позволяет многим потребителям читать один и тот же поток в своем темпе, возвращаться назад во времени и перечитывать сообщения.

#### RabbitMQ (Push)

Подробное описание архитектуры и настроек см. в основном файле: **[Обзор RabbitMQ](../rabbitmq/overview.md)**.

**Кратко:** Брокер отправляет сообщения консьюмерам и держит у каждого из них буфер неподтверждённых сообщений. Использует модель `Продюсер → Exchange → Очередь → Консьюмер`. Сообщение удаляется только после получения `ack`.

#### Kafka (Pull)

**Принцип:** Брокер хранит сообщения в партициях, консьюмеры циклично вызывают `poll()`, запрашивая данные.

**Контроль потока:** Осуществляется консьюмером через параметры:

- **Частота вызовов `poll()`** — если обработка замедляется, консьюмер реже вызывает `poll()`, создавая естественное обратное давление.
- **Размер батча** — параметры `fetch.min.bytes`, `fetch.max.bytes`, `max.poll.records` контролируют объем данных за один запрос. Увеличение батча повышает пропускную способность за счёт задержки.

### Сравнительная таблица

| Аспект | RabbitMQ (Push) | Kafka (Pull) |
| :--- | :--- | :--- |
| **Протокол** | `AMQP (Advanced Message Queuing Protocol)` 0-9-1/1.0 | Собственный бинарный поверх TCP/IP |
| **Модель данных** | Очереди, обменники (exchanges), биндинги | Темы как неизменяемый лог, партиции |
| **Доставка** | Push к потребителю | Pull с контролем темпа потребителем |
| **Порядок** | Внутри очереди, возможны нарушения при `requeue` | Строгий порядок внутри [партиции](./partitioning_and_balancing.md) |
| **Подтверждения** | `ack`/`nack`, `requeue`, `DLQ (Dead Letter Queue)` ([Гарантии доставки](./delivery_guarantees.md)) | Коммиты оффсетов, `DLQ` через топик ([Гарантии доставки](./delivery_guarantees.md)) |
| **Масштабирование** | Шардинг очередей, кластеризация | [Партиционирование](./partitioning_and_balancing.md) тем + группы потребителей |
| **Контроль нагрузки** | `prefetch`, `ack` | Частота `poll()`, размер батча |
| **Пропускная способность** | Умеренная, зависит от маршрутизации | Высокая за счёт батчинга и sequential I/O |
| **Задержка** | Ниже при обработке одиночных сообщений | Выше из-за интервала опроса и батчинга |
| **Повторная обработка** | `requeue` неподтверждённых | Управление оффсетом |

## Практические сценарии

### Обмен сообщениями между микросервисами

Обе системы подходят, выбор зависит от требований:

- **Kafka** — высокие нагрузки, возможность повторного чтения (Event Sourcing).
- **RabbitMQ** — простые сценарии, меньшая задержка для одиночных сообщений.

Рекомендуется нагрузочное тестирование под конкретный паттерн.

### Выбор гарантии доставки

- **At-least-once + идемпотентность** — для платежей, заказов, финансовых операций. Потеря недопустима, дубликаты обрабатываются идемпотентным кодом.
- **At-most-once** — для логов, метрик и некритичных событий. Дубликаты исключены, потеря одного события из миллиона — приемлемый риск.

Подробнее — [Гарантии доставки в очередях сообщений](./delivery_guarantees.md).

### Маршрутизация сообщений

**RabbitMQ:** Гибкая маршрутизация через обменники и правила биндинга (по паттерну, заголовкам). Работает, если продюсер добавил атрибуты маршрутизации.

**Kafka:** Встроенная маршрутизация отсутствует. Требуется приложение-фильтр (Kafka Streams), читающее из одного топика и перекладывающее в другие по содержимому.

### Распределение задач по воркерам

- **RabbitMQ**: Идеально подходит. Каждый воркер может забирать по одному сообщению. Если воркер занят или упал, сообщение может быть немедленно передано другому свободному. Обработка одного "проблемного" сообщения не блокирует остальные.
- **Kafka**: Менее гибко. Так как каждая партиция обрабатывается одним консьюмером в группе, обработка "проблемного" сообщения заблокирует всю партицию (Head-of-Line Blocking). Увеличение числа консьюмеров не поможет, если все партиции уже заняты. Эта проблема частично решается в новых версиях Kafka (KIP-932 `Queues for Kafka`; `KIP (Kafka Improvement Proposal)`).

### Сбор логов и поставка в аналитические платформы

- **Kafka**: Стандарт де-факто для этих задач благодаря следующим преимуществам:
  - **Высокая пропускная способность**: Способна выдерживать огромный поток логов от тысяч микросервисов.
  - **Горизонтальное масштабирование**: Легко масштабируется добавлением новых брокеров.
  - **Экосистема**: Существуют готовые фреймворки (`Kafka Connect`) и агенты (Logstash, Fluentd, Vector), которые упрощают сбор данных из различных источников (БД, приложения) и их загрузку в хранилища данных (ClickHouse, Hadoop, S3).
  - **Возможность перечитывания**: Данные можно загрузить в Kafka один раз, а затем многократно выгружать в разные аналитические системы для разных нужд.
- **RabbitMQ**: Может использоваться, но встречается значительно реже из-за меньшей пропускной способности и отсутствия развитой экосистемы для интеграции с платформами данных.

### Антипаттерн: отдельный микросервис для публикации

Выделять отдельный микросервис только ради публикации сообщений в брокер — антипаттерн. Это добавляет лишнюю сетевую точку отказа и порождает вопрос «как отправлять сообщения в этот сервис». Вместо этого публикация должна быть слоем абстракции внутри существующего сервиса (`Publisher` / `EventBus`), который бизнес-логика дёргает, не зная, что под капотом — RabbitMQ, Kafka или что-то ещё.

### Примеры кода

#### RabbitMQ: потребитель с управляемым потоком

```python
import pika

# Установка соединения
conn = pika.BlockingConnection(pika.ConnectionParameters('rabbit'))
ch = conn.channel()

# Ограничиваем "давление" на консьюмер: не более 20 неподтвержденных сообщений
ch.basic_qos(prefetch_count=20)
ch.queue_declare(queue='tasks', durable=True)

# Функция обработки сообщения
def handle(ch, method, props, body):
    process(body)  # Ваша логика
    # Подтверждаем успешную обработку
    ch.basic_ack(delivery_tag=method.delivery_tag)

# Подписываемся на очередь
ch.basic_consume(queue='tasks', on_message_callback=handle)
ch.start_consuming()
```

#### Kafka: потребитель с pull и батчингом

```python
from kafka import KafkaConsumer

# Создание консьюмера с ручным коммитом
consumer = KafkaConsumer(
    'events',
    bootstrap_servers=['kafka:9092'],
    enable_auto_commit=False,
    max_poll_records=500,        # Контроль размера батча
    fetch_min_bytes=1048576,     # Ждать, пока не наберется 1 МБ данных
)

while True:
    # Вытягиваем батч сообщений
    records = consumer.poll(timeout_ms=500)
    for tp, msgs in records.items():
        # Обрабатываем весь батч
        process_batch([m.value for m in msgs])
    # Коммитим оффсет после успешной обработки батча
    consumer.commit()
```

## Дополнительная информация

### Операционные аспекты

- **Пики нагрузки**: Kafka более устойчива к всплескам благодаря своей архитектуре на основе сегментированного лога и последовательных дисковых операций. RabbitMQ чувствителен к пикам, что требует аккуратной настройки `prefetch` и, возможно, горизонтального масштабирования.
- **Повторная обработка**: В RabbitMQ сообщение, которое не получило `ack`, может быть возвращено в начало очереди. В Kafka данные в логе неизменны, и повторная обработка реализуется через сброс оффсета консьюмера на более раннюю позицию.
