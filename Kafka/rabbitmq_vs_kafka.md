# Сравнение архитектур RabbitMQ и Apache Kafka

**Актуально для:** Apache Kafka 3.9 / 4.0 (KRaft), RabbitMQ 3.13 / 4.0

Выбор между RabbitMQ и Kafka — это фундаментальное архитектурное решение при проектировании распределенного обмена данными в инфраструктуре. Оба инструмента служат буфером между сервисами для их связывания (декупажа), сглаживания пиковых нагрузок и обеспечения изоляции при временной недоступности компонентов в рамках on-premise и bare-metal инсталляций.

Ключевое различие заключается в архитектурной парадигме: **традиционные очереди (Smart Broker / Dumb Client)** против **распределенного коммит-лога (Dumb Broker / Smart Client)**.

---

## Определения

- **Брокер сообщений (Message Broker):** Централизованный посредник, принимающий сообщения от продюсеров, управляющий их маршрутизацией и доставляющий их консьюмерам. После подтверждения обработки сообщение удаляется. Детали см. в **[Обзоре RabbitMQ](../rabbitmq/overview.md)**.
- **Распределенный лог (Distributed Commit Log):** Упорядоченное append-only хранилище записей на диске, разделенное на партиции. Записи персистентны, не удаляются при чтении и вытесняются только по истечении политик хранения. Детали см. в **[Обзоре Apache Kafka](./kafka_overview.md)**.
- **Smart Broker / Dumb Client:** Модель, в которой брокер выполняет сложную логику: маршрутизацию через обменники, отслеживание подтверждений каждого сообщения, фильтрацию, управление очередями и автоматическую отправку в DLQ. Клиенты остаются простыми (характерно для **RabbitMQ**).
- **Dumb Broker / Smart Client:** Модель, в которой брокер выполняет только последовательную запись и чтение бинарных сегментов лога, не зная о состоянии отдельных клиентов. Вся логика распределения нагрузки, отслеживания смещений (offsets), повторов и обработки ошибок возложена на клиентские библиотеки (характерно для **Kafka**).
- **Retention:** Политика удержания данных по времени (`retention.ms`) или суммарному размеру (`retention.bytes`). В RabbitMQ сообщение удаляется сразу после подтверждения (`ack`), в Kafka записи сохраняются независимо от факта вычитывания.
- **Офсет (Offset):** Монотонно возрастающий целочисленный идентификатор записи внутри партиции Kafka, однозначно определяющий позицию консьюмера в журнале.
- **Prefetch Count (QoS):** Лимит количества неподтвержденных сообщений, которые RabbitMQ отправляет консьюмеру в рамках одного канала. Базовый механизм предотвращения переполнения памяти клиента в Push-модели.
- **Dead Letter Queue (DLQ):** Очередь или топик для сообщений, обработка которых завершилась сбоем после исчерпания лимита попыток. В RabbitMQ реализуется брокером через Dead Letter Exchange (DLX), в Kafka — логикой консьюмера и выделенным топиком.
- **Share Groups (KIP-932):** Механизм потребления в Kafka («Queues for Kafka»), добавляющий семантику классической очереди: параллельные консьюмеры одной группы читают одну партицию с индивидуальной блокировкой и подтверждением записей на брокере.
- **Quorum Queue:** Отказоустойчивая реплицируемая очередь в RabbitMQ на базе алгоритма консенсуса Raft. Стандарт репликации в современных версиях брокера.
- **KRaft (Kafka Raft Metadata mode):** Встроенная система управления метаданными кластера Kafka на базе алгоритма Raft, полностью заменившая ZooKeeper.
- **Zero-Copy (`sendfile`):** Системный вызов Linux, передающий страницы памяти из Page Cache напрямую в сетевой сокет минуя пространство пользователя, что обеспечивает максимальную производительность Kafka.

## Базовые концепции и архитектура

### Ментальные модели брокеров

- **RabbitMQ — почтовое отделение (Message Broker):** Сообщения проходят транзитом через брокер. Как только сообщение доставлено и подтверждено консьюмером, оно удаляется из оперативной памяти или диска. Накопление миллионов сообщений является нештатным состоянием и ведет к деградации производительности.
- **Kafka — неизменяемая бухгалтерская книга (Distributed Log):** Сообщения последовательно записываются в конец журнала на диске и хранятся заданный период (retention). Любое количество независимых консьюмеров может одновременно или с разной скоростью вычитывать историю лога из произвольной позиции.

```
RabbitMQ (Smart Broker):
[Продюсер] ──> (Exchange) ──[Binding]──> [Queue (In-Memory/WAL)] ──Push──> [Консьюмер]
                                                │ (ack)
                                                ▼ (удаление)

Kafka (Dumb Broker):
[Продюсер] ──> [Broker: Partition Log on Disk] <──Pull── [Консьюмер Group A: Offset 105]
                        ├── 101 ├── 102 ├── 103 ├── 104 ├── 105 ├── 106 ──>
                                               <──Pull── [Консьюмер Group B: Offset 102]
```

### Модели доставки и контроль потока

- **Push-модель (RabbitMQ):** Брокер активно проталкивает сообщения подключенным клиентам. Брокер отслеживает состояние каждого отдельного сообщения (доставлено, ожидает ack).
  - *Контроль потока (Backpressure):* Регулируется параметром `prefetch_count` (QoS). Если консьюмер не подтверждает получение, брокер прекращает передачу новых сообщений данному воркеру.
  - *Защита брокера:* Механизм Flow Control блокирует TCP-сокеты продюсеров при превышении порогов памяти (`vm_memory_high_watermark`) или свободного места на диске (`disk_free_limit`).
- **Pull-модель (Kafka):** Консьюмеры самостоятельно запрашивают пакеты данных вызовом `poll()`. Контроль скорости чтения полностью находится на стороне клиента.
  - *Контроль потока (Backpressure):* Если обработчик перегружен, он просто реже вызывает `poll()`, не создавая нагрузки на брокер.
  - *Параметры батчинга:* `fetch.min.bytes` (минимальный объем данных для ответа), `fetch.max.wait.ms` (максимальное время ожидания накопления батча на брокере), `max.poll.records` (лимит записей за один вызов).
  - *Защита брокера:* Продюсеры пишут строго последовательно в конец файла; медленные читатели никак не влияют на скорость записи продюсеров.

| Механизм | RabbitMQ (Push) | Kafka (Pull) |
| :--- | :--- | :--- |
| **Управление скоростью клиента** | `prefetch_count` — лимит сообщений без `ack` | Частота циклов `poll()` и размер батча |
| **Буферизация на брокере** | Буфер неподтвержденных сообщений в RAM/Erlang ETS | `fetch.min.bytes` / `fetch.max.wait.ms` в сокете |
| **Пакетная обработка (Batching)** | Доставка по одному сообщению (или батчевый ack) | Нативная группировка пачками на продюсере и консьюмере |
| **Защита ресурсов брокера** | Flow Control: блокировка сокетов продюсеров по RAM/Disk | Ограничение квот (`quota.producer_byte_rate`), последовательный I/O |

### Модель хранения данных и использование ресурсов ОС

- **RabbitMQ:**
  - Очереди и сообщения оптимизированы для оперативной памяти. В классических очередях сообщения размещаются в куче процесса Erlang (BEAM) и индексах ETS.
  - При переполнении памяти брокер выполняет сброс (paging) сообщений на диск, что сопровождается резким падением пропускной способности (latency spike).
  - Кворумные очереди (Quorum Queues) сохраняют историю в собственный WAL (Write-Ahead Log) на диске для консенсуса Raft, но старые сообщения вытесняются сразу после подтверждения всеми репликами и клиентами.
- **Kafka:**
  - Данные организуются в виде файлов сегментов (`.log`) и разреженных индексов смещений (`.index`, `.timeindex`) на файловой системе (XFS/ext4).
  - Брокер намеренно оставляет большую часть RAM свободной от кучи JVM (рекомендуемый размер heap: 6–8 ГБ). Вся остальная свободная память хоста используется под **Page Cache** ядра Linux.
  - При чтении данных брокер использует системный вызов `sendfile(2)` (Zero-Copy): байты из Page Cache ядра передаются напрямую в сетевой интерфейс без копирования в адресное пространство Java и без создания сборщика мусора (GC).

### Гарантии порядка сообщений (Ordering)

- **RabbitMQ:** Гарантирует строгий порядок FIFO в рамках одной очереди только при условии **одного консьюмера**. Если к очереди подключено несколько параллельных воркеров (Competing Consumers), время завершения обработки не детерминировано. При отправке сообщения обратно в очередь (`basic_nack` с флагом `requeue=true`) порядок нарушается, так как сообщение помещается заново.
- **Apache Kafka:** Гарантирует строгий порядок **только внутри одной партиции**. Сообщения с одинаковым ключом (`message.key`) всегда попадают в одну и ту же партицию при неизменном количестве партиций топика. Глобального порядка во всем топике нет (за исключением топиков с ровно одной партицией).

### Сетевая архитектура и протоколы

- **RabbitMQ:**
  - Поддерживает стандартные протоколы прикладного уровня: **AMQP 0-9-1**, **AMQP 1.0** (нативно с RabbitMQ 4.0), **MQTT 3.1.1/5.0**, **STOMP**.
  - Для сценариев стриминга с версии 3.9 поддерживается специализированный бинарный протокол **RabbitMQ Stream Protocol** (порт 5552).
  - TCP-соединение является дорогим ресурсом в Erlang; поверх одного соединения мультиплексируются легковесные каналы (**Channels**).
- **Kafka:**
  - Использует собственный бинарный RPC-протокол поверх TCP (порт по умолчанию: 9092 для брокеров, 9093 для контроллеров KRaft).
  - Все сетевые фреймы оптимизированы под батчинг: запросы `ProduceRequest` и `FetchRequest` передают структурированные массивы записей.

### Архитектура кластеризации и консенсус

- **RabbitMQ:**
  - Кластер строится из узлов Erlang (BEAM), объединенных через Erlang Distributed Protocol (порт 25672) и демон сопоставления портов EPMD (порт 4369).
  - Для управления метаданными (пользователи, vhosts, обменники, топология) с версии 4.0 используется встроенная база данных **Khepri** на базе алгоритма Raft (полностью заменившая устаревшую распределенную БД Mnesia).
  - Репликация данных очередей: **Quorum Queues** образуют независимые Raft-группы на уровне очередей. Для сохранения кворума требуется нечетное число узлов ($2N+1$) и доступность большинства узлов.
- **Kafka:**
  - Начиная с версии 4.0 режим **KRaft (Kafka Raft)** является единственным поддерживаемым механизмом управления метаданными (поддержка Apache ZooKeeper удалена).
  - Выделенные узлы-контроллеры формируют единый метаданный лог `@metadata` с выбором лидера по Raft.
  - Репликация партиций строится по модели «Лидер — Последователи» с пулом синхронных реплик (**ISR — In-Sync Replicas**). Запись считается зафиксированной (High Watermark), когда она подтверждена всеми репликами из ISR.

### Производительность, задержка и размер сообщений

Ориентировочные порядки величин для типового bare-metal оборудования с NVMe-накопителями и 10GbE сетью:

- **RabbitMQ (Классические и кворумные очереди):**
  - *Пропускная способность:* 10 000 – 50 000 сообщений в секунду на узел.
  - *Задержка (Latency):* 1 – 3 мс (минимальная задержка при доставке отдельных сообщений в Push-модели).
  - *Накладные расходы:* Высокие на каждое отдельное сообщение (вычисление маршрутов в exchange, обновление индексов состояния unacked, ACK-пакеты).
- **RabbitMQ Streams:** До 1 000 000+ сообщений в секунду за счет append-only лога и бинарного протокола стримов.
- **Apache Kafka:**
  - *Пропускная способность:* 1 000 000+ сообщений в секунду на кластер.
  - *Задержка (Latency):* 5 – 25 мс (выше из-за ожидания накопления батчей `linger.ms` и буферизации).
  - *Накладные расходы:* Минимальные на брокере (последовательный I/O, передача блоками).
- **Размер полезной нагрузки:**
  - *RabbitMQ:* Лимит по умолчанию 16 MiB (настраивается параметром `max_message_size`). Рекомендуется не превышать 1 MiB во избежание фрагментации памяти Erlang.
  - *Kafka:* Лимит по умолчанию 1 MiB (`message.max.bytes`). Увеличение требует согласованного изменения `max.request.size` на продюсере, `replica.fetch.max.bytes` на брокере и `max.partition.fetch.bytes` на консьюмере.

### Нюансы гарантий доставки

Подробный разбор семантик см. в **[Гарантии доставки](./delivery_guarantees.md)**.

- **At-least-once (минимум один раз):** Стандарт для обоих инструментов. В RabbitMQ достигается связкой `publisher confirms` + persistent quorum queue + ручной `basic_ack`. В Kafka — параметрами `acks=all`, `min.insync.replicas=2` и коммитом офсетов строго после успешной обработки.
- **Идемпотентность:** Обязательна на консьюмерах в обеих системах. Сетевые таймауты, падения воркеров и повторные отправки неизбежно приводят к дубликатам.
- **Ограничения Exactly-Once (EOS):**
  - В Kafka транзакции (`isolation.level=read_committed`) работают строго в контуре «Kafka → обработка → Kafka». При записи во внешнюю реляционную СУБД или сторонний API транзакция прерывается, и система возвращается к семантике At-least-once.
  - В RabbitMQ транзакции AMQP блокируют поток обработки и на практике не используются в высоконагруженных системах из-за катастрофического падения производительности.

### Сравнительная архитектурная матрица

| Критерий | RabbitMQ (Queues) | Apache Kafka |
| :--- | :--- | :--- |
| **Основная абстракция** | Очередь (Queue), Обменник (Exchange) | Топик (Topic), Партиция (Partition) |
| **Принцип брокера** | Smart Broker / Dumb Client | Dumb Broker / Smart Client |
| **Модель получения** | Push (брокер шлет в сокет консьюмера) | Pull (консьюмер запрашивает через `poll`) |
| **Хранилище данных** | Память (Erlang heap) + WAL на диске | Файлы сегментов на диске + Page Cache ядра |
| **Жизнь сообщения** | Удаляется сразу после `ack` | Хранится по retention независимо от чтения |
| **Повторное чтение (Replay)** | Невозможно (данные удалены) | Нативно поддерживается (сброс офсета) |
| **Порядок доставки** | Внутри очереди для одного воркера | Строгий внутри партиции по ключу |
| **Масштабирование** | Разделение очередей, воркеры | Горизонтальное по числу партиций |
| **Консенсус метаданных** | Khepri (Raft) в Erlang-кластере | KRaft (Raft-контроллеры) |
| **Контроль нагрузки** | `prefetch_count` (QoS), Flow Control | Размер батча, частота `poll()`, квоты |
| **Маршрутизация** | Direct, Topic, Fanout, Headers на брокере | Отсутствует (фильтрация в приложениях) |
| **Потребление воркерами** | Competing Consumers из коробки | 1 партиция = 1 воркер (или Share Groups) |

## Практические сценарии и конфигурация

### Матрица выбора: когда какой инструмент

| Сценарий | Рекомендация | Техническое обоснование |
| :--- | :--- | :--- |
| **Фоновые задачи (Background Jobs)** | **RabbitMQ** | Единичное исполнение, естественная балансировка между любым числом воркеров, встроенные механизмы повторов и DLX. |
| **Сложная маршрутизация событий** | **RabbitMQ** | Фильтрация по заголовкам, ключам маршрутизации с масками (`audit.*.warning`) средствами брокера без написания кода. |
| **Стриминг событий (Event Sourcing)** | **Kafka** | Неизменяемый аудит-лог событий, возможность повторной обработки истории новыми микросервисами. |
| **Сбор метрик, трейсов и логов** | **Kafka** | Высокая пропускная способность, устойчивость к суточным накоплениям данных (backlog) без расхода RAM. |
| **Репликация изменений БД (CDC / Debezium)** | **Kafka** | Интеграция с Kafka Connect, сохранение порядка изменений по первичному ключу таблицы через ключ партиции. |
| **Высокая вариативность скорости читателей** | **Kafka** | Медленный аналитический консьюмер не влияет на быстрый онлайн-сервис благодаря независимому хранению офсетов. |
| **Интеграция с IoT и телеметрией** | **RabbitMQ** | Нативная поддержка легковесных протоколов MQTT и STOMP без промежуточных шлюзов. |
| **Магистраль данных + фоновые задачи** | **Гибрид** | Kafka как центральная шина событий, RabbitMQ для выполнения ресурсоемких асинхронных задач. |

### Микросервисы, Task Queues и Event Streaming

1. **Task Queues (RabbitMQ):**
   - Используется, когда задача имеет жизненный цикл: «получена → выполняется → завершена».
   - Пример: Отправка email-уведомлений, генерация PDF-отчетов, конвертация медиафайлов.
   - Если воркер аварийно завершился, TCP-канал разрывается, и брокер автоматически возвращает сообщение другим свободным воркерам.
2. **Event Streaming (Kafka):**
   - Используется, когда факт совершения действия («Заказ оформлен») представляет интерес для множества независимых систем (биллинг, склад, антифрод, рекомендательная система).
   - Продюсер отправляет событие один раз, не заботясь о количестве и типах подписчиков.

### Распределение задач по воркерам (Competing Consumers vs Share Groups)

- **RabbitMQ (Competing Consumers):**
  - Десятки воркеров могут слушать одну очередь `tasks`.
  - Брокер распределяет сообщения по принципу Round-Robin с учетом `prefetch_count`. Если один воркер выполняет тяжелую задачу 30 секунд, брокер продолжает отдавать быстрые задачи другим воркерам.
  - Добавление нового воркера мгновенно увеличивает пропускную способность.
- **Kafka (Классические Consumer Groups):**
  - Правило: **одна партиция назначается строго одному консьюмеру в группе**.
  - Если в топике 8 партиций, а запущено 16 воркеров, то 8 воркеров будут простаивать.
  - Если в партиции встретилось тяжелое сообщение (Head-of-Line Blocking), все последующие сообщения этой партиции ждут завершения его обработки.
- **Kafka Share Groups (KIP-932):**
  - Позволяет нескольким консьюмерам внутри share group параллельно забирать сообщения из одной партиции.
  - Брокер берет на себя блокировку записи на время обработки (`share.record.lock.duration.ms`) и ждет индивидуального подтверждения записи (`acknowledge`/`release`/`reject`).
  - Устраняет проблему Head-of-Line Blocking, приближая модель потребления Kafka к модели очередей RabbitMQ.

### Сбор логов, телеметрии и CDC

- **Kafka как буфер данных:** Системы сбора логов (Vector, Fluentbit, Logstash) сбрасывают терабайты данных в топики Kafka. Если целевое хранилище (ClickHouse, Elasticsearch) уходит на обслуживание, Kafka надежно сохраняет весь входящий поток на диске без риска падения по памяти.
- **Change Data Capture (CDC):** Фреймворк **Kafka Connect** и плагины (Debezium) вычитывают WAL СУБД (PostgreSQL logical replication) и записывают события изменений строк в Kafka. Партиционирование по первичному ключу таблицы гарантирует строгий порядок обновлений для каждой конкретной строки.

### Гибридная архитектура (Kafka Backbone + RabbitMQ Task Queue)

В зрелых инфраструктурах оба решения часто объединяются:

```
[Web / API сервисы]
        │
        ▼
[ Apache Kafka ] (Центральная шина событий: "UserRegistered", "PaymentReceived")
   │          │
   │          └──> [Аналитика / DWH / ClickHouse] (Пакетная выгрузка)
   ▼
[Worker-Gateway]
   │ (Трансляция событий в задачи)
   ▼
[ RabbitMQ ] (Очередь задач: "generate-welcome-pdf", "send-push")
   ├── [Worker 1]
   ├── [Worker 2]
   └── [Worker N]
```

- **Правило надежности:** Мост между Kafka и RabbitMQ должен быть идемпотентным. Смещение в Kafka коммитится только после того, как задача успешно подтверждена RabbitMQ (`publisher confirms`).

### Антипаттерны интеграции

1. **Выделенный HTTP-микросервис для публикации в брокер:** Создание сервиса-прослойки перед брокером добавляет сетевой оверхед, создает единую точку отказа и порождает проблему согласованности доставки.
   - *Решение:* Публиковать напрямую из сервисов через официальные SDK брокера с применением паттерна **Transactional Outbox**.
2. **Использование RabbitMQ в качестве долгосрочной базы данных:** Хранение миллионов сообщений в очередях приводит к деградации сборщика мусора Erlang, росту использования диска под индексы и блокировке продюсеров.
   - *Решение:* Вычитывать сообщения вовремя; для длительного хранения использовать Kafka с настроенным retention.
3. **Использование Kafka для RPC и легковесных очередей с коротким TTL:** Создание сотен динамических топиков под временные задачи перегружает метаданные KRaft и приводит к фрагментации файлов логов.

### Примеры клиентских реализаций (Python)

#### RabbitMQ: Воркер задач с ручным подтверждением и QoS (Push)

```python
import pika
import sys

# Подключение к брокеру RabbitMQ
params = pika.ConnectionParameters(host='192.168.10.11', port=5672)
connection = pika.BlockingConnection(params)
channel = connection.channel()

# Ограничение очереди unacked-сообщений: не более 20 сообщений на воркер
channel.basic_qos(prefetch_count=20)

# Объявление отказоустойчивой кворумной очереди с лимитом доставок
channel.queue_declare(
    queue='task_orders_queue',
    durable=True,
    arguments={
        'x-queue-type': 'quorum',
        'x-delivery-limit': 5,
        'x-dead-letter-exchange': 'orders_dlx'
    }
)

def process_task(ch, method, properties, body):
    try:
        # Бизнес-логика обработки задачи
        print(f"Обработка задачи: {body.decode()}")
        # Ручное подтверждение брокеру
        ch.basic_ack(delivery_tag=method.delivery_tag)
    except Exception as err:
        # Отклонение: возвращаем в очередь для повтора;
        # после x-delivery-limit попыток брокер сам отправит сообщение в orders_dlx
        print(f"Ошибка при обработке: {err}", file=sys.stderr)
        ch.basic_nack(delivery_tag=method.delivery_tag, requeue=True)

channel.basic_consume(queue='task_orders_queue', on_message_callback=process_task)
channel.start_consuming()
```

#### Apache Kafka: Консьюмер с управлением батчами и ручным коммитом (Pull)

```python
from kafka import KafkaConsumer
import json
import sys

# Инициализация консьюмера с контролем батчинга
consumer = KafkaConsumer(
    'orders_topic',
    bootstrap_servers=['192.168.10.11:9092', '192.168.10.12:9092'],
    group_id='orders_processing_group',
    enable_auto_commit=False,        # Ручной коммит для гарантии At-least-once
    auto_offset_reset='earliest',
    max_poll_records=500,            # Лимит записей в одном батче
    fetch_min_bytes=1048576,         # Ожидать накопления минимум 1 МБ данных
    fetch_max_wait_ms=500            # Лимит ожидания накопления 1 МБ на брокере
)

try:
    while True:
        # Вытягивание батча сообщений из партиций
        records = consumer.poll(timeout_ms=1000)
        if not records:
            continue

        for partition, messages in records.items():
            for msg in messages:
                payload = json.loads(msg.value.decode('utf-8'))
                # Выполнение идемпотентной бизнес-логики
                print(f"Партиция {msg.partition}, офсет {msg.offset}: {payload}")

        # Фиксация смещения только после успешной обработки всего батча
        consumer.commit()
except KeyboardInterrupt:
    pass
finally:
    consumer.close()
```

## Диагностика и устранение неисправностей (Troubleshooting)

### Сценарий 1: Блокировка продюсеров и исчерпание ресурсов

#### RabbitMQ: Memory Alarm и Flow Control

- **Симптомы:** Продюсеры получают таймауты при публикации; соединения переходят в статус `blocking` или `blocked`; в логах брокера появляется запись `vm_memory_high_watermark set. Running out of memory`.
- **Причина:** Объем оперативной памяти превысил `vm_memory_high_watermark`. Брокер включил глобальный Flow Control и перестал читать сокеты продюсеров для предотвращения аварийного OOM-killer.
- **Диагностика:**
  ```bash
  rabbitmq-diagnostics memory_breakdown
  # → binary: 2.4GB, queue_procs: 1.8GB, connection_readers: 0.5GB ...
  ```
- **Решение:**
  1. Выявить очереди с максимальным объемом сообщений через `rabbitmqctl list_queues name memory messages`.
  2. Увеличить количество консьюмеров или поднять `prefetch_count` на воркерах, если они недогружены.
  3. Временное экстренное поднятие лимита (если на хосте есть резерв RAM):
     ```bash
     rabbitmqctl eval 'application:set_env(rabbit, vm_memory_high_watermark, 0.8).'
     ```
  4. Перевести очереди на Quorum Queues или настроить политику TTL/максимальной длины очереди.

#### Apache Kafka: Producer Queue Full и Network Thread Exhaustion

- **Симптомы:** Продюсеры выбрасывают исключение `TimeoutException: Expiring 30 record(s) for topic-0:120000 ms has passed since batch creation`.
- **Причина:** Перегрузка дисковой подсистемы брокера или дефицит потоков ввода-вывода (`num.io.threads`), приводящие к росту очереди `queued.max.requests`.
- **Диагностика:**
  1. Проверить утилизацию дисков брокеров через `iostat -xz 1`.
  2. Проверить задержки очередей брокера через метрики JMX: `kafka.network:type=RequestChannel,name=RequestQueueTimeMs`.
- **Решение:**
  1. Увеличить размер батчинга на продюсере (`batch.size=65536`, `linger.ms=20`), чтобы снизить число I/O операций на запись.
  2. Перенести каталоги `log.dirs` на отдельные NVMe-накопители с файловой системой XFS.

### Сценарий 2: Критический рост отставания потребителей (Lag / Backlog)

#### RabbitMQ: Рост unacknowledged сообщений

- **Симптомы:** Метрика `messages_unacknowledged` непрерывно растет, очередь сообщений `messages_ready` не уменьшается.
- **Причина:** Зависание воркеров во время обработки, слишком высокий `prefetch_count` (один зависший воркер заблокировал 500 сообщений) или отсутствие таймаута на сокетах внешних сервисов.
- **Диагностика:**
  ```bash
  rabbitmqctl list_channels pid connection consumer_count messages_unacknowledged
  ```
- **Решение:**
  1. Уменьшить `prefetch_count` до значений 10–50 на консьюмера.
  2. Включить `consumer_timeout` (по умолчанию в RabbitMQ: 30 минут; при превышении брокер закрывает канал).
  3. Перезапустить зависшие процессы воркеров; брокер вернет unacked-сообщения обратно в очередь.

#### Apache Kafka: Растущий Consumer Lag и Rebalance Storm

- **Симптомы:** Метрика `LAG` в `kafka-consumer-groups.sh` растет; консьюмеры циклически исключаются из группы; в логах консьюмера записи: `CommitFailedException` и `RebalanceInProgressException`.
- **Причина:** Время обработки батча сообщений превышает `max.poll.interval.ms` (по умолчанию 300 000 мс / 5 минут). Координатор группы считает консьюмер «мертвым» и запускает перебалансировку всего пула партиций.
- **Диагностика:**
  ```bash
  kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group orders_processing_group --state
  # → GROUP                    COORDINATOR (ID)          STATE           MEMBERS
  # → orders_processing_group  node1:9092 (1)            PreparingRebalance 3
  ```
- **Решение:**
  1. Уменьшить `max.poll.records` (например, со 500 до 50), чтобы консьюмер успевал гарантированно обработать порцию данных до истечения интервала.
  2. Увеличить `max.poll.interval.ms`, если задачи требуют длительных операций ввода-вывода.
  3. Перейти на протокол кооперативной перебалансировки (`CooperativeStickyAssignor`), исключающий блокировку «Stop-the-World» для всей группы.

### Сценарий 3: Потеря кворума и деградация репликации

#### RabbitMQ: Потеря кворума в Quorum Queues

- **Симптомы:** Клиенты получают ошибку `541 INTERNAL_ERROR` при попытке публикации; в логах: `quorum_queue: leader lost and no candidate with quorum`.
- **Причина:** Отказ 2 из 3 узлов или сетевое разделение (Network Partition).
- **Решение:**
  1. Проверить статус доступности узлов: `rabbitmqctl cluster_status`.
  2. Восстановить сетевую связность между узлами кластера (порты 4369, 25672).
  3. Подробный регламент ручного восстановления кворума см. в **[RabbitMQ: Устранение неполадок](../rabbitmq/troubleshooting.md)**.

#### Apache Kafka: Under-Replicated Partitions (URP)

- **Симптомы:** Растет метрика `kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions`; брокеры возвращают ошибку `NOT_ENOUGH_REPLICAS` продюсерам при `acks=all`.
- **Причина:** Реплика выпала из ISR из-за сетевой задержки, дефицита дискового ввода-вывода или падения брокера.
- **Диагностика:**
  ```bash
  kafka-topics.sh --bootstrap-server localhost:9092 --describe --under-replicated-partitions
  ```
- **Решение:**
  1. Проверить доступность брокеров-последователей и загрузку их дисков.
  2. Проверить таймаут репликации `replica.lag.time.max.ms` (по умолчанию 30 000 мс).
  3. Детальные сценарии ликвидации аварий см. в **[Troubleshooting Playbook для Apache Kafka](./kafka_troubleshooting_playbook.md)**.

### Сценарий 4: Зацикливание «ядовитых» сообщений (Poison Pills)

- **RabbitMQ:** Ошибка парсинга вызывает `basic_nack(requeue=True)`, сообщение возвращается в начало очереди и немедленно берется тем же воркером, вызывая бесконечный шторм перезапусков.
  - *Решение:* Обязательно настраивать `x-delivery-limit` для Quorum Queues в сочетании с Dead Letter Exchange (`x-dead-letter-exchange`). После $N$ неуспешных доставок брокер сам переложит сообщение в карантинную DLQ-очередь.
- **Kafka:** Ошибка парсинга в консьюмере приводит к тому, что офсет не коммитится, и следующий вызов `poll()` перечитывает то же самое бинарное сообщение.
  - *Решение:* Реализовать логику перехвата исключений (try-except) в коде консьюмера: публикация сбойного сообщения в отдельный DLQ-топик с заголовками ошибки и последующий коммит офсета в основном топике.

## Рекомендации и лучшие практики (Best Practices)

### Sizing оборудования и планирование емкости

- **RabbitMQ:**
  - *RAM:* Основной критический ресурс. Рассчитывается исходя из ожидаемого размера сообщений в очередях и лимита соединений: не менее 16–32 ГБ RAM на узел.
  - *Диск:* Быстрые SSD/NVMe необходимы для WAL кворумных очередей.
  - *CPU:* Чувствителен к однопоточной производительности ядер для интенсивных очередей (одна классическая очередь обрабатывается одним процессом Erlang).
- **Apache Kafka:**
  - *RAM:* Достаточно 16–64 ГБ RAM на узел, из которых под кучу JVM выделяется строго 6–8 ГБ (сборщик мусора G1GC). Все остальное пространство отдается под Page Cache ядра Linux.
  - *Диск:* Дисковая подсистема критична для пропускной способности. Предпочтительны NVMe в RAID 10 с файловой системой XFS (опции монтирования `noatime`).
  - *Сеть:* Сетевой интерфейс 10GbE / 25GbE является стандартом для предотвращения бутылочного горлышка при репликации логов.

### Тюнинг операционной системы Linux

### Мониторинг и алертинг (Prometheus метрики)

#### Ключевые метрики RabbitMQ (`rabbitmq_prometheus` порт 15692)

- `rabbitmq_queue_messages_unacknowledged`: Всплеск свидетельствует о зависании консьюмеров.
- `rabbitmq_alarms_memory_used_watermark`: Индикатор срабатывания memory alarm (должен быть 0).
- `rabbitmq_alarms_free_disk_space_watermark`: Индикатор исчерпания диска.
- `rabbitmq_process_resident_memory_bytes`: Потребление RAM процессом BEAM.

#### Ключевые метрики Apache Kafka (JMX Exporter / `kafka_exporter`)

- `kafka_consumergroup_lag`: Отставание консьюмер-группы по конкретным партициям (основная SLO-метрика).
- `kafka_server_replicamanager_underreplicatedpartitions`: Количество недореплицированных партиций (критический алерт для SRE).
- `kafka_controller_kafkacontroller_activecontrollercount`: Должен быть строго равен 1 в кластере.
- `kafka_network_requestmetrics_totaltimems`: Латентность обработки клиентских запросов.

Подробнее см. в **[Kafka для мониторинга](./kafka_for_monitoring.md)** и **[RabbitMQ: Мониторинг и алертинг](../rabbitmq/monitoring_and_alerting.md)**.

### Безопасность и изоляция

- **RabbitMQ:** Изоляция сред (dev, stage, prod) строится на базе виртуальных хостов (**vhosts**). Права пользователей разграничиваются регулярными выражениями на конфигурацию, запись и чтение очередей/обменников. Поддерживается mTLS и интеграция с корпоративным LDAP.
- **Kafka:** Изоляция достигается префиксами имен топиков и списками контроля доступа (**ACL**). Аутентификация обеспечивается протоколами SASL/SCRAM или mTLS. Доступ гранулируется по операциям (`Read`, `Write`, `Describe`) для топиков, консьюмер-групп и кластера.

## Дополнительная информация

### Ограничения и краевые случаи

- **Цифры пропускной способности:** Значения в таблицах и примерах служат ориентирами архитектурного масштаба. В реальной среде производительность зависит от сетевой задержки, включения fsync, durability-настроек (`acks=all` против `acks=1`), размера батча и аппаратных характеристик дисков.
- **Критичность длительного накопления (Backlog):** Классические очереди RabbitMQ деградируют при накоплении многодневного бэклога из-за исчерпания RAM и сброса страниц на диск. Kafka и RabbitMQ Streams хранят данные на диске и устойчивы к бэклогам произвольного размера в рамках выделенного retention.
- **Специфика Share Groups (Kafka 4.2+):** Share Groups снимают ограничение «одна партиция = один консьюмер», но не поддерживают транзакции Exactly-Once и строгий порядок по ключу. Для строгой последовательности событий по сущностям следует использовать традиционные Consumer Groups.
- **Необратимость чтения vs Replay:** Подтвержденное сообщение в RabbitMQ удаляется навсегда. В Kafka перемещение офсета позволяет перечитать данные за прошлые периоды, однако неконтролируемый сброс офсета на продакшене без учета идемпотентности консьюмеров может привести к повторной обработке миллионов финансовых или учетных операций.
- **Разделение задач по профилю нагрузки:** Использование Kafka для передачи редких единичных RPC-сообщений или использование RabbitMQ в качестве витрины исторических данных для аналитики приводит к борьбе с внутренней архитектурой систем.
