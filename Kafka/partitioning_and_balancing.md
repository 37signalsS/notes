# Партиционирование и балансировка Kafka

Партиционирование — ключевой механизм горизонтального масштабирования и параллелизма в Apache Kafka.

**SSoT для смежных тем:**
- **[Обзор Apache Kafka](./kafka_overview.md)** — базовые компоненты: топики, брокеры, consumer groups
- **[Принципы очередей сообщений](./message_queues_principles.md)** — общие концепции: продюсер, консьюмер, брокер

## Определения

* **Партиция (Partition)**: Минимальная единица параллелизма в Kafka. Каждая партиция — это упорядоченный, неизменяемый лог (журнал) сообщений, куда данные дописываются последовательно. Порядок сообщений гарантируется только в пределах одной партиции.
* **Лидер и Последователь (Leader/Follower)**: Для каждой партиции одна из её реплик назначается **лидером**, который обрабатывает все запросы на чтение и запись. Остальные реплики — **последователи** (followers) — пассивно копируют данные с лидера.
* **In-Sync Replicas (ISR)**: Набор реплик (включая лидера), которые синхронизированы с лидером. Запись считается успешной (`acks=all`) только после того, как её подтвердили все реплики из списка ISR.
* **Replication Factor (RF)**: Общее количество копий (реплик) каждой партиции. Для production-сред рекомендуется `RF >= 3`.
* **min.insync.replicas (minISR)**: Минимальное количество реплик в ISR, которое должно подтвердить запись, чтобы она считалась успешной при `acks=all`. Обычно устанавливается в `RF - 1` для обеспечения отказоустойчивости.
* **Partitioner**: Клиентский компонент продюсера, который определяет, в какую партицию будет отправлено сообщение.
* **Ребалансировка (Rebalancing)**: Процесс перераспределения партиций между консьюмерами в одной consumer group при изменении их количества (добавлении нового или сбое существующего).

## Основные концепции

### Стратегии партиционирования (Partitioner)

Выбор стратегии партиционирования напрямую влияет на порядок обработки и распределение нагрузки.

1. **По ключу (Key-based Partitioning)**:
    * **Принцип**: Продюсер вычисляет `hash(key) % num_partitions` для определения целевой партиции.
    * **Гарантия**: Все сообщения с одинаковым ключом (например, `user_id`) попадают в одну и ту же партицию, что обеспечивает строгий порядок их обработки.
    * **Проблема**: "Горячие" ключи могут приводить к неравномерному распределению данных и нагрузки (`skew`).

2. **Без ключа (Round-Robin / Sticky Partitioning)**:
    * **Принцип**: Если ключ не указан, сообщения распределяются по партициям для равномерной нагрузки.
      * **Старый Round-Robin**: Каждое сообщение отправлялось в следующую партицию по кругу (неэффективно).
      * **Современный Sticky Partitioner**: Продюсер отправляет пачку сообщений (батч) в одну партицию, затем следующую пачку в другую. Это улучшает компрессию и снижает задержки.
    * **Гарантия**: Порядок на уровне всего топика не гарантируется.

3. **Кастомный Partitioner**:
    * Позволяет реализовать собственную логику распределения. Например, для учёта географии, веса клиентов или для борьбы с "горячими" ключами (например, шардируя ключ `key + #shard_id`).

### Балансировка потребителей (Consumer Rebalancing)

Когда состав consumer group меняется, Kafka запускает протокол ребалансировки, чтобы переназначить партиции.

**Стратегии назначения (`partition.assignment.strategy`):**

* **RangeAssignor**: Назначает партиции "диапазонами". Может приводить к небольшому перекосу нагрузки.
* **RoundRobinAssignor**: Распределяет партиции по очереди между всеми консьюмерами, обеспечивая более равномерную нагрузку.
* **CooperativeStickyAssignor (рекомендуемый)**:
  * Минимизирует количество перемещаемых партиций при ребалансировке. Во время ребалансировки консьюмеры не останавливают обработку тех партиций, которые за ними остались.
  * Значительно снижает длительность пауз "stop-the-world", критичных для потоковых приложений.

## Практические сценарии

### Выбор количества партиций

* **Определяет максимальный параллелизм**: Число партиций = максимальное количество активных консьюмеров в одной группе.
* **Влияет на производительность**: Слишком большое количество партиций увеличивает нагрузку на контроллер кластера, потребление памяти и количество открытых файловых дескрипторов.
* **Практическое правило**: Подбирать количество, исходя из целевой пропускной способности. Тестовый ориентир: 1-5 МБ/с на одну партицию при среднем размере сообщений.

### Настройки для продюсера

```ini
bootstrap.servers=broker1:9092,broker2:9092
# Максимальная надежность
acks=all
enable.idempotence=true
# Оптимизация производительности
compression.type=lz4
linger.ms=20
batch.size=131072
```

### Настройки для потребителя

```ini
group.id=payments-workers
bootstrap.servers=broker1:9092,broker2:9092
# Плавная ребалансировка без остановки мира
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
# Таймауты для обнаружения "мёртвых" консьюмеров
max.poll.interval.ms=300000
session.timeout.ms=10000
```

### Административные операции

#### Создание топика

Создание топика `payments` с 12 партициями, фактором репликации 3 и требованием как минимум 2 синхронизированных реплик для подтверждения записи.

```bash
kafka-topics.sh --bootstrap-server broker1:9092 
  --create --topic payments 
  --partitions 12 --replication-factor 3 
  --config min.insync.replicas=2
```

#### Увеличение числа партиций

Увеличить количество партиций можно, но уменьшить нельзя.

```bash
kafka-topics.sh --bootstrap-server broker1:9092 
  --alter --topic payments --partitions 24
```

**Важно**: Эта операция меняет отображение `hash(key)` на партицию, что может нарушить порядок для существующих ключей.

#### Ручная ребалансировка кластера

Для выравнивания нагрузки на брокеры (например, после добавления нового узла) используется `kafka-reassign-partitions.sh`.

```bash
# 1. Сгенерировать план перемещения
kafka-reassign-partitions.sh --bootstrap-server broker1:9092 
  --topics-to-move-json-file topics.json 
  --broker-list "1,2,3,4" --generate

# 2. Выполнить перемещение по сгенерированному плану
kafka-reassign-partitions.sh --bootstrap-server broker1:9092 
  --execute --reassignment-json-file reassignment.json

# 3. Вернуть лидерство предпочитаемым репликам для идеального баланса
kafka-preferred-replica-election.sh --bootstrap-server broker1:9092
```

## Additional Information

### Параметры брокера для авто-балансировки

```ini
# Разрешить брокеру автоматически запускать ребалансировку лидеров
auto.leader.rebalance.enable=true
# Запретить небезопасный выбор лидера из реплик, не входящих в ISR
unclean.leader.election.enable=false
# Количество партиций по умолчанию для авто-создаваемых топиков
num.partitions=3
```
