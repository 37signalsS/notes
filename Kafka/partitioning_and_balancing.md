# Партиционирование и балансировка в Apache Kafka

Партиционирование — это фундаментальный механизм Apache Kafka, обеспечивающий горизонтальное масштабирование, параллельную обработку данных и отказоустойчивость. Балансировка нагрузки распределяет эти партиции между брокерами кластера и потребителями внутри групп.

---

## Определения

- **Партиция (Partition):** Минимальная единица параллелизма и хранения в Kafka. Представляет собой упорядоченный, неизменяемый журнал (лог) сообщений, в который данные только дописываются.
- **Репликация (Replication):** Процесс копирования данных партиции на несколько брокеров для обеспечения отказоустойчивости.
- **Лидер реплики (Leader):** Узел кластера, который обрабатывает все запросы на чтение и запись для данной партиции.
- **Последователь реплики (Follower):** Узел кластера, который пассивно реплицирует данные с лидера. Не участвует в обслуживании клиентов (кроме случаев настройки `rack awareness` для чтения).
- **ISR (In-Sync Replicas):** Список реплик, которые полностью синхронизированы с лидером. Только реплика из ISR может быть выбрана новым лидером при сбое.
- **High Watermark (HW):** Офсет последнего сообщения, которое было успешно реплицировано на все ISR. Консьюмеры в режиме `read_committed` видят данные только до этого уровня.
- **Partitioner:** Клиентский компонент (на стороне продюсера), ответственный за выбор целевой партиции для сообщения.
- **Consumer Group Rebalancing:** Процесс перераспределения партиций между потребителями внутри одной группы.
- **Preferred Leader:** Реплика, которая изначально была назначена лидером при создании топика. Kafka стремится поддерживать именно эти реплики в роли лидеров для равномерного распределения нагрузки.
- **Rack Awareness:** Механизм учета физического расположения брокеров (стоек) для предотвращения потери данных при выходе из строя целой стойки.

## Основные концепции

### Стратегии партиционирования (Partitioner)

Эффективность распределения данных зависит от того, как продюсер выбирает партицию.

1.  **По ключу (Key-based Partitioning):**
    *   **Механизм:** `hash(key) % num_partitions`.
    *   **Гарантия:** Сообщения с одинаковым ключом всегда попадают в одну партицию, что обеспечивает строгий порядок обработки событий одного объекта (например, транзакции одного пользователя).
    *   **Проблема:** При наличии «тяжелых» ключей (Data Skew) одна партиция может быть перегружена.

2.  **Без ключа (Uniform Sticky Partitioning):**
    *   **Механизм:** Продюсер объединяет сообщения в батч и отправляет весь батч в одну партицию до его заполнения, затем переключается на следующую.
    *   **Преимущество:** Максимальная эффективность сжатия и низкая нагрузка на сеть по сравнению с Round-Robin, где сообщения распределяются поштучно.

3.  **Rack-aware Partitioning:**
    *   При создании топика Kafka распределяет реплики так, чтобы они находились на разных стойках (`broker.rack`), обеспечивая выживаемость данных при аварии в дата-центре.

### Механизмы ребалансировки потребителей

Ребалансировка запускается при изменении состава группы потребителей (добавление/удаление пода) или изменении метаданных топика (добавление партиций).

1.  **Eager Rebalancing (Stop-the-world):**
    *   Все консьюмеры группы прекращают чтение и отдают свои партиции.
    *   Группа простаивает, пока координатор перераспределяет ресурсы.
    *   Критично для систем с большим количеством партиций и жестким SLA.

2.  **Incremental Cooperative Rebalancing:**
    *   Доступно начиная с Kafka 2.4 (рекомендуется `CooperativeStickyAssignor`).
    *   Консьюмеры отдают только те партиции, которые должны быть перемещены. Остальные продолжают обработку.
    *   Процесс проходит в несколько этапов, минимизируя время простоя системы.

### Выбор лидера (Leader Election)

- **Clean Leader Election:** Новый лидер выбирается только из ISR. Если ISR пуст, партиция становится недоступной. Это приоритет консистентности (CP).
- **Unclean Leader Election:** Разрешает выбор лидера не из ISR (отставшей реплики) при падении лидера. Позволяет сохранить доступность, но ведет к потере данных. Настраивается через `unclean.leader.election.enable`.

## Практические сценарии

### Выбор количества партиций

Количество партиций — это предел параллелизма.
*   **Формула:** `Max(Число продюсеров * throughput, Число консьюмеров * throughput)`.
*   **Рекомендация:** Начинать с небольшого запаса (например, в 2-3 раза больше текущего числа воркеров).
*   **Ограничение:** Большое количество партиций (десятки тысяч на брокер) замедляет восстановление при сбоях и увеличивает нагрузку на контроллер.

### Оптимизация настроек для балансировки

**На стороне продюсера:**
```ini
# Использование современного Sticky Partitioner
partitioner.class=org.apache.kafka.clients.producer.internals.DefaultPartitioner
# Включение идемпотентности для предотвращения дублей при переключении лидеров
enable.idempotence=true
```

**На стороне потребителя:**
```ini
# Использование кооперативной стратегии для исключения stop-the-world
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
# Таймаут, после которого брокер считает консьюмера «мертвым» и запускает ребаланс
session.timeout.ms=10000
# Максимальное время обработки батча (если превышено — ребаланс)
max.poll.interval.ms=300000
```

### Административные операции

#### Расширение топика (увеличение партиций)
Партиции можно только добавлять.
```bash
kafka-topics.sh --bootstrap-server localhost:9092 \
  --alter --topic orders --partitions 24
```
**Важно:** Это ломает логику хеширования по ключу. Старые и новые данные с одним ключом окажутся в разных партициях, нарушая порядок.

#### Перераспределение партиций при расширении кластера
После добавления новых брокеров данные сами на них не переедут. Требуется ручной запуск.
```bash
# 1. Сгенерировать план (нужен список топиков в JSON)
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --topics-to-move-json-file topics.json --broker-list "1,2,3,4" --generate

# 2. Выполнить перемещение (план сохраняется в файл)
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
  --execute --reassignment-json-file expand-cluster-plan.json
```

#### Принудительная балансировка лидеров (Preferred Leader Election)
Для выравнивания нагрузки по CPU и сети:
```bash
kafka-leader-election.sh --bootstrap-server localhost:9092 \
  --election-type preferred --all-topic-partitions
```

## Дополнительная информация

### Конфигурация брокера для стабильности

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `auto.leader.rebalance.enable` | `true` | Фоновая автоматическая проверка баланса лидеров. |
| `min.insync.replicas` | `2` (при RF=3) | Гарантирует, что запись подтверждена минимум двумя нодами. |
| `unclean.leader.election.enable` | `false` | Запрет на выбор лидера из несинхронизированных реплик. |

### Глоссарий терминов

| Термин | Описание |
| :--- | :--- |
| **ISR** | In-Sync Replicas. Список реплик, готовых стать лидером без потери данных. |
| **Data Skew** | Перекос данных, когда одна партиция значительно больше остальных. |
| **Head-of-Line Blocking** | Ситуация в Consumer Groups, когда одно медленное сообщение блокирует всю партицию. |
| **Preferred Leader** | Изначально назначенный лидер для равномерного распределения. |
