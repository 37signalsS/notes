# Партиционирование и балансировка Kafka

Партиционирование — ключевой механизм горизонтального масштабирования и параллелизма в Apache Kafka.

## Определения

- **Партиция (Partition)** — минимальная единица параллелизма в Kafka. Каждая партиция представляет собой упорядоченный, неизменяемый лог (журнал) сообщений, куда данные дописываются последовательно. Порядок сообщений гарантируется строго в пределах одной партиции.
- **Лидер и Последователь (Leader/Follower)** — роли реплик партиции. Одна реплика назначается **лидером**, обрабатывающим все запросы на чтение и запись. Остальные реплики — **последователи** (followers) — пассивно копируют данные с лидера.
- **ISR (In-Sync Replicas)** — набор реплик (включая лидера), которые полностью синхронизированы с лидером. Запись считается успешной при `acks=all` только после подтверждения всеми репликами из ISR.
- **RF (Replication Factor)** — фактор репликации, определяющий общее количество копий (реплик) каждой партиции. Для продуктивных сред рекомендуется `RF >= 3`.
- **min.insync.replicas** — минимальное количество реплик в ISR, которое должно подтвердить запись для её признания успешной при использовании `acks (acknowledgements)=all`. Рекомендуемое значение: `RF - 1`.
- **Partitioner** — клиентский компонент продюсера, определяющий целевую партицию для отправки сообщения.
- **Ребалансировка (Rebalancing)** — процесс перераспределения партиций между консьюмерами внутри одной группы при изменении их состава (добавление нового участника или сбой существующего).

## Основные концепции

### Стратегии партиционирования (Partitioner)

Выбор стратегии напрямую влияет на порядок обработки данных и распределение нагрузки на брокеры.

1. **По ключу (Key-based Partitioning)**:
    - **Принцип**: Продюсер вычисляет `hash(key) % num_partitions`.
    - **Преимущество**: Все сообщения с одинаковым ключом (например, `user_id`) попадают в одну партицию, обеспечивая строгий порядок обработки событий одного объекта.
    - **Риск**: При наличии «горячих» ключей возможно неравномерное распределение данных (`skew`).

2. **Без ключа (Round-Robin / Sticky Partitioning)**:
    - **Принцип**: Равномерное распределение сообщений при отсутствии ключа.
    - **Sticky Partitioner**: Продюсер отправляет батч (пакет) сообщений в одну партицию, затем следующий батч — в другую. Это оптимизирует компрессию и снижает задержки за счёт эффективного батчинга.

3. **Кастомный Partitioner**:
    - Позволяет реализовать специфичную логику, например, распределение по географическому признаку или весу клиента.

### Балансировка потребителей (Consumer Rebalancing)

При изменении состава группы потребителей Kafka перераспределяет партиции между ними.

**Стратегии назначения (`partition.assignment.strategy`):**

- **RangeAssignor**: Назначение партиций диапазонами.
- **RoundRobinAssignor**: Циклическое распределение партиций между всеми участниками.
- **CooperativeStickyAssignor (рекомендуемая)**:
  - Минимизирует перемещение партиций. Консьюмеры не прекращают обработку закреплённых за ними партиций, которые не участвуют в перемещении.
  - Устраняет длительные паузы типа «stop-the-world», критичные для высоконагруженных систем.

## Практические сценарии

### Выбор количества партиций

- **Параллелизм**: Число партиций определяет максимальное количество активных консьюмеров в одной группе.
- **Производительность**: Избыточное количество партиций увеличивает нагрузку на контроллер кластера и потребление файловых дескрипторов.
- **Ориентир**: 1–5 МБ/с на одну партицию в зависимости от размера сообщений и инфраструктуры.

### Пример настроек продюсера

```ini
bootstrap.servers=broker1:9092,broker2:9092
# Максимальная надежность
acks=all
enable.idempotence=true
# Оптимизация производительности
compression.type=lz4 (LZ4)
linger.ms=20
batch.size=131072
```

### Пример настроек потребителя

```ini
group.id=payments-workers
bootstrap.servers=broker1:9092,broker2:9092
# Плавная ребалансировка
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
# Таймауты для обнаружения сбоев
max.poll.interval.ms=300000
session.timeout.ms=10000
```

### Административные операции

#### Создание топика

Создание топика `payments` с 12 партициями и фактором репликации 3.

```bash
kafka-topics.sh --bootstrap-server broker1:9092 \
  --create --topic payments \
  --partitions 12 --replication-factor 3 \
  --config min.insync.replicas=2
```

#### Увеличение числа партиций

Количество партиций можно увеличить (уменьшение невозможно).

```bash
kafka-topics.sh --bootstrap-server broker1:9092 \
  --alter --topic payments --partitions 24
```

> **Важно:** Изменение количества партиций ломает логику хеширования по ключу, что может нарушить порядок обработки для существующих ключей.

#### Ручная ребалансировка кластера

Для выравнивания нагрузки между брокерами (например, после расширения кластера) используется инструмент `kafka-reassign-partitions.sh`.

```bash
# 1. Генерация плана перемещения
kafka-reassign-partitions.sh --bootstrap-server broker1:9092 \
  --topics-to-move-json-file topics.json \
  --broker-list "1,2,3,4" --generate

# 2. Выполнение перемещения
kafka-reassign-partitions.sh --bootstrap-server broker1:9092 \
  --execute --reassignment-json-file reassignment.json
```

## Дополнительная информация

### Параметры брокера для авто-балансировки

```ini
# Автоматическая ребалансировка лидеров
auto.leader.rebalance.enable=true
# Запрет выбора несинхронного лидера (защита от потери данных)
unclean.leader.election.enable=false
# Количество партиций по умолчанию
num.partitions=3
```

### Термины и понятия

| Термин | Описание |
| :--- | :--- |
| **ISR (In-Sync Replicas)** | Реплики, полностью синхронизированные с лидером. |
| **min.insync.replicas** | Порог минимального числа реплик для подтверждения записи. |
| **RF (Replication Factor)** | Общее число копий каждой партиции в кластере. |
| **Rebalancing** | Процесс перераспределения нагрузки между консьюмерами. |
| **Stop-the-world** | Полная остановка обработки на время проведения операций. |
