# Партиционирование и балансировка в Apache Kafka

Партиционирование — это фундаментальный механизм Apache Kafka, обеспечивающий горизонтальное масштабирование, параллельную обработку данных и отказоустойчивость. Балансировка нагрузки распределяет эти партиции между брокерами кластера и потребителями внутри групп.

---

## Определения

- **Партиция (Partition):** Минимальная единица параллелизма и хранения в Kafka. Представляет собой упорядоченный, неизменяемый журнал (лог) сообщений, в который данные только дописываются.
- **Репликация (Replication):** Процесс копирования данных партиции на несколько брокеров для обеспечения отказоустойчивости.
- **Лидер реплики (Leader):** Узел кластера, который обрабатывает все запросы на чтение и запись для данной партиции.
- **Последователь реплики (Follower):** Узел кластера, который пассивно реплицирует данные с лидера.
- **Синхронные реплики (ISR — In-Sync Replicas):** Список реплик, которые полностью синхронизированы с лидером. Только реплика из ISR может быть выбрана новым лидером при сбое.
- **High Watermark (HW):** Офсет последнего сообщения, которое было успешно реплицировано на все ISR.
- **Partitioner:** Клиентский компонент (на стороне продюсера), ответственный за выбор целевой партиции для сообщения.
- **Preferred Leader:** Реплика, которая изначально была назначена лидером при создании топика.
- **Rack Awareness:** Механизм учета физического расположения брокеров (стоек) для предотвращения потери данных при выходе из строя целой стойки.
- **Under-Replicated Partitions (URP):** Партиции, у которых количество синхронных реплик (ISR) меньше заданного фактора репликации. Ключевая метрика здоровья кластера.

---

## Основные концепции

### Стратегии партиционирования (Partitioner)

Эффективность распределения данных зависит от того, как продюсер выбирает партицию.

1.  **По ключу (Key-based Partitioning):**
    *   **Механизм:** `hash(key) % num_partitions`.
    *   **Гарантия:** Строгий порядок обработки событий одного объекта.
    *   **Data Skew:** При низкой кардинальности ключа (мало уникальных значений) возникает перекос нагрузки на партиции.

2.  **Без ключа (Uniform Sticky Partitioning):**
    *   **Механизм:** Продюсер пишет весь батч в одну партицию до его заполнения, затем переключается.
    *   **Преимущество:** Максимальная эффективность сжатия и низкая нагрузка на сеть.

3.  **Кастомные партиционеры (Custom Partitioners):**
    *   **Приоритезация:** Выделение конкретных партиций под VIP-клиентов или критичный трафик.
    *   **Детерминизм:** Логика должна быть строго детерминированной, иначе порядок сообщений будет нарушен.
    *   **Сложные ключи:** Использование композитных ключей (например, `user_id:event_type`) для тонкого управления потоками.

### Механизмы ребалансировки потребителей

1.  **Incremental Cooperative Rebalancing (KIP-429):** Рекомендуемый режим. Консьюмеры отдают только перемещаемые партиции, остальные продолжают работу.
2.  **Статическое членство (Static Membership — KIP-345):** Использование `group.instance.id` в Kubernetes/Docker для исключения ребалансировок при кратковременном перезапуске подов.

### Автоматизация балансировки через Cruise Control

Для крупных кластеров ручное управление невозможно. Используется **Cruise Control** (от LinkedIn):
- **Hard Goals:** Незыблемые правила (например, Rack Awareness, лимит реплик на брокер).
- **Soft Goals:** Желаемые состояния (равномерная загрузка CPU, диска, сети).
- **Self-healing:** Автоматическое перемещение партиций с упавших брокеров или «битых» дисков (JBOD).

## Практические сценарии

### Выбор количества партиций и лимиты

*   **Формула:** `Max(Число продюсеров * throughput, Число консьюмеров * throughput)`.
*   **Лимиты:** На bare-metal серверах обычно рекомендуется не более **4,000–6,000 партиций на брокер**. Превышение ведет к росту нагрузки на контроллер и замедлению восстановления (Recovery Time).
*   **Влияние Tiered Storage:** Позволяет хранить огромные объемы данных, не нагружая балансировку локальных дисков брокеров.

### Тюнинг Bare Metal / VM окружения

Для эффективной работы системы ввода-вывода (I/O) необходима настройка ОС:
1.  **Дисковая подсистема (JBOD):** Используйте несколько путей в `log.dirs`. Рекомендуется XFS или Ext4. Избегайте RAID 5/6 (Kafka сама обеспечивает репликацию эффективнее).
2.  **I/O Scheduler:** Используйте `deadline` или `noop` (для SSD), чтобы исключить лишнюю сортировку запросов ядром.
3.  **Memory Management:** Установите `vm.swappiness = 1`, чтобы JVM не уходила в swap. Выделяйте не более 40-50% RAM под Heap JVM, оставляя остальное под **Page Cache ОС**.

### Перераспределение партиций (Partition Reassignment)

При добавлении брокеров данные не переносятся автоматически. Используется `kafka-reassign-partitions.sh`.

**Безопасное выполнение:**
1.  **Throttling:** Всегда указывайте лимит пропускной способности (например, `--throttle 5000000` — 5 МБ/с).
2.  **Мониторинг:** Следите за метрикой `UnderReplicatedPartitions`. Если она не растет — throttle можно увеличить.
3.  **Очистка (Cleanup):** После завершения переезда **обязательно** выполните команду с флагом `--verify`. Это единственный способ снять ограничения (throttles) с брокеров.

### Оптимизация настроек

**На стороне потребителя:**
```ini
# Использование кооперативной стратегии
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor
# Увеличение таймаутов для статического членства
session.timeout.ms=45000
```

## Дополнительная информация

### Конфигурация брокера для стабильности

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `auto.leader.rebalance.enable` | `true` | Фоновая проверка баланса лидеров. |
| `min.insync.replicas` | `2` (при RF=3) | Гарантия записи минимум на две ноды. |
| `unclean.leader.election.enable` | `false` | Запрет выбора лидера из несинхронизированных реплик. |
