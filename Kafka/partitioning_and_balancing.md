# Партиционирование и балансировка в Apache Kafka

Партиционирование — это фундаментальный механизм Apache Kafka, обеспечивающий горизонтальное масштабирование, параллельную обработку данных и отказоустойчивость. Балансировка нагрузки распределяет эти партиции между брокерами кластера и потребителями внутри групп.

---

## Предварительные требования

- **ОС:** Linux (RHEL/CentOS 8+, Ubuntu 20.04+, Debian 11+) или macOS 12+ для локальной разработки.
- **JVM:** Java 17+ (Kafka 4.x); Java 11 поддерживается только в ветке 3.x, Java 8 удален (KIP-750, KIP-1013).
- **Kafka:** 3.3+ для Sticky Partitioner (KIP-480) и CooperativeStickyAssignor (KIP-429); 3.7+ для KIP-848 (новый протокол групп, GA в 4.0); 3.9+ для Tiered Storage (GA).
- **Диск:** SSD/NVMe рекомендуется для production; XFS или Ext4. Избегайте RAID 5/6 — Kafka обеспечивает репликацию эффективнее.
- **Сеть:** Низкая задержка между брокерами (<1 мс внутри дата-центра); для cross-DC репликации настройте `replica.lag.time.max.ms` с запасом под RTT.
- **Память:** Не более 40–50% RAM под Heap JVM; остальное оставить под Page Cache ОС. Минимум 4–8 GB RAM на брокер для production.

## Определения

- **Партиция (Partition):** Минимальная единица параллелизма и хранения в Kafka. Представляет собой упорядоченный, неизменяемый журнал (лог) сообщений, в который данные только дописываются.
- **Репликация (Replication):** Процесс копирования данных партиции на несколько брокеров для обеспечения отказоустойчивости.
- **Лидер реплики (Leader):** Узел кластера, который обрабатывает все запросы на чтение и запись для данной партиции.
- **Последователь реплики (Follower):** Узел кластера, который пассивно реплицирует данные с лидера.
- **Синхронные реплики (ISR — In-Sync Replicas):** Список реплик, которые полностью синхронизированы с лидером. Только реплика из ISR может быть выбрана новым лидером при сбое.
- **High Watermark (HW):** Офсет последнего сообщения, которое было успешно реплицировано на все ISR.
- **Partitioner:** Клиентский компонент (на стороне продюсера), ответственный за выбор целевой партиции для сообщения.
- **Preferred Leader:** Реплика, которая изначально была назначена лидером при создании топика.
- **Rack Awareness:** Механизм учета физического расположения брокеров (стоек) для предотвращения потери данных при выходе из строя целой стойки.
- **Under-Replicated Partitions (URP):** Партиции, у которых количество синхронных реплик (ISR) меньше заданного фактора репликации. Ключевая метрика здоровья кластера.
- **Assignor (Assignment Strategy):** Алгоритм распределения партиций между консьюмерами внутри группы. Встроенные стратегии: `Range`, `RoundRobin`, `Sticky`, `CooperativeSticky`.
- **Rebalancing (Ребалансировка):** Процесс перераспределения партиций между консьюмерами при изменении состава группы.
- **Static Membership (Статическое членство, KIP-345):** Механизм, при котором консьюмер сохраняет назначение партиций при перезапуске, если он rejoins в пределах `session.timeout.ms`, используя `group.instance.id`.
- **KIP-848 (New Group Protocol):** Протокол управления группами, где назначение партиций выполняет координатор на стороне брокера инкрементально, без "Stop-the-world" пауз. GA с Kafka 4.0.
- **Data Locality:** Принцип размещения связанных данных в одной партиции для минимизации кросс-партиционных операций.

## Основные концепции

### Преимущества партиционирования

Партиционирование позволяет Kafka эффективно обрабатывать огромные потоки данных за счет следующих факторов:
- **Распределение (Distribution):** Данные топика распределяются по нескольким брокерам, что исключает появление единого узла-бутылочного горлышка.
- **Параллелизм (Parallelism) и чтение:** Каждая партиция может обрабатываться независимым консьюмером. Разделение топика на части позволяет множеству потребителей читать данные одновременно, что критично для горизонтального масштабирования. Без партиций пропускная способность была бы ограничена ресурсами одной машины.
- **Масштабируемость (Scalability):** Топики могут выходить за пределы ресурсов одного брокера (CPU, RAM, Disk), распределяя нагрузку на весь кластер.
- **Отказоустойчивость (Fault Tolerance):** При сбое одного брокера партиции на других узлах остаются доступными (в сочетании с репликацией).
- **Строгий порядок (Ordering):** Гарантируется строгая последовательность событий в пределах одной партиции в порядке их записи продюсером.
- **Локальность данных (Data Locality):** При правильном выборе ключа связанные события (например, все действия одного пользователя) оказываются в одной партиции, что упрощает оконную агрегацию и джойны на стороне консьюмера.

### Стратегии партиционирования (Partitioner)

Эффективность распределения данных зависит от того, как продюсер выбирает партицию.

1.  **По ключу (Key-based Partitioning):**
    *   **Механизм:** `hash(key) % num_partitions`. По умолчанию используется MurmurHash2.
    *   **Гарантия:** Строгий порядок обработки событий одного объекта (например, сообщения от одной зарядной станции или одного пользователя всегда попадают в одну партицию).
    *   **Data Skew:** При низкой кардинальности ключа (мало уникальных значений) возникает перекос нагрузки на партиции. Для диагностики используйте `kafka-run-class kafka.tools.DumpLogSegments` с последующим `awk`/`sort`/`uniq` на выбранной партиции.

2.  **Без ключа (Uniform Sticky Partitioning, KIP-480):**
    *   **Механизм:** Продюсер пишет весь батч в одну партицию до его заполнения, затем переключается на следующую. Начиная с Kafka 3.3 (KIP-794) логика учитывает изменение числа партиций.
    *   **Преимущество:** Максимальная эффективность сжатия и низкая нагрузка на сеть за счет крупных батчей.

3.  **Кастомные партиционеры (Custom Partitioners):**
    *   **Приоритезация:** Выделение конкретных партиций под VIP-клиентов или критичный трафик.
    *   **Детерминизм:** Логика должна быть строго детерминированной, иначе порядок сообщений будет нарушен.
    *   **Сложные ключи:** Использование композитных ключей (например, `user_id:event_type`) для тонкого управления потоками.

#### Сравнение стратегий назначения (Assignors)

| Стратегия | Поведение | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **Range** | Партиции сортируются; консьюмеры получают contiguous-диапазоны | Простота, порядок совпадает с порядком сортировки | Перекос при неравномерном ключевом распределении |
| **RoundRobin** | Циклическое распределение партиций по консьюмерам | Равномерный баланс без учета ключа | Нарушает локальность данных; перераспределяет все партиции при любом изменении состава |
| **Sticky** | Минимизирует перемещения партиций при ребалансировке; сохраняет существующие назначения | Нет лишних переключений; сохраняет порядок | Сложнее предсказать финальное распределение |
| **CooperativeSticky** | Инкрементальная ребалансировка (KIP-429): отзываются только перемещаемые партиции | Без Stop-the-world; минимальные простои | Требует поддержки у всех консьюмеров в группе |

**Рекомендация:** `CooperativeStickyAssignor` — де-факто стандарт для production начиная с Kafka 2.4+.

### Баланс количества партиций

Правильный выбор числа партиций критичен для производительности:

- **Over-partitioning (Избыток):** Каждая партиция требует ресурсов для репликации, метаданных и координации. Слишком большое количество партиций может замедлить работу контроллера и увеличить время восстановления (Recovery Time).
  - **Формула оценки:** На каждый брокер рекомендуется до 4,000–6,000 партиций (включая внутренние топики). При превышении контроллер начинает испытывать pressure из-за роста метаданных и увеличения времени лидер-элекшн.
  - **Влияние на консьюмеров:** Чем больше партиций, тем больше потоков и открытых файловых дескрипторов требуется консьюмер-группе.
- **Under-partitioning (Недостаток):** Слишком малое количество партиций ограничивает параллелизм (throughput), так как консьюмеры не могут эффективно распределить нагрузку.
  - **Формула:** `Max(Число продюсеров * целевой_throughput / throughput_на_партицию, Число консьюмеров * целевой_throughput / throughput_на_партицию)`.
  - **Важно:** Увеличить число партиций можно только в большую сторону; уменьшение невозможно без потери порядка по ключу. При увеличении количества партиций **старые сообщения остаются в своих исходных партициях** — перераспределения не происходит. Поскольку `hash(key) % N` пересчитывается с новым `N`, новые сообщения с тем же ключом могут попасть в другую партицию, что нарушает порядок событий для этого ключа между старыми и новыми записями. Поэтому количество партиций следует планировать заранее с запасом на 2–3 года роста.
- **Соответствие группе потребителей:** В идеале количество активных консьюмеров в группе должно быть **меньше или равно** количеству партиций. Лишние консьюмеры будут простаивать в статусе `IDLE`.
- **Локальность данных (Data Locality):** Правильный выбор ключа обеспечивает нахождение связанных данных в одной партиции для эффективной обработки.

### Репликация и высокая доступность

Репликация обеспечивает сохранность данных и непрерывность сервиса:

- **Высокая доступность (High Availability):** Если основной брокер (лидер) выходит из строя, другая реплика берет на себя его функции. Время переключения (failover) зависит от параметров `replica.lag.time.max.ms` и `session.timeout.ms` консьюмеров.
- **Отказоустойчивость (Fault Tolerance):** Защита от потери данных при аппаратных сбоях за счет хранения копий на разных узлах. Для rack-aware кластеров используйте `broker.rack` для гарантии распределения реплик по разным стойкам.
- **Масштабируемость чтения:** Реплики позволяют распределить нагрузку на чтение (read load) между несколькими брокерами, снижая нагрузку на лидера. По умолчанию чтение идет только через лидера; для follower-чтения требуется кастомный консьюмер с указанием `replica.fetch.max.bytes`.
- **Долговечность данных (Durability):** Гарантирует, что информация не будет потеряна даже при сбое брокера.
- **Увеличение пропускной способности:** В сочетании с партиционированием репликация позволяет значительно увеличить возможности параллельной обработки.

#### Формула выбора фактора репликации (RF)

| Среда | RF | min.insync.replicas | acks | Обоснование |
| :--- | :--- | :--- | :--- | :--- |
| Dev | 1 | 1 | all | Один брокер; допускается потеря данных |
| Staging | 2 | 2 | all | Два брокера; быстрый failover без потерь |
| Production | 3 | 2 | all | Три копии; потеря одного брокера не влияет на запись |

### Механизмы ребалансировки потребителей

1.  **Consumer Groups (Группы потребителей):** Набор консьюмеров, работающих совместно. Kafka гарантирует, что внутри одной группы каждая партиция читается **только одним** консьюмером.
2.  **Независимый прогресс:** Разные группы потребителей (например, `analytics` и `email`) читают один и тот же топик независимо. Каждая группа хранит свои смещения (offsets), что позволяет им обрабатывать данные со своей скоростью, не блокируя друг друга.
3.  **Rebalancing (Ребалансировка):** Если один из консьюмеров в группе выходит из строя, Kafka автоматически перераспределяет его партиции между оставшимися участниками группы.
4.  **Eager Rebalance (классический):** Все консьюмеры останавливают потребление, отдают все партиции, получают новый план и возобновляют работу. Проблема: Stop-the-world пауза, рост лага.
5.  **Incremental Cooperative Rebalancing (KIP-429):** Рекомендуемый режим. Консьюмеры отдают только перемещаемые партиции, остальные продолжают работу. Устраняет проблему "Stop-the-world" для всей группы.
6.  **Статическое членство (Static Membership — KIP-345):** Использование `group.instance.id` в Kubernetes/Docker для исключения ребалансировок при кратковременном перезапуске подов (в пределах `session.timeout.ms`).
7.  **Протокол KIP-848 (GA с Kafka 4.0):** Назначением партиций управляет координатор на стороне брокера инкрементально. Клиентский лидер группы больше не строит план распределения, что убирает паузы даже для очень больших групп. Клиенты подключаются через `group.protocol=consumer`.

### Алгоритмы выборов лидера

- **Preferred Leader Election:** По умолчанию Kafka стремится вернуть preferred leader (исходную реплику) для баланса дисков и сети. Запускается фоновым процессом при `auto.leader.rebalance.enable=true` или вручную через `kafka-leader-election.sh --election-type PREFERRED`.
- **Unclean Leader Election:** Если все реплики из ISR недоступны и `unclean.leader.election.enable=true`, лидером может стать отстающая реплика. **В production всегда `false`** — это защита от потери данных. При `false` запись блокируется до возвращения хотя бы одной ISR-реплики.

### Автоматизация балансировки через Cruise Control

Для крупных кластеров ручное управление невозможно. Используется **Cruise Control** (от LinkedIn):
- **Hard Goals:** Незыблемые правила (например, Rack Awareness, лимит реплик на брокер). Их нарушение блокирует план.
- **Soft Goals:** Желаемые состояния (равномерная загрузка CPU, диска, сети). Cruise Control ищет оптимум с учетом hard goals.
- **Self-healing:** Автоматическое перемещение партиций с упавших брокеров или «битых» дисков (JBOD).
- **Anomaly Detection:** Мониторинг отклонений от goals (перекошенные топики, перегруженные брокеры) и генерация `KafkaRebalance`-планов.

## Практические сценарии

### Сценарий: Отказ лидера партиции (Failover)

Предположим, топик имеет фактор репликации (RF) = 3.

1.  **Состояние:** Партиция 01 на Брокере 1 (Лидер), реплики — на Брокере 2 и 3 (Followers). ISR = [1, 2, 3].
2.  **Запись:** Продюсеры всегда отправляют данные Лидеру на Брокер 1. Брокеры 2 и 3 синхронизируют данные (ISR).
3.  **Сбой:** Брокер 1 выходит из строя.
4.  **Failover (Переключение):** Контроллер (в KRaft — кворум) crowns нового лидера из числа актуальных (up-to-date) последователей из ISR (например, Брокер 2). HW остаётся неизменным.
5.  **Прозрачность:** Продюсеры и консьюмеры автоматически переключаются на Брокер 2. Данные продолжают поступать и обрабатываться через нового лидера.

**Валидация после восстановления:**
```bash
# Проверить, что новый лидер не является preferred (если Брокер 1 ещё не поднялся)
kafka-topics.sh --bootstrap-server localhost:9092 --topic orders --describe
# → Partition: 0	Leader: 2	Replicas: 1,2,3	Isr: 2,3

# Вернуть preferred leader после возвращения Брокера 1
kafka-leader-election.sh --bootstrap-server localhost:9092 \
    --election-type PREFERRED --all-topic-partitions
# → Successfully started leader election for partitions orders-0, ...
```

### Выбор количества партиций и лимиты

*   **Формула:** `Max(Число продюсеров * throughput, Число консьюмеров * throughput)`.
*   **Лимиты:** На bare-metal серверах обычно рекомендуется не более **4,000–6,000 партиций на брокер**. В Kafka 4.0 с KRaft контроллер масштабируется лучше, но метаданные всё равно растут линейно. Превышение ведет к росту нагрузки на контроллер и замедлению восстановления (Recovery Time).
*   **Влияние Tiered Storage:** Позволяет хранить огромные объемы данных, не нагружая балансировку локальных дисков брокеров. Однако количество партиций по-прежнему влияет на метаданные и память контроллера.

**Практический пример:**
- Продюсеры генерируют 50 MB/s на топик.
- Одна партиция выдерживает ~5 MB/s при `acks=all` иBatch.size=32KB.
- Нужно минимум `ceil(50 / 5) = 10` партиций только для записи.
- Если консьюмеры могут обрабатывать 20 MB/s каждая, а их 3 — нужно минимум `ceil(3 * 20 / 5) = 12` партиций.
- **Итог:** 12 партиций покрывают и запись, и чтение.

### Тюнинг Bare Metal / VM окружения

Для эффективной работы системы ввода-вывода (I/O) необходима настройка ОС:
1.  **Дисковая подсистема (JBOD):** Используйте несколько путей в `log.dirs`. Рекомендуется XFS или Ext4. Избегайте RAID 5/6 (Kafka сама обеспечивает репликацию эффективнее).
2.  **I/O Scheduler:** Используйте `deadline` или `noop` (для SSD), чтобы исключить лишнюю сортировку запросов ядром.
3.  **Memory Management:** Установите `vm.swappiness = 1`, чтобы JVM не уходила в swap. Выделяйте не более 40-50% RAM под Heap JVM, оставляя остальное под **Page Cache ОС**.
4.  **Файловые дескрипторы:** Увеличьте `ulimit -n` до 100,000+ (Kafka открывает много сегментов и сокетов).
5.  **Сетевые буферы:** `net.core.rmem_max` и `net.core.wmem_max` ≥ 4 MB; `net.ipv4.tcp_rmem`/`tcp_wmem` с увеличенными значениями.

### Перераспределение партиций (Partition Reassignment)

При добавлении брокеров данные не переносятся автоматически. Используется `kafka-reassign-partitions.sh`.

**Безопасное выполнение:**
1.  **Throttling:** Всегда указывайте лимит пропускной способности (например, `--throttle 5000000` — 5 МБ/с). Для больших кластеров начните с 10–50 MB/s и мониторьте `UnderReplicatedPartitions`.
2.  **Генерация плана:** Используйте `--topics-to-move-json-file` или `--broker-list`. Сохраните текущую раскладку ("Current partition replica assignment") как план отката.
3.  **Мониторинг:** Следите за метрикой `UnderReplicatedPartitions` (JMX) и `kafka-log-dirs.sh --describe`. Если она растет — throttle можно уменьшить, а не увеличивать.
4.  **Очистка (Cleanup):** После завершения переезда **обязательно** выполните команду с флагом `--verify`. Это единственный способ снять ограничения (throttles) с брокеров.
5.  **Ожидание:** Не запускайте следующую ребалансировку, пока предыдущая не завершилась. Проверка: `kafka-reassign-partitions.sh --verify` должен показать `completed` для всех партиций.

**Полный пример:**
```bash
# ШАГ 1: Генерация плана
cat > topics.json <<EOF
{"topics": [{"topic": "orders"}, {"topic": "payments"}], "version": 1}
EOF

kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
    --topics-to-move-json-file topics.json \
    --broker-list "1,2,3,4" --generate
# → Current partition replica assignment
# → Proposed partition reassignment configuration

# Сохраните Proposed в reassignment.json; Current — в reassignment-backup.json

# ШАГ 2: Выполнение с троттлингом
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
    --reassignment-json-file reassignment.json --execute --throttle 50000000

# ШАГ 3: Мониторинг прогресса (повторять каждые 30–60 секунд)
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
    --reassignment-json-file reassignment.json --verify

# ШАГ 4: Ожидание завершения
# → Status of partition reassignment:
# → Reassignment of partition orders-0 is completed.
```

**Валидация:**
```bash
# Проверить, что троттлинг снят
kafka-reassign-partitions.sh --bootstrap-server localhost:9092 \
    --reassignment-json-file reassignment.json --verify
# → Throttle was removed.

# Проверить раскладку
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders
```

### Масштабирование консьюмеров

При добавлении консьюмеров в группу происходит автоматическая ребалансировка. Чтобы минимизировать простой:

1.  Используйте `CooperativeStickyAssignor` на всех консьюмерах.
2.  Установите `session.timeout.ms` с запасом (45–60 секунд) и `max.poll.interval.ms` > времени обработки батча.
3.  Для кратковременного масштабирования (например, деплой) используйте статическое членство (`group.instance.id`), чтобы избежать ребалансировки вообще.

**Валидация:**
```bash
# До добавления консьюмера
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group orders-processor
# → 2 members, 12 partitions, lag stable

# После добавления (CooperativeSticky)
# → 3 members; только перемещаемые партиции отдаются; остальные продолжают читать
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group orders-processor
```

### Оптимизация настроек

**На стороне продюсера:**
```ini
# Идемпотентный продюсер (включен по умолчанию с Kafka 3.0)
enable.idempotence=true

# Сжатие батчей целиком
compression.type=lz4

# Накопление батча
linger.ms=20
batch.size=32768

# Общий лимит на доставку
delivery.timeout.ms=120000
```

**На стороне потребителя:**
```ini
# Использование кооперативной стратегии
partition.assignment.strategy=org.apache.kafka.clients.consumer.CooperativeStickyAssignor

# Увеличение таймаутов для статического членства
session.timeout.ms=45000
max.poll.interval.ms=300000
max.poll.records=500

# Для статического членства (Kubernetes/Docker)
group.instance.id=pod-orders-processor-7d9f4b8c5-x2abc
```

**На стороне брокера (стабильность):**
```ini
# Автоматическая балансировка preferred leaders
auto.leader.rebalance.enable=true

# Запрет unclean leader election
unclean.leader.election.enable=false

# Минимальное количество ISR для записи при acks=all
min.insync.replicas=2

# Фактор репликации по умолчанию
default.replication.factor=3
```

## Дополнительная информация

### Конфигурация брокера для стабильности

| Параметр | Значение | Описание |
| :--- | :--- | :--- |
| `auto.leader.rebalance.enable` | `true` | Фоновая проверка баланса лидеров. |
| `min.insync.replicas` | `2` (при RF=3) | Гарантия записи минимум на две ноды. |
| `unclean.leader.election.enable` | `false` | Запрет выбора лидера из несинхронизированных реплик. |
| `default.replication.factor` | `3` | Количество реплик для новых топиков по умолчанию. |
| `num.partitions` | `12` | Количество партиций по умолчанию при создании топика. |
| `replica.lag.time.max.ms` | `30000` | Максимальное время без fetch-запросов перед исключением из ISR. |
| `num.replica.fetchers` | `2` | Количество потоков репликации на брокере (≥2 для production). |
| `broker.rack` | `rack-1` | Идентификатор стойки для Rack Awareness. |

### Типичные ошибки и диагностика

| Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| `UnderReplicatedPartitions > 0` постоянно | Медленный диск, сеть или перегруженный follower | `kafka-topics.sh --describe`, JMX `IsrShrinkRate` | Проверить `iostat`, `netstat`, `replica.lag.time.max.ms` |
| Консьюмеры в группе не распределяются равномерно | Неправильный assignor или data skew | `kafka-consumer-groups.sh --describe --members --verbose` | Перейти на `CooperativeStickyAssignor`; проверить кардинальность ключей |
| Падение консьюмера с `NotLeaderForPartitionException` | Реконфигурация партиции во время запроса | Логи консьюмера, `auto.leader.rebalance.enable` | Включить `CooperativeStickyAssignor`; добавить retry с backoff в клиент |
| Высокий Consumer Lag на одной партиции | Poison Pill, Hot Key или деградация лидера | `kafka-consumer-groups.sh --describe`, дамп лога партиции | DLQ для отравленных сообщений; перераспределить ключи; проверить диск лидера |
| Reassignment зависает | Недостаточный throttle или сетевые проблемы | `--verify` показывает `still in progress` | Уменьшить throttle; проверить `UnderReplicatedPartitions`; не прерывать процесс |
| Кластер не может выбрать лидера | Все реплики упали или `unclean.leader.election.enable=false` при RF=1 | `kafka-topics.sh --describe`, логи контроллера | Восстановить брокер; для dev снизить `min.insync.replicas` и `replication.factor` до 1 |
| Over-partitioning: высокий latency, медленный controller | Слишком много партиций на брокер (>6k) | JMX `RequestHandlerAvgIdlePercent`, логи контроллера | Увеличить количество брокеров; объединить топики с низким throughput; включить Tiered Storage |

### Проверка работоспособности после изменений

После любого изменения конфигурации партиционирования или балансировки выполните проверку:

```bash
# 1. Здоровье кластера: ровно один активный контроллер
kafka-run-class kafka.tools.JmxTool \
  --object-name "kafka.controller:type=KafkaController,name=ActiveControllerCount" \
  --one-time true
# → 1

# 2. Нет недореплицированных партиций
kafka-run-class kafka.tools.JmxTool \
  --object-name "kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions" \
  --one-time true
# → 0

# 3. Раскладка партиций и лидеров
kafka-topics.sh --bootstrap-server localhost:9092 --describe --topic orders

# 4. Статус группы консьюмеров
kafka-consumer-groups.sh --bootstrap-server localhost:9092 --describe --group orders-processor
# → LAG стабильный, CONSUMER-ID заполнен для всех партиций

# 5. Проверка preferred leaders (опционально)
kafka-leader-election.sh --bootstrap-server localhost:9092 \
    --election-type PREFERRED --all-topic-partitions --verbose
```

### Лучшие практики (Checklist)

- [ ] Фактор репликации (RF) ≥ 3 для production; `min.insync.replicas=2` + `acks=all`.
- [ ] `unclean.leader.election.enable=false` на всех брокерах.
- [ ] Используется `CooperativeStickyAssignor` у всех консьюмеров в группе.
- [ ] Количество партиций закладывается с запасом на 2–3 года роста; при необходимости увеличивается заблаговременно.
- [ ] `broker.rack` настроен для всех брокеров в multi-rack среде.
- [ ] Мониторинг `UnderReplicatedPartitions`, `ActiveControllerCount`, `Consumer Lag` настроен.
- [ ] Для Kubernetes/Docker: `group.instance.id` включен для статического членства.
- [ ] Throttle указан при любом reassignment; `--verify` выполнен после завершения.
- [ ] JVM Heap ≤ 50% RAM; `vm.swappiness=1`; Page Cache не ограничена.
- [ ] Регулярная проверка preferred leader election (раз в неделю или после maintenance).

### Глоссарий

| Термин | Описание |
| :--- | :--- |
| **ISR** | Синхронные реплики (In-Sync Replicas). Готовы стать лидером. |
| **Data Skew** | Перекос данных, когда одна партиция перегружена. |
| **Preferred Leader** | Изначально назначенный лидер для баланса. |
| **Rack Awareness** | Учет физического расположения брокеров (стоек). |
| **Assignor** | Алгоритм распределения партиций между консьюмерами группы. |
| **Cooperative Rebalance** | Инкрементальная ребалансировка без Stop-the-world (KIP-429). |
| **Static Membership** | Статическое членство группы без ребалансировки при кратковременном перезапуске (KIP-345). |
| **KIP-848** | Новый протокол групп с брокерным назначением партиций (GA в Kafka 4.0). |
