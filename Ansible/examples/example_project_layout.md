# Структура проекта Ansible

## Определения

**Структура проекта Ansible** — это организация каталогов и файлов, которая определяет, где хранятся плейбуки, роли, инвентарь, переменные и другие компоненты Ansible. Правильная структура критически важна для поддержки, масштабирования и повторного использования кода автоматизации.

## Основные концепции

Хотя Ansible гибок, сообщество выработало стандартную структуру каталогов, которая считается лучшей практикой. Она использует разделение данных (инвентарь, переменные) и логики (плейбуки, роли).

**Ключевые каталоги и файлы:**

-   `ansible.cfg`: Корневой файл конфигурации.
-   `inventory/`: Файлы инвентаря, описывающие хосты и группы.
-   `group_vars/` и `host_vars/`: Каталоги для переменных, применяемых к группам или отдельным хостам. Ansible автоматически загружает переменные из файлов, названных в честь групп или хостов.
-   `roles/`: Каталог для хранения [ролей](../../Ansible/ansible_roles.md).
-   `*.yml`: Плейбуки, находящиеся в корне проекта.

## Практические сценарии

### Сценарий 1: Стандартная структура проекта

Это наиболее распространенный и рекомендуемый подход.

```
/
├── ansible.cfg
├── inventory/
│   ├── production.ini
│   └── staging.ini
├── group_vars/
│   ├── all.yml           # Переменные для всех хостов
│   └── webservers.yml    # Переменные для группы webservers
├── host_vars/
│   └── db-server-01.yml  # Переменные для конкретного хоста
├── roles/
│   ├── common            # Общая базовая роль
│   └── nginx             # Роль для установки и настройки Nginx
├── site.yml              # Основной плейбук, применяющий конфигурацию ко всем хостам
└── webservers.yml        # Плейбук для настройки только веб-серверов
```

**Описание компонентов:**

-   **`site.yml`**: "Мастер-плейбук", который обычно включает другие плейбуки или роли для полной настройки инфраструктуры.
-   **`group_vars/`**: Ansible автоматически загружает переменные из файла `webservers.yml` для всех хостов в группе `webservers`. Файл `all.yml` применяется ко всем хостам в инвентаре.
-   **Преимущества**: Простота, предсказуемость, соответствует официальной документации Ansible. Идеально подходит для большинства проектов.

### Сценарий 2: Продвинутая структура со скриптом-оберткой

Этот подход используется в более сложных системах, где плейбуки могут генерироваться динамически. Он менее распространен и требует дополнительного уровня абстракции в виде скрипта-обертки.

```
/
├── ansible.cfg
├── core/
│   ├── roles/
│   └── plays/            # Каталог с "шаблонами" плейбуков
├── inventory/
│   ├── client_A/
│   └── client_B/
├── logs/
└── deploy.sh             # Скрипт-обертка для запуска
```

**Описание компонентов:**

-   **`core/`**: Центральный каталог с логикой.
    -   `roles/`: Хранилище стандартных ролей.
    -   `plays/`: Содержит "заготовки" плейбуков. Это не готовые к выполнению файлы, а шаблоны, в которые скрипт-обертка будет подставлять данные (например, имена хостов).
-   **`inventory/`**: Разделение инвентаря по окружениям или клиентам.
-   **`deploy.sh`**: Основная точка входа, которая выполняет следующую логику:
    1.  Анализирует инвентарь для определения целевых хостов.
    2.  Берет шаблон из `core/plays/`.
    3.  Генерирует временный, готовый к выполнению плейбук, подставляя в него нужные переменные.
    4.  Запускает `ansible-playbook` с сгенерированным плейбуком.
-   **Преимущества**: Высокая гибкость, возможность динамически конструировать плейбуки "на лету".
-   **Недостатки**: Усложняет проект, требует поддержки дополнительного скрипта (`deploy.sh`), менее очевиден для новых участников команды.

## Дополнительная информация

### Сравнение подходов

| Критерий | Стандартная структура | Структура со скриптом-оберткой |
| :--- | :--- | :--- |
| **Сложность** | Низкая | Высокая |
| **Гибкость** | Средняя (достаточная для 95% задач) | Очень высокая |
| **Прозрачность** | Высокая, легко понять "что происходит" | Низкая, логика скрыта в скрипте `deploy.sh` |
| **Рекомендация**| Рекомендуется для большинства проектов | Для сложных систем с динамическими требованиями |
