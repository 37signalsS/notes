# Пример из реальной практики: Архитектура Ansible для CI/CD и управления мультипроектной средой

## 1. Основная архитектура: Общая роль и раздельные инвентари

*   **Проблема:** Компания поддерживает серверы для множества проектов, каждый со своей уникальной конфигурацией.
*   **Решение:**
    1.  **Общая роль "CORE":** Создана одна большая, общая роль, которая содержит всю основную логику для настройки серверов. Эта роль хранится в отдельном, централизованном Git-репозитории и является общей для всех проектов.
    2.  **Раздельные инвентари:** Для каждого проекта создается собственный, отдельный Git-репозиторий, в котором хранится только инвентарь (файлы `inventory`, `group_vars`, `host_vars`) и специфичные для проекта настройки.

    При запуске конфигурации для конкретного проекта, общая роль "CORE" применяется к инвентарю этого проекта.

## 2. Управление сложными стеками: `kubespray` и `ceph-ansible`

*   **Форки для каждого кластера:** Вместо использования общего плейбука, для **каждого** развертываемого кластера (будь то Kubernetes или Ceph) создается отдельный **форк** соответствующего репозитория (`kubespray`, `ceph-ansible`).
*   **Хранение конфигурации:** В этом форке хранится вся конфигурация, специфичная для данного кластера (инвентарь, переменные). Это гарантирует, что каждый кластер имеет свою изолированную и версионируемую кодовую базу для своей конфигурации.

## 3. Специфические сценарии: CI/CD

Сценарии для развертывания приложений (CI/CD) являются уникальными для каждого проекта. Поэтому для каждого из них создается отдельный репозиторий, содержащий все необходимые плейбуки и роли.

## 4. Архитектура выполнения, CI/CD и безопасность

Это ключевой компонент всей системы, обеспечивающий безопасное и автоматизированное выполнение.

*   **Выделенный Control Node:** Существует один "секретный" сервер, который выступает в роли Ansible Control Node.
    *   Доступ к этому серверу строго ограничен для узкого круга администраторов.
    *   Только с этого сервера есть беcпарольный доступ по SSH-ключам ко всем управляемым серверам клиентов.

*   **Интеграция с GitLab CI:**
    *   **Триггер:** Процесс настройки запускается автоматически, когда администратор вносит изменения (делает `git push`) в репозиторий с инвентарем конкретного проекта.
    *   **GitLab Runner:** На "секретном" сервере установлен GitLab Runner, который и выполняет задания из CI/CD пайплайна.

*   **Цепочка выполнения и безопасность:** Чтобы предотвратить утечку SSH-ключей, используется многоуровневая система запуска:
    1.  **GitLab Runner** не запускает `ansible-playbook` напрямую.
    2.  Вместо этого он запускает **специальный wrapper-скрипт**.
    3.  Права на запуск этого скрипта предоставляются пользователю GitLab Runner через `sudo` с жестким ограничением: **разрешен запуск только этого единственного скрипта и ничего более**.
        ```sudoers
        gitlab-runner ALL=(ALL) NOPASSWD: /usr/local/bin/ansible_runner_script.sh
        ```
    4.  Таким образом, даже если злоумышленник получит контроль над окружением GitLab Runner, он не сможет прочитать SSH-ключи или выполнить произвольные команды на "секретном" сервере.

*   **Логирование и уведомления:**
    *   Весь вывод `ansible-playbook` (логи) перенаправляется в вывод задания GitLab CI, где его могут просматривать администраторы.
    *   Wrapper-скрипт дополнительно анализирует эти логи на наличие слова `Failed`.
    *   Если найдены неудавшиеся задачи, скрипт автоматически создает задачу в системе CRM (или любой другой системе трекинга), чтобы уведомить ответственного администратора о проблеме.

*   **Гибкость для администраторов:**
    *   Файл `.gitlab-ci.yml` находится в репозитории инвентаря каждого проекта и доступен для редактирования администраторам.
    *   Это позволяет им гибко настраивать процесс запуска: включать или отключать автоматический запуск, применять плейбук ко всем хостам или только к определенной группе (`--limit`).
