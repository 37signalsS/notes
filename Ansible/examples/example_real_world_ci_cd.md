# Архитектура Ansible для безопасного CI/CD в мультипроектной среде

## Определения

**Безопасная архитектура Ansible для CI/CD** — это подход к организации кода и процессов, который позволяет автоматизировать управление конфигурацией множества независимых проектов, обеспечивая при этом строгую изоляцию секретов (SSH-ключей) и разделение между логикой автоматизации (ролями) и конфигурацией конкретных окружений (инвентарем).

## Основные концепции

-   **Разделение кода и конфигурации**: Это фундаментальный принцип.
    -   **Код (Логика)**: Общая логика автоматизации (например, как установить Nginx, как настроить пользователя) выносится в централизованный репозиторий с общей Ansible-ролью (`CORE`). Это "КАК" мы делаем.
    -   **Конфигурация (Данные)**: Параметры для каждого конкретного проекта (список серверов, переменные, версии пакетов) хранятся в отдельных, изолированных Git-репозиториях. Это "ЧТО" мы настраиваем.

-   **Выделенный Control Node**: Существует единственный, хорошо защищенный сервер, который выступает в роли Ansible Control Node. Только у этого сервера есть SSH-доступ ко всей управляемой инфраструктуре. Доступ к самому Control Node строго ограничен.

-   **Безопасность через делегирование (Wrapper Script)**: Чтобы защитить SSH-ключи на Control Node от окружения CI/CD (например, GitLab Runner), прямой вызов `ansible-playbook` запрещается. Вместо этого используется скрипт-обертка с ограниченными правами `sudo`. GitLab Runner может запустить только этот скрипт и ничего более, что предотвращает утечку ключей и выполнение произвольных команд.

## Практические сценарии

### Сценарий: Построение безопасного CI/CD пайплайна

#### Часть 1: Структура репозиториев

1.  **Центральный репозиторий с общей ролью (`ansible-core-role`)**
    - Содержит одну большую роль (`CORE`), которая умеет настраивать все необходимые компоненты (веб-серверы, базы данных, пользователей и т.д.).
    ```
    ansible-core-role/
    └── roles/
        └── CORE/
            ├── tasks/
            │   ├── main.yml
            │   ├── nginx.yml
            │   └── postgres.yml
            └── templates/
    ```

2.  **Репозиторий для каждого проекта (`project-A-inventory`)**
    - Содержит только данные, специфичные для проекта A.
    ```
    project-A-inventory/
    ├── group_vars/
    │   └── all.yml
    ├── host_vars/
    │   └── server1.yml
    ├── inventory.ini
    └── .gitlab-ci.yml  # Пайплайн для этого проекта
    ```

3.  **Для сложных стеков (`kubespray`, `ceph-ansible`)**
    - Для каждого развертываемого кластера создается отдельный **форк** основного репозитория (`kubespray`). Вся конфигурация (инвентарь, переменные) хранится непосредственно в этом форке, что гарантирует полную изоляцию и версионируемость конфигурации кластера.

#### Часть 2: Архитектура выполнения CI/CD

Процесс запускается автоматически при `git push` в репозиторий инвентаря проекта.

**Цепочка выполнения:**

1.  **`git push`** в `project-A-inventory`.
2.  **GitLab CI** триггерит пайплайн, описанный в `.gitlab-ci.yml`.
3.  **GitLab Runner**, установленный на выделенном Control Node, получает задачу.
4.  Runner **не вызывает `ansible-playbook` напрямую**. Вместо этого он выполняет команду:
    ```bash
    sudo /usr/local/bin/ansible_runner_script.sh
    ```
5.  **Скрипт-обертка (`ansible_runner_script.sh`)** под правами суперпользователя (у которого есть доступ к SSH-ключам) выполняет `ansible-playbook`, передавая ему путь к инвентарю и другие параметры.
6.  Скрипт анализирует лог выполнения. При нахождении ошибок (`Failed`), он создает задачу в системе трекинга (например, Jira/CRM) через API.

**Настройка безопасности (`/etc/sudoers.d/gitlab-runner`):**

Ключевой элемент безопасности — это жесткое ограничение прав для пользователя `gitlab-runner`. Ему разрешено выполнять без пароля только один конкретный скрипт.

```sudoers
# Предоставляем пользователю gitlab-runner право выполнять
# ТОЛЬКО /usr/local/bin/ansible_runner_script.sh от имени любого пользователя
gitlab-runner ALL=(ALL) NOPASSWD: /usr/local/bin/ansible_runner_script.sh
```

#### Часть 3: Пример `.gitlab-ci.yml`

Этот файл находится в репозитории инвентаря (`project-A-inventory`) и позволяет администраторам проекта гибко управлять запуском.

```yaml
stages:
  - deploy

apply-configuration:
  stage: deploy
  script:
    # Запускаем обертку через sudo
    - sudo /usr/local/bin/ansible_runner_script.sh --playbook site.yml --inventory ./inventory.ini --limit ${ANSIBLE_LIMIT:-all}
  rules:
    # Запускать только для main ветки
    - if: '$CI_COMMIT_BRANCH == "main"'
  variables:
    # Администратор может переопределить эту переменную в GitLab
    # для запуска на конкретной группе хостов
    ANSIBLE_LIMIT: "all" 
```

## Дополнительная информация

### Преимущества и недостатки

| Преимущество | Недостаток |
| :--- | :--- |
| **Высокая безопасность**: SSH-ключи надежно изолированы от среды CI/CD. | **Повышенная сложность**: Требуется поддержка дополнительного скрипта-обертки. |
| **Четкое разделение ответственности**: Разработчики ролей и администраторы проектов работают с разными репозиториями. | **Сложнее в onboarding'е**: Новым членам команды нужно понять всю архитектуру, а не только стандартный Ansible. |
| **Масштабируемость**: Легко добавлять новые проекты, не затрагивая основную логику. | |
| **Аудит и автоматизация**: Полный контроль версий и автоматическое создание задач при сбоях. | |
