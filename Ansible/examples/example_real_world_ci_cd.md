# Архитектура Ansible для безопасного CI/CD в мультипроектной среде

## Определения

- **Безопасная архитектура Ansible для CI/CD** — комплексный подход к автоматизации управления конфигурацией, обеспечивающий строгую изоляцию секретов и разделение логики автоматизации от данных конкретных окружений.
- **Wrapper Script (скрипт-обертка)** — сценарий с жестко ограниченными правами доступа (через `sudo`), выступающий единственным шлюзом для запуска `ansible-playbook` из недоверенных сред (например, CI/CD-агентов).
- **Control Node (контрольный узел)** — выделенный защищенный сервер, являющийся единственной точкой входа в управляемую инфраструктуру по протоколу SSH (Secure Shell).

## Базовые концепции

### Разделение кода и конфигурации

Фундаментальный принцип организации масштабируемой автоматизации:

- **Код (Логика)**: Общая логика («КАК» выполнять настройку) инкапсулируется в централизованном репозитории с общими **[Ansible-ролями](../ansible_roles.md)**.
- **Конфигурация (Данные)**: Специфичные параметры («ЧТО» именно настраивать: список серверов, версии, **[переменные](../PlaybookStructure/variables.md)**) хранятся в изолированных репозиториях для каждого проекта.

### Безопасность через делегирование

Для защиты критически важных SSH-ключей на контрольном узле от компрометации через среду CI/CD (например, GitLab Runner) применяется механизм делегирования:

1. Прямой запуск `ansible-playbook` пользователю GitLab Runner запрещен.
2. GitLab Runner имеет право запускать только скрипт-обертку через `sudo`.
3. Скрипт-обертка выполняет валидацию входных параметров и запускает Ansible от имени пользователя, обладающего правами доступа к инфраструктуре.

Подробные рекомендации по ограничению прав доступа приведены в разделе **[Рекомендации по безопасности в Ansible](../ansible_security_best_practices.md)**. Общая концепция управления секретами в пайплайнах описана в разделе **[Управление секретами в CI/CD](../../CI-CD/DevSecOps/secrets_management.md)**.

## Практические сценарии

### Сценарий: Реализация безопасного пайплайна в GitLab CI

#### 1. Структура репозиториев

Для эффективного разделения ответственности используются два типа репозиториев:

**Центральный репозиторий ролей (`ansible-roles-repo`):**

```text
ansible-roles-repo/
└── roles/
    ├── nginx/
    ├── postgres/
    └── common/
```

**Репозиторий проекта (`project-A-inventory`):**

```text
project-A-inventory/
├── group_vars/
├── host_vars/
├── inventory.ini
├── site.yml
└── .gitlab-ci.yml
```

#### 2. Процесс выполнения деплоя

1. Разработчик вносит изменения в репозиторий проекта.
2. GitLab CI инициирует выполнение пайплайна.
3. GitLab Runner, установленный на контрольном узле, клонирует необходимые репозитории.
4. Runner вызывает скрипт-обертку:

   ```bash
   sudo /usr/local/bin/ansible_runner_script.sh --playbook site.yml --inventory ./inventory.ini --limit ${ANSIBLE_LIMIT:-all}
   ```

5. Скрипт выполняет **[запуск плейбука](../ansible_playbook_execution.md)** и возвращает результат в CI/CD систему.

#### 3. Пример скрипта-обертки (`ansible_runner_script.sh`)

Скрипт должен находиться в защищенной директории (например, `/usr/local/bin/`) с правами доступа `0755` (владелец `root`).

```bash
#!/bin/bash
# Путь к директории с общими ролями
ROLES_PATH="/opt/ansible/shared-roles"

# Сборка аргументов для запуска
ANSIBLE_ARGS="$@"
LOG_FILE="/var/log/ansible/runs/ansible-$(date +%F-%H%M%S).log"

# Выполнение плейбука
ansible-playbook --roles-path "$ROLES_PATH" $ANSIBLE_ARGS | tee "$LOG_FILE"

# Обработка результата
if [ ${PIPESTATUS[0]} -ne 0 ]; then
    echo "Ошибка выполнения плейбука. Проверьте лог: $LOG_FILE"
    exit 1
fi
```

#### 4. Настройка разрешений (`/etc/sudoers.d/gitlab-runner`)

```text
# Разрешить пользователю gitlab-runner запуск только одного скрипта без пароля
gitlab-runner ALL=(ALL) NOPASSWD: /usr/local/bin/ansible_runner_script.sh
```
