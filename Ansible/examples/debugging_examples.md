# Ansible: Примеры отладки типовых проблем

## Определения

**Отладка в Ansible** — процесс систематического поиска, анализа и устранения ошибок в плейбуках, ролях, инвентаре и конфигурации. Ошибки делятся на три категории:

- **Синтаксические** — неверный YAML, опечатки в именах модулей или переменных
- **Логические** — неправильный порядок задач, некорректные данные в переменных
- **Окружение** — проблемы с SSH-соединениями, правами доступа, зависимостями

## Базовые концепции

### Подход к отладке

Эффективная отладка начинается с внимательного чтения сообщений об ошибках Ansible. Общий подход:

1. **Изоляция проблемы** — запуск с `--limit <hostname>` для одного хоста, использование `--start-at-task` для начала с конкретной задачи
2. **Увеличение детализации** — флаги `-v`, `-vv`, `-vvv` для получения информации о переменных и SSH-параметрах
3. **Сухой прогон** — `--check` показывает планируемые изменения, `--diff` отображает изменения в файлах
4. **Проверка логики** — порядок задач, зависимости, права доступа

Инструменты отладки (`--check`, `--diff`, `--step`, `debugger`, модуль `debug`) подробно описаны в [PlaybookStructure/advanced.md](../PlaybookStructure/advanced.md#сценарий-3-отладка-плейбуков).

## Практические сценарии

### Сценарий 1: Ошибка синтаксиса в файле переменных

**Симптом:** Плейбук падает с `Syntax Error while loading YAML`, указывая на строку с переменной.

**Причина:** Jinja2-выражения (`{{ ... }}`) в YAML-файлах **обязательно** заключать в кавычки. Без них YAML-парсер не может обработать строку.

**Неправильно:**
```yaml
my_variable: {{ some_other_variable }}
```

**Решение:**
```yaml
my_variable: "{{ some_other_variable }}"
```

---

### Сценарий 2: Неправильный хост для подключения

**Симптом:** Ansible подключается по DNS-имени, игнорируя `ansible_host` из инвентаря.

**Причина:** В `host_vars/<hostname>.yml` переменная `ansible_host` переопределена пустым значением (`ansible_host:`). Переменные из `host_vars/` имеют приоритет над инвентарем.

**Решение:** Удалить файл из `host_vars/` или исправить значение `ansible_host`.

---

### Сценарий 3: Ошибка проверки ключа хоста при использовании Jump-хоста

**Симптом:** `Host key verification failed` при подключении через jump-хост. Прямое SSH (`ssh -J ...`) работает.

**Причина:** `host_key_checking = false` в `ansible.cfg` не влияет на дочерний SSH-процесс для `ProxyCommand`. Он использует системные настройки и проверяет `~/.ssh/known_hosts`.

**Решение:**
```ini
[ssh_connection]
ssh_args = -o ControlMaster=auto -o ControlPersist=60s -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null
```

---

### Сценарий 4: Ошибка типов (`can only join list, not NoneType`)

**Симптом:** `Unexpected Templating Type Error... can only join list, not NoneType`.

**Причина:** Операция (`union`, `join`) получила `None` вместо списка. Происходит при комментировании всех элементов списка:

**Неправильно (создает `None`):**
```yaml
my_list:
# - item1
# - item2
```

**Решение:** Явно указать пустой список:
```yaml
my_list: []
```

---

### Сценарий 5: Ошибка валидации из-за авто-преобразования YAML

**Симптом:** Задача с `validate` падает: сгенерированный конфиг содержит `PermitRootLogin True` вместо `yes`.

**Причина:** YAML-парсер преобразует `yes`, `no`, `on`, `off` в булевы типы (`True`/`False`).

**Решения:**

1. **Быстрый фикс (в переменных):**
   ```yaml
   sshd_permit_root_login: "yes"
   ```

2. **Надежный фикс (в шаблоне):**
   ```jinja
   PermitRootLogin {% if sshd_permit_root_login %}yes{% else %}no{% endif %}
   ```

### Сценарий 6: Логическая ошибка в данных конфигурации

**Симптом:** Плейбук отработал успешно, но приложение не работает.

**Причина:** Ошибка в **данных** (`group_vars`, `host_vars`), а не в логике плейбука. Например, при копировании инвентаря из другого проекта не изменены IP-адреса.

**Решение:**

1. Тщательно проверять данные при переносе конфигураций между окружениями
2. Внедрять **тесты на верификацию** (например, `verify.yml` в Molecule), проверяющие работоспособность сервиса (`curl`, подключение к БД), а не только факт запуска

---

### Сценарий 7: Опечатка в IP-адресе

**Симптом:** Плейбук падает на одном хосте с `unreachable`.

**Причина:** Опечатка в IP-адресе в инвентаре.

**Решение:** Исправить IP-адрес и запустить плейбук заново.

---

### Сценарий 8: Миграция с root на выделенного пользователя

**Симптом:** После отключения `PermitRootLogin` плейбук падает с `UNREACHABLE`.

**Причина:** Ansible продолжает подключаться как `root`, но SSH-доступ для root запрещен.

**Решение:**

1. Указать пользователя в инвентаре:
   ```ini
   [production]
   server1 ansible_host=IP ansible_user=ansible_user
   ```

2. Или в `ansible.cfg`:
   ```ini
   [defaults]
   remote_user = ansible_user
   ```

3. Добавить `become: true` для задач, требующих привилегий:
   ```yaml
   - name: Update apt cache
     ansible.builtin.apt:
       update_cache: yes
     become: true
   ```

Подробное руководство по миграции — в [user_migration_debugging.md](user_migration_debugging.md).
