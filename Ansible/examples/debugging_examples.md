# Ansible: Примеры отладки типовых проблем

## Определения

**Отладка в Ansible** — процесс систематического поиска, анализа и устранения ошибок в плейбуках, ролях, инвентаре и конфигурации. Ошибки делятся на три категории:

- **Синтаксические** — неверный YAML (YAML Ain't Markup Language), опечатки в именах модулей или переменных.
- **Логические** — неправильный порядок задач, некорректные данные в переменных.
- **Окружение** — проблемы с SSH (Secure Shell) соединениями, правами доступа, зависимостями.

## Базовые концепции

### Подход к отладке

Эффективная отладка начинается с анализа сообщений об ошибках. Общий алгоритм:

1. **Изоляция проблемы**: запуск с флагом `--limit <hostname>` для одного хоста или использование `--start-at-task` для начала с конкретной задачи.
2. **Увеличение детализации**: использование флагов `-v`, `-vv`, `-vvv` для получения подробной информации о значениях переменных и параметрах подключения.
3. **Безопасная проверка**:
   - `--check` — «сухой прогон» (dry run) без внесения изменений.
   - `--diff` — отображение различий в изменяемых файлах.
4. **Интерактивная отладка**: использование пошагового выполнения (`--step`) или встроенного отладчика (`debugger`).

Инструменты отладки подробно описаны в разделе **[Отладка плейбуков](../PlaybookStructure/advanced.md#сценарий-3-отладка-плейбуков)**.

## Практические сценарии

### Сценарий 1: Ошибка синтаксиса YAML (кавычки в переменных)

**Симптом:** выполнение плейбука прерывается ошибкой `Syntax Error while loading YAML`, указывающей на строку с переменной.

**Причина:** выражения Jinja2 (`{{ ... }}`) в YAML-файлах должны быть обязательно заключены в кавычки, если они стоят в начале значения. Без кавычек парсер воспринимает фигурные скобки как начало словаря.

**Неправильно:**

```yaml
my_variable: {{ some_other_variable }}
```

**Решение:**

```yaml
my_variable: "{{ some_other_variable }}"
```

### Сценарий 2: Игнорирование параметров инвентаря

**Симптом:** Ansible пытается подключиться по DNS (Domain Name System) имени, игнорируя параметр `ansible_host` из инвентаря.

**Причина:** переменная `ansible_host` переопределена в файле `host_vars/<hostname>.yml` (например, оставлена пустой). Переменные из `host_vars/` имеют приоритет над параметрами, указанными непосредственно в файле инвентаря.

**Решение:** проверить и исправить значение в `host_vars/` или удалить файл, если он не используется.

### Сценарий 3: Ошибка проверки ключа хоста через Jump-хост

**Симптом:** ошибка `Host key verification failed` при использовании промежуточного сервера (Jump-host), хотя прямое SSH-подключение работает.

**Причина:** параметр `host_key_checking = false` в `ansible.cfg` не всегда распространяется на дочерние процессы SSH при использовании `ProxyCommand`.

**Решение:** явно отключить проверку ключей в параметрах SSH:

```ini
[ssh_connection]
ssh_args = -o ControlMaster=auto -o ControlPersist=60s -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null
```

### Сценарий 4: Ошибка типов (NoneType в списках)

**Симптом:** ошибка `can only join list, not NoneType`.

**Причина:** операция (например, `union` или `join`) получила пустое значение (`None`) вместо списка. Часто возникает при комментировании всех элементов списка в YAML.

**Неправильно (создает None):**

```yaml
my_list:
# - item1
# - item2
```

**Решение:** явно инициализировать пустой список:

```yaml
my_list: []
```

### Сценарий 5: Автоматическое преобразование типов YAML

**Симптом:** задача с `validate` падает, так как в конфиг записалось `PermitRootLogin True` вместо ожидаемого `yes`.

**Причина:** YAML-парсер автоматически преобразует слова `yes`, `no`, `on`, `off`, `true`, `false` в булевы значения.

**Решение:** заключать строковые значения в кавычки или использовать явную логику в шаблоне:

```yaml
# В переменных
sshd_permit_root_login: "yes"

# В шаблоне Jinja2
PermitRootLogin {{ sshd_permit_root_login | ternary('yes', 'no') }}
```

### Сценарий 6: Опечатка в IP-адресе или DNS

**Симптом:** один из хостов возвращает ошибку `UNREACHABLE`.

**Причина:** опечатка в IP (Internet Protocol) адресе в инвентаре или некорректная запись в файле `/etc/hosts`.

**Решение:** проверить доступность хоста вручную командой `ping` или `ssh`, затем исправить данные в инвентаре.

### Сценарий 7: Проблемы при миграции с пользователя root

**Симптом:** после отключения удаленного доступа для `root` плейбук падает с ошибкой подключения.

**Причина:** Ansible по умолчанию пытается подключиться как `root`, если не указан другой пользователь.

**Решение:**

1. Указать пользователя в `ansible.cfg` (`remote_user`) или в инвентаре (`ansible_user`).
2. Использовать механизм `become: true` для задач, требующих привилегий суперпользователя.

Подробный разбор процесса миграции представлен в руководстве **[Отладка миграции на выделенного пользователя](user_migration_debugging.md)**.
