# Примеры отладки типовых проблем в Ansible

## Определения

**Отладка в Ansible** — систематический процесс идентификации и устранения неисправностей в коде автоматизации (плейбуки, роли), конфигурации инвентаря или сетевом взаимодействии.

**Основные категории ошибок:**
- **Синтаксические:** нарушение структуры YAML (YAML Ain't Markup Language) или правил Jinja2.
- **Логические:** ошибки в условиях `when`, неправильное использование фильтров или неверный порядок выполнения задач.
- **Инфраструктурные:** проблемы SSH (Secure Shell) соединения, отсутствие Python-зависимостей на целевых хостах или ошибки прав доступа (sudo/become).
- **Среда исполнения:** несоответствие версий коллекций или ядра Ansible.

**SSoT-примечание:** подробное описание инструментов отладки (флаги CLI, модуль `debug`) находится в основном разделе **[Отладка плейбуков](../PlaybookStructure/advanced.md#сценарий-3-отладка-плейбуков)**. Данный файл содержит практические сценарии и "работу над ошибками".

## Базовые концепции

### Инструменты диагностики

| Инструмент / Метод | Описание | Команда / Параметр |
|---|---|---|
| **Уровни детализации** | Вывод отладочной информации модулей и SSH. | `-v`, `-vv`, `-vvv`, `-vvvv` |
| **Переменные окружения** | Глобальное включение отладки или смена вывода. | `ANSIBLE_DEBUG=1`, `ANSIBLE_STDOUT_CALLBACK=debug` |
| **Статический анализ** | Проверка синтаксиса и антипаттернов без запуска. | `ansible-lint`, `ansible-playbook --syntax-check` |
| **Интерактивный отладчик** | Остановка выполнения при ошибке для инспекции. | `debugger: on_failed` (внутри задачи) |
| **Модуль debug** | Вывод значений переменных в процессе выполнения. | `ansible.builtin.debug: var=my_var` |

### Алгоритм изоляции проблемы

1.  **Сужение области поиска**: используйте `--limit <hostname>` для запуска на одном хосте.
2.  **Пошаговое выполнение**: флаг `--step` позволяет подтверждать каждую задачу вручную.
3.  **Проверка изменений**: `--check` (dry run) в сочетании с `--diff` показывает, какие именно строки в файлах были бы изменены.
4.  **Запуск с определенной задачи**: `--start-at-task="Name"` экономит время при отладке длинных плейбуков.

## Практические сценарии

### Сценарий 1: Ошибка синтаксиса YAML (кавычки в выражениях Jinja2)

**Симптом:** выполнение плейбука прерывается ошибкой `Syntax Error while loading YAML`, указывающей на строку с переменной.
**Причина:** в YAML значения, начинающиеся с `{{`, должны быть заключены в кавычки. Без них парсер воспринимает фигурные скобки как начало словаря.
**Решение:**
- Неправильно: `my_var: {{ other_var }}`
- Правильно: `my_var: "{{ other_var }}"`

### Сценарий 2: Конфликт приоритетов переменных инвентаря

**Симптом:** Ansible пытается подключиться по DNS-имени, игнорируя `ansible_host` из инвентаря.
**Причина:** переменная `ansible_host` переопределена в `host_vars/` или `group_vars/`. Файлы в этих директориях имеют более высокий приоритет, чем описание в `hosts.ini`.
**Решение:** проверьте иерархию переменных. Используйте `ansible-inventory --host <hostname>` для просмотра финальных значений, примененных к хосту.

### Сценарий 3: Ошибка SSH через промежуточный хост (Jump Host)

**Симптом:** ошибка `Host key verification failed` при использовании `ProxyCommand` или `ProxyJump`.
**Причина:** старый метод `ProxyCommand` не всегда корректно пробрасывает параметры проверки ключей.
**Решение:** используйте современный `ProxyJump` в `ansible.cfg` или конфигурации SSH.

```ini
[ssh_connection]
# Современный подход через ProxyJump
ssh_args = -o ProxyJump=user@jump-host:22 -o StrictHostKeyChecking=no
```

### Сценарий 4: Ошибка типов данных (NoneType)

**Симптом:** ошибка `can only join list, not NoneType` при использовании фильтров `join` или `union`.
**Причина:** переменная была определена, но не инициализирована (пустое значение в YAML интерпретируется как `None`).
**Решение:** явно инициализируйте пустые списки или используйте фильтр `default`.

```yaml
# Инициализация
my_list: []

# Безопасное использование
result: "{{ my_var | default([]) | union(other_var) }}"
```

### Сценарий 5: Автоматическое преобразование типов (Булевы значения)

**Симптом:** в конфигурационный файл записывается `True` вместо `yes`, что вызывает ошибку валидации сервиса.
**Причина:** YAML-парсер автоматически преобразует `yes`, `no`, `true`, `false` в булевы объекты.
**Решение:** заключайте строковые значения в кавычки или используйте явные фильтры.

```yaml
sshd_permit_root_login: "yes" # Строка останется строкой
```

### Сценарий 6: Проблемы сетевой связности (UNREACHABLE)

**Симптом:** один из хостов возвращает ошибку `UNREACHABLE`.
**Причина:** опечатка в IP-адресе, закрытый порт 22 или блокировка на уровне Firewall.
**Решение:**
```bash
ansible all -m ping --limit <hostname> # → проверка через модуль ping
ssh -v <hostname> # → отладка SSH-рукопожатия вручную
```

### Сценарий 7: Проблемы при миграции с пользователя root

**Симптом:** после отключения удаленного доступа для `root` плейбук падает с ошибкой подключения.
**Причина:** Ansible по умолчанию пытается подключиться как `root`, если не указан другой пользователь.
**Решение:**
1.  Указать пользователя в `ansible.cfg` (`remote_user`) или в инвентаре (`ansible_user`).
2.  Использовать механизм `become: true` для задач, требующих привилегий.

Подробный разбор процесса миграции представлен в руководстве **[Отладка миграции на выделенного пользователя](user_migration_debugging.md)**.
