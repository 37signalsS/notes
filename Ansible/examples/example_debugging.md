# Ansible: Отладка и решение типовых проблем

## Определения

**Отладка в Ansible** — это процесс систематического поиска, анализа и устранения ошибок в плейбуках, ролях, инвентаре и конфигурации. Ошибки могут быть синтаксическими (неверный YAML), логическими (неправильные данные или порядок задач) или связанными с окружением (проблемы с SSH-соединениями, правами доступа).

## Базовые концепции

### Общий подход к отладке

Эффективная отладка — это в первую очередь внимательное чтение сообщений об ошибках, которые предоставляет Ansible. Следующие шаги помогут локализовать почти любую проблему:

1.  **Изолируйте проблему:**
    *   Запускайте плейбук с ограничением до одного хоста, на котором проявляется ошибка: `ansible-playbook ... --limit <hostname>`.
    *   Используйте `--start-at-task "имя задачи"` для начала выполнения с определенного места.
    *   Комментируйте части плейбука, чтобы найти конкретную задачу, вызывающую сбой.

2.  **Увеличьте детализацию:**
    *   Используйте флаги `-v`, `-vv` или `-vvv`, чтобы получить максимум информации о значениях переменных и параметрах SSH-соединений.

3.  **Выполняйте "сухой прогон":**
    *   Флаг `--check` покажет, какие изменения Ansible *собирается* внести, но не выполнит их.
    *   Флаг `--diff` (`-D`) покажет точные изменения в содержимом файлов.

4.  **Проверяйте логику:**
    *   Опечатки в именах модулей, переменных, путях.
    *   Неправильный порядок задач (например, попытка настроить сервис до его установки).
    *   Отсутствие необходимых зависимостей на целевом хосте.
    *   Проблемы с правами доступа.

### Ключевые инструменты

Ansible предоставляет набор встроенных инструментов для отладки. Подробное описание каждого из них можно найти в файле **[Структура плейбуков](../ansible_playbook_structure.md#отладка-плейбуков)**.

*   **Флаги командной строки:** `--syntax-check`, `--check`, `--diff`, `--limit`, `--start-at-task`, `-v[vv]`.
*   **Интерактивные инструменты:** `--step` (пошаговое выполнение) и ключевое слово `debugger` для вызова отладчика.
*   **Модуль `debug`:** Позволяет выводить значения переменных или произвольные сообщения прямо во время выполнения плея.

## Практические сценарии

Ниже приведены примеры распространенных ошибок и методы их решения.

### Сценарий 1: Ошибка синтаксиса в файле переменных

*   **Симптом:** Плейбук падает с ошибкой синтаксиса (например, `Syntax Error while loading YAML.`), указывая на строку, где используется переменная. Ansible может намекать на отсутствующие кавычки.
*   **Причина:** При использовании Jinja2-выражений (`{{ ... }}`) в качестве значения для переменной в YAML-файле, все выражение **необходимо** заключать в кавычки. Без них YAML-парсер не может корректно обработать строку.
*   **Неправильно:**
    ```yaml
    my_variable: {{ some_other_variable }}
    ```
*   **Решение:** Добавить кавычки вокруг значения переменной.
    ```yaml
    my_variable: "{{ some_other_variable }}"
    ```

### Сценарий 2: Неправильный хост для подключения

*   **Симптом:** Ansible пытается подключиться к хосту по его DNS-имени, игнорируя IP-адрес, указанный через `ansible_host` в инвентаре.
*   **Причина:** В файле из `host_vars/` для данного хоста была переопределена переменная `ansible_host` и ей было присвоено пустое значение (`ansible_host:`). Переменные из `host_vars/` имеют более высокий приоритет, чем переменные, указанные в строке инвентаря, поэтому пустое значение затерло правильное.
*   **Решение:** Удалить некорректный файл из `host_vars/` или исправить в нем значение переменной `ansible_host`.

### Сценарий 3: Ошибка проверки ключа хоста при использовании Jump-хоста

*   **Симптом:** Ansible не может подключиться к хостам через jump-хост с ошибкой `Host key verification failed`. При этом прямое SSH-подключение (`ssh -J ...`) работает.
*   **Причина:** Настройки `host_key_checking = false` в `ansible.cfg` не влияют на дочерний процесс `ssh`, который запускается для `ProxyCommand`. Этот процесс использует системные настройки SSH и проверяет ключи в `~/.ssh/known_hosts`.
*   **Решение:** Добавить опции для отключения проверки ключей непосредственно в `ansible.cfg`.
    ```ini
    [ssh_connection]
    ssh_args = -o ControlMaster=auto -o ControlPersist=60s -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null
    ```

### Сценарий 4: Ошибка типов (`can only join list, not NoneType`)

*   **Симптом:** Плейбук падает с ошибкой `Unexpected Templating Type Error... can only join list, not NoneType`.
*   **Причина:** Операция (например, `union` или `join`) пыталась обработать переменную, ожидая список, но получила `None`. Часто это происходит, если в файле переменных закомментировать все элементы списка, оставив только ключ.
*   **Неправильно (создает `None`):**
    ```yaml
    my_list:
    # - item1
    # - item2
    ```
*   **Решение:** Если нужен пустой список, его нужно определить явно с помощью `[]`.
    ```yaml
    my_list: []
    ```

### Сценарий 5: Ошибка валидации из-за авто-преобразования YAML

*   **Симптом:** Задача с `validate` падает, т.к. сгенерированный конфиг содержит недопустимое значение, например, `PermitRootLogin True` вместо `yes`.
*   **Причина:** YAML-парсер автоматически преобразует строковые значения `yes`, `no`, `on`, `off` в булевы типы (`True`/`False`), которые некорректно обрабатываются многими сервисами.
*   **Решения:**
    1.  **Быстрый фикс (в переменных):** Заключить значение в кавычки, чтобы оно гарантированно считалось строкой: `sshd_permit_root_login: "yes"`.
    2.  **Надежный фикс (в шаблоне):** Использовать условный оператор для явного вывода нужной строки: `PermitRootLogin {% if sshd_permit_root_login %}yes{% else %}no{% endif %}`.

### Сценарий 6: Логическая ошибка в данных конфигурации

*   **Симптом:** Плейбук успешно отработал, но приложение не работает.
*   **Причина:** Ошибка кроется не в логике плейбука, а в **данных** (`group_vars`, `host_vars`). Например, при копировании инвентаря из другого проекта забыли поменять IP-адреса. Ansible синтаксически верно сгенерировал конфиги, но с некорректными для данного окружения значениями.
*   **Решение:**
    1.  Тщательно проверять все данные при переносе конфигураций между окружениями.
    2.  Внедрять **тесты на верификацию** (например, с помощью `verify.yml` в Molecule), которые проверяют работоспособность сервиса (делают `curl`, подключаются к БД), а не просто факт его запуска.

### Сценарий 7: Простая опечатка в IP-адресе

*   **Симптом:** Плейбук падает на одном конкретном хосте с ошибкой `unreachable`.
*   **Причина:** Опечатка в IP-адресе в файле инвентаря.
*   **Решение:** Исправить IP-адрес в инвентаре и запустить плейбук заново.

## Дополнительная информация

### Ускорение выполнения с помощью Mitogen

После отладки можно заметить, что плейбук выполняется медленно. Для кардинального ускорения можно использовать плагин-стратегию `mitogen`.

*   **Решение:** Включить `mitogen` в `ansible.cfg`:
    ```ini
    [defaults]
    # ...
    strategy_plugins = /path/to/mitogen/ansible_mitogen/plugins/strategy
    strategy = mitogen_linear
    ```
    Это значительно сократит время выполнения плейбука за счет оптимизации SSH-соединений.
