# Ansible: Примеры отладки типовых ошибок

### Сценарий 1: Ошибка синтаксиса в файле переменных

*   **Симптом:** Плейбук падает с ошибкой синтаксиса в файле переменных (например, `group_vars/all/vars.yml`), указывая на строку, где используется переменная. Ansible может намекать на отсутствующие кавычки.

*   **Расследование:** Проверяем указанный в ошибке файл.
    ```yaml
    # group_vars/student04.yml
    # ...
    # Неправильно:
    my_variable: {{ some_other_variable }}
    # ...
    # Правильно, но не относится к ошибке:
    ansible_ssh_proxy_internal_address: some_value
    ```
    Ansible не ругается на вторую переменную, так как считает ее обычной строкой. Проблема возникает, когда мы пытаемся использовать синтаксис `{{...}}` без кавычек.

*   **Причина:** При использовании Jinja2-выражений (`{{ ... }}`) в качестве значения для переменной в YAML-файле, все выражение **необходимо** заключать в кавычки. Без них YAML-парсер не может корректно обработать строку.

*   **Решение:** Добавить кавычки вокруг значения переменной.
    ```yaml
    # Правильно:
    my_variable: "{{ some_other_variable }}"
    ```

### Сценарий 2: Неправильный хост для подключения

*   **Симптом:** Ansible пытается подключиться к хосту по его DNS-имени, игнорируя IP-адрес, указанный через `ansible_host` в основном файле инвентаря.

*   **Расследование:**
    1.  Запускаем `ansible-playbook` с ключом `-vvv` для просмотра деталей SSH-соединения.
    2.  В выводе видим, что команда `ssh` использует DNS-имя (`ingress1.s04.slurm.io`), а не IP-адрес.
    3.  Проверяем файл инвентаря — там для хоста `ingress1` указан `ansible_host` с правильным IP.
    4.  Вспоминаем про [приоритет переменных](../ansible_playbooks.md#где-определять-переменные-и-их-приоритет). Переменные из `host_vars/` имеют более высокий приоритет, чем переменные, указанные в строке инвентаря.
    5.  Проверяем каталог `host_vars/` и находим там файл `ingress1.s04.slurm.io.yml`.

*   **Причина:** В файле `host_vars/ingress1.s04.slurm.io.yml` была переопределена переменная `ansible_host` и ей было присвоено пустое значение.
    ```yaml
    # host_vars/ingress1.s04.slurm.io.yml
    ansible_host:
    ```
    Пустое значение `ansible_host` затерло правильное значение из инвентаря, и Ansible по умолчанию попытался подключиться по имени хоста.

*   **Решение:** Удалить некорректный файл из `host_vars/` или исправить в нем значение переменной.

### Сценарий 3: Ошибка проверки ключа хоста при использовании Jump-хоста

*   **Симптом:** Ansible не может подключиться к хостам, находящимся во внутренней сети, через jump-хост (bastion). При этом прямое SSH-подключение через тот же jump-хост (`ssh -J ...`) работает. Ошибка может выглядеть как `Host key verification failed`.

*   **Расследование:**
    1.  Запускаем `ansible-playbook -vvv`.
    2.  Находим и копируем полную команду `ssh`, которую генерирует Ansible.
    3.  Пытаемся выполнить ее вручную в консоли и получаем предупреждение: `REMOTE HOST IDENTIFICATION HAS CHANGED!`.

*   **Причина:** Настройки `host_key_checking = false` и `record_host_keys = false` в `ansible.cfg` относятся только к прямым SSH-соединениям, которые инициирует сам Ansible. Когда используется jump-хост через `ProxyCommand`, Ansible запускает отдельный процесс `ssh`, который использует свои собственные настройки и по-прежнему проверяет отпечатки ключей в `~/.ssh/known_hosts`. Если IP-адрес внутреннего хоста ранее принадлежал другой машине, возникает конфликт ключей.

*   **Решение:** Добавить опции для отключения проверки ключей непосредственно в команду `ProxyCommand` внутри `ansible.cfg` или в переменной `ansible_ssh_common_args`.

    **Пример для `ansible.cfg`:**
    ```ini
    [ssh_connection]
    ssh_args = -o ControlMaster=auto -o ControlPersist=60s -o StrictHostKeyChecking=no -o UserKnownHostsFile=/dev/null
    ```
    Или добавить эти опции в строку `ProxyCommand`, если она формируется динамически через переменные.

### Сценарий 4: Опечатка в IP-адресе

*   **Симптом:** Плейбук успешно выполняется на части хостов, но падает на одном конкретном с ошибкой `unreachable`.

*   **Расследование:** Проверяем IP-адрес проблемного хоста (`master1`) в файле инвентаря.

*   **Причина:** Простая опечатка в IP-адресе в файле инвентаря.

*   **Решение:** Исправить IP-адрес в инвентаре и запустить плейбук заново.

### Ускорение выполнения с помощью Mitogen

После отладки всех ошибок можно заметить, что плейбук выполняется медленно. Для кардинального ускорения можно использовать плагин-стратегию `mitogen`.

*   **Решение:** Включить `mitogen` в `ansible.cfg`:
    ```ini
    [defaults]
    # ...
    strategy_plugins = /path/to/mitogen/ansible_mitogen/plugins/strategy
    strategy = mitogen_linear
    ```
    Это значительно сократит время выполнения плейбука за счет оптимизации SSH-соединений.

### Сценарий 5: Ошибка типов (`can only join list, not NoneType`)

*   **Симптом:** Плейбук падает с ошибкой `Unexpected Templating Type Error... can only join list, not NoneType`. Это означает, что операция (например, `union` или `join`) пыталась обработать переменную, ожидая, что это будет список, но вместо этого получила "ничего" (`None`).

*   **Расследование:**
    1.  Находим в коде плейбука или роли место, где используется проблемная переменная (в примере `Base YAM Exclude`).
    2.  Проверяем, где эта переменная определяется, например, в `group_vars/`.
    3.  Обнаруживаем, что переменная, которая должна была быть списком, полностью закомментирована или отсутствует.

*   **Причина:** Если в файле переменных закомментировать все элементы списка, сама переменная не становится пустым списком, а определяется как `None` (отсутствие значения).
    ```yaml
    # Неправильно! Это создаст 'None', а не пустой список.
    base_yum_exclude:
    # - pkg1
    # - pkg2
    ```
*   **Решение:** Если вам нужен пустой список, его нужно определить явно с помощью `[]`.
    ```yaml
    # Правильно:
    base_yum_exclude: []
    ```
    Теперь тип переменной будет `list`, и операции с ней будут выполняться корректно.

### Сценарий 6: Ошибка валидации из-за авто-преобразования YAML

*   **Симптом:** Задача, использующая модуль `template` с опцией `validate`, падает. В сообщении об ошибке говорится, что сгенерированный конфигурационный файл содержит недопустимую опцию, например, `unsupported options true`.

*   **Расследование:**
    1.  Изучаем задачу. Опция `validate: sshd -t -f %s` означает, что после генерации конфига из шаблона Ansible пытается проверить его синтаксис, запустив `sshd` в тестовом режиме. Ошибка говорит, что сам `sshd` не принимает сгенерированный конфиг.
    2.  Смотрим на переменную, которая используется в шаблоне (в примере `sshd_permit_root_login` со значением `yes`).
    3.  Смотрим на шаблон (`sshd_config.j2`) и видим строку `PermitRootLogin {{ sshd_permit_root_login }}`.

*   **Причина:** "Умный" YAML-парсер Ansible/Python автоматически преобразует строковые значения `yes`, `no`, `on`, `off` в булевы типы: `True` и `False`. В результате в шаблон вместо строки `"yes"` подставляется булево значение `True`, а в итоговый конфигурационный файл записывается слово `True`. Демон `sshd` не знает такого значения и считает его ошибкой.

*   **Решения:**
    1.  **Быстрый фикс (в файле переменных):** Заключить значение в кавычки, чтобы YAML-парсер гарантированно считал его строкой.
        ```yaml
        sshd_permit_root_login: "yes"
        ```
    2.  **Правильный фикс (в шаблоне):** Сделать шаблон более интеллектуальным, используя условный оператор. Это защитит от любых булевых значений.
        ```jinja2
        PermitRootLogin {% if sshd_permit_root_login %}yes{% else %}no{% endif %}
        ```
        Этот подход является более надежным.

### Сценарий 7: Логическая ошибка в данных конфигурации

*   **Симптом:** Плейбук успешно отработал (все задачи `ok` или `changed`), но приложение не работает, сервисы не могут соединиться друг с другом.

*   **Расследование:**
    1.  Запускаем плейбук повторно в режиме проверки (`--check`) и с выводом различий (`--diff`). Убеждаемся, что Ansible считает систему настроенной.
    2.  Вручную заходим на сервер и проверяем ключевые конфигурационные файлы, которые сгенерировал Ansible (например, `/etc/hosts`, `/etc/nginx/conf.d/my_app.conf`).
    3.  Сравниваем значения в файлах с ожидаемыми.

*   **Причина:** Ошибка кроется не в логике плейбука, а в **данных**, которые ему передали. Например, при копировании инвентаря из другого проекта забыли поменять IP-адреса.
    ```yaml
    # group_vars/all/main.yml

    # Список для генерации /etc/hosts
    base_etc_hosts_records:
      # Ошибка: IP-адрес из старого кластера (172.21.0.2), а должен быть из сети 172.21.4.0
      - ip: 172.21.0.2
        host: master1.s04
    ```
    Ansible синтаксически и лексически верно обработал эти данные и сгенерировал `/etc/hosts`, где `master1.s04` указывает на неправильный IP.

*   **Решение:**
    1.  Тщательно проверять все данные (переменные в `group_vars`, `host_vars`) при переносе конфигураций между окружениями.
    2.  Внедрять **тесты на верификацию** (`verify.yml` в Molecule или отдельный плейбук), которые не просто проверяют, что сервис запущен, а пытаются выполнить осмысленные действия: сделать `curl` к другому сервису по внутреннему имени, подключиться к базе данных и т.д. Это единственный надежный способ поймать логические ошибки конфигурации.

### Сценарий 8: Отладка чужого плейбука

1.  **Запускайте плейбук и внимательно читайте ошибки.** Ansible обычно дает достаточно информации, чтобы понять, что пошло не так.
2.  **Используйте `-vvv`:** Повышенный уровень детализации может показать неожиданные значения переменных или проблемы с путями.
3.  **Изолируйте проблему:** Комментируйте таски и запускайте их по одному, чтобы локализовать источник ошибки.
4.  **Проверяйте логику:** Что может быть причиной ошибок?
    *   Опечатки в именах модулей, переменных, путях.
    *   Неправильный порядок задач (например, попытка настроить сервис до его установки).
    *   Отсутствие необходимых зависимостей на целевом хосте.
    *   Проблемы с правами доступа.
