# Автоматизация сетевого оборудования с помощью Ansible

## Определения

**Сетевой модуль (Network Module)** — специализированный модуль Ansible, который всегда выполняется на управляющем узле (Control Node), так как на подавляющем большинстве сетевых коммутаторов и маршрутизаторов нет возможности запускать Python-код.

**Управление состоянием (State Management)** — ключевое преимущество Ansible при конфигурации сети, позволяющее заменять или объединять конфигурацию портов и VLAN (Virtual Local Area Network), а не просто отправлять "сырые" команды.

## Базовые концепции

### Плагины подключения

В отличие от стандартных Linux-серверов, сетевые устройства используют специфичные плагины для связи:

- `ansible.netcommon.network_cli`: Основной способ для работы с устройствами на базе CLI (Command Line Interface) over SSH (Secure Shell) (Cisco IOS, Juniper JunOS и др.).
- `ansible.netcommon.telnet`: Применяется для устаревших устройств, поддерживающих только Telnet (например, старые коммутаторы D-Link на уровне доступа). При его использовании необходимо явно задавать ожидаемые приглашения (`login_prompt`, `password_prompt`, `prompts`), так как они могут отличаться от стандартных.

### Повышение привилегий (Privilege Escalation)

Сетевое оборудование (например, коммутаторы Cisco) часто требует перехода из пользовательского режима в привилегированный (режим `enable`) для изменения конфигурации или снятия бэкапов. В Ansible это настраивается через переменные (обычно в `group_vars`):

- `ansible_become: yes`
- `ansible_become_method: enable`
- `ansible_become_password`: Пароль для привилегированного режима (рекомендуется шифровать через Ansible Vault).

### Параметр `state` и консистентность конфигурации

При работе с модулями, управляющими конфигурацией (например, `cisco.ios.ios_vlans`, `cisco.ios.ios_l2_interfaces`), параметр `state` определяет, как именно новые настройки применяются к устройству:

- `merged`: Слияние новой конфигурации с существующей. **Наиболее безопасный вариант.** Например, при добавлении клиентского VLAN на магистральный интерфейс (uplink), старые разрешённые VLAN (включая VLAN управления) не будут удалены.
- `replaced`: Замена конфигурации только для тех интерфейсов или VLAN, которые явно указаны в задаче. Настройки остальных сущностей остаются без изменений.
- `overridden`: Полная перезапись базы или конфигурации интерфейса. **Опасный вариант:** может удалить существующие VLAN (в том числе VLAN управления) и привести к потере доступа к устройству.
- `rendered`: Информационное состояние. Модуль не подключается к устройству, а просто генерирует и показывает CLI-команду, которая была бы выполнена.
- `gathered` / `parsed`: Используются для чтения и парсинга текущей конфигурации устройства без внесения в неё изменений.

## Практические сценарии

### Отключение постраничного вывода (Pagination)

Одной из частых проблем при выполнении команд (особенно "сырых" через `netcommon.telnet`) является постраничный вывод CLI-интерфейса. Если вывод длинный, устройство ждет нажатия пробела, из-за чего Ansible "зависает".
Для предотвращения этого первой задачей в плейбуке всегда должна идти команда отключения пагинации (например, `terminal length 0` для Cisco или `disable clipaging` для D-Link).

### Итерация по интерфейсам вместо диапазонов

Сетевые модули Ansible (в отличие от ручного ввода в CLI) обычно не поддерживают настройку сразу диапазона интерфейсов (команды вроде `interface range`). Модули спроектированы для управления состоянием каждой отдельной сущности.
Для настройки множества клиентских портов необходимо использовать стандартные циклы Ansible (`loop`), передавая модулю по одному интерфейсу за раз из списка (например, определенного в переменной `lan_ports`). Это гарантирует предсказуемость и консистентность состояния каждого порта.

### Структурирование инвентаря

При автоматизации сетевого оборудования критически важно жестко разделять инвентарь по ролям и уровням (например, `cisco_core` для ядра и `cisco_access` для уровня доступа).
Это исключает риск случайного применения шаблонов уровня ядра к коммутаторам доступа (и наоборот), что может повлечь за собой серьезные сетевые аварии.
