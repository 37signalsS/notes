# Автоматизация сетевого оборудования с помощью Ansible

## Определения

- **Сетевой модуль (Network Module)** — специализированный модуль Ansible, который всегда выполняется на **контрольном узле (Control Node)**, так как на большинстве сетевых коммутаторов и маршрутизаторов нет возможности запускать Python-код.
- **Управление состоянием (State Management)** — ключевое преимущество Ansible при конфигурации сети, позволяющее заменять или объединять конфигурацию портов и **VLAN (Virtual Local Area Network)**, а не просто отправлять последовательность команд.

## Базовые концепции

### Плагины подключения

В отличие от стандартных серверов Linux, сетевые устройства используют специфичные плагины для связи:

- `ansible.netcommon.network_cli`: основной способ для работы с устройствами на базе **CLI (Command Line Interface)** через протокол **SSH (Secure Shell)** (Cisco IOS, Juniper JunOS и др.).
- `ansible.netcommon.telnet`: применяется для устаревших устройств, поддерживающих только протокол Telnet (например, старые коммутаторы D-Link на уровне доступа). При его использовании необходимо явно задавать ожидаемые приглашения (`login_prompt`, `password_prompt`, `prompts`), так как они могут отличаться от стандартных.

### Повышение привилегий

Сетевое оборудование (например, коммутаторы Cisco) часто требует перехода из пользовательского режима в привилегированный (режим `enable`) для изменения конфигурации или создания резервных копий. В Ansible это настраивается через переменные (обычно в `group_vars`):

- `ansible_become: yes`
- `ansible_become_method: enable`
- `ansible_become_password`: пароль для привилегированного режима (рекомендуется шифровать через [Ansible Vault](../Vault/basics.md)).

### Параметр state и консистентность конфигурации

При работе с модулями, управляющими конфигурацией (например, `cisco.ios.ios_vlans`, `cisco.ios.ios_l2_interfaces`), параметр `state` определяет способ применения новых настроек:

- `merged`: слияние новой конфигурации с существующей. **Наиболее безопасный вариант.** Например, при добавлении клиентского VLAN на магистральный интерфейс (uplink), старые разрешённые VLAN (включая VLAN управления) не будут удалены.
- `replaced`: замена конфигурации только для тех интерфейсов или VLAN, которые явно указаны в задаче. Настройки остальных сущностей остаются без изменений.
- `overridden`: полная перезапись базы или конфигурации интерфейса. **Опасный вариант:** может удалить существующие VLAN (в том числе VLAN управления) и привести к потере доступа к устройству.
- `rendered`: информационное состояние. Модуль не подключается к устройству, а генерирует CLI-команду для предварительного просмотра.
- `gathered` / `parsed`: используются для чтения и разбора текущей конфигурации устройства без внесения изменений.

## Практические сценарии

### Отключение постраничного вывода

Одной из частых проблем при выполнении команд является постраничный вывод (**pagination**) интерфейса командной строки. Если вывод длинный, устройство ждет нажатия пробела, что приводит к зависанию Ansible.
Для предотвращения этого первой задачей в плейбуке должна идти команда отключения пагинации (например, `terminal length 0` для Cisco или `disable clipaging` для D-Link).

### Итерация по интерфейсам

Сетевые модули Ansible обычно не поддерживают настройку диапазона интерфейсов напрямую (аналог команды `interface range`). Модули спроектированы для управления состоянием каждой отдельной сущности.
Для настройки множества клиентских портов необходимо использовать циклы Ansible (`loop`), передавая модулю по одному интерфейсу за раз. Это гарантирует предсказуемость и консистентность состояния каждого порта.

### Структурирование инвентаря

При автоматизации сетевого оборудования важно разделять инвентарь по ролям и уровням (например, `cisco_core` для ядра и `cisco_access` для уровня доступа). Это исключает риск случайного применения шаблонов уровня ядра к коммутаторам доступа, что может повлечь за собой сетевые аварии.
