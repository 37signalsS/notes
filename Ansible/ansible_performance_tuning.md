# Ansible: Оптимизация и ускорение

## Основные концепции

### 1. SSH Pipelining

По умолчанию для каждой задачи Ansible устанавливает два SSH-соединения:
1.  Копирует Python-скрипт модуля на удаленный хост.
2.  Запускает этот скрипт.

Pipelining устраняет второе соединение. Вместо копирования файла скрипт передается через STDIN первого SSH-соединения и сразу выполняется. Это сокращает количество сетевых операций вдвое.

**Почему не включено по умолчанию?**
Эта опция требует, чтобы на удаленном хосте в конфигурации `sudoers` была отключена настройка `requiretty`. В некоторых системах она включена по умолчанию из соображений безопасности и может привести к ошибкам повышения привилегий (`become`).

**Как включить:**
Рекомендуется включать глобально в `ansible.cfg`.

```ini
# ansible.cfg
[ssh_connection]
pipelining = True
```
> **Важно:** Перед включением убедитесь, что `requiretty` отключен для пользователя Ansible на целевых системах.
>
> **Примечание:** SSH Pipelining, наряду с мультиплексированием, был одним из основных способов ускорения Ansible до появления сторонних плагинов, таких как `mitogen`. Он остается актуальным и эффективным методом оптимизации.

## 2. SSH Multiplexing (ControlPersist)

**Что это?**
Это функция OpenSSH, которая позволяет переиспользовать одно TCP-соединение для нескольких последовательных SSH-сессий к одному хосту. Ansible не устанавливает новое соединение для каждой задачи, а использует уже открытый "мастер-канал", чтобы все задачи выполнялись в рамках одного соединения.

**Эффект:**
Значительно снижает задержки и нагрузку на CPU, так как не тратятся ресурсы на TCP-рукопожатия и повторную SSH-аутентификацию для каждой задачи. Ускорение может достигать 3-10 раз. **Рекомендуется всегда держать включенным.**

**Как включить:**
В `ansible.cfg` добавьте аргументы для SSH в секцию `[ssh_connection]`.

```ini
# ansible.cfg
[ssh_connection]
# Аргументы для мультиплексирования
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
```
*   `ControlMaster=auto`: Включает мультиплексирование.
*   `ControlPersist=60s`: Мастер-соединение будет оставаться активным в течение 60 секунд после последней сессии, что позволяет мгновенно переподключаться.

## 3. Увеличение параллелизма (Forks)

**Что это?**
Параметр `forks` определяет, сколько хостов Ansible будет обрабатывать параллельно. По умолчанию это значение равно 5, что очень мало для больших инвентарей.

**Как работает:**
Ansible берет первую задачу и выполняет ее на `forks` хостах. Затем на следующих `forks` хостах и так далее, пока все хосты не завершат первую задачу. Только после этого он переходит ко второй.

**Как настроить:**
Значение подбирается экспериментально в зависимости от мощности контрольного узла (CPU и, в особенности, оперативной памяти).

*   **Глобально в `ansible.cfg`:**
    ```ini
    [defaults]
    forks = 100
    ```
*   **При запуске плейбука:**
    ```bash
    ansible-playbook my_playbook.yml --forks=100
    ```

> **Потребление памяти:**
> Чем больше форков, тем больше памяти требуется процессу Ansible. В реальных сценариях на старых версиях Ansible (2.4) при 300-400 форках потребление памяти могло достигать 32 ГБ. На практике, для большинства задач редко используется более 15-20 форков одновременно. Начинайте с небольшого значения (20-30) и увеличивайте по необходимости.

### Ограничение параллелизма для Rolling Updates

Иногда нужно ограничить параллелизм для конкретных операций (например, для последовательного обновления веб-серверов без простоя).

*   `serial: <N>`: Директива на уровне **плея**. Ограничивает количество хостов, на которых одновременно выполняется весь плей.
    ```yaml
    - hosts: webservers
      serial: 1 # Выполнять по одному хосту за раз
      tasks:
        # ...
    ```
*   `throttle: <N>`: Директива на уровне **задачи**. Ограничивает параллелизм для одной конкретной задачи.
    ```yaml
    - name: Restart web server
      ansible.builtin.service:
        name: nginx
        state: restarted
      throttle: 1 # Перезапускать строго по одному
    ```

## 4. Стратегии выполнения (Execution Strategies)

*   **`linear` (по умолчанию):** Самая медленная. Ansible ждет, пока **все** хосты завершат задачу 1, прежде чем **любой** из них сможет начать задачу 2.
*   **`free`:** Самая быстрая. Как только хост завершает задачу, он немедленно приступает к следующей, не дожидаясь остальных. Это идеальный вариант, если хосты разнородны по производительности или вам не важен синхронный порядок выполнения.

**Как настроить:**

*   **Глобально в `ansible.cfg`:**
    ```ini
    [defaults]
    strategy = free
    ```
*   **В плейбуке:**
    ```yaml
    - hosts: all
      strategy: free
      tasks:
        # ...
    ```
> **Примечание:** Существуют и другие стратегии, например, `debug` (linear с отладчиком) и `host_pinned` (вариация `free`). Стратегии являются плагинами, и можно написать свою. Одним из самых популярных сторонних плагинов-стратегий является `mitogen`, который значительно ускоряет выполнение за счет оптимизации транспортного уровня.

## 5. Оптимизация сбора фактов

Сбор фактов (`Gathering Facts`) в начале каждого плея может быть очень медленным, так как модуль `setup` опрашивает систему на предмет сотен параметров.

**1. Полное отключение:**
Если вам не нужны факты о системе, просто отключите их.
```yaml
- hosts: all
  gather_facts: false
  tasks:
    # ...
```

**2. Частичный сбор (`gather_subset`):**
Собирайте только то, что вам нужно.
*   `min`: Минимальный набор (архитектура, дистрибутив). Очень быстро.
*   `network`: Сетевая информация.
*   `hardware`: Информация об оборудовании (процессор, память). **Очень медленно**, избегайте, если не нужно.
*   `virtual`: Информация о виртуализации.

**Как использовать:**
```yaml
- hosts: all
  gather_subset: min # Собрать только минимальный набор
  tasks:
    # ...
```
Можно комбинировать или исключать:
*   `gather_subset: min,network`
*   `gather_subset: '!all,network'` (все, кроме сетевых)
*   `gather_subset: '!hardware,!network'` (все, кроме оборудования и сети)

## 6. Асинхронные задачи

Этот метод не ускоряет саму задачу, но позволяет плейбуку не ждать ее завершения. Полезно для долгих операций, таких как обновление системы, компиляция или длительные бэкапы.

*   `async: <seconds>`: Максимальное время выполнения задачи в фоне.
*   `poll: 0`: "Fire and forget". Ansible запускает задачу и сразу переходит к следующей.

**Пример:**
```yaml
- name: Run long background process
  ansible.builtin.command: /usr/bin/long_running_script.sh
  async: 3600 # Дать час на выполнение
  poll: 0     # Не ждать завершения
  register: long_task_result

# ... другие задачи выполняются немедленно ...

- name: Check status of the long task later
  ansible.builtin.async_status:
    jid: "{{ long_task_result.ansible_job_id }}"
  register: job_status
  until: job_status.finished
  retries: 30 # Проверять 30 раз
  delay: 60   # Каждые 60 секунд
```

## Продвинутые детали

## 7. Плагин Mitogen

**Mitogen** — это сторонний плагин, который кардинально меняет транспортный уровень Ansible, заменяя стандартные `linear` и `free` стратегии.

**Как работает:**
*   Устанавливает одно высокооптимизированное соединение с удаленным хостом.
*   Передает код модулей напрямую через STDIN, избегая создания файлов.
*   Запускает все задачи в одном долгоживущем Python-процессе, что исключает накладные расходы на запуск интерпретатора для каждой задачи.
*   Встроенные мультиплексинг и пайплайнинг.

**Эффект:**
Прирост скорости от 1.5 до 7-8 раз.

**Как использовать:**
1.  Установить Mitogen.
2.  Настроить `ansible.cfg` для использования плагинов Mitogen.
3.  Задать стратегию в плейбуке:
    ```yaml
    - hosts: all
      strategy: mitogen_linear # или mitogen_free
      tasks:
        # ...
    ```
На текущий момент это один из самых эффективных способов ускорить Ansible.

## 8. Измерение производительности с помощью Callback-плагинов

После применения оптимизаций возникает вопрос: как измерить их эффект? Для этого в Ansible существуют **Callback-плагины**.

**Что это?**
Callback-плагины — это расширения, которые "цепляются" к событиям Ansible (например, `on_task_start`, `on_play_end`) и выполняют определенные действия. Они не влияют на ход выполнения плейбука, но могут изменять его вывод или собирать метаданные.

### Профилирование и таймеры

Самые полезные для оптимизации callback-плагины — это те, которые измеряют время.

*   **`timer`**: Добавляет к выводу каждой задачи время, затраченное на ее выполнение. Позволяет быстро оценить длительность каждого шага.
*   **`profile_tasks`**: Не меняет вывод в реальном времени, но в конце выполнения плейбука выводит отсортированный список всех задач, от самой медленной до самой быстрой. Это ключевой инструмент для поиска "узких мест".
*   **`profile_roles`**: Аналогично `profile_tasks`, но агрегирует время по ролям.

### Управление выводом (STDOUT)

Существуют callback-плагины, которые полностью меняют формат вывода Ansible в консоль.
*   **`default`**: Стандартный вывод Ansible.
*   **`dense`**: Делает вывод более компактным, убирая лишние переносы строк.
*   **`debug`**: По заверению документации, улучшает вывод ошибок для отладки. На практике разница может быть не всегда заметна, так как основной вывод все равно остается в формате JSON, который требует внимательного разбора.
*   **`yaml`**: Выводит результаты в формате YAML, что удобно для машинной обработки.

### Как включить:

Callback-плагины настраиваются в файле `ansible.cfg`.

1.  **`stdout_callback`**: Управляет плагином для вывода. Одновременно может быть активен только один такой плагин.
2.  **`callback_whitelist`**: "Белый список" плагинов, которые должны быть загружены. Сюда добавляются все плагины, кроме stdout-плагина.

**Пример конфигурации `ansible.cfg` для профилирования:**
```ini
[defaults]
# ... другие настройки ...

# Включаем плагины для сбора времени
callback_whitelist = timer, profile_tasks, profile_roles

# Опционально: меняем формат вывода на более плотный
# stdout_callback = dense
```
После включения этих плагинов просто запустите ваш плейбук. В конце вы увидите подробный отчет о времени выполнения каждой задачи, что позволит вам объективно оценить эффективность примененных оптимизаций.

## 9. Оптимизация копирования файлов: `copy` vs `synchronize`

При копировании большого количества небольших файлов модуль `ansible.builtin.copy` может работать медленно, так как он устанавливает отдельное SSH-соединение для каждой операции.

### Модуль `synchronize`

Модуль `ansible.builtin.synchronize` является оберткой над утилитой `rsync` и может значительно ускорить процесс копирования файлов.

**Преимущества:**
*   Значительно быстрее `copy` для большого количества файлов.
*   Передает только изменения, что экономит трафик при повторных запусках.

**Недостатки и практический опыт:**
*   **Сложности с аутентификацией:** В прошлом у модуля были проблемы с передачей параметров SSH-подключения. Он мог некорректно работать при аутентификации по паролю, требуя обязательной настройки SSH-ключей.
*   **Зависимость от `rsync`:** Требует наличия `rsync` на обоих хостах (контрольном и управляемом).

### Когда что использовать?

*   **До появления `mitogen`:** `synchronize` был практически обязательным для ускорения развертывания проектов с большим количеством файлов.
*   **После появления `mitogen`:** Поскольку `mitogen` сам по себе кардинально ускоряет все SSH-операции, выигрыш от использования `synchronize` становится менее заметным. Зачастую можно вернуться к использованию стандартного и более простого модуля `copy`, так как общая скорость выполнения плейбука и так будет высокой.

**Вывод:** Если вы не используете `mitogen` и вам нужно быстро скопировать дерево каталогов, `synchronize` — ваш выбор. Если вы используете `mitogen`, начните со стандартного модуля `copy` и переходите к `synchronize` только если копирование файлов все еще является узким местом.
