# Ansible — оптимизация производительности

## Определения

**SSH Pipelining** — метод ускорения, при котором скрипты модулей передаются через стандартный ввод (STDIN) существующего SSH-соединения. Это исключает необходимость создания отдельного соединения для каждой задачи.

**SSH Multiplexing (ControlPersist)** — механизм OpenSSH, позволяющий переиспользовать одно TCP-соединение для нескольких последовательных SSH-сессий, что избавляет от задержек на повторную аутентификацию.

**Параллелизм (Forks)** — параметр, определяющий количество хостов, на которых Ansible может выполнять задачи одновременно.

**Кэширование фактов (Fact Caching)** — сохранение собранных системных данных во внешнее хранилище (Redis, файлы), что позволяет не собирать их заново при каждом запуске плейбука.

**Стратегия выполнения (Execution Strategy)** — плагин, определяющий порядок прохождения задач через группу хостов (например, `linear` или `free`).

## Основные концепции

### 1. Оптимизация сетевых соединений

#### Настройка SSH в ansible.cfg
Для максимальной скорости работы через SSH необходимо включить конвейеризацию и мультиплексирование в блоке `[ssh_connection]`:

```ini
[ssh_connection]
# Включение Pipelining (требует отключения requiretty в sudoers на хостах)
pipelining = True

# Настройка ControlPersist для переиспользования соединений
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
```

### 2. Управление параллелизмом

Параметр `forks` по умолчанию равен 5, что крайне мало для крупных сред. Рекомендуется увеличивать его до 50–100 в зависимости от ресурсов Control Node.

*   **В ansible.cfg:** `forks = 50`
*   **В CLI:** `ansible-playbook site.yml --forks 50`

### 3. Кэширование фактов (Fact Caching)

Сбор фактов (`gather_facts`) занимает значительное время. Кэширование позволяет ускорить запуск на 30–50%.

**Пример настройки файлового кэша в ansible.cfg:**
```ini
[defaults]
fact_caching = jsonfile
fact_caching_connection = /tmp/ansible_cache
# Время жизни кэша в секундах (например, 24 часа)
fact_caching_timeout = 86400
```

### 4. Стратегии выполнения

*   **Linear (по умолчанию):** Ansible ждет завершения текущей задачи на всех хостах перед переходом к следующей.
*   **Free:** Каждый хост проходит по задачам плейбука с максимально возможной скоростью, не дожидаясь остальных.

```yaml
- hosts: all
  strategy: free
  tasks:
    - name: Длительная задача
      ansible.builtin.yum:
        name: "*"
        state: latest
```

## Практические сценарии

### Последовательное обновление (Rolling Updates)

Использование `serial` и `throttle` позволяет безопасно обновлять высоконагруженные кластеры.

*   **`serial`** — разбивает выполнение всего плейбука на группы (батчи).
*   **`throttle`** — ограничивает количество одновременно выполняемых задач для конкретного шага.

```yaml
- hosts: web_servers
  serial: "25%" # Обновлять по четверти серверов за раз
  tasks:
    - name: Перезапуск балансировщика
      ansible.builtin.service:
        name: haproxy
        state: restarted
      throttle: 1 # Перезапускать строго по одному, даже если в батче больше хостов
```

### Асинхронные задачи

Идеально для операций, занимающих более 10–15 минут (например, пересборка RAID или скачивание тяжелых образов).

```yaml
- name: Запуск длительной операции в фоне
  ansible.builtin.command: /usr/local/bin/heavy_task.sh
  async: 3600 # Максимальное время выполнения
  poll: 0    # Не ждать завершения, перейти к следующей задаче
  register: job_result

- name: Проверка статуса позже
  ansible.builtin.async_status:
    jid: "{{ job_result.ansible_job_id }}"
  register: job_status
  until: job_status.finished
  retries: 30
  delay: 60
```

## Дополнительная информация

### Профилирование производительности

Для поиска "медленных" задач используйте встроенные callback-плагины.

**Включение в ansible.cfg:**
```ini
[defaults]
callbacks_enabled = timer, profile_tasks, profile_roles
```

### Использование Mitogen

**Mitogen** — это сторонний плагин, который может ускорить выполнение Ansible до 3 раз за счет замены стандартного SSH-транспорта.

*   **Плюсы:** Резкое снижение нагрузки на CPU контрольного узла.
*   **Ограничение:** Начиная с Ansible 2.15+, стабильность плагина может снижаться. Рекомендуется проверять совместимость с текущей версией `ansible-core`.
