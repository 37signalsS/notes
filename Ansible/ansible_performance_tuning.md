# Ansible: Оптимизация производительности

## Определения

* **SSH Pipelining**: метод, сокращающий количество SSH-операций за счёт передачи скриптов модулей через стандартный ввод (STDIN) существующего соединения, вместо создания второго для их выполнения.
* **SSH Multiplexing (ControlPersist)**: функция OpenSSH, позволяющая переиспользовать одно TCP-соединение для нескольких последовательных SSH-сессий, устраняя задержки на аутентификацию.
* **Forks**: параметр, определяющий количество хостов, которые Ansible обрабатывает параллельно.
* **Execution Strategy**: плагин, управляющий потоком выполнения задач на группе хостов (например, `linear`, `free`).
* **Facts**: переменные, содержащие информацию о системе (IP-адрес, версия ОС и др.), которые Ansible собирает (`gathers`) на Managed Node в начале выполнения.
* **Async Tasks (Асинхронные задачи)**: задачи, которые Ansible запускает в фоновом режиме, не дожидаясь их завершения.
* **Mitogen**: сторонний плагин, заменяющий транспортный уровень Ansible для ускорения выполнения Playbook.
* **Callback Plugins**: расширения, которые реагируют на события в Ansible (например, завершение задачи) и позволяют изменять вывод или собирать статистику.

## Основные концепции

### 1. Оптимизация SSH-соединений

#### SSH Pipelining

По умолчанию Ansible для каждой задачи устанавливает два SSH-соединения: одно для копирования Python-скрипта модуля, второе — для его запуска. **Pipelining** устраняет второе соединение, передавая скрипт через STDIN.

**Требование**: на Managed Node в конфигурации `sudoers` должна быть отключена опция `requiretty`.

**Включение в `ansible.cfg`**:

```ini
[ssh_connection]
pipelining = True
```

#### SSH Multiplexing (ControlPersist)

Функция OpenSSH позволяет переиспользовать одно TCP-соединение для множества SSH-сессий к одному хосту, что кардинально снижает задержки на повторную аутентификацию.

**Включение в `ansible.cfg`**:

```ini
[ssh_connection]
ssh_args = -o ControlMaster=auto -o ControlPersist=60s
```

* `ControlPersist=60s`: мастер-соединение остается активным 60 секунд после завершения последней сессии.

### 2. Параллелизм (Forks)

Параметр `forks` определяет, сколько хостов Ansible обрабатывает параллельно. Значение по умолчанию (5) обычно недостаточно для больших Inventory.

**Настройка**:

* **В `ansible.cfg`**:

    ```ini
    [defaults]
    forks = 50
    ```

* **В командной строке**:

    ```bash
    ansible-playbook site.yml --forks=50
    ```

> **Потребление памяти**: каждый форк создает отдельный процесс на Control Node. Подбирайте значение экспериментально (например, 20–30), следя за использованием RAM.

### 3. Стратегии выполнения

* **`linear` (по умолчанию)**: Ansible ждёт, пока **все** хосты завершат текущую задачу, прежде чем перейти к следующей.
* **`free`**: как только хост завершает задачу, он немедленно приступает к следующей, не ожидая остальных.

**Настройка в Playbook**:

```yaml
- hosts: all
  strategy: free
  tasks:
    # ...
```

### 4. Оптимизация сбора Facts

Сбор Facts (`gather_facts`) — ресурсоёмкая операция.

* **Полное отключение**: если Facts не используются в Playbook.

    ```yaml
    - hosts: all
      gather_facts: false
    ```

* **Частичный сбор (`gather_subset`)**: сбор только необходимых данных (например, `min`, `network`, `hardware`, `virtual`).

    ```yaml
    - hosts: all
      gather_subset: min,network
    ```

### 5. Измерение производительности (Callback Plugins)

Для поиска узких мест используйте Callback Plugins профилирования.

**Популярные плагины:**

* `timer`: показывает время выполнения каждой задачи.
* `profile_tasks`: выводит отсортированный по времени список задач в конце выполнения.
* `profile_roles`: агрегирует время выполнения по ролям.

**Включение в `ansible.cfg`** (для ansible-core >= 2.13):

```ini
[defaults]
callback_plugins = ~/.ansible/plugins/callback:/usr/share/ansible/plugins/callback
# Для активации конкретных плагинов:
callbacks_enabled = timer, profile_tasks, profile_roles
```

### 6. Выбор инструментов копирования

* **`ansible.builtin.copy`**: стандартный модуль, может быть медленным для большого количества файлов.
* **`ansible.builtin.synchronize`**: обертка над `rsync`. Передает только изменения, что значительно быстрее для больших объемов данных.

## Практические сценарии

### 1. Последовательное обновление (Rolling Updates)

Для управления порядком и скоростью выполнения на хостах используются `serial` и `throttle`.

* **`serial: <N>`**: ограничивает выполнение **всего Play** N хостами за раз.

    ```yaml
    - hosts: webservers
      serial: 2 # Выполнять Play группами по 2 хоста
      tasks:
        # ...
    ```

* **`serial` с процентами**: можно указать долю хостов в батче.

    ```yaml
    - hosts: webservers
      serial: '25%' # 25% хостов за раз
    ```

* **`serial` со списком (canary-стиль)**: батчи разных размеров по порядку.

    ```yaml
    - hosts: webservers
      serial: [1, 3, '10%'] # 1 → 3 → 10% от оставшихся
    ```

**По умолчанию (без `serial`):** Play выполняется на всех хостах параллельно — единственное ограничение `forks`.

* **`max_fail_percentage`**: прерывает Play, если в батче упало больше N% хостов.

    ```yaml
    - hosts: webservers
      serial: 2
      max_fail_percentage: 50 # прервать, если в батче упал ≥1 хост из 2
    ```

**Отличие `serial` от `forks`:**
- `forks` (глобально в `ansible.cfg` или `ansible-playbook --forks`) — сколько одновременных SSH-соединений может открыть Control Node. По умолчанию 5.
- `serial` — батчинг хостов внутри одного Play: Play выполняется на первой группе, ждёт завершения, переходит к следующей. `serial` работает поверх `forks`: внутри каждого батча параллелизм ограничен `forks`.

* **`throttle: <N>`**: ограничивает параллелизм для **одной конкретной задачи**.

    ```yaml
    - name: Перезапуск сервиса
      ansible.builtin.service:
        name: nginx
        state: restarted
      throttle: 1 # Перезапускать строго по одному
    ```

### 2. Асинхронное выполнение задач

Позволяет запускать длительные операции в фоне, не блокируя выполнение Playbook.

* `async`: максимальное время выполнения задачи (в секундах).
* `poll`: интервал опроса состояния. Если `poll: 0`, Ansible запускает задачу и сразу переходит к следующей.

**Пример (запуск и ожидание позже)**:

```yaml
- name: Запуск долгого процесса
  ansible.builtin.command: /usr/bin/long_script.sh
  async: 3600
  poll: 0
  register: job_result

- name: Проверка статуса задачи
  ansible.builtin.async_status:
    jid: "{{ job_result.ansible_job_id }}"
  register: job_status
  until: job_status.finished
  retries: 30
  delay: 60
```

## Дополнительная информация

### Плагин Mitogen

**Mitogen** — стороннее решение для кардинального ускорения Ansible (в 1.5–8 раз). Он заменяет стандартный способ передачи модулей через SSH более эффективным механизмом.

**Важно (Ansible 12+ / ansible-core 2.19+):** в новых версиях плагины стратегий объявляются устаревшими. Рекомендуется проверять совместимость Mitogen с используемой версией Ansible.

**Пример настройки `ansible.cfg`**:

```ini
[defaults]
strategy_plugins = /path/to/mitogen/plugins/strategy
strategy = mitogen_linear
```
