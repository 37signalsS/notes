# Ansible Automation Platform (AAP) и AWX: продвинутые функции

## Определения

**Ansible Automation Platform (AAP)** — корпоративная платформа автоматизации от Red Hat, включающая в себя контроллер (бывший Ansible Tower), частный реестр автоматизации (Automation Hub) и инструменты для разработки и анализа.

**AWX** — проект с открытым исходным кодом, на основе которого строится AAP. Является «upstream» версией для тестирования новых функций.

**Job Template (Шаблон задания)** — описание запуска плейбука, объединяющее инвентарь, учетные данные (credentials), проект и сам плейбук в единую сущность для запуска через API или веб-интерфейс.

**Workflow Job Template (Шаблон рабочего процесса)** — визуальный конструктор, позволяющий объединять несколько Job Templates в цепочки с логическими условиями (при успехе, при ошибке, всегда).

**Surveys (Опросы)** — интерактивные формы, которые запрашивают у пользователя значения переменных перед запуском шаблона, обеспечивая безопасный ввод данных без прямого доступа к коду.

## Основные концепции

### 1. Жизненный цикл Job Templates
Запуск задания в AAP/AWX проходит через несколько стадий:
1.  **Pending:** Задание поставлено в очередь и ожидает освобождения ресурсов в Execution Node.
2.  **Waiting:** Ожидание завершения зависимых задач или обновления проекта/инвентаря.
3.  **Running:** Непосредственное выполнение плейбука внутри Execution Environment (EE).
4.  **Completed:** Финальное состояние (Successful или Failed). Все логи сохраняются в БД для последующего аудита.

### 2. Workflows: визуальный редактор связей
Workflows позволяют строить сложные сценарии оркестрации:
*   **Узлы (Nodes):** Могут быть Job Templates, Inventory Syncs или Project Updates.
*   **Связи:**
    *   `On Success` (зеленая линия) — переход, если предыдущий шаг завершен успешно.
    *   `On Failure` (красная линия) — обработка ошибок (например, откат изменений или уведомление в Slack).
    *   `Always` (синяя линия) — выполнение независимо от результата (например, сбор логов).
*   **Approval Nodes:** Узлы, требующие ручного подтверждения администратором перед продолжением процесса.

### 3. Surveys: интерактивные опросы
Опросы позволяют абстрагировать технические детали от конечного пользователя:
*   **Типы полей:** Text, Password, Multiple Choice, Integer, Float.
*   **Валидация:** Можно задать регулярные выражения для проверки вводимых данных.
*   **Переменные:** Введенные значения передаются в плейбук как `extra_vars`.

## Практические сценарии

### Настройка RBAC (Role-Based Access Control)
RBAC в AAP/AWX строится на иерархии объектов: **Organizations → Teams → Users**.
*   **System Administrator:** Полный доступ ко всей платформе.
*   **Organization Admin:** Управление всеми объектами внутри одной организации.
*   **Project Admin:** Право на обновление кода проекта, но не обязательно на запуск заданий.
*   **Execute:** Право только на запуск Job Template (без возможности редактирования).
*   **Read:** Право только на просмотр настроек и результатов выполнения.

### Создание кастомных Credential Types
Если стандартных типов (SSH, AWS, Vault) недостаточно, можно создать свой тип учетных данных для работы с внешними API.

**Пример: API Токен для сервиса мониторинга**
1.  **Input Configuration (YAML):**
    ```yaml
    fields:
      - id: api_token
        type: string
        label: Service API Token
        secret: true
    ```
2.  **Injector Configuration (YAML):**
    ```yaml
    env:
      MONITORING_API_TOKEN: "{ {api_token} }"
    ```
*После этого в плейбуке переменная `MONITORING_API_TOKEN` будет доступна в окружении.*

## Дополнительная информация

### Масштабирование через Execution Nodes
В современных версиях AAP (2.x+) используется разделение на **Control Plane** (веб-интерфейс, база данных) и **Execution Plane** (узлы, где запускаются контейнеры с Execution Environments). Это позволяет масштабировать вычислительные мощности независимо от интерфейса управления.
