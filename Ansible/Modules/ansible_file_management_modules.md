# Ansible: Модули управления файлами

## Определения

**Модули управления файлами** — это группа специализированных инструментов Ansible (преимущественно `ansible.builtin`), предназначенных для декларативного манипулирования файловой системой на управляемых хостах. Они позволяют описывать желаемое состояние файлов и директорий, обеспечивая идемпотентность и безопасность операций.

**Атомарная перезапись (Atomic Move)** — стандартный механизм Ansible для обеспечения целостности данных. Вместо прямого редактирования файла Ansible создает временную копию (обычно в той же директории), вносит в неё изменения, устанавливает права и затем заменяет оригинал системным вызовом `rename`. Это гарантирует, что файл не окажется в поврежденном состоянии при сбое в процессе записи или нехватке места на диске.

**FQCN (Fully Qualified Collection Name)** — полное имя модуля (например, `ansible.builtin.template`). Использование FQCN является обязательным стандартом для предотвращения конфликтов имен и обеспечения предсказуемости выполнения во всех современных версиях Ansible.

## Основные концепции

### Группы модулей по назначению

1.  **Управление структурой и атрибутами:**
    *   `ansible.builtin.file`: Создание директорий (`directory`), симлинков (`link`), хардлинков (`hard`), пустых файлов (`touch`), управление правами, владельцами и удаление (`absent`).
    *   `ansible.builtin.stat`: Сбор фактов о файле (существование, контрольные суммы, права, `uid`, `gid`). Используется для принятия решений в последующих задачах через `register`.
    *   `ansible.builtin.find`: Рекурсивный поиск файлов по шаблонам, дате, размеру или содержимому.
    *   `ansible.builtin.tempfile`: Создание гарантированно уникальных временных файлов или директорий на управляемом хосте.
2.  **Перенос и получение данных:**
    *   `ansible.builtin.copy`: Копирование с контрольного узла или внутри удаленного хоста (`remote_src: yes`).
    *   `ansible.builtin.template`: Генерация файлов из шаблонов [Jinja2](../ansible_jinja_templating.md). Обработка происходит на контрольном узле.
    *   `ansible.builtin.fetch`: Копирование файлов с хостов на контрольный узел. **Ограничение**: Работает только с отдельными файлами; для выгрузки директорий используйте `ansible.posix.synchronize` в режиме `pull`.
    *   `ansible.builtin.get_url`: Загрузка файлов по HTTP/HTTPS/FTP напрямую на управляемый хост.
    *   `ansible.builtin.unarchive`: Распаковка архивов. Требует наличия `tar`, `unzip` или `xz` на целевом хосте. Может скачивать архив с контрольного узла или использовать локальный на хосте (`remote_src: yes`).
3.  **Редактирование содержимого:**
    *   `ansible.builtin.lineinfile`: Управление отдельными строками (добавление, замена, удаление). Идеально для простых правок системных конфигов.
    *   `ansible.builtin.blockinfile`: Вставка многострочных блоков текста, защищенных маркерами.
    *   `ansible.builtin.replace`: Массовая замена текста по регулярным выражениям.
    *   `ansible.builtin.patch`: Применение стандартных `patch`-файлов (diff).
    *   `ansible.builtin.assemble`: Сборка (конкатенация) одного файла из нескольких фрагментов, находящихся в директории.
4.  **Расширенные права и атрибуты (ansible.posix):**
    *   `ansible.posix.acl`: Управление расширенными списками контроля доступа (ACL).
    *   `ansible.posix.xattr`: Управление расширенными атрибутами файловой системы.

### Выбор стратегии редактирования файла

| Инструмент | Когда использовать | Плюсы | Минусы |
| :--- | :--- | :--- | :--- |
| **template** | Для сложных и динамических конфигов | SSoT, полный контроль через Jinja2 | Требует хранения и поддержки шаблона |
| **lineinfile** | Для одиночных правок в системных файлах | Минимум кода, не нужен шаблон | Трудно поддерживать при большом кол-ве правок |
| **blockinfile** | Для вставки блоков (напр. в `/etc/hosts`) | Четкие границы блока (маркеры) | Добавляет комментарии-маркеры в файл |
| **replace** | Для массового патчинга по Regex | Высокая гибкость поиска | Риск нарушить структуру файла при ошибке в Regex |

### Критически важные параметры

-   **`validate`**: Выполнение команды проверки синтаксиса перед финальной заменой файла (например, `validate: '/usr/sbin/visudo -cf %s'`). Символ `%s` заменяется на путь к временному файлу.
-   **`remote_src`**: Определяет местоположение источника. Если `yes`, `src` ищется на управляемом хосте (используется в `copy` и `unarchive`).
-   **`unsafe_writes`**: Позволяет Ansible изменять файлы, когда атомарная перезапись невозможна (например, при монтировании файлов напрямую в Docker-контейнеры через `bind mount` или на сетевых FS без поддержки `rename`). **Внимание**: Использование повышает риск повреждения файла при сбое в момент записи.
-   **`backup`**: Создает резервную копию файла с временной меткой в той же директории перед внесением изменений.
-   **`force`**: В модуле `copy` определяет, нужно ли перезаписывать файл, если он уже существует, но имеет другое содержимое.

### Права доступа, атрибуты и SELinux

Файловые модули поддерживают расширенное управление атрибутами:
- **`owner` / `group`**: Установка владельца и группы.
- **`mode`**: Права доступа. Рекомендуется использовать восьмеричный формат в кавычках (`'0644'`). Поддерживается символьный режим (например, `u+rw,g-w,o-r`).
- **`attributes`**: Флаги файловой системы Linux (например, `i` — запрет на изменение (immutable), `a` — только для дозаписи). Требует поддержки файловой системой (ext4, xfs).
- **SELinux**: Параметры `setype`, `seuser`, `serole`, `selevel` для управления контекстом безопасности. Если SELinux включен, Ansible пытается сохранить контекст при атомарном перемещении.

### Режим диагностики (Diff & Check Mode)

Файловые модули полноценно поддерживают флаги диагностики:
- **`--check`**: Показывает, будет ли файл изменен, не применяя изменений на практике.
- **`--diff`**: Показывает детальную разницу (unified diff) между текущим состоянием файла и планируемым. Очень полезно для валидации работы `template` и `lineinfile`.

## Практические сценарии

### Создание директорий и рекурсивное управление правами
Использование `recurse: yes` позволяет применить права ко всем вложенным объектам (только при `state: directory`).

```yaml
- name: "Настройка директории для хранения данных"
  ansible.builtin.file:
    path: /var/lib/myapp
    state: directory
    owner: myuser
    group: mygroup
    mode: '0750'
    recurse: yes
```

### Безопасное обновление конфигурации Sudoers
Модуль `template` с валидацией предотвращает блокировку доступа к системе из-за синтаксических ошибок.

```yaml
- name: "Настройка прав sudo для разработчиков"
  ansible.builtin.template:
    src: sudoers_developers.j2
    dest: /etc/sudoers.d/developers
    owner: root
    group: root
    mode: '0440'
    validate: '/usr/sbin/visudo -cf %s'
```

### Распаковка артефактов с проверкой существования
Если архив загружается через `get_url`, используйте `remote_src: yes` в `unarchive`. Параметр `creates` обеспечивает идемпотентность.

```yaml
- name: "Развертывание приложения из архива"
  ansible.builtin.unarchive:
    src: /tmp/app_v1.tar.gz
    dest: /opt/app
    remote_src: yes
    creates: /opt/app/bin/start.sh
```

### Редактирование системных конфигураций (`lineinfile`)
Эффективно для изменения конкретных параметров без замены всего файла.

```yaml
- name: "Включение пересылки трафика IPv4"
  ansible.builtin.lineinfile:
    path: /etc/sysctl.conf
    regexp: '^net.ipv4.ip_forward'
    line: 'net.ipv4.ip_forward=1'
    state: present
    backup: yes
```

### Тонкая настройка прав через ACL
Предоставление доступа конкретному пользователю без изменения владельца/группы директории.

```yaml
- name: "Разрешение чтения логов для пользователя мониторинга"
  ansible.posix.acl:
    path: /var/log/nginx
    entity: prometheus
    etype: user
    permissions: rx
    state: present
    recursive: yes
```

### Сбор логов по критериям (find + fetch)
Сначала ищем файлы по размеру и дате, затем выгружаем их на контрольный узел.

```yaml
- name: "Поиск тяжелых логов"
  ansible.builtin.find:
    paths: /var/log/myapp
    size: 10M
    age: 1d
  register: log_files

- name: "Выгрузка найденных логов"
  ansible.builtin.fetch:
    src: "{{ item.path }}"
    dest: "./backup_logs/{{ inventory_hostname }}/"
    flat: yes
  loop: "{{ log_files.files }}"
```

### Использование кастомных маркеров в blockinfile
Позволяет избежать конфликтов со стандартными маркерами Ansible, если файл уже содержит аналогичные комментарии.

```yaml
- name: "Добавление настроек в кастомный конфиг"
  ansible.builtin.blockinfile:
    path: /etc/my_app.conf
    marker: "# {mark} MY APP SETTINGS"
    block: |
      setting_a = true
      setting_b = false
```
