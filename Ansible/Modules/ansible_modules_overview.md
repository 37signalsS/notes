# Ansible: Обзор модулей

## Определения

**Модули Ansible** — это автономные единицы кода (плагины), которые выполняют конкретные задачи на управляемых хостах. В отличие от плагинов, которые работают на контрольном узле, модули копируются на целевой хост, выполняются и возвращают результат в формате JSON.

**Идемпотентность** — свойство модуля, гарантирующее, что повторное выполнение не изменит систему, если она уже находится в желаемом состоянии. Большинство нативных модулей Ansible идемпотентны по умолчанию.

**FQCN (Fully Qualified Collection Name)** — полное имя модуля, включающее пространство имен и коллекцию (например, `ansible.builtin.copy`). Начиная с Ansible 2.10, модули поставляются в составе **Коллекций**, и использование FQCN является обязательным стандартом для предотвращения конфликтов.

## Основные концепции

### Параметр state
Большинство модулей используют параметр `state` для описания желаемого состояния ресурса:
- `present` / `installed`: ресурс должен существовать (установка, если отсутствует).
- `absent` / `removed`: ресурс должен быть удален.
- `latest`: установка или обновление до последней доступной версии.
- `started` / `stopped` / `restarted` / `reloaded`: управление состоянием системных служб.

### Общие параметры модулей
Многие модули (особенно файловые) поддерживают стандартный набор аргументов:
- `owner` / `group`: установка владельца и группы.
- `mode`: задание прав доступа (например, `'0644'`).
- `backup`: создание резервной копии перед изменением (обычно для файлов).
- `remote_src`: указывает, находится ли источник на удаленном хосте (`yes`) или на контрольном узле (`no`).

### Режимы проверки и сравнения
- **Check Mode (`--check`)**: Режим "сухого запуска" (dry run). Модули сообщают, какие изменения были бы внесены, не изменяя систему.
- **Diff Mode (`--diff`)**: Показывает детальные изменения (разницу в строках текстовых файлов). Помогает понять, что именно будет изменено в конфигурации.

### Возвращаемые значения (Return Values)
После выполнения модуль возвращает JSON-структуру, которую можно сохранить через `register`:
- `changed`: булево значение, указывающее, были ли внесены изменения.
- `failed`: признак ошибки выполнения.
- `ansible_facts`: системные данные, собранные модулем (например, модулем `setup` или `package_facts`).
- `msg`: текстовое описание результата или ошибки.

Подробнее о сохранении этих данных: **[Регистрация результатов (register)](../PlaybookStructure/flow_control.md#регистрация-результатов-register)**.

### Безопасность
Для скрытия чувствительных данных (пароли, ключи) в логах и выводе используется директива задачи `no_log: true`.
См. также: **[Безопасность в Ansible](../ansible_security_best_practices.md)**.

## Практические сценарии

### Использование FQCN и регистрация результата
Пример установки пакета с последующим использованием возвращаемых данных:

```yaml
- name: "Установка Nginx через универсальный менеджер"
  ansible.builtin.package:
    name: nginx
    state: present
  become: true
  register: pkg_result

- name: "Вывод сообщения при установке"
  ansible.builtin.debug:
    msg: "Пакет был установлен или обновлен"
  when: pkg_result.changed
```

### Категории модулей по назначению

Ниже представлены основные группы модулей и ссылки на их подробное описание.

1.  **[Управление пакетами](ansible_package_management_modules.md)**: `package`, `apt`, `dnf`, `pip`.
2.  **[Управление файлами](ansible_file_management_modules.md)**: `copy`, `template`, `file`, `lineinfile`.

### Работа с документацией (ansible-doc)
Утилита `ansible-doc` — основной инструмент для изучения параметров модулей на контрольном узле.

```bash
# Просмотр полной справки и примеров модуля copy
ansible-doc ansible.builtin.copy

# Краткий список всех доступных модулей в системе
ansible-doc -l

# Просмотр справки только по конкретной коллекции
ansible-doc community.general.docker_container
```
