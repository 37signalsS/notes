# Ansible Pull — управление конфигурацией в pull-режиме

## Определения

**Ansible Pull** — это утилита, реализующая **pull-модель** управления конфигурацией в Ansible. В отличие от стандартной **[push-модели](./ansible_core_concepts.md#определения)**, где контрольный узел "проталкивает" конфигурацию на управляемые машины, `ansible-pull` позволяет управляемым узлам самостоятельно обновлять свою конфигурацию. Это скрипт, который объединяет в себе `git` и `ansible-playbook`: он скачивает плейбук из Git-репозитория и запускает его локально на узле.

## Основные концепции

В pull-режиме управляемые узлы (ноды) становятся активными инициаторами изменений. Вместо того чтобы центральный сервер подключался к сотням машин, каждая машина обращается к Git-репозиторию по расписанию (через **Systemd Timers** или **Cron**), скачивает актуальные инструкции и применяет их к себе (`localhost`).

**Преимущества:**

* **Масштабируемость:** Снимается нагрузка с контрольного узла. Ограничением становится только пропускная способность Git-сервера, что позволяет управлять тысячами хостов одновременно.
* **Автономность:** Ноды могут обновляться даже если они находятся за NAT или имеют нестабильное подключение к контрольному узлу (например, ноутбуки или удаленные филиалы).
* **Децентрализация:** Идеально подходит для инфраструктуры, где хосты появляются динамически (например, при автомасштабировании в облаке).

**Недостатки:**

* **Сложность управления секретами:** Требует безопасной передачи паролей Vault или ключей доступа на каждый узел.
* **Зависимость от агента:** На каждой управляемой машине должен быть установлен Ansible и Git.
* **Трудности с оркестрацией:** Сложно выполнять задачи, требующие координации между несколькими хостами (например, последовательное обновление кластера).

## Практические сценарии

### Базовый запуск с публичным репозиторием

По умолчанию `ansible-pull` ищет плейбук с именем `local.yml` или по имени хоста (FQDN).

```bash
ansible-pull \
  -U https://github.com/user/ansible-config.git \
  -C master \
  -d /opt/ansible-pull \
  -i localhost, \
  local.yml
```

* `-U` (`--url`): URL Git-репозитория.
* `-C` (`--checkout`): Ветка, тег или хэш коммита для загрузки.
* `-d` (`--directory`): Путь для клонирования (рекомендуется абсолютный путь).
* `-i` (`--inventory`): Список хостов. Для pull-режима это почти всегда `localhost,`.
* `local.yml`: Имя плейбука для запуска.

### Работа с приватными репозиториями

Для доступа к приватным репозиториям чаще всего используются SSH-ключи. Публичный ключ должен быть добавлен в Git-сервис (GitHub, GitLab), а приватный ключ — размещен на хосте (например, в `~/.ssh/id_rsa`).

```bash
ansible-pull \
  -U git@github.com:user/ansible-private-config.git \
  -d /opt/ansible-pull \
  local.yml
```

### Передача переменных и управление логикой

Для адаптации конфигурации под конкретный хост часто используются дополнительные переменные (`extra-vars`).

```bash
ansible-pull \
  -U https://github.com/user/ansible-config.git \
  -e "env=production role=webserver" \
  local.yml
```

### Работа с секретами (Ansible Vault)

В режиме pull хосту нужен доступ к паролю Vault. Хранить пароль в открытом виде на диске небезопасно.

**Рекомендуемый подход:** Использование внешнего скрипта для получения пароля из менеджера секретов (например, HashiCorp Vault, AWS Secrets Manager или системного хранилища ключей).

```bash
ansible-pull \
  -U https://github.com/user/ansible-config.git \
  --vault-password-file /usr/local/bin/get_vault_pass.sh \
  local.yml
```

Скрипт `get_vault_pass.sh` должен возвращать пароль в `stdout` и иметь права доступа `0700`.

### Автоматизация через Systemd Timers

Использование **Systemd Timers** является современным стандартом и предпочтительнее **Cron** из-за детального логирования (`journalctl`) и возможности контроля зависимостей (например, запуск только после появления сети).

1. **Создайте сервис (`/etc/systemd/system/ansible-pull.service`):**
```ini
[Unit]
Description=Ansible Pull Service
After=network-online.target
Wants=network-online.target

[Service]
Type=oneshot
# -o сообщает ansible-pull выполнять запуск только при наличии обновлений в git
ExecStart=/usr/bin/ansible-pull -o -U https://github.com/user/repo.git -d /opt/ansible local.yml
StandardOutput=journal
```

2. **Создайте таймер (`/etc/systemd/system/ansible-pull.timer`):**
```ini
[Unit]
Description=Run Ansible Pull every hour

[Timer]
OnCalendar=hourly
Persistent=true
RandomizedDelaySec=300

[Install]
WantedBy=timers.target
```

## Рекомендации и лучшие практики

1. **Идемпотентность:** Плейбуки должны быть строго идемпотентными, так как они запускаются автоматически и часто.
2. **Локальное соединение:** Всегда используйте `connection: local` в плейбуках, чтобы избежать накладных расходов на SSH-подключение к самому себе.
3. **Использование скрипта инициализации (`--setup`):** Флаг `-S` позволяет запустить скрипт перед выполнением основного плейбука (например, для настройки окружения).
4. **Очистка после выполнения:** Используйте флаг `--cleanup`, если необходимо удалять временную копию репозитория после завершения работы.
5. **Staggering (Разброс):** Добавляйте случайную задержку (`RandomizedDelaySec` в systemd или `sleep` в cron), чтобы сотни серверов не обращались к Git-серверу одновременно.
6. **Проверка изменений (`--check`):** Для критических систем можно сначала запускать pull в режиме проверки, логировать результат и применять изменения только после подтверждения.
