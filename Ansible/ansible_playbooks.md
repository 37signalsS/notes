# Ansible: Плейбуки (Playbooks)

Плейбуки являются ядром Ansible и представляют собой YAML-файлы, которые декларативно описывают желаемое состояние системы. Они позволяют оркестрировать сложную последовательность задач на управляемых узлах.

См. также:
* [Обзор Ansible](ansible_overview.md)
* [Выполнение плейбуков](ansible_playbook_execution.md)
* [Кроссплатформенные плейбуки Ansible](cross_platform_playbooks.md)
* [Пример: Развертывание Python-приложения](./ansible_python_app_deployment_example.md)

## Структура плейбука

Плейбук — это список одного или нескольких "плеев" (plays). Каждый плей определяет набор задач для выполнения на определенной группе хостов.

```yaml
---
- name: Play 1 - Настройка веб-серверов
  hosts: webservers
  become: true
  vars:
    http_port: 80
  tasks:
    - name: Установка Nginx
      apt:
        name: nginx
        state: present
  handlers:
    - name: Перезапуск Nginx
      service:
        name: nginx
        state: restarted

- name: Play 2 - Настройка баз данных
  hosts: db_servers
  become: true
  tasks:
    # ... задачи для баз данных
```

## Ключевые директивы

*   `hosts`: Определяет целевые хосты или группы из файла инвентаризации.
*   `tasks`: Список задач, которые выполняются последовательно.
*   `vars`: Словарь переменных, доступных в рамках плея.
*   `become: true/false`: Указывает, нужно ли повышать привилегии (например, через `sudo`).
*   `handlers`: Специальные задачи, которые выполняются только по уведомлению от других задач (через директиву `notify`).
*   `roles`: Список ролей для включения в плей.

## Переменные (Variables)

Для практического руководства по определению и переопределению переменных см. [Практическое руководство по переменным и фактам](./ansible_variables_and_facts.md).

### Где определять переменные и их приоритет

Переменные в Ansible могут быть определены во множестве мест. Понимание иерархии их приоритетов критически важно для отладки и предсказуемого поведения плейбуков. Чем выше уровень в списке, тем выше приоритет — значение переменной на более высоком уровне "перезаписывает" значение, установленное на более низком.

Ниже перечислены основные места для определения переменных в порядке **возрастания приоритета**:

1.  **Роли: `defaults/main.yml`**: Здесь задаются значения "по умолчанию" для переменных внутри роли. У них **самый низкий приоритет**, и они легко могут быть переопределены на любом другом уровне.
2.  **Инвентарь: Групповые переменные (`group_vars`)**: Переменные, общие для группы хостов. Задаются в файлах `group_vars/<group_name>.yml`.
3.  **Инвентарь: Переменные хоста (inline)**: Переменные, определенные прямо в файле инвентаря в строке с хостом (например, `my_host ansible_host=1.2.3.4 http_port=8080`).
4.  **Инвентарь: Переменные хоста (`host_vars`)**: Самые специфичные для инвентаря переменные, применяются к конкретному хосту. Задаются в файлах `host_vars/<hostname>.yml`.
5.  **Факты (`ansible_facts`)**: Переменные, которые Ansible автоматически собирает о системе (`gather_facts: true`).
6.  **Плейбук: `vars`**: Переменные, определенные непосредственно в плее (`- hosts: ... vars: ...`). Используются для значений, которые относятся к логике конкретного плея.
7.  **Плейбук: `vars_files`**: Переменные, подключенные из внешних YAML-файлов.
8.  **Роли: `vars/main.yml`**: Переменные, определенные внутри роли. Они имеют более высокий приоритет, чем `defaults` и переменные, определенные на уровне инвентаря и плейбука. Их следует рассматривать как "константы" роли.
9.  **Командная строка (`--extra-vars` или `-e`)**: Переменные, переданные при запуске `ansible-playbook`. **Имеют самый высокий приоритет** и переопределяют все остальные.
    ```bash
    ansible-playbook my_playbook.yml -e "my_var=new_value version=1.5"
    ```

### Факты Ansible (Ansible Facts)

На старте каждого плея Ansible по умолчанию выполняет задачу **`Gathering Facts`**. На этом этапе он собирает огромное количество информации (фактов) об управляемой системе:
*   Сетевые интерфейсы и IP-адреса.
*   Операционная система, ее семейство и версия.
*   Архитектура процессора.
*   Объем памяти.
*   И многое другое.

Все эти данные помещаются в одну большую переменную-словарь `ansible_facts`. Для удобства Ansible также создает множество "магических" переменных с префиксом `ansible_`, которые являются ярлыками для доступа к данным из `ansible_facts`.

*   **Пример:** `ansible_facts['os_family']` доступен как `ansible_os_family`.

**Использование фактов:**
Факты чрезвычайно полезны для создания универсальных плейбуков.

```yaml
- name: Установка Apache на Debian/Ubuntu
  ansible.builtin.apt:
    name: apache2
    state: present
  when: ansible_os_family == "Debian" # Используем факт для условного выполнения

- name: Установка Apache на RedHat/CentOS
  ansible.builtin.yum:
    name: httpd
    state: present
  when: ansible_os_family == "RedHat"
```

Вы можете посмотреть все собранные факты для хоста, выполнив задачу с модулем `debug`:
```yaml
- name: Показать все факты
  ansible.builtin.debug:
    var: ansible_facts
```

### Лучшие практики ("Дзен Ansible")

Гибкость системы переменных может привести к большой путанице. Чтобы избежать этого, рекомендуется следовать нескольким простым правилам ("Дзен Ansible"):

1.  **Определяйте переменную в одном месте.** Старайтесь не переопределять переменные на разных уровнях. Сложный для отладки плейбук — это плейбук, в котором значение переменной меняется 5 раз в зависимости от инвентаря, роли и параметров командной строки.
2.  **Используйте уникальные префиксы.** Чтобы избежать конфликтов имен между разными ролями, добавляйте префикс с названием роли или проекта.
    -   **Плохо:** `port: 8080`
    -   **Хорошо:** `my_app_nginx_port: 8080`
3.  **Избегайте общих имен.** Имена вроде `user`, `port`, `server`, `host` почти гарантированно вызовут конфликт.
    > Представьте, что у вас есть роль для Nginx с переменной `port: 80` и роль для Prometheus с переменной `port: 9090`. Если вы используете обе роли в одном плее, значение `port` станет непредсказуемым. В итоге ваш Nginx может попытаться запуститься на порту `9090`, а плейбук упадет с ошибкой.

## Условные конструкции (`when`)

Директива `when` позволяет выполнять задачу только при выполнении определенного условия. Условия могут использовать любые переменные: из инвентаря, `vars` или факты Ansible.

```yaml
- name: Завершить плейбук, если версия не поддерживается
  ansible.builtin.fail:
    msg: "Данная роль поддерживает только версию 7.x"
  when: my_app_version | int < 7
```

**Логические операции:**
-   **AND (И):** Когда вы передаете список условий, они объединяются по логическому "И". Задача выполнится, только если **все** условия истинны.
    ```yaml
    - name: "Перезагрузить сервис только если включено и были изменения"
      ansible.builtin.systemd:
        name: my_service
        state: reloaded
      when:
        - my_service_enabled
        - config_result is changed
    ```

-   **OR (ИЛИ):** Для логического "ИЛИ" используется явное ключевое слово `or`.
    ```yaml
    - name: "Выполнить, если система CentOS ИЛИ Ubuntu"
      ansible.builtin.debug:
        msg: "Это RedHat-based или Debian-based система."
      when: ansible_os_family == "RedHat" or ansible_os_family == "Debian"
    ```

## Циклы (`loop`)

Циклы позволяют выполнять одну и ту же задачу несколько раз с разными данными.

*   **Простой список:**
    ```yaml
    - name: Создание нескольких пользователей
      ansible.builtin.user:
        name: "{{ item }}"
        state: present
      loop:
        - alice
        - bob
        - carol
    ```

*   **Список словарей:**
    ```yaml
    - name: Установка нескольких пакетов
      ansible.builtin.apt:
        name: "{{ item.name }}"
        state: "{{ item.state }}"
      loop:
        - { name: 'nginx', state: 'present' }
        - { name: 'htop', state: 'present' }
        - { name: 'vim', state: 'latest' }
    ```

> **Примечание о `with_items`:**
> В старых версиях Ansible для циклов использовалась конструкция `with_items`. Она все еще работает, но `loop` является современным и более гибким стандартом, который заменяет все старые директивы `with_*`.

### Продвинутые циклы

#### Цикл с повторными попытками (`until`)

Иногда задача должна выполняться до тех пор, пока не будет достигнуто определенное условие (например, ожидание запуска веб-сервера). Для этого используется связка `until`, `retries` и `delay`.

```yaml
- name: Wait for service to be ready
  ansible.builtin.uri:
    url: http://localhost:8080/health
    status_code: 200
  register: health_check_result
  until: health_check_result.status == 200
  retries: 10 # Количество попыток
  delay: 5    # Пауза в секундах между попытками
```
Эта задача будет 10 раз с интервалом в 5 секунд отправлять запрос на `http://localhost:8080/health`, пока не получит ответ со статусом 200.

#### `include_tasks` vs `import_tasks`

Для выполнения блока из нескольких задач в цикле или по условию используются директивы `include_tasks` и `import_tasks`.

*   **`import_tasks` (статическое включение):**
    *   Содержимое файла **вставляется** в плейбук на этапе парсинга (до начала выполнения).
    *   Работает **только** для безусловного включения. **Не работает с `when` и `loop`**.
    *   Используется для простого структурирования и разбиения длинных плейбуков на логические части.

*   **`include_tasks` (динамическое включение):**
    *   Файл с задачами подключается и обрабатывается **в процессе выполнения** плея.
    *   **Работает с `loop` и `when`**. Это позволяет динамически выбирать, какой набор задач выполнять, или выполнять один и тот же набор задач несколько раз с разными параметрами.

**Пример:**
```yaml
# main.yml
- name: Включить задачи для Debian-подобных систем
  ansible.builtin.include_tasks: debian.yml
  when: ansible_os_family == "Debian"

- name: Включить задачи для RedHat-подобных систем
  ansible.builtin.include_tasks: redhat.yml
  when: ansible_os_family == "RedHat"
```

## Регистрация результатов (`register`)

Директива `register` позволяет сохранить результат выполнения задачи (включая ее статус, вывод и другие данные) в переменную. Эту переменную затем можно использовать в последующих задачах, например, в условных конструкциях `when`.

```yaml
- name: "Сгенерировать конфигурационный файл для whitelist"
  ansible.builtin.template:
    src: whitelist.j2
    dest: /etc/myapp/whitelist.conf
  register: whitelist_config # Сохраняем результат в переменную

- name: "Перезагрузить сервис, только если конфиг изменился"
  ansible.builtin.service:
    name: myapp
    state: reloaded
  when: whitelist_config is changed # Проверяем статус 'changed'
```
*   `register: whitelist_config`: Создает переменную `whitelist_config`, которая будет содержать всю информацию о выполнении задачи.
*   `when: whitelist_config is changed`: Следующая задача выполнится только в том случае, если предыдущая задача (`template`) внесла изменения в файл и вернула статус `changed`. Это более гибкая альтернатива `handlers`.

## Обработчики (`handlers`)

Обработчики — это специальные задачи, которые выполняются только один раз в конце плея и только в том случае, если на них было отправлено уведомление от другой задачи. Они идеально подходят для таких действий, как перезапуск служб.

**Проблема:** Представьте, что вы изменили конфигурацию Nginx. Чтобы изменения применились, сервис нужно перезагрузить. "Наивный" подход — просто добавить задачу в конец плейбука:
```yaml
# Не лучший способ!
- name: Reload Nginx
  ansible.builtin.service:
    name: nginx
    state: reloaded
```
Этот подход имеет два недостатка:
1.  Сервис будет перезагружаться при **каждом** запуске плейбука, даже если конфигурация не менялась. Это нарушает идемпотентность и может привести к кратковременным простоям.
2.  Если у вас несколько задач меняют конфигурацию, вам придется либо дублировать задачу перезагрузки, либо надеяться, что одной в конце хватит.

**Решение с `handlers`:**
Правильный способ — использовать связку `notify` и `handlers`.

```yaml
tasks:
  - name: Копирование конфигурации Nginx
    ansible.builtin.template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: Restart Nginx # Отправка уведомления

  - name: Установка нового SSL-сертификата
    ansible.builtin.copy:
      src: certs/new.crt
      dest: /etc/ssl/certs/new.crt
    notify: Restart Nginx # Еще одно уведомление

handlers:
  - name: Restart Nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
```
**Преимущества `handlers`:**
- **Идемпотентность:** Обработчик `Restart Nginx` будет вызван **только в том случае, если** задача `template` или `copy` реально изменила файлы (статус `changed`). Если файлы уже были в нужном состоянии (статус `ok`), уведомление не отправляется.
- **Эффективность:** Даже если 10 разных задач отправят уведомление обработчику `Restart Nginx`, он все равно выполнится **только один раз** в самом конце плея. Это предотвращает многократные и ненужные перезапуски сервиса.

## Делегирование задач (`delegate_to`)

Иногда возникает необходимость выполнить задачу не на целевом хосте, указанном в `hosts`, а на другой машине (чаще всего — на самом контрольном узле, `localhost`). Для этого используется директива `delegate_to`.

Классический пример — поиск локальных файлов, которые нужно скопировать на удаленный хост.

```yaml
- name: Find local artifacts to deploy
  hosts: app_servers
  tasks:
    - name: Find .war files on the control node
      ansible.builtin.find:
        paths: /path/to/local/artifacts
        patterns: "*.war"
      delegate_to: localhost # Выполнить эту задачу на машине, где запущен ansible
      register: found_artifacts

    - name: Deploy found artifacts to app servers
      ansible.builtin.copy:
        src: "{{ item.path }}"
        dest: /opt/tomcat/webapps/
      loop: "{{ found_artifacts.files }}"
      # Эта задача уже выполняется на хостах из группы 'app_servers'
```
В этом примере:
1.  Плей нацелен на `app_servers`.
2.  Первая задача (`find`) выполняется на `localhost` благодаря `delegate_to`. Она ищет файлы на машине, с которой вы запускаете плейбук.
3.  Результат поиска регистрируется в переменной `found_artifacts`. Эта переменная доступна в контексте хостов `app_servers`.
4.  Вторая задача (`copy`) выполняется уже на каждом сервере из `app_servers`, используя пути к файлам, найденным на `localhost`.

## Секции `pre_tasks` и `post_tasks`

Помимо основного блока `tasks`, который выполняется после подключения ролей, плейбук может содержать две специальные секции для задач: `pre_tasks` и `post_tasks`.

*   **`pre_tasks`**: Блок задач, который выполняется **до** выполнения всех ролей. Это полезно для предварительных проверок или подготовительных действий (например, проверка доступности внешних сервисов, установка зависимостей, необходимых для самих ролей).

*   **`post_tasks`**: Блок задач, который выполняется **после** выполнения всех ролей и их обработчиков. Это идеальное место для заключительных действий, которые должны произойти в самом конце.

**Пример:** Использование `post_tasks` для перезагрузки сервера после обновления ядра.

```yaml
- name: Full server setup
  hosts: all
  become: true

  roles:
    - role: base_setup
      # Эта роль может установить переменную 'kernel_updated: true', если ядро обновилось
    - role: nginx
    - role: users

  post_tasks:
    - name: Restart server after kernel upgrade
      ansible.builtin.shell: "sleep 10 && shutdown -r now"
      async: 1  # Не ждать завершения команды перезагрузки
      poll: 0   # "Fire and forget"
      when: kernel_updated is defined and kernel_updated

```
В этом примере:
1.  Сначала выполняются все роли (`base_setup`, `nginx`, `users`).
2.  Если в ходе выполнения роли `base_setup` было обновлено ядро (и установлен соответствующий факт или переменная `kernel_updated`), то в самом конце плея выполнится задача из `post_tasks` и перезагрузит сервер.

Это позволяет отделить логику ролей от финальных действий, которые должны завершать весь процесс конфигурации.

## Стратегии выполнения (Execution Strategies)

По умолчанию Ansible выполняет задачи последовательно на всех хостах в рамках одного плея. Однако существуют стратегии для управления параллелизмом и ускорения выполнения.

### Параллельное выполнение (`forks`)

Параметр `forks` определяет количество одновременных процессов (параллельных подключений), которые Ansible может использовать. Увеличение этого значения может значительно ускорить выполнение плейбуков в больших инфраструктурах. Значение по умолчанию — 5.

*   **Указание в командной строке:**
    ```bash
    ansible-playbook -i inventory.ini playbook.yml --forks=10
    ```

*   **Установка в `ansible.cfg`:**
    ```ini
    [defaults]
    forks = 10
    ```

### Асинхронное выполнение (`async` и `poll`)

Для длительных задач, которые могут блокировать выполнение всего плейбука (например, обновление системы, длительные вычисления), можно использовать асинхронный режим.

*   `async`: Максимальное время (в секундах), которое задача может выполняться в фоновом режиме.
*   `poll`: Интервал (в секундах), с которым Ansible будет проверять статус задачи. Если установить `poll: 0`, Ansible не будет ждать завершения задачи и сразу перейдет к следующей ("fire and forget").

**Пример асинхронной установки пакета:**
```yaml
- name: Установить тяжеловесный пакет асинхронно
  apt:
    name: big-package
    state: present
  async: 600  # Максимум 10 минут на выполнение
  poll: 15    # Проверять статус каждые 15 секунд
```

**Пример "fire and forget":**
```yaml
- name: Запустить долгий фоновый процесс
  command: /usr/bin/long_running_script.sh
  async: 3600 # Дать час на выполнение
  poll: 0     # Не ждать завершения
  register: long_task_result
```

Чтобы проверить статус асинхронной задачи, запущенной с `poll: 0`, можно использовать модуль `async_status`. Для этого нужно сохранить ID задачи (`ansible_job_id`), который возвращается при ее запуске.

```yaml
- name: Проверить статус задачи позже
  async_status:
    jid: "{{ long_task_result.ansible_job_id }}"
  register: job_status
  until: job_status.finished
  retries: 30
  delay: 60 # Проверять каждую минуту
```

### Параллелизм внутри задачи (`throttle`)

Ключевое слово `throttle` позволяет ограничить количество хостов, на которых одновременно выполняется *одна конкретная задача*. Это полезно для задач, которые создают высокую нагрузку на внешние системы (например, API, база данных) или требуют эксклюзивного доступа к общему ресурсу.

```yaml
- name: Обновление прошивки на сетевых устройствах
  community.network.firmware_upgrade:
    # ... параметры
  throttle: 1 # Выполнять строго по одному хосту за раз
```
Это отличается от `forks`, который является глобальным ограничителем для всего плея.

## Теги (Tags)

Теги позволяют выборочно запускать или пропускать определенные части плейбука. Это чрезвычайно полезно для больших плейбуков, где вы хотите выполнить только конкретную операцию (например, только перезапустить серверы приложений, не затрагивая базы данных).

Теги можно применять к плеям, задачам и ролям.

**Пример использования:**
```yaml
- name: Install and configure server
  hosts: all
  tasks:
    - name: Install base packages
      ansible.builtin.apt:
        name: htop
      tags:
        - packages

    - name: Configure nginx
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      tags:
        - configuration

- name: Deploy application
  hosts: app_servers
  tasks:
    - name: Copy application artifact
      ansible.builtin.copy:
        src: my_app.jar
        dest: /srv/app.jar
  tags:
    - deploy
```

**Запуск с тегами:**
```bash
# Запустить только задачи с тегом 'configuration'
ansible-playbook my_playbook.yml --tags configuration

# Запустить все, КРОМЕ задач с тегом 'deploy'
ansible-playbook my_playbook.yml --skip-tags deploy
```

**Специальные теги:**
- `always`: Задача с этим тегом будет выполняться всегда, даже если вы указали другие теги (за исключением случаев, когда вы явно ее пропускаете через `--skip-tags`).
- `never`: Задача с этим тегом никогда не будет выполняться, если только вы не укажете этот тег явно с помощью `--tags never`.

**Рекомендации:**
- Давайте тегам осмысленные и консистентные имена.
- Не создавайте слишком сложную и вложенную структуру тегов. Простота — залог успеха.
- Для ролей удобно использовать теги, соответствующие имени роли (например, `nginx`, `mysql`), чтобы можно было запустить или пропустить всю логику, связанную с конкретной технологией.

## Отладка плейбуков

Отладка — неотъемлемая часть работы с Ansible. Ниже перечислены основные инструменты и подходы. Для разбора реальных сценариев см. [Примеры отладки типовых ошибок](ansible_debugging_examples.md).

Для более подробного обзора ключей командной строки, полезных для отладки, см. [Ключи командной строки для `ansible-playbook`](ansible_playbook_cli_options.md).

### Повышение уровня детализации (`-v`, `-vvv`)

Это первый и самый простой шаг. Флаги `-v` (verbose) увеличивают количество выводимой информации.

*   `-v`: Показывает базовый результат выполнения каждого таска.
*   `-vv`: Более подробно, полезно для просмотра значений переменных.
*   `-vvv`: Максимальная детализация. Показывает детали SSH-соединения, пути к временным файлам на удаленных хостах.
*   `-vvvv`: Включает логирование на уровне соединения (очень много вывода).

```bash
ansible-playbook my_playbook.yml -vvv
```

### Режим проверки (`--check` и `--syntax-check`)

*   **`--syntax-check`**: Проверяет плейбуки только на синтаксические ошибки, не выполняя никаких действий на удаленных хостах. Это быстрый способ убедиться, что ваш YAML написан корректно.

*   **`--check`**: Запускает плейбук в режиме "сухого прогона" (dry run). Ansible покажет, какие изменения **были бы** внесены, но не будет выполнять их на самом деле.
    ```bash
    ansible-playbook my_playbook.yml --check
    ```
    **Ограничение:** Режим проверки не может предсказать сбои, которые зависят от реального выполнения предыдущих шагов. Если задача №2 зависит от файла, созданного задачей №1, то в режиме `--check` задача №1 не создаст файл, и задача №2, скорее всего, не будет выполнена или проверена корректно.

### Модуль `debug`

Позволяет выводить значения переменных или кастомные сообщения прямо во время выполнения плейбука. Это основной инструмент для проверки состояния и значений.

```yaml
- name: Print variable value
  ansible.builtin.debug:
    var: my_variable

- name: Print custom message
  ansible.builtin.debug:
    msg: "The user is {{ user_name }} and home dir is {{ home_dir }}"
```

### Пошаговое выполнение (`--step`)

Запускает плейбук в интерактивном режиме. Перед выполнением каждого таска Ansible будет спрашивать вашего подтверждения (`y/n/c`). Это позволяет дойти до проблемного места и проанализировать ситуацию.

```bash
ansible-playbook my_playbook.yml --step
```

### Стратегия `debug`

Помимо `debugger`, существует целая **стратегия выполнения** `debug`. Если она включена, при возникновении ошибки на любой задаче автоматически запускается интерактивный отладчик.

**Как использовать:**
Задайте стратегию при запуске плейбука.
```bash
ansible-playbook my_playbook.yml --strategy=debug
```
Это переводит весь плей в режим отладки. Внутри отладчика вы можете:
*   Просматривать и изменять значения переменных (`p my_var`, `p my_var = 'new_value'`).
*   Перезапускать проваленную задачу (`r` или `redo`).
*   Продолжить выполнение (`c` или `continue`).
*   Завершить работу (`q` или `quit`).

Эта стратегия не предназначена для использования в production, но очень мощна для интерактивной отладки сложных плейбуков.

### Ключевое слово `debugger`

`debugger` — это ключевое слово, которое можно добавить к любой задаче для вызова интерактивного отладчика. Это особенно полезно для точечной отладки конкретных задач без необходимости перезапускать весь плейбук или использовать объемный вербозный вывод.

**Использование:**
Добавляется непосредственно к задаче.

```yaml
- name: Моя задача с отладчиком
  ansible.builtin.command: some_command_that_might_fail
  debugger: on_failed # Вызывать отладчик только при сбое задачи
```

**Режимы работы `debugger`:**
*   `always`: Отладчик вызывается всегда, независимо от статуса задачи.
*   `never`: Отключает отладчик для данной задачи, даже если он включен глобально.
*   `on_failed`: Отладчик вызывается только в случае сбоя задачи.
*   `on_unreachable`: Отладчик вызывается, если хост недоступен.
*   `on_skipped`: Отладчик вызывается, если задача была пропущена.

**Команды отладчика (интерактивный режим):**
В интерактивном режиме отладчика доступны команды для анализа состояния:
*   `p <переменная>`: Печать значения переменной (например, `p hostvars['hostname']`).
*   `r` или `redo`: Перезапустить текущую задачу с текущими или измененными параметрами.
*   `c` или `continue`: Продолжить выполнение плейбука.
*   `q` или `quit`: Завершить выполнение плейбука.
*   `s` или `step`: Перейти к следующей задаче.
*   `l` или `list`: Показать текущий контекст задачи.
*   `a` или `args`: Показать аргументы, переданные в модуль.

**Примечание:** Хотя `debugger` является мощным инструментом, он используется реже, чем вербозный вывод или модуль `debug`, так как требует интерактивного вмешательства и запоминания команд. Его основное преимущество — возможность глубокого анализа одной задачи без лишнего шума.



### Ограничение выполнения

*   `--limit <хост или группа>`: Запускает плейбук только на указанных хостах. Полезно для отладки проблемы на конкретной машине.
    ```bash
    ansible-playbook my_playbook.yml --limit webserver1.example.com
    ```
*   `--start-at-task <имя таска>`: Начинает выполнение плейбука с указанной по имени задачи. Это экономит время, если проблема возникает в середине или конце большого плейбука, и вам не нужно каждый раз выполнять все предыдущие шаги.
    ```bash
    # Начать выполнение с задачи "Install php-fpm"
    ansible-playbook my_playbook.yml --start-at-task "Install php-fpm"
    ```

### Модули `fail` и `assert`

*   **`fail`**: Принудительно останавливает выполнение плейбука с ошибкой, если определенное условие истинно.
    ```yaml
    - name: Stop if Java is not installed
      fail:
        msg: "Java is not installed, but it is required."
      when: java_version_result.stdout == ""
    ```
*   **`assert`**: Проверяет, что определенные условия (инварианты) выполняются. Если нет — плейбук падает с ошибкой.
    ```yaml
    - name: Assert that the service is running
      assert:
        that:
          - service_status.status == 'running'
        fail_msg: "Service is not running!"
        success_msg: "Service is running as expected."
    ```

## Обработка ошибок

### `ignore_errors: true`

Позволяет продолжить выполнение плея, даже если задача завершилась с ошибкой. Полезно для некритичных операций.

```yaml
- name: Удаление временного файла (не падать, если его нет)
  file:
    path: /tmp/temp_file.txt
    state: absent
  ignore_errors: true
```

### `block`, `rescue`, `always`

Это аналог конструкции `try...catch...finally` в программировании.

*   **`block`**: Основной блок задач. Если любая из них провалится, выполнение перейдет в блок `rescue`.
*   **`rescue`**: Блок задач, который выполняется **только если** в `block` произошла ошибка. Используется для восстановления или логирования.
*   **`always`**: Блок, который выполняется **всегда** в конце, независимо от того, была ли ошибка.

```yaml
- name: Попытка выполнить рискованную операцию с восстановлением
  block:
    - name: Попытка запуска экспериментального сервиса
      service:
        name: experimental-service
        state: started

  rescue:
    - name: Если запуск не удался, вывести сообщение
      debug:
        msg: "Сервис experimental-service не запустился. Продолжаем без него."

  always:
    - name: Эта задача выполняется всегда
      debug:
        msg: "Завершение блока рискованной операции."
```

### `failed_when`

Позволяет переопределить стандартные условия сбоя задачи. По умолчанию, ненулевой код возврата команды означает ошибку. `failed_when` позволяет вам определить сбой по содержимому вывода или другим условиям.

```yaml
- name: Проверить, что команда не вернула определенный текст
  command: /usr/bin/my_script.sh
  register: script_result
  # Провалить задачу, если в выводе есть слово 'ERROR'
  failed_when: "'ERROR' in script_result.stdout"
```

### `changed_when`

Позволяет переопределить, когда задача считается "измененной" (`changed`). Многие команды (`shell`, `command`) по умолчанию всегда сообщают об изменении. `changed_when: false` — частый способ сделать их идемпотентными в отчетах.

```yaml
- name: Проверить наличие файла (это действие не меняет систему)
  command: ls /path/to/file.conf
  register: file_check
  changed_when: false # Не помечать как 'changed'
```

## Пример: Управление контейнерами Docker через systemd

Для управления множеством контейнеров как сервисов `systemd` целесообразно использовать системы управления конфигурацией, такие как Ansible. Это позволяет автоматизировать создание, настройку и запуск юнитов, а также использовать шаблоны для генерации однотипных конфигураций.

#### Шаблон юнита (Jinja2)

Можно создать универсальный шаблон `container.service.j2` для генерации юнитов. Этот шаблон может динамически подставлять параметры контейнера: имя, образ, порты, тома и переменные окружения.

```j2
[Unit]
Description={{ item.name }} container
Requires=docker.service
After=docker.service

[Service]
Restart=always
ExecStartPre=-/usr/bin/docker stop {{ item.name }}
ExecStartPre=-/usr/bin/docker rm {{ item.name }}
ExecStart=/usr/bin/docker run --rm --name {{ item.name }} \
{% if item.ports is defined %}
    {% for port in item.ports %}
    -p {{ port }} \
    {% endfor %}
{% endif %}
{% if item.volumes is defined %}
    {% for volume in item.volumes %}
    -v {{ volume }} \
    {% endfor %}
{% endif %}
{% if item.env is defined %}
    {% for var in item.env %}
    -e "{{ var }}" \
    {% endfor %}
{% endif %}
    {{ item.image }}
ExecStop=/usr/bin/docker stop {{ item.name }}

[Install]
WantedBy=multi-user.target
```

#### Переменные Ansible

В Ansible переменные для каждого контейнера можно описать в виде списка словарей, что делает конфигурацию наглядной и легко расширяемой.

**Пример (`vars/main.yml`):**
```yaml
containers:
  - name: app-nginx
    image: nginx:1.25
    ports:
      - "8080:80"
  - name: app-db
    image: mysql:8.0
    volumes:
      - "/opt/mysql/data:/var/lib/mysql"
    env:
      - "MYSQL_ROOT_PASSWORD=supersecret"
```

#### Задачи Ansible

Задача в плейбуке Ansible будет использовать этот шаблон для создания `.service` файлов для каждого контейнера из списка, перезагружать конфигурацию `systemd` и запускать сервисы.

```yaml
- name: Create systemd unit files for containers
  ansible.builtin.template:
    src: container.service.j2
    dest: "/etc/systemd/system/{{ item.name }}.service"
    owner: root
    group: root
    mode: '0644'
  loop: "{{ containers }}"
  notify: Reload systemd

- name: Start and enable container units
  ansible.builtin.systemd:
    name: "{{ item.name }}"
    state: restarted
    enabled: yes
  loop: "{{ containers }}"
```
*Обработчик `Reload systemd` должен содержать задачу `ansible.builtin.systemd: daemon_reload: yes`.*

Такой подход позволяет централизованно и декларативно управлять жизненным циклом контейнеров, интегрируя их в общую систему управления службами хоста.

## Пример: Управление Python-приложением (Gunicorn) через systemd

Аналогичный подход с `systemd` используется для управления жизненным циклом веб-приложений, не упакованных в контейнеры, например, написанных на Python с использованием фреймворка Flask или Django и запускаемых через WSGI-сервер Gunicorn.

#### Шаблон юнита Gunicorn (gunicorn.service.j2)

Шаблон для сервиса Gunicorn будет содержать специфичные для него параметры: рабочий каталог, путь к исполняемому файлу Gunicorn в виртуальном окружении, и пользователя, от которого запускается процесс.

```j2
[Unit]
Description=Gunicorn instance to serve {{ app_name }}
After=network.target

[Service]
User={{ service_user }}
Group={{ service_group }}
WorkingDirectory={{ app_path }}
ExecStart={{ app_path }}/venv/bin/gunicorn --workers 3 --bind unix:{{ app_path }}/{{ app_name }}.sock -m 007 wsgi:app
ExecReload=/bin/kill -s HUP $MAINPID
KillMode=mixed
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target

```
*   `WorkingDirectory`: указывает на корень проекта приложения.
*   `ExecStart`: запускает Gunicorn из виртуального окружения (`venv/bin/gunicorn`), создает сокет для связи с Nginx и указывает на WSGI-точку входа (`wsgi:app`).
*   `User/Group`: определяют пользователя и группу, от которых будет запущен сервис. Это важно для безопасности и прав доступа к файлам.

#### Задачи Ansible

Плейбук для развертывания такого сервиса будет состоять из следующих шагов:
1.  Создание `systemd`-юнита из шаблона.
2.  Перезагрузка демона `systemd` для применения изменений (через `handler`).
3.  Запуск и включение нового сервиса.

```yaml
- name: Create gunicorn systemd unit file
  ansible.builtin.template:
    src: gunicorn.service.j2
    dest: "/etc/systemd/system/{{ app_name }}.service"
    owner: root
    group: root
    mode: '0644'
  notify: Reload systemd

- name: Start and enable gunicorn service
  ansible.builtin.systemd:
    name: "{{ app_name }}"
    state: restarted
    enabled: yes
```

Затем в конфигурации Nginx настраивается проксирование запросов на unix-сокет, созданный Gunicorn:
```nginx
location / {
    proxy_pass http://unix:{{ app_path }}/{{ app_name }}.sock;
    # ... другие директивы proxy
}
```
Этот метод позволяет надежно управлять Python-приложениями как полноценными системными службами, автоматизируя их запуск, перезапуск и мониторинг.
