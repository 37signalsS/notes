# Ansible: Vault

### Определения

**Ansible Vault** — это встроенный в Ansible механизм для шифрования секретов, таких как пароли, API-ключи и SSL-сертификаты. Он позволяет безопасно хранить чувствительные данные (переменные) в системе контроля версий (Git) вместе с остальным кодом автоматизации.

### Базовые концепции

#### 1. Режимы работы: Шифрование файлов vs. строк

Ansible Vault поддерживает два основных подхода к шифрованию. Он может зашифровать **любой компонент Ansible**: плейбук, роль, инвентарь, шаблон или отдельную переменную. Расшифровка происходит прозрачно для пользователя, если предоставлен верный пароль.

##### Режим 1: Шифрование целых файлов (рекомендуемый)

Это основной и наиболее гибкий режим работы. Вы шифруете файл с переменными целиком.

**Преимущества:**
*   **Удобство управления:** Все связанные переменные находятся в одном месте.
*   **Смена пароля:** Пароль можно легко сменить для всего файла одной командой `rekey`, что критически важно для политик ротации секретов.
*   **Портативность:** Файл легко перемещать между проектами.

**Пример:** Шифрование файла с переменными для группы `main`.
```bash
# Файл group_vars/main.yml содержит:
# test: var1
# test2: var2
ansible-vault encrypt group_vars/main.yml
```
После выполнения команды содержимое файла будет заменено на зашифрованный блок.

##### Режим 2: Шифрование отдельных строк

Этот режим позволяет зашифровать конкретное значение и вставить его прямо в плейбук.

**Преимущества:**
*   Удобно для быстрых тестов, dev-окружений или когда нужно скрыть всего одну некритичную переменную.

**Недостатки:**
*   **Сложность смены пароля:** Если пароль от Vault изменится, вам придется вручную найти и перезашифровать **каждую** зашифрованную строку во всех плейбуках.
*   **Плохая масштабируемость:** Не подходит для управления большим количеством секретов.

**Пример:**
```bash
ansible-vault encrypt_string 'MySuperSecretValue' --name 'my_secret_var'
```
Команда вернет YAML-блок, который можно вставить в `vars` плейбука:
```yaml
my_secret_var: !vault |
  $ANSIBLE_VAULT;1.1;AES256
  396339623133326231336130393...
```

#### 2. Основные команды `ansible-vault`

*   **`encrypt <file>`**: Зашифровать существующий файл. После выполнения этой команды содержимое файла будет заменено на зашифрованный блок с заголовком, указывающим на используемый протокол шифрования и идентификатор (если указан).
*   **`decrypt <file>`**: Расшифровать файл (использовать с осторожностью, не коммитить расшифрованные файлы).
*   **`create <file>`**: Создать новый зашифрованный файл и открыть его для редактирования.
*   **`edit <file>`**: Безопасно отредактировать зашифрованный файл (он расшифровывается во временный файл, а после сохранения снова шифруется).
*   **`view <file>`**: Показать содержимое зашифрованного файла в консоли без редактирования.
*   **`rekey <file>`**: Сменить пароль для одного или нескольких зашифрованных файлов.

#### 3. Управление паролями

Ansible должен получить пароль от Vault для расшифровки данных во время выполнения плейбука. Если Ansible встретит зашифрованное место и не сможет его расшифровать (не будет предоставлен пароль или он окажется неверным), он остановится с ошибкой.

*   **Интерактивный ввод (`--ask-vault-pass`):**
    ```bash
    ansible-playbook my_playbook.yml --ask-vault-pass
    ```
    Ansible запросит пароль в консоли. Удобно для ручных запусков, но не подходит для автоматизации в CI/CD.

*   **Файл с паролем (`--vault-password-file <file>`):**
    Пароль хранится в текстовом файле, путь к которому передается Ansible.
    ```bash
    # Файл ~/.vault_pass содержит одну строку с паролем
    ansible-playbook my_playbook.yml --vault-password-file ~/.vault_pass
    ```
    Этот метод подходит для CI/CD, но сам файл с паролем нужно защищать (например, установить права 0600).

*   **Переменная окружения:**
    ```bash
    export ANSIBLE_VAULT_PASSWORD="MySecretPassword"
    ansible-playbook my_playbook.yml
    ```
    Ansible автоматически подхватит пароль из этой переменной.

*   **Исполняемый скрипт (самый гибкий способ):**
    В качестве файла с паролем можно указать исполняемый скрипт (с флагом `+x`). Ansible выполнит его и будет использовать его стандартный вывод (STDOUT) в качестве пароля.
    Это позволяет интегрировать Ansible с внешними системами хранения секретов (HashiCorp Vault, 1Password, Keycloak и т.д.).
    ```bash
    # vault.sh
    #!/bin/bash
    # Команда для получения секрета из внешнего хранилища
    /usr/local/bin/get-secret --name ansible-vault-password
    ```
    ```bash
    # Запуск
    ansible-playbook my_playbook.yml --vault-password-file ./vault.sh
    ```

#### 4. Использование нескольких хранилищ (`--vault-id`)

Для разделения секретов по окружениям (dev, stage, prod) или командам можно использовать несколько Vault, каждый со своим паролем. Это делается с помощью идентификаторов (`vault-id`).

**Как это работает:**

1.  При шифровании файла вы указываете его "имя" (ID) и источник пароля:
    ```bash
    # Шифруем файл для prod, пароль будет запрошен в консоли
    ansible-vault encrypt --vault-id prod@prompt group_vars/prod/secrets.yml
    
    # Шифруем файл для dev, пароль берется из файла
    ansible-vault encrypt --vault-id dev@./dev_pass.txt group_vars/dev/secrets.yml
    ```
    Зашифрованный файл будет содержать заголовок, указывающий на ID, который использовался при шифровании, например:
    ```
    $ANSIBLE_VAULT;1.1;AES256;prod
    ```

2.  При запуске плейбука вы указываете, какой пароль использовать для какого ID:
    ```bash
    ansible-playbook my_playbook.yml \
      --vault-id prod@~/.prod_vault_pass \
      --vault-id dev@~/.dev_vault_pass
    ```
    Ansible автоматически применит правильный пароль к каждому зашифрованному файлу. Если `--vault-id` не указан, используется хранилище по умолчанию.

##### Нюансы поведения `--vault-id`

По умолчанию Ansible довольно "снисходителен" к указанным `--vault-id`. Если вы предоставите несколько Vault ID и паролей (например, `id` и `non-id`):
```bash
ansible-playbook encrypted_playbook.yml --vault-id id@my_password.txt --vault-id non-id@another_password.txt
```
Ansible сначала попробует расшифровать файл паролем, соответствующим `id`, указанному в заголовке файла. Если это не сработает (или ID в заголовке файла отсутствует/не совпадает), он **переберет все остальные предоставленные пароли**, пытаясь найти подходящий. Это может быть как удобно, так и сбивать с толку.

Чтобы принудительно использовать только один конкретный `vault-id` для расшифровки, его нужно указать явно и убедиться, что он совпадает с тем, что был использован при шифровании.

### Практические сценарии

#### 1. Шифрование плейбука

Давайте зашифруем целый плейбук `playbook.yml` и запустим его.

1.  **Создадим простой плейбук `playbook.yml`:**
    ```yaml
    ---
    - name: Test Encrypted Playbook
      hosts: localhost
      connection: local
      tasks:
        - name: Show secret message
          ansible.builtin.debug:
            msg: "This is a secret message!"
    ```
2.  **Сохраним пароль в файл `vault_pass.txt`:**
    ```bash
    echo "MySuperSecretPassword" > vault_pass.txt
    chmod 600 vault_pass.txt # Важно защитить файл с паролем
    ```
3.  **Зашифруем плейбук с ID "test_id":**
    ```bash
    ansible-vault encrypt playbook.yml --vault-id test_id@vault_pass.txt
    ```
    После шифрования `playbook.yml` будет выглядеть примерно так:
    ```
    $ANSIBLE_VAULT;1.1;AES256;test_id
    616562366138653664323265323... (много зашифрованных данных)
    ```
4.  **Запустим зашифрованный плейбук:**
    ```bash
    ansible-playbook playbook.yml --vault-id test_id@vault_pass.txt
    ```
    Ansible прозрачно расшифрует плейбук и выполнит его.

#### 2. Безопасность в логах (`no_log: true`)

Даже если переменная зашифрована в Vault, ее значение может **попасть в логи** при выполнении плейбука, если задача выводит свои параметры в консоль.

**Пример проблемы:**
```yaml
- name: Create database user
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}" # db_password из Vault
```
В логе выполнения `ansible-playbook` с высоким уровнем детализации (`-vvv`) можно будет увидеть реальное значение `db_password`.

**Решение:**
Добавляйте `no_log: true` к любой задаче, которая работает с чувствительными данными. Эта директива скроет все параметры задачи из логов.

```yaml
- name: Create database user
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}"
  no_log: true # <-- ВАЖНО
```
Это маскирует *всю* задачу, а не только одно поле, но это необходимая мера безопасности.

#### Практический сценарий: Интеграция с Vagrant

*   **`vars/secrets.yml` **: Файл, содержащий зашифрованные секреты (например, `htpasswd_password`, `admin_ip`). Ansible определяет, что файл зашифрован, по заголовку `$ANSIBLE_VAULT;1.1;AES256`. Этот файл безопасно хранить в Git.
*   **`.vault_password`**: Простой текстовый файл, содержащий пароль для расшифровки `vars/secrets.yml`. **Этот файл никогда не должен попадать в Git.**
*   **`.gitignore`**: Стандартный файл Git, который должен содержать строку `.vault_password`, чтобы гарантировать, что "ключ" случайно не попадет в репозиторий.

##### Процесс работы: от `vagrant up` до Nginx

1.  **`Vagrantfile`**: Vagrant читает `Vagrantfile` и находит блок запуска Ansible. Ключевая строка `ansible.vault_password_file = ".vault_password"` дает Vagrant прямую инструкцию, какой файл использовать в качестве пароля для Vault.
    ```ruby
    # Vagrantfile
    machine.vm.provision :ansible do |ansible|
      ansible.playbook = "playbook.yml"
      ansible.vault_password_file = ".vault_password" # <--- КЛЮЧЕВОЙ МОМЕНТ
    end
    ```

2.  **Инструкция — `playbook.yml`**: Vagrant запускает Ansible, который читает плейбук. Директива `vars_files: - vars/secrets.yml` указывает, что нужно загрузить переменные из зашифрованного файла.

3.  **Расшифровка "на лету"**:
    *   Ansible видит заголовок `$ANSIBLE_VAULT` в `vars/secrets.yml`.
    *   Используя путь к паролю (`.vault_password`), полученный от Vagrant, он читает пароль.
    *   В оперативной памяти расшифровывает содержимое `vars/secrets.yml`. С этого момента переменные (например, `htpasswd_password`) доступны с их реальными значениями.

4.  **Выполнение задач**: Ansible начинает выполнять задачи, подставляя в них расшифрованные "на лету" значения переменных. Вместо простого копирования шаблона, плейбук может содержать более сложную логику, как в примере ниже.

    ```yaml
    # playbook.yml
    - name: Generate htpasswd file from vault
      ansible.builtin.command: >
        htpasswd -cb /etc/nginx/htpasswd vagrant '{{ htpasswd_password }}'
      args:
        creates: /etc/nginx/htpasswd
      no_log: true # <-- См. нюанс ниже

    - name: Configure Nginx with Self-Signed Certificate
      ansible.builtin.copy:
        dest: /etc/nginx/sites-enabled/site1.local.conf
        content: |
          server {
              listen 80;
              # ... (перенаправление на HTTPS)
          }

          server {
              listen 443 ssl;
              # ... (конфигурация SSL)

              location /admin {
                  allow {{ admin_ip }}; # <-- Сюда подставляется '192.168.77.1'
                  deny all;
                  auth_basic "Admin Area";
                  auth_basic_user_file /etc/nginx/htpasswd;
              }        
          }
      notify: Restart Nginx
    ```

    **Разбор примера:**
    *   **Задача 1: `Generate htpasswd file from vault`**
        *   `'{{ htpasswd_password }}'`: Сюда подставляется реальный пароль из расшифрованного Vault-файла.
        *   `no_log: true`: Скрывает вывод команды, чтобы пароль не попал в логи.

    *   **Задача 2: `Configure Nginx with Self-Signed Certificate`**
        *   `allow {{ admin_ip }};`: Внутри конфигурации Nginx переменная `admin_ip` из Vault используется для ограничения доступа к админ-панели.

##### Важные нюансы

*   Vagrant автоматизирует вызов, который вам пришлось бы делать вручную: `ansible-playbook --vault-password-file .vault_password playbook.yml`.

### Дополнительная информация

> **Важно:** Vault предназначен для хранения *существующих* секретов. Для генерации новых паролей используйте модуль `ansible.builtin.password`.

#### Предостережение: Шифрование общих ролей

Ansible Vault — отличный инструмент для защиты секретов, но его использование в общих ролях, которые распространяются или совместно используются с другими разработчиками, может вызвать проблемы.

**Проблема:** Если вы как разработчик зашифруете всю свою роль (например, `tasks/main.yml` или `templates/my_config.j2`) и отправите ее коллегам, они не смогут легко просматривать и отлаживать код роли, не имея пароля. Это значительно усложняет ревью кода, понимание логики и поиск ошибок, так как содержимое файлов будет нечитаемым.

**Рекомендация:** Шифруйте только те файлы или переменные, которые действительно содержат чувствительные данные (пароли, ключи, токены). Основную логику роли и шаблоны, не содержащие секретов, оставляйте в открытом виде. Секреты должны быть вынесены в отдельные зашифрованные файлы (например, `group_vars/all/vault.yml` или `host_vars/my_host/vault.yml`), которые используются ролями.
