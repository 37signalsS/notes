# Ansible

Ansible — это система с открытым исходным кодом для автоматизации развертывания программного обеспечения, управления конфигурацией и оркестрации. Он работает без агентов, подключаясь к узлам по SSH, и использует декларативные YAML-файлы (плейбуки) для описания желаемого состояния системы.

## Подготовка тестовой среды с Vagrant

Прежде чем устанавливать Ansible и писать плейбуки, крайне полезно настроить локальную тестовую среду. Это позволяет безопасно экспериментировать, не затрагивая рабочие серверы. [Vagrant](../Vagrant/vagrant_overview.md) — идеальный инструмент для этой цели.

Ниже приведен пример `Vagrantfile`, который создает две виртуальные машины:
1.  `control-node`: Машина, на которую мы установим Ansible.
2.  `server1`: Управляемый узел, на котором мы будем настраивать ПО.

Создайте файл с именем `Vagrantfile` и следующим содержимым:

```ruby
# -*- mode: ruby -*-
# vi: set ft=ruby :

Vagrant.configure("2") do |config|

  # 1. Контрольный узел (Ansible Control Node)
  config.vm.define "control-node" do |control_node|
    control_node.vm.box = "ubuntu/focal64"
    control_node.vm.hostname = "control-node"
    
    # Создаем приватную сеть, чтобы машины видели друг друга по статическим IP
    control_node.vm.network "private_network", ip: "192.168.50.10"
    
    # Синхронизируем локальную папку с плейбуками внутрь ВМ
    control_node.vm.synced_folder ".", "/vagrant"
    
    # Устанавливаем Ansible при первом запуске ВМ
    control_node.vm.provision "shell", inline: <<-SHELL
      apt-get update
      apt-get install -y software-properties-common
      add-apt-repository --yes --update ppa:ansible/ansible
      apt-get install -y ansible
    SHELL
  end

  # 2. Управляемый узел (Managed Node)
  config.vm.define "server1" do |server|
    server.vm.box = "ubuntu/focal64"
    server.vm.hostname = "server1"
    server.vm.network "private_network", ip: "192.168.50.11"
    
    # Включаем SSH-аутентификацию по паролю для демонстрационных целей
    server.vm.provision "shell", inline: <<-SHELL
      sed -i 's/PasswordAuthentication no/PasswordAuthentication yes/' /etc/ssh/sshd_config
      systemctl restart sshd
    SHELL
  end
end
```

**Ключевые директивы `Vagrantfile`:**
- `config.vm.define`: Определяет отдельную виртуальную машину.
- `config.vm.network "private_network", ip: "..."`: Назначает статический IP-адрес машине в изолированной сети. Это позволяет обращаться к машинам по предсказуемым адресам.
- `config.vm.synced_folder`: Монтирует текущую директорию (где лежит `Vagrantfile`) в папку `/vagrant` внутри виртуальной машины `control-node`. Это позволяет редактировать плейбуки на основной машине в удобном редакторе, а запускать их — из ВМ.
- `config.vm.provision "shell"`: Выполняет скрипт при создании машины. Мы используем это для автоматической установки Ansible на контрольный узел и для включения парольной аутентификации на управляемом узле.

После создания `Vagrantfile` выполните команду `vagrant up`. Vagrant скачает образ ОС и настроит обе виртуальные машины.

## Установка Ansible

Ansible написан на Python и требует его наличия на **контрольном узле**. Современные версии Ansible требуют Python 3.

Если вы не используете Vagrant-провижининг, как показано выше, вы можете установить Ansible вручную.

### Debian/Ubuntu
В стандартных репозиториях Ubuntu может быть устаревшая версия Ansible. Для установки актуальной версии рекомендуется использовать официальный PPA (Personal Package Archive).

```bash
sudo apt update
sudo apt install -y software-properties-common
# Добавляем репозиторий от команды Ansible
sudo add-apt-repository --yes --update ppa:ansible/ansible
# Устанавливаем Ansible
sudo apt install -y ansible
```

### CentOS/RHEL
```bash
sudo yum install -y epel-release
sudo yum install -y ansible
```

### С помощью `pip` (универсальный способ)
Этот способ позволяет установить последнюю версию Ansible в изолированное окружение.
```bash
python3 -m venv ansible_env
source ansible_env/bin/activate
pip install ansible
```

### Проверка установки и версии

После установки проверьте, что все работает, командой `ansible --version`.

```
ansible 2.9.6
  config file = /etc/ansible/ansible.cfg
  configured module search path = ['/home/vagrant/.ansible/plugins/modules', '/usr/share/ansible/plugins/modules']
  ansible python module location = /usr/lib/python3/dist-packages/ansible
  executable location = /usr/bin/ansible
  python version = 3.8.10 (default, Nov 26 2021, 20:14:08) [GCC 9.3.0]
```
Вывод показывает версию Ansible, путь к конфигурационному файлу и версию Python, которую он использует.

**О версиях Ansible:**
Существует два типа пакетов:
*   `ansible-core`: Минимальный пакет, содержащий ядро Ansible и базовые модули. Версии нумеруются как `2.11`, `2.12`, и т.д.
*   `ansible`: Пакет "community edition", который включает `ansible-core` и большой набор готовых коллекций и модулей от сообщества. Его версии нумеруются иначе (`4.x.x`, `5.x.x`). Например, `ansible 5.x` может содержать `ansible-core 2.12`.

Для обучения мы используем пакет `ansible`, так как он включает все необходимое "из коробки".

### Файл конфигурации (`ansible.cfg`)

Файл `ansible.cfg` позволяет централизованно управлять настройками самого Ansible, избавляя от необходимости каждый раз указывать одни и те же параметры в командной строке. "Дзен Ansible" заключается в том, чтобы выносить общие для всех проектов настройки в этот файл.

**Иерархия и приоритет**

Ansible ищет файл `ansible.cfg` в нескольких местах в строгом порядке. Будет использован **первый найденный** файл. Порядок приоритета (от высшего к низшему):
1.  **Переменная окружения `ANSIBLE_CONFIG`**: Путь к файлу конфигурации задан явно. Это самый приоритетный способ.
2.  **`ansible.cfg` в текущей директории**: Наличие `ansible.cfg` в корневой папке вашего проекта — самый распространенный и рекомендуемый способ, так как он позволяет иметь индивидуальные настройки для каждого проекта.
3.  **`~/.ansible.cfg`**: Скрытый файл конфигурации в домашней директории текущего пользователя.
4.  **/etc/ansible/ansible.cfg**: Глобальный конфигурационный файл для всей системы с самым низким приоритетом.

**Пример `ansible.cfg` для проекта:**
```ini
[defaults]
# Указываем путь к файлу инвентаря по умолчанию.
# Больше не нужно писать "-i <путь>" в каждой команде.
inventory = inventory.ini

# Общие параметры для SSH-подключений
[ssh_connection]
private_key_file = ~/.ssh/vagrant_key
host_key_checking = False

# Подавляет предупреждения о том, что Ansible управляет данным хостом впервые.
[defaults]
deprecation_warnings = False
```
- **`inventory`**: Задает путь к файлу инвентаря по умолчанию для проекта.
- **`private_key_file`**: Указывает путь к приватному SSH-ключу, который будет использоваться для всех хостов, если для них не определен другой ключ.
- **`host_key_checking`**: Отключает проверку SSH-ключа хоста при первом подключении. Удобно для тестовых сред, но **не рекомендуется** для продуктивных из соображений безопасности.

> **Проблема с правами на Windows**
> При использовании Vagrant на хосте с Windows, общая папка может быть смонтирована в Linux VM с правами `777` (world-writable). Из соображений безопасности Ansible проигнорирует `ansible.cfg` в такой директории. Решение — запускать `ansible` из другой директории с правильными правами или исправить права доступа к папке внутри ВМ.


### Файл инвентаризации (`inventory`)

Файл инвентаризации (inventory) — это основа Ansible, определяющая хосты и группы хостов, которыми вы управляете. Хотя можно перечислять просто IP-адреса, **рекомендуется** использовать псевдонимы (aliases) для каждого хоста. Это делает плейбуки и вывод команд гораздо более читаемыми.

Создадим файл `inventory.ini`:
```ini
# Псевдоним хоста
server1
```
Сам адрес и параметры подключения для `server1` будут заданы через переменные.

#### Способы определения параметров подключения

Параметры подключения (адрес, пользователь, пароль, ключ, тип подключения) задаются как переменные, привязанные к хосту.

**1. Переменные в файле инвентаризации (Рекомендуемый способ)**

Это наиболее наглядный и управляемый способ. Вместо указания параметров в одной строке, как в старых версиях, используйте переменные `ansible_host`, `ansible_user` и т.д.

```ini
# inventory.ini

[servers]
# Имя хоста, которое вы будете использовать в плейбуках
server1 ansible_host=192.168.50.11 ansible_user=vagrant ansible_ssh_pass=vagrant

[servers:vars]
# Эти переменные будут применены ко всем хостам в группе [servers]
# ansible_user=vagrant
# ansible_ssh_pass=vagrant
```
- `server1`: Псевдоним хоста.
- `ansible_host`: IP-адрес или DNS-имя целевой машины.
- `ansible_user`: Имя пользователя для SSH-подключения.
- `ansible_ssh_pass`: Пароль для SSH-подключения.

> **Внимание:** Хранение паролей в открытом виде в файле инвентаризации **крайне небезопасно**. Этот метод следует использовать только в изолированных учебных средах (например, с Vagrant, где по умолчанию используется пара `vagrant`/`vagrant`). Для реальных проектов **всегда** используйте [Ansible Vault](ansible_vault.md).

**2. Использование SSH-ключей (Самый безопасный способ)**

Наиболее безопасный и предпочтительный метод — использование SSH-ключей.

```ini
[servers]
prod_server ansible_host=195.2.73.85 ansible_user=root ansible_port=2414 ansible_ssh_private_key_file=~/.ssh/prod_id_rsa
```

> **Как найти нужную переменную?**
> Имена переменных, таких как `ansible_ssh_private_key_file`, не всегда очевидны. Их можно найти во встроенной документации для соответствующего плагина подключения. Например, чтобы увидеть все параметры для SSH-подключения, используйте команду: `ansible-doc -t connection ssh`.

### Типы подключений (Connection Plugins)

Хотя по умолчанию Ansible использует SSH, его архитектура является модульной. За способ подключения к управляемому узлу отвечают **плагины подключения (connection plugins)**.

Узнать, какие плагины доступны в вашей системе, можно с помощью команды `ansible-doc`:
```bash
ansible-doc -t connection -l
```
Вы увидите список, включающий:
- `ssh`: Стандартное подключение (по умолчанию).
- `local`: Для выполнения задач на самом контрольном узле.
- `docker`: Для подключения к Docker-контейнерам напрямую через Docker API.
- `kubernetes.core.kubectl`: Для выполнения команд через `kubectl exec`.
- `winrm`: Для подключения к машинам Windows.

Плагин для хоста задается через переменную `ansible_connection`.

**Пример смешанного инвентаря:**
Предположим, у нас есть VM `server1` и Docker-контейнер `my-app-container`.

```ini
# inventory.ini

[web]
server1 ansible_host=192.168.50.11 ansible_connection=ssh

[docker_apps]
app1 ansible_host=my-app-container ansible_connection=docker

[all:vars]
ansible_user=vagrant
ansible_ssh_pass=vagrant
```
- Для `server1` мы явно указываем `ansible_connection=ssh` (хотя это значение по умолчанию).
- Для `app1` мы указываем `ansible_connection=docker`, а в `ansible_host` передаем имя контейнера.
- Ansible будет использовать разные методы для подключения к этим двум хостам, но в плейбуке вы можете оперировать ими одинаково (например, `hosts: web, docker_apps`).

> **Важно: FQCN для плагинов**
> В Ansible 2.9 и старше можно было использовать короткие имена, например `docker`. В современных версиях (2.10+ и community-сборках 3+) требуется указывать полное имя коллекции (FQCN): `community.docker.docker`. Если короткое имя не работает, `ansible-doc` подскажет правильное полное имя.

## Ad-Hoc Команды: Первое знакомство
Для подробной информации и примеров см. [Ansible: Ad-Hoc команды и Факты](ansible_ad_hoc_commands_and_facts.md).

Ad-hoc команды — это быстрый способ выполнить одну задачу на управляемых узлах без написания плейбука. Они идеально подходят для проверки подключения и сбора информации.

**1. Проверка инвентаря**

Прежде всего, убедимся, что Ansible видит наши хосты. Для этого используется флаг `--list-hosts` и `-i` для указания пути к нашему файлу инвентаря.

```bash
# 'all' — это паттерн, означающий "все хосты"
ansible all -i inventory.ini --list-hosts

# Ожидаемый вывод:
#   hosts (1):
#     192.168.50.5
```
Если список пуст, проверьте путь к файлу и его содержимое.

**2. Проверка подключения (`ping`)**

Модуль `ping` — это основной способ проверить, что Ansible может подключиться к хосту, выполнить на нем Python-код и получить ответ.

```bash
ansible all -i inventory.ini -m ping
```

**3. Решение проблем с подключением**

При первом запуске вы, скорее всего, столкнетесь с ошибкой:

*   **`Permission denied`**: Это стандартная SSH-ошибка, означающая, что у Ansible нет прав на подключение. Чаще всего это связано с необходимостью ввести пароль.
    *   **Решение 1: Интерактивный ввод пароля.** Используйте флаг `--ask-pass`.
        ```bash
        ansible all -i inventory.ini -m ping --ask-pass
        ```
    *   **Проблема с `sshpass`**: Если вы получили ошибку `Failed to install required sshpass program`, значит, на вашей управляющей машине отсутствует утилита `sshpass`, необходимая Ansible для программной передачи пароля.
        *   **Решение**: Установите ее.
            ```bash
            # Для Debian/Ubuntu
            sudo apt install sshpass
            ```
    *   **Решение 2: Указание пароля в инвентаре.** Как показано выше, вы можете добавить `ansible_ssh_pass` в файл инвентаря, чтобы избежать ручного ввода пароля. **Помните о рисках безопасности.**

**Успешный результат `ping`:**

После успешного выполнения вы увидите JSON-ответ, подтверждающий, что соединение установлено.
```json
"192.168.50.5 | SUCCESS => {
    "changed": false, 
    "ping": "pong"
}
```
`"ping": "pong"` — это сигнал того, что все работает как надо.

**4. Выполнение команд (`command`, `shell` и `raw`)**

Для выполнения произвольных команд на удаленных узлах существует несколько модулей, каждый для своего уровня задач.

*   `command`: для простых команд без конвейеров (`|`), перенаправлений (`>`) или переменных окружения. Это модуль по умолчанию: если вы не указываете модуль через `-m`, Ansible попытается выполнить вашу строку как `command`.
*   `shell`: для выполнения сложных скриптов и команд в полноценной оболочке узла. Позволяет использовать пайпы, перенаправления и т.д.
*   `raw`: самый низкоуровневый способ. Просто выполняет команду через SSH без какой-либо Python-обертки. Ему не нужен Python на целевом хосте, что делает его ключевым инструментом для первоначальной настройки.

```bash
# Получить время работы системы (безопасно)
ansible all -i inventory.ini -a "uptime" # '-m command' подразумевается

# Посмотреть содержимое корневого каталога с помощью shell
ansible all -i inventory.ini -m shell -a "ls -la /"
```
- `-m`: указывает на используемый модуль.
- `-a`: передает аргументы в модуль.

> **Внимание:** Используйте `shell` и `raw` с осторожностью. Они часто нарушают **идемпотентность**, так как выполняют команды императивно, а не декларативно. Каждый запуск будет помечен как `changed`, и Ansible не сможет проверить, нужно ли действие на самом деле. Это "грязные хаки", которых стоит избегать в пользу специализированных модулей, если это возможно. Их основное применение — задачи, для которых нет модуля, или первоначальная установка Python.

## Плейбуки (Playbooks)

Плейбук — это YAML-файл, описывающий упорядоченный набор задач для выполнения на хостах. Это основной инструмент для оркестрации.

Для более подробной информации о структуре, директивах и примерах использования см. [Ansible: Плейбуки](ansible_playbooks.md) и [Выполнение плейбуков](ansible_playbook_execution.md).

### Идемпотентность

**Идемпотентность** — это фундаментальный принцип Ansible. Он гарантирует, что повторное выполнение операции не приведет к изменениям, если система уже находится в целевом состоянии.

*   `ok` (зеленый): Изменения не требуются.
*   `changed` (желтый): Были внесены изменения для достижения целевого состояния.

### Роли

Роли — это стандартный способ организации и переиспользования кода в Ansible. Они инкапсулируют задачи, переменные и шаблоны в модульную структуру.

Для более подробной информации см. [Ansible: Роли](ansible_roles.md).

**Создание роли:**

```bash
ansible-galaxy init <имя_роли>
```

**Структура роли:**

*   `tasks/main.yml`: Основной файл с задачами.
*   `handlers/main.yml`: Обработчики для этой роли.
*   `defaults/main.yml`: Переменные по умолчанию (самый низкий приоритет).
*   `vars/main.yml`: Переменные роли (высокий приоритет).
*   `files/`: Статические файлы для копирования на узлы.
*   `templates/`: Шаблоны Jinja2 (`.j2`).
*   `meta/main.yml`: Метаданные роли и зависимости.

### Шаблоны (Jinja2)

Шаблоны позволяют создавать динамические конфигурационные файлы с использованием переменных.

```yaml
- name: Create config from template
  template:
    src: config.j2 # Файл шаблона в директории templates
    dest: /etc/app/config.conf
```

### Установка Python на "голые" хосты (Bootstrapping)

Большинство модулей Ansible требуют наличия Python на целевом хосте. Если его нет, вы столкнетесь с ошибками. Проблема решается с помощью модуля `raw` и специальной структуры плейбука.

Модуль `raw` выполняет команду через SSH "как есть", без использования Python. Это позволяет установить Python на "голую" систему.

**Стратегия с двумя плеями:**

Чтобы автоматизировать этот процесс, плейбук разделяют на два плея:

1.  **Первый плей (установка Python):**
    *   Отключает сбор фактов (`gather_facts: false`), так как модуль `setup` (который собирает факты) тоже требует Python.
    *   Использует модуль `raw` для вызова пакетного менеджера (`apt`, `yum`) и установки Python.

2.  **Второй плей (основная настройка):**
    *   Выполняется после первого. К этому моменту Python уже установлен.
    *   Включает сбор фактов и использует стандартные Python-модули для дальнейшей настройки системы.

**Пример плейбука для bootstrapping:**

```yaml
---
- name: Play 1 - Bootstrap Python
  hosts: no_python_hosts
  become: true
  gather_facts: false # <-- Очень важно!

  tasks:
    - name: Install Python3 using raw command
      ansible.builtin.raw: apt-get update && apt-get install -y python3
      when: ansible_os_family == "Debian" # Пример для Debian-based систем

    - name: Install Python3 using raw command (RedHat)
      ansible.builtin.raw: yum install -y python3
      when: ansible_os_family == "RedHat"

- name: Play 2 - Main configuration
  hosts: no_python_hosts
  become: true
  # Здесь 'gather_facts' уже можно не указывать (по умолчанию true)
  
  tasks:
    - name: Now we can use regular modules
      ansible.builtin.ping: {}
```
Этот подход позволяет полностью автоматизировать подготовку хостов с нуля.

### Безопасность

Управление безопасностью — критически важный аспект при работе с Ansible.

*   **Управление привилегиями (`sudo`):** Правильная настройка `sudo` и использование выделенного пользователя являются основой безопасности.
    *   См. [Рекомендации по безопасности и использованию Sudo](ansible_security_best_practices.md)

*   **Шифрование секретов (`vault`):** **Всегда** используйте `ansible-vault` для шифрования чувствительных данных (паролей, токенов, ключей API) вместо хранения их в открытом виде.
    *   См. [Ansible: Vault](ansible_vault.md).

### Качество кода: Ansible Lint

Используйте `ansible-lint` для статического анализа плейбуков и ролей на соответствие лучшим практикам. Это также помогает выявлять потенциальные проблемы безопасности на раннем этапе.

`ansible-lint` проверяет код на соответствие набору правил, выявляя синтаксические и стилистические ошибки.

**Практическая польза:**
*   Очень полезен при первоначальном освоении Ansible, так как помогает усвоить правильный стиль написания задач и плейбуков.
*   Выдает конкретные замечания и предложения по исправлению.

**Ограничения:**
*   Содержит ограниченный набор правил (около 18), которые в основном являются тривиальными.
*   Для опытных пользователей, уже знакомых с лучшими практиками, его польза снижается.

**Установка:**
```bash
pip install ansible-lint
```

**Проверка плейбука:**
```bash
ansible-lint my_playbook.yml
```

### Включение TCP BBR на Ubuntu

Этот плейбук автоматизирует включение алгоритма контроля перегрузки [TCP BBR](../Networking/networks.md), что может значительно улучшить производительность сети.

```yaml
- name: Enable TCP BBR on Ubuntu
  hosts: all
  become: yes
  tags:
    - system
    - network
    - bbr
  tasks:
    - name: Ensure tcp_bbr module is loaded
      modprobe:
        name: tcp_bbr
        state: present

    - name: Make tcp_bbr module load on boot
      lineinfile:
        path: /etc/modules-load.d/bbr.conf
        line: tcp_bbr
        create: yes
        mode: '0644'

    - name: Apply BBR sysctl settings
      sysctl:
        name: "{{ item.key }}"
        value: "{{ item.value }}"
        sysctl_set: yes
        state: present
        reload: yes
      with_items:
        - { key: 'net.core.default_qdisc', value: 'fq' }
        - { key: 'net.ipv4.tcp_congestion_control', value: 'bbr' }
