# Ansible Vault: Использование нескольких хранилищ (Multi-Vault)

## Определения

- **Vault ID (Идентификатор хранилища)**: Текстовая метка (например, `dev`, `prod`, `common`), которая связывает зашифрованные данные с конкретным источником пароля. Это позволяет Ansible (инструмент автоматизации конфигураций) однозначно определить, какой ключ использовать для расшифровки.
- **Метка (Label)**: Имя Vault ID, указываемое перед символом `@` в аргументах командной строки (CLI — Command Line Interface) или в конфигурационных файлах.
- **Identity List (Список идентификаторов)**: Перечень пар `метка@источник`, определяющий все доступные ключи и их происхождение для текущего сеанса автоматизации.
- **AES-256**: Продвинутый стандарт шифрования (Advanced Encryption Standard) с длиной ключа 256 бит. В Ansible Vault используется для обеспечения симметричной защиты данных.

## Основные концепции

### Зачем нужно несколько хранилищ

В крупных проектах секреты разделены по уровням доступа или окружениям. Использование разных паролей для разработки (`dev`) и эксплуатации (`prod`) — критический стандарт безопасности. 
1. **Безопасность**: Команда разработки может иметь доступ только к `dev`-секретам, не имея технической возможности расшифровать `prod`-данные. Это реализует принцип наименьших привилегий.
2. **Производительность**: При использовании Vault ID инструмент Ansible мгновенно выбирает нужный ключ из памяти (RAM — Random Access Memory), не тратя время на перебор всех известных паролей для каждого файла.
3. **Аудит и отладка**: В логах и заголовках файлов четко видно, какой уровень доступа требуется для выполнения конкретной задачи.

### Преимущества и возможности (Ansible 2.4+)

Начиная с версии **Ansible 2.4**, используется формат заголовка `$ANSIBLE_VAULT;1.2;AES256;label`, где метка (label) встроена непосредственно в первую строку зашифрованного контента.

- **Строгое соответствие (`vault_id_match`)**: Параметр `vault_id_match = True` в файле настроек `ansible.cfg` заставляет систему использовать *только* тот ключ, который соответствует метке в заголовке. Это предотвращает попытки расшифровки "чужими" паролями и ускоряет работу.
- **Разнообразие источников**:
    - `prompt`: Интерактивный запрос пароля у пользователя.
    - `путь/к/файлу`: Чтение статического пароля из файла на диске.
    - `путь/к/скрипту.sh`: Выполнение клиентского скрипта для получения секрета из внешних систем управления (например, HashiCorp Vault или AWS Secrets Manager).

## Практические сценарии

### Сценарий 1: Создание секретов с привязкой к окружению

При создании секрета через CLI необходимо указывать идентификатор, чтобы Ansible прописал правильную метку версии 1.2 в заголовок.

```bash
# Создание файла для эксплуатации (пароль будет запрошен интерактивно)
ansible-vault create --vault-id prod@prompt group_vars/prod/vault.yml

# Инлайновое шифрование строки для разработки (через YAML-тег !vault)
ansible-vault encrypt_string --vault-id dev@.vault_pass_dev 'secret_val' --name 'vault_db_pass'
```

### Сценарий 2: Глобальная настройка в ansible.cfg

Рекомендуемый способ для командной разработки, позволяющий избежать ручной передачи аргументов при каждом запуске плейбука.

```ini
# ansible.cfg
[defaults]
# Список идентификаторов и источников
vault_identity_list = dev@.vault_pass_dev, prod@scripts/vault_client.sh, common@prompt

# Включение строгого соответствия меток (стандарт безопасности 2024-2025)
vault_id_match = True
```

### Сценарий 3: Запуск плейбука в CI/CD

В пайплайнах (CI/CD — Continuous Integration / Continuous Delivery — непрерывная интеграция и доставка) список идентификаторов можно передать через переменную окружения (ENV — Environment Variable).

```bash
# Передача списка источников через системную переменную окружения
export ANSIBLE_VAULT_IDENTITY_LIST="dev@/tmp/dev.pass, prod@/tmp/prod.pass"
ansible-playbook site.yml
```

### Сценарий 4: Ротация ключей для конкретного ID

Команда `rekey` позволяет обновить мастер-пароль или сменить метку для существующих секретов, сохраняя привязку к Vault ID.

```bash
# Смена пароля для файлов с меткой 'dev'
ansible-vault rekey --vault-id dev@old_pass.txt --new-vault-id dev@new_pass.txt group_vars/dev/vault.yml
```
