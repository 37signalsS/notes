# Ansible Vault: Использование нескольких хранилищ (Multi-Vault)

## Определения

- **Vault ID (Идентификатор хранилища)**: Текстовая метка (например, `dev`, `prod`, `common`), которая связывает зашифрованные данные с конкретным источником пароля.
- **Метка (Label)**: Имя Vault ID, указываемое перед символом `@` в аргументах командной строки или конфигурации.

## Основные концепции

### Зачем нужно несколько хранилищ

В крупных проектах секреты часто разделены по уровням доступа или окружениям. Использование разных паролей для `development` и `production` — стандарт безопасности. Без использования Vault ID Ansible пришлось бы перебирать все известные пароли для каждого файла, что замедляет работу и усложняет аудит.

### Преимущества и возможности

Современные версии Ansible (2.4+) используют формат заголовка `$ANSIBLE_VAULT;1.2;AES256;label`, который позволяет:
- **Мгновенно выбирать ключ**: Ansible видит метку (например, `prod`) и сразу запрашивает нужный пароль из соответствующего источника.
- **Использовать разные источники**:
    - `prompt`: Интерактивный ввод.
    - `path/to/file`: Чтение из файла.
    - `path/to/script.sh`: Выполнение скрипта (клиента), который возвращает пароль (например, из HashiCorp Vault или 1Password).
- **Строгое соответствие**: Параметр `vault_id_match = True` в `ansible.cfg` заставляет Ansible использовать *только* тот пароль, который соответствует метке в заголовке файла, исключая попытки расшифровки другими ключами.
- **Безопасность**: Команда разработки может иметь доступ только к `dev`-секретам, не имея технической возможности расшифровать `prod`.

### Рекомендации по именованию

Для прозрачности рекомендуется:
1. Использовать префикс `vault_` для всех зашифрованных переменных (например, `vault_api_key`).
2. В коде ссылаться на них через обычные переменные: `api_key: "{{ vault_api_key }}"`. Это позволяет легко отличить секреты от обычных данных в коде плейбуков.

## Практические сценарии

### Сценарий 1: Создание и шифрование с метками

Синтаксис: `--vault-id <label>@<source>`.

```bash
# Создание нового файла для продакшена (пароль будет запрошен)
ansible-vault create --vault-id prod@prompt group_vars/prod/vault.yml

# Шифрование существующего файла для разработки (пароль из файла)
ansible-vault encrypt --vault-id dev@.vault_pass_dev group_vars/dev/vault.yml
```

### Сценарий 2: Настройка в `ansible.cfg`

Для автоматизации можно определить список источников и включить строгое соответствие меток.

```ini
# ansible.cfg
[defaults]
# Список Vault ID: метка@источник
vault_identity_list = dev@.vault_pass_dev, prod@scripts/vault_client.sh

# Рекомендуется: использовать только подходящий ключ для каждого файла
vault_id_match = True
```

### Сценарий 3: Шифрование отдельных строк (Inline)

В современных проектах предпочтительнее шифровать конкретные переменные, а не целые файлы, чтобы Git-диффы оставались читаемыми.

```bash
ansible-vault encrypt_string --vault-id prod@prompt 'secret_password' --name 'vault_db_password'
```

### Сценарий 4: Запуск плейбука через переменные окружения

В CI/CD удобно передавать список источников через переменные окружения.

```bash
export ANSIBLE_VAULT_IDENTITY_LIST="dev@.tmp_dev_pass, prod@.tmp_prod_pass"
ansible-playbook site.yml
```

### Сценарий 5: Ротация пароля для конкретного ID

Команда `rekey` позволяет обновить пароль для файлов, принадлежащих конкретному хранилищу.

```bash
ansible-vault rekey --vault-id dev@old_pass.txt --new-vault-id dev@new_pass.txt secrets.yml
```
