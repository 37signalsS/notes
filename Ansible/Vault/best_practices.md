# Ansible Vault: Лучшие практики

## Определения

- **Лучшие практики Vault**: Набор правил и техник, направленных на минимизацию риска утечки секретов как в состоянии покоя (в Git), так и во время выполнения плейбука (в логах, кэше).

## Основные концепции

### Принцип минимального раскрытия

Основная цель при работе с секретами — они должны оставаться зашифрованными как можно дольше и находиться в открытом виде в памяти как можно меньше времени. Каждая операция, которая может привести к их записи в лог или на диск, является потенциальной уязвимостью.

Инструменты Ansible, такие как `no_log` и `cacheable: false`, являются прямым следствием этого принципа.

## Практические сценарии

### Сценарий 1: Предотвращение утечек в логах (`no_log: true`)

Даже если переменная зашифрована, ее значение может **попасть в логи** при выполнении плейбука, если задача выводит свои параметры в консоль. Это самая частая ошибка.

**Проблема:**

```yaml
- name: Create database user # ЗАДАЧА УЯЗВИМА
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}" # db_password из Vault, но будет виден в логах
```

**Решение:**
Добавляйте `no_log: true` к **любой задаче**, которая прямо или косвенно работает с чувствительными данными. Эта директива полностью скроет параметры и вывод задачи из консоли.

```yaml
- name: Create database user # ЗАДАЧА ЗАЩИЩЕНА
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}"
  no_log: true # <-- ВАЖНО
```

### Сценарий 2: Безопасная организация репозитория

- **Разделяйте конфигурацию и секреты**: Храните секреты в отдельных, специально названных файлах (например, `prod.vault.yml`) в каталогах `group_vars/` или `host_vars/`.
- **Не шифруйте код**: Шифруйте только файлы с переменными, а не `.yml` файлы с задачами. Логика автоматизации должна оставаться в открытом виде для удобства чтения и аудита.
- **Используйте `.gitignore`**: Всегда исключайте из Git (система контроля версий) файлы с паролями (`vault_pass.txt`), не зашифрованные секреты и временные файлы отладки.

### Сценарий 3: Предотвращение кэширования секретов

По умолчанию Ansible кэширует факты, собранные с хостов. Если вы получаете секрет из внешнего источника и сохраняете его как факт, он может быть записан на диск.

```yaml
- name: Получение секрета из внешнего источника
  ansible.builtin.set_fact:
    api_token: "{{ lookup('env', 'API_TOKEN') }}" # API — Application Programming Interface
    cacheable: false # <-- Запрещает кэширование этого факта
  no_log: true
```

### Сценарий 4: Шаблоны с секретами — явная уязвимость

**Критическое предупреждение:** Когда `ansible.builtin.template` рендерит Jinja2-шаблон, содержащий `{{ vault_var }}`, итоговый файл на диске (`dest`) содержит расшифрованный секрет в открытом виде. Vault защищает данные только в репозитории; на целевой машине пароль лежит в открытом виде.

```yaml
- name: Создание конфигурационного файла с секретом # УЯЗВИМО
  ansible.builtin.template:
    src: docker-compose.j2   # содержит {{ db_password }}
    dest: /opt/app/docker-compose.yml
    mode: '0600'             # ограничивает доступ, но в открытом виде на диске остаётся
  no_log: true               # скрывает вывод, но не защищает файл
```

`mode: '0600'` и `no_log: true` — необходимые, но недостаточные меры. Они ограничивают доступ к уже расшифрованному файлу и скрывают утечку из логов, но не устраняют корневую проблему: секрет записан на диск.

### Сценарий 5: Docker Compose/Swarm — замена переменных на Docker Secrets

Типичная ошибка — рендерить `docker-compose.yml` с подстановкой пароля из Vault напрямую в `environment`:

```yaml
# docker-compose.j2 — УЯЗВИМО: пароль попадёт в файл на диске
services:
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_PASSWORD: {{ app_db_users[0].password }}
```

Правильный подход: в шаблоне указывать `_FILE`-суффикс и внешний секрет, а сам секрет создавать через `community.docker.docker_secret`:

```yaml
# docker-compose.j2 — БЕЗОПАСНО: пароль только в RAM (Random Access Memory — оперативная память) Swarm
services:
  db:
    image: postgres:16-alpine
    secrets:
      - db_password
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password

secrets:
  db_password:
    external: true
```
```yaml
# Плейбук: создание секрета в Swarm перед deploy стека
- name: Создание секрета Docker Swarm из Vault
  community.docker.docker_secret:
    name: db_password
    data: "{{ app_db_users[0].password }}"
    state: present
  no_log: true
```

При таком подходе пароль из Vault попадает в память менеджера Swarm (шифруется с помощью алгоритма консенсуса Raft) и монтируется в контейнер через tmpfs (Temporary File System — временная файловая система в оперативной памяти) — на диск секрет не записывается никогда.
