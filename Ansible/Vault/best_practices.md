# Ansible Vault: Лучшие практики

## Безопасность в логах (`no_log: true`)

Даже если переменная зашифрована в Vault, ее значение может **попасть в логи** при выполнении плейбука, если задача выводит свои параметры в консоль.

**Пример проблемы:**

```yaml
- name: Create database user
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}" # db_password из Vault
```

В логе выполнения `ansible-playbook` с высоким уровнем детализации (`-vvv`) можно будет увидеть реальное значение `db_password`.

**Решение:**
Добавляйте `no_log: true` к любой задаче, которая работает с чувствительными данными. Эта директива скроет все параметры задачи из логов.

```yaml
- name: Create database user
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}"
  no_log: true # <-- ВАЖНО
```
Это маскирует *всю* задачу, а не только одно поле, но это необходимая мера безопасности. Также избегайте отладочного вывода секретов (например, `debug` с переменными, содержащими пароли).

## Организация и выполнение

### 1. Структура репозитория
- **Разделяйте конфигурации и секреты**: Чувствительные данные храните в отдельных файлах (`*.vault.yml`) в `group_vars/` или `host_vars/`, а не в коде ролей.
- **Используйте `.gitignore`**: Исключайте из Git файлы с паролями (`vault_pass.txt`), кэш инвентаря и временные файлы.
- **Не храните секреты в `sample` файлах**: Вместо этого держите шаблоны без значений.

### 2. Минимизация экспозиции при выполнении
- **Не используйте `--extra-vars`** для передачи секретов в открытом виде. Загружайте их из зашифрованного файла:
  ```bash
  ansible-playbook site.yml -e @prod/group_vars/all/app.vault.yml
  ```
- **Не кэшируйте секреты в фактах**. При использовании `set_fact` для временного хранения секрета отключайте кэширование:
  ```yaml
  - name: Секрет из внешнего источника
    set_fact:
      db_password: "{{ lookup('env', 'DB_PASS') }}"
      cacheable: false
    no_log: true
  ```
- **Контролируйте права доступа** к файлам, созданным из шаблонов с секретами:
  ```yaml
  - template:
      src: config.j2
      dest: /etc/app/config.yml
      mode: '0600'
    no_log: true
  ```

### 3. Безопасная передача ключа и ротация
- **В CI/CD** читайте пароль из защищенного хранилища и передавайте через скрипт или переменную окружения.
- **Используйте `vault-id`** для разделения доступа между окружениями (dev, stage, prod).
- **Проводите периодическую ротацию** ключей с помощью команды `rekey`:
  ```bash
  ansible-vault rekey app.vault.yml --vault-id old@prompt --new-vault-id new@prompt
  ```

### 4. Динамический инвентарь
- Убедитесь, что скрипты или плагины динамического инвентаря не возвращают чувствительные данные в `hostvars`.
- Отключайте или регулярно очищайте кэш инвентаря, если в нем потенциально могут оказаться секреты.

## Дополнительная информация

* Vault предназначен для хранения *существующих* секретов. Для генерации новых паролей используйте модуль [`ansible.builtin.password`](../../ansible_common_modules.md#7-модули-для-работы-с-паролями-и-чувствительными-данными).

### Предостережение: Шифрование общих ролей

Ansible Vault — отличный инструмент для защиты секретов, но его использование в общих ролях, которые распространяются или совместно используются с другими разработчиками, может вызвать проблемы.

**Проблема:** Если вы как разработчик зашифруете всю свою роль (например, `tasks/main.yml` или `templates/my_config.j2`) и отправите ее коллегам, они не смогут легко просматривать и отлаживать код роли, не имея пароля. Это значительно усложняет ревью кода, понимание логики и поиск ошибок, так как содержимое файлов будет нечитаемым.

**Рекомендация:** Шифруйте только те файлы или переменные, которые действительно содержат чувствительные данные (пароли, ключи, токены). Основную логику роли и шаблоны, не содержащие секретов, оставляйте в открытом виде. Секреты должны быть вынесены в отдельные зашифрованные файлы (например, `group_vars/all/vault.yml` или `host_vars/my_host/vault.yml`), которые используются ролями.
