# Ansible Vault: Лучшие практики

## Определения

- **Лучшие практики Vault**: Набор правил и техник, направленных на минимизацию риска утечки секретов как в состоянии покоя (в Git), так и во время выполнения плейбука (в логах, кэше).

## Основные концепции

### Принцип минимального раскрытия

Основная цель при работе с секретами — они должны оставаться зашифрованными как можно дольше и находиться в открытом виде в памяти как можно меньше времени. Каждая операция, которая может привести к их записи в лог или на диск, является потенциальной уязвимостью.

Инструменты Ansible, такие как `no_log` и `cacheable: false`, являются прямым следствием этого принципа.

## Практические сценарии

### Сценарий 1: Предотвращение утечек в логах (`no_log: true`)

Даже если переменная зашифрована, ее значение может **попасть в логи** при выполнении плейбука, если задача выводит свои параметры в консоль. Это самая частая ошибка.

**Проблема:**
```yaml
- name: Create database user # ЗАДАЧА УЯЗВИМА
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}" # db_password из Vault, но будет виден в логах
```

**Решение:**
Добавляйте `no_log: true` к **любой задаче**, которая прямо или косвенно работает с чувствительными данными. Эта директива полностью скроет параметры и вывод задачи из консоли.

```yaml
- name: Create database user # ЗАДАЧА ЗАЩИЩЕНА
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}"
  no_log: true # <-- ВАЖНО
```

### Сценарий 2: Безопасная организация репозитория

- **Разделяйте конфигурацию и секреты**: Храните секреты в отдельных, специально названных файлах (например, `prod.vault.yml`) в каталогах `group_vars/` или `host_vars/`.
- **Не шифруйте код**: Шифруйте только файлы с переменными, а не `.yml` файлы с задачами. Логика автоматизации должна оставаться в открытом виде для удобства чтения и аудита.
- **Используйте `.gitignore`**: Всегда исключайте из Git файлы с паролями (`vault_pass.txt`), не зашифрованные секреты и временные файлы отладки.

### Сценарий 3: Предотвращение кэширования секретов

По умолчанию Ansible кэширует факты, собранные с хостов. Если вы получаете секрет из внешнего источника и сохраняете его как факт, он может быть записан на диск.

```yaml
- name: Получение секрета из внешнего источника
  ansible.builtin.set_fact:
    api_token: "{{ lookup('env', 'API_TOKEN') }}"
    cacheable: false # <-- Запрещает кэширование этого факта
  no_log: true
```

### Сценарий 4: Контроль прав доступа
При создании файлов из шаблонов, содержащих секреты, всегда указывайте минимально необходимые права доступа.

```yaml
- name: Создание конфигурационного файла
  ansible.builtin.template:
    src: config.j2
    dest: /etc/app/config.yml
    mode: '0600' # Только владелец может читать и писать
  no_log: true
```
