# Ansible Vault: Лучшие практики

## Определения

- **Принцип минимального раскрытия (Least Exposure)**: Стратегия, при которой секретные данные остаются зашифрованными максимально долго и расшифровываются только в момент непосредственного использования в памяти процесса.
- **Эшелонированная защита (Defense in Depth)**: Подход к безопасности, при котором используется несколько уровней контроля (анализ, изоляция, защита при выполнении), обеспечивающий сохранность данных даже при компрометации одного из уровней.
- **EncryptedString (ansible-core 2.19+)**: Внутренний тип данных Ansible, автоматически помечающий секреты для предотвращения их случайного вывода в логи или консоль (Data Tagging).
- **no_log**: Директива задачи, которая скрывает весь вывод задачи в логах Ansible. Обязательна для всех операций с секретами.
- **Смешанный файл (Mixed File)**: YAML-файл, содержащий как обычные открытые переменные, так и зашифрованные значения `!vault`.
- **SOPS (Secrets OPerationS)**: Инструмент для шифрования только значений в YAML/JSON файлах с поддержкой PGP и внешних KMS. Позволяет сохранять читаемость ключей в Git.

## Основные концепции

### Предварительные требования

Для применения рекомендаций из данного руководства необходимы:

- **Ansible (ansible-core)**: версия 2.4 или выше (рекомендуется ansible-core 2.19+ для полной поддержки `EncryptedString` и Data Tagging).
- **Python**: 3.11+ (требование ansible-core 2.19+).
- **ansible-lint**: для статического анализа (правило `no-log-password`). Установка: `pip install ansible-lint`.
- **pre-commit**: для автоматической проверки перед коммитом (опционально). Установка: `pip install pre-commit`.
- **gitleaks**: для поиска plain-text секретов в Git-истории (опционально). Установка: `brew install gitleaks` (macOS) или `go install github.com/gitleaks/gitleaks/v8@latest`.
- **GPG**: для шифрования файлов паролей (опционально). Установка: `brew install gnupg` (macOS) или `apt install gnupg` (Linux).

Проверка версий:
```bash
ansible --version | head -1
# → ansible [core 2.19.0] или выше

ansible-lint --version
# → ansible-lint 25.1.0 или выше

pre-commit --version
# → pre-commit 4.0.0 или выше

gitleaks version
# → 8.28.0 или выше
```

### Уровни защиты секретов (Эшелонированная защита)

Безопасность секретов в Ansible строится на четырех фундаментальных уровнях:

1. **Статический анализ**: Использование линтеров (`ansible-lint`) и `pre-commit` хуков для предотвращения коммита открытых секретов.
2. **Изоляция в репозитории**: Четкое разделение переменных и кода, использование зашифрованных строк (`encrypt_string`) вместо шифрования целых файлов для сохранения читаемости YAML и Git-диффов.
3. **Защита Control Node**: Ограничение доступа к мастер-паролям Vault. Использование динамических источников (скрипты, Keyring, GPG) вместо хранения `vault_pass.txt` на диске.
4. **Защита при выполнении (Runtime)**: Использование директив `no_log`, управление кэшированием фактов и ограничение прав доступа на целевых хостах.

**Для DevOps:** Каждый уровень должен быть автоматизирован. Статический анализ — в CI/CD пайплайне, изоляция — через политики Git, защита Control Node — через секреты CI/CD, Runtime — через аудит выполнения плейбуков.

**Для SRE:** Внедрите мониторинг каждого уровня. Настройте алерты на пропущенные `no_log`, неудачные проверки `ansible-lint`, попытки коммита открытых секретов.

**Для Sysadmin:** Фокус на уровне Control Node: `chmod 600` для файлов паролей, `umask 0077`, контроль `$TMPDIR`, использование `ansible-vault view` вместо `decrypt`.

### Криптографические ограничения и актуальность

Ansible Vault использует схему **AES-256-CTR** с **10 000 итерациями PBKDF2-HMAC-SHA256**.

- **Критическое замечание**: 10 000 итераций — это низкий показатель по современным стандартам безопасности (OWASP рекомендует от 600 000+). Это делает файлы Vault уязвимыми к офлайн-перебору на GPU (видеокартах).
- **Рекомендация**: Используйте мастер-пароли Vault длиной **не менее 20-25 символов** с высокой энтропией.
- **Data Tagging (Core 2.19+)**: Механизм `EncryptedString` позволяет системе отслеживать происхождение данных. Если переменная была получена из Vault, Ansible будет блокировать её вывод даже при неявном использовании в модулях отладки.

**Для Sysadmin:** 10 000 итераций PBKDF2 компенсируются длиной пароля. На production-хостах используйте пароли длиной 25+ символов, сгенерированные через `openssl rand -base64 32`.

**Для SRE:** Установите политику минимальной длины мастер-паролей (20+ символов). Ведите журнал ротации и аудита использования Vault.

## Практические сценарии

### Сценарий 1: Предотвращение утечек в логах (`no_log: true`)

Даже если переменная зашифрована, ее значение может попасть в логи при выполнении задачи.

**Проблема (Уязвимо):**
```yaml
- name: Create database user
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}" # db_password будет виден в логах
```

**Решение (Стандарт безопасности):**
Добавляйте `no_log: true` к любой задаче, работающей с секретами. Это скроет параметры и вывод из консоли и логов.
```yaml
- name: Create database user
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}"
  no_log: true
```

**Для DevOps:** Добавьте `no_log: true` в шаблоны ролей. Используйте `ansible-lint` с правилом `no-log-password` для автоматического поиска нарушений.

**Для SRE:** Настройте алерт на появление секретов в логах Ansible. Регулярно проверяйте логи на наличие открытых значений.

### Сценарий 2: Безопасная организация репозитория

- **Разделяйте конфигурацию и секреты**: Храните секреты в отдельных файлах (например, `prod.vault.yml`) в каталогах `group_vars/` или `host_vars/`.
- **Используйте `encrypt_string` для прозрачности**: Вместо шифрования всего файла зашифруйте только значение переменной. Это позволяет видеть названия ключей в Git и упрощает Code Review.
  ```yaml
  # group_vars/all/secrets.yml
  db_password: !vault |
            $ANSIBLE_VAULT;1.1;AES256
            36383633...
  ```
- **Исключайте открытые секреты**: Всегда добавляйте `vault_pass.txt` и временные файлы в `.gitignore`.

**Для Sysadmin:** Настройте глобальный `.gitignore` для всех Ansible-проектов: `*.vault_pass*`, `*.tmp`, `.vault_pass`.

### Сценарий 3: Предотвращение кэширования секретов

Механизм кэширования фактов легко понять неправильно. Ansible сохраняет в кэш **только факты, помеченные `cacheable: true`** — обычный `set_fact` в кэш не попадает. Поэтому риск возникает не всегда, а только когда кто-то сознательно включил `cacheable`.

```yaml
# Опасно: значение попадёт в кэш-файл на диске открытым текстом
- name: Получить токен и сохранить в кэш
  ansible.builtin.set_fact:
    api_token: "{{ lookup('env', 'API_TOKEN') }}"
    cacheable: true     # ← вот эта строка делает факт кэшируемым

# Безопасно: cacheable не указан, значение живёт только в памяти прогона
- name: Получить токен без кэширования
  ansible.builtin.set_fact:
    api_token: "{{ lookup('env', 'API_TOKEN') }}"
```

Отключать `fact_caching` ради секретов не нужно — достаточно не помечать секретные факты как `cacheable`. Проверка в репозитории:

```bash
# Найти факты, которые попадут в кэш
rg -n -B5 'cacheable:\s*true' --glob '*.yml' . | rg -i 'password|token|secret|key'
# Если вывод непустой — эти значения попадут в кэш-файл
```

**Известная регрессия ansible-core 2.20+:** при использовании кэша инвентаря (`cache: True` в inventory-конфигурации) зашифрованные переменные могут сохраняться в кэш как **литеральная строка** `"$ANSIBLE_VAULT;1.2;AES256;..."` вместо ссылки на vault. На cache-hit переменная не расшифровывается. Проблема зафиксирована в [ansible/ansible#86369](https://github.com/ansible/ansible/issues/86369). Если используете кэш инвентаря вместе с vault-секретами, проверьте поведение после обновления или отключите кэширование для тех инвентарей, где есть `!vault`.

**Для SRE:** не используйте `cacheable: true` рядом с секретами. Для инвентарей с vault-секретами после обновления до 2.20+ проверьте cache-hit сценарий отдельно.

### Сценарий 4: Именование и косвенная адресация

Для предотвращения случайных утечек используйте префикс `vault_` и разделяйте декларацию и использование.

**Рекомендуемый подход:**
1. Зашифруйте значение с префиксом: `vault_db_password: !vault | ...`
2. Создайте публичную переменную-ссылку в другом файле: `db_password: "{{ vault_db_password }}"`

Это позволяет легко искать использование секретов через `grep` и менять источник секрета (например, переход на внешний менеджер секретов), не меняя код плейбуков.

**Для DevOps:** Внедрите обязательный префикс `vault_` для всех зашифрованных переменных. Добавьте проверку в `pre-commit` hook.

### Сценарий 5: Статический анализ и автоматизация (`pre-commit`)

1. **`ansible-lint`**: Правило `no-log-password` автоматически находит задачи, где используются переменные со словами `password`, `secret`, `token`, но отсутствует `no_log: true`.
2. **`pre-commit` хуки**: Используйте `ansible-vault-check` для проверки зашифрованности файлов и `gitleaks` для поиска plain-text секретов.
   ```yaml
   - repo: https://github.com/gitleaks/gitleaks
     rev: v8.21.2
     hooks:
       - id: gitleaks
   ```

**Для SRE:** Добавьте `ansible-lint` в CI/CD пайплайн. Настройте блокирование мержа при обнаружении нарушений.

### Сценарий 6: Ротация паролей и Rekey

Регулярная смена мастер-пароля — обязательная мера. При смене используйте `rekey`.

```bash
# Смена пароля во всех YAML-файлах репозитория
find . -type f -name "*.yml" -exec grep -l "\$ANSIBLE_VAULT" {} + | \
xargs ansible-vault rekey --vault-id old@source --new-vault-id new@source
```

**Для SRE:** При компрометации пароля выполните массовую ротацию. Удаляйте старые файлы паролей только после проверки расшифровки всех файлов.

**Для Sysadmin:** Никогда не удаляйте старый файл пароля до успешной проверки расшифровки всех файлов. Храните резервную копию старого пароля в защищенном хранилище в течение 7 дней после ротации.

### Сценарий 7: Безопасное редактирование (`view` vs `edit`)

Команда `ansible-vault edit` создает временную копию файла в `$TMPDIR`.
- **Риск**: На общих Control Node (Shared Server) другие пользователи могут попытаться прочитать временный файл в момент редактирования.
- **Рекомендация**: Используйте `ansible-vault view` для чтения. Для редактирования на общих серверах убедитесь, что `$TMPDIR` указывает на вашу личную защищенную директорию (`chmod 700`).

**Для Sysadmin:** Настройте `umask 0077` для автоматического ограничения прав на создаваемые файлы. Используйте `ansible-vault view` вместо `decrypt` для чтения секретов на production-хостах — `decrypt` оставляет открытый текст на диске.

### Сценарий 8: Интеграция с HashiCorp Vault (on-prem)

Для крупных Production сред рекомендуется использовать внешние системы как дополнительный слой защиты секретов.

- **Lookup-плагины**: Прямое получение из HashiCorp Vault во время выполнения.
  ```yaml
  - name: Получение пароля БД из HashiCorp Vault
    set_fact:
      db_pass: "{{ lookup('community.hashi_vault.vault_kv2_get', 'db').secret.password }}"
    no_log: true
  ```
- **AppRole**: Метод аутентификации для машин и скриптов, использующий пару `RoleID` и `SecretID`.

**Для SRE:** Используйте HashiCorp Vault как основной SSoT для production-секретов. Ansible Vault — для шифрования при хранении в Git.

### Сценарий 9: Шаблоны с секретами — Hardening

Когда `ansible.builtin.template` рендерит шаблон, итоговый файл на целевой машине содержит секрет в открытом виде.

**Меры защиты:**
- **Права доступа**: Всегда ограничивайте права доступа: `mode: '0600'` или `'0400'`.
- **Ephemeral storage**: По возможности записывайте чувствительные конфиги в `tmpfs` (RAM-диск).
- **no_log**: Скроет утечку из логов при рендеринге шаблона.

**Для Sysadmin:** На целевых хостах используйте `tmpfs` для конфигов с секретами. Настройте `mode: '0600'` для всех шаблонов, содержащих пароли или ключи.

### Сценарий 10: Контейнеризация — использование Docker Secrets

Типичная ошибка — подстановка пароля напрямую в `environment`. Правильный подход: использование встроенных механизмов оркестраторов.

```yaml
# docker-compose.yml — БЕЗОПАСНО: пароль передается через файл в RAM (tmpfs)
services:
  db:
    image: postgres:16-alpine
    secrets:
      - db_password
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password

secrets:
  db_password:
    external: true
```

**Для DevOps:** В Docker используйте `secrets` вместо `environment` для передачи секретов. Удаляйте секреты в `post` шагах CI/CD.

### Сценарий 11: `EncryptedString` и Data Tagging (ansible-core 2.19+)

С 2.19 значение из `!vault` хранится как `EncryptedString` — подкласс `str` с прикреплённым шифротекстом и тегом `VaultedValue`. Тег переносится при присваивании, поэтому можно отследить происхождение значения.

**Главное, что нужно понять: `EncryptedString` не скрывает значение автоматически.** Официальная документация формулирует это однозначно: шифрование защищает только данные «at rest», а после расшифровки («data in use») ответственность за то, чтобы секрет не попал в вывод, лежит на авторе плейбука и плагина — то есть на `no_log`.

```yaml
# Значение из vault доступно как обычная строка — debug покажет его открытым текстом
- name: Вывод vault-переменной
  ansible.builtin.debug:
    var: vault_api_key
  # → "vault_api_key": "sk-live-abc123..."   ← утечка в stdout и в CI-лог
```

Это подтверждается документацией: `ansible localhost -m debug -a var=new_user_password -e @vars.yml --vault-id dev@a_password_file` печатает `{"new_user_password": "hunter2"}`.

Как защититься:

```yaml
# 1. no_log на каждой задаче, работающей с секретом
- name: Применить конфигурацию с секретом
  ansible.builtin.template:
    src: app.config.j2
    dest: /etc/app/config.json
  no_log: true

# 2. no_log на уровне блока или плейбука — грубее, но надёжнее
- hosts: app_servers
  no_log: true
  tasks: ...
```

Что реально даёт Data Tagging:

| Возможность | Как использовать |
| :--- | :--- |
| Проверить происхождение значения | `VaultedValue.get_tag(value) is not None` — работает независимо от того, `EncryptedString` это или обычная тегированная `str` |
| Получить шифротекст обратно | `VaultHelper.get_ciphertext(value, with_tags=False)` — без знания пароля |
| Написать собственную защиту в плагине | Оберните вывод в `if VaultedValue.get_tag(value)` вместо `isinstance` |

Ограничения, о которых стоит знать:

- **`no_log` скрывает не всё.** Значение может утечь через `changed`, `diff`, вывод модуля, факты и сообщения об ошибках. Особенно опасен `--diff`: он печатает аргументы модулей, то есть и секреты;
- **шифротекст ≠ защита от вывода.** Значение, полученное из vault, можно напечатать через `msg`, `debug`, `lineinfile` и любым другим способом;
- **`to_yaml` и `to_json` на vault-значении ведут себя иначе, чем в 2.18.** С 2.19 тегированная строка сериализуется не так, как раньше. Если фильтру нужно открытое значение, преобразуйте явно. Отдельно стоит знать про [ansible/ansible#85783](https://github.com/ansible/ansible/issues/85783): `transform_to_native_types(..., redact=True)` на уже расшифрованном vault-значении возвращает значение, а не `<redacted>`;
- **`ANSIBLE_DISPLAY_ARGS_TO_STDOUT`** (по умолчанию `false` в 2.19) управляет выводом аргументов задачи. Менять его не нужно — безопасное значение уже по умолчанию;
- **глобальный `no_log`.** Опция `DEFAULT_NO_LOG` с переменной окружения `ANSIBLE_NO_LOG` включает `no_log` для всего прогона. Полезно в CI, где секреты передаются в модули, но вы настраиваете задачи, которые при этом «не меняются».

### Сценарий 12: SOPS — шифрование только значений в YAML

SOPS позволяет шифровать только значения переменных, сохраняя читаемость ключей:

```bash
# Установка SOPS
brew install sops  # macOS
# или
apt install sops  # Linux

# Шифрование файла с использованием GPG
sops --encrypt --in-place group_vars/prod/secrets.yml

# Расшифровка для чтения
sops --decrypt group_vars/prod/secrets.yml

# Редактирование (автоматическая расшифровка и перешифровка)
sops group_vars/prod/secrets.yml
```

```yaml
# group_vars/prod/secrets.yml (после шифрования)
db_password: ENC[AES256_GCM,data:encrypted_data_here,iv:iv_here,tag:tag_here]
api_key: ENC[AES256_GCM,data:another_encrypted_data,iv:iv_here,tag:tag_here]
```

**Интеграция с Ansible:** SOPS-зашифрованные значения можно использовать через lookup-плагин:
```yaml
- name: Получение секрета из SOPS
  ansible.builtin.set_fact:
    db_password: "{{ lookup('community.sops.sops', 'group_vars/prod/secrets.yml', key='db_password') }}"
  no_log: true
```

**Для Sysadmin:** Используйте SOPS с GPG для шифрования файлов без зависимостей от облачных KMS. Ключ GPG может быть защищен passphrase.

### Сценарий 13: GPG-шифрование файлов паролей Vault

Использование GPG для дополнительной защиты файлов паролей Vault:

```bash
# Создание GPG-ключа (если нет)
gpg --gen-key

# Шифрование файла пароля Vault
gpg --encrypt --recipient your@email.com .vault_pass_prod
# → .vault_pass_prod.gpg

# Удаление открытого файла
rm .vault_pass_prod

# Создание скрипта для расшифровки
cat > fetch_vault_pass.sh << 'EOF'
#!/bin/bash
gpg --decrypt .vault_pass_prod.gpg 2>/dev/null
EOF
chmod +x fetch_vault_pass.sh
```

```ini
# ansible.cfg
[defaults]
vault_password_file = ./fetch_vault_pass.sh
```

**Преимущества:** Файл пароля зашифрован на диске; расшифровывается только в момент использования; ключ GPG может быть защищен passphrase.

**Для Sysadmin:** Никогда не храните файл пароля в открытом виде. Используйте GPG-шифрование с защищенным ключом.

### Сценарий 14: Безопасность в CI/CD (GitHub Actions, GitLab CI)

Правила безопасной работы с Vault в CI/CD:

```yaml
# .github/workflows/secure_deploy.yml
name: Secure Deploy with Vault
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: self-hosted
    steps:
      - uses: actions/checkout@v4

      - name: Decrypt vault password
        env:
          VAULT_PASS_ENCRYPTED: ${{ secrets.VAULT_PASS_GPG }}
          GPG_PRIVATE_KEY: ${{ secrets.GPG_PRIVATE_KEY }}
          GPG_PASSPHRASE: ${{ secrets.GPG_PASSPHRASE }}
        run: |
          echo "$GPG_PRIVATE_KEY" > /tmp/gpg_key.asc
          gpg --import /tmp/gpg_key.asc
          rm /tmp/gpg_key.asc
          echo "$VAULT_PASS_ENCRYPTED" | gpg --decrypt --batch --passphrase "$GPG_PASSPHRASE" > /tmp/.vault_pass
          chmod 600 /tmp/.vault_pass

      - name: Run playbook
        env:
          ANSIBLE_VAULT_PASSWORD_FILE: /tmp/.vault_pass
        run: |
          ansible-playbook --vault-password-file /tmp/.vault_pass site.yml

      - name: Cleanup
        if: always()
        run: rm -f /tmp/.vault_pass /tmp/gpg_key.asc
```

**Ключевые принципы:**
- Никогда не храните пароли Vault в переменных окружения в открытом виде.
- Используйте зашифрованные секреты CI/CD для хранения зашифрованных паролей.
- Расшифровывайте пароли только в момент использования и удаляйте после.
- Ограничивайте доступ к секретам на уровне веток/окружений.

**Для DevOps:** На self-hosted раннере контролируйте права доступа к директории с секретами. Удаляйте временные файлы в `post` шагах. Никогда не передавайте пароль через `echo` в логи.

## Операции и команды

Полный справочник команд `ansible-vault` приведен в [Ansible Vault: Основы — Операции и команды](./basics.md#операции-и-команды).

**Best-practice-specific операции:**

| Операция | Рекомендация |
|----------|--------------|
| Просмотр секретов | Используйте `ansible-vault view` вместо `decrypt` для чтения секретов на production-хостах. `decrypt` оставляет открытый текст на диске. |
| Редактирование | На shared Control Node контролируйте `$TMPDIR` и права доступа. Установите `umask 0077`. |
| Ротация | Выполняйте массовую ротацию только после проверки расшифровки всех файлов. Удаляйте старые файлы паролей через 7 дней после успешной ротации. |
| Inline-шифрование | Используйте `ansible-vault encrypt_string` для отдельных переменных вместо шифрования целых файлов. |

**Приоритет источников паролей:** `ansible.cfg` < переменная окружения < аргументы командной строки.

## Устранение неполадок

### Ошибка: `Vault password not found for identity`

**Причина**: Vault ID указан в заголовке файла, но пароль для этой метки не предоставлен.

```bash
# Проверка vault_identity_list в ansible.cfg
grep vault_identity_list ansible.cfg

# Проверка существования файлов паролей
ls -la .vault_pass_*

# Проверка переданных Vault ID
env | grep ANSIBLE_VAULT
```

### Ошибка: `Decryption failed` для конкретного Vault ID

**Причина**: неверный пароль, несовпадение `vault_id` или повреждённый файл. Ansible не различает эти случаи: HMAC считается ключом, производным от пароля, поэтому при неверном пароле сообщение будет тем же.

```bash
# Проверка Vault ID в заголовке файла
head -1 secrets.yml
# → $ANSIBLE_VAULT;1.2;AES256;prod

# Попытка расшифровки с указанием правильного Vault ID
ansible-vault view --vault-id prod@.vault_pass_prod secrets.yml

# Если Vault ID не совпадает — перешифровка с правильной меткой
ansible-vault rekey --vault-id prod@old_pass --new-vault-id prod@new_pass secrets.yml
```

### Ошибка: `Too many vault secrets` при большом количестве Vault ID

**Причина**: формат 1.1 без меток или `vault_id_match=False`.

```bash
# Проверка количества Vault ID
grep -r "vault_id" ansible.cfg

# Оптимизация: группировка похожих окружений
# Вместо dev, dev-test, dev-staging, dev-local → dev (для всех dev-окружений)

# Включение строгого режима (рекомендуется)
# ansible.cfg
[defaults]
vault_id_match = True
```

### Ошибка: `ANSIBLE_VAULT_IDENTITY_LIST ignored` в CI/CD

**Причина**: ENV перезаписывается CLI или форматирование списка нарушено.

```bash
# НЕПРАВИЛЬНО: ENV перезаписывается CLI
ANSIBLE_VAULT_IDENTITY_LIST="prod@pass1" ansible-playbook --vault-id dev@pass2 site.yml

# ПРАВИЛЬНО: используйте либо ENV, либо CLI
export ANSIBLE_VAULT_IDENTITY_LIST="prod@pass1,dev@pass2"
ansible-playbook site.yml
```

### Предупреждение: `Vault ID label mismatch` (non-strict mode)

**Причина**: файл зашифрован с меткой `prod`, но предоставлен пароль для `dev`.

```yaml
# Исправление: перешифровка с правильной меткой
- name: Перешифровка с правильным Vault ID
  ansible.builtin.command: ansible-vault rekey --vault-id dev@old --new-vault-id prod@new secrets.yml
```

**Для SRE:** Включите `vault_id_match = True` в `ansible.cfg` для production. Это исключает эскалацию привилегий через доступ к dev-паролю в prod-окружении.

## Лучшие практики

- **`no_log: true`** — применяйте ко всем задачам, работающим с секретами, включая `set_fact` и `template`.
- **Мастер-пароли** — используйте пароли длиной от 20 символов с высокой энтропией; храните файлы паролей с правами `chmod 600`.
- **Vault ID** — используйте формат заголовка 1.2 с метками для всех новых проектов; это исключает неоднозначность при расшифровке.
- **Изоляция секретов** — храните секреты в отдельных файлах (`vault.yml`), исключайте их из репозитория через `.gitignore`.
- **Статический анализ** — используйте `ansible-lint` с правилом `no-log-password` и `pre-commit` хуки для предотвращения утечек.
- **Ротация** — регулярно меняйте мастер-пароли с помощью `ansible-vault rekey`; удаляйте старые файлы паролей после проверки.
- **Временные файлы** — в CI/CD удаляйте временные файлы с секретами в `post` шагах; на shared Control Node контролируйте `$TMPDIR`.
- **Шифрование паролей** — используйте GPG для дополнительной защиты файлов паролей Vault.
- **Предпочтение `view`** — используйте `ansible-vault view` вместо `decrypt` для чтения секретов; `decrypt` оставляет открытый текст на диске.
- **Динамические секреты** — для production используйте HashiCorp Vault или аналогичные on-prem системы для динамической выдачи секретов.

## Граничные случаи и ограничения

- **`no_log` и `debug`**: `no_log: true` скрывает вывод задачи, но не скрывает переменные, используемые в `register` или `debug` без `no_log`.
- **`EncryptedString` и lookup-плагины**: `EncryptedString` работает только с переменными, полученными напрямую из Vault. Lookup-плагины (HashiCorp) не помечают переменные как `EncryptedString`.
- **SOPS и Ansible**: SOPS-зашифрованные значения не расшифровываются автоматически Ansible; требуется lookup-плагин `community.sops.sops` из коллекции `community.sops`.
- **`EncryptedString` не скрывает значение**: `debug: var:` напечатает секрет открытым текстом. Защита — только `no_log` и дисциплина вывода.
- **Pre-commit хуки и обход**: Pre-commit хуки можно обойти через `git commit --no-verify`; используйте серверные хуки Git для дополнительной защиты.
- **GPG-шифрование и производительность**: GPG-расшифровка добавляет задержку (~100-500 мс) к каждому запуску плейбука.
- **Vault Pass скрипты и безопасность**: Скрипты получения пароля не должны логировать пароль; используйте `set +x` для отключения отладки.
- **`rekey` и параллельное выполнение**: Не запускайте `ansible-vault rekey` параллельно для файлов из одного окружения; это может привести к race condition.
- **Docker и tmpfs**: При использовании Docker Secrets убедитесь, что приложение поддерживает чтение пароля из файла (`*_FILE` переменные).
- **CI/CD и temporary files**: В CI/CD всегда удаляйте временные файлы с секретами в `post` шагах или `if: always()`.
- **Множественные Vault ID и производительность**: При использовании >10 Vault ID с форматом 1.1 (без меток) время расшифровки увеличивается пропорционально количеству хранилищ. Для формата 1.2 с `vault_id_match=True` количество не влияет на производительность.
