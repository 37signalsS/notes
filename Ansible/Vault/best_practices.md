# Ansible Vault: Лучшие практики

## Определения

- **Лучшие практики Vault**: Набор проверенных правил и техник, направленных на минимизацию риска утечки секретов как в состоянии покоя (в Git), так и во время выполнения автоматизации (в логах, кэше, отчетах).
- **Принцип минимального раскрытия**: Стратегия, при которой секретные данные остаются зашифрованными максимально долго и расшифровываются только в момент непосредственного использования в памяти.

## Основные концепции

### Эшелонированная защита

Безопасность секретов в Ansible строится на трех уровнях:
1. **Статический анализ**: Использование линтеров (`ansible-lint`) и `pre-commit` хуков для предотвращения коммита открытых секретов.
2. **Изоляция в репозитории**: Четкое разделение переменных и кода, использование зашифрованных строк (`encrypt_string`) вместо целых файлов.
3. **Защита при выполнении**: Использование директив `no_log`, управление кэшированием и ограничение прав доступа на целевых хостах.

Инструменты Ansible, такие как `no_log` и `cacheable: false`, являются инструментами реализации этих принципов.

## Практические сценарии

### Сценарий 1: Предотвращение утечек в логах (`no_log: true`)

Даже если переменная зашифрована, ее значение может **попасть в логи** при выполнении плейбука, если задача выводит свои параметры в консоль. Это самая частая ошибка.

**Проблема:**

```yaml
- name: Create database user # ЗАДАЧА УЯЗВИМА
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}" # db_password из Vault, но будет виден в логах
```

**Решение:**
Добавляйте `no_log: true` к **любой задаче**, которая прямо или косвенно работает с чувствительными данными. Эта директива полностью скроет параметры и вывод задачи из консоли.

```yaml
- name: Create database user # ЗАДАЧА ЗАЩИЩЕНА
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ db_password }}"
  no_log: true # <-- ВАЖНО
```

### Сценарий 2: Безопасная организация репозитория

- **Разделяйте конфигурацию и секреты**: Храните секреты в отдельных, специально названных файлах (например, `prod.vault.yml`) в каталогах `group_vars/` или `host_vars/`.
- **Не шифруйте код**: Шифруйте только файлы с переменными, а не `.yml` файлы с задачами. Логика автоматизации должна оставаться в открытом виде для удобства чтения и аудита.
- **Используйте `.gitignore`**: Всегда исключайте из Git (система контроля версий) файлы с паролями (`vault_pass.txt`), не зашифрованные секреты и временные файлы отладки.

### Сценарий 3: Предотвращение кэширования секретов

По умолчанию Ansible кэширует факты, собранные с хостов. Если вы получаете секрет из внешнего источника и сохраняете его как факт, он может быть записан на диск в кэш-файлы.

```yaml
- name: Получение секрета из внешнего источника
  ansible.builtin.set_fact:
    api_token: "{{ lookup('env', 'API_TOKEN') }}"
    cacheable: false # <-- Запрещает запись этого факта в кэш на диске
  no_log: true
```

### Сценарий 4: Именование и косвенная адресация

Для прозрачности и предотвращения случайных утечек используйте префикс `vault_` и разделяйте декларацию и использование.

**Рекомендуемый подход:**
1. Зашифруйте значение с префиксом: `vault_db_password: !vault | ...`
2. Создайте публичную переменную-ссылку: `db_password: "{{ vault_db_password }}"`

Это позволяет:
- Сразу видеть в коде, какая переменная является секретной.
- Легко искать использование секретов через `grep`.
- Менять источник секрета (Vault или plain-text для dev), не меняя код плейбуков.

### Сценарий 5: Статический анализ и автоматизация (`pre-commit`)

Используйте инструменты для автоматической проверки репозитория перед каждым коммитом.

1. **`ansible-lint`**: Правило `no-log-password` автоматически находит задачи, где используются переменные со словами `password`, `secret`, `token`, но отсутствует `no_log: true`.
2. **`pre-commit` хуки**: Используйте специализированные хуки для проверки, что файлы с секретами действительно зашифрованы.

```yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/ansible/ansible-lint
    hooks:
      - id: ansible-lint
  - repo: https://github.com/tellly/ansible-vault-check
    hooks:
      - id: ansible-vault-check # Проверяет наличие заголовка $ANSIBLE_VAULT
```

### Сценарий 6: Ротация паролей

Регулярная смена мастер-пароля Vault — стандарт безопасности. Для массового обновления используйте `rekey`.

```bash
# Смена пароля во всех yaml-файлах репозитория
find . -name "*.yml" | xargs ansible-vault rekey
```

### Сценарий 7: Интеграция с внешними менеджерами секретов

Для крупных корпоративных сред рекомендуется использовать Ansible Vault только как транспорт или полностью перейти на внешние системы:
- **HashiCorp Vault**: Использование lookup-плагинов (`community.hashicorp.vault`) для получения секретов в реальном времени.
- **SOPS (Secrets OPerationS)**: Позволяет шифровать только значения в YAML, оставляя ключи открытыми, что упрощает разрешение конфликтов слияния (Git merge).

### Сценарий 8: Шаблоны с секретами — явная уязвимость

**Критическое предупреждение:** Когда `ansible.builtin.template` рендерит Jinja2-шаблон, содержащий `{{ vault_var }}`, итоговый файл на диске (`dest`) содержит расшифрованный секрет в открытом виде. Vault защищает данные только в репозитории; на целевой машине пароль лежит в открытом виде.

```yaml
- name: Создание конфигурационного файла с секретом # УЯЗВИМО
  ansible.builtin.template:
    src: docker-compose.j2   # содержит {{ db_password }}
    dest: /opt/app/docker-compose.yml
    mode: '0600'             # ограничивает доступ, но в открытом виде на диске остаётся
  no_log: true               # скрывает вывод, но не защищает файл
```

`mode: '0600'` и `no_log: true` — необходимые, но недостаточные меры. Они ограничивают доступ к уже расшифрованному файлу и скрывают утечку из логов, но не устраняют корневую проблему: секрет записан на диск.

### Сценарий 9: Docker Swarm/Kubernetes — использование Secrets

Типичная ошибка — рендерить `docker-compose.yml` с подстановкой пароля напрямую в `environment`. Правильный подход: использовать механизмы оркестраторов для передачи секретов в память контейнера.

```yaml
# docker-compose.j2 — БЕЗОПАСНО: пароль только в RAM (Random Access Memory — оперативная память)
services:
  db:
    image: postgres:16-alpine
    secrets:
      - db_password
    environment:
      POSTGRES_PASSWORD_FILE: /run/secrets/db_password

secrets:
  db_password:
    external: true
```

При таком подходе секрет монтируется через `tmpfs` (Temporary File System — временная файловая система в оперативной памяти) и никогда не записывается на диск целевой машины в открытом виде.
