# Основные концепции Ansible

## Определения

**Push-модель** — основной способ работы Ansible: центральный управляющий узел «проталкивает» конфигурации и команды на управляемые хосты по SSH.

**Pull-модель** — управляемые хосты самостоятельно «подтягивают» конфигурации с центрального сервера с помощью утилиты [Ansible Pull](ansible_pull.md).

**Идемпотентность** — фундаментальный принцип Ansible. Гарантирует, что повторное выполнение операции не приведет к изменениям, если система уже находится в целевом состоянии.

## Базовые концепции

### Плейбуки — Playbooks

Плейбук — YAML-файл, описывающий упорядоченный набор задач для выполнения на хостах. Основной инструмент оркестрации.

Подробная информация: [выполнение плейбуков](ansible_playbook_execution.md), [структура плейбуков](PlaybookStructure/basics.md).

### Модули и плагины

**Модули** — единицы кода, выполняющие конкретные действия **на управляемых хостах** (установка пакетов, управление службами).

**Плагины** — фрагменты кода, расширяющие базовую функциональность и выполняющиеся **на контрольном узле** (плагины подключения, инвентаризации).

Техническое различие описано в [создании пользовательских модулей](ansible_custom_modules.md#модули-против-плагинов).

### Роли

Роли — стандартный способ организации и переиспользования кода в Ansible. Инкапсулируют задачи, переменные и шаблоны в модульную переносимую структуру.

См. [Ansible: Роли](ansible_roles.md).

### Шаблоны — Jinja2

Шаблоны позволяют создавать динамические конфигурационные файлы с использованием переменных. Ansible использует шаблонизатор Jinja2.

См. [шаблонизация с Jinja2](ansible_jinja_templating.md).

### Обработчики и уведомления

**Handlers (обработчики)** — это специальные задачи, которые запускаются только тогда, когда их «уведомляет» (`notify`) другая задача, статус которой изменился на `changed`.

*   **Назначение:** Перезапуск сервисов (Nginx, PostgreSQL) только после изменения их конфигурационных файлов.
*   **Особенность:** Обработчики выполняются в самом конце плейбука (после всех обычных задач), даже если они были уведомлены несколько раз.

```yaml
tasks:
  - name: Обновить конфиг Nginx
    ansible.builtin.template:
      src: nginx.conf.j2
      dest: /etc/nginx/nginx.conf
    notify: Restart Nginx

handlers:
  - name: Restart Nginx
    ansible.builtin.service:
      name: nginx
      state: restarted
```

### Сбор фактов и динамическая конфигурация

**Факты** — это переменные, автоматически собираемые Ansible с управляемых хостов (через модуль `setup`).

*   **Использование фактов для тюнинга:** Можно динамически рассчитывать параметры конфигурации на основе ресурсов хоста (например, `shared_buffers` для PostgreSQL на основе объема RAM).
*   **Модуль `package`:** Рекомендуется использовать универсальный модуль `ansible.builtin.package` вместо специфичных `apt` или `yum`. Он автоматически определит пакетный менеджер системы.

```yaml
- name: Установить веб-сервер
  ansible.builtin.package:
    name: nginx
    state: present
```

### Идемпотентность

Принцип гарантирует, что повторное выполнение операции не изменит результат после первого успешного выполнения.

- `ok` (зеленый) — изменения не требуются.
- `changed` (желтый) — внесены изменения для достижения целевого состояния.

## Практические сценарии

### Обнаружение дрейфа конфигурации — Drift

**Configuration drift (дрейф конфигурации)** — ситуация, когда реальное состояние управляемого хоста отклоняется от желаемого, описанного в плейбуках. Возникает из-за ручных изменений на серверах (через SSH, CLI, API), минуя Ansible.

#### Механизм обнаружения

Ansible обнаруживает дрейф через механизм **сравнения состояний**, который работает при каждом запуске плейбука:

1. **Сбор фактов (`gather_facts`)** — при подключении к хосту Ansible собирает текущее состояние системы (установленные пакеты, запущенные службы, содержимое файлов, пользователи и т. д.).

2. **Сравнение с желаемым состоянием** — каждый модуль сравнивает фактическое состояние (`current state`) с декларативно описанным в задаче (`desired state`):
   - `state: present` → модуль проверяет, существует ли ресурс.
   - `state: started` → модуль проверяет, запущена ли служба.
   - `state: latest` → модуль проверяет версию пакета.

3. **Возврат статуса**:
   - `ok` — текущее состояние совпадает с желаемым (дрейф отсутствует).
   - `changed` — обнаружено расхождение, внесены исправления (дрейф обнаружен и устранён).

#### Инструменты обнаружения

| Режим | Команда | Назначение |
| :--- | :--- | :--- |
| **Обычный запуск** | `ansible-playbook site.yml` | Автоматическое обнаружение и исправление дрейфа |
| **Check mode** | `ansible-playbook site.yml --check` | Только обнаружение, без исправлений (dry run) |
| **Diff mode** | `ansible-playbook site.yml --check --diff` | Показывает конкретные различия в файлах (как `git diff`) |
| **Пошаговый** | `ansible-playbook site.yml --step` | Интерактивное подтверждение каждого изменения |

**См. также:** [Drift Detection в IaC](../Concepts/iac_overview.md#drift-detection-обнаружение-ручных-изменений), [режим check и diff](ansible_playbook_execution.md#ключевые-опции-командной-строки), [идемпотентность](#идемпотентность).

### Начальная загрузка хостов — Bootstrapping

Большинство модулей Ansible требуют наличия Python на целевом хосте. Для автоматической установки Python на системы, где он отсутствует, используется модуль **`raw`**, который выполняет команду «как есть», без использования Python-интерпретатора.

**Стратегия с двумя этапами (плеями):**

1. **Первый этап (установка Python):**
    - Отключает сбор фактов (`gather_facts: false`), так как он тоже требует Python.
    - Использует модуль `raw` для вызова пакетного менеджера (`apt`, `yum`) и установки Python.

2. **Второй этап (основная настройка):**
    - Выполняется после первого и использует стандартные Python-модули.

```yaml
---
- name: Play 1 - Bootstrap Python
  hosts: no_python_hosts
  become: true
  gather_facts: false # <-- Очень важно!

  tasks:
    - name: Install Python3 using raw command
      ansible.builtin.raw: apt-get update && apt-get install -y python3
      when: ansible_os_family == "Debian"

- name: Play 2 - Main configuration
  hosts: no_python_hosts
  become: true
  
  tasks:
    - name: Now we can use regular modules
      ansible.builtin.ping: {}
```
