# Основные концепции Ansible и лучшие практики

## 5. Основные концепции

### Модели развертывания: Pull и Push

-   **Pull-модель**: Управляемые хосты самостоятельно "подтягивают" конфигурации и инструкции с центрального мастер-сервера (например, по расписанию). Хосты активно запрашивают свое состояние.
-   **Push-модель**: Центральный управляющий узел "проталкивает" конфигурации и команды на управляемые хосты. Инструкции доставляются по запросу или по событию.

Ansible по умолчанию использует **Push-модель** управления, подключаясь по SSH к удаленным узлам. Однако, он также поддерживает **Pull-модель** с помощью таких инструментов, как [Ansible Pull](ansible_pull.md), где управляемые хосты могут периодически запрашивать обновления из Git-репозитория.

### Модули и Плагины

-   **Модули**: Это единицы кода, которые выполняют конкретные действия на управляемых хостах (например, установка пакетов, управление службами, копирование файлов). Модули вызываются в рамках **задач (tasks)** внутри плейбуков.
-   **Плагины**: Это фрагменты кода, которые расширяют базовую функциональность Ansible (например, плагины подключения, инвентаризации, callback-плагины). Они не выполняют задачи напрямую на хостах, а изменяют поведение или предоставляют дополнительный функционал для Ansible.

### Плейбуки (Playbooks)
Плейбук — это YAML-файл, описывающий упорядоченный набор задач для выполнения на хостах. Это основной инструмент для оркестрации.
Для более подробной информации см. [Выполнение плейбуков](ansible_playbook_execution.md) и [Структура плейбуков](ansible_playbook_structure.md).

### Идемпотентность
**Идемпотентность** — это фундаментальный принцип Ansible. Он гарантирует, что повторное выполнение операции не приведет к изменениям, если система уже находится в целевом состоянии.
*   `ok` (зеленый): Изменения не требуются.
*   `changed` (желтый): Были внесены изменения для достижения целевого состояния.

### Роли
Роли — это стандартный способ организации и переиспользования кода в Ansible. Они инкапсулируют задачи, переменные и шаблоны в модульную структуру.
См. [Ansible: Роли](ansible_roles.md).

### Шаблоны (Jinja2)
Шаблоны позволяют создавать динамические конфигурационные файлы с использованием переменных.
См. [Шаблонизация с Jinja2](ansible_jinja2_templating.md).

### Установка Python на "голые" хосты (Bootstrapping)

Большинство модулей Ansible требуют наличия Python на целевом хосте. Если его нет, вы столкнетесь с ошибками. Проблема решается с помощью модуля `raw` и специальной структуры плейбука.

Модуль `raw` выполняет команду через SSH "как есть", без использования Python. Это позволяет установить Python на "голую" систему.

**Стратегия с двумя плеями:**

Чтобы автоматизировать этот процесс, плейбук разделяют на два плея:

1.  **Первый плей (установка Python):**
    *   Отключает сбор фактов (`gather_facts: false`), так как модуль `setup` (который собирает факты) тоже требует Python.
    *   Использует модуль `raw` для вызова пакетного менеджера (`apt`, `yum`) и установки Python.

2.  **Второй плей (основная настройка):**
    *   Выполняется после первого. К этому моменту Python уже установлен.
    *   Включает сбор фактов и использует стандартные Python-модули для дальнейшей настройки системы.

**Пример плейбука для bootstrapping:**

```yaml
---
- name: Play 1 - Bootstrap Python
  hosts: no_python_hosts
  become: true
  gather_facts: false # <-- Очень важно!

  tasks:
    - name: Install Python3 using raw command
      ansible.builtin.raw: apt-get update && apt-get install -y python3
      when: ansible_os_family == "Debian"

- name: Play 2 - Main configuration
  hosts: no_python_hosts
  become: true
  
  tasks:
    - name: Now we can use regular modules
      ansible.builtin.ping: {}
```

## 6. Экосистема и лучшие практики

### Ansible Galaxy
[Ansible Galaxy](https://galaxy.ansible.com) — это центральный репозиторий для поиска и обмена ролями и коллекциями.

### Безопасность
*   **Управление привилегиями (`sudo`):** Используйте выделенного пользователя для Ansible с настроенными правами `sudo`. См. [Рекомендации по безопасности](ansible_security_best_practices.md)
*   **Шифрование секретов (`vault`):** **Всегда** используйте `ansible-vault` для шифрования чувствительных данных. См. [Ansible: Vault](ansible_vault.md).

### Качество кода: Ansible Lint
Используйте `ansible-lint` для статического анализа плейбуков и ролей на соответствие лучшим практикам.
```bash
pip install ansible-lint
ansible-lint my_playbook.yml
```
