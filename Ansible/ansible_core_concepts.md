# Основные концепции Ansible

## Определения

**Декларативность** — основной подход Ansible, при котором описывается *желаемое состояние* системы (например, «пакет Nginx должен быть установлен»), а не последовательность команд для его достижения.

**Идемпотентность** — фундаментальный принцип, гарантирующий, что повторное выполнение операции не изменит систему, если она уже находится в целевом состоянии.

**Push-модель** — стандартный способ работы, где управляющий узел (**Control Node**) инициирует соединение с хостами по протоколу **SSH** или **WinRM**.

**Pull-модель** — альтернативный режим, при котором хосты самостоятельно запрашивают конфигурацию через [Ansible Pull](./ansible_pull.md).

## Основные концепции

### Инвентарь (Inventory)

Инвентарь — это список управляемых узлов, сгруппированных по назначению (например, `web`, `db`). 
- **Статический инвентарь:** Файлы в форматах YAML или INI.
- **Динамический инвентарь:** Плагины, получающие список хостов из внешних API (AWS, Yandex Cloud, NetBox). См. [Динамический инвентарь](./dynamic_inventory.md).

### Переменные (Variables)

Переменные позволяют параметризовать конфигурации, делая их универсальными. Ansible поддерживает сложную систему приоритетов (22 уровня), где переменные командной строки (`extra vars`) имеют наивысший приоритет.
Подробнее: [Переменные и факты](./PlaybookStructure/variables.md).

### Плейбуки (Playbooks)

Плейбук — это YAML-файл, описывающий сценарии автоматизации. Он состоит из «плеев» (**Plays**), которые связывают группы хостов из инвентаря с набором задач.
Подробнее: [выполнение плейбуков](./ansible_playbook_execution.md), [структура плейбуков](./PlaybookStructure/basics.md).

### Модули и плагины

Современный Ansible (2.10+) рекомендует использовать полное имя (**FQCN — Fully Qualified Collection Name**), например: `ansible.builtin.copy` вместо `copy`.

| Критерий | Модули (Modules) | Плагины (Plugins) |
| :--- | :--- | :--- |
| **Место исполнения** | **Управляемый хост** (копируются и запускаются) | **Контрольный узел** (выполняются внутри процесса Ansible) |
| **Жизненный цикл** | Краткосрочный (удаляются после выполнения) | Постоянный (загружены на время работы) |
| **Назначение** | Изменение состояния системы (декларативность) | Расширение внутренней логики (связь, фильтры) |

> **Примечание:** Модули для сетевого оборудования (Cisco, Juniper) и облачных провайдеров обычно выполняются на **контрольном узле** через API. См. [Сетевая автоматизация](./ansible_network_automation.md).

#### Типы плагинов
* **Lookup:** Получение данных из внешних источников (файлы, переменные окружения, Vault).
* **Filter:** Преобразование данных внутри шаблонов Jinja2.
* **Connection:** Протоколы связи с хостами (`ssh`, `local`, `docker`).
* **Inventory:** Динамическое формирование списка хостов.

### Роли и коллекции

- **Роли (Roles):** Метод организации задач, переменных и шаблонов в независимые блоки. См. [Ansible: Роли](./ansible_roles.md).
- **Коллекции (Collections):** Современный стандарт упаковки, включающий роли, модули и плагины. См. [Ansible Galaxy](./Roles/galaxy.md).

### Обработчики (Handlers)

Задачи, выполняемые только при получении уведомления (`notify`) от задачи, статус которой — `changed`.
- **Особенность:** Выполняются один раз в самом конце плея в порядке их определения, независимо от количества уведомлений.
- Подробнее: [Основы структуры плейбуков](./PlaybookStructure/basics.md#обработчики-и-идемпотентность).

### Сбор фактов (Facts)

Автоматический сбор системных переменных (IP, ОС, архитектура) перед выполнением задач (модуль `setup`). Данные доступны через переменную `ansible_facts`.

### Шаблонизация (Jinja2)

Использование шаблонов для создания динамических конфигураций. См. [Ansible: Jinja2](./ansible_jinja_templating.md).

### Стратегии выполнения (Strategies)

Определяют, как Ansible распределяет задачи между хостами:
- **Linear (по умолчанию):** Все хосты завершают одну задачу, прежде чем перейти к следующей.
- **Free:** Каждый хост проходит плейбук максимально быстро, не дожидаясь остальных.

### Среды выполнения (Execution Environments)

Современный подход, использующий контейнеры (вместо venv) для изоляции зависимостей (Python библиотеки, коллекции) и обеспечения идентичности сред выполнения.

## Практические сценарии

### Обнаружение дрейфа конфигурации (Drift)

**Configuration drift** — отклонение реального состояния сервера от описанного в коде. Ansible обнаруживает и исправляет дрейф в процессе выполнения.

Основные режимы запуска для анализа изменений (`--check`, `--diff`) и другие опции командной строки подробно описаны в разделе **[Выполнение плейбуков](./ansible_playbook_execution.md)**.

### Начальная загрузка хостов (Bootstrapping)

Если на хосте отсутствует Python, используется модуль **`raw`** для выполнения команд напрямую через SSH.

```yaml
---
- name: Play 1 - Bootstrap Python
  hosts: all
  become: true
  gather_facts: false # Нельзя собрать без Python
  tasks:
    - name: Install Python3
      ansible.builtin.raw: apt-get update && apt-get install -y python3

- name: Play 2 - Main Configuration
  hosts: all
  become: true
  gather_facts: true # Теперь Python есть
  tasks:
    - name: Regular task
      ansible.builtin.ping: {} # → вернет "pong" при успехе
```
