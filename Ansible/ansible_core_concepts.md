# Ansible

## Основные концепции

### Модели развертывания: Push и Pull

- **Push-модель (основная)**: Центральный управляющий узел "проталкивает" конфигурации и команды на управляемые хосты по SSH.
- **Pull-модель**: Управляемые хосты самостоятельно "подтягивают" конфигурации с центрального сервера. Эта модель реализуется с помощью утилиты [Ansible Pull](ansible_pull.md).

### Плейбуки (Playbooks)

Плейбук — это YAML-файл, описывающий упорядоченный набор задач для выполнения на хостах. Это основной инструмент для оркестрации.
Для более подробной информации см. [Выполнение плейбуков](ansible_playbook_execution.md) и [Структура плейбуков](ansible_playbook_structure.md).

### Модули и Плагины

- **Модули**: Единицы кода, которые выполняют конкретные действия **на управляемых хостах** (например, установка пакетов, управление службами).
- **Плагины**: Фрагменты кода, которые расширяют базовую функциональность и выполняются **на контрольном узле** (например, плагины подключения, инвентаризации).

Более детальное техническое различие описано в документе [Создание пользовательских модулей](ansible_custom_modules.md#1-теория-модули-vs-плагины).

### Роли

Роли — это стандартный способ организации и переиспользования кода в Ansible. Они инкапсулируют задачи, переменные и шаблоны в модульную, переносимую структуру.
См. [Ansible: Роли](ansible_roles.md).

### Шаблоны (Jinja2)

Шаблоны позволяют создавать динамические конфигурационные файлы с использованием переменных. Ansible использует шаблонизатор Jinja2.
См. [Шаблонизация с Jinja2](ansible_jinja2_templating.md).

### Идемпотентность

**Идемпотентность** — это фундаментальный принцип Ansible. Он гарантирует, что повторное выполнение операции не приведет к изменениям, если система уже находится в целевом состоянии.

- `ok` (зеленый): Изменения не требуются.
- `changed` (желтый): Были внесены изменения для достижения целевого состояния.

## Практические сценарии

### Установка Python на "голые" хосты (Bootstrapping)

Большинство модулей Ansible требуют наличия Python на целевом хосте. Для автоматической установки Python на системы, где он отсутствует, используется модуль `raw`, который выполняет команду "как есть", без использования Python-интерпретатора.

**Стратегия с двумя плеями:**

1. **Первый плей (установка Python):**
    - Отключает сбор фактов (`gather_facts: false`), так как он тоже требует Python.
    - Использует модуль `raw` для вызова пакетного менеджера (`apt`, `yum`) и установки Python.

2. **Второй плей (основная настройка):**
    - Выполняется после первого и использует стандартные Python-модули.

**Пример плейбука:**

```yaml
---
- name: Play 1 - Bootstrap Python
  hosts: no_python_hosts
  become: true
  gather_facts: false # <-- Очень важно!

  tasks:
    - name: Install Python3 using raw command
      ansible.builtin.raw: apt-get update && apt-get install -y python3
      when: ansible_os_family == "Debian"

- name: Play 2 - Main configuration
  hosts: no_python_hosts
  become: true
  
  tasks:
    - name: Now we can use regular modules
      ansible.builtin.ping: {}
```

## Дополнительная информация

### Ansible Galaxy

**[Ansible Galaxy](https://galaxy.ansible.com)** — это центральный репозиторий для поиска и обмена контентом Ansible, таким как роли и коллекции. Утилита командной строки `ansible-galaxy` позволяет управлять этим контентом.

Подробнее об управлении ролями с помощью Galaxy см. в [документе о ролях](ansible_roles.md#продвинутые-детали-управление-ролями-с-ansible-galaxy).

### Безопасность

- **Управление привилегиями (`sudo`):** Используйте выделенного пользователя для Ansible с настроенными правами `sudo`. См. [Рекомендации по безопасности](ansible_security_best_practices.md)
- **Шифрование секретов (`vault`):** **Всегда** используйте `ansible-vault` для шифрования чувствительных данных. См. [Ansible: Vault](ansible_vault.md).

### Качество кода: Ansible Lint

Используйте `ansible-lint` для статического анализа плейбуков и ролей на соответствие лучшим практикам.

```bash
pip install ansible-lint
ansible-lint my_playbook.yml
```
