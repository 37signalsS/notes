# Структура роли Ansible

## Определения

**Структура роли** — стандартизированная организация каталогов и файлов в роли Ansible, которая позволяет движку автоматически находить и выполнять ресурсы (задачи, обработчики, шаблоны, переменные) без явного указания полных путей.

**Каталог роли** — директория с предопределенной структурой подкаталогов. Каждый подкаталог имеет специфическое назначение и приоритет в жизненном цикле выполнения роли.

---

## Основные концепции

### Стандартная структура каталогов

| Каталог / Файл | Назначение |
| :--- | :--- |
| `tasks/` | Основные задачи роли (`main.yml` — входная точка) |
| `handlers/` | Обработчики уведомлений (перезапуск сервисов, выполнение по триггеру) |
| `templates/` | Jinja2-шаблоны конфигураций (`.j2`) |
| `files/` | Статические файлы для копирования |
| `defaults/` | Переменные по умолчанию (самый низкий приоритет, для настройки пользователем) |
| `vars/` | Внутренние переменные и константы роли (высокий приоритет) |
| `meta/` | Метаданные: автор, зависимости, платформы и спецификации аргументов |
| `library/` | Собственные модули на Python, поставляемые вместе с ролью |
| `module_utils/` | Общий Python-код, импортируемый модулями из `library/` |
| `lookup_plugins/` | Плагины для поиска данных (например, чтение из API или БД) |
| `filter_plugins/` | Пользовательские фильтры Jinja2 для обработки данных |
| `molecule/` | Конфигурации для тестирования роли (современный стандарт вместо `tests/`) |
| `README.md` | Полное описание роли, её параметров и примеров использования |

### Ключевые файлы и их назначение

#### Задачи и входные точки (`tasks/main.yml`)
Ansible всегда ищет `tasks/main.yml` как основную точку входа. Если логика сложная, рекомендуется разбивать её на файлы (например, `install.yml`, `configure.yml`, `service.yml`) и подключать их через `ansible.builtin.import_tasks` или `include_tasks` в основном файле.

#### Метаданные и спецификации (`meta/`)
*   **`main.yml`**: Описывает зависимости роли. Если роль A зависит от роли B, роль B будет выполнена до роли A.
*   **`argument_specs.yml`** (Ansible 2.11+): Позволяет формально описать интерфейс роли (входные параметры, их типы, значения по умолчанию и обязательность). Это заменяет громоздкие проверки `assert` и `fail` в задачах.

#### Изоляция переменных (Namespacing)
Поскольку в Ansible глобальное пространство имен переменных (Flat Namespace), крайне важно:
1.  **Префиксы:** Все переменные роли ДОЛЖНЫ начинаться с имени роли (например, `nginx_port`, `nginx_conf_path`).
2.  **Defaults vs Vars:** Используйте `defaults/main.yml` для всего, что пользователь МОЖЕТ захотеть изменить. Используйте `vars/main.yml` для того, что НЕ ДОЛЖНО меняться (например, пути к бинарным файлам в зависимости от ОС).

## Технические подробности поиска ресурсов (Search Path)

Ansible использует механизм относительного поиска для модулей `copy`, `template`, `script`, `patch`. При вызове из задачи в роли поиск происходит в следующем порядке:

1.  Каталог `files/` или `templates/` внутри **текущей роли**.
2.  Каталоги ресурсов во всех ролях, перечисленных в **зависимостях** (`meta/main.yml`).
3.  Каталог, где находится вызывающий плейбук.

Это позволяет "переопределять" файлы базовых ролей в дочерних или в основном проекте.

### Роли в составе коллекций

В современных проектах (Ansible 2.10+) роли часто упаковываются в коллекции. Структура:
```text
my_namespace/
└── my_collection/
    ├── roles/
    │   └── my_role/          # Стандартная структура роли внутри
    │       ├── tasks/
    │       └── meta/
    └── plugins/              # Общие плагины коллекции
```
Для использования такой роли необходимо указывать её полное имя (**FQCN — Fully Qualified Collection Name**):
```yaml
- name: Подключение роли из коллекции
  ansible.builtin.include_role:
    name: my_namespace.my_collection.my_role
```

## Практические сценарии

### Сценарий 1: Сравнение `defaults/main.yml` и `vars/main.yml`

| Параметр | `defaults/main.yml` | `vars/main.yml` |
| :--- | :--- | :--- |
| **Назначение** | Настройки для пользователя | Внутренние константы |
| **Приоритет** | 1 (самый низкий) | 15 (очень высокий) |
| **Пример** | `app_port: 8080` | `app_bin_path: /usr/local/bin/app` |

**Лучшая практика:** Большинство переменных определяйте в `defaults`. Используйте `vars` только для данных, которые зависят от дистрибутива ОС и не должны переопределяться пользователем вручную.

### Сценарий 2: Настройка зависимостей в `meta/main.yml`

Зависимости гарантируют выполнение необходимых компонентов перед основной ролью:

```yaml
# meta/main.yml
dependencies:
  - role: geerlingguy.nginx
    vars:
      nginx_http_port: 8080
  - role: my_custom_db_role
    allow_duplicates: false # Запрет повторного выполнения, если роль уже была вызвана
```

### Сценарий 3: Валидация аргументов через `meta/argument_specs.yml`

Пример глубокой валидации параметров роли:

```yaml
# meta/argument_specs.yml
argument_specs:
  main:
    short_description: Основная точка входа настройки приложения
    options:
      app_user:
        type: str
        required: true
        description: Пользователь, от которого работает сервис
      app_port:
        type: int
        default: 8080
        description: Порт приложения
      app_environment:
        type: str
        choices: ['prod', 'stage', 'dev']
        default: 'dev'
        description: Среда развертывания
```

### Сценарий 4: Использование плагинов внутри роли

Если роли нужен специфический фильтр для обработки строк, его можно разместить прямо в `filter_plugins/custom_filters.py`:

```python
# filter_plugins/custom_filters.py
def to_upper_custom(value):
    return value.upper() + "_SUFFIX"

class FilterModule(object):
    def filters(self):
        return {
            'my_upper': to_upper_custom
        }
```

В задачах (`tasks/main.yml`) он станет доступен автоматически:
```yaml
- name: Использование кастомного фильтра
  ansible.builtin.debug:
    msg: "{{ 'test' | my_upper }}" # Результат: TEST_SUFFIX
```

### Сценарий 5: Организация шаблонов и файлов

Для сложных ролей (например, `web-server`) рекомендуется структурировать подкаталоги для удобства навигации:

```text
roles/webserver/
├── files/
│   ├── static/
│   │   └── index.html
│   └── ssl/
│       └── dhparam.pem
├── templates/
│   ├── nginx/
│   │   ├── main.conf.j2
│   │   └── vhost.conf.j2
│   └── scripts/
│       └── cleanup.sh.j2
└── tasks/
    └── main.yml
```

Использование в задачах:
```yaml
- name: Деплой конфигурации Nginx
  ansible.builtin.template:
    src: nginx/vhost.conf.j2 # Путь относительно каталога templates/
    dest: /etc/nginx/sites-available/app.conf
```

## Дополнительная информация

### Приоритеты переменных

Иерархия приоритетов (от самого низкого к самому высокому):

1. `defaults/main.yml` в роли
2. Переменные из инвентаря (`group_vars`, `host_vars`)
3. `vars/main.yml` в роли
4. Переменные, переданные как аргументы при вызове роли (через `vars:`)
5. Extra vars (`-e` в командной строке)

Подробное описание уровней — в [PlaybookStructure/variables.md](../PlaybookStructure/variables.md).
