# Управление ролями через Git

## Определения

**Управление ролями через Git** — совокупность методов подключения внешних зависимостей напрямую из Git-репозиториев, минуя официальный реестр Ansible Galaxy.

**Внешняя роль** — роль, исходный код которой хранится в отдельном репозитории. Она подключается к основному проекту для обеспечения модульности и разделения ответственности.

---

## Основные концепции

Хотя Ansible Galaxy является стандартом, прямое управление через Git необходимо для приватных корпоративных ролей или когда требуется жесткий контроль версий на уровне Git-инструментария.

### 1. Современный стандарт: `requirements.yml` с Git-ссылками
Самый эффективный и рекомендуемый способ. Вы используете утилиту `ansible-galaxy`, но указываете Git-репозиторий вместо имени в Galaxy.

*   **Применимость:** Основной метод для Enterprise-проектов с приватными репозиториями.
*   **Синтаксис `requirements.yml`:**
    ```yaml
    roles:
      - name: my_private_role
        src: git@github.com:myorg/ansible-role-nginx.git
        scm: git
        version: v1.2.3  # Тег, ветка или SHA коммита
    ```
*   **Установка:** `ansible-galaxy install -r requirements.yml`

### 2. Git Submodules (Подмодули)
Механизм Git для встраивания одного репозитория в другой.

*   **Применимость:** Когда проект требует максимальной прозрачности версий на уровне Git и возможности легко переключаться между коммитами зависимых ролей.
*   **Особенности:** Требует выполнения `git submodule update --init` после клонирования основного проекта.
*   Подробное описание: **[Git Submodules](../../Git/git_submodules.md)**.

### 3. Git Subtree
Интеграция кода внешней роли непосредственно в историю основного репозитория.

*   **Применимость:** Когда нужно модифицировать код ролей прямо в основном проекте и иметь возможность отправлять эти правки ("push") обратно в репозиторий роли.
*   Подробное описание: **[Git Submodules vs Subtree](../../Git/git_submodules_and_subtree.md)**.

## Безопасность и аутентификация в CI/CD

При клонировании приватных ролей через Git критически важно правильно настроить доступ:

1.  **SSH Keys (Рекомендуется):** Использование `deploy keys` с правами только на чтение. В CI/CD ключевой файл передается через переменные окружения и добавляется в `ssh-agent`.
2.  **Personal Access Tokens (PAT):** Передача токена через URL (например, `https://token:x-oauth-basic@github.com/...`). 
    *   **Внимание:** Этот метод небезопасен, так как токен может попасть в логи. Используйте его только в изолированных средах с маскировкой переменных.
3.  **CI_JOB_TOKEN (GitLab):** Специальный токен, позволяющий клонировать другие проекты той же группы.

## Практические сценарии

### Сценарий 1: Установка приватных ролей одной командой

Использование `requirements.yml` позволяет автоматизировать подготовку окружения.

**Файл `requirements.yml`:**
```yaml
roles:
  - name: internal.security
    src: git@gitlab.company.com:devops/roles/security.git
    scm: git
    version: master
```

**Команда инициализации:**
```bash
ansible-galaxy install -r requirements.yml -p ./roles
```

### Сценарий 2: Подключение роли как подмодуля

Если вы хотите зафиксировать роль `nginx` на конкретном коммите:

```bash
# Добавление подмодуля
git submodule add git@github.com:example/role-nginx.git roles/nginx

# Обновление до последней версии в ветке
git submodule update --remote roles/nginx
```

## Дополнительная информация

### Сравнение методов управления

| Критерий | `requirements.yml` (Git) | Git Submodules | Git Subtree |
| :--- | :--- | :--- | :--- |
| **Сложность** | Низкая | Средняя | Высокая |
| **Изоляция кода** | Полная (папка `roles/` в `.gitignore`) | Ссылка на коммит | Код в основном репозитории |
| **Удобство обновления** | Одной командой | Требует команд Git | Требует сложных команд Git |
| **Модификация роли** | Сложно (нужен отдельный клон) | Возможна | Удобна |
| **Лучший выбор** | **Стандарт для большинства** | Для жесткого контроля версий | Для совместной разработки |
