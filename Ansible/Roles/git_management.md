# Ручное управление ролями через Git

## Определения

**Ручное управление ролями** — альтернативный подход к управлению зависимостями Ansible, который использует модуль `ansible.builtin.git` для клонирования ролей напрямую в локальный проект, вместо использования `ansible-galaxy`.

**Модуль `ansible.builtin.git`** — встроенный модуль Ansible для клонирования репозиториев Git, обеспечивающий контроль над исходным кодом ролей.

---

## Основные концепции

### Основная идея подхода

1. **Роли в отдельном репозитории:** Все роли проекта хранятся в одном выделенном Git-репозитории (например, `my-ansible-roles` на GitLab или GitHub).
2. **Основной проект отдельно:** Проект с плейбуками и инвентарем хранится в другом репозитории.
3. **Игнорирование папки `roles`:** В основном проекте директория `roles/` добавляется в `.gitignore`, так как ее содержимое управляется автоматически.
4. **Плейбук для инициализации:** Специальный плейбук (например, `init.yml`) клонирует репозиторий с ролями в локальную папку `roles/`.

### Подготовка проекта

**Шаг 1: Настройте `.gitignore`**

Добавьте в корень основного проекта:

```
# .gitignore
roles/
```

Это предотвратит случайное добавление папки с ролями в основной репозиторий.

**Шаг 2: Создайте плейбук инициализации**

Плейбук выполняется на `localhost` для подготовки рабочего окружения:

```yaml
# init.yml
---
- name: Download roles from Git repository
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Ensure roles directory exists
      ansible.builtin.file:
        path: roles
        state: directory

    - name: Clone or update roles repository
      ansible.builtin.git:
        repo: 'git@gitlab.com:your_user/my-ansible-roles.git' # SSH URL репозитория
        dest: roles
        version: master # Можно указать ветку, тег или коммит
        force: true # Перезаписывать локальные изменения, чтобы всегда иметь актуальную версию
```

## Практические сценарии

### Сценарий 1: Первоначальная загрузка ролей

```bash
ansible-playbook init.yml
```

### Сценарий 2: Обновление ролей до последней версии

```bash
# Через плейбук
ansible-playbook init.yml

# Или вручную через Git
cd roles
git pull
```

### Сценарий 3: Фиксация версии роли

Для воспроизводимости сборок укажите конкретный тег или коммит:

```yaml
- name: Clone roles repository with fixed version
  ansible.builtin.git:
    repo: 'git@gitlab.com:your_user/my-ansible-roles.git'
    dest: roles
    version: v1.2.0 # Тег или хеш коммита
    force: true
```

## Дополнительная информация

### Сравнение с Ansible Galaxy

| Критерий | Ручной метод (`git`) | Стандартный метод (`requirements.yml`) |
| :--- | :--- | :--- |
| **Простота** | Высокая. Легко понять, так как это просто `git clone`. | Средняя. Требует знания `ansible-galaxy` и формата `requirements.yml`. |
| **Управление версиями** | Ручное. Вы управляете версией через поле `version` или вручную в Git. | Автоматизированное. `ansible-galaxy` может управлять версиями ролей. |
| **Структура проекта** | Код ролей физически находится внутри проекта в папке `roles`. | Роли устанавливаются в системные или пользовательские директории, а не в проект. |
| **Изоляция** | Нет. Все роли из репозитория клонируются вместе. | Высокая. Можно устанавливать разные версии одной и той же роли для разных проектов. |
| **Лучший сценарий** | Небольшие проекты, обучение, полный контроль над кодом ролей. | Крупные проекты, сложные зависимости, необходимость строгого версионирования. |

Подробное описание стандартного метода см. в [galaxy.md](galaxy.md).

### Преимущества подхода

- **Прямой контроль:** Полный доступ к исходному коду ролей
- **Простота:** Не требует изучения `ansible-galaxy`
- **Гибкость:** Возможность модификации ролей локально

### Недостатки подхода

- **Отсутствие автоматизации:** Ручное управление версиями
- **Нет изоляции:** Конфликты версий при нескольких проектах
- **Сложность масштабирования:** Не подходит для крупных проектов с зависимостями
