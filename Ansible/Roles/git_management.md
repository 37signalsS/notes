# Управление ролями через Git

## Определения

**Управление ролями через Git** — альтернативный [Ansible Galaxy](galaxy.md) подход к управлению зависимостями, при котором внешние роли подключаются напрямую из Git-репозиториев.

**Внешняя роль** — роль, исходный код которой хранится в отдельном репозитории и подключается к основному проекту для выполнения задач автоматизации.

---

## Основные концепции

Существует три основных стратегии ручного управления ролями через Git, каждая из которых имеет свои области применения.

### 1. Плейбук инициализации (Ad-hoc клонирование)
Метод, при котором специальный плейбук клонирует необходимые репозитории в папку `roles/` перед запуском основной автоматизации.

*   **Применимость:** Быстрые прототипы, временные окружения, когда использование Galaxy избыточно.
*   **Реализация:** См. [Сценарий 1: Плейбук для инициализации](#сценарий-1-плейбук-для-инициализации).

### 2. Git Submodules
Механизм Git, позволяющий встраивать сторонние репозитории как подкаталоги в основной проект, сохраняя ссылку на конкретный коммит.

*   **Применимость:** Крупные проекты, требующие жесткой фиксации версий ролей и прозрачного отслеживания изменений.
*   **Реализация:** Подробные команды и принципы работы описаны в **[Git Submodules](../../Git/git_submodules.md)**.

### 3. Git Subtree
Интеграция содержимого другого репозитория непосредственно в историю основного проекта.

*   **Применимость:** Когда необходимо вносить правки в код ролей прямо из основного проекта и отправлять их обратно в репозиторий ролей.
*   **Реализация:** Сравнение и примеры использования — в **[Git Submodules vs Subtree](../../Git/git_submodules_and_subtree.md)**.

## Практические сценарии

### Сценарий 1: Плейбук для инициализации

Этот метод требует добавления папки `roles/` в `.gitignore` и создания скрипта подготовки.

**Настройка `.gitignore`:**
```ini
roles/
```

**Плейбук `init_roles.yml`:**
```yaml
---
- name: Pre-flight roles setup
  hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: Ensure roles directory exists
      ansible.builtin.file:
        path: roles
        state: directory

    - name: Clone roles repository
      ansible.builtin.git:
        repo: 'git@gitlab.com:org/ansible-roles.git'
        dest: roles
        version: master # Ветка, тег или SHA коммита
        force: true
```

### Сценарий 2: Подключение роли как подмодуля

Если роль `nginx` живет в отдельном репозитории, её можно добавить в проект одной командой:

```bash
git submodule add git@github.com:example/role-nginx.git roles/nginx
git commit -m "Add nginx role as submodule"
```

При клонировании проекта другими участниками потребуется выполнить:
```bash
git clone --recurse-submodules <url_проекта>
```

## Дополнительная информация

### Сравнение методов управления

| Критерий | Плейбук | Git Submodules | Ansible Galaxy |
| :--- | :--- | :--- | :--- |
| **Простота** | Высокая | Средняя | Средняя |
| **Фиксация версии** | Ручная (в YAML) | Жесткая (SHA коммита) | Гибкая (`requirements.yml`) |
| **Удобство обновления** | `ansible-playbook init.yml` | `git submodule update` | `ansible-galaxy install -r` |
| **Версионность ролей** | Одна версия на проект | Версии привязаны к коммитам | Централизованно в Galaxy/Git |
| **Лучший выбор** | Одиночные проекты | Сложные Enterprise-проекты | Стандарт индустрии |
