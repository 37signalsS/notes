# Framework принятия решений: когда использовать роль, плейбук или коллекцию

## Определения

**Роль (Role)** — логическая единица декомпозиции автоматизации, инкапсулирующая задачи, переменные, шаблоны и обработчики для настройки конкретного компонента системы.

**Плейбук (Playbook)** — императивный сценарий выполнения Ansible, определяющий последовательность задач на группе хостов.

**Коллекция (Collection)** — современный стандарт упаковки и распространения контента Ansible (начиная с версии 2.10), включающий роли, модули, плагины и документацию.

**Utility Role (Утилитарная роль)** — специализированная роль-библиотека, предназначенная для переиспользования общих компонентов в других ролях, а не для прямого назначения хостам.

**Composite Role (Композитная роль)** — высокоуровневая роль, агрегирующая несколько утилитарных ролей для формирования законченного технического состояния системы.

**Функциональная роль (Capability Role)** — роль, сгруппированная по домену ответственности или бизнес-функции (например, `monitoring_agent`, `backup_client`).

**Blast Radius** — масштаб последствий при сбое автоматизации. В контексте выбора между плейбуком и ролью, роль ограничивает радиус поражения одним компонентом, тогда как плейбук может затрагивать всю инфраструктуру.

**Change Management (управление изменениями)** — процесс контроля всех изменений в инфраструктуре с целью минимизации рисков. Роли обеспечивают атомарность и воспроизводимость изменений, что критично для SRE-практик.

**Observability (наблюдаемость)** — способность понимать внутреннее состояние системы по внешним сигналам. Выбор абстракции влияет на granularity метрик и логирования: роли дают детализацию на уровне компонента, плейбуки — на уровне сценария.

**Idempotency (идемпотентность)** — свойство системы приводить к одному и тому же состоянию при повторном запуске. Роли проектируются как идемпотентные единицы; плейбуки могут содержать неидемпотентные операции (например, аварийные перезагрузки).

## Базовые концепции / Архитектура / Принципы работы

### Иерархия абстракции в Ansible

Ansible предоставляет три уровня организации контента, каждый из которых решает свою задачу в экосистеме DevOps/SRE/Sysadmin:

```
Плейбук (Playbook)          Роль (Role)                    Коллекция (Collection)
├── Императивный            ├── Декомпозиция              ├── Упаковка и распространение
├── Хост-ориентированный   ├── Переиспользование         ├── Пространство имен
└── Разовое выполнение      └── Компонентная изоляция     └── Версионирование
```

### Жизненный цикл выполнения

Понимание того, как Ansible обрабатывает каждый тип контента, критично для принятия архитектурных решений:

1. **Плейбук** — точка входа. Определяет `hosts`, `become`, `vars`, `roles` и `tasks`. Выполняется последовательно. При ошибке в задаче плейбук останавливается (если не настроен `any_errors_fatal` или `ignore_errors`).
2. **Роль** — подпрограмма внутри плейбука. Загружает `defaults/`, `vars/`, выполняет `tasks/`, триггерит `handlers/`. Изолирована от других ролей через namespace переменных.
3. **Коллекция** — не выполняется напрямую. Предоставляет пространство имен для ролей и модулей, загружается через `collections_path`.

### Критерии выбора: роль vs плейбук

| Критерий | Роль | Плейбук |
| :--- | :--- | :--- |
| **Сложность** | Средняя/высокая (10+ задач) | Низкая/средняя (<10 задач) |
| **Переиспользование** | Требуется в нескольких проектах | Однократное использование |
| **Изоляция компонента** | Один логический сервис/компонент | Сквозной сценарий на уровне окружения |
| **Тестирование** | Требуется Molecule | Линтинг плейбука |
| **Команда разработки** | 3+ человек, разделение ответственности | 1-2 человека |
| **Change Management** | Атомарные изменения, откат | Сквозной деплой |
| **Blast Radius** | Ограничен одним компонентом | Затрагивает группу хостов |
| **SRE-перспектива** | Изолированное изменение с метриками | Ингредиент для release pipeline |

### Критерии выбора: роль vs коллекция

| Критерий | Роль | Коллекция |
| :--- | :--- | :--- |
| **Содержимое** | Только задачи, переменные, шаблоны | Роли + модули + плагины + документация |
| **Пространство имен** | Отсутствует (глобальное) | Обязательное (`namespace.collection`) |
| **Версионирование** | Семантическое (опционально) | Строгое семантическое версионирование |
| **Распространение** | Galaxy, Git | Galaxy, Automation Hub |
| **Расширяемость** | Ограничена каталогами роли | Полная (собственные модули, плагины) |
| **Зависимости** | `meta/main.yml` | `galaxy.yml` с рекурсивным разрешением |
| **Совместимость** | Зависит от ansible-core | `requires_ansible` в манифесте |
| **Экосистема** | Одна роль | Целая экосистема контента |

### Принцип "Role-First" (Ansible 2.21+)

Начиная с Ansible 2.21, рекомендуется проектировать автоматизацию вокруг ролей даже для простых сценариев:

1. **Интерфейс прежде реализации:** Начинайте с `meta/argument_specs.yml`.
2. **Единая ответственность:** Одна роль = один компонент.
3. **Слабая связность:** Роли не зависят от внутренних переменных других ролей.
4. **Идемпотентность:** Повторный запуск не вызывает неожиданных изменений.
5. **Поддержка Check Mode:** `--check` информативен и не обрывается ошибками.
6. **Observability by Design:** Роль генерирует метрики и логи на каждом значимом этапе.
7. **Совместимость Python:** Для ansible-core 2.21+ на управляемых узлах требуется Python 3.9+ (3.12+ рекомендуется).

### Выбор в контексте SRE / Sysadmin / DevOps

| Роль | Плейбук | Коллекция |
| :--- | :--- | :--- |
| **SRE:** Изменение с откатом и валидацией | **SRE:** Аварийный инцидент, emergency restart | **SRE:** Корпоративная платформа с RBAC |
| **Sysadmin:** Разовая настройка одного сервиса | **Sysadmin:** Патч-вторник, массовое обновление | **Sysadmin:** Стандартизация через Automation Hub |
| **DevOps:** Модуль CI/CD пайплайна | **DevOps:** Полный pipeline деплоя | **DevOps:** Распространение внутри организации |

## Практические сценарии

### Сценарий 1: Когда использовать плейбук

Плейбук подходит, когда:

```yaml
# ad-hoc сценарий для разового выполнения
- name: Emergency restart Nginx
  hosts: webservers
  become: true
  tasks:
    - name: Restart service
      ansible.builtin.service:
        name: nginx
        state: restarted
```

**Признаки:**
- Меньше 10 задач
- Нет необходимости в переиспользовании
- Сквозной сценарий на уровне окружения
- Быстрое исправление/инцидент (SRE: incident response)
- Sysadmin: one-time configuration change
- DevOps: часть pipeline, не требующая переиспользования

### Сценарий 2: Когда использовать роль

Роль подходит, когда:

```yaml
# playbook.yml
- hosts: webservers
  become: true
  roles:
    - role: nginx
      nginx_port: 443
      nginx_worker_processes: "auto"
```

**Признаки:**
- 10+ задач, логически сгруппированных
- Переиспользование в нескольких проектах
- Необходимость в тестировании (Molecule)
- Атомарные изменения для Change Management
- Команда разработки 3+ человек
- SRE: требуется изоляция blast radius и granular observability
- Sysadmin: стандартизация настройки компонента

### Сценарий 3: Когда использовать коллекцию

Коллекция подходит, когда:

```yaml
# galaxy.yml
namespace: myorg
name: platform
version: 1.0.0
dependencies:
  community.general: ">=9.0.0"
  ansible.posix: ">=1.5.0"
```

**Признаки:**
- Собственные модули и плагины
- Распространение внутри организации или публично
- Строгое пространство имен
- Зависимости от внешних коллекций
- Версионирование через Automation Hub/Galaxy
- DevOps: корпоративная экосистема IaC

### Сценарий 4: Когда использовать Utility Role

Utility Role подходит, когда:

```yaml
# roles/lib_common/tasks/main.yml
---
- name: Установка общих пакетов
  ansible.builtin.package:
    name: "{{ common_packages }}"
    state: present
```

**Признаки:**
- Код дублируется в ≥3 ролях
- Изменения затрагивают все роли одновременно
- Интерфейс стабилен (`argument_specs.yml`)
- Команда разработки ≥3 человек
- SRE: централизованное управление политиками (безопасность, мониторинг)

### Сценарий 5: Когда использовать Composite Role

Composite Role подходит, когда:

```yaml
# roles/web_server/tasks/main.yml
---
- name: Подключение общих функций
  ansible.builtin.include_role:
    name: lib_common

- name: Настройка веб-сервера
  ansible.builtin.include_role:
    name: nginx
```

**Признаки:**
- Агрегация ≥3 utility ролей
- Формирование законченного профиля сервера
- Change Management требует атомарного применения всего стека
- SRE: единый артефакт для release pipeline

### Сценарий 6: Миграция с плейбука на роль

Пошаговая стратегия:

```bash
# Шаг 1: Анализ плейбука
ansible-playbook monolithic.yml --list-tasks

# Шаг 2: Создание структуры роли
mkdir -p roles/myapp/{tasks,handlers,templates,defaults,vars,meta}

# Шаг 3: Перенос задач
# monolithic.yml → roles/myapp/tasks/main.yml

# Шаг 4: Перенос переменных
# vars: → roles/myapp/defaults/main.yml

# Шаг 5: Создание meta/argument_specs.yml
cat > roles/myapp/meta/argument_specs.yml << 'EOF'
argument_specs:
  main:
    short_description: "Deploy myapp"
    options:
      app_version:
        type: str
        required: true
EOF

# Шаг 6: Тестирование
cd roles/myapp && molecule test
```

### Сценарий 7: Миграция с ролей на коллекцию

Когда роли становятся слишком много и нужны собственные модули:

```bash
# Шаг 1: Инициализация коллекции
ansible-galaxy collection init myorg.platform

# Шаг 2: Перенос ролей
cp -r roles/nginx collections/myorg/platform/roles/

# Шаг 3: Добавление модулей
mkdir -p collections/myorg/platform/plugins/modules
cp custom_modules/*.py collections/myorg/platform/plugins/modules/

# Шаг 4: Создание galaxy.yml
cat > collections/myorg/platform/galaxy.yml << 'EOF'
namespace: myorg
name: platform
version: 1.0.0
requires_ansible: ">=2.21,<2.22"
dependencies:
  community.general: ">=9.0.0"
  ansible.posix: ">=1.5.0"
EOF

# Шаг 5: Сборка и публикация
ansible-galaxy collection build
ansible-galaxy collection publish myorg-platform-1.0.0.tar.gz
```

### Сценарий 8: Emergency Playbook для SRE

Плейбук для инцидент-респонса, где время важнее переиспользования:

```yaml
# playbooks/incident_emergency_restart.yml
---
- name: Emergency restart all payment services
  hosts: payment_cluster
  become: true
  gather_facts: false  # Ускорение при инциденте

  pre_tasks:
    - name: Snapshot current state
      ansible.builtin.command: systemctl list-units --type=service --state=running | grep payment
      register: payment_services_before
      changed_when: false

  tasks:
    - name: Restart payment-api
      ansible.builtin.service:
        name: payment-api
        state: restarted
      register: restart_result

    - name: Validate health after restart
      ansible.builtin.uri:
        url: "http://{{ inventory_hostname }}:8080/health"
        status_code: 200
      register: health_check

    - name: Fail if health check failed
      ansible.builtin.assert:
        that:
          - health_check.status == 200
        fail_msg: "Payment API unhealthy on {{ inventory_hostname }}"
      when: health_check is failed

  post_tasks:
    - name: Log incident snapshot
      ansible.builtin.copy:
        content: |
          BEFORE: {{ payment_services_before.stdout }}
          AFTER: {{ health_check.url }}
        dest: "/var/log/incidents/{{ ansible_date_time.iso8601 }}_payment_restart.log"
      delegate_to: localhost
      run_once: true
```

### Сценарий 9: Capability Role для команды безопасности

Группировка по домену ответственности:

```yaml
# playbooks/security_hardening.yml
---
- name: Security baseline
  hosts: all
  become: true
  roles:
    - role: security.ssh_hardening
    - role: security.firewall
    - role: security.audit
    - role: security.intrusion_detection
```

### Сценарий 10: Версионирование для enterprise

```yaml
# requirements.yml
---
roles:
  # Component-based: точные версии
  - name: mycorp.nginx
    version: "3.2.0"
    src: git@git.internal:ansible/roles/nginx.git

  # Utility: диапазон версий
  - name: mycorp.lib_common
    version: ">=2.0.0,<3.0.0"

  # Composite: pinned для стабильности
  - name: mycorp.web_server
    version: "1.5.3"

collections:
  - name: myorg.platform
    version: ">=1.0.0,<2.0.0"
    source: https://automation-hub.internal
```

## Операции и команды

| Задача | Рекомендация | Альтернатива |
| :--- | :--- | :--- |
| Разовый запуск на 1-2 хоста | Плейбук | — |
| Настройка одного компонента | Роль | — |
| Распространение контента в команде | Коллекция | Git-репозиторий с ролями |
| Общие задачи для нескольких ролей | Utility Role | `include_tasks` в плейбуке |
| Агрегация нескольких утилитарных ролей | Composite Role | Плейбук с `roles:` |
| Группировка по домену ответственности | Capability Role | Плейбук по окружению |
| Кастомные модули/плагины | Коллекция | `library/` в роли (устарело) |
| Версионирование и зависимости | Коллекция | `requirements.yml` |

## Устранение неполадок

### Проблема: Слишком много мелких ролей

**Симптом:** Роли выполняют атомарные операции (`user_add`, `package_install`), оркестрация сложная.

**Причина:** Отсутствие Composite/Utility паттерна. Каждая атомарная операция выделена в отдельную роль без агрегации.

**Решение:** Агрегируйте утилитарные роли в Composite Role:

```yaml
# roles/web_server/tasks/main.yml
---
- name: Подключение общих функций
  ansible.builtin.include_role:
    name: lib_common

- name: Настройка веб-сервера
  ansible.builtin.include_role:
    name: nginx
```

**Диагностика:**
```bash
# Просмотр количества ролей в плейбуке
ansible-playbook site.yml --list-tasks | grep "role:" | wc -l
# → 15

# Проверка глубины зависимостей
ansible-playbook site.yml -vvvv | grep "ENTER ROLE"
```

### Проблема: Плейбук-бог (God Playbook)

**Симптом:** Плейбук выполняет 50+ задач для настройки всего окружения.

**Причина:** Отсутствие декомпозиции на роли. Все логика сосредоточена в одном файле.

**Решение:** Разбейте на роли:

```yaml
# playbooks/site.yml
---
- name: Настройка веб-узла
  hosts: webservers
  become: true
  roles:
    - mycorp.base.users
    - mycorp.base.ssh_hardening
    - mycorp.platform.nginx
    - mycorp.app.deploy
```

**Диагностика:**
```bash
# Анализ размера плейбука
wc -l playbooks/site.yml
# → site.yml: 487 lines

# Просмотр всех задач
ansible-playbook site.yml --list-tasks | head -50
```

### Проблема: Коллекция для простой роли

**Симптом:** Создана коллекция только для одной роли без модулей и плагинов.

**Причина:** Неправомерное использование коллекции как контейнера для одной роли.

**Решение:** Используйте роль, если нет необходимости в пространстве имен или собственных модулях. Коллекция оправдана при ≥3 ролях или наличии кастомных модулей.

### Проблема: Переменные utility role не видны в вызывающей роли

**Симптом:** `include_role` изолирует переменные, вызывающая роль не имеет доступа к результатам.

**Причина:** По умолчанию `include_role` изолирует переменные (Ansible 2.17+).

**Решение:**
```yaml
# Использование public: true для экспорта переменных
- name: Подключение utility роли
  ansible.builtin.include_role:
    name: lib_common
    public: true  # Экспорт переменных в вызывающий контекст
```

### Проблема: Конфликт версий зависимостей

**Симптом:** Разные версии ролей в development и production окружениях.

**Решение:**
```yaml
# requirements.yml с фиксированными версиями
---
roles:
  - name: geerlingguy.nginx
    version: "3.2.0"

# Использование block в плейбуке для изоляции
- block:
    - role: geerlingguy.nginx
      vars:
        nginx_version: "1.24.0"
  when: environment == "production"
```

### Проблема: Падение роли в композиции

**Симптом:** Роль работает изолированно, но падает при включении в composite.

**Причина:** Конфликт переменных, обработчиков или порядок выполнения.

**Диагностика:**
```bash
# Запуск с максимальной отладкой
ansible-playbook site.yml -vvvv

# Просмотр собранных переменных
ansible-playbook site.yml --list-variables -l host1
```

**Решение:**
- Используйте префиксы переменных для изоляции (`nginx_`, `postgresql_`)
- Явно управляйте порядком через директиву `roles:` в плейбуке
- Для обработчиков используйте namespace в именах (`nginx_restart`, `php_restart`)

## Рекомендации

### Выбор контента

1. **Начинайте с плейбука:** Для простых сценариев используйте плейбук. Когда логика растет — выделите роль.
2. **Роли для переиспользования:** Если код используется в ≥2 проектах — выделите роль.
3. **Коллекции для команд:** Если команда 5+ человек и нужны собственные модули — используйте коллекцию.
4. **Utility Roles для DRY:** Если код дублируется в ≥3 ролях — выделите Utility Role.
5. **Composite Roles для сложных сценариев:** Агрегируйте утилитарные роли в композитные.
6. **Capability Roles для организационной структуры:** Группируйте по командам ответственности.

### Структура проекта

| Масштаб | Рекомендация |
| :--- | :--- |
| 1-2 проекта, 5-10 ролей | Плейбуки + локальные роли + `requirements.yml` |
| 3-5 проектов, 10-30 ролей | Git-репозитории с ролями + `requirements.yml` |
| 5+ проектов, 30+ ролей | Коллекции + Automation Hub/Galaxy |
| Enterprise, 100+ ролей | Private Galaxy (Pulp) + CI/CD пайплайны |

### Оценка зрелости

| Уровень | Характеристики | Рекомендация |
| :--- | :--- | :--- |
| **Начальный** | 1-2 плейбука, 5-10 ролей | Плейбуки + локальные роли |
| **Средний** | 10-30 ролей, CI/CD | Git-роли + Molecule + Galaxy |
| **Продвинутый** | 30+ ролей, собственные модули | Коллекции + Automation Hub |
| **Enterprise** | 100+ ролей, несколько команд | Private Galaxy + EE + RBAC |

### Тестирование и качество

1. **Molecule:** Тестируйте каждую роль в изолированной среде (Docker/Podman).
2. **ansible-lint:** Запускайте перед каждым коммитом. Используйте профиль `production`.
3. **Семантическое версионирование:** Git-теги (`v1.0.0`, `v1.1.0`, `v2.0.0`) для всех ролей и коллекций.
4. **Pre-commit hooks:** Используйте `.pre-commit-config.yaml` с `ansible-lint`, `yamllint`.
5. **Check Mode:** Все роли должны проходить `ansible-playbook --check` без ошибок.

### Безопасность

1. **Секреты вне кода:** Никогда не храните пароли в `defaults/main.yml`. Используйте Ansible Vault с внешним бэкендом (HashiCorp Vault, системный keyring).
2. **no_log:** Указывайте `no_log: true` для задач с секретами.
3. **Минимальные привилегии:** Используйте `become: false` там, где это возможно.
4. **Проверка подписей:** Используйте `ansible-galaxy collection verify` (Ansible 2.13+).

### Управление изменениями

1. **Атомарность:** Каждая роль = одно логическое изменение.
2. **Валидация:** После выполнения добавьте задачу проверки (`changed_when: false`).
3. **Теги:** Используйте `pre_deploy`, `deploy`, `rollback`, `validate`.
4. **Rollback:** Поддерживайте предыдущую версию роли для быстрого отката.

### Наблюдаемость

1. **Структурированные логи:** Используйте `debug` с четкими `msg` для ключевых этапов.
2. **Метрики:** Регистрируйте результаты задач (`register`) для Prometheus/Grafana.
3. **Callback-плагины:** Настройте `json`/`yaml` callback для централизованного логирования.
4. **Вербозность:** Контролируйте объем вывода в production через `verbosity`.

## Дополнительная информация

### Сравнение: роль vs плейбук vs коллекция

| Аспект | Роль | Плейбук | Коллекция |
| :--- | :--- | :--- | :--- |
| **Переиспользование** | Высокое | Низкое | Высокое |
| **Тестируемость** | Molecule | Линтинг | Molecule + ansible-test |
| **Версионирование** | Git теги | Git | Семантическое (galaxy.yml) |
| **Пространство имен** | Отсутствует | Отсутствует | Обязательное |
| **Зависимости** | `meta/main.yml` | `requirements.yml` | `galaxy.yml` |
| **Расширяемость** | Ограничена | Ограничена | Полная |
| **Blast Radius** | Компонент | Хост/группа | Экосистема |
| **Гранулярность отката** | Высокая (роль) | Средняя (плейбук) | Низкая (коллекция) |

### Матрица решений

```
Начало проекта?
├── Простой сценарий (<10 задач)?
│   └── Да → Плейбук
└── Сложный сценарий (10+ задач)?
    ├── Требуется переиспользование?
    │   ├── Да → Роль
    │   └── Нет → Плейбук с include_tasks
    └── Требуются собственные модули/плагины?
        └── Да → Коллекция
```

### Принятие решений: контекст SRE

| Ситуация | Выбор | Обоснование |
| :--- | :--- | :--- |
| Emergency restart сервиса | Плейбук | Скорость важнее переиспользования |
| Изменение конфигурации Nginx | Роль | Атомарность, тестируемость, откат |
| Корпоративные стандарты безопасности | Composite Role | Агрегация security + monitoring + logging |
| Новый модуль для работы с API | Коллекция | Пространство имен, версионирование |
| Патч-вторник на 100+ серверов | Плейбук + throttle | Централизованный контроль параллелизма |

### Когда превращать плейбук в роль

- Код дублируется в ≥2 плейбуках
- Логика становится сложнее 10 задач
- Необходимо тестирование через Molecule
- Команда разработки расширяется
- SRE: требуется granular observability и blast radius control

### Когда превращать роль в коллекцию

- Появилась необходимость в собственных модулях
- Требуется строгое пространство имен
- Нужно распространение через Automation Hub
- Зависимости от внешних коллекций
- DevOps: требуется enterprise-уровень управления контентом

### Граничные случаи

1. **Плейбук с одной ролью:** Если плейбук вызывает только одну роль и не содержит дополнительной логики — рассмотрите превращение в роль с `entry_points` или оставьте плейбук-обертку для ясности.
2. **Роль с conditional включением:** Если роль выполняется только при определенных условиях — используйте `include_role` с `when` вместо `roles:`.
3. **Коллекция с одной ролью:** Начинается с версии 1.0.0. Если не планируются модули/плагины — оставьте роль.
4. **Utility Role с side effects:** Utility роли не должны иметь побочных эффектов (создание файлов вне role_path, изменение глобальных фактов без явного экспорта).
5. **Версионирование ролей в CI/CD:** Фиксируйте версии в `requirements.yml` для каждого окружения. Разные окружения могут использовать разные версии одной роли.

### Ограничения

| Абстракция | Ограничение |
| :--- | :--- |
| **Плейбук** | Нет встроенного версионирования, сложное переиспользование, риск "god playbook" |
| **Роль** | Ограниченная расширяемость (нет кастомных модулей), глобальное пространство имен |
| **Коллекция** | Сложность публикации, требуется Automation Hub/Galaxy, накладные расходы на поддержку пространства имен |
| **Utility Role** | Сложность отладки при глубоких цепочках зависимостей, риск циклических ссылок |
| **Composite Role** | Дополнительный слой абстракции, требуется документация зависимостей |
