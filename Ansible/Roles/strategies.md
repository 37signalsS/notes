# Стратегии работы с ролями Ansible

## Определения

**Стратегия разбиения ролей** — подход к декомпозиции автоматизации на логические модули (роли) для улучшения переиспользования, тестируемости и поддерживаемости кода.

**Паттерн проектирования ролей** — типовое решение для организации структуры и взаимодействия ролей в проекте Ansible.

---

## Основные концепции

### Стратегии разбиения ролей

| Стратегия | Описание | Пример |
| :--- | :--- | :--- |
| **По компонентам** | Каждая роль отвечает за один логический сервис | `web`, `db`, `cache`, `monitoring` |
| **По слоям** | Разделение по уровням абстракции | `base` (пакеты, пользователи), `hardening` (безопасность), `runtime` (приложения) |
| **По платформам** | Вынос платформенных различий в условные задачи | `os-specific.yml` с `when:` для разных ОС |
| **По доменам ответственности** | Разбиение по функциональным областям | `networking`, `logging`, `proxy` |

### Принципы проектирования

1. **Единая ответственность:** Роль должна решать одну задачу и делать это хорошо.
2. **Минимальные зависимости:** Роль не должна зависеть от переменных из `host_vars` или других ролей.
3. **Параметризация:** Все настраиваемые значения выносятся в переменные (`defaults/main.yml`).
4. **Идемпотентность:** Повторный запуск роли не должен изменять состояние системы.

## Практические сценарии

### Сценарий 1: Многослойная архитектура

Плейбук применяет роли последовательно по слоям:

```yaml
---
- name: Apply base configuration
  hosts: all
  roles:
    - base        # Пакеты, пользователи, базовая настройка
    - hardening   # Политики безопасности

- name: Deploy application stack
  hosts: webservers
  roles:
    - nginx       # Веб-сервер
    - php         # Runtime приложения
    - monitoring  # Агенты мониторинга
```

### Сценарий 2: Кроссплатформенная роль

Вместо создания дублирующих ролей для разных ОС используйте условные включения:

```yaml
# roles/common/tasks/main.yml
---
- name: Include OS-specific tasks
  ansible.builtin.include_tasks: "{{ ansible_os_family | lower }}.yml"
  when: ansible_os_family in ['Debian', 'RedHat']
```

Структура файлов:

```
roles/common/
├── tasks/
│   ├── main.yml
│   ├── debian.yml
│   └── redhat.yml
```

### Сценарий 3: Композиция ролей через зависимости

Определите зависимости в `meta/main.yml` для автоматического применения связанных ролей:

```yaml
# roles/webapp/meta/main.yml
dependencies:
  - role: common
  - role: nginx
  - role: postgresql
    vars:
      postgresql_databases:
        - webapp_db
```

## Дополнительная информация

### Продвинутые паттерны

**Паттерн "Utility Role"** — создание служебной роли-библиотеки для общих компонентов (задач и обработчиков). Подробное описание в [ansible_advanced_role_structure.md](../ansible_advanced_role_structure.md).

### Антипаттерны

Частые ошибки при проектировании ролей:

- Роль зависит от переменных из `host_vars`
- Две роли используют общий файл задач через `include`
- Жестко заданные значения вместо переменных

Подробнее см. [ansible_bad_practices.md](../ansible_bad_practices.md).
