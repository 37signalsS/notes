# Стратегии проектирования ролей Ansible

## Определения

**Стратегия разбиения ролей** — методология декомпозиции автоматизации на независимые логические модули для повышения переиспользования кода, упрощения тестирования и поддержки.

**Композиция ролей** — процесс объединения нескольких специализированных ролей для решения комплексной задачи настройки узла.

---

## Основные концепции

### Стратегии декомпозиции

| Стратегия | Описание | Пример |
| :--- | :--- | :--- |
| **По компонентам (Component-based)** | Одна роль = один технический сервис или приложение. Самый распространенный подход. | `nginx`, `postgresql`, `redis` |
| **По слоям (Layered)** | Разделение на уровни абстракции: инфраструктура, платформа, приложение. | `base_os`, `security_hardening`, `app_runtime` |
| **По функциональным ролям (Capability-based)** | Группировка по бизнес-функциям или доменам ответственности. | `monitoring_agent`, `backup_client`, `logging` |
| **Микро-роли (Micro-roles)** | Максимальное дробление на атомарные функции. Полезно для сложных композиций. | `user_management`, `ssh_config`, `motd` |

### Принципы проектирования

1. **Единая ответственность (Single Responsibility):** Роль должна выполнять одну задачу. Если роль устанавливает и базу данных, и веб-сервер — её нужно разделить.
2. **Параметризация (Defaults first):** Все настройки должны иметь значения по умолчанию в `defaults/main.yml`. Избегайте жестко заданных путей и имен в задачах.
3. **Автономность:** Роль не должна полагаться на переменные, определенные в других ролях (за исключением глобальных фактов).
4. **Идемпотентность:** Многократный запуск роли не должен приводить к изменениям, если система уже в целевом состоянии.
5. **Версионность:** При использовании внешних ролей (из Galaxy или Git) всегда фиксируйте версии.

### Современные подходы

*   **Переход к коллекциям (Collections):** Вместо набора разрозненных ролей используйте [Collections](../ansible_roles.md#коллекция-collection), чтобы поставлять роли вместе с необходимыми модулями и плагинами.
*   **Shared Tasks:** Для очень мелких повторяющихся действий используйте общие файлы задач (`shared_tasks/`), которые подключаются через `include_tasks`.

## Практические сценарии

### Сценарий 1: Многослойная конфигурация узла

Комбинация базовой настройки безопасности и прикладного ПО:

```yaml
---
- name: Web Server Setup
  hosts: webservers
  roles:
    - role: system_base       # Общие настройки ОС
    - role: security_hard     # Настройки Firewall и SSH
    - role: nginx             # Веб-сервер
    - role: app_deploy        # Деплой кода приложения
```

### Сценарий 2: Кроссплатформенная логика через динамические включения

Вместо нагромождения условий `when` в каждой задаче, используйте включение файлов по фактам ОС:

```yaml
# tasks/main.yml
- name: Load OS-specific variables
  ansible.builtin.include_vars: "{{ item }}"
  with_first_found:
    - files:
        - "{{ ansible_facts['os_family'] }}.yml"
        - "default.yml"
      paths: ["../vars"]

- name: Execute OS-specific tasks
  ansible.builtin.include_tasks: "{{ ansible_facts['os_family'] | lower }}.yml"
```

### Сценарий 3: Композиция через зависимости (`meta/main.yml`)

Автоматическое выполнение зависимых ролей. Например, роль мониторинга приложения требует установленного агента:

```yaml
# meta/main.yml в роли 'app_monitoring'
dependencies:
  - role: prometheus_node_exporter
  - role: common_logging_agent
```

## Дополнительная информация

### Продвинутые паттерны

*   **[Паттерн Utility Role](utility_role_pattern.md):** Создание роли-библиотеки для хранения общих обработчиков (handlers) и задач, импортируемых другими ролями.
*   **Wrapper Roles:** Роль-обертка над сторонней ролью из Galaxy для задания специфических для компании настроек по умолчанию.

### Антипаттерны

*   **God Role:** Одна роль, которая делает "всё" (установка, конфиг, бэкап, мониторинг в одном флаконе).
*   **Tight Coupling:** Роли, которые не работают друг без друга или требуют строгого порядка определения переменных в инвентаре.
*   **Hardcoding:** Использование прямых путей (`/var/www/html`) вместо переменных (`nginx_web_root`).

Подробнее см. в **[Антипаттерны Ansible](../ansible_bad_practices.md)**.
