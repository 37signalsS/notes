# Стратегии работы с ролями Ansible

## Определения

**Стратегия разбиения ролей** — подход к декомпозиции автоматизации на логические модули (роли) для улучшения переиспользования, тестируемости и поддерживаемости кода.

**Паттерн проектирования ролей** — типовое решение для организации структуры и взаимодействия ролей в проекте Ansible.

---

## Основные концепции

### Стратегии разбиения ролей

| Стратегия | Описание | Пример |
| :--- | :--- | :--- |
| **По компонентам** | Каждая роль отвечает за один логический сервис | `web`, `db`, `cache`, `monitoring` |
| **По слоям** | Разделение по уровням абстракции (инфраструктурный, платформенный, прикладной) | `base` (пакеты), `hardening` (безопасность), `runtime` |
| **По платформам** | Вынос платформенных различий в условные задачи или отдельные роли | `os-specific.yml` с условиями `when` |
| **По функциональным областям** | Группировка задач по доменам ответственности | `networking`, `logging`, `backup` |

### Принципы проектирования ролей

1. **Единая ответственность (Single Responsibility):** Роль должна решать одну конкретную задачу и быть максимально автономной.
2. **Минимальные зависимости:** Избегайте неявных зависимостей от внешних переменных (`host_vars`) или порядка выполнения других ролей.
3. **Параметризация:** Все настраиваемые значения выносите в переменные по умолчанию (`defaults/main.yml`) для гибкой настройки под разные окружения.
4. **Идемпотентность:** Повторный запуск роли не должен изменять состояние системы, если она уже находится в целевом состоянии.

## Практические сценарии

### Сценарий 1: Многослойная архитектура

Плейбук применяет роли последовательно, переходя от общих настроек к специфичным для приложения:

```yaml
---
- name: Apply base configuration
  hosts: all
  roles:
    - base        # Общие пакеты, пользователи
    - hardening   # Настройка безопасности (SSH, Firewall)

- name: Deploy application stack
  hosts: webservers
  roles:
    - nginx       # Установка веб-сервера
    - php         # Среда выполнения
    - monitoring  # Агенты сбора метрик
```

### Сценарий 2: Кроссплатформенная роль через динамическое включение

Использование динамического импорта задач в зависимости от семейства операционной системы:

```yaml
# roles/common/tasks/main.yml
---
- name: Include OS-specific tasks
  ansible.builtin.include_tasks: "{{ ansible_facts['os_family'] | lower }}.yml"
  when: ansible_facts['os_family'] in ['Debian', 'RedHat']
```

Для реализации этого сценария необходимо создать файлы `debian.yml` и `redhat.yml` в директории `tasks/` роли. Подробнее о кроссплатформенности — в **[Кроссплатформенные концепции](../CrossPlatform/concepts.md)**.

### Сценарий 3: Композиция ролей через зависимости

Использование `meta/main.yml` для автоматического подключения необходимых ролей-зависимостей:

```yaml
# roles/webapp/meta/main.yml
dependencies:
  - role: common
  - role: nginx
  - role: postgresql
    vars:
      postgresql_databases:
        - webapp_db
```

## Дополнительная информация

### Продвинутые паттерны

**Паттерн "Utility Role"** — создание служебной роли-библиотеки для хранения общих компонентов (задач и обработчиков), которые импортируются другими ролями. Это позволяет избежать дублирования кода и централизовать управление общими операциями.
Подробное описание реализации — в **[Паттерн Utility Role](utility_role_pattern.md)**.

### Антипаттерны и частые ошибки

При проектировании ролей следует избегать следующих практик:

- Прямое обращение к `host_vars` или `group_vars` внутри логики роли.
- Использование общего файла задач несколькими ролями через `include` (скрытые зависимости).
- Жесткое кодирование (hardcode) значений вместо использования переменных.

Полный список антипаттернов и рекомендации по их исправлению приведены в **[Антипаттерны Ansible](../ansible_bad_practices.md)**.
