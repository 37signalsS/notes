# Ansible: Выполнение плейбуков

## Определения

**ansible-playbook** — утилита командной строки для запуска и выполнения плейбуков Ansible на управляемых хостах.

**Плей (Play)** — логически сгруппированный набор задач, применяемый к определенной группе хостов из инвентаря.

**Задача (Task)** — атомарная операция в плейбуке, вызывающая конкретный модуль Ansible для достижения желаемого состояния системы.

**PLAY RECAP** — итоговая сводка выполнения плейбука, отображающая статус задач по каждому хосту (ok, changed, unreachable, failed).

## Базовые концепции

### Запуск плейбука

Плейбуки запускаются с помощью команды `ansible-playbook`. Целевые серверы определяются в файле [инвентаризации (inventory)](ansible_setup_and_config.md).

```bash
ansible-playbook -i inventory.ini --ask-pass playbook.yml
# → Выполнение задач из playbook.yml на серверах из inventory.ini...
```

**Ключевые элементы команды:**

* `ansible-playbook`: Основная команда для инициации выполнения плейбука.
* `-i inventory.ini`: Указывает путь к файлу инвентаризации.
* `--ask-pass` (или `-k`): Запрашивает пароль для SSH-подключения к удаленным хостам.
* `playbook.yml`: Путь к файлу [плейбука](PlaybookStructure/basics.md), который необходимо выполнить.

### Анализ вывода выполнения

**PLAY**

```text
PLAY [Install and start nginx] ********************************************
```

Обозначает начало выполнения "плея" (play) — логически сгруппированного набора задач, применяемого к определенной группе хостов.

**TASK**

```text
TASK [Gathering Facts] ******************************************************
ok: [ws01]

TASK [install nginx] *******************************************************
changed: [ws01]
```

* `Gathering Facts`: Первая задача, выполняемая по умолчанию для сбора [фактов](PlaybookStructure/variables.md) о системе удаленного хоста.
* `changed`: Статус задачи, означающий, что она внесла изменения в систему (например, установила пакет, изменила конфигурационный файл).
* `ok`: Статус задачи, означающий, что система уже находилась в желаемом состоянии, и никаких изменений не потребовалось.

**PLAY RECAP**

```text
PLAY RECAP *****************************************************************
ws01                       : ok=5    changed=4    unreachable=0    failed=0
```

Итоговая сводка по всем хостам, участвовавшим в выполнении плейбука.

* `ok`: Количество задач, успешно выполненных без изменений.
* `changed`: Количество задач, успешно выполненных с изменениями.
* `unreachable`: Количество хостов, к которым Ansible не смог подключиться.
* `failed`: Количество хостов, на которых произошел сбой хотя бы одной задачи. (`failed > 0` означает, что плейбук не был выполнен успешно).

### Ключевые опции командной строки

Команда `ansible-playbook` поддерживает множество опций для гибкого управления выполнением плейбуков.

* `--inventory` ( `-i`): Указывает путь к файлу инвентаризации. Пример:

    ```bash
    ansible-playbook -i /path/to/inventory.ini playbook.yml
    # → Выполнение плейбука с указанным инвентарем...
    ```

* `--limit`: Ограничивает выполнение плейбука только указанными хостами или группами. Пример:

    ```bash
    # Выполнить только на хосте web1
    ansible-playbook -i inventory.ini --limit web1 playbook.yml
    # → Выполнение только для хоста web1...
    ```

* `--list-hosts`: Выводит список хостов, на которых будет выполнен плейбук, без фактического запуска. Полезно для проверки правильности инвентаря и фильтров.

    ```bash
    ansible-playbook -i inventory.ini site.yml --list-hosts
    # →   hosts (2):
    # →     web1
    # →     web2
    ```

* `--list-tasks`: Выводит список всех задач, которые будут выполнены, без фактического запуска. Полезно для анализа порядка выполнения и проверки тегов.

    ```bash
    ansible-playbook -i inventory.ini site.yml --list-tasks
    # →   play #1 (webservers): webservers  TAGS: []
    # →     tasks:
    # →       install nginx TAGS: [nginx]
    ```

* `--check` (dry-run): Запускает плейбук в режиме «сухого запуска» — задачи выполняются, но реальные изменения на хостах не вносятся. Модули сообщают, что *изменилось бы*, но не применяют изменения.

    ```bash
    ansible-playbook -i inventory.ini site.yml --check --diff
    # → Отображение ожидаемых изменений без их фактического применения...
    ```

* `--diff`: Показывает изменения, которые будут внесены в файлы, в стиле Git `diff`. Комбинируется с `--check` для контроля перед применением изменений.
* `--step`: Включает пошаговое выполнение. Перед каждой задачей Ansible будет спрашивать подтверждение (`y`/`n`/`c`) на выполнение.
* `--skip-tags`: Пропускает задачи с указанными тегами. Полезно для исключения опциональных задач (например, установка опциональных пакетов).

    ```bash
    ansible-playbook -i inventory.ini site.yml --skip-tags optional
    # → Пропуск задач с тегом 'optional'...
    ```

* `--tags`: Выполняет только задачи с указанными тегами.

    ```bash
    ansible-playbook -i inventory.ini site.yml --tags nginx
    # → Выполнение только задач с тегом 'nginx'...
    ```

* `--force-handlers`: Заставляет выполнять [обработчики (`handlers`)](PlaybookStructure/basics.md#обработчики-handlers-и-идемпотентность) даже если плейбук завершился с ошибкой. Рекомендуется для CI/CD-пайплайнов, чтобы гарантировать выполнение очистки или перезапуска сервисов.
* `--become`: Указывает на необходимость [повышения привилегий (`sudo`)](ansible_security_best_practices.md) для выполнения задач на удаленном хосте.
* `--ask-pass` (`-k`): Запрашивает пароль для SSH-подключения.
* `--ask-become-pass` (`-K`): Запрашивает пароль для повышения привилегий (`sudo`).

## Практические сценарии

### Интеграция с Vagrant: указание inventory

При использовании Ansible в качестве provisioner'а для Vagrant могут возникать проблемы с обнаружением хостов, если инвентарь определен в отдельном файле.

* **Проблема**: Vagrant по умолчанию создает временный inventory-файл только для создаваемых им машин и не знает о группах, определенных в вашем статическом файле `inventory.ini`. Это приводит к предупреждениям `[WARNING]: Could not match supplied host pattern...` и ошибкам `skipping: no hosts matched`.
* **Решение**: Чтобы Vagrant использовал ваш кастомный inventory-файл, необходимо явно указать путь к нему в `Vagrantfile` внутри блока конфигурации Ansible.

    **Пример в `Vagrantfile`:**

    ```ruby
    Vagrant.configure("2") do |config|
      # ...
      config.vm.provision "ansible" do |ansible|
        ansible.playbook = "playbook.yml"
        # Явно указываем путь к файлу инвентаря
        ansible.inventory_path = "path/to/your/inventory.ini"
      end
      # ...
    end
    ```

    Это заставит Ansible использовать правильный инвентарь, и он сможет находить хосты и группы, определенные в нем.
