# Ansible: Выполнение плейбуков

## Определения

**Выполнение плейбука** — это процесс запуска файла Ansible Playbook (`.yml`), который автоматизирует задачи по управлению конфигурацией, развертыванию или оркестрации на целевых хостах. Этот процесс инициируется командой `ansible-playbook` и является центральным элементом работы с Ansible.

## Основные концепции

### Запуск плейбука

Плейбуки запускаются с помощью команды `ansible-playbook`. Целевые серверы определяются в файле инвентаризации (inventory).

```bash
ansible-playbook -i inventory.ini --ask-pass playbook.yml
```
**Ключевые элементы команды:**
*   `ansible-playbook`: Основная команда для инициации выполнения плейбука.
*   `-i inventory.ini`: Указывает путь к файлу инвентаризации, содержащему список управляемых хостов.
*   `--ask-pass` (или `-k`): Запрашивает пароль для SSH-подключения к удаленным хостам.
*   `playbook.yml`: Путь к файлу плейбука, который необходимо выполнить.

### Анализ вывода выполнения

При запуске плейбука Ansible предоставляет подробный вывод, который информирует о ходе выполнения задач и состоянии управляемых хостов.

**PLAY**
```
PLAY [Install and start nginx] ********************************************
```
Обозначает начало выполнения "плея" (play) — логически сгруппированного набора задач, применяемого к определенной группе хостов.

**TASK**
```
TASK [Gathering Facts] ******************************************************
ok: [ws01]

TASK [install nginx] *******************************************************
changed: [ws01]
```
*   `Gathering Facts`: Первая задача, выполняемая по умолчанию для сбора информации (фактов) о системе удаленного хоста.
*   `changed`: Статус задачи, означающий, что она внесла изменения в систему (например, установила пакет, изменила конфигурационный файл).
*   `ok`: Статус задачи, означающий, что система уже находилась в желаемом состоянии, и никаких изменений не потребовалось.

**PLAY RECAP**
```
PLAY RECAP *****************************************************************
ws01                       : ok=5    changed=4    unreachable=0    failed=0
```
Итоговая сводка по всем хостам, участвовавшим в выполнении плейбука.
*   `ok`: Количество задач, успешно выполненных без изменений.
*   `changed`: Количество задач, успешно выполненных с изменениями.
*   `unreachable`: Количество хостов, к которым Ansible не смог подключиться.
*   `failed`: Количество хостов, на которых произошел сбой хотя бы одной задачи. (`failed > 0` означает, что плейбук не был выполнен успешно).

## Практические сценарии

### Ключевые опции командной строки

Команда `ansible-playbook` поддерживает множество опций для гибкого управления выполнением плейбуков.

*   `--inventory` ( `-i`): Указывает путь к файлу инвентаризации. Пример:
    ```bash
    ansible-playbook -i /path/to/inventory.ini playbook.yml
    ```
*   `--limit`: Ограничивает выполнение плейбука только указанными хостами или группами. Пример:
    ```bash
    # Выполнить только на хосте web1
    ansible-playbook -i inventory.ini --limit web1 playbook.yml
    ```
*   `--diff`: Показывает изменения, которые будут внесены в файлы, в стиле Git `diff`. Это полезно для контроля перед применением изменений.
*   `--step`: Включает пошаговое выполнение. Перед каждой задачей Ansible будет спрашивать подтверждение (`y`/`n`/`c`) на выполнение.
*   `--force-handlers`: Заставляет выполнять обработчики (`handlers`) даже если плейбук завершился с ошибкой. Рекомендуется для CI/CD-пайплайнов, чтобы гарантировать выполнение очистки или перезапуска сервисов.
*   `--become`: Указывает на необходимость повышения привилегий (`sudo`) для выполнения задач на удаленном хосте.
*   `--ask-pass` (`-k`): Запрашивает пароль для SSH-подключения.
*   `--ask-become-pass` (`-K`): Запрашивает пароль для повышения привилегий (`sudo`).

### Интеграция с Vagrant: указание inventory

При использовании Ansible в качестве provisioner'а для Vagrant могут возникать проблемы с обнаружением хостов, если инвентарь определен в отдельном файле.

*   **Проблема**: Vagrant по умолчанию создает временный inventory-файл только для создаваемых им машин и не знает о группах, определенных в вашем статическом файле `inventory.ini`. Это приводит к предупреждениям `[WARNING]: Could not match supplied host pattern...` и ошибкам `skipping: no hosts matched`.
*   **Решение**: Чтобы Vagrant использовал ваш кастомный inventory-файл, необходимо явно указать путь к нему в `Vagrantfile` внутри блока конфигурации Ansible.

    **Пример в `Vagrantfile`:**
    ```ruby
    Vagrant.configure("2") do |config|
      # ...
      config.vm.provision "ansible" do |ansible|
        ansible.playbook = "playbook.yml"
        # Явно указываем путь к файлу инвентаря
        ansible.inventory_path = "path/to/your/inventory.ini"
      end
      # ...
    end
    ```
    Это заставит Ansible использовать правильный инвентарь, и он сможет находить хосты и группы, определенные в нем.
