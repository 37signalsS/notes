# Кроссплатформенные плейбуки Ansible: Концепции

## Определения

- **Кроссплатформенный плейбук (Cross-Platform Playbook)** — сценарий, спроектированный для корректного выполнения на различных операционных системах (ОС) путем адаптации логики и параметров к целевой среде.
- **Факты Ansible (`ansible_facts`)** — системные переменные, автоматически собираемые Ansible с управляемых узлов (ОС, сетевые интерфейсы, архитектура процессора и др.).
- **Иерархия идентификации системы**:
    - **`ansible_facts['os_family']`** — верхнеуровневое семейство ОС (например, `Debian`, `RedHat`, `Suse`, `Windows`).
    - **`ansible_facts['distribution']`** — конкретный дистрибутив (например, `Ubuntu`, `CentOS`, `Fedora`).
    - **`ansible_facts['distribution_major_version']`** — мажорная версия ОС (например, `22`, `24` для Ubuntu; `7`, `8`, `9` для RHEL).

## Основные концепции

### Ключевые принципы разработки

1.  **Абстракция через переменные**: Никогда не используйте жестко заданные пути или имена пакетов в задачах. Выносите их в переменные, специфичные для ОС.
2.  **Использование словаря фактов**: Рекомендуется использовать современный синтаксис обращения к фактам через словарь: `ansible_facts['os_family']` вместо устаревшего `ansible_os_family`.
3.  **Принцип "Fail Fast"**: Если роль не поддерживает конкретную ОС, добавьте проверку (assertion) в начало `tasks/main.yml`.
4.  **Предпочтение универсальным модулям**: Используйте модуль `package` для простых операций установки, но переходите на нативные модули (`apt`, `dnf`), если требуются специфичные параметры (например, `update_cache`).

### Стратегии разделения логики

#### 1. Динамическое включение задач (`include_tasks`)
Подходит, когда наборы действий для разных ОС кардинально различаются (например, разная структура конфигурационных файлов).

```yaml
# tasks/main.yml
- name: Включение задач для конкретного семейства ОС
  ansible.builtin.include_tasks: "{{ ansible_facts['os_family'] | lower }}.yml"
```

#### 2. Загрузка переменных по фактам (`include_vars`)
Самый эффективный способ. Позволяет использовать один и тот же набор задач, подставляя в них системно-зависимые переменные.

```yaml
# tasks/main.yml
- name: Загрузка переменных для ОС
  ansible.builtin.include_vars: "{{ item }}"
  with_first_found:
    - files:
        - "{{ ansible_facts['distribution'] }}-{{ ansible_facts['distribution_major_version'] }}.yml"
        - "{{ ansible_facts['distribution'] }}.yml"
        - "{{ ansible_facts['os_family'] }}.yml"
        - "default.yml"
      paths: ["../vars"]
```

### Использование значений по умолчанию (`defaults`)

Директория `defaults/` в роли предназначена для переменных с самым низким приоритетом. Здесь следует определять параметры, которые являются общими для всех ОС или служат безопасными значениями "по умолчанию".

**Пример `defaults/main.yml`:**
```yaml
app_port: 8080
app_user: "appuser" # Может быть переопределено в vars/RedHat.yml как "nginx"
```

## Практические сценарии

### Сценарий 1: Адаптация параметров "на лету"
Использование тернарного оператора для простых различий, чтобы не создавать лишние файлы переменных.

```yaml
- name: Установка веб-сервера
  ansible.builtin.package:
    name: "{{ 'apache2' if ansible_facts['os_family'] == 'Debian' else 'httpd' }}"
    state: present

- name: Определение группы сервиса
  ansible.builtin.set_fact:
    web_group: "{{ (ansible_facts['os_family'] == 'RedHat') | ternary('nginx', 'www-data') }}"
```

### Сценарий 2: Кроссплатформенная проверка путей
Использование модуля `stat` для проверки существования директорий, которые могут отличаться в разных дистрибутивах.

```yaml
- name: Проверка директории конфигурации
  ansible.builtin.stat:
    path: "{{ config_dir }}"
  register: dir_check

- name: Создание конфига, если путь валиден
  ansible.builtin.template:
    src: config.j2
    dest: "{{ config_dir }}/app.conf"
  when: dir_check.stat.exists and dir_check.stat.isdir
```

### Сценарий 3: Блокировка неподдерживаемых систем
Гарантирует, что плейбук не нанесет вред системе, для которой он не тестировался.

```yaml
- name: Проверка поддержки ОС
  ansible.builtin.assert:
    that:
      - ansible_facts['os_family'] in ['Debian', 'RedHat']
    fail_msg: "Данная роль не поддерживает {{ ansible_facts['os_family'] }}"
```
