# Ansible: Управление ходом выполнения плейбука

## Определения

**Управление ходом выполнения** — это механизмы Ansible, позволяющие контролировать, какие задачи выполняются, когда и при каких условиях. К ним относятся условные конструкции, циклы, обработчики и теги.

## Основные концепции

- **Условные конструкции (`when`)**: Позволяют выполнять задачу только при выполнении определенного условия.
- **Циклы (`loop`)**: Позволяют выполнять одну и ту же задачу несколько раз с разными данными.
- **Регистрация результатов (`register`)**: Сохраняет результат выполнения задачи в переменную для последующего использования.
- **Обработка ошибок**: Механизмы `block`, `rescue`, `always`, `ignore_errors` для управления ошибками.
- **Теги (Tags)**: Позволяют выборочно запускать или пропускать части плейбука.

## Условные конструкции (when)

Директива `when` позволяет выполнять задачу только при выполнении определенного условия.

- **Логическое "И" (AND):** Список условий.
- **Логическое "ИЛИ" (OR):**

```yaml
- name: "Перезагрузить сервис только если включено и были изменения"
  ansible.builtin.systemd:
    name: my_service
    state: reloaded
  when:
    - my_service_enabled
    - config_result is changed
```

## Циклы (loop)

Позволяют выполнять одну и ту же задачу несколько раз с разными данными. `loop` является современным стандартом, заменяя `with_items`.

```yaml
- name: Установка нескольких пакетов
  ansible.builtin.apt:
    name: "{{ item.name }}"
    state: "{{ item.state }}"
  loop:
    - { name: 'nginx', state: 'present' }
    - { name: 'htop', state: 'latest' }
```

## Регистрация результатов (register)

Директива `register` позволяет сохранить результат выполнения задачи в переменную. По умолчанию Ansible выводит в консоль только краткий статус (`ok`, `changed`, `failed`), скрывая детали работы модуля. `register` "захватывает" полный JSON-ответ модуля для последующего анализа.

### Зачем и для чего нужен register:

1.  **Условное выполнение (Control Flow):** Самый частый сценарий — использование статуса `changed` или `failed` в последующих задачах через `when`.
2.  **Извлечение данных:** Получение конкретных значений, которые генерирует модуль (например, ID созданного инстанса, сгенерированный пароль, список найденных файлов).
3.  **Передача состояния между задачами:** Если задача B зависит от результата задачи A (например, нужно использовать IP-адрес, динамически выделенный на шаге A).
4.  **Отладка (Debugging):** Просмотр структуры ответа модуля через `ansible.builtin.debug: var=my_var`.
5.  **Обработка ошибок:** Проверка кода возврата (`rc`) или специфических сообщений об ошибках для принятия решения о продолжении или остановке плейбука.

```yaml
- name: "Сгенерировать конфигурационный файл"
  ansible.builtin.template:
    src: whitelist.j2
    dest: /etc/myapp/whitelist.conf
  register: whitelist_config # Сохраняем весь объект ответа

- name: "Перезагрузить сервис, только если конфиг изменился"
  ansible.builtin.service:
    name: myapp
    state: reloaded
  when: whitelist_config is changed # Используем свойство 'changed' из зарегистрированной переменной
```

## Обработка ошибок и управление статусом

Ansible позволяет переопределять стандартное поведение модулей в случае ошибок или при определении статуса "изменено".

### Переопределение статуса (changed_when)

Директива `changed_when` позволяет вручную контролировать, когда задача сообщает о внесении изменений. Это критично для модулей `command` и `shell`, которые по умолчанию всегда возвращают `changed: true`.

- **`changed_when: false`**: Задача выполнится, но всегда будет иметь статус `ok`. Полезно для команд чтения данных, проверки версий или мониторинга, которые не меняют состояние системы.
- **`changed_when: true`**: Задача всегда будет иметь статус `changed`. 

**Типичные сценарии использования `changed_when: true`:**

1.  **Гарантированный запуск обработчиков:** Когда команда выполняет действие, которое **обязательно** требует уведомления (`notify`) обработчика (например, перезапуск сервиса после сложной переконфигурации скриптом).
2.  **Фиксация факта работы:** Если скрипт внутри `shell` выполняет изменения, но не возвращает специфических признаков успеха, а вы хотите видеть в отчете `changed`, чтобы подтвердить выполнение.
3.  **Принудительная синхронизация:** В ситуациях, когда вы используете Ansible как инструмент исполнения (ad-hoc задачи в плейбуке), где важно видеть, что шаг был выполнен, а не пропущен.

```yaml
- name: "Обновить кэш приложения, если версия изменилась"
  ansible.builtin.shell: /usr/bin/update_app_cache.sh
  register: app_update
  # Считаем задачу изменившейся, только если в выводе есть "Updated"
  changed_when: "'Updated' in app_update.stdout"

- name: "Принудительный перезапуск через handler"
  ansible.builtin.command: /usr/bin/force_refresh.sh
  changed_when: true # Всегда вызывает notify, даже если скрипт идемпотентен
  notify: Restart Service
```

### Переопределение ошибок (failed_when)

Директива `failed_when` позволяет указать, какие условия считать критическим сбоем.

- **`failed_when: false`**: Принудительно помечает задачу как успешную (`ok`), даже если модуль вернул ошибку.
    *   **Зачем:** Используется для "мягких" проверок, когда ошибка ожидаема и не должна прерывать выполнение.
    *   **Отличие от `ignore_errors: true`**: `failed_when: false` делает статус задачи **`ok`** (зеленый). `ignore_errors: true` оставляет статус **`failed`** (красный), но позволяет плейбуку идти дальше.

**Типичные сценарии (распространенное применение):**

1.  **Проверка наличия ресурса:** Когда команда возвращает ненулевой код, если объект не найден (например, `grep` или `systemctl status`).
2.  **Запуск команд с "допустимым" сбоем:** Когда результат команды будет проанализирован позже в другой задаче.
3.  **Предотвращение остановки на необязательных шагах:** Очистка временных файлов, которых может не быть.

```yaml
- name: "Проверить наличие ошибки в выводе"
  ansible.builtin.command: /usr/bin/check_status.sh
  register: status_out
  # Задача провалена, если код возврата не 0 ИЛИ в выводе есть "CRITICAL"
  failed_when: 
    - status_out.rc != 0
    - "'CRITICAL' in status_out.stdout"

- name: "Проверить существование пользователя (может не быть)"
  ansible.builtin.command: id non_existent_user
  register: user_check
  failed_when: false # Не останавливаемся, если пользователя нет
```

- `ignore_errors: true`: Продолжить выполнение плейбука, даже если задача завершилась сбоем (статус будет `failed`, но выполнение не остановится).
- `block, rescue, always`: Аналог `try...catch...finally` для обработки ошибок на уровне групп задач. Пример: [advanced.md](advanced.md#сценарий-8-block--rescue--always--rollback).
- `changed_when: false`: Сделать команду идемпотентной в отчетах.

## Теги (Tags)

Теги позволяют выборочно запускать или пропускать части плейбука, что крайне полезно для отладки, ускорения выполнения и разделения сложных плейбуков на логические части. Теги можно применять к отдельным задачам, блокам, ролям и даже целым `include` или `import`.

#### Применение тегов

```yaml
tasks:
  - name: Install base packages
    ansible.builtin.apt:
      name: "{{ item }}"
    loop:
      - htop
      - git
    tags:
      - packages
      - base

  - name: Configure firewall
    community.general.ufw:
      rule: allow
      port: '80'
      proto: tcp
    tags:
      - firewall
      - security
```

#### Запуск с тегами

- **Выполнить только задачи с определенными тегами:**

    ```bash
    # Выполнить задачи с тегом 'packages' ИЛИ 'firewall'
    ansible-playbook my_playbook.yml --tags packages,firewall
    ```

- **Пропустить задачи с определенными тегами:**

    ```bash
    # Выполнить все, КРОМЕ задач с тегом 'security'
    ansible-playbook my_playbook.yml --skip-tags security
    ```

#### Специальные теги

Ansible имеет несколько встроенных тегов с особым поведением:

- `always`: Задача с этим тегом **всегда** будет выполняться, если только она не была явно пропущена с помощью `--skip-tags always`. Это полезно для критически важных задач (например, проверка конфигурации).

    ```yaml
    - name: "Always run this check"
      ansible.builtin.ping:
      tags:
        - always
    ```

- `never`: Задача с этим тегом **никогда** не будет выполняться по умолчанию. Ее можно запустить, только если явно указать тег с помощью `--tags never`. Это удобно для отладочных или опасных задач.

    ```yaml
    - name: "Debug task"
      ansible.builtin.debug:
        msg: "This is a debug message."
      tags:
        - never
    ```

- `tagged`: Выполняет только те задачи, у которых есть хотя бы один тег.

    ```bash
    ansible-playbook my_playbook.yml --tags tagged
    ```

- `untagged`: Выполняет только те задачи, у которых **нет ни одного** тега.

    ```bash
    ansible-playbook my_playbook.yml --tags untagged
    ```

- `all`: Выполняет все задачи (поведение по умолчанию).
