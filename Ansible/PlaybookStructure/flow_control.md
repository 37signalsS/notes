# Ansible: управление ходом выполнения

> **Надёжность: 10** (SSoT, актуализировано согласно Ansible 2.17+)

## Определения

**Управление ходом выполнения (Flow Control)** — механизмы Ansible, позволяющие динамически определять логику выполнения задач в зависимости от состояния системы, результатов предыдущих шагов или внешних условий.

**Условная конструкция (`when`)** — директива, определяющая выполнение задачи на основе логического выражения Jinja2. Поддерживает сложные составные условия.

**Цикл (`loop`)** — итератор, позволяющий выполнять одну задачу многократно для списка элементов. Современный стандарт, заменивший устаревшие конструкции `with_*`.

**Регистрация (`register`)** — механизм захвата и сохранения полного JSON-ответа модуля в переменную для последующего анализа и использования в логике плейбука.

**Тег (Tag)** — метка, позволяющая выборочно запускать или пропускать части плейбука при запуске через командную строку, не изменяя код.

## Базовые концепции

### Условные конструкции (when)

*   Принимает логические выражения в синтаксисе Jinja2 (без фигурных скобок `{{ }}`).
*   Если передается список условий, они трактуются как логическое «И» (AND).
*   Для логического «ИЛИ» (OR) используются явные операторы `or`.
*   Полезные тесты Jinja2: `is defined`, `is not defined`, `in`, `is match()`.

### Современные циклы (loop и loop_control)

Директива `loop` пришла на смену `with_items` и `with_dict`.
*   Текущий элемент итерации по умолчанию доступен через переменную `item`.
*   **Трансформация данных:** Для работы со словарями используется фильтр `dict2items`, для работы с вложенными списками — `subelements`.
*   **`loop_control`**: Позволяет тонко настраивать цикл:
    *   `loop_var`: Переопределяет имя переменной `item` (критично для вложенных циклов `include_tasks`).
    *   `pause`: Пауза между итерациями в секундах.
    *   `label`: Ограничивает объем вывода в консоль (скрывает длинные JSON-структуры).

### Регистрация и переопределение статусов

Ansible определяет успешность задачи по коду возврата (RC) и наличию изменений. Это поведение можно переопределить.
*   **`register`**: Захватывает полный объект ответа. Ключевые поля: `changed`, `failed`, `stdout`, `rc`.
*   **`changed_when`**: Задает условие, при котором задача считается изменившей систему (`changed: true`). Важно для идемпотентности модулей `shell` / `command`.
*   **`failed_when`**: Задает специфическое условие сбоя. Например, можно игнорировать ненулевой RC, если вывод содержит определенное предупреждение.

### Обработка ошибок (Error Handling)

*   **`ignore_errors: true`**: Выполнение продолжается даже при сбое задачи. Статус в логе остается `failed` (красный), но плейбук не прерывается.
*   **`block`, `rescue`, `always`**: Группировка задач для обработки исключений (аналог `try/catch/finally`):
    *   **`block`**: Основной набор задач. Если одна из них падает, управление передается в `rescue`.
    *   **`rescue`**: Выполняется только при ошибке внутри `block`. Задачи в `rescue` могут исправить ситуацию и вернуть статус плейбука в успешный.
    *   **`always`**: Выполняется всегда, даже если `block` упал, а `rescue` не смог обработать ошибку. Идеально для очистки ресурсов.

### Тегирование

Теги позволяют сегментировать плейбук.
*   **Специальные теги**:
    *   `always`: Задача выполняется всегда, если не пропущена явно через `--skip-tags always`.
    *   `never`: Задача никогда не выполняется, если не вызвана явно через `--tags never`.

## Практические сценарии

### Сценарий 1: Умная проверка состояния (changed_when / failed_when)

Типичный пример работы с `grep`, который возвращает код `1`, если ничего не найдено. Ansible по умолчанию считает это ошибкой. Мы переопределяем логику.

```yaml
- name: Проверить наличие настройки в конфигурации
  ansible.builtin.command: grep -q 'StrictHostKeyChecking no' /etc/ssh/ssh_config
  register: grep_result
  # Код 0 (найдено) или 1 (не найдено) считаем успехом. Остальные - реальная ошибка.
  failed_when: grep_result.rc not in [0, 1]
  # Чтение файла никогда не меняет состояние системы
  changed_when: false

- name: Добавить настройку, если она отсутствует
  ansible.builtin.lineinfile:
    path: /etc/ssh/ssh_config
    line: 'StrictHostKeyChecking no'
  when: grep_result.rc == 1
```

### Сценарий 2: Гарантированная очистка временных ресурсов (Block-Always)

Использование блоков для удаления временных файлов независимо от успеха операции сборки.

```yaml
- name: Работа с временными данными
  block:
    - name: Создать временную директорию
      ansible.builtin.file:
        path: /tmp/app_build
        state: directory

    - name: Сборка приложения (может упасть)
      ansible.builtin.command: /usr/bin/make_build --dir /tmp/app_build
  
  always:
    - name: Удалить временную директорию в любом случае
      ansible.builtin.file:
        path: /tmp/app_build
        state: absent
```

### Сценарий 3: Сложные циклы с loop_control

Итерация по словарю с ограничением вывода в консоль (использование `dict2items` и `label`).

```yaml
- name: Создание пользователей из словаря
  ansible.builtin.user:
    name: "{{ item.key }}"
    uid: "{{ item.value.uid }}"
    group: "{{ item.value.group }}"
    state: present
  loop: "{{ users_dict | dict2items }}"
  loop_control:
    # В консоль будет выводиться только имя пользователя, а не весь объект с паролями
    label: "{{ item.key }}"
  vars:
    users_dict:
      alice: { uid: 1001, group: 'developers' }
      bob:   { uid: 1002, group: 'admins' }
```

### Сценарий 4: Вложенные циклы через include_tasks и loop_var

При вызове динамических включений в цикле крайне важно переопределить `loop_var`, иначе внутренний цикл перезапишет переменную `item` внешнего цикла.

**Главный плейбук:**
```yaml
- name: Обработка каждого приложения
  ansible.builtin.include_tasks: process_app.yml
  loop: ['frontend', 'backend', 'api']
  loop_control:
    loop_var: app_name # Переопределяем item на app_name
```

**Файл `process_app.yml`:**
```yaml
- name: "Настройка компонентов для приложения {{ app_name }}"
  ansible.builtin.debug:
    msg: "Настраиваем {{ app_name }} - компонент {{ item }}"
  loop: ['config', 'service', 'logs']
  # Здесь используется стандартный item, и он не конфликтует с app_name
```
