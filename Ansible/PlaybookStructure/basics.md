# Ansible: Основы структуры плейбуков

## Определения

**Плейбук (Playbook)**: YAML-файл, который содержит один или несколько "плеев" (`plays`) для описания желаемого состояния системы и шагов по его достижению. Это основной инструмент для оркестрации в Ansible.

**Плей (Play)**: Основной строительный блок плейбука. Плей сопоставляет группу хостов из инвентаря с набором задач, которые на них нужно выполнить.

**Задача (Task)**: Отдельная атомарная операция, выполняемая Ansible (например, установка пакета, копирование файла). Каждая задача вызывает определенный [модуль Ansible](../Modules/ansible_modules_overview.md).

**Обработчик (Handler)**: Специальная задача, которая выполняется только один раз в конце плея и только после получения уведомления от другой задачи. Используется для таких действий, как перезапуск сервисов.

## Структура и порядок выполнения плея

Каждый плей в плейбуке — это словарь YAML, который определяет, **что** и **где** будет выполняться.

```yaml
---
- name: Play 1 - Настройка веб-серверов
  hosts: webservers
  become: true
  pre_tasks:
    - name: "Проверка: порт 80 свободен"
      # ...
  roles:
    - common
    - { role: nginx, nginx_port: 8080 }
  tasks:
    - name: Установка Nginx
      apt:
        name: nginx
        state: present
      notify: Перезапуск Nginx
  post_tasks:
    - name: "Финальная проверка"
      # ...
  handlers:
    - name: Перезапуск Nginx
      service:
        name: nginx
        state: restarted
```

### Ключевые директивы плея

* `name`: Описание плея, которое будет отображаться в логах.
* `hosts`: Целевые хосты или группы из инвентаря. Поддерживает паттерны: `build:run` — хосты из обеих групп, `all:!group` — исключить группу, `~regex` — по регулярному выражению.
* `tasks`: Список задач, выполняемых последовательно.
* `vars`: Словарь переменных, доступных в рамках плея.
* `become: true/false`: Указывает, нужно ли повышать привилегии (через `sudo`).
* `become_user`: Позволяет указать, каким пользователем стать после повышения привилегий (по умолчанию `root`).
* `become_method`: Метод повышения привилегий (по умолчанию `sudo`).
* `connection`: Тип подключения (`ssh` — по умолчанию, `local` — выполнение на контрольном узле без SSH). `connection: local` добавляется к `hosts:` (не заменяет его), таски выполняются локально.
* `roles`: Список [ролей](../ansible_roles.md) для включения в плей. Путь может быть именем роли (поиск в `roles_path`), относительным или абсолютным путем (`/ansible-lab/docker_setup`).

### Порядок выполнения

Ansible выполняет задачи в строгом порядке:

1. **`pre_tasks`**: Блок задач, выполняемый **до** всех ролей. Полезен для предварительных проверок.
2. **Роли (`roles`)**: Выполняются все задачи из подключенных ролей.
3. **Задачи (`tasks`)**: Основной блок задач плея.
4. **`post_tasks`**: Блок задач, выполняемый **после** всех ролей и `tasks`. Идеален для финальных действий.
5. **Обработчики (`handlers`)**: Выполняются в самом конце, если были уведомлены.

> **Область видимости роли:** роль и все её переменные существуют **только в рамках одного плея** (`- name:`). Если в плейбуке несколько плеев, каждый работает в изолированном контексте — переменные из роли первого плея недоступны во втором.

### Обработчики и идемпотентность

**Идемпотентность** — это ключевой принцип Ansible, означающий, что повторное выполнение операции не приводит к изменению состояния системы, если она уже находится в желаемом состоянии.

**Обработчики (Handlers)** — это специальный тип задач, который является основным инструментом для достижения идемпотентности при работе с сервисами.

* **Определение:** Обработчик — это задача (например, перезапуск сервиса), которая выполняется **только один раз** в самом конце плея и **только в том случае, если она была уведомлена** другой задачей.
* **Механизм работы:**
    1. Основная задача (например, копирование конфигурационного файла) выполняется.
    2. Если эта задача **фактически изменила состояние системы** (статус `changed`), она отправляет уведомление (`notify`) своему обработчику.
    3. В конце плея Ansible выполняет все уведомленные обработчики.
* **Результат:** Если конфигурационный файл не менялся, уведомление не отправляется, и сервис **не перезапускается**. Это предотвращает ненужные простои и позволяет безопасно запускать плейбуки многократно.

**Принудительный запуск обработчиков (`meta: flush_handlers`):**

По умолчанию обработчики выполняются в конце плея. Если следующие задачи зависят от результата обработчика (например, после изменения конфига Docker daemon нужно перезапустить, прежде чем запускать контейнеры), используйте `flush_handlers`:

```yaml
- name: Применить изменения Docker daemon
  ansible.builtin.meta: flush_handlers
```

`flush_handlers` немедленно запускает все накопившиеся уведомленные обработчики, не дожидаясь окончания плея.
