# Ansible: продвинутые возможности плейбуков

## Определения

**Статическое включение (`import_tasks`, `import_role`)** — механизм, при котором содержимое внешнего файла или роли вставляется в плейбук на этапе предварительного анализа (парсинга), до начала его выполнения.

**Динамическое включение (`include_tasks`, `include_role`)** — механизм, при котором внешние задачи или роли подключаются непосредственно в процессе выполнения плейбука, когда очередь доходит до соответствующего шага.

**Делегирование (`delegate_to`)** — перенос выполнения конкретной задачи с целевого хоста на другой узел (чаще всего на `localhost` — контрольный узел).

**Группировка задач (`block`)** — логическое объединение набора задач для совместного применения директив (условий, привилегий) или обработки ошибок.

## Базовые концепции

### Выбор между Import и Include

Выбор зависит от того, нужна ли вам гибкость во время выполнения или производительность на старте.

*   **`import_*` (Статика):**
    *   Файлы считываются один раз при запуске плейбука.
    *   Нельзя использовать циклы (`loop`) на уровне включения.
    *   Нельзя использовать переменные, определенные в ходе выполнения плейбука, в имени файла.
    *   Поддерживает наследование тегов: теги, примененные к `import`, распространяются на все вложенные задачи.
*   **`include_*` (Динамика):**
    *   Файлы считываются только в момент вызова.
    *   Позволяет использовать переменные в именах файлов и циклы.
    *   Позволяет применять условия `when` к самому включению (если условие ложно, задачи даже не будут считаны).

### Контроль делегирования и параллелизма

*   **`delegate_to`**: Модуль выполняется на указанном хосте. Например, при создании записи в DNS через API управление делегируется хосту, имеющему доступ к API.
*   **`delegate_facts: true`**: По умолчанию факты, собранные в делегированной задаче (например, через `ansible.builtin.setup`), приписываются целевому хосту. Если включить эту директиву, они будут сохранены для хоста, на который делегировали выполнение.
*   **`run_once: true`**: Задача выполняется только один раз для всего плея, даже если он запущен на сотне серверов. Полезно для миграций БД или отправки уведомлений.
*   **`throttle`**: Ограничивает количество параллельных потоков для конкретной задачи или блока. Полезно для работы с внешними API, имеющими лимиты запросов (rate limits), не замедляя при этом выполнение остального плейбука.

## Практические сценарии

### Сценарий 1: Динамическое включение задач под конкретную ОС

Использование `ansible.builtin.include_tasks` позволяет создавать гибкие кроссплатформенные плейбуки.

```yaml
- name: Подключить задачи для текущего семейства ОС
  ansible.builtin.include_tasks: "{{ ansible_facts['os_family'] | lower }}_tasks.yml"
```

### Сценарий 2: Оркестрация через localhost

Скачивание артефакта один раз на контрольный узел и последующее распространение.

```yaml
- name: Скачать дистрибутив на контрольный узел
  ansible.builtin.get_url:
    url: "https://artifactory.example.com/app.tar.gz"
    dest: "/tmp/app.tar.gz"
  delegate_to: localhost
  run_once: true

- name: Распаковать на целевых серверах
  ansible.builtin.unarchive:
    src: "/tmp/app.tar.gz"
    dest: "/opt/app"
    remote_src: false # Файл берется с контрольного узла
```

### Сценарий 3: Сбор фактов и проверка состояния (Assert)

Использование специализированных модулей сбора данных для валидации состояния системы.

```yaml
- name: Собрать информацию о пакетах и сервисах
  ansible.builtin.package_facts:
  ansible.builtin.service_facts:

- name: Валидация состояния
  ansible.builtin.assert:
    that:
      - "'nginx' in ansible_facts.packages"
      - ansible_facts.services['nginx.service'].state == 'running'
    fail_msg: "Nginx не установлен или не запущен"
```

### Сценарий 4: Отладка в коде и точки останова

В отличие от флагов командной строки, эти инструменты встраиваются непосредственно в логику плейбука.

```yaml
- name: Вывод значения переменной
  ansible.builtin.debug:
    var: result_of_command

- name: Точка останова при ошибке
  ansible.builtin.command: /usr/local/bin/risky_script.sh
  debugger: on_failed # Запускает интерактивную консоль при сбое
```

### Сценарий 5: Обработка ошибок и откат (Rollback)

Конструкция `block` / `rescue` / `always` позволяет реализовать логику восстановления после сбоев.

```yaml
- name: Обновление конфигурации с откатом
  block:
    - name: Применить новый конфиг
      ansible.builtin.template:
        src: app.conf.j2
        dest: /etc/app.conf
        backup: true
      register: config_deploy

    - name: Перезапустить сервис
      ansible.builtin.service:
        name: myapp
        state: restarted

  rescue:
    - name: Откат конфигурации при сбое
      ansible.builtin.copy:
        src: "{{ config_deploy.backup_file }}"
        dest: /etc/app.conf
        remote_src: true
      when: config_deploy.backup_file is defined

    - name: Перезапуск сервиса после отката
      ansible.builtin.service:
        name: myapp
        state: restarted
```
