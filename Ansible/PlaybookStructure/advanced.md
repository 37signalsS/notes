# Ansible: продвинутые возможности плейбуков

## Определения

**Статическое включение (`import_tasks`, `import_role`)** — механизм, при котором содержимое внешнего файла или роли вставляется в плейбук на этапе предварительного анализа (парсинга). Это как если бы вы скопировали содержимое файла в место вызова до выполнения.

**Динамическое включение (`include_tasks`, `include_role`)** — механизм подключения задач или ролей непосредственно в процессе выполнения плейбука. Это позволяет использовать переменные и циклы для определения того, что именно нужно подключить.

**Делегирование (`delegate_to`)** — перенос выполнения задачи с целевого хоста на другой узел (например, выполнение API-запроса с контрольного узла или обновление DNS-записи с балансировщика).

**Группировка задач (`block`)** — логическое объединение набора задач для совместной обработки ошибок (`rescue`, `always`) или применения общих директив (`when`, `become`).

## Базовые концепции

### Включения: Import vs Include

| Характеристика | `import_*` (Статика) | `include_*` (Динамика) |
| :--- | :--- | :--- |
| **Время считывания** | При запуске (Parsing time) | При выполнении (Execution time) |
| **Использование переменных** | Только из `vars`, `vars_files` | Любые, включая факты и результаты задач |
| **Циклы (`loop`)** | Запрещены | Разрешены |
| **Обработка условий (`when`)** | Применяется к каждой задаче внутри | Применяется к самому включению |
| **Видимость тегов** | Наследуются всеми вложенными задачами | Теги на `include` не видны вложенным задачам |

> **Рекомендация:** Используйте `import_*` для фиксированной структуры и `include_*` для гибкой логики, зависящей от условий среды (например, выбор ОС). Детальное сравнение `import_role` и `include_role` описано в **[Создании и использовании ролей](../Roles/usage.md)**.

### Делегирование и управление контекстом

*   **`delegate_to`**: Указывает хост, на котором будет выполнен модуль. Чаще всего используется `localhost` или `127.0.0.1`.
*   **`local_action`**: Сокращенная форма для `delegate_to: localhost`. Рекомендуется использовать полную форму для единообразия.
*   **`delegate_facts`**: Если установлено в `true`, факты, собранные в делегированной задаче (через модуль `setup`), будут привязаны к хосту, на который делегировали, а не к текущему.
*   **`run_once`**: Гарантирует, что задача выполнится только один раз на первом доступном хосте в группе. Идеально для миграций баз данных или скачивания артефактов.
*   **`throttle`**: Лимит конкурентности на уровне задачи. В отличие от `serial` (уровень плея), `throttle` позволяет не перегружать внешние ресурсы (API, БД) при большом количестве форков.

### Блоки и обработка исключений

Конструкция `block` позволяет реализовать логику `try-catch-finally`:
*   **`block`**: Основные задачи.
*   **`rescue`**: Задачи, выполняемые только при сбое в `block`.
*   **`always`**: Задачи, выполняемые независимо от успеха или сбоя предыдущих шагов (например, удаление временных файлов).

### Инструменты валидации и отладки

*   **`ansible.builtin.assert`**: Прекращает выполнение с ошибкой, если заданное условие не выполняется. Используется для "fail-fast" проверок.
*   **`ansible.builtin.debug`**: Вывод переменных или сообщений в лог.
*   **`debugger`**: Интерактивный отладчик, позволяющий инспектировать переменные и перезапускать задачи при сбоях. Режимы: `on_failed`, `on_unreachable`, `always`.

## Практические сценарии

### Сценарий 1: Динамическое подключение ролей и задач по ОС

Использование `include_tasks` для гибких кроссплатформенных плейбуков.

```yaml
- name: Подключить задачи для текущего семейства ОС
  ansible.builtin.include_tasks: "{{ ansible_facts['os_family'] | lower }}_tasks.yml"
```

### Сценарий 2: Оркестрация и делегирование (Скачивание артефакта)

Скачивание архива один раз на контрольный узел и последующее его распространение.

```yaml
- name: Скачать дистрибутив на контрольный узел
  ansible.builtin.get_url:
    url: "https://artifactory.example.com/app.tar.gz"
    dest: "/tmp/app.tar.gz"
  delegate_to: localhost
  run_once: true

- name: Распаковать на целевых серверах
  ansible.builtin.unarchive:
    src: "/tmp/app.tar.gz"
    dest: "/opt/app"
    remote_src: false # Файл берется с контрольного узла, а не скачивается хостами
```

### Сценарий 3: Атомарная миграция и обработка ошибок (Block/Rescue)

Использование `run_once` и логики восстановления (Rollback).

```yaml
- name: Миграция БД с откатом
  block:
    - name: Создать бэкап перед миграцией
      ansible.builtin.command: /usr/bin/db_backup
      run_once: true
      register: db_backup

    - name: Выполнить миграцию
      ansible.builtin.command: /usr/bin/db_migrate
      run_once: true

  rescue:
    - name: Откат БД из бэкапа
      ansible.builtin.command: "/usr/bin/db_restore --file {{ db_backup.stdout }}"
      run_once: true
```

### Сценарий 4: Ограничение нагрузки на API через throttle

```yaml
- name: Регистрация узлов во внешнем реестре
  ansible.builtin.uri:
    url: https://registry.example.com/api/nodes
    method: POST
    body_format: json
    body: { name: "{{ inventory_hostname }}" }
  throttle: 5 # Не более 5 одновременных запросов к API
```

### Сценарий 5: Сбор фактов и fail-fast проверка (Assert)

Использование встроенных модулей валидации состояния системы.

```yaml
- name: Собрать информацию о пакетах и сервисах
  ansible.builtin.package_facts:
  ansible.builtin.service_facts:

- name: Валидация состояния
  ansible.builtin.assert:
    that:
      - "'nginx' in ansible_facts.packages"
      - ansible_facts.services['nginx.service'].state == 'running'
    fail_msg: "Nginx не установлен или не запущен"
```

### Сценарий 6: Точки останова и отладка (Debugger)

Использование встроенного отладчика для анализа сбоев на лету.

```yaml
- name: Задача, склонная к ошибкам
  ansible.builtin.command: /usr/local/bin/risky_script.sh
  debugger: on_failed # Запустит интерактивную консоль при ошибке

- name: Вывод отладочной информации
  ansible.builtin.debug:
    var: result_of_command
```
