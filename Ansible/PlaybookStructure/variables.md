# Ansible: переменные и факты

> **Надёжность: 10** (SSoT, актуализировано согласно Ansible 2.17+)

## Определения

**Переменные (Variables)** — именованные значения, используемые для параметризации плейбуков и ролей. Позволяют адаптировать код под разные окружения (dev/prod) без изменения самой логики задач. Могут содержать строки, числа, логические значения, списки и словари.

**Факты (Facts)** — системные данные об управляемом хосте (ОС, IP-адреса, диски, память), которые Ansible автоматически собирает перед выполнением задач. Доступны через глобальный словарь `ansible_facts`.

**Магические переменные (Magic Variables)** — зарезервированные внутренние переменные Ansible (например, `inventory_hostname`, `hostvars`), значения которых вычисляются автоматически движком и не могут быть напрямую переопределены пользователем.

## Базовые концепции

### Иерархия приоритетов (Variable Precedence)

Ansible разрешает конфликты имен переменных с помощью сложной системы приоритетов (от низшего к высшему). Знание этой иерархии критично для отладки.

*Самый низкий приоритет (Легко переопределить):*
1.  **Defaults роли** (`roles/x/defaults/main.yml`) — базовые настройки, которые ожидают переопределения.
2.  **Инвентарь (Группы)** (`group_vars/all`, затем `group_vars/определенная_группа`).
3.  **Инвентарь (Хосты)** (`host_vars/конкретный_хост`).
4.  **Факты хоста** (`ansible_facts` и локальные факты `ansible_local`).

*Средний приоритет (Уровень плейбука):*
5.  **Переменные плея** (`vars`, `vars_files`, `vars_prompt` внутри плейбука).
6.  **Переменные роли** (`roles/x/vars/main.yml`) — жесткие настройки, которые роль использует для внутренних нужд. Не предназначены для переопределения пользователем.
7.  **Переменные блоков и задач** (`vars` внутри `block` или `task`).

*Высший приоритет (Сложно переопределить):*
8.  **Зарегистрированные переменные** (через `register` в задаче).
9.  **Переменные этапа выполнения** (`set_fact`, `include_vars`). Параметры ролей (`include_role: vars: {}`).
10. **Extra vars** (`-e` или `--extra-vars` в командной строке) — **Абсолютный приоритет**.

### Работа с фактами (ansible_facts)

По умолчанию сбор фактов (`gather_facts: true`) происходит в начале каждого плея с использованием модуля `ansible.builtin.setup`.
*   Современный синтаксис требует обращения через словарь `ansible_facts`: используйте `ansible_facts['os_family']` вместо устаревшего плоского формата `ansible_os_family`.
*   Для экономии времени выполнения на больших инвентарях сбор фактов часто отключают (`gather_facts: false`), собирая их точечно только там, где необходимо.

### Полезные магические переменные

*   `inventory_hostname`: Имя текущего хоста так, как оно записано в инвентаре (может не совпадать с реальным системным hostname).
*   `hostvars`: Глобальный словарь для доступа к переменным и фактам *других* хостов. Пример: `hostvars['db_node']['ansible_facts']['default_ipv4']['address']`.
*   `groups`: Словарь, где ключи — имена групп, а значения — списки хостов в них. Полезно для циклов.
*   `group_names`: Список имен групп, в которых состоит текущий обрабатываемый хост.

### Типизация и фильтры Jinja2

Ansible использует Jinja2 для интерполяции (`{{ var_name }}`). Важно использовать фильтры для безопасной работы с данными:
*   `default(value)`: Безопасный фоллбэк. Пример: `{{ proxy_port | default(8080) }}`.
*   `default(omit)`: Специальный фильтр, указывающий модулю полностью проигнорировать параметр, если переменная не определена.
*   `type_debug`: Фильтр для отладки типов (string, int, dict), полезен при сложных преобразованиях.
*   `to_json` / `from_yaml`: Конвертация структур данных.

## Практические сценарии

### Сценарий 1: Динамическое подключение переменных (include_vars)

Позволяет подгружать переменные в зависимости от состояния системы или других переменных прямо во время выполнения.

```yaml
- name: Динамическая загрузка конфигурации базы данных
  ansible.builtin.include_vars:
    file: "db_config_{{ environment_type }}.yml"
    name: db_settings # Опционально: загрузить всё в словарь, а не в глобальную область
  # Загрузит db_config_prod.yml или db_config_dev.yml
```

### Сценарий 2: Использование данных другого хоста (hostvars)

Оркестрация часто требует передачи данных от одного компонента (БД) к другому (Приложение).

```yaml
- name: Генерация конфига приложения с указанием IP базы данных
  ansible.builtin.template:
    src: app_conf.j2
    dest: /etc/myapp/app.conf
  vars:
    # Безопасное извлечение IP-адреса хоста 'db_server_01'
    db_ip: "{{ hostvars['db_server_01']['ansible_facts']['default_ipv4']['address'] }}"
  # Задача упадет, если факты для db_server_01 не были собраны в предыдущих плеях!
```

### Сценарий 3: Условная параметризация и default(omit)

Использование `default(omit)` позволяет писать чистые задачи, не создавая их дубликатов для случаев, когда параметр не требуется.

```yaml
- name: Создание пользователя с опциональным паролем
  ansible.builtin.user:
    name: "{{ user_name }}"
    state: present
    # Если password_hash не определен, параметр password вообще не передается модулю
    password: "{{ password_hash | default(omit) }}"
    group: "{{ default_group | default('users') }}"
```

### Сценарий 4: Создание фактов на лету (set_fact)

`set_fact` вычисляет значение и сохраняет его для текущего хоста до конца выполнения плейбука (действует как кэш).

```yaml
- name: Вычисление суммарной доступной памяти
  ansible.builtin.set_fact:
    total_mem_mb: "{{ (ansible_facts['memtotal_mb'] * 0.8) | int }}"

- name: Настройка JVM
  ansible.builtin.command: "java -Xmx{{ total_mem_mb }}m -jar app.jar"
```
