# Ansible: Структура плейбуков

## Определения

**Плейбук (Playbook)**: YAML-файл, который содержит один или несколько "плеев" (`plays`) для описания желаемого состояния системы и шагов по его достижению. Это основной инструмент для оркестрации в Ansible.

**Плей (Play)**: Основной строительный блок плейбука. Плей сопоставляет группу хостов из инвентаря с набором задач, которые на них нужно выполнить.

**Задача (Task)**: Отдельная атомарная операция, выполняемая Ansible (например, установка пакета, копирование файла). Каждая задача вызывает определенный [модуль Ansible](ansible_common_modules.md).

**Обработчик (Handler)**: Специальная задача, которая выполняется только один раз в конце плея и только после получения уведомления от другой задачи. Используется для таких действий, как перезапуск сервисов.

## Структура и порядок выполнения плея

Каждый плей в плейбуке — это словарь YAML, который определяет, **что** и **где** будет выполняться.

```yaml
---
- name: Play 1 - Настройка веб-серверов
  hosts: webservers
  become: true
  pre_tasks:
    - name: "Проверка: порт 80 свободен"
      # ...
  roles:
    - common
    - { role: nginx, nginx_port: 8080 }
  tasks:
    - name: Установка Nginx
      apt:
        name: nginx
        state: present
      notify: Перезапуск Nginx
  post_tasks:
    - name: "Финальная проверка"
      # ...
  handlers:
    - name: Перезапуск Nginx
      service:
        name: nginx
        state: restarted
```

### Ключевые директивы плея

* `name`: Описание плея, которое будет отображаться в логах.
* `hosts`: Целевые хосты или группы из инвентаря.
* `tasks`: Список задач, выполняемых последовательно.
* `vars`: Словарь переменных, доступных в рамках плея.
* `become: true/false`: Указывает, нужно ли повышать привилегии (через `sudo`).
* `become_user`: Позволяет указать, каким пользователем стать после повышения привилегий (по умолчанию `root`).
* `become_method`: Метод повышения привилегий (по умолчанию `sudo`).
* `roles`: Список [ролей](ansible_roles.md) для включения в плей.

### Порядок выполнения

Ansible выполняет задачи в строгом порядке:

1. **`pre_tasks`**: Блок задач, выполняемый **до** всех ролей. Полезен для предварительных проверок.
2. **Роли (`roles`)**: Выполняются все задачи из подключенных ролей.
3. **Задачи (`tasks`)**: Основной блок задач плея.
4. **`post_tasks`**: Блок задач, выполняемый **после** всех ролей и `tasks`. Идеален для финальных действий.
5. **Обработчики (`handlers`)**: Выполняются в самом конце, если были уведомлены.

### Обработчики (handlers)

Обработчики — это специальные задачи, которые выполняются **только один раз** в конце плея и только по уведомлению от другой задачи (`notify`). Они идеальны для перезапуска сервисов, обеспечивая идемпотентность и эффективность.

## Переменные и Факты

### Приоритет и область видимости переменных

Основное правило: переменные, определенные с более узкой областью видимости (например, для конкретного хоста) или в момент выполнения (например, через командную строку), переопределяют переменные с более общей областью видимости (например, для группы хостов).

#### Ключевые типы переменных

*   **`group_vars`**: Файлы в директории `group_vars/` (например, `group_vars/webservers.yml`) содержат переменные, которые применяются ко всем хостам в указанной группе. Файл `group_vars/all.yml` применяется ко **всем** хостам в инвентаре.
*   **`host_vars`**: Файлы в директории `host_vars/` (например, `host_vars/main-server.yml`) содержат переменные для конкретного хоста. Эти переменные имеют **более высокий приоритет**, чем `group_vars`.
*   **`extra vars`**: Переменные, передаваемые через командную строку с флагом `--extra-vars` (или `-e`). Имеют **наивысший приоритет** и переопределяют все остальные переменные. Пример: `ansible-playbook ... -e "version=1.2.3"`.

#### Полная иерархия приоритетов (от низшего к высшему)

1.  **Роли: `defaults/main.yml`**: Значения по умолчанию для роли. Самый низкий приоритет.
2.  **Переменные инвентаря**: Определенные в файле инвентаря (ini/yaml).
3.  **Инвентарь: `group_vars/all`**: Переменные для всех групп.
4.  **Инвентарь: `group_vars/*`**: Переменные для конкретных групп.
5.  **Инвентарь: `host_vars/*`**: Переменные для конкретных хостов.
6.  **Факты системы (Ansible Facts)**: Переменные, собранные о системе (`ansible_os_family` и др.).
7.  **Плейбук: `vars_files`**: Файлы с переменными, подключенные в плее.
8.  **Плейбук: `vars_prompt`**: Переменные, запрошенные у пользователя в интерактивном режиме.
9.  **Плейбук: `vars`**: Переменные, определенные непосредственно в плее.
10. **Роли: `vars/main.yml`**: Основные переменные роли. Имеют более высокий приоритет, чем `defaults`.
11. **Переменные блока (`block`)**: Переменные, определенные для задач внутри блока.
12. **Переменные задачи (`task`)**: Переменные, определенные на уровне конкретной задачи.
13. **`include_vars`**: Переменные, динамически загруженные с помощью модуля `include_vars`.
14. **`set_fact` / `register`**: Переменные, созданные в ходе выполнения плейбука.
15. **Параметры `include_role` и `import_role`**: Переменные, переданные при подключении роли.
16. **Командная строка: `extra-vars` (`-e`)**: Самый высокий приоритет. Переопределяет всё.

### Магические переменные (Magic Variables)

Это особые, зарезервированные переменные, которые **не могут быть заданы или переопределены пользователем**. Ansible всегда сам вычисляет их значения.

* `inventory_hostname`: Имя хоста, как оно указано в файле инвентаря.
* `hostvars`: Словарь, содержащий все переменные для всех хостов в инвентаре.
* `group_names`: Список групп, к которым принадлежит текущий хост.
* `groups`: Словарь, содержащий все группы инвентаря и список хостов в каждой из них.

#### Практический пример: синхронизация имени хоста с инвентарем

Задача: мы хотим, чтобы реальное имя сервера (hostname) соответствовало имени, которое мы задали ему в файле инвентаря.

```yaml
# roles/set_hostname/tasks/main.yml
- name: Set hostname based on inventory name
  ansible.builtin.hostname:
    name: "{{ inventory_hostname }}"
```

При выполнении этой задачи на хосте `192.168.1.10` его имя будет изменено на `srv-prod-1`. На хосте `192.168.1.20` — на `bckp-1`.

### Факты Ansible (Ansible Facts)

На старте каждого плея Ansible по умолчанию собирает информацию (факты) об управляемой системе: сетевые интерфейсы, ОС, память и т.д. Эти данные помещаются в переменную `ansible_facts` и чрезвычайно полезны для создания кроссплатформенных плейбуков.

#### Использование фактов в условиях

```yaml
- name: Установка Apache на RedHat/CentOS
  ansible.builtin.yum:
    name: httpd
    state: present
  when: ansible_facts.os_family == "RedHat" # Используем факт для условного выполнения
```

### Лучшие практики ("Дзен Ansible")

1. **Определяйте переменную в одном месте.** Избегайте многократного переопределения.
2. **Используйте уникальные префиксы.** Чтобы избежать конфликтов имен между ролями, добавляйте префикс с названием роли (`my_app_nginx_port: 8080`).
3. **Избегайте общих имен** (`user`, `port`, `server`).

## Управление ходом выполнения

### Условные конструкции (when)

Директива `when` позволяет выполнять задачу только при выполнении определенного условия.

* **Логическое "И" (AND):** Список условий.
* **Логическое "ИЛИ" (OR):**

```yaml
- name: "Перезагрузить сервис только если включено и были изменения"
  ansible.builtin.systemd:
    name: my_service
    state: reloaded
  when:
    - my_service_enabled
    - config_result is changed
```

### Циклы (loop)

Позволяют выполнять одну и ту же задачу несколько раз с разными данными. `loop` является современным стандартом, заменяя `with_items`.

```yaml
- name: Установка нескольких пакетов
  ansible.builtin.apt:
    name: "{{ item.name }}"
    state: "{{ item.state }}"
  loop:
    - { name: 'nginx', state: 'present' }
    - { name: 'htop', state: 'latest' }
```

### Регистрация результатов (register)

Сохраняет результат выполнения задачи в переменную. Часто используется с `when` для условного выполнения.

```yaml
- name: "Сгенерировать конфигурационный файл"
  ansible.builtin.template:
    src: whitelist.j2
    dest: /etc/myapp/whitelist.conf
  register: whitelist_config

- name: "Перезагрузить сервис, только если конфиг изменился"
  ansible.builtin.service:
    name: myapp
    state: reloaded
  when: whitelist_config is changed
```

### Обработка ошибок

* `ignore_errors: true`: Продолжить выполнение, даже если задача завершилась сбоем.
* `block, rescue, always`: Аналог `try...catch...finally` для обработки ошибок на уровне задач.
* `failed_when`: Переопределить условия, при которых задача считается проваленной.
* `changed_when: false`: Сделать команду идемпотентной в отчетах.

### Теги (Tags)

Теги позволяют выборочно запускать или пропускать части плейбука.

```yaml
tasks:
  - name: Install base packages
    ansible.builtin.apt:
      name: htop
    tags: [packages, base]

# Запустить только задачи с тегом 'packages'
ansible-playbook my_playbook.yml --tags packages
# Запустить все, КРОМЕ задач с тегом 'base'
ansible-playbook my_playbook.yml --skip-tags base
```

## Продвинутые возможности

### Структурирование плейбуков (import_tasks vs include_tasks)

* `import_tasks` (статическое включение): Содержимое файла вставляется на этапе парсинга (до выполнения). **Не работает с `loop`**.
* `include_tasks` (динамическое включение): Файл подключается в процессе выполнения. **Работает с `loop`**.

```yaml
- name: Включить задачи для Debian-подобных систем
  ansible.builtin.include_tasks: debian.yml
  when: ansible_os_family == "Debian"
```

### Выполнение задач на других хостах (delegate_to)

Позволяет выполнить задачу на другой машине (чаще всего `localhost`), а не на целевом хосте.

```yaml
- name: Find .war files on the control node
  ansible.builtin.find:
    paths: /path/to/local/artifacts
    patterns: "*.war"
  delegate_to: localhost
  register: found_artifacts
```

### Оптимизация производительности

Вопросы оптимизации и параллелизма (такие как `forks`, `async`, `throttle`, `until`) подробно рассмотрены в документе **[Ansible: Оптимизация производительности](ansible_performance_tuning.md)**.

## Отладка плейбуков

* `-v, -vvv`: Увеличение уровня детализации вывода.
* `--syntax-check`: Проверка синтаксиса YAML.
* `--check`: "Сухой прогон" (dry run) без внесения реальных изменений.
* `--step`: Интерактивное пошаговое выполнение.
* `--limit`: Ограничение выполнения на конкретном хосте.
* `--start-at-task`: Начало выполнения с указанной задачи.
* `debug`: Модуль для вывода значений переменных.
* `debugger`: Ключевое слово для вызова интерактивного отладчика на конкретной задаче.

## Практические примеры

### 1. Параметризация роли (defaults и group_vars)

Пример демонстрирует, как сделать размер swap-файла настраиваемым.

1. **Задача с переменной** (`roles/swap/tasks/main.yml`):

    ```yaml
    - name: Create swap file
      ansible.builtin.shell: "fallocate -l {{ swap_size }} /swapfile"
      args:
        creates: /swapfile
    ```

2. **Значение по умолчанию** (`roles/swap/defaults/main.yml`):

    ```yaml
    swap_size: 1g
    ```

3. **Переопределение для группы** (`group_vars/backup.yml`):

    ```yaml
    swap_size: 2g # Для бэкап-серверов
    ```

**Результат**: Приоритет `group_vars` выше, чем у `defaults`, поэтому для хостов из группы `backup` будет использовано значение `2g`.

### 2. Управление контейнерами Docker через systemd

**Шаблон `container.service.j2`:**

```j2
[Unit]
Description={{ item.name }} container
Requires=docker.service
After=docker.service
[Service]
Restart=always
ExecStartPre=-/usr/bin/docker stop {{ item.name }}
ExecStartPre=-/usr/bin/docker rm {{ item.name }}
ExecStart=/usr/bin/docker run --rm --name {{ item.name }} \
{% if item.ports is defined %}{% for port in item.ports %} -p {{ port }} \ {% endfor %}{% endif %}
    {{ item.image }}
ExecStop=/usr/bin/docker stop {{ item.name }}
[Install]
WantedBy=multi-user.target
```

**Задача Ansible:**

```yaml
- name: Create systemd unit files for containers
  ansible.builtin.template:
    src: container.service.j2
    dest: "/etc/systemd/system/{{ item.name }}.service"
  loop: "{{ containers }}"
  notify: Reload systemd
```
