# Ansible: "Плохой код" и антипаттерны

## 1. Устаревший "линейный" стиль

В старых версиях Ansible был распространен стиль написания задач с параметрами в одну строку.

**Плохо (старый стиль):**
```yaml
- name: Echo a message
  command: echo "Hello, World!" creates=/path/to/lock
```
Этот синтаксис поддерживается для обратной совместимости, но смешивает имя модуля с его аргументами и затрудняет чтение.

**Хорошо (современный YAML стиль):**
```yaml
- name: Echo a message
  ansible.builtin.command:
    cmd: echo "Hello, World!"
    creates: /path/to/lock
```
**Рекомендация:** Всегда используйте стандартный синтаксис YAML. Если вы встречаете старый стиль в ролях или плейбуках, по возможности проводите рефакторинг.

## 2. Отсутствие идемпотентности

Идемпотентность — это ключевой принцип Ansible. Отсутствие идемпотентности делает плейбуки непредсказуемыми и опасными.

### 2.1. На входе (легко заметить)

Это происходит, когда плейбук успешно выполняется один раз, но падает при повторном запуске.

*   **Пример:** Плейбук для настройки MySQL сначала меняет метод аутентификации `root` с `auth_socket` на парольный. При повторном запуске задача не сможет подключиться через сокет, и плейбук упадет с ошибкой.
*   **Результат:** Ошибку легко отследить и исправить, так как есть явное падение задачи.

### 2.2. На выходе (опасно и трудно заметить)

Это худший вид проблемы. Плейбук успешно выполняется каждый раз (статус `ok` или `changed`), но вносит в систему нежелательные, накапливающиеся изменения.

*   **Пример:** Использование `shell` или `command` для добавления строки конфигурации в файл.
    ```yaml
    # ПЛОХОЙ ПРИМЕР
    - name: Add setting to config file
      ansible.builtin.shell: echo "MySetting=true" >> /etc/myapp.conf
    ```
    При каждом запуске этого плейбука в `myapp.conf` будет добавляться новая строка `MySetting=true`, что почти наверняка приведет к сбою сервиса.
*   **Результат:** Нет ошибок выполнения, но состояние системы деградирует.

**Рекомендация:** Избегайте `shell` и `command` для управления состоянием. Используйте специализированные модули (`lineinfile`, `blockinfile`, `template`), которые по своей природе идемпотентны. Задача должна возвращать `ok`, если система уже находится в желаемом состоянии.

## 3. Слишком сложная автоматизация и "алгоритмизация"

Это попытка реализовать сложную бизнес-логику и алгоритмы прямо в плейбуке с помощью `shell`, `command` и сложных конструкций.

> Ansible — это декларативная система управления конфигурацией, а не язык программирования. Попытка писать алгоритмы в плейбуках — это как писать их на HTML.

**Плохо:**
*   Использование `awk`, `sed`, `grep` в длинных цепочках для обработки данных.
*   Реализация проверок (`if...then...else`) внутри shell-скриптов вместо использования `when` и модулей.
*   Написание многострочных скриптов в `shell` для выполнения бэкапов, проверок репликации и т.д.

**Пример (псевдокод):**
```yaml
# ПЛОХОЙ ПРИМЕР
- name: Create replica backup
  ansible.builtin.shell: |
    if [ -d /backup/replica ]; then
      echo "Backup directory exists."
      if [ is_replica_healthy() ]; then
        pg_basebackup -D /backup/replica
      else
        echo "Replica is not healthy!"
        exit 1
      fi
    else
      echo "Backup directory not found!"
      exit 1
    fi
```
**Почему это плохо?**
*   **Сложно читать и поддерживать.**
*   **Нарушает декларативный подход.** Вы описываете *как* делать, а не *какое* состояние получить.
*   **Скрывает логику.** Отладка превращается в анализ вывода shell-скриптов.

**Рекомендация:** Если вам нужна сложная логика, **напишите собственный модуль Ansible**. Модуль, написанный на Python, может содержать все необходимые проверки, быть идемпотентным и предоставлять пользователю плейбука простой декларативный интерфейс. Для сложных бизнес-задач можно создать отдельное приложение, которое Ansible будет только запускать и проверять его состояние.

## 4. Неочевидные зависимости между ролями

Это один из самых коварных антипаттернов, который приводит к сложным для отладки проблемам в больших инфраструктурах.

### Антипаттерн 1: Роль зависит от `host_vars`

Роль начинает напрямую использовать переменные, которые, как ожидается, определены в `host_vars` или `group_vars` инвентаря.

*   **Проблема:** Роль перестает быть переиспользуемой и "самодостаточной". Она неявно привязывается к конкретному проекту и структуре инвентаря. Другой инженер, пытаясь использовать эту роль в новом проекте, столкнется с ошибками из-за отсутствия переменных.

### Антипаттерн 2: Две роли используют общий файл задач

Две разные роли (`role_A` и `role_B`) включают в себя задачи из одного общего файла (`common_tasks.yml`) для переиспользования кода.

```
roles/
├── role_A/
│   └── tasks/
│       └── main.yml  (includes ../common/common_tasks.yml)
├── role_B/
│   └── tasks/
│       └── main.yml  (includes ../common/common_tasks.yml)
└── common/
    └── common_tasks.yml
```

*   **Проблема:** Инженер, работая над `role_A`, решает изменить `common_tasks.yml`. Он не знает (и не может легко проверить), что этот файл также используется в `role_B`, и непреднамеренно ломает ее. В Ansible нет простого способа отследить, где используется тот или иной файл задач.

**Рекомендация: Не бойтесь копировать код (`copy-paste`).**

В контексте Ansible самодостаточность и отсутствие скрытых зависимостей гораздо важнее, чем следование принципу DRY (Don't Repeat Yourself).

> Лучше иметь две роли с частично скопированными задачами, которые можно изменять независимо друг от друга, чем две роли со скрытой общей зависимостью, которая взорвется в самый неподходящий момент.
>
> Для более сложных сценариев, где переиспользование все же необходимо, можно использовать [продвинутые паттерны структурирования ролей](ansible_advanced_role_structure.md).

## 5. Конфликт задач из разных ролей

В больших проектах, где над разными ролями работают разные люди, неизбежно возникают конфликты.

*   **Проблема:** Роль `A` настраивает `/etc/resolv.conf` с одними параметрами, а роль `B` перезаписывает тот же файл своими параметрами. В итоге применяется только последнее изменение, а результат зависит от порядка выполнения ролей. Это трудно отследить, так как обе задачи по отдельности работают корректно.
*   **Решение:**
    1.  **Централизация:** Выносить управление общими ресурсами (как `/etc/resolv.conf`) в одну общую роль (например, `base_config`), которая применяется ко всем хостам.
    2.  **Коммуникация:** Команды должны договариваться о том, какая роль отвечает за какой ресурс.

## 6. Намеренно неидемпотентные сценарии

Хотя идемпотентность — это цель, существуют сценарии, где плейбук намеренно выполняется один раз и вносит необратимые изменения.

*   **Сценарий:** Первоначальная настройка сервера. Плейбук обновляет ядро системы, а затем в секции `post_tasks` вызывает перезагрузку сервера.
    ```yaml
      post_tasks:
        - name: Restart server after kernel upgrade
          ansible.builtin.shell: "sleep 10 && shutdown -r now"
          async: 1
          poll: 0
          when: kernel_updated is changed
    ```
*   **Обоснование:** Такой плейбук предназначен только для "голых" серверов. Повторный его запуск на уже настроенной системе не имеет смысла и может быть опасен (например, из-за перезагрузки). Такие плейбуки следует изолировать от основной массы идемпотентных сценариев управления конфигурацией.

## 7. Отсутствие префиксов у переменных

*   **Проблема:** В роли `nginx` есть переменная `port: 80`, а в роли `prometheus` — `port: 9090`. Если применить обе роли к одному хосту, значение `port` станет непредсказуемым и будет зависеть от порядка выполнения ролей. Это может привести к тому, что Nginx попытается запуститься на порту 9090.
*   **Рекомендация:** Всегда добавляйте к переменным внутри роли префикс, совпадающий с названием роли.
    *   **Плохо:** `port: 8080`
    *   **Хорошо:** `nginx_port: 8080`, `prometheus_port: 9090`
    Это позволяет избежать конфликтов и делает код более читаемым.
