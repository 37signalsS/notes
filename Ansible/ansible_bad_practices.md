# Ansible: Антипаттерны и плохие практики

## Определения

**Декларативность** — подход, при котором описывается *желаемое состояние* системы, а не последовательность шагов для его достижения.

**Идемпотентность** — следствие декларативного подхода, один из [ключевых принципов Ansible](ansible_core_concepts.md#идемпотентность). Гарантирует, что многократный запуск одной операции не изменит результат после первого успешного выполнения.

Нарушение этих принципов — корень большинства антипаттернов.

## Основные концепции

### Последствия нарушения идемпотентности

1. **Отсутствие идемпотентности на входе (легко заметить)**
    * **Что происходит:** Плейбук выполняется один раз, но падает при повторном запуске из-за изменившихся условий.
    * **Пример:** Плейбук для настройки MySQL меняет метод аутентификации `root` с `auth_socket` на парольный. При повторном запуске подключение через сокет невозможно, задача падает с ошибкой.
    * **Результат:** Легко отследить и исправить.

2. **Отсутствие идемпотентности на выходе (опасно и трудно заметить)**
    * **Что происходит:** Плейбук успешно выполняется каждый раз, но вносит нежелательные накапливающиеся изменения.
    * **Пример:** Использование `shell` для добавления строки в конфигурационный файл без проверки существования.

        ```yaml
        # ПЛОХОЙ ПРИМЕР
        - name: Add setting to config file
          ansible.builtin.shell: echo "MySetting=true" >> /etc/myapp.conf
        ```

        При каждом запуске добавляется новая строка, что приводит к сбою сервиса.
    * **Результат:** Деградация состояния системы без явных ошибок.

## Практические сценарии

### Антипаттерны на уровне кода

#### 1. «Алгоритмизация» и избыточное использование shell и command

Это попытка реализовать сложную бизнес-логику и алгоритмы прямо в плейбуке с помощью `shell`, `command` и сложных конструкций (`awk`, `sed`, `grep`).

> Ansible — это декларативная система, а не язык программирования. Попытка писать алгоритмы в плейбуках — это как писать их на HTML.

**Пример (псевдокод):**

```yaml
# ПЛОХОЙ ПРИМЕР
- name: Create replica backup
  ansible.builtin.shell: |
    if [ -d /backup/replica ]; then
      if is_replica_healthy; then
        pg_basebackup -D /backup/replica
      else
        echo "Replica is not healthy!"; exit 1
      fi
    else
      echo "Backup directory not found!"; exit 1
    fi
```

**Почему это плохо?**

* **Нарушает декларативный подход:** Вы описываете *как* делать, а не *какое* состояние получить.
* **Скрывает логику:** Отладка превращается в анализ вывода shell-скриптов.
* **Неидемпотентно по умолчанию:** `shell` и `command` не проверяют состояние системы и всегда возвращают `changed`.

**Рекомендация:**

* Для управления состоянием используйте специализированные модули (`ansible.builtin.lineinfile`, `ansible.builtin.blockinfile`, `ansible.builtin.template`).
* Для сложной логики **напишите собственный модуль Ansible**. Модуль, написанный на Python, может содержать все необходимые проверки и предоставлять простой декларативный интерфейс.

#### 2. Устаревший «линейный» стиль

**Плохо (старый стиль):**

```yaml
- name: Echo a message
  command: echo "Hello, World!" creates=/path/to/lock
```

**Хорошо (современный YAML стиль):**

```yaml
- name: Echo a message
  ansible.builtin.command:
    cmd: echo "Hello, World!"
    creates: /path/to/lock
```

### Архитектурные антипаттерны

#### 1. Неочевидные зависимости между ролями

Проблема возникает, когда роли перестают быть самодостаточными и начинают неявно зависеть от внешних факторов.

* **Антипаттерн 1: Роль зависит от `host_vars`**
    Роль напрямую использует переменные, которые должны быть определены в файлах инвентаря (`host_vars`/`group_vars`). Это делает роль непереиспользуемой и привязывает её к конкретному проекту.

* **Антипаттерн 2: Две роли используют общий файл задач (`includes`)**
    Изменение общего файла (`common_tasks.yml`) для одной роли может непреднамеренно сломать другую роль, которая его также использует. Отследить такие зависимости в Ansible сложно.

**Рекомендация: Не бойтесь копировать код (copy-paste).**

В контексте Ansible самодостаточность и отсутствие скрытых зависимостей важнее, чем принцип DRY (Don't Repeat Yourself).

> Лучше иметь две роли с частично скопированными задачами, которые можно изменять независимо, чем две роли со скрытой общей зависимостью.
>
> Для сложных сценариев переиспользования кода можно применять [продвинутые паттерны структурирования ролей](Roles/utility_role_pattern.md).

#### 2. Конфликт задач из разных ролей

* **Проблема:** Роль `A` настраивает `/etc/resolv.conf` с одними параметрами, а роль `B` перезаписывает тот же файл другими. Итоговый результат зависит от порядка выполнения ролей.
* **Решение:**
    1. **Централизация:** Выносить управление общими ресурсами в одну специальную роль (например, `base_config`).
    2. **Коммуникация:** Команды должны договариваться о том, какая роль за какой ресурс отвечает.

#### 3. Отсутствие префиксов у переменных

* **Проблема:** В роли `nginx` есть переменная `port: 80`, а в роли `prometheus` — `port: 9090`. Если применить обе роли к одному хосту, значение `port` будет перезаписано последней выполненной ролью.
* **Рекомендация:** Всегда добавляйте к переменным внутри роли префикс с названием роли.
  * **Плохо:** `port: 8080`
  * **Хорошо:** `nginx_port: 8080`, `prometheus_port: 9090`
