# Ansible — антипаттерны и плохие практики

## Определения

**Антипаттерн в Ansible** — это распространенный, но неэффективный или опасный способ решения задачи автоматизации, который ведет к нарушению идемпотентности, усложнению поддержки кода или снижению безопасности.

**Идемпотентность** — фундаментальный принцип Ansible, гарантирующий, что повторное выполнение операции не изменит систему, если она уже находится в целевом состоянии. Большинство антипаттернов напрямую или косвенно нарушают этот принцип.

## Основные концепции

### Нарушение идемпотентности

1.  **Скрытые изменения (Changed при каждом запуске):** Использование модулей, которые не умеют проверять текущее состояние (например, `shell`, `command`) без дополнительных условий. Это мешает отслеживанию реальных изменений в инфраструктуре.
2.  **Деградация при повторе:** Задачи, которые при каждом запуске добавляют данные (например, дописывают строку в конфиг через `shell: echo ... >> file`), вместо управления его состоянием.
3.  **Зависимость от порядка:** Плейбуки, результат которых меняется при изменении очередности задач из-за отсутствия явных проверок или использования глобальных переменных.

### Проблемы читаемости и поддержки

-   **Использование старого синтаксиса:** "Линейная" запись аргументов в одну строку затрудняет чтение и отладку. Современный стандарт — использование YAML-словарей.
-   **Отсутствие неймспейсов (FQCN):** Использование коротких имен модулей (например, `copy` вместо `ansible.builtin.copy`) может привести к конфликтам при установке сторонних коллекций.

## Практические сценарии

### Антипаттерны на уровне кода

#### 1. Злоупотребление командами оболочки

Попытка реализовать алгоритмическую логику через `ansible.builtin.shell` вместо использования декларативных модулей.

**Плохо (Императивный подход):**
```yaml
- name: Add setting if not exists
  ansible.builtin.shell: |
    if ! grep -q "Setting=true" /etc/app.conf; then
      echo "Setting=true" >> /etc/app.conf
    fi
```

**Хорошо (Декларативный подход):**
```yaml
- name: Ensure setting is present
  ansible.builtin.lineinfile:
    path: /etc/app.conf
    line: "Setting=true"
    state: present
```

#### 2. Использование `ignore_errors: true` вместо обработки состояний

Широкое использование `ignore_errors` скрывает реальные проблемы.

**Рекомендация:** Используйте `failed_when` для точного определения условий ошибки или `block/rescue` для обработки исключений.

#### 3. Хардкод секретов в плейбуках

Хранение паролей и токенов в открытом виде — критическая ошибка безопасности.

**Рекомендация:** Всегда используйте [Ansible Vault](./Vault/basics.md) или внешние Secret Managers.

### Архитектурные ошибки

#### 1. Глобальный `become: true`

Установка повышения привилегий на уровне всего плея, когда они нужны только для 1-2 задач.

**Последствия:** Повышается риск случайного изменения системных файлов задачами, которым это не требуется.
**Рекомендация:** Указывайте `become: true` только для конкретных задач или блоков.

#### 2. Отсутствие префиксов у переменных в ролях

Если роль `nginx` и роль `app` обе используют переменную `port`, возникнет конфликт.

**Плохо:** `port: 80`
**Хорошо:** `nginx_port: 80`, `app_port: 8080`

#### 3. Роли-гиганты ("God Roles")

Создание одной роли, которая делает всё: устанавливает базу, веб-сервер и настраивает мониторинг.

**Рекомендация:** Разделяйте логику. Одна роль = один компонент системы. Используйте зависимости в `meta/main.yml`.

## Инструменты контроля качества

Для предотвращения антипаттернов в CI/CD пайплайнах рекомендуется использовать инструменты статического анализа:

1.  **ansible-lint:** Основной инструмент для проверки плейбуков на соответствие лучшим практикам.
2.  **ansible-playbook --syntax-check:** Базовая проверка корректности YAML-структуры.
3.  **Molecule:** Фреймворк для полноценного тестирования ролей в изолированных окружениях (Docker/VM).
