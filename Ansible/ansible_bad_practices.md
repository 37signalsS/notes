# Ansible — антипаттерны и плохие практики

## Определения

**Антипаттерн в Ansible** — это распространенный, но неэффективный или опасный способ решения задачи автоматизации, который ведет к нарушению идемпотентности, усложнению поддержки кода или снижению безопасности.

**Идемпотентность** — фундаментальный принцип Ansible, гарантирующий, что повторное выполнение операции не изменит систему, если она уже находится в целевом состоянии. Большинство антипаттернов напрямую или косвенно нарушают этот принцип.

## Основные концепции

### Нарушение идемпотентности

1.  **Скрытые изменения (Changed при каждом запуске):** Использование модулей, которые не умеют проверять текущее состояние (например, `shell`, `command`) без параметров `creates`, `removes` или `changed_when`. Это делает вывод Playbook недостоверным.
2.  **Деградация при повторе:** Задачи, которые при каждом запуске добавляют данные (например, дописывают строку в конфиг через `shell: echo ... >> file`), вместо декларативного управления состоянием файла.
3.  **Зависимость от порядка:** Плейбуки, результат которых меняется при изменении очередности задач из-за отсутствия явных проверок или использования глобальных переменных.

### Проблемы читаемости и производительности

-   **Использование старого синтаксиса (Key=Value):** "Линейная" запись аргументов в одну строку затрудняет чтение и отладку. Современный стандарт — использование структурированных YAML-словарей.
-   **Отсутствие FQCN:** Использование коротких имен модулей (например, `copy` вместо `ansible.builtin.copy`) может привести к конфликтам при установке сторонних коллекций.
-   **Сбор фактов по умолчанию:** Оставленный включенным сбор фактов (`gather_facts: true`) на тысячах узлов, когда для задач эти системные переменные не требуются, критически снижает скорость выполнения.

## Практические сценарии

### Антипаттерны на уровне кода

#### 1. Злоупотребление командами оболочки

Попытка реализовать алгоритмическую логику через `ansible.builtin.shell` или `ansible.builtin.command` вместо использования встроенных декларативных модулей.

**Плохо (Императивный подход — сломает идемпотентность):**
```yaml
- name: Add setting if not exists
  ansible.builtin.shell: |
    if ! grep -q "Setting=true" /etc/app.conf; then
      echo "Setting=true" >> /etc/app.conf
    fi
```

**Хорошо (Декларативный подход):**
```yaml
- name: Ensure setting is present
  ansible.builtin.lineinfile:
    path: /etc/app.conf
    line: "Setting=true"
    state: present
```

#### 2. Старый формат передачи аргументов (Key-Value)

Затрудняет чтение и может вызывать ошибки парсинга при наличии спецсимволов.

**Плохо:**
```yaml
- name: Install package
  ansible.builtin.apt: name=nginx state=latest update_cache=yes
```

**Хорошо:**
```yaml
- name: Install package
  ansible.builtin.apt:
    name: nginx
    state: latest
    update_cache: true
```

#### 3. Использование `ignore_errors: true` вместо обработки состояний

Широкое использование `ignore_errors` скрывает реальные проблемы и делает отладку невозможной.

**Рекомендация:** Используйте `failed_when` для точного определения условий ошибки или конструкцию `block/rescue` для обработки исключений.

#### 4. Выполнение `command` без проверок идемпотентности

**Плохо:** Запуск приведет к статусу `CHANGED` при каждом выполнении.
```yaml
- name: Download application
  ansible.builtin.command: curl -O https://example.com/app.tar.gz
```

**Хорошо:** Использование модуля `get_url` или флага `creates` для `command`.
```yaml
- name: Download application
  ansible.builtin.get_url:
    url: https://example.com/app.tar.gz
    dest: /opt/app.tar.gz
```

### Архитектурные ошибки

#### 1. Глобальный `become: true`

Установка повышения привилегий на уровне всего Playbook, когда они нужны только для одной-двух задач (например, перезапуск службы).

**Последствия:** Повышается риск случайного изменения системных файлов.
**Рекомендация:** Указывайте `become: true` только для конкретных задач или блоков.

#### 2. Роли-гиганты ("God Roles")

Создание одной роли, которая делает всё: настраивает ОС, устанавливает СУБД, веб-сервер и подключает мониторинг.

**Рекомендация:** Разделяйте логику. Одна роль = один компонент системы. Используйте зависимости в `meta/main.yml`.

## Инструменты контроля качества

Для автоматического выявления антипаттернов (отсутствие FQCN, старый синтаксис, проблемы безопасности) используется статический анализатор `ansible-lint`. Он является обязательным инструментом в пайплайнах непрерывной интеграции.

```bash
ansible-lint site.yml
# → WARNING  [fqcn] Use FQCN for builtin module actions (copy).
# → ERROR    [yaml] Trailing spaces at the end of the line
```
