# Введение в Ansible

## Определения

- **Ansible** — это система автоматизации ИТ-инфраструктуры с открытым исходным кодом (Red Hat / IBM), предназначенная для управления конфигурациями, развертывания приложений и оркестрации сложных ИТ-процессов. Это один из ключевых инструментов реализации парадигмы **Infrastructure as Code (IaC)**.
- **Декларативность** — основной подход Ansible, при котором пользователь описывает *целевое состояние* системы (Desired State), а инструмент самостоятельно определяет необходимые действия для его достижения. Это избавляет инженера от написания сложных императивных скриптов с обработкой ошибок каждого шага. Подробнее см. в [Основных концепциях](./ansible_core_concepts.md).
- **Agentless (безагентная архитектура)** — архитектурная особенность, при которой для управления узлами не требуется установка на них специального ПО (агентов). Связь осуществляется через стандартные протоколы: **SSH** для Linux/Unix, **WinRM** или **SSH** для Windows. Это упрощает внедрение и снижает накладные расходы на ресурсы.
- **Идемпотентность** — свойство операции, гарантирующее, что повторное выполнение не изменит систему, если она уже находится в желаемом состоянии. Фундаментальный принцип надежности автоматизации. Подробнее см. **[Идемпотентность](../../Concepts/idempotency.md)**.
- **Push-архитектура** — модель работы, при которой Узел управления (Control Node) инициирует соединение и «проталкивает» конфигурацию на управляемые узлы.

## Основные концепции

### Архитектура и компоненты

1.  **Узел управления (Control Node):** Машина, на которой установлен Ansible. С неё запускаются все команды и сценарии. Поддерживаются только Unix-подобные системы (Linux, macOS, WSL2).
2.  **Управляемые узлы (Managed Nodes):** Целевые серверы, сетевые устройства или облачные ресурсы, которыми управляет Ansible. Для управления Linux-системами на них должен быть установлен **Python 3.7+**.
3.  **Инвентарь (Inventory):** Список хостов и групп хостов. Может быть статическим файлом (INI/YAML) или [динамическим скриптом](./dynamic_inventory.md), получающим данные из облаков или CMDB.
4.  **Модули (Modules):** Исполняемые автономные блоки кода, выполняющие конкретные задачи (установка пакетов, копирование файлов). Современный стандарт требует использования полного имени ресурса — **FQCN (Fully Qualified Collection Name)** (например, `ansible.builtin.apt` вместо `apt`).
5.  **Плейбуки (Playbooks):** Сценарии автоматизации, написанные на языке **YAML**, описывающие шаги развертывания и настройки.
6.  **Event-Driven Ansible (EDA):** Подход к реактивной автоматизации, позволяющий запускать действия на основе внешних событий (алертов, сообщений из очередей) в режиме реального времени. См. **[EDA — Реактивная автоматизация](./event-driven-ansible.md)**.

### Разделение пакетов: ansible-core и ansible

Для решения проблем с масштабированием проекта и скоростью выпуска обновлений, экосистема разделена на два компонента:
- **ansible-core**: Минимальное ядро системы, содержащее движок выполнения, CLI-утилиты (`ansible`, `ansible-playbook`) и набор базовых модулей (`ansible.builtin`). Обновляется строго по циклу релизов ядра.
- **ansible (Community пакет)**: Большой метапакет, включающий в себя `ansible-core` и тысячи модулей и плагинов от сообщества, упакованных в **Коллекции (Collections)**.
- **Execution Environments (EE)**: Современный способ упаковки Ansible, коллекций и зависимостей в контейнеры (**[подробнее](./ansible-execution-environments.md)**) для обеспечения идентичности сред выполнения.

### Преимущества использования

- **Минимальный порог входа:** Использование человекочитаемого формата YAML и системы шаблонизации **Jinja2**.
- **Единообразие инфраструктуры:** Исключение «серверов-снежинок» (уникальных серверов, настроенных вручную и невоспроизводимых автоматически).
- **Масштабируемость:** Возможность управления тысячами узлов одновременно благодаря параллельному выполнению (параметр `forks`).
- **Безопасность:** Отсутствие постоянно запущенных агентов, использование стандартных механизмов аутентификации ОС (SSH-ключи) и интеграция с **Ansible Vault** для защиты чувствительных данных.

## Практические сценарии

### Использование Ad-hoc команд

**Ad-hoc команды** — это быстрые одноразовые задачи, выполняемые в терминале без написания плейбука. Они оптимальны для первичной проверки или массового выполнения простых команд.

**Синтаксис:** `ansible <pattern> -m <module> -a "<arguments>"`

#### Проверка связи (модуль `ping`)
Проверяет доступность хостов по протоколу связи и наличие интерпретатора Python на удаленной стороне.
```bash
ansible all -m ping
# → server1.example.com | SUCCESS => { "ansible_facts": { "discovered_interpreter_python": "/usr/bin/python3" }, "changed": false, "ping": "pong" }
```

#### Управление пакетами (модуль `package`)
Универсальный модуль, выбирающий подходящий менеджер пакетов (`apt`, `yum`, `dnf`) автоматически. Флаг `--become` включает повышение привилегий (sudo).
```bash
# Установка nginx на группу web
ansible web -m package -a "name=nginx state=present" --become
# → web1.example.com | CHANGED => { "changed": true, "name": ["nginx"], "state": "present" }
```

#### Сбор информации (модуль `setup`)
Получение детальных фактов о системе (сетевые интерфейсы, ОС, железо) в формате JSON.
```bash
ansible all -m setup --tree /tmp/facts
# → Результаты собираются и сохраняются в файлы внутри директории /tmp/facts для каждого целевого хоста
```

#### Выполнение команд оболочки (модуль `shell`)
Используется, когда необходим функционал командной оболочки (конвейеры `|`, перенаправления `>`). Для простых команд без спецсимволов безопаснее использовать `ansible.builtin.command`.
```bash
ansible all -m shell -a "df -h | grep /dev/sda"
# → db1.example.com | CHANGED | rc=0 >> /dev/sda1  50G  20G  30G  40% /
```

## Дополнительная информация

### Рекомендации

- Для повторяющихся задач и управления конфигурацией всегда используйте плейбуки вместо ad-hoc команд, так как они обеспечивают идемпотентность и контроль версий.
- Используйте **FQCN** при вызове модулей для обеспечения стабильности и предотвращения конфликтов (например, `ansible.builtin.copy`).
- Храните инвентарь и плейбуки в системе контроля версий (Git), следуя принципам **GitOps**.
- Не отключайте проверку SSH-ключей (`host_key_checking = False`) в production без крайней необходимости.
