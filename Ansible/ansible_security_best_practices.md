# Ansible: Рекомендации по безопасности

## Определения

**Ключевой принцип безопасности Ansible** — не ограничивать возможности инструмента, а строго контролировать доступ к нему. Это означает предоставление Ansible полных прав `sudo` на управляемых узлах через выделенного пользователя и смещение фокуса безопасности на защиту **управляющего узла** (control node).

## Основные концепции

### Необходимость полных прав `sudo`

Ansible для выполнения большинства задач (установка пакетов, управление службами, изменение конфигураций) требует прав суперпользователя. Попытки ограничить `sudo` для пользователя Ansible набором разрешенных команд — **крайне плохая практика**, которая приводит к двум основным проблемам:
1.  **Хрупкость автоматизации:** Ansible использует множество системных команд и временных скриптов. Поддержка "белого списка" команд практически невозможна.
2.  **Сложность отладки:** При любом изменении в плейбуке или версии Ansible может потребоваться новая команда. Если она не разрешена, плейбук упадет с неинформативной ошибкой, поиск причины которой отнимает много времени.

Поэтому для большинства задач в плейбуках следует использовать директиву `become: true`.

### Выделенный пользователь для Ansible

На всех управляемых машинах рекомендуется создать отдельного пользователя (например, `ansible-runner`) с полными, беспарольными правами `sudo`.

**Преимущества:**

*   **Аудит и прозрачность:** В системных логах (`/var/log/auth.log`, `journalctl`) четко видно, какие действия выполнены именно Ansible.
*   **Разделение ответственности:** Это помогает отделить проблемы, внесенные автоматизацией, от ручных изменений.

## Практические сценарии

### Пошаговая настройка выделенного пользователя

Ниже приведен полный цикл настройки выделенного пользователя (назовем его `ansible_user`) на целевом хосте с использованием ad-hoc команд Ansible.

**Шаг 1: Создание пользователя**

```bash
ansible <hostname> -m user -a "name=ansible_user shell=/bin/bash state=present" --become
```
*   `--become` необходимо, так как создание пользователей требует прав `root`.

**Шаг 2: Создание `.ssh` директории**

```bash
ansible <hostname> -m file -a "path=/home/ansible_user/.ssh state=directory owner=ansible_user group=ansible_user mode=0700" --become
```

**Шаг 3: Копирование публичного SSH-ключа**

Эта команда копирует публичный ключ с управляющего узла на целевой, позволяя входить пользователем `ansible_user` без пароля.

```bash
ansible <hostname> -m copy -a 'content="{{ lookup("file", "~/.ssh/id_rsa.pub") }}" dest=/home/ansible_user/.ssh/authorized_keys owner=ansible_user group=ansible_user mode=0600' --become
```

**Шаг 4: Добавление пользователя в группу `sudo`**

Для этого проще выполнить команду на целевом хосте.

```bash
# На целевом хосте
sudo usermod -aG sudo ansible_user
```
*Примечание: в RedHat-based системах группа может называться `wheel`.*

**Шаг 5: Настройка беспарольного Sudo**

Для предоставления пользователю `ansible_user` беспарольного `sudo` создайте файл в `/etc/sudoers.d/` со следующим содержимым. Использование `sudoers.d` является лучшей практикой, так как позволяет избежать прямого редактирования основного файла `/etc/sudoers`.

**/etc/sudoers.d/90-ansible-user**
```
ansible_user ALL=(ALL) NOPASSWD: ALL
```
Эта конфигурация дает пользователю `ansible_user` возможность выполнять любые команды от имени любого пользователя без запроса пароля.

После этого необходимо настроить Ansible для использования этого пользователя. См. документацию по [Установке и настройке Ansible](ansible_setup_and_config.md).

## Дополнительная информация

### Контроль доступа к управляющему узлу

Основной фокус безопасности должен быть направлен на **управляющий узел** (control node), с которого запускается Ansible.

*   **Ограничьте доступ:** Только авторизованные и ответственные инженеры должны иметь SSH-доступ к машине, с которой выполняются плейбуки.
*   **Проверяйте код:** Внедрите процесс код-ревью для всех изменений в плейбуках и ролях.
*   **Используйте линтеры:** Применяйте инструменты статического анализа, такие как `ansible-lint`, для проверки плейбуков на соответствие лучшим практикам перед их запуском в продуктивной среде.
