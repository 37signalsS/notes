# Ansible: Рекомендации по безопасности и использованию Sudo

## Определения

При работе с Ansible, особенно в сложных и продуктивных средах, управление привилегиями является ключевым вопросом. Этот документ излагает рекомендуемый подход к безопасности, основанный на предоставлении Ansible достаточных прав для выполнения своих задач, и смещении фокуса контроля на уровень доступа к самому инструменту. Для общего понимания Ansible, см. [Введение в Ansible](ansible_introduction.md).

## 1. Необходимость `sudo`

Фундаментальный принцип заключается в том, что Ansible **нужен доступ с правами `sudo`**. Попытки запустить Ansible от пользователя без повышенных привилегий в реальных сценариях практически всегда приводят к проблемам.

*   **Причина:** Большинство комплексных плейбуков выполняют задачи, требующие прав суперпользователя: установка пакетов (`apt`, `yum`), управление службами (`systemd`), изменение системных конфигурационных файлов в `/etc`.
*   **Последствия ограничений:** Если у пользователя Ansible нет `sudo`, плейбуки будут падать с непредсказуемыми и часто непонятными ошибками, которые не всегда напрямую указывают на нехватку прав. Это значительно усложняет отладку.

Поэтому для большинства задач в плейбуках следует использовать директиву `become: true`.

## 2. Выделенный пользователь для Ansible

На всех управляемых машинах (тестовых, продуктивных) рекомендуется создать отдельного пользователя специально для Ansible (например, `ansible-runner` или `ansible-svc`).

**Преимущества:**

1.  **Аудит и прозрачность:** В системных логах (`/var/log/auth.log`, `journalctl`) будет четко видно, какие действия были выполнены именно Ansible, а какие — другими пользователями или системными процессами.
2.  **Разделение ответственности:** Это помогает отделить проблемы, внесенные автоматизацией, от проблем с безопасностью или ручными изменениями в системе.

Этому пользователю следует предоставить полные, беспарольные права `sudo`.

## 3. Опасность ограниченного `sudo`

Некоторые политики безопасности, особенно в средах на базе Red Hat с SELinux, предписывают ограничивать `sudo` для пользователя Ansible только определенным набором разрешенных команд через `sudoers`. **Это крайне плохая практика.**

*   **Хрупкость автоматизации:** Ansible использует множество различных системных команд, а также копирует на целевую машину и запускает временные скрипты. Составление и поддержка "белого списка" всех возможных исполняемых файлов — чрезвычайно трудоемкая и неблагодарная задача.

*   **Ад для отладки:** При любом изменении в плейбуке, роли или даже версии самого Ansible может потребоваться новая, непредусмотренная команда. Если ее нет в списке разрешенных, плейбук упадет с ошибкой, которая может быть совершенно не связана с правами доступа (например, "не могу выполнить модуль"). Поиск истинной причины таких сбоев превращается в кропотливую и трудоемкую работу, отнимающую часы.

Вместо того чтобы ограничивать *что* Ansible может делать, лучше контролировать *кто* может его запускать.

## 4. Контроль доступа к Ansible

Основной фокус безопасности должен быть направлен на **управляющий узел** (control node), с которого запускается Ansible.

*   **Ограничьте доступ:** Только авторизованные и ответственные инженеры должны иметь доступ к машине, с которой выполняются плейбуки.
*   **Проверяйте код:** Внедрите процесс код-ревью для всех изменений в плейбуках и ролях.
*   **Используйте линтеры:** Применяйте инструменты статического анализа, такие как `ansible-lint`, для проверки плейбуков на соответствие лучшим практикам перед их запуском в продуктивной среде.

## Итоговый подход

Рекомендуемая модель безопасности:

1.  **На целевых машинах:** Создайте выделенного пользователя с полными, беспарольными правами `sudo`.
2.  **На управляющем узле:** Строго контролируйте доступ к Ansible, его плейбукам и секретам (используя [Ansible Vault](ansible_vault.md)).
