# Ansible: Роли и Коллекции

Хотя можно писать всю автоматизацию в одном большом плейбуке, это быстро приводит к созданию громоздких и трудноподдерживаемых файлов. Поэтому в Ansible основным способом организации кода являются **роли**.

Роли позволяют объединять задачи, переменные, шаблоны и обработчики по логическому принципу (например, `role: nginx`, `role: mysql`, `role: web_app`) и переиспользовать их в разных проектах.

**Коллекции** — это современный способ распространения контента Ansible, который может включать не только роли, но и модули, плагины и документацию.

## 1. Компоненты автоматизации в Ansible

Любой сценарий Ansible состоит из четырех основных компонентов:

1.  **Задачи (Tasks):**
    *   Это атомарные шаги, из которых состоит процесс настройки сервера. Каждая задача — это вызов одного из [модулей Ansible](https://docs.ansible.com/ansible/latest/collections/index_module.html).
    *   Ansible имеет огромное количество встроенных модулей (около 500), но на практике 95% потребностей покрываются 10-15 основными (`apt`, `yum`, `copy`, `template`, `service` и т.д.).

2.  **Переменные (Variables):**
    *   Позволяют писать универсальные, параметризованные роли и плейбуки. Вместо жесткого кодирования значений (например, `port: 80`), вы используете переменные (`nginx_port: 80`), которые можно легко переопределить для разных окружений.

3.  **Шаблоны (Templates):**
    *   Ansible использует шаблонизатор **Jinja2** (популярный в мире Python) для создания динамических конфигурационных файлов.
    *   Шаблоны (`.j2` файлы) содержат переменные и логические конструкции, которые Ansible обрабатывает перед тем, как скопировать готовый файл на целевой сервер.

4.  **Обработчики (Handlers):**
    *   Это специальные задачи, которые выполняются только **один раз** в конце выполнения плея и только **если они были уведомлены** другой задачей.
    *   Основное применение — перезапуск сервисов. Если задача по изменению конфигурации внесла реальные изменения (`changed`), она отправляет уведомление хэндлеру. Если изменений не было (`ok`), хэндлер не вызывается, что предотвращает ненужные перезапуски.

## 2. Структура директорий роли

Роли имеют стандартизированную структуру каталогов. Это позволяет Ansible автоматически находить и использовать их содержимое.

```
<имя_роли>/
├── tasks/              # Основные задачи роли.
├── handlers/           # Обработчики, используемые в роли.
├── files/              # Статические файлы для копирования.
├── templates/          # Шаблоны Jinja2.
├── defaults/           # Переменные по умолчанию (низший приоритет).
├── vars/               # Переменные роли / константы (высокий приоритет).
├── meta/               # Метаданные роли, включая зависимости.
└── tests/              # Тесты для роли (для Molecule).
```

### `tasks/main.yml`
Это главный каталог роли, содержащий файлы с задачами. Файл `main.yml` является точкой входа. Ansible автоматически ищет и выполняет его при вызове роли. Внутри `main.yml` можно подключать другие файлы задач из этого же каталога с помощью `include_tasks`.

### `files/`
Каталог для хранения статических файлов, которые нужно скопировать на целевой сервер "как есть". Модуль `ansible.builtin.copy` автоматически ищет файлы в этой директории, если указан относительный путь.

### `templates/`
Каталог для хранения шаблонов Jinja2 (обычно с расширением `.j2`). Модуль `ansible.builtin.template` ищет шаблоны в этой директории. Он обрабатывает переменные и логику внутри шаблона и копирует на целевой хост уже готовый файл.

### `handlers/main.yml`
Здесь определяются обработчики. Как и в `tasks`, `main.yml` является основной точкой входа.

### `defaults/main.yml` vs `vars/main.yml`
Оба каталога предназначены для переменных, но имеют разный приоритет и назначение.

*   **`defaults/main.yml` (Переменные по умолчанию):**
    *   **Назначение:** Определить значения "по умолчанию" для переменных, которые пользователь роли может захотеть переопределить.
    *   **Приоритет:** **Самый низкий.** Значения из этого файла будут легко переопределены переменными из инвентаря, плейбука или командной строки.
    *   **Пример:** `nginx_worker_processes: 4`

*   **`vars/main.yml` (Константы роли):**
    *   **Назначение:** Определить переменные, которые не предназначены для переопределения извне. Их можно рассматривать как **константы** внутри роли, используемые для удобства написания задач.
    *   **Приоритет:** **Высокий.** Эти переменные переопределяют значения из `defaults`, инвентаря и плейбука, но могут быть переопределены через `--extra-vars` в командной строке.
    *   **Пример:** `nginx_config_path: /etc/nginx/nginx.conf`

> **Лучшая практика:** Большинство переменных следует определять в `defaults/main.yml`, чтобы сделать роль максимально гибкой и переиспользуемой. `vars/main.yml` используйте только для внутренних констант роли.

### `meta/main.yml`
Содержит метаданные роли, такие как автор, лицензия и, что самое важное, **зависимости**. Здесь можно указать другие роли, которые должны быть выполнены *перед* текущей.

```yaml
# meta/main.yml в роли 'my_app'
dependencies:
  - role: geerlingguy.nginx
  - role: geerlingguy.postgresql
    vars:
      postgresql_version: "14" # Можно передать параметры в зависимую роль
```

## 3. Использование ролей

### Создание каркаса роли
Утилита `ansible-galaxy` автоматически создает всю необходимую структуру директорий.

```bash
ansible-galaxy init my_new_role
```

### Использование ролей в плейбуке
Роли применяются к хостам с помощью ключевого слова `roles` в плейбуке.

```yaml
- name: Example playbook using roles
  hosts: webservers
  become: true

  roles:
    - common      # Простая роль по имени
    - geerlingguy.nginx       # Роль из коллекции
    - { role: my_app.memcached, port: 11211, tags: ["memcached"] } # Передача параметров и тегов
```

## 4. Ansible Galaxy
`ansible-galaxy` — это не только утилита, но и центральный репозиторий ([galaxy.ansible.com](https://galaxy.ansible.com)) для поиска и обмена контентом.

*   **Управление зависимостями (`requirements.yml`):**
    Лучшая практика — определять все внешние роли и коллекции в файле `requirements.yml`.
    ```yaml
    # requirements.yml
    roles:
      - name: geerlingguy.postgresql
        version: 1.8.0

    collections:
      - name: community.postgresql
        version: 2.3.0
    ```
    Установка зависимостей:
    ```bash
    ansible-galaxy install -r requirements.yml
    ```
### Приватный репозиторий Galaxy

Для крупных организаций стандартной практикой является развертывание собственного, приватного сервера Ansible Galaxy. Это позволяет хранить внутри компании специфические роли, не выкладывая их в публичный доступ.

Адрес приватного сервера настраивается в файле `ansible.cfg`:
```ini
[galaxy]
server_list = my_company_galaxy

[galaxy_server.my_company_galaxy]
url = https://galaxy.mycompany.com/


### Управление зависимостями (`requirements.yml`)

Вместо того чтобы устанавливать роли и коллекции по одной, лучшей практикой является определение всех зависимостей проекта в одном файле, который обычно называется `requirements.yml`.

Это позволяет любому члену команды быстро настроить рабочее окружение, выполнив всего пару команд.

**Пример `requirements.yml`:**

```yaml
# roles/requirements.yml

roles:
  # 1. Установка роли из Ansible Galaxy
  - name: geerlingguy.postgresql
    version: 1.8.0 # Можно указать конкретную версию

collections:
  # 2. Установка коллекции из Ansible Galaxy
  - name: community.postgresql
    version: 2.3.0

  # 3. Установка коллекции из Git-репозитория
  - name: https://github.com/ansible-collections/community.docker.git
    type: git
    version: main # Можно указать ветку, тег или коммит
```

**Установка зависимостей из файла:**

К сожалению, `ansible-galaxy` требует раздельного вызова для установки ролей и коллекций.

```bash
# 1. Установить роли из файла
ansible-galaxy role install -r requirements.yml

# 2. Установить коллекции из файла
ansible-galaxy collection install -r requirements.yml
```

### Пути установки

По умолчанию `ansible-galaxy` пытается установить контент в следующем порядке:
1.  `~/.ansible/roles` или `~/.ansible/collections` (в домашней директории пользователя).
2.  `/usr/share/ansible/roles` или `/usr/share/ansible/collections` (общесистемный путь).
3.  `/etc/ansible/roles` или `/etc/ansible/collections` (глобальный путь).

Вы можете переопределить эти пути в файле `ansible.cfg`.
