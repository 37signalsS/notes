# Ansible: Роли и Коллекции

## Определения

Хотя можно писать всю автоматизацию в одном большом плейбуке, это быстро приводит к созданию громоздких и трудноподдерживаемых файлов. Поэтому в Ansible основным способом организации и переиспользования кода являются **роли** и **коллекции**.

* **Роль (Role)**: Базовая единица переиспользования в Ansible. Это предопределенная структура файлов и каталогов, которая инкапсулирует набор задач, переменных, шаблонов и обработчиков для автоматизации настройки конкретного компонента системы (например, роль для установки Nginx).
* **Коллекция (Collection)**: Более крупная структура, которая является современным способом распространения контента Ansible. Коллекция может включать в себя несколько ролей, плагинов, модулей и документации, объединенных для работы с целой экосистемой (например, коллекция `community.postgresql` содержит всё для управления PostgreSQL).

## Основные концепции

### Компоненты роли

Любой сценарий Ansible состоит из четырех основных компонентов, которые инкапсулируются в ролях:

1. **Задачи (Tasks):** Атомарные шаги, каждый из которых вызывает один из [модулей Ansible](Modules/ansible_modules_overview.md) (`apt`, `copy`, `service` и т.д.).
2. **Переменные (Variables):** Позволяют параметризовать роли и плейбуки.
3. **Шаблоны (Templates):** Файлы `.j2` с использованием шаблонизатора [Jinja2](ansible_jinja2_templating.md) для создания динамических конфигураций.
4. **Обработчики (Handlers):** Специальные задачи для перезапуска сервисов, которые выполняются только один раз при получении [уведомления (`notify`)](PlaybookStructure/basics.md#обработчики-handlers-и-уведомления-notify).

### Структура роли

Роли имеют стандартизированную структуру каталогов, которую Ansible находит автоматически.

#### Внутренняя структура роли

Стандартные каталоги роли разделяют ответственность и позволяют Ansible автоматически находить ресурсы:

| Каталог | Назначение |
| :--- | :--- |
| `tasks/` | Основные задачи роли (main.yml как входная точка) |
| `handlers/` | Обработчики уведомлений (например, перезапуск сервиса) |
| `templates/` | Jinja2-шаблоны конфигураций |
| `files/` | Готовые файлы для копирования |
| `defaults/` | Переменные по умолчанию (низкий приоритет) |
| `vars/` | Жестко заданные переменные (высокий приоритет, используйте осторожно) |
| `meta/` | Зависимости ролей, поддерживаемые платформы |
| `tests/` или `molecule/` | Локальные проверки роли |

При создании роли с помощью `ansible-galaxy init` создается следующая структура:

* `tasks/main.yml`: Главный файл с задачами, точка входа для роли. Здесь описывается основная логика автоматизации. Ansible автоматически ищет и выполняет его при вызове роли.
* `handlers/main.yml`: Файл с обработчиками. Они выполняются только при вызове из задач через `notify`.
* `files/`: Каталог для хранения статических файлов (бинарные файлы, скрипты), которые нужно скопировать на целевой узел без изменений с помощью модуля `ansible.builtin.copy`.
* `templates/`: Каталог для хранения [шаблонов](ansible_jinja2_templating.md) конфигурационных файлов (`.j2`), которые обрабатываются модулем `ansible.builtin.template`.
* `defaults/main.yml`: Здесь задаются переменные по умолчанию (например, версии софта, стандартные порты). Они имеют самый низкий приоритет и могут быть легко переопределены.
* `vars/main.yml`: Здесь хранятся переменные, которые имеют более высокий приоритет и не предназначены для переопределения извне (константы роли).
* `meta/main.yml`: Описывает метаданные роли: автор, лицензия, поддерживаемые платформы и, что важно, зависимости от других ролей.
* `tests/`: Каталог для тестов роли, обычно с использованием [Molecule](ansible_testing_with_molecule.md).

#### Сравнение `defaults/main.yml` и `vars/main.yml`

* **`defaults/main.yml` (Переменные по умолчанию):**
  * **Назначение:** Определить значения "по умолчанию" для переменных, которые пользователь роли может захотеть переопределить.
  * **Приоритет:** **Самый низкий.** Значения из этого файла будут легко переопределены переменными из инвентаря, [плейбука](PlaybookStructure/basics.md) или командной строки.
  * **Пример:** `nginx_worker_processes: 4`

* **`vars/main.yml` (Константы роли):**
  * **Назначение:** Определить переменные, которые не предназначены для переопределения извне. Их можно рассматривать как **константы** внутри роли.
  * **Приоритет:** **Высокий.** Эти переменные переопределяют значения из `defaults`, инвентаря и плейбука, но могут быть переопределены через `--extra-vars` в командной строке.
  * **Пример:** `nginx_config_path: /etc/nginx/nginx.conf`

> **Лучшая практика:** Большинство переменных следует определять в `defaults/main.yml`, чтобы сделать роль максимально гибкой и переиспользуемой. `vars/main.yml` используйте только для внутренних констант роли.

#### Зависимости роли в `meta/main.yml`

Этот файл содержит метаданные роли, и, что самое важное, **зависимости**. Здесь можно указать другие роли, которые должны быть выполнены *перед* текущей.

```yaml
# meta/main.yml в роли 'my_app'
dependencies:
  - role: geerlingguy.nginx
  - role: geerlingguy.postgresql
    vars:
      postgresql_version: "14" # Можно передать параметры в зависимую роль
```

## Практические сценарии

### Создание и использование ролей

#### Создание каркаса роли

Утилита `ansible-galaxy` автоматически создает всю необходимую структуру директорий для новой роли.

```bash
# Команда создает директорию my_new_role с полной структурой
ansible-galaxy init my_new_role
```

#### Наполнение роли логикой

Основная работа происходит в файле `tasks/main.yml`.

**Пример: роль `set_time`**

1. **Создаем роль:**

    ```bash
    ansible-galaxy init set_time
    ```

2. **Добавляем задачу в `roles/set_time/tasks/main.yml`:**

    ```yaml
    ---
    # tasks file for set_time
    - name: Set timezone to Europe/Moscow
      ansible.builtin.timezone:
        name: Europe/Moscow
    ```

    *Важно: не удаляйте `---` в начале файла.*

#### Подключение роли в плейбуке

Роли применяются к хостам с помощью ключевого слова `roles` в плейбуке. Ansible автоматически ищет роли в директории `roles/` рядом с плейбуком.

**Пример `playbook.yml`:**

```yaml
---
- name: Configure servers
  hosts: webservers
  become: true
  roles:
    - set_time # Указываем имя роли
```

При запуске этого плейбука для всех хостов из группы `webservers` будет применена роль `set_time`, которая установит часовой пояс `Europe/Moscow`.

**Более сложные примеры подключения:**

```yaml
- name: Example playbook using roles
  hosts: webservers
  become: true

  roles:
    - common      # Простая роль по имени
    - geerlingguy.nginx       # Роль из коллекции
    - { role: my_app.memcached, port: 11211, tags: ["memcached"] } # Передача параметров и тегов
```

### Стратегии разбиения ролей

* **По компонентам**: `web`, `db`, `cache`, `monitoring` — каждая роль отвечает за один логический сервис.
* **По слоям**: `base` (пакеты, пользователи), `hardening` (политики безопасности), `runtime` (сервисы приложений). В playbook слои подключаются в определенном порядке.
* **По платформам**: выносите различия в отдельные задачи с `when:` или в поддиректории `tasks/`, не создавая дублирующих ролей. Например, `os-specific.yml` включается условно.
* **По доменам ответственности**: сетевые настройки, журналирование, прокси — для уменьшения связности.

### Ручное управление ролями через Git

Это альтернативный подход, который не использует `ansible-galaxy` для установки, а вместо этого полагается на модуль `ansible.builtin.git` для клонирования ролей в локальный проект. Этот метод подходит для небольших команд или для тех, кто предпочитает прямой контроль над исходным кодом ролей.

**Основная идея:**

1. **Роли в отдельном репозитории:** Все роли проекта хранятся в одном выделенном Git-репозитории (например, `my-ansible-roles` на GitLab или GitHub).
2. **Основной проект отдельно:** Проект с плейбуками и инвентарем хранится в другом репозитории.
3. **Игнорирование папки `roles`:** В основном проекте директория `roles/` добавляется в `.gitignore`, так как ее содержимое будет управляться автоматически.
4. **Плейбук для инициализации:** Создается специальный плейбук (например, `init.yml`), который клонирует репозиторий с ролями в локальную папку `roles/`.

**Шаг 1: Создайте `.gitignore` в корне основного проекта**

```
# .gitignore
roles/
```

Это предотвратит случайное добавление папки с ролями в основной репозиторий.

**Шаг 2: Создайте плейбук `init.yml` для загрузки ролей**
Этот плейбук выполняется на локальной машине (`localhost`) для подготовки рабочего окружения.

```yaml
# init.yml
---
- name: Download roles from Git repository
  hosts: localhost
  connection: local
  gather_facts: false

  tasks:
    - name: Ensure roles directory exists
      ansible.builtin.file:
        path: roles
        state: directory

    - name: Clone or update roles repository
      ansible.builtin.git:
        repo: 'git@gitlab.com:your_user/my-ansible-roles.git' # SSH URL вашего репозитория
        dest: roles
        version: master # Можно указать ветку, тег или коммит
        force: true # Перезаписывать локальные изменения, чтобы всегда иметь актуальную версию
```

**Шаг 3: Запуск и обновление**
Для первоначальной загрузки ролей или для их обновления до последней версии достаточно выполнить этот плейбук:

```bash
ansible-playbook init.yml
```

Как вариант, можно вручную обновить репозиторий:

```bash
cd roles
git pull
```

**Сравнение подходов:**

|  | **Ручной метод (`git` модуль)** | **Стандартный метод (`requirements.yml`)** |
| :--- | :--- | :--- |
| **Простота** | Высокая. Легко понять, так как это просто `git clone`. | Средняя. Требует знания `ansible-galaxy` и формата `requirements.yml`. |
| **Управление версиями** | Ручное. Вы управляете версией через поле `version` или вручную в Git. | Автоматизированное. `ansible-galaxy` может управлять версиями ролей. |
| **Структура проекта** | Код ролей физически находится внутри проекта в папке `roles`. | Роли устанавливаются в системные или пользовательские директории, а не в проект. |
| **Изоляция** | Нет. Все роли из репозитория клонируются вместе. | Высокая. Можно устанавливать разные версии одной и той же роли для разных проектов. |
| **Лучший сценарий** | Небольшие проекты, обучение, полный контроль над кодом ролей. | Крупные проекты, сложные зависимости, необходимость строгого версионирования. |

## Дополнительная информация

### Управление ролями с Ansible Galaxy

Ansible Galaxy — это официальный репозиторий ([galaxy.ansible.com](https://galaxy.ansible.com)) и утилита командной строки для поиска, обмена и управления контентом Ansible.

* **Создание каркаса роли:**

    ```bash
    ansible-galaxy role init my_new_role
    ```

* **Установка ролей и коллекций:**

    ```bash
    # Установить роль
    ansible-galaxy install geerlingguy.postgresql

    # Установить коллекцию
    ansible-galaxy collection install community.postgresql
    ```

* **Просмотр установленных компонентов:**

    ```bash
    ansible-galaxy role list
    ansible-galaxy collection list
    ```

### Управление зависимостями через `requirements.yml`

Лучшая практика — определять все внешние роли и коллекции в файле `requirements.yml`.

**Пример `requirements.yml`:**

```yaml
roles:
  # 1. Установка роли из Ansible Galaxy
  - name: geerlingguy.postgresql
    version: 1.8.0 # Можно указать версию

  # 2. Установка роли из Git-репозитория
  - src: https://github.com/geerlingguy/ansible-role-nginx.git
    scm: git
    name: nginx # Имя, которое будет у роли локально

collections:
  # 3. Установка коллекции из Ansible Galaxy
  - name: community.postgresql
    version: 2.3.0

  # 4. Установка коллекции из Git-репозитория
  - name: https://github.com/ansible-collections/community.docker.git
    type: git
    version: main # Ветка, тег или коммит
```

**Установка зависимостей из файла:**

К сожалению, `ansible-galaxy` требует раздельного вызова для установки ролей и коллекций.

```bash
# Установить роли
ansible-galaxy role install -r requirements.yml

# Установить коллекции
ansible-galaxy collection install -r requirements.yml
```

### Пути установки и приватный Galaxy

По умолчанию `ansible-galaxy` устанавливает контент в `~/.ansible/` или системные директории. Эти пути можно переопределить в `ansible.cfg`. Для крупных организаций стандартной практикой является развертывание собственного, приватного сервера Ansible Galaxy, адрес которого настраивается в `ansible.cfg`:

```ini
[galaxy]
server_list = my_company_galaxy

[galaxy_server.my_company_galaxy]
url = https://galaxy.mycompany.com/
```
