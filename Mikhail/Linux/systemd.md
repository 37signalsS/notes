# Systemd: Управление системой и службами

`systemd` — это современный менеджер системы и служб для Linux, который стал стандартом для большинства дистрибутивов. Он отвечает за инициализацию системы после загрузки ядра, а также за управление службами (демонами), сокетами, точками монтирования и другими системными ресурсами.

---

## 1. Ключевые концепции

### Юниты (Units)

`systemd` управляет ресурсами через **юниты**. Юнит — это конфигурационный файл, описывающий ресурс и то, как им управлять. Основные типы юнитов:

-   `.service`: Системная служба (например, `nginx.service`).
-   `.socket`: Сетевой сокет, который может активировать службу при поступлении соединения.
-   `.target`: Группа юнитов, аналог "уровней выполнения" (runlevels) в старых системах.
-   `.timer`: Юнит для запуска других юнитов по расписанию, замена `cron`.
-   `.mount` / `.automount`: Точки монтирования файловых систем.

**Расположение юнит-файлов:**
-   `/usr/lib/systemd/system/`: Юниты, поставляемые с установленными пакетами. **Не изменяйте их напрямую.**
-   `/etc/systemd/system/`: Юниты, созданные или измененные системным администратором. Эти файлы имеют приоритет над файлами в `/usr/lib/`.

### Таргеты (Targets)

Таргет — это точка синхронизации, которая группирует другие юниты. Основные таргеты:

-   `multi-user.target`: Стандартный многопользовательский режим без графического интерфейса (аналог runlevel 3).
-   `graphical.target`: Многопользовательский режим с графическим интерфейсом (аналог runlevel 5).

## 2. Управление службами (`systemctl`)

`systemctl` — это основной инструмент для взаимодействия с `systemd`.

### Базовые команды

```bash
# Запустить службу
sudo systemctl start nginx.service

# Остановить службу
sudo systemctl stop nginx.service

# Перезапустить службу
sudo systemctl restart nginx.service

# Перечитать конфигурацию службы без перезапуска (если служба это поддерживает)
sudo systemctl reload nginx.service

# Показать детальный статус службы
systemctl status nginx.service
```

### Управление автозапуском

```bash
# Включить автозапуск службы при загрузке системы
sudo systemctl enable nginx.service

# Отключить автозапуск
sudo systemctl disable nginx.service

# Проверить, включен ли автозапуск
systemctl is-enabled nginx.service
```

### Маскировка служб

Маскировка — это полное отключение службы, создающее символическую ссылку на `/dev/null`. Замаскированную службу нельзя запустить даже вручную.

```bash
# Запретить запуск службы
sudo systemctl mask bluetooth.service

# Отменить маскировку
sudo systemctl unmask bluetooth.service
```

### Просмотр юнитов

```bash
# Показать все активные юниты
systemctl list-units

# Показать все установленные юнит-файлы и их статус
systemctl list-unit-files
```

## 3. Просмотр логов (`journalctl`)

`systemd` имеет собственную систему логирования `journald`, которая собирает сообщения от ядра, служб и других компонентов.

```bash
# Просмотреть логи конкретной службы
journalctl -u nginx.service

# Отслеживать логи в реальном времени (как tail -f)
journalctl -f -u nginx.service

# Показать логи с начала текущей загрузки
journalctl -b

# Фильтровать по времени
journalctl --since "1 hour ago"

# Показать только ошибки и более критичные сообщения
journalctl -p err -b
```

## 4. Создание и редактирование юнитов

### Лучшая практика: `systemctl edit`

Чтобы изменить параметры существующей службы (например, `nginx.service`), не изменяя ее оригинальный файл, используйте `systemctl edit`.

```bash
sudo systemctl edit nginx.service
```

Эта команда создаст файл-дополнение (override) в `/etc/systemd/system/nginx.service.d/override.conf`. В нем нужно указать только те директивы, которые вы хотите изменить или добавить.

**Пример: добавить автоматический перезапуск для `nginx`:**
```ini
# В файле /etc/systemd/system/nginx.service.d/override.conf
[Service]
Restart=always
RestartSec=10
```

После любого изменения юнит-файлов, сообщите `systemd` об этом:
```bash
sudo systemctl daemon-reload
```

### Создание нового юнит-файла

Создайте файл, например, `/etc/systemd/system/my_app.service`.

```ini
[Unit]
# Человекочитаемое описание службы
Description=My Application
# Запускать после того, как будет готова сеть
After=network.target

[Service]
# simple: основной процесс службы - это главный процесс
Type=simple

# Команда для запуска
ExecStart=/usr/bin/my_app --config /etc/my_app.conf

# Политика перезапуска: перезапускать при сбое
Restart=on-failure
RestartSec=5s

# Запускать от имени непривилегированного пользователя
User=app_user
Group=app_group

# Рабочая директория
WorkingDirectory=/opt/my_app

# Переменные окружения
Environment="ENV_VAR=production"

[Install]
# Указывает, что юнит должен быть частью стандартного многопользовательского режима
WantedBy=multi-user.target
```

### Зависимости между юнитами

- **`After=` / `Before=`**: Управляют только **порядком** запуска, но не создают реальной зависимости.
- **`Wants=`**: "Мягкая" зависимость. `systemd` попытается запустить указанный юнит, но если тот не запустится, это не повлияет на основной юнит.
- **`Requires=`**: "Жёсткая" зависимость. Если юнит, указанный в `Requires=`, не сможет запуститься, то и зависимый от него юнит тоже не запустится.
- **`BindsTo=`**: Самая сильная связь. Работает как `Requires=`, но дополнительно привязывает жизненные циклы. Если связанный юнит останавливается или падает, `systemd` немедленно остановит и этот юнит.
- **`PartOf=`**: Похоже на `BindsTo=`, но работает в одну сторону. Если юнит, указанный в `PartOf=`, останавливается или перезапускается, то же самое произойдёт и с этим юнитом.

## 5. Продвинутые темы

### Задачи по расписанию: Timers

Таймеры — это современная замена `cron`. Они состоят из двух файлов: `.service` (что делать) и `.timer` (когда делать).

1.  **Создайте `.service` файл** (например, `/etc/systemd/system/my_backup.service`), описывающий задачу.
2.  **Создайте `.timer` файл** с тем же именем:
    `/etc/systemd/system/my_backup.timer`
    ```ini
    [Unit]
    Description=Run backup script daily at 2 AM

    [Timer]
    # Запускать ежедневно в 2 часа ночи. 
    # Другие форматы: hourly, daily, weekly, YYYY-MM-DD HH:MM:SS
    OnCalendar=*-*-* 02:00:00
    # Если система была выключена, запустить сразу после загрузки
    Persistent=true

    [Install]
    WantedBy=timers.target
    ```
3.  **Включите и запустите таймер (не сервис!):**
    ```bash
    sudo systemctl enable my_backup.timer
    sudo systemctl start my_backup.timer
    ```
4.  **Проверить активные таймеры:**
    ```bash
    systemctl list-timers
    ```

### Анализ производительности загрузки

`systemd-analyze` помогает выявить узкие места при загрузке системы.

```bash
# Общее время загрузки
systemd-analyze

# Время запуска каждого юнита
systemd-analyze blame

# Показать критическую цепь зависимостей, замедливших загрузку
systemd-analyze critical-chain
```

### Пользовательские службы

`systemd` может управлять службами для конкретного пользователя. Юниты хранятся в `~/.config/systemd/user/`. Управлять ими можно флагом `--user`.

```bash
systemctl --user start my_app.service
systemctl --user enable my_app.service
```
