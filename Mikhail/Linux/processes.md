# **В Linux существует несколько методов создания процессов:**

fork() — используется для создания нового процесса путем дублирования существующего. В результате выполнения fork() мы получаем два почти идентичных процесса, с одним важным исключением: системный вызов fork() возвращает два разных значения. В дочернем процессе это значение равно 0 (всегда помним, что согласно Linux-нумерологии 0 обозначает успех), а в родительском процессе возвращается идентификатор PID процесса-потомка. При создании процесса память не копируется сразу, а используется механизм **Copy-on-Write (CoW)**: родительский и дочерний процессы изначально используют одни и те же физические страницы памяти. Копия страницы создается только тогда, когда один из процессов пытается ее изменить.

exec() — используется для замены текущего процесса на новый, без возврата(дальнейшие команды в скрипте не будут выполняться, так как оболочка заменена). При вызове `exec` сохраняется PID процесса, его родительский процесс (PPID) и открытые файловые дескрипторы. Все остальное, включая адресное пространство, заменяется новым.

system() — создает новый процесс для работы команды, указанной в качестве аргумента. Метод ожидает завершения выполнения команды и возвращает статус ее выхода.

clone() — похож на fork(), но обеспечивает гораздо более тонкую настройку того, что будет общим у родительского и дочернего процессов. Он позволяет указать различные флаги для управления совместным использованием ресурсов (память, файловые дескрипторы, таблицы сигналов и т.д.) между родительским и дочерним процессами. 

# **Имя отчество (PID PPID)**

Здесь все довольно очевидно: PID (Process ID) — это уникальный номер, присваиваемый процессу ядром для контроля его выполнения и предоставления ресурсов. Каждый процесс также имеет атрибут PPID (Parent Process ID), который совпадает с идентификатором PID родительского процесса, то есть процесса, который его инициировал. Когда PID достигают максимального значения (заданного в `/proc/sys/kernel/pid_max`), они начинают циклически переиспользоваться.

Вариант получения PID и PPID:

```sh
pstree -p
```

# **Элементы процесса**

Процесс — это исполняемая программа в действии, со всем её окружением и контекстом. В ядре Linux каждый процесс (и каждый поток) представлен структурой данных `task_struct`. 

К элементам процесса (и, соответственно, полям `task_struct`) относят:

- **Дескриптор процесса (`task_struct`)**: Центральная структура данных в ядре, которая содержит всю информацию о процессе, включая:
    - **Состояние процесса**: `R` (Running), `S` (Sleeping), `D` (Disk sleep), `Z` (Zombie) и т.д.
    - **Идентификаторы**:
        - **PID (Process ID):** Уникальный идентификатор процесса.
        - **PPID (Parent Process ID):** Идентификатор родительского процесса.
        - **UID (User ID):** Идентификатор пользователя, запустившего процесс.
        - **EUID (Effective User ID):** Эффективный идентификатор пользователя. Используется для определения прав доступа к ресурсам. Обычно совпадает с UID, но может быть временно изменен при выполнении программ с флагом `setuid`.
        - **GID (Group ID):** Идентификатор группы пользователя.
        - **EGID (Effective Group ID):** Эффективный идентификатор группы. Аналогичен EUID, но для групп (используется для программ с флагом `setgid`).
    - **Информация для планировщика**: Приоритет, политика планирования, процессорное время.
    - **Управление памятью**: Указатели на структуры, описывающие адресное пространство процесса (`mm_struct`).
    - **Учетные данные (credentials)**: Информация о правах доступа (пользователь, группа).
    - **Открытые файлы**: Указатель на таблицу файловых дескрипторов.
    - **Обработчики сигналов**: Информация о том, как процесс реагирует на сигналы.
- **Контекст выполнения**: Состояние регистров процессора, счетчик команд и т.д.
- **Открытые файлы и дескрипторы**: По умолчанию каждый процесс при старте открывает три стандартных файловых дескриптора: stdin (стандартный ввод), stdout (стандартный вывод) и stderr (стандартный вывод ошибок).
- **Адресное пространство**: Виртуальная память, доступная процессу.
- **Иерархия**: Связи с родительским и дочерними процессами.

### Переключение контекста (Context Switching)

**Переключение контекста** — это процесс сохранения состояния (контекста) одного процесса и восстановления состояния другого, чтобы CPU мог переключиться на его выполнение. Это позволяет нескольким процессам разделять один процессорный ресурс и создает иллюзию одновременного выполнения (многозадачность).

**Когда это происходит?**
- **Многозадачность:** Планировщик ОС прерывает процесс по истечении его кванта времени.
- **Системный вызов:** Процесс запрашивает операцию у ядра (например, чтение с диска) и переходит в режим ожидания.
- **Аппаратное прерывание:** Устройства (сетевая карта, клавиатура) требуют внимания процессора.

**Как это работает:**
1.  **Сохранение контекста:** Ядро сохраняет состояние текущего процесса (регистры CPU, счетчик команд, указатель стека) в его **Блок управления процессом (Process Control Block, PCB)**.
2.  **Выбор следующего процесса:** Планировщик ОС выбирает следующий процесс из очереди готовых.
3.  **Восстановление контекста:** Ядро загружает контекст нового процесса из его PCB в регистры CPU.
4.  **Передача управления:** Процесс продолжает выполнение с того места, где был остановлен.

**Цена переключения:**
Переключение контекста — это накладные расходы. Основная проблема — **инвалидация кэша CPU и TLB**. Новому процессу приходится загружать свои данные из медленной оперативной памяти, что временно снижает производительность.

# **Типы процессов**

-   **Пользовательские процессы (User Processes):**
    -   Запускаются от имени обычных пользователей и работают в **пространстве пользователя (userspace)**.
    -   Их доступ к системным ресурсам и оборудованию строго ограничен. Для выполнения привилегированных операций (например, запись в системные файлы или работа с сетью) они должны обращаться к ядру через системные вызовы.

-   **Процессы ядра (Kernel Processes/Threads):**
    -   Работают исключительно в **пространстве ядра (kernelspace)** и имеют полный, неограниченный доступ ко всем ресурсам системы.
    -   Не являются результатом запуска пользовательских программ. Они выполняют внутренние задачи операционной системы: управление памятью, планирование других процессов, работа с драйверами.
    -   В выводе `ps` их часто можно узнать по квадратным скобкам вокруг имени, например `[kthreadd]`.

-   **Демоны (Daemons):**
    -   Это специальные пользовательские процессы, которые работают в фоновом режиме, ожидая определённых событий, и не требуют прямого взаимодействия с пользователем через терминал.
    -   Их родительским процессом часто является `systemd` (PID 1).
    -   Как правило, системные службы (демоны) запускаются от имени системных пользователей с идентификаторами (UID) в диапазоне до 1000.


# **Потоки**

Поток - это легковесный подпроцесс внутри процесса. Потоки внутри одного процесса используют общие ресурсы, такие как память. Они имеют свой уникальный идентификатор потока (TID), но используют тот же самый PID, что и процесс. Идентификатор группы потоков (TGID) является общим для всех потоков в рамках одного процесса и совпадает с PID самого процесса.

Зачем потоки: Потоки обеспечивают параллельное выполнение внутри одного процесса. Это позволяет эффективнее использовать многозадачность и многопроцессорные системы. Потоки внутри процесса могут легко обмениваться данными, так как они имеют общую память.

### **Процессы vs. Потоки: Ключевые различия в управлении ресурсами**

| Характеристика | Процесс | Поток |
| :--- | :--- | :--- |
| **Изоляция** | Процессы полностью изолированы друг от друга. У каждого есть свое собственное адресное пространство, память, открытые файлы и другие ресурсы. | Потоки разделяют адресное пространство и ресурсы своего родительского процесса. |
| **Создание** | Создание нового процесса (например, с помощью системного вызова `fork()`) является "дорогостоящей" операцией, так как требует выделения и копирования большого количества ресурсов. | Создание потока — более "легковесная" и быстрая операция, поскольку новый поток повторно использует ресурсы существующего процесса. |
| **Взаимодействие** | Взаимодействие между процессами (IPC — Inter-Process Communication) требует специальных механизмов, таких как каналы (pipes), сокеты или разделяемая память. | Потоки могут взаимодействовать напрямую через общую память, что значительно быстрее и проще. |
| **Надежность** | Сбой в одном процессе, как правило, не влияет на другие процессы в системе. | Ошибка в одном потоке (например, из-за неверного доступа к памяти) может привести к сбою всего процесса, включая все его потоки. |
| **Ресурсы CPU** | Процессы конкурируют за процессорное время как независимые единицы. Планировщик ОС выделяет каждому процессу свой квант времени. | Потоки одного процесса также конкурируют за CPU, но планировщик может рассматривать их как группу. На многоядерных системах потоки одного процесса могут выполняться **параллельно** на разных ядрах, обеспечивая истинный параллелизм. |
| **Ресурсы памяти** | Каждый процесс имеет свое собственное, изолированное виртуальное адресное пространство. Один процесс не может напрямую получить доступ к памяти другого. | Все потоки внутри одного процесса **разделяют общее адресное пространство**. Это означает, что они могут читать и изменять одни и те же данные и переменные, что упрощает взаимодействие, но требует механизмов синхронизации (например, мьютексов) для избежания "состояния гонки". |

### **Планировщик Linux и его отношение к процессам и потокам**

С точки зрения планировщика ядра Linux, фундаментальной единицей планирования является не процесс, а "задача" (task). В Linux, по сути, нет строгого разделения между процессами и потоками на уровне планировщика. Каждый поток рассматривается как отдельная задача, подлежащая планированию.

**Основные принципы работы планировщика:**

*   **Completely Fair Scheduler (CFS):** Для обычных процессов (не реального времени) в Linux используется планировщик CFS. Его главная цель — обеспечить "справедливое" распределение процессорного времени между всеми задачами. CFS не использует фиксированные кванты времени, а стремится дать каждой задаче долю процессорного времени.
*   **Виртуальное время (vruntime):** CFS отслеживает, сколько времени каждая задача уже поработала, используя переменную `vruntime`. Планировщик всегда выбирает для выполнения ту задачу, у которой наименьшее значение `vruntime`, то есть ту, которая получила меньше всего процессорного времени.
*   **Планирование на основе потоков:** Поскольку планировщик оперирует задачами, а каждый поток является задачей, то планирование в Linux по своей сути является планированием на основе потоков. Это означает, что потоки одного и того же процесса могут выполняться параллельно на разных ядрах процессора.
*   **Классы планирования:** В Linux существуют различные классы планирования. Помимо `SCHED_NORMAL` (для CFS), есть классы для процессов реального времени, такие как `SCHED_FIFO` (первым пришел — первым вышел) и `SCHED_RR` (циклическое обслуживание), которые имеют более высокий приоритет. Процессы реального времени будут выполняться до тех пор, пока они готовы к выполнению, даже если другие процессы "голодают".

# **Список процессов и информация о них**

Для просмотра и управления процессами используются утилиты `top`, `htop` и `ps`.

**Пример:** `top - 14:50:30 up 2 days,  4:21,  1 user,  load average: 0.05, 0.08, 0.07`

-   `14:50:30` — текущее системное время.
-   `up 2 days, 4:21` — **Uptime**. Показывает, как долго система работает без перезагрузки.
-   `1 user` — **Количество активных пользовательских сессий**.
-   `load average: 0.05, 0.08, 0.07` — **Средняя нагрузка** на систему за последние 1, 5 и 15 минут.

#### Интерактивные команды в `top`
-   **`1`**: Показать/скрыть статистику по каждому ядру CPU. Позволяет увидеть, равномерно ли распределена нагрузка.

#### Основные команды в `htop`
-   **t**: Вывести процессы в виде дерева.
-   **C**: Сортировать по CPU.
-   **M**: Сортировать по памяти (MEM).
-   **/**: Поиск по имени процесса.
-   **\**: Фильтр по имени процесса (сброс - Esc).
-   **u**: Показать процессы определенного пользователя.
-   **k**: Послать сигнал процессу.
-   **l**: Показать файлы, открытые процессом (использует `lsof`).
-   **e**: Показать переменные окружения процесса.
-   **Пробел**: Выделить/снять выделение с процесса для массовых действий (отменить все выделения - U).

**Кастомизация htop с бэкапом**

```bash
mkdir -p ~/.config/htop && [ -f ~/.config/htop/htoprc ] && mv ~/.config/htop/htoprc ~/.config/htop/htoprc.bak.$(date +%Y%m%d%H%M%S); curl -fsSL "https://gist.github.com/itcaat/45ea5994d66378fc4bd647cab860a05f/raw" -o ~/.config/htop/htoprc
```

### ps: Снимок состояния процессов

```sh 
ps aux --sort=%mem
```
- a: все связанное с этим терминалом и терминалами других пользователи
- u: с указанием пользователя который запустил процесс
- x: включая без терминала(отсоединенные от терминала)
- f: древовидное отображение
- t: привязка к терминалу

Вывод: STAT/S - статус процесса; TTY - указание териминала, с которго запущен процесс; STIME/START - время старта процесса, TIME - сколько времени центрального процессора занял процесс. Если есть столбик Ssl значит процесс/программа многопоточная.

| **free**   | 843M     | Полностью свободная память (не используется ни для чего).                   |

### Детальный разбор /proc/meminfo

Файл `/proc/meminfo` предоставляет исчерпывающую статистику об использовании оперативной и swap-памяти. Рассмотрим ключевые параметры:

**Общая память:**
-   `MemTotal`: Общий объем физической RAM.
-   `MemFree`: Количество полностью свободной, неиспользуемой памяти. Это "сырой" показатель, который часто бывает низким, так как Linux стремится использовать свободную память для кэширования.
-   `MemAvailable`: **Наиболее важный показатель для оценки свободной памяти.** Это оценка того, сколько памяти доступно для запуска новых приложений без необходимости выгрузки данных в swap. Включает `MemFree` и часть кэша, которую можно безболезненно освободить.

**Кэш и буферы:**
-   `Buffers`: Память, используемая для временного хранения "сырых" дисковых блоков. Это кэш метаданных файловой системы.
-   `Cached`: Память, используемая для кэширования данных, прочитанных с диска (page cache). При повторном чтении файла данные будут взяты отсюда, а не с медленного диска.
-   `SwapCached`: Память, которая была выгружена в swap, а затем снова загружена в RAM, но все еще остается в swap-файле. Если понадобится, ее можно будет быстро выгрузить обратно, не записывая на диск заново.

**Активная и неактивная память:**
-   `Active`: Память, которая активно используется в данный момент.
-   `Inactive`: Память, которая использовалась, но сейчас неактивна. Является основным кандидатом на вытеснение (reclaiming) при нехватке памяти.
-   `Active(anon)` / `Inactive(anon)`: Анонимная память (не связанная с файлами), которая активно/неактивно используется. Это, как правило, память процессов (стек, куча).
-   `Active(file)` / `Inactive(file)`: Память, используемая для кэширования файлов, которая активно/неактивно используется.
-   `Unevictable`: Страницы памяти, которые нельзя выгрузить в swap (например, заблокированные с помощью `mlock()`).
-   `Mlocked`: Память, заблокированная процессом с помощью системного вызова `mlock()`. Гарантированно не будет выгружена в swap.

**Swap-пространство:**
-   `SwapTotal`: Общий размер раздела или файла подкачки.
-   `SwapFree`: Количество свободного места в swap.

**Страницы памяти:**
-   `Dirty`: Память, которая была изменена, но еще не записана на диск. Если система внезапно выключится, эти данные будут потеряны.
-   `Writeback`: Память, которая в данный момент записывается на диск.
-   `AnonPages`: Анонимные (нефайловые) страницы памяти, используемые процессами.
-   `Mapped`: Память, которая отображена в адресное пространство процессов (например, файлы или библиотеки).
-   `Shmem`: Объем разделяемой памяти (включая `tmpfs`).

**Память ядра:**
-   `Slab`: Память, используемая ядром для кэширования собственных структур данных (inodes, dentries и т.д.).
-   `SReclaimable`: Часть `Slab`, которую можно освободить при нехватке памяти.
-   `SUnreclaim`: Часть `Slab`, которую освободить нельзя.
-   `KernelStack`: Память, выделенная для стеков потоков ядра.
-   `PageTables`: Память, занимаемая таблицами страниц, которые используются для трансляции виртуальных адресов в физические.

**Управление памятью:**
-   `CommitLimit`: Общий объем виртуальной памяти, который система может выделить. Рассчитывается как `SwapTotal + (MemTotal * vm.overcommit_ratio / 100)`.
-   `Committed_AS`: Объем виртуальной памяти, который уже был выделен (запрошен) процессами. Если это значение приближается к `CommitLimit`, система близка к нехватке памяти.

**Огромные страницы (Huge Pages):**
-   `HugePages_Total` / `HugePages_Free` / `Hugepagesize`: Информация о количестве и размере "огромных страниц". Они используются для уменьшения накладных расходов на управление памятью для приложений, работающих с большими объемами данных (например, базы данных).

# **Физическая и виртуальная память**

В Linux, как и в большинстве современных ОС, процессы не могут обращаться к физической оперативной памяти (RAM) напрямую. Вместо этого система предоставляет каждому процессу **виртуальную память** — абстракцию, которая решает несколько ключевых задач:

1.  **Изоляция:** Виртуальная память, выделенная одному процессу, полностью изолирована и недоступна для других. Это фундаментальный механизм безопасности, который не позволяет одному приложению "покуситься" на память другого.
2.  **Сопоставление с реальной памятью:** Когда процесс хочет записать или прочитать данные, происходит сопоставление (mapping) виртуальных адресов с физическими. Этим управляет ядро ОС в **пространстве ядра (kernelspace)**.

| Характеристика | Физическая память (RAM) | Виртуальная память |
| :--- | :--- | :--- |
| **Что это?** | Реальные аппаратные чипы на материнской плате. | Абстракция, создаваемая операционной системой. |
| **Скорость** | Очень высокая. | Значительно медленнее, особенно при доступе к данным на диске. |
| **Размер** | Ограничен объемом установленных модулей ОЗУ. | Ограничен размером жесткого диска и архитектурой процессора. |
| **Доступ** | Процессор может выполнять код только из физической памяти. | Процессы работают с виртуальными адресами, которые ОС и аппаратура "переводят" в физические. |

**Как это работает: Механизм страниц**

И физическая, и виртуальная память делятся на небольшие блоки фиксированного размера, называемые **страницами** (обычно 4 КБ).

1.  **Таблицы страниц:** Для каждого процесса ядро Linux ведет специальную карту — **таблицу страниц**. В этой таблице для каждой виртуальной страницы процесса записано, где она находится на самом деле:
    *   В какой-то физической странице в ОЗУ.
    *   На жестком диске в специальном разделе или файле (swap).
    *   Нигде (если память была запрошена, но еще не использовалась).

2.  **MMU (Memory Management Unit):** Это специальный аппаратный блок в процессоре. Когда программа обращается к адресу в своей виртуальной памяти, MMU на лету заглядывает в таблицу страниц и мгновенно преобразует виртуальный адрес в физический.

**Преимущества и принципы работы виртуальной памяти:**
*   **Изоляция процессов:** Каждый процесс работает в своем собственном "пузыре" виртуальной памяти и не может испортить память другого процесса. Виртуальная память, выделенная одному процессу, полностью изолирована и недоступна для других.
*   **Использование памяти, превышающей ОЗУ (Overcommit):** Программы могут запрашивать больше памяти, чем физически установлено. Неактивные страницы памяти выгружаются в **пространство подкачки (swap)** на диске. Linux часто использует механизм **"чрезмерного выделения" (overcommit)**, когда система *обещает* процессу больше виртуальной памяти, чем есть в RAM. Например, процессу дадут запрошенные 6 ГБ виртуальной памяти при наличии всего 4 ГБ физической. Процесс будет работать, пока его реальное потребление не превысит доступный объем в 4 ГБ. Как только это произойдет, и если swap будет исчерпан, возникнет ошибка выделения, которая может спровоцировать **OOM Killer**.
*   **Эффективное использование ОЗУ:** Общие библиотеки загружаются в физическую память только один раз, а не для каждого процесса.

### **Vmstat: мониторинг активности swap**

Утилита `vmstat` предоставляет информацию о процессах, памяти, подкачке, вводе-выводе, системных прерываниях и активности процессора. В контексте swap особенно важны два поля в её выводе:

-   **si (swap-in):** Объем памяти, загруженный из swap-раздела в RAM (в килобайтах в секунду). Постоянно высокое значение `si` свидетельствует о том, что системе не хватает оперативной памяти, и она вынуждена постоянно считывать данные с медленного диска.
-   **so (swap-out):** Объем памяти, выгруженный из RAM в swap-раздел (в килобайтах в секунду). Высокое значение `so` говорит о том, что система активно освобождает RAM, перемещая неактивные страницы в swap.

### Swap 

**Настройка `swappiness`**

Ключевой параметр, который управляет поведением swap — это `vm.swappiness`. Он задает ядру, насколько агрессивно нужно использовать swap (значение от 0 до 100).

-   `vm.swappiness` = **100**: Ядро будет очень активно выгружать данные в swap.
-   `vm.swappiness` = **10** (частая рекомендация): Ядро будет неохотно использовать swap, предпочитая сначала очищать файловый кэш.
-   `vm.swappiness` = **1** или **0**: Ядро будет избегать swap любой ценой и прибегнет к нему только чтобы предотвратить OOM-ошибку. Этот вариант рекомендуется для баз данных и других критичных к производительности сервисов.

# **Состояния процесса**

T(Stoped/Traced) - процесс остановлен обычно сигналом SIGSTOP, он не выполняется, но может быть возобновлён сигналом SIGCONT

W(Pading/Swapping) - в свопе(не имеет резидентных страниц)

<(High priority) - в приоритетном режиме

N(low priority) - в режиме низкого приоритета

L(Locked in memory) - real-time процесс, имеются страницы, заблокированные в памяти 

s(Session leader) - лидер сессии

R(Running) - выполнение

S(Sleeping) - прерываемый сон, процесс ожидает определенного события или ресурса, процесс реагирует на сигналы 

D(Disk sleep)(Uninterruptible sleep) - непрерывный сон, процесс ожидает определенного события, и не получает ошибок, процесс не реагирует ни на какие сигналы(обычно это происходит при ожидании операций ввода-вывода (записи на диск) на уровне ядра)

Z(Zombie) - зомби. Кратковременно в это состояние переходит **каждый** процесс после завершения своего выполнения. Процесс становится "зомби", когда он завершил работу, но его родительский процесс еще не "забрал" информацию о его завершении с помощью системного вызова `wait()` или `waitpid()`. В состоянии зомби от процесса остается только запись в таблице процессов (`task_struct`), которая содержит PID, код завершения и статистику об использованных ресурсах. Эта информация нужна родителю, чтобы узнать, как завершился дочерний процесс. Пока родитель не вызовет `wait()`, дочерний процесс будет существовать как зомби, занимая место в таблице процессов. Если родительский процесс "забывает" о своих дочерних процессах и не вызывает `wait()`, это может привести к накоплению зомби-процессов. В конечном итоге это может исчерпать доступные PID, и система не сможет создавать новые процессы. "Убить" зомби-процесс сигналом `SIGKILL` невозможно, так как он уже не является исполняемым кодом. Единственный способ его убрать — это дождаться, пока родительский процесс вызовет `wait()`, либо завершить сам родительский процесс (тогда "осиротевшего" зомби усыновит и очистит процесс `init`/`systemd`).

I(Idle) - процесс не активен и находится в режиме ожидания. Это может касаться как системных процессов, так и пользовательских, которые временно не выполняют никаких операций и ждут определенного события, чтобы продолжить работу. Статус появился в некоторых версиях ядра Linux и относится к процессам, которые не требуют активных ресурсов. Например, это может быть фоновая задача, ожидающая запуска по расписанию.

**Процесс-сирота (Orphan Process)**

Процесс-сирота — это дочерний процесс, который продолжает выполняться после того, как его родительский процесс завершился. 

Когда родительский процесс умирает, его дочерние процессы-сироты немедленно "усыновляются" `systemd`, который имеет PID 1. Этот процесс `systemd` становится новым родителем для осиротевших процессов и ожидает их завершения(завершает их), чтобы корректно освободить их ресурсы.

# **Приоритет процесса**

Приоритет процесса определяет, какую долю процессорного времени он получит по отношению к другим процессам, особенно когда система загружена.

### PR и NI: в чем разница?

В утилитах `top` и `htop` вы видите два значения: `PR` (Priority) и `NI` (Nice).
-   **`NI` (Nice value):** Это значение, которое пользователь может настраивать. Диапазон: от **-20** (самый высокий приоритет) до **+19** (самый низкий приоритет). По умолчанию большинство пользовательских процессов стартуют с `NI = 0`.
-   **`PR` (Priority):** Это реальный приоритет, который видит ядро. Для обычных процессов он вычисляется по формуле `PR = 20 + NI`. Вот почему процесс с `NI = 0` имеет `PR = 20`.

Чем **больше** значение `nice`, тем **меньше** у процесса фактический приоритет.

### Команды для управления приоритетом

-   **`nice`**: Запускает новую команду с указанным приоритетом.
    ```bash
    # Запустить команду с самым низким приоритетом
    nice -n 19 <команда>
    ```
-   **`renice`**: Изменяет приоритет уже запущенного процесса.
    ```bash
    # Понизить приоритет процесса с PID 1234
    renice 10 -p 1234
    ```
Уменьшать значение `NI` (повышать приоритет) может только `root`. Обычный пользователь может только увеличивать `NI` (понижать приоритет) для своих процессов.

# **Сигналы**

 Это программные прерывания, которые отправляются процессам для уведомления об определенных событиях. Они используются для управления поведением процессов (например, завершения, приостановки или перезапуска). 

Примеры распространенных сигналов(kill + сигнал + PID/PID-ы, или pkill имя_сервиса):
-SIGTERM (15): Стандартный и "вежливый" сигнал для завершения процесса (используется по умолчанию командой `kill`). Процесс может перехватить этот сигнал, чтобы выполнить очистку: сохранить данные, закрыть файлы и соединения. Программа может проигнорировать этот сигнал, если в ней прописана соответствующая логика.
-SIGKILL (9): "Жесткий" сигнал для немедленного и принудительного завершения процесса. Этот сигнал не может быть перехвачен или проигнорирован программой. Ядро операционной системы завершает процесс напрямую, не давая ему шанса на "уборку".
-SIGSTOP (17/19/23): Приостановка процесса.
-SIGCONT (18): Возобновление остановленного процесса.
-SIGHUP (1): Уведомление о потере терминала (часто используется для перечитывания конфигурации, например, используеться при выполнении nginx -s reload или  sudo systemctl reload nginx).
-SIGINT(2): Ctrl+C(похож на SIGTERM), сигнал прерывания с терминала.
-SIGQUIT(3): сигнал, аналогичный SIGINT, но при этом вызывается символом QUIT, и при завершении процесса производит дамп ядра.
-SIGCHLD – сигнал останова или завершения дочернего процесса (child process terminated or stopped). Если дочерний процесс останавливается или завершается, то ядро сообщит об этом родительскому процессу, послав ему данный сигнал. 

Завершить/остановить родительский и все его дочерние процессы:
```sh 
killall <PID> <имя>
```

Завершить все процессы определенного пользователя 
```sh 
ktllall -u <name_user>
```

# **Межпроцессное взаимодействие (IPC)**

Межпроцессное взаимодействие (IPC) — это набор механизмов, которые позволяют процессам обмениваться данными и синхронизировать свои действия.

**Основные механизмы IPC в Linux:**

*   **Каналы (Pipes):**
    *   **Неименованные каналы:** Однонаправленный канал данных для связи между родительским и дочерним процессами.
    *   **Именованные каналы (FIFO):** Файлы в файловой системе, которые ведут себя как каналы и могут использоваться для связи между несвязанными процессами.
*   **Очереди сообщений (Message Queues):** Позволяют процессам обмениваться сообщениями в асинхронном режиме.
*   **Разделяемая память (Shared Memory):** Самый быстрый способ IPC, позволяющий нескольким процессам совместно использовать одну и ту же область памяти. Требует синхронизации (например, с помощью семафоров).
*   **Семафоры (Semaphores):** Используются для синхронизации доступа к общим ресурсам.
*   **Сокеты (Sockets):** Гибкий механизм для двунаправленной связи как между процессами на одной машине (Unix Domain Sockets), так и по сети (Network Sockets).

    -   **Что такое сокет?** В контексте Linux, сокет — это специальный файл, который служит конечной точкой для обмена данными между процессами. Он работает как телефонная розетка: один процесс "подключается" к сокету, чтобы слушать входящие данные, а другой — чтобы их отправлять.

    -   **Пример: Docker Socket (`/var/run/docker.sock`)**
        -   **Docker Daemon (`dockerd`)** — это системный демон, который управляет контейнерами. Он создает Unix-сокет `/var/run/docker.sock` и "слушает" его.
        -   **Docker CLI (клиент `docker`)** — это утилита командной строки, которую вы используете. Когда вы выполняете команду `docker ps`, клиент подключается к файлу `/var/run/docker.sock` и отправляет через него API-запрос демону.
        -   Демон получает запрос, обрабатывает его и отправляет ответ (список контейнеров) обратно клиенту через тот же сокет.
        -   Таким образом, сокет позволяет двум разным процессам (клиенту и демону) безопасно и эффективно общаться в пределах одной системы.
*   **Сигналы (Signals):** Простейшая форма IPC для уведомления процесса о событии, не предназначенная для передачи данных.

### D-Bus

**D-Bus** — это современная и наиболее мощная система межпроцессного взаимодействия (IPC) в Linux. Она предоставляет высокоуровневую шину сообщений, которая позволяет приложениям и системным службам общаться друг с другом.

**Ключевые особенности:**
-   **Две шины:**
    -   **System Bus:** Глобальная шина для общесистемных служб (например, `systemd`, `NetworkManager`).
    -   **Session Bus:** Отдельная шина для приложений, запущенных в рамках сессии одного пользователя (например, для взаимодействия компонентов рабочего стола).
-   **Механизмы:** Поддерживает вызовы удалённых процедур (RPC), отправку сигналов (broadcasts) и получение свойств объектов.

**Инструменты для работы с D-Bus:**
-   `busctl`: Современная утилита для интроспекции и мониторинга D-Bus.
    ```bash
    # Показать список всех сервисов на системной шине
    busctl list
    ```
-   `dbus-send`: Команда для отправки сообщений в D-Bus.

# **Процессор**

- Вывод top/htop: 

us - сколько потратили процессорного времени в процентах на операции в пользовательском режиме/пространстве

sy - время потраченное на выполнение операций в пространстве ядра в процентах

ni - процент процессорного времени потраченного на выполнение операций с пониженным приоритетом через команду nice

wa - процент времени когда система ожидает завершения операций ввода/вывода, увеличение - проблемы с устройствами вводв/вывода (диски или сеть) 

hi - сколько процессорного времени было потрачено на аппаратные прерывания (железные поломки) 

si - время, потраченное на обработку программных прерываний (softirqs). Часто связано с интенсивным сетевым трафиком или операциями ввода-вывода.

st - сколько процессорного времени было украденно (актуально при использовании виртуалок)

**Показатели памяти:**

- **VIRT (Virtual Memory):** Виртуальная память. Это **весь** объем памяти, который процесс теоретически может использовать. Он включает в себя код программы, данные, общие библиотеки, а также страницы, выгруженные в swap, и память, которая была зарезервирована, но еще не используется. **Большое значение VIRT — это не всегда проблема.**

- **RES (Resident Memory):** Резидентная память. Это та часть виртуальной памяти процесса, которая в данный момент **физически находится в оперативной памяти (RAM)**. Это наиболее важный показатель для оценки реального потребления ОЗУ процессом.

- **SHR (Shared Memory):** Разделяемая память. Это часть резидентной памяти (RES), которая может быть разделена с другими процессами. В основном это общие библиотеки (например, `libc`), которые загружаются в память один раз и используются многими программами.

- **Уникальная память (USS - Unique Set Size):** Это наиболее точный показатель "личного" потребления памяти процессом. USS представляет собой объем памяти, который принадлежит **исключительно этому процессу** и не разделяется с другими. Именно этот объем памяти будет полностью освобожден, если процесс завершится.

Приблизительно оценить уникальную память можно по формуле: **`Уникальная память ≈ RES - SHR`**.

# **Load Average (LA)**

**Load Average (LA)** — это показатель средней длины очереди процессов, ожидающих получения ресурсов системы.

Ключевое отличие в Linux от классических Unix-систем заключается в том, какие процессы учитываются при подсчете:
-   **Классический Unix:** Учитывались только процессы в состоянии **R (Running/Runnable)** — то есть те, что активно используют или ожидают своей очереди на CPU.
-   **Linux:** Учитываются процессы в двух состояниях:
    1.  **R (Running/Runnable):** Активная работа с CPU.
    2.  **D (Uninterruptible Sleep):** Процессы, ожидающие завершения операций ввода-вывода (I/O), например, чтение с диска или ответ от сети.

LA отображается в виде трёх чисел, которые показывают среднюю нагрузку за последнюю 1, 5 и 15 минут. Например: `load average: 0.51, 0.72, 0.86`.

Значение Load Average следует соотносить с количеством ядер процессора.

*   **LA < количества ядер**: Система не перегружена.
*   **LA ≈ количеству ядер**: Система полностью загружена, но справляется.
*   **LA > количества ядер**: Система перегружена, и процессы ожидают в очереди.

Например, на 4-ядерном процессоре LA равное 4.0 означает полную загрузку.

Таким образом, высокий LA может быть вызван не только интенсивной работой CPU, но и проблемами с дисковой подсистемой или сетью.

Если на многоядерной системе `LA` равен 1, а процесс тупит, это может указывать на то, что **этот процесс полностью утилизирует одно ядро**, Такое часто случается, если запущено **однопоточное приложение**, которое не способно распределить свою нагрузку на несколько ядер. 

### Диагностика проблем I/O: iotop и iostat

Если вы наблюдаете высокий Load Average при низкой утилизации CPU, это почти всегда указывает на проблемы с операциями ввода-вывода (I/O). Процессы находятся в состоянии `D` (Uninterruptible Sleep), ожидая ответа от диска или сети. Для диагностики используются утилиты `iotop` и `iostat`.

#### iotop: мониторинг дискового ввода-вывода по процессам

**Описание колонок вывода**
*   **PID (TID)**: Идентификатор процесса (или потока).
*   **USER**: Пользователь, от имени которого запущен процесс.
*   **DISK READ / WRITE**: Скорость чтения с диска и записи на диск для конкретного процесса.
*   **SWAPIN**: Процент времени, который процесс тратит на перемещение данных в раздел подкачки (swap).
*   **IO>**: Процент времени, который процесс проводит в ожидании завершения операций ввода-вывода. Высокое значение (>90%) для процесса при невысокой скорости записи/чтения — явный признак проблем с диском.
*   **COMMAND**: Имя процесса или команда, которой он был запущен.

**Полезные опции**
*   `-o` или `--only`: Показывать только те процессы, которые в данный момент активно выполняют операции I/O.
*   `-P` или `--processes`: Отображать только процессы, скрывая отдельные потоки.
*   `-u <имя_пользователя>`: Отслеживать активность только указанного пользователя.
*   `-p <PID>`: Мониторить только конкретный процесс по его ID.
*   `-k`: Отображать скорость в килобайтах в секунду.
*   `-b` или `--batch`: Включить неинтерактивный режим для записи в лог.
*   `-n <число>`: Завершить работу после указанного числа обновлений (используется вместе с `-b`).

**Интерактивное управление**
*   **Стрелки влево/вправо**: Изменить колонку для сортировки.
*   **r**: Инвертировать порядок сортировки.
*   **o**: Включить/выключить режим отображения только активных процессов (аналог ключа `-o`).
*   **q**: Выйти из программы.

#### iostat: Статистика ввода-вывода

Если `iotop` показывает общую картину, то `iostat` предоставляет более детальную, численную статистику по дискам.

**Пример команды:**
```bash
# Показывает расширенную статистику (-x) в мегабайтах (-m) с временными метками (-t) каждую секунду (1) для диска nvme1
iostat -x -m -t 1 /dev/nvme1
```

**Ключевые колонки в выводе:**
-   `r/s` и `w/s`: Количество операций чтения и записи в секунду.
-   `rMB/s` и `wMB/s`: Скорость чтения и записи в мегабайтах в секунду.
-   `await`: Среднее время ожидания (в миллисекундах) для выполнения операций ввода-вывода. Высокое значение — явный признак "тормозов" диска.
-   `%util`: Процент времени, в течение которого устройство было занято. Если это значение приближается к 100%, диск работает на пределе своей производительности (насыщение).

**Время доступа к блоку**

В контексте `iotop` и дисковых операций, "доступ к блоку" (block device access) является фундаментальной операцией. Когда процесс читает или пишет данные, он обращается к блочному устройству (например, `/dev/sda`). Время, необходимое для выполнения этой операции, критически важно.

- **Нормальная работа:** В здоровой системе время доступа к блокам минимально (доли секунды).
- **Деградация:** При проблемах с диском (физический износ, ошибки контроллера, перегрузка I/O) это время резко возрастает. Процесс, запросивший операцию, "зависает" в ожидании, увеличивая свой показатель `IO>` в `iotop` и внося вклад в Load Average.

# **OOM_killer**

Очки негодности - чем выше это значение, тем вероятнее, что процесс будет убит. 

``` sh
cat /proc/<PID>/oom_adj

cat /proc/<PID>/oom_score_adj

cat /proc/<PID>/oom_score
```

1. **oom_adj —** числовой модификатор
от -17
до 15. Является более старым подходом для определения приоритетов киллера.
2. **oom_score_adj
 —** новый файл для настройки приоритетов. Используется для настройки через systemd. Его изменение приводит к автоматическому перерасчету параметра **oom_adj**. 
3. **oom_score —** текущий OOM-счет для процесса. Его значение
варьируют от
0 до 1000.

Параметры выше при изменении одного меняются пропорционально.

Выше значение OOM_killer: много памяти,дочерние процессы и их use память, чем выше nice. 

Ниже значение OOM_killer: более ранее создание процесса, доступ к железу, запущен ли процесс от рута

Можно повысить или понизить репутацию для процесса: для выставления репутации -1000:

``` sh
 sudo echo -1000 > /proc/174244/oom_score_adj
```

Но правильнее задать очки в самом systemd, в юните для сервиса, этот параметр:

```
[Service]  
OOMScoreAdjust=-1000
```

# **Как посмотреть файлы, используемые процессом?**

lsof — это утилита, которая показывает список открытых файлов для каждого процесса в системе      

```
lsof -p <PID>
```

-u user: Показать файлы, открытые определённым пользователем.
-c nginx | grep config: Показать файлы, используемые nginx в качестве конфиг файла.
+D directory: Показать процессы, использующие файлы в указанной директории.

Пример использования lsof 

- Вы заметили, что процесс потребляет много ресурсов или "завис". Используйте `lsof` или `/proc/<PID>/fd/`, чтобы проверить, какие файлы он использует. Возможно, процесс застрял на чтении большого файла или заблокирован из-за отсутствия доступа к файлу.

- Если вы удалили файл, но место на диске не освободилось, это может быть связано с тем, что файл всё ещё открыт каким-то процессом. Команда `lsof | grep deleted` поможет найти такие процессы.

- Если вы подозреваете, что процесс был скомпрометирован, проверьте, какие файлы он открывает. Например, если процесс читает `/etc/passwd` или записывает в `/tmp`, это может быть признаком атаки.

- В контейнерах Docker или Kubernetes вы можете использовать `lsof` или `/proc` для анализа, какие файлы контейнер использует из хостовой системы (например, mounted volumes или configmaps).

- При миграции или обновлении программного обеспечения важно знать, какие файлы и библиотеки использует процесс, чтобы избежать поломок.

# **Exit code**

**Exit code**(экзит код) (код завершения) — это целочисленное значение, которое программа или команда возвращает после своего завершения.

```sh
echo $0
```

- Стандартные значения exit codes, когда все гуд: 0

- Ненулевые значения:

`1`: Общая ошибка.
`2`: Неправильное использование команды (например, неверные аргументы).
`126`: Команда не может быть выполнена (например, из-за отсутствия прав). `127`: Команда не найдена.
`128 + N`: Ошибки, связанные с сигналами (например, `130` — прерывание через `Ctrl+C`).

## Перезапуск процесса без остановки PID

Представь, у тебя работает демон, и ты хочешь обновить его бинарник *без остановки процесса* и *без потери PID*. 

### Заменить текущий процесс на новый

```sh
exec /path/to/new/binary --with --args
```

- Команда `exec` заменяет текущий процесс новым — без создания нового PID.
- Все открытые файловые дескрипторы и сокеты сохраняются.
- Работает, только если у тебя уже есть нужные права (например, через systemd или под `sudo`).

### Пример 

Ты перекомпилировал новый nginx в `/usr/local/bin/nginx-new`, и хочешь подменить старый:

```sh
pidof nginx  # допустим, PID = 1234
sudo nsenter -t 1234 -m -u -i -n -p -- bash
cd /usr/local/bin
exec ./nginx-new -c /etc/nginx/nginx.conf
```
Новый бинарь работает в том же PID, открытые сокеты и дескрипторы остались на месте.

**Разбор команды `nsenter`:**

Эта команда позволяет "войти" в окружение другого процесса, используя его пространства имён (namespaces).

- `sudo nsenter`: Выполняем команду с правами суперпользователя.
- `-t 1234`: Целевой процесс с PID `1234`.
- `-m`: Войти в пространство имён монтирования (mount namespace). Файловая система будет выглядеть так же, как для целевого процесса.
- `-u`: Войти в пространство имён UTS (имя хоста).
- `-i`: Войти в пространство имён IPC (межпроцессное взаимодействие).
- `-n`: Войти в пространство имён сети (network namespace). У вас будут те же сетевые интерфейсы.
- `-p`: Войти в пространство имён PID.
- `-- bash`: Запустить `bash` внутри этого окружения. Это даёт нам интерактивную оболочку с "видом на мир" как у процесса `1234`.

# **Пространства имен (Namespaces)**

Пространства имен — это одна из ключевых технологий контейнеризации в Linux, позволяющая изолировать ресурсы для группы процессов.

- **User Namespace**: Позволяет процессу иметь права суперпользователя (root) внутри своего пространства имен, оставаясь при этом обычным непривилегированным процессом для основной системы. Это значительно повышает безопасность, так как даже если процесс будет скомпрометирован внутри контейнера, он не получит root-доступ к хост-системе.

# **Userspace и Kernelspace**

Операционная система разделяет свою работу на два фундаментальных режима: **Userspace (пространство пользователя)** и **Kernelspace (пространство ядра)**. Это разделение необходимо для защиты ядра и обеспечения стабильности системы.

- **Userspace:** Место, где выполняются ваши приложения (браузер, текстовый редактор, игры). У этих программ ограниченные права, и они не могут напрямую обращаться к оборудованию.
- **Kernelspace:** Место, где работает ядро операционной системы. Код в пространстве ядра имеет полный, неограниченный доступ ко всему оборудованию и памяти компьютера.

**Основные отличия:**

| Характеристика | Userspace (Пространство пользователя) | Kernelspace (Пространство ядра) |
| :--- | :--- | :--- |
| **Что здесь работает?** | Прикладные программы, системные утилиты и библиотеки. | Ядро ОС, драйверы устройств, системные модули. |
| **Уровень привилегий** | Низкий (ограниченный). Процессы изолированы друг от друга. | Высокий (полный, привилегированный). Полный контроль над системой. |
| **Доступ к оборудованию** | Нет прямого доступа. Для работы с диском или сетью нужно просить ядро. | Прямой и неограниченный доступ ко всему оборудованию. |
| **Доступ к памяти** | Каждый процесс имеет свое изолированное виртуальное адресное пространство. | Весь код ядра работает в едином адресном пространстве. |
| **Стабильность и сбои** | Сбой в приложении обычно приводит к "падению" только этого приложения. | Ошибка в коде ядра (например, в драйвере) приводит к критическому сбою всей системы (Kernel Panic). |

# **Системные вызовы (System Calls)**

Системный вызов — это основной механизм, с помощью которого программа в пространстве пользователя запрашивает у ядра операционной системы выполнение какой-либо привилегированной операции.

**Зачем они нужны?**
*   **Безопасность и стабильность:** Системные вызовы — это контролируемый шлюз к ресурсам. Ядро проверяет каждый запрос, предотвращая прямой доступ программ к критически важным данным и оборудованию.
*   **Управление ресурсами:** Единственный способ для программ запросить доступ к файлам, сетевым соединениям, памяти и другим устройствам.
*   **Абстракция:** Программисту не нужно знать, как устроен конкретный жесткий диск или сетевая карта. Он использует стандартизированные вызовы (`write()`, `send()`), а ядро само выполняет команду на конкретном оборудовании.

**Как они работают:**
1.  Программа в Userspace вызывает библиотечную функцию (например, `printf()`).
2.  Библиотечная функция подготавливает системный вызов, помещая его номер и аргументы в регистры процессора.
3.  Выполняется инструкция `syscall`, которая переключает процессор из режима пользователя в режим ядра.
4.  Ядро выполняет запрошенную операцию.
5.  Ядро возвращает результат и переключает процессор обратно в режим пользователя.

**Основные категории системных вызовов:**
*   **Управление процессами:** `fork()`, `execve()`, `exit()`, `wait()`
*   **Работа с файлами:** `open()`, `read()`, `write()`, `close()`
*   **Управление файловой системой:** `mkdir()`, `rmdir()`, `stat()`
*   **Сетевое взаимодействие:** `socket()`, `bind()`, `listen()`, `accept()`
*   **Управление памятью:** `brk()`, `mmap()`

# **Изоляция процессов: сокрытие процессов от других пользователей**

По умолчанию в большинстве дистрибутивов Linux любой пользователь может видеть все процессы, запущенные в системе, с помощью команд `ps`, `top` или `htop`. Хотя детальная информация (например, переменные окружения) доступна только владельцу процесса или `root`, сам факт существования процессов, их PID и имена видны всем. Это может представлять угрозу безопасности, раскрывая информацию о запущенных сервисах и их активности.

Чтобы усилить безопасность, можно настроить ядро так, чтобы пользователи могли видеть **только свои собственные процессы**.

Как это работает: опция `hidepid`

Это достигается путем монтирования виртуальной файловой системы `/proc` со специальной опцией `hidepid`.

**Возможные значения `hidepid`:**

-   `hidepid=0` (по умолчанию): Все пользователи могут видеть все процессы.
-   `hidepid=1`: Пользователи видят только свои процессы. Содержимое директорий `/proc/<PID>` скрыто от других пользователей, но сами директории (и, следовательно, номера PID) все еще видны.
-   `hidepid=2` (рекомендуется): Пользователи видят только свои процессы. Директории `/proc/<PID>`, принадлежащие другим пользователям, становятся для них невидимыми. Это наиболее строгий и безопасный вариант.

Дополнительно можно использовать опцию `gid`, чтобы создать группу-исключение (например, `auditors`), члены которой смогут видеть все процессы, как и `root`.

Как применить настройку

Чтобы изменения сохранялись после перезагрузки, необходимо отредактировать файл `/etc/fstab`.

1.  **Откройте `/etc/fstab` с правами `root`:**
    ```sh
    sudo nano /etc/fstab
    ```

2.  **Найдите строку, отвечающую за монтирование `/proc`** (или добавьте новую, если ее нет).

3.  **Добавьте опции `hidepid=2` и `gid=...`** в четвертое поле (опции монтирования).

    **Пример строки в `/etc/fstab`:**
    ```
    # <file system> <mount point>   <type>  <options>         <dump>  <pass>
    proc            /proc           proc    defaults,hidepid=2,gid=procview 0       0
    ```
    -   `hidepid=2`: Включает строгую изоляцию.
    -   `gid=procview`: Задает имя группы (или ее GID), которая будет исключена из этого правила. Не забудьте создать эту группу (`sudo groupadd procview`) и добавить в нее доверенных пользователей (`sudo usermod -aG procview <username>`).

4.  **Перемонтируйте `/proc`, чтобы применить изменения немедленно:**
    ```sh
    sudo mount -o remount /proc
    ```

После этого обычные пользователи, залогинившись в систему, при выполнении `ps aux` или `htop` увидят только свои собственные процессы и системные процессы, запущенные от их имени.

# **Управление лимитами ресурсов (`ulimit`)**

В Linux каждый пользователь и процесс имеет ограничения (лимиты) на потребление системных ресурсов, таких как количество открытых файлов, размер создаваемых файлов или объем используемой памяти. Утилита `ulimit` и конфигурационные файлы позволяют управлять этими лимитами.

### Просмотр и установка лимитов в командной строке

Команда `ulimit` позволяет просматривать и устанавливать лимиты для **текущей сессии оболочки**.

-   **Посмотреть все текущие лимиты:**
    ```bash
    ulimit -a
    ```
-   **Посмотреть лимит на количество открытых файлов (`nofile`):**
    ```bash
    ulimit -n
    ```
-   **Посмотреть лимит на размер core-файла (`coredump`):**
    ```bash
    ulimit -c
    ```
-   **Установить новый "мягкий" лимит (например, для открытых файлов):**
    ```bash
    # Установить лимит в 4096 файлов
    ulimit -n 4096
    ```

### Постоянная настройка лимитов

Изменения, сделанные с помощью `ulimit`, действуют только в текущей сессии. Для постоянной настройки используются:

1.  **/etc/security/limits.conf** (классический способ):
    Этот файл позволяет установить лимиты для пользователей или групп.
    ```
    # <domain>      <type>  <item>         <value>
    # -------------------------------------------------
    # Запретить пользователю 'student' создавать большие файлы
    student         hard    fsize          102400

    # Увеличить лимит открытых файлов для всех пользователей
    *               soft    nofile         65536
    *               hard    nofile         131072
    ```
    -   `*`: Применить правило для всех пользователей.
    -   `soft`: "Мягкий" лимит, который пользователь может изменять в пределах "жесткого" лимита.
    -   `hard`: "Жесткий" лимит, который может быть изменен только пользователем `root`.
    -   `nofile`: Указывает, что мы настраиваем максимальное количество открытых файлов.

2.  **Юниты `systemd`** (современный способ):
    Для сервисов, управляемых `systemd`, лимиты устанавливаются прямо в юнит-файле. Это более надежный и предпочтительный метод для служб.
    ```ini
    # /etc/systemd/system/my-app.service
    [Service]
    # Лимит на количество открытых файлов
    LimitNOFILE=65536

    # Лимит на количество процессов
    LimitNPROC=1024

    # Лимит на размер core-файла
    LimitCORE=infinity
    ```

## strace: Трассировка системных вызовов и сигналов

`strace` — это мощная утилита для отладки, которая перехватывает и записывает системные вызовы, которые процесс выполняет, и сигналы, которые он получает. Это незаменимый инструмент для диагностики проблем, когда поведение программы непонятно.

### Основные примеры использования

-   **Присоединиться к работающему процессу по PID:**
    ```bash
    sudo strace -p <PID>
    ```

-   **Запустить команду и отследить её:**
    ```bash
    strace -o trace.log <команда>
    ```

-   **Расширенный пример для отладки:**
    ```bash
    # -f: отслеживать дочерние процессы (forks)
    # -tt: добавить микросекунды к временным меткам
    # -T: показать время, затраченное на каждый системный вызов
    # -s 200: увеличить лимит на длину выводимой строки до 200 символов
    # -e trace=...: отслеживать только определённые вызовы (например, сетевые и связанные с открытием файлов)
    sudo strace -f -ttT -s 200 -e trace=network,open -o trace.log <команда>
    ```

### Проблемы с доступом (ptrace)

Если `strace` не работает и выдает ошибку `Operation not permitted`, возможно, система безопасности ограничивает использование системного вызова `ptrace`. Это можно проверить в файле `/proc/sys/kernel/yama/ptrace_scope`. Подробнее об этом можно прочитать в `man 2 ptrace`.

## Анализ сбоев: Coredump

**Coredump (дамп памяти)** — это файл, содержащий снимок рабочего адресного пространства процесса в момент его аварийного завершения. Он используется для посмертной отладки (post-mortem debugging), чтобы понять причину сбоя.

### Настройка и управление

-   **`ulimit`**: Для создания coredump необходимо, чтобы лимит на его размер был установлен в ненулевое значение.
    ```bash
    # Разрешить создание coredump неограниченного размера
    ulimit -c unlimited
    ```

-   **`/proc/sys/kernel/core_pattern`**: Этот файл определяет, куда и в каком формате будут сохраняться дампы. Его можно настроить для добавления полезной информации, такой как PID, имя исполняемого файла и время сбоя.

### Управление через `systemd-coredump`

В современных системах с `systemd` процесс создания и управления дампами централизован.

-   **Конфигурация:** `/etc/systemd/coredump.conf`.
-   **`coredumpctl`**: Утилита для работы с сохранёнными дампами.
    ```bash
    # Показать список всех сохранённых дампов
    coredumpctl list

    # Показать подробную информацию о последнем сбое
    coredumpctl info

    # Извлечь дамп в файл для анализа в gdb
    coredumpctl dump <PID> -o my_coredump
    ```
