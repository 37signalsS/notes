# Разница: /etc/sysctl.conf vs /etc/default/grub

**Ключевое отличие**:
*   **/etc/sysctl.conf**: Настраивает **уже работающее ядро** Linux (на лету).
*   **/etc/default/grub**: Настраивает **загрузчик GRUB**, который передаёт параметры ядру **в момент его запуска**.

# Запрет входа пользователей с пустым паролем

Этим способом можно только физически зайти на машину (или терминалом гипервизора), через ssh не получиться.

Для этого необходимо отредактировать файл `/etc/pam.d/common-auth` и в нем удалить слово `nullok` из первой строчки.

```
auth [success=1 default=ignore] pam_unix.so
```

# Отключить вход root под ssh

Для отключения входа пользователя `root` через ssh, необходимо отредактировать файл `/etc/ssh/sshd_config` и изменить значение параметра `PermitRootLogin`.

- `PermitRootLogin prohibit-password`: Эта опция запрещает вход по паролю под пользователем `root`, но разрешает ему вход по ssh-ключу, если он добавлен в `~/.ssh/authorized_keys`.
- `PermitRootLogin no`: Эта опция полностью запрещает вход под пользователем `root` как по паролю, так и по ssh-ключу.

# Доступ к su только для группы wheel

Для того, чтобы только пользователи, состоящие в группе `wheel`, могли использовать команду `su`, необходимо раскомментировать следующую строку в файле `/etc/pam.d/su`:

```
auth required pam_wheel.so
```

# Настройка прав sudoers для пользователя

Для предоставления прав `sudo` пользователю, а не группе, необходимо отредактировать файл `/etc/sudoers` (предпочтительно с помощью команды `visudo`).

Пример предоставления прав пользователю `username`:

```
username ALL=(ALL) ALL
```

Чтобы разрешить пользователю выполнять определенные команды без ввода пароля, используется опция `NOPASSWD:`.

Пример для пользователя `username`, которому разрешено выполнять команды `/usr/bin/cat` и `/usr/bin/anothercommand` без пароля:

```
username ALL=(ALL) NOPASSWD: /usr/bin/cat, /usr/bin/anothercommand
```

# Настройка прав на файлы учетных записей

Необходимо установить правильные права доступа на системные файлы, содержащие информацию о пользователях и группах.

- **`/etc/passwd` и `/etc/group`**: Эти файлы должны быть доступны для чтения всем пользователям, но запись должна быть разрешена только для `root`.

  ```bash
  chmod 644 /etc/passwd
  chmod 644 /etc/group
  ```

- **`/etc/shadow`**: Этот файл содержит хэши паролей и должен быть доступен для чтения и записи только `root`, а также для чтения группе `shadow` (или `root`). Остальным пользователям доступ должен быть закрыт.

  ```bash
  chmod 640 /etc/shadow
  ```

# Контроль целостности и прав доступа к системным файлам

Для предотвращения несанкционированного изменения системных файлов и сервисов, необходимо строго контролировать права доступа.

### Ограничение прав для новых файлов (umask)

Чтобы новые файлы по умолчанию создавались с ограниченными правами, используется команда `umask`. Установка `umask 077` гарантирует, что только владелец файла будет иметь к нему доступ (права `rw-` для файлов, `rwx` для каталогов), а группа и остальные пользователи не получат никаких прав.

```bash
# Установить umask для текущей сессии
umask 077
```
Для постоянной установки `umask` для всех пользователей, это значение можно прописать в системных профилях, например, в `/etc/profile` или `/etc/bashrc`.

### Права на системные файлы и каталоги

Системные файлы, особенно те, что отвечают за запуск сервисов, должны иметь права, предотвращающие их изменение обычными пользователями. Исполняемые файлы не должны иметь права на запись, а конфигурационные файлы не должны иметь права на выполнение.

- **Конфигурационные файлы**: Должны быть защищены от записи кем-либо, кроме `root`. Право на выполнение должно быть снято.
  ```bash
  # Пример для crontab
  chmod 644 /etc/crontab
  # Владелец: root, Группа: root
  # Права: rw-r--r--
  ```

- **Исполняемые файлы и библиотеки**: Должны быть защищены от записи. Право на выполнение должно быть только у владельца (и, если необходимо, у группы), но не у всех подряд.
  ```bash
  # Пример для исполняемого файла сервиса
  chmod 750 /usr/sbin/some-service
  # Владелец: root, Группа: root
  # Права: rwxr-x---
  ```

# Аудит и устранение небезопасных прав

Особую опасность представляют файлы, которые могут быть изменены любым пользователем и при этом выполнены с повышенными привилегиями (`sudo`). Необходимо регулярно проводить аудит системных каталогов на наличие таких файлов.

### Поиск файлов с небезопасными правами

Можно использовать команду `find` для поиска файлов в системных каталогах (таких как `/etc`, `/usr/sbin`, `/bin` и т.д.), которые имеют права на запись для группы или для всех пользователей.

```bash
# Поиск файлов, доступных для записи всем (world-writable)
find /etc /usr/sbin /usr/bin /sbin /bin -type f -perm -0002

# Поиск файлов, доступных для записи группе (group-writable)
find /etc /usr/sbin /usr/bin /sbin /bin -type f -perm -0020
```

### Устранение уязвимостей

При обнаружении файла с избыточными правами на запись, необходимо их удалить. Особенно опасно, если у такого файла одновременно есть право на выполнение.

```bash
# Пример: найден файл /usr/bin/some-script с правами 777 (rwxrwxrwx)

# Убираем права на запись и выполнение для группы и остальных
chmod go-wx /usr/bin/some-script

# В результате права станут 754 (rwxr-xr--) или 644 (rw-r--r--)
# в зависимости от исходных прав владельца.
# Для системных файлов рекомендуется устанавливать права явно, 
# например, 755 для исполняемых или 644 для конфигурационных.
```

**Важно:** Перед изменением прав системных файлов убедитесь, что это не нарушит работу легитимных сервисов, которым могут требоваться специфические права доступа.

# Защита компонентов времени выполнения

Ключевые компоненты системы, такие как стартовые скрипты, библиотеки и модули ядра, должны быть защищены от несанкционированного изменения. Владельцем этих файлов должен быть `root`.

### Стартовые скрипты

- **Systemd units** (например, в `/etc/systemd/system`): Это конфигурационные файлы, они не должны быть исполняемыми. Рекомендуемые права: `644` (`rw-r--r--`).
  ```bash
  chmod 644 /etc/systemd/system/some.service
  ```
- **SysVinit скрипты** (в `/etc/init.d/`): Это исполняемые скрипты. Права на запись и выполнение для кого-либо, кроме владельца, должны быть ограничены. Рекомендуемые права: `750` (`rwxr-x---`).
  ```bash
  chmod 750 /etc/init.d/some-script
  ```

### Системные библиотеки

Библиотеки (в каталогах `/usr/lib`, `/lib64` и т.п.) не должны быть доступны для записи никому, кроме `root`. 

- **Файлы библиотек (`.so`)**: Рекомендуемые права: `644` (`rw-r--r--`).
- **Каталоги библиотек**: Рекомендуемые права: `755` (`rwxr-xr-x`).

```bash
chmod 644 /usr/lib/some-library.so
```

### Модули ядра

Модули ядра (в `/lib/modules/`) критически важны для безопасности системы. Они должны быть доступны для записи только `root`.

- **Файлы модулей (`.ko`)**: Рекомендуемые права: `644` (`rw-r--r--`).

```bash
find /lib/modules/$(uname -r) -type f -name '*.ko' -exec chmod 644 {} \;
```

# Аудит SUID и GUID битов

Файлы с установленными битами SUID (Set User ID) или GUID (Set Group ID) выполняются с правами владельца или группы файла, а не с правами пользователя, который их запускает. Это может быть крайне опасно, если владельцем является `root`, так как любая уязвимость в такой программе может привести к получению полных прав в системе.

### Поиск файлов с SUID/GUID

Необходимо регулярно сканировать систему на наличие таких файлов, чтобы убедиться, что они действительно необходимы.

```bash
# Поиск файлов с битом SUID
find / -type f -perm -4000

# Поиск файлов с битом GUID
find / -type f -perm -2000
```

### Удаление SUID/GUID битов

Если вы обнаружили файл с SUID/GUID битом, который не является абсолютно необходимым для работы системы (например, кастомный скрипт или программа), этот бит следует немедленно удалить.

```bash
# Удаление SUID бита
chmod u-s /path/to/file

# Удаление GUID бита
chmod g-s /path/to/file
```

**Важно:** Некоторые системные утилиты, такие как `passwd`, `su`, `mount`, легитимно используют SUID/GUID для своей работы. Не удаляйте биты у стандартных системных программ без полного понимания последствий. Цель аудита — найти и обезвредить *нелегитимные* или *избыточные* файлы с такими правами.

# Защита домашних каталогов пользователей

Домашние каталоги пользователей не должны быть доступны для чтения или изменения другим пользователям системы.

### Права на домашний каталог

Рекомендуется устанавливать права, запрещающие доступ всем, кроме самого владельца. Права `750` (`rwxr-x---`) или `700` (`rwx------`) являются хорошим выбором.

```bash
# Запретить доступ к каталогу /home/user для всех, кроме владельца
chmod 700 /home/user
```

### Права на каталог `.ssh`

Каталог `.ssh` и его содержимое требуют особо строгих прав. Демон `sshd` не позволит выполнить вход по ключу, если права на домашний каталог, каталог `.ssh` или файл `authorized_keys` являются слишком открытыми.

- **Каталог `~/.ssh`**: Должен иметь права `700` (`rwx------`).
- **Файл с публичными ключами `~/.ssh/authorized_keys`**: Должен иметь права `600` (`rw-------`).
- **Файлы с приватными ключами (например, `~/.ssh/id_rsa`)**: Должны иметь права `600` (`rw-------`).

```bash
# Установка правильных прав для каталога .ssh и его содержимого
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
chmod 600 ~/.ssh/id_rsa
```

# Включить рандомизацию адресного пространства (ASLR)

**Address Space Layout Randomization (ASLR)** — это мера безопасности, которая случайным образом изменяет расположение ключевых областей данных процесса в виртуальной памяти (стек, куча, библиотеки). Это значительно усложняет эксплуатацию уязвимостей, связанных с повреждением памяти (например, переполнение буфера), так как злоумышленнику становится трудно предсказать адреса для внедрения вредоносного кода.

### Управление ASLR в Linux

ASLR контролируется через параметр ядра `kernel.randomize_va_space`.

-   **Проверить текущее значение:**
    ```bash
    cat /proc/sys/kernel/randomize_va_space
    ```

-   **Возможные значения:**
    -   `0`: ASLR отключена.
    -   `1`: Частичная рандомизация (стек, куча, библиотеки).
    -   `2`: Полная рандомизация (дополнительно рандомизируется расположение кода программы). Это наиболее безопасный вариант.

### Включение полной рандомизации

Чтобы изменение сохранялось после перезагрузки, необходимо добавить параметр в файл `/etc/sysctl.conf`.

1.  **Добавьте следующую строку в `/etc/sysctl.conf`:**
    ```
    kernel.randomize_va_space = 2
    ```

2.  **Примените изменения немедленно:**
    ```bash
    sudo sysctl -p
    ```

# Ограничение использования ptrace

**ptrace** — это системный вызов, который позволяет одному процессу (трассировщику) наблюдать и контролировать выполнение другого процесса (трассируемого), а также изменять его память и регистры. Это мощный инструмент, используемый отладчиками (например, `gdb`, `strace`) и другими диагностическими утилитами. Однако он также может быть использован злоумышленниками для внедрения кода в другие процессы.

### Уровни ограничений `ptrace_scope`

В Linux для ограничения использования `ptrace` существует параметр ядра `kernel.yama.ptrace_scope`.

-   **Проверить текущее значение:**
    ```bash
    cat /proc/sys/kernel/yama/ptrace_scope
    ```

-   **Возможные значения:**
    -   `0` (классический ptrace): Любой процесс может трассировать любой другой процесс (при условии совпадения UID).
    -   `1` (ограниченный ptrace): Трассировать можно только дочерние процессы, запущенные самим трассировщиком.
    -   `2` (только для администратора): Только процессы с `CAP_SYS_PTRACE` (обычно `root`) могут использовать `ptrace`.
    -   `3` (полный запрет): `ptrace` полностью отключен. Никто, включая `root`, не может его использовать. Это может нарушить работу легитимных приложений, таких как отладчики.

### Установка максимального ограничения

Чтобы полностью запретить `ptrace`, необходимо добавить параметр в файл `/etc/sysctl.conf`.

1.  **Добавьте следующую строку в `/etc/sysctl.conf`:**
    ```
    kernel.yama.ptrace_scope = 3
    ```

2.  **Примените изменения немедленно:**
    ```bash
    sudo sysctl -p
    ```

# Защита от небезопасных ссылок (symlinks и hardlinks)

Временные файлы и каталоги, доступные для записи всем пользователям (например, `/tmp`), могут быть использованы для атак с использованием символических (symlinks) и жестких (hardlinks) ссылок. Ядро Linux предоставляет механизмы для защиты от таких атак.

### Защита символических ссылок (`protected_symlinks`)

Этот параметр запрещает ядру переходить по символическим ссылкам, если родительский каталог ссылки доступен для записи всем (`world-writable`) или является "липким" (`sticky`).

-   **Значение `1` (включено):** Символическая ссылка будет разрешена, только если выполняется одно из условий:
    -   Владелец процесса, переходящего по ссылке, совпадает с владельцем ссылки.
    -   Родительский каталог ссылки не является `world-writable`.

-   **Значение `0` (отключено):** Никаких проверок не выполняется.

### Защита жестких ссылок (`protected_hardlinks`)

Этот параметр запрещает создание жестких ссылок на файлы, к которым у пользователя нет доступа на чтение и запись. Это предотвращает ситуацию, когда пользователь создает жесткую ссылку на важный системный файл (например, SUID-файл), чтобы в дальнейшем получить к нему несанкционированный доступ.

-   **Значение `1` (включено):** Жесткую ссылку можно создать, только если:
    -   Процесс уже имеет доступ на чтение/запись к файлу-источнику.
    -   UID процесса совпадает с UID файла-источника.

-   **Значение `0` (отключено):** Никаких проверок не выполняется.

### Включение защиты

Чтобы включить обе защиты, необходимо добавить соответствующие параметры в файл `/etc/sysctl.conf`.

1.  **Добавьте следующие строки в `/etc/sysctl.conf`:**
    ```
    fs.protected_symlinks = 1
    fs.protected_hardlinks = 1
    ```

2.  **Примените изменения немедленно:**
    ```bash
    sudo sysctl -p
    ```

# Защита от перезаписи FIFO и обычных файлов

Эти параметры предотвращают создание файлов в каталогах, доступных для записи всем (`world-writable` и `sticky`), если файл с таким именем уже существует. Это защищает от атак, когда злоумышленник создает файл (например, лог-файл в `/tmp`) до того, как это сделает легитимная служба, чтобы перехватить или подменить данные.

### Защита FIFO (`protected_fifos`)

Контролирует создание FIFO (именованных каналов).

-   `0`: Создание FIFO разрешено всегда.
-   `1`: Не разрешать создание FIFO в `world-writable` и `sticky` каталогах, если владелец каталога отличается от владельца создаваемого FIFO.
-   `2`: Дополнительно запрещает создание FIFO, если группа каталога отличается от группы создаваемого FIFO.

### Защита обычных файлов (`protected_regular`)

Аналогично `protected_fifos`, но для обычных файлов.

-   `0`: Создание файлов разрешено всегда.
-   `1`: Не разрешать создание файлов в `world-writable` и `sticky` каталогах, если владелец каталога отличается от владельца создаваемого файла.
-   `2`: Дополнительно запрещает создание, если группа каталога отличается от группы создаваемого файла.

### Включение максимальной защиты

Чтобы включить обе защиты с наиболее строгими правилами, необходимо добавить соответствующие параметры в файл `/etc/sysctl.conf`.

1.  **Добавьте следующие строки в `/etc/sysctl.conf`:**
    ```
    fs.protected_fifos = 2
    fs.protected_regular = 2
    ```

2.  **Примените изменения немедленно:**
    ```bash
    sudo sysctl -p
    ```

# Запрет создания core dump для SUID/SGID файлов

По умолчанию, Linux может создавать core dump файлы для отладки, когда приложение падает.
Однако, для исполняемых файлов с `setuid` или `setgid` битами, это может представлять угрозу безопасности, так как core dump может содержать чувствительную информацию из памяти процесса.

Чтобы запретить создание core dump файлов для таких исполняемых файлов, необходимо установить параметр ядра `fs.suid_dumpable` в `0`.

### Включение защиты

Чтобы изменение сохранялось после перезагрузки, необходимо добавить параметр в файл `/etc/sysctl.conf`.

1.  **Добавьте следующую строку в `/etc/sysctl.conf`:**
    ```
    fs.suid_dumpable = 0
    ```

2.  **Примените изменения немедленно:**
    ```bash
    sudo sysctl -p
    ```
