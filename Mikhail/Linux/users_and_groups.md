# Управление пользователями и группами в Linux

## Создание пользователей и первичная группа (User Private Groups)

В современных дистрибутивах Linux по умолчанию используется схема **User Private Groups (UPG)**.

1.  **Пользователь всегда состоит в группе:** Каждый пользователь должен состоять как минимум в одной (первичной) группе.
2.  **Автоматическое создание одноименной группы:** При создании нового пользователя (например, командой `useradd username`) без указания дополнительных параметров автоматически создается группа с таким же именем (`username`). Эта группа становится **первичной** для данного пользователя.

## Перенос пользователей и групп между системами

### Ключевые файлы

-   `/etc/passwd`: Содержит информацию о пользователях (имя, UID, GID, домашний каталог, оболочка).
-   `/etc/shadow`: Хранит хэши паролей пользователей и информацию о сроке их действия. **Этот файл доступен для чтения только `root`**.
-   `/etc/group`: Содержит информацию о группах.
-   `/etc/gshadow`: Хранит защищенную информацию о группах (например, пароли групп).

> **ВАЖНО:** Никогда не изменяйте права доступа к файлам `/etc/shadow` и `/etc/gshadow`. Неправильные права (например, предоставление доступа на чтение кому-либо, кроме `root`) могут привести к тому, что система не сможет корректно аутентифицировать пользователя или назначить ему правильные группы при входе. Это может полностью заблокировать вход в систему или привести к тому, что пользователь войдет с сильно урезанными правами.

### Процесс переноса

1.  **Скопируйте файлы с исходной машины:**
    Используйте `scp` или `rsync` для копирования файлов на целевую машину.
    ```bash
    # Выполнять на целевой машине или указать путь назначения
    scp root@source_machine:/etc/passwd /etc/passwd
    scp root@source_machine:/etc/shadow /etc/shadow
    scp root@source_machine:/etc/group /etc/group
    ```

2.  **Перенесите домашние директории:**
    Этот метод не переносит домашние каталоги пользователей (`/home/username`). Их необходимо скопировать отдельно.
    ```bash
    # Рекомендуется использовать rsync для сохранения прав
    rsync -avz --progress root@source_machine:/home/ /home/
    ```

### **ВАЖНО: Потенциальные риски**

-   **Конфликты UID/GID:** Этот метод может перезаписать существующих пользователей и группы на целевой машине, если их UID (User ID) или GID (Group ID) совпадают. Это особенно опасно для системных учётных записей.
-   **Чистые системы:** Метод наиболее безопасен при переносе на новую, "чистую" систему или на машину с идентичной базовой конфигурацией.
-   **Резервное копирование:** Всегда создавайте резервные копии оригинальных файлов на целевой машине перед их заменой.

## Что такое хэш-функция?

**Хэш** — это результат работы **хэш-функции**, математического алгоритма, который преобразует входные данные любого размера в строку фиксированной длины. Этот процесс является **односторонним**, то есть восстановить исходные данные из хэша невозможно, так как при преобразовании часть информации необратимо теряется.

Ключевые свойства хэш-функции:
1.  **Детерминированность:** Один и тот же ввод всегда даёт один и тот же хэш.
2.  **Фиксированный размер вывода:** Независимо от размера входных данных (будь то один символ или целый фильм), результат (хэш) всегда будет иметь одинаковую длину (например, 256 бит для SHA-256).
3.  **Необратимость:** Невозможно восстановить исходные данные, зная только их хэш. Это похоже на уравнение `x² = 4`, где, зная результат `4`, мы не можем однозначно сказать, был ли исходный `x` равен `2` или `-2`.
4.  **Сопротивление коллизиям:** Практически невозможно найти два разных набора входных данных, которые привели бы к одинаковому хэшу.

В Linux хэши используются для безопасного хранения паролей. В файле `/etc/shadow` хранятся не сами пароли, а их хэши. Когда пользователь вводит пароль, система вычисляет его хэш и сравнивает с тем, что записан в файле. Это гарантирует, что даже если злоумышленник получит доступ к этому файлу, он не сможет узнать реальные пароли пользователей.

Именно поэтому безопасные системы никогда не предлагают функцию "восстановить пароль", а только "сбросить" или "заменить пароль".
-   **Восстановление пароля (плохая практика):** Подразумевает, что сервис может прислать вам ваш старый пароль. Это возможно только если пароли хранятся в открытом виде или с помощью обратимого шифрования, что является грубым нарушением безопасности.
-   **Сброс пароля (хорошая практика):** Сервис не знает ваш старый пароль. Вместо этого он предоставляет одноразовый безопасный способ (например, ссылка на email) для установки **нового** пароля, хэш которого заменит старый.

## Мониторинг пользователей

-   `who`: Показывает, кто из пользователей **в данный момент** залогинен в системе (онлайн). Читает информацию из файла `/var/run/utmp`.
-   `w`: Более подробный вывод, чем у `who`. Показывает, кто залогинен и **что они делают** (какие процессы запущены).
-   `last`: Показывает историю **последних входов** в систему, читая файл `/var/log/wtmp`. Полезна, чтобы увидеть, кто заходил в систему ранее (оффлайн).
-   `id <имя_пользователя>`: Выводит информацию о пользователе. 
    -   `uid`: User ID.
    -   `gid`: ID **первичной (основной) группы**. У пользователя она одна. Новые файлы по умолчанию создаются с этой группой.
    -   `groups`: Список ID всех групп, в которые входит пользователь (включая первичную и все **втористепенные**).

## Соглашение о диапазонах UID: системные и пользовательские

Технически, ядро Linux не будет возражать, если вы создадите пользователя с UID 500 или запустите веб-сервер с UID 1500. Система будет работать. Однако это считается очень плохой практикой, и вот почему:

1.  **Нарушение общепринятой конвенции.** Это главный пункт. Весь мир Linux/Unix работает по соглашению: UIDs до 1000 (в некоторых дистрибутивах до 500) зарезервированы для системных учетных записей (служб, демонов), а всё, что выше — для обычных, "человеческих" пользователей. Нарушая это правило, вы создаете систему, которую сложно и опасно администрировать.

2.  **Риски безопасности.**
    *   **Пользователь с низким UID:** Если вы дадите пользователю UID, например, 70 (который может использоваться системным процессом), а потом установите пакет, который создает пользователя с таким же UID, ваш "человек" может внезапно стать владельцем системных файлов. Это прямой путь к нарушению безопасности.
    *   **Демон с высоким UID:** Системные службы часто имеют ограниченные права. Если вы запускаете демона под UID > 1000, другие системные утилиты и скрипты могут ошибочно принять его за обычного пользователя и, например, включить его в отчеты по дисковым квотам или в списки на резервное копирование домашних директорий.

3.  **Конфликты с системными пакетами.** При установке (`apt`, `yum`) многие пакеты (веб-серверы, базы данных) автоматически создают системного пользователя с заранее определенным UID из низкого диапазона. Если этот UID уже занят вашим "человеческим" пользователем, установка может завершиться с ошибкой или привести к непредсказуемым последствиям.

## Повышение привилегий: `su` против `sudo`

### `su` (substitute user)

-   **Что делает:** Переключает вас на сеанс другого пользователя. Если имя пользователя не указано, по умолчанию пытается переключиться на `root`.
-   **Какой пароль спрашивает:** Пароль **целевого пользователя** (того, на которого вы переключаетесь). Чтобы выполнить `su -`, вам нужно знать пароль `root`.
-   **Основной сценарий:** Полностью "стать" другим пользователем, получив его оболочку и окружение. Часто используется для перехода в сеанс `root`, если его пароль известен и включен.

### `sudo` (superuser do)

-   **Что делает:** Выполняет *одну или несколько команд* от имени другого пользователя (по умолчанию `root`), не переключая сеанс полностью.
-   **Какой пароль спрашивает:** Пароль **текущего пользователя** (вашего собственного).
-   **Как работает:** Проверяет файл `/etc/sudoers`, чтобы определить, имеет ли **текущий пользователь** (чей пароль и был введен) право выполнять указанную команду от имени целевого пользователя.
-   **Основной сценарий:** Временно повысить привилегии для выполнения конкретной административной задачи (установка ПО, редактирование конфигурационного файла). Это более безопасный и контролируемый подход, так как он не требует разглашения пароля `root` и позволяет гранулированно настраивать права.
-   **Логирование:** Каждое действие, выполненное через `sudo`, записывается в системный журнал (например, `/var/log/auth.log`), создавая полный аудиторский след.

#### Получение интерактивной оболочки через `sudo`

`sudo` также можно использовать для получения полноценной оболочки от имени другого пользователя, что является предпочтительной альтернативой `su`.

-   `sudo -i [-u <имя_пользователя>]`: Запускает **интерактивную login-оболочку**. Это лучший способ "стать" другим пользователем. Окружение будет таким же, как если бы этот пользователь вошел в систему: загрузятся его `.profile`, `.bashrc`, а текущим каталогом станет его домашний каталог.
-   `sudo -s [-u <имя_пользователя>]`: Запускает **интерактивную non-login оболочку**. Запускает оболочку, указанную в переменной `SHELL`, но не симулирует полный вход в систему (не считывает `.profile`) и оставляет вас в текущем каталоге.

Если `<имя_пользователя>` не указано, используется `root`.
