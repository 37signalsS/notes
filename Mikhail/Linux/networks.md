# Управление и диагностика сетей в Linux

В Linux интерфейс — это программная абстракция, которая управляется ядром и может соответствовать как физическому, так и виртуальному устройству.

### Типы интерфейсов

*   **Физические интерфейсы (`eth0`, `enp3s0`, `wlan0`)
    *   Это интерфейсы, которые напрямую связаны с аппаратным обеспечением — вашей сетевой картой (NIC) или Wi-Fi адаптером.
    *   Именно они отправляют и принимают данные по медному кабелю или через радиоволны.
    *   У каждого такого интерфейса есть уникальный физический адрес (MAC-адрес).

*   **Виртуальные интерфейсы**
    *   Они не привязаны к реальному "железу" и создаются программно для специальных задач.
    *   **`veth` (Virtual Ethernet):** Это "виртуальный патч-корд". Интерфейсы `veth` всегда создаются парами. Что отправляется в один конец пары, выходит из другого. Это ключевая технология для контейнеризации (например, в Docker), позволяющая соединить сетевое пространство контейнера с хост-системой.
    *   **`bridge` (мост, `br0`):** Это "виртуальный свитч". Он позволяет объединять несколько других интерфейсов (как физических, так и виртуальных) в единую сеть, чтобы они могли общаться друг с другом. Широко используется в виртуализации и Docker.
    *   **`tun`/`tap`:** Используются для создания туннелей, чаще всего для VPN. Они позволяют программам пользовательского пространства (user-space) отправлять и получать сетевые пакеты.

### `127.0.0.1` и `192.168.0.1` 


*   `127.0.0.1` — это адрес самого себя (loopback, localhost), связь процессов внутри одного и того же компьютера.
*   `192.168.0.1` — это локалка, связь между разными устройствами в одной локальной сети (LAN).

## 1. Управление сетевыми интерфейсами (`ip`)

Команда `ip` — это основной современный инструмент для управления сетевыми интерфейсами, IP-адресами и маршрутизацией.

-   **Посмотреть все IP-адреса и состояние интерфейсов:**
    ```bash
    ip a
    # или
    ip addr show
    ```

-   **Включить или выключить интерфейс:**
    ```bash
    # Выключить
    sudo ip link set dev eth0 down
    # Включить
    sudo ip link set dev eth0 up
    ```

-   **Добавить или удалить IP-адрес:**
    ```bash
    # Добавить
    sudo ip addr add 192.168.1.100/24 dev eth0
    # Удалить
    sudo ip addr del 192.168.1.100/24 dev eth0
    ```

## 2. Базовая диагностика: Связность и DNS

### Проверка доступности хоста (`ping`)

`ping` отправляет ICMP-запросы для проверки доступности хоста и измерения задержки.

-   **Анализ ответов `ping`:**
    -   **`Destination Host Unreachable`**: Ваш локальный маршрутизатор не знает, как добраться до цели. Проблема в вашей сети (нет маршрута, кабель отключен).
    -   **`Request Timed Out`**: Ответ не пришел вовремя. Причины: файрвол, перегрузка сети, хост выключен.
    -   **`TTL expired in transit`**: Пакет превысил лимит "прыжков". Чаще всего указывает на **петлю маршрутизации**.

-   **Тестирование MTU:**
    Отправка пакета, который не должен фрагментироваться. Помогает выявить проблемы с MTU на пути.
    ```bash
    # 1472 байта данных + 28 байт заголовков = 1500 байт
    ping -c 4 -s 1472 -M do 8.8.8.8
    ```

### Диагностика DNS (`dig`, `resolvectl`)

Правильная работа DNS — ключ к сетевой связности.

-   **`dig`**: Мощный инструмент для опроса DNS-серверов.
    ```bash
    # Получить A-запись для домена
    dig example.com

    # Запросить все типы записей
    dig example.com ANY

    # Провести полную трассировку запроса от корневых серверов
    dig +trace example.com

    # Опросить конкретный DNS-сервер
    dig @8.8.8.8 example.com
    ```

-   **`resolvectl`**: В системах с `systemd-resolved` эта утилита показывает статус резолвера и используемые DNS-серверы.
    ```bash
    # Проверить статус и текущие серверы
    resolvectl status

    # Узнать, как будет разрешено имя
    resolvectl query example.com
    ```

-   **Порядок разрешения имен (`/etc/nsswitch.conf`):**
    Этот файл определяет, в каком порядке система будет пытаться разрешить имя хоста (например, сначала посмотреть в `/etc/hosts`, а потом идти в DNS). Строка `hosts:` отвечает за этот порядок.
    ```
    # Пример: сначала локальные файлы, потом DNS
    hosts:          files dns
    ```

## 3. Анализ соединений и портов

### Активные соединения (`ss`)

Утилита `ss` — быстрая и современная замена `netstat`.

-   **Показать все слушающие TCP и UDP порты и процессы, которые их используют:**
    ```bash
    sudo ss -tulpan
    ```
    -   `-t`: TCP, `-u`: UDP, `-l`: слушающие сокеты, `-p`: процессы, `-n`: числовой вывод, `-a`: все сокеты.

-   **Узнать, какой процесс занял определённый порт:**
    ```bash
    sudo ss -lntp 'sport = :443'
    ```

### Сканирование портов (`nmap`)

`nmap` — незаменимый инструмент для аудита безопасности и исследования сети.

-   **Быстрое сканирование популярных портов на хосте:**
    ```bash
    nmap scanme.nmap.org
    ```

-   **Проверить, открыт ли конкретный порт:**
    ```bash
    nmap -p 80,443 192.168.1.1
    ```

-   **Определить версии служб, работающих на портах:**
    ```bash
    sudo nmap -sV 192.168.1.1
    ```

## 4. Маршрутизация и анализ пути

-   **Посмотреть таблицу маршрутизации:**
    ```bash
    ip route show
    ```

-   **Трассировка маршрута (`traceroute`):**
    Показывает путь (последовательность маршрутизаторов) до цели.
    ```bash
    traceroute example.com
    ```
    -   Если на узле отображаются `* * *`, он может блокировать ICMP. Попробуйте трассировку через TCP:
        ```bash
        sudo traceroute -T example.com
        ```

## 5. Анализ сетевого трафика (`tcpdump`)

Перехватывает и анализирует сетевые пакеты в реальном времени. Это мощный инструмент для глубокой диагностики.

-   **Прослушивать трафик на всех интерфейсах на порту 443:**
    ```bash
    sudo tcpdump -i any port 443 -nn
    ```
    -   `-i any`: все интерфейсы, `-nn`: не преобразовывать адреса и порты в имена.

## 6. Измерение производительности и бенчмаркинг

### `iperf3` (Пропускная способность)

`iperf3` — утилита для измерения пропускной способности сети между двумя хостами.

-   **На хосте-сервере:**
    ```bash
    iperf3 -s
    ```

-   **На хосте-клиенте:**
    ```bash
    # Простое измерение (клиент -> сервер)
    iperf3 -c <IP_адрес_сервера>

    # Измерение в обратную сторону (сервер -> клиент)
    iperf3 -c <IP_адрес_сервера> -R
    
    # Тест с несколькими потоками для насыщения канала
    # -t 60: время теста 60 секунд
    # -P 16: 16 параллельных потоков
    iperf3 -c <IP_адрес_сервера> -t 60 -P 16
    ```

### `ping` (Задержка и потери)

-   **Проверка средней задержки и потерь:**
    ```bash
    ping -c 20 example.com
    ```
    *Смотрите на `avg` в статистике и процент `packet loss`.*

### `curl` (Скорость загрузки)

-   **Измерение времени до начала передачи данных:**
    ```bash
    curl -o /dev/null -s -w "Время до первого байта: %{time_starttransfer}\n" https://example.com/file.zip
    ```
    *Чем меньше `time_starttransfer`, тем быстрее сервер отвечает, что косвенно говорит о низкой перегрузке.*

### `nload` / `bmon` (Визуализация трафика)

Инструменты для мониторинга сетевого трафика в реальном времени.

```bash
sudo apt install nload bmon
nload
# или
bmon
```
*Полезно запускать во время тестов `iperf3` для визуального контроля.*

## 7. iptables

`iptables` — классический инструмент для управления файрволом Netfilter. Он работает с **цепочками** правил.

-   **Основные цепочки:**
    -   `INPUT`: Входящий трафик, адресованный самому серверу.
    -   `OUTPUT`: Исходящий трафик с сервера.
    -   `FORWARD`: Транзитный трафик, проходящий через сервер.

-   **Посмотреть текущие правила:**
    ```bash
    sudo iptables -L -v -n
    ```

Очистить все правила (будьте осторожны, это может заблокировать вам доступ):
```sh
# Удалить все правила
sudo iptables -F
# Удалить все пользовательские цепочки
sudo iptables -X
```

### Базовые правила

Разрешить весь трафик на локальном интерфейсе `lo` (важно для работы многих приложений):
```sh
sudo iptables -A INPUT -i lo -j ACCEPT
sudo iptables -A OUTPUT -o lo -j ACCEPT
```

Установить политику по умолчанию (что делать с трафиком, который не подошел ни под одно правило):
```bash
# Блокировать весь входящий трафик по умолчанию
sudo iptables -P INPUT DROP
# Блокировать весь исходящий трафик по умолчанию
sudo iptables -P OUTPUT DROP
```
**Внимание:** После установки политики `DROP` вам нужно будет явно разрешать все необходимые соединения.

### Примеры правил

Разрешить входящие SSH-соединения с определённого IP:
```sh
sudo iptables -A INPUT -p tcp --dport 22 -s 172.16.238.15 -j ACCEPT
```

Разрешить исходящие HTTP/HTTPS соединения:
```sh
sudo iptables -A OUTPUT -p tcp --dport 80 -j ACCEPT
sudo iptables -A OUTPUT -p tcp --dport 443 -j ACCEPT
```

Удалить правило из цепочки по его номеру:
```sh
sudo iptables -D INPUT <номер_правила>
```

### Сохранение правил

Правила `iptables` сбрасываются при перезагрузке. Для их сохранения установите пакет `iptables-persistent`.
```sh
sudo apt-get install iptables-persistent
```
Во время установки вам будет предложено сохранить текущие правила. В дальнейшем для сохранения можно использовать команду:
```sh
sudo netfilter-persistent save
```

### Взаимодействие iptables и Docker

> **Ключевой момент:** Docker управляет своими правилами `iptables` и направляет трафик к контейнерам через цепочку **`FORWARD`**, а не `INPUT`.

- **Трафик к контейнерам идёт через `FORWARD`:** Когда вы пробрасываете порт с хоста в контейнер (например, `docker run -p 8080:80`), Docker добавляет правила в таблицу `nat`, чтобы перенаправлять трафик. Этот перенаправленный трафик обрабатывается цепочкой `FORWARD`, а не `INPUT`, как можно было бы ожидать.

**Проблема:** Если вы установили политику по умолчанию `sudo iptables -P FORWARD DROP`, вы не сможете получить доступ к опубликованным портам контейнеров.

**Правильное решение:** Docker создал специальную цепочку `DOCKER-USER`, которая выполняется раньше всех остальных правил Docker. Все кастомные правила для контейнеров следует добавлять в нее.

-   **Пример: разрешить доступ к порту 8080 с определенного IP:**
    ```bash
    # Трафик на все остальные порты будет обработан стандартными правилами Docker или заблокирован
    sudo iptables -I DOCKER-USER -i ext_if -p tcp --dport 8080 -s 1.2.3.4 -j ACCEPT
    ```
    - `-I DOCKER-USER`: Вставить правило в начало цепочки `DOCKER-USER`.
    - `-i ext_if`: Укажите ваш внешний сетевой интерфейс.

## 8. Продвинутые темы

### Проблема `TIME_WAIT`

Когда TCP-соединение закрывается, оно на некоторое время (обычно 60 секунд) переходит в состояние `TIME_WAIT` для гарантии доставки всех пакетов. На высоконагруженных серверах (например, прокси) большое количество таких сокетов может исчерпать лимит доступных портов.

-   **Диагностика:**
    ```bash
    ss -tan 'state time-wait' | wc -l
    ```

-   **Решение (настройка ядра):**
    Для постоянного применения добавьте эти строки в `/etc/sysctl.conf` и выполните `sudo sysctl -p`.
    ```ini
    # Разрешить повторное использование сокетов в состоянии TIME_WAIT для новых соединений (безопасно)
    net.ipv4.tcp_tw_reuse=1

    # Уменьшить время ожидания в TIME_WAIT (по умолчанию 60)
    net.ipv4.tcp_fin_timeout=30
    ```

### Оптимизация TCP с помощью BBR

**BBR (Bottleneck Bandwidth and Round-trip time)** — это современный алгоритм управления перегрузкой от Google.BBR моделирует реальную пропускную способность сети и задержку. Это позволяет достичь значительно более высокой производительности и низкой задержки, особенно в сетях с потерями или высокой задержкой (Long-Fat Networks).

1. Разведка: BBR периодически ненадолго увеличивает скорость отправки данных, чтобы проверить, не выросла ли пропускная способность канала (вдруг «трубу» расширили?).
2. Дренаж: После разведки он наоборот, немного снижает скорость, чтобы «осушить» возможные очереди из пакетов, которые могли скопиться в буферах маршрутизаторов, уменьшая задержку.
3. Стабильная работа: Основное время BBR работает на рассчитанной оптимальной скорости, которая обеспечивает максимальную пропускную способность при минимальной задержке

#### Процесс включения BBR на Ubuntu/Debian

**Шаг 1: Проверка версии ядра**

BBR требует ядро Linux версии `4.9` или выше.
```bash
uname -r
```

**Шаг 2: Проверка доступных алгоритмов**

Убедитесь, что `bbr` есть в списке доступных.
```bash
sysctl net.ipv4.tcp_available_congestion_control
```

**Шаг 3: Загрузка модуля (если необходимо)**

Обычно модуль уже загружен. Если нет, загрузите его и добавьте в автозагрузку.
```bash
# Загрузить модуль
sudo modprobe tcp_bbr

# Добавить в автозагрузку при старте системы
echo 'tcp_bbr' | sudo tee /etc/modules-load.d/bbr.conf
```

**Шаг 4: Настройка `sysctl`**

Добавьте следующие строки в `/etc/sysctl.conf` для активации BBR.
```ini
# /etc/sysctl.conf

# Включить Fair Queuing (обязательно для BBR)
net.core.default_qdisc = fq

# Установить BBR как алгоритм контроля перегрузки
net.ipv4.tcp_congestion_control = bbr
```

**Шаг 5: Применение и проверка**

Примените настройки и убедитесь, что BBR активен.
```bash
# Применить настройки
sudo sysctl -p

# Проверить, что BBR используется
sysctl net.ipv4.tcp_congestion_control
# Ожидаемый вывод: net.ipv4.tcp_congestion_control = bbr

# Убедиться, что модуль загружен
lsmod | grep bbr
```

#### BBRv2 и совместимость

-   **BBRv2:** Более новая, экспериментальная версия, нацеленная на улучшение справедливости при работе с потоками CUBIC. Требует кастомного ядра.
-   **Совместимость:** BBR может быть агрессивен по отношению к хостам с CUBIC. Также, старые прокси или VPN-шлюзы могут некорректно интерпретировать его поведение, хотя сегодня это встречается редко.

### Защита от IP Spoofing с помощью `rp_filter`

Параметр ядра `rp_filter` (Reverse Path Filter) — это механизм защиты от подмены IP-адреса отправителя (IP Spoofing). Он проверяет, является ли маршрут к источнику входящего пакета "логичным".

#### Режимы работы

-   `0`: **Фильтр выключен.** Никаких проверок не производится.
-   `1`: **Строгий режим (Strict Mode).** Ядро проверяет, что обратный маршрут до IP-адреса источника пакета проходит через тот же интерфейс, на который этот пакет пришел. Если нет — пакет отбрасывается. Это наиболее безопасный режим.
-   `2`: **Свободный режим (Loose Mode).** Ядро проверяет только то, что IP-адрес источника доступен через какой-либо из маршрутов в системе, не обязательно через тот же интерфейс. Пакет отбрасывается, только если источник недостижим.

#### Проверка и настройка

-   **Проверить текущие значения:**
    ```bash
    sysctl net.ipv4.conf.all.rp_filter
    sysctl net.ipv4.conf.default.rp_filter
    ```

-   **Применить временно (до перезагрузки):**
    ```bash
    # Строгий режим
    sudo sysctl -w net.ipv4.conf.all.rp_filter=1

    # Свободный режим
    sudo sysctl -w net.ipv4.conf.all.rp_filter=2
    ```

-   **Применить навсегда:**
    Добавьте нужные строки в файл `/etc/sysctl.conf` и затем примените настройки командой `sudo sysctl -p`.
    ```sh
    # Пример для /etc/sysctl.conf
    net.ipv4.conf.all.rp_filter=1
    net.ipv4.conf.default.rp_filter=1
    ```

### Что такое сокет?

**Сокет** — это программный интерфейс (представленный как файл в ОС) для обмена данными между процессами. Эти процессы могут выполняться как на одной машине, так и в сети.

### Основные типы сокетов

1.  **Сетевые сокеты (AF_INET, AF_INET6):**
    *   Используются для коммуникации по сети (например, через интернет).
    *   Они привязаны к IP-адресу и порту.
    *   Пример: веб-сервер, который "слушает" порт 80 для входящих HTTP-запросов.

2.  **Unix-сокеты (AF_UNIX):**
    *   Используются для обмена данными между процессами **на одной и той же машине**.
    *   Они не используют сетевой стек (IP-адреса и порты), а вместо этого создают специальный файл в файловой системе.
    *   **Преимущество:** Работают значительно быстрее сетевых сокетов, так как данные не проходят через сетевой интерфейс. Это делает их идеальными для локального IPC (Inter-Process Communication).

**Пример: Docker Socket (`/var/run/docker.sock`)**
Это Unix-сокет, который демон Docker (`dockerd`) использует как API. Клиент `docker` подключается к этому файлу для отправки команд. Доступ к этому файлу равносилен root-доступу к хост-системе.

## 9. Постоянные имена сетевых интерфейсов

Иногда сетевой интерфейс «пропадает» или переименовывается после перезагрузки (например, `ens3` в `enp0s3`), особенно на серверах, использующих `systemd-networkd`. Это может нарушить работу файрвола, скриптов и других сетевых конфигураций.

Решение — зафиксировать имя интерфейса с помощью правила `systemd.link`.

### Как это работает

1.  **Узнайте MAC-адрес нужного интерфейса:**
    ```bash
    ip link show
    ```
    Вы увидите что-то вроде `link/ether 52:54:00:ab:cd:ef`. Это и есть MAC-адрес.

2.  **Создайте файл правила `.link`:**
    Создайте файл `/etc/systemd/network/10-persistent.link` (имя может быть любым, но должно начинаться с числа и заканчиваться на `.link`).
    ```ini
    # /etc/systemd/network/10-persistent.link
    [Match]
    MACAddress=52:54:00:ab:cd:ef

    [Link]
    Name=lan0
    ```
    - `[Match]`: Условие, по которому `systemd-udevd` найдет устройство. `MACAddress` — самый надежный способ.
    - `[Link]`: Действие, которое нужно применить. `Name=lan0` задает новое, постоянное имя `lan0`.

3.  **Перезапустите службы:**
    Чтобы применить изменения, перезапустите службы, отвечающие за управление устройствами и сетью.
    ```bash
    sudo systemctl restart systemd-udevd
    sudo systemctl restart systemd-networkd
    ```

Теперь ваш сетевой интерфейс всегда будет называться `lan0`, независимо от порядка загрузки драйверов или изменений в оборудовании.

**Совет:** Вместо `MACAddress` можно использовать `Driver=` или `Path=`, если у вас несколько одинаковых сетевых карт и нужно привязаться к физическому порту.
