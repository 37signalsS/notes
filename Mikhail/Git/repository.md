# Шпаргалка по Git: от основ до продвинутых техник


# I. Основы Git

Этот раздел охватывает самые первые шаги и основной рабочий процесс в Git.

## 1. Первоначальная настройка

Перед началом работы необходимо указать ваше имя и адрес электронной почты. Это важно, так как эта информация будет встроена в каждый коммит.

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "ваш@email.com"
```

## 2. Создание репозитория

**Инициализация нового репозитория** в существующей папке:

```bash
# Создает скрытую директорию .git
git init
# Рекомендуется сразу указывать имя основной ветки (например, main)
git init --initial-branch=main
```

**Клонирование существующего репозитория:**

```bash
git clone <url_репозитория>
```

## 3. Основной рабочий процесс

Жизненный цикл файлов в Git:
1.  **Неотслеживаемый (untracked)** — Git не знает о файле.
2.  **Изменён (modified)** — файл изменён, но не добавлен в коммит.
3.  **Подготовлен (staged)** — файл отмечен для включения в следующий коммит.
4.  **Зафиксирован (committed)** — изменения сохранены в репозитории.

**Проверка статуса:**
```bash
git status
git status -s # Короткий (summary) формат
```

**Добавление файлов в область подготовленных (индексация):**
```bash
git add <имя_файла> # Добавить конкретный файл
git add .           # Добавить все новые и изменённые файлы в текущей директории
```

**Фиксация изменений (коммит):**
```bash
git commit -m "Краткое описание изменений"
git commit -am "Описание" # Добавляет все отслеживаемые файлы и сразу делает коммит
```

## 4. Просмотр истории (git log)

Просмотр истории коммитов:

```bash
git log
```

### Полезные флаги для `git log`:

**Форматирование вывода:**
*   `--oneline`: Показывает каждый коммит в одну строку.
*   `--graph`: Отображает историю в виде ASCII-графа.
*   `--pretty=format:"%h %s"`: Позволяет настроить формат вывода (`%h` - короткий хэш, `%s` - сообщение).
*   `--stat`: Отображает статистику изменённых файлов для каждого коммита.
*   `-p`: Показывает изменения (diff), внесённые в каждом коммите.

**Фильтрация коммитов:**
*   `-n <число>`: Ограничивает вывод указанным числом коммитов.
*   `--since="YYYY-MM-DD"` и `--until="YYYY-MM-DD"`: Фильтрует по дате.
*   `--author="<имя>"`: Поиск по автору.
*   `--grep="<паттерн>"`: Поиск по сообщению коммита.
*   `-S "<текст>"`: Поиск коммитов, где было добавлено или удалено указанное слово.
*   `--no-merges`: Исключает коммиты слияния.
*   `master..test`: Показывает коммиты, которые есть в ветке `test`, но нет в `master`.

**Анализ файлов:**
*   `-- <путь_к_файлу>`: Показывает историю изменений только для указанного файла.
*   `--follow <файл>`: Отслеживает историю файла, включая его переименования.
*   `--name-only`: Показывает только имена изменённых файлов.

## 5. Сравнение изменений (git diff)

*   `git diff`: Сравнение рабочей директории с областью подготовленных файлов (индексом).
*   `git diff --staged` (или `--cached`): Сравнение подготовленных файлов с последним коммитом (`HEAD`).
*   `git diff HEAD`: Сравнение рабочей директории с последним коммитом.

## 6. Управление файлами

**Переименование и перемещение:**
```bash
git mv <старое_имя> <новое_имя>
```

**Удаление:**
```bash
# Удаление файла из контроля версий и с диска
git rm <файл>

# Удаление файла только из контроля версий (оставить на диске)
git rm --cached <файл>
```

# II. Работа с ветками 


## 1. Создание и управление ветками

*   `git branch`: Список локальных веток.
*   `git branch -a`: Список всех веток (локальные и удалённые).
*   `git branch -vv`: Показывает локальные ветки и их связь с удалёнными.
*   `git branch <имя_ветки>`: Создать новую ветку.
*   `git branch <новая> <существующая>`: Создать новую ветку как копию существующей.
*   `git branch -d <имя_ветки>`: Удалить ветку (только если она полностью слита).
*   `git branch -D <имя_ветки>`: Принудительно удалить ветку.

## 2. Переключение между ветками

**Переключение на другую ветку:**
```bash
git switch <имя_ветки>
# или старый вариант
git checkout <имя_ветки>
```

**Создание новой ветки и переключение на неё:**
```bash
git switch -c <имя_ветки>
# или старый вариант
git checkout -b <имя_ветки>
```

## 3. Слияние веток (merge)

Перейдите на ветку, в которую хотите влить изменения, и выполните:
```bash
git merge <имя_ветки_для_слияния>
```
**Полезные флаги:**
*   `--squash`: Объединяет все коммиты из сливаемой ветки в один, не перенося историю.
*   `--abort`: Отменяет слияние, если возникли конфликты.
*   `--allow-unrelated-histories`: Разрешает слияние веток с несвязанной историей.

Для разрешения конфликтов слияния можно использовать визуальный инструмент:
```bash
git mergetool
```

## 4. Сравнение `merge` и `rebase` 

**Исходное состояние:**
```
      D---E <-- feature
     /
A---B---C <-- main
```

---

#### **Способ 1: `git merge` (сохраняет историю)**

`git merge` создает новый "коммит слияния" (`F`), который объединяет истории обеих веток.

```bash
git checkout main
git merge feature
```

**Результат:**
```
      D---E
     /     \
A---B---C---F <-- main, feature
```
*   **Плюсы:** История сохранена, видно, где и когда произошло слияние.
*   **Минусы:** Может создавать "шумную", нелинейную историю.

---

#### **Способ 2: `git rebase` (перезаписывает историю)**

`git rebase` перемещает вашу ветку, применяя её коммиты поверх последнего коммита целевой ветки.

```bash
git checkout feature
git rebase main
```

**Что происходит "под капотом":**

1.  Git "отматывает" вашу ветку `feature` до общего предка (`B`).
2.  Временно сохраняет ваши коммиты `D` и `E` (как патчи).
3.  Перемещает указатель `feature` на последний коммит в `main` (`C`).
4.  Применяет ваши сохраненные коммиты один за другим поверх `C`.

**Важно:** Применяя коммиты `D` и `E` на новую "базу" (`C`), Git создает **новые коммиты** (`D'` и `E'`). У них будет то же содержимое и сообщение, но другие хэши (SHA-1 ID), потому что у них другой родительский коммит.

**Результат:**
```
A---B---C---D'---E' <-- feature
```
*   **Плюсы:** Создает линейную и чистую историю.
*   **Минусы:** Перезаписывает историю (создает новые коммиты `D'` и `E'`). **Нельзя использовать для веток, с которыми работают другие люди.**

После `rebase` для обновления `main` потребуется `fast-forward` слияние:
```bash
git checkout main
git merge feature
```

Поскольку `main` является прямым предком `feature`, Git выполнит "перемотку вперед" (fast-forward), просто переместив указатель `main` на `E'`.

**Финальная история:**

```
A---B---C---D'---E' <-- main, feature
```

### 4.1. Интерактивное перебазирование

Для полного контроля над историей (объединение, переименование, удаление коммитов) используется интерактивный режим:

```bash
git rebase -i HEAD~3 # Пример для последних 3 коммитов
```
В редакторе можно выбрать действие для каждого коммита:
*   `pick`: использовать коммит.
*   `squash`: объединить коммит с предыдущим.
*   `fixup`: объединить с предыдущим, отбросив сообщение коммита.
*   `reword`: изменить сообщение коммита.
*   `drop`: удалить коммит.

## 6. Сравнение веток

*   `git log master..test`: Показать коммиты, которые есть в `test`, но нет в `master`.
*   `git cherry -v master`: Показать список коммитов в текущей ветке, которых нет в `master`.

## 7. Gitflow

Популярная модель ветвления, предлагающая строгую структуру для управления проектами.

**Основные ветки:**
*   `main` (или `master`): Стабильные релизы.
*   `develop`: Основная ветка для разработки.

**Вспомогательные ветки:**
*   `feature/*`: Для новых функций (от `develop`).
*   `release/*`: Для подготовки релиза (от `develop`).
*   `hotfix/*`: Для срочных исправлений (от `main`).

**Визуальная схема:**
```
      hotfix/*
         |
main ------o-----------o-------------------o----->
         / \
       /   \       /   \
release/*   \       /   \         release/*
       |     \     /     \           |
develop ---o----o---o---o---o---o---o---o--->
         \ / \ / \ / \ / \ / \ / \
 feature/*     feature/*     feature/*
```

# III. Удалённые репозитории

Работа с удалёнными репозиториями для совместной работы.

## 1. Управление удалёнными репозиториями

*   `git remote -v`: Список удалённых репозиториев.
*   `git remote add <имя> <url>`: Добавить новый.
*   `git remote remove <имя>`: Удалить.
*   `git remote rename <старое> <новое>`: Переименовать.
*   `git remote set-url <имя> <url>`: Изменить URL.
*   `git remote show <имя>`: Показать подробную информацию.

## 2. Синхронизация

*   `git fetch <имя>`: Загружает изменения, но не сливает их.
*   `git pull <имя> <ветка>`: Загружает и сливает изменения (`fetch` + `merge`).
*   `git push <имя> <ветка>`: Отправляет локальные изменения.

**Связать локальную ветку с удалённой и отправить изменения:**
```bash
git push --set-upstream origin <имя_ветки>
```

**Принудительная отправка (используйте с осторожностью!):**
*   `git push --force`: Перезаписывает историю в удалённой ветке. **Опасно!**
*   `git push --force-with-lease`: Более безопасная версия. Отклонит push, если кто-то другой внёс изменения.

## 3. Работа с SSH-ключами

**Создание нового SSH-ключа:**
```bash
ssh-keygen -t ed25519 -C "ваш@email.com" -f ~/.ssh/id_ed25519_project
```

**Добавление ключа в ssh-agent:**
```bash
eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519_project
chmod 600 ~/.ssh/id_ed25519_project
chmod 700 ~/.ssh
```

**Управление несколькими ключами** (`~/.ssh/config`):
```ini
# Стандартный ключ
Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519

# Ключ для конкретного проекта
Host project-alias
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_project
```
Клонирование с псевдонимом: `git clone git@project-alias:user/repo.git`

## 4. Создание Merge Request (GitLab)

Merge Request (MR) — это аналог Pull Request в GitLab.

### Способ 1: Стандартный `git push`

Это основной способ, не требующий дополнительных утилит.

1.  **Отправьте вашу ветку в GitLab.** При первом пуше используйте флаг `-u` (`--set-upstream`).
    ```bash
git push -u origin имя-вашей-ветки
```
2.  **Используйте ссылку из вывода.** GitLab вернет в терминал прямую ссылку для создания MR. Откройте ее в браузере.
    ```
    remote: To create a merge request for имя-вашей-ветки, visit:
    remote:   https://gitlab.com/your-group/your-project/-/merge_requests/new?merge_request%5Bsource_branch%5D=имя-вашей-ветки
    ```

### Способ 2: GitLab CLI (`glab`)

Официальная утилита для полноценной работы с GitLab из командной строки.

1.  **Установка и аутентификация.**
    Установите `glab` (например, `brew install glab`) и выполните вход:
    ```bash
glаb auth login
```
2.  **Создание MR.**
    После `git push` выполните команду. `glab` запустит интерактивный диалог для заполнения данных MR.
    ```bash
glаb mr create
```
    Или создайте MR одной командой с нужными флагами:
    ```bash
glаb mr create --title "Заголовок MR" --description "Описание." --target-branch main
```
    *   `--web`: откроет созданный MR в браузере.
    *   `--remove-source-branch`: удалит ветку после слияния.

# IV. Продвинутые техники

Инструменты для исправления ошибок и восстановления данных.

## 1. Отмена и исправление изменений

**Отмена `git add` (убрать файл из индекса):**
```bash
git reset <имя_файла>
```

**Отмена локальных изменений в файле:**
```bash
git restore <имя_файла>
```

**Отмена коммитов (`reset` vs `revert`):**
*   `git revert <хэш>`: Создаёт **новый** коммит, который отменяет изменения. Безопасно для опубликованной истории.
*   `git reset <хэш>`: **Перемещает** указатель `HEAD`, изменяя историю. **Опасно для опубликованной истории.**

**Режимы `git reset`:**
*   `--soft HEAD~1`: Отменяет коммит, но оставляет изменения в индексе (staged).
*   `--mixed HEAD~1` (по умолчанию): Отменяет коммит, изменения остаются в рабочей директории.
*   `--hard HEAD~1`: Полностью удаляет коммит и все связанные с ним изменения.

**Изменение последнего коммита:**
```bash
git commit --amend -m "Новое сообщение коммита"
```

**Полный сброс до удалённого состояния:**
```bash
git fetch --all
git reset --hard origin/main # Замените main на нужную ветку
```

**Очистка рабочей директории:**
```bash
git clean -n      # Показать, какие файлы будут удалены
git clean -fd     # Удалить неотслеживаемые файлы и директории
```

## 2. Восстановление данных

**`git reflog`**: Журнал всех изменений `HEAD`. Помогает найти "потерянные" коммиты.
```bash
git reflog
git reset --hard HEAD@{индекс} # Восстановиться к нужному состоянию
```

**`git fsck`**: Проверяет целостность базы данных и находит "висячие" коммиты.
```bash
git fsck --lost-found
```

**Восстановление удалённого файла:**
```bash
# 1. Найти хэш коммита, где файл существовал
git rev-list -n 1 HEAD -- <путь_к_файлу>

# 2. Восстановить файл из этого коммита
git checkout <хэш>^ -- <путь_к_файлу>
```

**Возврат одного файла к состоянию из другого коммита:**

```bash
git checkout <хэш_коммита> -- <имя_файла>
```

## 3. Временное сохранение (Stash)

Сохранить незакоммиченные изменения:
```bash
git stash save "сообщение"
git stash # Короткий вариант
```
*   `git stash list`: Показать список.
*   `git stash pop`: Применить последние изменения и удалить их из списка.
*   `git stash apply`: Применить, но оставить в списке.
*   `git stash clear`: Удалить все.

## 4. Метки (Tags)

Используются для обозначения релизов (например, `v1.0`).
*   `git tag <имя_тега>`: Создать лёгкий тег.
*   `git tag -a <имя_тега> -m "сообщение" <хэш_коммита>`: Создать аннотированный тег для конкретного коммита.
*   `git show <имя_тега>`: Показать информацию о теге.
*   `git tag -f -a <имя_тега> <хэш_коммита>`: Принудительно переместить (заменить) аннотированный тег на другой коммит.
*   `git push origin <имя_тега>`: Отправить тег в удалённый репозиторий.
*   `git push --tags`: Отправить все теги.
*   `git push --delete origin <имя_тега>`: Удалить тег из удалённого репозитория.

## 5. Перенос коммитов (Cherry-pick)

Применение коммита из другой ветки в текущую.
```bash
git cherry-pick <хэш_коммита_1> <хэш_коммита_2>
```
*   `--no-commit`: Применяет изменения, но не создаёт коммит, позволяя внести правки.

## 6. Поиск ошибок (Bisect)

Автоматический поиск коммита, который внёс ошибку.
```bash
git bisect start
git bisect bad <хэш_плохого_коммита>  # Коммит, где ошибка уже есть
git bisect good <хэш_хорошего_коммита> # Коммит, где ошибки еще не было
```
Git будет переключаться между коммитами. На каждом шаге проверяйте наличие ошибки и выполняйте `git bisect bad` или `git bisect good`. Когда проблемный коммит будет найден, завершите процесс:
```bash
git bisect reset
```

# V. Дополнительные инструменты и конфигурации

## 1. Игнорирование файлов

**`.gitignore`**: Создайте файл в корне проекта, чтобы исключить файлы и папки из отслеживания.

**Временное игнорирование отслеживаемых файлов:**
```bash
git update-index --assume-unchanged <файл> # Игнорировать изменения
git update-index --no-assume-unchanged <файл> # Вернуть отслеживание
```

## 2. Переписывание истории

**Внимание: эти команды изменяют историю. Не используйте их для коммитов, уже отправленных в общий репозиторий.**

Для удаления файла из всей истории (например, случайно закоммиченного секрета) рекомендуется использовать `git-filter-repo` вместо устаревшей `git filter-branch`.

```bash
# Пример для git-filter-repo
git filter-repo --path <путь_к_файлу> --invert-paths
```

## 3. Верификация коммитов (GPG)

Вы можете подписывать свои коммиты с помощью GPG-ключа для подтверждения их подлинности.
[Инструкция на Habr: Верификация коммитов GPG](https://habr.com/ru/articles/754128/)

## 4. Шифрование файлов (Git Crypt)

Расширение для шифрования конфиденциальных файлов.
1.  **Инициализация:** `git-crypt init`
2.  **Добавление GPG ключа:** `git-crypt add-gpg-user "ваш@email.com"`
3.  **Настройка шифрования:** Создайте файл `.gitattributes` и укажите, какие файлы шифровать (например, `secret.json filter=git-crypt diff=git-crypt`).
4.  **Блокировка/разблокировка:** `git-crypt lock` / `git-crypt unlock`.

## 5. Работа с большими файлами (Git LFS)

Расширение для хранения больших файлов вне основного репозитория.
```bash
git lfs install
git lfs track "*.psd" # Указать типы файлов для отслеживания
git add .gitattributes
```

## 6. Подпроекты (Submodules и Subtree)

*   **Submodule**: Ссылка на другой репозиторий. Полезно для зависимостей.
*   **Subtree**: Полное копирование истории другого репозитория в ваш.

## 7. Полезные настройки и псевдонимы

**Кэширование учетных данных для HTTPS:**
```bash
# Запомнить на 1 час
git config --global credential.helper 'cache --timeout=3600'
```

**Настройка Fast-forward слияния для `pull`:**
```bash
# Разрешить только fast-forward, чтобы избежать лишних merge-коммитов
git config --global pull.ff only
```

## 7. Автоматическая очистка истории с --fixup и --autosquash

В процессе работы над веткой часто возникают коммиты с мелкими исправлениями (например, "fix typo", "add log"). Такие коммиты "засоряют" историю, делая ее трудной для анализа. Для поддержания чистой и логичной истории коммитов перед слиянием ветки в main/develop рекомендуется объединять исправления с исходными коммитами.

Процесс можно автоматизировать с помощью флагов `git commit --fixup` и `git rebase --autosquash`.

⚠️ **Важно:** Этот метод, как и любой rebase, перезаписывает историю. Его следует применять только к локальным веткам, которые еще не были отправлены в общий репозиторий или над которыми не работают другие разработчики.

### Принцип работы

1.  `git commit --fixup <хэш_коммита>`
    Создает новый коммит с сообщением вида `fixup! <сообщение_старого_коммита>`. Этот коммит является исправлением для коммита, указанного через `<хэш_коммита>`.

2.  `git rebase -i --autosquash <базовый_коммит>`
    Запускает интерактивный rebase. Git автоматически обнаруживает `fixup!`-коммиты и перемещает их под соответствующими родительскими коммитами, помечая их действием `fixup`. Это позволяет объединить исправление с исходным коммитом, отбросив сообщение `fixup!`-коммита.

### Практический пример

#### 1. Исходная история коммитов
В ветке `mvp-server` есть два коммита.

```bash
$ git log --oneline
ab604f9 (HEAD -> mvp-server) feat: added handlers
dc4efa9 feat: listen port 8080
df9f0ae (main) mvp
```

#### 2. Обнаружение и исправление ошибки
В коде коммита `dc4efa9` была найдена опечатка: например, в файле `main.go` в логе использовалось слово `lisening` вместо `listening`.

Сначала мы исправляем эту ошибку в коде, а затем создаем `fixup`-коммит, нацеленный на исходный коммит с ошибкой.

```bash
# Исправляем опечатку в main.go
$ git add main.go
$ git commit --fixup dc4efa9
[mvp-server 62e7318] fixup! feat: listen port 8080
```
> **Примечание:** Если git-хуки мешают создать коммит с таким сообщением, используйте флаг `--no-verify`.

#### 3. Запуск автоматического rebase
Выполняется rebase относительно ветки `main` (или коммита `df9f0ae`, который является базовым для нашей работы).

```bash
$ git rebase -i --autosquash df9f0ae
```

Git откроет редактор с уже подготовленным планом:

```
pick dc4efa9 feat: listen port 8080
fixup 62e7318 fixup! feat: listen port 8080
pick ab604f9 feat: added handlers
```
Ничего менять не нужно. Достаточно сохранить и закрыть файл.

#### 4. Результат

Финальная история выглядит так, как будто коммита с исправлением никогда и не было, а изменения были внесены непосредственно в тот коммит, где была допущена ошибка. 

Если быть предельно точным с точки зрения Git, происходит следующее: rebase не изменяет старый коммит (коммиты в Git неизменяемы), а создает вместо него новый, который содержит объединенные изменения. Затем старый коммит удаляется из истории ветки.

```bash
$ git log --oneline
a72151f (HEAD -> mvp-server) feat: added handlers
0441501 feat: listen port 8080
df9f0ae (main) mvp
```

# VI. Git Hooks: Автоматизация проверок

Git Hooks — это скрипты, которые Git запускает автоматически при определенных событиях (коммит, пуш, мерж и т.д.). Они находятся в директории `.git/hooks` вашего репозитория.

Один из самых полезных хуков — `pre-push`. Он срабатывает перед отправкой коммитов на удаленный сервер, что делает его идеальным моментом для быстрой проверки кода.

## Преимущества использования Git Hooks

- **Экономия ресурсов CI/CD**: Простые проверки (синтаксис, поиск секретов) выполняются локально, не загружая CI/CD раннеры.
- **Стандартизация кода**: Обеспечивается соблюдение единых правил форматирования и качества кода для всей команды.
- **Предотвращение ошибок**: Снижается вероятность ошибок в основной ветке (`main`) или на продуктивном окружении.

## Примеры проверок для `pre-push` хука

- **Запуск линтеров**: `eslint`, `pylint`, `shellcheck`.
- **Проверка синтаксиса**: `python -m py_compile`, `terraform validate`.
- **Поиск закоммиченных секретов**: Использование инструментов вроде `truffleHog` или `git-secrets`.
- **Запуск модульных тестов**.
- **Проверка формата коммитов**.

```
