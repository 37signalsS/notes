# **История коммитов в git**

Мы можем ссылаться на коммит либо через его контрольную сумму, либо через его позицию относительно HEAD, например HEAD~4 ссылается на коммит, который находится 4 коммитами ранее HEAD.

Команда git revert <коммит> создаёт новый коммит, отменяющий изменения, но сохраняющий историю, в то время как git reset <коммит> перемещает указатель HEAD, предоставляя более чистую историю (будто этого коммита и не было вовсе).

Безвозвратно удаляет все локальные изменения и незакоммиченные файлы:

```sh
git reset --hard
```

Cбрасывает изменения локальной ветки до состояния удаленной ветки origin/main:

```sh
git reset --hard origin/main
```

# **Работа с ветками**

git branch <имя ветки> — создаёт новую ветку с HEAD, указывающим на HEAD. Если не передать аргумент `<имя ветки>`, то команда выведет список всех локальных веток.

```sh
git branch <имя ветки>
```

Создать новую вету которая будет точной копией другой ветки

```sh
git branch <имя_новой_ветки> <исходная ветка>
```

При создании нового репозитория можно указать какя ветка будет основной, например, develop

```sh
git init --initial-branch=develop
```

git checkout <имя ветки> — переключается на эту ветку. Можно передать опцию `-b`, чтобы создать новую ветку перед переключением.

```sh
git checkout <имя ветки>
```

Однако, для переключения между ветками (`checkout`) лучше использовать:

```sh
git switch <имя ветки>
```

Удалить ветку(но только если она полностью слита (merge) в текущую ветку или в основную ветку), но если изменения не нужны то используем флаг -D, который принудительно удаляет ветку:

```sh
git branch -d <имя ветки>
```

Привязать текущую ветку к указанной удалённой ветке:

```sh
git branch -u <имя удалённого репозитория>/<удалённая ветка>
```

Создать новую локальную ветку и начинает отслеживать удалённую:

```sh
git checkout -b <ветка> <имя удалённого репозитория>/<удалённая ветка>
```

Показывает локальные и отслеживаемые удалённые ветки:

```sh
git branch -vv
```

Показывает все ветки, включая удалённые:

```sh
git branch -a
```

Создать локальную ветку с таким же именем, как у удалённой, и начинает её отслеживать:

```sh
git checkout <удалённая ветка>
```

При создании новой ветки можно сразу указать, что она должна отслеживать удалённую:

```sh
git checkout --track origin/<удаленная_ветка>
```

# **Merge**

Слияние включает в себя создание нового коммита, который основан на общем коммите-предке двух ветвей и указывает на оба HEAD в качестве предыдущих коммитов.

Для слияния мы переходим на основную ветку и используем команду git merge <ветка которую хотим "добавить">.

Флаг --allow-unrelated-histories разрешает слияние, даже если истории коммитов двух репозиториев или веток не связаны. Или это можент пригодиться в случае если вы создали новый репозиторий и хотите добавить в него файлы из другого репозитория, но без общей истории.

# **Объединение нескольких коммитов(merge commit rebase commit)**

Покажет, какие коммиты были сделаны в сравнение с веткой master.

``` sh

```

``` sh
git rebase -i HEAD ~3
```

Ключ i означает работу в интерактивном режиме, а HEAD ~3 —что объединяться будут последние 3 коммита.

pick — это первый коммит.

squash — коммиты, которые вы будете сливать с первым (меняем pick на squash для коммитов которых хоти объединить, кроме первого).

# **Сжатие коммитов при слиянии веток(commit):**

Объединяет изменения из ветки в один коммит, не перенося историю всех промежуточных коммитов

``` sh
git merge --squash feature-branch
```

Отменяет слияние, вернув репозиторий в состояние до начала слияния


# **Просмотр изменений(git log)**

`-p` — показывает изменения в каждом коммите.

```sh
git log -p
```

`--stat` — показывает сокращённую статистику для коммитов.

```sh
git log --stat
```

`-n` — показывает `n` последних коммитов.

```sh

```

`--since=___` и `--until=___` позволяют фильтровать коммиты по дате. Например, покажет коммиты с 1 января 2019 года.

```sh

```

`--pretty` позволяет указать формат логов (например, `--pretty=oneline`). Также можно использовать `--pretty=format` для большей кастомизации.

```sh
git log --pretty=oneline
git log --pretty=format:"%h %s"
```

`--grep` и `-S` позволяют искать коммиты по содержимому. Например, позволяет посмотреть добавление/удаление функции.

```sh

```

--no-merges исключает коммиты слияния. Например, покажет, каких коммитов из ветки `test` нет в `master`.


--name-only добавляет к выводу истории имена изменённых файлов.

```sh
git log --name-only
```

Можно сочетать с `-n`, например, выведет три последних коммита с именами изменённых файлов.

```sh

```

Найти последний коммит, связанный с изменением файла data.json, и вывести его комментарий
```sh

```

Если у вас есть незавершённые изменения, которые нельзя фиксировать, их можно сохранить и «спрятать» с помощью команды `git stash`.

# **Как отменить последний коммит?(commit)**

**По умолчанию git reset использует флаг --mixed - убрать изменения из индекса, но оставить изменения в файлах которые были сделанны до/после выбранного коммита(пример - история коммитов A <- B <- C <- D <- E (HEAD), изменения из коммитов C, D, E остаются в рабочей директории, при откате на 3 коммита назад)**

--hard - удалить изменения в файлах и уберет изменения из индекса

``` sh
git reset --hard HEAD~1
```

HEAD ~ 1 означает один коммит до HEAD, т.е. до текущего положения.

Если нужно сохранить изменения в индексе для нового коммита, и оставить изменения в файлах(пример тот же что и в --mixed):

``` sh
git reset --soft HEAD ~1
```

НО, можно также использовать для отката комиита

``` sh
git restore --source HEAD~1 название_файла
```

# **Fast-forward (FF) слияние**

Fast-forward (FF) — это тип слияния, который применяется, если локальная ветка находится прямо "позади" удалённой. В таком случае коммит-история просто "перематывается" вперёд, добавляя недостающие коммиты из удалённой ветки. При этом не создаётся дополнительного merge-коммита.

Чтобы использовать только fast-forward при `git pull`:

```sh
git config pull.ff only
```

# **Работа с аннотированными тегами**

Аннотированными (или аннотируемыми) называются такие метки, которые содержат полную информацию о версии, включая имя и e-mail разработчика, а также дату и время создания.

Создать аннотированный тег:

```sh
git tag -a ver-2.5 a7d3f1c  -m "beta version 2.5"
```

- `git tag` — основная команда для работы с метками;
- `-a` — параметр для создания аннотированного тега, за которым следует его идентификатор;
- `a7d3f1c` - хеш коммита, для которого создается тег (не HEAD)
- `-m` — добавляет комментарий.

Вывести данные тега вместе с коммитом:

```sh
git show ver-2.5
```

Добавить тег в удалённый репозиторий:

```sh
git push origin ver-2.5
```

Удалить тег из удалённого репозитория:

```sh
git push origin --delete ver-2.5
```

# **Submodule**

Это механизм Git, позволяющий включать один репозиторий в другой как подпроект, сохраняя их независимую историю. Подмодули по сути являются ссылкой на конкретный коммит в другом репозитории. При клонировании репозиториев с подмодулями подмодули необходимо скачивать отдельно. Если исходный репозиторий перемещен или станет недоступным, папки подмодулей будут пустыми после клонирования.

Добавление существующего репо как подмодуля - git submodule add ссылка, подмодуль-репо будет в виде директории в родительском репо

Изменения в подмодуле не будут отслеживаться, например, при помощи git diff пока не зайдешь в директорию(но можно добавить --submodule)

Клонирование проекта с подмодулями - git clone основного_репо, git submodele init, git submodele update

Обновление подмодуля - git submodule update --remote имя_подмодуля (обнова из master), если нужна другая ветка - git config -f .gitmodules submodule.имя_подмодуля.branch имя_ветки

Обновление основного репо - git submodule update --init --recursive

# **Subtree**

Git Subtree предпочтительнее, когда вы хотите интегрировать внешний код в свой репозиторий и рассматривать его как часть своего проекта. Это полезно в случаях, когда вам нужно внести изменения во внешний код в рамках разработки вашего проекта. 

Добавление подпроекта
```sh
git subtree add --prefix=<локальный_каталог> <URL_репозитория> <ветка>
```
Обновление подпроекта
```sh
git subtree pull --prefix=<локальный_каталог> <URL_репозитория> <ветка>
```
Добавление удаленного репозитория:
```sh
git remote add -f <имя_удаленного> <URL_репозитория>
```
Использование удаленного репозитория для подпроекта:
```sh
git subtree add --prefix=<локальный_каталог> <имя_удаленного> <ветка>
```
