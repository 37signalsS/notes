# Управление ресурсами: Requests, Limits и QoS

Kubernetes позволяет точно управлять ресурсами CPU и памяти, которые выделяются контейнерам. Это достигается с помощью полей `requests` и `limits` в спецификации контейнера и приводит к назначению подам определенных классов качества обслуживания (QoS).

---

### Requests и Limits

*   **`requests` (Запросы):**
    *   **CPU:** Минимальное количество CPU, которое Kubernetes *гарантирует* контейнеру. Используется планировщиком для выбора подходящего узла.
    *   **Memory:** Минимальный объем памяти, который *гарантируется* контейнеру.

*   **`limits` (Лимиты):**
    *   **CPU:** Максимальное количество CPU, которое контейнер может использовать. Если контейнер пытается использовать больше, его CPU будет "троттлиться" (искусственно замедляться).
    *   **Memory:** Максимальный объем памяти, который контейнер может использовать. Если контейнер превышает этот лимит, он будет завершен (OOMKilled).

**Единицы измерения:**
*   **CPU:** Измеряется в "milliCPU" (m) или долях ядра. `1000m` эквивалентно `1` ядру vCPU/Core.
*   **Память:** Измеряется в байтах. Можно использовать суффиксы `Ki`, `Mi`, `Gi` (кибибайты, мебибайты, гибибайты).

---

### QoS (Quality of Service) Classes

На основе установленных `requests` и `limits` Kubernetes присваивает подам один из трех классов QoS, которые влияют на то, какие поды будут завершены первыми в случае нехватки ресурсов на узле.

1.  **`Guaranteed` (Гарантированный):**
    *   **Условия:** Каждый контейнер в поде должен иметь `requests` и `limits` для CPU и памяти, и они должны быть равны (`requests.cpu == limits.cpu` и `requests.memory == limits.memory`).
    *   **Приоритет:** Самый высокий. Эти поды будут завершены в последнюю очередь.

2.  **`Burstable` (Эластичный):**
    *   **Условия:** Хотя бы у одного контейнера в поде есть `requests`, но они не равны `limits`. Либо у некоторых контейнеров ресурсы не указаны вовсе.
    *   **Приоритет:** Средний. Поды могут использовать больше ресурсов, чем запрошено (до `limits`), если они доступны. Будут завершены после подов `BestEffort`.

3.  **`BestEffort` (Наилучшее усилие):**
    *   **Условия:** Ни у одного контейнера в поде не указаны ни `requests`, ни `limits`.
    *   **Приоритет:** Самый низкий. Эти поды получают ресурсы только по остаточному принципу и будут завершены первыми при нехватке ресурсов.

---

### Пример

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: qos-example
spec:
  containers:
    # QoS Class: Guaranteed
    - name: guaranteed-container
      image: nginx
      resources:
        requests:
          memory: "100Mi"
          cpu: "100m"
        limits:
          memory: "100Mi"
          cpu: "100m"

    # QoS Class: Burstable
    - name: burstable-container
      image: nginx
      resources:
        requests:
          memory: "128Mi"  # Минимальный объем памяти, который требуется контейнеру
          cpu: "250m"      # Минимальный объем процессорного времени(милицпу, в кубере проц это 100 милицпу) 
        limits:
          memory: "200Mi"

    # QoS Class: BestEffort
    - name: besteffort-container
      image: nginx
      # Нет requests и limits
```
