# Horizontal Pod Autoscaler (HPA): Автоматическое масштабирование приложений

**Horizontal Pod Autoscaler (HPA)** — это контроллер Kubernetes, который работает как термостат для вашего приложения. Он автоматически увеличивает или уменьшает количество подов в ответ на изменение нагрузки, обеспечивая эластичность, производительность и экономию ресурсов.

Вместо того чтобы вручную добавлять реплики в моменты пиковой нагрузки и убирать их ночью, вы позволяете HPA делать это за вас.

---

## Как HPA принимает решения?

HPA работает в цикле. Периодически (по умолчанию каждые 15 секунд) он запрашивает метрики у **Metrics Server**, сравнивает их с целевыми значениями и рассчитывает необходимое количество реплик по формуле:

`желаемыеРеплики = ceil(текущиеРеплики * ( текущаяМетрика / желаемаяМетрика ))`

**Пример:**
*   `текущиеРеплики`: 3
*   `желаемаяМетрика` (цель по CPU): 50%
*   `текущаяМетрика` (реальная нагрузка): 90%

`желаемыеРеплики = ceil(3 * (90 / 50)) = ceil(3 * 1.8) = ceil(5.4) = 6`

HPA увеличит количество реплик с 3 до 6.

## Анатомия манифеста HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: my-app-hpa
  namespace: default
spec:
  # 1. Ссылка на масштабируемый ресурс (Deployment, StatefulSet)
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: my-app

  # 2. Границы масштабирования
  minReplicas: 2
  maxReplicas: 10

  # 3. Метрики для принятия решений
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization # Тип цели — среднее использование
          averageUtilization: 50 # Целевой порог в 50%
    - type: Resource
      resource:
        name: memory
        target:
          type: AverageValue # Тип цели - среднее значение
          averageValue: 200Mi # Целевое значение в 200 мебибайт

  # 4. (Опционально) Поведение при масштабировании
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0
      policies:
      - type: Percent
        value: 100
        periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Pods
        value: 2
        periodSeconds: 60
```

1.  **`scaleTargetRef`**: Указывает, каким `Deployment` или `StatefulSet` будет управлять HPA.
2.  **`minReplicas` / `maxReplicas`**: Задает границы. HPA никогда не опустит количество подов ниже `minReplicas` и не поднимет выше `maxReplicas`.
3.  **`metrics`**: Список метрик. HPA будет рассчитывать необходимое количество реплик для *каждой* метрики и выберет **наибольшее** из полученных значений.
4.  **`behavior`**: Позволяет тонко настроить скорость масштабирования, чтобы избежать "дребезжания" (быстрого увеличения и уменьшения реплик). Например, можно настроить HPA на быстрое добавление подов при росте нагрузки и на медленное, осторожное их удаление при спаде.

## Предварительные требования для работы HPA

Чтобы HPA функционировал корректно, необходимо выполнить два условия:

1.  **Установить Metrics Server:** Для работы с базовыми метриками (`cpu`, `memory`) в кластере должен быть развернут компонент **Metrics Server**. Он собирает данные о потреблении ресурсов с каждого узла и предоставляет их HPA.

2.  **Задать запросы (requests) для контейнеров:** Чтобы HPA мог корректно рассчитывать утилизацию CPU в процентах, у контейнеров в вашем `Deployment` должны быть установлены запросы на ресурсы (`spec.containers.resources.requests`).
    ```yaml
    resources:
      requests:
        cpu: "200m" # 200 милли-ядер
        memory: "256Mi"
    ```
    Без этого HPA не знает, от какого базового значения считать процент.

## Масштабирование за пределами CPU и Memory

HPA может работать не только с CPU и памятью. С помощью адаптеров (например, Prometheus Adapter) его можно настроить на масштабирование по:

*   **Кастомным метрикам (Custom Metrics):** Метрики, связанные с подами. Например, количество запросов в секунду (RPS) на под.
*   **Внешним метрикам (External Metrics):** Метрики из внешних систем. Например, длина очереди в RabbitMQ или Kafka.

Это позволяет создавать более сложные и точные правила масштабирования, основанные на реальных бизнес-показателях вашего приложения.

## Лучшие практики

*   **Настройте `behavior`:** Чтобы предотвратить слишком агрессивное масштабирование вниз при кратковременных провалах нагрузки, установите `stabilizationWindowSeconds` для `scaleDown` (например, 300 секунд).
*   **Выбирайте правильную метрику:** Для I/O-bound приложений (например, веб-серверы) масштабирование по CPU может быть неэффективным. Рассмотрите кастомные метрики, такие как RPS.
*   **Не используйте HPA и VPA вместе для одной метрики:** Не пытайтесь одновременно автоматически масштабировать количество подов (HPA) и ресурсы для них (VPA) по одной и той же метрике (например, CPU). Это может привести к конфликтам.
