# Service

## 1. Что такое Service?

**Service** — это абстракция Kubernetes, которая определяет логическую группу `Pod`-ов и политику доступа к ним. Он предоставляет **стабильную сетевую точку входа** (IP-адрес и DNS-имя), которая не меняется, даже если `Pod`-ы, стоящие за ней, перезапускаются или перемещаются.

Основная задача `Service` — решить проблему непостоянства `Pod`-ов. `Pod`-ы могут быть уничтожены и созданы заново, получая новые IP-адреса. `Service` обеспечивает постоянный адрес, на который могут полагаться другие компоненты системы.

Связь между `Service` и `Pod`-ами устанавливается с помощью **меток и селекторов** (`labels` и `selectors`).

## 2. Service Discovery и kube-proxy

Kubernetes предлагает два основных способа обнаружения сервисов:

*   **DNS:** Внутренний DNS-сервер кластера (например, CoreDNS) создает A/AAAA-записи для каждого `Service`. Любой `Pod` в том же `namespace` может обратиться к сервису просто по его имени (например, `my-service`). `Pod` из другого `namespace` может использовать `my-service.namespace-name.svc.cluster.local`. **Это рекомендуемый способ.**
*   **Переменные окружения:** Когда `Pod` создается, `kubelet` добавляет в него переменные окружения для каждого активного `Service`. Этот метод имеет ограничения, например, `Pod` не получит переменные для `Service`, созданного после него.

За маршрутизацию трафика от `Service` к нужным `Pod`-ам отвечает компонент **`kube-proxy`**, который работает на каждом узле. Он использует один из режимов:
*   `iptables` (стандартный): настраивает правила `iptables` для перехвата и перенаправления трафика.
*   `ipvs`: использует IPVS (IP Virtual Server) для более производительной балансировки.
*   `userspace` (устарел).

## 3. Типы сервисов

### `ClusterIP`
*   **Описание:** Предоставляет внутренний IP-адрес, доступный **только внутри кластера**. Это тип **по умолчанию**.
*   **Использование:** Для внутренней коммуникации между компонентами приложения (например, бэкенд обращается к базе данных или кэшу).

### `NodePort`
*   **Описание:** Открывает статический порт (`NodePort`) в диапазоне 30000-32767 на **каждом узле** кластера. Трафик, приходящий на `NodeIP:NodePort`, перенаправляется на `Service`.
*   **Использование:** Для предоставления внешнего доступа к сервису на время разработки, для демо или для приложений, не требующих сложной балансировки.

### `LoadBalancer`
*   **Описание:** Создает внешний балансировщик нагрузки у облачного провайдера (AWS, GCP, Azure) и направляет трафик с него на `Service`. Является расширением `NodePort` и `ClusterIP` (трафик сначала попадает на `NodePort`, а затем на `ClusterIP`).
*   **Использование:** Стандартный способ публикации сервисов в интернет в облачных средах.

### `ExternalName`
*   **Описание:** Не проксирует трафик. Вместо этого создает **CNAME-запись** во внутреннем DNS, которая указывает на внешний сервис (например, `my.database.example.com`).
*   **Использование:** Для доступа к внешним сервисам изнутри кластера по внутреннему имени, чтобы скрыть реальный адрес и упростить конфигурацию.

### `Headless`
*   **Описание:** `Service` без `ClusterIP` (`spec.clusterIP: None`). Вместо проксирования и балансировки, DNS-запрос к такому сервису возвращает **IP-адреса всех `Pod`-ов**, подпадающих под селектор.
*   **Использование:** Для сценариев, где требуется прямое подключение к конкретным `Pod`-ам, например, для баз данных в `StatefulSet` или систем мониторинга.

## 4. Сводка по типам сервисов

| Тип             | Доступность                  | IP-адрес                               | Основной сценарий                               |
|-----------------|------------------------------|----------------------------------------|-------------------------------------------------|
| **`ClusterIP`** | Только внутри кластера       | Стабильный внутренний IP               | Внутренние коммуникации (backend-to-db)         |
| **`NodePort`**  | Внутри и снаружи кластера    | Через `IP_узла:NodePort`               | Разработка, отладка, простые внешние сервисы    |
| **`LoadBalancer`**| Из интернета                 | Внешний IP от облачного провайдера     | Публикация приложений в облаке                  |
| **`ExternalName`**| - (только DNS)               | - (CNAME на внешний ресурс)            | Доступ к внешним сервисам по внутреннему имени  |
| **`Headless`**  | Прямой доступ к `Pod`-ам     | IP-адреса `Pod`-ов через DNS           | Stateful-приложения (например, с `StatefulSet`) |

## 5. Пример: Service типа `NodePort`

Этот манифест создает `Service`, который находит все `Pod`-ы с меткой `app: my-app` и предоставляет к ним доступ.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-app-service
spec:
  # 1. Тип сервиса. Если не указан, по умолчанию используется ClusterIP.
  type: NodePort

  # 2. Селектор для выбора Pod'ов, на которые пойдет трафик.
  #    Должен соответствовать меткам в шаблоне Deployment, ReplicaSet и т.д.
  selector:
    app: my-app

  # 3. Описание портов.
  ports:
    - name: http
      protocol: TCP
      # port: Внутренний порт, на котором Service принимает трафик внутри кластера.
      port: 80
      # targetPort: Порт на Pod'ах, куда будет перенаправляться трафик.
      targetPort: 8080
      # nodePort: Статический порт на узлах (только для типа NodePort).
      # Если не указать, будет выбран случайный из диапазона 30000-32767.
      nodePort: 30080
```

**Как это работает:**
1.  Трафик, отправленный на `любой_узел_кластера:30080`, будет принят.
2.  `kube-proxy` перенаправит этот трафик на внутренний IP-адрес `Service` на порт `80`.
3.  `Service` выберет один из `Pod`-ов с меткой `app: my-app` и отправит трафик на его порт `8080`.
