# Affinity и Anti-Affinity в Kubernetes

**Affinity** и **Anti-Affinity** — это мощные механизмы Kubernetes, которые позволяют детально управлять размещением подов на узлах кластера. Они являются более гибкой альтернативой `nodeSelector` и позволяют задавать сложные правила привязки.

## Ключевые концепции

Правила Affinity состоят из двух частей: типа правила и фазы выполнения.

#### Типы правил:
*   `requiredDuringScheduling...` — **жесткое правило**. Планировщик разместит под, только если правило выполнено. Если подходящих узлов нет, под останется в состоянии `Pending`.
*   `preferredDuringScheduling...` — **мягкое правило**. Планировщик пытается выполнить правило, но если это невозможно, под будет размещен на любом другом доступном узле. Каждому правилу присваивается вес (`weight` от 1 до 100) для определения приоритета.

#### Фазы выполнения:
*   `...IgnoredDuringExecution` — правило учитывается **только в момент планирования**. Если метки на узле или на других подах изменятся после запуска пода, это никак на него не повлияет.
*   `...RequiredDuringExecution` (доступно только для Node Affinity) — правило **продолжает действовать** после запуска. Если метки на узle изменятся и перестанут удовлетворять правилу, Kubernetes попытается выселить (evict) под с этого узла.

---

## 1. Node Affinity (Привязка к узлам)

Позволяет размещать поды на узлах с определёнными метками.

**Основные операторы:**
*   `In`: Значение метки должно совпадать с одним из указанных.
*   `NotIn`: Значение метки не должно совпадать ни с одним из указанных.
*   `Exists`: Узел должен иметь метку с указанным ключом (значение не важно).
*   `DoesNotExist`: Узел не должен иметь метку с указанным ключом.
*   `Gt`: Значение метки (интерпретируемое как число) должно быть больше указанного.
*   `Lt`: Значение метки (интерпретируемое как число) должно быть меньше указанного.

---

## 2. Pod Affinity / Anti-Affinity (Привязка к подам)

Позволяет размещать поды в зависимости от того, где уже запущены другие поды.

*   **Pod Affinity:** Размещает поды вместе.
    *   **Сценарий:** Приложение и его кэш (например, Redis) должны находиться как можно ближе для минимизации сетевой задержки.
*   **Pod Anti-Affinity:** Размещает поды раздельно.
    *   **Сценарий:** Обеспечение высокой доступности. Реплики одного сервиса должны быть распределены по разным узлам или зонам доступности, чтобы сбой одного узла не вывел из строя весь сервис.

#### `topologyKey`
Этот ключ определяет "область" применения правила — узел, зону доступности, регион и т.д. Планировщик будет искать поды с нужными метками в пределах этой топологии.
*   `kubernetes.io/hostname`: Область — один узел.
*   `topology.kubernetes.io/zone`: Область — одна зона доступности.
*   `topology.kubernetes.io/region`: Область — один регион.

## Комплексный пример

Рассмотрим Deployment веб-приложения со следующими требованиями:
1.  **Жесткое:** Поды должны работать только на узлах с быстрыми дисками (`disktype: ssd`).
2.  **Мягкое:** Желательно размещать поды в зоне доступности `eu-central-1a`.
3.  **Мягкое (Anti-Affinity):** Для высокой доступности реплики этого же приложения должны быть распределены по разным узлам.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      affinity:
        # 1. Node Affinity: привязка к узлам
        nodeAffinity:
          # Жесткое правило: под будет запущен ТОЛЬКО на узле с меткой disktype=ssd.
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
              - matchExpressions:
                  - key: disktype
                    operator: In
                    values:
                      - ssd
          # Мягкое правило: планировщик будет стараться запустить под в указанной зоне.
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100 # Правило с наивысшим приоритетом
              preference:
                matchExpressions:
                  - key: topology.kubernetes.io/zone
                    operator: In
                    values:
                      - east
                  # - key: another-label
                  #   operator: Exists # Оператор Exists означает, что под будет запущен на узле, если у него есть метка 'another-label' (значение не важно).

        # 2. Pod Affinity: привязка к другим подам
        podAffinity:
          # Жесткое правило: запускать этот под на том же узле, где уже есть под с меткой app=database.
          requiredDuringSchedulingIgnoredDuringExecution:
            - labelSelector:
                matchExpressions:
                  - key: app
                    operator: In
                    values:
                      - database
              # topologyKey определяет "область" применения правила.
              # kubernetes.io/hostname означает, что поды должны быть на одном и том же узле.
              topologyKey: kubernetes.io/hostname

        # 3. Pod Anti-Affinity: избегание других подов
        podAntiAffinity:
          # Мягкое правило: стараться не запускать поды этого Deployment'а на одном и том же узле.
          preferredDuringSchedulingIgnoredDuringExecution:
            - weight: 100
              podAffinityTerm:
                labelSelector:
                  matchExpressions:
                    - key: app
                      operator: In
                      values:
                        - web-app
                # Разделяем поды в пределах одного узла
                topologyKey: kubernetes.io/hostname
      containers:
        - name: web-server
          image: nginx:latest
          ports:
            - containerPort: 80
```

## Рекомендации и лучшие практики

*   **Высокая доступность:** Всегда используйте `podAntiAffinity` для stateless-приложений, чтобы распределить их реплики по разным узлам (`topologyKey: kubernetes.io/hostname`) или зонам (`topologyKey: topology.kubernetes.io/zone`).
*   **Производительность:** Используйте `podAffinity` для компонентов, которые интенсивно обмениваются данными (например, приложение и кэш).
*   **Специализированное оборудование:** Используйте `nodeAffinity` для подов, требующих специфического оборудования (GPU, TPU) или определённых версий ОС.
*   **Надежность:** Отдавайте предпочтение мягким правилам (`preferred...`) перед жесткими (`required...`), чтобы избежать ситуации, когда поды не могут быть запланированы из-за отсутствия подходящих узлов.
