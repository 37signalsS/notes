# Ingress

## 1. Что такое Ingress?

**Ingress** — это объект API Kubernetes, который управляет внешним доступом к сервисам в кластере, как правило, по протоколам **HTTP** и **HTTPS**. Он действует как "умный" маршрутизатор или точка входа, позволяя определять правила маршрутизации трафика на основе имени хоста (например, `api.example.com`) или пути (например, `/v1/users`).

Ingress является высокоуровневой абстракцией, которая позволяет централизованно управлять доступом к множеству сервисов через единый IP-адрес.

## 2. Роль Ingress-контроллера

**Ingress не работает сам по себе.** Для его функционирования в кластере должен быть установлен и запущен **Ingress-контроллер**.

**Ingress-контроллер** — это приложение (обычно работающее как `Deployment`), которое отслеживает объекты `Ingress` в API-сервере Kubernetes и настраивает нижележащий прокси-сервер или балансировщик нагрузки в соответствии с правилами, описанными в этих объектах.

## 3. Схема работы: Путь трафика в Kubernetes

Представьте, что вы заходите в большой офисный центр:
*   **Ingress Controller** — это главный ресепшен на входе в здание.
*   **Service** — это внутренний номер отдела (например, "Отдел продаж, доб. 205").
*   **Pod** — это конкретный сотрудник за своим столом в этом отделе.

Вот как запрос проходит через всю цепочку: `Внешний мир -> Ingress Controller -> Service -> Pod`.

#### Шаг 1: Внешний трафик поступает в кластер

1.  **Пользователь** открывает в браузере сайт `https://my-app.com/path`.
2.  **DNS** преобразует домен `my-app.com` во внешний IP-адрес. Этот IP-адрес принадлежит внешнему балансировщику нагрузки (LoadBalancer), который облачный провайдер создал для службы Ingress Controller.
3.  Трафик попадает на этот внешний IP и перенаправляется на один из узлов (Node) вашего Kubernetes-кластера на определенный порт (`NodePort`).

#### Шаг 2: Ingress Controller (Ресепшен)

1.  На узле кластера запрос принимает **под Ingress Controller'а** (например, Nginx, Traefik). Это обычный веб-сервер, запущенный в кластере и настроенный на прием внешнего трафика.
2.  Ingress Controller смотрит на запрос:
    *   **Хост:** `my-app.com`
    *   **Путь:** `/path`
3.  Он анализирует все **ресурсы `Ingress`** (YAML-файлы с правилами), которые вы создали в кластере. Он ищет правило, которое соответствует этому хосту и пути.
4.  Найдя подходящее правило, Ingress Controller видит, на какой **`Service`** нужно перенаправить этот запрос. Например, правило может гласить: "Все запросы для `my-app.com/path` отправляй на сервис `my-app-service` на порт `80`".

#### Шаг 3: Service (Внутренний номер отдела)

1.  Ingress Controller не отправляет трафик напрямую в под. Он отправляет его на внутренний, стабильный IP-адрес сервиса — **ClusterIP**. Этот IP-адрес доступен только внутри кластера.
2.  **`Service`** — это абстракция. У него нет своего процесса, который принимает трафик. Его основная задача — постоянно отслеживать поды, у которых есть определенная метка (label), например, `app: my-app`.
3.  `Service` хранит список IP-адресов всех здоровых подов, соответствующих его селектору. Этот список называется **Endpoints**.

#### Шаг 4: От Service к поду (Магия `kube-proxy`)

Здесь в игру вступает `kube-proxy` — системный компонент, который работает на **каждом узле** кластера.

1.  `kube-proxy` видит, что Ingress Controller отправил пакет на виртуальный ClusterIP сервиса `my-app-service`.
2.  `kube-proxy` смотрит в список **Endpoints** для этого сервиса и выбирает IP-адрес одного из реальных, работающих подов.
3.  С помощью правил `iptables` (или `IPVS`) на уровне ядра операционной системы узла, `kube-proxy` "на лету" подменяет IP-адрес назначения (с ClusterIP сервиса на реальный IP пода) и перенаправляет пакет.

#### Шаг 5: Pod (Сотрудник за столом)

1.  Сетевой пакет, пройдя все эти этапы, наконец-то достигает конкретного пода.
2.  Контейнер с вашим приложением, работающий внутри пода, получает запрос, обрабатывает его и отправляет ответ.
3.  Ответ проходит весь путь в обратном порядке и доставляется пользователю.

## 4. Правила маршрутизации (Routing Rules)

### A. Маршрутизация по хосту (Host-based)

Можно направлять трафик с разных доменов на разные сервисы.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: multi-host-ingress
spec:
  rules:
    - host: "foo.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: foo-service
                port:
                  number: 80
    - host: "bar.example.com"
      http:
        paths:
          - pathType: Prefix
            path: "/"
            backend:
              service:
                name: bar-service
                port:
                  number: 80
```

### B. Маршрутизация по пути (Path-based)

Трафик одного домена можно направлять на разные сервисы в зависимости от пути.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: my-app-ingress
spec:
  rules:
    - host: "myapp.example.com"
      http:
        paths:
          - path: /api
            pathType: Prefix
            backend:
              service:
                name: api-service
                port:
                  number: 8080
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend-service # Имя сервиса, на который пойдет трафик
                port:
                  number: 80 # Порт этого сервиса
```
*   `pathType: Prefix` — соответствует любому пути, который начинается с указанного значения (например, `/api/v1`, `/api/v2`).
*   `pathType: Exact` — соответствует только точно указанному пути.

### C. Хост по умолчанию (Default Backend)

Можно определить сервис, который будет обрабатывать весь трафик, не соответствующий ни одному из правил.

```yaml
spec:
  defaultBackend:
    service:
      name: default-service
      port:
        number: 80
  rules:
    # ... правила ...
```

## 5. Настройка TLS/SSL

Ingress упрощает терминирование TLS-трафика.

1.  **Создайте `Secret` с сертификатом и ключом:**
    ```bash
    kubectl create secret tls my-app-tls-secret --cert=path/to/tls.crt --key=path/to/tls.key
    ```

2.  **Укажите этот `Secret` в манифесте Ingress:**

    ```yaml
    apiVersion: networking.k8s.io/v1
    kind: Ingress
    metadata:
      name: my-app-ingress
    spec:
      tls:
        - hosts:
            - myapp.example.com
          secretName: my-app-tls-secret # Имя секрета с сертификатом
      rules:
        - host: myapp.example.com
          http:
            paths:
              - path: /
                pathType: Prefix
                backend:
                  service:
                    name: my-app-service
                    port:
                      number: 80
    ```
Теперь трафик по `https://myapp.example.com` будет зашифрован.

## 6. Аннотации (Annotations)

Аннотации — это основной способ тонкой настройки поведения Ingress-контроллера. Они специфичны для каждого типа контроллера.

**Примеры для NGINX Ingress Controller:**
*   `nginx.ingress.kubernetes.io/rewrite-target: /` — перенаправляет трафик с указанного `path` на корневой путь (`/`) сервиса.
*   `nginx.ingress.kubernetes.io/ssl-redirect: "true"` — принудительно перенаправляет HTTP-трафик на HTTPS.
*   `nginx.ingress.kubernetes.io/proxy-body-size: "8m"` — устанавливает максимальный размер тела запроса.
*   `kubernetes.io/ingress.class: "nginx"` — указывает, какой Ingress-контроллер должен обрабатывать этот объект (актуально, если в кластере их несколько).
