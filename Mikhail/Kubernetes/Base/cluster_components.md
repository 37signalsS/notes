# Архитектура кластера Kubernetes: От Control Plane до Worker Node

Представьте кластер Kubernetes как слаженный оркестр. У него есть дирижер, который всем управляет (**Control Plane**), и музыканты, которые исполняют партию (**Worker Nodes**). Каждый компонент играет свою уникальную роль, обеспечивая стабильную и согласованную работу всей системы.

---

## Компоненты Control Plane (Управляющая плоскость)

Это мозг кластера. Control Plane принимает глобальные решения, отслеживает состояние всех объектов и реагирует на события. Для высокой доступности его компоненты могут быть реплицированы на нескольких мастер-узлах.

### 1. `etcd`
*   **Роль:** **Память и единственный источник правды кластера.**
*   **Описание:** Это надежное, согласованное и распределенное хранилище типа "ключ-значение". В `etcd` записано *всё* состояние кластера: конфигурации, спецификации и текущие статусы всех объектов. Любое изменение в кластере начинается с записи в `etcd`. Резервное копирование `etcd` является критически важной задачей.

### 2. `kube-apiserver` (API-сервер)
*   **Роль:** Центральный компонент и "фронтенд" управляющей плоскости.
*   **Ключевые функции:**
    *   Предоставляет HTTP/HTTPS API, через которое взаимодействуют все остальные компоненты, пользователи (`kubectl`) и внешние системы.
    *   Валидирует и обрабатывает все REST-запросы на изменение состояния объектов (создание пода, обновление сервиса и т.д.).
    *   Является **единственным компонентом**, который напрямую взаимодействует с `etcd`.

### 3. `kube-scheduler` (Планировщик)
*   **Роль:** **Диспетчер или логист.**
*   **Описание:** Его задача — назначать новосозданные поды на подходящие рабочие узлы. Он отслеживает поды без назначенного узла (`spec.nodeName`), анализирует их требования (ресурсы, `affinity`, `tolerations`) и состояние узлов, выбирая оптимальное место для запуска. Он не запускает под, а лишь решает, *где* он будет запущен.

### 4. `kube-controller-manager` (Менеджер контроллеров)
*   **Роль:** **Команда менеджеров-контроллеров.**
*   **Описание:** Это один процесс, который для эффективности объединяет в себе множество контроллеров. Каждый контроллер — это фоновый цикл, который следит за определенным аспектом кластера и приводит текущее состояние к желаемому (записанному в `etcd`).
    *   **Node Controller:** Реагирует на отказы узлов.
    *   **Deployment/ReplicaSet Controller:** Поддерживает заданное количество реплик пода.
    *   **Endpoints Controller:** Обновляет объект `Endpoints`, связывая `Service` с IP-адресами подов.

## Компоненты Worker Node (Рабочий узел)

Это машины, на которых непосредственно выполняются ваши приложения. Они управляются Control Plane и содержат все необходимое для запуска контейнеров.

### 1. `kubelet`
*   **Роль:** Главный агент Kubernetes на каждом рабочем узле.
*   **Ключевые функции:**
    *   Регистрирует узел в кластере, получая инструкции от `API-сервера`.
    *   Гарантирует, что контейнеры, описанные в спецификациях подов, запущены и работают корректно.
    *   Взаимодействует со средой выполнения контейнеров (например, `containerd`) для управления жизненным циклом контейнеров.
    *   Выполняет пробы (`liveness`, `readiness`, `startup`).
    *   Передаёт `API-серверу` отчеты о состоянии узла и подов.

### 2. `kube-proxy`
*   **Роль:** Сетевой прокси, отвечающий за реализацию сетевой модели Kubernetes на каждом узле.
*   **Ключевые функции:**
    *   Поддерживает сетевые правила на узле, которые обеспечивают маршрутизацию трафика для объектов `Service`.
    *   Перенаправляет трафик с виртуального IP-адреса сервиса на правильные IP-адреса подов.
    *   Работает в одном из режимов: `iptables` (наиболее распространенный), `ipvs` или `kernelspace`.

### 3. Container Runtime (Среда выполнения контейнеров)
*   **Роль:** **Движок для контейнеров.**
*   **Описание:** Программное обеспечение, которое непосредственно запускает контейнеры и управляет их жизненным циклом. Kubernetes совместим с любой средой, поддерживающей стандарт **CRI (Container Runtime Interface)**, например, `containerd` или `CRI-O`.

## Схема взаимодействия: Жизненный цикл создания пода

Как все это работает вместе? Рассмотрим простой сценарий создания `Deployment`:

1.  **Пользователь** отправляет команду `kubectl apply -f deployment.yaml`. `kubectl` преобразует ее в API-запрос и отправляет в **`kube-apiserver`**.
2.  **`kube-apiserver`** проверяет запрос и сохраняет спецификацию `Deployment` в **`etcd`**.
3.  **`kube-controller-manager`** (а именно, Deployment Controller) замечает новый объект `Deployment` и создает для него дочерний объект `ReplicaSet`.
4.  **`kube-controller-manager`** (уже ReplicaSet Controller) видит `ReplicaSet` и создает нужное количество подов в соответствии с полем `replicas`. У этих подов пока не назначен узел.
5.  **`kube-scheduler`** обнаруживает "бездомные" поды и, основываясь на своих правилах, выбирает для каждого из них подходящий узел.
6.  **`kube-apiserver`** записывает информацию о назначенном узле для каждого пода в **`etcd`**.
7.  **`kubelet`** на назначенном узле через `apiserver` видит, что ему поручен новый под.
8.  **`kubelet`** дает команду **`Container Runtime`** скачать образ и запустить контейнеры.
9.  **`kubelet`** постоянно сообщает о статусе пода обратно в **`kube-apiserver`**, который обновляет данные в **`etcd`**. Кластер приходит в желаемое состояние.
