# Архитектура кластера Kubernetes

Кластер Kubernetes состоит из двух типов узлов и их компонентов:
*   **Control Plane (Управляющая плоскость):** Мозг кластера. Принимает глобальные решения, обнаруживает и реагирует на события.
*   **Worker Nodes (Рабочие узлы):** Исполнители. Машины, на которых запускаются контейнеризированные приложения.

---

## Компоненты Control Plane

Компоненты Control Plane принимают глобальные решения о кластере (например, планирование подов), а также обнаруживают и реагируют на события в кластере. Они могут работать на одном мастер-узле или быть реплицированы для обеспечения высокой доступности.

### 1. `etcd`
*   **Роль:** Распределенное, согласованное хранилище типа "ключ-значение".
*   **Ключевые функции:**
    *   Является **единственным источником правды** (`source of truth`) для хранения всего состояния кластера: конфигураций, спецификаций и статусов объектов.
    *   Обеспечивает консистентность данных между компонентами Control Plane.
    *   Требует обязательного резервного копирования из-за своей критической важности.

### 2. `kube-apiserver` (API-сервер)
*   **Роль:** Центральный компонент и "фронтенд" управляющей плоскости.
*   **Ключевые функции:**
    *   Предоставляет HTTP/HTTPS API, через которое взаимодействуют все остальные компоненты, пользователи (`kubectl`) и внешние системы.
    *   Валидирует и обрабатывает все REST-запросы на изменение состояния объектов (создание пода, обновление сервиса и т.д.).
    *   Является **единственным компонентом**, который напрямую взаимодействует с `etcd`.

### 3. `kube-scheduler` (Планировщик)
*   **Роль:** Отвечает за назначение (размещение) подов на подходящие рабочие узлы.
*   **Ключевые функции:**
    *   Отслеживает поды, у которых не заполнено поле `spec.nodeName`.
    *   Принимает решение о размещении на основе множества факторов: запросы к ресурсам (`requests`), `affinity`/`anti-affinity`, `taints`/`tolerations`, доступность `PersistentVolume` и другие политики.

### 4. `kube-controller-manager` (Менеджер контроллеров)
*   **Роль:** Запускает и управляет набором фоновых процессов-контроллеров.
*   **Ключевые функции:**
    *   Каждый контроллер отслеживает состояние определённого типа ресурсов и приводит его в соответствие с желаемым состоянием, записанным в `etcd`.
    *   **Node Controller:** Реагирует на отказы узлов.
    *   **Deployment/ReplicaSet Controller:** Поддерживает заданное количество реплик пода.
    *   **Endpoints Controller:** Обновляет объект `Endpoints`, связывая `Service` с подами.
    *   **Service Account & Token Controllers:** Создают стандартные аккаунты и токены для доступа к API.

## Компоненты Worker Node

Эти компоненты работают на каждом узле и обеспечивают запуск и сетевую связность подов.

### 1. `kubelet`
*   **Роль:** Главный агент Kubernetes на каждом рабочем узле.
*   **Ключевые функции:**
    *   Регистрирует узел в кластере, получая инструкции от `API-сервера`.
    *   Гарантирует, что контейнеры, описанные в спецификациях подов, запущены и работают корректно.
    *   Взаимодействует со средой выполнения контейнеров (например, `containerd`) для управления жизненным циклом контейнеров.
    *   Выполняет пробы (`liveness`, `readiness`, `startup`).
    *   Передаёт `API-серверу` отчеты о состоянии узла и подов.

### 2. `kube-proxy`
*   **Роль:** Сетевой прокси, отвечающий за реализацию сетевой модели Kubernetes на каждом узле.
*   **Ключевые функции:**
    *   Поддерживает сетевые правила на узле, которые обеспечивают маршрутизацию трафика для объектов `Service`.
    *   Перенаправляет трафик с виртуального IP-адреса сервиса на правильные IP-адреса подов.
    *   Работает в одном из режимов: `iptables` (наиболее распространенный), `ipvs` или `kernelspace`.

### 3. Container Runtime (Среда выполнения контейнеров)
*   **Роль:** Программное обеспечение, отвечающее за запуск и управление контейнерами.
*   **Ключевые функции:**
    *   Kubernetes поддерживает любую среду, совместимую с **CRI (Container Runtime Interface)**.
    *   Популярные реализации: `containerd`, `CRI-O`.

## Схема взаимодействия компонентов

Простой сценарий создания `Deployment`:

1.  **Пользователь (`kubectl`)** -> **`kube-apiserver`**: Отправляет YAML-манифест.
2.  **`kube-apiserver`** -> **`etcd`**: Сохраняет состояние нового объекта `Deployment`.
3.  **`kube-controller-manager`** (через `apiserver`): Обнаруживает новый `Deployment`, создает `ReplicaSet`.
4.  **`kube-scheduler`** (через `apiserver`): Обнаруживает новые поды без назначенного узла и выбирает для них подходящие `Worker Nodes`.
5.  **`kube-apiserver`** -> **`etcd`**: Обновляет информацию о подах, записывая назначенные узлы.
6.  **`kubelet`** (на каждом назначенном узле): Обнаруживает, что на его узел назначен новый под.
7.  **`kubelet`** -> **`Container Runtime`**: Дает команду запустить контейнеры, описанные в поде.
8.  **`kubelet`** -> **`kube-apiserver`**: Постоянно сообщает о состоянии пода.
