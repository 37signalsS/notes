# Компоненты кластера Kubernetes

Кластер Kubernetes состоит из двух основных типов узлов: **Control Plane** (управляющая плоскость) и **Worker Nodes** (рабочие узлы).

---

## Control Plane Components

Компоненты Control Plane принимают глобальные решения о кластере (например, планирование подов), а также обнаруживают и реагируют на события в кластере. Они могут работать на одном мастер-узле или быть реплицированы для обеспечения высокой доступности.

### 1. `etcd`

*   **Роль:** Распределенное, согласованное хранилище типа "ключ-значение", которое используется как "единственный источник правды" для хранения всего состояния кластера.
*   **Ключевые моменты:**
    *   Хранит конфигурацию, спецификации и состояния всех объектов Kubernetes.
    *   Критически важен для работы кластера. Требует надежного резервного копирования.
    *   Для отказоустойчивости развертывается в виде кластера из нечетного числа узлов (обычно 3 или 5).

### 2. `kube-apiserver` (API-сервер)

*   **Роль:** Центральный компонент, который предоставляет API Kubernetes. Это "фронтенд" для Control Plane.
*   **Ключевые моменты:**
    *   Обрабатывает REST-запросы от пользователей (`kubectl`), UI и других компонентов кластера.
    *   Валидирует и обрабатывает запросы на изменение состояния объектов (например, создание пода).
    *   Единственный компонент, который напрямую взаимодействует с `etcd`.

### 3. `kube-scheduler` (Планировщик)

*   **Роль:** Отвечает за назначение подов на рабочие узлы.
*   **Ключевые моменты:**
    *   Отслеживает вновь созданные поды, у которых еще не назначен узел.
    *   Принимает решение о размещении, учитывая множество факторов: запросы к ресурсам (`requests`), политики `affinity`/`anti-affinity`, `taints` и `tolerations`, доступность `PersistentVolume`.

### 4. `kube-controller-manager` (Менеджер контроллеров)

*   **Роль:** Запускает фоновые процессы-контроллеры, которые приводят текущее состояние кластера к желаемому. У каждой абстракции есть контролер
*   **Ключевые моменты:**
    *   **Node Controller:** Отвечает за обнаружение и реакцию на отказ узлов.
    *   **Replication Controller:** Поддерживает правильное количество подов для каждого `ReplicaSet`.
    *   **Endpoints Controller:** Заполняет объект `Endpoints` (связывает `Service` и `Pod`).
    *   И многие другие контроллеры.

## Worker Node Components

Рабочие узлы — это машины (виртуальные или физические), на которых запускаются контейнеризированные приложения.

### 1. `kubelet`

*   **Роль:** Агент, который работает на каждом узле в кластере. Он гарантирует, что контейнеры, описанные в `PodSpecs`, запущены и работают.
*   **Ключевые моменты:**
    *   Получает спецификации подов от `API-сервера` и взаимодействует со средой выполнения контейнеров (например, `containerd`) для запуска/остановки контейнеров.
    *   Выполняет пробы `liveness` и `readiness`.
    *   Монтирует тома (`volumes`) в контейнеры.
    *   Сообщает `API-серверу` о состоянии узла и подов на нем.

### 2. `kube-proxy`

*   **Роль:** Сетевой прокси, который работает на каждом узле и отвечает за реализацию сетевых правил для объектов `Service`.
*   **Ключевые моменты:**
    *   Обеспечивает сетевую коммуникацию и балансировку нагрузки для сервисов. (трафик приходящий на определенный айпи адрес на определенный порт перенаправлять на цепочку, в цепочке два правила, первое правило - 50% трафика в другую цепочку, второе правило - в другую цепочку, обе цепочки ссылаются на айпи адреса подов)
    *   Может работать в нескольких режимах, наиболее распространенные — `iptables` и `ipvs`.

### 3. Container Runtime (Среда выполнения контейнеров)

*   **Роль:** Программное обеспечение, отвечающее за запуск контейнеров.
*   **Ключевые моменты:**
    *   Kubernetes поддерживает любую среду выполнения, совместимую с CRI (Container Runtime Interface).
    *   Примеры: `containerd`, `CRI-O`.
