# Сетевая модель в Kubernetes

Сетевая модель Kubernetes основана на наборе фундаментальных принципов, которые обеспечивают простую и предсказуемую коммуникацию между компонентами кластера.

### Основные принципы:

1.  **Каждый под получает свой уникальный IP-адрес:** Все контейнеры внутри одного пода разделяют один и тот же IP-адрес и сетевое пространство имен. Они могут общаться друг с другом через `localhost`.
2.  **Поды могут общаться с подами на других узлах:** Любой под может напрямую связаться с любым другим подом в кластере, используя его IP-адрес, без необходимости в NAT (Network Address Translation).
3.  **Агенты на узле (например, kubelet) могут общаться с подами на этом же узле.**

## Путь трафика: от Ingress до пода

**Внешний запрос → Ingress → Service → Pod**

1.  **Внешний запрос → Ingress Controller**
    *   Пользователь отправляет запрос (например, `http://my-app.com/path`).
    *   Запрос попадает на Ingress Controller (например, NGINX Ingress), который является точкой входа в кластер.

2.  **Ingress Controller → Service**
    *   Ingress Controller смотрит на свои правила (`Ingress Resource`). Он находит правило для `my-app.com` и видит, что трафик нужно направить на `Service` с именем, скажем, `frontend-service`.

3.  **Service → Endpoints**
    *   `Service` (`frontend-service`) служит стабильной "виртуальной" точкой входа с постоянным IP-адресом внутри кластера.
    *   У `Service` есть `selector` (например, `app: my-app`). Kubernetes автоматически отслеживает все здоровые поды с этой меткой и записывает их IP-адреса в специальный объект `Endpoints` (или `EndpointSlice`).

4.  **Endpoints → kube-proxy → Pod**
    *   На каждом узле в кластере работает системный компонент `kube-proxy`.
    *   `kube-proxy` следит за изменениями в `Service` и `Endpoints`. Он знает, что трафик для виртуального IP-адреса сервиса нужно направить на реальные IP-адреса подов.
    *   Для этого `kube-proxy` **программирует сетевые правила прямо на узле**, используя один из режимов:
        *   **iptables (по умолчанию):** Создает правила, которые перехватывают трафик и случайным образом перенаправляют его на один из IP-адресов пода.
        *   **IPVS:** Более производительный режим, использующий IP Virtual Server для балансировки нагрузки.
    *   В итоге, когда трафик от Ingress Controller попадает на узел, ядро системы, благодаря этим правилам, доставляет его в один из конечных подов.

### CNI (Container Network Interface)

Kubernetes не реализует сетевую модель самостоятельно. Вместо этого он делегирует эту задачу **CNI-плагинам**. CNI — это стандарт, который определяет, как среда выполнения контейнеров (например, `containerd`) должна настраивать сетевые интерфейсы для контейнеров.

После того как `kubelet` инициировал запуск Pod'а, он вызывает CNI-плагин для настройки сетевых ресурсов. Этот процесс включает следующие шаги:

1.  **Назначение IP-адреса Pod'у:** Каждому Pod'у в Kubernetes присваивается уникальный IP-адрес из диапазона, выделенного для кластера. 

2.  **Создание сетевого пространства имен (Network Namespace):** Для каждого Pod'а создаётся свой собственный, изолированный `network namespace`. Это гарантирует, что у Pod'а будет свой собственный сетевой стек (таблица маршрутизации, сетевые устройства, порты).

3.  **Настройка виртуальных Ethernet-устройств (veth-pair):** Создаётся пара виртуальных Ethernet-интерфейсов (`veth-pair`). Один конец этой пары помещается в сетевое пространство имен Pod'а (и становится его интерфейсом, например, `eth0`), а другой остаётся в корневом пространстве имен узла.

4.  **Подключение к мосту узла:** Конец `veth-пары`, находящийся в пространстве имен узла, подключается к сетевому мосту (например, `cni0`). Это позволяет Pod'ам на одном узле обмениваться трафиком через этот мост.

5.  **Настройка маршрутизации для межсетевого взаимодействия:** Для связи Pod'ов, расположенных на разных узлах, CNI-плагин настраивает маршруты. Часто это реализуется через оверлейные сети (например, с использованием VXLAN, как в **Flannel**) или через прямое управление маршрутами на узлах (как в **Calico**).

### Примерная схема трафика (с Flannel)

1.  **Внутри узла:**
    *   Под `Pod A` на `Node 1` хочет отправить пакет поду `Pod B` на том же узле.
    *   Трафик идет от `Pod A` через его `veth` интерфейс на сетевой мост `cni0`.
    *   Мост `cni0` видит, что IP-адрес назначения принадлежит `Pod B` на этом же узле, и напрямую отправляет трафик на его `veth` интерфейс.

2.  **Между узлами:**
    *   `Pod A` на `Node 1` хочет отправить пакет поду `Pod C` на `Node 2`.
    *   Трафик снова попадает на мост `cni0`.
    *   Мост видит, что IP-адрес назначения находится в другой подсети, и, согласно таблице маршрутизации, отправляет трафик на виртуальный туннельный интерфейс, созданный Flannel (например, `flannel.1`).
    *   Flannel инкапсулирует исходный пакет в новый UDP-пакет (используя VXLAN) и отправляет его на IP-адрес `Node 2`.
    *   На `Node 2` Flannel распаковывает пакет и направляет его на мост `cni0`, который доставляет его до `Pod C`.

### Доступ между неймспейсами: по умолчанию всё открыто

**Да, по умолчанию доступ между неймспейсами полностью открыт.** Любой под может связаться с любым другим подом в кластере, независимо от того, в каких неймспейсах они находятся.

#### Почему так сделано?

1.  **Namespaces — это не сетевая граница.** Основное предназначение неймспейсов — это **логическое разделение** ресурсов для управления (RBAC, квоты, организация). Они не создают сетевую изоляцию.
2.  **"Плоская" сетевая модель Kubernetes.** Kubernetes по умолчанию предполагает, что все компоненты кластера могут свободно общаться друг с другом. 
3.  **Роль CNI (например, Flannel).** Задача CNI-плагинов, таких как Flannel, — **реализовать** эту плоскую сеть. Flannel создает оверлейную сеть (обычно через VXLAN), которая соединяет все узлы, но он ничего не знает о неймспейсах и не фильтрует трафик между ними.

### Как изолировать неймспейсы: NetworkPolicy

Для создания сетевых границ и правил файрвола между подами используется объект **NetworkPolicy**.

**Ключевые особенности `NetworkPolicy`:**

*   **Работают как файрвол:** Позволяют создавать правила для входящего (Ingress) и исходящего (Egress) трафика.
*   **"Запрещено по умолчанию" (Default Deny):** Как только вы применяете к поду хотя бы одну политику, весь трафик, не разрешенный в ней явно, **блокируется**.
*   **Требуют поддержки от CNI:** **Это критически важный момент.** CNI-плагин Flannel **не поддерживает** `NetworkPolicy`. Чтобы политики работали, вам нужен более продвинутый CNI, например:
    *   **Calico** (самый популярный выбор для этой цели)
    *   **Cilium**
    *   **Weave Net**

#### Пример: Изоляция неймспейса

Чтобы разрешить подам из неймспейса `frontend` доступ к подам в неймспейсе `backend`, а весь остальной трафик в `backend` запретить, нужно:

1.  **Создать `NetworkPolicy` в неймспейсе `backend`:**

    ```yaml
    apiVersion: networking.k8s.io/v1
    kind: NetworkPolicy
    metadata:
      name: allow-from-frontend
      namespace: backend
    spec:
      podSelector: {} # Применяем ко всем подам в неймспейсе 'backend'
      policyTypes:
      - Ingress
      ingress:
      - from:
        - namespaceSelector:
            matchLabels:
              # Имя метки может быть любым, главное, чтобы оно было у нужного неймспейса
              kubernetes.io/metadata.name: frontend
    ```

2.  **Убедиться, что у неймспейса `frontend` есть соответствующая метка.** (Современные версии Kubernetes добавляют метку `kubernetes.io/metadata.name` автоматически, но для старых версий или кастомных меток может потребоваться команда `kubectl label namespace frontend ...`).

После применения этой политики (в кластере с Calico или другим поддерживающим CNI) поды в `backend` будут принимать трафик только от подов из `frontend`.
