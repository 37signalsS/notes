# Сетевые технологии

В этом документе собраны основные концепции и протоколы, связанные с работой компьютерных сетей.

## Часть 1: Основы и концепции

### Модели сети

#### Модель OSI

Сетевая модель OSI (Open Systems Interconnection) — это концептуальная модель, которая стандартизирует сетевые функции, разделяя их на семь уровней. Каждый уровень обслуживает вышестоящий уровень и использует функции нижестоящего. В процессе отправки данные проходят от 7-го уровня к 1-му, а при получении — в обратном порядке. Этот процесс называется **инкапсуляцией** (при отправке) и **декапсуляцией** (при получении).

На каждом уровне к данным добавляется заголовок (header), и этот блок данных называется **PDU (Protocol Data Unit)**. У каждого уровня PDU имеет своё название.

| Уровень (Layer) | PDU (Тип данных) | Функции | Примеры | Оборудование |
| :--- | :--- | :--- | :--- | :--- |
| **7. Прикладной (Application)** | **Данные (Data)** | Доступ к сетевым службам, пользовательский интерфейс. | HTTP, FTP, POP3, WebSocket | Хосты, Межсетевые экраны |
| **6. Представления (Presentation)** | **Данные (Data)** | Преобразование, сжатие и шифрование данных. | ASCII, JPEG, MIDI, SSL/TLS | Хосты, Межсетевые экраны |
| **5. Сеансовый (Session)** | **Данные (Data)** | Управление сеансом связи, установка, поддержание и завершение соединения. | RPC, PAP, L2TP, gRPC | Хосты, Межсетевые экраны |
| **4. Транспортный (Transport)** | **Сегменты (Segments)** для TCP<br>**Дейтаграммы (Datagrams)** для UDP | Обеспечение надёжности, контроль потока, прямая связь между конечными пунктами. | TCP, UDP, SCTP, Порты | Хосты, Межсетевые экраны |
| **3. Сетевой (Network)** | **Пакеты (Packets)**<br>(Иногда **Фрагменты**, если пакет был разбит) | Маршрутизация, логическая адресация (IP-адреса), определение пути. | IPv4, IPv6, ICMP, IPSec | Маршрутизатор, L3-коммутатор |
| **2. Канальный (Data Link)** | **Кадры (Frames)** | Физическая адресация (MAC-адреса), контроль ошибок на физическом уровне. | Ethernet, Wi-Fi, PPP, ARP | Коммутатор, Мост, Сетевая карта |
| **1. Физический (Physical)** | **Биты (Bits)** | Передача двоичных сигналов по физической среде (кабель, радиоволны). | USB, RJ-45, Оптоволокно | Концентратор, Повторитель, Кабель |

**Уровни:**
*   **Host layers**: 7–4 (Отвечают за представление данных и взаимодействие с приложениями)
*   **Media layers**: 1–3 (Отвечают за передачу данных по сети)

#### Модель TCP/IP

| Уровень | Протоколы и технологии |
|---|---|
| **Прикладной уровень** | HTTP, FTP, DNS, Telnet, SSH |
| **Транспортный уровень** | TCP, UDP |
| **Сетевой уровень** | IP, ICMP, NAT |
| **Канальный уровень** | Ethernet, IEEE 802.11 (Wi-Fi), TokenRing, E1 |

### Ключевые компоненты и адресация

#### IP-адрес и маска подсети

IP (Internet Protocol) — межсетевой протокол модели OSI, уникальный внутри подсети идентификатор устройства третьего (сетевого) уровня. Его главная задача — адресация узлов сети и маршрутизация пакетов до них. Ключевые сущности для межсетевого протокола: IP-адрес, маска подсети и маршрут. IP-адрес состоит из четырех октетов (4-байтовое или 32-битное число), последний из которых указывает номер хоста в сети.

Маска подсети (32-битное число) — служит для разделения сетевой части (адреса подсети) и части хоста IP-адреса.

#### MAC-адрес

MAC-адрес – это уникальный 48-битный аппаратный номер компьютера, который встроен в сетевую карту на стадии производства. MAC-адрес также известен как физический адрес сетевого устройства. В стандарте IEEE 802, канальный уровень (второй уровень) разделен на два подуровня:

*   Подуровень управления логическим каналом (LLC)
*   Подуровень управления доступом к среде (MAC)

MAC-адрес используется подуровнем управления доступом к среде (MAC) канального (второго) уровня модели OSI.

#### Порт

Это числовое значение (от 0 до 65535), которое используется для идентификации конкретного процесса или службы на устройстве. Когда компьютер обменивается данными по сети, он использует IP-адрес для определения устройства и номер порта для определения конкретной службы или приложения.

Порты делятся на три диапазона в соответствии с рекомендациями IANA (Internet Assigned Numbers Authority):

1.  **Системные (или общеизвестные) порты (Well-Known Ports): 0–1023**
    *   **Назначение:** Зарезервированы для стандартных, хорошо известных системных служб и протоколов.
    *   **Примеры:**
        *   `20/21`: FTP (File Transfer Protocol)
        *   `22`: SSH (Secure Shell)
        *   `25`: SMTP (Simple Mail Transfer Protocol)
        *   `53`: DNS (Domain Name System)
        *   `80`: HTTP (HyperText Transfer Protocol)
        *   `443`: HTTPS (HTTP Secure)
    *   **Особенность:** Для использования этих портов в большинстве операционных систем требуются права суперпользователя (root).

2.  **Зарегистрированные (или пользовательские) порты (Registered/User Ports): 1024–49151**
    *   **Назначение:** Предназначены для приложений и служб, которые устанавливаются пользователями или сторонним программным обеспечением. Компании могут официально зарегистрировать порт для своего приложения в IANA.
    *   **Примеры:**
        *   `1433`: Microsoft SQL Server
        *   `3306`: MySQL
        *   `5432`: PostgreSQL
        *   `8080`: Часто используется как альтернативный порт для веб-серверов.

3.  **Динамические (или частные) порты (Dynamic/Private/Ephemeral Ports): 49152–65535**
    *   **Назначение:** Используются для временных (эфемерных) соединений. Когда ваш компьютер (клиент) подключается к веб-серверу (например, на порт 443), он выбирает для себя случайный свободный порт из этого диапазона для исходящего соединения.
    *   **Особенность:** Эти порты не закрепляются за какой-либо службой на постоянной основе и свободны для использования любым приложением.

#### Разница между 127.0.0.1 и 0.0.0.0

| Характеристика | `127.0.0.1` (localhost) | `0.0.0.0` (любой IP) |
| :--- | :--- | :--- |
| **Назначение** | Обращение к своему компьютеру (loopback) | Прослушивание всех доступных сетевых интерфейсов |
| **Доступность** | Только с этого же компьютера | С любого компьютера (включая этот), имеющего доступ |
| **Использование** | Клиентская сторона (подключение к локальному серверу) | Серверная сторона (привязка сервиса к портам) |

**`127.0.0.1` (localhost)**:
*   **Что это?** Это специальный IP-адрес, который всегда указывает на ваш собственный компьютер. Он используется для тестирования сетевых приложений локально, без отправки трафика в реальную сеть.
*   **Как работает?** Когда вы обращаетесь к `127.0.0.1`, операционная система перехватывает этот запрос и направляет его обратно на вашу же машину. Этот трафик никогда не покидает пределы вашего компьютера.
*   **Пример использования:** Разработчики используют `localhost` для запуска и отладки веб-серверов или баз данных на своей машине, прежде чем развертывать их в интернете.

**`0.0.0.0` (любой IP-адрес)**:
*   **Что это?** Это немаршрутизируемый мета-адрес, который используется для обозначения "любого" или "всех" IP-адресов на локальной машине.
*   **Как работает?** Когда серверное приложение "слушает" порт на `0.0.0.0`, это означает, что оно будет принимать входящие соединения с любого сетевого интерфейса (например, Wi-Fi, Ethernet) на этом компьютере. Это делает приложение доступным не только с `localhost`, но и из локальной сети или интернета (если нет файрвола).
*   **Пример использования:** Если вы запускаете веб-сервер на `0.0.0.0:8080`, к нему можно будет подключиться:
    *   С этого же компьютера по адресу `http://localhost:8080` или `http://127.0.0.1:8080`.
    *   С другого устройства в той же локальной сети по адресу `http://<локальный_IP_вашего_компьютера>:8080`.
    *   Из интернета по адресу `http://<ваш_внешний_IP>:8080` (если настроен проброс портов).

Простыми словами, `127.0.0.1` — это адрес для "разговора с самим собой", а `0.0.0.0` — это инструкция для сервера "слушать всех, кто стучится в дверь".

### Сетевое оборудование

#### Коммутатор vs Маршрутизатор
*   **Коммутатор (Свитч)**:
    *   **Назначение**: Соединяет несколько устройств (компьютеры, принтеры и т.д.) в одну **локальную сеть (LAN)**.
    *   **Уровень OSI**: Работает на Канальном уровне (L2).
    *   **Как работает**: Пересылает данные конкретному получателю внутри сети, используя MAC-адреса устройств. Это похоже на работу почтового отделения внутри одного большого офисного здания.
    *   **Использование**: Идеален для создания сетей в домах и офисах, где нужно соединить множество устройств проводным способом.

*   **Маршрутизатор (Роутер)**:
    *   **Назначение**: Соединяет несколько сетей вместе. Чаще всего он соединяет вашу локальную сеть (LAN) с глобальной сетью — **Интернетом (WAN)**.
    *   **Уровень OSI**: Работает на Сетевом уровне (L3).
    *   **Как работает**: Направляет трафик между сетями, используя IP-адреса. Он определяет лучший путь для отправки данных. Это можно сравнить с работой городской почтовой службы, которая направляет письма между разными районами (сетями).
    *   **Дополнительные функции**: Часто включает в себя функции безопасности (брандмауэр), Wi-Fi для беспроводного подключения и DHCP для автоматической раздачи IP-адресов устройствам в сети.

| Характеристика | Коммутатор (Свитч) | Маршрутизатор (Роутер) |
| :--- | :--- | :--- |
| **Основная функция** | Соединение устройств в **одной** локальной сети (LAN) | Соединение **разных** сетей (например, LAN и Интернет) |
| **Уровень модели OSI** | Уровень 2 (Канальный) | Уровень 3 (Сетевой) |
| **Тип адреса** | MAC-адрес | IP-адрес |
| **Область действия** | Внутри локальной сети | Между сетями |
| **Пример использования** | Подключение 10 компьютеров в офисе к одной сети | Подключение домашней или офисной сети к Интернету |

В типичной домашней или офисной сети устройства сначала подключаются к коммутатору. Затем этот коммутатор подключается к маршрутизатору, который, в свою очередь, подключен к модему для выхода в Интернет. Многие современные домашние маршрутизаторы являются комбинированными устройствами и имеют встроенный коммутатор с несколькими портами Ethernet.

## Часть 2: Протоколы и их работа

### Транспортный уровень (L4)

#### TCP-handshake (тройное рукопожатие)

Установка TCP соединения:
*   **SYN (synchronize)** — Клиент отправляет на сервер специальный пакет SYN, уведомляя о намерении установить соединение и передавая начальный порядковый номер для передачи данных.
*   **SYN-ACK (synchronize-acknowledgment)** — Сервер, получив пакет SYN, отправляет ответный пакет SYN-ACK. Этот пакет подтверждает получение запроса и также содержит свой начальный номер для синхронизации.
*   **ACK (acknowledgment)** — Клиент отправляет пакет ACK для подтверждения получения пакета SYN-ACK. После этого соединение считается установленным, и данные могут передаваться.

### Сетевой уровень (L3)

#### ICMP (Internet Control Message Protocol)

Когда сетевое устройство (например, маршрутизатор) сталкивается с проблемой при обработке пакета, оно генерирует ICMP-сообщение и отправляет его источнику пакета. Каждое ICMP-сообщение содержит:
*   **Тип сообщения:** Указывает на характер события (например, "узел назначения недоступен").
*   **Код:** Уточняет причину (например, "порт недоступен").
*   **Данные:** Часто включают заголовок и первые 64 бита IP-пакета, вызвавшего ошибку.

**Основные типы ICMP-сообщений:**

*   **Echo Request / Echo Reply:** Основа утилиты `ping`. Позволяет проверить доступность узла и измерить время задержки.
*   **Destination Unreachable:** Сообщает, что пакет не может быть доставлен (например, узел не существует или порт закрыт).
*   **Time Exceeded:** Отправляется, когда время жизни (TTL) пакета истекает до того, как он достигнет места назначения. Используется утилитой `traceroute` для определения маршрута.
*   **Redirect:** Уведомляет хост о наличии более короткого пути для отправки пакетов.

### Прикладной уровень (L7) и службы

#### DNS (Domain Name System)

Это система, которая переводит доменные имена (например, google.com) в IP-адреса (например, 142.250.72.174). Это необходимо, потому что компьютеры работают с IP-адресами, а людям удобнее использовать понятные имена.

DNS работает по принципу иерархии:
1.  **Корневые серверы** — отвечают за верхний уровень системы.
2.  **TLD-серверы (Top-Level Domain)** — отвечают за домены первого уровня (например, .com, .org).
3.  **Авторитетные серверы** — содержат информацию о конкретных доменах.

Файл `/etc/resolv.conf` содержит настройки DNS-серверов, которые используются системой. Вы можете просмотреть его содержимое:
```bash
cat /etc/resolv.conf
```
Пример вывода:
```
nameserver 8.8.8.8
nameserver 8.8.4.4
```

**Процесс DNS-запроса (рекурсивный и итеративный)**

Существует два основных типа DNS-запросов:

1.  **Рекурсивный запрос (Recursive Query):**
    *   Клиент (например, ваш компьютер) отправляет запрос локальному DNS-серверу (резолверу) и просит его найти IP-адрес.
    *   Сервер берёт на себя всю работу: он опрашивает другие DNS-серверы (корневые, TLD, авторитетные) до тех пор, пока не найдёт ответ.
    *   Клиент получает окончательный ответ: либо IP-адрес, либо сообщение об ошибке.
    *   Этот тип запроса используется между клиентом и его DNS-резолвером.

2.  **Итеративный (нерекурсивный) запрос (Iterative/Non-Recursive Query):**
    *   DNS-сервер, получив запрос, возвращает лучший ответ, который у него есть на данный момент. 
    *   Если у сервера нет точного IP-адреса, он возвращает адрес другого DNS-сервера, который может знать больше (например, адрес сервера более высокого уровня).
    *   Клиент (в данном случае — другой DNS-сервер) должен сам отправить новый запрос следующему серверу.
    *   Этот процесс повторяется, пока не будет найден авторитетный сервер, который даст окончательный ответ.
    *   Этот тип запроса используется преимущественно при общении DNS-серверов между собой.

**Общая схема работы:**
1.  Ваш компьютер отправляет **рекурсивный** запрос своему DNS-резолверу (например, серверу провайдера).
2.  DNS-резолвер начинает серию **итеративных** запросов к другим серверам:
    *   Сначала к корневому серверу.
    *   Затем к серверу доменной зоны верхнего уровня (например, `.com`).
    *   Затем к авторитетному серверу для конкретного домена (например, `google.com`).
3.  Получив IP-адрес от авторитетного сервера, резолвер возвращает его вашему компьютеру.

**DNS и транспортные протоколы (UDP/TCP)**

DNS использует порт 53 и может работать как по UDP, так и по TCP.

**Почему DNS предпочитает UDP?**

В большинстве случаев DNS использует UDP по следующим причинам:
*   **Скорость:** UDP — протокол без установления соединения. Ему не требуется "тройное рукопожатие" (как в TCP), что значительно снижает задержку.
*   **Низкие накладные расходы:** DNS-запросы и ответы обычно маленькие и помещаются в один пакет. UDP имеет меньший заголовок, что делает его более эффективным для таких коротких обменов данными.

**Когда DNS использует TCP?**

DNS переключается на TCP в определённых ситуациях, и это связано с историческими ограничениями и необходимостью обеспечить надёжность.

*   **Большой размер ответа (более 512 байт):**
    *   **Почему 512 байт?** Этот лимит был установлен в оригинальном стандарте DNS (RFC 1035). В то время максимальный размер пакета (MTU), который гарантированно проходил через любую сеть без разделения, составлял 576 байт. Лимит в 512 байт для данных DNS оставлял запас для заголовков UDP (8 байт) и IP (20 байт), чтобы избежать **фрагментации IP-пакетов**.
    *   **Что такое фрагментация IP?** Если IP-пакет больше, чем MTU (Maximum Transmission Unit) следующего участка сети, маршрутизатор разбивает его на несколько меньших пакетов (фрагментов). Каждый фрагмент отправляется отдельно и собирается обратно в единое целое только на конечном узле. Фрагментация нежелательна, так как она увеличивает накладные расходы и снижает надёжность: потеря даже одного фрагмента приводит к потере всего пакета.
    *   **Почему TCP?** В отличие от UDP, TCP — это протокол с установлением соединения, который сам управляет разделением данных на сегменты и гарантирует их доставку и правильную сборку. Когда DNS-ответ не помещается в один UDP-пакет, система переключается на TCP, чтобы надёжно передать большой объём данных без риска, связанного с IP-фрагментацией.
    *   **Современный подход (EDNS):** Сегодня используется расширение EDNS (Extension Mechanisms for DNS), которое позволяет клиенту и серверу договориться об использовании UDP-пакетов большего размера (например, 4096 байт). Это значительно сокращает частоту переключений на TCP, но TCP всё равно остаётся обязательным резервным механизмом.

*   **Передача зоны (Zone Transfer):** При синхронизации DNS-записей между главным и вторичными серверами всегда используется TCP. Это необходимо для гарантированной и последовательной передачи всего списка записей, который может быть очень большим.

**Anycast и низкая задержка до, например, 8.8.8.8**

Anycast — это метод сетевой адресации, при котором один и тот же IP-адрес используется множеством серверов, расположенных в разных точках мира. Когда вы отправляете запрос на `8.8.8.8`, сеть автоматически направляет его к географически ближайшему к вам серверу. Это значительно сокращает расстояние и, как следствие, время задержки (ping).

#### Что такое TTL

Time to live (TTL) – это время жизни пакета. TTL показывает максимальный период времени существования набора данных (пакета).

В IPv4 TTL представляет собой восьмиразрядное поле IP-заголовка. Параметр TTL считается верхней границей времени существования IP-дейтаграммы в сети. Поле TTL устанавливается отправителем и уменьшается на каждом маршрутизаторе на 1.

Основное назначение – не допустить "зацикливания" пакета в сети.

При условии, что значение TTL на каком-либо из узлов достигнет 1, пакет данных уничтожается, а на исходный сервер посылается ICMP-сообщение с кодом 11 — «Превышение временного интервала». Маршрутизатор не пропускает пакеты с нулевым значением TTL.

**TTL в DNS**

TTL (Time To Live) в контексте DNS — это параметр в секундах, который указывает, как долго DNS-резолвер (например, сервер провайдера или публичный DNS) может кэшировать (хранить у себя) ответ на DNS-запрос.

##### Как это работает:

1.  Ваш компьютер запрашивает IP-адрес для `example.com`.
2.  DNS-резолвер (кэширующий сервер) обращается к авторитативному DNS-серверу, который хранит запись для `example.com`.
3.  Авторитативный сервер отвечает резолверу, отправляя IP-адрес и **значение TTL**, например, `3600` (1 час).
4.  Резолвер сохраняет эту запись в своем кэше на 3600 секунд и отдает IP-адрес вашему компьютеру.
5.  Если в течение следующего часа кто-то еще, использующий этот же резолвер, запросит `example.com`, резолвер мгновенно отдаст ответ из кэша, не обращаясь к авторитативному серверу.
6.  Как только TTL истечет, резолвер будет обязан снова запросить "свежую" запись у авторитативного сервера.

**Практическое применение:** Перед плановой миграцией сервиса на новый IP-адрес TTL для соответствующей A-записи намеренно понижают до минимального значения (например, 60-300 секунд) за несколько часов или дней до миграции. Это гарантирует, что после обновления IP-адреса пользователи быстро получат новую, корректную информацию.

#### DHCP

DHCP (Dynamic Host Configuration Protocol) — протокол динамической настройки узла. Он предназначен для автоматической выдачи устройствам IP-адресов и других сетевых параметров (маска подсети, шлюз по умолчанию).

**Способы назначения IP-адресов**
*   **Статическое назначение:** IP-адрес вручную закрепляется за MAC-адресом конкретного устройства. Используется в небольших сетях для устройств, требующих постоянного адреса.
*   **Динамическое назначение:** DHCP-сервер выдает IP-адрес из пула свободных адресов на определенное время (срок аренды).
*   **Автоматическое назначение:** Похоже на динамическое, но срок аренды не ограничен. IP остается за клиентом, пока он сам от него не откажется.

**Архитектура протокола DHCP**

DHCP использует архитектуру «клиент-сервер».
*   **Сервер DHCP:** Раздает IP-адреса и следит за их уникальностью.
*   **Клиент DHCP:** Любое устройство, запрашивающее сетевые настройки.
*   **Агенты ретрансляции DHCP:** Позволяют DHCP работать через несколько подсетей, пересылая запросы между ними.

**Принцип работы протокола DHCP (DORA)**

1.  **Discovery:** Клиент (еще без IP) отправляет широковещательное сообщение `DHCPDISCOVER` для поиска DHCP-сервера.
2.  **Offer:** DHCP-сервер (или несколько) отвечает сообщением `DHCPOFFER`, предлагая IP-адрес в аренду.
3.  **Request:** Клиент выбирает одно из предложений и отправляет `DHCPREQUEST`, сообщая всем, что адрес принят.
4.  **Acknowledgement:** Сервер подтверждает выделение адреса сообщением `DHCPACK`, передавая также срок аренды и другие настройки.

**Другие сообщения DHCP:**
*   `DHCPNAK`: Отказ в аренде IP-адреса.
*   `DHCPINFORM`: Запрос на получение дополнительных настроек сети (когда IP уже есть).
*   `DHCPRELEASE`: Досрочное освобождение IP-адреса клиентом.
*   `DHCPDECLINE`: Сообщение от клиента, если предложенный IP-адрес уже занят.

**Срок аренды IP-адреса**

IP-адрес выдается на определенное время. По умолчанию — 24 часа, но это настраивается. По истечении половины срока аренды клиент пытается его продлить.

###### **HTTP/1.0 (1996)**

-   **Проблема:** Медлительность. На каждый запрос (например, за HTML-файл, картинку, CSS) открывалось новое TCP-соединение, что создавало большие накладные расходы.

###### **HTTP/1.1 (1997)**

Ключевые улучшения, направленные на решение проблем производительности:

-   **Постоянные соединения (Keep-Alive):** Позволили браузеру отправлять несколько запросов в рамках одного TCP-соединения, что значительно сократило задержки.
-   **Конвейеризация (Pipelining):** Дала возможность отправлять следующий запрос, не дожидаясь ответа на предыдущий. Однако на практике эта функция работала плохо из-за **блокировки "Head-of-Line" (HOL Blocking)**: если первый запрос в очереди "зависал", все последующие ждали его завершения.

###### **HTTP/2 (2015)**

Революционное обновление, основанное на протоколе SPDY от Google:

-   **Мультиплексирование:** Главное нововведение. Позволяет передавать множество запросов и ответов **одновременно** в рамках одного TCP-соединения, разбивая их на бинарные "кадры" (frames). Это полностью решило проблему HOL-блокировки на уровне приложения.
-   **Бинарный протокол:** В отличие от текстового HTTP/1.1, стал более эффективным и менее подверженным ошибкам.
-   **Сжатие заголовков (HPACK):** Значительно уменьшило размер передаваемых заголовков, что особенно заметно на мобильных устройствах.
-   **Server Push:** Позволял серверу отправлять ресурсы (например, CSS и JS) клиенту еще до того, как он их запросит, предугадывая его потребности. На практике функция оказалась сложной в реализации и не всегда давала выигрыш.

###### **HTTP/3 (2022)**

Новейший стандарт, который решает последнюю оставшуюся проблему — блокировку Head-of-Line на уровне **транспортного протокола (TCP)**.

-   **Переход на QUIC (UDP):** HTTP/3 работает поверх протокола **QUIC**, который, в свою очередь, использует **UDP**. QUIC реализует мультиплексирование на транспортном уровне. Если один из потоков данных (например, загрузка картинки) теряет пакет, это **не влияет** на остальные потоки. Другие ресурсы продолжают загружаться без задержек.
-   **Более быстрое установление соединения:** QUIC объединяет в себе установку соединения и TLS-рукопожатие, что сокращает время на установку безопасного соединения.
-   **Улучшенная работа при смене сети:** Соединение привязывается не к паре IP:порт, а к уникальному идентификатору соединения. Это позволяет, например, без разрыва связи переключаться с Wi-Fi на мобильную сеть.

##### Отправка HTTP-запроса

После установки безопасного соединения клиент (браузер, `curl`) отправляет HTTP-запрос. Запрос и ответ имеют строго определенную минимальную структуру.

###### **Минимальный HTTP-запрос**

Для протокола **HTTP/1.1** минимальный запрос должен содержать три элемента:

1.  **Стартовая строка (Request Line):**
    *   **Метод:** `GET` (самый простой).
    *   **URI (путь):** `/` (корень ресурса).
    *   **Версия протокола:** `HTTP/1.1`.
2.  **Заголовок `Host`:** Обязателен в HTTP/1.1. Указывает, к какому сайту на сервере мы обращаемся, так как один IP-адрес может обслуживать множество доменов. Передают дополнительную информацию: User-Agent, Accept-Language, Cookies и т.д.
3.  **Пустая строка (CRLF):** Сигнал о том, что заголовки закончились.

###### **Минимальный HTTP-ответ**

Минимальный успешный ответ содержит:

1.  **Строка состояния (Status Line):**
    *   **Версия протокола:** `HTTP/1.1`.
    *   **Код состояния:** `200` (успех).
    *   **Пояснение:** `OK`.
2.  **Заголовки:** Для ответа с телом обязателен заголовок `Content-Length`, чтобы клиент знал, сколько байт данных ему нужно прочитать.
3.  **Пустая строка (CRLF):** Разделяет заголовки и тело ответа.
4.  **Тело ответа (Response Body):** Сами данные (могут быть пустыми).

### Протоколы безопасности

#### Шифрование и установка безопасного соединения (TLS/SSL)

##### Как работают TLS-сертификаты

TLS-сертификат (ранее известный как SSL-сертификат) — это цифровой паспорт для веб-сайта. Его главная задача — подтвердить, что сайт, на который вы зашли, действительно тот, за кого себя выдает, и обеспечить шифрование данных между вами и сайтом.

**Ключевые компоненты TLS-сертификата:**
*   **Информация о владельце:** Доменное имя (например, `www.google.com`).
*   **Открытый ключ сервера:** Используется для шифрования информации, которую может расшифровать только сервер с помощью своего секретного закрытого ключа.
*   **Информация об издателе:** Название центра сертификации (Certificate Authority, CA), который выдал сертификат.
*   **Цифровая подпись издателя:** Центр сертификации подписывает сертификат своим закрытым ключом. Это гарантия того, что сертификат подлинный.
*   **Срок действия:** Даты начала и окончания действия сертификата.

##### Как происходит TLS-рукопожатие (Handshake)

TLS-рукопожатие — это процесс переговоров между вашим браузером (клиентом) и веб-сервером. Его цель — безопасно договориться о параметрах шифрования и создать уникальные ключи для защиты текущей сессии.

**Упрощенная схема для TLS 1.2:**

1.  **`ClientHello`:** Браузер отправляет серверу поддерживаемые версии TLS, список шифронаборов и случайную строку данных.
2.  **`ServerHello`:** Сервер выбирает версию TLS и шифронабор, отправляет свой TLS-сертификат с открытым ключом и свою случайную строку данных.
3.  **Проверка и обмен ключами:**
    *   Клиент проверяет сертификат сервера.
    *   Клиент генерирует секрет (`pre-master secret`), шифрует его открытым ключом сервера и отправляет обратно.
4.  **Создание сеансовых ключей:**
    *   Сервер использует свой закрытый ключ для расшифровки `pre-master secret`.
    *   Теперь и у клиента, и у сервера есть три одинаковых компонента, из которых они генерируют идентичные сеансовые ключи.
5.  **Завершение:** Клиент и сервер обмениваются сообщениями, зашифрованными новыми сеансовыми ключами, подтверждая успешное завершение рукопожатия.

После этого вся дальнейшая информация между клиентом и сервером шифруется с помощью сеансовых ключей.

## Часть 3: Комплексные сценарии

### Что происходит, когда вы вводите адрес сайта

**Первый этап: Преобразование имени в IP-адрес (DNS)**

Когда вы вводите URL (например, `https://google.com`) в адресную строку браузера, компьютер должен сначала узнать IP-адрес сервера, на котором находится этот сайт. Для этого он использует систему доменных имён (DNS).

Поиск IP-адреса происходит пошагово:
1.  **Кеш браузера:** Сначала браузер проверяет собственный кеш.
2.  **Кеш ОС:** Если в браузере адреса нет, проверяется кеш операционной системы (например, файл `hosts`).
3.  **DNS-резолвер:** Если адрес не найден локально, запрос отправляется к DNS-серверу (обычно это сервер вашего интернет-провайдера или публичный сервер вроде `8.8.8.8`).
4.  **Рекурсивный запрос:** DNS-сервер ищет IP-адрес, опрашивая другие серверы в интернете по иерархии (корневые, TLD, авторитативные), пока не найдёт нужную запись.

**Второй этап: Межсетевое взаимодействие (ARP и IP)**

Получив IP-адрес назначения, ваш компьютер должен отправить ему данные. Но для отправки данных в локальной сети (например, вашему роутеру) нужен не IP, а физический MAC-адрес.

1.  **Определение шлюза:** Компьютер понимает, что IP-адрес назначения (`google.com`) находится за пределами локальной сети. Весь внешний трафик нужно отправлять на **шлюз по умолчанию** (обычно это ваш роутер).
2.  **ARP-запрос (Address Resolution Protocol):**
    *   Чтобы узнать MAC-адрес роутера, компьютер отправляет широковещательный **ARP-запрос** в локальную сеть с вопросом: "У кого IP-адрес шлюза (например, `192.168.1.1`)?".
    *   Роутер отвечает на этот запрос, сообщая свой MAC-адрес.
    *   Компьютер сохраняет эту информацию в своей ARP-таблице, чтобы не спрашивать каждый раз.
3.  **Передача пакета на IP-уровне:** Теперь, зная MAC-адрес роутера, компьютер может сформировать пакет. Данные инкапсулируются: HTTP-запрос помещается в TCP-сегмент, тот — в IP-пакет, а IP-пакет — в Ethernet-кадр, у которого в заголовке указан MAC-адрес роутера как получателя.

**Третий этап: Установка соединения и передача данных (TCP и HTTP/S)**

Пакет доходит до роутера, который далее перенаправляет его по глобальной сети, пока он не достигнет сервера назначения.

1.  **TCP-рукопожатие (TCP Handshake):** Перед обменом данными клиент (ваш браузер) и сервер устанавливают надёжное соединение с помощью трёхэтапного процесса (SYN, SYN-ACK, ACK).
2.  **TLS-рукопожатие (TLS Handshake):** Если используется HTTPS (порт 443), после установки TCP-соединения происходит дополнительный процесс согласования. Клиент и сервер договариваются о параметрах шифрования и обмениваются ключами, чтобы защитить передаваемые данные.
3.  **HTTP-запрос:** После установки безопасного соединения браузер отправляет **HTTP-запрос** (например, `GET / HTTP/1.1`) с просьбой отдать содержимое страницы.
4.  **HTTP-ответ:** Сервер обрабатывает запрос и отправляет обратно **HTTP-ответ**, который содержит:
    *   **Статус-код** (например, `200 OK`).
    *   **Заголовки** (информация о контенте, сервере и т.д.).
    *   **Тело ответа** (HTML-код страницы, изображения и другие ресурсы).

Браузер получает этот ответ, обрабатывает HTML, загружает дополнительные ресурсы (CSS, JavaScript) и отображает веб-страницу.

### Как работает `curl` и HTTP-запрос

Когда вы выполняете команду `curl https://google.com`, происходит следующая последовательность событий, которая наглядно демонстрирует работу сетевых протоколов, начиная с самого верхнего уровня.

1.  **Уровень 7: Прикладной (Application Layer)**
    *   **Парсинг URL:** `curl` как приложение анализирует введенный URL:
        *   **Протокол:** `https`
        *   **Домен:** `google.com`
        *   **Путь:** `/` (по умолчанию)
    *   **Формирование HTTP-запроса:** `curl` создает текстовый HTTP-запрос. Минимально он будет выглядеть так:
        ```http
        GET / HTTP/1.1
        Host: google.com
        User-Agent: curl/7.68.0
        Accept: */*
        ```

2.  **Подготовка к передаче: DNS-запрос**
    *   Чтобы отправить запрос, `curl` должен узнать IP-адрес сервера `google.com`.
    *   Операционная система инициирует **DNS-запрос** (обычно через UDP на порт 53), чтобы преобразовать доменное имя в IP-адрес (например, `142.250.185.78`).

3.  **Уровень 4: Транспортный (Transport Layer)**
    *   **Выбор порта:** `curl` видит протокол `https` и понимает, что нужно использовать стандартный порт `443`.
    *   **TCP-рукопожатие (Handshake):** Операционная система инициирует установку TCP-соединения с сервером `142.250.185.78` на порт `443`. Происходит обмен пакетами (SYN, SYN-ACK, ACK) для создания надежного канала связи.

4.  **Уровень 6: Представления (Presentation Layer) - TLS Handshake**
    *   Поскольку используется `https`, поверх установленного TCP-соединения происходит **TLS-рукопожатие**.
    *   Клиент (`curl`) и сервер договариваются об алгоритмах шифрования и обмениваются ключами, чтобы создать безопасный (зашифрованный) туннель для передачи данных.

5.  **Отправка и получение данных**
    *   **Отправка запроса:** Сформированный на шаге 1 HTTP-запрос отправляется через зашифрованный TLS-туннель на сервер.
    *   **Ответ сервера:** Сервер обрабатывает запрос и отправляет обратно HTTP-ответ, который также проходит через все уровни в обратном порядке (шифруется, упаковывается в TCP-сегменты, IP-пакеты и т.д.).
    *   **Декапсуляция:** Ваша система получает пакеты, извлекает из них данные, расшифровывает их и передает утилите `curl`.
    *   **Вывод:** `curl` выводит тело ответа (например, HTML-код страницы) в стандартный вывод (ваш терминал).

## Часть 4: Дополнительные технологии

### NAT (network address translation)

NAT — это технология, позволяющая перенаправлять трафик между локальной и глобальной сетями. Благодаря ей несколько устройств в локальной сети могут выходить в интернет, используя один "белый" IP-адрес, выданный провайдером.

**Виды NAT**
*   **Статический NAT:** Каждому локальному адресу присваивается уникальный глобальный адрес. Часто применяется для серверов, к которым нужен постоянный удаленный доступ.
*   **Динамический NAT:** Маршрутизатор выдаёт устройству случайный глобальный адрес из доступного пула.
*   **PAT (Port Address Translation) или перегруженный NAT:** Самый распространённый тип. Несколько устройств с уникальными локальными адресами используют один глобальный IP-адрес. Различение устройств происходит по номерам портов.

**Принцип работы PAT:**
1.  Устройство с локальным IP (например, 192.168.0.3) отправляет запрос в интернет.
2.  Роутер с глобальным IP (например, 208.135.26.4) подменяет локальный IP на свой глобальный, запоминая в таблице, какому устройству и порту соответствует этот запрос.
3.  Внешний сервер отвечает на глобальный IP роутера.
4.  Роутер, получив ответ, смотрит в свою таблицу и перенаправляет трафик на исходное устройство в локальной сети.

### Proxy

Прокси выполняет роль промежуточного звена между пользователем и интернетом, перенаправляя трафик через себя. Прокси позволяют ускорять загрузку страниц за счет кэширования, контролировать трафик и фильтровать нежелательный контент.

**Как прокси защищают от DDoS-атак?**

Ключевым методом является маскировка подлинного IP-адреса хоста. Злоумышленники взаимодействуют с прокси, а не с реальным сервером, что исключает прямую атаку.

Дополнительно прокси могут:
*   Фильтровать вредоносный трафик.
*   Ограничивать число запросов с одного IP (rate limiting).
*   Балансировать нагрузку, распределяя трафик между несколькими серверами.
*   Кэшировать контент для снижения нагрузки на основной сервер.
*   Блокировать ботов и применять гео-блокировку.

**Протоколы и виды прокси**

Прокси-серверы классифицируются по протоколам и функциональному назначению.

**По протоколам:**
*   **HTTP-прокси:** Специализируются на обработке HTTP-запросов, могут кэшировать контент для ускорения загрузки.
*   **HTTPS-прокси:** Аналогичны HTTP, но используют шифрование для защиты передаваемых данных.
*   **SOCKS-прокси:** Универсальны, поддерживают различные типы трафика (HTTP, FTP, P2P, игры), но обычно не кэшируют данные.

**По функциональному назначению:**
*   **Анонимные прокси:** Скрывают IP-адрес клиента для повышения приватности.
*   **Прозрачные прокси:** Не скрывают IP-адрес, используются для мониторинга и контроля трафика в корпоративных или образовательных сетях.

### QoS

QoS (Quality of Service, качество обслуживания) – функция маршрутизации, которая позволяет определять приоритеты полосы пропускания для определенных программ, клиентов или служб. QoS резервирует определенный объём пропускной способности для критичных приложений.
