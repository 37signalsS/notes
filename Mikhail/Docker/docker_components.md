# **Компоненты Docker: От ядра Linux до контейнера**

---

## **1. Ключевые концепции**

### **Что такое контейнер?**

**Контейнер** — это изолированный процесс (или группа процессов), работающий в собственном окружении, отделенном от основной операционной системы. Эта изоляция достигается с помощью двух ключевых механизмов ядра Linux: **namespaces** и **cgroups**.

Важно понимать, что **процессы в контейнере — это обычные процессы хост-системы**. Docker лишь создает для них иллюзию работы в отдельной машине. Если найти PID процесса внутри контейнера (`docker top <имя_контейнера>`) и затем поискать его на хосте (`ps aux | grep <PID>`), вы увидите тот же самый процесс.

### **Образ и Контейнер**

Это ключевые понятия, которые удобно объяснять через аналогию с программированием:

> **Образ (Image)** — это неизменяемый (immutable) шаблон, который содержит все необходимое для запуска приложения: код, библиотеки, переменные окружения и конфигурационные файлы. Образы состоят из слоев, доступных только для чтения. **Это как класс в ООП.**

> **Контейнер (Container)** — это запущенный экземпляр образа. При запуске Docker добавляет поверх неизменяемых слоев образа один **записываемый слой (writable layer)**, где хранятся все изменения. **Это как объект (экземпляр класса).**

### **Ключевое отличие от виртуальных машин**

| Характеристика | Контейнеры | Виртуальные машины (ВМ) |
| :--- | :--- | :--- |
| **Ядро ОС** | Используют ядро хост-системы | Имеют собственное, гостевое ядро ОС |
| **Изоляция** | На уровне процессов (namespaces, cgroups) | Полная, на уровне аппаратной эмуляции |
| **Ресурсы** | Легковесные, минимальные накладные расходы | Потребляют значительные ресурсы (RAM, CPU) |
| **Запуск** | Мгновенный (миллисекунды) | Медленный (минуты) |

Из-за общего ядра **невозможно** запустить контейнер, созданный для одной ОС, на ядре другой. Например, Windows-контейнеры требуют системных вызовов ядра Windows NT, которых нет в ядре Linux.

## **2. Технологии изоляции в ядре Linux**

### **До контейнеров: `chroot`**

До появления современных контейнерных технологий для изоляции файловой системы использовалась утилита `chroot` (change root). Она позволяла изменить корневой каталог для процесса, делая невозможным доступ к файлам за его пределами.

Однако у `chroot` были существенные ограничения:
*   **Неполная изоляция:** Процесс все еще мог взаимодействовать с другими процессами, использовать тот же сетевой стек и не имел ограничений по ресурсам.
*   **Только файловая система:** Изоляция касалась только видимости файлов, но не других системных ресурсов.

### **Namespaces: Изоляция окружения**

**Namespaces (пространства имен)** создают для процесса изолированное представление о системных ресурсах. Каждый контейнер получает свой набор пространств имен, не пересекающийся с хостом.

- **PID Namespace:** Изоляция процессов. Процесс внутри контейнера видит себя как PID 1.
- **Mount Namespace:** Изоляция файловой системы. У контейнера свой корневой каталог (`/`).
- **Network Namespace:** Изоляция сети. Свой сетевой стек, IP-адреса и порты.
- **UTS Namespace:** Изоляция имени хоста и домена (`hostname`).
- **IPC Namespace:** Изоляция межпроцессного взаимодействия (System V IPC, POSIX message queues).
- **User Namespace:** Изоляция ID пользователей и групп. Позволяет маппинг пользователя root в контейнере на обычного пользователя на хосте.
- **Cgroup Namespace:** Изоляция представления о cgroups.
- **Time Namespace:** Изоляция системного времени.

### **Cgroups: Управление ресурсами**

**Control Groups (cgroups)** — это механизм ядра, который ограничивает и учитывает потребление ресурсов группой процессов.

- **CPU:** Ограничение процессорного времени.
- **Memory:** Лимиты на использование оперативной памяти и swap.
- **IO:** Контроль операций ввода-вывода на блочные устройства.
- **PIDs:** Ограничение максимального количества процессов.
- **Devices:** Управление доступом к устройствам (`/dev`).

В современных дистрибутивах используется **cgroups v2**, которая предоставляет унифицированную иерархию для управления всеми ресурсами.

## **3. Архитектура Docker**

### **Клиент-серверная модель**

Docker работает по клиент-серверной архитектуре:
- **Docker CLI (`docker`):** Клиентская часть. Консольная утилита, которая отправляет команды демону через REST API.
- **Docker Daemon (`dockerd`):** Серверная часть. Фоновый процесс, который принимает команды от клиента и управляет объектами Docker (образами, контейнерами, сетями).

Основной рабочий процесс выглядит следующим образом: получив команду от клиента (например, `docker run`), **Docker Daemon** сначала ищет образ в локальном хранилище. Если образ отсутствует, демон обращается к реестру образов (по умолчанию **Docker Hub**), скачивает его и после этого создает и запускает контейнер.

### **Компоненты Docker Engine**

Современный Docker Engine состоит из нескольких компонентов, работающих вместе:

1.  **Docker Daemon (`dockerd`):** Высокоуровневый компонент. Отвечает за пользовательский интерфейс (API), управление образами, сетями и томами. Он больше не управляет контейнерами напрямую.

2.  **containerd:** Это отдельный демон, который находится между `dockerd` и `runc`. Его задачи:
    *   Управление полным жизненным циклом контейнера (от создания до удаления).
    *   Загрузка и хранение образов.
    *   Управление сетевыми интерфейсами контейнеров.
    `dockerd` передает ему запросы на запуск или остановку контейнеров. Такое разделение повышает стабильность: перезапуск `dockerd` не затрагивает уже запущенные контейнеры, так как ими управляет `containerd`.

3.  **runc:** Низкоуровневая среда выполнения контейнеров (container runtime). Это эталонная реализация спецификации **OCI (Open Container Initiative)**.
    *   `containerd` использует `runc` для фактического создания и запуска контейнера.
    *   `runc` напрямую взаимодействует с ядром Linux для создания `namespaces` и `cgroups`.

Процесс запуска выглядит так: `docker` (CLI) → `dockerd` (API) → `containerd` (управление) → `runc` (запуск).

### **Слоеная файловая система: OverlayFS**

Docker использует **storage drivers** для управления слоями образов. Самый распространенный драйвер — **OverlayFS**. Он "накладывает" файловую систему контейнера поверх файловой системы образа.

*   **Нижние слои (lowerdir):** Слои образа, доступны только для чтения.
*   **Верхний слой (upperdir):** Записываемый слой контейнера. Все изменения (создание, изменение, удаление файлов) происходят здесь.
*   **Результат (merged):** Виртуальное объединение всех слоев, которое видит процесс в контейнере.

Эта система позволяет эффективно хранить образы (общие слои переиспользуются) и мгновенно создавать контейнеры.

### **Docker Registry: Хранилище образов**

**Registry** — это сервис для хранения и распространения образов Docker.
*   **Docker Hub:** Публичный реестр по умолчанию.
*   Существуют и частные (private) решения, такие как Harbor, GitLab Container Registry или Nexus.
