# **Безопасность Docker: от атаки до защиты**

---

## **1. Главная угроза: Docker и Root-доступ**

В основе модели безопасности Docker лежит фундаментальный факт: **по умолчанию демон Docker (`dockerd`) работает с правами `root`**. Это означает, что любой пользователь или процесс, получивший доступ к управляющему сокету Docker, фактически получает `root`-доступ ко всей хост-системе.

---

## **2. Векторы атак**

### **2.1. Docker Socket (`/var/run/docker.sock`)**

Это основной способ локального взаимодействия с демоном. 

- **Права доступа:** По умолчанию сокет принадлежит пользователю `root` и группе `docker` с правами `660`. Это означает, что любой пользователь, добавленный в группу `docker`, имеет полный, неавторизованный доступ к Docker API.
- **Угроза:** Если злоумышленник получает доступ к сокету (напрямую или пробросив его в контейнер), он может запустить привилегированный контейнер и захватить контроль над хостом.

**Сценарий атаки (побег из контейнера с проброшенным сокетом):**

```sh
# 1. Злоумышленник находится в контейнере, куда по ошибке смонтировали сокет
# (docker run -v /var/run/docker.sock:/var/run/docker.sock ...)

# 2. Он устанавливает docker-cli и запускает новый контейнер, 
# монтируя корневую ФС хоста.
docker run -it --rm -v /:/host busybox chroot /host

# 3. Результат: он получает root-шелл на хост-системе.
whoami # -> root
```

### **2.2. Сетевой доступ (TCP)**

Демон можно настроить на прослушивание сетевых портов, что создает дополнительный вектор атаки.

- **Порт `2375` (HTTP):** **КРАЙНЕ НЕБЕЗОПАСНО.** Это незащищенный порт. Любой, кто может подключиться к нему по сети, получает полный контроль над демоном Docker.
- **Порт `2376` (HTTPS):** Безопасный вариант, использующий TLS для аутентификации и шифрования. Клиентские сертификаты обычно хранятся в `~/.docker/`, и их защита критически важна.
- **SSH:** Еще один безопасный способ удаленного доступа, который использует аутентификацию SSH.

## **3. Повышение привилегий и побег из контейнера**

Если злоумышленник получил доступ к сокету Docker (напрямую на хосте или пробросив его внутрь контейнера), повышение привилегий до `root` на хосте становится тривиальной задачей.

### **Сценарий 1: Прямой доступ к сокету на хосте**

Классическая атака заключается в запуске привилегированного контейнера с монтированием корневой файловой системы хоста.

```sh
# Эта команда запускает контейнер, который имеет полный доступ ко всем устройствам хоста
# и монтирует файловую систему хоста в /host внутри контейнера.
docker run -it --rm --privileged -v /:/host busybox chroot /host

# После выполнения этой команды вы окажетесь в оболочке с правами root на хосте.
whoami
# -> root
```

### **Сценарий 2: Побег из контейнера с проброшенным сокетом**

Это очень распространенная ошибка конфигурации. Если сокет Docker монтируется внутрь контейнера, это позволяет процессам внутри него управлять демоном Docker на хосте.

```sh
# 1. Запускаем контейнер, внутрь которого проброшен сокет
docker run -it --rm -v /var/run/docker.sock:/var/run/docker.sock alpine

# 2. Внутри этого контейнера устанавливаем docker-cli
apk add --no-cache docker-cli

# 3. Выполняем ту же атаку, что и в сценарии 1, но уже изнутри контейнера
docker run -it --rm --privileged -v /:/host busybox chroot /host
```

## **3. Лучшие практики по защите (Hardening)**

### **1. Не запускайте процессы от `root` внутри контейнера**

    ### **Риск "Побега из контейнера" (Container Escape)**
    Это самая серьезная угроза. Процессы в контейнере выполняются на ядре хост-системы. Хотя контейнеры изолированы, эта изоляция не абсолютна.
    - **Общее ядро:** Если в ядре Linux обнаружится уязвимость, вредоносный процесс, запущенный с правами `root` (UID 0) внутри контейнера, может проэксплуатировать её и получить полный `root`-доступ к хост-системе.
    - **UID 0 = UID 0:** Для ядра Linux пользователь `root` с UID 0 внутри контейнера — это тот же самый `root` с UID 0, что и на хосте. Разница лишь в ограничениях (namespaces, cgroups), которые накладывает Docker. Уязвимость в ядре может позволить обойти эти ограничения.

    Если же процесс в контейнере запущен от имени непривилегированного пользователя, его возможности для эксплуатации уязвимостей ядра значительно сокращаются.

    ### **Проблемы с правами на файлы в монтированных томах (Volumes)**
    Когда процесс, запущенный от `root` в контейнере, создает файлы в подключенном томе (volume), эти файлы на хост-системе также будут принадлежать пользователю `root`.
    - **Пример:** Вы монтируете директорию `./data` с хоста в контейнер. Приложение в контейнере (работающее от `root`) создает файл `log.txt`. На хост-системе владельцем `log.txt` будет `root`.
    - **Последствия:** Вы, как обычный пользователь на хосте, не сможете редактировать или удалять этот файл без использования `sudo`. Это создает неудобства и может нарушить работу скриптов сборки или CI/CD.

**Как правильно делать:** Создайте непривилегированного пользователя в `Dockerfile`.

```dockerfile
FROM debian:bullseye-slim

# 1. Выполняем действия от root (установка пакетов)
RUN apt-get update && apt-get install -y curl && rm -rf /var/lib/apt/lists/*

    # 2. Создаем группу и пользователя с фиксированным UID/GID
    # Использование фиксированных ID помогает избежать проблем с правами на файловых системах
    RUN groupadd --gid 1001 myuser && \
        useradd --uid 1001 --gid 1001 -m myuser

# 3. Копируем файлы и устанавливаем владельца
WORKDIR /app
COPY --chown=myuser:myuser . .

# 4. Переключаемся на созданного пользователя
USER myuser

# 5. Запускаем приложение от его имени
CMD ["./my-application"]
```

### **2. Используйте минималистичные образы**

#### **Образы Distroless: Максимальная безопасность**

**Distroless-образы от Google** — это базовые образы, которые содержат только ваше приложение и его runtime-зависимости (например, `glibc`, `openssl`). 

**Что в них отсутствует:**
-   Оболочки (`/bin/sh`, `bash`)
-   Менеджеры пакетов (`apt`, `apk`)
-   Стандартные утилиты (`ls`, `ps`, `curl`, `wget`)

**Пример: Сборка Go-приложения с помощью Distroless**
```dockerfile
# === Этап 1: Сборка ===
# Используем полноценный образ Go для компиляции
FROM golang:1.19 as builder

WORKDIR /app
COPY . .

# Собираем статически скомпилированный бинарный файл
RUN CGO_ENABLED=0 GOOS=linux go build -o my-app .

# === Этап 2: Финальный образ ===
# Используем базовый образ distroless
FROM gcr.io/distroless/static-debian11

# Копируем только скомпилированный бинарный файл из этапа сборки
COPY --from=builder /app/my-app /

# Указываем команду для запуска
CMD ["/my-app"]
```

**Главный компромисс: Сложность отладки**
Поскольку в образе нет shell, стандартная команда `docker exec -it my-container /bin/sh` не сработает. Эта проблема решаема с помощью специальных техник.

> **Подробное руководство по отладке distroless-контейнеров находится в файле [Docker: Справочник команд и руководство по отладке](./fix_problem.md).**

### **3. Управляйте правами (Capabilities)**

- **Никогда не используйте `--privileged`**. Этот флаг отключает почти все механизмы изоляции.
- **Используйте `--cap-drop=ALL` и `--cap-add`**: По умолчанию отключайте все права, а затем добавляйте только те, которые действительно необходимы вашему приложению (например, `NET_BIND_SERVICE` для прослушивания портов ниже 1024).

### **4. Не монтируйте Docker-сокет в контейнеры**

Если это абсолютно необходимо (например, для CI/CD), используйте прокси с авторизацией, которые ограничивают доступные команды API (например, [docker-socket-proxy](https://github.com/Tecnativa/docker-socket-proxy)).

### **5. Включите `seccomp` и `AppArmor`/`SELinux`**

Эти профили безопасности ограничивают системные вызовы (syscalls), которые может делать контейнер, обеспечивая дополнительный уровень защиты на уровне ядра.

## **4. Инструменты для сканирования и аудита**

- **Trivy:** Сканер уязвимостей для образов контейнеров. Прост в использовании и эффективен.
  ```sh
  trivy image my-app:latest
  ```
- **Dive:** Инструмент для исследования слоев Docker-образа. Помогает найти и устранить "раздутые" слои, уменьшая размер и поверхность атаки.
  ```sh
  dive my-app:latest
  ```
- **Docker Bench Security:** Скрипт, который проверяет вашу конфигурацию Docker на соответствие лучшим практикам безопасности.
  ```sh
  docker run -it --rm --net host --pid host --userns host --cap-add audit_control \
      -v /var/lib/docker:/var/lib/docker:ro \
      -v /etc:/etc:ro \
      docker/docker-bench-security
  ```

## **5. Rootless Docker: Современное решение**

**Rootless Docker** — это режим, в котором и демон Docker, и контейнеры запускаются от имени **непривилегированного пользователя**. Это наиболее эффективный способ защиты от атак, связанных с повышением привилегий.

- **Как это работает:** Используются **пространства имен пользователей (user namespaces)** ядра Linux. UID `root` (0) внутри контейнера сопоставляется с UID непривилегированного пользователя на хосте (например, 1001).
- **Преимущества:** Даже если злоумышленник сбежит из контейнера или получит доступ к сокету, он получит права не `root` на хосте, а лишь права того пользователя, от имени которого запущен Rootless Docker.

- **Установка:** 
  ```sh
  # Устанавливаем необходимые утилиты
  sudo apt-get install -y uidmap
  # Запускаем установочный скрипт от обычного пользователя
  dockerd-rootless-setuptool.sh install
  ```

- **Ограничения:** Rootless-режим имеет некоторые ограничения, связанные с работой сети (например, невозможность пробрасывать порты ниже 1024 без дополнительных настроек) и драйверов хранения.
