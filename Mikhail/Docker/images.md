# **Docker-образы: от создания до распространения**

---

## **1. Что такое образ Docker?**

**Образ (Image)** — это неизменяемый (immutable) шаблон, который содержит все необходимое для запуска приложения: код, среду выполнения, библиотеки, переменные окружения и конфигурационные файлы. Образы состоят из слоев, доступных только для чтения, что обеспечивает эффективность хранения и переиспользования.

---

## **2. Жизненный цикл образа: основные команды**

| Команда | Описание |
| :--- | :--- |
| `docker build -t <имя>:<тег> .` | Собирает образ из `Dockerfile` в текущей директории. |
| `docker images` | Показывает все образы, имеющиеся на хосте. |
| `docker pull <имя>:<тег>` | Скачивает образ из registry (например, Docker Hub). |
| `docker push <имя>:<тег>` | Загружает образ в registry. |
| `docker rmi <имя>:<тег>` | Удаляет образ. |
| `docker tag <исходный> <целевой>` | Создает новый тег (алиас) для существующего образа. |
| `docker history <имя>:<тег>` | Показывает слои, из которых состоит образ, и команды их создания. |

## **3. Управление образами и очистка**

### **"Висячие" и неиспользуемые образы**

**"Висячие" образы (dangling images)** — это слои, на которые больше не ссылается ни один тегированный образ. В списке `docker images` они отображаются как `<none>:<none>`.

Основная причина их появления — пересборка существующего образа с тем же тегом. Например, когда вы собираете `my-app:latest` заново, старый образ с этим тегом не удаляется, а теряет свой тег и становится "висячим".

**Промежуточные слои сборки** также могут оставаться в системе. Они не имеют имени и тега, но видны по их ID. Это происходит, если сборка была прервана или слои используются другими образами.

### **Команды для очистки**

| Команда | Описание |
| :--- | :--- |
| `docker images -f "dangling=true"` | Находит все "висячие" образы. |
| `docker image prune` | Удаляет все "висячие" образы. |
| `docker image prune -a` | Удаляет все неиспользуемые образы (те, от которых нет запущенных контейнеров). |
| `docker system prune -a --volumes` | **(Опасно)** Глобальная очистка: удаляет всё, что не используется — контейнеры, образы, сети и volumes. |

## **4. Перенос образов: `save`/`load` vs `export`/`import`**

Для переноса образов и контейнеров между системами без использования registry существуют две пары команд с принципиальными различиями.

### **`docker save` и `docker load`**

Эти команды работают с **образами**, сохраняя всю их структуру, включая слои, историю и метаданные.

- **`docker save`**: Создает `.tar`-архив из одного или нескольких образов.
  ```sh
  docker save -o my_images.tar my-image:latest another-image:1.0
  ```

- **`docker load`**: Загружает образы из `.tar`-архива, восстанавливая их в исходном виде.
  ```sh
  docker load -i my_images.tar
  ```

### **`docker export` и `docker import`**

Эти команды работают с **файловой системой контейнера**, а не с образом. Они создают "плоский" (flattened) архив без истории слоев.

- **`docker export`**: Создает `.tar`-архив файловой системы запущенного или остановленного контейнера.
  ```sh
  docker export my-container > my_container.tar
  ```

- **`docker import`**: Создает **новый** образ из `.tar`-архива файловой системы.
  ```sh
  cat my_container.tar | docker import - my-new-image:latest
  ```

### **Ключевые различия**

| Критерий | `save`/`load` | `export`/`import` |
| :--- | :--- | :--- |
| **Объект** | Образ (Image) | Файловая система контейнера |
| **Слои** | Сохраняются | Теряются (объединяются в один) |
| **История** | Сохраняется (`docker history`) | Теряется |
| **Метаданные** | Сохраняются (CMD, EXPOSE и т.д.) | Теряются |
| **Назначение** | Перенос/бекап образов | Создание "чистого" базового образа |

## **5. Продвинутые техники и анти-паттерны**

### **`docker commit`: анти-паттерн**

Команда `docker commit <контейнер> <новый_образ>` создает образ из текущего состояния контейнера. **Это считается плохой практикой, потому что:**
- **Нарушает воспроизводимость:** Невозможно понять, как образ был создан, в отличие от `Dockerfile`.
- **Раздувает образ:** Включает в себя временные файлы, логи и другие артефакты.
- **Скрывает историю:** Заменяет понятную историю слоев одной командой `commit`.

**Используйте `Dockerfile` для всех сборок.**

### **Объединение слоев (`--squash`)**

Флаг `docker build --squash` объединяет все слои, созданные в `Dockerfile`, в один.
- **Плюс:** Может незначительно уменьшить размер финального образа.
- **Минус:** Полностью **уничтожает кэширование слоев**, что делает последующие сборки очень медленными.

### **Схлопывание слоев с помощью `docker-squash`**

Встроенный флаг `docker build --squash` имеет существенный недостаток: он уничтожает весь кэш слоев. Более гибкой и мощной альтернативой является внешняя утилита **`docker-squash`**.

Она позволяет "схлопнуть" уже собранный образ, объединяя только нужные слои и сохраняя базовые слои нетронутыми. Это позволяет уменьшить размер образа, удалив временные файлы (например, кэш `apt` или `npm`), не жертвуя при этом кэшем базового образа.

**Принцип работы:**

1.  **Установка:**
    ```bash
    pip install docker-squash
    ```
2.  **Использование:**
    Утилита выгружает образ, схлопывает слои и загружает его обратно в Docker.
    ```bash
    # Схлопнуть последние 2 слоя
    docker-squash -f 2 my-image:latest -t my-image:squashed

    # Схлопнуть все слои, начиная с определенного (ID слоя можно взять из `docker history`)
    docker-squash -from 5a5295c74599 my-image:latest -t my-image:squashed
    ```

**Преимущества перед `docker build --squash`:**
*   **Сохранение кэша:** Не затрагивает базовые слои, позволяя Docker переиспользовать их при последующих сборках.
*   **Гибкость:** Позволяет точно указать, какие слои нужно объединить.
*   **Работа с существующими образами:** Можно оптимизировать образы, даже не имея доступа к их `Dockerfile`.

### **Реверс-инжиниринг образов**

**Внимание:** Это метод "последней надежды", если `Dockerfile` утерян безвозвратно, а не стандартная практика.

Эти утилиты анализируют слои образа и генерируют `Dockerfile`, который мог бы его создать. Они запускаются как Docker-контейнеры и требуют доступа к Docker-сокету хоста.

- **[dduvnjak/dockerfile-from-image](https://github.com/dduvnjak/dockerfile-from-image)**
  ```sh
  sudo docker run -v /var/run/docker.sock:/var/run/docker.sock --rm dduvnjak/dockerfile-from-image <IMAGE_ID>
  ```

- **[laniksj/dfimage](https://github.com/LanikSJ/dfimage)**
  ```sh
  sudo docker run -v /var/run/docker.sock:/var/run/docker.sock --rm laniksj/dfimage <IMAGE_ID>
  ```


### **Многоархитектурные образы (Multi-Arch)**

Современные CI/CD-системы позволяют собирать образы, которые могут работать на разных архитектурах процессоров (например, `amd64` и `arm64`). Это достигается с помощью `docker buildx`.

**Пример сборки:**
```sh
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t my-app:latest \
  --push .
```
Docker-демон на хосте автоматически выберет и запустит версию образа, соответствующую его архитектуре.

## **6. Оптимизация загрузки образов (`docker pull`)**

1.  **Настроить локальный кэширующий реестр (pull-through cache)**
    - Запустите легковесный дистрибутив `registry:2` на серверах или в непосредственной близости от нод.
    - Настройте Docker-демон на использование этого реестра в качестве зеркала (`registry-mirrors` в `/etc/docker/daemon.json`).
    - При первом скачивании образ закэшируется локально, и все последующие запросы будут обрабатываться мгновенно.

2.  **Использовать предзагрузку образов (Pre-pulling)**
    - В Kubernetes используйте политику `imagePullPolicy: IfNotPresent`. Контейнер не будет скачивать образ, если он уже есть на ноде.
    - Для запланированных обновлений можно использовать `CronJob` в Kubernetes или системный `cron`, который будет заранее скачивать нужные версии образов на все ноды кластера в часы низкой нагрузки.
