# Введение в безопасность Docker

В этом руководстве мы немного изучим архитектуру и модель безопасности Docker.

### Архитектура Docker

![Архитектура Docker](https://labs.iximiuz.com/content/files/tutorials/docker-security-introduction-a859718d/__static__/docker-security-docker-architecture-2.png)

Прежде чем перейти к деталям безопасности, стоит кратко рассказать об архитектуре Docker. По сути, это клиент-серверное приложение, где клиент общается с REST HTTP API. Взаимодействие между клиентом и сервером происходит либо локально через UNIX-сокет, либо удаленно по сети через HTTP или SSH.

По умолчанию Docker использует для всех коммуникаций UNIX-сокет, расположенный по адресу `/var/run/docker.sock`.

Сам сервер Docker также общается с реестрами контейнеров по HTTP для получения образов и выполнения таких задач, как создание и управление контейнерами и сетями.

### Просмотр трафика демона Docker

Мы можем просматривать трафик между клиентом и сервером Docker с помощью утилиты [`socat`](http://www.dest-unreach.org/socat/) и двух терминалов.

Сначала в первом терминале выполните эту команду, которая настроит `socat` для создания нового файла сокета и перенаправления всех запросов на сокет Docker:

`socat -v UNIX-LISTEN:/tmp/tempdock.sock,fork UNIX-CONNECT:/var/run/docker.sock`

Затем во втором терминале выполните следующую команду Docker, которая обратится к нашему временному сокету и запросит список образов.

`docker -H unix:///tmp/tempdock.sock images`

Вернувшись в первый терминал и немного прокрутив вверх, вы должны увидеть HTTP-запросы и ответы между клиентом и сервером, что немного проясняет, как работает Docker API. Если вы знакомы с HTTP-запросами, вы увидите, что это выглядит как довольно типичный REST API.

После завершения просмотра трафика в первом терминале (где вы запускали socat) нажмите `CTRL-C`, чтобы вернуться в командную строку.

### Системные компоненты Docker

![Системные компоненты Docker](https://labs.iximiuz.com/content/files/tutorials/docker-security-introduction-a859718d/__static__/docker-system-components.png)

Docker работает вместе с другими компонентами, которые используются для запуска контейнеров на хосте. Помимо основного демона Docker, есть демон [containerd](https://github.com/containerd/containerd) и [runc](https://github.com/opencontainers/runc/), который фактически запускает контейнеры.

### Поверхность атаки Docker

Как правило, поверхностью атаки установки Docker являются локальные файлы сокетов. Помимо сокета Docker (в `/run/docker.sock`), есть также сокет containerd, который обычно находится в `/run/containerd/containerd.sock` (Примечание: вы также увидите эти файлы в `/var/run`, который является символической ссылкой на `/run`).

Если демон Docker был настроен на прослушивание сети, по умолчанию он будет слушать порт `2375/TCP` или `2376/TCP`. Порт `2375` используется для небезопасной конфигурации, где любой, кто может достичь порта, может выполнять команды Docker и, вероятно, получить root-доступ к базовому хосту. Порт `2376` используется, когда настроена аутентификация TLS.

### Аутентификация демона Docker - Локальная

Когда локальный пользователь пытается получить доступ к демону Docker, доступ контролируется правами доступа к файлу сокета. По умолчанию файл сокета принадлежит пользователю `root` и группе `docker` и имеет права доступа `660`, что означает, что любой пользователь в группе `docker` будет иметь доступ к сокету Docker.

Выполнение приведенной ниже команды может подтвердить права доступа к сокету:

`ls -al /run/docker.sock`

### Удаленная аутентификация демона Docker - TLS

Если для демона Docker настроена аутентификация, скорее всего, это будут клиентские сертификаты TLS. Клиентские сертификаты по умолчанию хранятся в `~/.docker`, поэтому управление доступом к этому каталогу важно для их защиты. В [документации Docker](https://docs.docker.com/engine/security/protect-access/#use-tls-https-to-protect-the-docker-daemon-socket) есть подробности о том, как это настроить.

### Удаленная аутентификация демона Docker - SSH

Также возможно получить доступ к демону Docker через SSH. Это эффективно использует комбинацию прав SSH (пользователь должен иметь возможность подключаться по SSH к хосту, на котором работает демон Docker) и прав доступа к файлам, которые мы обсуждали ранее. В [документации Docker](https://docs.docker.com/engine/security/protect-access/#use-ssh-to-protect-the-docker-daemon-socket) есть подробности о том, как это настроить. Если требуется удаленный доступ к демону Docker, это, вероятно, будет более простым в управлении и более безопасным вариантом, чем предоставление доступа через TLS.

### Авторизация демона Docker

По умолчанию концепции авторизации для запросов к демону Docker не существует. Любой пользователь, имеющий доступ к сокету Docker, имеет полный доступ ко всем командам. В Docker есть концепция [плагинов авторизации](https://docs.docker.com/engine/extend/plugins_authorization/), но они не получили широкого распространения.

### Безопасность процессов контейнера

Одной из ключевых особенностей контейнеров Docker является то, что они являются просто процессами (подробнее об этом [здесь](https://labs.iximiuz.com/tutorials/containers-are-processes-d17b1df8)), использующими общее ядро Linux. В результате важно учитывать, какой пользователь используется внутри контейнеров. С точки зрения безопасности, к сожалению, по умолчанию все контейнеры запускаются от имени пользователя `root` внутри контейнера, если в `Dockerfile` нет явного оператора `USER` или если для смены пользователя не используется shell-скрипт как часть точки входа контейнера.

Мы можем увидеть это в действии, запустив новый контейнер с использованием очень простого образа веб-сервера под названием `ctrsec/swc`, который запускает процесс `simple-webserver`:

`docker run -d --name=rootwebserver ctrsec/swc`

Затем, если мы посмотрим на процессы на хосте, мы увидим процесс `simple-webserver`, работающий от имени пользователя `root`:

`ps -fC simple-webserver`

Вывод покажет процесс simple-webserver, который работает от имени `root`.

`UID          PID    PPID  C STIME TTY          TIME CMD root       19290   19265  0 14:59 ?        00:00:00 /simple-webserver`

После выполнения этих шагов остановите контейнер:

`docker stop rootwebserver`

Также возможно иметь образ контейнера, который не запускается от имени пользователя root. Это делается с помощью директивы `USER` в `Dockerfile`, и контейнеры на основе этого образа будут работать с UID не-root пользователя в зависимости от того, что настроено в образе.

Чтобы показать пример этого, мы будем использовать не-root версию образа `swc` под названием `swcnr`, которая работает с UID `3456`:

`docker run -d --name=nonrootwebserver ctrsec/swcnr`

Теперь выполним нашу команду ps из предыдущего примера:

`ps -fC simple-webserver`

Мы видим, что UID отличается:

`UID          PID    PPID  C STIME TTY          TIME CMD 3456       20138   20114  0 15:04 ?        00:00:00 /simple-webserver`

После того, как мы это увидели, остановите и этот веб-сервер:

`docker stop nonrootwebserver`

### Повышение привилегий в Docker

Как только у вас есть доступ к сокету Docker в данной системе, получение привилегий `root` на хосте должно быть тривиальным. Есть несколько способов сделать это, но самый простой — это [Самая бессмысленная команда Docker](https://zwischenzugs.com/2015/06/24/the-most-pointless-docker-command-ever/).

Если вы выполните команду:

`whoami`

Вы увидите, что в настоящее время вы являетесь пользователем `laborant` на хосте. Теперь выполните самую бессмысленную команду Docker.

`docker run -ti --privileged --net=host --pid=host --ipc=host --volume /:/host busybox chroot /host`

А затем снова выполните whoami. Теперь вы пользователь `root`!

Причина, по которой это работает, заключается в том, что, хотя Docker по умолчанию предоставляет уровни изоляции, он позволяет любому, кто может выполнять команды Docker, удалять любые или все эти уровни.

После выполнения этой команды не забудьте ввести `exit`, чтобы снова работать от имени пользователя `laborant`.

### Опасности '--privileged'

Одним из наиболее важных элементов бессмысленной команды Docker является флаг `--privileged`, который мы ей передали. Он по сути удаляет большинство основных защит.

### Побег из контейнера

Помимо прямого доступа к сокету Docker с хоста, вы также можете увидеть сокет Docker внутри контейнера. Когда сокет Docker монтируется в контейнер, относительно просто получить root-доступ к базовому хосту. Чтобы продемонстрировать это, сначала запустите новый контейнер с смонтированным внутри него сокетом Docker:

`docker run -it -v /var/run/docker.sock:/var/run/docker.sock raesene/alpine-containertools /bin/bash`

Поскольку в этом образе контейнера установлен клиент `docker`, вы можете выполнять команды docker изнутри контейнера. Например, `docker ps` покажет список запущенных контейнеров на хосте.

Затем просто выполните нашу бессмысленную команду Docker:

`docker run -ti --privileged --net=host --pid=host --ipc=host --volume /:/host busybox chroot /host`

На этом этапе покажется, что вы вернулись за пределы контейнера как пользователь `root`, но на самом деле это еще один контейнер, работающий на хосте!

Чтобы вернуться в исходную оболочку, используйте команду `exit` дважды. Первый раз вернет вас в первый контейнер, а второй раз — на хост.

### Rootless Docker

Одной из проблем безопасности Docker является то, что демон работает от имени `root`, поэтому любой злоумышленник, получивший доступ к сокету Docker, сможет повысить свои привилегии на хосте до root. Однако возможно запустить демон Docker от имени обычного пользователя, используя [rootless Docker](https://docs.docker.com/engine/security/rootless/).

В этой настройке Docker работает от имени обычного пользователя, что ограничивает влияние злоумышленника, получившего доступ к сокету, а также снижает влияние побега из контейнера.

Мы можем настроить rootless Docker на хосте, на котором уже есть стандартная "rootful" установка.

Сначала установите пакет uidmap, который используется rootless Docker:

`sudo apt update && sudo apt install -y uidmap`

Затем выполните предоставленный Docker shell-скрипт для установки Rootless Docker:

`dockerd-rootless-setuptool.sh install --force`

После завершения установки вы можете использовать docker context, чтобы показать исходную конфигурацию и новую rootless:

`docker context ls`

После того, как мы установили новую rootless-установку, мы можем повторить упражнение, которое мы выполнили ранее по безопасности процессов контейнеров, чтобы показать эффекты использования rootless docker.

Сначала запустите новый простой контейнер веб-сервера. Этот образ — тот, который в прошлый раз работал от имени root.

`docker run --name=rootlesswebserver -d ctrsec/swc`

Затем, если мы посмотрим на процессы на хосте, мы увидим, как изменился вывод.

`ps -fC simple-webserver`

Вывод покажет процесс `simple-webserver`, работающий от имени пользователя `laborant`, а не от имени `root`, как в прошлый раз.

`UID          PID    PPID  C STIME TTY          TIME CMD laborant    2143    2116  0 18:25 ?        00:00:00 /simple-webserver`

Теперь давайте подтвердим, как это выглядит внутри контейнера. Мы можем сделать это, выполнив команду `id`.

`docker exec rootlesswebserver id`

которая должна вернуть что-то вроде приведенного ниже, показывая, что содержащийся процесс думает, что он работает от имени `root`!

`uid=0(root) gid=0(root) groups=0(root),10(wheel)`

Rootless Docker работает с использованием [пространств имен пользователей](https://man7.org/linux/man-pages/man7/user_namespaces.7.html) и переназначения UID внутри контейнера на другой на хосте. В этом случае он переназначает UID 0 внутри контейнера на UID 1001 на хосте, который является UID пользователя `laborant`.
