# **Управление данными в Docker: Volumes, Bind Mounts и tmpfs**

---

## **1. Проблема: эфемерность контейнеров**

Контейнеры по своей природе **эфемерны** (временны). После удаления контейнера все данные, созданные в его файловой системе, безвозвратно теряются. Для приложений, которым требуется сохранять состояние (базы данных, пользовательские файлы, логи), такой подход неприемлем.

Docker решает эту проблему, предоставляя механизмы для хранения данных **вне контейнера**, на хост-машине.

---

## **2. Сравнение способов хранения данных**

| Характеристика | Docker Volumes | Bind Mounts | tmpfs Mounts |
| :--- | :--- | :--- | :--- |
| **Где хранятся** | Управляемая Docker директория на хосте (`/var/lib/docker/volumes/`) | Произвольный файл или директория на хосте | Оперативная память (RAM) хоста |
| **Управление** | Через Docker CLI и Docker Compose | Через Docker CLI и Docker Compose | Через Docker CLI и Docker Compose |
| **Персистентность** | **Да.** Данные сохраняются после удаления контейнера | **Да.** Файлы остаются на хосте | **Нет.** Данные исчезают при остановке контейнера |
| **Переносимость** | **Высокая.** Не зависят от структуры ФС хоста | **Низкая.** Жестко привязаны к пути на хосте | Неприменимо |
| **Основной сценарий**| Хранение данных приложений (БД, статика) | Разработка, проброс конфигов, "живая" перезагрузка | Хранение временных, некритичных данных (кэш, секреты) |
| **Безопасность** | **Высокая.** Изолированы от других процессов | **Низкая.** Возможны конфликты прав доступа (UID/GID) и доступ к ФС хоста | **Высокая.** Данные не записываются на диск |
| **Синтаксис в Compose** | `volumes` (top-level) и `services.volumes` | `services.volumes` (с указанием пути) | `services.tmpfs` |

## **3. Docker Volumes (Рекомендуемый способ)**

**Volume (том)** — это директория на хосте, которой полностью управляет Docker. Это **предпочтительный** и самый надежный способ для хранения персистентных данных.

### **Именованные vs Анонимные тома**

- **Именованные тома (Named Volumes):** Вы даете тому конкретное имя (например, `postgres-data`). Это лучший вариант: ими легко управлять, их можно переиспользовать и найти.
  - **Пример:** `-v postgres-data:/var/lib/postgresql/data` или `--mount type=volume,source=postgres-data,target=...`

- **Анонимные тома (Anonymous Volumes):** Docker создает том со случайным хеш-именем. Их сложно найти и переиспользовать. Они создаются, когда вы указываете только путь в контейнере.
  - **Пример:** `-v /var/lib/postgresql/data`
  - **Примечание:** Анонимные тома сохраняются после удаления контейнера, но если вы не знаете их ID, найти их можно только командой `docker volume ls`.

> **Рекомендация:** Всегда используйте **именованные тома** для данных, которые должны сохраняться.

### **Синтаксис: `--mount` против `-v`**

- `--mount`: Более новый, подробный и **рекомендуемый** синтаксис. Явно указывает тип монтирования (`volume`, `bind`, `tmpfs`).
  - `--mount type=volume,source=my-volume,target=/app/data`
- `-v`: Более короткий и старый синтаксис. Менее очевиден, но все еще широко используется.
  - `-v my-volume:/app/data`

### **Пример: `docker-compose.yml` с PostgreSQL**

Определение сервисов и томов в `docker-compose.yml` — стандарт индустрии.

```yaml
version: '3.8'

services:
  db:
    image: postgres:14
    container_name: my-postgres-db
    environment:
      - POSTGRES_PASSWORD=mysecretpassword
    # Монтируем именованный том 'postgres-data' в контейнер
    volumes:
      - postgres-data:/var/lib/postgresql/data
    restart: always

# Объявляем том на верхнем уровне для централизованного управления
volumes:
  postgres-data:
    # Docker использует драйвер по умолчанию ('local')
    driver: local
```
**Запуск:** `docker-compose up -d`. Docker Compose автоматически создаст том `postgres-data`.

### **Основные команды для управления томами**

| Команда | Описание |
| :--- | :--- |
| `docker volume create <имя>` | Создать новый том. |
| `docker volume ls` | Показать все тома. |
| `docker volume inspect <имя>` | Показать детальную информацию о томе (включая путь на хосте). |
| `docker volume rm <имя>` | Удалить том (том не должен использоваться контейнером). |
| `docker volume prune` | Удалить все неиспользуемые тома. |

## **4. Bind Mounts**

**Bind Mount** — это прямое монтирование файла или директории с хост-машины в контейнер. Docker не управляет этими файлами.

**Основные сценарии использования:**
- **Разработка:** Проброс исходного кода в контейнер для "живой" перезагрузки.
- **Конфигурация:** Передача статических конфигурационных файлов (например, `nginx.conf`).

### **Риски и особенности**
- **Права доступа:** UID/GID пользователя на хосте может не совпадать с UID/GID внутри контейнера, что приводит к ошибкам доступа (permission denied). Особенно актуально для Linux.
- **Маскировка файлов:** Если вы монтируете директорию с хоста в директорию контейнера, где уже были файлы, они станут недоступны (будут "замаскированы" файлами с хоста).

### **Пример: `docker-compose.yml` для разработки**

```yaml
version: '3.8'

services:
  web:
    image: node:18-alpine
    container_name: my-app
    working_dir: /app
    # Монтируем текущую директорию (.) в /app в контейнере
    volumes:
      - .:/app
    command: "npm start"
```

## **5. tmpfs Mounts**

**tmpfs** монтирует директорию в оперативную память хоста. Данные не записываются на диск и исчезают при остановке контейнера.

**Основное применение:**
- Хранение временных, некритичных данных (например, кэш).
- Хранение секретов, которые не должны оставаться на диске.

### **Пример с Docker CLI**

```sh
docker run -d --name temp-work \
  --mount type=tmpfs,destination=/app/cache \
  nginx:latest
```

### **Пример в Docker Compose**
```yaml
version: '3.8'

services:
  nginx:
    image: nginx:latest
    container_name: temp-work
    # Монтируем tmpfs в /app/cache
    tmpfs: /app/cache
```

## **6. Ключевые рекомендации и лучшие практики**

1.  **Volumes для данных.** Для любых данных, которые должны пережить контейнер (БД, загрузки), всегда используйте **именованные тома**.
2.  **Bind Mounts для разработки и конфигов.** Идеальны для проброса исходного кода и статических конфигурационных файлов.
3.  **Определяйте всё в `docker-compose.yml`.** Это делает вашу конфигурацию переносимой, версионируемой и легко читаемой.
4.  **Управляйте данными через контейнеры.** Не изменяйте файлы в `/var/lib/docker/volumes/` напрямую. Используйте утилиты (например, `pg_dump`) или API вашего приложения.
5.  **Настройте резервное копирование.** Регулярно создавайте бэкапы данных из томов. Для этого можно запустить временный контейнер, который подключится к тому и заархивирует его содержимое.
6.  **Избегайте анонимных томов.** Они "замусоривают" систему и не удаляются автоматически, если контейнер не был запущен с флагом `--rm`.
7.  **Используйте общий том для общих данных.** Если нескольким контейнерам нужен доступ к одним и тем же данным, монтируйте к ним один и тот же именованный том. Флаг `--volumes-from` устарел.
