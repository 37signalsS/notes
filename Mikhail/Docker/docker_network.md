### **Сети в Docker**

Docker предоставляет различные типы сетей для управления коммуникацией между контейнерами и внешним миром.

- **Bridge:**
    - Сеть по умолчанию.
    - Изолирует контейнеры, подключенные к ней, от сетей других контейнеров, но позволяет им общаться между собой.
    - Для доступа извне требуется проброс портов.
    - Docker создает виртуальный мост `docker0` на хосте.
    - Контейнеры в одной bridge-сети могут пинговать друг друга по IP-адресам.
    - Из контейнера в bridge-сети можно выходить в интернет (если на хосте есть доступ).

- **Host:**
    - Убирает сетевую изоляцию между контейнером и хостом.
    - Контейнер использует сетевой стек хоста напрямую.
    - Очень высокая производительность, но теряется безопасность и изоляция.

- **None:**
    - Полностью отключает сеть для контейнера.
    - Контейнер имеет свой сетевой стек, но без внешнего интерфейса.
    - Полезно для выполнения изолированных задач или пакетных заданий, не требующих сети.

- **Overlay:**
    - Используется для связи контейнеров, запущенных на разных хостах.
    - Является основой для сетевого взаимодействия в Docker Swarm.
    - Создает распределенную сеть, которая "накладывается" поверх сетей хост-машин.

- **Macvlan:**
    - Позволяет присвоить контейнеру MAC-адрес, делая его полноценным участником физической сети.
    - Контейнер будет виден как отдельное устройство в сети, подключенное к тому же коммутатору, что и хост.

### **Управление сетями**

- **Созданить новую сеть испльзуя драйвер bridge, подсеть и шлюз**
  ```sh
  docker network create --driver bridge --subnet=182.18.0.0/24 --gateway=182.18.0.1 wp-mysql-network
  ```

- **Подключить контейнер к сети:**
  ```sh
  docker network connect <network-name> <container-name>
  ```

- **Просмотр информации о сети:**
  ```sh
  docker network inspect <network-name>
  ```

- **Просмотр детальной информации о сети `bridge`**
  ```sh
  docker network inspect bridge
  ```

- **Список всех докер сетей**
  ```sh
  docker network ls
  ```

- **Определить все настройки контейнера и в том числе принадлежность к определенной сети**
  ```sh
  docker inspect alpine-1
  ```

- **Запустить контеней привязав его к определенной сети**
  ```sh
  docker run --name alpine-2 --network bridge -d alpine
  ```

- **Разрешение имен в пользовательских сетях**

  Если вы создаете свою собственную bridge-сеть, Docker включает встроенный DNS-сервер. Это означает, что вы можете обращаться к контейнерам по их именам, а не только по IP-адресам.

  **Как это работает:**

  1.  Когда контейнер подключается к пользовательской сети, Docker автоматически добавляет запись в файл `/etc/resolv.conf` внутри контейнера.
  2.  Эта запись указывает на встроенный DNS-сервер Docker (обычно `127.0.0.11`).
  3.  Когда вы пытаетесь обратиться к другому контейнеру по имени (например, `ping my-container`), DNS-запрос отправляется на этот сервер.
  4.  DNS-сервер Docker сопоставляет имя контейнера с его IP-адресом и возвращает его, позволяя установить соединение.

### **Утилита `brctl` для анализа bridge-сетей**

Для более глубокого анализа сетей типа `bridge` на хосте можно использовать утилиту `brctl`. Она позволяет просматривать существующие сетевые мосты и интерфейсы, подключенные к ним.

**Использование:**

Команда `brctl show` отображает все активные сетевые мосты на хосте.

```sh
brctl show
```
```
bridge name     bridge id               STP enabled     interfaces
docker0         8000.0242ac110002       no              veth1a2b3c4
                                                        veth5d6e7f8
```
*   **`bridge name`**: Имя сетевого моста. По умолчанию Docker создает мост с именем `docker0`.
*   **`bridge id`**: Уникальный идентификатор моста.
*   **`STP enabled`**: Показывает, включен ли протокол STP (Spanning Tree Protocol).
*   **`interfaces`**: Самая важная колонка в контексте Docker. Здесь перечислены все сетевые интерфейсы, подключенные к мосту. Для каждого запущенного контейнера, использующего сеть `bridge`, здесь будет отображаться его виртуальный Ethernet-интерфейс (`veth`).

Эти `veth`-интерфейсы представляют собой **виртуальные "патч-корды"** (вет-пары): один конец "кабеля" подключен к сетевому пространству имен контейнера (и виден внутри него как `eth0`), а другой — к мосту `docker0` на хосте. Именно через эту связь контейнеры в bridge-сети общаются друг с другом и с внешним миром (через NAT).

### **Проблема: Пропавший трафик Docker и iptables**

**Симптомы:**

- Вы настроили `iptables` с политикой `DROP` для `INPUT` и `FORWARD`.
- Запустили Docker-контейнер с пробросом порта (`-p 8080:80`).
- Локально (`curl http://localhost:8080`) контейнер доступен.
- Снаружи (`curl http://<host_ip>:8080`) — нет (`Connection refused`).

**Причина:**

Проблема в том, что `iptables` блокирует трафик, предназначенный для контейнера. Docker для проброса портов использует цепочку `FORWARD`, а не `INPUT`.

Когда пакет приходит на хост, `iptables` обрабатывает его так:
1.  **Цепочка `PREROUTING` (таблица `nat`):** Docker подменяет адрес назначения на внутренний IP-адрес контейнера.
2.  **Цепочка `FORWARD`:** Пакет перенаправляется к контейнеру.

Если у вас установлена политика `iptables -P FORWARD DROP`, то `iptables` отбросит этот пакет.

**Диагностика:**

Посмотрите счётчики пакетов в `iptables`:
```sh
sudo iptables -L -v -n
```
Вы увидите, что счётчики отброшенных пакетов (dropped) в цепочке `FORWARD` растут при попытке доступа к контейнеру.

**Решение:**

Нужно явно разрешить `iptables` перенаправлять трафик в Docker.

**Вариант 1 (простой):**

Разрешить весь трафик, идущий через интерфейс `docker0`.
```sh
sudo iptables -A FORWARD -o docker0 -j ACCEPT
```

**Вариант 2 (более строгий):**

Разрешить только установленные и связанные соединения.
```sh
# Разрешить трафик из контейнера наружу
sudo iptables -A FORWARD -i docker0 -o eth0 -j ACCEPT

# Разрешить установленные и связанные соединения к контейнеру
sudo iptables -A FORWARD -i eth0 -o docker0 -m state --state RELATED,ESTABLISHED -j ACCEPT
```
*Примечание: Замените `eth0` на ваш реальный сетевой интерфейс.*

**Вывод:**

- Трафик, который пробрасывается в Docker-контейнер, проходит через цепочку `FORWARD` в `iptables`.
- Если вы используете `iptables` с политикой `DROP`, не забудьте добавить правила для `FORWARD`, чтобы разрешить доступ к контейнерам.

**По умолчанию существуют/создаються три вида сетей в докере: bridge, none, host**
