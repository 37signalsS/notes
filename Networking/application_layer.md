### Прикладной уровень (L7)

#### DNS (Domain Name System)

Это система, которая переводит доменные имена (например, google.com) в IP-адреса (например, 142.250.72.174). Это необходимо, потому что компьютеры работают с IP-адресами, а людям удобнее использовать понятные имена.

DNS работает по принципу иерархии:

1.  **Корневые серверы** — отвечают за верхний уровень системы.
2.  **TLD-серверы (Top-Level Domain)** — отвечают за домены первого уровня (например, .com, .org).
3.  **Авторитетные серверы** — содержат информацию о конкретных доменах.

Файл `/etc/resolv.conf` содержит настройки DNS-серверов, которые используются системой. Вы можете просмотреть его содержимое:

```bash
cat /etc/resolv.conf
```
Пример вывода:
```
nameserver 8.8.8.8
nameserver 8.8.4.4
```

##### Локальное перенаправление DNS через `/etc/hosts`

Файл `/etc/hosts` — это простейший механизм разрешения имен. Система проверяет его **перед** тем, как отправить запрос на DNS-сервер. Это позволяет локально переопределить IP-адрес для любого домена.

```
# /etc/hosts
127.0.0.1   localhost
1.2.3.4     example.com
```
При попытке открыть `example.com` ваш компьютер будет обращаться к `1.2.3.4`, игнорируя реальную DNS-запись.

**Процесс DNS-запроса (рекурсивный и итеративный)**

Существует два основных типа DNS-запросов:

1.  **Рекурсивный запрос (Recursive Query):**
    *   Клиент (например, ваш компьютер) отправляет запрос локальному DNS-серверу (резолверу) и просит его найти IP-адрес.
    *   Сервер берёт на себя всю работу: он опрашивает другие DNS-серверы (корневые, TLD, авторитетные) до тех пор, пока не найдёт ответ.
    *   Клиент получает окончательный ответ: либо IP-адрес, либо сообщение об ошибке.
    *   Этот тип запроса используется между клиентом и его DNS-резолвером.

2.  **Итеративный (нерекурсивный) запрос (Iterative/Non-Recursive Query):**
    *   DNS-сервер, получив запрос, возвращает лучший ответ, который у него есть на данный момент. 
    *   Если у сервера нет точного IP-адреса, он возвращает адрес другого DNS-сервера, который может знать больше (например, адрес сервера более высокого уровня).
    *   Клиент (в данном случае — другой DNS-сервер) должен сам отправить новый запрос следующему серверу.
    *   Этот процесс повторяется, пока не будет найден авторитетный сервер, который даст окончательный ответ.
    *   Этот тип запроса используется преимущественно при общении DNS-серверов между собой.

**Общая схема работы:**

1.  Ваш компьютер отправляет **рекурсивный** запрос своему DNS-резолверу (например, серверу провайдера).
2.  DNS-резолвер начинает серию **итеративных** запросов к другим серверам:
    *   Сначала к корневому серверу.
    *   Затем к серверу доменной зоны верхнего уровня (например, `.com`).
    *   Затем к авторитетному серверу для конкретного домена (например, `google.com`).
3.  Получив IP-адрес от авторитетного сервера, резолвер возвращает его вашему компьютеру.

**DNS и транспортные протоколы (UDP/TCP)**

DNS использует порт 53 и может работать как по UDP, так и по TCP.

**Почему DNS предпочитает UDP?**

В большинстве случаев DNS использует UDP по следующим причинам:

*   **Скорость:** UDP — протокол без установления соединения. Ему не требуется "тройное рукопожатие" (как в TCP), что значительно снижает задержку.
*   **Низкие накладные расходы:** DNS-запросы и ответы обычно маленькие и помещаются в один пакет. UDP имеет меньший заголовок, что делает его более эффективным для таких коротких обменов данными.

**Когда DNS использует TCP?**

DNS переключается на TCP в определённых ситуациях, и это связано с историческими ограничениями и необходимостью обеспечить надёжность.

*   **Большой размер ответа (более 512 байт):**
    *   **Почему 512 байт?** Этот лимит был установлен в оригинальном стандарте DNS (RFC 1035). В то время максимальный размер пакета (MTU), который гарантированно проходил через любую сеть без разделения, составлял 576 байт. Лимит в 512 байт для данных DNS оставлял запас для заголовков UDP (8 байт) и IP (20 байт), чтобы избежать **фрагментации IP-пакетов**.
    *   **Что такое фрагментация IP?** Если IP-пакет больше, чем MTU (Maximum Transmission Unit) следующего участка сети, маршрутизатор разбивает его на несколько меньших пакетов (фрагментов). Каждый фрагмент отправляется отдельно и собирается обратно в единое целое только на конечном узле. Фрагментация нежелательна, так как она увеличивает накладные расходы и снижает надёжность: потеря даже одного фрагмента приводит к потере всего пакета.
    *   **Почему TCP?** В отличие от UDP, TCP — это протокол с установлением соединения, который сам управляет разделением данных на сегменты и гарантирует их доставку и правильную сборку. Когда DNS-ответ не помещается в один UDP-пакет, система переключается на TCP, чтобы надёжно передать большой объём данных без риска, связанного с IP-фрагментацией.
    *   **Современный подход (EDNS):** Сегодня используется расширение EDNS (Extension Mechanisms for DNS), которое позволяет клиенту и серверу договориться об использовании UDP-пакетов большего размера (например, 4096 байт). Это значительно сокращает частоту переключений на TCP, но TCP всё равно остаётся обязательным резервным механизмом.

*   **Передача зоны (Zone Transfer):** При синхронизации DNS-записей между главным и вторичными серверами всегда используется TCP. Это необходимо для гарантированной и последовательной передачи всего списка записей, который может быть очень большим.

**Anycast и низкая задержка до, например, 8.8.8.8**

Anycast — это метод сетевой адресации, при котором один и тот же IP-адрес используется множеством серверов, расположенных в разных точках мира. Когда вы отправляете запрос на `8.8.8.8`, сеть автоматически направляет его к географически ближайшему к вам серверу. Это значительно сокращает расстояние и, как следствие, время задержки (ping).

#### Виды DNS записей

| Название | Описание |
|---|---|
| **SOA - Start of Authority** | Указывает на местоположение эталонной записи о домене. Идентифицирует основной сервер имен для зоны, устанавливает параметры по умолчанию для зонной передачи, параметры длительности хранения информации и время жизни (TTL). |
| **A – (Address) хост** | Идентифицирует IPv4-адрес для определенного имени хоста. Пример: `example.com A 192.0.2.1` |
| **AAAA (IPv6 Address)** | Указывает IPv6-адрес для домена. Пример: `example.com AAAA 2001:db8::1` |
| **CAA (Certification Authority Authorization)** | Определяет, какие центры сертификации (CA) могут выдавать SSL-сертификаты для домена. Пример: `example.com CAA 0 issue "letsencrypt.org"` |
| **CERT (Certificate Record)** | Хранит криптографические сертификаты, включая PGP, PKIX и т. д. Редко используется. |
| **CNAME - Canonical Name** | Указывает, что домен является псевдонимом другого домена. Используется для поддоменов. Пример: `www.example.com CNAME example.com` |
| **DNSKEY** | Содержит открытые ключи, используемые в DNSSEC для верификации записей. Работает в паре с DS. |
| **DS (Delegation Signer)** | Передаёт доверие от родительской зоны к дочерней в DNSSEC. Указывает хэш DNSKEY-записи. |
| **HTTPS** | Новая запись, указывающая, как браузеры должны подключаться по HTTPS. Поддерживает альтернативные сервисы и оптимизацию соединения. |
| **LOC (Location)** | Указывает географическое местоположение домена (широта, долгота, высота). Редко используется. |
| **MX – (Mail Exchanger)** | Идентифицирует почтовые серверы, обслуживающие домен. Пример: `example.com MX 10 mail.example.com` |
| **NAPTR (Name Authority Pointer)** | Используется для динамического определения сервисов, например, в VoIP (SIP). |
| **NS – (Name Server)** | Идентифицирует все серверы имен для домена. Пример: `example.com NS ns1.example.net` |
| **PTR – (Pointer)** | Идентифицирует имена хостов, отображаемых на определенных IP-адресах. Хранится в зоне обратного просмотра. Пример: `1.2.0.192.in-addr.arpa PTR example.com` |
| **SMIMEA** | Определяет открытый ключ для S/MIME-подписей электронной почты, аналогично TLSA, но для e-mail. |
| **SRV - Service Locator** | Идентифицирует службу, которая имеется в домене. Позволяет получить имя хоста и номер порта серверов для определенных служб. Пример: `_sip._tcp.example.com SRV 10 60 5060 sipserver.example.com` |
| **SSHFP (SSH Fingerprint)** | Хранит отпечатки SSH-ключей, используется для безопасного соединения с серверами по SSH. |
| **SVCB (Service Binding)** | Новая запись, позволяет указывать предпочтительные способы подключения к сервисам (например, HTTP/3, DoH). |
| **TLSA** | Определяет, какие TLS-сертификаты доверены для сервиса, работающего по TCP/UDP. Используется в DANE. |
| **TXT** | Хранит произвольные текстовые данные. Часто используется для SPF, DKIM, DMARC. Пример: `example.com TXT "v=spf1 include:_spf.google.com ~all"` |
| **URI (Uniform Resource Identifier)** | Указывает URI-адреса, связанные с доменом, например, для SIP или других сервисов. Редко используется. |
| **SPF** | Содержит список доверенных серверов, с которых может отправляться почта данного домена. (Сейчас чаще всего реализуется через TXT-запись). |

#### Что такое TTL

Time to live (TTL) – это время жизни пакета. TTL показывает максимальный период времени существования набора данных (пакета).

В IPv4 TTL представляет собой восьмиразрядное поле IP-заголовка. Параметр TTL считается верхней границей времени существования IP-дейтаграммы в сети. Поле TTL устанавливается отправителем и уменьшается на каждом маршрутизаторе на 1.

Основное назначение – не допустить "зацикливания" пакета в сети.

При условии, что значение TTL на каком-либо из узлов достигнет 1, пакет данных уничтожается, а на исходный сервер посылается ICMP-сообщение с кодом 11 — «Превышение временного интервала». Маршрутизатор не пропускает пакеты с нулевым значением TTL.

#### TTL в DNS

TTL (Time To Live) в контексте DNS — это параметр в секундах, который указывает, как долго DNS-резолвер (например, сервер провайдера или публичный DNS) может кэшировать (хранить у себя) ответ на DNS-запрос.

**Как это работает:**

1.  Ваш компьютер запрашивает IP-адрес для `example.com`.
2.  DNS-резолвер (кэширующий сервер) обращается к авторитативному DNS-серверу, который хранит запись для `example.com`.
3.  Авторитативный сервер отвечает резолверу, отправляя IP-адрес и **значение TTL**, например, `3600` (1 час).
4.  Резолвер сохраняет эту запись в своем кэше на 3600 секунд и отдает IP-адрес вашему компьютеру.
5.  Если в течение следующего часа кто-то еще, использующий этот же резолвер, запросит `example.com`, резолвер мгновенно отдаст ответ из кэша, не обращаясь к авторитативному серверу.
6.  Как только TTL истечет, резолвер будет обязан снова запросить "свежую" запись у авторитативного сервера.

**Практическое применение:** Перед плановой миграцией сервиса на новый IP-адрес TTL для соответствующей A-записи намеренно понижают до минимального значения (например, 60-300 секунд) за несколько часов или дней до миграции. Это гарантирует, что после обновления IP-адреса пользователи быстро получат новую, корректную информацию.

#### DHCP

DHCP (Dynamic Host Configuration Protocol) — протокол динамической настройки узла. Он предназначен для автоматической выдачи устройствам IP-адресов и других сетевых параметров (маска подсети, шлюз по умолчанию).

**Способы назначения IP-адресов**
*   **Статическое назначение:** IP-адрес вручную закрепляется за MAC-адресом конкретного устройства. Используется в небольших сетях для устройств, требующих постоянного адреса.
*   **Динамическое назначение:** DHCP-сервер выдает IP-адрес из пула свободных адресов на определенное время (срок аренды).
*   **Автоматическое назначение:** Похоже на динамическое, но срок аренды не ограничен. IP остается за клиентом, пока он сам от него не откажется.

**Архитектура протокола DHCP**

DHCP использует архитектуру «клиент-сервер».
*   **Сервер DHCP:** Раздает IP-адреса и следит за их уникальностью.
*   **Клиент DHCP:** Любое устройство, запрашивающее сетевые настройки.
*   **Агенты ретрансляции DHCP:** Позволяют DHCP работать через несколько подсетей, пересылая запросы между ними.

**Принцип работы протокола DHCP (DORA)**

1.  **Discovery:** Клиент (еще без IP) отправляет широковещательное сообщение `DHCPDISCOVER` для поиска DHCP-сервера.
2.  **Offer:** DHCP-сервер (или несколько) отвечает сообщением `DHCPOFFER`, предлагая IP-адрес в аренду.
3.  **Request:** Клиент выбирает одно из предложений и отправляет `DHCPREQUEST`, сообщая всем, что адрес принят.
4.  **Acknowledgement:** Сервер подтверждает выделение адреса сообщением `DHCPACK`, передавая также срок аренды и другие настройки.

**Другие сообщения DHCP:**
*   `DHCPNAK`: Отказ в аренде IP-адреса.
*   `DHCPINFORM`: Запрос на получение дополнительных настроек сети (когда IP уже есть).
*   `DHCPRELEASE`: Досрочное освобождение IP-адреса клиентом.
*   `DHCPDECLINE`: Сообщение от клиента, если предложенный IP-адрес уже занят.

**Срок аренды IP-адреса**

IP-адрес выдается на определенное время. По умолчанию — 24 часа, но это настраивается. По истечении половины срока аренды клиент пытается его продлить.

**HTTP/1.0 (1996)**

-   Проблема: Медлительность. На каждый запрос (например, за HTML-файл, картинку, CSS) открывалось новое TCP-соединение, что создавало большие накладные расходы.

**HTTP/1.1 (1997)**

Ключевые улучшения, направленные на решение проблем производительности:

-   Постоянные соединения (Keep-Alive): Позволили браузеру отправлять несколько запросов в рамках одного TCP-соединения, что значительно сократило задержки.
-   Конвейеризация (Pipelining): Дала возможность отправлять следующий запрос, не дожидаясь ответа на предыдущий. Однако на практике эта функция работала плохо из-за блокировки "Head-of-Line" (HOL Blocking): если первый запрос в очереди "зависал", все последующие ждали его завершения.

**HTTP/2 (2015)**

Революционное обновление, основанное на протоколе SPDY от Google:

-   Мультиплексирование: Главное нововведение. Позволяет передавать множество запросов и ответов одновременно в рамках одного TCP-соединения, разбивая их на бинарные "кадры" (frames). Это полностью решило проблему HOL-блокировки на уровне приложения.
-   Бинарный протокол: В отличие от текстового HTTP/1.1, стал более эффективным и менее подверженным ошибкам.
-   Сжатие заголовков (HPACK): Значительно уменьшило размер передаваемых заголовков, что особенно заметно на мобильных устройствах.
-   Server Push: Позволял серверу отправлять ресурсы (например, CSS и JS) клиенту еще до того, как он их запросит, предугадывая его потребности. На практике функция оказалась сложной в реализации и не всегда давала выигрыш.

**HTTP/3 (2022)**

Новейший стандарт, который решает последнюю оставшуюся проблему — блокировку Head-of-Line на уровне транспортного протокола (TCP).

-   Переход на QUIC (UDP): HTTP/3 работает поверх протокола QUIC, который, в свою очередь, использует UDP. QUIC реализует мультиплексирование на транспортном уровне. Если один из потоков данных (например, загрузка картинки) теряет пакет, это не влияет на остальные потоки. Другие ресурсы продолжают загружаться без задержек.
-   Более быстрое установление соединения: QUIC объединяет в себе установку соединения и TLS-рукопожатие, что сокращает время на установку безопасного соединения.
-   Улучшенная работа при смене сети: Соединение привязывается не к паре IP:порт, а к уникальному идентификатору соединения. Это позволяет, например, без разрыва связи переключаться с Wi-Fi на мобильную сеть.

**Отправка HTTP-запроса**

После установки безопасного соединения клиент (браузер, `curl`) отправляет HTTP-запрос. Запрос и ответ имеют строго определенную минимальную структуру.

**Минимальный HTTP-запрос**

Для протокола **HTTP/1.1** минимальный запрос должен содержать три элемента:

1.  **Стартовая строка (Request Line):**
    *   **Метод:** `GET` (самый простой).
    *   **URI (путь):** `/` (корень ресурса).
    *   **Версия протокола:** `HTTP/1.1`.
2.  **Заголовок `Host`:** Обязателен в HTTP/1.1. Указывает, к какому сайту на сервере мы обращаемся, так как один IP-адрес может обслуживать множество доменов. Передают дополнительную информацию: User-Agent, Accept-Language, Cookies и т.д.
3.  **Пустая строка (CRLF):** Сигнал о том, что заголовки закончились.

**Минимальный HTTP-ответ**

Минимальный успешный ответ содержит:

1.  **Строка состояния (Status Line):**
    *   **Версия протокола:** `HTTP/1.1`.
    *   **Код состояния:** `200` (успех).
    *   **Пояснение:** `OK`.
2.  **Заголовки:** Для ответа с телом обязателен заголовок `Content-Length`, чтобы клиент знал, сколько байт данных ему нужно прочитать.
3.  **Пустая строка (CRLF):** Разделяет заголовки и тело ответа.
4.  **Тело ответа (Response Body):** Сами данные (могут быть пустыми).
