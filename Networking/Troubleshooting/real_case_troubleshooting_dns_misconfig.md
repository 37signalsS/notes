# Периодические 500-е ошибки из-за DNS-мисконфигурации

> Связанные темы: диагностика DNS ([dns/overview.md](../../Linux/Diagnostics/Networking/dns/overview.md)), протокол DNS ([dns.md](../Protocols/DNS/dns.md)), общая методология траблшутинга ([general_troubleshooting_methodology.md](../../Linux/Diagnostics/Troubleshooting/general_troubleshooting_methodology.md)), диагностика DNS в Docker ([dns_resolution_issues.md](../../Docker/Docker_network/troubleshooting/dns_resolution_issues.md)).

## Определения

- **DNS-мисконфигурация** — некорректная настройка DNS, приводящая к разрешению доменных имён в неверные IP-адреса. В данном кейсе — имя БД разрешается в адрес тестового, а не продуктивного сервера.
- **Ошибка 500 (Internal Server Error)** — HTTP-код, указывающий на непредвиденную проблему на стороне сервера. В данном случае вызвана логическими ошибками приложения из-за подключения не к той базе данных.

## Основные концепции

DNS — критический компонент распределённых систем. Приложения используют DNS для преобразования имён ресурсов (БД, внешние API, микросервисы) в IP-адреса. Неправильная настройка DNS приводит к подключению не к тому ресурсу, что вызывает ошибки логики и 500-е ответы, даже если сам ресурс исправен. Включение проверки DNS-разрешения в процесс траблшутинга обязательно, особенно в мультисервисных архитектурах с контейнеризацией.

## Практический сценарий: диагностика 500-х ошибок, вызванных DNS-мисконфигурацией

### Архитектура системы

Сервис `мойкотик-бармотик.рф` — пользователи периодически получали 500-е ошибки в личном кабинете. Мониторинг проблем не фиксировал.

Архитектура:

1. **Внешний балансировщик нагрузки** — единая точка входа, распределяет трафик.
2. **Nginx Reverse Proxy (3 сервера)** — принимают трафик от балансировщика, проксируют на бекенд. Работают в Docker-контейнерах.
3. **Бекенд-серверы приложений (6 серверов)** — Go-приложения в Docker-контейнерах.
4. **База данных (PostgreSQL)** — единая БД для всех серверов приложений.

### Процесс диагностики

**Шаг 1. Начальная диагностика.** `ping мойкотик-бармотик.рф` показал IP балансировщика — DNS фронтенда работает корректно.

**Шаг 2. Анализ балансировщика.** Веб-интерфейс подтвердил распределение на 3 Nginx-сервера. Логи балансировщика выявили периодические 500-е ошибки от всех 3 Nginx-серверов.

**Шаг 3. Анализ Nginx-серверов.** На одном из Nginx-серверов (`ss -lpn` + `docker ps`) подтверждена работа Docker-контейнера Nginx на 80-м порту. Конфигурация `upstream` содержала 6 IP-адресов серверов приложений.

**Шаг 4. Анализ логов Nginx.** `docker logs <nginx_container>` показал, что один из 6 серверов приложений стабильно возвращает ошибки. Картина подтвердилась на всех Nginx-серверах — проблема локализована на одном конкретном бекенд-сервере.

**Шаг 5. Анализ проблемного сервера приложения.** На проблемном сервере (`docker ps` + `docker logs <app_container>`) в логах Go-приложения обнаружены ошибки при выполнении `SELECT`-запросов к БД.

**Шаг 6. Анализ базы данных.** На сервере PostgreSQL (`systemctl status postgresql` + `journalctl -u postgresql`) ошибок не обнаружено. Ручное выполнение проблемного `SELECT` напрямую в БД прошло успешно — проблема не в БД или запросе, а в окружении.

**Шаг 7. Проверка DNS-разрешения (решающий шаг).** Проверка разрешения имени хоста БД с проблемного и рабочего серверов приложений (`nslookup <db_hostname>` изнутри контейнера) показала:

- На проблемном сервере DNS-имя БД разрешалось в IP-адрес **тестовой** БД.
- На рабочих серверах — в IP-адрес **продуктовой** БД.

Команды для комплексной проверки DNS — `dig` или `resolvectl` ([dns/overview.md](../../Linux/Diagnostics/Networking/dns/overview.md)):

```bash
# Проверка разрешения имени через dig
dig @<dns_server> <db_hostname>

# Проверка через systemd-resolved
resolvectl query <db_hostname>

# Сравнение результатов с разных хостов
for host in app1 app2 app3; do ssh $host "nslookup <db_hostname>"; done
```

### Причина проблемы

Сетевой инженер ошибочно прописал для одного из серверов приложений IP-адрес тестовой БД. Поскольку учётные данные совпадали, приложение успешно подключалось, но не находило нужные данные в тестовой базе, что приводило к логическим ошибкам и 500-м ответам.

## Дополнительная информация

**Важность DNS в распределённых системах.** Проблемы, кажущиеся ошибками приложения или БД, могут быть вызваны некорректным разрешением имён. Проверка DNS-разрешения — обязательный шаг траблшутинга в мультисервисных архитектурах.

**Предотвращение.** Использование систем управления конфигурацией для стандартизации сетевых настроек. Включение проверки DNS-разрешения (`nslookup`, `dig`) в автоматизированные тесты и CI/CD-пайплайны для критически важных сервисов. Внедрение Service Discovery (Consul, etcd, Kubernetes Service DNS) для динамического разрешения имён. Тщательная проверка окружения и параметров запуска сервисов при развёртывании в контейнерной среде. Настройка алертов на аномалии в разрешении DNS (Prometheus + Blackbox Exporter). Ведение актуальной документации по DNS-зонам и критическим зависимостям между сервисами.
