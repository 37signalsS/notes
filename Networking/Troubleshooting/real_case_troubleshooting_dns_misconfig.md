## Определения

- **DNS-мисконфигурация**: Некорректная настройка системы доменных имен (DNS), приводящая к разрешению доменных имен в неверные IP-адреса. В данном контексте — ошибочное разрешение имени базы данных в адрес тестового окружения вместо продуктивного.
- **Ошибка 500 (Internal Server Error)**: Общий код состояния HTTP, указывающий, что сервер столкнулся с неожиданным условием, которое помешало ему выполнить запрос. Часто свидетельствует о проблемах на стороне сервера, включая ошибки в логике приложения или некорректные зависимости.

## Основные концепции

Система доменных имен (DNS) является критически важным компонентом для работы распределенных систем. Приложения используют DNS для преобразования человекочитаемых доменных имен в IP-адреса сетевых ресурсов, таких как базы данных, внешние API или другие микросервисы. Неправильная настройка DNS может привести к тому, что приложение будет подключаться не к тому ресурсу, что вызовет непредсказуемое поведение, ошибки в логике и, как следствие, ошибки уровня 500, даже если сам ресурс (например, база данных) функционирует исправно. Важно всегда проверять корректность разрешения DNS-имен с точки зрения приложения.

## Практический сценарий: Диагностика 500-х ошибок, вызванных DNS-мисконфигурацией

### Ситуация и архитектура системы

Пользователи сервиса `мойкотик-бармотик.рф` периодически сталкивались с ошибками 500 в личном кабинете. Мониторинг при этом не регистрировал никаких проблем. Система имела следующую архитектуру:

1. **Внешний балансировщик нагрузки**: Единая точка входа, распределяющая трафик.
2. **Nginx Reverse Proxy (3 сервера)**: Принимают трафик от балансировщика и проксируют его на бекенд. Работают в Docker-контейнерах.
3. **Бекенд-серверы приложений (6 серверов)**: Go-приложения в Docker-контейнерах.
4. **База данных (PostgreSQL)**: Единая база данных для всех серверов приложений.

### Процесс траблшутинга

Проблема диагностировалась пошагово:

1. **Начальная диагностика**:
    - `ping мойкотика-бармотик.рф` показал IP-адрес балансировщика.
2. **Анализ балансировщика**:
    - Веб-интерфейс показал распределение нагрузки на 3 Nginx-сервера. Логи балансировщика выявили периодические 500-е ошибки от всех 3 Nginx-серверов.
3. **Анализ Nginx-серверов**:
    - На одном из Nginx-серверов (`ss -lpn` и `docker ps`) подтвердили работу Docker-контейнера с Nginx на 80-м порту.
    - Конфигурация Nginx (`upstream`) содержала 6 IP-адресов серверов приложений.
4. **Анализ логов Nginx**:
    - `docker logs <nginx_container>` показал, что один из 6 серверов приложений постоянно выдавал ошибки. Эта картина подтвердилась на других Nginx-серверах.
5. **Анализ проблемного сервера приложения**:
    - На проблемном сервере (`docker ps` и `docker logs <app_container>`) в логах Go-приложения обнаружены ошибки при выполнении `SELECT` запросов к БД.
6. **Анализ базы данных**:
    - На сервере PostgreSQL (`systemctl status postgresql`, `journalctl -u postgresql`) не было обнаружено ошибок.
    - **Ключевой тест**: Ручное выполнение проблемного `SELECT` запроса напрямую в БД прошло успешно. Это указало на то, что проблема не в самой БД или запросе, а в окружении.
7. **Поиск истинной причины (решающий шаг)**:
    - Проведена проверка разрешения DNS-имени хоста базы данных с проблемного и с рабочего серверов приложений (`nslookup <db_hostname>` изнутри контейнера).
    - **Результат**: На проблемном сервере DNS-имя базы данных разрешалось в IP-адрес **тестовой**, а не **боевой** БД.

    > **Диагностика DNS (подробнее):** Для комплексной проверки DNS используйте [`dig`](../../Linux/Diagnostics/Networking/dns_diagnostics.md) или [`resolvectl`](../../Linux/Diagnostics/Networking/dns_diagnostics.md):
>
    > ```bash
    > # Проверка разрешения имени через dig
    > dig @<dns_server> <db_hostname>
    > 
    > # Проверка через systemd-resolved
    > resolvectl query <db_hostname>
    > 
    > # Сравнение результатов с разных хостов
    > for host in app1 app2 app3; do ssh $host "nslookup <db_hostname>"; done
    > ```

### Причина проблемы

Причина заключалась в **DNS-мисконфигурации**: сетевой инженер ошибочно прописал для одного из серверов приложений IP-адрес тестовой базы данных. Поскольку логины и пароли совпадали, приложение успешно подключалось, но не находило нужные данные в тестовой базе, что приводило к логическим ошибкам и 500-м ответам.

## Дополнительная информация

- **Важность DNS в распределенных системах**: Этот случай подчеркивает, что проблемы, кажущиеся ошибками приложения или базы данных, могут быть вызваны некорректным разрешением имен. Всегда включайте проверку DNS-разрешения в процесс траблшутинга, особенно в мультисервисных архитектурах.
- **Предотвращение**:
  - Использование систем управления конфигурацией для стандартизации сетевых настроек.
  - Включение проверки DNS-разрешения (например, через `nslookup` или `dig`) в автоматизированные тесты и пайплайны CI/CD для критически важных сервисов.
  - Внедрение Service Discovery (например, Consul, etcd, Kubernetes Service DNS) для динамического и корректного разрешения имен сервисов.
  - Тщательная проверка окружения и параметров запуска для каждого сервиса, особенно при развертывании в контейнерной среде.
  - **Мониторинг DNS**: Настройка алертов на аномалии в разрешении DNS (например, через Prometheus + Blackbox Exporter).
  - **Документирование**: Ведение актуальной документации по DNS-зонам и критическим зависимостям между сервисами.
