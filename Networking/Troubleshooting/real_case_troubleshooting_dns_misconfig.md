# Периодические 500-е ошибки из-за DNS-мисконфигурации

> Эта заметка описывает практический сценарий (кейса) диагностики распределённой системы. Теоретические основы и инструменты диагностики представлены в разделах: **[Диагностика DNS](../../Linux/Diagnostics/Networking/dns/overview.md)**, **[Протокол DNS](../Protocols/DNS/dns.md)**, **[Общая методология диагностики](../../Linux/Diagnostics/Troubleshooting/general_troubleshooting_methodology.md)**.

## Определения

- **DNS-мисконфигурация (DNS Misconfiguration)** — некорректная настройка системы доменных имён **DNS (Domain Name System)**, приводящая к разрешению (resolving) имён в неверные **IP (Internet Protocol)** адреса. В данном кейсе — имя хоста базы данных разрешалось в адрес тестового сервера вместо продуктивного.
- **Ошибка 500 (HTTP 500 Internal Server Error)** — код состояния **HTTP (HyperText Transfer Protocol)**, указывающий на общую ошибку сервера. В данном сценарии она была вызвана логическими ошибками приложения при работе с некорректной базой данных.
- **Бэкенд (Backend)** — программно-аппаратная часть сервиса, отвечающая за логику работы и хранение данных.

## Основные концепции

Система DNS является фундаментом сетевого взаимодействия в распределённых архитектурах. Приложения используют DNS для поиска ресурсов: баз данных, внешних **API (Application Programming Interface)** и микросервисов.

Ошибки в DNS-разрешении часто маскируются под сбои прикладного уровня (ошибки приложения или БД). Если DNS возвращает IP-адрес исправного, но «не того» сервера (например, стейджинг вместо продакшена), приложение может подключаться успешно, но вести себя непредсказуемо из-за различий в схеме данных или их наполнении. Проверка DNS-разрешения — критический этап методологии «снизу вверх», позволяющий выявить проблемы до глубокого анализа кода.

## Практические сценарии

### Сценарий: Диагностика 500-х ошибок в сервисе «мойкотик-бармотик.рф»

**Проблема:** Пользователи периодически жаловались на 500-е ошибки в личном кабинете. Стандартный мониторинг не фиксировал падения сервисов, так как все компоненты были «живы» (up), но возвращали некорректные ответы.

**Архитектура системы:**

1. **Балансировщик нагрузки (Load Balancer)** — внешняя точка входа.
2. **Nginx Reverse Proxy** — 3 экземпляра в Docker-контейнерах.
3. **App Servers (Бэкенд)** — 6 экземпляров Go-приложения в Docker.
4. **DB (Database — база данных)** — PostgreSQL, общая для всех бэкендов.

#### Шаг 1: Начальная диагностика связности

Проверка доступности фронтенда подтвердила корректную работу внешней DNS-записи.

```bash
ping мойкотик-бармотик.рф
# → PING мойкотик-бармотик.рф (93.184.216.34) ... 64 bytes from ...
```

#### Шаг 2: Анализ балансировщика и прокси

Логи балансировщика подтвердили получение 500-х ошибок от всех трёх серверов Nginx. Однако Nginx логировал ошибки `500` как ответы от `upstream` (бэкенда).

#### Шаг 3: Локализация на уровне Nginx

Проверка конфигурации `upstream` в Nginx показала список из 6 бэкенд-серверов. Анализ логов Docker-контейнеров Nginx с помощью `grep` по коду 500 выявил, что ошибки возвращает только **один конкретный сервер приложений** (app-04) из шести.

#### Шаг 4: Анализ проблемного сервера приложения

Логи Go-приложения (`docker logs app-04`) содержали ошибки выполнения `SELECT`-запросов: `relation "orders" does not exist`. Это критическая аномалия, так как остальные 5 серверов работали нормально с той же БД, где таблица `orders` существует.

#### Шаг 5: Проверка базы данных

PostgreSQL работал штатно. Ручное выполнение запроса в консоли `psql` на основном сервере БД прошло успешно.

#### Шаг 6: Проверка DNS-разрешения (Решающий этап)

Сравнение разрешения имени хоста БД внутри контейнеров.

**На рабочем сервере (app-01):**

```bash
nslookup db.internal.local
# → Server:    127.0.0.11 (Docker DNS)
# → Address:   10.0.1.50 (Prod DB IP)
```

**На проблемном сервере (app-04):**

```bash
nslookup db.internal.local
# → Server:    127.0.0.11 (Docker DNS)
# → Address:   10.0.99.200 (Test DB IP)
```

**Причина:** Сетевой инженер при ручной отладке сервера `app-04` прописал в `/etc/hosts` IP-адрес тестовой базы данных и забыл удалить запись. 

**Важный технический нюанс:** Библиотека стандартного резолвера Linux (`libc`) при поиске имен сначала обращается к `/etc/hosts`, а затем к DNS-серверам (это поведение определяется в `/etc/nsswitch.conf`: `hosts: files dns`). В результате приложение подключалось к тестовой БД, где схема данных была устаревшей, что и вызывало логические ошибки (500) при попытке обращения к отсутствующим таблицам.

## Дополнительная информация

### Рекомендации по предотвращению

1. **Автоматизация конфигурации:** Использование **IaC (Infrastructure as Code — инфраструктура как код)** (Ansible, Terraform) полностью исключает ручные правки `/etc/hosts` и человеческий фактор.
2. **Service Discovery:** Использование динамических систем обнаружения сервисов (Consul, Kubernetes DNS) вместо статичных записей.
3. **Мониторинг целостности файлов:** Использование систем контроля конфигураций (Auditd, Tripwire) для отслеживания изменений в `/etc/hosts`.
4. **Централизованный DNS:** Все записи должны управляться централизованно (например, через CoreDNS или BIND), а не локально на хостах.
5. **Проверки при деплое (Pre-flight checks):** Автоматизированная проверка разрешения всех зависимостей перед запуском приложения.

### Полезные инструменты диагностики

- `dig` — детальный анализ DNS-записей, игнорирующий `/etc/hosts`. См. **[Инструмент dig](../../Linux/Diagnostics/Networking/dns/dig_tool.md)**.
- `getent hosts <name>` — показывает результат разрешения через системный резолвер (учитывает `/etc/hosts`).
- `resolvectl` — управление резолвером в системах с `systemd-resolved`.
- `nslookup` — быстрая проверка изнутри контейнеров.
