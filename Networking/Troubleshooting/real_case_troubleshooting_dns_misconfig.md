# Периодические 500-е ошибки из-за DNS-мисконфигурации

> Эта заметка описывает практический сценарий (кейс) диагностики распределённой системы. Теоретические основы и инструменты диагностики представлены в разделах: **[Диагностика DNS](../../Linux/Diagnostics/Networking/dns/overview.md)**, **[Протокол DNS](../Protocols/DNS/dns.md)**, **[Общая методология диагностики](../../Linux/Diagnostics/Troubleshooting/general_troubleshooting_methodology.md)**.

## Определения

- **DNS-мисконфигурация (DNS Misconfiguration)** — некорректная настройка системы доменных имён **DNS (Domain Name System)**, приводящая к разрешению (resolving) имён в неверные **IP (Internet Protocol)** адреса. В данном кейсе — имя хоста базы данных разрешалось в адрес тестового сервера вместо продуктивного.
- **Ошибка 500 (HTTP 500 Internal Server Error)** — код состояния **HTTP (HyperText Transfer Protocol)**, указывающий на общую ошибку сервера. В данном сценарии она была вызвана логическими ошибками приложения при работе с некорректной базой данных.
- **Бэкенд (Backend)** — программно-аппаратная часть сервиса, отвечающая за логику работы и хранение данных.

## Основные концепции

Система DNS является фундаментом сетевого взаимодействия в распределённых архитектурах. Приложения используют DNS для поиска ресурсов: баз данных, внешних **API (Application Programming Interface)** и микросервисов.

Ошибки в DNS-разрешении часто маскируются под сбои прикладного уровня (ошибки приложения или БД). Если DNS возвращает IP-адрес исправного, но «не того» сервера (например, стейджинг вместо продакшена), приложение может подключаться успешно, но вести себя непредсказуемо из-за различий в данных. Проверка DNS-разрешения — критический этап методологии «снизу вверх».

## Практические сценарии

### Сценарий: Диагностика 500-х ошибок в сервисе «мойкотик-бармотик.рф»

**Проблема:** Пользователи периодически жаловались на 500-е ошибки в личном кабинете. Стандартный мониторинг не фиксировал падения сервисов, так как все компоненты были «живы».

**Архитектура системы:**
1. **Балансировщик нагрузки (Load Balancer)** — внешняя точка входа.
2. **Nginx Reverse Proxy** — 3 экземпляра в Docker-контейнерах.
3. **App Servers (Бэкенд)** — 6 экземпляров Go-приложения в Docker.
4. **DB (Database — база данных / БД)** — PostgreSQL, общая для всех бэкендов.

#### Шаг 1: Начальная диагностика связности
Проверка доступности фронтенда подтвердила корректную работу внешней DNS-записи.
```bash
ping мойкотик-бармотик.рф
# → PING мойкотик-бармотик.рф (93.184.216.34) ... 64 bytes from ...
```

#### Шаг 2: Анализ балансировщика и прокси
Логи балансировщика подтвердили получение 500-х ошибок от всех трёх серверов Nginx.

#### Шаг 3: Локализация на уровне Nginx
Проверка конфигурации `upstream` в Nginx показала список из 6 бэкенд-серверов. Анализ логов Docker-контейнеров Nginx выявил, что ошибки возвращает только **один конкретный сервер приложений** из шести.

#### Шаг 4: Анализ проблемного сервера приложения
Логи Go-приложения (`docker logs <app_container>`) содержали ошибки выполнения `SELECT`-запросов: «relation "orders" does not exist». Это странно, так как остальные 5 серверов работали нормально с той же БД.

#### Шаг 5: Проверка базы данных
PostgreSQL работал штатно. Ручное выполнение того же SQL-запроса в консоли `psql` прошло успешно. Проблема явно в окружении одного конкретного сервера.

#### Шаг 6: Проверка DNS-разрешения (Решающий этап)
Сравнение разрешения имени хоста БД внутри контейнеров на рабочем и проблемном серверах.

**На рабочем сервере:**
```bash
nslookup db.internal.local
# → Address: 10.0.1.50 (Prod DB)
```

**На проблемном сервере:**
```bash
nslookup db.internal.local
# → Address: 10.0.99.200 (Test DB)
```

**Причина:** Сетевой инженер при ручной настройке одного из серверов прописал в `/etc/hosts` (или в локальном резолвере) IP-адрес тестовой базы данных. Приложение подключалось к тестовой БД, где отсутствовали актуальные таблицы продакшена, что вызывало ошибки логики.

## Дополнительная информация

### Рекомендации по предотвращению

1. **Автоматизация конфигурации:** Использование **IaC (Infrastructure as Code — инфраструктура как код)** (Ansible, Terraform) исключает человеческий фактор при настройке резолверов.
2. **Service Discovery:** Использование динамических систем обнаружения сервисов (Consul, Kubernetes DNS) вместо статичных записей в файлах или DNS-зонах.
3. **Мониторинг DNS:** Использование инструментов типа **Prometheus Blackbox Exporter** для периодической проверки корректности DNS-ответов с разных сегментов сети.
4. **Стандартизация окружения:** Проверка переменных окружения и конфигурационных файлов при деплое.

### Полезные инструменты диагностики
- `dig` — детальный анализ DNS-записей. См. **[Инструмент dig](../../Linux/Diagnostics/Networking/dns/dig_tool.md)**.
- `resolvectl` — управление резолвером в системах с `systemd-resolved`.
- `nslookup` — быстрая проверка изнутри контейнеров.
