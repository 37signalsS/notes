# Заказ не доходит до склада: исчерпание inodes на сервере БД

> Эта заметка является описанием практического сценария (кейса) по диагностике распределённой системы. Теоретические основы и инструменты диагностики описаны в: **[Диагностика файловых систем и inodes](../../Linux/Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md)**, **[Ссылки, Inode и Dentry](../../Linux/FileSystems/links_inodes_dentries.md)**, **[Общая методология диагностики](../../Linux/Diagnostics/Troubleshooting/general_troubleshooting_methodology.md)**.

## Определения

- **Inodes (Индексные дескрипторы)** — структуры данных в файловой системе **ОС (Operating System — операционная система)**, хранящие метаданные о файлах и директориях. В файловых системах семейства `ext` количество дескрипторов фиксируется при создании, а в `XFS` может выделяться динамически. Подробнее см. **[Inode](../../Linux/FileSystems/links_inodes_dentries.md#inode-индексный-дескриптор)**.
- **Producer Kafka (Продюсер)** — клиентское приложение, отправляющее сообщения в топик Kafka. См. **[Обзор Kafka](../../Kafka/kafka_overview.md)**.
- **Consumer Kafka (Консьюмер)** — клиентское приложение, читающее сообщения из топика Kafka.
- **Offset в Kafka** — уникальный последовательный идентификатор сообщения в пределах партиции, используемый для отслеживания позиции чтения.

## Основные концепции

В распределённых системах передача данных часто строится на брокерах сообщений, таких как Apache Kafka. Стабильность таких систем зависит от доступности ресурсов файловой системы на каждом узле цепочки.

Критическим, но часто игнорируемым ресурсом являются **inodes**. Их исчерпание делает невозможным создание новых файлов (логов, временных файлов, сокетов, PID-файлов), даже если на диске достаточно свободного места в гигабайтах. Это приводит к каскадным сбоям: приложения не могут запускаться, писать логи или корректно завершать транзакции. 

Типичный признак проблемы — ошибка `No space left on device` при наличии свободного места в выводе `df -h`.

## Практические сценарии

### Сценарий: Заказ не доходит до склада из-за сбоя базы данных

**Проблема:** Пользователи успешно создают заказы в интерфейсе (получают **HTTP (HyperText Transfer Protocol)** код 200), но заказы не отображаются в системе управления складом.

**Архитектура:** Frontend → Nginx (балансировщик) → Приложение (Python/Flask) → Kafka → Сервис склада (Consumer) → **DB (Database — база данных)** PostgreSQL.

#### Шаг 1: Проверка на стороне клиента

Анализ сетевых запросов в браузере подтвердил, что запрос `POST /orders` успешно отправляется на **IP (Internet Protocol)** сервера и возвращает статус 200.

#### Шаг 2: Анализ Nginx

Подключение по **SSH (Secure Shell)** к балансировщику. Логи Nginx (`/var/log/nginx/access.log`) показывают успешные ответы (200 OK) для запросов на создание заказа. Это означает, что запрос принят и корректно передан на `upstream`.

#### Шаг 3: Проверка сервера приложения

Приложение функционирует как продюсер Kafka. Проверка Docker-контейнеров показала статус `Up`. Логи приложения не содержат ошибок отправки; библиотека-клиент подтверждает доставку сообщений (Acks=all).

#### Шаг 4: Анализ Kafka

С помощью мониторинга (Grafana/Prometheus) установлено:
- **Consumer Lag** в топике `orders` равен 0.
- Сообщения вычитываются группой `store-group`.
Это означает, что сообщения успешно покидают Kafka, но не доходят до конечного состояния в БД.

#### Шаг 5: Проверка консьюмера (сервис склада)

Анализ логов сервиса в Elasticsearch/Kibana выявил повторяющиеся критические ошибки: 
`FATAL: could not connect to server: Connection refused`. Сервис не может подключиться к PostgreSQL.

#### Шаг 6: Диагностика сервера базы данных

База данных PostgreSQL запущена в Docker. Проверка статуса контейнеров:

```bash
docker ps -a
# → STATUS: Exited (1) 5 minutes ago
```

Попытка просмотра последних строк лога контейнера:

```bash
docker logs postgres_db --tail 20
# → FATAL: could not create lock file "postmaster.pid": No space left on device
```

Проверка свободного места на диске:

```bash
df -h
# → /dev/sda1 50G 20G 30G 40% /  # Место есть (используется 40%)
```

Проверка использования inodes (критический шаг):

```bash
df -i
# → /dev/sda1 3.2M 3.2M 0 100% / # Inodes ИСЧЕРПАНЫ (100%)
```

#### Поиск причины исчерпания inodes

Для поиска директории с аномальным количеством мелких файлов использовалась команда (для систем с GNU coreutils):

```bash
du --inodes -S /var/lib/docker/containers | sort -rh | head -n 10
# → 2800000 /var/lib/docker/containers/<id>/checkpoints
```

Альтернативный (более медленный, но универсальный) способ через `find`:

```bash
find /var/lib/docker/containers -xdev -printf '%h\n' | uniq -c | sort -rn | head -n 10
```

**Корень проблемы:** Тестовый контейнер со слишком агрессивными настройками `healthcheck` (интервал 1с) генерировал миллионы мелких временных файлов в директории `checkpoints`. Это забило таблицу дескрипторов всей файловой системы. PostgreSQL при старте пытался создать `.pid` файл, получал отказ от ОС и завершался.

#### Решение

1. **Остановка и удаление** проблемного тестового контейнера.
2. **Очистка** директории: `rm -rf /var/lib/docker/containers/<id>/checkpoints/*`.
3. **Запуск** PostgreSQL: `docker start postgres_db`.

#### Восстановление данных (Kafka Offset Management)

Поскольку консьюмер успел «прочитать» сообщения и закоммитить офсеты (автокоммит был включен), но фактически данные в БД не попали из-за ошибки подключения, потребовался сброс офсетов для повторной обработки заказов за период инцидента.

```bash
# 1. Остановка консьюмера (обязательно перед сбросом)
# 2. Сброс офсетов на конкретное время
kafka-consumer-groups --bootstrap-server kafka:9092 \
  --group store-group \
  --topic orders \
  --reset-offsets \
  --to-datetime 2026-06-06T10:00:00.000 \
  --execute
# → NEW-OFFSET: 45021
```

*Примечание: формат времени ISO 8601. Флаг `--execute` выполняет операцию, без него команда работает в режиме `--dry-run`.*

## Дополнительная информация

### Рекомендации по предотвращению подобных инцидентов

1. **Мониторинг ресурсов:** Настройка алертов в Prometheus через `node_exporter` на использование inodes (метрика `node_filesystem_files_free`). Порог срабатывания — 80-85%. См. **[Диагностика файловых систем](../../Linux/Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md#диагностика-нехватки-inodes)**.
2. **Лимиты Docker-логов:** Ограничение размера и количества файлов логов (`json-file` driver с `max-size` и `max-file`). Подробнее: **[Управление ротацией логов Docker](../../Docker/Docker_logs/docker_log_rotation.md)**.
3. **Изоляция данных:** Хранение данных базы данных (Volumes) на отдельном LVM-томе или выделенном диске. Это гарантирует, что переполнение системного раздела или раздела Docker не остановит работу СУБД.
4. **Настройка Healthchecks:** Избегайте слишком частых проверок состояния в Docker/Kubernetes. Оптимальный интервал — 10-30 секунд.
