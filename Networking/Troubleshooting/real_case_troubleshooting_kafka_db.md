# Заказ не доходит до склада: исчерпание inodes на сервере БД

> Связанные темы: диагностика файловой системы и inodes ([filesystem_and_disk_space_diagnostics.md](../../Linux/Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md)), inodes и dentries ([links_inodes_dentries.md](../../Linux/FileSystems/links_inodes_dentries.md)), общая методология траблшутинга ([general_troubleshooting_methodology.md](../../Linux/Diagnostics/Troubleshooting/general_troubleshooting_methodology.md)), Docker-логи ([journalctl.md](../../Linux/Diagnostics/journalctl.md)).

## Определения

- **Inodes (айноды)** — структуры данных в файловой системе Unix-подобных систем, хранящие метаданные о файлах и директориях (права доступа, владелец, временные метки, физическое расположение). Каждый файл или директория требует один inode.
- **Продюсер Kafka (Producer)** — клиентское приложение, отправляющее сообщения в топик Kafka.
- **Консьюмер Kafka (Consumer)** — клиентское приложение, читающее сообщения из топика Kafka.
- **Offset в Kafka** — уникальный последовательный идентификатор сообщения в пределах партиции. Консьюмеры используют offset для отслеживания позиции чтения.

## Основные концепции

В распределённых системах асинхронная передача данных часто строится на брокерах сообщений, таких как Apache Kafka. Продюсеры отправляют сообщения в топики, консьюмеры читают их, отслеживая прогресс через offset'ы. При остановке консьюмера чтение возобновляется с последнего сохранённого offset.

Стабильная работа систем критически зависит от ресурсов файловой системы. Помимо свободного дискового пространства, ключевой ресурс — inodes. Исчерпание свободных inodes означает невозможность создавать новые файлы или директории, даже если на диске есть свободное место. Это приводит к невозможности записи логов, создания временных файлов или запуска сервисов, требующих файловых операций.

## Практический сценарий: заказ не доходит до склада из-за исчерпания inodes на сервере БД

### Архитектура системы

**Проблема:** Пользователи создают заказы, получают подтверждение (код 200), но заказы не появляются на складе.

**Стек:** Фронтенд → Веб-сервер/прокси → Приложение → Kafka → Консьюмер (склад) → База данных.

### Процесс диагностики

**Шаг 1. Анализ на стороне клиента.** Проверка сетевых запросов в браузере (F12) подтвердила: `POST /orders` успешно уходит на IP сервера компании.

**Шаг 2. Исследование Nginx.** Подключение по SSH показало запущенный Nginx (балансировщик/прокси). Конфигурация (`/etc/nginx/nginx.conf`, `sites-available/*`) содержала `proxy_pass` на `upstream` с несколькими серверами. Логи Nginx (`access.log`, `error.log`) подтвердили успешную обработку `POST /orders` с кодом 200 — проблема дальше по цепочке.

**Шаг 3. Исследование сервера приложения.** Подключение к одному из серверов `upstream` показало запущенное приложение на Python (Gunicorn/Flask) в `/home/application`. Изучение кода (`requirements.txt`, функции обработки `/orders`) выявило отправку сообщений в Kafka. Найден `docker-compose.yml` с переменными окружения для подключения к Kafka — приложение функционирует как продюсер.

**Шаг 4. Исследование Kafka.** Через дашборд Grafana установлено: лаг в топике отсутствует — сообщения успешно отправляются продюсером и активно читаются консьюмером. В Wiki найдены потенциальные консьюмеры топика, среди которых `Store` (сервис склада) — логичный кандидат. Проверка состояния консьюмера `Store` показала: он пытается читать сообщения, но безуспешно.

**Шаг 5. Исследование сервера консьюмера.** Поиск логов консьюмера `Store` в Elasticsearch ([elasticsearch_overview.md](../../ELK_Stack/Elasticsearch/elasticsearch_overview.md)) выявил повторяющиеся ошибки: «не могу подключиться к базе данных» с указанием хоста БД.

**Шаг 6. Исследование сервера БД.** Подключение по SSH показало PostgreSQL в Docker-контейнере. Проверка статуса контейнера — **упал**. Логи контейнера (`docker logs <container_id>`) показали первичную ошибку «порт занят» (`Port is already allocated`), а после попытки перезапуска — «ошибка, связанная с диском». Права доступа к `/var/lib/postgresql/data` корректны. Проверка свободного места (`df -h`) показала его наличие, однако `df -i` выявил: **inodes закончились (100% использование)**.

Команды для диагностики inodes ([filesystem_and_disk_space_diagnostics.md](../../Linux/Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md), [links_inodes_dentries.md](../../Linux/FileSystems/links_inodes_dentries.md)):

```bash
# Проверка использования inodes на всех файловых системах
df -i

# Поиск директорий с большим количеством файлов (основная причина исчерпания inodes)
for i in /*; do echo "$i:"; find "$i" -xdev -type f | wc -l; done | sort -k2 -rn | head -20

# Альтернатива с использованием du
du --inodes -S / | sort -rh | head -20
```

### Причина и решение

**Причина:** На хосте с БД закончились свободные inodes. Причина — тестовый контейнер, генерировавший огромное количество мелких лог-файлов, исчерпав все доступные inodes на файловой системе. PostgreSQL не мог создать служебные файлы и, соответственно, запуститься.

**Решение:**

1. Остановлен тестовый контейнер, генерировавший избыточные логи.
2. Удалены ненужные лог-файлы для освобождения inodes.
3. Контейнер с БД успешно запущен.

### Финальные действия

Заказы, отправленные в Kafka во время недоступности БД, не были обработаны консьюмером `Store`. Для обработки потребовался сброс offset для консьюмера `Store` в Kafka, чтобы перечитать все необработанные сообщения из топика.

## Дополнительная информация

**Комплексность траблшутинга.** Проблемы в распределённых системах редко имеют одну очевидную причину и требуют последовательного поуровневого анализа каждого компонента стека.

**Мониторинг inodes.** Важно включить мониторинг использования inodes в систему Observability. Prometheus Node Exporter собирает метрики `node_filesystem_files_free` и `node_filesystem_files_total`.

Пример алерта для Prometheus:

```yaml
- alert: InodesExhaustionRisk
  expr: node_filesystem_files_free / node_filesystem_files_total < 0.1
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "Риск исчерпания inodes на {{ $labels.instance }}"
    description: "Свободно менее 10% inodes на файловой системе {{ $labels.mountpoint }}"
```

**Управление логами.** В тестовых и продуктивных окружениях необходимо контролировать генерацию и ротацию логов для предотвращения исчерпания дисковых ресурсов. Использовать `logrotate` для ротации логов. Настроить `journald` с ограничением размера (`SystemMaxUse=`, `RuntimeMaxUse=`). Для Docker-контейнеров установить лимиты на размер логов в `daemon.json`:

```json
{
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

**Управление офсетами Kafka.** При траблшутинге систем с Kafka следует помнить о возможности ручного управления офсетами консьюмеров для повторной обработки потерянных или необработанных сообщений.

**Изоляция сред.** Тестовые контейнеры, генерирующие большой объём данных, должны быть изолированы от продуктивных ресурсов. Используйте отдельные файловые системы для тестовых и продуктивных данных, применяйте cgroups и quotas для ограничения ресурсов.
