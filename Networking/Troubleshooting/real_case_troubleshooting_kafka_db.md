## Определения

- **Айноды (inodes)**: Структуры данных в файловой системе Unix-подобных систем, хранящие метаданные о файлах и директориях (например, права доступа, владельца, временные метки, физическое расположение данных на диске), но не само имя файла или его содержимое. Каждый файл или директория требует один айнод.
- **Продюсер Kafka (Producer)**: Клиентское приложение, которое отправляет (публикует) сообщения в топик Kafka.
- **Консьюмер Kafka (Consumer)**: Клиентское приложение, которое читает (подписывается) сообщения из топика Kafka.
- **Offset в Kafka**: Уникальный, последовательный идентификатор, который Kafka присваивает каждому сообщению в пределах одной партиции. Консьюмеры используют офсет для отслеживания своей позиции чтения в топике.

## Основные концепции

В распределенных системах часто используется асинхронная передача данных через брокеры сообщений, такие как Apache Kafka. Сообщения отправляются **продюсерами** в определенные **топики**, откуда затем читаются **консьюмерами**. Каждый консьюмер отслеживает свой прогресс чтения с помощью **офсетов**. Если консьюмер перестает работать, он возобновляет чтение с последнего сохраненного офсета при повторном запуске.

Стабильная работа систем, особенно баз данных, критически зависит от ресурсов файловой системы. Помимо свободного дискового пространства, важным ресурсом являются **айноды**. Исчерпание свободных айнодов означает, что операционная система не может создавать новые файлы или директории, даже если на диске есть свободное место. Это часто приводит к невозможности записи логов, создания временных файлов или запуска сервисов, требующих файловых операций.

## Практический сценарий: заказ не доходит до склада из-за исчерпания айнодов на сервере БД

### Вводная информация

**Проблема:** Пользователи создают заказы на посадочной странице, получают подтверждение (код 200), но заказы не появляются на складе.
**Предполагаемый стек:** Фронтенд -> Веб-сервер/прокси -> Приложение -> Kafka -> Консьюмер (склад) -> База данных.

### Пошаговый разбор траблшутинга

1. **Анализ на стороне клиента**:
    - Проверка сетевых запросов в браузере (F12) показала, что `POST` запрос на эндпоинт `/orders` успешно уходит на известный IP-адрес сервера компании.
2. **Исследование первого сервера (Nginx)**:
    - Подключение по SSH показало запущенный `Nginx`, вероятно, как балансировщик или прокси.
    - Изучение конфигурации Nginx (`/etc/nginx/nginx.conf`, `sites-available/*`) выявило `proxy_pass` на `upstream` с несколькими серверами.
    - Проверка логов Nginx (`access.log`, `error.log`) подтвердила успешную обработку `POST /orders` с кодом 200 и отсутствие ошибок, указывая на то, что проблема находится дальше по цепочке.
3. **Исследование второго сервера (Application)**:
    - Подключение по SSH к одному из серверов `upstream` показало запущенное приложение на Python (Gunicorn/Flask). Код располагался в `/home/application`.
    - Изучение кода (`requirements.txt`, функции обработки `/orders`) выявило, что функция отправляет сообщения в **Kafka**.
    - Найден `docker-compose.yml` с переменными окружения для подключения к Kafka (адрес брокера, топик). Приложение функционирует как **продюсер Kafka**.
4. **Исследование Kafka**:
    - Через дашборд Grafana для Kafka установлено, что **лаг в топике отсутствует**. Это означает, что сообщения успешно отправляются продюсером и активно читаются каким-то консьюмером.
    - В Wiki найдены потенциальные **консьюмеры** топика, среди которых `Store` (сервис склада) является логичным кандидатом.
    - Проверка состояния консьюмера `Store` в дашборде показала, что он активно пытается читать сообщения, но безуспешно.
5. **Исследование третьего сервера (Consumer)**:
    - Поиск логов консьюмера `Store` в [Elasticsearch](../../ELK_Stack/Elasticsearch/elasticsearch_overview.md) выявил повторяющиеся ошибки: **"не могу подключиться к базе данных"**, с указанием хоста БД.
6. **Исследование четвертого сервера (Database)**:
    - Подключение по SSH к серверу БД показало запущенную базу данных `PostgreSQL` в `Docker`-контейнере.
    - Проверка статуса контейнера БД обнаружила, что он **упал**.
    - Просмотр логов контейнера (`docker logs <container_id>`) показал первичную ошибку **"порт занят"** (`Port is already allocated`), а после попытки перезапуска — **"ошибка, связанная с диском"**.
    - Проверка прав доступа к директории `/var/lib/postgresql/data` показала, что они корректны.
    - Проверка свободного места (`df -h`) показала его наличие, однако `df -i` выявил, что **айноды закончились (100% использование)**.

    > **Диагностика inodes (подробнее):**
>
    > ```bash
    > # Проверка использования inodes на всех файловых системах
    > df -i
    > 
    > # Поиск директорий с большим количеством файлов (основная причина исчерпания inodes)
    > # Предупреждение: может занять много времени на больших файловых системах
    > for i in /*; do echo "$i:"; find "$i" -xdev -type f | wc -l; done | sort -k2 -rn | head -20
    > 
    > # Альтернатива с использованием du
    > du --inodes -S / | sort -rh | head -20
    > ```
    >
    > Подробнее см. [`filesystem_and_disk_space_diagnostics.md`](../../Linux/Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md) и [`links_inodes_dentries.md`](../../Linux/FileSystems/links_inodes_dentries.md).

### Причина и решение проблемы

**Причина:** На хосте с базой данных закончились свободные айноды. Это было вызвано другим тестовым контейнером, который генерировал огромное количество мелких лог-файлов, исчерпав все доступные айноды на файловой системе. Из-за этого PostgreSQL не мог создать свои служебные файлы и, соответственно, запуститься.

**Решение:**

1. Остановлен тестовый контейнер, генерировавший избыточные логи.
2. Удалены ненужные лог-файлы для освобождения айнодов.
3. Контейнер с базой данных успешно запущен.

### Финальные действия

Несмотря на решение основной проблемы, заказы, отправленные в Kafka во время недоступности БД, не были обработаны консьюмером `Store`. Для их обработки **было необходимо сбросить offset для консьюмера `Store` в Kafka**, чтобы он перечитал все необработанные сообщения из топика.

## Дополнительная информация

- **Комплексность траблшутинга**: Данный кейс иллюстрирует, что проблемы в распределенных системах редко имеют одну очевидную причину и требуют последовательного, поуровневого анализа каждого компонента стека.
- **Мониторинг айнодов**: Крайне важно включить мониторинг использования айнодов в систему Observability. Инструменты, такие как Prometheus Node Exporter, могут собирать метрики `node_filesystem_files_free` и `node_filesystem_files_total`.
  - **Пример алерта для Prometheus:**

    ```yaml
    - alert: InodesExhaustionRisk
      expr: node_filesystem_files_free / node_filesystem_files_total < 0.1
      for: 5m
      labels:
        severity: warning
      annotations:
        summary: "Риск исчерпания inodes на {{ $labels.instance }}"
        description: "Свободно менее 10% inodes на файловой системе {{ $labels.mountpoint }}"
    ```

- **Управление логами**: В тестовых и продуктивных окружениях необходимо тщательно контролировать генерацию и ротацию логов, чтобы предотвратить исчерпание дисковых ресурсов (включая айноды).
  - Используйте `logrotate` для ротации логов
  - Настройте `journald` с ограничением размера (`SystemMaxUse=`, `RuntimeMaxUse=`)
  - Для Docker-контейнеров установите лимиты на размер логов в `daemon.json`:

    ```json
    {
      "log-opts": {
        "max-size": "10m",
        "max-file": "3"
      }
    }
    ```

- **Управление офсетами Kafka**: При траблшутинге систем, использующих Kafka, всегда следует помнить о возможности ручного управления офсетами консьюмеров для повторной обработки потерянных или необработанных сообщений.
- **Изоляция сред**: Тестовые контейнеры или приложения, генерирующие большой объем данных, должны быть изолированы от продуктивных ресурсов, чтобы избегать влияния на критически важные сервисы.
  - Используйте отдельные файловые системы для тестовых и продуктивных данных
  - Применяйте cgroups и quotas для ограничения ресурсов
