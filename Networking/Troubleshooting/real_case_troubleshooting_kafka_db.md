# Заказ не доходит до склада: исчерпание inodes на сервере БД

> Эта заметка является описанием практического сценария (кейса) по диагностике распределённой системы. Теоретические основы и инструменты диагностики описаны в: **[Диагностика файловых систем и inodes](../../Linux/Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md)**, **[Ссылки, Inode и Dentry](../../Linux/FileSystems/links_inodes_dentries.md)**, **[Общая методология диагностики](../../Linux/Diagnostics/Troubleshooting/general_troubleshooting_methodology.md)**.

## Определения

- **Inodes (Индексные дескрипторы)** — структуры данных в файловой системе **ОС (Operating System — операционная система / ОС)**, хранящие метаданные о файлах и директориях. Подробнее см. **[Inode](../../Linux/FileSystems/links_inodes_dentries.md#inode-индексный-дескриптор)**.
- **Producer Kafka (Продюсер)** — клиентское приложение, отправляющее сообщения в топик Kafka. См. **[Обзор Kafka](../../Kafka/kafka_overview.md)**.
- **Consumer Kafka (Консьюмер)** — клиентское приложение, читающее сообщения из топика Kafka.
- **Offset в Kafka** — уникальный последовательный идентификатор сообщения в пределах партиции, используемый для отслеживания позиции чтения.

## Основные концепции

В распределённых системах передача данных часто строится на брокерах сообщений, таких как Apache Kafka. Стабильность таких систем зависит от доступности ресурсов файловой системы.

Критическим ресурсом являются **inodes**. Их исчерпание делает невозможным создание новых файлов (логов, временных файлов, сокетов), даже если на диске достаточно свободного места в гигабайтах. Это приводит к каскадным сбоям: приложения не могут запускаться, писать логи или корректно завершать транзакции.

## Практические сценарии

### Сценарий: Заказ не доходит до склада из-за сбоя базы данных

**Проблема:** Пользователи успешно создают заказы в интерфейсе (получают **HTTP (HyperText Transfer Protocol)** код 200), но заказы не отображаются в системе управления складом.

**Архитектура:** Frontend → Nginx (балансировщик) → Приложение (Python/Flask) → Kafka → Сервис склада (Consumer) → **DB (Database — база данных / БД)** PostgreSQL.

#### Шаг 1: Проверка на стороне клиента

Анализ сетевых запросов в браузере подтвердил, что запрос `POST /orders` успешно отправляется на **IP (Internet Protocol)** сервера.

#### Шаг 2: Анализ Nginx

Подключение по **SSH (Secure Shell)** к балансировщику. Логи Nginx (`/var/log/nginx/access.log`) показывают успешные ответы (200 OK) для запросов на создание заказа. Это означает, что запрос принят и передан на `upstream` (серверы приложения).

#### Шаг 3: Проверка сервера приложения

Приложение функционирует как продюсер Kafka. Проверка Docker-контейнеров с приложением показала, что они работают штатно, ошибок отправки в Kafka в логах нет.

#### Шаг 4: Анализ Kafka

С помощью мониторинга (Grafana) установлено, что лаг (очередь необработанных сообщений) в топике отсутствует. Это означает, что сообщения успешно вычитываются консьюмером склада. Однако данные в БД не появляются.

#### Шаг 5: Проверка консьюмера (сервис склада)

Поиск логов сервиса `Store` в Elasticsearch выявил повторяющиеся ошибки: `Connection refused` при попытке подключения к хосту базы данных.

#### Шаг 6: Диагностика сервера базы данных

База данных PostgreSQL запущена в Docker. Проверка статуса:

```bash
docker ps -a
# → STATUS: Exited (1) 5 minutes ago
```

Попытка просмотра логов контейнера:

```bash
docker logs postgres_db
# → FATAL: could not create lock file "postmaster.pid": No space left on device
```

Проверка свободного места на диске:

```bash
df -h
# → /dev/sda1 50G 20G 30G 40% /  (Место есть)
```

Проверка использования inodes:

```bash
df -i
# → /dev/sda1 3.2M 3.2M 0 100% / (Inodes исчерпаны)
```

#### Поиск причины исчерпания inodes

Для поиска директории с аномальным количеством мелких файлов использовалась команда:

```bash
du --inodes -S /var/lib/docker/containers | sort -rh | head -n 10
# → 2800000 /var/lib/docker/containers/<id>/checkpoints
```

**Корень проблемы:** Тестовый контейнер со специфическими настройками проверки состояния (healthchecks) генерировал миллионы мелких файлов в директории `checkpoints`, что привело к исчерпанию лимита inodes на всей файловой системе. PostgreSQL не смог создать служебный `.pid` файл и аварийно завершился.

#### Решение

1. Остановка и удаление проблемного тестового контейнера.
2. Очистка директории с избыточными файлами.
3. Запуск контейнера PostgreSQL.

#### Восстановление данных (Kafka Offset Management)

Так как консьюмер «прочитал» сообщения, но не смог записать их в БД (и, возможно, ошибочно закоммитил офсеты), потребовался сброс офсетов для повторной обработки заказов за период сбоя:

```bash
kafka-consumer-groups --bootstrap-server kafka:9092 --group store-group --topic orders --reset-offsets --to-datetime 2026-06-06T10:00:00.000 --execute
# → NEW-OFFSET: 45021
```

## Дополнительная информация

### Рекомендации по предотвращению подобных инцидентов

1. **Мониторинг ресурсов:** Настройка алертов в Prometheus на использование inodes (метрика `node_filesystem_files_free`). См. пример в **[Диагностика файловых систем](../../Linux/Diagnostics/Filesystem/filesystem_and_disk_space_diagnostics.md#диагностика-нехватки-inodes)**.
2. **Лимиты Docker-логов:** Ограничение размера и количества файлов логов для контейнеров. Подробнее: **[Управление ротацией логов Docker](../../Docker/Docker_logs/docker_log_rotation.md)**.
3. **Изоляция сред:** Хранение данных базы данных на отдельном диске или разделе (LVM-томе), чтобы сбои в `/var/lib/docker` не влияли на работоспособность СУБД.
4. **Управление квотами:** Использование дисковых квот для пользователей или контейнеров, если файловая система это поддерживает (XFS, ext4 с квотами).
