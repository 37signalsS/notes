# Политики кеширования и инвалидации в CDN

### Определения

- **Кеширование в CDN**: Процесс сохранения копий вашего контента на географически распределенных серверах (PoP) для ускорения доставки пользователям.
- **Инвалидация кеша (Cache Invalidation/Purge)**: Механизм принудительного удаления или пометки контента как "устаревшего" в кеше CDN, что заставляет CDN запросить свежую версию с исходного сервера (origin).
- **TTL (Time To Live)**: Время, в течение которого объект считается «свежим» и может отдаваться из кеша без запроса к origin.
- **Stale контент**: Устаревшая копия объекта в кеше, время жизни которой (TTL) истекло.

> Для общего понимания принципов работы CDN см. [Обзор CDN](cdn_overview.md).

---

### Основные концепции

#### Модель свежести и валидации

- **Свежесть (Freshness)**: Определяется директивами `Cache-Control: max-age` (для браузеров) и `s-maxage` (для CDN). Пока контент "свежий", он отдается из кеша немедленно.
- **Валидация (Validation)**: Когда TTL истекает, кеш может проверить, изменился ли контент на origin, используя заголовки `ETag` или `Last-Modified`. Если контент не изменился, origin отвечает статусом `304 Not Modified`, экономя трафик.

#### Ключевые HTTP-заголовки для управления кешем

| Заголовок/Директива      | Назначение                                           |
| ------------------------ | ---------------------------------------------------- |
| `Cache-Control: s-maxage`| Задает TTL специально для общих кешей, таких как CDN. |
| `Cache-Control: max-age` | Задает TTL для частных кешей (браузеров).           |
| `public` / `private`     | Разрешает или запрещает кеширование в общих кешах.     |
| `Vary`                   | Указывает CDN создавать разные версии кеша на основе значений заголовков запроса (например, `Accept-Encoding`, `Accept-Language`). |
| `stale-while-revalidate` | Позволяет отдавать устаревший контент, пока в фоне происходит его обновление. |
| `stale-if-error`         | Позволяет отдавать устаревший контент в случае ошибок на origin-сервере. |

#### Формирование ключа кеша (Cache Key)

Ключ кеша — это уникальный идентификатор объекта в кеше. По умолчанию он состоит из схемы, хоста и пути. Его можно настраивать, включая:

- **Query-параметры**: Важно кешировать только по параметрам, влияющим на контент, игнорируя рекламные и трекинговые (`utm_*`, `fbclid`, `gclid`).
- **Заголовки и Cookies**: Для создания разных версий контента (например, для мобильных и десктопных пользователей).
- **Host**: Для мультидоменных конфигураций (SaaS, white-label решения).

**Пример конфигурации Cache Key (псевдокод):**

```
cache_key = scheme + "://" + host + path + "?sort=" + query.sort
# Игнорируем: utm_*, fbclid, gclid, ref
```

**Важно:** Неправильная настройка ключа кеша ведет к:

- **Cache Fragmentation**: Слишком много вариаций одного контента, низкий Hit Ratio.
- **Cache Collision**: Разный контент отдается по одному ключу (ошибки персонализации).

### Практические сценарии

#### 1. Конфигурация TTL

**Долгоживущая статика (CSS, JS с версионированием в URL):**

```http
HTTP/1.1 200 OK
Content-Type: text/css
Cache-Control: public, max-age=31536000, immutable
```

*`immutable` указывает, что контент никогда не изменится.*

**Динамический HTML (главная страница):**

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: public, s-maxage=60, max-age=0, stale-while-revalidate=300
```

*Кешируется в CDN на 60 секунд, не кешируется в браузере и может быть отдан устаревшим до 5 минут при обновлении в фоне.*

#### 2. Механизмы инвалидации

- **Инвалидация по URL (Purge)**: Точечное удаление одного или нескольких объектов.
- **Инвалидация по тегам (Tag-based Purge / Surrogate Keys)**: Объектам на origin присваиваются теги. Инвалидация по тегу удаляет все связанные с ним объекты. Крайне эффективно для связанных данных (например, `product:123`, `category:A`).
- **Версионирование**: Самый надежный метод. Изменение URL (`/app.v123.js`) гарантирует, что CDN запросит новый файл, так как для него это новый объект.

**Пример API-запроса на инвалидацию по тегам:**

```bash
POST https://api.cdn.com/v1/purge
Authorization: Bearer <token>
Content-Type: application/json

{
  "tags": ["product:123", "posts"]
}
```

**Пример использования Surrogate Keys в origin-ответе:**

```http
HTTP/1.1 200 OK
Content-Type: text/html
Surrogate-Key: product:123 category:electronics brand:sony
Cache-Control: public, s-maxage=300
```

*При обновлении продукта `product:123` достаточно отправить purge по тегу — все страницы с этим продуктом (карточка товара, категории, рекомендации) будут обновлены автоматически.*

### Дополнительная информация

#### Best Practices 2025

- **TTL-стратегия**:
  - **Статика с хешем в URL** (`/app.a1b2c3.js`): `max-age=31536000, immutable` — кеширование на год.
  - **Динамический HTML**: `s-maxage=60-300`, `stale-while-revalidate=600` — баланс актуальности и производительности.
  - **API-ответы**: `s-maxage=10-60`, `stale-while-revalidate=300` — для long-tail контента.
  - **Изображения/видео**: `s-maxage=86400-604800` (1-7 дней) с ETag для валидации.

- **Инвалидация**:
  - **Приоритет 1**: Версионирование URL (изменение пути/имени файла).
  - **Приоритет 2**: Tag-based purge (Surrogate Keys) для групповой инвалидации.
  - **Приоритет 3**: Purge по URL — только для точечных исправлений.

- **Защита Origin**:
  - **Origin Shield**: Промежуточный уровень кеширования между PoP и origin для снижения нагрузки.
  - **Негативное кеширование**: Короткий TTL (30-300 сек) для 4xx/5xx ответов.
  - **Rate Limiting**: Ограничение запросов к origin при Cache Miss.

#### Рекомендации

- Используйте **длинный TTL** для статики с версионированием и **короткий TTL** с `stale-while-revalidate` для HTML и API.
- Предпочитайте **версионирование** и **инвалидацию по тегам** массовому удалению по URL (`*`), чтобы снизить пиковую нагрузку на origin.
- Настраивайте **негативное кеширование** (короткий TTL для 4xx/5xx ответов), чтобы защитить origin от лавинных запросов к несуществующим ресурсам.
- **Мониторинг**: Alert на Cache Hit Ratio <80% для статики, рост 5xx от origin.

#### Диагностика

Анализируйте заголовки ответа для отладки:

- `X-Cache: HIT/MISS` или `CF-Cache-Status: HIT/MISS/EXPIRED/STALE`
- `Age`: Время в кеше (сек)
- `Via`: Указание на CDN-прокси
- `X-Cache-Key`: Сформированный ключ кеша (если поддерживается)

#### Метрики

- **Cache Hit Ratio**: Ключевой показатель эффективности. Целевое значение — >90% для статики, >70% для динамики.
- **Origin Requests/sec**: Количество запросов к origin. Резкий рост — признак проблем с кешированием.
- **Bandwidth Savings**: Разница между трафиком пользователей и трафиком от origin.
- **Invalidation Latency**: Время между purge-запросом и фактическим удалением из кеша.
