# NetBox: Обзор и базовые концепции

## Определения

**NetBox** — специализированный инструмент класса **IPAM (IP Address Management)** и **DCIM (Data Center Infrastructure Management)** с открытым исходным кодом. Разработан для сетевых инженеров как «единый источник истины» (**Single Source of Truth, SSoT**) для инфраструктуры.

**IPAM** — управление адресным пространством: IP-адреса, префиксы, VLAN, VRF, ASN. Система отслеживает иерархию подсетей и статус их утилизации.

**DCIM** — управление физической инфраструктурой: площадки (Sites), здания, стойки (Racks), устройства, кабели и интерфейсы. Позволяет моделировать размещение оборудования вплоть до юнита и конкретного порта.

**SSoT (в контексте NetBox)** — принцип, при котором NetBox содержит идеальное, проектное состояние сети. Все системы автоматизации (Ansible, Terraform) должны брать данные из NetBox, а не из конфигураций самих устройств.

**Circuits** — модель для представления каналов связи (линий аренды, прямых подключений, VPN), связывающих сайты. Включает информацию о провайдерах, контрактах и физических точках подключения.

**Providers** — организации, предоставляющие услуги связи (операторы, провайдеры). Связаны с каналами (Circuits) и контактами.

**Contacts** — модель для хранения контактной информации (имена, email, телефоны) с привязкой к сайтам, провайдерам или другим объектам.

**Tags** — системная возможность для классификации и группировки объектов по произвольным признакам (среда, критичность, владелец).

**Custom Fields** — расширяемые пользователем поля для хранения специфичных данных (номер договора, дата ТО, стоимость аренды), которые отсутствуют в стандартных моделях.

**Custom Links** — гиперссылки, динамически генерируемые на основе атрибутов объекта (например, ссылка на тикет в Jira или документацию в Confluence).

**Webhooks** — HTTP-запросы, автоматически отправляемые NetBox при создании, изменении или удалении объектов. Используются для интеграции с CI/CD, системами мониторинга и внешними сервисами.

**Reports** — Python-скрипты для проверки целостности данных (валидация связей, проверка заполненности обязательных полей, поиск конфликтов адресации).

**Custom Scripts** — расширяемая логика для автоматизации задач (создание объектов по шаблону, массовые операции, интеграция с внешними API), работающая через очередь задач NetBox (RQ).

**Export Templates** — шаблоны на базе Jinja2 для экспорта данных NetBox в различные форматы (CSV, JSON, YAML, TXT) для интеграции с внешними системами.

**GraphQL** — альтернативный API для получения связанных данных за один запрос (например, устройства + их префиксы + сайты + провайдеры).

## Архитектура и компоненты

NetBox представляет собой веб-приложение на базе Python-фреймворка **Django**. Для работы требуется стек компонентов:

-   **PostgreSQL**: Основная база данных для структурированной информации.
-   **Redis**: Используется для кэширования данных и очередей задач.
-   **Gunicorn (WSGI)**: Сервер для запуска Python-кода приложения.
-   **Nginx/Apache**: Реверс-прокси для обработки HTTP/HTTPS, SSL-терминации и отдачи статики.
-   **RQ (Redis Queue)**: Фоновая обработка «тяжелых» задач (вебхуки, отчеты, скрипты).
-   **Housekeeping**: Служба очистки сессий и старых логов изменений.

### Ключевые особенности архитектуры

- **REST API**: Полнофункциональный API для CRUD-операций со всеми объектами. Поддерживает фильтрацию, пагинацию и аутентификацию по токенам.
- **GraphQL**: Альтернативный API для сложных запросов с вложенными связями. Оптимален для получения данных из нескольких моделей за один запрос.
- **Система плагинов**: Модульная архитектура, позволяющая расширять функционал через Django-приложения (плагины добавляют новые модели, views, API-эндпоинты).
- **Очередь задач (RQ)**: Фоновая обработка тяжелых операций (генерация отчетов, массовые обновления, отправка вебхуков).
- **Аудит изменений**: Автоматическое логирование всех операций с объектами (создание, изменение, удаление) с фиксацией пользователя и времени.

## Базовые концепции

### Иерархия адресного пространства (IPAM)

NetBox организует адресацию в древовидную структуру для контроля утилизации:

1.  **RIR (Regional Internet Registry)**: Организации-регистраторы (RIPE, ARIN, LACNIC, APNIC, AFRINIC).
2.  **Aggregate**: Крупные блоки (например, `10.0.0.0/8`), принадлежащие компании или полученные от RIR.
3.  **Prefix**: Конкретные подсети (`10.10.0.0/24`), выделенные под задачи или локации. Имеют статусы: Active, Container, Reserved, Deprecated.
4.  **IP Range**: Диапазоны внутри префикса (например, для пула DHCP). Используются для резервирования адресов без привязки к конкретным интерфейсам.
5.  **IP Address**: Конечные адреса, назначенные интерфейсам устройств. Каждый адрес может иметь статус (Active, Reserved, Deprecated) и привязку к интерфейсу.

### Моделирование оборудования (DCIM)

Инвентаризация базируется на иерархии объектов:
-   **Manufacturer / Device Type**: Описание модели (производитель, количество слотов, портов, высота в RU).
-   **Module Type**: Описание сменных компонентов (линейные карты, трансиверы, блоки питания).
-   **Device / Module**: Конкретные экземпляры с серийными номерами и Asset Tags, установленные в стойки.
-   **Device-type Library**: Открытая библиотека готовых шаблонов оборудования (device-type-defs), поддерживаемая сообществом.
-   **Device Roles**: Классификация устройств по функциональному назначению (Core Switch, Access Switch, Router, Firewall, Server, PDU).
-   **Device Status**: Текущее состояние устройства (Planned, Staged, Active, Decommissioning, Offline, Inventory).

### Моделирование физической инфраструктуры

- **Sites**: Физические локации (здания, дата-центры, офисы). Каждый сайт содержит стойки, устройства и патч-панели.
- **Racks**: Стоек с указанием размера (высота в RU), типа (2-post, 4-post, wall-mount) и физического размещения.
- **Power Panels и Power Feeds**: Моделирование электропитания (панели, линии электропитания, статус питания).
- **Cables**: Кабельные соединения между интерфейсами (оптика, медные патч-корды). Поддержка сложных сборок (Cable Profiles, Breakout-кабели).
- **Front/Back Ports**: Порты патч-панелей для моделирования кроссировок и соединений между стойками.

### Виртуализация и логические связи

NetBox поддерживает учет виртуальной инфраструктуры:
- **Virtualization Clusters**: Группы виртуальных машин (VMware, KVM, Proxmox).
- **Virtual Machines**: Виртуальные машины с интерфейсами и привязкой IP, аналогично физическому оборудованию.
- **Virtual Chassis**: Объединение физических коммутаторов в логический стек (supports "member" и "master" roles).
- **LAG (Link Aggregation Group)**: Агрегация интерфейсов (LACP) на уровне моделирования.

### Сетевые сервисы и каналы

- **Circuits**: Каналы связи (аренда, прямые подключения). Каждый канал связан с провайдером, контрактом и точками подключения (site circuit terminations).
- **Providers**: Провайдеры услуг связи с контактной информацией и ссылками на каналы.
- **Circuit Types**: Типы каналов (Point-to-Point, MPLS, VPN, Internet).
- **Circuit Groups**: Группировка каналов для удобства управления.

### Управление доступом и безопасность (RBAC)

**RBAC (Role-Based Access Control)** — модель управления доступом, основанная на ролях. В NetBox реализована через систему пользователей, групп, объектных разрешений и объектных выводов.

**Users** — учетные записи пользователей. Каждый пользователь может принадлежать к нескольким группам и иметь собственные разрешения.

**Groups** — группы пользователей для массового назначения разрешений. Например, `Network Engineers`, `NOC Operators`, `Read-only`.

**Object Permissions** — гранулярные права доступа на уровне объектов с фильтрацией по атрибутам:

| Разрешение | Описание | Пример |
| :--- | :--- | :--- |
| **View** | Просмотр объектов | Читать устройства |
| **Add** | Создание новых объектов | Создавать префиксы |
| **Change** | Изменение существующих | Обновлять интерфейсы |
| **Delete** | Удаление объектов | Удалять IP-адреса |

**Object Outputs** — ограничение доступа к конкретным атрибутам:

| Вывод | Описание | Пример |
| :--- | :--- | :--- |
| **_sites** | Доступ только к определенным сайтам | Инженеры видят только свои site |
| **device_roles** | Доступ только к определенным ролям | NOC не может менять core-устройства |
| **prefixes** | Доступ только к определенным подсетям | Финансовый отдел видит только 10.x.x.x |

**Настройка RBAC через веб-интерфейс:**

1. **Создание группы:** `Admin → Users → Groups → Add`
2. **Настройка разрешений:** `Admin → Users → Groups → Permissions`
3. **Назначение пользователей:** `Admin → Users → Users → Edit → Groups`

**Пример настройки разрешений:**

```python
# Создание группы с ограничениями
from users.models import Group, ObjectPermission

# Группа "NOC Engineers" — только просмотр и изменение интерфейсов
group = Group.objects.create(name='NOC Engineers')
ObjectPermission.objects.create(
    group=group,
    name='View Devices',
    model='dcim.device',
    actions=['view'],
    constraints={'site__slug__in': ['dc-north', 'dc-south']}
)

# Группа "Network Admins" — полный доступ к определенным сайтам
group_admins = Group.objects.create(name='Network Admins')
ObjectPermission.objects.create(
    group=group_admins,
    name='Full Access DC North',
    model='dcim.device',
    actions=['view', 'add', 'change', 'delete'],
    constraints={'site__slug': 'dc-north'}
)
```

**Token-based Authentication:**

| Параметр | Описание | Рекомендация |
| :--- | :--- | :--- |
| **write_enabled** | Разрешение на запись | `False` для скриптов мониторинга |
| **expires** | Срок действия токена | Устанавливайте для временных токенов |
| **allowed_ips** | Ограничение по IP | Whitelist для конкретных IP |
| **description** | Описание назначения | УказывайтеPurpose токена |

**Пример создания токена с ограничениями:**

```python
from users.models import Token

token = Token.objects.create(
    key='automation_token_2026',
    user_id=1,
    description='Ansible Automation Token',
    write_enabled=True,
    expires='2026-12-31',
    allowed_ips=['10.0.0.0/8', '192.168.1.0/24']
)
```

### Система изменений и аудита

- **Object Changes**: Автоматическое логирование всех изменений (создание, изменение, удаление) с фиксацией пользователя, времени и деталей.
- **Journal Entries**: Ручные записи в журнале объектов (заметки, комментарии к инцидентам).
- **Config Contexts**: Контекстные данные для устройств (например, специфичные настройки для разных site или role), используемые при генерации конфигураций.

### Config Contexts и Object Permissions

**Config Contexts** — механизм для хранения контекстных данных, привязанных к объектам NetBox. Используются для генерации конфигураций, интеграции с внешними системами и хранения учетных данных.

**Применение Config Contexts:**

| Сценарий | Данные | Пример |
| :--- | :--- | :--- |
| **Учетные данные** | SSH-логин, пароль, enable | Для Oxidized/Rancid |
| **Специфичные настройки** | NTP, DNS, syslog | Разные для каждого site |
| **Интеграция** | API-ключи внешних систем | Slack-токены, Jira URL |
| **Шаблоны** | Параметры для Jinja2 | Маска подсети, gateway |

**Иерархия Config Contexts:**

```
Global (вес: 1000)
├── Site-specific (вес: 900)
│   ├── dc-north
│   └── dc-south
├── Role-specific (вес: 800)
│   ├── access-switch
│   └── core-switch
└── Tag-specific (вес: 700)
    ├── production
    └── staging
```

**Создание Config Context через API:**

```python
import pynetbox
import os

nb = pynetbox.api(url=os.getenv('NETBOX_URL'), token=os.getenv('NETBOX_TOKEN'))

# Создание контекста для всех устройств в site
context = nb.extras.config_contexts.create(
    name='SSH Credentials - DC North',
    weight=1000,
    data={
        'ssh_username': 'admin',
        'ssh_password': 'secure_password',
        'ssh_port': 22,
        'enable_password': 'enable_pass'
    },
    description='Учетные данные для резервного копирования'
)

# Привязка к site
site = nb.dcim.sites.get(slug='dc-north')
context.sites.append(site.id)
context.save()
```

**Приоритеты Config Contexts:**

| Приоритет | Описание | Пример |
| :--- | :--- | :--- |
| **Высокий (1000+)** | Глобальные настройки | SSH- учетные данные |
| **Средний (500-999)** | Site-специфичные | NTP-серверы для сайта |
| **Низкий (<500)** | Роль-специфичные | Настройки для access-switch |

### Multi-tenancy в NetBox

**Tenant Group** — группа арендаторов для организации иерархии. Например, `Внутренние подразделения`, `Внешние клиенты`.

**Tenant** — арендатор (владелец ресурсов). Каждый tenant может владеть префиксами, VLAN, устройствами, каналами связи.

**Применение Multi-tenancy:**

| Сценарий | Описание |
| :--- | :--- |
| **MSP (Managed Service Provider)** | Разные клиенты — разные tenants |
| **Корпоративная сеть** | Разные подразделения — разные tenants |
| **Общественная инфраструктура** | Разные организации — разные tenants |

**Создание Tenant:**

```python
import pynetbox
import os

nb = pynetbox.api(url=os.getenv('NETBOX_URL'), token=os.getenv('NETBOX_TOKEN'))

# Создание tenant group
tenant_group = nb.tenancy.tenant_groups.create(
    name='Internal Departments',
    description='Внутренние подразделения компании'
)

# Создание tenant
tenant = nb.tenancy.tenants.create(
    name='Network Operations',
    slug='noc',
    group=tenant_group.id,
    description='Отдел сетевых операций'
)

# Привязка tenant к префиксу
prefix = nb.ipam.prefixes.get(prefix='10.0.0.0/8')
prefix.tenant = tenant.id
prefix.save()
```

**Модели, поддерживающие Tenant:**

| Модель | Описание |
| :--- | :--- |
| **Prefix** | Адресные пространства |
| **VLAN** | Виртуальные сети |
| **Device** | Сетевое оборудование |
| **Circuit** | Каналы связи |
| **IP Address** | IP-адреса |
| **Aggregate** | Агрегаты RIR |

**Иерархия tenant:**

```
Tenant Group: Внутренние подразделения
├── Tenant: Network Operations
├── Tenant: Server Team
└── Tenant: Security

Tenant Group: Внешние клиенты
├── Tenant: Client A
├── Tenant: Client B
└── Tenant: Client C
```

### Новое в NetBox 4.x (2025–2026)

-   **NetBox Branching (Ветвление)**: Рабочий процесс, аналогичный Git. Инженер создает ветку, вносит изменения (Stage), просматривает Diff и только после одобрения выполняет слияние (Merge) с основной базой.
-   **NetBox Copilot**: Встроенный ИИ-ассистент для анализа данных и генерации запросов на естественном языке.
-   **Remote Data Sources**: Возможность синхронизации данных напрямую из внешних источников (Git-репозитории, S3) без промежуточных скриптов.
-   **Cable Profiles**: Поддержка сложных кабельных сборок и Breakout-кабелей на уровне моделей.
-   **NetBox Data Exchange (NDX)**: Протокол обмена метаданными между инсталляциями и поставщиками.

## Практические сценарии

### Интеграция как SSoT для автоматизации

Использование NetBox как источника данных для генерации конфигураций:

1.  Инженер вносит изменения в NetBox (например, меняет описание интерфейса или выделяет новый VLAN).
2.  NetBox отправляет **Webhook** в систему CI/CD (GitLab CI, GitHub Actions, Jenkins).
3.  **Ansible/Terraform** запрашивает данные через REST API или GraphQL и применяет их на устройстве.
4.  После применения изменения конфигурации NetBox обновляет статус (например, помечает интерфейс как "configured").

**Пример интеграции с Ansible:**
```yaml
- name: Получение данных из NetBox
  hosts: localhost
  tasks:
    - name: Запрос устройств из NetBox
      uri:
        url: "https://netbox.example.com/api/dcim/devices/"
        headers:
          Authorization: "Token {{ netbox_token }}"
        method: GET
      register: devices

    - name: Группировка устройств по site
      add_host:
        name: "{{ item.name }}"
        groups: "site_{{ item.site.name }}"
        ansible_host: "{{ item.primary_ip4.address | default('undefined') }}"
      loop: "{{ devices.json.results }}"
```

### Контроль дрейфа конфигурации (Drift Detection)

Сравнение реального состояния сети с данными в NetBox:

1.  Скрипт опрашивает устройства по SNMP/SSH (используя Napalm или Netmiko).
2.  Данные сравниваются с базой NetBox через API.
3.  **Reports** подсвечивают расхождения (например, порт активен, но в NetBox помечен как свободный; VLAN настроен, но не выделен в IPAM).
4.  При необходимости инженер корректирует данные в NetBox или конфигурацию устройства.

**Пример отчета для проверки VLAN:**
```python
from extras.reports import Report

class VLANConsistencyReport(Report):
    description = "Проверка соответствия VLAN между NetBox и оборудованием"

    def test_vlan_existence(self):
        # Получение VLAN из NetBox
        nb_vlans = self.nb.ipam.vlans.all()
        # Сравнение с реальными VLAN на устройстве
        for vlan in nb_vlans:
            if not self.check_device_vlan(vlan.vid):
                self.log_failure(f"VLAN {vlan.vid} не найден на устройстве")
            else:
                self.log_success(f"VLAN {vlan.vid} корректен")
```

### Управление через Webhooks

Автоматическая уведомление внешних систем при изменениях в NetBox:

1.  Настройка Webhook в NetBox (Admin → Webhooks) с указанием URL получателя и событий (created, updated, deleted).
2.  При изменении объекта NetBox отправляет HTTP POST с JSON-представлением объекта.
3.  Внешний сервис обрабатывает уведомление (обновляет CMDB, отправляет уведомление в Slack, запускает пайплайн).

**Пример полезного payload:**
```json
{
  "event": "updated",
  "timestamp": "2026-01-15T10:30:00Z",
  "model": "interface",
  "object": {
    "id": 123,
    "name": "GigabitEthernet0/1",
    "device": {"name": "SW-01"},
    "description": "Подключение к серверу SVR-01",
    "status": "active"
  }
}
```

### Массовые операции через Custom Scripts

Выполнение массовых действий через встроенные скрипты NetBox:

1.  Создание скрипта в `netbox/scripts/` или через плагин.
2.  Скрипт получает данные из NetBox, выполняет логику (проверки, трансформации) и применяет изменения через API.
3.  Запуск из веб-интерфейса (Scripts → Run) или через API.

**Пример скрипта для массового назначения VLAN:**
```python
from extras.scripts import Script, StringVar, IntegerVar
from ipam.models import VLAN

class AssignVLANToDevices(Script):
    class Meta:
        name = "Назначение VLAN устройствам"
        description = "Массовое добавление VLAN к интерфейсам устройств指定ного site"

    site_name = StringVar(description="Имя site")
    vlan_id = IntegerVar(description="VID VLAN")

    def run(self, data, commit):
        site = Site.objects.get(name=data['site_name'])
        devices = Device.objects.filter(site=site)
        vlan = VLAN.objects.get(vid=data['vlan_id'])
        
        for device in devices:
            self.log_info(f"Обработка {device.name}")
            # Логика добавления VLAN к интерфейсам
            self.log_success(f"VLAN {vlan.vid} назначен для {device.name}")
```

### Автоматизация через pynetbox

Программное управление через Python API (подробности см. в [Автоматизация NetBox с использованием Python](./netbox-automation-python.md)):

```python
import pynetbox

nb = pynetbox.api(url="https://netbox.example.com", token="YOUR_TOKEN")

# Получение списка устройств с фильтрацией
devices = nb.dcim.devices.filter(site="dc-north", role="access-switch")

for device in devices:
    print(f"{device.name}: {device.primary_ip4}")

# Создание нового префикса
prefix = nb.ipam.prefixes.create(
    prefix="10.10.10.0/24",
    site={"slug": "dc-north"},
    status="active",
    description="Подсеть для серверов"
)
```

### Практический обход веб-интерфейса и создание объектов

NetBox имеет строгую иерархию зависимостей между объектами. При первом заполнении базы следуйте этой последовательности:

**1. Создание сайта (Site)**

Сайт — базовый контейнер для физической инфраструктуры (офис, дата-центр, домашняя лаборатория).

1. Перейдите: `DCIM → Sites → Add`
2. Заполните обязательные поля:
   - `Name`: имя сайта (например, `Homelab`)
   - `Slug`: уникальный идентификатор URL (строчные буквы, без пробелов, например `homelab`)
3. Опционально: `Region`, `Timezone`, `Physical Address`, `Description`

После создания сайта становится доступным добавление стоек, устройств и IP-префиксов.

**2. Создание серверной стойки (Rack)**

Стойка физически размещает устройства в юнитах (RU).

1. Перейдите: `DCIM → Racks → Add`
2. Заполните:
   - `Name`: например `Server Rack Homelab`
   - `Site`: выберите созданный сайт
   - `Status`: `Active` (или `Planned`, `Reserved`)
   - `Type`: `2-post` или `4-post` (стандарт 19 дюймов)
   - `Height`: высота в RU (например, `24U`)
   - `Width`: обычно `19` (стандарт) или `10` (колено-стойка)
3. На странице стойки видна схема с юнитами — устройства можно прикреплять к конкретным позициям.

**3. Создание роли устройства (Device Role)**

Роль определяет функциональное назначение оборудования.

1. Перейдите: `DCIM → Device Roles → Add`
2. Заполните:
   - `Name`: например `Core Switch`, `Proxmox Host`, `Firewall`
   - `Slug`: `core-switch`, `proxmox-host`
   - `Color`: визуальным маркером в интерфейсе
   - `VM Role`: включите, если роль может назначаться виртуальным машинам

**4. Создание производителя и типа устройства (Manufacturer → Device Type)**

Тип устройства описывает аппаратные характеристики (высота, количество интерфейсов).

1. Перейдите: `DCIM → Manufacturers → Add` → создайте производителя (например, `Self-built`, `HP`, `Dell`).
2. Перейдите: `DCIM → Device Types → Add`
   - `Manufacturer`: выберите созданного производителя
   - `Model`: например `Proxbox 2U`
   - `Height`: высота в RU (например, `2`)
   - `Full Depth`: `true`/`false` в зависимости от модели
   - На вкладке `Interfaces` добавьте интерфейсы: `eth0` (1000BASE-T), `eth1` (SFP+)

**5. Создание физического устройства (Device)**

Устройство — конкретный экземпляр, установленный в стойку.

1. Перейдите: `DCIM → Devices → Add`
2. Заполните:
   - `Name`: например `Proxmox Production`
   - `Role`: выберите роль `Proxmox Host`
   - `Device Type`: выберите созданный тип
   - `Site`: выберите сайт
   - `Rack`: выберите стойку
   - `Position`: юнит начала установки (например, `U16`)
   - `Status`: `Active`
   - `Side`: `Front` или `Rear` (куда обращена лицевая панель)
3. После создания устройство появится на схеме стойки.

**6. Создание кластера виртуализации (Cluster)**

Кластер объединяет виртуальные машины физического гипервизора.

1. Перейдите: `Virtualization → Clusters → Add`
2. Заполните:
   - `Name`: например `Proxmox Production`
   - `Type`: `Proxmox`
   - `Status`: `Active`
3. **Привязка физического устройства к кластеру:**
   - Откройте созданное ранее устройство `Proxmox Production` → `Edit`
   - В поле `Cluster` выберите `Proxmox Production`
   - Это создает связь: физический сервер → виртуальный кластер.

**7. Создание виртуальной машины (Virtual Machine)**

ВМ создается в контексте кластера.

1. Перейдите: `Virtualization → Virtual Machines → Add`
2. Заполните:
   - `Name`: например `Production Server`
   - `Status`: `Active`
   - `Cluster`: выберите `Proxmox Production`
   - `Role`: (опционально) выберите роль ВМ
   - `Site`: выберите сайт
3. На вкладке `Interfaces` можно добавить виртуальные интерфейсы.
4. На вкладке `Components` можно задать vCPU, память, диск.

**8. Создание интерфейса (Interface)**

Интерфейс — сетевая карта устройства или ВМ, к которой привязывается IP.

1. Откройте устройство или ВМ → `Interfaces → Add`
2. Заполните:
   - `Name`: например `eth0`
   - `Type`: `1000base-t` (медная гигабит), `SFP+ (10G)`, `virtual`
   - `Enabled`: `true`
   - `Description`: описание подключения

**9. Добавление IP-адреса (IPAM)**

IP-адрес назначается интерфейсу и становится частью IPAM.

1. Перейдите: `IPAM → IP Addresses → Add`
2. Заполните:
   - `Address`: например `10.20.0.4/16` (обязательно с маской подсети)
   - `Status`: `Active` / `Reserved` / `Deprecated`
   - `Assigned Object`: выберите интерфейс устройства или ВМ
   - `DNS Name`: (опционально) FQDN
3. После назначения IP отображается в таблице устройств и в разделе IPAM.

**10. Назначение основного IP-адреса (Primary IP)**

Для управления устройством через SSH/API указывается основной IP:

1. Откройте устройство → `Edit`
2. В поле `Primary IPv4` (или `Primary IPv6`) выберите созданный IP-адрес.
3. Сохраните — теперь в таблице устройств отображается управляющий адрес.

**Зависимости между объектами:**

```
Site
├── Rack
├── Device Role
├── Manufacturer → Device Type
│   └── Device (в Rack)
│       ├── Interface
│       └── IP Address (Primary IPv4/IPv6)
└── Prefix (IPAM)
    └── IP Address
```

### Интеграция с Kubernetes и CNI

Синхронизация состояния сети Kubernetes с NetBox (подробности см. в [Интеграция IPAM в Kubernetes](../../Kubernetes/Networking/Network/CNI/ipam.md)):

1.  **NetBox Operator** в Kubernetes автоматически синхронизирует Pod IP с NetBox.
2.  При создании Pod IP помечается в NetBox как `Active`.
3.  В метаданных NetBox сохраняется привязка: `Node Name`, `Pod Name`, `Namespace`.
4.  При удалении Pod IP освобождается и помечается как `Deprecated`.

## Варианты развертывания

1.  **Docker Compose**: Рекомендуемый метод (`netbox-docker`). Обеспечивает быструю развертку и изоляцию зависимостей.
2.  **Ручная установка (Bare Metal)**: Установка в ОС (Debian/Ubuntu). Дает полный контроль над тюнингом производительности.
3.  **NetBox Cloud**: SaaS-решение от NetBox Labs. Подходит для команд, желающих избежать обслуживания сервера.
4.  **High Availability (HA)**: Развертывание кластера с балансировщиком, несколькими узлами приложения и отказоустойчивыми БД/Redis.

### Сравнение вариантов развертывания

| Критерий | Docker Compose | Bare Metal | NetBox Cloud | HA Cluster |
| :--- | :--- | :--- | :--- | :--- |
| **Сложность настройки** | Низкая | Средняя | Минимальная | Высокая |
| **Производительность** | Средняя | Высокая | Зависит от плана | Высокая |
| **Масштабируемость** | Ограничена | Средняя | Автоматическая | Высокая |
| **Обслуживание** | Умеренное | Высокое | Минимальное | Высокое |
| **Стоимость** | Бесплатно + сервер | Бесплатно + сервер | Платная подписка | Бесплатно + кластер |
| **Отказоустойчивость** | Нет | Нет | Да | Да |

### Рекомендации по внедрению

-   **Поэтапный импорт**: Начните с IPAM (самое простое), затем переходите к DCIM и кабельным связям.
-   **Кастомные поля (Custom Fields)**: Используйте их для специфичных данных (номер договора, дата ТО, стоимость аренды), чтобы не перегружать стандартные поля.
-   **API-First**: Любое действие, выполняемое чаще одного раза в неделю, должно быть автоматизировано через Python (pynetbox) или Ansible.
-   **Валидация данных**: Настройте Reports для проверки целостности данных (отсутствующие IP, незаполненные обязательные поля, конфликты адресации).
-   **Ролевая модель**: Настройте Object Permissions для ограничения доступа (например, инженеры могут изменять только свои site, а аналитики — только просматривать).
-   **Резервное копирование**: Регулярно экспортируйте БД и медиа-файлы (особенно перед обновлением).

### Типовые ошибки и их решения

| Проблема | Вероятная причина | Решение |
| :--- | :--- | :--- |
| **502 Bad Gateway** | Не запущен Gunicorn или netbox-rq | Проверьте `systemctl status netbox netbox-rq` и логи |
| **Ошибки статики** | Нет прав на чтение папки static | `chown -R www-data:www-data /opt/netbox/netbox/static/` |
| **Redis Connection Error** | Неверный пароль или не запущен Redis | Проверьте `configuration.py` и `systemctl status redis` |
| **Duplicate IP Error** | IP уже назначен другому интерфейсу | Проверьте уникальность в IPAM или отключите строгую проверку |
| **Permission Denied** | Не хватает прав API-токена | Настройте Object Permissions или добавьте токен в группу |
| **Webhook не отправляется** | Некорректный URL или сертификат | Проверьте URL, SSL-сертификат и логи netbox-rq |
