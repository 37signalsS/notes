# NAT — трансляция сетевых адресов

## Определения

**NAT (Network Address Translation — трансляция сетевых адресов)** — технология преобразования IP-адресов в заголовках сетевых пакетов при их прохождении через маршрутизатор или межсетевой экран. Основное назначение — обеспечение доступа устройств из частных сетей в публичные сети (интернет) и повторное использование IPv4-адресного пространства.

NAT работает на [сетевом уровне (L3)](../../OSI_TCP_IP_Model/Network_layer/Concepts/network_layer_overview.md) модели OSI, но зачастую затрагивает транспортный уровень (L4) для подмены портов (PAT).

## Базовые концепции

### Частные и публичные IP-адреса

*   **Частный («серый») IP-адрес** — адрес из диапазонов [RFC 1918](../../Protocols/IP_addressing/special_addresses.md#частные-приватные-сети-rfc-1918), не маршрутизируемый в глобальной сети.
*   **Публичный («белый») IP-адрес** — глобально уникальный адрес, маршрутизируемый в интернете.

**Способ проверки NAT:**
Если IP-адрес на сетевом интерфейсе устройства (например, `192.168.x.x`) отличается от адреса, видимого внешним сервисам (например, через `curl ifconfig.me`), значит, устройство находится за NAT.

### Задачи и преимущества

1.  **Экономия адресного пространства:** Позволяет тысячам устройств использовать один публичный IP-адрес.
2.  **Безопасность (Security by Obscurity):** Скрывает внутреннюю топологию сети. Внешние узлы не могут инициировать соединение с внутренним хостом без явно настроенного проброса (DNAT).
3.  **Гибкость:** Позволяет менять провайдера или внутреннюю адресацию без перенастройки всех конечных узлов.

### Механизм отслеживания состояний (Conntrack)

Большинство реализаций NAT являются **stateful** (с сохранением состояния). В ядре Linux архитектура Netfilter разделяет два взаимосвязанных модуля:

*   **Conntrack (Connection Tracking)** — модуль, отслеживающий состояния соединений. Поддерживает таблицу соединений, но не выполняет трансляцию адресов. Работает независимо от NAT и используется также stateful-фильтрацией (firewall).
*   **NAT** — модуль, использующий записи conntrack для выполнения трансляции адресов и портов. NAT не имеет собственной таблицы — он заполняет поля NAT-расширения в существующих записях conntrack.

Эта архитектура означает, что conntrack является обязательным для NAT: если conntrack отключен (или соединение не отслеживается), NAT-правила работать не будут.

#### Состояния соединений (Conntrack States)

| Состояние | Описание | Пример | Таймаут по умолчанию (Linux) |
| :--- | :--- | :--- | :--- |
| **NEW** | Первый пакет сессии. Соединение ещё не установлено. | TCP SYN | 120 сек (tcp_timeout_syn_sent) |
| **ESTABLISHED** | Установленное соединение. После завершения handshake (для TCP) или первого пакета (для UDP/ICMP). | TCP SYN-ACK → данные | 432000 сек / 5 дней (tcp_timeout_established) |
| **RELATED** | Вспомогательное соединение, связанное с основным. | Трансляция FTP-данных, ICMP-ошибки, DTLS-сессии | 300 сек (udp_timeout_related) |
| **INVALID** | Пакет не может быть идентифицирован как NEW, ESTABLISHED или RELATED. Часто — некорректный стек TCP или аномалии. | Фрагментированные пакеты без заголовка L4, TCP RST без предшествующего соединения | — (пакет отбрасывается) |

**Нюансы состояний:**
*   Для **UDP** (без состояний на уровне протокола) conntrack тем не менее создаёт запись и отслеживает «виртуальное соединение» по комбинации源IP:порт → destIP:порт.
*   Для **ICMP** создаются отдельные записи для каждого типа/кода. ICMP-ответы (type 0/8) связываются с основным соединением как RELATED.
*   Состояние **INVALID** часто возникает при асимметричной маршрутизации (когда ответный пакет проходит через другой NAT-узел) или при некорректной фрагментации.

#### Таймауты Conntrack (Ключевые параметры Linux)

Полный список параметров доступен через:
```bash
sysctl -a | grep nf_conntrack
```

Наиболее важные таймауты для тюнинга:

| Параметр | Значение по умолчанию | Рекомендация для SRE |
| :--- | :--- | :--- |
| `nf_conntrack_tcp_timeout_established` | 432000 (5 дней) | 3600–7200 (1–2 часа) для высоконагруженных NAT-шлюзов |
| `nf_conntrack_tcp_timeout_time_wait` | 120 | 30–60 для ускорения освобождения портов |
| `nf_conntrack_tcp_timeout_close_wait` | 60 | 30 для быстрого освобождения «зависших» соединений |
| `nf_conntrack_udp_timeout` | 30 | Оставить по умолчанию |
| `nf_conntrack_udp_timeout_stream` | 180 | 60–120 для стриминговых сервисов (VoIP, видео) |
| `nf_conntrack_icmp_timeout` | 30 | Оставить по умолчанию |
| `nf_conntrack_generic_timeout` | 600 | 120 для протоколов без известных таймаутов |

**Связь таймаутов с портовым пространством:** TCP TIME_WAIT (состояние после закрытия соединения) удерживает порт занятым до истечения таймаута. Снижение `tcp_timeout_time_wait` позволяет быстрее переиспользовать порты, что критично при Port Exhaustion на NAT-шлюзах.

#### Архитектура таблицы Conntrack

Запись в таблице conntrack содержит несколько уровней информации:

```
# Пример записи из /proc/net/nf_conntrack:
ipv4     2 tcp      6 300 TIME_WAIT src=10.0.0.5 dst=8.8.8.8 sport=54321 dport=443
         src=8.8.8.8 dst=203.0.113.1 sport=443 dport=33456 [ASSURED] mark=0 use=2
```

*   **Первая строка:** Протокол (IPv4), версия, протокол L4 (tcp), номер протокола L4 (6), таймаут, текущее состояние.
*   **Строка «orig» (оригинал):** src/dst — исходный адрес назначения (внутренний хост → внешний сервер).
*   **Строка «reply» (ответ):** src/dst — ответный путь (внешний сервер → NAT-шлюз). Именно здесь хранятся транслированные адреса.
*   **[ASSURED]:** Соединение полностью установлено (получен ответ от remote). Записи без ASSURED удаляются при переполнении таблицы быстрее.

Поля NAT-расширений (не видны в `/proc/net/nf_conntrack` без `conntrack -L`) добавляются модулем NAT и содержат транслированные адреса/порты.

#### Conntrack Zones (зоны соединений)

Conntrack zones позволяют изолировать записи соединений для разных виртуальных сетей или VRF. Записи в разных зонах не конфликтуют друг с другом, даже если IP-адреса и порты совпадают.

**Зачем нужно:** На мульти-TENANT шлюзах, где несколько виртуальных сетей используют одинаковую адресацию (например, `192.168.0.0/16` в разных VRF), conntrack без зон не может различить соединения из разных сетей.

```
VRF-A (192.168.1.0/24) ──► Conntrack Zone 1 ──► NAT-шлюз
VRF-B (192.168.1.0/24) ──► Conntrack Zone 2 ──► NAT-шлюз
                              ↑
                    Записи в разных зонах
                    не конфликтуют
```

**Настройка:**
```bash
# Nftables: назначение зоны для конкретного интерфейса
nft add rule ip nat prerouting iifname "eth0.100" ct zone set 1
nft add rule ip nat prerouting iifname "eth0.200" ct zone set 2

# Просмотр записей по зоне
conntrack -L --zone 1
conntrack -L --zone 2
```

## Виды и механизмы трансляции

### Основные типы (классификация Netfilter)

*   **SNAT (Source NAT):** Изменение адреса источника. Используется для выхода из локальной сети. Применяется, когда у маршрутизатора есть статический публичный IP.
*   **Masquerading (Маскарадинг):** Динамический вариант SNAT. Автоматически использует IP-адрес внешнего интерфейса. Применяется при использовании DHCP или PPPoE. Имеет чуть большие накладные расходы, чем статический SNAT, так как проверяет адрес интерфейса для каждого нового соединения.
*   **DNAT (Destination NAT):** Изменение адреса назначения. Используется для публикации внутренних сервисов (Port Forwarding).

### Реализации механизмов

1.  **Static NAT (1:1):** Постоянное соответствие одного внутреннего IP одному внешнему. Не экономит адреса, используется для серверов.
2.  **Dynamic NAT:** Использование пула публичных адресов. Внутренний хост получает временный адрес из пула на время сессии.
3.  **PAT (Port Address Translation / NAT Overload):** Самый распространенный вид. Множество хостов транслируются в один IP, а уникальность обеспечивается подменой номеров портов TCP/UDP.

**Принцип работы PAT:**
1. Хост `10.0.0.5:54321` отправляет пакет на `8.8.8.8:443`.
2. Маршрутизатор заменяет `10.0.0.5` на свой публичный `203.0.113.1`, а порт `54321` на свободный порт `33456`.
3. В таблице conntrack создается запись: `10.0.0.5:54321 <-> 203.0.113.1:33456`.
4. Ответ от `8.8.8.8` приходит на порт `33456`, роутер делает обратную подмену и доставляет пакет хосту.

### Трансформация пакета при прохождении через NAT

NAT модифицирует заголовки пакетов на нескольких уровнях. Понимание этого процесса критично для диагностики проблем и настройки файрволов.

#### Что именно изменяется NAT:

| Уровень | Поле | Что происходит | Зачем |
| :--- | :--- | :--- | :--- |
| **IPv4 (L3)** | Source IP (SNAT) | Замена адреса источника на адрес NAT-шлюза | Маскировка внутренней сети |
| **IPv4 (L3)** | Destination IP (DNAT) | Замена адреса назначения на внутренний IP | Проброс портов, публикация сервисов |
| **IPv4 (L3)** | Header Checksum | Пересчёт контрольной суммы IP-заголовка | Изменённые поля делают старую контрольную сумму невалидной |
| **TCP/UDP (L4)** | Source/Dest Port (PAT) | Замена номера порта | Уникальная идентификация сессий при общем IP |
| **TCP/UDP (L4)** | TCP/UDP Checksum | Пересчёт контрольной суммы транспортного уровня | Псевдозаголовок (pseudo-header) включает IP-адреса, которые были изменены |

**Важно для понимания:**
*   NAT **не модифицирует** payload (тело пакета). Если приложение встраивает IP-адреса в payload (как это делают FTP, SIP, H.323), NAT-шлюз об этом «не знает» — отсюда необходимость ALG (Application Layer Gateway).
*   NAT **не работает** с протоколами, не имеющими портов TCP/UDP (например, ICMP — определяется типом/кодом; GRE — IP-протокол 47). Для ICMP NAT использует «виртуальные порты» (ID пакета), что работает не всегда корректно.
*   При SNAT на ответных пакетах NAT выполняет обратную операцию: подменяет Destination IP на внутренний адрес клиента и Destination Port на исходный порт клиента. Обратная трансляция происходит автоматически благодаря записи conntrack.

#### Влияние NAT на контрольные суммы TCP

Контрольная сумма TCP рассчитывается по [псевдозаголовку](../../Protocols/TCP/reliability_mechanisms/checksum.md), который включает IP-адреса источника и назначения. При изменении адресов NAT-шлюз **обязан** пересчитать TCP checksum. Это добавляет накладные расходы на обработку каждого пакета. В аппаратных NAT-устройствах (прogramмируемые логические матрицы) это делается линейно, но в программных реализациях (Linux Netfilter) является частью пути обработки пакета (softirq).

### Взаимодействие NAT с протоколами

#### ICMP

ICMP не имеет портов TCP/UDP, но NAT должен как-то сопоставлять запросы и ответы. Механизм зависит от типа ICMP-сообщения:

*   **Echo Request/Reply (ping, type 8/0):** NAT использует **Identifier (ID)** ICMP-заголовка как «виртуальный порт». При SNAT ID заменяется на уникальное значение, и в таблице conntrack создается запись. Ответный пакет матчится по этому ID.
*   **Destination Unreachable (type 3), Time Exceeded (type 11):** Эти сообщения содержат оригинальный IP-заголовок и первые 8 байт транспортного заголовка payload. NAT должен выполнить обратную трансляцию адресов внутри ICMP-payload, чтобы получатель (клиент) правильно идентифицировал вызвавшее проблему соединение. Это называется **NAT-Embedded-IP-Translation** и реализуется не во всех NAT-устройствах корректно.
*   **Проблемы:** Агрессивные файрволы могут блокировать ICMP-трансляции, что приводит к проблемам с Path MTU Discovery. При настройке NAT необходимо убедиться, что ICMP-типы 3 (Destination Unreachable) и 11 (Time Exceeded) проходят через NAT без искажений.

#### DNS

DNS-запросы (обычно UDP/53, реже TCP/53) проходят через NAT аналогично любому другому UDP-трафику. Однако есть нюанс:

*   **Split-Horizon DNS:** В корпоративных сетях внутренние DNS-серверы отвечают на запросы к внутренним доменам одним IP, а на запросы снаружи — другим. Если внутренний клиент за NAT обращается к внутреннему DNS-серверу по публичному IP домена (используя «внешний» DNS), DNAT должен перенаправить запрос на внутренний DNS-сервер. Некоторые DNS-серверы (например,BIND) поддерживают `split-dns` для корректной работы в таких сценариях.

#### FTP (Active и Passive режимы)

FTP-протокол передаёт IP-адреса и порты данных внутри командного канала (L7), что делает его проблемным для NAT:

*   **Active FTP:** Клиент сообщает серверу свой IP:Port для установки data-канала через команду `PORT`. NAT-шлюз должен модифицировать эту команду (заменив внутренний IP на публичный) — это делает **ALG-модуль** в iptables/nftables (`helper=ftp`).
*   **Passive FTP:** Сервер сообщает клиенту IP:Port для пассивного подключения. Если сервер за NAT, ALG должен заменить внутренний IP сервера на публичный. Это сложнее, так как ALG должен знать публичный IP NAT-шлюза.
*   **Рекомендация:** Использовать `nf_conntrack_ftp` модуль с корректно настроенным ALG. В nftables: `ct helper set "ftp"` для конкретного правила.

#### SIP (Session Initiation Protocol)

SIP использует SDP (Session Description Protocol) для описания медиа-сессий, встраивая IP-адреса и порты RTP/RTCP внутри тела сообщения (L7). NAT без ALG «не видит» эти адреса, что приводит к одностороннему аудио/видео или полной потере медиа-потока.

*   **ALG для SIP:** В большинстве маршрутизаторов SIP ALG включен по умолчанию. Однако он часто работает некорректно (особенно с SIP-сигнализацией через TLS, с нестандартными заголовками), что приводит к проблемам с VoIP. Рекомендация SRE-сообщества — **отключать SIP ALG** на файрволах и использовать серверную трансляцию (Session Border Controller / [SBC](../../../Networking/Concepts/session_border_controller.md)) или STUN/TURN на стороне клиентов.
*   **Проблема с обратным SIP:** Если SIP-сервер (Asterisk, FreeSWITCH) находится за NAT, входящие вызовы не смогут достучаться до него без явно настроенного DNAT или ICE/STUN.

#### Другие протоколы с проблемами NAT

| Протокол | Проблема | Решение |
| :--- | :--- | :--- |
| **SCTP** | Многопоточный (multi-homed), NAT должен отслеживать все потоки | Поддержка SCTP в Netfilter (nf_conntrack_sctp) |
| **GRE (IP 47)** | Нет портов — PAT не может различать туннели | Only один туннель через NAT; или инкапсуляция GRE в UDP (FOU) |
| **ESP (IP 50)** | Нет портов | NAT-Traversal (NAT-T): инкапсуляция ESP в UDP/4500 в IPsec |
| **WireGuard** | Использует UDP — проходит через NAT корректно | Нохождение через двойной NAT может вызвать задержки handshake |

## Классификация NAT по поведению (NAT Taxonomy)

Для P2P-приложений (VoIP, WebRTC, игры) критично, как NAT фильтрует входящие пакеты и как назначает порты:

| Тип | Описание | P2P-совместимость |
| :--- | :--- | :--- |
| **Full Cone** | Любой внешний хост может отправить пакет на открытый порт маппинга. | Отличная |
| **Restricted Cone** | Внешний хост может ответить, только если внутренний хост ранее отправлял ему пакет. | Хорошая |
| **Port Restricted** | Ограничение не только по IP, но и по порту внешнего хоста. | Средняя |
| **Symmetric NAT** | Для каждого нового адреса назначения создается новый маппинг порта. | Плохая (требует Relay) |

## Технологии интеграции с IPv6

В современной практике NAT используется для взаимодействия между IPv4 и IPv6:

*   **NAT64 / DNS64:** Позволяет IPv6-only узлам обращаться к IPv4-ресурсам. DNS64 синтезирует AAAA-записи, используя Well-Known Prefix `64:ff9b::/96`. NAT64 транслирует трафик.
*   **NPTv6 (Network Prefix Translation):** Безсостоятельная (stateless) трансляция префиксов IPv6. Сохраняет checksum-нейтральность и используется для мультикастинга. Описана в **RFC 6296**.
*   **NAT444:** Используется в сетях операторов связи (CGNAT), где трафик проходит через три уровня NAT.

## Механизмы преодоления NAT (NAT Traversal)

Для установления прямого соединения между хостами за NAT используются:

*   **STUN (Session Traversal Utilities for NAT):** Позволяет хосту узнать свой публичный IP и тип NAT.
*   **TURN (Traversal Using Relays around NAT):** Передача трафика через промежуточный сервер (Relay). Используется, когда прямое соединение невозможно (например, Symmetric NAT).
*   **ICE (Interactive Connectivity Establishment):** Фреймворк, выбирающий оптимальный путь (сначала STUN, затем TURN).
*   **ALG (Application Layer Gateway):** Модули в маршрутизаторах, которые анализируют полезную нагрузку протоколов (FTP, SIP, H.323) и на лету подменяют IP-адреса внутри пакетов. Часто вызывает проблемы с VoIP, поэтому SRE часто рекомендуют отключать SIP ALG.
*   **UDP Encapsulation:** Используется для прохождения протоколов без портов (например, IPsec ESP) через NAT (порт 4500).

## Hairpin NAT (петлевой NAT)

**Проблема:** Внутренний клиент пытается обратиться к внутреннему серверу по его **публичному** IP. Пакет доходит до роутера, транслируется (DNAT) на сервер, но сервер отвечает клиенту напрямую по LAN. Клиент отбрасывает пакет, так как ждал ответа от публичного IP, а получил от локального.

**Решение:** Hairpin NAT заставляет роутер выполнять SNAT для клиента, чтобы ответ сервера также прошел через роутер и подвергся обратной трансляции.

## Сложные сценарии и ограничения

### Двойной NAT (Double NAT)
Цепочка из двух NAT (например, роутер провайдера + домашний роутер).
*   **Проблемы:** Трудности с пробросом портов, увеличенная задержка, проблемы с IPsec VPN.

#### Carrier-Grade NAT (CGNAT)

Провайдерский NAT (**RFC 6598**, диапазон `100.64.0.0/10`) используется провайдерами для разделения одного публичного IP-адреса между тысячами абонентов. Это фактический стандарт для мобильных операторов и многих DSL/FTTH-провайдеров.

**Архитектура NAT444 (тройной NAT):**
1.  Домашний роутер выполняет SNAT (RFC 1918 → RFC 1918).
2.  CGNAT-шлюз провайдера выполняет SNAT (RFC 1918 → публичный IP).
3.  Некоторые крупные провайдеры используют третий уровень NAT (NAS/BRAS), создавая тройную трансляцию.

**Портовое пространство и Port Exhaustion:**

Один публичный IP-адрес CGNAT-шлюза может обслуживать ограниченное количество соединений из-за 16-битного поля порта (максимум 65535). Однако не все порты доступны:

| Параметр | Значение | Пояснение |
| :--- | :--- | :--- |
| Диапазон портов TCP | 1024–65535 | Порты 0–1023 — привилегированные, редко используются в PAT |
| Диапазон портов UDP | 1024–65535 | Аналогично |
| Доступно на один IP (TCP) | ~64511 | Порты, которые можно назначить одному абоненту |
| Рекомендуемый лимит на абонента | 2000–4000 портов | RFC 6269 рекомендует не превышать 2048 портов на пользователя |
| Агрессивный лимит | 256–512 портов | Для экономии IP; приводит к проблемам при P2P/игр VoIP |

**Проблемы CGNAT для абонентов:**
*   **Невозможность проброса портов:** Абонент не может публиковать сервисы (игровые серверы, веб-серверы) без двойного DNAT, что технически невозможно без сотрудничества провайдера.
*   **Проблемы с VoIP и P2P:** Многоуровневый NAT делает NAT Traversal (STUN/TURN) значительно менее эффективным. Некоторые SIP-клиенты не могут установить медиа-соединение.
*   **Проблемы с TCP-соединениями:** При большом количестве одновременных HTTP-соединений (современные браузеры開啟ают 6+ соединений на один домен) абонент может исчерпать доступные порты. Симптомы: таймауты при загрузке страниц, обрывы WebSocket.
*   **Идентификация абонента:** Провайдер может отслеживать абонента только по комбинации source IP + source port + timestamp (для динамического NAT).

**Диагностика CGNAT:**
```bash
# Сравнение внешнего IP с адресом интерфейса
ip addr show | grep "inet " | grep -v 127.0.0.1
curl ifconfig.me
# Если адреса отличаются — вы за NAT (возможно, за CGNAT)

# Признаки CGNAT: несколько приватных IP в traceroute
traceroute -n 8.8.8.8
# 1. 192.168.1.1  (домашний роутер)
# 2. 10.0.0.1     (CGNAT провайдера)  <-- Тройной NAT
# 3. 172.16.0.1   (ещё один уровень NAT)
# 4. * * *        (публичная сеть)
```

### NAT и фрагментация IP
NAT-устройства плохо справляются с фрагментированными пакетами, так как информация о портах L4 есть только в первом фрагменте. Это требует сборки пакетов на роутере (что ресурсозатратно) или корректной настройки [PMTUD](../../OSI_TCP_IP_Model/Network_layer/mtu_and_vpn.md#path-mtu-discovery-pmtud).

## NAT в контейнерах и оркестраторах

### Docker

В Docker-инфраструктуре NAT используется повсеместно для обеспечения связи контейнеров с внешним миром:

*   **Bridge-сеть (по умолчанию):** Docker-хост выполняет DNAT для публикованных портов (`-p 8080:80`) и SNAT (MASQUERADE) для исходящего трафика контейнеров. Детальный разбор пути пакета — в разделе [Packet Flow в Docker Bridge](../../../Docker/Docker_network/drivers/bridge.md#жизненный-цикл-пакета-packet-flow).
*   **Проблема conntrack в Docker:** При большом количестве контейнеров и соединений таблица conntrack на хосте может переполняться. Типичное решение — увеличение `nf_conntrack_max` и снижение таймаутов (详见 [Docker: Performance Tuning](../../../Docker/Docker_performance_tuning.md)).
*   **userland-proxy vs kernel NAT:** Docker может использовать пользовательский прокси (`userland-proxy`) для публикации портов, что обходит conntrack, но добавляет накладные расходы. Ядерный NAT (`--userland-proxy=false`) быстрее, но требует корректной настройки conntrack.

### Kubernetes

В Kubernetes NAT выполняется компонентом `kube-proxy` и зависит от выбранного режима:

| Режим | Механизм NAT | Особенности |
| :--- | :--- | :--- |
| **iptables** | DNAT-правила для каждого Service (ClusterIP → Pod IP) | Простая настройка, но O(n) сложность правил; при 10k+ сервисов — рост задержки |
| **IPVS** | DNAT через IPVS-модуль ядра (L4-балансировка) | Масштабируемость O(1), поддержка алгоритмов RR/WLC/LC |
| **nftables** | DNAT через nftables (начиная с K8s 1.29+) | Замена iptables, улучшенная производительность |
| **eBPF (Cilium)** | DNAT на уровне eBPF-программ (минуя Netfilter) | Максимальная производительность, полная видимость трафика |

**NAT-проблемы в Kubernetes:**
*   **Source IP Preservation:** При `externalTrafficPolicy: Cluster` (по умолчанию) пакет проходит через SNAT (masquerade), и реальный IP клиента теряется. Для сохранения source IP используйте `externalTrafficPolicy: Local` (но это ограничивает балансировку только локальными подами на узле).
*   **Conntrack и IPVS:** При использовании IPVS conntrack-модуль Netfilter всё равно активен для отслеживания состояний. Однако IPVS может конфликтовать с conntrack при определённых сценариях (асимметричная маршрутизация, `MasqueradeAll`).
*   **ip-masq-agent:** В кластерах с кастомными CNI (Flannel, Calico) агент `ip-masq-agent` управляет правилами masquerade для исходящего трафика подов. Конфигурация через ConfigMap определяет, какие CIDR не маскируются (например, внутренние подсети кластера).

### NAT в сетях подов (Pod-to-World)

Трафик из пода наружу проходит через несколько уровней трансляции:
1.  **Pod IP (containernetXX) → Node IP:** Выполняется CNI-плагином (Flannel VXLAN, Calico BGP). В режиме `Masquerade` (Flannel по умолчанию) Pod IP заменяется на IP узла.
2.  **Node IP → NAT Gateway / Internet:** Выполняется облачным NAT Gateway или настроенным на узле masquerade.
3.  **Ответный трафик:** Проходит обратные DNAT/SNAT трансляции для возврата пакета в под.

При маршрутизации трафика через внешний файрвол (NGFW, Cloud NGFW) проблема маскировки Pod IP (пункт 1) делает невозможной корректную фильтрацию. Решение — использование `externalTrafficPolicy: Local` или [Calico HostEndpoint с preDNAT](../../../Kubernetes/Security/network_policies/Calico/index.md).

## Рекомендации для SRE

### Мониторинг и алертинг

1.  **Размер conntrack-таблицы:** Отслеживать `nf_conntrack_count / nf_conntrack_max`. Алерт при достижении 80% заполнения.
    ```bash
    # Мониторинг в Prometheus (через node_exporter textfile collector):
    # nf_conntrack_count и nf_conntrack_max доступны как metircs
    # Алерт-правило:
    # ALERT ConntrackTableAlmostFull
    #   IF node_nf_conntrack_entries / node_nf_conntrack_entries_limit > 0.8
    #   FOR 5m
    ```
2.  **Port Exhaustion:** На NAT-шлюзах (особенно для Kubernetes egress) мониторить количество соединений на целевой IP:PORT.
    ```bash
    # Проверка количества исходящих соединений на целевой IP
    ss -s | grep estab
    cat /proc/net/nf_conntrack | grep "dst=8.8.8.8" | wc -l
    # Лимит: 65535 на одну пару srcIP:dstIP (PAT)
    ```
3.  **Дропнутые пакеты conntrack:**
    ```bash
    # Проверка количества отброшенных из-за переполнения conntrack
    conntrack -S | grep insert_failed
    # → insert_failed 12345 (если > 0 — таблица переполнялась)
    ```

### Настройка Conntrack для высоконагруженных систем

Рекомендуемая конфигурация для NAT-шлюзов и серверов с высоким числом соединений:

```ini
# /etc/sysctl.d/99-conntrack-tuning.conf

# Максимальный размер таблицы conntrack
# Зависит от доступной RAM: каждая запись ~300 байт
# 1M записей ~ 300MB RAM
net.netfilter.nf_conntrack_max = 1048576

# Размер хеш-таблицы (рекомендуется nf_conntrack_max / 4)
# Влияет на скорость поиска записей
net.netfilter.nf_conntrack_buckets = 262144

# Таймауты TCP (в секундах)
net.netfilter.nf_conntrack_tcp_timeout_established = 7200
net.netfilter.nf_conntrack_tcp_timeout_time_wait = 60
net.netfilter.nf_conntrack_tcp_timeout_close_wait = 30
net.netfilter.nf_conntrack_tcp_timeout_fin_wait = 60

# Таймауты UDP
net.netfilter.nf_conntrack_udp_timeout = 30
net.netfilter.nf_conntrack_udp_timeout_stream = 120
```

После применения:
```bash
sudo sysctl --system
# Проверка:
sysctl net.netfilter.nf_conntrack_max
cat /sys/module/nf_conntrack/parameters/hashsize
```

### Port Exhaustion: сценарии и решения

| Сценарий | Симптомы | Решение |
| :--- | :--- | :--- |
| **NAT-шлюз для Kubernetes egress** | Таймауты при обращении к внешним API; `TIME_WAIT`大量 | SNAT к нескольким внешним IP (multi-NAT); снижение `tcp_timeout_time_wait` |
| **CGNAT-пользователь** | Обрывы WebSocket, таймауты HTTP/2 | Обратиться к провайдеру; использовать IPv6; VPN для обхода CGNAT |
| **Высоконагруженный прокси (nginx/haproxy)** | `Cannot assign requested address` на исходящих соединениях | `net.ipv4.ip_local_port_range = 1024 65535`; `tcp_tw_reuse = 1` |
| **VPN-шлюз (IPsec/OpenVPN)** | Падение туннелей при большом числе клиентов | Мульти-NAT (пул внешних IP);`nf_conntrack_max` > 500k |

### Безопасность

5.  **NAT — это не средство защиты.** Он не заменяет Stateful Firewall (`nftables`, `iptables` в таблице `filter`, `firewalld`). NAT не проверяет содержимое пакетов и не защищает от атак на уровне приложения.
6.  **Блокировка ICMP:** Часто блокируют ICMP «для безопасности», но это приводит к проблемам с Path MTU Discovery и, как следствие, кuyenchenю пакетов и таймаутам. Рекомендуется разрешать ICMP-типы 3 (Destination Unreachable) и 11 (Time Exceeded) через NAT.
7.  **SIP ALG:** На большинстве современных файрволов SIP ALG включен по умолчанию и работает некорректно с TLS-шифрованным SIP. Рекомендация — отключить SIP ALG и использовать STUN/TURN или SBC.

### Диагностика NAT-проблем

8.  **Быстрая проверка:**
    ```bash
    # Определение типа NAT (важно для VoIP/WebRTC)
    stun stun.l.google.com:19302

    # Просмотр активных NAT-трансляций для конкретного хоста
    conntrack -L -s 192.168.1.10

    # Проверка, какие правила NAT активны
    iptables -t nat -L -v -n
    nft list ruleset | grep -A5 "nat"
    ```

9.  **Асимметричная маршрутизация и NAT:**
    Если трафик наружу идёт через один NAT-шлюз, а ответ возвращается через другой, conntrack-запись не будет найдена для ответного пакета. Результат — пакеты отбрасываются или транслируются некорректно. Решение — обеспечить симметричную маршрутизацию или использовать `stateless` NAT (только в простых сценариях).

10.  **Облачные NAT-шлюзы:** В AWS, GCP и Yandex Cloud рекомендуется использовать управляемые NAT Gateway. Они масштабируются автоматически и избавляют от необходимости администрировать `conntrack` на уровне ОС. Сравнение облачных NAT-шлюзов:
    *   **AWS NAT Gateway:** Автоматическое масштабирование, интеграция с VPC Flow Logs, CloudWatch метрики.
    *   **Yandex Cloud NAT Gateway:** Управляемый сервис, интеграция с Security Groups, статические публичные IP.
    *   **GCP Cloud NAT:** Автоматическое назначение внешних IP, поддержка Cloud Router для динамической маршрутизации.
