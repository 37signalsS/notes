# Качество трафика реального времени: 4 ключевых параметра

## Определения

**Трафик реального времени (Real-time traffic)** — это сетевой трафик, чувствительный к задержкам, их вариациям (джиттеру) и потерям. Для таких данных своевременность доставки критичнее, чем стопроцентная целостность (в отличие от передачи файлов, где важен каждый бит, но время доставки может варьироваться).

К основным типам приложений реального времени относятся:
*   **Онлайн-игры:** Шутеры (Counter-Strike 2, Valorant, Overwatch 2), MOBA (Dota 2, League of Legends), файтинги.
*   **Интерактивные коммуникации:** Видеозвонки (Zoom, Microsoft Teams, Skype) и IP-телефония (VoIP — Voice over Internet Protocol).
*   **Стриминг живого контента:** Трансляции с минимальной задержкой (Twitch, YouTube Live), облачный гейминг (GeForce Now).
*   **Удаленное управление:** RDP (Remote Desktop Protocol — протокол удалённого рабочего стола), VNC (Virtual Network Computing — виртуальные сетевые вычисления), управление промышленными роботами и дронами.

Для оценки качества такого трафика используются **четыре ключевых параметра**: **Latency**, **Bandwidth**, **Jitter** и **Loss**.

## Базовые концепции

### 1. Latency (Задержка)

**Latency (Задержка)** — это интервал времени между отправкой пакета данных и его получением.

**Компоненты задержки:**
1.  **Задержка распространения (Propagation Delay):** Время прохождения сигнала через физическую среду. Зависит от расстояния и скорости света в среде (в оптоволокне ~200 000 км/с).
2.  **Задержка передачи (Transmission Delay):** Время, необходимое для «выталкивания» всех бит пакета в канал. Зависит от пропускной способности.
3.  **Задержка в очереди (Queuing Delay):** Ожидание пакета в буферах маршрутизаторов при перегрузке (Congestion).
4.  **Задержка обработки (Processing Delay):** Время на анализ заголовков и поиск маршрута в таблице.

**RTT (Round-Trip Time — время кругового обхода):** Время, необходимое для прохождения пакета от отправителя к получателю и обратно. Именно RTT чаще всего измеряется утилитой `ping`.

**Нормальные значения RTT:**
*   **Локальная сеть (LAN):** <1 мс (идеально), <5 мс (норма).
*   **В пределах города:** 5–20 мс.
*   **Между городами (региональные):** 20–50 мс.
*   **Между странами/континентами:** 50–150 мс.
*   **Спутниковая связь (Starlink):** 25–50 мс.
*   **Спутниковая связь (Геостационарная):** 600–800 мс (непригодно для интерактивности).

**Влияние на комфорт:**

| Приложение | Макс. комфортная задержка (RTT) |
| :--- | :--- |
| **Шутеры (FPS)** | <50 мс (киберспорт — <20 мс) |
| **MOBA / MMO** | <100 мс |
| **VoIP (Голос)** | <150 мс |
| **Видеозвонки** | <200 мс |
| **Облачный гейминг** | <30–40 мс |

### 2. Bandwidth (Пропускная способность)

**Bandwidth (Пропускная способность)** — количество данных, которое канал способен передать за единицу времени.

**Характеристики:**
*   **Измерение:** Биты в секунду (бит/с, Kbps, Mbps, Gbps).
*   **Важное уточнение:** Увеличение пропускной способности **не уменьшает** задержку, если канал не перегружен. Канал становится «толще», но не «быстрее».

**Типичные требования к полосе:**

| Приложение | Мин. пропускная способность |
| :--- | :--- |
| **VoIP (один звонок)** | 64–128 Кбит/с |
| **Видеозвонок (720p)** | 1.5–2.5 Мбит/с |
| **Видеозвонок (HD 1080p)** | 3–5 Мбит/с |
| **Облачный гейминг (4K)** | 35–50 Мбит/с |
| **Онлайн-игры** | 0.5–2 Мбит/с (но важна стабильность) |

### 3. Jitter (Джиттер)

**Jitter (Джиттер)** — это статистическая вариация (колебание) задержки между доставкой последовательных пакетов.

**Визуализация:**
```text
Идеальный канал (Jitter = 0):
Пакет 1 → [20мс] → Получатель
Пакет 2 → [20мс] → Получатель
Пакет 3 → [20мс] → Получатель

Канал с высоким Jitter:
Пакет 1 → [10мс] → Получатель
Пакет 2 → [150мс] → Получатель (задержка!)
Пакет 3 → [15мс] → Получатель (пришел почти сразу после 2)
```

**Последствия:**
*   **Голос:** Прерывания, «роботизированный» звук.
*   **Игры:** «Рывки» (stuttering), телепортация объектов.
*   **Метод борьбы:** **Jitter Buffer** — буфер на стороне получателя, который накапливает пакеты и выдает их приложению с равномерным интервалом. Это сглаживает рывки, но увеличивает общую задержку.

### 4. Loss (Потеря пакетов)

**Loss (Потеря пакетов)** — процент пакетов, которые были отправлены, но не дошли до адресата.

**Симптомы превышения нормы:**

| Приложение | Допустимые потери | Последствия |
| :--- | :--- | :--- |
| **VoIP** | <1% | Пропуски в аудио, щелчки, выпадение слов. |
| **Видеозвонки** | <2% | Зависания картинки, «рассыпание» на квадраты. |
| **Онлайн-игры** | <0.5% | Пакет-лосс: действия игрока не регистрируются. |
| **Веб-сёрфинг** | <5% | Замедление из-за ретрансмиссий TCP. |

**Причины потерь:**
*   **Перегрузка (Congestion):** Буферы на маршрутизаторах переполнены, пакеты отбрасываются (**Tail Drop**).
*   **Помехи:** В Wi-Fi или мобильных сетях пакеты могут быть повреждены.
*   **Bufferbloat (Раздувание буфера):** Избыточная буферизация в дешевых роутерах, создающая огромные очереди и джиттер при нагрузке.

## Практические сценарии

### Диагностика проблем реального времени

**Сценарий 1: Лаги в играх при низком пинге**
*   **Симптомы:** Пинг 15 мс, но персонаж двигается рывками.
*   **Диагноз:** Высокий **Jitter**.
*   **Решение:** Перейти с Wi-Fi на провод (Ethernet), проверить нагрузку на роутер другими устройствами, настроить **QoS (Quality of Service)** для приоритезации игрового трафика.

**Сценарий 2: «Роботизированный» голос в Zoom/Teams**
*   **Симптомы:** Голос слышен кусками, металлический призвук.
*   **Диагноз:** Комбинация высокого **Jitter** и **Packet Loss**.
*   **Решение:** Проверить уровень сигнала Wi-Fi, сменить канал (2.4 ГГц → 5 ГГц), отключить фоновые загрузки (торренты, обновления).

**Сценарий 3: Задержка ввода в облачном гейминге**
*   **Симптомы:** Картинка красивая, но между нажатием кнопки и действием на экране проходит полсекунды.
*   **Диагноз:** Высокая **Latency** (часто из-за удаленности сервера или плохой маршрутизации провайдера).
*   **Решение:** Выбрать ближайший сервер, проверить наличие VPN (он может добавлять задержку), использовать протоколы с поддержкой **0-RTT** или **QUIC**.

## Инструменты диагностики

| Инструмент | Что измеряет | Прикладная команда |
| :--- | :--- | :--- |
| **ping** | Latency, Loss, Jitter (mdev) | `ping -c 100 8.8.8.8` |
| **mtr** | Потери и задержки по хопам | `mtr -v google.com` |
| **iperf3** | Throughput, Jitter (UDP) | `iperf3 -u -c <ip> -b 5M` |
| **gping** | Визуальный график задержки | `gping 1.1.1.1` |
| **Wireshark** | Глубокий анализ RTP/UDP потоков | `wireshark` |

**Интерпретация `ping`:**
```bash
$ ping -c 10 8.8.8.8
rtt min/avg/max/mdev = 18.234/20.567/25.891/2.345 ms
```
*   **avg:** Средний пинг (базовая задержка).
*   **mdev:** Среднеквадратичное отклонение. **Это ваш джиттер.** Если `mdev` составляет более 15–20% от `avg`, в real-time приложениях будут заметны проблемы.

## Современные технологии улучшения качества

*   **HTTP/3 (QUIC):** Устраняет блокировку начала очереди (HOL Blocking). Потеря одного пакета в одном потоке данных не тормозит остальные потоки.
*   **WebRTC:** Использует UDP и встроенные механизмы **FEC (Forward Error Correction — упреждающая коррекция ошибок)**, позволяющие восстанавливать потерянные пакеты без повторного запроса.
*   **Алгоритмы AQM (Active Queue Management):** Такие как **CoDel (Controlled Delay)** и **FQ-CoDel** в ядре Linux, борются с Bufferbloat, принудительно очищая очереди до того, как они станут слишком длинными.
