# Качество трафика реального времени: 4 ключевых параметра

## Определения

**Трафик реального времени (Real-time traffic)** — это сетевой трафик, чувствительный к задержкам, их вариациям (джиттеру) и потерям. Для таких данных своевременность доставки критичнее, чем стопроцентная целостность (в отличие от передачи файлов, где важен каждый бит, но время доставки может варьироваться).

**Задержка в одну сторону (One-Way Delay, OWD)** — интервал времени между отправкой пакета и его получением на удаленном узле. В отличие от RTT, измеряется только «туда». Для точного измерения требуется синхронизация часов между узлами (NTP, PTP, GPS).

**RTP (Real-time Transport Protocol)** — транспортный протокол прикладного уровня (L5/L7), определенный в **RFC 3550**, предназначенный для доставки аудио и видео в реальном времени. Работает поверх UDP. Обеспечивает последовательность пакетов, временные метки и идентификаторы источников.

**RTCP (RTP Control Protocol)** — вспомогательный протокол к RTP (также RFC 3550), используемый для передачи служебной информации: статистики потерь, джиттера, задержки, идентификаторов участников сессии.

**MOS (Mean Opinion Score — средний балл субъективного восприятия)** — интегральная метрика качества, полученная путем усреднения оценок слушателей по 5-балльной шкале (1 — плохо, 5 — отлично). Используется для оценки голосовых и видеокодеков.

**Goodput (Полезная пропускная способность)** — реальный объем полезных данных, доставленных приложению за секунду. Отличается от Bandwidth тем, что исключает заголовки протоколов, повторные передачи (retransmits) и отброшенные пакеты.

К основным типам приложений реального времени относятся:
*   **Онлайн-игры:** Шутеры (Counter-Strike 2, Valorant, Overwatch 2), MOBA (Dota 2, League of Legends), файтинги.
*   **Интерактивные коммуникации:** Видеозвонки (Zoom, Microsoft Teams, Skype) и IP-телефония (VoIP).
*   **Стриминг живого контента:** Трансляции с минимальной задержкой (Twitch, YouTube Live), облачный гейминг (GeForce Now, Xbox Cloud).
*   **Удаленное управление:** RDP (Remote Desktop), VNC, управление промышленными роботами, дронами и БПЛА.

Для оценки качества такого трафика используются **четыре ключевых параметра**: **Latency**, **Bandwidth**, **Jitter** и **Loss**.

## Базовые концепции

### 1. Latency (Задержка)

**Latency (Задержка)** — это интервал времени между отправкой пакета данных и его получением. Измеряется в миллисекундах (мс). При diagnosing real-time приложений различают:
*   **One-Way Delay (OWD):** задержка «туда».
*   **RTT (Round-Trip Time):** время «туда и обратно». Именно RTT чаще всего измеряется утилитой `ping`.

**Компоненты задержки:**

1.  **Задержка распространения (Propagation Delay):** Время прохождения сигнала через физическую среду. Зависит от расстояния и скорости света в среде (в оптоволокне ~200 000 км/с). Добавляет ~5 мс на каждые 1000 км.
2.  **Задержка передачи (Transmission Delay):** Время, необходимое для «выталкивания» всех бит пакета в канал. Зависит от пропускной способности (Bandwidth) и размера пакета.
3.  **Задержка в очереди (Queuing Delay):** Ожидание пакета в буферах маршрутизаторов при перегрузке (Congestion). Основный источник нестабильности.
4.  **Задержка обработки (Processing Delay):** Время на анализ заголовков, проверку контрольных сумм, поиск маршрута и выполнение правил файрвола.

**BDP (Bandwidth-Delay Product):** произведение пропускной способности канала на задержку. Определяет объем данных, который может «находиться в полете» в сети. Для высокоскоростных каналов с большой задержкой (например, 10 Гбит/с × 100 мс = 1 Гбит) требуется увеличенный размер буферов (RWND/CWND), иначе канал не будет загружен полностью.

**Типичные значения RTT (Актуально на 2026):**
*   **Локальная сеть (LAN):** <1 мс (идеально), <5 мс (норма).
*   **В пределах города:** 5–20 мс.
*   **Между городами (региональные):** 20–50 мс.
*   **Между странами/континентами:** 50–150 мс.
*   **Спутниковая связь (Starlink Gen 3):** 20–40 мс (сравнима с наземными линиями).
*   **Спутниковая связь (Геостационарная):** 600–800 мс (непригодно для интерактивности).

**Влияние на комфорт:**

| Приложение | Макс. комфортная задержка (RTT) |
| :--- | :--- |
| **Шутеры (FPS)** | <50 мс (киберспорт — <20 мс) |
| **MOBA / MMO** | <100 мс |
| **VoIP (Голос)** | <150 мс |
| **Видеозвонки** | <200 мс |
| **Облачный гейминг** | <30–40 мс |

### 2. Bandwidth (Пропускная способность)

**Bandwidth (Пропускная способность)** — количество данных, которое канал способен передать за единицу времени.

**Характеристики:**
*   **Измерение:** Биты в секунду (бит/с, Kbps, Mbps, Gbps).
*   **Важное уточнение:** Увеличение пропускной способности **не уменьшает** задержку, если канал не перегружен. Канал становится «толще», но не «быстрее».
*   **Goodput:** реальная скорость доставки полезных данных приложению. Может значительно отличаться от Bandwidth из-за перегрузки сети, повторных передач и overheard протоколов.

**BDP и требовательность real-time приложений:**
Для некоторых приложений важно не только количество бит в секунду, но и время их доставки. Например, поток 4K при 60 FPS требует не только высокой полосы, но и стабильного времени доставки каждого кадра (GOP, I-frame interval).

**Типичные требования к полосе (2026):**

| Приложение | Мин. пропускная способность | Примечание |
| :--- | :--- | :--- |
| **VoIP (Opus/G.711)** | 64–128 Кбит/с | Важна стабильность, а не объем |
| **Видеозвонок (720p)** | 1.5–2.5 Мбит/с | H.264/H.265/AV1 |
| **Видеозвонок (HD 1080p)** | 3–5 Мбит/с | AV1/H.265, зависит от движения в кадре |
| **Облачный гейминг (4K)** | 45–60 Мбит/с | Зависит от FPS (60/120) и кодера |
| **VR / Галлограммы** | 100+ Мбит/с | Требует высокой стабильности и низкого джиттера |

**Асимметричные каналы:** В DSL/LTE/Starlink скорость загрузки (Download) и отдачи (Upload) могут отличаться в 5–10 раз. Для облачного гейминга и видеоконференций критична именно Upload-полоса.

### 3. Jitter (Джиттер)

**Jitter (Джиттер)** — это статистическая вариация (колебание) задержки между доставкой последовательных пакетов. Измеряется как среднеквадратичное отклонение (MDev — Mean Deviation) или межквартильный разброс.

**Визуализация:**
```text
Идеальный канал (Jitter = 0):
Пакет 1 → [20мс] → Получатель
Пакет 2 → [20мс] → Получатель
Пакет 3 → [20мс] → Получатель

Канал с высоким Jitter:
Пакет 1 → [10мс] → Получатель
Пакет 2 → [150мс] → Получатель (задержка!)
Пакет 3 → [15мс] → Получатель (пришел почти сразу после 2)
```

**Последствия и методы борьбы:**
*   **Симптомы:** Прерывания звука, «рывки» в играх (stuttering), телепортация объектов, «роботизированный» голос.
*   **Jitter Buffer:** Буфер на стороне получателя, который накапливает пакеты и выдает их приложению с равномерным интервалом. Сглаживает рывки, но увеличивает общую Latency. Размер буфера является компромиссом между стабильностью и задержкой.
*   **Адаптивный Jitter Buffer:** Алгоритм, который динамически корректирует размер буфера на основе текущего уровня джиттера. Используется в WebRTC, Zfone, современных IP-АТС.
*   **Wi-Fi 7 MLO (Multi-Link Operation):** Использование нескольких диапазонов одновременно для минимизации джиттера, вызванного помехами и конкуренцией за канал.

**Связь с QoS:** Высокий джиттер часто является следствием Bufferbloat (раздувания буферов) в маршрутизаторах. Алгоритмы AQM (CoDel, PIE, fq_codel) снижают вариативность задержки, отбрасывая пакеты из «застоявшихся» очередей.

### 4. Loss (Потеря пакетов)

**Loss (Потеря пакетов)** — процент пакетов, которые были отправлены, но не дошли до адресата. В UDP-трафике (RTP, DNS) потеря не исправляется автоматически.

**Симптомы превышения нормы:**

| Приложение | Допустимые потери | Последствия |
| :--- | :--- | :--- |
| **VoIP** | <1% | Пропуски в аудио, щелчки, выпадение слов. |
| **Видеозвонки** | <2% | Зависания картинки, «рассыпание» на квадраты. |
| **Онлайн-игры** | <0.5% | Пакет-лосс: действия не регистрируются, телепортация. |
| **Веб-сёрфинг** | <5% | Замедление из-за ретрансмиссий TCP. |

**Механизмы компенсации и причины:**
*   **FEC (Forward Error Correction):** Передача избыточных данных для восстановления потерянных пакетов без перезапроса. Варианты: простой XOR-паритет, ULPFEC (Uneven Level Protection — неравномерная защита для ключевых кадров), FlexFEC.
*   **PLC (Packet Loss Concealment):** Генерация синтетических данных (звука/кадра) для маскировки пропусков. В голосовых кодеках (Opus, G.711) PLC анализирует предыдущие сэмплы и экстраполирует сигнал.
*   **ARQ (Automatic Repeat reQuest):** Запрос повторной передачи потерянного пакета. Применим в TCP или на прикладном уровне (QUIC, RTX в WebRTC). Не подходит для ultra-low-latency из-за ожидания ответа.
*   **Bufferbloat:** Избыточная буферизация в роутерах, создающая огромные очереди при нагрузке, что ведет к отбрасыванию пакетов (Tail Drop).
*   **Tail Drop:** Сброс пакетов при переполнении очереди. Решается через **AQM** (CoDel, PIE, fq_codel).

## Протоколы и кодекы реального времени

### RTP и RTCP

**RTP (Real-time Transport Protocol)** — стандартный транспорт для потокового аудио и видео. Ключевые поля заголовка:
*   **Sequence Number:** порядковый номер для обнаружения потерь и восстановления последовательности.
*   **Timestamp:** временная метка, привязанная к тактовой частоте кодера (например, 48000 Гц для аудио). Позволяет приемнику выдать данные с правильным интервалом (восстановить темп).
*   **SSRC:** уникальный идентификатор источника внутри потока.

**RTCP** периодически отправляет отчеты (Receiver Report, Sender Report) с полями:
*   **Fraction Lost:** доля потерянных пакетов с момента последнего отчета.
*   **Cumulative Number of Packets Lost:** общее количество потерянных пакетов за сессию.
*   **Interarrival Jitter:** вариация времени прибытия пакетов (сравнивается с RTP timestamp).
*   **Last SR / DLSR:**用于计算 round-trip propagation delay.

### Кодекы и MOS

| Кодек | Тип | Битрейт | MOS (G.722参考) | Особенности |
| :--- | :--- | :--- | :--- | :--- |
| **G.711 (PCM/A-law)** | Аудио, без сжатия | 64 Кбит/с | ~4.1 | Нулевая нагрузка на CPU, высокий MOS, но мало гибкости. |
| **G.722** | Аудио, широкополосный | 64 Кбит/с | ~4.5 | HD-голос, широкий спектр 50–7 кГц. |
| **Opus** | Аудио, адаптивный | 6–510 Кбит/с | ~4.7 | Стандарт WebRTC, адаптация под сетевые условия, SILK+CELT. |
| **G.729** | Аудио, сжатие | 8 Кбит/с | ~3.9 | Низкий битрейт, высокая нагрузка на CPU/DSP, патентные ограничения. |
| **H.264/AVC** | Видео | 1–8 Мбит/с (1080p) | N/A | Широко распространен, аппаратное ускорение. |
| **H.265/HEVC** | Видео | 0.5–5 Мбит/с (1080p) | N/A | ~30% экономия относительно H.264. |
| **VP8** | Видео | 0.5–4 Мбит/с (1080p) | N/A | Бесплатный, WebRTC MTI. |
| **VP9** | Видео | 0.3–3 Мбит/с (1080p) | N/A | ~25–35% экономия относительно VP8. |
| **AV1** | Видео | 0.2–2.5 Мбит/с (1080p) | N/A | ~50% экономия относительно H.264, роялти-фри (по состоянию на 2026 с оговорками). |

**Шкала MOS (ITU-T P.800):**
| Балл | Качество восприятия |
| :--- | :--- |
| 5 | Отлично (удовлетворительно для любых применений) |
| 4 | Хорошо (допустимо для VoIP, видео) |
| 3 | Удовлетворительно (уже заметны искажения) |
| 2 | Плохо (значительные искажения, утомляемость) |
| 1 | Плохо (непригодно для передачи информации) |

Для большинства бизнес-приложений целевой MOS ≥ 4.0 (т.е. PESQ ≥ 3.0 или POLQA ≥ 3.5).

## Технологии оптимизации качества

*   **L4S (Low Latency, Low Loss, Scalable Throughput):** Стандарт (RFC 9330), позволяющий сети и приложению мгновенно реагировать на перегрузку через ECN, поддерживая задержку <10 мс.
*   **BBRv3 (Bottleneck Bandwidth and RTT):** Алгоритм Google, максимизирующий пропускную способность при минимальном RTT, устойчив к случайным потерям.
*   **HTTP/3 (QUIC):** Устраняет блокировку начала очереди (HOL Blocking). Потеря одного пакета в одном потоке не тормозит остальные.
*   **WebRTC:** Использует UDP и встроенные механизмы FEC/PLC для коммуникаций реального времени.
*   **DSCP / CoS маркировка:** Приоритизация трафика на сетевом оборудовании. Для Voice используется DSCP EF (46), для Video — AF41 (34), для Background — CS1 (8).
*   **ECN (Explicit Congestion Notification):** Уведомление о перегрузке без отбрасывания пакетов. Критично для L4S и алгоритмов BBR.
*   **SQM (Smart Queue Management):** fq_codel, CAKE — борьба с Bufferbloat на уровне хоста и шлюза.

## Практические сценарии диагностики

### Сценарий 1: Лаги в играх при низком пинге

**Симптомы:** Пинг 15 мс, но персонаж двигается рывками, модели телепортируются.
**Диагноз:** Высокий **Jitter** или Bufferbloat на промежуточном узле.
**Шаги:**
1.  Запустите базовый `ping` для проверки среднего RTT и mdev:
    ```bash
    ping -c 100 8.8.8.8
    # → rtt min/avg/max/mdev = 18.234/20.567/25.891/2.345 ms
    ```
    *Ожидаемый результат:* `mdev` < 2 мс (стабильный канал). Если `mdev` > 5 мс при avg 20 мс — канал нестабилен.

2.  Запустите `mtr` для локализации хопа с проблемами:
    ```bash
    sudo mtr -rwb -c 200 game-server.example.com
    ```
    *Ожидаемый результат:* Потери (Loss%) и рост Latency на конкретном хопе указывают на перегруженный маршрутизатор.

3.  Проверьте загрузку канала:
    ```bash
    # Если есть торрент-клиент или фоновые бэкапы — ограничьте их.
    iperf3 -c <iperf-server> -t 30
    ```

**Решение:** Переход с Wi-Fi на Ethernet, включение SQM (FQ-CoDel/CAKE) на роутере, ограничение фонового трафика.

---

### Сценарий 2: «Роботизированный» голос в VoIP

**Симптомы:** Голос слышен кусками, металлический призвук, задержки.
**Диагноз:** Комбинация высокого **Jitter** и **Packet Loss**.
**Шаги:**
1.  Запустите `ping` длинной серией для анализа jitter и loss:
    ```bash
    ping -c 500 -i 0.2 voip-gateway.local
    ```
    *Ожидаемый результат:* Loss < 1%, mdev < 3 мс.

2.  Захватите VoIP-трафик (SIP signaling + RTP) в Wireshark:
    ```bash
    sudo tcpdump -i eth0 -n -s 0 udp port 5060 or udp portrange 16384-32767 -w voip_capture.pcap
    wireshark voip_capture.pcap
    ```
    В Wireshark примените фильтр `rtp` и проверьте Statistics → RTP → Show All Streams для Packet Loss и Jitter.

3.  Проверьте, нет ли фоновой нагрузки на канал:
    ```bash
    ss -ti dst :443 | grep -i retrans
    # или
    iperf3 -c <gateway> -u -b 1M -t 10
    ```

**Решение:** Использование диапазона 5/6 ГГц в Wi-Fi, проверка загрузки канала (торренты, бэкапы), настройка QoS на роутере (DSCP EF для VoIP), переход на провод.

### Сценарий 3: Задержка ввода (Input Lag) в облачном гейминге

**Симптомы:** Картинка плавная, но действие происходит с опозданием.
**Диагноз:** Высокая **Latency** из-за удаленности сервера или плохой маршрутизации.
**Шаги:**
1.  Измерьте RTT до ближайшего edge-узла облачного гейминга:
    ```bash
    ping -c 20 cloud-gaming-edge.example.com
    ```
    *Ожидаемый результат:* < 30 мс для игр с требованием <40 мс RTT.

2.  Проанализируйте маршрут:
    ```bash
    traceroute -T -p 443 cloud-gaming-edge.example.com
    ```
    На каждом хопе обратите внимание на время. Если время растет скачкообразно — вероятно, перегруженный узел.

3.  Проверьте маркировку DSCP на выходе:
    ```bash
    sudo tcpdump -i eth0 -n 'ip[1] & 0xfc == 0xb8' | head
    # EF = 0xB8 >> 2. Если пакеты не помечены — узел не приоритизирует их.
    ```

**Решение:** Выбор региона с минимальным RTT, проверка маршрутизации (MPLS vs Internet), включение DSCP-маркировки на клиенте, отключение аппаратного ускорения GPU если оно вносит задержку.

### Сценарий 4: Диагностика и эмуляция условий реального времени

**Симптомы:** Приложение падает или зависает при нестабильном канале.
**Диагноз:** Отсутствие обработки потерь и джиттера на стороне приложения.
**Шаги:**
1.  Эмуляция WAN-условий с помощью `tc netem`:
    ```bash
    # Создание корневой дисциплины с эмуляцией спутникового канала
    sudo tc qdisc add dev eth0 root netem delay 600ms 50ms distribution normal loss 0.5% 25%
    ```
    *Ожидаемый результат:* Приложение тестируется в условиях с задержкой 600 ± 50 мс и коррелированными потерями.

2.  Запуск теста и захват трафика:
    ```bash
    # На тестовом сервере
    iperf3 -s

    # На клиенте
    iperf3 -c <server-ip> -u -b 5M -t 30 -i 5
    ```
    *Ожидаемый результат:* iperf3 покажет Jitter и Lost/Total. Сравните с пороговыми значениями для вашего приложения.

3.  Сброс правил после тестирования:
    ```bash
    sudo tc qdisc del dev eth0 root
    ```

### Сценарий 5: Настройка QoS на Linux-роутере для VoIP и игр

**Симптомы:** Пинг в играх стабилен, но при начале скачивания файла появляются задержки.
**Диагноз:** Bufferbloat на шлюзе, отсутствие приоритезации.
**Шаги:**
1.  Установите дисциплину `fq_codel` на внешний интерфейс (WAN):
    ```bash
    sudo tc qdisc replace dev eth0 root fq_codel
    ```
    *Ожидаемый результат:* `tc qdisc show dev eth0` отображает `qdisc fq_codel`.

2.  Настройте маркировку DSCP для VoIP и игр на конечных устройствах (или через iptables):
    ```bash
    # Маркировка трафика Steam/игр (пример для портов)
    sudo iptables -t mangle -A OUTPUT -p udp --dport 27015:27030 -j DSCP --set-dscp-class CS4
    # Маркировка VoIP (SIP/RTP)
    sudo iptables -t mangle -A OUTPUT -p udp --dport 16384:32767 -j DSCP --set-dscp-class EF
    ```

3.  Настройте иерархический шейпинг (HTB) для гарантированной полосы:
    ```bash
    sudo tc qdisc replace dev eth0 root handle 1: htb default 20
    sudo tc class add dev eth0 parent 1: classid 1:1 htb rate 100mbit ceil 100mbit
    sudo tc class add dev eth0 parent 1:1 classid 1:10 htb rate 20mbit ceil 100mbit prio 0
    sudo tc class add dev eth0 parent 1:1 classid 1:20 htb rate 80mbit ceil 100mbit prio 1
    sudo tc qdisc add dev eth0 parent 1:10 fq_codel
    sudo tc qdisc add dev eth0 parent 1:20 fq_codel
    ```

4.  Проверка стабильности:
    ```bash
    watch -n 1 "tc -s class show dev eth0"
    ```
    *Ожидаемый результат:* В классе 1:10 (Voice/Game) потери (drops) близки к нулю даже при полной нагрузке на класс 1:20.

### Сценарий 6: Анализ RTP-потока в Wireshark

**Симптомы:** Нет явных потерь по `ping`, но качество звонка низкое.
**Диагноз:** Потери или джиттер именно в медиа-потоке (RTP), которые ICMP не видит.
**Шаги:**
1.  Захватите RTP-трафик:
    ```bash
    sudo tcpdump -i eth0 -n -s 0 udp portrange 16384-32767 -w rtp_capture.pcap
    ```
    *Ожидаемый результат:* Файл `rtp_capture.pcap` размером 10–50 МБ за 1–2 минуты разговора.

2.  Откройте в Wireshark и примените фильтр:
    ```
    rtp && ip.dst == <voip-gateway-ip>
    ```

3.  Анализ:
    *   **Telephony → RTP → Show All Streams:** отображает Packet Loss, Jitter, Max Delta для каждого потока.
    *   **Telephony → RTP → Create Substream:** для разбора кодера/декодера.
    *   **Серьезность:** Loss > 1% в голосовом потоке или Jitter > 30 мс — проблема в сети или Bufferbloat.

## Инструменты диагностики

| Инструмент | Что измеряет | Прикладная команда |
| :--- | :--- | :--- |
| **ping** | Latency, Loss, Jitter (mdev) | `ping -c 100 8.8.8.8` |
| **mtr** | Потери и задержки по хопам | `mtr -v google.com` |
| **iperf3** | Throughput, Jitter (UDP) | `iperf3 -u -c <ip> -b 50M` |
| **gping** | График Latency в реальном времени | `gping 1.1.1.1` |
| **Wireshark** | Анализ RTP/UDP потоков | `wireshark` |
| **tc netem** | Эмуляция плохих условий сети | `sudo tc qdisc add dev eth0 root netem delay 100ms` |
| **ss** | Состояние сокетов, RTT (TCP_INFO) | `ss -tin dst :443` |
| **tcpdump** | Захват пакетов для Wireshark | `tcpdump -i eth0 -w capture.pcap` |
| **nping** | TCP/UDP ping (проверка L4) | `nping --tcp -p 443 <host>` |

**Интерпретация `ping`:**
```bash
$ ping -c 10 8.8.8.8
rtt min/avg/max/mdev = 18.234/20.567/25.891/2.345 ms
```
*   **avg:** Средний пинг (базовая задержка).
*   **mdev (Mean Deviation):** Математический показатель джиттера. Если `mdev > 15-20%` от `avg`, в real-time приложениях будут заметны проблемы.

**Интерпретация `iperf3` (UDP):**
```bash
$ iperf3 -c 192.168.1.10 -u -b 100M -t 10
[ ID] Interval           Transfer     Bandwidth      Jitter    Lost/Total
[  5]   0.00-10.00  sec   119 MBytes   100 Mbits/sec  0.025 ms  0/86184 (0%)
```
*   **Jitter:** вариация задержки в UDP-потоке. < 1 мс — отлично, > 5 мс — проблема для VoIP.
*   **Lost/Total:** процент потерь. Для VoIP критично < 1%.

## Типичные ошибки и их устранение

| Ошибка / Симптом | Причина | Решение |
| :--- | :--- | :--- |
| `mdev > 20% от avg` в `ping` | Bufferbloat или нестабильный Wi-Fi | Включите `fq_codel`/`CAKE` на роутере, перейдите на Ethernet или 5/6 ГГц. |
| Потери > 1% при 0% потерь в `ping` | Потери именно в UDP/RTP-трафике | Захватите трафик в Wireshark, проверьте ACL/QoS на промежуточных устройствах. |
| VoIP работает, но игры лагают | Отсутствие приоритезации UDP-трафика игр | Настройте DSCP/CoS, выделите отдельный класс для игрового UDP. |
| `iperf3` показывает низкий Jitter, а в игре лаги | Проблема на стороне сервера игры или маршрутизации | Используйте `mtr` для поиска перегруженного хопа, проверьте RTT до конкретного game-server. |
| Облачный гейминг тормозит при низком `ping` | Высокая Latency из-за удаленности или маршрутизации | Выберите ближайший edge-регион, проверьте MTU/MSS на пути. |
| `ping` проходит, но сайты не открываются | Блокировка ICMP ≠ блокировка TCP/443 | Используйте `nping --tcp -p 443 <host>` или `curl -v <host>` для проверки L4/L7. |

## Рекомендации и очистка

### Best Practices
1.  **Всегда тестируйте в реальных условиях:** Эмуляция `tc netem` полезна, но не заменяет тестирования в production-среде.
2.  **Используйте RTT как первичную метрику:** Для большинства real-time приложений стабильность RTT важнее его абсолютного значения.
3.  **Следите за младшим перцентилем:** P50 показывает «средний» пользователь, а P99/P999 — наихудший опыт. Для корпоративных SLA используйте p95/p99.
4.  **Маркируйте трафик на Trust Boundary:** DSCP/CoS должны устанавливаться как можно ближе к источнику (сервер, рабочая станция), иначе их могут сбросить на границе автономной системы.
5.  **Не игнорируйте Upload-полосу:** Для видеоконференций и облачного гейминга критична именно скорость отдачи, а не загрузки.

### Очистка после тестирования

```bash
# Удаление правил tc
sudo tc qdisc del dev eth0 root 2>/dev/null || true
sudo tc qdisc del dev eth0 ingress 2>/dev/null || true

# Удаление правил iptables (если добавляли)
sudo iptables -t mangle -D OUTPUT -p udp --dport 27015:27030 -j DSCP --set-dscp-class CS4 2>/dev/null || true
sudo iptables -t mangle -D OUTPUT -p udp --dport 16384:32767 -j DSCP --set-dscp-class EF 2>/dev/null || true

# Остановка фоновых процессов iperf3
pkill iperf3
```
