# Качество трафика реального времени: 4 ключевых параметра

## Определения

**Трафик реального времени (Real-time traffic)** — это сетевой трафик, чувствительный к задержкам, их вариациям (джиттеру) и потерям. Для таких данных своевременность доставки критичнее, чем стопроцентная целостность (в отличие от передачи файлов, где важен каждый бит, но время доставки может варьироваться).

К основным типам приложений реального времени относятся:
*   **Онлайн-игры:** Шутеры (Counter-Strike 2, Valorant, Overwatch 2), MOBA (Dota 2, League of Legends), файтинги.
*   **Интерактивные коммуникации:** Видеозвонки (Zoom, Microsoft Teams, Skype) и IP-телефония (VoIP).
*   **Стриминг живого контента:** Трансляции с минимальной задержкой (Twitch, YouTube Live), облачный гейминг (GeForce Now, Xbox Cloud).
*   **Удаленное управление:** RDP (Remote Desktop), VNC, управление промышленными роботами, дронами и БПЛА.

Для оценки качества такого трафика используются **четыре ключевых параметра**: **Latency**, **Bandwidth**, **Jitter** и **Loss**.

## Базовые концепции

### 1. Latency (Задержка)

**Latency (Задержка)** — это интервал времени между отправкой пакета данных и его получением.

**Компоненты задержки:**
1.  **Задержка распространения (Propagation Delay):** Время прохождения сигнала через физическую среду. Зависит от расстояния и скорости света в среде (в оптоволокне ~200 000 км/с). Добавляет ~5 мс на каждые 1000 км.
2.  **Задержка передачи (Transmission Delay):** Время, необходимое для «выталкивания» всех бит пакета в канал. Зависит от пропускной способности (Bandwidth).
3.  **Задержка в очереди (Queuing Delay):** Ожидание пакета в буферах маршрутизаторов при перегрузке (Congestion). Основной источник нестабильности.
4.  **Задержка обработки (Processing Delay):** Время на анализ заголовков, поиск маршрута и выполнение правил файрвола.

**RTT (Round-Trip Time — время кругового обхода):** Время, необходимое для прохождения пакета от отправителя к получателю и обратно. Именно RTT чаще всего измеряется утилитой `ping`.

**Типичные значения RTT (Актуально на 2026):**
*   **Локальная сеть (LAN):** <1 мс (идеально), <5 мс (норма).
*   **В пределах города:** 5–20 мс.
*   **Между городами (региональные):** 20–50 мс.
*   **Между странами/континентами:** 50–150 мс.
*   **Спутниковая связь (Starlink Gen 3):** 20–40 мс (сравнима с наземными линиями).
*   **Спутниковая связь (Геостационарная):** 600–800 мс (непригодно для интерактивности).

**Влияние на комфорт:**

| Приложение | Макс. комфортная задержка (RTT) |
| :--- | :--- |
| **Шутеры (FPS)** | <50 мс (киберспорт — <20 мс) |
| **MOBA / MMO** | <100 мс |
| **VoIP (Голос)** | <150 мс |
| **Видеозвонки** | <200 мс |
| **Облачный гейминг** | <30–40 мс |

### 2. Bandwidth (Пропускная способность)

**Bandwidth (Пропускная способность)** — количество данных, которое канал способен передать за единицу времени.

**Характеристики:**
*   **Измерение:** Биты в секунду (бит/с, Kbps, Mbps, Gbps).
*   **Важное уточнение:** Увеличение пропускной способности **не уменьшает** задержку, если канал не перегружен. Канал становится «толще», но не «быстрее».

**Типичные требования к полосе (2026):**

| Приложение | Мин. пропускная способность | Примечание |
| :--- | :--- | :--- |
| **VoIP (Opus/G.711)** | 64–128 Кбит/с | Важна стабильность, а не объем |
| **Видеозвонок (720p)** | 1.5–2.5 Мбит/с | H.264/H.265 |
| **Видеозвонок (HD 1080p)** | 3–5 Мбит/с | AV1/H.265 |
| **Облачный гейминг (4K)** | 45–60 Мбит/с | Зависит от FPS (60/120) |
| **VR / Галлограммы** | 100+ Мбит/с | Требует высокой стабильности |

### 3. Jitter (Джиттер)

**Jitter (Джиттер)** — это статистическая вариация (колебание) задержки между доставкой последовательных пакетов.

**Визуализация:**
```text
Идеальный канал (Jitter = 0):
Пакет 1 → [20мс] → Получатель
Пакет 2 → [20мс] → Получатель
Пакет 3 → [20мс] → Получатель

Канал с высоким Jitter:
Пакет 1 → [10мс] → Получатель
Пакет 2 → [150мс] → Получатель (задержка!)
Пакет 3 → [15мс] → Получатель (пришел почти сразу после 2)
```

**Последствия и методы борьбы:**
*   **Симптомы:** Прерывания звука, «рывки» в играх (stuttering), телепортация объектов.
*   **Jitter Buffer:** Буфер на стороне получателя, который накапливает пакеты и выдает их приложению с равномерным интервалом. Сглаживает рывки, но увеличивает общую Latency.
*   **Wi-Fi 7 MLO (Multi-Link Operation):** Использование нескольких диапазонов одновременно для минимизации джиттера, вызванного помехами.

### 4. Loss (Потеря пакетов)

**Loss (Потеря пакетов)** — процент пакетов, которые были отправлены, но не дошли до адресата.

**Симптомы превышения нормы:**

| Приложение | Допустимые потери | Последствия |
| :--- | :--- | :--- |
| **VoIP** | <1% | Пропуски в аудио, щелчки, выпадение слов. |
| **Видеозвонки** | <2% | Зависания картинки, «рассыпание» на квадраты. |
| **Онлайн-игры** | <0.5% | Пакет-лосс: действия не регистрируются. |
| **Веб-сёрфинг** | <5% | Замедление из-за ретрансмиссий TCP. |

**Механизмы компенсации и причины:**
*   **FEC (Forward Error Correction):** Передача избыточных данных для восстановления потерянных пакетов без перезапроса.
*   **PLC (Packet Loss Concealment):** Генерация синтетических данных (звука/кадра) для маскировки пропусков.
*   **Bufferbloat:** Избыточная буферизация в роутерах, создающая огромные очереди при нагрузке.
*   **Tail Drop:** Сброс пакетов при переполнении очереди. Решается через **AQM** (CoDel, PIE).

## Технологии оптимизации качества

- **L4S (Low Latency, Low Loss, Scalable Throughput):** Стандарт (RFC 9330), позволяющий сети и приложению мгновенно реагировать на перегрузку через ECN, поддерживая задержку <10 мс.
- **BBRv3 (Bottleneck Bandwidth and RTT):** Алгоритм Google, максимизирующий пропускную способность при минимальном RTT, устойчив к случайным потерям.
- **HTTP/3 (QUIC):** Устраняет блокировку начала очереди (HOL Blocking). Потеря одного пакета в одном потоке не тормозит остальные.
- **WebRTC:** Использует UDP и встроенные механизмы FEC/PLC для коммуникаций реального времени.

## Практические сценарии диагностики

**Сценарий 1: Лаги в играх при низком пинге**
*   **Симптомы:** Пинг 15 мс, но персонаж двигается рывками.
*   **Диагноз:** Высокий **Jitter**.
*   **Решение:** Перейти с Wi-Fi на Ethernet, включить SQM (FQ-CoDel/Cake) на роутере.

**Сценарий 2: «Роботизированный» голос в VoIP**
*   **Симптомы:** Голос слышен кусками, металлический призвук.
*   **Диагноз:** Комбинация высокого **Jitter** и **Packet Loss**.
*   **Решение:** Использование диапазона 5/6 ГГц в Wi-Fi, проверка загрузки канала (торренты).

**Сценарий 3: Задержка ввода (Input Lag) в облачном гейминге**
*   **Симптомы:** Картинка плавная, но действие происходит с опозданием.
*   **Диагноз:** Высокая **Latency** из-за удаленности сервера или плохой маршрутизации.

## Инструменты диагностики

| Инструмент | Что измеряет | Прикладная команда |
| :--- | :--- | :--- |
| **ping** | Latency, Loss, Jitter (mdev) | `ping -c 100 8.8.8.8` |
| **mtr** | Потери и задержки по хопам | `mtr -v google.com` |
| **iperf3** | Throughput, Jitter (UDP) | `iperf3 -u -c <ip> -b 50M` |
| **gping** | График Latency в реальном времени | `gping 1.1.1.1` |
| **Wireshark** | Анализ RTP/UDP потоков | `wireshark` |

**Интерпретация `ping`:**
```bash
$ ping -c 10 8.8.8.8
rtt min/avg/max/mdev = 18.234/20.567/25.891/2.345 ms
```
*   **avg:** Средний пинг (базовая задержка).
*   **mdev (Mean Deviation):** Математический показатель джиттера. Если `mdev > 15-20%` от `avg`, в real-time приложениях будут заметны проблемы.
