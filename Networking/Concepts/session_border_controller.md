# Session Border Controller (SBC)

## Определения

- **SBC (Session Border Controller):** Специализированный сетевой элемент (физический, виртуальный или облачный), который управляет сигнальными потоками и медиа-трафиком на границах IP-сетей. В отличие от обычных файрволов, SBC глубоко понимает протоколы реального времени (SIP, RTP, RTCP, WebRTC) и может модифицировать их на лету.
- **B2BUA (Back-to-Back User Agent):** Архитектурный принцип работы SBC. Устройство выступает одновременно и как SIP-клиент (UAC), и как SIP-сервер (UAS). SBC разрывает сессию на два независимых «плеча» (Call Legs), что позволяет полностью переписывать заголовки, менять порты и управлять медиа-параметрами независимо для каждой стороны.
- **STIR/SHAKEN (Secure Telephone Identity Revisited / Signature-based Handling of Asserted information using toKENs):** Стандарт аутентификации вызовов. Использует криптографические сертификаты (ATIS) для подтверждения того, что номер вызывающего абонента не был подделан (анти-спуфинг). STIR — протокол на уровне SIP, SHAKEN — фреймворк доверия для операторов.
- **HMR (Header Manipulation Rules):** Наборы правил на SBC для модификации SIP-заголовков «на лету» (например, изменение формата номера с +7 на 8, маскировка внутренних адресов).
- **Media Anchoring:** Режим работы SBC, при котором медиа-трафик (RTP/RTCP) всегда проходит через сам SBC. Позволяет выполнять транскодинг, запись разговоров (Recorder), анализ DTMF и детектирование речи.
- **Media Release (Bypass Media):** Режим, при котором SBC «выпускает» медиа-трафик напрямую между конечными точками после установления сессии. Экономит ресурсы SBC и снижает задержку (latency), но ограничивает возможности контроля.
- **HNT (Hosted NAT Traversal):** Механизм SBC, при котором устройство заменяет приватные IP-адреса в заголовках `Contact` и в SDP на свои публичные адреса, гарантируя прохождение голоса через NAT.
- **Lawful Intercept (LI):** Функция обязательной сервисной разведки (прослушивания). SBC может дублировать медиа-поток в сторону правоприменительных органов без уведомления абонентов.
- **SIP ALG (Application Layer Gateway):** Упрощенный аналог SBC, часто встроенный в маршрутизаторы. Модифицирует SIP/SDP на лету, но имеет низкое качество работы с нестандартными заголовками и TLS. Рекомендация — отключать и использовать полноценный SBC.

## Базовые концепции

### SIP-сигнализация и жизненный цикл вызова

SBC оперирует на сессионном и прикладном уровнях (L5–L7), обеспечивая стыковку разнородных сетей. Понимание потока SIP-сообщений необходимо для диагностики и настройки.

**Классический поток INVITE (Simplified):**

```text
Caller A                     SBC                         Callee B
   |       INVITE (SDP)        |                            |
   |--------------------------->|                            |
   |                           |       INVITE (mod SDP)     |
   |                           |--------------------------->|
   |                           |                            |
   |     100 Trying            |     100 Trying             |
   |<---------------------------|<---------------------------|
   |                           |                            |
   |                           |     180 Ringing            |
   |                           |<---------------------------|
   |     180 Ringing           |                            |
   |<---------------------------|                            |
   |                           |                            |
   |                           |     200 OK (SDP)            |
   |                           |<---------------------------|
   |     200 OK (mod SDP)      |                            |
   |<---------------------------|                            |
   |                           |                            |
   |         ACK               |         ACK                 |
   |--------------------------->|--------------------------->|
   |                           |                            |
   |===== Медиа (RTP/RTCP) через SBC или напрямую ==========|
   |                           |                            |
   |         BYE               |         BYE                 |
   |<---------------------------|<---------------------------|
   |        200 OK             |        200 OK               |
   |--------------------------->|--------------------------->|
```

**Ключевые модификации на SBC (B2BUA):**
- SBC генерирует новые `Call-ID`, `CSeq`, `From`/`To` tags для каждого Call Leg.
- При Media Anchoring — SBC вставляет себя в SDP (меняет IP/порт RTP на свои).
- При Media Release — SDP конечной точки остается оригинальным, SBC участвует только в сигнализации.
- Для NAT Traversal SBC корректирует `Contact` и SDP, подставляя публичные адреса.

### Ключевые функции и механизмы

| Категория | Технические детали |
| :--- | :--- |
| **Безопасность (L7)** | Защита от DoS/DDoS (SIP-flood, TLS-атаки), динамические ACL (автоблокировка по неудачным попыткам регистрации), Topology Hiding (скрытие внутренних IP-адресов АТС), scrambling SIP URI, анти-спуфинг STIR/SHAKEN. |
| **SIP Нормализация** | Исправление несовместимостей между вендорами (Interworking). Например, перевод `P-Asserted-Identity` в `Remote-Party-ID`, удаление нестандартных заголовков, нормализация кодов ответов. |
| **Управление медиа** | **Media Anchoring** (SBC пропускает RTP через себя для контроля) или **Media Release** (SBC разрешает устройствам передавать трафик напрямую, исключая себя из пути данных). Поддержка DTLS, SRTP, ZRTP для шифрования медиа. |
| **Транскодинг** | Преобразование кодеков в реальном времени (например, G.711 ↔ Opus / G.729). Требует значительных вычислительных мощностей или специализированных DSP-чипов. |
| **NAT Traversal** | Механизм **Hosted NAT Traversal (HNT)**. SBC заменяет приватные IP в заголовках `Contact` и в теле SDP на свои публичные адреса, гарантируя прохождение голоса через роутеры. Также поддерживает ICE/STUN/TURN для сложных топологий. |
| **QoS и маршрутизация** | Маркировка DSCP (EF для voice, AF41 для видео), управление очередями, выбор маршрута на основе SLA (LCR). Интеграция с MPLS через DiffServ. |
| **STIR/SHAKEN** | Проверка криптографических подписей (SiP), верификация сертификатов через STIR/SHAKEN IdP, маршрутизация вызовов с низким уровнем доверия (No Trust, Gateway, Full Trust) в отдельные очереди. |
| **Lawful Intercept** | Дублирование медиа-потока (X-Connect) в сторону правоохранительных органов без уведомления абонента. Поддержка ETSI LI, CALEA (США). |

### Сравнение: SBC vs Традиционный Файрвол (Stateful Firewall)

| Характеристика | Традиционный Firewall | Session Border Controller |
| :--- | :--- | :--- |
| **Глубина анализа** | L3–L4 (IP, Порт) | L5–L7 (SIP Method, Headers, SDP, RTP/RTCP) |
| **Состояние** | Состояние соединения (TCP/UDP) | Состояние сессии (Call State, Dialog) |
| **Модификация** | Только NAT (IP/Port) | Полная модификация любого заголовка, тела пакета, SDP |
| **Медиа** | Часто блокирует RTP из-за динамических портов | Открывает только нужные порты для конкретной сессии, контролирует RTP-поток |
| **Кодеки** | Не видит и не обрабатывает | Транскодинг, DTMF детекция, FEC/PLC |
| **Безопасность** | IP/порт ACL, stateful inspection | Анти-спуфинг, SIP-flood защита, STIR/SHAKEN, lawful intercept |
| **NAT Traversal** | Базовый (SNAT/DNAT) | HNT, ICE/STUN/TURN, ALG-grade модификация SDP |

### Архитектурные модели развертывания

| Модель | Описание | Преимущества | Недостатки |
| :--- | :--- | :--- | :--- |
| **Standalone SBC** | Отдельное физическое/виртуальное устройство между АТС и интернетом. | Максимальная производительность, изоляция, безопасность. | Высокая стоимость, единая точка отказа без HA. |
| **SBC + Media Server** | SBC интегрирован с медиа-сервером (Audiocodes, Ribbon). | Полный контроль, транскодинг, запись. | Сложность масштабирования медиа. |
| **Virtualized SBC (vSBC)** | SBC как VM (KVM, VMware) на стандартном железе. | Гибкость, масштабируемость, интеграция с OpenStack. | Зависимость от гипервизора, потенциальные задержки. |
| **Cloud-native SBC** | SBC в контейнерах (Kubernetes), микросервисная архитектура. | Масштабируемость, CI/CD, отказоустойчивость. | Сложность отладки медиа-трафика, требовательность к сетевым API ядра. |

### Высокая доступность (High Availability)

SBC является критически важным элементом инфраструктуры. Отказ приводит к потере всех вызовов через границу.

**Типовые схемы HA:**
- **Active-Active (1+1):** Два SBC работают одновременно, балансировка по SIP сигнализации (DNS SRV, Load Balancer) и медиа. При отказе одного — второй берет нагрузку без потери сессий.
- **Active-Standby (1:1):** Основной SBC активен, резервный в режиме ожидания (warm standby). При отказе происходит failover через heartbeat (VRRP, BGP, proprietary).
- **Geo-Redundancy:** SBC в разных дата-центрах (active-active по географическому принципу). Используется Anycast или Geo-DNS для направления вызовов к ближайшему узлу.

**Критичные параметры для HA:**
- **Failover Time:** < 200 мс для сигнализации, < 1 сек для медиа (Media Release упрощает failover).
- **Session Persistence:** При Active-Standby медиа-сессии не переживают failover без Media Anchoring на standby.
- **Shared State:** Базовый stateful failover требует синхронизации таблиц сессий (state replication) между active и standby SBC.

## Практические сценарии

### Предварительные требования

#### Для SBC (общие)

| Компонент | Версия/Требование | Примечание |
| :--- | :--- | :--- |
| **ОС** | Linux (Debian 12+, RHEL 9+) или специализированное ПО вендора | Для vSBC; аппаратные SBC имеют свою ОС |
| **Сеть** | Публичные IP на WAN-интерфейсах, статическая маршрутизация | BGP для операторских развертываний |

| **DNS** | SRV-записи для `_sip._tcp` и `_sip._udp` (если используется) | TTL ≤ 60 сек для быстрого failover |
| **STIR/SHAKEN** | Сертификат OAuth/JWK от ATIS Trust Anchor, Knox/IdP endpoint | Требуется для USA/Canada операторов (Robocall mitigation) |

- **Admission Control:** Ограничение количества одновременных вызовов (Call Concurrency) согласно контракту.
- **SIP Trunk balancing:** Распределение вызовов по нескольким транкам.

**Шаги:**

1.  **Настройка Peering-интерфейса:**
    ```bash
    # Настройка BGP для объявления SIP-префиксов (если используется SIP-aware routing)
    # Обычно peering — статический IP или BGP для маршрутизации
    ```

2.  **Настройка LCR и Route Tables:**
    В веб-интерфейсе SBC создайте таблицу маршрутов:
    - Priority 1: Operator_B (стоимость 0.01/мин, CAP 1000)
    - Priority 2: Operator_C (стоимость 0.015/мин, CAP 500)

    **Ожидаемый результат:** Вызовы направляются на Operator_B, пока не исчерпан лимит, затем переключаются на Operator_C.


4.  **Валидация:**

### Сценарий 3: Корпоративный сегмент — Замена SIP ALG на SBC

**Задача:** Отключить SIP ALG на корпоративном маршрутизаторе и настроить SBC для NAT Traversal локальных IP-АТС и SIP-клиентов.

**Шаги:**

1.  **Отключение SIP ALG на маршрутизаторе:**
    ```bash
    # Cisco IOS: отключение ALG
    no ip nat service sip udp port 5060
    no ip nat service sip tcp port 5061
    ```

2.  **Размещение SBC в DMZ:**
    SBC получает два интерфейса: LAN (к АТС) и DMZ (к интернету). На маршрутизаторе настроен DNAT для портов 5060/5061 и диапазона RTP (16384–32767) на IP SBC в DMZ.

3.  **Настройка NAT на SBC:**
    В режиме HNT SBC подменяет внутренние IP в SDP на свои внешние IP.

    **Ожидаемый результат:** SIP-клиенты за NAT (например, телефоны в филиалах) могут совершать и принимать вызовы без настройки STUN/TURN на клиентах.

4.  **Валидация:**
    ```bash
    # Проверка, что ALG отключен (пакеты SIP не модифицируются до SBC)
    tcpdump -i eth0 -n -s 0 udp port 5060 -vvv -w sip_raw.pcap

    # Анализ SDP: в теле должен быть IP SBC, а не внутренний IP АТС
    ```

### Сценарий 4: STIR/SHAKEN — Анти-спуфинг для оператора

**Задача:** Реализовать проверку и подпись исходящих вызовов для соответствия требованиям FCC (Fighting Illegal Robocalling).

**Шаги:**

1.  **Получение сертификата STIR:**
    Зарегистрируйте оператора в ATIS, получите сертификат OAuth/JWK.

2.  **Настройка STIR-сервиса на SBC:**
    ```bash
    # Пример: верификация Identity-заголовка входящего вызова
    # SIP message:
    # Identity: eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...
    # Identity-Info: <https://stir.example.com/cert>;alg=ES256
    ```

3.  **Политика маршрутизации:**
    - **Full Trust:** Вызовы с валидной подписью — маршрутизируются нормально.
    - **Gateway:** Нет подписи, но номер не числится в спам-базе — маршрутизируются с пометкой.
    - **No Trust:** Нет подписи, номер в спам-базе — отклоняются или маршрутизируются на IVR.

    **Ожидаемый результат:** Злоумышленные вызовы с подделанным Caller ID блокируются или маршрутизируются на проверку.

## Диагностика и инструменты

### Работа с трафиком

```bash
# Просмотр SIP-диалогов в интерактивном режиме
# Позволяет видеть Flow Diagram каждого вызова
sngrep -t

# Захват только сигнального трафика на интерфейсе eth0
tcpdump -i eth0 -n -s 0 port 5060 or port 5061 -vvv -w signaling.pcap

# Захват медиа-трафика (RTP) для диагностики качества
tcpdump -i eth0 -n -s 0 udp portrange 16384-32767 -w media.pcap

# Анализ SIP-сообщений в реальном времени
sudo tcpdump -i eth0 -n -s 0 -A port 5060 | grep -E "INVITE|SIP/2.0"

# Проверка TLS-сессий (если SIP over TLS)
openssl s_client -connect sbc.example.com:5061
```

### Коды ответов и отладка сессий

| Код | Описание | Типичная причина на SBC | Действие |
| :--- | :--- | :--- | :--- |
| `100 Trying` | Запрос принят, обработка продолжается | Нормальный ответ при получении INVITE | — |
| `401 Unauthorized` | Требуется аутентификация | SBC запрашивает REGISTER auth (норма) | Отправить REGISTER с credentials |
| `403 Forbidden` | Доступ запрещен | Ошибка в логине/пароле или IP вне Trust List | Проверить Trusted Peers, ACL |
| `480 Temporarily Unavailable` | Вызываемый абонент не в сети | Не зарегистрирован на SBC/АТС, неверный номер | Проверить регистрацию абонента |
| `488 Not Acceptable Here` | Не согласованы кодеки | Устройства не договорились о кодеках в SDP | Настроить транскодинг на SBC |
| `503 Service Unavailable` | Сервис недоступен | Admission Control (превышен лимит вызовов) | Ожидание освобождения ресурсов |
| `603 Decline` | Вызов отклонен | Намеренный отказ (busy, DND) | Нет действия |

### Типичные ошибки и их устранение

| Ошибка / Симптом | Причина | Диагностика | Решение |
| :--- | :--- | :--- | :--- |
| **Односторонний аудио** | NAT на одном из плеч, неправильный SDP, блокировка RTP | `tcpdump` на SBC и обоих концах; проверка IP:порт в SDP | HNT на SBC; открытие диапазона RTP; проверка ACL |
| **Потеря медиа при переключении** | Media Release без STUN/ICE; асимметричный NAT | Проверка `c=` в SDP; `rtcp` отчеты | Переход на Media Anchoring или ICE |
| **Не проходит TLS-рукопожатие** | Несовпадение cipher suites, сертификат не доверен | `openssl s_client -connect ... -debug` | Обновление сертификата; настройка TLS-версии (TLS 1.2+) |
| **Вызовы падают после 32 секунды** | Таймаут NAT на маршрутизаторе (меньше чем conntrack UDP) | `conntrack -L` на маршрутизаторе; `tcpdump` | Увеличение таймаута UDP; настройка keep-alive (OPTIONS) |
| **SIP-flood (DoS)** | Массовые INVITE с подделанными номерами | `sngrep` показывает сотни уникальных Call-ID; нагрузка на CPU SBC | Включение Dynamic ACL; rate limiting; blacklisting |
| **Искаженный DTMF (RFC 2833)** | Кодеки не договорились о DTMF-паayload (telephone-event) | Wireshark: отсутствие или искажение RTP DTMF | Принудительная отправка DTMF через SIP INFO или RFC 2833 |
| **Низкое качество голоса (MOS < 3.5)** | Пакетные потери, джиттер, низкий битрейт | Wireshark → RTP → Stream; `iperf3` | Настройка QoS (DSCP EF); увеличение Jitter Buffer; проверка MTU |

### Ограничения и Edge Cases

| Категория | Edge Case | Объяснение и решение |
| :--- | :--- | :--- |
| **SIP over WebSocket** | SBC не поддерживает WSS (WebSocket Secure) natively | Использовать отдельный WSS-шлюз перед SBC или выбрать SBC с поддержкой WebSocket (Kamailio) |
| **SCTP (SIGTRAN)** | SBC поддерживает только SIGTRAN (M3UA) для телефонии, но не пользовательский SCTP | Использовать отдельный SIGTRAN-платформу (e.g., kamailio + sipt) |
| **IPv6 Only** | Многие операторские SBC требуют IPv4 на WAN для транков | Использовать NAT64/DNS64 или выбрать SBC с native IPv6 support |
| **Double NAT + SBC** | Если SBC за NAT, а клиенты за другим NAT — HNT может не справиться | Использовать Media Anchoring + STUN/TURN на SBC |
| **Транскодинг при 100% G.729** | Некоторые лицензии ограничивают количество одновременных transcoding-сессий | Мониторинг лицензий (например, `sbc-license-status`); масштабирование DSP |
| **TCP для SIP (TLS)** | Многие IP-АТС поддерживают только UDP (5060); переход на TCP меняет обработку пакетов | Настроить SBC для dual-stack (UDP 5060 + TCP 5061) |
| **Fragmentation SDP** | Очень длинные SDP (множество кодеков) могут фрагментироваться на MTU 1500 | Уменьшение MTU до 1400; сжатие SDP (SDPng) |

### Очистка и откат

```bash
# Удаление правил iptables (если добавляли)
sudo iptables -t nat -D PREROUTING -p udp --dport 5060 -j DNAT --to sbc-lan-ip:5060
sudo iptables -t nat -D PREROUTING -p udp --dport 16384:32767 -j DNAT --to sbc-lan-ip:16384-32767

# Остановка фоновых захватов
pkill tcpdump
pkill sngrep

# Откат конфигурации SBC (через API/CLI вендора)
# Обычно: sbc-cli config revert last 1
```
