# Сетевые зоны безопасности

> **Reliability Score: 10/10** (SSoT + Web Verification 2026)

## Определения

- **Зона безопасности (Security Zone):** Логический сегмент сети, объединяющий ресурсы с идентичными требованиями к безопасности и уровнем доверия. Границы зон определяются правилами на межсетевых экранах (МСЭ).
- **Радиус поражения (Blast Radius):** Область потенциального ущерба при компрометации одного узла внутри зоны. Зонирование направлено на минимизацию этого радиуса.
- **Уровень доверия (Trust Level):** Относительный показатель «чистоты» трафика. Традиционно: Интернет (0), DMZ (50), Внутренняя сеть (100). В современной модели [Zero Trust](./zero_trust_overview.md) уровень доверия к любой зоне по умолчанию равен нулю.

## Основные концепции

### Эволюция периметра: от DMZ к Zero Trust
Традиционная модель строится на защите периметра. Однако современная безопасность опирается на принцип **Assume Breach** (предположение о взломе): внутренняя сеть не считается безопасной, а зоны используются для ограничения «бокового перемещения» (Lateral Movement) злоумышленника.

### Типы стандартных зон

1.  **Публичная зона (Untrusted/Internet):** Весь внешний мир. Источник большинства атак.
2.  **Демилитаризованная зона (DMZ):** Буфер между Интернетом и внутренними ресурсами. Здесь размещаются публичные сервисы:
    - Веб-серверы и WAF.
    - Reverse Proxy / Load Balancers.
    - Внешние почтовые реле.
    - Jump-хосты (Bastion).
3.  **Внутренняя зона (Trusted/Internal):** Сегменты для офисных пользователей, серверов приложений и БД. Часто разделяется на `Apps` и `Data`.
4.  **Зона управления (Management/OOB):** Изолированная сеть Out-of-Band для доступа к IPMI/iDRAC, SSH оборудования и консолям управления.

## Специализированные зоны

### Зона данных держателей карт (CDE)
Требование стандарта **PCI DSS**. Весь сетевой сегмент, где передаются или хранятся данные карт, должен быть строго изолирован от офисной сети и Интернета. Доступ разрешается только через специализированные шлюзы с обязательной двухфакторной аутентификацией.

### Облачные зоны (VPC и Security Groups)
В облаках зоны реализуются через:
- **Virtual Private Cloud (VPC):** Изолированная виртуальная сеть.
- **Security Groups (SG):** Микро-файрволы на уровне каждого инстанса. Это позволяет реализовать зоны не на уровне подсетей, а на уровне ролей приложений.

## Практические сценарии

### Реализация DMZ с двумя файрволами
Наиболее надежная схема («Sandwich»):
- **Внешний МСЭ:** Пропускает только 80/443 порты из Интернета к балансировщику в DMZ.
- **Внутренний МСЭ:** Пропускает трафик только от балансировщика в DMZ к серверам приложений во внутренней сети по специфичным портам.

### Управление зонами в Linux (Firewalld)
Firewalld реализует концепцию зон на уровне ОС. Интерфейс или Source IP привязывается к зоне, которая определяет политику.

```bash
# Просмотр активных зон и привязанных интерфейсов
firewall-cmd --get-active-zones
# → result: 
# public
#   interfaces: eth0
# trusted
#   interfaces: eth1

# Перенос интерфейса в зону DMZ
sudo firewall-cmd --zone=dmz --change-interface=eth0 --permanent
sudo firewall-cmd --reload

# Проверка разрешенных сервисов в зоне
firewall-cmd --zone=dmz --list-services
# → result: ssh http https
```

### Изоляция управления (Management Network)
Для серверов в стойке или критичных ВМ:
1. Выделяется отдельный VLAN (например, VLAN 99).
2. На сервере SSH биндится только на IP из этого VLAN.
3. На МСЭ создается зона `MGMT`, доступ в которую разрешен только с VPN-шлюза администраторов.

## Сравнение моделей зонирования

| Параметр | Традиционное зонирование | Микросегментация / Zero Trust |
| :--- | :--- | :--- |
| **Основа** | IP-адреса и VLAN | Идентичность (Identity), Контекст |
| **Гранулярность** | Уровень подсети/сегмента | Уровень процесса/контейнера/пода |
| **Трафик** | Фокус на North-South (вход/выход) | Фокус на East-West (внутри ЦОД) |
| **Динамичность** | Статичные правила | Динамические политики (eBPF, Service Mesh) |
