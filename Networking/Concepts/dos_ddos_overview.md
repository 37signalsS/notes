# DoS/DDoS Overview

## Definitions

**DoS (Denial of Service)** — атака типа «отказ в обслуживании» из одного источника. Единственная точка атаки упрощает обнаружение и блокировку по IP-адресу.

**DDoS (Distributed Denial of Service)** — распределённая атака типа «отказ в обслуживании» из множества географически распределённых точек (ботнет). Значительно сложнее для отражения из-за большого количества атакующих хостов.

> **Подробный разбор:** Классификация атак, архитектура многоуровневой защиты и практические примеры — в [DDoS (Distributed Denial of Service)](../../Security/ApplicationSecurity/ddos_waf/ddos.md).

## Basic Concepts

Атаки классифицируются по уровням модели OSI, на которые они нацелены.

### L3/L4 — Сетевой и транспортный уровень (Volumetric)

Атаки направлены на переполнение пропускной способности сети или ресурсов сетевого оборудования.

- **Примеры:** UDP-флуд, ICMP-флуд, SYN-флуд, DNS/NTP Amplification.
- **Цель:** Забить входящий интернет-канал вредоносным трафиком, чтобы легитимный трафик физически не мог достичь сервера.
- **Защита:** Фильтрация на уровне провайдера/дата-центра, специализированные облачные сервисы очистки трафика. Защита на конечном сервере (например, через `iptables`) неэффективна — канал уже перегружен.

### L7 — Уровень приложения

Атаки направлены на исчерпание ресурсов приложения (CPU, память, подключения к БД) запросами, имитирующими легитимные.

- **Примеры:** HTTP-флуд, Slowloris, атаки на ресурсоёмкие API-эндпоинты.
- **Цель:** Заставить приложение выполнять ресурсоёмкие операции, что приводит к замедлению или отказу. Современные ботнеты мимикрируют под поведение реальных пользователей.
- **Защита:** Профессиональные распределённые [прокси-сервисы и CDN](./proxy.md) (Cloudflare, Qrator, Kaspersky DDoS Protection), которые терминируют и анализируют трафик, пропуская к серверу только очищенные запросы.

### Продвинутые методы защиты на сервере

- **XDP (eXpress Data Path):** Обработка пакетов на раннем этапе с высокой производительностью через [eBPF/XDP](../../Linux/Core/kernel/ebpf.md).
- **SYN Cookies:** Параметр `net.ipv4.tcp_syncookies=1` в Linux позволяет отвечать на SYN-запросы без выделения ресурсов до получения ответа от клиента.
- **Rate Limiting:** Модуль `limit_req` в Nginx ограничивает частоту запросов с одного IP. Недостаток: возможна блокировка легитимных пользователей за одним NAT.
- **Connection Limiting:** Модуль `limit_conn` в Nginx ограничивает число одновременных подключений с одного IP.

## Practical Scenarios

### Сценарий 1: Volumetric-атака (L3/L4)

**Задача:** Сервер подвергается UDP-флуду, канал перегружен на 90%.

**Решение:**
1. Локальная защита неэффективна — канал уже забит.
2. Обратиться к провайдеру/дата-центру для фильтрации на их уровне.
3. Для долгосрочной защиты подключить специализированный сервис очистки трафика (Cloudflare, Qrator, AWS Shield).

### Сценарий 2: HTTP-флуд (L7)

**Задача:** Веб-приложение замедлилось из-за массовых запросов к ресурсоёмкому endpoint.

**Решение:**
1. Подключить CDN/WAF для анализа и фильтрации трафика.
2. Настроить rate limiting на веб-сервере как временную меру.
3. Включить Challenge-Response (CAPTCHA, JS challenges) для подозрительных запросов.

### Сценарий 3: SYN-flood

**Задача:** Сервер получает большое количество SYN-пакетов, таблица соединений переполнена.

**Решение:**
1. Включить SYN Cookies: `sysctl -w net.ipv4.tcp_syncookies=1`.
2. Настроить мониторинг аномалий (RPS, bandwidth, error rate).
3. При масштабной атаке — подключить внешнюю DDoS-защиту.

## Additional Information

### Сложность защиты

Защита от современных L7-атак сравнима по сложности с фильтрацией спама. Требуется комплексный подход: репутационные базы IP, поведенческий анализ, глобальная экспертиза.

**Ключевой вывод:** Построить надёжную защиту от масштабных распределённых атак (особенно L7) силами одного сервера или локального файрвола практически невозможно. Необходимы специализированные внешние сервисы.
