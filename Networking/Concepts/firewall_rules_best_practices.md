# Контроль доступа: лучшие практики и правила файрвола

### Определения

- **Контроль доступа на уровне сети**: Процесс применения правил на файрволах для фильтрации трафика между сетями и системами.
- **Принцип минимальных привилегий**: Основополагающий принцип безопасности, согласно которому сущности (пользователю, сервису) должны предоставляться только те права доступа, которые необходимы для выполнения ее задач.
- **Default Deny (Запрет по умолчанию)**: Политика, при которой весь трафик, который не разрешен явным образом, блокируется.
- **Allowlist (Белый список)**: Подход, при котором разрешается только определенный, заранее известный трафик, а все остальное запрещается. Противоположность подходу **Blocklist** (черный список).

> Для понимания теоретических основ работы файрволов (Netfilter, Stateful/Stateless) см. **[Концепции сетевых файрволов](firewall_concepts.md)**.

---

### Основные концепции: Принципы Zero Trust

В контексте архитектуры [Zero Trust](./zero_trust_overview.md) сетевой контроль доступа строится на следующих принципах:

- **Никому не доверять по умолчанию**: Любой трафик, независимо от его источника (внутреннего или внешнего), считается потенциально враждебным.
- **Явное разрешение**: Каждое сетевое взаимодействие должно быть явно разрешено.
- **Микросегментация**: Сеть разбивается на мелкие, изолированные сегменты (вплоть до отдельного приложения), чтобы ограничить боковое передвижение злоумышленника в случае компрометации одного из узлов.
- **Строгий контроль Egress-трафика**: Не менее важен, чем контроль входящего трафика. Сервисы должны иметь возможность отправлять трафик только на разрешенные внешние адреса.

### Практические сценарии

#### Практики проектирования правил

1. **Начинайте с `DROP` по умолчанию**: Установите политику по умолчанию `DROP` для цепочек `INPUT`, `FORWARD` и `OUTPUT`.
2. **Первые правила — самые важные**: Сначала разрешайте критически важный трафик:
    - Трафик на `loopback` интерфейсе (`-i lo`).
    - Уже установленные и связанные соединения (`-m conntrack --ctstate ESTABLISHED,RELATED`).
3. **Будьте конкретны**: Указывайте протокол (`-p tcp`), порт назначения (`--dport 443`) и, по возможности, IP-адрес или подсеть источника (`-s 10.10.0.0/24`). Избегайте правил `any-any`.
4. **Контролируйте Egress**: Явно разрешайте исходящие соединения только к необходимым ресурсам (например, к конкретным DNS-серверам, репозиториям пакетов, API).
5. **Используйте зоны и интерфейсы**: Привязывайте правила к сетевым интерфейсам (`-i eth0`) для разделения [зон](./network_security_zones.md) (`public`, `internal`, `dmz`).
6. **Управляйте как кодом (IaC)**: Храните конфигурацию файрвола в системе контроля версий (Ansible, Terraform, Git). Это обеспечивает версионирование, аудит и атомарное применение изменений.
7. **Логируйте заблокированный трафик**: Добавьте правила для логирования пакетов, которые будут отброшены. Используйте префиксы и ограничение частоты, чтобы не переполнять логи.

    ```bash
    # Пример правила для логирования
    iptables -A INPUT -j LOG --log-prefix "INPUT dropped: " --log-level 4
    ```

#### Пример: Stateful `iptables` для веб-сервера

```bash
# 1. Установить политику "запретить всё"
iptables -P INPUT   DROP
iptables -P FORWARD DROP
iptables -P OUTPUT  DROP

# 2. Разрешить loopback и уже установленные соединения (входящие и исходящие)
iptables -A INPUT  -i lo -j ACCEPT
iptables -A OUTPUT -o lo -j ACCEPT
iptables -A INPUT  -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A OUTPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# 3. Ingress: разрешить SSH только из сети администраторов и HTTPS для всех
iptables -A INPUT -p tcp --dport 22 -s 10.10.0.0/24 -j ACCEPT
iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# 4. Egress: разрешить DNS (к нашему DNS) и HTTPS (для обновлений, API и т.д.)
iptables -A OUTPUT -p udp --dport 53 -d 10.0.1.53 -j ACCEPT
iptables -A OUTPUT -p tcp --dport 443 -j ACCEPT
```

**Альтернатива на nftables:** Эквивалентная конфигурация на современном nftables с дополнительными возможностями (rate limiting, fail2ban, динамические списки) описана в **[nftables: современная подсистема фильтрации](../../Linux/Networking/Settings/tools/nftables/index.md)**.

#### Пример: Kubernetes NetworkPolicy

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-backend-policy
spec:
  # Политика применяется к подам с этой меткой
  podSelector:
    matchLabels:
      app: backend
  policyTypes: ["Ingress", "Egress"]
  
  # Правила для входящего трафика (Ingress)
  ingress:
  - from:
    # Разрешить трафик только от подов с меткой app: frontend
    - podSelector:
        matchLabels:
          app: frontend
    ports:
    - protocol: TCP
      port: 8080

  # Правила для исходящего трафика (Egress)
  egress:
  - to:
    # Разрешить трафик к подам с меткой app: database
    - podSelector:
        matchLabels:
          app: database
    ports:
    - protocol: TCP
      port: 5432
```

### Дополнительная информация: Типичные ошибки

- **Слишком общие правила**: Использование `0.0.0.0/0` (any) там, где можно указать конкретную подсеть.
- **Отсутствие Egress-контроля**: Распространенная ошибка, которая позволяет скомпрометированному приложению беспрепятственно связываться с командными центрами злоумышленников.
- **Неправильный порядок правил**: В `iptables` первое совпавшее правило выигрывает. Слишком общее правило в начале может сделать последующие, более конкретные правила, бесполезными.
- **Конфликт `NAT` и `filter`**: Непонимание порядка обработки пакетов в таблицах Netfilter может привести к тому, что правила фильтрации не сработают так, как ожидается.
- **Отсутствие логирования `DROP`**: Сильно затрудняет отладку проблем с доступом и обнаружение атак.
