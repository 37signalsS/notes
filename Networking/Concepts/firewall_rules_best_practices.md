# Контроль доступа на уровне сети: лучшие практики и правила Firewall

## Определения

**Контроль доступа на уровне сети** — это применение правил на межсетевых экранах (файрволах) для определения, какой трафик разрешен, а какой блокируется. Правила анализируют параметры потока (IP-адреса, порты, протоколы) и, в случае stateful-подхода, состояние соединения.

В контексте [архитектуры Zero Trust](./zero_trust_overview.md) ключевыми принципами являются:
*   **Явное разрешение (Allowlist):** Разрешен только тот трафик, который явно необходим.
*   **Запрет по умолчанию (Default Deny):** Весь остальной трафик блокируется.
*   **Контроль исходящего трафика (Egress Control):** Строгий контроль над тем, куда сервисы могут инициировать соединения.

## Модели и типы фильтрации

| Критерий | Stateless | Stateful | L3/4 | L7 (WAF/NGFW) | Хостовый | Периферийный |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Контекст** | Минимальный | Состояние сессии | IP/порт | Семантика протокола | Локальный процесс | Сегмент/сеть |
| **Производительность** | Высокая | Ниже | Высокая | Ниже | Зависит от узла | Централизованная |
| **Точность** | Грубая | Выше | Грубая | Точная | Микросегментация | Макросегментация |

*   **Уровни:** L3/L4 (IP/порт) vs L7 (HTTP, DNS). L7-фильтрация дает больше контекста, но требует больше ресурсов.
*   **Состояние:** `stateless` файрволы быстрее, но `stateful` значительно упрощают правила, автоматически отслеживая установленные соединения (`ESTABLISHED`, `RELATED`).
*   **Размещение:**
    *   **Периферийный:** На границе сети или между сегментами.
    *   **Хостовый:** Непосредственно на каждом узле, ВМ или поде, обеспечивая последнюю линию защиты.
*   **Направления:**
    *   **Ingress (входящий):** Контроль доступа к сервисам.
    *   **Egress (исходящий):** Контроль доступа сервисов к внешним ресурсам. В Zero Trust так же важен, как и ingress.

## Практики проектирования правил

1.  **Политика по умолчанию `DROP`:** Начинайте с полного запрета входящего, исходящего и транзитного трафика.
2.  **Минимальные разрешения:** Добавляйте только те правила, которые абсолютно необходимы для работы сервиса.
3.  **Используйте Allowlist, а не Blocklist:** Явно разрешайте нужный трафик, а не пытайтесь заблокировать известный плохой.
4.  **Контролируйте Egress:** Четко определите, к каким внешним ресурсам (DNS-серверы, репозитории, API) вашим сервисам нужен доступ.
5.  **Раздельные слои:** Используйте комбинацию периферийных и хостовых файрволов для многоуровневой защиты.
6.  **Учитывайте `ESTABLISHED,RELATED`:** В `stateful` файрволах это позволяет не открывать лишние порты для ответного трафика.
7.  **Логирование:** Включите логирование для заблокированных пакетов (с ограничением частоты, чтобы избежать переполнения логов) для выявления аномалий и отладки правил.
8.  **Управление как кодом (IaC):** Храните конфигурацию файрвола в системе контроля версий (Ansible, Terraform) для аудита, версионирования и автоматического развертывания.
9.  **Используйте теги в облаках:** Вместо жестко заданных IP-адресов используйте теги или идентификаторы ресурсов (например, в Security Groups), где это возможно.
10. **NetworkPolicy в Kubernetes:** Применяйте `NetworkPolicy` для контроля трафика между подами (pod-to-pod) и для egress-контроля.

## Примеры правил

### Хостовый `iptables` (Stateful, Default Deny)

Этот пример настраивает файрвол на сервере, который разрешает только SSH из определенной подсети, входящий HTTPS и исходящие DNS и HTTPS.

```bash
# 1. Установить политику по умолчанию на DROP
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT DROP

# 2. Разрешить трафик для loopback-интерфейса
iptables -A INPUT  -i lo -j ACCEPT
iptables -A OUTPUT -o lo -j ACCEPT

# 3. Разрешить ответный трафик для уже установленных соединений
iptables -A INPUT  -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
iptables -A OUTPUT -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT

# 4. Ingress: разрешить SSH только из админ-подсети
iptables -A INPUT -p tcp --dport 22 -s 10.10.0.0/24 -j ACCEPT

# 5. Ingress: разрешить HTTPS для веб-сервера
iptables -A INPUT -p tcp --dport 443 -j ACCEPT

# 6. Egress: разрешить исходящие DNS и HTTPS
iptables -A OUTPUT -p udp --dport 53 -d 10.10.10.53 -j ACCEPT
iptables -A OUTPUT -p tcp --dport 443 -j ACCEPT
```

### Kubernetes NetworkPolicy

Эта политика разрешает входящий трафик к подам с меткой `app: web` только от ingress-шлюза, а исходящий — только к DNS и бэкенд-сервисам.

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: web-strict
spec:
  podSelector:
    matchLabels:
      app: web
  policyTypes: ["Ingress", "Egress"]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          role: ingress
    ports:
    - protocol: TCP
      port: 443
  egress:
  - to:
    - ipBlock:
        cidr: 10.10.10.53/32
    ports:
    - protocol: UDP
      port: 53
  - to:
    - podSelector:
        matchLabels:
          app: backend
    ports:
    - protocol: TCP
      port: 8443
```

## Типичные ошибки и подводные камни

*   **Правила "any-any":** Использование `0.0.0.0/0` для доступа к административным портам.
*   **Отсутствие Egress-контроля:** Позволяет скомпрометированному сервису бесконтрольно связываться с внешними сетями.
*   **Неверный порядок правил:** В `iptables` порядок имеет значение. Неправильно расположенное правило может быть "затенено" более общим правилом.
*   **Асимметричная маршрутизация:** Может приводить к разрыву `stateful`-сессий, так как ответный трафик идет через другой файрвол.
*   **Конфликты NAT и фильтрации:** Неправильное применение правил в цепочках `nat` и `filter` может привести к непредсказуемому поведению.
*   **Отсутствие логирования `DROP`:** Затрудняет отладку и обнаружение нелегитимных попыток доступа.
