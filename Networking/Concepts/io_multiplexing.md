# Мультиплексирование ввода-вывода (I/O Multiplexing)

## Определения

- **Мультиплексирование ввода-вывода (I/O Multiplexing):** Механизм, позволяющий одному потоку эффективно управлять множеством соединений путем мониторинга множества файловых дескрипторов (сокетов) и уведомления приложения о готовности к чтению или записи. Решает проблему блокирующего ввода-вывода.
- **Блокирующий ввод-вывод:** Операция ввода-вывода (например, `read()`), которая приостанавливает выполнение процесса до тех пор, пока данные не будут получены или отправлены.
- **Проблема C10k:** Историческая проблема эффективной обработки 10 000 и более одновременных соединений одним сервером.

## Основные концепции

### Классические механизмы: `select()` и `poll()`

Традиционные POSIX-совместимые механизмы для I/O мультиплексирования.

- **Принцип работы:** Приложение передает ядру список файловых дескрипторов для отслеживания. Ядро периодически сканирует этот список и возвращает те дескрипторы, которые готовы к выполнению операции ввода-вывода.
- **Недостатки:**
  - **Сложность O(n):** При каждом вызове ядро выполняет линейное сканирование всего списка дескрипторов, что неэффективно при большом их числе.
  - **Ограничение на количество дескрипторов:** `select()` имеет жесткое ограничение (обычно 1024), что делает его непригодным для решения проблемы C10k.

### Современный механизм в Linux: `epoll`

Специфичный для Linux механизм, разработанный для высокопроизводительных сетевых приложений (например, Nginx, Node.js) и эффективно решающий проблему C10k.

- **Сложность O(1):** Вместо повторной передачи всего списка, дескрипторы регистрируются в инстансе `epoll` один раз. Ядро самостоятельно отслеживает их состояние и при вызове `epoll_wait()` мгновенно возвращает только список дескрипторов, готовых к операциям.
- **Событийно-ориентированный подход (Event-driven):** Ядро уведомляет приложение только о произошедших событиях, а не заставляет его постоянно опрашивать состояние дескрипторов.
- **Режимы работы:**
  - **Level-triggered (по умолчанию):** `epoll` продолжает сообщать о готовности дескриптора до тех пор, пока все доступные данные не будут вычитаны (или данные не будут полностью записаны).
  - **Edge-triggered (`EPOLLET`):** `epoll` уведомляет о событии **только один раз** при изменении состояния дескриптора (например, при появлении новых данных в пустом буфере). Этот режим требует более внимательного программирования, но обеспечивает максимальную производительность.

## Практические сценарии

- **Высокопроизводительные серверы:** Механизмы I/O мультиплексирования, особенно `epoll`, являются основой для работы современных веб-серверов (таких как Nginx, Apache с MPM Event), прокси-серверов, баз данных и других сетевых приложений, которым необходимо обрабатывать тысячи одновременных соединений с минимальным потреблением ресурсов.
- **Event-driven архитектуры:** Использование событийных механизмов позволяет строить неблокирующие системы, где приложение реагирует на события, а не ждет их.

### Применение в современных системах

- **Nginx/Angie:** Используют `epoll` (Linux), `kqueue` (FreeBSD/macOS), `IOCP` (Windows) для асинхронной обработки соединений.
- **Node.js:** Event-driven архитектура на основе `epoll`/`kqueue`.
- **Redis:** Однопоточный сервер, использующий I/O мультиплексирование для высокой производительности.
