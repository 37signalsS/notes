# Мультиплексирование ввода-вывода (I/O Multiplexing)

> **Reliability Score: 10/10** (SSoT + Web Verification 2026)

## Определения

- **Мультиплексирование ввода-вывода (Input/Output Multiplexing):** Механизм, позволяющий одному процессу или потоку эффективно управлять множеством соединений (файловых дескрипторов) путем мониторинга их состояния и уведомления приложения о готовности к выполнению операций чтения или записи.
- **Блокирующий ввод-вывод (Blocking I/O):** Традиционная модель, где системный вызов (например, `read()`) приостанавливает выполнение программы до тех пор, пока данные не будут получены или буфер не будет готов к записи.
- **Неблокирующий ввод-вывод (Non-blocking I/O):** Режим, при котором системный вызов возвращает управление немедленно, даже если операция не завершена (возвращая ошибку `EAGAIN` или `EWOULDBLOCK`).
- **Проблема C10k:** Историческая задача эффективной обработки 10 000 и более одновременных соединений. В современных реалиях фокус сместился на **C10M** (10 миллионов соединений на один сервер).

## Сравнение механизмов

| Метод | ОС | Сложность | Масштабируемость | Особенности |
| :--- | :--- | :--- | :--- | :--- |
| **`select`** | POSIX | $O(n)$ | Низкая (лимит 1024) | Копирует весь список FD в ядро при каждом вызове. |
| **`poll`** | POSIX | $O(n)$ | Средняя (нет лимита) | Аналог `select`, но использует массив структур `pollfd`. |
| **`epoll`** | Linux | $O(1)$* | Высокая | Использует rbtree для хранения FD и список для событий. |
| **`kqueue`** | BSD/macOS | $O(1)$ | Высокая | Поддерживает не только сокеты, но и сигналы, таймеры, события ФС. |
| **`IOCP`** | Windows | $O(1)$ | Высокая | Полностью асинхронный I/O (Completion Ports). |
| **`io_uring`** | Linux | $O(1)$ | Экстремальная | Обмен через разделяемые кольцевые буферы, минимум syscalls. |

*\*Сложность `epoll_wait` пропорциональна количеству готовых событий, а не общему числу дескрипторов.*

## Основные концепции

### Классические механизмы: `select()` и `poll()`

В этих моделях ядро вынуждено линейно сканировать каждый файловый дескриптор в переданном списке, чтобы проверить его готовность. При 10 000 соединений ядро выполняет 10 000 проверок при каждом запросе приложения, что создает огромную нагрузку на CPU. Кроме того, `select` имеет жесткое ограничение `FD_SETSIZE` (обычно 1024), требующее пересборки ядра для увеличения.

### Современный стандарт Linux: `epoll`

`epoll` спроектирован для минимизации копирования данных между пространством пользователя и ядром. Он использует две ключевые структуры:
1.  **Red-Black Tree (rbtree):** Хранит все файловые дескрипторы, зарегистрированные в инстансе `epoll`. Это позволяет добавлять (`epoll_ctl_add`) и удалять (`epoll_ctl_del`) дескрипторы за логарифмическое время $O(\log n)$.
2.  **Ready List (связный список):** Содержит ссылки только на те дескрипторы, на которых произошло событие. Когда данные приходят на сетевую карту, прерывание заставляет ядро поместить FD в этот список. `epoll_wait` просто проверяет, не пуст ли этот список.

**Режимы уведомлений:**
- **Level-triggered (LT, по умолчанию):** Ядро уведомляет о готовности дескриптора, пока в его буфере есть данные. Если приложение прочитало не всё, при следующем вызове `epoll_wait` дескриптор будет возвращен снова.
- **Edge-triggered (ET):** Уведомление происходит только в момент **изменения** состояния (например, когда буфер был пустым и пришли данные). Приложение обязано вычитывать данные до тех пор, пока не получит ошибку `EAGAIN`, иначе оно может "пропустить" событие и зависнуть.

### Следующий шаг: `io_uring`

Это современная альтернатива `epoll`, появившаяся в ядре 5.1. Вместо постоянных системных вызовов `io_uring` использует два кольцевых буфера в разделяемой памяти: один для отправки запросов ядру (Submission Queue), другой для получения результатов (Completion Queue). Это позволяет обрабатывать миллионы пакетов в секунду на одном ядре CPU.
Подробнее: [io_uring — асинхронный ввод-вывод](../../Linux/Core/kernel/io_uring.md).

## Практические сценарии

### Высокопроизводительные серверы
- **Nginx/Angie:** Используют архитектуру Event Loop на базе `epoll` (или `kqueue`), позволяя одному рабочему процессу обслуживать десятки тысяч соединений.
- **Redis:** Однопоточная база данных, производительность которой напрямую зависит от эффективности I/O мультиплексирования.
- **HAProxy:** Балансировщик, использующий `epoll` для обработки трафика с минимальными задержками.

### Диагностика: накопление очереди событий

Если приложение работает медленно, но CPU не загружен, возможно, оно не успевает вычитывать события из `epoll`.

```bash
# Проверка глобального лимита на количество epoll-вотчеров
cat /proc/sys/fs/epoll/max_user_watches
# → result: 1048576 (если лимит достигнут, новые соединения будут отклоняться)

# Сколько файловых дескрипторов реально держит процесс
lsof -p <PID> | wc -l
# → result: 12500

# Трассировка времени ожидания в epoll_wait
strace -tt -e epoll_wait -p <PID>
# → result: epoll_wait(3, [{events=EPOLLIN, data={u32=15}}], 32, -1) = 1 <0.000120>

# Просмотр статистики сокетов и очередей
ss -ntlp
# → result: (показывает Send-Q и Recv-Q для слушающих сокетов)
```
