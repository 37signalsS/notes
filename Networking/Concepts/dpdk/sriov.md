# Обзор SR-IOV (Single Root I/O Virtualization)

### Определения

- **SR-IOV (Single Root I/O Virtualization)**: Спецификация интерфейса PCIe, разработанная PCI-SIG (релиз 1.1, 2010), которая позволяет одному физическому устройству (Physical Function, PF) представляться системе как несколько независимых виртуальных устройств (Virtual Functions, VF). Является стандартом де-факто для аппаратного разделения сетевых адаптеров в виртуализированных средах.
- **Physical Function (PF)**: Полнофункциональная PCI-функция, которая поддерживает спецификацию SR-IOV. PF обладает полным доступом к ресурсам устройства (включая конфигурационное пространство, BAR-регистры и DMA) и используется для настройки, управления и создания виртуальных функций. PF управляет встроенным L2-коммутатором NIC и контролирует политики безопасности для всех VF.
- **Virtual Function (VF)**: «Облегченная» PCI-функция, предназначенная исключительно для передачи данных. VF имеет собственный конфигурационный заголовок PCI, уникальный BDF (Bus/Device/Function) адрес, независимые очереди приёма/передачи и DMA-каналы, но зависит от PF в плане глобальной конфигурации. Каждая VF может быть передана отдельной ВМ или контейнеру.
- **IOMMU (Input-Output Memory Management Unit)**: Аппаратный блок (VT-d у Intel, AMD-Vi у AMD), который транслирует адреса ввода-вывода (IOVA) в физические адреса памяти (HPA). Необходим для безопасной изоляции памяти VF и предотвращения несанкционированного DMA-доступа между ВМ.
- **IOTLB (I/O TLB)**: Буфер трансляции адресов IOMMU, кэширующий последнюю трансляцию IOVA → HPA. Промахи IOTLB (IOTLB miss) вызывают обращение к страницам трансляции в памяти, что увеличивает задержку DMA-операций. Использование HugePages снижает количество промахов за счёт уменьшения числа записей в таблицах трансляции.
- **vDPA (vHost Data Path Acceleration)**: Гибридная технология, которая сохраняет стандартную плоскость управления VirtIO (для совместимости с гостевыми ОС), но ускоряет плоскость передачи данных за счёт прямого взаимодействия с оборудованием (SR-IOV NIC). Позволяет достичь производительности SR-IOV при сохранении возможности live-миграции.
- **SIOV (Scalable I/O Virtualization)**: Механизм, определённый в PCIe Base Specification 6.4/7.0 как преемник SR-IOV, предназначенный для гипермасштабных сред. Вводит понятие Scalable Device Interface (SDI) — облегчённых виртуальных интерфейсов без собственного конфигурационного пространства, BAR и MSI-X таблицы, что позволяет создавать тысячи интерфейсов на одно устройство с минимальными накладными расходами на кремний.
- **FLR (Function Level Reset)**: Механизм сброса отдельной PCI-функции без влияния на другие функции устройства. Используется для инициализации VF перед передачей ВМ или для восстановления VF после ошибки. Поддерживается всеми современными SR-IOV NIC.
- **MSI-X (Message Signaled Interrupts Extended)**: Механизм прерываний PCI, позволяющий каждой VF иметь независимый набор прерываний. Каждая очередь приёма/передачи VF привязана к отдельному прерыванию, что обеспечивает параллельную обработку на разных ядрах CPU.
- **NUMA (Non-Uniform Memory Access)**: Архитектура организации памяти в многосокетных системах, при которой каждый CPU имеет локальную память. Доступ к памяти удалённого NUMA-узла связан с дополнительной задержкой (через interconnect QPI/UPI). Для SR-IOV критически важно, чтобы VF и использующие её ВМ/контейнеры находились в одном NUMA-узле с сетевым адаптером.
- **PCIe Gen6**: Стандарт шины 2026 года со скоростью до 64 GT/s на линию, использующий модуляцию PAM4 и кодирование FLIT. Обеспечивает пропускную способность, критически важную для 800G-сетей и ИИ-фабрик. Включает улучшенную интеграцию SR-IOV и поддержку Scalable IOV.

### Архитектура и основные принципы

#### Проблема программной виртуализации
В стандартных схемах виртуализации (например, с использованием мостов Linux или Open vSwitch в режиме ядра) каждый пакет проходит через стек гипервизора:
1. Пакет поступает на NIC.
2. Генерируется прерывание процессора (softirq).
3. Гипервизор копирует пакет из памяти NIC в память ВМ (минимум 2 копирования).
4. Выполняется переключение контекста.
Это приводит к высокой нагрузке на CPU (40-60% при 10G), нестабильным задержкам (jitter) и ограничению пропускной способности. На скоростях 100G+ программный стек становится узким местом.

#### Аппаратное разделение ресурсов
SR-IOV переносит логику коммутации пакетов непосредственно на чип сетевого адаптера, исключая процессор хоста из пути данных (Data Path).

1.  **Встроенный L2-коммутатор (NIC Switch)**: Аппаратный блок внутри NIC, выполняющий фильтрацию и классификацию пакетов по MAC-адресам, VLAN-тегам и Classifier-TCAM правилам. Пакеты маршрутизируются напрямую из порта вверх по PCIe-шине к нужной VF, минуя PF и ядро ОС.
2.  **Прямой доступ к памяти (DMA)**: Каждая VF взаимодействует напрямую с памятью виртуальной машины через DMA-движок NIC. Сетевая карта записывает пакеты в память ВМ (или буфер DPDK-приложения), минуя процессор хоста и SYSRAM.
3.  **Изоляция через BAR**: Каждая VF имеет собственный конфигурационный заголовок и набор Base Address Register (BAR), что позволяет ОС/гипервизору регистрировать их как независимые PCI-устройства. VF получает собственный BDF-адрес (например, `0000:01:00.2`).
4.  **Независимые очереди DMA**: Каждая VF имеет отправные (TX) и receiving (RX) очереди с собственными кольцевыми буферами (descriptor rings) в памяти. Количество очередей VF определяется прошивкой NIC и обычно составляет от 1 до 16 очередей на VF.

#### Ограничения и ресурсы VF

Количество VF, которые можно создать на одном PF, ограничено несколькими факторами:

- **Конфигурационное пространство PCI**: Каждая VF требует уникального BDF-адреса. Стандарт PCI определяет максимум 8 функций на устройство (3 бита Function Number), но через ARI (Alternative Routing ID) поддерживается до 256 функций на устройство.
- **BAR-ресурсы**: VF используют выделенные BAR-регистры (SR-IOV BARs), отличные от BAR PF. Стандарт определяет до 6 BAR на VF. Каждый VF требует фиксированного объёма MMIO-пространства, выделяемого из резерва PF при включении SR-IOV. Типичные VF требуют 1-2 MB BAR-пространства.
- **Аппаратные ресурсы NIC**: Количество доступных TCAM-записей (фильтры), очередей DMA и внутренних буферов NIC распределяется между всеми VF. Переизбыточное создание VF может привести к деградации производительности.
- **Практические лимиты**: Большинство современных NIC (Intel E810, NVIDIA ConnectX-7) поддерживают до 64-256 VF на PF, однако реальная рекомендуемая величина обычно не превышает 16-64 VF в зависимости от сценария использования.

#### Пакетный путь (Packet Path) в SR-IOV

Входящий пакет проходит следующий путь внутри NIC:

```
Физический порт → MAC → RX Parser → Classifier (TCAM)
    → NIC Switch (L2 коммутация по MAC/VLAN)
        → DMA Engine → BAR/VF Queue → PCIe Bus → Память VF (ВМ/Контейнер)
```

Исходящий пакет:

```
Память VF → DMA Engine → TX Queue VF → TX Parser
    → MAC → Физический порт
```

Ключевой момент: на всём пути данных процессор хоста не участвует. Ядро ОС задействовано только при первичной настройке VF и обработке контрольных событий (изменение состояния линка, ошибки AER).

### NUMA-зависимость и оптимизация производительности

В многосокетных серверах (2-4 CPU) архитектура NUMA оказывает критическое влияние на производительность SR-IOV. Каждый физический сокет CPU образует отдельный NUMA-узел со своей локальной памятью и линиями PCI-шины.

#### Проблема удалённого NUMA-доступа

Если сетевой адаптер подключён к PCIe-шине NUMA-узла 0, а виртуальная машина с VF запущена на CPU NUMA-узла 1, каждый DMA-пакет проходит через interconnect (QPI/UPI/Infinity Fabric), что добавляет:
- **30-100 нс задержки** на каждый пакет (в зависимости от архитектуры CPU и загрузки interconnect).
- **Снижение пропускной способности** на 15-30% при высокой нагрузке из-за конкуренции за полосу interconnect.
- **Нестабильность задержек (jitter)**: В периоды высокой нагрузки на interconnect пакеты могут испытывать квантовые задержки, что критично для HFT и телеком-сценариев.

#### Проверка NUMA-локальности

```bash
# Определение NUMA-узла сетевого адаптера
cat /sys/class/net/<interface>/device/numa_node
# → 0 (адаптер подключён к NUMA-узлу 0)

# Проверка NUMA-топологии системы
lscpu | grep -i numa
# → NUMA node(s):        2
# → NUMA node0 CPU(s):   0-31
# → NUMA node1 CPU(s):   32-63

# Проверка PCI-устройства в контексте NUMA
cat /sys/bus/pci/devices/0000:01:00.0/numa_node
```

#### Рекомендации по оптимизации

1. **Привязка ВМ к локальному NUMA-узлу**: Запускайте ВМ с VF строго на тех ядрах CPU, которые принадлежат тому же NUMA-узлу, что и сетевой адаптер.
2. **CPU Pinning**: Используйте `cpuset` или `taskset` для привязки процессов обработки пакетов к ядрам локального NUMA-узла.
3. **HugePages в локальном NUMA**: Выделяйте HugePages на том же NUMA-узле, что и VF:
   ```bash
   # Выделение 1GB HugePages на NUMA-узле 0
   echo 4 > /sys/devices/system/node/node0/hugepages/hugepages-1048576kB/nr_hugepages
   ```
4. **IRQ Affinity**: Привязывайте прерывания VF к ядрам локального NUMA-узла:
   ```bash
   # Просмотр прерываний VF
   cat /proc/interrupts | grep <vf_pci_addr>

   # Привязка IRQ к ядрам NUMA-узла 0 (0-31)
   echo 1 > /proc/irq/<irq_number>/smp_affinity_list
   ```
5. **Изоляция ядер (HFT)**: Для ультра-низких задержек выделите изолированные ядра CPU исключительно под обработку пакетов VF с отключением прерываний и планировщика:
   ```bash
   # Параметр ядра: isolcpus=32-35 nohz_full=32-35 rcu_nocbs=32-35
   ```

### Интеграция с KVM/QEMU

SR-IOV VF может быть напрямую передан виртуальной машине KVM для достижения производительности уровня bare-metal.

#### Проброс VF в ВМ через virsh

```bash
# 1. Найти PCI-адрес созданной VF
lspci | grep -i "Virtual Function"
# → 0000:01:00.2 Ethernet controller: Intel Corporation Ethernet Controller E810

# 2. Присоединить VF к запущенной ВМ (hot-plug)
sudo virsh attach-interface <vm_name> hostdev 0000:01:00.2 \
  --mac 52:54:00:00:01:01 --managed --live --config

# 3. Проверить наличие VF внутри ВМ
virsh domiflist <vm_name>
```

#### Конфигурация через XML (постоянная)

```xml
<hostdev mode='subsystem' type='pci' managed='yes'>
  <source>
    <address domain='0x0000' bus='0x01' slot='0x00' function='0x2'/>
  </source>
  <alias name='hostdev0'/>
  <address type='pci' domain='0x0000' bus='0x06' slot='0x00' function='0x0'/>
</hostdev>
```

#### Живая миграция с SR-IOV VF (net_failover)

Для сохранения возможности live-миграции ВМ с прямым доступом к VF используется механизм **net_failover** (также известный как virtio-net standby). Он объединяет VF (primary) и virtio-net (standby) в логический bond:

1. **Обычный режим**: Трафик идёт через VF (максимальная производительность).
2. **Перед миграцией**: Гипервизор отключает VF (hot-unplug), трафик автоматически переключается на virtio-net.
3. **Миграция**: ВМ перемещается на целевой хост с активным virtio-net.
4. **После миграции**: На целевом хосте подключается новая VF, трафик возвращается на аппаратный путь.

```bash
# Пример скрипта миграции (исходный хост)
DOMAIN=vm-01
VF_XML=vf.xml

# Поднять virtio-net standby перед миграцией
virsh domif-setlink $DOMAIN vmtap01 up

# Отключить VF от ВМ
virsh detach-device --live --config $DOMAIN $VF_XML

# Выполнить миграцию
virsh migrate --live --persistent $DOMAIN qemu+ssh://$REMOTE_HOST/system
```

**Важно**: Внутри ВМ должен быть загружен модуль `net_failover`, а оба интерфейса (VF и virtio-net) должны иметь одинаковый MAC-адрес. Гипервизор (QEMU) автоматически управляет горячим подключением/отключением VF через PCIe hotplug.

### Безопасность и изоляция

Использование SR-IOV требует строгих мер контроля, так как VF делят общие физические ресурсы NIC:

- **Изоляция памяти**: Обеспечивается через IOMMU (VT-d/AMD-Vi). Каждая VF получает уникальный IOVA-адресное пространство, изолирующее DMA-операции. ВМ не может получить доступ к памяти хоста или других ВМ через свою VF. IOMMU транслирует IOVA в HPA через таблицы страниц в памяти, кэшируемые в IOTLB.
- **Защита от MAC/VLAN Spoofing**: PF может принудительно устанавливать MAC-адреса и VLAN-теги для VF, запрещая гостевой ОС изменять их ( spoofchk on ). По умолчанию spoof checking включён на всех современных NIC.
- **Rate Limiting (QoS)**: Аппаратное ограничение полосы пропускания (Egress/Ingress) на уровне каждой VF для предотвращения влияния шумных соседей (Noisy Neighbors). Полоса задаётся в Мбит/с через `ip link set ... vf N rate <Mbps>`.
- **Trust Mode**: Управляет уровнем доверия VF. В режиме `trust off` (по умолчанию) VF не может изменять глобальные параметры NIC (promiscuous mode, multicast фильтры). В режиме `trust on` VF получает расширенные привилегии, необходимые для NFV-сценариев.
- **PCIe Error Handling**: Механизм AER (Advanced Error Reporting) позволяет изолировать сбои (uncorrectable errors) в одной VF, не затрагивая работу PF и других VF. При критической ошибке VF выполняется Function Level Reset (FLR), восстанавливающий VF в начальное состояние.
- **Изоляция очередей**: DMA-очереди VF физически разделены в памяти NIC. Одна VF не может читать/писать в очереди другой VF, что обеспечивает аппаратную (а не программную) изоляцию.

### Живая миграция (Live Migration)

Традиционно VF не могут быть мигрированы, поскольку внутреннее состояние NIC (очереди DMA, регистры) является аппаратным и не может быть сохранено/восстановлено гипервизором. Современные механизмы решают эту проблему:

1.  **net_failover (VirtIO Standby)**: Использование «пары» из SR-IOV VF (primary, аппаратный путь) и virtio-net (standby, программный путь). Перед миграцией гипервизор отключает VF через PCIe hot-unplug, трафик автоматически переключается на virtio-net. После миграции на целевом хосте VF подключается заново. Требует: одинаковый MAC-адрес на VF и virtio-net, модуль `net_failover` в гостевой ОС, поддержку VIRTIO_NET_F_STANDBY. Доступно в QEMU 5.0+, KVM, libvirt.
2.  **vDPA State Transfer**: Гибридный подход, сохраняющий плоскость управления VirtIO для совместимости с гостевыми ОС. Ускоряет data path через прямое взаимодействие с SR-IOV NIC, но позволяет переключаться на программный vhost-net при миграции. Поддерживает перенос состояния очередей между разными поколениями и вендорами оборудования (NVIDIA, Intel).
3.  **ASAP2 (Advanced Switching and Parser Pipeline) с OVS**: Режим switchdev, при котором OVS программирует аппаратные правила фильтрации NIC напрямую. При миграции правила переносятся на целевой хост вместе с состоянием ВМ, обеспечивая непрерывность аппаратного ускорения.
4.  **VFIO SR-IOV Variant Driver**: Новый интерфейс ядра Linux (2025+), позволяющий гипервизору сохранять и восстанавливать состояние VF через драйвер-вариант, что делает возможной миграцию VF без привязки к конкретному физическому устройству.
5.  **Hardware Dirty Page Tracking**: Аппаратная поддержка отслеживания «грязных» страниц памяти при DMA-операциях (Intel VT-d Dirty Page Tracking). Сводит время простоя (Downtime) к значениям менее 500 мс даже для 800G-интерфейсов.

### Практические сценарии

- **ИИ-инфраструктуры (AI Fabric)**: Использование **GPUDirect RDMA** через VF для связи памяти GPU разных узлов, минуя CPU и системную память. SR-IOV VF обеспечивает прямой DMA-путь между GPU и сетевым адаптером, что критично для распределённого обучения (All-Reduce операции) на кластерах с InfiniBand/RoCEv2. См. [Практические сценарии](scenarios.md).
- **Телеком (NFV/5G/6G)**: База для работы виртуализированных функций сети (UPF, vCU/vDU), где требуется обработка трафика в реальном времени с минимальными задержками. VF выделяется каждой сетевой функции, обеспечивая изоляцию и производительность уровня bare-metal. Аппаратная разгрузка (checksum offload, RSS) снижает нагрузку на CPU NFV-приложений.
- **Публичные облака**: Предоставление Bare-metal производительности в виртуальной среде с обеспечением жёсткой изоляции клиентов. Каждому арендатору выделяется VF с настроенными политиками QoS и spoof checking, гарантирующими изоляцию трафика.
- **HFT (High-Frequency Trading)**: Ультра-низкая задержка (sub-microsecond) для обработки рыночных данных. VF с изолированными IRQ и привязкой к выделенным ядрам CPU обеспечивает предсказуемую обработку пакетов без вмешательства ядра. См. [Практические сценарии](scenarios.md).
- **Кибербезопасность (IDS/IPS)**: Проброс VF в контейнеры с DPI-приложениями (Suricata, nDPI) для анализа трафика на скоростях 100G+ без потерь пакетов.

| :--- | :--- | :--- | :--- |
| **Реализация** | Программная (Userspace) | Аппаратная (PCIe) | Программная (Ядро, eBPF) |
| **Гибкость** | Максимальная (любая логика на C/Rust) | Ограничена возможностями NIC | Средняя (eBPF-программы) |
| **Нагрузка на CPU** | Постоянная (Polling mode, 100% ядра) | Минимальная (Direct DMA, аппаратная обработка) | Адаптивная (по прерываниям, NAPI polling) |
| **Задержки** | Очень низкие (стабильные, ~1-5 мкс) | Минимально возможные (аппаратные, <1 мкс) | Низкие (~5-15 мкс) |
| **Пропускная способность** | Экстремальная (400G/800G) | Высокая (ограничена возможностями NIC) | Высокая (100G/200G) |
| **Совместимость с ВМ** | Требует DPDK-стека в госте | Прямой проброс VF в ВМ | Невозможен в ВМ (работает в ядре хоста) |
| **Live-миграция** | Не поддерживается | Ограничена (через net_failover/vDPA) | Поддерживается (часть ядра) |
| **Использование памяти** | HugePages (обязательно) | IOMMU + DMA (ограничено BAR VF) | Обычная память ядра |
| **Сценарий применения** | Обработка пакетов в userspace (NFV, HFT) | Прямой доступ ВМ/контейнеров к NIC | Маршрутизация/фильтрация в ядре (DPI, balancing) |

### Диагностика и устранение неисправностей

#### Проверка поддержки и начальная настройка

1.  **Проверка поддержки IOMMU**:
    ```bash
    dmesg | grep -e DMAR -e IOMMU
    # → "DMAR: IOMMU enabled"
    # Если вывод пуст — IOMMU не включён в BIOS или параметрах ядра
    ```

2.  **Проверка включенной поддержки SR-IOV в ядре**:
    ```bash
    modprobe vfio-pci
    lsmod | grep vfio
    # → vfio_pci vfio vfio_iommu_type1
    ```

3.  **Проверка максимального количества VF**:
    ```bash
    cat /sys/class/net/<interface>/device/sriov_totalvfs
    # → 64 (максимум поддерживаемых VF данным NIC)
    ```

#### Управление VF

4.  **Просмотр списка созданных VF**:
    ```bash
    lspci | grep -i "Virtual Function"
    # → 0000:01:00.2 Ethernet controller: Intel Corporation ...
    # → 0000:01:00.3 Ethernet controller: Intel Corporation ...
    ```

5.  **Проверка состояния VF через sysfs**:
    ```bash
    cat /sys/class/net/<interface>/device/sriov_numvfs
    # → 2 (создано 2 VF)
    ```

6.  **Настройка параметров VF через ip link**:
    ```bash
    # Просмотр всех VF с их параметрами
    ip link show <interface>
    # → vf 0 MAC 00:00:00:00:00:00, vlan 0, spoofchk on, trust off, rate unlimited

    # Назначение MAC и VLAN для VF
    sudo ip link set <interface> vf 0 mac 52:54:00:00:01:01 vlan 100

    # Включение trust mode (для NFV)
    sudo ip link set <interface> vf 0 trust on

    # Ограничение полосы (10 Гбит/с)
    sudo ip link set <interface> vf 0 rate 10000
    ```

#### NUMA и IRQ Affinity

7.  **Определение NUMA-узла VF**:
    ```bash
    cat /sys/class/net/<interface>/device/numa_node
    # → 0

    # Проверка, на каких ядрах обрабатываются прерывания VF
    cat /proc/interrupts | grep <vf_pci_addr>
    # → 48:  ... PCI-MSI-edge  enp1s0f0-TxRx-0
    # → 49:  ... PCI-MSI-edge  enp1s0f0-TxRx-1
    ```

8.  **Настройка IRQ Affinity для NUMA-локальности**:
    ```bash
    # Найти номер IRQ для очереди VF
    grep <vf_pci_addr> /proc/interrupts | awk '{print $1}' | tr -d ':'
    # → 48

    # Привязать IRQ к ядрам NUMA-узла 0 (битовая маска для ядер 0-7: ff)
    echo ff > /proc/irq/48/smp_affinity

    # Или через список ядер
    echo 0-7 > /proc/irq/48/smp_affinity_list
    ```

#### Типичные проблемы и решения

| Проблема | Симптом | Причина | Решение |
| :--- | :--- | :--- | :--- |
| VF не создаются | `echo N > sriov_numvfs` возвращает ошибку | Нехватка BAR-ресурсов PCIe или IOMMU не включён | Проверьте `dmesg` на ошибки IOMMU; попробуйте параметр ядра `pci=realloc`; уменьшите количество VF |
| VF не видна в ВМ | `lspci` в ВМ не показывает устройство | Некорректный пропуск VF через vfio-pci или libvirt | Проверьте XML-конфигурацию ВМ; убедитесь в `managed=yes` для hostdev |
| Низкая производительность VF | p99 задержка выше ожиданий, низкий throughput | NUMA-несоответствие, IRQ не привязаны, IOTLB misses | Проверьте NUMA-локальность; привязьте IRQ; используйте HugePages |
| VF исчезает после перезагрузки | VF не создаются автоматически | Нет конфигурации персистентности | Настройте Netplan, systemd-networkd или udev-rule (см. [Настройка SR-IOV](sriov_setup.md)) |
| Ошибки AER в dmesg | `pcieport ... AER ... Correctable/Uncorrectable error` | Проблемы с PCIe-шиной, нестабильная прошивка NIC | Обновите прошивку NIC; проверьте физическое подключение; попробуйте FLR через `remove`/`rescan` PCI-устройства |
| IOTLB miss rate высокий | Высокая CPU нагрузка в `iommu_fault_handler` | Фрагментированная память VF, отсутствие HugePages | Включите HugePages; закрепите память (mlock); используйте `iommu=pt` для хостовых устройств |

#### Принудительный сброс VF (FLR)

```bash
# Через sysfs — удалить и восстановить VF
echo 0 > /sys/class/net/<interface>/device/sriov_numvfs
echo <N> > /sys/class/net/<interface>/device/sriov_numvfs

# Через PCI remove/rescan (для сброса устройства)
echo 1 > /sys/bus/pci/devices/0000:01:00.2/remove
echo 1 > /sys/bus/pci/rescan
```
