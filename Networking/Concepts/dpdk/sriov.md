# Обзор SR-IOV (Single Root I/O Virtualization)

## Определения

- **SR-IOV (Single Root I/O Virtualization)**: Спецификация, которая позволяет одному физическому PCIe-устройству (например, сетевой карте) представляться операционной системе как несколько отдельных виртуальных устройств.
- **Physical Function (PF)**: "Полная" функция PCIe, которая включает в себя возможность управления SR-IOV. PF видна хостовой системе (гипервизору) и используется для настройки и управления.
- **Virtual Function (VF)**: "Облегченная" функция PCIe, которая обладает только возможностями для передачи данных. VF можно напрямую "пробросить" (PCI Passthrough) в виртуальную машину или контейнер, предоставляя им почти нативный доступ к железу.

---

## Основные концепции

#### Проблема виртуализации сети без SR-IOV

В традиционной виртуализации сетевой трафик от виртуальной машины (ВМ) проходит через несколько программных слоев в гипервизоре:

1. **Virtio-драйвер** в ВМ отправляет пакеты.
2. **Программный коммутатор** (vSwitch) в гипервизоре (например, OVS или Linux Bridge) обрабатывает и направляет эти пакеты.
3. **Физический драйвер** в гипервизоре отправляет пакеты через реальную сетевую карту.

Этот путь создает задержки (latency) и потребляет ресурсы CPU из-за переключений контекста и копирования данных.

#### Архитектура SR-IOV: Прямой доступ к оборудованию

SR-IOV решает эту проблему, создавая на физической сетевой карте несколько VF, которые можно напрямую подключить к ВМ.

```
┌────────────────────┐      ┌────────────────────┐
│        ВМ 1        │      │        ВМ 2        │
│   (Драйвер VF)     │      │   (Драйвер VF)     │
└─────────┬──────────┘      └──────────┬─────────┘
          │ (PCI Passthrough)          │ (PCI Passthrough)
┌─────────▼────────────────────────────▼─────────┐
│     Физическая сетевая карта с SR-IOV          │
│                                                │
│  ┌─────────────────┐ ┌─────┐ ┌─────┐ ┌─────┐   │
│  │       PF        │ │ VF1 │ │ VF2 │ │ ... │   │
│  │ (Для гипервизора) │ └─────┘ └─────┘ └─────┘   │
│  └─────────────────┘                           │
└────────────────────────────────────────────────┘
```

Трафик от ВМ идет напрямую в VF на сетевой карте, минуя программный коммутатор гипервизора. Это обеспечивает производительность, близкую к "голому железу".

---

## Преимущества использования

1. **Разгрузка гипервизора (Offloading)**: Виртуальные машины работают с сетью напрямую, исключая программные слои эмуляции. Это значительно снижает нагрузку на центральный процессор (CPU) хоста.
2. **Оптимизация ресурсов**: Технология позволяет найти баланс между высокой производительностью (свойственной PCI Passthrough) и возможностью совместного использования одной физической карты несколькими ВМ.
3. **Повышение безопасности**: Аппаратная изоляция виртуальных функций (VF) на уровне PCIe снижает риски вмешательства одной ВМ в сетевой трафик или работу другой ВМ.

## Практические сценарии

### Высоконагруженные среды и финансовые транзакции

В системах, где критически важна минимальная задержка (например, алгоритмическая торговля или межбанковские расчеты), SR-IOV применяется для:

- Предоставления прямого доступа к сетевому интерфейсу для приложений, чувствительных к Latency.
- Использования выделенных VF для разделения трафика управления (PF) и трафика данных (VF).
- Мониторинга производительности каждой ВМ без влияния на общую пропускную способность.

### Сравнение DPDK и SR-IOV

Хотя обе технологии нацелены на производительность, они работают на разных уровнях.

| Критерий | DPDK | SR-IOV |
| :--- | :--- | :--- |
| **Уровень** | Программный (Software) | Аппаратный (Hardware) |
| **Механизм** | Обход ядра в userspace | Прямой доступ к железу (PCI passthrough) |
| **Гибкость** | **Высокая**. Пакеты доступны приложению для любой обработки. | **Низкая**. Функциональность ограничена возможностями NIC. |
| **Требования**| Любая NIC (но лучше с хорошими драйверами) | NIC с аппаратной поддержкой SR-IOV |
| **Live Migration ВМ** | Возможен (с некоторыми оговорками) | Как правило, **не поддерживается**. |

#### Комбинация SR-IOV и DPDK для максимальной производительности

Наилучший результат достигается при их совместном использовании:

1. **SR-IOV** предоставляет VF, который пробрасывается в ВМ или контейнер.
2. **DPDK-приложение**, запущенное внутри, использует этот VF для обработки пакетов в userspace с максимальной скоростью.

```
┌───────────────────────────────────────────┐
│       ВМ / Контейнер                      │
│   ┌───────────────────────────────────┐   │
│   │         DPDK Приложение           │   │
│   └─────────────────┬─────────────────┘   │
└─────────────────────┼─────────────────────┘
                      │ (Прямой доступ к VF)
┌─────────────────────▼─────────────────────┐
│      VF (проброшен в гостевую систему)     │
└─────────────────────┬─────────────────────┘
                      │
┌─────────────────────▼─────────────────────┐
│    Физическая сетевая карта с SR-IOV       │
└───────────────────────────────────────────┘
```

Этот подход является стандартом для Cloud-Native Network Functions (CNF) и других требовательных к производительности сетевых приложений.
