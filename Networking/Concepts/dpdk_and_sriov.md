# DPDK и SR-IOV: Высокопроизводительные сетевые технологии

## Определения

**DPDK (Data Plane Development Kit)** — это набор библиотек и драйверов для быстрой обработки пакетов в userspace, обходя стек ядра Linux. Обеспечивает производительность до миллионов пакетов в секунду на одном ядре CPU.

**SR-IOV (Single Root I/O Virtualization)** — это технология аппаратной виртуализации сетевых адаптеров, позволяющая одному физическому NIC представляться как несколько виртуальных (VF — Virtual Functions) для прямого назначения ВМ или контейнерам.

## DPDK (Data Plane Development Kit)

### Проблема стандартного сетевого стека Linux

```
┌─────────────────────────────────────────────────────────────┐
│                    ПРИЛОЖЕНИЕ (userspace)                   │
└───────────────────────┬─────────────────────────────────────┘
                        │ Системные вызовы (read/write/send/recv)
┌───────────────────────▼─────────────────────────────────────┐
│                      СТЕК TCP/IP (ядро)                     │
│  - Socket layer                                             │
│  - TCP/UDP layer                                            │
│  - IP layer                                                 │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                    ДРАЙВЕР СЕТЕВОЙ КАРТЫ                    │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                    СЕТЕВОЙ АДАПТЕР (NIC)                    │
└─────────────────────────────────────────────────────────────┘
```

**Накладные расходы стандартного стека:**
- Переключение контекста userspace ↔ kernel (syscall overhead)
- Копирование данных между kernel и userspace
- Прерывания (interrupts) для каждого пакета
- Обработка в ядре (scheduling, locking)
- **Результат:** ~1-2 Mpps (million packets per second) на ядро

### Архитектура DPDK

```
┌─────────────────────────────────────────────────────────────┐
│                    ПРИЛОЖЕНИЕ DPDK                          │
│  - Обработка пакетов в userspace                            │
│  - Прямой доступ к памяти NIC                               │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                    DPDK LIBRARIES                           │
│  - EAL (Environment Abstraction Layer)                      │
│  - Mempool (управление памятью)                             │
│  - Ring (lock-free очереди)                                 │
│  - PMD (Poll Mode Drivers)                                  │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│         UIO/VFIO (Userspace I/O) + Hugepages                │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│                    СЕТЕВОЙ АДАПТЕР (NIC)                    │
│         Прямой доступ из userspace!                         │
└─────────────────────────────────────────────────────────────┘
```

### Ключевые компоненты DPDK

| Компонент | Назначение |
|-----------|------------|
| **EAL** | Абстракция от ОС, управление памятью, потоками |
| **Mempool** | Пул фиксированных буферов для пакетов |
| **Ring** | Lock-free кольцевые буферы (очереди) |
| **PMD** | Poll Mode Drivers — драйверы в userspace |
| **MBuf** | Структура для хранения пакетов |
| **Mempool** | Предварительно выделенная память для mbuf |

### Hugepages

DPDK использует hugepages (2MB или 1GB) вместо стандартных 4KB страниц:
- Уменьшает размер TLB (Translation Lookaside Buffer)
- Снижает количество page faults
- Улучшает локальность данных

```bash
# Настройка hugepages
# /etc/sysctl.conf
vm.nr_hugepages = 1024

# Проверка
cat /proc/meminfo | grep Huge
```

### PMD (Poll Mode Drivers)

Вместо прерываний DPDK использует polling:

```c
// Пример polling loop в DPDK
while (1) {
    // Прием пакетов (не блокируется!)
    nb_rx = rte_eth_rx_burst(port_id, queue_id, rx_pkts, BURST_SIZE);
    
    if (nb_rx > 0) {
        // Обработка пакетов
        process_packets(rx_pkts, nb_rx);
    }
    
    // Отправка пакетов
    rte_eth_tx_burst(port_id, queue_id, tx_pkts, nb_tx);
}
```

**Преимущества polling:**
- Нет overhead от прерываний
- Предсказуемая задержка (latency)
- Максимальная пропускная способность

**Недостатки:**
- 100% загрузка CPU ядра
- Неэффективен при низкой нагрузке

### Производительность DPDK

| Метрика | Linux Kernel | DPDK | Улучшение |
|---------|--------------|------|-----------|
| **Throughput** | 1-2 Mpps | 100+ Mpps | 50-100x |
| **Latency** | 10-50 μs | 1-5 μs | 10x |
| **Jitter** | Высокий | Низкий | Стабильнее |
| **CPU per packet** | Высокое | Минимальное | Эффективнее |

### Использование DPDK

**Сценарии применения:**
- NFV (Network Function Virtualization)
- Виртуальные маршрутизаторы (vRouter)
- Load balancers
- 5G packet core
- IPS/IDS высокой производительности
- High-frequency trading

**Примеры продуктов на DPDK:**
- VPP (Vector Packet Processing) от Cisco
- OVS-DPDK (Open vSwitch with DPDK)
- DPDK-based NAT
- Telecom applications

## SR-IOV (Single Root I/O Virtualization)

### Проблема виртуализации сети

```
┌─────────────────────────────────────────────────────────────┐
│                    VM 1                                     │
│  ┌─────────────────────────────────────────────────────┐    │
│  │                 virtio-net                          │    │
│  └─────────────────────┬───────────────────────────────┘    │
└────────────────────────┼────────────────────────────────────┘
                         │ Переключение контекста
┌────────────────────────┼────────────────────────────────────┐
│  HYPERVISOR (KVM)      │                                    │
│  ┌─────────────────────▼───────────────────────────────┐    │
│  │              vSwitch (OVS/linux bridge)             │    │
│  └─────────────────────┬───────────────────────────────┘    │
└────────────────────────┼────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────┐
│              ФИЗИЧЕСКИЙ NIC                                 │
└─────────────────────────────────────────────────────────────┘

Накладные расходы: 
- Переключение VM → Hypervisor
- Обработка в vSwitch
- Копирование данных
```

### SR-IOV Архитектура

```
┌─────────────────────────────────────────────────────────────┐
│                    VM 1                                     │
│  ┌─────────────────────────────────────────────────────┐    │
│  │                 VF Driver                           │    │
│  └─────────────────────┬───────────────────────────────┘    │
└────────────────────────┼────────────────────────────────────┘
                         │ Прямой доступ к VF (PCI passthrough)
┌────────────────────────┼────────────────────────────────────┐
│  HYPERVISOR (KVM)      │                                    │
│                        │ VF - Virtual Function              │
└────────────────────────┼────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────┐
│              ФИЗИЧЕСКИЙ NIC с SR-IOV                         │
│  ┌─────────────────────────────────────────────────────┐    │
│  │  PF (Physical Function) - управление                │    │
│  │  ┌─────┬─────┬─────┬─────┐                          │    │
│  │  │ VF0 │ VF1 │ VF2 │ VF3 │  Virtual Functions       │    │
│  │  └─────┴─────┴─────┴─────┘                          │    │
│  └─────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘

Результат: VM напрямую работает с виртуальным NIC!
```

### VF (Virtual Functions) и PF (Physical Function)

**Physical Function (PF):**
- Полнофункциональный PCIe-функция
- Доступен хосту (hypervisor)
- Управление конфигурацией SR-IOV
- Может создавать VF

**Virtual Function (VF):**
- "Облегченный" PCIe-функция
- Только для передачи данных
- Назначается ВМ напрямую (PCI passthrough)
- Каждая ВМ видит VF как отдельный NIC

### Настройка SR-IOV

```bash
# 1. Включить SR-IOV в BIOS

# 2. Загрузить модуль ядра
modprobe vfio-pci

# 3. Включить SR-IOV на NIC (пример Intel)
echo 4 > /sys/class/net/eth0/device/sriov_numvfs

# 4. Проверка созданных VF
lspci | grep Eth

# 5. Привязка VF к VFIO (для passthrough)
devbind.py --bind=vfio-pci 0000:04:10.0

# 6. Назначение VM в libvirt
<hostdev mode='subsystem' type='pci' managed='yes'>
  <source>
    <address domain='0x0000' bus='0x04' slot='0x10' function='0x0'/>
  </source>
</hostdev>
```

### Сравнение DPDK и SR-IOV

| Критерий | DPDK | SR-IOV |
|----------|------|--------|
| **Уровень** | Software (userspace) | Hardware (NIC) |
| **Требования** | Любой NIC + Hugepages | Поддержка SR-IOV в NIC |
| **Производительность** | Очень высокая | Максимальная (близка к bare metal) |
| **Гибкость** | Высокая (software-defined) | Ограничена возможностями NIC |
| **Live Migration** | Поддерживается | Не поддерживается |
| **Сложность** | Высокая | Средняя |
| **Использование** | NFV, vRouter, apps | ВМ с требованиями к сети |

### Комбинирование DPDK + SR-IOV

```
┌─────────────────────────────────────────────────────────────┐
│                    Container/Pod                            │
│  ┌─────────────────────────────────────────────────────┐    │
│  │              DPDK Application                       │    │
│  │         (Обработка пакетов userspace)               │    │
│  └─────────────────────┬───────────────────────────────┘    │
└────────────────────────┼────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────┐
│              VF (Virtual Function)                          │
│         Прямой доступ через PCI passthrough                 │
└───────────────────────┬─────────────────────────────────────┘
                        │
┌───────────────────────▼─────────────────────────────────────┐
│              ФИЗИЧЕСКИЙ NIC (SR-IOV)                        │
└─────────────────────────────────────────────────────────────┘

Результат: Максимальная производительность!
```

**Преимущества комбинации:**
- VF предоставляет bare-metal доступ к NIC
- DPDK обрабатывает пакеты с максимальной эффективностью
- Идеально для Cloud-Native Network Functions (CNF)

## Практические сценарии

### Сценарий 1: Kubernetes + SR-IOV

```yaml
# SR-IOV Network Device Plugin
apiVersion: v1
kind: Pod
metadata:
  name: sriov-pod
  annotations:
    k8s.v1.cni.cncf.io/networks: sriov-network
spec:
  containers:
  - name: app
    image: my-app:latest
    resources:
      limits:
        intel.com/sriov_net: '1'  # Запрос 1 VF
```

### Сценарий 2: OVS-DPDK

```bash
# Установка OVS с DPDK
ovs-vsctl --no-wait set Open_vSwitch . other_config:dpdk-init=true
ovs-vsctl --no-wait set Open_vSwitch . other_config:dpdk-socket-mem="1024"

# Создание DPDK порта
ovs-vsctl add-port br0 dpdk0 -- set Interface dpdk0 type=dpdk \
    options:dpdk-devargs=0000:04:00.0

# Проверка
ovs-vsctl show
```

### Сценарий 3: VPP (Vector Packet Processing)

```bash
# Конфигурация VPP
# /etc/vpp/startup.conf
dpdk {
  dev 0000:04:00.0
  num-mbufs 131072
}

# Запуск
systemctl start vpp

# CLI VPP
vppctl show interfaces
vppctl show hardware
```
