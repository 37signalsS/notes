# VPN vs. Service Mesh для сетевой безопасности

## Роль в архитектуре Zero Trust

В [архитектуре Zero Trust](./zero_trust_overview.md) как VPN, так и Service Mesh играют важную, но разную роль. Их выбор и комбинация зависят от того, какой трафик необходимо защитить: **north-south** (входящий/исходящий) или **east-west** (внутренний, между сервисами).

*   **VPN (Virtual Private Network):**
    *   **Назначение:** Создает зашифрованный туннель на **L3/L4** для безопасного доступа к частным сетям. Традиционно решает задачу защиты трафика **north-south** — удаленный доступ сотрудников, соединение "площадка-площадка" (site-to-site).
    *   **Роль в Zero Trust:** Остается актуальным для шифрования трафика на транспортном уровне между физически разделенными периметрами (например, между ДЦ и облаком), но не обеспечивает гранулярного контроля внутри этих периметров.

*   **Service Mesh (Сетка сервисов):**
    *   **Назначение:** Представляет собой слой инфраструктуры на **L7**, который управляет взаимодействием между сервисами. Обеспечивает сквозную аутентификацию (mTLS), детальную авторизацию и глубокую наблюдаемость (телеметрию).
    *   **Роль в Zero Trust:** Является ключевым инструментом для защиты трафика **east-west**. Политики доступа привязываются не к IP-адресам, а к криптографически подтвержденной идентичности рабочих нагрузок (workload identity).

## Ключевые различия

| Критерий | VPN | Service Mesh |
| :--- | :--- | :--- |
| **Сетевой уровень** | L3/L4 туннели (IPsec, WireGuard) | L7 прокси/sidecar (Envoy), иногда eBPF |
| **Идентичность** | IP-адреса, подсети, сертификаты туннеля | SPIFFE/SVID, сервисные аккаунты |
| **Шифрование** | Шифруется весь трафик внутри туннеля | mTLS между конкретными сервисами |
| **Политики доступа** | ACL на основе IP/портов | Правила на уровне L7 (методы, пути, заголовки) |
| **Наблюдаемость** | Ограничена (счетчики трафика) | Детальная (трассировка, метрики запросов) |
| **Гранулярность** | Макросегментация (сетевые сегменты) | Микросегментация (на уровне сервисов и методов) |
| **Прозрачность для приложений** | Обычно полностью прозрачна | Прозрачна для кода, но требует sidecar-прокси |
| **Накладные расходы** | Управление ключами, маршрутизацией | Управление плоскостью контроля, сертификатами, sidecar'ами |

## Примеры конфигураций

### 1. VPN: Туннель WireGuard

Минимальная конфигурация для site-to-site соединения. Трафик между `10.10.0.1` и `10.10.0.2` будет инкапсулирован и зашифрован.

```ini
# Хост A
[Interface]
Address = 10.10.0.1/24
PrivateKey = <A-PRIVATE>
ListenPort = 51820

[Peer]
PublicKey = <B-PUBLIC>
AllowedIPs = 10.10.0.2/32
Endpoint = 203.0.113.2:51820
PersistentKeepalive = 25
```

### 2. Service Mesh: Политика доступа в Istio

Эта конфигурация требует строгого mTLS во всем меше и разрешает `POST`-запросы к сервису `orders` только от сервиса `payments`.

```yaml
# Включить строгий mTLS для всего пространства имен
apiVersion: security.istio.io/v1beta1
kind: PeerAuthentication
metadata:
  name: mesh-mtls
  namespace: istio-system
spec:
  mtls:
    mode: STRICT
---
# Разрешить доступ от 'payments' к 'orders'
apiVersion: security.istio.io/v1beta1
kind: AuthorizationPolicy
metadata:
  name: allow-payments-to-orders
  namespace: orders
spec:
  selector:
    matchLabels:
      app: orders
  action: ALLOW
  rules:
  - from:
    - source:
        # Идентификация на основе сервисного аккаунта
        principals: ["cluster.local/ns/payments/sa/payments-sa"]
    to:
    - operation:
        methods: ["POST"]
        paths: ["/v1/orders"]
```

## Паттерны комбинирования и ограничения

*   **Гибридный подход:** VPN используется для создания безопасного транспортного канала между облаком и on-premise ДЦ (north-south), а Service Mesh — для контроля и защиты трафика между микросервисами внутри облачного кластера (east-west).
*   **Миграция:** Часто начинают с VPN для быстрого обеспечения связности, а затем постепенно внедряют Service Mesh для критичных сервисов, начиная с режима `PERMISSIVE` (разрешающего и mTLS, и обычный трафик) и переходя к `STRICT`.
*   **Производительность:** VPN, работая на более низком уровне, обычно вносит меньше задержек. Оверхед Service Mesh (задержки в sidecar-прокси) является платой за детальные политики и телеметрию на L7.
*   **Сложность:** VPN требует управления ключами и маршрутизацией. Service Mesh требует развертывания и управления плоскостью контроля, жизненным циклом сертификатов и конфигурацией прокси.
*   **Подводные камни:**
    *   **VPN:** Неправильная настройка `split-tunneling`, утечки DNS.
    *   **Service Mesh:** Неверная конфигурация политик, несовместимость с некоторыми протоколами, рост задержек из-за каскада прокси.
