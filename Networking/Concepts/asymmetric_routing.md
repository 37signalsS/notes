# Асимметричная маршрутизация

## Определения

**Асимметричная маршрутизация (Asymmetric Routing)** — ситуация, при которой пакеты одного и того же соединения (или потока) проходят через разные сетевые пути на подходе к назначению и на обратном пути. То есть входящий и исходящий трафик между двумя хостами проходит через разные маршрутизаторы, файрволы или сетевые интерфейсы.

Асимметрия — не ошибка сама по себе. Во многих сетях она возникает намеренно (например, при использовании ECMP или multiple uplinks). Однако она становится проблемой, когда на пути трафика находятся устройства с сохранением состояния (stateful firewall, NAT, IDS/IPS), которым необходимо «видеть» оба направления потока для корректной работы.

**Симметричная маршрутизация (Symmetric Routing)** — обратная ситуация: входящий и исходящий трафик проходят через один и тот же сетевой путь (через один маршрутизатор/интерфейс). Это理想альное поведение для stateful-устройств.

## Базовые концепции

### Почему возникает асимметрия

| Причина | Описание | Типичный сценарий |
| :--- | :--- | :--- |
| **Несимметричные маршруты** | Маршрутизатор находит кратчайший путь для каждого направления независимо | Два провайдера с разной метрикой; BGP-политики |
| **ECMP (Equal-Cost Multi-Path)** | Трафик распределяется по нескольким равнозначным путям, и обратный путь может пройти через другой интерфейс | Spine-leaf архитектура, сервер с несколькими шлюзами |
| **Multiple default gateways** | На хосте настроено несколько шлюзов по умолчанию (например, через bonding или несколько NIC) | Сервер с двумя провайдерами |
| **Return path через другой NAT-шлюз** | Трафик уходит через один NAT-шлюз, а возвращается через другой | Двойной NAT, CGNAT, HA-пара шлюзов |
| **Mangle/routing policy** | Правила `ip rule` или `tc` перенаправляют трафик по разным путям | Policy-based routing, маркировка трафика |
| **Несимметричные маршруты в Overlay** | В VXLAN/Geneve туннелях ingress и egress VTEP находятся на разных узлах | Kubernetes CNI, OVS-DPDK |

### Влияние на conntrack

Conntrack (connection tracking) — основной механизм, который «ломается» при асимметричной маршрутизации.

**Проблема:**
```
Хост A ──(path 1)──► Firewall ──► Хост B
Хост B ──(path 2)──► Другой маршрутизатор ──► Хост A
                       ↑
              Файрвол не видит ответный пакет!
```

1. Хост A отправляет пакет через файрвол → файл создает запись conntrack (состояние NEW → ESTABLISHED).
2. Хост B отвечает через другой маршрут → ответный пакет **не проходит** через файрвол.
3. Файрвол не находит conntrack-записи для ответного пакета → **отбрасывает** его как INVALID.

**Симптомы:**
- Соединения устанавливаются, но данные не передаются (или передаются односторонне).
- TCP-соединения «висят» в состоянии SYN-SENT или ESTABLISHED без обмена данными.
- UDP-трафик работает «в одну сторону» (запрос доходит, ответ теряется).
- Логи файрвола содержат大量 `INVALID` пакетов.

### Влияние на другие stateful-механизмы

| Механизм | Проблема при асимметрии |
| :--- | :--- |
| **Stateful Firewall** | Не видит ответный пакет → блокирует соединение |
| **NAT** | Conntrack-запись не найдена для ответного пакета → трансляция не выполняется → пакет отброшен |
| **IDS/IPS** | Видит только одну сторону потока → не может анализировать контекст соединения |
| **TCP Sequence Validation** | Если два маршрута имеют разную задержку, порядок пакетов может нарушиться |
| **Proxy (L7)** | Прокси не получает ответ от backend → таймаут или retry |

### Когда асимметрия допустима

Не всякая асимметрия — проблема. Она допустима когда:

- **Нет stateful-устройств на пути:** Если трафик проходит только через stateless маршрутизаторы (без файрвола, без NAT), асимметрия не влияет на доставку.
- **Используется stateless NAT:** В некоторых простых сценариях (например, NAT без conntrack) ответный пакет обрабатывается без привязки к записи.
- **Conntrack отключен (NOTRACK):** Правила `raw` таблицы (`NOTRACK`) отключают отслеживание для конкретного трафика.
- **Используется `rp_filter=0`:** Отключение reverse path filtering позволяет принимать пакеты из «неожиданных» направлений (но снижает защиту от IP spoofing).

## Практические сценарии

### Диагностика асимметрии

#### Определение маршрута пакетов

```bash
# Маршрут до целевого хоста
ip route get 10.0.0.5
# → 10.0.0.5 via 192.168.1.1 dev eth0 src 192.168.1.10 uid 0

# Обратный маршрут (от целевого хоста)
# На целевом хосте:
ip route get 192.168.1.10
# → Если маршрут идёт через другой интерфейс — асимметрия

# Мониторинг в реальном времени
watch -n 1 'conntrack -L -p tcp --dport 80 2>/dev/null | head -5'
```

#### Проверка через traceroute

```bash
# Traceroute туда
traceroute -n 10.0.0.5
# → 1: 192.168.1.1 (eth0) → 2: 10.0.0.5

# Traceroute обратно (на целевом хосте)
traceroute -n 192.168.1.10
# → 1: 10.0.0.1 (eth1) → 2: 192.168.1.10
# Если hop 1 отличается — асимметрия
```

#### Проверка через tcpdump

```bash
# На файрволе: смотрим, видим ли мы ответные пакеты
tcpdump -i eth0 host 10.0.0.5 and port 80 -n

# На целевом хосте: проверяем, через какой интерфейс уходит ответ
tcpdump -i eth1 host 192.168.1.10 and port 80 -n
```

#### Проверка reverse path filtering

```bash
# Значение rp_filter для каждого интерфейса
sysctl net.ipv4.conf.all.rp_filter
sysctl net.ipv4.conf.eth0.rp_filter

# 0 = отключен (принимает пакеты из любого направления)
# 1 = строгий (принимает только из ожидаемого направления)
# 2 = свободный (принимает, если есть маршрут в исходной таблице)
```

### Решения

#### 1. Отключение reverse path filtering (быстрое решение)

```bash
# Временно (до перезагрузки)
sysctl -w net.ipv4.conf.all.rp_filter=0
sysctl -w net.ipv4.conf.eth0.rp_filter=0

# Постоянно
cat >> /etc/sysctl.d/99-asymmetric.conf << 'EOF'
net.ipv4.conf.all.rp_filter = 0
net.ipv4.conf.default.rp_filter = 0
EOF
sysctl --system
```

**Важно:** Отключение `rp_filter` снижает защиту от IP spoofing. Используйте только когда асимметрия — осознанное архитектурное решение.

#### 2. Обход conntrack для трафика (NOTRACK)

```bash
# В таблице raw: пометить трафик как не требующий отслеживания
iptables -t raw -A PREROUTING -s 10.0.0.0/24 -d 10.0.0.0/24 -j NOTRACK
iptables -t raw -A PREROUTING -s 10.0.0.0/24 -d 10.0.0.0/24 -j ACCEPT
```

**Когда использовать:** Между серверами, где нет NAT и stateful firewall, но нужна максимальная производительность (например, между LB и backend в одном VLAN).

#### 3. Policy-based routing (создание симметричных маршрутов)

```bash
# Добавить таблицу маршрутизации
echo "100 isp1" >> /etc/iproute2/rt_tables

# Маршруты для трафика через ISP1
ip rule add from 192.168.1.10/32 table isp1
ip route add default via 192.168.1.1 dev eth0 table isp1

# Маршруты для трафика через ISP2 (для другого IP)
echo "200 isp2" >> /etc/iproute2/rt_tables
ip rule add from 192.168.1.11/32 table isp2
ip route add default via 192.168.1.2 dev eth1 table isp2
```

**Пример:** Два провайдера (eth0 → ISP1, eth1 → ISP2). Трафик от IP 192.168.1.10 Always идёт через ISP1, а от IP 192.168.1.11 — через ISP2. Это обеспечивает симметрию для каждого IP.

#### 4. Синхронизация состояний conntrack (conntrackd)

```bash
# Установка conntrackd
apt install conntrackd

# Конфигурация (/etc/conntrackd/conntrackd.conf)
# На обоих файрволах:
Sync {
    Mode FTFW {
        # Full-text tracking: синхронизация всех изменений
    }
    UDP {
        IPv4_address 10.0.0.1
        IPv4_address 10.0.0.2
        Port 3780
    }
}
```

**Как работает:** Два файрвола обмениваются состояниями conntrack через UDP-канал. Когда файрвол A создает запись conntrack, он передает ее файрволу B. Теперь оба файрвола знают о соединении и могут обрабатывать пакеты в любом направлении.

**Когда использовать:** HA-пара файрволов (active-passive или active-active) где трафик может проходить через любой из них.

#### 5. ECMP с хешем по 5-tuple (симметрия на уровне потока)

```bash
# На маршрутизаторе (FRRouting example)
router bgp 65000
  neighbor 10.0.0.5
  address-family ipv4 unicast
    maximum-paths 4
    bgp bestpath multipath-relax

# На сервере: выбор hash policy для ECMP
sysctl -w net.fib_multipath_hash_policy=1
```

**Принцип:** Хеш вычисляется по 5-tuple (src_ip, dst_ip, src_port, dst_port, protocol). Все пакеты одного соединения всегда идут через один и тот же next-hop. Это обеспечивает симметрию на уровне соединений, но не на уровне отдельных пакетов.

## Устранение неполадок

### Симптом: Соединение устанавливается, но данные не приходят

**Диагностика:**
```bash
# 1. Проверка conntrack на файрволе
conntrack -L -p tcp --dport 80 | grep "10.0.0.5"
# → Должна быть запись с ESTABLISHED

# 2. Проверка是否有 INVALID пакеты
conntrack -S | grep invalid
# → Если invalid > 0 — асимметрия

# 3. Проверка маршрута обратного пути
ssh 10.0.0.5 "ip route get 192.168.1.10"
# → Если маршрут через другой интерфейс — асимметрия подтверждена
```

**Решение:**
```bash
# Вариант A: отключить rp_filter (если асимметрия осознанная)
sysctl -w net.ipv4.conf.all.rp_filter=0

# Вариант B: настроить policy routing для симметрии
ip rule add from 10.0.0.5 table 100
ip route add default via <gateway> table 100
```

### Симптом: NAT-трансляция не работает для ответных пакетов

**Диагностика:**
```bash
# Просмотр NAT-трансляций
conntrack -L -p tcp --dport 80 -s 192.168.1.10

# Проверка, есть ли SNAT/DNAT в записи
# Должно быть: src=192.168.1.10 dst=8.8.8.8 → src=203.0.113.1 dst=8.8.8.8

# Если reply-строка содержит оригинальные адреса — трансляция не применилась
```

**Решение:**
```bash
# Убедиться, что оба направления проходят через один NAT-шлюз
# Добавить статический маршрут на обратном пути:
ip route add 192.168.1.0/24 via 192.168.1.1
```

### Симптом: TCP RST после установки соединения

**Причина:** Stateful файрвол видит SYN → SYN-ACK → ACK, но когда клиент отправляет данные, ответный пакет приходит через другой файрвол, который не имеет conntrack-записи и отправляет RST.

**Решение:**
```bash
# 1. Включить NOTRACK для внутреннего трафика
iptables -t raw -A PREROUTING -s 10.0.0.0/8 -d 10.0.0.0/8 -j NOTRACK

# 2. Или синхронизировать conntrack через conntrackd
systemctl enable conntrackd
```

### Вопросы на собеседованиях

1. **Что такое асимметричная маршрутизация и чем она опасна?** — Ответ: пакеты одного соединения проходят через разные пути; stateful устройства (firewall, NAT) не видят ответный пакет и отбрасывают его.
2. **Как диагностировать асимметрию?** — Ответ: `traceroute` в обе стороны, `conntrack -S | grep invalid`, `tcpdump` на обоих маршрутизаторах, проверка `rp_filter`.
3. **Что такое `rp_filter` и зачем его отключают?** — Ответ: reverse path filter проверяет, приходит ли пакет из ожидаемого направления; отключают когда асимметрия — осознанное решение.
4. **Как обеспечить симметрию при ECMP?** — Ответ: хеш по 5-tuple (`net.fib_multipath_hash_policy=1`) + одинаковая политика на всех маршрутизаторах.
5. **Как синхронизировать conntrack между двумя файрволами?** — Ответ: `conntrackd` — демон, передающий состояния через UDP.
