# Жизненный цикл веб-запроса

## Определения

**Жизненный цикл веб-запроса (Web Request Lifecycle)** — это полная последовательность этапов, которую проходит запрос от момента инициации пользователем (ввод URL в адресную строку или клик по ссылке) до финальной отрисовки полученного контента в браузере.

Этот процесс, занимающий от десятков до сотен миллисекунд, вовлекает множество сетевых узлов и протоколов:
1.  **Клиент (User Agent):** Браузер или CLI-утилита (`curl`, `wget`) на устройстве пользователя.
2.  **Локальная сеть (LAN — Local Area Network):** Домашний или офисный роутер, коммутаторы, беспроводные точки доступа.
3.  **Интернет-провайдер (ISP — Internet Service Provider):** Узел доступа к глобальной сети (Edge Router).
4.  **Магистральные сети и IXP (Internet Exchange Points — точки обмена трафиком):** Глобальная инфраструктура передачи данных, связывающая провайдеров через протокол **BGP (Border Gateway Protocol)**.
5.  **CDN (Content Delivery Network — сеть доставки контента) / Edge Nodes:** Промежуточные серверы, кэширующие контент ближе к пользователю для снижения **RTT (Round Trip Time)**.
6.  **Сервер-источник (Origin Server):** Целевой веб-сервер, балансировщик нагрузки (**Load Balancer**) или кластер приложений, где формируется финальный ответ.

## Основные концепции

### Разрешение доменного имени (DNS)

Для установления соединения браузеру необходимо преобразовать доменное имя (например, `google.com`) в IP-адрес.

1.  **Локальное кэширование:**
    *   **Кэш браузера:** Проверка внутренних записей (собственный TTL браузера).
    *   **Кэш ОС и файл `hosts`:** Проверка системной таблицы соответствий (в Linux — через `nsswitch.conf`).
    *   **Локальный резолвер:** Запрос к локальной службе (например, `systemd-resolved` или DNS-сервер на роутере).

2.  **Рекурсивный поиск:**
    *   Если адрес не найден, запрос отправляется к **рекурсивному резолверу** провайдера или публичным сервисам (Cloudflare `1.1.1.1`, Google `8.8.8.8`).
    *   **Рекурсивный vs Итеративный (нерекурсивный) запросы**: 
        *   **Рекурсивный**: Резолвер берет на себя всю работу по поиску и обязан вернуть либо готовый IP-адрес, либо ошибку.
        *   **Итеративный**: Сервер возвращает не сам IP, а «отсылку» (referral) к другому DNS-серверу, который стоит ближе к цели в иерархии.
    *   **Anycast:** Современные DNS-серверы используют технологию Anycast, позволяющую одному IP-адресу принадлежать множеству физических серверов по всему миру. Запрос направляется к ближайшему узлу.

3.  **Безопасность и современные протоколы (Актуально на 2026):**
    *   **DoH (DNS over HTTPS):** Инкапсуляция DNS-запросов в HTTPS-трафик для защиты от перехвата и подмены (порт 443).
    *   **DoT (DNS over TLS):** Передача запросов через выделенный зашифрованный канал (порт 853).
    *   **DoQ (DNS over QUIC):** Современный стандарт (RFC 9250), обеспечивающий минимальную латентность за счет исключения Head-of-Line blocking и поддержки **0-RTT**.
    *   **Happy Eyeballs v3:** Алгоритм параллельного разрешения имен (одновременный запрос `A` и `AAAA` записей) с выбором наиболее быстрого протокола (IPv6 или IPv4) на основе реального RTT и истории успеха соединений.

4.  **Иерархический поиск:** Резолвер последовательно опрашивает корневые серверы (**Root**), серверы доменных зон (**TLD**) и, наконец, авторитативный сервер владельца домена.

### Межсетевое взаимодействие (ARP и IP)

1.  **Маршрутизация:** ОС определяет, находится ли целевой IP в локальной подсети. Если нет, пакеты направляются на **шлюз по умолчанию** (Default Gateway).
2.  **Протокол ARP (Address Resolution Protocol):** Для передачи данных внутри сегмента Ethernet необходим физический **MAC-адрес**. Компьютер отправляет широковещательный запрос в LAN, чтобы узнать MAC-адрес шлюза. Подробнее см. **[ARP](../Protocols/arp.md)**.
3.  **IP-пакетизация:** Данные упаковываются в IP-пакеты, содержащие адреса источника и назначения, TTL (Time To Live) пакета и флаги фрагментации.

### Установка соединения и безопасность (TCP/QUIC и TLS)

1.  **Транспортный уровень:**
    *   **TCP (Transmission Control Protocol):** Традиционный метод с трехэтапным рукопожатием (SYN, SYN-ACK, ACK). Обеспечивает надежную доставку и контроль потока.
    *   **QUIC (UDP-based):** Основа **HTTP/3**. Устраняет проблему Head-of-Line blocking на уровне TCP и поддерживает **Connection Migration** (сохранение соединения при смене IP-адреса клиента).
2.  **Рукопожатие TLS (Transport Layer Security):**
    *   **TLS 1.3:** Сокращает рукопожатие до 1 RTT и поддерживает режим **0-RTT** (Early Data) для ускорения повторных соединений.
    *   **Handshake:** Согласование версии протокола, обмен ключами через **ECDHE** (Elliptic Curve Diffie-Hellman Ephemeral) и проверка сертификата сервера.
    *   **SNI (Server Name Indication):** Позволяет клиенту указать имя хоста в начале рукопожатия, что необходимо для работы нескольких сайтов на одном IP.
    *   **OCSP Stapling:** Механизм, при котором сервер сам предоставляет доказательство валидности своего сертификата. Подробнее см. **[TLS — Transport Layer Security](../Protocols/tls.md)**.
3.  **Алгоритмы контроля перегрузки (Congestion Control):**
    *   В 2026 году стандартом является **BBRv3**, который ориентируется на реальный RTT и пропускную способность, а не на потери пакетов, что критично для стабильности веб-приложений в мобильных сетях.
4.  **HTTP-обмен:**
    *   **Запрос:** Браузер отправляет заголовки (Headers), куки (Cookies) и тело запроса.
    *   **HSTS (HTTP Strict Transport Security):** Заголовок, предписывающий браузеру всегда использовать HTTPS.
    *   **Мультиплексирование:** В **HTTP/2** и **HTTP/3** запросы передаются параллельно через одно соединение.

### Обработка на стороне сервера и рендеринг

1.  **Серверная обработка:**
    *   Запрос принимается балансировщиком (L4 или L7).
    *   Обратный прокси (Nginx, Angie, HAProxy) выполняет TLS-терминацию и проксирование.
    *   Приложение (Backend) обрабатывает запрос, взаимодействуя с базами данных и кэшем. Для обработки тысяч соединений применяются механизмы **[мультиплексирования ввода-вывода (select, poll, epoll)](./io_multiplexing.md)**.
2.  **Рендеринг в браузере (Critical Rendering Path):**
    *   **DOM (Document Object Model):** Парсинг HTML и построение дерева объектов.
    *   **CSSOM (CSS Object Model):** Обработка стилей.
    *   **Layout (Reflow):** Расчет геометрии и позиций каждого элемента.
    *   **Paint:** Отрисовка пикселей на экране.
    *   **Compositing:** Наложение слоев с использованием GPU-акселерации.

## Практические сценарии

### Сценарий 1: Запрос через VPN (WireGuard)

Когда вы используете **VPN** (например, [WireGuard](../../Vpn/wireguard.md)), процесс усложняется из-за туннелирования и инкапсуляции.

#### Подготовка и DNS
1. **Туннель:** VPN-клиент уже установил зашифрованный канал. Маршрутизация направляет трафик в виртуальный интерфейс (`wg0`).
2. **DNS через VPN:** Запрос инкапсулируется в зашифрованный UDP-пакет VPN. VPN-сервер декапсулирует его и отправляет на свой резолвер, предотвращая **DNS-leak**.

#### Установка соединения и передача данных
1. **Инкапсуляция TCP:** Исходный TCP SYN-пакет упаковывается в VPN-пакет.
2. **Сквозное TLS:** TLS-соединение устанавливается **между браузером и целевым сервером**. VPN-сервер не может расшифровать этот трафик, он лишь пересылает зашифрованные пакеты.

**Схема трафика через VPN:**
```text
┌─────────────┐
│  Браузер    │  https://google.com
└──────┬──────┘
       │ DNS-запрос / TCP SYN / TLS Handshake
       ▼
┌─────────────────────────────────┐
│  Сетевой стек ОС (Маршрутизация)│
│  dev wg0 (VPN Interface)        │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  VPN-клиент (Инкапсуляция)      │
│  Шифрование (ChaCha20-Poly1305) │
└──────────────┬──────────────────┘
               │ Зашифрованный пакет
               ▼
┌─────────────────────────────────┐
│  Интернет-провайдер (ISP)       │
│  Видит только VPN-трафик        │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  VPN-сервер (Декапсуляция)      │
└──────────────┬──────────────────┘
               │ Оригинальный пакет
               ▼
┌─────────────────────────────────┐
│  Целевой сервер (google.com)    │
└─────────────────────────────────┘
```

### Сценарий 2: Диагностика через `curl https://google.com`

Команда `curl -v` наглядно показывает этапы жизненного цикла:

1. **DNS-запрос:** Поиск IP через системный резолвер.
2. **TCP Handshake:** `* Trying <IP>:443... Connected.`
3. **TLS Handshake:** Согласование шифров, проверка сертификата, результат: `* SSL connection using TLSv1.3`.
4. **ALPN:** Согласование протокола (например, `h2`).
5. **HTTP обмен:** Отправка GET-запроса и получение ответа.

Для глубокого анализа используются: `dig` (DNS), `mtr` (маршруты), `ss` (сокеты), а также **[Wireshark](../ServicesAndTools/Wireshark/definitions.md)**.
