# Жизненный цикл веб-запроса

## Определения

**Жизненный цикл веб-запроса (Web Request Lifecycle)** — это полная последовательность этапов, которую проходит запрос от момента инициации пользователем (ввод URL (Uniform Resource Locator — унифицированный указатель ресурса) или клик по ссылке) до финальной отрисовки полученного контента в браузере.

Этот процесс, занимающий от десятков до сотен миллисекунд, вовлекает множество сетевых узлов и протоколов:
1.  **Клиент (User Agent):** Браузер или CLI (Command Line Interface — интерфейс командной строки) утилита на устройстве пользователя.
2.  **Локальная сеть (LAN — Local Area Network):** Домашний или офисный роутер, коммутаторы, беспроводные точки доступа.
3.  **Интернет-провайдер (ISP — Internet Service Provider):** Узел доступа к глобальной сети (Edge Router).
4.  **Магистральные сети и IXP (Internet Exchange Points — точки обмена трафиком):** Глобальная инфраструктура передачи данных, связывающая провайдеров через протокол BGP (Border Gateway Protocol — протокол граничного шлюза).
5.  **CDN (Content Delivery Network — сеть доставки контента) / Edge Nodes:** Промежуточные серверы, кэширующие контент ближе к пользователю для снижения RTT (Round Trip Time — время кругового обхода).
6.  **Сервер-источник (Origin Server):** Целевой веб-сервер, балансировщик нагрузки (Load Balancer) или кластер приложений, где формируется финальный ответ.

## Базовые концепции

### Разрешение доменного имени (DNS)

Для установления соединения браузеру необходимо преобразовать доменное имя (например, `google.com`) в IP (Internet Protocol — межсетевой протокол) адрес. Этот этап называется **DNS-резолвингом**.

1.  **Локальное кэширование:**
    *   **Кэш браузера:** Проверка внутренних записей (собственный TTL (Time To Live — время жизни) браузера).
    *   **Кэш ОС (Operating System — операционная система) и файл `hosts`:** Проверка системной таблицы соответствий.
    *   **Локальный резолвер:** Запрос к локальному DNS-серверу (например, в `systemd-resolved` или на роутере).
2.  **Рекурсивный запрос:**
    *   Если адрес не найден, запрос отправляется к **рекурсивному резолверу** провайдера или публичным сервисам (Cloudflare `1.1.1.1`, Google `8.8.8.8`).
    *   **Рекурсивный vs Итеративный (нерекурсивный) запросы**: 
        *   **Рекурсивный**: Резолвер берет на себя всю работу по поиску и обязан вернуть либо готовый IP-адрес, либо ошибку.
        *   **Итеративный**: Сервер может вернуть не сам IP, а «отсылку» (referral) к другому DNS-серверу, который стоит ближе к цели в иерархии.
    *   **Anycast:** Современные DNS-серверы используют технологию Anycast, позволяющую одному IP-адресу принадлежать множеству физических серверов по всему миру. Запрос направляется к ближайшему узлу.

3.  **Безопасность и современные протоколы:**
    *   **DoH (DNS over HTTPS):** Инкапсуляция DNS-запросов в HTTPS-трафик для защиты от перехвата и подмены (порт 443).
    *   **DoT (DNS over TLS):** Передача запросов через выделенный зашифрованный канал (порт 853).
    *   **IPv6:** Браузеры одновременно запрашивают записи `A` (IPv4) и `AAAA` (IPv6), используя алгоритм **Happy Eyeballs** для выбора наиболее быстрого протокола.
4.  **Иерархический поиск:** Резолвер последовательно опрашивает корневые серверы (Root), серверы доменных зон (TLD (Top-Level Domain — домен верхнего уровня)) и, наконец, авторитативный сервер владельца домена.

### Межсетевое взаимодействие (ARP и IP)

После получения IP-адреса формируются сетевые пакеты.

1.  **Маршрутизация:** ОС определяет, находится ли целевой IP в локальной подсети. Если нет, пакеты направляются на **шлюз по умолчанию** (Default Gateway).
2.  **Протокол ARP (Address Resolution Protocol — протокол определения адреса):** Для передачи данных внутри сегмента Ethernet необходим физический **MAC-адрес** (Media Access Control — управление доступом к среде). Компьютер отправляет широковещательный запрос в LAN, чтобы узнать MAC-адрес шлюза. Подробнее см. **[ARP](../Protocols/arp.md)**.
3.  **IP-пакетизация:** Данные упаковываются в IP-пакеты, содержащие адреса источника и назначения, а также флаги фрагментации и TTL пакета.

### Установка соединения и безопасность (TCP/QUIC и TLS)

1.  **Транспортный уровень:**
    *   **TCP (Transmission Control Protocol — протокол управления передачей):** Традиционный метод с трехэтапным рукопожатием (SYN, SYN-ACK, ACK). Обеспечивает надежную доставку и контроль потока.
    *   **QUIC (UDP-based):** Основа **HTTP/3**. Устраняет проблему Head-of-Line blocking на уровне TCP и поддерживает **Connection Migration** (сохранение соединения при смене IP-адреса клиента, например, при переходе с Wi-Fi на LTE).
2.  **Рукопожатие TLS (Transport Layer Security — безопасность транспортного уровня):**
    *   **Handshake:** Согласование версии протокола (TLS 1.2/1.3), обмен ключами (обычно через ECDHE — Elliptic Curve Diffie-Hellman Ephemeral) и проверка сертификата сервера.
    *   **TLS 1.3:** Сокращает рукопожатие до 1 RTT и поддерживает режим **0-RTT** (Early Data) для ускорения повторных соединений.
    *   **SNI (Server Name Indication):** Позволяет клиенту указать имя хоста в начале рукопожатия, что необходимо для работы нескольких сайтов на одном IP.
    *   **OCSP Stapling (Online Certificate Status Protocol):** Механизм, при котором сервер сам предоставляет доказательство валидности своего сертификата. Подробнее см. **[TLS — Transport Layer Security](../Protocols/tls.md)**.
3.  **HTTP-обмен:**
    *   **Запрос:** Браузер отправляет заголовки (Headers), куки (Cookies) и тело запроса.
    *   **HSTS (HTTP Strict Transport Security):** Заголовок, предписывающий браузеру всегда использовать HTTPS.
    *   **Мультиплексирование:** В **HTTP/2** и **HTTP/3** запросы передаются параллельно через одно соединение.

### Обработка на стороне сервера и рендеринг

1.  **Серверная обработка:**
    *   Запрос принимается балансировщиком (L4 или L7).
    *   Обратный прокси (Nginx, HAProxy) выполняет TLS-терминацию и проксирование.
    *   Приложение (Backend) обрабатывает запрос, взаимодействуя с базами данных и кэшем. Для обработки тысяч соединений применяются механизмы **[мультиплексирования ввода-вывода (select, poll, epoll)](./io_multiplexing.md)**.
2.  **Рендеринг в браузере:**
    *   **Парсинг:** Построение **DOM** (Document Object Model — объектная модель документа) и **CSSOM** (CSS Object Model — объектная модель CSS).
    *   **Критический путь:** Расчет геометрии (Layout), отрисовка элементов (Paint) и композиция слоев (Compositing).

## Практические сценарии

### Сценарий 1: Запрос через VPN (WireGuard/OpenVPN)

Когда вы используете **VPN** (Virtual Private Network — виртуальная частная сеть) (например, [WireGuard](../../Vpn/wireguard.md), [OpenVPN](../Tunnels/tunneling_overview.md)), процесс усложняется из-за туннелирования.

#### Подготовка VPN-соединения
До начала запроса VPN-клиент уже установил зашифрованный туннель:
1. **Аутентификация:** Обмен ключами и сертификатами.
2. **Создание интерфейса:** В системе создан виртуальный интерфейс (`tun0`, `wg0`).
3. **Маршрутизация:** Шлюз по умолчанию теперь указывает на VPN-интерфейс.

#### DNS-разрешение через VPN
1. **Запрос попадает в туннель:** Из-за изменённой таблицы маршрутизации DNS-запрос (UDP порт 53) направляется в VPN-интерфейс.
2. **Инкапсуляция:** VPN-клиент зашифровывает DNS-пакет и упаковывает его во внешний UDP/TCP пакет.
3. **Разрешение:** VPN-сервер декапсулирует запрос и отправляет его на свой резолвер. Это предотвращает [DNS-leak](../Tunnels/tunneling_overview.md#безопасность-и-производительность).

#### Установка соединения и передача данных
1. **Инкапсуляция TCP:** Исходный TCP SYN-пакет упаковывается в VPN-пакет.
2. **Сквозное TLS:** TLS-соединение устанавливается **между браузером и целевым сервером**. VPN-сервер не может расшифровать этот трафик, он лишь пересылает зашифрованные пакеты.
3. **Возврат трафика:** Ответ от сервера инкапсулируется VPN-сервером и возвращается клиенту.

#### Схема трафика через VPN

```text
┌─────────────┐
│  Браузер    │  https://google.com
└──────┬──────┘
       │ 1. DNS-запрос (UDP 53)
       │ 2. TCP SYN (порт 443)
       │ 3. TLS Handshake
       │ 4. HTTP-запрос/ответ
       ▼
┌─────────────────────────────────┐
│  Сетевой стек ОС                │
│  ┌───────────────────────────┐  │
│  │ Таблица маршрутизации     │  │
│  │ default dev wg0 (VPN)     │  │
│  └───────────────────────────┘  │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  VPN-клиент (tun0/wg0)          │
│  ┌───────────────────────────┐  │
│  │ Инкапсуляция              │  │
│  │ Шифрование (AES-256/ChaCha)│  │
│  │ Внешний IP: VPN-сервер    │  │
│  └───────────────────────────┘  │
└──────────────┬──────────────────┘
               │  Зашифрованный пакет
               ▼
┌─────────────────────────────────┐
│  Интернет-провайдер (ISP)       │
│  Видит только VPN-трафик        │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  VPN-сервер                     │
│  Декапсулирует пакет и          │
│  отправляет его от своего IP    │
└──────────────┬──────────────────┘
               │  Оригинальный пакет
               ▼
┌─────────────────────────────────┐
│  Целевой сервер (google.com)    │
└─────────────────────────────────┘
```

### Сценарий 2: Диагностика через `curl https://google.com`

Команда `curl -v` наглядно показывает этапы жизненного цикла запроса:

1. **Прикладной уровень (Application Layer):** `curl` анализирует URL (протокол `https`, домен `google.com`, порт `443`).
2. **DNS-запрос:** `curl` запрашивает IP-адрес через системный резолвер.
3. **TCP Handshake:** Инициация соединения с сервером на порт 443.
4. **TLS Handshake:**
   * Согласование параметров шифрования.
   * Проверка сертификата.
   * Создание защищенного туннеля.
5. **HTTP обмен:**
   * Отправка GET-запроса через TLS.
   * Получение ответа (Headers + Body).
   * Вывод контента в терминал.

Для детального анализа используются: `dig` (DNS), `mtr`/`traceroute` (маршруты), `ss` (состояния сокетов), а также **[Wireshark и TCPDump](../ServicesAndTools/Wireshark/definitions.md)** для захвата пакетов.
