# Жизненный цикл веб-запроса

## Определения

**Жизненный цикл веб-запроса (Web Request Lifecycle)** — это полная последовательность шагов, которая происходит с момента, когда пользователь инициирует запрос в браузере (например, вводит URL или нажимает на ссылку), до момента, когда он получает и отображает запрошенный контент. Этот процесс включает в себя преобразование доменного имени в IP-адрес, установку сетевого соединения, отправку запроса, обработку его сервером и получение ответа.

## Базовые концепции

### Этап 1: Преобразование имени в IP-адрес (DNS)

Когда вы вводите URL (например, `https://google.com`) в адресную строку браузера, компьютер должен сначала узнать IP-адрес сервера, на котором находится этот сайт. Для этого он использует систему доменных имён ([DNS](../Protocols/DNS/dns.md)).

Поиск IP-адреса происходит пошагово:

1. **Кеш браузера:** Сначала браузер проверяет собственный кеш.
2. **Кеш ОС:** Если в браузере адреса нет, проверяется кеш операционной системы (например, файл `hosts`).
3. **DNS-резолвер:** Если адрес не найден локально, запрос отправляется к DNS-серверу (обычно это сервер вашего интернет-провайдера или публичный сервер вроде `8.8.8.8`).
4. **Рекурсивный запрос:** DNS-сервер ищет IP-адрес, опрашивая другие серверы в интернете по иерархии (корневые, TLD, авторитативные), пока не найдёт нужную запись.

### Этап 2: Межсетевое взаимодействие (ARP и IP)

Получив IP-адрес назначения, ваш компьютер должен отправить ему данные. Но для отправки данных в локальной сети (например, вашему роутеру) нужен не IP, а физический MAC-адрес.

1. **Определение шлюза:** Компьютер понимает, что IP-адрес назначения (`google.com`) находится за пределами локальной сети. Весь внешний трафик нужно отправлять на **шлюз по умолчанию** (обычно это ваш роутер).
2. **[ARP (Address Resolution Protocol)](../Protocols/arp.md):**
    * Чтобы узнать MAC-адрес роутера, компьютер отправляет широковещательный **ARP-запрос** в локальную сеть с вопросом: "У кого IP-адрес шлюза (например, `192.168.1.1`)?".
    * Роутер отвечает на этот запрос, сообщая свой MAC-адрес.
    * Компьютер сохраняет эту информацию в своей ARP-таблице, чтобы не спрашивать каждый раз.
3. **Передача пакета на IP-уровне:** Теперь, зная MAC-адрес роутера, компьютер может сформировать пакет для отправки [HTTP-запроса](../Protocols/http.md).

### Этап 3: Установка соединения и передача данных (TCP и HTTP/S)

Пакет доходит до роутера, который далее перенаправляет его по глобальной сети, пока он не достигнет сервера назначения.

1. **[TCP-рукопожатие (TCP Handshake)](../Protocols/TCP/overview.md#установка-соединения-tcp-handshake-тройное-рукопожатие):** Перед обменом данными клиент (ваш браузер) и сервер устанавливают надёжное соединение с помощью трёхэтапного процесса (SYN, SYN-ACK, ACK).
2. **[TLS-рукопожатие (TLS Handshake)](../Protocols/tls.md#процесс-рукопожатия-tls-handshake):** Если используется HTTPS (порт 443), после установки TCP-соединения происходит дополнительный процесс согласования. Клиент и сервер договариваются о параметрах шифрования и обмениваются ключами, чтобы защитить передаваемые данные.
    В ходе этого рукопожатия сервер отправляет клиенту свой **цифровой сертификат**, который содержит **публичный ключ** сервера и **цепочку доверия** до корневого удостоверяющего центра. Клиент проверяет валидность и доверие к этому сертификату. Для хостинга нескольких доменов на одном IP-адресе используется механизм **SNI (Server Name Indication)**, который позволяет клиенту указать имя домена, для которого он запрашивает сертификат, уже на этапе TLS-рукопожатия.
3. **[HTTP-запрос](../Protocols/http.md):** После установки безопасного соединения браузер отправляет **HTTP-запрос** (например, `GET / HTTP/1.1`) с просьбой отдать содержимое страницы.
4. **HTTP-ответ:** Сервер обрабатывает запрос и отправляет обратно **HTTP-ответ**, который содержит:
    * **Статус-код** (например, `200 OK`).
    * **Заголовки** (информация о контенте, сервере и т.д.).
    * **Тело ответа** (HTML-код страницы, изображения и другие ресурсы).

Браузер получает этот ответ, обрабатывает HTML, загружает дополнительные ресурсы (CSS, JavaScript) и отображает веб-страницу. На стороне сервера для эффективной обработки множества одновременных подключений применяются механизмы [мультиплексирования ввода-вывода (select, poll, epoll)](./io_multiplexing.md).

## Практические сценарии

### Пример: `curl https://google.com` через VPN

Когда вы подключены к VPN (например, [WireGuard](../../Vpn/wireguard.md), [OpenVPN](../Tunnels/tunneling_overview.md)) и открываете `https://google.com`, процесс усложняется из-за туннелирования трафика.

#### Этап 0: Подготовка VPN-соединения

До начала запроса VPN-клиент уже установил зашифрованный туннель:

1. **Аутентификация:** VPN-клиент прошёл аутентификацию на VPN-сервере (обмен ключами, сертификатами).
2. **Создание туннельного интерфейса:** В системе создан виртуальный интерфейс (`tun0`, `wg0` и т.д.) с IP-адресом из VPN-сети.
3. **Изменение маршрутизации:** Таблица маршрутизации обновлена — **шлюз по умолчанию** теперь указывает на VPN-интерфейс.
4. **Настройка DNS:** Системный DNS-резолвер настроен на использование DNS-сервера VPN-провайдера (или корпоративного DNS).

```bash
# Пример таблицы маршрутизации при активном VPN
$ ip route show
default dev wg0  # Весь трафик идёт через WireGuard
10.0.0.0/24 dev wg0 proto kernel scope link src 10.0.0.2
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100  # Локальная сеть напрямую
```

#### Этап 1: DNS-разрешение через VPN

1. **Приложение отправляет DNS-запрос:** Браузер запрашивает разрешение `google.com`.
2. **Запрос попадает в VPN-туннель:** Из-за изменённой таблицы маршрутизации DNS-запрос (UDP порт 53) направляется в VPN-интерфейс.
3. **Инкапсуляция:** VPN-клиент инкапсулирует DNS-запрос в зашифрованный пакет.
4. **Транспортировка:** Пакет передаётся через физический интерфейс (например, `eth0` или `wlan0`) на VPN-сервер.
5. **Разрешение на стороне VPN:** VPN-сервер декапсулирует запрос и отправляет его на свой DNS-резолвер.
6. **Ответ возвращается:** DNS-ответ (IP-адрес `google.com`) возвращается через туннель в зашифрованном виде.

> **Важно:** При использовании VPN ваш DNS-трафик виден только VPN-провайдеру, а не вашему ISP. Это предотвращает [DNS-leak](../Tunnels/tunneling_overview.md#безопасность-и-производительность).

#### Этап 2: Установка соединения через VPN

1. **Определение маршрута:** Система видит, что IP-адрес `google.com` (например, `142.250.185.78`) находится за пределами локальной сети.
2. **Маршрутизация в туннель:** Из-за маршрута по умолчанию через `wg0` пакет направляется в VPN-туннель.
3. **Инкапсуляция TCP-пакетов:**
   * Исходный TCP SYN-пакет (назначение: `142.250.185.78:443`) упаковывается в VPN-пакет.
   * Внешний заголовок указывает: источник = ваш VPN IP, назначение = VPN-сервер.
4. **Транспортировка через ISP:** Зашифрованный VPN-пакет проходит через вашего интернет-провайдера до VPN-сервера.
5. **Декапсуляция на VPN-сервере:** VPN-сервер извлекает оригинальный TCP-пакет и отправляет его в интернет от своего имени.

#### Этап 3: TCP/TLS Handshake через VPN

1. **TCP Handshake:** VPN-сервер устанавливает TCP-соединение с `google.com` от вашего имени.
2. **TLS Handshake:** Происходит согласование шифрования между вашим браузером и сервером Google.
   * **Важно:** TLS-соединение **сквозное** (end-to-end) — VPN-сервер не может расшифровать содержимое трафика.
3. **HTTP-запрос:** Ваш браузер отправляет зашифрованный HTTP-запрос через VPN-туннель.
4. **HTTP-ответ:** Google отправляет ответ, который проходит через VPN-сервер, инкапсулируется и возвращается вам.

#### Этап 4: Возврат трафика

1. **Ответ от Google:** Сервер Google отправляет HTTP-ответ на IP-адрес VPN-сервера.
2. **Инкапсуляция ответа:** VPN-сервер упаковывает ответ в зашифрованный VPN-пакет.
3. **Транспортировка обратно:** Пакет проходит через ISP до вашего клиента.
4. **Декапсуляция:** VPN-клиент извлекает оригинальный TCP-пакет и передаёт его в сетевой стек ОС.
5. **Доставка приложению:** ОС доставляет данные в браузер.

### Схема трафика через VPN

```
┌─────────────┐
│  Браузер    │  https://google.com
└──────┬──────┘
       │ 1. DNS-запрос (UDP 53)
       │ 2. TCP SYN (порт 443)
       │ 3. TLS Handshake
       │ 4. HTTP-запрос/ответ
       ▼
┌─────────────────────────────────┐
│  Сетевой стек ОС                │
│  ┌───────────────────────────┐  │
│  │ Таблица маршрутизации     │  │
│  │ default dev wg0 (VPN)     │  │
│  └───────────────────────────┘  │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  VPN-клиент (tun0/wg0)          │
│  ┌───────────────────────────┐  │
│  │ Инкапсуляция              │  │
│  │ Шифрование (AES-256)      │  │
│  │ Внешний IP: VPN-сервер    │  │
│  └───────────────────────────┘  │
└──────────────┬──────────────────┘
               │  Зашифрованный UDP-пакет
               │  (порт 51820 для WireGuard)
               ▼
┌─────────────────────────────────┐
│  Ваш ISP (интернет-провайдер)   │
│  Видит только зашифрованный     │
│  трафик на VPN-сервер           │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│  VPN-сервер                     │
│  ┌───────────────────────────┐  │
│  │ Декапсуляция              │  │
│  │ Расшифрование             │  │
│  │ Исходный IP: ваш VPN IP   │  │
│  └───────────────────────────┘  │
└──────────────┬──────────────────┘
               │  Оригинальный TCP-пакет
               │  (источник: ваш VPN IP)
               ▼
┌─────────────────────────────────┐
│  Google (142.250.185.78)        │
│  Видит запрос от VPN-сервера    │
└─────────────────────────────────┘
```

### Пример: `curl https://google.com` (без VPN)

Когда вы выполняете команду `curl https://google.com`, происходит следующая последовательность событий, которая наглядно демонстрирует работу сетевых протоколов, начиная с самого верхнего уровня.

1. **Уровень 7: Прикладной (Application Layer)**
    * **Парсинг URL:** `curl` как приложение анализирует введенный URL:
        * **Протокол:** `https`
        * **Домен:** `google.com`
        * **Путь:** `/` (по умолчанию)
    * **Формирование HTTP-запроса:** `curl` создает текстовый [HTTP-запрос](../Protocols/http.md). Минимально он будет выглядеть так:

        ```http
        GET / HTTP/1.1
        Host: google.com
        User-Agent: curl/8.4.0
        Accept: */*
        ```

2. **Подготовка к передаче: DNS-запрос**
    * Чтобы отправить запрос, `curl` должен узнать IP-адрес сервера `google.com`.
    * Операционная система инициирует **DNS-запрос** (обычно через UDP на порт 53), чтобы преобразовать доменное имя в IP-адрес (например, `142.250.185.78`).

3. **Уровень 4: Транспортный (Transport Layer)**
    * **Выбор порта:** `curl` видит протокол `https` и понимает, что нужно использовать стандартный порт `443`.
    * **TCP-рукопожатие (Handshake):** Операционная система инициирует установку TCP-соединения с сервером `142.250.185.78` на порт `443`. Происходит обмен пакетами (SYN, SYN-ACK, ACK) для создания надежного канала связи.

4. **Уровень 6: Представления (Presentation Layer) - TLS Handshake**
    * Поскольку используется `https`, поверх установленного TCP-соединения происходит **TLS-рукопожатие**.
    * Клиент (`curl`) и сервер договариваются об алгоритмах шифрования и обмениваются ключами, чтобы создать безопасный (зашифрованный) туннель для передачи данных.

5. **Отправка и получение данных**
    * **Отправка запроса:** Сформированный на шаге 1 [HTTP-запрос](../Protocols/http.md) отправляется через зашифрованный TLS-туннель на сервер.
    * **Ответ сервера:** Сервер обрабатывает запрос и отправляет обратно [HTTP-ответ](../Protocols/http.md), который также проходит через все уровни в обратном порядке (шифруется, упаковывается в TCP-сегменты, IP-пакеты и т.д.).
    * **Декапсуляция:** Ваша система получает пакеты, извлекает из них данные, расшифровывает их и передает утилите `curl`.
    * **Вывод:** `curl` выводит тело ответа (например, HTML-код страницы) в стандартный вывод (ваш терминал).

Подробнее о `curl` и других утилитах, таких как `wget` и `httpie`, читайте в заметке о [HTTP-клиентах в Linux](../../Linux/Networking/Tools/http_clients/overview.md). Для детального анализа каждого этапа используются специализированные утилиты: `dig`, `curl`, `traceroute`, `mtr`, `ss` ([инструменты для диагностики сети](../../Linux/Networking/network_diagnostics_tools.md)), а также [Wireshark и TCPDump](../ServicesAndTools/Wireshark/definitions.md) для глубокого исследования пакетов. Диагностика VPN-соединений описана в разделах [Туннелирование](../Tunnels/tunneling_overview.md) и [WireGuard](../../Vpn/wireguard.md).
