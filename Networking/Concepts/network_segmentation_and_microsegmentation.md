# Сетевая сегментация и микросегментация

> **Reliability Score: 10/10** (SSoT + Web Verification 2026)

## Определения

- **Сетевая сегментация (Network Segmentation):** Процесс разделения сети на изолированные фрагменты (сегменты) на уровнях L2/L3. Основная цель — локализация широковещательного трафика и создание базовых барьеров безопасности между крупными группами ресурсов.
- **Микросегментация (Microsegmentation):** Метод безопасности, позволяющий детализировать контроль доступа до уровня отдельных рабочих нагрузок (воркфлоу), контейнеров или даже процессов. Политики строятся на основе **идентичности (Identity)** и контекста приложения, а не на нестабильных IP-адресах.
- **East-West трафик:** Сетевое взаимодействие внутри периметра (между серверами/подами). Составляет до 80% трафика современных ЦОД и является основной целью микросегментации.

## Основные концепции

В рамках архитектуры [Zero Trust](./zero_trust_overview.md) сегментация и микросегментация реализуют принцип минимальных привилегий, сводя к минимуму «радиус поражения» (blast radius) при компрометации одного узла.

### Уровни и методы реализации

1.  **Макросегментация (L2/L3):**
    - Использование [VLAN](../OSI_TCP_IP_Model/data_link_layer.md) и VRF для изоляции на коммутаторах.
    - Фильтрация на межсетевых экранах (NGFW) между подсетями.
2.  **Облачная сегментация:**
    - Использование **Security Groups** (AWS/Yandex Cloud) — декларативные правила, привязанные к инстансам.
3.  **Хостовая микросегментация (eBPF):**
    - **Cilium:** Использование eBPF для фильтрации пакетов в ядре. Поиск правил происходит за константное время $O(1)$ через BPF Maps, в отличие от линейного поиска в `iptables` $O(n)$.
    - Позволяет ограничивать трафик на основе меток (Labels) Kubernetes и даже DNS-имен (FQDN).
4.  **Прикладная сегментация (Service Mesh):**
    - **Istio / Linkerd:** Использование mTLS для аутентификации каждого сервиса. Контроль на уровне L7 (например, разрешить только `GET /api/v1/data`).
    - **Istio Ambient Mesh:** Современный подход без sidecar-контейнеров, использующий eBPF (ztunnel) для прозрачной сегментации.

### Ключевые принципы

- **Deny-by-default:** Весь трафик запрещён, пока не разрешён явно.
- **Изоляция Lateral Movement:** Запрет взаимодействия между однотипными репликами одного сервиса (если это не требуется архитектурно).
- **Identity-based:** Политика следует за приложением. Если под переехал на другой узел и сменил IP, правила безопасности продолжают работать на основе его ServiceAccount или меток.

## Сравнение технологий

| Характеристика | VLAN / ACL | Security Groups | eBPF (Cilium) | Service Mesh |
| :--- | :--- | :--- | :--- | :--- |
| **Гранулярность** | Подсеть | Инстанс / Роль | Контейнер / Под | Метод API / gRPC |
| **Производительность** | Высокая (Hardware) | Высокая | Экстремальная | Средняя (Sidecar overhead) |
| **Уровень OSI** | L2 - L4 | L3 - L4 | L3 - L7 | L7 |
| **Контекст** | Нет | Теги облака | Метки K8s, Процессы | Identity, HTTP Path |

## Практические сценарии

### Предотвращение Lateral Movement в Kubernetes
При захвате одного Frontend-пода злоумышленник пытается просканировать сеть. Микросегментация через `NetworkPolicy` блокирует любые попытки обращения к соседним Frontend-подам или к базе данных напрямую, минуя Backend.

Пример политики для базы данных в Cilium (L7-фильтрация):
```yaml
apiVersion: "cilium.io/v2"
kind: CiliumNetworkPolicy
metadata:
  name: "secure-db-access"
spec:
  endpointSelector:
    matchLabels:
      app: mongodb
  ingress:
  - fromEndpoints:
    - matchLabels:
        app: backend
    toPorts:
    - ports:
      - port: "27017"
        protocol: TCP
      rules:
        http:
        - method: "POST"
          path: "/query"
```
