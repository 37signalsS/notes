# Уровень представления (L6)

## Определения

**Уровень представления (Presentation Layer, L6)** — шестой уровень эталонной модели **OSI (Open Systems Interconnection)**. Он отвечает за преобразование данных между сетевым форматом и форматом, который ожидает приложение, обеспечивая синтаксическую совместимость систем с разной архитектурой.

Если прикладной уровень (L7) работает с семантикой (смыслом) данных, то уровень L6 работает с их синтаксисом (структурой представления).

- **PDU (Protocol Data Unit):** Данные (Data) — преобразованные (кодированные, сжатые, зашифрованные) данные. Размер PDU зависит от алгоритма: от 0% (сжатие) до +40% (TLS overhead) к исходному размеру.
- **Адресация:** Отсутствует. Опирается на идентификаторы сеансового уровня (L5) или порты транспортного уровня (L4).

### Единицы данных и инкапсуляция

| Характеристика | Описание |
| :--- | :--- |
| **PDU** | Данные (Data) — закодированные/сжатые/зашифрованные |
| **Заголовок L6** | Зависит от алгоритма: TLS Record (5 байт), Zstd Frame (9 байт), ASN.1 DER (variable) |
| **Префикс** | Протокол-специфичный: TLS ContentType (1 байт), Version (2 байта), Length (2 байта) |
| **Размер overhead** | 5-40+ байт (TLS) / 0 байт (простая кодировка) / 9+ байт (сжатие) |

**Пример инкапсуляции (HTTPS GET-запрос):**

```text
[HTTP GET /api/users HTTP/1.1\r\nHost: example.com]  ← L7: прикладной протокол
         ↓ L6: TLS шифрование
[TLS Application Data: ContentType=0x17, Version=0x0303, AES-256-GCM]  ← L6: зашифрованные данные
         ↓ L4: транспорт
[TCP Segment: Src=49152 Dst=443] + TLS Data  ← L4: сегмент
         ↓ L3: маршрутизация
[IP Packet: Src=192.168.1.100 Dst=93.184.216.34] + TCP Segment  ← L3: пакет
         ↓ L2: коммутация
[Ethernet Frame: Src MAC, Dst MAC] + IP Packet + [FCS]  ← L2: кадр
         ↓ L1: физическая передача
010101011...  ← L1: биты
```

## Базовые концепции

### Взаимодействие с соседними уровнями

```text
L7 (Прикладной)  ← Формирует данные, определяет формат (JSON, Protobuf, XML)
       ↕
L6 (Представления) ← Кодирование, сжатие, шифрование (TLS)
       ↕
L5 (Сеансовый)   ← Управление сессиями (отсутствует в TCP/IP как отдельный слой)
       ↕
L4 (Транспортный) ← TCP/UDP: доставка данных между процессами
```

| Уровень | Взаимодействие с L6 |
| :--- | :--- |
| **L7 → L6** | Приложение передаёт «сырые» данные (текст, JSON, бинарный объект). L6 определяет формат, кодирует и шифрует |
| **L6 → L5** | Преобразованные данные передаются в сеансовый уровень для управления сессиями |
| **L5 → L6** | При приёме L5 передаёт зашифрованные/сжатые данные обратно в L6 для декодирования |
| **L6 → L7** | Декодированные данные в исходном формате передаются приложению |

**Ключевое замечание:** В модели TCP/IP функции L6 распределены между:
- **Прикладным уровнем (L7):** Протоколы (HTTP/2, gRPC) сами решают вопросы сжатия и сериализации.
- **Библиотеками приложения:** Шифрование (OpenSSL/BoringSSL) и работа с форматами (JSON, Protobuf) реализуются программно внутри кода приложения или Middleware.

### Основные функции

1.  **Кодирование и трансляция:** Преобразование между кодировками (например, ASCII ↔ EBCDIC или UTF-8) и порядком байтов (Endianness). Критично для совместимости систем с разной архитектурой (x86 vs ARM, Big-Endian vs Little-Endian).
2.  **Сериализация (Serialization):** Перевод сложных структур данных (объектов в памяти) в последовательность байт для передачи и восстановление (десериализация) на принимающей стороне. Определяет производительность и размер трафика.
3.  **Сжатие (Compression):** Уменьшение объема данных для экономии полосы пропускания (L6-сжатие не зависит от типа контента, в отличие от L7-сжатия). Выбор алгоритма определяет баланс «скорость CPU vs размер данных».
4.  **Шифрование (Encryption):** Обеспечение конфиденциальности данных путем их преобразования в нечитаемый вид (например, TLS). Гарантирует, что данные недоступны третьим лицам при передаче по сети.

### Статус в модели TCP/IP

В практическом стеке **TCP/IP** уровень представления не выделен как отдельный системный слой. Его функции распределены между:
- **Прикладным уровнем (L7):** Протоколы (HTTP/2, gRPC) сами решают вопросы сжатия и сериализации.
- **Библиотеками приложения:** Шифрование (OpenSSL/BoringSSL) и работа с форматами (JSON, Protobuf) реализуются программно внутри кода приложения или Middleware.

## Технические детали реализации

### Представление данных и кодирование

| Параметр | Описание | Сетевой стандарт / Примеры |
| :--- | :--- | :--- |
| **Кодировка текста** | Маппинг символов в числа. UTF-8 — доминирующий стандарт (98% веб-страниц). | **UTF-8** (стандарт), UTF-16 (Windows API), ASCII (7 бит), ISO-8859-1 (Latin-1). |
| **Порядок байтов** | Расположение байтов в памяти. | **Big-Endian** (Network Byte Order) для протоколов; Little-Endian — нативный для x86/ARM. |
| **ASN.1** | Абстрактная нотация для описания структур. Определяет «как выглядят данные» независимо от платформы. | Используется в сертификатах **X.509** и SNMP. Кодируется: **DER** (бинарный, детерминированный), **PEM** (Base64 + заголовки), **BER** (переменный). |
| **Base64** | Кодирование бинарных данных в ASCII-строку (64 printable chars). Не является шифрованием. | Email (MIME), Data URLs, JWT, K8s Secrets (Base64 в `data`), TLS certificate pinning. |
| **MIME** | Стандарт описания типов контента для email и HTTP. | `Content-Type`, `Content-Transfer-Encoding: base64`. |

### Кодировка текста: детали

| Кодировка | Размер символа | Поддержка | Применение |
| :--- | :--- | :--- | :--- |
| **UTF-8** | 1-4 байта | 1,114,112 символов (все Unicode) | Веб, Linux, API, UTF-8 everywhere philosophy |
| **UTF-16** | 2 или 4 байта | BMP + Supplementary | Windows internals, Java (внутреннее представление) |
| **UTF-32** | 4 байта | BMP + Supplementary | Редко используется (перерасход памяти) |
| **ASCII** | 1 байт (7 бит) | 128 символов | Легаси-системы, C-строки |
| **ISO-8859-1** | 1 байт | 256 символов (Latin) | HTTP default charset, legacy HTML |

### Сериализация (Data Serialization)

В современных распределенных системах выбор формата сериализации определяет производительность (CPU) и объем трафика:

| Формат | Тип | Размер (отн.) | Скорость | Схема | Применение |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **JSON** | Текстовый | 1.0x (baseline) | Средняя | Нет | REST API, Web, конфигурации |
| **Protobuf** | Бинарный | 0.3-0.5x | Высокая | `.proto` файлы | gRPC, внутренняя связь, Kafka |
| **FlatBuffers** | Бинарный | 0.4x | Экстремальная (zero-copy) | `.fbs` файлы | High-performance, игры, Unity |
| **Apache Avro** | Бинарный | 0.3-0.4x | Высокая | JSON-схема | Kafka, Big Data, Hadoop |
| **MessagePack** | Бинарный | 0.5-0.7x | Высокая | Нет (self-describing) | Redis, MongoDB, RPC |
| **CBOR** | Бинарный | 0.4-0.6x | Высокая | JSON-подобная | IoT (CoAP), CBOR Web Token |
| **XML** | Текстовый | 1.5-3.0x | Низкая | XSD/DTD | SOAP, legacy enterprise |
| **YAML** | Текстовый | 1.2x | Низкая | Нет | Конфигурации (K8s, Ansible) |
| **Ion** | Бинарный | 0.3-0.5x | Высокая | `.ion` файлы | AWS, DynamoDB |
| **MsgPack** | Бинарный | 0.5-0.7x | Высокая | Нет | Embedded, game servers |

**Критерии выбора формата:**
- **Производительность CPU:** FlatBuffers > Protobuf > Avro > MessagePack > JSON
- **Размер трафика:** Protobuf ≈ Avro < FlatBuffers < MessagePack < JSON
- **Человекочитаемость:** JSON > YAML > XML > (все бинарные)
- **Схемная совместимость:** Avro ( schemas with defaults) > Protobuf (backward/forward compatible) > FlatBuffers
- **Zero-copy доступ:** FlatBuffers (без десериализации) > Ion > все остальные

### Сжатие данных (Compression)

Современные стандарты (2026+) ориентированы на баланс между нагрузкой на CPU и степенью сжатия:

| Алгоритм | Степень сжатия | Скорость (CPU) | Размер overhead | Применение |
| :--- | :--- | :--- | :--- | :--- |
| **Zstandard (Zstd)** | Высокая | Экстремальная | 9-18 байт frame | Логи, телеметрия, KV-хранилища, Network transfer |
| **Brotli** | Очень высокая (текст) | Средняя | ~10 байт | Веб (статические ресурсы), CDN, HTTP/2 |
| **LZ4** | Средняя | Экстремальная | 7+ байт | Кэши, RAM-диски, real-time обработка |
| **gzip** | Хорошая | Средняя | 10+ байт | HTTP/1.1, email, legacy системы |
| **Snappy** | Средняя | Экстремальная | Минимальный | Hadoop, Kafka (default), внутренняя связь |

- **Zstandard (Zstd):** Разработан Meta. Является «золотым стандартом» для логов и передачи данных в реальном времени благодаря экстремальной скорости декомпрессии. Поддерживает уровни сжатия 1-22 и trained dictionaries.
- **Brotli:** Оптимизирован для веба (статические ресурсы). Показывает лучшие результаты сжатия текстовых данных, чем Gzip. Использует предварительно созданную таблицу частых слов для URL/html/css/js.
- **LZ4:** Самый быстрый алгоритм, используется там, где задержка критичнее объема (кэши, RAM-диски). Скорость >500 МБ/с на одном ядре.
- **gzip:** Классический алгоритм на основе deflate. Универсальная поддержка (100% браузеров). Подробнее: **[Сжатие на стороне сервера](../../WebServers/Concepts/web_performance/server_compression.md)**.

### Согласование сжатия (Content Negotiation)

Сжатие согласовывается на уровне L7 через HTTP-заголовки, но является функцией L6:

```text
Клиент:  Accept-Encoding: gzip, deflate, br, zstd
Сервер:  Content-Encoding: zstd
         Content-Type: application/json
         Vary: Accept-Encoding
```

**Важно:** Заголовок `Vary: Accept-Encoding` обязателен — без него CDN/кэши могут отдать сжатый ответ клиенту, не поддерживающему алгоритм.

## Практические сценарии

### Сценарий 1: Роль TLS в контексте L6

Хотя TLS часто ассоциируют с L4 (поскольку он «оборачивает» TCP), функционально — это типичный L6:
- **Согласование (Cipher Suite Negotiation):** Договоренность о «языке» (алгоритмах) шифрования.
- **ALPN (Application-Layer Protocol Negotiation):** Выбор прикладного протокола (HTTP/1.1 vs HTTP/2) до начала передачи данных L7.
- **Data Transformation:** Превращение байтов прикладного уровня в зашифрованный поток L6.

| TLS версия | RTT handshake | PFS | Ключевые особенности | Статус (2026) |
| :--- | :--- | :--- | :--- | :--- |
| **TLS 1.0/1.1** | 2-RTT | Нет | Устаревшие, уязвимы (BEAST, POODLE) | **Запрещён** (RFC 8996) |
| **TLS 1.2** | 2-RTT | Опционально | SHA-256, AES-GCM, ECDHE | Поддержка, но не рекомендуется |
| **TLS 1.3** | 1-RTT | Обязательно | 0-RTT, ECH, только AEAD-шифры | **Рекомендуемый стандарт** |
| **QUIC (HTTP/3)** | 0-RTT (resume) | Встроен | Шифрование UDP-трафика, Connection Migration | Растущее adoption |

### Сценарий 2: Сетевая безопасность и ASN.1

Сертификаты безопасности (X.509) используют стандарт **ASN.1 (Abstract Syntax Notation One)** для описания своей структуры. При передаче по сети они кодируются по правилам **DER (Distinguished Encoding Rules)** — это классическая задача уровня представления: гарантировать, что структура сертификата будет идентично понята любым устройством, независимо от его ОС.

**Форматы сертификатов:**

| Формат | Описание | Расширение | Использование |
| :--- | :--- | :--- | :--- |
| **DER** | Бинарный, детерминированный | `.der`, `.cer` | Java (cacerts), Windows, LDAP |
| **PEM** | Base64(DER) + заголовки | `.pem`, `.crt`, `.key` | Linux, nginx, Let's Encrypt |
| **PKCS#12** | Контейнер (сертификат + ключ + цепочка) | `.p12`, `.pfx` | Windows, Java KeyStore, импорт/экспорт |
| **PKCS#10** | Certificate Signing Request (CSR) | `.csr` | Запрос на выпуск сертификата |
| **PKCS#7** | Цепочка сертификатов (без ключа) | `.p7b`, `.p7c` | Кросс-подписи, CA bundle |

### Сценарий 3: gRPC и кодогенерация

В gRPC уровень представления автоматизирован:
1.  Определяем контракт в Protobuf.
2.  Компилятор генерирует код сериализации для нужного языка.
3.  При вызове метода объект в памяти Go/Python прозрачно превращается в бинарный поток L6, понятный приемнику.

**Пример: Protobuf vs JSON (те же данные):**

```protobuf
// message.proto
message User {
  int32 id = 1;
  string name = 2;
  string email = 3;
}
```

| Формат | Размер (байты) | Время парсинга (отн.) |
| :--- | :--- | :--- |
| JSON `{"id":1,"name":"John","email":"john@example.com"}` | 52 | 1.0x |
| Protobuf (binary) | 28 | 0.3x |
| FlatBuffers | 32 | 0.1x (zero-copy) |

### Сценарий 4: Сжатие HTTP-ответа

```bash
# Проверка поддержки сжатия клиентом
curl -sI -H "Accept-Encoding: gzip, br, zstd" https://example.com

# Ответ сервера:
# Content-Encoding: br
# Content-Length: 1234   (вместо 4567 без сжатия = 73% savings)
# Vary: Accept-Encoding
```

| Алгоритм | Размер JSON (1 КБ) | Время сжатия | Время декомпрессии |
| :--- | :--- | :--- | :--- |
| gzip (level 6) | ~350 байт | 15 мкс | 5 мкс |
| Brotli (level 6) | ~280 байт | 30 мкс | 8 мкс |
| Zstd (level 3) | ~310 байт | 5 мкс | 2 мкс |
| LZ4 | ~420 байт | 1 мкс | 0.5 мкс |

## Наблюдаемость и безопасность L6

### Безопасность уровня L6

| Угроза | Описание | Защита |
| :--- | :--- | :--- |
| **MITM (Man-in-the-Middle)** | Перехват и модификация трафика между клиентом и сервером | TLS 1.3, проверка сертификатов, CT (Certificate Transparency) |
| **Cipher Suite downgrade** | Принуждение к использованию слабых алгоритмов шифрования | TLS 1.3 (запрещены слабые алгоритмы), серверная политика |
| **Certificate forgery** | Подделка сертификата для имитации сервера | CA trust chain, CAA DNS record, CT logs, HPKP (устарел) |
| **SNI sniffing** | Перехват имени хоста в открытом виде (ClientHello) | ECH (Encrypted Client Hello), TLS 1.3 + ECH |
| **Бreak-and-inspect** | Расшифровка трафика промежуточным устройством (corporate proxy) | mTLS, certificate pinning, End-to-End encryption |
| **Padding Oracle** | Атака на CBC-режим шифрования | TLS 1.3 (только AEAD-шифры: AES-GCM, ChaCha20) |
| **CRIME/BREACH** | Утечка данных через сжатие (Side-channel) | Отключение сжатия TLS (TLS-level), разные ключи для разных контентов |

### Диагностика L6

```bash
# === TLS/SSL ===

# Проверка TLS-соединения и Cipher Suite
openssl s_client -connect example.com:443 -servername example.com

# Проверка сертификата (сроки, владелец, цепочка)
openssl s_client -connect example.com:443 2>/dev/null | openssl x509 -noout -text

# Проверка поддержки ALPN (HTTP/2)
openssl s_client -connect example.com:443 -alpn h2,http/1.1

# Проверка OCSP Stapling
openssl s_client -connect example.com:443 -status

# ПроверкаTLS-заголовков через curl
curl -vI https://example.com 2>&1 | grep -E "SSL|TLS|subject|issuer|expire"

# Проверка cipher suites (все поддерживаемые)
nmap --script ssl-enum-ciphers -p 443 example.com

# Быстрая проверка (testssl.sh)
testssl.sh --fast https://example.com

# Проверка цепочки сертификатов
openssl verify -CAfile /etc/ssl/certs/ca-certificates.crt server.crt

# === Кодировка и сериализация ===

# Проверка кодировки файла
file --mime-encoding secret.txt

# Конвертация DER → PEM
openssl x509 -in cert.der -inform DER -out cert.pem -outform PEM

# Просмотр ASN.1 структуры сертификата
openssl asn1parse -in cert.pem -i

# Проверка Base64
echo "SGVsbG8=" | base64 -d

# Проверка сжатия ответа
curl -sI -H "Accept-Encoding: gzip, br, zstd" https://example.com | grep -i content-encoding
```

## Дополнительная информация

### Связь с соседними уровнями OSI

- **[Прикладной уровень (L7)](./application_layer.md):** Определяет формат данных (JSON, Protobuf) и семантику. L6 обеспечивает транспорт и шифрование для L7-протоколов.
- **[Сеансовый уровень (L5)](./session_layer.md):** Управление жизненным циклом сессий. В TCP/IP модели функции L5/L6 распределены между L7 (HTTP/2 streams) и L4 (TCP keepalive).
- **[Транспортный уровень (L4)](./transport_layer.md):** TCP/UDP обеспечивают доставку зашифрованных данных L6.
