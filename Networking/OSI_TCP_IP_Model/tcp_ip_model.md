# Модель TCP/IP

## Определения

**Модель TCP/IP (Transmission Control Protocol/Internet Protocol)** — практическая многоуровневая модель сетевого взаимодействия, стандарт де-факто для современного Интернета. В отличие от теоретической [модели OSI](./osi_model.md) (Open Systems Interconnection), она была разработана на основе реально существующих протоколов, что определило её доминирование.

**Стек протоколов TCP/IP** — иерархический набор протоколов, реализующий модель TCP/IP. Название происходит от двух ключевых протоколов: TCP (транспортный) и IP (сетевой).

### История и стандарты

| Параметр | Значение |
| :--- | :--- |
| **Разработчик** | DARPA (Defense Advanced Research Projects Agency) / IETF (Internet Engineering Task Force) |
| **Год появления** | 1970-е (TCP — 1974, разделение на TCP/IP — 1978) |
| **Стандарты** | RFC (Request for Comments), STD (Internet Standard) |
| **Ключевые RFC** | RFC 791 (IPv4, STD 5), RFC 8200 (IPv6, STD 86), RFC 9293 (TCP, **заменяет RFC 793**, август 2022, STD 7), RFC 768 (UDP), RFC 9000 (QUIC, май 2021) |
| **Текущий статус** | Основной стандарт Интернета |

## Базовые концепции

### Уровни модели (4-х и 5-ти уровневые версии)

В классической документации выделяют 4 уровня. Однако для удобства диагностики и проектирования в DevOps/SRE часто используют **гибридную 5-уровневую модель**, разделяющую уровень сетевого доступа на канальный и физический.

| № | Уровень (5 слоёв) | Соответствие OSI | Функции | Протоколы и ссылки |
| :--- | :--- | :--- | :--- | :--- |
| **5** | **Прикладной (Application)** | L7, L6, L5 | Взаимодействие с приложениями, представление данных, шифрование | [HTTP](../Protocols/HTTP/http_basics.md), [DNS](../Protocols/DNS/dns.md), SMTP, FTP, [TLS](../Protocols/tls.md), gRPC, QUIC, SSH |
| **4** | **Транспортный (Transport)** | L4 | Доставка между процессами, надёжность, контроль потока | [TCP](../Protocols/TCP/overview.md), [UDP](../Protocols/udp.md), SCTP |
| **3** | **Сетевой (Internet)** | L3 | Глобальная адресация, маршрутизация, фрагментация | [IP](../Protocols/IP_addressing/ip_overview.md), [ICMP](../Protocols/ICMP/icmp_overview.md), [ARP](../Protocols/arp.md), OSPF, [BGP](../Protocols/bgp.md) |
| **2** | **Канальный (Data Link)** | L2 | Доставка в пределах ЛВС, MAC-адресация | [Ethernet](../Protocols/ethernet.md), Wi-Fi, PPP, VLAN (802.1Q) |
| **1** | **Физический (Physical)** | L1 | Передача битов через физическую среду | Кабели (витая пара, оптика), SFP, Hub |

#### Технические детали и оборудование уровней

**1. Физический и Канальный уровни (L1-L2)**
- **Функции:** Физическая доставка в пределах локальной сети. Контроль целостности через FCS (Frame Check Sequence).
- **Адресация:** [MAC-адреса](../Concepts/mac_address.md) (Media Access Control).
- **Оборудование:** Коммутаторы (L2), мосты, сетевые карты (NIC), повторители, трансиверы.
- **Особенности IPv6:** Отказ от широковещательных рассылок (broadcast). Вместо ARP используется **NDP (Neighbor Discovery Protocol)**, работающий через ICMPv6 multicast.
- **Связанные заметки:** [data_link_layer.md](./data_link_layer.md), [physical_layer.md](./physical_layer.md).

**2. Сетевой уровень (Internet Layer / L3)**
- **Функции:** Маршрутизация между сетями (internetworking). Определение пути (path selection).
- **Адресация:** [IP-адреса](../Protocols/IP_addressing/ip_overview.md) (IPv4/IPv6).
- **Оборудование:** Маршрутизаторы (роутеры), L3-коммутаторы.
- **Программируемость:** В современных Linux-системах обработка пакетов на этом уровне может быть оптимизирована с помощью **eBPF (XDP)**, позволяя отбрасывать нежелательный трафик до его попадания в основной стек ядра.
- **Связанные заметки:** [network_layer_overview.md](./Network_layer/Concepts/network_layer_overview.md).

**3. Транспортный уровень (Transport Layer / L4)**
- **Функции:** Связь между процессами через **[порты](../Concepts/network_ports.md)**. Обеспечение надежности (TCP) или минимальной задержки (UDP). Сегментация данных.
- **Оборудование:** Хосты, L4-брандмауэры (iptables/nftables), L4-балансировщики (IPVS).
- **Современные технологии:** Внедрение алгоритмов контроля перегрузки нового поколения (например, **BBR** от Google) значительно повышает пропускную способность TCP на зашумленных каналах.
- **Связанные заметки:** [transport_layer.md](./transport_layer.md).

**4. Прикладной уровень (Application Layer / L5-L7)**
- **Функции:** Протоколы пользовательских приложений, интерфейс между сетью и ПО. В TCP/IP этот уровень объединяет сеансовые функции и функции представления.
- **Оборудование:** Хосты, прокси-серверы, L7-балансировщики (Nginx, HAProxy), WAF (Web Application Firewall).
- **Связанные заметки:** [application_layer.md](./application_layer.md).

### Единицы данных (PDU) и Инкапсуляция

Процесс движения данных сверху вниз сопровождается **инкапсуляцией** (добавлением заголовков), а снизу вверх — **декапсуляцией**.

| Уровень | Название PDU | Состав | Размер заголовка |
| :--- | :--- | :--- | :--- |
| **Прикладной** | Данные / Сообщение | Полезная нагрузка приложения | Зависит от протокола |
| **Транспортный** | Сегмент (TCP) / Дейтаграмма (UDP) | [L4 заголовок] + Данные | 20-60 байт (TCP) / 8 байт (UDP) |
| **Сетевой** | Пакет | [L3 заголовок] + Сегмент/Дейтаграмма | 20 байт (IPv4) / 40 байт (IPv6) |
| **Канальный** | Кадр (Frame) | [L2 заголовок] + Пакет + [FCS] | 14-22 байта |
| **Физический** | Биты | Сигналы в среде передачи | Н/П |

**Схема инкапсуляции:**
```text
Данные приложения (HTTP GET / JSON)
         ↓
[TCP/UDP заголовок] + Данные = Сегмент/Дейтаграмма
         ↓
[IP заголовок] + Сегмент = IP-пакет
         ↓
[Ethernet заголовок] + Пакет + FCS = Кадр
         ↓
Биты (электрические/световые сигналы)
```

**Детальный пример инкапсуляции (HTTP GET запрос через TCP):**

```text
[Данные] HTTP GET /api/data HTTP/1.1\r\nHost: example.com
         ↓
[TCP заголовок: Src=49152, Dst=443, Seq=1, Ack=1, Flags=SYN] + Данные = TCP-сегмент (20+ байт)
         ↓
[IP заголовок: Src=192.168.1.100, Dst=93.184.216.34, TTL=64] + Сегмент = IP-пакет (20 байт)
         ↓
[Ethernet заголовок: Src MAC=AA:BB:CC:DD:EE:FF, Dst MAC=00:11:22:33:44:55] + Пакет + [FCS] = Ethernet-кадр (14 байт)
         ↓
Биты (электрические сигналы в UTP-кабиле)
```

**Важные правила инкапсуляции:**

1. **IP-адреса** (L3) остаются неизменными от отправителя до получателя (за исключением NAT).
2. **MAC-адреса** (L2) меняются на каждом узле (маршрутизаторе) — они отвечают за доставку до следующего «хопа».
3. **Порты** (L4) остаются неизменными на протяжении всего маршрута (за исключением PAT/NAT).

**MTU (Maximum Transmission Unit) и MSS (Maximum Segment Size):**

| Параметр | Описание | Значение по умолчанию |
| :--- | :--- | :--- |
| **MTU** | Максимальный размер IP-пакета (L3) без фрагментации | 1500 байт (Ethernet) |
| **Jumbo Frame** | Увеличенный MTU для высокоскоростных сетей | до 9000 байт |
| **MSS** | Максимальный размер полезной нагрузки TCP-сегмента | 1460 байт (1500 - 20 IP - 20 TCP) |

**Формула расчета MSS:**
```
MSS = MTU - (IP Header) - (TCP Header)
MSS = 1500 - 20 - 20 = 1460 байт
```

**Проблема несоответствия MTU/MSS:**
- При туннелировании (GRE, IPsec, VXLAN) добавляется оверхед (50-73 байт)
- Без PMTUD (Path MTU Discovery) пакеты могут отбрасываться (blackhole)
- **Решение:** TCP MSS Clamping — принудительное уменьшение MSS для учета заголовков туннеля

## Практические сценарии

### Сценарий 1: Запрос веб-страницы (HTTPS)

| Шаг | Уровень | Действие |
| :--- | :--- | :--- |
| 1 | Прикладной | Браузер формирует HTTP GET-запрос. Инициируется TLS-рукопожатие. |
| 2 | Транспортный | Создание TCP-сегмента. Порт источника (динамический) → Порт назначения (443). |
| 3 | Сетевой | Создание IP-пакета. IP клиента → IP сервера. Определение шлюза. |
| 4 | Канальный | Инкапсуляция в Ethernet-кадр. MAC клиента → MAC шлюза (через ARP или NDP). |
| 5 | Передача | Пакет проходит через роутеры (изменение L2-заголовка на каждом хопе). |
| 6 | Прием | Сервер выполняет декапсуляцию и передает данные веб-серверу. |

### Сценарий 2: Получение IP-адреса по DHCP

Детальное описание протокола и процесса DORA приведено в [Обзоре DHCP](../Protocols/DHCP/dhcp_overview.md).

| Шаг | Уровень | Действие |
| :--- | :--- | :--- |
| 1 | Канальный | Клиент отправляет широковещательный кадр DHCPDISCOVER (MAC: `FF:FF:FF:FF:FF:FF`). |
| 2 | Сетевой | IP-пакет имеет адрес `0.0.0.0` (источник) и `255.255.255.255` (назначение). |
| 3 | Транспортный | Используется UDP (порты 67 для сервера и 68 для клиента). |
| 4 | Ответ | DHCP-сервер отвечает DHCPOFFER, предлагая свободный IP. |
| 5 | Финализация | Клиент подтверждает выбор (DHCPREQUEST), сервер закрепляет адрес (DHCPACK). |

### Сценарий 3: Современный стек (QUIC / HTTP3)

В HTTP/3 транспортный уровень изменяется:
- Вместо TCP используется **QUIC**, работающий поверх **UDP**.
- Шифрование (TLS 1.3) интегрировано непосредственно в QUIC.
- Это позволяет избежать "блокировки начала очереди" (Head-of-Line Blocking) и ускорить установку соединения (0-RTT).

### Сценарий 4: Облачные сети (Overlay-сети)

В Kubernetes и облачных средах часто используются наложенные (overlay) сети (например, VXLAN).
- Исходный L2/L3 пакет инкапсулируется в другой UDP-пакет.
- Это позволяет создавать виртуальные L2-сегменты поверх маршрутизируемой L3-инфраструктуры.
- **PDU в этом случае:** `[Физический L2][Физический L3][UDP/VXLAN][Виртуальный L2][Виртуальный L3][Данные]`.

## Инструментарий диагностики

Для эффективной работы DevOps/SRE важно знать, на каком уровне модели работает инструмент:

| Уровень | Инструменты диагностики | Назначение |
| :--- | :--- | :--- |
| **L7 (Прикладной)** | `curl`, `wget`, `dig`, `nslookup`, `telnet`, `openssl s_client`, `grpcurl` | Тестирование HTTP/HTTPS, DNS, TLS, gRPC |
| **L4 (Транспортный)** | `ss` (заменяет `netstat`), `nc` (netcat), `nmap`, `iperf3`, `tcpdump` (фильтр по порту) | Тестирование портов, производительности TCP/UDP |
| **L3 (Сетевой)** | `ip addr`, `ip route`, `ping`, `traceroute`, `mtr`, `tcpdump` | Маршрутизация, доступность, задержки |
| **L2 (Канальный)** | `arp`, `ip neigh`, `bridge link`, `ethtool -i` | ARP-таблицы, VLAN, состояние интерфейсов |
| **L1 (Физический)** | `ethtool`, `ip link`, `dmesg`, логи коммутатора (CRC errors, flaps) | Состояние кабелей, скорости, ошибки |

**Примеры использования:**

```bash
# L7: Тестирование HTTP-ответа
curl -I https://example.com
# → HTTP/2 200, server: cloudflare

# L7: Проверка DNS-резолвинга
dig example.com A +short
# → 93.184.216.34

# L7: Проверка TLS-соединения
openssl s_client -connect example.com:443 -servername example.com
# → Protocol: TLSv1.3, Cipher: TLS_AES_256_GCM_SHA384

# L4: Проверка доступности TCP-порта
nc -zv 192.168.1.1 22
# → Connection to 192.168.1.1 22 port [tcp/ssh] succeeded!

# L4: Просмотр активных соединений
ss -tnp
# → State  Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process

# L4: Тест пропускной способности
iperf3 -c 192.168.1.100 -t 10
# → [ ID] Interval       Transfer     Bitrate

# L3: Проверка маршрута
traceroute -n 8.8.8.8
# → 1  192.168.1.1  0.5 ms
#   2  10.0.0.1     1.2 ms

# L3: Анализ сетевого трафика
tcpdump -i eth0 host 192.168.1.100 -nn
# → tcpdump: verbose output suppressed, use -v for detail

# L2: Просмотр ARP-таблицы
ip neigh show
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE

# L1: Проверка состояния интерфейса
ethtool eth0
# → Speed: 1000Mb/s, Duplex: Full, Link detected: yes
```

### Современные технологии и стек TCP/IP

Модель TCP/IP адаптируется к новым требованиям производительности и масштабируемости:

**Высокопроизводительная обработка пакетов:**
- **eBPF (extended Berkeley Packet Filter):** Выполнение пользовательского кода в ядре Linux на разных уровнях стека. XDP (eXpress Data Path) работает на уровне L2/L3, обрабатывая пакеты до основного стека ядра — для создания высокопроизводительных брандмауэров и балансировщиков.
- **DPDK (Data Plane Development Kit):** Приложения в пользовательском пространстве напрямую обрабатывают пакеты, минуя ядро. Используется для создания высокопроизводительных VNF (Virtual Network Functions).

**Облачные и контейнерные сети:**
- **Overlay-сети (VXLAN, Geneve):** Создают виртуальные L2-сегменты поверх L3-инфраструктуры. Инкапсулируют Ethernet-кадры в UDP-пакеты для масштабирования L2 через L3-маршрутизаторы.
- **Service Mesh (Istio, Linkerd):** Работают на L7, добавляя sidecar-прокси (Envoy) для управления трафиком между микросервисами — circuit breaking, retry, observability.
- **CNI-плагины Kubernetes:** Calico (BGP/routing), Flannel (VXLAN), Cilium (eBPF) — реализуют сетевую политику и маршрутизацию на уровне контейнеров.

**Программируемые сети (SDN):**
- **OpenFlow:** Разделение control plane и data plane — контроллер управляет коммутаторами L2/L3 централизованно.
- **P4:** Язык программирования для определения обработки пакетов на коммутаторах, адаптация оборудования под нестандартные протоколы.

### Безопасность и DDoS-атаки

Понимание уровней модели TCP/IP критично для выбора средств защиты:

| Тип атаки | Уровень | Механизм | Защита |
| :--- | :--- | :--- | :--- |
| **SYN-flood** | L4 | Заваливание SYN-пакетами для исчерпания очередей TCP | SYN cookies, увеличение backlog, Anycast |
| **UDP-flood** | L4 | Поток UDP-пакетов для забивания канала | Rate-limiting, фильтрация на уровне провайдера |
| **ICMP-flood (Ping flood)** | L3 | Поток ICMP Echo Request | Фильтрация ICMP, ограничение скорости |
| **HTTP-flood** | L7 | Имитация легитимных HTTP-запросов | WAF, CAPTCHA, анализ поведения |
| **Slowloris** | L7 | Медленное открытие соединений для исчерпания воркеров | Таймауты, rate-limiting |
| **DNS amplification** | L3/L7 | Усиление DNS-запросов для DDoS | BCP38 (anti-spoofing), response rate limiting |

**Примеры защиты:**
```bash
# Защита от SYN-flood (Linux)
sysctl -w net.ipv4.tcp_syncookies=1
sysctl -w net.ipv4.tcp_max_syn_backlog=2048

# Ограничение количества соединений с одного IP (iptables)
iptables -A INPUT -p tcp --dport 80 -m connlimit --connlimit-above 50 -j DROP

# Rate-limiting ICMP
iptables -A INPUT -p icmp --icmp-type echo-request -m limit --limit 1/s -j ACCEPT
```
