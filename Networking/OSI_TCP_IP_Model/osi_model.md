# Модель OSI

## Определения

**Модель OSI (Open Systems Interconnection Reference Model)** — концептуальная семиуровневая модель, разработанная ISO для стандартизации сетевых функций и обеспечения совместимости различных технологий. Она описывает, как данные проходят путь от приложения на одном компьютере до приложения на другом.

Вся сетевая инженерия — это, по сути, **набор протоколов**, где каждый следующий уровень решает проблему, которую не решил предыдущий. Модель OSI служит универсальным «языком» для описания сетевых процессов.

**Открытая система** — система (компьютер, сетевое устройство), соответствующая открытым стандартам и способная взаимодействовать с другими открытыми системами независимо от производителя.

### История и стандарты

| Параметр | Значение |
| :--- | :--- |
| **Разработчик** | ISO совместно с IEC |
| **Стандарт** | ISO/IEC 7498-1:1994 |
| **Год принятия** | 1984 |
| **Текущий статус** | Теоретическая основа, вытеснена практической [моделью TCP/IP](./tcp_ip_model.md) |

## Базовые концепции

### Уровни модели OSI

Каждый уровень решает свою задачу и ничего не знает о том, что происходит выше или ниже (принцип инкапсуляции). Взаимодействие происходит только с соседними уровнями через интерфейсы и с аналогичным уровнем удаленной системы через протоколы.

| Уровень (Layer) | PDU (Тип данных) | Основные функции | Примеры | Оборудование |
| :--- | :--- | :--- | :--- | :--- |
| **7. Прикладной (Application)** | **Данные (Data)** | Интерфейс взаимодействия приложений с сетью. | HTTP, FTP, DNS, gRPC, SMTP, SSH | Хосты, L7-WAF, Proxy |
| **6. Представления (Presentation)** | **Данные (Data)** | Кодирование, сжатие, шифрование, сериализация. | SSL/TLS, JSON, XML, JPEG, ASCII | Хосты |
| **5. Сеансовый (Session)** | **Данные (Data)** | Управление сеансами (создание, поддержание, разрыв, чекпоинты). | RPC, NetBIOS, Sockets API | Хосты |
| **4. Транспортный (Transport)** | **Сегменты / Дейтаграммы**| Доставка между процессами, контроль целостности и потока. | TCP, UDP, SCTP, QUIC | Хосты, L4-FW, Балансировщики (NLB) |
| **3. Сетевой (Network)** | **Пакеты (Packets)** | Логическая адресация и выбор пути (маршрутизация). | IPv4, IPv6, ICMP, IPsec, BGP | Маршрутизатор, L3-Switch |
| **2. Канальный (Data Link)** | **Кадры (Frames)** | Физическая адресация, доставка в локальной сети, контроль ошибок. | Ethernet, Wi-Fi, ARP, STP | Коммутатор (Switch), Bridge |
| **1. Физический (Physical)** | **Биты (Bits)** | Передача сигналов по физической среде. | Кабели (UTP, Fiber), Радиоволны, SFP | Хаб, Репитер, Медиаконвертер |

*   **Верхние уровни (Host layers): 7–4** — реализуются программно в ОС и приложениях. Фокус на данных и взаимодействии процессов.
*   **Нижние уровни (Media layers): 1–3** — реализуются аппаратно и программно. Фокус на передаче через среду.

### Единицы данных (PDU) и Инкапсуляция

Процесс передачи данных основана на двух ключевых процессах: **инкапсуляции** (при отправке) и **декапсуляции** (при получении). Каждый уровень добавляет свой заголовок (и иногда трейлер) к данным, полученным от вышестоящего уровня.

| Уровень | PDU (Единица данных) | Состав | Размер заголовка |
| :--- | :--- | :--- | :--- |
| **L7. Прикладной** | Данные (Data) | Полезная нагрузка приложения (HTTP-запрос, JSON, XML) | Зависит от протокола |
| **L6. Представления** | Данные (Data) | Кодированные/сжатые/зашифрованные данные | Зависит от алгоритма |
| **L5. Сеансовый** | Данные (Data) | Данные с информацией о сеансе (идентификаторы, контрольные точки) | Зависит от протокола |
| **L4. Транспортный** | **Сегмент (TCP) / Дейтаграмма (UDP)** | [L4 заголовок (20-60 байт)] + Данные | 20 байт (минимум) |
| **L3. Сетевой** | **Пакет (Packet)** | [L3 заголовок (20-60 байт)] + Сегмент/Дейтаграмма | 20 байт (IPv4) / 40 байт (IPv6) |
| **L2. Канальный** | **Кадр (Frame)** | [L2 заголовок (14-22 байта)] + Пакет + [FCS/CRC (4 байта)] | 14-22 байта |
| **L1. Физический** | **Биты (Bits)** | Электрические/оптические/радиосигналы | Н/П (физический уровень) |

**Схема инкапсуляции:**

```text
[ Прикладной ] ----> Данные (Data)
[ Представления] ----> [H6][ Данные ]
[ Сеансовый ] ----> [H5][ Данные ]
[ Транспортный ] ----> [H4 (Порты)][ Данные ] = СЕГМЕНТ
[ Сетевой ] ----> [H3 (IP)][ Сегмент ] = ПАКЕТ
[ Канальный ] ----> [H2 (MAC)][ Пакет ][T2 (CRC)] = КАДР
[ Физический ] ----> 0101010110... = БИТЫ
```

**Детальный пример инкапсуляции (HTTP GET запрос):**

```text
Данные приложения (HTTP GET /api/data HTTP/1.1\r\nHost: example.com)
         ↓
[TCP заголовок: Src=49152, Dst=80, Seq=1, Ack=1, Flags=SYN] + Данные = TCP-сегмент
         ↓
[IP заголовок: Src=192.168.1.100, Dst=93.184.216.34, TTL=64] + Сегмент = IP-пакет
         ↓
[Ethernet заголовок: Src MAC=AA:BB:CC:DD:EE:FF, Dst MAC=00:11:22:33:44:55] + Пакет + [FCS] = Ethernet-кадр
         ↓
Биты (электрические сигналы в UTP-кабиле или световые в оптике)
```

**Важные правила инкапсуляции:**

1.  **IP-адреса** (L3) остаются неизменными от отправителя до получателя (за исключением NAT). Они определяют конечные точки коммуникации.
2.  **MAC-адреса** (L2) меняются на каждом узле (маршрутизаторе), так как они отвечают за доставку только до следующего «хопа» в локальном сегменте. Коммутатор (L2) не изменяет MAC-адреса.
3.  **Порты** (L4) остаются неизменными на протяжении всего маршрута (за исключением PAT/NAT).

**MTU (Maximum Transmission Unit) и MSS (Maximum Segment Size):**

- **MTU:** Максимальный размер IP-пакета (L3). По умолчанию для Ethernet — 1500 байт. Для jumbo frames — до 9000 байт.
- **MSS:** Максимальный размер полезной нагрузки TCP-сегмента (L4). Рассчитывается как: `MSS = MTU - (IP Header) - (TCP Header)`. Обычно это 1460 байт (1500 - 20 - 20).
- **Проблема:** Несоответствие MSS/MTU (например, при туннелировании) без механизма PMTUD (Path MTU Discovery) приводит к фрагментации или молчаливому отбрасыванию пакетов (blackhole).
- **Решение:** TCP MSS Clamping — установка максимального размера сегмента меньше MTU для учета заголовков туннеля.

### Логическое взаимодействие (Peer-to-Peer)

Уровни одной системы взаимодействуют с соответствующими уровнями другой системы так, будто они соединены напрямую. Например, L4 на стороне отправителя добавляет порядковый номер TCP-сегмента, который проверяется L4 на стороне получателя, при этом промежуточные узлы (маршрутизаторы L3) этот номер не анализируют.

**Пиры (peers)** — сущности одного уровня на разных машинах. Пирами могут быть процессы, устройства или люди — глобально это абстракция, означающая «сущности одного уровня».

**Ключевая особенность:** общение пиров — виртуальное. Два HTTP-пира (клиент и сервер) считают, что разговаривают напрямую, горизонтально. В коде это выглядит буквально так: вызывается метод `http.post()`, сервер вызывает `http.listen()`. Однако ни один байт не летит горизонтально — данные едут «лифтом» вниз до физической среды, потом по проводу, затем «лифтом» вверх в обратном порядке.

```
Виртуальное общение (пунктир):  L7 ←——————→ L7
                                    ↓
Физическое перемещение (сплошная): L7 → L6 → L5 → L4 → L3 → L2 → L1 → Кабель → L1 → L2 → L3 → L4 → L5 → L6 → L7
```

Абстракция пера позволяет думать горизонтально, хотя всё на самом деле движется вертикально. Без этой абстракции проектирование компьютерных сетей было бы задачей неподъёмной: разработчик пишет `send` и представляет собеседника, а не семь слоёв под собой.

## Практические сценарии

### Сценарий 1: Запрос веб-страницы (HTTPS) — прохождение по уровням OSI

| Шаг | Уровень | Действие | Детали |
| :--- | :--- | :--- | :--- |
| 1 | **L7 (Прикладной)** | Браузер формирует HTTP GET-запрос | Создается HTTP-сообщение с заголовками (Host, User-Agent, Accept) и телом запроса |
| 2 | **L6 (Представления)** | TLS-шифрование данных | HTTP-сообщение шифруется с помощью TLS 1.3 (AES-256-GCM). Добавляется TLS-заголовок |
| 3 | **L5 (Сеансовый)** | Управление TLS-сеансом | УстанавливаетсяTLS-сеанс с уникальным Session ID, согласовываются параметры шифрования |
| 4 | **L4 (Транспортный)** | Создание TCP-сегмента | Порт источника (динамический, например 49152) → Порт назначения (443). Добавляется TCP-заголовок с флагами SYN для установки соединения |
| 5 | **L3 (Сетевой)** | Создание IP-пакета | IP клиента (например, 192.168.1.100) → IP сервера (93.184.216.34). Добавляется IP-заголовок с TTL |
| 6 | **L2 (Канальный)** | Инкапсуляция в Ethernet-кадр | MAC клиента → MAC шлюза (через ARP-запрос если не известен). Добавляется Ethernet-заголовок и FCS |
| 7 | **L1 (Физический)** | Передача битов | Электрические сигналы в UTP-кабиле или световые — в оптическом волокне |
| 8 | **Прохождение** | Пакет проходит через роутеры | На каждом хопе L2-заголовок перезаписывается (новый MAC-адрес следующего узла), L3 и L4 остаются неизменными |
| 9 | **Прием** | Сервер выполняет декапсуляцию | Последовательно снимаются заголовки L1→L2→L3→L4→L5→L6, данные передаются веб-серверу на L7 |

### Сценарий 2: DNS-резолвинг (получение IP-адреса по имени)

| Шаг | Уровень | Действие |
| :--- | :--- | :--- |
| 1 | **L7** | Приложение (или ОС) формирует DNS-запрос A-записи для `example.com` |
| 2 | **L6** | Данные кодируются в формат DNS (бинарный протокол) |
| 3 | **L5** | Устанавливается DNS-сеанс (обычно UDP, без установленного соединения) |
| 4 | **L4** | UDP-дейтаграмма: порт клиента (динамический) → порт DNS-сервера (53) |
| 5 | **L3** | IP-пакет: клиент → DNS-сервер (например, 8.8.8.8) |
| 6 | **L2** | Ethernet-кадр: MAC клиента → MAC шлюза |
| 7 | **L1** | Передача по физической среде |

### Траблшутинг по уровням OSI

Метод «разделяй и властвуй» в диагностике сетей (обычно снизу вверх):

1.  **L1 (Физический):** Горят ли лампочки на порту? Цел ли кабель? Есть ли питание? Не повреждены ли SFP-модули?
2.  **L2 (Канальный):** Видит ли коммутатор MAC-адрес устройства (`show mac address-table`)? Нет ли ошибок в VLAN? Проходит ли ARP-запрос? Не заблокирован ли порт протоколом STP?
3.  **L3 (Сетевой):** Проходит ли `ping` до шлюза или удаленного хоста? Верна ли таблица маршрутизации (`ip route`)? Нет ли проблем с MTU (фрагментация)?
4.  **L4 (Транспортный):** Открыт ли нужный порт (`nc -zv`, `telnet`)? Проходит ли TCP-рукопожатие (Handshake)? Не блокирует ли трафик Firewall или Security Group?
5.  **L5/L6 (Сеансовый/Представления):** Нет ли проблем с TLS-сертификатами (истекли, неверный CA)? Корректна ли кодировка данных? Совпадают ли версии протоколов сериализации (например, Protobuf)?
6.  **L7 (Прикладной):** Что в логах приложения? Корректен ли HTTP-запрос (заголовки, метод)? Нет ли ошибок аутентификации (401/403) или проблем на стороне бэкенда (5xx)?

### Сравнение балансировщиков трафика

| Параметр | L4-балансировщик (NLB) | L7-балансировщик (ALB/Ingress) |
| :--- | :--- | :--- |
| **База принятия решений** | IP, TCP/UDP порт | URL, заголовки HTTP, Cookies, SNI |
| **Производительность** | Экстремально высокая (анализ только L4-заголовков) | Ниже (требуется парсинг L7-данных) |
| **Безопасность** | Базовая фильтрация по IP/Port | Глубокий анализ (WAF), терминация SSL/TLS |
| **Возможности** | Прозрачная проксируемость | Sticky Sessions, Path-based routing, манипуляция заголовками |
| **Примеры** | IPVS, HAProxy (TCP mode), AWS NLB | Nginx, Envoy, Traefik, AWS ALB |

### Безопасность и DDoS-атаки

*   **L3/L4 атаки:** SYN-flood, UDP-flood. Цель — забить канал или исчерпать ресурсы сетевого стека. Защита: фильтрация на уровне провайдера, Anycast, увеличение очередей TCP.
*   **L7 атаки:** HTTP-flood, Slowloris. Цель — исчерпать ресурсы приложения (CPU, RAM, коннекты к БД). Защита: Rate-limiting, WAF, анализ поведения пользователей.

### Инструментарий диагностики по уровням OSI

Для эффективной работы DevOps/SRE важно знать, на каком уровне модели работает инструмент:

| Уровень | Инструменты диагностики | Назначение |
| :--- | :--- | :--- |
| **L7 (Прикладной)** | `curl`, `wget`, `dig`, `nslookup`, `telnet`, `openssl s_client`, `grpcurl` | Тестирование HTTP/HTTPS, DNS, TLS, gRPC |
| **L6 (Представления)** | `openssl s_client`, `openssl x509`, `curl -v` | Проверка TLS-сертификатов, шифрования |
| **L5 (Сеансовый)** | `ss`, `netstat`, `lsof` | Мониторинг активных сеансов и соединений |
| **L4 (Транспортный)** | `ss`, `nc` (netcat), `nmap`, `iperf3`, `tcpdump` (фильтр по порту) | Тестирование портов, производительности TCP/UDP |
| **L3 (Сетевой)** | `ip addr`, `ip route`, `ping`, `traceroute`, `mtr`, `tcpdump` | Маршрутизация, доступность, задержки |
| **L2 (Канальный)** | `arp`, `ip neigh`, `bridge link`, `ethtool -i`, `brctl show` | ARP-таблицы, VLAN, состояние интерфейсов |
| **L1 (Физический)** | `ethtool`, `ip link`, `dmesg`, логи коммутатора (CRC errors, flaps) | Состояние кабелей, скорости, ошибки |

**Примеры использования:**

```bash
# L7: Тестирование HTTP-ответа
curl -I https://example.com
# → HTTP/2 200, server: cloudflare

# L6: Проверка TLS-сертификата
openssl s_client -connect example.com:443 -servername example.com
# → Protocol: TLSv1.3, Cipher: TLS_AES_256_GCM_SHA384

# L5: Просмотр активных TCP-соединений
ss -tnp
# → State  Recv-Q Send-Q  Local Address:Port  Peer Address:Port  Process

# L4: Проверка доступности порта
nc -zv 192.168.1.1 22
# → Connection to 192.168.1.1 22 port [tcp/ssh] succeeded!

# L3: Проверка маршрута
traceroute -n 8.8.8.8
# → 1  192.168.1.1  0.5 ms
#   2  10.0.0.1     1.2 ms

# L2: Просмотр ARP-таблицы
ip neigh show
# → 192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE

# L1: Проверка состояния интерфейса
ethtool eth0
# → Speed: 1000Mb/s, Duplex: Full, Link detected: yes
```

## Дополнительная информация

### Роль в современной практике

Хотя Интернет построен на базе стека TCP/IP, модель OSI остается незаменимой:
*   **Универсальный стандарт:** позволяет разным вендорам (Cisco, Juniper, Arista) взаимодействовать друг с другом.
*   **Аналитический инструмент:** помогает декомпозировать сложные архитектурные проблемы на понятные зоны ответственности.
*   **Обучение:** дает фундамент для понимания того, как работают инкапсуляция и абстракция в ИТ-системах.

### Современные технологии и модели OSI

Модель OSI остается актуальной даже с появлением новых технологий, хотя некоторые из них абстрагируются от строгого разделения уровней:

**Высокопроизводительная обработка пакетов:**
- **eBPF (extended Berkeley Packet Filter):** Позволяет выполнять пользовательский код в ядре Linux на разных уровнях стека. Например, XDP (eXpress Data Path) работает на уровне L2/L3, обрабатывая пакеты до того, как они попадут в основной стек ядра. Это позволяет создавать высокопроизводительные брандмауэры и балансировщики.
- **DPDK (Data Plane Development Kit):** Позволяет приложениям в пользовательском пространстве напрямую обрабатывать пакеты, минуя ядро. Используется для создания высокопроизводительных виртуальных сетевых функций (VNF).

**Облачные и контейнерные сети:**
- **Overlay-сети (VXLAN, Geneve):** Создают виртуальные L2-сегменты поверх L3-инфраструктуры. Инкапсулируют оригинальные Ethernet-кадры в UDP-пакеты, что позволяет масштабировать L2-сегменты через L3-маршрутизаторы.
- **Service Mesh (Istio, Linkerd):** Работают на L7, добавляя sidecar-прокси (Envoy) для управления трафиком между микросервисами. Реализуют circuit breaking, retry, observability на прикладном уровне.

**Программируемые сети (SDN):**
- **OpenFlow:** Протокол, позволяющий контроллеру SDN управлять коммутаторами L2/L3, разделяя control plane (решения о маршрутизации) и data plane (фактическая передача пакетов).
- **P4 (Programming Protocol-independent Packet Processors):** Язык программирования для определения того, как коммутаторы обрабатывают пакеты на L2/L3, что позволяет адаптировать оборудование под нестандартные протоколы.

### Сравнение моделей OSI и TCP/IP

| Уровни OSI | Уровень TCP/IP | Обоснование |
| :--- | :--- | :--- |
| **L7. Прикладной** | **Прикладной** | В TCP/IP шифрование, сжатие и управление сеансами возложены на само приложение или специализированные библиотеки (например, OpenSSL). |
| **L6. Представления** | | |
| **L5. Сеансовый** | | |
