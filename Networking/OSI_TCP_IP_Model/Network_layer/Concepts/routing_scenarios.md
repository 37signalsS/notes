# Практические сценарии маршрутизации

## Определения

**Шлюз по умолчанию (Default Gateway)** — сетевой узел (обычно маршрутизатор), которому хост пересылает IP-пакеты в случае, если адрес назначения находится за пределами текущей локальной подсети и для него нет более специфичного маршрута. В таблице маршрутизации обозначается как префикс `0.0.0.0/0`.

**Прямая доставка (Direct Delivery)** — процесс передачи данных между узлами в рамках одного широковещательного домена (L2-сегмента), не требующий участия маршрутизатора на сетевом уровне.

## Базовые концепции

### Алгоритм принятия решения о маршрутизации на хосте

При отправке пакета стек TCP/IP выполняет следующую логику:

1.  **Локальность:** Применяет маску подсети к IP-адресу назначения. Если полученный адрес сети совпадает с адресом локальной сети интерфейса — используется **прямая доставка** через [ARP](../../../Protocols/arp.md).
2.  **Таблица маршрутов:** Если адрес внешний, ОС ищет наиболее точное совпадение (Longest Prefix Match) в таблице маршрутизации.
3.  **Default Gateway:** Если специфичный маршрут не найден, пакет отправляется на шлюз по умолчанию.

## Практические сценарии

### Сценарий 1: Прямая доставка в одном L2-сегменте

**Условия:**
- Хост А: `192.168.1.10/24`, MAC: `AA:AA`
- Хост Б: `192.168.1.20/24`, MAC: `BB:BB`

**Процесс:**
1. Хост А видит, что `192.168.1.20` входит в его подсеть `192.168.1.0/24`.
2. Хост А проверяет свою ARP-таблицу. Если записи нет, отправляет широковещательный ARP-запрос.
3. Получив ответ, Хост А инкапсулирует IP-пакет в Ethernet-кадр с MAC-адресом назначения `BB:BB`.
4. Пакет доставляется через коммутатор напрямую.

### Сценарий 2: Маршрутизация через Default Gateway

**Условия:**
- Хост А: `192.168.1.10/24`, Gateway: `192.168.1.1`
- Цель: `8.8.8.8` (Google DNS)

**Процесс:**
1. Хост А определяет, что `8.8.8.8` не принадлежит локальной сети.
2. Ищет маршрут к `8.8.8.8`, находит только `default via 192.168.1.1`.
3. Пакет инкапсулируется в кадр, где **IP назначения = 8.8.8.8**, но **MAC назначения = MAC шлюза** (`192.168.1.1`).
4. Маршрутизатор получает кадр, видит свой MAC, «вскрывает» его до IP-уровня, анализирует `8.8.8.8` и пересылает дальше по своим таблицам.

### Сценарий 3: Асимметричная маршрутизация и Reverse Path Filter (rp_filter)

**Проблема:** Трафик входит в сервер через один интерфейс (`eth0`), а политика маршрутизации или шлюз по умолчанию заставляют ответ уходить через другой (`eth1`).

**Последствия:**
- Большинство современных брандмауэров и систем защиты (например, в Linux) отбросят такой пакет по механизму **RPF (Reverse Path Filtering)**, так как «ответ пришел не оттуда, куда мог бы уйти запрос».
- Решение в Linux: настройка `net.ipv4.conf.all.rp_filter` или использование **Policy-Based Routing (PBR)**.

### Сценарий 4: Разделение трафика через Policy-Based Routing (PBR)

**Задача:** Направлять трафик от приложения «А» через канал провайдера 1, а трафик приложения «Б» — через провайдера 2 (или VPN).

**Реализация:**
1. Создаются дополнительные таблицы маршрутизации в `/etc/iproute2/rt_tables`.
2. Используются правила `ip rule` для выбора таблицы на основе IP-адреса источника (`from`), маркировки пакета (`fwmark`) или интерфейса.
3. Подробнее см. в разделе **[Сценарии PBR](../../../../../Linux/Networking/Policy_Based_Routing/scenarios.md)**.

### Сценарий 5: Изоляция трафика через VRF (Virtual Routing and Forwarding)

**Задача:** Запустить на одном сервере два процесса, которые должны иметь одинаковые IP-адреса, но находиться в изолированных сетевых окружениях (например, для тестов или мультитенантности).

**Концепция:**
- **VRF** позволяет создавать несколько независимых таблиц маршрутизации и привязывать к ним конкретные интерфейсы.
- Это «VLAN для L3». Трафик в одной VRF-таблице полностью невидим для другой, даже если IP-адреса перекрываются.
- Подробнее: **[VRF в Linux](../../../../../Linux/Networking/vrf.md)**.

### Сценарий 6: Маршрутизация в облачных VPC

В облаках (Yandex Cloud, AWS) маршрутизация управляется на уровне SDN (Software Defined Networking):
- **Таблицы маршрутов подсетей:** Каждая подсеть имеет привязанную таблицу.
- **Internet Gateway / NAT Gateway:** Специфичные узлы, которые являются «шлюзом по умолчанию» для выхода в мир.
- В отличие от классических сетей, здесь нельзя просто «поднять» IP на интерфейсе; он должен быть разрешен в управляющей панели облака (Security Groups / Allow IP Forwarding).

### Сценарий 7: Типичная ошибка — маршрут на IP вместо сети

**Ошибка:** Попытка добавить маршрут как `ip route add 192.168.10.5/24 via ...`.
**Причина сбоя:** Маска `/24` указывает, что запись относится к сети `192.168.10.0`. Если в записи указан хост `.5`, ядро может либо проигнорировать её, либо интерпретировать как маршрут к хосту `/32`, что приведет к недоступности остальных узлов сети `192.168.10.0/24`.

**Правило:** В таблицах маршрутизации всегда указывайте **адрес сети** (хостовая часть обнулена по маске).

### Сценарий 8: Anycast маршрутизация

**Принцип:** Один и тот же IP-адрес анонсируется из разных географических точек.
- Пакет пользователя доставляется до **ближайшего** (с точки зрения метрик BGP/OSPF) узла.
- Широко используется в DNS (8.8.8.8, 1.1.1.1) и CDN для минимизации задержек (RTT).
