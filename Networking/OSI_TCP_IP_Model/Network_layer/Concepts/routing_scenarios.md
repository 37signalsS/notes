# Практические сценарии маршрутизации

## Определения

**Шлюз по умолчанию (Default Gateway)** — маршрутизатор, которому хост отправляет пакеты, адресованные устройствам за пределами локальной подсети. Подробнее о его роли и настройке см. в [Маршрутизация в Linux](../../../../../Linux/SystemAdministration/routing.md#4-маршрут-по-умолчанию-default-gateway).

## Базовые концепции

### Логика маршрутизации на хосте

Ключевая задача [сетевого уровня](./network_layer_overview.md) на хосте — определить, как доставить пакет:

- **Напрямую получателю** — если адресат в той же локальной сети.
- **На шлюз по умолчанию** — если адресат во внешней сети.

Решение принимается путём сравнения адреса сети отправителя и получателя с использованием маски подсети. Этот процесс является фундаментальной частью IP-маршрутизации.

## Практические сценарии

### Сценарий 1: Обмен трафиком в одной подсети

**Условия:**

- Хост **А**: `192.168.1.10/24`
- Хост **Б**: `192.168.1.20/24`
- Маска: `255.255.255.0` (`/24`)

**Процесс:**

1. **Определение местоположения:** Хост **А** применяет маску к своему IP и IP получателя:
   - Сеть отправителя: `192.168.1.0`
   - Сеть получателя: `192.168.1.0`
   - **Вывод:** адресат в той же сети.

2. **Поиск MAC-адреса ([ARP](../../../Protocols/arp.md)):** Хост **А** отправляет **ARP-запрос**: "Кто имеет IP `192.168.1.20`?". Хост **Б** отвечает со своим MAC-адресом.

3. **Прямая отправка:** Хост **А** отправляет IP-пакет, инкапсулированный в Ethernet-кадр, напрямую на MAC-адрес хоста **Б**.

**Вывод:** Шлюз по умолчанию в этом сценарии не участвует.

### Сценарий 2: Отправка трафика во внешнюю сеть

**Условия:**

- Хост **А**: `192.168.1.10/24`
- Сервер в интернете: `8.8.8.8`
- Шлюз по умолчанию: `192.168.1.1`

**Процесс:**

1. **Определение местоположения:** Хост **А** применяет маску к IP назначения:
   - Сеть отправителя: `192.168.1.0`
   - Сеть получателя: `8.8.8.0`
   - **Вывод:** адресат во внешней сети.

2. **Отправка на шлюз:**
   - IP-пакет инкапсулируется в Ethernet-кадр.
   - MAC-адрес назначения = **MAC-адрес шлюза** (получен через ARP).
   - IP-адрес назначения = `8.8.8.8` (конечный сервер).

3. **Дальнейшая маршрутизация:** Шлюз распаковывает кадр, анализирует IP назначения (`8.8.8.8`) и пересылает пакет дальше на основе своей таблицы маршрутизации.

**Вывод:** Шлюз необходим для связи с любыми устройствами за пределами локальной подсети.

### Сценарий 3: Разные IP-сети на одном канальном уровне

**Условия:**

- Три хоста подключены к одному коммутатору (L2).
- Хост 1: `192.168.1.1/24`
- Хост 2: `192.168.1.2/24`
- Хост 3: `192.168.0.3/24`
- Все хосты в одном широковещательном домене L2, но в разных IP-сетях.

**Проблема:**

Хост 1 и хост 2 находятся в одной IP-сети `192.168.1.0/24` и могут обмениваться данными напрямую на L2/L3. Хост 3 физически подключен к тому же коммутатору, но находится в другой IP-сети `192.168.0.0/24`.

**Результат:**

- **L1/L2:** Все хосты могут обмениваться кадрами (физическая и канальная доступность).
- **L3:** Хост 1 и хост 3 не "видят" друг друга на сетевом уровне, так как адреса сетей не совпадают.

**Таблица маршрутизации хоста 1 (начальная):**

| IP сеть назначения | IP адрес маршрутизатора | Интерфейс | Комментарий |
| :--- | :--- | :--- | :--- |
| `192.168.1.0/24` | `192.168.1.1` | eth0 | Добавляется автоматически при настройке IP |

**Решение — добавление статических маршрутов:**

Для обеспечения связи между хостами 1 и 3 необходимо добавить маршруты.

```bash
# На хосте 1 — маршрут до сети 192.168.0.0/24 напрямую
ip route add 192.168.0.0/24 dev eth0

# На хосте 3 — маршрут до сети 192.168.1.0/24 напрямую
ip route add 192.168.1.0/24 dev eth0
```

**Таблица маршрутизации хоста 1 (после добавления):**

| IP сеть назначения | IP адрес маршрутизатора | Интерфейс |
| :--- | :--- | :--- |
| `192.168.1.0/24` | `192.168.1.1` | eth0 |
| `192.168.0.0/24` | `0.0.0.0` | eth0 |

После добавления маршрутов хосты 1 и 3 смогут обмениваться данными напрямую, несмотря на разные IP-сети.

**Вывод:** Физическое подключение к одному коммутатору не гарантирует доступность на сетевом уровне. Для связи между разными IP-сетями требуются соответствующие записи в таблице маршрутизации.

### Сценарий 5: Типичная ошибка — IP-адрес вместо IP-сети

При настройке таблиц маршрутизации новички часто прописывают конкретный **IP-адрес** хоста вместо **IP-сети**. В результате маршрут не работает.

**Суть проблемы:** В таблице маршрутизации должны указываться **IP-сети**, так как логика поиска маршрута основана на применении маски к адресу назначения.

#### Почему это не работает? (Пример)

Рассмотрим маршрутизатор с ошибочными записями (вместо сетей указаны адреса):

1. `192.168.10.2/24`
2. `192.168.20.2/24`

Пакет приходит для адреса назначения **192.168.20.2** (хост 2).

**Алгоритм маршрутизатора:**

1. **Проверка записи 1:**
   - Применяет маску `/24` к адресу назначения `192.168.20.2` → получает `192.168.20.0`.
   - Сравнивает с адресом в записи: `192.168.20.0 ≠ 192.168.10.2`.
   - Маршрут не подходит.
2. **Проверка записи 2:**
   - Применяет маску `/24` к адресу назначения `192.168.20.2` → получает `192.168.20.0`.
   - Сравнивает с адресом в записи: `192.168.20.0 ≠ 192.168.20.2`.
   - **Внимание:** Несмотря на то, что адрес совпал с хостом, равенства нет, так как маскированный IP (`.0`) не равен IP-адресу в таблице (`.2`).
   - Маршрут не подходит.

**Итог:** Пакет отбрасывается, так как подходящих маршрутов нет.

**Вывод:** Всегда указывайте в таблице маршрутизации именно **IP-сети** (адрес сети с нулевой хостовой частью), а не отдельные IP-адреса.

### Сценарий 6: Маршрутизация VPN-трафика через промежуточный сервер

**Задача:** Пользователи подключаются к сети через VPN-сервер, но весь их интернет-трафик или трафик до определенных ресурсов должен проходить через другой внутренний сервер (шлюз), например, для фильтрации или обхода ограничений.

**Условия:**
- **VPN-сервер:** `10.8.0.1` (внутренний IP в VPN-сети), `192.168.1.10` (IP в локальной сети).
- **Шлюз (Gateway):** `192.168.1.20`.
- **Клиент VPN:** `10.8.0.5`.

**Процесс:**

1. **Настройка маршрутизации на VPN-сервере:**
   Необходимо указать VPN-серверу, что трафик, приходящий от клиентов, должен пересылаться на шлюз.
   ```bash
   # Добавление маршрута по умолчанию через шлюз для VPN-подсети (в отдельной таблице или глобально)
   ip route add default via 192.168.1.20
   ```

2. **Включение Forwarding (пересылки пакетов):**
   На обоих серверах (VPN и шлюз) должен быть разрешен форвардинг на уровне ядра Linux.
   ```bash
   sysctl -w net.ipv4.ip_forward=1
   ```

3. **Настройка NAT (MASQUERADE) на шлюзе:**
   Чтобы трафик мог вернуться обратно к VPN-клиенту, шлюз должен "маскировать" пакеты своим IP-адресом при отправке во внешнюю сеть.
   ```bash
   # На шлюзе (192.168.1.20)
   iptables -t nat -A POSTROUTING -s 10.8.0.0/24 -o eth0 -j MASQUERADE
   ```

4. **Разрешение трафика в Firewall:**
   ```bash
   iptables -A FORWARD -s 10.8.0.0/24 -j ACCEPT
   iptables -A FORWARD -d 10.8.0.0/24 -m state --state ESTABLISHED,RELATED -j ACCEPT
   ```

**Вывод:** Комбинация статической маршрутизации и правил NAT позволяет гибко управлять путями прохождения трафика даже для удаленных клиентов.
