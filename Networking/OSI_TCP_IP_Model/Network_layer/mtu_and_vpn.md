# MTU, PMTUD и диагностика в VPN/облаках

## Определения

**MTU (Maximum Transmission Unit)** — максимальный размер кадра канального уровня (L2), который может быть передан через сетевой интерфейс. Стандарт для Ethernet — **1500 байт**.

**MSS (Maximum Segment Size)** — максимальный размер полезной нагрузки **TCP-сегмента** (L4). Это объем данных, который TCP может поместить в один IP-пакет без учета заголовков.
- Формула: `MSS = MTU - (IP_Header) - (TCP_Header)`.
- Для стандартного Ethernet: `1500 - 20 - 20 = 1460 байт`.

**Path MTU (PMTU)** — наименьшее значение MTU среди всех участков пути от отправителя до получателя. Именно оно определяет реальный лимит размера пакета для сессии.

## Базовые концепции

### Path MTU Discovery (PMTUD)

Механизм (RFC 1191 для IPv4, RFC 8201 для IPv6), позволяющий хостам автоматически определять минимальный MTU на пути следования.

#### Принцип работы (IPv4)
1. Отправитель шлет пакет с флагом **DF (Don't Fragment)**.
2. Если пакет слишком велик для какого-то узла, маршрутизатор отбрасывает его и возвращает **ICMP Type 3 Code 4** (Fragmentation Needed), указывая свой MTU.
3. Отправитель снижает размер пакетов до указанного значения.

#### Принцип работы (IPv6)
Маршрутизаторы в IPv6 никогда не фрагментируют пакеты. Если пакет велик, узел шлет **ICMPv6 Type 2** (Packet Too Big). Обязательный минимальный MTU в IPv6 — **1280 байт**.

### Проблема «Черной дыры» (PMTUD Black Hole)
Если на пути следования файрволы блокируют ICMP-сообщения (Type 3/Code 4 для IPv4 или Type 2 для IPv6), отправитель никогда не узнает о необходимости снизить MTU.
- **Симптом:** Соединение (Handshake) устанавливается, но передача данных (например, загрузка страницы или вывод `ls` в SSH) «зависает» навсегда.

## Влияние туннелирования на MTU

Любая инкапсуляция добавляет свои заголовки, «отъедая» место у полезных данных.

| Технология | Оверхед (байт) | MTU (при физическом 1500) | Примечание |
| :--- | :--- | :--- | :--- |
| **IPsec (ESP)** | 56–73 | ~1420 | Зависит от алгоритма шифрования |
| **WireGuard** | 60–80 | 1420 | Рекомендуемый стандарт |
| **VXLAN** | 50 | 1450 | Стандарт для Overlay в облаках |
| **GENEVE** | 50+ | 1450 | Используется в современных CNI (Cilium) |
| **GRE** | 24–28 | 1476 | Базовый L3-туннель |
| **GRETAP** | 42 | 1458 | L2-over-GRE |

## Практические сценарии диагностики

### Метод 1: Проверка с помощью ping (DF-биты)
Позволяет вручную найти «потолок» MTU без фрагментации.

```bash
# -M do — запретить фрагментацию (установить DF-бит)
# -s <size> — размер данных ICMP. Итоговый MTU = size + 28 (IP+ICMP заголовки)

# Тест для MTU 1500:
ping -s 1472 -M do <ip_цели>

# Если ответ: "Frag needed and DF set (mtu = 1420)" — это значение и есть лимит.
```

### Метод 2: Использование tracepath
Утилита автоматически опрашивает узлы на пути и выводит MTU для каждого хопа.

```bash
tracepath -n google.com
# → 1:  [LOCALHOST]              pmtu 1500
# → 1:  192.168.1.1               0.2ms
# → 2:  10.0.0.1                  pmtu 1420
# → Resume: pmtu 1420
```

## Методы решения (Митигация)

### 1. TCP MSS Clamping
Самый эффективный метод для TCP-трафика. Маршрутизатор (шлюз) на лету перехватывает SYN-пакеты и принудительно уменьшает в них значение MSS до безопасного (например, 1360).

**В Linux (iptables):**
```bash
iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --set-mss 1360
```

### 2. Принудительная настройка MTU
Настройка MTU непосредственно на виртуальном интерфейсе.

```bash
# Для WireGuard или Cilium-интерфейса
ip link set dev wg0 mtu 1420
```

### 3. Разрешение ICMP
На всех межсетевых экранах **обязательно** должны быть разрешены:
- IPv4: ICMP Type 3, Code 4.
- IPv6: ICMPv6 Type 2.
