# MTU (Maximum Transmission Unit)

## Определения

**MTU (Maximum Transmission Unit)** — максимальный размер пакета (включая IP-заголовок), который может быть передан через сетевой интерфейс без фрагментации.

**Разновидности MTU:**

| Тип | Описание | Значение |
|-----|----------|----------|
| **L2 MTU (Ethernet MTU)** | Размер полезной нагрузки L2-фрейма (без заголовка Ethernet) | Локальное значение для сегмента сети |
| **L3 MTU (IP MTU)** | Размер IP-пакета (включая IP-заголовок) | Имеет значение на всём пути (Path) |
| **Media MTU** | L2 MTU + 4 байта (FCS — контрольная сумма L2-фрейма) | L2 MTU + 4 байта |
| **Path MTU** | Минимальный MTU среди всех сегментов на пути от отправителя к получателю | Определяет максимальный размер пакета для end-to-end соединения |

**Стандарт де-факто:** Path MTU = **1500 байт** (Ethernet).

**TCP MSS (Maximum Segment Size)** — максимальный размер полезной нагрузки TCP (без IP- и TCP-заголовков). Рассчитывается как:

```
MSS = MTU - IP_header (20 байт) - TCP_header (20 байт)
MSS = 1500 - 40 = 1460 байт (для стандартного Ethernet)
```

## Базовые концепции

### PDU (Protocol Data Unit)

**PDU** — единица данных протокола, включающая все служебные заголовки и полезную нагрузку.

| Уровень | PDU | Соотношение с MTU |
|---------|-----|-------------------|
| **L2** | MPDU (MAC Layer PDU) | Media MTU |
| **L3** | IP Packet | L3 MTU |
| **L4** | TCP Segment / UDP Datagram | Зависит от MSS/MTU |

**Пример расчёта для ICMP ping:**

```
L3 PDU = payload (32 байта) + IP header (20 байт) + ICMP header (8 байт) = 60 байт
```

Подробнее о структуре IP-пакета: [Структура IP-пакета (IPv4)](./Protocols/ip_packet_structure.md).

### Path MTU Discovery (PMTUD)

**PMTUD** — алгоритм определения минимального MTU на пути следования пакета (RFC 1191).

**Механизм работы:**

1. Хост A отправляет пакет хосту B с установленным **DF (Don't Fragment)** битом в IP-заголовке
2. Если на пути встречается устройство с MTU < размера пакета:
   - Устройство отбрасывает пакет
   - Отправляет ICMP **Destination Unreachable, Fragmentation Needed** (Type 3, Code 4) с указанием своего MTU
3. Хост A уменьшает MTU и повторяет отправку

**Схема PMTUD:**

```
Хост A (MTU=1500, DF=1) → [Роутер MTU=1400] → Хост B
                          ↓
                    ICMP "Fragmentation Needed (MTU=1400)"
                          ↓
Хост A (MTU=1400, DF=1) → [Роутер MTU=1400] → Хост B (успех)
```

**Проблемы PMTUD:**

| Проблема | Описание | Решение |
|----------|----------|---------|
| **ICMP заблокирован** | Файрволы блокируют ICMP Destination Unreachable | Разрешить ICMP Type 3 Code 4 |
| **DF не установлен** | Приложение не устанавливает DF-флаг | Настроить приложение/ОС |
| **Асимметричный путь** | Разные MTU в прямом и обратном направлении | Использовать TCP MSS Clamping |

### Почему VPN ломает MTU

VPN создает туннель, который инкапсулирует исходные IP-пакеты в новые пакеты с дополнительными заголовками:

| Тип VPN | Дополнительный оверхед | Эффективный MTU |
|---------|------------------------|-----------------|
| **[IPsec (ESP)](../../Tunnels/ipsec/ipsec.md)** | ~56-73 байта | ~1427-1444 байта |
| **WireGuard** | ~60 байт (IP+UDP+WireGuard) | ~1440 байт |
| **OpenVPN (UDP)** | ~69 байт | ~1431 байт |
| **GRE** | ~24 байта | ~1476 байт |

Когда исходный пакет (1500 байт) попадает в VPN-туннель, суммарный размер превышает MTU внешнего интерфейса. Это приводит к:

1. **Фрагментации** — пакет разбивается на части (если DF-флаг не установлен)
2. **Drops** — пакет отбрасывается (если DF-флаг установлен и фрагментация запрещена)
3. **Проблемам с PMTUD** — ICMP-сообщения "Fragmentation Needed" могут блокироваться файрволами

### Jumbogram (гигантские пакеты)

**Jumbogram** — IP-пакеты с MTU > 1500 байт (максимум для IPv4 = **65535 байт**).

**Особенности:**

- **Полезны только в p2p-соединениях** с гарантированной поддержкой Jumbo Frames на всех хопах
- **Бесполезны или вредны** в общем случае: высокая вероятность рассогласования MSS и дропа пакетов
- **TUN/TAP интерфейсы** часто имеют MTU по умолчанию 65535, что вызывает проблемы при использовании с VPN

**Рекомендация:** Не использовать MTU > 1500 без явной необходимости и уверенности в поддержке Path.

## Практические сценарии

### Золотое правило траблшутинга

> **Если ping до хоста работает, а приложение не работает — в 99% случаев проблема в MTU.**

**Почему ping работает:**

- Ping по умолчанию несёт **32 байта** полезной нагрузки
- L3 PDU = 32 (payload) + 20 (IP) + 8 (ICMP) = **60 байт** — пролезает везде
- Задача ping — проверить связность (маршрутизацию), а не возможность передачи больших пакетов

**Типичные сценарии проблем:**

| Сценарий | Описание |
|----------|----------|
| **Разработчик VPN** | Установил MTU 65535 на TUN/TAP интерфейсе «для эффективности» |
| **Безопасники** | Заблокировали ICMP на всех входах/выходах |
| **Провайдер** | Подрезал L3 MTU на ingress-интерфейсах маршрутизаторов |
| **Комбинация** | Все вышеперечисленное одновременно |

### Симптомы проблем с MTU (MTU mismatch)

**Ключевые признаки:**

- Сеть работает нормально: пакеты идут, CPU свободен, линк стабильный
- Соединения периодически «подвисают», throughput падает
- Мелкие пакеты (SSH, ping) работают, большие (HTTPS, SCP, файловая передача) — нет
- TCP-ретрансмиссии без явных ошибок сети
- **Intermittent drops** — периодическая потеря пакетов при стабильном соединении

**Причина:** На пути следования встречается участок с MTU меньше, чем размер отправляемых пакетов. Это приводит к:

1. **Фрагментации** — если DF-флаг не установлен (снижает производительность)
2. **Отбрасыванию пакетов** — если DF-флаг установлен (вызывает TCP retransmit)

**Решение:** Согласовать MTU на всех устройствах по пути или уменьшить MSS/TCP сегменты.

### Диагностика MTU

#### 1. Проверка MTU интерфейса

Просмотр текущего MTU сетевых интерфейсов:

```bash
ip link show <iface>
# Пример вывода:
# 2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
```

#### 2. Ручной поиск Path MTU через ping

Последовательный подбор размера пакета для нахождения максимального работающего MTU.

**Алгоритм:**

```bash
# Шаг 1: Проверка 1500 байт (1472 + 28 заголовков)
ping -M do -s 1472 8.8.8.8
# Если ошибка "Frag needed and DF set" — уменьшаем

# Шаг 2: Проверка 1470 байт
ping -M do -s 1470 8.8.8.8
# Прошло → продолжаем уменьшать

# Шаг 3: Проверка 1475 байт
ping -M do -s 1475 8.8.8.8
# Не прошло → ищем между 1470 и 1475

# Шаг 4: Проверка 1472 байт
ping -M do -s 1472 8.8.8.8
# Прошло → Path MTU = 1500 (1472 + 28)

# Шаг 5: Проверка 1473 байт
ping -M do -s 1473 8.8.8.8
# Не прошло → точка найдена
```

**Расчёт Path MTU:**

```
Path MTU = размер_payload + 28 (IP + ICMP заголовки)
Path MTU = 1472 + 28 = 1500 байт
```

**Преимущества:**

- Универсальность — `ping` доступен в любой ОС
- Не требует дополнительного ПО

**Недостатки:**

- Трудоёмкость — много ручных проверок
- Неточность — требует понимания расчётов

#### 3. Автоматическая диагностика через tracepath

Утилита `tracepath` автоматически определяет максимальный поддерживаемый размер пакета на пути до хоста:

```bash
tracepath <host>
# Пример:
tracepath example.com
```

**Преимущества `tracepath`:**

- Автоматически определяет MTU на каждом хопе
- Не требует ручного подбора размеров
- Показывает, где именно происходит ограничение MTU

**Сравнение методов:**

| Метод | Точность | Скорость | Доступность |
|-------|----------|----------|-------------|
| `ping -M do -s <size>` | Высокая | Низкая | Везде |
| `tracepath` | Средняя | Высокая | Linux/Unix |
| `mtupath` | Высокая | Высокая | Требуется установка |

#### 4. Автоматизированный поиск Path MTU (mtupath)

Утилита [mtupath](https://www.iea-software.com/products/mtupath/) автоматизирует ручной поиск и дополнительно рассчитывает MSS.

**Пример использования:**

```bash
mtupath.exe 8.8.8.8
```

**Вывод утилиты:**

- Path MTU
- Рекомендуемый MSS
- Индикация возможных «чёрных дыр» на маршруте

**Преимущества:**

- Автоматизация — не требует ручного подбора
- Дополнительная информация — расчёт MSS, детекция проблем

**Недостатки:**

- Может отсутствовать под рукой
- Требует установки

### Решения

1. **Уменьшение MTU на VPN-интерфейсе:**

   ```bash
   ip link set dev wg0 mtu 1420
   ```

2. **TCP MSS Clamping** на маршрутизаторе/VPN-шлюзе — ограничение размера TCP-сегмента в SYN-пакетах

3. **Включение PMTUD** и пропуск ICMP «Fragmentation Needed» через файрвол

4. **Настройка TUN/TAP интерфейсов:**

   ```bash
   # Уменьшить MTU с 65535 до разумного значения
   ip link set dev tun0 mtu 1500
   ```

## Дополнительная информация

### Рекомендации для безопасников

ICMP гораздо гибче, чем принято считать. На МСЭ можно:

- **Запретить** потенциально опасные типы ICMP (Redirect, Timestamp)
- **Разрешить** критичные для работы сети (Destination Unreachable, Time Exceeded, Echo Request/Reply с rate limiting)

**Пример минимально необходимого:**

- ICMP Type 3 Code 4 (Fragmentation Needed) — для PMTUD
- ICMP Type 3 (Destination Unreachable) — для диагностики
- ICMP Type 11 (Time Exceeded) — для traceroute
- ICMP Type 8/0 (Echo Request/Reply) — для мониторинга

Теория фрагментации описана в [Фрагментация IP-пакетов](./Protocols/ip_fragmentation.md). Протокол для PMTUD — [ICMP](../../Protocols/icmp.md). Утилита диагностики MTU — [ping](../../../Linux/Diagnostics/Networking/ping.md).
