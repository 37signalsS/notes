# MTU, PMTUD и его диагностика

## Определения

### Ключевые термины

- **MTU (Maximum Transmission Unit):** Максимальный размер **IP-пакета** (L3 PDU, заголовок + данные), который может быть передан через сетевой интерфейс без фрагментации. Для стандартного Ethernet MTU равен **1500 байт**.
- **Path MTU:** Минимальный MTU на всем пути от отправителя к получателю. Именно это значение определяет максимальный размер пакета для всего соединения.
- **MSS (Maximum Segment Size):** Максимальный размер **полезной нагрузки TCP-сегмента** (данных), не включая IP- и TCP-заголовки.

### Расчет MSS

MSS напрямую зависит от MTU и является ключевым параметром для TCP-соединений.

```text
MSS = Path MTU - (IP-заголовок) - (TCP-заголовок)
MSS = 1500 - 20 - 20 = 1460 байт (для стандартного Ethernet)
```

Правильная настройка MSS предотвращает IP-фрагментацию для TCP-трафика.

## Базовые концепции

### Path MTU Discovery (PMTUD)

**PMTUD** — это механизм (RFC 1191), позволяющий хосту-отправителю динамически определить `Path MTU` для конкретного соединения.

#### Механизм работы

1. Хост-отправитель (A) отправляет пакеты с установленным флагом **DF (Don't Fragment)** в IP-заголовке.
2. Если на пути встречается маршрутизатор с MTU, меньшим, чем размер пакета, он отбрасывает пакет.
3. Этот маршрутизатор отправляет хосту A ICMP-сообщение **Type 3, Code 4 ("Destination Unreachable: Fragmentation Needed")**, в котором указывает свой MTU.
4. Получив это сообщение, хост A уменьшает размер своих пакетов до указанного MTU и повторяет отправку.

#### Схема работы

```text
Хост А (отправляет пакет 1500 байт, DF=1)
     |
     v
[Роутер (MTU=1400)]  ---> отбрасывает пакет, отправляет ICMP "Fragmentation Needed (MTU=1400)"
     ^
     |
(Хост А получает ICMP, снижает MTU до 1400)
     |
     v
Хост А (отправляет пакет 1400 байт, DF=1)
     |
     v
[Роутер (MTU=1400)]  ---> успешно пропускает пакет
     |
     v
Хост Б (получает пакет)
```

#### Проблемы PMTUD

| Проблема | Описание | Решение |
| :--- | :--- | :--- |
| **"Черная дыра" PMTUD** | Файрволы блокируют ICMP-сообщения `Type 3/Code 4`. Отправитель не получает уведомление о необходимости снизить MTU и продолжает слать большие пакеты, которые молча отбрасываются. | **Разрешить ICMP Type 3 Code 4** на файрволах. |
| **Асимметричный маршрут** | Прямой и обратный пути имеют разный MTU. | Использовать **TCP MSS Clamping**. |

### Влияние VPN на MTU

VPN-туннели добавляют к каждому пакету свои заголовки, уменьшая эффективный MTU для полезной нагрузки.

| Тип VPN | Дополнительный оверхед (примерно) | Эффективный MTU (из 1500) |
| :--- | :--- | :--- |
| **[IPsec (ESP)](../../Tunnels/ipsec/ipsec.md)** | 56–73 байта | ~1427 |
| **WireGuard** | 60 байт (IP+UDP+WG) | 1440 |
| **OpenVPN (UDP)** | 69 байт | ~1431 |
| **GRE** | 24 байта | 1476 |

Если исходный пакет размером 1500 байт инкапсулируется в VPN-пакет, его итоговый размер превысит 1500 байт, что приведет либо к **фрагментации**, либо к **отбрасыванию пакета**.

### Использование Jumbo Frames

**Jumbo Frames** — это Ethernet-кадры с MTU > 1500 байт (обычно 9000).

- **Польза:** Увеличивают пропускную способность и снижают нагрузку на CPU за счет уменьшения количества пакетов.
- **Требования:** Должны поддерживаться **всеми** устройствами в сетевом сегменте (коммутаторы, маршрутизаторы, сетевые карты).
- **Риски:** Использование в сетях, где поддержка не гарантирована, приводит к проблемам с MTU. Интерфейсы `tun`/`tap` часто по умолчанию имеют MTU 65535, что требует обязательной коррекции при работе с физическими сетями.

## Практические сценарии

### Диагностика проблем с MTU

> **Золотое правило:** Если `ping` работает, а TCP-соединения (веб-сайты, SSH) "зависают", — в 99% случаев проблема связана с MTU.

Это происходит потому, что `ping` отправляет маленькие пакеты, которые проходят через любой MTU, в то время как TCP пытается отправить большие сегменты данных.

#### Основные симптомы

- Маленькие пакеты (ping, DNS) проходят, большие (HTTPS, SCP) — нет.
- Соединение устанавливается, но "зависает" при передаче данных.
- Высокий процент TCP-ретрансмиссий без видимых потерь пакетов.

#### Метод 1: Ручной поиск Path MTU с помощью `ping`

Этот метод позволяет точно определить Path MTU, отправляя пакеты разного размера с флагом `DF`.

```bash
# -M do — установить флаг Don't Fragment (DF)
# -s <size> — размер полезной нагрузки ICMP

# 1. Проверяем стандартный MTU 1500. Размер данных = 1500 - 28 (заголовки IP+ICMP) = 1472
ping -c 3 -M do -s 1472 8.8.8.8
# PING 8.8.8.8 (8.8.8.8) 1472(1500) bytes of data.
# --- 8.8.8.8 ping statistics ---
# 3 packets transmitted, 0 received, +3 errors, 100% packet loss, time 2033ms
# Ошибка! Значит, Path MTU < 1500.

# 2. Уменьшаем размер, например, до 1400 (payload 1372)
ping -c 3 -M do -s 1372 8.8.8.8
# 64 bytes from 8.8.8.8: icmp_seq=1 ttl=118 time=1.23 ms
# Успех! Ищем "потолок" методом деления пополам.

# 3. Находим максимальный работающий размер. Например, 1464 (Path MTU 1492).
ping -c 3 -M do -s 1464 8.8.8.8 # Успех
ping -c 3 -M do -s 1465 8.8.8.8 # Ошибка

# Path MTU = (последний успешный размер payload) + 28
# Path MTU = 1464 + 28 = 1492 байта
```

#### Метод 2: Автоматический поиск с помощью `tracepath`

Утилита `tracepath` (входит в `iputils` в Linux) автоматически определяет Path MTU.

```bash
tracepath 8.8.8.8
# 1?: [LOCALHOST]                      pmtu 1500
# 1:  _gateway (192.168.1.1)           0.362ms
# 2:  ...
# 10: 142.251.229.121 (142.251.229.121) 1.543ms
#     Resume: pmtu 1492 hops 10 back 62
```

Вывод `pmtu 1492` сразу показывает итоговый Path MTU.

### Методы решения проблем с MTU

1. **Настройка MTU на интерфейсе:** Самый простой способ, если у вас есть доступ к устройству, ограничивающему MTU.

    ```bash
    # Для VPN-интерфейса
    ip link set dev wg0 mtu 1420
    ```

2. **TCP MSS Clamping:** Маршрутизатор (часто пограничный или VPN-шлюз) "на лету" перехватывает TCP SYN-пакеты и уменьшает в них значение MSS. Это заставляет хосты отправлять TCP-сегменты меньшего размера, которые гарантированно проходят через узкий участок сети.

3. **Корректная настройка файрвола:** Разрешите ICMP `Type 3, Code 4` для корректной работы PMTUD.

## Рекомендации для сетевой безопасности

Блокировка всего ICMP-трафика — плохая практика, которая вредит диагностике сети. Рекомендуется разрешать как минимум:

- **Type 3 (Destination Unreachable):** Критично для работы PMTUD (Code 4) и общей диагностики.
- **Type 11 (Time Exceeded):** Необходимо для работы `traceroute`.
- **Type 8/0 (Echo Request/Reply):** Для `ping`, с ограничением по частоте (rate limiting) для защиты от флуда.
