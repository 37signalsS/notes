# Транспортный уровень (L4)

## Определения

**Транспортный уровень (Transport Layer, L4)** — первый сквозной (end-to-end) уровень модели **OSI (Open Systems Interconnection)**, обеспечивающий логическую передачу данных непосредственно между **процессами** на конечных хостах. В отличие от нижестоящих уровней, оперирующих хостами и маршрутами (L3) или физическими линками (L2), L4 отвечает за то, чтобы поток байт от приложения на одном сервере попал к нужному приложению на другом, с заданными параметрами надежности.

- **PDU (Protocol Data Unit):** Единица данных. **Сегмент** (в TCP) или **дейтаграмма** (в UDP).
- **Адресация:** [Сетевые порты](../Concepts/network_ports.md) (16-битное число, 0–65535).
- **Сокет (Socket):** Логическая конечная точка соединения, определяемая комбинацией `[IP-адрес]:Порт`. Соединение TCP однозначно идентифицируется 4-tuple (исходный IP, исходный порт, целевой IP, целевой порт). Подробнее: **[Socket API](../Concepts/socket_api.md)**.

## Базовые концепции

### Связь с соседними уровнями

```text
L5 (Сеансовый) — TLS, HTTP/2, QUIC Connection ID
    ↓ Потоки (streams), сессии
L4 (Транспортный) — TCP/UDP, порты, 4-tuple, надёжность
    ↓ Сегменты / Дейтаграммы
L3 (Сетевой) — IP-адресация, маршрутизация
    ↓ Пакеты (IP/IPv6)
```

**Взаимодействие с L5 (Сеансовый):**
- L5 использует одно транспортное соединение (TCP) для нескольких логических сессий (HTTP/2 streams)
- QUIC мультиплексирует потоки поверх UDP без HOL-blocking
- TLS handshake опирается на TCP (или UDP для QUIC)

**Взаимодействие с L3 (Сетевой):**
- L4 получает от L3 IP-пакеты и демультиплексирует их по портам назначения
- L4 инкапсулирует сегменты в IP-пакеты для отправки
- MTU/MSS: L4 должен учитывать размер IP-заголовка (20–60 байт) при формировании сегментов

### Ключевые функции и механизмы

| Функция | Описание |
| :--- | :--- |
| **Мультиплексирование** | Объединение данных от разных процессов (с разными портами источника) в единый поток IP-пакетов L3. |
| **Демультиплексирование** | Распределение входящих IP-пакетов по процессам на основе порта назначения в заголовке L4. |
| **Сегментация** | Разбиение непрерывного потока данных прикладного уровня на части, размер которых не превышает **MSS**. |
| **Управление потоком (Flow Control)** | Согласование скорости передачи со скоростью обработки на стороне получателя (например, механизм Window Size в TCP), чтобы избежать переполнения приемного буфера. |
| **Управление перегрузкой (Congestion Control)** | Реакция отправителя на перегрузку сети (потери или рост задержек) путем изменения алгоритма отправки (Congestion Window — cwnd). |

### Флаги TCP и состояния сессии

Протокол TCP устанавливает и поддерживает состояние логического соединения с помощью управляющих флагов (битов в заголовке):

- **SYN (Synchronize):** Инициализация соединения и синхронизация начальных порядковых номеров (Sequence Numbers).
- **ACK (Acknowledgment):** Подтверждение успешного получения данных или управляющего пакета.
- **FIN (Finish):** Нормальное завершение соединения со стороны отправителя (означает «я больше не буду отправлять данные»).
- **RST (Reset):** Жесткий сброс соединения (например, порт закрыт или приложение упало).
- **PSH (Push):** Указание немедленно передать данные приложению, не дожидаясь заполнения буфера.

**Управление состоянием (TCP State Machine):**
Инженеру (SRE) важно понимать два критических состояния при завершении соединения, которые часто вызывают проблемы:
- `CLOSE_WAIT`: Наше ядро получило FIN от удаленной стороны и ответило ACK, но наше *приложение* еще не вызвало функцию `close()` для сокета. Скопление таких сокетов — признак утечки ресурсов в коде приложения.
- `TIME_WAIT`: Состояние, в которое переходит сокет *инициатора* разрыва (того, кто первым послал FIN) после полного завершения 4-way handshake. Длится 2*MSL (обычно 60 секунд) для гарантии того, что в сети не осталось "заблудившихся" пакетов старой сессии. На высоконагруженных прокси может привести к исчерпанию портов (TCP Port Exhaustion).

### Связь L3 и L4: MTU и MSS

- **MTU (Maximum Transmission Unit):** Максимальный размер IP-пакета (L3). По умолчанию для Ethernet — 1500 байт.
- **MSS (Maximum Segment Size):** Максимальный размер полезной нагрузки TCP-сегмента (L4). Это то, что TCP вставляет в IP-пакет.
- **Формула:** `MSS = MTU - (IP Header) - (TCP Header)`. Обычно это 1460 байт (1500 - 20 - 20).
- Несоответствие MSS/MTU (например, при туннелировании) без механизма PMTUD или TCP MSS Clamping приводит к фрагментации или молчаливому отбрасыванию пакетов (blackhole). Подробнее: **[MTU и PMTUD](./Network_layer/mtu_and_vpn.md)**.

## Ключевые протоколы

| Протокол | Тип | Заголовок | Характеристики | Сфера применения |
| :--- | :--- | :--- | :--- | :--- |
| **[TCP](../Protocols/TCP/overview.md)** | Потоковый | 20–60 байт | Надежный, 3-way handshake, гарантия доставки и порядка (Sequence Numbers). | HTTP/1.1-2, БД (PostgreSQL, MySQL), SSH. |
| **[UDP](../Protocols/udp.md)** | Дейтаграммный | 8 байт | Без установки соединения, без гарантий доставки. Заголовок всего 8 байт. | DNS, NTP, потоковое видео (RTP), игры. |
| **QUIC** | Гибридный | ~20–48 байт | Мультиплексируемый транспорт поверх UDP. Встроенное шифрование TLS 1.3, устраняет проблему HoL (Head-of-Line) блокировки на уровне TCP. 0-RTT setup. | HTTP/3, мобильные приложения. |
| **SCTP** | Потоковый/Сообщений | 12 байт + опции | Поддержка нескольких потоков (multi-streaming) и нескольких IP (multi-homing) в одной сессии. | Сигнальные сети телефонии (SS7, 4G/5G ядра). |
| **MPTCP** | Потоковый | 20+ байт (TCP + MP опции) | Multipath TCP — использование нескольких путей (интерфейсов) одновременно. Совместим с NAT. | Мобильные устройства (Wi-Fi + 4G), CDN. |

### Детальное сравнение TCP и UDP

| Характеристика | TCP | UDP |
| :--- | :--- | :--- |
| **Соединение** | 3-way handshake (SYN → SYN-ACK → ACK) | Без соединения (connectionless) |
| **Порядок** | Гарантируется (Sequence Numbers) | Не гарантируется |
| **Доставка** | Гарантируется (retransmission) | Не гарантируется |
| **Контроль потока** | Window Size (flow control) | Отсутствует |
| **Контроль перегрузки** | CUBIC, BBR, Reno | Отсутствует (на уровне приложения) |
| **Накладные расходы** | Высокие (заголовок + handshake + ACK) | Низкие (8 байт заголовок) |
| **Задержка** | Выше (ожидание ACK, retransmit timeout) | Минимальная |
| **Broadcast/Multicast** | Не поддерживает | Поддерживает |

### Алгоритмы управления перегрузкой (TCP Congestion Control)

Сетевой стек Linux позволяет выбирать алгоритм управления перегрузкой:
- **CUBIC (По умолчанию в большинстве ОС):** Loss-based алгоритм. Увеличивает окно отправки (cwnd) по кубической функции до тех пор, пока не обнаружит потерю пакета. Хорошо работает в сетях с низкой задержкой, но агрессивно сбрасывает скорость при малейших потерях.
- **BBR (Bottleneck Bandwidth and RTT):** Model-based алгоритм от Google. Оценивает реальную пропускную способность канала и RTT (задержку), стараясь поддерживать канал полным, но без переполнения буферов маршрутизаторов (Bufferbloat). Резко повышает пропускную способность на каналах с высоким RTT и случайными потерями (Wi-Fi, 4G, трансконтинентальные линки).

## Современные технологии и высокопроизводительная обработка

В высоконагруженных системах (2026+) стандартный стек ядра Linux (обработка L4 -> копирование в User Space) может стать узким местом.
1.  **Zero-copy (Нулевое копирование):** Системные вызовы `sendfile` или `splice` позволяют ядру передавать данные напрямую из файловой системы в сетевой буфер сокета (L4), минуя пространство пользователя.
2.  **eBPF Socket Redirection (sockmap):** Технология, позволяющая перенаправлять трафик между двумя сокетами внутри одного хоста (например, от Envoy/Nginx-прокси к приложению) на уровне ядра. Пакеты передаются напрямую между буферами сокетов, избегая полного прохода через стек TCP/IP.
3.  **Kernel TLS (kTLS):** Перенос операций симметричного шифрования данных на уровень ядра. Это позволяет комбинировать Zero-copy и защищенные L4-каналы.
4.  **XDP (eXpress Data Path) и DPDK:** Инструменты, позволяющие анализировать, маршрутизировать или сбрасывать L4-пакеты (например, при L4 DDoS атаках, таких как SYN Flood) на этапе драйвера сетевой карты, до того, как ядро создаст структуру `sk_buff`.

## Безопасность транспортного уровня (L4)

| Атака | Описание | Защита |
| :--- | :--- | :--- |
| **SYN Flood** | Заваливание SYN-пакетами для исчерпания очередей TCP (半开 соединения) | SYN cookies, `tcp_syncookies=1`, увеличение backlog, Anycast |
| **UDP Flood** | Поток UDP-пакетов для забивания канала (L4 DDoS) | Rate-limiting, фильтрация на уровне провайдера, nftables |
| **ACK Flood** | Поток ACK-пакетов для перегрузки stateful firewall | Состоянные таблицы (conntrack), rate-limiting |
| **RST Flood** | Поддельные RST-пакеты для разрыва соединений | Валидация последовательных номеров,.tcp_challenge_ack_limit |
| **TCP RST Injection** | Перехват и отправка RST для завершения легитимных соединений | Шифрование (TLS),.sequence randomization |
| **Port Scanning** | Сканирование портов для обнаружения сервисов | Nmap detection, fail2ban, rate-limiting |
| **TCP Reset Attack** | Принудительный разрыв соединения (цензура) | Шифрование, TCP-MD5 (BGP), TCP-AO |

**Пример защиты от SYN Flood (Linux):**
```bash
# Включение SYN cookies (защита без переполнения backlog)
sysctl -w net.ipv4.tcp_syncookies=1

# Увеличение размера backlog (очереди полуоткрытых соединений)
sysctl -w net.core.somaxconn=65535
sysctl -w net.ipv4.tcp_max_syn_backlog=65535

# Уменьшение таймаута SYN-ACK retransmit
sysctl -w net.ipv4.tcp_synack_retries=2

# Ограничение SYN-ACK retransmit (снижение влияния атаки)
sysctl -w net.ipv4.tcp_syn_retries=2

# Просмотр текущих TCP-соединений и их состояний
ss -s
```

## Практические сценарии (L4 Load Balancing)

На уровне L4 работают сетевые балансировщики (Network Load Balancers). В отличие от L7-балансировщиков (Nginx http, Traefik), они не анализируют содержимое запроса (HTTP-заголовки, URL), а оперируют только IP-адресами и TCP/UDP портами.

- **Инструменты:** IPVS (LVS), HAProxy (режим `mode tcp`), Nginx (модуль `stream`), Cilium (через eBPF).
- **Преимущества:** Экстремальная пропускная способность, минимальная задержка, прозрачность для шифрования (TLS-терминация происходит на бэкенде, балансировщик просто перекладывает TCP-сегменты).

### Выбор между TCP и UDP

| Требование | Рекомендация | Обоснование |
| :--- | :--- | :--- |
| Важна 100% целостность | **TCP** | Если потерян 1 байт, данные станут невалидными (JSON, бинарник). |
| Важна минимальная задержка | **UDP** | Ожидание подтверждения ACK и повторные передачи (Retransmissions) в TCP создают неприемлемые паузы для RT-данных. |
| Смена IP (Roaming) | **QUIC** | Механизм Connection ID на уровне протокола позволяет не разрывать логическую сессию при смене сети на уровне L3 (смена IP). |
| Мультипоток + Multi-homing | **SCTP** | Поддержка нескольких потоков и IP в одной сессии. |
| Множество путей (Wi-Fi + 4G) | **MPTCP** | Использование нескольких интерфейсов одновременно. |

### Инкапсуляция: L5 → L4 → L3

```text
L5/L7 (HTTP/1.1):
  [GET /index.html HTTP/1.1\r\nHost: example.com\r\n\r\n]

        ↓ Инкапсуляция в TCP-сегмент (L4)

TCP-сегмент:
  [Src Port 49152][Dst Port 443][Seq=1][Ack=1][Flags=PSH|ACK][Data: HTTP GET]

        ↓ Инкапсуляция в IP-пакет (L3)

IP-пакет:
  [IP Src 10.0.0.1][IP Dst 93.184.216.34][TCP Segment]

        ↓ Инкапсуляция в Ethernet-кадр (L2)

Ethernet-кадр:
  [MAC Src][MAC Dst][EtherType 0x0800][IP Packet][FCS]
```

**Практическое замечание — позиция TLS в стеке:**
TLS-рукопожатие (`TLS Handshake`) выполняется поверх уже установленного TCP-соединения. Поэтому в разных источниках TLS описывают по-разному: от «над L4» до «в диапазоне L4–L7». Правильнее считать TLS частью верхних уровней (L5–L7), которая использует TCP как транспорт: сначала происходит TCP 3-way handshake (L4), затем внутри этого сегмента передаётся TLS ClientHello — то есть TLS «сидит» поверх TCP, но не является частью самого транспортного протокола.

## Практическая диагностика (Linux)

### Инструменты и команды

```bash
# === Просмотр соединений ===

# Просмотр всех TCP/UDP соединений (заменяет netstat)
ss -tnlp          # TCP, listening, с именами процессов
ss -ulnp          # UDP, listening
ss -s             # Сводка по соединениям (TCP established, time-wait и т.д.)

# Просмотр соединений в состоянии ESTABLISHED
ss -tn state established

# Просмотр соединений с таймерами
ss -tno state established '( dport = :443 )'

# Фильтрация по порту назначения
ss -tn dst :443
ss -tn sport = :80

# Просмотр TCP_INFO (детальная статистика)
ss -tni dst :443
# → cubic wscale:7,7 rto:204 rtt:1.5/0.75 ato:40 ...

# === Производительность и тестирование ===

# Тест пропускной способности TCP (клиент)
iperf3 -c <server_ip> -t 30 -P 4    # 4 параллельных потока, 30 секунд
iperf3 -c <server_ip> -u -b 1G      # UDP тест, 1 Гбит/с

# Тест пропускной способности TCP (сервер)
iperf3 -s

# Проверка RTT до хоста
ping -c 10 <host>

# TCP ping (проверка доступности порта)
nping --tcp -p 443 <host>

# === Захват и анализ пакетов ===

# Захват TCP-пакетов на порту 443
tcpdump -i eth0 tcp port 443 -nn -c 100

# Захват с фильтрацией по флагам (SYN, ACK, RST)
tcpdump -i eth0 'tcp[tcpflags] & (tcp-syn) != 0'
tcpdump -i eth0 'tcp[tcpflags] & (tcp-rst) != 0'

# Захват с выводом в файл для Wireshark
tcpdump -i eth0 -w capture.pcap port 443

# Анализ TCP-соединений (RTT, retransmits)
tcpdump -i eth0 -nn 'tcp[tcpflags] & (tcp-syn) != 0' -tttt

# === Мониторинг в реальном времени ===

# Просмотр TCP retransmits в реальном времени
ss -ti dst :443 | grep -i retrans

# Просмотр состояний TCP (для обнаружения TIME_WAIT, CLOSE_WAIT)
ss -tan | awk '{print $1}' | sort | uniq -c | sort -rn

# Просмотр stats по интерфейсу
ip -s link show eth0

# Мониторинг netstat (legacy, но полезно)
netstat -s | grep -i "retransmit\|timeout\|reset"

# === Диагностика проблем ===

# Поиск «заблудившихся» пакетов ( traceroute с TCP)
traceroute -T -p 443 <host>

# Проверка MSS (для обнаружения фрагментации)
ss -tni dst :443 | grep -i mss

# Поиск соединений в CLOSE_WAIT (утечка ресурсов в приложении)
ss -tnp state close-wait

# Поиск соединений в TIME_WAIT (исчерпание портов)
ss -tan state time-wait | wc -l

# Проверка ephemeral port range
cat /proc/sys/net/ipv4/ip_local_port_range
# → 32768   60999

# Просмотр TCP-буферов (глобально и per-socket)
sysctl net.core.rmem_max net.core.wmem_max net.ipv4.tcp_rmem net.ipv4.tcp_wmem

# Просмотр настроек TCP congestion control
sysctl net.ipv4.tcp_congestion_control
# → cubic

# Просмотр BBR (если включён)
sysctl net.ipv4.tcp_available_congestion_control
# → reno cubic bbr
```

## Дополнительная информация

### Сводка по модели OSI

| Характеристика | Описание |
| :--- | :--- |
| **PDU** | Сегмент (TCP) / Дейтаграмма (UDP) |
| **Ключевая задача** | Доставка данных между процессами (end-to-end) |
| **Адресация** | Порты (16 бит, 0–65535) |
| **Оборудование** | NIC (с offload), Linux kernel stack, сервисные.mesh-агенты |
| **Примеры стандартов** | RFC 9293 (TCP), RFC 768 (UDP), RFC 9000 (QUIC), RFC 4960 (SCTP), RFC 8684 (MPTCP) |

### Сводка по протоколам

| Протокол | PDU | Тип | Ключевая особенность |
| :--- | :--- | :--- | :--- |
| **TCP** | Сегмент | Потоковый | Надёжность, порядок, 3-way handshake |
| **UDP** | Дейтаграмма | Дейтаграммный | Скорость, без соединения |
| **QUIC** | Дейтаграмма | Гибридный | 0-RTT, мультиплексирование без HoL |
| **SCTP** | Чанк | Потоковый | Multi-streaming, multi-homing |
| **MPTCP** | Сегмент | Потоковый | Множество путей (Wi-Fi + 4G) |
