## Ключевые директивы для тюнинга

Эти настройки обычно производятся в главном конфигурационном файле `nginx.conf`.

-   **`worker_processes`**: Определяет количество рабочих процессов Nginx.
    -   **Рекомендация:** `auto`. Nginx автоматически определит оптимальное количество, равное числу ядер процессора.
    ```nginx
    worker_processes auto;
    ```

-   **`worker_connections`**: Максимальное количество одновременных соединений, которое может обработать один рабочий процесс.
    -   **Рекомендация:** Устанавливается в зависимости от лимитов системы. Общее количество соединений = `worker_processes` * `worker_connections`.
    ```nginx
    events {
        worker_connections 1024;
    }
    ```

-   **`reuseport`**: Позволяет создавать отдельный слушающий сокет для каждого рабочего процесса. Это устраняет "узкое место" в виде одного сокета и позволяет ядру более эффективно распределять нагрузку.
    ```nginx
    listen 80 reuseport;
    ```

-   **`sendfile`**: Разрешает Nginx использовать системный вызов `sendfile()`, который копирует данные напрямую из одного файлового дескриптора в другой (например, с диска в сокет), минуя копирование в пространство пользователя. Значительно ускоряет отдачу статических файлов.
    ```nginx
    sendfile on;
    ```

-   **`keepalive_timeout`**: Время в секундах, в течение которого сервер не закрывает keep-alive соединение после обработки запроса. Позволяет клиенту выполнять несколько запросов в рамках одного соединения.
    ```nginx
    keepalive_timeout 65;
    ```

-   **`gzip`**: Включает сжатие ответов "на лету". Уменьшает объем передаваемого трафика, но создает дополнительную нагрузку на CPU.
    ```nginx
    gzip on;
    gzip_types text/plain text/css application/json application/javascript;
    ```

-   **`proxy_cache`**: При использовании Nginx в качестве прокси-сервера, кэширование ответов от бэкенда позволяет значительно снизить нагрузку на него.
    ```nginx
    proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=my_cache:10m;
    server {
        ...
        proxy_cache my_cache;
        ...
    }
    ```

## Балансировка нагрузки с `upstream`

Блок `upstream` позволяет определить группу серверов (бэкендов), между которыми Nginx будет распределять запросы. Это основа для построения отказоустойчивых и масштабируемых систем.

```nginx
# Блок http
upstream backend_servers {
    # Алгоритм балансировки
    least_conn;

    # Список серверов
    server 10.0.0.1:8080 weight=3;
    server 10.0.0.2:8080 max_fails=2 fail_timeout=10s;
    server 10.0.0.3:8080 backup;
}

server {
    listen 80;
    server_name myapp.com;

    location / {
        proxy_pass http://backend_servers;
    }
}
```

### Алгоритмы балансировки

1.  **Round-robin (по умолчанию):** Запросы распределяются по серверам поочередно.
2.  **Least Connections (`least_conn`):** Новый запрос отправляется на сервер с наименьшим количеством активных соединений. Эффективен при неравномерной нагрузке.
3.  **IP Hash (`ip_hash`):** Запросы от одного и того же клиента (на основе его IP-адреса) всегда отправляются на один и тот же сервер. Необходимо для приложений, использующих локальные сессии.

### Параметры серверов в `upstream`

-   `weight=N`: Вес сервера. Чем выше значение, тем больше запросов он будет получать. По умолчанию `1`.
-   `max_fails=N`: Количество неудачных попыток соединения, после которого сервер считается недоступным. По умолчанию `1`.
-   `fail_timeout=T`: Время (в секундах), на которое сервер будет исключен из балансировки после `max_fails` неудач. По умолчанию `10s`.
-   `backup`: Помечает сервер как резервный. Он будет использоваться только в том случае, если все остальные серверы в группе недоступны.

-   **`upstream keepalive`**: При проксировании запросов, Nginx может поддерживать активные keep-alive соединения с бэкенд-серверами, что снижает задержки.
    ```nginx
    upstream backend {
        server backend.example.com;
        keepalive 16;
    }
    ```

-   **Использование `epoll`**: В Linux Nginx автоматически использует `epoll` — наиболее эффективный метод обработки сетевых событий. Убедитесь, что в секции `events` не указан другой, менее производительный метод.
    ```nginx
    events {
        use epoll; # Обычно включено по умолчанию
    }

## Кэширование статических файлов

Для ускорения загрузки сайта клиентами можно включить кэширование статических файлов в браузере с помощью заголовков `expires` и `Cache-Control`.

```nginx
location ~* ^.+\.(?:css|cur|js|jpe?g|gif|htc|ico|png|html|xml|otf|ttf|eot|woff|woff2|svg)$ {
    expires 30d;
    add_header Cache-Control public;
}
```

## Настройки таймаутов

Корректная настройка таймаутов помогает предотвратить длительное удержание соединений.

- `client_header_timeout 10;`: Таймаут для чтения заголовков запроса клиента.
- `client_body_timeout 10;`: Таймаут для чтения тела запроса клиента.
- `keepalive_timeout 10;`: Время, в течение которого keep-alive соединение остается открытым на стороне сервера.

## Расширенные настройки Gzip

Более детальная настройка сжатия.

```nginx
server {
    # Включает сжатие
    gzip on;
    # Устанавливает степень сжатия (1-9)
    gzip_comp_level 5;
    # Отключает сжатие для старых браузеров IE
    gzip_disable "msie6";
    # Указывает, какие MIME-типы подвергать сжатию
    gzip_types text/plain text/css application/json application/x-javascript text/xml application/xml application/xml+rss text/javascript;
}
```

## Настройки буферов

Оптимизация буферов для обработки клиентских запросов.

- `client_body_buffer_size 24k;`: Размер буфера для чтения тела запроса. Если тело запроса больше, оно будет записано во временный файл.
- `client_max_body_size 6m;`: Максимально допустимый размер тела запроса клиента.
- `client_header_buffer_size 1k;`: Размер буфера для чтения заголовков. Для большинства запросов 1 КБ достаточно, но запросы с длинными cookies могут требовать большего значения.

## Кэш открытых файлов

Nginx может кэшировать метаданные о файлах, что ускоряет доступ к ним.

```nginx
# Конфигурирует кэш для метаданных файлов
# max=5000: максимальное количество элементов в кэше
# inactive=20s: время, после которого элемент удаляется, если не используется
open_file_cache max=5000 inactive=20s;

# Время, через которое элементы кэша должны быть перепроверены
open_file_cache_valid 30s;

# Минимальное число обращений к файлу за время `inactive`, чтобы он оставался в кэше
open_file_cache_min_uses 2;

# Кэширование ошибок поиска файлов
open_file_cache_errors on;
