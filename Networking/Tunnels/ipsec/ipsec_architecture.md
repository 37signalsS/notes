# IPsec: архитектура и детализация

> **Основной документ:** [ipsec.md](./ipsec.md).

Данный файл содержит углублённый архитектурный материал по внутренним механизмам IPsec, процессам обработки пакетов и структурам данных в ядре.

---

## Определения и компоненты ядра

**SPD (Security Policy Database)** — база данных политик безопасности. Это "мозг" IPsec, определяющий судьбу пакета: должен ли он быть защищён, пропущен без изменений (`bypass`) или отброшен (`discard`).

**SAD (Security Associations Database)** — база данных ассоциаций безопасности. Содержит конкретные параметры шифрования и ключи для активных туннелей.

**SPI (Security Parameter Index)** — 32-битное число в заголовке AH/ESP. Используется приемником для поиска нужной записи в SAD.

**Traffic Selectors (TS)** — селекторы трафика (IP-адреса, протоколы, порты), которые согласуются между узлами для определения того, какой именно трафик попадает в конкретную SA.

## Протоколы управления ключами (IKE)

### IKEv1: Классическая двухфазная модель
1. **Phase 1 (ISAKMP SA):** Создание защищенного канала для управления.
   - **Main Mode:** 6 сообщений, защищает идентификаторы узлов.
   - **Aggressive Mode:** 3 сообщения, быстрее, но идентификаторы передаются в открытом виде.
2. **Phase 2 (IPsec SA / Quick Mode):** Создание одного или нескольких туннелей для данных внутри Фазы 1.

### IKEv2: Современная архитектура
В IKEv2 понятия "фаз" заменены на типы SA:
- **IKE_SA:** Аналог Фазы 1. Устанавливается при первом обмене (IKE_SA_INIT).
- **CHILD_SA:** Аналог Фазы 2. Туннели для данных, создаваемые в рамках IKE_SA. Первый CHILD_SA создается автоматически при аутентификации (IKE_AUTH).

**Ключевое отличие:** IKEv2 намного эффективнее при пересогласовании ключей (rekeying) и поддерживает механизм **MOBIKE**, позволяющий менять IP-адреса без переустановки туннелей.

## Обработка пакетов (Packet Flow)

### Исходящий трафик (Outbound)
1. Пакет попадает на сетевой стек.
2. Ядро ищет совпадение в **SPD**.
3. Если действие `protect`:
   - Ищется активная SA в **SAD**.
   - Если SA нет — запускается демон IKE (strongSwan) для согласования.
   - Если SA есть — пакет инкапсулируется (ESP/AH), шифруется и отправляется.

### Входящий трафик (Inbound)
1. Ядро видит пакет ESP (протокол 50).
2. Извлекает **SPI** из заголовка.
3. Ищет SA в **SAD** по паре `(Destination IP, SPI)`.
4. Если SA найдена — пакет расшифровывается и проверяется на целостность.
5. Выполняется проверка **SPD** (проверка того, что пакет пришел именно через ту туннельную политику, которая для него предназначена).

## Защита и целостность

### Окно защиты от повторов (Anti-Replay)
Механизм защиты от атак воспроизведения. Использует порядковые номера (Sequence Numbers):
- **Sequence Number (32-bit):** Классический счетчик. При переполнении SA должна быть пересоздана.
- **Extended Sequence Number (ESN / 64-bit):** Используется для высокоскоростных каналов (10Gbps+), чтобы избежать частого rekeying из-за переполнения 32-битного счетчика. В заголовке ESP всё равно передаются только младшие 32 бита, старшие учитываются при расчете контрольной суммы (ICV).

### NAT Traversal (NAT-T) architecture
Поскольку ESP (протокол 50) не имеет портов, NAT не может выполнить трансляцию PAT.
**Архитектурное решение:** Инкапсуляция ESP в UDP.
- Порт **500**: Начало согласования.
- Порт **4500**: Используется, если обнаружен NAT. Пакеты ESP оборачиваются в UDP заголовок.

## Сравнение AH и ESP

| Функция | AH (IP 51) | ESP (IP 50) |
|---------|------------|-------------|
| **Шифрование** | Нет | Да |
| **Аутентификация** | Да (включая заголовок IP) | Да (только полезная нагрузка) |
| **NAT Friendly** | Нет (ломается при изменении IP/портов) | Да (с NAT-T) |
| **Актуальность** | Устарел | Основной стандарт |
