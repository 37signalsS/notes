# IPsec: диагностика и устранение неполадок стека KAME/racoon

> **Основной документ:** [IPsec (основной документ)](./ipsec.md).

Данный файл содержит методику диагностики и отладки устаревшей реализации IPsec через стек KAME и демон управления ключами racoon.

> **ВНИМАНИЕ:** Для диагностики современных систем (strongSwan, LibreSwan) используйте **[раздел диагностики в основном документе](./ipsec.md#управление-и-диагностика)**.

---

## Определения и терминология

**ISAKMP SA (Phase 1)** — защищённый канал управления. Если Фаза 1 не установлена, согласование ключей для данных невозможно. В KAME Phase 1 управляется демоном `racoon` и хранится в SAD с флагом `tunnel != 0`.

**IPsec SA (Phase 2 / Quick Mode)** — конкретный туннель для передачи пользовательского трафика (ESP/AH). Определяется комбинацией: SPI (Security Parameters Index) + протокол (ESP/AH) + адрес назначения.

**SAD (Security Association Database)** — база данных в ядре Linux, хранящая ключи и параметры шифрования для активных туннелей. В KAME реализована через модуль `af_key` и доступна через PF_KEY или `setkey`.

**SPD (Security Policy Database)** — база данных политик, определяющая, какой именно трафик подлежит защите (перехвату ядром). Определяет направление (in/out/forward), подсети назначения/источника и требуемый уровень защиты.

**PF_KEY** — протокол взаимодействия между пользовательским пространством (racoon) и ядром Linux для управления SAD/SPD. Реализован через модуль `af_key`. Диагностический интерфейс: `/var/run/pf_key.sock`.

**SPI (Security Parameters Index)** — 32-битный идентификатор, уникально определяющий SA в пределах конкретного пира и протокола. Используется в заголовке ESP для маршрутизации пакета к соответствующей записи в SAD.

**Traffic Selectors (TS)** — диапазоны IP-адресов и портов, определяющие, какой трафик должен быть защищён данным SA. Несовпадение TS — одна из наиболее частых причин сбоя согласования Фазы 2.

**NO_PROPOSAL_CHOSEN (Notify Message 14)** — сообщение-уведомление IKE, указывающее, что предложения шифрования не совпадают. В KAME отображается в логах racoon как `no suitable proposal found`.

**INVALID_KE_PAYLOAD (Notify Message 17)** — уведомление о несовместимости параметров обмена ключами (DH-группа). В KAME встречается редко, так как KAME поддерживает ограниченный набор DH-групп.

**INVALID_SYNTAX (Notify Message 7)** — синтаксическая ошибка в сообщении IKE. В KAME может указывать на некорректную конфигурацию `racoon.conf` или повреждённые данные.

**DEBUG levels (racoon)** — уровни детализации логирования: 0 (только ошибки), 1 (базовая информация), 2 (детали согласования), 3 (отладкаפא킷ов), 4 (максимальная детализация). Уровень 3+ значительно замедляет работу демона.

**syslog facility** — категория логирования в Unix. Racoon по умолчанию использует `daemon`. Для перенаправления логов используется директива `sysloglog` в `racoon.conf`.

## Основные концепции

### Архитектура диагностики KAME

Диагностический стек KAME/racoon состоит из трёх уровней:

```
+---------------------------+
|     racoon (демон)        |  ← Логи: syslog, отладочный вывод
|  Фаза 1 / Фаза 2 / DPD   |     Команды: racoonctl
+---------------------------+
            | PF_KEY socket
+---------------------------+
|     af_key (модуль ядра)  |  ← Диагностика: setkey, ip xfrm
|  SAD / SPD / XFRM state   |     Анализ: tcpdump, Wireshark
+---------------------------+
            |
+---------------------------+
|     Сетевой стек          |  ← Пакеты: tcpdump, netstat
|  IP / UDP 500 / ESP 50    |     Маршрутизация: ip route
+---------------------------+
```

**Ключевой принцип:** При диагностике KAME всегда начинайте с верхнего уровня (логи racoon), затем опускайтесь в ядро (setkey/ip xfrm), и только потом анализируйте сеть (tcpdump). Это позволяет быстро локализовать проблему.

### Уровни логирования racoon

| Уровень | Описание | Когда использовать |
|---------|----------|-------------------|
| 0 | Только критические ошибки | Production (минимальный overhead) |
| 1 | Базовая информация о согласовании | Начальная диагностика |
| 2 | Детали proposal, селекторов трафика | Поиск расхождений в конфигурации |
| 3 | Отдельные IKE-сообщения | Глубокая отладка |
| 4 | Все пакеты вhex-формате | Анализ протокольных ошибок |

**Важно:** Уровни 3–4 генерируют огромный объём логов и могут замедлить работу демона. Используйте их только вällю短时间内 и отключайте сразу после сбора данных.

Настройка уровня логирования:
```bash
# В racoon.conf
log debug2;  # Уровень 2

# Или через командную строку
racoon -F -d -d    # Уровень 2 (-d -d)
racoon -F -d -d -d  # Уровень 3 (-d -d -d)
```

### Диагностические ограничения KAME

1. **Нет встроенного трассировщика:** В отличие от strongSwan (`swanctl --log`), KAME не предоставляет централизованный лог согласования.
2. **Асинхронные логи:** Racoon записывает логи по мере обработки событий, что может привести к перемешиванию сообщений от разных пиров.
3. **Ограниченный контроль SA:** Невозможно посмотреть ключи шифрования (для безопасности), только параметры согласования.
4. **PF_KEY limited:** Утилита `setkey` не показывает SPI для outbound SA — только для inbound.

## Инструментарий диагностики

### Специализированные команды racoon

| Команда | Описание | Пример вывода |
|---------|----------|---------------|
| `racoonctl show-sa isakmp` | Просмотр статуса Фазы 1 | `10.0.255.1[500] 10.0.1.1[500] established` |
| `racoonctl show-sa esp` | Просмотр активных туннелей Фазы 2 | `10.0.255.1[500] esp 0x... <-> 10.0.1.1[500]` |
| `racoonctl vpn-connect <IP>` | Ручной запуск согласования | Нет вывода при успехе |
| `racoonctl delete-sa isakmp` | Принудительное удаление канала управления | Нет вывода при успехе |
| `racoon -F -d` | Запуск демона на переднем плане с отладочным выводом | Детальный лог в stdout |
| `racoon -F -d -d` | Уровень отладки 2 | Детали proposal и селекторов |
| `racoon -F -d -d -d` | Уровень отладки 3 | Все IKE-сообщения |
| `racoonctl show-sa isakmp -a` | Показать все SA включая завершённые | Включает history |

### Низкоуровневая диагностика (ядро Linux)

В современных дистрибутивах для работы с ядром можно использовать как legacy-утилиту `setkey`, так и современные команды `ip xfrm`.

| Задача | Legacy (`setkey`) | Современный (`ip xfrm`) | Примечание |
|--------|-------------------|-------------------------|------------|
| Просмотр SAD (ключи) | `setkey -D` | `ip xfrm state` | setkey не показывает outbound SPI |
| Просмотр SPD (политики) | `setkey -DP` | `ip xfrm policy` | setkey показывает полные селекторы |
| Очистка SAD | `setkey -F` | `ip xfrm state flush` | Очищает ВСЕ SA, включая другие IPSec-клиенты |
| Очистка SPD | `setkey -FP` | `ip xfrm policy flush` | Аналогично |
| Детальный просмотр SAD | `setkey -D -n` | `ip -s xfrm state` | Показывает счётчики пакетов |
| Просмотр по конкретному SPI | `setkey -D \| grep -A1 <SPI>` | `ip xfrm state spi <SPI>` | Поиск конкретной SA |
| Просмотр статистики | `setkey -D -n` | `ip -s xfrm state` | Пакеты, байты, ошибки |
| Проверка CSP (crypto policy) | — | `ip xfrm state count` | Количество активных SA |

### Вспомогательные команды ядра

```bash
# Проверка загруженных модулей ядра
lsmod | grep -E "af_key|esp4|ah4|xfrm4_tunnel"

# Информация о модуле af_key
modinfo af_key

# Проверка заголовков ESP в ядре
cat /proc/net/ipsec_spi          #_SPI table (если доступен)
cat /proc/net/pf_key             # PF_KEY statistics

# Просмотр statistics ядра по IPsec
netstat -s | grep -i ipsec
# или
cat /proc/net/snmp | grep -i Esp
```

## Методика устранения неисправностей

### Алгоритм диагностики KAME

При возникновении проблем с IPsec туннелем следуйте алгоритму:

```
1. Логи racoon → определить стадию сбоя
   ├── "phase1 negotiation failed" → Проверка сетевой связности (шаг 1)
   ├── "failed to get sainfo" → Несовпадение конфигурации Фазы 2 (шаг 2)
   ├── "no policy found" → Проверка SPD (шаг 3)
   └── SA установлен, трафик не проходит → Проверка ядра (шаг 4)

2. Проверка ядра (setkey/ip xfrm) → подтвердить или опровергнуть
3. Анализ трафика (tcpdump) → окончательная локализация
4. Исправление → повторная проверка
```

### 1. Проверка сетевой связности и Firewall

IPsec требует открытия следующих портов и протоколов на внешних интерфейсах:
- **UDP 500:** Для согласования IKE (Internet Key Exchange).
- **UDP 4500:** Для работы NAT-Traversal (NAT-T).
- **IP Protocol 50 (ESP):** Для передачи зашифрованных данных.
- **IP Protocol 51 (AH):** Если используется аутентификация заголовков (редко).

**Диагностический чеклист:**

```bash
# 1. Проверка доступности UDP 500 на удалённом шлюзе
nc -zvu <remote_ip> 500
# → Connection to <remote_ip> 500 port [udp/isakmp] succeeded!

# 2. Проверка маршрута до удалённого шлюза
ip route get <remote_ip>
# → <remote_ip> via <gateway> dev eth0 src <local_ip>

# 3. Проверка Firewall (iptables)
sudo iptables -L -n -v | grep -E "500|4500|50|51"
# → Должны отсутствовать REJECT/DROP правила для этих портов

# 4. Проверка Netfilter.conntrack для ESP
sudo conntrack -L -p esp 2>/dev/null
# → Должны отображаться активные соединения ESP

# 5. Проверка NAT-T (если за NAT)
sudo grep "nat_traversal" /etc/racoon.conf
# → nat_traversal on;
```

### 2. Анализ логов racoon (определение стадии сбоя)

Разбор ключевых сообщений в логах и их диагностика:

| Сообщение в логе | Стадия сбоя | Вероятная причина | Решение |
|------------------|-------------|-------------------|---------|
| `failed to get sainfo` | Фаза 2 | Несовпадение подсетей или алгоритмов | Проверить секции `sainfo` в `racoon.conf` |
| `no policy found` | SPD | Трафик не попадает под правила | Проверить `spdadd` в `ipsec-tools.conf` |
| `invalid secret` | Фаза 1 (аутентификация) | Ошибка PSK | Проверить `/etc/racoon/psk.txt` и права |
| `phase1 negotiation failed` | Фаза 1 | Блокировка UDP 500 или неверный IP | Проверить Firewall и маршрутизацию |
| `notify: no phase2 found` | Фаза 2 | Партнер запросил неописанный туннель | Синхронизировать селекторы трафика |
| `could not get psk` | Фаза 1 | Файл ключей недоступен | Проверить владельца (`root`) и права |
| `ISAKMP-SA established` | Фаза 1 OK | Успешное согласование | Переходить к проверке Фазы 2 |
| `DELETE notification` | Сброс SA | Таймаут или ручное удаление | Проверить DPD и keepalive |
| `Dying peer detected` | DPD failure | Потеря связи с пиром | Проверить сетевую связность |

### 3. Проверка состояний в ядре

Если логи показывают успешное установление SA (`ISAKMP-SA established`), но трафик не проходит:

1.  **Проверьте наличие SPI:** `ip xfrm state` должен показывать две записи для каждого туннеля (входящий и исходящий).
    ```bash
    ip xfrm state | grep -E "proto ESP|spi"
    # → proto esp spi 0x... reqid ... mode tunnel
    # → proto esp spi 0x... reqid ... mode tunnel
    ```

2.  **Проверьте счётчики пакетов:**
    ```bash
    ip -s xfrm state
    # →ackets 1234 bytes 567890
    # Если счетчики растут на одной стороне, но не на другой —
    # пакеты блокируются Firewall на стороне приёмника или теряются в пути.
    ```

3.  **Проверьте SPD (политики):**
    ```bash
    ip xfrm policy
    # → src 192.168.1.0/24 dst 192.168.255.0/24
    # → dir fwd priority ...
    # → tmpl src 10.0.1.1 dst 10.0.255.1
    ```

4.  **Проверьте асимметрию SA:**
    ```bash
    # На ЛОКАЛЬНОМ шлюзе
    ip xfrm state | grep "proto esp"
    # На УДАЛЁННОМ шлюзе
    ip xfrm state | grep "proto esp"
    # SPI должны совпадать: local_in == remote_out, local_out == remote_in
    ```

### 4. Анализ трафика (tcpdump)

Для отладки процесса согласования и проверки прохождения данных используйте следующие фильтры:

```bash
# Просмотр процесса согласования (Фаза 1 и 2)
tcpdump -n -i any port 500 or port 4500

# Просмотр зашифрованного трафика (ESP)
tcpdump -n -i any proto 50

# Детальный захват для конкретного пира
tcpdump -n -i any host <remote_gateway_ip> -w ipsec_debug.pcap

# Анализ дампа в Wireshark
wireshark ipsec_debug.pcap
```

**Интерпретация вывода tcpdump:**

| Наблюдение | Вероятная проблема |
|------------|-------------------|
| Initiator → Responder: SA, KE, Nonce (без ответа) | Блокировка UDP 500 в обратном направлении |
| Initiator → Responder → Notify: NO_PROPOSAL_CHOSEN | Несовпадение алгоритмов шифрования |
| Initiator → Responder → Notify: INVALID_KE_PAYLOAD | Несовместимые DH-группы |
| SA согласованы, но ESP-пакетов нет | Нет маршрута или SPD-политики |
| ESP-пакеты идут в одну сторону | Асимметричные SA или Firewall |
| ESP-пакеты идут в обе стороны, но нет ответа | Шлюз не маршрутизирует трафик через SA |

## Типовые проблемы и решения

### Проблемы Фазы 1 (IKE SA)

| Проблема | Symptom в логах | Вероятная причина | Диагностика | Решение |
|----------|-----------------|-------------------|-------------|---------|
| **NO_PROPOSAL_CHOSEN** | `phase1 negotiation failed` | Несовпадение алгоритмов шифрования/hashing/DH-групп | `racoon -F -d -d` — сравнить proposal initiator/responder | Синхронизировать секции `remote` и `proposal` |
| **INVALID_KE_PAYLOAD** | `notify: invalid_ke_payload` | DH-группы не совместимы (modp1024 vs modp2048) | Проверить `dh_group` в `racoon.conf` | Использовать одну DH-группу на обеих сторонах |
| **INVALID_SYNTAX** | `notify: invalid_syntax` | Синтаксическая ошибка в IKE-сообщении | Проверить версию racoon, целостность конфига | Обновить racoon, проверить `racoon.conf` |
| **AUTHENTICATION_FAILED** | `invalid secret` | Неверный PSK или файл ключей повреждён | Сравнить PSK на обеих сторонах, `cat /etc/racoon/psk.txt` | Убедиться в идентичности PSK, `chmod 600` |
| **Долгая согласование Фазы 1** | `phase1 negotiation failed` через 30 сек | Медленный DH или таймаут | `tcpdump -n port 500` — считать retry | Увеличить `lifetime` или проверить задержку сети |
| **DPD dead peer** | `Dying peer detected` | Потеря связи, firewall блокирует DPD | `ping <remote_ip>`, проверить UDP 500 | Проверить маршрутизацию, добавить `dpd_delay` |
| **Агрессивный режим** | `aggressive mode` в логах | Используется небезопасный aggressive mode | `grep -i aggressive /etc/racoon.conf` | Перейти на `exchange_mode main` |

### Проблемы Фазы 2 (Quick Mode)

| Проблема | Symptom в логах | Вероятная причина | Диагностика | Решение |
|----------|-----------------|-------------------|-------------|---------|
| **failed to get sainfo** | `failed to get sainfo` | Несовпадение подсетей, портов или алгоритмов в Фазе 2 | Сравнить `sainfo` с `spdadd` | Синхронизировать селекторы трафика |
| **no policy found** | `no policy found` | Трафик не попадает под SPD-политики | `setkey -DP`, проверить src/dst | Добавить/исправить `spdadd` в `ipsec-tools.conf` |
| **no phase2 found** | `notify: no phase2 found` | Партнер запросил туннель для неописанной подсети | Сравнить селекторы на обеих сторонах | Добавить `sainfo` для отсутствующей подсети |
| **Ah, не ESP** | `auth only` | Используется AH вместо ESP | `grep "auth" /etc/racoon.conf` | Заменить `authentication_algorithm` на `esp` |
| **Несовпадение PFS** | `no suitable sainfo` | DH-группы PFS не совпадают | `grep "pfs_group" /etc/racoon.conf` | Синхронизировать `pfs_group` |
| **Lifetime mismatch** | SA создана, но быстро сбрасывается | Разные `lifetime` на сторонах | Проверить `lifetime` в `sainfo` | Установить одинаковый lifetime |

### Проблемы трафика (SA установлены)

| Проблема | Symptom | Вероятная причина | Диагностика | Решение |
|----------|---------|-------------------|-------------|---------|
| **Асимметричные SA** | `ip xfrm state` — разные SPI | Некорректная синхронизация SA | Сравнить SPI на обеих сторонах | Пересоздать SA: `setkey -F && setkey -f ipsec-tools.conf` |
| **Фрагментация** | Пинг работает, TCP/HTTP нет | MTU слишком велик для ESP | `ping -M do -s 1400 <ip>`, `tracepath <ip>` | MSS Clamping: `iptables -t mangle -A FORWARD -p tcp --tcp-flags SYN,RST SYN -j TCPMSS --clamp-mss-to-pmtu` |
| **NAT-Traversal** | SA согласованы, но трафик не проходит | NAT-T не активен | `ip xfrm state` — проверить encap | Включить `nat_traversal on;`, проверить UDP 4500 |
| **Нет маршрута** | `ip xfrm state` — SA есть, пакеты не уходят | Маршрут не ведёт через IPsec | `ip route get <dst>`, `ip xfrm policy` | Добавить маршрут или исправить SPD |
| **Firewall блокирует** | ESP-пакеты видны на входе, нет ответа | iptables/nftables блокирует ESP | `tcpdump -n proto 50`, `iptables -L -n -v` | Разрешить ESP (protocol 50) |
| **Повторная инкапсуляция** | Огромные задержки, loss | Трафик проходит через SA дважды | `tcpdump -n proto 50` — двойные ESP-пакеты | Проверить SPD: исключить уже зашифрованный трафик |
| **Счётчики не растут** | `ip -s xfrm state` — packets 0 | Трафик не попадает в SA | `ip xfrm policy` — проверить fwd-политику | Проверить `spdadd` и маршрутизацию |

### Проблемы конфигурации

| Проблема | Symptom | Вероятная причина | Решение |
|----------|---------|-------------------|---------|
| **`could not get psk`** | Racoon не запускается | Файл `psk.txt` не существует или нет прав | `chmod 600 /etc/racoon/psk.txt`, `chown root:root` |
| **`parse failure`** | Racoon падает при старте | Синтаксическая ошибка в `racoon.conf` | Проверить скобки, точки с запятой, опции |
| **`policy not found`** | SPD пуст | `setkey` не запущен или конфиг пуст | `setkey -f /etc/ipsec-tools.conf` |
| **Duplicated SA** | Множественные SA для одного пира | Racoon не удаляет старые SA при rekeying | `racoonctl delete-sa isakmp`, перезапуск |
| **Replay attack detected** | `replay check` в логах | Счётчик пакетов переполнен | Увеличить `replay_window` в `racoon.conf` |

## Граничные случаи и ограничения

### Ограничения стека KAME

1. **Только IKEv1:** KAME не поддерживает IKEv2. Это означает отсутствие EAP-аутентификации, MOBIKE, Childless IKE_SA и других современных функций.
2. **Ограниченная криптография:** По умолчанию — 3DES, SHA1, MODP 1024. AES поддерживается, но не AEAD (AES-GCM). Для поддержки AES-GCM необходим патч или альтернативная реализация.
3. **PF_KEY limitations:** Утилита `setkey` не показывает outbound SPI — только inbound. Для полной картины используйте `ip xfrm state`.
4. **Нет динамической маршрутизации:** KAME не интегрируется с BGP/OSPF. Статические маршруты обязательны.
5. **Асимметричные SA:** При реagонировании (rekeying) могут возникнуть временные асимметричные SA, которые приводят к потере пакетов.

### Проблемы совместимости

| Устройство/ПО | Проблема | Решение |
|---------------|----------|---------|
| **Cisco IOS** | Modern Cisco запрещает 3DES/SHA1 | Настроить AES-256/SHA-256 или использовать legacy-режим |
| **Juniper SRX** | Несовпадение селекторов трафика | Синхронизировать `proxy-id` с `sainfo` |
| **strongSwan** | strongSwan не поддерживает KAME | Использовать совместимый IPsec-стек (LibreSwan) |
| **Windows Server** | Windows IKEv1 требует точной настройки | Убедиться в совпадении всех параметров |
| **MikroTik** | RouterOS использует собственную реализацию | Синхронизировать proposal и sainfo |

### Диагностические ловушки

1. **Ложные срабатывания DPD:** Если DPD проверяет связь слишком часто, это может привести к ложному сбросу SA. Рекомендуется `dpd_delay 30; dpd_retry 3;`.
2. **Фрагментация IKE:** IKE-сообщения могут фрагментироваться, если их размер превышает MTU. Используйте `Fragmentation` extension (IKEv1 fragmented).
3. **Конфликт с other IPsec:** Если на системе одновременно работают racoon и strongSwan,他们会 конфликтовать за PF_KEY socket. Убедитесь, что запущен только один демон.
4. **Rekeying storm:** При коротком `lifetime` (например, 60 сек) и большом количестве туннелей racoon может уйти в бесконечный rekeying, потребляя 100% CPU.
