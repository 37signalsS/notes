# IPSec (IP Security)

## Definitions

**IPSec (IP Security)** — набор протоколов и технологий для организации защищённого соединения на сетевом уровне (L3) путём аутентификации и шифрования IP-пакетов.

**Ключевое отличие от других туннельных технологий:** IPSec не создаёт явных туннельных интерфейсов (как GRE, PPP, L2TP). Вместо этого используется концепция **Security Associations (SA)** и **Security Policy (SP)**.

---

## Basic Concepts

### Архитектура и протоколы

| Протокол | Назначение | Порт/Протокол |
|----------|------------|---------------|
| **ISAKMP** | Фреймворк для управления SA (термины SA, SP, SAD, SPD) | — |
| **IKE (IKEv1/IKEv2)** | Аутентификация и обмен ключами | UDP 500, 4500 (NAT-T) |
| **ESP** | Аутентификация + шифрование | IP-протокол 50 |
| **AH** | Только аутентификация | IP-протокол 51 |

### Двухфазная модель установления соединения

```
Фаза 1: ISAKMP SA (вспомогательный туннель)
  ↓
Фаза 2: IPsec SA (туннель пользовательских данных)
```

**Фаза 1:** Стороны договариваются о параметрах шифрования и аутентифицируют друг друга.

| Режим | Описание | Применение |
|-------|----------|------------|
| **Main** | Поочередный обмен параметрами | Постоянные каналы (site-to-site) |
| **Aggressive** | Все параметры в одном сообщении | Временные сессии (remote access) |

**Фаза 2:** По защищённому ISAKMP-туннелю стороны договариваются о параметрах шифрования пользовательского трафика.

**Особенности:**

- **SA-туннели однонаправленные** — для двусторонней связи требуется два туннеля (src→dst и dst→src)
- **ISAKMP SA** — двунаправленный, действует постоянно
- **IPsec SA** — однонаправленный, имеет время жизни

### Security Associations (SA) и Security Policy (SP)

**SA (Security Association)** — логический туннель от одного сетевого устройства к другому. Не является сетевым интерфейсом в классическом понимании.

**Базы данных:**

- **SAD (Security Associations Database)** — хранит параметры активных SA
- **SPD (Security Policy Database)** — политики безопасности (правила пропуска трафика)

**SP (Security Policy)** — правила, определяющие какой трафик и как обрабатывается IPSec. Аналог ACL.

**Параметры SP:** адрес источника, адрес назначения, направление (in, out, fwd), параметры туннеля (ESP/AH, режим, требования).

> **Важно:** Классическая маршрутизация здесь не работает. Трафик направляется в туннель на основе SP, а не таблицы маршрутизации.

### Режимы инкапсуляции

| Режим | Описание | Применение |
|-------|----------|------------|
| **Транспортный** | Шифруется только полезная нагрузка | GRE/L2TP/PPP поверх IPsec; объединение офисов |
| **Туннельный** | Шифруется весь исходный IP-пакет + внешний IP-заголовок | Site-to-site VPN, подключение к инфраструктуре партнёров |

### NAT-Traversal (NAT-T)

**Проблема:** ESP не содержит заголовков TCP/UDP (они зашифрованы), что делает невозможным работу NAT с трансляцией портов (PAT).

**Решение:** NAT-T добавляет UDP-заголовок к ESP-пакетам.

**Механизм:**

1. В фазе 1 стороны согласовывают поддержку NAT-T
2. При успешном согласовании ESP-пакеты инкапсулируются в UDP
3. Порт UDP: **4500** (стандарт для NAT-T)

### MTU и фрагментация

| Тип | Оверхед | Эффективный MTU |
|-----|---------|-----------------|
| **IPsec ESP (туннельный)** | ~56-73 байта | ~1427-1444 байта |
| **Минимальный** | ~40 байт | <1460 байт |

**Последствия:**

- При стандартном MTU 1500 байт реальный MTU IPSec-туннеля ≈ 1420-1440 байт
- Для PPPoE (MTU 1380) реальный MTU < 1340 байт
- Требуется настройка **Path MTU Discovery (PMTUD)** или ручное уменьшение MTU/MSS

## Practical Scenarios

### Сценарий: Подключение к API партнёра через IPSec (Network-Network)

**Контекст:** Организация подключается к закрытому API партнёра. Инфраструктура партнёра стандартизирована, требуется IPSec Network-Network.

```
IPSec: 10.0.1.1 <-> 10.0.255.1
Сервис: 192.168.1.1 <-> 192.168.255.1
```

**Особенности Network-Network:**

- IPSec поднимается между одними IP-адресами (внешние интерфейсы)
- Сервис работает между другими IP-адресами (внутренние сети)
- Фильтрация внутри инфраструктуры партнёра по внутренним IP

### Реализации IPSec на Linux

| Решение | Описание | Актуальность |
|---------|----------|--------------|
| **strongSwan** | Современная реализация, поддержка IKEv2, активная разработка | **Рекомендуется** |
| **LibreSwan** | Форк FreeSWAN, фокус на безопасности, поддержка Red Hat | Актуально |
| **KAME/racoon** | Из BSD, наиболее предсказуемый, устаревший | Устаревший |

### Установка strongSwan (Debian/Ubuntu)

```bash
apt-get install strongswan strongswan-pki libcharon-extra-plugins
```

### Базовая конфигурация strongSwan (`/etc/ipsec.conf`)

```bash
config setup
    charondebug="ike 1, knl 1, cfg 0"

conn %default
    ikelifetime=60m
    keylife=20m
    rekeymargin=3m
    keyingtries=1
    keyexchange=ikev2

conn partner-net
    left=10.0.1.1
    leftsubnet=192.168.1.0/24
    leftid=10.0.1.1
    right=10.0.255.1
    rightsubnet=192.168.255.0/24
    auto=start
    authby=psk
```

### Файл секретов (`/etc/ipsec.secrets`)

```bash
10.0.1.1 10.0.255.1 : PSK "SUPERPASSWORD"
```

### Управление strongSwan

```bash
# Запуск и проверка статуса
ipsec start
ipsec status

# Перезагрузка конфигурации
ipsec reload

# Просмотр деталей SA
ipsec statusall
```

### Альтернатива через iproute2 (управление SA/SP)

```bash
# Управление Security Associations
ip xfrm state add src 10.0.1.1 dst 10.0.255.1 proto esp spi 0x1000 \
  reqid 1 mode tunnel auth sha256-96 "0x1234..." enc aes-128-cbc "0x5678..."

# Управление Security Policies
ip xfrm policy add src 192.168.1.0/24 dst 192.168.255.0/24 dir out \
  tmpl src 10.0.1.1 dst 10.0.255.1 proto esp reqid 1 mode tunnel

# Просмотр
ip xfrm state
ip xfrm policy
```

## Additional Information

### Сравнение с другими VPN-технологиями

| Технология | Уровень | Шифрование | Туннельный интерфейс |
|------------|---------|------------|---------------------|
| **IPSec** | L3 | Встроенное (ESP) | Нет (SA + SP) |
| **WireGuard** | L3 | Встроенное | Да (wgN) |
| **OpenVPN** | L2/L3 | Встроенное | Да (tunN/tapN) |
| **GRE** | L2/L3 | Опционально (через IPSec) | Да (greN) |

### Диагностика и troubleshooting

**Важно:** Туннель поднимается только при наличии трафика!

```bash
# Тестовый пинг для поднятия туннеля
ping -I 192.168.1.1 192.168.255.1

# Захват трафика для анализа
tcpdump -i eth1 host 10.0.255.1

# Проверка логов
journalctl -u strongswan -f
```

### Типовые проблемы

| Проблема | Возможная причина | Решение |
|----------|-------------------|---------|
| Туннель не поднимается | Нет трафика | Отправить тестовый пакет (ping) |
| `No route to host` | Проблема с ARP для /32 маски | Добавить статическую ARP-запись |
| Фаза 1 не проходит | Несоответствие PSK или алгоритмов | Проверить секреты и `exchange_mode` |
| Фаза 2 не проходит | Несоответствие SP | Проверить правила `spdadd` или `ip xfrm policy` |
| Трафик не идёт | Неправильная маршрутизация | Проверить маршруты и secondary IP |
