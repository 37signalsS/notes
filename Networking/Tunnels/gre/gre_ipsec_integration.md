# Интеграция GRE с IPsec: защищённое туннелирование

## Определения и назначение

**GRE over IPsec (Generic Routing Encapsulation over IP Security)** — технология создания защищённых виртуальных каналов, объединяющая гибкость GRE (поддержка любых протоколов, мультикаста и динамической маршрутизации) с безопасностью IPsec (шифрование, аутентификация и контроль целостности).

Данная комбинация является классическим решением для построения **Site-to-Site VPN** в корпоративных сетях, где требуется передача трафика протоколов маршрутизации (OSPF, BGP) через защищённый туннель.

**Ключевые характеристики:**

| Параметр | Значение |
|----------|----------|
| **Протокол GRE** | IP 47 |
| **Протокол IPsec** | **ESP (Encapsulating Security Payload)** — IP 50 |
| **Порты IKE (IKEv1/v2)** | UDP 500, UDP 4500 (при использовании NAT-T) |
| **Эффективный MTU** | ~1400–1420 байт (при базовом 1500) |
| **Рекомендуемый режим** | GRE over IPsec (туннелирование GRE внутри IPsec) |

## Базовые концепции

### Варианты комбинирования протоколов

#### 1. GRE over IPsec (рекомендуемый)
Исходный пакет инкапсулируется в GRE, который затем защищается протоколом IPsec ESP.
*   **Схема:** `[Внешний IP][ESP][GRE][Внутренний IP][Данные]`
*   **Плюсы:** Полная защита GRE-трафика, включая заголовок GRE. Поддержка мультикаста.
*   **Минусы:** Двойная инкапсуляция увеличивает накладные расходы (overhead).

#### 2. IPsec over GRE (не рекомендуется)
Пакет сначала защищается IPsec, а затем инкапсулируется в GRE-туннель.
*   **Схема:** `[Внешний IP][GRE][IPsec ESP][Внутренний IP][Данные]`
*   **Минусы:** Заголовок GRE передаётся в открытом виде. Более высокий overhead. Используется только в специфических legacy-сценариях.

### Режимы работы IPsec для GRE

| Режим | Описание | Применение с GRE |
|-------|----------|------------------|
| **Туннельный** | Шифруется весь пакет, добавляется новый внешний IP-заголовок. | Универсальный вариант для Site-to-Site. |
| **Транспортный** | Шифруется только полезная нагрузка исходного IP-пакета. | Используется для минимизации overhead, если GRE и IPsec терминируются на одних и тех же узлах. |

### Проблемы MTU и фрагментации

Суммарный overhead при использовании GRE over IPsec может достигать **80–100 байт**, что значительно снижает эффективный MTU.

**Рекомендации по настройке:**
1.  Установить MTU на GRE-интерфейсе: `1400` байт.
2.  Настроить **MSS Clamping**: ограничить TCP MSS до `1360` байт для предотвращения фрагментации.
3.  Разрешить прохождение ICMP-трафика для работы Path MTU Discovery.

### NAT Traversal (NAT-T)

Поскольку протокол ESP (IP 50) не имеет портов, он не может проходить через классический NAT (PAT). Технология NAT-T автоматически инкапсулирует ESP-пакеты в **UDP 4500**, если обнаруживает NAT между конечными точками туннеля.

## Современные альтернативы

В современных системах Linux часто предпочтительнее использовать нативные интерфейсы, которые упрощают настройку и маршрутизацию:

1.  **VTI (Virtual Tunnel Interface):** Виртуальный интерфейс, который ведет себя как GRE, но работает напрямую с политиками IPsec. Позволяет использовать стандартную маршрутизацию (`ip route`).
2.  **XFRM Interfaces (`type xfrm`):** Самый современный подход в ядре Linux (начиная с 4.19+). Позволяет привязывать зашифрованный трафик к конкретному интерфейсу с использованием `if_id`, обеспечивая чистое разделение трафика и поддержку сетевых пространств имен (NetNS).

## Практические сценарии

### Настройка через strongSwan (современный метод swanctl)

Файл конфигурации `/etc/swanctl/conf.d/gre.conf`:

```hcl
connections {
    gw-gw {
        remote_addrs = 203.0.113.2
        local_addrs = 198.51.100.1
        proposals = aes256-sha256-modp2048
        
        children {
            gre-tunnel {
                # Протокол 47 означает GRE
                remote_ts = 203.0.113.2/32[gre]
                local_ts = 198.51.100.1/32[gre]
                esp_proposals = aes256-sha256
                mode = transport
                start_action = trap
            }
        }
    }
}
```

### Настройка через LibreSwan (классический метод)

Файл `/etc/ipsec.d/gre.conf`:

```bash
conn gre-vpn
    left=198.51.100.1
    right=203.0.113.2
    # Ограничение политики только протоколом GRE
    leftprotoport=47
    rightprotoport=47
    type=transport
    authby=secret
    auto=start
```

## Дополнительная информация

### Диагностика и отладка

**Инструментарий Linux:**
*   `ip xfrm state` — просмотр активных зашифрованных сессий (SA).
*   `ip xfrm policy` — проверка правил трансформации трафика.
*   `tcpdump -i any esp` — перехват зашифрованных пакетов.

**Типовые ошибки:**
*   **Ошибка в Phase 2:** Несоответствие селекторов трафика (Traffic Selectors). Для GRE это должны быть конкретные IP-адреса и протокол 47.
*   **Проблемы MTU:** Симптомы — мелкие пакеты (ICMP) проходят, а крупные (HTTP/SSH) зависают. Решается через MSS Clamping.

### Преимущества и недостатки

**Плюсы:**
*   Поддержка протоколов динамической маршрутизации (OSPF, EIGRP, BGP).
*   Возможность передачи L2-трафика (через GRETAP).
*   Прозрачная маршрутизация внутри защищённого канала.

**Минусы:**
*   Высокий overhead (снижение полезной нагрузки).
*   Сложность отладки (необходимость следить за состоянием двух протоколов).
