# Keepalived

## Определения

Keepalived — это сервис для Linux, который обеспечивает высокую доступность (High Availability) и отказоустойчивость для серверов и приложений. Чаще всего он используется для создания кластера с виртуальным [IP-адресом](../Protocols/ip.md) (VIP) по протоколу **VRRP (Virtual Router Redundancy Protocol)**.

- **Высокая доступность (High Availability, HA):** Подход, при котором система спроектирована так, чтобы минимизировать время простоя. Сервис почти всегда работает, но в случае сбоя возможен короткий перерыв (несколько секунд или минут), необходимый для переключения на резервный компонент. VRRP является классическим примером технологии для обеспечения высокой доступности.
- **Отказоустойчивость (Fault Tolerance, FT):** Более строгий подход, при котором система продолжает работать без видимых для пользователя перебоев даже при отказе одного из компонентов. Пользователь ничего не замечает. Примером может служить агрегация каналов (LACP), где трафик мгновенно перераспределяется при обрыве одного из соединений.
- **Плавающий IP (Floating IP) или Виртуальный IP (Virtual IP, VIP):** Это IP-адрес, который не привязан жестко к одному физическому серверу. В рамках кластера высокой доступности он может "перемещаться" с одного узла на другой. Узел, владеющий VIP в данный момент, называется `MASTER`. Если он выходит из строя, VIP переназначается одному из резервных (`BACKUP`) узлов.

## Основные концепции

Основная задача Keepalived — предоставить единую точку входа (виртуальный IP-адрес) для группы серверов. Если основной сервер (`MASTER`) выходит из строя, Keepalived автоматически передает VIP-адрес резервному серверу (`BACKUP`), который становится новым `MASTER`. Этот процесс для клиента происходит прозрачно.

### Принцип работы (Active-Passive)

1.  **Настройка:** На двух или более серверах устанавливается и настраивается Keepalived. Один сервер назначается как `MASTER` (с более высоким приоритетом), остальные как `BACKUP`. Важно, чтобы сам плавающий IP-адрес **не был** статически прописан в настройках сетевых интерфейсов. Каждый узел должен иметь свой собственный уникальный статический IP.
2.  **Обмен состоянием (Heartbeat):** `MASTER` сервер периодически отправляет VRRP-сообщения (advertisements) в сеть, сообщая о своем "здоровье" и владея виртуальным IP-адресом. По умолчанию это делается через **мультикаст**.
3.  **Ожидание:** `BACKUP` серверы слушают эти сообщения. Пока они приходят, `BACKUP` серверы остаются в пассивном состоянии. Переключение происходит, если от мастера не было сообщений в течение интервала, равного `3 * advert_int`.
4.  **Отказ (Failover):** Если `MASTER` сервер перестает отправлять сообщения (из-за сбоя, остановки сервиса или провала скрипта проверки), `BACKUP` серверы понимают, что мастер недоступен.
5.  **Переключение и Gratuitous ARP:** `BACKUP` сервер с наивысшим приоритетом берет на себя роль `MASTER` и "захватывает" виртуальный IP-адрес. Чтобы все устройства в сети немедленно узнали, что у VIP сменился MAC-адрес (и теперь трафик нужно слать на новый узел), новый `MASTER` отправляет в сеть **Gratuitous ARP** (самопроизвольный ARP) запрос. Этот кадр заставляет сетевые коммутаторы и хосты обновить свои ARP-таблицы, обеспечивая быструю и прозрачную смену маршрута.
6.  **Восстановление (Failback):** Когда бывший `MASTER` возвращается в строй, по умолчанию он снова становится `MASTER` из-за своего более высокого приоритета (это называется `preemption`). Чтобы избежать лишних переключений и кратковременных простоев, на узлах часто используют директиву `nopreempt`. В этом случае узел, захвативший роль `MASTER`, будет удерживать ее до собственного сбоя, даже если первоначальный `MASTER` вернулся в сеть.

### Защита от Split-Brain и безопасная коммуникация

**Split-Brain** ("расщепление мозга") — это критическая ошибка, при которой из-за нарушения связи между узлами два или более из них одновременно решают, что они являются главными. В случае Keepalived это приводит к тому, что несколько узлов пытаются владеть одним VIP-адресом, вызывая конфликт и нарушение работы сервиса.

#### Рекомендации по минимизации рисков:

-   **Выделенный канал связи:** Обмен VRRP-пакетами (heartbeats) крайне чувствителен к задержкам и потерям в общей сети. Кроме того, при использовании мультикаста в общей сети существует риск атак "человек посередине" (MITM). **Настоятельно рекомендуется** организовывать обмен heartbeat-сообщениями через прямое физическое соединение между узлами кластера (dedicated link).
-   **Режим Unicast:** Вместо мультикаста можно настроить Keepalived в режиме `unicast`, явно указав IP-адреса соседних узлов (`unicast_peer`). Это повышает безопасность, так как пакеты не рассылаются по всему сегменту сети.
-   **Агрегация (LACP):** Для максимальной надежности выделенный канал связи можно организовать на базе агрегированных интерфейсов (например, LACP/bonding). Если один из физических линков или портов выйдет из строя, heartbeat-трафик продолжит ходить по оставшемуся, предотвращая ложный Split-Brain.
-   **Кворум:** В кластере из двух узлов полностью защититься от Split-Brain невозможно. Если связь между ними теряется, оба могут стать `MASTER`. Для надежной защиты от Split-Brain в кластерах из 3+ узлов используется механизм **кворума**, который гарантирует, что только большинство может принимать решения. Keepalived "из коробки" не имеет кворума, но его можно реализовать с помощью внешних скриптов.

Подробнее об этой проблеме и механизмах защиты читайте в [общем обзоре репликации и Split-Brain](../../Databases/Concepts/replication.md#проблема-split-brain-и-решение-через-кворум).

## Практические сценарии

### Проверка состояния сервиса

Keepalived может отслеживать не только доступность сервера, но и состояние конкретного приложения (например, HAProxy или Nginx). Это критически важно, так как сервер может быть доступен, но приложение на нем — нет.

Это реализуется с помощью проверочных скриптов (`vrrp_script`):

- Скрипт периодически проверяет, запущен ли нужный процесс или выполняет более сложную проверку (например, делает HTTP-запрос).
- Если скрипт завершается с кодом ошибки (не 0), Keepalived считает, что сервис неисправен.
- В этом случае `MASTER` узел может добровольно "отпустить" VIP (понизив свой приоритет), позволяя `BACKUP` узлу взять на себя нагрузку.

#### Пример скрипта для проверки HAProxy

Примитивный скрипт, использующий `pidof` для проверки, запущен ли процесс HAProxy.

```bash
#!/bin/sh
# /etc/keepalived/check_haproxy.sh

if pidof haproxy > /dev/null; then
  exit 0 # Сервис работает
else
  exit 1 # Сервис не работает
fi
```

> Для более надежной проверки рекомендуется использовать методы, проверяющие реальную работоспособность сервиса, например, `curl` к его статусной странице.

### Детальный разбор конфигурации

```keepalived
# Глобальный блок, router_id должен быть уникальным для каждого узла
global_defs {
   router_id my_router_1
}

# (Опционально) Скрипт для проверки состояния сервиса
vrrp_script chk_app {
   script "/path/to/check_script.sh" # Путь к скрипту
   interval 2                        # Проверять каждые 2 секунды
   weight -10                        # При провале вычесть 10 из приоритета
   fall 2                            # Считать сервис упавшим после 2 неудачных проверок
   rise 3                            # Считать сервис поднявшимся после 3 удачных
}

vrrp_instance VI_1 {
    # --- Основные параметры ---
    state MASTER                     # Роль по умолчанию: MASTER или BACKUP
    interface eth0                   # Интерфейс, на котором будет "висеть" VIP
    virtual_router_id 51             # Уникальный ID для vrrp-группы (0-255), одинаковый на всех узлах
    priority 101                     # Приоритет (1-254), у MASTER должен быть выше, чем у BACKUP

    # --- Настройки переключения ---
    advert_int 1                     # Интервал отправки VRRP-анонсов (в секундах)
    nopreempt                        # (Рекомендуется для BACKUP) Запрещает "возврат" VIP на бывший MASTER,
                                     # когда тот восстановится. Это предотвращает лишние переключения.

    # --- Аутентификация (НЕБЕЗОПАСНО!) ---
    # Блок аутентификации устарел и считается небезопасным.
    # В VRRPv2 пароль передается в открытом виде. В VRRPv3 поддержка аутентификации
    # была удалена из стандарта. Используйте unicast-режим и выделенную сеть.
    authentication {
        auth_type PASS
        auth_pass "mypass"           # Максимум 8 символов
    }

    # --- Сетевые настройки ---
    virtual_ipaddress {
        192.168.1.100/24 dev eth0    # Виртуальный IP-адрес
        # 2001:db8::1/64 dev eth0     # Можно добавлять несколько адресов, включая IPv6
    }
    
    # --- Режим Unicast (рекомендуется) ---
    # Явное указание IP-адресов участников кластера вместо мультикаста.
    # unicast_src_ip 10.0.0.1           # IP-адрес этого узла в сети для heartbeat
    # unicast_peer {
    #     10.0.0.2                     # IP-адрес соседа
    # }

    # --- Отслеживание скриптов ---
    track_script {
        chk_app                      # Имя скрипта, который нужно отслеживать
    }
}
```

### Настройка Firewall

Для корректной работы VRRP необходимо разрешить одноименный протокол в системном файрволе. VRRP работает поверх IP (как TCP или UDP) и имеет номер протокола **112**.

Пример для `firewalld`:
```bash
sudo firewall-cmd --add-protocol=vrrp --permanent
sudo firewall-cmd --reload
```
Пример для `iptables`:
```bash
sudo iptables -A INPUT -p vrrp -j ACCEPT
```

## Дополнительная информация

### Версии VRRP

- **VRRPv2**: Классическая версия, наиболее распространенная. Не поддерживает IPv6.
- **VRRPv3**: Более новая версия, которая добавляет поддержку как для IPv4, так и для IPv6, а также более точные таймеры для анонсов (в миллисекундах). Выбор версии обычно определяется автоматически, но может быть указан в конфигурации.

### Надежность скриптов проверки

В некоторых случаях `pidof` может вернуть несколько PID. Для надежной работы рекомендуется использовать скрипт-обертку, который гарантирует возврат только кода выхода (0 или 1), игнорируя стандартный вывод `pidof`. Например: `pidof haproxy > /dev/null && exit 0 || exit 1`.
