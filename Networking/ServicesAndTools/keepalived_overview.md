# Keepalived

Keepalived — это сервис для Linux, который обеспечивает высокую доступность (High Availability) и отказоустойчивость для серверов и приложений. Чаще всего он используется для создания кластера с виртуальным [IP-адресом](../../Protocols/ip.md) (VRRP - Virtual Router Redundancy Protocol).

## Обзор

Основная задача Keepalived — предоставить единую точку входа (виртуальный IP-адрес) для группы серверов. Если основной сервер (MASTER) выходит из строя, Keepalived автоматически передает виртуальный IP-адрес резервному серверу (BACKUP), который становится новым MASTER. Этот процесс для клиента происходит прозрачно.

## Принцип работы (Active-Passive)

1.  **Настройка:** На двух или более серверах устанавливается и настраивается Keepalived. Один сервер назначается как `MASTER`, остальные как `BACKUP`.
2.  **Обмен состоянием:** `MASTER` сервер периодически отправляет мультикаст-сообщения (VRRP advertisements) в сеть, сообщая о своем "здоровье" и владея виртуальным IP-адресом.
3.  **Ожидание:** `BACKUP` серверы слушают эти сообщения. Пока они приходят, `BACKUP` серверы остаются в пассивном состоянии, не владея виртуальным IP.
4.  **Отказ:** Если `MASTER` сервер перестает отправлять сообщения (из-за сбоя сервера, сети, остановки сервиса Keepalived или отказа отслеживаемого приложения), `BACKUP` серверы понимают, что мастер недоступен.
5.  **Переключение:** `BACKUP` сервер с наивысшим приоритетом берет на себя роль `MASTER` и "захватывает" виртуальный IP-адрес. Теперь весь трафик, идущий на этот IP, будет обрабатываться новым мастером. Этот процесс происходит прозрачно для клиентов.
6.  **Восстановление:** Когда бывший `MASTER` возвращается в строй, он может либо снова стать `MASTER` (если настроен на это), либо остаться `BACKUP`, в зависимости от конфигурации приоритетов и директив `nopreempt`.

## Защита от Split-Brain

Проблема "Split-Brain" возникает, когда из-за сетевых проблем или других сбоев оба узла (MASTER и BACKUP) считают себя активными и пытаются владеть одним и тем же виртуальным [IP-адресом](../../Protocols/ip.md). Это приводит к конфликтам и нарушению работы сервиса.

-   **Два узла:** В кластере из двух узлов полностью защититься от Split-Brain крайне сложно. Если связь между ними теряется, оба могут стать MASTER.
-   **Три и более узлов:** Для надежной защиты от Split-Brain рекомендуется использовать кластер из трех и более узлов с механизмом кворума (например, с использованием Corosync/Pacemaker или других решений, которые могут интегрироваться с Keepalived). Это позволяет большинству узлов принимать решение о том, кто является истинным MASTER, предотвращая ситуацию, когда несколько узлов одновременно объявляют себя активными.

## Проверка состояния сервиса

Keepalived может не только проверять доступность самого сервера, но и отслеживать состояние конкретного приложения (например, HAProxy или Nginx). Это критически важно для обеспечения реальной высокой доступности, так как сам сервер может быть доступен, но приложение на нем не функционирует.

Это реализуется с помощью проверочных скриптов (`vrrp_script`).
-   Скрипт периодически проверяет, запущен ли нужный процесс или выполняет более сложную проверку работоспособности приложения.
-   Если скрипт завершается с кодом ошибки (не 0), Keepalived считает, что сервис неисправен.
-   В этом случае `MASTER` узел может "отпустить" виртуальный IP, даже если сам сервер продолжает работать, позволяя `BACKUP` узлу взять на себя нагрузку.

### Пример скрипта для проверки HAProxy

Пример скрипта, использующего команду `pidof` для проверки запущенного процесса HAProxy. `pidof haproxy` возвращает PID процесса, если он запущен, и ничего не возвращает (с кодом ошибки), если процесс не найден. Keepalived интерпретирует код возврата 0 как успешную проверку, а любой другой код — как ошибку.

```bash
#!/bin/sh
# /etc/keepalived/check_haproxy.sh

if pidof haproxy > /dev/null; then
  exit 0 # Сервис работает
else
  exit 1 # Сервис не работает
fi
```
Эта проверка является достаточно примитивной и лишь подтверждает, что процесс HAProxy запущен. Для более надежной проверки можно добавить логику, которая будет проверять доступность HAProxy по сети (например, `curl` к его статусной странице) или работоспособность бэкендов, которые он обслуживает.

**Примечание из практики:** В некоторых случаях `pidof` может вернуть несколько PID, если запущено несколько экземпляров процесса. В такой ситуации Keepalived может некорректно интерпретировать вывод. Для надежной работы рекомендуется использовать скрипт-обертку, который гарантирует возврат только кода выхода (0 или 1), игнорируя стандартный вывод `pidof`. Например, `pidof haproxy > /dev/null && exit 0 || exit 1`.

## Пример конфигурации

```keepalived
global_defs {
   router_id LVS_DEVEL
}

vrrp_script chk_haproxy {
   script "/etc/keepalived/check_haproxy.sh"
   interval 2
   weight 2
}

vrrp_instance VI_1 {
    state MASTER          # или BACKUP на резервном сервере
    interface eth0
    virtual_router_id 51
    priority 101          # Приоритет (у MASTER выше)
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111
    }
    virtual_ipaddress {
        192.168.1.100/24  # Виртуальный [IP-адрес](../../Protocols/ip.md)
    }
    track_script {
        chk_haproxy
    }
}
```
