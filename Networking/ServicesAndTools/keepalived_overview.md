# Keepalived: Высокая доступность с VRRP

## Definitions

**Keepalived** — демон для Linux, обеспечивающий высокую доступность (HA) и отказоустойчивость через управление виртуальным IP-адресом (VIP) на базе протокола **VRRP (Virtual Router Redundancy Protocol)**.

**Статус (2026):** Keepalived остается стандартом де-факто для HA в bare-metal и VM-окружениях. Актуальная стабильная версия — 2.3.x с поддержкой VRRPv3, unicast-режима и расширенных health checks.

**VRRP (Virtual Router Redundancy Protocol)** — протокол, позволяющий группе маршрутизаторов (или серверов) совместно владеть виртуальным IP-адресом. Один узел становится `MASTER`, остальные — `BACKUP`. При отказе `MASTER` один из `BACKUP` автоматически принимает на себя роль `MASTER`.

**Виртуальный IP (Virtual IP, VIP / Floating IP)** — IP-адрес, не привязанный жёстко к одному физическому серверу. В рамках HA-кластера он «перемещается» между узлами. Узел, владеющий VIP в данный момент, называется `MASTER`.

**Высокая доступность (HA)** vs **Отказоустойчивость (FT):**

- **HA** — минимизация простоя; при сбое допустим краткий перерыв (секунды/минуты) на переключение. VRRP — классический пример HA.
- **FT** — система продолжает работать без видимых перебоев. Пример — агрегация каналов (LACP), где трафик мгновенно перераспределяется при обрыве одного из соединений.

Подробнее об общих принципах HA — в [обзоре высокой доступности](../../Concepts/High_Availability/ha_overview.md).

## Basic Concepts

### Принцип работы (Active-Passive)

1. **Настройка:** На двух или более серверах устанавливается Keepalived. Один сервер назначается `MASTER` (с более высоким приоритетом), остальные — `BACKUP`. Плавающий IP **не должен** быть статически прописан в настройках сетевых интерфейсов — каждый узел имеет свой уникальный статический IP.
2. **Heartbeat (VRRP advertisements):** `MASTER` периодически отправляет VRRP-сообщения, сообщая о своём «здоровье». По умолчанию используется **мультикаст**.
3. **Ожидание:** `BACKUP` серверы слушают эти сообщения. Пока они приходят, `BACKUP` остаются пассивными. Переключение инициируется, если от мастера не было сообщений в течение `3 * advert_int`.
4. **Failover:** Если `MASTER` перестаёт отправлять сообщения (сбой, остановка сервиса, провал скрипта проверки), `BACKUP` сервер с наивысшим приоритетом становится новым `MASTER`.
5. **Gratuitous ARP:** Новый `MASTER` отправляет Gratuitous ARP-запрос, заставляя коммутаторы и хосты обновить ARP-таблицы. Это обеспечивает быструю и прозрасную смену маршрута к VIP.
6. **Failback:** Когда бывший `MASTER` возвращается, по умолчанию он снова становится `MASTER` благодаря более высокому приоритету (**preemption**). Для предотвращения лишних переключений используют `nopreempt` — узел, захвативший роль `MASTER`, удерживает её до собственного сбоя.

### Защита от Split-Brain

**Split-Brain** — критическая ошибка, при которой два или более узла одновременно считают себя `MASTER` из-за нарушения связи между ними. Несколько узлов владеют одним VIP, вызывая конфликт IP и MAC-адресов.

#### Рекомендации по минимизации рисков

- **Выделенный канал связи:** VRRP-пакеты чувствительны к задержкам и потерям. Обмен heartbeat-сообщениями рекомендуется организовать через прямое физическое соединение между узлами кластера (dedicated link).
- **Режим Unicast (обязательно для production):** Вместо мультикаста явно указываются IP-адреса соседних узлов (`unicast_peer`). Это повышает безопасность и упрощает работу в облачных средах, где мультикаст часто заблокирован.
- **Агрегация (LACP):** Выделенный канал на базе LACP/bonding предотвращает ложный Split-Brain при выходе одного из физических линков.
- **Кворум:** В кластере из двух узлов полностью защититься от Split-Brain невозможно. Для кластеров из 3+ узлов механизм кворума гарантирует, что только большинство принимает решения. Keepalived «из коробки» не имеет кворума — его реализуют через внешние скрипты.
- **Отключение аутентификации VRRP:** Блок `authentication` в VRRPv2 передаёт пароль в открытом виде. В VRRPv3 аутентификация удалена из стандарта. **Рекомендация:** полагаться на unicast + выделенную сеть + firewall rules.

Подробнее о проблеме Split-Brain и механизмах защиты через кворум — в [репликации БД](../../Databases/Concepts/replication.md#проблема-split-brain-и-решение-через-кворум).

### Версии VRRP

| Версия | Особенности |
| :--- | :--- |
| **VRRPv2** | Классическая версия, наиболее распространённая. Не поддерживает IPv6. |
| **VRRPv3** | Поддержка IPv4 и IPv6, более точные таймеры анонсов (в миллисекундах). |

### Настройка Firewall

VRRP работает поверх IP (протокол **112**, как TCP — 6, UDP — 17). Необходимо разрешить его в файрволе.

**firewalld:**

```bash
sudo firewall-cmd --add-protocol=vrrp --permanent
sudo firewall-cmd --reload
```

**iptables:**

```bash
# Разрешить VRRP только от соседа
sudo iptables -A INPUT -p vrrp -s 10.0.0.2 -j ACCEPT
# Заблокировать все остальные VRRP-пакеты
sudo iptables -A INPUT -p vrrp -j DROP
```

## Practical Scenarios

### Проверка состояния сервиса (vrrp_script)

Keepalived отслеживает не только доступность сервера, но и состояние приложения (HAProxy, Nginx). Реализуется через проверочные скрипты (`vrrp_script`):

- Скрипт периодически проверяет работоспособность сервиса (процесс, HTTP-запрос).
- При коде ошибки (не 0) Keepalived снижает приоритет `MASTER`, позволяя `BACKUP` узлу принять VIP.

**Примитивная проверка процесса (не рекомендуется для production):**

```bash
#!/bin/bash
# /etc/keepalived/check_haproxy.sh
if pidof haproxy > /dev/null && exit 0 || exit 1; then
  exit 0
fi
exit 1
```

**Рекомендуемый скрипт для production** с HTTP-проверкой:

```bash
#!/bin/bash
# /etc/keepalived/check_haproxy.sh

# Проверка через HTTP status page
if curl -sf http://localhost:8404/status > /dev/null 2>&1; then
    exit 0
fi

# Альтернативная проверка
if curl -sf http://localhost:80/health > /dev/null 2>&1; then
    exit 0
fi

# Все проверки провалились
exit 1
```

### Полный пример конфигурации

```keepalived
# Глобальный блок — router_id уникален для каждого узла
global_defs {
   router_id my_router_1
}

# Скрипт проверки состояния
vrrp_script chk_app {
   script "/etc/keepalived/check_haproxy.sh"
   interval 2            # Проверять каждые 2 секунды
   weight -10            # При провале вычесть 10 из приоритета
   fall 2                # Считать сервис упавшим после 2 неудач
   rise 3                # Считать сервис поднявшимся после 3 удач
}

vrrp_instance VI_1 {
    state MASTER                     # MASTER или BACKUP
    interface eth0                   # Интерфейс для VIP
    virtual_router_id 51             # ID vrrp-группы (0-255), одинаковый на всех узлах
    priority 101                     # Приоритет (1-254), у MASTER выше
    advert_int 1                     # Интервал VRRP-анонсов (сек)

    nopreempt                        # Запрет возврата VIP на бывший MASTER

    virtual_ipaddress {
        192.168.1.100/24 dev eth0
    }

    # Unicast — обязательно для production
    unicast_src_ip 10.0.0.1
    unicast_peer {
        10.0.0.2
    }

    track_script {
        chk_app
    }

    track_interface {
        eth0 weight -20
    }
}
```

### HA для API-сервера Kubernetes (bare-metal)

Критический сценарий — единый стабильный VIP для нескольких `kube-apiserver` на разных master-узлах. Keepalived управляет VIP, гарантируя его доступность на одном из работающих узлов. VIP затем используется L4-балансировщиком (HAProxy) для распределения трафика.

Подробное руководство — в [настройке HA API-сервера с Keepalived и HAProxy](../../Kubernetes/Installation/kubeadm/ha_concepts.md).

### HA для MySQL (плавающий IP)

В multi-source репликации MySQL Keepalived обеспечивает единую точку входа для пишущих клиентов. VIP активен только на одном узле; при отказе текущего мастера другой узел захватывает VIP. Клиенты кратковременно теряют соединение, но после переподключения по тому же IP попадают на новый активный узел.

Подробности — в [multi-source репликации MySQL](../../Databases/MySQL/multi-source-replication.md#3-отказоустойчивость-с-помощью-плавающего-ip-vip).

## Additional Information

### Механизмы failover и их связь с Keepalived

Keepalived реализует **IP failover** на уровне сети (L3/L4). Для более комплексного управления ресурсами (VIP + сервисы + зависимости + fencing) используют **Pacemaker/Corosync**. Keepalived проще и легче, но ограничен управлением VIP и health checks.

Подробнее о механизмах failover, кворуме и fencing — в [механизмах failover](../../Concepts/High_Availability/ha_failover_mechanisms.md).

### Тайминги heartbeat: баланс между чувствительностью и стабильностью

- **Короткие интервалы** (`advert_int < 1s`) → ложные failover при сетевых задержках.
- **Длинные интервалы** (`advert_int > 3s`) → увеличение времени восстановления (MTTR).
- **Рекомендация для production:** `advert_int 1`, `fall 2-3`, `rise 2-3`.

### Надежность скриптов проверки

`pidof` может вернуть несколько PID. Рекомендуется использовать скрипт-обёртку, гарантирующий возврат только кода выхода: `pidof haproxy > /dev/null && exit 0 || exit 1`. Для production предпочтительны HTTP-проверки (`curl` к status page или health endpoint).
