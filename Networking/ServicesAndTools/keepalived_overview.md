# Keepalived — обзор и настройка HA

## Определения

**Keepalived** — демон для Linux, обеспечивающий высокую доступность (HA — High Availability) и отказоустойчивость через управление виртуальным IP-адресом (VIP) на базе протокола **VRRP (Virtual Router Redundancy Protocol)**.

**Статус (2026):** Keepalived остается стандартом де-факто для обеспечения высокой доступности в bare-metal и VM-окружениях. Актуальная стабильная версия — 2.3.x с поддержкой VRRPv3, unicast-режима и расширенных проверок состояния (health checks).

**VRRP (Virtual Router Redundancy Protocol)** — сетевой протокол, позволяющий группе серверов совместно владеть виртуальным IP-адресом. Один узел становится `MASTER`, остальные — `BACKUP`. При отказе `MASTER` один из `BACKUP` автоматически принимает на себя его роль.

**Виртуальный IP (Virtual IP, VIP / Floating IP)** — IP-адрес, не привязанный жёстко к одному физическому серверу. В рамках кластера высокой доступности он перемещается между узлами. Узел, владеющий VIP в данный момент, называется `MASTER`.

**Высокая доступность (HA)** vs **Отказоустойчивость (FT):**

- **HA (High Availability)** — минимизация времени простоя; при сбое допустим краткий перерыв (секунды) на переключение. Общие принципы описаны в **[обзоре High Availability](../../Concepts/High_Availability/ha_overview.md)**.
- **FT (Fault Tolerance)** — система продолжает работать без видимых перебоев. Пример — агрегация каналов (LACP), где трафик мгновенно перераспределяется при обрыве одного из соединений.

## Основные концепции

### Принцип работы (Active-Passive)

1. **Настройка:** На двух или более серверах устанавливается Keepalived. Один сервер назначается `MASTER` (с более высоким приоритетом), остальные — `BACKUP`. Плавающий IP не должен быть статически прописан в настройках сетевых интерфейсов ОС.
2. **Heartbeat (VRRP advertisements):** `MASTER` периодически отправляет VRRP-сообщения, сообщая о своей доступности. По умолчанию используется мультикаст (multicast).
3. **Ожидание:** `BACKUP` серверы слушают эти сообщения. Переключение инициируется, если от мастера не было сообщений в течение `3 * advert_int`.
4. **Failover:** Если `MASTER` перестаёт отправлять сообщения, `BACKUP` сервер с наивысшим приоритетом становится новым `MASTER`.
5. **Gratuitous ARP:** Новый `MASTER` отправляет Gratuitous ARP-запрос, заставляя коммутаторы обновить ARP-таблицы для мгновенного перенаправления трафика на новый MAC-адрес.
6. **Failback:** Когда оригинальный `MASTER` восстанавливается, он по умолчанию забирает роль `MASTER` обратно (preemption). Для предотвращения лишних переключений используют опцию `nopreempt`.

### Защита от Split-Brain

**Split-Brain** — критическая ошибка, при которой два или более узла одновременно считают себя `MASTER` из-за нарушения связи между ними, что приводит к конфликту IP-адресов.

#### Рекомендации по минимизации рисков

- **Выделенный канал связи:** Обмен heartbeat-сообщениями рекомендуется организовать через прямое физическое соединение или выделенный VLAN.
- **Режим Unicast (рекомендуется для production):** Вместо мультикаста явно указываются IP-адреса соседних узлов (`unicast_peer`). Это повышает безопасность и надежность.
- **Кворум:** В кластере из двух узлов невозможно полностью защититься от Split-Brain без внешней логики. Для кластеров из 3+ узлов механизмы кворума гарантируют корректность принятия решений.
- **Безопасность VRRP:** В VRRPv3 аутентификация удалена из стандарта как небезопасная. Рекомендуется полагаться на Unicast и правила сетевого экрана (firewall).

Подробнее о проблеме Split-Brain — в [репликации БД](../../Databases/Concepts/replication.md#проблема-split-brain-и-решение-через-кворум).

### Версии VRRP

| Версия | Особенности |
| :--- | :--- |
| **VRRPv2** | Наиболее распространённая версия. Не поддерживает IPv6. |
| **VRRPv3** | Поддержка IPv4 и IPv6, точность таймеров в миллисекундах. |

### Настройка сетевого экрана (Firewall)

VRRP работает поверх IP (протокол **112**). Необходимо разрешить его прохождение.

**firewalld:**

```bash
sudo firewall-cmd --add-protocol=vrrp --permanent
sudo firewall-cmd --reload
```

**iptables:**

```bash
# Разрешить VRRP только от доверенного соседа
sudo iptables -A INPUT -p vrrp -s 10.0.0.2 -j ACCEPT
sudo iptables -A INPUT -p vrrp -j DROP
```

## Практические сценарии

### Проверка состояния сервиса (vrrp_script)

Keepalived может отслеживать состояние конкретных приложений (HAProxy, Nginx) через скрипты:

```bash
#!/bin/bash
# /etc/keepalived/check_haproxy.sh
if curl -sf http://localhost:8404/status > /dev/null 2>&1; then
    exit 0
fi
exit 1
```

### Пример конфигурации (keepalived.conf)

```keepalived
global_defs {
   router_id LVS_DEVEL
}

vrrp_script chk_haproxy {
   script "/etc/keepalived/check_haproxy.sh"
   interval 2
   weight -20
}

vrrp_instance VI_1 {
    state MASTER
    interface eth0
    virtual_router_id 51
    priority 101
    advert_int 1

    unicast_src_ip 10.0.0.1
    unicast_peer {
        10.0.0.2
    }

    virtual_ipaddress {
        192.168.1.100/24
    }

    track_script {
        chk_haproxy
    }
}
```

### Сценарии использования

- **HA для API-сервера Kubernetes:** Обеспечение стабильного VIP для `kube-apiserver` в связке с HAProxy. Подробнее: [настройка HA API-сервера](../../Kubernetes/Installation/kubeadm/ha_concepts.md).
- **HA для MySQL:** Использование плавающего IP для переключения между мастером и репликой. Подробнее: [отказоустойчивость MySQL](../../Databases/MySQL/multi-source-replication.md#3-отказоустойчивость-с-помощью-плавающего-ip-vip).

### Диагностика

```bash
# Проверка владения VIP
ip addr show eth0

# Мониторинг логов в реальном времени
journalctl -u keepalived -f

# Перехват VRRP-пакетов
tcpdump -i eth0 -n vrrp
```

## Дополнительная информация

### Сравнение с Pacemaker

Keepalived реализует **IP failover** на сетевом уровне. Для управления сложными зависимостями между сервисами, дисками и кворумом чаще используется связка **Pacemaker + Corosync**. Keepalived предпочтителен для простых сценариев управления виртуальным IP.

Подробнее о механизмах переключения — в [механизмах failover](../../Concepts/High_Availability/ha_failover_mechanisms.md).

### Оптимизация таймеров

- **advert_int:** Интервал анонсов. Значение `1` является оптимальным для большинства сетей.
- **preemption:** По умолчанию включено. Если MASTER восстанавливается, он забирает VIP обратно. Если это нежелательно (например, для БД), используйте `nopreempt`.
