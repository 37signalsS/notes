# Keepalived

## Определения

Keepalived — это сервис для Linux, который обеспечивает высокую доступность (High Availability) и отказоустойчивость для серверов и приложений. Чаще всего он используется для создания кластера с виртуальным [IP-адресом](../../Protocols/ip.md) (VIP) по протоколу **VRRP (Virtual Router Redundancy Protocol)**.

## Основные концепции

### Обзор

Основная задача Keepalived — предоставить единую точку входа (виртуальный IP-адрес) для группы серверов. Если основной сервер (`MASTER`) выходит из строя, Keepalived автоматически передает VIP-адрес резервному серверу (`BACKUP`), который становится новым `MASTER`. Этот процесс для клиента происходит прозрачно.

### Принцип работы (Active-Passive)

1. **Настройка:** На двух или более серверах устанавливается и настраивается Keepalived. Один сервер назначается как `MASTER` (с более высоким приоритетом), остальные как `BACKUP`.
2. **Обмен состоянием:** `MASTER` сервер периодически отправляет мультикаст-сообщения (VRRP advertisements) в сеть, сообщая о своем "здоровье" и владея виртуальным IP-адресом.
3. **Ожидание:** `BACKUP` серверы слушают эти сообщения. Пока они приходят, `BACKUP` серверы остаются в пассивном состоянии.
4. **Отказ (Failover):** Если `MASTER` сервер перестает отправлять сообщения (из-за сбоя, остановки сервиса или провала скрипта проверки), `BACKUP` серверы понимают, что мастер недоступен.
5. **Переключение:** `BACKUP` сервер с наивысшим приоритетом берет на себя роль `MASTER` и "захватывает" виртуальный IP-адрес. Теперь весь трафик, идущий на этот VIP, будет обрабатываться им.
6. **Восстановление (Failback):** Когда бывший `MASTER` возвращается в строй, по умолчанию он снова становится `MASTER` из-за своего более высокого приоритета. Чтобы избежать лишних переключений, на `BACKUP`-узлах часто используют директиву `nopreempt`. В этом случае узел, захвативший роль `MASTER`, будет удерживать ее до собственного сбоя, даже если первоначальный `MASTER` вернулся в сеть.

### Защита от Split-Brain

**Split-Brain** ("расщепление мозга") — это критическая ошибка в кластерных системах, при которой из-за нарушения связи (например, сетевого сбоя между узлами) два или более узла одновременно решают, что они являются главными. В случае Keepalived это приводит к тому, что несколько узлов пытаются владеть одним и тем же VIP-адресом, вызывая конфликт и нарушение работы сервиса.

- **Два узла:** В кластере из двух узлов полностью защититься от Split-Brain крайне сложно. Если связь между ними теряется, оба могут стать `MASTER`.
- **Три и более узлов:** Для надежной защиты от Split-Brain рекомендуется использовать нечетное количество узлов и механизм кворума, который гарантирует, что только большинство может принимать решения. Keepalived "из коробки" не имеет кворума, но его можно реализовать с помощью внешних скриптов или интегрировать с более сложными решениями (например, Corosync/Pacemaker).

Подробнее об этой проблеме и механизмах защиты читайте в [общем обзоре репликации и Split-Brain](../../Databases/Concepts/replication.md#проблема-split-brain-и-решение-через-кворум).

## Практические сценарии

### Проверка состояния сервиса

Keepalived может отслеживать не только доступность сервера, но и состояние конкретного приложения (например, HAProxy или Nginx). Это критически важно, так как сервер может быть доступен, но приложение на нем — нет.

Это реализуется с помощью проверочных скриптов (`vrrp_script`):

- Скрипт периодически проверяет, запущен ли нужный процесс или выполняет более сложную проверку (например, делает HTTP-запрос).
- Если скрипт завершается с кодом ошибки (не 0), Keepalived считает, что сервис неисправен.
- В этом случае `MASTER` узел может добровольно "отпустить" VIP (понизив свой приоритет), позволяя `BACKUP` узлу взять на себя нагрузку.

#### Пример скрипта для проверки HAProxy

Примитивный скрипт, использующий `pidof` для проверки, запущен ли процесс HAProxy.

```bash
#!/bin/sh
# /etc/keepalived/check_haproxy.sh

if pidof haproxy > /dev/null; then
  exit 0 # Сервис работает
else
  exit 1 # Сервис не работает
fi
```

> Для более надежной проверки рекомендуется использовать методы, проверяющие реальную работоспособность сервиса, например, `curl` к его статусной странице.

### Пример конфигурации

```keepalived
global_defs {
   router_id LVS_DEVEL
}

vrrp_script chk_haproxy {
   script "/etc/keepalived/check_haproxy.sh"
   interval 2 # Проверять каждые 2 секунды
   weight 2   # При провале скрипта вычитать 2 из приоритета
}

vrrp_instance VI_1 {
    state MASTER          # или BACKUP на резервном сервере
    interface eth0
    virtual_router_id 51  # Должен быть одинаковым на всех узлах кластера
    priority 101          # Приоритет (у MASTER выше, чем у BACKUP)
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass 1111    # Пароль должен быть одинаковым
    }
    virtual_ipaddress {
        192.168.1.100/24  # Виртуальный IP-адрес
    }
    track_script {
        chk_haproxy
    }
}
```

## Дополнительная информация

### Версии VRRP

- **VRRPv2**: Классическая версия, наиболее распространенная. Не поддерживает IPv6.
- **VRRPv3**: Более новая версия, которая добавляет поддержку как для IPv4, так и для IPv6, а также более точные таймеры для анонсов (в миллисекундах). Выбор версии обычно определяется автоматически, но может быть указан в конфигурации.

### Надежность скриптов проверки

В некоторых случаях `pidof` может вернуть несколько PID. Для надежной работы рекомендуется использовать скрипт-обертку, который гарантирует возврат только кода выхода (0 или 1), игнорируя стандартный вывод `pidof`. Например: `pidof haproxy > /dev/null && exit 0 || exit 1`.
