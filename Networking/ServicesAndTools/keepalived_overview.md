# Keepalived: Обзор

**Keepalived** — это легковесный и надежный сервис для Linux, который обеспечивает высокую доступность (High Availability) и балансировку нагрузки. Его основная задача — гарантировать, что сервис (например, веб-сервер или база данных) останется доступным, даже если один из серверов в кластере выйдет из строя.

Keepalived решает две ключевые задачи:
1.  **Отказоустойчивость IP-адресов:** С помощью протокола **VRRP** он управляет "плавающим" виртуальным IP-адресом (VIP), который всегда назначен на работающий сервер.
2.  **Проверка состояния сервисов:** Он может отслеживать работоспособность локальных сервисов (например, Nginx, HAProxy) и инициировать переключение, если сервис перестал отвечать.

---

## Протокол VRRP (Virtual Router Redundancy Protocol)

В основе Keepalived лежит протокол VRRP. Вот как он работает в кластере из двух серверов:

1.  **Роли:** В кластере всегда есть один сервер в состоянии **`MASTER`** и один или несколько в состоянии **`BACKUP`**.
2.  **Виртуальный IP (VIP):** `MASTER`-сервер владеет виртуальным IP-адресом. Весь трафик от клиентов идет на этот VIP.
3.  **Анонсы:** `MASTER` периодически отправляет в сеть мультикаст-сообщения (VRRP advertisements), сообщая "я жив".
4.  **Механизм отказа:**
    -   Если `BACKUP`-сервер перестает получать анонсы от `MASTER` в течение заданного интервала, он считает, что `MASTER` вышел из строя.
    -   `BACKUP` немедленно переходит в состояние `MASTER` и "забирает" себе VIP-адрес, отправляя в сеть ARP-сообщение, чтобы обновить таблицы маршрутизации у клиентов и маршрутизаторов.
5.  **Восстановление:** Когда оригинальный `MASTER` возвращается в строй, он может либо вернуть себе VIP (если у него выше приоритет — `preempt`), либо остаться в `BACKUP` состоянии.

Этот процесс происходит автоматически и обычно занимает доли секунды, обеспечивая практически бесшовное переключение для клиентов.

## Основные компоненты конфигурации

Конфигурация Keepalived находится в файле `/etc/keepalived/keepalived.conf`.

### 1. `vrrp_instance`

Это главный блок, описывающий VRRP-инстанс.

```
vrrp_instance VI_1 {
    state MASTER          # Начальное состояние (MASTER или BACKUP)
    interface eth0        # Сетевой интерфейс для VRRP
    virtual_router_id 51  # Уникальный ID для группы VRRP (должен быть одинаковым на всех узлах)
    priority 101          # Приоритет (у MASTER должен быть выше, чем у BACKUP)

    advert_int 1          # Интервал отправки анонсов (в секундах)

    authentication {
        auth_type PASS
        auth_pass 1111
    }

    virtual_ipaddress {
        192.168.1.100/24    # Наш плавающий VIP-адрес
    }
}
```

### 2. `vrrp_script` (Проверка состояния сервисов)

Keepalived был бы бесполезен, если бы он отслеживал только доступность сервера, но не самого сервиса на нем. Для этого используются скрипты проверки.

-   **Логика:** Скрипт периодически выполняется. Если он завершается с ошибкой (код выхода не 0), Keepalived считает, что сервис неисправен, и снижает приоритет узла, что может инициировать переключение.

```
vrrp_script chk_haproxy {
    script "/usr/bin/killall -0 haproxy"   # Проверить, запущен ли процесс haproxy
    interval 2                            # Проверять каждые 2 секунды
    weight -20                            # Если проверка провалена, отнять 20 от приоритета
}
```

Этот скрипт нужно "привязать" к `vrrp_instance` с помощью директивы `track_script`.

```
vrrp_instance VI_1 {
    ...
    track_script {
        chk_haproxy
    }
    ...
}
```

### 3. `notify` скрипты

Keepalived может выполнять внешние скрипты при смене состояния (например, при переходе в `MASTER` или `BACKUP`). Это полезно для логирования, отправки уведомлений или выполнения специфических действий.

```
notify_master "/path/to/script.sh master"
notify_backup "/path/to/script.sh backup"
notify_fault  "/path/to/script.sh fault"
```

## Типовой сценарий использования: Отказоустойчивый HAProxy

Классическая связка для обеспечения высокой доступности веб-сервисов:

-   **Два сервера:** На обоих установлен HAProxy и Keepalived.
-   **Конфигурация:**
    -   HAProxy на обоих серверах настроен одинаково для балансировки трафика на бэкенд-серверы.
    -   Keepalived на одном сервере настроен как `MASTER`, на другом — как `BACKUP`.
    -   Настроен `vrrp_script` для проверки процесса `haproxy`.
-   **Как работает:**
    1.  Трафик идет на VIP, который находится на `MASTER`-сервере.
    2.  Если процесс `haproxy` на `MASTER`-сервере падает, скрипт проверки проваливается.
    3.  Keepalived на `MASTER` снижает свой приоритет, и `BACKUP`-сервер забирает VIP себе.
    4.  Трафик мгновенно перенаправляется на второй сервер с работающим HAProxy.
