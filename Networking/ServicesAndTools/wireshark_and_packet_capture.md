# Wireshark и анализ сетевого трафика

Wireshark — это мощный инструмент для анализа сетевого трафика, позволяющий захватывать и интерактивно просматривать содержимое пакетов. Он широко используется для диагностики сетевых проблем, анализа протоколов и обучения.

## Введение в Wireshark и захват пакетов

Захват пакетов в Linux и других операционных системах осуществляется через библиотеку **`libpcap` (Packet Capture library)**. Эта библиотека является основой для многих инструментов анализа трафика, включая `tcpdump`, `tshark` и сам Wireshark.

*   **`tcpdump`**: Консольная утилита для захвата и анализа сетевого трафика. Умеет сохранять дампы в файлы формата `.pcap`.
*   **`tshark`**: Консольная версия Wireshark, обладающая более широкими возможностями по сравнению с `tcpdump`, включая более детальное отображение информации и поддержку формата `.pcapng`.
*   **Wireshark**: Графический инструмент, который может как захватывать трафик в реальном времени, так и читать файлы дампов, созданные `tcpdump` или `tshark`.

### Как работает libpcap

`libpcap` работает по-разному на разных операционных системах. В Linux она использует семейство сокетов `AF_PACKET`, которое позволяет любому процессу получать доступ к пакетам в "сыром" виде, как они приходят на сетевой интерфейс, а также отправлять полностью сформированные вручную пакеты. Для работы `libpcap` обычно требуются привилегии `root`. В Linux и BSD можно предоставить эти привилегии обычному пользователю через POSIX capabilities или настройки SELinux/AppArmor. Например, в Fedora Wireshark часто получает необходимые права через контекст SELinux.

### libpcap в Windows

В Windows нет встроенного механизма захвата трафика, как в Unix-подобных системах. Для Wireshark и других инструментов в Windows используется сторонняя библиотека `Npcap` (ранее `WinPcap`), которая является драйвером, работающим через интерфейс NDIS.

## Захват пакетов в Linux и Promiscuous Mode

В Linux захват пакетов происходит через семейство сокетов **`AF_PACKET`**. Это позволяет любому процессу получать доступ к пакетам в том виде, в каком они пришли на сетевой интерфейс, и отправлять полностью сформированные вручную пакеты.

### Привилегии для захвата

Для захвата пакетов обычно требуются привилегии `root`. Однако в Linux и BSD существует возможность предоставить эти привилегии обычному пользователю:

*   **POSIX capabilities**: С помощью утилиты `getcap` можно посмотреть, какие возможности (`capabilities`) присвоены исполняемому файлу.
*   **SELinux**: В некоторых дистрибутивах (например, Fedora) права на захват трафика могут быть настроены через контекст SELinux, присвоенный исполняемому файлу Wireshark. Пользователь должен принадлежать к соответствующей группе (например, `wireshark`).

### Промискусный режим (Promiscuous Mode)

По умолчанию сетевой интерфейс обрабатывает только пакеты, предназначенные ему. Для захвата всего трафика, проходящего через интерфейс (например, в случае моста или транзитной машины), необходимо включить **промискусный режим**.

*   **Включение промискусного режима**:
    ```bash
    sudo ip link set dev <interface_name> promisc on
    ```
    Wireshark может включать промискусный режим самостоятельно при захвате, но `tcpdump` и `tshark` по умолчанию этого не делают.

*   **Пример создания моста для захвата**:
    ```bash
    sudo ip link add name br0 type bridge
    sudo ip link set dev br0 up
    sudo ip link set dev br0 promisc on
    ```
    Затем к мосту `br0` можно подключить виртуальные машины или другие интерфейсы.

## Инструменты для захвата и анализа трафика

### TShark

`tshark` — это консольная версия Wireshark, которая предоставляет более широкие возможности по сравнению с `tcpdump`, включая более детальный анализ протоколов и сохранение в формате `pcapng`.

*   **Захват и вывод детальной информации:**
    ```bash
    sudo tshark -i <interface_name>
    ```
*   **Захват и сохранение в файл (pcapng):**
    ```bash
    sudo tshark -i <interface_name> -w output.pcapng
    ```

### Форматы файлов дампов

*   **pcap (Packet Capture):** Старый, но широко используемый формат.
*   **pcapng (Packet Capture Next Generation):** Более новый формат, который поддерживает дополнительные метаданные, такие как имя интерфейса, комментарии к пакетам и т.д. `tshark` по умолчанию сохраняет в `pcapng`.

## Интерфейс Wireshark и основные функции

Интерфейс Wireshark традиционно состоит из трех основных частей:

*   **Верхняя панель** (Packet List Pane): Отображает список захваченных пакетов с краткой информацией (номер, время, источник, назначение, протокол, длина, информация).
*   **Средняя панель** (Packet Details Pane): Представляет собой древовидную структуру с детальной расшифровкой выбранного пакета по протоколам (Ethernet, IP, TCP/UDP, HTTP и т.д.).
*   **Нижняя панель** (Packet Bytes Pane): Показывает содержимое выбранного пакета в виде шестнадцатеричного дампа и его ASCII-представления. При выборе определенного поля в "Packet Details Pane", соответствующая часть в дампе подсвечивается, демонстрируя инкапсуляцию.

### Фильтры захвата (Capture Filters) и Фильтры отображения (Display Filters)

Это ключевое различие при работе с Wireshark:

*   **Фильтры захвата (`Capture Filters`)**: Применяются на уровне библиотеки `libpcap` **до** того, как пакеты будут записаны в дамп. Они используются для отбрасывания неинтересного трафика на высоконагруженных системах, чтобы избежать создания слишком больших файлов дампов. Синтаксис фильтров захвата совпадает с синтаксисом `tcpdump` (например, `host 192.168.1.1`, `port 80`).
*   **Фильтры отображения (`Display Filters`)**: Применяются **после** захвата трафика и позволяют фильтровать уже записанные пакеты в интерфейсе Wireshark. Они гораздо более гибкие и мощные, позволяют фильтровать по полям протоколов различных уровней (например, `ip.addr == 192.168.1.1`, `tcp.port == 80`, `vlan.id == 20`).

### Анализ VLAN-трафика

Wireshark позволяет легко анализировать трафик с тегами VLAN. Фильтр отображения `vlan.id == <ID>` позволяет выделить пакеты, принадлежащие конкретному VLAN.

### Контрольные суммы IP-пакетов (Offload)

Иногда в дампах можно увидеть пакеты с "битыми" контрольными суммами. Это не всегда означает реальную проблему. Если на сетевой карте включен **offload** (аппаратное вычисление контрольных сумм), то с точки зрения программного обеспечения контрольная сумма может отсутствовать, и пакеты будут выглядеть некорректно. Для точной диагностики offload можно временно отключить.

### Разрешение имен (Name Resolution)

Wireshark может разрешать IP-адреса в доменные имена и MAC-адреса в имена производителей.

*   **MAC-адреса**: Wireshark имеет встроенную базу данных префиксов MAC-адресов (OUI - Organizational Unit Identifier), что позволяет отображать производителя сетевой карты (например, `PC-SYSTEMS_TEC`). Эту опцию (`Resolve Physical Addresses`) можно отключить, чтобы видеть "сырые" MAC-адреса.
*   **DNS**: Wireshark может выполнять DNS-запросы для разрешения IP-адресов в доменные имена. Эту опцию (`Resolve Network Addresses`) рекомендуется отключать при анализе больших дампов, так как она может потреблять много ресурсов и времени.

### Структура пакета в Wireshark

Интерфейс Wireshark наглядно отображает многоуровневую структуру пакета:

1.  **Frame**: Информация о самом фрейме, как он был получен сетевой картой (размер, время захвата).
2.  **Ethernet**: Заголовок канального уровня (MAC-адреса источника и назначения, EtherType).
3.  **VLAN**: Если присутствует, информация о теге VLAN (ID, приоритет).
4.  **IP (IPv4/IPv6)**: Заголовок сетевого уровня (IP-адреса источника и назначения, протокол следующего уровня).
5.  **TCP/UDP**: Заголовок транспортного уровня (порты источника и назначения, флаги, контрольные суммы).
6.  **Application Layer**: Данные прикладного уровня (например, HTTP-заголовки, SSH-трафик).

При выделении любого заголовка в Wireshark, соответствующая часть пакета в шестнадцатеричном дампе подсвечивается.

Например, при анализе HTTP-трафика, можно увидеть следующую инкапсуляцию:
1.  На самом нижнем уровне (сетевые интерфейсы, например, Ethernet) передается весь кадр. В нем содержится заголовок Ethernet.
2.  Внутри данных Ethernet кадра находится заголовок IP.
3.  Внутри данных IP-пакета находится заголовок TCP (для HTTP).
4.  И, наконец, внутри данных TCP-сегмента содержится заголовок и данные прикладного уровня — HTTP-запрос или ответ, включая саму веб-страницу (HTML).

Выбирая различные уровни протоколов в "Packet Details Pane", можно наблюдать, как Wireshark подсвечивает соответствующие части пакета в "Packet Bytes Pane", наглядно демонстрируя, как данные одного протокола вкладываются в другой.

## Анализ TCP-соединений

Анализ TCP является одной из фундаментальных задач при диагностике сетей. Wireshark предоставляет мощные средства для детального разбора всего жизненного цикла TCP-соединения.

### Установка соединения (Three-way Handshake)

TCP-соединение устанавливается с помощью трехэтапного рукопожатия:

1.  **Клиент → Сервер: `SYN`**
    *   Клиент отправляет сегмент с установленным флагом `SYN` (Synchronize). Это запрос на установку соединения.
    *   В этом пакете клиент задает свой начальный `Sequence Number` (ISN). Wireshark для удобства отображает его как относительный номер `Seq=0`.
    *   В опциях TCP (`TCP Options`) этого сегмента передается важная информация:
        *   **MSS (Maximum Segment Size)**: Максимальный размер данных, который клиент может принять в одном TCP-сегменте.
        *   **Window Scale**: Множитель для поля `Window Size`, позволяющий использовать окна больше 65535 байт.
        *   **SACK Permitted**: Сообщает, что клиент поддерживает `Selective Acknowledgments` (выборочные подтверждения).

2.  **Сервер → Клиент: `SYN, ACK`**
    *   Сервер отвечает сегментом, в котором установлены флаги `SYN` и `ACK` (Acknowledgment).
    *   Флаг `SYN` означает, что сервер также синхронизирует свой `Sequence Number`.
    *   Флаг `ACK` подтверждает получение `SYN` от клиента. Поле `Acknowledgment Number` устанавливается в `клиентский ISN + 1`.

3.  **Клиент → Сервер: `ACK`**
    *   Клиент отправляет сегмент с флагом `ACK`, подтверждая получение `SYN` от сервера. `Acknowledgment Number` устанавливается в `серверный ISN + 1`.

После этого обмен данными может начинаться. Современные браузеры могут открывать несколько параллельных TCP-соединений к одному серверу для ускорения загрузки ресурсов.

### Передача данных

*   **PSH (Push) Flag**: Когда в TCP-сегменте с данными установлен флаг `PSH`, это является указанием для принимающей стороны немедленно передать эти данные приложению, не дожидаясь заполнения буфера. Это часто используется в конце логического блока данных, например, в конце HTTP-запроса.
*   **Сборка сегментов (Reassembly)**: Одно большое сообщение прикладного уровня (например, HTTP-ответ) часто разбивается на несколько TCP-сегментов. Wireshark автоматически определяет это и может показать полное сообщение. В интерфейсе он указывает, из каких сегментов было собрано сообщение ("TCP segment of a reassembled PDU"). Для просмотра полного потока данных удобнее всего использовать функцию **"Follow TCP Stream"** (`Analyze` -> `Follow` -> `TCP Stream`), которая убирает заголовки и показывает только данные прикладного уровня в том виде, в котором их "видит" приложение.

### Завершение соединения (Four-way Handshake)

Для корректного разрыва соединения каждая сторона должна независимо закрыть свою часть соединения:

1.  **Сторона 1 → Сторона 2: `FIN, ACK`**
    *   Сторона, инициирующая закрытие, отправляет сегмент с флагом `FIN` (Finish).
2.  **Сторона 2 → Сторона 1: `ACK`**
    *   Другая сторона подтверждает получение `FIN`.
3.  **Сторона 2 → Сторона 1: `FIN, ACK`**
    *   Когда вторая сторона готова к закрытию, она отправляет свой собственный `FIN`.
4.  **Сторона 1 → Сторона 2: `ACK`**
    *   Первая сторона подтверждает получение `FIN` от второй. Соединение считается полностью закрытым.

### Keep-Alive

Для поддержания долгоживущих, но неактивных соединений (например, `Connection: keep-alive` в HTTP), стороны могут обмениваться `TCP Keep-Alive` пакетами. Это пустые TCP-сегменты, которые просто подтверждают, что другая сторона все еще на связи, и сбрасывают таймеры неактивности на сетевом оборудовании.

## Анализ UDP-трафика

UDP (User Datagram Protocol) — это простой, легковесный протокол транспортного уровня без установки соединения. Его анализ в Wireshark прямолинеен из-за отсутствия сложной механики состояний, как в TCP.

### Структура UDP-дейтаграммы

Заголовок UDP чрезвычайно прост и состоит всего из 4 полей (8 байт):

*   **Source Port**: Порт отправителя. Часто это динамически назначаемый ("эфемерный") порт, который операционная система выделяет приложению-клиенту (например, `nslookup` или `dig`).
*   **Destination Port**: Порт получателя. Обычно это широко известный порт сервиса (например, порт `53` для DNS).
*   **Length**: Длина всей UDP-дейтаграммы в байтах (заголовок + данные).
*   **Checksum**: Контрольная сумма для проверки целостности заголовка и данных.

Основная функция UDP — это **демультиплексирование** трафика с помощью портов. Когда ОС получает UDP-дейтаграмму, она смотрит на `Destination Port` и передает данные соответствующему приложению, которое "слушает" этот порт. В ответной дейтаграмме порты меняются местами, что позволяет доставить ответ исходному приложению. Wireshark позволяет наглядно отследить это, показывая, как разные клиентские процессы (`nslookup`, `dig`) получают разные исходные порты, но отправляют запросы на один и тот же порт сервера.

Как и в случае с TCP, для UDP-пакетов доступна функция **"Follow UDP Stream"**, которая изолирует все дейтаграммы между двумя конечными точками (IP-адрес и порт).

## Анализ HTTP-трафика

Анализ HTTP-трафика (нешифрованного, передаваемого по порту 80) — одна из наиболее частых задач при работе с Wireshark. Для фильтрации используется фильтр отображения `http`.

### HTTP-запрос и ответ (GET и 200 OK)

*   **HTTP GET Request**: При запросе веб-страницы браузер отправляет текстовый запрос, который включает:
    *   **Стартовая строка**: `GET / HTTP/1.1` — метод, запрашиваемый ресурс и версия протокола.
    *   **Заголовки (Headers)**: Пары "ключ-значение", например:
        *   `Host`: Обязательный заголовок, указывающий доменное имя сервера.
        *   `User-Agent`: Информация о браузере клиента.
        *   `Connection: keep-alive`: Указывает на желание сохранить TCP-соединение открытым для последующих запросов.

*   **HTTP Response (200 OK)**: В ответ на успешный запрос сервер отправляет:
    *   **Строка состояния**: `HTTP/1.1 200 OK` — версия протокола, код состояния и его текстовое описание.
    *   **Заголовки (Headers)**:
        *   `Content-Type`: MIME-тип передаваемого содержимого (например, `text/html; charset=utf-8`).
        *   `Content-Length`: Размер тела ответа в байтах.
        *   `Server`: Информация о серверном ПО (например, `GitHub.com`).
    *   **Тело ответа (Body)**: Содержимое ресурса, например, HTML-код страницы.

### Кэширование в HTTP: Conditional GET и 304 Not Modified

Для экономии трафика браузеры используют кэширование. При повторном запросе ресурса браузер может отправить **условный запрос (Conditional GET)**, чтобы проверить, изменился ли ресурс на сервере.

*   **Заголовки для валидации**: В условном GET-запросе браузер отправляет один из заголовков, полученных от сервера при первом запросе:
    *   `If-None-Match`: Содержит значение `ETag` (Entity Tag) — уникальный идентификатор версии ресурса.
    *   `If-Modified-Since`: Содержит дату и время из заголовка `Last-Modified`.
*   **Ответ `304 Not Modified`**: Если ресурс на сервере не изменился (ETag совпадает или дата модификации не изменилась), сервер отвечает кодом `304 Not Modified`. Этот ответ не содержит тела, что значительно сокращает объем передаваемых данных. Браузер, получив такой ответ, отображает ресурс из своего кэша.

### Другие HTTP-взаимодействия

*   **`404 Not Found`**: При анализе трафика можно увидеть запросы к ресурсам, которые не существуют на сервере (например, браузеры часто автоматически запрашивают `/favicon.ico`). В ответ сервер вернет статус `404 Not Found`.
*   **"Follow TCP Stream"**: Эта функция особенно полезна для HTTP, так как она собирает воедино все запросы и ответы в рамках одного TCP-соединения и представляет их в виде единого, легко читаемого диалога.

## Анализ DNS-трафика

Wireshark является отличным инструментом для анализа работы протокола DNS. В отличие от HTTP, данные в DNS передаются в бинарном формате. Для генерации DNS-запросов удобно использовать утилиты командной строки, такие как `nslookup` или `dig`.

Для фильтрации DNS-пакетов в Wireshark используется фильтр отображения `dns`.

### Структура DNS-запроса и ответа

DNS-взаимодействие обычно происходит по протоколу UDP через порт 53.

*   **Transaction ID**: 16-битный идентификатор, который используется клиентом для сопоставления DNS-ответов с отправленными запросами. Wireshark автоматически связывает запросы и ответы с одинаковым Transaction ID.
*   **Flags**: Набор флагов, определяющих тип и параметры сообщения.
    *   **Query/Response (QR)**: Указывает, является ли пакет запросом (`0`) или ответом (`1`).
    *   **Recursion Desired (RD)**: В запросе клиент устанавливает этот флаг, чтобы попросить сервер выполнить рекурсивный запрос.
    *   **Recursion Available (RA)**: В ответе сервер устанавливает этот флаг, если он поддерживает рекурсию.
    *   **Authoritative Answer (AA)**: Важный флаг в ответе. Если он установлен (`1`), это означает, что ответ является **авторитетным**, то есть получен непосредственно от сервера, отвечающего за данную доменную зону. Если флаг сброшен (`0`), ответ **неавторитетный** и, скорее всего, взят из кэша промежуточного DNS-резолвера.
*   **Sections**: Тело DNS-сообщения разделено на секции:
    *   **Queries**: Секция запроса, содержащая доменное имя и тип запрашиваемой записи (например, `A` для IPv4-адреса).
    *   **Answers**: Секция ответа, содержащая запрошенную ресурсную запись (например, IP-адрес для `A`-записи), а также `TTL` (Time To Live), указывающее, как долго этот ответ можно кэшировать.

### Примеры анализа DNS в Wireshark

#### Авторитетный и неавторитетный ответ

При отправке запроса к локальному кэширующему DNS-серверу, в ответном пакете флаг `Authoritative Answer` обычно сброшен (`0`). Это говорит о том, что сервер вернул данные из своего кэша. Если же направить запрос напрямую к авторитетному DNS-серверу доменной зоны (например, `nslookup example.com ns1.example.com`), то в ответе флаг `Authoritative Answer` будет установлен (`1`).

#### Ответ с несколькими IP-адресами

Для крупных доменов, таких как `yandex.ru`, DNS-ответ часто содержит несколько `A`-записей. В Wireshark это будет видно в секции `Answers`, где будет перечислено несколько ресурсных записей с разными IP-адресами для одного и того же доменного имени. В заголовке DNS при этом поле `Answer RRs` (Resource Records) будет содержать число, соответствующее количеству ответов.

#### Запрос различных типов записей

С помощью таких утилит, как `nslookup` или `dig`, можно запрашивать различные типы DNS-записей, указывая нужный тип в параметрах (`nslookup -type=...`).

*   **`A` и `AAAA`**: Самые распространенные запросы на получение IPv4 и IPv6 адресов соответственно.
*   **`CNAME` (Canonical Name)**: Запрос на каноническое имя. Ответ показывает, что запрашиваемое имя является псевдонимом (alias) для другого, "канонического" имени.
*   **`MX` (Mail Exchanger)**: Запрос на получение почтовых серверов для домена. Ответ может содержать несколько `MX`-записей, каждая со своим **приоритетом (preference)**. Почтовые клиенты должны пытаться доставить почту сначала на сервер с наименьшим значением приоритета.
*   **`NS` (Name Server)**: Запрос на получение авторитетных серверов имен для доменной зоны. Ответ, как правило, содержит несколько `NS`-записей для обеспечения отказоустойчивости.

#### Обратный DNS-запрос (PTR)

Обратный DNS-запрос позволяет по IP-адресу определить соответствующее ему доменное имя.

*   **Формирование запроса**: Для этого используется специальный домен `in-addr.arpa` для IPv4. IP-адрес "переворачивается" и добавляется к этому домену. Например, для IP `77.88.44.55` будет сформирован запрос на `PTR`-запись для имени `55.44.88.77.in-addr.arpa`.
*   **Анализ в Wireshark**: В Wireshark будет виден DNS-запрос типа `PTR` к этому специальному доменному имени. В ответе, в секции `Answers`, будет содержаться `PTR`-запись, указывающая на доменное имя, связанное с данным IP-адресом.

## Дешифрование TLS-трафика

Wireshark способен дешифровать TLS-трафик, если у вас есть приватный ключ сервера.

*   **Настройка**: В `Preferences` -> `Protocols` -> `TLS` можно добавить приватный ключ, указав IP-адрес, порт и путь к файлу ключа.
*   **Пример**: На сайте Wireshark в разделе `sample_captures` можно найти примеры дампов с уже подготовленными ключами для дешифрования TLS.
*   **Альтернатива**: При отладке собственного кода или демонстрациях иногда проще временно отключить шифрование (использовать `null cipher`) в настройках сервера, чем заниматься дешифрованием в Wireshark.

## Дополнительные возможности Wireshark

*   **Комментарии к пакетам**: Можно добавлять произвольные комментарии к отдельным пакетам (`Packet Comments`), что очень удобно для совместной работы или документирования проблем. Пакеты с комментариями можно фильтровать (`frame.comment`) и даже раскрашивать в интерфейсе Wireshark.
*   **Генерация правил файрвола**: Wireshark имеет устаревшую функцию для генерации правил `iptables` (и других файрволов), но она не поддерживает `nftables` и может некорректно определять имена интерфейсов.
*   **Анализ туннельного трафика**: Wireshark корректно разбирает туннельные протоколы, такие как [GRE](../../Tunnels/gre.md). Он покажет внешний заголовок туннеля (например, IPv4 для GRE) и вложенный в него протокол (например, ICMP).
*   **Интерпретация проблемных пакетов**:
    *   **`Connection Refused`**: Часто проявляется как `SYN` пакет, на который приходит `RST-ACK` вместо `SYN-ACK`, указывая на то, что на целевом порту никто не слушает.
    *   **IP Spoofing**: Wireshark покажет пакеты с поддельными IP-адресами, но их интерпретация требует внимательного анализа и понимания ожидаемого трафика.
