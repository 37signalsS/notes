# gRPC — обзор фреймворка

## Определения

**gRPC (gRPC Remote Procedure Calls)** — это высокопроизводительный универсальный фреймворк для удалённого вызова процедур (RPC) с открытым исходным кодом. Он позволяет приложениям взаимодействовать друг с другом так же просто, как при вызове локальных методов, скрывая детали сетевого обмена.

gRPC является стандартом де-факто для межсервисного взаимодействия (East-West traffic) в микросервисных архитектурах и облачных решениях.

**Актуальность (2025–2026):** Фреймворк полностью поддерживает **HTTP/3 (QUIC)** в стабильных версиях большинства языков, что решает проблему блокировки очереди (HOL) на транспортном уровне. Также gRPC стал основным транспортом для **Model Context Protocol (MCP)**, обеспечивая стандартизированный интерфейс для взаимодействия между AI-агентами и инструментами.

## Основные концепции

### Protocol Buffers (Protobuf)

В основе gRPC лежит использование **Protocol Buffers** как языка описания интерфейсов (IDL) и механизма сериализации.

*   **Контрактный подход:** API строго описывается в `.proto` файлах. Это единственный источник истины (SSoT) для клиентской и серверной сторон.
*   **Бинарный формат:** Данные передаются в сжатом бинарном виде, что обеспечивает более высокую скорость обработки и меньшее потребление трафика по сравнению с JSON/XML.
*   **Генерация кода:** Специальные плагины (`protoc`) генерируют типизированные заглушки (stubs) для более чем 10 языков программирования, что исключает ошибки ручного написания DTO.

### Транспорт и протоколы

gRPC работает исключительно поверх современных версий HTTP, используя их продвинутые возможности:

*   **Мультиплексирование (HTTP/2 и HTTP/3):** Отправка множества запросов и ответов одновременно через одно соединение без ожидания завершения предыдущих.
*   **Двунаправленная потоковая передача:** Возможность одновременно отправлять и получать данные в рамках одного RPC-вызова.
*   **Сжатие заголовков:** Использование HPACK (HTTP/2) или QPACK (HTTP/3) для минимизации оверхеда на метаданные.
*   **QUIC (HTTP/3):** Позволяет избежать разрыва соединения при смене IP-адреса клиента (например, переход с Wi-Fi на 4G) благодаря Connection ID.

### Типы взаимодействия

1.  **Унарный (Unary):** Классический "запрос-ответ".
2.  **Потоковый серверный (Server Streaming):** Клиент отправляет запрос, сервер возвращает поток сообщений.
3.  **Потоковый клиентский (Client Streaming):** Клиент отправляет поток сообщений, сервер возвращает один ответ.
4.  **Двунаправленный потоковый (Bidirectional Streaming):** Обе стороны обмениваются независимыми потоками данных.

## Жизненный цикл вызова

### Статусы и ошибки
В отличие от HTTP с его кодами 2xx/4xx/5xx, gRPC использует собственный набор из 16 статус-кодов (например, `OK`, `NOT_FOUND`, `DEADLINE_EXCEEDED`, `UNAVAILABLE`). Ошибка передаётся в HTTP-трейлерах (Trailers) — специальных заголовках, отправляемых *после* тела сообщения.

### Метаданные (Metadata)
Метаданные (аналог HTTP-заголовков) позволяют передавать контекст, не являющийся частью бизнес-логики: токены аутентификации, ID запроса для трассировки и т.д.

### Deadlines и Timeouts
*   **Deadline:** Абсолютный момент времени, до которого должен быть получен ответ. gRPC автоматически пробрасывает дедлайны по всей цепочке микросервисов (Deadline Propagation), предотвращая каскадные зависания ресурсов.
*   **Timeout:** Относительное время ожидания.

## Практические сценарии

### Балансировка нагрузки
Из-за долгоживущих соединений HTTP/2 традиционная балансировка на уровне L4 (например, через `kube-proxy`) неэффективна — все запросы могут уйти на один под.
**Решения:**
*   **Client-side load balancing:** Клиент получает список всех IP подов и сам распределяет запросы между ними (например, библиотека gRPC-Go).
*   **Look-aside load balancing:** Внешний сервис (Control Plane) сообщает клиенту, куда отправлять трафик.
*   **Proxy load balancing:** Использование L7-балансировщиков (Envoy, Nginx, HAProxy), умеющих терминировать gRPC и перераспределять отдельные вызовы.

### Интеграция в инфраструктуру
*   **Kubernetes:** Нативная поддержка gRPC-проб (`livenessProbe`, `readinessProbe`) начиная с версии 1.24+.
*   **Service Mesh:** Istio и Linkerd используют gRPC для управления конфигурацией и телеметрией.
*   **API Gateway:** Маршрутизация на основе методов и сервисов gRPC через **[Gateway API](../../Kubernetes/Networking/gateway_api/definitions.md)** (ресурс `GRPCRoute`).

### gRPC-Web
Позволяет вызывать gRPC-сервисы напрямую из браузера (JavaScript/TypeScript). Поскольку браузеры не дают прямого доступа к HTTP/2 кадрам, требуется прокси-слой (обычно Envoy), который транслирует запросы gRPC-Web в стандартный gRPC.

## Дополнительная информация

### Безопасность
*   **TLS/mTLS:** Рекомендуемый стандарт для gRPC. Взаимная аутентификация (mTLS) обеспечивает проверку как сервера, так и клиента на уровне сертификатов.
*   **Интерцепторы (Interceptors):** Позволяют внедрять общую логику (логирование, метрики, авторизацию) до или после выполнения основного метода.

### Сравнение с альтернативами

| Параметр | gRPC | REST (JSON) | GraphQL |
| :--- | :--- | :--- | :--- |
| **Формат** | Protobuf (Бинарный) | JSON (Текст) | JSON (Текст) |
| **Производительность** | Высокая | Средняя | Средняя |
| **Типизация** | Строгая (IDL) | Слабая | Строгая (Schema) |
| **Стриминг** | Нативный (4 типа) | Ограничен (SSE) | Subscriptions |
| **Сценарий** | Микросервисы | Публичные API | Фронтенд-запросы |
