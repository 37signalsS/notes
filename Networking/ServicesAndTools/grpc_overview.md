# gRPC — обзор фреймворка

## Определения

**gRPC (gRPC Remote Procedure Calls)** — это современный высокопроизводительный фреймворк с открытым исходным кодом, изначально разработанный Google. Он реализует модель удалённого вызова процедур (RPC), позволяя клиентскому приложению напрямую вызывать методы на удалённом сервере так же просто, как если бы это был локальный объект.

gRPC является фундаментом для архитектуры микросервисов, обеспечивая эффективное взаимодействие между компонентами системы на разных языках программирования.

**Текущий статус (2025–2026):** Фреймворк активно внедряет поддержку протокола **HTTP/3 (QUIC)** для минимизации задержек и устранения блокировок очереди (head-of-line blocking). Также ведётся интеграция с **Model Context Protocol (MCP)** для стандартизации взаимодействия с AI-моделями.

## Основные концепции

### Protocol Buffers (Protobuf)

Основным механизмом сериализации и описания интерфейсов (IDL) в gRPC является **Protocol Buffers**.

- **Контракт в `.proto` файлах:** API описывается в виде сервисов и сообщений. Этот файл служит единым источником истины для всех сторон взаимодействия.
- **Бинарная сериализация:** Данные передаются в компактном бинарном формате, что значительно быстрее и экономнее текстового JSON.
- **Строгая типизация:** Обязательное определение типов данных на этапе проектирования минимизирует ошибки в рантайме.
- **Генерация кода:** На основе `.proto` файлов автоматически создаются типизированные клиентские библиотеки и серверные интерфейсы для большинства популярных языков (Go, Python, Java, C++, Rust и др.).

**Пример описания сервиса:**

```protobuf
syntax = "proto3";

package greeter;

service Greeter {
  // Метод SayHello принимает сообщение HelloRequest и возвращает HelloReply
  rpc SayHello (HelloRequest) returns (HelloReply);
}

message HelloRequest {
  string name = 1;
}

message HelloReply {
  string message = 1;
}
```

### Транспорт: HTTP/2 и HTTP/3

gRPC использует преимущества современных транспортных протоколов:

- **Мультиплексирование (HTTP/2):** Позволяет отправлять множество запросов и ответов параллельно через одно TCP-соединение.
- **Сжатие заголовков (HPACK/QPACK):** Уменьшает накладные расходы на передачу метаданных.
- **Двунаправленный стриминг:** Поддержка потоковой передачи данных в обе стороны в рамках одного вызова.
- **QUIC (HTTP/3):** Экспериментальная поддержка HTTP/3 позволяет избежать HOL-blocking на транспортном уровне и обеспечивает быструю миграцию соединений между сетями.

### Типы потоковой передачи (Streaming)

gRPC поддерживает четыре модели взаимодействия:

1. **Унарный RPC (Unary):** Классический цикл «запрос-ответ».
2. **Потоковая передача с сервера (Server Streaming):** Один запрос клиента — поток ответов сервера (например, передача логов в реальном времени).
3. **Потоковая передача от клиента (Client Streaming):** Поток сообщений клиента — один финальный ответ сервера (например, загрузка большого файла частями).
4. **Двунаправленный стриминг (Bidirectional):** Клиент и сервер отправляют потоки данных независимо и одновременно (например, чаты или игровые механики).

## Практические сценарии

### Основные области применения

- **Межсервисное взаимодействие:** Стандарт де-факто для внутренней связи микросервисов благодаря производительности и типизации.
- **Мобильные приложения:** Экономия трафика и заряда батареи за счёт бинарного формата.
- **Real-time сервисы:** Использование стриминга для чатов, биржевых котировок и IoT-мониторинга.
- **Observability:** Протокол OTLP в [OpenTelemetry](../../OpenTelemetry/otlp_protocol.md) использует gRPC для эффективной передачи трасс и метрик.
- **Инфраструктурные компоненты:**
  - [Docker](../../Docker/docker_overview.md) использует gRPC для связи `dockerd` с `containerd`.
  - Kubernetes использует gRPC в CRI (Container Runtime Interface) и для проверок состояния в [Consul](../../Consul/consul_health_checks.md).

### gRPC-Web и работа в браузере

Поскольку браузеры не имеют полного доступа к HTTP/2 кадрам, для работы веб-приложений используется **gRPC-Web**.

- **Проксирование:** Требуется промежуточный слой (например, [Envoy](../../Kubernetes/Networking/gateway_api/envoy_gateway.md)), который транслирует запросы от браузера в стандартный gRPC.
- **Ограничения:** В браузерной среде недоступен полноценный клиентский и двунаправленный стриминг.

## Дополнительная информация

### Безопасность

- **mTLS (Mutual TLS):** Основной метод обеспечения безопасности, при котором и клиент, и сервер проверяют сертификаты друг друга.
- **Интерцепторы (Interceptors):** Механизм промежуточного ПО для реализации аутентификации (JWT), логирования и мониторинга.
- **Deadlines/Timeouts:** Обязательная практика в gRPC для предотвращения зависания ресурсов при медленных ответах.

### Сравнение gRPC и REST

| Характеристика | gRPC | REST |
| :--- | :--- | :--- |
| **Протокол** | HTTP/2 / HTTP/3 | HTTP/1.1 / HTTP/2 |
| **Формат данных** | Protobuf (бинарный) | JSON / XML (текстовый) |
| **Типизация** | Строгая (IDL) | Слабая (OpenAPI/Swagger опционально) |
| **Стриминг** | Нативный, 4 типа | Ограничен (SSE, WebSocket) |
| **Браузеры** | Через прокси (gRPC-Web) | Нативная поддержка |
